# ⚠️ 주의점 총정리와 MPMC 의 고민

> 코드를 다 짜 본 뒤에 읽는 노트다. 앞의 레벨들이 "어떻게 만드나"였다면 여기는
> **"무엇이 실제로 터지나"** 와 **"생산자가 둘 이상이면 어떻게 되나"** 다.
> 면접의 후반 라운드 — 시스템 설계와 디버깅 — 는 대부분 이 노트의 내용에서 나온다.

# 파트 1. 실무에서 실제로 터지는 함정 12가지

## 1. size 가 2의 거듭제곱이 아닌데 마스킹을 쓴다

```c
rb2_init(&q, buf, 1000);   /* mask = 999 = 0b1111100111 💀 */
```

`& 999` 는 마스킹이 아니라 **비트를 뭉개는 연산**이다. 인덱스 3이 3으로, 4가 4로 가지만
1000이 0이 아니라 **968** 이 된다. 데이터가 엉뚱한 곳에 쓰이고 덮어써진다.

> **방어**: `init` 에서 `is_pow2` 를 검사해 **false 를 리턴**하라. 그리고 컴파일 타임에 잡아라.
> ```c
> _Static_assert((SIZE & (SIZE - 1)) == 0, "size must be power of two");
> ```
> 런타임 검사보다 `_Static_assert` 가 100배 낫다. **빌드가 깨지면 절대 출하되지 않는다.**

## 2. `n & (n-1) == 0` 에서 `n != 0` 을 빼먹는다

`0 & 0xFFFFFFFF == 0` 이라 **0이 2의 거듭제곱으로 통과**한다. `mask = 0xFFFFFFFF` →
`buf[idx & 0xFFFFFFFF]` → 아무 주소나 쓴다. 힙/스택이 통째로 오염된다.

## 3. 인덱스를 `int` 로 선언한다

- 부호 있는 오버플로는 **UB**. `-O2` 에서 컴파일러가 "오버플로는 없다"고 가정해 검사를 지워버린다.
- `(head - tail) % size` 가 **음수**를 리턴한다 (`-4 % 8 == -4`).
- `%` 를 `&` 로 바꾸는 최적화가 **안 된다**.

> **규칙: 인덱스는 무조건 `uint32_t` (또는 `size_t`).**

## 4. 8비트 MCU 에서 16비트 인덱스를 원자적이라고 가정한다

AVR 에서 `uint16_t head` 는 **2번의 8비트 접근**이다. 중간에 인터럽트가 들어오면
상위 바이트는 새 값, 하위 바이트는 옛 값인 **찢어진(torn) 값**을 읽는다.

> 8비트 MCU 에서는 (a) 인덱스를 `uint8_t` 로 (버퍼 ≤ 256), 또는 (b) 인덱스 접근을
> 크리티컬 섹션으로 감싼다. `atomic_is_lock_free()` 로 확인할 수 있다.

## 5. 같은 링에 ISR 이 둘 이상 쓴다

```c
void USART1_IRQHandler(void) { rb4_push(&rx, byte); }
void USART2_IRQHandler(void) { rb4_push(&rx, byte); }   /* 💀 SPSC 가 아니다 */
```

**SPSC 의 전제가 깨진다.** 우선순위가 다르면 높은 쪽이 낮은 쪽의 `push` 중간에 선점해
`head` 를 동시에 갱신한다. 데이터가 겹쳐 쓰이고 조용히 사라진다.

> **방어**: 링을 ISR 마다 하나씩 만든다. 정말 하나로 합쳐야 하면 파트 2(MPMC)로.
> 또는 두 ISR 의 **우선순위를 같게** 설정하면 서로 선점하지 못하므로 사실상 직렬화된다
> (Cortex-M 에서 같은 우선순위 인터럽트는 중첩되지 않는다). **싸고 효과적인 트릭이다.**

## 6. 데이터보다 인덱스를 먼저 공개한다

[레벨 4 §5](05_level4_spsc.html) 참조. **단일 스레드 테스트로는 절대 안 잡힌다.**

## 7. `volatile` 로 충분하다고 믿는다

[레벨 4 §3](05_level4_spsc.html) 참조. 단일 코어 M0/M3/M4 에서는 우연히 동작하고,
M7·Cortex-A·LTO·컴파일러 교체에서 깨진다.

## 8. 크리티컬 섹션에서 `__enable_irq()` 로 복구한다

```c
__disable_irq();
...
__enable_irq();     /* 💀 원래 꺼져 있었다면? 켜버린다 */
```

중첩 크리티컬 섹션에서 안쪽이 끝날 때 바깥의 보호가 풀린다. 반드시 저장/복구:

```c
uint32_t pri = __get_PRIMASK();
__disable_irq();
...
__set_PRIMASK(pri);
```

## 9. 버퍼 크기를 "충분히 크게" 잡고 끝낸다

크기 산정은 **계산**이다. 추측이 아니다.

```
 필요 크기 ≥ (최대 생산 속도 − 최소 소비 속도) × 최악 소비 지연
```

예: 1Mbps UART = 125KB/s. 소비자가 최악 10ms 늦는다면 → **1250바이트 필요** → 2048 할당.
"최악 소비 지연"은 다른 인터럽트, 플래시 쓰기(수십 ms 동안 인터럽트 차단!), RTOS 스케줄링
지터를 전부 포함한 값이다.

> **플래시 쓰기가 링버퍼를 죽이는 고전적 사고다.** 내장 플래시 erase 는 수십~수백 ms 동안
> CPU 를 멈추거나 인터럽트를 막는다. 그동안 UART 링이 넘친다.

## 10. 오버플로를 조용히 무시한다

```c
if (rb_full(&q)) return;   /* 💀 아무도 모른다 */
```

**유실은 일어난다.** 문제는 "몇 개 유실됐는지 모른다"는 것이다.
`dropped` 카운터를 두고 부팅 진단이나 텔레메트리에 반드시 노출하라.
필드에서 올라온 버그 리포트를 해결하는 건 결국 이 숫자다.

## 11. 링버퍼에 포인터를 넣고 수명을 관리하지 않는다

```c
rbg_push(&q, &msg);   /* msg 가 스택 변수라면? */
```

- **구조체를 값으로** 넣으면 안전 (복사됨).
- **포인터를 넣으면** 소비자가 꺼낼 때까지 그 메모리가 살아 있어야 한다.
  → 정적 풀(pool allocator)에서 할당하고 소비자가 반납하는 구조가 필요하다.
- 큰 데이터라 복사가 아까우면 **포인터 + 풀** 또는 [zero-copy](06_level5_overwrite_zerocopy.html)로 간다.

## 12. 디버거로 링버퍼를 들여다보며 "왜 값이 이상하지" 한다

- **pop 은 데이터를 지우지 않는다.** `tail` 뒤쪽의 낡은 값은 정상이다.
- `head`/`tail` 이 free-running 이면 디버거에 보이는 값(`4294967290` 같은)은 배열 인덱스가
  아니다. `head & mask` 로 봐야 한다.
- 최적화 빌드에서는 atomic 변수도 레지스터에 있을 수 있어 메모리 값이 낡아 보인다.

# 파트 2. MPMC — 생산자/소비자가 둘 이상이면

## 13. 먼저: 정말 MPMC 가 필요한가?

**대부분은 아니다.** MPMC 는 임베디드에서 거의 항상 **설계 실수의 징후**다. 먼저 물어라.

| 상황 | 더 나은 해법 |
|---|---|
| ISR 3개가 같은 로그 링에 쓴다 | **ISR 마다 링 하나** + 소비자가 라운드로빈으로 드레인 |
| 태스크 5개가 같은 TX 큐에 쓴다 | **태스크마다 링** + TX 태스크가 우선순위대로 뽑아 쓰기 |
| 소비자 여러 개가 같은 데이터를 본다 | MPMC 가 아니라 **브로드캐스트/pub-sub**. 각 구독자가 자기 `tail` 을 가진다 |
| 워커 풀이 작업을 나눠 가진다 | 여기가 **진짜 MPMC** 가 맞는 거의 유일한 경우 (보통 Linux 쪽) |
| 그냥 여러 태스크가 큐를 쓴다 | **RTOS 큐** (`xQueueSend`) — 내부적으로 뮤텍스/크리티컬 섹션. 충분히 빠르다 |

> **면접 답변**: *"먼저 정말 MPMC 가 필요한지 되묻겠습니다. 생산자별로 SPSC 링을 나누면
> 무락을 유지하면서 문제가 사라지는 경우가 대부분입니다. 링이 N개면 메모리는 늘지만
> 각각이 독립적이라 캐시 경합도 없고, 어느 생산자가 넘쳤는지도 따로 알 수 있습니다.
> 정말 하나의 큐가 필요하다면..."* (아래로 이어간다)

## 14. MPMC 가 왜 어려운가 — SPSC 논증이 어디서 무너지나

SPSC 는 이 한 줄에 기대고 있었다.

> `head` 는 생산자 **한 명만** store 한다.

생산자가 둘이면:

```
 시각   생산자 A                  생산자 B                 결과
 ────   ─────────                 ─────────                ────
  t0    h = head (= 5)
  t1                              h = head (= 5)
  t2    buf[5] = 'A'
  t3                              buf[5] = 'B'            💥 A 의 데이터가 사라짐
  t4    head = 6
  t5                              head = 6                💥 한 칸만 전진
```

**자리 예약**과 **데이터 쓰기**가 원자적이지 않다는 게 핵심이다.

## 15. 시도 ① — CAS 로 자리만 예약한다

```c
uint32_t h;
do {
    h = atomic_load(&q->head);
    if (h - atomic_load(&q->tail) == q->size) return false;   /* full */
} while (!atomic_compare_exchange_weak(&q->head, &h, h + 1));  /* 내 자리를 찜한다 */

q->buf[h & q->mask] = v;   /* ★ 여기가 문제 */
```

CAS 덕분에 **두 생산자가 같은 슬롯을 받지는 않는다.** 하지만 새 문제가 생긴다.

> **생산자 A 가 슬롯 5를 예약했지만 아직 안 썼는데, 생산자 B 가 슬롯 6을 예약하고 먼저 다 썼다.
> `head` 는 이미 7이다. 소비자는 "슬롯 5,6에 데이터가 있다"고 믿고 슬롯 5를 읽는다 → 쓰레기.**

`head` 가 "예약된 곳"과 "완성된 곳" 두 가지를 동시에 의미할 수 없기 때문이다.

### 부분 해법: 인덱스를 2개로 (`reserved` / `committed`)

생산자가 `reserved` 를 CAS 로 올리고, 다 쓰면 `committed` 를 올린다. 하지만 **`committed` 는
순서대로 올라가야 한다** — A 가 느리면 B 는 A 를 기다려야 한다. 결국 **일부 직렬화**가 생기고,
lock-free 라기보다 obstruction-free 에 가까워진다.

## 16. 시도 ② — Vyukov MPMC 큐 (슬롯별 시퀀스 번호) ⭐

실무에서 가장 널리 쓰이는 **정답**이다. 아이디어: **슬롯마다 자기 상태를 들고 있게 한다.**

```c
typedef struct {
    atomic_uint_fast32_t seq;   /* 이 슬롯의 "세대" */
    T                    data;
} cell_t;

typedef struct {
    cell_t  *buf;
    uint32_t mask;
    alignas(64) atomic_uint_fast32_t enqueue_pos;   /* 캐시라인 분리 */
    alignas(64) atomic_uint_fast32_t dequeue_pos;
} mpmc_t;

/* 초기화: buf[i].seq = i */
```

**규칙 두 줄이 전부다.**

| 슬롯 상태 | `seq` 값 | 의미 |
|---|---|---|
| 쓸 수 있음 | `seq == pos` | 이 세대에 아직 아무도 안 썼다 |
| 읽을 수 있음 | `seq == pos + 1` | 데이터가 완성되어 공개됐다 |
| 아직 아님 | 그 외 | 다른 생산자/소비자가 처리 중 → 재시도 |

```c
bool mpmc_push(mpmc_t *q, T v) {
    cell_t *c; uint32_t pos = atomic_load_explicit(&q->enqueue_pos, memory_order_relaxed);
    for (;;) {
        c = &q->buf[pos & q->mask];
        uint32_t seq = atomic_load_explicit(&c->seq, memory_order_acquire);
        intptr_t diff = (intptr_t)seq - (intptr_t)pos;
        if (diff == 0) {                                  /* 쓸 수 있다 */
            if (atomic_compare_exchange_weak_explicit(&q->enqueue_pos, &pos, pos + 1,
                    memory_order_relaxed, memory_order_relaxed)) break;   /* 내 자리 확보 */
        } else if (diff < 0) {
            return false;                                 /* 가득 참 */
        } else {
            pos = atomic_load_explicit(&q->enqueue_pos, memory_order_relaxed);  /* 남이 가져감 */
        }
    }
    c->data = v;
    atomic_store_explicit(&c->seq, pos + 1, memory_order_release);   /* ★ 여기서 공개 */
    return true;
}
```

**§15의 문제가 해결되는 이유**: 데이터의 유효성이 **전역 `head` 가 아니라 슬롯 자신의 `seq`** 로
표현된다. 생산자 A 가 느리면 슬롯 5의 `seq` 가 안 올라가고, 소비자는 슬롯 5에서 **그냥 기다린다.**
슬롯 6이 먼저 완성되어도 소비자가 잘못 읽을 길이 없다.

**성질**:
- 진짜 lock-free (wait-free 는 아니다 — 재시도 루프가 있다)
- **bounded**: 고정 크기, 동적 할당 없음 → **임베디드에 적합**
- 슬롯마다 `seq` 필드가 붙어 메모리가 늘어난다 (원소당 4~8바이트)
- CAS 가 실패하면 재시도 → 경합이 심하면 성능이 떨어진다

> 출처: Dmitry Vyukov, "Bounded MPMC queue". `moodycamel::ConcurrentQueue`, Rust `crossbeam`,
> DPDK 의 `rte_ring` 이 전부 이 계열이다.

## 17. ABA 문제 — 왜 인덱스 방식이 포인터 방식보다 안전한가

포인터를 CAS 하는 lock-free 리스트에서는 **ABA 문제**가 있다.

```
 스레드 1: head 가 A 임을 읽는다 → CAS(A → B) 를 준비
 스레드 2: A 를 pop, X 를 pop, A 를 다시 push  (head 는 A → X → A)
 스레드 1: CAS 를 실행 → head 가 여전히 A 이므로 성공 💥 (그 사이 리스트가 완전히 달라졌다)
```

**링버퍼는 이 문제에서 상대적으로 자유롭다.** 인덱스가 **단조 증가**하기 때문이다.
`pos` 가 같은 값으로 돌아오려면 큐를 **2^32 번** 돌아야 한다. 실질적으로 불가능하고,
Vyukov 큐는 `seq` 가 세대를 구분하므로 더 안전하다.

> 일반적 해법은 **태그 붙인 포인터**(포인터 + 카운터를 128비트 CAS 로)다. Cortex-M 에는
> 그런 명령이 없다. **임베디드에서 lock-free 리스트를 직접 만들지 마라.**
> 링버퍼(bounded, 인덱스 기반)로 해결되는 문제로 바꿔라.

## 18. MPSC / SPMC — 반쪽만 여러 개일 때

| 형태 | 난이도 | 방법 |
|---|---|---|
| **SPSC** | 쉬움 | 레벨 4. CAS 조차 필요 없다 |
| **MPSC** (ISR 여럿 → 태스크 하나) | 중간 | 생산자 쪽만 CAS 로 `head` 예약. 여전히 §15 문제가 있어 슬롯 `seq` 나 per-producer 링이 필요 |
| **SPMC** (태스크 하나 → 워커 여럿) | 중간 | 소비자 쪽만 CAS. 작업 분배(work stealing)에서 쓴다 |
| **MPMC** | 어려움 | Vyukov 시퀀스 링 |

> **임베디드에서 MPSC 가 필요하면**: 생산자마다 SPSC 링을 두고 소비자가 라운드로빈으로 드레인하는
> 쪽이 거의 항상 낫다. 코드가 단순하고, 어느 생산자가 넘쳤는지도 개별로 알 수 있으며,
> 우선순위별 드레인 정책도 자연스럽게 얹힌다.

## 19. 그냥 락을 쓰는 게 나은 경우

**lock-free 는 목적이 아니라 수단이다.** 아래라면 락이 정답이다.

- 생산자·소비자가 모두 **태스크**(ISR 아님)이고 RTOS 가 있다 → `xQueueSend` 가 충분히 빠르고 훨씬 안전하다
- 큐 연산 빈도가 **초당 수천 회 이하**다 → 락 오버헤드가 측정되지 않는다
- 팀에 메모리 모델을 아는 사람이 나뿐이다 → **유지보수 불가능한 코드는 버그다**
- 우선순위 상속(priority inheritance) 뮤텍스가 있으면 우선순위 역전도 해결된다

> **면접에서 이 말을 할 수 있으면 시니어로 보인다**: *"lock-free 는 ISR 이 관여할 때처럼
> 락을 쓸 수 없는 경우에 씁니다. 태스크끼리라면 RTOS 큐가 더 안전하고 충분히 빠릅니다.
> 무락 코드는 리뷰와 디버깅 비용이 훨씬 크기 때문에, 필요해서 쓰는 것이지 빨라서 쓰는 게 아닙니다."*

# 파트 3. 테스트와 검증 전략

동시성 코드는 "값이 맞는지"로 테스트할 수 없다. 아래 네 가지로 한다.

### ① 불변식(invariant)을 검사한다

```
 생산한 총량 == 소비한 총량 + 남은 양 + 드롭된 양
 0 <= used <= size
 tail 은 항상 레코드 경계에 있다 (레코드 링의 경우)
```

매 연산 뒤에 디버그 빌드에서 `assert` 로 확인한다. `L4_spsc.c` Q5, `L5a_overwrite.c` Q6 이 이 방식이다.

### ② 인덱스 랩 지점을 강제로 만든다

```c
q.head = q.tail = 0xFFFFFFFCu;   /* 9.5시간을 기다리는 대신 */
```

`L2_mask.c` Q5 가 이걸 한다. **실제 기기에서는 며칠 만에 한 번 오는 경로**를 1초 만에 테스트한다.

### ③ 호스트에서 스트레스 테스트를 돌린다

```sh
# 실제 스레드로 수백만 회, sanitizer 를 켜고
cc -std=c11 -O2 -fsanitize=thread stress.c -lpthread && ./a.out
```

- **ThreadSanitizer(TSan)** 가 데이터 레이스를 잡아준다. `volatile` 로 짠 코드는 여기서 걸린다.
- MCU 코드를 호스트에서 돌릴 수 있게 **하드웨어 의존성을 분리해 두는 설계**가 여기서 보상받는다.
- 다만 TSan 은 x86 메모리 모델 위에서 도는 것이라 **ARM 에서만 나는 재배치 버그는 못 잡는다.**
  그래서 ①의 불변식 검사를 실기에서도 돌린다.

### ④ 실기에서 카운터를 관찰한다

`dropped`, `overwritten`, `max_used`(수위 최고점)를 텔레메트리에 실어 보낸다.
`max_used` 가 `size` 에 근접한다면 **크기 산정이 틀린 것**이고, 언젠가 반드시 넘친다.

# 파트 4. 한 장 요약 — 상황별 선택표

| 상황 | 레벨 | 추가로 필요한 것 |
|---|---|---|
| 단일 스레드, 크기가 2의 거듭제곱 아님 | **L1** (count) | — |
| 단일 스레드, 성능 중요 | **L2** (mask) | — |
| ISR → 메인, 바이트 스트림 | **L2 + L4** | drop 카운터 |
| ISR → 메인, 고정 크기 메시지 | **L3(매크로) + L4** | all-or-nothing |
| 로그 (크래시 직전 보존) | **L5a** | 레코드 단위 드롭, 크리티컬 섹션 또는 블랙박스 |
| 고속 UART/SPI DMA | **L5b** | 캐시 clean/invalidate, 32B 정렬, DMA 접근 가능 영역 |
| 여러 ISR 이 생산 | **L4 × N개 링** | 라운드로빈 드레인 (MPMC 피하기) |
| 태스크끼리, RTOS 있음 | **RTOS 큐** | 무락 불필요 |
| 워커 풀 (Linux) | **Vyukov MPMC** | `alignas(64)`, 스트레스 테스트 |

## 20. 체크

- [ ] `_Static_assert` 로 2의 거듭제곱을 **컴파일 타임에** 강제하는 코드를 쓸 수 있다
- [ ] 8비트 MCU 에서 16비트 인덱스가 왜 위험한지 말할 수 있다
- [ ] 두 ISR 이 같은 링에 쓸 때의 해법 2가지(링 분리 / 우선순위 동일화)를 안다
- [ ] 버퍼 크기를 **계산식**으로 산정할 수 있다 (생산속도·소비지연·플래시 쓰기)
- [ ] 링버퍼에 포인터를 넣을 때의 수명 관리 문제를 설명할 수 있다
- [ ] MPMC 가 필요해 보일 때 **먼저 물어야 할 것**이 무엇인지 안다
- [ ] 단순 CAS 로 `head` 만 예약하면 왜 부족한지 타임라인으로 설명할 수 있다
- [ ] Vyukov 큐의 `seq == pos` / `seq == pos+1` 규칙을 설명할 수 있다
- [ ] 링버퍼가 ABA 문제에서 상대적으로 자유로운 이유를 안다
- [ ] "lock-free 를 쓰지 말아야 할 때"를 세 가지 댈 수 있다
- [ ] 불변식 검사 / 랩 강제 / TSan / 실기 카운터 — 네 가지 검증 전략을 안다
- [ ] 상황별 선택표를 보지 않고 세 가지 상황에 답할 수 있다
