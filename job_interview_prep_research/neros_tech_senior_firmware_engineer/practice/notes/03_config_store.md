# 03. 설정 저장소 / 파라미터 스토어 (Config Store) — Q1–Q6 🗄️

> Neros "Senior Firmware Engineer, Platform" JD의 한 줄:
> *"design and maintain the interfaces other teams build on, keeping them **stable** as the platform evolves underneath."*
> config store는 그 문장이 가장 아프게 적용되는 곳이다. **여러 팀·여러 기체(airframe)가 같은
> 스토어를 쓰고, FW는 계속 올라간다(OTA).** 파라미터 하나 추가했다고 다른 기체가 부팅 못 하면
> 그건 platform 팀 장애다.
>
> 빌드: `cc -std=c11 -Wall -Wextra -O0 -g solutions/03_config_store.c -o /tmp/n03 && /tmp/n03`
> (또는 `make prob N=03_config_store`)

---

## 왜 이 주제가 Neros에서 중요한가

- **하나의 플랫폼, 여러 제품.** 기체마다 다른 파라미터 집합 + 공통 파라미터. 스키마가
  기체별로 갈라지면 공통 런타임이 유지될 수 없다 → **key-value 인터페이스**로 고정.
- **FW는 항상 올라가고, 가끔 내려간다(rollback).** 신버전이 쓴 config를 구버전이 읽고,
  구버전이 쓴 config를 신버전이 읽어도 죽으면 안 된다 → forward + backward compatibility 둘 다.
- **전원은 언제든 끊긴다.** 배터리 분리, 브라운아웃, 충돌. 쓰다 만 config로 벽돌이 되면 안 된다
  → A/B 슬롯 + CRC + 원자적 커밋.
- **파라미터는 안전 장치이기도 하다.** failsafe 고도, geofence, 모터 한계. "값이 없으면
  0으로 시작" 같은 처리는 사고로 직결 → 항상 **명시적 기본값(fallback)**.

## 개념 정리

### 1) 왜 fixed struct를 flash에 통째로 쓰면 안 되는가

```c
// 절대 하지 말 것
fwrite(&cfg, sizeof cfg, 1, f);      // 또는 flash_write(addr, &cfg, sizeof cfg)
```

| 문제 | 왜 |
|------|-----|
| **padding** | 컴파일러/버전/최적화에 따라 구조체 구멍이 달라진다. `sizeof`가 바뀌면 전부 깨짐 |
| **정렬(alignment)** | 일부 MCU는 비정렬 word 접근에서 hard fault |
| **엔디안** | MCU(LE)와 Linux 툴(빌드 머신)이 같은 이미지를 읽는다면 반드시 명시 |
| **필드 추가** | 구조체 중간에 필드 하나 넣으면 기존 이미지 전체가 의미가 달라짐 |
| **부분 해석 불가** | 모르는 필드를 "건너뛸" 방법이 없다 |

→ 해법: **바이트 단위 직렬화(serialization)**. `wr_u32le/rd_u32le`로 한 필드씩 읽고 쓴다.
구조체는 *RAM에서의 표현*, 플래시에 있는 건 *wire format*. 이 둘을 분리하는 게 전부다.

### 2) TLV(key-value)가 fixed struct보다 나은 이유

레코드 = `[u16 id LE][u8 len][payload]`

- **모르는 id를 건너뛸 수 있다** (len을 알기 때문). 이게 forward compatibility의 전부.
- **부분 집합이 유효하다.** 기체 A는 20개, 기체 B는 35개 파라미터 → 같은 코드, 같은 포맷.
- **필드 추가가 append.** 기존 레코드 위치가 안 바뀐다.
- 대가: 레코드당 3바이트 오버헤드, 검색이 O(n) 선형 스캔. (수십~수백 개 파라미터 규모면 무의미)

### 3) 호환성 규칙 — 외워둘 것

| 방향 | 의미 | 규칙 |
|------|------|------|
| **Backward compat** | 신 코드가 **구** 데이터를 읽음 | 없는 필드는 **기본값**으로 채운다 (Q4 v1→v3) |
| **Forward compat** | 구 코드가 **신** 데이터를 읽음 | 모르는 id/꼬리 바이트는 **무시**하고 계속 진행 (Q2/Q3/Q4) |

**Robustness principle**: "보낼 땐 엄격하게, 받을 땐 관대하게."
단, 관대함 ≠ 무방비. **길이/CRC/size는 엄격하게 검사**하고, *모른다는 사실 자체*에만 관대하다.

- 절대 금지: **id 재사용**(retire만 하고 번호는 영구 소각), **enum 값 재배정**, **필드 의미 변경**.
- 필드 삭제 → 실제로는 "deprecated 표시 + 읽으면 무시". id는 되돌려 쓰지 않는다.
- 가능하면 **모르는 TLV를 보존(preserve)해서 다시 써준다** → 구버전이 저장해도 신버전 파라미터가
  날아가지 않는다. (구버전이 unknown을 버리면 rollback 한 번에 설정이 증발한다)

### 4) size + version 헤더 패턴

```
[u16 size][u16 version][payload...]
```

- `size`가 **맨 앞**인 이유: 버전을 몰라도 "이 레코드가 몇 바이트인지"는 항상 알 수 있다
  → 모르는 버전을 통째로 건너뛰거나, 잘림을 즉시 감지.
- `size != 실제 길이` → **거부**. 잘렸거나 깨진 것이고, 여기서 막지 않으면 뒤에서 out-of-bounds.
- `version`은 **해석 규칙**의 버전. 필드를 append만 하면 version은 잘 안 올라간다
  (version을 올리는 건 *의미가 바뀔 때*).
- 신버전(더 큰) 이미지를 받으면 → 아는 만큼만 읽고 꼬리는 무시. 단, **그걸 다시 저장하면
  꼬리가 날아간다**는 걸 문서화하거나, 원본 바이트를 보존해서 되쓴다.

### 5) A/B 슬롯과 원자적 커밋

```
slot A: [seq][crc][data...]
slot B: [seq][crc][data...]
load  : 유효한(crc OK, seq!=0) 슬롯 중 seq 최대
commit: 항상 '비활성' 슬롯에 seq = active_seq + 1 로 기록
```

- 활성 슬롯은 **절대 건드리지 않는다** → 쓰는 도중 전원이 나가도 최악은 "새 슬롯 CRC 불일치"
  뿐이고, 직전 정상 config는 그대로 로드된다.
- 실제 flash 순서가 중요: **erase → data 기록 → 마지막에 seq/crc 헤더 기록.**
  헤더가 "이제 유효하다"는 커밋 포인트다. 헤더를 먼저 쓰면 그 사이 전원이 나갔을 때
  "유효하다고 주장하는 쓰레기"가 된다.
- `seq` 랩어라운드: u32면 실전에선 안 돌지만, 면접에선 "부호 없는 뺄셈으로 비교
  `(int32_t)(a - b) > 0`" 또는 커밋 시 리셋 규칙을 말할 수 있어야 한다.
- 동률(seq 같음)이면 **결정적으로** 한쪽을 고른다(여기선 A). 비결정적이면 재현 불가 버그가 된다.

### 6) CRC 범위 — 어디까지 덮을 것인가

- CRC는 **seq + data 전체**를 덮어야 한다. data만 덮으면 seq 필드가 깨졌을 때
  "유효한데 순번이 이상한" 슬롯이 생겨 잘못된 config를 최신이라고 고른다.
- CRC 필드 자신은 당연히 제외. (또는 CRC 자리를 0으로 두고 전체 계산하는 방식)
- CRC32는 **무작위 비트 오류 검출**용이지 **위·변조 방지가 아니다.** 인증이 필요하면 CMAC/서명.
- 저장 시점: 마지막. 검증 시점: 매 부팅 + 매 로드.

### 7) Flash wear와 erase 단위

- NOR flash는 **바이트 단위로 1→0 쓰기만 가능**, 0→1은 **섹터 전체 erase**로만. 그래서
  "config 한 값만 바꾸기" = 사실상 섹터 다시 쓰기.
- erase 단위(4KB 등)가 곧 슬롯 단위여야 한다. 슬롯 두 개가 같은 섹터에 있으면 A/B의 의미가 없다
  (한 번의 erase가 둘 다 날린다). **A와 B는 서로 다른 물리 섹터.**
- 내구성(endurance) ~10K–100K erase cycle. 1Hz로 저장하면 하루 만에 수명을 태운다
  → 쓰기 합치기(coalesce), 변경 없으면 skip, 텔레메트리 같은 고빈도 값은 config에 넣지 않기.
- 대안: **append-only 저널 + 가끔 compaction**(레코드를 이어 붙이다 섹터가 차면 최신본만
  다른 섹터로 정리). wear를 섹터 전체에 분산.

### 8) Migration 전략

1. **읽을 때 올린다(upgrade-on-read).** 가장 단순하고 안전. 저장은 항상 최신 포맷으로.
2. **한 번에 한 단계씩**(v1→v2→v3 체인)으로 짜면 버전이 늘어나도 코드가 선형으로 관리된다.
3. 마이그레이션은 **멱등(idempotent)** 해야 한다 — 전원이 나가서 다시 해도 같은 결과.
4. 기본값은 **코드 한 곳에만** 정의(`CFG_DEF_*`), 마이그레이션과 factory reset이 같은 값을 쓴다.
5. 새 파라미터를 추가할 땐 "기본값으로 돌아가는 기존 기체"가 안전한 값인지 먼저 따진다.

## 각 Q의 핵심 포인트

| Q | 함수 | 한 줄 핵심 |
|---|------|-----------|
| **Q1** | `tlv_put_u32` / `tlv_put_bytes` | 용량 검사는 `off + need <= cap`이 아니라 **`cap - off >= need`** (size_t 오버플로 회피). 실패는 `0`이라는 명확한 sentinel |
| **Q2** | `tlv_find` | 헤더 3바이트가 **통째로** 남았을 때만 진입, 선언된 len만큼 payload가 없으면 **break**. 버퍼 밖을 한 바이트도 읽지 않는다 |
| **Q3** | `cfg_get_u32` | 없으면 fallback, **있는데 길이가 4가 아니어도 fallback**. 모르는 id는 거부가 아니라 skip = forward compatibility |
| **Q4** | `cfg_upgrade` | `size != raw_len` 먼저 거부 → 버전별로 있는 만큼만 읽고 나머지는 기본값 → **ver > 3이면 꼬리 무시** |
| **Q5** | `slot_select` | 유효 = `seq != 0 && crc == 계산값`. 유효한 것 중 seq 최대, 한쪽만 깨지면 자동 fallback, 둘 다 깨지면 `-1`(공장 기본값) |
| **Q6** | `cfg_commit` | **항상 비활성 슬롯에** `seq = active_seq + 1` + 새 CRC. 활성 슬롯을 안 건드리는 것이 원자성의 전부 |

## 흔한 함정 체크리스트

- [ ] **구조체를 flash에 통째로 저장** → padding/정렬/엔디안/컴파일러 버전에 인질로 잡힘
- [ ] `sizeof(struct)`를 온-플래시 포맷 길이로 사용 (패딩 포함 값이라 플랫폼마다 다름)
- [ ] **enum 값 재사용 / id 재배정** → 구버전이 다른 의미로 해석해 조용히 오동작 (가장 위험)
- [ ] **필드 삭제 후 그 자리·그 id 재사용** → deprecate만 하고 번호는 영구 소각해야 함
- [ ] 모르는 TLV를 **버리고** 다시 저장 → rollback 한 번에 신버전 설정 전멸
- [ ] `off + len > cap` 식 오버플로 가능한 경계 검사
- [ ] TLV 순회에서 **잘린 마지막 레코드** 미방어 → out-of-bounds read (전원 차단 시 실제로 생김)
- [ ] 길이 검사 없이 payload를 `u32`로 캐스팅해 읽기
- [ ] CRC가 **seq를 안 덮음** → 순번이 깨진 슬롯을 최신이라고 선택
- [ ] A/B 슬롯이 **같은 erase 섹터**에 있음 → 한 번의 erase로 둘 다 소실
- [ ] 커밋 순서를 헤더 먼저 → 쓰다 만 슬롯이 "유효"로 보임
- [ ] 값이 없을 때 0으로 시작 (failsafe 파라미터에서는 사고)
- [ ] 고빈도 값을 config에 저장 → flash wear

## 면접 꼬리질문 (답 요지 포함)

1. **"구조체를 그냥 flash에 쓰면 뭐가 문제죠?"**
   → padding/정렬/엔디안이 컴파일러·MCU·최적화 옵션에 따라 달라지고, 필드를 추가하면 기존
   이미지 해석이 전부 틀어진다. 그리고 모르는 필드를 건너뛸 방법이 없다. RAM 표현과 wire
   format을 분리하고 바이트 단위로 직렬화해야 한다.

2. **"구버전 FW가 신버전이 저장한 config를 읽으면요? 반대는요?"**
   → 신→구(forward): 모르는 id와 꼬리 바이트를 무시하고 진행. 구→신(backward): 없는 필드는
   기본값으로 채운다. 추가로, **구버전이 저장할 때 모르는 TLV를 보존**해야 rollback 후에도
   신버전 설정이 살아남는다. id/enum 값은 절대 재사용하지 않는다.

3. **"쓰는 도중 전원이 나가면 어떻게 되나요? 어떻게 증명하죠?"**
   → 항상 비활성 슬롯에만 쓰므로 활성 슬롯은 무사하다. flash 순서는 erase → data → 마지막에
   seq/crc 헤더(= 커밋 포인트). 증명은 "각 write 경계마다 전원을 끊는" 주입 테스트로,
   모든 지점에서 부팅 후 유효한 config가 로드되는지 확인 (Q6 테스트가 그 축소판).

4. **"CRC는 어디부터 어디까지 덮어야 하나요? CRC32면 충분한가요?"**
   → seq를 포함한 슬롯 전체(CRC 필드 자신 제외). seq를 빼면 순번만 깨진 슬롯을 최신으로
   오인한다. CRC32는 무작위 비트 오류 검출용이고 **위·변조 방지는 아니다** — 파라미터가
   안전에 영향을 준다면 서명/CMAC이 따로 필요하다.

5. **"파라미터를 매 프레임 저장하면 안 되는 이유는?"**
   → NOR flash는 0→1을 섹터 erase로만 되돌릴 수 있고 내구성이 ~10K–100K cycle이라 금방 탄다.
   변경 없으면 skip, 여러 변경을 합쳐서 한 번에 커밋, 고빈도 값은 config가 아니라 telemetry로.
   필요하면 append-only 저널 + compaction으로 wear를 분산한다.

6. **"파라미터를 하나 없애달라는 요청이 오면요?"**
   → 포맷에서 지우는 게 아니라 **deprecate**: 코드는 읽으면 무시, id는 영구 소각, 문서에
   "retired" 기록. 그리고 최소 한 릴리스는 두 버전 FW가 섞여 날아다니므로, 없어진 파라미터가
   기본값으로 떨어졌을 때 안전한지부터 확인한다.
