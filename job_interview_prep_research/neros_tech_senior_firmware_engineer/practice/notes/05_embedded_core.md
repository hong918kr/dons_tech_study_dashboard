# 📝 임베디드 기본기 복습 — 레지스터 / 비트 / 엔디안 / 고정소수점 / 메모리 레이아웃 — Q1~Q6

> 01~04 는 Neros 플랫폼 특화(logging / framing / config / IPC)였다. **05 는 성격이 다르다.**
> 회사를 가리지 않고 펌웨어 폰스크린에 **거의 반드시** 나오는 기본기만 모았다.
> 화려한 트릭은 없다. 대신 "정확히 아는가"를 본다 — `volatile` 이 무엇을 보장하고 무엇을
> 보장하지 **않는지**, `1u << 32` 가 왜 UB 인지, `sizeof(struct)` 를 와이어에 쓰면 왜 터지는지.
>
> 드론 펌웨어에서의 위치: 페리페럴 설정 = **레지스터 RMW**, IMU/바로미터/GNSS =
> **big-endian + 12/14/16비트 2의 보수 디코드**, FPU 없는(또는 ISR 에서 FPU 를 못 쓰는) MCU 의
> 필터/스케일링 = **고정소수점 Q포맷**.

## 1. `volatile` — 정확한 의미와 한계 ⭐

### 의미 (표준의 말)
`volatile` 객체에 대한 접근은 **관측 가능한 부수효과(observable side effect)** 다.
컴파일러는 그 접근을 **지우거나, 합치거나, 서로 재배치할 수 없다**. 소스에 쓴 개수만큼,
쓴 순서대로 실제 load/store 가 나간다.

### 왜 MMIO 에 필수인가
페리페럴 레지스터는 "메모리처럼 생겼지만 메모리가 아니다".

| 없으면 생기는 일 | 실제 증상 |
|---|---|
| 반복 읽기를 레지스터에 캐싱 | `while (!(*SR & RXNE)) ;` 가 **무한루프** |
| 값을 안 쓰는 읽기를 삭제 | read-to-clear 플래그가 **안 지워짐** → 인터럽트 폭주 |
| 연속 store 를 마지막 하나로 합침 | 설정 시퀀스가 깨져 페리페럴이 **엉뚱한 모드**로 |
| 접근 순서 재배치 | DMA enable 이 주소 설정보다 **먼저** 나감 |

### 보장하지 **않는** 것 (여기서 갈린다)
- **원자성 ❌** — `*reg |= mask` 는 load / or / store **3연산**이다.
- **CPU·버스 재정렬 방지 ❌** — 컴파일러만 묶는다. 멀티코어/AXI 는 `DMB`/`DSB` 가 따로 필요.
- **쓰기 버퍼 플러시 ❌** — "쓰고 바로 인터럽트 클리어 후 리턴" 하면 늦게 도착해 ISR 재진입
  (Cortex-M 의 고전 버그: 클리어 후 `DSB`).
- **캐시 일관성 ❌** — 레지스터 영역은 MPU 로 Device/Strongly-ordered 로 잡아야 한다.
- **스레드 동기화 의미 ❌** — 표준이 보장하지 않는다. → 동기화는 C11 `_Atomic`.

> **면접 한 줄**: "`volatile` 은 **컴파일러에게** 하는 말이고, `atomic` 은 **CPU 에게** 하는 말이다.
> `volatile` 은 접근이 사라지지 않게 할 뿐, 그 접근이 원자적이라고는 말하지 않는다."

### `volatile` 포인터 문법 (자주 틀림)
```c
volatile uint32_t *p;   // 가리키는 대상이 volatile  <- MMIO 는 이것
uint32_t *volatile p;   // 포인터 변수 자체가 volatile
volatile uint32_t *volatile p;  // 둘 다
#define GPIOA_ODR (*(volatile uint32_t *)0x40020014UL)  // CMSIS 스타일
```

## 2. RMW 레이스 — "읽고-고치고-쓰기"는 원자적이 아니다 ⭐

```
 태스크: v = *GPIO_ODR;          // 0x00
 태스크: v |= (1 << 3);          // 0x08
        ---- 여기서 인터럽트 ----
 ISR   : *GPIO_ODR |= (1 << 7);  // 완료 -> 0x80
        ---- 복귀 ----
 태스크: *GPIO_ODR = v;          // 0x08  <-- ISR 이 켠 bit7 이 사라졌다 (lost update)
```

증상은 **"가끔, 오래 돌리면, 릴리즈 빌드에서만"** LED/모터/CS 핀이 이상해지는 것.
재현이 안 돼서 가장 잡기 싫은 버그 부류다.

### 해법 4가지
| 방법 | 내용 | 비용/주의 |
|---|---|---|
| **임계구역** | `PRIMASK` 저장 → `__disable_irq()` → RMW → 복원 | 가장 범용. 인터럽트 지연(지터) 발생. **저장·복원**을 써야 중첩에서 안전 |
| **HW 원자 경로** | STM32 `GPIOx->BSRR` (set/reset 전용, 순수 write), bit-banding | 공짜로 원자적. **있으면 무조건 이걸 쓴다** |
| **LDREX/STREX** | ARMv7-M 배타 접근 루프 | 인터럽트를 막지 않음. 단 Device 메모리에서는 미보장 — 보통 RAM 변수용 |
| **소유자 단일화** | 해당 레지스터는 한 컨텍스트만 건드리게 설계 | 공짜. **플랫폼 팀의 정답**인 경우가 많다 |

> 04 IPC / 01 로깅에서 본 원칙과 같다: **"쓰기 주체를 하나로 만들면 락이 사라진다."**

## 3. 시프트 UB — 조용히 틀리는 3가지 (C11 6.5.7)

1. **시프트량 ≥ 피연산자 폭** → UB.
   x86 은 `shift & 31` 로 감고, ARM 은 0 을 내놓고, 상수면 컴파일러가 접어버린다.
   → `(1u << 32) - 1` 은 **0xFFFFFFFF 가 아니다**. 플랫폼마다 다르다.
2. **음수만큼 시프트** → UB.
3. **부호있는 값의 좌시프트 오버플로** → UB. `1 << 31` 은 `int` 면 UB, `1u << 31` 은 OK.

```c
// 틀림
uint32_t mask = (1u << width) - 1u;          // width == 32 에서 UB

// 맞음
uint32_t width_mask(uint32_t width) {
    if (width == 0u)  return 0u;
    if (width >= 32u) return 0xFFFFFFFFu;
    return (1u << width) - 1u;
}
```

우시프트도 같다: `x >> 32` 는 UB. `bits_extract` 에서 `shift >= 32` 를 먼저 막는 이유.

**덤: 정수 승격(integer promotion)**
`uint16_t a = 0xFFFF; a << 16` 에서 `a` 는 먼저 `int` 로 승격 → 부호있는 오버플로 UB.
`uint8_t`/`uint16_t` 를 시프트할 때는 **먼저 `uint32_t` 로 캐스팅**한다.
(`~` 도 같다: `uint8_t x; ~x` 는 `int` 결과라 상위 비트가 1 로 깔린다.)

## 4. 부호 확장 (sign extension)

센서 레지스터는 **12 / 14 / 16 / 18 / 20비트 2의 보수**가 흔하다 (ADC, IMU, 자력계).
상위 비트는 0 으로 채워져 오므로 그대로 `int` 로 읽으면 음수가 **큰 양수**로 보인다.
전형적 증상: "가속도계가 가끔 4090 으로 튄다" (= 사실은 −6).

```c
// 12비트: 0xFFF -> -1, 0x800 -> -2048, 0x7FF -> +2047
uint32_t m    = width_mask(width);
uint32_t v    = value & m;
uint32_t sign = 1u << (width - 1u);
return (int32_t)(v ^ sign) - (int32_t)sign;   // 오버플로 없이 '정의된' 관용구
```

- 대안 1: 비트필드 `struct { int32_t s : 12; }` — 동작하지만 비트필드 레이아웃은 **구현정의**.
- 대안 2: `(int32_t)(value << 20) >> 20` — 부호있는 좌시프트 오버플로 + 산술 우시프트 의존(구현정의).
  실무에서는 잘 쓰이지만 **면접에서는 위의 xor-빼기 관용구**가 안전한 답이다.
- `uint16_t → int16_t` 직접 캐스팅도 범위 밖이면 **구현정의**(C11 6.3.1.3). 전 세계 실제 컴파일러는
  2의 보수 랩을 하지만, "안다"는 표시로 `sign_extend` 를 통과시키는 편이 깔끔하다.

## 5. 엔디안 · 정렬(alignment) · strict aliasing ⭐

### 절대 하면 안 되는 것
```c
uint32_t v = *(uint32_t *)&rx_buf[3];   // ❌ 3중 지뢰
```

| 지뢰 | 내용 |
|---|---|
| **정렬** | Cortex-M0/M0+ 는 비정렬 `LDR` 자체가 불가 → **HardFault**. M3/M4 는 `LDR/STR` 만 봐주고 `LDM/STM/LDRD`, `SCB->CCR.UNALIGN_TRP`, Device 메모리에서는 폴트. 봐줘도 버스 사이클이 쪼개져 **느리다** |
| **strict aliasing** | `uint8_t[]` 를 `uint32_t` 로 읽는 것은 형식 규칙 위반(UB). `-O2` 에서 컴파일러가 "안 겹친다"고 가정해 읽기/쓰기를 재배치 → **최적화 빌드에서만 깨지는 버그** |
| **엔디안** | 캐스팅은 **호스트 엔디안**으로 읽는다. 와이어는 프로토콜이 정한 엔디안이 따로 있다 |

### 항상 하는 것
```c
uint32_t read_le32(const uint8_t *p) {
    return (uint32_t)p[0] | ((uint32_t)p[1] << 8)
         | ((uint32_t)p[2] << 16) | ((uint32_t)p[3] << 24);
}
```
- 정렬 무관, aliasing 안전(`uint8_t`/`char` 는 **무엇이든 alias 할 수 있는 예외**), 엔디안을 코드가 **선언**.
- 느리지 않다: 컴파일러가 이 패턴을 알아보고 정렬 보장 지점에서는 `ldr`/`rev` 한 방으로 접는다.
- `memcpy(&v, p, 4)` 도 합법적인 대안(aliasing/정렬 안전) — 단 **엔디안은 여전히 호스트 것**이다.

### 엔디안 상식
- **network byte order = big-endian.** 대부분의 센서 레지스터 맵(BMI270, MS5611, u-blox 일부)이 BE.
- x86 / ARM(일반 설정) 은 LE. 그래서 "BE 센서 → LE MCU → LE 호스트" 변환이 상시 발생.
- `htons/ntohs` 는 호스트 엔디안에 따라 **아무것도 안 할 수도** 있다. 와이어 코드에서는
  `read_be16()` 처럼 **엔디안을 이름에 박은 함수**를 쓰는 게 버그가 적다.
- 런타임 엔디안 체크: `union { uint32_t u; uint8_t b[4]; } x = {1}; x.b[0] == 1 → LE`.
  (C 에서 union type-punning 은 합법. C++ 에서는 UB.)

## 6. 고정소수점 Q포맷 — 라운딩과 새추레이션 ⭐

### 왜 float 을 피하나
- FPU 없는 코어(M0/M0+/M3): float 은 **소프트 라이브러리 호출** = 수십~수백 사이클 + 코드 크기.
- FPU 가 있어도 **ISR 에서 쓰면** FPU 컨텍스트(S0–S31, FPSCR) 스태킹 때문에 지터가 커진다
  (lazy stacking, RTOS 태스크별 FPU 컨텍스트 …).
- **재현성**: float 은 값 크기에 따라 정밀도가 달라져 적분기/필터의 비트 단위 재현이 어렵다.
  제어 루프와 HIL 테스트는 **결정적**이어야 한다.

### Q15 정의
`int16_t` 를 `[-1.0, +1.0)` 로 해석. 실수값 = `raw / 32768`.

| raw | 값 |
|---|---|
| `0x4000` (16384) | +0.5 |
| `0x7FFF` (32767) | +0.999969… (**+1.0 은 표현 불가**) |
| `0x8000` (−32768) | −1.0 |

### 곱셈: Q15 × Q15 = Q30 → >>15
```c
int32_t prod = (int32_t)a * (int32_t)b;   // 확장 필수! int16*int16 을 int16 에 담으면 끝
prod = (prod + (1 << 14)) >> 15;          // 반올림
if (prod > 32767) prod = 32767;           // 포화
if (prod < -32768) prod = -32768;
```

**라운딩이 왜 중요한가**: 그냥 `>> 15` 는 반올림이 아니라 **−∞ 쪽 버림**(산술 시프트)이다.
매 샘플 −0.5 LSB 씩 편향이 쌓이면 IIR 필터/적분기에 **DC 드리프트**가 생긴다.
`+(1 << 14)` 한 줄이 그것을 없앤다. (테스트: `q15_mul(1, 16384)` 는 반올림하면 **1**,
버리면 **0**.)

**새추레이션이 왜 중요한가**: `-1.0 × -1.0 = +1.0` 은 Q15 로 표현 불가.
랩어라운드하면 **최댓값이 최솟값으로 뒤집혀** 제어기가 즉시 발산한다 (모터 풀스로틀 → 역방향).
포화는 "틀리지만 안전한 방향으로 틀린다". DSP 명령(`QADD`, `SSAT`)이 존재하는 이유.

### 정수 스케일링 (ADC → mV)
```c
mv = (counts * vref_mv + full_scale/2) / full_scale;   // +fs/2 = 반올림
```
- **오버플로**: `counts(16bit) * vref_mv` 는 uint32 에서 아슬아슬하다. 64비트 중간값이 제일 단순.
- 64비트 곱이 비싼 코어라면 나눠서:
  `(c/fs)*vref + ((c%fs)*vref + fs/2)/fs` — 32비트만으로 같은 결과.
- 순서가 전부다: **곱하기 먼저, 나누기 나중.** `(counts/full_scale)*vref_mv` 는 거의 항상 0.

### 그 밖의 Q포맷 상식
- `Q15` (int16), `Q31` (int32), `Q16.16` (int32, 정수부 16 + 소수부 16) 이 실무 3대장.
- **덧셈은 같은 Q끼리만**, 곱셈은 Q합이 되므로 시프트로 되돌린다. Q 를 주석/타입명에 박아라.
- 나눗셈은 최대한 피하고 **역수 곱 + 시프트**(`reciprocal multiply`)로 바꾼다.

## 7. `strlcpy` vs `strncpy`, `memcpy` vs `memmove` ⭐

### strncpy 의 3가지 함정
1. `strlen(src) >= n` 이면 **NUL 을 안 붙인다** → 이후 `strlen`/`printf` 가 버퍼 밖으로 달린다.
2. `src` 가 짧으면 남는 자리를 **전부 0 으로 채운다** → 큰 버퍼에서 쓸데없이 느리다.
   (원래 용도는 문자열이 아니라 고정폭 필드 — 옛 UNIX 디렉터리 엔트리)
3. 반환값이 `dst` 라 **잘렸는지 알 수 없다**.

### strlcpy 계약 (이 문제의 `safe_copy`)
- `cap > 0` 이면 **항상** NUL 종료.
- `cap` 바이트를 **절대** 넘지 않는다.
- 반환값 = `strlen(src)` = "잘리지 않았다면 썼을 길이".
- 따라서 **`if (safe_copy(d, cap, s) >= cap) { 잘림 처리 }`** 로 절단을 **감지**할 수 있다.

> 핵심은 성능이 아니라 **감지 가능성**이다. 조용한 절단은 설정값·경로·기체 ID 를 망가뜨리고
> 한참 뒤에 엉뚱한 곳에서 터진다. (`snprintf` 도 같은 철학: 반환값 >= size 면 잘린 것.)

### memcpy vs memmove
| | 계약 | 겹치면 |
|---|---|---|
| `memcpy` | **겹치지 않음이 전제** (`restrict`) | **UB**. 구현(SIMD/역방향/블록)에 따라 결과가 달라진다 |
| `memmove` | 겹쳐도 됨 | "src 를 먼저 전부 읽은 것과 같은 결과"를 보장 |

구현은 방향 선택뿐:
```c
if (d < s) 앞에서부터;   // dst 가 앞 -> 아직 안 읽은 영역을 안 건드림
else       뒤에서부터;   // dst 가 뒤 -> 뒤에서 오면 안전
```

**증명 (문제의 테스트)**: `"0123456789"` 에서 `dst = buf+2, src = buf+0, n = 5`
- 정답(memmove) → `"0101234789"`
- 앞에서부터만 복사 → `"0101010789"` — 방금 쓴 `'0','1'` 을 다시 읽어 **자기 자신을 복제**한다.

> 실무 팁: `memcpy` 의 겹침 UB 는 `-O0` 에서는 우연히 맞고 `-O3`/다른 libc 에서만 깨진다.
> **"겹칠 수 있으면 무조건 memmove"** 가 규칙. 링 버퍼 wrap 구간이 대표적 위험 지대.

## 8. 구조체 패딩 vs 와이어 포맷 — `packed` 의 함정 ⭐

```c
typedef struct {
    uint8_t  id;        // offset 0
    uint8_t  flags;     // offset 1
    // ---- padding 2바이트 ----   <-- t_us 를 4바이트 경계에 놓기 위해
    uint32_t t_us;      // offset 4
    int16_t  ax, ay, az;// 8, 10, 12
    uint16_t volt_mv;   // 14
} sensor_pkt_t;         // sizeof == 16,  와이어는 14
```

### `memcpy(out, &pkt, sizeof pkt)` 가 금지인 이유 4가지
1. **길이가 다르다** — 패딩 2바이트가 같이 나간다(16 vs 14).
2. **패딩 내용은 불확정값(indeterminate)** — 스택 쓰레기가 그대로 링크로 나간다.
   보안 맥락에서는 **정보 유출**(실제 CVE 유형). `memset(&pkt, 0, ...)` 도 컴파일러가
   패딩까지 0 으로 유지해준다는 보장이 없다.
3. **엔디안** — 타깃과 호스트가 다르면 값이 뒤집힌다.
4. **레이아웃이 계약이 아니다** — 컴파일러/ABI/옵션이 바뀌면 조용히 달라진다.
   (32비트 vs 64비트, 포인터·`size_t`·`enum`·비트필드 포함 시 특히)

### `__attribute__((packed))` 로 때우면?
동작은 한다. 대가:
- **비표준** (GCC/Clang 확장, MSVC 는 `#pragma pack`).
- packed 멤버의 **주소를 잡으면 비정렬 포인터**가 된다. 그 포인터를 받은 함수는 정렬을
  가정하고 `LDR` 을 쓰다가 **Cortex-M0 에서 HardFault**. (GCC 의 `-Waddress-of-packed-member`
  가 이걸 경고한다 — 절대 끄지 말 것.)
- ARM 에서 packed 필드 접근은 바이트 단위 코드로 풀려 **오히려 느릴 수** 있다.
- **엔디안 문제는 그대로 남는다.**

> **정답은 언제나 필드 단위 명시적 직렬화.**
> 구조체 = 메모리 표현(빠르게 다루려고 정렬됨), 와이어 = 별도 계약(바이트가 전부).
> 둘을 분리하면 컴파일러·아키텍처·언어(호스트 디코더가 Python 이어도)가 바뀌어도 안 깨진다.
> 01 로깅, 02 프레이밍, 04 IPC 에서 똑같은 결론이 나왔다 — **이건 이 뱅크 전체의 관통 원칙**이다.

### 패딩 줄이기 (부수 지식)
멤버를 **큰 것부터 작은 것 순**으로 정렬하면 패딩이 줄어든다. RAM 이 수십 KB 인 MCU 에서
배열로 수백 개 잡는 구조체라면 실질적 절약. `_Static_assert(sizeof(x) == N, ...)` 로 박아두면
누가 멤버를 추가했을 때 **빌드가 깨지며** 알려준다 — 런타임에 발견하는 것보다 훨씬 싸다.

## 9. 각 Q 핵심 포인트 한 줄

| Q | 함수 | 한 줄 |
|---|---|---|
| **Q1** | `reg_set/clear/toggle_bits`, `reg_write_field` | `volatile` 은 접근을 보존할 뿐 **원자성은 없다**. RMW 는 임계구역 또는 BSRR 같은 HW 원자 경로로 |
| **Q2** | `bits_extract/insert`, `sign_extend` | `1u << 32` 는 **UB**. width 0/32 를 분기로 막고, 좁은 2의 보수는 `(v^sign)-sign` 으로 펼친다 |
| **Q3** | `bswap16/32`, `read_be16`, `read_le32`, `write_be16` | 와이어는 **항상 `uint8_t` + 시프트/OR**. 포인터 캐스팅은 정렬·aliasing·엔디안 3중 지뢰 |
| **Q4** | `q15_mul`, `q15_sat_add`, `adc_to_mv` | 중간값은 **한 단계 넓은 타입**, `+(1<<14)` 로 반올림, 끝에서 **포화**. 곱하기 먼저 나누기 나중 |
| **Q5** | `safe_copy`, `memmove_impl` | strlcpy 계약 = **항상 NUL 종료 + would-be 길이 반환**(절단 감지). 겹치면 memcpy 가 아니라 memmove |
| **Q6** | `pkt_serialize/deserialize` | `sizeof(struct) != 와이어 크기`. 구조체는 메모리 표현, 와이어는 **필드 단위 명시 직렬화** |

## 10. 흔한 함정 (체크리스트)

- [ ] MMIO 포인터에 `volatile` 누락 → 폴링 루프가 무한루프, read-to-clear 가 안 지워짐.
- [ ] `volatile` 만 믿고 `*reg |= mask` 를 ISR 과 태스크가 동시에 → **lost update**.
- [ ] 임계구역에서 `__enable_irq()` 로 복원 → 원래 꺼져 있었으면 **강제로 켜버린다**. PRIMASK 저장·복원 필수.
- [ ] `(1u << width) - 1` 에서 `width == 32` → **UB**. `x >> 32` 도 UB.
- [ ] `uint16_t` 를 `<< 16` → 정수 승격으로 `int` 오버플로 UB. 먼저 `(uint32_t)` 캐스팅.
- [ ] 12/14비트 센서 값을 **부호 확장 없이** 사용 → 음수가 큰 양수로 튄다.
- [ ] 필드 삽입 시 `value` 를 width 로 안 자름 → **옆 필드를 침범**해 페리페럴이 엉뚱한 모드로.
- [ ] 와이어 버퍼 `uint8_t*` 를 `uint32_t*` 로 캐스팅 → M0 HardFault / `-O2` 에서만 깨짐.
- [ ] `htons` 로 다 된다고 생각 → 호스트가 BE 면 아무 일도 안 한다. 엔디안을 **이름에 박아라**.
- [ ] `int16 * int16` 을 `int16`/`int` 폭에서 계산 → Q30 중간값 오버플로. `(int32_t)` 확장 필수.
- [ ] Q15 곱에서 반올림 생략 → 필터에 **DC 드리프트** 누적.
- [ ] 포화 없이 랩어라운드 → 최댓값이 최솟값으로 뒤집혀 **제어기 발산**.
- [ ] `(counts / full_scale) * vref_mv` → 정수 나눗셈이 먼저라 거의 항상 0. **곱셈 먼저.**
- [ ] `strncpy` 후 NUL 종료 가정 → 버퍼 오버리드. 그리고 **잘렸는지 알 수 없다**.
- [ ] 반환값을 `strlen(dst)` 로 착각 → 절단 감지 실패. strlcpy 는 **`strlen(src)`** 를 돌려준다.
- [ ] 겹칠 수 있는 영역에 `memcpy` → `-O0` 에선 통과, 최적화/다른 libc 에서 데이터 파괴.
- [ ] `memcpy(wire, &struct, sizeof struct)` → 패딩 유출 + 길이 불일치 + 엔디안 의존.
- [ ] `packed` 구조체 멤버의 **주소를 넘김** → 비정렬 포인터 → HardFault. (경고를 끄지 말 것)
- [ ] 와이어 크기를 `sizeof` 로 계산 → 상수로 박고 `_Static_assert` 로 고정하라.

## 11. 면접 꼬리질문 (답 요지 포함)

**Q. "`volatile` 이면 스레드 사이에 안전한 것 아닌가요?"**
→ 아니다. `volatile` 은 **컴파일러**에게 "이 접근을 지우지도 합치지도 재배치하지도 마라"고
할 뿐이다. 보장하지 않는 것: (1) 원자성 — `x++` 는 load/add/store 3연산, (2) **CPU 재정렬**과
쓰기 버퍼, (3) 캐시 일관성, (4) 표준이 정의한 동기화 의미(happens-before).
단일코어 베어메탈에서 **ISR ↔ main 사이의 단일 워드 플래그**에는 관습적으로 통하지만
(그것도 정렬된 워드 store 가 원자적이라는 **하드웨어** 성질 덕분이지 `volatile` 덕분이 아니다),
멀티코어/SMP/RTOS 로 가면 틀린다. 정답은 C11 `_Atomic` + acquire/release, 또는 임계구역.
한 줄: **"`volatile` 은 컴파일러에게, `atomic` 은 CPU 에게 하는 말."**

**Q. "`*reg |= (1 << 3);` 한 줄인데 왜 레이스인가요? 어떻게 고치죠?"**
→ 한 줄이지만 기계어로는 `LDR / ORR / STR` 3개다. 중간에 인터럽트가 끼어 같은 레지스터를
건드리면 ISR 의 갱신이 `STR` 에 덮여 사라진다(lost update). 고치는 순서: ①
**HW 원자 경로가 있으면 그것부터** — STM32 라면 `GPIOx->BSRR = (1u << 3)` 은 순수 write 라
RMW 자체가 없다(bit-banding 도 동일). ② 없으면 **PRIMASK 를 저장하고** `__disable_irq()`,
RMW, 복원 — `__enable_irq()` 로 복원하면 원래 꺼져 있던 인터럽트를 강제로 켜는 버그가 된다.
③ RAM 변수라면 `LDREX/STREX` 루프(인터럽트를 안 막아 지터가 없다). ④ 설계로: 이 레지스터를
만지는 컨텍스트를 **하나로 정한다**. 실무 우선순위는 ④ → ① → ② 다.

**Q. "왜 `rx_buf` 를 `uint32_t*` 로 캐스팅하면 안 되나요? 성능이 아깝지 않나요?"**
→ 세 가지 이유가 동시에 걸린다. (1) **정렬**: 페이로드는 임의 오프셋에서 시작한다. Cortex-M0
는 비정렬 `LDR` 이 아예 없어 HardFault, M4 도 `LDM`/`LDRD`/Device 메모리에서 폴트하고 봐주는
경우에도 버스 사이클이 쪼개져 느리다. (2) **strict aliasing**: `uint8_t[]` 를 `uint32_t` 로 읽는
것은 형식 규칙 위반이라 `-O2` 에서 컴파일러가 접근을 재배치한다 — 디버그 빌드에서는 멀쩡한
버그가 생긴다. (3) **엔디안**: 캐스팅은 호스트 엔디안으로 읽으므로 프로토콜이 BE 면 그냥 틀린다.
성능은 걱정할 필요 없다 — `p[0] | p[1]<<8 | ...` 패턴을 컴파일러가 인식해서 정렬이 보장되는
곳에서는 `ldr` 한 방(필요하면 `rev`)으로 접는다. 즉 **안전한 쪽이 공짜**다.

**Q. "FPU 가 있는 MCU 인데도 고정소수점을 써야 하나요?"**
→ 세 가지를 따진다. (1) **ISR/제어 루프 안인가** — FPU 컨텍스트 스태킹(S0–S31 + FPSCR)이
인터럽트 지연과 지터를 키운다. RTOS 라면 태스크마다 FPU 컨텍스트가 붙어 RAM 도 먹는다.
(2) **결정성이 필요한가** — float 은 값 크기에 따라 정밀도가 달라져 적분기/필터의 비트 단위
재현이 어렵다. HIL 재현, 로그 리플레이, 인증(DO-178 류)에서는 결정성이 요구사항이다.
(3) **double 로 승격되지 않는가** — `x * 0.5` 는 `double` 연산이고 M4F 의 FPU 는 단정밀도만
한다. 소프트 double 로 떨어져 수백 사이클을 먹는다(`0.5f` 를 안 써서 생기는 고전 사고).
결론: 상위 레벨 계산·초기화·텔레메트리는 float 도 괜찮고, **고속 제어 루프와 ISR 은 고정소수점**.
그리고 고정소수점을 쓰면 **오버플로/포화를 강제로 설계**하게 되는 부수 효과가 오히려 안전하다.

**Q. "센서 패킷을 그냥 구조체로 `memcpy` 해서 보내면 안 되나요? `packed` 붙이면 되죠?"**
→ `memcpy` 는 네 가지가 깨진다: 패딩이 같이 나가 길이가 틀리고, 패딩은 **불확정값**이라
스택 쓰레기(잠재적 정보 유출)가 실리고, 엔디안이 다르면 값이 뒤집히고, 컴파일러·ABI·옵션이
바뀌면 레이아웃이 조용히 달라진다. `packed` 는 1·2번만 덮는다: 엔디안은 그대로고, 게다가
**packed 멤버의 주소를 잡으면 비정렬 포인터**가 되어 그걸 넘겨받은 코드가 Cortex-M0 에서
HardFault 를 낸다(그래서 `-Waddress-of-packed-member` 가 있다). 또 ARM 에서 packed 접근은
바이트 단위로 풀려 오히려 느릴 수 있다. 정답은 **필드 단위 명시적 직렬화** — 구조체는 메모리
표현, 와이어는 별도 계약으로 분리하고, 와이어 크기는 상수 + `_Static_assert` 로 못 박아
누가 멤버를 추가하면 **빌드가 깨지게** 한다. 호스트 디코더가 Python 이든 Rust 든 같은 계약을
보고 구현할 수 있다는 것도 큰 이점이다.
