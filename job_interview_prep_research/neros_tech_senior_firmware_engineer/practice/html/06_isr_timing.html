1. 전체 그림 — 비행 펌웨어의 골격#

  [하드웨어]      [ISR = top half]           [main loop = bottom half]
  IMU DRDY  ---->  레지스터 읽기              while (1) {
  UART RX   ---->  payload 저장 (Q1)            now = millis();           <- Q2/Q3
  TIM tick  ---->  tick++ (Q3)                  if (main_take(&s)) ...    <- Q1
  GPIO      ---->  work_post(id) (Q6)           debounce_update(...)      <- Q4
                   |                             sched_run(&s, now);      <- Q5
                   | 수십~수백 사이클로 끝       work_process();           <- Q6
                   v                            kick_watchdog();
              (절대 금지: printf, malloc,     }
               mutex 대기, 블로킹 I/O, 긴 루프)

핵심 원칙 한 줄: ISR 은 "사실을 기록"만 하고, "의미 해석"은 main loop 가 한다.

2. ISR 설계 원칙 — top half / bottom half ⭐#

리눅스 용어지만 베어메탈/RTOS 에서도 똑같이 쓴다.

top half (ISR)bottom half (main loop / 태스크)
하는 일하드웨어 응답(플래그 클리어, FIFO 비우기), 데이터 복사, 큐에 post파싱, 필터, 제어 계산, 로깅, I/O
예산수십 µs 이하. 8kHz 루프면 125µs 안에 전부 끝나야 한다수 ms 도 허용
금지printf, malloc, snprintf, 부동소수(FPU 컨텍스트), mutex 대기, 블로킹, 긴 루프없음
이유인터럽트 비활성/선점 불가 구간이 길어지면 다른 인터럽트를 놓친다(overrun)—

ISR 안에서 mutex 를 잡으면 안 되는 이유: mutex 는 "기다림"을 전제한다. ISR 은 태스크가 아니라서 블록될 수 없고(블록하면 시스템이 그대로 멈춘다), 태스크가 락을 쥔 채 ISR 이 들어오면 그 자리에서 데드락이다. ISR ↔ main 공유 자료는 락이 아니라 구조(SPSC 큐, 플래그 핸드셰이크, seqlock, 또는 아주 짧은 인터럽트 마스킹)로 푼다.

ISR 에서 쓸 수 있는 동기화 도구 3가지#

  1. 플래그 + 순서 규칙 (Q1) — 가장 싸다. 단일 이벤트.
  2. SPSC 링 큐 (Q6, 그리고 01_ring_logging) — 이벤트가 여러 개일 때 정답.
  3. critical section = 인터럽트 마스킹 (__disable_irq() / BASEPRI) — 확실하지만 그 구간만큼 인터럽트 지연이 늘어난다. 아래 6절 참고.

3. volatile vs atomic vs barrier ⭐⭐#

면접에서 가장 자주 나오는 구별. 세 개는 서로 다른 문제를 푼다.

막아주는 것못 막는 것
volatile컴파일러가 값을 레지스터에 캐싱/중복 제거/삭제하는 것CPU 재정렬, RMW 원자성, 비-volatile 접근과의 재정렬
컴파일러 배리어 (atomic_signal_fence, asm volatile("":::"memory"))컴파일러의 명령 재정렬CPU 재정렬 (멀티코어에서 무용)
메모리 배리어 (atomic_thread_fence, DMB)CPU 의 out-of-order / store buffer 재정렬원자성 자체
C11 atomic (atomic_load_explicit 등)위 전부 + read-modify-write 원자성—
  • volatile int x; x++; 는 원자적이지 않다 (load / add / store 3연산). ISR 과 main 이 둘 다 증가시키면 값을 잃는다. → 소유자를 한쪽으로 몰거나 atomic RMW 를 써라.
  • 단일코어 MCU 의 ISR↔main: 실제 재정렬 주체는 컴파일러뿐이다 (ISR 은 명령 경계에서 들어오므로 CPU 재정렬은 관측되지 않는다). → volatile + 컴파일러 배리어 + "데이터 먼저, 플래그 나중" 이면 충분.
  • 멀티코어 / SMP Linux / DMA: volatile 만으로는 틀린다. 진짜 배리어 또는 atomics 필요. DMA 는 캐시를 안 보므로 추가로 캐시 유지(clean/invalidate) 까지 필요하다.
  • 한 줄 답변: "volatile 은 컴파일러에게 하는 말이고, barrier/atomic 은 CPU 에게 하는 말이다."

sig_atomic_t 는 뭔가?#

C 표준이 "비동기 시그널/인터럽트가 끼어들어도 찢어지지 않게(atomically) 읽고 쓸 수 있다"고 보장하는 유일한 정수 타입. 그래서 전통적으로 ISR 플래그에 쓴다. 단, 보장하는 건 단일 load/store 의 비분할성뿐이다 — 순서도, ++ 의 원자성도 보장하지 않는다.

4. 인터럽트 지연 · 지터 · 우선순위#

 이벤트 발생 ──┬── interrupt latency ──┬── ISR 실행 ──┬── 응답 완료
               │                        │              │
        (1) 인터럽트 마스킹 구간         (3) 현재 명령    (5) ISR 본문
        (2) 더 높은/같은 우선순위 ISR        완료 대기
            선행 실행                    (4) 벡터 페치 + 스택 푸시
  • interrupt latency: 이벤트 → ISR 첫 명령까지. 결정적(deterministic) 최악값이 중요하다.
  • jitter: latency 의 변동 폭. 제어 루프에서는 평균보다 지터가 더 해롭다 (샘플링 간격이 흔들리면 미분항이 노이즈가 된다).
  • 최악 지연을 늘리는 주범: ① 긴 critical section, ② 긴 ISR(같은/낮은 우선순위를 막음), ③ 플래시 쓰기/erase(코어 스톨), ④ DMA 버스 경합, ⑤ 캐시/TCM 미스.
  • ARM Cortex-M 우선순위: 숫자가 작을수록 높다. BASEPRI 로 "이 레벨 이하만 마스킹" 할 수 있어 PRIMASK(전부 차단)보다 낫다 — 안전 critical ISR 은 계속 살려둔다. tail-chaining / late arrival 덕에 연속 인터럽트의 오버헤드가 작다.
  • NMI / HardFault 는 마스킹 불가.
  • 원칙: 주기가 짧고 데드라인이 빡빡한 것에 높은 우선순위 (rate-monotonic 의 직관). 제어 루프 타이머 > IMU DRDY > UART > 로깅/텔레메트리.

priority inversion 과 우선순위 상속 ⭐#

 우선순위  H(높음) ─── 락 대기 ────────────────► 실행
           M(중간)        ──── 실행 ────           (H 가 M 때문에 밀린다!)
           L(낮음)  ─ 락 보유 ─           ─ 락 해제
  • 우선순위 역전: 낮은 우선순위 L 이 락을 쥔 채 선점당하고, 중간 우선순위 M 이 CPU 를 독차지하면, 락을 기다리는 H 가 M 보다 늦게 실행된다. 실제 사례: Mars Pathfinder(1997) 가 이걸로 반복 리셋됐고, 원격으로 우선순위 상속을 켜서 고쳤다.
  • 해법
    • priority inheritance: L 이 락을 쥐고 있는 동안 L 의 우선순위를 H 로 일시 승격. FreeRTOS 의 mutex(xSemaphoreCreateMutex)가 이걸 한다. (binary semaphore 는 안 한다 — 상호배제에는 semaphore 말고 mutex 를 써야 하는 이유.)
    • priority ceiling: 락마다 "이 락을 쓰는 태스크 중 최고 우선순위"를 미리 정해두고, 잡는 순간 그 레벨로 올린다. 더 결정적이고 데드락도 막지만 정적 분석이 필요하다.
    • 가장 확실한 해법은 공유를 없애는 것: ISR↔main 은 락 없는 큐(Q6)로, 태스크 간에는 메시지 패싱으로. 안 잡는 락은 역전되지 않는다.

5. critical section 최소화#

// 나쁨: 계산까지 인터럽트 끄고 한다
__disable_irq();
process_everything(&shared);      // 200µs -> 그동안 모든 인터럽트가 밀린다
__enable_irq();

// 좋음: 복사만 하고 밖에서 처리한다
__disable_irq();
snapshot = shared;                // 몇 사이클
shared.count = 0;
__enable_irq();
process_everything(&snapshot);    // 인터럽트 켜진 상태로
  • 마스킹 구간은 그대로 최악 인터럽트 지연에 더해진다. "몇 줄"이 아니라 몇 사이클로 재라.
  • 중첩 대비: PRIMASK 를 저장/복원해야 한다 (uint32_t s = __get_PRIMASK(); __disable_irq(); ...; __set_PRIMASK(s);). 무조건 __enable_irq() 하면 바깥 critical section 을 깬다.
  • 더 좋은 것은 락이 필요 없는 구조: Q1 의 플래그 핸드셰이크, Q3 의 재시도 읽기, Q6 의 SPSC 큐는 전부 마스킹 없이 성립한다.

6. 틱 wraparound — 49.7일의 저주 ⭐#

카운터랩 주기
uint32_t ms (1kHz)49.7일
uint32_t µs (1MHz)71.6분 ← 가장 자주 물린다
uint16_t ms65.5초
uint64_t µs58만 년 (사실상 무한)
// 틀림: 랩 순간 조용히 뒤집힌다
if (now > start + timeout) { ... }        // start+timeout 이 랩하면 영원히 거짓
if (now > deadline) { ... }

// 맞음: 절대 시각을 비교하지 말고 '차이'를 본다
if ((uint32_t)(now - start) >= timeout) { ... }
#define time_after(a, b)  ((int32_t)((b) - (a)) < 0)

왜 되는가: 부호없는 뺄셈은 모듈로 2^32 로 정의돼 있어 랩을 자동으로 처리한다. 그 차이를 int32_t 로 해석하면 "가까운 미래 / 가까운 과거"가 부호로 갈린다. 전제: 두 시각의 간격이 2^31 미만(ms 면 24.8일)이어야 한다. 이보다 오래된 타임스탬프를 비교하면 여전히 뒤집힌다 → 장기 시각은 64비트를 쓰거나 주기적으로 리베이스한다.

timeout_ms 는 timeout_ms > 0 이어야 의미가 있다. 0 이면 항상 만료(즉시 true)다.
"무한 대기"를 0 으로 인코딩하는 API 가 많으니 계약을 문서에 박아라.

7. 주기 스케줄링 — 드리프트 vs 버스트 ⭐#

(a) 드리프트#

next_due = now + period;     // ✗ 실행 지연이 매 주기 누적된다
next_due += period;          // ✓ 고정 격자(cadence). 지연은 흡수되고 위상이 유지된다

전자는 sched_run 이 3ms 늦게 호출될 때마다 다음 주기가 3ms씩 밀린다. 100Hz 가 며칠 뒤에는 97Hz 가 되고, 두 태스크의 상대 위상도 흐트러진다. FreeRTOS 가 vTaskDelay(상대) 말고 vTaskDelayUntil(절대)을 따로 두는 이유가 정확히 이것이다.

(b) 버스트 (backlog 정책)#

플래시 쓰기·디버거 정지·긴 ISR 로 200ms 멈췄다가 돌아오면 10ms 태스크의 밀린 주기가 20개다.

정책동작언제
skip backlog (이 문제)1회만 실행하고 next_due 를 now 이후로 점프, 건너뛴 수를 missed 로 계수제어/센서 루프의 기본값. 옛날 데이터로 20번 도는 건 무의미하고, 그 버스트가 다음 주기를 또 밀어 악순환을 만든다
catch-up밀린 만큼 전부 실행적산이 의미 있는 작업(적분, 카운팅, 애니메이션 프레임)
reset phase (next_due = now + period)위상을 버리고 다시 시작위상이 상관없는 하우스키핑
t->next_due += t->period;                      // 고정 케이던스
if (!time_after(t->next_due, now)) {           // 아직도 과거 = 스톨했다
    uint32_t skip = (now - t->next_due) / t->period + 1;
    t->missed += skip;                         // 조용히 버리지 말고 센다
    t->next_due += skip * t->period;           // 위상(격자)은 유지한 채 점프
}

missed 를 텔레메트리로 내보내라. "루프가 가끔 이상해요"를 숫자로 바꾸는 유일한 방법이다.

협력형(cooperative)의 한계#

이 스케줄러는 태스크가 스스로 빨리 리턴해야 성립한다. 한 태스크가 50ms 를 먹으면 다른 모든 태스크가 그만큼 밀린다(선점 불가). 장점은 락이 거의 필요 없다는 것(태스크끼리 서로 선점하지 않으므로 태스크 간 공유 데이터에 임계구역이 필요 없다 — ISR 과의 공유는 여전히 필요하다). RTOS 로 갈지 말지는 "가장 긴 태스크 < 가장 짧은 데드라인"이 성립하느냐로 판단한다.

8. Watchdog#

  • IWDG(독립 워치독) 는 별도 저속 클럭으로 돌아 코어가 죽어도 살아 있다. 주기적으로 "먹여야(kick/pet)" 하고 안 먹이면 리셋.
  • 어디서 먹이는가가 설계다. 타이머 ISR 에서 무조건 먹이면 main loop 가 죽어도 워치독이 안 터진다 — 워치독이 무의미해진다. 정석: 각 주기 태스크가 "나 살아있음" 비트를 세우고, main loop 에서 모든 비트가 모였을 때만 kick 한 뒤 비트를 클리어한다 (multi-task watchdog / task alive mask).
  • window watchdog(WWDG) 는 "너무 일찍 먹여도 리셋" — 폭주한 루프가 워치독만 계속 먹이는 상황을 잡는다.
  • 리셋 원인(RCC_CSR 등)을 부팅 시 읽어 비휘발성에 남겨라. "왜 재부팅됐는지"를 모르면 현장 디버깅이 불가능하다.
  • 부팅 초기의 긴 작업(플래시 포맷, 센서 캘리브레이션)은 워치독 타임아웃을 넘기기 쉽다 → 미리 타임아웃을 길게 잡거나 그 구간에서 명시적으로 kick 한다.

9. 각 Q 핵심 포인트 한 줄#

Q함수한 줄
Q1isr_event / main_take / evt_missedpayload 먼저, flag 나중. volatile 은 배리어가 아니다. 소비 전 재발생은 missed 로 센다
Q2time_after / timeout_expired / elapsed절대 시각 비교 금지. 차이로 판단: (int32_t)(b-a) < 0, (now-start) >= timeout
Q3isr_tick / tick_read32비트 코어의 64비트 값은 hi→lo→hi 재시도(seqlock)로 스냅샷. 재시도 없으면 42억 틱이 사라진다
Q4debounce_update / debounce_pressed_edgeN회 연속 일치로만 레벨 확정, 에지는 전이 순간 한 번만 래치(consume-on-read). 카운터는 포화
Q5sched_runnext_due += period = 드리프트 0. 스톨 backlog 는 burst 대신 skip + missed 계수
Q6work_post / work_processISR 은 post 만(오버플로도 블로킹 대신 lost++), main 이 FIFO 로 디스패치. head 스냅샷으로 무한 드레인 방지

11. 면접 꼬리질문 (답 요지 포함)#

Q. "ISR 과 main 이 공유하는 변수에 volatile 만 붙이면 충분한가?" → 세 가지를 구분해서 답한다. (1) volatile 은 컴파일러가 값을 레지스터에 캐싱하거나 접근을 없애는 걸 막을 뿐이다. (2) 순서는 volatile 접근끼리만 보장되고, 비-volatile 접근과의 재정렬이나 CPU 재정렬은 못 막는다. (3) 원자성은 전혀 보장하지 않는다 — x++ 는 3연산. 단일코어 ISR↔main 이면 volatile + 컴파일러 배리어 + "데이터 먼저, 플래그 나중" 으로 충분하지만, 멀티코어/SMP/DMA 가 끼면 진짜 배리어(DMB)나 C11 atomics, 그리고 DMA 라면 캐시 유지까지 필요하다. "volatile 은 컴파일러에게 하는 말, barrier 는 CPU 에게 하는 말."

Q. "타임아웃을 if (now > start + timeout) 로 짰다. 뭐가 문제인가?" → 32비트 ms 틱은 49.7일(µs면 71분)에 랩한다. start + timeout 이 랩을 넘으면 그 값이 아주 작은 수가 되어 조건이 영원히 거짓이 되거나, 반대로 now 가 랩하면 즉시 참이 된다. 절대 시각을 비교하지 말고 차이로 판단해야 한다: (uint32_t)(now - start) >= timeout. 부호없는 뺄셈이 모듈로 2^32 라 랩을 자동으로 처리한다. 대소 비교가 필요하면 리눅스 time_after 관용구 (int32_t)(b - a) < 0. 전제는 두 시각의 간격이 2^31 미만이라는 것. 그리고 테스트를 랩 경계에 직접 놓고 짜라 — 49.7일 뒤에 현장에서 발견하면 늦다.

Q. "제어 루프가 가끔 한 주기를 건너뛴다. 어떻게 디버깅하나?" → 추측 대신 계측한다. ① ISR 진입/탈출에 GPIO 토글을 넣고 로직 애널라이저로 실행 시간과 주기를 본다(가장 빠르고 정확). ② DWT 사이클 카운터로 ISR/태스크별 최악 실행시간(WCET)과 지터를 기록해 high-water mark 로 남긴다. ③ 스케줄러의 missed/overrun 카운터를 텔레메트리로 뽑는다. ④ 인터럽트 마스킹 구간의 최대 길이를 계측한다. 흔한 범인은 플래시 쓰기(코어 스톨), 긴 critical section, 우선순위가 잘못 매겨진 통신 ISR, DMA 버스 경합, 그리고 로깅 경로에서의 블로킹 I/O다. "먼저 재고, 그다음 고친다" 는 태도 자체가 답의 절반이다.

Q. "우선순위 역전이 뭔가? 겪어봤다면 어떻게 고쳤나?" → 낮은 우선순위 태스크 L 이 락을 쥔 채 선점당하고 중간 우선순위 M 이 CPU 를 점유하면, 락을 기다리는 높은 우선순위 H 가 M 보다도 늦게 실행되는 현상. Mars Pathfinder 가 이걸로 반복 리셋됐다. 해법은 priority inheritance(락 보유자를 대기자 우선순위로 일시 승격 — FreeRTOS mutex 가 제공, binary semaphore 는 제공하지 않음), priority ceiling(락마다 상한을 정적으로 부여, 더 결정적이고 데드락도 방지). 다만 진짜 해법은 공유를 없애는 것 — ISR↔태스크는 락 없는 SPSC 큐로, 태스크 간은 메시지 패싱으로. 잡지 않는 락은 역전되지 않는다.

Q. "32비트 MCU 에서 64비트 마이크로초 타임스탬프를 어떻게 안전하게 읽나?" → 32비트 코어는 64비트를 한 번에 load 하지 못하므로 hi/lo 사이에 인터럽트가 들어오면 값이 찢어진다 — hi=0(구값)+lo=0(신값) 이면 42억 틱이 통째로 사라진다. 선택지는 셋. ① seqlock 스타일 재시도: hi → lo → hi 를 읽고 두 hi 가 같을 때만 채택(이 문제의 방식). 락 없고 지터 없고 최대 1회 재시도면 끝난다. ② 인터럽트 마스킹: 확실하지만 그만큼 인터럽트 지연이 늘어난다. ③ 하드웨어 지원: 64비트 타이머를 가진 코어거나, 하위 타이머를 읽으면 상위가 래치되는 페리페럴이면 그냥 읽으면 된다. ARMv7-M 에서 LDRD 는 원자적이지 않다는 점도 같이 말하면 좋다.

Q. "스케줄러가 200ms 멈췄다 돌아왔다. 밀린 20개 주기를 어떻게 할 건가?" → 작업의 성격에 따라 다르다고 답해야 한다. 제어 루프/센서 폴링은 skip: 200ms 전 데이터를 20번 처리하는 건 무의미하고, 그 버스트가 다음 주기를 또 밀어 악순환을 만든다. 1회만 실행하고 next_due 를 now 이후로 점프시키되 위상(period 격자)은 유지하고, 건너뛴 수를 missed 로 세서 텔레메트리로 보낸다. 반대로 적산이 의미 있는 작업(오도메트리 적분, 카운터, 통신 타임아웃 만료 처리)은 catch-up 이 맞다. 그리고 이런 일이 왜 생겼는지를 같이 조사한다 — 보통 플래시 쓰기나 디버거 정지, 긴 ISR 이고, 워치독 설계도 이 구간을 견디게 맞춰야 한다.
