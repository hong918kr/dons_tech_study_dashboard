02. Telemetry Framing (텔레메트리 프레이밍) · Q1-Q6 📡

바이트 스트림 위로 텔레메트리 레코드를 온전히 넘기는 법. CRC-16 → COBS → 수신 FSM 재동기화.

플랫폼약 5분🔧 make prob N=02_telemetry_framing
바이트 스트림(UART/radio) 위에서 텔레메트리 레코드 하나를 통째로, 온전하게 건네주는 법.
byte order → CRC-16 → COBS → 프레임 빌더 → 스트리밍 수신 FSM(재동기 포함) 순서로 쌓아 올린다.
Neros "Senior Firmware Engineer, Platform" 의 공용 런타임(logging/telemetry/IPC)이
맨 밑에서 깔고 있는 계층이 정확히 이것이다.

왜 이 토픽인가 (Neros 맥락)#

  • Neros 는 재밍에 견디는 자체 무선 링크로 FPV 드론을 몬다. 링크는 조용히 실패하지 않는다: 비트가 뒤집히고, 바이트가 통째로 사라지고, 수신기가 프레임 중간부터 붙는다.
  • UART/radio 는 경계가 없는 바이트 스트림이다. "어디서부터 어디까지가 한 레코드인가"를 프로토콜이 스스로 말해줘야 한다 → framing.
  • 플랫폼 팀이 만드는 건 한 개의 파서가 아니라 모든 팀이 쓰는 런타임이다. 로그 채널, 텔레메트리 채널, MCU↔Linux IPC 가 같은 프레이머를 공유한다. 그래서 "깨져도 안 멈추고 다음 프레임에 다시 붙는다"가 기능이 아니라 요구사항이다.
  • 대역폭이 곧 예산이다. 오버헤드가 payload 대비 몇 %인지 상한이 계산되는가를 묻는다.

핵심 개념#

1) 프레이밍 방식 비교#

방식동작장점단점
delimiter (sentinel)특정 바이트(0x00, 0x7E)로 경계 표시재동기가 공짜: 다음 delimiter 찾으면 끝payload 에 그 바이트가 나오면 escape/stuffing 필요
length-prefix[len][payload][crc]오버헤드 고정, 한 번에 read 가능len 이 깨지면 스트림 전체가 미아가 된다. 복구하려면 결국 sync word 를 추가
byte stuffing (SLIP)0xC0 를 0xDB 0xDC 로 치환구현 단순최악의 경우 크기 2배. 버퍼 산정 불가
COBS0x00 을 code 바이트 거리로 표현0x00 완전 제거 + 오버헤드 상한 고정코드가 한 겹 더, 스트리밍 인코딩이 살짝 까다로움

실무 정답은 대개 COBS + 0x00 delimiter + CRC 조합이다. length-prefix 를 같이 쓰더라도 길이 자체가 CRC 로 보호되어야 하고, 그 CRC 를 읽으려면 어차피 프레임 끝을 알아야 한다 — delimiter 가 그 닭-달걀 문제를 끊어준다.

2) COBS 오버헤드 = 254바이트당 1바이트 (≤ 0.4%)#

  • code 바이트 하나가 최대 254바이트의 데이터 블록을 커버한다(code 0xFF = 254B, 뒤에 0 없음).
  • 따라서 인코딩 길이 ≤ len + ceil(len/254) + 1. 입력이 무엇이든 상한이 계산된다 → 수신 버퍼를 정적으로 잡을 수 있다(= malloc 없는 펌웨어에서 결정적).
  • 이게 "Consistent"의 의미다: SLIP 처럼 최악 2배로 터지지 않는다.
  • 주의: 0이 하나도 없는 payload 도 +1 바이트는 낸다(선두 code 바이트).

3) CRC 선택: checksum vs CRC-16 vs CRC-32#

비용검출력언제
XOR/sum8거의 0약함(짝수개 비트오류·자리바뀜 못 잡음)NMEA 같은 레거시/텍스트
CRC-16 (0x1021)비트당 시프트 or 512B LUT임의 위치 버스트 오류 16비트까지 100%, 홀수 비트오류 전부프레임 ≤ 수백 바이트인 텔레메트리 — 여기서의 선택
CRC-321KB LUT더 강함. 프레임이 KB 급이거나 링크가 아주 나쁠 때펌웨어 이미지, 대용량 blob

프레임이 작을수록(≤ 256B) CRC-16 의 잔여 오류율은 충분히 낮고, 2바이트 vs 4바이트의 대역폭 차이가 링크 예산에서 더 크게 느껴진다.

CRC-16/CCITT-FALSE = poly 0x1021, init 0xFFFF, 무반사(no reflect), final xor 없음. 표준 check value: "123456789" → 0x29B1. (init 0x0000 인 XMODEM 변종은 0x31C3 — 다른 물건이다.)

4) CRC 가 잡는 것 / 못 잡는 것#

잡는다

  • 단일/홀수 개 비트 오류, 16비트 이하 버스트 오류(100%), 임의 2비트 오류(프레임 길이 제한 내).

못 잡는다

  • 악의적 변조: CRC 는 선형(linear)이다. 공격자는 payload 를 바꾸고 CRC 를 맞춰 다시 쓸 수 있다. 인증이 필요하면 MAC(HMAC/AES-CMAC) 이지 CRC 가 아니다. (재밍 환경 = 스푸핑 가능 환경)
  • 프레임 통째 유실·중복·순서 뒤바뀜: 이건 시퀀스 번호가 잡는다.
  • CRC 를 잘못된 범위에 계산한 버그: 오류 0건으로 보이지만 실제론 아무것도 안 지키는 상태.
  • 이론적 충돌: 2^-16 확률로 깨진 프레임이 통과한다. 명령 채널이면 시퀀스 번호 + 상위 검증을 얹는다.

5) 재동기(resync) 설계 — 이 파일의 핵심#

원칙: "실패는 정상 경로다." 수신기는 어떤 입력으로도 잠기면 안 된다.

  1. delimiter 가 곧 동기점이다. COBS 덕에 프레임 내부에는 0x00 이 절대 없으므로, 0x00 을 본 순간 "여기가 프레임 끝"이라고 무조건 단정할 수 있다. 탐색이 필요 없다.
  2. delimiter 를 받으면 성공이든 실패든 버퍼를 먼저 리셋한다. 리셋을 검증 뒤로 미루면 에러 경로에서 리셋을 빼먹는 버그가 반드시 생긴다.
  3. 오버플로는 폐기 + 계속 먹기. 버퍼가 넘치면 그 프레임에 "버림" 플래그만 세우고, delimiter 가 올 때까지 조용히 삼킨다. 여기서 버퍼를 비우고 다시 쌓기 시작하면 프레임 꼬리를 새 프레임의 머리로 오해한다(가짜 프레임 양산).
  4. 카운터를 분리한다: frames_ok / crc_err / overrun. 현장 디버깅에서 이 세 숫자의 비율이 곧 진단이다 — crc_err 만 증가 = 링크 품질/간섭, overrun 만 증가 = 송신 측 MTU 불일치 또는 소비 지연, 둘 다 0 인데 frames_ok 도 0 = 보드레이트/배선/전원 문제(바이트 자체가 안 옴).
  5. 빈 프레임(연속 delimiter)은 조용히 무시한다. 링크 idle 에 0x00 을 흘려보내는 구현이 흔하고, 이걸 에러로 세면 카운터가 오염되어 진단이 죽는다.

6) 부분 프레임(partial frame)과 타임아웃#

  • delimiter 가 영영 안 오면 버퍼는 반쯤 찬 채로 영원히 대기한다. 송신기가 프레임 중간에 죽거나 링크가 끊기면 실제로 일어난다.
  • 그래서 실무 수신기는 inter-byte timeout(예: 마지막 바이트 이후 N ms)을 두고 프레임을 폐기 + timeout 카운터 증가 후 리셋한다. 이 연습 파일은 시간 소스를 안 쓰므로 버퍼 초과(overrun)로 같은 상황을 흉내 낸다 — 면접에서는 반드시 타임아웃을 먼저 말할 것.
  • 타임아웃 값은 프레임최대길이 / 보드레이트 의 수 배로 잡는다(예: 115200bps, 70B → 약 6ms → 20~50ms).

문제별 핵심 포인트#

  • Q1. put/get u16/u32 LE — 멀티바이트 필드는 바이트 단위로 직접 깔고 직접 읽는다. 정렬(alignment)·패딩·호스트 엔디안에 의존하지 않으므로 MCU와 Linux 지상국이 항상 일치한다.
  • Q2. crc16_ccitt — 바이트를 상위 8비트에 XOR → 8번 시프트, MSB 가 1이면 poly XOR. 검증은 항상 known-answer("123456789" → 0x29B1) 로. 속도가 필요하면 256엔트리 LUT(512B).
  • Q3. cobs_encode — code 바이트 자리를 미리 비워두고(reserve) 블록이 끝날 때 채운다. 0을 만나거나 254바이트가 차면 블록 마감. 0xFF 블록으로 입력이 정확히 끝나면 code 예약 불필요.
  • Q4. cobs_decode — code-1 바이트 복사 후, code != 0xFF 이고 입력이 남았을 때만 0을 복원. "마지막 블록 뒤에는 0 없음" 규칙을 빠뜨리면 payload 끝에 유령 0이 붙는다.
  • Q5. frame_build — CRC 는 원본 payload 에 대해 계산 → LE 2B 로 붙임 → 전체를 COBS → 마지막에 0x00. 순서를 뒤집어 COBS 결과 위에 CRC 를 얹으면 검증 범위가 stuffing 을 포함해 의미가 흐려지고, 수신 측은 CRC 를 읽으려고 COBS 를 먼저 풀어야 하는 순환에 빠진다.
  • Q6. rx_feed FSM — 바이트 하나씩 누적 → delimiter 에서 디코드+CRC → 성공 시 true. 어떤 경로로 빠져나가든 버퍼는 리셋되고, 카운터는 frames_ok/crc_err/overrun 으로 분리. 오버런 프레임은 delimiter 까지 삼켜서 버리고, 파서는 절대 멈추지 않는다.

흔한 함정#

  1. packed struct 직송 — memcpy(tx, &telem, sizeof telem). 패딩(컴파일러/ABI마다 다름), 호스트 엔디안, 타입 크기(long, enum, 포인터), 정렬이 전부 전선에 노출된다. __attribute__((packed)) 를 붙여도 엔디안은 안 고쳐지고, ARM 에서는 비정렬 접근이 느려지거나(strict-alignment 코어에서는) 폴트난다. → 필드별 직렬화(Q1)가 정답.
  2. 엔디안을 문서화하지 않음 — "LE 인가 BE 인가"는 취향이 아니라 프로토콜 스펙의 항목이다. 한쪽이 바꾸면 조용히 값이 뒤집힌 채 비행한다. CRC 자체도 2바이트라 순서를 정해야 한다.
  3. CRC 범위 모호 — payload 만? 헤더 포함? COBS 전? 후? 한 줄로 못 적으면 반드시 어긋난다. 여기 규칙: CRC = crc16(payload), 그 다음 payload||crc 전체를 COBS.
  4. 검증 전에 크기를 믿음 — 디코드 결과 길이가 2 미만인데 dl - 2 를 하면 size_t 언더플로로 거대한 길이가 나온다. 크기 검사를 뺄셈보다 먼저.
  5. 에러 경로에서 리셋 누락 — 한 번 깨진 뒤 파서가 영원히 쓰레기를 모으는 클래식 버그.
  6. 오버런 시 버퍼만 비우고 계속 쌓기 — 프레임 꼬리가 다음 프레임의 머리로 붙어 가짜 프레임이 생긴다.
  7. 카운터 통합 — errors 하나로 뭉치면 현장에서 원인 분리가 불가능해진다.

면접 꼬리질문#

  1. "왜 length-prefix 대신 COBS + delimiter 인가?" → length 가 깨지면 스트림 전체가 미아가 되고 재동기 수단이 따로 필요하다. COBS 는 프레임 안에 0x00 이 존재할 수 없음을 보장하므로 delimiter 하나로 경계 판정과 재동기가 동시에 해결된다. 오버헤드 상한도 254:1 로 계산 가능해 정적 버퍼를 잡을 수 있다.
  1. "COBS 오버헤드는 최악 얼마이고 왜 상한이 있나?" → code 바이트 하나가 최대 254B 를 커버하므로 len + ceil(len/254) + 1, 즉 0.4% 미만 + 1B. SLIP/byte-stuffing 은 최악 2배라 버퍼 산정이 불가능하다. 이 예측 가능성이 "Consistent" 의 핵심.
  1. "CRC-16 이면 충분한가? CRC-32 나 해시를 쓰면?" → 프레임이 수백 바이트 이하면 CRC-16 이 버스트 16비트까지 100% 검출하고 잔여 오류율도 충분히 낮다. 2바이트 절약이 링크 예산에 직접 들어간다. 단 CRC 는 무결성이지 인증이 아니다 — 재밍/스푸핑 환경에서 명령 채널이라면 CRC 위에 시퀀스 번호와 MAC(AES-CMAC 등)을 얹어야 한다.
  1. "프레임 중간에 링크가 끊기면? 수신기가 영원히 기다리지 않나?" → 그래서 inter-byte timeout 이 필요하다. 마지막 바이트 이후 N ms(프레임 최대 전송시간의 수 배) 지나면 폐기 + timeout 카운터 + 리셋. 버퍼 오버플로도 같은 폐기 경로로 합류시키되, delimiter 를 볼 때까지 계속 삼켜서 꼬리가 다음 프레임에 붙지 않게 한다.
  1. "현장에서 링크가 이상하다는데 어디부터 보나?" → frames_ok / crc_err / overrun(+ timeout, bytes_rx) 비율부터 본다. crc_err 만 증가 → RF 품질·간섭·안테나. overrun 만 증가 → 송수신 MTU 불일치나 소비 지연(ISR→태스크). bytes_rx 는 도는데 frames_ok=0 → 보드레이트/프레이밍 파라미터 불일치. bytes_rx 자체가 0 → 배선·전원·핀먹스. 카운터를 분리해 둔 덕에 재현 없이 원인이 좁혀진다.
  1. "ISR 안에서 rx_feed 를 돌려도 되나?" → 바이트당 작업은 O(1)이라 누적은 ISR 에서 해도 되지만, 디코드+CRC(프레임당 수십~수백 사이클) 는 ISR 지연을 튀게 한다. 실무는 ISR 은 링버퍼에 밀어넣기만 하고, delimiter 를 본 시점에 플래그/세마포어로 태스크를 깨워 파싱한다(01번 토픽의 SPSC 링버퍼와 짝).
