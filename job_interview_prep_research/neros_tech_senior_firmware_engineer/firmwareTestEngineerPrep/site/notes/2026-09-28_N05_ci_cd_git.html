1. CI/CD 한 문단#

  • CI (Continuous Integration): 커밋·MR마다 자동으로 빌드하고 테스트한다. "main은 항상 빌드되고 테스트를 통과한다"를 기계가 보장
  • CD (Continuous Delivery/Deployment): 통과한 빌드를 릴리즈 가능한 상태(서명된 펌웨어 이미지, 릴리즈 노트)로 자동 포장. 펌웨어에선 "양산 라인·필드에 배포 가능한 이미지까지" [추정: 드론은 수동 승인 게이트가 있을 가능성 큼]
  • 테스트 엔지니어의 역할: 파이프라인에 어떤 테스트를 어느 단계에 둘지 설계하고, 결과를 모니터링해서 릴리즈 전 빌드 안정성을 책임진다 (JD 문장 그대로)

2. .gitlab-ci.yml 기본 문법#

GitLab은 저장소 루트의 .gitlab-ci.yml을 읽어 pipeline을 만든다. pipeline = stage의 순서, stage 안의 job은 병렬.

핵심 키워드:

키워드의미
stagesstage 순서. 앞 stage의 job이 전부 성공해야 다음으로 (기본)
script실행할 셸 명령. 0이 아닌 종료 코드면 job 실패
imagejob을 돌릴 Docker 이미지 (docker executor일 때)
artifactsjob 결과 파일을 저장·다음 job에 전달. reports:junit은 테스트 결과 UI
needsstage 순서 무시하고 특정 job만 기다림 (DAG) → 빠른 파이프라인
rules이 job을 언제 만들지 (MR, main, 스케줄, 변경 파일)
tags어떤 runner에서 돌릴지 (하드웨어 붙은 runner 선택)
cache의존성(pip, 툴체인 다운로드)을 job 간 재사용. artifacts와 다름
parallel / parallel:matrix같은 job을 N개 또는 변수 조합별로 복제
when: manual사람이 버튼을 눌러야 실행 (릴리즈 게이트)
resource_group같은 그룹의 job은 한 번에 하나만 → 리그 독점
timeoutjob 제한 시간
retry실패 시 재시도. when: runner_system_failure처럼 인프라 실패만 재시도하게 제한 가능
interruptible새 커밋이 오면 이전 파이프라인 job 취소 가능

2.2 artifacts vs cache#

  • artifacts: 이 파이프라인의 결과물 (펌웨어 바이너리, 리포트, 로그). 다음 stage job이 받아 씀. 다운로드 가능
  • cache: 속도용 재사용 파일 (pip 캐시, 다운로드한 SDK). 없어도 결과는 같아야 함
  • 흔한 실수: 빌드한 펌웨어를 cache로 넘김 → 다른 파이프라인의 옛 바이너리를 테스트할 위험

→ 4개 job이 병렬로 생긴다. (제품명은 예시 [추정])

3. Runner — 하드웨어는 어디에 붙나#

  • runner = job을 실제로 실행하는 에이전트 프로그램(gitlab-runner). 등록할 때 executor(shell, docker, kubernetes 등)와 tag를 정함
  • shared runner: 클라우드/공용 서버. 빌드·unit·SITL에 사용. 병렬 많이
  • self-hosted tagged runner: 리그 옆 호스트 PC에 설치, tag 예: hil, fc-rev-b, rig-03. USB 장비 접근이 필요하므로 보통 shell executor 또는 장치를 넘긴 docker [추정: 일반적 관행]
  • runner 설정 concurrent = 1 (runner 호스트 전체) 또는 job에 resource_group: rig-03 → 리그 동시 사용 방지
  • 리그가 여러 대면 resource_group을 리그별로 두지 않고, 같은 tag의 runner 여러 대가 각자 concurrent=1로 잡을 나눠 가짐 → 자연스러운 리그 풀
  • CI_RUNNER_DESCRIPTION처럼 어느 리그에서 돌았는지를 결과에 남긴다 (리그별 flaky 추적)

4. 펌웨어 파이프라인 설계 (화이트보드용)#

설계 원칙 (말로 할 것):

  • 빠른 것 먼저, 비싼 것 나중. MR에선 피드백 속도가 생명 → HIL은 smoke만
  • 실패는 가장 싼 단계에서. nightly에서 잡힌 버그 → MR 단계로 내릴 수 있는 테스트를 추가
  • main은 항상 초록. 깨지면 최우선으로 revert 또는 fix (build stability가 JD 문장)
  • 릴리즈 = 태그된 커밋의 재현 빌드. 릴리즈 후보는 nightly보다 넓은 매트릭스 + 사람 승인
  • 결과는 데이터로 남긴다. 통과/실패 + 측정값 + 리그 + FW hash → 추세 분석

5. Flaky 테스트 정책#

단계규칙
감지같은 커밋에서 PASS와 FAIL이 모두 나오면 flaky. rerun으로 통과한 것도 flaky로 기록
측정테스트별·리그별 flaky율(최근 N회) 대시보드. JUnit 리포트를 모아 저장
격리 (quarantine)기준(예: 최근 50회 중 2% 초과 [예시 수치]) 넘으면 @pytest.mark.quarantine → MR 게이트에서 빠지고 nightly에서만 돌며 티켓 + 담당자
수정원인 분류: 테스트 코드(sleep, 상태 누수) / 리그(USB, 전원, 케이블) / 진짜 FW 간헐 버그
복귀수정 후 반복 실행(예: 100회 루프)으로 확인하고 quarantine 해제
금지조용한 무한 재시도, 이유 없는 skip, 허용오차를 슬쩍 넓히기
  • 핵심 메시지: flaky 테스트는 파이프라인 신뢰를 갉아먹는다. 사람들이 빨간불을 무시하기 시작하면 진짜 버그도 무시된다
  • 드론 맥락: 간헐적 실패는 필드 고장의 전조일 수 있다 → "flaky니까 무시"가 아니라 FW 간헐 버그 가능성부터 배제

7. Git 워크플로#

7.1 브랜치와 MR#

  • Trunk-based / short-lived branches: main에서 짧은 feature 브랜치 → MR → 리뷰 + CI 통과 → merge. 펌웨어 팀 12명 규모엔 이게 흔함 [추정]
  • 릴리즈 브랜치: release/1.4 에서 버그픽스만 cherry-pick → 태그 v1.4.2
  • MR 규칙: CI 초록 필수, 리뷰어 1명+, 테스트 추가 여부 확인

7.2 rebase vs merge#

mergerebase
히스토리merge commit이 생기고 분기 모양이 남음일직선. 내 커밋을 main 최신 위로 다시 쌓음
장점실제 일어난 일 그대로, 공유 브랜치에 안전읽기 쉬움, bisect가 쉬움
주의히스토리 지저분이미 push해서 남이 쓰는 브랜치는 rebase 금지 (히스토리 재작성)
  • 흔한 팀 규칙: 내 브랜치는 git rebase origin/main으로 최신화, MR은 squash 또는 fast-forward merge
  • git pull --rebase, 충돌 시 git rebase --continue / --abort

7.3 git bisect — 회귀를 찾는 테스트 엔지니어의 무기#

"v1.3에선 되던 failsafe 테스트가 v1.4에서 실패한다. 커밋이 200개 사이에 있다" → 이진 탐색으로 약 8번(log2 200 ≈ 7.6) 테스트하면 범인 커밋을 찾는다.

  • 125 = 이 커밋은 판정 불가(skip). 빌드 깨진 커밋 처리
  • flaky한 버그는 한 커밋에서 여러 번 돌려야 오판 안 함 (--count는 pytest-repeat plugin [추정: 플러그인 필요], 또는 셸 루프)
  • 하드웨어 리그에서 자동으로 bisect를 돌리는 job을 만들어 두면 "nightly 실패 → 아침에 범인 커밋 리포트"가 된다

7.4 태그와 펌웨어 버전, git hash 삽입#

  • 릴리즈 = annotated tag (git tag -a v1.4.2 -m "..."). 버전은 semver 비슷하게
  • 빌드 시 git describe --tags --dirty --always → 예: v1.4.2-17-g3a9f2c1-dirty (태그 이후 17커밋, hash 3a9f2c1, 커밋 안 된 변경 있음)
  • 이 문자열을 바이너리에 넣는다:
  • 부팅 배너·CLI version 명령·telemetry로 노출 → HIL 테스트가 플래시 후 버전을 읽어 기대 hash와 비교. "옛 펌웨어로 거짓 PASS" 방지
  • -dirty가 붙은 바이너리는 릴리즈 파이프라인에서 거부
  • 방산 추적성: "어떤 기체에 어떤 펌웨어가 들어갔나" → 양산 라인에서 버전 기록 [추정: 양산 규모상 필요]

8. 면접 예상 질문 + 영어 모범 답변#

Q1. "How would you integrate HIL tests into our GitLab pipeline?"#

I'd keep the merge-request pipeline fast: build every target in a pinned toolchain image, run host unit tests and SITL in parallel on shared runners, then a five-to-ten-minute HIL smoke on a rig. Each rig host runs a GitLab runner with tags like hil and the board revision, with concurrency one or a resource group so two jobs never share a rig. The HIL job starts with a rig health check, flashes the artifact from the build job, reads the version back, and publishes a JUnit report plus logs as artifacts even on failure. The full regression and soak tests run nightly on a schedule across all rigs, and releases add a manual approval gate after flight test.

Q2. "How do you keep builds stable before a release?"#

Main has to stay green, so a broken main is the top priority — revert first, then fix. I watch trends, not just today's result: pass rate and flaky rate per test and per rig, and measured values like boot time or loop jitter, so slow regressions show up before they fail. For the release candidate I rebuild from the tag, reject dirty builds, run the widest matrix, and attach the results to the release.

Q3. "Rebase or merge?"#

For my own branch I rebase onto main so history stays linear and bisect stays easy. I never rebase a branch other people have pulled. For merging into main I follow the team's convention — squash or fast-forward is common.

Q4. "A test started failing last week and nobody knows why."#

I'd git bisect it on a rig. Mark the last known good and the first bad commit, and run a script that builds, flashes, and runs the failing test several times per commit — exit 125 to skip commits that don't build. That finds the culprit in about log-two-of-N runs. If it's intermittent I increase the repetitions per commit so one lucky pass doesn't mislead the search.

Q5. "You haven't used GitLab CI or Jenkins?" (갭 질문)#

Honestly, not as the owner of the pipeline — at my previous teams the CI infrastructure was run by others. But the concepts map directly to what I have built: the chamber test platform had scheduling, shared hardware, status monitoring and results that other engineers relied on. I've gone through GitLab CI specifically — stages, rules, tagged runners, resource groups, JUnit artifacts — and I'm confident I can own it quickly. (Don: 실제로 CI를 만진 경험이 있으면 첫 문장 교체)
