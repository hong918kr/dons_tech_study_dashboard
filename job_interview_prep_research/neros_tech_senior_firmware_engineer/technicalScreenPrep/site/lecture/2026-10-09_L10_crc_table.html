🧮 L10 · CRC 테이블 방식 — 처음부터 천천히 (스크린의 CRC.c 이해하기)

32분 읽기601줄22개 절

10-08 스크린 Task 2에서 받은 CRC.c는 테이블(표) 방식이었다 [확인됨 Don]. 정확한 다항식은 기억에 없어서, 가장 흔한 CRC-8 (poly 0x07)로 처음부터 설명한다. 수학을 몰라도 따라올 수 있게 나머지 → XOR → 손으로 나누기 → 코드 → 표 순서로 한 계단씩 올라간다. 이 페이지의 숫자는 전부 프로그램으로 계산한 출력을 그대로 붙인 것이고, 같은 숫자를 C 테스트로 다시 확인했다 (python3 lecture/crc/explain.py, make -C lecture/crc test).

0. 이 노트 읽는 법#

구간내용필요도
1 ~ 6장CRC가 뭔지, 손으로 계산하기, 코드 한 줄의 의미꼭
7 ~ 9장표가 왜 되는지, 실제 CRC.c, 패킷에서 쓰는 법꼭 (스크린 Task 2와 직결)
10 ~ 11장CRC-16, CRC-32알면 좋음
12 ~ 15장파라미터 · 절충 · 테스트 · 면접 질문참고

끝까지 가서 외울 것은 세 줄뿐이다 (16장). 막히면 그 장의 숫자 출력을 손가락으로 한 줄씩 따라가면 된다.

1. CRC가 하려는 일 — "나머지"로 오류 찾기#

먼저 10진수로 생각해 보자. 보내는 쪽과 받는 쪽이 "7로 나눈 나머지를 같이 보내자"고 약속했다고 하자.

  • 데이터가 조금만 깨져도 나머지가 달라질 가능성이 높다 → 받은 쪽이 "깨졌다"를 알 수 있다
  • CRC가 하는 일이 정확히 이것이다. 다만 두 가지가 다르다:
  • ① 숫자 대신 비트열을 나눈다
  • ② 보통의 빼기 대신 XOR로 나눈다 (2장) — 그래야 하드웨어 · 코드로 아주 싸게 계산된다
  • 약속한 나누는 수(위의 7)를 CRC에서는 생성 다항식, poly라고 부른다. CRC-8에서는 0x07

2. 준비물 ① XOR — 자리올림 없는 덧셈#

aba XOR b
000
011
101
110
  • "같으면 0, 다르면 1". 덧셈인데 1 + 1 = 0이고 자리올림(받아올림)이 없다
  • 그래서 빼기도 XOR과 똑같다 (1 − 1 = 0, 0 − 1 = 1, 빌려오기 없음) → CRC 나눗셈에서 "빼기"는 전부 XOR
  • C에서는 ^. 예: 0b1100 ^ 0b1010 = 0b0110
  • 같은 값을 두 번 XOR하면 원래대로: x ^ k ^ k = x (나중에 7장에서 쓴다)

3. 준비물 ② poly 0x07을 9비트로 읽기#

  • 0x07 = 0000 0111. 그런데 CRC-8의 진짜 나누는 수는 맨 앞에 1이 하나 더 붙은 9비트 1 0000 0111 (= 0x107)이다
  • 다항식으로 쓰면 x⁸ + x² + x + 1 — 비트가 1인 자리의 번호가 지수다 (8번, 2번, 1번, 0번 자리)
  • 맨 앞 1(x⁸)은 항상 1이라서 적지 않는다. 그래서 문서 · 코드에는 0x07만 나온다
  • 왜 맨 앞이 항상 1인가: 나누는 수의 맨 앞자리가 0이면 그건 그냥 더 짧은 수다. 8비트 나머지를 얻으려면 9비트짜리로 나눠야 한다 (10진수에서 두 자리 수로 나누면 나머지는 한 자리인 것처럼)

4. 손으로 나눠 보기 — 데이터 '1' (0x31)#

학교에서 배운 긴 나눗셈과 같다. 다른 점은 빼기 대신 XOR, 그리고 "몇 번 들어가나"를 고민할 필요가 없다는 것 — 맨 앞 비트가 1이면 나누는 수를 XOR, 0이면 건너뛴다. 이게 전부다.

한 줄씩 읽기:

6. 바이트가 여러 개면 — "12" (0x31, 0x32)#

  • 첫 바이트를 처리한 결과 0x97이 상자에 남아 있는 상태에서 두 번째 바이트를 XOR한다 (0x97 ^ 0x32 = 0xA5)
  • 즉 앞의 모든 데이터가 상자 안에 요약돼 있고, 새 바이트가 거기에 섞인 뒤 다시 8번 돈다
  • 그래서 어느 바이트의 어느 비트가 바뀌어도 결과가 바뀐다
  • 위 출력의 아래쪽 [테이블 방식]이 바이트당 한 줄로 같은 답을 낸다 — 이게 7장의 주제

7. 테이블은 왜 되나 — 핵심 장#

7.1 관찰: 8번 돌리는 일은 "8비트 값 하나"에만 달려 있다#

6장에서 두 번째 바이트를 처리할 때를 다시 보자:

  1. crc ^= byte → 상자 = 0xA5
  2. 8번 돌린다 → 0x72

2번에서 8번 돌리는 동안 쓰는 정보는 상자 안의 8비트(0xA5)뿐이다. 데이터를 더 읽지도 않고, 이전 상태를 따로 기억하지도 않는다. 그러니 "0xA5를 넣고 8번 돌리면 0x72가 나온다"는 사실은 언제나 같다.

8비트 값은 0x00~0xFF, 256가지뿐이다. → 256개 결과를 미리 다 계산해서 표에 적어 두면, 8번 돌리는 대신 표를 한 번 보면 된다.

7.2 그래서 루프가 한 줄이 된다#

  • T[i] = "상자에 i를 넣고 8번 돌린 결과"
  • 6장 예: T[0x00 ^ 0x31] = T[0x31] = 0x97 → T[0x97 ^ 0x32] = T[0xA5] = 0x72. 비트 방식과 같은 답

7.3 표 만드는 코드 — 5장 루프의 안쪽을 256번#

  • 5장 코드에서 crc ^= *data++ 부분만 빼고, "8번 돌리기"를 i = 0..255 각각에 대해 해 둔 것이다

7.4 보너스: 표는 8칸만 있으면 나머지를 만들 수 있다 (XOR 성질)#

CRC 계산은 XOR과 시프트로만 돼 있어서 T[a ^ b] = T[a] ^ T[b]가 성립한다. 그래서 비트 하나짜리 8칸만 알면 어떤 칸이든 조합으로 나온다:

  • T[0x01] = 0x07 — 바이트 1을 넣으면 정확히 poly가 나온다. 맨 아래 1이 7번 밀려 올라가 맨 위에 도착하고, 8번째에 밀려 나가면서 ^0x07이 한 번 일어나기 때문
  • 그래서 처음 보는 CRC.c의 표에서 둘째 칸(T[1])을 보면 poly를 바로 안다
  • T[0x02] = 0x0E = 0x07 × 2 … 처음 몇 칸은 그냥 두 배씩, 맨 위가 넘칠 때부터 XOR이 섞인다

8. 실제 CRC.c 모양 — 표를 flash에 박아 둔 것#

표 읽는 법:

질문답

9. 패킷에서 쓰는 법 — 스크린 Task 2와 연결#

L09의 프레임 형식(SYNC | LEN | PAYLOAD | CRC)으로:

  • 보내는 쪽: LEN + PAYLOAD에 대해 crc8() → 프레임 끝에 붙인다 (SYNC는 보통 범위 밖 — 프로토콜마다 확인)
  • 받는 쪽: 같은 범위로 다시 계산해서 받은 CRC와 비교. 다르면 그 프레임을 버린다 (L09의 extract_packet은 SYNC 한 바이트만 버리고 다시 찾는다)
  • 마지막 줄: 이런 CRC(반사 없음 · xorout 0)는 CRC까지 포함해서 다시 돌리면 0이 나온다 → "0인가?"만 봐도 된다
  • extract_packet 입장에서는 crc8(data, len)의 안이 비트 방식이든 표 방식이든 결과가 같다 — 표는 속도를 위한 것일 뿐

10. CRC-16 — 상자가 16비트일 뿐, 생각은 같다#

CRC-16/CCITT-FALSE(poly 0x1021, 시작값 0xFFFF)로 '1'을 처리하는 한 번을 숫자로:

왜 (crc << 8) ^ T[(crc >> 8) ^ byte]인가 — 천천히:

단계설명
① 상자를 둘로 나눈다위 8비트(crc >> 8 = 0xFF)와 아래 8비트(0xFF)
② 새 바이트는 위 8비트와 섞인다비트 방식에서 crc ^= byte << 8 — 바이트가 상자 위쪽에 XOR된다
③ 8번 돌리는 동안 "맨 위 비트가 1인가?"를 보는 건 위 8비트뿐그러니 8번 동안 일어나는 XOR들은 (위 8비트 ^ byte) 값 하나로 정해진다 → 표 인덱스 = 0xFF ^ 0x31 = 0xCE
④ 아래 8비트는 8번 밀리는 동안 위로 올라갈 뿐crc << 8 (16비트로 자르면 0xFF00)
⑤ 둘을 합친다0xFF00 ^ T[0xCE] = 0xFF00 ^ 0x3882 = 0xC782
  • CRC-8에서는 상자 전체가 8비트라 ④가 없었다 → T[crc ^ byte]만 남은 것
  • T16[1] = 0x1021 — 여기서도 둘째 칸이 poly
  • 같은 poly · 같은 식에 시작값만 0x0000이면 CRC-16/XMODEM (check 값 0x31C3) — 시작값 하나로 결과가 달라진다

11. CRC-32 (반사형) — 거울에 비친 같은 것#

  • Ethernet · zlib · PNG의 CRC-32는 비트를 아래(LSB)부터 처리한다 (UART가 LSB부터 보내는 순서). 그래서 모든 게 거울처럼 뒤집힌다:

표 방식 == 비트 방식 (무작위 200번)빠른 구현이 원리 구현과 같은지 (정답 모델 비교)
나머지 0 (residue)데이터 + CRC를 다시 돌리면 0
1비트 오류를 전부 잡나32바이트 × 8비트 = 256가지를 하나씩 뒤집어 본다

15. 면접 · 온사이트 질문#

질문답의 핵심
"Why a CRC instead of a checksum?"합 · XOR 체크섬은 순서가 바뀌거나 같은 비트가 두 번 틀리면 못 잡는다. CRC는 1비트 오류 전부, CRC 폭 이하 길이의 연속 오류(burst) 전부를 잡는다
"How does the table version work?"8번 돌리는 일이 8비트 값 하나(crc ^ byte)에만 달려 있으니, 256개 결과를 미리 표로. 바이트당 표 한 번
"Table in RAM or flash?"고정이면 const로 flash (RAM 0). 시작할 때 만들면 코드는 작지만 RAM을 쓴다
"Our CRC doesn't match the other side."7개 파라미터를 하나씩 + CRC 범위(SYNC 포함?) + CRC 바이트 순서. "123456789" check 값부터 맞춘다
"Does a CRC protect against tampering?"아니다 — 우연한 오류 검출용. 위조 방지는 HMAC · 서명 (secure boot · OTA)
"Would you use the STM32 CRC peripheral?"큰 데이터(이미지 검증)엔 예. 단 기본 설정이 zlib CRC-32와 다를 수 있으니 상대편과 파라미터 확인

16. 외울 세 줄 + 스스로 확인#

① CRC = 데이터를 poly로 XOR-나눗셈한 나머지. ② 비트 방식 = "맨 위가 1이면 밀고 ^poly, 아니면 밀기만"을 비트마다. ③ 표 방식 = 그 8번을 256개 미리 계산 → crc = T[crc ^ byte].

질문답
CRC-8 poly 0x07은 실제로 몇 비트로 나누나?9비트 1 0000 0111 — 맨 앞 1은 생략해서 적는다
비트 방식에서 왜 8번 반복하나?바이트 하나 = 8비트, 비트 하나에 나눗셈 한 단계
표의 칸이 왜 256개인가?crc ^ byte가 8비트 → 가능한 값 256가지
T[1]은 무엇인가?poly (0x07)
CRC-16 표 루프에서 crc << 8은 무엇인가?아래 8비트가 8번 밀려 위로 올라간 것
같은 poly인데 결과가 다르다면?init · 반사 · xorout · 범위 · 바이트 순서 중 무엇이 다른지
