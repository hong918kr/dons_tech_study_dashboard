1. Task 1 · 문제 재구성 (Don 기억 기준)#

"Implement a byte ring buffer in C. The caller provides the storage. Define the struct yourself."

함수동작 (Don 기억)재구성에서 정한 세부 [추정]
rb_init(rb_t *rb, uint8_t *rb_buf, uint8_t capacity)밖에서 받은 버퍼로 초기화head = tail = count = 0
rb_is_empty / rb_is_fullcount == 0 / count == capacity
rb_push_byte(rb, uint8_t byte) / rb_pop_byte(rb, uint8_t *out)한 바이트가득 / 비면 false (pop 결과는 *out으로)
rb_push(rb, items, len)남은 자리 < len이면 false아무것도 안 넣는다 (부분 쓰기 없음)
rb_pop(rb, items, len)들어 있는 것 < len이면 false아무것도 안 뺀다
rb_peek(rb, uint8_t offset, …)tail에서 offset번째 보기bool rb_peek(const rb_t*, uint8_t offset, uint8_t *out) — 범위 밖이면 false, 소비 안 함 [확인됨 Don: 출력 인자 이름 *out]
  • 면접관이 "외부 버퍼 + uint8_t capacity"로 준 의미 [추정]: 펌웨어 스타일(정적 버퍼, malloc 없음)을 아는지, 그리고 용량이 2의 거듭제곱이 아닐 수 있다 → 마스크 대신 %가 필요
  • rb_peek(offset)이 들어 있는 이유 [추정]: Task 2에서 헤더와 CRC를 꺼내지 않고 들여다보려고 — 두 문제가 이어져 있었다

2. Task 1 · 참고 풀이#

결정이유 (면접에서 말할 것)
count로 full/empty 구분head == tail이 빈 것인지 가득 찬 것인지 모호함을 없앤다. 용량 전부 사용
% capacity용량이 임의 값(uint8_t)이라 & (N-1) 마스크를 못 쓴다
bulk는 먼저 검사 후 실행all-or-nothing — 실패하면 상태가 그대로 (호출자가 재시도하기 쉬움, 프레임이 반쪽으로 안 들어감)
bulk를 push_byte 반복으로가장 단순하고 맞추기 쉽다. 성능이 필요하면 wrap 지점에서 memcpy 두 번 (4절)
peek은 const rb_t*보기만 한다는 것을 타입으로 약속
NULL 검사 생략이 재구성에선 생략. 실무 API라면 rb, items, byte NULL 검사 또는 assert — 면접에서 "I'd add NULL checks / asserts at the API boundary"라고 말하면 충분

4. Task 1 · 꼬리 질문과 온사이트에서 나올 확장#

질문답의 핵심
"The producer is a UART ISR, consumer is main. Is this safe?"아니다 — push와 pop이 둘 다 count를 고친다 (read-modify-write 경쟁). 해결: ① 짧은 critical section(인터럽트 끄기), ② count를 없애고 free-running head/tail (head는 ISR만, tail은 main만 쓰기 = SPSC) + C11 atomics acquire/release (L05 C 06, onsitePrep N05)
"Make bulk push faster."wrap 지점까지 memcpy 한 번 + 나머지 앞에서 한 번 (L03 10절)
"Why uint8_t capacity? What breaks?"최대 255 바이트. rb_peek의 uint8_t offset도 같은 한계. 큰 버퍼면 size_t로 — API 타입이 섞이면 경고 · 버그의 원인
"Return how many were written instead of false?"부분 쓰기 버전: size_t rb_write(rb, items, len) → 쓴 개수 반환 (UART 스트림엔 이쪽이 자연스럽다). 프레임 단위면 all-or-nothing이 맞다 — 정책 선택을 말로
"Overwrite oldest when full?"tail을 한 칸 밀고 dropped++ — 로그 · 텔레메트리용. 명령 큐엔 쓰지 않는다
"Feed it from DMA?"circular DMA + NDTR로 head 계산, half/full/idle 인터럽트, 캐시 invalidate (onsitePrep dma_circular_rx.c)
"How do you test the ISR version?"host: 두 스레드로 수백만 개 시퀀스 번호 + ThreadSanitizer. 타깃: 최대 baud 카운터 패턴 + 플래시 쓰기 부하, drop 카운터 0

5. Task 2 · extract_packet (보너스) 재구성#

"Implement extract_packet. A CRC library (CRC.c) is provided." — 함수 하나. 패킷 형식 · CRC 종류 · 시그니처는 기억에 없음 → 아래는 가장 전형적인 형태로 [추정]한 것.

5.1 가정한 형식과 시그니처#

실제 면접의 CRC.c는 테이블(lookup table) 방식이었다 [확인됨 Don]. 위는 같은 결과를 내는 비트 방식이다. 테이블 방식이 어떻게 만들어지고 왜 같은 값이 나오는지는 L10 CRC 테이블 방식 — extract_packet 입장에서는 crc8(data, len) 호출만 같으면 내부 구현은 상관없다.

5.2 알고리즘 — 왜 rb_peek(offset)이 필요했나#

단계할 일쓰는 함수
1앞쪽 쓰레기를 SYNC가 나올 때까지 버린다rb_peek(0) · rb_pop_byte
2LEN을 꺼내지 않고 본다. 없으면 "need more"rb_peek(1)
3프레임 전체(LEN + 3)가 다 왔는지 count로 확인. 아직이면 아무것도 버리지 않고 "need more"rb->count
4LEN + PAYLOAD를 peek으로 복사해 CRC 계산, 받은 CRC와 비교rb_peek(1..LEN+2) · crc8
5CRC가 틀리면 SYNC 한 바이트만 버리고 1로 (그 뒤에 진짜 프레임이 있을 수 있다)rb_pop_byte
6맞으면 프레임을 pop해서 payload를 out에 복사, 길이 반환rb_pop
  • 핵심: 확인이 끝나기 전에는 꺼내지 않는다(peek) → 프레임이 반만 왔을 때 데이터를 잃지 않는다. 그래서 Task 1에 rb_peek(offset)이 있었다고 보는 게 자연스럽다

찾은 버그: 노이즈로 생긴 가짜 0xAA 뒤에 LEN = 200이 오면, 프레임(203바이트)이 용량 8짜리 버퍼에는 절대 다 들어올 수 없다. 처음 버전은 "아직 다 안 왔다"며 영원히 PKT_NEED_MORE를 돌려주고, 버퍼가 차서 진짜 패킷도 못 들어온다 → 링크가 멈춤. 수정: LEN + 3 > capacity면 가짜 sync로 보고 한 바이트 버린다. 수정 전 코드로 이 테스트를 돌리면 assert 실패를 실제로 확인했다.

면접 · 온사이트에서 쓸 문장: "I'd also test a false sync followed by an impossible length — a naive parser waits forever and the link stalls." — 테스트 엔지니어다운 엣지 케이스

꼬리 질문답의 핵심
"CRC16 instead?"프레임 끝 2바이트, 엔디언 확인 (little/big), 라이브러리 함수 시그니처만 바뀐다
"Byte-by-byte from an ISR?"peek 대신 상태 머신(WAIT_SYNC → LEN → PAYLOAD → CRC)으로 바이트마다 처리 — 버퍼 재스캔 없음
"Timeout between bytes?"마지막 바이트 이후 N ms 지나면 상태 리셋 (반쪽 프레임에 영원히 매달리지 않게)
"Escape sequences?"SYNC가 payload에 나올 수 있다 → 길이 기반이면 괜찮지만 resync가 늦을 수 있음. 대안: COBS / SLIP
"How would you test this on the rig?"실제 UART로 프레임 + 노이즈 + 비트 오류 주입, 처리량 · CRC 오류 카운터 · resync 시간 측정 (S02)
