# 🧾 C05 비행 로그에서 유실 · 중복 · 순서 바뀜 세기 (16비트 wrap)

> 테스트 엔지니어 일상 그 자체: 로그를 받아 "패킷 몇 개 잃었나?" 질문이 단계적으로 어려워진다 — 기본 → 카운터 wrap → 깨진 줄 → 늦게 온 패킷.

## 1. 면접관 문장 (단계적으로 나옴)

> "Here's a log from a 10-minute flight test. Every telemetry line has a seq field. Tell me how many packets we lost."
> "...The counter is 16-bit."
> "...Some lines are corrupted."
> "...Sometimes packets arrive out of order."

## 2. 먼저 던질 질문

1. "Does the first line start at 0, or anywhere?" → 첫 값을 기준으로
2. "If a packet arrives late, is it lost or not?" → 늦게라도 왔으면 lost에서 빼고 reordered로
3. "A big backwards jump — reboot, or very late packet?" → 반쪽(32768) 기준으로 앞/뒤 판단
4. "Corrupted lines: skip and count?"

## 3. 손으로

| 입력 seq | expected | diff = (seq−expected) mod 65536 | 판정 |
|---|---|---|---|
| 65534 | — | — | 기준 |
| 65535 | 65535 | 0 | 정상 |
| 0 | 0 | 0 | 정상 (**wrap은 gap이 아님**) |
| 3 | 1 | 2 | 앞으로 점프 → 1, 2 유실 |
| 2 | 4 | 65534 (> 32768) | 과거 값 → missing에 있음 → 늦게 옴: lost −1, reordered +1 |
| 2 | 4 | 65534 | 과거 값 → missing에 없음 → 중복 |

## 4. 엣지 케이스

- [ ] 줄이 하나뿐 → lost 0
- [ ] wrap 경계 정확히 (65535 → 0)
- [ ] wrap을 건넌 gap (65535 → 2 = 0, 1 유실)
- [ ] 중복
- [ ] 늦게 온 패킷 · 그 패킷의 중복
- [ ] `seq=` 뒤 숫자 없음, 65536 이상, 바이너리 쓰레기 줄
- [ ] 큰 gap에서 missing 기록이 메모리를 무한정 먹지 않게 (상한)

## 5. 접근

- `diff = (seq - expected) % mod`: 0이면 정상, `< mod/2`면 앞으로 점프(diff개 유실), 아니면 과거 값
- 과거 값은 `missing` 집합으로 늦게 온 것 vs 중복 구분. 집합 크기에 상한 (오래된 것부터 잊음 — 잊은 것은 lost로 남음)
- 파싱은 `re.search(r"\bseq=(\d+)\b", line)` 하나, 실패하면 `bad_lines += 1` 하고 계속 (로그 하나 깨졌다고 분석 전체가 죽으면 안 됨)

## 6. 테스트 핵심

```python
run = lambda seqs: analyze(["t=0 seq=%d" % s for s in seqs])
assert run([65534, 65535, 0, 1])["lost"] == 0
assert run([65535, 2])["lost"] == 2
r = run([1, 3, 2, 2]); assert r["reordered"] == 1 and r["duplicates"] == 1
```
