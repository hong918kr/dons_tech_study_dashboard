2. 신호 하나가 지나가는 길 — Michael의 latency 질문을 그림으로#

구간지연을 만드는 것측정 방법
stick → EdgeTX 출력ADC 샘플 주기, mixer 주기, CRSF 출력 주기조종기 CRSF 출력 선을 로직 분석기로, stick 대신 알려진 계단 입력 (트레이너 포트 / 시뮬레이션)
TX → RF → RXELRS packet rate(예: 500 Hz면 주기 2 ms → 평균 대기 ~1 ms), 패킷 손실 시 다음 패킷까지TX 입력 CRSF와 RX 출력 CRSF를 같은 로직 분석기 두 채널로 → 같은 채널 값이 나타나는 시각 차
RX → FCCRSF 프레임 길이 ÷ 420 kbaud (26바이트 ≈ 0.6 ms), FC RX task 주기, rc smoothing 필터CRSF 프레임 끝 ↔ DShot 출력 변화 (FC 안은 GPIO 토글 + DWT로 쪼갬)
FC 루프gyro/PID 루프 주기(예: 8 kHz → 125 µs)Betaflight CLI tasks(task별 주기 · 실행 시간) [확인 필요: 출력 형식]
FC → 모터DShot600 프레임 16비트 × 1.67 µs ≈ 27 µs, ESC 처리, 모터 · 프롭 기계 응답DShot 선 디코드, bidirectional DShot eRPM으로 실제 회전 변화
전체 (glass-to-glass 포함)위 합 + 영상고속 카메라로 stick과 모터/화면을 같이 촬영, 또는 LED + 포토다이오드

한 줄 답 (다음에 쓸 것): "I'd break the pipeline at every interface I can probe — the CRSF line out of the radio, the CRSF line into the flight controller, and the DShot line out — capture them on one logic analyzer with a shared timebase, inject a known step, and measure each hop. Inside the flight controller I'd use GPIO toggles or the cycle counter. Then I'd repeat it thousands of times to get a distribution, not one number, because the packet-rate wait is random."
