1. 세 세션 공통 틀 — 어떤 질문이든 이 순서#

순서할 일영어 한 줄
① 질문범위 · 제약 · 실패했을 때 동작"Before I start — a couple of questions about constraints."
② 가정 말하기답이 없으면 내가 정하고 적어 둔다"I'll assume X; tell me if that's wrong."
③ 그림 먼저블록도 / 데이터 흐름 / 상태"Let me draw the data flow first."
④ 깊게 하나면접관이 고르게 한다"Which part do you want me to go deeper on?"
⑤ 고장 모드무엇이 깨지면 어떻게 되나"Now, what happens when things go wrong."
⑥ 검증각 주장을 어떻게 테스트하나 (테스트 직군이므로 항상 마지막에)"Here's how I'd prove each of these."

2.2 Task 표 — 외워서 그릴 5줄 (비행 제어기, Cortex-M7 급 가정)#

task트리거주기우선순위
자이로 → 필터 → PID → 믹서 → 모터자이로 data-ready 인터럽트 → SPI DMA 완료4 kHz (250 µs)최상
RX 파싱 · 채널 갱신UART idle-line 인터럽트패킷마다 (250 Hz~1 kHz)2
failsafe 감시1 ms tick1 kHz2
배터리 ADC · 텔레메트리 TXtimer10~100 Hz3~4
로깅 (flash) · CLI/USB큐 / 이벤트—최하 (막혀도 루프에 영향 없게)
  • "How many tasks?" → "About five or six. Everything at the loop rate lives in one task so there's no hand-off jitter between gyro, PID and motor. Slower work is split by rate, and anything that can block — flash, USB — gets its own low-priority task."
  • "Which scheduler?" → "Preemptive fixed-priority RTOS, priorities by rate-monotonic — shorter period, higher priority. ISRs stay short and hand work to tasks. On the control path I avoid locks entirely with a latest-value double buffer; elsewhere mutexes with priority inheritance."
  • superloop은 언제? 일이 2~3개이고 마감이 하나일 때. 느린 일이 빠른 일을 막는 게 단점.

2.3 "Entire process" — 전원 켜고 비행까지#

부트로더(이미지 CRC 검사) → 클럭 · MPU · 메모리 → 드라이버 초기화 → 센서 self-test (WHO_AM_I, 값 범위) → 설정 로드(CRC) → task 시작 → 무장 전 점검 (스로틀 low · link alive · 센서 OK · 배터리 OK) → 무장 → 루프. watchdog은 루프 맨 끝에서만 킥.

3. 깊게 들어갈 하나 — 숫자까지 말할 수 있게#

3.1 Stack "증명" (stack · proof · pstack)#

단계방법
정적gcc -fstack-usage → 함수별 크기, 호출 그래프 최악 경로 합. 재귀 · 함수 포인터 · VLA는 금지 (분석이 깨짐)
인터럽트 몫예외 진입 8워드(32 B), FPU 문맥 포함 26워드(104 B) + ISR 사용량 × 중첩 깊이 → MSP에 더한다
동적시작 시 stack을 0xA5로 칠하고(painting) 스트레스 후 안 지워진 깊이 = high-water mark
여유상한/실측의 1.25~1.5배 [관례]
보호MPU guard · canary · RTOS overflow hook → 넘치면 조용히 깨지지 않고 즉시 fault
  • PSP vs MSP: MSP = 리셋 후 기본 · ISR · 커널. PSP = RTOS task(thread mode) 각자의 stack. 문맥 전환은 PendSV에서 PSP를 바꿔 끼우는 것. → "ISR stack usage goes on the MSP, not on every task stack."
  • Linux pstack <pid>: 실행 중 프로세스의 모든 스레드 stack trace (gdb 기반). companion computer에서 멈춘 프로세스 볼 때.
  • 영어: "I size it statically from the worst-case call path plus interrupt frames, confirm with stack painting under stress, keep 25–50% margin, and put an MPU guard below it so an overflow faults instead of corrupting memory."

3.2 타이밍 "증명"#

  1. 최악 실행 시간 C를 측정: 시작/끝 GPIO 토글 → 스코프, 또는 DWT cycle counter
  2. 이용률 U = Σ C/T. rate monotonic 충분조건 U ≤ n(2^(1/n) − 1) → n=3이면 0.78, n이 크면 0.69
  3. 애매하면 응답 시간 분석: R = C + Σ⌈R/T_j⌉·C_j (높은 우선순위 j) 반복 → R ≤ 마감이면 OK
예CTC/T
제어 루프80 µs250 µs0.32
RX30 µs1 ms0.03
텔레메트리200 µs20 ms0.01
합0.36 ≤ 0.78 ✓

RX 응답: R = 30 + ⌈R/250⌉·80 = 110 µs ≤ 1 ms ✓. 실측 아티팩트: 루프 지터 히스토그램 · CPU load(idle 카운터).

3.3 RX · TX · Motor#

경로구조함정
RXUART DMA 순환 버퍼 + idle-line 인터럽트 → task가 새 바이트만 파싱 (sync · len · CRC) → 최신값 mailbox + 수신 시각큐로 쌓으면 오래된 조종 명령이 늦게 적용됨
failsafe마지막 정상 프레임 시각 vs now, 100 ms 넘으면 failsafeCRC 실패 프레임은 "수신"이 아니다
TX고정 크기 큐 (가득 차면 오래된 것 버림 + 카운트) → DMA 송신송신 때문에 루프가 기다리면 안 됨
Motor믹서 → saturation → timer + DMA (PWM/DShot)무장 전 · 고장 · watchdog 리셋 시 기본값 0 보장

3.4 고장 모드 → 테스트 (마지막 5분용 표)#

주장검증
루프가 4 kHz 지터 없이 돈다GPIO + 스코프, 지터 히스토그램을 HIL CI에서 매번

과부하에도 루프는 지킨다로깅 · 텔레메트리 최대 → 루프 주기 측정

4. Debugging strategy — 어떤 버그든 이 순서#

4.1 틀 (발표와 같은 단어)#

단계할 일영어 한 줄
0. 증상 정리무엇이 · 언제부터 · 몇 대 중 몇 대 · 무엇이 바뀌었나 (FW/HW rev/환경)"What changed, and how many units?"
1. Repro재현 조건 찾기, 재현율 숫자로. 안 되면 조건을 극단으로 (온도 · 전압 · 부하 · 반복)"First I make it fail on demand."
2. Isolate반으로 나누기: FW vs HW, 보드 바꾸기, FW 버전 git bisect, 기능 끄기, 층 분리"Then I split the system in half until one block is left."
3. Capture실패 순간의 증거: 로그 · 레지스터 · 스코프/로직 분석기 트리거 · fault 덤프"I capture evidence at the moment of failure, not after."
4. Resolve원인 하나를 측정으로 확인한 뒤 고친다. 고친 뒤 같은 측정으로 재확인"I confirm the root cause with a measurement before I change anything."
↳ WAR (병렬)고치는 데 오래 걸리면 work-around로 빌드/라인을 먼저 풀어 준다"If the fix takes time, a work-around unblocks the build in parallel."
5. Itemize이 버그를 잡는 테스트 항목을 만든다"Then the check that would have caught it becomes a test item."
6. Stress · Scale같은 종류를 스트레스로 더 찾고, 다른 라인/제품에 적용"And I roll it out to the other lines."

4.2 증상 → 먼저 볼 것 (FW · 보드)#

증상먼저 볼 것
HardFaultCFSR(0xE000ED28) · HFSR(0xE000ED2C) · MMFAR/BFAR 읽기. stacked frame(R0–R3, R12, LR, PC, xPSR)에서 PC → addr2line. EXC_RETURN bit 2로 MSP/PSP 중 어느 stack인지
랜덤 리셋리셋 원인 레지스터 (STM32 RCC_CSR: watchdog · brownout · pin · software) → 원인별로 나눈다. brownout이면 전원 레일 스코프
가끔 데이터가 깨짐race (ISR ↔ task 공유 변수, volatile/atomic/critical section), DMA 버퍼와 캐시 일관성(Cortex-M7), stack overflow로 옆 메모리 덮음
디버거 붙이면 안 생김 / 릴리스에서만 생김타이밍 의존(race), 최적화로 드러나는 UB, 초기화 안 된 변수, volatile 누락
시간이 지나면 멈춤메모리 누수 · 큐 포화 · 카운터 overflow(32비트 ms는 49.7일) · 우선순위 역전 · deadlock
성능/지터GPIO 토글 + 스코프로 구간 측정, ISR 길이, 높은 우선순위 task가 CPU 독점

4.3 버스 디버그 — 30초 답#

버스먼저 볼 것

영어: "I start at the wire. If the bytes are on the bus, the problem is on the receiving side; if they aren't, it's the sender or the configuration."

5. 고장 난 PDB + 회로도#

5.1 30초 답 (외우기)#

"First I don't power it. I read the schematic for rating mistakes, inspect the board, and check for shorts with a meter. Then I power it from a current-limited bench supply, ramp the voltage, and measure each rail against the schematic. When something is off I isolate that block — lift a part, cut the load — and confirm the root cause with a measurement before I change the design. Finally I add the check that would have caught it to the board test."

순서: 증상(전부 vs 일부 보드?) → 회로도 리뷰 → 육안/현미경 → 무전원 저항 측정(단락) → 전류 제한 전원으로 천천히 → 레일 전압 · 리플 → 열화상 → 전자 부하 · 과도 → 블록 분리 → 같은 측정으로 재확인 · 기록.

6. 테스트 안 된 새 서브시스템 통합 + 결과 정리#

영어: "I'd go bottom-up — power, then talking on the bus, then function, then performance and fault injection — but I'd order the work by risk, so the thing that could crash the aircraft gets tested first."
