🔁 C02 고정 크기 FIFO — 꽉 찼을 때 (지난번 놓친 overflow)

4분 읽기77줄9개 절

"ring buffer"라는 단어 없이 나오는 ring buffer. ISR이 넣고 main이 뺀다 · 메모리 고정 이 두 말이 들리면 이것. 지난번 피드백의 정확한 지점: full 상태 push. 정책 두 가지(거절 / 가장 오래된 것 덮어쓰기)와 카운터를 코드와 테스트로 보여 준다.

1. 면접관 문장#

"An interrupt hands us one byte at a time and the main loop drains them later. Memory is fixed at startup — you can't grow anything. Give me put and get, and tell me what happens when the main loop falls behind."

마지막 문장 "what happens when the main loop falls behind" = overflow 질문이다. 여기서 바로 정책을 묻는다.

2. 먼저 던질 질문#

  1. "When it's full, should a new byte be rejected, or should it overwrite the oldest?" (UART RX는 보통 거절 + 카운트, 로그/텔레메트리 히스토리는 보통 덮어쓰기)
  2. "Do you want to know how many were lost?" → 카운터
  3. "Single producer, single consumer?" → 후속 질문 대비
  4. "Bulk put — all-or-nothing or partial?"

3. 손으로 (capacity 3)#

동작dataheadtailcount반환
put 1,2,3[1,2,3]003True×3
put 4 (거절)[1,2,3]003False, dropped=1
put 4 (덮어쓰기)[4,2,3]113True, overwritten=1
get (덮어쓰기 뒤)1222 (1은 사라짐)

덮어쓰기에서 실수하기 쉬운 점: head만 움직이고 tail을 안 밀면 다음 get이 방금 쓴 새 값을 돌려준다.

4. 엣지 케이스#

5. 접근#

  • data = [0]*cap 한 번만 할당, head(쓸 자리) · tail(읽을 자리) · count
  • count를 두면 empty/full 구분이 쉽다 (안 두면 한 칸 비우는 방식 — 말로 설명할 수 있게)
  • Python으로 빠르게: deque(maxlen=cap)는 덮어쓰기 정책만 된다. 거절 정책은 len(q) == cap 검사를 직접

6. 테스트 핵심#

  • 모델 대조: 랜덤 put/get 5000번을 deque와 비교 → wrap 버그를 다 잡는다

7. 후속 질문#

질문답
ISR과 main이 동시에 쓰면?SPSC: head는 ISR만, tail은 main만 갱신 → count를 공유하면 경쟁 → count 대신 free-running head/tail 차이로
C에서 %가 느리면?크기를 2의 거듭제곱으로, & (N-1)
덮어쓰기 + SPSC는?생산자가 tail을 건드리게 되어 단순 SPSC가 깨짐 → 거절이 기본이거나 critical section
이 FIFO를 어떻게 테스트하나 (테스트 직군)경계 4개 + 모델 대조 + 카운터 검증 + ISR 속도로 넣는 스트레스
