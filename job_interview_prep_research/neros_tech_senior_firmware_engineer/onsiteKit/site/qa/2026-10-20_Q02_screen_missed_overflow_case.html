1. 먼저 — 알 수 있는 것과 없는 것#

내용
확인된 것리크루터가 전한 한 줄: "missed the overflow case". 문제는 C byte ring buffer — rb_init(rb, uint8_t *buf, uint8_t capacity), size_t count/head/tail, push/pop byte, bulk push/pop all-or-nothing, rb_peek(rb, uint8_t offset, …)
모르는 것그때 Don이 쓴 실제 코드는 남아 있지 않다. 그래서 "overflow"가 아래 중 무엇이었는지 확정할 수 없다
그래서이 API에서 "overflow"라고 불릴 수 있는 4가지를 전부 막고, 전부 테스트로 보여 주는 것이 온사이트의 답이다 [추정]

스스로 떠올려 볼 질문: 그때 ① 꽉 찬 상태에서 push 테스트를 썼나? ② bulk push에서 자리 검사를 쓰기 전에 했나? ③ 그 검사를 count + len > capacity로 썼나 len > capacity - count로 썼나? ④ 면접관에게 "꽉 차면 어떻게 할까요?"를 물었나? — 기억나는 것이 있으면 알려 주면 이 페이지를 고친다.

2. "overflow case" 후보 4가지#

#경우틀린 코드 모양결과맞는 처리
①꽉 찬 상태에서 push_byte (가장 유력 [추정])full 검사 없이 쓰기, 또는 검사는 했지만 테스트에서 안 보여 줌head가 tail을 넘어가 가장 오래된 데이터를 조용히 덮어씀, count > capacityif count == capacity: return False + dropped += 1 (또는 정책이 overwrite면 tail도 같이 밀기)
②bulk push가 남은 자리보다 클 때바이트를 넣다가 중간에 full을 만남 → 일부만 들어감all-or-nothing 위반 — 프레임이 반쪽만 들어감쓰기 전에 if len > capacity - count: return False — 아무것도 바꾸지 않음
③검사식 자체의 정수 overflow (C)if (count + len > capacity)len이 아주 크면 count + len이 size_t에서 한 바퀴 돌아 작은 수가 됨 → 검사 통과 → 배열 밖 쓰기빼기 쪽으로: len > capacity - count (count ≤ capacity가 항상 참이라 빼기는 안전)
④uint8_t 인덱스/카운트 wrap (C)head나 새 count를 uint8_t 변수에 저장255 다음 0으로 돌아감 → 검사가 틀린 값을 봄인덱스 · count는 size_t, 다음 칸은 % capacity

③ · ④ 실제로 돌려 본 결과 (C, -Wall)#

출력: A wrong=0 right=1 · B newc=44 · C head=0 — 세 가지 모두 컴파일러 경고 없이 지나간다. 테스트로만 잡힌다.

3. 온사이트(Python)에서 — 코드보다 먼저 말로#

Python에는 ③ · ④ 같은 정수 overflow가 없다. 그래서 이번에 보여 줄 것은 ①②의 정책과 테스트다.

  1. 시작할 때: "Last time I missed the full-buffer case, so I'll call out overflow behavior up front."
  2. 질문: "When it's full, should a new byte be rejected, or should it overwrite the oldest?" — 정책을 면접관이 정하게 한다
  3. 질문: "For a bulk write that doesn't fit — all-or-nothing, or write what fits and return the count?"
  4. 잃은 데이터는 센다: "Losing data silently is the worst bug, so I count what I drop."
  5. 마지막 테스트에 overflow 줄이 반드시 있다: 꽉 찬 push → 반환값 · 카운터 · 기존 데이터와 순서가 그대로

4. Python 참고 풀이 + 테스트 (실행해서 OK 확인)#

테스트 줄막는 후보
push_byte(4) is False and dropped == 1 + 기존 데이터 순서 확인① 꽉 찬 상태 push
push(b"xyz") is False and count == 3 · 용량보다 큰 bulk · len 0② bulk all-or-nothing
20바퀴 push/pop · wrap 상태에서 peek④에 해당하는 인덱스 wrap (Python판)

5. 꼬리 질문 대비#

질문답
"What if it's a UART RX buffer and data keeps coming?"거절 + 카운트가 기본. 카운터를 텔레메트리로 내보내면 "main loop가 밀린다"는 것을 필드에서 볼 수 있다. 근본 해결은 버퍼 크기 · 소비 속도 · DMA
"When would you overwrite instead?"최신 값만 의미 있는 로그 · 텔레메트리 히스토리. 명령 큐에는 절대 안 쓴다 (오래된 명령이 사라짐)
"In C, how do you write the free-space check?"len > capacity - count — 더하기 대신 빼기로 써서 정수 overflow를 피한다
"ISR producer, main consumer?"count를 둘 다 고치면 경쟁. head는 ISR만, tail은 main만 쓰는 SPSC + free-running 인덱스
