1. 왜 중요한가 (FTE 관점)#

FW Test Engineer의 일은 "테스트를 많이 돌리는 것"이 아니다. 어떤 결함을 어느 층에서 가장 싸게 잡을지 정하고, 그 층을 자동으로 돌게 만드는 것이다.

드론은 SSD보다 이 결정이 더 중요하다. 이유는 세 가지다.

  1. 위층이 매우 비싸고 위험하다. 비행 시험 한 번은 배터리 · 조종사 · 장소 · 날씨 · 기체 파손 위험을 쓴다. SSD 챔버는 밤새 무인으로 돌지만, 비행은 사람이 붙어야 한다.
  2. 물리 세계가 루프 안에 있다. 제어 루프의 "정답"은 하나의 값이 아니라 응답 모양(rise time · overshoot · 노이즈)이다. 판정 기준(오라클)을 만드는 것 자체가 일이다.
  3. 안전 결함은 되돌릴 수 없다. 모터가 부팅 직후 도는 버그, failsafe가 늦는 버그는 사람을 다치게 한다. 그래서 failsafe · arming 같은 안전 경로는 여러 층에서 중복으로 테스트한다.

2. 용어부터 바로잡기 — SITL · SIH · HITL · HIL bench#

같은 단어가 프로젝트마다 다른 뜻으로 쓰인다. 면접이나 회의에서 "HIL"이라고 하면 무엇이 진짜고 무엇이 가짜인지를 먼저 확인해야 한다.

2.2 핵심 구분#

  • SITL: "코드 로직이 맞나". 타이밍 · 메모리 · 버스 · 인터럽트는 PC 것이라 가짜다.
  • PX4 HITL: "실제 MCU에서 이 FW가 실시간으로 돌 수 있나 (CPU · 메모리 · 스케줄링)". 하지만 센서 드라이버 · SPI · DMA · 실제 IMU 노이즈는 우회된다. 센서 값이 MAVLink 메시지로 들어오기 때문이다.
  • HIL bench: "실제 전기 신호에서 맞게 동작하나". 실제 UART 프레이밍 · 실제 DShot 파형 · 실제 전원 강하 · 실제 버스 에러를 본다. 비행 물리는 보통 없다.

⚠️ Gemini 정정: Gemini는 "PX4는 테스트 PC가 MAVLink의 HIL_SENSOR 패킷만 쏴주면 펌웨어가 알아서 가상 비행 시뮬레이션(SITL/HITL) 모드로 잘 돌아간다"고 했다. 부분만 맞다. PX4 문서 기준으로 (1) MAVLink 시뮬레이터 API(HIL_SENSOR · HIL_GPS 입력, HIL_ACTUATOR_CONTROLS 출력, TCP 4560)는 Gazebo Classic 같은 외부 시뮬레이터용 경로이고, (2) 새 Gazebo(gz) SITL은 MAVLink가 아니라 gz_bridge로 Gazebo transport를 직접 쓴다. (3) HITL은 "community supported"로 표시돼 있고 문서상 Gazebo Classic만 나오며 pwm_out_sim 모듈이 들어간 펌웨어가 필요하다. (4) 외부 시뮬레이터 없이 FC 안에서 물리를 돌리는 SIH가 대안으로 안내된다. 그리고 HITL은 센서 드라이버를 우회하므로 "실제 보드 테스트"와 같은 말이 아니다.

⚠️ Gemini 정정: Gemini는 "SITL/HIL 테스트 벤치"를 하나의 그림에 묶고, 3단계(브링업 → SITL/유닛 → HIL)로 끝냈다. 실제로는 그 위에 통합 리그 · 비행 시험 · 공장(EOL) · 필드 텔레메트리 층이 있고, 그 아래에 정적 분석이 있다. 그리고 "HIL"이 PX4 HITL(센서는 MAVLink로 가짜)인지 HIL bench(전기 신호 진짜)인지 구분해야 한다. 이 단원은 10층으로 다시 정리한다.

3.3 L1 — 정적 분석 · 빌드 검사#

무엇을 하나

  • 컴파일러 경고를 에러로 (-Werror). Betaflight CI는 실제로 make EXTRA_FLAGS=-Werror checks와 make EXTRA_FLAGS=-Werror test-all을 돌린다 (GitHub Actions ci.yml, 2026-10 master 기준 확인).
  • 정적 분석기: cppcheck (Betaflight Makefile에 cppcheck-result.xml 타깃이 있음), clang-tidy, 상용 도구 (Coverity, Polyspace, PC-lint 등) [도구 선택은 회사마다].
  • 코딩 규칙: MISRA C:2012 계열 (자동차 기원, 방산 · 항공에서도 자주 참고). 오픈소스 FC FW는 MISRA를 따르지 않는다 → 포크에 전부 적용하면 경고 폭탄. 새 코드 / 안전 경로만 적용하는 게 현실적 [추정].
  • 스택 사용량: GCC -fstack-usage가 함수별 .su 파일을 만든다. 호출 그래프와 합쳐 최악 스택 깊이를 추정 (인터럽트 중첩은 따로 더한다).
  • 바이너리 크기: arm-none-eabi-size로 .text / .data / .bss를 타깃별로 기록하고 이전 커밋과 비교. F4 계열처럼 flash가 빡빡한 타깃은 기능 추가가 곧 빌드 실패다.
  • 타깃 매트릭스 빌드: 지원하는 모든 보드 타깃이 빌드되는지. Betaflight CI는 make targets-ci-grouped-print로 그룹을 만들어 병렬 빌드한다.

3.4 L2 — Unit test (호스트 컴파일, googletest)#

무엇을 하나

FW 소스 파일 하나(또는 몇 개)를 PC용 컴파일러로 빌드하고, 의존하는 함수는 테스트 파일 안에서 가짜(stub)로 만든다. Betaflight는 src/test/unit/에 xxx_unittest.cc 파일이 있고, src/test/Makefile에 테스트마다 xxx_unittest_SRC(어떤 소스를 같이 빌드하나)와 xxx_unittest_DEFINES(어떤 기능 플래그를 켜나)가 정의돼 있다.

못 잡는 것: 실제 타이밍, 인터럽트 경쟁(race), DMA, 컴파일러 최적화 차이(호스트 gcc/clang ≠ arm-none-eabi-gcc -O2), 엔디안 · 정렬(alignment) 차이.

기법 확장

  • Property-based testing: "아무 바이트열을 넣어도 파서가 죽지 않고, 유효 프레임을 넣으면 같은 값이 나온다" 같은 성질을 무작위 입력 수천 개로 검사. Python은 Hypothesis 라이브러리, C/C++은 RapidCheck 등 [확인 필요: C++ 라이브러리 현황]. FC FW 파서를 Python으로 감싸거나(ctypes) 같은 로직을 Python 참조 구현으로 만들어 비교.
  • Mutation testing: 코드를 일부러 조금 바꿔서(< → <=, 상수 +1) 테스트가 그 변화를 잡는지 본다. 테스트 스위트의 품질을 재는 방법. C/C++용 도구로 Mull 등 [확인 필요].
  • 커버리지: gcov/lcov로 line · branch 커버리지. 안전 경로(failsafe · arming)는 branch 커버리지를 따로 본다. 항공 DO-178C의 MC/DC는 개념만 참고 (10절).

CI 위치: per-commit, 차단. 전체가 수 분 안.

3.7 L5 — HITL (실제 FC + 시뮬레이션 센서/물리)#

무엇을 하나 (PX4 의미): 실제 FC 보드에 FW를 올리고 SYS_AUTOSTART를 HIL 기체(예: HIL Quadcopter X = 1001)로 설정한다. PC의 Gazebo Classic이 USB/UART로 FC와 MAVLink를 주고받는다. FC는 실제 MCU에서 실시간으로 추정기 · 제어기를 돌린다.

이 층에서만 보이는 것이 층에서도 안 보이는 것

실제 컴파일러 · 최적화 · 메모리 배치모터 · ESC · 전원
MAVLink 통신 부하가 루프에 주는 영향실제 RC 링크
flash에 저장된 파라미터 처리진동

Betaflight에는?: Betaflight 업스트림에는 PX4식 HITL 모드가 없다 [확인 필요]. 비슷한 효과를 내려면 (1) MSP로 RC를 주입(MSP_SET_RAW_RC)하고 실제 IMU는 책상 위 정지 상태로 두거나, (2) 포크에 "리플레이 자이로" 드라이버를 넣어 기록된 IMU 데이터를 루프에 먹이는 방법이 있다 (6.6절). (2)는 FW 수정이 필요하므로 테스트 빌드 전용 플래그로 격리해야 한다 [추정].

CI 위치: nightly. 보드가 필요하므로 보드 팜과 같이 운영.

3.8 L6 — HIL bench (실제 보드 · 실제 버스 · 주입 자극 · 계측기)#

이 층이 FW Test JD의 "HIL 테스트 시스템 구축"의 중심이다 [추정, 공고 문구 근거]. 벤치 하드웨어 설계는 R08, 여러 벤치를 플랫폼으로 묶는 건 R09.

잡는 것못 잡는 것
실제 UART 프레이밍 · baud 오차 · 깨진 프레임 처리비행 물리 · 진동 · 바람
입력 → 출력 지연 분포 (CRSF → DShot)실제 RF 환경 (다중 경로 · 간섭) — 감쇠기는 경로 손실만 흉내

failsafe 출력 (DShot 0 / disarm)이 실제 핀에서 몇 ms에 나오나장기 열화

CI 위치: per-merge에는 5~10분 smoke (부팅 · 버전 확인 · arm/disarm · RX loss 1회 · 지연 100회). nightly에 전체 (지연 수천 회 · 전원 스윕 · 퍼징 · 장시간). 릴리스 후보는 전체 + 여러 보드 리비전.

⚠️ Gemini 정정: Gemini 그림은 "RF 감쇠기로 0 dB → 90~95 dB 올리면 드론이 20 km 멀어졌을 때"를 흉내 낸다고 했다. 감쇠기는 경로 손실(평균 신호 세기)만 흉내 낸다. 다중 경로 페이딩 · 도플러 · 간섭 · 안테나 패턴은 없다. 그리고 "몇 dB = 몇 km"는 주파수 · 안테나 이득 · 송신 출력 · 수신 감도에 따라 달라지므로 그대로 쓰면 안 된다. 벤치 감쇠 테스트의 정답은 "km"가 아니라 "감쇠 X dB에서 LQ/패킷 손실이 Y, failsafe가 Z dB에서 발생" 같은 링크 마진 곡선이다 (R05).

3.9 L7 — 통합 리그 (완성 기체 · 프롭 없음 / 추력대 / 테더)#

⚠️ 안전: 프롭을 단 모터 회전은 손가락 절단 · 파편 위험이 있다. 프롭 장착 테스트는 고정된 추력대 · 보호망 · 비상 정지 스위치 · 전류 제한 전원으로만 하고, LiPo 충전/방전은 방화 백 · 감독 하에 한다. 이 층의 실습은 Don 혼자 집에서 하지 않는다.

형태무엇을 보나예
프롭 없이 모터만ESC 프로토콜 · bidirectional DShot eRPM · 모터 순서/방향 · 전류 · 온도4모터 동시 스로틀 스윕 중 FC 리셋 없음, 레일 전압
추력 측정대 (load cell)스로틀 → 추력 곡선 · 효율 · 응답 시간모터/프롭 조합 비교, ESC FW 변경 회귀

진동대 위 FC진동 스펙트럼이 추정기/필터에 주는 영향특정 주파수에서 aliasing

잡는 것: 모터 켠 상태의 EMI가 IMU · GPS · 수신기에 주는 영향, 전원 계통 ripple, 진동, 열. 못 잡는 것: 실제 비행 기동 · 바람 · 장거리 링크. CI 위치: 자동 CI보다는 릴리스 후보 게이트 (사람이 붙는 반자동). 추력대는 스크립트로 자동화 가능.

3.10 L8 — 비행 시험 (스크립트 기동 · 텔레메트리 · chase)#

원칙: 비행 시험도 "날려 보고 느낌"이 아니라 테스트 케이스다. 기동이 정해져 있고, 기록할 데이터가 정해져 있고, 판정 기준이 정해져 있다.

4.3 설계 규칙#

  • per-commit은 결정적(deterministic)이어야 한다. 하드웨어 · 시간 · 랜덤에 기대는 테스트는 per-commit에 넣지 않는다. flaky가 하나라도 있으면 개발자가 CI를 무시하기 시작한다.
  • HIL smoke는 짧고 강하게. 하드웨어 자원은 공유되고 비싸다. per-merge HIL은 "이 빌드가 보드를 벽돌로 만들지 않나 + 안전 경로 1개" 정도.
  • nightly 실패는 자동 bisect. ArduPilot bisect-helper.py처럼 "테스트 이름 + 범위"로 원인 커밋을 찾는 도구를 만든다.
  • 결과는 기계가 읽는 형식 + 원자료 보존. JUnit XML (Betaflight make junittest) 같은 표준 형식으로 CI 대시보드에, 원자료(로직 분석기 캡처 · 블랙박스)는 아티팩트 저장소에 FW 해시와 함께.
  • 게이트를 넘는 기준이 문서에 있어야 한다. "nightly에서 지연 p99가 X ms를 넘으면 RC 차단" 같은 규칙이 릴리스 체크리스트(9.5절)와 연결된다.

Don 경험 범위: Don은 GitLab CI · Jenkins 실무 경험이 없다. 대신 web 기반 test automation과 챔버 테스트 플랫폼 SDK(스케줄링 포함)를 만들었다 — "테스트를 언제 · 어느 자원에서 · 어떤 순서로 돌릴지"를 정하는 스케줄러 문제는 같다. CI 도구 자체는 R10의 실습으로 채운다.

6.1 T1 요구사항 기반 테스트#

요구사항 한 줄마다 테스트 케이스가 최소 하나. 요구사항이 숫자를 안 주면 테스트 엔지니어가 숫자를 물어봐야 한다. "failsafe가 빨리 동작해야 한다"는 테스트할 수 없다. "RC 신호 손실 후 X ms 안에 stage 1 진입, Y s 후 모터 출력 0 또는 착륙 절차"는 테스트할 수 있다.

Betaflight 2026-10 master의 failsafe.c 기본값은 failsafe_delay = 15 (0.1초 단위 → stage 1 1.5초), failsafe_procedure = FAILSAFE_PROCEDURE_DROP_IT, failsafe_throttle = 1000, 그리고 RX 데이터 실패 판정 최소 주기 PERIOD_RXDATA_RECOVERY = 100 ms, failsafe 갱신 주기 PERIOD_RXDATA_FAILURE = 10 ms이다. 즉 기본 설정에서 "0.5초 뒤 0"은 맞지 않는다. 더 중요한 교훈: 오라클은 매직 넘버가 아니라 DUT의 실제 설정(diff all)에서 계산해야 한다. 6.7 T7 타이밍 / 지연 테스트 — 숫자 하나가 아니라 분포#

왜 분포인가: 링크 지연에는 무작위 대기가 들어 있다. ELRS 500 Hz면 패킷 주기 2 ms → stick 변화가 다음 패킷까지 평균 ~1 ms 기다린다. FC 루프 · RX task 주기도 위상이 랜덤이다. 그래서 1회 측정값은 의미가 없고, p50 · p95 · p99 · max와 히스토그램이 필요하다.

  3. 수천 번 반복, 자극 시각을 루프 주기에 대해 랜덤 위상으로 (항상 같은 위상이면 분포가 아니라 한 점만 본다).

7.1 왜 어려운가#

파서는 "이 바이트 → 이 값"이라는 정답이 있다. 제어 루프는 출력이 시간에 따른 모양이고, 센서 노이즈 · 기체 차이 · 배터리 상태에 따라 매번 조금씩 다르다. 그래서 정답 "값" 대신 허용 범위를 가진 특징량으로 판정한다.

7.2 오라클 종류#

오라클설명예
특징량 한계응답에서 숫자를 뽑아 한계와 비교overshoot ≤ 25%, settling ≤ 0.25 s
기준 대비 (회귀)이전 릴리스 결과와 비교, 차이가 한계 이내rise time 변화 ≤ ±10%
모델 기반기대 응답 모델(전달함수)과의 오차RMS 오차 ≤ X
불변식(invariant)항상 성립해야 하는 성질disarm 중 모터 출력 = 0, 각도 모드에서 각도 ≤ 최대 각

통계여러 번의 분포로 판정p99 지연, 통과율 하한 (8절)

메타모픽 테스트는 "정답을 모를 때" 특히 유용하다. 예: roll +200 deg/s 계단과 −200 deg/s 계단의 overshoot는 (대칭 기체라면) 거의 같아야 한다. 예제 코드 self-test [2]가 같은 생각.

8. 통계적 판정과 flaky 테스트#

8.1 몇 번 돌려야 하나#

"한 번도 실패 안 했다"로 통과율을 주장하려면 횟수가 필요하다. N번 연속 성공일 때 통과율의 95% 단측 하한은 (0.05)^(1/N)이다. rule of three: 0 실패 N회 → 실패율 상한 ≈ 3/N (95%).

주장하고 싶은 통과율 (95% 신뢰)0 실패로 필요한 횟수
90%29
95%59
99%299
99.9%2995

(runs_needed_zero_fail()로 계산. 99% → 299는 self-test에서 확인.)

의미: "failsafe가 1000번 중 1번 늦는다"는 버그는 nightly에서 50번 돌려서는 거의 안 보인다. 안전 경로의 확률적 결함은 soak에서 수천 회 돌려야 한다. 또는 원인을 찾아 결정적으로 재현하는 unit test로 내린다.

8.2 flaky 다루기#

원인예처리
테스트 자체 타이밍 가정sleep(0.5) 후 상태 확인조건 대기 (polling + timeout)로
시뮬레이션 가속 과다ArduPilot --speedup 높을 때 RC override timeout가속 낮추기, 타임아웃을 시뮬레이션 시간으로
공유 자원 경합같은 USB 허브의 다른 벤치자원 잠금 · 격리
장비 상태로직 분석기 버퍼 · 케이블 접촉장비 self-check를 테스트 앞에
진짜 FW 결함경쟁 조건 · 우선순위 역전재시도로 덮지 말 것 — 버그로 등록

규칙

  • 자동 재시도(retry)는 결과를 FLAKY로 기록하고 통과로 세지 않는다. "재시도로 통과"는 통계적으로 실패율을 숨긴다.
  • flaky 비율을 테스트별로 추적한다 (대시보드). 비율이 오르면 FW 회귀 신호일 수 있다.
  • 격리(quarantine) 목록은 기한과 담당자가 있어야 한다.
  • 예제 flaky_check(): 19/20 통과 → FLAKY (조사 대상), 20/20 → NEED_MORE (99% 주장에 부족), 300/300 → STABLE_PASS.

참고: 코드의 Wilson 하한(양측)은 보고용, 0 실패 판정은 단측 정확 하한 (1−0.95)^(1/N)을 쓴다. Wilson은 더 보수적이라 300/300에서도 0.987로 99%에 못 미친다 — 처음 self-test가 이 차이로 실패했고, 판정 기준을 명시적으로 고쳤다. 판정 통계를 문서에 적어 두는 이유가 이것이다.

8.3 SSD 쪽과 비교#

SSD 신뢰성 시험(Don의 chip reliability · PCIe 커버리지 경험)은 샘플 수 × 시간으로 신뢰도를 말한다. 드론 FW 회귀에서는 같은 생각을 반복 횟수 × 조건 매트릭스로 적용한다. 차이는 드론은 1회 비용이 층마다 6자릿수 이상 차이 난다는 것 (unit µs vs 비행 반나절) — 그래서 통계가 필요한 테스트는 최대한 아래층으로 내린다.
