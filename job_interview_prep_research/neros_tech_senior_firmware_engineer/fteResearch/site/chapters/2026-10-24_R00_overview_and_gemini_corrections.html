4. 한 장 요약 — 꼭 가져갈 12가지#

  1. FTE는 "판정하는 장치와 소프트웨어"를 만드는 일이다. SSD 검증의 자동화 · 플랫폼 · 스트레스 감각은 그대로 쓰인다. 새로 익힐 것은 닫힌 루프 제어, 실시간(µs) 타이밍, RF 링크, 그리고 빠른 릴리스 속도다. → R01
  2. 가장 큰 차이는 오라클(합격 기준)이다. SSD는 "쓴 데이터 = 읽은 데이터"처럼 정답이 분명하다. 드론은 제어 시스템이라 step response · 지연 분포 · 허용 오차 · 통계로 판정한다. → R01, R07
  3. 드론은 보드 여러 장의 시스템이다. FC · 무선 RX/TX · ESC · 조종기 · companion · 영상 · GCS가 서로 다른 오픈소스를 돌린다. 버스 하나하나가 테스트 지점이다. → R02
  4. Betaflight는 RTOS가 없는 협조형 scheduler다. gyro → filter → PID → mixer → DShot 경로가 가장 높은 우선순위다. src/main/fc/tasks.c의 task_attributes[], src/main/scheduler/scheduler.c, src/main/fc/core.c의 taskMainPidLoop가 핵심 파일이다. → R03
  5. Betaflight 저장소에 이미 테스트 도구가 있다. googletest 유닛 테스트 약 90개(src/test/unit/, make test)와 SITL 끝단 테스트 하네스(src/test/sitl/sitl_harness.py, RC는 UDP 9004 · MSP는 TCP 5761)가 있다. 포크 테스트는 이 위에서 시작한다. → R03, R10
  6. PX4와 ArduPilot은 "자기 자신을 테스트하는 법"의 교과서다. ArduPilot은 Tools/autotest에 SITL 위의 Python 시나리오(wait_* 헬퍼 · sim-time 타임아웃)가 있다. PX4는 test/mavsdk_tests(C++/Catch2, CI는 SIH)를 쓴다. 둘 다 "기체 추상화 + 조건 대기 + 로그 기반 판정" 구조다. → R04
  7. 프로토콜은 테스트하기 가장 좋은 경계다. CRSF · SBUS · DShot · MSP · MAVLink는 프레임이 정해져 있다. 그래서 conformance · fuzz · resync · 타이밍 테스트를 자동화하기 쉽다. → R05
  8. failsafe 시간은 외우지 말고 설정에서 계산한다. Betaflight 기본값은 failsafe_delay=15, 즉 1.5 s의 stage 1이다. Gemini가 말한 "0.5 s 후 모터 0"이 아니다. 판정 기준은 보드의 실제 설정에서 유도해야 한다. → R03, R07, R08
  9. SITL · HITL · HIL 벤치는 서로 다른 것이다. SITL은 PC 안에서 FW와 물리를 같이 돌린다. PX4 HITL은 진짜 FC에 가짜 센서를 MAVLink로 넣는 방식이다(커뮤니티 지원, 센서 드라이버를 거치지 않음). HIL 벤치는 진짜 보드에 진짜 버스와 계측기를 붙인다. 각각 잡는 버그가 다르다. → R07
  10. HIL 벤치의 핵심은 "사람 없이 돌다가, 망가져도 스스로 복구하는 것"이다. 전원 · 플래시 · 리셋 · 자극 · 관측 · 측정 · 복구가 모두 Python으로 돌아야 한다. 결과도 PASS / FAIL / INFRA_FAIL로 나눠야 한다. → R08
  11. 스케일되는 플랫폼은 WHAT · HOW · WHERE를 가른다. 테스트 의도, 프로토콜 · 드라이버, 벤치 · 자원을 분리한다. 기체는 상속이 아니라 capability 조합으로 모델링한다. 그러면 기체 · 펌웨어 스택 · 벤치가 늘어도 한 층만 고치면 된다. 같은 테스트를 책상 → CI → nightly → release → 공장 → RMA까지 다시 쓴다. → R09
  12. Don의 SSD 챔버 SDK 경험은 드론 HIL 플랫폼과 거의 같은 모양이다. 장비 제어, 스케줄링, 상태 모니터링, 시퀀스 자동화, 다른 엔지니어가 쓰는 SDK가 그대로 대응된다. 이것이 가장 강한 연결 고리다. → R01, R09

5.2 Betaflight / INAV#

Gemini 주장바로잡은 내용단원
RC loss 후 "정확히 0.5 s 뒤 모터 0"기본 failsafe_delay=15, 즉 1.5 s의 stage 1이다. 그동안은 armed 상태로 idle이고, 이어서 기본 절차 DROP_IT → disarm으로 간다. 검사는 scheduler에서 10 ms마다 돈다R03 · R07 · R08
CRSF 파서는 0xC8을 찾고 1바이트씩 resync한다Betaflight는 바이트 사이 시간 간격(frameTimeNeededUs 1748 µs)으로 프레임을 자른다. 길이를 확인하고, CRC가 틀리면 프레임 전체를 버린다. 1바이트 resync는 PC 쪽 스트림 파서의 기법이다R03
DShot = 11비트 + 4비트 CRC11비트 throttle + 1비트 telemetry 요청 + 4비트 CRC = 16비트다. bidirectional DShot은 CRC를 반전한다. DSHOT1200은 제거됐다R03 · R05
Blackbox는 125 µs마다 기록한다기본 기록률은 PID 루프의 1/4이다. 설정으로 바뀐다R03
Blackbox flash는 "16 MB~128 MB"흔한 W25Q128은 128 Mbit = 16 MB다. Mbit와 MB를 섞은 것이다R02
Betaflight는 GPS Position Hold를 거의 못 한다2025.12 릴리스부터 ALTITUDE_HOLD · POSITION_HOLD가 들어왔다. master에는 GPS_RESCUE와 flight-plan task도 있다. 웨이포인트 미션은 여전히 INAV/PX4/ArduPilot 영역이다R01 · R02 · R03
IMU는 항상 8 kHz센서마다 다르다. ICM-42688-P는 8 kHz, BMI270은 3.2 kHz다R02 · R08
MSP로 FC를 "강제 제어"한다MSP_SET_MOTOR는 disarm 상태의 모터 테스트 값만 쓴다. MSP_SET_RAW_RC는 MSP RX provider나 MSP override 모드가 있어야 동작한다R03
HITL은 MSP_SIMULATOR로 한다INAV에만 있다 (0x201F). Betaflight에는 그런 명령이 없다R03
SITL 위치 src/main/target/SITL/Betaflight는 지금 src/platform/SIMULATOR/에 있다. 옛 경로는 INAV에서만 맞다R03 · R10
CI는 GitLab에서 make testupstream은 GitHub Actions(.github/workflows/ci.yml 등)에서 make checks와 make test-all을 돈다. Neros 내부 CI는 [추정]R07

5.3 PX4 / ArduPilot#

Gemini 주장바로잡은 내용단원
PX4 HITL은 "HIL_SENSOR만 쏘면 된다"SYS_HITL=1이 필요하다. 커뮤니티 지원이고 Gazebo Classic에서만 문서화돼 있으며, 센서 드라이버를 우회한다. 새 Gazebo는 gz_bridge를 쓴다. 대안은 SIH다R04 · R07
PX4 테스트는 C++ · Python · Swift로 짠다저장소 안의 통합 테스트는 C++/Catch2만 있다. CI는 Gazebo가 아니라 SIH를 쓴다R04
ArduPilot autotest는 "저수준 패킷 직접 파싱"수백 개의 고수준 wait_* 헬퍼와 MAVProxy 위에 서 있다. sim-time 타임아웃과 최소 유지 시간으로 판정한다R04
ArduPilot은 "제품 객체와 테스트 객체를 분리한다"실제로는 vehicle_test_suite.py 기반 클래스를 쓴다. 기체별 테스트는 그 기체 클래스의 메서드다. "제품 객체 하나만 추가하면 테스트 1000개" 주장은 과장이다R09
ArduPilot은 강하게 결합된(tightly coupled) 구조다AP_HAL이 이식성을 만든다. "통째로 결합"은 단순화가 지나치다R04
ROS 2/DDS는 PX4 쪽 이야기다ArduPilot에도 AP_DDS가 있다(4.5부터)R04 · R06
PX4는 F7/H7만 쓴다STM32F4 보드도 있다R04
GPL은 추가 개발 코드를 "모두에게 무료로 공개"해야 한다의무는 배포할 때, 바이너리를 받은 사람에게 생긴다. 같은 프로그램으로 결합된 부분에 적용되고, 별도 프로세스로 통신하는 앱은 보통 따로 본다. Betaflight도 GPLv3라는 점이 빠졌다 (법률 자문 아님)R02 · R04

5.4 무선 링크 · 영상 · Linux#

Gemini 주장바로잡은 내용단원
LR1121 = 900 MHz 칩, RX = STM32 + SX1280LR1121은 sub-GHz와 2.4 GHz를 모두 지원한다(LORA_DUAL 모드). 흔한 RX는 ESP8285 + SX1280이다R02
RX = STM32 기반지금 ExpressLRS master의 빌드 타깃은 ESP32/ESP8285뿐이다. STM32는 FC에 내장된 "SPI ExpressLRS" 수신기(Betaflight 쪽)로만 남았다R05
가짜 헤더 0xAA로 파서 테스트0xAA는 예전 연습 문제 파서의 sync 값이다. CRSF sync(주소)는 0xC8(FC) · 0xEE(TX 모듈) 등이다R05
CRSF 파서 = 1바이트 버리고 재동기 (하나의 정답)구현마다 다르다. Betaflight는 시간 간격으로 프레임을 자르고, ExpressLRS는 CRC 실패 시 소비한 바이트를 다 버리고, EdgeTX는 1바이트만 버리고 다시 찾는다. 같은 깨진 입력에 결과가 다를 수 있으니 기대값을 구현별로 적어야 한다R05
RC 프레임은 항상 26바이트RX → FC는 26바이트다. EdgeTX → TX 모듈은 주소 0xEE와 상태 바이트가 붙어 27바이트(length 25)다R05
bidirectional DShot eRPM → dynamic notcheRPM은 RPM filter에 들어간다R05
RX → FC UART "420k ~ 5.25M baud"FC 쪽 표준은 420000이다. 921600 · 1.87M · 3.75M은 조종기 ↔ TX 모듈 쪽 설정이다. 5.25M은 확인하지 못했다R02
ESC MCU는 "STM32G0, $1짜리"STM32G071은 AM32가 지원하는 MCU 중 하나일 뿐이다. EFM8 · AT32 · GD32도 흔하다. 가격은 근거가 없다R02
감쇠기 0~95 dB = 20 km를 "완벽히 모사"RCDAT-6000-90은 0~90 dB다. 2.4 GHz에서 20 km 자유공간 손실은 이미 약 126 dB다. 감쇠기는 평균 경로 손실만 흉내 낸다. fading과 간섭은 따로 다뤄야 한다. conducted 시험은 링크 마진을 재는 것이다R01 · R07 · R08
SPI 센서 에뮬레이터가 필수FC가 SPI master라서 에뮬레이터가 레지스터 읽기에 실시간으로 답해야 하고, 보드의 IMU도 떼어 내야 한다. 더 싼 대안은 SITL 소켓이나 녹화된 IMU 재생이다R07 · R08
SWD는 굽기 · RTT 로그 전용이고 명령은 못 보낸다RTT는 양방향이다. SWD로 동작 중에 메모리를 읽고 쓸 수도 있다. 명령을 UART/CRSF/MSP로 보내는 진짜 이유는 출하되는 경로를 테스트하기 위해서다R08
RTT는 "CPU 부하 없이"오버헤드가 작지만 0은 아니다. µs 타이밍 측정에는 GPIO 토글 + 로직 분석기가 더 안전하다R01
OpenHD/WFB-ng는 "아무 Wi-Fi 칩을 해킹"raw 802.11 injection(monitor mode) + FEC다. 패치된 드라이버를 쓰는 특정 칩셋이 필요하다R02 · R06
"microDDS"정식 이름은 Micro XRCE-DDS / uXRCE-DDS다(PX4 v1.14부터 Fast-RTPS bridge를 대체)R06
Jetson 위 OS는 Yocto기본은 JetPack/L4T(Ubuntu)다. Yocto는 meta-tegra를 쓰는 선택지다R06
RTSP로 저지연 영상RTSP는 세션 제어다. rtspsrc 기본 jitter buffer가 2000 ms라서 설정하지 않으면 지연이 크다R06
PREEMPT_RT는 외부 패치6.12부터 mainline이다 (x86 · arm64 · riscv)R06

5.5 Gemini가 맞게 짚은 것#

정정만 있는 건 아니다. 아래는 확인 결과 맞았다.

  • CRSF 프레임 [addr][len][type][payload][crc], CRC-8 poly 0xD5, RC 채널 16 × 11비트 = 22바이트
  • SBUS 25바이트, 100 kbaud 8E2, 반전 신호
  • Betaflight는 bare-metal 협조형 scheduler이고, PX4는 NuttX + uORB + EKF2, ArduPilot은 ChibiOS
  • ArduPilot Tools/autotest는 테스트 플랫폼 설계의 좋은 참고서다
  • 기체가 달라도 "물리적 벤치 · 계측 장비는 공통, 대화하는 프로토콜만 다르다"는 큰 그림
  • latency는 한 번의 숫자가 아니라 분포(히스토그램 · p99)로 봐야 한다
