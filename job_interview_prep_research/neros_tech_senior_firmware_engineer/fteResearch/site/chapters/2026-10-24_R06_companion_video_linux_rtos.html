0. 이 단원을 읽는 법#

  • 앞 단원과의 관계: 드론 전체 배치도는 R02, FC 안쪽(Betaflight · PX4)은 R03 · R04, MAVLink · CRSF 같은 링크 프로토콜은 R05에 있다.

정리하면 FTE 입장에서 이 영역은 세 가지 이유로 중요하다.

  1. 지연(latency)이 제품 사양이다. FPV 조종에서 영상 지연은 조종 품질 그 자체다. Platform 공고는 지연을 아예 "release gate"로 만들겠다고 쓴다.
  2. Linux가 끼면 고장 모드가 늘어난다. 부팅 실패, OTA 중 전원 차단, 열로 인한 클럭 저하, 스케줄링 지터 — MCU 펌웨어에는 없던 종류다.
  3. 여러 팀의 경계가 여기 모인다. FC ↔ companion(MAVLink/DDS), 기체 ↔ 지상(영상 · 텔레메트리), 지상 ↔ 외부 C2(ATAK/CoT). 경계는 테스트하지 않으면 반드시 깨진다.

3. Companion computer — Jetson + ROS 2 + DDS/uXRCE-DDS + MAVLink router#

3.1 무엇인가#

Companion computer는 FC 옆에 붙는 고성능 Linux 컴퓨터다. FC는 1 kHz~8 kHz 제어 루프를 돌리는 MCU이고, companion은 카메라 영상 처리 · 물체 인식 · 경로 계획 · 고수준 명령을 맡는다. 그리고 결과를 "이 방향 · 이 속도로 가라" 같은 setpoint로 FC에 내려준다.

3.2 PX4 uXRCE-DDS가 실제로 어떻게 붙나 (공식 문서로 확인)#

PX4 공식 문서 기준 사실들이다.

  • uXRCE-DDS는 PX4 v1.14에서 들어왔고, v1.13의 Fast-RTPS Bridge를 대체했다.
  • 구조: FC 안의 client(uxrce_dds_client)가 companion의 agent(MicroXRCEAgent)에 serial 또는 UDP로 붙는다. agent가 ROS 2 DDS 세계에 토픽을 대신 내보낸다.
  • 어떤 uORB 토픽을 내보낼지는 PX4 저장소 src/modules/uxrce_dds_client/dds_topics.yaml에 정의된다.
  • 기본 네임스페이스는 PX4가 내보내는 쪽 /fmu/out/, PX4가 받는 쪽 /fmu/in/.
  • 기본 UDP 포트 8888(UXRCE_DDS_PRT), DDS domain 0(UXRCE_DDS_DOM_ID).
  • ROS 2 쪽은 같은 메시지 정의(px4_msgs)로 빌드해야 한다. 버전 붙은 메시지는 translation node가 처리하지만, 버전 없는 메시지는 정확히 일치해야 한다 → 메시지 정의 불일치가 대표 회귀 원인.
  • 보안 경고(공식 문서): DDS 트래픽은 인증이 없고 uORB에 바로 닿는다. FC ↔ companion 링크를 격리하라고 쓴다.

ArduPilot도 같은 방향으로 왔다. ArduPilot 4.5부터 AP_DDS로 Micro XRCE-DDS 전송을 지원하고 ROS 2 서비스(arm, mode)를 쓸 수 있다. SITL에서는 sim_vehicle.py ... --enable-dds, agent는 ros2 run micro_ros_agent micro_ros_agent udp4 -p 2019 형태다(4.6 이후 문서 기준) [확인 필요: 버전별 프로파일 인자 차이].

⚠️ Gemini 정정: Gemini는 "microDDS"라는 이름을 쓰고, 비교표에서 PX4만 "최강 (MAVLink / microDDS 표준)", ArduPilot은 "최강 (MAVLink 표준)"처럼 DDS를 PX4 전용인 듯 썼다. 정식 이름은 eProsima Micro XRCE-DDS이고 PX4 쪽 모듈 이름은 uXRCE-DDS다. ArduPilot도 4.5부터 AP_DDS로 같은 Micro XRCE-DDS를 지원한다. "DDS = PX4만"은 틀린 말이다.

⚠️ Gemini 정정: Gemini 배치도는 Jetson을 "OS: Ubuntu Linux (Yocto)"로 적었다. Jetson 기본 OS는 NVIDIA JetPack/L4T (Ubuntu 기반)이고, Yocto로 Jetson 이미지를 만드는 건 커뮤니티 레이어(OE4T meta-tegra)를 쓰는 별도 선택이다. Neros가 어느 쪽인지는 모른다 [확인 필요]. 단, Platform/Embedded Linux 공고가 Yocto/Buildroot를 소유한다고 쓰므로 양산 기체는 자체 이미지일 가능성이 있다 [추정].

3.3 MAVLink router — FC 하나, 손님 여럿#

FC의 MAVLink 포트는 보통 하나다. 그런데 손님은 여럿이다: companion의 자율 노드, 지상 GCS, 로그 기록기, 테스트 PC. 이걸 나눠 주는 게 mavlink-routerd다 (mavlink-router 공식 README 확인).

  • 설정 파일 기본 위치 /etc/mavlink-router/main.conf, 추가 설정 /etc/mavlink-router/config.d/.
  • 엔드포인트: UART, UDP(normal = 보내는 쪽 / server = 듣는 쪽), TCP. TCP 서버 기본 포트 5760.
  • 로그: Log 설정 시 ArduPilot은 .bin, PX4는 .ulg로 FC 로그 저장. LogTelemetry(-T)는 원시 텔레메트리를 .tlog로.
  • SnifferSysID로 지정한 system ID 쪽에 모든 트래픽을 복사 → 테스트 PC를 sniffer로 붙이면 FC ↔ companion 대화 전체를 녹화할 수 있다.

FTE 포인트: 라우터는 "보이지 않는 중간자"다. 라우터가 패킷을 늦게 넘기거나, 버퍼가 차서 버리거나, 재시작 중 heartbeat가 끊기면 FC는 companion 링크 손실로 판단할 수 있다. 라우터 자체를 테스트 대상 목록에 넣어야 한다.

3.5 FTE는 어떻게 테스트하나#

3.5.1 메시지 주기 · 지연 측정#

가장 기본은 ROS 2 CLI다.

하지만 CLI는 "사람이 보는 값"이다. 릴리스 게이트로 쓰려면 자동으로 수집하고 판정해야 한다. 설계 요점:

  • 지연은 두 시각의 차다. 보내는 쪽 타임스탬프(메시지 header 또는 PX4 timestamp 필드)와 받는 쪽 수신 시각. 두 시계가 같은 머신이 아니면 시간 동기(PTP/gPTP, PPS)부터 확인해야 의미가 있다. Platform 공고가 "hardware time-stamping and time synchronization"을 따로 적은 이유다.
  • 한 번 재지 말고 수천 번 재서 분포를 본다. 판정은 평균이 아니라 p99 · p99.9 · max, 그리고 "기준선 대비 몇 % 나빠졌나".
  • 부하 조건을 같이 기록한다: CPU 사용률, GPU 클럭, 온도, 다른 노드 실행 여부. 조건이 없는 지연 숫자는 비교할 수 없다.

3.5.2 ROS 2 launch_testing — 노드 묶음을 띄워 놓고 assert#

launch_testing은 ROS 2 공식 통합 테스트 도구다 (ros2/launch 저장소 README 확인).

  • generate_test_description() 함수가 테스트할 시스템을 띄우는 LaunchDescription을 돌려준다.
  • 그 안에 launch_testing.actions.ReadyToTest()를 넣어 "이제 테스트 시작해도 된다"를 알린다.
  • 일반 unittest.TestCase 클래스는 프로세스가 도는 동안 실행된다 (active test).
  • @launch_testing.post_shutdown_test()가 붙은 클래스는 프로세스가 끝난 뒤 실행된다 → 종료 코드 · 로그 검사.
  • 주요 assert: proc_output.assertWaitFor(msg, timeout=10), launch_testing.asserts.assertExitCodes(proc_info).
  • 실행: launch_test my_test.py, CMake에서는 add_launch_test(test/my_test.py) 로 colcon test에 편입.

이 구조는 SITL과 잘 맞는다. PX4 SITL + agent + 우리 노드를 한 launch에 묶고, "arm 명령 → 3초 안에 /fmu/out/vehicle_status의 arming_state 변화" 같은 시나리오를 assert한다 R04.

3.5.3 rosbag 재생 = 회귀 오라클#

rosbag2(ros2 bag record / ros2 bag play)는 토픽을 그대로 녹화 · 재생한다. Jazzy 계열 기본 저장 형식은 MCAP이다 (rosbag2 changelog: "set MCAP as default plugin"). 재생 옵션 --rate, --loop, --clock [Hz]가 있다 [확인 필요: 배포판별 help 출력].

회귀 오라클로 쓰는 방법:

  1. 기준이 되는 비행/벤치 데이터를 녹화한다(카메라 · IMU · odometry). 이걸 golden input으로 고정 · 버전 관리.
  2. 기준 버전 소프트웨어로 재생 → 출력 토픽(예: 탐지 결과, 계획된 setpoint)을 녹화 → golden output.
  3. 새 버전으로 같은 입력을 재생 → 출력 비교. 완전 일치가 아니라 허용 오차 규칙으로 비교(탐지 박스 IoU ≥ 0.9, setpoint 차 ≤ ε, 메시지 수 차 ≤ 1%).
  4. 재생 결정성이 깨지는 원인을 먼저 없앤다: use_sim_time + --clock으로 시간을 bag에 맞추고, 스레드 수 · 난수 seed 고정.

Platform 공고의 "flight logs support deterministic replay"가 바로 이것이다. 로그가 재생 가능하려면 클럭 도메인과 동기 상태가 로그에 같이 기록되어야 한다는 것도 공고가 직접 적었다.

3.5.5 CPU/GPU 열 · throttling#

Jetson은 온도가 오르면 클럭을 낮춘다. NVIDIA 포럼 답변 기준으로 throttling은 짧게 일어날 수 있어 기본 1초 간격 tegrastats로는 놓칠 수 있다. 간격을 줄이고 파일로 남긴다.

  • 볼 필드: 온도(CPU@, GPU@ 등)와 클럭(GR3D_FREQ, CPU 주파수). 온도보다 클럭 하락이 throttling의 더 확실한 신호다.
  • Jetson Nano 사례에서 "over-current throttling" 메시지는 실제로 입력 전압 부족인 경우가 많다고 NVIDIA 직원이 답했다 → 열 문제로 단정하기 전에 전원부터.
  • 시험 설계: 열 챔버(또는 히트건/밀폐 박스) + 고정 부하(추론 루프) + 30~60분 동안 추론 지연 p99, fps, 클럭, 온도를 같은 시간축에 기록. "시작 5분 vs 마지막 5분"의 p99 비교를 판정 기준으로.
  • Platform 공고가 "under sustained thermal load"라고 쓴 게 이 시험이다.

4.2 GStreamer — 블록을 이어 붙이는 영상 프레임워크#

GStreamer는 element(블록)를 !로 이어 파이프라인을 만든다. src → 변환 → 인코더 → payloader → 네트워크 sink, 받는 쪽은 그 반대.

  • Jetson에서는 소프트웨어 x264enc 대신 하드웨어 인코더 플러그인(nvv4l2h264enc 등)을 쓴다 [확인 필요: JetPack 버전별 element 이름].
  • 지연을 키우는 숨은 기본값이 많다. 예: rtspsrc의 latency 속성 기본값은 2000 ms(GStreamer 공식 문서 확인). 지터 버퍼 크기, 인코더 B-frame, sync=true 디스플레이 대기, queue 크기가 모두 지연이다. FTE가 파이프라인 문자열을 설정 파일처럼 버전 관리 · diff해야 하는 이유.
  • 포트 5600은 PX4/QGC 영상 예제에서 흔히 쓰는 UDP 포트다 [확인 필요: QGC 기본값].

4.3 OpenHD · WFB-ng — Wi-Fi 칩으로 만든 단방향 방송 링크#

WFB-ng 공식 README에서 확인한 것:

  • Wi-Fi 카드를 monitor mode로 두고 패킷을 주입(injection)한다. 접속(association) · ACK 절차가 없다 → 재전송 대기가 없어 지연이 작다.
  • RTP 패킷을 802.11 프레임에 1:1로 실어 보낸다(UDP 패킷 하나 = 무선 패킷 하나, 크기 가변).
  • FEC: 기본 설정은 12개 블록 중 4개 손실까지 복구 (즉 k=8, n=12로 읽힌다). FEC 파라미터는 동작 중 바꿀 수 있다.
  • 지원 칩: RTL8812AU · RTL8812EU (패치된 드라이버 필요), 일부 Atheros 칩(README는 TX 전력 제어에 커널 패치 필요라고 씀) [확인 필요: 정확한 모델명]. 아무 Wi-Fi 칩이나 되는 게 아니다.
  • libsodium으로 암호화 · 인증, wfb_keygen으로 키 쌍.
  • MAVLink 양방향, IP 터널(고대역 영상에는 비권장), TX 다이버시티(RSSI 기반 송신 카드 선택).
  • 링크 상태 보기: wfb-cli gs, 로그 journalctl -xu wifibroadcast@gs.
  • 숫자 지연 주장은 README에 없다.

OpenHD는 이런 broadcast 방식 위에 영상 · 텔레메트리 · RC를 묶은 소프트웨어 모음이고, 지상 앱은 QOpenHD다(openhdfpv.org). OpenHD가 내부적으로 WFB-ng 코드를 얼마나 쓰는지는 버전마다 다르다 [확인 필요].

⚠️ Gemini 정정: Gemini는 OpenHD/WFB-ng를 "일반 Wi-Fi 칩의 모니터 모드를 해킹"한다고 썼다. 실제로는 monitor mode + 패킷 injection을 지원하는 특정 칩셋과 패치된 드라이버가 필요하다(WFB-ng README의 RTL8812AU/EU 등). 아무 노트북 Wi-Fi로는 안 된다. 또 "재전송 지연 없이"는 맞지만 그 대가로 FEC가 복구 못 하는 손실은 그대로 화면 깨짐이 된다 — 테스트할 지점이다.

4.5 Glass-to-glass 지연 — 어떻게 재나#

"Glass-to-glass"는 카메라 렌즈 유리 → 화면 유리까지 전체 지연이다. 파이프라인 tracer로는 못 잰다. 방법은 크게 네 가지.

방법장비원리해상도장점단점
A. 스톱워치/타이머 촬영고주사율 화면에 ms 타이머, 일반 카메라/폰실제 타이머와 영상 속 타이머를 한 사진에 같이 찍고 차이 읽기화면 주사율에 묶임(60 Hz면 ~16.7 ms 단위)공짜, 빠름수동, 반복 어려움, 디스플레이 주사 위치 오차
B. LED + 고속 카메라LED(GPIO로 깜빡), 240~1000 fps 카메라LED 실물과 화면 속 LED를 같은 고속 영상에 찍어 프레임 수 차이고속 카메라 프레임 간격(240 fps ≈ 4.2 ms)직관적, 조종 입력까지 같이 찍을 수 있음수동 분석, 샘플 수 적음
C. LED + 포토다이오드 + 스코프GPIO LED, 화면에 붙인 포토다이오드, DSO 또는 로직 분석기CH1 = LED 구동 신호, CH2 = 화면 밝기 변화, 두 엣지 간 시간µs 단위 (스코프 기준)자동화 가능, 수천 번 반복 → 분포화면 내 포토다이오드 위치에 따라 스캔아웃 시간 포함/제외가 달라짐
D. 타임스탬프 오버레이송신 측 timeoverlay/clockoverlay 또는 프레임 ID 바코드, 수신 측 캡처 + OCR/디코드영상에 박힌 송신 시각 vs 수신 · 표시 시각동기된 시계 기준 ms무인 장시간, 프레임별 지연 → 드롭 · 지터도 같이카메라 센서 · 디스플레이 구간 제외(파이프라인 일부만), 시계 동기 필요

FTE가 회귀 게이트로 쓰기 좋은 건 C다. 이유는 R08과 같다 — 스코프 측정은 사람 없이 반복되고, 결과가 숫자 분포로 나온다.

측정 주의점:

  • 디스플레이 스캔아웃: 화면은 위에서 아래로 그린다. 포토다이오드를 화면 위쪽에 붙이면 아래쪽보다 짧게 나온다. 위치를 고정 · 기록한다.
  • 카메라 노출 · 프레임 주기: LED가 켜지는 순간이 카메라 프레임 노출의 어디인지에 따라 0~1 프레임(60 fps면 0~16.7 ms) 무작위 지연이 추가된다. 그래서 분포가 넓게 나오는 게 정상이고, LED 토글 시점을 일부러 랜덤화해야 편향이 없다.
  • 인코더 GOP: I-frame 직후와 P-frame 중간의 지연이 다를 수 있다.
  • RF 조건: 감쇠기 0 dB / 링크 마진 근처 두 조건을 따로 잰다. 4.6 참고.
  • K05 노트의 latency 파이프라인(stick → … → motor)과 합치면 조종 입력부터 "조종사가 결과를 보는 순간"까지의 전체 루프가 된다. Ground Software 공고 "latency … of the operator's control path"가 이 전체다.

5. 임베디드 Linux — Yocto · Buildroot · U-Boot · OTA · PREEMPT_RT#

5.1 무엇이고 어디에 있나#

임베디드 Linux는 companion(Jetson 등), 지상 장비(handset/GCS), 영상 수신 장비, 무전기 보드에 들어가는 제품 전용 Linux 이미지다. Embedded Linux 공고는 이 이미지를 "the distribution, kernel, bootloader, and SDK that our flight, ground-station, and autonomy software teams build on"이라고 쓴다 [확인됨 공고]. 즉 여러 제품의 공통 바닥이다. 바닥이 흔들리면 위의 모든 팀이 흔들린다 → FTE에게는 가장 레버리지가 큰 회귀 대상 중 하나.

Don은 EmbeddedLinux 자습 노트(모듈 A–S)에서 커널 · 디바이스 트리 · Buildroot · QEMU 랩을 이미 다뤘다. 이 장은 그 지식을 "어떻게 자동으로 검증하나" 쪽으로 돌린다.

5.3 이미지 빌드 재현성 — 같은 입력이면 같은 비트#

재현성은 "같은 소스 + 같은 설정이면 같은 해시의 이미지"다. 방산 제품에서는 현장에 나간 이미지를 나중에 똑같이 다시 만들 수 있어야 버그를 재현하고 보안 감사에 답할 수 있다. Autonomy Platform 공고의 "versioned and reproducible artifacts"가 이것이다.

테스트 방법:

  1. 같은 커밋을 서로 다른 빌드 머신 · 다른 시각 · 다른 경로에서 두 번 빌드.
  2. 최종 이미지와 패키지별 해시 비교. 다르면 diffoscope로 어느 파일 · 어느 바이트가 다른지 찾는다.
  3. 흔한 원인: 빌드 시각이 박힘(SOURCE_DATE_EPOCH 미설정), 빌드 경로가 디버그 정보에 박힘, 파일 순서(tar 정렬), 호스트 도구 버전 차이, 네트워크에서 "latest"를 받음.
  4. CI에 "주 1회 이중 빌드 + 비교" 잡을 두면 재현성 회귀를 조기에 잡는다 R09.

Yocto는 공식적으로 재현 가능한 빌드를 목표로 oe-selftest -r reproducible 테스트를 갖고 있다 [확인 필요: 현재 릴리스의 정확한 이름]. 무거운 빌드라 Don의 방침대로 가이드만 둔다.

5.4 부팅 시간 측정#

현장에서 "전원 넣고 영상이 나올 때까지"는 운용자가 직접 느끼는 숫자다. 회귀가 잘 생긴다(새 서비스 추가, 드라이버 probe 지연, fsck).

구간측정 방법
전원 → U-Boot 배너전원 공급기 출력 ON 신호(또는 전류 상승)와 UART 첫 바이트를 스코프/로직 분석기로
U-Boot → kernel 시작UART 로그에 테스트 PC 수신 타임스탬프 (grabserial 류 또는 pyserial로 줄마다 시각)
kernel 내부printk.time=1 커널 로그 시각, initcall_debug로 느린 드라이버 찾기
init → 서비스 readysystemd-analyze, systemd-analyze blame, systemd-analyze critical-chain
서비스 → "제품 ready"앱이 ready 순간 GPIO 토글 또는 로그 마커 → 영상이면 첫 프레임 시각

판정: 각 구간 p95가 기준선 대비 +X% 이내. 구간을 나눠 기록해야 "어디서 늘었는지"가 바로 보인다. SSD에서 power-on → ready 시간을 단계별로 나눠 보던 것과 같은 사고방식이다(9장).

5.5 ptest · oeqa · Buildroot run-tests#

Yocto 공식 Test Environment Manual에서 확인한 것:

  • 런타임 이미지 테스트는 testimage 클래스. local.conf에 IMAGE_CLASSES += "testimage"를 넣고 bitbake <image> -c testimage.
  • 어떤 테스트를 돌릴지는 TEST_SUITES (예: ping ssh df systemd ...). 순서가 의존성을 만든다.
  • 기본 타깃은 QEMU(TEST_TARGET 기본값 "qemu"). 하드웨어는 simpleremote(이미 부팅된 보드, TEST_TARGET_IP 필요) 또는 레이어의 lib/oeqa/controllers/에 사용자 정의 controller를 만든다 → 전원 · 플래시 · 부팅을 우리 벤치 코드로 제어하는 연결점.
  • testexport: 테스트를 빌드 머신 밖으로 내보내 별도 테스트 서버에서 실행 (TEST_SERVER_IP, TEST_TARGET_IP).
  • ptest: 패키지가 원래 가진 upstream 테스트를 타깃에서 ptest-runner로 실행. 보통 DISTRO_FEATURES에 ptest, 이미지에 ptest-pkgs [확인 필요: 사용 중 릴리스의 변수 이름].

Buildroot 공식 매뉴얼("Using the runtime tests framework"):

  • support/testing/run-tests -l 로 목록, support/testing/run-tests -d dl -o output_folder -k tests.init.test_busybox.TestInitSystemBusyboxRw 로 하나 실행.
  • 각 테스트는 정해진 설정을 빌드하고, 선택적으로 출력물을 검사하고, QEMU로 부팅해 기능을 확인한다. -k가 없으면 출력 폴더를 지운다.
  • 우리 제품용 테스트를 같은 Python 구조로 추가할 수 있다 → "이 defconfig로 빌드하면 영상 서비스가 부팅 후 10초 안에 뜬다" 같은 테스트.

5.8 PREEMPT_RT 와 cyclictest#

사실 확인: PREEMPT_RT는 2024-09-20 Linus Torvalds가 병합해 Linux 6.12부터 메인라인에 들어왔다. 병합 커밋 메시지 기준 지원 아키텍처는 x86(32/64), ARM64, RISC-V. 설정에서 EXPERT를 켜야 고를 수 있다(heise, 위키 등). 단, 메인라인에 들어왔다고 모든 드라이버가 RT에서 좋은 지연을 보장하지는 않는다 — 보드 · 드라이버별 측정이 여전히 필요하다.

⚠️ Gemini 정정: Gemini는 PREEMPT_RT를 "리눅스 커널에 실시간 패치를 입혀"라고 설명했다. 6.12부터는 외부 패치가 아니라 메인라인 설정 옵션이다(x86/arm64/riscv). 다만 제품이 6.12 이전 커널(예: 벤더 BSP 5.x)을 쓰면 여전히 외부 RT 패치가 필요하다 — Jetson BSP의 커널 버전은 JetPack 버전마다 다르다 [확인 필요].

cyclictest는 rt-tests 패키지의 표준 지연 측정 도구다. 주기 타이머로 깨어나서 "깨어나야 했던 시각 vs 실제 깨어난 시각" 차이를 잰다.

옵션뜻
--mlockall (-m)메모리 잠금, 페이지 폴트 제거
--smp (-S)CPU마다 측정 스레드
--priority=80 (-p)SCHED_FIFO 우선순위
--interval=200 (-i)주기 200 µs
--histogram=400 (-h)0~400 µs 히스토그램 출력
--duration=1h (-D)측정 시간
--quiet (-q)끝에 요약만

출력은 스레드마다 Min / Act / Avg / Max (µs). 판정은 Max와 히스토그램 꼬리다. 평균은 거의 의미 없다.

시험 설계:

  1. 기준: 같은 보드 · 같은 커널 설정에서 무부하 1시간 + 부하 1시간(stress-ng CPU/메모리/IO + 네트워크 + 영상 인코딩 실제 부하).
  2. 산출: 히스토그램 그래프, Max, 99.999% 지점.
  3. 회귀 판정: Max가 기준선 + 여유 이내, 꼬리 모양 변화.
  4. 원인 추적 도구: ftrace + --breaktrace(임계 초과 시 추적 중단) [확인 필요: 옵션 이름], rtla timerlat(커널 내장 RT 분석 도구) [확인 필요: 대상 커널에 포함 여부].
  5. 공고 연결: Embedded Linux "Real-time tuning — PREEMPT_RT, latency analysis", Platform "CPU affinity and isolation … jitter and deadline analysis".

5.9 OTA A/B 업데이트 — 전원 차단 · 롤백 · bootcount#

A/B(dual copy)는 rootfs(와 커널)를 두 벌 두고, 안 쓰는 쪽에 새 이미지를 쓴 뒤 다음 부팅에서 바꾸는 방식이다. 새 쪽이 부팅에 실패하면 bootcount가 다 떨어져 이전 쪽으로 돌아간다(rollback).

RAUC 공식 문서(U-Boot 연동)에서 확인한 메커니즘:

  • U-Boot 환경 변수 BOOT_ORDER(예: A B)와 슬롯별 남은 시도 횟수 BOOT_A_LEFT, BOOT_B_LEFT.
  • 부팅 시도마다 카운터가 줄고, 부팅 성공 후 rauc status mark-good이 카운터를 리셋한다. 이 명령은 보통 다른 서비스가 다 뜬 뒤 실행되는 systemd 유닛으로 둔다.
  • 사용자 공간은 fw_printenv / fw_setenv(/etc/fw_env.config)로 U-Boot 환경을 읽고 쓴다. 환경은 이중(redundant) 저장을 권장.
  • 부팅된 슬롯은 커널 커맨드라인 rauc.slot=<bootname>으로 알려준다.

Mender도 같은 원리다: U-Boot bootcount · bootlimit · upgrade_available 조합, 새 이미지가 정상이면 commit, commit 전에 재부팅되면 롤백 (Mender 문서 · 포럼). SWUpdate도 dual-copy + 부트로더 변수 방식을 지원한다 [확인 필요: 변수 이름].
