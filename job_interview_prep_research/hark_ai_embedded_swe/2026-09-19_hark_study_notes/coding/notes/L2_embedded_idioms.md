# L2. 임베디드 관용구 — 디바운스·고정소수점·CRC·시간

> **목표**: 펌웨어 어느 프로젝트에나 반드시 한 번은 나오는 네 가지 관용구를, 화이트보드에서 그림으로 설명하고 그 자리에서 코드로 쓸 수 있게 만든다.
> **수록 문제**: 14 debounce_fsm · 15 fixed_point_filter · 16 crc8_table · 17 timer_wheel
> **언제 다시 보나**: (1) 상태기계를 그려야 할 때 상태를 몇 개로 쪼갤지 막힐 때. (2) Q 포맷의 범위·해상도·오버플로 여유를 계산해야 할 때. (3) CRC 스펙(poly/init/refin/xorout)을 읽어야 할 때. (4) `uint32_t` tick을 비교하는 줄을 쓸 때. 이 네 순간에 이 노트만 열면 된다.

---

## 0. 왜 이게 면접에 나오나

L0(비트)과 L1(메모리)은 "C를 아는가"를 본다. L2는 **"펌웨어를 써 본 적이 있는가"**를 본다. 네 주제 모두 면접관이 직접 디버깅한 버그와 1:1로 대응하기 때문이다.

| 주제 | 면접관이 겪은 버그 | 확인하려는 것 |
|---|---|---|
| 디바운스 | "버튼이 가끔 두 번 눌린다"는 필드 리포트 | 물리 세계의 노이즈를 코드 경계에서 막는 감각 |
| 고정소수점 | FPU 없는 파트에서 오디오에 DC offset이 쌓임 | 정수 범위를 손으로 계산하는 습관 |
| CRC | 자기들끼리는 맞는데 상대 장비와 안 맞는 CRC | 스펙을 외부 기준값으로 검증하는 태도 |
| 시간 비교 | 부팅 49.7일 뒤 모든 타임아웃이 즉시 발동 | `uint32_t` 산술과 wrap을 이해하는지 |

네 개 다 **코드는 20줄인데 틀리면 필드에서 터지고 재현이 어렵다**. 면접 가성비가 가장 높은 구간이다.
## 1. 디바운스와 상태기계

### 1.1 접점이 튀는 이유 — 하드웨어에서 출발

기계식 스위치는 금속 조각 두 개가 부딪히는 것이다. 부딪히면 튄다. 접점이 붙었다 떨어지는 것이 5~20 ms 동안 수십 번 반복된다.

```
  3.3V ──────┐ ┌─┐ ┌┐ ┌──────────────────┐ ┌┐ ┌─┐ ┌──────
  0V         └─┘ └─┘ └┘ └──────────────────┘ └┘ └─┘ └──
             |<--12ms-->|    안정 구간     |<--8ms-->|
              누름 바운스                    뗌 바운스
  GPIO를 1 ms마다 그대로 읽으면: 누름 6번, 뗌 6번으로 보인다
```

디바운스의 정의는 한 문장이다. **"같은 값이 충분히 오래 유지되면 그 값을 믿는다."** 충분히 오래 = 바운스보다 길고 사람의 연타보다 짧은 값. 실무에서 15~30 ms를 쓰고, 문제 14는 20 ms다.

### 1.2 상태기계 다이어그램

상태는 네 개다. "안정된 두 값" + "각 방향의 후보 상태".

```
                      raw=1 (t_edge = now)
        ┌──────────────────────────────────────┐
        │                                      v
  ┌───────────┐                        ┌───────────────┐
  │  IDLE     │                        │  WAIT_PRESS   │
  │ (뗌 안정) │<───────────────────────│  (누름 후보)  │
  └───────────┘   raw=0 : n_glitch++   └───────────────┘
        ^                                      │ raw=1 그리고
        │ raw=0 그리고                         │ now - t_edge >= 20ms
        │ now - t_edge >= 20ms                 │   -> emit PRESS
        │   -> emit RELEASE                    │      t_press = t_edge
        │                                      v
  ┌───────────────┐   raw=1 : n_glitch++  ┌────────────┐
  │ WAIT_RELEASE  │──────────────────────>│  DOWN      │
  │  (뗌 후보)    │<──────────────────────│ (누름 안정)│
  └───────────────┘   raw=0 (t_edge=now)  └────────────┘
                                                │ raw=1 그리고 !long_fired
                                                │ 그리고 now - t_press >= 800ms
                                                v  -> emit LONG_PRESS
                                        long_fired = true (상태는 DOWN 유지)
```

읽어야 할 세 가지. (1) **이벤트는 전이에서만 나온다** — 그래서 호출당 최대 하나다. (2) **후보 상태에서 되돌아가는 화살표에는 이벤트가 없다** — 바운스를 삼키는 자리가 정확히 여기다. (3) **롱프레스는 상태 추가 없이 `long_fired` 플래그로 처리한다** — 상태를 늘리면 뗌 처리를 두 군데 써야 한다.

### 1.3 왜 `t_press = t_edge` 인가

롱프레스를 "물리적으로 누른 순간부터"로 재려면 확정 시각이 아니라 후보 시작 시각을 기준으로 삼아야 한다.

```
t=0    raw가 1이 됨 (t_edge = 0)   <- 사용자가 실제로 누른 순간
t=20   PRESS 확정. t_press = 0 으로 둔다(확정 시각 20이 아니다)
t=800  LONG_PRESS                  <- t_press = 20 이었다면 t=820. 20 ms 늦다
```

20 ms는 사람이 못 느끼지만, 이 선택을 "어느 쪽으로 했고 왜"로 말할 수 있는지가 면접에서 갈린다.

### 1.4 디바운스 구현 세 가지

| 방식 | 상태 | 장점 | 단점 |
|---|---|---|---|
| 시간 기반 (문제 14) | 상태 + 타임스탬프 | 폴링 주기와 무관하게 동작 | 구조체가 조금 크다 |
| 카운터/적분기 | `uint8_t` 카운터 | 아주 작다 | 폴링 주기가 바뀌면 특성이 바뀐다 |
| 시프트 레지스터 | `uint8_t` 히스토리 | 한 줄로 끝난다 | 고정 창. 롱프레스 얹기 불편 |

```c
/* 시프트 레지스터 버전. 8회 연속 같은 값이면 확정 = 폴링 주기 x 8 */
hist = (uint8_t)((hist << 1) | (raw ? 1u : 0u));
if (hist == 0xFFu)      { /* 확정 눌림 */ }
else if (hist == 0x00u) { /* 확정 뗌   */ }
```

폴링이 불규칙해지면 안정 시간도 같이 흔들린다. 그래서 문제 14는 시간 기반을 택했다.
## 2. 고정소수점 — Q 포맷

### 2.1 Q 포맷 표

Q 포맷은 "정수를 `2^n`으로 나눠서 읽기로 약속한 것"이다. 하드웨어는 정수만 안다. 소수점은 사람의 머릿속에만 있다.

| 포맷 | 저장 타입 | 배율 | 표현 범위 | 해상도(1 LSB) |
|---|---|---|---|---|
| Q7 | `int8_t` | `2^7` = 128 | -1.0 ~ +0.9921875 | 0.0078125 |
| **Q15** | `int16_t` | `2^15` = 32768 | -1.0 ~ +0.999969482421875 | 0.000030517578125 |
| UQ16 | `uint16_t` | `2^16` = 65536 | 0.0 ~ +0.9999847412109375 | 0.0000152587890625 |
| Q31 | `int32_t` | `2^31` | -1.0 ~ +0.9999999995343387 | 0.0000000004656612873 |
| **Q16.16** | `int32_t` | `2^16` = 65536 | -32768.0 ~ +32767.9999847412109375 | 0.0000152587890625 |
| Q8.24 | `int32_t` | `2^24` | -128.0 ~ +127.99999994039536 | 0.000000059604644775 |

읽는 법: **Q15는 "소수부 15비트"**, **Q16.16은 "정수부 16비트 + 소수부 16비트"**다. 앞에 정수부 자릿수가 붙어 있으면 후자, 없으면 전체가 소수부다.

세 가지를 반드시 같이 외운다. (1) `+1.0`은 Q15에 **없다** — 최대는 `32767/32768 = 0.99997`이고 `-1.0`은 있다. 2의 보수라 비대칭이다. (2) 따라서 `(-1.0) x (-1.0)`이 유일한 오버플로 조합이라 포화시켜야 한다. (3) Q15 x Q15 = **Q30**이므로 곱하기 전에 `int32_t`로 넓히지 않으면 결과가 들어갈 곳이 없다.

```
  Q15 a  :  s.fffffffffffffff                    (16 bit)
  Q15 b  :  s.fffffffffffffff                    (16 bit)
  a * b  :  ss.ffffffffffffffffffffffffffffff    (32 bit, Q30)
              ^^^^^^^^^^^^^^^^ 여기가 쓸 Q15    + 버려지는 15비트
  >> 15  :  s.fffffffffffffff                    <- 여기서 반올림한다
```

### 2.2 반올림 한 줄이 왜 중요한가

`>> 15`는 **버림**이다. 버림은 음수 쪽으로 치우친다(산술 시프트). 평균 -0.5 LSB의 편향이 곱셈마다 생긴다.

```
그냥 시프트:    (p) >> 15            편향 -0.5 LSB, 오차 [-1, 0]
반올림 더하기:  (p + (1<<14)) >> 15   편향  0.0 LSB, 오차 [-0.5, +0.5]
```

48 kHz 오디오에서 샘플당 곱셈이 하나면 초당 48000번 편향이 들어간다. IIR처럼 결과를 다시 상태에 쓰는 필터에서는 이것이 **DC offset으로 쌓여** 스피커 코일이 한쪽으로 밀린다.

### 2.3 두 필터를 나란히

```
이동평균 (FIR), N=8 :  y[k] = (x[k] + ... + x[k-7]) / 8

  x ──┬──> [ buf[8] 링버퍼 ] ──> sum ──> / 8 ──> y
      └────────────────────────────┘  러닝 합: 새 것 더하고 가장 오래된 것 빼기

1차 IIR (EWMA)      :  y[k] = y[k-1] + alpha * (x[k] - y[k-1])

  x ──> (-) ──> x alpha ──> (+) ──┬──> y
        ^                    ^    │
        └──────── acc ───────┴────┘   상태 하나가 전부
```

| | 이동평균 (N=8) | 1차 IIR |
|---|---|---|
| 기억 | 정확히 8샘플. 그 전 값은 출력에 전혀 없다 | 무한. 지수적으로 잊는다(시간상수 약 `1/alpha` 샘플) |
| RAM | 22바이트 | 6바이트 |
| 비용 | 덧셈·뺄셈·나눗셈 각 1 (N이 `2^k`면 시프트) | 뺄셈·곱셈·덧셈 각 1. 나눗셈 없음 |

**스텝 응답을 정확히 N샘플에 끝내야 하면 이동평균**, **RAM과 사이클이 아까우면 IIR**이다. 같은 잡음 제거량이면 IIR이 거의 항상 싸다.

### 2.4 상태를 Q30으로 두는 이유 — dead band

IIR을 이렇게 쓰는 코드를 흔히 본다.

```c
y += (x - y) >> 3;        /* alpha = 1/8. 짧고 빠르다. 그리고 멈춘다. */
```

`x - y`가 8보다 작아지면 `>> 3`이 0이 되고, 그 순간부터 `y`는 영원히 움직이지 않는다. 상수 입력에 대해 `y`가 `x - 7`에서 멈출 수 있다. 이것이 **dead band**이고, 온도 센서라면 "0.7도가 영구히 안 맞는다"로 나타난다. 문제 15는 상태를 출력보다 15비트 더 정밀하게(Q30) 들고 있어서 이 문제가 없다.

```c
int32_t y   = f->acc >> 15;           /* 출력은 Q15 */
int32_t err = (int32_t)x - y;         /* -65535 .. +65535 */
f->acc += (int32_t)f->alpha * err;    /* 상태는 Q30. 1 LSB보다 작은 변화도 남는다 */
```

`err`가 1이라도 `acc`는 `alpha`만큼 확실히 움직이고, 그것이 쌓여 언젠가 `acc >> 15`를 한 칸 옮긴다. 그래서 상수 입력에 **정확히** 수렴한다.

### 2.5 오버플로 예산을 손으로 계산하기

면접에서 점수가 되는 부분은 코드가 아니라 **이 계산을 코드 쓰기 전에 하는 것**이다.

```
  |err| <= 65535 (x=+32767, y=-32768)   alpha <= 32767
  |곱|  <= 65535 x 32767 = 2,147,418,945
  int32 한계             = 2,147,483,647   ->  여유 64,702. 들어간다. 딱.
```

이어서 바로 말할 것. **"그래서 `alpha`를 Q16(최대 65535)으로 키우면 이 줄이 넘칩니다."** 한계를 아는 것이 구현을 아는 것보다 높은 평가를 받는다.
## 3. CRC — 비트 루프에서 테이블로

### 3.1 CRC는 나눗셈이다

CRC는 메시지를 GF(2) 계수 다항식으로 보고 생성 다항식으로 나눈 **나머지**다. GF(2)에서 덧셈과 뺄셈이 모두 XOR이라 나눗셈이 "시프트하고 XOR하기"가 된다.

```
  비반사(MSB-first), CRC-16/CCITT-FALSE (05번 문제)
    crc ^= (b << 8);   바이트를 위쪽에 XOR
    8번: 최상위 비트가 1이면 crc = (crc << 1) ^ 0x1021, 아니면 crc <<= 1

  반사(LSB-first), CRC-8/MAXIM-DOW (16번 문제)
    crc ^= b;          바이트를 아래쪽에 XOR
    8번: 최하위 비트가 1이면 crc = (crc >> 1) ^ 0x8C, 아니면 crc >>= 1

  0x31 = 0011 0001  ->  뒤집으면 1000 1100 = 0x8C
```

`0x8C`는 `0x31`을 비트 반전한 값이다. **같은 다항식인데 표기가 반대**다. CRC 구현에서 가장 흔한 혼동 지점이다.

### 3.2 비트 vs 테이블 — 같은 일을 하는 두 그림

```
[비트 루프]  바이트 하나에 8회전          [테이블]  바이트 하나에 참조 1회

   crc ──XOR── b                            crc ──XOR── b
        │                                        │
        v                                        v  index 0..255
   ┌─> shift 1 ──> LSB=1? ──yes──> ^0x8C ─┐   ┌──────────────────┐
   │                 │                    │   │ table[0]   = 0x00│
   │                 no ───────────────>  │   │ table[1]   = 0x5E│
   └────────── 8번 반복 <──────────────────┘   │    ...           │
        │                                     │ table[255] = 0xC3│
        v                                     └────────┬─────────┘
     새 crc                                            v
                                                    새 crc

   시프트 8, 분기 8, XOR<=8 / Flash 0     XOR 1, 로드 1 / Flash 256바이트

   왜 되나: CRC는 GF(2) 위에서 선형이라 한 바이트 갱신을
            crc_next = f(crc XOR b) 로 쓸 수 있다(f = 위의 8회전).
            (crc XOR b)는 0..255 중 하나 -> 전부 미리 계산 가능.
            table[i] = f(i) = "crc가 0일 때 바이트 i를 먹인 결과"
   중간 지점: 니블 테이블 16바이트, 바이트당 참조 2회.
```

CRC-8은 레지스터가 8비트라서 `crc = table[crc ^ b]`로 끝난다. CRC-16/32에서는 레지스터가 인덱스보다 넓으므로 위쪽을 살려야 한다.

```c
crc = (uint16_t)((crc << 8) ^ table[((crc >> 8) ^ b) & 0xFFu]);   /* CRC-16 */
crc = (crc >> 8) ^ table[(crc ^ b) & 0xFFu];                      /* CRC-32 반사 */
```

### 3.3 CRC 스펙은 항목 일곱 개다

CRC를 "poly 0x31 CRC-8"이라고만 말하는 스펙은 불완전하다. 일곱 개가 다 있어야 값이 정해진다.

| 항목 | 뜻 | 16번 문제의 값 |
|---|---|---|
| width | 레지스터 비트 폭 | 8 |
| poly | 생성 다항식(정방향 표기) | `0x31` |
| init | 시작 레지스터 값 | `0x00` |
| refin | 입력 바이트를 LSB부터 먹는가 | true |
| refout | 출력을 비트 반전하는가 | true |
| xorout | 마지막에 XOR할 값 | `0x00` |
| check | `"123456789"`에 대한 값 | `0xA1` |

**`check`가 있어야 스펙이다.** 새 CRC를 구현하면 항상 `"123456789"`로 먼저 검증한다. 자기들끼리 일관되고 상대 장비와 안 맞는 CRC는 이 한 줄이 없어서 생긴다. 16번 문제는 DS18B20 데이터시트의 scratchpad 예제(`50 05 4B 46 7F FF 0C 10` -> `0x1C`)를 두 번째 기준값으로 더 둔다. 같은 poly를 비트 방향만 틀리게 구현하면 `0xA2`가 나온다 — `0xA1`과 1비트 차이라서, 우연히 비슷한 값이 나오는 것이 더 위험하다.

### 3.4 residue — 비교 없이 검증하기

`xorout = 0`인 변종은 좋은 성질이 있다. 메시지 뒤에 그 CRC를 붙여 **이어서 한 번 더 돌리면 0이 된다**.

```
  송신:  [ msg ][ crc ]
  수신:  crc8(msg 와 crc를 이어서) == 0 ?

  따로 계산해서 비교할 필요가 없다. 1-Wire 드라이버가 이 형태를 쓴다.
```

`xorout`이 0이 아니면 이 값이 0이 아닌 다른 상수가 되고, 그 상수를 **residue**라고 부른다. 스펙에 residue가 적혀 있으면 이 방식을 쓸 수 있다.

### 3.5 CRC가 보장하는 것과 보장하지 않는 것

| 잡는다 | 못 잡는다 |
|---|---|
| 모든 1비트 에러 | 생성 다항식의 배수에 해당하는 에러 패턴 |
| `width` 비트 이하의 모든 버스트 에러 | 의도적 위조(CRC는 서명이 아니다) |
| 대부분의 랜덤 에러 (`1/2^width` 확률로 통과) | `init = 0x00`일 때 메시지 앞에 붙은 `0x00`들 |

마지막 항목이 실전 함정이다. `init = 0x00`이면 `crc8({}) = crc8({00}) = crc8({00 00}) = 0x00`이라 앞이 0으로 채워진 프레임의 길이 에러를 못 잡는다. 그래서 많은 변종이 `init = 0xFF`를 쓴다. CRC-8/MAXIM-DOW는 `init = 0x00`이고, 1-Wire는 프레임 길이가 고정이라 문제가 되지 않는다. 약점을 아는 것도 스펙을 아는 것이다.
## 4. 시간 — wrap-safe 비교

### 4.1 수직선으로 보기

MCU의 tick은 거의 항상 free-running `uint32_t`다. 1 ms tick이면 `2^32` ms = **49.7일**마다 0으로 돌아온다. 항상 켜져 있는 제품에서는 반드시 일어나는 일이다.

tick 값은 직선이 아니라 원이다. `0xFFFFFFFF` 다음이 `0x00000000`이다. wrap 근처만 확대해 보면:

```
  deadline = 0xFFFFFFFB                    now = 0x00000005
        |                                       |
  ──────+──────+──────+──────+──────+═══════════+──────>
     FFFFFFFB FFFFFFFD FFFFFFFF  wrap 0x0      0x5

   now - deadline = 0x5 - 0xFFFFFFFB = 0x0000000A
                    (uint32_t 뺄셈은 2^32 모듈로. 정확히 +10)
   (int32_t)0xA = +10 >= 0        ->  "도달했다". 맞다.
   순진한 비교 5 >= 4294967291    ->  false. 틀리다. 49.7일 뒤 여기서 터진다.
```

핵심은 **뺄셈의 결과를 부호 있는 정수로 읽는 것**이다.

```
  (uint32_t)(now - deadline) 의 32비트 패턴을 int32_t로 재해석하면
    0x00000000 .. 0x7FFFFFFF  ->  +0 .. +2^31-1  ->  now가 뒤 (도달)
    0x80000000 .. 0xFFFFFFFF  ->  -2^31 .. -1    ->  now가 앞 (미도달)

              미도달                      도달
    <─────────────────────────|─────────────────────────>
    -2^31                 deadline                 2^31-1
```

"두 시각의 실제 차이가 `2^31`보다 작다"는 가정 아래 부호 하나로 순서가 나온다. 그래서 지연을 `2^31 - 1`로 제한한다. 1 ms tick에서 `2^31` ms = **24.8일**이다. 더 긴 타이머가 필요하면 tick을 64비트로 올리거나 계층을 하나 더 쌓는다.

### 4.2 시간 비교 세 가지 패턴

| 목적 | 쓰는 식 | 이유 |
|---|---|---|
| 경과 시간 (얼마나 지났나) | `(uint32_t)(now - then) >= LIMIT` | unsigned 뺄셈이 2^32 모듈로로 정확하다 |
| 만료 판정 (시각에 도달했나) | `(int32_t)(now - deadline) >= 0` | 미래/과거를 부호로 구분해야 한다 |
| 절대 비교 | 쓰지 않는다 | wrap에서 무조건 깨진다 |

문제 14(디바운스)는 첫 번째, 문제 17(타이머)은 두 번째를 쓴다. 이유가 다르다. 경과 시간은 기준 시각이 **항상 과거**라 차이가 항상 양수이므로 unsigned로 충분하다. 만료 판정은 deadline이 미래일 수도 과거일 수도 있어 양쪽을 구분해야 하므로 부호가 필요하다.

캐스트를 빼면 `uint32_t >= 0`이 되어 **항상 true**다. 캐스트를 잊은 것이 이 버그의 가장 흔한 형태다.

### 4.3 drift-free 재장전

주기 타이머를 다시 거는 방법이 두 가지 있다. 둘의 차이가 장기 실행에서 드러난다.

```
  100 ms 주기, tw_tick이 37 ms 늦게 불린 경우

  expiry = now + period  (드리프트 있음)
     expiry: 100 -> 237 -> 374 -> 511 ...   매번 37 ms씩 밀린다
     하루 뒤엔 지연이 누적되고 다른 타이머와의 위상도 무너진다
  expiry += period       (드리프트 없음)
     expiry: 100 -> 200 -> 300 -> 400 ...   원래 격자에 붙어 있다
     늦게 본 회차만 늦고 다음 회차는 제자리
```

주기 타이머는 거의 항상 후자를 원한다. 1초 주기로 시계를 그리는 코드가 전자면 하루에 몇 분이 밀린다.

그리고 `expiry += period`를 쓰면 새 질문이 생긴다. **만료가 다섯 번 지나 있으면 콜백을 다섯 번 부르나?** 몰아서 부르면 이미 바쁜 루프를 더 밀어 악순환이 되고, 버리면 조용히 회차를 잃는다. 문제 17은 버리는 쪽을 택하고 `n_missed`로 센다. 진단 카운터가 있으면 필드에서 "루프가 밀렸다"를 증명할 수 있다. 정책 선택 자체보다 **선택했다는 사실과 근거를 말할 수 있는지**가 중요하다.

### 4.5 콜백 재진입 — 순서가 정책이다

콜백은 다른 타이머를 취소할 수도, 새로 걸 수도, 자기 자신을 재시작할 수도 있다. 그래서 `tw_tick()`의 순서가 곧 명세가 된다.

```
  1) 만료된 슬롯 목록을 먼저 확정한다(스냅샷)
       -> 콜백이 새로 만든 타이머는 이번 tw_tick에서 실행되지 않는다
          (슬롯 번호에 따라 되기도 안 되기도 하는 비결정성 제거)
  2) 각 슬롯 실행 직전에 active와 만료를 다시 확인한다
       -> 앞선 콜백이 취소했거나 미래로 재시작한 타이머는 건너뛴다
  3) 재장전(또는 비활성화)을 콜백 호출 '전에' 끝낸다
       -> 콜백이 자기 자신을 취소·재시작해도 나중에 되살아나지 않는다
```

3번을 뒤집으면(콜백 먼저, 재장전 나중) **"콜백에서 `tw_cancel(self)`를 불렀는데 타이머가 계속 돈다"**는 버그가 된다. 재진입 설계에서 가장 자주 나오는 실수다.

## 면접 질문 10개

**1. 버튼 디바운스를 어떻게 구현하나?**
같은 값이 일정 시간 유지되면 그 값을 확정하는 상태기계로 만듭니다. 상태는 안정 두 개와 후보 두 개, 총 네 개입니다. 후보 상태에서 값이 되돌아가면 이벤트 없이 조용히 되돌아가고, 그것이 바운스를 삼키는 자리입니다. 시간은 20 ms 정도를 쓰는데 바운스보다 길고 사람의 연타보다 짧아야 합니다. 폴링 주기와 무관하게 동작하도록 카운터가 아니라 타임스탬프 차이로 판정합니다.
"I model it as a four-state machine: two stable states and one candidate state per direction, and a value is only accepted after it has been stable for twenty milliseconds."

**2. 롱프레스는 어디에 붙이나? 상태를 하나 더 만들어야 하나?**
상태를 늘리지 않고 누름 시각과 플래그 하나로 처리합니다. 누름이 확정된 상태에서 누름 시각으로부터 800 ms가 지났고 아직 이벤트를 내지 않았으면 한 번 내고 플래그를 세웁니다. 상태를 늘리면 뗌 처리를 두 군데 써야 해서 오히려 복잡해집니다. 누름 시각은 확정 시각이 아니라 후보가 시작된 시각으로 잡아야 사용자 체감과 맞습니다.
"I keep the long press as a timestamp plus a one-shot flag inside the pressed state, rather than adding a fifth state that would duplicate the release logic."

**3. Q15가 정확히 무엇인가? `+1.0`은 왜 없나?**
`int16_t`를 `32768`로 나눠 읽기로 약속한 형식입니다. 범위는 `-1.0`부터 `+0.99997`까지이고 해상도는 `1/32768`입니다. 2의 보수라 음수 쪽이 한 칸 더 넓어서 `-1.0`은 있고 `+1.0`은 없습니다. 그래서 `(-1.0)` 곱하기 `(-1.0)`이 유일한 오버플로 조합이고, 이것만 포화시키면 나머지 모든 입력은 안전합니다.
"Q15 stores a fraction as an int16 scaled by thirty-two thousand seven hundred sixty-eight, so the range is minus one to just under plus one, and minus one times minus one is the single case that saturates."

**4. 고정소수점 곱셈에서 반올림을 왜 하나?**
`>> 15`는 버림이라 곱셈마다 평균 0.5 LSB의 편향이 생깁니다. 결과를 다시 상태에 쓰는 IIR에서는 이 편향이 DC offset으로 누적되어 오디오에서는 스피커가 한쪽으로 밀리고 센서에서는 값이 서서히 치우칩니다. 시프트 전에 `1 << 14`를 더하면 편향이 0이 되고 오차가 플러스마이너스 0.5 LSB로 대칭이 됩니다. 한 줄 비용으로 누적 오차를 없애는 거래입니다.
"A bare right shift truncates, which biases every product by half an LSB, and in a recursive filter that bias accumulates into an audible DC offset."

**5. 이동평균과 1차 IIR 중 무엇을 고르나?**
스텝 응답이 정확히 N 샘플 안에 끝나야 하거나 선형 위상이 필요하면 이동평균입니다. RAM과 사이클이 아까우면 IIR입니다. 8샘플 이동평균이 22바이트와 나눗셈 하나를 쓰는 데 비해 IIR은 6바이트와 곱셈 하나로 끝나고, 비슷한 잡음 제거량을 냅니다. 단 IIR은 기억이 무한해서 오래된 값이 지수적으로만 사라집니다.
"I pick the boxcar when I need a bounded, exactly-N-sample memory, and the first-order IIR when RAM and cycles matter more than the exact shape of the response."

**6. 고정소수점에서 오버플로를 어떻게 막나?**
코드를 쓰기 전에 각 중간값의 최대 크기를 손으로 계산합니다. 예를 들어 IIR의 오차항은 최대 65535, `alpha`는 최대 32767이라 곱이 약 21억 4천만으로 `int32_t` 한계에 6만 정도 여유를 두고 들어갑니다. 계산해서 안 들어가면 상태의 Q 포맷을 바꾸거나 `alpha` 범위를 줄이거나 64비트 곱을 씁니다. 32 곱하기 32에서 64비트 곱은 ARM에서 한 명령이라 생각보다 싸고, 비싼 것은 64비트 나눗셈입니다.
"I compute the worst-case magnitude of every intermediate before writing the line, and I state the remaining headroom in a comment so the next person can see the budget."

**7. CRC 테이블은 왜 256개면 되나?**
CRC는 GF(2) 위에서 선형이라 한 바이트 갱신을 "레지스터와 입력 바이트를 XOR한 뒤 8회전 시프트"로 쓸 수 있습니다. XOR 결과가 0부터 255 중 하나이므로 그 256가지를 미리 계산해 두면 런타임에는 배열 참조 한 번이 됩니다. Flash 256바이트를 내고 바이트당 8회전을 없애는 거래이고, 니블 테이블 16바이트로 중간 지점을 잡을 수도 있습니다.
"Because CRC update factors into a function of the register XOR the input byte, and that XOR has only two hundred fifty-six possible values."

**8. 새 CRC를 구현했다. 맞는지 어떻게 확인하나?**
카탈로그의 check 값으로 확인합니다. ASCII `"123456789"` 9바이트에 대한 값이 스펙에 적혀 있고, CRC-8/MAXIM-DOW는 `0xA1`입니다. 자기 구현끼리만 비교하면 일관되게 틀린 CRC가 나오고, 그것이 상대 장비와 안 맞는 사고의 전형입니다. 가능하면 데이터시트의 실제 프레임 예제를 두 번째 기준값으로 더 씁니다. 그리고 poly와 비트 방향을 함께 확인합니다. 같은 poly를 방향만 틀리게 쓰면 값이 1비트만 달라져서 더 위험합니다.
"I check against the published check value for the named variant before anything else, because a CRC that is only self-consistent is the classic interoperability bug."

**9. `uint32_t` tick을 어떻게 비교하나?**
경과 시간은 `(uint32_t)(now - then)`으로 구합니다. unsigned 뺄셈은 `2^32` 모듈로라 wrap을 건너도 차이가 정확합니다. 만료 판정은 `(int32_t)(now - deadline) >= 0`으로 합니다. 미래와 과거를 부호로 구분해야 하기 때문입니다. `now >= deadline`은 wrap에서 무조건 깨지고, 1 ms tick이면 부팅 49.7일 뒤에 모든 타임아웃이 즉시 발동합니다. 대가로 표현 가능한 차이가 플러스마이너스 `2^31`로 줄어드니 지연을 그 아래로 제한합니다.
"I always compare time as a signed difference, never as absolute values, because the tick is modulo two to the thirty-two and rolls over about every fifty days."

**10. 주기 타이머를 다시 거는 두 방법의 차이는?**
`expiry += period`는 원래 격자에 붙어 있어서 드리프트가 없고, `expiry = now + period`는 늦게 본 만큼이 매번 누적되어 밀립니다. 1초 주기로 시간을 세는 코드가 후자면 하루에 몇 분이 틀립니다. 대신 전자를 쓰면 "만료가 여러 번 지났을 때 콜백을 몇 번 부르나"를 정해야 합니다. 저는 한 번만 부르고 건너뛴 횟수를 카운터에 세는 쪽을 택합니다. 몰아서 부르면 이미 밀린 루프를 더 밀어 악순환이 되기 때문입니다.
"Re-arming with expiry plus period keeps the original phase, so the timer is drift-free, and the price is that I must decide what to do with periods that were missed."

## 체크리스트

- [ ] 디바운스 상태기계를 네 상태로 그리고, 이벤트가 나오는 전이를 짚을 수 있다
- [ ] 후보 상태에서 되돌아가는 화살표가 왜 이벤트를 내지 않는지 설명할 수 있다
- [ ] Q15의 범위와 해상도를 숫자로 말할 수 있다 (`-1.0` ~ `+0.99997`, `1/32768`)
- [ ] Q15 x Q15 = Q30 이고 `int32_t`로 넓혀야 하는 이유를 그림으로 그릴 수 있다
- [ ] `>> 15` 전에 `1 << 14`를 더하는 이유를 "편향"이라는 말로 설명할 수 있다
- [ ] `(-1.0) x (-1.0)`이 유일한 포화 조합인 이유를 말할 수 있다
- [ ] `y += (x - y) >> k`의 dead band를 재현하고 고칠 수 있다
- [ ] 중간 계산의 최대 크기를 손으로 계산해 int32 여유를 숫자로 댈 수 있다
- [ ] CRC 스펙 일곱 항목을 나열하고 `table[i] = f(i)`를 GF(2) 선형성으로 설명할 수 있다
- [ ] 반사 CRC에서 `0x31`이 `0x8C`가 되는 것을 손으로 뒤집어 보일 수 있다
- [ ] `"123456789"` check 값과 residue 0으로 검증하는 습관이 있다
- [ ] 경과 시간과 만료 판정의 식이 왜 다른지 설명할 수 있다
- [ ] wrap 수직선을 그려 `(int32_t)(now - deadline)`의 부호와 `2^31`(24.8일) 한계를 설명할 수 있다
- [ ] drift-free 재장전과 그 대가(놓친 주기 정책)를 함께 말할 수 있다
- [ ] 콜백 앞에서 재장전을 끝내야 하는 이유를 `tw_cancel(self)`로 설명할 수 있다
