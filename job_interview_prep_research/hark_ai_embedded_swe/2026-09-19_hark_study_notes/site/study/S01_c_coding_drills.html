0. 이 노트를 쓰는 법#

모든 풀이는 cc -std=c11 -Wall -Wextra -O2로 경고 없이 컴파일되고, 각 문제마다 작은 assert 테스트(정상 경로, 경계, wrap-around, 손상 입력)를 통과한 코드다. 테스트 main()은 지면 때문에 뺐다. 헤더에 들어갈 static inline 함수 묶음은 그대로 .h로 옮기면 된다.

면접 코딩에서 임베디드 면접관이 보는 것은 알고리즘 난이도가 아니라 다음 네 가지다.

  1. 누가 이 코드를 동시에 부르나: ISR, task, DMA, 다른 코어. 공유 변수마다 "writer가 누구인지"를 먼저 말한다.
  2. 메모리가 어디서 오나: 정적 배열, pool, 스택. malloc을 쓰면 왜 쓰는지 설명해야 한다.
  3. 정수 폭과 부호: uint8_t 승격, 1 << 31, 64-bit host의 UL, 음수 right shift.
  4. 실패 경로: full/empty, CRC 불일치, 타임아웃, 전원 차단. "그리고 에러 카운터를 남긴다"까지 말하면 필드 경험이 있는 사람으로 보인다.

풀이 순서 공식은 항상 같다: 인터페이스(함수 시그니처)부터 쓰고 → 불변식(invariant) 한 줄 → 코드 → 테스트 케이스 3개를 소리 내어 돌린다.

1. 동시성·메모리#

Q01. Implement a lock-free single-producer single-consumer ring buffer that a UART RX ISR writes and a task reads.#

왜 묻나: 임베디드 코딩 면접 1순위 문제다. Hark 같은 기기라면 SoC–MCU 사이 UART/SPI IPC, 센서 FIFO, 로그 버퍼가 전부 이 구조다. 면접관은 full/empty 구분, index wrap, 그리고 "왜 lock 없이 안전한가"를 설명하는지 본다.

문제: 크기 고정, 바이트 단위. producer는 ISR 하나, consumer는 task 하나. put은 full이면 실패를 돌려주고, get은 empty면 실패를 돌려준다. 인터럽트를 끄지 말 것.

접근:

  • head는 producer만, tail은 consumer만 쓴다. 각 변수의 writer가 한 명이므로 read-modify-write 경쟁이 없다.
  • index를 버퍼 크기로 자르지 않고 32-bit로 계속 증가시키고, 접근할 때만 & (SIZE-1)로 자른다. 그러면 head - tail이 unsigned wrap 덕분에 항상 정확한 개수가 되고, "한 칸 비워 두기" 없이 SIZE개를 꽉 채울 수 있다. 이를 위해 SIZE는 2의 거듭제곱이어야 한다.
  • 순서가 핵심이다. producer는 데이터를 쓴 뒤 head를 올려야 하고, consumer는 데이터를 읽은 뒤 tail을 올려야 한다. 컴파일러와 CPU가 이 순서를 바꾸지 못하게 release/acquire를 쓴다.

복잡도/메모리: put/get 모두 O(1). 메모리는 SIZE + 8 byte. 분기 1개, 나눗셈 없음.

메모리 배리어 이야기 (반드시 말할 것):

  • volatile만으로는 부족하다. volatile은 "이 변수 접근을 없애거나 합치지 마라"일 뿐, 일반 변수(buf[])와의 순서를 보장하지 않는다. 컴파일러는 buf[h] = b를 head 갱신 뒤로 옮길 수 있다.
  • 단일 코어 Cortex-M에서 ISR과 task는 같은 코어에서 돌기 때문에 CPU가 자기 자신이 본 순서를 뒤집지는 않는다. 이 경우 실제로 필요한 것은 컴파일러 배리어다. 그래도 C11 release/acquire로 쓰면 이식성이 생기고, GCC는 ARMv7-M에서 보통 release store 앞에 DMB를 넣는다(ARMv8-M Mainline은 STL/LDA 명령을 쓸 수 있다). 비용은 수 사이클이다.
  • 진짜 하드웨어 배리어가 필요한 경우: 듀얼코어(예: SoC와 MCU가 공유 SRAM으로 mailbox를 두는 구조), DMA가 버퍼를 읽는 경우, Cortex-M7처럼 write buffer·cache가 있는 코어에서 다른 bus master가 볼 때. 이때는 DMB와 함께 cache clean/invalidate도 필요하다.
  • 32-bit 정렬 변수의 load/store는 Cortex-M에서 single-copy atomic이라 head/tail이 찢어져 읽히는 일은 없다. 64-bit index였다면 찢어짐이 생긴다.

엣지 케이스: SIZE가 2의 거듭제곱이 아니면 h & (SIZE-1)이 틀린다(_Static_assert로 막았다). index가 0xFFFFFFFF에서 0으로 넘어가도 h - t는 정확하다(테스트로 확인). full일 때 ISR은 기다릴 수 없으므로 드롭하고 overflow 카운터를 올린다. consumer가 여럿이면 이 구조는 깨진다.

English answer: "Head is written only by the ISR and tail only by the task, so each index has a single writer and I don't need a lock. I let the indices run free as 32-bit counters and mask on access, so head minus tail is always the fill level even across wrap, and I can use every slot. The producer writes the data first and then publishes head with a release store; the consumer reads head with acquire before touching the data. On a single-core Cortex-M that's mostly a compiler barrier, but it becomes a real DMB requirement with a second core or DMA."

꼬리질문:

  • "여러 바이트를 한 번에 넣으려면?" → 연속 공간 길이를 계산해 memcpy 두 번(끝까지, 처음부터)으로 나누고 head는 마지막에 한 번만 올린다. DMA가 직접 쓰게 하려면 "연속으로 쓸 수 있는 길이"를 돌려주는 API가 필요하다.
  • "producer가 둘(ISR 두 개)이면?" → 우선순위가 다른 ISR은 서로 선점하므로 head에 경쟁이 생긴다. critical section(PRIMASK/BASEPRI)으로 감싸거나 LDREX/STREX CAS로 slot을 예약한다.
  • "task를 언제 깨우나?" → ISR에서 vTaskNotifyGiveFromISR() 후 portYIELD_FROM_ISR(), Zephyr는 k_sem_give(). 바이트마다 깨우면 전력 낭비라 idle line 인터럽트나 임계치 기준으로 깨운다. Zephyr에는 이미 ring_buf API가 있다.

Don 스토리 연결: SSD FW의 submission/completion queue도 head/tail doorbell 구조라 같은 원리다. "NVMe queue에서 doorbell 쓰기 전에 엔트리 쓰기가 보여야 해서 barrier를 넣었다"는 식으로 연결한다.

Q02. Write a fixed-block memory pool allocator with O(1) alloc and free. No malloc allowed.#

왜 묻나: 배터리 기기 MCU는 heap 단편화가 곧 필드 크래시다. BLE 패킷, 오디오 프레임, 이벤트 메시지를 같은 크기 블록으로 관리하는 것은 표준 패턴이다. FreeRTOS에는 고정 블록 pool이 기본 제공되지 않고, Zephyr에는 k_mem_slab이 이 역할을 한다.

문제: 블록 크기와 개수는 컴파일 타임 상수. alloc은 O(1), 고갈 시 NULL. free는 O(1), 잘못된 포인터는 거부. ISR과 task 양쪽에서 부를 수 있어야 한다.

접근: free 블록 자체의 앞부분에 "다음 free 블록" 포인터를 저장하는 intrusive free list. 별도 메타데이터 배열이 필요 없다. union으로 "free일 때는 링크, 사용 중일 때는 데이터"를 표현한다. 공유 상태(free_head)는 짧은 critical section으로 보호한다.

타깃에서는 critical section을 이렇게 정의한다(CMSIS 이름).

복잡도/메모리: alloc/free O(1). 오버헤드는 pool 전체에 포인터 1개와 카운터 2개. 블록당 오버헤드 0.

엣지 케이스: 블록 크기는 포인터 크기 이상이고 정렬돼야 한다(_Static_assert). 블록 중간 주소나 다른 pool 주소를 free하면 범위·정렬 검사로 거부한다. double free는 이 코드로는 못 잡는다(아래 꼬리질문). high_water는 EVT 빌드에서 로그로 뽑아 pool 크기를 정하는 근거로 쓴다.

English answer: "I carve a static array into equal blocks and thread a free list through the blocks themselves, so there's no per-block overhead. Alloc pops the head and free pushes it back, both O(1) and deterministic, which matters in an ISR. I protect the head with a short PRIMASK critical section, validate that freed pointers belong to the pool, and track a high-water mark to size the pool from real usage."

꼬리질문:

  • "double free는?" → 블록당 1 bit 사용 bitmap을 두거나, free 시 블록에 poison 패턴(예: 0xDEADBEEF)을 써 두고 확인한다. debug 빌드에서만 켜도 된다.
  • "크기가 여러 종류면?" → 64/256/1024 같은 size class별 pool을 두고 요청 크기 이상인 가장 작은 class에서 꺼낸다(slab 방식). 내부 단편화는 생기지만 외부 단편화는 없다.
  • "critical section 없이 가능한가?" → LDREX/STREX로 lock-free stack을 만들 수 있지만 ABA 문제가 있다. MCU에서는 수 사이클짜리 PRIMASK 구간이 더 단순하고 검증하기 쉽다.

Q03. The I2S microphone DMA runs in circular mode with half-transfer and transfer-complete interrupts. Show how the ISR hands audio frames to a processing task, and detect overruns.#

왜 묻나: JD의 I2S 드라이버와 "on-device AI 추론 지원"이 만나는 지점이다. 예를 들어 Hark 같은 always-on 기기라면 마이크 → I2S/PDM DMA → wake word 모델 입력이 이 구조다. 면접관은 DMA가 쓰는 절반과 CPU가 읽는 절반을 분리하는지, task가 늦었을 때를 감지하는지 본다.

문제: 버퍼 buf[2][160](16 kHz, 10 ms 프레임). DMA가 0번 절반을 다 채우면 HT 인터럽트, 1번 절반을 다 채우면 TC 인터럽트가 온다. ISR은 복사하지 말고 "이 절반 준비됨"만 알린다. task가 처리 끝나기 전에 DMA가 같은 절반을 다시 채우면 overrun으로 센다.

접근: 절반마다 1 bit의 ready 플래그. ISR은 fetch_or로 bit를 세우고, 이미 세워져 있었다면 overrun. task는 bit를 보고 해당 절반을 처리한 뒤 fetch_and로 지운다. 두 컨텍스트가 같은 word의 다른 bit를 바꾸므로 원자적 RMW가 필요하다.

복잡도/메모리: ISR은 O(1)로 원자 연산 하나. 메모리는 2 x 160 x 2 B = 640 B. 복사 0회(zero-copy).

엣지 케이스: task 처리 시간이 프레임 주기(10 ms)를 넘으면 overrun이 계속 쌓인다. 이 카운터가 0이 아니면 모델 추론 시간이 예산을 넘은 것이다. 단, 이 방식은 다음 HT에서야 늦음을 감지한다. 실제 데이터 오염은 TC 시점(DMA가 같은 절반을 다시 쓰기 시작)부터이므로, 엄밀하게 하려면 처리 끝에 DMA의 현재 쓰기 위치(남은 전송 카운트 레지스터)를 읽어 처리 중이던 절반을 이미 침범했는지 확인한다. Cortex-M0(ARMv6-M)는 LDREX/STREX가 없어 atomic_fetch_or가 라이브러리 호출이나 interrupt 차단으로 구현된다. D-cache가 있는 코어(Cortex-M7)는 DMA가 쓴 영역을 CPU가 읽기 전에 SCB_InvalidateDCache_by_Addr()로 invalidate해야 하고, 버퍼는 cache line(32 B) 정렬·크기여야 한다.

English answer: "The DMA runs circular over two halves. The half-transfer and transfer-complete ISRs only set a ready bit for the half that just filled and notify the task; no copying in the ISR. The task processes that half in place and clears the bit. If the ISR finds the bit already set, the task missed its deadline, so I count an overrun instead of silently processing torn audio. That counter is the first thing I check when the inference budget is too tight."

꼬리질문:

  • "overrun이 나면 어떻게 하나?" → 오디오는 시간 연속성이 중요하므로 늦은 프레임을 버리고 최신 프레임부터 처리한다. 근본 해결은 3개 이상 버퍼(queue of frames)로 지터를 흡수하거나, 추론을 더 큰 프레임 단위로 묶는 것.
  • "벤더 DMA가 HT/TC를 안 주면?" → 예를 들어 nRF52의 I2S는 RXPTRUPD 이벤트마다 다음 버퍼 포인터를 써 넣는 방식이라 ping-pong을 소프트웨어로 돌린다. 개념은 같다.
  • "task를 어떻게 깨우나?" → FreeRTOS면 ISR에서 xTaskNotifyFromISR()로 half 번호를 값으로 넘기고, task는 xTaskNotifyWait()로 블록한다. 그러면 ready_mask 없이도 된다.

Q04. Implement aligned_malloc and aligned_free on top of malloc.#

왜 묻나: DMA 버퍼, cache line 정렬, ML tensor arena(보통 16 B 정렬 요구) 때문에 자주 나온다. 포인터 산술, uintptr_t, "원래 포인터를 어떻게 기억하나"를 본다.

문제: align은 2의 거듭제곱. 반환 주소는 align의 배수. aligned_free는 그 주소만 받아서 해제해야 한다.

접근: size + align - 1 + sizeof(void*)만큼 넉넉히 잡고, 포인터 한 칸을 확보한 뒤 위로 올림 정렬한다. 정렬된 주소 바로 앞 칸에 원본 포인터를 저장해 두면 free 때 꺼낼 수 있다.

복잡도/메모리: O(1) + malloc 비용. 낭비는 최대 align - 1 + sizeof(void*) byte.

엣지 케이스: align이 0이거나 2의 거듭제곱이 아니면 NULL. size가 매우 크면 덧셈 overflow로 작은 버퍼가 잡히는 보안 버그가 생기므로 먼저 검사한다. aligned_free(NULL)은 no-op. align이 포인터 크기보다 작으면 저장 칸이 정렬되지 않으므로 올린다.

English answer: "I over-allocate by alignment minus one plus one pointer, round the address up with a mask, and stash the original pointer in the word just before the aligned block. Free reads it back and calls free on the original. I check that alignment is a power of two and guard the size addition against overflow."

꼬리질문:

  • "표준 함수는?" → C11 aligned_alloc()(C11 기준 size가 alignment의 배수여야 함), POSIX posix_memalign(). 베어메탈 newlib에도 memalign()이 있다.
  • "정적 버퍼면?" → _Alignas(32) static uint8_t dma_buf[512]; 또는 GCC __attribute__((aligned(32))). 링커 스크립트에서 DMA 가능 영역 섹션에 넣는 것까지 말하면 좋다.
  • "cache line 정렬만 하면 끝인가?" → 크기도 cache line 배수로 올려야 한다. 아니면 버퍼 끝 cache line을 다른 변수와 공유해서 invalidate 때 그 변수가 날아간다.

2. 비트·레지스터#

Q05. Write macros to set, clear, and update a multi-bit field in a memory-mapped register, then configure a SPI controller with them.#

왜 묻나: BSP·드라이버 작성의 기본기다. 면접관은 volatile 포인터, 마스크 계산, read-modify-write가 한 번의 read와 한 번의 write인지, 그리고 W1C(write-1-to-clear) 레지스터에서 RMW가 위험하다는 것을 아는지 본다.

문제: 가상의 SPI CTRL 레지스터(주소와 비트 배치는 설명용 가짜): bit0 EN, bit1 CPOL, bit2 CPHA, bit[11:4] CLKDIV, bit[15:12] WORD(word size - 1). 다른 비트는 보존해야 한다. 설정 변경 전 EN을 내리는 게 이 IP의 규칙이다.

접근: GENMASK(hi, lo)로 마스크를 만들고, FIELD_PREP는 값을 마스크 위치로 shift, FIELD_GET은 반대로 꺼낸다(Linux 커널 매크로 이름을 빌렸다). 모든 상수를 32-bit unsigned로 고정한다.

실제 타깃에서는 레지스터를 이렇게 선언한다(주소는 가상).

복잡도/메모리: 상수 마스크는 컴파일 타임에 접혀서 LDR → BIC/ORR → STR 몇 명령이 된다.

엣지 케이스:

  • 처음에 1UL << n으로 썼다가 64-bit host 테스트에서 GENMASK가 틀렸다. UL은 ARM에서는 32-bit지만 x86-64 host에서는 64-bit다. host 단위 테스트를 돌리는 팀이라면 uint32_t로 고정해야 한다.
  • 1 << 31은 signed int overflow(UB)다. 항상 1u.
  • W1C 비트(인터럽트 status 등)가 같은 레지스터에 있으면 RMW가 읽은 1을 다시 써서 다른 pending 플래그를 지워 버린다. W1C 레지스터는 지울 bit만 쓴다.
  • ISR과 task가 같은 레지스터를 RMW하면 read와 write 사이에 선점되어 한쪽 변경이 사라진다. critical section, 또는 SET/CLR 별도 레지스터(많은 GPIO IP가 제공)나 Cortex-M3/M4의 bit-banding을 쓴다.

English answer: "I build masks with a GENMASK-style macro, shift values into place with FIELD_PREP, and update with a single read, mask, or, write on a volatile pointer. I keep everything unsigned 32-bit to avoid the 1 << 31 undefined behavior and host-width surprises. I'd also call out write-1-to-clear status bits, where read-modify-write is actually a bug, and ISR-versus-task races on shared registers."

꼬리질문:

  • "C bit-field struct로 레지스터를 매핑하면?" → bit-field 배치 순서와 접근 폭이 구현 정의라 컴파일러가 byte 접근을 만들 수 있다. 벤더 헤더(CMSIS)는 _Pos/_Msk 매크로 방식을 쓴다.
  • "volatile이 없으면?" → 폴링 루프 while (!(*STATUS & READY))가 한 번 읽고 무한 루프로 최적화된다.
  • "레지스터 쓰기 후 바로 효과가 보장되나?" → 버스 브리지를 지나는 주변장치는 write가 늦게 도착할 수 있다. 인터럽트 플래그를 지운 직후 ISR을 빠져나오면 같은 인터럽트가 다시 걸리는 문제가 있어, 쓰기 후 같은 레지스터를 한 번 읽거나 __DSB()를 둔다.

Q06. Count set bits, reverse the bits of a 32-bit word, and find the first set bit. Then tell me what the hardware gives you.#

왜 묻나: 짧은 워밍업이지만 "bitmap으로 free slot 찾기", "RTOS ready list에서 최고 우선순위 찾기", "SPI LSB-first 변환" 같은 실무와 연결해 말하는지 본다.

접근: popcount는 x &= x - 1(가장 낮은 1 제거) 반복 또는 SWAR(2, 4, 8 bit 단위로 병렬 합산). bit reverse는 인접 1, 2, 4, 8, 16 bit 그룹을 차례로 교환. ffs는 이진 탐색으로 0인 하위 절반을 건너뛴다.

복잡도/메모리: Kernighan은 O(set bit 수), SWAR·reverse·ffs는 분기 거의 없는 O(1)(log 32 = 5단계). 메모리 0. 8-bit lookup table(256 B)을 쓰면 더 빠르지만 flash를 쓴다.

하드웨어가 주는 것:

연산Cortex-M3/M4/M7 (ARMv7-M)Cortex-M0/M0+ (ARMv6-M)GCC builtin
count leading zerosCLZ 1 명령없음(소프트웨어)__builtin_clz
bit reverseRBIT 1 명령없음CMSIS __RBIT()
byte reverseREV, REV16REV, REV16 있음__builtin_bswap32
count trailing zerosRBIT + CLZ소프트웨어__builtin_ctz
popcount전용 명령 없음없음__builtin_popcount(라이브러리 호출 가능)

엣지 케이스: x == 0일 때 __builtin_ctz(0)와 __builtin_clz(0)는 결과가 정의되지 않는다. 그래서 ffs32는 0을 먼저 처리한다. lowest_set의 0u - x는 unsigned라 정의된 동작이다(-x를 signed로 쓰면 INT_MIN에서 overflow).

English answer: "Kernighan's trick clears the lowest set bit each iteration, so it's proportional to the number of ones; SWAR does it branch-free in a handful of ops. On Cortex-M3 and up I'd just use CLZ and RBIT through the builtins or CMSIS intrinsics, and I'd guard the zero input because ctz and clz of zero are undefined. FreeRTOS uses exactly this CLZ trick to pick the highest ready priority when the port-optimised task selection is enabled."

꼬리질문:

  • "RTOS에서 어디에 쓰나?" → FreeRTOS의 configUSE_PORT_OPTIMISED_TASK_SELECTION은 ready 우선순위를 bitmap으로 두고 CLZ로 최고 우선순위를 O(1)에 찾는다(대신 우선순위 32개 제한).
  • "32-bit보다 큰 bitmap에서 첫 free slot은?" → word 단위로 ~word != 0인 곳을 찾고 그 word 안에서 ctz. 2단 bitmap(summary word)을 두면 O(1)에 가까워진다.
  • "x가 2의 거듭제곱인지?" → x && !(x & (x - 1)). ring buffer 크기 검사와 정렬 검사에 쓴다.

Q07. A sensor sends little-endian 16- and 32-bit fields packed at odd offsets. Parse them safely on any CPU.#

왜 묻나: I2C/SPI 센서, BLE 패킷(little-endian), 네트워크(big-endian) 파싱에서 매일 만나는 문제다. 포인터 캐스트 *(uint32_t *)(buf + 1)로 푸는지(오답) 보는 게 핵심이다.

접근: 바이트를 하나씩 읽어 shift로 조립하면 host의 endian과 정렬에 무관하게 항상 정답이다. 성능이 필요하면 memcpy로 읽고 필요 시 byte swap한다. 컴파일러는 이 memcpy를 LDR 한 개로 줄인다(unaligned 접근을 지원하는 코어라면).

복잡도/메모리: O(1). -O2에서 get_le32는 Cortex-M4 같은 little-endian 코어에서 LDR 하나로, get_be32는 LDR + REV로 컴파일되는 경우가 많다.

엣지 케이스:

  • *(uint32_t *)(buf + 1)은 두 가지로 틀렸다: strict aliasing 위반(UB), 그리고 정렬 위반. Cortex-M3/M4/M7은 LDR/STR의 unaligned 접근을 하드웨어로 처리하지만(CCR.UNALIGN_TRP가 0일 때) LDM/STM/LDRD는 fault가 나고, 컴파일러가 두 접근을 LDRD로 합치면 터진다. Cortex-M0/M0+는 unaligned 접근이 항상 HardFault다.
  • p[1] << 8에서 uint8_t는 int로 승격된 뒤 shift된다. p[3] << 24는 p[3] >= 0x80이면 signed int overflow(UB)이므로 32-bit 조립은 먼저 (uint32_t)로 캐스트한다.
  • __attribute__((packed)) struct로 매핑하는 방법도 있지만 이식성이 떨어지고, packed 멤버의 주소를 다른 함수에 넘기면 정렬 가정이 깨진다.

English answer: "I never cast a byte pointer to a wider type: that's both a strict-aliasing violation and an alignment fault on Cortex-M0 or with LDRD on M4. I assemble the value from bytes with shifts, casting to uint32_t before shifting past 24 bits, which is correct regardless of host endianness. If it's hot, memcpy into a local and byte-swap; the compiler turns that into a single load plus REV."

꼬리질문:

  • "htonl을 직접 구현하면?" → host가 little-endian이면 bswap32, big-endian이면 그대로. __BYTE_ORDER__ == __ORDER_LITTLE_ENDIAN__(GCC/Clang 매크로)로 컴파일 타임 분기한다.
  • "센서의 12-bit 부호 있는 값(2의 보수)을 int16으로?" → (int16_t)(raw << 4) >> 4는 음수 right shift가 구현 정의라 피하고, (int16_t)((raw ^ 0x800) - 0x800)로 부호 확장한다.
  • "구조체를 그대로 UART로 보내면?" → padding, endian, 정렬 때문에 다른 CPU(SoC 쪽 Cortex-A)와 호환되지 않는다. 필드별 직렬화 함수를 쓴다.

3. 신호·상태머신#

Q08. Debounce a mechanical button sampled every 1 ms, and report press, release, and long-press events.#

왜 묻나: 웨어러블급 기기의 물리 버튼(전원, push-to-talk) 입력. 상태머신 설계 능력과 "인터럽트로 할까, 주기 폴링으로 할까"의 전력 트레이드오프를 본다.

문제: raw 입력은 수 ms 동안 튄다(스위치마다 다르고 길면 10~20 ms). 20 ms 연속 안정되면 상태를 확정한다. 1초 이상 누르면 long-press를 한 번만 보낸다.

접근: 4-state FSM. "후보" 상태에서 타이머가 찰 때까지 같은 값이 유지되어야 확정한다. 이벤트는 반환값으로 내보내고, FSM은 하드웨어를 모른다(테스트 가능).

복잡도/메모리: tick당 O(1), 버튼당 8 byte 정도.

엣지 케이스: 3 ms on/2 ms off로 튀는 입력은 이벤트를 내지 않는다(테스트로 확인). release 중 bounce는 PRESSED로 돌아가고 long-press는 다시 보내지 않는다. held는 포화시켜 65초 이상 눌러도 wrap하지 않는다.

English answer: "It's a four-state machine: released, maybe-pressed, pressed, maybe-released. A candidate state only commits after the input has been stable for the debounce window, so any bounce sends it back. Events come out as return values so the logic is hardware-independent and unit-testable. For power, I wouldn't poll at 1 kHz forever: I'd take a GPIO edge interrupt to wake, run the debounce with a timer only while the button is active, then go back to sleep."

꼬리질문:

  • "저전력으로 하려면?" → 평상시엔 GPIO edge 인터럽트(wake source)만 켜 두고, 첫 edge에서 인터럽트를 끄고 타이머로 debounce, 확정 후 다시 edge 인터럽트. 1 kHz SysTick을 계속 돌리면 tickless idle이 깨진다.
  • "하드웨어 debounce는?" → RC 필터 + 슈미트 트리거 입력. 일부 MCU는 GPIO에 디지털 glitch filter가 있다(벤더마다 다름).
  • "버튼 8개를 한 번에?" → 8-bit 병렬 debounce: 최근 N 샘플을 shift register로 두고, 모두 1이면 눌림, 모두 0이면 뗌. bitwise 연산으로 8개를 동시에 처리한다.

Q09. Implement a moving average and a first-order IIR low-pass filter in fixed point for a sensor or audio level meter. No floating point.#

왜 묻나: Cortex-M0+나 FPU를 꺼 둔 저전력 경로, 또는 오디오 샘플 처리에서 Q-format 산술은 기본기다. 오버플로, 반올림, 음수 shift를 아는지 본다. INT8 양자화 모델 입출력 스케일링과도 이어진다.

문제: (a) 16-tap moving average, 샘플당 O(1). (b) EMA y += alpha (x - y), alpha = 1/2^k. (c) Q15 곱셈(오디오 gain)을 반올림·포화 포함해서.

접근: (a)는 running sum에 들어오는 값을 더하고 나가는 값을 뺀다. (b)는 y를 2^k배 스케일한 누산기로 들고 있으면 매 샘플 반올림 오차가 버려지지 않고 누산기에 남아, 정상 상태에서 입력값에 정확히 수렴한다. (c)는 Q15 x Q15 = Q30이므로 반올림 상수를 더하고 15 shift, 그리고 -1 x -1 = +1이 Q15로 표현 불가하니 포화.

복잡도/메모리: (a) 샘플당 덧셈 2, 나눗셈 1(MA_LEN이 상수 2의 거듭제곱이고 warm-up 이후라면 shift로 바꿀 수 있음), 메모리 32 B + 12 B. (b) 샘플당 shift 2, 덧셈 2, 메모리 8 B. (c) 곱셈 1.

엣지 케이스:

  • sum 폭: 16개 x 32767 = 약 2^19라 int32로 충분하다. 1024-tap이면 2^25로 여전히 괜찮지만 32-bit 누산 한계를 매번 계산해서 말한다.
  • 음수의 >>는 C에서 구현 정의다. ARM GCC/Clang은 산술 shift(ASR)를 쓰지만, 이식성을 요구하면 나눗셈을 쓰거나 주석으로 가정을 명시한다. 나눗셈(/)은 0 쪽으로 버림, ASR은 음의 무한대 쪽으로 버림이라 결과가 1 LSB 다르다.
  • EMA의 k가 크면 initial x 2^k가 int32를 넘지 않는지 확인(int16 x 2^15까지 안전).
  • INT16_MIN x INT16_MIN은 테스트로 포화를 확인했다.

English answer: "The moving average keeps a running sum, adding the new sample and subtracting the one falling out of the window, so it's O(1) per sample and I size the accumulator for N times full scale. For the IIR I use alpha equal to one over two to the k so it's shifts only, and I keep the state scaled by two to the k so the rounding error stays in the accumulator instead of biasing the output. Q15 multiply is a 32-bit product, add half an LSB, shift by 15, and saturate the minus-one times minus-one case. On an M4 I'd use the DSP instructions or CMSIS-DSP instead of hand-rolling."

꼬리질문:

  • "EMA의 cutoff는?" → 시정수가 약 2^k 샘플이다. alpha가 작을 때 차단 주파수는 대략 fs x alpha / (2 pi).
  • "M4에서 더 빠르게?" → SSAT/QADD 같은 포화 명령과 SMLAD(16-bit 두 쌍 곱셈 누산). CMSIS에는 __SSAT(), CMSIS-DSP에는 arm_mult_q15(), arm_biquad_cascade_df1_q15()가 있다.
  • "float을 쓰면 안 되나?" → M4F/M33에 single-precision FPU가 있으면 float도 좋다. 다만 ISR에서 FPU를 쓰면 lazy stacking으로 컨텍스트가 커지고, FPU 켜 둔 상태의 전력도 고려한다.

4. 통신·무결성#

Q10. Implement CRC-16/CCITT bitwise, then make it table-driven. What's the check value?#

왜 묻나: factory test 프로토콜, calibration 레코드, SoC–MCU 패킷, 부트로더 이미지 헤더에 전부 CRC가 붙는다. 파라미터(poly, init, reflect, xorout)를 구분해서 말하는지 본다. CRC-16/CCITT라는 이름 하나로 여러 변형이 있다.

문제: CRC-16/CCITT-FALSE(poly 0x1021, init 0xFFFF, 입력·출력 반사 없음, xorout 0). 스트리밍(여러 번 나눠 호출) 가능해야 한다.

접근: MSB-first 시프트 레지스터. 바이트를 상위 8 bit에 XOR하고, 8번 "MSB가 1이면 shift 후 poly XOR". 테이블 버전은 이 8번 루프 결과를 256개 미리 계산해 두고 바이트당 한 번 lookup한다.

복잡도/메모리:

방식바이트당 연산코드/데이터쓸 곳
bitwise8 루프(shift, 분기, XOR)테이블 0 B부트로더, 작은 패킷
256-entry tablelookup 1 + shift/XOR512 B(const면 flash)대량 데이터, 이미지 검증
16-entry nibble tablelookup 232 B절충
하드웨어 CRC 유닛거의 0 CPU없음많은 MCU에 있음(벤더마다 설정 다름)

엣지 케이스: 표준 check 값은 문자열 "123456789"에 대해 0x29B1이다(테스트로 확인). 같은 poly로 init 0이면 CRC-16/XMODEM(check 0x31C3)이다. 데이터 뒤에 CRC를 big-endian으로 붙여 전체를 다시 CRC하면 0이 나온다(xorout 0, 비반사 변형의 성질). 길이 0이면 init 그대로. 테이블은 부팅 시 생성하면 RAM 512 B, const로 미리 계산해 두면 flash 512 B다.

English answer: "CRC-16/CCITT-FALSE is polynomial 0x1021, init 0xFFFF, no reflection, no final XOR, and the check value for the ASCII string one through nine is 0x29B1; I always quote the full parameter set because XMODEM uses the same polynomial with init zero. The bitwise version shifts eight times per byte; the table version precomputes those eight steps for all 256 byte values and trades 512 bytes for about eight times fewer operations. If the MCU has a CRC peripheral I'd use that, and verify it against the software version with the check string."

꼬리질문:

  • "CRC가 잡는 것과 못 잡는 것은?" → 모든 단일 bit 에러, 홀수 개 bit 에러(0x1021 다항식이 (x+1) 인수를 가짐), 일정 길이 이하 메시지의 모든 이중 bit 에러, 16 bit 이하 burst 에러를 잡는다. 의도적 변조는 못 막는다. OTA 이미지의 무결성 + 진위는 SHA-256 + 서명(ECDSA P-256 등)이 필요하다.
  • "CRC-32와 언제 바꾸나?" → 데이터가 길수록(수 KB 이상) 16-bit CRC의 미검출 확률 2^-16이 부족하다. flash 이미지, 큰 calibration blob은 CRC-32.
  • "reflected CRC 테이블은?" → LSB-first라 shift 방향이 반대이고 poly도 반사(0x1021 → 0x8408)한다.

Q11. Write a byte-at-a-time parser for a UART framed protocol with start byte, length, command, payload, and CRC. It must resynchronize after garbage and time out on partial frames.#

왜 묻나: factory test 명령 채널, SoC–MCU 사이 UART IPC, BLE HCI UART transport가 모두 이런 프레이밍이다. Don의 factory test-node 경험과 가장 직접 연결되는 코딩 문제다. 면접관은 상태머신, 길이 검증(버퍼 overflow 방지), 재동기화, 타임아웃을 본다.

문제: 프레임 | 0xA5 | LEN | CMD | PAYLOAD[LEN] | CRC_H | CRC_L |. CRC는 LEN부터 PAYLOAD까지 CRC-16/CCITT-FALSE. LEN 최대 64. 바이트 사이가 50 ms를 넘으면 프레임 폐기. RX ISR이 링버퍼(Q01)에 넣고 task가 한 바이트씩 parser_feed를 부른다고 가정.

복잡도/메모리: 바이트당 O(1)(CRC 8 루프). 파서 상태 약 90 B. 버퍼 복사 없음.

엣지 케이스:

  • LEN 검증이 없으면 payload[pos++]가 overflow한다. 공격자/노이즈가 LEN=255를 보내는 게 첫 테스트 케이스다.
  • payload 안에 0xA5가 들어 있어도 길이 기반이라 문제없다(테스트로 확인). 대신 CRC 실패 후에는 이미 지나간 바이트 속의 진짜 SOF를 놓칠 수 있다. 그래서 타임아웃이나 다음 프레임에서 재동기화된다.
  • LEN=0 프레임(명령만)은 PAYLOAD 상태를 건너뛴다.
  • 에러 카운터는 공장 라인에서 "케이블 불량 vs FW 버그"를 구분하는 핵심 데이터다.
  • now_ms 비교는 unsigned 뺄셈이라 49.7일 wrap에도 안전하다.

English answer: "It's a state machine fed one byte at a time from the RX ring buffer: hunt for the start byte, read and validate the length before touching the payload buffer, accumulate the CRC incrementally, and compare at the end. Any timeout between bytes, over-length field, or CRC mismatch drops back to hunting and bumps a counter. The length check is what prevents a buffer overflow from a corrupted frame, and the counters are what let the factory tell a bad cable from a firmware bug."

꼬리질문:

  • "payload에 SOF가 나오면 재동기화가 어렵지 않나?" → 더 강한 방법은 COBS 또는 SLIP처럼 바이트 스터핑으로 구분자가 payload에 절대 안 나오게 하는 것이다. 그러면 구분자 = 프레임 경계가 보장된다.
  • "ACK/재전송은?" → 헤더에 sequence 번호를 넣고, 수신 측이 seq와 결과 코드로 ACK, 송신 측은 타임아웃 후 재전송하며 수신 측은 같은 seq를 중복 실행하지 않는다.
  • "DMA로 받으면?" → UART RX DMA를 circular로 돌리고 idle line 인터럽트(벤더마다 다름)에서 DMA 쓰기 위치까지를 파서에 먹인다. 바이트마다 인터럽트가 없어 전력과 CPU가 준다.

Don 스토리 연결: Apple factory test-node 아키텍처에서 테스트 스테이션–DUT 명령 채널을 설계한 경험. "에러 카운터와 타임아웃을 프로토콜에 넣어 라인에서 재현 안 되는 실패를 분류했다" 식으로 연결한다.

Q12. Build a command dispatcher for a factory test shell: parse a line like "led 2 on" and call the right handler from a table.#

왜 묻나: JD의 "factory test & calibration firmware"가 실제로는 이런 셸이다. 함수 포인터 테이블, 문자열 토큰화, 인자 검증, 그리고 테이블을 flash에 두는 것(const)을 본다.

접근: { name, handler, min_args, help } 구조체 배열을 const로 둔다. 입력 줄을 제자리에서 토큰화(구분자를 '\0'으로 바꾸고 argv에 포인터 저장)하고, 이름으로 선형 탐색해 argc 검사 후 호출한다. 핸들러는 숫자를 strtol로 파싱하고 끝 문자까지 검사한다.

복잡도/메모리: 명령 탐색 O(명령 수 x 이름 길이). 명령이 수십 개면 충분하다. 수백 개면 이름으로 정렬해 bsearch(). 테이블은 .rodata(flash), 스택은 argv[8] 포인터 32 B(32-bit).

엣지 케이스: 빈 줄, 공백만 있는 줄, \r\n, 인자 과다(argv overflow 방지로 -1), 인자 부족, strtol의 부분 파싱("2x"), 범위 밖 인덱스. 0x 접두사는 strtol(..., 0)로 허용했다. strtok는 내부 static 상태를 써서 재진입이 안 되므로 직접 토큰화했다.

English answer: "The command table is a const array of name, handler, minimum argument count, and help string, so it lives in flash and adding a command is one line. I tokenize the line in place into argc and argv without strtok, look up the name, validate the argument count centrally, and let each handler validate its own values with strtol, checking the end pointer. Every command returns a numeric status so the test station can parse results without scraping text."

꼬리질문:

  • "명령을 여러 모듈이 등록하게 하려면?" → 링커 섹션 트릭: 각 모듈이 __attribute__((section(".cmds"), used))로 엔트리를 두고, 링커 스크립트가 시작/끝 심볼을 만든다. Zephyr의 SHELL_CMD_REGISTER()가 이 방식이다. FreeRTOS에는 FreeRTOS+CLI의 FreeRTOS_CLIRegisterCommand()가 있다.
  • "양산 출하 후 이 셸은?" → 출하 전 잠금: provisioning 완료 플래그(OTP 등)가 서면 셸을 비활성화하거나, 인증(challenge-response) 뒤에만 열리게 한다. 디버그 포트 잠금과 함께 말한다.
  • "사람이 아니라 테스트 스테이션이 쓴다면?" → 텍스트보다 Q11 같은 바이너리 프레임 + 결과 코드가 파싱이 확실하고 빠르다. 두 모드를 둘 수 있다.

Q13. Implement a software timer service: start one-shot or periodic timers, stop them, and fire callbacks from a 1 ms tick. Handle tick counter wraparound.#

왜 묻나: RTOS의 software timer(FreeRTOS timer service task, Zephyr k_timer)가 내부적으로 하는 일이다. 연결 리스트 조작, wrap-safe 시간 비교, 주기 타이머 drift를 본다.

접근: 만료 시각 순으로 정렬된 단일 연결 리스트. tick에서는 head만 보면 되므로 만료되지 않은 tick은 O(1)이다. 시간 비교는 (int32_t)(a - b) <= 0로 해서 32-bit tick 카운터가 넘어가도 맞다. 주기 타이머는 expiry += period(now가 아니라 이전 만료 기준)로 누적 drift를 없앤다. 삽입·삭제는 pointer-to-pointer로 head 특수 케이스를 없앤다.

복잡도/메모리: tick O(1)(만료 없을 때), 만료된 타이머당 삽입 O(n). start/stop O(n). 타이머 구조체는 호출자가 소유(정적 할당), 서비스 쪽 추가 메모리 없음.

엣지 케이스: 시작값 0xFFFFFFF0에서 wrap을 넘기는 테스트를 통과했다. 비교는 두 시각 차이가 2^31 tick(1 ms tick이면 약 24.8일) 미만이라는 가정이다. 이미 동작 중인 타이머를 다시 start하면 먼저 빼고 넣는다(중복 삽입으로 리스트 순환이 생기는 버그 방지). 콜백 안에서 자기 자신을 stop/start해도, 콜백 호출 전에 리스트를 정리해 두었으므로 일관된다.

English answer: "I keep active timers in a list sorted by absolute expiry, so each tick only checks the head. Times are compared with a signed difference so the 32-bit tick counter can wrap safely, as long as timeouts are under two to the thirty-one ticks. Periodic timers reschedule from their previous expiry, not from now, so they don't drift. I'd run the callbacks in a task rather than the SysTick ISR, the same way FreeRTOS uses a timer service task, so callbacks can block briefly and the list doesn't need interrupt locking."

꼬리질문:

  • "타이머가 수천 개면?" → hashed timing wheel: 슬롯 배열에 expiry % N으로 넣고 tick마다 한 슬롯만 본다. 삽입 O(1). Linux 커널 타이머가 계층형 wheel을 쓴다.
  • "tickless idle과 어떻게 맞추나?" → head의 expiry까지 남은 시간을 계산해 저전력 타이머(RTC 등)를 그 시각에 맞추고 잠든다. 깨어나면 지난 tick 수만큼 시간을 한 번에 진행한다. 정렬 리스트는 "다음 만료"를 O(1)에 주므로 tickless에 유리하다.
  • "ISR에서 timer_start를 부르면?" → 리스트를 task와 공유하므로 경쟁이 생긴다. FreeRTOS처럼 명령 queue로 timer task에 요청을 보내거나(xTimerStartFromISR()), critical section으로 보호한다.

Q14. Store factory calibration data in flash so that a power loss during an update never leaves the device uncalibrated. Show the record format and the load/save logic.#

왜 묻나: JD의 factory calibration, OTA, 그리고 "전원 차단 안전성"이 한 문제에 다 들어 있다. A/B 이미지 OTA와 같은 원리(두 벌 + 버전 + 무결성 검사 + 마지막에 commit)를 작은 규모로 설명할 수 있는지 본다. SSD FW 출신에게 특히 유리한 질문이다.

문제: 마이크 gain, IMU offset, 배터리 용량 같은 cal 값. flash sector 두 개(slot A/B). 레이아웃이 나중에 바뀔 수 있다. 부팅 시 가장 최신의 유효한 레코드를 읽고, 둘 다 무효면 기본값 + "uncalibrated" 상태로 부팅.

접근: 레코드에 magic, 레이아웃 version, size, 단조 증가 seq, 끝에 CRC-32. 저장은 항상 "현재 유효본이 아닌" slot에 한다. flash에서는 erase → 본문 program → CRC를 마지막에 program해서 CRC가 commit 역할을 한다. 로드는 두 slot을 검증하고 seq가 최신인 쪽(wrap-safe 비교)을 고른다.

복잡도/메모리: 로드 = CRC 두 번(레코드 크기에 비례). RAM은 레코드 한 개. flash는 2 sector.

엣지 케이스:

  • 지워진 flash는 보통 0xFF로 읽힌다. magic 검사로 걸러진다(테스트: 초기 0xFF 상태에서 load 실패).
  • 한 slot이 손상되면 다른 slot으로 fallback하고, 다음 저장은 손상된 쪽에 쓴다(테스트로 확인).
  • seq는 0xFFFFFFFF → 0 wrap에도 signed 차이 비교로 최신을 고른다(테스트로 확인).
  • CRC 범위는 offsetof(cal_record_t, crc)까지라 struct padding도 포함된다. padding 값이 불확정이면 CRC가 흔들리므로 저장 전 구조체를 memset으로 0 초기화하거나 padding이 없게 필드를 배치한다(이 레이아웃은 padding 없음: 4+2+2+4+8+6+2 = 28, crc 오프셋 28).
  • version이 다르면 무효 처리했지만, 실제 제품에서는 구 버전 레코드를 읽어 새 레이아웃으로 migration해야 한다. cal 데이터는 공장에서만 만들 수 있어 버리면 안 된다.

English answer: "I keep two copies in separate flash sectors, each with a magic, a layout version, a sequence number, and a CRC-32 at the end. A save always goes to the slot that isn't the current valid one: erase, program the body, and program the CRC last so the CRC acts as the commit record. On boot I validate both and take the valid one with the newer sequence number, using a signed difference so the counter can wrap. A power cut at any point leaves at least the previous record intact, which is the same principle as A/B firmware updates."

꼬리질문:

  • "flash가 아니라 OTP에 넣으면?" → OTP는 한 번만 쓰므로 공장 cal의 원본(골든 카피)이나 키 해시에 쓰고, 현장에서 바뀌는 값(배터리 학습값 등)은 flash에 둔다.
  • "보안은?" → CRC는 변조를 못 막는다. 기기 인증서·키는 secure element나 보호 파티션에 두고, cal 데이터도 변조가 문제라면 MAC/서명을 붙인다.
  • "SoC와 MCU가 같은 cal 데이터를 써야 하면?" → 한쪽(보통 MCU 또는 SoC의 보호 파티션)을 소유자로 정하고 부팅 시 IPC로 전달하며, version과 CRC를 같이 보내 불일치를 감지한다.

Don 스토리 연결: SSD FW에서 FTL 메타데이터·로그를 전원 차단(sudden power loss)에 안전하게 쓰던 경험이 그대로 적용된다. "SPOR 테스트 문화"를 말하면 설득력이 크다.
