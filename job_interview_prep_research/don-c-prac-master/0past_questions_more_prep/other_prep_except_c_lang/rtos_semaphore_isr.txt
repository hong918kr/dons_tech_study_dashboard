실전 면접 대비 RTOS/세마포어/ISR 문제 세트
다음은 C 언어를 사용하며 Ubuntu 22.04 환경(사실상 bare-metal 가정, 필요시 pthread 활용 가능)을 전제로 한 RTOS 스케줄링, 세마포어/동기화 객체, 인터럽트/ISR 관련 문제들입니다. 각 문제는 구현과 시나리오 분석 유형을 혼합하였고, 면접에서 자주 언급되는 개념들을 포함하고 있습니다. 문제당 약 30분 이내에 해결 가능한 난이도로 구성하였으며, 각 문제에는 문제 설명, 요구사항 및 제약 조건, 함수 시그니처 템플릿이 제공됩니다.



고정 우선순위 스케줄러 미니 구현


    문제 설명: 우선순위 기반의 프리엠프티브 스케줄러를 단순 모형으로 구현하는 문제입니다. 
    여러 개의 태스크(Task)가 정적 우선순위를 가지고 실행되며, 가장 높은 우선순위의 준비 완료(ready) 상태 태스크가 언제나 CPU를 차지합니다. 
    동일 우선순위 내에서는 라운드 로빈(time slice) 방식으로 일정 시간(tick)마다 실행권을 교대로 넘겨줍니다.


요구사항 및 제약 조건:

    Ready 비트맵을 이용하여 현재 실행 가능(ready)한 태스크들 중 최우선 순위 태스크를 O(1) 시간에 찾아낼 것[1]. 
    (예: 우선순위 0이 최고, 숫자가 클수록 낮은 우선순위일 때, 비트셋이나 배열로 비어있지 않은 최고 우선순위 큐를 빠르게 찾기)
    태스크를 우선순위별 대기 큐로 관리하고, 각 우선순위별로 다수의 태스크가 있을 수 있음[1]. 
    동일 우선순위에서는 한 태스크가 정해진 시간 조각을 소비하면 다음 태스크로 교체(round-robin)되도록 타임슬라이스를 구현할 것.

    태스크 추가, 종료, 또는 블록/웨이크업 시 스케줄러가 즉시 우선순위 재평가를 하여 선점 발생 여부를 판단해야 합니다. 
    (예: 낮은 우선순위 태스크 실행 중 높은 우선순위 태스크가 ready 상태가 되면 즉시 컨텍스트 스위치)

(선택 요구사항) 우선순위 역전(Priority Inversion) 대응: 
    우선순위가 낮은 태스크가 높은 태스크가 필요한 리소스를 점유하여 발생하는 역전 현상을 완화하기 위해 우선순위 상속(priority inheritance) 메커니즘을 고려합니다[1].
    이는 선택사항으로, 구현한다면 뮤텍스 획득 시 리소스를 점유한 태스크의 우선순위를 일시 상향 조정하는 방식을 모형화합니다.
    시스템은 단일 프로세서 환경으로 가정하며, 태스크 스케줄링 간 인터럽트에 의한 간섭은 없음(tick 타이머 인터럽트만 고려). 
    구현 시 실제 컨텍스트 스위치는 하지 않고, 다음 실행할 태스크를 선정하는 로직을 중심으로 합니다.




함수 시그니처 템플릿: (아래는 스케줄러의 핵심 자료구조와 함수를 설계하기 위한 템플릿입니다.)


#define MAX_PRIORITY    32
#define MAX_TASKS       128

typedef struct {
    int id;
    int priority;
    // ... (필요 시 상태, 사용 CPU 시간, etc.)
} Task;

// 우선순위별 준비 큐 (각 큐에 task ID 저장), 및 ready 비트맵
static int ready_queues[MAX_PRIORITY][MAX_TASKS];
static int queue_head[MAX_PRIORITY], queue_tail[MAX_PRIORITY];
static unsigned int ready_bitmap;

// 스케줄러 초기화
void scheduler_init(void);

// 새로운 태스크 추가 (주어진 우선순위로 ready 상태 진입)
void add_task(int task_id, int priority);

// 태스크가 블록되거나 종료하여 ready 상태를 떠남
void remove_task(int task_id, int priority);

// 주기적 타이머 tick 호출 – 타임슬라이스 관리 및 우선순위 스케줄링 결정
void scheduler_tick(void);

// 실행 가능한 태스크 중 최고 우선순위 태스크 선택
int schedule_next(void);








카운팅 세마포어 구현 및 ISR 연계


문제 설명:
    카운팅 세마포어(counting semaphore)를 구현하고, 이를 인터럽트 서비스 루틴(ISR)과 태스크 간 동기화에 사용하는 문제입니다. 
    세마포어는 특정 리소스의 사용 가능 개수를 나타내며, ISR에서 세마포어 신호를 주어(task에게) 이벤트를 알리고, 
    태스크는 세마포어를 기다려 ISR이 발생한 이벤트를 처리하는 시나리오를 가정합니다. 
    예를 들어, ISR이 센서 데이터 수신을 감지하면 세마포어를 give하여 데이터 처리 태스크를 깨우는 방식입니다.

요구사항 및 제약 조건:


세마포어 구조체를 정의하고 초기화, wait(pend) 및 signal(post) 연산을 구현합니다.
이 때 세마포어의 초기 카운트를 설정할 수 있어야 하며, 카운트 값은 사용 가능한 리소스 개수 혹은 대기 중인 이벤트 개수를 나타냅니다.
wait 연산은 세마포어 카운트가 0이면 호출한 태스크를 블록 처리해야 합니다. 
실제 RTOS에서는 해당 태스크를 세마포어의 대기 큐에 넣고 스케줄러를 통해 다른 태스크를 실행합니다.
(본 구현에서는 시간 제한 대기 기능도 요구됩니다: wait에 타임아웃(ms) 인자를 추가하여, 주어진 시간 내에 세마포어가 가용해지지 않으면 실패/타임아웃을 리턴합니다[2].)

signal 연산은 세마포어 카운트를 증가시키고, 대기 중인 태스크가 있으면 하나를 깨워 ready 상태로 전환시킵니다. 
일반 태스크 문맥에서 signal을 호출할 경우 스케줄러를 적절히 호출하여 높은 우선순위 대기 태스크가 즉시 실행될 수 있도록 합니다.
ISR context에서 signal 가능: ISR은 블로킹을 할 수 없으므로 세마포어를 줄 때 별도의 함수를 사용하거나 특별 처리해야 합니다

 (예: semaphore_give_from_ISR). 
ISR에서 세마포어 신호를 주면 해당 세마포어를 기다리는 태스크를 깨우기만 하고 바로 리턴합니다.
ISR 내부에서는 절대로 블로킹 연산을 해서는 안 되므로, wait는 ISR 내부에서 사용하지 않는 것이 원칙입니다 (ISR에서는 세마포어를 획득하지 않음).


멀티스레드 환경에서 세마포어 카운트 증감과 대기 큐 조작은 원자적이어야 합니다. 
실제 RTOS에서는 이를 위해 인터럽트를 일시 비활성화하거나 원자적 연산을 사용합니다. 
본 구현에서는 필요한 경우 임계 구역을 설정해주어야 합니다.
환경은 단일 프로세서 RTOS 가정이며, 구현 검증을 위해 pthread 등으로 ISR과 태스크를 시뮬레이트할 수 있습니다. 
예를 들어, 하나의 스레드를 ISR 역할로 사용하여 주기적으로 세마포어를 signal하고, 다른 스레드가 wait으로 이벤트를 기다리는 식으로 테스트 가능합니다.
함수 시그니처 템플릿:


typedef struct {
    volatile int count;
    // 대기 중인 태스크를 관리할 자료구조 (예: 대기 태스크ID 큐 등)
    // ... (필요 시 조건변수 또는 이벤트 플래그 등을 사용할 수도 있음)
} Semaphore;

// 세마포어 초기화 (초기 카운트 값 설정)
void sem_init(Semaphore *sem, int initial_count);

// 세마포어 획득 (count 감소, 필요 시 블록; timeout(ms) 후 실패 시 -1 리턴, 성공 시 0)
int sem_wait_timeout(Semaphore *sem, unsigned int timeout_ms);

// 세마포어 반환 (count 증가, 대기 태스크 깨움)
void sem_signal(Semaphore *sem);

// (ISR 전용) 세마포어 반환 -- ISR 컨텍스트에서 호출, non-blocking
void sem_signal_from_ISR(Semaphore *sem);


우선순위 역전 시나리오 분석 및 해결
문제 설명: 우선순위 역전(priority inversion) 현상의 발생 시나리오를 이해하고 해결책을 제시하는 문제입니다. 우선순위 역전이란 낮은 우선순위의 태스크가 공유 자원을 점유한 상태에서 높은 우선순위 태스크가 그 자원을 기다리다가, 중간 우선순위 태스크들 때문에 실행되지 못하는 상황을 말합니다[3]. 이 문제는 실시간 시스템의 응답 지연을 초래할 수 있으며, 1997년 Mars Pathfinder 소프트웨어 오류로도 유명한 개념입니다.
요구사항 및 제약 조건:
다음 시나리오를 고려합니다: 세 개의 태스크 L, M, H가 있으며, 우선순위는 H > M > L 입니다. L 태스크가 리소스(예: 뮤텍스)를 획득하여 사용 중이고, 이후 H 태스크가 해당 리소스를 요청하여 블록됩니다. 그 동안 M 태스크가 수행되면서 L의 리소스 해제가 지연되어 H 태스크가 장시간 블록 상태로 있는 상황이 발생합니다. 이 시나리오에서 어떤 일이 일어나며 그것이 왜 문제가 되는지 서술하십시오.
우선순위 역전 문제를 완화하거나 해결하는 방법을 두 가지 이상 제시하십시오. 예를 들어, 우선순위 상속 (Priority Inheritance)이나 우선순위 천장 (Priority Ceiling) 프로토콜 적용, 또는 시스템 설계 단계에서 공유자원 사용 최소화 등이 있습니다[1][4]. 각 방법에 대해 개략적으로 원리를 설명하십시오. 특히 우선순위 상속의 경우, L 같은 낮은 태스크가 높은 태스크(H)에게 리소스를 제공하기 전까지 일시적으로 H의 우선순위를 상속받아 실행 우선권을 높이는 방식을 설명합니다.
(심화) 우선순위 상속을 스케줄러/뮤텍스에 구현하려면 필요한 자료구조와 알고리즘을 간략히 설계해보십시오. 예를 들어 뮤텍스 구조체에 현재 소유자 태스크의 우선순위 정보를 저장하고 대기 중인 최고 우선순위 태스크를 추적하여, 뮤텍스를 가진 태스크의 우선순위를 동적으로 조정하는 로직을 제시할 수 있습니다. 이때 체인 발생(여러 단계의 우선순위 역전)에도 대응해야 함을 언급합니다.
이 문제는 시나리오 분석 중심으로, 코드 구현보다는 개념 설명과 설계 방안을 요구합니다. 면접에서는 이 시나리오에 대해 구체적으로 묻고 해결 능력을 평가할 수 있으므로, 답변 시 실제 사례나 RTOS에서 어떻게 이 문제를 다루는지 함께 언급하면 좋습니다. (예: “일부 RTOS의 mutex는 우선순위 상속을 기본 제공하여 priority inversion을 완화한다” 등[5])
함수 시그니처 템플릿: (우선순위 상속이 적용된 뮤텍스의 구조 및 인터페이스 예시)


typedef struct {
    int owner_task_id;      // 뮤텍스 현재 소유 태스크 ID (없으면 -1)
    int owner_orig_prio;    // 뮤텍스 소유자의 원래 우선순위
    // 대기 중인 태스크들의 우선순위 목록/큐
    // ...
} PriorityInheritMutex;

// Priority Inheritance 지원 뮤텍스 초기화
void pi_mutex_init(PriorityInheritMutex *mtx);

// 뮤텍스 락 획득 (필요시 우선순위 상속 처리)
void pi_mutex_lock(PriorityInheritMutex *mtx);

// 뮤텍스 락 해제 (우선순위 원복 등 처리)
void pi_mutex_unlock(PriorityInheritMutex *mtx);
인터럽트 후반부 처리(Deferred Work) 큐 구현
문제 설명: 인터럽트 서비스 루틴(ISR)은 가능한 한 신속하게 필수 작업만 처리하고 종료해야 하며, 시간이 오래 걸리는 작업이나 블로킹이 필요한 작업은 추후 처리(deferred work)로 미뤄야 합니다[6]. 이를 위해 흔히 보텀 하프(bottom half) 또는 DPC(Deferred Procedure Call) 메커니즘을 사용합니다[7]. 이 문제에서는 ISR에서 후반부 작업을 요청하면, 별도의 높은 우선순위 작업이 그 요청들을 순차 또는 우선순위별로 처리하는 큐(queue)를 구현합니다.
요구사항 및 제약 조건:
ISR 내에서 호출할 수 있는 함수를 통해 지연 작업을 큐잉할 수 있어야 합니다. 예를 들어 defer_work(handler, arg, priority) 형태로, 수행해야 할 함수를 함수 포인터와 인자로 등록합니다. 이 호출은 ISR 컨텍스트에서 non-blocking으로 즉시 리턴해야 하며, 큐에 작업을 넣는 동안 필요한 최소한의 시간만 소모해야 합니다.
등록된 작업들은 우선순위 기반으로 정렬되거나 별도의 우선순위 큐를 가질 수 있습니다[8]. 높은 우선순위의 지연 작업이 먼저 처리되도록 설계합니다. (단, 구현을 단순화하기 위해 FIFO 순서로 처리하되, 작업마다 우선순위 필드를 두고 중요한 작업 여부를 로그 정도는 할 수 있습니다.)
후반부 처리 담당 태스크를 가정합니다. 이 태스크는 (일반적으로 다른 태스크보다 높은 우선순위로) 대기하다가 ISR이 큐에 작업을 넣으면 깨어나서 해당 작업을 수행합니다. 모든 지연 작업을 처리하면 다시 잠들거나 대기합니다. 구현에서는 별도의 스레드를 생성하여 대기-처리-반복하도록 할 수 있습니다.
큐의 자료구조는 고정 크기 원형 버퍼(ring buffer) 등을 사용할 수 있으며, 다중 생산자(여러 ISR) - 단일 소비자(후반부 태스크) 시나리오를 고려해 설계합니다. 원자적 조작 또는 인터럽트 마스킹으로 큐 상태를 보호해야 데이터 손실이나 손상이 없습니다.
(선택 요구사항) 처리해야 할 작업이 일정 시간 내에 수행되지 못하면(예: 큐에 계속 남아 있음) 경고를 출력하거나 드롭하는 등의 예외 처리도 고려합니다. 이는 시스템 안정성을 위한 것으로, 실시간 성능을 해치지 않도록 후반부 작업이 밀리지 않게 모니터링합니다.
함수 시그니처 템플릿:


#define MAX_DEFERRED_WORK  16

typedef void (*DeferredHandler)(void *arg);

// 지연 작업 큐 요소 정의
typedef struct {
    DeferredHandler handler;
    void *arg;
    int priority;
} DeferredWorkItem;

// 지연 작업 큐 구조체
typedef struct {
    DeferredWorkItem buffer[MAX_DEFERRED_WORK];
    int head;
    int tail;
    int count;
} DeferredQueue;

// 지연 작업 큐 초기화
void dq_init(DeferredQueue *dq);

// ISR 등에서 호출: 작업 큐잉 (성공 시 0, 큐 풀 경우 -1 등)
int defer_work(DeferredQueue *dq, DeferredHandler handler, void *arg, int priority);

// 후반부 처리 태스크가 주기적으로 호출: 대기 중인 작업 처리
void process_deferred_work(DeferredQueue *dq);
각 문제는 면접 상황에서 실무적으로 유의미한 주제를 다루며, 직접 코드를 구현하거나 시나리오를 분석하면서 학습 효과를 높이도록 설계되었습니다. 또한 제시된 템플릿을 활용하면 바로 구현을 시작하고 테스트할 수 있어, 답안 검증 및 실습이 용이합니다.
