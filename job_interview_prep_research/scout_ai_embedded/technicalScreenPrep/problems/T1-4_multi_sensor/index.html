T1-4 · Multi-Sensor Overheat

IDT1-4
PriorityP1
Patternarray of per-item state machines + input validation
Time30 min

파일: stub.c(여기서 풀기) · solution.c(정답) · 실행: ./run.sh T1-4 / ./run.sh T1-4 sol

1. Problem

A robot has up to MAX_SENSORS = 16 temperature sensors. Their readings arrive interleaved in one array, in arrival order. Each reading has a sensor id, a timestamp in ms, and a temperature in tenths of a degree Celsius.

Run an independent overheat detector for every sensor, with the same rules as T1-2:

  • NORMAL → OVERHEATED after N_CONFIRM = 3 consecutive readings >= HIGH_C10 (850) from that sensor. Emit an Alert {id, t_ms} on that reading.
  • OVERHEATED → NORMAL after 3 consecutive readings <= LOW_C10 (800) from that sensor (no alert). A reading that breaks the streak resets that sensor's counter.
  • Alerts are returned in input order.

Bad input:

  • id >= MAX_SENSORS → ignore the reading and count it in *dropped.
  • A reading whose t_ms is not after the previous accepted reading of the same sensor (older or equal; compare wrap-safe) → ignore it and count it in *dropped. It must not change the streak.

Write at most out_cap alerts into out but always return the total number of alerts. out may be NULL when out_cap == 0; dropped may be NULL. No malloc.

#define MAX_SENSORS 16
#define HIGH_C10    850
#define LOW_C10     800
#define N_CONFIRM   3
typedef struct { uint8_t id; uint32_t t_ms; int16_t temp_c10; } Reading;
typedef struct { uint8_t id; uint32_t t_ms; } Alert;

size_t process(const Reading *r, size_t n, Alert *out, size_t out_cap, size_t *dropped);

Example

(id, t_ms, temp):
(0,0,860) (1,0,700) (2,0,900)
(0,100,870) (1,100,900) (2,100,700)
(0,200,880) (1,200,910) (20,200,999) (2,200,900)
(1,300,920) (0,300,890) (2,300,900)
(1,250,950)                     <- older than sensor 1's last reading (300)
(2,400,900)

return 3, out = {0,200} {1,300} {2,400}, dropped = 2 (id 20, and sensor 1 at t=250)

Constraints

  • 0 <= n <= 1,000,000. Timestamps are uint32_t ms and may wrap around 2^32.
  • The array is in arrival order; different sensors' timestamps may interleave arbitrarily.

Clarifying questions to ask (first 3 minutes)

  1. Are the detectors independent per sensor, with the same thresholds for all sensors?
  2. What should happen to an id outside the valid range — ignore, count, or fail?
  3. Is "time order" per sensor or global? What do we do with a stale or duplicate timestamp?
  4. Should alerts be ordered by input order or sorted by timestamp?
  5. Do I report only the overheat start, or recovery events too?

    Alert one[2] = { {0, 0}, {0xEE, 0xDEAD} };

    CHECK(process(a, sizeof a / sizeof a[0], NULL, 0, NULL) == 3);

    /* 6. timestamps wrap around 2^32 and are still "newer" */
    const Reading d[] = { {7,0xFFFFFF00u,900}, {7,0xFFFFFFF0u,900}, {7,0x10u,900} };

    const Reading e[] = { {15,0,900}, {16,0,900}, {15,1,900}, {16,1,900}, {15,2,900}, {16,2,900} };

3. 힌트 (막힐 때 하나씩)

Hint 1 — Item = 센서별 상태

T1-2의 Detector를 센서 수만큼 배열로 둡니다: SensorState st[MAX_SENSORS]. id가 0..15라서 해시가 필요 없고 st[id]로 바로 찾습니다. 함수 시작에서 memset으로 0 초기화하면 "한 번도 안 나온 센서"도 자동으로 NORMAL, streak 0입니다.

Hint 2 — 검증 순서
  1. id >= MAX_SENSORS이면 배열에 접근하기 전에 버립니다(범위 밖 쓰기 = 메모리 오염).
  2. 그 센서를 본 적이 있고 (int32_t)(t - last_t) <= 0이면 버립니다. 처음 보는 센서는 비교할 기준이 없으니 bool seen이 필요합니다.
  3. 통과한 읽기만 last_t를 갱신하고 streak 로직으로 보냅니다.
Hint 3 — 출력은 T1-1과 같은 패턴

if (cnt < out_cap) out[cnt] = …; cnt++; 알림은 입력을 앞에서부터 처리하면서 생기는 순서 그대로 쌓이므로 정렬이 필요 없습니다.

4. 풀이

4.1 핵심 아이디어 — 그림으로 보기

센서마다 레인(lane)을 하나씩 그리면, 섞여 들어온 입력이 사실은 서로 독립인 T1-2 감지기 3개라는 게 보입니다. 각 레인의 streak은 다른 센서의 읽기에 영향을 받지 않습니다.

센서 2를 보면 700(t=100)이 streak을 0으로 되돌려서, 900이 다시 세 번 연속된 t=400에서야 알림이 나옵니다. sensor 1의 t=250(950)을 받아 줬다면 이미 과열 상태라 이벤트는 없지만, 과열 전이었다면 시간을 거슬러 streak을 올리는 버그가 됩니다.

/*
 * T1-4  Multi-Sensor Overheat
 *
 * Readings from up to MAX_SENSORS sensors arrive interleaved in one array (input order = arrival
 * order). Run an independent T1-2 style detector per sensor and report every overheat START as
 * an Alert {id, t_ms}, in input order.
 *
 * Definitions (agreed with the interviewer):
 *   - Per sensor: NORMAL -> OVERHEATED after N_CONFIRM consecutive readings >= HIGH_C10 (alert on
 *     that reading); OVERHEATED -> NORMAL after N_CONFIRM consecutive readings <= LOW_C10 (no alert).
 *     A reading that breaks the streak resets that sensor's counter.
 *   - id >= MAX_SENSORS: ignored and counted in *dropped.
 *   - A reading whose t_ms is not AFTER that sensor's previous accepted reading (older or equal,
 *     compared wrap-safe) is ignored and counted in *dropped. It does not touch the streak.
 *   - Write at most out_cap alerts into out, but ALWAYS return the total number of alerts.
 *     out may be NULL when out_cap == 0. dropped may be NULL.
 *   - No malloc. O(n) time, O(MAX_SENSORS) state.
 *
 * Reference solution.  Build & run:  ./run.sh T1-4 sol
 */
#include <stdio.h>
#include <stdint.h>
#include <stdbool.h>
#include <stddef.h>
#include <string.h>

static int g_fail;
#define CHECK(c) do { if (!(c)) { printf("FAIL line %d: %s\n", __LINE__, #c); g_fail++; } } while (0)

#define MAX_SENSORS 16
#define HIGH_C10    850
#define LOW_C10     800
#define N_CONFIRM   3

typedef struct { uint8_t id; uint32_t t_ms; int16_t temp_c10; } Reading;
typedef struct { uint8_t id; uint32_t t_ms; } Alert;

typedef struct {
    uint32_t last_t;      /* timestamp of the last accepted reading */
    uint8_t  streak;      /* consecutive readings toward the other state */
    bool     seen;        /* has this sensor reported yet? */
    bool     overheated;
} SensorState;

size_t process(const Reading *r, size_t n, Alert *out, size_t out_cap, size_t *dropped)
{
    SensorState st[MAX_SENSORS];
    memset(st, 0, sizeof st);
    size_t cnt = 0, drop = 0;

    for (size_t i = 0; i < n; i++) {
        if (r[i].id >= MAX_SENSORS) { drop++; continue; }        /* validate before indexing */
        SensorState *s = &st[r[i].id];

        if (s->seen && (int32_t)(r[i].t_ms - s->last_t) <= 0) {  /* not newer: wrap-safe */
            drop++;
            continue;
        }
        s->seen = true;
        s->last_t = r[i].t_ms;

        int16_t t = r[i].temp_c10;
        bool toward = s->overheated ? (t <= LOW_C10) : (t >= HIGH_C10);
        if (!toward) { s->streak = 0; continue; }
        if (++s->streak < N_CONFIRM) continue;

        s->streak = 0;
        s->overheated = !s->overheated;
        if (s->overheated) {                                     /* only the START is an alert */
            if (cnt < out_cap) out[cnt] = (Alert){ r[i].id, r[i].t_ms };
            cnt++;
        }
    }
    if (dropped) *dropped = drop;
    return cnt;
}

int main(void)
{
    Alert out[8];
    size_t dropped;

    /* 1. basic: three sensors interleaved, one bad id, one stale reading */

        {0,   0, 860}, {1,   0, 700}, {2,   0, 900},
        {0, 100, 870}, {1, 100, 900}, {2, 100, 700},
        {0, 200, 880}, {1, 200, 910}, {20, 200, 999}, {2, 200, 900},
        {1, 300, 920}, {0, 300, 890}, {2, 300, 900},
        {1, 250, 950},                                  /* older than sensor 1's t=300 */
        {2, 400, 900},
    };
    dropped = 99;
    size_t k = process(a, sizeof a / sizeof a[0], out, 8, &dropped);
    CHECK(k == 3 && dropped == 2);
    CHECK(k >= 3 && out[0].id == 0 && out[0].t_ms == 200);
    CHECK(k >= 3 && out[1].id == 1 && out[1].t_ms == 300);
    CHECK(k >= 3 && out[2].id == 2 && out[2].t_ms == 400);

    /* 2. empty input */

코드 읽는 포인트

  • if (r[i].id >= MAX_SENSORS)가 &st[r[i].id]보다 먼저 옵니다. 순서가 바뀌면 포인터 계산만으로도 UB입니다.
  • (int32_t)(r[i].t_ms - s->last_t) <= 0: 두 시각 차이가 2^31 ms(약 24.8일) 미만이면 랩어라운드가 있어도 "더 최근인가"를 정확히 판단합니다(테스트 6번: 0xFFFFFFF0 → 0x10은 +32 ms).
  • 같은 시각(== 0)도 버립니다. 같은 샘플이 두 번 들어오면 한 번의 고온이 streak을 2 올리기 때문입니다.
  • SensorState는 함수 지역 배열이라 호출마다 새로 시작합니다. 실제 펌웨어라면 상태를 호출자 구조체로 빼서 스트리밍으로 이어 갑니다(§6).

4.5 복잡도

  • 시간 O(n) — 읽기마다 O(1)(배열 인덱싱 + T1-2 로직).
  • 추가 메모리 O(MAX_SENSORS) = 128바이트 스택. 출력 버퍼는 호출자가 줍니다.

5. 임베디드 관점으로 말할 것

  • 신뢰할 수 없는 입력에서 온 인덱스는 항상 검사: id는 CAN/I2C 프레임에서 옵니다. 검사 없이 st[id]에 쓰면 스택의 다른 변수를 덮어씁니다. 실제 사고 원인 1순위인 패턴입니다.
  • 버린 개수를 세서 돌려주기: 조용히 버리면 센서 배선 문제나 버스 오류를 아무도 모릅니다. dropped 카운터는 진단(telemetry)으로 올라갑니다.
  • 고정 크기 테이블: 센서 수 상한이 정해져 있으니 정적 배열이면 충분합니다. 메모리 사용량이 컴파일 시점에 정해지고, 할당 실패가 없습니다.
  • 구조체 크기와 정렬: 필드를 큰 것부터(uint32_t → uint8_t → bool) 놓아서 패딩 없이 8바이트입니다. 순서를 섞으면 12바이트가 될 수 있다는 걸 말할 수 있으면 좋습니다.
  • 한 센서만 볼 때의 로직은 T1-2, 고장 판정(stuck/dropout)을 센서별로 붙이면 T1-6, 가장 뜨거운 K개 센서는 T2-10.

6. Follow-up 질문과 답

Follow-up (English)답
Sensor ids are arbitrary 32-bit values, still at most 16 sensors.크기 32(2의 거듭제곱, 부하율 ≤ 50%)인 오픈 어드레싱 해시 테이블을 둡니다. slot = hash(id) & 31, 충돌 시 선형 탐사, 빈 칸이면 새 센서 등록. 가득 차면 새 센서를 버리고 dropped로 셉니다. 16개면 단순 선형 검색도 충분히 빠르다는 점도 말합니다.
Report how many sensors are overheated right now, in O(1).uint8_t n_hot 카운터를 두고 OVERHEAT 전이에서 ++, RECOVERED 전이에서 --. 또는 uint16_t hot_mask의 비트를 세우고 popcount. 마스크면 "어떤 센서인지"도 바로 압니다.
Which sensor overheated first?첫 알림이 곧 답입니다(입력 순서 = 도착 순서). 타임스탬프 기준이라면 알림 중 t_ms가 가장 이른 것을 랩 안전 비교로 고릅니다.
Make it streaming instead of a batch function.SensorState st[MAX_SENSORS]를 typedef struct { SensorState st[MAX_SENSORS]; uint32_t dropped; } Monitor;로 빼고 Event monitor_update(Monitor *m, const Reading *r)가 알림 여부를 돌려주게 합니다.
What if a sensor stops reporting?센서별 last_t가 있으니 주기적으로 now - last_t > timeout을 검사해서 dropout으로 판정합니다. 과열 상태에서 끊기면 보수적으로 과열 유지(fail-safe) → T1-6.

7. 자주 하는 실수

  • id 범위 검사 없이 st[id] 접근 → 테스트 1·7번에서 스택 오염(ASan이 잡음)
  • 센서 하나의 streak을 전역으로 둠 → 다른 센서의 읽기가 streak을 리셋해서 알림을 놓침
  • last_t == 0을 "본 적 없음"으로 씀 → t=0 읽기 뒤에 같은 t=0 중복이 오면 처음 보는 센서로 착각해서 통과시킴
  • t_ms < last_t로 비교 → 랩어라운드(테스트 6번)에서 정상 읽기를 버림
  • 버린 읽기에서도 last_t나 streak을 갱신 → 테스트 3번 실패
  • id >= MAX_SENSORS 대신 id > MAX_SENSORS → id 16이 통과, 테스트 7번 실패
