0. 문제 한국어로 먼저 보기

영어 원문(§1)을 읽기 전에 무슨 상황이고 뭘 만들어야 하는지만 빠르게 잡는 요약입니다. 풀이 힌트는 없습니다.

한 줄 요약: Ethernet/IO 경로의 benchmark tool을 짭니다. 선로가 낼 수 있는 최대 frame rate(line rate)를 계산하고, RFC 2544 방식으로 frame을 하나도 잃지 않는 최대 속도(throughput)를 찾고, 부하별 frame loss 곡선을 그립니다.

상황

  • traffic generator가 DUT(device under test)에 정해진 속도로 frame을 일정 시간(trial) 동안 보내고, 몇 개가 돌아왔는지 셉니다. 받은 수 == 보낸 수일 때만 zero loss입니다.
  • 코드는 DUT를 trial callback trial(ctx, rate_fps, frame_len, n_frames) → frames_received 하나로만 봅니다. DUT는 stub.c 아래쪽 mock입니다.
    • mock은 초당 처리 가능한 frame 수(pps_max, per-packet 처리 한계)가 있어서, 그보다 빨리 보내면 일부를 버립니다. 그래서 작은 frame은 loss가 나고 큰 frame은 line rate까지 갑니다.
    • 특정 trial 하나에 일시적 이벤트를 넣을 수 있습니다: FLAKY_BOOST(그 trial만 용량을 넘어도 안 잃음) / FLAKY_DROP(그 trial만 frame 1개를 잃음, 예: bit error).
  • 선로 위의 frame 하나는 frame 자체(frame_len, FCS 포함, 64..9216 B) 말고도 20 B를 더 씁니다: preamble 7 + SFD 1 + IFG(inter-frame gap) 12.
  • 속도 단위: pct_x100 = line rate의 0.01 % 단위 정수(0..10000, 10000 = 100 %).
    • rate_fps = line_fps * pct_x100 / 10000 (내림)
    • trial당 frame 수 n = rate_fps * trial_ms / 1000 (내림, 최소 1)

1. Problem

You are writing the throughput benchmark for an Ethernet / IO path on a new SoC. A traffic generator offers frames to the device under test (DUT) at a chosen rate for a fixed trial time and counts how many come back. Implement the line-rate math, the RFC 2544 §26.1 throughput search (highest rate with zero frame loss), and the RFC 2544 §26.3 frame-loss-rate curve.

Your code sees the DUT only through a trial callback. The DUT is a mock at the bottom of stub.c: it forwards at most pps_max frames/s (per-packet processing limit), so small frames lose and large frames reach line rate. It can inject one transient event at a chosen trial index: FLAKY_BOOST (that trial loses nothing even above capacity) or FLAKY_DROP (that trial loses exactly one frame, e.g. a bit error).

Units: rates are searched in pct_x100 = 0.01 % of line rate (0..10000). rate_fps = line_fps * pct_x100 / 10000 (floor); frames per trial n = rate_fps * trial_ms / 1000 (floor, at least 1).

Requirements:

  • line_rate_fps: frame_len includes the FCS, valid 64..9216. Each frame also costs 20 bytes on the wire (preamble 7 + SFD 1 + IFG 12). Result = link_bps / ((frame_len + 20) * 8), floor. Bad args → 0.
  • rfc2544_throughput:
    1. Trial at 100 %. Zero loss → candidate = 100 %.
    2. Otherwise binary search with lo = 0 (pass), hi = 10000 (fail): while hi − lo > res_x100, mid = lo + (hi − lo) / 2, run a trial, zero loss → lo = mid, else hi = mid. Candidate = lo.
    3. Confirm: one more trial at the candidate. Zero loss → done. Loss → hi = candidate, lo = 0, back to step 2. A candidate of 0 (nothing passed) is returned without a confirmation.
    • At most max_trials trials in total; when the budget runs out → -ETIMEDOUT with out->trials set and the rate fields 0.
    • On success fill rate_fps, pct_x100, trials (including confirmations).
  • rfc2544_loss_curve: trials at 100 %, 90 %, …, 10 % of line rate. One LossPoint per step, lost = sent − received (0 if received ≥ sent), loss_x100 = lost * 10000 / sent (floor). Stop after two consecutive steps with zero lost frames, or after the 10 % step. Return the number of points; -ENOSPC if cap is too small.
  • Bad arguments → -EINVAL without running any trial.

Constraints

  • C11, integer math only (no float), no malloc. Everything in uint64_t without overflow (link_bps up to hundreds of Gb/s, trials of 60 s or more).
  • The mock DUT is deterministic and counts its own trials (1-based).

Clarifying questions to ask (first 3 minutes)

  1. Is frame_len with or without the FCS? Does "line rate" include preamble and IFG? (RFC 2544 uses frame sizes with FCS; the wire adds 20 B.)
  2. What resolution do you want for throughput — absolute fps or % of line rate — and is there a time budget for the whole run?
  3. Is "zero loss" strictly zero frames, or is there an acceptance threshold? Do duplicated / extra frames count as a failure?
  4. Trial duration: the RFC says at least 60 s. Can I use shorter trials to search and a long trial only to confirm?
  5. Are both ports on one clock, or can the tester and DUT differ by up to ±100 ppm?
  6. Is the path back-pressured (PCIe/AXI) or does it drop on overflow (Ethernet, camera)?

/* =====================================================================
 * Test harness: mock DUT (do not edit)
 * A path limited by per-packet processing: it forwards up to pps_max frames/s.
 * Offered above that, it forwards n * pps_max / rate of the n frames (floor).
 * ===================================================================== */
enum { FLAKY_NONE, FLAKY_BOOST, FLAKY_DROP };

typedef struct {
    uint64_t pps_max;       /* forwarding capacity, frames/s */
    uint32_t trials;        /* trials run so far */
    uint32_t flaky_at;      /* 1-based trial index with a transient event; 0 = off */
    int      flaky_kind;    /* BOOST: that trial loses nothing (e.g. a competing bus
                               master was idle); DROP: that trial loses 1 frame (bit error) */
    uint64_t max_rate;      /* highest rate ever offered */
    uint64_t rate_log[64];  /* offered rate per trial */
} MockDut;

static uint64_t mock_trial(void *ctx, uint64_t rate_fps, uint32_t frame_len, uint64_t n)
{
    MockDut *d = ctx;
    (void)frame_len;
    d->trials++;
    if (d->trials <= 64) d->rate_log[d->trials - 1] = rate_fps;
    if (rate_fps > d->max_rate) d->max_rate = rate_fps;
    uint64_t rx = n;
    if (rate_fps > d->pps_max) rx = n * d->pps_max / rate_fps;
    if (d->trials == d->flaky_at) {
        if (d->flaky_kind == FLAKY_BOOST) rx = n;
        if (d->flaky_kind == FLAKY_DROP && rx > 0) rx--;
    }
    return rx;
}

static MockDut mk(uint64_t pps_max) { MockDut d; memset(&d, 0, sizeof d); d.pps_max = pps_max; return d; }

3. 힌트 (막힐 때 하나씩)

Hint 1 — 탐색 변수는 fps가 아니라 pct_x100

탐색은 0..10000 정수 범위에서 하고, trial 직전에만 rate = line * pct / 10000으로 바꿉니다. 해상도가 frame 크기와 상관없이 같은 의미(0.1 % = 10)가 되고, 결과를 % of line rate로 바로 보고할 수 있습니다. rate가 line보다 커지는 일도 없습니다(내림).

Hint 2 — 탐색 + 확인을 한 루프로

run_trial() 헬퍼 하나에 "예산 검사 → trials++ → rate/n 계산 → fn() == n"을 몰아넣으면 예산 초과 처리가 한 군데로 모입니다. 바깥 루프는 for (;;) { 필요하면 이진 탐색; 후보 확인; 통과면 break; 아니면 hi = 후보, lo = 0 } 모양입니다. 100 %가 바로 통과한 경우는 "탐색은 건너뛰고 확인만" 하는 같은 루프입니다.

Hint 3 — "zero loss"는 반올림한 %가 아니라 frame 개수로

4억 개 중 1개를 잃으면 loss_x100은 0으로 내림됩니다. 그래도 그 단계는 zero loss가 아닙니다. 연속 카운터(zero_run)는 lost == 0으로만 올리고, 하나라도 잃으면 0으로 되돌립니다.

4. 풀이

4.1 핵심 아이디어 — line rate는 선로 위 비트로 계산

Ethernet에서 frame 하나가 차지하는 시간은 frame 바이트만이 아닙니다. 앞에 preamble 7 B + SFD 1 B가 붙고, 뒤에 최소 IFG 12 B가 비어 있어야 합니다. 그래서 "frame 슬롯" 하나 = frame_len + 20 바이트입니다.

4.2 이진 탐색과 확인 trial

throughput은 "frame을 하나도 안 잃는 최대 rate"입니다. 통과/실패가 rate에 대해 단조(어느 rate 아래는 다 통과, 위는 다 실패)라고 보고 이진 탐색합니다. 0.1 % 해상도면 100 % trial 1번 + 탐색 10번(10000 / 2^10 ≈ 9.8 ≤ 10) + 확인 1번 = 12번입니다.

확인 trial이 필요한 이유: 단조 가정은 실제로 깨집니다. 다른 bus master가 잠깐 쉬었거나, 열·클럭 상태가 좋았던 trial 하나가 용량보다 높은 rate를 거짓 통과시키면, 그 뒤 탐색은 전부 그 위에서만 일어나고 결과가 높게 나옵니다. 마지막에 후보를 다시 돌려 보면 이걸 잡습니다. 반대로 거짓 실패(bit error로 1개 잃음)는 확인으로 못 잡습니다. 결과가 낮게 나올 뿐 재현은 되기 때문입니다(테스트 6번).

/*
 * L3  RFC 2544 Throughput Search for an Ethernet / IO Path -- Reference solution
 *
 * A traffic generator offers frames to a device under test (DUT) at a chosen rate for a
 * fixed trial time and counts how many come back. The DUT here is a MOCK at the bottom of
 * this file; your code only sees it through a trial callback:
 *
 *     uint64_t trial(void *ctx, uint64_t rate_fps, uint32_t frame_len, uint64_t n_frames)
 *         -> frames received (zero loss <=> received == sent)
 *
 * Rates are expressed in 0.01 % of line rate ("pct_x100", 0..10000).
 *     rate_fps(pct_x100) = line_fps * pct_x100 / 10000          (floor)
 *     frames per trial   = rate_fps * trial_ms / 1000            (floor, at least 1)
 *
 * Implement:
 *   line_rate_fps       max frames/s on the wire. frame_len includes the FCS (64..9216);
 *                       every frame also costs 20 bytes on the wire (preamble 7 + SFD 1 +
 *                       IFG 12). Floor. Bad args (link_bps == 0, len out of range) -> 0.
 *   rfc2544_throughput  RFC 2544 sec 26.1: highest rate with ZERO frame loss.
 *                       1) trial at 100 %. Zero loss -> candidate = 100 %.
 *                       2) else binary search: lo = 0 (pass), hi = 10000 (fail);
 *                          while hi - lo > res_x100: mid = lo + (hi - lo) / 2, trial,
 *                          zero loss -> lo = mid, else hi = mid. candidate = lo.
 *                       3) confirm: one more trial at the candidate. Zero loss -> done.
 *                          Loss -> hi = candidate, lo = 0, go back to the search in 2).
 *                          (candidate 0 = nothing passed: done without a confirmation.)
 *                       At most max_trials trials in total; budget gone -> -ETIMEDOUT.
 *                       Bad args -> -EINVAL. out->trials is always set.
 *   rfc2544_loss_curve  RFC 2544 sec 26.3: trials at 100 %, 90 %, ..., 10 % of line rate.
 *                       Record one LossPoint per step. Stop after two CONSECUTIVE steps with
 *                       zero lost frames (or after the 10 % step). Returns the number of
 *                       points, -ENOSPC if pts[] is too small, -EINVAL on bad args.
 *
 * Integer math only (no float), no malloc.
 *
 * Build & run:  ./run.sh L3 sol
 */

uint64_t line_rate_fps(uint64_t link_bps, uint32_t frame_len)
{
    if (link_bps == 0 || frame_len < FRAME_MIN || frame_len > FRAME_MAX) return 0;
    return link_bps / ((uint64_t)(frame_len + WIRE_OVERHEAD) * 8u);   /* bits per frame slot */
}

static uint64_t rate_at(uint64_t line, uint32_t pct) { return line * pct / PCT_FULL; }

static uint64_t frames_for(uint64_t rate, uint32_t trial_ms)
{
    uint64_t n = rate * trial_ms / 1000u;
    return n ? n : 1u;
}

/* One trial at pct. Returns 1 = zero loss, 0 = loss, -ETIMEDOUT = budget used up. */
static int run_trial(trial_fn fn, void *ctx, uint64_t line, uint32_t len,
                     const TputCfg *cfg, uint32_t pct, uint32_t *trials)
{
    if (*trials >= cfg->max_trials) return -ETIMEDOUT;
    (*trials)++;
    uint64_t rate = rate_at(line, pct);
    uint64_t n = frames_for(rate, cfg->trial_ms);
    return fn(ctx, rate, len, n) == n;      /* more than sent (duplicates) is also a fail */
}

int rfc2544_throughput(trial_fn fn, void *ctx, uint64_t link_bps, uint32_t frame_len,
                       const TputCfg *cfg, TputResult *out)
{
    if (out == NULL) return -EINVAL;
    memset(out, 0, sizeof *out);
    uint64_t line = line_rate_fps(link_bps, frame_len);
    if (fn == NULL || cfg == NULL || line == 0 || cfg->res_x100 == 0 ||
        cfg->res_x100 > PCT_FULL || cfg->max_trials == 0 || cfg->trial_ms == 0)
        return -EINVAL;

    uint32_t trials = 0, lo = 0, hi = PCT_FULL, cand = PCT_FULL;
    int ok = run_trial(fn, ctx, line, frame_len, cfg, PCT_FULL, &trials);
    if (ok < 0) goto timeout;
    bool search = !ok;                      /* 100 % passed -> skip straight to confirming it */
    for (;;) {
        if (search) {
            while (hi - lo > cfg->res_x100) {
                uint32_t mid = lo + (hi - lo) / 2;
                ok = run_trial(fn, ctx, line, frame_len, cfg, mid, &trials);
                if (ok < 0) goto timeout;
                if (ok) lo = mid; else hi = mid;
            }
            cand = lo;
            if (cand == 0) break;           /* nothing passes: nothing to confirm */
        }
        ok = run_trial(fn, ctx, line, frame_len, cfg, cand, &trials);   /* confirmation */
        if (ok < 0) goto timeout;
        if (ok) break;
        hi = cand; lo = 0; search = true;   /* candidate was a false pass: search below it */
    }
    out->pct_x100 = cand;
    out->rate_fps = rate_at(line, cand);
    out->trials = trials;
    return 0;

timeout:
    out->trials = trials;
    return -ETIMEDOUT;
}

int rfc2544_loss_curve(trial_fn fn, void *ctx, uint64_t link_bps, uint32_t frame_len,
                       uint32_t trial_ms, LossPoint *pts, int cap)
{
    uint64_t line = line_rate_fps(link_bps, frame_len);
    if (fn == NULL || pts == NULL || cap < 1 || line == 0 || trial_ms == 0) return -EINVAL;

    int n = 0, zero_run = 0;
    for (uint32_t pct = PCT_FULL; pct >= LOSS_STEP && zero_run < 2; pct -= LOSS_STEP) {
        if (n == cap) return -ENOSPC;
        uint64_t rate = rate_at(line, pct), sent = frames_for(rate, trial_ms);
        uint64_t rx = fn(ctx, rate, frame_len, sent);
        uint64_t lost = rx >= sent ? 0 : sent - rx;
        pts[n] = (LossPoint){ pct, rate, sent, lost, (uint32_t)(lost * PCT_FULL / sent) };
        n++;
        zero_run = lost == 0 ? zero_run + 1 : 0;   /* decide on frame count, not rounded % */
    }
    return n;
}

/* =====================================================================
 * Test harness: mock DUT (do not edit)
 * A path limited by per-packet processing: it forwards up to pps_max frames/s.
 * Offered above that, it forwards n * pps_max / rate of the n frames (floor).
 * ===================================================================== */
enum { FLAKY_NONE, FLAKY_BOOST, FLAKY_DROP };

typedef struct {
    uint64_t pps_max;       /* forwarding capacity, frames/s */
    uint32_t trials;        /* trials run so far */
    uint32_t flaky_at;      /* 1-based trial index with a transient event; 0 = off */
    int      flaky_kind;    /* BOOST: that trial loses nothing (e.g. a competing bus
                               master was idle); DROP: that trial loses 1 frame (bit error) */
    uint64_t max_rate;      /* highest rate ever offered */
    uint64_t rate_log[64];  /* offered rate per trial */
} MockDut;

static uint64_t mock_trial(void *ctx, uint64_t rate_fps, uint32_t frame_len, uint64_t n)
{
    MockDut *d = ctx;
    (void)frame_len;
    d->trials++;
    if (d->trials <= 64) d->rate_log[d->trials - 1] = rate_fps;
    if (rate_fps > d->max_rate) d->max_rate = rate_fps;
    uint64_t rx = n;
    if (rate_fps > d->pps_max) rx = n * d->pps_max / rate_fps;
    if (d->trials == d->flaky_at) {
        if (d->flaky_kind == FLAKY_BOOST) rx = n;
        if (d->flaky_kind == FLAKY_DROP && rx > 0) rx--;
    }
    return rx;
}

    /* 2. DUT that forwards at line rate: 100 % + one confirmation = 2 trials */
    d = mk(UINT64_MAX);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &cfg, &r) == 0);
    CHECK(r.pct_x100 == 10000 && r.rate_fps == 14880952u && r.trials == 2 && d.trials == 2);
    d = mk(UINT64_MAX);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 1518, &cfg, &r) == 0);
    CHECK(r.pct_x100 == 10000 && r.rate_fps == 812743u && r.trials == 2);

    /* 3. path capped at 9.1 Mfps: 64 B tops out at 61.12 %, 1518 B reaches line rate */
    d = mk(9100000u);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &cfg, &r) == 0);
    CHECK(r.pct_x100 == 6112 && r.rate_fps == 9095237u && r.trials == 12);
    CHECK(d.rate_log[0] == 14880952u && d.rate_log[1] == 7440476u && d.rate_log[2] == 11160714u);
    CHECK(d.rate_log[11] == r.rate_fps);                    /* last trial = confirmation */
    CHECK(d.max_rate == 14880952u);                         /* never offered above line rate */
    d = mk(9100000u);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 1518, &cfg, &r) == 0);
    CHECK(r.pct_x100 == 10000 && r.trials == 2);

    /* 4. frame-size sweep on a 3.0 Mfps path (RFC 2544 frame sizes) */
    {
        static const uint32_t sz[7]  = { 64, 128, 256, 512, 1024, 1280, 1518 };
        static const uint32_t exp[7] = { 2011, 3544, 6620, 10000, 10000, 10000, 10000 };
        int ok = 0;
        for (int i = 0; i < 7; i++) {
            d = mk(3000000u);
            ok += rfc2544_throughput(mock_trial, &d, G10, sz[i], &cfg, &r) == 0 && r.pct_x100 == exp[i];
        }
        CHECK(ok == 7);
    }

    /* 5. flaky false PASS at trial 3 (75 %): the confirmation catches it */
    d = mk(9100000u); d.flaky_at = 3; d.flaky_kind = FLAKY_BOOST;
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &cfg, &r) == 0);
    CHECK(r.pct_x100 == 6114 && r.rate_fps == 9098214u && r.trials == 23);
    CHECK(r.rate_fps <= 9100000u);                          /* never above the real capacity */
    d = mk(9100000u); d.flaky_at = 3; d.flaky_kind = FLAKY_BOOST;
    const TputCfg small = { 10, 20, 60000 };
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &small, &r) == -ETIMEDOUT);
    CHECK(r.trials == 20 && d.trials == 20 && r.pct_x100 == 0);

    /* 6. flaky false FAIL (1 frame dropped at trial 2, 50 %): NOT caught -> low result */
    d = mk(9100000u); d.flaky_at = 2; d.flaky_kind = FLAKY_DROP;
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &cfg, &r) == 0);
    CHECK(r.pct_x100 == 4990 && r.rate_fps == 7425595u && r.trials == 12);

    /* 7. dead path (forwards nothing): 0 %, no confirmation trial */
    d = mk(0);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &cfg, &r) == 0);
    CHECK(r.pct_x100 == 0 && r.rate_fps == 0 && r.trials == 11);

    /* 8. frame-loss curve, 9.1 Mfps path at 64 B: stops after 60 % and 50 % are clean */
    d = mk(9100000u);
    CHECK(rfc2544_loss_curve(mock_trial, &d, G10, 64, 60000, pts, 10) == 6);
    CHECK(pts[0].pct_x100 == 10000 && pts[0].loss_x100 == 3884 && pts[0].sent == 892857120u);
    CHECK(pts[1].loss_x100 == 3205 && pts[2].loss_x100 == 2355 && pts[3].loss_x100 == 1263);
    CHECK(pts[4].lost == 0 && pts[5].lost == 0 && pts[5].pct_x100 == 5000);
    d = mk(UINT64_MAX);
    CHECK(rfc2544_loss_curve(mock_trial, &d, G10, 1518, 60000, pts, 10) == 2);
    CHECK(pts[1].pct_x100 == 9000 && pts[1].lost == 0);
    /* one dropped frame at the 50 % step rounds to 0.00 % but is NOT zero loss */
    d = mk(9100000u); d.flaky_at = 6; d.flaky_kind = FLAKY_DROP;
    CHECK(rfc2544_loss_curve(mock_trial, &d, G10, 64, 60000, pts, 10) == 8);
    CHECK(pts[5].lost == 1 && pts[5].loss_x100 == 0 && pts[7].pct_x100 == 3000);
    /* path that loses at every step (1 Mfps < 10 % of 64 B line rate): all 10 steps */
    d = mk(1000000u);
    CHECK(rfc2544_loss_curve(mock_trial, &d, G10, 64, 60000, pts, 10) == 10);
    CHECK(pts[9].pct_x100 == 1000 && pts[9].lost > 0);

    /* 9. bad arguments */
    d = mk(UINT64_MAX);
    const TputCfg bad_res = { 0, 32, 60000 }, bad_tr = { 10, 0, 60000 }, bad_ms = { 10, 32, 0 };
    CHECK(rfc2544_throughput(NULL, &d, G10, 64, &cfg, &r) == -EINVAL);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 63, &cfg, &r) == -EINVAL);
    CHECK(rfc2544_throughput(mock_trial, &d, 0, 64, &cfg, &r) == -EINVAL);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &bad_res, &r) == -EINVAL);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &bad_tr, &r) == -EINVAL);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &bad_ms, &r) == -EINVAL);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, NULL, &r) == -EINVAL);
    CHECK(rfc2544_throughput(mock_trial, &d, G10, 64, &cfg, NULL) == -EINVAL);
    CHECK(d.trials == 0);                                   /* no trial on bad args */
    d = mk(9100000u);
    CHECK(rfc2544_loss_curve(mock_trial, &d, G10, 64, 60000, pts, 3) == -ENOSPC);
    CHECK(rfc2544_loss_curve(mock_trial, &d, G10, 64, 60000, pts, 0) == -EINVAL);
    CHECK(rfc2544_loss_curve(mock_trial, &d, G10, 9217, 60000, pts, 10) == -EINVAL);

    printf(g_fail ? "%d FAILED\n" : "ALL PASS\n", g_fail);
    return g_fail != 0;
}

코드 읽는 포인트

  • line_rate_fps의 곱셈은 (uint64_t)(frame_len + 20) * 8로 64-bit에서 합니다. 400 GbE도 4e11이라 uint64_t로 충분합니다.
  • rate_at()은 내림이라 pct = 10000이면 정확히 line이고 절대 넘지 않습니다. tester가 line rate를 넘겨 보내라고 하면 결과가 의미 없습니다(테스트 3번 max_rate).
  • run_trial()이 예산 검사 → trials++ → fn() == n을 한 곳에서 합니다. received > sent(중복 frame)도 실패로 봅니다. == 하나로 둘 다 잡힙니다.
  • bool search: 100 %가 통과한 경우는 탐색을 건너뛰고 같은 확인 경로를 탑니다. 100 %의 확인이 실패하면 hi = 10000, lo = 0에서 탐색이 시작되므로 별도 코드가 필요 없습니다.
  • mid = lo + (hi - lo) / 2: 여기서는 값이 작아 overflow는 없지만, 습관적으로 쓰는 형태입니다.
  • loss 곡선의 zero_run은 lost == 0으로만 판단합니다. loss_x100은 보고용이고 판정용이 아닙니다.

4.5 복잡도

  • throughput: trial 수 = 1 + ⌈log2(10000 / res)⌉ + 1 (확인 실패가 없을 때). res 10 → 12번. 시간 = trial 수 × trial 길이: 60 s trial이면 12분 / frame 크기, RFC 2544 기본 7개 크기면 약 84분.
  • loss 곡선: 최대 10 trial. 메모리는 둘 다 O(1) + 호출자 배열.

5. 임베디드 관점으로 말할 것

  • IFG/preamble을 빼먹으면 숫자가 틀린다: 64 B에서 20 B를 빼면 19.5 Mfps가 나와 31 % 부풀려집니다. 반대로 L2 bit rate로 보고하면 64 B line rate가 7.62 Gb/s밖에 안 돼 보여서 "DUT가 느리다"는 오해가 생깁니다. 보고서에는 fps와 % of line rate를 같이 적습니다.
  • trial 길이 = 통계: RFC 2544는 trial을 60 s 이상으로 권합니다. 짧은 trial은 FIFO가 overflow하기 전에 끝나서 거짓 통과가 납니다. 예: 9.1 Mfps 경로에 한계보다 0.1 % 높은 rate를 주면 초과분이 초당 9,100개라, 1,000-frame buffer가 약 0.11 s를 버팁니다 → 0.1 s trial은 통과로 나옵니다. 한계에 가까울수록 오래 버티니, 바로 그 구간에서 짧은 trial이 틀립니다. 실무에서는 짧은 trial(예: 2–10 s)로 탐색하고 마지막 확인만 60 s로 돌리는 방식이 흔합니다. 또 trial이 끝난 뒤 약 2 s 기다렸다가 수신 카운터를 읽어야 in-flight frame을 loss로 잘못 세지 않습니다.
  • latency (§26.2): throughput rate에서 120 s 스트림을 보내고, 60 s쯤에 timestamp를 박은 frame 하나를 넣어 TX/RX 시각 차를 잽니다. 최소 20번 반복해 평균. store-and-forward 장비는 마지막 비트 입력 → 첫 비트 출력(LIFO), cut-through는 첫 비트 → 첫 비트(FIFO)로 정의가 다릅니다(RFC 1242). 반드시 throughput 이하 rate에서 재야 합니다. 그 위에선 queue가 무한히 쌓여 latency가 trial 길이에 비례할 뿐입니다. 분포 통계(min/p50/p99)는 V4, timestamp 정합은 V12.
  • back-to-back (§26.4): 최소 IFG로 burst를 보내고, loss 없이 통과하는 가장 긴 burst 길이를 찾습니다(burst 2 s 이상, 50번 반복). throughput이 "지속 처리 능력"이라면 back-to-back은 buffer 깊이를 잽니다. 이것도 같은 이진 탐색 코드에 "rate" 대신 "burst 길이"를 넣으면 됩니다.
  • SoC 내부 경로에 그대로 적용: JD의 "throughput, latency, resource utilization, IO frequency" 벤치마크가 바로 이 방법입니다.
    • drop하는 경로(MIPI CSI-2 카메라 입력, Ethernet MAC RX, ADC 스트림): 상대에게 back-pressure를 못 겁니다. "zero-loss throughput" = FIFO overflow 카운터가 0으로 유지되는 최대 지속 rate. 카메라 frame rate × 해상도를 올려 가며 같은 탐색을 합니다 → V9.
    • back-pressure가 있는 경로(AXI, PCIe, DMA → DDR): loss가 안 나고 대신 상류가 멈춥니다. 그래서 기준을 "offered rate 대비 achieved rate가 99.9 % 이상" 또는 "latency p99가 한계 이하"로 바꿔 같은 탐색을 합니다. DMA 엔진은 V3, PCIe 링크 쪽은 L2, 생산자/소비자 ring overflow는 L5.
    • NPU IO: 입력 tensor DMA rate를 올려 가며 NPU가 frame 마감 안에 끝내는 최대 rate를 찾습니다. 결과는 "frames/s at zero deadline miss".
  • traffic generator 정확도: SW로 만든 generator는 타이머 jitter 때문에 평균 rate는 맞아도 순간 burst가 생겨 거짓 loss가 납니다. 그래서 tester는 FPGA/HW에서 IFG를 bit 단위로 맞춥니다. SoC 검증에서도 CPU 루프보다 HW traffic generator(AXI traffic generator IP, DMA 엔진의 rate limiter)를 씁니다. 또 Ethernet은 ±100 ppm 클럭 차이가 허용되므로, tester 클럭이 DUT보다 빠르면 100 %에서 완벽한 DUT도 조금씩 잃습니다.
  • BER과 frame loss는 다르다: bit error 하나 → FCS 불일치 → frame drop → loss로 셈. 10 GbE 64 B line rate 60 s면 선로 비트가 6 × 10^11개, 그중 frame 비트가 약 4.6 × 10^11개라서, BER 1e-12 링크면 trial당 오류 frame 기대값이 약 0.46개입니다. 용량 문제가 아니라 링크 문제로 loss가 날 수 있으니, throughput 전에 PRBS로 링크를 먼저 검증합니다 → V6. FLAKY_DROP 테스트가 이 상황입니다.

5.1 면접관 Iris Lee(SW·시스템 출신 Principal)가 파고들 포인트

  • "Why binary search, and why the confirmation trial?" → 통과/실패가 rate에 대해 단조라고 가정하면 이진 탐색이 trial 수를 log로 줄입니다(0.1 %에 12번). 하지만 실제 DUT는 비결정적이라 거짓 통과 하나가 결과 전체를 끌어올립니다. 확인 trial이 그걸 잡고, 거짓 실패는 못 잡으니 전체 테스트를 반복해 분산도 봅니다. "Binary search assumes monotonic pass/fail, which real systems violate; the confirmation trial catches a false pass, and repeating the whole run catches a false fail."
  • "Your trial is 60 seconds. How long does a full RFC 2544 run take, and how do you shorten it?" → frame 크기 7개 × 12 trial × 60 s ≈ 84분, latency·back-to-back까지 하면 몇 시간입니다. 짧은 trial로 탐색 → 60 s로 확인, 이전 결과 근처에서 탐색 시작(warm start), 여러 포트 병렬. 단, 확인 trial은 절대 줄이지 않습니다. "Search with short trials, confirm with the full 60 seconds, and start the next frame size near the last answer; the confirmation length is the one thing I never cut."
  • "You lost 1 frame in 446 million. Is that a throughput problem?" → 아닐 가능성이 큽니다. 한 개 단발 loss는 용량 한계(수백만 개씩 잃음)와 모양이 다르고, BER 1e-12면 기대되는 수준입니다. FCS 에러 카운터를 같이 읽어서 "drop 원인 = CRC 에러"인지 "drop 원인 = FIFO overflow"인지 나눕니다. 카운터를 원인별로 나눠 놓는 게 테스트 설계의 핵심입니다. "A single lost frame looks like a bit error, not a capacity limit, so I read the FCS-error and FIFO-overflow counters separately before I call it a throughput failure."
  • "How does this apply to the SoC, not an Ethernet switch?" → 같은 framework에서 trial callback만 바꿉니다. 카메라/MAC처럼 drop하는 경로는 overflow 카운터, AXI/PCIe처럼 back-pressure가 있는 경로는 achieved/offered 비율이나 latency p99를 판정 기준으로 씁니다. generator도 CPU가 아니라 HW(DMA rate limiter, AXI traffic generator)로 해야 burst 없이 정확합니다. "The search and reporting stay the same; only the trial changes — for a camera path the pass criterion is zero FIFO overflow, for an AXI or PCIe path it's achieved over offered rate and a p99 latency bound."
  • "How do you trust the traffic generator?" → generator를 먼저 loopback으로 자가 측정합니다(DUT 없이 100 %에서 zero loss, IFG가 12 B로 정확한지). 그리고 rate 계산은 내림이라 line rate를 넘을 수 없게 했습니다. 클럭 ppm 차이도 확인합니다. "I calibrate the generator against itself in loopback first — it must hit 100 percent with zero loss and exact 12-byte gaps — and the rate math rounds down so it can never exceed line rate."

6. Follow-up 질문과 답

Follow-up (English)답
Why search in % of line rate instead of fps?해상도가 frame 크기와 무관하게 같은 의미가 되고(0.1 %), 결과를 RFC 2544 보고 형식(% of line + fps)으로 바로 낼 수 있습니다. 정수 0..10000이라 float가 필요 없고, 내림으로 line rate를 넘을 수 없습니다.
The DUT passes 100 % but loses frames at 90 %. Possible?가능합니다. 비단조 동작의 예: 특정 rate에서만 interrupt coalescing 타이머와 맞물려 FIFO가 넘치거나, rate limiter/shaper의 토큰 버킷 경계. 이진 탐색은 이걸 못 봅니다. 그래서 §26.3 loss 곡선(10 % 단위 전 구간)을 같이 돌려 단조성을 확인합니다.
What if the tester clock is 100 ppm faster than the DUT's egress?같은 속도 포트끼리 forwarding하면 DUT는 받는 것보다 100 ppm 느리게 내보냅니다. 100 % 60 s 64 B면 약 892,857,120 × 1e-4 ≈ 89,286개가 쌓여 버퍼를 넘치면 loss. 결과가 99.99 %처럼 나오는 이유이고, tester가 DUT 포트 클럭을 측정해 보정하거나 같은 기준 클럭을 씁니다.
How would you measure latency per §26.2 with this code?throughput 결과 rate에서 trial을 돌리면서 frame 하나에 TX timestamp를 넣고 RX에서 차이를 잽니다. 20번 이상 반복해 평균(우리는 min/p50/p99도). 반드시 throughput 이하 rate에서 — 그 위에선 queue가 계속 쌓여서 latency가 "측정"이 아니라 "trial 길이"가 됩니다.
How do you implement back-to-back (§26.4)?같은 탐색에서 변수만 바꿉니다: rate는 100 %(최소 IFG) 고정, burst 길이(frame 수)를 이진 탐색해 loss 없는 최대 burst를 찾습니다. 결과 × frame 크기 ≈ DUT의 유효 buffer 깊이. 50번 반복해 평균.
How do you tell a capacity limit from a link problem?loss 모양과 카운터. 용량 한계는 rate에 비례해 대량으로 잃고(위 표처럼 수억 개), 수신 MAC의 overflow/no-buffer 카운터가 올라갑니다. 링크 문제는 rate와 무관하게 소량이고 FCS/CRC 에러 카운터가 올라갑니다. 링크는 PRBS로 먼저 검증 → V6.
The trial budget runs out. What do you report?실패(-ETIMEDOUT)로 보고하고 trial 로그를 남깁니다. 마지막 "확인되지 않은" 후보를 결과처럼 내면 안 됩니다. 예산 초과 자체가 DUT가 불안정하다는 신호(거짓 통과/실패 반복)라서 그 자체로 버그 리포트감입니다.
Mapping to a DMA → DDR path on the SoC?DMA는 back-pressure가 있어서 loss가 안 납니다. offered rate를 rate limiter로 올려 가며 achieved bandwidth와 latency p99를 기록하고, "achieved ≥ 99.9 % of offered"를 통과 기준으로 같은 탐색을 합니다. 동시에 다른 master(CPU, NPU)의 트래픽을 걸어 interconnect contention 아래서의 값도 냅니다 → V3, V4.

7. 자주 하는 실수

  • frame당 20 B(preamble + SFD + IFG)를 빼먹음 → 64 B line rate가 19.5 Mfps로 나와서 DUT가 "61 %"가 아니라 "47 %"처럼 보임 (테스트 1번)
  • frame_len에 FCS를 또 더함 → 64 B를 68 B로 계산
  • 이진 탐색 결과를 확인 없이 보고 → 거짓 통과 하나로 75 % 보고 (테스트 5번)
  • 탐색을 fps로 하면서 hi = line + 1 같은 경계 → line rate 초과 trial
  • trial 예산이 없음 → 불안정한 DUT에서 무한 루프. 상한과 -ETIMEDOUT이 필요 (테스트 5번 max_trials = 20)
  • zero loss를 loss_x100 == 0으로 판정 → 1개 잃은 단계도 통과로 셈 (테스트 8번)
  • received > sent(중복 frame)를 통과로 봄 → >= 대신 ==
  • rate * trial_ms나 n * pps_max를 32-bit로 계산 → 25 GbE 60 s에서 overflow
  • trial 끝나자마자 카운터를 읽음 → 아직 오는 중인 frame을 loss로 셈 (실장비에서 2 s 대기)
