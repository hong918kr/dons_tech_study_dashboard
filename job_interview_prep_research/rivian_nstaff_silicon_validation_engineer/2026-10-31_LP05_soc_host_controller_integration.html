0. TL;DR

  • 이 노트로 답할 수 있는 것: "새 SoC에서 PCIe root complex를 Linux로 살리려면 뭘 하나?", "device tree에 뭐가 들어가나 / ranges는 무슨 뜻인가?", "link는 올라왔는데 첫 config read가 멈춘다", "x86에선 되는데 우리 ARM SoC에선 안 된다", "PERST#는 누가, 언제 푸나?".
  • 외울 것 ①: bring-up 순서 = 전원(regulator) → refclk → PHY(SerDes) init + controller reset 해제 → PERST# assert 유지 ≥100 ms (PCIE_T_PVPERL_MS) → LTSSM enable → PERST# deassert → link-up 폴링 (DWC: 10회 × 90 ms) → Gen3+ 면 100 ms 더 대기 (PCIE_RESET_CONFIG_WAIT_MS) → pci_host_probe() 열거.
  • 외울 것 ②: DT 핵심 4종 = reg/reg-names(DBI·config·atu 레지스터 창) · ranges(CPU 주소 → PCI 주소 창: I/O, 32-bit MEM, 64-bit prefetchable MEM) · interrupt-map(INTx) + msi-map(MSI → GIC ITS) · reset-gpios(PERST#) + clocks/resets/phys/power-domains.
  • 외울 것 ③: iATU (internal Address Translation Unit, DesignWare 컨트롤러의 주소 변환표) = outbound(CPU가 쓰는 주소 → PCIe TLP 주소; config는 매 접근마다 CFG0/CFG1 타입으로 재프로그램) + inbound(장치 DMA 주소 → SoC 메모리 주소, dma-ranges).
  • 실측(이 노트에서 직접 돌림): QEMU virt의 ranges 32-bit MEM 창을 512 KiB로 줄였더니 BAR 0 [mem size 0x00100000]: can't assign; no space → Some PCI device resources are unassigned, try booting with pci=realloc → 드라이버 probe -EINVAL. "DT 창이 작으면 장치는 보이는데 드라이버가 실패한다" 를 실제 로그로 보여줄 수 있음.
  • 30초 영어 답 (headline: "How would you bring up PCIe RC on a new SoC?"): "I split it into hardware sequencing and software description. The device tree describes the controller: register regions like DBI and the config window, the ranges that map CPU address windows to PCI memory and I/O space, interrupts — interrupt-map for INTx and msi-map to the GIC ITS — plus clocks, resets, PHY, power domain and the PERST# GPIO. The driver, usually a vendor glue on top of the DesignWare core, then powers the slot, starts refclk, initializes the PHY, holds PERST# for at least 100 ms, enables the LTSSM, releases PERST#, and polls for link-up. Once the link is up it programs the iATU outbound windows and hands off to pci_host_probe for enumeration. When something fails I check, in order: LTSSM state in the vendor debug register, link-up, the iATU and ranges windows, then MSI routing and the inbound/DMA path."

1. 🔰 처음 보는 사람을 위한 설명

1.1 비유: 아파트 단지와 외부 고속도로

  • SoC 내부 = 하나의 아파트 단지. 단지 안에는 내부 도로(AXI/NoC 인터커넥트)가 있고, 집집마다(DRAM, UART, GPU…) 번지수(물리 주소)가 있다. CPU는 "0xF020_0000번지에 편지 보내" 하듯이 주소에 읽고 쓰기만 한다.
  • PCIe = 단지 밖으로 나가는 고속도로. 고속도로의 차는 "편지"가 아니라 TLP(Transaction Layer Packet: PCIe에서 주고받는 패킷 — "메모리 읽기", "메모리 쓰기", "설정 읽기" 같은 요청서)로 다닌다. 주소 체계도 단지 내부와 다르다(PCI 주소 공간).
  • Host controller (= Root Complex 쪽 컨트롤러 IP) = 단지와 고속도로를 잇는 인터체인지 + 톨게이트. 단지 내부 편지를 받아 TLP로 바꿔 고속도로에 내보내고(outbound), 고속도로에서 들어온 TLP를 단지 내부 편지로 바꿔 DRAM에 배달한다(inbound).
  • iATU = 톨게이트에 붙은 주소 변환표. "단지 번지 0xF020_0000~0xF0FF_FFFF로 온 편지는 고속도로 주소 0xF020_0000~ 메모리 쓰기 TLP로 바꿔라", "0xF000_0000 창으로 온 건 버스 1번 장치 0의 설정(config) 읽기 TLP로 바꿔라" 같은 줄들이 들어 있다.
  • PHY (SerDes) = 실제 도로 포장과 차선. 디지털 비트를 수 GHz 아날로그 신호로 바꿔 구리선에 싣는 회로. 차선 수 = lane 수(x1/x2/x4…).
  • refclk = 양쪽 톨게이트가 공유하는 신호등 박자(100 MHz 기준 클럭). 박자가 안정되지 않으면 차가 못 다닌다.
  • PERST# = 고속도로 진입로의 공사중 차단기(PCIe Reset 신호, # = active-low: 전압이 LOW일 때 "리셋 중"). 전원과 박자가 안정될 때까지 내려 두었다가, 준비되면 올려서 "이제 링크 학습 시작해도 돼"라고 알린다.
  • Device Tree (DT) = 단지 설계도. ARM SoC는 x86 PC처럼 BIOS/ACPI가 "PCIe 컨트롤러가 여기 있고 창은 이만큼"이라고 알려주지 않는 경우가 많아서, 커널에게 설계도 파일(.dts → .dtb) 로 컨트롤러 위치·주소 창·인터럽트·클럭·리셋 핀을 알려 준다.
  • "Integration(통합)" 이란 = 새 단지(SoC)에 인터체인지(컨트롤러 IP)를 설치하고, 도로 포장(PHY), 신호등(클럭), 차단기(PERST#), 전기(전원 도메인)를 연결하고, 설계도(DT)를 정확히 그리고, 교통관제 소프트웨어(Linux 드라이버)를 맞추는 전체 작업이다. 검증 엔지니어는 "이게 다 맞게 연결됐나"를 증명하는 사람.

1.2 그림: SoC 안에서 PCIe host controller가 놓이는 자리

 +--------------------------------- SoC ------------------------------------------+
 |                                                                                 |
 |  CPU cores ---+                                                                 |
 |               |      AXI / NoC interconnect (단지 내부 도로)                       |
 |  DRAM ctrl ---+----------+--------------------+-------------------+              |
 |               |          | (AXI slave:        | (AXI master:      | (APB:        |
 |  GIC + ITS ---+          |  CPU->PCIe MMIO)   |  PCIe DMA->DRAM)  |  레지스터)     |
 |  (인터럽트)    |          v                    ^                   v              |
 |  SMMU --------+   +--------------------------------------------------------+     |
 |  (IOMMU)          |  PCIe controller IP (예: Synopsys DesignWare "DWC")      |     |
 |                   |   - DBI 레지스터: 자기 자신(root port)의 config space     |     |
 |                   |   - iATU: outbound/inbound 주소 변환표                   |     |
 |                   |   - MAC / Data Link / LTSSM (링크 학습 상태기계)          |     |
 |                   |   - (옵션) 내장 MSI 컨트롤러, eDMA                        |     |
 |                   |   - vendor glue("app"/"elbi"/"apb" 레지스터: LTSSM enable,|     |
 |                   |     link-up 상태, 인터럽트 모음)                          |     |
 |                   +---------------------------+----------------------------+     |
 |   clocks(CRU) ---> aclk/pclk/aux/pipe         | PIPE interface (병렬 데이터)       |
 |   resets      ---> pwr / pipe / core          v                                   |
 |   power domain --> PD_PCIE        +------------------------+                     |
 |                                   |  PHY = SerDes (TX/RX)  | <--- refclk 100 MHz |
 |   GPIO ---------------------------+------------------------+                     |
 +----|---------------------------------------|--------------------------------------+
      | PERST# (GPIO, active-low)              | lanes (TX+/-, RX+/- 차동쌍) x1..x16
      v                                        v
 +------------------------------------------------------------------+
 |  Endpoint (NVMe SSD, NIC, FPGA, 카메라 브리지 ...)                   |
 +------------------------------------------------------------------+
  • CPU가 장치 레지스터를 읽을 때 경로: CPU → 인터커넥트 → AXI slave 포트 → iATU outbound 변환 → TLP → PHY → 장치.
  • 장치가 DMA로 DRAM에 쓸 때 경로: 장치 → TLP → 컨트롤러 → (iATU inbound 변환) → SMMU(있으면 주소 재변환/권한 검사) → AXI master 포트 → DRAM.
  • 장치가 MSI(메모리 쓰기 형태의 인터럽트)를 보낼 때: 장치 → "주소 X에 값 Y 쓰기" TLP → 컨트롤러 → GIC ITS의 doorbell 주소에 쓰기 → CPU 인터럽트. (또는 컨트롤러 내장 MSI 블록이 받아서 SPI 하나로 모아 줌.)

2.4 iATU: outbound / inbound 레지스터와 config TLP 생성

레지스터 배치 (6.18 pcie-designware.h)

[구형 viewport 방식]  DBI + 0x900 PCIE_ATU_VIEWPORT : bit31 = 방향(1=inbound), [index] 선택
                      DBI + 0x904 ... 선택된 region의 레지스터 (공유 창)
[unroll 방식, 4.80+]  atu_base(기본 DBI + 0x300000 = DEFAULT_DBI_ATU_OFFSET (0x3<<20))
                      region 주소 = atu_base + (index << 9) + (inbound ? 0x100 : 0)

region 레지스터 (unroll offset)
 +0x00 REGION_CTRL1 : [4:0] TYPE  0x0=MEM 0x2=IO 0x4=CFG0 0x5=CFG1 0x10=MSG, bit13 INCREASE_REGION_SIZE, [22:20] func
 +0x04 REGION_CTRL2 : bit31 ENABLE, bit30 BAR_MODE(inbound), bit28 CFG_SHIFT_MODE(ECAM용), bit22 INHIBIT_PAYLOAD
 +0x08 LOWER_BASE   : CPU 쪽(부모 버스) 시작 주소 하위 32
 +0x0C UPPER_BASE   :                     상위 32
 +0x10 LIMIT        : 끝 주소 하위 32
 +0x14 LOWER_TARGET : PCI 쪽 주소 하위 32  (CFG 타입이면 [31:24]=bus [23:19]=dev [18:16]=fn)
 +0x18 UPPER_TARGET : PCI 쪽 주소 상위 32
 +0x20 UPPER_LIMIT  : 끝 주소 상위 32 (4.60a+)
  • outbound 프로그램 순서 (dw_pcie_prog_outbound_atu): base/limit/target 쓰고 → CTRL1에 type → CTRL2에 ENABLE → ENABLE 비트가 읽힐 때까지 최대 5회 × 9 ms 확인 (안 되면 "Outbound iATU is not being enabled"). 주소/크기는 region_align(보통 4K/64K) 정렬, 창이 region_limit을 넘으면 -EINVAL.
  • dw_pcie_iatu_setup(): DT ranges에서 만든 bridge->windows 중 MEM 창마다 outbound region 1개, IO 창 1개(region 부족하면 config 창과 공유 → cfg0_io_shared), dma-ranges마다 inbound region 1개. region 수가 부족하면 "Ranges exceed outbound iATU size (%d)" 경고.
  • config TLP 생성 (dw_pcie_other_conf_map_bus, 핵심 로직):
/* 6.18 pcie-designware-host.c 요약 (원문 축약) */
busdev = PCIE_ATU_BUS(bus->number) | PCIE_ATU_DEV(PCI_SLOT(devfn)) | PCIE_ATU_FUNC(PCI_FUNC(devfn));
type   = pci_is_root_bus(bus->parent) ? PCIE_ATU_TYPE_CFG0   /* root port 바로 아래 버스 → Type 0 */
                                      : PCIE_ATU_TYPE_CFG1;  /* 그 아래(스위치 너머) → Type 1 */
atu.parent_bus_addr = pp->cfg0_base;  /* DT reg "config" 창의 CPU 주소 */
atu.pci_addr = busdev;                 /* TLP의 목적지 BDF */
dw_pcie_prog_outbound_atu(pci, &atu);  /* 매 접근마다 region 재프로그램 */
return pp->va_cfg0_base + where;       /* CPU는 그냥 이 주소를 readl() */
  • 해석: root bus(bus 0)에는 root port 자신만 있고, 그 config는 DBI로 직접 읽는다(dw_pcie_own_conf_map_bus). bus 1(= root port의 secondary bus)의 장치는 링크 바로 건너편이니 Type 0. bus 2 이상은 스위치를 거쳐야 하니 Type 1 (스위치가 자기 secondary/subordinate 범위를 보고 Type 0으로 바꿔 전달).
  • 결과적으로 config 창 하나(예 RK3588: 1 MiB)를 매번 다른 BDF로 돌려 쓴다 → 동시 접근은 pp->lock/config 경로 락으로 직렬화. 최신 DWC는 ecam_enabled + CFG_SHIFT_MODE로 진짜 ECAM처럼 쓰는 모드도 있음 (dw_pcie_config_ecam_iatu).
  • inbound: dma-ranges가 있으면 dw_pcie_prog_inbound_atu(type MEM, parent_bus_addr, pci_addr, size). 없을 때 RC의 inbound가 변환 없이 통과(pass-through)하는지는 IP 설정·버전에 따라 다름 추정 — 데이터시트로 확인할 항목.

2.5 ECAM (generic host, QEMU virt, ZynqMP)

  • config 주소 = ECAM_base + (bus << 20) + (dev << 15) + (fn << 12) + reg (PCIE_ECAM_BUS_SHIFT 20, PCIE_ECAM_DEVFN_SHIFT 12, include/linux/pci-ecam.h). 256 bus × 1 MiB = 256 MiB 창.
  • QEMU virt: reg = <0x40 0x10000000 0x00 0x10000000> → ECAM 0x40_1000_0000, 256 MiB → dmesg ECAM at [mem 0x4010000000-0x401fffffff] for [bus 00-ff] (실측 §3.1).
  • ZynqMP NWL: cfg 창 0x80_0000_0000, 256 MiB, 드라이버가 PCIE_ECAM_OFFSET(bus->number, devfn, where)로 바로 계산 — iATU 재프로그램 없음.

ranges = <0x1000000 0x00 0x00        0x00 0x3eff0000   0x00 0x10000

                 0x1800 0 0 1  &gic          0 0  0x00 0x06 0x04>; // dev3 INTA -> SPI 6
 엔트리 1개 = 10셀: child addr 3 + child pin 1 + parent phandle 1 + parent #address-cells(GIC=2) 2 + GIC irq spec 3

  • 실측 검증 (LP06 랩 2): edu를 root port(00:02.0) 아래 01:00.0에 두고 INTx 강제 → /proc/interrupts에 GIC-0 37 Level edu_lp06. 계산: bridge swizzle 후 pin = INTA, root port slot 2 → 0x1000 0 0 1 → SPI 5 → 32+5 = 37 ✓.

  1. 전원: regulator(슬롯 3.3V/12V) + SoC 내부 PD on. (PD가 꺼진 채 DBI를 읽으면 hang/SError.)
  2. refclk: SoC PLL 또는 외부 클럭 버퍼/클럭칩 (ZCU102는 si5341). PERST# 해제 전 ≥100 µs 안정.
  3. PHY init + controller reset 해제 + 클럭 enable: PHY PLL lock → PIPE clock이 나와야 컨트롤러 MAC 레지스터가 정상.

  8. iATU outbound/inbound 프로그램 (dw_pcie_setup_rc, 실제로는 link 전 단계에서 이미 함) → pci_host_probe 열거 → BAR 배정 → EP 드라이버 probe.
  • PERST#는 누가? RC 쪽(SoC GPIO 또는 컨트롤러 전용 핀)이 드라이버 코드로 제어. 슬롯/M.2 표준상 host가 구동. 일부 보드는 CPLD/PMIC가 제어하거나, 펌웨어(U-Boot)가 이미 풀어 둔 상태로 Linux에 넘어옴 → Linux가 다시 assert/deassert하면 장치가 리셋됨 (의도적이어야 함).

2.9 통합 디버그 체크리스트

증상 A: "Phy link never came up" (링크가 영원히 안 뜸)

  1. LTSSM 상태 레지스터 읽기 (DWC 0x728[5:0] 또는 vendor glue, debugfs ltssm_status): Detect.Quiet(0x0)에 머묾 → 상대 receiver 감지 실패: 장치 전원, PERST# 극성/타이밍, lane 배선, AC coupling cap. Polling(0x2–0x4) 반복 → refclk/SSC 불일치, bit lock 실패, lane polarity. Config(0x7–0xc) → lane 번호/폭 협상 실패(lane reversal). Recovery 루프 → SI/equalization 문제 → max-link-speed = <1>로 낮춰서 Gen1이면 뜨는지.
  2. PHY PLL lock 상태 비트, pipe clock 존재 여부.
  3. PERST# 핀을 오실로스코프로: 실제로 HIGH로 올라가는가? (DT 극성 실수 1순위)
  4. refclk 존재/주파수/SSC 설정 (common clock vs separate refclk).

증상 B: "link up인데 첫 config read에서 멈춘다 / SError / 0xFFFFFFFF만 나온다"

  1. config 창(reg-names "config")이 실제로 SoC 메모리 맵의 PCIe AXI slave 영역 안인가? DT 주소 오타 → 아무도 응답 안 하는 주소 → 인터커넥트 hang.
  2. iATU: CFG0 region이 enable 되었나 ("Outbound iATU is not being enabled" 로그), region_align 위반은 없나, viewport vs unroll 오검출, atu reg 주소 틀림. cpu_addr_fixup 필요한 SoC(인터커넥트가 상위 비트를 잘라먹음)인데 안 넣음.
  3. 타이밍: Gen3+인데 100 ms 대기 전에 config → CRS → 일부 컨트롤러는 CRS를 재시도로 처리 못 하고 hang/abort.
  4. 클럭 도메인: aclk_slv/aclk_dbi 꺼짐, PD 꺼짐 → 레지스터 접근 자체가 hang.
  5. 장치가 아직 리셋 중(PERST#가 너무 빨리 풀렸거나 다시 assert됨).
  6. 버스 에러를 abort 대신 0xFFFFFFFF로 바꾸는 컨트롤러 설정("error response" 모드)이 있는지 데이터시트 확인.

증상 C: "열거는 되는데 BAR 할당 실패 / 드라이버 probe -EINVAL·-ENOMEM"

  1. dmesg can't assign; no space → DT ranges 창이 너무 작음 / 32-bit BAR인데 64-bit 창만 있음 / prefetchable 64-bit BAR인데 prefetchable 창 없음. (§6.1에서 실제로 재현)
  2. pci=realloc, 창 확장, 브리지 창 정렬(1 MiB 단위) 고려.

증상 D: "같은 EP가 x86에선 되는데 우리 ARM SoC에선 안 됨"

의심 지점x86에서 숨겨지던 이유ARM에서 확인할 것

4. 꼬리 질문 체인

체인 1 — "How would you bring up the PCIe root complex on a new SoC under Linux?"

Q → 꼬리1 DT → 꼬리2 ranges → 꼬리3 config read hang (모범 답 펼치기)

Q. How would you bring up the PCIe root complex on a new SoC under Linux? "First I'd identify the controller IP — most SoCs use DesignWare, so there's a DWC core in drivers/pci/controller/dwc and I'd write or reuse a vendor glue. Then the hardware sequence: enable the power domain and slot regulators, start refclk, init the PHY, release controller resets, hold PERST# for at least 100 ms, enable the LTSSM and release PERST#, then poll for link-up. After link-up I check speed and width against the expected values, wait the extra 100 ms for Gen3 and above, and let pci_host_probe enumerate. I'd bring it up at Gen1 x1 first, then raise speed and width."

  • 한국어 핵심: IP 확인 → 전원/refclk/PHY/리셋 → PERST# 100 ms → LTSSM → link-up → 열거. Gen1부터 올린다.

꼬리1. What goes in the device tree? "Register regions with names — DBI, the config window, sometimes a separate ATU or app region. The ranges for I/O, 32-bit memory and 64-bit prefetchable memory; bus-range; num-lanes and max-link-speed; the controller interrupts plus interrupt-map for INTx and msi-map or msi-parent for MSI; iommu-map if there's an SMMU; and clocks, resets, PHYs, power domain, the slot supplies and the PERST# GPIO. I keep chip-fixed things in the SoC dtsi and board wiring — PERST# GPIO, regulators, actual lane count — in the board dts."

  • 한국어 핵심: reg/ranges/irq/msi/iommu/clk/reset/phy/pd/PERST#. SoC dtsi vs 보드 dts 분리.

꼬리2. What's the ranges property mapping? "Each entry maps a PCI address range to a CPU physical range. The first three cells are the PCI address — the top cell has the space code, 01 for I/O, 10 for 32-bit memory, 11 for 64-bit memory, and bit 30 for prefetchable — then the CPU address and the size. So 0x02000000 0 0xf0200000 0 0xf0200000 0 0xe00000 is a 14 MB non-prefetchable 32-bit window, identity-mapped. Linux turns these into host bridge windows, and on DesignWare each window becomes an outbound iATU region. If a window is too small, BAR assignment fails — I actually reproduced that in QEMU by shrinking the window, and got 'can't assign; no space'."

  • 한국어 핵심: phys.hi = 공간 코드(ss) + prefetch 비트. 창마다 outbound iATU 하나. 작으면 BAR 실패.

꼬리3. Link is up but the first config read hangs — what now? "Link-up only proves the physical and data link layers; a config read additionally needs the AXI path, the config window and the iATU. I'd check that the config window address in the DT is inside the controller's slave aperture, that the outbound iATU region for CFG0 actually got enabled and is aligned, and that the bus and DBI clocks and power domain are on. Then timing: for Gen3 and above, software must wait 100 ms after training before the first config request, otherwise the device may return CRS and some controllers don't handle that. I'd also make sure the controller is set to return all-ones on errors rather than raise an SError."

  • 한국어 핵심: link ≠ config 경로. config 창 주소 → iATU enable/정렬 → 클럭·PD → 100 ms/CRS → 에러 응답 모드.

꼬리4 (추가). How do you tell 'device not responding' from 'our host bridge is broken'? "I read the root port's own config space through DBI — that doesn't go over the link. If the root port's Link Status shows DL_Active and the right speed but reads to bus 1 fail, the problem is the outbound path or the device. Then an analyzer or the controller's debug counters tell me whether a CfgRd0 TLP actually went out and whether a completion came back."

  • 한국어 핵심: root port(DBI)는 링크 안 탐 → 경계 나누기. TLP가 나갔나/completion이 왔나.

체인 2 — "Who controls PERST# and why does the timing matter?"

Q → 꼬리1 refclk 전 해제 → 꼬리2 극성 → 꼬리3 펌웨어가 이미 풀어 둠 (모범 답 펼치기)

Q. Who controls PERST# and why does the timing matter? "The host drives PERST# — on an SoC that's usually a GPIO the controller driver toggles, described by reset-gpios. It tells the endpoint that power and reference clock are not yet valid. The CEM spec requires PERST# to stay asserted at least 100 ms after power is stable and at least 100 microseconds after refclk is stable. Linux encodes those as PCIE_T_PVPERL_MS and PCIE_T_PERST_CLK_US. When PERST# is released the endpoint starts its LTSSM, so if it's released early the device can start training with an unstable clock or before its own internal reset finished."

  • 한국어 핵심: host(GPIO, reset-gpios)가 구동. 전원 후 ≥100 ms, refclk 후 ≥100 µs.

꼬리1. What happens if PERST# is released before refclk is stable? "The endpoint's PLL can't lock or locks to a drifting clock, so receiver detect or bit lock fails. You typically see the LTSSM stuck in Detect or bouncing between Polling and Detect, or it trains at a degraded speed and later goes into Recovery loops with correctable errors. Some devices never recover until another PERST# cycle. On the scope I'd capture PERST#, refclk and the power rail together to check the sequence."

  • 한국어 핵심: PLL lock 실패 → Detect/Polling 반복, 저속 학습, Recovery 루프. 스코프로 3신호 동시 캡처.

꼬리2 (추가). The DT says GPIO_ACTIVE_HIGH for PERST#, but PERST# is active-low. Bug? "Not necessarily — it depends on the driver's convention. The Rockchip DWC glue writes 0 to assert and 1 to release, so it pairs with GPIO_ACTIVE_HIGH in the board DT, while the Qualcomm driver treats 1 as 'assert' and expects GPIO_ACTIVE_LOW. Mixing them inverts the reset, and the device either stays in reset forever or never sees a reset pulse. So I check the driver code and then confirm on a scope."

  • 한국어 핵심: DT 극성 플래그 × 드라이버의 0/1 의미가 짝. Rockchip(0=assert) vs Qcom(1=assert). 스코프로 확정.

꼬리3 (추가). U-Boot already brought the link up. Should Linux reset it again? "It's a choice. Re-asserting PERST# gives a known state and exercises the full sequence, which is what I'd want in validation. But some designs keep the link to avoid re-training time or because a boot device sits behind it; then the driver checks link-up first — DWC's host init only calls start_link if the link isn't already up. In validation I'd test both paths, because warm boot with an already-trained link is a different code path."

  • 한국어 핵심: DWC는 이미 link up이면 start_link 생략. 검증은 두 경로 다.

체인 3 — "Same endpoint works on an x86 host but not on our ARM SoC. Why?"

Q → 꼬리1 coherency → 꼬리2 MSI 경로 → 꼬리3 DMA mask (모범 답 펼치기)

Q. Same endpoint works on an x86 host but not on our ARM SoC. Why? "x86 firmware hides a lot: DMA is cache-coherent, RAM starts at zero, MSI goes to a fixed address, and the firmware already sized the windows. On an ARM SoC I'd look at five things: cache coherency and whether the DT says dma-coherent correctly; the inbound window and IOMMU stream-ID mapping for DMA; the MSI path through msi-map to the GIC ITS; the DMA mask versus where RAM actually is; and the ranges windows for 64-bit BARs. The symptom usually tells me which — corrupted data points to coherency, timeouts with no interrupt point to MSI, and SMMU faults point to the IOMMU map."

  • 한국어 핵심: coherency · inbound/IOMMU · MSI(ITS) · DMA mask · 64-bit 창. 증상으로 분류.

꼬리1. How does cache coherency break it? "If the SoC's PCIe master isn't hardware-coherent, the CPU may read stale cache lines after the device DMA'd new data, or the device reads memory before the CPU's writes were flushed. The DMA API handles it with cache maintenance in dma_map and dma_sync, but only if the driver uses the API and the DT doesn't wrongly claim dma-coherent. A wrong dma-coherent flag shows up as intermittent data corruption that disappears when you add prints."

  • 한국어 핵심: non-coherent면 DMA API가 flush/invalidate. 잘못된 dma-coherent = 간헐적 데이터 깨짐.

꼬리2. MSI enabled but no interrupts arrive on the ARM board. "MSI is just a memory write, so I follow the write: the device must have Bus Master enabled, the MSI address programmed in its capability must be the ITS doorbell or the controller's MSI target, the inbound path must not block or translate that address, and msi-map must give the ITS the right DeviceID for this RID. With an analyzer I can see whether the MWr TLP left the device; if it did, it's on the SoC side. Falling back to INTx is a quick way to split the problem."

  • 한국어 핵심: MSI = MWr. Bus Master → MSI 주소 → inbound → DeviceID 매핑. INTx로 바꿔서 분리.

꼬리3 (추가). Why would a 32-bit-DMA device fail only on ARM? "On many ARM SoCs, RAM starts above 1 GB or even above 4 GB, so a device with a 32-bit or smaller DMA mask can't reach most memory directly. The kernel either bounces through SWIOTLB, uses the IOMMU to remap into the device's range, or fails dma_set_mask. I reproduced the failure in QEMU: QEMU virt RAM starts at 0x4000_0000, and asking for a 28-bit mask returned -EIO."

  • 한국어 핵심: ARM RAM은 높은 주소 → 좁은 DMA mask 실패/bounce. 실측: 28-bit → -5.

체인 4 (추가) — "Explain the iATU. How does a config read become a Type 0 or Type 1 TLP?"

Q → 꼬리1 Type0/1 → 꼬리2 region 부족 → 꼬리3 ECAM과 차이 (모범 답 펼치기)

Q. Explain the iATU. "The iATU is DesignWare's address translation table. Each outbound region has a base, a limit, a target and a type: CPU accesses that hit the region become PCIe requests of that type with the address rebased to the target. Memory windows from ranges become MEM regions; I/O becomes an IO region. Inbound regions do the reverse for device DMA, from dma-ranges. Regions have alignment and size limits and a fixed count, which the driver prints at boot."

  • 한국어 핵심: region = base/limit/target/type. outbound(ranges), inbound(dma-ranges). 수·정렬 제한.

꼬리1. How are Type 0 vs Type 1 config requests generated? "For config, the driver reprograms one outbound region on every access: type CFG0 or CFG1, and the target holds bus, device and function in bits 31:24, 23:19, 18:16. If the target bus is directly below the root port it uses CFG0, so the device on the link answers; for deeper buses it uses CFG1 so switches forward it. The root port's own registers are read through DBI, not over the link."

  • 한국어 핵심: 매 접근 재프로그램, target에 BDF, 바로 아래 = CFG0, 더 아래 = CFG1, 자기 자신 = DBI.

꼬리2. What if there aren't enough iATU regions? "The driver warns 'Ranges exceed outbound iATU size' and drops windows, and I/O may share the config region. The fix is to merge windows in the DT or drop the I/O window, which modern devices rarely need."

  • 한국어 핵심: 창 합치기/I/O 창 제거.

꼬리3. How is that different from ECAM? "ECAM maps the whole config space linearly — bus shifted by 20, device-function by 12 — so each device has a fixed 4 KB slot in a 256 MB window and no reprogramming is needed. It's simpler and lock-free but costs address space. QEMU virt and ZynqMP's PS controller use ECAM; newer DesignWare can emulate it with a shift mode."

  • 한국어 핵심: ECAM = 선형 256 MiB, 재프로그램 없음.

체인 5 (추가) — "Link trains at Gen1 but not at Gen3. What do you do from the integration side?"

Q → 꼬리1 DT로 무엇을 → 꼬리2 검증 계획 (모범 답 펼치기)

Q. Link trains at Gen1 but not at Gen3. "Gen1 and Gen2 use fixed de-emphasis, Gen3 adds 128b/130b and equalization, so failing only at Gen3 usually points to signal integrity or equalization presets. I'd read the LTSSM state and Link Status 2 equalization bits, check lane-by-lane error counters, and try different TX presets — the DT now has eq-presets-8gts for that. Then compare with a known-good board and check channel loss against the budget."

  • 한국어 핵심: Gen3 = EQ. LTSSM/EQ 비트/lane 카운터 → preset 바꿔 보기 (eq-presets-8gts).

꼬리1. What can you change in DT for bring-up? "max-link-speed to cap the speed, num-lanes to test a single lane, equalization presets, and ASPM-disable properties to remove power-state transitions while debugging."

  • 한국어 핵심: speed cap, lane 줄이기, EQ preset, ASPM 끄기.

꼬리2. How would you turn this into a validation plan? "A matrix: speed Gen1 to max, width x1 to max, cold boot versus warm reset versus PERST# toggle, temperature and voltage corners, many iterations each, logging link-up time, final speed and width, and AER correctable counts. Any run that lands at a lower speed or width is a failure even if the link is up."

  • 한국어 핵심: 속도×폭×리셋 종류×코너×반복, downtrain도 실패로. (LP14)

6.3 [의사코드] 최소 host controller bring-up (DWC 스타일, 실제 드라이버 아님)

/* [의사코드] — 컴파일/실행 안 함. 이름은 6.18 DWC API를 따랐지만 구조 설명용. */
static int mysoc_pcie_probe(struct platform_device *pdev)
{
    struct mysoc_pcie *p = ...;                     /* glue private */
    struct dw_pcie *pci = &p->pci;

    /* 0. 리소스: reg-names "dbi","apb","config" / clocks / resets / phy / reset-gpios */
    p->apb  = devm_platform_ioremap_resource_byname(pdev, "apb");
    p->perst = devm_gpiod_get(&pdev->dev, "reset", GPIOD_OUT_LOW);  /* 극성 규칙은 DT 플래그와 짝 */
    p->phy  = devm_phy_get(&pdev->dev, "pcie-phy");

    /* 1. 전원 */
    regulator_enable(p->vpcie3v3);                  /* 슬롯 3.3V */
    pm_runtime_enable(&pdev->dev); pm_runtime_get_sync(&pdev->dev);   /* power-domains */

    /* 2. 리셋 잡은 상태로 PHY/클럭 */
    reset_control_assert(p->rst);
    phy_init(p->phy); phy_power_on(p->phy);         /* SerDes PLL lock, refclk 출력(내부 refclk인 경우) */
    reset_control_deassert(p->rst);
    clk_bulk_prepare_enable(p->num_clks, p->clks);  /* aclk_mst/slv/dbi, pclk, aux, pipe */

    /* 3. DWC 코어에 맡김: get_resources → iATU detect → setup_rc → start_link → wait → pci_host_probe */
    pci->ops = &mysoc_dw_ops;                       /* .link_up / .start_link / .get_ltssm */
    pci->pp.ops = &mysoc_host_ops;                  /* .init */
    return dw_pcie_host_init(&pci->pp);
}

static int mysoc_start_link(struct dw_pcie *pci)    /* dw_pcie_ops.start_link */
{
    struct mysoc_pcie *p = to_mysoc(pci);
    gpiod_set_value_cansleep(p->perst, 1);          /* PERST# assert (논리 1 = assert 규칙이라고 가정) */
    writel(LTSSM_ENABLE, p->apb + APP_CTRL);        /* vendor glue 레지스터 [가상 이름] */
    msleep(PCIE_T_PVPERL_MS);                       /* 100 ms: 전원/refclk 안정 보장 */
    gpiod_set_value_cansleep(p->perst, 0);          /* PERST# deassert → EP가 LTSSM 시작 */
    return 0;                                       /* 이후 코어가 dw_pcie_wait_for_link(): 10 × 90 ms */
}

static bool mysoc_link_up(struct dw_pcie *pci)      /* dw_pcie_ops.link_up */
{
    u32 v = readl(to_mysoc(pci)->apb + APP_STATUS); /* [가상 이름] */
    return (v & PHY_LINKUP) && (v & DL_ACTIVE);
}

7. 자주 틀리는 것

  1. "link up = 다 됐다" — link up은 PHY/DLL까지. config 경로(AXI 창 + iATU + 클럭/PD)는 별개. 첫 config read hang은 대부분 이쪽.
  2. PERST# 극성: DT 플래그(GPIO_ACTIVE_LOW/HIGH)와 드라이버의 gpiod_set_value(…, 0/1) 의미가 짝. Rockchip glue는 0=assert(ACTIVE_HIGH와 짝), Qualcomm은 1=assert(ACTIVE_LOW와 짝). 섞으면 영원히 리셋 or 리셋 펄스 없음.
  3. ranges 64-bit 창을 non-prefetchable(0x03000000)로: 루트 버스에선 동작하지만 브리지 NP 창은 32-bit → 스위치 너머 64-bit NP BAR는 못 감. 관례는 0x43000000. (QEMU virt에서 실제로 경고 나옴)
  4. CPU 주소 ≠ PCI 주소일 수 있음: ranges가 1:1이 아닐 때 BAR 레지스터에 써진 값(PCI 주소)과 /proc/iomem·sysfs resource의 주소(CPU 주소)가 다르다. lspci -v의 Memory at ...은 기본적으로 커널이 본 주소(CPU 쪽), lspci -b(bus-centric)는 카드가 버스에서 보는 주소 (LP13). 애널라이저 TLP 주소와 비교할 땐 -b 쪽.
  5. Gen3+ 100 ms 규칙은 "PERST# 해제 후"가 아니라 "링크 학습 완료 후" 100 ms (5 GT/s 초과 포트). 5 GT/s 이하는 Conventional Reset 종료 후 100 ms.
  6. num-lanes를 SoC dtsi 값 그대로: 보드가 x2로 배선됐는데 x4로 두면 학습은 x2로 되거나 lane 검출 지연. 보드 dts에서 override (Rock 5B+ 실제 예).
  7. dma-coherent를 "있으면 빠르니까" 넣기: 하드웨어가 coherent가 아니면 간헐적 데이터 깨짐. 반대로 빼면 느려질 뿐 정확함.
  8. msi-map 길이/베이스 실수: RID 범위가 bus-range보다 작으면 일부 버스의 MSI가 매핑 안 됨 (RK3588은 16 bus × 256 = 0x1000으로 정확히 맞춤).
  9. PD/클럭 꺼진 상태에서 devmem으로 DBI 읽기 → 시스템 hang. 디버그 도구 자체가 버스를 멈출 수 있다.
  10. QEMU의 LnkSta 값(16 GT/s x32)을 실제 학습 결과로 믿기 — 에뮬레이션 기본값.
