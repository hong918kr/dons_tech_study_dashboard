0. TL;DR

  • 이 노트로 답할 수 있는 것: "DDR training이 실패한다 / 고온에서만 / 10장 중 2장만 실패한다 — 어떻게 디버그?", "메모리 테스트를 짜 봐라 (data bus · address bus · March C-)", "write leveling이 뭐고 왜 필요?", "ECC는 어떻게 검증?".
  • 외울 것 ①: 3층 구조 — memory controller(디지털: 명령 스케줄링·refresh·ECC·주소 매핑) ↔ DFI ↔ PHY(아날로그: IO·delay line·VREF·training 엔진) ↔ PCB ↔ DRAM. training은 PHY가 "보드 배선 지연"을 측정해서 지연값을 맞추는 과정.
  • 외울 것 ②: init/training 순서 — 전원·클럭 안정 → RESET_n 해제 → CKE → ZQ 캘리브레이션(임피던스) → MR(mode register) 쓰기 → CA training(LPDDR4/DDR5) → write leveling(CK vs DQS) → read gate(DQS 언제 열까) → read eye/deskew → write eye/deskew → VREF training(2D) → 마지막 memtest. 어느 단계가 실패했는지 = 어느 신호 그룹이 문제인지.
  • 외울 것 ③: 테스트 순서 = 진단 순서 — data bus(walking 1s, 한 주소) → address bus(2의 거듭제곱 주소) → device/March C-(모든 셀). 순서를 어기면 오진한다: 이 노트의 실측 결과에서 data line short와 "칩 없음"이 address test에서는 "A0 주소선 고장"으로 잘못 보였다 (§6).
  • March C- = {⇕(w0); ⇑(r0,w1); ⇑(r1,w0); ⇓(r0,w1); ⇓(r1,w0); ⇕(r0)}, 10N, SAF·TF·AF·CFin·CFid·CFst 검출. 단, word 단위 메모리에서 0/1 배경만 쓰면 같은 word 안의 비트끼리 붙은 고장은 못 본다 → data background 6개로 반복하면 잡힘 (실측).
  • 고온 실패 = 마진 부족 + refresh(고온에서 셀 누설↑ → refresh 2배 필요) + VREF/임피던스 drift. 보드 일부만 실패 = swap test(DRAM/SoC/보드 중 무엇을 따라가나).
  • 30초 영어 답 (headline: "DDR training fails on a new board"): "First I make sure it's really a DDR problem: rails including VDDQ and VPP are in spec and quiet, the reference clock is clean, reset and CKE timing are right, and the controller config matches the actual part — type, density, speed, and the board's byte and bit swizzle. Then I read which training step failed and on which byte lane, because that localizes the problem: CA training points at the clock and command bus, write leveling at the CK-to-DQS relationship on one lane, read gate at latency config or DQS, and a narrow eye on a few bits at routing or solder on those balls. I drop the frequency to see if it's marginal or hard, compare lanes and boards, and only after training passes do I run the bus tests and March C- with caches off."

1. 🔰 처음 보는 사람을 위한 설명

1.1 DRAM이 뭐고 왜 bring-up에서 제일 자주 막히나

비유: DDR = SoC(사무실) 옆에 붙은 거대한 창고. 창고에는 수십억 개 사물함(cell)이 있고, 사무실과 창고 사이에는 수십 가닥의 컨베이어 벨트(데이터선 DQ) 와 주문서 벨트(명령/주소선 CA) 가 깔려 있다. 문제는 이 벨트가 초당 수십억 번 물건을 나른다는 것. 벨트마다 길이가 몇 mm씩 다르면 물건이 도착하는 시점이 조금씩 어긋나고, 너무 빨라서 그 "조금"이 치명적이다. 그래서 창고를 쓰기 전에 매번 "벨트마다 언제 물건을 내려놓고 언제 집어야 하는지" 시험 운행(training) 을 해서 타이밍표를 만든다. 그다음 창고 사물함이 진짜로 물건을 잘 보관하는지 전수 검사(memtest) 를 한다.

  • 왜 bring-up에서 자주 막히나:
    • SoC 안 SRAM은 칩 내부라서 "그냥 된다". DDR은 칩 밖 PCB 배선 + 다른 회사 칩(DRAM) 이 끼어 있어서 보드마다·온도마다·전압마다 결과가 달라진다.
    • 설정값(타이밍·임피던스·배선 지연·비트 순서)이 수백 개이고 하나만 틀려도 "가끔" 깨진다 — 가장 디버그하기 싫은 종류.
    • DDR이 안 되면 그 위의 모든 것(U-Boot, Linux, NPU 모델 로딩)이 안 된다. 그래서 bring-up FW는 SRAM에서 돌면서 DDR을 초기화한다 (→ BV08).

1.2 세 조각: controller · PHY · DRAM

비유: controller = 창고 관리 사무실(어떤 주문을 먼저 처리할지, 언제 청소(refresh)할지 결정), PHY = 하역장 작업반(벨트 속도·타이밍을 실제로 맞추는 손), DRAM = 창고 건물.

  SoC 내부                                                    PCB             DRAM 패키지
 ┌──────────────────────────────┐   DFI    ┌──────────────────┐   배선   ┌──────────────────────┐
 │ Memory Controller (디지털)     │ (표준    │ DDR PHY (아날로그) │ ───────▶ │ DRAM die             │

        │ (tRCD, tRP, CL, tRFC …)             │ training 결과가 여기 저장        │ (CL, ODT, VREF …)
  • Controller: "무엇을 언제" — 읽기/쓰기 요청을 DRAM 명령으로 바꾸고, 타이밍 규칙(tRCD 등)을 지키고, 주기적으로 refresh를 넣는다. ECC도 보통 여기.
  • PHY: "정확히 몇 피코초에" — 신호를 실제로 내보내고 받는 아날로그 회로. 비트마다 지연 탭(delay tap) 이 있어서 training으로 찾은 값을 넣는다. 최신 PHY는 training 알고리즘을 PHY 안의 작은 마이크로컨트롤러 펌웨어로 돌린다 (예: NXP i.MX8M은 U-Boot SPL이 lpddr4_pmu_train_1d/2d imem/dmem 펌웨어 바이너리를 PHY에 올린다 확인됨9).
  • DFI (DDR PHY Interface): controller와 PHY 사이의 업계 표준 인터페이스 — 그래서 controller IP와 PHY IP를 다른 회사 것으로 조합할 수 있다.
  • DRAM: 셀 배열 + MR(mode register) — CL(읽기 지연), 버스트 길이, ODT, 드라이브 세기, VREF 등을 controller가 MR 쓰기 명령으로 설정.

1.3 주소: channel · rank · bank · row · column

비유: 창고 단지의 주소 체계. channel = 독립된 출입 도로(도로마다 따로 트럭이 다님), rank = 같은 도로를 쓰는 창고 동(한 번에 한 동만 응답), bank = 동 안의 독립된 층(층마다 따로 셔터를 열어 둘 수 있음), row = 층의 한 통로(통로 셔터를 열어야 물건을 꺼낼 수 있음 = ACTIVATE), column = 통로 안 선반 칸.

 CPU 물리주소 0x8_1234_5678 ──(controller 주소 매핑)──▶ ch1 · rank0 · BG2 · bank1 · row 0x1A2B · col 0x3C
                                                       │      │      │       │        │        │
 channel: 독립 버스(LPDDR4는 x16 채널) ─────────────────┘      │      │       │        │        │
 rank:    같은 버스, CS로 선택 ───────────────────────────────┘      │       │        │        │
 bank group / bank: 독립 셀 배열 (각자 row buffer 1개) ─────────────┴───────┘        │        │
 row:     ACT로 row buffer에 "펼침" (수 KB 페이지) ─────────────────────────────────┘        │
 column:  펼친 row에서 RD/WR로 burst 단위 접근 ──────────────────────────────────────────────┘

 접근 한 번:  ACT(row 열기) ─tRCD─▶ RD(col) ─CL─▶ 데이터 burst ··· PRE(row 닫기) ─tRP─▶ 다음 ACT
  • 같은 bank의 다른 row를 연달아 접근하면 PRE→ACT를 매번 해야 해서 느리다(row miss). 메모리 테스트가 주소 순서를 바꾸면 이 경로를 일부러 자극할 수 있다.
  • 주소 매핑 설정이 틀리면(예: DRAM 밀도를 8Gb로 설정했는데 실제 16Gb) → training은 통과하고 memtest에서 address aliasing 으로 보인다. "training 통과 + 특정 주소 비트 패턴에서만 실패"의 1순위 가설.

1.4 왜 training이 필요한가 — "eye"

비유: 데이터선 위의 비트는 회전문처럼 일정 시간만 "열려 있는(유효한)" 구간이 있다. 수신기는 그 구간 한가운데에서 사진을 찍어야(샘플링) 정확하다. 배선 길이·온도·전압에 따라 문이 열리는 시점이 비트마다 다르므로, 각 비트마다 문이 언제 열리고 닫히는지 직접 재서 가운데를 찾는 것이 training.

 한 비트(DQ)의 "eye" (여러 번 겹쳐 그린 파형)       DQS(스트로브) = "지금 찍어라" 신호

   전압 ▲      ┌───────────────────┐               DQS  ──┐   ┌───┐   ┌───
   VDDQ │ ╲    │                   │    ╱                  └───┘   └───┘
        │  ╲   │   EYE (안전 구간)   │   ╱                     ▲ 원래 엣지
   VREF ┼───╳──┼─────────●─────────┼──╳───  ← 판정 기준      ▲ training으로 옮긴 위치 = eye 가운데
        │  ╱   │      ↑중앙 샘플      │   ╲
        │ ╱    │                   │    ╲
        └──────┴───────────────────┴──────▶ 시간
              left edge         right edge
              ◀──── eye 폭 (timing margin) ────▶ ,  위아래 = eye 높이 (voltage margin)
  • timing training(1D): 지연 탭을 쓸어서 left/right edge를 찾고 가운데에 놓는다.
  • VREF training(2D): 판정 기준 전압도 같이 쓸어서 가로×세로 둘 다 가장 넓은 점을 찾는다.
  • 결과 레지스터의 eye 폭/높이 = margin. 이걸 보드끼리·온도별로 비교하는 것이 characterization (→ BV12).

1.5 fly-by와 write leveling — 그림 한 장

비유: 택배 트럭(CK·명령)이 한 줄로 늘어선 집 4채를 차례로 돈다(fly-by). 첫 집은 일찍, 마지막 집은 늦게 도착한다. 그런데 소포(DQ/DQS)는 집마다 각자 직통 도로로 간다. 그러면 집마다 "트럭 도착 시각"과 "소포 도착 시각"의 차이가 다르다 → 집마다 소포 출발 시각을 다르게 조정해야 한다 = write leveling.

            CK/CMD/ADDR: fly-by (데이지 체인) ─────────────────────────────────▶ 종단(VTT)
 SoC ──┬──────────────┬──────────────┬──────────────┬──────────────┐
       │ +0 ps        │ +150 ps      │ +300 ps      │ +450 ps      │  ← CK 도착 지연 (예시 숫자)
    ┌──▼──┐        ┌──▼──┐        ┌──▼──┐        ┌──▼──┐
    │DRAM0│        │DRAM1│        │DRAM2│        │DRAM3│
    └──▲──┘        └──▲──┘        └──▲──┘        └──▲──┘
       │ DQ/DQS 바이트 lane 0~3 = 각자 point-to-point (거의 같은 길이)
 SoC ──┴──────────────┴──────────────┴──────────────┘

 write leveling: DRAM이 "DQS 상승 엣지 순간의 CK 값"을 DQ로 되돌려 줌 → controller가 DQS 지연을
                 0→1 바뀌는 지점까지 밀어서 lane마다 CK와 정렬 (DDR 스펙 tDQSS 만족)
  • DDR3/DDR4 모듈·다칩 보드는 CK/CA를 fly-by로 깐다(분기 stub이 신호를 망치기 때문). 그래서 write leveling이 필수 확인됨45.
  • LPDDR4/5는 보통 SoC 옆 1~2개 패키지에 point-to-point라 fly-by 스큐는 작지만, 그래도 CK↔DQS(LPDDR5는 WCK2CK leveling) 정렬 단계가 있다 확인됨6.

1.6 메모리 테스트는 왜 여러 개인가

비유: 창고 점검을 세 단계로 한다. ① 벨트 자체 점검(data bus): 컨베이어 한 줄에 물건을 하나씩 올려 32개 벨트가 각각 움직이는지 — 사물함 하나만 써도 됨. ② 주소 표지판 점검(address bus): "3번 통로"라고 써 붙인 표지판이 진짜 3번으로 가는지 — 1, 2, 4, 8… 번지만 확인하면 표지판 전선 하나하나를 다 확인한 셈. ③ 사물함 전수 검사(device/March): 모든 사물함이 0과 1을 둘 다 보관하고, 옆 사물함을 건드려도 안 바뀌는지.

순서가 중요한 이유: 벨트가 고장이면 표지판 점검 결과도 엉터리, 표지판이 고장이면 사물함 검사 결과가 "사물함 불량"처럼 보이지만 실제로는 배선 문제.

2.4 ECC — SECDED · 카운터 · 주입 · scrub

비유: 택배 상자마다 검수 스티커(check bits) 를 붙여 보낸다. 받는 쪽은 스티커로 "물건 하나가 바뀌었으면 원래대로 고치고(SEC), 둘이 바뀌었으면 고칠 순 없지만 알아챈다(DED)".

  • SECDED: 64 data bit + 8 check bit (Hamming + 전체 패리티) → 1비트 정정, 2비트 검출. DIMM의 x72 구조가 이것 확인됨7.
  • LPDDR에는 여분 폭이 없다 → controller가 같은 DRAM의 일부 영역에 ECC를 저장하는 inline ECC (용량·대역폭 일부 희생) 확인됨: Synopsys가 inline ECC를 별도 기능으로 언급6. 자동차 기능 안전(ISO 26262) 때문에 자동차 SoC는 LPDDR + inline ECC 조합이 흔하다 추정.
  • ECC 종류 구분 (면접 함정): on-die ECC(DDR5, DRAM 내부, 밖에서 안 보임) ≠ link ECC(LPDDR5, 전송 오류만) ≠ system/inline ECC(controller, end-to-end). on-die ECC만 있으면 버스 오류는 못 잡는다 확인됨7.
  • ECC init(scrub): ECC 메모리는 쓰기 전 check bit가 쓰레기 → 처음 읽으면 UE. 그래서 부트 초기에 전체를 한 번 써서 초기화. Zynq MPSoC는 FSBL이 이걸 한다 확인됨12. SPL에서 ECC를 켰는데 init 순서를 잘못 잡아 문제가 된 사례도 U-Boot 메일링 리스트에 있다 확인됨12.
  • 카운터와 보고: controller의 CE/UE 카운트 레지스터 + 오류 주소/syndrome 레지스터 + 인터럽트. 예: Synopsys DDRC(ZynqMP)의 Linux synopsys_edac 드라이버는 ECC_ERRCNT(CE/UE 수), ECC_CEADDR0/1·ECC_CSYND0(CE 위치·syndrome)을 읽는다 확인됨13.
  • 주입(injection): 같은 드라이버가 CONFIG_EDAC_DEBUG일 때 sysfs inject_data_error(주소 지정 → ECC_POISON0/1 레지스터 설정), inject_data_poison("CE" 또는 UE 선택)을 제공 확인됨13. 주입 방식 일반: (a) controller의 poison/inject 레지스터, (b) ECC 끄고 데이터만 바꿔 쓴 뒤 ECC 켜고 읽기(check bit 불일치 유발), (c) 1비트/2비트 각각.
  • Patrol scrub: 백그라운드로 전체 메모리를 읽어 CE를 미리 고쳐 쓰기 → 1비트 오류가 쌓여 2비트(UE)가 되기 전에 제거. Linux EDAC sdram_scrub_rate로 노출 확인됨14.

2.5 Refresh와 온도

  • DRAM 셀은 커패시터 → 전하가 샌다. 온도가 높을수록 빨리 샌다 → refresh를 더 자주.
  • DDR4: 8192번 REF / 64 ms → tREFI 7.8 µs, 85 °C 초과(확장 온도)에서는 3.9 µs(2× refresh) — DDR 세대 공통 관행 (DDR4 데이터시트 온도 표로 재확인 필요 추정); Intel도 고온 범위에서는 tREFI를 데이터시트 값으로 줄이라고 함 확인됨15.
  • LPDDR4: refresh window 32 ms, tREFI ≈ 3.9 µs, MR4가 DRAM 온도/필요 refresh 배율(0.5×~4×)을 알려 준다 확인됨15 → controller(또는 SW)가 MR4를 주기적으로 읽어 refresh 간격을 바꿔야 한다. TI 플랫폼 답변: HW는 MR4를 polling만 하고 간격 변경은 SW 몫 확인됨15.
  • 실제 에라타: NXP i.MX8MM ERR050805 — LPDDR4가 85 °C 이상에서 시작하면 controller의 자동 derating이 실패할 수 있음 → U-Boot는 자동 derating을 끄고 고정 2× refresh 적용 확인됨15. 자동차(AEC-Q100 Grade 2 = −40~105 °C, Grade 1 = −40~125 °C) 보드에서 그대로 나올 법한 문제.
  • 고온에서 같이 나빠지는 것: VREF/임피던스 drift(→ 주기적 ZQ cal·retraining), 타이밍 마진 축소, PDN 노이즈 증가.

2.6 메모리 테스트 알고리즘 (정밀)

2.6.1 Data bus test — walking 1s (Barr)

  • 한 주소에 1<<0, 1<<1, …, 1<<31을 차례로 쓰고 바로 읽는다. n비트 버스에 n개 패턴이면 각 데이터선이 다른 선과 독립적으로 0/1이 되는지 확인 (2ⁿ 불필요) 확인됨2.
  • 여기서는 "쓰고 바로 읽기"가 괜찮다 — 목표가 배선이지 칩 존재가 아니므로. 대신 칩이 없어도 통과할 수 있다 (버스 커패시턴스가 방금 쓴 값을 잠깐 붙잡아 둠) 확인됨2 → 실측 F12에서 DBUS 통과 확인.
  • 버스가 여러 칩으로 나뉘면(byte lane마다 다른 DRAM) 칩마다 한 주소씩 돌려야 한다 확인됨2. 실패 패턴의 set bit = 고장 데이터선; exp ^ act = 고장 비트 마스크.

2.6.2 Address bus test — power-of-two offsets (Barr)

  • 원리: 주소선 하나가 고장 나면 그 비트만 다른 두 주소가 같은 셀을 가리킨다(aliasing). 주소선은 log₂N개뿐이므로 offset 0, 1, 2, 4, 8, …만 보면 모든 주소선을 한 번씩 토글한 셈 → O(log N) 접근 확인됨2.
  • 알고리즘 확인됨23:
    1. 모든 power-of-two offset에 PATTERN(0xAAAAAAAA) 쓰기.
    2. stuck-high 검사: offset 0(base)에 ANTI(0x55555555) 쓰기 → 모든 power-of-two offset이 여전히 PATTERN이어야 함. base를 PATTERN으로 복구.
    3. stuck-low / short 검사: 각 offset t에 ANTI를 쓰고 → base와 t가 아닌 모든 offset이 PATTERN인지 확인 → t 복구.
  • 매 쓰기 후 다른 모든 위치를 확인해야 하는 이유: 쓰기 하나가 다른 곳을 몰래 덮어쓸 수 있기 때문 확인됨2.
  • 실측으로 본 미묘한 점 (§6 결과): base가 0 정렬이면 stuck-low 주소선(A4)도 offset 16이 base와 겹치므로 step 2에서 먼저 걸린다(F08 s2:A4). step 3이 꼭 필요한 건 base와는 안 겹치고 두 offset끼리만 겹치는 경우 — wired-OR short(A2·A3 → 4와 8이 둘 다 12로)(F11 s3:A2). Barr 주석의 "step 2 = stuck high, step 3 = stuck low/shorted"는 의도이고, 실제 어느 step에서 걸리는지는 고장 모양에 달렸다.
  • 한계 확인됨2: 칩 선택용 상위 주소선(테스트 범위 내에서 고정)과 버스 폭 때문에 고정되는 하위 비트는 테스트 불가. 예: 32-bit 주소 공간에서 128 KB 블록은 17비트만 검사. base는 테스트 비트가 0이어야 한다.
  • DDR에서는 CPU 주소 비트 → bank/row/column 비트로 매핑되므로, "CPU 주소 A4 고장"이 실제로는 "column 비트 C1" 같은 다른 이름일 수 있다. 실패 주소를 controller 매핑으로 역변환해서 보고하면 HW 팀이 바로 핀을 찾는다.

2.6.3 Device test — increment / invert (Barr)

  • pass 1: 모든 주소에 증가값(addr+1) 쓰기 → pass 2: 확인 + 비트 반전값 쓰기 → pass 3: 반전값 확인. 모든 비트가 0과 1을 한 번씩 보관하는지, 주소마다 값이 달라서 칩 없음·aliasing도 잡힘 확인됨2. 4N 접근(실측).
  • 한계: 접근 순서가 단방향이고 배경 패턴이 주소값이라 coupling fault 보장이 없다 → 실측 F05(CFid) 놓침.

    • 각 원소는 "읽고 나서 쓴다" → 앞 원소가 남긴 값이 그대로인지 먼저 확인. 이웃 셀 쓰기로 값이 바뀌었으면(coupling) 여기서 보인다.

    • M5 ⇕(r0) → M4 마지막 쓰기 이후 생긴 고장을 확인 (빼먹으면 9N, 커버리지 구멍).
    • AF 검출: 주소 디코더 고장(두 주소 → 한 셀, 또는 셀에 접근 불가)은 "w1 했는데 다른 주소에서 1이 보임"으로 걸린다(실측 F08~F11 모두 M1).

2.6.6 캐시 · MMU · DMA · 실행 위치

  • 캐시: 캐시 켠 채 작은 영역을 테스트하면 캐시를 테스트하게 된다. bring-up 셀 테스트는 해당 영역을 Device / Normal Non-cacheable로 매핑하거나 캐시 off. 캐시 켠 테스트는 별도 목적(burst·line fill/evict 경로, 대역폭 + 무결성) — 이때는 캐시보다 훨씬 큰 범위를 써야 DRAM까지 간다. memtest86도 캐시 끄기 옵션 제공 확인됨17.
  • volatile: 테스트 포인터는 volatile uint32_t * — 없으면 컴파일러가 "방금 쓴 값"을 그대로 돌려주는 최적화로 읽기를 없앤다.
  • write buffer / 순서: Device 메모리 속성이면 순서 보장. Normal non-cacheable이면 쓰기 뒤 DSB 후 읽기가 안전 추정 — 아키텍처별 확인.
  • DMA: (a) CPU 루프보다 수십 배 빠른 fill/compare, (b) 여러 master 동시 트래픽으로 controller 스케줄링·대역폭 스트레스, (c) 캐시 일관성 버그(clean/invalidate 누락)는 "메모리 고장처럼" 보인다 → 먼저 non-cacheable 버퍼로 배제 (→ LP08).
  • 실행 위치: 테스트 코드·스택이 테스트 영역 안에 있으면 자기 자신을 지운다. DDR 테스트는 SRAM/TCM에서 실행, 또는 DDR을 반으로 나눠 A에서 돌며 B 테스트 → 코드 이동 → A 테스트. Barr: C 스택이 RAM을 필요로 하므로 경우에 따라 어셈블리 구현 확인됨2.
  • 규모 계산: 8 GB를 10N(64-bit 접근, 읽기+쓰기 각 5회) → 약 80 GB 트래픽. 실효 10 GB/s면 ≈ 8 s지만 uncached 단일 코어 루프는 그보다 훨씬 느리다 추정 → bring-up은 bus test + 샘플 영역 March, 전체 March·bit fade·hammer는 야간 회귀/SLT로.

4. 꼬리 질문 체인

Chain 1 — "DDR training fails on a new board. How do you debug?"

Q → 꼬리1 → 꼬리2 → 꼬리3 (답 펼치기)

Q. DDR training fails on a new board. How do you debug? "I treat it bottom-up. Before blaming training I confirm the DDR rails are in spec and sequenced, ripple is acceptable at the DRAM, the PHY PLL is locked at the right frequency, and RESET_n and CKE timing match the datasheet. Then I confirm the configuration matches the hardware: DRAM part number, density, ranks, speed, and the board's byte and bit swizzle. Only then do I look at the training log — which step failed, on which channel and byte lane — and I retry at a lower frequency to tell a hard fault from a marginal one."

  • 한국어 핵심: 전원·클럭·리셋 → 설정=실물 → 실패 단계·lane → 저속 재시도.

꼬리1. Which training step fails tells you what? "Each step exercises a different group of signals. If ZQ or init fails, I suspect power, reset sequencing, the ZQ resistor, or a wrong memory type. CA training failing points at CK and the command bus. Write leveling failing on one byte lane points at that lane's DQS pair, the feedback DQ bit mapping, or solder on that byte. Read gate points at read latency configuration or DQS reception, and a narrow read or write eye on a few bits points at those specific traces or balls. If everything trains but the memory test fails, I look at address mapping, timing parameters, and refresh."

  • 한국어 핵심: 단계 = 신호 그룹. lane/bit 단위로 좁힌다.

꼬리2. It passes at room temperature but fails at hot. "That says the design works but margin is thin, so I measure margin rather than guess. I compare training results — eye width and VREF window per lane — at 25 and at the hot corner to see whether all lanes shrink uniformly or one lane collapses. Then I check temperature-dependent mechanisms: refresh rate, because DRAM leaks faster and above 85 degrees the refresh interval typically has to halve; whether the controller actually tracks the LPDDR temperature register; impedance and VREF drift, which is why periodic ZQ calibration and retraining matter; and power integrity under load. A real example is an NXP i.MX8M Mini erratum where auto-derating above 85 degrees could fail, and the fix was a fixed 2x refresh."

  • 한국어 핵심: 고온 = 마진 부족 → lane별 eye 비교 + refresh(2×, MR4 추적) + ZQ/VREF drift + PI.

꼬리3. Only 2 of 10 boards fail. "Board-to-board variation means assembly or component variation, not the design — unless those two boards share a lane that's already the weakest on every board. I compare training margins across all ten; if the passing boards have the same lane barely passing, it's a design margin issue and the two failures are just the tail. If the failing boards are clearly different, I do swap tests: move the DRAM or the SoC from a failing board to a good one, or use a socketed board, and see whether the failure follows the part or stays with the board. Following the board points at solder, X-ray for BGA voids, or a PCB fabrication issue; following the part points at a lot or a marginal die."

  • 한국어 핵심: 10장 margin 비교 → 약한 lane 공통이면 설계, 아니면 swap test(부품 따라가나 보드에 남나).

꼬리4 (추가). How do you know your fix didn't just move the problem? "I re-run the full matrix — all boards, both temperature corners, voltage margins — and compare the minimum margin, not just pass or fail. A setting that fixes one lane can shrink another, so the report is the worst-case margin before and after, per lane."

  • 한국어 핵심: pass/fail 말고 최소 margin before/after.

Chain 2 — "Write a memory test."

Q → 꼬리1 → 꼬리2 → 꼬리3 (답 펼치기)

Q. Write a memory test. "I'd write three tests and run them in order: a data bus test, an address bus test, and a cell test like March C-. The data bus test walks a one across all 32 bits at a single address, which proves each data line independently in 32 writes. The address bus test writes a pattern at power-of-two offsets and checks that writing the base or any one offset doesn't show up anywhere else, which finds stuck and shorted address lines in log N accesses. Then March C- covers every cell with ten operations per word. Each test reports address, expected, actual, and the XOR so the hardware team can map it to a pin." (→ §6 화이트보드 코드)

  • 한국어 핵심: data bus → address bus → March C-, 실패는 {addr, exp, act, xor}.

꼬리1. Why does walking-1s on the data bus not find address-line shorts? "Because it only ever touches one address. An address-line fault makes two addresses alias, and you can only see aliasing by writing one location and reading a different one. The data bus test writes and reads the same word, so the address lines never change. In my simulation a stuck or shorted address line passed the data bus test every time, and the address test caught it on the exact line."

  • 한국어 핵심: 한 주소만 쓰므로 주소선이 안 바뀜 — aliasing은 "A에 쓰고 B에서 읽어야" 보인다.

꼬리2. What does March C- detect that a simple write/read doesn't? "A write-then-immediately-read test only proves a cell can hold a value for a nanosecond, and it reads before any neighbor is written. March C- reads every cell before rewriting it, after the whole array has been swept in both directions, so coupling faults — where writing one cell flips or forces another — get caught regardless of whether the aggressor is above or below the victim. It also catches transition faults and address decoder faults, and it's still linear, 10N. In my fault-injection run the naive test missed both coupling faults and all address faults; March C- caught all of them. The idempotent coupling fault was caught only by March C-, in the fourth element."

  • 한국어 핵심: 읽기-먼저 + 양방향 → CF·TF·AF. 실측: CFid는 March C-만 M4에서 잡음.

꼬리3. Why disable the cache — or why not? "For bring-up cell testing I disable it or map the region non-cacheable, because otherwise I'm mostly testing the cache and the writes may never reach DRAM. But I also run with caches on as a separate test, over a range much bigger than the cache, because that exercises burst reads and writes, line fills and evictions — the access pattern real software uses — and that's where signal-integrity problems under back-to-back traffic show up. And I run DMA traffic in parallel to stress the controller from multiple masters."

  • 한국어 핵심: 셀 테스트는 non-cacheable, 별도로 캐시 on + 캐시보다 큰 범위 + DMA 동시 부하.

꼬리4 (추가). What does March C- miss? "Retention faults, because there's no delay between writing and reading — that's a bit-fade test. Neighborhood pattern-sensitive faults and some linked faults need longer algorithms like March B or March SS. And on a 32-bit word memory with only all-zeros and all-ones, two bits in the same word that are shorted always carry the same value, so I repeat March C- with several data backgrounds like 5555 and 3333. In my simulation the plain March C- missed a data-line short and the six-background version caught it."

  • 한국어 핵심: retention · NPSF · linked · word 안 bridging → bit fade, March B/SS, data background.

꼬리5 (추가). How do you test the DRAM you're running from, and how long does it take for 8 GB? "I don't — code and stack run from on-chip SRAM or TCM during the DDR test, or I split DDR in two and relocate. For 8 GB, 10N with 64-bit accesses is about 80 GB of traffic, so seconds with DMA but much longer from an uncached CPU loop. So bring-up uses bus tests plus sampled March regions; full March, bit fade and hammer go to the nightly regression and SLT."

  • 한국어 핵심: SRAM에서 실행 · 8 GB 10N ≈ 80 GB 트래픽 → DMA/샘플링, 전체는 야간/SLT.

Chain 3 — "What's write leveling and why is it needed?"

Q → 꼬리1 → 꼬리2 (답 펼치기)

Q. What's write leveling and why is it needed? "With multiple DRAMs, clock, command, and address are routed fly-by — daisy-chained past each device — to avoid stubs, so the clock arrives at each DRAM at a different time. The data strobes are point-to-point per byte lane, so each lane's DQS has a different skew relative to the clock at its DRAM. Write leveling fixes that: the DRAM enters a mode where it samples CK on the rising edge of DQS and returns that value on a DQ pin, and the controller sweeps the DQS delay per lane until it sees the zero-to-one transition. That aligns DQS to CK at each device to meet tDQSS."

  • 한국어 핵심: fly-by → lane마다 CK 도착 시각 다름 → DRAM이 DQS로 CK를 샘플해 DQ로 회신 → 0→1 지점 탐색.

꼬리1. Does LPDDR need it? "LPDDR is usually point-to-point next to the SoC, so the fly-by skew is small, but there's still a clock-to-strobe alignment step — LPDDR4 has write leveling, and LPDDR5 calls it WCK2CK leveling because writes use the separate WCK clock. LPDDR also adds command bus training, because the CA bus runs fast."

  • 한국어 핵심: LPDDR도 정렬 단계 있음 (LPDDR5 = WCK2CK leveling) + CBT.

꼬리2. Write leveling fails on one byte lane only. What do you check? "That lane's DQS pair — polarity and continuity, probing near the DRAM ball during the leveling sequence; the feedback DQ bit for that lane, because a swizzle mistake means the controller listens to the wrong pin; solder on that byte's balls, so X-ray; and whether the required delay is beyond the tap range, which I can test by changing frequency. Then I check if the same lane fails on other boards to separate design from assembly."

  • 한국어 핵심: DQS 쌍 · 피드백 DQ swizzle · BGA 솔더 · 탭 범위 · 다른 보드도 같은 lane?

Chain 4 — "How would you validate ECC?"

Q → 꼬리1 → 꼬리2 → 꼬리3 (답 펼치기)

Q. How would you validate ECC? "With error injection on every path. I inject single-bit errors and expect correction, the correctable counter to increment, the error address and syndrome registers to point at the injected location, and the interrupt to fire. I inject double-bit errors and expect detection without correction, the uncorrectable path — interrupt, bus error or abort — and correct logging. I check that injection at different addresses reports the right address, which also validates the address decoding in the error logs. And I verify ECC initialization: memory must be scrubbed before first read or you get false uncorrectable errors."

  • 한국어 핵심: 1비트 주입 → 정정·CE·주소·인터럽트 / 2비트 → 검출·UE 경로 / 주소 일치 / init scrub.

꼬리1. How do you inject errors? "Most controllers have poison or inject registers — on the Synopsys controller in Zynq MPSoC, Linux exposes them through EDAC sysfs when the kernel has EDAC debug enabled. Without that, I disable ECC, write data with one or two bits flipped so the stored check bits don't match, re-enable ECC, and read back."

  • 한국어 핵심: poison 레지스터 (Linux synopsys_edac inject_data_error, EDAC_DEBUG) 또는 ECC off 상태에서 데이터만 바꿔 쓰기.

꼬리2. ECC correctable counts are slowly climbing in the field or the chamber. What do you do? "A correctable error rate is a margin signal, not something to ignore. I log the error addresses and look for a pattern: the same address or row suggests a weak cell — a candidate for retirement or a retention problem; the same bit position across many addresses suggests a lane — signal integrity or training; errors that track temperature suggest refresh or margin. I correlate with temperature and voltage logs, check patrol scrub is on so single-bit errors don't accumulate into double-bit, and reproduce on the bench with margining."

  • 한국어 핵심: CE 증가 = 마진 경고. 같은 주소 = 셀 / 같은 비트 = lane / 온도 추종 = refresh·마진.

꼬리3 (추가). What's the difference between on-die ECC, link ECC, and system ECC? "On-die ECC in DDR5 corrects inside the DRAM and is invisible to the controller, so it doesn't protect the bus. LPDDR5 link ECC protects the transfer on the channel only. System or inline ECC in the controller protects end to end and gives you counters and addresses, which is what functional safety needs. LPDDR has no extra width, so automotive SoCs use inline ECC, trading some capacity and bandwidth."

  • 한국어 핵심: on-die(DRAM 안) ≠ link(전송) ≠ system/inline(end-to-end, 기능 안전).

Chain 5 (추가) — "How do you characterize DDR margin across boards and temperature?"

Q → 꼬리1 → 꼬리2 (답 펼치기)

Q. How do you characterize DDR margin? "I read the training results per lane and bit — left and right edges and the VREF window — and I also do active margining: shift the delay or VREF away from the trained center until a memory test fails, in both directions. I do that across boards, temperatures and supply voltages, and report the minimum margin per lane against a guideline. That separates lanes that are weak on every board, which is a design issue, from boards that are weak, which is assembly."

  • 한국어 핵심: 훈련값 읽기 + 능동 margining(중앙에서 밀어서 실패점) × 보드 × 온도 × 전압 → lane별 최소값.

꼬리1. How many boards is enough? "Enough to see the distribution, not just pass/fail — for early bring-up, every board we have, typically tens; for characterization, boards from multiple fab lots and DRAM lots, with corner silicon if available. I'd agree the numbers with the design team based on the margin we need to guarantee."

  • 한국어 핵심: 분포를 볼 만큼, lot 다양성 + corner silicon (→ BV12).

꼬리2. What would you report? "A per-lane table of minimum margin at each corner, the worst case highlighted, compared to the guideline and to the previous board revision, with the test conditions, and any failures with their address, bit, and lane decoded."

  • 한국어 핵심: lane × 코너 최소 margin + 이전 rev 대비 + 실패 디코드.

Chain 6 (추가) — "Training passes, but Linux crashes randomly under load."

Q → 꼬리1 (답 펼치기)

Q. Training passes and memtest passes, but Linux crashes randomly under load. "A short test at idle isn't the same as real traffic. I check what's different under load: temperature rising during the run, power-supply droop with all cores and the NPU active, and multi-master traffic patterns. I'd run memory stress with caches on and DMA in parallel, log temperature and ECC counters, and check whether periodic retraining and refresh rate adjustment are enabled. I'd also rule out software: cache maintenance bugs with DMA look exactly like memory corruption, so I repeat with non-cacheable buffers."

  • 한국어 핵심: 부하 = 온도·PDN droop·멀티 마스터 → 캐시 on + DMA 스트레스 + 온도/ECC 로그 + 캐시 일관성 버그 배제.

꼬리1. How do you tell a DDR problem from a software bug? "Patterns: DDR errors cluster by bit or lane and correlate with temperature and voltage; software corruption clusters by data structure or buffer boundary and correlates with code paths. Changing DDR margin — lower frequency, higher voltage — making the crash go away is strong evidence for hardware; it making no difference points at software."

  • 한국어 핵심: 비트/lane·온도 상관 = HW, 버퍼 경계·코드 경로 상관 = SW, 마진 바꿔서 사라지면 HW (→ BV14).

  • 결과 해석 — 면접에서 말할 것 10개:
    1. DBUS는 데이터선 고장만 잡고(F06, F07) 주소·셀 고장은 전부 놓친다 — 한 주소만 쓰므로 당연.
    2. DBUS는 "칩 없음"(F12)도 통과 — 쓰자마자 읽으면 버스에 남은 값이 돌아온다. Barr 글의 경고 그대로 확인됨2. NAIVE(쓰고 바로 읽기)도 같은 이유로 통과.
    3. ABUS는 주소선 고장을 정확한 선 번호로 지목(F08 A4, F09 A6, F10/F11 A2). 98 접근(0.4N)뿐.
    4. 그러나 ABUS를 data bus test 전에 돌리면 오진: F07(데이터선 short)과 F12(칩 없음)가 "s2:A0" = 주소선 A0 고장처럼 보인다. xor가 0x00000008, 0xff000000처럼 일부 비트만 다르면 데이터 쪽, 0xffffffff(통째로 반대 패턴)면 진짜 aliasing — xor 모양이 진단 단서.
    5. step 2 vs step 3: stuck-low(A4)와 wired-AND short는 base와 겹쳐 step 2에서, wired-OR short는 offset끼리만 겹쳐 step 3에서만 잡힘(F11 s3:A2).
    6. CFid(F05)는 March C-만 잡았다(M4). aggressor(9) < victim(50)이고 victim을 0으로 강제하는 고장은 ⇓ 방향에서 victim이 1이 된 뒤에 aggressor가 0→1 쓰기를 해야 드러난다 — 단방향 테스트(DEVICE, RANDOM)는 구조적으로 못 본다.
    7. March C-도 F07(같은 word 안 데이터선 short)을 놓쳤다 — 배경이 0x00000000/0xFFFFFFFF뿐이면 D3과 D4가 항상 같은 값. 배경 6개(MARCH-DB)는 두 번째 배경 0x55555555에서 잡음(60N).
    8. retention(F13)은 BITFADE만 — 쓰고 바로(수백 사이클 안에) 읽는 테스트는 시간이 지나야 사라지는 비트를 못 본다.
    9. RANDOM은 넓게 잡지만 진단이 흐리다: 주소 고장 xor가 0xb578bcd1처럼 난수 → "어느 선?"을 말해 주지 않는다. 그리고 CFid는 놓침.
    10. 비용: DBUS 0.2N, ABUS 0.4N, March C- 10N, 배경 6개 60N. → bring-up 첫 순서는 싼 bus test로 배선을 증명하고, 비싼 셀 테스트는 그 뒤.

6.2 화이트보드용 March C- (함수 본문 30줄)

  • 코드: onsitePrep/bv09/march_cminus_whiteboard.c — 함수 부분(시작·끝 주석 사이) 30줄. main()은 smoke test.
typedef struct { size_t idx; uint32_t exp, act; int elem; } MemFail;

/* March C-: {any(w0); up(r0,w1); up(r1,w0); down(r0,w1); down(r1,w0); any(r0)}  = 10N
 * returns 0 = pass, -1 = fail (*f = first failure). m must be uncached / device memory. */
int march_cminus(volatile uint32_t *m, size_t n, MemFail *f)
{
    static const struct { int up, rd, wr; uint32_t rv, wv; } el[6] = {
        { 1, 0, 1, 0,           0           },   /* M0 any(w0)     */
        { 1, 1, 1, 0,           0xFFFFFFFFu },   /* M1 up(r0,w1)   */
        { 1, 1, 1, 0xFFFFFFFFu, 0           },   /* M2 up(r1,w0)   */
        { 0, 1, 1, 0,           0xFFFFFFFFu },   /* M3 down(r0,w1) */
        { 0, 1, 1, 0xFFFFFFFFu, 0           },   /* M4 down(r1,w0) */
        { 1, 1, 0, 0,           0           },   /* M5 any(r0)     */
    };
    for (int e = 0; e < 6; e++) {
        for (size_t i = 0; i < n; i++) {
            size_t a = el[e].up ? i : n - 1 - i;     /* no unsigned a >= 0 bug */
            if (el[e].rd) {
                uint32_t v = m[a];
                if (v != el[e].rv) {
                    f->idx = a; f->exp = el[e].rv; f->act = v; f->elem = e;
                    return -1;                       /* stop at FIRST failure */
                }
            }
            if (el[e].wr)
                m[a] = el[e].wv;
        }
    }
    return 0;
}

  • 말하면서 쓸 포인트: ① 원소를 표(데이터)로 만들면 6개 루프 대신 1개 → 실수 줄고 March C+/B로 확장 쉬움 ② 내려가는 루프는 n - 1 - i (unsigned a >= 0 무한 루프 함정) ③ volatile + "uncached/Device 매핑" 주석 ④ 첫 실패에서 멈추고 {idx, exp, act, elem} 보고, 실전은 실패 링버퍼 ⑤ 확장: data background 루프 추가, 64-bit 접근, 영역 분할 멀티코어.

7. 자주 틀리는 것

  1. "training이 통과했으니 DDR은 OK" — training은 타이밍을 맞췄다는 뜻일 뿐. 주소 매핑·타이밍 파라미터·refresh 오류는 memtest에서만 보인다. 반대로 memtest 통과도 "그 온도·그 전압에서"일 뿐.
  2. 테스트 순서를 무시 — address test나 March를 먼저 돌리면 데이터선 고장이 "주소 고장"·"셀 고장"으로 오진된다 (실측 F07/F12 → s2:A0). 항상 data bus → address bus → cell.
  3. March C-의 원소를 틀리게 말함 — 정확히 ⇕(w0) ⇑(r0,w1) ⇑(r1,w0) ⇓(r0,w1) ⇓(r1,w0) ⇕(r0), 10N. M5를 빼먹으면 9N(커버리지 구멍), "w 다음 r"로 쓰면 coupling을 못 잡는다.
  4. word 메모리에 0/1 배경만 — 같은 word 안 비트 short를 못 본다 (실측 F07). data background 반복.
  5. 캐시 켠 채 작은 영역 테스트 — 캐시를 테스트한 것. 그리고 volatile 빠짐 → 컴파일러가 읽기를 없앰.
  6. "쓰고 바로 읽기"로 충분하다고 생각 — 칩 없음·coupling·주소 고장을 놓친다 (실측 NAIVE: 고장 13개 중 4개만 검출 — 셀 SA0/SA1·TF·D7 stuck-high).
  7. ECC 켠 상태로 셀 테스트하고 "에러 없음" — 1비트 고장이 자동 정정돼 숨는다. ECC off raw 테스트 또는 CE 카운터를 함께 확인. ECC init(scrub) 없이 읽으면 가짜 UE.
  8. on-die ECC = ECC 있음 — DDR5 on-die ECC는 버스 오류를 못 잡고 카운터도 controller에 안 보인다. 기능 안전에는 system/inline ECC.
  9. 고온 실패를 "부품 불량"으로 단정 — 먼저 refresh 배율(MR4 추적, 2× refresh), ZQ/retraining 주기, lane별 margin 비교. 실제 에라타(i.MX8MM ERR050805)처럼 controller 자동 derating 문제일 수도.
  10. 2/10 보드 실패를 바로 "조립 불량" — 나머지 8장도 같은 lane이 겨우 통과하고 있으면 설계 마진 문제다. 분포를 먼저 본다.
