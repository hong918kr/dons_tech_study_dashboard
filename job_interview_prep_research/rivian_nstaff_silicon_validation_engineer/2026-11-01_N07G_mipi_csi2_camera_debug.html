0. TL;DR

  • 이 페이지로 답할 것: "The camera stream drops frames and the RX reports ECC errors — debug it." 를 센서 → SerDes → D-PHY → CSI-2 RX → ISP → DDR 경로를 따라 "어느 구간에서 프레임이 사라지나" 로 좁히는 법. 시나리오 G1–G10 (프레임 0개 · SoT · 온도 ECC · 대각선 찢어짐 · 색 · 4대 drop · VC 섞임 · FE 누락 · 카메라 간 timestamp 1 프레임 · 15 fps).
  • 기초(D-PHY 레인, 패킷 구조, V4L2)는 LP00A §5, 테스트 플랜·에러 종류·ECC 3-bit 오정정 실험은 N06E E3, 패킷 단위 ECC/CRC 코드는 V9. 여기선 증상 → 구간 → 증거와 스트림 단위 진단 코드.
  • 외울 것 ① 구간마다 "받은 수 vs 보낸 수" 카운터를 맞춰 본다: 센서 frame# → (deser lock·에러) → RX FS/FE 수·packet count → line count·WC → DMA DONE 수 → V4L2 sequence gap. 숫자가 처음 어긋나는 구간이 범인.
  • 외울 것 ② 에러 종류가 계층을 말해 준다: SoT/SoT sync = PHY 진입(settle·레인·클럭 모드) · ECC1 증가 = 신호 마진 경고(아직 동작) · ECC2/CRC = 실제 손상 · frame sync error = FS/FE 구조(FE 손실·VC 충돌) · line buffer full = 하류(DDR/ISP) 역압 · 에러 0인데 이상 = 설정(WC·DT·Bayer·stride).
  • 외울 것 ③ D-PHY HS 진입: LP-11 → LP-01 → LP-00 → HS-0 → sync byte → 데이터 → HS-trail → LP-11. 수신기 THS-SETTLE 창 = 85 ns + 6 UI ~ 145 ns + 10 UI 2 — 레인 속도가 바뀌면 settle 값도 다시 계산해야 한다 (G2 단골 버그).
  • ★ 면접관 포인트: 다중 카메라 동기 = "언제의 timestamp인가(노출 시작/SoF/EoF)" 정의 → 하나의 PTP 시계 → FSYNC → LED 스트로브 물리 기준으로 검증. 1 프레임 정확히 어긋남은 이산(시퀀스·파이프라인) 문제, 점점 커지면 free-run drift (G9).
  • 30초 영어 답 (헤드라인): "First I'd find where frames disappear, by comparing counts stage by stage: frame numbers from the sensor, frame-start and frame-end counts and packet counts at the receiver, and buffers completed by the DMA. ECC errors tell me the layer: rising single-bit corrections mean the physical link is losing margin, two-bit and CRC errors mean real corruption, and SoT errors point at the HS entry — settle time or lane setup. If the receiver is error-free but buffers are still missing and the line buffer reports full, it's downstream bandwidth, not the link. Then I'd turn one knob at a time — lane rate, settle value, temperature, number of cameras — and add the failing condition to the regression with the counters as pass criteria."

30초 영어 답

"Zero frames with zero errors means nothing is reaching the packet layer, so I go bottom-up. First, is the sensor actually streaming — I read its mode and stream registers over I2C and look at the clock lane on a scope. Second, if there's HS activity but the receiver's packet count stays at zero, I check ordering: some receivers must see the lane in LP-11 before streaming starts, so if the sensor begins HS before the receiver is enabled, it never synchronizes. Third, lane count and clock mode in the device tree versus the sensor. With a SerDes, I first use the deserializer's pattern generator to split the camera side from the SoC side."

  • "The scope shows HS bursts on all lanes, the receiver still sees nothing. Next?"
답

"Then it's the receiver's PHY configuration or enable. I'd read the per-lane stop-state and SoT-sync bits: if they never change, the PHY isn't enabled or is on the wrong lanes; if SoT sync errors climb, it sees HS but can't find the sync — lane mapping, polarity or settle. 30초 영어 답

"Single-bit ECC corrections rising with temperature is the link losing margin before it actually fails — the header still decodes, but the bit error rate is climbing, and CRC errors on the much longer payload follow. I'd localize by heating one thing at a time: only the SoC with a thermal forcer, only the camera, then the whole system, and compare per-lane counts and the deserializer's link counters. Then I'd step the lane rate down and re-sweep settle at temperature. My pass criterion is zero corrected errors, not zero uncorrected ones, because corrections are the early warning."

꼬리 질문

  • "Why not just accept 1-bit errors since ECC fixes them?"
답

"Because the same bit error rate that flips header bits also hits the payload, where CRC only detects, so frames get dropped. Corrections are a margin measurement; I want zero in validation." 한국어 핵심: 같은 BER이 payload에도 → CRC drop, 3비트면 오정정(N06E 실험 93%) → ECC1은 마진 지표, 0이 기준.

  • "How long do you need to run to claim a BER of 1e-12?"
답

"With zero errors, about three over the BER in bits for 95 percent confidence — three times ten to the twelfth bits. At four lanes times 2.5 gigabits, that's 10 gigabits per second, so roughly five minutes per corner. That's why I'd run it per lane rate and temperature point rather than as one long soak." 한국어 핵심: 에러 0 기준 3/BER 비트(95%) → 10 Gb/s면 약 300초, 코너마다.

"A clean diagonal tear with no receiver errors is almost never signal integrity — it's a line-length mismatch.   • "Why does a ramp pattern help more than color bars here?"
답

"Then it's not configuration, it's an occasional short or long line — a word-count corruption or a dropped packet mid-frame. 30초 영어 답

"Half the frame rate has two very different causes, and the receiver tells them apart. If the frame-start interval at the receiver is also 66 milliseconds and the sensor's frame numbers are contiguous, the sensor really is running at 15 — usually exposure longer than the frame time stretching the frame, or a wrong timing table. If the receiver sees 30 but only every other frame completes to memory, frames are lost after the receiver — typically too few buffers queued or a DMA re-arm problem. So I measure the rate at each stage instead of only at the application."

꼬리 질문

  • "The app sees 29.97 instead of 30.00. Do you care?"
답

"It depends on the requirement, but I'd check it against the sensor's clock tolerance: the sensor's frame rate comes from its own oscillator and PLL settings, so a 0.1 percent offset could be the line-length rounding in the mode table or an oscillator error. If cameras must be synchronized, they should be triggered, and then the rate should match the trigger exactly — any difference is a free-running camera." 한국어 핵심: 0.1% 차이 = 모드 테이블 반올림/오실레이터, 동기 카메라면 trigger와 정확히 같아야 함(다르면 free-run).

  • "How do you prove zero drops over 24 hours?"
답

"Count at every stage with hardware counters and frame numbers, not by watching the stream: sensor frame numbers contiguous, receiver frame starts equal frame ends, DMA completions equal frame starts, and the V4L2 sequence without gaps. At 30 fps that's about 2.6 million frames per camera per day, and I'd log any mismatch with its timestamp so it can be correlated with load or temperature." 한국어 핵심: 구간별 카운터·frame#·V4L2 seq로 증명, 30 fps × 24 h ≈ 260만 프레임/카메라, 불일치는 시각과 함께 기록.

6. 꼬리 질문 체인

체인 1 — "The camera stream drops frames and the RX reports ECC errors."

Q → 꼬리1 "They're all single-bit corrected errors — do you care?" → 꼬리2 "It only happens above 95 °C." → 꼬리3 "How do you turn that into a production screen?"

Q. Frames drop and the receiver reports ECC errors — debug it.

"First, are the drops caused by the errors or just coincident? I'd line up per-frame counters: which frames had ECC or CRC errors and which frames never completed to memory. If they match, it's the link; if drops happen on clean frames with line-buffer-full, it's downstream bandwidth. For link errors I check the type — SoT points at HS entry, rising single-bit ECC at margin — and whether it's one lane, one camera, or all." 한국어 핵심: drop과 에러가 같은 프레임인지부터 → 링크 vs 하류 분리, 에러 종류·레인·카메라로 좁히기.

꼬리1. All single-bit corrected — do you care?

"Yes. Corrections are a margin measurement: the same error rate hits the payload where CRC can only detect, and three-bit header errors can be miscorrected into a wrong VC or word count. In validation, the pass criterion is zero corrections at every corner." 한국어 핵심: ECC1 = 마진 지표, payload CRC drop·3비트 오정정 위험 → 기준은 0.

꼬리2. Only above 95 °C.

"Then I heat one component at a time to see whose temperature matters — SoC, camera module, or cable and connectors — and re-run the settle sweep and a lane-rate step-down at temperature. If the settle window shifts with SoC temperature, it's receiver PHY characterization; if the deserializer's link counters rise, it's the SerDes link or power-over-coax." 한국어 핵심: 부품별 가열로 온도 주인 찾기, 고온 settle sweep·속도↓, deser 카운터로 SerDes 구분.

꼬리3. Production screen?

"I'd turn the characterization into a short margin test: run the test pattern at a slightly stressed condition — one step higher lane rate or a settle value offset from nominal — for a few seconds and require zero corrections. That catches marginal parts and boards in system-level test without a chamber, and the guard band comes from the PVT data." 한국어 핵심: 약간 가혹한 조건(속도↑·settle offset)에서 짧은 TPG 테스트로 SLT 스크린, guard band는 PVT 데이터로.

체인 2 — "How do you know where in the pipeline a frame got lost?"

Q → 꼬리1 "The ISP has no frame counter." → 꼬리2 "It happens once a day."

Q. Where in the pipeline did the frame get lost?

"I count at every boundary on one time base: sensor frame numbers in the frame-start packets, deserializer link status, receiver frame start, end and packet counts, line count per VC, DMA completions, and the V4L2 sequence. The first stage where counts diverge is the culprit. My analyzer does exactly that from the receiver event log." 한국어 핵심: 경계마다 같은 시간축 카운트 → 처음 어긋나는 구간이 범인.

꼬리1. The ISP has no frame counter.

"Then I use what surrounds it: the receiver's output count going in, the DMA write completions coming out, and an interrupt or a GPIO toggle at each ISP frame-done if firmware can add one. Or I bypass the ISP — RAW straight to DDR — and see whether the loss disappears. And I'd file a design-for-debug request for a counter in the next revision." 한국어 핵심: 앞뒤 카운터·GPIO 토글·ISP bypass로 대체, 다음 리비전에 카운터 요청(DFD).

꼬리2. It happens once a day.

"Then I need a trigger, not a log dump: on a frame-number gap or a DONE mismatch, firmware freezes the counters, saves a snapshot of the receiver status and the last few hundred events from a ring buffer, and pulses a GPIO so a scope in segmented mode captures the lanes at that moment. And I'd raise the rate of the suspected condition — more cameras, more DDR load, higher temperature — to turn once a day into once an hour." 한국어 핵심: 하루 1회면 트리거 기반 캡처(카운터 freeze·링버퍼·GPIO→스코프) + 조건 강화로 빈도↑.

체인 3 — "How would you validate multi-camera synchronization?" (면접관 특허 영역)

Q → 꼬리1 "Where would you take the timestamp?" → 꼬리2 "Software says the cameras are within 10 µs. Do you believe it?" → 꼬리3 "Now add LiDAR."

Q. Validate multi-camera synchronization.

"Define the requirement first — skew between cameras, and accuracy against the vehicle time base. All timestamps come from one PTP-disciplined hardware clock; cameras are triggered by FSYNC pulses generated from that clock. Then I measure per-camera period jitter, frame-number gaps and per-frame inter-camera skew over long runs, and validate the whole chain physically with an LED strobe all cameras can see." 한국어 핵심: 요구 정의 → 하나의 PTP HW 시계 + FSYNC → jitter·gap·skew 통계 → LED 스트로브로 물리 검증.

꼬리1. Where would you take the timestamp?

"As close to the hardware event as possible: a latch of the PTP clock at frame start in the CSI-2 receiver, not in an interrupt handler or at DMA completion. Then I convert it to start of exposure using a measured per-mode offset, and say in the data which definition it is." 한국어 핵심: RX SoF에서 PHC HW latch, 모드별 측정 오프셋으로 노출 시작 환산, 정의 명시.

꼬리2. Software says within 10 µs — believe it?

"Not without a physical reference. Software only compares numbers that share the same errors — a wrong per-sensor latency, a trigger taking effect a frame later, or a path asymmetry are invisible to it. The LED strobe and a scope on the trigger lines measure what actually happened." 한국어 핵심: SW 비교는 같은 오류를 공유 → 물리 기준(LED·스코프) 없이는 못 믿음.

꼬리3. Now add LiDAR.

"LiDAR is a rotating sensor, so each camera should expose when the LiDAR beam crosses its field of view; the trigger is derived from the LiDAR's phase on the same PTP time base. I'd validate with a target both sensors see and compare the timestamps of the detections, and watch for the classic whole-second or 18-second offsets from PPS and GPS-versus-UTC handling." 한국어 핵심: 카메라 trigger를 LiDAR 회전 위상에 맞춤(같은 PTP), 공통 타깃으로 검증, 1 s/18 s 오프셋 함정 (deck §7 #13).

체인 4 — "The camera is behind a SerDes link. How do you split the problem?"

Q → 꼬리1 "The deserializer reports lock but frames are corrupt." → 꼬리2 "It only fails with the longest cable."

Q. How do you split SerDes problems from CSI-2 problems?

"Treat it as two links. First the deserializer: local I2C works, forward link locked, its link error counters clean, back-channel I2C to the serializer and sensor works. Then use the deserializer's own test pattern into the SoC — if that's clean, the SoC receiver and the board hop are fine and the problem is on the camera side." 한국어 핵심: 두 링크로 나눔 → deser lock·카운터·역방향 I2C, deser TPG로 SoC 구간 분리.

꼬리1. Lock is reported but frames are corrupt.

"Lock only says the clock recovered, not that the data is clean. I'd read the deserializer's link error or CRC counters, then compare the sensor's test pattern through the whole chain with the deserializer's pattern into the SoC. If only the full chain fails, it's the serializer link margin or the sensor's CSI-2 output into the serializer." 한국어 핵심: lock ≠ 데이터 정상 → deser 에러 카운터, 전체 체인 TPG vs deser TPG 비교.

꼬리2. Only with the longest cable.

"That's channel loss and possibly power: longer coax means more attenuation and more voltage drop on power-over-coax. I'd measure the camera's supply voltage at the module during streaming, check the SerDes link margin indicators if the part has them, and run a cable-length by temperature matrix. Whether Rivian's parts expose eye monitoring I'd check in the datasheet." 한국어 핵심: 긴 케이블 = 감쇠 + PoC 전압 강하 → 모듈 전압 측정, 마진 지표, 길이×온도 매트릭스 추정.

9. 자주 틀리는 것

  1. "ECC 에러 = 데이터 깨짐"으로 뭉뚱그림 — ECC1(정정, 마진 경고) · ECC2(헤더 손실 → 패킷/FE 손실) · CRC(payload) · SoT(PHY 진입)는 계층이 다르다. 종류별로 말하기.
  2. 앱 fps만 보고 "카메라가 drop한다" — 센서·RX·DMA·앱 중 어디서 줄었는지 구간별 숫자 없이는 결론 불가 (G6, G10).
  3. settle을 상수로 생각 — ns 창은 거의 같아도 카운터 값은 레인 속도에 비례. 모드 바꾸면 재계산 (G2).
  4. ECC1을 "고쳐졌으니 OK" — 같은 BER이 payload엔 CRC drop, 3비트면 헤더 오정정. 검증 기준은 0 (G3, N06E E3 3-bit 실험).
  5. deser "lock" = 정상이라고 가정 — lock은 클럭 복원일 뿐, 링크 에러 카운터·TPG로 데이터 확인.
  6. 에러 0인데 영상 이상 → SI부터 의심 — 에러 0 + 이상 = 거의 설정(WC/stride, Bayer 순서, DT, VC 매핑) (G4, G5, G7).
  7. 동일 센서 여러 대 = 기본 VC 같음을 잊음 — deser 재매핑 누락 (G7).
  8. timestamp 정의 없이 "동기됐다" — SOE/SoF/EOF/DMA done 중 무엇인지, rolling shutter 줄 시각까지. SW가 보고하는 skew는 물리 기준(LED·스코프)으로 확인 (G9).
  9. sequence 번호로 카메라 간 짝짓기 — 시작 시 drop 하나면 영원히 1 프레임 어긋남. 짝짓기는 HW timestamp nearest-match (G9).
  10. 에러 주입 시 "검출"만 확인 — 차량에선 복구(다음 FS에서 정상, 피해 1 프레임, hang 0)가 더 중요 (G8).
