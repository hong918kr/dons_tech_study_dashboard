0. TL;DR

  • 이 노트로 답할 수 있는 것: "PCIe 드라이버 probe 뼈대를 써 봐라", "왜 pci_set_master? 왜 DMA mask? MSI vs INTx? 왜 write 뒤에 read-back?", "커널 드라이버 없이 레지스터를 찌르는 검증 툴은 어떻게 만드나 (resource0 mmap / UIO / VFIO), 위험은?", "드라이버가 어떻게 장치에 붙나 (id table, modalias, bind/unbind, driver_override)".
  • 외울 것 ① probe 순서 (6줄): pcim_enable_device → pcim_iomap_region(pdev, 0, name) (6.18에서 pcim_iomap_regions는 DEPRECATED) → pci_set_master → dma_set_mask_and_coherent(DMA_BIT_MASK(장치 능력)) (현행 DMA API 문서: 64-bit mask는 절대 실패 안 함, "64 시도 후 32 fallback"은 잘못된 관용구로 명시 — 장치가 64-bit 지원하면 64, 아니면 32를 처음부터 고름) → pci_alloc_irq_vectors(pdev, 1, N, PCI_IRQ_MSIX | PCI_IRQ_MSI | PCI_IRQ_INTX) + pci_irq_vector() → devm_request_irq / pci_request_irq → 장치 init. remove는 "장치 조용히 → IRQ → DMA 정지 → 버퍼 해제 → unmap → disable", pcim_*/devm_*이면 대부분 자동.
  • 외울 것 ② 하드웨어 비트: pcim_enable_device = COMMAND bit1 Memory Space Enable (enabling device (0000 -> 0002)), pci_set_master = bit2 Bus Master Enable(DMA와 MSI 둘 다 장치가 메모리 write를 하는 것이라 필요), MSI 사용 시 커널이 bit10 INTx Disable 세팅 → 실측 COMMAND = 0x0406.
  • 외울 것 ③ MMIO: writel은 posted(완료 응답 없음) → 순서/도착 보장이 필요하면 같은 장치의 레지스터를 readl로 읽어서 flush. readl/writel은 일반 메모리(DMA 버퍼)와의 순서 barrier 포함, _relaxed는 같은 장치 내 순서만.
  • 실측 하이라이트: QEMU virt + edu에서 내 드라이버가 ID=0x010000ed, factorial(10)=3628800 (MSI IRQ), DMA 256 B 왕복 PASS. 28-bit DMA mask는 -5로 실패(virt RAM이 0x4000_0000부터라서) → "x86에선 되는데 ARM에선 안 되는" 전형을 직접 재현. INTx 모드는 GIC-0 37 Level, MSI 모드는 GICv2m-PCI-MSI ... Edge.
  • 30초 영어 답 (headline: "Write the skeleton of a PCIe driver probe"): "I'd declare a pci_device_id table with MODULE_DEVICE_TABLE so udev can autoload the module. In probe: pcim_enable_device to turn on memory decoding, pcim_iomap_region to claim and map BAR0, pci_set_master because both DMA and MSI are memory writes from the device, then dma_set_mask_and_coherent with the width the device really supports — 64 bits never fails, so the old try-64-then-32 pattern isn't needed. Then pci_alloc_irq_vectors asking for MSI-X, MSI or INTx, request_irq on pci_irq_vector, and finally initialize the device and enable its interrupts last. With the managed pcim_ and devm_ APIs, the error paths and remove mostly unwind themselves; in remove I only quiesce the hardware — stop interrupts and DMA — before the core frees the rest."

1. 🔰 처음 보는 사람을 위한 설명

1.1 비유: 회사에 새로 온 장비와 전담 매니저

  • PCIe 장치(endpoint) = 회사에 새로 들어온 장비(예: 고속 복사기). 장비에는 창구가 있고(레지스터), 창구에 서류를 넣거나(write) 표시판을 읽어서(read) 일을 시킨다.
  • 드라이버 = 그 장비 전담 매니저(커널 코드). 매니저가 하는 일: 장비 전원 켜기, 창구 위치 확인, 장비가 창고(RAM)에 직접 드나들 수 있게 허락, 장비가 "다 했어요" 벨을 누르면 받기.
  • Linux 드라이버 모델 = 인력 사무소 매칭.
    • bus(PCI 버스) = 사무소. 장비 목록과 매니저 목록을 둘 다 가지고 있다.
    • device(struct pci_dev) = 열거(enumeration) 때 발견된 장비 한 대. "vendor 0x1234, device 0x11e8" 같은 명찰이 있다.
    • driver(struct pci_driver) = 매니저. "나는 이런 명찰을 가진 장비를 다룰 수 있다"는 자격증 목록(pci_device_id 테이블)을 낸다.
    • 사무소가 명찰과 자격증이 맞는 쌍을 찾으면 probe()(첫 출근 인수인계)를 부른다. 장비가 빠지거나 매니저가 그만두면 remove().
  • BAR (Base Address Register: 장치가 "내 레지스터 창구를 이 크기만큼 메모리 주소에 매핑해 달라"고 요청하는 칸) = 창구의 번지. 열거 때 커널이 번지를 정해 BAR에 적어 준다 (LP04). 드라이버는 그 물리 주소를 ioremap 해서 CPU가 포인터로 접근할 수 있게 만든다.
  • MMIO (Memory-Mapped I/O: 장치 레지스터를 메모리 주소처럼 읽고 쓰는 방식) = 창구에 서류 넣기. writel(값, 주소) / readl(주소).
  • DMA (Direct Memory Access: CPU를 거치지 않고 장치가 RAM을 직접 읽고 쓰는 것) = 장비가 창고(RAM)에 직접 가서 물건을 가져오고 갖다 놓는 것. 매니저는 "창고 몇 번 칸을 써라"(DMA 주소)만 알려 준다. 장비가 갈 수 있는 창고 범위가 DMA mask.
  • IRQ (Interrupt Request: 장치가 CPU에게 "일 끝났어/봐 줘"라고 알리는 신호) = 초인종. 옛날식은 전용 선(INTx), 요즘은 "특정 주소에 쪽지를 쓰는 것"(MSI/MSI-X).
  • User-space 검증 툴 = 매니저(커널 드라이버) 없이 직원이 직접 창구를 만지는 것. 빠르게 레지스터를 찌르기엔 좋지만, 창고 출입(DMA)과 초인종(IRQ)을 안전하게 다루려면 UIO나 VFIO 같은 출입증 시스템이 필요하다.

	/* { PCI_DEVICE_CLASS(PCI_CLASS_STORAGE_EXPRESS, 0xffffff) },  class 매칭 예 (nvme) */
	{ }                                       /* 끝 표시 (0으로 채운 항목) */
};
MODULE_DEVICE_TABLE(pci, edu_ids);            /* → modinfo의 alias: 줄 */

static struct pci_driver edu_driver = {
	.name = "edu_lp06", .id_table = edu_ids,
	.probe = edu_probe, .remove = edu_remove,
	.dev_groups = edu_groups,                 /* sysfs 속성 자동 생성/삭제 */

};

2.3 remove / shutdown / 에러 경로

  • 권장 remove 순서 (docs.kernel.org/PCI/pci.html §1.5): ① 장치가 IRQ를 못 내게 → ② free_irq → ③ DMA 정지 → ④ DMA 버퍼 해제(streaming 먼저, coherent 나중) → ⑤ 다른 서브시스템에서 unregister → ⑥ iounmap, pci_disable_device → ⑦ release_region.
  • managed API를 쓰면 devres가 등록 역순으로 풀어 준다: devm_request_irq → pci_alloc_irq_vectors → pcim_iomap_region → pcim_enable_device. 그래서 내 edu_remove()는 하드웨어 조용히(STATUS IRQ enable 끄기) 만 한다. 단, DMA 정지는 자동이 아님 — 장치가 계속 DMA 중이면 해제된 메모리에 쓴다 (가장 위험한 버그).
  • pci_disable_device()는 BME만 끈다 (do_pci_disable_device: COMMAND_MASTER만 clear, 6.18 확인) — Memory Space Enable은 남음. 실측: 두 번째 insmod에서 enabling device 메시지가 다시 안 나옴(MEM 비트가 이미 1).
  • .shutdown: reboot/kexec 시 호출 — DMA 정지 필수(kexec 후 새 커널 메모리를 장치가 덮어쓰는 버그).
  • surprise removal(케이블 뽑힘, 링크 다운): MMIO read가 0xFFFFFFFF → 드라이버는 readl() == ~0을 "장치 사라짐" 신호로 처리하고 pci_device_is_present()로 확인 (LP09).

  • MMIO 트레이싱: 6.18에는 rwmmio tracepoint(CONFIG_TRACE_MMIO_ACCESS)가 readl/writel 안에 들어 있음 → 드라이버의 레지스터 접근 순서를 ftrace로 볼 수 있음 [LP13].

2.5 DMA 기초 (깊은 내용은 LP08)

  • DMA 주소 ≠ CPU 물리 주소 ≠ 커널 가상 주소. 장치에게는 반드시 DMA API가 준 dma_addr_t를 줌. 실측: cpu=ffff000003ebb000 dma=0x0000000043ebb000 — IOMMU 없는 virt라 DMA 주소 = 물리 주소(0x43eb_b000), CPU는 linear map 가상 주소.
  • coherent: dma_alloc_coherent(dev, size, &handle, GFP_KERNEL) — 디스크립터 링, 상태 블록. non-coherent SoC에선 uncached로 매핑.
  • streaming: dma_map_single(dev, buf, len, DMA_TO_DEVICE) → 장치에 주소 전달 → 완료 후 dma_unmap_single (또는 dma_sync_single_for_cpu/device). 반드시 dma_mapping_error() 확인.
  • 28-bit edu 실험이 보여 주는 것: 장치 mask(28)보다 RAM(0x4000_0000=30비트 이상)이 높고 IOMMU도 없으면 dma_set_mask가 거부 → SWIOTLB도 같은 RAM이라 못 도움. 해결은 IOMMU(SMMU)로 장치 주소 공간을 낮은 주소에 매핑하거나, 장치가 더 넓은 주소를 지원하게 하는 것.

4. 꼬리 질문 체인

체인 1 — "Write the skeleton of a PCIe driver probe."

Q → pci_set_master → DMA mask → MSI/MSI-X/INTx → read-back (모범 답 펼치기)

Q. Write the skeleton of a PCIe driver probe. "Allocate a private struct with devm_kzalloc. pcim_enable_device, then pcim_iomap_region for BAR0 and check IS_ERR. pci_set_master. dma_set_mask_and_coherent with the device's real address width. pci_alloc_irq_vectors with min 1 and the max I need, allowing MSI-X, MSI and INTx, then devm_request_irq on pci_irq_vector(pdev, 0). Store drvdata, initialize the device, and enable interrupts on the device last. Every step returns an error with dev_err_probe, and because everything is managed, the unwind is automatic. I wrote exactly this for QEMU's edu device and ran it."

  • 한국어 핵심: enable → iomap_region → set_master → DMA mask(장치 능력대로) → irq vectors → request_irq → init(인터럽트 마지막). managed라 unwind 자동. 직접 돌려 봤다.

꼬리1. Why pci_set_master? "It sets Bus Master Enable in the command register. Without it the device isn't allowed to initiate transactions, so its DMA reads and writes are blocked — and MSI too, since an MSI is just a memory write from the device. It's a classic silent failure: MMIO works, but DMA never completes and interrupts never arrive."

  • 한국어 핵심: COMMAND bit2. DMA와 MSI 둘 다 장치가 요청을 내는 것. MMIO는 되는데 DMA/IRQ만 안 됨 = BME 의심.

꼬리2. Why set a DMA mask, and what if 64-bit fails? "The mask tells the DMA layer which bus addresses the device can generate, so it never hands the device an address it would truncate. Per the current DMA API docs, a 64-bit mask never fails — the kernel bounces or remaps if needed — so the old 'try 64, fall back to 32' idiom is actually discouraged; you pick the mask from what the hardware supports. Masks of 32 bits or more are always accepted with direct mapping; smaller ones depend on where RAM is, and that's the case where you must check the return value. In my lab a 28-bit mask failed with -EIO because the ARM virt machine's RAM starts at 1 GB."

  • 한국어 핵심: 주소 잘림 방지. 64-bit은 never fail(문서), 64→32 fallback은 구식. <32-bit만 실패 가능 → 반환값 검사. 28-bit -EIO 실측.

꼬리3. MSI vs MSI-X vs INTx? "INTx is a shared, level-triggered virtual wire, so the handler must check the device's status and return IRQ_NONE if it's not ours, and must clear the cause or it fires forever. MSI is a memory write, edge-like, not shared, up to 32 contiguous vectors with one address. MSI-X has a table in a BAR with up to 2048 vectors, each with its own address, data and mask, so you can give every queue its own vector and CPU. I prefer MSI-X, then MSI, then INTx, which is what pci_alloc_irq_vectors does with all three flags."

  • 한국어 핵심: INTx 공유·레벨(원인 clear 필수), MSI 32개·edge, MSI-X 2048·vector별 mask·affinity.

꼬리4. Why do you need a read-back after a write? "PCIe memory writes are posted — the CPU gets no completion, and the write may sit in buffers in the root complex or a switch. A read to the same device is non-posted and, by ordering rules, can't pass the earlier write, so when the read returns, the write has reached the device. I use it after a reset or before a delay that the hardware timing depends on, and after disabling interrupts on the device so I know it took effect."

  • 한국어 핵심: posted write는 도착 보장 없음. 같은 장치 read는 추월 불가 → flush. 리셋·지연·IRQ disable 뒤.

꼬리5 (추가). readl vs readl_relaxed? "Both are single, little-endian accesses ordered with respect to other accesses to the same device. The non-relaxed versions also order against normal memory: writel has a barrier before it so the DMA descriptors I wrote to RAM are visible before the doorbell, and readl has a barrier after so I don't read DMA data before checking the status. Relaxed is for hot paths where no DMA buffer is involved."

  • 한국어 핵심: 일반 메모리(DMA 버퍼)와의 순서 차이. doorbell 앞 writel 필수.

체인 2 — "How would you build a validation tool that pokes device registers without writing a kernel driver?"

Q → resource0/UIO/VFIO → 위험 → 인터럽트·DMA (모범 답 펼치기)

Q. Validation tool without a kernel driver? "Three levels. For quick register access, mmap /sys/bus/pci/devices/<BDF>/resource0 with O_SYNC and use volatile 32-bit accesses — no driver needed, as long as memory decoding is enabled. If I need interrupts, bind uio_pci_generic with new_id; read() on /dev/uioN blocks until an INTx arrives. If I need DMA or MSI safely, use VFIO: bind vfio-pci, map DMA buffers through the IOMMU, and get MSI-X as eventfds. I've run the first two against QEMU's edu device."

  • 한국어 핵심: resource0(레지스터만) → UIO(INTx) → VFIO(DMA+MSI, IOMMU 보호). 두 개 실측.

꼬리1. Risks? "With resource0, the kernel driver may still be bound, so two agents touch the same registers — and some registers have read side effects, like read-to-clear status. There's no protection on DMA: if I program a DMA address from user space without an IOMMU, the device can overwrite any physical memory, which is why uio_pci_generic is documented as insecure for DMA devices and clears bus mastering on close. Kernel lockdown can also forbid resource mmap. VFIO fixes the DMA problem but needs an IOMMU and takes the whole IOMMU group."

  • 한국어 핵심: 동시 접근, read-to-clear, DMA 보호 없음, lockdown, VFIO는 IOMMU group 단위.

꼬리2. How does UIO deliver an interrupt for a PCI device? "uio_pci_generic only supports INTx. Its kernel handler checks the Interrupt Status bit and sets INTx Disable in the command register to stop the level interrupt, then wakes the reader. User space reads a 4-byte event count, services and acks the device, then clears INTx Disable through the config file to re-arm. My lab got counts 1, 2, 3, 4 in a row with that loop."

  • 한국어 핵심: INTx Disable로 mask → read 카운트 → 장치 ACK → config로 unmask. 실측 count 1→4.

꼬리3 (추가). Why can't UIO do MSI? "Generic UIO has a single interrupt and no way to program and route MSI vectors or mask them per vector, and MSI isn't shared so masking via the command register doesn't apply. VFIO exposes MSI and MSI-X through ioctls that set up eventfds per vector. For a production user-space driver like DPDK, VFIO is the standard."

  • 한국어 핵심: UIO는 단일 IRQ·INTx mask 방식. MSI/MSI-X는 VFIO eventfd.

체인 3 (추가) — "Your driver doesn't load automatically when the device appears. Debug it."

Q → modalias → bind 수동 → driver_override (모범 답 펼치기)

Q. Driver doesn't autoload. "Autoload is uevent to udev to modprobe by modalias. I'd check the device's modalias in sysfs, compare it with modinfo aliases of my module — if MODULE_DEVICE_TABLE is missing there's no alias — and make sure depmod ran so modules.alias has it. Then I'd load the module by hand: if it binds, it's the autoload path; if it doesn't, the ID table doesn't match, maybe because of subsystem IDs or a class mask."

  • 한국어 핵심: modalias ↔ modinfo alias ↔ depmod. 수동 로드로 경로/매칭 분리.

꼬리1. Another driver grabbed the device first. How do you switch it? "Unbind it from the current driver through its unbind file, write my driver's name to the device's driver_override, then trigger drivers_probe. That's exactly how people move a NIC to vfio-pci. I demoed it on edu: overriding to a non-existent driver left it unbound, clearing the override let my driver take it back."

  • 한국어 핵심: unbind → driver_override → drivers_probe. 실측 데모.

꼬리2. new_id vs driver_override? "new_id adds an ID to a driver's dynamic table, so every matching device can bind to it — useful for a new device revision. driver_override is per device and restricts that one device to one driver, which is safer when several identical devices exist and only one should go to VFIO."

  • 한국어 핵심: new_id = 드라이버 쪽 전역, driver_override = 장치 하나 지정.

체인 4 (추가) — "Interrupts work at first, then the system hangs with an interrupt storm (or interrupts stop)."

Q → INTx 레벨 → MSI 손실 → 디버그 순서 (모범 답 펼치기)

Q. Interrupt storm after a while. "With INTx that's almost always the handler not clearing the cause on the device. INTx is level-triggered, so the line stays asserted and the handler runs forever; the kernel eventually says 'nobody cared' and disables the IRQ. Also on a shared line, the handler must return IRQ_NONE when its device has nothing pending. Fix: read status, ack exactly those bits, and read back to flush the ack before returning."

  • 한국어 핵심: INTx 레벨 → 원인 ACK 안 하면 storm → "nobody cared". 공유 시 IRQ_NONE. ACK 후 read-back.

꼬리1. With MSI the interrupts just stop. "MSI is edge-like, so if the device only sends a new MSI when its status goes from zero to non-zero, and the driver didn't ack everything, the device never generates another one. Other causes: the vector got masked, bus mastering got cleared by a reset, or the MSI address changed after an affinity move and the device didn't update. I check /proc/interrupts counts, the device's status register, and the MSI capability with lspci."

  • 한국어 핵심: edge라 ACK 누락 시 재발생 없음, mask, BME 꺼짐, 주소 변경. /proc/interrupts + status + lspci MSI.

꼬리2. How do you prove whether the device sent the interrupt? "Read the device's own interrupt status register — if it's set, the device thinks it raised one. Then on real hardware, a protocol analyzer shows whether the MWr to the MSI address went out. If the device sent it but the CPU didn't get it, it's the host side: ITS mapping, IOMMU interrupt remapping, or a masked vector."

  • 한국어 핵심: 장치 status → analyzer의 MWr → host 쪽(ITS/IOMMU/mask).

6.3 드라이버 핵심 부분 (전체는 edu_lp06.c)

static irqreturn_t edu_isr(int irq, void *data)
{
	struct edu *edu = data;
	u32 st = readl(edu->bar0 + EDU_REG_IRQ_STATUS);

	if (!st)
		return IRQ_NONE;	/* shared INTx line: not ours */
	writel(st, edu->bar0 + EDU_REG_IRQ_ACK);	/* edu.rst: ACK is required even with MSI */
	edu->last_irq_status = st;
	edu->irq_count++;
	complete(&edu->done);
	return IRQ_HANDLED;
}

static int edu_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	...
	ret = pcim_enable_device(pdev);                         /* 1. COMMAND.MEM */
	edu->bar0 = pcim_iomap_region(pdev, 0, DRV_NAME);       /* 2. request + ioremap BAR0 */
	if (IS_ERR(edu->bar0))
		return dev_err_probe(dev, PTR_ERR(edu->bar0), "BAR0\n");
	pci_set_master(pdev);                                   /* 3. COMMAND.BME */
	ret = dma_set_mask_and_coherent(dev, DMA_BIT_MASK(dma_bits));   /* 4. */
	flags = force_intx ? PCI_IRQ_INTX : (PCI_IRQ_MSI | PCI_IRQ_INTX);
	nvec = pci_alloc_irq_vectors(pdev, 1, 1, flags);        /* 5. MSI → INTx fallback */
	edu->irq = pci_irq_vector(pdev, 0);
	ret = devm_request_irq(dev, edu->irq, edu_isr,
			       pdev->msi_enabled ? 0 : IRQF_SHARED, DRV_NAME, edu);   /* 6. */
	pci_set_drvdata(pdev, edu);
	edu_selftest(edu);                                      /* 7. device init / test */
	return 0;
}

7. 자주 틀리는 것

  1. pci_set_master 누락 → MMIO는 정상, DMA·MSI만 조용히 실패. lspci BusMaster- 확인.
  2. pcim_iomap_regions() + pcim_iomap_table()을 새 코드에 — 6.18에서 DEPRECATED. pcim_iomap_region() + IS_ERR().
  3. pci_request_irq를 managed로 착각 → remove에서 pci_free_irq 안 하면 모듈 언로드 후 핸들러가 남음. devm_request_irq는 자동.
  4. 장치 인터럽트를 request_irq 전에 켬 → 핸들러 없는 IRQ, INTx면 storm/"nobody cared".
  5. INTx 핸들러가 원인 확인 없이 IRQ_HANDLED → 공유 라인에서 다른 장치 인터럽트를 삼킴. 원인 없으면 IRQ_NONE.
  6. MSI면 ACK 필요 없다고 생각 → edu처럼 status를 안 지우면 다음 이벤트 때 MSI가 다시 안 오는 장치가 많음 (edge 재발생 조건).
  7. write 직후 "장치에 도착했다"고 가정 → posted. 같은 장치 read-back으로 flush.
  8. 64-bit 레지스터를 32-bit 두 번으로 쪼개 씀 → 장치가 하위 write에서 latch하면 반쪽 값으로 동작. edu는 0x84 무시. 데이터시트의 lo/hi 순서 확인.
  9. DMA mask를 장치 능력보다 크게 → 장치가 상위 비트를 잘라 엉뚱한 RAM에 씀(QEMU edu의 edu_clamp_addr가 바로 이 동작을 흉내). 작게 잡으면 ARM에서 실패(§3.4).
  10. remove에서 DMA 정지 없이 버퍼 해제 → use-after-free를 하드웨어가 함. devres는 DMA를 멈춰 주지 않는다. .shutdown도 같음(kexec).
  11. 커널 드라이버가 붙은 채로 resource0 mmap 툴 실행 → 두 주체가 같은 레지스터 조작. 검증 툴은 unbind 후 사용하거나 드라이버의 debugfs를 경유.
  12. "64-bit 시도 → 실패하면 32-bit" 관용구를 정답처럼 말하기 — 옛 드라이버엔 많지만 현행 DMA API HOWTO는 64-bit mask가 never fail이라 이 패턴을 wrong이라고 명시. 면접에선 "장치 능력대로 고르고, 32 미만 mask만 실패 검사"가 최신 답 (LP00 목록의 "64→32 fallback" 문구는 이 노트로 정정).
  13. 옛 예제의 PCI_IRQ_LEGACY — 6.18에선 없음, PCI_IRQ_INTX.
