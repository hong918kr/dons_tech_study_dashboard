## 1. 프로세스 · 스레드 · 왜 스레드를 쓰나

**프로세스**는 실행 중인 프로그램 하나다. 자기만의 주소 공간(메모리 맵)을 가지므로 프로세스 A의 포인터 `0x1000` 과 프로세스 B의 `0x1000` 은 완전히 다른 물리 메모리다.

**스레드**는 같은 프로세스 안에서 **주소 공간을 공유하면서 따로 도는 실행 흐름**이다. 스레드마다 따로 갖는 것은 사실상 **PC(프로그램 카운터), 레지스터, 스택** 뿐이고, 전역 변수와 `malloc` 으로 잡은 힙, 열린 파일 디스크립터는 **전부 공유**다.

베어메탈로 번역하면 이렇다. MCU에서 main loop 와 UART RX ISR 은 같은 메모리를 보고 각자 스택만 다르다. 그게 정확히 스레드 두 개다. 차이는 ISR 은 하드웨어가 강제로 끼어드는 것이고 스레드는 **OS 스케줄러가 아무 때나 끊는다**는 것, 그리고 멀티코어에서는 진짜로 **동시에** 실행된다는 것 — 인터럽트 끄기로는 막을 수 없다.

스레드를 쓰는 이유는 셋 중 하나다.

- **블로킹을 숨기려고**: LTE 모뎀 응답을 기다리는 동안 도어 이벤트 처리는 계속돼야 한다.
- **코어를 쓰려고**: 4코어 게이트웨이에서 파싱/암호화를 나눠 돌린다.
- **역할을 나눠 코드를 단순하게 하려고**: 수집 스레드 / 처리 스레드 / 업로드 스레드.

Verkada GC31-E 같은 게이트웨이 데몬이 딱 이 모양이다. 모뎀 감시, 링크 health check, LAN 쪽 디바이스 관리, 클라우드 업로드가 각각 스레드고 **중간에 큐로 연결**돼 있다. 이 노트 전체가 그 "중간에 있는 것"을 안전하게 만드는 이야기다. POSIX 에서는 API 두 개면 시작할 수 있다.

```c
pthread_create(&cons, NULL, consumer, NULL);
pthread_join(prod[i], NULL);
```

`pthread_create(&tid, attr, fn, arg)` 는 `fn(arg)` 를 실행하는 스레드를 만들고 핸들을 `tid` 에 넣는다(`attr` 은 스택 크기 같은 옵션, `NULL` 이면 기본값). `pthread_join(tid, NULL)` 은 그 스레드가 끝날 때까지 **기다린다.** join 을 안 하면 `main` 이 먼저 끝나 프로세스가 통째로 사라지면서 스레드가 중간에 증발한다.

## 2. 공유가 왜 위험한가 — race condition 을 눈으로

`counter++` 는 C 소스에서는 한 줄이지만 CPU에서는 **세 동작**이다.

```
    load   r0 <- [counter]      ; 메모리에서 레지스터로 읽는다
    add    r0 <- r0 + 1         ; 레지스터에서 더한다
    store  [counter] <- r0      ; 레지스터를 메모리에 쓴다
```

이 세 동작 사이에 다른 스레드가 끼어들 수 있다. 두 스레드가 각각 한 번씩 증가시키는
경우를 시간축으로 펼쳐 보자. 시작값은 10 이다.

```
 시간 ↓   T1                          T2                        메모리[counter]
  t0     load  r0 <- 10                                                10
  t1                                 load  r0 <- 10                    10
  t2     add   r0 = 11                                                 10
  t3                                 add   r0 = 11                     10
  t4     store [counter] <- 11                                         11
  t5                                 store [counter] <- 11             11
```

두 번 증가시켰는데 결과는 11 이다. T2 가 읽은 10 은 이미 **낡은 값**이었고, T1 의 증가는 통째로 덮여 사라졌다. 이것을 **lost update** 라고 부른다. 8만 번 돌리면 결과가 5만 근처에서 아무 값이나 나오고, 실행할 때마다 다르다.

race condition 의 정확한 정의는 "동시에 접근했다"가 아니라 이 셋이 **모두** 성립할 때다.

1. 두 개 이상의 스레드가 같은 메모리 위치에 접근한다
2. 그중 최소 하나는 **쓰기**다
3. 둘 사이의 **순서를 강제하는 동기화가 없다**

셋 중 **하나만 없애도** 문제가 사라진다는 게 중요하다. 쓰기를 없애거나(읽기 전용 데이터), 공유를 없애거나(스레드별로 세다가 마지막에 합치기), 순서를 강제하거나(mutex, atomic, join). 이 노트의 모든 기법은 3번을 만드는 서로 다른 방법일 뿐이다.

race 가 무서운 진짜 이유는 결과가 틀리다는 게 아니라 **거의 항상 맞게 나온다**는 것이다. 개발 보드에서 이틀 동안 멀쩡하다가 현장에 나간 게이트웨이가 3주 뒤 한 번 죽는다. 그래서 "돌려보니 되더라"는 증거가 아니다(§8).

## 3. 임계구역과 mutex

**임계구역(critical section)** 은 "이 구간 안에서는 데이터의 불변식이 잠깐 깨져도 되는, 대신 한 번에 한 스레드만 들어가는 구간"이다. 큐에 항목을 넣는 동안 `tail` 은 이미 움직였는데 `count` 는 아직 안 늘어난 순간이 반드시 존재한다. 그 순간을 남이 보면 안 된다. **mutex(mutual exclusion)** 는 그 구간의 문지기다. `lock` 을 부른 스레드만 들어가고, 이미 누가 들어가 있으면 **잠든다**(스핀하지 않는다 — OS가 스케줄에서 빼버린다).

```c
pthread_mutex_init(&q->m, NULL);
pthread_mutex_lock(&q->m);
pthread_mutex_unlock(&q->m);
pthread_mutex_destroy(&q->m);
```

`pthread_mutex_t` 는 그냥 구조체다. `init` 으로 초기화하고(두 번째 인자 `NULL` = 기본 속성), 쓸 때 `lock`/`unlock`, 다 쓰면 `destroy`.

mutex 를 처음 배울 때 놓치는 게 하나 있다. mutex 는 **상호배제만 주는 게 아니라 메모리 가시성도 준다**. `unlock` 은 release, `lock` 은 acquire 로 동작해서(§5), "A 스레드가 unlock 하기 전에 쓴 모든 것"은 "B 스레드가 그 mutex 를 lock 한 뒤"에 반드시 보인다. 그래서 mutex 로 감싼 데이터는 캐시나 재정렬 문제를 따로 걱정할 필요가 없다. 값이 안 보인다면 **어딘가 락을 안 잡고 접근하는 경로가 있는 것**이다. 지켜야 할 규칙은 넷이다.

- **락은 변수가 아니라 불변식을 보호한다.** `{count, head, tail}` 처럼 같이 맞아야 하는 필드는 반드시 같은 락, 같은 임계구역에서 함께 바꾼다.
- **임계구역은 짧게.** 락을 쥔 채로 `write()`, `printf()`, 콜백 호출, 대용량 memcpy 금지. 문제 03이 이걸 극단까지 밀어붙인 예다(락 안에서는 인덱스 3개만 바꾼다).
- **모든 경로에서 unlock.** 중간 `return`, 에러 분기에서 빠뜨리면 그 자리에서 데드락이다. 01의 `bq_push` 가 `return false` 직전에 `pthread_mutex_unlock` 을 부르는 이유다.
- **락 순서를 하나로 정한다.** 락 두 개 이상을 잡을 일이 생기면 항상 같은 순서로(문제 09).

## 4. 기다리기 — condition variable

mutex 는 "지금 들어가도 되나"를 해결하지만 "**데이터가 생길 때까지 기다린다**"는 못 한다.
락을 쥔 채로 기다리면 데이터를 넣어줄 스레드가 락을 못 잡아서 영원히 멈춘다.

**condition variable(condvar)** 은 **대기열**이다. 락이 아니다. 의미는 하나다:
"지금은 조건이 안 맞으니, **락을 놓고** 나를 재워라. 누가 조건을 바꾸면 깨워라."

```c
pthread_cond_wait(&q->not_empty, &q->m);
pthread_cond_signal(&q->not_empty);
pthread_cond_broadcast(&q->not_empty);
```

`pthread_cond_wait(cv, m)` 은 **세 가지를 원자적으로** 한다.

1. `m` 을 unlock 하고
2. 이 스레드를 `cv` 대기열에 넣고 재우고
3. 깨어날 때 `m` 을 **다시 lock 해서** 돌아온다

1과 2가 원자적이라는 게 핵심이다. 안 그러면 "락을 놓은 직후, 잠들기 직전"에 signal 이 도착해서 그 신호를 놓치고 영원히 자는 **lost wakeup** 이 생긴다. 그래서 `cond_wait` 은 **반드시 mutex 를 잡은 상태에서** 불러야 한다.

### 왜 `if` 가 아니라 `while` 인가

이게 condvar 에서 가장 많이 틀리는 곳이다. 01의 실제 코드는 이렇다.

```c
while (q->count == 0 && !q->closed)
    pthread_cond_wait(&q->not_empty, &q->m);
```

이유 1 — **깨어난다고 조건이 맞다는 보장이 없다.** 소비자가 둘일 때를 보자.
큐는 비어 있고 C1, C2 가 둘 다 `not_empty` 에서 자고 있다.

```
 시간 ↓  생산자 P                    C1                  C2            count
  t0                               wait 중              wait 중          0
  t1    lock / push / count=1                                            1
  t2    unlock + signal(not_empty)
  t3                               깨어남 → lock 시도    깨어남 → lock 시도  1
  t4                               lock 획득            (락 대기)          1
  t5                               count!=0 → pop 수행                    0
  t6                               unlock               lock 획득          0
  t7                                                    count == 0  ← !!
```

t7 에서 C2 는 **깨어났지만 큐는 이미 비어 있다**. `if` 였다면 C2 는 그대로 진행해서
`q->buf[q->head]` 를 읽고 `q->count--` 를 해버린다. count 가 언더플로하고
쓰레기 이벤트가 업로드된다. `while` 이면 조건을 다시 보고 그냥 다시 잔다.

이유 2 — **spurious wakeup**. POSIX 는 아무도 signal 하지 않았는데도 `cond_wait` 이
반환할 수 있다고 명시한다(시그널 처리, 구현 최적화 등). 규격이 허용하는 동작이라
"내 코드는 그럴 일 없다"가 통하지 않는다.

그래서 외울 규칙은 하나다. **조건 검사는 언제나 `while`. condvar 는 "조건이 바뀌었을지도
모른다"는 힌트일 뿐, "조건이 맞다"는 약속이 아니다.**

### signal vs broadcast

- `signal` 은 대기 중인 스레드 **하나**를 깨운다(누구인지는 정해져 있지 않다).
- `broadcast` 는 대기 중인 **전부**를 깨운다.

평상시 push/pop 은 `signal` 이면 충분하다 — 항목 하나를 넣었으니 하나만 깨우면 된다.
그런데 **종료**는 다르다. `closed = true` 는 **대기 중인 모두에게** 해당되는 상태 변화다.

```c
q->closed = true;
pthread_mutex_unlock(&q->m);
/* 대기 중인 모든 스레드를 깨워야 한다 → signal이 아니라 broadcast */
pthread_cond_broadcast(&q->not_empty);
pthread_cond_broadcast(&q->not_full);
```

여기서 `signal` 을 쓰면 하나만 깨어나 종료하고 나머지는 영원히 잔 채로 `join` 이 안 끝난다.
**"모두에게 해당되는 상태 변화면 broadcast"** 가 판단 기준이다.

한 가지 더. 01 은 `unlock` 을 먼저 하고 그다음 `signal` 한다.

```c
pthread_mutex_unlock(&q->m);          /* unlock 먼저 → 깨어난 소비자가 곧장 lock 획득 */
pthread_cond_signal(&q->not_empty);
```

락을 쥔 채로 signal 하면 깨어난 스레드가 `cond_wait` 안에서 락을 다시 잡으려다 바로 다시 잠든다(hurry up and wait). 둘 다 **정확하기는 하다** — 성능 차이일 뿐이다.

## 5. 원자 연산과 memory order

mutex 로 다 되는데 왜 atomic 이 필요한가. ISR 안에서는 mutex 를 쓸 수 없고(스케줄러가 잠재울 수 없다), 바이트 하나 주고받는 데 mutex 는 너무 비싸기 때문이다. C11 의 `_Atomic` 은 두 가지를 준다. **원자성**(§2의 load/add/store 가 쪼개지지 않음)과 **순서(memory order)**. 두 번째가 진짜 어려운 부분이다.

### 컴파일러와 CPU는 순서를 바꾼다

02의 생산자는 개념적으로 이 두 줄이다.

```c
r->buf[t] = b;                         /* 데이터 먼저 */
/* release: 위의 데이터 write가 tail publish 이전에 보이도록 보장 */
atomic_store_explicit(&r->tail, next, memory_order_release);
```

이 둘은 서로 다른 주소를 건드리므로 **단일 스레드 관점에서는 순서를 바꿔도 결과가 같다.**
그래서 컴파일러도 CPU도 마음대로 바꿀 수 있다(store buffer, out-of-order 실행).
바꾸면 이런 일이 생긴다.

```
 실제로 소비자 코어에 보이는 순서
 ─────────────────────────────────────────────────────────
  (2) tail = next      ← 먼저 보임 : "새 바이트 있음!"
  (1) buf[t] = b       ← 아직 안 보임

 소비자:  h != tail 이네 → *out = r->buf[h];   ← 쓰레기 값을 읽는다
```

증상은 "가끔 한 바이트가 이상하다"이다. 100만 바이트에 한 번. 최악의 버그 종류다.

### release / acquire 를 그림으로

`release` 는 **문을 닫으면서 짐을 다 들여놓는 것**, `acquire` 는 **문을 열고 나서 짐을
꺼내는 것**이다. 둘은 **짝으로만** 의미가 있다.

```
 T_생산자 (ISR)                          T_소비자 (task)
 ─────────────────────────────          ─────────────────────────────
  r->buf[t] = b;            ┐
                            │ 이 위의 write 는
                            │ 아래로 내려갈 수 없다
  store(tail, next,         │
        RELEASE)      ●─────┼──── synchronizes-with ───▶ ○ load(tail, ACQUIRE)
                                                          │ 이 아래의 read 는
                                                          │ 위로 올라갈 수 없다
                                                          └ *out = r->buf[h];
                                                             ← b 가 반드시 보인다
```

소비자가 acquire 로 **새 tail 값을 실제로 읽었다면**, 생산자가 release 이전에 쓴 **모든 것**이 소비자에게 보인다. 이것을 happens-before 관계가 생겼다고 말한다. "데이터 먼저, 공개는 나중에(publish)" — 이 한 문장이 release/acquire 의 전부다.

`relaxed` 는 원자성만 주고 순서는 아무것도 보장하지 않는다. 그럼 언제 쓰나. **내가 유일한 writer 라서 남과의 순서를 따질 필요가 없는 값**을 읽을 때다.

```c
unsigned t = atomic_load_explicit(&r->tail, memory_order_relaxed); /* 내가 쓴 값 */
```

`tail` 은 생산자만 쓴다. 생산자가 자기가 쓴 값을 읽는 건 단일 스레드 이야기라 순서 보장이
필요 없다. 반면 상대가 쓴 인덱스를 볼 때는 acquire 를 쓴다.

```c
if (next == atomic_load_explicit(&r->head, memory_order_acquire))
    return false;                      /* full (한 칸은 항상 비워둔다) */
```

| memory order | 보장하는 것 | 언제 쓰나 |
|---|---|---|
| `relaxed` | 원자성만. 순서 보장 없음 | 내가 유일한 writer 인 값을 내가 읽을 때, 통계 카운터 |
| `acquire` | 이 load 이후의 접근이 앞으로 못 넘어옴 | 상대가 publish 한 인덱스/플래그를 **읽을** 때 |
| `release` | 이 store 이전의 접근이 뒤로 못 넘어감 | 데이터를 다 쓴 뒤 인덱스/플래그를 **공개**할 때 |
| `seq_cst` | 전역 단일 순서. 가장 비싸고 가장 안전 | 헷갈리면 일단 이것(기본값). 나중에 완화 |

### `volatile` 로는 안 되는 이유

베어메탈에서 `volatile` 은 매일 쓰던 도구다. 그런데 `volatile` 이 하는 일은 딱 하나다.
**"이 접근을 컴파일러가 지우거나 합치거나 레지스터에 캐싱하지 마라."**
`volatile` 이 하지 **않는** 일은 이것들이다.

- 원자성을 주지 않는다 — `volatile int c; c++;` 는 여전히 load/add/store 세 동작이다.
- **다른 변수와의 순서를 보장하지 않는다** — 위 그림의 재정렬을 전혀 막지 못한다.
- CPU 레벨 메모리 배리어를 넣지 않는다 — 멀티코어에서 캐시 가시성 보장이 없다.

베어메탈 단일 코어에서 `volatile` 링버퍼가 동작했던 이유는 `volatile` 이 옳아서가 아니라
**단일 코어라 재정렬이 관찰되지 않았고, ISR 진입/복귀가 사실상 배리어 역할을 했기** 때문이다.
멀티코어 Cortex-A(게이트웨이)에서는 그 가정이 무너진다. 그래서 `_Atomic` 을 쓴다.
면접에서 이 대비를 직접 말하면 "베어메탈만 아는 사람"이 아니라는 신호가 된다.

## 6. 실시간 데이터 전달 패턴 세 가지

셋 다 "생산자 → 소비자"지만 **느린 소비자를 어떻게 다루느냐**가 다르다. 이 축으로 외운다. 판단 기준은 **"데이터가 기록(record)이냐 상태(state)냐"** 다.

| 패턴 | 소비자가 느리면 | 생산자가 블록되나 | 대표 문제 |
|---|---|---|---|
| 블로킹 큐 (bounded) | 생산자가 기다린다(backpressure) | 예 | 01 |
| 링버퍼 + drop 정책 | 새 데이터를 버리고 카운트 | 아니오 | 02, 05 |
| 더블/트리플 버퍼 | 중간 프레임을 버리고 최신만 | 아니오 | 03, 04 |

출입 이벤트는 기록이라 하나도 잃으면 안 된다 → 블로킹 큐. 센서 측정값이나 신호 품질은 상태라 최신값만 맞으면 된다 → 더블버퍼. UART 바이트 스트림은 기록이지만 ISR 이 기다릴 수 없다 → 링버퍼 + drop 카운터.

**drop 을 조용히 하지 마라.** 버릴 거면 반드시 세고 텔레메트리로 올린다. 03이 `dropped` 를 구조체 필드로 들고 있는 이유고, 면접에서 가산점이 큰 디테일이다.

## 7. 종료와 정리

동시성 코드에서 버그가 가장 많이 남는 곳은 알고리즘이 아니라 **종료 경로**다. "자고 있는 스레드를 어떻게 깨워서 내보내나"가 전부고, 표준 프로토콜은 이 순서다.

1. **상태를 바꾼다** — 락을 잡고 `closed = true` (또는 `stop = true`)
2. **전부 깨운다** — 관련된 모든 condvar 에 `broadcast`
3. **드레인** — 소비자는 남은 항목을 다 처리한 뒤에 루프를 빠져나온다
4. **join** — 모든 스레드가 실제로 끝난 것을 확인한다
5. **자원 해제** — 그 **다음에** `free`, `mutex_destroy`, `cond_destroy`

순서가 뒤집히면 use-after-free 다. 4번 전에 5번을 하면 아직 도는 스레드가 해제된 mutex 를 만진다. 01의 `main` 이 정확히 이 순서다(`bq_close` → `pthread_join(cons, NULL)` → `bq_destroy`). `bq_pop` 이 `false` 를 반환하는 조건이 "닫혔다"가 아니라 **"닫혔고 그리고 비었다"** 인 것도 같은 이유다 — 닫자마자 종료하면 큐에 남은 이벤트가 사라진다.

```c
if (q->count == 0) {                  /* closed && empty → 종료 신호 */
    pthread_mutex_unlock(&q->m);
    return false;
}
```

`while` 조건이 `q->count == 0 && !q->closed` 이므로 여기 도달했다는 건 "비었고, 그리고 닫혔다"는 뜻이다. 이 짧은 구조가 **종료 프로토콜 전체**다.

## 8. 동시성 코드를 어떻게 믿나

"돌려보니 되던데요"는 증거가 아니다. race 는 기본적으로 **잘 동작한다**. 세 가지를 쓴다.

**불변식을 글로 적는다.** 코드를 쓰기 전에 주석으로 남긴다. 예: "`count` 는 항상 0 이상 `cap` 이하", "`tail` 은 생산자만 쓴다", "`reader_idx` 가 가리키는 버퍼는 writer 가 절대 건드리지 않는다". 면접에서 이걸 먼저 말하면 코드가 절반만 완성돼도 점수를 받는다.

**스트레스 + 자기검증 테스트.** 10문제의 self test 가 전부 이 모양이다. 작은 버퍼(01은 cap=8)로 블로킹 경로를 강제하고, 수만 번 돌리고, **끝에 합/개수/순서를 검증**한다. 눈으로 출력을 보는 게 아니라 `assert` 로 자동 판정한다.

```c
assert(ev.seq == last_seq[ev.door_id] + 1);
```

**ThreadSanitizer(TSan).** 컴파일 옵션 하나(`make tsan N=01`)로 "동기화 없이 같은 주소에 접근한 쌍"을 런타임에 잡아준다. 결과가 우연히 맞아도 잡는다는 게 핵심이다. 경고는 `WARNING: ThreadSanitizer: data race` 로 시작하고 충돌한 두 접근의 스택을 같이 보여준다. 느리고(5~15배) 못 잡는 종류도 있지만(락 순서 문제 일부, 실행되지 않은 경로), **깨끗하게 나올 때까지는 아무것도 주장하지 않는다**가 기본 자세다.

참고로 문제 04(seqlock)는 **의도적으로** TSan 경고가 난다. 그래서 `make all-tsan` 이 04만 건너뛴다. 의도된 race 와 버그를 구분할 수 있다는 것도 실력이다.

## 9. 베어메탈 경험 ↔ POSIX 대응표

이미 다 해본 것들이다. 이름만 바꿔 붙이면 된다.

| 베어메탈 / RTOS 에서 하던 것 | Linux 사용자 공간에서 대응하는 것 | 주의할 차이 |
|---|---|---|
| UART RX ISR + main loop | 생산자 스레드 + 소비자 스레드 | 스케줄러가 **아무 때나** 끊는다 |
| `__disable_irq()` / `cli`-`sei` 로 임계구역 | `pthread_mutex_lock` / `unlock` | 멀티코어에서는 인터럽트 끄기가 통하지 않는다 |
| DMA 완료 플래그를 폴링 | `pthread_cond_wait` + 상태 변수 | 폴링 대신 재운다 = CPU/전력 절약 |
| `volatile` 공유 플래그 | `_Atomic` + acquire/release | `volatile` 은 순서를 보장하지 않는다 |
| head/tail 링버퍼 | 문제 02 SPSC ring (`_Atomic` 인덱스) | 구조는 그대로, 인덱스 타입만 바뀐다 |
| ping-pong DMA 버퍼 | 문제 03 double buffer | 락은 데이터가 아니라 **소유권**을 보호 |
| RTOS 세마포어로 태스크 깨우기 | condvar (또는 `sem_t`) | condvar 는 **반드시** mutex 와 한 쌍 |
| 워치독 리셋 | 스레드 health 타임스탬프 + 감시 스레드 | 문제 07 참고 |
| 로직 애널라이저로 타이밍 관찰 | TSan / `perf` / 스트레스 테스트 | 눈으로 보는 대신 도구가 판정 |

## 10. 용어 사전

| 용어 | 한 줄 정의 |
|---|---|
| race condition | 둘 이상이 같은 메모리에 접근하고, 하나 이상이 쓰기이며, 순서 동기화가 없는 상태 |
| critical section | 한 번에 한 스레드만 들어가야 하는 코드 구간 |
| mutex | 임계구역의 문지기. lock/unlock 이 acquire/release 로도 동작한다 |
| condition variable | "조건이 바뀔 때까지 락을 놓고 자는" 대기열. mutex 와 한 쌍 |
| spurious wakeup | 아무도 signal 하지 않았는데 `cond_wait` 이 반환하는 것. 그래서 `while` |
| lost wakeup | 잠들기 직전에 온 signal 을 놓쳐 영원히 자는 것. `cond_wait` 이 원자적인 이유 |
| deadlock | 서로가 쥔 락을 기다려 아무도 못 나아가는 상태 |
| invariant | 임계구역 밖에서는 항상 참이어야 하는 데이터 조건 |
| backpressure | 소비자가 느릴 때 생산자를 늦춰서 균형을 맞추는 것 |
| tearing | 절반만 갱신된 데이터를 읽는 것(앞쪽은 새 값, 뒤쪽은 옛 값) |
| happens-before | "A 가 B 보다 먼저 일어났다"고 언어가 보장하는 순서 관계 |
| memory order | atomic 연산이 주변 접근의 재정렬을 얼마나 막는지의 등급 |
| release / acquire | 데이터를 다 쓰고 공개 / 공개를 보고 데이터를 읽기. 짝으로만 의미 있음 |
| SPSC / MPSC | Single Producer Single Consumer / Multi Producer Single Consumer |
| lock-free | 락 없이 atomic 만으로 동작. 어떤 스레드가 멈춰도 전체는 진행 |
| TSan | ThreadSanitizer. 런타임에 data race 를 잡는 컴파일러 도구 |

## 11. 학습 순서

이 노트를 다 읽었으면 다음 순서로 간다. **01과 03이 최우선**이다 — 01은 업계 표준
인터뷰 문제고, 03은 리크루터 메일에 주제가 직접 적혀 있다.

1. **01 bounded queue** — mutex + condvar 2개 + 종료 프로토콜. 여기서 §3, §4를 손으로 익힌다.
2. **03 double buffer** — "락은 소유권을 보호한다". §6의 최신값 패턴.
3. **02 SPSC ring** — atomic 과 release/acquire. §5를 코드로 확인한다. 베어메탈 링버퍼의 정식 버전.
4. **05 drop policy queue** — 01의 변형. 블로킹 대신 버리기, 그리고 세기.
5. **04 seqlock** — 03의 lock-free 버전. TSan 이 왜 경고하는지 이해하는 게 목적.
6. **06 thread pool**, **07 periodic timer** — 여러 워커와 시간 기반 동작.
7. **08 config swap**, **09 lock order** — refcount 와 데드락 회피.
8. **10 testable driver** — 위 전부를 테스트 가능한 모듈로 묶기.

각 문제는 이렇게 푼다. 해당 노트의 §0~§3 을 읽고 → `starters/NN_*.c` 를 열어 **15분은 혼자** 써 보고 → `make run N=NN` 으로 채점하고 → 막히면 노트 §4 를 단계별로 따라가고 → 마지막에 `make sol N=NN` 과 `make tsan N=NN` 으로 확인한다.

```sh
make list          # 문제 목록
make run N=01      # 내가 푼 것 실행
make sol N=01      # 모범답안 실행
make tsan N=01     # ThreadSanitizer 로 race 검사
```

- [ ] `counter++` 가 왜 안전하지 않은지 3단계로 설명할 수 있다
- [ ] race condition 의 세 조건을 말하고, 셋 중 하나를 없애는 방법을 각각 댈 수 있다
- [ ] `cond_wait` 이 원자적으로 하는 세 가지를 말할 수 있다
- [ ] 조건 검사에 `while` 을 쓰는 이유를 두 가지 댈 수 있다
- [ ] signal 과 broadcast 를 언제 쓰는지 기준을 한 문장으로 말할 수 있다
- [ ] release/acquire 짝이 무엇을 보장하는지 "데이터 먼저, 공개는 나중" 으로 설명할 수 있다
- [ ] `volatile` 이 동기화 도구가 아닌 이유를 세 가지 댈 수 있다
- [ ] 종료 프로토콜 5단계를 순서대로 말할 수 있다
