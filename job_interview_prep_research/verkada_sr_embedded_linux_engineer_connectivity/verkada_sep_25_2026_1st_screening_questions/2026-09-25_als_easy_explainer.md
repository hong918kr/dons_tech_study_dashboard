## 0장. 30초 요약

카메라에 **밝기 센서(ALS)**가 붙어 있다. 센서를 읽는 벤더 함수는 **최대 1초 동안 멈춘다(블로킹)**.
문제는 이것이다.

> "이 느린 함수를, **아무도 기다리지 않고** 언제든 읽을 수 있는 API로 감싸라."

- **Part 1**: `get_most_recent_lux()` — 지금 가장 최근 밝기값
- **Part 2**: `get_lux_at(t)` — 최근 10분 중 **아무 시각 t**의 밝기값

정답의 뼈대는 한 줄이다.

> **기다리는 일은 전담 스레드 한 명에게 맡기고, 나머지는 그 사람이 적어둔 메모만 읽는다.**

## 1장. 문제 다시 읽기 (비유로)

### 벤더 함수가 하는 일

```c
struct SensorReading read_next_sample(void);
```

이 함수를 창밖 밝기를 봐주는 **직원**이라고 생각하자. 부르면 이렇게 행동한다.

| 상황 | 반환 | 걸리는 시간 |
|---|---|---|
| 1초 동안 밝기가 안 변함 | `NO_CHANGE` | **정확히 1초** |
| 중간에 밝기가 변함 | `VALID` + lux + timestamp | 0~1초 (변한 순간) |
| 가끔 고장 (1/10000) | `ERROR`, 값은 쓰레기 | 즉시 |
| **맨 처음 호출** | `VALID` | **안 기다림** |

여기서 **`NO_CHANGE`의 뜻이 중요하다.** "값이 없다"가 아니라 **"안 바뀌었으니 아까 그 값이 여전히 정답"**이다.

### 왜 그냥 쓰면 안 되나

```c
float get_most_recent_lux(void) {
    return read_next_sample().lux;   /* ❌ 이렇게 하면 탈락 */
}
```

세 가지가 동시에 잘못된다.

1. **최대 1초 멈춘다.** "non-blocking API를 만들라"는 요구를 정면으로 어긴다.
2. **`NO_CHANGE`가 오면 lux 칸이 안 채워진다.** 쓰레기 값을 돌려주게 된다.
3. **여러 스레드가 부르면 깨진다.** 벤더 함수는 내부에 `static` 상태와 `rand()`를 쓴다 → thread-safe가 아니다.

## 2장. 핵심 아이디어 — 한 장 그림

```
        ┌─────────────────────────────────────────────────────────┐
        │  sampler 스레드 (딱 1개)                                  │
        │  while (running) {                                       │
        │      r = read_next_sample();   ← 여기서만 기다린다          │
        │      VALID면 메모를 갱신                                   │
        │  }                                                       │
        └───────────────┬─────────────────────┬───────────────────┘
                        │ 최신값               │ 기록
                        ▼                     ▼
              ┌──────────────────┐   ┌──────────────────────────┐
              │ 화이트보드         │   │ 노트 (최근 10분)           │
              │ "지금 3.94 lux"   │   │ (t=0, 3.94)              │
              │  = 한 칸짜리       │   │ (t=1.4s, 3.35)           │
              └────────┬─────────┘   │ (t=1.95s, 5.54) ...      │
                       │             └───────────┬──────────────┘
                       │                         │
        readers ───────┴─────────────────────────┘
        (몇 개든 상관없음. 절대 센서를 기다리지 않는다)
```

### 왜 sampler가 정확히 1개인가 — 면접 단골 질문

- 벤더 함수가 **thread-safe가 아니라서** 2개 이상이면 내부 상태가 깨진다.
- 2개가 돌아도 **정보가 2배가 되지 않는다.** 센서는 하나뿐이다 — 낭비일 뿐이다.
- 0개면? 아무도 센서를 읽지 않으니 메모가 영원히 비어 있다.

> **면접에서 할 말**: "The blocking call lives in exactly one thread. Readers never touch the sensor — they only read state that thread publishes."

## 3장. Part 1 — 최신값 (쉬운 순서로)

### 3.1 먼저 mutex 버전으로 (면접에서도 이걸 먼저 쓴다)

```c
static pthread_mutex_t g_lock = PTHREAD_MUTEX_INITIALIZER;
static float g_latest = NAN;          /* 아직 값 없음 = NAN */

/* sampler 스레드가 VALID를 받았을 때 */
static void publish(float lux) {
    pthread_mutex_lock(&g_lock);
    g_latest = lux;
    pthread_mutex_unlock(&g_lock);
}

/* 누구나 부를 수 있다 */
float get_most_recent_lux(void) {
    pthread_mutex_lock(&g_lock);
    float v = g_latest;
    pthread_mutex_unlock(&g_lock);
    return v;                          /* 센서를 기다리지 않는다 */
}
```

이걸로 **이미 정답이다.** 락을 잡는 시간이 나노초 단위이고, 센서 대기와는 아무 상관이 없다.

### 3.2 그다음 atomic 버전 (모범답안이 쓰는 방식)

락도 없애고 싶다면 "float 한 개"를 원자적으로 바꿔치기하면 된다. 그런데 C에는 `_Atomic float`의 이식성 문제가 있어서, **float을 32비트 정수로 옮겨 담아** 다룬다.

```c
static _Atomic uint32_t g_bits = 0x7FC00000u;   /* NaN의 비트 = "아직 없음" */

static void publish(float lux) {
    uint32_t b;
    memcpy(&b, &lux, sizeof b);                  /* float → 비트 (UB 없이) */
    atomic_store_explicit(&g_bits, b, memory_order_release);
}

float get_most_recent_lux(void) {
    uint32_t b = atomic_load_explicit(&g_bits, memory_order_acquire);
    float v;
    memcpy(&v, &b, sizeof v);                    /* 비트 → float */
    return v;
}
```

**왜 이렇게까지?**
- float 값 하나를 그냥 대입하면 "찢어진 값"이 나올 가능성이 이론적으로 있다(정렬·플랫폼에 따라). `_Atomic uint32_t`는 **표준이 원자성을 보장**한다.
- `memcpy`를 쓰는 이유는 포인터로 타입을 바꿔 읽는 것(strict aliasing 위반)이 C에서 정의되지 않은 동작이기 때문이다. `memcpy`는 컴파일러가 알아서 지운다 — 비용 0.
- 결과적으로 reader는 **원자적 로드 한 번** = 락도, 대기도, 재시도도 없다(wait-free).

### 3.3 "non-blocking"은 세 단계가 있다 — 이걸 말하면 점수

| 단계 | 뜻 | 이 문제에서 |
|---|---|---|
| ① 센서를 기다리지 않음 | getter가 1초 블로킹 호출을 하지 않음 | **최소 요구** |
| ② 아주 짧은 락만 | mutex를 나노초만 잡음 | 3.1 버전 — 충분히 합격 |
| ③ 락도 없음 (wait-free) | 원자적 로드 하나 | 3.2 버전 |

면접에서는 **"어느 의미의 non-blocking을 원하세요?"라고 되묻는 것**이 가장 좋은 첫 반응이다.

### 3.4 시작할 때 — 첫 샘플은 init에서 미리

벤더 함수는 **첫 호출이 안 막힌다**고 했다. 이걸 이용한다.

```c
int init_recent_lux(void) {
    SensorReading r = read_next_sample();   /* 안 막힘 → 공짜로 첫 값 확보 */
    if (r.status == VALID) publish(r.lux);
    running = true;
    pthread_create(&g_thread, NULL, sampler_main, NULL);
    return 0;
}
```

이러면 `init` 직후에 `get_most_recent_lux()`를 불러도 **바로 값이 나온다.** 아니면 첫 1초 동안 NaN이 나온다.

## 4장. Part 2 — 최근 10분 아무 시각

### 4.1 "시각 t의 값"부터 정의한다

센서는 **변할 때만** 알려준다. 그래서 밝기 그래프는 **계단 모양**이다.

```
 lux
  5.54 ┤                         ┌──────────────
  3.94 ┤────────────┐            │
  3.35 ┤            └────────────┘
       └────┬───────┬────────────┬─────────────→ 시간
           0s     1.40s        1.95s
                  ↑ 여기서 3.35로 바뀜
       t = 1.0s  → 3.94   (1.40s 이전이므로 여전히 첫 값)
       t = 1.6s  → 3.35
       t = 2.0s  → 5.54
```

즉 **"t 이하(<=)인 것 중 가장 최근 샘플의 값"**이다. 한 문장으로 정의하고 시작하면 나머지가 다 풀린다.

### 4.2 메모리는 얼마나?

- 진짜 ALS는 빛을 모아 측정하므로 보통 **초당 10번 이하**다.
- 10분 = 600초 → **최대 6000개**.
- 샘플 하나 = `uint64 timestamp + float lux` = 16바이트(패딩 포함).
- 8192개(2의 거듭제곱)로 잡으면 **128KB**. 게이트웨이에서 전혀 부담 없다.

> 이렇게 **숫자로 계산해서 말하는 것**이 임베디드 면접의 핵심이다. "적당히 큰 배열"이라고 하면 안 된다.

### 4.3 자료구조: 링버퍼 + 이진 탐색

- 샘플은 **시간 순서대로만** 들어온다 → 배열이 자동으로 정렬돼 있다.
- 오래된 건 앞에서 버리고 새 건 뒤에 넣는다 → **링버퍼**(고정 크기, malloc 없음).
- 정렬돼 있으니 조회는 **이진 탐색** O(log n). 6000개면 13번 비교면 끝.

```
        tail(가장 오래된)                    head(다음에 쓸 자리)
             ↓                                    ↓
   [ ][ ][ (t=1.4, 3.35) ][ (t=1.95, 5.54) ][ ][ ][ ]
             └──────── 시간 오름차순 ────────┘
```

### 4.4 ★ 가장 중요한 함정 — 10분 경계 직전 샘플을 지우면 안 된다

"10분보다 오래된 건 다 버리자"가 직관인데, **그러면 틀린다.**

```
   지금 시각 = 12:00:00,  창 = 최근 10분 (11:50:00 부터)

   샘플:  11:45  4.0 lux   ← 10분보다 오래됨
          11:58  6.0 lux

   질문: get_lux_at(11:52) = ?
   정답: 4.0   ← 11:45 샘플이 그 시각의 "진짜 값"이다
                  (그 뒤로 안 변했으니까 11:45 값이 계속 유효)

   그런데 11:45 샘플을 "오래됐다"고 지워버리면 → 답할 수 없다 (NaN)
```

그래서 규칙은 이렇게 된다.

> **"다음 샘플도 창 밖일 때만" 가장 오래된 샘플을 버린다.** 창 경계를 덮고 있는 샘플 하나는 남긴다.

모범답안에서 이 부분이다.

```c
while (n >= 2) {
    uint64_t next_ts = buf[(tail + 1) & MASK].ts;
    if (next_ts > now || now - next_ts < WINDOW)   /* 다음 게 아직 창 안이면 */
        break;                                      /* 지금 것은 남겨둔다 */
    tail++;                                         /* 둘 다 창 밖일 때만 버림 */
    n--;
}
```

### 4.5 조회 코드 — 이진 탐색 한 줄씩

```c
float get_lux_at(uint64_t t) {
    uint64_t now = get_timestamp();
    if (t > now || now - t > WINDOW) return NAN;    /* 미래거나 너무 오래됨 */

    pthread_mutex_lock(&lock);
    uint32_t lo = 0, hi = n;                        /* "t보다 큰 첫 샘플" 찾기 */
    while (lo < hi) {
        uint32_t mid = lo + (hi - lo) / 2;
        if (buf[(tail + mid) & MASK].ts <= t) lo = mid + 1;
        else                                  hi = mid;
    }
    float r = (lo > 0) ? buf[(tail + lo - 1) & MASK].lux   /* 그 바로 앞이 정답 */
                       : NAN;                              /* 첫 샘플보다도 과거 */
    pthread_mutex_unlock(&lock);
    return r;
}
```

핵심은 **"t보다 큰 첫 번째 샘플을 찾고, 그 바로 앞을 답한다"**는 것뿐이다(upper_bound).

### 4.6 경계 조건 표 — 먼저 말하면 점수

| 들어온 t | 답 | 왜 |
|---|---|---|
| 미래 | NaN | 아직 모른다 |
| 10분보다 오래됨 | NaN | 보관하지 않는다 |
| 첫 샘플보다 과거 | NaN | 그때 밝기를 모른다 |
| 샘플 시각과 정확히 같음 | 그 샘플 값 | `<=` 이므로 포함 |
| 샘플 사이 | 앞 샘플 값 | 계단 그래프 |

## 5장. 자주 놓치는 세 가지

### ERROR 처리
`ERROR`는 **즉시** 돌아온다. 그냥 `continue`하면 CPU를 100% 태우며 무한 루프를 돈다. → 카운터를 올리고 **10ms쯤 쉬었다가** 재시도. 그리고 `lux`/`timestamp`는 쓰레기이므로 **절대 저장하지 않는다.**

### 시계가 거꾸로 갈 수 있다
`gettimeofday`는 NTP가 조정하면 **뒤로 점프**할 수 있다. 그러면 배열 정렬이 깨져 이진 탐색이 틀린다. → 새 timestamp가 마지막 것보다 작으면 **마지막 값으로 올려서** 저장(단조 증가 유지). 실무에선 `CLOCK_MONOTONIC`을 쓰는 게 정답이라고 덧붙인다.

### 종료
`deinit`에서 플래그를 내리고 `pthread_join`. 단, sampler가 센서 안에서 최대 1초 잠들어 있으므로 **종료에 최대 1초가 걸린다**는 걸 말해준다. join 없이 자원을 해제하면 use-after-free.

## 6장. 면접관이 들으려던 10가지 — 한 줄 답

| # | 질문 | 답 |
|---|---|---|
| 1 | getter가 왜 `read_next_sample()`을 직접 못 부르나 | 최대 1초 블로킹 + `NO_CHANGE`면 값이 없음 + 벤더 함수가 thread-safe 아님 |
| 2 | 누가 센서를 부르나, 몇 개, 왜 1개 | 전담 sampler 스레드 1개. 벤더 함수가 thread-safe가 아니고, 2개여도 정보가 늘지 않음 |
| 3 | "non-blocking"의 뜻 | 3단계(센서 대기 없음 / 짧은 락 / 완전 wait-free). 어느 쪽을 원하는지 되묻는다 |
| 4 | Part 1에 mutex냐 atomic이냐, float 읽기는 원자적인가 | C 표준은 보장하지 않는다. `_Atomic uint32_t`에 비트로 담으면 보장된다. 먼저 mutex로 맞히고 atomic으로 개선 |
| 5 | 10분이면 메모리 얼마 | 최대 10Hz × 600초 = 6000개, 16B → 8192칸 128KB |
| 6 | 자료구조와 조회 비용, 꽉 차면? | 링버퍼 + 이진 탐색 O(log n). 꽉 차면 가장 오래된 것을 버리고 overflow 카운터 |
| 7 | 창 경계의 샘플을 지우나 | **안 지운다.** 다음 샘플도 창 밖일 때만 버린다 |
| 8 | 미래/10분 이전/첫 샘플 이전 | 전부 NaN (또는 에러 코드 반환 API로 바꾸자고 제안) |
| 9 | ERROR / 시계 점프 | ERROR는 저장 안 하고 백오프. 시계 역행은 마지막 값으로 클램프, 실무는 monotonic 시계 |
| 10 | 시작과 종료 | 첫 호출이 안 막히는 걸 이용해 `init`에서 첫 값 확보. 종료는 플래그 + join, 최대 1초 |

## 8장. 다음에 비슷한 문제가 나오면 (일반화)

이 문제는 사실 **하나의 패턴**이다.

> **느리거나 블로킹인 소스** + **아무 때나 읽고 싶은 소비자** → 전담 스레드 1개가 소스를 돌리고, 결과를 **스냅샷(최신값)** 또는 **히스토리(링버퍼)**로 공개한다.

같은 패턴이 쓰이는 곳: 모뎀 신호 세기 폴링, GPS 위치, 온도 센서, 카메라 프레임(= 더블 버퍼), 클라우드 설정 동기화.

그래서 다음에 이런 문제를 만나면 이 순서로 말하면 된다.

1. "이 소스를 부르는 스레드는 하나로 두겠습니다."
