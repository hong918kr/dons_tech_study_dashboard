# Ch.28 락 — 하드웨어 원자 명령과 OS 수면으로 상호 배제 만들기

> 📖 원문: [28. Locks](../book-md/C28_locks.md) · [PDF p.310](../Operating%20Systems%20-%20Three%20Easy%20Pieces.pdf#page=310) · ⏱️ 읽기 약 90분 (실험 포함) · 🔗 선행: [Ch.26](2026-09-30_C26_concurrency_intro.md), [Ch.27](2026-09-30_C27_thread_api.md), [Ch.10](2026-09-30_C10_multiprocessor_scheduling.md)

## 0. 한눈에 보기

- **락(lock)** 은 임계 구역을 "마치 원자 명령 하나처럼" 실행되게 만드는 변수다. 평가 기준은 셋: **정확성(상호 배제)**, **공정성(굶주림 없음)**, **성능(무경쟁 / 단일 CPU 경쟁 / 멀티 CPU 경쟁)**.
- 진화 과정: 인터럽트 끄기(단일 CPU 전용) → 그냥 플래그(틀림) → **test-and-set** 스핀락 → **compare-and-swap** → **LL/SC** (Apple Silicon의 `ldaxr/stxr`) → **fetch-and-add 티켓락**(공정) → **yield** → **큐 + park/unpark**(잠들기) → **futex** → **2단계 락**.
- 결론: 진짜 락 = **하드웨어 원자 명령(빠른 경로) + OS 수면/깨움(느린 경로)**. 리눅스 futex, macOS의 `os_sync_wait_on_address`/`os_unfair_lock` 이 그 구현이다.
- 이 Mac(M2)에서 10가지 락을 직접 만들어 쟀다: 순수 스핀락은 스레드가 늘수록 100–300 ns/op로 나빠지고, **티켓락은 코어 수(8)를 넘기면 361 µs/op로 붕괴**했다. 잠드는 락(futex, pthread)은 16 스레드에서도 약 25–40 ns/op로 평탄했다.

> **THE CRUX: HOW TO BUILD A LOCK** — "How can we build an efficient lock? Efficient locks provided mutual exclusion at low cost, and also might attain a few other properties we discuss below. What hardware support is needed? What OS support?"
>
> → 효율적인 락은 어떻게 만드나? 효율적인 락은 적은 비용으로 상호 배제를 제공하고, 그 밖의 몇 가지 성질도 가질 수 있다. 하드웨어 지원은 무엇이 필요하고, OS 지원은 무엇이 필요한가?

> **THE CRUX: HOW TO AVOID SPINNING** — "How can we develop a lock that doesn't needlessly waste time spinning on the CPU?"
>
> → CPU 위에서 쓸데없이 돌며 시간을 낭비하지 않는 락은 어떻게 만드나?

## 1. 5분 복습표

| 용어 | 한 줄 뜻 | 예시 / 비유 |
|---|---|---|
| 락(lock) / mutex | 임계 구역에 한 스레드만 들여보내는 변수 | `pthread_mutex_t` |
| owner | 지금 락을 잡고 있는 스레드 | 열쇠를 가진 사람 |
| coarse / fine-grained | 큰 락 하나 vs 데이터마다 작은 락 | 리눅스 BKL vs 오늘날 커널 |
| 스핀락(spin lock) | 풀릴 때까지 CPU를 돌며 기다리는 락 | 커널 `spinlock_t` |
| test-and-set (atomic exchange) | 옛 값을 읽으면서 새 값을 쓰기, 원자적으로 | x86 `xchg`, ARM `swp` |
| compare-and-swap (CAS) | 기대값과 같을 때만 새 값으로 바꾸기 | x86 `lock cmpxchg`, ARM `cas` |
| LL/SC | 읽고 감시 → 그 사이 아무도 안 썼을 때만 쓰기 성공 | ARM `ldaxr/stxr`, MIPS `ll/sc` |
| fetch-and-add | 값을 1 올리고 옛 값을 돌려주기 | ARM `ldadd`, x86 `lock xadd` |
| 티켓락(ticket lock) | 번호표 + 현재 차례로 FIFO 보장 | 은행 번호표 |
| 굶주림(starvation) | 경쟁에서 계속 져서 영원히 못 들어감 | TAS 스핀락의 최악 |
| yield | "나 말고 다른 애 돌려줘" 시스템콜 | `sched_yield()` |
| park / unpark | 잠들기 / 특정 스레드 깨우기 (Solaris) | 대기 큐 |
| wakeup/waiting race | 잠들기 직전에 깨우기가 먼저 와서 영원히 잠듦 | `setpark()` 로 해결 |
| futex | 사용자 공간 정수 + 커널 대기 큐 | 리눅스 `futex(2)`, macOS `os_sync_wait_on_address` |
| 2단계 락(two-phase lock) | 잠깐 스핀 → 그래도 안 되면 잠듦 | glibc adaptive mutex |
| 메모리 순서(memory ordering) | 다른 코어에 쓰기가 보이는 순서 규칙 | acquire/release, `dmb` |

## 2. 락의 기본 아이디어 (28.1 – 28.2)

```c
lock_t mutex;          // 전역 락 변수
...
lock(&mutex);
balance = balance + 1; // 임계 구역
unlock(&mutex);
```

락은 그냥 **변수**다. 상태는 둘: **풀림(available/unlocked/free)** 또는 **잡힘(acquired/locked/held)**. 구현에 따라 누가 잡고 있는지(owner), 기다리는 순서(queue) 같은 정보를 더 담을 수 있지만 사용자에게는 감춰진다.

- `lock()`: 풀려 있으면 잡고 리턴. 잡혀 있으면 **풀릴 때까지 리턴하지 않는다.**
- `unlock()`: 기다리는 스레드가 없으면 그냥 풀림으로. 있으면 그중 하나가 (결국) 알아채고 잡는다.

락은 프로그래머에게 **스케줄링에 대한 최소한의 통제권**을 돌려준다. 스레드는 OS가 마음대로 스케줄하지만, 락으로 감싼 코드에는 한 번에 하나만 들어간다는 것만은 프로그래머가 보장할 수 있다.

POSIX는 락을 **mutex**(mutual exclusion)라 부른다. 락 변수를 인자로 받으므로 데이터마다 다른 락을 쓸 수 있다:

- **coarse-grained**: 큰 락 하나로 모든 임계 구역을 보호 → 단순하지만 동시성이 낮다.
- **fine-grained**: 자료구조마다 다른 락 → 여러 스레드가 동시에 서로 다른 락 안에 있을 수 있다 ([Ch.29](2026-09-30_C29_concurrent_data_structures.md)).

## 3. 락을 어떻게 평가하나 (28.3 – 28.4)

| 기준 | 질문 |
|---|---|
| 정확성 | 상호 배제를 제공하나? 두 스레드가 동시에 임계 구역에 못 들어가나? |
| 공정성 | 경쟁하는 스레드마다 공평한 기회가 있나? **굶주리는** 스레드가 있나? |
| 성능 (무경쟁) | 스레드 하나가 잡고 풀 때의 오버헤드는? |
| 성능 (단일 CPU 경쟁) | 한 CPU에서 여러 스레드가 다툴 때 낭비는? |
| 성능 (멀티 CPU 경쟁) | 여러 CPU의 스레드가 다툴 때는? |

이 표의 다섯 줄을 §17의 벤치마크로 이 Mac에서 전부 측정한다.

## 4. 인터럽트 끄기 (28.5)

단일 프로세서 시절의 첫 해법:

```c
void lock()   { DisableInterrupts(); }
void unlock() { EnableInterrupts(); }
```

인터럽트가 없으면 문맥 교환도 없으니, 임계 구역이 원자적으로 실행된다. **장점은 단순함.** 단점은 많다:

1. **특권 명령을 아무 스레드에게나 허용해야 한다.** 탐욕스러운 프로그램이 lock()만 부르고 CPU를 독점하거나, 무한 루프에 빠지면 OS는 영원히 제어를 못 찾는다 → 재부팅밖에 없다.
2. **멀티프로세서에서 안 된다.** 내 CPU의 인터럽트를 꺼도 다른 CPU의 스레드는 임계 구역에 들어온다.
3. **인터럽트를 잃을 수 있다.** 오래 꺼 두면 디스크 I/O 완료 같은 이벤트를 놓친다.
4. **느리다.** 인터럽트 마스킹/언마스킹은 현대 CPU에서 일반 명령보다 느리게 실행되는 경향이 있다.

그래서 인터럽트 끄기는 **OS 내부에서 제한적으로만** 쓴다. OS는 자기 자신을 믿으니 신뢰 문제가 없다. (리눅스의 `spin_lock_irqsave()` = 이 CPU의 인터럽트 끄기 + 다른 CPU를 막는 스핀락, 두 개를 합친 것.)

### 4.1 ASIDE: Dekker와 Peterson — 하드웨어 도움 없는 락

```c
int flag[2]; int turn;
void init()   { flag[0] = flag[1] = 0; turn = 0; }
void lock()   {
    flag[self] = 1;          // 나 들어가고 싶어
    turn = 1 - self;         // 그래도 네 차례로 양보
    while ((flag[1-self] == 1) && (turn == 1 - self))
        ;                    // 상대가 원하고, 상대 차례면 기다림
}
void unlock() { flag[self] = 0; }
```

- `flag`: "들어가고 싶다"는 의사 표시. `turn`: 둘 다 원할 때의 양보 순서.
- 둘 다 동시에 들어오려 하면 **turn에 마지막으로 쓴 쪽이 기다린다** (양보한 쪽이 지는 구조).
- 로드와 스토어만으로 2-스레드 상호 배제가 된다. 하지만 책은 **"현대 하드웨어에선 안 된다(relaxed memory consistency)"** 고 한 줄로 넘어간다.

이 Mac에서 정말 안 되는지 확인했다 (§17.3): `volatile int` 로 짠 Peterson은 2×2,000,000번 중 **1~6번 상호 배제가 깨졌다.** 이유: ARM은 `flag[self]=1` (store)이 다른 코어에 보이기 전에 그 뒤의 `flag[other]` (load)를 먼저 실행할 수 있다(**store→load 재배치**, 스토어 버퍼). 그러면 두 스레드가 서로의 flag를 0으로 읽고 동시에 들어간다. C11 `seq_cst` 원자 변수로 바꾸면(arm64 `stlr`/`ldar`) 손실 0이 된다.

## 5. 첫 시도: 그냥 플래그 하나 (28.6, Figure 28.1)

```c
typedef struct __lock_t { int flag; } lock_t;
void init(lock_t *mutex) { mutex->flag = 0; }       // 0 → 풀림, 1 → 잡힘
void lock(lock_t *mutex) {
    while (mutex->flag == 1)   // TEST
        ;                      // spin-wait
    mutex->flag = 1;           // SET
}
void unlock(lock_t *mutex) { mutex->flag = 0; }
```

문제 두 개.

**정확성**: TEST와 SET 사이에 끼어들 수 있다 (Figure 28.2).

| Thread 1 | Thread 2 |
|---|---|
| lock(): `while (flag == 1)` → 0이므로 통과 | |
| *인터럽트 → T2로* | |
| | lock(): `while (flag == 1)` → 0이므로 통과 |
| | `flag = 1` → 임계 구역 진입 |
| | *인터럽트 → T1로* |
| `flag = 1` → **임계 구역 진입 (둘 다!)** | |

시뮬레이터로 정확히 이 스케줄을 강제해 보면(-P) count가 2가 아니라 1이 된다 (§17.4).

**성능**: 기다리는 스레드가 `flag` 를 끝없이 확인하는 **spin-waiting**. 단일 CPU에선 특히 낭비가 심하다 — 기다리는 상대(락 주인)는 내가 CPU를 놓아야 돌 수 있는데, 나는 타임슬라이스 끝까지 돌기만 한다.

> **TIP — THINK ABOUT CONCURRENCY AS A MALICIOUS SCHEDULER** — 가장 나쁜 순간에 인터럽트를 거는 **악의적인 스케줄러**인 척 생각하라. 그런 순서가 아무리 드물어도 **가능하기만 하면** 그 방법은 틀린 것이다.

## 6. 동작하는 스핀락: test-and-set (28.7)

하드웨어가 TEST와 SET을 **한 명령으로 원자적으로** 해 준다면? SPARC `ldstub`, x86 `xchg`, ARMv8.1 `swp` 가 그것이다. 의미를 C로 쓰면:

```c
int TestAndSet(int *old_ptr, int new) {
    int old = *old_ptr;  // 옛 값 읽기
    *old_ptr = new;      // 새 값 쓰기
    return old;          // 옛 값 돌려주기
}                        // ← 이 3줄이 하드웨어에서 원자적으로
```

```c
void lock(lock_t *lock) {
    while (TestAndSet(&lock->flag, 1) == 1)
        ;  // spin
}
void unlock(lock_t *lock) { lock->flag = 0; }
```

왜 동작하나? 두 경우만 보면 된다.

- **flag=0 (풀림)**: TestAndSet이 0을 돌려주므로 while을 빠져나가고, **동시에 flag=1로 바뀌어 있다.** 락 획득.
- **flag=1 (잡힘)**: TestAndSet이 1을 돌려주고 1을 다시 쓴다(변화 없음). 계속 돈다. 주인이 0으로 풀면 다음 TestAndSet이 0을 받고 1을 쓰며 획득.

검사와 설정이 하나의 원자 연산이므로 **오직 한 스레드만** 0을 받는다. 단일 CPU에서 제대로 쓰려면 **선점형 스케줄러**(타이머 인터럽트)가 필요하다. 선점이 없으면 스핀하는 스레드가 CPU를 영원히 안 놓는다.

## 7. 스핀락 평가 (28.8)

| 기준 | 결과 |
|---|---|
| 정확성 | ✔ 상호 배제 보장 |
| 공정성 | ✘ **보장 없음.** 경쟁 중 한 스레드가 영원히 질 수 있다 (굶주림) |
| 성능, 단일 CPU | ✘ 주인이 임계 구역에서 선점되면 나머지 N−1개가 **각자 타임슬라이스 전체를 헛돌림** |
| 성능, 멀티 CPU | △ 스레드 수 ≈ CPU 수이고 임계 구역이 짧으면 꽤 좋다 (다른 코어에서 곧 풀리므로) |

### 7.1 계산 예: 단일 CPU에서 스핀으로 낭비되는 시간

- 원문 상황: 스레드 N개, 한 CPU, 타임슬라이스 10 ms. 주인이 임계 구역에서 선점됨.
- 나머지 N−1개가 차례로 돌며 각자 10 ms씩 헛돈다 → 낭비 = (N−1) × 10 ms.
- N=2 → 10 ms, N=4 → 30 ms, **N=100 → 990 ms**. 1초 가까이 아무 일도 안 한다.

새 예제 (멀티 CPU, 이 Mac 실측 기반): 8코어에 TAS 스레드 16개. 실측 308 ns/op(§17.2). 무경쟁 5 ns 대비 **약 60배**. 이 차이는 거의 전부 캐시라인 핑퐁(락 변수가 든 128B 라인의 독점 소유권이 코어 사이를 오감)과 선점된 주인을 기다리는 시간이다.

## 8. compare-and-swap (28.9)

```c
int CompareAndSwap(int *ptr, int expected, int new) {
    int actual = *ptr;
    if (actual == expected)
        *ptr = new;
    return actual;
}

void lock(lock_t *lock) {
    while (CompareAndSwap(&lock->flag, 0, 1) == 1)
        ;  // spin
}
```

"flag가 0이면 1로 바꿔라"를 원자적으로. 스핀락으로 쓸 때는 test-and-set과 동작이 같다. 하지만 CAS가 **더 강력한** 이유는 "내가 본 값에서 아무도 안 바꿨을 때만 내 계산 결과를 반영"하는 **낙관적 갱신**이 가능하기 때문이다:

```c
// 락 없이 아무 연산이나 원자적으로 (예: 최댓값 갱신)
int old = *p;
while (!CAS(p, old, max(old, v)))   // 실패하면 old 가 최신값으로 갱신된 뒤 재시도
    old = *p;
```

이게 **락-프리(lock-free)** 자료구조의 기본 벽돌이다 ([Ch.32](2026-09-30_C32_concurrency_bugs.md) 참고). 책에 나온 x86 인라인 어셈블리는 `lock cmpxchgl` + `sete` 이고, M2에서는 `casa` 한 명령이 된다 (§17.1).

## 9. Load-Linked / Store-Conditional (28.10) — Apple Silicon이 원래 쓰던 방식

MIPS(`ll/sc`), Alpha, PowerPC(`lwarx/stwcx`), **ARM(`ldrex/strex`, ARMv8의 `ldxr/stxr`)** 이 제공하는 명령 쌍이다.

```c
int LoadLinked(int *ptr) { return *ptr; }           // 읽고, 이 주소를 '감시' 시작
int StoreConditional(int *ptr, int value) {
    if (no one has updated *ptr since the LoadLinked to this address) {
        *ptr = value;
        return 1;   // 성공
    } else {
        return 0;   // 실패 (아무것도 안 씀)
    }
}

void lock(lock_t *lock) {
    while (1) {
        while (LoadLinked(&lock->flag) == 1)
            ;                                   // 0 이 될 때까지
        if (StoreConditional(&lock->flag, 1) == 1)
            return;                             // 1 로 바꾸기 성공 → 획득
        // 실패 → 처음부터
    }
}
// David Capel 의 한 줄 버전:
// while (LoadLinked(&lock->flag) || !StoreConditional(&lock->flag, 1)) ;
```

두 스레드가 둘 다 LL로 0을 읽고 SC를 시도해도, **먼저 SC한 쪽만 성공**한다. 두 번째 SC는 "그 사이 누가 썼다"는 게 감지되어 실패하고 처음부터 다시 한다.

### 9.1 ARM64에서 실제로: exclusive monitor

ARM은 이 "감시"를 **exclusive monitor** 라는 하드웨어로 구현한다.

- `ldaxr w0, [x1]`: **Load-Acquire eXclusive Register**. 값을 읽고, 그 주소(정확히는 그 주소를 포함하는 블록, 보통 캐시라인)에 대해 이 코어의 monitor를 "exclusive" 상태로 만든다. `a` 는 acquire 순서(이후 메모리 접근이 이 load보다 앞서 보이지 않음).
- `stxr w2, w3, [x1]`: **Store eXclusive**. monitor가 아직 exclusive면 저장하고 `w2=0`(성공), 그 사이 다른 코어가 그 라인에 썼으면(캐시 일관성 프로토콜이 무효화를 보내면 monitor가 풀림) 저장하지 않고 `w2=1`(실패).
- `stlxr`: Store-Release eXclusive. 이전 접근들이 이 store보다 먼저 보이도록 보장.
- `clrex`: monitor를 수동으로 해제.

이 Mac에서 C11 원자 연산을 **LSE 없는 ARMv8.0(-mcpu=apple-a7)** 으로 컴파일하면 컴파일러가 정확히 Figure 28.6 모양의 LL/SC 루프를 만든다 (§17.1):

```text
_tas:
	mov	w9, #1
LBB0_1:
	ldaxr	w8, [x0]        ; LoadLinked
	stxr	w10, w9, [x0]   ; StoreConditional, w10 = 0 성공 / 1 실패
	cbnz	w10, LBB0_1     ; 실패하면 다시
```

반면 기본 설정(M1/M2 = ARMv8.5)으로 컴파일하면 **LSE(Large System Extensions)** 원자 명령 한 개로 끝난다: TAS → `swpa`, CAS → `casa`, fetch-and-add → `ldadd`. ARMv8.1에서 LSE가 추가된 이유가 바로 **코어가 많을 때 LL/SC 루프가 경쟁으로 계속 실패(livelock 경향)하는 문제** 때문이다 — 원자 연산을 캐시/인터커넥트 쪽에서 한 번에 처리(far atomic)할 수 있게 했다.

## 10. fetch-and-add 와 티켓락 (28.11)

```c
int FetchAndAdd(int *ptr) {
    int old = *ptr;
    *ptr = old + 1;
    return old;
}

typedef struct __lock_t { int ticket; int turn; } lock_t;
void lock_init(lock_t *lock) { lock->ticket = 0; lock->turn = 0; }
void lock(lock_t *lock) {
    int myturn = FetchAndAdd(&lock->ticket);  // 번호표 뽑기
    while (lock->turn != myturn)
        ;                                     // 내 번호 불릴 때까지
}
void unlock(lock_t *lock) { lock->turn = lock->turn + 1; }  // 다음 번호
```

**은행 번호표**다. `ticket` 은 번호표 기계, `turn` 은 전광판. 결정적 차이: **모든 스레드의 진행이 보장된다.** 번호표를 뽑은 순간 내 앞 사람 수가 확정된다. TAS 스핀락은 이런 보장이 없어서 운 나쁜 스레드가 영원히 질 수 있다.

티켓락의 숨은 약점: **다음 차례 스레드가 CPU에 없으면 모두가 기다린다.** TAS는 "아무나 먼저 잡는 쪽"이 진행하지만, 티켓락은 "정해진 그 스레드"만 진행할 수 있다. 스레드 수가 코어 수를 넘으면 다음 차례가 선점되어 있을 확률이 높아지고 성능이 붕괴한다 — 이 Mac 실측에서 T=16일 때 **361 µs/op** (pthread 24 ns/op의 약 15,000배, §17.2).

티켓락은 **리눅스 커널의 스핀락**으로 실제로 쓰였다(2008년 2.6.25부터). 그 후 캐시라인 하나를 모든 코어가 바라보는 문제 때문에 **MCS 락**([MS91] Mellor-Crummey & Scott, 각자 자기 노드를 spin) 기반의 **qspinlock** 으로 바뀌었다(2015년 4.2 무렵).

## 11. 너무 많은 스핀: 이제 어쩌지? (28.12)

하드웨어 락은 단순하고 정확하다. 문제는 **선점된 주인을 기다리며 스핀하는 낭비**다. 단일 CPU에서 주인이 임계 구역 도중 인터럽트되면, 기다리는 스레드는 **값이 바뀔 리 없는** 변수를 타임슬라이스 내내 확인한다. N개면 N−1 타임슬라이스.

**하드웨어만으로는 해결할 수 없다. OS의 도움이 필요하다.**

## 12. 단순한 접근: 그냥 양보 (28.13, Figure 28.8)

```c
void lock() {
    while (TestAndSet(&flag, 1) == 1)
        yield();   // 스핀 대신 CPU 양보
}
```

`yield()` 는 호출자를 running → **ready** 로 옮기는 시스템콜이다(blocked가 아니다). 즉 스스로를 deschedule한다.

- 2 스레드, 1 CPU: 잘 동작. 락이 잡혀 있으면 양보 → 주인이 돌아 마저 끝냄.
- **100 스레드**: 주인이 선점되면 나머지 99개가 각각 "돌고 → 양보"를 반복한 뒤에야 주인 차례가 온다. 스핀(99 타임슬라이스 낭비)보단 낫지만 **문맥 교환 99번**의 비용이 크다.
- **굶주림은 여전하다.** 운 나쁜 스레드는 양보만 하다 끝날 수 있다.

계산 예: 문맥 교환 1회 ≈ 2–5 µs라고 하면, 99번 = 약 0.2–0.5 ms. 스핀으로 99 × 10 ms ≈ 1 s 낭비하던 것보다 1000배 이상 낫지만, 여전히 0이 아니고 스레드 수에 비례한다.

## 13. 큐 사용: 스핀 대신 잠들기 (28.14, Figure 28.9)

진짜 문제는 **너무 많은 걸 운(스케줄러)에 맡긴 것**이다. 다음에 누가 락을 받을지 **명시적으로** 정해야 한다. 그러려면 OS 지원 + 대기자 큐가 필요하다. Solaris 방식:

- `park()`: 호출한 스레드를 잠재운다.
- `unpark(threadID)`: 특정 스레드를 깨운다.

```c
typedef struct __lock_t { int flag; int guard; queue_t *q; } lock_t;

void lock(lock_t *m) {
    while (TestAndSet(&m->guard, 1) == 1)
        ;                         // guard 를 스핀으로 잡는다 (아주 짧은 구간)
    if (m->flag == 0) {
        m->flag = 1;              // 락 획득
        m->guard = 0;
    } else {
        queue_add(m->q, gettid());
        m->guard = 0;
        park();                   // 잠든다
    }
}

void unlock(lock_t *m) {
    while (TestAndSet(&m->guard, 1) == 1)
        ;
    if (queue_empty(m->q))
        m->flag = 0;              // 아무도 안 기다림 → 풀기
    else
        unpark(queue_remove(m->q)); // 락을 다음 스레드에 '직접 전달' (flag 는 1 그대로)
    m->guard = 0;
}
```

읽는 포인트 네 개:

1. **guard는 스핀락**이지만 보호하는 건 flag와 큐 조작 **몇 개의 명령**뿐이다. 사용자 임계 구역(임의로 길 수 있음)을 스핀으로 기다리는 게 아니므로 낭비가 제한된다.
2. **큐 = FIFO** → 굶주림이 없다.
3. **unlock이 flag를 0으로 안 내린다.** 깨어난 스레드는 park()에서 리턴할 뿐 guard를 갖고 있지 않으니 flag를 1로 설정할 수 없다. 그래서 락을 **풀지 않고 그대로 넘겨준다(handoff)**.
4. (책의 질문) guard 해제를 park() **뒤로** 옮기면? → 잠든 스레드가 guard를 쥔 채 자므로 **아무도 lock/unlock을 못 해서 전체가 멈춘다.**

### 13.1 wakeup/waiting race 와 setpark()

`m->guard = 0;` 과 `park();` 사이에 끼어들면?

1. T1: 큐에 자기를 넣고 guard 해제. 아직 park 전.
2. *문맥 교환* → 주인 T2가 unlock: 큐에서 T1을 꺼내 `unpark(T1)`. 그런데 T1은 아직 안 잤다 → 깨우기가 허공에.
3. T1 다시 실행 → `park()` → **영원히 잠듦** (깨워 줄 사람이 이미 지나감).

Solaris의 해결: `setpark()` — "나 곧 잘 거야"를 미리 선언. 그 뒤 park 전에 unpark가 오면 park가 **즉시 리턴**한다.

```c
queue_add(m->q, gettid());
setpark();      // 새 코드
m->guard = 0;
park();
```

다른 해결: guard를 커널에 넘겨서, 커널이 "락 해제 + 잠들기"를 원자적으로 하게 한다. → 이게 바로 다음의 futex 아이디어이고, [Ch.27](2026-09-30_C27_thread_api.md)/[Ch.30](2026-09-30_C30_condition_variables.md)의 `pthread_cond_wait(cond, mutex)` 가 mutex를 인자로 받는 이유와 같다.

## 14. OS마다 다른 지원: futex (28.15)

리눅스 **futex**(fast userspace mutex): 사용자 공간의 정수 하나 + 커널 안의 그 주소별 대기 큐.

- `futex_wait(addr, expected)`: `*addr == expected` 이면 잠든다. **다르면 즉시 리턴.** (검사와 잠들기가 커널 안에서 원자적 → wakeup/waiting race 해결)
- `futex_wake(addr)`: 그 주소에서 자는 스레드 하나를 깨운다.

glibc nptl의 `lowlevellock.h` 에서 가져온 Figure 28.10:

```c
void mutex_lock (int *mutex) {
  int v;
  /* Bit 31 was clear, we got the mutex (this is the fastpath) */
  if (atomic_bit_test_set (mutex, 31) == 0)
    return;
  atomic_increment (mutex);
  while (1) {
      if (atomic_bit_test_set (mutex, 31) == 0) {
          atomic_decrement (mutex);
          return;
      }
      /* We have to wait now. First make sure the futex value
         we are monitoring is truly negative (i.e. locked). */
      v = *mutex;
      if (v >= 0)
        continue;
      futex_wait (mutex, v);
  }
}

void mutex_unlock (int *mutex) {
  /* Adding 0x80000000 to the counter results in 0 if and only if
     there are not other interested threads */
  if (atomic_add_zero (mutex, 0x80000000))
    return;
  /* There are other threads waiting for this mutex, wake one of them up. */
  futex_wake (mutex);
}
```

정수 하나에 두 정보를 담는다: **bit 31 = 잡힘 여부**(그래서 잡히면 음수), **나머지 비트 = 대기자 수**.

### 14.1 계산 예: futex 정수 값 따라가기

| 단계 | 동작 | mutex 값 (16진) | 해석 |
|---|---|---|---|
| 0 | 초기 | 0x00000000 | 풀림, 대기 0 |
| 1 | A: bit_test_set(31) → 0 반환 (fast path) | 0x80000000 | 잡힘, 대기 0 |
| 2 | B: bit_test_set(31) → 1 반환 (실패) | 0x80000000 | |
| 3 | B: atomic_increment | 0x80000001 | 잡힘, 대기 1 |
| 4 | B: 재시도 실패, v = 0x80000001 (음수) → futex_wait(mutex, v) | 0x80000001 | B 잠듦 |
| 5 | A: unlock, +0x80000000 | 0x00000001 | 0이 아님 → 대기자 있음 |
| 6 | A: futex_wake | 0x00000001 | B 깨움 |
| 7 | B: bit_test_set(31) → 0 반환 → 획득 | 0x80000001 | |
| 8 | B: atomic_decrement | 0x80000000 | 잡힘, 대기 0 |
| 9 | B: unlock, +0x80000000 → 0 (32비트 넘침) | 0x00000000 | 0 → wake 생략 |

**무경쟁일 때(0→1→9 경로)는 원자 명령 2개, 시스템콜 0개.** 이게 "흔한 경우를 빠르게"다. 4단계에서 `v` 를 넘기는 이유: 그 사이 A가 unlock해서 값이 바뀌었다면 futex_wait가 **바로 리턴**한다 — 잠들기 직전 깨우기를 놓치는 문제가 구조적으로 없다.

### 14.2 macOS에서는?

- macOS 커널(XNU)에도 같은 기능이 있다: 오랫동안 비공개 `__ulock_wait/__ulock_wake` 였고, **macOS 14.4부터 공개 API `os_sync_wait_on_address()` / `os_sync_wake_by_address_any()`** 가 생겼다 (헤더 `<os/os_sync_wait_on_address.h>`). 의미는 futex_wait/wake와 같다: "주소의 값이 expected면 잠들어라".
- `os_unfair_lock`: 이 위에 만든 Apple의 저수준 락. 헤더 설명에 따르면 락 값에 **소유 스레드 정보**를 담아 커널이 **우선순위 역전(priority inversion)** 을 해결하는 데 쓴다. 이름 그대로 공정성은 시도하지 않는다 (풀자마자 다시 잡을 수 있음).
- `pthread_mutex_t`: 커널의 psynch 대기 큐를 쓰는 범용 뮤텍스. 정책 속성이 FAIRSHARE(1)/FIRSTFIT(3) 두 가지인데, `pthread_mutexattr_getpolicy_np` 로 확인한 이 Mac의 **기본값은 3(FIRSTFIT)** 이었다.

§17.2의 `futex` 락은 Drepper의 "Futexes Are Tricky" 3-상태 뮤텍스(0=풀림, 1=잡힘·대기자 없음, 2=잡힘·대기자 있을 수 있음)를 `os_sync_wait_on_address` 로 직접 구현한 것이다.

## 15. 2단계 락 (28.16)

리눅스 락은 오래된 아이디어(1960년대 Burroughs의 **Dahm Lock**)의 변형인 **2단계 락(two-phase lock)** 이다.

- **1단계**: 락이 곧 풀릴 것 같으니 **잠깐 스핀**한다. 잡으면 시스템콜 없이 끝.
- **2단계**: 그래도 못 잡으면 **잠든다**. 풀리면 깨어난다.

위의 glibc 코드는 스핀을 한 번만 하는 셈이고, 일반화하면 일정 시간/횟수 스핀 후 futex로 잠든다. **하이브리드**: 두 좋은 아이디어를 섞으면 더 좋을 수 있다. 다만 하드웨어, 스레드 수, 워크로드에 따라 다르다 — 모든 경우에 좋은 단일 범용 락을 만드는 건 어렵다.

판단 기준(경험칙): 문맥 교환 왕복 비용이 C, 락 보유 시간이 H라면 **H < C 면 스핀이 유리**, H > C 면 잠드는 게 유리. 모르면 **C만큼 스핀하고 잠들기** — 최악에도 최적의 2배 이내라는 고전적 경쟁비(competitive ratio) 결과가 있다(스키 대여 문제와 같은 구조).

이 Mac 실측(§17.2): futex(스핀 없음) T=8에서 잠든 횟수 20,623회, twophase(200회 스핀) 37,613회. **이번 측정에서는 스핀 단계가 잠듦을 줄이지 못했고 처리량도 비슷하거나 약간 나빴다** — 임계 구역이 `counter++` 하나라 너무 짧고, 200번 스핀 동안 캐시라인을 두드리는 비용이 오히려 경쟁을 키웠을 수 있다. "하이브리드가 좋은지는 워크로드에 달렸다"는 책의 말 그대로다.

## 16. 요약 (28.17)

진짜 락은 이렇게 만든다: **더 강력한 하드웨어 명령 하나 + OS 지원**(Solaris의 park/unpark, 리눅스의 futex, macOS의 ulock/os_sync). 세부는 다르고 실제 코드는 매우 튜닝되어 있다. 현대 멀티프로세서에서 여러 락 전략을 비교한 연구로는 David 등의 SOSP'13 논문 [D+13]을 보라.

### 17.1 C11 원자 연산이 M2에서 어떤 명령이 되나 — C28_atomics_asm.c

```c
// C28_atomics_asm.c — C11 원자 연산이 Apple Silicon(arm64)에서 어떤 명령으로 바뀌는지 본다.
//   cc -O2 -S code/C28_atomics_asm.c -o -                    (기본: M1/M2 = ARMv8.5, LSE 원자 명령)
//   cc -O2 -S -mcpu=apple-a7 code/C28_atomics_asm.c -o -     (LSE 없는 ARMv8.0 → LL/SC 루프)
#include <stdatomic.h>

// test-and-set (atomic exchange)
int tas(atomic_int *p) {
    return atomic_exchange_explicit(p, 1, memory_order_acquire);
}

// compare-and-swap: *p == expected 이면 new 를 쓰고 1, 아니면 0
int cas(atomic_int *p, int expected, int new_value) {
    return atomic_compare_exchange_strong_explicit(p, &expected, new_value,
                                                   memory_order_acquire, memory_order_relaxed);
}

// fetch-and-add (ticket lock 의 핵심)
int faa(atomic_int *p) {
    return atomic_fetch_add_explicit(p, 1, memory_order_relaxed);
}

// unlock = release store
void release(atomic_int *p) {
    atomic_store_explicit(p, 0, memory_order_release);
}
```

읽는 법:

- 기본(M2): 책의 네 가지 하드웨어 프리미티브가 **명령 하나씩**으로 존재한다. `swpa`(TestAndSet), `casa`(CompareAndSwap), `ldadd`(FetchAndAdd). 접미사 `a` = acquire 순서.
- `-mcpu=apple-a7`(2013년 A7, ARMv8.0, LSE 없음): 전부 **LL/SC 루프**로 바뀐다. CAS 실패 경로의 `clrex` 는 monitor를 정리하는 것. `faa` 는 순서가 relaxed라 `ldxr`(acquire 없음)를 쓴다.
- unlock(release store)은 둘 다 `stlr` — 일반 store에 release 순서만 붙인 것. 락 해제에 원자적 RMW는 필요 없다(주인만 쓰므로).

### 17.2 락 10종 벤치마크 — C28_locks_bench.c (핵심 실험)

TAS, TTAS, CAS, LL/SC(인라인 어셈블리), 티켓, TAS+yield, futex, 2단계, pthread_mutex, os_unfair_lock을 같은 인터페이스로 만들고, 

- **실험 1(처리량)**: T개 스레드가 각자 100,000번 `lock → counter++ → unlock`. counter가 총 획득 수와 같은지 검증(상호 배제 확인)하고 ns/op 측정. 3초 넘으면 중단.
- **실험 2(공정성)**: 4 스레드가 300 ms 동안 경쟁. 스레드별 획득 수 min/max와 **handoff 비율**(연속 두 획득의 주인이 달랐던 비율).

```c
// C28_locks_bench.c — OSTEP Ch.28 의 락들을 C11 atomics 로 직접 만들고
// macOS(Apple M2) 의 pthread_mutex / os_unfair_lock 과 비교한다.
//
//  tas       : test-and-set 스핀락        (Fig 28.3, atomic_exchange → swpa)
//  ttas      : test-and-test-and-set      (먼저 읽기만 하며 기다림)
//  cas       : compare-and-swap 스핀락     (Fig 28.4, → casa)
//  llsc      : LL/SC 스핀락, arm64 인라인 어셈블리 ldaxr/stxr (Fig 28.6)
//  ticket    : fetch-and-add 티켓락        (Fig 28.7, → ldadd)
//  tas_yield : TAS + sched_yield()         (Fig 28.8)
//  futex     : 3-상태 futex 뮤텍스 (Drepper) — macOS 의 os_sync_wait_on_address 사용
//  twophase  : 잠깐 스핀 후 futex 로 잠드는 2단계 락 (28.16)
//  pthread   : pthread_mutex_t
//  unfair    : os_unfair_lock (macOS 의 저수준 락)
//
// 실험 1 (처리량): T 개 스레드가 각자 ITERS 번 lock → counter++ → unlock. 결과값 검증 + 시간.
// 실험 2 (공정성): 4 스레드가 300ms 동안 경쟁. 스레드별 획득 횟수의 min/max.
//
// build: cc -Wall -Wextra -O2 -pthread code/C28_locks_bench.c -o .work/bin/C28_locks_bench
#include <os/lock.h>
#include <os/os_sync_wait_on_address.h>
#include <pthread.h>
#include <sched.h>
#include <stdatomic.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>

// ------------------------------------------------------------ 락 구현들
typedef struct {
    _Alignas(128) atomic_int flag;     // tas/ttas/cas/llsc/yield/futex 공용 (M2 캐시라인 128B)
    _Alignas(128) atomic_int ticket;   // ticket lock
    _Alignas(128) atomic_int turn;
    pthread_mutex_t mutex;
    os_unfair_lock unfair;
} lock_t;

static atomic_long futex_waits;        // futex 계열이 실제로 커널에서 잠든 횟수

// ---- test-and-set
static void tas_lock(lock_t *l) {
    while (atomic_exchange_explicit(&l->flag, 1, memory_order_acquire) == 1)
        ;                                                     // spin
}
static void spin_unlock(lock_t *l) { atomic_store_explicit(&l->flag, 0, memory_order_release); }

// ---- test-and-test-and-set: 풀린 것처럼 "보일" 때만 원자 교환 시도
static void ttas_lock(lock_t *l) {
    for (;;) {
        while (atomic_load_explicit(&l->flag, memory_order_relaxed) == 1)
            ;                                                 // 캐시에서 읽기만 하며 대기
        if (atomic_exchange_explicit(&l->flag, 1, memory_order_acquire) == 0)
            return;
    }
}

// ---- compare-and-swap
static void cas_lock(lock_t *l) {
    int expected = 0;
    while (!atomic_compare_exchange_weak_explicit(&l->flag, &expected, 1,
                                                  memory_order_acquire, memory_order_relaxed))
        expected = 0;                                         // 실패하면 expected 가 덮어써지므로 리셋
}

// ---- load-linked / store-conditional (arm64 전용 인라인 어셈블리)
static void llsc_lock(lock_t *l) {
#if defined(__aarch64__)
    int tmp, fail;
    __asm__ volatile(
        "1: ldaxr  %w0, [%2]      \n"   // LoadLinked (acquire) : 값 읽고 '감시' 시작
        "   cbnz   %w0, 1b        \n"   // 1 이면 잡혀 있음 → 다시
        "   mov    %w0, #1        \n"
        "   stxr   %w1, %w0, [%2] \n"   // StoreConditional : 그 사이 누가 썼으면 실패(fail=1)
        "   cbnz   %w1, 1b        \n"   // 실패하면 처음부터
        : "=&r"(tmp), "=&r"(fail)
        : "r"(&l->flag)
        : "memory");
#else
    cas_lock(l);
#endif
}

// ---- ticket lock (fetch-and-add)
static void ticket_lock(lock_t *l) {
    int myturn = atomic_fetch_add_explicit(&l->ticket, 1, memory_order_relaxed);
    while (atomic_load_explicit(&l->turn, memory_order_acquire) != myturn)
        ;                                                     // 내 차례까지 spin
}
static void ticket_unlock(lock_t *l) {
    atomic_fetch_add_explicit(&l->turn, 1, memory_order_release);
}

// ---- TAS + yield
static void yield_lock(lock_t *l) {
    while (atomic_exchange_explicit(&l->flag, 1, memory_order_acquire) == 1)
        sched_yield();                                        // CPU 를 양보
}

// ---- futex mutex: 0 = free, 1 = locked(대기자 없음), 2 = locked(대기자 있을 수 있음)
static void fwait(atomic_int *addr, int val) {
    atomic_fetch_add_explicit(&futex_waits, 1, memory_order_relaxed);
    os_sync_wait_on_address((void *)addr, (uint64_t)val, sizeof(int), OS_SYNC_WAIT_ON_ADDRESS_NONE);
}
static void futex_slow(lock_t *l, int c) {
    if (c != 2) c = atomic_exchange_explicit(&l->flag, 2, memory_order_acquire);
    while (c != 0) {
        fwait(&l->flag, 2);                                   // *flag == 2 일 때만 잠든다
        c = atomic_exchange_explicit(&l->flag, 2, memory_order_acquire);
    }
}
static void futex_lock(lock_t *l) {
    int c = 0;
    if (atomic_compare_exchange_strong_explicit(&l->flag, &c, 1,
                                                memory_order_acquire, memory_order_relaxed))
        return;                                               // fast path: 경쟁 없음 → 시스템콜 0
    futex_slow(l, c);
}
static void futex_unlock(lock_t *l) {
    if (atomic_fetch_sub_explicit(&l->flag, 1, memory_order_release) != 1) {
        atomic_store_explicit(&l->flag, 0, memory_order_release);
        os_sync_wake_by_address_any((void *)&l->flag, sizeof(int), OS_SYNC_WAKE_BY_ADDRESS_NONE);
    }
}

// ---- two-phase: 1단계 스핀(최대 SPIN 번) → 2단계 futex 수면
#define SPIN 200
static void twophase_lock(lock_t *l) {
    for (int i = 0; i < SPIN; i++) {
        int c = 0;
        if (atomic_load_explicit(&l->flag, memory_order_relaxed) == 0 &&
            atomic_compare_exchange_weak_explicit(&l->flag, &c, 1,
                                                  memory_order_acquire, memory_order_relaxed))
            return;
    }
    int c = 0;
    if (atomic_compare_exchange_strong_explicit(&l->flag, &c, 1,
                                                memory_order_acquire, memory_order_relaxed))
        return;
    futex_slow(l, c);
}

// ---- 라이브러리 락
static void pth_lock(lock_t *l)      { pthread_mutex_lock(&l->mutex); }
static void pth_unlock(lock_t *l)    { pthread_mutex_unlock(&l->mutex); }
static void unfair_lock(lock_t *l)   { os_unfair_lock_lock(&l->unfair); }
static void unfair_unlock(lock_t *l) { os_unfair_lock_unlock(&l->unfair); }

typedef struct {
    const char *name;
    void (*lock)(lock_t *);
    void (*unlock)(lock_t *);
} lockops_t;

static const lockops_t LOCKS[] = {
    {"tas", tas_lock, spin_unlock},       {"ttas", ttas_lock, spin_unlock},
    {"cas", cas_lock, spin_unlock},       {"llsc", llsc_lock, spin_unlock},
    {"ticket", ticket_lock, ticket_unlock}, {"tas_yield", yield_lock, spin_unlock},
    {"futex", futex_lock, futex_unlock},  {"twophase", twophase_lock, futex_unlock},
    {"pthread", pth_lock, pth_unlock},    {"unfair", unfair_lock, unfair_unlock},
};
#define NLOCKS (int)(sizeof(LOCKS) / sizeof(LOCKS[0]))

// ------------------------------------------------------------ 벤치마크
static lock_t L;
static const lockops_t *ops;
static long counter;                   // 락으로 보호되는 공유 변수 (일부러 atomic 아님)
static long iters;
static atomic_int stop;
static atomic_int go;

typedef struct { _Alignas(128) long acquired; double end; } perthread_t;
static double now(void);
static long last_owner = -1, handoffs;  // 락 안에서만 갱신: 소유자가 바뀐 횟수
static perthread_t stats[64];

static void reset_lock(void) {
    memset(&L, 0, sizeof(L));
    pthread_mutex_init(&L.mutex, NULL);
    L.unfair = OS_UNFAIR_LOCK_INIT;
    counter = 0;
    last_owner = -1;
    handoffs = 0;
    atomic_store(&futex_waits, 0);
}

static void *throughput_worker(void *arg) {
    perthread_t *me = arg;
    while (!atomic_load(&go)) ;
    for (long i = 0; i < iters; i++) {
        if (atomic_load_explicit(&stop, memory_order_relaxed)) break;   // 시간 초과 시 중단
        ops->lock(&L);
        counter++;
        ops->unlock(&L);
        __atomic_store_n(&me->acquired, me->acquired + 1, __ATOMIC_RELAXED);  // main 이 읽어 감
    }
    me->end = now();                    // 각자 끝난 시각 → 전체 시간 = max(end) - 시작
    return NULL;
}

static void *fairness_worker(void *arg) {
    perthread_t *me = arg;
    while (!atomic_load(&go)) ;
    while (!atomic_load_explicit(&stop, memory_order_relaxed)) {
        ops->lock(&L);
        counter++;
        if (last_owner != (long)(me - stats)) { handoffs++; last_owner = (long)(me - stats); }
        me->acquired++;
        ops->unlock(&L);
    }
    return NULL;
}

static double now(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

// 실험 1 한 칸: ns/op 를 돌려준다. DEADLINE 초를 넘기면 중단하고 *timedout = 1.
#define DEADLINE 3.0
static double run_throughput(int nthreads, int *timedout) {
    pthread_t t[64];
    reset_lock();
    memset(stats, 0, sizeof(stats));
    atomic_store(&go, 0);
    atomic_store(&stop, 0);
    for (int i = 0; i < nthreads; i++) pthread_create(&t[i], NULL, throughput_worker, &stats[i]);
    double t0 = now();
    atomic_store(&go, 1);
    *timedout = 0;
    for (;;) {                                  // main 은 감시자: 다 끝났나? 시간 초과인가?
        long done = 0;
        for (int i = 0; i < nthreads; i++) done += __atomic_load_n(&stats[i].acquired, __ATOMIC_RELAXED);
        if (done == iters * nthreads) break;
        if (now() - t0 > DEADLINE) { atomic_store(&stop, 1); *timedout = 1; break; }
        struct timespec ts = {0, 1000 * 1000};
        nanosleep(&ts, NULL);
    }
    for (int i = 0; i < nthreads; i++) pthread_join(t[i], NULL);
    double dt = 0;
    for (int i = 0; i < nthreads; i++) if (stats[i].end - t0 > dt) dt = stats[i].end - t0;
    long done = 0;
    for (int i = 0; i < nthreads; i++) done += stats[i].acquired;
    if (counter != done) {                      // 상호 배제 검증: 잃어버린 ++ 가 없어야 한다
        printf("\n!! %s: counter=%ld expected=%ld\n", ops->name, counter, done);
        exit(1);
    }
    return dt * 1e9 / (double)done;
}

int main(int argc, char *argv[]) {
    iters = (argc > 1) ? atol(argv[1]) : 200000;
    const int TH[] = {1, 2, 4, 8, 16};
    const int NTH = (int)(sizeof(TH) / sizeof(TH[0]));

    printf("== 실험 1: 처리량 (각 스레드 %ld 회 lock/++/unlock, ns/op = 총시간/총획득수)\n", iters);
    printf("%-10s", "lock");
    for (int j = 0; j < NTH; j++) printf("   T=%-2d ns/op", TH[j]);
    printf("   futex sleeps@T=8\n");
    printf("(* = %.0f s 안에 못 끝나서 중단, 그때까지 처리한 것으로 계산)\n", DEADLINE);
    ops = &LOCKS[0];
    { int to; run_throughput(1, &to); }          // 워밍업 (페이지 폴트·주파수 상승)
    for (int k = 0; k < NLOCKS; k++) {
        ops = &LOCKS[k];
        printf("%-10s", ops->name);
        long sleeps8 = -1;
        for (int j = 0; j < NTH; j++) {
            int to;
            double nsop = run_throughput(TH[j], &to);
            printf("   %11.1f%s", nsop, to ? "*" : " ");
            if (TH[j] == 8) sleeps8 = atomic_load(&futex_waits);
            fflush(stdout);
        }
        if (k == 6 || k == 7) printf("   %ld", sleeps8);
        printf("\n");
    }

    const int FT = 4;
    printf("\n== 실험 2: 공정성 (%d 스레드, 300 ms 경쟁, 스레드별 획득 횟수)\n", FT);
    printf("   handoff = 연속 두 획득의 소유 스레드가 달랐던 비율 (100%%면 매번 다른 스레드에게 넘어감)\n");
    for (int k = 0; k < NLOCKS; k++) {
        ops = &LOCKS[k];
        pthread_t t[8];
        reset_lock();
        memset(stats, 0, sizeof(stats));
        atomic_store(&go, 0);
        atomic_store(&stop, 0);
        for (int i = 0; i < FT; i++) pthread_create(&t[i], NULL, fairness_worker, &stats[i]);
        atomic_store(&go, 1);
        struct timespec ts = {0, 300 * 1000 * 1000};
        nanosleep(&ts, NULL);
        atomic_store(&stop, 1);
        for (int i = 0; i < FT; i++) pthread_join(t[i], NULL);
        long mn = stats[0].acquired, mx = stats[0].acquired, sum = 0;
        for (int i = 0; i < FT; i++) {
            long a = stats[i].acquired;
            if (a < mn) mn = a;
            if (a > mx) mx = a;
            sum += a;
        }
        printf("%-10s total=%9ld  min=%9ld  max=%9ld  max/min=%5.2f  handoff=%5.1f%%  [",
               ops->name, sum, mn, mx, mn ? (double)mx / (double)mn : 0.0,
               100.0 * (double)handoffs / (double)sum);
        for (int i = 0; i < FT; i++) printf("%s%ld", i ? " " : "", stats[i].acquired);
        printf("]\n");
    }
    return 0;
}
```

해석:

- **무경쟁(T=1)은 전부 약 5 ns.** 원자 명령 하나 + 함수 포인터 호출. futex/pthread도 fast path라 시스템콜이 없다 (책의 "흔한 경우를 빠르게").
- **순수 스핀락(tas/ttas/cas/llsc)은 스레드가 늘수록 나빠진다.** T=8에서 100–215 ns, T=16에서 135–308 ns. 락 변수가 든 캐시라인의 독점 소유권이 코어 사이를 계속 오가는 비용(캐시라인 핑퐁)이다. 이번 실행에선 llsc가 스핀락 중 가장 나았는데, 기다리는 동안 `ldaxr`(읽기)만 반복하다 0일 때만 쓰기를 시도해 TTAS처럼 동작하기 때문으로 보인다. (C로 짠 ttas는 이 짧은 임계 구역에선 이득이 없었다 — 측정해 보기 전엔 모른다.)
- **티켓락: T=8에서 2.7 µs, T=16에서 361 µs (3초 타임아웃)**. 코어(8)보다 스레드(16)가 많으면 **다음 번호표의 주인이 CPU에서 쫓겨나 있는** 일이 잦고, 그동안 나머지 15개는 모두 헛돈다. 공정성의 대가가 극적으로 드러난다.
- **잠드는 락(futex/twophase/pthread/unfair)은 16 스레드에서도 24–41 ns로 평탄.** 지는 쪽이 잠들어서 캐시라인을 두드리지 않는다. futex는 T=8에서 80만 번 획득 중 약 2만 번(2.6%)만 커널에서 잠들었다.
- **tas_yield가 의외로 가장 빨랐다(T=16에서 12 ns).** 지는 스레드가 즉시 양보하므로 이긴 스레드가 따뜻한 캐시라인으로 연속해서 다시 잡는다(실험 2의 handoff 11%). 처리량은 "불공정하게 몰아주기"에서 나온다. 책의 경고(100 스레드 라운드로빈에서 문맥 교환 99번)는 스레드가 코어 수보다 훨씬 많을 때의 이야기이고, 16 스레드/8 코어에선 그 비용이 아직 작다.
- **공정성(실험 2)**: 티켓락만 **max/min = 1.00, handoff 100%** — 완벽한 FIFO. 대신 매 획득마다 캐시라인이 다른 코어로 넘어가 총 처리량은 4.1M으로 tas(5.2M)보다 낮다. ttas/cas/llsc는 max/min 2.0–2.5배, handoff 0.1–2.3% — 푼 스레드가 곧바로 다시 잡는(자기 캐시에 라인이 있으니 유리) **굶주림 경향**이 보인다. pthread는 handoff 1.1%로 FIRSTFIT 정책다운 "몰아주기"지만 300 ms 동안의 총량은 고르게(1.02) 나눴고 처리량은 최고(16.2M)였다.

```c
// C28_peterson.c — 책 ASIDE 의 Peterson 알고리즘이 "현대 하드웨어에선 안 된다"는 말을
// Apple M2 (ARM, 약한 메모리 모델)에서 직접 확인한다.
//   plain  : volatile int 로만 구현 (컴파일러 재배치는 막지만 CPU 재배치는 못 막음)
//   seqcst : 같은 코드를 C11 atomic (memory_order_seq_cst) 로 구현 → arm64 에서 stlr/ldar 로 컴파일되어 store→load 재배치 금지
// build: cc -Wall -Wextra -O0 -pthread code/C28_peterson.c -o .work/bin/C28_peterson
#include <pthread.h>
#include <stdatomic.h>
#include <stdio.h>

#ifndef LOOPS
#define LOOPS 2000000
#endif

// ---- plain 버전
static volatile int flag_v[2];
static volatile int turn_v;
// ---- seq_cst 버전
static volatile atomic_int flag_a[2];   // volatile: -O2 에서 clang 이 turn_a 접근을 통째로 지워 무한 대기한 것을 관찰해서 붙임
static volatile atomic_int turn_a;

static long counter;                    // 보호 대상 (일부러 평범한 변수)
static int use_atomic;

static void lock(int self) {
    int other = 1 - self;
    if (use_atomic) {
        atomic_store(&flag_a[self], 1);
        atomic_store(&turn_a, other);
        while (atomic_load(&flag_a[other]) == 1 && atomic_load(&turn_a) == other)
            ;
    } else {
        flag_v[self] = 1;               // (1) store
        turn_v = other;                 // (2) store
        while (flag_v[other] == 1 && turn_v == other)   // (3) load — (1)보다 먼저 보일 수 있다!
            ;
    }
}

static void unlock(int self) {
    if (use_atomic) atomic_store(&flag_a[self], 0);
    else flag_v[self] = 0;
}

static void *worker(void *arg) {
    int self = (int)(long)arg;
    for (int i = 0; i < LOOPS; i++) {
        lock(self);
        counter = counter + 1;
        unlock(self);
    }
    return NULL;
}

static void run(int atomic_mode) {
    pthread_t a, b;
    use_atomic = atomic_mode;
    counter = 0;
    pthread_create(&a, NULL, worker, (void *)0L);
    pthread_create(&b, NULL, worker, (void *)1L);
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    printf("%-7s counter = %ld (expected %d, lost %ld)\n",
           atomic_mode ? "seqcst" : "plain", counter, 2 * LOOPS, 2L * LOOPS - counter);
}

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);
    for (int r = 0; r < 3; r++) run(0);
    for (int r = 0; r < 3; r++) run(1);
    return 0;
}
```

- **plain**: 400만 번 중 1–6번 상호 배제 실패. 드물지만 0이 아니다 — 펌웨어에서 "몇 주에 한 번 깨지는" 종류의 버그. 앞선 실행에서는 손실 0인 회차도 있었다.

- 덤으로 겪은 함정: 처음엔 atomic 변수를 그냥 `atomic_int` 로 두고 `-O2` 로 빌드했더니 seqcst 버전이 **영원히 멈췄다.** 디스어셈블해 보니 clang이 `turn_a` 에 대한 load/store를 통째로 없애 버렸다(같은 스레드가 방금 쓴 값을 읽는다고 보고 전달한 뒤, 읽히지 않는 store를 제거한 것으로 보인다). `volatile atomic_int` 로 바꾸니 해결. 손으로 만든 동기화 알고리즘은 **하드웨어와 컴파일러 둘 다** 상대해야 한다는 교훈 — "검증된 프리미티브를 써라"의 이유.

## 18. 펌웨어 엔지니어의 눈으로

- **인터럽트 끄기는 펌웨어의 일상**: Cortex-R/M 단일 코어 FW에서 `cpsid i`/`cpsie i`, BASEPRI 마스킹은 정당한 락이다(신뢰 문제 없음 — 모든 코드가 FW). 단, 책의 단점 3번(인터럽트 유실/지연)이 그대로 사양 문제로 나타난다: NVMe 커맨드 도착 인터럽트 지연이 길어지면 QoS 테일 레이턴시가 나빠진다. 그래서 "인터럽트 끄는 구간 최대 N µs" 같은 규칙을 둔다.
- **멀티코어 SSD 컨트롤러의 코어 간 락**: Cortex-R은 `ldrex/strex`(= 이 장의 LL/SC)로 스핀락을 만들고, 대기 중엔 `wfe`(이벤트 대기, 저전력)로 잠들었다가 해제 쪽의 `sev` 로 깨운다. 이게 펌웨어판 "2단계 락"이다. 일부 SoC는 하드웨어 세마포어 레지스터(읽으면 test-and-set)가 있는데, 이게 바로 Burroughs RDLK의 후손이다.
- **exclusive monitor의 함정**: `ldrex/strex` 는 **캐시 가능한(cacheable) 일반 메모리**에서만 제대로 동작하도록 보장된다. Device/Strongly-ordered 메모리나 캐시를 끈 SRAM에 락 변수를 두면 SC가 항상 실패하거나 원자성이 깨질 수 있다 — FW에서 "락 변수를 TCM/비캐시 영역에 뒀더니 이상하다"는 버그의 원인. 또한 예외 진입/복귀 시 `clrex` 가 필요하다(문맥 교환 중 남은 monitor가 다른 문맥의 SC를 성공시키지 않도록).
- **티켓락의 붕괴 = 우선순위/선점과 FIFO의 충돌**: RTOS에서 FIFO 대기 큐의 뮤텍스를 쓰면, 큐의 다음 태스크가 낮은 우선순위라 늦게 스케줄되는 동안 높은 우선순위 태스크가 기다리는 **우선순위 역전**이 생긴다. 그래서 RTOS 뮤텍스는 FIFO가 아니라 **우선순위 순 대기 + 우선순위 상속**을 쓰고, macOS `os_unfair_lock` 이 락 값에 owner를 담는 이유도 같다.
- **Apple SoC 코프로세서 ↔ AP 공유 메모리**: AP와 코프로세서가 하드웨어 일관성 도메인 밖이면 LL/SC나 LSE 원자 명령이 서로에게 원자적이지 않다. 이 경우 메일박스 하드웨어(doorbell 레지스터)나 단일 쓰기자 링 버퍼 + 명시적 캐시 유지 관리로 동기화한다 — "원자 명령은 같은 일관성 도메인 안에서만 원자적"이라는 점이 핵심.
- **AI 가속기 호스트 드라이버**: 커맨드 큐 submit 경로는 보통 짧은 스핀락(또는 per-CPU 큐로 락 제거), 완료 대기는 futex 류의 수면(또는 폴링 + 일정 시간 뒤 인터럽트 모드 전환 = 2단계). NVMe 리눅스 드라이버의 하이브리드 폴링(`io_poll_delay`)도 같은 철학이다.

### Q1. test-and-set 스핀락을 구현하고, 그 정확성·공정성·성능을 평가하라.
<details>
<summary>답 보기</summary>

```c
void lock(atomic_int *f)   { while (atomic_exchange_explicit(f, 1, memory_order_acquire)) ; }
void unlock(atomic_int *f) { atomic_store_explicit(f, 0, memory_order_release); }
```

- **정확성**: 교환이 원자적이라 0을 받는 스레드는 하나뿐 → 상호 배제. **acquire/release** 가 임계 구역 안의 메모리 접근이 락 밖으로 새지 않게 한다 (ARM 같은 약한 메모리 모델에서 필수).
- **공정성**: 없음. 해제 직후 누가 잡을지는 하드웨어 경쟁 → **굶주림 가능** (M2 실측: TTAS/CAS 계열 max/min 2–2.5배).
- **성능**: 무경쟁 수 ns. 멀티코어 경쟁 시 캐시라인 핑퐁(M2 T=16에서 약 300 ns/op). 단일 CPU에서 주인이 선점되면 대기자가 **타임슬라이스 전체를 낭비**.
- 개선: TTAS(읽기로 대기), 지수 백오프, `wfe`/`pause` 힌트, 티켓/MCS(공정성), 수면 락(futex).

</details>

### Q2. LL/SC 와 CAS 의 차이는? ABA 문제와 어떤 관계가 있나?
<details>
<summary>답 보기</summary>

- **CAS**는 "값이 expected와 **같으면**" 쓴다. 그 사이 값이 A→B→A로 바뀌었어도 성공한다 → **ABA 문제** (락-프리 스택에서 pop한 노드가 재사용되어 같은 주소로 돌아오는 경우 치명적). 해결: 태그/버전 카운터를 붙인 double-width CAS, hazard pointer, epoch 기반 회수.
- **LL/SC**는 "그 사이 **누가 썼으면**" 실패한다 → 값이 같아도 실패하므로 원리적으로 ABA에 강하다. 대신 **spurious failure**(문맥 교환, 캐시라인 축출, 같은 라인의 다른 변수 쓰기 등으로 실패)가 있어 항상 루프로 감싸야 하고, LL과 SC 사이에 다른 메모리 접근을 많이 넣으면 안 된다.
- ARM: v8.0은 `ldxr/stxr` 만, v8.1 LSE부터 `cas`/`swp`/`ldadd` 추가. 코어가 많을 때 LL/SC 재시도 폭주를 피하려는 목적.

</details>

### Q3. 티켓락이 TAS 락보다 공정한데, 왜 리눅스는 티켓 스핀락을 버렸나? 그리고 사용자 공간에서 티켓락을 쓰면 무슨 일이 생기나?
<details>
<summary>답 보기</summary>

- **확장성**: 모든 대기자가 **같은 캐시라인(turn)** 을 spin한다. unlock 한 번에 그 라인이 무효화되고 N개 코어가 다시 읽어 간다 → O(N) 트래픽. 코어가 많으면 붕괴. 그래서 각자 **자기 노드를 spin하는 MCS 락** 기반 qspinlock으로 교체(4.2 커널 무렵).
- **선점 문제**: 커널 스핀락은 잡는 동안 선점을 끄니 괜찮지만, **사용자 공간에선 다음 차례 스레드가 선점될 수 있다.** 그러면 FIFO 때문에 모두가 그 한 스레드를 기다린다. M2 실측: 16 스레드/8 코어에서 361 µs/op (pthread의 약 15,000배).
- 교훈: 공정성은 공짜가 아니다. 사용자 공간에선 **잠드는 락**을 쓰고, 공정성이 필요하면 커널 큐(FIFO handoff)로 구현된 락을 쓴다.

</details>

### Q4. futex 기반 mutex의 fast path/slow path를 설명하고, wakeup을 놓치지 않는 이유를 말하라.
<details>
<summary>답 보기</summary>

- 상태: 0=풀림, 1=잡힘(대기자 없음), 2=잡힘(대기자 있을 수 있음).
- **lock fast path**: `CAS(0→1)` 성공 → 끝. 시스템콜 없음.
- **lock slow path**: 값을 2로 바꾸고(`xchg`) 옛 값이 0이 아니면 `futex_wait(addr, 2)` — 커널이 **"값이 아직 2인지"를 검사하고 잠드는 것을 원자적으로** 한다. 그 사이 unlock으로 값이 바뀌었으면 즉시 리턴 → 다시 시도. 그래서 "검사 후 잠들기 사이의 깨우기 유실"이 없다.
- **unlock**: `fetch_sub` 로 1→0이면 대기자 없음 → 끝(시스템콜 없음). 2였으면 0으로 내리고 `futex_wake(addr, 1)`.
- 핵심: **흔한 경우(무경쟁)는 사용자 공간 원자 명령 하나**, 경쟁 시에만 커널. macOS 대응: `os_sync_wait_on_address` / `os_sync_wake_by_address_any`.

</details>

### Q5. 스핀할지 잠들지는 어떻게 결정하나? 커널 안에서 잠드는 락을 쓸 수 없는 곳은?
<details>
<summary>답 보기</summary>

- **락 보유 시간 H vs 문맥 교환 왕복 비용 C**: H < C면 스핀, H > C면 수면. 모르면 **2단계 락**(C만큼 스핀 후 수면, 최악에도 최적의 2배 이내).
- 스핀이 유리한 조건: 멀티코어, 짧은 임계 구역, 스레드 수 ≤ 코어 수, 주인이 선점되지 않음(커널은 스핀락 보유 중 선점 금지).
- **잠들 수 없는 곳**: 인터럽트 핸들러(하드 IRQ, softirq), 선점·인터럽트가 꺼진 구간, 스핀락을 이미 잡은 상태 → 여기선 스핀락만. 리눅스에선 `spin_lock_irqsave` (인터럽트 핸들러와 공유하는 데이터).
- 펌웨어 대응: ISR에선 뮤텍스 금지, 인터럽트 마스킹/스핀/락-프리 링.

</details>

### Q6. Peterson 알고리즘은 이론적으로 맞는데 왜 현대 CPU에서 깨지나? 어떻게 고치나?
<details>
<summary>답 보기</summary>

- Peterson은 **순차 일관성(sequential consistency)** 을 가정한다: 내 `flag[self]=1` store가 그 뒤의 `flag[other]` load보다 먼저 다른 코어에 보인다는 것.
- x86(TSO)조차 **store→load 재배치**를 허용한다(스토어 버퍼). ARM/POWER는 더 약하다. 그러면 두 스레드가 상대 flag를 0으로 읽고 둘 다 진입한다. M2 실측: 400만 번 중 1–6번 실패.
- 수정: store와 load 사이에 **full fence**(x86 `mfence`, ARM `dmb ish`) 또는 C11 `seq_cst` 원자 변수(arm64에선 `stlr`+`ldar` 로 충분). 그리고 컴파일러 재배치도 막아야 한다 — 실제로 `-O2` 에서 clang이 atomic 접근을 지워 무한 대기한 사례를 겪었다.
- 실무 교훈: 직접 만든 동기화 대신 **검증된 프리미티브**(mutex, atomic RMW)를 쓴다.

</details>

## 20. 자가 점검 & 숙제

### 퀴즈

Q1. Figure 28.9 (큐 락)에서 unlock이 대기자를 깨울 때 `flag` 를 0으로 내리지 않는 이유는?

<details>
<summary>정답</summary>

깨어난 스레드는 park()에서 리턴할 뿐 **guard를 갖고 있지 않아서** flag를 1로 다시 설정할 수 없다. 그래서 락을 "풀었다가 다시 잡게" 하지 않고 **잡힌 상태 그대로 직접 넘겨준다(handoff)**. 덤으로 그 사이 다른 스레드가 끼어들어 락을 가로채는 것도 막아 FIFO 공정성이 유지된다.

</details>

Q2. 단일 CPU, 스레드 5개, 타임슬라이스 20 ms. TAS 스핀락의 주인이 임계 구역 중에 선점됐다. 주인이 다시 돌기까지 낭비되는 CPU 시간의 최대값은? yield 락이면?

<details>
<summary>정답</summary>

스핀: 나머지 4개가 각자 슬라이스 전체를 헛돌 수 있으므로 4 × 20 = **80 ms**. yield: 4개가 각각 "TAS 한 번 실패 → yield" 하므로 문맥 교환 4번 + 몇 명령 ≈ 4 × (수 µs) = **수십 µs**. (단, 굶주림은 둘 다 해결 안 됨.)

</details>

Q3. glibc futex 락(Figure 28.10)에서 락 값이 `0x80000003` 이면 무슨 상태인가? 이 상태에서 주인이 unlock하면 값은?

<details>
<summary>정답</summary>

bit 31이 켜져 있으니 **잡힘**, 하위 비트 3 = **대기자(관심 있는 스레드) 3개**. unlock은 `+0x80000000` → `0x00000003`(0이 아님) → `futex_wake` 로 하나를 깨운다. 깨어난 스레드가 bit 31을 set하고 성공하면 decrement해서 `0x80000002` 가 된다.

</details>

Q4. M2 벤치에서 티켓락은 T=4까지는 다른 스핀락과 비슷했는데 T=16에서 수천 배 느려졌다. TAS는 왜 같은 붕괴를 겪지 않았나?

<details>
<summary>정답</summary>

TAS는 **누구든 지금 CPU에 있는 스레드**가 락을 잡을 수 있다. 티켓락은 **번호표 순서의 바로 그 스레드**만 다음에 들어갈 수 있으므로, 그 스레드가 선점되어 있으면(16 스레드 > 8 코어라 흔함) 모든 스레드가 그 스레드의 다음 타임슬라이스까지 기다린다. 공정성(FIFO)이 선점과 만나면 처리량이 붕괴한다.

</details>

Q5. arm64에서 락 해제(`unlock`)를 `swp` 같은 원자 RMW가 아니라 `stlr`(store-release) 하나로 해도 되는 이유는?

<details>
<summary>정답</summary>

해제 시점엔 **주인만** 그 변수에 쓰므로 경쟁하는 쓰기가 없다 → 원자적 RMW가 필요 없다. 필요한 건 순서뿐: 임계 구역 안의 모든 메모리 접근이 "락 풀림(0)"보다 **먼저** 다른 코어에 보여야 한다. 이게 release 의미이고 `stlr` 이 정확히 그것을 보장한다. (티켓락의 `turn++` 도 주인만 쓰므로 원리적으로는 load + store-release로 충분하다.)

</details>
