# Ch.14 메모리 API — malloc/free 와 흔한 버그, 그리고 도구로 잡기

> 📖 원문: [14. Interlude: Memory API](../book-md/C14_interlude_memory_api.md) · [PDF p.141](../Operating%20Systems%20-%20Three%20Easy%20Pieces.pdf#page=141) · ⏱️ 읽기 약 35분 · 🔗 선행: [Ch.13](2026-09-30_C13_address_spaces.md)

## 0. 한눈에 보기

- C 프로그램의 메모리는 두 종류: 컴파일러가 알아서 관리하는 **스택(자동, automatic)** 과 프로그래머가 직접 관리하는 **힙(heap)**.
- 힙 API 는 `malloc(size)` / `free(ptr)` 두 개뿐이지만, 버그의 대부분이 여기서 나온다: 할당 깜빡, 크기 부족(오버플로), 초기화 안 함, 해제 깜빡(leak), 너무 일찍 해제(dangling), 두 번 해제, 엉뚱한 포인터 해제.
- "컴파일됐다 / 한 번 돌았다" 는 "맞다" 가 아니다. 이 장의 핵심 실습은 **macOS 에서 `-fsanitize=address` (ASan) 와 `leaks` 로 실제 버그를 잡아 보는 것**.
- `malloc` 은 시스템 콜이 아니라 **라이브러리** 다. 그 밑에서 `brk/sbrk`, `mmap` 같은 시스템 콜로 OS 에서 메모리를 받아 온다.

## 1. 5분 복습표

| 용어 | 한 줄 뜻 | 예시 / 비유 |
|---|---|---|
| 스택 메모리(automatic) | 함수 진입 때 생기고 리턴 때 사라짐. 컴파일러가 관리 | `int x;` |
| 힙 메모리(heap) | 명시적으로 받고 명시적으로 돌려줌 | `malloc(sizeof(int))` |
| `malloc(size)` | size 바이트를 힙에서 받아 포인터 반환, 실패 시 NULL | `double *d = malloc(sizeof(double));` |
| `free(ptr)` | malloc 이 준 포인터를 돌려줌. 크기는 안 넘김 | 라이브러리가 크기를 기억한다 |
| `sizeof` | 컴파일 타임 연산자. 포인터에 쓰면 포인터 크기 | `sizeof(int*)` = 8 |
| `calloc` / `realloc` | 0 으로 채운 할당 / 크기 바꾸며 복사 | 동적 배열 늘리기 |
| 세그멘테이션 폴트(segfault) | 불법 메모리 접근으로 OS 가 프로세스를 죽임 | NULL 역참조 |
| 버퍼 오버플로(buffer overflow) | 할당한 것보다 더 씀 | `malloc(strlen(s))` 후 strcpy |
| 메모리 누수(memory leak) | 해제를 잊음 | 오래 도는 서버가 결국 OOM |
| 댕글링 포인터(dangling pointer) | 해제된 메모리를 가리키는 포인터 | use-after-free |
| 이중 해제(double free) | 같은 포인터를 두 번 free | 할당기 내부 자료구조 손상 |
| 잘못된 해제(invalid free) | malloc 이 안 준 주소를 free | `free(arr + 50)` |
| ASan(AddressSanitizer) | 컴파일러 계측 + 섀도 메모리로 메모리 오류 검출 | `cc -fsanitize=address` |
| `brk` / `sbrk` / `mmap` | 힙 끝(break) 이동 / 익명 메모리 매핑 시스템 콜 | malloc 의 재료 공급원 |

## 2. 메모리의 두 종류 (14.1)

```c
void func() {
    int x;                                   // 스택: 컴파일러가 알아서
    int *p = (int *) malloc(sizeof(int));    // 포인터 p 는 스택, *p 는 힙
    ...
}
```

두 번째 줄에서 **스택 할당과 힙 할당이 동시에** 일어난다. 컴파일러는 포인터 변수 `p`(8바이트)를 스택에 잡고, `malloc` 은 힙에서 4바이트를 받아 그 주소를 `p` 에 넣는다. 함수가 리턴하면 `p` 는 사라지지만 힙의 4바이트는 남는다 — free 를 안 했다면 누수.

함수 호출보다 오래 살아야 하는 데이터 → 힙. 이 "오래 사는 메모리" 가 필요하기 때문에 힙이 존재한다.

## 3. malloc() (14.2)

```c
#include <stdlib.h>
void *malloc(size_t size);
```

- 인자는 **바이트 수** 하나. 숫자를 직접 쓰지 말고 `sizeof` 를 쓴다: `malloc(sizeof(double))`.
- `sizeof` 는 **컴파일 타임 연산자** 다. 함수 호출이 아니다.
- 반환형이 `void *` 라 캐스트는 C 에서는 필요 없다(가독성용 "나 알고 쓰는 거야" 표시일 뿐).

### sizeof 함정

```c
int *x = malloc(10 * sizeof(int));
printf("%zu\n", sizeof(x));      // 8  — 포인터 크기 (64비트)
int y[10];
printf("%zu\n", sizeof(y));      // 40 — 배열은 컴파일러가 크기를 안다
```

(아래 "직접 해보기" 의 `sizeof` 모드 실제 출력: 8 / 40.) 원문은 `%d` 로 찍지만 `sizeof` 는 `size_t` 라 `%zu` 가 맞다 — `-Wall` 이 경고를 낸다.

### 문자열은 strlen + 1

문자열 공간은 `malloc(strlen(s) + 1)` — 끝의 `'\0'` 자리. `sizeof(s)` 는 `s` 가 포인터면 8 이 나와 틀린다. 그냥 `strdup(s)` 를 쓰면 편하다.

> **TIP — 의심되면 돌려 보라(WHEN IN DOUBT, TRY IT OUT)**: man 페이지보다 직접 짠 작은 코드가 진실이다. 저자들도 `sizeof` 설명을 코드로 확인했다.

## 4. free() (14.3)

```c
int *x = malloc(10 * sizeof(int));
...
free(x);
```

`free` 는 **크기를 받지 않는다**. 그러니 malloc 라이브러리가 "이 포인터는 40바이트였다" 를 어딘가 기억해야 한다 — 보통 포인터 바로 앞의 **헤더** 에 적어 둔다(Ch.17 에서 직접 구현).

할당은 쉽다. **언제, 어떻게, 정말 해제해도 되는지** 아는 게 어렵다.

### 5.1 할당을 잊음 (Forgetting To Allocate Memory)

```c
char *src = "hello";
char *dst;            // oops! 할당 안 함
strcpy(dst, src);     // segfault
```

`dst` 는 쓰레기 값(또는 NULL)을 가리킨다. 그 주소가 주소 공간에 매핑되어 있지 않으면 **세그멘테이션 폴트**. 해결: `dst = malloc(strlen(src) + 1)` 또는 `strdup`.

> **TIP — 컴파일됐다/돌았다 ≠ 맞다(IT COMPILED OR IT RAN ≠ IT IS CORRECT)**: "어제는 됐는데요!" 는 변명이 안 된다. 컴파일러, OS, 하드웨어를 탓하기 전에 내 코드를 의심하라.

### 5.2 충분히 할당하지 않음 — 버퍼 오버플로

```c
char *dst = (char *) malloc(strlen(src));   // 1바이트 모자람
strcpy(dst, src);
```

무섭게도 **대개 잘 돈다**. malloc 이 내부적으로 크기를 반올림해서(예: 16바이트 단위) 여유가 있거나, 덮어쓴 바이트가 아무도 안 쓰는 곳이라서. 아래 실습에서 일반 빌드는 `dst=hello` 를 멀쩡히 찍고 끝났다. 하지만 이건 보안 취약점의 단골 원인이다.

### 5.3 초기화를 잊음 — uninitialized read

`malloc` 은 내용을 0 으로 채워 주지 **않는다**. 운 좋으면 0, 운 나쁘면 이전 사용자의 데이터. 0 이 필요하면 `calloc`.

### 5.4 해제를 잊음 — memory leak

오래 도는 프로그램(서버, DB, 그리고 **OS 자체**)에서 치명적. GC 언어도 참조를 계속 들고 있으면 누수는 그대로다.

> **ASIDE — 프로세스가 끝나면 왜 누수가 사라지나**: 메모리 관리는 **두 층** 이다. (1) OS 는 프로세스에게 페이지를 주고, 프로세스가 죽으면 **전부** 회수한다. (2) 프로세스 안에서 malloc/free 가 힙을 쪼개 쓴다. 짧은 프로그램에서 free 를 빼먹어도 (1) 이 다 회수하므로 실제 손실은 없다. 하지만 습관은 나쁘고, 장수 프로그램과 커널에서는 진짜 문제다.

### 5.5 다 쓰기 전에 해제 — dangling pointer

free 한 뒤 그 포인터를 쓰면(use-after-free) 크래시하거나, 더 나쁘게는 그 사이 malloc 이 같은 메모리를 다른 용도로 재활용해서 **남의 데이터를 조용히 덮어쓴다**.

### 5.6 두 번 해제 — double free

결과는 정의되지 않음(undefined). 할당기 내부 자료구조가 꼬여 크래시하거나 이상 동작. 공격자에게는 힙 익스플로잇 재료.

### 5.7 free 를 잘못 호출 — invalid free

free 에는 malloc 이 준 포인터만 넘겨야 한다. 배열 중간 주소를 넘기면 할당기가 그 앞 바이트를 "헤더" 라고 믿고 읽는다.

### 요약 — 도구를 써라

원문은 purify 와 valgrind 를 권한다. **valgrind 는 Apple Silicon macOS 에서 돌지 않으므로**, 이 노트는 macOS 기본 도구로 대체한다: **ASan(`-fsanitize=address`)**, **`leaks`**, **`lldb`**.

## 6. OS 의 지원: brk, sbrk, mmap (14.5)

malloc/free 는 **시스템 콜이 아니다**. 라이브러리가 주소 공간 안의 힙을 관리하고, 모자라면 OS 에 요청한다.

- `brk(addr)`: 프로그램 **break**(힙의 끝) 위치를 addr 로 옮긴다. `sbrk(incr)` 는 증가량을 받는 버전.
- 직접 부르지 말 것 — malloc 과 꼬인다.
- `mmap()`: 파일과 무관한 **익명(anonymous) 메모리 영역** 을 만든다. 스왑 공간과 연결되며(Ch.21), 이것도 힙처럼 관리할 수 있다.

현실 메모: macOS 에서 `sbrk` 는 deprecated 이고 시스템 malloc 은 내부적으로 `mmap`/`mach_vm_allocate` 로 영역을 받는다. glibc 는 작은 요청은 `brk` 힙, 큰 요청(기본 128KB 이상)은 별도 `mmap` 을 쓴다. Ch.13 실습에서 1MB malloc 이 다른 영역(`0x7ce800000`)에서 나온 것도 같은 맥락이다.

## 7. 기타 호출 (14.6)

- `calloc(n, size)`: 할당 + **0 으로 채움** → 5.3 의 uninit read 를 예방.
- `realloc(p, new_size)`: 더 큰(또는 작은) 영역을 만들고 옛 내용을 복사한 뒤 새 포인터를 돌려준다. 제자리 확장이 되면 복사 없이 같은 포인터. **반환값을 반드시 다시 받아야** 하고, 실패 시 NULL 이므로 `p = realloc(p, n)` 패턴은 실패 때 원래 포인터를 잃는다(누수).

```c
int *tmp = realloc(v, new_cap * sizeof *v);
if (!tmp) { /* v 는 여전히 유효 */ handle_oom(); }
else v = tmp;
```

### 8.1 버그 7종을 한 파일에 — `code/C14_memory_bugs.c`

```c
// C14_memory_bugs.c — 14.4절 "흔한 실수"를 하나씩 일부러 저지르고 도구로 잡아 보기
// 정상 빌드 : cc -Wall -Wextra -O0 -g code/C14_memory_bugs.c -o .work/bin/C14_bugs
// ASan 빌드 : cc -Wall -Wextra -O0 -g -fsanitize=address code/C14_memory_bugs.c -o .work/bin/C14_bugs_asan
// 실행      : .work/bin/C14_bugs_asan <mode>   (mode: sizeof overflow uaf double invalid leak uninit null)
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void demo_sizeof(void) {
    int *x = malloc(10 * sizeof(int));
    int arr[10];
    printf("sizeof(x)   = %zu  (포인터 크기일 뿐, 40이 아니다)\n", sizeof(x));
    printf("sizeof(arr) = %zu  (배열은 컴파일러가 크기를 안다)\n", sizeof(arr));
    free(x);
}

// 버그 1: strlen(src) 만큼만 할당 → '\0' 1바이트가 넘친다 (heap-buffer-overflow)
static void bug_overflow(void) {
    const char *src = "hello";
    char *dst = malloc(strlen(src));          // too small! (+1 빠짐)
    strcpy(dst, src);
    printf("dst=%s\n", dst);
    free(dst);
}

// 버그 2: free 한 뒤에 사용 (dangling pointer → heap-use-after-free)
static void bug_uaf(void) {
    int *data = malloc(100 * sizeof(int));
    data[0] = 7;
    free(data);
    printf("data[0]=%d\n", data[0]);
}

// 버그 3: 같은 포인터를 두 번 free (double free)
static void bug_double(void) {
    int *p = malloc(sizeof(int));
    free(p);
    free(p);
}

// 버그 4: malloc이 준 포인터가 아닌 값을 free (invalid free)
static void bug_invalid(void) {
    int *data = malloc(100 * sizeof(int));
    free(data + 50);                          // 배열 한가운데
}

// 버그 5: 해제 깜빡 (memory leak)
static void bug_leak(void) {
    for (int i = 0; i < 3; i++) {
        char *p = malloc(64);
        p[0] = 'x';
        (void)p;                              // free 안 함
    }
    printf("leaked 3 x 64 bytes\n");
}

// 버그 6: 초기화하지 않은 heap 읽기 (uninitialized read) — ASan은 못 잡는다
static void bug_uninit(void) {
    int *p = malloc(4 * sizeof(int));
    printf("uninit p[0..3] = %d %d %d %d\n", p[0], p[1], p[2], p[3]);
    int *q = calloc(4, sizeof(int));
    printf("calloc q[0..3] = %d %d %d %d\n", q[0], q[1], q[2], q[3]);
    free(p); free(q);
}

// 버그 7: 할당을 깜빡 — NULL 역참조 (숙제 Q1의 null.c)
static void bug_null(void) {
    int *p = NULL;
    printf("about to deref NULL\n");
    fflush(stdout);
    *p = 1;
}

int main(int argc, char *argv[]) {
    const char *m = argc > 1 ? argv[1] : "sizeof";
    if (!strcmp(m, "sizeof"))   demo_sizeof();
    else if (!strcmp(m, "overflow")) bug_overflow();
    else if (!strcmp(m, "uaf"))      bug_uaf();
    else if (!strcmp(m, "double"))   bug_double();
    else if (!strcmp(m, "invalid"))  bug_invalid();
    else if (!strcmp(m, "leak"))     bug_leak();
    else if (!strcmp(m, "uninit"))   bug_uninit();
    else if (!strcmp(m, "null"))     bug_null();
    else { fprintf(stderr, "unknown mode %s\n", m); return 2; }
    printf("[%s] 끝까지 실행됨\n", m);
    return 0;
}
```

두 빌드 모두 **경고 0개** — 컴파일러는 이 버그들을 하나도 못 잡는다는 것 자체가 교훈이다.

## 9. 펌웨어 엔지니어의 눈으로

- **펌웨어는 대개 malloc 을 금지하거나 부팅 때만 쓴다.** SSD FW 에선 NVMe 커맨드 컨텍스트, 버퍼 디스크립터를 **고정 크기 풀(pool)** 로 미리 잡아 두고 free list 로 돌렸다 — 이게 Ch.17 의 segregated list / slab 과 같은 구조이고, 단편화와 비결정적 지연을 원천 차단한다. 면접에서 "왜 임베디드에서 malloc 을 피하나?" 에는 **단편화, 최악 지연(WCET), 실패 처리 경로** 세 가지로 답한다.
- **매직 넘버 + 헤더 검사** 는 펌웨어에서도 그대로 쓴다: 버퍼 디스크립터에 magic/owner 필드를 두고 반환 시 assert — double free 와 엉뚱한 반환을 FW 수준에서 잡는 방법. Ch.17 의 `assert(hptr->magic == 1234567)` 이 바로 그것.
- **use-after-free 의 FW 버전은 DMA 다.** CPU 가 버퍼를 free 해서 재사용했는데 디바이스(NAND 컨트롤러, PCIe 엔드포인트)가 아직 그 주소로 DMA 중이면, ASan 도 못 잡는 오염이 생긴다. 해결은 "DMA 완료 인터럽트/완료 큐 엔트리를 받은 뒤에만 free" 라는 소유권 규칙과, IOMMU(DART)로 해제된 버퍼의 디바이스 매핑을 끊는 것.
- **누수는 "언젠가 재부팅" 이 아니라 "필드 불량"** 이다. 수년간 꺼지지 않는 SSD 에서 커맨드 하나당 디스크립터 하나가 새면 결국 큐가 막힌다. 그래서 FW 는 풀마다 사용량 카운터와 high-watermark 를 로그로 남긴다.
- AI 가속기 런타임(CUDA, Metal)에도 `cudaMalloc/cudaFree` 가 있고, compute-sanitizer 가 ASan 역할을 한다. 디바이스 메모리 할당은 비싸서 PyTorch 같은 프레임워크는 **캐싱 할당기** 를 위에 얹는다 — 다시 Ch.17 의 세계.

<details>
<summary>답 보기</summary>

**아니다, 라이브러리 함수** 다. libc 의 할당기가 이미 받아 둔 힙 영역을 쪼개서 준다(free list, 헤더, 분할/병합).
힙이 모자랄 때만 OS 에 **`brk/sbrk`**(힙 끝 이동) 또는 **`mmap`**(익명 매핑)으로 더 받는다. glibc 는 큰 요청(기본 128KB 이상)을 바로 mmap 하고, 반환 시 munmap 한다.
그래서 대부분의 malloc 은 커널 진입 없이 수십 ns 에 끝나고, 가끔 큰 지연이 튄다.

</details>

### Q2. free(ptr) 는 크기를 안 받는데 어떻게 얼마를 해제할지 아나?
<details>
<summary>답 보기</summary>

할당기가 사용자 포인터 **바로 앞에 헤더** 를 두고 크기(와 magic, 플래그)를 적어 둔다. free 는 `ptr - sizeof(header)` 로 헤더를 찾는다.
그래서 malloc(N) 은 실제로 **N + 헤더 크기 + 정렬 패딩** 을 쓴다. 다른 방식으로는 크기 클래스별 페이지(slab, jemalloc 의 run)를 써서 **주소만 보고 크기 클래스를 아는** 방법이 있다(헤더 없음).
이 구조 때문에 invalid free(배열 중간 주소)는 엉뚱한 바이트를 헤더로 읽어 할당기를 망가뜨린다.

</details>

### Q3. use-after-free 와 double free 는 왜 보안 취약점이 되나?
<details>
<summary>답 보기</summary>

free 된 청크는 할당기의 **free list 노드** 로 재사용된다(next 포인터가 사용자 데이터 자리에 들어감). use-after-free 로 그 자리를 쓰면 공격자가 **free list 의 next 포인터를 조작** 해 다음 malloc 이 임의 주소를 반환하게 만들 수 있다.
double free 는 같은 청크가 free list 에 두 번 들어가 **두 번의 malloc 이 같은 메모리를 반환** → 한 객체를 다른 타입으로 덮어쓰는 타입 혼동.
대응: 하드닝된 할당기(safe-linking, 포인터 암호화), quarantine, ASan/MTE(ARM Memory Tagging), 그리고 free 후 포인터를 NULL 로.

</details>

### Q4. ASan 은 어떻게 동작하고, 무엇을 못 잡나?
<details>
<summary>답 보기</summary>

컴파일러가 **모든 load/store 앞에 섀도 메모리 검사** 를 삽입한다. 응용 메모리 8바이트당 섀도 1바이트(0 = 전부 유효, 1~7 = 앞 k 바이트만 유효, 음수 = redzone/freed). malloc 청크 양옆에 **redzone**, free 된 청크는 **quarantine** 에 잠시 보관해 재사용을 늦춘다.
오버헤드: 대략 **2배 느림, 메모리 2~3배**.
못 잡는 것: **초기화 안 된 읽기**(→ MSan), redzone 을 건너뛰어 다른 유효 청크에 떨어지는 큰 오버플로, quarantine 이 밀려난 뒤의 UAF, 그리고 macOS 에서는 누수(LSan 미지원 → `leaks`).

</details>

### Q5. realloc 사용 시 흔한 실수는?
<details>
<summary>답 보기</summary>

1. `p = realloc(p, n)` — 실패하면 NULL 이 p 를 덮어써 **원래 블록 누수**. 임시 변수로 받는다.
2. realloc 후 **옛 포인터를 계속 사용** — 블록이 옮겨졌으면 dangling.
3. 1개씩 늘리기 — 매번 복사하면 O(n²). **2배씩 키워야** 분할 상환 O(1).
4. 새로 늘어난 부분은 초기화되지 않는다.

</details>

### Q6. 프로세스가 끝나면 free 안 한 메모리는 어떻게 되나? 그럼 free 는 왜 하나?
<details>
<summary>답 보기</summary>

메모리 관리는 두 층이다. OS 는 프로세스 종료 시 그 주소 공간의 **모든 페이지(코드, 스택, 힙)를 회수** 하므로 시스템 차원의 누수는 없다.
그래도 free 해야 하는 이유: **장수 프로세스**(서버, 데몬, 커널, 펌웨어)에서는 누수가 누적돼 OOM 으로 죽고, 라이브러리 코드는 누가 얼마나 오래 쓸지 모르며, 누수 도구의 잡음을 줄여 진짜 버그를 보이게 하려면 깨끗해야 한다.

</details>

## 11. 자가 점검 & 숙제

### 퀴즈 1. `char *s = "hi"; char *d = malloc(sizeof(s)); strcpy(d, s);` 는 맞나?
<details>
<summary>답 보기</summary>

64비트에서 `sizeof(s)` = 8 이라 "hi\0" 3바이트는 들어가므로 **우연히 동작** 하지만 의도와 다르다. 문자열이 8바이트 이상이면 오버플로. 정답은 `malloc(strlen(s) + 1)` 또는 `strdup(s)`.

</details>

### 퀴즈 2. 일반 빌드에서 overflow 버그가 아무 문제 없이 돈 이유는?
<details>
<summary>답 보기</summary>

malloc 이 5바이트 요청을 내부 최소 단위(예: 16바이트)로 반올림해 줘서, 넘친 1바이트(`'\0'`)가 **같은 블록의 패딩** 에 떨어졌기 때문. 다른 크기·다른 할당기에서는 옆 청크의 헤더를 깨뜨린다.

</details>

### 퀴즈 3. ASan 섀도 바이트 `05` 와 `fd` 는 각각 무슨 뜻?
<details>
<summary>답 보기</summary>

`05`: 해당 8바이트 중 **앞 5바이트만 접근 가능**(5바이트 할당의 끝). `fd`: **free 된 힙 영역**(use-after-free 탐지용).

</details>

### 퀴즈 4. `free(data + 50)` (data 는 int 100개) 에 ASan 이 "200 bytes inside" 라고 한 이유는?
<details>
<summary>답 보기</summary>

포인터 산술은 요소 단위다. `data + 50` 은 `50 * sizeof(int) = 200` 바이트 뒤.

</details>

### 원문 Homework 중 꼭 해볼 것

- **Q5 (data[100] = 0)**: 100개짜리 배열의 101번째에 쓰기 → 일반 실행은 조용하고 ASan 은 heap-buffer-overflow 를 낸다. **off-by-one 이 "돌아간다" 는 착각** 을 확인하는 문제.
- **Q7 (중간 포인터 free)**: 위 `invalid` 모드. macOS 일반 실행은 SIGTRAP 으로 죽는다 — **할당기가 헤더 기반으로 동작한다** 는 걸 체감하는 문제.
- **Q8 (realloc 벡터)**: 2배씩 키우는 벡터와 1개씩 키우는 벡터, 연결 리스트를 비교 → **분할 상환 비용과 캐시 지역성** 을 확인하는 문제. ASan 빌드로 돌려 경계 버그도 함께 잡아 볼 것.
