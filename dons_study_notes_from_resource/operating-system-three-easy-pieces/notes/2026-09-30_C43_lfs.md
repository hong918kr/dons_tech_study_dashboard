## 0. 한눈에 보기

> **CRUX — "How can a file system transform all writes into sequential writes? For reads, this task is impossible, as the desired block to be read may be anywhere on disk. For writes, however, the file system always has a choice, and it is exactly this choice we hope to exploit."**
> (FS는 모든 쓰기를 어떻게 순차 쓰기로 바꿀 수 있나? 읽기는 원하는 블록이 어디 있든 가야 하니 불가능하지만, 쓰기는 FS가 **어디에 쓸지 고를 수 있다** — 바로 그 선택권을 이용한다.)

- 동기(Rosenblum & Ousterhout, 1991): 메모리가 커져 **읽기는 캐시가 흡수** → 디스크 트래픽은 점점 **쓰기**. 순차 vs 랜덤 I/O 격차는 계속 벌어짐. FFS는 작은 파일 하나 만드는 데 짧은 seek를 6번 하고, RAID-4/5의 small-write 문제도 신경 안 씀.
- 아이디어: 모든 업데이트(데이터 + **메타데이터까지**)를 메모리의 **segment** 에 모았다가, 꽉 차면 디스크의 **빈 곳에 한 번에 순차로** 쓴다. **절대 덮어쓰지 않는다.**
- 새 문제 1: inode가 계속 이동 → **imap**(inode 번호 → 최신 inode 주소)이라는 간접 계층, imap 조각도 로그에 같이 쓰고, 고정 위치의 **checkpoint region(CR)** 이 imap 조각들을 가리킨다.
- 새 문제 2: 옛 버전이 쓰레기로 남음 → **cleaner(GC)** 가 세그먼트 단위로 live 블록만 모아 새 세그먼트에 쓰고 옛 세그먼트를 해제. liveness 판정은 **segment summary**, 정책은 **hot/cold 분리**.
- 크래시: CR 두 개를 번갈아 쓰고 타임스탬프로 원자성 확보, 마지막 CR 이후는 **roll-forward**.
- LFS의 유산: WAFL, ZFS, btrfs, F2FS, 그리고 **SSD의 FTL** — Don이 7년 동안 만든 바로 그 구조.

## 2. 순차로 쓰기 (43.1)

데이터 블록 D를 파일에 쓰면 메타데이터(inode)도 갱신해야 한다. LFS는 **둘 다** 디스크의 다음 빈 자리에 붙여 쓴다.

```text
| D        | I (blk[0]: A0) |
  A0
```

inode는 보통 128B 정도로 데이터 블록(4KB)보다 훨씬 작지만, 그림에선 같은 크기로 그린다. 이게 LFS의 전부다: **모든 업데이트를 디스크에 순차로 쓴다.** 나머지는 이 결정 때문에 생기는 "디테일"이다.

> **TIP — 디테일이 중요하다.** "큰 그림은 알겠고 나머지는 디테일"이라고 반만 배우지 마라. LFS도 아이디어는 쉽지만 실제로 동작하게 하려면 까다로운 경우들을 다 생각해야 한다.

## 3. 순차로, 그리고 효과적으로 (43.2)

순서대로 쓰는 것만으론 부족하다. 시간 T에 주소 A를 쓰고, 조금 뒤 T+δ에 A+1을 쓰면 그 사이 디스크가 돌아가 버려서 **T_rotation − δ** 를 기다려야 한다. peak를 내려면 **연속 쓰기를 많이(또는 하나의 큰 쓰기로)** 내보내야 한다.

그래서 LFS는 **write buffering**: 업데이트를 메모리에 모아 **segment**(수 MB) 단위로 한 번에 쓴다. 원문 예: 파일 j에 블록 4개, 파일 k에 블록 1개 → 7블록짜리 세그먼트 하나로:

```text
| D[j,0] | D[j,1] | D[j,2] | D[j,3] | I[j] blk[0..3]=A0..A3 | D[k,0] | I[k] blk[0]=A5 |
  A0       A1       A2       A3                               A5
```

## 4. 얼마나 모아야 하나 (43.3)

위치 잡기 T_position, 최대 전송률 R_peak, 한 번에 D MB를 쓴다면:

```text
T_write     = T_position + D / R_peak
R_effective = D / T_write = D / (T_position + D / R_peak)
```

R_effective = F × R_peak 가 되도록 D를 풀면:

```text
D = F × R_peak × (T_position + D / R_peak)
D = F × R_peak × T_position + F × D
D (1 − F) = F × R_peak × T_position
D = F / (1 − F) × R_peak × T_position
```

[Ch.41 FFS](2026-09-30_C41_ffs.md)의 amortization 식과 같은 식이다. 원문 예: T = 10ms, R = 100MB/s, F = 0.9 → D = 0.9/0.1 × 100MB/s × 0.01s = **9MB**. 원문 질문 "95%? 99%?" → **19MB**, **99MB** (아래 코드 출력 2번).

**새 예제 — NVMe SSD:** T 자리에 명령당 고정 오버헤드 ~20µs, R = 3000MB/s를 넣으면 F = 0.9 에 D = 9 × 3000MB/s × 0.00002s = **0.54MB**. 디스크보다 훨씬 작은 chunk로 peak에 가까워진다 — 하지만 SSD 내부에는 GC라는 다른 이유로 큰 순차 쓰기가 여전히 유리하다(11절).

## 5. 문제: inode 찾기 (43.4)

- old UNIX FS: inode가 고정 위치 배열 → `start + inum × size` 곱셈 한 번.
- FFS: 그룹별 inode 덩어리 → 그룹 크기와 시작 주소만 알면 역시 계산.
- **LFS: inode가 디스크 여기저기 흩어져 있고, 덮어쓰지 않으니 최신 버전이 계속 이동한다.** 계산으로는 못 찾는다.

## 6. 해법: 간접 계층 imap (43.5)

**inode map(imap)**: inode 번호를 받아 **최신 inode의 디스크 주소**를 돌려주는 구조. 단순 배열(엔트리당 4B 디스크 포인터)이라고 생각하면 된다. inode가 디스크에 쓰일 때마다 imap 갱신.

> **TIP — 간접 계층을 써라.** "컴퓨터 과학의 모든 문제는 간접 계층 하나로 풀린다"(Wheeler) — 사실은 "대부분의"이고, 뒷말이 있다: "**간접 계층이 너무 많다는 문제만 빼고**." 가상 메모리도, 파일이라는 개념도 간접 계층이다. imap은 **inode 번호의 가상화**다. 대가는 추가 오버헤드.

imap도 영속화해야 한다. 고정 위치에 두면 매 업데이트마다 그곳으로 seek → 순차 쓰기 이점이 사라진다. 그래서 **imap 조각을 다른 새 정보 바로 옆에** 같이 쓴다:

```text
| D        | I[k] blk[0]: A0 | imap map[k]: A1 |
  A0         A1
```

## 7. 완성: checkpoint region (43.6)

## 8. 읽기 과정 요약 (43.7)

메모리에 아무것도 없을 때: **CR 읽기 → CR이 가리키는 imap 조각 전부 읽어 메모리에 캐시** → 이후 inode 번호가 오면 imap에서 주소를 찾아 inode 읽기 → direct/indirect 포인터로 데이터 읽기(UNIX FS와 동일). 공통 경우에 LFS의 읽기 I/O 수는 일반 FS와 **같다**. 추가 일은 메모리 안 imap 조회뿐.

## 9. 디렉터리는? (43.8)

디렉터리 구조는 고전 UNIX와 같다: (이름, inode 번호) 쌍의 모음. 디렉터리 `dir` 에 파일 `foo` 를 만들면 한 번의 순차 쓰기로:

```text
| D[k] | I[k] blk[0]=A0 | D[dir] (foo,k) | I[dir] blk[0]=A2 | imap map[k]=A1, map[dir]=A3 |
  A0     A1               A2               A3
```

`/dir/foo` 접근: imap(메모리)에서 dir의 inode 위치 A3 → dir inode → 디렉터리 데이터 A2 → (foo, k) → imap에서 k의 위치 A1 → inode k → 데이터 A0.

### 9.1 recursive update problem

제자리에 쓰지 않는 FS에서는 inode가 갱신될 때마다 **위치가 바뀐다**. 만약 디렉터리가 inode **주소**를 들고 있었다면 디렉터리도 바뀌어야 하고(새 위치), 그 부모도, 그 부모의 부모도… 루트까지 전부 다시 써야 한다.

LFS는 imap으로 이걸 막는다: 디렉터리는 **inode 번호**만 들고 있고, 위치 변화는 **imap에만** 반영된다. 간접 계층 덕분에 갱신이 전파되지 않는다. (원문 각주가 인용하는 [Z+12] 논문: FTL도 같은 문제를 갖고, SSD 안에 imap과 같은 구조가 있다.)

## 10. 새 문제: 쓰레기 수집 (43.9 ~ 43.11)

### 10.1 쓰레기가 생기는 방식

- 파일 k의 블록 D0를 **덮어쓰면**: 새 D0 + 새 I[k] 기록 → 옛 D0, 옛 I[k] **둘 다 garbage**.
- 파일 k에 블록을 **append** 하면: 새 D1 + 새 I[k] → 옛 I[k]만 garbage, 옛 D0는 새 inode가 여전히 가리키므로 **live**.

옛 버전을 남겨 사용자가 복원하게 할 수도 있다(**versioning FS**). LFS는 최신만 유지하고 백그라운드에서 **청소(cleaning)** 한다 — GC다.

### 10.2 왜 세그먼트 단위로 청소하나

블록 하나씩 해제하면 디스크가 **구멍 숭숭**한 상태가 되어 큰 연속 공간을 못 찾고 쓰기 성능이 무너진다. 그래서 cleaner는 **세그먼트 단위**: 오래된(부분적으로 사용 중인) 세그먼트 M개를 읽어 live 블록만 추려 새 세그먼트 N개(N < M)로 쓰고, M개를 통째로 해제한다.

### 10.3 메커니즘: 블록이 살아 있나? (43.10)

세그먼트 머리에 **segment summary block**: 각 데이터 블록이 **어느 inode(N)의 몇 번째 블록(T)** 인지 기록. 주소 A의 블록 D가 live인지:

```c
(N, T) = SegmentSummary[A];
inode = Read(imap[N]);
if (inode[T] == A)
     // block D is alive
else
     // block D is garbage
```

"inode가 지금 그 오프셋으로 가리키는 주소가 정확히 A인가?" 그렇다면 live, 아니면 더 새 버전이 있다는 뜻. 지름길: 파일이 삭제/잘리면 **version number** 를 올려 imap에 기록하고, 세그먼트에도 기록해 두면 버전만 비교해서 inode를 읽지 않고 바로 dead 판정.

### 10.4 정책: 언제, 어떤 세그먼트를? (43.11)

- **언제**: 주기적으로, 유휴 시간에, 또는 디스크가 꽉 차서 어쩔 수 없을 때. 이건 쉽다.
- **어느 것**: 어렵다(논문이 여럿). 원문 LFS 논문은 **hot/cold 분리**:
  - **hot 세그먼트**: 내용이 자주 덮어쓰인다 → 기다리면 더 많은 블록이 저절로 죽는다 → **늦게** 청소.
  - **cold 세그먼트**: 죽은 블록이 좀 있지만 나머지는 안정적 → **빨리** 청소(기다려도 더 안 죽는다).
  - 이를 구현한 휴리스틱이 **cost-benefit**: 이득 = (1−u) × age, 비용 = 1 + u (세그먼트 읽기 1 + live u 쓰기). (1−u)·age/(1+u)가 큰 세그먼트부터. 완벽하진 않고 이후 더 나은 방법들이 나왔다(Matthews 등).

## 11. 크래시 복구와 로그 (43.12)

정상 동작: 세그먼트에 버퍼링 → 쓰기, CR이 로그의 head/tail 세그먼트를 가리키고 각 세그먼트는 다음 세그먼트를 가리킨다. CR은 주기적으로 갱신. 크래시는 두 곳에서 날 수 있다.

1. **CR 쓰는 도중**: LFS는 **CR을 디스크 양 끝에 2개** 두고 **번갈아** 쓴다. 갱신 프로토콜: 헤더(타임스탬프) → 본문 → 마지막 블록(타임스탬프). 크래시하면 두 타임스탬프가 불일치 → 그 CR은 버리고 **타임스탬프가 일관된 가장 최근 CR** 을 쓴다.
2. **세그먼트 쓰는 도중**: CR은 30초마다라 마지막 일관 스냅샷은 꽤 오래됐을 수 있다. 그냥 CR + imap부터 시작하면 **최근 수십 초 업데이트를 잃는다**. 그래서 **roll forward**: 마지막 CR에서 로그의 끝을 찾고, 그 다음 세그먼트들을 읽어 **유효한 업데이트**가 있으면 FS에 반영한다(Rosenblum 학위논문 참조).

[Ch.42](2026-09-30_C42_crash_consistency_journaling.md) 관점: LFS는 **로그 자체가 FS**라 저널을 따로 둘 필요가 없고, CR 이중화 + 타임스탬프가 TxB/TxE 역할을 한다.

## 12. 요약 (43.13)

LFS = 덮어쓰지 않고 항상 빈 곳에 쓰고, 옛 공간은 나중에 청소로 회수. DB에서는 **shadow paging**, FS에서는 **copy-on-write**라 부른다. 쓰기를 메모리 세그먼트에 모아 순차로 내보내 효율이 높다. 대가는 **쓰레기**와 **청소 비용** — LFS 초기 영향력을 제한한 논쟁거리였다(Seltzer 등: fsync 많은 DB 워크로드에서 약점). 그러나 WAFL, ZFS, btrfs, 그리고 **플래시 SSD**가 COW 방식을 쓰며 LFS의 유산은 살아 있다.

> **TIP — 결함을 미덕으로 바꿔라.** NetApp **WAFL** 은 옛 버전을 **스냅샷**으로 제공해서, 청소를 덜 자주 해도 되고 사용자는 실수로 지운 파일을 되살리는 기능을 얻었다. 결함(쓰레기)이 기능이 됐다.

## 13. 직접 해보기

### 13.1 장난감 LFS + cleaner (C)

`code/C43_lfs_cleaner.c`: 64세그먼트 × 16블록 로그. 파일 = 데이터 1블록 + inode 1블록. 갱신 = 둘 다 새 위치에 append, imap 갱신. liveness는 원문 의사코드 그대로. free 세그먼트가 3개 이하면 청소. 정책 비교(greedy vs cost-benefit), 워크로드 비교(uniform vs hot/cold 90/10), 로그 헤드 1개 vs 2개(cleaner가 옮긴 블록을 별도 헤드에 모아 **cold끼리** 두기).

```c
/*
 * C43_lfs_cleaner.c — 장난감 LFS: 로그 append + imap + segment summary + cleaner
 *
 *  - 모든 쓰기는 "현재 세그먼트"의 다음 빈 칸에 append (덮어쓰기 없음)
 *  - 파일 하나 = 데이터 블록 1개 + inode 1개. 갱신 시 둘 다 새 위치에 append
 *  - imap[inum] = 최신 inode 주소, inode 내용(ptr) = 최신 데이터 블록 주소
 *  - segment summary(ss[addr]) = 이 블록이 (어떤 종류, 몇 번 inode) 였는지
 *  - liveness: 원문 의사코드 그대로  (N,T)=SS[A]; if inode[N][T]==A → live
 *  - free 세그먼트가 부족하면 cleaner 가 victim 세그먼트의 live 블록만 옮기고 해제
 *  - 정책 비교: greedy(가장 비어 있는 세그먼트) vs cost-benefit (Rosenblum: (1-u)*age/(1+u))
 *  - 워크로드: uniform vs hot/cold(쓰기 90% 가 파일 10% 에 몰림)
 *  - 지표: write amplification = (사용자 쓰기 + cleaner 복사) / 사용자 쓰기
 *
 * build: cc -Wall -Wextra -O0 code/C43_lfs_cleaner.c -o .work/bin/C43_lfs_cleaner
 */
#include <stdint.h>
#include <stdio.h>
#include <string.h>

#define NSEG 64
#define SEGB 16
#define NB (NSEG * SEGB)
#define MAXF 512

enum { T_NONE = 0, T_DATA = 1, T_INODE = 2 };
typedef struct { int type, inum; } ss_t;

static ss_t ss[NB];
static int imap[MAXF], dptr[MAXF], seg_free[NSEG], seg_time[NSEG];
static int head_seg[2], head_off[2], nfiles, now, segregate;
#define cur_seg head_seg[0]
static long user_w, clean_w, cleaned_segs, thrash;
static double cleaned_u_sum;

static uint32_t rng = 12345;
static uint32_t rnd(void) { rng = rng * 1103515245u + 12345u; return (rng >> 8) & 0xffffff; }

static void reset(int nf) {
    memset(ss, 0, sizeof ss);
    for (int s = 0; s < NSEG; s++) { seg_free[s] = 1; seg_time[s] = 0; }
    for (int i = 0; i < MAXF; i++) imap[i] = dptr[i] = -1;
    head_seg[0] = head_seg[1] = -1; head_off[0] = head_off[1] = SEGB; nfiles = nf; now = 0;
    user_w = clean_w = cleaned_segs = thrash = 0; cleaned_u_sum = 0;
}

static int nfree(void) { int n = 0; for (int s = 0; s < NSEG; s++) n += seg_free[s]; return n; }

/* h=0: 사용자 쓰기 로그 헤드, h=1: cleaner 전용 헤드(segregate=1 일 때만) */
static int alloc_h(int h) {
    if (!segregate) h = 0;
    if (head_off[h] == SEGB) {
        int s = 0;
        while (s < NSEG && !seg_free[s]) s++;
        if (s == NSEG) { fprintf(stderr, "disk full\n"); return -1; }
        seg_free[s] = 0; head_seg[h] = s; head_off[h] = 0;
        seg_time[s] = now;
    }
    if (h == 0) seg_time[head_seg[h]] = now; /* cleaner 가 옮긴 블록은 나이를 유지 */
    return head_seg[h] * SEGB + head_off[h]++;
}
static int alloc_blk(void) { return alloc_h(0); }

static int is_live(int a) {
    if (ss[a].type == T_DATA) return dptr[ss[a].inum] == a;   /* inode[N][T] == A ? */
    if (ss[a].type == T_INODE) return imap[ss[a].inum] == a;  /* imap[N] == A ? */
    return 0;
}

static void put(int a, int type, int inum) { ss[a].type = type; ss[a].inum = inum; }

static void write_file(int inum) {
    int a = alloc_blk(); put(a, T_DATA, inum); dptr[inum] = a;
    int b = alloc_blk(); put(b, T_INODE, inum); imap[inum] = b;
    user_w += 2;
}

static int live_in(int s) { int n = 0; for (int i = 0; i < SEGB; i++) n += is_live(s * SEGB + i); return n; }

static int clean_one(int costbenefit) {
    int best = -1;
    double bestv = 0;
    for (int s = 0; s < NSEG; s++) {
        if (seg_free[s] || s == head_seg[0] || s == head_seg[1]) continue;
        int l = live_in(s);
        if (l == SEGB) continue;
        double u = (double)l / SEGB, v;
        if (costbenefit) v = (1 - u) * (double)(now - seg_time[s] + 1) / (1 + u);
        else v = 1 - u;
        if (best < 0 || v > bestv) { best = s; bestv = v; }
    }
    if (best < 0) return 0;
    cleaned_u_sum += (double)live_in(best) / SEGB;
    cleaned_segs++;
    int dirty[SEGB], nd = 0;
    for (int i = 0; i < SEGB; i++) {
        int a = best * SEGB + i;
        if (!is_live(a)) continue;
        int inum = ss[a].inum;
        if (ss[a].type == T_DATA) { /* 데이터 복사 → inode 도 바뀌어야 함 */
            int na = alloc_h(1); put(na, T_DATA, inum); dptr[inum] = na; clean_w++;
        }
        int seen = 0;
        for (int k = 0; k < nd; k++) if (dirty[k] == inum) seen = 1;
        if (!seen) dirty[nd++] = inum;
    }
    for (int k = 0; k < nd; k++) {
        int inum = dirty[k];
        int nb = alloc_h(1); put(nb, T_INODE, inum); imap[inum] = nb; clean_w++;
    }
    for (int i = 0; i < SEGB; i++) put(best * SEGB + i, T_NONE, -1);
    seg_free[best] = 1;
    return 1;
}

static void run(const char *wname, int hotcold, int cb, int seg, int nf, long nupd) {
    reset(nf);
    segregate = seg;
    for (int i = 0; i < nf; i++) write_file(i); /* 초기 채우기 */
    user_w = clean_w = 0;
    for (long t = 0; t < nupd; t++) {
        now++;
        /* 64번 청소해도 free 가 안 늘면 "thrash" 로 세고 그냥 진행 (빈 세그먼트 3개 여유) */
        int guard = 0;
        while (nfree() <= 3) {
            if (guard++ == 64) { thrash++; break; }
            if (!clean_one(cb)) { printf("  (cleaner stuck at t=%ld)\n", t); return; }
        }
        int f;
        if (hotcold && rnd() % 100 < 90) f = (int)(rnd() % (uint32_t)(nf / 10));
        else f = (int)(rnd() % (uint32_t)nf);
        write_file(f);
    }
    printf("%-9s %-13s %-9s util=%4.1f%%  WA=%5.2f  cleaned=%6ld, victim u=%.2f, thrash=%ld\n", wname,
           cb ? "cost-benefit" : "greedy", seg ? "2 heads" : "1 head", 100.0 * nf * 2 / NB, (double)(user_w + clean_w) / user_w,
           cleaned_segs, cleaned_segs ? cleaned_u_sum / cleaned_segs : 0, thrash);
}

static void dump(int nblk) {
    for (int a = 0; a < nblk; a++) {
        if (ss[a].type == T_NONE) continue;
        printf("  A%-3d SS=(%s, inum %d)  -> %s\n", a, ss[a].type == T_DATA ? "data " : "inode",
               ss[a].inum, is_live(a) ? "LIVE" : "dead (garbage)");
    }
}

int main(void) {
    printf("== 1. tiny trace: write f0, f1, overwrite f0, overwrite f0 ==\n");
    reset(4);
    write_file(0); write_file(1); write_file(0); write_file(0);
    dump(16);
    printf("  imap: f0 -> A%d, f1 -> A%d  (segment 0 live = %d/16)\n", imap[0], imap[1], live_in(0));

    printf("\n== 2. how much to buffer: D = F/(1-F) * Rpeak * Tpos (Rpeak=100MB/s, T=10ms) ==\n");
    double Fs[] = { 0.5, 0.9, 0.95, 0.99 };
    for (int i = 0; i < 4; i++) printf("  F=%2.0f%% -> D = %6.1f MB\n", Fs[i] * 100, Fs[i] / (1 - Fs[i]) * 100 * 0.01);

    printf("\n== 3. cleaner policies (64 segs x 16 blks, 200k file updates) ==\n");
    int nfs[] = { 256, 384 };
    for (int k = 0; k < 2; k++) {
        rng = 12345; run("uniform", 0, 0, 0, nfs[k], 200000);
        rng = 12345; run("uniform", 0, 1, 0, nfs[k], 200000);
        rng = 12345; run("hot/cold", 1, 0, 0, nfs[k], 200000);
        rng = 12345; run("hot/cold", 1, 1, 0, nfs[k], 200000);
        rng = 12345; run("hot/cold", 1, 0, 1, nfs[k], 200000);
        rng = 12345; run("hot/cold", 1, 1, 1, nfs[k], 200000);
    }
    return 0;
}
```

  - **hot/cold인데 로그 헤드가 1개면 오히려 uniform보다 나쁘다**(75%에서 2.92 vs 2.16). 원래 LFS 논문의 유명한 반직관적 결과와 같은 방향: 지역성이 있어도 hot·cold 블록이 같은 세그먼트에 **섞이면** cold 블록이 세그먼트 사용률을 높게 붙잡아 둔다. cost-benefit 정책만으로는 거의 차이가 없다(2.90).
  - **cleaner 출력을 별도 헤드로 분리(cold끼리 모으기) + cost-benefit** 이면 75%에서 **WA 1.95** — hot/cold greedy 1 head(2.92) 대비 약 1/3 감소. 원문 "cold는 빨리, hot은 늦게"가 실제로 효과를 내려면 **분리(segregation)** 가 같이 있어야 한다는 걸 보여 준다.
  - `thrash` = 64번 연속 청소해도 free 세그먼트가 안 늘어난 횟수. greedy 2 heads 75%에서 3회 발생: 이 모델에선 데이터 블록을 옮기면 **그 inode도 새로 써야** 해서, live 데이터는 많고 inode는 다른 세그먼트에 있는 victim을 청소하면 해제하는 것보다 더 많이 쓴다. 실제 LFS가 inode를 블록 단위로 묶어 쓰는 이유이기도 하다. (장난감 모델의 한계 — 숫자는 경향만 볼 것.)

## 14. 펌웨어 엔지니어의 눈으로

- **SSD FTL = LFS.** NAND는 덮어쓰기가 불가능(erase-before-write, erase는 블록 단위)하니 FTL은 필연적으로 로그 구조다: 호스트 쓰기는 **열린 블록(active block)에 순차 append**, 옛 페이지는 invalid(=garbage), **GC가 victim 블록의 valid 페이지만 옮기고 erase** = LFS cleaner. segment ≈ NAND 슈퍼블록(여러 die의 같은 블록 번호 묶음).
- **imap ≈ L2P 테이블, CR ≈ 맵 루트/체크포인트, segment summary ≈ 페이지 OOB의 역매핑(LBA) 정보.** GC의 liveness 판정이 원문 의사코드와 똑같다: OOB에서 이 물리 페이지의 LBA를 읽고, **L2P[LBA] == 이 물리 주소** 이면 valid. 많은 FW는 이걸 매번 하지 않으려고 블록별 **VPC(valid page count) + valid bitmap** 을 유지한다 — LFS의 version number 지름길과 같은 동기.
- **recursive update problem은 FTL 설계에도 그대로 나온다.** 매핑 페이지 자체를 NAND에 쓰면 그 위치가 바뀌고, 그걸 가리키는 상위 디렉터리(GTD)도 바뀌어야 한다. FW는 상위 구조를 **DRAM에 상주시키고 체크포인트 때만** 쓰는 식으로 전파를 끊는다 — imap + CR 30초 갱신과 같은 해법.
- **hot/cold 분리 = 멀티 스트림 / 다중 open block.** 13.1 결과처럼 hot/cold가 섞이면 WA가 크게 오른다. SSD FW는 **호스트 쓰기 스트림과 GC 쓰기 스트림을 다른 open block에** 쓰고(GC로 살아남은 데이터 = cold), NVMe **Streams/FDP(Flexible Data Placement)** 로 호스트가 수명 힌트를 주게 한다. Don이 경험한 "GC 데이터용 별도 블록"이 바로 13.1의 "2 heads" 실험이다. victim 선택도 greedy(최소 VPC) vs cost-benefit(나이 고려)로 같은 논쟁이 있고, wear leveling 때문에 SSD에서는 **erase count** 까지 비용 함수에 들어간다.
- **write amplification = 1/(1−u) 직관과 over-provisioning.** LFS가 디스크가 찰수록 느려지듯, SSD도 사용자 가용 용량 대비 **OP(예비 공간)** 가 작을수록 GC victim의 valid 비율이 높아져 WA가 커진다. 13.1의 util 50% vs 75% 비교가 OP 28% vs 7% 비교와 같은 그림.
- **CR 이중화 + 타임스탬프 = FW 맵 체크포인트 이중화 + 시퀀스.** 그리고 roll-forward = 마지막 맵 체크포인트 이후 **열린 블록들의 OOB를 스캔해 L2P를 재구성**하는 SPOR 단계. lfs.py `-N -D` 결과("file not found")는 FW에서 roll-forward를 빼먹었을 때 "Flush까지 끝난 데이터가 전원 손실 후 사라지는" 버그와 같은 모양이다.

## 15. 면접 질문

### Q1. LFS의 핵심 아이디어와, 그 아이디어가 등장한 배경(1990년대 초 하드웨어 추세)은?
<details>
<summary>답 보기</summary>

추세: **메모리 증가 → 읽기는 캐시가 흡수, 디스크 트래픽은 쓰기 위주**, 순차/랜덤 성능 격차 확대, FFS는 작은 파일 생성에 짧은 seek 여러 번, RAID-5 small write 문제. 아이디어: 데이터와 **메타데이터 모두**를 메모리 **segment** 에 버퍼링해 디스크 빈 곳에 **큰 순차 쓰기**로, **절대 덮어쓰지 않음**. 버퍼 크기는 D = F/(1−F) × R × T (T=10ms, R=100MB/s, 90%면 9MB).

</details>

### Q2. LFS에서 inode는 어떻게 찾나? imap은 어디에 저장되고, 그걸 또 어떻게 찾나?
<details>
<summary>답 보기</summary>

inode가 계속 이동하므로 **imap**(inode 번호 → 최신 inode 주소)이라는 간접 계층. imap을 고정 위치에 두면 매번 seek이 생기니 **imap 조각을 데이터·inode와 같은 세그먼트에** 쓴다. 그 조각들은 디스크 고정 위치의 **checkpoint region**(약 30초마다 갱신, 2개 교대)이 가리킨다. 마운트 시 CR → imap 전체를 메모리에 캐시하므로 평상시 읽기 I/O 수는 일반 FS와 같다. imap은 디렉터리가 inode **번호**만 들게 해서 **recursive update problem** 도 막는다.

</details>

### Q3. cleaner는 블록이 살아 있는지 어떻게 판단하고, 어떤 세그먼트를 먼저 청소하나?
<details>
<summary>답 보기</summary>

**segment summary** 에 블록마다 (inode N, 오프셋 T) 기록. `inode = imap[N]` 을 읽어 `inode[T] == A` 면 live. 삭제/truncate 시 올리는 **version number** 로 지름길. 정책: 언제(주기적/유휴/꽉 찼을 때)는 쉽고, 어느 것은 **cost-benefit**: (1−u)·age/(1+u) 최대인 세그먼트 — **cold는 빨리, hot은 늦게**(hot은 기다리면 저절로 더 죽는다). 실제 효과를 내려면 청소로 살아남은 블록을 **cold끼리 별도 세그먼트에 모으는 분리**가 함께 필요하다.

</details>

### Q4. LFS의 크래시 복구는 저널링 FS와 어떻게 다른가?
<details>
<summary>답 보기</summary>

LFS는 로그가 곧 FS라 별도 저널이 없다. **CR 2개를 번갈아** 쓰고 헤더/끝 블록의 **타임스탬프가 일치하는 최신 CR** 을 채택(원자적 CR 갱신). CR 이후의 업데이트는 로그 끝을 따라 세그먼트를 읽어 **roll-forward** 로 복구. 저널링은 제자리 갱신 + 별도 로그 redo. 둘 다 "커밋 마커 + 순서" 로 원자성을 얻는다는 점은 같다.

</details>

### Q5. SSD의 FTL과 LFS의 대응 관계를 설명하고, LFS에서 배운 교훈 중 FTL 설계에 직접 쓰이는 것을 들어라.
<details>
<summary>답 보기</summary>

NAND는 제자리 덮어쓰기 불가 → FTL은 본질적으로 LFS. **segment ↔ (슈퍼)블록, imap ↔ L2P, segment summary ↔ OOB 역매핑, cleaner ↔ GC, CR ↔ 맵 체크포인트, roll-forward ↔ SPOR 시 open block 스캔**. 직접 쓰이는 교훈: (1) liveness = "역매핑이 가리키는 LBA의 현재 매핑이 나인가", (2) **hot/cold 분리**(GC 스트림 분리, NVMe Streams/FDP), (3) victim 선택(greedy vs cost-benefit + erase count), (4) 사용률이 높을수록 WA 폭증 → **over-provisioning**, (5) 간접 계층으로 갱신 전파 차단.

</details>

<details>
<summary>답 보기</summary>

D = 0.95/0.05 × 200MB/s × 0.005s = 19 × 1MB = **19MB**.

</details>

### 퀴즈 2. 파일 k(블록 2개, D0·D1)의 D1만 덮어썼다. 새로 생기는 garbage는 무엇이고, 무엇이 여전히 live인가? (imap 조각 포함)
<details>
<summary>답 보기</summary>

새로 쓰는 것: D1', I[k]', imap 조각'. garbage가 되는 것: **옛 D1, 옛 I[k], 옛 imap 조각**(그 조각의 다른 엔트리들은 새 조각에 복사되어 있음). **D0는 live** — 새 inode가 여전히 가리킨다.

</details>

### 퀴즈 3. 세그먼트 사용률 u인 세그먼트를 청소하면 세그먼트 하나당 순수하게 얻는 빈 공간은? u = 0.8이면 빈 세그먼트 1개를 얻기 위해 몇 개를 읽어야 하나?
<details>
<summary>답 보기</summary>

세그먼트 하나 청소 → live u만큼 다시 쓰므로 순증 = **1 − u**. u = 0.8이면 0.2개씩 → 빈 세그먼트 1개에 **5개 읽기 + 4개 분량 쓰기**. (inode 재기록까지 치면 더 비싸다.) 디스크가 찰수록 LFS가 급격히 느려지는 이유.

</details>

### 퀴즈 4. imap이 없다고 가정하고 `/a/b/c` 의 c 파일 데이터 한 블록을 덮어쓰면 무엇을 다시 써야 하나?
<details>
<summary>답 보기</summary>

c의 데이터 → c의 inode(위치 변경) → c의 inode 주소를 담은 b의 디렉터리 데이터 → b의 inode → a의 디렉터리 데이터 → a의 inode → 루트 디렉터리 데이터 → 루트 inode → (루트 위치를 담은) 고정 영역. **루트까지 전부** — recursive update problem. imap이 있으면 c의 데이터, c의 inode, imap 조각 3개면 끝.

</details>

이 판(v0.91) 원문에는 43장 Homework 문항이 없지만, `lfs.py` README 흐름대로:
