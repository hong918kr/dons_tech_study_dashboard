# Ch.04 프로세스 — 실행 중인 프로그램이라는 추상화

> 📖 원문: [04. The Abstraction: The Process](../book-md/C04_the_abstraction_the_process.md) · [PDF p.46](../Operating%20Systems%20-%20Three%20Easy%20Pieces.pdf#page=46) · ⏱️ 읽기 약 40분 · 🔗 선행: [Ch.02](2026-09-30_C02_intro.md)

## 0. 한눈에 보기

- **프로세스(process) = 실행 중인 프로그램.** 디스크 위의 프로그램은 죽은 바이트 덩어리일 뿐이고, OS가 그걸 메모리에 올리고 CPU에 태워서 살아 있는 프로세스로 만든다.
- 프로세스를 정의하는 건 그 **기계 상태(machine state)**: 주소 공간(code, data, heap, stack), 레지스터(PC, SP 포함), 열린 파일 목록.
- 프로세스는 **Running / Ready / Blocked** 세 상태(+ 생성 중, 좀비)를 오간다. OS는 이를 **프로세스 리스트**와 프로세스마다 하나씩인 **PCB(Process Control Block)** 로 추적한다.
- OS 설계 원칙 두 개: **시분할(time sharing)** 과 **정책/메커니즘 분리(separate policy and mechanism)**.
- 원문 CRUX: *"Although there are only a few physical CPUs available, how can the OS provide the illusion of a nearly-endless supply of said CPUs?"* — 물리 CPU는 몇 개뿐인데, OS는 어떻게 CPU가 거의 무한히 있는 것 같은 착시를 줄까?

## 1. 5분 복습표

| 용어 | 한 줄 뜻 | 예시 / 비유 |
|---|---|---|
| 프로세스 (process) | 실행 중인 프로그램 | 터미널에서 `./a.out` 하면 생기는 것 |
| 프로그램 (program) | 디스크 위의 실행 파일 (명령어 + 정적 데이터) | Mach-O, ELF 파일 |
| 기계 상태 (machine state) | 실행 중 프로그램이 읽고 쓰는 모든 것 | 메모리, 레지스터, 열린 파일 |
| 주소 공간 (address space) | 프로세스가 접근할 수 있는 메모리 | code / data / heap / stack |
| PC (program counter) | 다음에 실행할 명령어 주소 | x86 `rip`, arm64 `pc` |
| 스택 포인터 / 프레임 포인터 | 스택 꼭대기 / 현재 함수 프레임 | arm64 `sp`, `x29` |
| 시분할 (time sharing) | 자원을 시간으로 나눠 번갈아 쓰기 | CPU를 10 ms씩 돌아가며 |
| 공간 분할 (space sharing) | 자원을 공간으로 쪼개 나눠 주기 | 디스크 블록, 메모리 |
| 메커니즘 (mechanism) | "어떻게"에 답하는 저수준 장치 | 컨텍스트 스위치 |
| 정책 (policy) | "무엇을/어느 것을"에 답하는 알고리즘 | 스케줄링 정책 |
| Running / Ready / Blocked | 실행 중 / 실행 가능하지만 대기 / 이벤트 대기 | CPU 위 / 런큐 / 디스크 I/O 대기 |
| 스케줄됨 / 디스케줄됨 (scheduled / descheduled) | Ready→Running / Running→Ready | 스케줄러의 결정 |
| 좀비 (zombie) | 종료했지만 부모가 아직 거두지(wait) 않은 상태 | `ps` 의 `Z`, `<defunct>` |
| PCB (Process Control Block) | 프로세스 하나의 정보를 담는 커널 구조체 | xv6 `struct proc`, Linux `task_struct` |
| 레지스터 문맥 (register context) | 멈춘 프로세스의 레지스터 저장본 | xv6 `struct context` |

## 2. 프로세스라는 추상화 (4.0 ~ 4.1)

웹 브라우저, 메일, 게임, 음악 플레이어… 우리는 프로그램을 동시에 수십, 수백 개 돌리고 싶다. 그리고 "지금 CPU가 비어 있나?" 를 신경 쓰고 싶지 않다. 그냥 실행하면 돌아가야 한다.

OS는 이를 **CPU 가상화**로 해결한다. 프로세스 하나를 조금 돌리고, 멈추고, 다른 것을 돌리고… 이렇게 하면 물리 CPU 하나로 가상 CPU 여러 개가 있는 착시를 만든다. 이 기법이 **시분할(time sharing)** 이다. 대가는 성능이다. CPU를 나눠 쓰면 각자는 느려진다.

> **TIP — 시분할(그리고 공간 분할)을 써라**
> 시분할: 한 자원을 한 주체가 잠깐, 다음 주체가 잠깐 쓰는 식으로 나눈다(CPU, 네트워크 링크). 공간 분할(space sharing): 자원을 공간적으로 쪼개 나눠 준다. 디스크가 대표적이다. 한 블록이 파일에 할당되면 지울 때까지 다른 파일에 주지 않는다.

CPU 가상화를 잘하려면 두 층이 필요하다.

- **메커니즘(mechanism)**: 필요한 기능을 구현하는 저수준 방법/프로토콜. 예: **컨텍스트 스위치** — 한 CPU에서 프로그램 하나를 멈추고 다른 걸 시작하는 능력.
- **정책(policy)**: 그 위의 "지능". 어떤 결정을 내리는 알고리즘. 예: 실행 가능한 프로그램이 여럿일 때 **어느 것**을 돌릴지 정하는 **스케줄링 정책**. 과거 정보(최근 1분간 누가 많이 돌았나), 워크로드 지식, 성능 지표(대화형 응답성 vs 처리량)를 쓴다.

> **TIP — 정책과 메커니즘을 분리하라**
> 메커니즘은 **how** 질문에 답한다("컨텍스트 스위치를 어떻게 하나?"). 정책은 **which** 질문에 답한다("지금 어느 프로세스를 돌리나?"). 둘을 나누면 메커니즘을 다시 생각하지 않고도 정책만 바꿀 수 있다. 일반적인 모듈화 원칙이다.

### 프로세스를 이루는 것: 기계 상태

프로세스를 이해하려면 "이 프로그램이 실행 중에 읽거나 바꿀 수 있는 기계의 부분" 을 목록으로 만들면 된다.

1. **메모리 = 주소 공간(address space)**: 명령어도 메모리에 있고, 읽고 쓰는 데이터도 메모리에 있다.
2. **레지스터**: 많은 명령어가 레지스터를 읽고 쓴다. 특히 특별한 레지스터들:
   - **PC (program counter, 또는 IP instruction pointer)**: 지금 어느 명령어를 실행 중인지.
   - **스택 포인터(SP)와 프레임 포인터(FP)**: 함수 인자, 지역 변수, 리턴 주소가 있는 스택을 관리.
3. **I/O 정보**: 프로세스가 현재 열어 둔 파일 목록 등.

이 세 가지만 저장해 두면 프로세스를 멈췄다가 정확히 같은 지점에서 다시 시작할 수 있다. 이것이 [Ch.06](2026-09-30_C06_limited_direct_execution.md) 컨텍스트 스위치의 기본 아이디어다.

## 3. 프로세스 API — 어떤 OS든 있어야 하는 것 (4.2)

실제 UNIX API는 [Ch.05](2026-09-30_C05_process_api.md) 에서 보고, 여기서는 "무엇이 있어야 하나" 만.

| 기능 | 뜻 | UNIX / macOS 예 |
|---|---|---|
| Create | 새 프로세스 만들기 (셸에서 명령 입력, 아이콘 더블클릭) | `fork()` + `exec()`, `posix_spawn()` |
| Destroy | 강제로 없애기 (안 끝나는 프로세스 죽이기) | `kill(pid, SIGKILL)` |
| Wait | 프로세스가 끝날 때까지 기다리기 | `wait()`, `waitpid()` |
| Miscellaneous Control | 일시 정지(suspend)와 재개(resume) 등 | `SIGSTOP` / `SIGCONT` |
| Status | 얼마나 돌았나, 어떤 상태인가 | `ps`, `top`, `proc_pidinfo()` |

## 4. 프로세스 생성 — 프로그램이 프로세스가 되기까지 (4.3)

OS가 프로그램을 돌리려면 무엇을 해야 할까? 순서대로.

1. **코드와 정적 데이터를 메모리에 로드**: 프로그램은 디스크(또는 SSD)에 실행 파일 형식(Linux ELF, macOS Mach-O)으로 있다. 그 바이트를 읽어 프로세스 주소 공간에 놓는다.
   - 옛날/단순한 OS는 실행 전에 한꺼번에 **즉시(eagerly)** 로드했다.
   - 현대 OS는 **게으르게(lazily)** 로드한다. 실제로 그 코드/데이터가 필요해질 때(페이지 폴트) 그 조각만 읽는다. 이 장치는 [Ch.21](2026-09-30_C21_swapping_mechanisms.md) 의 페이징 · 스와핑에서.
2. **스택 할당**: C 프로그램의 지역 변수, 함수 인자, 리턴 주소용. OS는 스택을 `main()` 의 인자인 `argc` 와 `argv` 배열로 초기화한다.
3. **힙 할당**: `malloc()` 으로 요청하는 동적 데이터용. 처음엔 작고, 부족하면 라이브러리가 OS에 더 달라고 한다(`brk`/`mmap`).
4. **I/O 초기화**: UNIX에서는 프로세스마다 기본으로 **파일 디스크립터 3개**(stdin 0, stdout 1, stderr 2)가 열려 있다.
5. **진입점으로 점프**: `main()` (정확히는 C 런타임의 시작 코드)으로 CPU 제어를 넘긴다. 이 "넘기는" 특별한 방법이 [Ch.06](2026-09-30_C06_limited_direct_execution.md) 의 return-from-trap이다.

## 5. 프로세스 상태 (4.4)

단순화하면 프로세스는 세 상태 중 하나다.

- **Running(실행)**: CPU 위에서 명령어를 실행 중.
- **Ready(준비)**: 실행할 수 있지만 OS가 지금은 다른 걸 돌리기로 함.
- **Blocked(대기)**: 어떤 이벤트가 일어나기 전까지 실행할 수 없음. 대표 예: 디스크 I/O를 시작했으면 끝날 때까지 Blocked. 그동안 다른 프로세스가 CPU를 쓴다.

전이(transition):

- Ready → Running: **스케줄됨(scheduled)**. Running → Ready: **디스케줄됨(descheduled)**. 둘 다 OS 마음대로.
- Running → Blocked: I/O 시작 같은 대기 동작.
- Blocked → Ready: 이벤트 발생(I/O 완료). 바로 Running이 될 수도 있다(OS가 그렇게 정하면).

### 트레이스로 보기

**CPU만 쓰는 두 프로세스** (원문 Figure 4.3): Process0가 4틱 동안 Running, 그동안 Process1은 Ready. P0가 끝나면 P1이 4틱. 총 8틱, CPU는 내내 바쁘다.

**I/O가 끼는 경우** (원문 Figure 4.4):

```text
Time  Process0   Process1   Notes
  1   Running    Ready
  2   Running    Ready
  3   Running    Ready      Process0 initiates I/O
  4   Blocked    Running    Process0 is blocked,
  5   Blocked    Running      so Process1 runs
  6   Blocked    Running
  7   Ready      Running    I/O done
  8   Ready      Running    Process1 now done
  9   Running    –
 10   Running    –          Process0 now done
```

계산해 보자. CPU가 쉬는 틱이 있나? 1~3은 P0, 4~8은 P1, 9~10은 P0. **10틱 중 10틱 CPU 사용 = 100%.** 만약 OS가 P0의 I/O 동안 P1을 돌리지 않았다면: P0 3틱 실행 + I/O 대기 3틱(CPU 놂) + P0 나머지 2틱 + P1 5틱 = **13틱**, CPU 이용률은 10/13 ≈ **77%** 로 떨어진다.

여기서 OS가 내린 결정이 두 개 있다.

1. P0가 I/O를 하는 동안 P1을 돌렸다 → 자원 이용률이 올라감. 좋은 결정.
2. P0의 I/O가 7에서 끝났는데 P0로 바로 돌아가지 않고 P1을 계속 돌렸다 → 좋은 결정인지 불분명하다. 이런 결정을 하는 것이 **스케줄러**이고 [Ch.07](2026-09-30_C07_scheduling_intro.md) 부터 다룬다. 아래 §8 시뮬레이터에서 이 두 번째 결정을 바꾸면 총 시간이 31틱 → 21틱으로 줄어드는 예를 실제로 돌려 본다.

## 6. 자료구조 — 프로세스 리스트와 PCB (4.5)

OS도 프로그램이다. 그러니 상태를 추적할 자료구조가 있다.

- **프로세스 리스트(process list)**: 모든 프로세스(Ready인 것, 지금 Running인 것, Blocked인 것)를 추적. I/O가 끝나면 **올바른 프로세스를 깨워** Ready로 옮겨야 하므로 Blocked 프로세스도 추적해야 한다.
- **PCB(Process Control Block)**: 프로세스 하나에 대한 정보를 담은 C 구조체를 부르는 근사한 이름.

xv6(MIT의 교육용 UNIX)의 실제 구조체(원문 Figure 4.5):

```c
// the registers xv6 will save and restore
// to stop and subsequently restart a process
struct context {
   int eip;
   int esp;
   int ebx;
   int ecx;
   int edx;
   int esi;
   int edi;
   int ebp;
};
// the different states a process can be in
enum proc_state { UNUSED, EMBRYO, SLEEPING,
                  RUNNABLE, RUNNING, ZOMBIE };
// the information xv6 tracks about each process
// including its register context and state
struct proc {
   char *mem;                  // Start of process memory
   uint sz;                    // Size of process memory
   char *kstack;               // Bottom of kernel stack
                               // for this process
   enum proc_state state;      // Process state
   int pid;                    // Process ID
   struct proc *parent;        // Parent process
   void *chan;                 // If non-zero, sleeping on chan
   int killed;                 // If non-zero, have been killed
   struct file *ofile[NOFILE]; // Open files
   struct inode *cwd;          // Current directory
   struct context context;     // Switch here to run process
   struct trapframe *tf;       // Trap frame for the
                               // current interrupt
};
```

읽는 법:

- `context`: **레지스터 문맥(register context)**. 프로세스가 멈출 때 레지스터를 여기 저장하고, 다시 돌릴 때 여기서 복원한다. [Ch.06](2026-09-30_C06_limited_direct_execution.md) 의 `swtch()` 가 바로 이 구조체를 읽고 쓴다.
- `state`: 책의 세 상태 + 추가 상태. `RUNNABLE` = Ready, `SLEEPING` = Blocked, `EMBRYO` = 생성 중(초기 상태), `ZOMBIE` = 종료됐지만 아직 정리 안 됨.
- `kstack`: 프로세스마다 하나씩인 **커널 스택**. trap 때 하드웨어가 레지스터를 여기에 저장한다.
- `chan`: 무엇을 기다리며 자고 있는지(어떤 이벤트에서 깨워야 하는지).
- `ofile`, `cwd`: I/O 상태. 열린 파일, 현재 디렉터리.
- `tf`: 현재 인터럽트/trap의 **trap frame** (유저 레지스터 저장본).

### 좀비 상태가 왜 필요한가

프로세스가 끝났다고 바로 PCB를 지우면, 부모가 "자식이 성공했나(종료 코드 0)? 실패했나?" 를 알 길이 없다. 그래서 종료 후에도 PCB를 남겨 두는 마지막 상태가 **좀비(zombie)** 다. 부모가 `wait()` 를 부르면 종료 코드를 받아 가고, OS는 그제야 자료구조를 정리한다. 아래 §8의 실험에서 `ps` 의 `Z` 상태와 `wait` 후 사라지는 것을 실제로 본다.

> **ASIDE — 자료구조: 프로세스 리스트**
> 여러 프로그램을 동시에 돌리는 OS라면 반드시 이와 비슷한 구조가 있다. 실제 OS의 PCB는 훨씬 크다: Linux `task_struct` 는 수 KB, macOS(XNU)는 BSD 쪽 `struct proc` 과 Mach 쪽 `task`/`thread` 로 나뉘어 있다.

## 7. 정리 (4.6)

프로세스는 OS의 가장 기본적인 추상화이고, 단순히 "실행 중인 프로그램" 이다. 이제 남은 건 두 가지다: 프로세스를 구현하는 저수준 **메커니즘**([Ch.06](2026-09-30_C06_limited_direct_execution.md))과, 프로세스를 똑똑하게 스케줄링하는 상위 **정책**([Ch.07](2026-09-30_C07_scheduling_intro.md) ~ [Ch.10](2026-09-30_C10_multiprocessor_scheduling.md)).

### 8.1 프로세스의 기계 상태 들여다보기 — [code/C04_layout.c](../code/C04_layout.c)

```c
// C04_layout.c — 프로세스 = 실행 중인 프로그램. OS가 만들어 준 "기계 상태"를 들여다본다.
// code / static data / heap / stack 주소, argc/argv 위치, 기본으로 열려 있는 fd 0/1/2.
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int initialized_global = 42;   // static data (.data)
int zero_global;               // static data (.bss, 0으로 채워짐)

int main(int argc, char *argv[]) {
    int local = 7;                          // stack
    int *heap = malloc(16);                 // heap
    printf("pid %d, parent pid %d\n", (int)getpid(), (int)getppid());
    printf("code   main()             at %p\n", (void *)main);
    printf("data   initialized_global at %p (= %d)\n", (void *)&initialized_global, initialized_global);
    printf("bss    zero_global        at %p (= %d)\n", (void *)&zero_global, zero_global);
    printf("heap   malloc(16)         at %p\n", (void *)heap);
    printf("stack  local              at %p\n", (void *)&local);
    printf("stack  argv[]             at %p (argc=%d, argv[0]=\"%s\")\n", (void *)argv, argc, argv[0]);
    // OS가 미리 열어 준 표준 입출력 fd 0, 1, 2 확인
    for (int fd = 0; fd < 5; fd++) {
        int flags = fcntl(fd, F_GETFL);
        printf("fd %d: %s\n", fd, flags == -1 ? "closed" : "open");
    }
    free(heap);
    return 0;
}
```

실행 결과(`.work/bin/C04_layout a b`):

```text

data   initialized_global at 0x10481c000 (= 42)
```

해석:

- code(`0x104814548`) < data(`0x10481c000`) < heap(`0x105075930`) < stack(`0x16b5eabdc`). 원문 그림처럼 code/data가 아래, 스택이 훨씬 위에 있다. data가 `0x...c000` 처럼 딱 떨어지는 주소에서 시작하는 건 macOS arm64의 페이지 크기가 **16 KB**(`0x4000`)이고 세그먼트(`__TEXT`, `__DATA`)가 페이지 경계에 정렬되기 때문이다(`0x10481c000` 은 `0x4000` 의 배수).
- `argv` 배열은 `local` 보다 **높은 주소**에 있다. OS(정확히는 커널의 exec)가 스택 꼭대기에 `argc/argv/envp` 를 깔아 놓고, 그 아래로 `main` 의 프레임이 쌓였다. 원문 4.3절 "OS가 스택을 argc/argv로 초기화한다" 그대로다.
- `argc=3` (`a`, `b` 포함). fd 0, 1, 2는 열려 있고 3부터는 닫혀 있다. OS가 미리 열어 준 세 개다.
- 실행할 때마다 주소가 바뀐다(ASLR). 구조(순서)는 같다.

### 8.2 프로세스 상태를 `ps` 로 보기 — [code/C04_states.c](../code/C04_states.c)

```c
// C04_states.c — 프로세스 상태를 실제 ps 로 관찰한다.
//  child1: 무한 루프       → Running/Ready  (ps STAT 'R')
//  child2: sleep()        → Blocked        (ps STAT 'S')
//  child3: SIGSTOP 받음    → Stopped(suspend)(ps STAT 'T')
//  child4: 바로 exit()     → wait() 전까지 Zombie (ps STAT 'Z')
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

static pid_t spawn(int kind) {
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); exit(1); }
    if (pid == 0) {
        switch (kind) {
        case 1: for (volatile unsigned long i = 0;; i++) ; // CPU만 씀
        case 2: sleep(100); break;                          // 이벤트(타이머) 대기
        case 3: for (;;) pause();                           // 곧 SIGSTOP 받음
        case 4: _exit(7);                                   // 즉시 종료 → 좀비
        }
        _exit(0);
    }
    return pid;
}

int main(void) {
    pid_t p[5];
    for (int k = 1; k <= 4; k++) p[k] = spawn(k);
    kill(p[3], SIGSTOP);
    usleep(300 * 1000);  // 자식들이 자리 잡을 시간

    char cmd[256];
    snprintf(cmd, sizeof cmd, "ps -o pid,ppid,stat,command -p %d,%d,%d,%d,%d",
             (int)getpid(), (int)p[1], (int)p[2], (int)p[3], (int)p[4]);
    printf("parent=%d  spin=%d  sleep=%d  stopped=%d  zombie=%d\n",
           (int)getpid(), (int)p[1], (int)p[2], (int)p[3], (int)p[4]);
    fflush(stdout);
    system(cmd);

    // 좀비 수거: wait 하면 종료 코드(7)를 받아 오고 PCB가 사라진다
    int status;
    pid_t w = waitpid(p[4], &status, 0);
    printf("reaped %d, exit status = %d\n", (int)w, WEXITSTATUS(status));
    fflush(stdout);
    snprintf(cmd, sizeof cmd, "ps -o pid,stat -p %d || echo '(pid %d is gone)'", (int)p[4], (int)p[4]);
    system(cmd);

    // 정리: 나머지 자식 죽이고 수거
    for (int k = 1; k <= 3; k++) { kill(p[k], SIGKILL); waitpid(p[k], NULL, 0); }
    return 0;
}
```

실행 결과:

```text
parent=62415  spin=62416  sleep=62417  stopped=62418  zombie=62419
  PID  PPID STAT COMMAND
62415 62404 S    .work/bin/C04_states
62416 62415 R    .work/bin/C04_states
62417 62415 S    .work/bin/C04_states
62418 62415 T    .work/bin/C04_states
62419 62415 Z    <defunct>
reaped 62419, exit status = 7
  PID STAT
(pid 62419 is gone)
```

책의 상태와 `ps` STAT 글자의 대응:

| ps STAT | 뜻 | 책의 상태 |
|---|---|---|
| R | runnable (실행 중이거나 런큐에서 대기) | Running 또는 Ready (ps는 둘을 구분 안 함) |
| S | sleeping (이벤트 대기, 짧은 잠) | Blocked |
| T | stopped (SIGSTOP 등으로 정지) | "Miscellaneous Control"의 suspend |
| Z | zombie | 종료 후 부모가 wait 하기 전 |

- 부모(62415) 자신도 `S` 다. `system()` 안에서 `ps` 가 끝나길 **기다리는 중**(Blocked)이기 때문이다.
- 좀비는 `COMMAND` 가 `<defunct>` 로 나온다. 주소 공간은 이미 해제됐고 PCB(종료 코드)만 남아 있다는 뜻.
- `waitpid()` 로 종료 코드 **7** 을 받아 온 순간 PCB가 사라져 `ps` 에서도 안 보인다.

계산으로 확인: CPU 일은 총 21틱(P0의 io 발행 3 + io_done 3 = 6, P1~P3 15)으로 고정이다. `IMMEDIATE` 는 P0가 I/O를 끝내자마자 다음 I/O를 다시 걸어 두므로 **I/O 대기 15틱이 전부 다른 프로세스의 CPU 일과 겹친다** → 총 21틱, CPU 100%. `LATER` 는 P0가 P1~P3가 끝날 때까지 기다리다가, 마지막에 I/O 두 번(10틱)을 아무것도 겹치지 못하고 혼자 기다린다 → 21 + 10 = 31틱.

교훈: **I/O를 자주 하는 프로세스를 빨리 다시 돌려 주면 장치와 CPU를 동시에 바쁘게 만들 수 있다.** 이게 [Ch.08 MLFQ](2026-09-30_C08_mlfq.md) 가 대화형(I/O 많은) 작업에 높은 우선순위를 주는 이유 중 하나다.

## 9. 펌웨어 엔지니어의 눈으로

- **RTOS 태스크 = 프로세스(주소 공간 없는)**. FreeRTOS의 TCB(Task Control Block)는 xv6 `struct proc` 의 축소판이다: 저장된 스택 포인터(레지스터는 태스크 스택에 push), 상태(Running/Ready/Blocked/Suspended), 우선순위, 기다리는 이벤트 리스트. 다만 보통 **MMU 기반 주소 공간 분리가 없다**(MPU로 영역 보호 정도). SSD 컨트롤러 FW에서 "태스크" 라고 부르던 것이 정확히 이것이다.
- **Blocked → Ready 전이 = ISR이 태스크를 깨우는 것**. NAND 읽기 완료 인터럽트가 오면 ISR이 세마포어를 give → 그 세마포어를 기다리던(Blocked) 태스크가 Ready로. `chan` 필드(무엇을 기다리나)가 RTOS의 이벤트 그룹/큐 대기 리스트다.
- **§8.3의 `IO_RUN_IMMEDIATE` 교훈 = NVMe 큐 깊이(queue depth)**. 호스트가 I/O를 하나 끝내자마자 다음 I/O를 넣어 장치를 계속 바쁘게 유지하는 것과 같다. 컨트롤러 FW 입장에서도 다이(die)마다 명령을 끊김 없이 넣어 NAND 병렬성을 채우는 것이 처리량의 핵심이었다.
- **좀비 = 완료 큐(Completion Queue) 엔트리**. NVMe 명령이 끝나도 호스트가 CQ 엔트리를 소비(doorbell로 head 갱신)하기 전까지 슬롯이 회수되지 않는 것과 비슷하다: "결과를 누군가 받아 가야 자원이 풀린다".
- **AI 가속기 컨텍스트**: GPU/NPU 드라이버도 "컨텍스트"(채널, 커맨드 큐, 페이지 테이블 포인터, 저장된 엔진 상태)를 프로세스처럼 관리한다. 선점 시 엔진 상태를 메모리에 저장/복원하는 것이 `struct context` 의 가속기 버전이다.

## 10. 면접 질문

### Q1. 프로그램과 프로세스의 차이는?
<details>
<summary>답 보기</summary>

**프로그램**은 디스크 위의 정적인 실행 파일(코드 + 정적 데이터)이다. **프로세스**는 그 프로그램의 **실행 인스턴스**로, OS가 만든 **주소 공간**(code, data, heap, stack), **레지스터 상태**(PC, SP 등), **OS 자원**(열린 파일, PID, 부모, 권한, 상태)을 함께 가진다. 같은 프로그램으로 프로세스를 여러 개 만들 수 있고, 각자 독립된 상태를 갖는다.

</details>

### Q2. 프로세스 상태 전이를 그리고, 각 전이를 일으키는 사건을 말하라.
<details>
<summary>답 보기</summary>

**Ready → Running**: 스케줄러가 선택(dispatch). **Running → Ready**: 타이머 인터럽트로 선점되거나 yield. **Running → Blocked**: I/O 요청, 락/세마포어 대기, sleep. **Blocked → Ready**: I/O 완료 인터럽트, 이벤트 신호. 추가로 생성 시 **New(EMBRYO) → Ready**, 종료 시 **Running → Zombie → (부모 wait 후) 제거**. Blocked에서 Running으로 **바로** 가지 않는다는 점이 핵심: 깨어나면 먼저 Ready가 되고 스케줄러가 고른다.

</details>

### Q3. PCB에는 무엇이 들어 있나? 컨텍스트 스위치 때 무엇을 저장하나?
<details>
<summary>답 보기</summary>

PID, 상태, 부모 포인터, **저장된 레지스터 문맥**(PC, SP, callee-saved 레지스터), 커널 스택 포인터, 주소 공간 정보(페이지 테이블 루트, 예: arm64 TTBR0 값 / x86 CR3), 열린 파일 테이블, 현재 디렉터리, 스케줄링 정보(우선순위, 사용 시간), 시그널 정보, 대기 중인 이벤트 등. 컨텍스트 스위치 때는 **커널 레지스터 문맥**(xv6 `struct context`)을 PCB에 저장하고, 유저 레지스터는 trap 때 이미 **커널 스택의 trap frame**에 저장돼 있다. 주소 공간이 바뀌면 페이지 테이블 레지스터도 바꾼다.

</details>

### Q4. 좀비 프로세스와 고아(orphan) 프로세스는? 좀비가 쌓이면 무엇이 문제인가?
<details>
<summary>답 보기</summary>

**좀비**: 종료했지만 부모가 아직 `wait()` 로 종료 상태를 거두지 않은 프로세스. 메모리는 해제됐지만 **PID와 PCB(종료 코드)** 는 남는다. 쌓이면 **PID 고갈**, 프로세스 테이블 고갈로 새 프로세스를 못 만든다. 해결: 부모가 `waitpid()` 를 부르거나, `SIGCHLD` 핸들러에서 거두거나, `SIGCHLD` 를 `SIG_IGN` 으로 설정. **고아**: 부모가 먼저 죽은 프로세스. init/launchd(PID 1)나 서브리퍼(subreaper)에게 입양되고, 입양한 쪽이 나중에 거둔다.

</details>

### Q5. 정책과 메커니즘을 분리하라는 원칙을 예를 들어 설명하라.
<details>
<summary>답 보기</summary>

메커니즘은 **how**: 컨텍스트 스위치, 타이머 인터럽트, 페이지 테이블 갱신. 정책은 **which/when**: 다음에 어떤 프로세스를 돌릴지(FIFO, RR, MLFQ, CFS), 어떤 페이지를 쫓아낼지(LRU 근사). 분리하면 **메커니즘은 그대로 두고 정책만 교체**할 수 있다. 예: Linux의 스케줄링 클래스(CFS, RT, deadline)는 같은 `context_switch()` 를 쓴다. 펌웨어 예: NAND 명령 디스패치는 메커니즘, GC 대상 블록 선택(greedy vs cost-benefit)은 정책.

</details>

### 원문 숙제 중 꼭 해볼 것

- **문제 2 vs 3** (`-l 4:100,1:0` vs `-l 1:0,4:100`): 순서만 바꿔도 11 → 7틱. **I/O와 CPU 겹치기(overlap)** 의 가치를 확인하는 문제. (위 §8.3에서 실행)
- **문제 6 vs 7** (`IO_RUN_LATER` vs `IO_RUN_IMMEDIATE`): 31 → 21틱. **I/O 완료 후 스케줄링 정책** 하나가 이용률을 크게 바꾼다는 것을 확인하는 문제. (위 §8.3에서 실행)
- **문제 8** (`-s 1 -l 3:50,3:50` 등 무작위): 트레이스를 먼저 손으로 예측하고 `-c` 로 맞춰 본다. **상태 전이 규칙을 정확히 이해했는지** 확인하는 문제.
