# Ch.02 운영체제 입문 — 가상화 · 동시성 · 영속성, 세 조각의 지도

> 📖 원문: [02. Introduction to Operating Systems](../book-md/C02_introduction_to_operating_systems.md) · [PDF p.24](../Operating%20Systems%20-%20Three%20Easy%20Pieces.pdf#page=24) · ⏱️ 읽기 약 35분 · 🔗 선행: 없음 (책 전체의 지도)

## 0. 한눈에 보기

- 프로그램은 그냥 **명령어를 하나씩 fetch → decode → execute** 할 뿐이다. 그런데 그 뒤에서 "여러 프로그램이 동시에 도는 것처럼, 각자 메모리를 독차지한 것처럼, 장치를 쉽게 쓰는 것처럼" 보이게 만드는 소프트웨어가 있다. 그게 **운영체제(OS)** 다.
- OS의 핵심 기법은 **가상화(virtualization)**: 물리 자원(CPU, 메모리, 디스크)을 더 쓰기 쉽고 강력한 "가상" 형태로 바꿔 준다. 그래서 OS를 **가상 머신**, **표준 라이브러리**(시스템 콜 수백 개), **자원 관리자(resource manager)** 라고도 부른다.
- 책은 세 조각(Three Easy Pieces)으로 간다: **가상화**(CPU · 메모리), **동시성**(concurrency), **영속성**(persistence).
- 원문 CRUX: *"How does the operating system virtualize resources? … what mechanisms and policies are implemented by the OS to attain virtualization? How does the OS do so efficiently? What hardware support is needed?"* — OS는 자원을 **어떻게** 가상화하는가? 어떤 메커니즘과 정책을 쓰고, 어떻게 효율적으로 하며, 하드웨어는 무엇을 도와줘야 하는가?

## 1. 5분 복습표

| 용어 | 한 줄 뜻 | 예시 / 비유 |
|---|---|---|
| 폰 노이만 모델 (Von Neumann model) | 명령어도 데이터도 메모리에 있고, CPU가 하나씩 꺼내 실행 | fetch → decode → execute 반복 |
| 운영체제 (OS) | 프로그램 실행을 쉽고, 올바르고, 효율적으로 만드는 소프트웨어 덩어리 | macOS(XNU), Linux, Zephyr(RTOS) |
| 가상화 (virtualization) | 물리 자원을 쓰기 쉬운 가상 자원으로 바꿔 보여 주기 | CPU 1개 → 프로세스마다 "내 CPU" |
| 시스템 콜 (system call) | 앱이 OS 기능을 부르는 공식 입구 | `open()`, `write()`, `fork()` |
| 자원 관리자 (resource manager) | CPU · 메모리 · 디스크를 여러 프로그램에 나눠 주는 역할 | 누가 지금 CPU를 쓸지 결정 |
| 정책 (policy) | "어느 것을" 고를지 정하는 알고리즘 | 스케줄러가 다음에 돌릴 프로세스 선택 |
| 메커니즘 (mechanism) | "어떻게" 할지 구현하는 저수준 장치 | 컨텍스트 스위치 |
| 주소 공간 (address space) | 프로세스마다 보이는 사적인 가상 메모리 | 두 프로세스가 같은 주소에 다른 값 |
| PID | 프로세스 식별 번호 | `getpid()` |
| 스레드 (thread) | 같은 메모리 공간에서 도는 실행 흐름 | `pthread_create()` |
| 원자성 (atomicity) | "한 번에 전부, 아니면 전혀" 실행됨 | `counter++` 는 원자적이지 않다 |
| 영속성 (persistence) | 전원이 꺼져도 데이터가 남는 것 | 파일 시스템, SSD |
| 유저 모드 / 커널 모드 (user / kernel mode) | 하드웨어가 강제하는 권한 수준 | 유저 모드에서는 디스크 I/O 직접 불가 |
| trap / return-from-trap | 권한을 올리며 커널로 들어가기 / 내리며 돌아오기 | arm64 `svc`, `eret` |
| 멀티프로그래밍 (multiprogramming) | 여러 작업을 메모리에 올려 두고 번갈아 실행 | I/O 기다리는 동안 다른 작업 실행 |

## 2. 프로그램이 돌아갈 때 무슨 일이 생기나 (도입)

CPU 입장에서 프로그램 실행은 단순하다. 메모리에서 명령어를 꺼내고(fetch), 무슨 명령인지 해석하고(decode), 실행한다(execute). 끝나면 다음 명령어. 이게 초당 수십억 번 반복된다. 현대 CPU는 내부적으로 여러 명령을 동시에, 순서도 바꿔서(out-of-order) 실행하지만, 프로그램이 보는 모델은 "명령어가 하나씩 순서대로 실행된다" 이다.

그런데 이 단순한 그림만으로는 설명이 안 되는 일이 많다.

- CPU는 몇 개뿐인데 프로그램 수백 개가 **동시에** 도는 것처럼 보인다.
- 프로그램마다 메모리를 **혼자** 쓰는 것처럼 보인다.
- `write()` 한 줄이면 디스크(SSD)에 데이터가 들어간다. 컨트롤러 레지스터, DMA, 큐 같은 건 신경 쓰지 않는다.

이 착시와 편의를 만드는 소프트웨어가 OS다. OS가 쓰는 주된 무기가 **가상화**다. 물리 자원 하나를 받아서, 더 일반적이고 쓰기 쉬운 가상 자원으로 바꿔 준다.

OS를 부르는 세 가지 이름이 OS가 하는 일을 그대로 요약한다.

- **가상 머신(virtual machine)**: 물리 자원을 가상 자원으로 바꿔 주니까.
- **표준 라이브러리(standard library)**: 앱이 부를 수 있는 시스템 콜을 수백 개 제공하니까. 프로그램 실행, 메모리 할당, 파일 접근이 다 이 API를 거친다.
- **자원 관리자(resource manager)**: CPU · 메모리 · 디스크를 여러 프로그램이 나눠 쓰게 하니까. 효율, 공정성 등 목표에 맞춰 관리한다.

> **CRUX — 자원을 어떻게 가상화하나 (HOW TO VIRTUALIZE RESOURCES)**
> "왜" 가상화하는지는 뻔하다(쓰기 쉬우니까). 이 책의 질문은 **어떻게**다: 어떤 메커니즘과 정책을 쓰는가, 어떻게 효율적으로 하는가, 하드웨어 지원은 무엇이 필요한가.

## 3. CPU 가상화 (2.1)

책의 첫 프로그램 `cpu.c` 는 1초 동안 시간만 확인하며 돌다가(`Spin(1)`), 받은 문자열을 출력하고, 이를 영원히 반복한다. 혼자 돌리면 재미없다. `A A A A …`.

재미있는 건 네 개를 동시에 돌릴 때다. CPU가 하나뿐인 기계에서도 `A B D C A B D C …` 가 섞여 나온다. 네 프로그램이 **동시에 도는 것처럼** 보인다.

- 이 착시가 **CPU 가상화**다. CPU 하나(또는 몇 개)를 사실상 무한히 많은 가상 CPU처럼 보이게 한다.
- 실제로는 OS가 A를 조금 돌리고, 멈추고, B를 조금 돌리고… 를 아주 빠르게 반복한다(**시분할, time sharing**). 이걸 하는 저수준 장치(컨텍스트 스위치, 타이머 인터럽트)는 [Ch.06](2026-09-30_C06_limited_direct_execution.md) 에서 본다.
- 둘이 동시에 돌고 싶어 하면 누가 먼저? 이건 **정책(policy)** 의 문제다. 스케줄링 정책은 [Ch.07](2026-09-30_C07_scheduling_intro.md) 부터.

이 Mac(M2, 코어 8개)에서 직접 돌려 보면(§10 직접 해보기), 4개 정도는 코어가 남아서 진짜로 **병렬**로 돈다. 코어보다 많은 16개를 돌리면 각 프로세스가 벽시계 시간 2초 동안 실제로 받은 CPU 시간이 약 0.6초(약 30%)밖에 안 된다. 각자 "내 CPU"가 있다고 믿지만 실제로는 나눠 쓰고 있다는 증거다.

## 4. 메모리 가상화 (2.2)

물리 메모리 모델은 단순하다. 바이트 배열이다. 읽으려면 주소를 주고, 쓰려면 주소와 데이터를 준다. 명령어 자체도 메모리에 있으므로, 명령어를 가져올 때마다(fetch) 메모리에 접근한다.

책의 `mem.c` 는 `malloc()` 으로 int 하나를 받고, 그 주소를 찍고, 1초마다 값을 1씩 올린다. 두 개를 동시에 돌리면:

- 두 프로세스 모두 **같은 주소**(`00200000`)에 메모리를 받았다고 출력한다.
- 그런데 값은 **각자 따로** 증가한다.

같은 주소인데 다른 값. 각 프로세스가 **자기만의 가상 주소 공간(virtual address space)** 을 갖고, OS가 이것을 물리 메모리 어딘가에 매핑(mapping)하기 때문이다. 한 프로세스의 메모리 접근은 다른 프로세스(그리고 OS)의 주소 공간에 영향을 주지 않는다.

> **주의 — 주소 공간 무작위화(ASLR)**
> 책의 예제가 "같은 주소"를 보이려면 ASLR(address-space layout randomization)을 꺼야 한다. macOS arm64는 모든 실행 파일이 PIE라서 ASLR을 끌 수 없다. 그래서 이 노트의 실험은 `malloc` 후 `fork()` 로 부모/자식을 만들어 **같은 가상 주소, 다른 값** 을 보인다(fork는 주소 공간을 통째로 복사하므로 주소가 같다). 따로 두 번 실행하면 주소가 매번 바뀌는 것도 함께 확인한다.

이 장치(주소 변환, 페이지 테이블, TLB)는 [Ch.13](2026-09-30_C13_address_spaces.md) 부터 차근차근 나온다.

## 5. 동시성 (2.3)

**동시성(concurrency)** 은 "한 프로그램 안에서 여러 일을 동시에 할 때 생기는 문제들"을 부르는 말이다. 이 문제는 OS 안에서 먼저 나타났다. OS 자체가 프로세스 A를 돌리다가 B를 돌리고, 인터럽트를 처리하고… 여러 일을 저글링하기 때문이다. 지금은 멀티스레드 앱도 똑같은 문제를 겪는다.

책의 `threads.c`: 스레드 두 개가 공유 변수 `counter` 를 각각 `loops` 번 증가시킨다. 기대값은 `2 × loops`.

- `loops = 1000` → 2000. 맞다.
- `loops = 100000` → 143012, 137298… 틀리고, 매번 다르다.

이유: `counter++` 가 **명령어 세 개**이기 때문이다. 이 Mac에서 컴파일한 코드를 디스어셈블하면 정확히 이렇게 나온다(§10의 실제 출력).

```text
ldr  w8, [x9, #0x4]    ; ① 메모리 → 레지스터 (load)
add  w8, w8, #0x1      ; ② 레지스터 +1
str  w8, [x9, #0x4]    ; ③ 레지스터 → 메모리 (store)
```

세 명령어가 **원자적(atomic)** 으로 실행되지 않으므로, 두 스레드의 명령어가 섞이면 한쪽의 증가가 사라진다(**lost update**). 숫자로 따라가 보자. `counter = 50` 에서 시작.

```text
시간  스레드 1                     스레드 2                     메모리 counter
 t1   ldr w8 ← 50                                                 50
 t2   add w8 = 51                                                 50
 t3                                ldr w8 ← 50   (아직 50!)        50
 t4                                add w8 = 51                    50
 t5   str 51 → counter                                            51
 t6                                str 51 → counter               51   ← 52가 되어야 함
```

두 번 증가했는데 결과는 51. 한 번이 증발했다. 반복 횟수가 클수록 이런 충돌이 일어날 기회가 많아져 결과가 크게 틀어진다.

## 6. 영속성 (2.4)

DRAM은 **휘발성(volatile)** 이다. 전원이 나가거나 시스템이 죽으면 데이터가 사라진다. 그래서 데이터를 **영속적(persistent)** 으로 저장할 하드웨어(HDD, SSD 같은 I/O 장치)와 소프트웨어가 필요하다. 디스크를 관리하는 OS 소프트웨어를 **파일 시스템(file system)** 이라 한다.

CPU · 메모리와 다른 점이 하나 있다. **OS는 앱마다 사적인 가상 디스크를 만들어 주지 않는다.** 파일은 원래 공유하라고 있는 것이다. 에디터가 만든 `main.c` 를 컴파일러가 읽고, 컴파일러가 만든 실행 파일을 셸이 실행한다.

책의 `io.c` 는 시스템 콜 세 번으로 `/tmp/file` 에 "hello world" 를 쓴다: `open()` → `write()` → `close()`. 이 호출들은 파일 시스템으로 가서 처리된다. 그 뒤에서 파일 시스템이 하는 일은 꽤 지저분하다.

- 새 데이터를 디스크 **어디에** 둘지 정하고, 그걸 추적하는 자료구조(inode, 비트맵, 디렉터리)를 갱신한다.
- 장치에 I/O 요청을 보낸다. 장치 드라이버(device driver)는 장치의 저수준 인터페이스를 정확히 알아야 한다.
- 성능을 위해 쓰기를 바로 내리지 않고 잠시 모아 두었다가 **묶어서(batch)** 쓴다. 그래서 `write()` 가 리턴해도 데이터는 아직 메모리(page cache)에 있을 수 있다. 확실히 내리려면 `fsync()`.
- 쓰는 도중 죽어도 복구 가능하도록 **저널링(journaling)** 이나 **copy-on-write** 같은 쓰기 순서 프로토콜을 쓴다.

> **CRUX — 데이터를 어떻게 영속적으로 저장하나 (HOW TO STORE DATA PERSISTENTLY)**
> 올바르게 하려면 어떤 기법이? 빠르게 하려면 어떤 메커니즘과 정책이? 하드웨어 · 소프트웨어 고장 앞에서 신뢰성은 어떻게? → 책의 세 번째 조각([Ch.36](2026-09-30_C36_io_devices.md) ~, 특히 [Ch.42 저널링](2026-09-30_C42_crash_consistency_journaling.md), [부록 Flash SSD](2026-09-30_C0I_flash_ssd.md)).

## 7. 설계 목표 (2.5)

OS를 만든다면 어떤 목표로 트레이드오프를 정할까? 좋은 트레이드오프를 찾는 것이 시스템을 만드는 핵심이다.

- **추상화(abstraction)**: 시스템을 편하고 쉽게 쓰게 한다. 트랜지스터 → 게이트 → 프로세서 → 어셈블리 → C → 큰 프로그램, 모든 층이 아래층을 몰라도 되게 해 준다. OS의 대표 추상화는 프로세스, 주소 공간, 파일.
- **고성능(high performance)** = **오버헤드 최소화**: 가상화는 공짜가 아니다. 시간(명령어가 더 든다)과 공간(메모리, 디스크)을 쓴다. 둘 다 최소화하되, 완벽은 못 한다.
- **보호(protection)** 와 **격리(isolation)**: 한 앱의 악의 또는 실수가 다른 앱이나 OS를 망가뜨리면 안 된다. 격리가 OS의 핵심 원칙이다.
- **신뢰성(reliability)**: OS가 죽으면 그 위의 모든 것이 죽는다. 수백만 줄짜리 OS를 안 죽게 만드는 건 어렵다.
- 그 밖에 **에너지 효율**, **보안**(보호의 확장), **이동성**(작은 기기). 쓰임새에 따라 목표 비중이 달라진다. 데이터센터 서버 OS와 웨어러블 RTOS는 다르게 만들어진다.

### 새 예제: 멀티프로그래밍이 CPU 이용률을 얼마나 올리나

역사 절의 "I/O 기다리는 동안 다른 작업을 돌리면 CPU를 더 잘 쓴다" 를 숫자로 확인해 보자. 각 작업이 시간의 80%를 I/O 대기로 보낸다고 하자(CPU 사용 20%). 작업들이 서로 독립이라고 단순화하면, CPU가 노는 경우는 **모든 작업이 동시에 I/O 대기 중일 때**뿐이다.

- 작업 1개: CPU 이용률 = 1 − 0.8 = 0.20 → **20%**
- 작업 2개: 1 − 0.8² = 1 − 0.64 = **36%**
- 작업 4개: 1 − 0.8⁴ = 1 − 0.4096 = **59%**
- 작업 10개: 1 − 0.8¹⁰ = 1 − 0.107 = **89%**

메모리에 작업을 여러 개 올려 둘 수 있다면 CPU 이용률이 크게 오른다. 대신 이제 **메모리 보호**(서로의 메모리를 건드리지 않게)와 **동시성**(인터럽트가 아무 때나 와도 OS가 올바르게) 문제가 생긴다. 이 둘이 이 책 나머지의 큰 줄기다. [Ch.04](2026-09-30_C04_process.md) 의 `process-run.py` 시뮬레이터로 이 효과를 직접 볼 수 있다.

## 8. 짧은 역사 (2.6)

좋은 아이디어는 시간이 지나며 쌓였다. 흐름만 잡으면 된다.

1. **초기 OS = 그냥 라이브러리**. 메인프레임에서 한 번에 한 프로그램. 실행 순서는 사람(operator)이 정했다. **일괄 처리(batch processing)**: 작업들을 모아 한꺼번에 돌림. 컴퓨터가 너무 비싸서 사람이 앞에 앉아 대화식으로 쓰는 건 낭비였다.
2. **보호의 등장 = 시스템 콜**. OS 코드는 장치를 제어하므로 특별하게 다뤄야 한다. 아무 앱이나 디스크 아무 데나 읽으면 프라이버시가 끝난다. 그래서 파일 시스템을 라이브러리로 두면 안 된다. Atlas 컴퓨터가 **시스템 콜** 을 도입했다: 특별한 하드웨어 명령어 쌍과 하드웨어 상태로 OS 진입을 **공식적이고 통제된** 과정으로 만들었다.
   - 프로시저 호출과 시스템 콜의 핵심 차이: 시스템 콜은 OS로 점프하면서 **동시에 하드웨어 권한 수준을 올린다**.
   - 앱은 **유저 모드(user mode)** 에서 돈다. 하드웨어가 할 수 있는 일을 제한한다(디스크 I/O 시작, 임의 물리 메모리 접근, 패킷 전송 불가).
   - **trap** 명령어 → 하드웨어가 OS가 미리 정해 둔 **trap handler** 로 제어를 넘기고 **커널 모드(kernel mode)** 로 올린다 → 일을 마치면 **return-from-trap** 으로 유저 모드로 내리며 원래 자리로 돌아간다. 이게 [Ch.06](2026-09-30_C06_limited_direct_execution.md) 의 주인공이다.
3. **멀티프로그래밍 시대**. 미니컴퓨터(DEC PDP 계열)로 값이 싸지고 개발자가 늘었다. OS가 여러 작업을 메모리에 올려 두고 빠르게 전환했다. I/O가 느리니 기다리는 동안 다른 작업을 돌리면 이득(위 §7 계산). 이로부터 **메모리 보호**와 **인터럽트가 있는 상태에서의 동시성** 문제가 중요해졌다. 그리고 **UNIX** (Ken Thompson, Dennis Ritchie, Bell Labs): Multics 등의 좋은 아이디어를 더 단순하게.
4. **현대(PC 시대)**. Apple II, IBM PC. 처음엔 오히려 후퇴했다. DOS는 메모리 보호가 없었고, Mac OS 9 이하는 **협력형(cooperative) 스케줄링**이라 무한 루프 하나가 전체 시스템을 멈춰 재부팅해야 했다. 이후 미니컴퓨터의 교훈이 돌아왔다: Mac OS X는 UNIX가 핵심, Windows NT, 그리고 폰도 Linux(Android) 같은 70년대 미니컴퓨터 스타일 OS를 돌린다.

> **ASIDE — UNIX의 중요성**
> 작고 강력한 프로그램을 **파이프**로 이어 더 큰 작업을 만든다: `grep foo file.txt | wc -l`. C 컴파일러를 함께 제공했고, 소스를 거의 무료로 나눠 줬고, 작고 읽기 쉬운 C 커널이라 사람들이 고쳐 볼 수 있었다. Berkeley의 BSD(가상 메모리, 파일 시스템, 네트워킹), 이후 SunOS, AIX, HP-UX, IRIX 등 변종이 생겼다.

> **ASIDE — 그리고 Linux**
> Linus Torvalds가 UNIX의 원리를 빌려 코드 없이 새로 만들었다. 인터넷 기업(Google, Amazon, Facebook)과 Android가 Linux 위에 섰다. Steve Jobs는 UNIX 기반 NeXTStep을 Apple로 가져가 macOS의 뿌리가 됐다(지금 이 노트의 코드를 돌린 Darwin/XNU가 그 후손이다).

## 9. 이 책이 다루지 않는 것 (2.7 정리)

네트워킹, 그래픽 장치, 깊은 보안은 다루지 않는다. 다루는 것은 CPU · 메모리 가상화, 동시성, 장치와 파일 시스템을 통한 영속성이다. 이 장은 지도일 뿐이니 세부를 다 이해하려 하지 말고 "어느 장에서 무엇을 배우는지"만 잡으면 된다.

### 10.1 CPU 가상화 — [code/C02_cpu.c](../code/C02_cpu.c)

```c
// C02_cpu.c — OSTEP Figure 2.1 (cpu.c) 변형: 1초 돌다가 문자열 출력, N번 반복 후 종료.
// 사용법: ./C02_cpu <문자열> <반복횟수>
#include <stdio.h>
#include <stdlib.h>
#include <sys/time.h>
#include <sys/resource.h>
#include <unistd.h>

static double now(void) {
    struct timeval t;
    gettimeofday(&t, NULL);
    return (double)t.tv_sec + (double)t.tv_usec / 1e6;
}

// Spin: 시스템 콜 gettimeofday()를 계속 부르며 'howlong' 초 동안 CPU를 태운다.
static void spin(double howlong) {
    double t = now();
    while (now() - t < howlong)
        ; // busy-wait
}

int main(int argc, char *argv[]) {
    if (argc != 3) {
        fprintf(stderr, "usage: %s <string> <loops>\n", argv[0]);
        return 1;
    }
    int loops = atoi(argv[2]);
    for (int i = 0; i < loops; i++) {
        spin(0.5);
        printf("%s (pid %d) #%d\n", argv[1], (int)getpid(), i);
        fflush(stdout);
    }
    // 벽시계 시간 vs 실제로 CPU를 받은 시간 비교 (가상 CPU 착시의 증거)
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    double cpu = ru.ru_utime.tv_sec + ru.ru_utime.tv_usec / 1e6 +
                 ru.ru_stime.tv_sec + ru.ru_stime.tv_usec / 1e6;
    printf("%s done: wall %.2f s, cpu %.2f s (%.0f%%)\n", argv[1], loops * 0.5, cpu,
           100.0 * cpu / (loops * 0.5));
    return 0;
}
```

(주석의 "시스템 콜 gettimeofday()" 는 정확히는 macOS에서 **commpage** 라는 커널이 매핑해 준 읽기 전용 페이지를 읽어 커널 진입 없이 끝난다. [Ch.06](2026-09-30_C06_limited_direct_execution.md) 측정에서 약 10 ns로 나온다.)

### 10.2 메모리 가상화 — [code/C02_mem.c](../code/C02_mem.c)

```c
// C02_mem.c — OSTEP Figure 2.3 (mem.c) 변형.
// malloc 한 뒤 fork() 해서 부모/자식이 "같은 가상 주소"를 각자 증가시킨다.
// 같은 주소인데 값이 따로 논다 = 각 프로세스가 자기만의 가상 주소 공간을 가진다.
#include <assert.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int main(void) {
    int *p = malloc(sizeof(int));                       // a1
    assert(p != NULL);
    *p = 0;                                             // a3
    pid_t rc = fork();
    assert(rc >= 0);
    int step = (rc == 0) ? 1 : 100;                     // 자식은 +1, 부모는 +100
    printf("(%d) %s: address of p = %p\n", (int)getpid(),
           rc == 0 ? "child " : "parent", (void *)p);   // a2
    for (int i = 0; i < 3; i++) {
        usleep(100 * 1000);
        *p = *p + step;
        printf("(%d) %s: *p = %d\n", (int)getpid(), rc == 0 ? "child " : "parent", *p); // a4
        fflush(stdout);
    }
    if (rc > 0)
        wait(NULL);
    free(p);
    return 0;
}
```

```text
(61530) parent: *p = 300
```

같은 주소 `0x104ac9970` 에서 자식은 1, 2, 3, 부모는 100, 200, 300. 서로의 쓰기가 전혀 보이지 않는다. 가상 주소는 같지만 **다른 물리 페이지**로 매핑되어 있다(fork 직후엔 같은 물리 페이지를 공유하다가 쓰는 순간 복사하는 copy-on-write. [Ch.05](2026-09-30_C05_process_api.md) 와 [Ch.23](2026-09-30_C23_vax_vms.md) 참고).

프로그램을 따로 두 번 실행하면(ASLR 때문에) 주소부터 다르다:

```text
(61539) child : address of p = 0x100f7d970
(61545) child : address of p = 0x104b2d970
```

### 10.3 동시성 — [code/C02_threads.c](../code/C02_threads.c)

```c
// C02_threads.c — OSTEP Figure 2.5 (threads.c). 두 스레드가 공유 counter를 loops번씩 증가.
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>

static volatile int counter = 0;
static int loops;

static void *worker(void *arg) {
    (void)arg;
    for (int i = 0; i < loops; i++)
        counter++;              // load → add → store: 원자적이지 않다
    return NULL;
}

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "usage: %s <loops>\n", argv[0]);
        return 1;
    }
    loops = atoi(argv[1]);
    pthread_t p1, p2;
    printf("Initial value : %d\n", counter);
    pthread_create(&p1, NULL, worker, NULL);
    pthread_create(&p2, NULL, worker, NULL);
    pthread_join(p1, NULL);
    pthread_join(p2, NULL);
    printf("Final value   : %d (expected %d)\n", counter, 2 * loops);
    return 0;
}
```

실행 결과:

```text
$ ./C02_threads 1000
Initial value : 0
Final value   : 2000 (expected 2000)
$ ./C02_threads 100000
Initial value : 0
Final value   : 100000 (expected 200000)
$ ./C02_threads 100000
Initial value : 0
Final value   : 200000 (expected 200000)
$ ./C02_threads 1000000
Initial value : 0
Final value   : 1418128 (expected 2000000)
```

`100000` 을 다섯 번 더 돌린 결과(`Final value` 줄만):

```text
Final value   : 107765 (expected 200000)
Final value   : 103385 (expected 200000)
Final value   : 128125 (expected 200000)
Final value   : 154262 (expected 200000)
Final value   : 136990 (expected 200000)
```

`1000` 은 맞는다. 스레드 하나가 1000번을 도는 시간이 스레드 생성 시간보다 짧아서 두 스레드가 거의 겹치지 않기 때문이다. `100000` 은 매번 다르고, 가끔은 정답(200000)도 나온다. 이게 동시성 버그가 무서운 이유다: **재현이 안 된다.**

`objdump -d --no-show-raw-insn .work/bin/C02_threads` 로 본 `worker` 의 루프 몸통(실제 출력 일부):

```text

100000654:     	add	w8, w8, #0x1
100000658:     	str	w8, [x9, #0x4]
```

`_loops` 바로 옆(+4)이 `counter` 다. `ldr` / `add` / `str` 세 개로 쪼개져 있다.

### 10.4 영속성 — [code/C02_io.c](../code/C02_io.c)

```c
// C02_io.c — OSTEP Figure 2.6 (io.c) + fsync. open/write/fsync/close 4개의 시스템 콜.
#include <assert.h>
#include <fcntl.h>
#include <stdio.h>
#include <sys/stat.h>
#include <unistd.h>

int main(void) {
    const char *path = "/tmp/ostep_c02_file";
    int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC, S_IRWXU);
    assert(fd > -1);
    ssize_t rc = write(fd, "hello world\n", 12);
    assert(rc == 12);
    // write()가 돌아와도 데이터는 아직 커널 버퍼(page cache)에 있을 수 있다.
    // fsync()를 불러야 "디스크(SSD)까지 갔다"를 요청한다.
    assert(fsync(fd) == 0);
    close(fd);

    struct stat st;
    assert(stat(path, &st) == 0);
    printf("fd=%d, wrote %zd bytes, file size on fs = %lld bytes\n", fd, rc, (long long)st.st_size);
    return 0;
}
```

실행 결과(그리고 `cat /tmp/ostep_c02_file`):

```text
fd=3, wrote 12 bytes, file size on fs = 12 bytes
hello world
```

`fd=3` 인 이유: 0, 1, 2는 이미 stdin/stdout/stderr 로 열려 있고, UNIX는 **가장 낮은 빈 번호**를 준다([Ch.04](2026-09-30_C04_process.md), [Ch.05](2026-09-30_C05_process_api.md) 의 리다이렉션이 이 규칙을 이용한다). 책 원문 코드는 `write(fd, "hello world\n", 13)` 으로 NUL 바이트까지 13바이트를 쓰는데, 여기서는 12로 고쳤다.

> 참고: macOS에서 `fsync()` 는 데이터를 드라이브까지 보내지만, 드라이브 **내부 쓰기 캐시**까지 비우라고 강제하지는 않는다. 그건 `fcntl(fd, F_FULLFSYNC)` 이다. SSD 펌웨어 쪽에서 보면 FLUSH 커맨드를 보내느냐 마느냐의 차이다.

## 11. 펌웨어 엔지니어의 눈으로

- **"OS = 자원 관리자 + 가상화"는 SSD 컨트롤러 FW가 하던 일 그대로다.** FTL은 NAND의 물리 블록/페이지를 호스트에게 **논리 블록 주소(LBA)** 라는 가상 공간으로 보여 준다. 덮어쓰기 불가, 지우기 단위 큼, 배드 블록 같은 지저분함을 숨긴다. 매핑 테이블(L2P)은 OS의 페이지 테이블, garbage collection과 wear leveling은 "정책"이다. OS의 메모리 가상화와 구조가 같다.
- **메커니즘/정책 분리**: NVMe 큐 처리, DMA 디스크립터 세팅이 메커니즘이고, 어떤 큐를 먼저 서비스할지(arbitration: round-robin, weighted), GC를 언제 돌릴지가 정책이다. 면접에서 "이 설계에서 무엇이 mechanism이고 무엇이 policy냐" 를 나눠 말하면 깔끔하다.
- **lost update는 레지스터 read-modify-write에서도 똑같이 생긴다.** 펌웨어에서 ISR과 메인 루프가 같은 레지스터의 다른 비트를 `reg |= bit` 로 건드리면 `counter++` 와 같은 load/modify/store 경쟁이 난다. 해결도 같다: 인터럽트 잠깐 끄기, 원자적 set/clear 레지스터(W1S/W1C), 락. 멀티코어 SoC(예: 코프로세서 여럿)라면 arm64 `ldxr/stxr` 또는 LSE 원자 명령.
- **`write()` 가 리턴해도 영속적이지 않다.** 호스트 page cache → 드라이브 DRAM 쓰기 캐시 → NAND. 전원 손실 복구(PLP, 캐패시터로 남은 데이터 flush)를 설계해 본 사람은 `fsync` vs `F_FULLFSYNC` vs NVMe FLUSH / FUA 의 차이가 어디서 나오는지 바로 보인다.
- **AI 가속기 관점**: GPU/NPU 드라이버도 "디바이스 메모리를 프로세스마다 가상화"(GPU 페이지 테이블, IOMMU/Apple DART), "커맨드 큐를 여러 컨텍스트가 나눠 쓰기"(시분할 · 우선순위 정책)를 한다. 이 책의 CPU · 메모리 가상화 아이디어가 그대로 가속기로 옮겨 간다.

## 12. 면접 질문

### Q1. 운영체제가 하는 일을 한 문장으로, 그리고 세 가지로 나눠 설명하라.
<details>
<summary>답 보기</summary>

한 문장: OS는 **하드웨어 자원을 가상화하고 관리해서**, 여러 프로그램이 **안전하고 효율적으로, 쉽게** 실행되게 하는 소프트웨어다.

세 가지: (1) **가상화** — CPU를 시분할로 나눠 "프로세스마다 CPU", 메모리를 주소 변환으로 나눠 "프로세스마다 주소 공간". (2) **동시성** — 여러 실행 흐름이 공유 데이터를 건드릴 때 올바르게 동작하게 하는 락 · 조건 변수 등 제공. (3) **영속성** — 파일 시스템으로 데이터를 장치에 안전하게 저장, 크래시 후에도 일관성 유지. 이 모든 것을 **보호(protection)/격리(isolation)** 를 지키며 **오버헤드 최소**로.

</details>

### Q2. 시스템 콜과 일반 함수 호출의 차이는?
<details>
<summary>답 보기</summary>

일반 함수 호출은 같은 권한 수준에서 **임의의 주소로** 점프한다. 시스템 콜은 **trap 명령어**(x86 `syscall`, arm64 `svc`)로 커널에 진입하면서 **하드웨어 권한 수준을 동시에 올린다**(유저 모드 → 커널 모드). 점프할 곳도 호출자가 고를 수 없고 OS가 부팅 때 등록해 둔 **trap handler**(벡터 테이블)로만 간다. 돌아올 때는 **return-from-trap**(arm64 `eret`)으로 권한을 내리며 복귀한다. 비용도 다르다: 이 Mac(M2)에서 함수 호출 약 2 ns, `getppid()` 시스템 콜 약 93 ns(부하가 클 때는 300 ns대까지), 약 40배 이상 차이.

</details>

### Q3. `counter++` 를 두 스레드가 10만 번씩 하면 왜 20만이 안 나오나? 어떻게 고치나?
<details>
<summary>답 보기</summary>

`counter++` 는 **load → add → store** 세 명령어이고 원자적이지 않다. 두 스레드가 같은 옛 값을 load하면 한쪽의 증가가 덮어써진다(**lost update**, data race). 결과는 실행마다 다르다(비결정적).

고치는 법: (1) **mutex** 로 임계 구역을 감싼다. (2) 원자적 증가 명령: C11 `atomic_fetch_add`, arm64 LSE `ldadd` 또는 `ldxr/stxr` 루프. (3) 아예 공유를 피한다: 스레드별 로컬 카운터를 두고 마지막에 합친다(가장 빠름, per-CPU counter와 같은 아이디어).

</details>

### Q4. 왜 `write()` 가 성공했는데 전원이 나가면 데이터가 없어질 수 있나?
<details>
<summary>답 보기</summary>

`write()` 는 보통 데이터를 **커널의 page cache** 에 복사하고 바로 리턴한다. 파일 시스템은 성능을 위해 쓰기를 모아(batch) 나중에 내린다. 그 사이 전원이 나가면 사라진다. **`fsync()`** 를 불러야 커널이 데이터와 메타데이터를 장치로 보낸다. 장치 안에도 DRAM 쓰기 캐시가 있으므로 진짜 내구성을 원하면 FLUSH/FUA(macOS는 `F_FULLFSYNC`)까지 필요하다. 그리고 쓰기 도중 크래시 시 파일 시스템 일관성은 **저널링이나 copy-on-write** 로 지킨다.

</details>

### Q5. 협력형(cooperative) 멀티태스킹의 문제는? 현대 OS는 어떻게 해결했나?
<details>
<summary>답 보기</summary>

협력형은 프로세스가 스스로 CPU를 양보(yield)하거나 시스템 콜을 할 때만 OS가 제어권을 얻는다. 그래서 **무한 루프 하나가 시스템 전체를 멈출 수 있다**(Mac OS 9 이하, 재부팅 필요). 현대 OS는 **타이머 인터럽트**를 써서 일정 시간마다 하드웨어가 강제로 커널로 진입시킨다(**선점형, preemptive**). 그러면 OS가 언제든 제어권을 되찾아 다른 프로세스로 전환할 수 있다. 자세한 건 [Ch.06](2026-09-30_C06_limited_direct_execution.md).

</details>

### 퀴즈

1. CPU 가상화, 메모리 가상화가 각각 만들어 내는 "착시"를 한 줄씩 말해 보라.
2. OS가 디스크에 대해서는 프로세스마다 사적인 가상 디스크를 만들어 주지 **않는** 이유는?

<details>
<summary>정답</summary>

3. 1 − 0.5³ = 1 − 0.125 = **87.5%**.
4. 정책: 다음에 어떤 프로세스를 돌릴지 고르는 스케줄링 알고리즘, 어떤 페이지를 쫓아낼지(교체 정책). 메커니즘: 컨텍스트 스위치, 주소 변환 하드웨어, trap.

</details>
