0. 한눈에 보기#

  • 락(lock)은 "동시에 들어오지 마"만 해결한다. 그런데 스레드는 자주 "어떤 조건이 참이 될 때까지 기다려야" 한다 (자식이 끝났나? 버퍼에 데이터가 있나?). 돌면서 확인하는 spin 방식은 CPU를 태운다.
  • 조건 변수(condition variable, CV) 는 "조건이 맞지 않을 때 스스로 들어가 잠드는 명시적 대기 큐"다. 연산은 둘뿐: wait(cv, mutex) 와 signal(cv).
  • wait() 는 락을 풀고 잠드는 것을 원자적으로 하고, 깨어나면 락을 다시 잡고 리턴한다. 이 원자성이 lost wakeup 을 막는다.
  • 실전 규칙 세 개: ① 상태 변수(done, count)를 꼭 둔다 ② 항상 while 로 재확인 (Mesa 의미론) ③ 기다리는 조건이 다르면 CV를 나눈다 (생산자용 empty, 소비자용 fill). 누구를 깨워야 할지 모르면 broadcast (covering condition).

THE CRUX: HOW TO WAIT FOR A CONDITION — "In multi-threaded programs, it is often useful for a thread to wait for some condition to become true before proceeding. The simple approach, of just spinning until the condition becomes true, is grossly inefficient and wastes CPU cycles, and in some cases, can be incorrect. Thus, how should a thread wait for a condition?"

→ 멀티스레드 프로그램에서 스레드는 흔히 어떤 조건이 참이 될 때까지 기다렸다가 진행해야 한다. 조건이 참이 될 때까지 그냥 도는(spin) 방법은 CPU를 엄청 낭비하고, 경우에 따라서는 틀리기까지 한다. 그렇다면 스레드는 조건을 어떻게 기다려야 하는가?

가장 단순한 방법은 공유 변수 done 을 두고 부모가 while (done == 0) ; 로 도는 것 (Fig 30.2). 동작은 하지만 부모가 CPU를 통째로 태운다. 단일 CPU라면 자식이 돌 기회까지 뺏는다. 원하는 건 "조건이 참이 될 때까지 부모를 재우는 것" 이다.

이 생각은 Dijkstra의 "private semaphore" [D68]에서 시작했고, Hoare가 모니터(monitor) 연구에서 "condition variable"이라는 이름을 붙였다 [H74] (→ 부록 D 모니터).

3. 정의와 루틴 (30.1)#

POSIX 인터페이스:

wait() 가 뮤텍스를 인자로 받는다는 게 핵심이다. 호출할 때 뮤텍스를 쥐고 있어야 하고, wait() 의 책임은:

  1. 뮤텍스를 풀고 + 호출자를 재운다 — 이 두 개를 원자적으로(atomically).
  2. 누군가 signal 해서 깨면, 리턴하기 전에 뮤텍스를 다시 잡는다.

3.1 올바른 join (Fig 30.3)#

두 가지 경우를 따라가 보자.

  • 경우 1 — 부모가 먼저 thr_join(): 락 잡음 → done==0 → wait() (락 풀고 잠듦) → 자식이 돌아서 "child" 출력 → thr_exit() 가 락 잡고 done=1, signal → 부모가 락을 다시 잡고 wait() 에서 리턴 → while 재확인 done==1 → 탈출 → "parent: end".
  • 경우 2 — 자식이 먼저 끝남: 자식이 done=1, signal (자는 사람이 없어 아무 일도 없음) → 부모가 thr_join() 에서 done==1 을 보고 아예 안 잔다.

경우 2가 done 의 존재 이유다. CV 자체는 기억(memory)이 없다. signal 은 "지금 자고 있는 사람"에게만 전달된다.

3.2 틀린 버전 1 — 상태 변수가 없다#

자식이 먼저 돌면 signal 이 허공으로 사라지고, 부모는 나중에 wait() 해서 영원히 잔다. (아래 7.1에서 실제로 재현.)

3.3 틀린 버전 2 — 락 없이 signal/wait#

부모가 done==0 을 확인한 직후, wait 하기 직전에 인터럽트 → 자식이 done=1 + signal (아무도 안 잠) → 부모가 돌아와 잠듦 → 영원히. 확인(check)과 잠들기(sleep) 사이의 틈을 락이 메워 줘야 한다. 그래서 POSIX wait() 는 아예 뮤텍스를 인자로 받는다.

TIP — ALWAYS HOLD THE LOCK WHILE SIGNALING: signal 할 때 락을 쥐는 건 엄밀히 항상 필요하진 않지만 가장 단순하고 안전하다. wait 할 때 락을 쥐는 건 팁이 아니라 의무다 (wait 는 락이 잡혀 있다고 가정하고, 풀고, 다시 잡는다). 일반화: signal 이든 wait 이든 락을 쥐고 하라.

4. 생산자/소비자(bounded buffer) 문제 (30.2)#

Dijkstra가 처음 제기한 문제 [D72]이고, 이 문제 때문에 일반화된 세마포어가 발명됐다 (Ch.31). 현실 예:

  • 멀티스레드 웹 서버: 생산자가 HTTP 요청을 작업 큐에 넣고, 워커(소비자)가 꺼내 처리.
  • 유닉스 파이프 grep foo file.txt | wc -l: grep(생산자) → 커널 안의 bounded buffer → wc(소비자).

규칙은 뻔하다: count==0 일 때만 put, count==1 일 때만 get. 어기면 assert 가 터진다.

4.3 Mesa 의미론 vs Hoare 의미론#

왜 이런 일이 생기나? signal 은 스레드를 "깨우기만" 한다. 깨어난 스레드는 Ready 큐로 갈 뿐이고, 실제로 돌 때까지 세상은 바뀔 수 있다. signal 은 "상태가 바뀌었다"는 힌트(hint) 일 뿐이다. 이걸 Mesa 의미론이라 부른다 (Lampson & Redell이 Mesa 언어로 처음 구현 [LR80]). 반대로 Hoare 의미론은 signal 받은 스레드가 즉시 실행되므로 조건이 참임이 보장되지만 구현이 어렵다. 사실상 모든 실제 시스템은 Mesa 다.

4.4 시도 2: CV 1개 + while (Fig 30.8) — 여전히 틀림#

if 를 while 로 바꾸면 첫 번째 버그는 사라진다. Tc1 이 깨어나면 락을 쥔 채 즉시 재확인(c2)하고, 비었으면 다시 잔다.

TIP — USE WHILE (NOT IF) FOR CONDITIONS: while 은 항상 맞고, if 는 signal 의미론에 따라 맞을 수도 있다. while 은 spurious wakeup(signal 1번에 2명이 깨는 등 구현 세부로 생기는 헛깨움)도 같이 처리한다. 그냥 항상 while 을 쓰고 행복해져라.

그런데 CV 가 하나뿐이라는 두 번째 버그가 남는다 (Fig 30.9):

Tc1 이 값을 꺼낸 뒤 signal 을 하는데, 같은 CV에 Tc2(소비자)와 Tp(생산자)가 함께 자고 있다. 버퍼를 비웠으니 당연히 Tp 를 깨워야 하지만, signal 은 아무나 하나를 깨운다. Tc2 를 깨우면 Tc2 는 재확인 → 비었음 → 다시 잠. Tc1 도 잠. Tp 는 아무도 안 깨워 줌. 셋 다 잠든다. (데드락처럼 보이지만 원인은 "엉뚱한 사람을 깨운 것".) 아래 7.4에서 OSTEP 숙제 코드로 이 상태를 실제로 재현했다.

4.5 정답: CV 2개 + while (Fig 30.10)#

깨우는 방향을 정해 주면 된다. 생산자는 empty 에서 기다리고 fill 을 signal, 소비자는 fill 에서 기다리고 empty 를 signal. 이제 소비자가 소비자를 깨우는 일은 구조적으로 불가능하다.

칸이 여러 개면 생산자가 여러 개 연달아 넣고 나서야 잠들므로 문맥 교환이 줄고, 생산자/소비자가 여럿이면 동시에 진행할 여지가 커진다.

손으로 따라가 보기 (새 예제) — MAX=3, 생산자 1, 소비자 1. 생산자가 먼저 쭉 돈다고 하자.

5. Covering Condition (30.3)#

Lampson & Redell의 Pilot 논문 [LR80] 예제 — 멀티스레드 메모리 할당기 (Fig 30.13):

시나리오: 빈 힙에서 Ta 가 allocate(100), Tb 가 allocate(10) 으로 둘 다 잠듦. Tc 가 free(50). signal 이 Ta 를 깨우면 Ta 는 50<100 이라 다시 잠들고, 정작 만족 가능한 Tb 는 계속 잔다. 깨우는 쪽은 각 대기자가 얼마를 원하는지 모른다.

해법: signal → broadcast. 전부 깨우고, 각자 while 로 자기 조건을 재확인하게 한다. 이런 조건을 covering condition(깨워야 할 모든 경우를 보수적으로 "덮는" 조건)이라 부른다. 대가는 불필요하게 깬 스레드들의 재확인 비용 (thundering herd).

주의: "signal 을 broadcast 로 바꿨더니 고쳐졌다"인데 그럴 이유가 없어 보인다면, 그건 버그를 덮은 것일 가능성이 높다 (예: 4.4의 CV 1개 문제는 broadcast 로도 "고쳐지지만" 정답은 CV를 나누는 것). 할당기처럼 대기 조건이 스레드마다 다를 때만 broadcast 가 가장 간단한 정답이다.

6. 요약 (30.4)#

  • 락 다음으로 중요한 동기화 도구가 CV. 프로그램 상태가 원하는 상태가 아닐 때 스레드를 재운다.
  • 쓰는 법은 공식처럼 외워 두자: lock → while (!조건) wait → 상태 변경 → signal → unlock.
  • 생산자/소비자: CV 2개 + while. 대기 조건이 제각각이면: broadcast (covering condition).

7.1 join: 상태 변수의 존재 이유 (code/C30_join_cv.c)#

[1] 부모가 먼저 기다리는 경우, [2] 자식이 먼저 끝나는 경우(Fig 30.3), [3] 상태 변수 없이 자식이 먼저 signal 하는 경우(3.2의 틀린 버전)를 돌린다. 틀린 버전은 영원히 멈추므로 데모에서는 1초 pthread_cond_timedwait 로 "잠든 채 깨지 못했음"만 감지한다.

해석: [2]에서 부모는 done==1 을 보고 아예 wait() 를 부르지 않는다. [3]에서는 그 "기억"이 없어서 signal 이 증발했다.

7.2 진짜로 동작하는 bounded buffer (code/C30_bounded_buffer.c)#

Fig 30.12 를 그대로 옮겨서 생산자 2, 소비자 3, MAX=4, 40만 개 를 흘린다. 모든 값이 1..400000 으로 서로 달라서 개수와 합(=N(N+1)/2) 으로 유실/중복이 없음을 검증한다. 또 "깨어났는데 조건이 여전히 거짓이라 다시 잠든 횟수"를 세서 Mesa 의미론을 눈으로 확인한다. 인자 broadcast 를 주면 signal 대신 broadcast.

해석:

  • 40만 개가 정확히 한 번씩 소비됐다 (합 80,000,200,000 = 400000×400001/2). CV 2개 + while 은 맞다.
  • signal 모드에서도 소비자가 깨어났는데 버퍼가 비어 있어서 다시 잔 횟수가 58,223번이다. signal 은 한 명만 깨우는데도! 깨어난 소비자가 락을 다시 잡기 전에, 그때 막 c1 에 도착한(잠든 적 없는) 다른 소비자가 먼저 락을 잡고 값을 가져간 경우다 — 바로 Fig 30.7 의 "Tc2 sneaks in" 이다. if 였다면 이 5.8만 번이 전부 assert 실패였다. Mesa 의미론은 이론이 아니라 매 초 수만 번 일어나는 일이다.
  • broadcast 는 재확인 실패가 조금 늘었지만, 대기자가 CV당 많아야 2~3명이라 차이가 작다. 같은 프로그램을 3번씩 더 돌리면 elapsed 가 signal 0.95~1.45s, broadcast 0.89~1.14s 로 둘 다 흔들려서, 이 규모에선 성능 차이는 노이즈 수준이다. broadcast 의 비용은 대기자가 수십~수백 명일 때 드러난다.

7.3 covering condition (code/C30_covering_condition.c)#

5장의 할당기를 그대로 만든다. Ta(100) 대기 → 20ms 후 Tb(10) 대기 → 50ms 에 Tc 가 free(50). 영원히 자는 걸 보여 주기 위해 대기는 1초 타임아웃.

해석: signal 은 먼저 잠든 Ta 를 깨웠고(이 실행에서는 FIFO처럼 동작), Ta 는 다시 잠들고, 50바이트가 있는데도 Tb 는 1초 내내 굶었다. broadcast 에서는 Tb 가 54ms 에 바로 성공. Ta 가 끝까지 못 받는 건 정상이다 — 힙에 40바이트뿐이니 다음 free 를 기다려야 한다.

7.4 OSTEP 숙제 threads-cv — 틀린 버전들을 실제로 깨뜨리기#

숙제 코드는 C 이고 -P/-C "sleep string" 으로 각 지점(p0..p6, c0..c6)에서 몇 초 잘지 지정해 스케줄을 조종할 수 있다 (-P 1,2 = 생산자가 p0 에서 1초, p1 에서 2초). 원래 make 로 빌드하지만, 원본 폴더를 더럽히지 않으려고 바이너리를 .work/bin/hw/ 에 뽑았다 ((int) arg 캐스트 때문에 파일당 경고 4개가 나오는데, 숙제 원본 코드의 경고다).

(a) 정답 버전, 생산자1·소비자1·버퍼2 — NF 는 찬 칸 수, u/f 는 use/fill 포인터, * 는 둘이 같은 칸:

소비자가 c2(비었음) → 잠 → 생산자 p4/p5 가 채우고 signal → 소비자 c3(wait 에서 깸) → c4(get) 를 반복한다. 마지막엔 main 이 EOS(end-of-stream)를 넣어 소비자를 끝낸다.

(b) CV 1개 + while, 생산자1·소비자2·버퍼1 → 셋 다 잠듦 (Fig 30.9 재현). 아무 sleep 도 안 줬는데 10번 중 4번 멈췄다 (3초 알람으로 강제 종료, exit 142 = SIGALRM). 같은 조건에서 main-two-cvs-while 은 10번 중 0번.

멈춘 실행의 -v 트레이스 (pty 로 받아서 버퍼링 없이 저장, 끝부분이 멈춘 지점):

뒤에서부터 읽자. P0 는 버퍼가 차서 p2 → Cond_wait 로 잠듦. C1 이 깨어나(c3) 값 1 을 꺼내고(c4) c5 에서 signal — 같은 CV 에 P0 와 C0 가 자고 있었는데 C0(소비자)가 깨어남(c3). C0 는 재확인(c2) → 비었음 → 다시 잠. C1 도 c1, c2 → 비었음 → 잠. P0, C0, C1 셋 다 잠들고 끝 — 교과서 Fig 30.9 와 똑같은 그림이다.

(c) CV 2개 + if → 빈 버퍼에서 get (Fig 30.7 재현). 생산자를 p0 에서 1초, p1(락을 쥔 채)에서 2초 재우고, C1 을 c0 에서 2초 재운다. 의도: C0 가 먼저 잠듦 → 생산자가 락을 쥐고 있는 동안 C1 이 락 대기 줄에 섬 → 생산자가 put + signal(C0) → 락을 풀면 C1 이 먼저 들어가 값을 가져감 → C0 는 if 를 이미 지나서 재확인 없이 get.

C0 가 c2 에서 잠들고, 생산자가 채우고 signal, 그런데 C1 이 먼저 c1 → c4 로 가져감. 그 뒤 C0 가 c3(깨어남) → 곧장 do_get() → error: tried to get an empty buffer. 다만 macOS 뮤텍스가 대기 순서를 엄격히 보장하지 않아서 이 스케줄도 매번 깨지지는 않는다 (처음 5회 중 1회 실패, 이어서 10회는 모두 통과). "테스트가 통과했다"가 "맞다"는 뜻이 아니라는 좋은 예다. 같은 스케줄의 main-two-cvs-while 은 C0 가 깨어나 재확인하므로 오류가 날 수 없다.

8. 펌웨어 엔지니어의 눈으로#

  • NVMe SQ/CQ = bounded buffer 그 자체. 호스트가 생산자(SQ tail 증가 + doorbell write = signal(fill)), 컨트롤러 FW 가 소비자(SQ head 증가). CQ 는 방향이 반대. 링이 "찼는지"는 보통 count 대신 한 칸 비워 두기((tail+1)%N == head 이면 full)로 판정한다 — 생산자와 소비자가 각자 자기 포인터만 쓰므로 락 없이도 SPSC 링이 성립한다. 책의 count 버전은 MPMC 를 위해 락으로 묶은 것.
  • 베어메탈의 lost wakeup 은 "플래그 확인 후 WFI" 사이의 틈이다. if (!flag) __WFI(); 는 확인 직후 IRQ 가 와서 flag 를 세우면 다음 IRQ 까지 잠든다. 정답은 __disable_irq(); while (!flag) { __WFI(); /* IRQ 펜딩이면 깸 */ __enable_irq(); __disable_irq(); } 패턴 — Cortex-M 의 WFI 는 PRIMASK 로 마스킹돼 있어도 펜딩 인터럽트로 깨므로, "확인 + 잠들기" 가 원자적이 된다. pthread_cond_wait 가 뮤텍스를 받는 이유와 정확히 같은 구조.
  • ISR 은 wait 할 수 없다, signal 만 한다. RTOS 에서 ISR → 태스크 알림은 xSemaphoreGiveFromISR / k_sem_give / task notification 으로 하고, 태스크 쪽은 상태(완료 카운트, CQ 엔트리의 phase bit)를 while 로 재확인한다. 리눅스 커널의 wait_event(wq, cond) 매크로가 바로 "while (!cond) sleep" 을 내장한 것.
  • AI 가속기 드라이버의 fence 대기 = covering condition. 여러 스레드가 서로 다른 fence 번호(seqno)를 기다리고, 인터럽트 핸들러는 "완료된 seqno 가 N 까지 올라갔다"만 안다. 그래서 대기 큐 전체를 깨우고(wake_up_all), 각자 completed_seqno >= my_seqno 를 재확인한다 — 5장의 bytesLeft >= size 와 같은 모양. 대기자가 많아 thundering herd 가 문제면 seqno 별 대기 리스트로 쪼갠다 (= CV 를 나누는 것).
  • SSD FTL 의 GC ↔ 호스트 쓰기: free block 풀이 바닥나면 쓰기 경로가 "free block >= 필요량" 을 기다리고, GC 가 블록을 회수할 때 깨운다. 요청 크기가 제각각이면 할당기 예제처럼 broadcast + 재확인, 또는 가장 작은 요청부터 깨우는 정책이 필요하다.

9. 면접 질문#

Q1. pthread_cond_wait() 는 왜 뮤텍스를 인자로 받나?#

답 보기

조건 확인과 잠들기 사이의 틈(race window) 을 없애기 위해서다. 사용자가 unlock(); sleep(); 을 따로 하면, 그 사이에 다른 스레드가 상태를 바꾸고 signal 해 버려서 lost wakeup 이 생긴다. wait() 는 "뮤텍스 해제 + 대기 큐 진입"을 원자적으로 하고, 깨어나면 뮤텍스를 다시 획득한 뒤 리턴한다. 그래서 리턴 직후 while 조건 재확인을 락 보호 아래에서 할 수 있다. 커널 구현으로는 대기 큐 등록을 먼저 하고 나서 락을 푸는 순서로 틈을 막는다 (리눅스 prepare_to_wait → 확인 → schedule()).

Q2. CV 를 기다릴 때 왜 if 가 아니라 while 인가?#

답 보기

Mesa 의미론 때문이다. signal 은 깨운 스레드를 Ready 로 옮길 뿐이고, 그 스레드가 실제로 락을 다시 잡을 때까지 다른 스레드가 끼어들어 상태를 바꿀 수 있다 (생산자/소비자에서 다른 소비자가 값을 먼저 가져가는 경우). 또 POSIX 는 spurious wakeup(signal 없이 깨거나 한 번에 여러 명이 깸)을 허용한다. 그래서 깨어나면 조건을 반드시 재확인해야 한다. 실측: 정답 bounded buffer(생산 2·소비 3·버퍼 4)에서도 "깨어났는데 비어 있음"이 40만 건 중 약 5.8만 번 일어났다. 재확인 비용은 작고, 안 하면 정확성이 깨진다.

Q3. 생산자 여럿·소비자 여럿인 bounded buffer 를 mutex + CV 로 구현해 보라. CV 는 몇 개가 필요한가?#

답 보기

뮤텍스 1개 + CV 2개(empty, fill) + 상태 count, fill_ptr, use_ptr. 생산자: lock; while (count==MAX) wait(empty); put; signal(fill); unlock. 소비자: lock; while (count==0) wait(fill); get; signal(empty); unlock. CV 가 하나면 소비자의 signal 이 다른 소비자를 깨울 수 있어 모두가 잠드는 상황이 생긴다 (생산자는 아무도 안 깨워 줌). CV 를 나누면 "생산자는 소비자만, 소비자는 생산자만" 깨우게 구조적으로 보장된다. broadcast 로도 동작은 하지만 그건 근본 원인을 덮는 것이다.

Q4. signal 과 broadcast 는 언제 각각 쓰나? broadcast 의 비용은?#

답 보기

모든 대기자가 같은 조건을 기다리고 깨어난 한 명이 그 조건을 "소비"한다면 signal (예: 버퍼 한 칸). 대기자들의 조건이 제각각이라 깨우는 쪽이 누가 진행 가능한지 모르면 broadcast — covering condition (예: 크기가 다른 메모리 할당 요청, 서로 다른 fence seqno). 또 상태 변화가 여러 대기자를 동시에 진행 가능하게 하면(예: 배리어 해제, shutdown 플래그) broadcast. 비용은 thundering herd: N 명이 깨서 락을 두고 경쟁하고 대부분 다시 잠든다 → 문맥 교환·캐시라인 핑퐁. 대기자가 많으면 조건별로 CV/대기 리스트를 쪼개는 게 낫다.

Q5. signal 은 unlock 전에 해야 하나, 후에 해야 하나?#

답 보기

책의 권고는 락을 쥔 채 signal — 가장 단순하고 항상 맞다. 3.3 처럼 락 없이 상태를 바꾸고 signal 하면 lost wakeup 이 생긴다. 상태 변경 자체는 반드시 락 안에서 해야 하고, signal 만 unlock 뒤로 옮기는 건 정확성 면에서 대체로 괜찮다. 성능 면에서 락 안 signal 은 "깨어난 스레드가 바로 락에서 다시 막히는" 왕복이 생길 수 있는데, 많은 구현(glibc, 커널)이 wait morphing 등으로 이걸 줄인다. 면접 답: "기본은 락 안에서. 측정해서 문제가 보이면 상태 변경은 락 안, signal 은 unlock 직후로 옮기는 걸 검토."

Q6. Hoare 의미론과 Mesa 의미론의 차이는? 왜 실제 시스템은 Mesa 인가?#

답 보기

Hoare: signal 하는 순간 락과 CPU 가 즉시 대기자에게 넘어가므로, 대기자는 조건이 참인 상태에서 깨어난다 → if 로 충분. 대신 signal 하는 쪽이 강제로 양보해야 하고(추가 문맥 교환), 스케줄러와 강하게 엮여 구현이 어렵다. Mesa: signal 은 "상태가 바뀌었을 수 있다"는 힌트. 대기자는 그냥 Ready 가 되고 나중에 락 경쟁을 한다 → while 필수. 구현이 단순하고, signal 하는 쪽이 계속 달릴 수 있어 효율적이며, spurious wakeup·timeout·취소 같은 현실적 요구와 잘 맞는다. 그래서 pthread, Java, 리눅스 커널 모두 Mesa.

10. 자가 점검 & 숙제#

퀴즈 1. 상태 변수 done 을 빼면 어떤 실행 순서에서 문제가 생기나?#

정답

자식이 부모보다 먼저 thr_exit() 를 실행하는 순서. 자식의 signal 은 자는 스레드가 없어서 사라지고, 부모는 나중에 wait() 해서 영원히 잔다 (7.1 [3] 실측).

퀴즈 2. CV 1개 + while 버전이 망가지려면 최소 몇 개의 스레드가 필요한가? 각각 무엇인가?#

정답

3개: 생산자 1 + 소비자 2 (버퍼 1칸). 소비자 하나가 꺼낸 뒤 signal 이 생산자 대신 다른 소비자를 깨워야 하므로 같은 CV 에서 소비자와 생산자가 동시에 자고 있어야 한다. (생산자 2 + 소비자 1 로도 대칭적으로 가능.)

퀴즈 3. MAX=3 링 버퍼에서 put 을 5번, get 을 3번 하면 fill_ptr, use_ptr, count 는?#

정답

예를 들어 put 3 → get 2 → put 2 → get 1 순서라면 (count 가 0..3 을 벗어나지 않는 순서), fill_ptr = 5 % 3 = 2, use_ptr = 3 % 3 = 0, count = 5 − 3 = 2. 포인터는 순서와 무관하게 "누적 횟수 mod MAX" 다.

퀴즈 4. 다음 중 broadcast 가 "버그 은폐"가 아니라 정답인 경우는? (a) CV 1개 생산자/소비자 (b) 크기가 다른 메모리 할당 대기 (c) 스레드 N 개가 모두 도착할 때까지 기다리는 배리어#

정답

(b)와 (c). (b)는 깨우는 쪽이 누가 진행 가능한지 몰라서(covering condition), (c)는 한 사건으로 모든 대기자가 진행 가능해져서. (a)는 CV 를 둘로 나누는 게 정답이다.

숙제 (OSTEP threads-cv, 원문 v0.91 에는 문항이 없어 숙제 README 기준)#

  • ./main-two-cvs-while -p 1 -c 3 -m 1 -l 100 과 -m 10 으로 소비자별 소비량(Consumer consumption)이 어떻게 달라지는지 보기 → 버퍼 크기와 공정성/동시성의 관계 확인.
  • main-two-cvs-while-extra-unlock 은 do_fill() / do_get() 를 락 밖에서 부른다. -p 2 -c 2 -m 4 등으로 돌려 ensure 오류가 나는 스케줄을 찾기 → put/get 자체도 임계 구역임을 확인.
  • 7.4 (c)의 sleep string 을 바꿔서 main-two-cvs-if 를 더 확실하게 깨뜨리는 스케줄을 찾아보기 (힌트: "깨어난 소비자가 락을 다시 잡기 전" 에 다른 소비자를 들여보내야 한다) → Mesa 의미론의 틈을 조종하는 연습.
