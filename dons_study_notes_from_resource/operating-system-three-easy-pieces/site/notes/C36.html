0. 한눈에 보기#

CRUX: HOW TO INTEGRATE I/O INTO SYSTEMS — "How should I/O be integrated into systems? What are the general mechanisms? How can we make them efficient?" (I/O를 시스템에 어떻게 녹여 넣을까? 일반적인 메커니즘은 무엇이고, 어떻게 효율적으로 만들까?)

  • 장치는 인터페이스(레지스터 몇 개) 와 내부(마이크로컨트롤러 + 펌웨어 + 메모리) 두 부분으로 나뉜다. OS는 status/command/data 레지스터를 읽고 써서 장치를 부린다.
  • 가장 단순한 방법(폴링 + PIO)은 CPU를 두 번 낭비한다: 기다리느라(polling), 데이터를 손으로 옮기느라(PIO). 해법은 각각 인터럽트 와 DMA 다.
  • 하지만 인터럽트가 항상 이기지는 않는다. 빠른 장치에서는 폴링이 지연이 더 짧고, 폭주하는 장치에서는 인터럽트가 livelock 을 만든다 → hybrid, coalescing.
  • 레지스터 접근은 전용 명령(in/out) 또는 memory-mapped I/O 로 한다. 장치별 차이는 디바이스 드라이버 가 감싸서 나머지 OS를 장치 중립적으로 만든다(대가: 장치 고유 기능/에러 정보의 손실).

2. 시스템 구조 (36.1)#

책의 그림 36.1은 CPU–메모리가 메모리 버스로, 그래픽 같은 고성능 장치가 범용 I/O 버스(PCI) 로, 디스크·마우스 같은 느린 장치가 주변 버스(SCSI/SATA/USB) 로 붙는 계층 구조다.

왜 계층으로 나누나? 책의 답은 두 단어: 물리와 비용.

  • 빠른 버스일수록 짧아야 한다(신호 무결성, 스큐). 그래서 메모리 버스에는 꽂을 자리가 거의 없다.
  • 고성능 버스는 설계·제조 비용이 비싸다. 느린 장치까지 거기에 둘 이유가 없다.
  • 반대로 느린 버스에는 많은 장치 를 매달 수 있다.

오늘날 구조로 옮기면 이렇게 된다. 기본 생각은 그대로이고 이름만 바뀌었다.

현대 시스템에서 하나 더 생긴 것은 IOMMU(Intel VT-d, ARM SMMU, Apple DART)다. 장치가 DMA 로 메모리를 직접 건드리기 때문에, 장치가 보는 주소(IOVA)를 물리 주소로 번역하고 권한을 검사하는 MMU 가 장치 쪽에도 필요해졌다. OSTEP 은 여기까지 다루지 않지만 DMA 를 이해하면 바로 다음 질문이 이것이다.

3. 표준 장치와 표준 프로토콜 (36.2–36.3)#

3.1 장치 = 인터페이스 + 내부#

책의 "canonical device"(그림 36.2)는 두 층이다.

  • 인터페이스: 시스템에 보이는 레지스터 3개 — status(지금 상태), command(무엇을 할지), data(주고받을 데이터).
  • 내부: 마이크로컨트롤러(CPU), 메모리(DRAM/SRAM), 장치 전용 칩. 책은 "현대 RAID 컨트롤러는 수십만 줄의 펌웨어 를 가진다"고 적는다. SSD 컨트롤러도 정확히 이 구조다(멀티코어 Cortex-R/ARC + DRAM + NAND 채널 엔진 + ECC 엔진).

이 구분이 중요한 이유: OS 입장에서 장치는 레지스터의 프로토콜 일 뿐이고, 그 뒤에서 무슨 일이 일어나는지는 펌웨어가 숨긴다. FTL 이 바로 그 "숨겨진 내부"의 대표 예다(부록 I).

3.2 표준 프로토콜#

네 단계가 단순하고 잘 돌아간다. 그런데 CPU 가 두 군데서 낭비된다.

  1. (1)(4)의 polling: 느린 장치(디스크 수 ms)를 기다리는 동안 CPU 는 같은 레지스터만 읽는다.
  2. (2)의 PIO: 4KB 블록이면 4바이트씩 1024번 레지스터에 쓴다. 단순 복사에 CPU 를 쓴다.

이 두 낭비가 각각 36.4(인터럽트)와 36.5(DMA)의 주제다.

4. 인터럽트로 CPU 낭비 줄이기 (36.4)#

CRUX — HOW TO AVOID THE COSTS OF POLLING: "How can the OS check device status without frequent polling, and thus lower the CPU overhead required to manage the device?"

4.1 아이디어: 재우고, 장치가 깨우게 하자#

OS 는 요청을 보낸 프로세스를 BLOCKED 로 재우고 다른 프로세스로 문맥 교환한다. 장치는 끝나면 하드웨어 인터럽트 를 올리고, CPU 는 미리 정해진 ISR(interrupt service routine) 로 점프한다. ISR 은 결과(데이터·에러 코드)를 거두고 기다리던 프로세스를 깨운다.

책의 타임라인(1 = 프로세스1, 2 = 프로세스2, p = polling):

가운데 5칸에서 CPU 와 디스크가 동시에 일한다. 이것이 계산과 I/O 의 중첩(overlap) 이고, Ch.07 스케줄링에서 본 "I/O 하는 동안 다른 작업 돌리기"의 하드웨어 기반이다.

4.2 인터럽트가 항상 좋은 건 아니다#

TIP — INTERRUPTS NOT ALWAYS BETTER THAN PIO: 인터럽트는 느린 장치 에서만 의미가 있다. 빠른 장치라면 인터럽트 처리 + 문맥 교환 비용이 이득보다 크다. 인터럽트 폭주는 livelock 도 만든다.

숫자로 따져 보자. 인터럽트 경로의 고정 비용을 C_irq(인터럽트 진입·ISR·wakeup·문맥 교환 두 번), 장치 지연을 T_dev 라 하자.

  • 폴링: 지연 ≈ T_dev, CPU 소모 ≈ T_dev
  • 인터럽트: 지연 ≈ T_dev + C_irq, CPU 소모 ≈ C_irq (나머지 시간은 남이 씀)

예제 1 (책의 디스크): T_dev = 10 ms, C_irq = 5 µs → 인터럽트는 지연을 0.05% 늘리는 대신 CPU 10 ms 를 돌려준다. 압승.

예제 2 (새 예제, 저지연 NVMe — Optane 급 4KB read ~10 µs): T_dev = 10 µs, C_irq = 5 µs → 인터럽트는 지연을 50% 늘린다. 돌려받는 CPU 는 10 µs 인데 그 시간에 문맥 교환하고 돌아오면 남는 게 거의 없다. 그래서 Linux 는 이런 장치에 io_poll/io_uring IOPOLL 같은 폴링 모드 를 둔다.

손익분기는 대략 T_dev ≈ C_irq 근처다. 장치 속도를 모르거나 들쭉날쭉하면 hybrid: 잠깐 폴링하다가 안 끝나면 인터럽트로 잔다(two-phase). 아래 "직접 해보기"에서 이 세 경우를 모두 실제로 측정한다.

4.3 livelock 과 coalescing#

  • livelock: 패킷마다 인터럽트가 오면, 폭주 시 CPU 가 ISR 만 돌고 사용자 프로세스(실제로 요청을 처리할 웹 서버)는 못 돈다. 시스템은 바쁜데 진척이 없다. 해법은 부하가 크면 폴링으로 전환 해서 OS 가 처리량을 통제하는 것(Linux NAPI 가 정확히 이것).
  • coalescing(병합): 장치가 인터럽트를 바로 올리지 않고 조금 기다렸다가, 그 사이 끝난 다른 완료들과 묶어 한 번만 올린다. 대가는 지연. NVMe 의 Interrupt Coalescing(Feature 08h: aggregation time / threshold)이 그대로 이 아이디어다.

5. DMA 로 데이터 이동 맡기기 (36.5)#

CRUX — HOW TO LOWER PIO OVERHEADS: "With PIO, the CPU spends too much time moving data to and from devices by hand. How can we offload this work and thus allow the CPU to be more effectively utilized?"

PIO 로 큰 데이터를 옮기면 CPU 가 다시 "복사기"가 된다(타임라인의 c). DMA(Direct Memory Access) 엔진 은 메모리↔장치 전송만 하는 특수 장치다. OS 는 "데이터가 메모리 어디에 있고(주소), 얼마나(길이), 어느 장치로" 를 알려 주고 손을 뗀다. 전송이 끝나면 DMA 컨트롤러가 인터럽트를 올린다.

계산 예(새 예제): 구형 ATA PIO mode 4 는 약 16.6 MB/s 다. 4KB 를 PIO 로 옮기면 4096 B ÷ 16.6 MB/s ≈ 247 µs 동안 CPU 가 묶인다. 같은 일을 DMA 로 하면 CPU 는 descriptor 몇 워드(주소·길이·방향)를 쓰는 데 1 µs 남짓이면 끝나고, 나머지 ~246 µs 는 다른 프로세스 몫이다. 초당 1만 IOPS 라면 PIO 는 CPU 247% (= 코어 2.5개) 를 복사에 쓰는 셈이다.

DMA 를 쓰면 새 문제가 생긴다(책 범위 밖이지만 면접 단골).

  • 캐시 일관성: 장치가 DRAM 에 직접 쓰면 CPU 캐시에는 옛 값이 남을 수 있다. coherent 인터커넥트가 아니면 드라이버가 DMA 전후에 cache clean/invalidate 를 해야 한다(Linux dma_map_single/dma_sync_*).
  • 주소: 장치는 가상 주소를 모른다. 물리 주소(또는 IOMMU 가 번역해 줄 IOVA)를 줘야 하고, 4KB 페이지가 물리적으로 흩어져 있으면 scatter-gather 리스트 가 필요하다(NVMe PRP/SGL).
  • 고정(pinning): 전송 중 그 페이지가 swap out 되면 안 된다.

6. 장치와 대화하는 두 방법 (36.6)#

CRUX — HOW TO COMMUNICATE WITH DEVICES: "How should the hardware communicate with a device? Should there be explicit instructions? Or are there other ways to do it?"

방식어떻게보호오늘날
명시적 I/O 명령x86 in/out 으로 별도 포트 주소 공간 접근특권 명령 (유저는 못 씀)레거시 PC 장치(IDE 0x1F0, UART 0x3F8)
memory-mapped I/O레지스터를 물리 주소에 매핑, 보통의 load/store페이지 테이블로 커널에만 매핑ARM SoC 전부, PCIe BAR, NVMe doorbell

책은 "둘 중 압도적인 우위는 없다"고 하지만, 실무에서 MMIO 를 쓰면 메모리처럼 보이지만 메모리가 아니다 라는 함정을 알아야 한다.

  • 컴파일러: 레지스터 읽기 두 번을 하나로 합치거나 지워 버릴 수 있다 → volatile (또는 readl/writel 접근자).
  • CPU/인터커넥트: store 순서를 바꾸거나 합칠 수 있다 → ARM 에서는 MMIO 영역을 Device 메모리 속성(nGnRE 등)으로 매핑하고, "descriptor 를 DRAM 에 쓴 뒤 doorbell 을 친다" 사이에 barrier(wmb()/dsb st)를 둔다. 순서가 뒤집히면 장치가 덜 쓴 descriptor 를 DMA 로 읽어 간다.
  • PCIe 쓰기는 posted 라서 writel 이 리턴해도 장치에 도착했다는 보장이 없다. 확인하려면 같은 장치 레지스터를 한 번 읽는다(read-back flush).

7. OS 에 끼워 넣기: 디바이스 드라이버 (36.7)#

CRUX — HOW TO BUILD A DEVICE-NEUTRAL OS: "How can we keep most of the OS device-neutral, thus hiding the details of device interactions from major OS subsystems?"

답은 언제나처럼 추상화 다. 장치를 아는 코드는 맨 아래 디바이스 드라이버 한 곳에만 둔다.

  • 장점: 파일시스템은 SCSI 인지 IDE 인지 USB 인지 몰라도 된다.
  • 단점: 장치의 특별한 능력이 묻힌다. 책의 예: SCSI 는 풍부한 에러 정보(sense key/ASC/ASCQ)를 주지만, 상위에는 일반 EIO 하나만 올라간다. NVMe 도 마찬가지로 Status Code Type/Status Code, 미디어 에러 위치 같은 정보가 FS 에서는 대부분 -EIO 로 뭉개진다.
  • 규모: Linux 커널 코드의 70% 이상이 드라이버 다. 드라이버는 핵심 커널 코드보다 버그가 몇 배 많고(책 인용: 7배), 커널 크래시의 주원인이다.

8. 사례 연구: xv6 IDE 드라이버 (36.8)#

8.1 IDE 레지스터#

주소레지스터메모
0x3F6Controlbit1 nIEN=0 이면 인터럽트 enable, bit2 SRST=reset
0x1F0Data port16/32bit PIO 데이터
0x1F1Errorstatus 의 ERROR=1 일 때 읽음 (BBK, UNC, IDNF, ABRT ...)
0x1F2Sector count몇 섹터
0x1F3–0x1F5LBA low/mid/highLBA 비트 0–23
0x1F6Drive/Head1 L 1 D LBA[27:24]: L=LBA 모드, D=master/slave
0x1F7Command / Status쓰면 command, 읽으면 status (BUSY READY FAULT SEEK DRQ CORR IDX ERR)

0x1F7 하나가 쓰면 command, 읽으면 status 라는 점이 재미있다. 레지스터는 메모리가 아니라 "주소 하나에 걸린 두 개의 다른 신호선"일 수 있다. SSD FW 의 레지스터 맵에서도 W1C(write-1-to-clear), RO/WO 공유 주소는 흔하다.

8.2 프로토콜#

  1. Status(0x1F7)를 읽어 BUSY=0, READY=1 이 될 때까지 기다린다.
  2. Sector count, LBA, drive 번호를 0x1F2–0x1F6 에 쓴다.
  3. 0x1F7 에 READ 또는 WRITE 명령을 쓴다 → 시작.
  4. 쓰기라면 READY && DRQ 를 기다려 데이터 포트에 데이터를 쓴다.
  5. 인터럽트를 처리한다(섹터마다 또는 묶어서 한 번).
  6. 매 동작 후 status 의 ERROR 비트를 보고, 켜져 있으면 Error 레지스터를 읽는다.

8.3 코드 따라 읽기#

읽을 때 짚을 점:

  • 폴링과 인터럽트가 섞여 있다. 명령을 내기 전 "준비됐나?"(①)는 짧으니 폴링, 실제 I/O 완료(⑦→⑨)는 길으니 인터럽트. 이것이 4.2 의 손익분기를 코드로 옮긴 모습이다.
  • ISR 이 다음 요청을 발행한다(⑩). 장치가 놀지 않게 하는 고전 패턴. NVMe 처럼 큐가 깊은 장치에서는 아예 여러 개를 미리 넣어 둔다(queue depth).
  • 락 + sleep/wakeup: ide_rw 와 ide_intr 가 같은 큐를 만지므로 ide_lock. sleep(b, &ide_lock) 은 잠들면서 락을 원자적으로 놓는다 — Ch.30 조건 변수의 wait 와 같은 계약이다.
  • 책 코드는 "simplified" 라 그대로는 컴파일이 안 된다. while ((int r = inb(...)) ...) 는 C 문법이 아니고, ide_intr 의 b 는 초기화되지 않았다. 실제 xv6 는 b = idequeue; 로 큐 머리를 꺼내고, 빈 큐면 spurious interrupt 로 보고 리턴한다. 면접에서 코드 리뷰 문제로 내기 좋은 지점이다.
  • ERROR 처리 부재: 책 프로토콜 6단계(ERROR → Error 레지스터 확인)를 이 간략 버전은 거의 안 한다. 실제 드라이버 코드의 상당 부분은 에러·타임아웃·리셋 경로다.

9. 역사 메모 (36.9)#

인터럽트는 1950년대 초 UNIVAC 에 이미 있었고, DMA 의 원조로는 DYSEAC 또는 IBM SAGE 가 거론된다. 책의 결론: "누가 먼저냐"는 별로 중요하지 않다. 빠른 CPU 와 느린 장치 라는 조건이 있으면 누구나 "느린 I/O 를 기다리는 동안 CPU 에게 딴 일을 시키자"는 생각에 도달한다.

10. 직접 해보기#

10.1 C: 폴링 vs 인터럽트, PIO vs DMA 를 실제로 재 보기#

장치를 별도 스레드로 흉내 내고, 레지스터는 _Atomic 공유 변수(= MMIO 처럼 load/store 로 접근)로 둔다. 드라이버(main 스레드)가 기다리는 동안 자기 스레드가 태운 CPU 시간 을 CLOCK_THREAD_CPUTIME_ID 로 잰다. "인터럽트"는 condvar 로 잠들었다가 장치 스레드가 signal 하는 것으로 대신했다(실제 ISR→wakeup 경로와 같은 모양: 잠들기 → 깨우기 → 스케줄러가 다시 돌림).

조용한 상태(다른 작업이 적을 때, Apple M2 8코어)에서의 실제 출력:

해석:

  • [1/2] 대기 CPU: 같은 200 µs 장치를 200번 쓰는 동안, 폴링 드라이버는 wall 시간의 100% 를 CPU 로 태웠다(I/O 당 31만 번 status 읽기). 인터럽트 드라이버는 2% 만 썼다. 나머지 98% 는 다른 프로세스가 쓸 수 있는 시간이다.
  • PIO vs DMA wall 시간: PIO 쪽이 I/O 당 약 (59.08 − 41.37)/200 ≈ 89 µs 더 걸렸다. 4KB 를 1024번 핸드셰이크로 넘기느라 코어 간 캐시라인이 1024번 왕복한 비용이다. 실제 PIO 는 버스 트랜잭션이 훨씬 느리니 차이는 더 크다.
  • [3] 빠른 장치: 장치가 즉시 끝나면 폴링 p50 0.21 µs vs 인터럽트(잠들기→깨우기) p50 1.83 µs. 9배 차이. 4.2 의 "빠른 장치는 폴링" 그대로다.
  • [4] hybrid: 20 µs 까지 spin. 10 µs 장치는 spin 안에서 끝나서 한 번도 안 잤고(지연 10.29 µs), 50 µs 장치는 매번 잤다(드라이버 CPU 는 I/O 당 22.7 µs 로 제한).

같은 바이너리를 다른 에이전트들이 빌드를 돌려 load average 가 45 인 상태 에서 돌린 실제 출력도 붙인다.

부하가 걸리면 그림이 바뀐다. 인터럽트(=잠든 스레드 깨우기)의 p50 이 1.8 µs → 수십~100 µs 로 뛰고, DMA+인터럽트의 wall 시간이 폴링보다 오히려 길어졌다. 잠든 스레드는 깨어난 뒤 CPU 를 다시 배정받아야 하기 때문이다(wakeup latency = 스케줄링 지연). 폴링은 p50 이 그대로지만 p99 는 수십 ms 로 튄다 — spin 중인 스레드도 결국 선점당하니까. 실시간 시스템이 "인터럽트 지연(interrupt latency)"과 "스케줄링 지연"을 따로 예산 잡는 이유가 이것이다.

10.2 OSTEP 시뮬레이터: process-run.py 로 overlap 보기#

이 판(v0.91)의 Ch.36 에는 숙제가 없다. 대신 file-devices/ 에 들어 있는 process-run.py 로 "폴링 = I/O 끝날 때까지 CPU 를 안 넘김", "인터럽트 = I/O 동안 다른 프로세스 실행"을 흉내 낼 수 있다(-S SWITCH_ON_END vs -S SWITCH_ON_IO). PID 0 은 I/O 1번, PID 1 은 CPU 4번.

느린 I/O(-L 5)에서는 overlap 덕분에 9 → 6 tick. 이제 I/O 를 1 tick 으로 빠르게 하면?

빠른 장치에서는 "넘겨줬다가 돌려받기"가 오히려 손해다(6 vs 5 tick, PID 0 의 완료 시점은 6 vs 2). I/O 가 끝났는데도 PID 0 이 READY 로 4 tick 을 기다린 것이 wakeup 후 스케줄링 지연 이다 — 10.1 의 부하 실험과 같은 현상이다.

11. 펌웨어 엔지니어의 눈으로#

  • "canonical device 의 내부"가 바로 Don 이 짜던 코드다. 호스트가 보는 status/command/data 는 NVMe 에서 SQ/CQ + doorbell 레지스터(BAR0 + 0x1000 이후)로 바뀌었을 뿐이다. 호스트는 SQ entry(64B)를 DRAM 에 쓰고 SQ tail doorbell 을 MMIO 로 친다 → 컨트롤러 FW 가 SQE 를 DMA 로 가져와(fetch) 처리 → CQE(16B)를 호스트 메모리에 DMA 로 쓰고 phase bit 를 뒤집음 → MSI-X. "명령 쓰기 = doorbell", "status 폴링 = CQ phase bit 폴링" 이 1:1 대응이다.
  • 폴링/인터럽트 선택은 장치 안에서도 똑같이 나온다. 컨트롤러 FW 의 NAND 채널 완료는 보통 폴링(또는 HW 큐 상태 폴링 루프)이고, 호스트 쪽 완료는 MSI-X + coalescing 이다. tR ~50 µs 수준 이벤트를 RTOS 태스크 전환으로 받을지, 메인 루프 폴링으로 받을지가 4.2 의 손익분기 문제다. 호스트 측에서 Linux NVMe poll_queues 와 io_uring IOPOLL 이 이 문제의 호스트 쪽 답이다.
  • coalescing 파라미터는 FW 가 구현한다. NVMe Set Features(Interrupt Coalescing: Aggregation Threshold/Time, 100 µs 단위)를 받으면 FW 는 CQ 별로 카운터·타이머를 관리해서 MSI-X 를 지연시킨다. 벤치마크 QD1 지연이 나빠지는 대신 QD32 IOPS 에서 호스트 CPU 가 줄어드는 trade-off 를 직접 측정해 봤을 것이다.
  • DMA 와 IOMMU 는 Apple SoC 에서 피부로 느끼는 부분. Apple 의 DART 는 코프로세서/PCIe 장치마다 IOVA 공간을 따로 준다. RF 칩셋 통합 디버깅에서 "장치가 엉뚱한 주소에 DMA → DART fault" 는 레지스터 덤프보다 IOMMU fault 로그가 먼저 말해 준다. DMA 를 켠 순간 "장치도 MMU 아래 있어야 한다"는 결론이 나온다.
  • AI 가속기 = 거대한 DMA 장치. GPU/NPU 드라이버도 이 장의 구조 그대로다: 커맨드 버퍼(=descriptor 링)를 메모리에 쓰고 doorbell MMIO → 가속기의 DMA 엔진이 가중치/활성화를 HBM↔호스트 사이로 옮기고 → 완료는 fence/interrupt. "PIO 로 텐서를 옮기면 안 된다"는 이 장의 DMA 동기와 같은 이야기다.

12. 면접 질문#

Q1. 인터럽트가 폴링보다 항상 좋은가? 언제 폴링을 고르나?#

답 보기

아니다. 인터럽트 경로에는 고정 비용(인터럽트 진입, ISR, wakeup, 문맥 교환 2번, 캐시 오염)이 있다. 장치 지연이 이 비용과 비슷하거나 작으면(수 µs 급 NVMe, RDMA NIC) 폴링이 지연도 짧고 오히려 CPU 도 덜 쓴다. 반대로 ms 급 장치(HDD)는 인터럽트로 CPU 를 돌려받는 이득 이 압도적이다. 속도를 모르면 hybrid(잠깐 spin → sleep). 또 인터럽트 폭주 시 livelock 위험이 있어 고부하 네트워크는 NAPI 처럼 폴링으로 전환한다. 직접 측정에서도 즉시 끝나는 장치는 폴링 p50 0.2 µs vs 인터럽트 1.8 µs 였다.

Q2. DMA 를 쓰면 드라이버가 추가로 신경 써야 하는 것은?#

답 보기
  1. 캐시 일관성: non-coherent 시스템이면 장치→메모리(read) 후 invalidate, 메모리→장치(write) 전 clean. 2) 주소: 장치는 VA 를 모르므로 PA 또는 IOMMU 가 번역할 IOVA 를 준다. 흩어진 페이지는 scatter-gather(NVMe PRP/SGL). 3) pinning: 전송 중 페이지가 swap/migrate 되면 안 된다. 4) 순서: descriptor 를 메모리에 다 쓴 뒤 doorbell MMIO 를 쳐야 하므로 사이에 write barrier. 5) 보안: IOMMU 없이 장치가 아무 메모리나 DMA 할 수 있으면 악성 장치(Thunderbolt DMA 공격)가 커널 메모리를 읽는다.

Q3. port-mapped I/O 와 memory-mapped I/O 의 차이와, MMIO 를 C 로 다룰 때의 함정은?#

답 보기

PMIO 는 x86 in/out 같은 별도 명령 + 별도 I/O 주소 공간, MMIO 는 레지스터를 물리 주소 공간에 매핑 해 일반 load/store 로 접근한다. MMIO 함정: 컴파일러가 접근을 합치거나 없애지 못하도록 volatile(또는 readl/writel), CPU 가 재배열·병합·투기적 접근을 하지 못하도록 uncached/Device 메모리 속성, 다른 메모리 쓰기와의 순서를 보장하는 barrier, PCIe posted write 라 도착 확인이 필요하면 read-back. 읽기에 부작용이 있는 레지스터(read-to-clear)는 디버거로 메모리 덤프만 떠도 상태가 바뀐다.

Q4. xv6 IDE 드라이버에서 ide_intr 가 다음 요청을 직접 발행하는 이유는? 락은 왜 필요한가?#

답 보기

장치가 놀지 않게 하기 위해서다. 완료 인터럽트 시점이 다음 명령을 낼 가장 빠른 시점이고, 깨어난 프로세스가 스케줄될 때까지 기다리면 그만큼 디스크가 논다. 락은 ide_rw(프로세스 문맥, 큐에 추가)와 ide_intr(인터럽트 문맥, 큐에서 제거)가 같은 큐를 동시에 만지기 때문에 필요하다. 단일 CPU 라도 인터럽트가 끼어들 수 있으므로 xv6 의 acquire 는 인터럽트도 끈다. 또 sleep(b, &ide_lock) 은 잠들면서 락을 놓아서 lost wakeup 을 막는다(조건 변수의 wait 와 같은 계약).

Q5. 인터럽트 coalescing 을 FW 에 구현한다면 무엇을 trade-off 하고 어떻게 튜닝하나?#

답 보기

지연 vs 호스트 CPU/인터럽트 수. 완료 N 개 또는 시간 T 중 먼저 도달하는 조건에서 MSI-X 를 올린다(NVMe: Aggregation Threshold, Time). QD1 에서는 기다려도 더 묶일 완료가 없으므로 T 만큼 순수 손해 다 → 큐 깊이가 낮으면 coalescing 을 끄거나 T 를 작게. 고 QD 대역폭 워크로드는 N 을 키워 인터럽트를 수십 배 줄인다. 구현 시 CQ 별 카운터/타이머, 큐가 비면 즉시 flush, 에러 완료는 즉시 보고 같은 예외가 필요하다. 검증은 QD 별 p50/p99 지연과 호스트 인터럽트율을 같이 본다.

퀴즈#

퀴즈 1. 표준 프로토콜에서 CPU 가 낭비되는 두 지점과 각각의 해법은?

정답

status 를 기다리는 polling → 인터럽트, 데이터를 직접 옮기는 PIO → DMA.

퀴즈 2. 장치 지연 3 µs, 인터럽트 경로 비용 6 µs. 지연을 최소화하려면 폴링과 인터럽트 중 무엇?

정답

폴링. 인터럽트는 지연이 3 → 9 µs 로 세 배가 된다. 돌려받는 CPU(3 µs)도 인터럽트 비용(6 µs)보다 작다.

퀴즈 3. 0x1F7 레지스터를 "쓰면 command, 읽으면 status" 로 쓰는 게 가능한 이유는?

정답

장치 레지스터는 메모리 셀이 아니라 주소 디코더 뒤의 하드웨어 신호다. 같은 주소라도 read strobe 와 write strobe 가 다른 회로로 연결될 수 있다. 그래서 MMIO 는 "메모리처럼 보이지만 메모리가 아니다".

퀴즈 4. 드라이버 추상화가 정보 손실을 일으키는 책의 예는?

정답

SCSI 의 풍부한 에러 보고가 generic block layer 를 거치며 EIO 하나로 뭉개진다.
