0. 한눈에 보기#

CRUX — "How can we organize file system data structures so as to improve performance? What types of allocation policies do we need on top of those data structures? How do we make the file system 'disk aware'?" (성능을 높이려면 FS 자료구조를 어떻게 배치해야 하나? 그 위에 어떤 할당 정책이 필요한가? FS를 어떻게 "디스크를 의식하게" 만드나?)

  • 켄 톰슨의 원조 UNIX FS는 단순했지만 디스크를 랜덤 접근 메모리처럼 다뤄서 디스크 대역폭의 2% 밖에 못 썼다: inode와 데이터가 멀고, free list 때문에 단편화되고, 블록이 512B로 너무 작았다.
  • Berkeley의 FFS(Fast File System) 는 인터페이스(API)는 그대로 두고 내부만 바꿨다: 디스크를 cylinder group(block group) 으로 나누고, 그룹마다 superblock 사본·비트맵·inode·데이터를 둔다.
  • 정책의 주문(mantra): 관련 있는 것은 가까이, 관련 없는 것은 멀리. 디렉터리는 "디렉터리 적고 free inode 많은" 그룹에, 파일은 부모 디렉터리와 같은 그룹에, 데이터는 자기 inode와 같은 그룹에.
  • 예외: 큰 파일은 그룹 하나를 독차지하지 않도록 chunk 단위로 여러 그룹에 흩는다. 성능 손해는 chunk를 충분히 크게 해서 amortize.
  • 그 외: 4KB 블록 + 512B sub-block(작은 파일 낭비 방지), 회전을 고려한 parameterization, 긴 파일 이름, symlink, 원자적 rename — "쓸 만하게 만들기"도 중요한 교훈.

2. 문제: 형편없는 성능 (41.1)#

원조 UNIX FS의 디스크 배치는 이게 전부다: S | Inodes | Data. 단순하고 파일/디렉터리 계층이라는 추상화를 잘 제공했지만, 성능은 처음부터 나빴고 시간이 갈수록 더 나빠져 디스크 대역폭의 2% 까지 떨어졌다(McKusick 측정). 원인 세 가지:

  1. inode와 데이터가 멀다. 파일을 읽으면 inode 읽고 → 긴 seek → 데이터. 아주 흔한 패턴이 매번 비싸다.
  2. free list 단편화. 빈 블록 리스트가 디스크 여기저기를 가리키고, 할당은 그냥 "다음 free 블록"을 가져간다.
  3. 블록이 512B로 작다. 내부 단편화는 적지만, 블록마다 위치 잡기 비용을 내야 해서 전송 효율이 나쁘다.

단편화 예 (원문):

빈 공간이 4블록인데 연속 4블록이 아니라 2+2라서 E가 쪼개진다. 디스크 조각 모음(defrag) 도구가 하는 일이 바로 이걸 다시 붙이는 것이다(데이터 옮기고 inode 갱신).

3. FFS: 디스크를 의식하라 (41.2)#

FFS의 핵심 전략: 같은 인터페이스(open/read/write/close…) + 다른 내부 구현. 이후 거의 모든 FS가 이 길을 따른다 — 응용 호환성은 유지하고 내부는 성능·신뢰성을 위해 바꾼다.

4. 구조: cylinder group (41.3)#

  • cylinder = 여러 플래터 표면에서 중심으로부터 같은 거리의 트랙들. FFS는 연속된 N개의 cylinder를 하나의 cylinder group 으로 묶는다. 같은 그룹 안의 두 파일은 오가도 seek이 짧다.
  • 현대 디스크는 기하 정보를 숨기고 논리 블록 주소 공간만 노출한다(Ch.37). 그래서 ext2/3/4는 그냥 주소 공간의 연속 구간을 block group 으로 쓴다. 이름만 다르고 목적은 같다.
  • 그룹 하나 안에는 FS가 가져야 할 것이 다 있다:
    • S: superblock 사본 — mount에 필수라서 그룹마다 복제. 한 사본이 깨져도 다른 사본으로 mount.
    • ib / db: 그룹별 inode bitmap / data bitmap. 비트맵은 큰 연속 빈 공간을 찾기 쉬워서 free list의 단편화 문제를 피한다.
    • Inodes / Data: vsfs와 같은 inode 영역과 데이터 영역. 그룹 대부분은 데이터.

ASIDE — FFS에서 파일 하나 만들기. /foo/bar.txt(4KB) 생성: 새 inode → inode bitmap + inode 쓰기, 데이터 → data bitmap + data block 쓰기 — 현재 그룹에만 최소 4번(버퍼링될 수 있음). 그리고 부모 디렉터리 foo 에 엔트리 추가(기존 블록에 들어가거나 새 블록+data bitmap), foo 의 inode도 크기·mtime 갱신. 파일 하나 만드는 데 이만큼이다. Ch.40의 "create = 10 I/O"와 같은 이야기를 그룹 관점에서 본 것.

5. 정책: 파일과 디렉터리를 어디에 둘까 (41.4)#

주문: 관련 있는 것은 같은 그룹에, 관련 없는 것은 다른 그룹에. "관련"을 정하는 단순 휴리스틱:

  1. 디렉터리: 할당된 디렉터리 수가 적고(디렉터리를 그룹에 고르게 분산) free inode가 많은(그 디렉터리의 파일들을 나중에 담을 수 있게) 그룹을 골라 디렉터리의 inode와 데이터를 둔다.
  2. 파일:
    • 파일의 데이터 블록을 자기 inode와 같은 그룹에 (inode↔데이터 긴 seek 제거).
    • 같은 디렉터리의 파일들은 그 디렉터리의 그룹에. /dir1/1.txt, /dir1/2.txt, /dir1/3.txt 는 같은 그룹, /dir99/4.txt 는 멀리.

연구 결과가 아니라 상식에 근거한 정책이다: 한 디렉터리의 파일들은 함께 쓰이는 경우가 많다(여러 .c 를 컴파일해 하나로 링크).

6. 파일 지역성 측정 (41.5)#

정책이 맞는지 SEER 트레이스로 확인한다. 거리 지표 = 연속된 두 open의 공통 조상까지 디렉터리 트리를 몇 단계 올라가야 하나.

두 open거리원문 측정(누적)
같은 파일을 다시 open0약 7%
같은 디렉터리의 다른 파일 (dir/f → dir/g)10+1 합쳐 약 40%
형제 디렉터리 (proj/src/foo.c → proj/obj/foo.o)2추가로 약 25%
  • 거리 0~1이 약 40% → FFS 가정은 (이 트레이스에서) 타당하다.
  • 거리 2 약 25%는 FFS 정책이 잡지 못하는 지역성이다: src 와 obj 는 서로 다른 디렉터리라 다른 그룹에 갈 수 있다.
  • "Random" 비교선(같은 파일들을 무작위 순서로)도 결국 루트를 공유하므로 어느 정도 지역성이 보이지만 트레이스보다 확실히 낮다.

7. 큰 파일 예외 (41.6)#

규칙 없이 큰 파일을 첫 그룹에 다 넣으면 그 그룹이 꽉 차서, 그 디렉터리의 "관련 파일"들이 들어갈 자리가 없어진다 → 지역성이 깨진다.

FFS의 해법: 첫 그룹에 일정량(예: direct 포인터 12블록)만 넣고, 다음 "큰 chunk"(예: 첫 indirect 블록이 가리키는 1024블록)는 다른 그룹(사용률 낮은 곳)에, 그다음 chunk는 또 다른 그룹에…

순차 읽기 성능이 나빠지지 않나? → chunk를 충분히 크게 하면 된다. 이게 amortization: 오버헤드(seek)당 일(전송)을 많이 하면 오버헤드 비율이 줄어든다.

7.1 계산: 몇 KB를 읽어야 seek 비용이 묻히나#

위치 잡기 T = 10ms, 전송률 R = 40MB/s. 시간의 절반은 seek, 절반은 전송(= peak의 50%)이 목표면, 10ms 동안 전송할 양은:

일반식: peak의 비율 F를 원하면 전송 시간 = F/(1−F) × T 이므로

원문은 90% → "3.69MB", 99% → "40.6MB" 라고 쓰는데, 이건 3686.4KB, 40550.4KB 를 1MB = 1000KB 로 읽은 값이다(1MiB 기준이면 3.60MiB, 39.6MiB). 이 장은 R을 1MB=1024KB 로 환산했다가 결과는 1000으로 나눠 표기한 셈이라 단위가 섞여 있다는 점만 알아 두자. 핵심 메시지는 같다: peak에 가까워질수록 chunk가 폭발적으로 커진다(F/(1−F)).

새 예제 — NVMe가 아닌 요즘 HDD: T = 8ms, R = 250MB/s 에서 90%를 원하면 D = 9 × 250 × 0.008 = 18MB. 전송률은 빨리 좋아지고 seek은 느리게 좋아지므로(원문 41.6 마지막 문단) 필요한 chunk 크기는 해마다 커진다.

7.2 FFS가 실제로 한 일#

FFS는 위 계산을 쓰지 않고 inode 구조를 그대로 따랐다: 첫 12 direct 블록은 inode와 같은 그룹, 이후 간접 블록 하나(와 그것이 가리키는 블록 전부)마다 다른 그룹. 4KB 블록 + 4B 주소면 1024블록 = 4MB 마다 그룹 이동, 첫 48KB만 예외. 위 표로 보면 4MB chunk = 약 90% 대역폭 — 꽤 괜찮은 선택이다(아래 코드 출력 2번 표).

8. FFS의 그 밖의 것들 (41.7)#

8.1 sub-block#

당시 파일의 다수가 ~2KB였는데 4KB 블록이면 내부 단편화로 디스크의 절반 가까이 낭비될 수 있었다. 해법: 512B sub-block. 1KB 파일 = sub-block 2개. 파일이 커져 4KB가 차면 4KB 블록을 찾아 sub-block들을 복사하고 해제한다.

복사 I/O가 비효율적이므로, FFS는 libc를 수정해 쓰기를 4KB 단위로 버퍼링해서 내보내게 했다 → 대부분의 경우 sub-block 경로 자체를 피한다. (커널 문제를 라이브러리 버퍼링으로 우회한 좋은 예.)

8.2 parameterization (회전 고려 배치)#

SCSI 이전, 호스트 CPU가 디스크를 직접 다루던 시절: 블록 0 읽기가 끝나고 블록 1을 요청하면 이미 블록 1이 헤드를 지나가 버려 한 바퀴를 통째로 기다렸다. FFS는 블록을 하나 건너 하나(디스크마다 최적 skip 수를 측정)로 배치해 다음 요청 시간을 벌었다.

대신 트랙을 두 바퀴 돌아야 다 읽으므로 peak의 50%만 나온다. 현대 디스크는 트랙 전체를 내부 track buffer 에 읽어 두므로 FS가 이런 걸 신경 쓸 필요가 없다 — 잘 설계된 추상화의 이득.

8.3 쓸 만하게 만들기#

긴 파일 이름(고정 8자 대신), symbolic link(하드 링크는 디렉터리를 못 가리키고 볼륨을 못 넘는다 — inode 번호는 볼륨 안에서만 의미 있으므로), 원자적 rename().

TIP — 시스템을 쓸 만하게 만들어라. 디스크 인지 배치라는 기술 혁신 못지않게, 논문으로 쓰기 어려운 작은 기능들("The Symbolic Link: Hard Link's Long Lost Cousin" 같은 14쪽 논문은 아무도 안 읽는다)이 FFS 채택을 도왔다. 사용성은 종종 깊은 기술만큼 중요하다.

9. 요약 (41.8)#

FFS는 파일 관리가 OS에서 가장 흥미로운 문제 중 하나임을 보여 준 분수령이다. ext2/ext3는 명백한 후손이고, 모든 현대 시스템이 FFS의 교훈을 따른다: 디스크를 디스크처럼 다뤄라.

10. 직접 해보기#

10.1 amortization · 큰 파일 예외 · sub-block 계산 (C)#

해석:

  • 4KB 블록마다 seek하면 peak의 1% — 원조 UNIX FS의 "2%"가 과장이 아니다(그쪽은 512B 블록이라 더 나빴을 것).
  • FFS의 4MB chunk는 90.9% — 큰 파일을 흩어도 순차 읽기 손해가 10% 정도.
  • 3번 표는 파일 하나당 비율이라 파일 수와 무관하다. 2KB 파일만 있는 FS라면 4KB 블록은 공간의 절반을 낭비 — 원문의 "roughly half the disk being wasted".

10.2 ffs.py 시뮬레이터#

(그룹 4~8 줄 생략, 모두 빈 칸.) in.example1 = dir /a, dir /b, file /a/c 2, file /a/d 2, file /a/e 2, file /b/f 2.

  • 디렉터리 /a, /b 는 서로 다른 그룹(1, 2)에 분산 — "디렉터리 적고 free inode 많은 그룹" 정책.
  • /a/c,d,e 의 inode와 데이터는 모두 부모 /a 의 그룹 1, /b/f 는 그룹 2 — 파일 배치 정책.

같은 입력에 -I(파일 inode를 부모 그룹 대신 모든 그룹에 고르게 뿌림):

/a 의 파일 c, d, e가 그룹 3, 4, 5로 흩어졌다 → ls -l /a 나 컴파일처럼 한 디렉터리를 훑는 작업이 매번 그룹을 넘나들며 seek한다. FFS가 왜 "부모 그룹에" 를 고집하는지 시각적으로 보인다.

큰 파일 예외 (in.largefile = file /a 40, 그룹당 데이터 30블록):

  • 예외 없이는 /a 가 그룹 0을 꽉 채우고 그룹 1까지 넘친다 → 루트 디렉터리의 다른 파일이 그룹 0에 들어갈 자리가 없다.
  • -L 4 면 4블록씩 10개 그룹에 고르게 퍼진다 (그룹 3~8 줄 생략, 모두 aaaa).
  • -T 로 파일의 span(첫 블록~마지막 블록 주소 거리)을 보면: -L 0 은 filespan 59, -L 4 는 filespan 372. 파일이 디스크 전체에 퍼진 대가다. 4블록 chunk는 위 표의 "4KB × 4 = 16KB chunk" 수준이라 순차 읽기 대역폭이 크게 떨어진다 — chunk를 키워야(예: -L 30) amortize 된다.

11. 펌웨어 엔지니어의 눈으로#

  • cylinder group ↔ NAND die/plane 스트라이핑은 정반대 목표다. HDD는 "관련 데이터를 가까이(seek 최소화)", SSD FTL은 "연속 LBA를 여러 die/channel에 흩어(병렬성 최대화)"가 기본이다. 그래서 FFS식 배치 휴리스틱은 SSD에서 대부분 무의미하고, 오히려 ext4의 block group 지역성이 SSD 내부 매핑과 무관해진다. 면접에서 "FFS의 아이디어 중 SSD에서도 유효한 것은?"이라고 물으면: amortization(큰 I/O가 명령 오버헤드·맵 갱신을 묶는다)과 hot/cold 분리(관련 수명끼리 모으기)는 유효, seek 기반 배치는 무효.
  • amortization 식 D = F/(1−F)·R·T 는 NVMe에도 그대로 적용된다. T 자리에 "명령당 고정 오버헤드"(doorbell, 인터럽트, FW 명령 파싱, 맵 lookup ~수 µs)를 넣으면, 4KB 랜덤 I/O로는 대역폭이 안 나오고 128KB+ 순차 I/O나 큐 깊이로 오버헤드를 숨겨야 하는 이유가 같은 식으로 나온다. AI 가속기 DMA도 마찬가지: 디스크립터 처리 오버헤드를 묻으려면 DMA 전송 크기를 키우거나 체인으로 묶는다.
  • superblock 사본 분산 = FW의 메타데이터 이중화. SSD FW도 부팅 정보·맵 루트를 서로 다른 블록/die에 여러 벌 두고 시퀀스 번호로 최신 정상본을 고른다. 한 die가 죽어도 mount(부팅)이 가능해야 한다는 같은 요구.
  • sub-block ↔ NAND 페이지보다 작은 쓰기. 16KB NAND 페이지에 4KB 호스트 쓰기가 오면 FW는 write buffer에서 모아(aggregate) 한 페이지로 프로그램한다 — FFS가 libc 버퍼링으로 sub-block 복사를 피한 것과 같은 패턴. 모으지 못하고 FUA/flush가 오면 패딩하거나 partial page program을 하게 되고, 이게 작은 sync 쓰기의 쓰기 증폭 원인이다.
  • parameterization ↔ 하드웨어 타이밍에 맞춘 배치. 지금 디스크의 track buffer가 그 일을 대신하듯, NAND에서도 multi-plane / cache program 타이밍에 맞춰 FW가 쓰기를 배치한다. "하위 계층이 똑똑해지면 상위 계층은 그 세부를 잊어도 된다"는 같은 교훈.

12. 면접 질문#

Q1. 원조 UNIX FS는 왜 그렇게 느렸나? FFS는 무엇을 바꿨나?#

답 보기

디스크를 랜덤 접근 메모리처럼 다뤘다: (1) inode와 데이터가 멀어 매번 긴 seek, (2) free list 할당이 시간이 갈수록 단편화, (3) 512B 블록이라 블록마다 위치 잡기 비용. 대역폭의 2%. FFS는 API는 그대로 두고 cylinder group(그룹마다 superblock 사본, 비트맵, inode, 데이터), 배치 정책(디렉터리 분산, 파일은 부모 그룹, 데이터는 inode 그룹), 4KB 블록 + 512B sub-block, 큰 파일 예외를 도입했다.

Q2. FFS의 디렉터리/파일 배치 정책을 설명하고, 그 정책이 놓치는 지역성은?#

답 보기

디렉터리: 할당 디렉터리 수가 적고 free inode가 많은 그룹. 파일: 부모 디렉터리 그룹에 inode를, inode와 같은 그룹에 데이터를. 근거는 namespace locality(SEER 트레이스에서 거리 0~1이 약 40%). 놓치는 것: proj/src/foo.c → proj/obj/foo.o 같은 거리 2 접근(약 25%). 형제 디렉터리는 서로 다른 그룹에 놓이므로 seek이 생긴다.

Q3. 큰 파일 예외가 왜 필요하고, 순차 읽기 성능 손해를 어떻게 정당화하나? 수식으로.#

답 보기

큰 파일이 그룹을 독차지하면 그 디렉터리의 다른 관련 파일이 들어갈 자리가 없어진다. 그래서 chunk 단위로 여러 그룹에 분산. 손해는 amortization: peak 비율 F를 얻으려면 chunk D = F/(1−F) × R × T. T=10ms, R=40MB/s면 50%에 409.6KB, 90%에 약 3.6MiB. FFS는 간접 블록 단위(1024블록 = 4MB)로 그룹을 옮겨 약 90% 를 얻는다.

Q4. ext4는 cylinder 정보를 모르는데 block group은 여전히 의미가 있나? SSD에서는?#

답 보기

HDD에서는 LBA가 대략 물리 위치와 단조 대응하므로 연속 LBA 구간 = 가까운 위치라는 가정이 여전히 성립해 의미가 있다. SSD에서는 FTL이 LBA를 임의의 NAND 위치에 매핑하므로 seek 기반 지역성은 무의미. 다만 그룹별 메타데이터 분산(락 경합 감소, 손상 격리), 큰 연속 할당(extent 수 감소, 큰 I/O 유도)은 여전히 이득이다. SSD에 맞춘 FS(F2FS)는 오히려 LFS 스타일 + hot/cold 로그 분리를 쓴다.

Q5. sub-block의 비용은 무엇이었고 FFS는 그걸 어떻게 피했나? 비슷한 패턴을 아는가?#

답 보기

파일이 4KB까지 자라면 sub-block들을 4KB 블록으로 복사해야 해서 추가 I/O가 생긴다. FFS는 libc가 쓰기를 4KB 단위로 버퍼링하게 바꿔 대부분 이 경로를 피했다. 같은 패턴: SSD FW의 write buffer aggregation(4KB 호스트 쓰기를 모아 16KB NAND 페이지로 프로그램), 네트워크의 Nagle 알고리즘, DB의 group commit — "작은 쓰기를 모아 큰 단위로".

13. 자가 점검 & 숙제#

퀴즈 1. T = 5ms, R = 200MB/s 디스크에서 peak의 80%를 얻으려면 chunk는? (1MB = 1000KB로 계산)#

답 보기

D = 0.8/0.2 × 200MB/s × 0.005s = 4 × 1MB = 4MB.

퀴즈 2. 그룹당 inode 10개, 데이터 30블록인 FS에서 FFS 정책대로 /a(디렉터리) 아래 2블록 파일 12개를 만들면 무슨 일이 생기나?#

답 보기

/a 가 inode 1개를 쓰므로 그룹에 남은 inode는 9개 → 파일 9개까지는 /a 의 그룹에 들어가고, 10번째부터는 inode가 부족해 다른 그룹으로 넘어간다(데이터 30블록은 2×9=18로 충분). 디렉터리 배치 정책이 "free inode가 많은 그룹"을 고르는 이유가 이것이다. ffs.py 로 직접 확인한 결과 (dir /a + file /a/f1 2 … file /a/f12 2 를 입력 파일로):

a(=/a) + 파일 9개(b~j)가 그룹 1의 inode 10칸을 채우고, 나머지 3개(k, l, m)는 그룹 2로 넘어갔다.

퀴즈 3. 원조 UNIX FS의 "2% 대역폭"을 4KB 블록 seek 계산(1%)과 비교해 보면, 블록 크기 하나만 512B → 4KB로 바꿀 때 랜덤 배치 기준 대역폭은 몇 배 좋아지나? (T=10ms, R=40MB/s)#

답 보기

512B: 전송 0.0125ms, 효율 ≈ 0.5KB/(10.0125ms) ≈ 0.05MB/s (≈0.12%). 4KB: 0.39MB/s (≈1%). 약 8배. 블록 크기 증가는 amortization의 가장 단순한 형태다. 그래도 1% 수준이라 배치(지역성) 없이는 해결되지 않는다.
