0. 한눈에 보기#

THE CRUX: HOW TO DESIGN A SCALABLE FILE PROTOCOL — "How should one redesign the protocol to minimize the number of server interactions, i.e., how could they reduce the number of TestAuth messages? Further, how could they design the protocol to make these server interactions efficient?" (서버와의 상호작용 수 — 특히 TestAuth 메시지 — 를 최소화하려면 프로토콜을 어떻게 다시 설계해야 하나? 그리고 남은 상호작용을 어떻게 효율적으로 만들까?)

  • AFS(CMU, Satya)의 목표는 확장성(scale): 서버 한 대가 클라이언트를 최대한 많이 받는 것.
  • 핵심 1 — 파일 통째 캐싱(whole-file caching) 을 클라이언트 로컬 디스크에: open 때 전체를 가져오고, read/write 는 로컬, close 때 바뀌었으면 통째로 올린다.
  • 핵심 2 — callback: "파일이 바뀌면 내가 알려줄게" 라는 서버의 약속. NFS 의 GETATTR 폴링을 인터럽트로 바꾼 것.
  • 일관성이 설명하기 쉽다: 다른 기계 간에는 "close 때 보이고, 그때 다른 캐시는 무효화", 충돌하면 last writer(closer) wins.
  • 대가: 서버가 상태(callback 목록) 를 가지므로 크래시 복구가 NFS 보다 복잡하고, 큰 파일의 일부만 읽고 쓰는 워크로드에 약하다.

2. 도입: 목표는 scale#

AFS 는 1980년대 CMU 에서 M. Satyanarayanan("Satya") 교수가 이끈 프로젝트다. 목표는 단순했다: 서버 한 대가 가능한 한 많은 클라이언트를 지원하도록 분산 파일 시스템을 설계하는 것.

확장성에 영향을 주는 요소는 많지만 가장 중요한 건 클라이언트-서버 프로토콜 설계다. NFS 는 클라이언트가 캐시 내용이 바뀌었는지 서버에 주기적으로 확인하게 만든다. 확인 한 번마다 서버 CPU 와 네트워크를 쓰니, 이게 서버 하나가 받을 수 있는 클라이언트 수를 제한한다.

또 하나의 차이: AFS 는 처음부터 사용자가 이해할 수 있는 동작을 일급 목표로 삼았다. NFS 의 캐시 일관성은 attribute cache 타임아웃 같은 구현 세부에 좌우되어 설명하기 어렵다. AFS 는 단순하다: 파일을 열면 대체로 서버의 최신 일관된 사본을 받는다.

3. AFS 버전 1 (49.1)#

(실제 이름은 ITC distributed file system.) 모든 AFS 버전의 기본 원칙은 클라이언트 로컬 디스크에 파일 통째 캐싱이다.

  • open(): 파일 전체를 서버에서 가져와(Fetch) 로컬 디스크의 파일로 저장.
  • read() / write(): 로컬 FS 로 리다이렉트 → 네트워크 통신 없음, 빠르다. 로컬 FS 를 쓰니 블록이 클라이언트 메모리에도 캐시된다.
  • close(): 파일이 수정됐으면 통째로 서버에 올린다(Store, 전체 파일 + 경로 이름).

NFS 와의 대비가 분명하다: NFS 는 블록을 메모리에, AFS 는 파일 전체를 로컬 디스크에 캐싱한다.

4. 버전 1 의 문제들 (49.2)#

AFS 설계자들은 프로토타입을 오래 측정해서 무엇이 잘못됐는지 찾았다.

TIP — 측정하고 나서 만들어라 (Measure Then Build, Patterson's Law): 새 시스템을 만들기 전에 기존 시스템을 측정해 문제를 증명하라. 그러면 (1) 진짜 문제를 풀고 있다는 증거가 생기고, (2) 새 시스템이 실제로 나아졌는지 보일 측정 수단도 이미 갖추게 된다.

측정으로 찾은 두 가지 주요 문제:

  1. 경로 탐색 비용이 너무 크다: Fetch/Store 마다 클라이언트가 전체 경로를 보내니, 서버가 매번 루트에서 home, home 에서 remzi... 를 따라 내려간다. 클라이언트가 많으면 서버 CPU 의 상당 부분이 디렉터리 경로 걷기에 쓰였다.
  2. TestAuth 가 너무 많다: NFS 의 GETATTR 폭주와 똑같다. 서버는 "네 캐시 써도 돼" 라고 답하느라 시간을 보냈고, 답은 대부분 "안 바뀌었어" 였다.

그 외 두 문제:

  • 서버 간 부하 불균형 → 관리자가 서버 사이에 옮길 수 있는 volume 도입으로 해결.
  • 클라이언트마다 프로세스 하나 → 문맥 교환 등 오버헤드 → AFSv2 에서 스레드 기반 서버로 해결.

5. 프로토콜 개선 (49.3)#

결과적으로 서버 CPU 가 병목이 되어, 서버 하나가 클라이언트 20대만 받아도 과부하였다. TestAuth 가 너무 많고, Fetch/Store 때 디렉터리 계층을 너무 오래 걷는다. → 0절의 CRUX.

6. AFS 버전 2 (49.4)#

6.1 callback — 폴링을 인터럽트로#

callback 은 서버가 클라이언트에게 하는 약속이다: "네가 캐시하고 있는 파일이 수정되면 알려줄게." 이 상태를 서버에 추가하면, 클라이언트는 더 이상 캐시가 유효한지 서버에 물을 필요가 없다. 서버가 "아니다" 라고 할 때까지 유효하다고 가정한다. 원문 표현대로, 여기 "폴링 vs 인터럽트" 비유를 넣으면 된다.

6.2 FID — 경로 탐색을 클라이언트로#

AFSv2 는 경로 이름 대신 FID(file identifier) 로 파일을 지정한다. FID = (volume ID, file ID, uniquifier). uniquifier 는 파일이 삭제돼 volume/file ID 가 재사용될 때 구분하는 번호 — NFS 의 generation 번호와 같다.

이제 서버가 경로를 걷는 게 아니라 클라이언트가 한 성분씩 걷고, 결과를 캐시한다. /home/remzi/notes.txt 접근 (home 은 / 에 마운트된 AFS 디렉터리):

  1. home 디렉터리 내용을 Fetch → 로컬 디스크 캐시 + home 에 callback 등록
  2. remzi 디렉터리 Fetch → 캐시 + callback
  3. notes.txt Fetch → 캐시 + callback → 파일 디스크립터 반환

첫 접근은 메시지가 많지만 모든 디렉터리와 파일에 callback 이 걸리므로, 이후 접근은 서버 통신이 전혀 없다. 캐시된 파일에 대해 AFS 는 거의 로컬 디스크 FS 처럼 동작한다.

ASIDE — 캐시 일관성은 만병통치약이 아니다 (Cache Consistency Is Not A Panacea): 여러 클라이언트가 체크인/체크아웃하는 코드 저장소 같은 응용은 FS 의 기본 일관성에 기댈 수 없고, 명시적 파일 잠금 같은 추가 장치가 필요하다. NFS/AFS 의 일관성은 "다른 기계로 로그인해도 내 파일의 합리적인 버전이 보인다" 정도의 일상적 사용을 위한 것이다. 그 이상을 기대하면 눈물 나는 좌절이 기다린다.

7. 캐시 일관성 (49.5)#

NFS 에서 본 두 측면 — update visibility(서버가 언제 새 버전을 갖나)와 cache staleness(서버가 새 버전을 가진 뒤 클라이언트가 언제 그걸 보나) — 을 AFS 에선 callback 과 파일 통째 캐싱 덕에 쉽게 설명할 수 있다.

7.1 다른 기계 사이#

갱신이 서버에 보이는 시점 = 다른 캐시가 무효화되는 시점 = 수정된 파일이 close 되는 순간. 클라이언트가 열고, (여러 번) 쓰고, 닫으면 → 새 파일이 서버로 flush(보이게 됨) → 서버가 사본을 가진 모든 클라이언트의 callback 을 끊는다 → 그 클라이언트들은 다음 open 때 새 버전을 다시 Fetch.

7.2 같은 기계 안#

예외: 같은 기계의 프로세스끼리는 쓰기가 즉시 보인다(close 를 기다리지 않음). 일반 UNIX 의미론 그대로라서, 한 기계만 쓰면 기대대로 동작한다. 다른 기계로 옮겨야 비로소 AFS 의 일반 규칙이 드러난다.

7.3 동시에 고치면: last writer wins#

드물게 서로 다른 기계의 프로세스가 같은 파일을 동시에 고치면, AFS 는 자연스럽게 last writer wins — 더 정확히는 last closer wins — 가 된다. 마지막으로 close 한 클라이언트가 서버에 파일 전체를 마지막으로 올리므로 그 파일이 남는다. 결과 파일은 한 클라이언트가 만든 온전한 파일이다.

NFS 와 대비: 블록 단위 프로토콜이라 각 클라이언트가 블록을 서버로 flush 하는 순서가 섞이면, 최종 파일이 두 클라이언트 갱신의 혼합이 될 수 있다. JPEG 이미지를 두 클라이언트가 조각조각 고쳤다면 유효한 JPEG 이 아닐 것이다.

7.4 Figure 49.3 타임라인 따라가기#

Client1 의 P1, P2(같은 기계), Client2 의 P3, 서버 디스크. 캐시 열은 각 클라이언트 캐시 내용.

포인트:

  • P2 의 read()→B: 같은 기계(Client1)라 P1 의 close 전에도 B 가 보인다.
  • P3 의 read()→A: 다른 기계라 P1 이 close 하기 전엔 서버의 A 를 본다.
  • P1 의 close → 서버가 Client2 의 callback 을 끊음(✁) → P3 의 다음 open 은 B 를 새로 Fetch.
  • 마지막: P3 가 C 를 먼저 close, P1 이 D 를 나중에 close → 서버에 D 가 남는다. P3 의 C 는 통째로 사라졌다.

8. 크래시 복구 (49.6)#

서버가 상태(callback)를 가지므로 복구는 NFS 보다 복잡하다.

클라이언트 재부팅: C1 이 재부팅하는 동안 서버가 C1 에게 callback recall 을 보냈다면(예: C2 가 C1 이 캐시한 F 를 수정), C1 은 그 중요한 메시지를 놓쳤을 수 있다. 그래서 다시 합류한 C1 은 모든 캐시 내용을 의심해야 한다. F 에 다음에 접근할 때 TestAuth 로 "내 F 아직 유효해?" 를 묻고, 유효하면 쓰고 아니면 새로 Fetch.

서버 크래시: callback 목록은 메모리에 있다. 재부팅한 서버는 어느 클라이언트가 어떤 파일을 가졌는지 모른다. 그래서 모든 클라이언트가 서버가 죽었었다는 걸 알아채고 캐시 전체를 의심하고 사용 전에 재검증해야 한다. 이 사실을 제때 알리지 못하면 클라이언트가 stale 파일을 쓸 위험이 있다. 구현 방법:

  • 서버가 다시 살아나면 각 클라이언트에 "캐시 믿지 마!" 메시지를 보낸다.
  • 클라이언트가 주기적으로 서버가 살아 있는지 확인(heartbeat).

→ 더 확장 가능하고 합리적인 캐싱 모델에는 비용이 따른다. NFS 에선 클라이언트가 서버 크래시를 거의 눈치채지 못했다.

9. AFSv2 의 확장성과 성능 (49.7)#

새 프로토콜로 측정해 보니 서버당 약 50 클라이언트(v1 은 20)를 지원했다. 클라이언트 성능도 흔한 경우엔 모든 접근이 로컬이라 로컬 FS 에 가까웠다. 새 파일을 만들거나 기존 파일을 쓸 때만 Store 가 필요하다.

9.1 워크로드별 비교 (Figure 49.4)#

가정: 작은 파일 Ns 블록, 중간 Nm, 큰 파일 NL 블록. 작은/중간 파일은 클라이언트 메모리에 들어가고, 큰 파일은 로컬 디스크엔 들어가지만 메모리엔 안 들어간다. 블록당 원격 접근 Lnet, 로컬 메모리 Lmem, 로컬 디스크 Ldisk, 그리고 Lnet > Ldisk > Lmem. 첫 접근은 어느 캐시에도 없고, 재접근은 캐시 용량이 충분하면 적중.

워크로드NFSAFSAFS/NFS
1. 작은 파일 순차 읽기Ns · LnetNs · Lnet1
2. 작은 파일 순차 재읽기Ns · LmemNs · Lmem1
3. 중간 파일 순차 읽기Nm · LnetNm · Lnet1
4. 중간 파일 순차 재읽기Nm · LmemNm · Lmem1

관찰:

  1. 대부분 비슷하다 (1, 3, 5): 첫 읽기는 원격 fetch 가 지배. AFS 가 로컬 디스크에 쓰는 비용은 로컬 FS 의 페이지 캐시에 흡수돼 숨는다. 재읽기도 AFS 의 디스크 사본이 결국 메모리 캐시에서 읽히므로 NFS 와 비슷(2, 4).
  2. 큰 파일 재읽기(6)는 AFS 승: AFS 는 로컬 디스크에서 다시 읽지만, NFS 는 메모리에만 블록을 캐시하므로 메모리보다 큰 파일은 서버에서 다시 전부 가져와야 한다. AFS 가 Lnet/Ldisk 배 빠르고, NFS 는 서버 부하까지 늘린다.
  3. 새 파일 순차 쓰기(8, 9)는 비슷: AFS 는 로컬 사본에 쓰고 close 때 서버로; NFS 는 메모리에 버퍼링하다 close 때(flush-on-close) 서버로.
  4. 덮어쓰기(10)는 AFS 가 2배 느림: AFS 는 open 때 어차피 덮어쓸 옛 파일 전체를 먼저 Fetch 한다. NFS 는 그냥 블록을 덮어쓴다. (NFS 읽기가 블록 정렬이라고 가정, 그리고 O_TRUNC 로 열지 않았다고 가정 — O_TRUNC 면 AFS 도 fetch 안 함.)
  5. 큰 파일의 작은 부분 접근(7, 11)은 NFS 압승: AFS 는 open 때 전체를 가져오고, 수정했으면 전체를 다시 올린다 — 한 블록을 위해 2·NL 블록 전송. NFS 는 요청 크기에 비례한 I/O 만.

결론: 두 시스템은 서로 다른 가정을 했고 그래서 다른 성능을 낸다. 어느 쪽이 나은지는 언제나 워크로드에 달렸다.

9.2 숫자로 보기#

블록 4 KB, Lnet = 1 ms, Ldisk = 0.1 ms, Lmem = 0.001 ms, Ns = 4 (16 KB), Nm = 1000 (4 MB), NL = 10⁶ (4 GB) 로 두면 (아래 C 코드 [3] 의 실제 출력):

  • 6번: NFS 1000 s vs AFS 100 s — AFS 10배 빠름 (Ldisk/Lnet = 0.1).
  • 7번: NFS 1 ms vs AFS 1000 s — 10⁶ 배 차이. 4 GB 로그 파일에서 한 줄 읽으려고 4 GB 를 받아 오는 셈.
  • 11번: NFS 1 ms vs AFS 2000 s — 한 블록 고치려고 8 GB 를 주고받는다.

새 예제 — 데이터베이스 파일: 10 GB DB 에서 랜덤 4 KB 업데이트를 1000번, 각각 open-write-close 한다면 NFS ≈ 1000 × Lnet = 1 s. AFS ≈ 1000 × (2 × 2.5×10⁶ 블록 × 1 ms) — 사실상 불가능. AFS 가 "대부분의 파일은 공유가 드물고, 통째로 순차 접근된다" 는 워크로드 가정 위에 서 있다는 게 이렇게 드러난다.

10. AFS 의 다른 개선들 (49.8)#

FFS 가 심볼릭 링크 등을 더했듯, AFS 도 쓰기 편하고 관리하기 쉬운 기능을 넣었다.

  • 진짜 전역 이름 공간(global namespace): 모든 클라이언트에서 파일 이름이 같다. NFS 는 클라이언트마다 원하는 곳에 마운트할 수 있어서, 이름이 같으려면 관례와 큰 관리 노력이 필요하다.
  • 보안: 사용자 인증, 파일을 비공개로 유지하는 메커니즘. NFS 는 오랫동안 원시적이었다.
  • 유연한 사용자 관리 접근 제어(ACL): 누가 어떤 파일에 접근할지 사용자가 세밀하게 제어. 일반 UNIX FS 처럼 NFS 는 이게 약하다.
  • 관리 도구: 서버 관리를 단순하게 하는 도구들. 시스템 관리 측면에서 AFS 는 "몇 광년 앞서" 있었다.

ASIDE — 워크로드의 중요성 (The Importance Of Workload): 시스템 평가에서 어려운 것 하나가 워크로드 선택이다. AFS 설계자들은 측정 경험으로 "대부분의 파일은 자주 공유되지 않고, 통째로 순차 접근된다" 고 가정했고, 그 가정하에서 AFS 설계는 완벽하게 말이 된다. 하지만 항상 맞지는 않는다. 큰 로그 파일에 주기적으로 조금씩 추가하는 응용, 트랜잭션 DB 의 랜덤 업데이트는 AFS 에 아주 곤란하다. 워크로드 연구들(Baker 등 B+91, Harter 등 H+11, Roselli 등 R+00, Vogels V99, 그리고 AFS 회고 H+88)을 참고하라.

11. 요약 (49.9)#

  • AFS 는 NFS 와 꽤 다르게 분산 FS 를 만들 수 있음을 보여 준다. 특히 프로토콜 설계가 중요하다: 파일 통째 캐싱과 callback 으로 서버 상호작용을 최소화해서 서버 하나가 많은 클라이언트를 지원하고, 사이트에 필요한 서버 수를 줄인다.
  • 단일 이름 공간, 보안, ACL 등으로 쓰기 좋다. 일관성 모델이 이해하고 추론하기 쉽고, NFS 처럼 가끔 이상한 동작을 보이지 않는다.
  • 하지만 AFS 는 쇠퇴 중이다. NFS 는 열린 표준이라 많은 업체가 지원했고, Windows 쪽 CIFS 와 함께 시장을 지배한다. AFS 의 지속적 영향은 시스템 자체보다 아이디어일 것이다. 실제로 NFSv4 는 서버 상태(open 메시지 등)를 추가해 점점 AFS 를 닮아 가고 있다 (NFSv4 의 delegation 은 callback 과 같은 발상).

(이 버전의 afs.py 는 실행하면 맨 앞에 ARG ... 줄과 내부 액션 리스트를 출력한다 — 아래에선 빈 줄과 함께 생략했다. 또 -d 값과 무관하게 invalidate file:a cache: {...} 디버그 줄이 찍힌다.)

① 문제 내기 → 직접 예측 → -c 로 확인 (README 예제)

예측: c0 의 write 는 옛 값 0 을 1 로 덮는다. c0 가 close 해서 서버가 1 이 된 뒤에 c1 이 open 하므로 c1 은 1 을 읽는다. 서버 최종값 1.

-d 1 로 서버 동작(getfile/putfile)이 보인다. c1 의 getfile 이 이미 [1] 을 받아 간다.

② callback 과 캐시 상태 보기 (-d 7) — c0 가 읽으려고 연 상태에서 c1 이 쓰고 닫는다.

읽는 법: c1 의 close → putfile → 서버가 c0 에게 callback → c0 캐시가 v=0(무효)이 된다. 하지만 c0 는 이미 파일을 열고 있으므로(r=1) 열려 있는 동안엔 옛 내용 0 을 계속 읽는다. 원문의 "open 시점의 사본" 의미론 — 다음 open 때 새로 Fetch 한다.

③ 숙제 4~5: -A oa1:w1:c1,oa1:r1:c1 에서 c1 이 읽는 값

계산: 각 클라이언트가 3개 동작(open, read/write, close)을 하므로 가능한 인터리빙은 C(6,3) = 20가지. c1 이 1 을 읽으려면 c1 의 open 이 c0 의 close 이후여야 한다(open 때 Fetch 한 사본을 읽으니까). 즉 c0 의 3동작이 c1 의 첫 동작보다 모두 앞서야 하므로 000111 단 1가지. 나머지 19가지는 0 을 읽는다. 실제로 랜덤 스케줄 시드 1~8 을 돌려 보면 c1 의 read 는 시드 4 에서만 1, 나머지 7번은 0 이었다. -S 01, -S 100011 은 둘 다 c1 의 open 이 c0 의 close 보다 앞서서 0. (-S 100011 에선 c1 의 read 직전에 invalidate 가 오지만, 이미 열린 파일이라 0.)

④ 숙제 6: 둘 다 쓰면 — last closer wins

  • -S 011100: c1 이 먼저 1 을 쓰고 close, 그 뒤 c0 가 2 를 쓰고 close → 최종 2 (c0 가 마지막 closer).
  • -S 010011: c0 가 먼저 1 을 쓰고 close, c1 이 2 를 쓰고 나중에 close → 최종 2 (이번엔 c1 이 마지막 closer).
  • 시뮬레이터는 쓰기마다 전역 카운터로 값을 매기므로 두 경우 모두 "2" 지만, 누가 쓴 2 인지가 다르다. 최종값을 결정하는 건 쓰기 순서가 아니라 close 순서다. 두 클라이언트 모두 open 시점에 0 을 Fetch 했기 때문에, 각자의 write 는 "0 → 새 값" 으로 보인다.

13. 펌웨어 엔지니어의 눈으로#

  • callback = 폴링을 인터럽트로. NVMe 호스트가 CQ 를 계속 폴링(io_uring IOPOLL, SPDK)하느냐 MSI-X 인터럽트를 받느냐의 트레이드오프와 같다. 폴링은 상태가 없고 단순하지만 아무 일 없을 때도 비용(서버 CPU / 호스트 CPU)이 든다. 인터럽트(callback)는 "변화가 있을 때만" 비용이 들지만, 통지 대상 목록(서버의 callback 표, 인터럽트 벡터/마스크 상태)을 관리해야 하고 놓친 통지를 복구하는 로직이 필요하다(8절, 인터럽트 유실 시 폴링 fallback).
  • callback 표 = 디렉터리 기반 캐시 일관성. 서버가 "누가 이 파일을 캐시하고 있나" 를 기록하고 쓰기 시 해당 클라이언트에만 무효화를 보내는 것은 멀티코어/멀티소켓 SoC 의 directory(snoop filter) 프로토콜과 똑같다. NFS 의 GETATTR 폴링은 "디렉터리 없이 매번 확인" 하는 셈. 디렉터리가 날아가면(서버 크래시) 모든 사본을 무효화하는 수밖에 없다는 점도 같다.
  • 서버 재부팅 = 휘발성 매핑 상태 유실. SSD FTL 이 DRAM 에 들고 있던 L2P 캐시/더티 상태를 SPO 로 잃으면, 부팅 시 NAND 의 메타데이터(OOB, 저널)로 재구성하기 전까지 아무것도 믿을 수 없다. AFS 서버가 callback 을 잃은 뒤 "모든 클라이언트는 캐시를 의심하라" 를 공지하는 것과 같은 상황이고, heartbeat 는 컨트롤러 watchdog / 호스트의 keep-alive(NVMe-oF Keep Alive) 와 같은 장치다.
  • 파일 통째 캐싱 vs 블록 캐싱 = 가속기의 "모델 통째 로드" vs "페이지 단위 온디맨드". 추론 가속기에 모델 가중치를 HBM/SRAM 에 통째로 올리는 방식은 AFS(첫 로드는 비싸지만 이후 전부 로컬), CUDA UVM 처럼 page fault 로 필요한 부분만 가져오는 방식은 NFS 다. 워크로드 7/11번처럼 "큰 것 중 일부만 쓰는" 경우(예: MoE 에서 일부 expert 만 활성) 통째 로드는 끔찍하게 낭비된다 — 9.2절의 10⁶배가 그대로 재현된다.
  • last closer wins = 원자적 교체(atomic replace). FW 업데이트에서 이미지를 슬롯에 통째로 쓰고 마지막에 포인터(active slot)만 바꾸는 A/B 업데이트는 "섞인 이미지" 를 막는 AFS 식 설계다. 블록 단위로 제자리 덮어쓰면 중간에 끊겼을 때 NFS 식 "A/B 혼합" 펌웨어가 된다.

14. 면접 질문#

Q1. NFS 와 AFS 의 캐싱 설계를 비교하라.#

답 보기
  • 단위/위치: NFS 는 블록을 클라이언트 메모리에, AFS 는 파일 전체를 클라이언트 로컬 디스크에.
  • 유효성 검사: NFS 는 open 시 GETATTR 폴링 + attribute cache(타임아웃), AFS 는 서버의 callback(변경 시 통지).
  • 서버 상태: NFS 는 stateless, AFS 는 callback 목록이라는 상태를 가짐.
  • 일관성 의미론: NFS 는 타임아웃에 좌우돼 추론이 어려움(가끔 stale), AFS 는 "close 시 서버 갱신 + 다른 캐시 무효화", 동시 수정은 last closer wins.
  • 결과: AFS 는 서버 부하가 낮아 확장성이 좋고 큰 파일 재읽기에 강함. NFS 는 큰 파일의 일부 접근, 덮어쓰기에 강하고 크래시 복구가 단순.

Q2. callback 이 확장성을 높이는 이유와 그 대가는?#

답 보기

callback 이 없으면 서버 부하가 open 횟수에 비례한다(매번 "바뀌었어?"). 대부분 답은 "아니" 라 낭비다. callback 은 서버가 변경이 있을 때만 연락하게 해서 부하를 변경 횟수에 비례하게 만든다 — 폴링을 인터럽트로 바꾼 것.

대가: (1) 서버가 누가 무엇을 캐시하는지 메모리에 유지해야 하고(메모리, 관리 비용), (2) 크래시 복구가 어려워진다 — 서버 재부팅 시 callback 표를 잃으므로 모든 클라이언트가 캐시를 재검증해야 하고, 클라이언트는 재부팅/분할 동안 놓친 break 때문에 캐시를 의심해야 한다. (3) 통지를 보장하려면 heartbeat 같은 장치가 필요하다.

Q3. AFS 가 NFS 보다 크게 불리한 워크로드는? 이유는?#

답 보기

큰 파일의 작은 부분을 읽거나 쓰는 워크로드(Figure 49.4 의 7, 11번). AFS 는 open 때 파일 전체를 가져오고, 수정했으면 close 때 전체를 다시 올린다 — 한 블록 쓰기에 2·NL 블록 전송. NFS 는 요청 크기만큼만. 또 기존 파일 덮어쓰기(10번)는 쓸모없는 사전 Fetch 때문에 2배. 로그 append, DB 랜덤 업데이트가 대표적인 나쁜 예. AFS 가 "파일은 대부분 통째로 순차 접근, 공유는 드묾" 이라는 워크로드 가정 위에 설계됐기 때문이다.

Q4. AFS 서버가 크래시 후 재부팅했다. 무엇이 문제고 어떻게 복구하나?#

답 보기

callback 목록은 메모리에 있어서 사라졌다. 서버는 어느 클라이언트가 어떤 파일을 캐시하는지 모르므로, 이후 파일이 바뀌어도 break 를 보낼 대상을 모른다. 클라이언트가 이 사실을 모르면 stale 캐시를 계속 쓴다.

복구: (1) 서버가 재부팅 후 모든 클라이언트에 "캐시 믿지 마" 를 통지하거나, (2) 클라이언트가 heartbeat 로 서버 재부팅(epoch 변화)을 감지. 감지한 클라이언트는 캐시된 모든 항목을 TestAuth 로 재검증한 뒤 사용한다. callback 을 lease(유효 기간 있는 약속)로 만들면 서버가 기간만 기다리면 되므로 더 견고해진다(NFSv4 delegation, 이후 분산 시스템의 lease 개념).

Q5. "last writer wins" 가 NFS 의 블록 단위 동작보다 나은 점과 한계는?#

답 보기

장점: 최종 파일이 한 클라이언트가 만든 온전한 버전이다. NFS 는 블록 flush 순서가 섞여 두 클라이언트 갱신의 혼합(깨진 JPEG 등)이 될 수 있다.

한계: 먼저 close 한 쪽의 작업은 경고 없이 통째로 사라진다(lost update). 동시 수정을 제대로 하려면 응용이 파일 잠금이나 버전 관리 같은 추가 장치를 써야 한다 — 원문 ASIDE "캐시 일관성은 만병통치약이 아니다".

15. 자가 점검 & 숙제#

퀴즈 1. 같은 기계의 두 프로세스와 다른 기계의 프로세스가 보는 갱신 시점은 어떻게 다른가?#

답 보기

같은 기계: 로컬 FS 를 공유하므로 쓰기가 즉시 보인다(UNIX 의미론). 다른 기계: 쓴 쪽이 close 해서 Store 하고 서버가 callback 을 끊은 뒤, 다음 open 에서 새 버전을 Fetch 해야 보인다. 이미 열어 둔 파일은 닫기 전까지 옛 사본을 계속 읽는다.

퀴즈 2. AFSv1 에서 서버 CPU 를 가장 많이 잡아먹은 두 가지와 AFSv2 의 해결책은?#

답 보기

(1) 전체 경로 이름을 받아 서버가 경로 탐색 → FID 도입, 클라이언트가 경로를 한 성분씩 걷고 캐시. (2) 과도한 TestAuth → callback 도입. (덤: 부하 불균형은 volume, 프로세스-per-클라이언트는 스레드로.)

퀴즈 3. Lnet = 2 ms, Ldisk = 0.5 ms 일 때 메모리보다 큰 파일의 순차 재읽기에서 AFS 는 NFS 보다 몇 배 빠른가?#

답 보기

AFS/NFS = NL·Ldisk / NL·Lnet = 0.5 / 2 = 0.25 → AFS 가 4배 빠르다. 그리고 NFS 는 그만큼 서버 부하도 더 준다.

퀴즈 4. -A oa1:w1:c1,oa1:r1:c1 에서 c1 이 1 을 읽는 스케줄은 20가지 중 몇 가지인가?#

답 보기

1가지(000111). c1 의 open 이 c0 의 close 이후여야 하는데, c1 의 open 이 c1 의 첫 동작이므로 c0 의 세 동작이 모두 먼저여야 한다.

숙제 (원문 Homework, afs.py)#

  • 질문 2 — callback 이 정확히 언제 생기나: -d 3 으로 여러 시드를 돌려 보기 → "수정된 파일이 close 되어 putfile 이 일어날 때, 그 파일을 캐시한 다른 클라이언트에게" 라는 정확한 조건을 확인하는 문제.
  • 질문 3 — 캐시 상태 예측: -c -d 7 로 각 단계의 (v, d, r) 비트를 예측 → 열린 파일은 무효화돼도 닫힐 때까지 옛 내용을 유지(refcnt)하는 의미론을 확인하는 문제.
  • 질문 6 — 최종값을 결정하는 것: -A oa1:w1:c1,oa1:w1:c1 을 여러 -S 로 → 쓰기 순서가 아니라 close 순서(last closer wins)가 최종값을 정한다는 것을 확인하는 문제.
