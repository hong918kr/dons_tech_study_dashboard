0. 한눈에 보기#

CRUX — "How can we speed up address translation, and generally avoid the extra memory reference that paging seems to require? What hardware support is required? What OS involvement is needed?" (주소 변환을 어떻게 빠르게 하고, 페이징이 요구하는 추가 메모리 접근을 어떻게 피할까? 하드웨어 지원은 무엇이 필요하고 OS는 무엇을 해야 하나?)

  • Ch.18의 선형 페이징은 모든 메모리 접근마다 PTE를 읽는 추가 접근이 붙어 2배 이상 느리다.
  • 해법: MMU 안에 자주 쓰는 VPN→PFN 변환을 담아 두는 작은 하드웨어 캐시, TLB(Translation Lookaside Buffer) — 더 정확한 이름은 "주소 변환 캐시".
  • TLB가 잘 맞는 이유는 공간 지역성(같은 페이지 안의 접근)과 시간 지역성(곧 다시 쓰는 페이지). 한 페이지에 한 번만 미스가 난다.
  • 새로 생기는 문제: TLB 미스를 누가 처리하나(HW vs OS), 컨텍스트 스위치 때 다른 프로세스의 변환을 어떻게 구분하나(flush vs ASID), 꽉 차면 무엇을 버리나(LRU vs random).
  • Don의 M2 맥에서 직접 TLB 크기를 측정해 본다 (16KB 페이지!).

3. 예제: 배열 접근 (19.2)#

8-bit 가상 주소, 16바이트 페이지 → VPN 4비트(16 페이지), offset 4비트. int a[10] 이 VA 100부터 있다.

  • 페이지가 2배(32B)였다면? a[0..6]이 VA 100~127 → 한 페이지(VPN 3: 96~127), a[7..9]는 VPN 4 → 미스 2번, 80%. 페이지가 클수록 순차 접근의 미스가 줄어든다.
  • 현실(4KB 페이지, int 4B)에서는 1024번 접근에 미스 1번 → hit rate 99.9%. 16KB 페이지(Apple Silicon)면 4096번에 1번.

TIP — 가능하면 캐시를 써라 (USE CACHING WHEN POSSIBLE) 캐시는 시스템 성능의 가장 기본 기법. 시간·공간 지역성을 이용해 작고 빠른 온칩 메모리에 복사본을 둔다. "그럼 캐시를 크게 만들면?" → 빛의 속도 같은 물리 법칙 때문에 빠른 캐시는 작을 수밖에 없다. 큰 캐시는 느리고, 그럼 의미가 없다.

3.1 새 예제 — 유효 접근 시간 (EAT) 계산#

메모리 접근 100ns, TLB 조회는 공짜라고 하자.

TLB hit rate가 99% 이상이면 페이징의 비용이 사실상 사라진다 — 원문의 "TLB가 가상 메모리를 가능하게 만들었다"는 말의 정량적 의미. (실제로는 PTE가 데이터 캐시에 있으면 워크가 훨씬 싸다.)

4. 누가 TLB 미스를 처리하나? (19.3)#

4.1 하드웨어 관리 (CISC, x86)#

하드웨어가 페이지 테이블 위치(CR3 레지스터)와 정확한 형식을 안다. 미스가 나면 HW page walker가 테이블을 걷고 TLB를 채운 뒤 재시도. OS는 테이블만 만들어 두면 된다. 단점: 페이지 테이블 형식이 하드웨어에 고정된다 (x86의 다단계 형식).

4.2 소프트웨어 관리 (RISC, MIPS R10k, SPARC v9)#

미스 시 하드웨어는 예외만 올린다 (Figure 19.3의 line 11: RaiseException(TLB_MISS)). 커널 모드로 들어가 OS의 TLB 미스 핸들러가 테이블을 찾아보고, 특권 명령어로 TLB를 갱신하고 return-from-trap.

두 가지 미묘한 점:

  1. 복귀 PC가 다르다. 시스템 콜에서 돌아올 때는 trap 다음 명령어로, TLB 미스에서 돌아올 때는 trap을 일으킨 그 명령어로 돌아가 재실행해야 한다. 그래서 하드웨어는 예외 원인에 따라 다른 PC를 저장한다 (Ch.06 LDE의 trap과 비교).
  2. 무한 TLB 미스 방지. 미스 핸들러 코드 자체가 TLB 미스를 내면? → 핸들러를 변환 없는 물리 메모리(unmapped) 에 두거나 (MIPS의 kseg0), TLB 일부를 wired(고정) 엔트리로 예약해 핸들러를 매핑.

장점: 유연성(OS 마음대로 페이지 테이블 자료구조 선택 — 해시, 역페이지 테이블 등)과 하드웨어 단순성.

ASIDE — RISC vs CISC 1980년대 대논쟁. CISC는 강력한 고수준 명령어(문자열 복사 등), RISC(버클리 Patterson, 스탠퍼드 Hennessy)는 "명령어 세트는 컴파일러의 타깃이니 단순하고 빠른 원시 연산만"을 주장. 이후 Intel이 내부에서 명령어를 micro-op으로 쪼개 RISC처럼 처리하면서 논쟁은 잦아들었다. 오늘날 ARM(RISC)도 HW page walker를 쓰므로, TLB 관리 방식은 RISC/CISC 구분과 무관해졌다.

5. TLB 안에는 무엇이? (19.4)#

전형적 TLB: 32, 64, 128 엔트리, 완전 연관(fully associative) — 변환이 어느 칸에든 있을 수 있어 모든 칸을 병렬로 비교한다. 그래서 엔트리에 VPN과 PFN 둘 다 들어 있다.

ASIDE — TLB valid 비트 ≠ 페이지 테이블 valid 비트 PTE invalid = "이 프로세스가 할당하지 않은 페이지, 접근하면 보통 프로세스 종료". TLB valid = "이 TLB 칸에 쓸 만한 변환이 들어 있나". 부팅 직후엔 모든 TLB 칸이 invalid이고, 컨텍스트 스위치 때 모든 TLB valid 비트를 0으로 만들면 이전 프로세스의 변환을 못 쓰게 된다.

6. 컨텍스트 스위치 문제 (19.5)#

P1의 VPN 10 → PFN 100, P2의 VPN 10 → PFN 170. 둘 다 TLB에 있으면 하드웨어는 어느 게 누구 것인지 모른다.

해법 1 — flush: 스위치 때 TLB 전체 무효화. HW 관리 TLB에선 PTBR(CR3)을 바꿀 때 자동으로 flush. 정확하지만 스위치마다 콜드 TLB 미스 폭탄.

해법 2 — ASID(address space identifier): TLB 엔트리에 프로세스 구분용 짧은 ID(예: 8비트)를 붙인다. OS는 스위치 때 "현재 ASID" 특권 레지스터만 바꾼다. 여러 프로세스의 변환이 공존 가능.

또 다른 경우: 서로 다른 프로세스, 다른 VPN, 같은 PFN — P1의 VPN 10과 P2의 VPN 50이 모두 PFN 101(공유 라이브러리 코드 페이지, r-x)을 가리킨다. 공유는 물리 메모리를 아낀다. (커널처럼 모든 프로세스가 같은 VPN으로 공유하는 경우엔 global 비트로 ASID 비교를 생략.)

6.1 ASID가 부족하면? (원문 질문: 256개 넘는 프로세스)#

8-bit ASID면 동시에 256개뿐. 실제 OS(예: 리눅스 arm64)는 ASID를 재활용한다: "세대(generation) 번호 + ASID"를 프로세스에 붙이고, ASID를 다 쓰면 세대를 올리고 TLB 전체를 한 번 flush 한 뒤 새로 나눠 준다. x86은 PCID 12비트(4096), arm64는 8 또는 16비트.

7. 교체 정책 (19.6)#

새 엔트리를 넣을 때 무엇을 버릴까?

  • LRU: 가장 오래 안 쓴 것. 지역성을 활용.
  • Random: 단순하고 코너 케이스에 강함. 예: TLB 크기 n, 프로그램이 n+1개 페이지를 루프로 돌면 LRU는 매번 다음에 쓸 놈을 버려 100% 미스. random은 훨씬 낫다.

8. 실제 TLB 엔트리: MIPS R4000 (19.7)#

  • G (global): 세팅되면 ASID 무시 (전역 공유 페이지).
  • ASID 8비트, C (coherence) 3비트: 캐시 정책, D (dirty), V (valid).
  • 보통 32 또는 64 엔트리. wired 레지스터로 앞쪽 몇 칸을 OS 전용으로 고정.
  • TLB 조작 특권 명령어: TLBP(probe: 있는지 검색), TLBR(read), TLBWI(지정 칸에 write), TLBWR(random 칸에 write). 이게 유저 모드에서 된다면? 아무 물리 메모리나 매핑 → 머신 탈취.

TIP — RAM은 항상 RAM이 아니다 (Culler's Law) "Random Access"라도 TLB가 커버하지 않는 페이지에 무작위 접근하면 훨씬 비싸다. 접근하는 페이지 수가 TLB coverage를 넘으면 성능이 급락한다. 아래 측정이 바로 그 증거다.

9. 요약에서 짚을 점 (19.8)#

  • TLB coverage 초과: 짧은 시간에 TLB 엔트리 수보다 많은 페이지를 만지면 미스 폭증. 해법: 큰 페이지(huge/large page) 로 한 엔트리가 덮는 범위를 늘린다 (DBMS가 즐겨 씀, Ch.20 ASIDE).
  • 물리 인덱스 캐시(physically-indexed cache) 면 캐시 접근 전에 변환이 끝나야 해서 TLB가 파이프라인 병목이 된다. 그래서 VIPT(virtually-indexed, physically-tagged) L1: 인덱스는 페이지 offset 비트로만(변환 불필요), 태그 비교는 PA로. 이 경우 L1 크기 ≤ 페이지 크기 × way 수 제약이 생긴다 — Apple M 시리즈가 16KB 페이지 덕분에 128KB L1D(8-way × 16KB) 를 VIPT로 만들 수 있는 이유 중 하나다.

10. 직접 해보기 — 내 맥의 TLB 측정하기#

10.1 코드#

원문 Homework(Measurement)의 tlb.c 를 구현. 고려한 점(숙제 Q1, Q5~Q7 답):

  • 페이지 크기: 하드코딩 금지. getpagesize() = sysconf(_SC_PAGESIZE) = Apple Silicon에서 16384. 4096으로 가정하면 한 페이지 안을 4번 찍게 되어 TLB 크기를 4배로 잘못 잰다.
  • 타이머(Q1): gettimeofday() 는 µs 해상도라 한 번 접근(~1ns)을 못 잰다 → clock_gettime(CLOCK_MONOTONIC_RAW) 로 수억 번 접근을 묶어서 재고 나눈다.
  • 컴파일러 최적화(Q5): 결과(checksum)를 출력해 루프가 "쓸모없다"고 제거되지 않게 한다. 스펙대로 -O0.
  • 코어 고정(Q6): macOS는 스레드를 특정 코어에 pin하는 API가 없다(affinity는 힌트일 뿐). 대신 QoS를 USER_INTERACTIVE로 올려 P-core에서 돌 확률을 높였다. (Linux면 sched_setaffinity / taskset -c 0.)
  • demand zero(Q7): 측정 전에 배열을 한 번 다 써서 첫 접근 페이지 폴트를 측정 밖으로 뺐다.
  • 캐시 set 충돌 함정 (원문에 없는 추가): 페이지마다 같은 offset을 찍으면 모든 접근이 L1D의 같은 set에 몰려 TLB가 아니라 캐시 충돌을 재게 된다. 그래서 페이지마다 128B(캐시 라인 크기)씩 offset을 엇갈렸다.
  • 두 가지 모드: 원문 그대로의 a[i] += 1 루프(접근끼리 독립 → 아웃오브오더 CPU가 미스 여러 개를 겹쳐서 처리해 미스 비용이 가려짐)와, 무작위 순서 포인터 추적(다음 주소가 이전 load 결과 → 지연이 그대로 드러남).

10.3 해석#

  • 포인터 추적: 256페이지(4MB)까지 ~0.9ns(≈ 3.5GHz에서 3사이클, L1 hit + L1 TLB hit). 512페이지에서 2.9ns로 점프 → 1단계 데이터 TLB는 256~512 엔트리 사이. 데이터 자체는 페이지당 128B 한 줄씩이라 512 × 128B = 64KB로 L1D(128KB, sysctl hw.perflevel0.l1dcachesize)에 들어가므로, 이 점프는 캐시가 아니라 TLB 탓이다.
  • 2048 → 4096페이지(32MB → 64MB)에서 7.8 → 17ns → 2단계 TLB도 넘침. 2단계 TLB 커버리지는 32MB와 64MB 사이(공개 분석들이 말하는 M1/M2 P-core L2 TLB 약 3072 엔트리 × 16KB = 48MB와 일치). 이후는 페이지 테이블 워크 비용 (PTE가 L2 캐시에 있으므로 DRAM 왕복보다는 싸다).
  • 원문 방식 루프: 1단계 TLB 경계가 거의 안 보이고(1.1~1.2ns 평탄), 2048~4096에서만 ~5.5ns로 오른다. 접근끼리 의존성이 없어 CPU가 여러 TLB 미스를 동시에 처리(memory-level parallelism) 해 비용을 숨긴 것. 원문(2000년대 x86)이 5ns→20ns→70ns 계단을 본 것과 달리, 현대 코어에선 측정 방법 자체가 결과를 바꾼다.
  • 1~4페이지에서 시간이 오히려 큰 것(3.0ns)은 TLB와 무관한 루프 오버헤드 + 같은 주소에 대한 store→load 의존성 때문이다 (원소가 적으면 같은 원소를 바로 다시 갱신).
  • 측정 노이즈(숙제 Q3): 같은 설정을 여러 번 돌리면 이렇게 흔들린다.

trials가 1~10이면 타이머·콜드 미스가 지배해 엉터리(177ns, 35ns)이고, 충분히 반복해도 run-to-run으로 2배 가까이 흔들린다 (스윕은 3회 중 최솟값을 써서 5.5ns). 원인 후보: P/E 코어 이동, 다른 프로세스(이 맥은 측정 당시 메모리 압박으로 compressor가 활발했다), DVFS. 그래서 절대값보다 "계단의 위치"를 읽어야 한다.

주의 — 측정 한계. Apple은 TLB 구성을 공식 공개하지 않는다. 위 수치는 "이 측정 방법으로 본 경계"이며, 엔트리 수를 정확히 확정하려면 2의 거듭제곱 사이를 더 촘촘히 스윕해야 한다.

11. 펌웨어 엔지니어의 눈으로#

  • SSD FTL의 매핑 캐시 = TLB. DRAM-less SSD나 DFTL 계열은 L2P 테이블 전체를 못 올려서 자주 쓰는 매핑만 SRAM/DRAM에 캐시(CMT: cached mapping table)하고, 미스면 NAND에서 매핑 페이지를 읽는다 = 페이지 테이블 워크. 순차 워크로드 hit rate가 높고 랜덤 4K에서 떨어지는 것도 TLB coverage 문제와 같은 구조다.
  • IOMMU/SMMU에도 TLB(IOTLB)가 있다. 드라이버가 IO 페이지 테이블을 바꾼 뒤 명시적 무효화(Arm SMMUv3의 CMD_TLBI_NH_VA + CMD_SYNC, Apple DART의 TLB flush 레지스터)를 안 하면 디바이스가 옛 PA로 DMA 한다 — 메모리 오염 버그의 단골. 무효화 비용 때문에 리눅스는 IOVA 해제를 모아서 flush하는 "lazy/flush queue" 모드를 쓴다 (원문의 flush 비용 논의와 같은 트레이드오프).
  • PCIe ATS / ATC: 디바이스(NIC, GPU, NPU)가 자기 안에 변환 캐시(ATC) 를 두고 IOMMU에 번역을 요청한다. 이건 "디바이스 쪽 TLB"이고, OS는 무효화 시 ATS Invalidate 메시지를 보내 완료를 기다려야 한다. PCIe 디버깅 경험이 있는 Don에게 TLP 레벨에서 보이는 TLB 프로토콜이다.
  • GPU/AI 가속기: GPU는 SM마다 L1 TLB, 공유 L2 TLB를 두고 2MB 큰 페이지를 기본으로 쓴다 (텐서 수십 GB를 4KB로 매핑하면 coverage가 턱없이 부족). 가속기 펌웨어/드라이버 면접에서 "왜 huge page?"의 답은 결국 TLB reach다.
  • ASID ≈ 커맨드 큐별 컨텍스트 ID. GPU/SMMU는 스트림 ID / PASID 로 여러 프로세스의 변환을 구분해 TLB에 공존시킨다 (SMMU의 StreamID + SubstreamID(PASID), 원문 ASID의 디바이스 버전).

12. 면접 질문#

Q1. TLB 미스 시 x86과 MIPS는 각각 무슨 일이 일어나나?#

답 보기
  • x86 (HW 관리): MMU의 page walker가 CR3부터 4단계 테이블을 걷고 TLB를 채운 뒤 명령어를 재시도. OS 개입 없음. 형식이 HW에 고정.
  • MIPS (SW 관리): TLB refill 예외 → 커널 핸들러가 테이블을 찾아 TLBWR 로 채우고 예외를 낸 명령어로 복귀. 핸들러는 unmapped 영역(kseg0)이나 wired 엔트리에 둬 재귀 미스를 막는다.
  • 공통: PTE가 invalid/권한 위반이면 결국 OS 예외 처리.

Q2. 컨텍스트 스위치 때 TLB는 어떻게 처리하나? ASID가 모자라면?#

답 보기
  • 단순: 전체 flush (CR3 쓰기 시 자동). 정확하지만 스위치 후 콜드 미스.
  • ASID/PCID: 엔트리에 주소 공간 태그 → flush 없이 공존. OS는 현재 ASID 레지스터만 변경.
  • 커널 매핑은 global 비트로 ASID 비교 생략.
  • 부족하면 generation + 재활용: 다 쓰면 세대 증가 후 한 번 전체 flush. (x86 PCID 12bit, arm64 8/16bit.)
  • 보너스: 멀티코어에서 PTE를 바꾸면 다른 코어의 TLB도 무효화해야 함 → TLB shootdown(IPI 또는 arm64의 broadcast TLBI ...IS).

Q3. TLB 크기는 어떻게 측정하나? 함정은?#

답 보기
  • 페이지당 한 원소씩 N개 페이지를 반복 접근, N을 2배씩 늘리며 접근당 시간의 계단을 찾는다 (Saavedra-Barrera).
  • 함정: 페이지 크기 하드코딩(Apple 16KB), 타이머 해상도(수억 번 묶어 측정), 컴파일러 제거(결과 사용), 코어 이동(pinning), demand-zero 폴트(미리 초기화), 캐시 set 충돌(offset 엇갈리기), MLP로 미스 은닉(포인터 추적으로 의존성 만들기).

Q4. huge page는 왜 쓰고, 단점은?#

답 보기
  • TLB coverage 증가: 4KB × 1536 = 6MB vs 2MB × 1536 = 3GB. 큰 랜덤 접근 자료구조(DB 버퍼 풀, ML 텐서, GPU 메모리)에서 미스 급감. 페이지 테이블 워크도 한 단계 짧아짐.
  • 단점: 내부 단편화, 연속 물리 메모리 확보 어려움(compaction 필요), 스왑/페이지 폴트 단위가 커져 지연 증가, fork/COW 비용.
  • 리눅스: hugetlbfs(명시적), THP(투명). macOS arm64는 기본 16KB로 중간 해법.

Q5. VIPT 캐시는 무엇이고 TLB와 어떤 관계인가?#

답 보기
  • Virtually Indexed Physically Tagged: set 인덱스를 페이지 offset 비트로만 뽑아 TLB 조회와 캐시 조회를 병렬로. 태그 비교는 TLB가 준 PA로.
  • 인덱스+라인 offset 비트가 페이지 offset 안에 있어야 aliasing이 없으므로 캐시 크기 ≤ 페이지 크기 × 연관도. 16KB 페이지 × 8-way = 128KB → Apple M 시리즈의 큰 L1D가 가능한 이유.

Q6. 디바이스 드라이버에서 IOMMU 매핑을 해제한 직후 버퍼를 재사용했더니 데이터가 깨졌다. 원인은?#

답 보기
  • IOTLB(또는 디바이스 ATC) 무효화 누락/지연: IO 페이지 테이블에서 PTE를 지웠지만 IOMMU TLB에 옛 변환이 남아 있어 디바이스의 늦은 DMA가 재사용된 프레임에 써짐.
  • 해결: unmap 후 TLBI + sync 완료 대기(SMMU CMD_SYNC, ATS invalidate completion) 후에 프레임 해제. lazy flush 모드라면 flush queue가 비워질 때까지 프레임을 재사용하지 않도록.

13. 자가 점검 & 숙제#

퀴즈 1. 64엔트리 TLB, 4KB 페이지의 coverage는? 16KB 페이지면?#

답 보기

64 × 4KB = 256KB, 64 × 16KB = 1MB. 같은 TLB로 4배 넓게 본다.

퀴즈 2. 원문 배열 예제에서 페이지가 8바이트면 hit rate는?#

답 보기

VA 100~139, 페이지 8B → 페이지당 int 2개. a[0] (VA 100–103)은 VPN 12(96~103)의 뒷절반에 혼자, a[1]·a[2]는 VPN 13, a[3]·a[4]는 VPN 14, a[5]·a[6]은 VPN 15, a[7]·a[8]은 VPN 16, a[9]는 VPN 17. 미스 = VPN 12~17 각 1회 = 6회, hit 4회 → 40%.

퀴즈 3. TLB valid=0 과 PTE valid=0 의 차이를 한 문장씩.#

답 보기

TLB valid=0: "이 TLB 칸은 비어 있다(캐시 미스일 뿐)". PTE valid=0: "이 가상 페이지는 할당되지 않았다(접근하면 보통 프로세스 종료)".

퀴즈 4. SW 관리 TLB에서 미스 핸들러 복귀 PC가 syscall 복귀 PC와 다른 이유는?#

답 보기

syscall은 요청을 완료했으니 다음 명령어로 가야 하고, TLB 미스는 명령어가 실행되지 못했으니 같은 명령어를 재실행해야 한다.
