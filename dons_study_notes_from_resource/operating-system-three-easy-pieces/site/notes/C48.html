0. 한눈에 보기#

CRUX: HOW TO BUILD A DISTRIBUTED FILE SYSTEM — "How do you build a distributed file system? What are the key aspects to think about? What is easy to get wrong? What can we learn from existing systems?" (분산 파일 시스템은 어떻게 만드나? 핵심 고려사항은? 무엇을 틀리기 쉬운가? 기존 시스템에서 무엇을 배울까?)

THE CRUX: HOW TO DEFINE A STATELESS FILE PROTOCOL — "How do we define the protocol to both be stateless and support the POSIX file system API?" (상태 없는(stateless) 프로토콜이면서 POSIX 파일 API 를 지원하려면 프로토콜을 어떻게 정의해야 하나?)

  • NFSv2 의 설계 목표는 단 하나: 서버 크래시로부터의 단순하고 빠른 복구.
  • 수단은 stateless 서버: 서버는 클라이언트에 대해 아무것도 기억하지 않는다. 모든 요청이 파일 핸들(volume, inode, generation) + 절대 offset 등 필요한 정보를 다 담는다.
  • 그 덕에 대부분의 연산이 멱등(idempotent) → 클라이언트는 무슨 실패든 "그냥 다시 보내면" 된다.
  • 성능을 위한 클라이언트 캐싱이 캐시 일관성 문제를 낳고, NFS 는 이를 flush-on-close + GETATTR + attribute cache 로 "대충" 푼다 → 가끔 이상한 동작.
  • 서버는 WRITE 를 안정 저장소에 커밋한 뒤에야 성공을 돌려줘야 한다 → NVRAM, WAFL 같은 산업이 여기서 탄생.

2. 기본적인 분산 파일 시스템 (도입, 48.1)#

클라이언트 여러 대 + 서버 한 대(또는 몇 대). 서버가 디스크에 데이터를 저장하고, 클라이언트는 잘 정의된 프로토콜 메시지로 데이터를 요청한다.

왜 이렇게 하나? 그냥 로컬 디스크를 쓰면 안 되나?

  • 쉬운 공유: Client 0 에서 작업하다 Client 2 로 옮겨도 같은 파일 시스템이 보인다.
  • 중앙 관리: 백업을 수많은 클라이언트가 아니라 몇 대의 서버에서만.
  • 보안: 서버를 잠긴 기계실에 두면 물리적 위협이 줄어든다.

구조는 두 소프트웨어 조각으로 이루어진다.

  • client-side file system: 응용이 부르는 open() read() write() close() mkdir() 등을 받아, 필요한 프로토콜 메시지로 바꿔 서버에 보낸다. 응용 입장에선 로컬 FS 와 똑같다(성능만 빼고) — 투명한 접근(transparent access).
  • file server: 메시지를 받아 디스크(또는 자기 메모리 캐시)에서 블록을 읽어 돌려준다.

read() 한 번의 흐름: 응용 read() → client-side FS 가 서버에 "블록 X 읽어 줘" → 서버가 디스크/캐시에서 읽어 응답 → client-side FS 가 사용자 버퍼에 복사 → 완료. 같은 블록을 다시 읽으면 클라이언트 메모리(또는 로컬 디스크) 캐시에서 해결되어 네트워크 트래픽 0 일 수도 있다.

ASIDE — 서버는 왜 죽나 (Why Servers Crash): 정전, 수십만~수백만 줄 코드의 버그(좋은 코드도 수백~수천 줄당 몇 개), 메모리 누수, 그리고 네트워크 분할(partition) — 클라이언트와 서버가 둘 다 멀쩡한데 서로 통신만 안 되면, 클라이언트 입장에선 서버가 죽은 것과 구분이 안 된다.

3. NFS 의 등장 (48.2) — 열린 프로토콜#

Sun 은 독자적인 폐쇄 시스템 대신 열린 프로토콜(open protocol) — 클라이언트와 서버가 주고받는 메시지 형식만 정확히 규정 — 을 공개했다. 그래서 여러 회사가 NFS 서버를 만들어 경쟁하면서도 상호 운용이 됐다(Oracle/Sun, NetApp, EMC, IBM...). NFS 의 성공은 이 "열린 시장" 전략 덕이 크다.

4. 초점: 단순하고 빠른 서버 크래시 복구 (48.3)#

이 장은 오랫동안 표준이었던 NFSv2 를 다룬다(v3 는 작은 변경, v4 는 큰 변경). 다중 클라이언트-단일 서버 환경에서는 서버가 죽은 1분 = 모든 클라이언트 사용자가 멈춘 1분이다. 그래서 목표는 빠르고 단순한 서버 크래시 복구.

5. 빠른 복구의 열쇠: 상태 없음 (48.4)#

NFSv2 는 stateless 프로토콜로 설계됐다. 서버는 어느 클라이언트가 어느 블록을 캐시하는지, 어떤 파일을 열었는지, 파일 포인터가 어디인지 — 아무것도 추적하지 않는다. 각 요청이 그 요청을 처리하는 데 필요한 정보를 모두 담는다.

반례: stateful 한 open()#

만약 client-side FS 가 서버에 "foo 를 열고 descriptor 를 줘" 라고 보내고, 서버가 자기 쪽에서 열어 fd 를 돌려준다면? 이후 read 는 "이 fd 로 몇 바이트 읽어 줘" 가 된다. 이때 fd 는 클라이언트와 서버가 공유하는 상태 — Ousterhout 의 표현으로 분산 상태(distributed state) — 다.

이 공유 상태가 크래시 복구를 망친다.

  • 서버 크래시: 첫 read 후 서버가 죽었다가 살아났다. 두 번째 read 가 fd 를 들고 오지만, fd→파일 매핑은 메모리에만 있었으므로 사라졌다. 복구하려면 클라이언트가 "fd 3 은 foo 였어" 같은 정보를 들고 있다가 서버에 다시 알려주는 복구 프로토콜이 필요하다.
  • 클라이언트 크래시: 클라이언트가 파일을 열고 죽으면 close() 가 영원히 안 온다. 서버는 fd 자원을 언제 회수해야 하나? 클라이언트가 죽었다는 걸 감지해야 한다 — 이것도 어려운 문제.

그래서 NFS 는 각 클라이언트 연산이 필요한 정보를 다 담는 stateless 방식을 택했다. 서버는 그냥 다시 켜지면 끝, 클라이언트는 최악의 경우 요청을 재시도하면 된다.

7. 프로토콜에서 분산 파일 시스템으로 (48.6)#

client-side FS 가 열린 파일 상태를 전부 추적하고, 응용 요청을 프로토콜 메시지로 번역한다. 서버는 들어오는 메시지에 응답만 한다.

포인트 세 가지:

  1. 클라이언트가 모든 상태를 가진다: fd → 파일 핸들 매핑, 현재 파일 위치. 응용의 read() 에는 offset 이 없지만, client-side FS 가 현재 위치를 offset 으로 바꿔 넣는다.
  2. 서버와의 대화 시점: 처음 open 때 LOOKUP. 경로가 길면 경로 성분마다 하나씩 — /home/remzi/foo.txt 는 LOOKUP 3번(/에서 home, home 에서 remzi, remzi 에서 foo.txt).
  3. 각 요청이 자급자족: 서버는 요청 하나만 보고 완전히 처리할 수 있다. 이것이 크래시에서 우아하게 복구하는 비결이다.

계산 예제: 메시지 수 세기#

/home/remzi/notes/a.txt (경로 성분 4개, 크기 20 KB, NFS 블록 8 KB)를 열어 끝까지 읽고 닫는다. 캐시는 비어 있다.

  • LOOKUP: home, remzi, notes, a.txt → 4
  • READ: ⌈20 / 8⌉ = 3 (offset 0, 8192, 16384)
  • close: 0
  • 합계 7 RPC = 14 메시지(요청+응답). 같은 경로의 다른 파일 b.txt 를 이어서 열면, 디렉터리 핸들을 캐시했다면 LOOKUP 1번만 추가.

8. 멱등 연산으로 서버 실패 다루기 (48.7)#

클라이언트가 요청을 보냈는데 응답이 안 온다. 원인은 세 가지(Figure 48.6).

클라이언트는 이 셋을 구분할 수 없다. NFSv2 의 답은 단순하고 우아하다: 그냥 재시도한다. 타이머를 걸고, 만료되면 같은 요청을 다시 보낸다.

이게 가능한 이유가 멱등성(idempotency): 연산을 여러 번 해도 한 번 한 것과 효과가 같다.

  • 메모리에 값을 세 번 store = 한 번 store → 멱등
  • 카운터를 세 번 increment ≠ 한 번 → 비멱등
  • 읽기만 하는 연산은 당연히 멱등. 쓰는 연산은 따져 봐야 한다.
연산멱등?이유
LOOKUP, GETATTR, READ예읽기만 함
WRITE(FH, offset, count, data)예정확한 offset 을 담고 있어 몇 번을 써도 같은 결과

(가상) APPEND(FH, data)아니오재시도마다 끝에 또 붙음 — 그래서 NFS 에는 없다

WRITE 가 멱등이라는 것이 핵심이다. Case 1 이면 재시도가 처음 실행, Case 2 면 서버가 살아난 후 재시도가 처음 실행, Case 3 이면 서버가 같은 데이터를 같은 위치에 한 번 더 쓴다 — 결과는 같다. 손실과 서버 실패를 하나의 방식으로 처리한다. Ch.47 에서 at-most-once 를 위해 서버가 들고 있어야 했던 "중복 제거 테이블" 이 아예 필요 없어진다.

TIP — 멱등성은 강력하다 (Idempotency Is Powerful): 여러 번 실행해도 되는 연산은 실패 처리가 쉽다 — 그냥 재시도하면 된다.

mkdir 같은 예외: 서버가 MKDIR 을 성공적으로 실행했는데 응답이 유실되면, 재시도는 "이미 존재함" 으로 실패한다. 실제로는 성공했는데 클라이언트는 실패를 본다.

TIP — 완벽은 좋음의 적이다 (Perfect Is The Enemy Of The Good, Voltaire's Law): mkdir 을 멱등하게 재설계할 수도 있지만 굳이? NFS 는 중요한 경우를 잘 처리하고 전체 설계를 깔끔하게 유지한다. 완벽하지 않음을 받아들이고 시스템을 만드는 것이 좋은 엔지니어링이다. (실제 NFS 서버들은 최근 응답을 기억하는 duplicate request cache 로 이런 경우를 상당 부분 땜질한다 — 엄밀한 stateless 에서 살짝 벗어난 실용적 타협.)

9. 성능 향상: 클라이언트 캐싱 (48.8)#

모든 read/write 가 네트워크를 타면 느리다. 네트워크는 로컬 메모리나 디스크보다 보통 느리다. 해법: 클라이언트 캐싱.

  • 읽기 캐시: 서버에서 읽은 데이터(와 메타데이터)를 클라이언트 메모리에 둔다. 첫 접근은 비싸도 이후는 빠르다.
  • 쓰기 버퍼: 응용의 write() 는 클라이언트 캐시에만 넣고 즉시 성공 반환, 나중에 서버로 보낸다. 응용의 write 지연을 실제 쓰기 성능과 분리(decouple).

그럼 다 됐나? 아니다. 여러 클라이언트 캐시가 생기면 캐시 일관성 문제가 생긴다.

10. 캐시 일관성 문제 (48.9)#

클라이언트 셋, 서버 하나, 파일 F.

  • C1 이 F 를 읽어 F[v1] 을 캐시.
  • C2 가 F 를 덮어써서 F[v2] 를 만들었는데 아직 자기 캐시에만 있다.
  • C3 는 아직 F 에 접근 안 함.

하위 문제가 두 개다.

  1. update visibility (갱신 가시성): C2 가 쓰기를 버퍼링하는 동안 C3 가 F 를 열면 옛 버전 v1 을 받는다. "C2 에서 고치고 C3 로 로그인했더니 옛날 파일이!" — 다른 클라이언트의 갱신은 언제 보이게 되나?
  2. stale cache (낡은 캐시): C2 가 결국 서버로 flush 해서 서버는 v2 인데, C1 은 여전히 캐시의 v1 을 읽는다.

NFSv2 구현의 해법도 두 개다.

  • flush-on-close (close-to-open 일관성): 파일을 쓰고 닫을 때 클라이언트가 모든 더티 페이지를 서버로 flush. 그러면 이후 다른 노드가 open 하면 최신 버전을 본다. → 문제 1 해결.
  • open 시 GETATTR 검사: 캐시된 내용을 쓰기 전에 GETATTR 로 서버의 수정 시각을 가져와, 캐시에 들여온 시각보다 최신이면 무효화(invalidate) 하고 서버에서 다시 읽는다. 아니면 캐시 사용. → 문제 2 해결.

새 문제: GETATTR 폭주 → attribute cache#

Sun 팀이 이걸 구현하자 서버가 GETATTR 요청에 파묻혔다. 흔한 경우는 "한 클라이언트만 반복해서 접근" 인데도 매번 "누가 이거 바꿨어?" 를 물으니, 대부분 답은 "아니" 였다.

좋은 엔지니어링 원칙: 흔한 경우(common case)를 위해 설계하고 그걸 잘 동작하게 하라.

그래서 attribute cache 를 추가했다. 속성은 처음 접근 때 캐시에 들어가고 일정 시간(예: 3초) 뒤 만료된다. 그 3초 동안은 서버에 묻지 않고 캐시된 파일을 그냥 쓴다.

계산 예제: GETATTR 부하#

클라이언트 50대, 각자 자기 파일을 0.5초마다 열어 읽는다(공유 없음). 60초 동안 서버가 받는 검증 요청은?

  • attribute cache 없음: 50 × (60 / 0.5) = 50 × 120 = 6000 GETATTR
  • 3초 attribute cache: 50 × (60 / 3) = 1000 GETATTR (6배 감소)
  • 대가: 다른 클라이언트가 파일을 바꾼 뒤 최대 3초 동안 stale read 가능.

(아래 "직접 해보기" 의 실제 NFS 트레이스에서도 요청의 절반 이상이 속성 요청이다.)

11. NFS 캐시 일관성 평가 (48.10)#

  • flush-on-close 의 성능 문제: 잠깐 만들었다 곧 지우는 임시 파일도 close 때 서버로 강제 전송된다. 이상적이라면 지워질 때까지 메모리에만 두어 서버 통신을 아예 없앨 텐데.
  • attribute cache 의 의미론 문제: 지금 받은 게 어느 버전인지 추론하기가 매우 어렵다. 최신일 때도 있고, attribute cache 가 아직 만료 안 돼서 옛 버전일 때도 있다. 대부분 괜찮지만 가끔(지금도!) 이상한 동작이 나온다.

NFS 는 구현 세부사항이 사용자가 관찰하는 의미론(semantics)을 정의해 버린 흥미로운 사례다 — 원래는 의미론을 먼저 정하고 구현이 따라야 하는데 거꾸로 됐다. (다음 장 AFS 는 이 점을 정면으로 고친다.)

12. 서버 쪽 write buffering 의 함정 (48.11)#

서버도 메모리가 많아서 읽은 데이터/메타데이터를 캐시한다(읽기 성능 소폭 향상). 문제는 쓰기다.

NFS 서버는 WRITE 를 안정 저장소(stable storage) 에 강제로 쓰기 전에는 절대 성공을 응답하면 안 된다.

왜? 클라이언트가 세 블록을 순서대로 덮어쓴다고 하자.

  1. 첫 WRITE: 서버가 디스크에 쓰고 성공 응답.
  2. 둘째 WRITE: 서버가 메모리에만 두고 성공 응답 → 디스크에 쓰기 전에 크래시.
  3. 서버 재부팅 후 셋째 WRITE 성공.

클라이언트는 셋 다 성공으로 알지만 파일은 aaaa / yyyy / cccc — 옛 블록이 끼어 있다. 응용에 따라 재앙. 클라이언트의 복구 전략("응답 없으면 재시도")은 서버가 성공이라고 말하지 않았을 때만 작동하기 때문이다. 성공이라고 해 놓고 잃어버리면 클라이언트는 재시도할 이유가 없다.

결론: 서버는 커밋 후 응답해야 하고, 그러면 쓰기 성능이 병목이 된다. 이걸 풀려고 회사가 생겼다 — Network Appliance(NetApp):

  • 트릭 1: 쓰기를 먼저 배터리 백업 메모리(NVRAM) 에 넣는다 → 데이터 잃을 걱정 없이 즉시 응답, 디스크 쓰기는 나중에.
  • 트릭 2: 디스크에 빨리 쓰도록 특별히 설계된 FS (WAFL, LFS 의 영향 — Ch.43).

(참고: NFSv3 는 WRITE(UNSTABLE) + COMMIT 을 도입해 "일단 버퍼링해도 되지만 COMMIT 응답 전까지는 클라이언트가 데이터를 들고 있다가, 서버 재부팅(verifier 변화)을 감지하면 다시 보낸다" 는 방식으로 이 성능 문제를 완화했다.)

13. 요약 (48.12)#

  • NFS 는 서버 실패 앞에서 단순하고 빠른 복구를 중심으로, 신중한 프로토콜 설계로 그 목표를 이뤘다.
  • 멱등성이 핵심: 실패한 연산을 안전하게 재실행할 수 있으니, 서버가 실행했든 안 했든 그냥 재시도하면 된다.
  • 다중 클라이언트-단일 서버에 캐싱을 넣으면 캐시 일관성 문제가 생기고, NFS 는 이를 다소 임시방편(ad hoc) 으로 풀어서 가끔 이상한 동작이 관찰된다.
  • 서버 캐싱도 까다롭다: 서버로의 쓰기는 성공 응답 전에 안정 저장소에 강제 기록되어야 한다.
  • 다루지 않은 것: 보안. 초기 NFS 는 아무 클라이언트 사용자나 다른 사용자인 척하기 쉬웠다. 이후 Kerberos 같은 인증 서비스와 통합되며 개선됐다.

14.1 C 코드: 멱등성, 파일 핸들 generation, 서버 write buffering#

세 가지를 한 프로그램으로 확인한다.

  1. 진짜 파일로: NFS 식 pwrite(offset 지정) 를 3번 재시도 vs O_APPEND write() 를 3번 재시도.
  2. 작은 in-memory 서버로: inode 재사용 시 generation 번호가 옛 핸들을 ESTALE 로 막는 것.
  3. 원문의 x/y/z → a/b/c 예제: 서버가 메모리에만 두고 성공 응답한 뒤 크래시하는 경우 vs 커밋 후 응답.

해석:

  • [1] offset 을 담은 WRITE 는 3번 보내도 16바이트 그대로 — 재시도가 무해하다. 반면 "현재 끝에 붙여라" 는 재시도마다 8바이트씩 늘어 32바이트. 서버가 "현재 위치" 라는 상태에 의존하는 연산은 멱등이 아니다. NFS 가 append 를 프로토콜에 두지 않고 클라이언트가 파일 크기(attributes)를 보고 offset 을 계산하게 한 이유다. (그래서 NFS 위에서 여러 클라이언트가 동시에 O_APPEND 하면 서로 덮어쓸 수 있다 — 유명한 함정.)
  • [2] 같은 inode 0 이 재사용됐지만 generation 이 1 → 2 로 바뀌어, 옛 핸들은 ESTALE 로 거부된다. generation 이 없었다면 client A 가 secret.key 를 읽었을 것.
  • [3a] 원문 그림 그대로 aaaa / yyyy / cccc — 클라이언트는 모두 성공으로 알고 있다. [3b] 커밋 후 응답하면 크래시 시점과 관계없이 정상.

14.2 OSTEP dist-nfs: 실제 NFS 트레이스 들여다보기#

.tools/ostep-homework/dist-nfs 에는 시뮬레이터가 아니라 Berkeley Auspex NFS 트레이스 샘플(sampleTrace.csv, 1000줄)만 들어 있다(README: "Traces can be found here: http://iotta.snia.org/traces/nfs"). 각 줄은 시각 연산종류 READ/RW FID: <파일ID> OFF: <offset> SIZE: <크기> HOST: <클라이언트> 형식이다. 최신판 OSTEP 숙제처럼 awk 로 통계를 내 본다.

해석:

  • 약 118초 동안 클라이언트 52대가 파일 184개에 요청 1000개를 보냈다.
  • 요청 1000개 중 512개(51 %)가 Attr(속성) 요청이다. 실제 데이터 블록 읽기(Block)는 389개(39 %)뿐. 10절에서 본 "서버가 GETATTR 에 파묻혔다" 는 이야기가 실제 트레이스 숫자로 보인다 — attribute cache 가 있어도 이 정도다.
  • Close 는 10개뿐인데 Open 은 64개다. NFSv2 프로토콜에는 open/close 메시지 자체가 없으므로, 이 트레이스의 Open/Close 는 트레이스 수집 도구가 요청 패턴으로부터 추정해 붙인 이벤트로 보인다(추정 — README 에 형식 설명이 없다). 어쨌든 서버 입장에선 close 를 알 길이 없다는 stateless 의 성격과 맞아떨어진다.
  • 블록 요청 크기는 1 KB, 8 KB, 4 KB 순. 8 KB 는 NFSv2 READ/WRITE 한 번의 최대 전송 크기다.

15. 펌웨어 엔지니어의 눈으로#

  • "WRITE 는 안정 저장소에 쓴 뒤에 성공" = SSD 의 volatile write cache 와 FUA/Flush. NVMe 컨트롤러가 DRAM 쓰기 캐시를 쓰면서 completion 을 일찍 올리는 것은 정확히 48.11 의 서버 write buffering 이다. 그래서 호스트는 FUA 비트나 Flush 커맨드로 "안정 저장소까지" 를 요구하고, 엔터프라이즈 SSD 는 PLP(power-loss protection) 커패시터로 DRAM 내용을 정전 시 NAND 에 덤프한다 — NetApp 의 NVRAM 트릭과 같은 발상이다. Don 이 겪은 SPO(sudden power off) 복구 테스트의 "ack 된 쓰기는 반드시 살아 있어야 한다" 는 판정 기준이 바로 이 규칙이다.
  • LBA 기반 쓰기는 멱등, Zone Append 는 비멱등. NVMe Write(LBA, data)는 NFS WRITE(FH, offset)처럼 몇 번 재실행해도 같은 결과라서, 호스트가 타임아웃/리셋 후 재발행해도 안전하다. 반면 ZNS 의 Zone Append 는 "현재 write pointer 에 붙여라" 라 [1]의 O_APPEND 와 같은 비멱등 연산 — 리셋 후 재시도하면 데이터가 두 번 기록될 수 있어 호스트 FS 가 반환된 LBA 를 보고 중복을 처리해야 한다.
  • stateless 서버 ↔ 컨트롤러 리셋 복구. NVMe 컨트롤러 리셋 후 in-flight 커맨드 상태는 사라지고, 호스트 드라이버가 재발행한다. 컨트롤러 FW 가 "호스트가 뭘 하다 말았는지" 를 기억할 필요가 없게 커맨드가 자급자족(LBA, 길이, PRP)이기 때문에 가능한 설계다. 반대로 상태가 있는 기능(예: 진행 중이던 Sanitize, Format, FW activate)은 전원 손실 후 복구 시퀀스를 따로 설계해야 한다 — 48.4 의 "공유 상태가 복구를 어렵게 한다" 그대로.
  • generation 번호 = 재사용되는 식별자의 ABA 방지. NVMe CID 나 DMA 디스크립터 슬롯, IOMMU(DART) 매핑 ID 를 재사용할 때 generation/phase 비트를 붙이는 것과 같다. NVMe CQ 의 phase tag 가 큐가 한 바퀴 돌 때마다 뒤집혀 "이 엔트리가 이번 바퀴 것인지" 를 판별하는 것이 바로 generation 번호의 1비트 버전이다.
  • flush-on-close / GETATTR 무효화 = non-coherent DMA 의 cache clean / invalidate. 하드웨어 coherence 가 없는 SoC 에서 CPU 가 버퍼를 써서 디바이스에 넘길 땐 clean(flush) 을, 디바이스가 쓴 결과를 읽기 전엔 invalidate 를 해야 한다. "언제 flush 하고 언제 무효화하나" 라는 NFS 의 캐시 일관성 질문과 구조가 같고, 타이밍을 대충 정하면 "가끔 옛 데이터를 본다" 는 NFS 식 이상 동작이 그대로 나온다.

16. 면접 질문#

Q1. NFSv2 가 stateless 를 택한 이유와 대가는?#

답 보기

목표는 빠르고 단순한 서버 크래시 복구. 서버가 open 파일, 파일 포인터, 캐시 보유 클라이언트 같은 분산 상태를 갖지 않으므로, 재부팅 후 복구 프로토콜 없이 바로 서비스를 재개하고 클라이언트는 재시도만 하면 된다. 클라이언트 크래시도 서버가 감지할 필요가 없다.

대가: (1) 모든 요청이 FH, offset 등 전체 정보를 담아야 해서 메시지가 커지고, (2) 서버가 누가 캐시하는지 모르니 캐시 일관성을 클라이언트 폴링(GETATTR) 으로 해결해야 해서 서버 부하와 애매한 의미론이 생기고, (3) 파일 잠금 같은 상태 필요 기능은 별도 프로토콜(NLM)로 밀려났다. NFSv4 는 결국 상태(open, lease, delegation)를 도입했다.

Q2. NFS 파일 핸들의 구성 요소와 generation 번호가 필요한 이유는?#

답 보기

(volume ID, inode 번호, generation 번호). volume 은 서버가 export 하는 여러 FS 중 어느 것인지, inode 는 그 안의 파일, generation 은 inode 재사용 시 증가한다.

파일이 삭제되고 같은 inode 번호가 새 파일에 재할당되면, 옛 핸들을 가진 클라이언트가 엉뚱한 새 파일에 접근할 수 있다(보안/무결성 문제, 일종의 ABA). generation 이 다르면 서버는 ESTALE 을 반환한다. 핸들이 경로가 아니라 inode 기반이라서 rename 에도 유효하다는 장점도 있다.

Q3. NFS WRITE 는 멱등인데 MKDIR 은 왜 아닌가? 멱등하게 만들려면?#

답 보기

WRITE 는 (FH, 절대 offset, count, data) 를 담아 몇 번 실행해도 같은 바이트가 같은 위치에 있게 된다. MKDIR 은 첫 실행이 성공한 뒤 응답이 유실되면 재시도가 "이미 존재함(EEXIST)" 으로 실패한다 — 상태는 같아도 응답이 다르다.

멱등하게 만드는 방법: (1) 서버의 duplicate request cache(XID 기반으로 최근 응답 재전송 — 실제 NFS 서버들이 씀), (2) "생성하되 이미 있으면 성공" 의미론, (3) 클라이언트가 고유 토큰(예: NFSv3 exclusive create 의 verifier)을 보내 서버가 "같은 요청자의 재시도" 를 식별. 원문의 결론은 Voltaire's Law — 대부분을 깔끔하게 처리하면 충분하다.

Q4. NFS 의 close-to-open 일관성과 attribute cache 가 만드는 이상 동작을 설명하라.#

답 보기
  • flush-on-close: 쓴 클라이언트가 close 하면 더티 데이터를 서버에 밀어 넣는다 → 그 이후에 open 하는 다른 클라이언트는 최신본을 본다(update visibility).
  • open 시 GETATTR: 수정 시각을 비교해 캐시를 무효화(stale cache).
  • attribute cache(예: 3초): GETATTR 을 줄이려고 속성을 캐시하므로, 그 시간 동안은 서버의 새 버전을 못 보고 옛 캐시를 쓴다.

결과: 다른 클라이언트가 파일을 바꾸고 닫은 직후 내가 열었는데도 최대 수 초간 옛 내용을 볼 수 있다. 보장 수준이 타임아웃 같은 구현 세부로 정의돼 추론이 어렵다. 또 열린 채로 쓰는 중인 파일은 다른 클라이언트에 언제 보일지 정해져 있지 않다.

Q5. NFS 서버가 WRITE 를 메모리에만 두고 성공을 돌려주면 무슨 일이 생기나? 성능은 어떻게 확보하나?#

답 보기

클라이언트의 복구 전략은 "응답이 없으면 재시도" 다. 서버가 성공을 응답한 뒤 크래시로 데이터를 잃으면 클라이언트는 재시도할 이유가 없어, 조용한 데이터 손실이 생긴다. 원문 예: a/b/c 를 썼는데 결과가 a / y / c.

성능 확보: (1) NVRAM(배터리 백업 메모리) 에 쓰고 즉시 응답(NetApp), (2) 디스크에 빠르게 쓰는 로그 구조 FS(WAFL), (3) NFSv3 의 UNSTABLE WRITE + COMMIT — 서버는 버퍼링 가능, 클라이언트는 COMMIT 전까지 데이터를 보관하고 서버 재부팅(write verifier 변경)을 감지하면 재전송. SSD 의 PLP/FUA 와 같은 구조다.

Q6. stateless 설계에서 READDIR 의 cookie 는 어떤 역할인가?#

답 보기

큰 디렉터리를 여러 번에 나눠 읽을 때 "어디까지 읽었나" 라는 커서 상태가 필요하다. stateful 서버라면 서버가 커서를 기억하겠지만, NFS 는 서버가 불투명한 cookie 를 응답에 넣어 주고 클라이언트가 보관했다가 다음 READDIR 에 돌려준다. 상태를 서버에서 클라이언트로 옮기는 stateless 설계의 전형 — HTTP 의 페이지네이션 토큰과 같다.

17. 자가 점검 & 숙제#

퀴즈 1. /a/b/c/d.txt 를 처음 open 하고 24 KB 를 8 KB 단위로 읽은 뒤 close 한다. NFSv2 RPC 는 몇 개?#

답 보기

LOOKUP 4개(a, b, c, d.txt) + READ 3개(24/8) + close 0개 = 7개. 캐싱 일관성 검사를 위해 open 시 GETATTR 이 붙는 구현이면 +1 (단, LOOKUP 응답에 속성이 오므로 보통 생략 가능).

퀴즈 2. 다음 중 그냥 재시도해도 안전한 연산은? (a) READ(fh, 4096, 512) (b) WRITE(fh, 0, 8, "abcdefgh") (c) REMOVE(dirfh, "x") (d) "파일 끝에 로그 한 줄 추가"#

답 보기

(a), (b) 는 멱등이라 안전. (c) 는 첫 시도가 성공했으면 재시도가 ENOENT 로 실패(상태는 같지만 응답이 틀림). (d) 는 재시도마다 줄이 추가되는 비멱등 — NFS 에 이런 연산이 없는 이유.

퀴즈 3. attribute cache 타임아웃이 3초일 때, C2 가 t=10.0s 에 파일을 닫았다. C1 은 t=8.5s 에 마지막으로 GETATTR 을 했다. C1 이 새 버전을 처음 볼 수 있는 가장 이른 open 시각은?#

답 보기

C1 의 속성 캐시는 8.5 + 3 = 11.5s 까지 유효하다. 그 전(10.0~11.5s)의 open 은 캐시된 속성만 보고 옛 버전을 쓴다. 11.5s 이후 첫 open 에서 GETATTR → 수정 시각이 바뀐 걸 보고 무효화 → 새 버전. 즉 최대 1.5초간 stale.

퀴즈 4. 서버가 NVRAM 에 쓰고 바로 성공을 응답하는 것은 48.11 의 규칙 위반인가?#

답 보기

아니다. 규칙은 "안정(persistent) 저장소에 커밋한 뒤 응답" 이다. 배터리 백업 NVRAM 은 크래시/정전에도 내용이 살아남으므로 안정 저장소로 간주된다. 단, 배터리 고장 감지 시 write-through 로 전환하는 등 그 가정을 지키는 장치가 필요하다(SSD PLP 커패시터 헬스 체크와 같은 이야기).

숙제 (원문 v0.91 에는 이 장의 Homework 절이 없다 — 최신판의 dist-nfs 트레이스 숙제 흐름으로)#

  • 숙제 1 — 트레이스 기본 통계: 위 awk 로 트레이스 기간, 클라이언트 수, 연산 종류별 비율을 구해 보기 → "속성 요청이 서버 부하의 절반" 이라는 주장을 숫자로 확인하는 문제.
  • 숙제 2 — 파일별 순차성: 같은 FID 의 Block 요청 offset 이 증가하는지 검사하는 awk 를 짜 보기 (awk '$2=="Block"{print $5, $7}' | sort -k1,1 -k2n,2) → NFS 클라이언트의 read-ahead/순차 접근 패턴을 확인하는 문제. AFS 의 "파일은 대부분 통째로 순차 접근된다" 가정과 연결된다.
  • 숙제 3 — 위 C 코드 확장: [3] 에 "서버가 크래시 후 클라이언트가 응답 못 받은 WRITE 를 재시도" 경로를 추가 → 커밋 후 응답 + 멱등 WRITE + 재시도 의 조합이 왜 완전한지 확인하는 문제.
