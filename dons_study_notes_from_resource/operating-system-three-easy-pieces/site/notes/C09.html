0. 한눈에 보기#

지금까지의 스케줄러는 반환시간·응답시간을 최적화하려 했다. 비례 배분(proportional-share, 공정 배분 fair-share) 스케줄러는 목표가 다르다: 각 job 이 CPU 의 정해진 비율을 받도록 보장한다. 대표 구현이 Waldspurger 의 로또 스케줄링(lottery) 과 그 결정론 버전인 보폭 스케줄링(stride) 이다.

CRUX: HOW TO SHARE THE CPU PROPORTIONALLY — "How can we design a scheduler to share the CPU in a proportional manner? What are the key mechanisms for doing so? How effective are they?"

(CPU 를 비율대로 나눠 주는 스케줄러를 어떻게 설계할까? 핵심 메커니즘은? 얼마나 효과적인가?)

  • 티켓(ticket) = 몫. 티켓 비율 = CPU 비율.
  • 로또: 매 slice 마다 추첨. 단순하고 전역 상태가 거의 없지만, 짧은 구간에선 비율이 어긋난다.
  • 보폭: pass += stride (= BIG / tickets), pass 가 가장 작은 job 실행. 매 주기 정확하지만 새 job 의 pass 를 정해야 한다.
  • 이 판(v0.91) 원문에는 없지만 이후 판에 추가된 Linux CFS 도 "가중치로 나눈 가상 실행시간"이라는 같은 아이디어다 (8.1 보충).

2. 기본 개념: 티켓이 곧 몫 (9.1)#

A 가 티켓 75장, B 가 25장이면 목표는 A 75%, B 25%. 로또 스케줄러는 매 time slice 마다 당첨 티켓 번호를 뽑는다. 총 100장이니 0~99 중 하나. A 가 0~74, B 가 75~99 를 가지고 있으면 당첨 번호로 누가 돌지 정해진다.

원문의 당첨 번호 20개와 결과:

B(75 이상)는 85, 76, 99, 83 의 4번 = 20%. 목표 25% 와 다르다. 로또는 확률적으로만 맞는다 — 오래 경쟁할수록 목표 비율에 가까워진다.

TIP — 무작위성을 써라: 무작위 결정의 장점 셋. (1) 이상한 코너 케이스가 없다 — 예: LRU 는 순환 순차 접근에서 최악이지만 Random 은 최악 케이스가 없다. (2) 가볍다 — 프로세스별로 티켓 수 정도만 기억하면 된다. (3) 빠르다 — 난수 생성만 빠르면 결정도 빠르다 (그래서 빠를수록 의사난수 쪽으로 간다).

TIP — 몫을 표현할 땐 티켓: 티켓은 CPU 뿐 아니라 무엇이든 "소유 비율"을 표현하는 범용 메커니즘이다. Waldspurger 는 하이퍼바이저에서 게스트 OS 의 메모리 몫을 티켓으로 표현했다 (VMware ESX, [W02]).

3. 티켓 메커니즘 (9.2)#

3.1 티켓 화폐 (currency)#

사용자가 자기만의 화폐 단위로 job 들에게 티켓을 나눠 주면, 시스템이 전역 화폐로 환산한다.

원문 예. 사용자 A, B 가 각각 전역 티켓 100장.

새 예. 사용자 X(전역 300장)가 X1 에 1, X2 에 3 (X 화폐 총 4), 사용자 Y(전역 100장)가 Y1 하나.

사용자 수준 몫(X 75%, Y 25%)은 job 을 몇 개 띄우든 유지된다 — job 을 많이 띄워서 몫을 늘리는 꼼수가 안 통한다.

3.2 티켓 양도 (transfer)#

클라이언트가 서버에 일을 맡길 때 자기 티켓을 서버에 잠시 넘겨 서버가 그 일을 빨리 처리하게 한다. 끝나면 돌려받는다. (우선순위 역전 해결의 "우선순위 상속"과 같은 발상.)

3.3 티켓 인플레이션 (inflation)#

프로세스가 스스로 티켓 수를 올리거나 내린다. 서로 신뢰하지 않는 환경에선 욕심 많은 프로세스가 기계를 독차지하니 의미가 없고, 서로 신뢰하는 그룹 안에서 "나 지금 CPU 더 필요해"를 다른 프로세스와 통신 없이 알리는 용도로 쓴다.

4. 구현 (9.3)#

필요한 건 세 가지뿐: 좋은 난수 생성기, 프로세스 목록, 전체 티켓 수.

원문 예. A=100, B=50, C=250 (총 400), 당첨 번호 300.

최적화: 리스트를 티켓 많은 순으로 정렬하면 순회 횟수가 줄어든다(정확성엔 영향 없음). 티켓 대부분을 소수 프로세스가 가지고 있을 때 효과가 크다. job 이 아주 많으면 누적합 트리(Fenwick 트리 등)로 O(log n) 에 찾을 수 있다.

주의(원문 각주): "0 ~ total−1 범위의 난수"를 정확히 만드는 건 의외로 까다롭다. rand() % total 은 total 이 난수 범위의 약수가 아니면 modulo bias 가 생긴다. 아래 C 코드는 학습용으로 % total 을 그대로 썼다.

5. 예: 로또는 얼마나 공정한가 (9.4)#

같은 티켓(100장), 같은 길이 R 인 두 job 이 경쟁한다. 이상적으로는 둘이 거의 동시에 끝나야 한다.

$$U = \frac{\text{먼저 끝난 job 의 완료 시각}}{\text{나중에 끝난 job 의 완료 시각}}$$

예: R = 10, 첫 job 이 10 에, 둘째가 20 에 끝나면 U = 10/20 = 0.5 (가장 불공정). 완벽히 공정하면 U ≈ 1. 원문 Fig 9.2 는 R 을 1~1000 으로 바꾸며 30회 평균 U 를 그렸다 — job 이 짧으면 꽤 불공정하고, 길어질수록 1 에 다가간다. 아래는 이 노트의 C 프로그램("직접 해보기" 9.2)으로 직접 다시 만든 곡선이다.

R = 1 이면 U 가 항상 정확히 0.5 다 — 한 job 은 1 에, 다른 job 은 2 에 끝날 수밖에 없으니까. 이건 로또라서가 아니라 slice 단위가 거칠어서 생기는 하한이다.

6. 티켓은 어떻게 나눠 주나? (9.5)#

어려운 문제다. "사용자가 제일 잘 안다"며 사용자에게 티켓을 주고 알아서 나누라는 건 사실상 답이 아닌 답(non-solution) 이다. 일반적인 job 집합에 대해 티켓 배분 문제는 열려 있다. 이게 비례 배분이 범용 CPU 스케줄러로 널리 안 쓰이는 이유 중 하나다.

7. 왜 결정론적이지 않나? — 보폭 스케줄링 (9.6)#

무작위는 단순하지만 짧은 구간에선 비율을 정확히 못 맞춘다. 그래서 Waldspurger 는 결정론적 stride scheduling 을 만들었다.

  • stride = 큰 수 / 티켓 수. A=100, B=50, C=250 이고 큰 수 10,000 이면 stride = 100, 200, 40.
  • pass = 누적 진행량. 처음엔 모두 0.
  • 매번 pass 가 가장 작은 job 을 돌리고, 돌린 job 의 pass 에 stride 를 더한다.

원문 Fig 9.3 트레이스 (동률이면 A → B → C 순으로 고른다고 가정):

C 5번, A 2번, B 1번 = 250 : 100 : 50 에 정확히 비례. 로또는 시간이 지나야 확률적으로 맞고, stride 는 매 주기 끝마다 정확히 맞는다.

새 예. A=3장, B=2장, 큰 수 60 → stride A=20, B=30.

7.1 그런데 왜 로또를 쓰나? — 전역 상태#

stride 에는 로또에 없는 약점이 있다: 전역 상태. 실행 도중 새 job 이 들어오면 pass 를 얼마로 줘야 하나? 0 으로 주면 기존 job 들의 pass 를 따라잡을 때까지 CPU 를 독점한다. 로또는 새 job 의 티켓만 전체 티켓 수에 더하면 끝 — 새 프로세스를 자연스럽게 받아들인다. (실전 해법: 새 job 의 pass 를 현재 최소 pass, 혹은 "전역 pass" 로 맞춘다. "직접 해보기" 9.2 의 Part 4 가 이 차이를 숫자로 보여준다.)

8. 요약 (9.7)#

로또는 무작위성을 영리하게 써서, stride 는 결정론적으로 비례 배분을 이룬다. 둘 다 개념적으로 흥미롭지만 범용 CPU 스케줄러로 널리 쓰이지는 않았다.

  • I/O 와 잘 안 맞는다 — 잠들었다 깨어난 job 을 어떻게 셈할지 애매하다 [AC97].
  • 티켓 배분 문제가 열려 있다 — 브라우저에 티켓을 몇 장 줘야 하나?

그래서 범용 OS 는 MLFQ 같은 스케줄러가 더 매끄럽다. 반면 몫 배분이 쉬운 영역에선 비례 배분이 단순하고 효과적이다: 가상화 데이터센터에서 "Windows VM 에 CPU 1/4, 나머지는 Linux" 같은 경우. VMware ESX 는 메모리도 비례 배분한다 [W02].

8.1 보충: Linux CFS (이 판 원문에는 없음)#

이 절은 v0.91 원문에는 없고 OSTEP 이후 판(v1.00+) 9장에 추가된 내용을 요약한 것이다. 원문 링크의 PDF 에서는 찾을 수 없다.

Linux 의 Completely Fair Scheduler(CFS, 2.6.23~6.5) 는 stride 와 같은 결정론적 비례 배분이다. 핵심은 가상 실행시간(vruntime).

  • 각 프로세스가 돌 때마다 vruntime += 실제 실행시간 × (1024 / weight). nice 0 의 weight 가 1024 이므로 nice 0 프로세스는 실제 시간만큼 vruntime 이 오른다. (stride 의 pass += BIG / tickets 와 같은 꼴: weight = 티켓, 1024 = BIG.)
  • 고를 때는 vruntime 이 가장 작은 프로세스. 프로세스들을 vruntime 기준 레드-블랙 트리에 두어 최소 찾기/삽입이 O(log n).
  • 얼마나 돌릴지: sched_latency(예: 48 ms)를 n 개 프로세스에 가중치 비율로 나눈다. 단 너무 잘게 쪼개지지 않게 min_granularity(예: 6 ms) 하한.
  • nice(−20 ~ +19) → weight 표: nice 0 = 1024, nice −5 = 3121, nice +5 = 335 처럼 한 단계에 약 1.25배.
  • 잠들었다 깨어난 프로세스의 vruntime 은 현재 트리의 최소 vruntime 근처로 맞춘다 — 오래 잔 프로세스가 독점하지 않게. 이게 바로 7.1 의 "새 job pass 문제"의 Linux 식 해답이다(대신 자주 자는 프로세스는 손해를 볼 수 있다).

계산 예. A 는 nice −5(weight 3121), B 는 nice 0(1024), sched_latency 48 ms.

실제 시간은 3:1 로 나뉘지만 vruntime 은 같은 속도로 오른다 — "가상 시간으로는 완전히 공정". Linux 6.6 부터는 CFS 대신 EEVDF(Earliest Eligible Virtual Deadline First, Ch.10 원문에서 BFS 설명에 언급된 그 알고리즘)가 기본이 됐다.

9. 직접 해보기#

9.1 OSTEP 시뮬레이터 lottery.py#

숙제 1: 3개 job, seed 1.

앞부분 (실제 출력):

grep DONE 결과: JOB 0 DONE at time 2, JOB 2 DONE at time 6, JOB 1 DONE at time 12.

손으로 검증하는 법: 당첨 번호 = 난수 % 총 티켓. 첫 줄 651593 % 153 = 119. 티켓 구간은 job 0 = 0~83, job 1 = 84~108, job 2 = 109~152 → 119 는 job 2. job 0 이 끝나면 총 티켓이 153 → 69 로 줄고 구간이 다시 매겨진다(job 1 = 0~24, job 2 = 25~68): 93859 % 69 = 19 → job 1.

숙제 2: 티켓이 극단적으로 불균형(1 : 100)이면?

seed 1~10 으로 반복해 "job 1 이 끝나기 전 job 0 이 몇 번 돌았나"를 센 결과: seed 2 에서만 1번, 나머지 9개 seed 는 0번. 이론값: 10번 추첨 중 job 0 이 한 번이라도 당첨될 확률 = 1 − (100/101)^10 ≈ 9.4% — 관찰(10번 중 1번)과 맞는다. 티켓 1장짜리 job 은 사실상 기아 상태가 된다.

숙제 3·4: 같은 티켓, 길이 100 두 job 의 불공정도와 quantum 의 영향.

U = 먼저/나중: q=1 → 0.98, 0.95, 0.98, 0.995, 0.905 (평균 ≈ 0.96). q=10 → 0.80, 0.95, 0.95, 0.95, 0.80 (평균 0.89). quantum 이 커지면 길이 100 이 추첨 10번짜리 job 이 되어, 위 곡선에서 R=10 쪽(U≈0.83)으로 이동한다. 즉 불공정도는 "시간"이 아니라 추첨 횟수에 달렸다.

  • Part 4: 새 job D(100장 = 전체 500장 중 20%)를 pass=0 으로 넣으면 기존 job 들의 pass 가 이미 수만이라 D 가 100 slice 를 전부 독점한다. 현재 최소 pass 로 맞춰 넣으면 정확히 공정 몫 20 을 받는다. CFS 가 새/깨어난 태스크의 vruntime 을 min_vruntime 기준으로 놓는 이유.

10. 펌웨어 엔지니어의 눈으로#

  • NVMe WRR 의 가중치는 사실상 stride. High/Medium/Low 큐에 가중치(예: 8:4:1)를 주고 한 라운드에서 가중치만큼 커맨드를 가져오는 건 "주기 끝마다 비율이 정확한" stride 와 같은 성질이다. FW 구현은 deficit/credit 카운터로 하는데, 이게 pass 의 다른 이름이다. 펌웨어에선 RNG 를 안 쓰고 정수 연산만으로 결정론을 확보하는 stride 계열이 압도적으로 선호된다(재현성 = 디버깅 가능성).
  • pass/vruntime 오버플로는 펌웨어에서 진짜 버그 원인. 32비트 pass 가 래핑되면 "최소 pass" 비교가 뒤집혀 한 큐가 굶는다. 해법은 TCP 시퀀스 번호처럼 (int32_t)(a - b) < 0 으로 비교하거나 주기적으로 전체에서 min 을 빼 정규화하는 것. Linux CFS 도 vruntime 비교에 부호 있는 차이를 쓴다.
  • 멀티 테넌트 SSD/가속기 QoS = 티켓 화폐. NVMe namespace 나 SR-IOV VF 별로 대역폭/IOPS 몫을 주고, 그 안에서 큐별로 다시 나누는 계층 구조는 "사용자 화폐 → 전역 화폐" 환산과 같다. GPU 가상화(NVIDIA vGPU)의 time-sliced 스케줄러가 best-effort / equal-share / fixed-share 정책을 고르게 하는 것도 비례 배분 선택지다.
  • 티켓 양도 ≈ 우선순위 상속. RTOS 에서 고우선순위 태스크가 저우선순위 태스크의 mutex 를 기다리면 우선순위를 빌려주는 것(priority inheritance)과 같은 구조다. 호스트 커맨드를 처리하는 FW 백엔드 태스크가 요청한 큐의 몫을 따라가게 하는 설계도 이 아이디어다.
  • "I/O 와 잘 안 맞는다"는 약점은 스토리지에서 그대로 보인다. 잠깐 쉬던 테넌트가 돌아와 밀린 몫을 한꺼번에 요구하면(= 오래 잔 프로세스) 다른 테넌트 latency 가 튄다. 그래서 토큰 버킷처럼 적립 한도(burst cap) 를 둔다 — CFS 가 깨어난 태스크의 vruntime 을 min_vruntime 근처로 끌어올리는 것과 같은 목적.

11. 면접 질문#

Q1. 로또 스케줄링과 보폭 스케줄링을 비교하라. 각각 언제 쓰나?#

답 보기
  • 로또: 매 slice 무작위 추첨. 상태가 거의 없음(티켓 수, 총합), 새 job 추가가 쉬움, 최악 케이스 없음. 대신 짧은 구간에서 비율 오차가 크고 상대 오차가 1/√n 로만 줄어든다.
  • stride: pass += BIG/tickets, 최소 pass 실행. 매 주기 정확한 비율, 결정론적이라 재현·디버깅이 쉽다. 대신 전역 상태(새 job 의 pass 를 정해야 함)와 우선순위 큐(O(log n)) 필요.
  • 실무: 결정론과 지연 보장이 중요한 커널/펌웨어(Linux CFS, NVMe WRR, 네트워크 WFQ)는 stride 계열, 분산 환경처럼 전역 상태를 유지하기 어려운 곳은 무작위(예: 로드밸런싱의 "power of two choices")가 유리.

Q2. stride 스케줄러에 새 프로세스가 들어오면 pass 를 몇으로 줘야 하나?#

답 보기
  • 0 으로 주면 기존 프로세스 pass 를 따라잡을 때까지 독점 (C 실험: 100 slice 중 100).
  • 일반적으로 현재 최소 pass(또는 전역 가상 시간)로 맞춘다 → 즉시 공정 몫(실험: 20/100)부터 시작.
  • 같은 문제가 잠들었다 깨어난 프로세스에도 있다. Linux CFS 는 깨어난 태스크의 vruntime 을 max(자기 vruntime, min_vruntime − 약간의 보너스) 로 놓아 독점도, 과한 불이익도 막는다.

Q3. Linux CFS 에서 nice 값은 어떻게 CPU 비율로 바뀌나? vruntime 은 어떻게 계산되나?#

답 보기
  • nice → weight 표(nice 0 = 1024, 한 단계마다 약 1.25배; nice −5 = 3121). 비율은 weight 의 비로 정해지므로 절대 nice 값이 아니라 nice 차이가 중요하다(nice 0 vs 5 와 nice 10 vs 15 의 비율이 같다).
  • 할당 시간: slice_i = sched_latency × weight_i / Σweight (하한 min_granularity).
  • vruntime += 실행시간 × 1024 / weight_i — 무거운 프로세스는 vruntime 이 천천히 오른다.
  • 선택: vruntime 최소, 레드-블랙 트리로 O(log n). (6.6 이후 기본은 EEVDF.)

Q4. 로또 스케줄링에서 두 job 의 티켓이 1 : 100 이면 어떤 문제가 생기나?#

답 보기
  • 티켓 1장짜리는 매 추첨에서 1/101 확률. 상대 job 이 10 slice 로 끝날 동안 한 번이라도 돌 확률 ≈ 1 − (100/101)^10 ≈ 9.4% — 사실상 기아(시뮬레이터 seed 10개 중 1개에서만 1번 실행).
  • 짧은 구간에선 비율 보장도 사실상 없음. 응답시간 보장이 없다는 점이 비례 배분의 본질적 약점.
  • 대책: 최소 몫 보장(floor), stride 로 바꿔 결정론적으로 주기마다 최소 1번 보장, 혹은 대화형 job 에 별도 우선순위 클래스.

Q5. 비례 배분 스케줄러가 범용 OS 에서 MLFQ 만큼 안 쓰였던 이유와, 그래도 잘 맞는 영역은?#

답 보기
  • I/O 와 궁합: 잠든 동안의 몫을 어떻게 셈할지 애매(쌓아 주면 깨어나 폭주, 안 주면 대화형이 손해).
  • 티켓 배분 문제: "브라우저에 몇 장?"에 답이 없다. MLFQ 는 행동을 보고 자동으로 정한다.
  • 잘 맞는 곳: 몫이 계약으로 정해지는 곳 — VM/컨테이너 CPU shares(cgroups cpu.weight), 하이퍼바이저 메모리 shares, 네트워크/스토리지 QoS, GPU 가상화. Linux 의 CFS 자체도 결국 비례 배분이고 cgroup 계층 = 티켓 화폐다.

12. 자가 점검 & 숙제#

퀴즈 1. 사용자 P(전역 200장)가 P1:P2 = 1:4 로, 사용자 Q(전역 100장)가 Q1:Q2:Q3 = 1:1:2 로 나눴다. 각 job 의 CPU 비율은?#

답 보기

전역 총 300. P1 = 200×1/5 = 40, P2 = 160, Q1 = 100×1/4 = 25, Q2 = 25, Q3 = 50. 비율: P1 13.3%, P2 53.3%, Q1 8.3%, Q2 8.3%, Q3 16.7%.

퀴즈 2. A=40장, B=10장, C=50장, BIG=200 일 때 stride 와 첫 한 주기 동안의 실행 순서는? (동률은 A→B→C)#

답 보기

stride A=5, B=20, C=4. 주기 길이 = pass 가 모두 20 이 될 때 → A 4번, B 1번, C 5번 (40:10:50 = 4:1:5). 순서: A(0→5) B(0→20) C(0→4) C(4→8) A(5→10) C(8→12) A(10→15) C(12→16) A(15→20) C(16→20) → A B C C A C A C A C.

퀴즈 3. 로또에서 목표 25% 인 job 의 실제 비율이 ±1%p 안에 들어오려면 대략 몇 slice 가 필요한가? (표준편차 1개 기준)#

답 보기

비율의 표준편차 = √(p(1−p)/n) = √(0.1875/n). 이게 0.01 이하가 되려면 n ≥ 0.1875/0.0001 = 1875 slice. C 실험에서 1000 slice 때 1.6%p 어긋났던 것과 맞는 크기다.

퀴즈 4. CFS 에서 nice 0 프로세스 3개와 nice −5 프로세스 1개가 있다. sched_latency 48 ms 일 때 nice −5 프로세스의 slice 는?#

답 보기

Σweight = 3×1024 + 3121 = 6193. slice = 48 × 3121/6193 ≈ 24.2 ms. nice 0 각각은 48 × 1024/6193 ≈ 7.9 ms (min_granularity 6 ms 보다 크므로 그대로).
