# E1. RTOS-aware ISR 규칙 — FromISR, woken 플래그, 그리고 ISR에서 하면 안 되는 일

> **이 노트를 다 읽으면**: FreeRTOS `...FromISR` API가 왜 따로 있는지(블록 금지, 저장/복원식 크리티컬 섹션, "스위치는 나중에")를 소스로 설명할 수 있다 · `pxHigherPriorityTaskWoken`을 NULL로 넘기거나 덮어쓰면 지연이 정확히 "최대 1 tick"이 된다는 것을 tick 주파수 3가지로 재서 보여 줄 수 있다 · ISR 안의 블로킹 호출, 뮤텍스, `vTaskDelay`, `malloc`, `printf`, 긴 루프, FPU가 각각 무엇을 망가뜨리는지 assert 켜고/끄고 실험한 결과로 말할 수 있다 · Zephyr의 `k_is_in_isr()`, `K_NO_WAIT` 규칙, `IRQ_DIRECT_CONNECT` + `ISR_DIRECT_DECLARE`의 반환값이 재스케줄을 어떻게 바꾸는지 측정 숫자로 설명할 수 있다
> **왜 필요한가**: "ISR에서 `xSemaphoreGive` 대신 왜 `xSemaphoreGiveFromISR`을 쓰나?", "`xHigherPriorityTaskWoken`은 뭐고 안 쓰면 어떻게 되나?", "ISR에서 하면 안 되는 일을 말해 보라"는 RTOS 펌웨어 면접 최빈출 3종 세트다. 실무에서는 "가끔 1 ms 늦게 도는 태스크", "현장에서만 나는 리스트 손상 HardFault", "ISR 안 로그 한 줄 때문에 놓친 IMU 샘플"이 전부 이 규칙에서 나온다
> **Don 기준 난이도**: ISR을 짧게 쓰고 플래그만 세운다는 bare-metal 감각, NVIC 우선순위·BASEPRI(B3), 크리티컬 섹션(C7)은 이미 안다 / 새로 배울 부분은 RTOS가 ISR에 요구하는 **계약**(어떤 API를, 어떤 우선순위에서, 어떤 인자로)과, 그 계약을 어겼을 때 커널 안에서 실제로 무엇이 깨지는지
> **선행 노트**: B2(예외 진입·복귀), B3(NVIC·BASEPRI·`configMAX_SYSCALL_INTERRUPT_PRIORITY`), B4(PendSV), C7(크리티컬 섹션 — `taskENTER_CRITICAL_FROM_ISR`), C8(커널 진입), D1 §4(세마포어 give의 FromISR 규약과 yield 누락 히스토그램), D7(ISR 밖으로 일 미루기), EL F6(Linux 인터럽트 처리)·EL F2(실행 문맥). 이어지는 노트: E2(우선순위 배치 · zero-latency IRQ), E3(지연 분해 · 측정), E4(ISR → 태스크 경로 · 인터럽트 폭주)

## 0. 큰 그림 — 이게 왜 필요한가

bare-metal 펌웨어에서 ISR 규칙은 단순했다. "짧게 쓰고, 공유 변수는 `volatile`로, 메인 루프가 플래그를 보게 하라." Don이 SSD 컨트롤러에서 NVMe doorbell ISR이 커맨드 큐 인덱스만 갱신하고 실제 처리를 executive 루프에 넘긴 것이 정확히 그 모양이다.

RTOS를 올리면 ISR과 메인 루프 사이에 **스케줄러**라는 제3자가 끼어든다. 이제 ISR은 플래그만 세우는 게 아니라 "자고 있는 태스크를 깨워 달라"고 커널에 부탁해야 한다. 그런데 커널은 자기 자료구조(ready 리스트, 이벤트 리스트, 큐)를 태스크 문맥에서 쓰려고 만들었다. ISR이 그 자료구조를 건드리려면 **세 가지가 달라야** 한다.

- **기다릴 수 없다.** ISR은 태스크가 아니라서 블록할 "자기 자신"이 없다. 블로킹 API를 부르면 커널은 "지금 돌던 태스크"(= ISR에게 끊긴 태스크)를 재운다. 엉뚱한 태스크가 잔다(§4.3에서 실측).
- **잠금 방식이 다르다.** 태스크용 크리티컬 섹션은 중첩 카운터 하나로 BASEPRI를 0까지 내린다. ISR은 들어올 때의 BASEPRI를 저장했다가 그대로 돌려놓아야 한다(C7 §3).
- **그 자리에서 컨텍스트 스위치를 할 수 없다.** 스위치는 모든 ISR이 끝난 뒤 PendSV가 한다. 그래서 ISR은 "높은 태스크를 깨웠으니 나가면 바꿔 달라"는 **요청만** 남긴다. 그게 `pxHigherPriorityTaskWoken` + `portYIELD_FROM_ISR`이다.

그리고 이 계약은 **어느 우선순위의 ISR이 지키는가**에 따라 갈린다. 아래 그림이 이 노트 전체의 지도다.

### 실습 환경 한 줄

QEMU `mps2-an385`(Cortex-M3 @ 25 MHz) 위의 FreeRTOS V11.3.2(lab 템플릿, 1 kHz tick, `configMAX_SYSCALL_INTERRUPT_PRIORITY` = 0x20)와 Zephyr v4.4.2(같은 보드, 100 Hz tick, tickless). 타이밍은 FreeRTOS는 `ICOUNT=1`, Zephyr는 `-icount shift=5`(명령 1개 = 32 ns)로 재고, 시계는 FPGAIO 25 MHz 카운터(0x40028018)다. **QEMU icount 기준이라 실제 칩과 절대값은 다르다**(캐시, 플래시 wait state, 예외 스태킹 사이클, UART baud 지연이 모델링되지 않는다). 예제 소스는 `~/.rtos_scratch/E1/`, 빌드 산출물은 VM의 `/var/tmp/rtos/E1/`. 공용 헤더 `e1.h`는 D1의 `d1.h`와 같은 도우미(TIMER0 시작·정지, 경과 사이클, `stat_t`)에 IPSR·BASEPRI 읽기와 `STIR`(소프트웨어 IRQ 트리거)를 더한 것이다.

## 1. 규칙 한 장 — 먼저 결론

이 노트에서 하나씩 실험으로 확인할 규칙을 먼저 나열한다. 각 줄 끝의 절 번호가 근거다.

1. **문턱 아래 우선순위의 ISR만 커널 API를 부른다.** 우선순위를 안 정한 IRQ는 리셋값 0 = 가장 급함 = 금지 영역이다 (§5, B3).
2. **ISR에서는 이름이 `FromISR`로 끝나는 API만 부른다** (FreeRTOS). Zephyr는 같은 이름이지만 **timeout은 `K_NO_WAIT`만** (§2, §6).
3. **`BaseType_t woken = pdFALSE;`로 시작해서, 모든 FromISR 호출에 같은 `&woken`을 넘기고, ISR 맨 끝에서 `portYIELD_FROM_ISR(woken)` 한 번** (§3).
4. **기다리는 것은 전부 금지**: 블로킹 take/receive, `vTaskDelay`/`k_sleep`, 뮤텍스, 이벤트 그룹 대기 (§4).
5. **뮤텍스는 ISR에서 절대 쓰지 않는다** — 소유자가 태스크여야 우선순위 상속이 성립한다 (§4.5).
6. **`printf`, 동적 할당, 상한 없는 루프, (FPU 코어가 아니면) 부동소수점은 ISR 밖으로** (§4.4, §4.6).
7. **개발 빌드는 `configASSERT` / `CONFIG_ASSERT=y`로** — 위 실수 대부분을 첫 실행에서 잡아 준다. 끄면 같은 실수가 "가끔 나는 이상한 버그"로 바뀐다 (§4.3, §5).

## 2. FreeRTOS의 `...FromISR` API 가족

### 2.1 왜 이름이 다른 함수를 따로 두나

직관: 태스크용 `xQueueSend()`와 ISR용 `xQueueSendFromISR()`는 같은 큐에 같은 데이터를 넣는다. 그런데 태스크용은 "자리가 없으면 기다린다"는 경로를 품고 있고, ISR용은 그 경로가 아예 없다. 비유하면 태스크용은 "줄이 길면 줄 서서 기다리는 손님", ISR용은 "줄이 길면 그냥 돌아가는 배달원"이다. 배달원은 다음 집이 기다리고 있으니 줄을 설 수 없다.

정의: FreeRTOS V11.3.2 `queue.c`의 `xQueueGenericSendFromISR()` 주석이 이유를 그대로 적어 두었다.

```c
    /* Similar to xQueueGenericSend, except without blocking if there is no room
     * in the queue.  Also don't directly wake a task that was blocked on a queue
     * read, instead return a flag to say whether a context switch is required or
     * not (i.e. has a task with a higher priority than us been woken by this
     * post). */
```

그리고 `port.c`의 `vPortValidateInterruptPriority()` 주석에는 "FreeRTOS maintains separate thread and ISR API functions to ensure interrupt entry is as fast and simple as possible."라고 되어 있다. 정리하면 FromISR 변형은 태스크용과 **네 가지가 다르다**.

| 차이 | 태스크용 (`xQueueGenericSend`) | ISR용 (`xQueueGenericSendFromISR`) |
|---|---|---|
| 기다림 | `xTicksToWait`만큼 블록 가능 (`vTaskPlaceOnEventList`) | 인자 자체가 없다. 꽉 차 있으면 즉시 `errQUEUE_FULL` |
| 크리티컬 섹션 | `taskENTER_CRITICAL()` → `vPortEnterCritical()`: BASEPRI = 0x20, 중첩 카운터 `uxCriticalNesting++`, 나갈 때 0이 되면 BASEPRI = 0 | `taskENTER_CRITICAL_FROM_ISR()` → `portSET_INTERRUPT_MASK_FROM_ISR()` = `ulPortRaiseBASEPRI()`: 이전 BASEPRI를 **반환값으로 저장**, 나갈 때 `vPortSetBASEPRI(저장값)`로 복원 |
| 높은 태스크를 깨웠을 때 | 그 자리에서 `queueYIELD_IF_USING_PREEMPTION()` → PendSV | 스위치 안 함. `*pxHigherPriorityTaskWoken = pdTRUE`만 |
| 진입 검사 | VECTACTIVE ≠ 0이면 assert (`port.c:438`) | `portASSERT_IF_INTERRUPT_PRIORITY_INVALID()` — 지금 ISR의 우선순위가 문턱 아래인지 (`port.c:803`) |

크리티컬 섹션 차이가 왜 중요한지는 C7 §3.5에서 자세히 봤다. 한 줄로: ISR 진입은 BASEPRI를 바꾸지 않으므로, ISR이 "나갈 때 무조건 0"으로 내리면 다른 문맥이 올려 둔 마스크를 풀어 버릴 수 있다. 그래서 ISR은 저장/복원식만 쓴다.

`portmacro.h`(ARM_CM3)에서 두 매크로가 어떻게 정의되는지 보자.

```c
#define portSET_INTERRUPT_MASK_FROM_ISR()         ulPortRaiseBASEPRI()
#define portCLEAR_INTERRUPT_MASK_FROM_ISR( x )    vPortSetBASEPRI( x )
#define portDISABLE_INTERRUPTS()                  vPortRaiseBASEPRI()
#define portENABLE_INTERRUPTS()                   vPortSetBASEPRI( 0 )
#define portENTER_CRITICAL()                      vPortEnterCritical()
#define portEXIT_CRITICAL()                       vPortExitCritical()
```

`ulPortRaiseBASEPRI()`는 `mrs %0, basepri` → `msr basepri, 0x20` → `isb` → `dsb`이고 이전 값을 돌려준다. 앱이 직접 ISR 안에서 짧은 보호 구간이 필요하면 이 쌍을 쓴다.

```c
void UART_RX_IRQHandler(void)
{
    UBaseType_t saved = taskENTER_CRITICAL_FROM_ISR();   /* = portSET_INTERRUPT_MASK_FROM_ISR() */
    ring_push(&rx_ring, UART_DATA);                      /* 다른 kernel-aware ISR과 공유하는 링 */
    taskEXIT_CRITICAL_FROM_ISR(saved);                   /* 저장한 값으로 복원 — 0으로 내리지 않는다 */
}
```

(위 코드는 모양을 보여 주는 조각이라 실행하지 않았다. 실제 동작은 예제 3의 디스어셈블에서 확인한다.)

**FromISR 짝이 없는 것** — 즉 ISR에서는 대안이 없는 것:

- `vTaskDelay`, `xTaskDelayUntil` — ISR은 잘 수 없다.
- 뮤텍스 take (`xSemaphoreTake(mutex, …)`) — §4.5. (`xSemaphoreTakeFromISR`은 존재하지만 뮤텍스에는 쓰면 안 된다.)
- `xEventGroupWaitBits`, `xEventGroupSync` — 기다리는 API.
- `xTaskCreate`, `vTaskDelete`, `vTaskSuspend`, `vTaskPrioritySet` — 리스트 대수술이라 태스크 문맥 전용.
- `pvPortMalloc`, `vPortFree` — 스케줄러 잠금을 쓴다(§4.2 예제 6의 MODE=5).

`xTaskResumeFromISR`은 문서에서도 "ISR → 태스크 동기화에 쓰지 말라"고 한다. 태스크가 아직 suspend되기 전에 resume이 오면 사건을 잃기 때문이다. 깨우기는 task notification이나 세마포어로 한다.

### 2.3 예제 2 — 두 변형의 비용, FromISR을 태스크에서 부르면, 그리고 양쪽에서 쓸 수 있는 도우미

무엇을 확인하는 코드인지: ① 같은 세마포어에 태스크용 give/take와 FromISR give/take를 1000번씩 해서 한 번 비용을 잰다. ② FromISR을 태스크에서 부르면 어떻게 되나. ③ `xPortIsInsideInterrupt()`로 문맥을 보고 알맞은 API를 고르는 도우미 `sig_give()`를 ISR과 태스크 양쪽에서 부른다. ISR은 TIMER0 줄(IRQ 8, 우선순위 0x40)을 `STIR`로 소프트웨어 트리거한다.

```c
/* E1 ex2 — task API vs FromISR API: cost, and one helper that works in both contexts */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "e1.h"
#define N 1000
static SemaphoreHandle_t sem;
static volatile uint32_t isr_give, isr_take, isr_ipsr, isr_path;

static int sig_give(SemaphoreHandle_t s)        /* safe from task or ISR */
{
    if (xPortIsInsideInterrupt()) {
        BaseType_t woken = pdFALSE;
        xSemaphoreGiveFromISR(s, &woken);
        portYIELD_FROM_ISR(woken);
        return 1;                               /* took the ISR path */
    }
    xSemaphoreGive(s);
    return 0;                                   /* took the task path */
}
void TIMER0_IRQHandler(void)                    /* pended by software (STIR), prio 0x40 */
{
    BaseType_t woken = pdFALSE;
    isr_ipsr = ipsr();
    uint32_t t = CYC();
    for (int i = 0; i < N; i++) xSemaphoreGiveFromISR(sem, &woken);  /* count 1, then full */
    isr_give = CYC() - t;
    t = CYC();
    for (int i = 0; i < N; i++) xSemaphoreTakeFromISR(sem, &woken);  /* 1 hit, then empty */
    isr_take = CYC() - t;
    isr_path = sig_give(sem);
    portYIELD_FROM_ISR(woken);
}
static void task(void *arg)
{
    (void)arg;
    BaseType_t w;
    uint32_t t = CYC();
    for (int i = 0; i < N; i++) xSemaphoreGive(sem);
    uint32_t tg = CYC() - t;
    t = CYC();
    for (int i = 0; i < N; i++) xSemaphoreTake(sem, 0);
    uint32_t tt = CYC() - t;
    t = CYC();
    for (int i = 0; i < N; i++) xSemaphoreGiveFromISR(sem, &w);       /* FromISR from a task */
    uint32_t tf = CYC() - t;
    xSemaphoreTake(sem, 0);
    board_printf_raw("task: IPSR=%u  xSemaphoreGive        %u ns/op\n", (unsigned)ipsr(), tg * 40 / N);
    board_printf_raw("task: IPSR=%u  xSemaphoreTake(,0)    %u ns/op\n", (unsigned)ipsr(), tt * 40 / N);
    board_printf_raw("task: IPSR=%u  xSemaphoreGiveFromISR %u ns/op (no assert!)\n", (unsigned)ipsr(), tf * 40 / N);
    NVIC_IPR(8) = 0x40; NVIC_ISER0 = 1u << 8;
    STIR = 8;                                   /* run the ISR now */
    __asm volatile("dsb; isb");
    board_printf_raw("ISR : IPSR=%u xSemaphoreGiveFromISR %u ns/op\n", (unsigned)isr_ipsr, isr_give * 40 / N);
    board_printf_raw("ISR : IPSR=%u xSemaphoreTakeFromISR %u ns/op\n", (unsigned)isr_ipsr, isr_take * 40 / N);
    xSemaphoreTake(sem, 0);
    board_printf_raw("sig_give(): from ISR took %s path, from task took %s path\n",
                     isr_path ? "FromISR" : "task", sig_give(sem) ? "FromISR" : "task");
    board_exit(0);
}
int main(void)
{
    sem = xSemaphoreCreateBinary();
    xTaskCreate(task, "t", 512, NULL, 2, NULL);
    vTaskStartScheduler();
    return 1;
}
```

출력에서 볼 것:

- **FromISR give가 태스크용 give보다 싸다**: ISR 안에서 1.54 µs, 태스크용 2.50 µs(QEMU icount 기준). 태스크용은 `xQueueGenericSend()`의 `for(;;)` 루프 · 타임아웃 구조체 · 중첩 카운터를 거치고, FromISR은 저장/복원 BASEPRI 한 쌍과 리스트 조작뿐이다. "ISR 진입을 가능한 한 빠르고 단순하게"라는 소스 주석의 숫자 버전이다.
- **FromISR을 태스크에서 부르면 assert가 안 터진다**(1.28 µs). `vPortValidateInterruptPriority()`는 IPSR이 16 이상(= 외부 IRQ)일 때만 우선순위를 검사하고, IPSR = 0(thread mode)이면 그냥 지나간다. 태스크 문맥에서는 BASEPRI 저장/복원도 올바르게 동작하므로 이 포트에서는 실제로 문제가 없다. 그래서 ISR 안(1.54 µs)보다 오히려 빠르다 — 검사 함수 본문을 건너뛰기 때문이다. 다만 FreeRTOS 문서는 FromISR을 태스크에서 쓰는 것을 보장하지 않고, 깨운 태스크로의 전환을 `woken`으로 직접 처리해야 하므로 습관으로 삼지 않는다.
- `xPortIsInsideInterrupt()`는 IPSR이 0이 아닌지만 본다(`portmacro.h` 190행). `sig_give()`처럼 드라이버 공용 함수가 양쪽 문맥에서 불릴 때 쓰는 표준 방법이다. Zephyr의 `k_is_in_isr()`도 같은 일을 한다(§6).

**Don 경험과 연결**: SSD 펌웨어에서 "ISR에서도 불리고 executive 루프에서도 불리는 로그 함수"를 만들 때, 인터럽트를 끌지 말지를 호출자 문맥에 따라 바꿨던 것과 같은 문제다. RTOS에서는 그 분기가 "어느 API를 부르나"로 바뀐다.

**함정**: `xPortIsInsideInterrupt()`는 PendSV · SysTick · SVC 안에서도 참이다(IPSR 11, 14, 15). 그리고 문턱 위(zero-latency) ISR에서도 참이므로, "ISR이면 FromISR을 부른다"는 분기만으로는 §5의 우선순위 규칙까지 지켜 주지 않는다.

## 3. `pxHigherPriorityTaskWoken`과 `portYIELD_FROM_ISR` — "스위치는 나가면서"

> D1 §4는 세마포어 하나로 이 규약을 소개하고, yield를 빼먹었을 때 지연이 0~1 ms에 고르게 퍼지는 히스토그램(n = 200, 1 kHz tick)을 이미 측정했다. 이 절은 그 결과를 반복하지 않고 **다른 각도**에서 본다: NULL을 넘기는 경우, tick 주파수를 바꾸는 경우, 한 ISR 안에서 여러 API를 부를 때 생기는 플래그 버그.

### 3.1 직관과 순서

ISR 안에서는 컨텍스트 스위치를 할 수 없다. 스위치는 "지금 돌던 태스크의 레지스터를 그 태스크 스택에 저장하고 다른 태스크 스택에서 꺼내는" 일인데, ISR이 돌고 있는 동안 CPU는 handler mode에 있고 태스크 스택(PSP) 위에는 하드웨어가 쌓은 예외 프레임이 있다. 그래서 Cortex-M RTOS는 스위치를 **가장 낮은 우선순위의 PendSV 예외**에 맡긴다(B4, C2). ISR은 PendSV를 pending으로 만들어 두기만 하고, 모든 ISR이 끝나면 하드웨어가 tail-chaining으로 PendSV에 들어간다.

그림 2 — FreeRTOS ISR이 높은 우선순위 태스크를 깨우는 순서. ③의 `portYIELD_FROM_ISR`은 그 자리에서 스위치하지 않고 ICSR의 PENDSVSET 비트만 쓴다. 그래서 ④처럼 yield 뒤의 ISR 코드도 끝까지 돈다. 스위치는 ⑤ PendSV에서, ISR이 끝난 직후에 일어난다.

V11.3.2 `portable/GCC/ARM_CM3/portmacro.h` 98~111행이 정의다.

```c
#define portEND_SWITCHING_ISR( xSwitchRequired ) \
    do                                           \
    {                                            \
        if( xSwitchRequired != pdFALSE )         \
        {                                        \
            traceISR_EXIT_TO_SCHEDULER();        \
            portYIELD();                         \
        }                                        \
        else                                     \
        {                                        \
            traceISR_EXIT();                     \
        }                                        \
    } while( 0 )
#define portYIELD_FROM_ISR( x )    portEND_SWITCHING_ISR( x )
```

`portYIELD()`는 `portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT;` 뒤에 `dsb` · `isb`다. 두 이름(`portYIELD_FROM_ISR`, `portEND_SWITCHING_ISR`)은 이 포트에서 **완전히 같다**. 오래된 포트 중에는 한쪽 이름만 정의한 것이 있어서 둘 다 남아 있다. 새 코드는 `portYIELD_FROM_ISR`을 쓴다.

규약을 정리하면 네 줄이다.

1. `BaseType_t woken = pdFALSE;` — **반드시 pdFALSE로 초기화**. FromISR API는 깨운 태스크가 지금 돌던 태스크보다 높을 때 `pdTRUE`로 **올리기만** 하고 내리지 않는다.
2. ISR 안의 **모든** FromISR 호출에 **같은** `&woken`을 넘긴다. 하나라도 높은 태스크를 깨웠으면 `pdTRUE`로 남는다.
3. ISR **맨 끝**에서 `portYIELD_FROM_ISR(woken);` 한 번. 중간에 불러도 동작은 같지만(PENDSVSET은 ISR이 끝나야 효과가 있다), 읽는 사람이 "여기서 전환된다"고 오해하고 그 뒤에 코드를 덧붙이기 쉽다.
4. `woken`은 **반환값이 아니다**. FromISR API의 반환값은 성공/실패(`pdPASS`, `errQUEUE_FULL`)다.

"woken이 참"의 정확한 뜻은 "깨운 태스크의 우선순위 > `pxCurrentTCB`의 우선순위"다(`tasks.c` `xTaskRemoveFromEventList()`, 5500행). 같은 우선순위면 거짓이다 — 같은 우선순위 태스크끼리는 tick의 time slicing이 순서를 정한다.

### 3.2 빼먹어도 "언젠가는" 전환되는 이유 — `xYieldPendings`

D1 §4.2에서 소스로 본 안전망을 짧게 다시 짚는다. `xTaskRemoveFromEventList()`는 깨운 태스크가 더 높으면 `xReturn = pdTRUE`와 함께 `xYieldPendings[ 0 ] = pdTRUE`도 세운다(주석: "in case the user is not using the xHigherPriorityTaskWoken parameter"). 그리고 `xTaskIncrementTick()`(4831행에서 시작) 끝부분, 5020행에서

```c
                if( xYieldPendings[ 0 ] != pdFALSE )
                {
                    xSwitchRequired = pdTRUE;
                }
```

로 바꿔 SysTick 핸들러가 PendSV를 걸게 한다(`port.c` 501~507행, `configUSE_PREEMPTION == 1`일 때). 그러니 yield를 빼먹은 대가는 **"다음 tick까지"**, 또는 그 전에 다른 이유(다른 ISR의 yield, 태스크의 블로킹 호출)로 스위치가 일어나면 그때까지다.

그렇다면 예측: **최악 지연 ≈ tick 주기 1개, 평균 ≈ tick 주기의 절반**. tick 주파수를 바꿔서 확인한다.

### 3.3 예제 4 — NULL을 넘기면: tick 주파수 1000 · 250 · 100 Hz

무엇을 확인하는 코드인지: `xSemaphoreGiveFromISR(sem, NULL)`은 API가 허용하는 호출이다. V11.3.2 `queue.c`(7곳)와 `tasks.c`(4곳)는 `if( pxHigherPriorityTaskWoken != NULL )`을 확인한 뒤에만 플래그를 쓴다. NULL을 넘기면 woken을 받을 길이 없으니 yield도 할 수 없다. TIMER0을 tick 주기의 1.37배로 돌려 IRQ 위상이 tick에 대해 고르게 흩어지게 하고, prio 1 busy 태스크가 CPU를 쥔 상태에서 prio 3 waiter가 깨어나는 지연을 100번 잰다. 같은 소스를 `configTICK_RATE_HZ`만 바꿔 세 번 빌드한다.

```c
/* E1 ex5 — pxHigherPriorityTaskWoken = NULL: the wake waits for the next tick.
 *   Build with -DconfigTICK_RATE_HZ=1000/250/100; the worst case scales with the tick period */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "e1.h"
#define N 100
#define TICK_CYC (25000000u / configTICK_RATE_HZ)
static SemaphoreHandle_t sem;
static volatile int pass_null;
void TIMER0_IRQHandler(void)
{
    TIMER_INTCLR(TIMER0_BASE) = 1;
    if (pass_null) {
        xSemaphoreGiveFromISR(sem, NULL);           /* allowed by the API: "optional" */
    } else {
        BaseType_t woken = pdFALSE;
        xSemaphoreGiveFromISR(sem, &woken);
        portYIELD_FROM_ISR(woken);
    }
}
static void busy(void *arg) { (void)arg; for (;;) { } }   /* prio 1 keeps the CPU busy */
static void run(int null)
{
    stat_t s = { 0 };
    pass_null = null;
    timer0_start(TICK_CYC + TICK_CYC * 37u / 100u, 0x40);  /* 1.37 tick: phase drifts */
    for (int i = 0; i < N; i++) {
        xSemaphoreTake(sem, portMAX_DELAY);
        stat_add(&s, timer0_elapsed());
    }
    timer0_stop();
    board_printf_raw("tick=%u Hz %s ", (unsigned)configTICK_RATE_HZ, null ? "NULL " : "woken");
    stat_print("", &s);
}
static void waiter(void *arg)                       /* prio 3 */
{
    (void)arg;
    run(0);
    run(1);
    board_exit(0);
}
int main(void)
{
    sem = xSemaphoreCreateBinary();
    xTaskCreate(waiter, "wait", 512, NULL, 3, NULL);
    xTaskCreate(busy, "busy", 128, NULL, 1, NULL);
    vTaskStartScheduler();
    return 1;
}
```

### 3.4 예제 5 — 한 ISR에 FromISR이 둘 이상일 때의 플래그 버그

무엇을 확인하는 코드인지: UART 같은 주변장치 ISR은 흔히 "RX 완료"와 "TX 비었음"을 한 번에 처리하며 FromISR을 두 번 부른다. rx 세마포어에는 prio 3 hi 태스크가 기다리고, tx 세마포어에는 아무도 기다리지 않는다. 네 가지 ISR을 비교한다.

- A (정답): 한 플래그를 두 호출에 공유하고 마지막에 yield 한 번.
- B (버그): 호출마다 다른 플래그 `w1`, `w2`를 쓰고 마지막 것만 yield에 넘긴다. hi를 깨운 `w1`이 버려진다.
- C (버그): API의 **반환값**(`pdPASS`)을 woken인 줄 알고 yield에 넘긴다. 아무도 안 깨웠는데 매번 PendSV가 걸린다.
- D (정답): C와 같은 ISR에서 woken을 제대로 넘긴다.

PendSV가 실제로 몇 번 스위치 판단을 했는지 세려고, 앱 폴더(`trace/`)에 템플릿 설정을 include하고 trace 매크로 하나만 더한 `FreeRTOSConfig.h`를 두었다.

```c
/* E1: template config + a counter of context-switch decisions (one per PendSV run) */
#include "/var/rtoslab/templates/freertos-mps2/FreeRTOSConfig.h"
extern volatile unsigned long e1_switch_calls;
#define traceTASK_SWITCHED_IN() ( e1_switch_calls++ )
```

`traceTASK_SWITCHED_IN()`은 `vTaskSwitchContext()`가 다음 태스크를 고를 때마다 불린다. PendSV 핸들러는 매번 `vTaskSwitchContext()`를 부르므로(같은 태스크로 "전환"하더라도) PendSV 실행 횟수를 세는 셈이다. busy 태스크는 2 µs(50 사이클) 넘게 CPU를 못 받은 구간을 모두 더해 "빼앗긴 시간"을 잰다.

```c
/* E1 ex6 — woken-flag bugs inside one ISR: overwritten flag, "return value as woken" */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "../e1.h"
#define N 100
volatile unsigned long e1_switch_calls;
static SemaphoreHandle_t rx, tx;                  /* rx: hi task waits; tx: nobody waits */
static volatile int mode;
static volatile uint32_t nstall, sumstall;
void TIMER0_IRQHandler(void)
{
    TIMER_INTCLR(TIMER0_BASE) = 1;
    if (mode == 0) {                              /* A: one flag for all calls, yield once */
        BaseType_t woken = pdFALSE;
        xSemaphoreGiveFromISR(rx, &woken);
        xSemaphoreGiveFromISR(tx, &woken);
        portYIELD_FROM_ISR(woken);
    } else if (mode == 1) {                       /* B: separate flags, yield on the last */
        BaseType_t w1 = pdFALSE, w2 = pdFALSE;
        xSemaphoreGiveFromISR(rx, &w1);           /* w1 = pdTRUE ... and then forgotten */
        xSemaphoreGiveFromISR(tx, &w2);
        portYIELD_FROM_ISR(w2);
    } else {                                      /* C: return value used as the flag */
        BaseType_t woken = pdFALSE;               /* D: same ISR, correct flag */
        BaseType_t r = xSemaphoreGiveFromISR(tx, &woken);  /* pdPASS = 1 when tx was empty */
        xSemaphoreTakeFromISR(tx, &woken);        /* empty it again for the next IRQ */
        portYIELD_FROM_ISR(mode == 2 ? r : woken);
    }
}
static void busy(void *arg)                       /* prio 1: sums the time it lost */
{
    (void)arg;
    uint32_t prev = CYC();
    for (;;) { uint32_t now = CYC(), g = now - prev; if (g > 50) { nstall++; sumstall += g; } prev = now; }
}
static void hi(void *arg)                         /* prio 3 */
{
    (void)arg;
    static const char *name[] = { "A one flag     ", "B overwritten  ", "C ret-as-woken ", "D correct flag " };
    for (mode = 0; mode < 4; mode++) {
        stat_t s = { 0 };
        vTaskDelay(2);
        nstall = sumstall = 0; e1_switch_calls = 0;
        timer0_start(25000u + 925u, 0x40);        /* 1.037 ms */
        if (mode < 2) {
```

### 3.5 Don 경험과 연결, 그리고 함정

SSD 펌웨어의 "ISR이 이벤트 비트를 세우고, executive 루프가 다음 바퀴에 본다"는 구조에서 executive 루프의 한 바퀴 주기가 곧 최악 반응 시간이었다. FreeRTOS에서 yield를 빼먹으면 **tick 주기가 그 바퀴 주기 역할을 한다**. 우선순위 선점이라는 RTOS의 핵심 장점을 한 줄 누락으로 잃는 셈이다.

함정 세 가지:

- **"테스트는 다 통과했다"**: 값은 맞고 지연만 늘어난다. 지연 히스토그램(E3)을 재지 않으면 안 보인다.
- **"다음 tick"이 멀수록 나빠진다**: 예제 4처럼 지연은 tick 주기에 비례한다. 안전망이 tick이 아니라 "다음에 우연히 일어나는 스위치 지점"인 커널에서는 더 길어질 수 있다 — Zephyr의 direct ISR에서 같은 종류의 실수가 tickless 때문에 최대 660 ms(이론 상한 671 ms)까지 늘어나는 것을 §6.5에서 본다.
- **SMP FreeRTOS**에서는 `portYIELD_FROM_ISR`이 "이 코어"만 스위치한다. 다른 코어의 태스크를 깨운 경우는 커널이 코어 간 인터럽트로 처리한다(C10).

### 4.2 예제 6 — assert를 켜고 여덟 가지 실수를 한 번씩

무엇을 확인하는 코드인지: TIMER0 ISR(우선순위 0x40, MODE 8만 0x10)이 한 번 뜨면서 MODE에 따라 한 가지 실수를 한다. lab 템플릿의 `configASSERT`는 파일:줄을 찍고 종료코드 253으로 끝난다. assert가 안 터지면 태스크가 살아서 상태를 찍는다.

> B3 예제 11(문턱 위 ISR의 FromISR, 우선순위 미설정, PRIGROUP)과 C7 예제 5(ISR에서 `taskENTER_CRITICAL`)가 이미 assert 두 개를 보여 줬다. 이 예제는 "블로킹 · 지연 · 할당 · 뮤텍스"까지 넓혀서 **어느 assert가 무엇을 잡는지** 지도를 만든다.

```c
/* E1 ex3 — what each ISR rule violation actually does (FreeRTOS V11.3.2, configASSERT on)
 *   -DMODE=1..8, see the switch in the ISR */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "queue.h"
#include "e1.h"
static SemaphoreHandle_t sem, mtx;
static QueueHandle_t q;
static volatile int isr_done;
void TIMER0_IRQHandler(void)
{
    TIMER_INTCLR(TIMER0_BASE) = 1;
    timer0_stop();
    BaseType_t woken = pdFALSE;
    uint32_t v = 7;
    switch (MODE) {
    case 1: xSemaphoreGive(sem); break;                     /* task API, no timeout   */
    case 2: (void)xQueueSend(q, &v, 0); break;              /* task API, "0 = no block" */
    case 3: (void)xSemaphoreTake(sem, 10); break;           /* blocking take, 10 ticks */
    case 4: vTaskDelay(1); break;                           /* sleep inside an ISR     */
    case 5: { void *p = pvPortMalloc(32); vPortFree(p); } break;
    case 6: xSemaphoreGiveFromISR(mtx, &woken); break;      /* mutex held by a task    */
    case 7: (void)xSemaphoreTakeFromISR(mtx, &woken); break;/* free mutex, taken by ISR */
    case 8: xSemaphoreGiveFromISR(sem, &woken); break;      /* ISR prio 0x10, see main */
    }
    isr_done = 1;
    portYIELD_FROM_ISR(woken);
}
static void task(void *arg)
{
    (void)arg;
    if (MODE == 6) xSemaphoreTake(mtx, 0);                  /* task owns the mutex */
    timer0_start(2500, MODE == 8 ? 0x10 : 0x40);            /* one IRQ after 100 us */
    vTaskDelay(2);
    board_printf_raw("MODE=%d: ISR returned (isr_done=%d), task alive\n", MODE, isr_done);
    if (MODE == 7) {
        board_printf_raw("  mutex holder after ISR take = %s\n",
                         xSemaphoreGetMutexHolder(mtx) == NULL ? "NULL (nobody)" : "task");
        board_printf_raw("  task take(mutex, 5) = %s\n",
                         xSemaphoreTake(mtx, 5) == pdTRUE ? "pdTRUE" : "pdFALSE (timeout)");
    }
    board_exit(0);
}
int main(void)
{
    sem = xSemaphoreCreateBinary();
    mtx = xSemaphoreCreateMutex();
    q = xQueueCreate(1, sizeof(uint32_t));
    xTaskCreate(task, "t", 512, NULL, 2, NULL);
    vTaskStartScheduler();
    return 1;
}
```

출력에서 볼 것:

- **MODE 1~5가 전부 같은 줄 `port.c:438`에서 잡힌다.** `vPortEnterCritical()`의 `configASSERT( ( portNVIC_INT_CTRL_REG & portVECTACTIVE_MASK ) == 0 )` 하나다. 태스크용 give, timeout 0인 send, 블로킹 take, `vTaskDelay`, `pvPortMalloc` — 다섯 가지 실수가 결국 모두 `taskENTER_CRITICAL()`을 지나기 때문이다. `vTaskDelay`와 `pvPortMalloc`은 `vTaskSuspendAll()`로 스케줄러를 잠근 뒤 `xTaskResumeAll()` 안에서 `taskENTER_CRITICAL()`을 부르다 걸린다. 즉 **"FromISR이 아닌 커널 함수는 거의 전부 VECTACTIVE 검사 하나에 걸린다"**. 이 assert가 FreeRTOS ISR 규칙의 문지기다.

- **MODE 6** — 태스크가 쥔 뮤텍스를 ISR이 give: `queue.c:1360`의 `configASSERT( ... !( ( pxQueue->uxQueueType == queueQUEUE_IS_MUTEX ) && ( pxQueue->u.xSemaphore.xMutexHolder != NULL ) ) )`. 소스 주석: "priority inheritance makes no sense for an interrupt, only tasks."
- **MODE 7이 가장 무섭다 — assert가 없다.** 비어 있는 뮤텍스를 ISR이 `xSemaphoreTakeFromISR`로 가져가면 성공한다. 그런데 소유자 기록(`xMutexHolder`)은 태스크용 take 경로(`xQueueSemaphoreTake`)에서만 채워지므로 **소유자 NULL인 잠긴 뮤텍스**가 된다. 이후 태스크의 take는 timeout까지 기다리다 실패하고, 이 뮤텍스를 돌려줄 "소유자"가 세상에 없다. 우선순위 상속도 상속해 줄 대상이 없다. 증상은 "가끔 영원히 멈추는 태스크"다.
- **MODE 8** — 우선순위 0x10(문턱 0x20보다 급함) ISR의 FromISR: `port.c:803`. §5에서 이 검사를 자세히 본다.

### 4.3 예제 7 — assert를 끄면 같은 실수가 무엇이 되나

assert가 있으면 첫 실행에서 멈춘다. 양산 빌드처럼 `configASSERT`를 끄면 같은 실수가 **무엇으로 바뀌는지**가 현장 디버깅에서 중요하다. 그것을 직접 본다.

무엇을 확인하는 코드인지: 앱 폴더(`noassert/`)에 템플릿 설정을 include하고 `configASSERT`만 `#undef`한 `FreeRTOSConfig.h`를 둔다. prio 1 victim 태스크가 CPU를 쥐고 돌며 "자기가 CPU를 못 받은 가장 긴 구간"을 기록한다. ISR은 victim이 도는 중에 한 번 떠서 MODE에 따라 태스크용 API를 부른다. MODE 3(블로킹 take)은 시스템이 멈출 것으로 예상해, C7 예제 11과 같은 방식의 **문턱 위(0x00) 감시 ISR**(DUALTIMER, IRQ 10)을 20 ms 뒤에 띄운다. 감시 ISR은 커널을 부르지 않고 MSP 위의 예외 프레임에서 끊긴 문맥의 IPSR과 PC만 읽는다.

```c
/* E1 ex4 — the same violations with configASSERT OFF: what really happens
 *   victim (prio 1) spins and records its longest gap; the ISR fires once while victim runs */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "queue.h"
#include "../e1.h"
static SemaphoreHandle_t sem, mtx;
static QueueHandle_t q;
static volatile uint32_t gap_max, isr_bp_after, isr_ret = 99;
void TIMER0_IRQHandler(void)
{
    TIMER_INTCLR(TIMER0_BASE) = 1;
    timer0_stop();
    uint32_t v = 7;
    switch (MODE) {
    case 1: isr_ret = xSemaphoreGive(sem); break;           /* task API, never blocks here */
    case 2: isr_ret = xQueueSend(q, &v, 0); break;
    case 3: isr_ret = xSemaphoreTake(sem, 10); break;       /* count = 0 -> "blocks"       */
    case 4: vTaskDelay(5); isr_ret = 0; break;
    }
    isr_bp_after = basepri();
}
/* zero-latency "watchdog" (IRQ10, prio 0x00, no kernel calls): who is running after 20 ms? */
#define DT1(o) REG32(0x40002000u + (o))
void wd_c(uint32_t *f)
{
    board_printf_raw("  [wd 20ms] interrupted ctx: IPSR=%u PC=0x%x (still inside an ISR)\n",
                     (unsigned)(f[7] & 0x1FFu), (unsigned)f[6]);
    board_exit(2);
}
__attribute__((naked)) void DUALTIMER_IRQHandler(void) { __asm volatile("mrs r0, msp\n b wd_c"); }
static void victim(void *arg)                               /* prio 1: the interrupted task */
{
    (void)arg;
    uint32_t prev = CYC();
    for (;;) {
        uint32_t now = CYC();
        if (now - prev > gap_max) gap_max = now - prev;
        prev = now;
    }
}
static void observer(void *arg)                             /* prio 3 */
{
    (void)arg;
    vTaskDelay(2);
    gap_max = 0;
    if (MODE == 3) {                                        /* arm the 20 ms watchdog */
        DT1(0x00) = 20u * 25000u; DT1(0x08) = 0x80u | 0x20u | 0x02u | 0x01u;
        NVIC_IPR(10) = 0x00; NVIC_ISER0 = 1u << 10;
    }
    timer0_start(25000, 0x40);                              /* one IRQ after 1 ms */
    vTaskDelay(30);
    board_printf_raw("MODE=%d: api ret=%u, BASEPRI after=0x%x, victim longest gap=%u us\n",
                     MODE, (unsigned)isr_ret, (unsigned)isr_bp_after, (unsigned)(gap_max / 25u));
    if (MODE == 1) board_printf_raw("  sem count now=%u (give worked)\n",
                                    (unsigned)uxSemaphoreGetCount(sem));
    board_exit(0);
}
int main(void)
{
    sem = xSemaphoreCreateBinary();
    mtx = xSemaphoreCreateMutex();
    q = xQueueCreate(1, sizeof(uint32_t));
    (void)mtx;
    xTaskCreate(victim, "victim", 256, NULL, 1, NULL);
    xTaskCreate(observer, "obs", 512, NULL, 3, NULL);
    vTaskStartScheduler();
    return 1;
}
```

출력에서 볼 것:

- **MODE 1 · 2 (태스크용 give, timeout 0 send)**: 겉보기에 정상이다. give는 성공했고(count 1), ISR이 끝난 뒤 BASEPRI도 0이다. 단일 코어 Cortex-M3에서 문턱 아래 ISR이 돌 수 있는 순간에는 BASEPRI가 이미 0이고 `uxCriticalNesting`도 0이므로(태스크가 크리티컬 섹션 안이면 이 ISR은 막혀 있다), "0으로 내린다"가 우연히 맞는 값이 된다. **우연히 동작하는 코드**다. 포트가 바뀌거나, 깨운 태스크가 높아서 `queueYIELD_IF_USING_PREEMPTION()`이 불리거나, 언젠가 이 함수에 블로킹 경로가 생기면 깨진다. 그래서 FreeRTOS는 이것을 assert로 막는다.
- **MODE 3 (블로킹 take, count 0, timeout 10 tick)**: 20 ms 뒤 감시 ISR이 본 것은 **IPSR = 24(= IRQ 8, TIMER0 ISR) 안의 PC 0x1288 = `vListInsert()`의 `list.c:192`** — 1 ms에 들어간 ISR이 19 ms 동안 못 나왔다. `list.c:192`는 FreeRTOS에서 유명한 줄이다. 바로 위 주석이 "If you find your application is crashing here then likely causes are ... 3) Calling an API function from within a critical section or when the scheduler is suspended, or calling an API function that does not end in "FromISR" from an interrupt."이고, 루프 안 주석은 "IF YOU FIND YOUR CODE STUCK HERE, SEE THE NOTE JUST ABOVE."다. 소스를 따라가면 이렇게 해석된다: `xQueueSemaphoreTake()`는 끊긴 victim을 대기 리스트에 넣고 `portYIELD_WITHIN_API()`를 부르지만, ISR 안이라 스위치가 일어나지 않고 함수의 `for(;;)`가 다시 돈다. tick은 이 ISR보다 낮은 SysTick(0xFF)이 세므로 **timeout은 영원히 지나지 않는다**. 그 상태로 같은 리스트 항목을 다시 넣으면서 리스트가 고리로 꼬여 `vListInsert`의 정렬 삽입 루프가 끝나지 않는다. 결과: 0x40 이하 모든 IRQ와 모든 태스크가 영원히 멈춘다.
- **MODE 4 (`vTaskDelay(5)`)**: ISR은 바로 나왔는데 **victim이 5 ms 동안 CPU를 못 받았다**(4999 µs). 커널이 `pxCurrentTCB`(= ISR이 끊은 victim)를 delayed 리스트에 넣었기 때문이다. victim 코드에는 `vTaskDelay`가 한 줄도 없는데 victim이 잔다. 현장에서 이 증상은 "어떤 태스크가 가끔 이유 없이 몇 ms씩 멈춘다"로 보이고, 멈추는 태스크가 매번 다르다(그때 끊긴 태스크가 다르니까).

그림 4 — assert를 끄고 같은 실수를 했을 때 실제로 일어난 일(예제 7, 예제 10). 주황은 "지금은 동작하지만 보장 없음", 빨강은 실제 고장. 블로킹 계열 실수의 공통점은 **엉뚱한 태스크(끊긴 태스크)가 대가를 치른다**는 것이다.

**Don 경험과 연결**: SSD 펌웨어에서 "커맨드 처리 루프가 가끔 수 ms 멈추는데 그 루프 코드에는 아무 문제가 없던" 버그를 떠올리면 된다. 원인이 다른 곳(ISR)에 있고, 피해자가 매번 바뀌는 버그는 가장 찾기 어렵다. 그래서 RTOS에서는 **assert를 끈 양산 빌드라도 `configASSERT`를 "로그 남기고 리셋"으로 정의해 남겨 두는** 팀이 많다(코드 크기와 몇 사이클을 대가로).

### 4.4 예제 8 — "짧게"를 숫자로: 금지된 일 하나가 ISR을 얼마나 늘리나

무엇을 확인하는 코드인지: 같은 ISR(give 하나)에 금지된 일을 하나씩 더해 ISR 본문 시간을 FPGAIO 카운터로 잰다. 각 모드를 3번 돌려 첫 실행과 최솟값(정상 상태)을 함께 본다. 끝에서 `objdump`로 ISR이 실제로 부르는 함수를 확인한다.

```c
/* E1 ex8 — how long the ISR body takes when it does "forbidden" things (Cortex-M3, no FPU) */
#include <stdlib.h>
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "e1.h"
static SemaphoreHandle_t sem;
static volatile int mode;
static volatile float fin = 1.25f, fout;
static volatile uint32_t dur;
static volatile uint32_t sink;
void TIMER0_IRQHandler(void)                       /* pended by STIR, prio 0x40 */
{
    uint32_t t = CYC();
    BaseType_t woken = pdFALSE;
    switch (mode) {
    case 0: break;                                 /* just the give below */
    case 1: board_printf_raw("[isr] imu sample %u\n", (unsigned)t); break;  /* ~24 chars */
    case 2: { float x = fin;                       /* 16 multiply-adds: soft-float calls on M3 */
              for (int i = 0; i < 16; i++) x = x * 1.0001f + 0.5f;
              fout = x; } break;
    case 3: { void *p = malloc(64); sink = (uint32_t)(uintptr_t)p; free(p); } break; /* newlib */
    case 4: for (volatile int i = 0; i < 200; i++) { } break;  /* "short" polling loop */
    }
    xSemaphoreGiveFromISR(sem, &woken);
    dur = CYC() - t;
    portYIELD_FROM_ISR(woken);
}
static void task(void *arg)
{
    (void)arg;
    static const char *name[] = { "give only        ", "+ printf 24 chars", "+ 16 float madd  ",
                                  "+ malloc/free 64B", "+ 200-iter loop  " };
    static uint32_t res[5];
    NVIC_IPR(8) = 0x40; NVIC_ISER0 = 1u << 8;
    for (mode = 0; mode < 5; mode++) {
        uint32_t best = 0xFFFFFFFFu;
        for (int r = 0; r < 3; r++) {               /* 1st run includes first-use costs */
            STIR = 8;
            xSemaphoreTake(sem, portMAX_DELAY);
            if (dur < best) best = dur;
            if (r == 0) res[mode] = dur;
        }
        board_printf_raw("\n%s first=%u ns  steady=%u ns\n", name[mode], res[mode] * 40, best * 40);
    }
    board_exit(0);
}
int main(void)
{
    sem = xSemaphoreCreateBinary();
    xTaskCreate(task, "t", 512, NULL, 2, NULL);
    vTaskStartScheduler();
    return 1;
}
```

출력에서 볼 것:

- give만 하는 ISR 본문은 **2.16 µs**. 이것이 기준선이다.
- printf 한 줄(실제로 찍힌 문자열은 줄바꿈 포함 23자 — 소스 주석의 "~24"는 어림이었다)은 **12.6 µs = 기준선의 6배**. 그런데 이것은 QEMU의 UART가 baud 시간을 모델링하지 않아서 나온 숫자다. 실칩 115200 baud, TX FIFO 1바이트에서 블로킹 putc라면 23자 × 86.8 µs ≈ **2.0 ms**(예제 12에서 계산)이고, 그동안 같거나 낮은 우선순위 IRQ와 모든 태스크가 기다린다. 1 kHz rate loop 두 주기다.
- Cortex-M3에는 FPU가 없어서 `x * 1.0001f + 0.5f`가 `__aeabi_fmul`, `__addsf3` **라이브러리 호출**로 컴파일됐다. 16회에 **46.9 µs**. 드론 FC에서 "ISR에서 자이로 값을 보정까지 해서 넘기자"는 유혹이 이 숫자다. FPU가 있는 M4F/M7에서는 연산 자체는 몇 사이클이지만, ISR이 FPU를 쓰는 순간 예외 프레임이 8워드에서 26워드로 커지고(lazy stacking이 켜져 있으면 실제 저장은 첫 FPU 명령 때) 그 비용이 붙는다. B2 예제 12와 B6 예제 4에서 프레임 크기 변화를 봤다. QEMU는 스태킹 사이클을 모델링하지 않으므로 그 비용은 여기서 재지 못한다.
- newlib `malloc`/`free`는 4.5 µs(첫 호출 6.4 µs — 처음에는 `sbrk`로 힙을 키운다). 시간보다 **재진입**이 문제다. newlib은 `__malloc_lock`/`__malloc_unlock` 훅으로 보호하는데, 기본 구현은 아무것도 하지 않는다. 태스크가 `malloc` 안에 있을 때 ISR이 `malloc`을 부르면 같은 자유 리스트를 동시에 고친다. FreeRTOS `pvPortMalloc`은 예제 6 MODE=5처럼 assert로 막힌다.
- 200회 빈 루프(`volatile` 카운터)는 **40.8 µs**. "잠깐 기다리는 루프"가 ISR 안에 있으면 이만큼이 그대로 다른 모든 것의 지연이 된다. 하드웨어 레지스터 상태를 폴링하는 루프는 상한조차 없다.

"ISR을 짧게"의 기준은 절대값이 아니라 **예산**이다. 가장 짧은 마감(예: 20 kHz FOC 전류 루프 = 50 µs 주기)에서 그 ISR보다 낮거나 같은 우선순위의 모든 ISR 최악 길이를 합한 것이 남은 예산을 넘으면 안 된다. 이 계산과 측정 방법은 E3, 배치는 E2에서 한다.

### 4.5 뮤텍스는 왜 ISR에서 절대 안 되나

직관: 뮤텍스는 "열쇠"다. 열쇠를 빌려 간 사람(소유자)이 반드시 돌려준다는 약속 위에서 두 가지 기능이 동작한다. ① 소유자만 풀 수 있다. ② 높은 우선순위 태스크가 기다리면 소유자의 우선순위를 잠시 올려 준다(우선순위 상속, D3).

ISR은 둘 다 할 수 없다.

- ISR은 "소유자"가 될 수 없다. 커널의 소유자 필드는 `TaskHandle_t`(TCB 포인터)이고, ISR은 TCB가 없다. ISR 안에서 `pxCurrentTCB`는 **끊긴 태스크**를 가리킨다.
- ISR은 우선순위를 상속받을 수 없다. ISR의 우선순위는 NVIC가 정하고 태스크 우선순위와 다른 축이다.
- ISR은 기다릴 수 없으니, 뮤텍스가 잠겨 있을 때 할 수 있는 일이 없다. 바쁘게 기다리면 뮤텍스를 쥔 태스크가 못 돌아서 영원히 풀리지 않는다(단일 코어 교착).

예제 6에서 본 대로 FreeRTOS는 "소유자가 있는 뮤텍스를 ISR이 give"만 assert로 잡고(`queue.c:1360`), "ISR이 take"는 막지 않는다(MODE 7: 소유자 없는 잠긴 뮤텍스). Zephyr는 `k_mutex_lock()`과 `k_mutex_unlock()` 입구에서 `__ASSERT(!arch_is_in_isr(), "mutexes cannot be used inside ISRs")`로 둘 다 막는다(`kernel/mutex.c` 115, 234행, 예제 9).

ISR과 태스크가 같은 자원을 써야 하면 대안은 셋이다.

1. **짧은 크리티컬 섹션**: 태스크 쪽은 `taskENTER_CRITICAL()`, ISR 쪽은 `taskENTER_CRITICAL_FROM_ISR()`. 수 µs 이하일 때 (C7).
2. **소유권을 태스크 하나에**: ISR은 큐/스트림 버퍼로 요청만 넣고, 게이트키퍼 태스크가 자원을 독점한다 (D7 §5).
3. **lock-free 구조**: SPSC 링버퍼처럼 한쪽만 쓰고 한쪽만 읽는 구조 (D8).

### 4.6 FPU — 코어마다 규칙이 다르다

| 코어 | ISR에서 float을 쓰면 | 규칙 |
|---|---|---|
| Cortex-M0/M0+/M3 (FPU 없음) | 소프트웨어 라이브러리 호출. 예제 8: 16회 46.9 µs | ISR에서는 정수 · 고정소수점만. 변환은 태스크에서 |
| Cortex-M4F/M7/M33/M55 (FPU 있음, lazy stacking 기본) | 첫 FPU 명령에서 S0~S15 · FPSCR이 스택에 저장되어 프레임 26워드 (B6). 중첩 깊이만큼 MSP 사용량 증가 | 써도 되지만 MSP 크기를 FPU 프레임 기준으로 잡는다. 최악 지연에 스태킹 시간을 넣는다 |
| Zephyr + `CONFIG_FPU_SHARING` | 스레드 간 FP 문맥을 커널이 관리한다 | ISR에서의 FP 사용 규칙은 아키텍처마다 다르므로 Zephyr 문서 "Floating Point Services"(`doc/kernel/services/other/float.rst`)에서 확인 |

FreeRTOS의 ARM_CM4F 포트는 태스크 전환 때 EXC_RETURN 비트 4를 보고 "이 태스크가 FPU를 썼을 때만" S16~S31을 저장한다(B6, C2). ISR은 이 메커니즘 밖이므로 하드웨어 lazy stacking이 전부다.

## 5. 문지기 — `configASSERT`, `vPortValidateInterruptPriority`, `xPortIsInsideInterrupt`

### 5.1 `vPortValidateInterruptPriority()`가 하는 일

큐의 핵심 FromISR 4개(`xQueueGenericSendFromISR`, `xQueueGiveFromISR`, `xQueueReceiveFromISR`, `xQueuePeekFromISR`)와 `tasks.c`의 FromISR 6개(notify, resume, tick count, 우선순위 조회 — 목록은 B3 예제 11)는 입구에서 `portASSERT_IF_INTERRUPT_PRIORITY_INVALID()`를 부른다. 이벤트 그룹 · 타이머 · 스트림 버퍼의 FromISR은 내부에서 이 함수들을 거쳐 같은 검사에 닿는다. ARM_CM3 `portmacro.h`에서 이것은 `configASSERT_DEFINED == 1`일 때만 `vPortValidateInterruptPriority()`로 정의된다. 함수 본문(`port.c` 766~820행)의 핵심은 세 줄이다.

```c
        __asm volatile ( "mrs %0, ipsr" : "=r" ( ulCurrentInterrupt )::"memory" );
        if( ulCurrentInterrupt >= portFIRST_USER_INTERRUPT_NUMBER )
        {
            ucCurrentPriority = pcInterruptPriorityRegisters[ ulCurrentInterrupt ];
            configASSERT( ucCurrentPriority >= ucMaxSysCallPriority );      /* port.c:803 */
        }
        configASSERT( ( portAIRCR_REG & portPRIORITY_GROUP_MASK ) <= ulMaxPRIGROUPValue );  /* :819 */
```

- IPSR로 **지금 돌고 있는 예외 번호**를 읽고, 그것이 외부 IRQ(16 이상)이면 NVIC IPR 바이트를 직접 읽어 문턱과 비교한다. `ucMaxSysCallPriority`는 `xPortStartScheduler()`가 실제 칩의 구현 비트 수에 맞춰 계산해 둔 값이다(B3 예제 8).
- 두 번째 assert는 PRIGROUP(서브 우선순위 비트)이 0이 아니면 막는다(B3 §5.2).
- **검사하지 않는 경우**: IPSR이 16 미만 — thread mode(0)와 시스템 예외(SVC 11, PendSV 14, SysTick 15). 예제 2에서 태스크가 FromISR을 불러도 assert가 안 터진 이유다.

예제 6 MODE=8 출력(`port.c:803`)이 이 검사가 잡은 것이다. "우선순위를 안 정한 IRQ = 0 = 무조건 걸림"은 B3 예제 11 MODE=2에서 봤다.

### 5.2 Zephyr에는 이 검사가 없다 — 대신 빌드 시점에

Zephyr Cortex-M에는 "지금 ISR의 우선순위가 커널이 막을 수 있는 범위인가"를 **런타임에** 보는 검사가 없다. 대신 구조가 실수를 어렵게 만든다.

- `IRQ_CONNECT(irq, prio, ...)`의 `prio`는 논리 번호이고, 아키텍처 코드가 커널이 쓰는 영역(`_IRQ_PRIO_OFFSET`) 아래로만 매핑한다(B3 §8.1). 보통 IRQ는 구조적으로 `irq_lock()`의 BASEPRI 아래에 놓인다.
- 커널 밖(zero-latency) IRQ는 `IRQ_ZERO_LATENCY` 플래그로 **명시해야만** 만들 수 있다. `include/zephyr/arch/arm/irq.h`의 `ARCH_IRQ_CONNECT`는 이 플래그를 보면 `BUILD_ASSERT(!(flags_p & IRQ_ZERO_LATENCY), "ZLI interrupts must be registered using IRQ_DIRECT_CONNECT()")`로 빌드를 실패시키고, `ARCH_IRQ_DIRECT_CONNECT`는 `CONFIG_ZERO_LATENCY_IRQS`가 꺼져 있으면 `"ZLI interrupt registered but feature is disabled"`로 실패시킨다. 우선순위 범위도 `_CHECK_PRIO`의 `BUILD_ASSERT`가 본다.
- 그래서 Zephyr에서 남는 실수는 "ZLI ISR 안에서 커널 API를 부르는 것"인데, 이것은 런타임 검사가 없다. `ISR_DIRECT_DECLARE` 주석이 "Any ISRs that serve IRQs configured with the IRQ_ZERO_LATENCY flag must always return 0"이라고 경고하는 것이 전부다. 이 영역 설계는 E2.

### 5.3 `configASSERT`를 양산에서 어떻게 하나

| 선택 | 장점 | 단점 |
|---|---|---|
| 개발: 무한 루프 + 브레이크포인트 (`taskDISABLE_INTERRUPTS(); for(;;);`) | 디버거로 콜 스택을 바로 본다 | 현장에서는 멈춤 = 워치독 리셋 |
| 양산: 끔 | 코드 크기 · 사이클 절약 | 예제 7처럼 실수가 "가끔 나는 이상한 버그"가 된다 |
| 양산: 파일 · 줄 · LR을 noinit RAM에 기록하고 리셋 | 현장 로그에서 원인 추적 (M1, E8) | 수 KB 코드, 문자열 테이블 |

lab 템플릿의 정의(`board_printf_raw` + `board_exit(253)`)는 세 번째의 축소판이다. FreeRTOS는 `configASSERT`가 정의되어 있으면 `configASSERT_DEFINED`를 1로 만들고(`FreeRTOS.h` 99~101행), 포트는 그 값으로 `vPortValidateInterruptPriority()` 자체를 넣거나 뺀다. **assert를 끄면 우선순위 검사 함수도 이미지에서 사라진다**는 뜻이다.

## 6. Zephyr 쪽 규칙 — 같은 이름, `K_NO_WAIT`, 그리고 direct ISR

### 6.1 직관: 이름을 나누는 대신 인자로 나눈다

Zephyr는 FreeRTOS처럼 `...FromISR`을 따로 두지 않는다. ISR에서도 `k_sem_give()`, `k_msgq_put()`를 그대로 부른다. 대신 규칙이 **인자**에 있다.

- timeout을 받는 API는 ISR에서 **`K_NO_WAIT`만** 허용한다. 기다릴 수 없으니 "지금 되면 하고 안 되면 에러 코드"다.
- 재스케줄은 앱이 요청하지 않는다. 보통 ISR은 공용 `_isr_wrapper`를 거쳐 불리고, wrapper 끝의 `z_arm_int_exit()`(별칭 `z_arm_exc_exit`, `arch/arm/core/cortex_m/exc_exit.c`)가 `_kernel.ready_q.cache != _kernel.cpus->current`이면 PendSV를 건다. FreeRTOS의 woken + yield를 커널이 자동으로 한다(D1 §4.4).
- 문맥 판별은 `k_is_in_isr()` = `arch_is_in_isr()` = `__get_IPSR() != 0`(`arch/arm/include/cortex_m/exception.h` 93행). FreeRTOS `xPortIsInsideInterrupt()`와 같은 방법이다.

어떤 API가 ISR에서 되는지는 Doxygen 주석의 `@isr_ok` 표시로 알 수 있다. v4.4.2 `include/zephyr/kernel.h`에 72개가 있다. 주석 다음에 오는 함수 이름을 뽑으면 이렇다.

| `kernel/mutex.c:115, 234` | `__ASSERT(!arch_is_in_isr(), "mutexes cannot be used inside ISRs")` | lock · unlock 모두 금지 |
| `kernel/sched.c:1222` | `__ASSERT(!arch_is_in_isr(), "")` (`z_impl_k_sleep`) | ISR에서 sleep 금지 |
| `kernel/sched.c:1152` | 같음 (`z_impl_k_yield`) | ISR에서 yield 금지 |
| `kernel/thread.c:791` | `"Threads may not be created in ISRs"` | 스레드 생성 금지 |
| `kernel/kheap.c:88, 185` | `!arch_is_in_isr() ‖ K_NO_WAIT` | 힙 할당은 K_NO_WAIT만 |

(표 안의 `‖`는 C의 논리합 연산자를 표 문법과 겹치지 않게 바꿔 적은 것이다.)

**중요**: `__ASSERT`는 `CONFIG_ASSERT=y`일 때만 코드가 생긴다. v4.4.2 `subsys/debug/Kconfig`에서 `config ASSERT`의 기본값은 `default y if TEST` — 즉 **보통 앱 빌드에서는 꺼져 있다**. FreeRTOS lab 템플릿이 `configASSERT`를 켜 둔 것과 반대다. 개발 중에는 `prj.conf`에 `CONFIG_ASSERT=y`를 직접 넣는다.

### 6.2 예제 9 — `k_is_in_isr()` 세 문맥, `K_NO_WAIT`의 반환값, 그리고 assert 세 개

무엇을 확인하는 코드인지: 같은 함수 `in_isr()`을 ① `irq_offload()`(테스트용으로 함수를 ISR 문맥에서 동기 실행해 주는 API)와 ② 진짜 하드웨어 IRQ(CMSDK TIMER0, IRQ 8)에서 부르고, 메인 스레드에서 `k_is_in_isr()`와 IPSR을 비교한다. ISR 안에서 `K_NO_WAIT`로 빈 세마포어를 take하고 길이 1 메시지 큐에 두 번 put해 반환값을 본다. `-DMODE=1..3`이면 ISR에서 timeout 있는 take, 뮤텍스 lock, sleep을 시도한다. `irq_offload()`는 `CONFIG_IRQ_OFFLOAD`가 필요하고 그것은 `depends on TEST`라서 `CONFIG_TEST=y`를 켰다(그 결과 `CONFIG_ASSERT`도 기본 y가 되지만 명시해 두었다).

```text
# prj.conf
CONFIG_BOOT_BANNER=n
CONFIG_TEST=y
CONFIG_IRQ_OFFLOAD=y
CONFIG_ASSERT=y
```

```c
/* E1 ex9 — Zephyr v4.4.2: k_is_in_isr() in three contexts, ISR-safe calls with K_NO_WAIT,
 *   and (-DMODE=1..3) what CONFIG_ASSERT says when an ISR passes a timeout or locks a mutex */
#include <zephyr/kernel.h>
#include <zephyr/irq.h>
#include <zephyr/irq_offload.h>
#include <zephyr/sys/printk.h>
#include <cmsis_core.h>
#include "zexit.h"
#ifndef MODE
#define MODE 0
#endif
K_SEM_DEFINE(sem, 0, 1);
K_MUTEX_DEFINE(mtx);
K_MSGQ_DEFINE(mq, 4, 1, 4);

static void report(const char *who)
{
	printk("%-14s k_is_in_isr=%d IPSR=%u\n", who, k_is_in_isr(), (unsigned)__get_IPSR());
}
static void in_isr(const void *arg)
{
	report((const char *)arg);
	uint32_t v = 1;
	printk("  k_sem_take(K_NO_WAIT)      = %d\n", k_sem_take(&sem, K_NO_WAIT));
	printk("  k_msgq_put(K_NO_WAIT) x2   = %d, %d\n",
	       k_msgq_put(&mq, &v, K_NO_WAIT), k_msgq_put(&mq, &v, K_NO_WAIT));
#if MODE == 1
	printk("  k_sem_take(K_MSEC(10)) ...\n");
	(void)k_sem_take(&sem, K_MSEC(10));
#elif MODE == 2
	printk("  k_mutex_lock(K_NO_WAIT) ...\n");
	(void)k_mutex_lock(&mtx, K_NO_WAIT);
#elif MODE == 3
	printk("  k_sleep(K_MSEC(1)) ...\n");
	(void)k_sleep(K_MSEC(1));
#endif
}
static void t0_isr(const void *arg)               /* real hardware IRQ: CMSDK TIMER0, IRQ 8 */
{
	*(volatile uint32_t *)0x40000000u = 0;        /* stop */
	*(volatile uint32_t *)0x4000000Cu = 1;        /* INTCLR */
	in_isr(arg);
	k_sem_give(&sem);
}
int main(void)
{
	report("main thread");
	irq_offload(in_isr, "irq_offload");           /* runs in_isr() via SVC */
	k_msgq_purge(&mq);
	IRQ_CONNECT(8, 2, t0_isr, "TIMER0 IRQ", 0);
	irq_enable(8);
	*(volatile uint32_t *)0x40000008u = 2500;     /* RELOAD: 100 us */
	*(volatile uint32_t *)0x40000004u = 2500;
```

### 6.3 예제 10 — `CONFIG_ASSERT=n`에서 ISR이 timeout을 넘기면

무엇을 확인하는 코드인지: 보통 앱 빌드처럼 assert를 끄고, 진짜 TIMER0 IRQ가 prio 7 victim 스레드를 끊은 상태에서 ISR이 `k_sem_take(&sem, K_MSEC(10))`(MODE 1) 또는 `k_sleep(K_MSEC(10))`(MODE 2)을 부른다. victim은 FreeRTOS 예제 7처럼 자기 최장 공백을 기록한다. FreeRTOS와 같은 조건으로 재려고 QEMU를 `-icount shift=5`로 직접 실행했다.

```c
/* E1 ex10 — CONFIG_ASSERT=n: an ISR that passes a timeout. Who actually sleeps? */
#include <zephyr/kernel.h>
#include <zephyr/irq.h>
#include <zephyr/sys/printk.h>
#include "zexit.h"
#define REG(a)  (*(volatile uint32_t *)(a))
#define CYC()   REG(0x40028018u)                       /* FPGAIO 25 MHz counter */
K_SEM_DEFINE(sem, 0, 1);
static volatile uint32_t gap_max, isr_ret = 99, isr_us;
static volatile int stop;
static void t0_isr(const void *arg)
{
	ARG_UNUSED(arg);
	REG(0x40000000u) = 0; REG(0x4000000Cu) = 1;         /* stop TIMER0, INTCLR */
	uint32_t t = CYC();
#if MODE == 1
	isr_ret = (uint32_t)k_sem_take(&sem, K_MSEC(10));   /* count 0: "wait 10 ms" */
#else
	isr_ret = (uint32_t)k_sleep(K_MSEC(10));
#endif
	isr_us = (CYC() - t) / 25u;
}
static void victim_fn(void *a, void *b, void *c)       /* prio 7: the thread we interrupt */
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	uint32_t prev = CYC();
	while (!stop) { uint32_t now = CYC(); if (now - prev > gap_max) gap_max = now - prev; prev = now; }
}
K_THREAD_DEFINE(victim, 1024, victim_fn, NULL, NULL, NULL, 7, 0, 0);
int main(void)                                          /* prio 0 (default main) */
{
	k_msleep(5);
	gap_max = 0;
	IRQ_CONNECT(8, 2, t0_isr, NULL, 0);
	irq_enable(8);
	REG(0x40000008u) = 25000; REG(0x40000004u) = 25000; REG(0x40000000u) = 1 | 8;  /* 1 ms */
	k_msleep(40);
	stop = 1;
	printk("MODE=%d ISR: call returned %d after %u us (ISR did not wait)\n",
	       MODE, (int)isr_ret, (unsigned)isr_us);
	printk("victim thread (was running) longest gap = %u us\n", (unsigned)(gap_max / 25u));
	z_exit();
	return 0;
}
```

- `.config`: 이 빌드는 `CONFIG_USE_SWITCH`가 꺼져 있다 → `z_swap()`이 아래의 `arch_swap()`(PendSV 방식)을 쓴다.
- 이유를 소스로: `z_impl_k_sem_take()`는 count가 0이면 `z_pend_curr(&lock, key, &sem->wait_q, timeout)`을 부른다. `_current`(= ISR이 끊은 victim)를 대기 큐에 넣고 `z_swap()` → `arch_swap()`(`arch/arm/include/cortex_m/kernel_arch_func.h` 87행)으로 간다. Cortex-M의 `arch_swap()`은 `_current->arch.swap_return_value = -EAGAIN;`을 써 두고 PENDSVSET을 세운 뒤 `irq_unlock(0)`을 하고 바로 반환한다. ISR 안이라 PendSV는 ISR이 끝나야 돌므로, ISR은 **-EAGAIN(-11)** 을 받고 계속 진행한다. 반환값은 "timeout"처럼 보이지만 실제로 기다린 것은 victim이다. 게다가 `irq_unlock(0)`은 ISR 한가운데서 BASEPRI를 0으로 내린다.
- 19 ms인 이유: 100 Hz tick에서 `K_MSEC(10)` = 1 tick이고, 상대 timeout은 `kernel/timeout.c` 111행 `to->dticks = timeout.ticks + 1 + ticks_elapsed;`로 "최소 그만큼 지난 뒤"를 보장하려고 1 tick을 더한다. 그래서 1~2 tick(10~20 ms) 사이에서 깬다.
- `k_sleep()`도 마찬가지다(`z_tick_sleep()`이 `unready_thread(_current)` 후 `z_swap()`). 반환값 0은 "다 잤다"는 뜻인데 잔 것은 victim이다.

그림 6 — Zephyr Cortex-M의 두 ISR 경로(v4.4.2). 보통 ISR은 벡터 테이블의 모든 칸이 `_isr_wrapper`를 가리키고, wrapper가 IPSR로 번호를 구해 `_sw_isr_table`에서 (함수, 인자)를 꺼내 부른 뒤 `z_arm_int_exit()`로 재스케줄을 판단한다(B2 예제 15). direct ISR은 벡터 테이블에 함수가 직접 들어가고, 재스케줄 판단은 **반환값이 0이 아닐 때만** 한다.

`arch/arm/core/cortex_m/isr_wrapper.c`의 `_isr_wrapper()`가 매번 하는 일 셋:

1. `CONFIG_PM`이면 저전력 idle에서 깨어난 처리(`pm_system_resume()`).
2. `__get_IPSR() - 16`으로 `_sw_isr_table`을 인덱싱해 `entry->isr(entry->arg)` 호출 — **인자 전달**.
3. 끝에서 `z_arm_exc_exit()` — **재스케줄 판단**.

direct ISR은 이 셋을 앱이 고른다. `include/zephyr/irq.h`와 `include/zephyr/arch/arm/irq.h`(v4.4.2)의 정의:

```c
#define ARCH_ISR_DIRECT_DECLARE(name) \
	static inline int name##_body(void); \
	ARCH_ISR_DIAG_OFF \
	__attribute__ ((interrupt ("IRQ"))) void name(void) \
	{ \
		int check_reschedule; \
		ISR_DIRECT_HEADER(); \
		check_reschedule = name##_body(); \
		ISR_DIRECT_FOOTER(check_reschedule); \
	} \
	ARCH_ISR_DIAG_ON \
	static inline int name##_body(void)

static inline void arch_isr_direct_footer(int maybe_swap)
{
#ifdef CONFIG_TRACING_ISR
	sys_trace_isr_exit();
#endif
	if (maybe_swap != 0) {
		z_arm_int_exit();
	}
}
```

- `ISR_DIRECT_DECLARE(name) { ... return 0 또는 1; }` — 본문을 `name_body()`로 만들고, 바깥 `name()`이 HEADER → body → FOOTER(반환값)를 부른다. 반환값이 0이면 `z_arm_int_exit()`를 **건너뛴다**.
- `ISR_DIRECT_PM()` — `CONFIG_PM`이면 `_arch_isr_direct_pm()`, 아니면 빈 매크로. 저전력 idle 중에 이 IRQ로 깰 수 있다면 넣어야 한다. `irq.h` 주석: "It may be omitted, but be careful!", 그리고 ZLI에서는 쓰면 안 된다.
- `IRQ_DIRECT_CONNECT(irq, prio, isr, flags)` — 인자 없음(`void name(void)`), 스택 전환 없음, 그리고 `IRQ_ZERO_LATENCY` 플래그와 함께 쓰면 커널 밖 IRQ가 된다(E2).

`irq.h`의 `ISR_DIRECT_DECLARE` 주석 예시가 이 계약을 잘 보여 준다: 일이 없으면 `return 0; // don't bother checking if we have to z_swap()`, `k_sem_give()`를 했으면 `return 1;`. 즉 **direct ISR의 반환값이 FreeRTOS의 woken 역할**이다. 그리고 FreeRTOS와 똑같은 실수를 할 수 있다.

### 6.5 예제 11 — direct ISR이 `k_sem_give()` 후 0을 반환하면

무엇을 확인하는 코드인지: TIMER0(1.037 ms 주기)이 세마포어를 give하고, prio 0 메인 스레드가 그것을 `K_FOREVER`로 기다린다. prio 8 busy 스레드는 커널을 전혀 부르지 않고 돈다. ISR 연결을 세 가지로 바꾼다: MODE 0 = `IRQ_CONNECT`, 1 = direct + `return 1`, 2 = direct + `return 0`. ISR은 메인이 기다리기 시작한 뒤 첫 IRQ의 시각을 기록하고, 메인은 깨어난 시각과의 차이를 잰다. 메인은 `K_FOREVER`로 기다리므로 **커널 timeout이 하나도 걸려 있지 않다**는 점이 중요하다.

```c
/* E1 ex11 — Zephyr: IRQ_CONNECT vs IRQ_DIRECT_CONNECT, and a direct ISR that returns 0 */
#include <zephyr/kernel.h>
#include <zephyr/irq.h>
#include <zephyr/sys/printk.h>
#include "zexit.h"
#define REG(a)  (*(volatile uint32_t *)(a))
#define CYC()   REG(0x40028018u)                     /* FPGAIO 25 MHz counter */
#ifndef MODE
#define MODE 0              /* 0: IRQ_CONNECT, 1: direct + return 1, 2: direct + return 0 */
#endif
#define N 10
K_SEM_DEFINE(sem, 0, 1);
static volatile uint32_t t_irq, armed;
static inline void body(void)
{
	REG(0x4000000Cu) = 1;                             /* TIMER0 INTCLR */
	if (armed) { t_irq = CYC(); armed = 0; }
	k_sem_give(&sem);
}
#if MODE == 0
static void t0_isr(const void *arg) { ARG_UNUSED(arg); body(); }
#else
ISR_DIRECT_DECLARE(t0_direct)
{
	body();
	ISR_DIRECT_PM();                                  /* no-op unless CONFIG_PM */
	return MODE == 1 ? 1 : 0;                         /* 0 = "skip the reschedule check" */
}
#endif
static void busy_fn(void *a, void *b, void *c)        /* prio 8: never calls the kernel */
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	for (;;) { }
}
K_THREAD_DEFINE(busy, 512, busy_fn, NULL, NULL, NULL, 8, 0, 0);
int main(void)                                        /* prio 0: the woken thread */
{
	uint32_t mn = ~0u, mx = 0; uint64_t sum = 0;
#if MODE == 0
	IRQ_CONNECT(8, 2, t0_isr, NULL, 0);
#else
	IRQ_DIRECT_CONNECT(8, 2, t0_direct, 0);
#endif
	irq_enable(8);
	REG(0x40000008u) = 25925; REG(0x40000004u) = 25925; REG(0x40000000u) = 1 | 8;  /* 1.037 ms */
	for (int i = 0; i < N; i++) {
		k_sem_reset(&sem);
		armed = 1;
		(void)k_sem_take(&sem, K_FOREVER);              /* no kernel timeout is pending */
		uint32_t lat = (CYC() - t_irq) * 40u;           /* ns */
		if (lat < mn) mn = lat;
		if (lat > mx) mx = lat;
		sum += lat;
	}
	printk("MODE=%d n=%d wake latency min=%u avg=%u max=%u ns\n", MODE, N, mn,
	       (uint32_t)(sum / N), mx);
	z_exit();
	return 0;
}
```

### 6.6 `irq_offload()` — 테스트에서 ISR 문맥 만들기

예제 9에서 봤듯이 `irq_offload(routine, param)`은 routine을 SVC 예외 안에서 **동기적으로** 실행하고 돌아온다(`kernel/irq_offload.c`가 `offload_sem`으로 직렬화, `CONFIG_IRQ_OFFLOAD_NESTED`면 생략). 용도:

- 드라이버 함수가 ISR에서 불려도 안전한지(`k_is_in_isr()` 분기, `K_NO_WAIT` 처리)를 하드웨어 없이 Ztest로 검증한다(M8).
- `CONFIG_ASSERT=y`와 함께 쓰면 "ISR에서 금지된 호출"이 테스트에서 바로 터진다.

한계: SVC 우선순위에서 돌기 때문에 진짜 IRQ의 NVIC 우선순위, 중첩, BASEPRI 상호작용은 재현하지 않는다. `CONFIG_IRQ_OFFLOAD`는 `depends on TEST`라 양산 이미지에는 들어가지 않는다. FreeRTOS에는 같은 이름의 API가 없다 — 이 노트처럼 `STIR`로 남는 IRQ를 소프트웨어 트리거하는 것이 가장 가까운 방법이다(예제 2, 8).

## 7. FreeRTOS vs Zephyr — ISR 체크리스트 한 장

| 항목 | FreeRTOS V11.3.2 | Zephyr v4.4.2 |
|---|---|---|
| ISR용 API | 이름이 다른 함수 `...FromISR` | 같은 함수, timeout은 `K_NO_WAIT`만 (`@isr_ok` 표시) |
| ISR에서 안 되는 호출 | FromISR이 아닌 전부, 특히 블로킹 · `vTaskDelay` · 뮤텍스 · `pvPortMalloc` | `k_mutex_*`, `k_sleep`, `k_yield`, `k_thread_create`, timeout ≠ `K_NO_WAIT` |
| 깨운 뒤 재스케줄 | 앱: `woken = pdFALSE` → `&woken` 공유 → `portYIELD_FROM_ISR(woken)` | 자동: `_isr_wrapper` → `z_arm_int_exit()`. direct ISR은 반환값 1 |
| 빼먹었을 때 | 다음 tick까지 (예제 4, 5: 최대 1 tick) | direct ISR `return 0`: 다음 보통 인터럽트까지 (예제 11: 19 ms ~ 660 ms) |
| 문맥 판별 | `xPortIsInsideInterrupt()` (IPSR ≠ 0) | `k_is_in_isr()` (IPSR ≠ 0) |
| ISR 안 짧은 보호 구간 | `taskENTER_CRITICAL_FROM_ISR()` / `taskEXIT_CRITICAL_FROM_ISR(x)` (BASEPRI 저장/복원) | `irq_lock()` / `irq_unlock(key)` 또는 `k_spin_lock()` (C7 §8) |
| 우선순위 규칙 | NVIC 값 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY` (숫자로) | `IRQ_CONNECT` 우선순위는 자동으로 커널 영역 아래. 커널 밖은 `IRQ_ZERO_LATENCY` 명시 |
| 우선순위 실수 검출 | 런타임 `vPortValidateInterruptPriority()` → `port.c:803` | 빌드 시점 `BUILD_ASSERT` (ZLI 플래그 · 범위). ZLI 안의 API 호출은 검출 없음 |
| 잘못된 API 검출 | `configASSERT` — VECTACTIVE 검사 `port.c:438` | `CONFIG_ASSERT` — `arch_is_in_isr()` 검사 (sem.c:136, mutex.c:115, sched.c:1222 …) |
| assert 기본값 | 사용자가 `FreeRTOSConfig.h`에 정의 (lab 템플릿은 켬) | `default y if TEST` — 보통 앱은 꺼짐 |
| assert 끄고 블로킹 호출 | 끊긴 태스크가 잠듦 / ISR 무한 루프 (예제 7) | 끊긴 스레드가 잠듦, -EAGAIN (예제 10) |
| ISR 문맥 테스트 도구 | 없음 (STIR로 IRQ 트리거) | `irq_offload()` (`CONFIG_TEST`) |
| 최소 지연 경로 | 커널 밖 ISR (문턱 위) — 커널 API 금지 | `IRQ_DIRECT_CONNECT` + `ISR_DIRECT_DECLARE`, ZLI |

## 10. 실무에서 다시 보기

### 10.1 드론 비행 제어기 — IMU data-ready ISR

STM32H7급 FC에서 IMU(SPI, 8 kHz data-ready)는 보통 이렇게 쓴다.

```c
void EXTI4_IRQHandler(void)                    /* IMU DRDY, NVIC prio = 문턱 바로 아래 */
{
    EXTI->PR1 = EXTI_PR1_PIF4;                  /* 1. 원인 지우기 */
    imu_ts[imu_wr & 7] = TIM2->CNT;             /* 2. 타임스탬프만 찍는다 (E5) */
    imu_wr++;
    BaseType_t woken = pdFALSE;
    vTaskNotifyGiveFromISR(imu_task, &woken);   /* 3. 가장 가벼운 깨우기 (D5) */
    portYIELD_FROM_ISR(woken);                  /* 4. 자세 추정 태스크로 바로 */
}
```

(실칩 레지스터 이름을 쓴 모양 예시라 이 랩에서는 실행하지 않았다.)

SPI 읽기 자체는 ISR에서 하지 않는다. DMA를 시작하는 일은 ISR에서 해도 되지만(레지스터 몇 개), 완료 대기는 태스크가 한다(E6). 자이로 보정 계산(float)도 태스크로 — H7은 FPU가 있어 연산은 빠르지만, ISR 프레임이 26워드로 커지고 그 ISR의 최악 길이가 같은 우선순위 그룹 전체에 더해진다(예제 8, B6). ESC용 DShot 타이머 ISR처럼 µs 단위 마감이 있는 것은 문턱 위(zero-latency)에 두고 커널을 부르지 않는다(E2).

### 10.2 로봇 관절 모터 컨트롤러 — 20 kHz FOC + CAN

FOC 전류 루프 ISR(ADC 변환 완료, 20 kHz = 50 µs 주기)은 커널 API를 부르지 않는 문턱 위 ISR로 두는 경우가 많다. 그 ISR이 태스크에 알릴 일(과전류 fault, 1 kHz 속도 루프용 데이터 준비)이 생기면 **직접 FromISR을 부르지 않고** 문턱 아래의 "다리" IRQ를 `NVIC_SetPendingIRQ`(STIR)로 pend한다(B3 예제 11 MODE 0). CAN RX ISR은 문턱 아래에서 `xQueueSendFromISR`로 프레임을 넘기고, 큐가 차서 `errQUEUE_FULL`이 오면 버린 프레임 카운터를 올린다 — ISR은 기다릴 수 없으니 실패 처리 경로가 반드시 있어야 한다(예제 9의 `-ENOMSG`와 같은 얘기).

### 10.3 Linux SoC 옆 센서 허브 (Zephyr)

Zephyr 드라이버 API의 콜백(예: UART `uart_irq_callback_set`, GPIO `gpio_init_callback`)은 **ISR 문맥에서 불린다**. 콜백 안에서 `k_msleep()`이나 `k_mutex_lock()`을 쓰면 예제 9처럼 assert(켜져 있으면) 또는 예제 10처럼 엉뚱한 스레드 정지(꺼져 있으면)가 된다. 드라이버 공용 함수를 쓸 때 `k_is_in_isr()`로 분기하거나, 콜백에서는 `k_work_submit()`/`k_msgq_put(..., K_NO_WAIT)`만 한다(D7 §4). 개발 보드 빌드의 `prj.conf`에 `CONFIG_ASSERT=y`를 넣는 것을 팀 규칙으로 둔다 — 기본값이 꺼짐이라는 것을 모르는 사람이 많다.

### 10.4 Don의 SSD 펌웨어와 연결

| SSD 펌웨어 (bare-metal executive) | RTOS ISR 규칙 |

## 12. 면접에서 이렇게 말한다

**Q.** Why does FreeRTOS have separate `FromISR` versions of its API? (FreeRTOS는 왜 FromISR API를 따로 두나?)

**A.** 세 가지가 다르기 때문이다. ISR은 블록할 수 없으니 timeout 인자와 대기 경로가 없다. 크리티컬 섹션이 중첩 카운터식이 아니라 BASEPRI 저장/복원식이다. 그리고 높은 태스크를 깨워도 그 자리에서 스위치하지 않고 플래그만 돌려준다. 그 덕에 ISR 경로가 짧다 — 큐 send 기준 코드가 404 B에서 232 B로, give가 2.5 µs에서 1.5 µs로 줄었다(QEMU).

> FreeRTOS keeps separate ISR APIs because three things differ in interrupt context. An ISR cannot block, so the FromISR variants have no timeout and no wait path. The critical section must save and restore BASEPRI instead of using the task-level nesting counter, which would drop BASEPRI to zero. And the ISR cannot context-switch on the spot, so the API only reports through pxHigherPriorityTaskWoken that a higher-priority task was woken, and the ISR requests the switch with portYIELD_FROM_ISR at the end. The result is a shorter, simpler path: on my QEMU Cortex-M3 measurements xQueueGenericSendFromISR is about half the code size of xQueueGenericSend.

**꼬리 질문**: "Zephyr는?" → 같은 함수에 `K_NO_WAIT`만 허용하고, 재스케줄은 ISR wrapper 출구가 자동으로 한다.

**Q.** What is `xHigherPriorityTaskWoken` for, and what happens if you pass NULL or forget `portYIELD_FROM_ISR`? (그 플래그는 무엇이고 빼먹으면?)

**A.** FromISR API가 "지금 돌던 태스크보다 높은 태스크를 깨웠다"는 사실을 알려 주는 플래그다. ISR 끝에서 그것을 `portYIELD_FROM_ISR`에 넘기면 PendSV가 걸려서 ISR이 끝나자마자 그 태스크로 간다. 빼먹어도 커널이 `xYieldPendings`로 기억해 두었다가 다음 tick에서 전환하므로 기능은 맞지만, 지연이 최대 1 tick이 된다. 실제로 재 보니 1 kHz에서 평균 0.5 ms, 100 Hz에서 평균 5 ms, 최대 10 ms였고 yield가 있으면 tick과 무관하게 9 µs였다.

> It tells the ISR whether the API call unblocked a task with higher priority than the one that was interrupted. You initialise it to pdFALSE, pass the same variable to every FromISR call in the handler, and call portYIELD_FROM_ISR with it at the end, which just pends PendSV so the switch happens right after the ISR returns. If you pass NULL or skip the yield, the kernel still records a pending yield and switches on the next tick, so it works functionally but the wake-up latency becomes uniformly distributed up to one tick period. I measured nine microseconds with the yield, versus an average of half a tick and a worst case of a full tick without it, at 1000, 250 and 100 Hz.

**꼬리 질문**: "한 ISR에서 FromISR을 두 번 부르면?" → 같은 변수를 넘긴다. 따로 받아서 마지막 것만 넘기면 앞의 `pdTRUE`가 사라진다.

**Q.** List the things you must not do in an ISR under an RTOS, and why. (ISR에서 하면 안 되는 것은?)

**A.** 기다리는 모든 것 — 블로킹 take, delay, sleep, 뮤텍스. ISR에는 블록할 주체가 없어서 커널이 끊긴 태스크를 재운다. 태스크용 API(크리티컬 섹션 방식이 다름), 문턱보다 급한 ISR에서의 커널 API(커널이 막을 수 없음), printf와 malloc(블로킹 · 재진입), 상한 없는 루프, FPU 없는 코어에서의 float. 공통 원리는 "ISR의 길이는 같거나 낮은 우선순위의 모든 것의 지연"이라는 것이다.

> Anything that can wait: blocking receives with a timeout, delays, sleeps and mutexes. An ISR has no task identity, so the kernel would put the interrupted task to sleep instead. I demonstrated that with asserts disabled: vTaskDelay in an ISR stalled an unrelated task for five milliseconds, and a blocking take spun forever inside vListInsert. Also non-ISR API variants, any kernel call from an interrupt above the max syscall priority, printf and malloc because they block or are not reentrant, unbounded loops, and floating point on cores without an FPU. The underlying rule is that every microsecond in an ISR is added to the latency of everything at the same or lower priority.

**Q.** Why can't you use a mutex from an ISR? (ISR에서 뮤텍스를 못 쓰는 이유는?)

**A.** 뮤텍스는 소유자가 태스크라는 전제 위에 있다. 소유자만 풀 수 있고, 우선순위 상속은 소유자 태스크의 우선순위를 올린다. ISR은 TCB가 없고 우선순위 축도 다르며 기다릴 수도 없다. FreeRTOS에서는 ISR이 빈 뮤텍스를 take하면 assert 없이 성공해서 "소유자 없는 잠긴 뮤텍스"가 되고 태스크가 영원히 못 얻는 것을 실험으로 봤다. Zephyr는 `k_mutex_lock`에서 assert로 막는다.

> A mutex assumes its owner is a task: only the owner may release it, and priority inheritance boosts the owner's priority. An ISR has no task control block, its priority lives in the NVIC rather than the scheduler, and it cannot wait if the mutex is held. In FreeRTOS, taking a free mutex from an ISR actually succeeds with no assert and leaves a locked mutex with a NULL holder, so tasks then time out forever. Zephyr asserts in k_mutex_lock. For data shared between an ISR and a task I use a short ISR-safe critical section, a lock-free single-producer single-consumer buffer, or a gatekeeper task.

**Q.** How does FreeRTOS catch an ISR that calls the API from the wrong priority? (잘못된 우선순위를 어떻게 잡나?)

**A.** `configASSERT`가 정의되어 있으면 FromISR 입구에서 `vPortValidateInterruptPriority`가 IPSR로 현재 IRQ 번호를 읽고, NVIC의 그 IRQ 우선순위 바이트가 `configMAX_SYSCALL_INTERRUPT_PRIORITY`보다 급하면 assert한다. 리셋값 0인 IRQ는 무조건 걸린다. thread mode와 시스템 예외는 검사하지 않는다. assert를 끄면 이 함수 자체가 빠진다.

> When configASSERT is defined, every core FromISR function calls vPortValidateInterruptPriority on entry. It reads IPSR to get the active exception number, looks up that interrupt's priority byte in the NVIC, and asserts if it is logically higher than configMAX_SYSCALL_INTERRUPT_PRIORITY, because the kernel's BASEPRI critical sections cannot mask it. An interrupt left at its reset priority of zero always fails that check. It also asserts if priority grouping leaves sub-priority bits. With configASSERT undefined the check is compiled out, which is why I keep asserts on in development builds and log-and-reset in production.

**Q.** In Zephyr, what's the difference between `IRQ_CONNECT` and `IRQ_DIRECT_CONNECT`? (Zephyr의 두 연결 방식 차이는?)

**A.** 보통 ISR은 공용 wrapper가 PM 복귀, 인자 전달, 출구의 재스케줄 판단을 해 준다. direct ISR은 벡터에 바로 들어가서 셋 다 선택이 된다. `ISR_DIRECT_PM()`을 넣을지, 반환값을 1로 해서 재스케줄을 검사할지 앱이 정한다. 스레드를 깨우고 0을 반환하면 FreeRTOS에서 yield를 빼먹은 것과 같고, tickless에서는 더 나빠서 실측 19 ms(시간 슬라이스), 슬라이스를 끄면 최대 660 ms까지 늦어졌다.

> IRQ_CONNECT goes through the common _isr_wrapper, which handles power-management exit, passes the argument from the software ISR table, and on exit checks whether a higher-priority thread became ready and pends PendSV. IRQ_DIRECT_CONNECT puts the handler straight into the vector table and makes those steps optional: you call ISR_DIRECT_PM yourself and the return value of the ISR_DIRECT_DECLARE body decides whether the reschedule check runs. If you give a semaphore and return zero, the woken thread waits for the next ordinary interrupt. On a tickless 100 Hz build I measured about 19 milliseconds, set by the time-slice timer, and up to 660 milliseconds with time slicing disabled.

**꼬리 질문**: "그럼 direct ISR은 왜 쓰나?" → wrapper 몇십 사이클과 간접 호출을 줄이고, ZLI는 direct여야만 한다(`ARCH_IRQ_CONNECT`가 `BUILD_ASSERT`로 거부).

**Q.** How do you write a function that may be called from both a task and an ISR? (양쪽에서 불리는 함수는?)

**A.** FreeRTOS는 `xPortIsInsideInterrupt()`, Zephyr는 `k_is_in_isr()`로 IPSR을 보고 분기한다. FreeRTOS에서는 ISR 쪽에서 FromISR + woken + yield, 태스크 쪽에서 보통 API. Zephyr에서는 timeout을 `k_is_in_isr() ? K_NO_WAIT : K_MSEC(n)`으로 고른다. 다만 둘 다 PendSV · SVC 안에서도 참이고, zero-latency ISR인지는 알려 주지 않는다.

> Check the execution context at run time: xPortIsInsideInterrupt in FreeRTOS or k_is_in_isr in Zephyr, both of which just test IPSR. In FreeRTOS the ISR branch uses the FromISR call with a woken flag and portYIELD_FROM_ISR, and the task branch uses the normal call. In Zephyr the same call works in both, but the timeout must be K_NO_WAIT in the ISR branch. Note that these helpers return true for any exception, including SVC and PendSV, and they cannot tell you whether you are in a zero-latency interrupt where no kernel call is allowed, so priority discipline is still needed.

## 15. 요약 & 체크리스트

RTOS에서 ISR은 "플래그만 세우는 짧은 함수"에 더해 **커널과의 계약**을 지켜야 한다. FreeRTOS는 그 계약을 이름(`FromISR`)과 woken 플래그로, Zephyr는 인자(`K_NO_WAIT`)와 ISR 출구의 자동 재스케줄로 표현한다. 계약의 핵심은 셋이다: ISR은 기다리지 않는다, ISR은 자기 방식(저장/복원)으로만 마스크한다, ISR은 스위치를 요청만 하고 실행은 PendSV에 맡긴다. 이 노트의 측정에서 yield 한 줄을 빼먹으면 지연이 tick 주기만큼(1 kHz에서 최대 1 ms, 100 Hz에서 10 ms), Zephyr direct ISR이 0을 반환하면 최대 SysTick 한 바퀴(660 ms)까지 늘었다. 블로킹 호출은 assert가 있으면 첫 실행에서 `port.c:438` / `sem.c:136`으로 잡히지만, 없으면 **끊긴 태스크가 잠들거나** ISR이 `vListInsert`에서 영원히 돈다. 그래서 개발 빌드는 assert를 켜고, 양산은 "기록하고 리셋"으로 남긴다.

- [ ] FromISR이 태스크용 API와 다른 네 가지(기다림, 크리티컬 섹션, 스위치, 진입 검사)를 말할 수 있다
- [ ] `woken = pdFALSE` → 같은 `&woken` 공유 → 끝에서 `portYIELD_FROM_ISR(woken)`을 습관으로 쓴다
- [ ] yield 누락 · NULL의 대가가 "최대 1 tick, 평균 tick/2"인 이유를 `xYieldPendings`로 설명할 수 있다
- [ ] 한 ISR 안의 여러 FromISR에서 플래그를 덮어쓰거나 반환값을 넘기는 버그를 알아본다
- [ ] ISR에서 블로킹 호출을 하면 "끊긴 태스크가 잠든다"는 것을 예로 설명할 수 있다
- [ ] `list.c:192`에서 멈춘 시스템을 보면 ISR 규칙 위반 · 우선순위 · 스택 오버플로를 먼저 의심한다
- [ ] ISR에서 뮤텍스가 안 되는 이유(소유자 · 상속 · 대기)와 대안 세 가지를 말할 수 있다
- [ ] printf · malloc · 긴 루프 · float의 ISR 비용을 숫자로 말할 수 있다 (예제 8)
- [ ] `vPortValidateInterruptPriority`가 무엇을 읽고 무엇을 검사하지 않는지 안다
- [ ] Zephyr에서 `K_NO_WAIT` 규칙과 `@isr_ok` 표시, `CONFIG_ASSERT` 기본값(꺼짐)을 안다
- [ ] `ISR_DIRECT_DECLARE`의 반환값과 `ISR_DIRECT_PM`의 역할을 설명하고, 0을 반환하면 생기는 지연을 말할 수 있다
- [ ] `irq_offload()`로 ISR 문맥 테스트를 만들 수 있고 그 한계(SVC 우선순위)를 안다
