# C5. tick과 시간 관리 — 커널의 시계, 지연, 타임아웃, 그리고 카운터 wrap

> **이 노트를 다 읽으면**: tick 하나가 커널 안에서 무엇을 하는지 `xTaskIncrementTick()`을 한 줄씩 따라가며 설명하고 그 비용을 µs 단위로 잴 수 있다 · tick rate를 해상도·세금·`pdMS_TO_TICKS` 반올림 관점에서 골라 근거를 댈 수 있다 · `vTaskDelay` / `xTaskDelayUntil` / `xTaskPeriodicDelay`의 차이를 500주기 측정과 타임라인으로 보여 주고 상황에 맞게 고를 수 있다 · tick 카운터 wrap(32비트·16비트), 멈춘 스케줄러의 pended tick, 다단계 타임아웃(`xTaskCheckForTimeOut`), Zephyr의 delta list와 "+1 tick" 규칙을 소스 줄 번호로 설명할 수 있다
> **왜 필요한가**: "vTaskDelay와 vTaskDelayUntil의 차이는?", "tick rate는 어떻게 정하나?", "tick 카운터가 넘치면?"은 펌웨어 면접의 단골이다. 실무에서는 제어 루프 주기가 조용히 20% 늘어나는 버그, 49.7일 뒤에 터지는 wrap 버그, "20 ms 타임아웃"이 48 ms 걸리는 드라이버 버그로 나타난다.
> **Don 기준 난이도**: 타이머 인터럽트로 ms 카운터를 올리고 타임아웃을 세는 일, unsigned 뺄셈으로 wrap을 피하는 법은 SSD 펌웨어에서 이미 했다 / FreeRTOS가 delayed list 두 개로 wrap을 처리하는 방식, `xNextTaskUnblockTime` 최적화, pended tick, 세 지연 API의 정확한 의미, Zephyr의 64비트 tick·delta list·+1 tick 규칙은 새로 배운다
> **선행 노트**: A1(§9 delay vs until 맛보기), A5(§3 Zephyr +1 tick, k_timeout_t), A7(§6 tick 세금 1.47 µs), EL F8(jiffies·HZ·hrtimer). 함께 읽을 노트: B4(SysTick 하드웨어), C1(리스트 자료구조), C2(PendSV), C6(tickless), D6(소프트웨어 타이머), E5·E7(HW 타이머·주기 정확도)

## 0. 큰 그림 — 이게 왜 필요한가

Don이 SSD 펌웨어에서 매일 쓰던 패턴을 떠올려 보자. 하드웨어 타이머가 1 ms마다 인터럽트를 걸고, ISR은 전역 카운터 `g_ms`를 하나 올린다. 메인 루프의 여러 작업은 "`g_ms - start >= timeout`이면 타임아웃" 식으로 그 카운터를 읽어 시간을 판단한다. NVMe 명령 타임아웃, 백그라운드 GC를 몇 ms마다 돌릴지, 전원 손실 감지 후 몇 ms 안에 flush할지 — 전부 이 카운터 위에서 돌았다.

RTOS의 **tick**이 정확히 이것이다. 다만 RTOS는 카운터를 올리는 김에 두 가지 일을 더 한다.

1. **"지금 깨워야 할 태스크가 있나?"를 본다.** 태스크가 `vTaskDelay(10)`이나 `xQueueReceive(q, &v, 20)`으로 잠들면 커널은 그 태스크를 "깨울 tick 값" 순으로 정렬된 리스트(delayed list)에 넣어 둔다. tick이 그 값에 닿으면 태스크를 ready로 옮긴다. bare-metal에서는 메인 루프가 매번 카운터를 **폴링**했지만, RTOS에서는 태스크가 "이 시각에 깨워 줘"라고 **맡기고** CPU를 내놓는다.
2. **같은 우선순위끼리 CPU를 나눠 쓰게 한다(time slicing).** 같은 우선순위의 ready 태스크가 둘 이상이면 tick마다 차례를 넘긴다(C4).

그래서 tick은 RTOS의 **시계이자 알람 시계**다. 이 노트는 그 시계가 어떻게 돌고(§1~3), 시계가 한 바퀴 돌면 무슨 일이 생기고(§4), 그 시계 위에서 지연·주기·타임아웃을 어떻게 정확하게 만드는지(§5~7), Zephyr는 같은 일을 어떻게 다르게 하는지(§8)를 소스와 측정으로 따라간다.

## 1. tick은 커널의 시계다 — `xTickCount`와 tick rate

> 🔁 이 절은 Bare-Metal BM C7(SysTick · DWT)과 겹친다 (주인: 이 노트). SysTick 레지스터(LOAD·VAL·CTRL·CALIB)와 클럭 소스 선택은 RTOS B4가 주인이다.

### 1.1 직관 — 벽시계의 초침

tick은 커널 벽시계의 초침이다. 초침이 1초마다 움직이는 시계로는 "0.3초 뒤"를 표현할 수 없다. 1 kHz tick이면 커널이 아는 가장 작은 시간 단위는 1 ms이고, "1.5 ms 기다려"는 커널 입장에서 의미가 없다. 그리고 초침은 **이산적으로** 움직인다. 태스크가 "1칸 뒤에 깨워 줘"라고 말한 순간이 이번 칸의 끝 무렵이었다면, 1칸 뒤는 거의 바로다(§5.3에서 0~1 tick 분포로 확인).

### 1.2 정의 — FreeRTOS의 시간 변수와 매크로

| 이름 | 위치 | 뜻 |
|---|---|---|
| `xTickCount` | `tasks.c` (static volatile) | 스케줄러 시작 후 지나간 tick 수. 초기값 `configINITIAL_TICK_COUNT`(기본 0) |
| `TickType_t` | `portmacro.h` | tick 값의 타입. `configTICK_TYPE_WIDTH_IN_BITS`로 16/32/64비트 (Cortex-M3 포트는 16 또는 32) |
| `configTICK_RATE_HZ` | `FreeRTOSConfig.h` | 1초당 tick 수. 랩 기본 1000 |
| `portTICK_PERIOD_MS` | `portmacro.h:79` | `( TickType_t ) 1000 / configTICK_RATE_HZ` — **정수 나눗셈**. 1 kHz 초과면 0이 된다 |
| `pdMS_TO_TICKS(ms)` | `projdefs.h:42` | `( ms × configTICK_RATE_HZ ) / 1000`을 `uint64_t`로 계산한 뒤 `TickType_t`로 캐스트 — **내림**, 그리고 **잘림** |
| `portMAX_DELAY` | `portmacro.h:64/67` | `TickType_t`의 최댓값(16비트면 0xffff, 32비트면 0xffffffff). 블로킹 API에서 "무한 대기" |
| `xTaskGetTickCount()` / `xTaskGetTickCountFromISR()` | `tasks.c:4213/4232` | `xTickCount` 읽기. 태스크용 / ISR용 |
| `xNextTaskUnblockTime` | `tasks.c` (static) | delayed list 머리의 깨울 값 캐시. §3 최적화의 핵심 |

`xTickCount`는 **태스크·ISR 모두가 읽는 공유 변수**다. 32비트 포트에서는 `portTICK_TYPE_IS_ATOMIC`이 1이라(ARM_CM3 `portmacro.h:71`) 읽기에 크리티컬 섹션이 필요 없다. 8/16비트 MCU에서 32비트 tick을 쓰면 읽기가 찢어질(tearing) 수 있어서 커널이 크리티컬 섹션으로 감싼다(`FreeRTOS.h:2925` 근처의 매핑).

### 1.3 tick rate 고르기 — 해상도와 세금의 거래

| tick rate | 1 tick | 장점 | 단점 | 어울리는 곳 |
|---|---|---|---|---|
| 100 Hz | 10 ms | 세금 거의 0 (예제 4: 0.01%) | `vTaskDelay`·타임아웃 해상도 10 ms, `pdMS_TO_TICKS(5)` = 0 | 배터리 센서 노드, UI, 느린 프로토콜 |
| 1000 Hz | 1 ms | ms와 1:1 — 계산 실수가 적다, 세금 0.14% @25 MHz | 1 ms보다 빠른 주기는 못 만든다 | **대부분의 FreeRTOS 제품의 기본값** (드론 FC의 텔레메트리·상태 머신) |
| 10000 Hz | 0.1 ms | 타임아웃 해상도 100 µs | 세금 1.47% @25 MHz, `portTICK_PERIOD_MS` = 0, 16비트 tick이면 6.5초마다 wrap | 타임아웃 해상도가 꼭 필요한 곳 — 보통은 대신 HW 타이머(E5) |

결정 규칙은 단순하다.

- **tick은 "잠들고 깨는" 해상도**만 결정한다. 1 kHz rate loop(드론 자세 제어)를 tick으로 돌리면 깨어나는 시각이 tick 경계에 묶이고, 깨어난 뒤 실제로 CPU를 받는 시각은 다른 태스크·ISR에 따라 흔들린다. **정밀한 주기는 HW 타이머 ISR(또는 IMU의 data-ready 인터럽트) + 태스크 통지**로 만든다(E5, E7). tick은 그보다 느슨한 일(10 ms 이상 주기, 타임아웃)에 쓴다.
- 1 kHz가 기본값인 이유: ms와 tick이 1:1이라 `pdMS_TO_TICKS` 반올림 오차가 없고(§1.4), 세금이 작다.
- tick rate를 올리기 전에 **"그 해상도가 필요한 것이 무엇인가"**를 묻는다. 대개 그것 하나만 HW 타이머로 빼는 편이 싸다.
- Zephyr는 기본이 tickless라 `CONFIG_SYS_CLOCK_TICKS_PER_SEC`가 "인터럽트 주기"가 아니라 "시간 해상도"다(§8.7, C6). 그래서 실보드 기본값이 10 kHz다.

### 1.4 예제 1 — `pdMS_TO_TICKS` 내림과 SysTick 정수 나눗셈 오차

무엇을 확인하나: tick rate를 100 / 1000 / 1500 Hz로 바꿔 빌드하고, `pdMS_TO_TICKS(ms)`가 몇 tick이 되는지와 실제로 잠든 시간을 잰다. 1500 Hz에서는 25 MHz를 1500으로 나누면 나머지가 생기는데, 포트가 그 나머지를 어떻게 처리하는지도 10초 동안 누적해서 본다.

```c
/* C5 ex1: pdMS_TO_TICKS 내림과 SysTick 정수 나눗셈 — tick rate를 바꾸면 무엇이 깨지나 */
#include "FreeRTOS.h"
#include "task.h"
#include "c5.h"
static void task(void *p)
{
    (void)p;
    board_printf_raw("configTICK_RATE_HZ=%u  SysTick LOAD+1=%u cycles (ideal %u.%u)\n",
        (unsigned)configTICK_RATE_HZ, (unsigned)(REG32(0xE000E014u) + 1u),
        (unsigned)(BOARD_CPU_HZ / configTICK_RATE_HZ),
        (unsigned)((BOARD_CPU_HZ % configTICK_RATE_HZ) * 10u / configTICK_RATE_HZ));
    static const uint32_t ms[] = { 1, 3, 5, 10, 25 };
    for (unsigned i = 0; i < 5; i++) {
        TickType_t t = pdMS_TO_TICKS(ms[i]);
        vTaskDelay(1);                                   /* tick 경계 직후에서 시작 */
        uint32_t a = board_now_us();
        vTaskDelay(t);
        uint32_t d = board_now_us() - a;
        board_printf_raw("  vTaskDelay(pdMS_TO_TICKS(%u)) = %u ticks -> slept %u us\n",
                         ms[i], (unsigned)t, d);
    }
    /* 긴 구간에서 tick 하나의 실제 길이: 10 s 분량의 tick을 us 시계로 잰다 */
    TickType_t n = (TickType_t)configTICK_RATE_HZ * 10u;
    vTaskDelay(1);
    uint32_t a = board_now_us();
    vTaskDelay(n);
    uint32_t d = board_now_us() - a;
    board_printf_raw("  %u ticks took %u us (ideal 10000000, error %d us = %d ppm)\n",
                     (unsigned)n, d, (int)(d - 10000000u), ((int)(d - 10000000u)) / 10);
    board_exit(0);
}
int main(void)
{
    xTaskCreate(task, "t", 512, NULL, 2, NULL);
    vTaskStartScheduler();
    return 1;
}
```

- 결론: **tick rate는 코어 클럭을 나누어떨어뜨리는 값, 그리고 1000의 약수·배수(100, 1000, 10000)로 고른다.**

### 1.5 예제 2 — rate별 반올림 표 (Python)

무엇을 확인하나: 같은 ms 요청이 tick rate에 따라 몇 tick이 되고, 그 tick 수가 실제로 몇 ms인지 표로 본다. FreeRTOS(`pdMS_TO_TICKS`, 내림)와 Zephyr(`K_MSEC`, 올림)를 나란히 계산한다.

```python
# C5 ex13: pdMS_TO_TICKS(ms) = ms * HZ / 1000 (정수 내림) — tick rate별로 요청과 실제 tick 길이의 차이
rates = [100, 250, 300, 1000, 1024, 1500, 10000]
reqs = [1, 3, 5, 10, 33]
print("HZ     " + "".join(f"{m:>4} ms           " for m in reqs))
for hz in rates:
    row = []
    for m in reqs:
        t = m * hz // 1000                      # FreeRTOS projdefs.h: 내림
        real = t * 1000 / hz                    # 그 tick 수가 뜻하는 ms
        row.append(f"{t:>5}t={real:6.2f}ms ")
    print(f"{hz:<6} " + "".join(row))
print()
for hz in rates:                                # Zephyr K_MSEC = 올림 (k_ms_to_ticks_ceil)
    t = [-(-m * hz // 1000) for m in reqs]
    print(f"Zephyr ceil @{hz:<5}: " + " ".join(f"{m}ms->{x}t" for m, x in zip(reqs, t)))
```

### 1.6 함정 정리

- `pdMS_TO_TICKS()` 결과가 0이 될 수 있는 모든 곳(짧은 지연, 짧은 타임아웃)에 `configASSERT(t > 0)`을 두거나, 직접 올림 매크로를 만든다: `#define MS_TO_TICKS_CEIL(ms) ((TickType_t)(((uint64_t)(ms) * configTICK_RATE_HZ + 999u) / 1000u))`.
- `portTICK_PERIOD_MS`로 나누는 옛 코드(`ms / portTICK_PERIOD_MS`)는 1 kHz 초과에서 **0으로 나누기**가 된다(1000 / 10000 = 0). `pdMS_TO_TICKS`를 쓴다.
- `pdMS_TO_TICKS`는 64비트로 곱하지만 마지막에 `TickType_t`로 **캐스트**한다. 16비트 tick에서 큰 값은 조용히 잘린다(§4.5 예제 8).
- tick rate를 바꾸면 **모든 ms 숫자의 의미가 바뀐다**. 코드에 tick 숫자를 직접 쓰지 말고(`vTaskDelay(10)`), 항상 `pdMS_TO_TICKS()`를 거친다. 그래야 rate를 바꿀 때 컴파일러가 다시 계산한다.

## 2. tick 한 번의 비용 — 무엇에 비례하나

A7 §6은 "tick 하나 = 1.47 µs, CPU 손실은 rate에 정비례"를 바쁜 카운터로 쟀다. 여기서는 한 단계 더 들어간다. **tick 핸들러 자체를 감싸서** tick마다 걸린 시간을 기록하고, (a) 잠든 태스크가 많으면 비싸지는지, (b) 같은 tick에 여러 태스크가 깨면 얼마나 비싸지는지를 따로 잰다.

### 2.1 예제 3 — tick 핸들러 시간 vs 잠든 태스크 N · 깨는 태스크 K

무엇을 확인하나: `-DC5_OWN_SYSTICK`으로 빌드해 `SysTick_Handler`를 앱이 정의하고, 그 안에서 포트의 `xPortSysTickHandler()`를 FPGA 카운터로 감싼다. N개의 태스크는 아주 먼 미래(100만 tick 뒤)에 깨도록 잠들고, K개의 태스크는 10 tick마다 **같은 tick에** 깬다(공통 기준점 `g_base`에서 `xTaskDelayUntil`). 300 tick 동안 tick마다 핸들러 시간을 기록해 "조용한 tick"과 "깨우는 tick"을 나눠 평균낸다.

```c
/* C5 ex2: tick 핸들러 하나가 몇 ns인가 — 잠든 태스크 N개, 같은 tick에 깨는 태스크 K개에 따라
 * 빌드: -DC5_OWN_SYSTICK -DN=.. -DK=..  (SysTick_Handler를 직접 감싸 xPortSysTickHandler 시간을 잰다) */
#include "FreeRTOS.h"
#include "task.h"
#include "c5.h"
#define NS 400
void xPortSysTickHandler(void);
static volatile uint32_t hd[NS], htk[NS], nh, armed;
void SysTick_Handler(void)
{
    uint32_t t0 = CYC();
    xPortSysTickHandler();
    uint32_t d = CYC() - t0;
    if (armed && nh < NS) { hd[nh] = d; htk[nh] = xTaskGetTickCountFromISR(); nh++; }
}
static TickType_t g_base;
static void sleeper(void *p) { (void)p; for (;;) vTaskDelay(1000000u); }   /* 먼 미래에 깬다 */
static void waker(void *p)                                                  /* K개가 같은 tick에 깬다 */
{ (void)p; TickType_t b = g_base; for (;;) xTaskDelayUntil(&b, 10); }
static void meas(void *p)
{
    (void)p;
    uint32_t t0 = CYC(), cal = CYC() - t0;                 /* CYC() 두 번 읽는 비용 */
    for (int i = 0; i < N; i++) xTaskCreate(sleeper, "s", 128, NULL, 1, NULL);
    g_base = xTaskGetTickCount();                         /* 과거 또는 지금이어야 한다 (§5.5 함정) */
    for (int i = 0; i < K; i++) xTaskCreate(waker, "w", 128, NULL, 2, NULL);
    vTaskDelay(20);                                        /* 모두 자리 잡을 때까지 */
    nh = 0; armed = 1;
    vTaskDelay(300);
    armed = 0;
    uint32_t qmin = ~0u, qmax = 0, qn = 0, wn = 0; uint64_t qs = 0, ws = 0;
    for (uint32_t i = 0; i + 1 < nh; i++) {                /* 마지막 = meas 자신이 깨는 tick, 제외 */
        uint32_t d = hd[i] - cal;
        if (K > 0 && (htk[i] - g_base) % 10u == 0) { ws += d; wn++; continue; }
        if (d < qmin) qmin = d;
        if (d > qmax) qmax = d;
        qs += d; qn++;
    }
    board_printf_raw("N=%u sleepers K=%u wakers: quiet tick min/avg/max = %u/%u/%u ns",
                     N, K, qmin * 40u, (uint32_t)(qs / qn) * 40u, qmax * 40u);
    if (wn) board_printf_raw("  wake tick avg = %u ns (%u samples)", (uint32_t)(ws / wn) * 40u, wn);
    board_printf_raw("\n");
    board_exit(0);
}
int main(void)
{
    xTaskCreate(meas, "meas", 512, NULL, 6, NULL);
    vTaskStartScheduler();
    return 1;
}
```

- **깨우는 tick은 K에 정비례한다**: K=1 3.9 µs, K=8 14.8 µs, K=32 52.5 µs. (52.48 − 3.92) / 31 ≈ **태스크 하나 깨울 때마다 1.57 µs**(약 39 명령). 각 태스크마다 delayed list에서 빼고(`listREMOVE_ITEM`), event list에 걸려 있으면 거기서도 빼고, ready list 끝에 붙이고(`prvAddTaskToReadyList`), 우선순위 비트맵을 갱신한다.
- 그러므로 **tick ISR의 최악 실행 시간은 "같은 tick에 깰 수 있는 태스크 수"로 정해진다.** 예를 들어 드론 FC에서 10개 태스크가 모두 `xTaskDelayUntil(&last, pdMS_TO_TICKS(10))`로 같은 기준점에서 시작하면 10 ms마다 한 tick이 다른 tick보다 10배 비싸다. tick ISR은 `configKERNEL_INTERRUPT_PRIORITY`(가장 낮음)라 다른 ISR을 막지는 않지만, 그 동안 **모든 태스크가 멈춘다**. 기준점을 엇갈리게(phase offset) 두면 비용이 고르게 퍼진다.

예제를 처음 짰을 때는 `g_base = xTaskGetTickCount() + 5`(5 tick 뒤부터 시작하라는 의도)로 썼는데, K개의 waker가 **한 번도 잠들지 않고** CPU를 독차지했다. 기준점이 미래면 `xTaskDelayUntil`이 "tick이 wrap했다"고 오해하기 때문이다. §5.5 예제 11에서 따로 재현한다.

### 2.2 예제 4 — tick rate × 부하 시나리오의 CPU 손실

무엇을 확인하나: A7의 바쁜 카운터 방식(인터럽트를 막고 200 ms 동안 루프를 센 기준선 대비, 인터럽트를 켜고 센 값이 얼마나 줄었나)으로, tick rate 100/1000/10000 Hz × (잠든 태스크 0개 / 32개 / 10 ms 주기 태스크 8개)의 9가지 조합을 잰다.

```c
/* C5 ex3: tick rate x 잠든 태스크 수 x 주기 태스크 -> 잃는 CPU (바쁜 카운터 방식)
 * 빌드: -DconfigTICK_RATE_HZ=.. -DNS=<잠든 태스크 수> -DNP=<10 ms 주기 태스크 수> */
#include "FreeRTOS.h"
#include "task.h"
#include "c5.h"
#define WINDOW (25000000u / 5)                       /* 200 ms 가상 시간 */
static uint32_t count_for_window(void)
{
    uint32_t n = 0, t0 = CYC();
    while (CYC() - t0 < WINDOW) n++;
    return n;
}
static void sleeper(void *p) { (void)p; for (;;) vTaskDelay(portMAX_DELAY - 1); }
static void periodic(void *p)                        /* 10 ms 주기, 서로 다른 위상 */
{
    TickType_t last = xTaskGetTickCount();
    vTaskDelay((TickType_t)(uintptr_t)p);
    last += (TickType_t)(uintptr_t)p;
    for (;;) xTaskDelayUntil(&last, pdMS_TO_TICKS(10) ? pdMS_TO_TICKS(10) : 1);
}
static void meas(void *p)
{
    (void)p;
    for (int i = 0; i < NS; i++) xTaskCreate(sleeper, "s", 128, NULL, 2, NULL);
    for (int i = 0; i < NP; i++)
        xTaskCreate(periodic, "p", 128, (void *)(uintptr_t)(i % (pdMS_TO_TICKS(10) + 1)), 3, NULL);
    vTaskDelay(pdMS_TO_TICKS(30) + 2);              /* 다른 태스크들이 자리 잡게 */
    portDISABLE_INTERRUPTS();
    uint32_t base = count_for_window();
    portENABLE_INTERRUPTS();
    uint32_t with = count_for_window();
    uint32_t bp = (uint32_t)((uint64_t)(base - with) * 10000u / base);   /* 0.01 % 단위 */
    board_printf_raw("rate=%u Hz NS=%u NP=%u: lost=%u.%u%u%% (%u ns per 1 ms)\n",
                     (unsigned)configTICK_RATE_HZ, NS, NP, bp / 100u, (bp / 10u) % 10u, bp % 10u,
                     (uint32_t)((uint64_t)(base - with) * 1000000u / base));
    board_exit(0);
}
int main(void)
{
    xTaskCreate(meas, "meas", 512, NULL, 1, NULL);
    vTaskStartScheduler();
    return 1;
}
```

### 2.3 예제 5 — 아낀 비용은 어디로 갔나: 잠들 때의 정렬 삽입

무엇을 확인하나: tick이 리스트를 안 봐도 되는 대가로, **잠드는 쪽**이 delayed list를 깨울 값 순서로 정렬해 넣는다(`vListInsert()`, `list.c:192`의 선형 탐색). N개가 먼저 잠든 상태에서 (a) 가장 먼저 깨는 위치(머리)에 들어가는 `vTaskDelay(3)`과 (b) 모든 태스크 뒤(꼬리)에 들어가는 `vTaskDelay(2000000)`의 "호출 → 다음 태스크가 CPU를 받기까지" 시간을 비교한다. 낮은 우선순위 태스크가 시각을 찍은 뒤 `xTaskAbortDelay()`로 측정 태스크를 바로 깨운다.

```c
/* C5 ex2b: tick에서 아낀 비용은 어디로 갔나 — 잠들 때 delayed list 정렬 삽입(vListInsert)은 O(N)
 * 빌드: -DN=<먼저 잠든 태스크 수>. meas가 vTaskDelay(d)를 부른 순간부터 낮은 우선순위 태스크가 CPU를 받을 때까지 */
#include "FreeRTOS.h"
#include "task.h"
#include "c5.h"
static volatile uint32_t t_call, t_got;
static TaskHandle_t hmeas;
static void sleeper(void *p) { (void)p; for (;;) vTaskDelay(1000000u); }   /* 깨울 값 = 약 now+1000000 */
static void low(void *p)                 /* 기록하고 meas를 xTaskAbortDelay로 바로 깨운다 */
{ (void)p; for (;;) { if (t_call && !t_got) { t_got = CYC(); xTaskAbortDelay(hmeas); } } }
static uint32_t one(TickType_t d)
{
    t_got = 0; t_call = CYC();
    vTaskDelay(d);                       /* 여기서 meas가 잠들고 low가 달린다 */
    uint32_t r = t_got - t_call; t_call = 0;
    return r;
}
static void meas(void *p)
{
    (void)p;
    for (int i = 0; i < N; i++) xTaskCreate(sleeper, "s", 128, NULL, 2, NULL);
    xTaskCreate(low, "low", 128, NULL, 1, NULL);
    vTaskDelay(5);
    uint32_t head = 0, tail = 0;
    for (int i = 0; i < 8; i++) { head += one(3); tail += one(2000000u); }   /* tail: 모든 sleeper 뒤 */
    board_printf_raw("N=%u sleepers: delay->switch  head insert %u ns   tail insert %u ns\n",
                     N, head / 8u * 40u, tail / 8u * 40u);
    board_exit(0);
}
int main(void)
{
    xTaskCreate(meas, "meas", 512, NULL, 3, &hmeas);
    vTaskStartScheduler();
    return 1;
}
```

출력에서 볼 것:

- 머리에 들어가는 `vTaskDelay(3)`은 N과 무관하게 **8.52 µs**(API 진입 + 리스트 삽입 + PendSV 전환 + 다음 태스크 시작까지 전부)다. 비교 한 번 만에 자리가 정해진다.
- 꼬리에 들어가는 `vTaskDelay(2000000)`은 **N에 비례**한다: 8.60 → 9.88 → 13.72 → 18.84 µs. (18840 − 8600) / 64 = **잠든 태스크 하나 지나갈 때마다 160 ns**(약 5 명령: 다음 노드 읽기, 값 비교, 분기). `vListInsert()`의 `for( pxIterator = ...; pxIterator->pxNext->xItemValue <= xValueOfInsertion; ... )` 한 줄이 그대로 보인다.
- 즉 FreeRTOS는 **비용을 tick(자주, ISR 안)에서 잠드는 호출(가끔, 태스크 문맥)로 옮겼다**. 잠드는 쪽은 O(N), tick은 O(1) + 깨는 수만큼. 태스크가 수십 개 수준인 MCU에서는 좋은 거래다. `<=` 비교라 같은 깨울 값끼리는 먼저 잠든 순서(FIFO)로 깬다.
- 실무 함의: 태스크 문맥의 `vTaskDelay`·`xQueueReceive(…, timeout)` 호출 비용은 "현재 잠든 태스크 수"에 따라 늘 수 있다. 수백 개 타이머가 필요한 설계라면 D6의 소프트웨어 타이머(하나의 데몬 태스크 + 자체 정렬 리스트)나 Zephyr의 delta list(§8.2)와 비교해 본다.

### 2.4 tick rate를 정하는 순서 (실무 체크)

1. 시스템에서 **tick으로 만들 가장 짧은 지연·타임아웃**을 적는다(예: I2C 재시도 대기 2 ms, CAN heartbeat 타임아웃 50 ms).
2. 그 값을 정수 tick으로 표현할 수 있는 가장 낮은 rate를 고른다(보통 1 kHz).
3. 그보다 정밀해야 하는 것(1 kHz 이상 제어 루프, µs 타임스탬프)은 tick이 아니라 HW 타이머·입력 캡처·DMA로 뺀다(E5, E7, J7).
4. 세금을 계산한다: rate × (tick당 비용). 25 MHz M3에서 1.47 µs면 1 kHz = 0.15%. 480 MHz H7이면 같은 명령 수가 대략 0.08 µs라 10 kHz도 0.08%다. 세금보다는 **같은 tick에 몰리는 깨우기**(예제 3)가 tick ISR 최악값을 정한다.
5. 배터리 장비면 tickless(C6)를 먼저 생각한다 — rate를 낮추는 것보다 효과가 크다.

그림 4 — `xTaskIncrementTick()`의 결정 흐름(단일 코어 경로). 대부분의 tick은 세 번째 상자에서 "아니오"로 빠져 리스트를 보지 않는다.

`xTaskIncrementTick()`의 단일 코어 경로를 주석과 함께 줄여 옮기면 이렇다(SMP 분기, 트레이스, 커버리지 마커 생략).

```c
BaseType_t xTaskIncrementTick( void )                        /* tasks.c:4831 */
{
    TCB_t * pxTCB; TickType_t xItemValue; BaseType_t xSwitchRequired = pdFALSE;

    if( uxSchedulerSuspended == 0 )                          /* (1) 스케줄러가 돌고 있으면 */
    {
        const TickType_t xConstTickCount = xTickCount + 1;
        xTickCount = xConstTickCount;                         /* (2) 시계 한 칸 */
        if( xConstTickCount == 0 )
            taskSWITCH_DELAYED_LISTS();                       /* (3) wrap: 리스트 교환 (§4) */

        if( xConstTickCount >= xNextTaskUnblockTime )         /* (4) 깨울 태스크가 있을 때만 */
        {
            for( ; ; )
            {
                if( listLIST_IS_EMPTY( pxDelayedTaskList ) )
                { xNextTaskUnblockTime = portMAX_DELAY; break; }
                pxTCB = listGET_OWNER_OF_HEAD_ENTRY( pxDelayedTaskList );
                xItemValue = listGET_LIST_ITEM_VALUE( &( pxTCB->xStateListItem ) );
                if( xConstTickCount < xItemValue )            /* (5) 머리가 아직이면 */
                { xNextTaskUnblockTime = xItemValue; break; } /*     다음 깨울 값을 캐시하고 끝 */
                listREMOVE_ITEM( &( pxTCB->xStateListItem ) );          /* (6) delayed list에서 */
                if( listLIST_ITEM_CONTAINER( &( pxTCB->xEventListItem ) ) != NULL )
                    listREMOVE_ITEM( &( pxTCB->xEventListItem ) );      /*     큐·세마포어 대기에서도 */
                prvAddTaskToReadyList( pxTCB );                          /*     ready list 끝으로 */
                if( pxTCB->uxPriority > pxCurrentTCB->uxPriority )
                    xSwitchRequired = pdTRUE;                 /* (7) 더 높으면 선점 */
            }
        }
        if( listCURRENT_LIST_LENGTH( &( pxReadyTasksLists[ pxCurrentTCB->uxPriority ] ) ) > 1U )
            xSwitchRequired = pdTRUE;                         /* (8) time slicing */
        /* configUSE_TICK_HOOK == 1 이면 vApplicationTickHook() (xPendedTicks == 0일 때만) */
        if( xYieldPendings[ 0 ] != pdFALSE )
            xSwitchRequired = pdTRUE;                         /* (9) 미뤄 둔 yield */
    }
    else
    {
        xPendedTicks += 1U;                                   /* (10) 스케줄러가 멈췄으면 쌓아 둔다 (§6) */
        /* tick hook은 스케줄러가 멈춰도 호출된다 */
    }
    return xSwitchRequired;
}
```

### 3.2 `xNextTaskUnblockTime` — 왜 N이 비용에 안 나타나나

delayed list는 깨울 값 순으로 정렬돼 있으므로 머리만 보면 "가장 먼저 깰 태스크"를 안다. 커널은 그 머리 값을 `xNextTaskUnblockTime`에 캐시해 두고 tick마다 **정수 비교 한 번**(`xConstTickCount >= xNextTaskUnblockTime`)만 한다. 이 값은 세 곳에서 갱신된다.

| 언제 | 어디서 | 무엇을 |
|---|---|---|
| 태스크가 잠들 때 | `prvAddCurrentTaskToDelayedList()` (`tasks.c:8685`) | 새 깨울 값이 캐시보다 작으면 캐시를 그 값으로 |
| tick에서 머리 태스크를 깨운 뒤 | `xTaskIncrementTick()` (5) | 새 머리의 값으로, 리스트가 비면 `portMAX_DELAY`로 |
| 리스트 교환·태스크 삭제·지연 취소 뒤 | `prvResetNextTaskUnblockTime()` | 머리를 다시 읽어서 |

Don의 SSD 펌웨어 비유로 말하면, 타임아웃 테이블 전체를 매 ms 훑는 대신 "다음 만료 시각" 하나를 들고 있다가 그 시각이 됐을 때만 테이블을 보는 것이다. 하드웨어 타이머의 compare 레지스터와 같은 발상이고, tickless(C6)는 이 값을 실제 하드웨어 compare 레지스터에 써서 그때까지 tick 자체를 꺼 버린다.

### 3.3 깨어나는 태스크는 리스트 두 개에서 빠진다

TCB에는 리스트 항목이 두 개 있다(C1).

- `xStateListItem` — 태스크의 **상태** 리스트(ready / delayed / suspended 중 하나)에 걸린다.
- `xEventListItem` — **무엇을 기다리는지**(큐의 `xTasksWaitingToReceive`, 세마포어 등)에 걸린다. 우선순위 순으로 정렬된다.

`xQueueReceive(q, &v, 20)`으로 잠든 태스크는 두 리스트에 동시에 걸린다. 큐에 데이터가 오면 큐 쪽 코드가 event list에서 꺼내고 상태 리스트도 정리한다. 20 tick이 먼저 지나면 tick 쪽 코드(위 (6))가 delayed list에서 꺼내면서 event list에서도 뺀다. 태스크는 `xQueueReceive` 안의 루프로 돌아와 `xTaskCheckForTimeOut()`이 `pdTRUE`를 돌려주므로 `errQUEUE_EMPTY`를 반환한다(§7.4).

### 3.4 time slicing 요청

(8)은 "현재 우선순위의 ready 리스트에 태스크가 둘 이상이면 tick마다 전환을 요청"한다. 이 요청은 **현재 태스크가 그 우선순위에서 돌고 있을 때만** 의미가 있다. `configUSE_TIME_SLICING = 0`이면 같은 우선순위 태스크는 누가 양보(블록·`taskYIELD()`)할 때까지 돌아간다. 슬라이스 길이는 **정확히 1 tick이 아니다** — 태스크가 tick 중간에 시작했으면 그 tick의 나머지만 받는다. 자세한 정책 차이는 C4.

- Zephyr 쪽 tick 경로(`sys_clock_isr` 96 B + `sys_clock_announce_locked` 184 B + `sys_clock_set_timeout` 224 B + `z_time_slice` 92 B)는 FreeRTOS(`SysTick_Handler` 44 B + 본체 412 B)보다 크고, tickless라 매번 다음 타임아웃을 하드웨어에 다시 프로그램한다(§8.2). A7에서 Zephyr 주기 tick이 tick당 약 3~4.5 µs로 FreeRTOS의 2~3배였던 것과 맞는 그림이다.

### 3.6 Don 경험과 연결

SSD 펌웨어의 타이머 ISR이 "카운터 증가 + 만료 콜백 몇 개 호출"이었다면, FreeRTOS tick은 "카운터 증가 + 만료 태스크를 ready로 옮기기"다. **콜백을 ISR에서 실행하지 않는다**는 점이 다르다. 깨어난 태스크의 코드는 PendSV 뒤 태스크 문맥에서 돈다. 그래서 tick ISR은 짧고 결정적이다(깨는 수에만 비례). 반대로 Zephyr의 `sys_clock_announce()`는 만료된 `_timeout`의 **콜백 함수(`t->fn(t)`)를 ISR 문맥에서 직접 호출**한다(§8.2). 스레드 깨우기도 그 콜백(`z_thread_timeout`) 중 하나이고, `k_timer`의 만료 함수도 같은 길로 ISR에서 돈다(D6).

### 4.2 커널은 어떻게 wrap을 견디나 — 리스트를 두 개 둔다

`prvAddCurrentTaskToDelayedList()`(`tasks.c:8685`)가 핵심이다(단일 코어, 주석 줄임).

```c
xTimeToWake = xConstTickCount + xTicksToWait;          /* 넘칠 수 있다 — 괜찮다 */
listSET_LIST_ITEM_VALUE( &( pxCurrentTCB->xStateListItem ), xTimeToWake );
if( xTimeToWake < xConstTickCount )                     /* 넘쳤다 = wrap 뒤에 깰 태스크 */
    vListInsert( pxOverflowDelayedList, &( pxCurrentTCB->xStateListItem ) );
else
{
    vListInsert( pxDelayedList, &( pxCurrentTCB->xStateListItem ) );
    if( xTimeToWake < xNextTaskUnblockTime )
        xNextTaskUnblockTime = xTimeToWake;
}
```

깨울 값이 넘친 태스크는 **다른 리스트(overflow list)** 에 들어간다. 그러면 각 리스트 안에서는 값의 크기 비교가 항상 올바른 시간 순서가 된다. `xTickCount`가 0xFFFFFFFF → 0이 되는 tick에 `taskSWITCH_DELAYED_LISTS()`(`tasks.c:267`)가 두 리스트의 **포인터만 바꾼다**.

```c
#define taskSWITCH_DELAYED_LISTS()                                                \
    do {                                                                          \
        List_t * pxTemp;                                                          \
        configASSERT( ( listLIST_IS_EMPTY( pxDelayedTaskList ) ) );               \
        pxTemp = pxDelayedTaskList;                                               \
        pxDelayedTaskList = pxOverflowDelayedTaskList;                            \
        pxOverflowDelayedTaskList = pxTemp;                                       \
        xNumOfOverflows = ( BaseType_t ) ( xNumOfOverflows + 1 );                 \
        prvResetNextTaskUnblockTime();                                            \
```

### 4.3 예제 7 — `configINITIAL_TICK_COUNT=0xFFFFFFF0`으로 wrap을 16 tick 뒤로 당기기

무엇을 확인하나: 커널을 wrap 16 tick 전에서 시작시키고, (a) `vTaskDelay(10)` 반복, (b) `xTaskDelayUntil(&last, 7)` 반복, (c) 앱 코드의 마감 비교 두 가지(나쁜 방식 `now < deadline`, 올바른 방식 `(TickType_t)(now - start) < dur`)를 동시에 돌린다. `xNumOfOverflows`는 static이라 직접 못 읽으므로 `vTaskSetTimeOutState()`가 채워 주는 `TimeOut_t.xOverflowCount`로 엿본다.

```c
/* C5 ex4: tick 카운터 wrap — configINITIAL_TICK_COUNT=0xFFFFFFF0 으로 시작해서 16 tick 뒤 0을 지나게 한다 */
#include "FreeRTOS.h"
#include "task.h"
#include "c5.h"
static uint32_t ovf(void) { TimeOut_t t; vTaskSetTimeOutState(&t); return (uint32_t)t.xOverflowCount; }
static void rel(void *p)                               /* 상대 지연: vTaskDelay(10) */
{
    (void)p;
    for (int i = 0; i < 4; i++) {
        TickType_t a = xTaskGetTickCount(); uint32_t u = board_now_us();
        vTaskDelay(10);
        board_printf_raw("[rel ] tick 0x%x -> 0x%x  slept %u us  overflows=%u\n",
                         (unsigned)a, (unsigned)xTaskGetTickCount(), board_now_us() - u, ovf());
    }
    vTaskDelete(NULL);
}
static void absl(void *p)                              /* 절대 지연: xTaskDelayUntil(&last, 7) */
{
    (void)p;
    TickType_t last = xTaskGetTickCount();
    for (int i = 0; i < 5; i++) {
        BaseType_t slept = xTaskDelayUntil(&last, 7);
        board_printf_raw("[abs ] woke at 0x%x  last=0x%x  slept=%d\n",
                         (unsigned)xTaskGetTickCount(), (unsigned)last, (int)slept);
    }
    vTaskDelete(NULL);
}
static void cmp(void *p)                               /* 마감 비교: 나쁜 방식 vs 올바른 방식 */
{
    (void)p;
    vTaskDelay(4);                                     /* tick = 0xFFFFFFF4 근처 */
    TickType_t start = xTaskGetTickCount(), deadline = start + 20;   /* deadline이 wrap해서 작아진다 */
    uint32_t n_bad = 0, n_ok = 0;
    while (xTaskGetTickCount() < deadline) { n_bad++; vTaskDelay(1); }               /* BUG */
    TickType_t s2 = xTaskGetTickCount();
    while ((TickType_t)(xTaskGetTickCount() - s2) < 20) { n_ok++; vTaskDelay(1); }  /* OK */
    board_printf_raw("[cmp ] start=0x%x deadline=0x%x  bad loop ran %u ticks, good loop ran %u ticks\n",
                     (unsigned)start, (unsigned)deadline, n_bad, n_ok);
    vTaskDelay(30);
    board_exit(0);
}
int main(void)
{
    board_printf_raw("configINITIAL_TICK_COUNT=0x%x\n", (unsigned)configINITIAL_TICK_COUNT);
    xTaskCreate(rel, "rel", 256, NULL, 3, NULL);
    xTaskCreate(absl, "abs", 256, NULL, 2, NULL);
    xTaskCreate(cmp, "cmp", 256, NULL, 1, NULL);
    vTaskStartScheduler();
    return 1;
}
```

출력에서 볼 것:

- `[rel ] tick 0xfffffffa -> 0x4`: wrap을 건너뛴 `vTaskDelay(10)`이 정확히 10 tick(9967 µs) 잤다. 이 순간 `overflows`가 0 → 1이 됐다. 이 태스크는 잠들 때 깨울 값 0x4가 넘쳤으므로 overflow list에 들어갔다가 교환으로 살아났다.
- `[abs ]`는 0xfffffff7 → 0xfffffffe → 0x5 → 0xc → 0x13으로 **7 tick 간격이 wrap을 지나서도 그대로**다. `xTaskDelayUntil`의 wrap 분기(§5.2)가 동작했다.
- `[cmp ]`: start = 0xfffffff4, deadline = start + 20 = **0x8**(넘쳐서 작아짐). 나쁜 루프 `while (now < deadline)`은 첫 비교에서 0xfffffff4 < 0x8이 거짓이라 **0번** 돌고 끝났다. "20 ms 기다리기"가 0 ms가 된 것이다. 올바른 루프 `(TickType_t)(now - s2) < 20`은 정확히 20번 돌았다. 커널은 wrap을 처리하지만 **앱 코드의 비교는 커널이 대신 처리해 주지 않는다.**
- 각 `slept` 값이 10000 µs보다 약간 짧은 것(9967~9994 µs)은 `a`를 찍은 시각이 tick 경계 직후가 아니라 앞 줄 출력이 끝난 뒤이기 때문이다. `vTaskDelay(n)`은 "n번째 tick 경계에서 깬다"이므로 실제로는 n−1 tick 초과 ~ n tick이다(§5.3).

### 4.4 앱 코드의 wrap 안전 규칙

| 하고 싶은 것 | 틀린 코드 | 맞는 코드 |
|---|---|---|
| 경과 시간 | `now > start + dur` | `(TickType_t)(now - start) >= dur` |
| 마감 지났나 | `now >= deadline` | `(int32_t)(now - deadline) >= 0` (32비트, 차이가 2^31 미만일 때) |
| 남은 시간 | `deadline - now` (음수 가능성 무시) | `vTaskSetTimeOutState` + `xTaskCheckForTimeOut` (§7) |
| 긴 시간 측정 | 32비트 tick을 일·주 단위로 비교 | 64비트 카운터를 따로 둔다(`xTaskGetTickCount` + 자체 wrap 카운터, 또는 Zephyr `k_uptime_ticks()`) |

부호 없는 뺄셈은 모듈로 2^32 산술이라 wrap을 한 번 지나도 차이가 맞다. 단 **차이 자체가 한 바퀴 이상**이면 틀린다(49.7일 넘는 타임아웃). 16비트 tick에서 이 규칙을 쓸 때는 `(TickType_t)` 캐스트를 꼭 붙인다 — 붙이지 않으면 C의 정수 승격(int로 확장) 때문에 뺄셈이 음수가 된다. Linux `time_after()` 매크로와 같은 발상이다(EL F8 §5.4).

### 4.5 예제 8 — 16비트 tick: 6.55초마다 wrap, 그리고 조용한 잘림

무엇을 확인하나: `configTICK_TYPE_WIDTH_IN_BITS=TICK_TYPE_WIDTH_16_BITS`, 10 kHz로 빌드한다(8/16비트 MCU 포트나 RAM을 아끼는 설정에서 실제로 쓴다). `pdMS_TO_TICKS(10000)`, `xQueueReceive(…, portMAX_DELAY − 1)`, `xQueueReceive(…, portMAX_DELAY)`, `vTaskDelay(portMAX_DELAY)`가 각각 언제 돌아오는지 본다. main 태스크는 8초에 q2로만 데이터를 보낸다.

```c
/* C5 ex5: 16비트 tick (configTICK_TYPE_WIDTH_IN_BITS=TICK_TYPE_WIDTH_16_BITS) @ 10 kHz
 * — 6.55초마다 wrap, pdMS_TO_TICKS 조용한 잘림, portMAX_DELAY 와 portMAX_DELAY-1 의 차이 */
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "c5.h"
static QueueHandle_t q1, q2;
static uint32_t t0;
static void ms(const char *who, const char *what)
{ uint32_t u = board_now_us() - t0; board_printf_raw("%u ms  [%s] %s  (tick=%u)\n",
      u / 1000u, who, what, (unsigned)xTaskGetTickCount()); }
static void sleeper(void *p)
{ (void)p; vTaskDelay(pdMS_TO_TICKS(10000)); ms("sleep", "vTaskDelay(pdMS_TO_TICKS(10000)) returned"); vTaskDelete(NULL); }
static void waitA(void *p)
{ (void)p; int v; BaseType_t r = xQueueReceive(q1, &v, portMAX_DELAY - 1);
  ms("A", r ? "got data" : "TIMEOUT (waited portMAX_DELAY-1 = 65534 ticks)"); vTaskDelete(NULL); }
static void waitB(void *p)
{ (void)p; int v; BaseType_t r = xQueueReceive(q2, &v, portMAX_DELAY);
  ms("B", r ? "got data (portMAX_DELAY never timed out)" : "TIMEOUT"); vTaskDelete(NULL); }
static void forever(void *p)
{ (void)p; vTaskDelay(portMAX_DELAY); ms("C", "vTaskDelay(portMAX_DELAY) returned!"); vTaskDelete(NULL); }
static void main_task(void *p)
{
    (void)p;
    t0 = board_now_us();
    board_printf_raw("sizeof(TickType_t)=%u portMAX_DELAY=%u rate=%u Hz -> wrap every %u ms\n",
        (unsigned)sizeof(TickType_t), (unsigned)portMAX_DELAY, (unsigned)configTICK_RATE_HZ,
        (unsigned)(65536u * 1000u / configTICK_RATE_HZ));
    board_printf_raw("pdMS_TO_TICKS(1000)=%u  pdMS_TO_TICKS(10000)=%u (want 100000)\n",
        (unsigned)pdMS_TO_TICKS(1000), (unsigned)pdMS_TO_TICKS(10000));
    q1 = xQueueCreate(1, sizeof(int)); q2 = xQueueCreate(1, sizeof(int));
    xTaskCreate(sleeper, "sl", 256, NULL, 2, NULL);
    xTaskCreate(waitA, "A", 256, NULL, 2, NULL);
    xTaskCreate(waitB, "B", 256, NULL, 2, NULL);
    xTaskCreate(forever, "C", 256, NULL, 2, NULL);
    vTaskDelay(pdMS_TO_TICKS(3000)); vTaskDelay(pdMS_TO_TICKS(3000)); vTaskDelay(pdMS_TO_TICKS(2000));
    int v = 1; ms("main", "send to q2 at ~8 s"); xQueueSend(q2, &v, 0);
    vTaskDelay(10);
    board_exit(0);
}
int main(void)
{
    xTaskCreate(main_task, "m", 512, NULL, 3, NULL);
    vTaskStartScheduler();
    return 1;
}
```

- A: `portMAX_DELAY − 1` = 65534 tick 대기는 정확히 6.553초에 타임아웃. tick은 그 순간 0(wrap)이었다.
- B: 블로킹 API(`xQueueReceive`)에 `portMAX_DELAY`를 주면 **진짜 무한 대기**다. wrap을 지나 8초에 데이터를 받았다. `INCLUDE_vTaskSuspend == 1`이면 이 태스크는 delayed list가 아니라 **suspended list**에 들어가 시간으로는 절대 깨지 않는다(§7.1).
- **C: `vTaskDelay(portMAX_DELAY)`는 무한이 아니다.** 6.553초(65535 tick) 뒤에 돌아왔다. `vTaskDelay()`는 `prvAddCurrentTaskToDelayedList( xTicksToDelay, pdFALSE )`로 "무한 대기 허용" 인자를 **pdFALSE**로 넘기기 때문에 `portMAX_DELAY`도 그냥 큰 숫자로 취급된다. 32비트에서는 49.7일 뒤에 깬다. "영원히 재우기"는 `vTaskSuspend(NULL)`이나 `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)`로 한다.

### 4.6 함정 — wrap 관련

- 테스트 빌드에 **`configINITIAL_TICK_COUNT`를 wrap 몇 초 전으로** 두는 것을 CI 기본으로 한다. Linux의 `INITIAL_JIFFIES`와 같은 역할이다. 49.7일 버그를 부팅 몇 초 만에 터뜨린다.
- 16비트 tick에서는 `pdMS_TO_TICKS`·곱셈 결과가 65535를 넘지 않는지 `configASSERT`로 확인한다. 최대 대기는 65534 tick(10 kHz면 6.55초)이다.
- `vTaskDelay(portMAX_DELAY)`를 "영원히"로 쓰지 않는다.
- 런타임 통계 카운터(`portGET_RUN_TIME_COUNTER_VALUE`), 자체 ms 카운터, 로그 타임스탬프도 같은 wrap 문제를 갖는다. 랩의 `board_now_us()`도 약 171초마다 wrap한다(`board.h` 주석).

## 5. 지연 API 세 가지 — `vTaskDelay` / `xTaskDelayUntil` / `xTaskPeriodicDelay`

### 5.1 직관 — 상대 지연, 절대 지연, 건너뛰는 절대 지연

- **`vTaskDelay(n)`** — "**지금부터** n tick 뒤에 깨워 줘." 기준이 매번 "지금"이라 일하는 시간과 선점당한 시간이 주기에 그대로 더해진다(드리프트).
- **`xTaskDelayUntil(&last, T)`** — "**지난번 깨기로 한 시각(last) + T**에 깨워 줘." 격자(grid)에 맞춘다. 늦어서 이미 그 시각이 지났으면 **잠들지 않고 바로 돌아온다** → 밀린 주기를 연달아 실행하며 따라잡는다(catch-up). `vTaskDelayUntil()`은 반환값만 버리는 같은 동작이다(`xTaskDelayUntil`은 V10.4.2에 도입, 지금 `vTaskDelayUntil`은 `task.h:1006`의 매크로).
- **`xTaskPeriodicDelay(&last, T)`** — V11.3.1에 새로 들어온 API. 격자에 맞추되 **놓친 주기는 건너뛰고 다음 격자에서** 깬다(skip). 반환값으로 지나간 주기 수를 알려 준다.

### 5.2 소스로 보는 세 함수

`vTaskDelay()`(`tasks.c` V11.3.2, 2500줄 근처)는 짧다.

```c
void vTaskDelay( const TickType_t xTicksToDelay )
{
    BaseType_t xAlreadyYielded = pdFALSE;
    if( xTicksToDelay > ( TickType_t ) 0U )              /* 0이면 잠들지 않고 양보만 */
    {
        vTaskSuspendAll();
        prvAddCurrentTaskToDelayedList( xTicksToDelay, pdFALSE );  /* pdFALSE: portMAX_DELAY도 유한 */
        xAlreadyYielded = xTaskResumeAll();
    }
    if( xAlreadyYielded == pdFALSE )
        taskYIELD_WITHIN_API();
}
```

`xTaskDelayUntil()`(`tasks.c:2414`)의 핵심은 wrap을 고려한 "잠들어야 하나" 판단이다.

```c
xTimeToWake = *pxPreviousWakeTime + xTimeIncrement;
if( xConstTickCount < *pxPreviousWakeTime )          /* tick이 last 이후 wrap했다 */
{   /* 깰 시각도 wrap했고 아직 안 왔을 때만 잔다 */
    if( ( xTimeToWake < *pxPreviousWakeTime ) && ( xTimeToWake > xConstTickCount ) )
        xShouldDelay = pdTRUE;
}
else
{   /* 깰 시각이 wrap했거나(미래) 아직 안 왔으면 잔다 */
    if( ( xTimeToWake < *pxPreviousWakeTime ) || ( xTimeToWake > xConstTickCount ) )
        xShouldDelay = pdTRUE;
}
*pxPreviousWakeTime = xTimeToWake;                   /* 잠들든 안 잠들든 격자 한 칸 전진 */
if( xShouldDelay != pdFALSE )
    prvAddCurrentTaskToDelayedList( xTimeToWake - xConstTickCount, pdFALSE );
return xShouldDelay;                                 /* pdFALSE = 늦어서 안 잤다 */
```

두 가지를 기억한다. (1) `*pxPreviousWakeTime`은 **잠들지 않아도 T만큼 전진**한다 — 그래서 늦으면 밀린 칸 수만큼 연달아 즉시 돌아와 catch-up이 된다. (2) "`now < last`면 wrap했다"고 가정한다 — 그래서 `last`를 **미래 값으로 초기화하면** wrap으로 오해해 영영 잠들지 않는다(예제 11).

`xTaskPeriodicDelay()`(`tasks.c:2365`)는 나눗셈으로 계산한다.

```c
const TickType_t xTicksElapsed = xTickCount - *pxPreviousWakeTime;  /* 부호 없는 뺄셈: wrap 안전 */
xIncrements = xTicksElapsed / xTimeIncrement;            /* 지나간 주기 수: 0, 1, 2 이상 */
xTicksIncrements = xIncrements * xTimeIncrement;
*pxPreviousWakeTime += xTicksIncrements;                 /* 기준점을 지금 직전 격자로 */
xTicksToWait = xTimeIncrement - ( xTicksElapsed - xTicksIncrements );  /* 다음 격자까지 */
prvAddCurrentTaskToDelayedList( xTicksToWait, pdFALSE ); /* 항상 잔다 (최소 1 tick) */
return xIncrements;
```

`DelayUntil`과 달리 `*pxPreviousWakeTime`이 "다음에 깰 시각"이 아니라 **"지금 직전의 격자점"**으로 갱신된다. 그래서 정상 상태에서 반환값은 1이고(직전 깨어남 이후 정확히 한 주기), 첫 호출은 0(아직 한 주기도 안 지남), 주기를 넘쳤으면 2 이상이다. **놓친 주기 수 = 반환값 − 1**. 그리고 항상 다음 격자까지 잠든다 — 따라잡기 폭주가 없다.

### 5.3 예제 9 — `vTaskDelay(1)`은 0~1 tick이다 (그리고 Zephyr는 1~2 tick)

무엇을 확인하나: tick 경계에 맞춘 뒤 0~999 µs 사이 임의 시간을 바쁜 대기로 보내고(=tick 안의 임의 위상) `vTaskDelay(1)`·`vTaskDelay(2)`가 실제로 잔 시간을 1000번 잰다. 같은 실험을 Zephyr `k_sleep(K_TICKS(1))`·`(2)`로 1 kHz tick에서 한다.

```c
/* C5 ex8: vTaskDelay(1)은 실제로 얼마나 자나 — tick 안의 임의 위상에서 1000번 호출해 분포를 본다 */
#include "FreeRTOS.h"
#include "task.h"
#include "c5.h"
#define NSAMP 1000
static void sample(TickType_t n)
{
    uint32_t bins[12] = { 0 }, mn = ~0u, mx = 0; uint64_t sum = 0;
    for (int i = 0; i < NSAMP; i++) {
        vTaskDelay(1);                                  /* tick 경계로 맞춘 뒤 */
        spin_us(rnd(1000));                             /* tick 안의 임의 위상 0..999 us */
        uint32_t a = board_now_us();
        vTaskDelay(n);
        uint32_t d = board_now_us() - a;
        if (d < mn) mn = d;
        if (d > mx) mx = d;
        sum += d;
        bins[(d / 250u) > 11u ? 11u : d / 250u]++;      /* 250 us 칸 */
    }
    board_printf_raw("vTaskDelay(%u) @%u Hz: min=%u avg=%u max=%u us\n  bins(250us):", (unsigned)n,
                     (unsigned)configTICK_RATE_HZ, mn, (uint32_t)(sum / NSAMP), mx);
    for (int b = 0; b < (int)(n * 4u + 1u) && b < 12; b++) board_printf_raw(" %u", bins[b]);
    board_printf_raw("\n");
}
static void task(void *p)
{
    (void)p;
    sample(1);
    sample(2);
    board_exit(0);
}
int main(void)
{
    xTaskCreate(task, "t", 512, NULL, 2, NULL);
    vTaskStartScheduler();
    return 1;
}
```

```c
/* C5 ex9b: Zephyr k_sleep(K_TICKS(n)) 분포 @1 kHz — FreeRTOS ex8과 같은 방법(임의 위상, 1000회, 250 us 칸) */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>
#define CYC() (*(volatile uint32_t *)0x40028018u)
static uint32_t seed = 12345u;
static uint32_t rnd(uint32_t n) { seed = seed * 1103515245u + 12345u; return (seed >> 8) % n; }
static void spin_us(uint32_t us) { uint32_t t0 = CYC(); while (CYC() - t0 < us * 25u) { } }
static void sample(int n)
{
	uint32_t bins[14] = { 0 }, mn = ~0u, mx = 0, sum = 0;
	for (int i = 0; i < 1000; i++) {
		k_sleep(K_TICKS(1));
		spin_us(rnd(1000000u / CONFIG_SYS_CLOCK_TICKS_PER_SEC));
		uint32_t a = CYC();
		k_sleep(K_TICKS(n));
		uint32_t d = (CYC() - a) / 25u;
		mn = MIN(mn, d); mx = MAX(mx, d); sum += d;
		bins[MIN(d / 250u, 13u)]++;
	}
	printk("k_sleep(K_TICKS(%d)) @%u Hz: min=%u avg=%u max=%u us\n  bins(250us):", n,
	       CONFIG_SYS_CLOCK_TICKS_PER_SEC, mn, sum / 1000u, mx);
	for (int b = 0; b < 4 * n + 5 && b < 14; b++) printk(" %u", bins[b]);
	printk("\n");
}
int main(void)
{
	sample(1);
	sample(2);
	register uint32_t r0 __asm__("r0") = 0x18, r1 __asm__("r1") = 0x20026;
	__asm volatile("bkpt 0xab" : : "r"(r0), "r"(r1) : "memory");
	return 0;
}
```

출력에서 볼 것:

- **FreeRTOS `vTaskDelay(1)`: 12~1005 µs, 평균 498 µs** — 0~1 tick에 거의 균일하게 퍼진다. "1 tick 기다려"는 "**다음 tick 경계까지**"라는 뜻이기 때문이다. 경계 직전에 부르면 거의 0이다. `vTaskDelay(2)`는 1008~2005 µs. 일반적으로 **`vTaskDelay(n)`의 실제 지연은 (n−1, n] tick**이다.
- **Zephyr `k_sleep(K_TICKS(1))`: 1030~2028 µs, 평균 1520 µs** — 1~2 tick. Zephyr는 상대 타임아웃에 1 tick을 더해 "**최소 요청한 시간 이상**"을 보장한다(`kernel/timeout.c:111`, §8.2). 대신 평균 0.5 tick 더 오래 잔다.
- 두 커널의 철학 차이다: FreeRTOS는 "tick 경계 n번째", Zephyr는 "최소 n tick". FreeRTOS에서 "최소 1 ms"가 필요하면 `vTaskDelay(pdMS_TO_TICKS(1) + 1)`처럼 직접 1을 더한다(1 kHz에서 1~2 ms).
- 1000번 중 5번(Zephyr는 27번)이 마지막 칸에 있는 것은 임의 위상이 0 근처일 때 깨어남 지연(커널 경로 수 µs)이 더해져서다.

### 5.4 예제 10 — 500주기 drift: 들쭉날쭉한 일 + 방해꾼 + 한 번의 초과 실행

무엇을 확인하나: A1 §9가 "일정한 2.5 ms 일, 100주기"로 보여 준 차이를 더 현실적인 조건에서 다시 잰다. 10 ms 주기, 일은 1~3 ms 임의(세 API에 같은 수열), 7 ms마다 0.3 ms를 쓰는 더 높은 우선순위 태스크(방해꾼), 그리고 k = 200에서 한 번 25 ms(센서 재시도 같은 사고). 각 주기 시작 시각과 이상적인 격자(시작 tick + k × 10 ms)의 차이(위상 오차)를 20주기마다, 그리고 k = 199~205에서 찍는다. 출력 숫자 단위는 **100 µs**다(`err / 100`).

```c
/* C5 ex7: 10 ms 주기 태스크 500주기 — vTaskDelay / xTaskDelayUntil / xTaskPeriodicDelay 의 위상 오차.
 * 일은 1~3 ms로 들쭉날쭉, 7 ms마다 0.3 ms 쓰는 높은 우선순위 방해꾼, k=200에서 한 번 25 ms 초과 실행 */
#include "FreeRTOS.h"
#include "task.h"
#include "c5.h"
#define T 10u
#define NPER 500
static void intruder(void *p)
{ (void)p; TickType_t l = xTaskGetTickCount(); for (;;) { xTaskDelayUntil(&l, 7); spin_us(300); } }
static const char *const nm[3] = { "vTaskDelay", "xTaskDelayUntil", "xTaskPeriodicDelay" };
static void per(void *p)
{
    (void)p;
    vTaskDelay(1);
    uint32_t off = board_now_us() % 1000u;               /* tick이 울리는 us 위상 (방해꾼 없는 tick 1) */
    for (int api = 0; api < 3; api++) {
        vTaskDelay(3); c5_seed = 777u;                    /* 세 API 모두 같은 일 수열 */
        TickType_t last = xTaskGetTickCount();
        uint32_t g0 = board_now_us(), hist[3] = { 0, 0, 0 };
        g0 -= (g0 + 1000u - off) % 1000u;                 /* 기준 = 이 tick이 울린 시각 */
        board_printf_raw("%s:", nm[api]);
        for (uint32_t k = 0; k < NPER; k++) {
            int32_t err = (int32_t)(board_now_us() - g0) - (int32_t)(k * T * 1000u);   /* 위상 오차 */
            if (k % 20 == 0 || (k >= 199 && k <= 205)) board_printf_raw(" %u:%d", k, err / 100);
            spin_us(k == 200 ? 25000u : 1000u + rnd(2000));
            if (api == 0) vTaskDelay(T);
            else if (api == 1) xTaskDelayUntil(&last, T);
            else { TickType_t n = xTaskPeriodicDelay(&last, T); hist[n > 2 ? 2 : n]++; }
        }
        uint32_t span = board_now_us() - g0;
        board_printf_raw("\n  -> %u periods took %u ms (ideal %u)", NPER, span / 1000u, NPER * T);
        if (api == 2) board_printf_raw("  returns: 0->%u 1->%u >=2->%u", hist[0], hist[1], hist[2]);
        board_printf_raw("\n");
    }
    board_exit(0);
}
int main(void)
{
    xTaskCreate(intruder, "intr", 256, NULL, 4, NULL);
    xTaskCreate(per, "per", 512, NULL, 3, NULL);
    vTaskStartScheduler();
    return 1;
}
```

출력에서 볼 것(위상 오차 = 숫자 × 0.1 ms):

- **`vTaskDelay`: 500주기 = 5791 ms (+15.8%).** 위상 오차가 주기마다 평균 1.58 ms씩 쌓여 k = 480에서 **+761 ms**. 주기 = 일(평균 2 ms) + 10 tick − tick 경계까지 남은 몫 + 방해꾼. 일의 길이가 들쭉날쭉하니 주기도 들쭉날쭉하다(20주기마다 증가량이 30.0~33.3 ms로 흔들림). k = 200의 25 ms 사고는 그대로 +25 ms 계단으로 남는다.
- **`xTaskDelayUntil`: 정확히 5000 ms.** 평소 오차 0(가끔 0.3 ms = 방해꾼이 같은 tick에 먼저 돈 경우 — 그것은 시작 지연이지 누적이 아니다). k = 200에서 25 ms를 쓰자 k = 201은 **15.3 ms 늦게**, k = 202는 7.8 ms, k = 203은 0.2 ms 늦게 시작 — **두 주기를 쉬지 않고 연달아 돌며 따라잡았다**(catch-up). 그 동안 이 태스크는 CPU를 쉬지 않고 쓴다.
- **`xTaskPeriodicDelay`: k = 201부터 +20.0 ms에 고정** — 놓친 두 칸(slot 201·202)을 버리고 slot 203의 격자 시각에 바로 맞췄다. 그 뒤로 오차는 계속 정확히 20.0 ms(= 버린 두 주기). 500번 호출 중 반환값 1이 498번, 0이 1번(첫 호출), 2 이상이 1번(사고 직후, 실제 값은 3 = 두 칸 건너뜀)이다. 전체 시간 5020 ms = 5000 + 버린 2주기.
- 어느 쪽이 맞는지는 **일의 성격**이 정한다. 적분기·카운터·로그처럼 모든 샘플이 필요하면 catch-up(`xTaskDelayUntil`), 제어 루프처럼 최신 샘플만 의미 있으면 skip(`xTaskPeriodicDelay`). 어느 쪽이든 반환값으로 **사고를 감지해 카운트**한다(A1 §10의 miss 정책).

### 5.5 예제 11 — 기준점을 미래로 잡으면 `xTaskDelayUntil`이 잠들지 않는다

무엇을 확인하나: "5 tick 뒤부터 10 tick 주기로 돌고 싶다"며 `last = now + 5`로 초기화하면 무슨 일이 생기는가. 예제 3을 처음 짤 때 실제로 밟은 함정이다.

```c
/* C5 ex11: pxPreviousWakeTime을 "미래"로 초기화하면 — xTaskDelayUntil이 wrap으로 착각해 잠들지 않는다 */
#include "FreeRTOS.h"
#include "task.h"
#include "c5.h"
static void task(void *p)
{
    (void)p;
    vTaskDelay(10);
    TickType_t last = xTaskGetTickCount() + 5;            /* "5 tick 뒤부터 10 tick 주기로" 라는 의도 */
    board_printf_raw("now=%u last(init)=%u\n", (unsigned)xTaskGetTickCount(), (unsigned)last);
    for (int i = 0; i < 4; i++) {
        BaseType_t r = xTaskDelayUntil(&last, 10);
        board_printf_raw("  DelayUntil #%d: now=%u last=%u slept=%d\n", i, (unsigned)xTaskGetTickCount(),
                         (unsigned)last, (int)r);
    }
    /* 올바른 방법: 먼저 시작 시각까지 기다린 뒤, 그 시각을 기준점으로 */
    TickType_t start = xTaskGetTickCount() + 5;
    vTaskDelay(start - xTaskGetTickCount());
    last = start;
    for (int i = 0; i < 3; i++) {
        BaseType_t r = xTaskDelayUntil(&last, 10);
        board_printf_raw("  fixed #%d: now=%u last=%u slept=%d\n", i, (unsigned)xTaskGetTickCount(),
                         (unsigned)last, (int)r);
    }
    board_exit(0);
}
int main(void)
{
    xTaskCreate(task, "t", 512, NULL, 2, NULL);
    vTaskStartScheduler();
    return 1;
}
```

- `xTaskPeriodicDelay`도 미래 기준점에서 깨진다. `xTickCount - last`가 부호 없는 뺄셈으로 거대한 수가 되어 "주기가 엄청나게 많이 지났다"로 계산된다.

### 5.6 어느 것을 쓰나

| 상황 | 쓸 것 | 이유 |
|---|---|---|
| "적어도 n ms 쉬어라" (재시도 대기, 디바운스) | `vTaskDelay(pdMS_TO_TICKS(ms) + 1)` | 주기가 아니라 최소 간격이 목적. +1로 (n−1, n] 문제를 막는다 |
| 고정 주기, 모든 주기가 필요 (적분, 로깅, 오디오 블록) | `xTaskDelayUntil` + 반환값 검사 | catch-up. `pdFALSE`가 연속되면 과부하 경보 |
| 고정 주기, 최신 값만 중요 (제어 루프, 텔레메트리) | `xTaskPeriodicDelay` + 반환값 검사 | skip. 반환값 − 1 = 버린 주기 수 |
| 1 kHz 이상, 지터 수 µs 이하 | HW 타이머 ISR → 태스크 통지 | tick 격자와 스케줄링 지터를 피한다 (E5, E7) |
| 여러 태스크가 같은 주기 | 기준점(phase)을 엇갈리게 | 예제 3: 같은 tick에 몰리면 tick ISR이 그만큼 길어진다 |

## 6. 스케줄러가 멈춘 동안의 tick — `xPendedTicks`

### 6.1 직관

`vTaskSuspendAll()`은 인터럽트는 그대로 두고 **스케줄러만** 멈춘다(C7: 크리티컬 섹션 두 종류). 그 동안에도 SysTick은 울린다. 하지만 tick이 태스크를 깨워 ready list를 건드리면 멈춘 스케줄러와 충돌한다. 그래서 `xTaskIncrementTick()`은 스케줄러가 멈췄으면 `xTickCount`도 올리지 않고 **`xPendedTicks`만 1 올린다**((10)). `xTaskResumeAll()`이 스케줄러를 다시 켜면서 쌓인 수만큼 `xTaskIncrementTick()`을 **연달아 호출**한다(`tasks.c` 4150줄 근처의 `do { … } while( xPendedCounts > 0 )`).

반대로 `taskENTER_CRITICAL()`(BASEPRI로 인터럽트 마스킹)은 SysTick 인터럽트 자체를 막는다. SysTick의 pending 비트는 하나뿐이라, 마스킹 동안 tick이 여러 번 와도 **풀릴 때 한 번만** 들어온다. 나머지는 **사라진다** — 커널 시계가 실제 시간보다 영구히 늦어진다.

### 6.2 예제 12 — 5 tick 멈춤: pended(보존) vs 마스킹(유실)

무엇을 확인하나: 낮은 우선순위 태스크 lo가 (a) `vTaskSuspendAll()` 상태로 5 ms, (b) `taskENTER_CRITICAL()` 상태로 5 ms 바쁘게 돈다. 높은 우선순위 hi는 `xTaskDelayUntil(&last, 2)`로 2 tick마다 깨며 시각을 찍는다. (b) 뒤에는 `xTaskCatchUpTicks(4)`로 잃어버린 tick을 보정한다.

```c
/* C5 ex6: 스케줄러를 5 tick 동안 멈추면(vTaskSuspendAll) tick은 xPendedTicks에 쌓였다가 한꺼번에 처리된다.
 * 같은 5 ms를 인터럽트 마스킹(taskENTER_CRITICAL)으로 막으면 tick 4개가 사라진다 -> xTaskCatchUpTicks */
#include "FreeRTOS.h"
#include "task.h"
#include "c5.h"
static uint32_t t0;
static void show(const char *s)
{ board_printf_raw("  %u us  tick=%u  %s\n", board_now_us() - t0, (unsigned)xTaskGetTickCount(), s); }
static void hi(void *p)                                   /* 2 tick마다 깨는 높은 우선순위 태스크 */
{
    (void)p;
    TickType_t last = xTaskGetTickCount();
    for (int i = 0; i < 12; i++) { xTaskDelayUntil(&last, 2); show("hi woke"); }
    vTaskDelete(NULL);
}
static void lo(void *p)
{
    (void)p;
    vTaskDelay(1);                                        /* tick 1 경계 직후 */
    spin_us(200);
    show("lo: vTaskSuspendAll + spin 5000 us");
    vTaskSuspendAll();
    spin_us(5000);
    show("lo: still suspended (tick frozen)");
    BaseType_t y = xTaskResumeAll();
    show(y ? "lo: xTaskResumeAll -> yielded" : "lo: xTaskResumeAll -> no yield");
    vTaskDelay(2);
    spin_us(200);
    show("lo: taskENTER_CRITICAL + spin 5000 us");
    taskENTER_CRITICAL();
    spin_us(5000);
    taskEXIT_CRITICAL();
    show("lo: after critical (4 ticks lost)");
    xTaskCatchUpTicks(4);
    show("lo: after xTaskCatchUpTicks(4)");
    vTaskDelay(6);
    board_exit(0);
}
int main(void)
{
    xTaskCreate(hi, "hi", 256, NULL, 4, NULL);
    xTaskCreate(lo, "lo", 256, NULL, 2, NULL);
    t0 = board_now_us();                                  /* 대략 tick 0 */
    vTaskStartScheduler();
    return 1;
}
```

- 교훈: **tick 한 주기보다 긴 크리티컬 섹션은 시간을 잃는다.** 플래시 지우기처럼 길게 인터럽트를 막아야 하면 전후로 하드웨어 시계(RTC·자유 실행 타이머)를 읽어 `xTaskCatchUpTicks()`로 보정한다. 대부분은 크리티컬 섹션 대신 `vTaskSuspendAll()`이나 뮤텍스로 바꾸는 것이 답이다(C7, D2).

## 7. 블로킹 호출의 타임아웃 — `xTicksToWait`와 다단계 타임아웃

### 7.1 `xTicksToWait`의 세 가지 값

| 값 | 의미 | 커널 안에서 |
|---|---|---|
| `0` | 기다리지 않음(폴링) | 바로 `errQUEUE_EMPTY` 등 반환 |
| `1` ~ `portMAX_DELAY − 1` | 최대 n tick | event list(무엇을 기다리나) + **delayed list**(언제 포기하나) 둘 다에 건다 |
| `portMAX_DELAY` (+ `INCLUDE_vTaskSuspend == 1`) | 무한 | event list + **suspended list**. 시간으로는 깨지 않는다 |

`portMAX_DELAY`가 suspended list로 가는 분기가 `prvAddCurrentTaskToDelayedList()`의 첫 줄이다.

```c
#if ( INCLUDE_vTaskSuspend == 1 )
    if( ( xTicksToWait == portMAX_DELAY ) && ( xCanBlockIndefinitely != pdFALSE ) )
    {
        /* 시간 이벤트로 깨지 않도록 delayed list가 아니라 suspended list에 넣는다 */
        listINSERT_END( &xSuspendedTaskList, &( pxCurrentTCB->xStateListItem ) );
    }
    else
#endif
    { /* §4.2의 delayed / overflow delayed 삽입 */ }
```

큐·세마포어 API는 `vTaskPlaceOnEventList()` → `prvAddCurrentTaskToDelayedList( xTicksToWait, pdTRUE )`로 `pdTRUE`를 넘기고, `vTaskDelay()`는 `pdFALSE`를 넘긴다. 예제 8의 B(무한)와 C(65535 tick 뒤 깸)의 차이가 이 인자 하나다. 이렇게 suspended list에 들어간 태스크도 `eTaskGetState()`는 event list를 확인해 `eBlocked`로 보고한다(`vTaskSuspend()`로 멈춘 진짜 suspended와 구분).

### 7.2 다단계 타임아웃이 왜 필요한가

드라이버는 보통 한 번의 블로킹으로 끝나지 않는다. "UART에서 8바이트를 받되 전체 20 ms 안에", "SPI 플래시 busy 비트가 풀릴 때까지 폴링하되 전체 50 ms 안에". 바이트마다 `xQueueReceive(q, &b, pdMS_TO_TICKS(20))`을 부르면 **매번 20 ms를 새로 준다** — 바이트가 19 ms마다 하나씩 오면 8바이트에 152 ms가 걸려도 타임아웃이 안 난다. 남은 시간을 직접 `now - start`로 계산하면 wrap·`portMAX_DELAY`·중간 선점을 다 신경 써야 한다.

FreeRTOS는 이 계산을 API로 준다.

```c
void vTaskSetTimeOutState( TimeOut_t * const pxTimeOut )      /* tasks.c:5665 */
{
    taskENTER_CRITICAL();
    pxTimeOut->xOverflowCount = xNumOfOverflows;               /* 지금 wrap 횟수 */
    pxTimeOut->xTimeOnEntering = xTickCount;                   /* 지금 tick */
    taskEXIT_CRITICAL();
}

BaseType_t xTaskCheckForTimeOut( TimeOut_t * const pxTimeOut,  /* tasks.c:5693 (줄임) */
                                 TickType_t * const pxTicksToWait )
{
    const TickType_t xConstTickCount = xTickCount;
    const TickType_t xElapsedTime = xConstTickCount - pxTimeOut->xTimeOnEntering;
    if( pxCurrentTCB->ucDelayAborted != pdFALSE )              /* xTaskAbortDelay로 깨움 = 타임아웃 취급 */
    { pxCurrentTCB->ucDelayAborted = pdFALSE; xReturn = pdTRUE; }
    else if( *pxTicksToWait == portMAX_DELAY ) xReturn = pdFALSE;   /* 무한은 절대 안 끝남 */
    else if( ( xNumOfOverflows != pxTimeOut->xOverflowCount ) &&
             ( xConstTickCount >= pxTimeOut->xTimeOnEntering ) )
    { xReturn = pdTRUE; *pxTicksToWait = 0; }                  /* 한 바퀴 이상 지남 */
    else if( xElapsedTime < *pxTicksToWait )
    {
        *pxTicksToWait -= xElapsedTime;                        /* 남은 시간으로 줄이고 */
        vTaskInternalSetTimeOutState( pxTimeOut );             /* 기준점을 지금으로 다시 */
        xReturn = pdFALSE;
    }
    else { *pxTicksToWait = 0; xReturn = pdTRUE; }             /* 다 썼다 */
    return xReturn;
}
```

`xTaskCheckForTimeOut()`은 **남은 시간(`*pxTicksToWait`)을 갱신하고 기준점도 지금으로 옮긴다**. 그래서 루프에서 반복해 불러도 경과 시간이 두 번 빠지지 않는다. `xNumOfOverflows`를 같이 저장해 wrap을 한 바퀴 넘게 지난 경우까지 처리한다.

### 7.3 예제 13 — "8바이트를 20 ms 안에": 버그 버전 vs `xTaskCheckForTimeOut` 버전

무엇을 확인하나: 6 ms마다 1바이트가 오는 느린 센서(시뮬레이션 태스크)에서 8바이트를 "20 ms 예산"으로 읽는다. 측정 도중 tick이 wrap하도록 `configINITIAL_TICK_COUNT=0xFFFFFFF8`로 빌드한다.

```c
/* C5 ex10: "8바이트를 20 ms 안에" — 바이트마다 타임아웃을 새로 주는 버그 vs vTaskSetTimeOutState/xTaskCheckForTimeOut.
 * configINITIAL_TICK_COUNT=0xFFFFFFF8 로 빌드: 측정 도중 tick이 wrap해도 맞는지 같이 본다 */
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "c5.h"
static QueueHandle_t rxq;
static void uart_rx_sim(void *p)                     /* 6 ms마다 1바이트 도착 (느린 센서) */
{
    (void)p;
    TickType_t l = xTaskGetTickCount();
    for (uint8_t c = 0;; c++) { xTaskDelayUntil(&l, 6); xQueueSend(rxq, &c, 0); }
}
static int read_bad(uint8_t *buf, int n, TickType_t total)    /* 바이트마다 total을 다시 준다 */
{
    int got = 0;
    while (got < n && xQueueReceive(rxq, &buf[got], total) == pdTRUE) got++;
    return got;
}
static int read_good(uint8_t *buf, int n, TickType_t total)   /* 남은 시간만 기다린다 */
{
    TimeOut_t to; TickType_t left = total; int got = 0;
    vTaskSetTimeOutState(&to);
    while (got < n) {
        if (xTaskCheckForTimeOut(&to, &left) != pdFALSE) break;  /* left가 0이 되면 끝 */
        if (xQueueReceive(rxq, &buf[got], left) == pdTRUE) got++;
    }
    return got;
}
static void drv(void *p)
{
    (void)p;
    uint8_t buf[8];
    for (int v = 0; v < 2; v++) {
        xQueueReset(rxq);
        TickType_t a = xTaskGetTickCount();
        int got = v ? read_good(buf, 8, pdMS_TO_TICKS(20)) : read_bad(buf, 8, pdMS_TO_TICKS(20));
        TickType_t b = xTaskGetTickCount();
        board_printf_raw("%s: got %d/8 bytes in %u ms (budget 20 ms)  tick 0x%x -> 0x%x\n",
                         v ? "read_good" : "read_bad ", got, (unsigned)(b - a), (unsigned)a, (unsigned)b);
    }
    board_exit(0);
}
int main(void)
{
    rxq = xQueueCreate(16, 1);
    xTaskCreate(uart_rx_sim, "rx", 256, NULL, 3, NULL);
    xTaskCreate(drv, "drv", 512, NULL, 2, NULL);
    vTaskStartScheduler();
    return 1;
}
```

### 7.4 커널도 같은 패턴을 쓴다

`xQueueReceive()`(`queue.c:1509`)의 블로킹 루프가 정확히 이 구조다. 처음 블록할 때 `vTaskInternalSetTimeOutState( &xTimeOut )`(1590줄), 깨어나서 다시 루프를 돌 때마다 `xTaskCheckForTimeOut( &xTimeOut, &xTicksToWait )`(1609줄)로 남은 시간을 줄이고, 아직 남았고 큐가 비었으면 `vTaskPlaceOnEventList( …, xTicksToWait )`로 **남은 시간만큼** 다시 잔다. 그래서 "다른 태스크가 데이터를 먼저 가져가서 헛깨어남(spurious wakeup)"이 생겨도 전체 타임아웃은 지켜진다. `queue.c`에서 같은 쌍이 1102/1121(송신), 1760/1779, 1970/1989에도 있다.

### 7.5 `xTaskAbortDelay()` — 바깥에서 대기를 끊기

`xTaskAbortDelay(task)`(`tasks.c:4737`, `INCLUDE_xTaskAbortDelay`)는 delayed 또는 blocked 상태의 태스크를 즉시 ready로 옮기고 `ucDelayAborted`를 세운다. 그 태스크의 `xTaskCheckForTimeOut()`은 이를 **타임아웃으로** 보고한다(위 코드 첫 분기). 예를 들어 드론의 링크 태스크가 `xQueueReceive(…, 500 ms)`로 기다리는 동안 failsafe 관리자가 "지금 바로 정리하라"고 깨울 때 쓴다. 예제 5에서도 측정 태스크를 깨우는 데 썼다.

## 8. Zephyr의 시간 관리 — 64비트 tick, delta list, "+1 tick"

### 8.1 `k_timeout_t` — 정수가 아니라 구조체

Zephyr의 블로킹 API는 tick 숫자가 아니라 `k_timeout_t`를 받는다(`include/zephyr/sys/clock.h:67`).

```c
#ifdef CONFIG_TIMEOUT_64BIT          /* 기본 y (kernel/Kconfig:873) */
typedef int64_t k_ticks_t;
#else
typedef uint32_t k_ticks_t;
#endif
typedef struct {
	k_ticks_t ticks;
} k_timeout_t;
```

| 만드는 매크로 | 뜻 | 변환 |
|---|---|---|
| `K_NO_WAIT` | 기다리지 않음 | ticks = 0 |
| `K_FOREVER` | 무한 | ticks = `K_TICKS_FOREVER` = −1 |
| `K_TICKS(t)` | t tick (상대) | 그대로 |
| `K_MSEC(ms)` · `K_USEC(us)` · `K_NSEC` · `K_SECONDS` | 시간 (상대) | `k_ms_to_ticks_ceil64` 등 — **올림** (`clock.h:129`) |
| `K_CYC(c)` | HW 사이클 (상대) | `k_cyc_to_ticks_ceil64` — 올림 |
| `K_TIMEOUT_ABS_TICKS(t)` · `_MS` · `_US` · `_CYC` … | 부팅 후 절대 시각 | `Z_TICK_ABS(t)` = −2 − t, **음수 공간에 인코딩** (`clock.h:150`) |

절대 타임아웃은 ticks 값의 **음수 영역**에 담긴다. `Z_TICK_ABS(t) = K_TICKS_FOREVER - 1 - t`라서 0 이상의 절대 tick t가 −2, −3, …으로 바뀌고, 같은 매크로를 한 번 더 적용하면 원래 값이 나온다(소스 주석: "Clever, huh?"). 그래서 `Z_IS_TIMEOUT_RELATIVE(timeout)`은 `ticks >= 0` 검사 하나로 끝난다(`clock.h:161`). 이 인코딩은 64비트에서만 의미가 있어서, `CONFIG_TIMEOUT_64BIT=n`이면 모든 타임아웃이 상대로 취급되고 `K_TIMEOUT_ABS_*`를 쓸 수 없다(Kconfig 도움말: "This feature also gates the availability of absolute timeout values").

`k_sem_take(&s, 100)`처럼 정수를 넘기면 **컴파일 에러**다(A5 §3). 단위 실수를 타입이 막아 준다 — FreeRTOS의 `TickType_t`가 못 하는 일이다.

### 8.2 `kernel/timeout.c` — 한 리스트, 차이(delta)만 저장

Zephyr의 모든 시간 대기(스레드 sleep, 블로킹 API 타임아웃, `k_timer`, `k_work_delayable`)는 `struct _timeout` 하나로 표현되고, **하나의 정렬 리스트 `timeout_list`**에 들어간다(`timeout.c:18`). 각 노드는 절대 시각이 아니라 **앞 노드와의 차이 `dticks`**만 저장한다 — delta list. 그래서 시간이 흘러도 머리 노드의 `dticks` 하나만 줄이면 되고, 64비트 절대 시각 비교도 wrap도 필요 없다. 커널 시계 `curr_tick`은 64비트(`static uint64_t curr_tick`, `timeout.c:16`)라 현실적으로 넘치지 않는다.

`z_add_timeout()`(`timeout.c:88`)의 핵심 — 여기에 그 유명한 **+1**이 있다.

```c
if (Z_IS_TIMEOUT_RELATIVE(timeout)) {
	ticks_elapsed = elapsed();                            /* 마지막 announce 이후 지난 tick */
	has_elapsed = true;
	to->dticks = timeout.ticks + 1 + ticks_elapsed;       /* timeout.c:111 — +1 tick */
	ticks = curr_tick + to->dticks;
} else {
	k_ticks_t dticks = Z_TICK_ABS(timeout.ticks) - curr_tick;
	to->dticks = max(1, dticks);                          /* 절대: +1 없음, 최소 1 */
	ticks = timeout.ticks;
}
for (t = first(); t != NULL; t = next(t)) {               /* 정렬 삽입: delta를 빼 가며 걷는다 */
	if (t->dticks > to->dticks) {
		t->dticks -= to->dticks;                          /* 뒤 노드의 delta를 줄이고 */
		sys_dlist_insert(&t->node, &to->node);            /* 그 앞에 끼운다 */
		break;
	}
	to->dticks -= t->dticks;
}
if (t == NULL) sys_dlist_append(&timeout_list, &to->node);
if (to == first() && announce_remaining == 0)
	sys_clock_set_timeout(next_timeout(ticks_elapsed), false);   /* 새 머리면 HW 타이머 재설정 */
```

**+1의 이유**: tickless 커널에서 "지금"은 tick 경계 사이 어딘가다. `elapsed()`는 마지막 announce 이후 **완전히 지난** tick 수만 센다. 지금 tick의 남은 몫을 모르므로, 요청한 n tick을 **최소한** 보장하려면 경계 하나를 더 기다려야 한다. 결과적으로 상대 타임아웃의 실제 대기는 **(n, n+1] tick**이고(예제 9: 1030~2028 µs), FreeRTOS의 **(n−1, n]**과 정확히 한 tick 어긋난다. 절대 타임아웃에는 +1이 없다 — 목표 시각이 tick 경계로 이미 정해져 있기 때문이다.

tick(또는 tickless에서 만료)이 오면 드라이버가 `sys_clock_announce(dticks)`를 부르고, `sys_clock_announce_locked()`(`timeout.c:223`)가 만료 노드를 처리한다.

```c
announce_remaining = ticks;
for (t = first(); (t != NULL) && (t->dticks <= announce_remaining); t = first()) {
	int dt = t->dticks;
	curr_tick += dt;                         /* 그 노드의 만료 시각으로 시계를 옮기고 */
	t->dticks = 0;
	remove_timeout(t);
	t->dticks = TIMEOUT_DTICKS_ANNOUNCING;
	k_spin_unlock(&timeout_lock, key);
	t->fn(t);                                /* 콜백을 ISR 문맥에서 실행 (z_thread_timeout, 타이머 만료 등) */
	key = k_spin_lock(&timeout_lock);
	announce_remaining -= dt;
}
if (t != NULL) t->dticks -= announce_remaining;   /* 남은 머리의 delta를 줄이고 */
curr_tick += announce_remaining;
announce_remaining = 0;
sys_clock_set_timeout(next_timeout(0), false);    /* 다음 만료에 HW 타이머를 맞춘다 */
k_spin_unlock(&timeout_lock, key);
z_time_slice();                                   /* CONFIG_TIMESLICING */
```

콜백 중에 새 타임아웃을 추가하면 `elapsed()`가 0을 돌려준다(`announce_remaining != 0`이므로, `timeout.c:70`). 즉 **콜백 안에서 건 상대 타임아웃은 "지금 울린 타임아웃의 원래 시각" 기준**이 된다 — `k_timer`의 주기가 콜백 실행 지연만큼 밀리지 않는 이유다.

### 8.3 예제 14 — delta list를 그대로 옮긴 작은 모델 (VM 호스트)

무엇을 확인하나: `z_add_timeout()`의 삽입 루프와 `sys_clock_announce_locked()`의 만료 루프만 남긴 C 모델로, 타임아웃 넷(30, 10, 20, 20 tick)을 넣고 12 tick을 알린 뒤, 하나를 다시 넣고 25 tick을 알린다. 락과 콜백 인자는 뺐다. 커널 자료구조는 `static`이라 앱에서 직접 볼 수 없어서, 동작 원리를 눈으로 보려고 호스트에서 돌렸다.

```c
/* C5 ex12 (VM 호스트 gcc): Zephyr kernel/timeout.c 의 delta list 를 그대로 옮긴 작은 모델.
 * z_add_timeout()의 삽입 루프와 sys_clock_announce_locked()의 만료 루프만 남겼다 (락·콜백 인자 생략). */
#include <stdio.h>
#include <stdint.h>
struct to { struct to *next; int64_t dticks; const char *name; };
static struct to *head; static uint64_t curr_tick; static int announce_remaining;
static void dump(const char *why)
{
    printf("%-26s curr_tick=%2llu  list:", why, (unsigned long long)curr_tick);
    int64_t abs = curr_tick;
    for (struct to *t = head; t; t = t->next) { abs += t->dticks; printf(" %s(+%lld @%lld)", t->name, (long long)t->dticks, (long long)abs); }
    printf("\n");
}
static void add(struct to *n, int64_t ticks, int64_t elapsed)  /* relative timeout */
{
    n->dticks = ticks + 1 + elapsed;                 /* timeout.c:111 — the +1 tick */
    struct to **pp = &head;
    for (; *pp; pp = &(*pp)->next) {
        if ((*pp)->dticks > n->dticks) { (*pp)->dticks -= n->dticks; break; }
        n->dticks -= (*pp)->dticks;
    }
    n->next = *pp; *pp = n;
}
static void announce(int ticks)
{
    announce_remaining = ticks;
    while (head && head->dticks <= announce_remaining) {
        struct to *t = head; int dt = (int)t->dticks;
        curr_tick += dt; head = t->next;
        if (head) head->dticks += 0;                 /* remove_timeout: next->dticks += t->dticks(=0) */
        printf("    fire %s at tick %llu\n", t->name, (unsigned long long)curr_tick);
        announce_remaining -= dt;
    }
    if (head) head->dticks -= announce_remaining;
    curr_tick += announce_remaining; announce_remaining = 0;
}
int main(void)
{
    static struct to a = { .name = "A" }, b = { .name = "B" }, c = { .name = "C" }, d = { .name = "D" };
    add(&a, 30, 0); dump("add A: K_TICKS(30)");
    add(&b, 10, 0); dump("add B: K_TICKS(10)");
    add(&c, 20, 0); dump("add C: K_TICKS(20)");
    add(&d, 20, 0); dump("add D: K_TICKS(20) (tie)");
    announce(12);   dump("announce(12)");
    add(&b, 5, 0);  dump("re-add B: K_TICKS(5)");
    announce(25);   dump("announce(25)");
    return 0;
}
```

출력에서 볼 것:

- `K_TICKS(30)`이 `+31`로 들어갔다 — +1 규칙(`timeout.c:111`). B·C·D도 모두 요청 + 1 시각(11, 21, 21)에 만료된다.
- 같은 시각(21)인 C와 D는 `+10`, `+0`으로 이어진다. `t->dticks > to->dticks`(엄격히 큼)일 때만 앞에 끼우므로 같은 값은 **먼저 넣은 것 뒤**에 붙는다 — FIFO, FreeRTOS `vListInsert`의 `<=`와 같은 규칙이다.
- `announce(12)`: 머리 B(11)만 만료되고, curr_tick은 12, 새 머리 C의 delta는 10 → 9(= 21 − 12)로 **하나만** 바뀌었다. 나머지 노드는 손대지 않았다.
- 다시 넣은 B(5 tick, 절대 18)는 C의 delta를 9 → 3으로 줄이며 앞에 끼었다. 삽입은 FreeRTOS와 마찬가지로 O(N) 걷기다.
- `announce(25)` 한 번에 B·C·D·A가 순서대로 만료되고 curr_tick = 37이 됐다. tickless에서 오래 잔 뒤 한꺼번에 몇 tick을 알리는 경우가 이것이다.

### 8.4 예제 15 — `CONFIG_SYS_CLOCK_TICKS_PER_SEC` = 100 / 1000 / 10000

무엇을 확인하나: 같은 Zephyr 앱을 tick rate만 바꿔 세 번 빌드한다(모두 기본 tickless). `K_MSEC`·`K_USEC`·`K_CYC`가 몇 tick이 되는지, `k_sleep(K_TICKS(1))`과 `k_sleep(K_MSEC(1))`의 실제 분포(임의 위상 200회), 일 2 ms + `k_msleep(10)` 루프와 `K_TIMEOUT_ABS_TICKS` 루프의 100주기 시간, `k_uptime_get()` 한 칸의 크기를 본다.

```c
/* C5 ex9: Zephyr 시간 — k_timeout_t 변환, +1 tick 규칙, k_sleep(K_TICKS(1)) 분포, 절대 타임아웃 주기 */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>
#define CYC() (*(volatile uint32_t *)0x40028018u)          /* FPGAIO 25 MHz */
#define US(c) ((c) / 25u)
#define TICK_US (1000000u / CONFIG_SYS_CLOCK_TICKS_PER_SEC)
static uint32_t seed = 12345u;
static uint32_t rnd(uint32_t n) { seed = seed * 1103515245u + 12345u; return (seed >> 8) % n; }
static void spin_us(uint32_t us) { uint32_t t0 = CYC(); while (CYC() - t0 < us * 25u) { } }
static void dist(const char *name, k_timeout_t to)
{
	uint32_t mn = ~0u, mx = 0, sum = 0, n = 200;
	for (uint32_t i = 0; i < n; i++) {
		k_sleep(K_TICKS(1));                                /* tick 경계에 맞추고 */
		spin_us(rnd(TICK_US));                              /* tick 안 임의 위상 */
		uint32_t a = CYC();
		k_sleep(to);
		uint32_t d = US(CYC() - a);
		mn = MIN(mn, d); mx = MAX(mx, d); sum += d;
	}
	printk("  %-16s min=%u avg=%u max=%u us\n", name, mn, sum / n, mx);
}
static void period(const char *name, int absolute)          /* 10 ms 주기, 일 2 ms, 100주기 */
{
	int64_t t0 = k_uptime_ticks();
	uint32_t c0 = CYC();
	for (int k = 1; k <= 100; k++) {
		spin_us(2000);
		if (absolute) k_sleep(K_TIMEOUT_ABS_TICKS(t0 + k_ms_to_ticks_ceil64(10 * k)));
		else k_msleep(10);
	}
	printk("  %-16s 100 periods = %u us (ideal 1000000)\n", name, US(CYC() - c0));
}
int main(void)
{
	printk("tick=%u Hz tickless=%d sizeof(k_ticks_t)=%u\n", CONFIG_SYS_CLOCK_TICKS_PER_SEC,
	       IS_ENABLED(CONFIG_TICKLESS_KERNEL), (unsigned)sizeof(k_ticks_t));
	printk("  K_MSEC(1)=%u K_MSEC(3)=%u K_USEC(150)=%u K_CYC(1000)=%u ticks (ceil)\n",
	       (uint32_t)K_MSEC(1).ticks, (uint32_t)K_MSEC(3).ticks, (uint32_t)K_USEC(150).ticks,
	       (uint32_t)K_CYC(1000).ticks);
	dist("K_TICKS(1)", K_TICKS(1));
	dist("K_MSEC(1)", K_MSEC(1));
	period("k_msleep(10)", 0);
	period("ABS timeout", 1);
	int64_t u0 = k_uptime_get();                               /* k_uptime_get 한 칸 = 몇 cycle? */
	while (k_uptime_get() == u0) { }
	uint32_t a = CYC(); u0 = k_uptime_get();
	while (k_uptime_get() == u0) { }
	printk("  k_uptime_get step = %u us, k_cycle_get_32 rate = %u Hz\n", US(CYC() - a),
	       sys_clock_hw_cycles_per_sec());
	register uint32_t r0 __asm__("r0") = 0x18, r1 __asm__("r1") = 0x20026;
	__asm volatile("bkpt 0xab" : : "r"(r0), "r"(r1) : "memory");
	return 0;
}
```

출력에서 볼 것:

- `sizeof(k_ticks_t)=8` — `CONFIG_TIMEOUT_64BIT` 기본값 y. `tickless=1` — mps2/an385도 tickless가 기본이다(`TICKLESS_KERNEL`은 `default y if TICKLESS_CAPABLE`).
- **변환은 전부 올림**: 100 Hz에서 `K_MSEC(1)`·`K_MSEC(3)`·`K_USEC(150)`·`K_CYC(1000)`이 모두 1 tick(10 ms). 10 kHz에서 `K_USEC(150)` = 2 tick(200 µs), `K_CYC(1000)`(40 µs) = 1 tick.
- **`K_TICKS(1)`은 항상 1~2 tick**: 100 Hz 10.0~20.0 ms, 1 kHz 1.04~2.03 ms, 10 kHz 133~232 µs. 10 kHz에서 하한이 133 µs(= 100 + 약 33 µs)인 것은 tick이 짧아져서 잠들기·깨어나기 커널 경로(25 MHz에서 약 33 µs)가 보이기 시작한 것이다. tick을 더 올려도 이 바닥 아래로는 못 내려간다.
- **`k_msleep(10)` 루프는 tick rate에 따라 주기가 달라진다**: 100 Hz 20.0 ms, 1 kHz 13.0 ms, 10 kHz 12.1 ms. 계산하면 `dticks = 요청 + 1 + elapsed()`이므로 다음 깨어남 = 마지막 announce 시각 + (일하는 동안 완전히 지난 tick) + 요청 + 1. 1 kHz: 2 + 10 + 1 = 13 ms, 10 kHz: 2 + 10 + 0.1 = 12.1 ms, 100 Hz: 2 ms 일은 한 tick도 못 채워 elapsed = 0 → 0 + 1 + 1 = 2 tick = 20 ms. **"10 ms 주기"가 tick rate에 따라 12.1 / 13 / 20 ms가 된다.**

### 8.5 시간 읽기 함수 고르기

| 함수 | 단위 · 폭 | 해상도 | wrap | 쓰는 곳 |
|---|---|---|---|---|
| `k_uptime_get()` | ms, `int64_t` | max(1 tick, 1 ms) | 사실상 없음 | 로그, 타임아웃 계산, 사람이 읽는 시간 |
| `k_uptime_get_32()` | ms, `uint32_t` | 같음 | 49.7일 | 짧은 경과 시간(부호 없는 뺄셈으로) |
| `k_uptime_ticks()` | tick, `int64_t` | 1 tick | 사실상 없음 | 절대 타임아웃 기준점(`K_TIMEOUT_ABS_TICKS(t0 + …)`) |
| `k_cycle_get_32()` | HW 사이클, `uint32_t` | 1 사이클(여기 40 ns) | 25 MHz에서 171.8초 | 짧은 구간 측정, 센서 타임스탬프 |
| `sys_timepoint_calc()` / `sys_timepoint_timeout()` | `k_timepoint_t` | 1 tick | 없음 | 다단계 타임아웃 — FreeRTOS `TimeOut_t`에 해당 |

마지막 줄이 §7의 Zephyr 판이다. `sys_timepoint_calc(timeout)`(`timeout.c:317`)이 "만료 시각"을 64비트 tick으로 한 번 계산해 두고, 루프마다 `sys_timepoint_timeout(tp)`(`timeout.c:338`)로 남은 시간을 `k_timeout_t`로 돌려받아 블로킹 API에 넘긴다. 64비트라 wrap 처리가 필요 없다. 다만 상대 타임아웃을 만들 때 `max(1, dt)`만 더하고(+1이 아님), 남은 시간을 `K_TICKS(remaining)` 상대 타임아웃으로 넘기면 거기서 다시 +1이 붙는다는 점은 기억한다.

### 8.6 `k_sleep()`이 돌려주는 것

`z_impl_k_sleep()`(`kernel/sched.c:1218`)은 남은 시간을 ms로 돌려준다. 정상 만료면 0이고, 다른 스레드가 `k_wakeup()`으로 일찍 깨우면 남은 ms다. 내부의 `z_tick_sleep()`(`sched.c:1172`)은 `z_add_thread_timeout()` → `z_add_timeout(&thread->base.timeout, z_thread_timeout, ticks)`(`kernel/include/timeout_q.h:82`)로 위의 delta list에 들어간다. `K_NO_WAIT`면 잠들지 않고 `k_yield()`만 한다 — FreeRTOS `vTaskDelay(0)`과 같다.

### 8.7 tickless에서 `TICKS_PER_SEC`의 뜻

`kernel/Kconfig:826`의 기본값은 `default 100 if QEMU_TARGET || SOC_POSIX`, `default 10000 if TICKLESS_KERNEL`, 그 밖 100이다. 도움말이 분명히 말한다: tickless에서 이 값은 "**최소 시간 해상도**이지 인터럽트 빈도가 아니다". 예제 15의 10 kHz 빌드도 tick 인터럽트를 초당 1만 번 받지 않는다 — 다음 타임아웃 시각에만 SysTick을 맞춘다(그래서 A7에서 tickless + slicing off의 tick 세금이 0%였다). tick을 올리는 비용이 인터럽트 세금이 아니라 **64비트 나눗셈·변환 비용과 타이머 재프로그램 빈도**로 바뀐다. 자세한 동작은 C6.

이어지는 노트: C1(리스트·ready 비트맵의 자료구조), C2(PendSV 전환), C4(time slicing 정책), C6(tickless — `xNextTaskUnblockTime`·`sys_clock_set_timeout`을 하드웨어 compare로), C7(크리티컬 섹션 두 종류와 tick 유실), D6(소프트웨어 타이머·`k_timer` — 같은 시간 리스트 위의 콜백), E5·E7(HW 타이머로 tick보다 정밀한 주기).

## 10. 실무에서 다시 보기

### 10.1 드론 비행 제어기 — 무엇을 tick에 맡기고 무엇을 안 맡기나

예를 들어 STM32H7급 드론 FC라면: IMU는 8 kHz data-ready 인터럽트, rate loop는 그 인터럽트(또는 DMA 완료)가 태스크 통지로 깨우는 최고 우선순위 태스크, attitude loop 1 kHz도 같은 체인으로 나눠 돌린다. **tick은 이 체인에 끼지 않는다.** tick(1 kHz)은 텔레메트리 50 Hz, GNSS 파서 타임아웃, 배터리 감시 10 Hz, failsafe 타임아웃(RC 링크 끊김 500 ms) 같은 느슨한 일에 쓴다.

```c
/* 패턴 (실행 예제 아님): 50 Hz 텔레메트리 — 최신 상태만 보내면 되므로 skip 정책 */
static void telemetry_task(void *p)
{
    TickType_t last = xTaskGetTickCount();                 /* 지금 = 과거 쪽 기준점 */
    for (;;) {
        TickType_t n = xTaskPeriodicDelay(&last, pdMS_TO_TICKS(20));
        if (n > 1) stats.telemetry_skipped += n - 1;        /* 사고를 세어 둔다 */
        send_mavlink_attitude();
    }
}
```

failsafe 타임아웃은 "마지막 RC 패킷 시각"을 tick으로 저장하고 `(TickType_t)(now - last_rx) > pdMS_TO_TICKS(500)`로 비교한다(§4.4). RC 수신 태스크를 `xQueueReceive(q, &pkt, pdMS_TO_TICKS(100))`으로 기다리게 하고 타임아웃이 연속 5번이면 failsafe — 단, 수신 중간에 여러 단계(헤더 → 페이로드 → CRC)를 기다린다면 §7의 `xTaskCheckForTimeOut`으로 전체 예산을 지킨다.

### 10.2 로봇 관절 모터 컨트롤러 — CAN heartbeat

FOC 전류 루프 20 kHz는 PWM 타이머 ISR 안에서 돈다(tick과 무관). 상위 제어기에서 오는 CAN heartbeat는 10 ms 주기, 30 ms 동안 안 오면 토크를 끈다. tick 1 kHz, `xQueueReceive(can_rx, &f, pdMS_TO_TICKS(30))`가 타임아웃이면 즉시 안전 정지. 여기서 `pdMS_TO_TICKS`의 내림이 위험 쪽이다 — tick rate를 300 Hz로 바꾸면 30 ms가 9 tick = 30 ms라 괜찮지만 25 ms는 7 tick = 23.3 ms가 되어 정상 heartbeat 지터에도 오작동할 수 있다. 안전 타임아웃은 올림 매크로로 쓴다(§1.6).

### 10.3 센서 허브 MCU — 타임스탬프는 tick으로 찍지 않는다

Linux SoC 옆에서 IMU 샘플에 타임스탬프를 붙이는 센서 허브라면, 1 ms tick은 해상도가 모자라고 ISR·스케줄링 지연만큼 흔들린다. 타임스탬프는 **자유 실행 HW 타이머(32비트 µs 카운터 또는 입력 캡처)** 로 data-ready 핀 엣지에서 찍고, 32비트 wrap은 상위 비트를 소프트웨어로 확장해 64비트로 만든다. tick은 "샘플 배치를 언제 SPI로 올려 보낼지"(예: 5 ms마다)에만 쓴다. Zephyr라면 `k_cycle_get_32()`가 이 역할의 출발점이다(25 MHz에서 171.8초 wrap — 확장 필요).

### 10.4 SSD 컨트롤러 펌웨어 — 49.7일 테스트

엔터프라이즈 SSD는 몇 년씩 전원이 안 꺼진다. RTOS 기반 SSD 펌웨어라면 32비트 1 kHz tick은 49.7일마다 wrap한다. 검증 빌드에서 `configINITIAL_TICK_COUNT`를 wrap 10초 전으로 두고 전체 회귀 테스트(NVMe 명령 타임아웃, 백그라운드 GC 주기, 전원 손실 flush 타이머)를 돌리는 것이 가장 싼 보험이다. 예제 7의 "나쁜 비교가 0 ms로 끝난다"가 바로 현장에서 "명령이 즉시 타임아웃 처리돼 abort가 쏟아진다"로 나타나는 버그다.

## 12. 면접에서 이렇게 말한다

**Q.** What is the difference between `vTaskDelay()` and `vTaskDelayUntil()`? When would you use `xTaskPeriodicDelay()`?

**A.** `vTaskDelay`는 "지금부터 n tick" 상대 지연이라 일하는 시간만큼 주기가 늘고 drift가 쌓인다. `xTaskDelayUntil`은 "지난번 깨기로 한 시각 + T" 절대 지연이라 격자에 맞고, 늦으면 잠들지 않고 바로 돌아와 따라잡는다. V11.3.1의 `xTaskPeriodicDelay`는 놓친 주기를 건너뛰고 다음 격자에서 깨며 지나간 주기 수를 돌려준다. 측정에서 10 ms 주기 500번이 `vTaskDelay`로 5.79초, 나머지 둘은 5.00초였다. 모든 샘플이 필요하면 catch-up, 제어 루프처럼 최신 값만 의미 있으면 skip을 쓴다.

> `vTaskDelay` is relative — it sleeps n ticks from now, so the period becomes T plus the execution time and drift accumulates; in my measurement a 10 ms task with 1–3 ms of work took 5.79 s for 500 periods. `xTaskDelayUntil` is absolute — it wakes at the previous wake time plus T, so it stays on the grid, and if it's late it returns immediately to catch up. `xTaskPeriodicDelay`, added in 11.3.1, also stays on the grid but skips missed periods and returns how many periods elapsed. I use catch-up when every sample matters, like integration or logging, and skip for control loops where only the latest sample is useful — and in both cases I check the return value to count overruns.

**꼬리 질문**: "그럼 1 kHz 제어 루프도 `xTaskDelayUntil`로 돌리나?" → 아니다. tick 격자와 스케줄링 지터에 묶이므로 HW 타이머나 data-ready 인터럽트 → 태스크 통지로 만든다.

**Q.** How do you choose the tick rate?

**A.** tick은 잠들고 깨는 해상도와 타임아웃 해상도만 정한다. 그 해상도가 필요한 가장 짧은 지연을 정수 tick으로 표현할 수 있는 가장 낮은 rate, 보통 1 kHz를 고른다. ms와 1:1이라 `pdMS_TO_TICKS` 반올림 문제가 없고 코어 클럭으로 나누어떨어져야 한다. 세금은 rate × tick당 비용(25 MHz M3에서 1.47 µs → 1 kHz에 0.15%)이다. 그보다 정밀한 것은 tick을 올리지 않고 HW 타이머로 뺀다.

> The tick only sets the resolution of delays and timeouts, so I pick the lowest rate that represents the shortest timeout I need as an integer number of ticks — usually 1 kHz, because it maps one-to-one to milliseconds and divides the core clock evenly. The overhead is roughly rate times the per-tick cost; I measured about 1.5 µs per tick on a 25 MHz Cortex-M3, so 0.15% at 1 kHz. Anything that needs better than that — a fast control loop or precise timestamps — goes on a hardware timer rather than a faster tick. For battery devices I'd look at tickless idle first.

**꼬리 질문**: "1500 Hz는?" → 25 MHz를 못 나눠 SysTick LOAD가 잘리고 −40 ppm 오차가 생긴다. 그리고 ms 변환이 전부 어긋난다.

**Q.** What happens when the tick counter overflows?

**A.** FreeRTOS는 delayed list를 두 개 둔다. 잠들 때 깨울 값(`now + n`)이 넘치면 overflow list에 넣고, tick이 0으로 wrap하는 순간 두 리스트의 포인터를 바꾼다. 그래서 각 리스트 안의 비교는 항상 맞다. `xNumOfOverflows`도 올려서 타임아웃 계산이 한 바퀴 넘게 지난 경우를 판단한다. 커널은 안전하지만 앱의 `now > start + dur` 같은 비교는 깨진다 — 부호 없는 뺄셈으로 써야 한다. 테스트에서는 `configINITIAL_TICK_COUNT`를 wrap 직전으로 둔다.

> FreeRTOS keeps two delayed lists. When a task blocks and its wake time `now + n` overflows, it goes into the overflow list; when the tick count wraps to zero, the kernel just swaps the two list pointers and increments an overflow counter, so comparisons within each list are always correct. The kernel is safe, but application code that writes `now > start + timeout` breaks at the wrap — you have to use unsigned subtraction, `now - start >= timeout`. To catch those bugs I set `configINITIAL_TICK_COUNT` a few seconds before the wrap in test builds, like Linux does with `INITIAL_JIFFIES`; otherwise at 1 kHz with 32-bit ticks you only see it after 49.7 days in the field.

**Q.** If I call `vTaskDelay(1)`, how long does the task actually sleep?

**A.** 0~1 tick이다. "다음 tick 경계까지"라는 뜻이라 경계 직전에 부르면 거의 0이다. 1 kHz에서 1000번 재니 12~1005 µs에 고르게 퍼졌다. 일반적으로 `vTaskDelay(n)`은 (n−1, n] tick이다. 최소 n tick이 필요하면 n + 1을 준다. Zephyr는 상대 타임아웃에 1 tick을 더해서 (n, n+1]이다 — 같은 실험에서 1030~2028 µs였다.

> Anywhere between zero and one tick. It means "wake me at the next tick boundary", so if you call it just before the boundary you barely sleep at all — I measured a uniform spread from about 12 µs to 1 ms at a 1 kHz tick. In general `vTaskDelay(n)` gives you between n−1 and n ticks, so if I need at least n ticks I pass n+1. Zephyr does the opposite: it adds one tick to every relative timeout to guarantee the minimum, so `k_sleep(K_TICKS(1))` gives one to two ticks.

**Q.** How would you implement a timeout that spans several blocking calls in a driver?

**A.** 단계마다 같은 타임아웃을 주면 전체 시간이 단계 수만큼 늘어난다. `vTaskSetTimeOutState()`로 시작 시각을 저장하고, 매 블로킹 전에 `xTaskCheckForTimeOut(&to, &left)`를 불러 남은 시간을 줄이고 0이면 빠진다. 줄어든 `left`를 블로킹 호출에 넘긴다. wrap과 `portMAX_DELAY`, abort까지 처리해 준다. `xQueueReceive` 내부도 같은 패턴이다. 6 ms 간격 바이트 8개를 20 ms 예산으로 읽으니 순진한 버전은 48 ms, 이 패턴은 정확히 20 ms에 3바이트로 돌아왔다.

> Passing the same timeout to every step makes the total grow with the number of steps — in my test reading eight bytes that arrive every 6 ms with a "20 ms" timeout per byte took 48 ms. Instead I record the start with `vTaskSetTimeOutState`, and before each blocking call I call `xTaskCheckForTimeOut`, which subtracts the elapsed time from the remaining budget and tells me when it's exhausted; I pass the updated remaining ticks to the blocking call. It handles tick wrap, `portMAX_DELAY` and aborted delays, and it's exactly the pattern `xQueueReceive` uses internally. In Zephyr the equivalent is `sys_timepoint_calc` and `sys_timepoint_timeout`.

**Q.** What does the tick interrupt cost, and does it grow with the number of tasks?

**A.** 잠든 태스크 수와는 무관하다. 커널이 다음 깨울 시각(`xNextTaskUnblockTime`)을 캐시해 두고 tick마다 비교 한 번만 하기 때문이다. 측정에서 잠든 태스크 0~64개 모두 1.5 µs였다. 비용은 그 tick에 **깨우는 태스크 수**에 비례한다 — 하나당 약 1.6 µs. 대신 잠드는 쪽이 정렬 삽입으로 O(N)을 낸다(잠든 태스크 하나당 160 ns).

> Not with the number of blocked tasks. FreeRTOS caches the next unblock time, so a quiet tick is one comparison — I measured the same 1.5 µs with zero or 64 sleeping tasks on a 25 MHz M3. What scales is the number of tasks woken on that tick, about 1.6 µs each, so if many tasks share the same period and phase you get one expensive tick; I stagger their phases. The cost doesn't disappear, it moves to the blocking call: inserting into the sorted delayed list is linear in the number of sleepers, about 160 ns per task in my measurement.

**Q.** What happens to ticks while the scheduler is suspended, versus while interrupts are disabled?

**A.** `vTaskSuspendAll()` 동안 tick ISR은 계속 오지만 시계를 올리지 않고 `xPendedTicks`만 센다. `xTaskResumeAll()`이 그 수만큼 tick 처리를 재생하므로 시간은 보존된다. 인터럽트를 막으면 SysTick pending이 하나뿐이라 여러 tick이 와도 하나만 남고 나머지는 사라진다. 5 ms 막았더니 4 tick을 잃었고 `xTaskCatchUpTicks(4)`로 보정했다.

> With the scheduler suspended the tick interrupt still runs, but it only increments `xPendedTicks`; `xTaskResumeAll` replays those ticks, so no time is lost — tasks that should have woken just run late. With interrupts masked, SysTick has a single pending bit, so several missed ticks collapse into one and the rest are gone; in my test a 5 ms critical section at 1 kHz lost four ticks permanently until I called `xTaskCatchUpTicks`. So long critical sections don't just add latency, they make the kernel clock drift.

**Q.** How does Zephyr's timeout handling differ from FreeRTOS?

**A.** Zephyr는 64비트 `curr_tick`이라 wrap 걱정이 없고, 모든 시간 대기를 하나의 delta list에 앞 노드와의 차이로 저장한다. 타임아웃은 타입(`k_timeout_t`)이라 단위 실수가 컴파일 에러가 되고, ms 변환은 올림이다. 상대 타임아웃에 1 tick을 더해 최소 시간을 보장한다(`timeout.c:111`). 기본이 tickless라 tick rate는 해상도일 뿐 인터럽트 빈도가 아니다. 그래서 FreeRTOS 코드를 옮길 때 상대 지연 주기 루프가 1 tick씩 늘어난다 — 절대 타임아웃이나 `k_timer`로 바꾼다.

> Zephyr keeps a 64-bit tick count, so there is no wrap handling, and every timed wait — sleeps, API timeouts, timers — sits in one delta list where each node stores only the difference from the previous one. Timeouts are a struct, `k_timeout_t`, so passing a raw number is a compile error, and millisecond conversion rounds up. Relative timeouts get one extra tick to guarantee the minimum, which shifts periodic loops: a `k_msleep(10)` loop with 2 ms of work ran at 20 ms per iteration at the default 100 Hz on QEMU. So for periodic work I use absolute timeouts or a periodic `k_timer`. And because the kernel is tickless by default, the tick rate is the time resolution, not the interrupt rate.

## 13. 직접 해보기

1. **개념**: tick rate 250 Hz에서 `pdMS_TO_TICKS(10)`은 몇 tick이고 실제로 몇 ms인가? `vTaskDelay(pdMS_TO_TICKS(10))`을 tick 안의 임의 시점에서 부르면 실제 대기는 어느 범위인가? 정답/힌트: 10 × 250 / 1000 = 2.5 → 내림 2 tick = 8 ms. `vTaskDelay(2)`는 (1, 2] tick이므로 4~8 ms.
2. **코드**: 예제 7(`ex4_wrap.c`)에 `xTaskPeriodicDelay(&last, 7)` 태스크를 하나 더 넣고 wrap을 지나도 반환값이 1로 유지되는지 확인하라. 그 다음 `last`를 미래(`now + 3`)로 초기화하면 반환값이 무엇이 되는지 예측하고 돌려 보라. 정답/힌트: wrap을 지나도 `xTickCount - last`가 부호 없는 뺄셈이라 1이 유지된다. 미래 기준점이면 뺄셈 결과가 2^32 근처라 반환값이 거대한 수(약 2^32 / 7)가 된다.
3. **측정**: 예제 3을 `configUSE_TIME_SLICING=0`과 같은 우선순위 바쁜 태스크 2개 조건으로 다시 돌려, time slicing 전환이 있는 tick과 없는 tick의 핸들러 시간을 비교하라. PendSV 비용은 핸들러 밖에 있다는 점을 고려해 바쁜 카운터 방식(예제 4)으로도 재 보라. 정답/힌트: 핸들러 안 시간은 거의 같고(전환 요청 플래그만 세움), 바쁜 카운터 손실은 tick마다 PendSV 전환만큼 늘어난다.
4. **코드**: §7의 `read_good`을 "SPI 플래시 busy 비트 폴링" 버전으로 바꿔라: 1 tick씩 `vTaskDelay(1)`하며 상태 레지스터를 읽되 전체 50 ms 예산을 `xTaskCheckForTimeOut`으로 지킨다. busy가 30 ms 뒤 풀리는 경우와 80 ms 뒤 풀리는 경우를 시뮬레이션하라. 정답/힌트: 루프 맨 앞에서 `xTaskCheckForTimeOut`, 그 뒤 상태 확인, 그 뒤 `vTaskDelay(1)`. 30 ms면 성공, 80 ms면 50 ms 근처(+1 tick 이내)에서 타임아웃.
5. **측정**: 예제 15를 `-DCONFIG_TICKLESS_KERNEL=n`으로 다시 빌드해 `k_msleep(10)` 루프 주기가 tickless 때와 같은지 확인하라. 같다면 왜인가? 정답/힌트: +1 규칙은 `z_add_timeout()`에 있으므로 주기 tick에서도 그대로다. 주기 tick 모드에서는 `elapsed()`가 0(`sys_clock_elapsed()`가 0을 돌려줌)이라 계산이 조금 달라질 수 있으니 실제 숫자를 보고 설명하라.
6. **설계**: 32비트 1 kHz tick의 FreeRTOS 제품에서 "부팅 후 경과 시간"을 몇 년 동안 ms로 정확히 제공해야 한다. tick hook 없이, `xTaskGetTickCount()`만으로 64비트 업타임을 만드는 함수를 설계하라(호출 간격이 49.7일보다 짧다는 가정을 명시). 정답/힌트: 마지막으로 읽은 32비트 값과 상위 32비트를 static으로 들고, 새 값이 이전보다 작으면 상위를 1 올린다. 여러 태스크가 부르면 크리티컬 섹션으로 감싼다. 호출 간격이 한 바퀴를 넘으면 wrap을 놓친다 — 그래서 최소 한 번은 주기적으로 부르는 태스크를 둔다.
7. **측정**: 예제 3에서 K = 16개 waker의 기준점을 `g_base + i`(i = 0..15)로 엇갈리게 바꾸고, 최악 tick 핸들러 시간이 얼마로 줄어드는지 재라. 정답/힌트: 각 tick에 하나씩만 깨므로 최악이 약 3.9 µs(K = 1 수준)로 내려가야 한다.

## 14. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| tick | 커널 시계의 한 칸 | 주기 타이머 인터럽트 한 번 = 커널 시간 1 단위 |
| tick rate | 1초당 tick 수 | FreeRTOS `configTICK_RATE_HZ`, Zephyr `CONFIG_SYS_CLOCK_TICKS_PER_SEC` |
| `xTickCount` | FreeRTOS 커널 시계 | `TickType_t`, 스케줄러 시작부터 센 tick 수 |
| `TickType_t` | tick 값의 타입 | 16/32/64비트 — wrap 주기를 정한다 |
| delayed list | 시간 대기 중인 태스크 리스트 | 깨울 tick 값 순으로 정렬, FreeRTOS는 두 개(정상 + overflow) |
| overflow delayed list | wrap 뒤에 깰 태스크 리스트 | 깨울 값이 넘친 태스크를 따로 보관, wrap 때 교환 |
| `xNextTaskUnblockTime` | 다음 깨울 시각 캐시 | tick마다 리스트 대신 이 값 하나만 비교 |
| wrap (overflow) | 카운터가 최댓값에서 0으로 | 32비트 1 kHz = 49.7일 |
| `configINITIAL_TICK_COUNT` | tick 초기값 | wrap 테스트용, V10.0.0부터, 기본 0 |
| 상대 지연 | "지금부터 n" | `vTaskDelay`, `k_sleep(K_MSEC(n))` |
| 절대 지연 | "시각 t에" | `xTaskDelayUntil`, `K_TIMEOUT_ABS_TICKS` |
| drift | 주기 오차의 누적 | 상대 지연 주기 루프에서 생긴다 |
| catch-up | 밀린 주기를 연달아 실행 | `xTaskDelayUntil`의 늦었을 때 동작 |
| skip | 밀린 주기를 버리고 다음 격자로 | `xTaskPeriodicDelay`의 동작 |
| `xPendedTicks` | 스케줄러 정지 중 쌓인 tick 수 | `xTaskResumeAll`에서 재생 |
| `xTaskCatchUpTicks` | 잃은 tick 보정 | 인터럽트를 오래 막은 뒤 시계를 앞으로 |
| `TimeOut_t` | 타임아웃 기준점 | 시작 tick + wrap 횟수 |
| `xTaskCheckForTimeOut` | 남은 시간 계산 | 남은 tick을 줄이고 다 썼으면 `pdTRUE` |
| `k_timeout_t` | Zephyr 타임아웃 타입 | 구조체, 음수 영역에 절대 시각 인코딩 |
| delta list | 차이만 저장하는 정렬 리스트 | Zephyr `timeout_list`, 머리 하나만 줄이면 된다 |
| +1 tick 규칙 | Zephyr 상대 타임아웃 보정 | 최소 대기 보장, `timeout.c:111` |
| `sys_clock_announce` | Zephyr의 "tick 왔다" | 드라이버가 지난 tick 수를 알리면 만료 처리 |
| `curr_tick` | Zephyr 커널 시계 | 64비트, 사실상 wrap 없음 |
| tickless | 필요할 때만 타이머 인터럽트 | Zephyr 기본, FreeRTOS `configUSE_TICKLESS_IDLE` (C6) |

## 15. 요약 & 체크리스트

tick은 RTOS 커널의 시계이자 알람 시계다. FreeRTOS는 매 tick `xTaskIncrementTick()`에서 32비트 `xTickCount`를 올리고, 캐시해 둔 `xNextTaskUnblockTime`과 비교 한 번으로 대부분의 tick을 끝내며(잠든 태스크 수와 무관하게 1.5 µs), 깨울 때만 태스크당 약 1.6 µs를 쓴다. 대신 잠드는 쪽이 정렬 삽입 O(N)을 낸다. 카운터 wrap은 delayed list 두 개와 포인터 교환으로 처리하지만, 앱 코드의 비교는 부호 없는 뺄셈으로 직접 지켜야 하고 `configINITIAL_TICK_COUNT`로 테스트한다. tick rate는 필요한 타임아웃 해상도로 정하며(보통 1 kHz, 클럭을 나누어떨어뜨리는 값), `pdMS_TO_TICKS`의 내림·잘림을 조심한다. 주기 태스크는 `vTaskDelay`가 아니라 `xTaskDelayUntil`(catch-up) 또는 `xTaskPeriodicDelay`(skip)로 만들고, 기준점은 항상 과거로 잡는다. `vTaskDelay(n)`은 (n−1, n] tick, Zephyr 상대 타임아웃은 +1 규칙으로 (n, n+1] tick이다. 스케줄러 정지는 tick을 pended로 보존하지만 인터럽트 마스킹은 tick을 잃는다. 여러 단계 블로킹의 전체 예산은 `xTaskCheckForTimeOut`(Zephyr는 `sys_timepoint_*`)으로 지킨다. Zephyr는 64비트 시계, delta list, 타입 있는 타임아웃, tickless 기본값으로 같은 문제를 다르게 푼다.

- [ ] tick 하나에 커널이 하는 일 세 가지(시계, 깨우기, time slicing)를 말할 수 있다
- [ ] `xNextTaskUnblockTime` 때문에 tick 비용이 잠든 태스크 수와 무관하다는 것을 측정값과 함께 설명할 수 있다
- [ ] tick rate를 고르는 기준(타임아웃 해상도, 클럭 나눗셈, 세금, ms 변환)을 말할 수 있다
- [ ] `pdMS_TO_TICKS`의 내림과 16비트 잘림 예를 들 수 있다
- [ ] 두 개의 delayed list와 `taskSWITCH_DELAYED_LISTS()`로 wrap을 처리하는 방식을 그림으로 그릴 수 있다
- [ ] 앱 코드의 wrap 안전 비교(`(TickType_t)(now - start) >= dur`)를 쓸 수 있고 `configINITIAL_TICK_COUNT`로 테스트할 수 있다
- [ ] `vTaskDelay` / `xTaskDelayUntil` / `xTaskPeriodicDelay`의 차이를 타임라인으로 그리고, 반환값의 의미를 말할 수 있다
- [ ] `vTaskDelay(1)`이 0~1 tick, Zephyr `K_TICKS(1)`이 1~2 tick인 이유를 소스 줄로 설명할 수 있다
- [ ] `pxPreviousWakeTime`을 미래로 잡으면 왜 잠들지 않는지 설명할 수 있다
- [ ] 스케줄러 정지(pended)와 인터럽트 마스킹(유실)의 차이, `xTaskCatchUpTicks`의 용도를 말할 수 있다
- [ ] `vTaskSetTimeOutState` / `xTaskCheckForTimeOut`으로 다단계 타임아웃 드라이버 루프를 쓸 수 있다
- [ ] Zephyr `k_timeout_t`, delta list, +1 tick 규칙, 절대 타임아웃, `k_uptime_get`과 `k_cycle_get_32`의 차이를 말할 수 있다

## Bare-Metal 노트와의 관계

Bare-Metal 나침반의 BM C7 행(핵심 개념: "SysTick 설정, DWT CYCCNT 켜기(DEMCR.TRCENA), 정확한 지연 함수 직접 구현")과의 대응이다. 이 노트는 "tick을 커널 시간 관리에 쓰는 부분"의 주인이고, SysTick 하드웨어 자체는 RTOS B4, 사이클 카운터 측정 도구는 RTOS M6가 다룬다.

| BM ID | BM 주제 | 이 노트의 해당 절 | Bare-Metal 쪽에 남길 내용 |
|---|---|---|---|
| BM C7 | SysTick 설정 (주기 인터럽트 만들기) | §1.4 (LOAD 정수 나눗셈 오차만), 레지스터 상세는 RTOS B4 | RTOS 없이 SysTick을 켜는 최소 코드와 CLKSOURCE 선택, 이 노트 §1 링크 |
| BM C7 | ms tick 카운터와 타임아웃 비교 | §1.2, §4.4 (wrap 안전 비교), §7 | 슈퍼 루프의 `volatile uint32_t g_ms`와 원자 읽기, 폴링 타임아웃 패턴 |
| BM C7 | 정확한 지연 함수 직접 구현 | §5 (RTOS의 지연은 잠드는 지연, (n−1, n] tick 문제) | DWT CYCCNT·SysTick VAL 기반 바쁜 대기 `delay_us()`와 최적화·인터럽트 영향 |
| BM C7 | DWT CYCCNT 켜기 (DEMCR.TRCENA) | 이 노트에 없음 (QEMU에 DWT 없음, 측정은 FPGA 카운터로 대신) — RTOS M6 | CYCCNT 켜는 순서, 실칩에서 사이클 측정 |
