# C10. SMP RTOS — 코어가 둘이 되면 커널의 무엇이 바뀌나: 전역 ready queue, 스핀락 크리티컬 섹션, IPI, affinity

> **이 노트를 다 읽으면**: AMP · SMP · BMP를 칩 예시와 함께 구분하고 고를 수 있다 · FreeRTOS SMP의 "가장 높은 우선순위 N개가 동시에 돈다" 규칙과 `configRUN_MULTIPLE_PRIORITIES` · `configUSE_CORE_AFFINITY` · `configUSE_TASK_PREEMPTION_DISABLE`이 실제로 무엇을 바꾸는지 직접 돌려서 설명할 수 있다 · SMP에서 크리티컬 섹션이 "인터럽트 마스크 + 스핀락"이 되는 이유와 `portGET_TASK_LOCK` / `portGET_ISR_LOCK` 두 락의 역할을 소스로 말할 수 있다 · 단일 코어에서만 안전하던 코드(우선순위로 배제, `k_sched_lock`)가 2코어에서 깨지는 장면을 재현하고 고칠 수 있다

> **Don 기준 난이도**: 멀티코어 Cortex-R SSD 펌웨어(코어마다 실행부 하나 = AMP), 스핀락 · 메모리 배리어 개념(EL F4 · F5)은 이미 안다 / 새로 배울 부분은 **커널 하나가 여러 코어를 같이 스케줄**할 때 생기는 일 — 전역 스케줄링 결정, 코어 간 인터럽트(IPI), 우선순위만으로는 배제가 안 된다는 사실, 그리고 FreeRTOS · Zephyr가 이를 구현한 소스

## 0. 큰 그림 — 코어가 둘이면 "누가 다음 일을 고르나"가 두 번 결정된다

Don이 SSD 컨트롤러에서 본 구조를 떠올려 보자. 컨트롤러 안에 Cortex-R 코어가 여러 개 있었고, 보통 **코어마다 맡은 일이 정해져** 있었다. 호스트 인터페이스(NVMe) 코어, FTL 코어, NAND 채널 코어 — 각 코어에 실행부(executive) 하나가 돌고, 코어끼리는 공유 메모리의 큐와 doorbell 인터럽트로 일을 넘겼다. 이게 **AMP**(Asymmetric Multiprocessing)다. 코어마다 독립 펌웨어가 돌고, 코어 사이 경계가 곧 소프트웨어 모듈 경계다.

RTOS가 **SMP**(Symmetric Multiprocessing)로 돌면 그림이 완전히 달라진다. **커널 하나, 이미지 하나, ready queue 하나**가 코어 둘을 같이 관리한다. 태스크는 "어느 코어"에 속하지 않는다. 스케줄러가 매 순간 "지금 ready인 태스크 중 어떤 것들을 어느 코어에 올릴지"를 고른다. 단일 코어 RTOS의 규칙 "가장 높은 우선순위 태스크 **하나**가 돈다"가 "가장 높은 우선순위 태스크 **N개**(N = 코어 수)가 돈다"로 바뀐다.

그 중간이 **BMP**(Bound Multiprocessing)다. 커널은 SMP 커널 하나인데, 태스크를 전부 특정 코어에 고정(pin)해서 AMP처럼 예측 가능하게 쓴다.

그림 1 — AMP · SMP · BMP. AMP는 코어마다 커널(또는 bare-metal)이 따로, SMP는 커널 하나가 코어 둘을 같이, BMP는 SMP 커널 위에서 태스크를 전부 코어에 고정한다.

SMP 커널 안에서는 다음 다섯 가지가 단일 코어와 다르다. 이 노트는 이 다섯 가지를 차례로 직접 돌려 본다.

1. **ready queue가 공유된다** — 두 코어가 같은 자료구조를 동시에 만질 수 있다. 그래서 커널 자료구조를 만지는 구간(크리티컬 섹션)은 **인터럽트 마스크만으로는 부족하고 스핀락이 필요**하다 (§5).
2. **스케줄링 결정이 전역이다** — "가장 높은 N개"를 고르고, 어느 코어를 선점할지도 골라야 한다 (§2, §4).
3. **다른 코어에게 "다시 골라"라고 알려야 한다** — 코어 0에서 깨운 태스크가 코어 1의 지금 태스크보다 높으면 코어 1을 인터럽트해야 한다. 이게 **IPI**(Inter-Processor Interrupt)다 (§6).
4. **우선순위가 배제 수단이 아니다** — 단일 코어에서는 "높은 우선순위가 도는 동안 낮은 것은 못 돈다"가 사실이었다. SMP에서는 둘이 동시에 돈다. `k_sched_lock()` · `vTaskSuspendAll()`도 의미가 달라진다 (§3, §4).
5. **어디서 도는지가 성능과 결정성을 바꾼다** — migration(코어 이동), 캐시 · 버스 공유, false sharing. 그래서 **affinity**(코어 고정) API가 생겼다 (§7, §8, §9).

### 실습 환경 한 줄

- **Zephyr v4.4.2 SMP**: QEMU `virt` 머신의 Cortex-A53 × 2 (`qemu_cortex_a53/qemu_cortex_a53/smp`, Zephyr SDK 1.0.1 툴체인, Zephyr SDK의 QEMU 10.0.2). 비교용 단일 코어는 같은 SoC의 `qemu_cortex_a53` 보드와, SMP 보드에 `-DCONFIG_MP_MAX_NUM_CPUS=1`을 준 빌드.
- **FreeRTOS V11.3.2 SMP**: QEMU `mps2-an521`(SSE-200, **Cortex-M33 × 2**, Ubuntu QEMU 10.2.1) 위에 `ARM_CM33_NTZ` 포트를 `configNUMBER_OF_CORES = 2`로 직접 올렸다. 랩 템플릿은 M3 전용이라 시작 코드 · 링커 스크립트 · 보조 코어 깨우기 · IPI를 직접 썼다 (§4.3). 이 포트의 SMP 지원은 V11.3.1(2026-08)에 들어온 것이다.
- **타이밍 주의 — 이 노트의 숫자는 QEMU TCG 기준이다**. SMP 보드는 `CONFIG_QEMU_ICOUNT=n`(Zephyr 보드 설정 주석: "icount does not work well with SMP")이라 가상 시계 = 호스트 실제 시간이고, 두 가상 CPU는 MTTCG(멀티스레드 TCG)로 호스트 스레드 두 개에서 진짜 병렬로 돈다(§8.1에서 확인). 그래서 **결과가 실행마다 달라지고**, 캐시 · 버스 · 메모리 순서(memory ordering)는 실제 칩과 같지 않다. 이 노트가 보여 주려는 것은 절대값이 아니라 **현상의 존재와 상대 비교**(lost update가 생기나, IPI가 몇 번 가나, 1코어 대비 몇 배인가)다. 측정은 VM 호스트(Lima `elinux`, aarch64, 6 vCPU, 커널 7.0.0-38-generic)의 부하가 낮을 때(load average 0.1~3) 반복해서 최솟값 또는 백분위를 썼다.

## 1. AMP · SMP · BMP — 정의와 실제 칩

### 1.1 정의

| 방식 | 커널 · 이미지 | 태스크는 어디서 도나 | 코어 종류 | 코어 간 통신 | 장점 | 약점 |
|---|---|---|---|---|---|---|
| AMP (비대칭) | 코어마다 따로 (RTOS A + RTOS B, 또는 RTOS + bare-metal, 또는 Linux + RTOS) | 빌드할 때 정해진 코어 | 달라도 된다 (M7 + M4, A + M) | 메일박스 · HSEM · 공유 RAM · OpenAMP/RPMsg | 코어별 독립 검증, 장애 격리, 결정성 | 부하가 한쪽에 몰려도 못 나눔, 코드 · 데이터 이중화 |
| SMP (대칭) | 커널 하나, 이미지 하나 | 스케줄러가 매번 고른다 (어느 코어든) | 같아야 한다 (같은 ISA · 같은 메모리 뷰) | 커널 API 그대로 (큐 · 세마포어가 코어를 넘나든다) | 부하 자동 분산, 프로그래밍 모델 하나 | 락 경쟁, migration, 타이밍 예측 어려움 |
| BMP (고정 SMP) | 커널 하나 | 태스크마다 코어 하나로 고정 | 같아야 한다 | 커널 API 그대로 | AMP처럼 예측 가능 + API 하나 | 부하 분산 포기, 고정 설계가 필요 |

"대칭"의 뜻은 **어느 코어도 특별하지 않다**는 것이다. 모든 코어가 같은 커널 코드를 돌리고, 같은 ready queue를 보고, 어떤 태스크든 실행할 수 있다. 부팅 때 primary 코어가 먼저 초기화를 하는 것 정도만 다르다.

| Arm Cortex-R52 클러스터 (예: NXP S32Z/S32E) | R52 여러 개, lockstep 쌍 가능 | 코어별 RTOS + 하이퍼바이저(AMP 쪽이 많음) | O5 · O6 · P6 |
| Arm Cortex-R82 | 64-bit Armv8-R, 클러스터 최대 8코어, 클러스터 내 하드웨어 일관성 (2020-09 발표, SSD · 연산 스토리지 겨냥) | SMP 가능 | FreeRTOS `ARM_CR82` 포트가 SMP 지원 (V11.3.0) — Don의 SSD 경력과 직접 연결 |
| AI 가속기 SoC의 제어 클러스터 | Cortex-R / M / RISC-V 제어 코어 몇 개 | 칩마다 다름 (공개 자료 적음) | 이름 있는 예는 확인 못 함 — 구조만 §11.4 |

멀티코어가 된 이유는 셋이다. (1) 클럭을 올리는 것보다 코어를 하나 더 넣는 것이 전력 · 면적당 성능이 좋다. (2) **역할 분리** — 무선 스택 · 보안 · 실시간 제어를 서로 방해 없이 돌리고 싶다(AMP 동기). (3) 연산이 늘었다 — 센서 퓨전, 작은 신경망 추론, 압축 · 암호. 이 중 (3)이 SMP의 동기다.

### 1.3 Don의 경험으로 번역

| SSD 펌웨어에서 | RTOS 용어 |
|---|---|
| 코어마다 다른 실행부, 코어 간 메시지 큐 + doorbell | AMP + 메일박스 |
| 모든 코어가 같은 작업 풀에서 일을 꺼내 처리 (있었다면) | SMP 전역 ready queue |
| 공유 자료구조에 하드웨어 세마포어 / 스핀락 | SMP 크리티컬 섹션의 스핀락 |

### 2.1 전역 ready queue vs 코어별 ready queue

- **전역(global) 스케줄링**: ready queue가 하나다. 어떤 코어든 스케줄링할 때 같은 큐에서 "지금 가장 높은 것"을 꺼낸다. FreeRTOS SMP(`pxReadyTasksLists[]` 하나)와 Zephyr SMP 기본(`_kernel.ready_q` 하나)이 이 방식이다. 장점: 부하가 자동으로 고르게 퍼지고, 항상 "가장 높은 N개"가 돈다. 단점: 모든 코어가 큐 하나를 두고 락 경쟁을 한다.
- **코어별(partitioned) 스케줄링**: 코어마다 ready queue가 있고 태스크는 한 큐에만 산다. Zephyr의 `CONFIG_SCHED_CPU_MASK_PIN_ONLY=y`가 이 방식이다 — `struct _cpu` 안에 `ready_q`가 생긴다(`include/zephyr/kernel_structs.h`). 락 경쟁이 적고 예측하기 쉽지만, 한 코어가 바쁘고 다른 코어가 놀아도 일을 옮기지 않는다.

이론(어느 쪽이 스케줄 가능성 면에서 유리한가, Dhall 효과)은 N8이 다룬다. 이 노트는 구현만 본다.

### 2.2 "가장 높은 우선순위 N개가 돈다"

단일 코어 규칙: ready인 태스크 중 **가장 높은 하나**가 돈다.
SMP 규칙: ready인 태스크 중 **가장 높은 N개**가 돈다(N = 코어 수, affinity가 허락하는 범위에서).

이 한 줄이 모든 차이를 만든다. 예를 들어 드론 비행 제어기가 듀얼코어 MCU에서 SMP로 돈다면, 자세 제어 태스크(높음)와 로그 태스크(낮음)는 **동시에** 돈다. 단일 코어였다면 로그 태스크는 자세 제어 태스크가 잠들 때만 돌았다. 코드가 그 사실에 기대고 있었다면(예: "로그 태스크가 도는 동안엔 제어 루프가 공유 버퍼를 안 만진다") SMP에서 깨진다(§3.3).

FreeRTOS는 이 규칙을 끄는 옵션까지 준다: `configRUN_MULTIPLE_PRIORITIES = 0`이면 **서로 다른 우선순위 태스크는 동시에 돌지 않는다**. 높은 태스크가 ready면 낮은 태스크를 다른 코어에서도 내린다. 그 대가로 코어가 논다. §4.2에서 실제로 돌려 본다.

### 2.3 예제 1 — 두 CPU가 정말 같이 도는가 (Zephyr, 스레드별 실행 CPU 세기)

무엇을 확인하나: 같은 우선순위 스레드 4개가 SMP에서는 두 CPU에 퍼지고, 단일 코어에서는 한 CPU에 몰리는지, 그리고 그 결과 벽시계 시간이 줄어드는지.

```text
# ex1/prj.conf
CONFIG_PRINTK=y
CONFIG_SCHED_CPU_MASK=y
```

```c
/* ex1: 두 CPU가 정말 같이 도는가 — 스레드마다 실행된 CPU id를 센다 */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>

#define NT 4
#define STK 2048
K_THREAD_STACK_ARRAY_DEFINE(stk, NT, STK);
static struct k_thread th[NT];
static volatile uint32_t on_cpu[NT][2];   /* [thread][cpu] 샘플 수 */
static volatile int done;

static int my_cpu(void)
{
	unsigned int key = arch_irq_lock();   /* 읽는 중 migration 방지 */
	int id = arch_curr_cpu()->id;
	arch_irq_unlock(key);
	return id;
}

static void worker(void *p1, void *p2, void *p3)
{
	int me = (int)(uintptr_t)p1;
	for (int i = 0; i < 2000; i++) {
		on_cpu[me][my_cpu()]++;
		k_busy_wait(100);                 /* 100 us 계산하는 척 */
		if ((i % 50) == 0) {
			k_yield();
		}
	}
	done++;   /* 일부러 atomic이 아님: 아래 ex2에서 다룬다 */
}

int main(void)
{
	printk("CONFIG_SMP=%d MP_MAX_NUM_CPUS=%d arch_num_cpus()=%u main on cpu%d\n",
	       IS_ENABLED(CONFIG_SMP), CONFIG_MP_MAX_NUM_CPUS, arch_num_cpus(), my_cpu());
	int64_t t0 = k_uptime_get();
	for (int i = 0; i < NT; i++) {
		k_thread_create(&th[i], stk[i], STK, worker, (void *)(uintptr_t)i,
				NULL, NULL, 5, 0, K_NO_WAIT);
	}
	for (int i = 0; i < NT; i++) {
		k_thread_join(&th[i], K_FOREVER);
	}
	int64_t t1 = k_uptime_get();
	for (int i = 0; i < NT; i++) {
		printk("T%d: cpu0=%4u cpu1=%4u\n", i, on_cpu[i][0], on_cpu[i][1]);
	}
	printk("4 threads x 2000 x 100us = 800 ms of work, wall = %lld ms\n", t1 - t0);
	return 0;
}
```

출력에서 볼 것: SMP에서는 **한 스레드가 두 CPU를 오간다**(T0이 cpu0에서 650번, cpu1에서 1350번 — 50번마다 `k_yield()`할 때 다른 CPU로 옮겨 갔다). 이게 migration이다. 벽시계는 800 → 480 ms. 이상적인 400 ms보다 긴 이유는 50번마다의 `k_yield`와 스케줄링 비용, 그리고 `k_busy_wait`이 시계를 보며 도는 루프라 QEMU 호스트 스케줄링 영향을 받기 때문이다.

### 2.4 `arch_curr_cpu()->id`를 읽을 때 왜 인터럽트를 막았나

`my_cpu()`가 `arch_irq_lock()`으로 감싼 이유: SMP에서 스레드는 **언제든 다른 CPU로 옮겨질 수 있다**. CPU 구조체 포인터를 읽은 직후 선점되어 다른 CPU로 옮겨지면, 이미 "옛 CPU"의 id를 들고 있게 된다. Zephyr는 이 실수를 잡으려고 `_current_cpu` 매크로에 `__ASSERT_NO_MSG(!z_smp_cpu_mobile())`를 넣어 뒀다(`include/zephyr/kernel_structs.h`) — "지금 이 스레드가 옮겨질 수 있는 상태면 CPU 포인터를 쓰지 마라". 인터럽트가 막혀 있으면 이 CPU에서 선점이 안 되니 안전하다.

이 문제는 단일 코어에 없다. 그리고 FreeRTOS SMP도 똑같다: `portGET_CORE_ID()` 값은 그 순간에만 맞다. FreeRTOS 커널 코드가 `prvCheckForRunStateChange()` 안에서 락을 다시 잡은 뒤 `xCoreID = portGET_CORE_ID()`를 **다시 읽는 것**(§5.2)도 같은 이유다.

함정: "현재 코어 번호"로 배열(`per_cpu_buf[core]`)을 고르는 코드는 그 배열을 쓰는 동안 migration이 없어야 한다. 인터럽트를 막거나, 스레드를 그 코어에 pin하거나, 배열 원소 접근 자체를 atomic으로 만든다.

## 3. 단일 코어에서 안전하던 것이 2코어에서 깨진다

### 3.1 예제 2 — 공유 카운터: 보호 없음 / k_spinlock / atomic_inc, 1코어 vs 2코어

무엇을 확인하나: 같은 우선순위 스레드 둘이 공유 카운터를 20만 번씩 올릴 때 결과가 틀리는지, 그리고 1코어(시분할)와 2코어(진짜 병렬)에서 틀리는 모양이 어떻게 다른지.

```c
/* ex2: 공유 카운터 — 보호 없음 / k_spinlock / atomic_inc, 1코어 vs 2코어 */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>
#include <zephyr/sys/atomic.h>

#define N   200000
#define STK 2048
K_THREAD_STACK_ARRAY_DEFINE(stk, 2, STK);
static struct k_thread th[2];
static volatile uint32_t plain;
static uint32_t locked;
static atomic_t at;
static struct k_spinlock lock;
static int mode;

static void worker(void *p1, void *p2, void *p3)
{
	for (int i = 0; i < N; i++) {
		if (mode == 0) {
			plain++;                    /* LDR → ADD → STR: 끼어들 틈 */
		} else if (mode == 1) {
			k_spinlock_key_t k = k_spin_lock(&lock);
			locked++;
			k_spin_unlock(&lock, k);
		} else {
			atomic_inc(&at);
		}
	}
}

static void run(int m, const char *name)
{
	mode = m;
	uint64_t c0 = k_cycle_get_64();
	for (int i = 0; i < 2; i++) {
		k_thread_create(&th[i], stk[i], STK, worker, NULL, NULL, NULL,
				5, 0, K_NO_WAIT);
	}
	k_thread_join(&th[0], K_FOREVER);
	k_thread_join(&th[1], K_FOREVER);
	uint64_t ns = k_cyc_to_ns_floor64(k_cycle_get_64() - c0);
	uint32_t v = (m == 0) ? plain : (m == 1) ? locked : (uint32_t)atomic_get(&at);
	printk("%-9s result=%7u expected=%u lost=%6u  %4u ns/inc\n", name, v,
	       2 * N, 2 * N - v, (uint32_t)(ns / (2 * N)));
}

int main(void)
{
	printk("cpus=%u, timer %u Hz\n", arch_num_cpus(),
	       sys_clock_hw_cycles_per_sec());
	run(0, "plain++");
	run(1, "spinlock");
	run(2, "atomic");
	return 0;
}
```

- **단일 코어에서도 `plain++`은 틀린다.** 시분할(`CONFIG_TIMESLICE_SIZE=1`)로 같은 우선순위 스레드가 tick마다 교대하므로, LDR과 STR 사이에서 선점되면 상대가 한 time slice 동안 올린 값을 통째로 덮어쓴다. 한 번 잘못 끊길 때마다 **수천~수만 개**가 한꺼번에 사라진다. 이 보드는 `CONFIG_QEMU_ICOUNT=y`(명령 수 기반 가상 시계)라 세 번 모두 거의 같은 숫자가 나왔다(결정적).
- **SMP에서는 실행마다 다르다** — 48k, 80k, 0. 0이 나온 3회차는 두 스레드가 거의 겹치지 않고 돈 경우다. "몇 번 돌려 봤는데 괜찮았다"가 SMP 버그 검증으로 쓸모없는 이유다.
- spinlock · atomic은 둘 다 항상 정확하다. 비용은 §8에서 제대로 잰다(여기 ns/inc는 1회 측정이라 참고만).
- 교훈: `plain++` 공유는 단일 코어에서도 원래 버그였다(시분할 또는 ISR이 있으면). SMP는 그 버그를 **더 자주, 더 무작위로** 드러낸다. 진짜 "SMP에서만 나타나는" 버그는 §3.3의 예제 4다.

출력에서 볼 것:

- `k_spin_lock` = **① 이 CPU의 IRQ 마스크(`msr daifset, #2`) → ② 락 변수에 CAS** → 임계 구역 → **③ release 저장 → ④ IRQ 상태 복원**. 소스(`include/zephyr/spinlock.h`)의 `k.key = arch_irq_lock();` 다음 `while (!atomic_cas(&l->locked, 0, 1)) { do { arch_spin_relax(); } while (atomic_get(&l->locked) != 0); }`가 그대로 보인다. 실패하면 CAS를 반복하지 않고 **읽기만 하며 기다렸다가**(`ldar` 루프, test-and-test-and-set) 풀린 것 같을 때만 CAS를 다시 한다 — 캐시 라인을 덜 흔든다.
- atomic 연산이 `__aarch64_cas8_acq_rel` 같은 **함수 호출**이다. GCC의 outline atomics: 실행 시점에 CPU가 LSE(`casal` 명령)를 지원하면 그것을, 아니면 LDXR/STXR 루프를 쓴다. Cortex-A53은 Armv8.0이라 LSE가 없어서 LL/SC 루프로 간다. (랩 README가 말한 "Ubuntu gcc로 Zephyr를 빌드하면 outline atomics 때문에 링크 안 됨"이 바로 이 함수들이다 — Zephyr SDK 툴체인은 이걸 libgcc에 넣어 준다.)
- 왜 IRQ를 먼저 막나: 락을 쥔 채 같은 CPU의 ISR이 같은 락을 잡으려 하면 영원히 돈다(self-deadlock, EL F4 §4). Zephyr의 `k_spin_lock`은 항상 irqsave 버전이다. 그래서 **Zephyr에서는 같은 `k_spinlock`을 스레드와 ISR이 함께 써도 된다**.
- 단일 코어 빌드에서는 ②③이 사라지고(`#ifdef CONFIG_SMP`) `k_spin_lock` = `irq_lock`이다. 같은 소스가 UP에서는 "인터럽트 끄기", SMP에서는 "인터럽트 끄기 + 스핀락"이 된다. **이게 이 노트 제목의 "SMP에서 크리티컬 섹션 = 스핀락"이다.**

### 3.3 예제 4 — 우선순위와 `k_sched_lock`으로 배제하던 코드 (SMP에서만 깨진다)

단일 코어 RTOS에서 흔한 두 관용구가 있다.

- **"나보다 높은 건 없다"**: 가장 높은 우선순위 태스크는 다른 태스크에게 선점되지 않으니, 공유 데이터를 락 없이 고친다. 낮은 쪽만 조심하면 된다.
- **"스케줄러 잠금 = 가벼운 뮤텍스"**: 낮은 태스크는 `k_sched_lock()`(FreeRTOS는 `vTaskSuspendAll()`)으로 스케줄러를 잠그고 고친다. 그동안 어떤 스레드도 끼어들 수 없다(ISR은 예외).

단일 코어에서는 이 둘을 합치면 정말로 안전하다. SMP에서는?

무엇을 확인하나: 같은 코드를 단일 코어와 2코어에서 돌렸을 때, 2코어에서만 값이 사라지는지. 그리고 "둘 다 `k_sched_lock`"과 "둘 다 `k_spinlock`"은 어떤지.

```text
# ex3/prj.conf
CONFIG_PRINTK=y
CONFIG_SYS_CLOCK_TICKS_PER_SEC=1000
CONFIG_QEMU_ICOUNT=n
```

```c
/* ex3: 단일 코어 가정 "높은 우선순위 + k_sched_lock = 상호 배제"가 SMP에서 깨진다 */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>
#define ROUNDS 200
#define BURST  5000
#define STK    2048
K_THREAD_STACK_DEFINE(stk_h, STK);
K_THREAD_STACK_DEFINE(stk_l, STK);
static struct k_thread th_h, th_l;
static volatile uint32_t shared;
static struct k_spinlock lock;
static int mode;               /* 0: H 잠금 없음 + L sched_lock, 1: 둘 다 spinlock, 2: 둘 다 sched_lock */
static volatile uint32_t h_cpus, l_cpus;

static void bump(void)
{
	for (int j = 0; j < BURST; j++) {
		shared++;
	}
}
static void guarded(bool is_high)
{
	if (mode == 1) {
		k_spinlock_key_t k = k_spin_lock(&lock);
		bump();
		k_spin_unlock(&lock, k);
	} else if (mode == 0 && is_high) {
		bump();                         /* "나보다 높은 스레드는 없다": UP에서는 안전 */
	} else {
		k_sched_lock();                 /* UP: 다른 스레드가 끼어들 수 없다 */
		bump();
		k_sched_unlock();
	}
}
static void high(void *a, void *b, void *c)     /* prio 2 */
{
	for (int r = 0; r < ROUNDS; r++) {
		h_cpus |= BIT(arch_curr_cpu()->id);
		guarded(true);
		k_msleep(1);
	}
}
static void low(void *a, void *b, void *c)      /* prio 8 */
{
	for (int r = 0; r < ROUNDS; r++) {
		l_cpus |= BIT(arch_curr_cpu()->id);
		guarded(false);
		k_busy_wait(300);
	}
}
static void run(int m, const char *name)
{
	mode = m; shared = 0; h_cpus = l_cpus = 0;
	k_thread_create(&th_l, stk_l, STK, low, NULL, NULL, NULL, 8, 0, K_NO_WAIT);
	k_thread_create(&th_h, stk_h, STK, high, NULL, NULL, NULL, 2, 0, K_NO_WAIT);
	k_thread_join(&th_h, K_FOREVER);
	k_thread_join(&th_l, K_FOREVER);
	printk("%-20s cpus=%u shared=%7u lost=%6u (H cpus 0x%x, L cpus 0x%x)\n", name,
	       arch_num_cpus(), shared, 2 * ROUNDS * BURST - shared, h_cpus, l_cpus);
}
int main(void)
{
	run(0, "H nolock+L schedlock");
	run(2, "both k_sched_lock");
	run(1, "both k_spinlock");
	return 0;
}
```

(빈 줄 몇 개를 빼고 실은 것 말고는 실행한 소스 그대로다. `h_cpus`의 `|=`는 스레드 하나만 쓰므로 경쟁이 없다.)

출력에서 볼 것:

- **단일 코어: 세 방식 모두 0** — 우선순위와 스케줄러 잠금만으로 진짜 안전했다. 이 코드는 단일 코어 시절에 몇 년이고 테스트를 통과했을 것이다.
- **2코어: 앞의 두 방식은 매번 1만~2만 개를 잃는다.** H(prio 2)와 L(prio 8)이 서로 다른 CPU에서 **동시에** 돈다(H cpus, L cpus 마스크가 서로 다른 비트). `k_sched_lock()`은 "**이 CPU에서** 지금 스레드를 선점하지 마라"(현재 스레드의 `base.sched_locked` 카운트)일 뿐, 다른 CPU를 멈추지 않는다. 둘 다 `k_sched_lock()`을 걸어도 마찬가지다.
- `k_spinlock`만 2코어에서 정확하다. **SMP에서 상호 배제 수단은 스핀락(짧은 구간)과 뮤텍스 · 세마포어(긴 구간) 뿐이다.** 우선순위 · 스케줄러 잠금 · 인터럽트 끄기(`irq_lock`)는 "이 코어 안에서만" 효과가 있다.

함정 — Zephyr의 `irq_lock()`: SMP 빌드에서 `irq_lock()`은 이 CPU 인터럽트 마스크 + **전역 락**(`kernel/smp.c`의 `z_smp_global_lock()`, 스레드별 재진입 카운트)이다. 그래서 `irq_lock`끼리는 코어를 넘어 배제가 되지만, 무거운 전역 락이라 성능이 나쁘고 Zephyr 문서도 새 코드에서는 `k_spinlock`을 쓰라고 한다. 반대로 `arch_irq_lock()`은 이 CPU만 막는다.

FreeRTOS에서 같은 실험을 하면 결과가 **조금 다르다**(§4.5): `vTaskSuspendAll()`은 SMP에서 전역 task lock을 쥐기 때문에 "둘 다 SuspendAll"은 안전하다. 하지만 "H는 잠금 없음"인 경우는 똑같이 깨진다.

## 4. FreeRTOS SMP — "N개"를 고르는 규칙과 옵션, 그리고 QEMU 듀얼 M33에서 실제로 돌리기

### 4.1 역사와 지원 포트 (V11.3.2 소스 기준)

FreeRTOS는 V11.0.0(2023-12)에서 SMP를 메인라인에 합쳤다(그 전에는 별도 `smp` 브랜치와 ESP-IDF 자체 변형). `History.txt`의 해당 줄: "FreeRTOS Version 11.0.0 is the first to merge Symmetric Multiprocessing (SMP) support into the mainline release." 커널 하나로 SMP와 단일 코어를 다 빌드한다 — `configNUMBER_OF_CORES`(기본 1)만 바꾸면 `tasks.c`가 `#if ( configNUMBER_OF_CORES > 1 )` 분기로 SMP 코드를 켠다.

SMP를 쓰려면 **포트가** 다음 매크로를 정의해야 한다(`include/FreeRTOS.h`가 없으면 `#error`를 낸다).

| 매크로 | 뜻 | 단일 코어 기본값 |
|---|---|---|
| `portGET_CORE_ID()` | 지금 코드가 도는 코어 번호 | `0` |
| `portYIELD_CORE( x )` | 코어 x에게 "다시 스케줄해" 인터럽트(IPI) | `portYIELD()` |
| `portGET_TASK_LOCK( xCoreID )` / `portRELEASE_TASK_LOCK` | 태스크 쪽 커널 락 (재진입 스핀락) | 빈 매크로 |
| `portGET_ISR_LOCK( xCoreID )` / `portRELEASE_ISR_LOCK` | ISR과도 공유하는 커널 락 | 빈 매크로 |
| `portGET_CRITICAL_NESTING_COUNT( xCoreID )` 등 | 코어별 크리티컬 섹션 중첩 수 | TCB 안 `uxCriticalNesting` |

### 4.2 스케줄링 규칙을 소스로 — `prvYieldForTask()`

태스크 하나가 ready가 될 때(세마포어 give, 지연 만료, `vTaskResume` 등) 커널은 "이 태스크를 지금 어느 코어에서 돌려야 하나"를 정한다. 그 함수가 `tasks.c`의 `prvYieldForTask()`다. 핵심만 남기면:

```c
/* tasks.c (V11.3.2) prvYieldForTask() 요약 — 크리티컬 섹션 안에서만 불린다 */
xLowestPriorityToPreempt = pxTCB->uxPriority - 1;
for( xCoreID = 0; xCoreID < configNUMBER_OF_CORES; xCoreID++ )
{
    xCurrentCoreTaskPriority = pxCurrentTCBs[ xCoreID ]->uxPriority;
    if( idle 태스크면 ) xCurrentCoreTaskPriority -= 1;     /* idle은 tskIDLE_PRIORITY - 1로 취급 */

    if( 그 코어가 실행 중이고 xYieldPendings[ xCoreID ] == pdFALSE )
    {
        if( xCurrentCoreTaskPriority <= xLowestPriorityToPreempt )
            if( pxTCB->uxCoreAffinityMask 에 xCoreID 비트가 있고 )          /* configUSE_CORE_AFFINITY */
                if( pxCurrentTCBs[ xCoreID ]->xPreemptionDisable == pdFALSE ) /* configUSE_TASK_PREEMPTION_DISABLE */
                {   xLowestPriorityToPreempt = xCurrentCoreTaskPriority;
                    xLowestPriorityCore = xCoreID;  }

        #if ( configRUN_MULTIPLE_PRIORITIES == 0 )
            /* 새 태스크보다 낮은(idle 아닌) 태스크를 돌리는 코어는 전부 양보시킨다 */
            if( 낮은 태스크 ) { prvYieldCore( xCoreID ); xYieldCount++; }
        #endif
    }
}
if( xLowestPriorityCore >= 0 ) prvYieldCore( xLowestPriorityCore );   /* RMP=0이면 xYieldCount == 0 일 때만 */
```

읽는 법:

- **"가장 낮은 우선순위 태스크를 돌리는 코어"를 선점 대상으로 고른다.** 새 태스크보다 낮아야 하고, 새 태스크의 affinity가 그 코어를 허락해야 하고, 그 코어의 태스크가 선점 금지(`vTaskPreemptionDisable`) 상태가 아니어야 한다. 이게 "가장 높은 N개가 돈다"를 유지하는 방법이다.
- idle 태스크는 우선순위를 하나 더 낮게 쳐서, 놀고 있는 코어가 가장 먼저 선택된다.
- `configRUN_MULTIPLE_PRIORITIES == 0`이면 **새 태스크보다 낮은 태스크를 돌리는 모든 코어**에 양보를 요청한다. 그래서 한 번에 한 우선순위 레벨만 돈다.
- 실제 "양보 요청"은 `prvYieldCore( xCoreID )` 매크로다:

```c
/* tasks.c (V11.3.2) */
#define prvYieldCore( xCoreID )                                                          \
do {                                                                                     \
    if( ( xCoreID ) == ( BaseType_t ) portGET_CORE_ID() )                                \
    {   /* 이 코어면: 크리티컬 섹션이 끝날 때 양보하도록 표시만 */                         \
        xYieldPendings[ ( xCoreID ) ] = pdTRUE;                                          \
    }                                                                                    \
    else                                                                                 \
    {   /* 다른 코어면: 아직 요청 안 했을 때만 IPI */                                     \
        if( pxCurrentTCBs[ ( xCoreID ) ]->xTaskRunState != taskTASK_SCHEDULED_TO_YIELD ) \
        {                                                                                \
            portYIELD_CORE( xCoreID );                                                   \
            pxCurrentTCBs[ ( xCoreID ) ]->xTaskRunState = taskTASK_SCHEDULED_TO_YIELD;   \
        }                                                                                \
    }                                                                                    \
} while( 0 )
```

(한국어 주석은 덧붙인 것이다.)

`xTaskRunState`는 SMP TCB의 새 필드다. 실행 중이면 **그 태스크가 도는 코어 번호**, 아니면 `taskTASK_NOT_RUNNING`, 양보 요청을 받았으면 `taskTASK_SCHEDULED_TO_YIELD`. 단일 코어의 `pxCurrentTCB` 하나가 `pxCurrentTCBs[ configNUMBER_OF_CORES ]` 배열이 됐다.

옵션 정리 (전부 `include/FreeRTOS.h`에서 기본값 · 제약 확인):

| 옵션 | 기본값 | 효과 | 제약 |
|---|---|---|---|
| `configNUMBER_OF_CORES` | 1 | 코어 수. 1보다 크면 SMP 코드 | 포트가 위 매크로를 정의해야 함 |
| `configRUN_MULTIPLE_PRIORITIES` | 0 | 1: 다른 우선순위 태스크도 동시에 돈다. 0: 한 번에 한 우선순위 레벨만 | `configUSE_TASK_PREEMPTION_DISABLE`를 쓰려면 1이어야 함 (`#error`) |
| `configUSE_CORE_AFFINITY` | 0 | `vTaskCoreAffinitySet/Get`, `xTaskCreateAffinitySet` 사용 가능 | 단일 코어에서 켜면 `#error` |
| `configTASK_DEFAULT_CORE_AFFINITY` | `tskNO_AFFINITY` | affinity 안 준 태스크의 기본 마스크 | affinity 켤 때만 |
| `configUSE_TASK_PREEMPTION_DISABLE` | 0 | `vTaskPreemptionDisable/Enable`: 이 태스크는 다른 코어의 결정으로 선점되지 않음 | SMP 전용, RMP=1, 선점 스케줄러 필요 |
| `configUSE_PASSIVE_IDLE_HOOK` | 0 | 코어 0이 아닌 코어의 idle(passive idle) 태스크용 훅 | SMP에서는 정의 필수 |
| `configIDLE_AFFINITY` | 0 | idle 태스크를 자기 코어에 고정 (V11.3.1 추가) | affinity 켤 때 |

함정: `configRUN_MULTIPLE_PRIORITIES`의 **기본값이 0**이다. 단일 코어 코드를 "가장 덜 놀라게" 옮기려는 선택이지만, 0이면 코어가 놀 수 있다(아래 실험). 1로 바꾸는 순간 §3.3 같은 우선순위 기반 가정이 다 깨진다.

### 4.3 QEMU mps2-an521(Cortex-M33 × 2) 위에 FreeRTOS SMP를 직접 올리기

랩에 FreeRTOS SMP 템플릿은 없다. 하지만 QEMU `mps2-an521`은 SSE-200 서브시스템 — **Cortex-M33 두 개**가 메모리를 공유하는 칩 — 을 모델링하고, V11.3.1부터 `ARM_CM33_NTZ` 포트가 SMP를 지원한다. 포트 ReadMe(`portable/ARMv8M/non_secure/ReadMe.txt`)가 요구하는 것을 그대로 구현하면 된다.

포트 ReadMe가 정한 부팅 순서:

- primary(코어 0): `.data` · `.bss` 초기화 → `main()` → 태스크 생성 · affinity 지정 → `vTaskStartScheduler()` → `xPortStartScheduler()`가 tick 타이머 설정 후 `ucPrimaryCoreInitDoneFlag = 1` → **`configWAKE_SECONDARY_CORES()`** 호출 → `ucSecondaryCoresReadyFlags[]`가 다 설 때까지 대기 → 첫 태스크 시작.
- secondary(코어 1): 코어별 초기화 → IPI 수단 설정 → `vPortConfigureInterruptPriorities()` → `ucSecondaryCoresReadyFlags[0] = pdTRUE` → **`svc 102`**(`portSVC_START_SCHEDULER`)로 자기 코어의 첫 태스크 시작.
- 애플리케이션이 줄 것: `configCORE_ID_REGISTER`(코어 번호 레지스터 주소), `configWAKE_SECONDARY_CORES`(코어 1 깨우는 함수), `vInterruptCore(core)`(IPI — 포트에는 아무것도 안 하는 weak 함수만 있다).

AN521에서 각각에 해당하는 하드웨어(주소는 Zephyr `soc/arm/mps2/soc.c`와 `boards/arm/mps2/mps2_an521-common.dtsi`에서 확인):

| 필요한 것 | AN521 (SSE-200) | 주소 (Secure 별칭) |
|---|---|---|
| 코어 번호 | CPU_IDENTITY.CPUID | `0x5001F000` |
| 코어 1 깨우기 | 시스템 제어 INITSVTOR1(코어 1 벡터 테이블), CPU_WAIT | `0x50021114`, `0x50021118` |
| IPI | 전용 doorbell을 안 쓰고 **CMSDK 타이머를 1카운트로 쏘아** 그 IRQ를 대상 코어의 NVIC에서만 켬 (TIMER0 → 코어 0, IRQ 3 / TIMER1 → 코어 1, IRQ 4) | `0x50000000`, `0x50001000` |
| 콘솔 | CMSDK UART0 (폴링) | `0x50200000` |
| 코드 / RAM | SSRAM1 / SSRAM2·3 | `0x10000000` / `0x38000000` |

IPI를 타이머로 흉내 낸 이유: SSE-200 내부 장치 인터럽트는 두 코어의 NVIC에 같이 들어가지만(QEMU armsse가 IRQ를 두 CPU로 나눈다), NVIC는 코어마다 따로라 **받을 코어의 NVIC에서만 그 IRQ를 enable**하면 "코어 x만 받는 인터럽트"가 된다. 실제 칩이라면 MHU(Message Handling Unit) doorbell을 쓸 자리다. 동작은 같다: 다른 코어에 인터럽트를 걸고, 그 ISR이 PendSV를 걸어 재스케줄한다.

#### 예제 5 — 보드 지원 코드 (startup.c · board.c)

무엇을 확인하나: 두 코어가 같은 벡터 테이블로 깨어나 CPUID로 갈라지는 시작 코드, 그리고 포트 ReadMe의 secondary 흐름 · IPI 구현.

```c
/* startup.c: 두 코어가 같은 벡터 테이블로 깨어난다. CPUID를 읽어 core1이면 스택을 바꾸고 secondary_main으로 */
#include <stdint.h>
extern uint32_t __stack0_top, __stack1_top, __etext, __data_start, __data_end, __bss_start, __bss_end;
extern void SVC_Handler(void), PendSV_Handler(void), SysTick_Handler(void);
extern void TIMER0_Handler(void), TIMER1_Handler(void), HardFault_Handler(void);
extern int main(void);
extern void secondary_main(void);
void Reset_Handler(void);
static void Default_Handler(void) { for (;;) { } }

__attribute__((section(".vectors"), used))
static void (*const vectors[32])(void) = {
	(void (*)(void))&__stack0_top, Reset_Handler, Default_Handler, HardFault_Handler,
	Default_Handler, Default_Handler, Default_Handler, Default_Handler,
	0, 0, 0, SVC_Handler, Default_Handler, 0, PendSV_Handler, SysTick_Handler,
	Default_Handler, Default_Handler, Default_Handler, TIMER0_Handler,   /* IRQ3 */
	TIMER1_Handler,                                                       /* IRQ4 */
};

void primary_reset(void)
{
	uint32_t *s = &__etext, *d = &__data_start;
	while (d < &__data_end) { *d++ = *s++; }
	for (d = &__bss_start; d < &__bss_end; ) { *d++ = 0; }
	main();
	for (;;) { }
}

__attribute__((naked)) void Reset_Handler(void)
{
	__asm volatile(
		"ldr r0, =0x5001F000 \n"     /* CPU_IDENTITY.CPUID */
		"ldr r0, [r0]        \n"
		"cbz r0, 1f          \n"
		"ldr r1, =__stack1_top \n"
		"msr msp, r1         \n"
		"b secondary_main    \n"
		"1: b primary_reset  \n");
}
```

```c
/* board.c (앞부분): AN521 보드 지원 — UART0 출력, core1 깨우기, 타이머로 만든 IPI */
#include "FreeRTOS.h"
#include "task.h"
#define REG(a)      (*(volatile uint32_t *)(a))
#define UART0       0x50200000u
#define TIMER(c)    (0x50000000u + 0x1000u * (c))   /* TIMER0→core0 IRQ3, TIMER1→core1 IRQ4 */
#define SYSCTL      0x50021000u
extern volatile uint8_t ucSecondaryCoresReadyFlags[];
extern void vPortConfigureInterruptPriorities(void);
volatile uint32_t ulIpiCount[2];
/* ... uart_puts / uart_putu / board_exit(semihosting) / vAssertCalled / HardFault_Handler
       / memset / memcpy 는 평범한 코드라 생략 ... */

static void enable_ipi_irq(uint32_t core)        /* 자기 NVIC에서 자기 타이머 IRQ만 켠다 */
{
	*(volatile uint8_t *)(0xE000E400u + 3 + core) = 0xFF;   /* 가장 낮은 우선순위 */
	REG(0xE000E100u) = 1u << (3 + core);
}
void vInterruptCore(uint8_t ucCoreID)            /* portYIELD_CORE(x)가 부른다 */
{
#ifdef NO_IPI
	(void)ucCoreID; return;                      /* 실험: 포트의 weak stub처럼 아무것도 안 함 */
#endif
	REG(TIMER(ucCoreID) + 0x4) = 1;              /* VALUE=1 → 곧 0 → IRQ */
	REG(TIMER(ucCoreID) + 0x0) = 0x9;            /* ENABLE | IRQ ENABLE */
}
static void ipi_isr(uint32_t core)
{
	REG(TIMER(core) + 0x0) = 0;
	REG(TIMER(core) + 0xC) = 1;                  /* INTCLEAR */
	ulIpiCount[core]++;
	portYIELD_FROM_ISR(pdTRUE);                  /* 이 코어에 PendSV → 재스케줄 */
}
void TIMER0_Handler(void) { ipi_isr(0); }
void TIMER1_Handler(void) { ipi_isr(1); }

BaseType_t xWakeSecondaryCores(void)             /* configWAKE_SECONDARY_CORES */
{
	REG(SYSCTL + 0x114) = 0x10000000u;           /* INITSVTOR1 = 같은 벡터 테이블 */
	REG(SYSCTL + 0x118) = 0;                     /* CPUWAIT 해제 → core1 리셋 핸들러 시작 */
	return pdTRUE;
}
void secondary_main(void)                        /* core1: ReadMe의 secondary flow 3~7단계 */
{
	enable_ipi_irq(1);
	vPortConfigureInterruptPriorities();
	ucSecondaryCoresReadyFlags[0] = pdTRUE;
	__asm volatile("dsb \n svc 102" ::: "memory"); /* portSVC_START_SCHEDULER */
	for (;;) { }
}
void board_primary_init(void) { enable_ipi_irq(0); }
```

#### 예제 6 — "누가 어느 코어에서 도나": RUN_MULTIPLE_PRIORITIES 1 / 0 / affinity

무엇을 확인하나: 계속 도는(블록하지 않는) 태스크 H(3) · M(2) · L(1)이 코어 둘에서 100 tick 동안 각각 몇 번 돌았는지 — 설정에 따라 누가 굶는지.

```c
/* main.c: FreeRTOS SMP 의미 확인 — 우선순위 3·2·1 바쁜 태스크 셋이 코어 둘에서 어떻게 도나 */
#include "FreeRTOS.h"
#include "task.h"
void uart_puts(const char *s); void uart_putu(uint32_t v); void board_exit(void);
void board_primary_init(void);
extern uint8_t ucPortGetCoreID(void);
extern volatile uint32_t ulIpiCount[2];
static volatile uint32_t cnt[3][2];               /* [task][core] 루프 횟수 */
static TaskHandle_t h[3];
static const char *nm[3] = {"H(prio3)", "M(prio2)", "L(prio1)"};

static void busy(void *p)
{
	uint32_t me = (uint32_t)p;
	for (;;) { cnt[me][ucPortGetCoreID()]++; }
}

static void monitor(void *p)                      /* prio 6, 100 tick 뒤 결과 출력 */
{
	(void)p;
	vTaskDelay(100);
	for (int i = 0; i < 3; i++) { vTaskSuspend(h[i]); }
	uart_puts("EXP " EXPNAME " RUN_MULTIPLE_PRIORITIES=");
	uart_putu(configRUN_MULTIPLE_PRIORITIES); uart_puts("\n");
	for (int i = 0; i < 3; i++) {
		uart_puts("  "); uart_puts(nm[i]); uart_puts(" core0=");
		uart_putu(cnt[i][0] / 1000); uart_puts("k core1="); uart_putu(cnt[i][1] / 1000);
		uart_puts("k\n");
	}
	uart_puts("  IPIs received: core0="); uart_putu(ulIpiCount[0]);
	uart_puts(" core1="); uart_putu(ulIpiCount[1]); uart_puts("\n");
	board_exit();
}

int main(void)
{
	board_primary_init();
	for (uint32_t i = 0; i < 3; i++) {
		xTaskCreate(busy, nm[i], 256, (void *)i, 3 - i, &h[i]);
	}
#ifdef PIN_HM_CORE0                               /* H와 M을 core0에만 허용 */
	vTaskCoreAffinitySet(h[0], 1 << 0);
	vTaskCoreAffinitySet(h[1], 1 << 0);
#endif
	xTaskCreate(monitor, "mon", 512, NULL, 6, NULL);
	vTaskStartScheduler();
	for (;;) { }
}
```

출력에서 볼 것:

- **RMP=1**: H와 M이 각 코어를 하나씩 차지하고 L(가장 낮음)은 0번 — "가장 높은 2개가 돈다". 단일 코어였다면 M도 굶었을 것이다. M이 H와 **동시에** 돈다는 게 SMP의 핵심 변화다.
- **RMP=0**: H만 돈다. 코어 하나는 **idle**이다. M은 ready인데도 못 돈다 — "다른 우선순위 태스크는 동시에 돌지 않는다"를 지키려고 코어를 놀린다. 단일 코어 시절의 "높은 게 돌면 낮은 건 안 돈다" 가정을 지켜 주는 대신 처리량을 버린다. FreeRTOS 문서도 이 설정이 코어를 놀릴 수 있다고 적는다.
- **RMP=1 + H·M을 core0에 고정**: core0에서는 H가 M을 밀어내고(M 0번), core1은 **L**이 차지한다. 우선순위로는 M > L인데 L이 돈다. "가장 높은 N개"는 **affinity를 만족하는 범위에서** 고르기 때문이다. affinity를 잘못 주면 우선순위 역전처럼 보이는 일이 생긴다.
- 루프 횟수의 절대값(약 47만 회 / 100 ms)은 QEMU가 M33을 호스트 속도로 돌린 값이라 의미 없다. IPI가 1번씩인 건 시작 직후 monitor 태스크 배치 때문이다.

### 4.4 RP2040 포트는 어떻게 하나 (코드 읽기)

실제 듀얼코어 MCU 포트는 하드웨어 기능을 그대로 쓴다. `portable/ThirdParty/GCC/RP2040`:

- 락: RP2040 SIO 블록의 **하드웨어 스핀락**(읽으면 획득 시도, 쓰면 해제) 두 개. Cortex-M0+에는 LDREX/STREX가 없어서 소프트웨어만으로는 스핀락을 못 만든다 — 그래서 칩에 하드웨어 스핀락이 들어갔다.
- IPI: 코어 간 FIFO에 아무 값이나 쓰면 상대 코어에 FIFO 인터럽트가 걸린다. 그 핸들러가 재스케줄한다.
- AN521에서 내가 한 "타이머로 IPI"와 구조가 같다. 칩마다 "상대 코어에 인터럽트를 거는 방법"만 다르다.

### 4.5 예제 7 — FreeRTOS SMP에서 `vTaskSuspendAll` 관용구

무엇을 확인하나: §3.3의 Zephyr 실험을 FreeRTOS SMP로. H(prio 3, core0)는 "나보다 높은 건 없다"로 잠금 없이, L(prio 1, core1)은 `vTaskSuspendAll()`로 보호할 때 / 둘 다 `vTaskSuspendAll()` / 둘 다 `taskENTER_CRITICAL()`.

```c
/* main_race.c: FreeRTOS SMP — 단일 코어에서 안전하던 vTaskSuspendAll 관용구가 코어 둘에서는? */
#include "FreeRTOS.h"
#include "task.h"
void uart_puts(const char *s); void uart_putu(uint32_t v); void board_exit(void);
void board_primary_init(void);
#define ROUNDS 100
#define BURST  2000
static volatile uint32_t shared;
static volatile int finished;

static void bump(void) { for (int j = 0; j < BURST; j++) { shared++; } }

static void guarded(int is_high)
{
#if MODE == 2
	(void)is_high; taskENTER_CRITICAL(); bump(); taskEXIT_CRITICAL();
#else
	if (is_high && MODE == 0) { bump(); return; }   /* "나보다 높은 건 없다" */
	vTaskSuspendAll(); bump(); (void)xTaskResumeAll();
#endif
}
static void high(void *p)   /* prio 3, core0 */
{
	(void)p;
	for (int r = 0; r < ROUNDS; r++) { guarded(1); vTaskDelay(1); }
	finished++;  /* 두 태스크가 동시에 끝나지 않으므로 여기서는 문제없음 */
	vTaskSuspend(NULL);
}
static void low(void *p)    /* prio 1, core1 */
{
	(void)p;
	for (int r = 0; r < ROUNDS; r++) { guarded(0); for (volatile int k = 0; k < 3000; k++) { } }
	while (finished == 0) { }
	uart_puts(LABEL); uart_puts(": shared="); uart_putu(shared);
	uart_puts(" expected="); uart_putu(2 * ROUNDS * BURST);
	uart_puts(" lost="); uart_putu(2 * ROUNDS * BURST - shared); uart_puts("\n");
	board_exit();
}
int main(void)
{
	TaskHandle_t hH, hL;
	board_primary_init();
	xTaskCreate(high, "H", 256, NULL, 3, &hH);
	xTaskCreate(low, "L", 256, NULL, 1, &hL);
	vTaskCoreAffinitySet(hH, 1 << 0);
	vTaskCoreAffinitySet(hL, 1 << 1);
	vTaskStartScheduler();
	for (;;) { }
}
```

```text
H-nolock+L-SuspendAll: shared=398268 expected=400000 lost=1732
H-nolock+L-SuspendAll: shared=398484 expected=400000 lost=1516
both-SuspendAll: shared=400000 expected=400000 lost=0
both-SuspendAll: shared=400000 expected=400000 lost=0
both-ENTER_CRITICAL: shared=400000 expected=400000 lost=0
both-ENTER_CRITICAL: shared=400000 expected=400000 lost=0
```

(모드마다 두 번 실행. 각 줄 뒤 `qemu exit=0`은 생략.)

출력에서 볼 것:

- **"H 잠금 없음 + L SuspendAll"은 깨진다** — Zephyr와 같다. 우선순위는 배제가 아니다.
- **"둘 다 SuspendAll"은 안전하다** — Zephyr의 "둘 다 `k_sched_lock`"(§3.3, 1만~2만 손실)과 **다르다**. SMP `vTaskSuspendAll()`은 `portGET_TASK_LOCK()`(전역 재진입 스핀락)을 잡고 `xTaskResumeAll()`까지 놓지 않기 때문이다(아래 §5.2 소스). 다른 코어가 `vTaskSuspendAll()`이나 `taskENTER_CRITICAL()`을 부르면 그 락에서 돈다. 즉 FreeRTOS SMP의 `vTaskSuspendAll`은 사실상 **전역 커널 락**이다 — 안전하지만, 오래 쥐면 다른 코어의 모든 커널 호출이 멈춘다.
- 결론: 이식할 때 "`vTaskSuspendAll`로 보호하던 데이터"는 **그 데이터를 만지는 모든 곳이 같은 수단을 쓰는지** 확인한다. 한 곳이라도 "나는 높으니까 괜찮다"면 SMP에서 깨진다.

## 5. SMP에서 크리티컬 섹션 = 인터럽트 마스크 + 스핀락

> 단일 코어 크리티컬 섹션(BASEPRI, 중첩 카운트)은 C7이 다룬다. 스핀락 개념은 EL F4. 여기서는 **FreeRTOS SMP가 두 락을 어떻게 쓰는지**만 소스로 읽는다.

### 5.1 왜 인터럽트 마스크만으로는 부족한가

단일 코어에서 `taskENTER_CRITICAL()`은 "BASEPRI를 올려 커널 인터럽트를 막는다"였다. 이 코어에서 커널 자료구조를 만질 수 있는 다른 주체는 ISR뿐이니 그걸로 충분했다. 코어가 둘이면 **다른 코어의 태스크와 ISR**이 같은 `pxReadyTasksLists`를 만질 수 있다. 내 코어의 인터럽트 마스크는 저쪽 코어에 아무 효과가 없다. 그래서 둘 다 해야 한다.

- 인터럽트 마스크: **내 코어**의 ISR이 끼어드는 것을 막는다 (그리고 락을 쥔 채 ISR에서 같은 락을 잡는 self-deadlock을 막는다).
- 스핀락: **다른 코어**가 같은 자료구조에 들어오는 것을 막는다.

`tasks.c`(V11.3.2)의 SMP `vTaskEnterCritical()`:

```c
void vTaskEnterCritical( void )
{
    portDISABLE_INTERRUPTS();
    {
        const BaseType_t xCoreID = ( BaseType_t ) portGET_CORE_ID();
        if( xSchedulerRunning != pdFALSE )
        {
            if( portGET_CRITICAL_NESTING_COUNT( xCoreID ) == 0U )
            {
                portGET_TASK_LOCK( xCoreID );
                portGET_ISR_LOCK( xCoreID );
            }
            portINCREMENT_CRITICAL_NESTING_COUNT( xCoreID );

            if( portGET_CRITICAL_NESTING_COUNT( xCoreID ) == 1U )
            {
                portASSERT_IF_IN_ISR();
                if( uxSchedulerSuspended == 0U )
                {
                    prvCheckForRunStateChange();
                }
            }
        }
    }
}
```

(trace 매크로와 주석은 뺐다.)

그리고 ISR용:

```c
UBaseType_t vTaskEnterCriticalFromISR( void )
{
    UBaseType_t uxSavedInterruptStatus = 0;
    const BaseType_t xCoreID = ( BaseType_t ) portGET_CORE_ID();
    if( xSchedulerRunning != pdFALSE )
    {
        uxSavedInterruptStatus = portSET_INTERRUPT_MASK_FROM_ISR();
        if( portGET_CRITICAL_NESTING_COUNT( xCoreID ) == 0U )
        {
            portGET_ISR_LOCK( xCoreID );
        }
        portINCREMENT_CRITICAL_NESTING_COUNT( xCoreID );
    }
    return uxSavedInterruptStatus;
}
```

읽는 법:

- **락이 둘인 이유**: 커널 상태 중에는 태스크만 만지는 것(태스크 생성 · 삭제, 스케줄러 일시 정지 상태)과 ISR도 만지는 것(ready list, 이벤트 리스트)이 섞여 있다. **task lock**은 "태스크 쪽 커널 작업을 한 번에 한 코어만", **ISR lock**은 "ISR까지 포함해서 한 번에 한 코어만"이다. ISR은 ISR lock만 잡으므로, 어떤 코어가 `vTaskSuspendAll()`로 task lock만 오래 쥐고 있어도 **다른 코어의 ISR은 `xxxFromISR` API를 계속 쓸 수 있다**. 둘을 하나로 합치면 그 ISR이 오래 막힌다.
- **잡는 순서가 항상 task → ISR**이다. 순서가 고정되어야 두 코어가 서로 반대 순서로 잡아 데드락하는 일이 없다(락 순서 규칙, EL F4).
- **중첩 카운트가 코어별**이다(`portGET_CRITICAL_NESTING_COUNT( xCoreID )`). 처음 들어갈 때(0 → 1)만 락을 잡고, 마지막에 나갈 때(1 → 0)만 놓는다. 그래서 락 자체는 같은 코어에서 다시 잡을 필요가 없다 — 그래도 포트의 락 함수는 **재진입(recursive)**으로 만들어져 있다(아래 `vPortRecursiveLock`). Zephyr `k_spinlock`은 재진입이 **안 된다**(Zephyr SMP 문서: 같은 스핀락을 중첩해 잡으면 안 된다) — 두 커널의 차이다.
- **`prvCheckForRunStateChange()`**: 크리티컬 섹션에 막 들어왔는데, 그 사이 다른 코어가 "너 양보해"(`xTaskRunState == taskTASK_SCHEDULED_TO_YIELD`)를 걸어 뒀으면? 락을 쥔 채로는 양보할 수 없으니, **락을 모두 놓고 → 인터럽트를 잠깐 켜서 대기 중인 IPI를 받아 양보하고 → 다시 돌아와 인터럽트를 끄고 → 코어 번호를 다시 읽고(이제 다른 코어일 수 있다) → 락을 다시 잡는다.** 이 루프가 없으면 양보 요청을 받은 태스크가 크리티컬 섹션 안에서 계속 돌아, 더 높은 태스크가 그 코어를 못 얻는다.

```c
/* tasks.c prvCheckForRunStateChange() 핵심 */
while( pxThisTCB->xTaskRunState == taskTASK_SCHEDULED_TO_YIELD )
{
    uxPrevCriticalNesting = portGET_CRITICAL_NESTING_COUNT( xCoreID );
    if( uxPrevCriticalNesting > 0U ) { portSET_CRITICAL_NESTING_COUNT( xCoreID, 0U ); portRELEASE_ISR_LOCK( xCoreID ); }
    portRELEASE_TASK_LOCK( xCoreID );
    portMEMORY_BARRIER();
    portENABLE_INTERRUPTS();       /* 여기서 대기 중이던 IPI → PendSV → 양보 */
    portDISABLE_INTERRUPTS();
    xCoreID = ( BaseType_t ) portGET_CORE_ID();   /* 다른 코어에서 깨어났을 수 있다 */
    portGET_TASK_LOCK( xCoreID );
    portGET_ISR_LOCK( xCoreID );
    portSET_CRITICAL_NESTING_COUNT( xCoreID, uxPrevCriticalNesting );
    if( uxPrevCriticalNesting == 0U ) { portRELEASE_ISR_LOCK( xCoreID ); }
}
```

- **나갈 때**(`vTaskExitCritical`): 중첩이 0이 되면 `xYieldPendings[ xCoreID ]`를 **락을 쥔 상태에서** 읽어 두고, ISR lock → task lock 순으로 놓고, 인터럽트를 켠 뒤, 양보가 미뤄져 있었으면 `portYIELD()`. `prvYieldCore()`가 자기 코어에 대해 IPI 대신 `xYieldPendings`만 세우는 이유가 이것이다 — 크리티컬 섹션 안에서는 양보할 수 없으니 나갈 때 한다.
- **`vTaskSuspendAll()`(SMP)**: 인터럽트 마스크 → `portGET_TASK_LOCK` → (필요하면 `prvCheckForRunStateChange`) → `portGET_ISR_LOCK` → `++uxSchedulerSuspended` → ISR lock만 놓고 인터럽트 복원. **task lock은 쥔 채로 돌아온다.** `xTaskResumeAll()`에서야 놓는다(`tasks.c` 4089행 부근). 예제 7에서 "둘 다 SuspendAll"이 안전했던 이유이고, 동시에 "SuspendAll 구간이 길면 다른 코어의 모든 커널 API가 멈춘다"는 비용이다.

## 6. IPI — 다른 코어에게 "다시 골라"라고 알리기

### 6.1 왜 필요한가

코어 0의 태스크가 세마포어를 give해서, 코어 1에서만 돌 수 있는(또는 코어 1이 가장 낮은 태스크를 돌리고 있는) 높은 태스크가 ready가 됐다고 하자. 커널은 이 사실을 코어 0에서 알았다. 코어 1은 지금 낮은 태스크를 신나게 돌리는 중이고 커널에 들어올 일이 없다. **코어 1을 인터럽트하지 않으면** 코어 1은 다음 tick(그나마 tick이 그 코어에 있다면)까지, 또는 지금 태스크가 스스로 블록할 때까지 모른다. 그래서 커널은 코어 1에 인터럽트를 건다 — **IPI(Inter-Processor Interrupt)**. Arm GIC에서는 SGI(Software Generated Interrupt), Cortex-M 멀티코어 칩에서는 MHU doorbell · 코어 간 FIFO 같은 칩 고유 장치다.

### 6.2 예제 9 — FreeRTOS SMP: IPI가 있을 때와 없을 때

무엇을 확인하나: core1에 바쁜 낮은 태스크 L(prio 1)이 있고, 같은 core1에 고정된 W(prio 4)가 알림을 기다린다. core0의 G(prio 2)가 5 tick마다 `xTaskNotifyGive(W)`. `vInterruptCore()`를 구현했을 때와 비워 뒀을 때(포트 weak stub과 같음) W가 몇 번 깨어나나, 얼마나 걸리나.

```c
/* main_ipi.c: core0의 태스크가 core1의 고우선순위 태스크를 깨운다 — IPI가 있을 때/없을 때 */
#include "FreeRTOS.h"
#include "task.h"
void uart_puts(const char *s); void uart_putu(uint32_t v); void board_exit(void);
void board_primary_init(void);
extern volatile uint32_t ulIpiCount[2];
#define DT_VALUE (*(volatile uint32_t *)0x50002004u)     /* DUALTIMER1, 감소 카운터 */
static TaskHandle_t hW;
static volatile uint32_t t_give, wakes, lat_min = 0xFFFFFFFF, lat_max, lat_sum;

static void low_busy(void *p) { (void)p; for (;;) { } }      /* prio1, core1 점유 */
static void waiter(void *p)                                    /* prio4, core1 */
{
	(void)p;
	for (;;) {
		ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
		uint32_t d = t_give - DT_VALUE;                        /* 감소 카운터라 give - now */
		wakes++; lat_sum += d;
		if (d < lat_min) { lat_min = d; }
		if (d > lat_max) { lat_max = d; }
	}
}
static void giver(void *p)                                     /* prio2, core0 */
{
	(void)p;
	uint32_t t_start = DT_VALUE;
	for (int i = 0; i < 20; i++) {
		vTaskDelay(5);
		t_give = DT_VALUE;
		xTaskNotifyGive(hW);              /* 내부: prvYieldForTask → portYIELD_CORE(1) */
	}
	uart_puts("100 ticks = "); uart_putu((t_start - DT_VALUE) / 20); uart_puts(" us by DUALTIMER\n");
	vTaskDelay(10);
	uart_puts(IPI_LABEL); uart_puts(": waiter woke "); uart_putu(wakes);
	uart_puts("/20, latency(us) min "); uart_putu(wakes ? lat_min / 20 : 0);
	uart_puts(" avg "); uart_putu(wakes ? lat_sum / wakes / 20 : 0);
	uart_puts(" max "); uart_putu(lat_max / 20);
	uart_puts(" | IPIs core0="); uart_putu(ulIpiCount[0]);
	uart_puts(" core1="); uart_putu(ulIpiCount[1]); uart_puts("\n");
	board_exit();
}

int main(void)
{
	TaskHandle_t hL, hG;
	board_primary_init();
	*(volatile uint32_t *)0x50002000u = 0xFFFFFFFFu;            /* Timer1Load */
	*(volatile uint32_t *)0x50002008u = (1u << 7) | (1u << 1);  /* enable, 32-bit, free-run */
	xTaskCreate(low_busy, "L", 256, NULL, 1, &hL);
	xTaskCreate(waiter, "W", 256, NULL, 4, &hW);
	xTaskCreate(giver, "G", 512, NULL, 2, &hG);
	vTaskCoreAffinitySet(hL, 1 << 1);
	vTaskCoreAffinitySet(hW, 1 << 1);
	vTaskCoreAffinitySet(hG, 1 << 0);
	vTaskStartScheduler();
	for (;;) { }
}
```

- **IPI 없음: 0/20.** W는 한 번도 못 돈다. 커널은 `prvYieldCore(1)`에서 core1의 L을 `taskTASK_SCHEDULED_TO_YIELD`로 표시하고 `portYIELD_CORE(1)`을 불렀지만 아무 일도 안 일어났다. 게다가 이 포트에서 **SysTick은 primary 코어에만** 설정된다(`xPortStartScheduler()`가 `vPortSetupTimerInterrupt()`를 primary에서만 부른다) — core1에는 tick도 없다. 바쁜 L이 스스로 블록하지 않는 한 core1은 영원히 재스케줄하지 않는다. "IPI는 최적화가 아니라 **정확성**의 일부"라는 증거다.
- 포트가 `vInterruptCore`를 **weak stub**으로 둔 것(링크는 되는데 아무 일도 안 한다)은 함정이다. 보드 bring-up 때 이걸 빼먹으면 "가끔 높은 태스크가 늦게 돈다"(tick이 있는 코어로 우연히 옮겨질 때만 돈다)는 증상이 난다.

### 6.3 Zephyr의 IPI 경로

```text

   └ flag_ipi(ipi_mask_create(thread))     # kernel/ipi.c: _kernel.pending_ipi 비트 OR (atomic)
... 스케줄 지점에서 (스케줄러 락을 쥔 채)
   └ signal_pending_ipi()                   # pending_ipi를 atomic_clear로 꺼내
        ├ CONFIG_ARCH_HAS_DIRECTED_IPIS → arch_sched_directed_ipi(cpu_bitmap)
        └ 아니면                         → arch_sched_broadcast_ipi()
arm64: send_ipi(SGI_SCHED_IPI = SGI 0, mask)  # arch/arm64/core/smp.c
받는 CPU: sched_ipi_handler() → z_sched_ipi() → (ISR 끝에서) 재스케줄
```

`ipi_mask_create()`(kernel/ipi.c)가 **누구에게 보낼지**를 정한다. `CONFIG_IPI_OPTIMIZE=n`(기본)이면 그냥 "나 빼고 전부"(`IPI_ALL_CPUS_MASK`). `=y`이면 각 CPU에 대해 "그 CPU의 현재 스레드가 새 스레드보다 낮고 선점 가능하고, 새 스레드의 `cpu_mask`가 그 CPU를 허락하는가"를 따져 필요한 CPU만 고른다. 관련 Kconfig(`kernel/Kconfig.smp`에서 확인): `SCHED_IPI_SUPPORTED`(아키텍처가 선택), `IPI_OPTIMIZE`, `SCHED_IPI_CASCADE`(CPU mask 사용 시 연쇄 IPI로 국소적 스케줄 오류 보정), `TRACE_SCHED_IPI`(테스트용: `z_sched_ipi()` 안에서 `z_trace_sched_ipi()` 훅 호출).

```c
/* ex5: 다른 코어의 스레드를 깨우면 IPI가 간다 — 개수와 깨어남 지연 */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>

#define ITER 200
#define STK  2048
static volatile uint32_t ipi_cnt[2];
void z_trace_sched_ipi(void) { ipi_cnt[arch_curr_cpu()->id]++; }  /* IPI 핸들러 안 */

K_THREAD_STACK_DEFINE(s_w, STK); K_THREAD_STACK_DEFINE(s_g, STK); K_THREAD_STACK_DEFINE(s_l, STK);
static struct k_thread t_w, t_g, t_l;
static K_SEM_DEFINE(sem, 0, 1);
static volatile uint64_t t_give;
static uint32_t lat[ITER];
static volatile int stop;

static void waiter(void *a, void *b, void *c)          /* prio 2 */
{
	for (int i = 0; i < ITER; i++) {
		k_sem_take(&sem, K_FOREVER);
		lat[i] = (uint32_t)k_cyc_to_ns_floor64(k_cycle_get_64() - t_give);
	}
}
static void giver(void *a, void *b, void *c)           /* prio 5, cpu0 */
{
	for (int i = 0; i < ITER; i++) {
		k_msleep(1);
		t_give = k_cycle_get_64();
		k_sem_give(&sem);
	}
}
static void busy(void *a, void *b, void *c)            /* prio 10, cpu1을 계속 점유 */
{
	while (!stop) { }
}

static void run(int wcpu)
{
	uint32_t i0 = ipi_cnt[0], i1 = ipi_cnt[1];
	stop = 0;
	k_thread_create(&t_l, s_l, STK, busy, NULL, NULL, NULL, 10, 0, K_FOREVER);
	k_thread_create(&t_w, s_w, STK, waiter, NULL, NULL, NULL, 2, 0, K_FOREVER);
	k_thread_create(&t_g, s_g, STK, giver, NULL, NULL, NULL, 5, 0, K_FOREVER);
	k_thread_cpu_pin(&t_l, 1); k_thread_cpu_pin(&t_w, wcpu); k_thread_cpu_pin(&t_g, 0);
	k_thread_start(&t_l); k_thread_start(&t_w); k_thread_start(&t_g);
	k_thread_join(&t_w, K_FOREVER); k_thread_join(&t_g, K_FOREVER);
	stop = 1; k_thread_join(&t_l, K_FOREVER);
	uint32_t mn = UINT32_MAX, mx = 0; uint64_t sum = 0;
	for (int i = 0; i < ITER; i++) {
		mn = MIN(mn, lat[i]); mx = MAX(mx, lat[i]); sum += lat[i];
	}
	printk("waiter on cpu%d: wake latency min %5u avg %5u max %6u ns | IPIs cpu0 %u cpu1 %u\n",
	       wcpu, mn, (uint32_t)(sum / ITER), mx, ipi_cnt[0] - i0, ipi_cnt[1] - i1);
	for (int i = 0; i < ITER; i += 1) { printk("L%d %u\n", wcpu, lat[i]); }
}

int main(void)
{
	printk("IPI_OPTIMIZE=%d\n", IS_ENABLED(CONFIG_IPI_OPTIMIZE));
	run(0);   /* 같은 코어(cpu0)에서 깨움: IPI 불필요 */
	run(1);   /* 다른 코어(cpu1)의 스레드를 깨움: IPI로 cpu1을 재스케줄 */
	return 0;
}
```

그림 6 — 예제 10 측정. 왼쪽: cpu1이 받은 IPI 수(깨움 200회). 오른쪽: `IPI_OPTIMIZE=y`에서 같은 코어 / 다른 코어 깨어남 지연(ns를 µs로).

출력에서 볼 것:

- **`IPI_OPTIMIZE=n`이면 waiter가 cpu0에 있어도 cpu1이 IPI를 370번 받는다.** 스레드가 ready가 될 때마다(giver의 `k_msleep` 만료, waiter의 깨어남 등) "나 빼고 전부"에게 broadcast하기 때문이다. cpu1의 바쁜 스레드는 쓸데없이 매번 인터럽트되어 스케줄러를 돌고 같은 스레드로 돌아간다 — 실제 제품이라면 **cpu1에서 도는 hard RT 루프에 지터**를 넣는 원인이다.
- **`IPI_OPTIMIZE=y`이면 같은 코어 깨움 때 cpu1 IPI가 21번**으로 줄고, 다른 코어 깨움 때는 **정확히 200번**(깨움 한 번에 하나).
- 지연: 같은 코어 p50 약 5 µs, 다른 코어(IPI 경유) p50 약 32 µs. **다른 코어로 깨우는 쪽이 한 단계 더 비싸다.** 다만 이 차이의 대부분은 QEMU가 SGI를 다른 vCPU 스레드로 전달하는 비용이다. 실제 Cortex-A/R + GIC에서 SGI 전달은 보통 이보다 훨씬 짧다 — 이 노트에서 재지 못했으므로 숫자는 쓰지 않는다. 확실한 건 **같은 코어 깨움(IPI 없음) < 다른 코어 깨움(IPI 경유)**이라는 순서다.
- 설계 교훈: 지연에 민감한 "깨우는 쪽 · 깨어나는 쪽" 쌍(예: IMU ISR → 자세 제어 태스크)은 **같은 코어에 두는 것**이 지연과 지터 모두에 유리하다. 그리고 hard RT 코어에 쓸데없는 IPI가 가지 않게 한다(`IPI_OPTIMIZE`, 그 코어에 다른 스레드를 안 둠).

### 7.1 API

| 커널 | API | Kconfig / config | 규칙 |
|---|---|---|---|
| Zephyr | `k_thread_cpu_mask_clear/enable_all/enable/disable`, `k_thread_cpu_pin(thread, cpu)` | `CONFIG_SCHED_CPU_MASK` (SIMPLE 스케줄러 필요) | 스레드가 **실행 가능하지 않을 때만** 바꿀 수 있다(`kernel/cpu_mask.c`: 아니면 `-EINVAL`). 보통 `K_FOREVER`로 만들고 → 마스크 → `k_thread_start` |
| Zephyr | 위 + 코어별 run queue | `CONFIG_SCHED_CPU_MASK_PIN_ONLY` | 스레드마다 CPU 하나만, 시작 전에만 |
| FreeRTOS | `vTaskCoreAffinitySet(task, mask)`, `vTaskCoreAffinityGet`, `xTaskCreateAffinitySet` | `configUSE_CORE_AFFINITY = 1` | 실행 중에도 바꿀 수 있다. 바꾼 결과 지금 코어가 허락되지 않으면 그 코어에 양보를 건다(`tasks.c` `vTaskCoreAffinitySet`의 `prvYieldCore`) |

### 7.2 예제 11 — 코어별 간트를 trace 훅으로 그리기 + migration 세기

무엇을 확인하나: 같은 우선순위 계산 스레드 A · B · C(각 30 ms)가 2코어에서 time slice(2 ms)로 돌 때 실제로 어느 CPU에서 언제 돌았나, 몇 번 옮겨 다녔나. 그리고 A를 cpu1 전용으로, B · C를 cpu0으로 pin하면 어떻게 바뀌나.

방법: `CONFIG_TRACING_USER=y`면 커널이 컨텍스트 스위치 때 `sys_trace_thread_switched_in_user()`(weak 함수)를 부른다. arm64에서는 `arch/arm64/core/switch.S`가 새 스레드로 바꾼 직후 `z_thread_mark_switched_in()`을 부르고, 그게 이 훅까지 온다. 훅 안에서 (시각, CPU, 현재 스레드)를 **CPU별 배열**에 적는다 — CPU별이라 락이 필요 없다.

```text
# ex4/prj.conf
CONFIG_PRINTK=y
CONFIG_SCHED_CPU_MASK=y
CONFIG_TRACING=y
CONFIG_TRACING_USER=y
CONFIG_SYS_CLOCK_TICKS_PER_SEC=1000
CONFIG_TIMESLICING=y
CONFIG_TIMESLICE_SIZE=2
```

```c
/* ex4: switched_in 훅으로 코어별 간트 기록 + migration 수, 고정(pin) 전후 비교 */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>
#include <string.h>
#define NEV 400
#define STK 2048
struct ev { uint32_t t; struct k_thread *th; };
static struct ev evs[2][NEV];
static volatile uint32_t nev[2];
static volatile int rec;
static uint64_t t0;
void sys_trace_thread_switched_in_user(void)      /* 스위치 경로에서 불린다 */
{
	int c = arch_curr_cpu()->id;
	if (rec && nev[c] < NEV) {
		evs[c][nev[c]].t = (uint32_t)(k_cycle_get_64() - t0);
		evs[c][nev[c]++].th = arch_curr_cpu()->current;
	}
}
K_THREAD_STACK_ARRAY_DEFINE(stk, 3, STK);
static struct k_thread th[3];
static void work(void *a, void *b, void *c)
{
	for (int i = 0; i < 60; i++) {
		k_busy_wait(500);                  /* 총 30 ms 계산 */
	}
}
static void run(bool pin)
{
	memset((void *)nev, 0, sizeof(nev));
	for (int i = 0; i < 3; i++) {
		k_thread_create(&th[i], stk[i], STK, work, NULL, NULL, NULL, 5, 0, K_FOREVER);
		if (pin) {                         /* A는 cpu1 전용, B·C는 cpu0 */
			k_thread_cpu_pin(&th[i], i == 0 ? 1 : 0);
		}
	}
	t0 = k_cycle_get_64(); rec = 1;
	for (int i = 0; i < 3; i++) {
		k_thread_start(&th[i]);
	}
	for (int i = 0; i < 3; i++) {
		k_thread_join(&th[i], K_FOREVER);
	}
	rec = 0;
	int last[3] = {-1, -1, -1}, mig[3] = {0};
	printk("--- pin=%d nev=%u/%u\n", pin, nev[0], nev[1]);
	for (int c = 0; c < 2; c++) {
		for (uint32_t k = 0; k < nev[c]; k++) {
			struct k_thread *t = evs[c][k].th;
			const char *n = (t == &th[0]) ? "A" : (t == &th[1]) ? "B" :
					(t == &th[2]) ? "C" : "other";
			printk("EV %d %u %s\n", c, (uint32_t)(evs[c][k].t / 62U), n);
		}
	}
	/* migration: 시간순으로 합쳐 같은 스레드가 다른 cpu에서 다시 시작된 횟수 */
	uint32_t i0 = 0, i1 = 0;
	while (i0 < nev[0] || i1 < nev[1]) {
		int c = (i1 >= nev[1] || (i0 < nev[0] && evs[0][i0].t < evs[1][i1].t)) ? 0 : 1;
		struct k_thread *t = evs[c][c ? i1++ : i0++].th;
		for (int i = 0; i < 3; i++) {
			if (t == &th[i]) { if (last[i] >= 0 && last[i] != c) mig[i]++; last[i] = c; }
		}
	}
	printk("migrations A=%d B=%d C=%d, switches cpu0=%u cpu1=%u\n",
	       mig[0], mig[1], mig[2], nev[0], nev[1]);
}
int main(void)
{
	run(false);
	run(true);
	return 0;
}
```

그림 7 — 예제 11의 실제 스위치 기록으로 그린 코어별 간트. 위: 고정 없음 — A · B · C가 2 ms time slice마다 두 CPU를 번갈아 옮겨 다닌다. 아래: A를 cpu1에 고정 — A는 30 ms 동안 한 번도 끊기지 않고, B · C는 cpu0에서 나눠 쓴다.

출력에서 볼 것:

- **고정 없음: 세 스레드가 합쳐서 22번 CPU를 옮겼다**(A 4, B 13, C 5). 스레드 3개를 CPU 2개에 나누니 time slice가 끝날 때마다 "가장 오래 기다린 스레드"가 비는 CPU에 들어간다. 실제 칩이라면 옮길 때마다 L1 캐시 · 분기 예측기가 식는다. QEMU는 캐시를 모델링하지 않으므로 그 비용은 여기서 보이지 않는다.
- **고정: migration 0.** A는 cpu1에서 46 µs부터 약 30.4 ms까지 **한 번의 스위치도 없이** 돌았다(cpu1 스위치 3번 = A 시작, 끝난 뒤 idle 둘). 대가로 cpu0의 B · C는 각각 30 ms 일을 60 ms에 걸쳐 끝냈다. 전체 완료 시간이 약 49 ms → 58 ms로 늘었다(마지막 스위치 기록 49.1 ms / 57.6 ms). **결정성과 처리량을 맞바꾼 것**이다.
- 함정(직접 겪음): 처음에는 훅에서 `k_current_get()`을 썼는데, 새로 시작하는 스레드의 첫 switch-in이 "other"로 찍혔다. arm64 Zephyr는 `k_current_get()`이 TLS(스레드 로컬 저장소) 기반 값을 읽을 수 있어 스위치 경로 한가운데서는 아직 옛 값일 수 있다. CPU 구조체의 `arch_curr_cpu()->current`(커널이 이미 바꿔 둔 `_current`)를 읽자 정확해졌다. **스위치 훅 안에서는 커널 내부 상태를 직접 읽는 게 안전하다.** (정확한 원인 코드 줄은 확인 못 함 — 현상과 해결만 확인.)

## 8. 성능 — 코어가 둘이면 두 배인가

### 8.1 예제 12 — 같은 일을 1코어 vs 2코어로, 공유 방식별

무엇을 확인하나: 스레드 2개가 각각 100만 번 반복하는 일을, 같은 SMP 커널에서 `CONFIG_MP_MAX_NUM_CPUS` 1과 2로 돌려 시간 비교. 반복마다 (0) 계산만, (1) 공유 `atomic_inc`, (2) 공유 `k_spinlock` + `++`, (3) 스레드별 카운터 `++`.

```text
# ex6/prj.conf
CONFIG_PRINTK=y
CONFIG_SYS_CLOCK_TICKS_PER_SEC=1000
```

```c
/* ex6: 같은 일을 스레드 2개로 — 코어 1개 vs 2개, 공유 방식별 시간 */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>
#include <zephyr/sys/atomic.h>
#define OPS  1000000            /* 스레드당 반복 */
#define STK  2048
K_THREAD_STACK_ARRAY_DEFINE(stk, 2, STK);
static struct k_thread th[2];
static atomic_t shared_at;
static uint32_t shared_sp;
static struct k_spinlock lock;
struct padded { volatile uint32_t v; uint8_t pad[60]; };
static struct padded local[2];  /* 스레드별 카운터, 64B씩 떨어뜨림 */
static volatile uint32_t sink;
static int mode;
static uint64_t c00;
static volatile uint64_t ts[2][2]; static volatile int tc[2];
static void worker(void *p1, void *p2, void *p3)
{
	int me = (int)(uintptr_t)p1;
	ts[me][0] = k_cycle_get_64(); tc[me] = arch_curr_cpu()->id;
	uint32_t x = 12345 + me;
	for (int i = 0; i < OPS; i++) {
		x = x * 1103515245u + 12345u;          /* 계산 몇 명령 */
		if (mode == 1) {
			atomic_inc(&shared_at);
		} else if (mode == 2) {
			k_spinlock_key_t k = k_spin_lock(&lock);
			shared_sp++;
			k_spin_unlock(&lock, k);
		} else if (mode == 3) {
			local[me].v++;
		}
	}
	sink = x;
	ts[me][1] = k_cycle_get_64();
}
static uint32_t run_us(int m)
{
	mode = m;
	uint64_t c0 = k_cycle_get_64(); c00 = c0;
	for (int i = 0; i < 2; i++) {
		k_thread_create(&th[i], stk[i], STK, worker, (void *)(uintptr_t)i,
				NULL, NULL, 5, 0, K_NO_WAIT);
	}
	k_thread_join(&th[0], K_FOREVER);
	k_thread_join(&th[1], K_FOREVER);
	return (uint32_t)(k_cyc_to_ns_floor64(k_cycle_get_64() - c0) / 1000);
}
int main(void)
{
	static const char *nm[4] = {"compute", "atomic", "spinlock", "per-thread"};
	for (int m = 0; m < 4; m++) {
		uint32_t best = UINT32_MAX;
		printk("cpus=%u %-10s runs(us):", arch_num_cpus(), nm[m]);
		for (int r = 0; r < 7; r++) {
			uint32_t us = run_us(m);
			best = MIN(best, us);
			printk(" %u", us);
			if (r == 0) printk("[T0 cpu%d %u-%u T1 cpu%d %u-%u]", tc[0],
				(uint32_t)((ts[0][0]-c00)/62), (uint32_t)((ts[0][1]-c00)/62), tc[1],
```

### 8.2 예제 13 — "스레드별 카운터"인데 왜 두 배가 안 되나: false sharing

예제 12의 per-thread가 ×1.15밖에 안 나온 것이 이상하다. 공유가 없는데? 심볼 주소를 보자:



`mode`(0x...528)와 `local[0].v`(0x...530)가 **같은 64바이트 줄**(0x...500–0x...53F)에 있다. 두 스레드는 매 반복 `mode`를 읽고, 스레드 0은 같은 줄의 `local[0].v`에 쓴다. 쓸 때마다 다른 코어의 그 줄 사본이 무효화된다 — **false sharing**(논리적으로 공유하지 않는 변수가 같은 캐시 라인에 있어 생기는 공유).

QEMU는 게스트 캐시를 모델링하지 않는데 왜 보이나? 게스트 메모리는 결국 호스트 메모리이고, 두 vCPU 스레드는 **호스트의 진짜 코어 두 개**에서 돈다. 호스트 캐시 일관성 비용이 그대로 드러난다. 깨끗하게 확인하는 실험:

```c
/* ex7: 스레드별 카운터인데 왜 느린가 — 두 카운터 사이 거리(stride)를 바꿔 본다 */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>
#define OPS 2000000
#define STK 2048
K_THREAD_STACK_ARRAY_DEFINE(stk, 2, STK);
static struct k_thread th[2];
static uint8_t area[1024] __aligned(256);
static int stride;
static void worker(void *p1, void *p2, void *p3)
{
	volatile uint32_t *c = (volatile uint32_t *)&area[(int)(uintptr_t)p1 * stride];
	for (int i = 0; i < OPS; i++) {
		(*c)++;                        /* 각자 자기 카운터만 쓴다: 논리적 공유 없음 */
	}
}
static uint32_t run_us(void)
{
	uint64_t c0 = k_cycle_get_64();
	for (int i = 0; i < 2; i++) {
		k_thread_create(&th[i], stk[i], STK, worker, (void *)(uintptr_t)i,
				NULL, NULL, 5, 0, K_NO_WAIT);
	}
	k_thread_join(&th[0], K_FOREVER);
	k_thread_join(&th[1], K_FOREVER);
	return (uint32_t)(k_cyc_to_ns_floor64(k_cycle_get_64() - c0) / 1000);
}
int main(void)
{
	static const int s[] = {4, 64, 128, 256};
	for (int k = 0; k < 4; k++) {
		stride = s[k];
		uint32_t best = UINT32_MAX;
		for (int r = 0; r < 7; r++) {
			best = MIN(best, run_us());
		}
		printk("cpus=%u stride=%3d B  best of 7 = %6u us\n", arch_num_cpus(), stride, best);
	}
	return 0;
}
```

```text
cpus=1 stride=128 B  best of 7 =  16461 us
cpus=1 stride=256 B  best of 7 =  16603 us
cpus=2 stride=  4 B  best of 7 =  21820 us
cpus=2 stride= 64 B  best of 7 =   8291 us
cpus=2 stride=128 B  best of 7 =   8244 us
```

### 9.1 SMP(global)의 실시간 약점

- **응답 시간 분석이 어렵다.** 단일 코어 RTA(N3)는 "나보다 높은 태스크만 나를 막는다"에서 출발한다. global SMP에서는 태스크가 어느 코어에서 돌지, 언제 옮겨질지가 다른 모든 태스크에 달려 있다. global 고정 우선순위 스케줄링은 이용률이 낮아도 마감을 놓치는 경우가 있다(Dhall 효과, N8).
- **migration 비용**이 WCET에 들어간다 — 캐시가 식고, 실제 칩에서는 수 µs~수십 µs가 될 수 있다(칩마다 다름, 이 노트에서 실측 못 함).
- **스핀락 대기**가 WCET에 들어간다 — 다른 코어가 커널 락을 쥐고 있으면 내 코어의 커널 호출 · ISR(FromISR API)이 기다린다. FreeRTOS SMP에서 다른 코어의 긴 `vTaskSuspendAll` 구간이 그렇다(§5.2).
- **IPI 지터** — 관계없는 코어 간 깨움이 내 코어에 IPI를 보내 매번 스케줄러를 돌게 한다(예제 10의 `IPI_OPTIMIZE=n`).
- **공유 캐시 · 버스 · 메모리 컨트롤러 간섭** — 다른 코어가 메모리를 세게 쓰면 내 루프의 실행 시간이 늘어난다. 이건 pin을 해도 사라지지 않는다(N8: MemGuard 같은 대역폭 조절, 캐시 파티셔닝).

### 9.2 그래서 실무 규칙

1. **hard RT 루프는 코어 하나에 pin**한다(BMP). 그 코어에는 그 루프와 그 루프의 ISR만 둔다. 예제 11처럼 pin한 스레드는 한 번도 끊기지 않았다.
2. 그 루프를 **깨우는 쪽(ISR · 생산자)도 같은 코어**에 둔다 — 깨움에 IPI가 끼지 않게(예제 10: 같은 코어 p50 약 5 µs vs 다른 코어 약 32 µs, QEMU 기준 순서).
3. **IRQ affinity**도 정리한다 — hard RT 코어에는 그 루프의 IRQ만 라우팅한다(GIC · 칩 인터럽트 라우터 설정).
4. 나머지(통신, 로깅, 파일 시스템, 추론 같은 throughput 일)는 다른 코어(들)에서 global하게 돌린다.
5. 공유 데이터는 **짧은 스핀락 또는 lock-free 큐(SPSC 링버퍼)**로 넘긴다. hard RT 쪽이 블로킹 뮤텍스에서 기다리는 일이 없게.
6. 안전 등급이 다른 일을 섞어야 하면(예: ASIL D 제어 + QM 텔레매트리) **SMP 하나로 묶지 않는다** — 커널 하나의 버그가 둘 다 죽인다. AMP(코어마다 다른 이미지), lockstep 코어, 하이퍼바이저 분할을 검토한다(O5 · O6 · P6).
7. 코어 종류가 다르면(M7 + M4) 선택지는 AMP뿐이다(P4).

### 9.3 FreeRTOS · Zephyr 설정으로 옮기면

| 목표 | FreeRTOS SMP | Zephyr SMP |
|---|---|---|
| 루프 태스크를 코어 1에 고정 | `configUSE_CORE_AFFINITY=1`, `vTaskCoreAffinitySet(h, 1 << 1)` | `CONFIG_SCHED_CPU_MASK=y`, `K_FOREVER`로 생성 → `k_thread_cpu_pin(t, 1)` → `k_thread_start` |
| 다른 태스크는 코어 1 금지 | `configTASK_DEFAULT_CORE_AFFINITY = (1 << 0)` | 각 스레드 `k_thread_cpu_mask_disable(t, 1)` 또는 `PIN_ONLY` 설계 |
| 쓸데없는 IPI 줄이기 | 포트 `vInterruptCore`가 정확히 대상 코어만 (포트 구현) | `CONFIG_IPI_OPTIMIZE=y` |

| 단일 코어 가정 코드 보호 (과도기) | `configRUN_MULTIPLE_PRIORITIES=0` — 코어가 놀 수 있음 (예제 6) | 해당 옵션 없음 — 코드를 고쳐야 함 |

## 11. 실무에서 다시 보기

### 11.1 드론 비행 제어기를 듀얼코어 MCU로 옮길 때

예를 들어 단일 코어 STM32F4급에서 FreeRTOS로 돌던 비행 제어기를 RP2350 같은 듀얼 M33으로 옮긴다고 하자. 흔한 계획: "core1은 IMU 읽기 + 자세 rate loop, core0은 나머지(텔레메트리, GNSS, 로그)".

- 이건 **BMP**다. FreeRTOS SMP라면 rate loop 태스크와 IMU 처리를 `vTaskCoreAffinitySet(h, 1 << 1)`로 core1에 고정하고, 나머지 태스크는 `configTASK_DEFAULT_CORE_AFFINITY`를 core0으로. IMU 데이터 준비 인터럽트도 core1로 라우팅한다(칩의 인터럽트 라우팅 기능).
- 옛 코드에서 "rate loop가 가장 높으니 공유 setpoint 구조체를 락 없이 읽는다"였다면, core0의 텔레메트리 태스크가 **동시에** 그 구조체를 쓸 수 있다. 예제 4 · 7의 버그다. 고치는 법: setpoint는 seqlock(쓰는 쪽이 짝수/홀수 카운터) 또는 더블 버퍼 + atomic 포인터 교체, 또는 아주 짧은 스핀락.
- `configRUN_MULTIPLE_PRIORITIES=0`으로 "일단 옛 가정대로" 돌리면 버그는 숨지만, rate loop가 도는 동안 core0의 낮은 태스크들이 다 멈춘다(예제 6) — 듀얼코어로 옮긴 의미가 없다. 과도기 진단용으로만 쓴다.

### 11.2 로봇 관절 모터 컨트롤러 — 20 kHz FOC는 어디에

- FOC 전류 루프(50 µs 주기)는 보통 **ISR 안에서** 돈다(A7, E1). 듀얼코어라면 그 ISR을 한 코어에 고정하고 그 코어에는 RTOS 태스크를 거의 안 둔다 — 사실상 bare-metal 코어 + RTOS 코어의 AMP/BMP다.
- CAN 통신 · 상태 머신 · 진단은 다른 코어에서. 두 코어 사이 setpoint 전달은 SPSC 링버퍼(Anduril C 문제은행의 그것)나 메일박스.
- 피할 것: 전류 루프 ISR에서 FreeRTOS `FromISR` API를 부르는 것 — SMP에서는 ISR lock을 잡아야 하고(§5.2), 다른 코어가 그 락을 쥐고 있으면 50 µs 예산 안에서 기다리게 된다.

### 11.3 SSD 컨트롤러 — Don의 경험과 Cortex-R82

- Don이 본 SSD 펌웨어는 코어별 역할 분담(AMP)이었다. Cortex-R82는 클러스터 안 하드웨어 일관성을 제공하고 FreeRTOS `ARM_CR82` 포트가 SMP를 지원한다(V11.3.0). 즉 "FTL 작업을 코어 여러 개가 하나의 작업 풀에서 꺼내 처리"하는 SMP 설계가 RTOS 수준에서 가능해졌다.
- 그래도 NAND 채널 타이밍처럼 hard한 부분은 여전히 코어 고정이 맞다. 혼합(BMP + 일부 global 풀)이 현실적이다.
- 면접에서 이렇게 연결할 수 있다: "SSD 펌웨어에서 코어마다 실행부를 돌리고 doorbell로 일을 넘겼다 — 그게 AMP이고, SMP RTOS에서는 그 doorbell이 커널 IPI(`portYIELD_CORE`)가 되고, 공유 큐의 하드웨어 세마포어가 커널 스핀락이 된다."

### 11.4 AI 가속기 SoC의 제어 클러스터

AI 가속기 SoC에는 보통 큰 Linux 클러스터(Cortex-A) 옆에 실시간 제어 코어(Cortex-R/M 또는 RISC-V) 몇 개가 있어 가속기 명령 큐, DMA, 전원 · 클럭, 안전 감시를 맡는다. 이름 있는 제품의 내부 구성은 공개 자료로 확인하지 못했다. 구조적으로는:

- Linux ↔ 제어 코어는 AMP(remoteproc/RPMsg, P5).
- 제어 코어들끼리는 SMP RTOS 하나로 묶을 수도, 코어마다 기능을 나눌 수도 있다. 가속기 작업 디스패치처럼 throughput이 중요한 일은 SMP, 안전 감시는 별도 코어(가능하면 lockstep).
- Rivian 실리콘 검증 같은 직무에서 "이 제어 코어 펌웨어가 SMP인가 AMP인가, IPI는 무엇으로 하나, 코어 간 큐는 어떻게 보호하나"는 bring-up 체크리스트 질문이다.

## 13. 면접에서 이렇게 말한다

**Q.** "What's the difference between AMP and SMP on a multicore MCU, and when would you pick each?"

**A.** AMP는 코어마다 독립 펌웨어(다른 RTOS나 bare-metal)가 돌고 메일박스 · 공유 메모리로 통신한다. SMP는 커널 하나가 같은 종류의 코어 여러 개를 하나의 ready queue로 스케줄한다. 코어 종류가 다르거나(M7 + M4), 안전 등급이 다르거나, 각 코어를 따로 검증해야 하면 AMP. 같은 코어이고 throughput 일을 자동 분산하고 싶으면 SMP. hard RT 루프는 SMP에서도 코어에 고정(BMP)한다.

> AMP runs an independent image per core — different RTOSes or bare-metal — talking through mailboxes and shared memory; SMP runs one kernel image that schedules all identical cores from a shared ready queue. I pick AMP when the cores are heterogeneous, like an M7 plus an M4, or when I need isolation between criticality levels. I pick SMP for throughput work that benefits from load balancing, and even then I pin the hard real-time loop and its interrupt to one core, which is effectively bound multiprocessing.

**꼬리 질문**: "Why can't you run SMP on an STM32H747?" → 코어가 M7과 M4로 ISA · 캐시 · FPU가 달라 같은 이미지를 둘 다에서 돌릴 수 없다.

**Q.** "In FreeRTOS SMP, how is a critical section implemented?"

**A.** 단일 코어에서는 인터럽트 마스크(BASEPRI)뿐이었지만 SMP에서는 다른 코어도 커널 자료구조를 만지므로 스핀락이 필요하다. `vTaskEnterCritical`은 이 코어 인터럽트를 끄고, 코어별 중첩 카운트가 0이면 task lock과 ISR lock을 순서대로 잡는다. ISR 버전은 ISR lock만 잡는다. 락 둘로 나눈 이유는 한 코어가 스케줄러를 일시 정지(task lock 보유)해도 다른 코어 ISR이 FromISR API를 쓸 수 있게 하려는 것. 들어올 때 다른 코어가 양보를 요청해 뒀으면 `prvCheckForRunStateChange`가 락을 풀고 양보한 뒤 다시 잡는다.

> On a single core it's just masking interrupts, but with SMP another core can touch the ready lists, so it becomes interrupt masking plus spinlocks. vTaskEnterCritical disables interrupts on this core and, on the first nesting level, takes the task lock and then the ISR lock — always in that order to avoid deadlock. The FromISR variant only takes the ISR lock, so a core that has suspended the scheduler, holding the task lock, doesn't block interrupt handlers on other cores. The port supplies the locks — LDREX/STREX with WFE/SEV on Armv8-M, hardware spinlocks on the RP2040.

**꼬리 질문**: "Is the lock recursive?" → FreeRTOS 포트 락(`vPortRecursiveLock`)은 소유 코어를 기록해 재진입을 허용한다. Zephyr `k_spinlock`은 재진입이 안 된다.

**Q.** "If a high-priority task is running, can a low-priority task run at the same time?"

**A.** 단일 코어에서는 아니다. SMP에서는 기본적으로 그렇다 — 가장 높은 N개가 돈다. 그래서 우선순위를 상호 배제 수단으로 쓰던 코드가 깨진다. 직접 Zephyr로 재현했을 때 단일 코어에서는 0, 2코어에서는 매번 1만 개 넘게 값을 잃었다. FreeRTOS는 `configRUN_MULTIPLE_PRIORITIES=0`으로 다른 우선순위의 동시 실행을 막을 수 있지만 코어가 논다 — 실험에서 높은 태스크가 도는 동안 다른 코어는 idle이었다.

> On a single core, no. On SMP, yes by default — the scheduler runs the N highest-priority ready tasks, so priority is no longer mutual exclusion. I reproduced it in Zephyr: code that relied on priority plus k_sched_lock lost zero updates on one core and over ten thousand per run on two. FreeRTOS has configRUN_MULTIPLE_PRIORITIES set to zero to keep the old guarantee, but in my test that left the second core idle while the high-priority task ran, so it's a migration crutch, not a design.

**Q.** "What is an IPI and why does an SMP RTOS need it?"

**A.** 다른 코어에 거는 인터럽트다. 코어 0에서 깨운 태스크가 코어 1의 현재 태스크보다 높으면, 코어 1은 커널에 들어올 일이 없으니 인터럽트로 재스케줄을 시켜야 한다. FreeRTOS에서는 `prvYieldForTask`가 선점할 코어를 고르고 `portYIELD_CORE`로 IPI를 보낸다. Cortex-M33 SMP 포트에서 IPI를 비워 둔 채 돌려 보니 다른 코어의 높은 태스크가 20번 중 한 번도 못 깨어났다 — 보조 코어에는 tick도 없었다.

> It's an interrupt one core sends to another. When core 0 readies a task that should preempt what core 1 is running, core 1 has no reason to enter the kernel, so the kernel interrupts it — on FreeRTOS, prvYieldForTask picks the lowest-priority eligible core and calls portYIELD_CORE; on Zephyr, flag_ipi plus signal_pending_ipi end in a GIC SGI on arm64. When I brought up FreeRTOS SMP on a dual Cortex-M33 in QEMU and left the IPI hook empty, a high-priority task on the second core woke zero times out of twenty, because that core didn't even have a tick. So IPIs are about correctness, not just latency.

**꼬리 질문**: "How do you reduce IPI overhead?" → 필요한 코어에만 보낸다(Zephyr `CONFIG_IPI_OPTIMIZE`: 실험에서 불필요한 IPI 370 → 21회), 깨우는 쪽과 깨어나는 쪽을 같은 코어에 둔다.

**Q.** "Would you put a hard real-time control loop on an SMP RTOS?"

**A.** 넣을 수는 있지만 global 스케줄링에 맡기지 않는다. 루프 태스크와 그 IRQ를 한 코어에 고정하고, 그 코어에는 관계없는 태스크 · IRQ · IPI가 안 가게 한다. 생산자 ISR도 같은 코어에 둬서 깨움에 IPI가 끼지 않게 한다. 그래도 공유 캐시 · 버스 간섭은 남으므로 최악 실행 시간은 다른 코어에 부하를 건 상태에서 측정한다. 안전 등급이 다르면 AMP나 lockstep을 쓴다.

> Yes, but not under global scheduling. I'd pin the loop task and its interrupt to one core, keep unrelated tasks, IRQs and IPIs off that core, and put the producer ISR on the same core so the wake-up never needs an IPI — in my measurements a same-core wake was several times faster than a cross-core one. Pinning doesn't remove shared cache and bus interference, so I'd measure worst-case execution time with the other cores loaded. If the loop has a different safety level from the rest, I'd rather use AMP or a lockstep core than share one SMP kernel.

**Q.** "Two threads each increment their own counter on different cores, yet it's slower than one core. Why?"

**A.** false sharing이다. 두 카운터가 같은 캐시 라인에 있으면 쓸 때마다 라인이 두 코어 사이를 오간다. 실험에서 4바이트 간격이면 2코어가 1코어보다 느렸고(×0.78), 64바이트 이상 떨어뜨리자 정확히 두 배가 됐다. 코어별 데이터는 캐시 라인 크기로 정렬 · 패딩한다.

> False sharing: the counters are logically private but sit on the same cache line, so every write invalidates the other core's copy and the line ping-pongs. In my test, counters four bytes apart made two cores slower than one — about 0.78x — and spacing them 64 bytes apart gave a clean 2x. Per-core data should be aligned and padded to the cache line size of the actual part, 32 bytes on a Cortex-M7, 64 on an A53.

**Q.** "How does vTaskSuspendAll behave differently on FreeRTOS SMP compared to Zephyr's k_sched_lock?"

**A.** FreeRTOS SMP의 `vTaskSuspendAll`은 전역 task lock을 잡고 `xTaskResumeAll`까지 쥔다. 그래서 둘 다 SuspendAll을 쓰는 코드는 코어 사이에서도 직렬화된다(실험에서 손실 0). Zephyr `k_sched_lock`은 현재 스레드의 카운트만 올려 이 CPU에서의 선점만 막는다 — 둘 다 써도 다른 CPU에서 동시에 돈다(손실 발생). 둘 다 "잠금 없이 들어오는 코드" 하나만 있으면 깨진다.

> On FreeRTOS SMP, vTaskSuspendAll takes the global task lock and holds it until xTaskResumeAll, so two tasks that both use it are serialized across cores — I measured zero lost updates. Zephyr's k_sched_lock only bumps a per-thread count that stops preemption on the current CPU, so two threads using it on different CPUs still run concurrently and I lost updates every run. In both kernels, a single path that skips the lock breaks it, and on FreeRTOS holding the task lock for long stalls every kernel call on the other cores.

## 14. 직접 해보기

1. **개념** — 3코어 SMP에서 우선순위 5 · 4 · 3 · 2인 바쁜 태스크 넷이 ready다. `configRUN_MULTIPLE_PRIORITIES` 1과 0일 때 각각 무엇이 돌고 몇 코어가 노나? 우선순위 5인 태스크만 core0으로 고정하면?
   정답/힌트: RMP=1이면 5 · 4 · 3이 돌고 2는 대기, 노는 코어 0개. RMP=0이면 5만 돌고 코어 2개가 idle. 5를 core0에 고정해도 RMP=1이면 5(core0) · 4 · 3(나머지)로 같다.

2. **코드** — 예제 4(§3.3)의 "H nolock + L schedlock"을 Zephyr에서 **고치지 말고** 같은 코어에 두 스레드를 pin해서 통과시켜 보라. 무엇을 얻고 무엇을 잃나?
   정답/힌트: `K_FOREVER` 생성 → `k_thread_cpu_pin(&th_h, 0)`, `k_thread_cpu_pin(&th_l, 0)` → `k_thread_start`. 손실 0이 되지만 그 두 스레드는 병렬성을 잃는다 — "같은 코어에 묶으면 단일 코어 가정이 살아난다"는 BMP식 이식 전략.

3. **코드** — FreeRTOS AN521 예제 6에 `vTaskPreemptionDisable(h[1])`(M)을 시작 직후 걸고 H를 잠시 블록시켰다가 깨워 보라(RMP=1). M이 도는 코어를 H가 선점할 수 있나?
   정답/힌트: `prvYieldForTask`는 `xPreemptionDisable == pdFALSE`인 코어만 후보로 고른다. M 코어는 빠지고 다른 코어(L 또는 idle)를 선점한다. `configUSE_TASK_PREEMPTION_DISABLE`는 RMP=1에서만 허용된다.

4. **측정** — 예제 10을 waiter와 giver를 **둘 다 cpu1**에 두고(busy 스레드는 cpu0으로) 다시 재서, "같은 코어" 지연이 CPU 번호와 무관한지 확인하라. `IPI_OPTIMIZE=n/y`에서 이번엔 어느 CPU의 IPI 수가 줄어드나?
   정답/힌트: 같은 코어 지연은 cpu1에서도 p50 수 µs대여야 한다. 불필요한 IPI는 이번엔 cpu0으로 간다.

5. **측정** — 예제 13의 `area`를 `__aligned(256)` 대신 정렬 없이 두고 stride 64로 돌리면 결과가 흔들리나? 왜?
   정답/힌트: 배열 시작이 64바이트 경계가 아니면 stride 64여도 두 카운터가 같은 줄에 걸칠 수 없지만(4바이트 변수), 다른 핫 변수와 같은 줄에 놓일 수 있다 — 예제 12의 `mode` 사례처럼. 링크 배치에 따라 달라진다. 심볼 주소를 `nm`으로 확인.

6. **코드 읽기** — FreeRTOS `tasks.c`에서 `vTaskCoreAffinitySet()`을 읽고, 실행 중인 태스크의 affinity에서 지금 코어를 빼면 어떤 함수로 무엇이 일어나는지 순서대로 적어라.
   정답/힌트: 크리티컬 섹션 → 마스크 갱신 → 그 태스크가 실행 중이고 새 마스크가 지금 코어를 허락하지 않으면 `prvYieldCore( xCoreID )` → (다른 코어면 IPI) → 그 코어가 재스케줄하며 `prvSelectHighestPriorityTask`가 affinity를 보고 다른 태스크를 고름.

7. **설계** — 드론 FC를 듀얼 M33(공유 SRAM, 캐시 없음)으로 옮긴다. IMU ISR(4 kHz), rate loop, attitude loop(500 Hz), 텔레메트리, 로그, GNSS 파서를 어떤 코어에 어떤 방식으로 두고, 코어 간 데이터는 무엇으로 넘길지 한 쪽으로 써 보라.
   정답/힌트: core1 = IMU ISR + rate loop + attitude(pin, 같은 코어 깨움), core0 = 나머지(global 또는 pin). setpoint는 seqlock 또는 더블 버퍼, 로그는 SPSC 링버퍼. 캐시가 없으니 false sharing은 없지만 SRAM 뱅크 경쟁이 있을 수 있다 — 루프 데이터를 다른 뱅크에 두는 것을 검토(칩 데이터시트 확인).

## 15. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| AMP | Asymmetric Multiprocessing | 코어마다 독립된 OS/펌웨어 이미지. 코어 종류가 달라도 된다 |
| SMP | Symmetric Multiprocessing | 커널 하나가 같은 종류 코어 여럿을 하나의 ready queue로 스케줄 |
| BMP | Bound Multiprocessing | SMP 커널 위에서 태스크를 전부 코어에 고정해 쓰는 방식 |
| global scheduling | 전역 스케줄링 | ready queue 하나, 어떤 태스크든 어떤 코어든 |
| partitioned scheduling | 분할 스케줄링 | 코어마다 ready queue, 태스크는 한 코어에 묶임 |
| core affinity | 코어 친화성 | 태스크가 돌 수 있는 코어 집합(비트마스크) |
| pin | 고정 | affinity를 코어 하나로 정하는 것 |
| migration | 코어 이동 | 태스크가 다른 코어에서 다시 시작되는 것. 캐시가 식는다 |
| IPI | Inter-Processor Interrupt | 다른 코어에 거는 인터럽트. SMP 커널은 재스케줄 요청에 쓴다 |
| SGI | Software Generated Interrupt | Arm GIC의 IPI 수단. Zephyr arm64는 SGI 0을 스케줄 IPI로 쓴다 |
| doorbell / MHU | 메일박스 인터럽트 장치 | Cortex-M 멀티코어 칩에서 코어 간 인터럽트를 거는 하드웨어 |
| spinlock | 스핀락 | 잠겨 있으면 돌며 기다리는 락. SMP 크리티컬 섹션의 재료 |
| task lock / ISR lock | FreeRTOS SMP 커널 락 | 태스크 쪽 커널 상태 / ISR과 공유하는 커널 상태를 지키는 두 스핀락 |
| `configRUN_MULTIPLE_PRIORITIES` | FreeRTOS 설정 | 0이면 서로 다른 우선순위 태스크가 동시에 돌지 않는다 (기본 0) |
| `xTaskRunState` | FreeRTOS TCB 필드 | 실행 중인 코어 번호, 또는 NOT_RUNNING / SCHEDULED_TO_YIELD |
| passive idle | FreeRTOS SMP | 코어 0이 아닌 코어의 idle 태스크 |
| `k_sched_lock` | Zephyr API | 현재 스레드를 이 CPU에서 선점되지 않게 함. SMP에서 배제 수단이 아니다 |
| LDREX / STREX | Arm 배타적 접근 명령 | 다른 접근이 끼면 STREX가 실패 — 스핀락 · atomic의 바탕 |
| WFE / SEV | Arm 이벤트 대기 / 보내기 | 스핀락 대기 중 잠들기 · 해제할 때 깨우기 |
| outline atomics | GCC aarch64 기능 | atomic을 함수(`__aarch64_cas8_acq_rel` 등)로 불러 실행 시점에 LSE/LLSC 선택 |
| false sharing | 거짓 공유 | 서로 다른 변수가 같은 캐시 라인에 있어 생기는 코어 간 경쟁 |
| MTTCG | Multi-threaded TCG | QEMU가 vCPU마다 호스트 스레드를 써서 병렬 에뮬레이션하는 방식 |
| lockstep | 락스텝 | 두 코어가 같은 명령을 동시에 실행해 결과를 비교하는 안전 기능 (SMP와 다름) |

## 16. 요약 & 체크리스트

코어가 둘 이상인 MCU에서 실행 방식은 AMP(코어마다 독립 이미지), SMP(커널 하나 · ready queue 하나), BMP(SMP + 전부 고정) 중 하나다. SMP 커널은 "가장 높은 우선순위 N개"를 돌리기 위해 전역 ready queue를 공유하고, 그 때문에 크리티컬 섹션이 인터럽트 마스크 + 스핀락이 되며(FreeRTOS: task lock + ISR lock, Zephyr: `k_spin_lock` = IRQ 마스크 + CAS), 다른 코어의 결정을 바꾸려면 IPI를 보낸다. QEMU에서 직접 재현한 핵심 사실: 우선순위 · `k_sched_lock`으로 배제하던 코드는 단일 코어에서 손실 0, 2코어에서 매번 1만 개 이상을 잃었고, FreeRTOS SMP에서 `configRUN_MULTIPLE_PRIORITIES=0`은 한 코어를 놀렸으며, IPI를 비워 두자 다른 코어의 높은 태스크가 한 번도 깨어나지 못했다. 성능 면에서는 공유가 없으면 거의 선형으로 확장되지만 경쟁하는 atomic · 스핀락 · false sharing은 2코어를 1코어보다 느리게 만들었다(QEMU TCG 기준, 모양만 믿을 것). hard real-time 루프는 SMP에 올리더라도 그 루프와 그 IRQ, 그 생산자를 한 코어에 고정하고, 공유 자원 간섭은 측정으로 확인한다.

- [ ] AMP · SMP · BMP를 정의하고, STM32H747이 왜 AMP뿐인지 말할 수 있다
- [ ] "가장 높은 N개가 돈다"와 `configRUN_MULTIPLE_PRIORITIES` 0/1의 차이를 예제 6 결과로 설명할 수 있다
- [ ] `prvYieldForTask` → `prvYieldCore` → `portYIELD_CORE` 경로와 `xTaskRunState`의 역할을 말할 수 있다
- [ ] SMP `vTaskEnterCritical`이 잡는 두 락과 순서, ISR 버전과의 차이를 그릴 수 있다
- [ ] `prvCheckForRunStateChange`가 왜 락을 풀었다 다시 잡는지 설명할 수 있다
- [ ] Zephyr `k_spin_lock`의 생성 코드(IRQ 마스크 + CAS + relax 루프)를 읽을 수 있다
- [ ] 우선순위 · `k_sched_lock` · `vTaskSuspendAll`이 SMP에서 각각 배제가 되는지/안 되는지 말할 수 있다
- [ ] IPI가 없으면 무슨 일이 생기는지, Zephyr `IPI_OPTIMIZE`가 무엇을 줄이는지 숫자로 말할 수 있다
- [ ] Zephyr · FreeRTOS에서 태스크를 코어에 고정하는 코드를 쓸 수 있다 (생성 시점 규칙 포함)
- [ ] false sharing을 재현 · 진단(`nm`으로 주소 확인) · 수정할 수 있다
- [ ] hard RT 루프를 SMP에 올릴 때의 규칙(pin, 같은 코어 깨움, IRQ affinity, 간섭 측정)을 말할 수 있다
- [ ] QEMU TCG 측정에서 믿을 수 있는 것(현상 · 순서 · 모양)과 없는 것(절대 지연, 메모리 순서, 캐시)을 구분할 수 있다
