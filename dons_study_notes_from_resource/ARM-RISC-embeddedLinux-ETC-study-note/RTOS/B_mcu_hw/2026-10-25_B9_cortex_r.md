# B9. Cortex-R 계열 — "A 코어의 예외 모델 + MCU의 결정성", 하드웨어 스태킹 없는 코어에 RTOS를 올리는 법

> **이 노트를 다 읽으면**: R5 · R52 · R52+ · R82가 어디서 왜 쓰이는지(SSD 컨트롤러 · 자동차 ECU · AI SoC 안전 섬) 설명할 수 있다 · Cortex-R52 bare-metal startup(벡터 테이블, EL2 → EL1, 모드별 스택, GICv3, generic timer)을 처음부터 써서 QEMU에서 돌릴 수 있다 · "하드웨어 스태킹이 없다"는 것이 IRQ 진입 코드와 RTOS 포트에 무슨 일을 시키는지 명령 수로 말할 수 있다 · MPU 2단계(EL1 + EL2), TCM ECC 초기화, lockstep(DCLS)을 펌웨어 쪽 할 일로 정리할 수 있다
> **왜 필요한가**: Rivian 같은 차량 SoC, NVIDIA Orin 같은 AI SoC의 안전 섬, SSD 컨트롤러는 Cortex-M이 아니라 Cortex-R을 쓴다. 면접에서 "Cortex-M 포트와 Cortex-R 포트는 뭐가 다른가?", "R52의 EL2는 왜 있나?", "lockstep 코어에서 startup이 특별히 해야 하는 일은?"이 나오면 Don의 SSD 7년 경험을 RTOS 언어로 번역해서 답해야 한다
> **Don 기준 난이도**: 멀티코어 Cortex-R bare-metal(실행부 · TCM · ECC · 인터럽트)은 이미 몸으로 안다 / 새로 배울 부분은 Armv8-R의 EL2와 2단계 MPU, GICv3 시스템 레지스터 인터페이스, FreeRTOS · Zephyr의 Cortex-R 포트가 IRQ 진입을 어떻게 소프트웨어로 처리하는지, Cortex-M 포트와의 비용 차이
> **선행 노트**: B1(Cortex-M 프로그래머 모델), B2(예외 진입 · 하드웨어 스태킹 — 이 노트의 대조군), B4(RTOS가 쓰는 세 예외), B8(캐시 · TCM이 있는 MCU), EL C5(예외 레벨), EL H6(인터럽트 컨트롤러), EL F8(타이머). 이어지는 노트: C2(컨텍스트 스위치), C7(크리티컬 섹션), E2(인터럽트 우선순위 설계), O6 · P6(분할 · 하이퍼바이저)
> 🔁 **Bare-Metal 겹침**: BM D9(Cortex-R5 / R52 bare-metal: R 프로파일 startup, TCM ECC 초기화, MPU 설정, lockstep DCLS, R52 EL2) — 이 노트가 주인. Bare-Metal 노트는 이 노트를 링크하고 "RTOS 없이 실행부(executive) 하나로 멀티코어 R을 돌릴 때의 코어 간 통신 · 부트 순서"만 더한다

## 0. 큰 그림 — Cortex-R은 왜 따로 있나

Don이 SSD 컨트롤러에서 만졌던 코어를 떠올려 보자. 한 칩 안에 Cortex-R 코어가 셋쯤 있고, 코어마다 TCM이 붙어 있고, 각 코어는 실행부(executive) 루프 하나를 돌린다. 호스트 명령은 하드웨어 큐로 들어오고, NAND 쪽 완료는 인터럽트로 온다. Linux는 없다. 그런데 Cortex-M도 아니었다. 왜일까?

이유는 세 가지다. 첫째, **클럭과 처리량**이다. SSD 컨트롤러는 수 GB/s의 데이터를 흘려야 하므로 MCU보다 훨씬 높은 클럭과 긴 파이프라인이 필요했다. 둘째, **결정성**이다. 높은 클럭이 필요하다고 Cortex-A를 쓰면 MMU · 큰 캐시 · 투기 실행 때문에 인터럽트 응답이 들쭉날쭉해진다. 셋째, **신뢰성**이다. TCM과 캐시에 ECC가 붙고, 필요하면 코어 두 개를 lockstep으로 묶어 계산 오류까지 잡는다. 이 세 가지를 동시에 만족시키려고 Arm이 만든 것이 **R 프로파일(Real-time profile)** 이다.

그림 1 — Cortex-R 계열 지도. R5는 Armv7-R(32비트), R52 · R52+는 Armv8-R AArch32(EL2 하이퍼바이저 추가), R82는 Armv8-R AArch64(64비트, 선택 MMU로 Linux도 가능)다. 아래 사용처는 공개 자료로 확인한 예다(참고 자료 참조).

한 줄로 말하면 **Cortex-R = Cortex-A의 예외 모델(모드 · 뱅크 레지스터 · GIC) + Cortex-M 수준의 결정성(MMU 대신 MPU, TCM, 짧은 인터럽트 경로)** 이다. RTOS 엔지니어 입장에서 이게 중요한 이유는, **포트(port) 계층이 Cortex-M과 완전히 다르기 때문이다.** Cortex-M에서 "ISR을 그냥 C 함수로 쓸 수 있는" 이유(B2의 하드웨어 스태킹)가 Cortex-R에는 없다. 그 빈자리를 포트의 어셈블리가 메운다. 이 노트는 그 빈자리를 직접 코드로 채워 보고, 비용을 명령 수로 잰다.

### 실습 환경 한 줄

QEMU 10.2.1 `mps3-an536`(Cortex-R52, 이 노트에서는 1코어) 위에서 **직접 쓴 bare-metal startup** + FreeRTOS V11.3.2(`ARM_CRx_No_GIC` 포트) + Zephyr v4.4.2(`fvp_baser_aemv8r/fvp_aemv8r_aarch32` 보드를 overlay로 AN536에 옮김). 대조군은 QEMU `mps2-an385`(Cortex-M3). 툴체인은 Ubuntu `arm-none-eabi-gcc` 14.2(`-mcpu=cortex-r52 -marm`)와 Zephyr SDK 1.0.1 `arm-zephyr-eabi`. 타이밍 수치는 **QEMU icount 기준(명령 1개 = 32 ns, `-icount shift=5`)** 이다. 캐시 · 버스 · 파이프라인 · 예외 진입 사이클을 모델링하지 않으므로 실제 칩과 절대값은 다르다. 이 노트의 숫자는 "명령을 몇 개 실행했나"로 읽는다.

빌드 · 실행 스크립트는 두 줄짜리다(소스는 `~/.rtos_scratch/B9/`, 산출물은 VM `/var/tmp/rtos/B9/`).

```sh
# build.sh <name> <src...> : Cortex-R52, ARM state, freestanding (libc 없음)
arm-none-eabi-gcc -mcpu=cortex-r52 -marm -mfloat-abi=softfp -mfpu=fpv5-d16 -O2 -g -Wall -Wextra \
  -ffreestanding -nostdlib -Icommon -T common/r52.ld -o $O/app.elf common/start.S common/lib.c "$@" -lgcc
# run.sh <elf> : ICOUNT=1이면 -icount shift=5,align=off,sleep=off
qemu-system-arm -M mps3-an536 -smp 1 -nographic -monitor none -serial stdio \
  -semihosting-config enable=on,target=native -kernel $E
```

`-kernel`에 ELF를 주면 QEMU가 세그먼트를 그 주소에 올리고 ELF entry(`_start`)에서 CPU 0을 시작한다. 프로그램은 Arm semihosting `SYS_EXIT`(`HLT #0xF000`)로 QEMU를 끝낸다.

## 1. R 프로파일의 정체 — A · R · M 세 프로파일 비교

### 1.1 직관: "A의 몸에 M의 심장"

Cortex-M을 공부한 사람이 R을 처음 보면 놀라는 점은 **R이 M보다 A에 훨씬 가깝다**는 것이다. 레지스터 모델(뱅크 레지스터를 가진 7~8개 모드), 예외 벡터(분기 명령 8개), 인터럽트 컨트롤러(GIC), 시스템 레지스터(CP15)가 전부 A 쪽이다. 다른 점은 메모리 시스템이다. **MMU가 없고 MPU만 있다**(R82는 선택 MMU). 주소 변환이 없으니 TLB miss도, page walk도 없다. 대신 TCM과 ECC, lockstep 같은 "결정성 · 신뢰성" 장치가 붙는다.

| 항목 | Cortex-A (예: A53) | **Cortex-R (R5 / R52)** | Cortex-M (예: M3 / M33) |
|---|---|---|---|
| 메모리 보호 | MMU (가상 주소) | **MPU** (물리 주소 그대로, R82는 MMU 선택) | MPU |
| 예외 모델 | 모드(v7-A) / EL0–EL3 | **모드 + 뱅크 레지스터**, R52는 EL0–EL2 | Thread / Handler, MSP / PSP |
| 예외 진입 | 소프트웨어가 저장 | **소프트웨어가 저장** | **하드웨어가 8워드 자동 스태킹** |
| 벡터 테이블 | 분기 명령 테이블 (VBAR) | **분기 명령 8개** (VBAR / HVBAR) | 주소 테이블 (VTOR) |
| 인터럽트 컨트롤러 | GIC | **GIC** (R5는 GICv1/v2 또는 VIC 포트, R52는 GICv3) | NVIC (코어에 내장) |
| 시스템 레지스터 | CP15 / MSR | **CP15** (`MRC` / `MCR`) | 메모리 맵 SCB (0xE000E000) |
| 빠른 메모리 | 캐시 | **TCM + 캐시, ECC** | TCM은 일부(M7 · M55 · M85) |
| 신뢰성 | RAS | **lockstep(DCLS)**, ECC | 일부 칩만 lockstep |

> 표 읽는 법: Cortex-R 열의 굵은 글씨가 RTOS 포트에 직접 영향을 주는 차이다. 특히 "예외 진입 = 소프트웨어가 저장" 한 줄 때문에 포트 어셈블리가 Cortex-M보다 몇 배 길어진다(§5, §9).

### 1.2 세 세대의 차이

| 항목 | **R5** (Armv7-R) | **R52 / R52+** (Armv8-R AArch32) | **R82** (Armv8-R AArch64) |
|---|---|---|---|
| 명령어 | A32 + T32 | A32 + T32 | A64 |
| 권한 단계 | PL0 / PL1 (모드 7개) | **EL0 / EL1 / EL2** (Hyp 모드 추가) | EL0 / EL1 / EL2 (AArch64 레지스터) |
| MPU | PMSAv7: 크기 2의 거듭제곱, 서브리전, 겹치면 번호 큰 영역 우선 | **PMSAv8-32**: base / limit, 64바이트 단위, **겹치면 fault**, EL2 MPU로 2단계 | PMSAv8-64 + 선택 VMSA(MMU) |
| 인터럽트 | GIC(v1/v2 메모리 맵 CPU 인터페이스) 또는 VIC 포트 | **GICv3, CPU 인터페이스 = 시스템 레지스터(`ICC_*`)** | GICv3 |
| 타이머 | 코어 밖 (SoC 타이머) | **Generic Timer 내장** (CNTP / CNTV / CNTHP) | Generic Timer |
| TCM | ATCM / BTCM (B0 / B1) | ATCM / BTCM / CTCM | TCM |
| 이 노트에서 | 개념 · FreeRTOS `ARM_CR5` 포트 비교 | **QEMU AN536으로 전부 실행** | FreeRTOS `ARM_CR82` 포트 소개만 |

R52는 R5의 단순한 후속이 아니다. **EL2가 생긴 것이 가장 큰 변화**다. 하이퍼바이저 모드가 있으니 한 코어 위에 RTOS 두 개를 올려 격리할 수 있고(§6.3), 리셋하면 코어가 **EL1이 아니라 EL2(Hyp 모드)에서 깨어난다**(§3). Armv8-R에는 EL3(Secure Monitor)가 없다. 그래서 R52의 가장 높은 권한은 EL2다.

### 1.3 예제 1 — 리셋 직후 R52가 스스로 말하는 것 (ID 레지스터)

무엇을 확인하나: 코어가 정말 EL2(Hyp)에서 시작하는지, QEMU의 R52에 MPU 영역 몇 개 · FPU 레지스터 몇 개 · 타이머 주파수가 몇인지 CP15 ID 레지스터로 직접 읽는다. `el2_hook()`은 startup이 EL2에서 부르는 C 함수다(§3).

```c
/* ex1 — reset lands in EL2 (Hyp): read Cortex-R52 ID registers, then drop to EL1 */
#include "r52.h"

static const char *mode_name(uint32_t m)
{
    switch (m & 0x1f) {
    case 0x10: return "USR"; case 0x11: return "FIQ"; case 0x12: return "IRQ";
    case 0x13: return "SVC"; case 0x16: return "MON"; case 0x17: return "ABT";
    case 0x1a: return "HYP"; case 0x1b: return "UND"; case 0x1f: return "SYS";
    default:   return "???";
    }
}

void el2_hook(void)
{
    uart_init();
    uint32_t cpsr = get_cpsr(), midr = RD_CP15(0, c0, c0, 0);
    uint32_t mpuir = RD_CP15(0, c0, c0, 4), hmpuir = RD_CP15(4, c0, c0, 4);
    uint32_t mvfr0;
```

출력에서 볼 것:

- `CPSR` 하위 5비트 `0x1a` = **Hyp 모드**. 리셋 직후 R52는 EL2에 있다. `ERET` 뒤에는 `0x13`(SVC, EL1)이다. 상위 `0x6...`은 앞선 비교 명령이 남긴 Z · C 플래그다.
- `MIDR` part `0xd13` = Cortex-R52, `r1p3`. implementer `0x41` = Arm.
- `ID_MMFR0` PMSA 필드 `4` = **PMSAv8**. MMU(VMSA) 필드는 0이다 — MMU가 없다.
- `MPUIR` · `HMPUIR` = EL1 MPU 16영역, EL2 MPU 16영역. **MPU가 두 벌**이라는 것이 R52의 특징이다(§6).
- `MVFR0` 하위 필드 2 = D 레지스터 32개(D0–D31). QEMU 모델 기준이다(실제 칩은 구성에 따라 다를 수 있다 — TRM 확인).
- `CNTFRQ` = 62.5 MHz. QEMU AN536의 generic timer 주파수다. 나중에 Zephyr 설정과 맞지 않아 문제가 된다(§9.3).

### 1.4 함정

- **"R은 M의 큰 버전"이라고 생각하는 것**: 레지스터 모델과 예외 처리는 A 쪽이다. Cortex-M 포트를 그대로 옮길 수 없다. 포트를 고른다면 FreeRTOS `ARM_CR5` · `ARM_CRx_*` · `ARM_CR82` 중에서 고른다(§9.1).
- **R52 리셋 = EL1이라고 가정하는 것**: EL2에서 깬다. EL2에서 할 일(HVBAR, 타이머 접근 허용, FPU 트랩 해제)을 하지 않고 EL1로 내려가면 나중에 타이머 레지스터 접근이 UNDEF가 되거나 FPU 명령이 EL2로 트랩된다.

### 2.1 직관: 모드마다 "자기 책상"이 있다

Cortex-M에는 스택 포인터가 두 개(MSP · PSP)뿐이다. Cortex-R(그리고 v7-A)은 **예외 종류마다 모드가 따로 있고, 모드마다 자기 SP · LR · SPSR을 가진다.** 비유하면 직원(코어) 한 명이 일 종류마다 다른 책상을 쓰는 것이다. ### 2.2 정의 — 모드 표

| 모드 | CPSR.M | EL | 들어가는 때 | 뱅크 레지스터 | RTOS에서의 역할 |
|---|---|---|---|---|---|
| USR | 0x10 | EL0 | 비특권 코드 | (기본 r13/r14) | MPU 격리된 태스크 (Zephyr userspace, FreeRTOS MPU 포트) |
| FIQ | 0x11 | EL1 | FIQ (GICv3 Group 0) | SP · LR · SPSR + **r8–r12** | 커널 밖 초고속 인터럽트 (Cortex-M의 zero-latency ISR 자리) |
| IRQ | 0x12 | EL1 | IRQ (GICv3 Group 1) | SP · LR · SPSR | 진입만 하고 곧바로 SVC/SYS로 옮기는 경우가 많다 (§5) |
| SVC | 0x13 | EL1 | `SVC` 명령, 리셋 뒤 EL1 진입 | SP · LR · SPSR | FreeRTOS yield(`SVC 0`), Zephyr 시스템 콜 · ISR 스택 |
| ABT | 0x17 | EL1 | prefetch / data abort | SP · LR · SPSR | MPU 위반 처리 (§6) |
| HYP | 0x1A | EL2 | 리셋, `HVC`, 트랩 | SP_hyp · ELR_hyp · SPSR_hyp | 하이퍼바이저 (§6.3) |
| UND | 0x1B | EL1 | 정의 안 된 명령 | SP · LR · SPSR | lazy FPU 저장 트릭 (Zephyr, §5.6) |
| SYS | 0x1F | EL1 | `CPS #0x1F`로만 | (USR와 공유) | **FreeRTOS · Zephyr 태스크가 도는 모드** |

Cortex-M과 대응시키면 이렇다. M의 Thread 모드 + PSP ≈ R의 SYS 모드(태스크 스택), M의 Handler 모드 + MSP ≈ R의 SVC 모드(ISR · 커널 스택). R에는 "예외 종류별 모드"가 추가로 있을 뿐이다.

### 2.3 예제 2 — 뱅크 레지스터를 눈으로 보기

무엇을 확인하나: 각 모드의 SP가 정말 다른지, FIQ의 r8이 정말 따로인지, `SVC` 명령이 SVC 모드로 들어가며 LR · SPSR을 어떻게 남기는지 확인한다. `MRS Rd, SP_irq` 같은 **banked register 접근 명령**(Armv7VE · Armv8-R에 있음)으로 다른 모드의 레지스터를 모드 전환 없이 읽는다.

```c
/* ex2 — banked registers: each A/R mode has its own SP/LR/SPSR; FIQ also banks r8-r12 */
#include "r52.h"
#define RD_BANKED(reg) ({ uint32_t _v; __asm volatile("mrs %0, " #reg : "=r"(_v)); _v; })

void el2_hook(void) { uart_init(); }

/* SVC handler in asm: save r0-r3,r12,lr on SVC stack, call C with SVC number */
__attribute__((naked)) void svc_entry(void)
{
    __asm volatile(
        "push {r0-r3, r12, lr}\n"
        "ldr  r0, [lr, #-4]\n"          /* the SVC instruction itself (ARM state) */
        "bic  r0, r0, #0xff000000\n"    /* imm24 = SVC number */
        "mrs  r1, spsr\n"
        "mov  r2, sp\n"
        "bl   svc_c\n"
        "pop  {r0-r3, r12, lr}\n"
        "movs pc, lr\n");               /* return: PC=LR_svc, CPSR=SPSR_svc */
}

void svc_c(uint32_t num, uint32_t spsr, uint32_t sp)
{
    printf("  in SVC handler: num=%u CPSR=0x%08x SPSR_svc=0x%08x SP_svc=0x%08x\n",
           num, get_cpsr(), spsr, sp);
}

int main(void)
{
    uint32_t sp_now; __asm volatile("mov %0, sp" : "=r"(sp_now));  /* own mode: plain SP */
    printf("SP_svc=0x%08x SP_irq=0x%08x SP_fiq=0x%08x\n",
           sp_now, RD_BANKED(SP_irq), RD_BANKED(SP_fiq));
    printf("SP_abt=0x%08x SP_und=0x%08x SP_usr(=SYS)=0x%08x\n",
           RD_BANKED(SP_abt), RD_BANKED(SP_und), RD_BANKED(SP_usr));

    /* r8 is shared by USR/SYS/SVC/IRQ/ABT/UND but FIQ has its own r8_fiq */
    uint32_t r8_sys, r8_fiq;
    __asm volatile("mov r8, #0x55\n"
                   "cps #0x11\n" "mov r8, #0xF1\n" "cps #0x13\n"   /* write r8 in FIQ mode */
                   "mov %0, r8\n" "mrs %1, r8_fiq\n"
                   : "=r"(r8_sys), "=r"(r8_fiq) :: "r8");
    printf("r8 (SVC view)=0x%x  r8_fiq=0x%x  -> FIQ has private r8\n", r8_sys, r8_fiq);

    /* switch to SYS mode: same r0-r14 as USR, but privileged */
    uint32_t sp_sys, cpsr_sys;
    __asm volatile("cps #0x1f\n" "mov %0, sp\n" "mrs %1, cpsr\n" "cps #0x13\n"
                   : "=r"(sp_sys), "=r"(cpsr_sys));
    printf("in SYS: CPSR=0x%08x SP=0x%08x\n", cpsr_sys, sp_sys);

    printf("calling svc #42 from SVC mode, CPSR=0x%08x\n", get_cpsr());
    __asm volatile("svc #42" ::: "lr", "memory");
    printf("back, CPSR=0x%08x\n", get_cpsr());
    return 0;
}
```

```text
SP_abt=0x20004628 SP_und=0x20004a28 SP_usr(=SYS)=0x20005a28
r8 (SVC view)=0x55  r8_fiq=0xf1  -> FIQ has private r8
```

링커가 정한 스택 꼭대기(`arm-none-eabi-nm -n`)와 비교한다.

```text

20002e28 B __stack_svc_top
20003e28 B __stack_irq_top
```

출력에서 볼 것:

- 각 모드의 SP가 startup에서 넣어 준 꼭대기 값 그대로다. SVC만 8바이트 작은 이유는 `main`이 `push {r8, lr}`을 했기 때문이다.
- SVC 모드에서 r8에 `0x55`를 넣고, FIQ 모드로 가서 r8에 `0xF1`을 넣었는데 SVC의 r8은 그대로 `0x55`다. **FIQ 핸들러는 r8–r12를 저장하지 않고 써도 된다** — 그래서 "Fast" IRQ다.
- SVC 핸들러 안에서 `SPSR_svc` = 호출 직전 CPSR(`0x...1d3`), SVC 번호 42는 `LR - 4` 위치 명령어의 하위 24비트에서 꺼냈다. FreeRTOS `FreeRTOS_SVC_Handler`도 같은 방법으로 SVC 번호를 꺼낸다(§9).
- 핸들러 복귀는 `movs pc, lr` — **S 접미사가 붙은 PC 쓰기는 SPSR을 CPSR로 복사**한다. Cortex-M의 `bx lr`(EXC_RETURN 마법 값)과 전혀 다른 방식이다.

### 2.4 함정 — 자기 모드의 뱅크 레지스터를 MRS로 읽으면 UNDEF

이 예제의 첫 버전은 SVC 모드에서 `mrs r1, SP_svc`를 썼다. 결과는 이랬다.

```text
UNEXPECTED exception kind=0x1 lr=0x200007f8 cpsr=0x000001db
```

`kind=1`은 Undefined 예외, CPSR `0x1b`는 UND 모드다. `objdump`로 `lr - 4` = `0x200007f4`를 보면 바로 그 명령이다.

```text
200007f0:	e92d4100 	push	{r8, lr}
200007f4:	e1031300 	mrs	r1, SP_svc
```

Arm 아키텍처는 **현재 모드의 뱅크 레지스터를 banked MRS로 접근하는 것을 UNPREDICTABLE로 정의**하고, QEMU는 이를 UNDEF로 처리한다. 현재 모드의 SP는 그냥 `mov rX, sp`로 읽는다. 또 EL1에서 `SP_hyp`처럼 **더 높은 EL의 레지스터**를 읽는 것도 허용되지 않는다. 실칩에서 UNPREDICTABLE은 "가끔 동작하는 것처럼 보이는" 최악의 버그가 되므로, QEMU가 UNDEF로 잡아 준 것이 오히려 고맙다.

### 2.5 RTOS와 연결 — 왜 태스크는 SYS 모드에서 도나

FreeRTOS `ARM_CRx_No_GIC/port.c`의 첫 태스크 SPSR 값은 `portINITIAL_SPSR = 0x01f`(System mode, ARM, IRQ · FIQ 허용)다. Zephyr `cortex_a_r`도 스레드를 SYS 모드에서 돌린다(§9.3의 Zephyr 출력 `CPSR mode=0x1f`). 이유는 이렇다.

- **SYS는 특권 모드**라서 태스크가 CP15 · 주변장치에 접근할 수 있다(MPU 격리가 필요하면 USR).
- **SYS는 USR와 r13/r14를 공유**한다. 그래서 "태스크 스택 = SP_usr/SP_sys"가 되고, 커널은 IRQ · SVC 모드의 자기 스택을 따로 가진다. Cortex-M의 PSP(태스크) / MSP(커널) 분리와 같은 효과다.
- IRQ 진입 후 `SRSDB SP!, #0x1F`(아래 §5)로 **"돌아갈 주소 + 상태"를 곧바로 태스크(SYS) 스택에 저장**할 수 있다. 그러면 컨텍스트 스위치가 "SP_sys만 바꾸면 끝"이 된다.

## 3. 리셋에서 C까지 — Cortex-R52 startup 직접 쓰기

> 🔁 이 절은 Bare-Metal BM D9(R 프로파일 startup · R52 EL2)와 겹친다 (주인: 이 노트).

### 3.1 직관: M은 "주소표 두 칸"이면 되고, R은 "짐을 직접 푼다"

Cortex-M 리셋은 하드웨어가 거의 다 해 준다. 벡터 테이블 0번 칸에서 MSP를 읽고, 1번 칸(Reset_Handler)으로 점프한다(B5). Cortex-R52 리셋은 아무것도 해 주지 않는다. **SP도 없고, 모드는 EL2(Hyp)이고, 벡터 베이스도 정해야 하고, EL1로 내려가는 것도 소프트웨어가 `ERET`로 한다.** 그 다음에는 모드 6개의 SP를 하나씩 넣어야 한다. Don이 SSD 컨트롤러 startup에서 봤던 "모드마다 `CPS` 하고 `ldr sp, =...`" 줄들이 바로 이것이다.

| 단계 | Cortex-M3 (B5) | Cortex-R52 (이 노트의 `start.S`) |
|---|---|---|
| 첫 SP | 하드웨어가 vector[0]에서 MSP 로드 | 소프트웨어가 `ldr sp, =__stack_hyp_top` |
| 시작 모드 | Thread, privileged | **EL2 Hyp 모드** |
| 벡터 베이스 | VTOR (기본 0x0) | **HVBAR**(EL2) · **VBAR**(EL1)를 CP15로 쓴다 |
| 벡터 형식 | 함수 주소 배열 | **분기 명령 8개** (`b` 또는 `ldr pc, [...]`) |
| 권한 낮추기 | CONTROL.nPRIV | `SPSR_hyp` · `ELR_hyp` 설정 후 `ERET` |
| 스택 | MSP / PSP 둘 | **모드별 6개 + Hyp 1개** |
| 타이머 접근 | SysTick 그냥 사용 | EL2가 **CNTHCTL**로 EL1 접근 허용 |
| FPU 켜기 | CPACR | **HCPTR**(EL2 트랩 해제) + **CPACR** + **FPEXC.EN** |

### 3.3 벡터 테이블 두 벌

무엇을 확인하나: EL2용(HVBAR)과 EL1용(VBAR) 벡터 테이블을 만든다. EL2 쪽은 `b` 분기, EL1 쪽은 `ldr pc, [pc, #off]` + 주소 리터럴 방식을 일부러 섞었다. `b`는 ±32 MB 안에서만 닿고, `ldr pc`는 32비트 주소 어디든 닿는다(Zephyr `vector_table.S`가 `ldr pc, =z_arm_reset` 방식을 쓴다).

```asm
/* start.S — Cortex-R52 (Armv8-R AArch32) reset: EL2(Hyp) -> EL1(SVC), per-mode stacks */
    .syntax unified
    .arm
    .fpu fpv5-d16

/* ---------- EL2 (Hyp) vector table: HVBAR ---------- */
    .section .vectors, "ax"
    .align 5
    .global hyp_vectors
hyp_vectors:
    b   _start          @ 0x00 reset (not used via HVBAR)
    b   hyp_undef       @ 0x04 undefined instruction (taken to Hyp)
    b   hyp_hvc         @ 0x08 HVC
    b   hyp_pabt        @ 0x0C prefetch abort (Hyp)
    b   hyp_dabt        @ 0x10 data abort (Hyp)
    b   hyp_trap        @ 0x14 Hyp trap: exceptions from EL1/EL0 routed to EL2
    b   hyp_irq         @ 0x18 IRQ
    b   hyp_fiq         @ 0x1C FIQ

/* ---------- EL1 vector table: VBAR (ldr pc table style) ---------- */
    .align 5
    .global el1_vectors
el1_vectors:
    ldr pc, v_reset     @ 0x00
    ldr pc, v_undef     @ 0x04
    ldr pc, v_svc       @ 0x08
    ldr pc, v_pabt      @ 0x0C
    ldr pc, v_dabt      @ 0x10
    nop                 @ 0x14 (reserved at EL1)
    ldr pc, v_irq       @ 0x18
    ldr pc, v_fiq       @ 0x1C
v_reset: .word _start
v_undef: .word undef_entry
v_svc:   .word svc_entry
v_pabt:  .word pabt_entry
v_dabt:  .word dabt_entry
v_irq:   .word irq_entry
v_fiq:   .word fiq_entry

/* weak default handlers: report kind + LR, then exit */
    .macro DEFAULT name, kind
    .weak \name
\name:
    mov r0, #\kind
    mov r1, lr
    b   exc_unexpected
    .endm
    DEFAULT undef_entry, 1
    DEFAULT svc_entry,   2
    DEFAULT pabt_entry,  3
    DEFAULT dabt_entry,  4
    DEFAULT irq_entry,   6
    DEFAULT fiq_entry,   7
    DEFAULT hyp_undef,   0x11
    DEFAULT hyp_hvc,     0x12
    DEFAULT hyp_pabt,    0x13
    DEFAULT hyp_dabt,    0x14
    DEFAULT hyp_trap,    0x15
    DEFAULT hyp_irq,     0x16
    DEFAULT hyp_fiq,     0x17

```

빌드 결과를 `objdump -d`로 보면 벡터 테이블이 정말 "명령어 8개"다.

```text

20000010:	b	200000c8 <hyp_dabt>
```

출력에서 볼 것: 오프셋 0x18이 IRQ, 0x1C가 FIQ다. EL1의 0x14는 비어 있다(v7의 옛 자리). EL2의 0x14는 **Hyp Trap** — EL1/EL0에서 EL2로 올라오는 예외(HVC, 2단계 MPU fault 등)가 전부 여기로 온다(§6.3). 테이블은 32바이트 정렬이어야 한다(`.align 5`). Zephyr `reset.S`도 같은 이유로 `__start`를 `.align 5`로 둔다는 주석이 있다.

### 3.4 리셋 경로 — EL2 → EL1

```asm
    .text
    .global _start
_start:
    ldr  sp, =__stack_hyp_top
    ldr  r0, =hyp_vectors
    mcr  p15, 4, r0, c12, c0, 0     @ HVBAR
    mov  r0, #3
    mcr  p15, 4, r0, c14, c1, 0     @ CNTHCTL: PL1PCTEN|PL1PCEN (EL1 may use phys counter/timer)
    mrc  p15, 4, r0, c1, c1, 2      @ HCPTR
    bic  r0, r0, #(3 << 10)         @ do not trap cp10/cp11 (FPU) to EL2
    mcr  p15, 4, r0, c1, c1, 2
    ldr  r0, =__bss_start           @ zero .bss
    ldr  r1, =__bss_end
    mov  r2, #0
1:  cmp  r0, r1
    strlo r2, [r0], #4
    blo  1b
    bl   el2_hook                   @ C code at EL2 (weak, may be empty)
    ldr  r0, =el1_vectors
    mcr  p15, 0, r0, c12, c0, 0     @ VBAR (EL1)
    ldr  r0, =el1_entry
    msr  elr_hyp, r0
    mov  r0, #0x1d3                 @ SPSR: A,I,F masked, mode = SVC (0x13)
    msr  spsr_hyp, r0
    eret                            @ EL2 -> EL1

el1_entry:
    cps  #0x12
    ldr  sp, =__stack_irq_top
    cps  #0x11
    ldr  sp, =__stack_fiq_top
    cps  #0x17
    ldr  sp, =__stack_abt_top
    cps  #0x1b
    ldr  sp, =__stack_und_top
    cps  #0x1f
    ldr  sp, =__stack_sys_top
    cps  #0x13
    ldr  sp, =__stack_svc_top
    mrc  p15, 0, r0, c1, c0, 2      @ CPACR: cp10/cp11 full access
    orr  r0, r0, #(0xf << 20)
    mcr  p15, 0, r0, c1, c0, 2
    isb
    mov  r0, #0x40000000            @ FPEXC.EN
    vmsr fpexc, r0
    bl   main
    bl   qemu_exit

    .weak el2_hook
el2_hook:
    bx   lr
```

한 줄씩 읽으면 이렇다.

1. `ldr sp, =__stack_hyp_top` — 하드웨어가 SP를 주지 않으므로 C를 부르기 전에 반드시 넣는다.
2. `HVBAR` — EL2 예외 벡터. 이것을 안 넣으면 EL2에서 나는 첫 예외가 0번지 근처로 날아간다.
3. `CNTHCTL = 3` — EL1이 물리 카운터(`CNTPCT`)와 물리 타이머(`CNTP_*`)를 쓰도록 허용한다. 하이퍼바이저가 게스트에게 "시계를 직접 만져도 된다"고 허락하는 비트다.
4. `HCPTR`의 TCP10/TCP11을 지운다 — EL1의 FPU 명령이 EL2로 트랩되지 않게 한다.
5. `.bss` 0 채우기 → `el2_hook()` (EL2에서 할 C 코드, 기본은 빈 함수).
6. `VBAR` — EL1 벡터. `SPSR_hyp = 0x1D3`(A · I · F 마스크, 모드 SVC), `ELR_hyp = el1_entry`, `ERET`. **ERET 한 명령이 PC = ELR_hyp, CPSR = SPSR_hyp를 동시에** 한다.
7. EL1에서 `CPS`로 모드를 돌며 SP 6개를 넣는다. 마지막에 SVC로 돌아와 `main`.
8. `CPACR`(cp10/cp11 접근) + `FPEXC.EN` — 둘 다 해야 VFP 명령이 UNDEF가 안 된다.

Zephyr v4.4.2 `arch/arm/core/cortex_a_r/reset.S`도 같은 일을 한다. `CONFIG_AARCH32_ARMV8_R`이면 CPSR 모드가 HYP인지 보고, `HACTLR`(EL1에게 IMP DEF 레지스터 접근 허용)을 설정한 뒤 `msr elr_hyp, r0` · `eret`로 SVC 모드 `EL1_Reset_Handler`로 내려간다. (원문 발췌, `...`는 생략한 줄)

```asm
    /* Check if we are starting in HYP mode */
    mrs r0, cpsr
    and r0, r0, #MODE_MASK
    cmp r0, #MODE_HYP
    bne EL1_Reset_Handler
    ...
    /* Init HACTLR: Enable EL1 access to all IMP DEF registers */
    ldr r0, =HACTLR_INIT
    mcr p15, 4, r0, c1, c0, 1
   /* Go to SVC mode */
    ...
    msr elr_hyp, r0
    dsb
    isb
    eret
```

### 3.5 링커 스크립트 — 스택 일곱 개

```text
/* r52.ld — everything in AN536 DDR (0x20000000), as QEMU -kernel loads ELF segments */
ENTRY(_start)
MEMORY { DDR (rwx) : ORIGIN = 0x20000000, LENGTH = 16M }
SECTIONS
{
    .text : { KEEP(*(.vectors)) *(.text*) *(.rodata*) } > DDR
    .data : { *(.data*) } > DDR
    .bss (NOLOAD) : { __bss_start = .; *(.bss*) *(COMMON) . = ALIGN(4); __bss_end = .; } > DDR
    .stacks (NOLOAD) : ALIGN(8) {
        . += 0x1000; __stack_hyp_top = .;
        . += 0x1000; __stack_svc_top = .;
        . += 0x1000; __stack_irq_top = .;
        . += 0x400;  __stack_fiq_top = .;
        . += 0x400;  __stack_abt_top = .;
        . += 0x400;  __stack_und_top = .;
        . += 0x1000; __stack_sys_top = .;
    } > DDR
}
```

Cortex-M 링커 스크립트(B5)와 다른 점은 `.stacks` 섹션 하나에 모드별 스택을 나란히 둔 것뿐이다. 실제 제품에서는 IRQ · SVC 스택을 **TCM에** 두는 경우가 많다(§7). 인터럽트 진입이 스택에 저장하는 시간이 TCM 접근 지연으로 정해지기 때문이다.

### 3.6 함정

- **FIQ · IRQ 스택 크기를 너무 작게**: Cortex-M은 ISR이 MSP 하나를 쓰지만, R은 IRQ 모드 스택이 따로라서 "IRQ 스택은 작아도 되겠지" 하고 256바이트만 주기 쉽다. 그런데 §5의 비재진입 방식(IRQ 모드에 머무는 방식)은 C 핸들러 전체가 IRQ 스택을 쓴다. 재진입 방식(SVC로 옮기는 방식)은 SVC 스택이 커야 한다. **어느 방식인지 먼저 정하고 크기를 정한다.**
- **`ERET` 전에 `SPSR_hyp`의 I 비트를 열어 두기**: EL1에 내려가자마자 IRQ가 들어오는데 IRQ 스택은 아직 없다. 이 노트처럼 마스크한 채(`0x1D3`) 내려가서 스택을 다 넣은 뒤 `cpsie i`로 연다.
- **두 번째 코어**: QEMU AN536은 CPU 1을 `start-powered-off`로 시작하고, 소스 주석에 "실제 하드웨어에서는 두 코어 사이에 RAM에서 LDREX/STREX를 쓸 수 없어 진짜 SMP가 아니다"라고 적혀 있다. 이 노트는 1코어만 쓴다. 실제 멀티코어 R에서는 MPIDR.Aff0로 코어를 구분해 각자 스택을 고르는 코드가 맨 앞에 온다(P 모듈).

## 4. GICv3와 generic timer — 첫 IRQ 받기

### 4.1 직관: NVIC는 코어 안에, GIC는 코어 옆에

Cortex-M의 NVIC는 코어의 일부라서 "인터럽트 번호 → 벡터 테이블 칸"이 하드웨어로 이어진다. ISR 진입과 동시에 어느 인터럽트인지 이미 정해져 있다. Cortex-R의 GIC는 **별도 블록**이다. 모든 IRQ는 벡터 테이블의 **한 칸(0x18)** 으로 들어오고, 소프트웨어가 GIC에게 "지금 어느 인터럽트야?"를 물어야 한다(**acknowledge = IAR 읽기**). 처리가 끝나면 "끝났다"를 알려야 한다(**EOI = EOIR 쓰기**). 이 두 단계가 Cortex-M에는 없다.

GICv3는 세 부분으로 나뉜다(자세한 GIC 구조는 EL H6).

| 부분 | AN536 주소 | 하는 일 | R52에서 접근 |
|---|---|---|---|
| Distributor (GICD) | 0xF0000000 | SPI(공유 인터럽트, INTID 32+) 라우팅 · 우선순위 · 활성화 | 메모리 맵 |
| Redistributor (GICR) | 0xF0100000 | 코어별 SGI(0–15) · PPI(16–31) 설정, 코어 깨우기(`GICR_WAKER`) | 메모리 맵 |
| CPU interface (ICC) | — | IAR / EOIR / PMR / IGRPEN | **시스템 레지스터** (`MRC p15, 0, Rt, c12, c12, 0` = ICC_IAR1) |

R52의 generic timer는 코어마다 있는 **PPI**로 나온다. EL1 물리 타이머(CNTP)는 INTID 30, 가상 타이머(CNTV)는 27, Hyp 타이머(CNTHP)는 26이다(Zephyr `fvp-aemv8r.dtsi`의 `GIC_PPI 14` = 16 + 14 = 30과 같은 값).

### 4.2 예제 3 — 1 kHz 타이머 IRQ 다섯 번

무엇을 확인하나: GICv3 초기화(`lib.c`의 `gic_init_ppi`) → CNTP 타이머 설정 → IRQ 벡터 → 소프트웨어 저장 → C에서 IAR · EOIR까지 한 바퀴를 돈다. 주기는 `CVAL += period`로 다시 걸어서 드리프트가 없게 한다(C5의 `vTaskDelayUntil`과 같은 아이디어).

먼저 GIC 초기화 부분(`common/lib.c`)이다.

```c
/* Route one PPI (INTID 16..31) of CPU0 to Group 1 and enable it */
void gic_init_ppi(uint32_t intid, uint8_t prio)
{
    uint32_t sgi = GICR_BASE + 0x10000;
    REG32(GICD_BASE + 0x0) = (1u << 4) | (1u << 1) | 1u;       /* GICD_CTLR: ARE, EnableGrp1, EnableGrp0 */
    REG32(GICR_BASE + 0x14) &= ~(1u << 1);                     /* GICR_WAKER.ProcessorSleep = 0 */
    while (REG32(GICR_BASE + 0x14) & (1u << 2)) { }            /* wait ChildrenAsleep = 0 */
    REG32(sgi + 0x080) |= 1u << intid;                         /* GICR_IGROUPR0: Group 1 */
    ((volatile uint8_t *)(sgi + 0x400))[intid] = prio;         /* GICR_IPRIORITYR */
    REG32(sgi + 0x100) = 1u << intid;                          /* GICR_ISENABLER0 */
    ICC_PMR(0xFF);                                             /* allow all priorities */
    ICC_IGRPEN1(1);
    ISB();
}
```

```c
/* ex3 — first IRQ on Cortex-R52: generic timer (PPI 30) -> GICv3 -> IRQ vector -> C */
#include "r52.h"

void el2_hook(void) { uart_init(); }

/* Software context save: NOTHING is stacked by hardware on A/R profile */
__attribute__((naked)) void irq_entry(void)
{
    __asm volatile(
        "sub   lr, lr, #4\n"          /* LR_irq = interrupted PC + 4 -> fix return addr */
        "srsdb sp!, #0x13\n"          /* push LR_irq + SPSR_irq onto the SVC stack */
        "cps   #0x13\n"               /* continue in SVC mode (frees IRQ mode for nesting) */
        "push  {r0-r3, r12, lr}\n"    /* AAPCS caller-saved regs + LR_svc */
        "and   r1, sp, #4\n"          /* 8-byte stack alignment for AAPCS */
        "sub   sp, sp, r1\n"
        "push  {r1, r2}\n"
        "bl    irq_c\n"
        "pop   {r1, r2}\n"
        "add   sp, sp, r1\n"
        "pop   {r0-r3, r12, lr}\n"
        "rfeia sp!\n");               /* pop PC + CPSR in one instruction */
}

static volatile uint32_t ticks;
static uint64_t stamp[5];
static const uint32_t period = 62500;   /* 1 ms at 62.5 MHz */

void irq_c(void)
{
    uint32_t iar = ICC_IAR1();          /* acknowledge: returns INTID */
    uint32_t id = iar & 0xffffff;
    if (id == INTID_CNTP) {
        if (ticks < 5) stamp[ticks] = CNTPCT();
        ticks++;
        SET_CNTP_CVAL(CNTP_CVAL() + period);   /* next deadline, drift-free */
    } else {
        printf("spurious/unknown INTID %u\n", id);
    }
    ICC_EOIR1(iar);                     /* end of interrupt (priority drop + deactivate) */
}

int main(void)
{
    gic_init_ppi(INTID_CNTP, 0xA0);
    uint64_t t0 = CNTPCT();
    SET_CNTP_CVAL(t0 + period);
    SET_CNTP_CTL(1);                    /* ENABLE=1, IMASK=0 */
    ISB();
    __asm volatile("cpsie i");
    while (ticks < 5) __asm volatile("wfi");
    SET_CNTP_CTL(0);
    for (int i = 0; i < 5; i++)
        printf("tick %d at +%u ticks (%u ns)\n", i, (uint32_t)(stamp[i] - t0),
               (uint32_t)(stamp[i] - t0) * 16);
    printf("GICD_TYPER=0x%08x (ITLinesNumber=%u -> %u INTIDs)\n", REG32(GICD_BASE + 4),
           REG32(GICD_BASE + 4) & 0x1f, 32 * ((REG32(GICD_BASE + 4) & 0x1f) + 1));
    printf("GICR_TYPER=0x%08x%08x\n", REG32(GICR_BASE + 0xC), REG32(GICR_BASE + 0x8));
    return 0;
}
```

출력에서 볼 것:

- 간격이 정확히 62,500 tick(1 ms)이고, 매번 마감보다 **40 tick(640 ns) 늦게** C 본문에 닿는다. 40 tick = 20 명령(icount에서 tick 16 ns, 명령 32 ns). 이 20 명령이 "타이머 만료 → WFI 깨어남 → 벡터 → 소프트웨어 저장 → `irq_c` → `CNTPCT` 읽기"까지의 길이다. 다음 절에서 이것을 쪼갠다.
- `GICD_TYPER.ITLinesNumber = 3` → INTID 128개(QEMU 소스의 SPI 96개 + 내부 32개). 실제 SoC는 수백 개가 흔하다.
- `GICR_TYPER` 하위 비트의 `Last`(bit 4) = 1 — 이 redistributor가 마지막(코어 1개)이다.

### 4.3 RTOS 커널과 연결

FreeRTOS Cortex-R 포트에서 이 IAR → 처리 → EOIR 순서는 누가 할까? `ARM_CR5` 포트는 **GICv2 메모리 맵 CPU 인터페이스**를 가정한다. `portmacro.h`에 `portICCIAR_INTERRUPT_ACKNOWLEDGE_OFFSET (0x0C)`, `portICCEOIR_END_OF_INTERRUPT_OFFSET (0x10)`, `portICCPMR_PRIORITY_MASK_OFFSET (0x04)`이 있고, `configINTERRUPT_CONTROLLER_BASE_ADDRESS + configINTERRUPT_CONTROLLER_CPU_INTERFACE_OFFSET`으로 주소를 만든다. 즉 **R52의 GICv3(시스템 레지스터 인터페이스)에는 맞지 않는다.** 그래서 이 노트는 인터럽트 컨트롤러를 앱에 맡기는 `ARM_CRx_No_GIC` 포트를 골랐다(§9.2). Zephyr는 `arm_gic_get_active()` / `arm_gic_eoi()`로 추상화해서 GICv2 · v3를 드라이버(`drivers/interrupt_controller/intc_gicv3.c`)가 맡는다.

### 4.4 함정

- **EOI를 빼먹으면**: 그 우선순위 이하의 인터럽트가 다시는 안 들어온다(GIC는 그 INTID가 아직 active라고 본다). 증상은 "첫 tick 한 번만 오고 시스템이 멈춤".
- **IAR을 읽기 전에 IRQ를 다시 열면**: 같은 인터럽트가 다시 들어와 무한 중첩된다. Zephyr `_isr_wrapper`도 `arm_gic_get_active` **뒤에** `cpsie i`를 한다(주석: "most interrupt controllers require that the nested interrupts are handled after the active interrupt is acknowledged").
- **GICR_WAKER를 안 깨우면**: redistributor가 잠든 채라 PPI가 안 온다. GICv2에는 없던 단계라서 R5 코드를 R52로 옮길 때 자주 빠진다.

## 5. 하드웨어 스태킹이 없다 — 소프트웨어 컨텍스트 저장

### 5.1 직관: 이삿짐센터(M)와 직접 이사(R)

B2에서 본 Cortex-M은 인터럽트가 오면 **하드웨어가** r0–r3, r12, lr, pc, xPSR 8워드를 현재 스택에 쌓고, LR에 EXC_RETURN 값을 넣고, 벡터 테이블의 C 함수로 바로 뛴다. ISR은 평범한 AAPCS C 함수다. 이삿짐센터가 짐을 싸 주는 셈이다.

Cortex-R은 하드웨어가 딱 세 가지만 한다. **CPSR을 SPSR_irq에 복사, 돌아갈 주소(+4)를 LR_irq에 넣기, 모드를 IRQ로 바꾸고 I 비트 세우기.** 그리고 벡터 0x18의 **명령 하나**를 실행한다. 나머지 — 레지스터 저장, 스택 정렬, C 호출, 복원, 복귀 — 는 전부 소프트웨어 몫이다. 직접 이사다.

### 5.2 정의 — 진입 시퀀스의 각 명령이 하는 일

```asm
irq_entry:                       @ vector 0x18: ldr pc, v_irq  (1)
    sub   lr, lr, #4             @ (2) LR_irq = 끼어든 명령 주소 + 4 → 돌아갈 주소로 고친다
    srsdb sp!, #0x13             @ (3) LR_irq와 SPSR_irq를 "SVC 모드 스택"에 바로 push
    cps   #0x13                  @ (4) SVC 모드로 이동 → IRQ 모드는 다음 IRQ를 위해 비워 둔다
    push  {r0-r3, r12, lr}       @ (5) AAPCS caller-saved + LR_svc (C가 망가뜨릴 수 있는 것)
    and   r1, sp, #4             @ (6) AAPCS: C 호출 시 SP는 8바이트 정렬
    sub   sp, sp, r1             @     정렬 보정값을 r1에 기억
    push  {r1, r2}               @     (보정값 저장, 8바이트 유지)
    bl    irq_c                  @ (7) C 본문
    pop   {r1, r2}
    add   sp, sp, r1
    pop   {r0-r3, r12, lr}
    rfeia sp!                    @ PC와 CPSR을 스택에서 한 번에 복원 (SRS의 짝)
```

- **SRS / RFE**: SRS(Store Return State)는 "현재 모드의 LR과 SPSR을 **지정한 모드의 스택에**" 저장하는 명령이다. RFE(Return From Exception)는 그 두 워드를 꺼내 PC · CPSR에 넣는다. Armv6에서 생겼고, Cortex-M의 하드웨어 스태킹과 가장 가까운 "반자동" 도구다.
- **왜 SVC로 옮기나(재진입)**: IRQ 모드에 머문 채 C를 부르고 그 안에서 IRQ를 다시 열면, 새 IRQ가 **LR_irq를 덮어써서** 첫 IRQ의 C 함수 복귀 주소가 사라진다. 그래서 중첩을 허용하는 커널(Zephyr, FreeRTOS)은 IRQ 모드에서 최소한만 저장하고 SVC(또는 SYS)로 옮긴다.
- **왜 r4–r11은 안 저장하나**: AAPCS에서 r4–r11은 callee-saved라서 C 함수가 쓰면 스스로 복원한다. B2의 Cortex-M 하드웨어 스태킹이 r0–r3, r12, lr만 저장하는 것과 **같은 이유**다. 컨텍스트 스위치를 할 때만 r4–r11이 필요하다(C2).

`SRSDB` 뒤 SVC 스택의 모습(영문 그림):

```
 high addr
 +----------------+  <- SP_svc before IRQ
 | SPSR_irq       |  srsdb (2 words)
 | LR_irq (ret PC)|
 +----------------+
 | LR_svc         |  push {r0-r3, r12, lr}
 | r12            |
 | r3 .. r0       |
 +----------------+
 | r2 (pad)       |  push {r1, r2}   (alignment fix-up)
 | r1 = 0 or 4    |
 +----------------+  <- SP_svc when irq_c() runs (8-byte aligned)
 low addr
```

### 5.3 예제 4 — 진입 방식 네 가지를 icount로 재기

무엇을 확인하나: 같은 타이머 IRQ에 대해 진입 방식 네 가지를 만들고, **타이머 마감(CVAL) → C 본문의 첫 `CNTPCT` 읽기**까지와 **마감 → main으로 복귀**까지를 잰다. icount에서 타이머 tick 2개 = 명령 1개다.

- S0: 최소 — IRQ 모드에 머물고 caller-saved만 저장(재진입 불가)
- S1: 재진입 — SRS로 SVC 스택, SVC로 이동(Zephyr · FreeRTOS CR5 계열)
- S2: GCC `__attribute__((interrupt("IRQ")))` — 컴파일러가 저장 코드를 만든다
- S3: RTOS 태스크 전체 — SYS 스택에 r0–r12, lr + VFP d0–d15 + FPSCR (FreeRTOS `portSAVE_CONTEXT`와 같은 모양)

```c
/* ex4 — IRQ entry cost on R52 for 4 entry styles (QEMU icount: 1 insn = 32 ns, 1 timer tick = 16 ns) */
#include "r52.h"
#ifndef STYLE
#define STYLE 0
#endif
void el2_hook(void) { uart_init(); }
static volatile uint32_t n;
static uint32_t lat[3], rt[3];
static uint64_t dl[3];
static void body(uint64_t now)               /* the "real work": record latency, ack, rearm */
{
    uint32_t iar = ICC_IAR1();
    if (n < 3) { dl[n] = CNTP_CVAL(); lat[n] = (uint32_t)(now - dl[n]); }
    n++;
    SET_CNTP_CVAL(CNTP_CVAL() + 62500);
    ICC_EOIR1(iar);
}
#if STYLE == 2   /* GCC generates the save/restore for us */
__attribute__((interrupt("IRQ"))) void irq_entry(void) { body(CNTPCT()); }
#else
void irq_c(void) { body(CNTPCT()); }
__attribute__((naked)) void irq_entry(void)
{
#if STYLE == 0   /* minimal: stay in IRQ mode, save AAPCS caller-saved regs only */
    __asm volatile("sub lr, lr, #4\n push {r0-r3, r12, lr}\n bl irq_c\n"
                   "pop {r0-r3, r12, lr}\n movs pc, lr\n");
#elif STYLE == 1 /* reentrant: SRS to SVC stack, switch to SVC (Zephyr/FreeRTOS CR5 style) */
    __asm volatile("sub lr, lr, #4\n srsdb sp!, #0x13\n cps #0x13\n push {r0-r3, r12, lr}\n"
                   "and r1, sp, #4\n sub sp, sp, r1\n push {r1, r2}\n bl irq_c\n"
                   "pop {r1, r2}\n add sp, sp, r1\n pop {r0-r3, r12, lr}\n rfeia sp!\n");
#elif STYLE == 3 /* RTOS full task context: SRS to SYS stack, r0-r12+lr, FPU d0-d15+FPSCR */
    __asm volatile("sub lr, lr, #4\n srsdb sp!, #0x1f\n cps #0x1f\n push {r0-r12, lr}\n"
                   "vmrs r1, fpscr\n vpush {d0-d15}\n push {r1}\n bl irq_c\n"
                   "pop {r1}\n vpop {d0-d15}\n vmsr fpscr, r1\n pop {r0-r12, lr}\n rfeia sp!\n");
#endif
}
#endif
int main(void)
{
    gic_init_ppi(INTID_CNTP, 0xA0);
    SET_CNTP_CVAL(CNTPCT() + 62500);
    SET_CNTP_CTL(1);
    ISB();
    __asm volatile("cpsie i");
    for (uint32_t seen = 0; seen < 3; ) {
        __asm volatile("wfi");
        uint64_t t = CNTPCT();            /* first thing after the IRQ returned */
        if (n > seen) { rt[seen] = (uint32_t)(t - dl[seen]); seen = n; }
    }
    SET_CNTP_CTL(0);
    printf("STYLE %d: deadline->C body = %u %u %u ticks (%u insns), deadline->back in main = %u insns\n",
           STYLE, lat[0], lat[1], lat[2], lat[2] / 2, rt[2] / 2);
    return 0;
}
```

S2는 처음에 이렇게 경고가 났다.

```text

   18 | __attribute__((interrupt("IRQ"))) void irq_entry(void) { body(CNTPCT()); }
      | ^~~~~~~~~~~~~
```

GCC의 `interrupt("IRQ")`는 **정수 레지스터만** 저장한다. ISR 안의 C 코드(또는 컴파일러가 고른 `memcpy` 등)가 VFP 레지스터를 쓰면 끼어든 태스크의 FPU 값이 망가진다. 그래서 그 파일은 `-mgeneral-regs-only`로 빌드했다(경고 0개). 네 방식의 결과다.

```text
STYLE 0: deadline->C body = 12 12 12 ticks (6 insns), deadline->back in main = 39 insns
STYLE 1: deadline->C body = 22 22 22 ticks (11 insns), deadline->back in main = 46 insns
STYLE 2: deadline->C body = 8 8 8 ticks (4 insns), deadline->back in main = 35 insns
STYLE 3: deadline->C body = 22 22 22 ticks (11 insns), deadline->back in main = 47 insns
```

GCC가 S2에 만들어 준 코드는 이렇다(`objdump`, 앞부분과 끝만).

```text
2000079c <irq_entry>:
2000079c:	sub	lr, lr, #4
200007a0:	push	{r0, r1, r2, r3, ip, lr}
200007a4:	mrrc	15, 0, r2, r3, cr14
200007a8:	mrc	15, 0, r0, cr12, cr12, {0}
...
20000814:	mcrr	15, 2, r3, r2, cr14
20000818:	mcr	15, 0, r0, cr12, cr12, {1}
2000081c:	ldm	sp!, {r0, r1, r2, r3, ip, pc}^
```

출력에서 볼 것:

- 세 번 다 같은 숫자 — icount라 결정적이다.
- S0 → S1: 진입이 5 명령 늘었다(`srsdb`, `cps`, 정렬 3개). **재진입을 허용하는 값이 5 명령**이다.
- S1과 S3의 진입 명령 수는 같다(11). `vpush {d0-d15}`가 명령 **1개**로 세어지기 때문이다. 실제 칩에서 이 명령은 128바이트를 쓰므로 수십 사이클이 걸린다. **QEMU icount는 명령 수만 세고 메모리 트래픽은 세지 않는다.** 그래서 오른쪽 그림의 "스택 워드 수"를 같이 봐야 한다.
- S2는 컴파일러가 본문(`body`)을 핸들러 안에 인라인해서 `bl`이 없고, 복귀를 `ldm sp!, {..., pc}^` 하나로 끝냈다. `^`가 붙은 PC 포함 `ldm`은 "레지스터 복원 + SPSR → CPSR"을 한 명령으로 한다. 가장 짧지만 **재진입 불가 · FPU 미저장**이다. 작은 bare-metal ISR에는 좋고, RTOS 커널 진입에는 못 쓴다.

### 5.4 예제 5 — 같은 측정을 Cortex-M3에서

무엇을 확인하나: `mps2-an385`(Cortex-M3)에서 CMSDK TIMER0 IRQ로 같은 측정을 한다. ISR은 **평범한 C 함수**이고 벡터 테이블에 주소만 들어 있다. 타이머는 25 MHz(40 ns)로 내려 세므로 `RELOAD - VALUE`가 만료 후 지난 tick이다.

```c
/* ex5 — the same measurement on Cortex-M3 (mps2-an385): hardware stacking, C function in vector */
#include "board.h"
static volatile uint32_t n;
static uint32_t lat[3], rt[3];
#define RELOAD 25000u                       /* 1 ms at 25 MHz, 1 tick = 40 ns */

void TIMER0_IRQHandler(void)                /* plain C function: no asm, no attribute */
{
    uint32_t v = TIMER_VALUE(TIMER0_BASE);  /* first thing in the C body */
    TIMER_INTCLR(TIMER0_BASE) = 1;
    if (n < 3) lat[n] = RELOAD - v;
    n++;
}

int main(void)
{
    TIMER_RELOAD(TIMER0_BASE) = RELOAD;
    TIMER_VALUE(TIMER0_BASE) = RELOAD;
    NVIC_IPR(8) = 0x80;
    NVIC_ISER0 = 1u << 8;
    TIMER_CTRL(TIMER0_BASE) = 0x9;          /* EN | IRQ EN */
    for (uint32_t seen = 0; seen < 3; ) {
        __asm volatile("wfi");
        uint32_t v = TIMER_VALUE(TIMER0_BASE);
        if (n > seen) { rt[seen] = RELOAD - v; seen = n; }
    }
    TIMER_CTRL(TIMER0_BASE) = 0;
    board_printf_raw("M3: deadline->C body = %u %u %u ticks(40ns) = %u ns, deadline->back in main = %u ns\n",
                     lat[0], lat[1], lat[2], lat[2] * 40, rt[2] * 40);
    return 0;
}
```

```text
   text	   data	    bss	    dec	    hex	filename
   4372	     96	    360	   4828	   12dc	/var/tmp/rtos/B9/ex5/app.elf
M3: deadline->C body = 2 2 2 ticks(40ns) = 80 ns, deadline->back in main = 520 ns
[board_exit] code=0
```

ISR의 생성 코드는 첫 명령부터 본문이다(앞 4줄).

```text
000000c0 <TIMER0_IRQHandler>:
      c0:	mov.w	r1, #1073741824	@ 0x40000000
      c4:	movs	r0, #1
      c6:	ldr	r3, [pc, #32]	@ (e8 <TIMER0_IRQHandler+0x28>)
      c8:	ldr	r2, [r1, #4]
```

출력에서 볼 것: 80 ns = 명령 2.5개 분량 — `ldr r2, [r1, #4]`(VALUE 읽기)가 네 번째 명령이니, 저장용 소프트웨어 명령은 **0개**다. 복귀도 `bx lr` 하나(하드웨어가 EXC_RETURN을 보고 8워드를 pop)다. 단, QEMU는 Cortex-M의 하드웨어 스태킹 사이클을 모델링하지 않는다(랩 README). 실제 Cortex-M3는 진입에 12 사이클이 걸린다고 Arm이 밝힌다. 그러니 "M3가 0 ns"가 아니라 **"M3는 그 일을 하드웨어가 고정 사이클로 한다, R은 소프트웨어가 명령으로 한다"** 가 정확한 결론이다.

### 5.5 예제 6 — objdump로 세는 정적 비용

무엇을 확인하나: 동적 측정과 별도로, 진입 스텁의 명령 수와 바이트 수를 `objdump`에서 직접 센다. Python 스크립트가 각 ELF의 `irq_entry`를 디스어셈블한다.

```python
# ex11 — static view: how many instructions/bytes does each IRQ entry stub cost? (objdump-based)
import subprocess, re
B = "/var/tmp/rtos/B9"
def func(elf, name, tool="arm-none-eabi-objdump"):
    out = subprocess.run([tool, "-d", "--no-show-raw-insn", elf], capture_output=True, text=True).stdout
    m = re.search(r"^[0-9a-f]+ <%s>:\n(.*?)(?:\n\n|\Z)" % re.escape(name), out, re.S | re.M)
    return [l.split("\t", 1)[1].strip() for l in m.group(1).splitlines() if "\t" in l and ".word" not in l]
rows = []
for s, label in [(0, "R52 S0 minimal (IRQ mode)"), (1, "R52 S1 reentrant SRS->SVC"),
                 (3, "R52 S3 full task ctx + FPU")]:
    ins = func(f"{B}/ex4_s{s}/app.elf", "irq_entry")
    bl = next(i for i, x in enumerate(ins) if x.startswith("bl"))
    rows.append((label, 1 + bl + 1, len(ins) - bl - 1, 4 * len(ins)))   # +1 = 'ldr pc' in vector
ins = func(f"{B}/ex4_s2/app.elf", "irq_entry")
first = next(i for i, x in enumerate(ins) if x.startswith("mrrc"))
rows.append(("R52 S2 gcc interrupt(\"IRQ\")", 1 + first, 2, None))
rows.append(("M3 plain C (hw stacking)", 0, 0, 0))
print(f"{'entry style':32s} {'sw insns before C':>18s} {'sw insns after C':>17s} {'stub bytes':>10s}")
for r in rows:
    print(f"{r[0]:32s} {r[1]:18d} {r[2]:17d} {('-' if r[3] is None else r[3]):>10}")
print("R52 S1 entry sequence:", " ; ".join(x.replace("\t", " ") for x in func(f"{B}/ex4_s1/app.elf", "irq_entry")[:8]))
```

```text
entry style                       sw insns before C  sw insns after C stub bytes
R52 S0 minimal (IRQ mode)                         4                 2         20
R52 S1 reentrant SRS->SVC                         9                 4         48
R52 S3 full task ctx + FPU                        9                 5         52
R52 S2 gcc interrupt("IRQ")                       3                 2          -
M3 plain C (hw stacking)                          0                 0          0
R52 S1 entry sequence: sub lr, lr, #4 ; srsdb sp!, #19 ; cps #19 ; push {r0, r1, r2, r3, ip, lr} ; and r1, sp, #4 ; sub sp, sp, r1 ; push {r1, r2} ; bl 2000079c <irq_c>
```

출력에서 볼 것: "C 전 명령 수"(벡터의 `ldr pc` 포함)가 동적 측정의 "C 본문까지 명령 수"와 거의 같다(S1: 정적 9 + 본문 앞 명령들 = 동적 11). 스텁 바이트는 20~52바이트, Cortex-M3는 0바이트(대신 벡터 테이블이 48칸 × 4바이트 = 192바이트, `g_vectors` 크기 `0xc0`). Cortex-R의 벡터 테이블은 명령 8개 + 리터럴 7개 = 60바이트로 오히려 작다. 인터럽트 번호별 분기는 소프트웨어 표(Zephyr `_sw_isr_table`)가 한다.

### 5.7 FPU — Cortex-M의 lazy stacking은 없다

B6에서 본 Cortex-M4F/M7은 FPU 레지스터 저장을 하드웨어가 **게으르게**(lazy stacking, FPCCR) 해 준다. Cortex-R에는 그런 하드웨어가 없다. 선택지는 셋이다.

| 방법 | 누가 쓰나 | 비용 |
|---|---|---|
| 모든 IRQ에서 VFP를 저장 (S3) | 단순한 bare-metal | IRQ마다 33워드 이상 |
| 태스크가 "나 FPU 쓴다"고 선언, 그 태스크만 저장 | FreeRTOS `vPortTaskUsesFPU()` · `ulPortTaskHasFPUContext` (`configUSE_TASK_FPU_SUPPORT` 1), 또는 모든 태스크(2) | 선언한 태스크만 |
| FPU를 꺼 두고 첫 VFP 명령의 UNDEF에서 저장 (소프트웨어 lazy) | Zephyr `CONFIG_FPU_SHARING` — `_isr_wrapper`가 `FPEXC`를 0으로 만들고, 주석대로 "The undefined instruction handler uses this to know that it needs to save the current floating context" | 실제로 FPU를 쓸 때만 |

FreeRTOS `ARM_CRx_No_GIC/portASM.S`의 `portSAVE_CONTEXT`는 이렇게 생겼다(원문 일부, 주석 줄 생략).

```asm
    SRSDB   SP!, #SYS_MODE
    CPS     #SYS_MODE
    PUSH    {R0-R12, R14}
    LDR     R2, =ulCriticalNesting
    LDR     R1, [R2]
    PUSH    {R1}
    LDR     R2, =ulPortTaskHasFPUContext
    LDR     R3, [R2]
    CMP     R3, #0
    VMRSNE  R1,  FPSCR
    VPUSHNE {D0-D15}
    PUSHNE  {R1}
    PUSH    {R3}
    LDR     R0, =pxCurrentTCB
    LDR     R1, [R0]
    STR     SP, [R1]
```

Cortex-M3 포트의 `xPortPendSVHandler`가 `stmdb r0!, {r4-r11, r14}` 한 줄로 끝나는 것(C2)과 비교하면, R 포트는 **하드웨어가 안 해 준 r0–r3 · r12 · LR · SPSR까지** 직접 저장한다. 크리티컬 섹션 중첩 카운트(`ulCriticalNesting`)도 태스크마다 저장한다 — Cortex-M 포트는 BASEPRI로 대신하는 부분이다(C7).

### 5.8 Don 경험과 연결

SSD 펌웨어에서 IRQ 진입 어셈블리를 손대 본 적이 있다면 아마 S0 또는 S1 모양이었을 것이다. 실행부(executive) 구조에서는 ISR이 큐에 이벤트만 넣고 끝나니 **재진입이 필요 없어서 S0**(IRQ 모드에서 끝내기)가 흔하다. RTOS를 올리면 ISR 끝에서 "더 높은 우선순위 태스크가 깨어났나?"를 보고 컨텍스트 스위치를 해야 하므로, 출구 경로가 길어지고 진입은 S1/S3 쪽으로 간다. 이 차이가 "RTOS를 올리면 인터럽트 지연이 늘어난다"의 실체다.

### 5.9 함정

- **`sub lr, lr, #4`를 빼먹기**: 복귀가 끼어든 명령 다음 명령으로 가서 **명령 하나를 건너뛴다.** 증상은 "가끔 변수 하나가 안 바뀜", "가끔 루프 카운터가 하나 덜 셈" — 아주 찾기 어렵다. (data abort는 `-8`, undefined는 0, SVC는 0이다 — 모드마다 다르다.)
- **`movs pc, lr`의 S를 빼먹기**: SPSR이 CPSR로 복원되지 않아 IRQ 모드에 갇힌 채 태스크 코드로 돌아간다.
- **8바이트 정렬 무시**: AAPCS는 공개 함수 호출 경계에서 SP 8바이트 정렬을 요구한다. 어긋나면 `strd` · `ldrd`나 VFP 64비트 접근이 정렬 fault를 내거나 `printf("%lld")`가 엉뚱한 값을 찍는다. FreeRTOS `FreeRTOS_IRQ_Handler`도 "Ensure bit 2 of the stack pointer is clear" 주석과 함께 `AND R2, R0, #4` · `SUB SP, SP, R2`를 한다.
- **GCC `interrupt` 속성 + FPU**: 위 경고 그대로다. `-mgeneral-regs-only` 또는 직접 VFP 저장.

## 6. MPU — PMSAv8-32와 2단계(EL1 MPU + EL2 MPU)

> 🔁 이 절은 Bare-Metal BM D9(MPU 설정 · R52 EL2)와 겹친다 (주인: 이 노트).

### 6.1 직관: 주소 변환 없는 "출입 명부"

MPU는 "이 주소 범위는 누가 · 읽기/쓰기/실행 중 무엇을 · 어떤 메모리 속성으로" 쓸 수 있는지 적은 **출입 명부**다. MMU처럼 주소를 바꾸지 않으므로 page table도 TLB miss도 없다. 그래서 접근 시간이 결정적이다. Cortex-M MPU(F 모듈)와 개념은 같지만, R은 세대마다 형식이 다르고 R52에는 **명부가 두 권**(EL1용, EL2용) 있다.

| 항목 | PMSAv7 (R5, Armv7-M도 비슷) | **PMSAv8-32 (R52)** |
|---|---|---|
| 영역 지정 | base + size(2의 거듭제곱), base는 size 정렬 | **base + limit**, 64바이트 단위 |
| 서브리전 | 8개로 쪼개 끄기 가능 | 없음 |
| 겹침 | 허용, 번호 큰 영역이 이김 | **겹치면 fault** (아래 예제에서 확인) |
| 속성 | TEX/C/B 비트 | **MAIR 인덱스** (Normal WB, Device-nGnRE …) |
| 레지스터 | DRBAR / DRSR / DRACR | **PRSELR → PRBAR / PRLAR**, MAIR0/1 |
| 단계 | 1단계 | **EL1 MPU + EL2 MPU(HPRBAR / HPRLAR)** |

### 6.2 예제 7 — EL1 MPU: 권한 fault, 영역 없음, 겹침

무엇을 확인하나: 영역 4개(DDR 코드/데이터, 주변장치, 읽기 전용 guard 페이지, **일부러 겹친 영역**)를 만들고 MPU를 켠 뒤 (1) guard 읽기, (2) guard 쓰기, (3) 영역 밖 읽기, (4) 겹친 곳 읽기, (5) 겹치지 않은 곳 읽기를 한다. Data Abort 핸들러가 DFSR · DFAR를 찍고 그 명령을 건너뛴다.

```c
/* ex6 — EL1 MPU (PMSAv8-32) on R52: regions, permission fault, background fault, overlap fault */
#include "r52.h"
void el2_hook(void) { uart_init(); }

static void mpu_region(uint32_t idx, uint32_t prbar, uint32_t prlar)
{
    WR_CP15(0, c6, c2, 1, idx);      /* PRSELR */
    ISB();
    WR_CP15(0, c6, c3, 0, prbar);    /* PRBAR: base | SH<<3 | AP<<1 | XN */
    WR_CP15(0, c6, c3, 1, prlar);    /* PRLAR: limit | AttrIndx<<1 | EN */
}

/* data abort: LR_abt = faulting instruction + 8 */
__attribute__((naked)) void dabt_entry(void)
{
    __asm volatile("sub lr, lr, #8\n push {r0-r3, r12, lr}\n mov r0, lr\n bl dabt_c\n"
                   "pop {r0-r3, r12, lr}\n add lr, lr, #4\n movs pc, lr\n");  /* skip it */
}
static volatile int faults;
void dabt_c(uint32_t pc)
{
    uint32_t dfsr = RD_CP15(0, c5, c0, 0), dfar = RD_CP15(0, c6, c0, 0);
    uint32_t st = dfsr & 0x3f;
    printf("  DataAbort pc=0x%08x DFAR=0x%08x DFSR=0x%08x STATUS=0x%02x (%s) WnR=%u\n", pc, dfar, dfsr, st,
           (st & 0x3c) == 0x0c ? "permission" : (st & 0x3c) == 0x04 ? "translation/background" : "other",
           (dfsr >> 11) & 1);
    faults++;
}

int main(void)
{
    printf("MPUIR regions=%u\n", (RD_CP15(0, c0, c0, 4) >> 8) & 0xff);
    WR_CP15(0, c10, c2, 0, 0x04FF);                     /* MAIR0: attr0=Normal WB, attr1=Device-nGnRE */
    mpu_region(0, 0x20000000 | 0,          0x20EFFFC0 | (0 << 1) | 1); /* DDR code/data, EL1 RW */
    mpu_region(1, 0xE0000000 | 1,          0xFFFFFFC0 | (1 << 1) | 1); /* peripherals, device, XN */
    mpu_region(2, 0x20F00000 | (2 << 1) | 1, 0x20F00FC0 | 1);         /* guard page: EL1 read-only */
    mpu_region(3, 0x20E00000 | 1,          0x20E00FC0 | 1);           /* overlaps region 0! */
    uint32_t sctlr = RD_CP15(0, c1, c0, 0);
    sctlr &= ~(1u << 17);                               /* BR=0: no background region */
    DSB();
    WR_CP15(0, c1, c0, 0, sctlr | 1);                   /* SCTLR.M = 1: MPU on */
    ISB();
    printf("MPU on, SCTLR=0x%08x\n", RD_CP15(0, c1, c0, 0));

    volatile uint32_t *guard = (uint32_t *)0x20F00000, *hole = (uint32_t *)0x30000000;
    volatile uint32_t *ovl = (uint32_t *)0x20E00000;
    printf("1) read guard  -> %u\n", *guard);
    printf("2) write guard\n");   *guard = 1;
    printf("3) read 0x30000000 (no region)\n"); (void)*hole;
    printf("4) read 0x20E00000 (two regions match)\n"); (void)*ovl;
    printf("5) read 0x20E01000 (region 0 only) -> %u\n", ovl[1024]);
    printf("faults=%d\n", faults);
    return 0;
}
```

```text
MPUIR regions=16
MPU on, SCTLR=0x30c50839
1) read guard  -> 0
2) write guard
  DataAbort pc=0x2000092c DFAR=0x20f00000 DFSR=0x00000a0c STATUS=0x0c (permission) WnR=1
3) read 0x30000000 (no region)
  DataAbort pc=0x20000944 DFAR=0x30000000 DFSR=0x0000020c STATUS=0x0c (permission) WnR=0
4) read 0x20E00000 (two regions match)
  DataAbort pc=0x20000960 DFAR=0x20e00000 DFSR=0x0000020c STATUS=0x0c (permission) WnR=0
5) read 0x20E01000 (region 0 only) -> 0
faults=3
```

출력에서 볼 것:

- (2) 쓰기 fault: `WnR=1`, DFAR가 정확히 guard 주소. 스택 오버플로 guard를 이렇게 만든다(F 모듈, Zephyr `CONFIG_MPU_STACK_GUARD`).
- (3) `SCTLR.BR = 0`(background 영역 없음)이라 영역 밖은 전부 fault다. EL1 MPU를 켜면 **주변장치 영역을 빠뜨린 순간 UART printf부터 죽는다** — 그래서 region 1을 먼저 만들었다.
- (4) **겹친 주소는 region 0에도 있는데 fault**가 났다. PMSAv8은 "번호 큰 영역 우선"이 아니다. R5(PMSAv7) 코드를 R52로 옮길 때 가장 흔한 함정이다.
- DFSR bit 9 = 1(`0x200`) — long-descriptor 형식의 상태 코드라는 뜻이다. QEMU는 세 경우 모두 STATUS `0x0C`(level 0 permission fault)로 보고했다. 즉 **DFSR만으로는 "권한 위반 · 영역 없음 · 겹침"을 구분할 수 없다** — 핸들러가 DFAR를 MPU 영역표와 대조해야 한다. (실칩도 같은 코드를 쓰는지는 TRM에서 확인 못 함.)

무엇을 확인하나: `el2_hook()`(EL2)에서 게스트용 창(DDR 0x20000000–0x20EFFFFF + 주변장치)만 EL2 MPU에 등록하고 `HCR.VM = 1`로 켠다. EL1 게스트가 창 밖(0x20F00000)에 쓰면 EL2로 트랩되는지, `HVC`가 EL2로 오는지 본다.

```c
/* ex7 — R52 EL2 MPU as "stage 2": hypervisor confines EL1; guest console via HVC; faults trap to EL2 */
#include "r52.h"

static void hmpu_region(uint32_t idx, uint32_t hprbar, uint32_t hprlar)
{
    WR_CP15(4, c6, c2, 1, idx);      /* HPRSELR */
    ISB();
    WR_CP15(4, c6, c3, 0, hprbar);   /* HPRBAR */
    WR_CP15(4, c6, c3, 1, hprlar);   /* HPRLAR */
}

void el2_hook(void)                  /* runs in Hyp mode before the ERET to EL1 */
{
    uart_init();
    WR_CP15(4, c10, c2, 0, 0x04FF);                          /* HMAIR0 */
    hmpu_region(0, 0x20000000 | (1 << 1),      0x20EFFFC0 | 1);           /* DDR: RW for EL1/EL0 */
    hmpu_region(1, 0xE0000000 | (1 << 1) | 1,  0xFFFFFFC0 | (1 << 1) | 1); /* periph, device, XN */
    /* 0x20F00000.. is NOT given to the guest */
    uint32_t hcr = RD_CP15(4, c1, c1, 0);
    WR_CP15(4, c1, c1, 0, hcr | 1);                          /* HCR.VM = 1: EL2 MPU checks EL1&0 */
    ISB();
    printf("[EL2] HCR=0x%08x, guest window = 0x20000000-0x20EFFFFF + periph\n", RD_CP15(4, c1, c1, 0));
}

/* Hyp Trap vector (HVBAR+0x14): exceptions from EL1/EL0 that are routed to EL2 */
__attribute__((naked)) void hyp_trap(void)
{
    __asm volatile("push {r0-r3, r12, lr}\n mrs r0, elr_hyp\n mov r1, sp\n bl hyp_trap_c\n"
                   "msr elr_hyp, r0\n pop {r0-r3, r12, lr}\n eret\n");
}

uint32_t hyp_trap_c(uint32_t elr, uint32_t *frame)
{
    uint32_t hsr = RD_CP15(4, c5, c2, 0), ec = hsr >> 26;
    if (ec == 0x12 && (hsr & 0xffff) == 1) { printf("%s", (const char *)frame[0]); return elr; } /* guest putc */
    if (ec == 0x12 && (hsr & 0xffff) == 2) { printf("0x%08x", frame[0]); return elr; }
    printf("  [EL2 trap] mode=0x%x HSR=0x%08x EC=0x%02x ", get_cpsr() & 0x1f, hsr, ec);
    if (ec == 0x24) {                                        /* data abort from lower EL */
        printf("guest data abort HDFAR=0x%08x at pc=0x%08x -> skip\n", RD_CP15(4, c6, c0, 0), elr);
        return elr + 4;
    }
    if (ec == 0x12) {                                        /* HVC from EL1 */
        printf("HVC #%u from guest\n", hsr & 0xffff);
        return elr;                                          /* ELR already points after HVC */
    }
    printf("unhandled\n");
    qemu_exit(1);
    return elr;
}

/* guest (EL1) has no UART access: QEMU 10.2.1 crashes on EL1 MMIO when HCR.VM=1 (see note) */
static void gputs(const char *str) { register const char *r0 __asm("r0") = str; __asm volatile("hvc #1" :: "r"(r0) : "memory"); }
static void gputx(uint32_t v) { register uint32_t r0 __asm("r0") = v; __asm volatile("hvc #2" :: "r"(r0) : "memory"); }

int main(void)
{
    gputs("[EL1] guest running, CPSR="); gputx(get_cpsr()); gputs("\n");
    volatile uint32_t *inside = (uint32_t *)0x20E00000, *outside = (uint32_t *)0x20F00000;
    *inside = 7;
    gputs("[EL1] wrote inside window, read back "); gputx(*inside); gputs("\n");
    gputs("[EL1] writing outside window...\n");
    *outside = 7;
    gputs("[EL1] continued after the hypervisor skipped it\n");
    __asm volatile("hvc #7" ::: "memory");
    gputs("[EL1] back from HVC #7\n");
    return 0;
}
```

```text
[EL2] HCR=0x00000001, guest window = 0x20000000-0x20EFFFFF + periph
[EL1] guest running, CPSR=0x000001d3
[EL1] wrote inside window, read back 0x00000007
[EL1] writing outside window...
  [EL2 trap] mode=0x1a HSR=0x9382004c EC=0x24 guest data abort HDFAR=0x20f00000 at pc=0x20000970 -> skip
[EL1] continued after the hypervisor skipped it
  [EL2 trap] mode=0x1a HSR=0x4a000007 EC=0x12 HVC #7 from guest
[EL1] back from HVC #7
```

출력에서 볼 것:

- 게스트의 창 밖 쓰기가 **EL1 Data Abort가 아니라 EL2 Hyp Trap**(모드 0x1A)으로 갔다. `HSR.EC = 0x24`(하위 EL에서 온 data abort), `HSR` 하위의 `0x4c` = WnR(bit 6) + DFSC `0x0C`. `HDFAR` = 문제 주소, `ELR_hyp` = 문제 명령 주소다.
- `HVC #7`은 `EC = 0x12`, `HSR` 하위 16비트가 HVC 번호다. 하이퍼바이저 콜(hypercall)의 기본 형태다.
- 이 예제의 게스트 printf는 **UART가 아니라 HVC 1 · 2로 하이퍼바이저에게 부탁한다**(반가상화 콘솔). 왜 그랬는지가 다음 함정이다.

### 6.4 함정 — QEMU 10.2.1에서 HCR.VM + EL1 MMIO = QEMU 세그폴트

이 예제의 첫 버전은 EL1에서 평소처럼 UART printf를 했다. 결과는 QEMU 프로세스가 죽는 것이었다.

```text
[EL2] HCR=0x00000001, guest window = 0x20000000-0x20EFFFFF + periph
exit=139
bash: line 1: 1395109 Segmentation fault         ./run.sh /var/tmp/rtos/B9/ex7/app.elf
```

`-d int,mmu,in_asm` 로그의 마지막 줄은 EL1의 UART 상태 레지스터 읽기에 대한 MPU 조회였다.

```text
PMSA MPU lookup for reading at 0xe7c00004 mmu_idx 65 -> Hit (prot rw-)
PMSA MPU lookup for reading at 0xe7c00004 mmu_idx 49 -> Hit (prot rw-)
```

두 단계 모두 Hit인데 그 직후 QEMU가 죽었다. 공유 UART(0xE0205000, `-serial null -serial null -serial stdio`)로 바꿔도, EL2 영역의 XN · 속성을 바꿔도 똑같이 죽었다. DDR 접근(코드 · 데이터)은 2단계 검사를 정상 통과했다. 즉 **QEMU 10.2.1의 R52 모델에서 "HCR.VM = 1 상태의 EL1 MMIO 접근"이 에뮬레이터 버그를 밟는다.** 실칩 동작과는 무관하다. 그래서 게스트는 MMIO를 건드리지 않고 HVC로 출력하게 바꿨다 — 실제 하이퍼바이저에서도 쓰는 방식(반가상화 콘솔)이라 공부에는 오히려 좋다. (QEMU 업스트림 이슈 등록 여부는 확인 못 함.)

## 7. TCM과 ECC 초기화

> 🔁 이 절은 Bare-Metal BM D9(TCM ECC 초기화)와 겹친다 (주인: 이 노트).

### 7.1 직관: 코어 바로 옆 책상 서랍

TCM(Tightly Coupled Memory)은 캐시가 아니라 **코어 전용 SRAM**이다. 캐시처럼 hit/miss가 없으니 접근 시간이 항상 같다. 그래서 인터럽트 벡터 · ISR · 스택 · 제어 루프 데이터처럼 "늦으면 안 되는 것"을 둔다. B8에서 본 Cortex-M7 ITCM/DTCM과 같은 생각이고, Cortex-R에서는 더 오래되고 더 중심적인 기능이다.

| 항목 | R5 | R52 |
|---|---|---|
| TCM 개수 | ATCM, BTCM(B0 / B1 두 뱅크) | ATCM, BTCM, CTCM |
| 위치 지정 · 켜기 | CP15 TCM region 레지스터(c9, c1) — base · size · enable | `IMP_ATCMREGIONR` / `IMP_BTCMREGIONR` / `IMP_CTCMREGIONR` (`MRC p15, 0, Rt, c9, c1, 0/1/2`) — base · size · EL1/EL2 enable |
| ECC 켜기 | ACTLR의 ATCMPCEN · B0TCMPCEN · B1TCMPCEN (Zephyr `tcm.c`가 이 비트를 끄는 `z_arm_tcm_disable_ecc()`를 가짐) | 구현 정의 레지스터 — 정확한 비트는 TRM 확인(이 노트에서는 확인 못 함) |
| 리셋 시 위치 | 구성 핀(예: ATCM을 0번지에) | 구성 핀 + region 레지스터 |

### 7.2 ECC 초기화 규칙 — 왜 부팅 때 TCM을 지우나

ECC TCM은 데이터 64비트(granule)마다 ECC 비트를 함께 저장한다. 전원을 켠 직후 SRAM 내용은 쓰레기이고 **ECC 비트도 쓰레기**다. 이 상태에서

- 읽으면: ECC 검사가 실패해 **정정 불가 오류 → abort**가 난다.
- 바이트 · 하프워드 · 워드로 쓰면: 하드웨어가 granule의 나머지 바이트를 **읽어서(read-modify-write)** ECC를 다시 계산하는데, 그 읽기가 쓰레기 ECC를 만나 역시 오류가 난다.

그래서 startup 맨 앞에서 **ECC 검사를 끈 상태로, 또는 아직 아무도 읽지 않은 상태에서, granule 전체를 쓰는 64비트 정렬 쓰기(STRD · STM)로 TCM 전체를 한 번 채운다.** 그 뒤에야 `.data` 복사, 스택 사용, ECC 검사 켜기를 한다. Don이 SSD 부트 코드에서 봤던 "TCM 전체 zero-fill 루프"가 이것이다.

### 7.3 예제 9 — QEMU의 TCM, 그리고 초기화 루프 비용

무엇을 확인하나: (1) QEMU가 `IMP_xTCMREGIONR`를 구현하는지(UNDEF 핸들러로 잡을 준비를 해 둔다), (2) 0번지 ATCM과 0xEE000000 ATCM0이 같은 메모리인지, (3) 32 KB를 0으로 채우는 루프 세 가지(바이트 · 워드 · STM 8레지스터)의 명령 수.

```c
/* ex8 — TCM on R52 (QEMU AN536): IMP_xTCMREGIONR, aliasing, ECC-style init cost (64-bit stores) */
#include "r52.h"
static volatile int undef_hits;
void el2_hook(void) { uart_init(); }

/* UNDEF: LR_und = faulting instruction + 4 (ARM state) -> just return to skip it */
__attribute__((naked)) void undef_entry(void)
{
    __asm volatile("push {r0-r3, r12, lr}\n bl undef_c\n pop {r0-r3, r12, lr}\n movs pc, lr\n");
}
void undef_c(void) { undef_hits++; }

static void tcm_regs(void)
{
    uint32_t a = 0xdeadbeef, b = 0xdeadbeef, c = 0xdeadbeef;
    __asm volatile("mrc p15, 0, %0, c9, c1, 0" : "+r"(a));   /* IMP_ATCMREGIONR */
    __asm volatile("mrc p15, 0, %0, c9, c1, 1" : "+r"(b));   /* IMP_BTCMREGIONR */
    __asm volatile("mrc p15, 0, %0, c9, c1, 2" : "+r"(c));   /* IMP_CTCMREGIONR */
    printf("ATCMREGIONR=0x%08x BTCMREGIONR=0x%08x CTCMREGIONR=0x%08x undef_hits=%d\n", a, b, c, undef_hits);
}

static uint32_t t_insn(uint64_t t0) { return (uint32_t)((CNTPCT() - t0) / 2); }  /* icount: 2 ticks = 1 insn */

int main(void)
{
    tcm_regs();
    volatile uint32_t *atcm_lo, *atcm_hi = (uint32_t *)0xEE000000;
    __asm volatile("mov %0, #0" : "=r"(atcm_lo));     /* address 0 without -Warray-bounds noise */
    atcm_lo[4] = 0x1234;
    printf("write 0x1234 @0x00000010, read @0xEE000010 = 0x%x  (%s)\n", atcm_hi[4],
           atcm_hi[4] == 0x1234 ? "same RAM" : "different RAM");

    /* ECC TCM rule: write every 64-bit granule before the first read. Compare loops on 32 KB */
    uint64_t t0 = CNTPCT();
    for (volatile uint8_t *p = (uint8_t *)0xEE100000; p < (uint8_t *)0xEE108000; p++) *p = 0;
    uint32_t n_byte = t_insn(t0);

    t0 = CNTPCT();
    for (volatile uint32_t *p = (uint32_t *)0xEE100000; p < (uint32_t *)0xEE108000; p++) *p = 0;
    uint32_t n_word = t_insn(t0);

    t0 = CNTPCT();
    __asm volatile(
        "ldr r0, =0xEE100000\n ldr r1, =0xEE108000\n"
        "mov r2, #0\n mov r3, #0\n mov r4, #0\n mov r5, #0\n"
        "mov r6, #0\n mov r7, #0\n mov r8, #0\n mov r9, #0\n"
        "1: stmia r0!, {r2-r9}\n cmp r0, r1\n blo 1b\n"     /* 32 bytes = 4 granules per STM */
        ::: "r0", "r1", "r2", "r3", "r4", "r5", "r6", "r7", "r8", "r9", "memory");
    uint32_t n_stm = t_insn(t0);
    printf("zero 32KB BTCM: byte loop %u insns, word loop %u insns, STM 8 regs %u insns\n",
           n_byte, n_word, n_stm);
    return 0;
}
```

```text
ATCMREGIONR=0x00000000 BTCMREGIONR=0x00000000 CTCMREGIONR=0x00000000 undef_hits=0
write 0x1234 @0x00000010, read @0xEE000010 = 0x0  (different RAM)
zero 32KB BTCM: byte loop 98310 insns, word loop 24583 insns, STM 8 regs 3084 insns
```

출력에서 볼 것:

- QEMU는 TCM region 레지스터를 **읽으면 0(RAZ)** 으로 구현했다(UNDEF 아님). 실칩이라면 base · size · enable 비트가 보였을 것이다. 즉 QEMU AN536은 TCM을 "주소에 붙은 RAM"으로만 흉내 낸다.
- 0번지의 ATCM과 0xEE000000의 ATCM0은 **서로 다른 RAM**이다(`info mtree`에서도 이름이 `ATCM`과 `ATCM0`로 따로였다). 실제 AN536 FPGA 이미지에서는 별칭(alias)일 수 있지만 QEMU에서는 아니다. TCM 별칭에 기대는 코드는 QEMU에서 검증할 수 없다.
- **ECC는 QEMU가 모델링하지 않는다.** 초기화하지 않고 읽어도 아무 일이 없다. 그래서 이 노트는 "ECC 오류를 재현"하지 못하고, 대신 초기화 루프의 비용만 잰다.
- 32 KB를 지우는 데 바이트 루프 98,310 명령 vs STM 3,084 명령 — **32배 차이**다. TCM이 1 MB라면 바이트 루프는 300만 명령이 넘는다. 부팅 시간 예산이 있는 차량 ECU(예: 수십 ms 안에 CAN 응답)에서는 이 차이가 실제 요구사항을 가른다.

### 7.4 RTOS와 연결

- Zephyr: `arch/arm/core/cortex_a_r/reset.S`에 `CONFIG_DISABLE_TCM_ECC`이면 `bl z_arm_tcm_disable_ecc`가 있고, `tcm.c`는 Armv7-R에서 ACTLR의 ATCM/B0TCM/B1TCM ECC 비트를 끈다. `fault.c`는 "Synchronous Parity/ECC Error @ 0x%08x"를 출력하는 경로를 가진다. 링커 쪽에서는 DT의 `zephyr,itcm` · `zephyr,dtcm` chosen 노드와 `__itcm_text` 같은 섹션 매크로로 코드를 TCM에 둔다(H 모듈).
- FreeRTOS: 커널은 TCM을 모른다. 링커 스크립트에서 `.text`의 ISR · `tasks.c`의 핫 함수 · 태스크 스택(`xTaskCreateStatic`에 TCM 배열을 넘김)을 TCM 섹션에 넣는 것은 BSP의 일이다.

## 8. lockstep(DCLS)과 안전 — QEMU로 보여 줄 수 없는 것

> 🔁 이 절은 Bare-Metal BM D9(lockstep DCLS)와 겹친다 (주인: 이 노트).

### 8.1 직관: 같은 시험을 두 명이 동시에 푼다

DCLS(Dual-Core Lock-Step)는 **같은 코어 두 개가 같은 입력으로 같은 명령을 매 사이클 함께 실행**하고, 비교기가 두 코어의 출력을 비교하는 구성이다. 우주선 · 방사선 · 전압 글리치로 한쪽 플립플롭이 뒤집히면 출력이 달라지고, 비교기가 오류 신호를 낸다. 소프트웨어가 눈치채지 못하는 계산 오류를 하드웨어가 잡는 것이 목적이다(ISO 26262 ASIL D의 단골 수단). 코어 하나 분량의 소프트웨어만 보이므로 프로그래머 입장에서는 **코어 하나**다.

### 8.2 펌웨어가 해야 하는 일

**1. 레지스터 전부를 리셋 직후 정의된 값으로**: 리셋은 레지스터를 0으로 만들지 않는다. 두 코어의 초기화 안 된 레지스터 값이 다르면, 그 값을 처음 스택에 push하는 순간(값이 버스로 나가는 순간) 비교기가 불일치를 본다. Zephyr v4.4.2 `reset.S`의 `CONFIG_DCLS` 블록은 주석 그대로 "Initialise CPU registers to a defined state if the processor is configured as Dual-redundant Core Lock-step (DCLS). This is required for state convergence of the two parallel executing cores." 를 하고, SVC · FIQ(r8–r12 포함) · IRQ · ABT · UND · SYS 모드를 돌며 r13 · r14 · SPSR까지 0으로 채운다. FPU가 있으면 VFP 레지스터도 채운다.

**2. 메모리도 같은 이유로**: 두 코어가 같은 TCM/캐시를 읽으므로 메모리 자체는 하나지만, ECC 초기화(§7)를 하지 않으면 첫 읽기가 ECC 오류를 낸다.

**3. 오류 처리 경로**: 비교 오류는 보통 코어 밖 안전 관리자(예: NVIDIA FSI의 Hardware Safety Manager가 SOC_ERROR를 올린다 — NVIDIA DriveOS 문서)로 가서 리셋 · 안전 상태 전이를 일으킨다. 펌웨어는 부팅 때 "지난번 리셋이 lockstep 오류였나"를 읽어 기록하고(E8 워치독 리셋 원인 기록과 같은 패턴), 자가 진단(비교기 자체를 테스트하는 STL — Software Test Library)을 주기적으로 돌린다.

### 8.3 정직하게 — QEMU에서 안 되는 것

QEMU `mps3-an536`은 DCLS를 모델링하지 않는다(코어 하나를 에뮬레이션하고 비교기가 없다). 그래서 이 절은 실행 예제가 없다. 위의 Zephyr 코드는 `CONFIG_DCLS`(`depends on CPU_HAS_DCLS`, 기본 y)가 켜진 SoC에서만 빌드된다. 실제로 검증하려면 lockstep을 지원하는 개발 보드(예: TI · NXP의 R5F/R52 lockstep 칩)와 벤더의 오류 주입(fault injection) 기능이 필요하다.

## 9. RTOS를 Cortex-R에 올리기 — FreeRTOS와 Zephyr 실습

### 9.1 FreeRTOS V11.3.2의 Cortex-R 포트 지도

`/var/rtoslab/src/FreeRTOS-Kernel/portable/GCC/`에서 직접 확인한 목록이다.

| 포트 폴더 | 대상 | 인터럽트 컨트롤러 | 특징 |
|---|---|---|---|
| `ARM_CR5` | Cortex-R4/R5 (Armv7-R) | **GICv2 메모리 맵 CPU 인터페이스** (`portICCIAR...OFFSET 0x0C` 등) | 우선순위 마스킹으로 크리티컬 섹션(ICCPMR) |
| `ARM_CRx_No_GIC` | Armv7-R / v8-R AArch32 일반 | **없음 — 앱이 `vApplicationIRQHandler`에서 직접** | 크리티컬 섹션 = `CPSID I` (전역 마스킹) |
| `ARM_CRx_MPU` | Cortex-R + MPU 격리 | — | `mpu_wrappers_v2_asm.S`, 태스크별 MPU 영역 |
| `ARM_CR82` | Cortex-R82 (Armv8-R **AArch64**) | GICv3 (`ICC_PMR_EL1`) | V11.3.0(2026-03)에 non-MPU SMP 포트 + MPU 지원 추가(History.txt), `configNUMBER_OF_CORES` |

R52(GICv3 + AArch32)에 딱 맞는 GCC 포트는 없다. `ARM_CR5`는 GICv2 MMIO를 가정하고, `ARM_CR82`는 AArch64다. 그래서 이 노트는 **`ARM_CRx_No_GIC` + 직접 쓴 GICv3/generic timer glue**를 썼다. 실무에서 R52에 FreeRTOS를 올릴 때도 벤더 SDK(NXP S32 · Renesas · TI)가 이런 glue를 BSP로 제공하는 것이 보통이다.

### 9.2 예제 10 — FreeRTOS on Cortex-R52 (그리고 같은 시험을 M3에서)

무엇을 확인하나: `ARM_CRx_No_GIC` 포트가 요구하는 훅 세 개(`configSETUP_TICK_INTERRUPT`, `configCLEAR_TICK_INTERRUPT`, `configEOI_ADDRESS`)와 `vApplicationIRQHandler`를 R52용으로 채워 FreeRTOS를 띄운다. 태스크가 어느 모드에서 도는지, `vTaskDelay`가 tick으로 깨어나는지, task notification ping-pong 1,000회의 스위치 비용이 얼마인지 본다.

포트 훅 설정(`FreeRTOSConfig.h`) 중 R52 전용 부분이다.

```c
/* port hooks (ARM_CRx_No_GIC): tick = EL1 physical generic timer via GICv3 PPI 30 */
#ifndef __ASSEMBLER__
#include <stdint.h>
extern volatile uint32_t ulDummyEOI;
void vSetupTickTimer(void);
void vClearTickTimer(void);
#endif
#define configSETUP_TICK_INTERRUPT()            vSetupTickTimer()
#define configCLEAR_TICK_INTERRUPT()            vClearTickTimer()
#define configEOI_ADDRESS                       ( ( uint32_t ) &ulDummyEOI )  /* EOI done via ICC_EOIR1 */
#define configASSERT( x )                       do { if( !( x ) ) { for( ;; ) { } } } while( 0 )
#endif
```

`configEOI_ADDRESS`는 포트 어셈블리가 IRQ 끝에서 "그 주소에 한 번 쓴다"(GICv2 EOIR을 가정한 설계)라서, GICv3에서는 EOI를 C에서 `ICC_EOIR1`로 하고 이 주소는 더미 변수로 둔다. 벡터 연결은 링커 옵션 `--defsym=irq_entry=FreeRTOS_IRQ_Handler --defsym=svc_entry=FreeRTOS_SVC_Handler`로 했다(startup의 weak 핸들러를 덮어쓴다, 추가 분기 명령 0개).

```c
/* ex9 — FreeRTOS V11.3.2 on Cortex-R52 (ARM_CRx_No_GIC port + our GICv3/generic-timer glue) */
#include "r52.h"
#include "FreeRTOS.h"
#include "task.h"

volatile uint32_t ulDummyEOI;
static const uint32_t period = 62500;           /* 62.5 MHz / 1000 Hz */
void el2_hook(void) { uart_init(); }

void vSetupTickTimer(void)
{
    gic_init_ppi(INTID_CNTP, 0xA0);
    SET_CNTP_CVAL(CNTPCT() + period);
    SET_CNTP_CTL(1);
}
void vClearTickTimer(void) { SET_CNTP_CVAL(CNTP_CVAL() + period); }

extern void FreeRTOS_Tick_Handler(void);
void vApplicationIRQHandler(void)               /* called by FreeRTOS_IRQ_Handler in SVC mode */
{
    uint32_t iar = ICC_IAR1();
    if ((iar & 0xffffff) == INTID_CNTP) FreeRTOS_Tick_Handler();
    ICC_EOIR1(iar);
}

static TaskHandle_t hPing, hPong;
#define ROUNDS 1000
static void pong(void *arg)
{
    (void)arg;
    for (;;) { ulTaskNotifyTake(pdTRUE, portMAX_DELAY); xTaskNotifyGive(hPing); }
}
static void ping(void *arg)
{
    (void)arg;
    printf("ping task: CPSR=0x%08x (mode 0x%x = SYS)\n", get_cpsr(), get_cpsr() & 0x1f);
    vTaskDelay(pdMS_TO_TICKS(3));
    printf("after vTaskDelay(3): tick=%u\n", (unsigned)xTaskGetTickCount());
    uint64_t t0 = CNTPCT();
    for (int i = 0; i < ROUNDS; i++) { xTaskNotifyGive(hPong); ulTaskNotifyTake(pdTRUE, portMAX_DELAY); }
    uint32_t ticks = (uint32_t)(CNTPCT() - t0);
    printf("%d ping-pong rounds (2 switches each): %u timer ticks -> %u insns per switch (icount)\n",
           ROUNDS, ticks, ticks / 2 / (2 * ROUNDS));
    qemu_exit(0);
}

int main(void)
{
    printf("main in mode 0x%x, starting scheduler\n", get_cpsr() & 0x1f);
    xTaskCreate(ping, "ping", 512, NULL, 2, &hPing);
    xTaskCreate(pong, "pong", 512, NULL, 3, &hPong);
    vTaskStartScheduler();
    return 1;
}
```

그림 8 — 같은 FreeRTOS 설정 · 같은 ping-pong에서 스위치 1회당 명령 수와 `.text` 크기(측정). R52 이미지에는 우리 printf · GIC glue도 들어 있어 크기 비교는 대략적이다.

출력에서 볼 것:

- `main`은 SVC(0x13)에서 돌고, **태스크는 SYS(0x1F)** 에서 돈다 — `portINITIAL_SPSR = 0x01f` 그대로다.
- `vTaskDelay(3)` 뒤 tick = 3 — generic timer → GICv3 PPI 30 → `FreeRTOS_IRQ_Handler` → `vApplicationIRQHandler` → `FreeRTOS_Tick_Handler` 경로가 정상이다.
- 스위치 1회: M3 273 명령, R52 320~327 명령. **커널 C 코드(`vTaskSwitchContext`, notify API)는 같고, 차이 약 50 명령은 포트**에서 온다. M3는 PendSV가 r4–r11만 저장하면 되지만, R52 포트는 SVC 진입에서 r0–r12 · LR · SPSR · 크리티컬 중첩 카운트 · FPU 플래그를 소프트웨어로 저장한다. 다시 말하지만 이것은 **명령 수**다. 실칩 사이클은 R52가 훨씬 높은 클럭과 이중 발행(dual issue)을 가지므로 절대 시간은 R52가 보통 더 빠르다.
- R52 yield는 PendSV가 아니라 **`SVC 0`**(`vPortYield`)이고, ISR 안의 스위치는 `FreeRTOS_IRQ_Handler`의 출구(`switch_before_exit`)에서 한다. Cortex-M의 "가장 낮은 우선순위 PendSV로 미루기"(B4)에 해당하는 장치가 없다 — 대신 **중첩 카운트가 0일 때만** 스위치한다(`ulPortInterruptNesting`).

### 9.3 예제 11 — Zephyr v4.4.2 on AN536: 보드가 없을 때 옮겨 심기

먼저 사실 확인: Zephyr v4.4.2 트리에는 **AN536 보드가 없다**(`grep -ril an536 boards soc dts` 결과 없음). R52 보드는 `fvp_baser_aemv8r`(Arm FVP 전용, QEMU 아님)와 실칩 보드들이다. 그래서 순서대로 해 봤다.

(1) FVP 보드를 그대로 빌드하면 빌드는 된다.



(2) 그 이미지를 QEMU AN536에서 돌리면 **아무것도 안 나온다**(5초 timeout).


이유: FVP 보드의 콘솔은 PL011 UART(0x9C090000), GIC는 0xAF000000, RAM은 0x0이다. AN536에는 셋 다 그 주소에 없다.

(3) overlay로 GIC와 RAM을 AN536 주소로 옮기고 PL011을 끈다. 콘솔은 Zephyr `CONFIG_SEMIHOST_CONSOLE`을 쓰려 했더니 빌드가 실패했다.


`semihost.c`는 `CONFIG_ISA_ARM` 또는 `CONFIG_ISA_THUMB2`를 요구하는데, `cortex_a_r/Kconfig`에서 이 심볼을 select하는 것은 `ARMV7_A` · `ARMV7_R`뿐이고 **Armv8-R(`AARCH32_ARMV8_R`)은 select하지 않는다.** v4.4.2의 빈틈이다. 그래서 앱에 printk 훅(semihosting `SYS_WRITEC`)을 직접 넣었다.

(4) 마지막으로, 타이머 주파수: FVP 보드 기본값은 100 MHz인데 QEMU AN536의 `CNTFRQ`는 62.5 MHz(예제 1)다. 고치지 않으면 Zephyr의 시간이 0.625배로 흐른다. `CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC=62500000`으로 맞췄다.

```c

#include <zephyr/kernel.h>
#include <zephyr/version.h>
#include <zephyr/init.h>
#include <zephyr/sys/printk-hooks.h>

/* Zephyr v4.4.2 SEMIHOST does not build for Armv8-R (#error Unsupported ISA) and the
 * board's PL011 does not exist on AN536 -> our own printk hook: semihosting SYS_WRITEC */
static int semi_putc(int c)
{
    char ch = (char)c;
    register uint32_t r0 __asm__("r0") = 0x03;      /* SYS_WRITEC */
    register char *r1 __asm__("r1") = &ch;
    __asm__ volatile("hlt #0xf000" :: "r"(r0), "r"(r1) : "memory");
    return c;
}
static int semi_console_init(void) { __printk_hook_install(semi_putc); return 0; }
SYS_INIT(semi_console_init, PRE_KERNEL_1, 0);

static void worker(void *a, void *b, void *c)
{
    ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
    for (int i = 0; i < 3; i++) {
        uint32_t cpsr;
        __asm__ volatile("mrs %0, cpsr" : "=r"(cpsr));
        printk("worker %d: uptime=%lld ms CPSR mode=0x%x\n", i, k_uptime_get(), cpsr & 0x1f);
        k_msleep(10);
    }
}
K_THREAD_DEFINE(w, 1024, worker, NULL, NULL, NULL, 5, 0, 0);

int main(void)
{
    uint32_t midr;
    __asm__ volatile("mrc p15, 0, %0, c0, c0, 0" : "=r"(midr));
    printk("Zephyr %s on %s, MIDR=0x%08x, sys clock %d Hz\n", KERNEL_VERSION_STRING,
           CONFIG_BOARD_TARGET, midr, sys_clock_hw_cycles_per_sec());
    k_msleep(50);
    printk("main done at %lld ms\n", k_uptime_get());
    return 0;
}
```

### 10.1 FreeRTOS (`portable/GCC/ARM_CRx_No_GIC/portASM.S`, `port.c`)

1. 벡터 0x18 → `FreeRTOS_IRQ_Handler`: `SUB LR, LR, #4` → `PUSH {LR}` · `MRS LR, SPSR` · `PUSH {LR}`(IRQ 스택) → `CPS #SVC_MODE` → `PUSH {R0-R3, R12}` → `ulPortInterruptNesting++` → 8바이트 정렬 → `BLX vApplicationIRQHandler`.
2. 우리 `vApplicationIRQHandler`(C): `ICC_IAR1` 읽기 → INTID 30이면 `FreeRTOS_Tick_Handler()` → `ICC_EOIR1`.
3. `FreeRTOS_Tick_Handler`(`port.c`): `xTaskIncrementTick()`이 참이면 `ulPortYieldRequired = pdTRUE` → `configCLEAR_TICK_INTERRUPT()`(우리 `vClearTickTimer`, CVAL 재설정).
4. 다시 어셈블리: `CPSID i` → `ulICCEOIR` 주소에 쓰기 → 중첩 카운트 복원 → 0이 아니면 `exit_without_switch`, `ulPortYieldRequired`면 `switch_before_exit`.
5. `switch_before_exit`: IRQ 스택의 LR · SPSR을 되돌려 놓고 `portSAVE_CONTEXT`(SRSDB → SYS 스택, r0–r12 · r14 · 중첩 카운트 · FPU) → `vTaskSwitchContext()`(`tasks.c`, `pxCurrentTCB` 교체) → `portRESTORE_CONTEXT`(… `RFEIA SP!`).

포트 어셈블리 크기(`nm -n`으로 다음 심볼과의 거리): `FreeRTOS_SVC_Handler` 304바이트, `FreeRTOS_IRQ_Handler`(출구 경로 포함) 324바이트. 대조로 M3 포트는 `PendSV_Handler` 68바이트 · `SVC_Handler` 36바이트 · `SysTick_Handler` 44바이트였다(`nm -S`). 같은 일을 하는 코드가 Cortex-R에서 약 4배 길다 — 하드웨어 스태킹이 없는 값이다.

### 10.2 Zephyr (`arch/arm/core/cortex_a_r/`)

1. `vector_table.S`: `ldr pc, =_isr_wrapper`(IRQ, 오프셋 0x18). FIQ는 `CONFIG_USE_SWITCH`가 아니면 `z_arm_nmi`.
2. `isr_wrapper.S` `_isr_wrapper`: `sub lr, lr, #4` → `srsdb #MODE_SYS!` → `cps #MODE_SYS` → `push {r0-r3, r12, lr}` → (`CONFIG_FPU_SHARING`이면 FPEXC 저장 후 VFP 끄기) → `cps #MODE_SVC`(주석: "Use SVC mode stack for predictable interrupt behaviour") → `bl arm_gic_get_active` → `cpsie i`(중첩 허용) → `_sw_isr_table`에서 ISR 찾아 `blx r3` → `bl arm_gic_eoi` → `bx z_arm_int_exit`.
3. `exc_exit.S` `z_arm_int_exit` → 스위치가 필요하면 `swap_helper.S`의 `z_arm_do_swap`(스레드 레지스터를 `struct k_thread`의 callee-saved 영역에 저장 · 복원). 협조적 스위치는 `z_arm_svc` 경로.
4. 리셋: `reset.S`(EL2 → EL1, `CONFIG_DCLS` 레지스터 초기화, `CONFIG_DISABLE_TCM_ECC`), `prep_c.c`, `tcm.c`.

두 커널 모두 Cortex-R에서 하는 일은 같다: **소프트웨어가 레지스터를 저장 → GIC에서 INTID 읽기 → 처리 → EOI → 필요하면 스위치.** Cortex-M 포트의 PendSV · 하드웨어 스태킹 · BASEPRI 자리를 Cortex-R에서는 IRQ 출구 경로 · SRS/RFE · CPSID(또는 GIC PMR)가 맡는다. 깊은 한 줄씩 읽기는 C2(컨텍스트 스위치), 크리티컬 섹션 비교는 C7, 인터럽트 우선순위 설계는 E2로 넘긴다.

## 13. 면접에서 이렇게 말한다

**Q.** "How is porting an RTOS to a Cortex-R different from porting it to a Cortex-M?"

**A.** 가장 큰 차이는 예외 진입이다. Cortex-M은 하드웨어가 8워드를 쌓아 주니 ISR이 C 함수이고, 포트는 PendSV에서 r4–r11만 저장한다. Cortex-R은 하드웨어가 LR과 SPSR만 바꾸므로 포트 어셈블리가 IRQ 진입에서 레지스터 저장 · 모드 전환 · 스택 정렬 · GIC acknowledge/EOI · 복귀까지 다 한다. 같은 FreeRTOS ping-pong에서 스위치당 명령이 M3 273개, R52 320~327개였고 포트 어셈블리는 약 4배 길었다.

> On Cortex-M the hardware stacks eight registers and an ISR is just a C function; the port only saves r4–r11 in PendSV. On Cortex-R the hardware only banks LR and SPSR and switches mode, so the port's assembly has to do everything: save the caller-saved registers, move from IRQ to SVC or SYS mode for nesting, align the stack, acknowledge the interrupt in the GIC, signal EOI, and return with RFE or MOVS PC. In my QEMU measurement with the same FreeRTOS config, a context switch was about 273 instructions on an M3 and about 320 on an R52, and the R port's assembly was roughly four times larger.

**꼬리 질문**: "Why do Cortex-R kernels switch from IRQ mode to SVC or SYS mode?" → 중첩 IRQ가 LR_irq를 덮어쓰기 때문, 그리고 SYS 스택에 바로 저장하면 스위치가 SP 교체로 끝나기 때문.

**Q.** "What does the Cortex-R52 add over the R5, and why does it matter for software?"

**A.** Armv8-R로 바뀌면서 EL2 하이퍼바이저와 2단계 MPU, GICv3 시스템 레지스터 인터페이스, 내장 generic timer가 생겼다. 소프트웨어 입장에서는 리셋이 EL2에서 시작하니 startup이 ERET로 EL1에 내려가야 하고, MPU가 base/limit 형식이라 겹침이 fault이며, 한 코어에 서로 다른 ASIL의 OS를 격리해 올릴 수 있다.

> The R52 is Armv8-R. It adds EL2 with a hypervisor mode and a second-stage MPU, a GICv3 CPU interface accessed through system registers, and an integrated generic timer. For software that means the core resets into EL2, so the startup code must configure HVBAR, timer access and FPU traps and then ERET into EL1. The MPU uses base and limit registers with 64-byte granularity, and overlapping regions fault instead of using priority. And the EL2 MPU lets a small hypervisor isolate two RTOS partitions with different ASIL levels on one core.

**Q.** "What must startup code do on a lockstep (DCLS) core?"

**A.** 리셋은 레지스터를 0으로 만들지 않는다. 두 코어의 초기화 안 된 값이 처음 버스로 나가는 순간 비교기가 불일치를 보므로, 모든 모드의 r0–r14 · SPSR · VFP 레지스터를 정의된 값으로 채운다. 그리고 TCM · 캐시 ECC를 64비트 쓰기로 초기화하고, 지난 리셋 원인이 lockstep 오류였는지 기록한다.

> Reset does not clear the register file, and in lockstep the redundant core compares every output. If an uninitialised register is pushed to the stack, the two cores may disagree and raise a compare error. So startup walks through every mode and zeroes r0 to r14, the SPSRs and the FPU registers; Zephyr's reset.S does exactly that under CONFIG_DCLS. Then it initialises the ECC-protected TCMs with full 64-bit writes before anything reads them, and it records whether the last reset came from a lockstep or ECC error.

**Q.** "Why do you have to initialise ECC-protected TCM at boot, and how?"

**A.** 전원 직후 데이터와 ECC가 둘 다 쓰레기라서, 읽거나 부분 쓰기(read-modify-write)를 하면 정정 불가 오류가 난다. 그래서 ECC 검사를 켜기 전에 granule 전체를 덮는 64비트 이상 정렬 쓰기로 TCM 전체를 채운다. QEMU에서 32 KB를 STM으로 지우면 3,084 명령, 바이트 루프면 98,310 명령이었다.

> At power-up both the data and the ECC bits are random. A read, or a byte write that forces a read-modify-write of the 64-bit granule, will hit an uncorrectable error. So the boot code fills the whole TCM with aligned 64-bit or wider stores, for example STM with eight registers, before enabling ECC checking or touching the memory otherwise. On QEMU, clearing 32 KB took about three thousand instructions with STM versus almost one hundred thousand with a byte loop, which matters for boot-time budgets.

**Q.** "In GICv3 on a Cortex-R52, walk me through handling one timer interrupt."

**A.** 타이머가 PPI 30을 올리고, 코어는 벡터 0x18로 간다. 진입 코드가 LR을 고치고 레지스터를 저장한 뒤, C에서 ICC_IAR1을 읽어 INTID를 얻고, 다음 마감을 CVAL에 다시 쓰고, ICC_EOIR1에 IAR 값을 써서 끝낸다. 그 다음 RTOS면 스케줄링 필요 여부를 보고 복귀한다. 초기화로는 GICD_CTLR의 ARE와 그룹 활성화, GICR_WAKER 깨우기, IGROUPR · IPRIORITYR · ISENABLER, ICC_PMR · ICC_IGRPEN1이 필요하다.

> The EL1 physical timer asserts PPI 30 in the redistributor. The core takes the IRQ vector at offset 0x18; the entry code fixes LR, saves registers, and calls C. The handler reads ICC_IAR1 to get the INTID, does the work, for a periodic tick it adds the period to CNTP_CVAL so there is no drift, and writes the IAR value back to ICC_EOIR1. Setup beforehand is GICD_CTLR with affinity routing and group enables, clearing ProcessorSleep in GICR_WAKER, then group, priority and enable for INTID 30 in the SGI frame, and finally ICC_PMR and ICC_IGRPEN1.

**Q.** "Your SSD firmware ran a bare-metal executive on Cortex-R. Why would you or wouldn't you put an RTOS there?"

**A.** 실행부는 사실상 우선순위 하나짜리 스케줄러이고, 모든 핸들러가 짧으면 가장 빠르고 결정적이다. 핸들러 중 하나가 길어져 지연 요구를 깨기 시작하거나, 우선순위가 다른 일(관리 명령 · 로그 · 열 관리)이 섞이면 선점형 RTOS가 이긴다. 대신 Cortex-R에서는 IRQ 진입 비용이 늘어나니, 가장 빡빡한 경로는 FIQ나 커널 밖 ISR로 남기는 하이브리드를 고르겠다.

> The executive is essentially a one-priority, run-to-completion scheduler driven by hardware queues. When every handler is short, it is the fastest and most deterministic design, which is why many SSD controllers use it. I would move to a preemptive RTOS when some work becomes long enough to break the latency of other work, or when different priorities get mixed, like admin commands, logging and thermal management. On Cortex-R the RTOS adds software entry and exit cost to every interrupt, so I would keep the tightest path, for example a NAND completion that feeds DMA, as an FIQ or zero-latency handler outside the kernel, and put the rest in tasks.

**Q.** "What is the EL2 MPU used for, concretely?"

**A.** HCR.VM을 켜면 EL1/EL0의 모든 접근이 EL2 MPU를 한 번 더 통과한다. 하이퍼바이저가 파티션마다 메모리 창을 주고, 창 밖 접근은 게스트 OS가 아니라 EL2의 Hyp Trap으로 온다. QEMU에서 게스트가 창 밖에 쓰자 HSR.EC 0x24로 EL2가 받았다.

> With HCR.VM set, every EL1 and EL0 access is checked against the EL2 MPU after the guest's own MPU. A small hypervisor gives each partition a memory window. Any access outside it traps to EL2 through the Hyp Trap vector, not to the guest. In my QEMU test, a guest write outside its window arrived at EL2 with HSR.EC equal to 0x24 and the faulting address in HDFAR, and HVC calls arrived with EC 0x12. This is the hardware basis for freedom from interference between mixed-criticality partitions.

## 14. 직접 해보기

**1. 개념**: Cortex-M3와 Cortex-R52에서 IRQ가 들어올 때 하드웨어가 하는 일을 각각 세 줄로 써라. 그리고 FreeRTOS 포트가 그 차이를 메우기 위해 추가로 하는 일을 한 줄로 써라.

정답/힌트: M = 8워드 push · EXC_RETURN을 LR에 · 벡터 주소로 점프. R = CPSR → SPSR_irq · 복귀 주소 → LR_irq · IRQ 모드로 바꾸고 0x18 실행. 포트는 r0–r3 · r12 · LR · SPSR 저장과 모드 전환 · 정렬 · EOI · RFE 복귀를 한다.

**2. 코드**: 예제 4의 S1을 고쳐 **중첩**을 실제로 일으켜라. 우선순위가 높은 두 번째 PPI(예: 가상 타이머 CNTV, INTID 27)를 걸고, `irq_c` 안에서 `cpsie i` 후 잠깐 바쁜 루프를 돌게 한다. 두 번째 IRQ가 첫 IRQ 안에서 처리되는지 로그로 보여라. S0로 같은 일을 하면 어떻게 깨지는가?

정답/힌트: CNTV는 `MCR p15, 0, Rt, c14, c3, 0/1`(TVAL/CTL), CNTHCTL에서 EL1 접근이 필요할 수 있다. GIC 우선순위는 숫자가 작을수록 높다. S0에서 중첩하면 LR_irq가 덮어써져 첫 IRQ 복귀가 망가진다.

**3. 코드**: 예제 7에 두 번째 게스트 창을 만들고, EL2 Hyp 타이머(CNTHP, INTID 26)로 1 ms마다 "게스트 A ↔ 게스트 B"의 ELR/SPSR/SP를 바꿔 치는 아주 작은 시간 분할 하이퍼바이저를 써라(게스트 출력은 HVC 콘솔).

정답/힌트: EL2에서 받는 IRQ는 HVBAR+0x18로 온다. 게스트 컨텍스트 = r0–r12, SP_usr/SP_svc 등 뱅크 레지스터, ELR_hyp, SPSR_hyp. HCR.IMO로 IRQ를 EL2로 라우팅하는 비트도 살펴본다.

**4. 측정**: 예제 4의 S3에서 `vpush {d0-d15}`를 `vpush {d0-d7}`로 줄이면 icount 숫자가 바뀌는가? 바뀌지 않는다면 왜이고, 실칩에서는 어떻게 다를지 사이클로 추정하라.

정답/힌트: 명령 수는 같으니 icount는 그대로다. 실칩은 대략 저장 바이트에 비례(64비트 버스면 d 레지스터 하나 ≈ 1 beat)하므로 절반 가까이 줄어든다 — 정확한 수치는 R52 TRM의 명령 타이밍 참조.

**5. 측정**: 예제 9의 STM 루프를 `strd` 루프와 16레지스터 STM(r0–r12 · lr까지 활용)로 바꿔 32 KB 초기화 명령 수를 비교하고, 1 MB TCM이면 icount 기준 몇 ms인지 계산하라.

정답/힌트: 명령 수 ≈ (바이트 / 한 번에 쓰는 바이트) × 루프 명령 수. 32 ns/명령으로 환산.

**6. 조사 + 코드**: FreeRTOS `ARM_CR5` 포트의 크리티컬 섹션(`ulPortSetInterruptMask`)은 GIC PMR을 쓰고, `ARM_CRx_No_GIC`는 `CPSID I`를 쓴다. 두 방식이 "커널 밖(zero-latency) 인터럽트"를 허용하는지 각각 답하고, R52 GICv3에서 PMR 방식을 쓰려면 `ICC_PMR`을 어떻게 다루면 되는지 써 보라.

정답/힌트: PMR 방식은 `configMAX_API_CALL_INTERRUPT_PRIORITY`보다 높은 인터럽트를 열어 둘 수 있다(Cortex-M BASEPRI와 같은 역할, B3 · C7). CPSID는 전부 막는다. GICv3에서는 `MCR p15, 0, Rt, c4, c6, 0`(ICC_PMR)에 쓰고 ISB.

**7. Zephyr**: 예제 11의 overlay에 AN536 CMSDK UART 노드(`arm,cmsdk-uart`, 0xE7C00000)를 넣어 semihosting 대신 UART 콘솔로 바꿔 보라. 무엇이 막히는가?

정답/힌트: `UART_CMSDK_APB`는 `select PINCTRL`이고 `clocks` phandle의 `clock-frequency`를 읽는다. FVP SoC에 pinctrl 드라이버가 없으면 빌드가 막힌다 — 보드를 제대로 하나 만드는 것이 정답(H 모듈의 out-of-tree 보드).

| IAR / EOIR | Interrupt Acknowledge / End Of Interrupt | INTID 받기 / 처리 끝 알리기 |
| PPI / SPI / SGI | 인터럽트 종류 | 코어 전용(16–31) / 공유(32+) / 소프트웨어 생성(0–15) |

| HSR / HDFAR | Hyp Syndrome / Hyp Data Fault Address | EL2 트랩의 원인(EC)과 주소 |

## 16. 요약 & 체크리스트

Cortex-R은 "Cortex-A의 예외 모델 + MCU의 결정성"이다. 모드와 뱅크 레지스터, 분기 명령 벡터 테이블, GIC, CP15는 A 쪽이고, MPU · TCM · ECC · lockstep은 결정성과 신뢰성을 위한 R만의 장치다. RTOS 엔지니어에게 가장 중요한 사실은 **하드웨어 스태킹이 없다**는 것이다. IRQ가 오면 하드웨어는 LR과 SPSR만 바꾸고, 저장 · 모드 전환 · 정렬 · GIC acknowledge/EOI · 복귀는 소프트웨어가 한다. QEMU icount에서 재 보면 IRQ → C 본문이 M3는 소프트웨어 명령 0개(하드웨어가 12 사이클로 처리), R52는 최소 방식 6개 · 재진입 방식 11개였고, 같은 FreeRTOS ping-pong의 스위치 비용은 M3 273 · R52 320~327 명령, 포트 어셈블리는 약 4배 길었다. R52(Armv8-R)는 EL2에서 리셋되어 startup이 ERET로 EL1에 내려가야 하고, EL2 MPU로 게스트를 가두는 2단계 보호가 있다(창 밖 쓰기 → HSR.EC 0x24로 EL2 트랩). PMSAv8은 겹침이 fault라서 R5 MPU 코드를 그대로 옮기면 깨진다. TCM ECC는 부팅 때 64비트 쓰기로 먼저 채워야 하고(32 KB: STM 3,084 vs 바이트 98,310 명령), lockstep 코어는 모든 모드 레지스터를 0으로 채운 뒤 시작한다. FreeRTOS에는 R52 GICv3에 딱 맞는 GCC 포트가 없어 `ARM_CRx_No_GIC` + GIC glue로 올렸고, Zephyr v4.4.2에는 AN536 보드가 없어 FVP BaseR 보드를 overlay로 옮겼다. QEMU는 ECC · lockstep · 사이클을 모델링하지 않고, HCR.VM + EL1 MMIO에서 QEMU 10.2.1이 세그폴트하는 버그도 만났다.

- [ ] Cortex-R5 · R52 · R52+ · R82의 아키텍처와 대표 사용처(SSD · 자동차 · 안전 섬 · 스토리지)를 말할 수 있다
- [ ] R52가 EL2(Hyp)에서 리셋되는 것을 보이고, startup의 EL2 할 일(HVBAR · CNTHCTL · HCPTR · ERET)을 순서대로 쓸 수 있다
- [ ] 모드별 뱅크 레지스터 표를 그리고, RTOS 태스크가 SYS 모드에서 도는 이유를 말할 수 있다
- [ ] IRQ 진입 시퀀스(`sub lr` · `srsdb` · `cps` · `push` · 정렬 · `rfeia`)의 각 줄이 왜 필요한지 설명할 수 있다
- [ ] Cortex-M 하드웨어 스태킹과 Cortex-R 소프트웨어 저장의 비용 차이를 측정 숫자로 말할 수 있다
- [ ] GICv3 초기화(GICD_CTLR · GICR_WAKER · PPI 설정 · ICC_PMR · IGRPEN1)와 IAR → EOIR 흐름을 쓸 수 있다
- [ ] PMSAv7과 PMSAv8-32의 차이(특히 겹침)와 EL2 MPU 2단계 보호를 설명하고 fault 레지스터(DFSR/DFAR, HSR/HDFAR)를 읽을 수 있다
- [ ] TCM ECC 초기화가 왜 필요하고 어떤 쓰기로 해야 하는지 말할 수 있다
- [ ] lockstep(DCLS) 코어의 startup이 레지스터를 전부 채우는 이유를 설명할 수 있다
- [ ] FreeRTOS의 Cortex-R 포트 네 가지(`ARM_CR5` · `ARM_CRx_No_GIC` · `ARM_CRx_MPU` · `ARM_CR82`)를 구분하고 R52에 무엇을 쓸지 고를 수 있다
- [ ] Zephyr `cortex_a_r`의 IRQ 경로(`_isr_wrapper` → `arm_gic_get_active` → `_sw_isr_table` → `arm_gic_eoi` → `z_arm_int_exit`)를 따라갈 수 있다
- [ ] SSD 실행부 경험을 RTOS 용어로 번역해 면접에서 말할 수 있다
