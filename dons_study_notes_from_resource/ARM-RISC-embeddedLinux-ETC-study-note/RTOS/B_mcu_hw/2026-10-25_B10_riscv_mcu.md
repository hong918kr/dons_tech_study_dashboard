# B10. RISC-V MCU 관점 — 하드웨어가 덜 해 주는 CPU 위에 RTOS를 올리면 무엇이 달라지나

> **이 노트를 다 읽으면**: M/U 모드와 trap CSR(mstatus · mtvec · mcause · mepc · mtval · mie/mip · mscratch)만으로 bare-metal 트랩 핸들러를 직접 쓰고 mret으로 돌아올 수 있다 · CLINT mtimecmp로 1 kHz tick을, PLIC claim/complete로 외부 인터럽트를 돌리고 CLIC · AIA가 무엇을 바꾸는지 NVIC와 비교해 말할 수 있다 · PMP로 U-mode 태스크를 가두고 fault의 mcause/mtval을 읽을 수 있다 · FreeRTOS GCC/RISC-V 포트와 Zephyr RISC-V 아키 코드가 "하드웨어 스태킹 없음"을 어떻게 메우는지, 그 비용을 Cortex-M3와 명령 수로 비교해 말할 수 있다
> **왜 필요한가**: ESP32-C/P 계열, RP2350 Hazard3, GD32V, CH32V, nRF54의 RISC-V 보조 코어처럼 RISC-V MCU가 드론·로봇·차량 보드에 빠르게 들어오고 있다. 면접에서 "What changes when you port an RTOS from Cortex-M to RISC-V?"는 단골 질문이고, 실무에서는 트랩 진입 어셈블리 · tick 타이머 · 인터럽트 컨트롤러 드라이버를 다시 써야 한다.
> **Don 기준 난이도**: 레지스터 저장/복원, 인터럽트 ACK, MPU 영역 설계, 원자 연산의 필요성은 SSD 펌웨어에서 이미 안다 / CSR 명령으로 다루는 특권 레지스터, "하드웨어가 아무것도 안 밀어 준다"는 사실, 표준이 여러 개로 갈라진 인터럽트 컨트롤러(CLINT · PLIC · CLIC · AIA), PMP의 NAPOT 인코딩, LR/SC 예약 개념을 새로 배운다
> **선행 노트**: B1(Cortex-M 프로그래머 모델), B2(예외 진입 · 복귀 — 하드웨어 8워드 스태킹), B3(NVIC 우선순위), B4(SysTick · PendSV · SVC). RISC-V ISA 개요(base · 확장 이름 · 명령 인코딩 · RVV)는 [Hark E3 노트](../../../../../dons_study_note_from_experience/embeddedAIPrepBasedOnHarkAIJD/site/E/2026-09-30_E3_risc_v.html)에 있으니 여기서 반복하지 않는다. 이어지는 노트: C2(컨텍스트 스위치), C3(첫 태스크 시작), E1(ISR 설계), F5(유저 모드 격리), P2(멀티코어)
> 🔁 **Bare-Metal 겹침**: BM E1(ISA와 확장) · E2(특권 아키텍처) · E3(인터럽트 컨트롤러) · E4(PMP/ePMP) — 이 노트가 주인. Bare-Metal 노트는 이 노트를 링크하고 "칩 데이터시트 기준 레지스터 설정 순서와 startup 어셈블리(BM E5)"만 더한다

## 0. 큰 그림 — 이게 왜 필요한가

Don이 지금까지 RTOS를 공부한 무대는 Cortex-M이었다. Cortex-M은 친절한 CPU다. 인터럽트가 들어오면 **하드웨어가** r0–r3, r12, lr, pc, xPSR 8워드를 스택에 밀어 넣고, 벡터 테이블에서 핸들러 주소를 꺼내고, 끝나면 `bx lr` 한 번(EXC_RETURN)으로 전부 되돌린다(B2). 그래서 ISR을 평범한 C 함수로 쓸 수 있고, RTOS 포트의 어셈블리는 PendSV 안의 "r4–r11 8개 더 저장" 정도로 짧다.

표준 RISC-V는 반대쪽 끝에 있다. 트랩이 나면 하드웨어는 **PC(mepc)와 원인(mcause), 그리고 상태 비트 몇 개(mstatus)만** 바꾸고 mtvec 주소로 점프한다. 범용 레지스터는 하나도 저장하지 않는다. 스택 포인터도 바꾸지 않는다. 그 다음은 전부 소프트웨어 몫이다 — 진입 어셈블리가 레지스터를 저장하고, C를 부르고, 복원하고, `mret`을 실행한다. SSD 펌웨어에 비유하면 "DMA 엔진이 descriptor를 자동으로 써 주던 컨트롤러"에서 "레지스터 하나하나를 CPU가 직접 써야 하는 컨트롤러"로 옮겨 온 것과 같다. 일은 같지만 누가 하느냐가 다르다.

그림 1 — 같은 "인터럽트 한 번"을 두 아키텍처가 나누는 방식. RISC-V는 하드웨어 단계가 짧은 대신 빨간 두 칸(저장 · 복원)을 소프트웨어가 떠맡는다. 숫자는 4절에서 직접 잰다.

이 차이 하나가 RTOS 포팅의 거의 모든 것을 바꾼다.

| 주제 | Cortex-M에서 (B1–B4) | RISC-V에서 (이 노트) | 이 노트의 절 |
|---|---|---|---|
| 특권 | Thread/Handler × privileged/unprivileged | M / S / U 모드 (MCU는 M 또는 M+U) | 2 |
| 설정 레지스터 | MRS/MSR, 메모리 맵 SCB | CSR 명령(`csrr` · `csrw` · `csrs` · `csrc`) | 2 |
| 예외 진입 | 8워드 하드웨어 스태킹 | 저장 없음 — 소프트웨어가 전부 | 2, 4 |
| 벡터 | 주소 표(VTOR) | mtvec: direct(한 곳) 또는 vectored(점프 명령 배열) | 2, 3 |
| tick 타이머 | SysTick(코어 내장, 자동 reload) | CLINT mtime/mtimecmp(메모리 맵, 매번 다시 씀) | 3 |
| 인터럽트 컨트롤러 | NVIC 하나 | PLIC · CLIC · AIA · 벤더 고유 — 칩마다 다름 | 3 |
| 시스템 콜 | `svc #n` | `ecall` (mcause 8/11) | 2, 7 |
| 미뤄 둔 스위치 | PendSV(최저 우선순위) | 표준에 없음 — ecall 또는 타이머 ISR 안에서 직접 | 7, 8 |
| 메모리 보호 | MPU | PMP / Smepmp | 5 |
| 원자 연산 | LDREX/STREX | LR/SC + AMO (A 확장) | 6 |
| 크리티컬 섹션 | BASEPRI로 일부만 막기 | mstatus.MIE로 전부 막기(표준 CLINT/PLIC 기준) | 7 |

### 실습 환경 한 줄

QEMU 10.2 `qemu-system-riscv32 -machine virt -bios none`(RAM 0x80000000, NS16550 UART 0x10000000, CLINT 0x02000000, PLIC 0x0C000000, mtime 10 MHz) 위의 **직접 쓴 bare-metal**(Zephyr SDK 1.0.1의 `riscv64-zephyr-elf-gcc` 14.3, `-march=rv32imac_zicsr_zifencei -mabi=ilp32`) · 같은 머신 위의 **FreeRTOS V11.3.2 GCC/RISC-V 포트** · **Zephyr v4.4.2 `qemu_riscv32`** · 비교용 **QEMU `mps2-an385`(Cortex-M3)** bare-metal과 FreeRTOS ARM_CM3 포트. 수치는 전부 `-icount shift=5`(명령 1개 = 32 ns 가상 시간; Zephyr의 RISC-V 실행은 보드 기본값 `shift=6`)로 잰 **QEMU icount 기준이며, 실제 칩과 절대값은 다르다**(캐시 · 플래시 wait state · 버스 · 파이프라인 · Cortex-M의 12사이클 스태킹을 QEMU가 모델링하지 않는다). 그래서 이 노트의 비교 단위는 "사이클"이 아니라 **실행한 명령 수**다. icount 아래에서 RISC-V `minstret` CSR은 정확한 명령 수를 준다(예제 1에서 확인).

## 1. ISA와 확장 — RTOS가 신경 쓰는 것만

> 🔁 이 절은 Bare-Metal BM E1(ISA와 확장)과 겹친다 (주인: 이 노트). base ISA · 명령 형식 · RVV 상세는 Hark E3에 있다.

### 1.1 직관 — "이름 문자열 = 이 칩이 해 주는 일의 목록"

RISC-V 칩의 데이터시트 첫 줄에는 `RV32IMAC`이나 `rv32imac_zicsr_zifencei_zba_zbb_zbs` 같은 문자열이 있다. Hark E3에서 읽는 법을 봤다. RTOS 포팅 엔지니어의 질문은 하나다: **"이 글자들 중 무엇이 커널 코드를 바꾸나?"**

### 1.2 정의 — RTOS 관점의 확장 표

| 확장 | 뜻 | RTOS·포트에 미치는 영향 |
|---|---|---|
| I / E | 기본 정수 명령, 레지스터 32개 / 16개 | E(RV32E)면 저장할 레지스터가 15개 → FreeRTOS `portCONTEXT_SIZE`가 15워드, 스택 정렬 8바이트(`__riscv_32e` 분기). CH32V003이 RV32EC |
| M | 곱셈 · 나눗셈 | 없으면 tick 계산의 `/`가 libgcc 호출로 바뀐다 |
| A | 원자 명령 LR/SC · AMO (Zalrsc + Zaamo로 쪼개짐) | 단일 코어는 인터럽트 끄기로 대체 가능. 멀티코어 · Zephyr `atomic_*` · 스핀락에 필수 (6절). ESP32-C3는 A가 없다 |
| C | 16비트 압축 명령 (Zca 등으로 쪼개짐) | 코드 크기 25~30% 감소. **트랩 핸들러가 명령을 건너뛸 때 길이가 2 또는 4** — 예제 2 |
| F / D | 단정밀 / 배정밀 FPU | 컨텍스트에 f0–f31 + fcsr 추가. mstatus.FS(Off/Initial/Clean/Dirty)로 lazy 저장 (B6의 RISC-V판) |
| Zicsr | CSR 명령 | 없으면 트랩 처리 자체가 불가능 — 사실상 필수 |
| Zifencei | `fence.i` (명령 캐시 동기화) | 코드를 RAM에 쓰고 실행할 때(부트로더, 동적 로딩) |
| Zicntr / Zihpm | `cycle` · `time` · `instret` 읽기 / 성능 카운터 | 런타임 통계, 측정. `time`은 mtime의 그림자(예제 1) |
| Zba / Zbb / Zbs | 주소 계산 · 기본 비트 조작(clz, ctz, cpop, rev8 …) · 단일 비트 | Zbb가 없으면 FreeRTOS의 `__builtin_clz`(최고 우선순위 찾기)가 libgcc `__clzsi2` 호출이 된다 — 8절에서 측정 |
| Zcb / Zcmp / Zcmt | 압축 명령 추가 / **push·pop 묶음 명령**(`cm.push`, `cm.popret`) / 점프 테이블 | Zcmp는 함수 prologue · epilogue를 한 명령으로. ISR 저장 비용을 줄이는 표준 방법 중 하나 |
| V | 벡터 | 컨텍스트에 v0–v31 + vstart · vcsr …, mstatus.VS로 lazy 저장 (FreeRTOS `configENABLE_VPU`) |
| P | 패킹 SIMD(DSP) | 이 노트 작성 시점에 비준 확인 못 함(초안). 벤더 DSP 확장이 먼저 쓰인다 |
| Smepmp | 강화 PMP | M-mode까지 묶는 보안 정책 (5절) |

"extension 이름이 길어지는 이유"는 표준이 큰 확장을 작은 조각으로 쪼개고 있기 때문이다. 예를 들어 A는 Zalrsc(LR/SC)와 Zaamo(AMO)로, C는 Zca · Zcf · Zcd로 나뉘었다. Zephyr의 `.config`에도 그대로 나온다(예제 10 빌드의 `CONFIG_RISCV_ISA_EXT_ZAAMO=y`, `CONFIG_RISCV_ISA_EXT_ZALRSC=y`, `CONFIG_RISCV_ISA_EXT_ZCA=y`).

### 1.3 개발 환경 — 맨 처음 만나는 세 파일

> 🔁 이 절의 startup은 Bare-Metal BM E5(RISC-V startup)가 더 깊게 다룬다. 여기서는 예제를 돌리는 데 필요한 최소만 쓴다.

예제를 돌리기 위해 아무것도 없는 상태에서 세 파일을 만들었다. Cortex-M 템플릿의 `startup.c`(벡터 테이블 + Reset_Handler)에 해당한다. 중요한 차이 두 가지가 있다. **(1) 벡터 테이블이 없다** — 리셋 후 CPU는 정해진 주소(QEMU virt는 0x1000의 mrom 몇 줄이 0x80000000으로 점프)에서 명령을 실행할 뿐이고, 초기 SP를 하드웨어가 읽어 주지 않는다. 그래서 `_start`가 첫 명령으로 `sp`를 직접 설정한다. **(2) `gp`(global pointer)** — 링커가 `gp ± 2 KB` 안의 전역 변수 접근을 `lui+addi` 두 명령 대신 `gp` 기준 한 명령으로 줄이는 "linker relaxation"을 하므로, `gp`를 `__global_pointer$`로 맞춰야 한다. 이때 `la gp, …` 자체가 relax되어 "gp 기준으로 gp를 계산"하는 모순이 생기지 않도록 `.option norelax`로 감싼다.

```asm
/* start.S — RV32 bare-metal 시작 코드 (QEMU virt, -bios none). hart마다 8 KB 스택 */
    .section .text.init, "ax"
    .globl _start
_start:
    .option push
    .option norelax            /* gp 자신을 gp-상대로 relax하지 않게 */
    la    gp, __global_pointer$
    .option pop
    csrr  t0, mhartid
    slli  t1, t0, 13           /* sp = __stack_top - hartid × 8 KB */
    la    sp, __stack_top
    sub   sp, sp, t1
    bnez  t0, secondary
    la    t0, __bss_start      /* hart 0: .bss 0 채우기 */
    la    t1, __bss_end
1:  bgeu  t0, t1, 2f
    sw    zero, 0(t0)
    addi  t0, t0, 4
    j     1b
2:  li    t0, 1
    la    t1, bss_ready
    sw    t0, 0(t1)            /* 다른 hart에게 "이제 C 돌려도 된다" */
    call  main
    call  board_exit           /* a0 = main의 리턴값 */
secondary:
    la    t1, bss_ready
3:  lw    t0, 0(t1)
    beqz  t0, 3b
    csrr  a0, mhartid
    call  secondary_main       /* 약한 기본 구현 = park */
park:
    wfi
    j     park
    .weak secondary_main
secondary_main:
    j     park
    .data
    .align 2
bss_ready: .word 0
```

### 예제 1 — 깨어난 hart가 자기소개: misa, ID CSR, mstatus, 카운터

무엇을 확인하는 코드인가: 리셋 직후 CSR의 값, `misa`로 읽은 확장 목록, 그리고 icount 아래에서 `minstret`이 정확한 명령 수를 주는지.

```c
/* ex1 — 맨 처음 깨어난 RV32 hart가 자기 자신을 소개한다: misa, ID CSR, mstatus, sp/gp */
#include "board.h"
int main(void) {
    uint32_t misa = csr_read(misa);
    kprintf("hello from RV32 M-mode (QEMU virt, -bios none)\n");
    kprintf("misa      = 0x%08x  MXL=%u (1=32bit)  ext=", misa, misa >> 30);
    for (int i = 0; i < 26; i++)
        if (misa & (1u << i)) kputc('A' + i);
    kprintf("\nmvendorid = 0x%x  marchid = 0x%x  mimpid = 0x%x  mhartid = %u\n",
            csr_read(mvendorid), csr_read(marchid), csr_read(mimpid), csr_read(mhartid));
    uint32_t ms = csr_read(mstatus);
    kprintf("mstatus   = 0x%08x  MIE=%u MPIE=%u MPP=%u\n", ms, (ms >> 3) & 1, (ms >> 7) & 1, (ms >> 11) & 3);
    kprintf("mtvec     = 0x%08x  (리셋 후 아직 설정 안 함)\n", csr_read(mtvec));
    uint32_t sp, gp;
    __asm volatile("mv %0, sp" : "=r"(sp));
    __asm volatile("mv %0, gp" : "=r"(gp));
    kprintf("sp        = 0x%08x  gp = 0x%08x\n", sp, gp);
    uint32_t c0 = csr_read(mcycle), i0 = csr_read(minstret);
    uint64_t t0 = mtime_read();
    for (volatile int k = 0; k < 1000; k++) { }
    uint32_t c1 = csr_read(mcycle), i1 = csr_read(minstret);
    uint64_t t1 = mtime_read();
    uint32_t tm; __asm volatile("rdtime %0" : "=r"(tm));            /* Zicntr: time CSR (mtime의 그림자) */
    kprintf("rdtime    = %u   mtime(MMIO) = %u\n", tm, (uint32_t)mtime_read());
    kprintf("1000-iter loop: mcycle +%u  minstret +%u  mtime +%u (10 MHz)\n",
            c1 - c0, i1 - i0, (uint32_t)(t1 - t0));
    return 0;
}
```

출력에서 볼 것:
- QEMU 기본 `rv32` CPU는 `ACDFHIMSU` — S(supervisor) · H(hypervisor)까지 있는 "다 있는" 코어다. 실제 MCU 코어 모델인 SiFive E31은 `ACIMU`(M+U만, S 없음), lowRISC Ibex는 `CIMU`(A도 없음)다. **RTOS 포트는 misa가 아니라 컴파일 옵션(`-march`)을 믿는다** — misa는 WARL이고 0을 돌려줘도 되는 레지스터라서, 확인용으로만 쓴다.
- `mtvec = 0` — 리셋 후 트랩 벡터가 정해지지 않았다. 이 상태에서 트랩이 나면 주소 0으로 점프한다. **mtvec 설정은 startup의 첫 일 중 하나**다(Cortex-M에서는 벡터 테이블이 리셋 시점에 이미 있다).
- 1000번 도는 루프가 `minstret +5017` — 반복당 5명령 + 측정 오버헤드. `mcycle +160544`는 5017 × 32 = 160544, 즉 QEMU icount에서 mcycle은 "가상 ns"로 나온다. `mtime +1605`(10 MHz = 100 ns 단위)는 160.5 µs로 같은 시간이다. 그래서 이 노트에서는 **명령 수는 minstret, 시간은 mtime**으로 잰다. icount 없이 돌리면 minstret이 54167처럼 엉뚱한 값이 나온다(호스트 시간 기반) — 측정은 반드시 `ICOUNT=1`.
- `rdtime`(Zicntr의 `time` CSR)과 MMIO `mtime`이 2 차이로 같은 시계다. 실칩에서는 `time` CSR 읽기가 M-mode 소프트웨어 에뮬레이션(트랩)인 경우도 있으니 데이터시트를 본다.

### 1.4 프로파일 — "이 조합이면 이 소프트웨어가 돈다"

확장 조합이 너무 많아서 RISC-V International은 **프로파일**로 묶는다. RVA23(애플리케이션 프로세서용, 2024년 10월 비준 — Linux 배포판이 기대하는 조합, V와 H 포함)이 대표다. RVI20U32/U64는 "I만 있는 최소 집합"이다. **MCU용 표준 프로파일은 이 노트 작성 시점(2026-10)에 비준된 것을 확인하지 못했다.** 그래서 MCU 세계에서는 여전히 "칩마다 `-march` 문자열을 데이터시트에서 읽어 맞춘다"가 현실이다. Zephyr는 이것을 DTS의 `riscv,isa-extensions` 속성으로 표현하고 Kconfig `CONFIG_RISCV_ISA_EXT_*`로 바꾼다(9절 칩 표의 근거).

### 1.5 Don 경험과 연결

SSD 컨트롤러에서 "이 SoC의 Cortex-R은 FPU가 있나, ECC TCM이 있나"를 확인하고 빌드 옵션을 바꾸던 일과 같다. 다른 점은 RISC-V는 그 선택지가 수십 개라는 것, 그리고 **같은 이름의 확장이라도 버전 · 비준 상태가 다를 수 있다**는 것이다(1.2 표의 P, 3절의 CLIC).

### 1.6 함정

- `-march`에 칩에 없는 확장(예: ESP32-C3에 `a`)을 넣으면 그 명령이 나오는 순간 illegal instruction(mcause 2)이다. 반대로 빼먹으면 손해만 본다(Zbb 없이 clz → 함수 호출).
- `-march`와 `-mabi`는 짝이다. `rv32imafc` + `ilp32`는 FPU 명령은 쓰되 float 인자를 정수 레지스터로 넘기고, `ilp32f`는 f 레지스터로 넘긴다. 라이브러리(multilib)와 앱이 다르면 링크 에러나 조용한 ABI 불일치가 난다.
- GCC 12 이후로 `zicsr` · `zifencei`가 `i`에서 분리되었다. 오래된 예제의 `-march=rv32imac`는 CSR 명령에서 어셈블러 에러가 난다 — `_zicsr_zifencei`를 붙인다.

## 2. 특권 아키텍처 — M/S/U 모드와 trap CSR

> 🔁 이 절은 Bare-Metal BM E2(특권 아키텍처)와 겹친다 (주인: 이 노트).

### 2.1 직관 — 모드는 셋, MCU가 쓰는 건 하나 또는 둘

| 모드 | 인코딩 | 누가 쓰나 | Cortex-M 감각 |
|---|---|---|---|
| M (Machine) | 3 | 부트, 트랩 처리, 대부분의 MCU 펌웨어 전체. **반드시 있다** | Handler mode + privileged Thread |
| S (Supervisor) | 1 | MMU를 쓰는 OS 커널(Linux) | Cortex-A EL1 — MCU에는 보통 없다 |
| U (User) | 0 | 격리된 앱 · RTOS 사용자 태스크 | unprivileged Thread |

MCU는 **M만**(가장 단순: FreeRTOS RISC-V 포트는 태스크도 M-mode에서 돌린다) 또는 **M+U**(PMP로 태스크를 가둔다: Zephyr userspace)를 쓴다. Cortex-M과 달리 "Handler mode"라는 별도 모드가 없다 — 트랩 핸들러도 그냥 M-mode 코드이고, "지금 트랩 안인가"는 소프트웨어가 기억해야 한다(FreeRTOS는 ISR 스택으로 갈아탄 것, Zephyr는 `_current_cpu->nested` 카운터로 안다).

### 2.2 정의 — RTOS가 만지는 M-mode CSR

CSR은 12비트 번호로 접근하는 특수 레지스터다. `csrr rd, csr`(읽기), `csrw csr, rs`(쓰기), `csrs`/`csrc`(비트 세트/클리어 — 원자적 read-modify-write), `csrrw rd, csr, rs`(맞바꾸기)가 Zicsr 명령이다. Hark E3의 표를 RTOS 포팅에 필요한 깊이로 다시 정리한다.

| CSR | 비트 · 필드 | 하드웨어가 트랩 때 하는 일 | RTOS가 쓰는 곳 |
|---|---|---|---|
| `mstatus` | MIE(bit 3) 전역 인터럽트 허용 · MPIE(bit 7) 트랩 직전 MIE · MPP(bits 12:11) 트랩 직전 모드 · FS(14:13) · VS(10:9) | MPIE ← MIE, MIE ← 0, MPP ← 이전 모드 | 크리티컬 섹션(`csrc mstatus, 8`), 태스크 초기 프레임의 mstatus 값(0x1880) |
| `mtvec` | BASE(31:2) · MODE(1:0) 0=direct 1=vectored | PC ← BASE (vectored + 인터럽트면 BASE + 4 × 원인 번호) | 커널 시작 때 트랩 진입점 등록 |
| `mepc` | 트랩 난 명령(예외) 또는 다음에 실행할 명령(인터럽트)의 주소 | ← PC | 태스크 프레임 0번 칸. ecall이면 +4 해서 저장 |
| `mcause` | bit 31 = 인터럽트 여부 · 나머지 = 원인 코드 | ← 원인 | 디스패치: 7 = M 타이머, 11 = M 외부, 동기 11 = M-mode ecall |
| `mtval` | 잘못된 주소, 또는 잘못된 명령의 비트 | ← 부가 정보 (0이어도 된다) | fault 덤프 (Cortex-M MMFAR/BFAR 역할) |
| `mie` / `mip` | MSIE/MSIP(3) · MTIE/MTIP(7) · MEIE/MEIP(11) — 인터럽트 "종류"별 허용 / 대기 | mip는 장치 상태를 반영 | tick 켜기: `csrs mie, 0x80`. FreeRTOS는 `0x880`(타이머+외부) |
| `mscratch` | 아무 의미 없는 32비트 | 아무것도 안 함 | 트랩 진입 첫 명령에서 sp와 맞바꿔 커널 스택 / per-CPU 포인터 꺼내기 (2.6) |
| `mcycle` · `minstret` | 64비트 카운터(RV32는 h 짝) | — | 런타임 통계, 이 노트의 측정 |
| `mhartid` | 코어 번호 | — | SMP 부팅, per-hart mtimecmp 주소 계산 |
| `pmpcfg0..` · `pmpaddr0..` | 보호 영역 | 접근 검사 | 5절 |

`mret`이 하는 일은 트랩 진입의 정확한 역순이다: PC ← mepc, MIE ← MPIE, MPIE ← 1, 모드 ← MPP, 그리고 **MPP ← 지원되는 가장 낮은 모드**(U가 있으면 U). 이 마지막 규칙 때문에 예제 8에서 M-mode 태스크 안에서 읽은 mstatus.MPP가 0으로 나온다 — "U-mode로 돌고 있다"는 뜻이 아니다.

### 2.3 mcause 코드 — 외워 둘 것만

| mcause | 종류 | 언제 | RTOS 반응 |
|---|---|---|---|
| 0x80000003 | M software interrupt | CLINT msip에 1 쓰기 | SMP IPI, 소프트웨어 yield |
| 0x80000007 | M timer interrupt | mtime ≥ mtimecmp | tick |
| 0x8000000B | M external interrupt | PLIC이 MEIP를 올림 | PLIC claim → 장치 ISR |
| 2 | illegal instruction | 없는 명령, U에서 CSR 접근 | fault 덤프 |
| 3 | breakpoint | `ebreak` | 디버거 / assert |
| 4 / 6 | load / store-AMO address misaligned | 정렬 안 된 접근(하드웨어가 지원 안 할 때) | fault |
| 5 / 7 | load / store-AMO access fault | PMP 위반, 없는 주소 | MPU fault 처리 (5절) |
| 8 | ecall from U-mode | U 태스크의 시스템 콜 | syscall 디스패치 |
| 11 | ecall from M-mode | M-mode `ecall` | FreeRTOS `portYIELD()` |

### 2.4 트랩 진입 어셈블리 — "하드웨어 스태킹"을 손으로

Cortex-M 하드웨어가 해 주던 일을 직접 쓴 것이 아래 `trap.S`다. 프레임은 144바이트(32 + 4워드, 16바이트 정렬)로, `r[2]`에는 트랩 직전의 sp를 둔다. 이 한 파일이 예제 2, 3(B), 5, 7의 공용 진입점이다.

```asm
/* trap.S — 표준 RISC-V는 하드웨어가 레지스터를 하나도 안 밀어 준다 → 전부 소프트웨어로 저장.
 * 프레임(144 B): r[0..31] (r[2]=트랩 직전 sp), 32:mepc 33:mcause 34:mtval 35:mstatus
 * mscratch 규칙: M에서 돌 때 0, U에서 돌 때 = 커널 스택 top                       */
    .equ FRAME, 144
    .section .text.trap, "ax"
    .globl trap_entry
    .align 4                       /* mtvec BASE는 4바이트 정렬 (vectored면 더 큰 정렬) */
trap_entry:
    csrrw sp, mscratch, sp         /* sp <-> mscratch */
    bnez  sp, 1f                   /* mscratch != 0 → U에서 왔다: sp = 커널 스택 */
    csrr  sp, mscratch             /* M에서 왔다: 원래 sp 복구 (mscratch에 있음) */
1:  addi  sp, sp, -FRAME
    sw x1, 4(sp);   sw x3, 12(sp);  sw x4, 16(sp);  sw x5, 20(sp)
    sw x6, 24(sp);  sw x7, 28(sp);  sw x8, 32(sp);  sw x9, 36(sp)
    sw x10, 40(sp); sw x11, 44(sp); sw x12, 48(sp); sw x13, 52(sp)
    sw x14, 56(sp); sw x15, 60(sp); sw x16, 64(sp); sw x17, 68(sp)
    sw x18, 72(sp); sw x19, 76(sp); sw x20, 80(sp); sw x21, 84(sp)
    sw x22, 88(sp); sw x23, 92(sp); sw x24, 96(sp); sw x25, 100(sp)
    sw x26, 104(sp); sw x27, 108(sp); sw x28, 112(sp); sw x29, 116(sp)
    sw x30, 120(sp); sw x31, 124(sp)
    csrrw t0, mscratch, zero       /* t0 = 트랩 직전 sp, 핸들러 동안 mscratch = 0 */
    sw t0, 8(sp)
    csrr t0, mepc;    sw t0, 128(sp)
    csrr t0, mcause;  sw t0, 132(sp)
    csrr t0, mtval;   sw t0, 136(sp)
    csrr t0, mstatus; sw t0, 140(sp)
    mv a0, sp
    call trap_handler              /* void trap_handler(struct frame *f) */
    lw t0, 128(sp); csrw mepc, t0  /* C가 mepc를 바꿨을 수 있다 (ecall이면 +4) */
    lw t0, 140(sp); csrw mstatus, t0
    srli t0, t0, 11; andi t0, t0, 3
    bnez t0, 2f                    /* MPP != U → mscratch는 0 유지 */
    addi t1, sp, FRAME; csrw mscratch, t1
2:  lw x1, 4(sp);   lw x3, 12(sp);  lw x4, 16(sp);  lw x5, 20(sp)
    lw x6, 24(sp);  lw x7, 28(sp);  lw x8, 32(sp);  lw x9, 36(sp)
    lw x10, 40(sp); lw x11, 44(sp); lw x12, 48(sp); lw x13, 52(sp)
    lw x14, 56(sp); lw x15, 60(sp); lw x16, 64(sp); lw x17, 68(sp)
    lw x18, 72(sp); lw x19, 76(sp); lw x20, 80(sp); lw x21, 84(sp)
    lw x22, 88(sp); lw x23, 92(sp); lw x24, 96(sp); lw x25, 100(sp)
    lw x26, 104(sp); lw x27, 108(sp); lw x28, 112(sp); lw x29, 116(sp)
    lw x30, 120(sp); lw x31, 124(sp)
    lw sp, 8(sp)                   /* 마지막에 sp 복구 */
    mret
```

```c
#pragma once
#include <stdint.h>
struct frame { uint32_t r[32]; uint32_t mepc, mcause, mtval, mstatus; };   /* 144 B */
void trap_entry(void);
```

읽을 점:
- 저장 30개 + 복원 30개 + CSR 8개 + 분기 몇 개 = **정적으로 87명령**(objdump로 셈, 예제 11). 여기에 C 디스패처가 붙는다. Cortex-M3라면 이 87명령 중 "8워드 저장 · 복원"은 하드웨어 몫이고, 나머지 레지스터는 컴파일러가 C ISR prologue에서 필요한 만큼만 저장한다.
- x0(zero)은 저장할 필요가 없고, sp(x2)는 특별 취급, gp(x3) · tp(x4)도 실은 바뀌지 않지만 단순하게 다 저장했다.
- `mepc`를 C에서 고칠 수 있도록 프레임에 넣고 복귀 전에 다시 `csrw mepc` 한다. 이것이 "시스템 콜 리턴값 쓰기"와 "ecall 다음 명령으로 넘어가기"의 통로다.

### 예제 2 — mtvec(direct) + ecall을 "SVC"처럼, 동기 예외 네 종류

무엇을 확인하는 코드인가: `ecall` 한 번 왕복의 명령 수(같은 함수에 `nop`을 넣은 것과 비교), 그리고 illegal instruction · load access fault · misaligned AMO · ebreak에서 하드웨어가 채워 주는 mcause/mepc/mtval.

```c
/* ex2 — mtvec(direct) + ecall을 "SVC"처럼: a7=번호, a0=인자. 동기 예외 3종의 mcause/mepc/mtval */
#include "board.h"
#include "frame.h"
static volatile uint32_t last_cause;
void trap_handler(struct frame *f) {
    last_cause = f->mcause;
    if (f->mcause == 11) {                       /* ecall from M-mode */
        if (f->r[17] == 1) f->r[10] = f->r[10] * 2;          /* sys 1: double(a0) */
        f->mepc += 4;                            /* ecall 다음 명령으로 (ecall은 항상 4바이트) */
        return;
    }
    kprintf("  trap: mcause=%u mepc=0x%08x mtval=0x%08x\n", f->mcause, f->mepc, f->mtval);
    uint16_t lo = *(uint16_t *)f->mepc;          /* 문제 명령 건너뛰기: 압축(16b)이면 +2 */
    f->mepc += ((lo & 3) == 3) ? 4 : 2;
}
#define CALL(name, insn) __attribute__((noinline)) uint32_t name(uint32_t no, uint32_t arg) { \
    register uint32_t a0 __asm("a0") = arg, a7 __asm("a7") = no; \
    __asm volatile(insn : "+r"(a0) : "r"(a7) : "memory"); return a0; }
CALL(syscall1, "ecall")
CALL(nopcall, "nop")
int main(void) {
    csr_write(mtvec, (uint32_t)trap_entry);      /* MODE=0 direct: 모든 트랩이 BASE로 */
    kprintf("mtvec = 0x%08x (mode=%u)\n", csr_read(mtvec), csr_read(mtvec) & 3);
    uint32_t i0 = csr_read(minstret);
    uint32_t r = syscall1(1, 21);
    uint32_t i1 = csr_read(minstret);
    nopcall(1, 21);
    uint32_t i2 = csr_read(minstret);
    kprintf("ecall sys1(21) -> %u, mcause=%u, ecall vs nop: +%u instructions\n",
            r, last_cause, (i1 - i0) - (i2 - i1));
    kprintf("illegal instruction (csrw to read-only cycle):\n");
    __asm volatile(".word 0xc0001073");          /* = unimp (csrrw x0, cycle, x0) */
    kprintf("load from unmapped 0x10200000:\n");
    volatile uint32_t v = *(volatile uint32_t *)0x10200000u; (void)v;
    kprintf("misaligned lw (QEMU emulates it) then misaligned amoadd.w:\n");
    uint32_t p = 0x80008002u, one = 1, old;
    __asm volatile("lw %0, 0(%1)" : "=r"(old) : "r"(p));
    __asm volatile("amoadd.w %0, %1, (%2)" : "=r"(old) : "r"(one), "r"(p) : "memory");
    kprintf("ebreak:\n");
    __asm volatile("ebreak");
    kprintf("back in main, done\n");
    return 0;
}
```

```text
illegal instruction (csrw to read-only cycle):
  trap: mcause=2 mepc=0x80000588 mtval=0xc0001073
load from unmapped 0x10200000:
  trap: mcause=5 mepc=0x8000059a mtval=0x10200000
```

출력에서 볼 것:
- `mtvec = 0x80000070 (mode=0)` — BASE가 4바이트 정렬이면 direct 모드는 충분하다.
- **ecall 한 번 = nop보다 109명령 더**. 하드웨어 진입/복귀는 사실상 0명령이고, 109개 대부분이 trap.S의 저장 · 복원(약 70)과 C 디스패처다. Cortex-M3의 같은 실험(예제 4)은 `svc` vs `nop`이 **+5명령**이다.
- illegal instruction은 `mtval = 0xc0001073`, 즉 **명령 비트 자체**를 준다(QEMU 구현; 스펙상 0이어도 된다). 디코더 없이도 무슨 명령이 문제였는지 바로 안다.
- 없는 주소(0x10200000) 읽기는 mcause 5, `mtval = 주소`. Cortex-M의 BusFault + BFAR에 해당한다. 참고로 0x50000000을 읽으면 아무 일도 없었다 — QEMU virt에서 0x40000000–0x7FFFFFFF는 PCIe MMIO 창이라 "있는 주소"다. **"없는 주소"는 메모리 맵을 보고 고른다.**
- misaligned `lw`는 QEMU가 그냥 처리했고(스펙은 하드웨어 지원 · 트랩 둘 다 허용), misaligned `amoadd.w`는 트랩했다. 스펙의 기대는 store/AMO misaligned(6) 계열인데 QEMU 10.2는 **4(load misaligned)** 로 보고했다. 이런 세부는 에뮬레이터와 실칩이 다를 수 있으니 실칩에서 다시 확인한다.
- ebreak는 mcause 3, mtval = PC. 압축 명령 `c.ebreak`(2바이트)라서 핸들러가 길이를 보고 +2 했다. **예외 후 "그 명령 건너뛰기"는 항상 길이 판정이 필요하다**(하위 2비트가 `11`이면 4바이트).

### 2.5 mepc 규칙 — 무한 트랩의 원인 1순위

| 트랩 종류 | mepc가 가리키는 곳 | 복귀 전 할 일 |
|---|---|---|
| 인터럽트(비동기) | 아직 실행 안 한 다음 명령 | 그대로 mret |
| ecall · ebreak · fault(동기) | **트랩을 일으킨 그 명령** | 에뮬레이션/서비스 후 건너뛰려면 +4(또는 +2). 안 하면 같은 명령에서 영원히 트랩 |

FreeRTOS 포트는 이 규칙을 그대로 코드로 쓴다. `portcontextSAVE_EXCEPTION_CONTEXT`가 `addi a1, a1, 4  /* Synchronous so update exception return address to the instruction after the instruction that generated the exception. */`를 하고, 인터럽트 경로는 "unmodified exception return address"를 저장한다(`portable/GCC/RISC-V/portContext.h`). 단, FreeRTOS는 **모든 동기 예외에 +4**를 한다 — 압축된 fault 명령이면 2바이트 어긋난 곳으로 돌아간다. 포트가 "동기 예외 = ecall"만 정상 경로로 가정하기 때문에 괜찮은 것이고, 다른 예외는 `freertos_risc_v_application_exception_handler`(기본 구현: `j .`로 멈춤)에서 처리해야 한다.

### 2.6 mscratch 트릭 — 스택을 어떻게 고르나

트랩 진입 첫 명령 시점에는 **모든 범용 레지스터가 살아 있는 값**이라 손댈 수 없다. 그런데 저장하려면 쓸 곳(스택 주소)이 필요하다. 해법이 `csrrw sp, mscratch, sp` — 레지스터 하나도 망가뜨리지 않고 sp와 mscratch를 맞바꾸는 한 명령이다.

- 예제의 규칙: "M-mode에서 도는 동안 mscratch = 0, U-mode에서 도는 동안 mscratch = 커널 스택 top". 맞바꾼 뒤 sp가 0이 아니면 U에서 온 것(sp가 이제 커널 스택), 0이면 M에서 온 것(원래 sp를 mscratch에서 되찾는다).
- Zephyr는 같은 CSR에 `_current_cpu` 포인터를 둔다(`arch/riscv/core/isr.S`의 `get_current_cpu` 매크로: SMP나 USERSPACE면 `csrr \dst, mscratch`). 진입하자마자 `csrrw s0, mscratch, s0`로 per-CPU 구조체를 얻고, 거기서 privileged 스택 주소를 꺼낸다.
- Cortex-M은 이 문제가 없다 — 하드웨어가 예외 진입 때 자동으로 MSP를 쓰니까(B1의 MSP/PSP). **RISC-V에서 MSP/PSP 분리는 소프트웨어 관례**다.

### 2.7 함정

- mtvec을 설정하기 전에 트랩이 나면(예: startup에서 잘못된 주소 접근) PC가 0으로 가서 엉뚱한 곳을 실행한다. 증상: "아무 출력 없이 멈춤". `_start` 초반에 임시 `mtvec = 무한 루프`를 넣어 두면 디버거로 잡기 쉽다.
- vectored 모드 BASE 정렬: 스펙은 4바이트 정렬만 요구하지만 구현이 더 큰 정렬(64 · 256바이트)을 요구할 수 있다. FreeRTOS는 `freertos_risc_v_trap_handler`를 `.align 8`(256바이트)로, Zephyr는 `CONFIG_RISCV_TRAP_HANDLER_ALIGNMENT`로 맞춘다.
- `csrw mstatus, x`로 통째로 쓰면 FS/VS 같은 다른 필드를 날린다. MIE만 바꿀 때는 `csrs`/`csrc`를 쓴다(포트의 `portDISABLE_INTERRUPTS()`가 `csrc mstatus, 8`인 이유).
- RV32에서 64비트 CSR(`mcycle`/`mcycleh`)을 읽을 때 두 번 읽는 사이에 하위가 넘치면 찢긴 값이 나온다. hi → lo → hi 재확인 루프(board.c의 `mtime_read`와 같은 방식)를 쓴다.

## 3. 타이머와 인터럽트 컨트롤러 — CLINT · PLIC · CLIC · AIA

### 3.1 직관 — NVIC 하나가 하던 일을 여러 블록이 나눠 맡는다

### 3.2 CLINT — mtime, mtimecmp, msip

CLINT(Core-Local Interruptor)는 SiFive가 만든 사실상의 표준 블록이다(표준화 버전은 ACLINT). 레지스터는 세 가지뿐이다.

| 레지스터 | QEMU virt 주소 | 뜻 |
|---|---|---|
| `msip[hart]` | 0x02000000 + 4 × hart | 1을 쓰면 그 hart에 software interrupt (MSIP) — SMP IPI |
| `mtimecmp[hart]` | 0x02004000 + 8 × hart | 64비트 비교값. `mtime ≥ mtimecmp`인 동안 MTIP가 **계속** 켜져 있다(레벨) |
| `mtime` | 0x0200BFF8 | 64비트 자유 증가 카운터, 모든 hart 공유. virt는 10 MHz |

SysTick과의 결정적 차이:
- **자동 reload가 없다.** tick마다 ISR이 `mtimecmp += 주기`를 직접 써야 한다. 안 쓰면 MTIP가 계속 켜져 있어 ISR에서 나오자마자 다시 들어온다(인터럽트 폭풍).
- **인터럽트를 "지우는" 방법이 mtimecmp를 미래로 옮기는 것**이다. 끄고 싶으면 `mtimecmp = 0xFFFFFFFF_FFFFFFFF`.
- RV32에서는 64비트를 32비트 두 번에 쓴다. 쓰는 중간에 잠깐 "과거 값"이 되면 거짓 인터럽트가 난다. 스펙이 권하는 순서는 **lo ← 0xFFFFFFFF → hi ← 새 hi → lo ← 새 lo**. FreeRTOS `portUPDATE_MTIMER_COMPARE_REGISTER` 매크로가 정확히 이 순서다(`li a4, -1` / `sw a4, 0(a0)` / `sw a3, 4(a0)` / `sw a2, 0(a0)`).
- **주파수가 CPU 클럭이 아니다.** mtime은 보통 저속 고정 클럭(virt 10 MHz, 실칩은 32.768 kHz RTC나 분주 클럭)으로 돈다. FreeRTOS 포트는 `uxTimerIncrementsForOneTick = configCPU_CLOCK_HZ / configTICK_RATE_HZ`로 계산하므로, 이 포트에서 `configCPU_CLOCK_HZ`는 사실상 **"mtime 주파수"** 다. 실제 CPU 클럭을 넣으면 tick이 엉뚱하게 느려진다(12절 표).

### 예제 3 — 1 kHz tick: vectored + 속성 ISR vs direct + 전체 저장

무엇을 확인하는 코드인가: CLINT로 1 kHz tick을 만들고, 두 가지 트랩 진입 방식에서 인터럽트 1회가 프로그램에 얹는 명령 수와 진입 지연을 잰다. (A) mtvec vectored 모드 + GCC `__attribute__((interrupt("machine")))` C ISR — 컴파일러가 **쓰는 레지스터만** 저장하고 `mret`으로 끝낸다. (B) direct 모드 + 예제 2의 trap.S(30개 전부 저장) + C 디스패처.

```c
/* ex3 — CLINT mtimecmp로 1 kHz tick. (A) vectored mtvec + interrupt 속성 C ISR vs
 * (B) direct mtvec + 31레지스터 전체 저장(trap.S). 인터럽트 1회당 추가 명령 수를 minstret으로 잰다 */
#include "board.h"
#include "frame.h"
#define TICK (MTIME_HZ / 1000)                       /* 10000 mtime = 1 ms */
#define R32(a) (*(volatile uint32_t *)(a))
static volatile uint32_t ticks, lat_min = ~0u, lat_max;
static uint64_t next;
static inline void tick_body(void) {
    uint32_t lat = R32(MTIME) - (uint32_t)next;     /* 예정 시각 대비 늦은 정도 (100 ns 단위) */
    if (lat < lat_min) lat_min = lat;
    if (lat > lat_max) lat_max = lat;
    next += TICK;
    R32(MTIMECMP) = 0xFFFFFFFFu; R32(MTIMECMP + 4) = (uint32_t)(next >> 32); R32(MTIMECMP) = (uint32_t)next;
    ticks++;
}
__attribute__((interrupt("machine"))) void mtimer_isr(void) { tick_body(); }
__attribute__((interrupt("machine"))) void unexpected_isr(void) { board_exit(3); }
__attribute__((naked, aligned(64))) void vec_table(void) {   /* vectored: BASE + 4 × cause */
    __asm volatile(".option push; .option norvc\n"
        "j unexpected_isr; j unexpected_isr; j unexpected_isr; j unexpected_isr\n"
        "j unexpected_isr; j unexpected_isr; j unexpected_isr; j mtimer_isr\n"
        ".option pop");
}
void trap_handler(struct frame *f) {                 /* (B) 경로의 C 디스패처 */
    if (f->mcause == 0x80000007u) tick_body(); else board_exit(4);
}
static uint32_t run(uint32_t n) {                    /* n번 도는 바쁜 루프의 명령 수 */
    uint32_t i0 = csr_read(minstret);
    for (volatile uint32_t k = 0; k < n; k++) { }
    return csr_read(minstret) - i0;
}
static void measure(const char *name, uint32_t mtvec, uint32_t base) {
    ticks = 0; lat_min = ~0u; lat_max = 0;
    csr_write(mtvec, mtvec);
    next = mtime_read() + TICK; mtimecmp_write(next);
    csr_set(mie, 1u << 7);                           /* MTIE */
    csr_set(mstatus, 1u << 3);                       /* MIE */
    uint32_t d = run(1000000);
    csr_clear(mstatus, 1u << 3);
    kprintf("%s: ticks=%u  extra instr/IRQ=%u  latency(mtime) min=%u max=%u\n",
            name, ticks, (d - base) / ticks, lat_min, lat_max);
}
int main(void) {
    uint32_t base = run(1000000);                    /* 인터럽트 없이 */
    kprintf("no IRQ   : 1e6 loop = %u instructions\n", base);
    measure("(A) vectored + interrupt attr", (uint32_t)vec_table | 1u, base);
    measure("(B) direct + full 31-reg save", (uint32_t)trap_entry, base);
    return 0;
}
```

```text
no IRQ   : 1e6 loop = 5000006 instructions
(A) vectored + interrupt attr: ticks=160  extra instr/IRQ=48  latency(mtime) min=4 max=4
(B) direct + full 31-reg save: ticks=160  extra instr/IRQ=120  latency(mtime) min=17 max=18
```

출력에서 볼 것:
- 바쁜 루프 1e6회 = 5,000,006명령(icount 32 ns → 160 ms) 동안 tick 160번 — 1 kHz가 맞다.
- **(A) 48명령 / (B) 120명령.** 같은 일(지연 기록 + mtimecmp 갱신 + 카운터 증가)인데 진입 방식만으로 2.5배 차이다. (A)의 디스어셈블(예제 11)을 보면 저장 7개 + 복원 7개 + 본문 약 31개 + `mret` + 벡터 `j` 1개다.
- 진입 지연 `min=max=4`(mtime 100 ns 단위 = 400 ns ≈ 12명령)와 `17~18`(≈ 53명령). (B)는 ISR이 mtime을 읽기 전까지 30개 저장 + CSR 읽기 + `call`을 지나야 한다. **소프트웨어 저장 비용은 그대로 인터럽트 지연이다.** QEMU icount에서 인터럽트는 번역 블록 경계에서만 확인되므로 이 숫자는 "실행 명령 기준 하한" 정도로 읽는다.
- vectored 테이블은 `.option norvc`로 감싸서 각 `j`가 정확히 4바이트가 되게 했다. 압축되어 2바이트가 되면 `BASE + 4 × 7` 계산이 어긋난다.
- (A)가 빠른 대신 대가가 있다. 속성 ISR 안에서 **함수를 부르면** 컴파일러는 caller-saved 16개를 전부 저장해야 하고, 컨텍스트 스위치를 하려면 결국 나머지(callee-saved 12개)도 저장해야 한다. RTOS 포트가 "tick ISR은 전체 저장"을 택하는 이유다(7, 8절).

### 3.3 PLIC — priority, enable, threshold, claim, complete

PLIC(Platform-Level Interrupt Controller)은 장치 인터럽트를 모아 hart별 "context"(hart × 모드)에 MEIP/SEIP 한 줄로 전달한다.

| 레지스터 (virt, context 0 = hart0 M-mode) | 주소 | 동작 |
|---|---|---|
| priority[n] | 0x0C000000 + 4n | 0 = 꺼짐, 1..7(virt). 클수록 높다 — **NVIC와 반대 방향** |
| pending | 0x0C001000 | 게이트웨이가 잡아 둔 요청 비트 (읽기 전용) |
| enable[ctx] | 0x0C002000 + 0x80 × ctx | 이 context가 받을 소스 비트맵 |
| threshold[ctx] | 0x0C200000 + 0x1000 × ctx | priority > threshold인 것만 전달 |
| claim/complete[ctx] | 0x0C200004 + 0x1000 × ctx | **읽기 = claim**(가장 높은 pending ID를 받고 그 pending을 내림), **쓰기 = complete**(그 ID를 다시 받을 수 있게) |

threshold는 BASEPRI와 같은 역할이다 — "이 우선순위 이하는 막아라". 다만 hart의 전역 스위치(mstatus.MIE)와 별개로 PLIC 안에서 걸러진다.

### 예제 7 — PLIC으로 UART 송신을 인터럽트 구동하기 (+ complete 빼먹기)

무엇을 확인하는 코드인가: 16550의 "송신 버퍼 빔" 인터럽트(IER.ETBEI)를 PLIC 소스 10으로 받아 문자열을 한 글자씩 내보낸다. [1] 정상, [2] threshold ≥ priority로 막기, [3] complete를 일부러 빼먹기.

```c
/* ex7 — PLIC: UART(IRQ 10) 송신-빔 인터럽트로 문자열을 인터럽트 구동 출력.
 * priority / enable / threshold / claim / complete를 하나씩, complete 빼먹기 실험까지 */
#include "board.h"
#include "frame.h"
#define R32(a) (*(volatile uint32_t *)(a))
#define R8(a)  (*(volatile uint8_t *)(a))
#define UART_IRQ       10
#define PLIC_PRIO(n)   R32(PLIC + 4u * (n))
#define PLIC_PENDING   R32(PLIC + 0x1000u)
#define PLIC_ENABLE    R32(PLIC + 0x2000u)        /* context 0 = hart0 M-mode */
#define PLIC_THRESH    R32(PLIC + 0x200000u)
#define PLIC_CLAIM     R32(PLIC + 0x200004u)      /* 읽기 = claim, 쓰기 = complete */
static const char *volatile txp;
static volatile uint32_t irqs, skip_complete;
void trap_handler(struct frame *f) {
    if (f->mcause != 0x8000000Bu) board_exit(6);  /* M external interrupt만 기대 */
    uint32_t id = PLIC_CLAIM;                     /* 가장 높은 우선순위 pending ID, pending 비트 내림 */
    irqs++;
    if (id == UART_IRQ) {
        if (*txp) R8(UART0) = (uint8_t)*txp++;    /* THR에 한 글자 → 다시 빌 때 또 인터럽트 */
        else R8(UART0 + 1) = 0;                   /* 다 보냈으면 IER.ETBEI 끄기 */
    }
    if (!skip_complete) PLIC_CLAIM = id;          /* complete: 이 ID를 다시 받을 수 있게 */
}
static void send(const char *s, uint32_t thresh, uint32_t no_complete) {
    txp = s; irqs = 0; skip_complete = no_complete;
    PLIC_THRESH = thresh;
    R8(UART0 + 1) = 0x02;                         /* IER.ETBEI: THR 비면 IRQ */
    for (volatile int k = 0; k < 200000; k++) { } /* 잠깐 기다림 */
    R8(UART0 + 1) = 0;
    kprintf("\n  -> threshold=%u complete=%s : irqs=%u, PLIC pending bit10=%u\n", thresh,
            no_complete ? "skipped" : "yes", irqs, (PLIC_PENDING >> UART_IRQ) & 1);
}
int main(void) {
    csr_write(mtvec, (uint32_t)trap_entry);
    PLIC_PRIO(UART_IRQ) = 1;                      /* 0 = 꺼짐, 1..7 */
    PLIC_ENABLE = 1u << UART_IRQ;
    csr_set(mie, 1u << 11);                       /* MEIE */
    csr_set(mstatus, 1u << 3);
    kprintf("[1] ");  send("PLIC drives TX!", 0, 0);
    kprintf("[2] ");  send("masked", 1, 0);       /* priority 1 <= threshold 1 → 전달 안 됨 */
    PLIC_THRESH = 0;                              /* 문턱을 내리면 남아 있던 pending이 들어온다 */
    for (volatile int k = 0; k < 1000; k++) { }
    kprintf("\n[3] ");  send("no complete", 0, 1);
    return 0;
}
```

```text
[1] PLIC drives TX!
  -> threshold=0 complete=yes : irqs=16, PLIC pending bit10=0
[2] 
  -> threshold=1 complete=yes : irqs=0, PLIC pending bit10=1
m
[3] n
  -> threshold=0 complete=skipped : irqs=1, PLIC pending bit10=1
```

출력에서 볼 것:
- [1] 15글자 + 마지막 "보낼 것 없음" 1회 = **irqs=16**. 각 claim이 ID 10을 돌려줬다.
- [2] threshold=1, priority=1 → 전달 안 됨(**irqs=0**). 그런데 **pending bit10=1** — 요청은 PLIC 게이트웨이에 잡혀 있다. 그 뒤 threshold를 0으로 내리자 잡혀 있던 요청이 들어와 `m` 한 글자가 나갔다(그 사이 IER을 꺼서 더 이상은 안 나옴). "마스크 = 버림"이 아니라 "마스크 = 보류"다.
- [3] complete를 안 쓰자 **딱 1번**(`n`)만 들어오고 그 뒤로는 UART가 계속 요청해도(pending=1) 다시 안 들어온다. Don이 SSD에서 인터럽트 ACK를 빼먹어 본 hang과 같은 모양이다. 실제 버그에서는 "처음 한 번은 되는데 그 다음부터 장치가 죽은 것 같다"로 보인다.
- 이 예제는 kprintf(폴링)와 인터럽트 출력이 같은 UART에 섞인다. RTOS에서는 이런 공유 자원을 뮤텍스나 단일 출력 태스크로 묶는다(D 모듈).

### 3.4 PLIC 위에서 중첩 인터럽트를 하려면

PLIC + CLINT 조합에는 **하드웨어 선점이 없다.** 트랩 진입 때 MIE=0이 되므로, 높은 우선순위 장치가 낮은 우선순위 ISR을 끊고 들어오려면 소프트웨어가:

1. mepc · mstatus(그리고 레지스터)를 저장하고,
2. claim으로 ID를 받은 뒤 threshold를 그 ID의 priority로 올리고,
3. `csrs mstatus, MIE`로 인터럽트를 다시 켜고 ISR을 실행하고,
4. MIE를 끄고 threshold를 되돌리고 complete를 쓰고 복원한다.

Cortex-M의 NVIC가 하드웨어로 하는 일(B3의 선점 그룹, B2의 late-arrival · tail-chaining)을 네 단계 소프트웨어로 흉내 내는 것이다. FreeRTOS RISC-V 포트는 **중첩을 지원하지 않는다**(ISR 스택 하나, 트랩 안에서 MIE를 켜지 않음). Zephyr는 PLIC 드라이버(`drivers/interrupt_controller/intc_plic.c`)가 claim/complete를 처리하고, 중첩은 CLIC 계열에서 지원한다.

### 3.5 CLIC — MCU를 위한 표준, 그러나 아직 비준 전

CLIC(Core-Local Interrupt Controller)은 "NVIC 같은 RISC-V 인터럽트 컨트롤러"를 목표로 한 표준 작업이다. 핵심 아이디어:

- 인터럽트 **번호마다** level(선점 단계)과 priority를 둔다(`clicintctl`). 높은 level이 낮은 level ISR을 하드웨어로 선점한다.
- **selective hardware vectoring** — 번호마다 "이 인터럽트는 벡터 테이블에서 주소를 꺼내 바로 핸들러로"(Cortex-M처럼 주소 표)를 고를 수 있다. mtvec MODE=3이 CLIC 모드다.
- 트랩 상태(mpil · 이전 level)를 mcause 등에 추가로 저장해 중첩 복귀를 하드웨어가 돕는다.

**비준 상태 (2026-10-25 웹 확인)**: GitHub `riscv/riscv-fast-interrupt` 저장소의 최신 릴리스는 **v0.20(2026-07-31)** 이고, 문서는 **"Advanced Core-Local Interrupt Controller (ACLIC)"** 로 이름이 바뀌어 **"Stable" 상태**(anything could still change)로 적혀 있다. 릴리스 노트에는 Smeihv · Smnip · Smidctrl 같은 하위 확장 이름이 보인다. 즉 **비준(ratified)된 표준 CLIC은 아직 없다** — BM 나침반의 "아직 비준 전"은 여전히 맞다.

그래서 실제 칩은 **벤더 구현**을 쓴다.

| 구현 | 칩 | 특징 (출처) |
|---|---|---|
| Nuclei ECLIC | GD32VF103 (Bumblebee 코어) | CLIC 초안 기반 + 자체 확장. Zephyr DTS `compatible = "nuclei,eclic"` |
| Nordic VPR CLIC | nRF54 계열의 RISC-V 보조 코어(VPR) | Zephyr `soc/nordic/common/vpr/Kconfig`가 `RISCV_HAS_CLIC` · `RISCV_VECTORED_MODE` · **`RISCV_SOC_HAS_ISR_STACKING`**(하드웨어가 레지스터를 쌓음)을 select |
| Hazard3 Xh3irq | RP2350의 RISC-V 코어 | 중첩 · 우선순위가 있는 Hazard3 고유 컨트롤러. Zephyr `hazard3,hazard3-intc` |
| WCH PFIC | CH32V 계열(QingKe 코어) | NVIC를 닮은 벤더 컨트롤러 + HPE(Hardware Prologue/Epilogue, 하드웨어 레지스터 저장). Zephyr DTS `wch,pfic`. HPE 단수는 QingKe V4 매뉴얼 기준 3단 — 원문 표는 이 노트에서 직접 확인 못 함 |
| Espressif interrupt matrix | ESP32-C3 · C6 | 주변장치 → CPU 인터럽트 라인을 매핑하는 Espressif 고유 블록. Zephyr `espressif,esp32-intc` |

**QEMU 10.2 virt는 CLIC을 모델링하지 않는다** — 이 노트에서 CLIC 동작은 실행해서 보여 줄 수 없다. Zephyr 소스에서 구조만 확인했다: `drivers/interrupt_controller/intc_clic.c`, `intc_nrfx_clic.c`, `Kconfig.clic`(`CLIC_SMCLICSHV_EXT` 등).

### 3.6 AIA — 애플리케이션 프로세서의 인터럽트 (짧게)

AIA(Advanced Interrupt Architecture, 2023년 비준)는 APLIC(유선 인터럽트를 받아 우선순위 처리)과 IMSIC(MSI — 메시지, 즉 메모리 쓰기로 전달되는 인터럽트를 hart별 파일에 기록)로 PLIC을 대체한다. PCIe MSI, 가상화(게스트 인터럽트 파일)에 맞춘 설계라 **MCU에서는 드물다**. QEMU virt는 `-machine virt,aia=aplic-imsic`으로 켤 수 있고, Zephyr에는 `intc_riscv_aplic.c` · `intc_riscv_imsic.c` 드라이버가 있다. RTOS 포팅 관점에서 기억할 것은 "AIA 칩이면 claim/complete 대신 `mtopei` CSR 등 다른 레지스터로 ID를 읽는다" 정도다.

### 3.7 NVIC와 나란히

| 항목 | Cortex-M NVIC | PLIC + CLINT | CLIC 계열 |
|---|---|---|---|
| 우선순위 방향 | 숫자 작을수록 높다 | 숫자 클수록 높다 (0 = 꺼짐) | 클수록 높다 |
| 하드웨어 선점 | 있음 (선점 그룹) | **없음** — 소프트웨어 4단계 | 있음 (level) |
| 벡터 | 번호별 주소 표 | 종류 3개뿐 → 소프트웨어 디스패치 | 번호별 (SHV 선택) |
| 레지스터 저장 | 8워드 하드웨어 | 0 | 0 (표준) / 벤더는 하드웨어 저장 있음 |
| ACK | 대개 장치 플래그만 | **claim + complete** 필수 | 장치 플래그 (+ 모드에 따라) |
| 마스크 | PRIMASK / BASEPRI | mstatus.MIE / threshold | mstatus.MIE / mintthresh |
| tick 타이머 | SysTick (코어 내장, 자동 reload) | mtimecmp (매번 다시 씀) | mtimecmp 또는 벤더 타이머 |
| 지연 꼬리 처리 | tail-chaining · late-arrival | 없음 (소프트웨어가 루프로 다시 claim) | 구현에 따라 |

## 4. 하드웨어 스태킹이 없다 — 트랩 비용을 명령 수로 재기

### 4.1 직관

B2에서 본 Cortex-M의 8워드 프레임은 **AAPCS의 caller-saved 레지스터 집합과 정확히 같다**. 그래서 하드웨어가 그것만 밀어 주면 컴파일러가 만든 C 함수가 그대로 ISR이 된다. RISC-V psABI의 caller-saved는 **ra, t0–t6, a0–a7 = 16개**다. 같은 원리로 "C 함수를 부를 수 있는 ISR"을 만들려면 최소 16개를 저장해야 하고, 그 일을 하드웨어가 안 하니 소프트웨어가 한다. 컨텍스트 스위치까지 하려면 s0–s11 12개 + sp까지 해서 사실상 31개 전부다.

### 예제 4 — 비교 기준: Cortex-M3의 SysTick C ISR과 SVC 왕복

무엇을 확인하는 코드인가: 예제 2 · 3과 같은 실험을 Cortex-M3(mps2-an385)에서. QEMU Arm에는 명령 카운터 CSR이 없으므로 icount(32 ns/명령)와 FPGAIO 25 MHz 카운터(40 ns)로 `명령 수 = 카운트 × 40 / 32`로 환산했다.

```c
/* ex4m — 비교용 Cortex-M3(mps2-an385): SysTick 1 kHz C ISR와 SVC 왕복의 "추가 명령 수".
 * QEMU에 명령 카운터가 없으므로 ICOUNT(명령 1개 = 32 ns) + FPGAIO 25 MHz 카운터(40 ns)로 환산 */
#include "board.h"
#define FPGA_CNT REG32(0x40028018u)
#define SYST_CSR REG32(0xE000E010u)
#define SYST_RVR REG32(0xE000E014u)
#define SYST_CVR REG32(0xE000E018u)
static volatile uint32_t ticks, lat_min = ~0u, lat_max;
void SysTick_Handler(void) {                       /* 하드웨어가 r0-r3,r12,lr,pc,xpsr을 이미 밀었다 */
    uint32_t lat = (SYST_RVR - SYST_CVR);          /* reload 후 지난 cycle (SysTick은 자동 reload) */
    if (lat < lat_min) lat_min = lat;
    if (lat > lat_max) lat_max = lat;
    ticks++;
}
void SVC_Handler_C(uint32_t *f) { f[0] = f[0] * 2; }   /* f[0] = 쌓인 r0 */
__attribute__((naked)) void SVC_Handler(void) {
    __asm volatile("mrs r0, msp\n b SVC_Handler_C");
}
static uint32_t run(uint32_t n) {
    uint32_t t0 = FPGA_CNT;
    for (volatile uint32_t k = 0; k < n; k++) { }
    return FPGA_CNT - t0;
}
#define CALL(name, insn) __attribute__((noinline)) uint32_t name(uint32_t a) { \
    register uint32_t r0 __asm("r0") = a; __asm volatile(insn : "+r"(r0) :: "memory"); return r0; }
CALL(svc1, "svc #1")
CALL(nop1, "nop")
int main(void) {
    uint32_t base = run(1000000);
    board_printf_raw("no IRQ : 1e6 loop = %u counts (x40ns)\n", base);
    SYST_RVR = 25000 - 1; SYST_CVR = 0; SYST_CSR = 7;   /* CPU clock, TICKINT, ENABLE → 1 kHz */
    uint32_t d = run(1000000);
    SYST_CSR = 0;
    uint32_t n = ticks;
    board_printf_raw("SysTick: ticks=%u extra instr/IRQ=%u latency(cycles) min=%u max=%u\n",
                     n, (d - base) * 5 / 4 / n, lat_min, lat_max);
    uint32_t t0 = FPGA_CNT, s = 0;
    for (uint32_t i = 0; i < 10000; i++) s += svc1(i);
    uint32_t t_svc = FPGA_CNT - t0;
    t0 = FPGA_CNT;
    for (uint32_t i = 0; i < 10000; i++) s += nop1(i);
    uint32_t t_ref = FPGA_CNT - t0;
    board_printf_raw("SVC round trip = svc vs nop: +%u instr/call (sum=%u)\n", (t_svc - t_ref) * 5 / 4 / 10000, s);
    board_exit(0);
}
```

### 4.4 Don 경험과 연결

SSD 펌웨어의 "fast path ISR"을 떠올리면 된다. NAND 완료 인터럽트처럼 초당 수십만 번 오는 ISR은 레지스터를 덜 쓰도록 짜고, 무거운 일은 태스크로 넘겼다. RISC-V에서는 이 습관이 **필수**가 된다. 드론 비행 제어기의 8 kHz IMU ISR을 예로 들면, 1회 120명령 진입 비용은 초당 96만 명령 — 100 MHz급 코어의 약 1%가 "레지스터 저장"에만 간다. 속성 ISR + vectored로 48명령이면 0.4%다.

## 5. PMP — RISC-V의 MPU

> 🔁 이 절은 Bare-Metal BM E4(PMP/ePMP)와 겹친다 (주인: 이 노트).

### 5.1 직관

PMP(Physical Memory Protection)는 "주소 범위마다 R/W/X 권한"을 거는 표다. Cortex-M MPU와 같은 목적이지만 규칙이 다르다.

- **번호가 낮은 entry가 이긴다.** 주소가 여러 entry에 걸리면 가장 낮은 번호의 설정만 본다. 그래서 "넓은 허용 영역 위에 좁은 금지 영역"을 만들려면 금지를 **앞 번호**에 둔다(Cortex-M MPU는 높은 번호가 이긴다 — 반대다).
- **U-mode는 기본 거부, M-mode는 기본 허용.** U-mode 접근이 어떤 entry에도 안 걸리면 fault. M-mode는 entry에 걸려도 **L(lock) 비트가 없으면 검사를 건너뛴다.**
- **L 비트는 리셋 전까지 영구.** 잠긴 entry는 다시 쓸 수 없고, M-mode에도 권한이 적용된다. 부트 ROM을 보호하거나 "M-mode도 이 영역을 실행 못 하게" 할 때 쓴다.

### 5.2 정의 — pmpcfg와 pmpaddr

`pmpcfgN`(RV32: entry 4개를 8비트씩) 한 바이트의 구조: **L(7) · 00 · A(4:3) · X(2) · W(1) · R(0)**. A는 영역 모양이다.

| A | 이름 | 영역 |
|---|---|---|
| 0 | OFF | 꺼짐 |
| 1 | TOR | Top Of Range: `pmpaddr[i-1] ≤ 주소 < pmpaddr[i]` (entry 0은 0부터) |
| 2 | NA4 | 4바이트 하나 |
| 3 | NAPOT | 2의 거듭제곱 크기, 크기만큼 정렬된 영역 |

`pmpaddr`에는 **주소 >> 2**가 들어간다(34비트 물리 주소를 32비트에 담으려고). NAPOT 인코딩은 "하위에 1을 채워 크기를 표현"한다: `pmpaddr = (base >> 2) | (size / 8 − 1)`. 예를 들어 0x80002000의 4 KB 페이지는 `(0x80002000 >> 2) | (4096/8 − 1) = 0x20000800 | 0x1FF = 0x200009FF`. 16 MB RAM(0x80000000)은 `0x20000000 | 0x1FFFFF = 0x201FFFFF`. 예제 5 출력과 똑같다.

### 예제 5 — U-mode 태스크를 PMP로 가두기

무엇을 확인하는 코드인가: M-mode가 PMP 두 entry를 설정하고 `mret`으로 U-mode "태스크"로 내려간다. 태스크는 ecall로 커널 서비스를 부르고(mcause 8), 보호 페이지를 읽고(mcause 5), CSR을 만진다(mcause 2). 마지막으로 L 비트를 켜서 M-mode까지 묶이는지 본다.

```c
/* ex5 — PMP로 U-mode "태스크"를 가둔다: 허용 RAM은 OK, 보호 페이지는 load access fault(5),
 * CSR 접근은 illegal(2), 커널 호출은 ecall from U(8). 마지막에 L(lock) 비트가 M-mode까지 묶는 것 확인 */
#include "board.h"
#include "frame.h"
static uint32_t secret[1024] __attribute__((aligned(4096))) = {0xC0FFEE};   /* 4 KB 보호 페이지 */
static uint32_t kstack[512] __attribute__((aligned(16)));                   /* 트랩용 커널 스택 */
static uint32_t ustack[256] __attribute__((aligned(16)));                   /* U 태스크 스택 */
static volatile uint32_t shared = 7;
#define NAPOT(base, size) (((base) >> 2) | (((size) >> 3) - 1))
static void ucall(uint32_t no, const char *s) {
    register uint32_t a0 __asm("a0") = (uint32_t)s, a7 __asm("a7") = no;
    __asm volatile("ecall" : "+r"(a0) : "r"(a7) : "memory");
}
static void user_main(void) {                       /* U-mode에서 돈다: UART도 직접 못 만진다 */
    ucall(1, "  [U] hello via ecall\n");
    ucall(1, shared == 7 ? "  [U] read shared OK\n" : "  [U] ???\n");
    volatile uint32_t v = secret[0]; (void)v;       /* → load access fault */
    uint32_t ms; __asm volatile("csrr %0, mstatus" : "=r"(ms)); (void)ms;   /* → illegal */
    ucall(2, "");                                   /* 종료 요청 */
}
static const char *const why[] = {[2] = "illegal instruction", [5] = "load access fault",
                                  [7] = "store access fault", [8] = "ecall from U"};
void trap_handler(struct frame *f) {
    uint32_t from = (f->mstatus >> 11) & 3;
    if (f->mcause == 8) {                           /* 커널 서비스 */
        f->mepc += 4;
        if (f->r[17] == 1) { kprintf("%s", (const char *)f->r[10]); return; }
        kprintf("[M] U task exited. now set L bit on entry0 and touch secret from M:\n");
        csr_write(pmpcfg0, (csr_read(pmpcfg0) & ~0xFFu) | 0x98);   /* L=1, A=NAPOT, RWX=000 */
        volatile uint32_t v = secret[0]; (void)v;
        csr_write(pmpcfg0, csr_read(pmpcfg0) & ~0xFFu);             /* 잠긴 entry는 안 바뀐다 */
        kprintf("[M] pmpcfg0 after clear attempt = 0x%08x (locked until reset)\n", csr_read(pmpcfg0));
        board_exit(0);
    }
    kprintf("  [M] trap from %s: mcause=%u (%s) mepc=0x%08x mtval=0x%08x\n", from ? "M" : "U",
            f->mcause, f->mcause < 9 && why[f->mcause] ? why[f->mcause] : "?", f->mepc, f->mtval);
    f->mepc += ((*(uint16_t *)f->mepc & 3) == 3) ? 4 : 2;           /* 그 명령만 건너뛴다 */
}
int main(void) {
    csr_write(mtvec, (uint32_t)trap_entry);
    csr_write(pmpaddr0, NAPOT((uint32_t)secret, 4096));             /* entry0: secret, U 권한 없음 */
    csr_write(pmpaddr1, NAPOT(0x80000000u, 0x1000000u));            /* entry1: RAM 16 MB, RWX */
    csr_write(pmpcfg0, (0x1Fu << 8) | 0x18u);                       /* cfg1=NAPOT|RWX, cfg0=NAPOT|--- */
    kprintf("pmpaddr0=0x%08x pmpaddr1=0x%08x pmpcfg0=0x%08x\n",
            csr_read(pmpaddr0), csr_read(pmpaddr1), csr_read(pmpcfg0));
    kprintf("[M] M-mode reads secret[0]=0x%x (unlocked entry: M bypasses PMP)\n", secret[0]);
    csr_write(mscratch, (uint32_t)&kstack[512]);                    /* U에서 트랩 → 이 스택 */
    csr_clear(mstatus, 3u << 11);                                   /* MPP = U(0) */
    csr_write(mepc, (uint32_t)user_main);
    __asm volatile("mv sp, %0; mret" :: "r"(&ustack[256]));         /* U-mode로 "떨어진다" */
    return 1;
}
```

```text
  [U] read shared OK
  [M] trap from U: mcause=5 (load access fault) mepc=0x800004d4 mtval=0x80002000
  [M] trap from U: mcause=2 (illegal instruction) mepc=0x800004dc mtval=0x300027f3
```

출력에서 볼 것:
- `pmpcfg0 = 0x00001f18` — entry 1 = 0x1F(NAPOT + RWX), entry 0 = 0x18(NAPOT, 권한 없음).
- M-mode는 `secret[0]=0xc0ffee`를 읽는다 — 잠기지 않은 entry는 M에 적용되지 않는다.
- `mret`(MPP=0)으로 U-mode에 내려가자 U는 UART를 직접 못 만지므로 ecall(a7=1)로 출력을 부탁한다. 커널 쪽 trap 진입은 mscratch의 커널 스택으로 갈아탄다(2.6).
- 보호 페이지 읽기 → **mcause 5, mtval = 0x80002000**(정확한 주소). Cortex-M의 MemManage + MMFAR와 같다.
- U에서 `csrr mstatus` → **mcause 2, mtval = 0x300027f3**(그 명령의 인코딩). 특권 위반이 별도 원인 코드가 아니라 illegal instruction으로 온다는 점이 Cortex-M(UsageFault/HardFault)과 다르다.
- L 비트를 켠 뒤 M-mode 읽기도 **trap from M, mcause 5**. 그리고 `pmpcfg0` 지우기 시도는 무시되어 `0x00001f98`이 그대로다.

### 5.3 RTOS 커널 안에서 — Zephyr의 PMP

FreeRTOS GCC/RISC-V 포트에는 MPU(PMP) 포트가 없다 — 태스크가 전부 M-mode다(7절). Zephyr는 `arch/riscv/core/pmp.c`에서 PMP를 쓴다.
- `CONFIG_RISCV_PMP=y`(qemu_riscv32 defconfig 기본값)면 커널이 PMP를 관리하고, `CONFIG_PMP_STACK_GUARD`로 스택 아래에 보호 영역을 둘 수 있다.
- userspace(`CONFIG_USERSPACE`)에서는 스레드 전환 때 `z_riscv_pmp_usermode_enable`로 그 스레드의 메모리 도메인을 PMP에 쓴다(`arch/riscv/core/switch.S`에서 호출). 즉 **PMP 재프로그래밍이 컨텍스트 스위치 비용에 들어간다** — 8절 측정의 "PMP 끈 빌드"가 더 빠른 이유 중 하나다.
- entry 수는 칩마다 다르다(Zephyr `CONFIG_PMP_SLOTS`, qemu_riscv32 빌드에서 16). Hazard3는 최대 16 영역(README).

### 5.4 Smepmp(ePMP) — M-mode도 믿지 않기

기본 PMP는 "M-mode는 다 믿는다"는 전제다. 보안 부팅 · TEE에서는 M-mode 코드 버그로 U-mode 메모리의 공격 코드를 실행하는 일을 막고 싶다. Smepmp(2021년 비준)는 `mseccfg` CSR을 추가한다.

| 비트 | 이름 | 효과 |
|---|---|---|
| MML | Machine Mode Lockdown | L 비트의 의미를 "M 전용 영역"으로 바꾼다. M-mode는 U용 영역(L=0)을 **실행할 수 없고**, 경우에 따라 읽기 · 쓰기도 못 한다 |
| MMWP | Machine Mode Whitelist Policy | M-mode도 기본 거부 — 어떤 entry에도 안 걸리면 fault |
| RLB | Rule Locking Bypass | 부트 중에는 잠긴 entry를 고칠 수 있게 (마지막에 끈다) |

Cortex-M33의 TrustZone + MPU 조합과 목표가 비슷하다(B7, L 모듈).

### 5.5 Cortex-M MPU와 비교

| 항목 | Cortex-M MPU (Armv7-M) | RISC-V PMP |
|---|---|---|
| 영역 수 | 8 또는 16 | 0~64 (구현) |
| 우선순위 | 높은 번호가 이긴다 | **낮은 번호가 이긴다** |
| 크기 · 정렬 | 2의 거듭제곱 + subregion (v8-M은 base/limit) | NAPOT(2의 거듭제곱) 또는 TOR(임의 경계, entry 2개 소비) |
| 특권 코드 | PRIVDEFENA로 기본 맵 허용 | M은 L 없으면 검사 안 함 |
| 위반 | MemManage(MMFAR) | access fault(mcause 1/5/7, mtval) |
| 메모리 속성 | 캐시 · 공유 속성 포함 | 없음 — 속성은 별도(PMA, 칩 고정) |

### 5.6 함정

- 금지 영역을 높은 번호에 두면 앞의 허용 영역이 이겨서 보호가 안 된다(MPU 습관 그대로 쓰면 틀린다).
- U-mode로 내려가기 전에 코드 · 스택 영역을 허용하지 않으면 `mret` 직후 첫 명령에서 instruction access fault(mcause 1)가 난다.
- PMP 변경 후에는 `sfence.vma`(S-mode가 있을 때)나 구현 문서가 요구하는 fence가 필요할 수 있다. MCU에서는 보통 즉시 반영되지만 확인한다.
- NAPOT 영역은 크기만큼 정렬되어 있어야 한다. 예제의 `aligned(4096)`이 없으면 base의 하위 비트가 크기 비트와 섞여 엉뚱한 영역이 된다.

## 6. A 확장 — LR/SC와 AMO

### 6.1 직관

Cortex-M3의 LDREX/STREX와 같은 개념이 LR/SC다. `lr.w`(load-reserved)가 주소를 "예약"하고, 그 사이 다른 hart가 같은 곳에 쓰면 예약이 깨져 `sc.w`(store-conditional)가 실패(rd ≠ 0)한다. 실패하면 처음부터 다시 한다. AMO(`amoadd.w`, `amoswap.w`, `amoor.w` …)는 "읽고-계산하고-쓰기"를 **한 명령**으로 원자적으로 한다 — Armv8.1-A의 LSE 원자 명령에 해당하고, Cortex-M에는 없다.

### 예제 6 — 두 hart가 공유 카운터를 10만 번씩

무엇을 확인하는 코드인가: `-smp 2`로 hart 2개를 띄워 같은 카운터를 올린다. 일반 `++`(lw → addi → sw), `amoadd.w`, LR/SC 루프를 비교하고 SC 실패 횟수를 센다. startup이 hart별 스택을 주고 hart 1은 `secondary_main`으로 간다(예제의 start.S).

```c
/* ex6 — A 확장: 2개 hart가 공유 카운터를 10만 번씩 올린다. 일반 ++ vs amoadd.w vs LR/SC 루프 */
#include "board.h"
#define N 100000
static volatile uint32_t c_plain, c_amo, c_lrsc, sc_fail[2], done, go;
static inline void amo_inc(volatile uint32_t *p) {
    __asm volatile("amoadd.w zero, %1, (%0)" :: "r"(p), "r"(1) : "memory");
}
static inline uint32_t lrsc_inc(volatile uint32_t *p) {     /* 리턴: SC 실패(재시도) 횟수 */
    uint32_t t, fail, retries = 0;
    __asm volatile("1: lr.w %0, (%3)\n"
                   "   addi %0, %0, 1\n"
                   "   sc.w %1, %0, (%3)\n"
                   "   beqz %1, 2f\n"
                   "   addi %2, %2, 1\n"
                   "   j 1b\n"
                   "2:" : "=&r"(t), "=&r"(fail), "+r"(retries) : "r"(p) : "memory");
    return retries;
}
static void work(uint32_t hart) {
    while (!go) { }
    for (int i = 0; i < N; i++) c_plain++;              /* lw → addi → sw: 원자 아님 */
    for (int i = 0; i < N; i++) amo_inc(&c_amo);
    for (int i = 0; i < N; i++) sc_fail[hart] += lrsc_inc(&c_lrsc);
    amo_inc(&done);
}
void secondary_main(uint32_t hart) { work(hart); for (;;) __asm volatile("wfi"); }
int main(void) {
    go = 1;
    work(0);
    while (done != 2) { }
    kprintf("expected %u\n", 2 * N);
    kprintf("plain ++  : %u (lost %u)\n", c_plain, 2 * N - c_plain);
    kprintf("amoadd.w  : %u\n", c_amo);
    kprintf("lr/sc loop: %u (sc retries hart0=%u hart1=%u)\n", c_lrsc, sc_fail[0], sc_fail[1]);
    return 0;
}
```

### 6.2 RTOS 커널 안에서

- **FreeRTOS RISC-V 포트(단일 코어)** 는 A 확장을 쓰지 않는다. 크리티컬 섹션 = `csrc mstatus, 8`(인터럽트 끄기) + `xCriticalNesting` 카운터다(`portmacro.h`의 `portENTER_CRITICAL`). A가 없는 ESP32-C3에서도 그대로 돈다.
- **Zephyr**의 `atomic_inc` 등은 A가 있으면 컴파일러 내장(`__atomic_*`)이 AMO로 바뀐다. SMP에서 `k_spinlock`은 원자 연산 + 인터럽트 끄기다(P 모듈).
- A가 없는 단일 코어에서 원자성이 필요하면 "인터럽트 끄고 읽고-쓰고 켜기"가 유일한 방법이다(Cortex-M0의 상황과 같다, B7).
- AMO는 메모리 순서 비트 `.aq`(acquire) · `.rl`(release)을 붙일 수 있다. 락 획득은 `amoswap.w.aq`, 해제는 `amoswap.w.rl` 또는 `fence rw,w` 다음 `sw`. 단일 hart MCU에서는 순서가 문제 되지 않지만, DMA · 다른 코어와 공유하는 메모리에서는 `fence`가 필요하다(Don이 아는 "DMA descriptor 쓰고 doorbell 전에 barrier"와 같은 규칙).

```c
/* ex8 — FreeRTOS V11.3.2 GCC/RISC-V 포트로 2-task 데모 (QEMU virt rv32, CLINT mtime tick) */
#include "FreeRTOS.h"
#include "task.h"
extern void freertos_risc_v_trap_handler(void);
static void blink(void *arg) {
    const char *name = arg;
    TickType_t period = name[0] == 'A' ? pdMS_TO_TICKS(100) : pdMS_TO_TICKS(250);
    TickType_t last = xTaskGetTickCount();
    for (int n = 0; n < (name[0] == 'A' ? 5 : 2); n++) {
        vTaskDelayUntil(&last, period);
        uint32_t ms;
        __asm volatile("csrr %0, mstatus" : "=r"(ms));
        kprintf("[%s] tick=%u mtime=%u us  mstatus.MIE=%u MPP=%u\n", name, (unsigned)xTaskGetTickCount(),
                (uint32_t)(mtime_read() / 10), (ms >> 3) & 1, (ms >> 11) & 3);
    }
    kprintf("[%s] stack high-water = %u words\n", name, (unsigned)uxTaskGetStackHighWaterMark(NULL));
    if (name[0] == 'B') board_exit(0);
    vTaskDelete(NULL);
}
int main(void) {
    csr_write(mtvec, (uint32_t)freertos_risc_v_trap_handler);     /* direct 모드, 모든 트랩 → 포트 */
    kprintf("mtvec=0x%08x  TCB-first SP frame = %u bytes (portCONTEXT_SIZE)\n",
            csr_read(mtvec), (unsigned)(31 * sizeof(StackType_t)));
    xTaskCreate(blink, "A", 512, "A", 2, NULL);
    xTaskCreate(blink, "B", 512, "B", 1, NULL);
    vTaskStartScheduler();
    return 1;
}
```

### 7.2 태스크 스택 프레임 — pxPortInitialiseStack이 만드는 것

`portASM.S`의 `pxPortInitialiseStack`이 새 태스크의 스택 꼭대기에 쌓는 31워드(124바이트, `portCONTEXT_SIZE`)다. TCB 첫 멤버 `pxTopOfStack`이 이 프레임의 맨 아래(word 0)를 가리킨다.

```
 high address  (pxTopOfStack before init)
 +-----------------------------+
 | word 30  xCriticalNesting=0 |   portCRITICAL_NESTING_OFFSET = 30
 | word 29  x31 (t6)           |
 |   ...    x11..x30           |
 | word  8  x10 (a0)=pvParams  |   task argument
 | word  7  x9  (s1)           |
 |   ...    x5..x8             |
 | word  2  x1 (ra) = xTaskReturnAddress  (prvTaskExitError)
 | word  1  mstatus = 0x1880   |   MPIE=1, MPP=M  (MIE=0 here)
 | word  0  mepc = pxCode      |   <- TCB->pxTopOfStack (SP)
 +-----------------------------+
 low address
 not stored: x0 (zero), x2 (sp: lives in TCB), x3 (gp), x4 (tp)
 + portasmADDITIONAL_CONTEXT_SIZE words between mstatus and mepc (chip specific)
```

Cortex-M3 포트(B4, C2)의 프레임은 "하드웨어 8워드 + 소프트웨어 r4–r11 8워드 = 16워드(64바이트) + EXC_RETURN"이다. RISC-V는 **두 배 가까운 124바이트를 전부 소프트웨어가** 쓰고 읽는다. 태스크 20개면 컨텍스트만 2.5 KB — 작은 MCU에서는 스택 산정(F3)에 바로 영향을 준다.

### 7.3 트랩 처리 흐름 — freertos_risc_v_trap_handler

포트 소스를 줄여서 읽으면 이렇다(실제 코드, 주석 일부 생략).

```asm
freertos_risc_v_trap_handler:
    portcontextSAVE_CONTEXT_INTERNAL      /* x1, x5..x31, critical nesting, mstatus 저장, TCB에 sp 기록 */
    csrr a0, mcause
    csrr a1, mepc
    bge a0, x0, synchronous_exception     /* bit31 = 0 → 동기 예외 */
asynchronous_interrupt:
    store_x a1, 0( sp )                   /* 인터럽트: mepc 그대로 */
    load_x sp, xISRStackTop               /* ISR 전용 스택으로 갈아탄다 */
    j handle_interrupt
synchronous_exception:
    addi a1, a1, 4                        /* ecall 다음 명령으로 */
    store_x a1, 0( sp )
    load_x sp, xISRStackTop
    j handle_exception
handle_interrupt:
    /* mcause == 0x80000007 (M timer)? */
    portUPDATE_MTIMER_COMPARE_REGISTER    /* mtimecmp += 1 tick (lo=-1, hi, lo 순서) */
    call xTaskIncrementTick
    beqz a0, processed_source             /* 깨울 태스크 없으면 스위치 안 함 */
    call vTaskSwitchContext
    j processed_source
handle_exception:
    li t0, 11                             /* 11 == environment call (M-mode ecall) */
    bne a0, t0, application_exception_handler
    call vTaskSwitchContext               /* portYIELD() = ecall 의 정체 */
    j processed_source
processed_source:
    portcontextRESTORE_CONTEXT            /* pxCurrentTCB의 sp → 레지스터 복원 → mret */
```

이 흐름에서 Cortex-M 포트와 달라지는 점:
- **PendSV가 없다.** Cortex-M은 "스위치가 필요하다"를 PendSV pending으로 미루고, 모든 ISR이 끝난 뒤 최저 우선순위에서 한 번 스위치한다(B4). RISC-V 포트는 **트랩 안에서 바로** `vTaskSwitchContext`를 부르고, 복원 단계에서 다른 태스크의 스택을 읽어 mret한다. 중첩 인터럽트가 없으니(3.4) "ISR 한가운데에서 스위치"라는 위험이 없어서 가능한 설계다.
- **`portYIELD()` = `ecall`.** 태스크의 yield도 트랩을 한 번 거친다(동기 예외 경로, mcause 11). Cortex-M의 `portYIELD`는 PendSV를 pend하는 레지스터 쓰기 한 번이다.
- **`portYIELD_FROM_ISR(x)`는 그냥 `vTaskSwitchContext()` 호출이다**(`portEND_SWITCHING_ISR`). 이미 트랩 안이고 복원이 공통 경로이기 때문이다. 대신 애플리케이션 ISR은 반드시 이 포트의 트랩 진입을 통해 불려야 한다 — 자기 `interrupt("machine")` 속성 ISR에서 FreeRTOS `FromISR` API를 부르고 스위치를 기대하면 안 된다.
- **장치 인터럽트는 사용자가 디스패치한다.** mtimer가 아닌 인터럽트는 weak 심볼 `freertos_risc_v_application_interrupt_handler`로 간다(기본 구현은 `j .`로 멈춤). PLIC claim/complete는 여기서 직접 한다 — 예제 7의 `trap_handler`가 그대로 이 자리에 들어간다.
- **ISR 스택이 따로 있다**(`xISRStackTop`). Cortex-M의 MSP에 해당하는 것을 소프트웨어로 만든 것이다.

### 7.4 첫 태스크 시작 — xPortStartFirstTask는 mret이 아니라 ret

`xPortStartScheduler`는 `vPortSetupTimerInterrupt()`로 첫 mtimecmp를 쓰고, `csrs mie, 0x880`(MTIE + MEIE)을 켠 다음 `xPortStartFirstTask`로 간다. 이 함수는 첫 태스크 프레임에서 레지스터를 읽되 **`mret`이 아니라 `ret`** 으로 태스크 함수에 들어간다 — 프레임의 mepc 값을 `x1`(ra)에 넣고 `ret`. 그래서 MPIE→MIE 복원이 일어나지 않으므로 코드가 직접 `addi x5, x5, 0x08`(MIE 세트) 후 `csrw mstatus, x5`를 한다(소스 주석: "Set MIE bit so the first task starts with interrupts enabled - required as returns with ret not eret"). Cortex-M의 첫 태스크 시작(SVC 0 → 예외 복귀, C3)과 비교하면 훨씬 단순하다 — 이미 M-mode이니 "특권을 내려가는 복귀"가 필요 없기 때문이다.

### 7.5 크리티컬 섹션 — BASEPRI가 없다

Cortex-M 포트의 핵심 설정 `configMAX_SYSCALL_INTERRUPT_PRIORITY`(B3)는 이 포트에 **없다**. `portENTER_CRITICAL()`은 `csrc mstatus, 8` — **모든** 인터럽트를 끈다. "커널을 안 부르는 초고속 ISR은 크리티컬 섹션 중에도 들어오게" 하는 Cortex-M의 기법을 쓸 수 없다는 뜻이다. 드론 FC의 모터 PWM 갱신 같은 ISR이 커널 크리티컬 섹션 길이만큼 지연된다. PLIC threshold로 흉내 낼 수는 있지만 포트가 해 주지 않는다. 이것이 RISC-V MCU에서 CLIC · 벤더 컨트롤러가 중요한 이유다.

### 7.6 FPU · 벡터 lazy 저장

`configENABLE_FPU=1`이면 저장 매크로가 `mstatus.FS`를 보고 **Dirty(3)일 때만** f0–f31 + fcsr(33워드)을 저장하고, 저장 후 FS를 Clean으로 바꾼다(`portContext.h`). 복원도 프레임의 mstatus.FS가 Dirty였을 때만. Cortex-M4F의 FPCCR lazy stacking(B6)을 하드웨어 대신 소프트웨어가 FS 비트로 하는 것이다. 벡터(`configENABLE_VPU`)도 같은 방식으로 `mstatus.VS`를 본다.

## 8. Zephyr qemu_riscv32 그리고 컨텍스트 스위치 비용

### 8.1 Zephyr RISC-V는 저장을 둘로 나눈다

Zephyr RISC-V는 `CONFIG_USE_SWITCH=y`(arch_switch 방식)다. 트랩 진입(`arch/riscv/core/isr.S`의 `_isr_wrapper`)은 **caller-saved 16개**(ra, t0–t6, a0–a7)와 mepc · mstatus · s0만 `struct arch_esf`(80바이트, 예제 10 출력)에 저장한다 — C 함수를 부르기에 딱 충분한 만큼, 즉 Cortex-M 하드웨어 프레임의 소프트웨어판이다. 스레드를 실제로 바꿀 때만 `z_riscv_switch`(`arch/riscv/core/switch.S`)가 `DO_CALLEE_SAVED`로 s0–s11 + ra + sp(`_callee_saved_t`, 56바이트)를 **TCB(`struct k_thread`) 안에** 저장한다. 그리고 `k_yield()` 같은 협력적 전환은 트랩을 거치지 않고 `arch_switch()` → `z_riscv_switch`로 **함수 호출처럼** 바꾼다(`CONFIG_RISCV_ALWAYS_SWITCH_THROUGH_ECALL`을 켜면 ecall로 강제).

| 항목 | FreeRTOS RISC-V | Zephyr RISC-V |
|---|---|---|
| 트랩 진입 저장 | 31워드 전부 (태스크 스택) | 16 + 4워드 (esf, 현재 스택) |
| 스위치 때 추가 저장 | 없음 (이미 다 저장) | callee-saved 14워드 → TCB |
| 협력적 yield | `ecall` → 트랩 | 함수 호출 `z_riscv_switch` |
| 지연된 스위치 | 트랩 안에서 즉시 | ISR 끝(`no_reschedule` 전)에 `z_get_next_switch_handle` |
| 중첩 인터럽트 | 지원 안 함 | CLIC level 지원(`CONFIG_RISCV_HAS_CLIC`) |
| 하드웨어 스태킹 SoC | 없음 | `CONFIG_RISCV_SOC_HAS_ISR_STACKING`(nRF54 VPR) |
| U-mode 스레드 | 없음 | `CONFIG_USERSPACE` + PMP |

### 예제 9 — FreeRTOS yield 비용: rv32 vs Cortex-M3 (같은 소스)

무엇을 확인하는 코드인가: 같은 우선순위 두 태스크가 `taskYIELD()`를 1만 번씩 주고받는다. rv32는 `minstret`, M3는 FPGAIO 카운터 × 40/32로 명령 수를 잰다. M3 쪽은 템플릿 설정에서 run-time stats · trace를 끈 `FreeRTOSConfig.h`(m3/ 폴더)를 써서 두 설정을 맞췄다(stats를 켜 둔 첫 측정은 M3가 100명령으로 나왔다 — `vTaskSwitchContext` 안의 `board_now_us()` 호출 때문).

```c
/* ex9 — 같은 소스로 FreeRTOS taskYIELD() 컨텍스트 스위치 비용: rv32(virt) vs Cortex-M3(mps2).
 * rv32: minstret(정확한 명령 수) · M3: ICOUNT 가상시간(32 ns/명령)을 25 MHz FPGAIO 카운터로 환산 */
#include "FreeRTOS.h"
#include "task.h"
#ifdef __riscv
#define PRINT kprintf
static inline uint32_t instr_now(void) { uint32_t v; __asm volatile("csrr %0, minstret" : "=r"(v)); return v; }
extern void freertos_risc_v_trap_handler(void);
#else
#include "board.h"
#define PRINT board_printf_raw
static inline uint32_t instr_now(void) { return REG32(0x40028018u) * 5u / 4u; }  /* 40ns/32ns */
#endif
#define N 10000
static volatile uint32_t t_start, t_end, done;
static void pinger(void *arg) {
    if (arg) t_start = instr_now();
    for (int i = 0; i < N; i++) taskYIELD();     /* 같은 우선순위 상대에게 CPU를 넘긴다 */
    if (++done == 2) {
        t_end = instr_now();
        uint32_t per = (t_end - t_start) / (2 * N);
        PRINT("%s: %u yields in %u instr -> %u instr per switch\n",
#ifdef __riscv
              "rv32 (GCC/RISC-V port)",
#else
              "Cortex-M3 (GCC/ARM_CM3 port)",
#endif
              2 * N, t_end - t_start, per);
        board_exit(0);
    }
    vTaskDelete(NULL);
}
int main(void) {
#ifdef __riscv
    __asm volatile("csrw mtvec, %0" :: "r"(freertos_risc_v_trap_handler));
#endif
    xTaskCreate(pinger, "P1", 256, (void *)1, 1, NULL);
    xTaskCreate(pinger, "P2", 256, NULL, 1, NULL);
    vTaskStartScheduler();
    return 1;
}
```

### 예제 10 — Zephyr v4.4.2: qemu_riscv32 2-thread와 mps2/an385 비교

무엇을 확인하는 코드인가: Zephyr에서 같은 우선순위 두 스레드의 `k_yield()` 핑퐁. rv32(qemu_riscv32)는 `rtos-zrun`(보드 기본 `-icount shift=6`)에서 `minstret`으로, M3(mps2/an385)는 `rtos-run-mps2` ICOUNT=1에서 FPGAIO로 잰다. 그리고 `CONFIG_TIMESLICING`과 PMP · 스택 sentinel을 끈 빌드로 비용을 분해한다.

```c
/* ex10 — Zephyr v4.4.2 qemu_riscv32: 2개 스레드 + k_yield() 핑퐁의 스위치당 명령 수(minstret) */
#include <zephyr/kernel.h>
#ifdef CONFIG_RISCV
#include <zephyr/arch/riscv/csr.h>
#define INSTR() ((uint32_t)csr_read(minstret))            /* icount 아래에서 정확한 명령 수 */
#else
#define INSTR() (sys_read32(0x40028018) * 5u / 4u)        /* M3: FPGAIO 25 MHz, icount shift=5 가정 */
#endif
#define N 10000
static volatile uint32_t t0, done;
static void pinger(void *p1, void *p2, void *p3)
{
	ARG_UNUSED(p2); ARG_UNUSED(p3);
	if (p1) t0 = INSTR();
	for (int i = 0; i < N; i++) k_yield();
	if (++done == 2) {
		uint32_t d = INSTR() - t0;
		printk("zephyr %s: %u yields in %u instr -> %u instr per switch\n", CONFIG_BOARD, 2 * N, d, d / (2 * N));
	}
}
K_THREAD_DEFINE(ping1, 1024, pinger, (void *)1, NULL, NULL, 5, 0, 50);
K_THREAD_DEFINE(ping2, 1024, pinger, NULL, NULL, NULL, 5, 0, 50);
int main(void)
{
#ifdef CONFIG_RISCV
	printk("board=%s  mtvec=0x%08lx  mstatus.MPP=%lu  sys clock=%u Hz\n", CONFIG_BOARD,
	       csr_read(mtvec), (csr_read(mstatus) >> 11) & 3, sys_clock_hw_cycles_per_sec());
#endif
	printk("sizeof(struct arch_esf)=%u  sizeof(_callee_saved_t)=%u\n",
	       (unsigned)sizeof(struct arch_esf), (unsigned)sizeof(_callee_saved_t));
	for (int i = 0; i < 3; i++) {
		k_msleep(100);
		printk("main: uptime=%lld ms\n", k_uptime_get());
	}
	k_msleep(200);
	return 0;
}
```

- `sizeof(struct arch_esf)` = rv32 80 / M3 32(하드웨어 프레임 8워드), `_callee_saved_t` = rv32 56 / M3 36(r4–r11 + psp).

### 예제 11 — 트랩 · 스위치 코드의 정적 크기 (objdump)

무엇을 확인하는 코드인가: 위 숫자가 어디서 오는지, 각 포트의 진입 · 스위치 코드를 명령 수로 센다.

```sh
#!/bin/bash
# ex11 — 트랩/스위치 코드의 정적 명령 수를 objdump로 센다 (RISC-V vs Cortex-M3)
OD=/var/rtoslab/zephyr-sdk-1.0.1/gnu/riscv64-zephyr-elf/bin/riscv64-zephyr-elf-objdump
O=/var/tmp/rtos/B10
fn() {  # fn <objdump> <elf> <symbol> : 그 심볼부터 다음 심볼 전까지 명령 수
  $1 -d --no-show-raw-insn $2 | awk -v s="<$3>:" '$0~s{f=1;next} f&&/^[0-9a-f]+ </{exit} f&&/^ *[0-9a-f]+:\t[a-z]/{n++} END{print n}'; }
```

## 11. 실무에서 다시 보기

**장면 1 — 드론 FC를 ESP32-C6로 옮길 때.** 기존 STM32H7 코드의 IMU ISR은 `configMAX_SYSCALL_INTERRUPT_PRIORITY`보다 높은 우선순위로 두어 커널 크리티컬 섹션과 무관하게 들어오게 했다. RISC-V 포트에서는 그 개념이 없으므로(7.5) 크리티컬 섹션 최대 길이를 재고(E3), ISR 지연 예산에 더해야 한다. 그리고 tick ISR이 `configCPU_CLOCK_HZ`를 mtime 주파수로 쓰는지 먼저 확인한다(ESP-IDF는 자체 포트를 쓰므로 그 문서를 따른다).

**장면 2 — RP2350에서 Arm/RISC-V를 비교해 보기.** 같은 보드에서 같은 펌웨어를 Cortex-M33 빌드와 Hazard3 빌드로 돌려 ISR 지연 · 스위치 비용을 실측할 수 있다. 이 노트의 icount 숫자(명령 수)를 실칩 사이클로 다시 재는 좋은 연습이다(14절 연습 6).

**장면 3 — 로봇 관절 컨트롤러의 20 kHz 전류 루프.** 50 µs마다 오는 ISR이 1회 120명령 진입 비용이면 100 MHz 코어에서 1.2 µs(2.4%) — 허용 가능하지만, 크리티컬 섹션 동안 막혀 지연이 커지는 것이 더 위험하다. CLIC/ECLIC 칩이라면 전류 루프 ISR을 높은 level에 두어 하드웨어 선점을 쓰고, 커널 API는 부르지 않는다(ISR → 태스크 알림은 낮은 level ISR이나 소프트웨어 인터럽트로 한 단계 거친다).

**장면 4 — SSD 컨트롤러/AI SoC의 RISC-V 관리 코어.** 요즘 SoC의 부트 · 전원 · 보안 관리 코어는 RISC-V인 경우가 많다(Rivian · Hark 같은 SoC 팀 JD에서 RISC-V가 보이는 이유). 이런 코어는 보통 PLIC + CLINT 또는 AIA를 쓰고, 펌웨어는 PMP L 비트로 자기 ROM을 잠근다. 예제 5의 lock 실험이 그대로 부트 ROM 보호 코드다.

## 13. 면접에서 이렇게 말한다

**Q.** What changes when you port an RTOS from Cortex-M to RISC-V?

**A.** 핵심은 "하드웨어가 해 주던 일을 소프트웨어가 한다"는 것이다. 트랩 때 레지스터를 하나도 안 밀어 주므로 진입 어셈블리를 새로 쓰고, PendSV가 없으니 스위치를 트랩 안이나 ecall로 하고, SysTick 대신 CLINT mtimecmp를 매 tick 다시 쓰고, NVIC 대신 PLIC/CLIC 드라이버를 쓴다. BASEPRI가 없어 크리티컬 섹션이 모든 인터럽트를 막는다는 것도 큰 차이다.

> Three things move from hardware to software. First, trap entry: standard RISC-V saves nothing but mepc, mcause and mstatus, so the port writes the register save and restore — FreeRTOS saves all 31 registers, Zephyr splits caller-saved on entry and callee-saved on switch. Second, there is no PendSV, so FreeRTOS switches directly inside the trap and yields with ecall. Third, timing and interrupts are platform blocks: the tick is CLINT mtimecmp, which has no auto-reload, and external interrupts go through a PLIC with claim and complete, or a CLIC on MCU-class parts. And since there's no BASEPRI, a FreeRTOS critical section masks every interrupt.

**꼬리 질문**: "How much more expensive is it?" → 이 노트의 숫자: 인터럽트 1회 18 vs 48~120명령, yield 76 vs 156명령(QEMU icount, 명령 수 기준; Cortex-M 스태킹 사이클은 제외).

**Q.** Walk me through what the hardware does on a RISC-V machine-mode trap, and what mret does.

**A.** mepc에 PC, mcause에 원인, mtval에 부가 정보, MPIE ← MIE · MIE ← 0, MPP ← 이전 모드, PC ← mtvec. mret은 그 역: PC ← mepc, MIE ← MPIE, 모드 ← MPP, MPP ← 최저 모드.

> On a trap the hart writes the PC into mepc, the cause into mcause with bit 31 set for interrupts, extra information like the faulting address into mtval, copies MIE into MPIE and clears MIE, records the previous privilege in MPP, and jumps to mtvec — base, or base plus four times the cause in vectored mode for interrupts. No general-purpose registers and no stack switch. mret reverses it: PC from mepc, MIE from MPIE, privilege from MPP, and MPP is reset to the lowest supported mode. For synchronous exceptions like ecall, mepc points at the instruction itself, so the handler must add four or it traps forever.

**Q.** Compare CLINT/PLIC with NVIC. What about CLIC?

**A.** CLINT은 타이머 · 소프트웨어 인터럽트, PLIC은 장치 인터럽트를 모아 MEIP 한 줄로 보낸다. 우선순위는 있지만 하드웨어 선점 · 번호별 벡터가 없고 claim/complete가 필요하다. CLIC은 NVIC처럼 번호별 level · priority · 벡터를 주지만 표준은 아직 비준 전이라 실제로는 ECLIC · PFIC 같은 벤더 구현을 쓴다.

> NVIC is one block that gives per-interrupt priority, hardware preemption, a vector per IRQ and automatic stacking. On a standard RISC-V core there are only three interrupt inputs. CLINT drives the timer and software interrupts, and the PLIC aggregates device interrupts with priority, enable and threshold into a single external-interrupt line; the handler claims the ID and must write complete, and nesting has to be done in software. CLIC is the MCU-oriented design closest to NVIC — per-interrupt levels, hardware preemption and selective vectoring — but as of my last check the standard is still a stable draft, not ratified, so real chips use vendor versions like Nuclei ECLIC, WCH PFIC or the Hazard3 controller on RP2350.

**꼬리 질문**: "What happens if you forget the PLIC complete?" → 첫 한 번만 들어오고 그 소스는 다시 안 들어온다(예제 7).

**Q.** How does the FreeRTOS RISC-V port do a context switch?

**A.** 모든 트랩이 `freertos_risc_v_trap_handler`로 온다. 31워드를 현재 태스크 스택에 저장하고 SP를 TCB에 쓴 뒤 ISR 스택으로 갈아탄다. 타이머면 mtimecmp 갱신 + `xTaskIncrementTick`, ecall(mcause 11)이면 바로 `vTaskSwitchContext`. 끝에서 `pxCurrentTCB`의 스택을 복원하고 mret — 그 사이 pxCurrentTCB가 바뀌었으면 다른 태스크로 돌아간다.

> Every trap enters freertos_risc_v_trap_handler. It saves x1 and x5 to x31, the critical nesting count and mstatus on the current task's stack, stores sp into the first word of the TCB, and switches to a dedicated ISR stack. If mcause is the machine timer it rewrites mtimecmp and calls xTaskIncrementTick; if it's an M-mode ecall — which is what portYIELD expands to — it calls vTaskSwitchContext directly. The exit path loads sp from whatever pxCurrentTCB now points to, restores registers, writes mepc and mstatus and executes mret. There's no PendSV; it's safe because the port doesn't nest interrupts.

**Q.** What is PMP and how is it different from an Arm MPU?

**A.** 주소 범위별 R/W/X 표. 낮은 번호가 이기고, U는 기본 거부, M은 L 비트가 없으면 검사를 안 받는다. NAPOT · TOR 인코딩, 위반은 access fault + mtval. 캐시 속성은 없다.

> PMP is a table of up to 64 entries, each a TOR or naturally aligned power-of-two region with read, write and execute bits. The lowest-numbered matching entry wins — the opposite of the Armv7-M MPU — user mode is denied by default when nothing matches, and machine mode is only checked against entries with the lock bit, which also makes the entry immutable until reset. Violations are access faults, cause 1, 5 or 7, with the address in mtval. Unlike the MPU it carries no cacheability attributes; Smepmp adds mseccfg so machine mode can be restricted as well.

**Q.** LR/SC versus AMO — when would you use each?

**A.** AMO는 더하기 · 스왑 · 비트 연산을 한 명령으로 — 카운터 · 플래그 · 간단한 락. LR/SC는 임의의 read-modify-write(비교 후 교환, 리스트 삽입)에. 단일 코어 RTOS는 둘 다 안 쓰고 인터럽트를 끄기도 한다.

> AMOs do a single read-modify-write — add, swap, and, or, min, max — in one instruction, so they're ideal for counters, flags and simple spinlocks with aq and rl ordering bits. LR/SC is the general mechanism: load-reserved, compute anything, store-conditional, retry on failure, which is how you build compare-and-swap. In my two-hart test a plain increment lost up to ninety-nine thousand of two hundred thousand updates while both atomic forms were exact — but the same test under single-threaded icount showed no race at all, which is a good reminder to test concurrency on real parallel execution.

**Q.** Why is a Zephyr k_yield on RISC-V sometimes eight times more expensive than you'd expect?

**A.** 타임 슬라이싱이 켜져 있으면 스위치마다 슬라이스 타이머를 다시 설정한다 — 측정상 815 → 106명령. 레지스터 저장보다 커널 설정이 더 컸다.

> I measured it. With CONFIG_TIMESLICING on, each switch calls z_reset_time_slice, which reprograms the tickless machine timer — reading mtime and writing a 64-bit mtimecmp — and that took a yield from about 106 instructions to 815 on qemu_riscv32, and 78 to 448 on a Cortex-M3. The architectural difference, split caller and callee saves versus hardware stacking, was only about 30 percent once timeslicing was off. So before blaming the ISA, profile the kernel configuration.

**Q.** Which RISC-V features would you check first when choosing an MCU for a flight controller?

**A.** 인터럽트 컨트롤러가 하드웨어 선점을 하는지(CLIC 계열인지 PLIC인지), A 확장 · FPU · Zbb, 코어 수와 원자 연산, 그리고 쓸 RTOS 포트의 성숙도.

> First the interrupt controller, because a high-rate IMU or motor ISR needs hardware preemption and low latency — a CLIC-style controller like ECLIC, PFIC or Hazard3's, or vendor hardware stacking, rather than a bare PLIC. Then the ISA string: F for the control math, A if there's more than one core, Zbb and Zcmp for cheaper context switches. And finally the software: whether FreeRTOS or Zephyr already has a maintained port for that interrupt controller, because writing trap entry and nesting yourself is where the bugs live.

## 14. 직접 해보기

1. (개념) mcause = 0x8000000B와 mcause = 0x0000000B는 각각 무엇이고, 핸들러에서 mepc를 어떻게 다뤄야 하나? 정답/힌트: 앞은 M 외부 인터럽트(mepc 그대로), 뒤는 M-mode ecall(mepc += 4). bit 31을 먼저 본다.
2. (계산) 0x80010000에서 시작하는 64 KB 영역의 NAPOT `pmpaddr` 값과, entry 2에 R/X만 주고 잠그는 `pmpcfg0`의 바이트 값을 구하라. 정답/힌트: `(0x80010000 >> 2) | (65536/8 − 1) = 0x20004000 | 0x1FFF = 0x20005FFF`, cfg 바이트 = L(0x80) + NAPOT(0x18) + X(0x04) + R(0x01) = 0x9D → `pmpcfg0`의 bits 23:16.
3. (코드) 예제 3의 (B)를 고쳐 트랩 진입에서 caller-saved 16개만 저장하는 `trap_entry_fast`를 만들고 extra instr/IRQ를 다시 재라. 48과 120 사이 어디쯤이 나오나? 정답/힌트: s0–s11은 C 함수가 스스로 보존하므로 저장하지 않아도 된다(Zephyr `_isr_wrapper`와 같은 생각). 측정 전에 objdump로 명령 수를 예상해 보라.
4. (코드) 예제 7을 바꿔 PLIC 위에서 중첩을 구현하라: UART ISR 안에서 threshold를 올리고 MIE를 다시 켠 뒤, msip(소프트웨어 인터럽트)를 걸어 끼어드는지 확인한다. 정답/힌트: mepc · mstatus를 C 지역 변수에 저장하고 `csrs mstatus, 8`, 끝나면 `csrc` 후 되돌린다. 3.4절 4단계.
5. (측정) 예제 9를 `configUSE_PORT_OPTIMISED_TASK_SELECTION=0`으로 빌드해 rv32 yield 비용이 어떻게 바뀌나 재라. Zbb 유무와 비교하라. 정답/힌트: generic 선택은 우선순위 리스트를 위에서부터 훑는다 — 우선순위 수(8)에 비례하는 비용. `EXTRA_CFLAGS=-DconfigUSE_PORT_OPTIMISED_TASK_SELECTION=0`.
6. (측정) Zephyr 예제 10에 `-DCONFIG_RISCV_ALWAYS_SWITCH_THROUGH_ECALL=y`를 더해 yield가 트랩을 거치게 하고 비용을 재라. FreeRTOS(ecall 방식)와 가까워지나? 정답/힌트: 협력적 스위치도 `_isr_wrapper`의 esf 저장을 거치게 된다. timeslicing은 끈 빌드끼리 비교한다.
7. (조사) 갖고 있거나 관심 있는 RISC-V MCU 하나(예: RP2350, CH32V307)의 데이터시트에서 ISA 문자열 · 인터럽트 컨트롤러 · mtime 주파수 · PMP 영역 수를 찾아 9절 표에 한 줄을 채워라. 정답/힌트: Zephyr DTS(`dts/riscv/<vendor>/`)와 벤더 데이터시트를 함께 본다. 두 출처가 다르면 데이터시트가 우선.

| HPE | Hardware Prologue/Epilogue | WCH QingKe의 하드웨어 레지스터 저장 기능 |

| icount | QEMU instruction counting | 명령 1개 = 고정 가상 시간. 결정적 측정의 기반 |

## 16. 요약 & 체크리스트

표준 RISC-V는 트랩 때 mepc · mcause · mtval · mstatus만 바꾸고 레지스터는 하나도 저장하지 않는다. 그래서 RTOS 포트는 진입 어셈블리(FreeRTOS는 31워드 전부, Zephyr는 caller-saved 16개 + 스위치 때 callee-saved)를 직접 쓰고, PendSV 없이 트랩 안에서 바로 스위치하며(FreeRTOS `portYIELD` = `ecall`), SysTick 대신 자동 reload가 없는 CLINT mtimecmp를 매 tick 다시 쓴다. 장치 인터럽트는 PLIC(claim/complete, 하드웨어 선점 없음)이나 CLIC 계열(아직 비준 전, 벤더 구현)로 오고, BASEPRI가 없어 FreeRTOS 크리티컬 섹션은 모든 인터럽트를 막는다. 보호는 PMP(낮은 번호 우선, U 기본 거부, L 비트), 원자성은 LR/SC · AMO. QEMU icount로 잰 비용은 인터럽트 1회 18(M3) vs 48~120(rv32)명령, yield 76 vs 141~156명령(FreeRTOS)이었고, Zephyr에서는 아키텍처보다 timeslicing 설정(815 → 106)이 더 큰 변수였다.

- [ ] M/S/U 모드와 MCU가 쓰는 조합(M, M+U)을 Cortex-M 모드와 대응시켜 말할 수 있다
- [ ] 트랩 진입 5단계와 mret 4단계를 mstatus 비트 이름으로 말할 수 있다
- [ ] mcause 0x80000007 / 0x8000000B / 2 / 5 / 8 / 11의 뜻과 mepc 처리 규칙을 안다
- [ ] mscratch로 커널 스택을 고르는 진입 코드를 손으로 쓸 수 있다
- [ ] CLINT mtimecmp를 RV32에서 안전한 순서로 쓰고, 자동 reload가 없다는 것을 안다
- [ ] PLIC priority · threshold · claim · complete를 쓰고, complete를 빼먹었을 때의 증상을 안다
- [ ] CLIC의 비준 상태(2026-10: v0.20, ACLIC Stable)와 벤더 구현 예 세 개를 말할 수 있다
- [ ] PMP NAPOT 값을 계산하고, 낮은 번호 우선 · L 비트 · U 기본 거부를 설명할 수 있다
- [ ] LR/SC와 AMO의 차이, 단일 코어 RTOS가 A 없이도 도는 이유를 안다
- [ ] FreeRTOS RISC-V 포트의 `configMTIME_BASE_ADDRESS` · `configMTIMECMP_BASE_ADDRESS` · `configISR_STACK_SIZE_WORDS` · chip-specific extensions 헤더를 설정할 수 있다
- [ ] `freertos_risc_v_trap_handler`와 `xPortStartFirstTask`(ret으로 시작)의 흐름을 설명할 수 있다
- [ ] "Cortex-M → RISC-V 포팅에서 달라지는 것"을 측정 숫자와 함께 1분 안에 말할 수 있다

## Bare-Metal 노트와의 관계

| BM ID | BM 주제 | 이 노트의 해당 절 | Bare-Metal 쪽에 남길 내용 |
|---|---|---|---|
| BM E1 | ISA와 확장 (RV32I/E, M·A·F·D·C, Zicsr, Zb 계열, Zc 계열, V, P, 프로파일) | 1절(RTOS 관점 확장 표, misa, 프로파일), 9절(칩별 ISA) | 명령 인코딩 · 어셈블리 작성 실습은 Hark E3 링크, 칩 데이터시트에서 ISA 문자열을 읽어 `-march`/multilib을 고르는 절차 |
| BM E2 | 특권 아키텍처 (M/S/U, mstatus, mtvec, mcause, mepc, mtval, mie/mip, mret) | 2절(CSR 표, 트랩 흐름 그림, trap.S, 예제 2) | 디버거(OpenOCD/GDB)로 CSR을 보는 방법, `ebreak`와 디버그 모드 |
| BM E3 | 인터럽트 컨트롤러 (CLINT, PLIC, CLIC, AIA) | 3절(예제 3 · 7, CLIC 상태, NVIC 비교), 4절(비용) | 실칩 ECLIC/PFIC 레지스터 설정 순서, 인터럽트 지연을 GPIO + 스코프로 재기 |
| BM E4 | PMP / ePMP (TOR/NAPOT, lock, Smepmp) | 5절(예제 5, Smepmp, MPU 비교) | 부트 ROM · 보안 부트에서 PMP 잠금 순서, RLB 사용 시점 |
| BM E5 | RISC-V startup (`_start`, gp, crt0) | 1.3절(최소 start.S · link.ld만) | **주인은 Bare-Metal**: gp relaxation 상세, `.data` 복사가 있는 XIP 플래시 startup, crt0 · picolibc 연동 |
