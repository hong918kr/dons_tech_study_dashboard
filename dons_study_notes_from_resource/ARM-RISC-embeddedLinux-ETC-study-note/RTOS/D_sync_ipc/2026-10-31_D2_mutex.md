# D2. 뮤텍스 — 열쇠 하나와 주인 이름표: 소유권 · 재귀 · 타임아웃 · ISR 금지 · 크리티컬 섹션과 고르기

> **이 노트를 다 읽으면**: 뮤텍스의 소유권 규칙을 FreeRTOS와 Zephyr에서 직접 깨 보고 각 커널이 어떻게 반응하는지(assert, `-EPERM`, 아무 일 없음) 말할 수 있다 · 재귀 뮤텍스가 정당한 경우와 설계 냄새를 구분하고 타임아웃 에러 경로를 설계할 수 있다 · ISR에서 뮤텍스가 금지인 세 가지 이유를 커널 소스 줄 번호로 보여 줄 수 있다 · 뮤텍스, 크리티컬 섹션, 스케줄러 잠금 중 무엇을 쓸지 측정 숫자(비용과 "누가 기다리나")로 고를 수 있다
> **왜 필요한가**: 면접에서는 "mutex vs semaphore" 다음에 거의 반드시 "그럼 mutex vs critical section은? ISR에서 mutex를 쓰면?"이 나온다. 실무에서는 드론 FC의 I2C 버스 하나를 IMU · 기압계 · 자력계가 나눠 쓰고, 그 버스 뮤텍스를 잘못 잡은 한 줄이 1 kHz 제어 루프를 1 ms씩 밀어낸다
> **Don 기준 난이도**: 공유 자원 중재(SSD의 NAND 채널 arbitration), 인터럽트 끄기는 이미 안다 / 새로 배울 부분은 "주인"이라는 개념이 커널 안에서 어떤 필드로 존재하는지(`xMutexHolder`, `owner`), 소유권 검사가 **어디서** 일어나는지(FreeRTOS는 API가 아니라 assert 하나), 경합 시 비용(수십 µs)과 그 비용을 **누가** 내는지
> **선행 노트**: A5(API 로제타 — 재귀 기본값 비교), C1(커널 자료구조 — 리스트), C7(크리티컬 섹션 · 스케줄러 잠금 구현과 L 스윕), D1(세마포어), EL A8(pthread mutex 타입 · futex), EL F4(Linux `struct mutex`). 이어지는 노트: D3(우선순위 역전 · PIP · PCP), D7(게이트키퍼 태스크), D9(데드락 · 락 순서)

## 0. 큰 그림 — 이게 왜 필요한가

펌웨어에는 "한 번에 한 명만 써야 하는 것"이 생각보다 많다. 드론 비행 제어기라면 IMU와 기압계가 같은 I2C 버스에 붙어 있고, 텔레메트리와 디버그 로그가 같은 UART로 나가고, 블랙박스 로거와 파라미터 저장이 같은 SPI 플래시를 쓴다. 이 자원을 만지는 코드가 **태스크** 여러 개에 흩어져 있고, 한 번 만지는 시간이 수백 µs ~ 수 ms라서 그동안 인터럽트를 꺼 둘 수도 없다. 이럴 때 쓰는 도구가 **뮤텍스(mutex, mutual exclusion)**다.

직관은 이렇다. **뮤텍스 = 열쇠 하나 + 주인 이름표.** 열쇠를 가져간 태스크의 이름이 열쇠에 붙는다. 열쇠를 돌려줄 수 있는 것은 이름표의 주인뿐이다. 열쇠가 없어서 못 들어가는 태스크는 문 앞에서 **잠든다**(CPU를 다른 태스크에게 넘긴다). 그리고 이름표가 있으니 커널은 "지금 낮은 우선순위의 누군가가 열쇠를 쥐고 높은 우선순위가 기다린다"는 사실을 알 수 있고, 주인의 우선순위를 잠시 올려 준다(우선순위 상속, D3).

그림 1 — 뮤텍스의 직관. 열쇠(잠금)에 주인 이름표(owner)가 붙는다는 점이 세마포어(D1)와 다른 전부다. 이름표가 있어서 "주인만 푼다", "주인을 올려 준다"가 가능하고, 이름표를 달 수 없는 ISR은 뮤텍스를 쓸 수 없다.

**Don 경험과 연결**: SSD 컨트롤러에서 NAND 채널 하나에 다이(die) 여러 개가 붙어 있고, 여러 FTL 작업(호스트 읽기, GC, 웨어 레벨링)이 그 채널을 원한다. 채널 arbiter가 한 명령 시퀀스에게 채널을 주면, 그 시퀀스가 끝날 때까지(예: 명령 → 주소 → tR 대기 → 데이터 전송) 다른 시퀀스는 끼어들 수 없고, 채널을 반납하는 것도 그 시퀀스 자신이다. 이것이 정확히 뮤텍스다. 다른 점은 하나다. SSD 펌웨어에서는 tR(수십 µs) 동안 채널을 쥐고 **다른 다이의 명령을 끼워 넣는**(interleaving) 최적화를 직접 짰을 것이다. RTOS 뮤텍스로 옮기면 그 최적화는 "tR 대기 동안 뮤텍스를 놓는다"(§8.1의 좋은 설계)가 된다.

### 0.1 이 노트의 지도와 경계

| 절 | 내용 | 경계 (다른 노트가 주인) |
|---|---|---|
| §1 소유권 | 누가 풀 수 있나, 어기면 FreeRTOS · Zephyr가 어떻게 반응하나 | 세마포어와의 차이 자체는 D1 |
| §2 재귀 뮤텍스 | 카운터, 정당한 경우 vs 설계 냄새, API 섞기 버그 | 각 RTOS 기본값 비교표는 A5 §3.7 |
| §3 타임아웃 | 예산 정하기, 에러 경로, `portMAX_DELAY`의 위험 | 데드락 탐지는 D9 |
| §4 ISR 금지 | 세 가지 이유, 커널이 잡는 곳 | ISR → 태스크 위임은 D7, FromISR 규칙은 E1 |
| §5 고르기 | 뮤텍스 vs 크리티컬 섹션 vs 스케줄러 잠금: 비용과 "누가 기다리나" | 크리티컬 섹션 구현과 길이 L 스윕은 C7 |
| §6 상속 맛보기 | 한 문단 + 측정 한 줄 | 역전 · PIP · PCP 분석은 **D3** |
| §7 커널 안 | `Queue_t` 안의 뮤텍스, `struct k_mutex`, 넘겨주기 방식 차이 | 리스트 구조는 C1 |
| §8 실무 | I2C 버스, UART 로거, SPI 플래시, SSD 채널 | 게이트키퍼 구현은 D7 |

Linux 쪽은 이미 공부했다. pthread mutex의 normal / errorcheck / recursive 타입과 futex는 EL A8 §2 · §8, 커널 `struct mutex`의 세 단계 경로(fast path, optimistic spinning, slow path)는 EL F4 §5에 있다. 이 노트는 그 개념을 다시 설명하지 않고 **MCU RTOS에서 달라지는 점**만 쓴다. 가장 큰 차이 세 가지를 먼저 적어 둔다.

| 항목 | Linux (EL A8 / F4) | MCU RTOS (이 노트) |
|---|---|---|
| 소유자 검사 | errorcheck 타입이면 `EPERM`, 커널은 디버그 옵션 | FreeRTOS: API에는 없고 **assert 하나**뿐. Zephyr: `-EPERM`을 돌려주지만 Kconfig로 사라진다 |
| 우선순위 상속 | 기본 꺼짐 (`PTHREAD_PRIO_INHERIT`로 켬) | FreeRTOS · Zephyr 뮤텍스는 **항상 켜짐** |
| 경합 시 대기 | futex로 커널 진입, SMP에서는 spin 먼저 | 단일 코어라 spin 의미 없음 → 바로 블록 + 컨텍스트 스위치 (수십 µs, §5) |

### 실습 환경 한 줄

QEMU `mps2-an385`(Cortex-M3 @ 25 MHz)에서 FreeRTOS V11.3.2(ARM_CM3 포트, 랩 기본 `FreeRTOSConfig.h`: 1 kHz tick, `configASSERT` 켜짐)와 Zephyr v4.4.2(`mps2/an385`, 1 kHz tick, `CONFIG_QEMU_ICOUNT_SHIFT=5`)를 돌린다. 타이밍은 모두 icount(명령 1개 = 32 ns 가상 시간, 결정적)이고 시계는 FPGAIO COUNTER(0x40028018, 25 MHz, 1 카운트 = 40 ns)다. **숫자는 QEMU icount 기준이며 실제 칩과 절대값은 다르다**(캐시 · 플래시 wait state · 버스 · 예외 스태킹을 모델링하지 않음). 이 노트가 보이려는 것은 **상대 비교와 모양**이다.

모든 FreeRTOS 예제가 쓰는 작은 헤더 `d2.h`와 빌드 스크립트다. 이 노트를 쓰는 동안 VM의 루트 파일시스템이 읽기 전용(emergency remount)이 되어 있어서 빌드 산출물을 평소 위치(`/var/tmp/rtos/D2`) 대신 tmpfs `/tmp/rtosD2`에 두었다. 명령의 모양은 같다.

```c
/* d2.h — D2 helpers for QEMU mps2-an385 + FreeRTOS (cycle clock, TIMER0, spin) */
#ifndef D2_H
#define D2_H
#include "board.h"
#define CYC()        REG32(0x40028018u)            /* FPGAIO 25 MHz counter: 1 cyc = 40 ns */
#define CYC_NS(c)    ((unsigned)((c) * 40u))
static inline void timer0_start(uint32_t period, uint8_t prio)
{
    TIMER_CTRL(TIMER0_BASE) = 0;
    TIMER_RELOAD(TIMER0_BASE) = period - 1;
    TIMER_VALUE(TIMER0_BASE) = period - 1;
    TIMER_INTCLR(TIMER0_BASE) = 1;
    NVIC_IPR(8) = prio;
    NVIC_ISER0 = 1u << 8;
    TIMER_CTRL(TIMER0_BASE) = 1u | 8u;             /* enable + IRQ */
}
static inline void timer0_stop(void) { TIMER_CTRL(TIMER0_BASE) = 0; }
static inline uint32_t timer0_elapsed(void)       /* cycles since TIMER0 raised its IRQ */
{
    return TIMER_RELOAD(TIMER0_BASE) - TIMER_VALUE(TIMER0_BASE);
}
static inline void spin_cyc(uint32_t c) { uint32_t t = CYC(); while (CYC() - t < c) { } }
static inline void spin_us(uint32_t us) { spin_cyc(us * 25u); }
#endif
```

Zephyr 쪽은 `rtos-zbuild`를 감싼 `zrun.sh`로 빌드하고 `rtos-zrun`으로 실행했다(캐시 경로만 `/tmp`로 돌렸다).

## 1. 소유권 — 잠근 태스크만 푼다

### 1.1 정의

**뮤텍스**는 값이 0 또는 1인 잠금에 **소유자(owner, holder)** 필드가 붙은 커널 객체다.

- **take / lock**: 비어 있으면 "주인 = 나"로 적고 바로 돌아온다. 차 있으면 주어진 시간(timeout)만큼 잠들어 기다린다.
- **give / unlock**: 주인만 할 수 있다. 주인 필드를 비우고(또는 다음 대기자로 바꾸고) 기다리던 태스크 중 우선순위가 가장 높은 것을 깨운다.
- 주인이 있기 때문에 **우선순위 상속**(§6, D3)과 **재귀 잠금**(§2)이 가능하다.

세마포어(D1)와의 차이는 "주인"이 있느냐 하나다. 그래서 세마포어는 "ISR이 주고 태스크가 받는" 신호용으로 쓰고, 뮤텍스는 "같은 태스크가 잡고 같은 태스크가 놓는" 상호 배제용으로만 쓴다.

### 1.2 API 한눈에

| 동작 | FreeRTOS V11.3.2 | Zephyr v4.4.2 |
|---|---|---|
| 만들기 | `xSemaphoreCreateMutex()` / `xSemaphoreCreateMutexStatic(&buf)` | `K_MUTEX_DEFINE(m)` / `k_mutex_init(&m)` |
| 재귀용 만들기 | `xSemaphoreCreateRecursiveMutex()` | 따로 없음 — `k_mutex`는 항상 재귀 |
| 잡기 | `xSemaphoreTake(m, ticks)` → `pdTRUE` / `pdFALSE` | `k_mutex_lock(&m, timeout)` → 0 / `-EBUSY` / `-EAGAIN` |
| 재귀 잡기 | `xSemaphoreTakeRecursive(m, ticks)` | `k_mutex_lock` 그대로 |
| 놓기 | `xSemaphoreGive(m)` | `k_mutex_unlock(&m)` → 0 / `-EPERM` / `-EINVAL` |
| 재귀 놓기 | `xSemaphoreGiveRecursive(m)` | `k_mutex_unlock` 그대로 |
| 주인 묻기 | `xSemaphoreGetMutexHolder(m)` (`INCLUDE_xSemaphoreGetMutexHolder`) | `m.owner` 필드 (공개 API 없음, 디버깅용) |
| 필요한 설정 | `configUSE_MUTEXES 1`, 재귀는 `configUSE_RECURSIVE_MUTEXES 1` | 기본 포함 |
| ISR에서 | **금지** (`semphr.h`: "Mutex type semaphores cannot be used from within interrupt service routines") | **금지** (`kernel.h`: "Mutexes may not be locked in ISRs") |

FreeRTOS의 뮤텍스 함수 이름이 전부 `xSemaphore...`인 이유는 §7에서 본다. FreeRTOS에서 뮤텍스는 "길이 1, 항목 크기 0인 큐"이고, 세마포어도 같은 큐다. 같은 함수가 큐의 종류를 보고 뮤텍스일 때만 주인을 기록한다.

### 1.3 예제 1 — FreeRTOS: 주인이 아닌 태스크가 give하면?

무엇을 확인하나: (1) 비어 있는 뮤텍스를 give하면, (2) A가 쥐고 잠든 사이 B(주인 아님)가 give하면 무슨 일이 일어나는지. 같은 소스를 랩 기본 config(`configASSERT` 켬)와 `configASSERT`를 지운 config(양산 빌드에서 흔한 모양)로 두 번 돌린다.

```c
/* ex1 — FreeRTOS mutex ownership: who may give? (holder query, give-when-free, non-owner give) */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
static SemaphoreHandle_t m;
static volatile int a_inside;                       /* 1 while task A believes it owns m */
static const char *holder(void)
{
    TaskHandle_t h = xSemaphoreGetMutexHolder(m);
    return h ? pcTaskGetName(h) : "(none)";
}
static void task_a(void *p)                          /* prio 2: the real owner */
{
    (void)p;
    xSemaphoreTake(m, portMAX_DELAY);
    a_inside = 1;
    board_printf_raw("A: took m, holder=%s\n", holder());
    vTaskDelay(10);                                  /* still inside the critical region */
    board_printf_raw("A: woke up, holder=%s -> giving\n", holder());
    a_inside = 0;
    BaseType_t r = xSemaphoreGive(m);
    board_printf_raw("A: give returned %d, holder=%s\n", (int)r, holder());
    board_exit(0);
}
static void task_b(void *p)                          /* prio 1: not the owner */
{
    (void)p;
    board_printf_raw("B: holder=%s, give on a FREE mutex -> %d\n", holder(), (int)xSemaphoreGive(m));
    xTaskCreate(task_a, "A", 512, NULL, 2, NULL);   /* A preempts, takes m, sleeps */
    board_printf_raw("B: holder=%s, now B (not owner) calls give...\n", holder());
    BaseType_t r = xSemaphoreGive(m);
    board_printf_raw("B: give returned %d, holder=%s\n", (int)r, holder());
    if (xSemaphoreTake(m, 0) == pdTRUE)
        board_printf_raw("B: took m too! A inside=%d -> two tasks in the region\n", a_inside);
    for (;;) vTaskDelay(100);
}
int main(void)
{
    m = xSemaphoreCreateMutex();
    xTaskCreate(task_b, "B", 512, NULL, 1, NULL);
    vTaskStartScheduler();
    return 1;
}
```

덤으로, `configASSERT`를 끄자 커널 소스 자체에서 경고 두 개가 나왔다(assert 안에서만 쓰던 변수가 남는다). 내 코드의 경고가 아니므로 이 config에서는 `-Wno-unused-variable -Wno-unused-but-set-variable`로 커널 경고를 따로 끄는 것이 보통이다.

### 1.4 예제 2 — Zephyr: 에러 코드로 돌려준다

무엇을 확인하나: Zephyr `k_mutex`의 소유권 · 재귀 · 타임아웃 에러 코드와, ISR에서 잠그면 무슨 일이 일어나는지. `CONFIG_ASSERT=y`로 빌드한다.

```c
/* ex2 — Zephyr k_mutex: owner, lock_count, error codes, and k_mutex_lock from an ISR */
#include <zephyr/kernel.h>
static K_MUTEX_DEFINE(m);
static void show(const char *who)
{
    printk("%-22s owner=%s lock_count=%u\n", who,
           m.owner ? k_thread_name_get(m.owner) : "(none)", m.lock_count);
}
static void other_fn(void *a, void *b, void *c)          /* prio 3: never the owner */
{
    ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
    printk("other: unlock (not owner)   -> %d\n", k_mutex_unlock(&m));
    show("other: after that");
    printk("other: lock(K_NO_WAIT)      -> %d\n", k_mutex_lock(&m, K_NO_WAIT));
    int64_t t0 = k_uptime_get();
    int r = k_mutex_lock(&m, K_MSEC(5));
    printk("other: lock(K_MSEC(5))      -> %d after %lld ms\n", r, k_uptime_get() - t0);
    if (r == 0) { show("other: GOT it"); k_mutex_unlock(&m); }
}
K_THREAD_DEFINE(other, 1024, other_fn, NULL, NULL, NULL, 3, 0, K_TICKS_FOREVER);
static void isr_cb(struct k_timer *t)                    /* runs in the SysTick ISR */
{
    ARG_UNUSED(t);
    printk("timer ISR: calling k_mutex_lock(K_NO_WAIT)...\n");
    printk("timer ISR: returned %d\n", k_mutex_lock(&m, K_NO_WAIT));
    show("timer ISR: after lock");
}
static K_TIMER_DEFINE(tm, isr_cb, NULL);
int main(void)
{
    k_thread_name_set(k_current_get(), "main");
    k_thread_name_set(other, "other");
#ifndef SKIP_FIRST
    printk("main: unlock never-locked     -> %d\n", k_mutex_unlock(&m));
#endif
    k_mutex_lock(&m, K_FOREVER);
    k_mutex_lock(&m, K_FOREVER);                         /* recursive: same owner */
    show("main: locked twice");
    k_thread_start(other);                               /* prio 3 < main? main is 0 */
    k_msleep(20);                                        /* let other run while we hold m */
    k_mutex_unlock(&m);
    show("main: unlock #1");
    k_mutex_unlock(&m);
    show("main: unlock #2");
    k_timer_start(&tm, K_MSEC(1), K_NO_WAIT);
    k_msleep(5);
    printk("main: done\n");
    return 0;
}
```

### 1.5 예제 2b — `CONFIG_NO_RUNTIME_CHECKS=y`이면 `-EPERM`이 사라진다

Zephyr의 소유권 검사는 `CHECKIF()` 매크로로 쓰여 있다(`kernel/mutex.c:238`, `:246`). 이 매크로의 정의(`include/zephyr/sys/check.h`)는 Kconfig에 따라 세 가지로 바뀐다.

```c
#if defined(CONFIG_ASSERT_ON_ERRORS)
#define CHECKIF(expr) \
	__ASSERT_NO_MSG(!(expr));   \
	if (0)
#elif defined(CONFIG_NO_RUNTIME_CHECKS)
#define CHECKIF(...) \
	if (0)
#else
#define CHECKIF(expr) \
	if (expr)
#endif
```

`CONFIG_NO_RUNTIME_CHECKS=y`이면 `CHECKIF(mutex->owner != _current) { return -EPERM; }`가 `if (0) { ... }`가 된다. 검사가 **사라지고 unlock이 그대로 진행된다**. 무엇을 확인하나: 같은 ex2를 `CONFIG_ASSERT=n`, `CONFIG_NO_RUNTIME_CHECKS=y`(`norc.conf`)로 다시 빌드한다. 첫 시도는 소스 그대로, 두 번째는 첫 줄(안 잠긴 뮤텍스 unlock)을 빼고(`-DSKIP_FIRST=1`, `CMakeLists.txt`에서 `target_compile_definitions(app PRIVATE SKIP_FIRST)`로 바꿔 준다).

출력에서 볼 것은 세 장면이다.

2. **주인 아닌 unlock → 0(성공)**, 그리고 주인의 `lock_count`가 2 → 1로 줄었다. main이 첫 unlock을 하자 주인이 사라진다. main은 아직 한 번 더 잡고 있다고 믿는데 뮤텍스는 이미 풀렸다 — 예제 1의 FreeRTOS assert-끔과 같은 종류의 오염이다.
3. **ISR에서 lock → 0(성공), 주인 = `idle`.** ISR이 걸렸을 때 실행 중이던 스레드가 idle이었으니 `_current`가 idle이고, 뮤텍스의 주인이 idle 스레드로 기록됐다. ISR에서의 "주인"이 무의미하다는 것(§4)을 그대로 보여 준다.

### 1.6 정리 — 규칙을 어기면 각 커널은 어떻게 반응하나

| 잘못 | FreeRTOS (assert 켬) | FreeRTOS (assert 끔) | Zephyr 기본 | Zephyr `NO_RUNTIME_CHECKS` |
|---|---|---|---|---|
| 비어 있는 뮤텍스 give/unlock | `pdFAIL`(0) | `pdFAIL`(0) | `-EINVAL` | NULL 역참조 → MPU FAULT (예제 2b) |
| 주인 아닌 태스크가 give/unlock | assert `tasks.c:6861` | **성공**, 두 태스크가 안에 | `-EPERM`, 상태 그대로 | **성공**, 주인의 `lock_count` 감소 |
| 주인 아닌 태스크가 재귀 give | `pdFAIL` (assert 아님, §2) | `pdFAIL` | (재귀 구분 없음) `-EPERM` | 성공 |
| ISR에서 take/lock | assert `port.c:438` (§4) | 조용히 진행 (주인 = 끼어든 태스크) | `CONFIG_ASSERT=y`면 assert `mutex.c:115`, 아니면 진행 | 진행, 주인 = `idle` (예제 2b) |
| 같은 태스크가 일반 뮤텍스를 두 번 take | 자기 자신을 기다림 (예제 3) | 같음 | 재귀로 성공 | 재귀로 성공 |

**함정**: "Zephyr는 `-EPERM`을 주니까 안전하다"는 반만 맞다. 반환값을 **검사하지 않으면** 의미가 없고(대부분의 코드가 `k_mutex_unlock(&m);`로 버린다), 코드 크기를 줄이려고 `CONFIG_NO_RUNTIME_CHECKS`를 켜면 검사 자체가 없어진다. FreeRTOS 쪽은 "양산에서 `configASSERT`를 끈다"가 같은 효과다. 그래서 개발 · 시험 빌드에서는 assert를 반드시 켜 두고, 소유권 위반은 **설계로** 없앤다(뮤텍스를 다루는 코드를 한 모듈의 래퍼 함수 하나로 모은다, §3.4).

## 2. 재귀 뮤텍스 — 같은 주인이 여러 번

### 2.1 직관과 정의

**재귀 뮤텍스(recursive mutex)**는 주인이 이미 쥔 뮤텍스를 또 잡으면 막지 않고 **카운터만 올린다**. 놓을 때는 카운터를 내리고, 0이 되는 순간에만 진짜로 풀린다. "문을 세 번 잠근 주인은 세 번 열어야 나갈 수 있다."

FreeRTOS에서는 생성 함수부터 다르다(`xSemaphoreCreateRecursiveMutex`). 카운터는 뮤텍스 안의 `uxRecursiveCallCount`다. Zephyr의 `k_mutex`는 **항상 재귀**이고 카운터는 `lock_count`다(예제 2의 `lock_count=2`). 각 RTOS의 기본값 비교는 A5 §3.7에 있다.

### 2.2 예제 3 — 일반 뮤텍스의 자기 교착, 재귀 카운터, give 규칙, API 섞기

무엇을 확인하나: (1) 일반 뮤텍스를 같은 태스크가 두 번 take하면, (2) 재귀 뮤텍스를 3번 잡고 1번씩 놓을 때 기다리던 B가 언제 깨어나는지, (3) 주인 아닌 B의 `xSemaphoreGiveRecursive`, (4) 재귀로 2번 잡고 **일반 give**로 놓으면. 카운터는 공개 API가 없어서, 정적 할당 버퍼(`StaticSemaphore_t`)의 더미 필드를 kernel-aware 디버거처럼 들여다본다(`pvDummy1[2]` = `xMutexHolder`, `u.uxDummy2` = `uxRecursiveCallCount`, 레이아웃은 §7.1 그림).

```c
/* ex3 — plain vs recursive mutex: self-deadlock, nested take count, give rules, API mixing */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
static StaticSemaphore_t rbuf;                      /* peek inside like a kernel-aware debugger */
static SemaphoreHandle_t m, r;
#define R_HOLDER() ((TaskHandle_t)rbuf.pvDummy1[2])  /* Queue_t.u.xSemaphore.xMutexHolder */
#define R_COUNT()  ((unsigned)rbuf.u.uxDummy2)       /* Queue_t.u.xSemaphore.uxRecursiveCallCount */
static const char *nm(TaskHandle_t h) { return h ? pcTaskGetName(h) : "(none)"; }
static void peek(const char *s) { board_printf_raw("  %s: holder=%s count=%u\n", s, nm(R_HOLDER()), R_COUNT()); }
static void task_b(void *p)                          /* prio 3: wants r, and tries a non-owner give */
{
    (void)p;
    board_printf_raw("B: GiveRecursive (not owner) -> %d\n", (int)xSemaphoreGiveRecursive(r));
    TickType_t t0 = xTaskGetTickCount();
    BaseType_t ok = xSemaphoreTakeRecursive(r, portMAX_DELAY);
    board_printf_raw("B: got r=%d after %u ticks\n", (int)ok, (unsigned)(xTaskGetTickCount() - t0));
    peek("B holding");
    xSemaphoreGiveRecursive(r);
    vTaskSuspend(NULL);
}
static void task_a(void *p)                          /* prio 2 */
{
    (void)p;
    TickType_t t0 = xTaskGetTickCount();
    xSemaphoreTake(m, portMAX_DELAY);
    BaseType_t again = xSemaphoreTake(m, 5);         /* same task, plain mutex, 5-tick timeout */
    board_printf_raw("A: plain mutex 2nd take -> %d after %u ticks (self-deadlock)\n",
                     (int)again, (unsigned)(xTaskGetTickCount() - t0));
    xSemaphoreGive(m);
    for (int i = 0; i < 3; i++) xSemaphoreTakeRecursive(r, portMAX_DELAY);
    peek("A took r x3");
    xTaskCreate(task_b, "B", 512, NULL, 3, NULL);    /* B preempts and blocks on r */
    for (int i = 3; i > 0; i--) {
        vTaskDelay(2);
        xSemaphoreGiveRecursive(r);                  /* B wakes only on the last one */
        peek("A gave 1");
    }
    board_printf_raw("A: extra GiveRecursive -> %d\n", (int)xSemaphoreGiveRecursive(r));
    /* API mixing: take recursively twice, then a PLAIN give */
    xSemaphoreTakeRecursive(r, 0); xSemaphoreTakeRecursive(r, 0);
    peek("A took r x2");
    board_printf_raw("A: plain xSemaphoreGive(r) -> %d\n", (int)xSemaphoreGive(r));
    peek("A after plain give");
    board_printf_raw("sizeof(StaticSemaphore_t)=%u\n", (unsigned)sizeof(StaticSemaphore_t));
    board_exit(0);
}
int main(void)
{
    m = xSemaphoreCreateMutex();
    r = xSemaphoreCreateRecursiveMutexStatic(&rbuf);
    xTaskCreate(task_a, "A", 512, NULL, 2, NULL);
    vTaskStartScheduler();
    return 1;
}
```

출력에서 볼 것:

1. **일반 뮤텍스를 주인이 또 take** → 5 tick 기다리다 실패. 자기가 쥔 열쇠를 자기가 기다렸다. `portMAX_DELAY`였다면 **영원히** 멈춘다(자기 교착, self-deadlock).
2. **재귀 카운터**: 3번 잡으면 count=3, 한 번 놓을 때마다 2, 1. B는 **세 번째 give에서야** 깨어났다(`after 6 ticks` = 2 tick × 3). B의 줄이 A의 마지막 `peek`보다 먼저 찍힌 것은 B(우선순위 3)가 give 순간 A를 선점했기 때문이다.
3. **주인 아닌 `GiveRecursive` → 0**, assert 없음. `xQueueGiveMutexRecursive()`는 처음부터 `xMutexHolder == xTaskGetCurrentTaskHandle()`을 직접 비교해서 아니면 `pdFAIL`을 돌려준다(`queue.c:759`~). 일반 `xSemaphoreGive`(§1.3)와 반응이 다르다 — 재귀 쪽이 오히려 더 친절하다.
4. **API 섞기 버그**: 재귀로 2번 잡고 일반 `xSemaphoreGive`로 한 번 놓으면 **뮤텍스가 통째로 풀리고(holder=none) 카운터는 2로 남는다**. 일반 give는 카운터를 모른다. 다음 주인은 count=3에서 시작하므로 3번 놓아야 풀린다 — 아무도 3번 놓지 않으니 결국 영원히 잠긴 뮤텍스가 된다. `semphr.h`도 "This macro must not be used on mutexes created using xSemaphoreCreateMutex()"처럼 짝을 맞추라고 적어 둘 뿐 검사하지 않는다.

### 2.3 언제 정당하고, 언제 설계 냄새인가

재귀 뮤텍스는 "이미 잡고 있는지 모르는 코드"를 위한 도구다. 그 자체가 신호다 — **누가 언제 잠그는지 설계에서 정해지지 않았다**.

| 상황 | 판단 | 대안 |
|---|---|---|
| 공개 함수 `log_write()`가 잠그고, 내부에서 다시 공개 함수 `log_flush()`를 부르는데 그것도 잠근다 | 설계 냄새 (가장 흔함) | 잠그는 공개 함수 + 잠그지 않는 내부 함수 `log_flush_locked()`로 나눈다 |
| 콜백을 등록받는 드라이버: 콜백 안에서 사용자가 같은 드라이버 API를 다시 부를 수 있다 | 정당할 수 있음 | 콜백을 잠금 밖에서 부른다 (잠금 → 상태 복사 → 풀기 → 콜백) |
| 서드파티 스택(파일시스템, USB, lwIP)의 포팅 계층이 "재귀 뮤텍스를 달라"고 요구한다 | 정당 (선택권이 없음) | 그 계층에만 쓰고 앱 코드로 퍼지지 않게 한다 |
| 재귀 호출하는 알고리즘(트리 순회)이 공유 자료구조를 만진다 | 설계 냄새 | 바깥에서 한 번 잠그고 내부 재귀 함수는 잠그지 않는다 |
| Zephyr로 옮겼더니 원래 FreeRTOS에서 교착하던 코드가 "그냥 돈다" | 위험 | 재귀가 숨긴 이중 잠금을 찾아서 고친다 (A5 §3.7) |

재귀 뮤텍스가 위험한 이유는 두 가지다. 첫째, **불변식(invariant)이 깨진 상태로 다시 들어간다.** 바깥 함수가 자료구조를 반쯤 고친 상태에서 안쪽 함수가 같은 자료구조를 "온전하다"고 믿고 읽는다 — 뮤텍스가 막아 주지 않는 버그다. 둘째, **풀었다고 생각했는데 안 풀린다.** 어느 경로에서 take가 한 번 더 일어나면 바깥의 마지막 give 뒤에도 count=1로 남는다. 위 예제의 "API 섞기"가 그 변형이다.

`_locked()` 분리 패턴은 이렇게 생겼다(구조만 보이는 실행하지 않은 조각이다).

```c
/* not executed — the usual fix: public functions lock, *_locked() helpers assume the lock is held */
static SemaphoreHandle_t log_mtx;                   /* plain mutex, not recursive */
static void log_flush_locked(void) { /* drain ring to UART; caller holds log_mtx */ }
void log_flush(void)
{
    xSemaphoreTake(log_mtx, portMAX_DELAY);
    log_flush_locked();
    xSemaphoreGive(log_mtx);
}
void log_write(const char *s)
{
    xSemaphoreTake(log_mtx, portMAX_DELAY);
    /* append s to ring ... */
    if (/* ring nearly full */ 0) log_flush_locked();   /* NOT log_flush(): no second take */
    xSemaphoreGive(log_mtx);
}
```

**Don 경험과 연결**: SSD 펌웨어에서 "이 함수는 채널 락을 쥔 상태로만 불러야 한다"를 함수 이름 접미사나 assert(`ASSERT(chan_lock_held(ch))`)로 표시했다면 같은 패턴이다. FreeRTOS에서는 `configASSERT(xSemaphoreGetMutexHolder(log_mtx) == xTaskGetCurrentTaskHandle())`를 `_locked()` 함수 첫 줄에 넣으면 된다.

## 3. 타임아웃 — 기다림에 예산을 붙인다

### 3.1 타임아웃 값은 어떻게 정하나

`xSemaphoreTake(m, ticks)`와 `k_mutex_lock(&m, timeout)`의 두 번째 인자는 "최대 얼마나 기다릴지"다. 값은 감으로 정하지 않는다. **다른 주인이 이 뮤텍스를 쥐는 최악 시간**을 알면 예산이 나온다.

- 예산 = (다른 태스크들의 최악 보유 시간 중 최댓값) + (그 사이 선점해 들어올 수 있는 더 높은 태스크 · ISR의 시간) + 여유.
- 그리고 예산 < **내 마감까지 남은 시간**이어야 한다. 1 kHz 루프에서 2 ms를 기다리면 기다리는 것만으로 주기를 놓친다(예제 4).
- 단위는 tick이다. FreeRTOS에서 `xSemaphoreTake(m, 2)`는 "tick 경계를 2번 지날 때까지"라서 실제로는 1~2 ms(1 kHz tick)다. Zephyr는 ms를 tick으로 **올림**하고 +1 tick을 더한다(예제 2: 5 ms → 6 ms). µs 단위 예산이 필요하면 뮤텍스 타임아웃이 아니라 설계(보유 시간을 줄이기)로 해결한다.

### 3.2 예제 4 — 버스 주인이 멈췄을 때: 타임아웃이 있는 태스크 vs `portMAX_DELAY` 태스크

무엇을 확인하나: 드론 FC의 I2C 버스 뮤텍스를 기압계 태스크가 잡은 채 **오지 않는 I2C 완료 인터럽트를 영원히 기다리는** 버그를 일부러 만든다. IMU 태스크(1 kHz, 예산 2 tick)는 타임아웃 에러 경로로 버티고, 로그 태스크(`portMAX_DELAY`)는 영원히 멈춘다. 감시(supervisor) 태스크가 40 ms 뒤에 상태를 본다.

```c
/* ex4 — take with timeout: error path for a stuck bus owner vs a portMAX_DELAY waiter */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
static SemaphoreHandle_t bus;
static TaskHandle_t h_imu, h_log;
static volatile unsigned imu_ok, imu_timeout, imu_consec, log_writes;
typedef enum { BUS_OK = 0, BUS_BUSY = -1 } bus_err_t;
static bus_err_t bus_xfer(TickType_t budget, uint32_t work_us)   /* the only door to the bus */
{
    if (xSemaphoreTake(bus, budget) != pdTRUE) return BUS_BUSY;  /* never touch HW without it */
    uint32_t t = board_now_us(); while (board_now_us() - t < work_us) { }
    xSemaphoreGive(bus);
    return BUS_OK;
}
static void imu_task(void *p)                       /* prio 4, 1 kHz, budget 2 ticks */
{
    (void)p;
    TickType_t last = xTaskGetTickCount();
    for (;;) {
        uint32_t t0 = board_now_us();
        if (bus_xfer(2, 100) == BUS_OK) { imu_ok++; imu_consec = 0; }
        else {
            imu_timeout++;
            if (++imu_consec == 1)
                board_printf_raw("[%u ms] imu: bus timeout after %u us, holder=%s -> use last sample\n",
                                 (unsigned)xTaskGetTickCount(), (unsigned)(board_now_us() - t0),
                                 pcTaskGetName(xSemaphoreGetMutexHolder(bus)));
            if (imu_consec == 5) board_printf_raw("[%u ms] imu: 5 misses in a row -> request bus recovery\n",
                                                  (unsigned)xTaskGetTickCount());
        }
        xTaskDelayUntil(&last, 1);
    }
}
static void baro_task(void *p)                      /* prio 2: takes the bus, then hangs inside */
{
    (void)p;
    vTaskDelay(10);
    xSemaphoreTake(bus, portMAX_DELAY);
    board_printf_raw("[%u ms] baro: took bus, waiting for an I2C IRQ that never comes...\n",
                     (unsigned)xTaskGetTickCount());
    ulTaskNotifyTake(pdTRUE, portMAX_DELAY);       /* BUG: blocking forever while holding */
}
static void log_task(void *p)                       /* prio 1: uses portMAX_DELAY */
{
    (void)p;
    for (;;) { xSemaphoreTake(bus, portMAX_DELAY); log_writes++; xSemaphoreGive(bus); vTaskDelay(3); }
}
static void sup_task(void *p)                       /* prio 5: supervisor */
{
    (void)p;
    vTaskDelay(40);
    static const char *st[] = { "Running", "Ready", "Blocked", "Suspended", "Deleted", "Invalid" };
    board_printf_raw("[%u ms] sup: imu ok=%u timeout=%u | log writes=%u, log state=%s, imu state=%s\n",
                     (unsigned)xTaskGetTickCount(), imu_ok, imu_timeout, log_writes,
                     st[eTaskGetState(h_log)], st[eTaskGetState(h_imu)]);
    board_printf_raw("[%u ms] sup: log is stuck forever (portMAX_DELAY); imu kept its 1 kHz loop\n",
                     (unsigned)xTaskGetTickCount());
    board_exit(0);
}
int main(void)
{
    bus = xSemaphoreCreateMutex();
    xTaskCreate(imu_task, "imu", 512, NULL, 4, &h_imu);
    xTaskCreate(baro_task, "baro", 512, NULL, 2, NULL);
    xTaskCreate(log_task, "log", 512, NULL, 1, &h_log);
    xTaskCreate(sup_task, "sup", 512, NULL, 5, NULL);
    vTaskStartScheduler();
    return 1;
}
```

```text
[10 ms] baro: took bus, waiting for an I2C IRQ that never comes...
[13 ms] imu: bus timeout after 2013 us, holder=baro -> use last sample
[21 ms] imu: 5 misses in a row -> request bus recovery
[40 ms] sup: imu ok=11 timeout=14 | log writes=4, log state=Blocked, imu state=Blocked
[40 ms] sup: log is stuck forever (portMAX_DELAY); imu kept its 1 kHz loop
[board_exit] code=0
[exit=0]
```

출력에서 볼 것:

1. IMU의 첫 타임아웃은 **2013 µs** 뒤에 돌아왔다(2 tick). 에러 경로가 주인 이름(`holder=baro`)을 찍었다 — 현장 로그에서 "누가 쥐고 안 놓나"를 바로 알려 주는 한 줄이다. `xSemaphoreGetMutexHolder`를 켜 두는 이유다.
2. 5번 연속 실패는 13 ms → 21 ms, 즉 **실패 한 번에 2 ms**가 걸렸다. 1 kHz 루프에 2 tick 예산을 준 것이 잘못이다. 기다리는 동안 이미 다음 주기가 지나간다. 이 루프라면 예산은 0(`xSemaphoreTake(bus, 0)`, 못 잡으면 이번 주기는 건너뜀)이나 1 tick 미만이 맞다. **예산 < 주기**를 지키지 않으면 타임아웃이 있어도 루프가 밀린다.
3. 40 ms 동안 IMU는 ok 11 + timeout 14번 — **살아서 돌았다**. 로그 태스크는 4번 쓰고 `Blocked`에 멈췄고, 아무 흔적도 남기지 않는다. `portMAX_DELAY`로 기다리는 태스크는 주인이 돌아오지 않으면 **영원히 아무 말 없이** 멈춘다.

### 3.3 `portMAX_DELAY` / `K_FOREVER`를 써도 되는 때

`portMAX_DELAY`(FreeRTOS에서 `INCLUDE_vTaskSuspend 1`이면 진짜 무한)와 `K_FOREVER`는 금지가 아니다. 쓸 수 있는 조건은 이렇다.

- 모든 주인의 보유 구간이 **블로킹 없이 유한**하다는 것이 코드로 보장된다(구간 안에 I/O 대기 · 큐 대기 · delay가 없다).
- 그래도 멈추면 잡아 줄 **독립된 감시 수단**이 있다 — 태스크별 체크인 기반 워치독(M 모듈), 감시 태스크의 `eTaskGetState`.
- 기다리는 태스크가 마감이 없는 배경 작업(로그, 통계)이고, 멈춰도 제어 루프에 영향이 없다.

반대로 **마감이 있는 태스크**(제어 루프, 통신 응답)는 항상 유한한 예산을 주고 반환값을 검사한다. 예산을 넘긴 것은 "버그가 났다"는 신호이므로, 에러 경로는 조용히 넘어가지 말고 **세고(count), 남기고(log), 올린다(escalate)**.

| 에러 경로 단계 | 예제 4에서 | 실무 예 |
|---|---|---|
| 이번 주기 대처 | 지난 샘플 재사용 | 센서 퓨전에 "이번 IMU 샘플 없음" 표시, 예측만 진행 |
| 세기 | `imu_timeout++`, 연속 횟수 `imu_consec` | 헬스 카운터 → 텔레메트리로 송신 |
| 남기기 | 첫 실패에 주인 이름 출력 | 블랙박스 로그에 `holder`, tick, 연속 횟수 |
| 올리기 | 5연속이면 버스 복구 요청 | I2C 버스 복구(SCL 9펄스 + STOP, J2), 센서 재초기화, 고장 모드 전환 |

### 3.4 에러 경로에서 unlock을 잊지 않는 구조

뮤텍스 버그의 큰 부분이 "에러로 일찍 return하면서 give를 빠뜨림"이다. 예제 4의 `bus_xfer()`처럼 **뮤텍스를 만지는 코드를 한 함수(문)로 모으고, 그 함수의 출구를 하나로** 만든다. C에서는 `goto out;` 패턴이 정석이다.

```c
/* not executed — single-exit pattern: every path after a successful take reaches the give */
int i2c_read_reg(uint8_t dev, uint8_t reg, uint8_t *val)
{
    int err;
    if (xSemaphoreTake(i2c_mtx, pdMS_TO_TICKS(1)) != pdTRUE)
        return -EBUSY;                          /* not taken: must NOT give */
    err = i2c_hw_write(dev, &reg, 1);
    if (err) goto out;                          /* NACK, arbitration lost ... */
    err = i2c_hw_read(dev, val, 1);
out:
    xSemaphoreGive(i2c_mtx);                    /* exactly one give per successful take */
    return err;
}
```

규칙은 두 줄이다. **take가 실패했으면 give하지 않는다**(§1.3의 "비어 있는 뮤텍스 give"가 된다). **take가 성공했으면 모든 경로가 give를 지난다.** 리뷰할 때는 함수 안의 `return` 문마다 "이 시점에 뮤텍스를 쥐고 있나?"를 표시해 본다.

## 4. ISR에서 뮤텍스가 금지인 이유

### 4.1 세 가지 이유

1. **ISR은 주인이 될 수 없다.** 뮤텍스의 주인은 "태스크(TCB)"다. ISR은 태스크가 아니라, 그 순간 실행 중이던 아무 태스크의 스택 위에서 잠깐 도는 코드다. ISR이 take하면 커널은 "지금 현재 태스크"(`pxCurrentTCB`, `_current`)를 주인으로 적는데, 그것은 **우연히 끼어들림을 당한 태스크**다(예제 2b의 `owner=idle`). 그 태스크는 자기가 주인인 줄도 모르고, give할 일도 없다.
2. **ISR은 잠들 수 없다.** 뮤텍스가 차 있으면 기다려야 하는데, ISR은 블록할 수 없다(블록 = 이 실행 흐름을 멈추고 다른 태스크로 전환. ISR 위에는 전환할 "자기 태스크"가 없다). 기다리지 않는 `K_NO_WAIT` / 0 tick이면 실패를 받을 뿐인데, 그러면 ISR이 "자원을 못 썼다"를 어떻게 처리하나라는 문제가 남는다.
3. **우선순위 상속이 ISR을 올려 줄 수 없다.** 태스크가 ISR이 쥔 뮤텍스를 기다리면, 상속은 주인의 **스케줄러 우선순위**를 올리는데, ISR의 우선순위는 NVIC 하드웨어 우선순위라 스케줄러가 바꿀 수 없다. 거꾸로 ISR이 태스크가 쥔 뮤텍스를 원해도 ISR은 기다릴 수 없으니 상속할 일도 없다. FreeRTOS `xTaskPriorityInherit()`의 첫 주석이 정확히 이것이다: "If the mutex is taken by an interrupt, the mutex holder is NULL. Priority inheritance is not applied in this scenario."

### 4.2 예제 5 — FreeRTOS에서 ISR이 뮤텍스를 만지는 세 가지 방법

무엇을 확인하나: kernel-aware 우선순위(0x40)의 TIMER0 ISR에서 (MODE 1) 일반 `xSemaphoreTake`, (MODE 2) `xSemaphoreTakeFromISR` / `xSemaphoreGiveFromISR`, (MODE 3) 태스크가 쥔 뮤텍스를 `xSemaphoreGiveFromISR`로 놓기.

```c
/* ex5 — mutex from an ISR in FreeRTOS: MODE 1 Take, MODE 2 TakeFromISR/GiveFromISR, MODE 3 GiveFromISR on a held mutex */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "d2.h"
#ifndef MODE
#define MODE 1
#endif
static SemaphoreHandle_t m;
static volatile int step;
static const char *nm(TaskHandle_t h) { return h ? pcTaskGetName(h) : "(none)"; }
void TIMER0_IRQHandler(void)                       /* prio 0x40: kernel-aware, may call FromISR */
{
    TIMER_INTCLR(TIMER0_BASE) = 1;
    BaseType_t w = pdFALSE, r;
    switch (step) {
    case 1: board_printf_raw("ISR: xSemaphoreTake(m, 0)...\n"); r = xSemaphoreTake(m, 0);
            board_printf_raw("ISR: returned %d\n", (int)r); break;
    case 2: r = xSemaphoreTakeFromISR(m, &w);
            board_printf_raw("ISR: TakeFromISR -> %d, holder=%s\n", (int)r, nm(xSemaphoreGetMutexHolderFromISR(m))); break;
    case 3: board_printf_raw("ISR: GiveFromISR, holder=%s\n", nm(xSemaphoreGetMutexHolderFromISR(m)));
            r = xSemaphoreGiveFromISR(m, &w); board_printf_raw("ISR: returned %d\n", (int)r); break;
    default: break;
    }
    step = 0;
    portYIELD_FROM_ISR(w);
}
static void task_t(void *p)                        /* prio 2 */
{
    (void)p;
    timer0_start(25000, 0x40);                     /* 1 ms */
#if MODE == 1
    step = 1; vTaskDelay(3);
#elif MODE == 2
    step = 2; vTaskDelay(3);                       /* ISR "owns" it now (holder NULL) */
    board_printf_raw("task: Take(m, 5) -> %d (ISR took it)\n", (int)xSemaphoreTake(m, 5));
    step = 3; vTaskDelay(3);                       /* ISR gives it back: allowed, holder is NULL */
    board_printf_raw("task: Take(m, 5) -> %d, holder=%s\n", (int)xSemaphoreTake(m, 5), nm(xSemaphoreGetMutexHolder(m)));
#else
    xSemaphoreTake(m, portMAX_DELAY);              /* the task owns it ... */
    step = 3; vTaskDelay(3);                       /* ... and an ISR "releases" it */
#endif
    board_printf_raw("task: done\n");
    board_exit(0);
}
int main(void)
{
    m = xSemaphoreCreateMutex();
    xTaskCreate(task_t, "T", 512, NULL, 2, NULL);
    vTaskStartScheduler();
    return 1;
}
```

- **MODE 2** — `xSemaphoreTakeFromISR`은 **성공한다**. `xQueueReceiveFromISR()`는 뮤텍스인지 보지 않고 카운트만 내리므로 주인은 NULL로 남는다. 태스크는 그동안 못 잡고(0), ISR이 `GiveFromISR`로 돌려주자 잡는다. 동작은 하지만 이것은 **주인 없는 이진 세마포어**를 쓴 것과 같다. 상속도, 소유권 검사도 없다. 이렇게 쓸 거라면 처음부터 세마포어(D1)를 쓴다.
- **MODE 3** — 태스크가 주인인 뮤텍스를 ISR이 놓으려 하자 `queue.c:1360`에서 멈췄다. `xQueueGiveFromISR()`의 `configASSERT( ... !( ( pxQueue->uxQueueType == queueQUEUE_IS_MUTEX ) && ( pxQueue->u.xSemaphore.xMutexHolder != NULL ) ) )`이고, 바로 위 주석이 "priority inheritance makes no sense for an interrupt, only tasks"다.

### 4.3 Zephyr

Zephyr는 `z_impl_k_mutex_lock()`과 `z_impl_k_mutex_unlock()` 첫 줄에 `__ASSERT(!arch_is_in_isr(), "mutexes cannot be used inside ISRs")`를 둔다. `CONFIG_ASSERT=y`면 예제 2처럼 멈추고, 기본(`CONFIG_ASSERT`는 테스트 빌드가 아니면 기본 n)이면 **아무 검사 없이 진행**해서 예제 2b처럼 `owner=idle`이 된다. 경합 중이면 더 나쁘다. `K_FOREVER`로 부르면 ISR 안에서 `z_pend_curr()`가 현재 스레드를 대기 큐에 넣으려 한다. 그리고 Zephyr의 `k_timer` 만료 콜백은 **ISR 문맥**에서 돈다는 점이 함정이다. "타이머 콜백에서 로그 뮤텍스를 잡는" 코드가 FreeRTOS(타이머 서비스 태스크 문맥)에서는 돌다가 Zephyr로 옮기면 깨진다(A5 §3.4, D6).

### 4.4 ISR이 공유 자원을 써야 한다면

| 하고 싶은 것 | 쓸 것 | 노트 |
|---|---|---|
| ISR이 데이터를 태스크와 나눈다 (몇 바이트) | 크리티컬 섹션(태스크 쪽) + ISR은 그대로 | C7 |
| ISR이 고속으로 데이터를 넘긴다 | 락 없는 SPSC 링버퍼 | D8 |
| ISR이 "이벤트 났다"만 알린다 | 세마포어 · task notification (`...FromISR`) | D1, D5 |
| ISR이 I2C · SPI처럼 뮤텍스로 보호되는 자원을 쓰고 싶다 | 일을 태스크로 넘긴다 → 그 태스크가 뮤텍스를 잡는다 | D7 (`xTimerPendFunctionCallFromISR`, `k_work`) |

## 5. 고르기 — 뮤텍스 vs 크리티컬 섹션 vs 스케줄러 잠금

C7 §5.2에 "무엇을 막아야 하나"에서 출발하는 결정표가 있고, C7 §6은 잠금 길이 L이 IRQ · 태스크 지연에 얼마를 더하는지 PRIMASK · BASEPRI · 스케줄러 잠금으로 쟀다. 이 절은 그 표의 **뮤텍스 칸**을 숫자로 채운다. (1) 잡고 놓는 데 드는 **비용**, (2) 같은 50 µs 구간을 지킬 때 **누가 기다리나**.

### 5.1 세 도구는 막는 대상이 다르다

| | 크리티컬 섹션 (`taskENTER_CRITICAL` / `irq_lock`) | 스케줄러 잠금 (`vTaskSuspendAll` / `k_sched_lock`) | 뮤텍스 |
|---|---|---|---|
| 막는 것 | kernel-aware ISR 전부 + 모든 태스크 전환 | 모든 태스크 전환 (ISR은 돈다) | **같은 뮤텍스를 원하는 태스크만** |
| 안에서 블록 | 금지 | 금지 (FreeRTOS: 블로킹 API는 assert) | 가능 (단, 다른 대기자가 그만큼 기다린다) |
| ISR과 공유 | 가능 | 불가 (ISR은 막히지 않는다) | 불가 |
| 주인 · 상속 | 없음 | 없음 | 있음 |
| 잘못 썼을 때 피해 | 시스템 전체 IRQ 지연 | 시스템 전체 태스크 지연 | 그 자원을 쓰는 태스크들 + 역전(D3) |
| 적당한 길이 | 수 µs 이하 | 수~수십 µs | 수십 µs ~ ms, I/O 포함 |

### 5.2 예제 6 — FreeRTOS: 각 도구의 비용

무엇을 확인하나: 경합 없는 take+give 쌍, 재귀 뮤텍스(첫 단계 / 이미 쥔 상태에서 중첩), `taskENTER_CRITICAL`/`taskEXIT_CRITICAL` 쌍, `vTaskSuspendAll`/`xTaskResumeAll` 쌍을 각각 1000번 돌린 평균. 그리고 **경합 상황**: 낮은 태스크(lo, 1)가 쥔 뮤텍스를 높은 태스크(hi, 3)가 take해서 블록하는 경로, lo의 give가 hi를 깨워 hi가 take에서 돌아오기까지의 넘겨주기(handoff) 경로를 200번씩 잰다. 빈 루프 비용은 뺐다. 측정 중 1 ms SysTick이 몇 번 끼어든 것은 평균에 섞여 있다(1000회 × 6 µs ≈ 6 ms → tick 6번).

```c
/* ex6 — cost of each protection primitive (FreeRTOS V11.3.2, QEMU icount: 1 cyc = 40 ns) */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "d2.h"
#define N 1000
static SemaphoreHandle_t m, r;
static TaskHandle_t hi;
static volatile uint32_t t_block0, t_got, sink;
#define MEASURE(label, body) do { uint32_t t0 = CYC(); for (int i = 0; i < N; i++) { body; } \
    uint32_t c = (CYC() - t0) - base; \
    board_printf_raw("%s: %u ns\n", label, CYC_NS(c) / N); } while (0)
static void hi_task(void *p)                        /* prio 3: the contender */
{
    (void)p;
    for (;;) {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
        t_block0 = CYC();
        xSemaphoreTake(m, portMAX_DELAY);           /* blocks: lo holds m */
        t_got = CYC();
        xSemaphoreGive(m);
    }
}
static void lo_task(void *p)                        /* prio 1: measures */
{
    (void)p;
    uint32_t base = 0, t0 = CYC();
    for (int i = 0; i < N; i++) { sink = i; }
    base = CYC() - t0;
    MEASURE("mutex take+give (uncontended)", { xSemaphoreTake(m, 0); xSemaphoreGive(m); });
    MEASURE("recursive take+give (1st level)", { xSemaphoreTakeRecursive(r, 0); xSemaphoreGiveRecursive(r); });
    xSemaphoreTakeRecursive(r, 0);
    MEASURE("recursive take+give (nested)", { xSemaphoreTakeRecursive(r, 0); xSemaphoreGiveRecursive(r); });
    xSemaphoreGiveRecursive(r);
    MEASURE("taskENTER/EXIT_CRITICAL pair", { taskENTER_CRITICAL(); sink = i; taskEXIT_CRITICAL(); });
    MEASURE("vTaskSuspendAll/xTaskResumeAll", { vTaskSuspendAll(); sink = i; (void)xTaskResumeAll(); });
    uint64_t s_blk = 0, s_hand = 0; uint32_t mx_blk = 0, mx_hand = 0;
    for (int i = 0; i < 200; i++) {
        xSemaphoreTake(m, portMAX_DELAY);
        xTaskNotifyGive(hi);                        /* hi runs, blocks on m, PI boosts lo to 3 */
        uint32_t t_back = CYC(), blk = t_back - t_block0;
        UBaseType_t boosted = uxTaskPriorityGet(NULL);
        uint32_t t_give = CYC();
        xSemaphoreGive(m);                          /* disinherit + switch to hi */
        uint32_t hand = t_got - t_give;
        s_blk += blk; s_hand += hand; if (blk > mx_blk) mx_blk = blk; if (hand > mx_hand) mx_hand = hand;
        if (i == 0) board_printf_raw("lo priority while hi waits: %u (base 1)\n", (unsigned)boosted);
    }
    board_printf_raw("contended: hi take -> blocked -> lo runs: avg %u ns max %u ns\n",
                     CYC_NS((uint32_t)(s_blk / 200)), CYC_NS(mx_blk));
    board_printf_raw("contended: lo give -> hi returns from take: avg %u ns max %u ns\n",
                     CYC_NS((uint32_t)(s_hand / 200)), CYC_NS(mx_hand));
    board_exit(0);
}
int main(void)
{
    m = xSemaphoreCreateMutex();
    r = xSemaphoreCreateRecursiveMutex();
    xTaskCreate(hi_task, "hi", 512, NULL, 3, &hi);
    xTaskCreate(lo_task, "lo", 512, NULL, 1, NULL);
    vTaskStartScheduler();
    return 1;
}
```

### 5.3 예제 7 — Zephyr: 같은 측정

무엇을 확인하나: 같은 보드에서 Zephyr `k_mutex`, `irq_lock`, `k_sched_lock`의 비용과 경합 넘겨주기. main(우선순위 5)이 측정하고 hi(2)가 경쟁자다.

```c
/* ex7 — Zephyr v4.4.2 cost of k_mutex / irq_lock / k_sched_lock and a contended handoff */
#include <zephyr/kernel.h>
#define CYC()     (*(volatile uint32_t *)0x40028018u)      /* FPGAIO 25 MHz: 1 cyc = 40 ns */
#define N 1000
static K_MUTEX_DEFINE(m);
static K_SEM_DEFINE(go, 0, 1);
static volatile uint32_t t_block0, t_got, sink;
#define MEASURE(label, body) do { uint32_t t0 = CYC(); for (int i = 0; i < N; i++) { body; } \
    uint32_t c = (CYC() - t0) - base; printk("%-34s %5u ns\n", label, c * 40u / N); } while (0)
static void hi_fn(void *a, void *b, void *c)              /* prio 2: the contender */
{
    ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
    for (;;) {
        k_sem_take(&go, K_FOREVER);
        t_block0 = CYC();
        k_mutex_lock(&m, K_FOREVER);                       /* blocks: main holds m */
        t_got = CYC();
        k_mutex_unlock(&m);
    }
}
K_THREAD_DEFINE(hi, 1024, hi_fn, NULL, NULL, NULL, 2, 0, 0);
int main(void)
{
    k_thread_priority_set(k_current_get(), 5);
    uint32_t base, t0 = CYC();
    for (int i = 0; i < N; i++) { sink = i; }
    base = CYC() - t0;
    MEASURE("k_mutex_lock+unlock (uncontended)", { k_mutex_lock(&m, K_NO_WAIT); k_mutex_unlock(&m); });
    k_mutex_lock(&m, K_NO_WAIT);
    MEASURE("k_mutex lock+unlock (nested)", { k_mutex_lock(&m, K_NO_WAIT); k_mutex_unlock(&m); });
    k_mutex_unlock(&m);
    MEASURE("irq_lock/irq_unlock pair", { unsigned k = irq_lock(); sink = i; irq_unlock(k); });
    MEASURE("k_sched_lock/k_sched_unlock pair", { k_sched_lock(); sink = i; k_sched_unlock(); });
    uint64_t s_blk = 0, s_hand = 0; uint32_t mx_blk = 0, mx_hand = 0;
    for (int i = 0; i < 200; i++) {
        k_mutex_lock(&m, K_FOREVER);
        k_sem_give(&go);                                   /* hi runs, blocks on m, PI boosts main */
        uint32_t blk = CYC() - t_block0;
        int boosted = k_thread_priority_get(k_current_get());
        uint32_t t_give = CYC();
        k_mutex_unlock(&m);                                /* restore prio + switch to hi */
        uint32_t hand = t_got - t_give;
        s_blk += blk; s_hand += hand; if (blk > mx_blk) mx_blk = blk; if (hand > mx_hand) mx_hand = hand;
        if (i == 0) printk("main prio while hi waits: %d (base 5)\n", boosted);
    }
    printk("contended: hi lock -> blocked -> main runs: avg %u ns max %u ns\n",
           (uint32_t)(s_blk / 200) * 40u, mx_blk * 40u);

}
```

### 5.4 예제 8 — 같은 50 µs 구간을 네 가지로 지키면, 누가 기다리나

무엇을 확인하나: 낮은 태스크 lo(1)가 "잠금 → 50 µs 작업 → 풀기 → 10~40 µs(의사 난수) 쉬기"를 반복한다. 잠금 방법은 보호 없음 / 뮤텍스 / 크리티컬 섹션 / 스케줄러 잠금. 피해자 세 명의 최대 지연을 300개씩 잰다.

- **kernel-aware ISR 진입** — TIMER0(우선순위 0x40, 약 500 µs 주기)이 IRQ를 올린 뒤 ISR 첫 줄까지.
- **무관한 높은 태스크** — 그 ISR이 깨우는 hi(4). 공유 데이터를 **만지지 않는다**. IRQ → hi 실행까지.
- **같은 자원을 원하는 태스크** — DUALTIMER(0x40, 약 730 µs)가 깨우는 ct(3). 같은 방법으로 잠그고 2 µs 일한다. IRQ → 잠금 획득까지.

쉬는 시간을 난수로 섞은 이유는 C7 §6.1과 같다. icount는 결정적이라 주기가 맞물리면 IRQ가 늘 같은 위상에만 떨어진다.

```c
/* ex8 — same 50 us section protected 4 ways: who pays? (kernel-aware ISR, unrelated hi task, contender) */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "d2.h"
#define NS 300
#define DT_LOAD REG32(0x40002000u)
#define DT_VAL  REG32(0x40002004u)
#define DT_CTRL REG32(0x40002008u)
#define DT_CLR  REG32(0x4000200Cu)
typedef struct { uint32_t n, max; } st_t;
static st_t s_isr, s_hi, s_ct;
static SemaphoreHandle_t m;
static TaskHandle_t hi, ct;
static volatile int method, running;
static const char *names[] = { "none", "mutex", "critical", "sched_lock" };
static void add(st_t *s, uint32_t v) { if (s->n < NS) { s->n++; if (v > s->max) s->max = v; } }
static void lock(void)   { if (method == 1) xSemaphoreTake(m, portMAX_DELAY); else if (method == 2) taskENTER_CRITICAL(); else if (method == 3) vTaskSuspendAll(); }
static void unlock(void) { if (method == 1) xSemaphoreGive(m); else if (method == 2) taskEXIT_CRITICAL(); else if (method == 3) (void)xTaskResumeAll(); }
void TIMER0_IRQHandler(void)                        /* prio 0x40, ~500 us: wakes the UNRELATED hi task */
{
    uint32_t lat = timer0_elapsed(); TIMER_INTCLR(TIMER0_BASE) = 1;
    if (!running) return;
    add(&s_isr, lat);
    BaseType_t w = pdFALSE; vTaskNotifyGiveFromISR(hi, &w); portYIELD_FROM_ISR(w);
}
void DUALTIMER_IRQHandler(void)                     /* prio 0x40, ~730 us: wakes the contender */
{
    DT_CLR = 1;
    if (!running) return;
    BaseType_t w = pdFALSE; vTaskNotifyGiveFromISR(ct, &w); portYIELD_FROM_ISR(w);
}
static void hi_task(void *p)                        /* prio 4: never touches the shared data */
{
    (void)p;
    for (;;) { ulTaskNotifyTake(pdTRUE, portMAX_DELAY); if (running) add(&s_hi, timer0_elapsed()); }
}
static void ct_task(void *p)                        /* prio 3: needs the same shared data */
{
    (void)p;
    for (;;) {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
        lock(); uint32_t v = DT_LOAD - DT_VAL; spin_us(2); unlock();
        if (running) add(&s_ct, v);
    }
}
static void lo_task(void *p)                        /* prio 1: holds the section for L = 50 us */
{
    (void)p;
    uint32_t seed = 1;
    timer0_start(12500 + 7, 0x40);
    DT_CTRL = 0; DT_LOAD = 18250 - 1; NVIC_IPR(10) = 0x40; NVIC_ISER0 = 1u << 10; DT_CTRL = 0xE2;
    for (method = 0; method < 4; method++) {
        s_isr = s_hi = s_ct = (st_t){0, 0}; running = 1;
        while (s_isr.n < NS || s_ct.n < NS) {
            lock(); spin_us(50); unlock();
            seed = seed * 1103515245u + 12345u; spin_us(10 + (seed >> 16) % 30);
        }
        running = 0;
        board_printf_raw("%s: ISR entry max %u ns | unrelated hi task max %u ns | contender max %u ns\n",
                         names[method], CYC_NS(s_isr.max), CYC_NS(s_hi.max), CYC_NS(s_ct.max));
    }
    board_exit(0);
}
int main(void)
{
    m = xSemaphoreCreateMutex();
    xTaskCreate(hi_task, "hi", 512, NULL, 4, &hi);
    xTaskCreate(ct_task, "ct", 512, NULL, 3, &ct);
    xTaskCreate(lo_task, "lo", 512, NULL, 1, NULL);
    vTaskStartScheduler();
    return 1;
}
```

```text
sched_lock: ISR entry max 3680 ns | unrelated hi task max 60600 ns | contender max 69200 ns
```

그림 4 — 같은 50 µs 구간을 네 가지로 지켰을 때 세 피해자의 최대 지연(예제 8). 크리티컬 섹션은 **모두**를 L만큼 늦추고, 스케줄러 잠금은 ISR만 풀어 주고, 뮤텍스는 **경쟁자만** 늦춘다 — 대신 경쟁자는 L보다 더 오래(약 102 µs) 기다린다.

출력에서 볼 것 — 행마다 읽는다.

1. **보호 없음**이 기준선이다. ISR 진입 1.8 µs, hi는 ISR + 스위치로 13.2 µs, ct는 hi가 먼저 도는 경우까지 26.6 µs.
2. **크리티컬 섹션**: ISR 진입이 **51.1 µs** — 50 µs 구간이 끝나야 ISR이 들어온다. hi 63 µs, ct 75 µs. 무관한 태스크도, ISR도 전부 L을 낸다. A7 · C7에서 잰 "BASEPRI 50 µs 아래 kernel-aware IRQ 50.84 µs"와 거의 같은 값이다.
3. **스케줄러 잠금**: ISR 진입은 3.7 µs로 풀려났다(ISR은 막지 않으니까). 그러나 ISR이 깨운 hi는 **60.6 µs**를 기다린다. 무관한 태스크도 L을 낸다.
4. **뮤텍스**: ISR 3.9 µs, **무관한 hi 21.0 µs** — 기준선(13.2)보다 7.8 µs 늘었을 뿐 L과 무관하다(늘어난 몫은 뮤텍스 함수 안의 짧은 크리티컬 섹션과, 경합 처리 중 커널 경로). 대신 **경쟁자 ct는 101.8 µs**로 네 방법 중 가장 길다. 50 µs 구간의 남은 부분 + ct가 블록하는 경로(약 20 µs) + 넘겨주기(약 12 µs) + 그 사이 hi가 끼어든 시간(약 13~20 µs)이 쌓인 값이다.

결론은 하나의 문장이다. **뮤텍스는 비용을 그 자원을 원하는 태스크에게만 몰아준다.** 무관한 높은 태스크와 ISR의 지연을 지키는 것이 목적이면 뮤텍스가 정답이고, 경쟁자의 지연까지 짧아야 하면 구간 L 자체를 줄여야 한다(어느 도구도 경쟁자의 L을 없애 주지 않는다).

## 6. 우선순위 상속 — 맛보기만 (본론은 D3)

FreeRTOS와 Zephyr의 뮤텍스에는 **우선순위 상속(priority inheritance)**이 기본으로 들어 있다. 높은 태스크가 낮은 태스크가 쥔 뮤텍스를 기다리기 시작하면, 커널은 주인의 우선순위를 기다리는 태스크의 우선순위까지 잠시 올린다. 그러면 그 사이에 중간 우선순위 태스크가 끼어들어 주인을 굶기는 일("무한 역전")이 막히고, 주인은 빨리 일을 끝내 뮤텍스를 돌려준다. 돌려주는 순간 원래 우선순위로 내려간다. 이 노트에서 본 것은 그 현상의 증거 한 줄씩이다 — 예제 6의 `lo priority while hi waits: 3 (base 1)`, 예제 7의 `main prio while hi waits: 2 (base 5)`. 왜 이것이 필요한지(1997년 Mars Pathfinder), 상속이 못 막는 것(연쇄 블로킹, 전이적 상속, FreeRTOS가 "쥔 뮤텍스 개수"만 세서 생기는 한계), 그리고 대안인 priority ceiling(OCPP · ICPP)은 **D3**가 주인이다. 여기서는 한 가지만 기억한다. **세마포어(D1)에는 주인이 없어서 상속이 없다.** 상호 배제에 세마포어를 쓰면 안 되는 가장 큰 이유가 이것이다.

## 7. RTOS 커널 안에서는 무슨 일이 일어나나

### 7.1 FreeRTOS — 뮤텍스는 "길이 1, 항목 크기 0"인 큐다

`xSemaphoreCreateMutex()`는 매크로이고(`semphr.h:735`), 펼치면 `xQueueCreateMutex( queueQUEUE_TYPE_MUTEX )`다(재귀는 `queueQUEUE_TYPE_RECURSIVE_MUTEX` = 4, 일반은 1, `queue.h:74`, `:77`). `xQueueCreateMutex()`(`queue.c:647`)는 길이 1, 항목 크기 0인 큐를 만들고 `prvInitialiseMutex()`(`queue.c:617`)로 세 필드를 덮어쓴다.

```c
            pxNewQueue->u.xSemaphore.xMutexHolder = NULL;
            pxNewQueue->uxQueueType = queueQUEUE_IS_MUTEX;

            /* In case this is a recursive mutex. */
            pxNewQueue->u.xSemaphore.uxRecursiveCallCount = 0;

            traceCREATE_MUTEX( pxNewQueue );

            /* Start with the semaphore in the expected state. */
            ( void ) xQueueGenericSend( pxNewQueue, NULL, ( TickType_t ) 0U, queueSEND_TO_BACK );
```

마지막 줄이 재미있다. 뮤텍스는 **"항목 1개가 들어 있는 큐" = 열린 상태**로 시작해야 하므로, 만들자마자 자기 자신에게 빈 항목 하나를 send한다. take = 그 항목을 꺼냄(카운트 1 → 0), give = 다시 넣음(0 → 1). 예제 1의 "비어 있는 뮤텍스 give → `errQUEUE_FULL`"이 여기서 나온다.

`uxQueueType`은 진짜 필드가 아니라 `#define uxQueueType pcHead`, `#define queueQUEUE_IS_MUTEX NULL`(`queue.c:65`~`66`)이다. 뮤텍스는 저장 공간이 없으니 저장 영역 시작 포인터 `pcHead`가 필요 없고, 그 자리에 NULL을 넣어 "나는 뮤텍스"라는 표시로 쓴다. 그리고 큐의 `pcTail` · `pcReadFrom` 자리(union `u`)를 뮤텍스는 `xMutexHolder` · `uxRecursiveCallCount`로 쓴다. 메모리 한 바이트도 더 쓰지 않고 큐 구조체를 뮤텍스로 재활용한 것이다.

| 단계 | 함수 (파일) | 하는 일 |
|---|---|---|
| take, 열려 있음 | `xQueueSemaphoreTake()` (`queue.c:1659`) | 크리티컬 섹션 안에서 `uxMessagesWaiting` 1 → 0, `xMutexHolder = pvTaskIncrementMutexHeldCount()` (현재 TCB를 돌려주며 `uxMutexesHeld++`, `tasks.c:7772`) |
| take, 잠겨 있음 | 같은 함수의 블록 경로 | `xTaskPriorityInherit(xMutexHolder)` (`tasks.c:6745`)로 주인 우선순위 올림 → `vTaskPlaceOnEventList(&xTasksWaitingToReceive, ticks)` → `xTaskResumeAll()` + yield |
| take, 시간 초과 | 같은 함수 | 상속이 있었다면 `vTaskPriorityDisinheritAfterTimeout()` (`tasks.c:6942`) — 남은 대기자 중 최고 우선순위까지만 내림 |
| give | `xQueueGenericSend()` (`queue.c:949`) → `prvCopyDataToQueue()` (`queue.c:2395`) | `xTaskPriorityDisinherit(xMutexHolder)` (`tasks.c:6848`) → `xMutexHolder = NULL` → 카운트 0 → 1 → 대기자 중 최고 우선순위를 ready로 |
| give 안의 검사 | `xTaskPriorityDisinherit()` | `configASSERT( pxTCB == pxCurrentTCB )` (6861), `configASSERT( pxTCB->uxMutexesHeld )` (6862) — 소유권 검사의 전부 |
| 재귀 take / give | `xQueueTakeMutexRecursive()` (`queue.c:818`) / `xQueueGiveMutexRecursive()` (`queue.c:759`) | 주인 = 나면 카운터만, 아니면 일반 take로. give는 주인 아니면 `pdFAIL`, 카운터가 0이 될 때만 진짜 send |

소스를 읽다 보면 놀라운 점 세 가지가 보인다.

1. **필드 이름은 `xMutexHolder`다.** 예전 버전과 많은 블로그 글은 `pxMutexHolder`라고 쓰는데, V11의 `SemaphoreData_t`(`queue.c:74`~`78`) 필드는 `xMutexHolder`다. `xQueueGiveMutexRecursive()`의 주석에는 아직 옛 이름 `pxMutexHolder`가 남아 있다. kernel-aware 디버거 스크립트를 쓸 때 주의한다.
2. **소유권 검사는 API가 아니라 상속 해제 함수 안의 assert다.** 그래서 `configASSERT`를 끄면 검사가 통째로 사라진다(예제 1). 반면 재귀 give는 API 안에서 직접 비교하므로 assert와 무관하게 `pdFAIL`이다(예제 3).
3. **TCB는 쥔 뮤텍스의 "목록"이 아니라 "개수"만 센다**(`uxMutexesHeld`). 그래서 상속받은 우선순위는 **쥔 뮤텍스를 전부 돌려줘야** 원래대로 내려간다(`xTaskPriorityDisinherit`의 "Only disinherit if no other mutexes are held"). 그리고 태스크를 지울 때(`vTaskDelete`) 커널은 그 태스크가 어떤 뮤텍스를 쥐었는지 **알 방법이 없다** — 예제 9의 원인이다. 그 한계가 상속 정확도에 미치는 영향은 D3에서 본다.

그림 7 — Zephyr `z_impl_k_mutex_lock()`(`kernel/mutex.c:107`)의 흐름. 상속 관련 줄은 `#if (CONFIG_PRIORITY_CEILING < K_LOWEST_THREAD_PRIO)` 안에 있다. 기본값 `CONFIG_PRIORITY_CEILING=-128`이면 켜져 있고, 이 값을 idle 우선순위 이상으로 올리면 상속이 꺼진다. 이름과 달리 이것은 priority ceiling 프로토콜(D3)이 아니라 "상속으로 올라갈 수 있는 상한"이다.

unlock(`kernel/mutex.c:230`)에서 볼 것은 두 가지다.

- `lock_count > 1`이면 카운터만 내리고 끝난다 — **스핀락도 잡지 않는다**(주인만 이 필드를 바꾸므로).
- 마지막 unlock은 `new_owner = z_unpend_first_thread(&mutex->wait_q); mutex->owner = new_owner;`로 **다음 주인을 unlock 안에서 정해 버린다.** 기다리던 스레드는 깨어날 때 이미 주인이다(`lock_count`도 1 그대로 넘어간다). FreeRTOS는 다르다. give는 카운트를 1로 되돌리고 대기자를 ready로 옮길 뿐이고, 대기자는 깨어나서 `xQueueSemaphoreTake()`의 `for (;;)` 루프를 다시 돌며 take를 **다시 시도**한다.

이 차이가 드러나는 장면을 직접 본다.

### 7.3 예제 12 — 놓자마자 다시 잡으면: FreeRTOS는 "새치기", Zephyr는 "이미 넘겨줌"

무엇을 확인하나: 우선순위가 **높은** 주인이 뮤텍스를 놓자마자(그 사이 CPU를 내주지 않고) 다시 잡으면, 기다리던 **낮은** 태스크는 어떻게 되나.

```c
/* ex12a — FreeRTOS: after give, can a HIGHER-prio giver take the mutex back before the waiter runs? */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
static SemaphoreHandle_t m;
static const char *nm(TaskHandle_t h) { return h ? pcTaskGetName(h) : "(none)"; }
static void waiter(void *p)                          /* prio 1 */
{
    (void)p;
    board_printf_raw("W: waiting for m\n");
    xSemaphoreTake(m, portMAX_DELAY);
    board_printf_raw("W: finally got m at tick %u\n", (unsigned)xTaskGetTickCount());
    board_exit(0);
}
static void giver(void *p)                           /* prio 3 */
{
    (void)p;
    xSemaphoreTake(m, portMAX_DELAY);
    xTaskCreate(waiter, "W", 512, NULL, 1, NULL);
    vTaskDelay(1);                                   /* W runs and blocks on m */
    xSemaphoreGive(m);                               /* W becomes ready, but G keeps the CPU */
    BaseType_t again = xSemaphoreTake(m, 0);
    board_printf_raw("G: give then take(0) -> %d, holder=%s (barging)\n", (int)again, nm(xSemaphoreGetMutexHolder(m)));
    vTaskDelay(3);
    xSemaphoreGive(m);
    board_printf_raw("G: gave again at tick %u\n", (unsigned)xTaskGetTickCount());
    vTaskSuspend(NULL);
}
int main(void)
{
    m = xSemaphoreCreateMutex();
    xTaskCreate(giver, "G", 512, NULL, 3, NULL);
    vTaskStartScheduler();
    return 1;
}
```

```c
/* ex12b — Zephyr: k_mutex_unlock hands ownership straight to the waiter */
#include <zephyr/kernel.h>
static K_MUTEX_DEFINE(m);
static void w_fn(void *a, void *b, void *c)              /* prio 7 (lower than main) */
{
    ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
    printk("W: waiting for m\n");
    k_mutex_lock(&m, K_FOREVER);
    printk("W: got m at %lld ms\n", k_uptime_get());
    k_mutex_unlock(&m);
}
K_THREAD_DEFINE(w, 1024, w_fn, NULL, NULL, NULL, 7, 0, K_TICKS_FOREVER);
int main(void)
{
    k_thread_name_set(w, "W");
    k_thread_priority_set(k_current_get(), 3);
    k_mutex_lock(&m, K_FOREVER);
    k_thread_start(w);
    k_msleep(1);                                         /* W runs and blocks on m */
    k_mutex_unlock(&m);                                  /* W is now the owner, main still runs */
    int r = k_mutex_lock(&m, K_NO_WAIT);
    printk("main: unlock then lock(K_NO_WAIT) -> %d, owner=%s (handoff)\n", r,
           m.owner ? k_thread_name_get(m.owner) : "(none)");
    k_msleep(3);
    return 0;
}
```

```text
W: waiting for m
G: give then take(0) -> 1, holder=G (barging)
G: gave again at tick 4
W: finally got m at tick 4
[board_exit] code=0
[exit=0]
```

```text
W: waiting for m
main: unlock then lock(K_NO_WAIT) -> -16, owner=W (handoff)
W: got m at 2 ms
```

출력에서 볼 것: FreeRTOS에서는 G가 give 직후 take(0)에 **성공**했다. W는 ready 상태였지만 아직 실행되지 않았으니 뮤텍스는 "열려 있는" 상태였고, G가 새치기(barging)했다. W는 깨어나 다시 시도했다가 또 잠들고, G가 3 tick 뒤에 다시 놓은 뒤에야(tick 4) 얻었다. Zephyr에서는 unlock 순간 **주인이 이미 W로 바뀌어 있어서** main의 lock(K_NO_WAIT)은 `-EBUSY`였다.

어느 쪽이 좋은가? 새치기 방식은 처리량이 좋다(높은 태스크가 연달아 쓸 때 스위치가 없다). 직접 넘겨주기는 공정하다(기다린 태스크가 반드시 다음 차례다). 실무 함의는 이것이다. FreeRTOS에서 높은 태스크가 `while (1) { take; 짧은 일; give; }`처럼 쉬지 않고 돌면 낮은 대기자는 **영원히 못 얻을 수 있다**(기아, D9). 그런 루프 안에는 give 뒤에 블록하는 지점(delay, 큐 대기)이 반드시 있어야 한다.

## 8. 실무에서 다시 보기

### 8.1 드론 FC — IMU와 기압계가 나눠 쓰는 I2C 버스 (예제 10)

예를 들어 드론 비행 제어기라면 IMU(1 kHz, 읽기 80 µs)와 기압계(100 Hz, "변환 시작 명령 50 µs → 변환 2 ms 대기 → 결과 읽기 300 µs")가 I2C 버스 하나를 쓴다. 기압계 드라이버를 쓰는 방법은 두 가지다.

- **나쁜 설계**: 버스를 잡고, 명령 보내고, **잡은 채로** 2 ms 기다리고, 읽고, 놓는다. 코드가 단순하고 "트랜잭션이 원자적"이라 안심이 된다.
- **좋은 설계**: 명령 보내고 **놓고**, 2 ms 기다리고, 다시 잡고 읽고 놓는다. 변환 중에는 버스가 놀고 있으니 다른 장치가 쓰게 둔다(SSD의 tR 동안 채널을 다른 다이에 주는 것과 같다).

무엇을 확인하나: IMU는 데이터 레디 인터럽트(TIMER0, 999.56 µs — tick과 위상이 조금씩 어긋나게)로 깨어나고, 버스 예산은 1 tick이다. 400 주기 동안 IMU가 버스를 기다린 시간의 분포를 두 설계로 잰다.

```c
/* ex10 — drone FC: IMU (1 kHz) and baro share one I2C bus mutex; good vs bad baro design */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "d2.h"
#ifndef BAD
#define BAD 0
#endif
#define NCYC 400
static SemaphoreHandle_t i2c;
static uint32_t hist[5], wmax, miss;                /* bins: <10, <100, <400, >=400 us, timeout */
static uint64_t wsum;
static void xfer(uint32_t us) { spin_us(us); }      /* stands in for a polled I2C transaction */
static TaskHandle_t h_imu;
void TIMER0_IRQHandler(void)                        /* IMU data-ready, ~1 kHz, not tick-aligned */
{
    TIMER_INTCLR(TIMER0_BASE) = 1;
    BaseType_t w = pdFALSE; vTaskNotifyGiveFromISR(h_imu, &w); portYIELD_FROM_ISR(w);
}
static void imu_task(void *p)                       /* prio 4: 80 us read, bus budget 1 tick */
{
    (void)p;
    timer0_start(24989, 0x40);                       /* 999.56 us: phase drifts vs the 1 ms tick */
    for (int n = 0; n < NCYC; n++) {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
        uint32_t t0 = CYC();
        if (xSemaphoreTake(i2c, 1) != pdTRUE) { miss++; hist[4]++; continue; }
        uint32_t w = (CYC() - t0) / 25;              /* us waited for the bus */
        xfer(80);
        xSemaphoreGive(i2c);
        wsum += w; if (w > wmax) wmax = w;
        hist[w < 10 ? 0 : w < 100 ? 1 : w < 400 ? 2 : 3]++;
    }
    board_printf_raw("%s: IMU wait avg %u us max %u us | <10:%u <100:%u <400:%u >=400:%u timeout:%u\n",
                     BAD ? "BAD (hold across delay)" : "GOOD (release during conversion)",
                     (unsigned)(wsum / (NCYC - miss)), wmax, hist[0], hist[1], hist[2], hist[3], hist[4]);
    board_exit(0);
}
```

출력에서 볼 것:

1. 좋은 설계의 최악 대기 **304 µs**는 "다른 주인의 최장 보유 구간"(기압계 읽기 300 µs)과 정확히 같다. **뮤텍스 대기의 최악값 = 다른 주인들의 최장 보유 구간 + 오버헤드**다. 이 값이 IMU 주기(1 ms) 안에 들어가므로 이 설계는 안전하다. 더 줄이려면 기압계 읽기를 쪼개거나(300 µs → 짧은 트랜잭션 여러 번) DMA로 바꾼다.
2. 나쁜 설계는 기압계가 2 ms 변환 대기 동안 버스를 쥐고 있어서, 그 구간에 걸린 IMU 주기는 1 tick 예산 안에 못 얻고 **35번 샘플을 잃었다**(10 ms마다 2~3 주기). 우선순위 상속은 여기서 아무 도움이 안 된다. 기압계는 잠들어(블록) 있으니 우선순위를 올려도 더 빨리 끝나지 않는다. **뮤텍스를 쥔 채 블록하는 것**은 상속이 해결하지 못하는 지연이다.

### 8.2 공유 UART 로거 — 뮤텍스보다 게이트키퍼

여러 태스크가 `printf`처럼 UART로 로그를 찍으면 문자가 섞인다. 가장 쉬운 고침은 UART 뮤텍스지만, 계산해 보면 문제가 보인다. 115200 bps 8N1에서 한 글자는 10 비트 = 86.8 µs이고, 80자 한 줄은 **6.9 ms**다. 폴링 방식 드라이버라면 로그 한 줄을 찍는 태스크가 6.9 ms 동안 뮤텍스를 쥔다. 제어 루프 태스크가 로그를 한 줄 찍으려다 다른 태스크의 로그 뒤에서 6.9 ms를 기다리면 1 kHz 루프가 7주기를 놓친다.

그래서 로그는 **게이트키퍼(gatekeeper) 태스크**가 정석이다. UART를 만지는 태스크는 단 하나(낮은 우선순위)이고, 다른 태스크는 메시지를 큐에 넣고(복사 수 µs) 바로 돌아간다. 자원에 주인이 하나뿐이니 뮤텍스가 필요 없다. 구현과 큐가 찼을 때의 정책(버림, 카운트)은 D7, 큐 깊이 설계는 D4에서 다룬다. 뮤텍스는 "버스 트랜잭션처럼 **호출한 태스크가 결과를 기다려야 하는**" 자원에 남겨 둔다.

### 8.3 SPI 플래시 — 장치 잠금과 버스 잠금, 두 단계

블랙박스 로거가 SPI 플래시에 쓰는데, 같은 SPI 버스에 IMU도 있다고 하자. 플래시 섹터 erase는 수십 ms 걸리고(데이터시트 값, 칩마다 다름), 그동안 플래시는 status 레지스터의 BUSY 비트만 응답한다.

- **버스 뮤텍스**는 SPI 트랜잭션 하나(수 µs ~ 수백 µs) 동안만 잡는다. erase 명령을 보낸 뒤 바로 놓는다.
- **장치 뮤텍스**(플래시 전용)는 erase가 끝날 때까지(BUSY 폴링 + `vTaskDelay`) 쥔다. 다른 태스크가 erase 중인 플래시에 읽기를 보내지 않게 막는 것은 버스가 아니라 장치의 일이다.
- 두 뮤텍스를 다 잡아야 할 때는 **항상 같은 순서**(장치 → 버스)로 잡는다. 순서가 엇갈리면 ABBA 데드락이다(D9, EL A8 §10).

```c
/* not executed — two-level locking for an SPI NOR flash on a shared SPI bus */
int flash_erase_sector(uint32_t addr)
{
    xSemaphoreTake(flash_mtx, portMAX_DELAY);       /* device: held for the whole erase (tens of ms) */
    spi_cmd(CMD_WREN, 0);                           /* each spi_cmd() takes/gives spi_bus_mtx inside */
    spi_cmd(CMD_SE, addr);
    while (spi_read_status() & SR_BUSY)             /* bus is free between polls */
        vTaskDelay(pdMS_TO_TICKS(1));
    xSemaphoreGive(flash_mtx);
    return 0;
}
```

이 구조에서 IMU의 최악 버스 대기는 "SPI 트랜잭션 하나"이지 "erase 하나"가 아니다. 예제 10의 좋은 설계와 같은 원리다.

### 8.4 SSD 컨트롤러 펌웨어 (Don의 경험)

SSD에서 NAND 채널 arbitration을 RTOS 언어로 옮기면 이렇게 대응한다.

| SSD 펌웨어 | RTOS 뮤텍스 설계 |
|---|---|
| 채널 grant를 받은 명령 시퀀스만 채널을 놓는다 | 소유권 — 주인만 give |
| tR · tPROG 대기 동안 채널을 놓고 다른 다이 명령을 끼운다 | 블록하는 대기 동안 뮤텍스를 놓는다 (§8.1 좋은 설계) |
| 호스트 읽기가 GC보다 먼저 grant를 받는다 | 대기 목록이 우선순위 순 + 상속 |
| 채널 grant 타임아웃 → 채널 리셋 · 명령 재시도 | take 타임아웃 → 세고, 남기고, 버스 복구로 올림 (§3.3) |
| 멀티코어 FW에서 HW 세마포어로 코어 간 자원 보호 | 단일 코어 RTOS에서는 뮤텍스. SMP RTOS에서는 커널이 스핀락을 함께 쓴다 (C10) |

다른 점은 "누가 중재하나"다. SSD에서는 HW arbiter나 FW 스케줄러가 grant 순서를 **명시적으로** 정한다. RTOS 뮤텍스는 대기 목록의 우선순위 순서 + (FreeRTOS라면) 새치기(§7.3)로 **암묵적으로** 정해진다. 공정성이 중요한 자원(예: 여러 태스크가 같은 비율로 써야 하는 버스)이라면 뮤텍스 대신 게이트키퍼가 요청 순서를 명시적으로 정하는 편이 SSD 방식에 더 가깝다.

### 8.5 예제 9 — 뮤텍스를 쥔 태스크를 지우면

무엇을 확인하나: 워커 W가 뮤텍스를 잡은 상태에서 `vTaskDelete(W)`. 그 뒤 idle 태스크가 W의 TCB를 해제하고, **같은 크기**의 새 태스크 X를 만들면 heap_4가 그 블록을 다시 준다.

```c
/* ex9 — deleting a task that holds a mutex: the mutex stays locked, and the holder pointer goes stale */
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
static SemaphoreHandle_t m;
static TaskHandle_t w, x;
static void worker(void *p) { (void)p; xSemaphoreTake(m, portMAX_DELAY); for (;;) vTaskDelay(100); }
static void newbie(void *p)                          /* never took m */
{
    (void)p;
    board_printf_raw("X: am I the holder? %s -> calling xSemaphoreGive(m)\n",
                     xSemaphoreGetMutexHolder(m) == xTaskGetCurrentTaskHandle() ? "YES (!)" : "no");
    BaseType_t r = xSemaphoreGive(m);
    board_printf_raw("X: give returned %d\n", (int)r);
    board_exit(0);
}
static void boss(void *p)                            /* prio 3 */
{
    (void)p;
    xTaskCreate(worker, "W", 256, NULL, 2, &w);
    vTaskDelay(2);                                   /* W takes m */
    board_printf_raw("boss: holder=%s (%x)\n", pcTaskGetName(xSemaphoreGetMutexHolder(m)),
                     (unsigned)xSemaphoreGetMutexHolder(m));
    vTaskDelete(w);                                  /* W dies with m locked */
    vTaskDelay(5);                                   /* idle task frees W's TCB + stack */
    TickType_t t0 = xTaskGetTickCount();
    BaseType_t ok = xSemaphoreTake(m, 10);
    board_printf_raw("boss: take after delete -> %d after %u ticks, holder ptr still %x\n",
                     (int)ok, (unsigned)(xTaskGetTickCount() - t0), (unsigned)xSemaphoreGetMutexHolder(m));
    xTaskCreate(newbie, "X", 256, NULL, 1, &x);      /* same size: heap_4 reuses W's block */
    board_printf_raw("boss: new task X handle = %x\n", (unsigned)x);
    vTaskDelay(5);
    for (;;) vTaskDelay(100);
}
int main(void)
{
    m = xSemaphoreCreateMutex();
    xTaskCreate(boss, "boss", 512, NULL, 3, NULL);
    vTaskStartScheduler();
    return 1;
}
```

```text
boss: holder=W (20001cf0)
boss: take after delete -> 0 after 10 ticks, holder ptr still 20001cf0
boss: new task X handle = 20001cf0
X: am I the holder? YES (!) -> calling xSemaphoreGive(m)

[configASSERT] /var/rtoslab/src/FreeRTOS-Kernel/tasks.c:6862
[board_exit] code=253
[exit=1]
```

출력에서 볼 것: W가 죽은 뒤에도 뮤텍스는 **영원히 잠겨 있다**(boss의 take가 10 tick 뒤 실패). 주인 포인터 0x20001cf0은 이미 해제된 메모리를 가리킨다. 그리고 새 태스크 X가 **같은 주소**를 받자, 커널 눈에는 X가 주인이 됐다. X가 give하자 첫 assert(`pxTCB == pxCurrentTCB`)는 **통과**했고, 두 번째 assert(`uxMutexesHeld`가 0이 아님, 6862)에서야 잡혔다 — X의 TCB는 새로 만들어져 쥔 개수가 0이었기 때문이다. assert가 꺼져 있었다면 `uxMutexesHeld`가 0에서 빼져 최댓값으로 넘어가고, 그 뒤 X의 상속 해제는 영원히 일어나지 않는다. Zephyr도 같다. `kernel/thread.c`와 `kernel/sched.c`에는 뮤텍스를 언급하는 줄이 하나도 없다 — 스레드를 abort해도 쥔 뮤텍스는 풀리지 않는다. **규칙: 다른 태스크를 밖에서 지우지 않는다.** 태스크가 끝나야 하면 플래그 · 통지로 "스스로 정리하고 끝내라"고 요청하고, 태스크는 쥔 것을 다 놓은 뒤 `vTaskDelete(NULL)`로 스스로 끝낸다.

## 10. 면접에서 이렇게 말한다

**Q.** What is the difference between a mutex and a binary semaphore?

**A.** 뮤텍스에는 주인이 있다. 잡은 태스크만 놓을 수 있고, 주인이 있으니 커널이 우선순위 상속을 할 수 있고 재귀 잠금도 가능하다. 이진 세마포어는 주인이 없는 깃발이라 ISR이 주고 태스크가 받는 신호용이다. 상호 배제에는 뮤텍스, 이벤트 신호에는 세마포어다.

> A mutex has an owner: only the task that took it may give it back, and because the kernel knows the owner it can apply priority inheritance and support recursive locking. A binary semaphore has no owner; it is a flag, typically given by an ISR and taken by a task. I use mutexes for mutual exclusion and semaphores or task notifications for signalling.

**꼬리 질문**: "FreeRTOS에서 주인이 아닌 태스크가 give하면?" → `configASSERT`가 켜져 있으면 `xTaskPriorityDisinherit` 안의 assert에 걸리고, 꺼져 있으면 성공해 버려서 두 태스크가 동시에 임계 구역에 들어간다(예제 1).

**Q.** Why can't you use a mutex in an ISR?

**A.** 세 가지다. ISR은 태스크가 아니라서 주인이 될 수 없다 — 커널은 끼어들림을 당한 태스크를 주인으로 적는다. ISR은 블록할 수 없어서 기다릴 수 없다. 그리고 우선순위 상속은 스케줄러 우선순위를 올리는 것인데 ISR의 우선순위는 NVIC 하드웨어라 올릴 수 없다. FreeRTOS는 `vPortEnterCritical`의 VECTACTIVE assert와 `xQueueGiveFromISR`의 assert로 잡고, Zephyr는 `CONFIG_ASSERT`에서 `arch_is_in_isr()` assert로 잡는다.

> Three reasons. Ownership: an ISR is not a task, so the kernel would record whichever task was interrupted as the owner. Blocking: an ISR cannot sleep, so it cannot wait for a locked mutex. Inheritance: the kernel can raise a task's priority, but not an ISR's hardware priority. If an ISR needs a bus, it should signal a task with a semaphore or notification, or defer the work, and that task takes the mutex.

**Q.** How do you choose between a mutex, a critical section and a scheduler lock?

**A.** "무엇을 막아야 하나"와 "구간 안에서 블록하나"로 고른다. ISR과 공유하면 크리티컬 섹션(또는 락 없는 구조). 블록이 들어가면 뮤텍스만 가능하다. 몇 줄짜리면 크리티컬 섹션이 가장 싸다 — 제가 잰 값으로 쌍이 0.9 µs, 뮤텍스 쌍은 5.9 µs다. 그 사이는 무관한 높은 태스크를 지켜야 하는지로 갈린다. 같은 50 µs 구간을 쟀을 때 크리티컬 섹션은 ISR까지 51 µs 늦췄고, 스케줄러 잠금은 무관한 태스크를 61 µs 늦췄고, 뮤텍스는 무관한 태스크를 21 µs로 지켰지만 경쟁자는 102 µs를 기다렸다.

> I start from what must be excluded and whether the section blocks. Shared with an ISR: a short critical section or a lock-free structure. Contains blocking I/O: a mutex, nothing else is legal. A few instructions: a critical section, because it is about six times cheaper than a mutex pair. In between, the question is whether unrelated high-priority tasks may be delayed by the section length. A mutex only delays tasks that want the same resource, but those contenders pay the section plus roughly thirty microseconds of block-and-handoff overhead on a Cortex-M3 class part.

**Q.** When is a recursive mutex justified?

**A.** 서드파티 스택이 요구하거나, 잠금을 쥔 채 사용자 콜백을 불러야 하는 드물게 정당한 경우뿐이다. 대부분은 "누가 언제 잠그는지 정하지 않은" 설계 냄새다. 공개 함수는 잠그고 내부 `_locked()` 함수는 잠그지 않게 나누는 것이 정석이다. 재귀는 불변식이 깨진 상태로 다시 들어가는 버그를 숨기고, Take/Give 짝이 틀리면 카운터가 남아 영원히 안 풀린다.

> Rarely: when a third-party stack's porting layer demands it, or when a callback may re-enter the same API. Usually it is a design smell. I split public functions that lock from internal `_locked` helpers that assume the lock is held, and assert the holder in those helpers. Recursive locking can hide re-entering a data structure whose invariant is temporarily broken.

**Q.** What timeout do you put on a mutex take, and what do you do when it expires?

**A.** 다른 주인들의 최악 보유 시간 + 선점 여유로 정하고, 내 주기보다 작아야 한다. 1 kHz 루프에 2 ms를 기다리면 기다리는 동안 주기를 놓친다. 시간 초과는 버그 신호라서 이번 주기 대처(지난 샘플), 카운트, 로그(주인 이름 포함), 연속이면 버스 복구 같은 상위 조치로 올린다. `portMAX_DELAY`는 마감 없는 배경 태스크에만 쓰고 워치독이 받쳐 줘야 한다.

> I derive it from the worst-case hold time of the other owners plus preemption, and it must be shorter than my own period. On expiry I degrade for this cycle, count it, log the current holder, and escalate after consecutive failures, for example an I2C bus recovery. `portMAX_DELAY` is only for background tasks, backed by a task watchdog.

**Q.** What happens if a task holding a mutex is deleted?

**A.** FreeRTOS도 Zephyr도 풀어 주지 않는다. FreeRTOS TCB는 쥔 뮤텍스의 개수만 세고 목록이 없다. 뮤텍스는 영원히 잠기고 주인 포인터는 해제된 TCB를 가리킨다. 제가 해 보니 같은 크기의 새 태스크가 그 메모리를 다시 받아서 커널이 그 태스크를 주인으로 착각했다. 그래서 태스크는 밖에서 지우지 않고, 스스로 정리하고 끝나게 한다.

> Neither FreeRTOS nor Zephyr releases it. FreeRTOS only counts held mutexes per task, it has no list. The mutex stays locked forever and the holder pointer dangles; in my test a new task reused the freed TCB address and the kernel believed it was the owner. So tasks are asked to clean up and delete themselves rather than being deleted from outside.

**Q.** Does a mutex in FreeRTOS hand ownership directly to the waiting task?

**A.** 아니다. give는 뮤텍스를 열고 대기자를 ready로 옮길 뿐이고, 대기자는 깨어나서 다시 take한다. 그래서 give한 태스크가 더 높은 우선순위면 바로 다시 잡을 수 있다(새치기). Zephyr의 `k_mutex_unlock`은 unlock 안에서 다음 주인을 정해 버려서, 놓자마자 다시 잡으면 `-EBUSY`다. 높은 태스크가 쉬지 않고 take/give를 반복하면 FreeRTOS에서는 낮은 대기자가 굶을 수 있다.

> No. Give reopens the mutex and readies the highest-priority waiter, which then retries the take, so a higher-priority giver can immediately retake it. Zephyr's unlock picks the next owner inside unlock, so an immediate re-lock returns `-EBUSY`. In FreeRTOS that means a tight take/give loop in a high-priority task can starve a lower waiter.

## 11. 직접 해보기

1. **개념** — 예제 1의 assert-끔 빌드에서 A가 마지막 give를 했을 때 B의 TCB `uxMutexesHeld`는 몇이 되나? 정답/힌트: B가 take할 때 B의 개수가 1이 되고, A의 give는 주인(B)에 대해 `xTaskPriorityDisinherit`를 부르므로 B의 개수가 0이 된다. B는 쥐고 있다고 믿지만 커널 장부에서는 0개다.
2. **코드** — 예제 3에 `xSemaphoreTakeRecursive(m, 0)`(일반 뮤텍스 `m`에 재귀 API)를 넣어 보라. 동작하나? 정답/힌트: `xQueueTakeMutexRecursive()`는 큐 타입을 검사하지 않고 주인 비교만 한다. 일반 뮤텍스도 재귀처럼 동작한다 — 그래서 더더욱 짝을 지켜야 한다.
3. **측정** — 예제 6에 이진 세마포어(`xSemaphoreCreateBinary`) take+give 쌍과 task notification(`xTaskNotifyGive` + `ulTaskNotifyTake(pdTRUE, 0)`) 쌍을 추가해 뮤텍스 쌍과 비교하라. 정답/힌트(직접 재서 확인할 것): 세마포어는 같은 큐 경로이지만 주인 기록 · 상속 해제가 없으니 뮤텍스보다 조금 싸야 하고, 통지는 큐를 거치지 않으니 훨씬 싸야 한다(D5).
4. **측정** — 예제 8에서 L을 10 µs와 200 µs로 바꿔 네 방법의 표를 다시 만들어라. 경쟁자 열에서 뮤텍스의 "고정 오버헤드"(L을 뺀 값)가 L과 무관하게 거의 일정한지 확인하라. 정답/힌트: 블록 경로 + 넘겨주기 + hi 끼어듦으로 수십 µs가 L과 무관하게 붙는다. L이 작을수록 뮤텍스가 상대적으로 손해다.
5. **코드** — 예제 10의 나쁜 설계에서 IMU 예산을 `xSemaphoreTake(i2c, 0)`(기다리지 않음)으로 바꾸면 타임아웃 수와 IMU 루프의 지터는 어떻게 바뀌나? 정답/힌트: 못 잡는 주기는 바로 건너뛰므로 기다리느라 다음 주기를 밀어내는 일은 없어진다. 대신 손실 수는 버스가 막힌 시간 비율만큼 그대로 남는다 — 근본 해결은 설계(놓기)다.
6. **Zephyr** — 예제 7을 `CONFIG_PRIORITY_CEILING=15`(idle 우선순위 이상)로 빌드하고 "main prio while hi waits"를 다시 보라. 정답/힌트: 상속 코드가 `#if`로 빠져서 main은 5 그대로다. 상속을 끈 커널에서 경쟁자 지연이 어떻게 나빠지는지는 D3의 실험 주제다.
7. **설계** — 드론 FC에 IMU 2개(SPI1), 기압계 · 자력계(I2C1), 블랙박스 플래시(SPI1과 공유)가 있다. 필요한 뮤텍스 목록, 각 뮤텍스를 쥐는 최악 시간, 잡는 순서 규칙을 표로 만들어라. 정답/힌트: 버스마다 하나(SPI1, I2C1) + 플래시 장치 하나. 순서는 장치 → 버스로 고정. SPI1의 최악 보유는 플래시 page program 한 번(트랜잭션)이지 erase 전체가 아니다(§8.3).

## 12. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| mutex | 상호 배제 잠금 | 주인 이름표가 붙은 열쇠 하나. 잡은 태스크만 놓는다 |
| owner / holder | 주인 | 뮤텍스를 쥔 태스크. FreeRTOS `xMutexHolder`, Zephyr `owner` |
| recursive mutex | 재귀 뮤텍스 | 주인이 또 잡으면 카운터만 올린다. 카운터가 0이 될 때 풀린다 |
| `uxRecursiveCallCount` / `lock_count` | 재귀 카운터 | FreeRTOS / Zephyr의 재귀 깊이 필드 |
| self-deadlock | 자기 교착 | 자기가 쥔 뮤텍스를 자기가 기다림 |
| timeout budget | 대기 예산 | take가 기다릴 최대 시간. 다른 주인의 최악 보유 시간으로 정한다 |
| priority inheritance | 우선순위 상속 | 기다리는 높은 태스크의 우선순위를 주인에게 잠시 빌려준다 (D3) |
| `uxMutexesHeld` | 쥔 뮤텍스 개수 | FreeRTOS TCB 필드. 목록이 아니라 개수라서 0이 될 때만 상속 해제 |
| `owner_orig_prio` | 원래 우선순위 | Zephyr가 상속 전에 기억해 두는 주인의 우선순위 |
| barging | 새치기 | give 직후 대기자가 실행되기 전에 다른 태스크가 다시 잡는 것 (FreeRTOS) |
| direct handoff | 직접 넘겨주기 | unlock이 다음 주인을 바로 정함 (Zephyr) |
| critical section | 크리티컬 섹션 | 인터럽트(BASEPRI 이하)를 막아 구간을 보호 (C7) |
| scheduler lock | 스케줄러 잠금 | 태스크 전환만 막는다. ISR은 돈다 (C7) |
| gatekeeper task | 게이트키퍼 태스크 | 자원을 만지는 유일한 태스크. 다른 태스크는 큐로 요청 (D7) |
| `CHECKIF` | Zephyr 런타임 검사 매크로 | Kconfig에 따라 `if`, assert, 또는 아무것도 아님으로 바뀐다 |
| VECTACTIVE | ICSR 하위 8비트 | 지금 처리 중인 예외 번호. 0이 아니면 ISR 안 |

## 13. 요약 & 체크리스트

뮤텍스는 "열쇠 하나 + 주인 이름표"다. 이름표 덕분에 주인만 놓을 수 있고(소유권), 주인이 또 잡을 수 있고(재귀), 커널이 주인을 올려 줄 수 있다(상속, D3). 그러나 이름표 검사는 생각보다 얇다. FreeRTOS는 give 경로의 assert 한 줄(`tasks.c:6861`)이 전부라 `configASSERT`를 끄면 두 태스크가 동시에 임계 구역에 들어가고, Zephyr는 `-EPERM`을 주지만 `CONFIG_NO_RUNTIME_CHECKS`면 사라지고 안 잠긴 뮤텍스 unlock이 NULL 역참조가 된다. ISR은 주인이 될 수 없고 블록할 수 없어서 뮤텍스를 쓸 수 없다. 타임아웃 예산은 다른 주인의 최악 보유 시간으로 정하고, 내 주기보다 짧아야 하며, 시간 초과는 세고 남기고 올린다. 비용은 경합 없는 쌍 5.9 µs(크리티컬 섹션의 6.6배), 경합마다 약 33 µs이고, 그 비용은 **같은 자원을 원하는 태스크만** 낸다 — 무관한 높은 태스크와 ISR은 지켜진다. 가장 흔한 실무 실수는 뮤텍스를 쥔 채 블록하는 것이고(예제 10: 샘플 35개 손실), 이것은 상속으로도 고쳐지지 않는다.

- [ ] 뮤텍스와 이진 세마포어의 차이를 "주인" 한 단어로 설명하고, 그 결과(상속 · 재귀 · ISR 금지)를 이어 말할 수 있다
- [ ] FreeRTOS에서 주인 아닌 give가 어디서 잡히는지(`xTaskPriorityDisinherit`의 assert) 말하고, assert를 끄면 무슨 일이 생기는지 보였다
- [ ] Zephyr `k_mutex_lock` / `unlock`의 반환값 다섯 가지(0, `-EBUSY`, `-EAGAIN`, `-EPERM`, `-EINVAL`)를 안다
- [ ] 재귀 뮤텍스의 카운터 동작과 "일반 give로 놓으면 카운터가 남는" 버그를 설명할 수 있다
- [ ] `_locked()` 함수 분리로 재귀 뮤텍스를 없애는 패턴을 쓸 수 있다
- [ ] 타임아웃 예산을 "다른 주인의 최악 보유 + 선점 < 내 주기"로 정하고, 시간 초과의 에러 경로 네 단계를 말할 수 있다
- [ ] ISR에서 뮤텍스가 금지인 세 가지 이유와, 대신 쓸 것(세마포어 · 통지 · 위임 · 크리티컬 섹션)을 안다
- [ ] 뮤텍스 · 크리티컬 섹션 · 스케줄러 잠금이 각각 **누구를** 기다리게 하는지 측정 숫자로 말할 수 있다
- [ ] FreeRTOS 뮤텍스가 큐(`queueQUEUE_TYPE_MUTEX`, 길이 1, 크기 0)이고 `pcHead` 자리가 뮤텍스 표시라는 것을 안다
- [ ] FreeRTOS(새치기)와 Zephyr(직접 넘겨주기)의 give/unlock 차이와 기아 위험을 설명할 수 있다
- [ ] 뮤텍스를 쥔 채 블록하는 버그를 찾아 "대기 동안 놓기"로 고칠 수 있다
- [ ] 뮤텍스를 쥔 태스크를 밖에서 지우면 안 되는 이유를 예제 9로 설명할 수 있다
