# D10. Zephyr 고유 IPC — k_fifo · k_lifo · k_stack · k_msgq · k_pipe · k_mbox와 zbus: "무엇을 넘기고, 메모리는 누가 쥐나"

> **이 노트를 다 읽으면**: Zephyr의 데이터 전달 객체 7종과 zbus를 "참조 vs 복사 · 고정 vs 가변 · ISR 가능 여부 · 수신자 수 · 동기 여부 · 메모리 소유권"의 여섯 축으로 비교해 고를 수 있다 · `k_fifo`의 "첫 word 예약" 규칙이 왜 있고, 어기면 어떻게 부서지는지(실제 BUS FAULT까지) 설명할 수 있다 · Zephyr 4.1에서 다시 만든 `k_pipe`(`k_pipe_write`/`read`/`reset`/`close`)와 `k_mbox`의 매칭·동기 전달, zbus의 listener / subscriber / msg_subscriber와 priority boost(HLP)를 소스 수준으로 말할 수 있다 · QEMU에서 객체별 1회 비용 · 전달 지연 · footprint를 직접 재서 "zbus는 공짜가 아니다"를 숫자로 보여 줄 수 있다
> **왜 필요한가**: Zephyr 기반 제품(Nordic nRF 계열, 센서 허브, 드론·로봇 보조 MCU)의 코드를 열면 FreeRTOS의 `xQueueSend` 하나 대신 `k_fifo_put`, `k_msgq_put`, `zbus_chan_pub`가 섞여 있다. 면접에서는 "k_fifo와 k_msgq의 차이는?", "zbus subscriber가 메시지를 잃을 수 있나?", "FreeRTOS 큐 코드를 Zephyr로 옮길 때 무엇을 쓰나?"가 나온다
> **Don 기준 난이도**: 링버퍼 · intrusive 리스트 · DMA 버퍼 free-list는 SSD 펌웨어에서 매일 쓴 것이다 / 새로 배울 부분은 Zephyr가 이것들을 **어떤 이름의 어떤 객체로** 나눠 놓았는지, `swap_data`로 대기자에게 직접 넘기는 커널 패턴, 4.1 pipe 재작성, zbus의 VDED · HLP · net_buf 비용
> **선행 노트**: A5(API 로제타 — FreeRTOS ↔ Zephyr 이름 대응), C1(Zephyr `_wait_q_t` · `sys_dlist`), C2(context switch 비용 — time slicing이 스위치를 비싸게 만든다), C12(커널 소스 투어). 같은 모듈의 D1(`k_sem`), D2(`k_mutex`), D4(메시지 큐 일반론과 `k_msgq` 기본), D5(`k_event` · `k_poll`), D7(`k_work`)과는 ID로만 연결한다

## 0. 큰 그림 — 왜 Zephyr에는 "큐"가 일곱 개나 있나

FreeRTOS에서 태스크끼리 데이터를 넘기는 기본 도구는 사실상 하나다. `xQueueSend`/`xQueueReceive`, 즉 **고정 크기 아이템을 복사하는 큐**다(stream/message buffer는 D5). 포인터를 넘기고 싶으면 "포인터 크기 아이템의 큐"를 만든다. Don이 SSD 펌웨어에서 쓰던 방식도 비슷했을 것이다. 명령 디스크립터는 미리 잡아 둔 풀에서 꺼내고, 큐에는 디스크립터 **인덱스나 포인터만** 넣고, 링버퍼에는 고정 크기 엔트리를 복사했다.

Zephyr는 이 선택지들을 **처음부터 서로 다른 커널 객체로** 나눠 두었다. Zephyr의 뿌리인 Wind River 코드에서 온 이름들이다(`queue.c` · `stack.c` · `msg_q.c` · `mailbox.c` 머리의 저작권이 "Wind River Systems", 2010~2016이다).

- **포인터를 넘기는** 것(0 copy): `k_fifo`, `k_lifo`, 그 밑바닥의 `k_queue`
- **값 하나(word)를 넘기는** 것: `k_stack`
- **고정 크기 메시지를 복사하는** 것: `k_msgq` (FreeRTOS 큐와 가장 닮았다 — 기본은 D4)
- **바이트 스트림을 복사하는** 것: `k_pipe`
- **보낸 쪽과 받는 쪽이 만나서(rendezvous) 넘기는** 것: `k_mbox`
- **한 생산자 → 여러 관찰자에게 퍼뜨리는** 것: zbus (커널 객체가 아니라 `subsys/zbus`의 서브시스템)

이 노트는 이 지도를 그리고, 각 객체의 "Zephyr에만 있는 동작"을 실행으로 확인한 뒤, 같은 QEMU 보드에서 비용을 잰다.

그림 1 — Zephyr의 데이터 전달 객체를 두 축에 놓았다. 왼쪽으로 갈수록 복사가 적고(대신 메모리 수명 관리를 앱이 진다), 위로 갈수록 길이가 자유롭다. 점선의 zbus는 커널 객체가 아니라 `k_sem` · `k_msgq` · `k_fifo` · `net_buf` 위에 세운 서브시스템이다.

SSD 펌웨어에 빗대면 이렇다. `k_fifo`는 "디스크립터 자체에 next 포인터가 박혀 있는 명령 리스트", `k_stack`은 "빈 버퍼 인덱스를 쌓아 두는 free-list", `k_msgq`는 "고정 크기 엔트리 링버퍼", `k_pipe`는 "UART 로그 바이트 링", `k_mbox`는 "호스트가 완료 응답을 받을 때까지 기다리는 동기 명령", zbus는 "온도 센서 값을 여러 모듈(열 관리, 로그, SMART)에 동시에 알리는 이벤트 버스"다.

### 실습 환경 한 줄

QEMU `mps2-an385`(Cortex-M3 @ 25 MHz) + **Zephyr v4.4.2**(`/var/rtoslab/zephyrproject/zephyr`, 툴체인 Ubuntu arm-none-eabi-gcc 14.2, picolibc), 기본 `-Os`. QEMU는 `-icount shift=5,align=off,sleep=off`(명령 1개 = 32 ns, FreeRTOS 노트의 `ICOUNT=1`과 같은 조건, `prj.conf`에도 `CONFIG_QEMU_ICOUNT_SHIFT=5`)로 직접 실행하고 semihosting으로 끝낸다. 시간은 MPS2 FPGAIO COUNTER(0x40028018, 25 MHz = 40 ns 단위)로 잰다. **QEMU icount 기준이라 실제 칩과 절대값은 다르다**(캐시 · 플래시 wait state · 버스 · 예외 스태킹 사이클 미모델링). 비교는 상대값으로 읽는다.

모든 예제는 같은 틀이다. `CMakeLists.txt`는 Zephyr 표준 4줄에 `target_compile_options(app PRIVATE -Wall -Wextra)`와 공통 헤더 폴더를 더했고, 공통 헤더 `d10.h`는 아래 12줄이다.

```c
/* D10 공통: QEMU 종료(semihosting) + 25 MHz FPGAIO 카운터 */
#pragma once
#include <stdint.h>
static inline void qemu_exit(int code)
{
	register unsigned r0 __asm__("r0") = 0x18, r1 __asm__("r1") = code ? 0x20023 : 0x20026;
	__asm volatile("bkpt 0xab" : : "r"(r0), "r"(r1) : "memory");
	for (;;) {
	}
}
/* MPS2 FPGAIO COUNTER: 리셋부터 25 MHz로 증가 (1 tick = 40 ns) */
#define FPGA_CNT (*(volatile uint32_t *)0x40028018)
static inline uint32_t cnt_ns(uint32_t d) { return d * 40U; }
```

빌드 · 실행 스크립트(`zr.sh <예제>`)는 이렇게 생겼다. VM 루트 파일시스템이 이 노트를 쓰는 동안 읽기 전용으로 바뀌어서(ext4 `emergency_ro`) 빌드 산출물은 `/tmp/rtos/D10/`(tmpfs)에 두었다.

```sh
S=/Users/donh/.rtos_scratch/D10/$E; O=/tmp/rtos/D10/$E
/var/rtoslab/bin/rtos-zbuild mps2/an385 $S $O "$@" || { echo BUILD FAILED; exit 1; }
timeout 20 qemu-system-arm -machine mps2-an385 -cpu cortex-m3 -nographic -monitor none -serial stdio \
  -semihosting-config enable=on,target=native -icount shift=5,align=off,sleep=off \
  -kernel $O/zephyr/zephyr.elf
```

Zephyr 에러 코드는 Zephyr 자체 `errno.h` 값이다. 이 노트에서 나오는 숫자: `-11` = `-EAGAIN`, `-12` = `-ENOMEM`, `-16` = `-EBUSY`, `-32` = `-EPIPE`, `-35` = `-ENOMSG`, `-140` = `-ECANCELED`.

### 1.1 비교 표

먼저 결론부터 한 장으로 본다. 아래 표의 "ISR" 칸은 `include/zephyr/kernel.h`의 Doxygen `@isr_ok` 표시를 직접 확인한 결과다(§1.3에 확인 방법).

| 객체 | 넘기는 것 | 크기 | ISR에서 보내기 | ISR에서 받기 | 받는 쪽 | 동기성 | 메모리 소유권 |
|---|---|---|---|---|---|---|---|
| `k_fifo` / `k_lifo` (`k_queue`) | 아이템 **포인터** | 임의(첫 word 예약) | ✓ (`@isr_ok`) | `K_NO_WAIT`로 ✓ | 대기자 1명이 가져감 | 비동기 | 앱이 아이템을 소유, 꺼낼 때까지 건드리면 안 됨 |
| `k_stack` | `stack_data_t` 값 하나 (32비트에서 4 B) | 고정 1 word | ✓ | `K_NO_WAIT`로 ✓ | 대기자 1명 | 비동기 | 값이라 소유권 문제 없음(포인터를 넣으면 fifo와 같음) |
| `k_msgq` | 메시지 **복사본** | 고정(정의 시) | `K_NO_WAIT`로 ✓ | `K_NO_WAIT`로 ✓ | 대기자 1명 | 비동기 | 커널 링버퍼가 복사본 소유 |
| `k_pipe` (4.1~) | 바이트 **복사본** | 가변, 경계 없음 | 문서상 ✗ (`@isr_ok` 없음) | 문서상 ✗ | 대기자 1명씩 | 비동기, 부분 전송 | 커널 링버퍼(크기 0 가능) |
| `k_mbox` | 송신 버퍼 → 수신 버퍼 **1회 복사** | 가변(수신 쪽이 자를 수 있음) | ✗ | ✗ | **특정 스레드 지정 가능** | 동기(`put`) / 비동기(`async_put`) | 송신자가 복사 끝날 때까지 버퍼 유지 |
| zbus listener | 채널 메시지를 **잠근 채 직접 읽기** | 채널마다 고정 | publish를 `K_NO_WAIT`로 | 콜백이 publisher 문맥(ISR일 수도)에서 돈다 | **N명 모두** | 동기(publish 안) | 채널이 1개 소유 |
| zbus subscriber | **채널 포인터**만(알림) | 고정 | publish를 `K_NO_WAIT`로 | ✗ (`zbus_sub_wait`는 스레드 전용) | N명 | 비동기, 최신값만 | 채널이 소유, 늦게 읽으면 덮인 값 |
| zbus msg_subscriber | **net_buf 복사본** | 고정 | publish를 `K_NO_WAIT`로 | ✗ | N명 | 비동기, 매 메시지 | net_buf 풀이 소유, 풀 고갈 시 `-ENOMEM` |

### 1.4 공통 골격 — 모든 객체는 "버퍼 + wait_q + spinlock"이다

Zephyr 소스를 열어 보면 여섯 개 객체가 거의 같은 모양이다. 구조체에 **데이터를 담는 곳**(sflist, 링버퍼, 배열)과 **기다리는 스레드 줄**(`_wait_q_t`, C1 §5.3)과 `struct k_spinlock` 하나가 있다. 보내는 쪽은 "줄 선 사람이 있으면 그 사람에게 직접 주고, 없으면 버퍼에 넣는다". 받는 쪽은 "버퍼에 있으면 꺼내고, 없으면 내 받을 곳 주소를 `_current->base.swap_data`에 적어 두고 줄을 선다(`z_pend_curr`)". 이 대칭은 D1의 `k_sem`, C12에서 읽은 `sem.c`와 똑같다. 차이는 **무엇을 넘기느냐**뿐이다. 자세한 내부는 §10에서 함수 단위로 본다.

| 객체 | 구조체 크기 (이 빌드) | 데이터 저장소 | 대기 줄 | 소스 |
|---|---|---|---|---|
| `k_fifo` / `k_lifo` | 16 B | `sys_sflist_t data_q` (아이템 안의 next) | `wait_q` 1개 (받는 쪽만 기다린다) | `kernel/queue.c` 505줄 |
| `k_stack` | 24 B | `stack_data_t` 배열 + `base`/`next`/`top` | `wait_q` 1개 (pop만) | `kernel/stack.c` 240줄 |
| `k_msgq` | (D4) | 링버퍼 `buffer_start`/`read_ptr`/`write_ptr` | `wait_q` **1개를 reader와 writer가 같이 쓴다** | `kernel/msg_q.c` 536줄 |
| `k_pipe` | — | `struct ring_buf` | `data`(reader)와 `space`(writer) **2개** | `kernel/pipe.c` 358줄 |

## 2. `k_fifo` · `k_lifo` · `k_queue` — 아이템 안에 next 포인터를 박는 intrusive 큐

### 2.1 직관 — "명령 디스크립터의 첫 필드가 next"

SSD 펌웨어의 명령 큐를 떠올리자. 디스크립터 구조체 맨 앞에 `struct cmd *next`를 두고, 큐에는 head/tail 포인터만 둔다. 데이터는 한 바이트도 복사하지 않는다. 대신 규칙이 하나 생긴다. **큐에 들어가 있는 동안 디스크립터의 next 필드는 큐의 것이다.** `k_fifo`가 정확히 이것이다. 헤더의 문서가 이렇게 말한다.

```text
 * This routine adds a data item to @a fifo. A FIFO data item must be
 * aligned on a word boundary, and the first word of the item is reserved
 * for the kernel's use.
```

`k_fifo`와 `k_lifo`는 따로 구현이 없다. 둘 다 `struct k_queue _queue` 하나를 감싼 구조체이고, `k_fifo_put`은 `k_queue_append`, `k_lifo_put`은 `k_queue_prepend`를 부르는 **매크로**다. 꺼내는 쪽은 둘 다 `k_queue_get`(머리에서 꺼냄)이다. 즉 "FIFO냐 LIFO냐"는 넣을 때 꼬리에 붙이느냐 머리에 붙이느냐뿐이다.

`k_queue`의 리스트는 `sys_slist`가 아니라 `sys_sflist`다. "flagged" 단일 연결 리스트로, next 포인터의 **하위 2비트를 플래그로** 쓴다(`SYS_SFLIST_FLAGS_MASK = __alignof__(sys_sfnode_t) - 1`, `BUILD_ASSERT(... >= 0x3)`). 아이템이 word 정렬이어야 하는 이유가 이것이다. 플래그 비트 0은 "이 노드는 커널이 heap에서 만든 `alloc_node`다"라는 표시다(§2.4).

### 2.2 예제 1 — 첫 word 예약, 0 copy, 대기자 직접 전달, alloc_put

무엇을 확인하는 코드인지: (1) put 뒤에 아이템의 첫 word가 실제로 next 포인터가 되는지, (2) 꺼낸 포인터가 넣은 객체 그 자체인지(복사 없음), (3) 이미 기다리는 스레드가 있으면 아이템이 리스트를 거치지 않고 바로 넘어가는지(첫 word가 그대로인지), (4) lifo 순서, (5) `k_fifo_alloc_put`이 resource pool을 얼마나 먹는지.

```c
/* D10 ex1 — k_fifo/k_lifo: 첫 word 예약, zero-copy, 대기자 직접 전달, alloc_put과 resource pool */
#include <zephyr/kernel.h>
#include "d10.h"

struct imu_sample {
	void *fifo_reserved; /* 첫 word = 커널의 next 포인터 자리 */
	uint32_t seq;
	int16_t gyro[3];
};

K_FIFO_DEFINE(fifo);
K_FIFO_DEFINE(fifo_w);
K_LIFO_DEFINE(lifo);
static struct imu_sample s[3];
static const uint32_t cfg_word = 0xC0FFEE; /* 예약 word가 없는 읽기 전용 데이터 */
K_HEAP_DEFINE(tiny, 128); /* alloc_put 전용 작은 resource pool */

static void waiter(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	struct imu_sample *p = k_fifo_get(&fifo_w, K_FOREVER);
	printk("waiter got %p seq=%u reserved=%p (untouched)\n", (void *)p, p->seq,
	       p->fifo_reserved);
}
K_THREAD_DEFINE(w_id, 1024, waiter, NULL, NULL, NULL, 1, 0, 0);

int main(void)
{
	struct imu_sample *p;

	k_thread_priority_set(k_current_get(), 5); /* waiter(1)보다 낮게 */
	k_msleep(1); /* waiter가 먼저 fifo_w에서 블록되게 */
	printk("sizeof k_fifo=%u k_lifo=%u imu_sample=%u\n", (unsigned)sizeof(struct k_fifo),
	       (unsigned)sizeof(struct k_lifo), (unsigned)sizeof(struct imu_sample));
	for (int i = 0; i < 3; i++) {
		s[i].seq = 100 + i;
		s[i].fifo_reserved = (void *)0xDEADBEEF;
	}
	k_fifo_put(&fifo_w, &s[0]); /* 대기자 있음 → 리스트를 거치지 않는다 */

	for (int i = 0; i < 3; i++) {
		s[i].fifo_reserved = (void *)0xDEADBEEF;
		k_fifo_put(&fifo, &s[i]);
	}
	printk("after put: s0.res=%p (&s1=%p) s1.res=%p (&s2=%p) s2.res=%p\n",
	       s[0].fifo_reserved, (void *)&s[1], s[1].fifo_reserved, (void *)&s[2],
	       s[2].fifo_reserved);
	while ((p = k_fifo_get(&fifo, K_NO_WAIT)) != NULL) {
		printk("fifo get %p seq=%u\n", (void *)p, p->seq);
	}
	for (int i = 0; i < 3; i++) {
		k_lifo_put(&lifo, &s[i]);
	}
	while ((p = k_lifo_get(&lifo, K_NO_WAIT)) != NULL) {
		printk("lifo get seq=%u\n", p->seq);
	}

	int r, n = 0;
	k_thread_heap_assign(k_current_get(), &tiny);
	while ((r = k_fifo_alloc_put(&fifo, (void *)&cfg_word)) == 0) {
		n++;
	}
	printk("alloc_put into 128 B heap: %d ok, then %d\n", n, r);
	const uint32_t *q = k_fifo_get(&fifo, K_NO_WAIT);
	printk("got %p (&cfg_word=%p) val=0x%x\n", (const void *)q, (const void *)&cfg_word, *q);
	r = k_fifo_alloc_put(&fifo, (void *)&cfg_word);
	printk("after one get, alloc_put again: %d\n", r);
	qemu_exit(0);
	return 0;
}
```

출력에서 볼 것:

- `after put` 줄: `s0.res=0x20000330`이 `&s1`과 같고, `s1.res`가 `&s2`, 마지막 `s2.res=0`이다. 0xDEADBEEF로 채워 둔 첫 word를 커널이 next 포인터로 덮어썼다. 그림 3 위쪽 그대로다.
- `fifo get` 주소가 `s[0..2]` 주소 그대로다. **복사가 없다.** 같은 객체를 생산자와 소비자가 번갈아 만진다는 뜻이므로, 소비자가 다 쓰고 "돌려주기" 전까지 생산자는 그 아이템을 재사용하면 안 된다(§2.3 버그 2).
- `waiter got ... reserved=0xdeadbeef (untouched)`: 우선순위 1인 waiter가 이미 `fifo_w`에서 블록되어 있었으므로, `k_fifo_put`은 아이템을 리스트에 넣지 않고 waiter의 반환값으로 바로 꽂았다. 그래서 첫 word를 건드리지조차 않았다. 소스로는 `queue_insert()`가 `z_unpend_first_thread()`로 대기자를 찾으면 `prepare_thread_to_run(thread, data)` → `z_thread_return_value_set_with_data()`로 끝내고 `sys_sfnode_init(data, 0)`에 도달하지 않는다(§10).
- `lifo get`은 102 → 101 → 100. 같은 `k_queue`를 머리에 붙였을 뿐이다.
- `alloc_put into 128 B heap: 5 ok, then -12`: `alloc_node`는 8 B(`sys_sfnode_t` 4 B + `void *data` 4 B)지만 `sys_heap`의 chunk 헤더와 정렬 때문에 128 B heap에 5개만 들어갔다. 6번째에서 `-ENOMEM`. 하나를 꺼내면(get이 `k_free`) 다시 들어간다.

`k_fifo_alloc_put`의 heap은 "호출 스레드의 `resource_pool`"이다(`z_thread_malloc` → `z_thread_alloc_helper`, `kernel/mempool.c`). ISR에서 부르면 시스템 heap(`_SYSTEM_HEAP`)을 쓴다. 기본값을 소스에서 확인하면 이렇다.

- 부팅 중의 dummy thread는 `K_HEAP_MEM_POOL_SIZE > 0`이면 `k_thread_system_pool_assign(dummy_thread)`를 받는다(`kernel/thread.c` `z_dummy_thread_init`). 새 스레드는 `new_thread->resource_pool = _current->resource_pool`로 **만든 스레드의 pool을 물려받는다**. 그래서 `main`과 `K_THREAD_DEFINE` 스레드는 시스템 heap이 있으면 자동으로 그것을 쓴다.
- `CONFIG_HEAP_MEM_POOL_SIZE`가 0(기본)이면 pool이 NULL이고 `alloc_put`은 항상 `-ENOMEM`이다.
- 대기자가 있으면 할당 자체를 하지 않는다(소스 주석: "Only need to actually allocate if no threads are pending").

### 2.3 예제 2 — k_fifo를 부수는 세 가지 방법

무엇을 확인하는 코드인지: 실무에서 실제로 나오는 세 버그 — (1) 구조체에 예약 word를 안 둠, (2) 아직 큐 안에 있는 아이템을 다시 put, (3) 함수 지역 변수(스택)를 put하고 함수가 끝남.

```c
/* D10 ex2 — k_fifo 세 가지 버그: 예약 word 누락, 큐 안의 아이템 재삽입, 스택 아이템 */
#include <zephyr/kernel.h>
#include "d10.h"

struct bad_msg { /* 예약 word 없음! */
	uint32_t seq;
	uint32_t val;
};
struct msg {
	void *reserved;
	uint32_t seq;
};
K_FIFO_DEFINE(fq);

static __noinline void produce_local(void)
{
	struct msg loc = {.seq = 777};

	k_fifo_put(&fq, &loc); /* 함수가 끝나면 loc는 사라진다 */
}
static __noinline void scribble(void)
{
	volatile uint32_t junk[32];

	for (int i = 0; i < 32; i++) {
		junk[i] = 0xAAAAAAAA;
	}
	(void)junk[0];
}
static int drain(const char *tag)
{
	struct msg *p;
	int n = 0;

	while ((p = k_fifo_get(&fq, K_NO_WAIT)) != NULL && n < 10) {
		printk("  %s get seq=%u\n", tag, p->seq);
		n++;
	}
	return n;
}

int main(void)
{
	/* (1) 예약 word 누락: 첫 필드 seq가 next 포인터로 덮인다 */
	static struct bad_msg b[2] = {{.seq = 1, .val = 10}, {.seq = 2, .val = 20}};

	k_fifo_put(&fq, &b[0]);
	k_fifo_put(&fq, &b[1]);
	printk("(1) b0.seq=0x%x (&b1=%p) b1.seq=0x%x\n", b[0].seq, (void *)&b[1], b[1].seq);
	(void)k_fifo_get(&fq, K_NO_WAIT);
	(void)k_fifo_get(&fq, K_NO_WAIT);

	/* (2) 아직 큐 안에 있는 아이템을 다시 put */
	static struct msg A = {.seq = 1}, B = {.seq = 2}, C = {.seq = 3};

	k_fifo_put(&fq, &A);
	k_fifo_put(&fq, &B);
	k_fifo_put(&fq, &C);
	k_fifo_put(&fq, &B); /* B를 "다시 보내기" */
	printk("(2) put A,B,C,B -> got %d items\n", drain("(2)"));

	/* (3) 스택에 있던 아이템 */
	produce_local();
	scribble();
	printk("(3) stack item:\n");
	drain("(3)");
	qemu_exit(0);
	return 0;
}
```

### 2.4 `k_queue`에만 있는 것들

`k_fifo`/`k_lifo` 매크로가 감추는 `k_queue` API 중 쓸 만한 것을 v4.4.2 헤더에서 확인하면:

| API | 하는 일 | 주의 |
|---|---|---|
| `k_queue_insert(q, prev, data)` | `prev` 뒤에 끼워 넣기 | 우선순위 큐를 직접 만들 때 |
| `k_queue_append_list(q, head, tail)` | 이미 이어진 아이템 리스트를 한 번에 붙임 | 대기자가 여럿이면 앞에서부터 한 명씩 직접 준다 |
| `k_queue_merge_slist(q, list)` | `sys_slist_t`를 통째로 옮김 | 성공하면 원본 `list`를 비운다 |
| `k_queue_remove(q, data)` | 중간의 아이템 제거 (O(n)) | **v4.4.2 소스에서 `queue->lock`을 잡지 않는다** (아래) |
| `k_queue_unique_append(q, data)` | 이미 있으면 안 넣음 | 순회도 lock 없이 한다 |
| `k_queue_peek_head` / `peek_tail` | 꺼내지 않고 보기 | 4.4.2에서 lock 버그가 고쳐졌다 (release notes #112435) |
| `k_queue_cancel_wait(q)` | 기다리는 첫 스레드를 `NULL` 반환으로 깨움 | "종료 신호"용 |

`k_queue_remove`의 본문은 `sys_sflist_find_and_remove(&queue->data_q, ...)` 한 줄이고 spinlock이 없다. 헤더 문서는 `@isr_ok`라고 적혀 있다. 단일 코어에서도 다른 스레드나 ISR이 같은 큐에 put하는 동안 remove가 리스트를 걷고 있으면 꼬일 수 있다고 읽힌다(소스를 읽은 해석이고, 레이스를 재현해 보지는 않았다). 4.4.2 릴리스 노트의 고친 버그 목록에 "`k_queue_peek_head()`/`k_queue_peek_tail()` dereference a node without holding the queue lock"(#112435)이 있는 것을 보면, 이 파일의 lock 규율은 아직 다듬어지는 중이다. 실무 규칙: `k_queue_remove`는 그 큐를 만지는 문맥이 하나뿐일 때만 쓴다.

### 2.5 흔한 함정

- 아이템 구조체 첫 필드를 `void *fifo_reserved;`로 두는 것을 잊는다 → 첫 필드 데이터 파괴(예제 2-1).
- `const` 테이블이나 플래시에 있는 데이터를 `k_fifo_put` → 커널이 첫 word에 **쓴다**. 실칩에서는 플래시 쓰기 fault다. 그런 데이터는 `k_fifo_alloc_put`으로 넣는다(예제 1의 `cfg_word`).
- 같은 아이템을 두 큐에 동시에 넣는다 → next 필드가 하나뿐이니 두 리스트가 섞인다. 두 큐에 걸쳐야 하면 next 필드를 두 개 두고 `CONTAINER_OF`로 돌아오는 `sys_slist`를 직접 쓰거나 복사 객체를 쓴다.
- `k_fifo_get`이 `NULL`을 돌려주는 경우는 두 가지다. 타임아웃, 그리고 누군가 `k_fifo_cancel_wait`을 부른 경우. 둘을 구분하려면 별도 플래그가 필요하다.

## 3. `k_stack` — word 하나짜리 LIFO, 버퍼 free-list의 정석

### 3.1 정의

`k_stack`은 `stack_data_t`(= `uintptr_t`, Cortex-M에서 4 B) 배열 위의 LIFO다. `K_STACK_DEFINE(name, n)`이 배열까지 만든다. 값을 복사하지만 값이 4 B뿐이라 "포인터를 넘기는 가장 싼 방법"이기도 하다. 전형적인 용도는 **빈 버퍼 풀(free-list)** 이다. DMA 버퍼 N개의 주소를 넣어 두고, 쓰는 쪽이 pop, 다 쓴 쪽(흔히 DMA 완료 ISR)이 push한다. LIFO라서 방금 반납된 버퍼(캐시에 남아 있을 가능성이 큰 버퍼)가 먼저 다시 나간다.

`k_mbox`의 async 경로도 내부에서 `K_STACK_DEFINE(async_msg_free, CONFIG_NUM_MBOX_ASYNC_MSGS)`를 descriptor free-list로 쓴다(§6.4). 커널 스스로가 이 패턴의 사용자다.

### 3.2 예제 6 — DMA 버퍼 free-list

무엇을 확인하는 코드인지: LIFO 순서, 가득 찼을 때와 비었을 때의 에러 코드, 그리고 ISR(`k_timer` 콜백)에서 push하면 블록된 pop이 깨어나는지.

```c
/* D10 ex6 — k_stack: DMA 버퍼 free-list, LIFO, 에러 코드, ISR push */
#include <zephyr/kernel.h>
#include "d10.h"

#define NBUF 4
static uint8_t dma_buf[NBUF][64] __aligned(4);
K_STACK_DEFINE(freelist, NBUF);

static void tmr_cb(struct k_timer *t)
{
	ARG_UNUSED(t);
	/* DMA 완료 ISR이 버퍼를 돌려준다고 가정 */
	int r = k_stack_push(&freelist, (stack_data_t)dma_buf[2]);

	printk("  ISR(in_isr=%d): push buf2 -> %d\n", k_is_in_isr(), r);
}
K_TIMER_DEFINE(tmr, tmr_cb, NULL);

int main(void)
{
	stack_data_t v;
	int r;

	printk("sizeof(stack_data_t)=%u sizeof(struct k_stack)=%u\n",
	       (unsigned)sizeof(stack_data_t), (unsigned)sizeof(struct k_stack));
	for (int i = 0; i < NBUF; i++) {
		k_stack_push(&freelist, (stack_data_t)dma_buf[i]);
	}
	r = k_stack_push(&freelist, (stack_data_t)dma_buf[0]);
	printk("push to full stack: %d\n", r);
	printk("pop order:");
	for (int i = 0; i < NBUF; i++) {
		k_stack_pop(&freelist, &v, K_NO_WAIT);
		printk(" buf%d", (int)(((uint8_t *)v - dma_buf[0]) / 64));
	}
	printk("\n");
	r = k_stack_pop(&freelist, &v, K_NO_WAIT);
	printk("pop empty, NO_WAIT: %d\n", r);
	r = k_stack_pop(&freelist, &v, K_MSEC(20));
	printk("pop empty, 20 ms : %d\n", r);

	k_timer_start(&tmr, K_MSEC(30), K_NO_WAIT);
	int64_t t0 = k_uptime_get();

	r = k_stack_pop(&freelist, &v, K_FOREVER);
	printk("blocked pop -> %d, buf%d after %lld ms\n", r,
	       (int)(((uint8_t *)v - dma_buf[0]) / 64), k_uptime_get() - t0);
	qemu_exit(0);
	return 0;
}
```

```text
             RAM:        6464 B         4 MB      0.15%
*** Booting Zephyr OS build v4.4.2 ***

```

출력에서 볼 것:

- 넣은 순서 0,1,2,3 → 꺼낸 순서 3,2,1,0. LIFO.
- 가득 찬 stack에 push → `-12`(`-ENOMEM`). 이 검사는 `CHECKIF(stack->next == stack->top)`이다. `CHECKIF`는 `CONFIG_NO_RUNTIME_CHECKS=y`면 **사라지고**, `CONFIG_ASSERT_ON_ERRORS=y`면 assert가 된다. 런타임 검사를 끈 릴리스 빌드에서 push를 너무 많이 하면 배열 밖에 쓴다. 풀 크기 = stack 크기로 맞추면 넘칠 일이 없다.
- 빈 stack을 `K_NO_WAIT`로 pop → `-16`(`-EBUSY`), 타임아웃 → `-11`(`-EAGAIN`). **같은 "없음"인데 `k_msgq`는 `-ENOMSG`, `k_stack`은 `-EBUSY`다.** 객체마다 에러 코드가 다르다. 반환값을 `== -EAGAIN`으로만 검사하는 공용 래퍼를 만들면 `K_NO_WAIT` 경로를 놓친다. `!= 0`으로 검사하는 습관이 안전하다.
- ISR에서 push한 `buf2`가 30 ms 뒤 블록된 pop으로 바로 넘어갔다. `z_impl_k_stack_push`도 대기자가 있으면 배열에 넣지 않고 `z_thread_return_value_set_with_data(first_pending_thread, 0, (void *)data)`로 직접 준다.

## 4. `k_msgq` — Zephyr에만 있는 부분만

> 메시지 큐 일반론(복사 vs 포인터, 깊이 설계, 블로킹 send/receive)과 FreeRTOS 큐와의 기본 비교는 D4가 다룬다. 여기서는 **Zephyr v4.4.2의 `k_msgq`에만 있는 동작**만 본다.

### 4.1 정렬 — 4.4.2 문서는 "필요 없다"고 말한다

예전 Zephyr 문서는 "메시지 크기는 정렬의 배수여야 한다"는 식으로 정렬을 강조했다. v4.4.2 헤더의 `K_MSGQ_DEFINE` 문서는 이렇게 적는다.

```text
 * The message queue's ring buffer contains space for @a q_max_msgs messages,
 * each of which is @a q_msg_size bytes long. Alignment of the message queue's
 * ring buffer is not necessary, setting @a q_align to 1 is sufficient.
```

구현을 보면 이유가 분명하다. `put_msg_in_queue()`와 `z_impl_k_msgq_get()`은 `memcpy(msgq->write_ptr, data, msgq->msg_size)`로만 복사하고, 링버퍼 안의 메시지를 구조체 포인터로 캐스팅해 읽는 일이 없다. 그래서 6 B짜리 `__packed` 구조체도 `q_align = 1`로 문제없다(예제 3). 다만 **성능은 다르다**: 기본 `-Os` 빌드의 picolibc `memcpy`는 28 B짜리 바이트 루프다(§8.2에서 디스어셈블로 확인). 큰 메시지라면 정렬보다 최적화 옵션이 비용을 좌우한다. `K_MSGQ_DEFINE`의 버퍼는 `__noinit`이라 부팅 때 0으로 지워지지 않는다는 점도 알아 둔다.

### 4.2 `k_msgq_put_front`, `peek_at`, `get_attrs`, `purge`

v4.4.2에 실제로 있는 확장 API(모두 `__syscall`):

| API | 동작 | 소스에서 본 사실 |
|---|---|---|
| `k_msgq_put_front(q, data)` | 큐 **맨 앞**에 넣기 (긴급 메시지) | 타임아웃 인자가 없다. 항상 `K_NO_WAIT`로 `put_msg_in_queue(..., false)`. 가득 차면 `-ENOMSG` |
| `k_msgq_peek(q, data)` | 맨 앞 복사, 꺼내지 않음 | |
| `k_msgq_peek_at(q, data, idx)` | idx번째 복사 | 링 wrap을 계산한다 |
| `k_msgq_get_attrs(q, attrs)` | `msg_size`, `max_msgs`, `used_msgs` | 세 필드를 **lock 없이** 읽는다 (순간값) |
| `k_msgq_num_free_get` / `num_used_get` | 빈 칸 / 찬 칸 | inline, lock 없음 |
| `k_msgq_purge(q)` | 큐 비우기 | **기다리는 스레드를 전부 `-ENOMSG`로 깨운다** (아래) |
| `k_msgq_alloc_init` / `k_msgq_cleanup` | 버퍼를 resource pool에서 할당 / 해제 | 대기자가 있으면 cleanup은 `-EBUSY` |

`put_front`는 `read_ptr`를 한 칸 **뒤로** 물리고(시작이면 `buffer_end`로 wrap) 그 자리에 쓴다. `write_ptr`는 그대로다.

### 4.3 예제 3 — 홀수 크기 메시지, put_front, peek_at, purge가 reader를 깨운다

무엇을 확인하는 코드인지: 6 B 메시지 + 정렬 1, `put_front` 순서와 가득 찼을 때의 동작, `peek_at`, `get_attrs`, 그리고 `purge`가 (a) 꽉 찬 큐에서 기다리는 writer와 (b) **빈 큐에서 기다리는 reader**에게 각각 무엇을 돌려주는지.

```c
/* D10 ex3 — k_msgq의 Zephyr 고유 기능: 홀수 크기, put_front, peek_at, attrs, purge */
#include <zephyr/kernel.h>
#include "d10.h"

struct __packed rc_cmd { /* 6 B: 4의 배수가 아니다 */
	uint8_t ch;
	uint8_t flags;
	int32_t value;
};
K_MSGQ_DEFINE(q6, sizeof(struct rc_cmd), 4, 1);
K_MSGQ_DEFINE(qr, 4, 2, 4); /* reader가 빈 큐에서 대기 */
K_MSGQ_DEFINE(qw, 4, 1, 4); /* writer가 꽉 찬 큐에서 대기 */

static void reader(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	uint32_t v = 0;
	int r = k_msgq_get(&qr, &v, K_FOREVER);
	printk("  reader: k_msgq_get(K_FOREVER) returned %d\n", r);
}
static void writer(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	uint32_t v = 2;
	int r = k_msgq_put(&qw, &v, K_FOREVER);
	printk("  writer: k_msgq_put(K_FOREVER) returned %d\n", r);
}
K_THREAD_DEFINE(rd, 1024, reader, NULL, NULL, NULL, 1, 0, 10);
K_THREAD_DEFINE(wr, 1024, writer, NULL, NULL, NULL, 1, 0, 10);

int main(void)
{
	struct rc_cmd c = {0};
	struct k_msgq_attrs at;
	uint32_t one = 1;

	k_thread_priority_set(k_current_get(), 5);
	printk("q6 buffer=%p msg_size=%u\n", (void *)q6.buffer_start, (unsigned)q6.msg_size);
	for (int i = 0; i < 3; i++) {
		c.ch = 'A' + i;
		c.value = 1000 + i;
		k_msgq_put(&q6, &c, K_NO_WAIT);
	}
	c.ch = 'Z'; /* 긴급 명령: 맨 앞에 */
	c.value = -1;
	printk("put_front Z: %d\n", k_msgq_put_front(&q6, &c));
	printk("put_front when full: %d (no blocking)\n", k_msgq_put_front(&q6, &c));
	k_msgq_peek_at(&q6, &c, 2);
	printk("peek_at(2) = %c/%d\n", c.ch, c.value);
	k_msgq_get_attrs(&q6, &at);
	printk("attrs: msg_size=%u max=%u used=%u free=%u\n", (unsigned)at.msg_size,
	       at.max_msgs, at.used_msgs, k_msgq_num_free_get(&q6));
	printk("order:");
	while (k_msgq_get(&q6, &c, K_NO_WAIT) == 0) {
		printk(" %c", c.ch);
	}
	printk("\n");

	k_msgq_put(&qw, &one, K_NO_WAIT); /* qw를 가득 채운다 */
	k_msleep(20);                    /* reader·writer가 블록되게 (시작 지연 10 ms) */
	printk("purge qw (writer waiting on full queue):\n");
	k_msgq_purge(&qw);
	k_msleep(1);
	printk("purge qr (reader waiting on EMPTY queue):\n");
	k_msgq_purge(&qr);
	k_msleep(1);
	qemu_exit(0);
	return 0;
}
```

- **`reader: k_msgq_get(K_FOREVER) returned -35`**. 빈 큐에서 영원히 기다리던 reader가 `purge`로 깨어나 `-ENOMSG`를 받았다. 헤더의 `k_msgq_purge` 문서와 `z_impl_k_msgq_purge()`의 주석은 둘 다 "blocked waiting to send" 스레드만 말하는데( "wake up any threads that are waiting to write"), `k_msgq`는 reader와 writer가 **같은 `wait_q` 하나**를 쓰므로 루프가 reader까지 깨운다. 한편 `k_msgq_get`의 반환값 문서는 "`-ENOMSG` Returned without waiting **or queue purged**"라고 적어 두었으니, 문서끼리도 살짝 어긋나 있지만 동작 자체는 의도된 것으로 봐야 한다. 실무 의미: 소비자 스레드의 `K_FOREVER` 루프가 `-ENOMSG`를 "있을 수 없는 일"로 처리하면 안 된다. 드론 FC에서 "모드 전환 시 명령 큐 purge"를 했더니 명령 처리 스레드가 에러 경로로 빠져 종료되는 버그가 이렇게 생긴다.

### 4.4 Zephyr `k_msgq`와 FreeRTOS 큐의 차이 — D4에 없는 것만

| 항목 | Zephyr `k_msgq` (v4.4.2) | FreeRTOS 큐 (V11.3.2) |
|---|---|---|
| 맨 앞에 넣기 | `k_msgq_put_front`, 블록 안 함 | `xQueueSendToFront`, 블록 가능 |
| 대기 줄 | reader · writer 공용 1개 | `xTasksWaitingToSend` / `xTasksWaitingToReceive` 2개 |
| 비우기 | `purge`: 대기자 전부 `-ENOMSG`로 깨움 (reader 포함) | `xQueueReset`: 기다리던 송신자 **1명**만 깨워 다시 시도하게 함, reader는 계속 대기 |
| 대기자에게 직접 | `put`이 대기 reader의 버퍼(`swap_data`)로 바로 `memcpy` (복사 1회) | 큐 저장소로 복사 후 수신자가 다시 복사 (복사 2회) |
| ISR 전용 API | 없음, 같은 함수를 `K_NO_WAIT`로 | `...FromISR` 별도 함수 |
| 덮어쓰기 | 없음 | `xQueueOverwrite` (길이 1 큐) |
| poll / 큐 셋 | `k_poll`의 `K_POLL_TYPE_MSGQ_DATA_AVAILABLE` (D5) | Queue Set (D4) |

"대기자에게 직접" 행이 §8의 측정에서 드러난다. 수신자가 이미 기다리고 있으면 `k_msgq`는 링버퍼를 건너뛴다.

## 5. `k_pipe` — Zephyr 4.1에서 새로 쓴 바이트 스트림

### 5.1 무엇이 바뀌었나 — 버전별 사실

`k_pipe`는 4.x에서 API가 통째로 바뀐 객체다. 이 랩의 v4.4.2 트리에 들어 있는 문서로 확인한 사실:

- **4.1**: release notes "The pipe API has been reworked", `CONFIG_PIPES` deprecated, `k_pipe_close()` 추가. migration guide 4.1의 대응표를 옮기면 아래와 같다.
- **4.3**: release notes "Removed APIs and options"에 "The legacy pipe object API was removed. Use the new pipe API instead."
- **v4.4.2**: `kernel/pipe.c` 하나(358줄, 저작권 2024 Måns Ansgariusson)만 있고 `kernel/CMakeLists.txt`가 `CONFIG_MULTITHREADING`이면 무조건 컴파일한다. `CONFIG_PIPES` 심볼은 `kernel/Kconfig`에 더 이상 없다. 4.4.2 릴리스 노트에는 `k_pipe` 관련 CVE(CVE-2026-10671)도 하나 있다: user 스레드가 `k_pipe_init` syscall로 **사용 중인 pipe를 다시 초기화**해 wait queue를 망가뜨릴 수 있었다(verifier가 `K_SYSCALL_OBJ_NEVER_INIT` 대신 `K_SYSCALL_OBJ`를 썼다). 4.4.2 소스의 `z_vrfy_k_pipe_init`은 `K_SYSCALL_OBJ_NEVER_INIT`이다.

| 옛 API (~4.0) | 새 API (4.1~) | 바뀐 점 (migration guide 4.1) |
|---|---|---|
| `k_pipe_put(pipe, data, len, &written, min_xfer, timeout)` | `k_pipe_write(pipe, data, len, timeout)` | `min_xfer` 삭제, 쓴 바이트 수가 반환값 |
| `k_pipe_get(pipe, data, len, &read, min_xfer, timeout)` | `k_pipe_read(pipe, data, len, timeout)` | `min_xfer` 삭제, 읽은 바이트 수가 반환값 |
| `k_pipe_flush` · `k_pipe_buffer_flush` | `k_pipe_reset` | 데이터 버림, 블록 안 함, 대기자는 `-ECANCELED` |
| `k_pipe_alloc_init` · `k_pipe_cleanup` | **삭제** | 동적 할당 pipe 없음 |
| `k_pipe_read_avail` · `k_pipe_write_avail` | **삭제** | 남은 바이트 수를 물어볼 수 없음 |
| 없음 | `k_pipe_close` | 대기자 전부 에러로 깨움, 남은 데이터는 읽을 수 있음, 다시 쓰려면 `k_pipe_init` |

4.1 이전에 쓰인 Zephyr pipe 예제·블로그 글은 옛 API다. **v4.3 이후에는 컴파일되지 않는다.** 포팅할 때 `min_xfer`로 "최소 N 바이트는 보장" 같은 의미를 쓰던 코드는 새 API에서 다시 설계해야 한다.

### 5.2 새 의미 — "len을 다 채울 때까지 기다린다, 타임아웃이면 부분"

소스(`z_impl_k_pipe_read`)의 루프를 그대로 읽으면 규칙은 세 줄이다.

1. 링버퍼에서 꺼낼 수 있는 만큼 꺼낸다. `len`을 다 채웠으면 `len`을 돌려준다.
2. 덜 채웠는데 pipe가 닫혔으면 지금까지 읽은 수(0이면 `-EPIPE`).
3. 아니면 `data` 대기 줄에서 기다린다. 타임아웃이면 지금까지 읽은 수(0이면 `-EAGAIN`).

즉 POSIX `read()`처럼 "있는 만큼 주고 돌아오기"가 **아니다**. `K_FOREVER`로 16 B를 읽으면 16 B가 다 올 때까지 안 돌아온다. "있는 만큼"을 원하면 `K_NO_WAIT`로 읽는다. 쓰기도 대칭이다. 그리고 메시지 경계가 없다. 5 B 프레임 세 개를 써도 reader는 그것을 8 B + 7 B로 읽을 수 있다.

쓰는 쪽에는 최적화가 하나 있다. **pipe가 비어 있고 기다리는 reader가 있으면** `copy_to_pending_readers()`가 링버퍼를 건너뛰고 reader의 버퍼(reader 스택 위의 `struct pipe_buf_spec`이 가리키는 곳)로 바로 `memcpy`한다. reader가 원하는 양을 다 받았을 때만 깨운다. 그래서 reader는 깨어나자마자 "다 찼다"를 본다.

### 5.3 예제 4 — 경계 없음, 부분 전송, reset, close

무엇을 확인하는 코드인지: 위 규칙을 전부. 32 B pipe에 5 B 프레임 세 개를 쓰고 8 B를 읽기, 빈 pipe `K_NO_WAIT`, 버퍼보다 큰 쓰기, 블록된 reader에게 6 B + 10 B, 타임아웃 부분 읽기, reset 중의 reader, close 뒤의 쓰기 · 읽기.

```c
/* D10 ex4 — 4.1 이후 k_pipe: 바이트 스트림, 부분 전송, reset/close */
#include <zephyr/kernel.h>
#include "d10.h"

K_PIPE_DEFINE(pp, 32, 4);
static uint8_t rx[64];
static volatile int phase;

static void reader(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	int r;

	while (phase == 0) { k_msleep(1); }
	r = k_pipe_read(&pp, rx, 16, K_FOREVER); /* 16 B가 다 찰 때까지 */
	printk("  [%lld ms] reader: read(16, FOREVER) = %d\n", k_uptime_get(), r);
	r = k_pipe_read(&pp, rx, 16, K_MSEC(30));
	printk("  [%lld ms] reader: read(16, 30ms) = %d\n", k_uptime_get(), r);
	r = k_pipe_read(&pp, rx, 16, K_FOREVER);
	printk("  [%lld ms] reader: read during reset = %d\n", k_uptime_get(), r);
}
K_THREAD_DEFINE(rd, 1024, reader, NULL, NULL, NULL, 1, 0, 0);

int main(void)
{
	static const uint8_t frame[5] = {0xA5, 1, 2, 3, 0x5A};
	uint8_t big[40] = {0};
	int r;

	k_thread_priority_set(k_current_get(), 5);
	/* 1) 프레임 경계가 없다 */
	for (int i = 0; i < 3; i++) {
		k_pipe_write(&pp, frame, sizeof(frame), K_NO_WAIT);
	}
	r = k_pipe_read(&pp, rx, 8, K_NO_WAIT);
	printk("3x5B written, read(8) = %d: %02x %02x %02x %02x %02x | %02x %02x %02x\n", r,
	       rx[0], rx[1], rx[2], rx[3], rx[4], rx[5], rx[6], rx[7]);
	r = k_pipe_read(&pp, rx, 64, K_NO_WAIT);
	printk("read(64, NO_WAIT) = %d (rest)\n", r);
	printk("read on empty, NO_WAIT = %d\n", k_pipe_read(&pp, rx, 4, K_NO_WAIT));
	r = k_pipe_write(&pp, big, sizeof(big), K_NO_WAIT);
	printk("write(40) into 32 B pipe, NO_WAIT = %d\n", r);
	k_pipe_reset(&pp);

	/* 2) 블로킹 reader에게 6 B, 10 B를 나눠 쓴다 */
	phase = 1;
	k_msleep(5);
	printk("[%lld ms] main: write 6\n", k_uptime_get());
	k_pipe_write(&pp, big, 6, K_NO_WAIT);
	k_msleep(10);
	printk("[%lld ms] main: write 10\n", k_uptime_get());
	k_pipe_write(&pp, big, 10, K_NO_WAIT);
	/* reader의 두 번째 read: 6 B만 주고 타임아웃 */
	k_pipe_write(&pp, big, 6, K_NO_WAIT);
	k_msleep(50);
	/* 3) reader가 기다리는 중 reset */
	k_pipe_reset(&pp);
	k_msleep(1);
	/* 4) close: 남은 데이터는 읽히고, 그다음 -EPIPE */
	k_pipe_write(&pp, frame, 5, K_NO_WAIT);
	k_pipe_close(&pp);
	printk("after close: write = %d\n", k_pipe_write(&pp, frame, 5, K_NO_WAIT));
	printk("after close: read  = %d\n", k_pipe_read(&pp, rx, 16, K_NO_WAIT));
	printk("after close: read  = %d\n", k_pipe_read(&pp, rx, 16, K_NO_WAIT));
	qemu_exit(0);
	return 0;
}
```

출력에서 볼 것:

- `read(8) = 8: a5 01 02 03 5a | a5 01 02`: 두 번째 프레임 중간에서 잘렸다. **pipe는 메시지 경계를 모른다.** UART 프레임처럼 경계가 중요한 데이터면 앱이 길이 헤더나 동기 바이트(여기서는 0xA5 … 0x5A)로 다시 찾아야 한다. 고정 크기 메시지면 `k_msgq`가 맞다.
- `write(40) into 32 B pipe, NO_WAIT = 32`: 들어가는 만큼만 넣고 32를 돌려준다. **반환값이 `len`보다 작을 수 있다.** 반환값을 무시하면 8 B를 조용히 잃는다.
- 그림 5의 세 결과(16, 6, -140)가 실제 로그 그대로다. 두 번째 read가 6을 돌려준 것은 "타임아웃 → 읽은 만큼"이다. 타임아웃을 0으로 착각해 `-EAGAIN`만 검사하면 이 6 B를 놓친다.
- close 뒤: write는 바로 `-32`(`-EPIPE`), read는 남은 5 B를 먼저 돌려주고 그다음 `-EPIPE`. migration guide의 "all data in the pipe is available to readers until the pipe is emptied" 그대로다. 로그 스트림을 닫을 때 "남은 바이트를 다 비운 뒤 EOF"를 표현할 수 있게 된 것이 `close`의 존재 이유다.

### 5.4 버퍼 크기 0인 pipe

`k_pipe_init(pipe, NULL, 0)`과 `K_PIPE_DEFINE(name, 0, align)`을 문서가 허용한다("or zero if no ring buffer is used"). 링버퍼가 없으면 `ring_buf_put`이 항상 0을 넣으므로, writer는 **기다리는 reader에게 직접 복사**하는 경로로만 데이터를 넘긴다. 즉 "reader가 와서 받을 때까지 writer가 기다리는" 바이트 단위 rendezvous가 된다. `k_mbox`보다 가벼운 동기 전달이 필요할 때 쓸 수 있다(이 노트에서는 실행하지 않았다).

### 5.5 흔한 함정

- 옛 API 예제를 그대로 붙인다 → v4.3부터 링크 에러가 아니라 **컴파일 에러**(함수 선언이 없음).
- `k_pipe_read(..., K_FOREVER)`를 "들어온 만큼 즉시 반환"으로 착각 → 텔레메트리 스레드가 마지막 몇 바이트를 들고 영원히 잔다.
- 반환값의 부분 전송을 무시한다.
- `k_pipe_reset`은 데이터를 버리고 대기자를 `-ECANCELED`로 깨운다. reset 진행 중(`PIPE_FLAG_RESET`, 대기자가 아직 다 안 빠짐)에 새로 부른 read/write도 `-ECANCELED`다. 이것을 치명 에러로 처리하면 스트림 재동기화 도중 스레드가 죽는다.

## 6. `k_mbox` — 송신자와 수신자가 만나서 넘기는 우편함

### 6.1 직관 — "등기 우편"

`k_msgq`가 우체통(넣고 떠난다)이라면 `k_mbox`는 **등기 우편**이다. 보내는 사람(`k_mbox_put`)은 받는 사람이 서명할 때까지 창구에서 기다린다. 받는 사람(`k_mbox_get`)은 "누구에게서 온 것만 받겠다"를 정할 수 있고, 보내는 사람은 "누구에게 보낸다"를 정할 수 있다. 그리고 두 사람은 **`info` 값 하나를 서로 맞바꾼다**. 데이터는 송신자의 버퍼에서 수신자의 버퍼로 **딱 한 번** 복사된다. 커널 안에는 데이터 저장소가 아예 없다(구조체에 대기 줄 두 개와 spinlock뿐).

`struct k_mbox_msg`의 앱이 채우는 필드:

| 필드 | 송신자가 넣는 값 | 수신자가 넣는 값 | 교환 후 |
|---|---|---|---|
| `size` | 보낼 바이트 수 | 받을 수 있는 최대 | 수신자: `min(둘)`; 송신자: 수신자가 실제 받은 수 |
| `info` | 앱 정의 32비트 | 앱 정의 32비트 | **서로 바뀐다** |
| `tx_data` | 송신 버퍼 주소 | (무시) | |
| `tx_target_thread` | 받을 스레드 또는 `K_ANY` | (커널이 `_current`로 채움) | |
| `rx_source_thread` | (커널이 `_current`로 채움) | 받을 송신자 또는 `K_ANY` | 수신자: 실제 송신자 |

매칭 조건은 `mbox_message_match()` 그대로다: (송신 target이 `K_ANY`이거나 수신자 자신) 그리고 (수신 source가 `K_ANY`이거나 송신자 자신).

### 6.2 예제 5 — 대상 지정, info 교환, 크기 절단, 지연 수신, async

무엇을 확인하는 코드인지: (1) 수신자가 없을 때 `K_NO_WAIT` put, (2) 더 높은 우선순위의 A가 `K_ANY`로 기다려도 B를 지정한 메시지는 B에게만 가는지, (3) 수신자가 4 B만 받겠다고 하면 송신자의 `size`가 어떻게 되는지, `info` 교환, (4) 수신자가 버퍼 없이 get한 뒤 20 ms 일하고 `k_mbox_data_get`할 때 송신자가 언제 풀려나는지, (5) `k_mbox_async_put` + 세마포어.

```c
/* D10 ex5 — k_mbox: 대상 지정, info 교환, 크기 절단, 지연 수신, async put */
#include <zephyr/kernel.h>
#include <string.h>
#include "d10.h"

K_MBOX_DEFINE(mb); K_SEM_DEFINE(done, 0, 1);
extern const k_tid_t ta, tb;
#define T() ((int)k_uptime_get())
#define UNUSED3 ARG_UNUSED(p1); ARG_UNUSED(p2); ARG_UNUSED(p3)

static void thr_a(void *p1, void *p2, void *p3)
{
	UNUSED3;
	char buf[16];
	for (;;) {
		struct k_mbox_msg rx = {.size = sizeof(buf), .info = 0xA,
					.rx_source_thread = K_ANY};
		k_mbox_get(&mb, &rx, buf, K_FOREVER);
		printk("  [%d] A got \"%s\" size=%u info=0x%x\n", T(), buf, (unsigned)rx.size, rx.info);
	}
}
static void thr_b(void *p1, void *p2, void *p3)
{
	UNUSED3;
	char buf[16] = {0};
	struct k_mbox_msg rx = {.size = 4, .info = 0xB, .rx_source_thread = K_ANY};

	k_mbox_get(&mb, &rx, buf, K_FOREVER); /* 4 B만 받겠다 */
	printk("  [%d] B got \"%.4s\" size=%u info=0x%x\n", T(), buf, (unsigned)rx.size, rx.info);
	rx = (struct k_mbox_msg){.size = 16, .rx_source_thread = K_ANY};
	k_mbox_get(&mb, &rx, NULL, K_FOREVER); /* 데이터는 나중에 */
	printk("  [%d] B matched, size=%u, working 20 ms before data_get\n", T(), (unsigned)rx.size);
	k_busy_wait(20000);
	k_mbox_data_get(&rx, buf);
	k_msleep(30);
	rx = (struct k_mbox_msg){.size = 16, .rx_source_thread = K_ANY};
	k_mbox_get(&mb, &rx, buf, K_FOREVER);
	printk("  [%d] B got async \"%s\"\n", T(), buf);
}
K_THREAD_DEFINE(ta, 1024, thr_a, NULL, NULL, NULL, 2, 0, 10);
K_THREAD_DEFINE(tb, 1024, thr_b, NULL, NULL, NULL, 3, 0, 10);

static int send(k_tid_t to, const char *s, uint32_t info)
{
	struct k_mbox_msg tx = {.size = strlen(s) + 1, .info = info, .tx_data = (void *)s,
				.tx_target_thread = to};
	int t0 = T(), r = k_mbox_put(&mb, &tx, K_MSEC(100));
	printk("[%d] put(%s) ret=%d after %d ms, tx.size=%u tx.info=0x%x\n", T(),
	       to == K_ANY ? "ANY" : (to == tb ? "B" : "A"), r, T() - t0, (unsigned)tx.size, tx.info);
	return r;
}

int main(void)
{
	k_thread_priority_set(k_current_get(), 5);
	struct k_mbox_msg tx0 = {.size = 0, .tx_target_thread = K_ANY};
	printk("put before receivers exist, NO_WAIT: %d\n", k_mbox_put(&mb, &tx0, K_NO_WAIT));
	k_msleep(20);
	send(tb, "ARM-MOTORS", 0x100); /* A가 더 높은 우선순위로 기다려도 B에게만 */
	send(K_ANY, "RTL", 0x200);
	send(tb, "CALIB", 0x300);       /* B가 data_get 할 때까지 반환하지 않는다 */
	static const char as[] = "LOG-ROTATE"; struct k_mbox_msg atx = {.size = sizeof(as), .tx_data = (void *)as, .tx_target_thread = tb};
	int t0 = T();
	k_mbox_async_put(&mb, &atx, &done);
	printk("[%d] async_put returned after %d ms\n", T(), T() - t0);
	k_sem_take(&done, K_FOREVER);
	printk("[%d] async done sem after %d ms\n", T(), T() - t0);
	qemu_exit(0);
	return 0;
}
```

출력에서 볼 것:

- `put before receivers exist, NO_WAIT: -35`: 맞는 수신자가 없으면 `-ENOMSG`.
- `B got "ARM-" size=4`: A(우선순위 2)가 B(3)보다 높은 우선순위로 같은 mbox에서 기다렸지만 target이 B라 B가 받았다. 4 B로 잘렸다. 송신자 쪽은 `tx.size=4`(수신자가 실제로 받은 양), `tx.info=0xb`(B가 넣어 둔 info)로 바뀌어 돌아왔다. **송신자는 "몇 바이트가 전달됐나"와 "수신자가 답한 값 하나"를 반환값 없이 받는다.** 명령 → 짧은 응답 코드 패턴에 딱 맞다.
- `put(ANY)`는 A가 받았다. 대기 줄(`rx_msg_queue`)은 우선순위 순이고, `_WAIT_Q_FOR_EACH`로 앞에서부터 맞는 사람을 찾는다.
- `B matched, size=6` → 20 ms busy-wait → `data_get` → 송신자 `put(B) ret=0 after 20 ms`. **동기 `k_mbox_put`은 수신자가 데이터를 실제로 가져갈 때까지 돌아오지 않는다.** 그리고 소스를 보면 매칭이 된 뒤의 대기는 `z_pend_curr(&mbox->lock, key, NULL, K_FOREVER)`, 즉 **`put`에 준 timeout이 적용되지 않는다.** 예제의 `K_MSEC(100)`은 "수신자를 찾을 때까지"의 한도일 뿐이다. 수신자가 `data_get`을 잊으면 송신자는 영원히 잔다.
- async: `async_put returned after 0 ms`, 세마포어는 B가 실제로 받은 40 ms 뒤(B가 30 ms 자고 tick 경계)에 왔다.

### 6.3 언제 `k_mbox`가 값어치를 하나

장점은 셋이다. 복사가 1회이고(커널 버퍼 없음), 송신자가 "전달 완료"를 동기적으로 알 수 있고, 특정 스레드를 지정할 수 있다. 큰 가변 길이 블록을 "전달 완료 확인과 함께" 넘길 때, 예를 들어 센서 허브에서 펌웨어 업데이트 청크를 플래시 쓰기 스레드에 넘기고 "받았다"를 확인한 뒤 다음 청크를 읽는 경우가 그렇다.

단점이 더 많다.

- syscall이 없다. **user mode 스레드에서 못 쓴다**(§9).
- ISR에서 못 쓴다.
- 동기 put은 수신자의 처리 시간만큼 송신자를 붙잡는다. 송신자가 수신자보다 높은 우선순위면 우선순위 역전처럼 보이는 지연이 생긴다(D3의 관점으로 보면 "높은 우선순위가 낮은 우선순위의 처리를 기다리는" 구조 자체다).
- 측정(§8.3)에서 handoff가 `k_msgq` 16 B보다 2배 가까이 느리다.
- Zephyr 문서 · 샘플에서도 사용 빈도가 낮다. 새 코드에서는 `k_msgq` + 응답용 `k_sem`, 또는 zbus가 흔하다.

### 6.4 async put의 정체 — dummy thread와 `k_stack` 풀

`k_mbox_async_put`이 "비동기"인 방법이 재미있다. `kernel/mailbox.c`는 부팅 때 `CONFIG_NUM_MBOX_ASYNC_MSGS`(기본 10)개의 `struct k_mbox_async { struct _thread_base thread; struct k_mbox_msg tx_msg; }`를 만들고 `K_STACK_DEFINE(async_msg_free, …)`에 주소를 쌓는다. async put은 그중 하나를 pop해서 메시지를 복사하고, **가짜 스레드(`_THREAD_DUMMY`)** 를 송신자로 대기 줄에 세운다. 진짜 송신자는 바로 돌아간다. 수신자가 메시지를 다 가져가면 `mbox_message_dispose()`가 descriptor를 push로 반납하고 세마포어를 준다.

결과 두 가지:

- **footprint**: 10개 descriptor가 RAM 800 B(`async_msg.0 b 800`, §8.4의 nm 출력). `k_mbox`를 쓰는 순간 async를 안 써도 RAM이 늘어난다. 안 쓰면 `CONFIG_NUM_MBOX_ASYNC_MSGS=0`.
- **블록**: 풀이 비면 `mbox_async_alloc()`이 `k_stack_pop(&async_msg_free, …, K_FOREVER)`로 기다린다. 이름은 async인데 **블록할 수 있다.**

## 7. zbus — 한 채널, 여러 관찰자

### 7.1 무엇이고 왜 쓰나

zbus(Zephyr bus)는 `subsys/zbus`의 publish-subscribe 서브시스템이다. 이 트리의 릴리스 노트로 확인한 이력: **3.3**에서 추가, **3.5**에서 message subscriber 추가, **3.6**에서 채널 잠금을 mutex에서 semaphore로 바꾸고 HLP priority boost 도입, **4.2**에서 "stable status with the release of API version v1.0.0", **4.4**에서 async listener(`CONFIG_ZBUS_ASYNC_LISTENER`)와 실험적 proxy agent(`CONFIG_ZBUS_PROXY_AGENT`, 다른 코어/도메인으로 채널 중계) 추가.

생각의 단위가 "큐"가 아니라 **채널**이다. 채널은 타입이 정해진 메시지 **한 개**를 담은 공유 변수 + 잠금 + 관찰자 목록이다. publish는 "채널 값을 바꾸고 관찰자들에게 알린다"이다. 큐처럼 메시지가 쌓이지 않는다(msg_subscriber는 예외). 그래서 앱 구조가 "모듈 A가 모듈 B의 큐에 넣는다"(A가 B를 안다)에서 "A가 IMU 채널에 쓰고, 관심 있는 모듈이 채널을 관찰한다"(A는 B를 모른다)로 바뀐다. Nordic의 Asset Tracker Template(nRF91용, nRF Connect SDK 기반)이 모듈 간 통신을 zbus로, 모듈 동작을 SMF(State Machine Framework)로 짠 것이 대표적인 사례다.

관찰자는 네 종류다(`enum zbus_observer_type`).

| 종류 | 정의 매크로 | 받는 것 | 어디서 실행되나 | Kconfig |
|---|---|---|---|---|
| listener | `ZBUS_LISTENER_DEFINE(name, cb)` | 콜백 `cb(chan)` | **publisher 문맥, 채널 잠금 안** (ISR publish면 ISR) | 기본 |
| subscriber | `ZBUS_SUBSCRIBER_DEFINE(name, qsize)` | `k_msgq`로 **채널 포인터만** | 자기 스레드, `zbus_sub_wait` 뒤 `zbus_chan_read` | 기본 |
| msg_subscriber | `ZBUS_MSG_SUBSCRIBER_DEFINE(name)` | `net_buf`에 담긴 **메시지 복사본** | 자기 스레드, `zbus_sub_wait_msg` | `CONFIG_ZBUS_MSG_SUBSCRIBER` (`NET_BUF` select) |
| async listener (4.4) | `ZBUS_ASYNC_LISTENER_DEFINE(name, cb)` | 복사본으로 콜백 | work queue 스레드 (D7) | `CONFIG_ZBUS_ASYNC_LISTENER` (MSG_SUBSCRIBER select) |

publish 한 번의 흐름(VDED — Virtual Distributed Event Dispatcher)은 `zbus_chan_pub()` → validator → `chan_lock()`(priority boost + `k_sem_take`) → `memcpy(chan->message, msg)` → `_zbus_vded_exec()`(관찰자 목록을 **정의 순서대로** 돌며 종류별 통지) → `chan_unlock()`이다.

### 7.2 예제 7 — 드론 FC: IMU → failsafe listener + estimator + slow subscriber + logger

무엇을 확인하는 코드인지: (1) VDED 통지 순서, (2) listener가 어느 스레드 문맥에서 어떤 우선순위로 도는지(priority boost 확인), (3) 높은 우선순위 subscriber와 낮은 우선순위 subscriber가 3샘플 burst에서 각각 무엇을 읽는지, (4) msg_subscriber는 무엇을 받는지.

```c
/* D10 ex7 — zbus 드론 FC: IMU 채널 → failsafe listener + estimator subscriber
 *          + slow subscriber + logger msg_subscriber */
#include <zephyr/kernel.h>
#include <zephyr/zbus/zbus.h>
#include "d10.h"

struct imu_msg { uint32_t seq; int16_t acc_z; int16_t gyr[3]; };

static void failsafe_cb(const struct zbus_channel *ch)
{
	const struct imu_msg *m = zbus_chan_const_msg(ch); /* 채널 잠금 안에서 직접 읽기 */
	printk("  L failsafe seq=%u ctx=%s prio=%d%s\n", m->seq, k_thread_name_get(k_current_get()),
	       k_thread_priority_get(k_current_get()), m->acc_z > 3000 ? "  -> FAILSAFE!" : "");
}
ZBUS_LISTENER_DEFINE(failsafe_lis, failsafe_cb);
ZBUS_SUBSCRIBER_DEFINE(est_sub, 4);
ZBUS_SUBSCRIBER_DEFINE(slow_sub, 8);
ZBUS_MSG_SUBSCRIBER_DEFINE(log_msub);
ZBUS_CHAN_DEFINE(imu_chan, struct imu_msg, NULL, NULL,
		 ZBUS_OBSERVERS(failsafe_lis, est_sub, slow_sub, log_msub), ZBUS_MSG_INIT(0));

static void sub_loop(const struct zbus_observer *o, const char *tag)
{
	const struct zbus_channel *ch;
	struct imu_msg m;

	while (zbus_sub_wait(o, &ch, K_FOREVER) == 0) {
		zbus_chan_read(ch, &m, K_MSEC(5)); /* 참조만 받았으니 지금 값을 읽는다 */
		printk("  S %s got notify, reads seq=%u\n", tag, m.seq);
	}
}
static void est_thread(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	IF_ENABLED(CONFIG_ZBUS_PRIORITY_BOOST, (zbus_obs_attach_to_thread(&est_sub);))
	sub_loop(&est_sub, "estimator(2)");
}
static void slow_thread(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	sub_loop(&slow_sub, "slow(7)");
}
static void log_thread(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	const struct zbus_channel *ch;
	struct imu_msg m;

	while (zbus_sub_wait_msg(&log_msub, &ch, &m, K_FOREVER) == 0) {
		printk("  M logger(7) copy seq=%u acc_z=%d\n", m.seq, m.acc_z);
	}
}
K_THREAD_DEFINE(est, 1024, est_thread, NULL, NULL, NULL, 2, 0, 0);
K_THREAD_DEFINE(slow, 1024, slow_thread, NULL, NULL, NULL, 7, 0, 0);
K_THREAD_DEFINE(logt, 1024, log_thread, NULL, NULL, NULL, 7, 0, 0);

static void imu_thread(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	k_msleep(10);
	for (uint32_t i = 1; i <= 3; i++) { /* 3샘플 burst */
		struct imu_msg m = {.seq = i, .acc_z = (i == 3) ? 4000 : 1000};
		printk("P imu pub seq=%u (prio %d)\n", i, k_thread_priority_get(k_current_get()));
		int r = zbus_chan_pub(&imu_chan, &m, K_MSEC(1));
		printk("P pub seq=%u ret=%d\n", i, r);
	}
	k_msleep(20);
	qemu_exit(0);
}
K_THREAD_DEFINE(imu, 1024, imu_thread, NULL, NULL, NULL, 4, 0, 0);
```

`prj.conf`: `CONFIG_ZBUS=y`, `CONFIG_ZBUS_MSG_SUBSCRIBER=y`, `CONFIG_ZBUS_CHANNEL_NAME=y`, `CONFIG_ZBUS_OBSERVER_NAME=y`, `CONFIG_HEAP_MEM_POOL_SIZE=2048`, `CONFIG_THREAD_NAME=y`(+ 공통 두 줄).

출력에서 볼 것:

- 각 publish마다 `L failsafe` → `S estimator` → `P pub ret=0` 순서다. listener는 `ctx=imu`, 즉 **IMU 스레드 자신이 콜백을 실행**했고, 그때 우선순위가 4가 아니라 **1**이다. estimator가 `zbus_obs_attach_to_thread`로 자기 우선순위 2를 채널에 알렸으므로, `chan_lock()`이 publisher를 `highest_observer_priority - 1 = 1`로 올렸다(HLP, §7.4).
- estimator(2)는 publisher(원래 4)보다 높지만 boost 때문에 VDED 도중에 끼어들지 못하고, `chan_unlock()`이 우선순위를 4로 되돌리는 순간 선점해서 읽었다. 그래서 seq 1, 2, 3을 하나씩 정확히 읽었다.
- slow(7)는 publisher보다 낮아서 burst가 다 끝난 뒤에 돌았다. 알림 3개(큐에 `&imu_chan` 3개)를 받았지만 세 번 다 **seq=3**을 읽었다. **subscriber는 "채널이 바뀌었다"는 알림만 받는다. 값은 읽는 시점의 최신값이다.** seq 1, 2는 이 관찰자에게 영원히 사라졌다. zbus 문서도 "there are no message delivery guarantees for subscribers"라고 적는다.
- logger(7)도 같은 우선순위로 늦게 돌았지만 seq 1, 2, 3과 각각의 `acc_z`를 다 받았다. publish마다 `net_buf`에 복사본이 만들어져 fifo에 쌓였기 때문이다.
- `-> FAILSAFE!`는 seq 3의 `acc_z=4000`을 listener가 publish 안에서 즉시 본 것이다. failsafe 판단처럼 "지금 이 값에 즉시 반응"은 listener, 상태 추정처럼 "최신값만 있으면 된다"는 subscriber, 로깅처럼 "하나도 빠짐없이"는 msg_subscriber — 이것이 세 종류를 고르는 기준이다.

`CONFIG_ZBUS_PRIORITY_BOOST=n`으로 같은 앱을 다시 빌드하면 출력 순서는 똑같고 listener 줄만 `prio=4`로 바뀐다(실행 결과, 핵심 줄만).

```text
P imu pub seq=1 (prio 4)
  L failsafe seq=1 ctx=imu prio=4
  S estimator(2) got notify, reads seq=1
P pub seq=1 ret=0
```

순서가 같아 보이는 것은 estimator의 `zbus_chan_read(…, K_MSEC(5))`가 채널이 풀릴 때까지 기다려 주기 때문이다. 속에서 무슨 일이 일어나는지는 §7.4의 그림과 §8.3의 측정(`read failed 500/500`)이 보여 준다. 덧붙여, 처음에는 `zbus_obs_attach_to_thread()`를 조건 없이 불렀다가 boost를 끈 빌드에서 `error: implicit declaration of function 'zbus_obs_attach_to_thread'`를 만났다. 이 함수는 `CONFIG_ZBUS_PRIORITY_BOOST`일 때만 선언된다. 그래서 예제는 `IF_ENABLED(CONFIG_ZBUS_PRIORITY_BOOST, (...))`로 감쌌다. Kconfig 하나로 API가 사라지는 Zephyr다운 함정이다.

### 7.3 예제 8 — zbus의 함정 다섯 개

무엇을 확인하는 코드인지: (1) 아무도 꺼내 가지 않는 msg_subscriber가 있으면 무슨 일이 생기나, 그리고 **그 뒤에 등록된 관찰자**는 통지를 받나, (2) 큐가 꽉 찬 subscriber가 publisher를 얼마나 붙잡나, (3) ISR에서 publish, (4) validator, (5) runtime observer 추가 · 제거.

```c
/* D10 ex8 — zbus 함정: net_buf 풀 고갈, 느린 subscriber, ISR publish, validator, runtime observer */
#include <zephyr/kernel.h>
#include <zephyr/zbus/zbus.h>
#include "d10.h"

struct tel { uint32_t seq; int32_t v; };
static int tail_n, late_n;
static void tail_cb(const struct zbus_channel *ch) { ARG_UNUSED(ch); tail_n++; }
static void isr_cb(const struct zbus_channel *ch)
{
	printk("  isr_lis: in_isr=%d v=%d\n", k_is_in_isr(),
	       ((const struct tel *)zbus_chan_const_msg(ch))->v);
}
static void late_cb(const struct zbus_channel *ch) { ARG_UNUSED(ch); late_n++; }
static bool tel_ok(const void *msg, size_t sz) { ARG_UNUSED(sz); return ((const struct tel *)msg)->v >= 0; }

ZBUS_MSG_SUBSCRIBER_DEFINE(msub_log); /* 아무도 꺼내 가지 않는다 */
ZBUS_LISTENER_DEFINE(tail_lis, tail_cb);
ZBUS_SUBSCRIBER_DEFINE(sub2, 2);      /* 큐 2칸, 아무도 읽지 않는다 */
ZBUS_LISTENER_DEFINE(isr_lis, isr_cb);
ZBUS_LISTENER_DEFINE(late_lis, late_cb);
ZBUS_CHAN_DEFINE(chan_a, struct tel, NULL, NULL, ZBUS_OBSERVERS(msub_log, tail_lis), ZBUS_MSG_INIT(0));
ZBUS_CHAN_DEFINE(chan_b, struct tel, NULL, NULL, ZBUS_OBSERVERS(sub2), ZBUS_MSG_INIT(0));
ZBUS_CHAN_DEFINE(chan_c, struct tel, tel_ok, NULL, ZBUS_OBSERVERS(isr_lis), ZBUS_MSG_INIT(0));

static void tmr_cb(struct k_timer *t)
{
	ARG_UNUSED(t);
	struct tel m = {.v = 42};
	int r = zbus_chan_pub(&chan_c, &m, K_NO_WAIT);   /* ISR에서 */
	int r2 = zbus_chan_pub(&chan_b, &m, K_MSEC(50)); /* ISR이면 NO_WAIT로 바뀐다 */

	printk("  ISR pub chan_c=%d, chan_b(full)=%d\n", r, r2);
}
K_TIMER_DEFINE(tmr, tmr_cb, NULL);

int main(void)
{
	struct tel m = {0};
	int r, first_err = -1;

	for (int i = 0; i < 20; i++) {
		m.seq = i;
		r = zbus_chan_pub(&chan_a, &m, K_NO_WAIT);
		if (r && first_err < 0) {
			first_err = i;
			printk("chan_a pub #%d -> %d\n", i, r);
		}
	}
	printk("chan_a: 20 pubs, first error at #%d, tail_lis notified %d times\n", first_err, tail_n);

	for (int i = 0; i < 3; i++) {
		int64_t t0 = k_uptime_get();

		r = zbus_chan_pub(&chan_b, &m, K_MSEC(50));
		printk("chan_b pub #%d -> %d after %lld ms\n", i, r, k_uptime_get() - t0);
	}
	m.v = -5;
	printk("chan_c invalid msg -> %d\n", zbus_chan_pub(&chan_c, &m, K_NO_WAIT));
	printk("add late_lis at runtime -> %d\n", zbus_chan_add_obs(&chan_c, &late_lis, K_MSEC(10)));
	k_timer_start(&tmr, K_MSEC(10), K_NO_WAIT);
	k_msleep(30);
	printk("late_lis notified %d time(s); rm -> %d\n", late_n,
	       zbus_chan_rm_obs(&chan_c, &late_lis, K_MSEC(10)));
	qemu_exit(0);
	return 0;
}
```

출력에서 볼 것:

- **`chan_a pub #15 -> -12`, `tail_lis notified 15 times`**. 기본 `CONFIG_ZBUS_MSG_SUBSCRIBER_NET_BUF_POOL_SIZE=16`이다. 15개가 `msub_log`의 fifo에 쌓인 상태에서 16번째 publish는 원본 buf(16번째)는 받았지만 clone을 못 받아 `-ENOMEM`이 됐다. 그리고 `_zbus_vded_exec()`는 `-ENOMEM`이면 **즉시 return**한다. 그래서 목록에서 뒤에 있던 `tail_lis`는 #15~#19 다섯 번의 통지를 못 받았다. **느린 로거 하나가 같은 채널의 다른 관찰자(listener까지)를 굶긴다.** zbus 문서의 "ZBus always delivers the messages to the listeners, message subscribers"는 풀이 남아 있을 때의 이야기다. 대책: msg_subscriber를 목록 맨 뒤에 두고, 풀을 넉넉히(`…_POOL_SIZE`), 소비 스레드 우선순위를 충분히, 채널마다 풀을 나누려면 `CONFIG_ZBUS_MSG_SUBSCRIBER_NET_BUF_POOL_ISOLATION` + `zbus_chan_set_msg_sub_pool()`.
- 그리고 풀은 **시스템 전체가 공유**한다(isolation을 안 켜면). chan_a의 로거가 풀을 다 먹으면 다른 채널의 msg_subscriber 통지도 실패한다.
- `chan_b pub #2 -> -11 after 60 ms`: subscriber 큐(2칸)가 차 있으면 `k_msgq_put(obs->queue, &chan, 남은 timeout)`이 publisher를 timeout까지 붙잡는다(50 ms → tick 경계로 60 ms). 이 동안 **채널 잠금도 쥐고 있다.** 다른 publisher와 reader가 모두 막힌다. 문서의 설계 팁 "Try to give consumers a high priority to avoid losses"가 이 뜻이다.
- ISR(`k_timer` 콜백)에서 publish: `isr_lis: in_isr=1`. listener 콜백이 **ISR 안에서** 돌았다. 그리고 같은 ISR에서 chan_b에 `K_MSEC(50)`을 줬지만 `zbus_chan_pub`이 ISR이면 timeout을 `K_NO_WAIT`로 바꾸므로 꽉 찬 큐에 대해 즉시 `-35`(`-ENOMSG`, `k_msgq_put`의 no-wait 실패 코드)가 나왔다. 문서: "Be careful with publications inside ISR because the scheduler won't preempt the VDED."
- validator가 거부하면 `-ENOMSG`, 채널 값은 바뀌지 않는다.
- `zbus_chan_add_obs` → 0, 다음 ISR publish에서 `late_lis`가 1번 통지됨, `zbus_chan_rm_obs` → 0. runtime observer는 정적 관찰자 **다음에** 통지된다(`_zbus_vded_exec`의 두 번째 루프). 문서 경고: "ZBus priority boost does not consider runtime observers on the HOP calculations."

### 7.4 priority boost(HLP) — 왜 필요하고, 무엇을 대가로 치르나

zbus의 채널 잠금은 `k_sem`(초기값 1)이다. 세마포어에는 소유자가 없으니 `k_mutex`의 priority inheritance(D2, D3)가 없다. 대신 zbus는 **Highest Locker Protocol**을 손으로 구현한다(`chan_lock()`, `subsys/zbus/zbus.c:401`).

- 채널마다 `highest_observer_priority`(HOP)를 미리 계산해 둔다. `zbus_obs_attach_to_thread()`로 스레드에 붙은 관찰자의 우선순위 중 가장 높은 값이다. 붙이지 않은 관찰자는 `ZBUS_MIN_THREAD_PRIORITY`(= `CONFIG_NUM_PREEMPT_PRIORITIES - 1`)로 계산된다.
- publish(또는 notify)하는 스레드의 우선순위가 HOP보다 낮으면 잠그기 전에 `k_thread_priority_set(현재, MAX(HOP - 1, 0))`로 **HOP보다 한 단계 높게** 올린다.
- 잠금을 풀 때 원래 우선순위로 되돌린다. ISR에서는 boost를 하지 않는다.

효과는 "VDED 도중에는 관찰자 스레드도, 그 사이 우선순위의 스레드도 publisher를 선점할 수 없다"이다. 이것이 없으면 아래 그림 아래쪽처럼 된다. 높은 우선순위 subscriber는 `k_msgq_put` 순간 깨어나 publisher를 선점하고, `zbus_chan_read`로 채널을 읽으려다가 **publisher가 아직 쥐고 있는 잠금**에 막힌다. `K_NO_WAIT`면 `-EBUSY`, timeout이 있으면 잠들었다가 publisher가 풀어 줄 때 다시 깨어난다. context switch 두 번이 공짜로 더해진다.

그림 7 — HLP boost의 효과. 위: publisher가 HOP-1로 올라가 VDED를 끝까지 하고, 우선순위를 되돌리는 순간 subscriber가 선점한다. 아래: subscriber가 VDED 중간에 끼어들었다가 잠금에 막힌다. §8.3에서 이 아래쪽 경우를 `read failed 500/500`으로 실측한다.

대가도 있다. (1) publish마다 `k_thread_priority_get/set`이 두 번씩 돈다(§8.2: listener 하나짜리 채널의 publish가 boost 때문에 6.6 → 10.8 µs). (2) boost 동안 publisher는 자기 우선순위가 아니라 HOP-1로 돈다. 그 사이 우선순위의 무관한 스레드는 publish가 끝날 때까지 못 돈다(문서가 말하는 HLP의 "Inheritance-related Priority Inversion"). listener 콜백이 길면 그 시간 전체가 boost된 우선순위로 실행된다. **listener를 ISR처럼 짧게** 쓰라는 문서의 규칙이 여기서 나온다. (3) `zbus_obs_attach_to_thread`를 안 부르면 boost는 HOP를 모르고 사실상 꺼진 것과 같다.

### 7.5 `zbus_chan_claim` / `finish` 와 `zbus_chan_notify`

`zbus_chan_claim(chan, timeout)`은 채널 잠금만 잡는다(boost 없이 `k_sem_take`). 그 사이 `zbus_chan_msg(chan)`으로 메시지를 제자리에서 고치거나 `user_data`를 만지고, `zbus_chan_finish(chan)`로 푼다. 큰 메시지의 일부 필드만 바꿀 때 복사를 아낀다. 바꾼 뒤 알리려면 `zbus_chan_notify(chan, timeout)`(memcpy 없이 VDED만). listener 콜백 안에서는 이미 채널이 잠겨 있으므로 `zbus_chan_const_msg(chan)`으로 직접 읽는다(예제 7의 failsafe). **listener 안에서 같은 채널에 `zbus_chan_read`나 `pub`을 부르면 자기 자신이 쥔 세마포어를 기다리는 데드락**이다(D9).

## 8. 측정 — 같은 보드에서 객체별 비용 · 지연 · 크기

### 8.1 무엇을 어떻게 재나

세 가지를 잰다.

1. **대기자 없는 경로의 1회 비용**(예제 9): 한 스레드가 보내고 바로 받는다. 블록도 context switch도 없다. "커널 객체 코드 자체 + 복사"의 비용이다. 1000회 평균.
2. **전달 지연**(예제 10, 11): 높은 우선순위 수신자가 이미 블록된 상태에서 낮은 우선순위 송신자가 보낸다. send 직전 카운터(`t0`)부터 수신자가 받기 함수에서 돌아온 순간까지. context switch 1번이 들어간다. 500회 평균.
3. **footprint**(예제 12): 객체 하나만 쓰는 최소 앱의 `size` − 빈 앱의 `size`.

모두 `-icount shift=5`로 결정적이다(같은 바이너리는 몇 번을 돌려도 같은 숫자). 절대값은 실칩과 다르고, **상대 비교와 "어떤 Kconfig가 얼마를 더하나"** 를 읽는다.

### 8.2 예제 9 — 대기자 없는 경로의 1회 비용

무엇을 확인하는 코드인지: 각 객체로 16 B / 64 B를 한 번 보내고 한 번 받는 비용, zbus publish의 관찰자 구성별 비용. 같은 소스를 Kconfig만 바꿔 네 번 빌드했다.

```c
/* D10 ex9 — 같은 스레드에서 보내고 받기: 대기자 없는 경로의 1회 왕복 비용 */
#include <zephyr/kernel.h>
#include <zephyr/zbus/zbus.h>
#include <string.h>
#include "d10.h"

#define N 1000
#define BENCH(name, body)                                                                  \
	do {                                                                               \
		uint32_t t0 = FPGA_CNT;                                                    \
		for (int i = 0; i < N; i++) { body; }                                      \
		printk("%-16s %5u ns\n", name, cnt_ns(FPGA_CNT - t0) / N);                 \
	} while (0)

struct m16 { uint8_t d[16]; };
struct item { void *res; uint8_t d[12]; };
K_FIFO_DEFINE(f);
K_STACK_DEFINE(st, 4);
K_MSGQ_DEFINE(q16, 16, 4, 4);
K_MSGQ_DEFINE(q64, 64, 4, 4);
K_PIPE_DEFINE(p, 128, 4);
static void nop_cb(const struct zbus_channel *ch) { ARG_UNUSED(ch); }
ZBUS_LISTENER_DEFINE(lis1, nop_cb);
ZBUS_LISTENER_DEFINE(lis3, nop_cb);
ZBUS_SUBSCRIBER_DEFINE(sub1, 4);
ZBUS_SUBSCRIBER_DEFINE(sub3, 4);
ZBUS_CHAN_DEFINE(c_l, struct m16, NULL, NULL, ZBUS_OBSERVERS(lis1), ZBUS_MSG_INIT(0));
ZBUS_CHAN_DEFINE(c_s, struct m16, NULL, NULL, ZBUS_OBSERVERS(sub1), ZBUS_MSG_INIT(0));
#ifdef CONFIG_ZBUS_MSG_SUBSCRIBER
ZBUS_MSG_SUBSCRIBER_DEFINE(msub3);
ZBUS_CHAN_DEFINE(c_3, struct m16, NULL, NULL, ZBUS_OBSERVERS(lis3, sub3, msub3), ZBUS_MSG_INIT(0));
#endif
static uint8_t b64[64], r64[64];
static struct item it;

int main(void)
{
	const struct zbus_channel *ch;
	stack_data_t v;

	printk("per-op cost, N=%d, icount shift=5, MSG_SUBSCRIBER=%d PRIORITY_BOOST=%d\n", N,
	       IS_ENABLED(CONFIG_ZBUS_MSG_SUBSCRIBER), IS_ENABLED(CONFIG_ZBUS_PRIORITY_BOOST));
	BENCH("memcpy 64B", memcpy(r64, b64, 64); __asm volatile("" ::: "memory"));
	BENCH("k_fifo put+get", k_fifo_put(&f, &it); (void)k_fifo_get(&f, K_NO_WAIT));
	BENCH("k_stack push+pop", k_stack_push(&st, 1); k_stack_pop(&st, &v, K_NO_WAIT));
	BENCH("k_msgq 16B", k_msgq_put(&q16, b64, K_NO_WAIT); k_msgq_get(&q16, r64, K_NO_WAIT));
	BENCH("k_msgq 64B", k_msgq_put(&q64, b64, K_NO_WAIT); k_msgq_get(&q64, r64, K_NO_WAIT));
	BENCH("k_pipe 16B", k_pipe_write(&p, b64, 16, K_NO_WAIT); k_pipe_read(&p, r64, 16, K_NO_WAIT));
	BENCH("k_pipe 64B", k_pipe_write(&p, b64, 64, K_NO_WAIT); k_pipe_read(&p, r64, 64, K_NO_WAIT));
	BENCH("zbus pub 1 lis", zbus_chan_pub(&c_l, b64, K_NO_WAIT));
	BENCH("zbus 1 sub", zbus_chan_pub(&c_s, b64, K_NO_WAIT); zbus_sub_wait(&sub1, &ch, K_NO_WAIT);
	      zbus_chan_read(ch, r64, K_NO_WAIT));
#ifdef CONFIG_ZBUS_MSG_SUBSCRIBER
	BENCH("zbus 3 obs", zbus_chan_pub(&c_3, b64, K_NO_WAIT); zbus_sub_wait(&sub3, &ch, K_NO_WAIT);
	      zbus_chan_read(ch, r64, K_NO_WAIT); zbus_sub_wait_msg(&msub3, &ch, r64, K_NO_WAIT));
#endif
	qemu_exit(0);
	return 0;
}
```

그림 9 — zbus publish 비용을 키우는 두 Kconfig. listener 하나짜리 채널의 publish가 6.6 µs에서 45.6 µs로 7배가 된다. 이 채널에는 msg_subscriber가 **하나도 없는데도** 그렇다.

출력에서 볼 것(그리고 이 노트에서 가장 실무적인 숫자들):

- **`k_fifo`(2.4 µs)와 `k_stack`(1.6 µs)은 크기와 무관하다.** 포인터 하나 · word 하나만 옮긴다. 큰 데이터를 넘길수록 이 둘(+ 버퍼 풀)이 유리해진다.
- **`k_msgq` 16 B → 64 B에서 7.3 → 19.6 µs.** 48 B 늘었는데 12.3 µs, 바이트당 약 128 ns(복사가 put·get 두 번이니 복사 1바이트당 64 ns ≈ 명령 2개)다. `-O2`로 빌드하면 64 B가 5.9 µs다. 차이의 원인은 커널이 부르는 `memcpy`다. 기본 `-Os` 빌드는 `CONFIG_PICOLIBC_SIZE_OPTIMIZATIONS=y`가 되어 picolibc `memcpy`가 바이트 루프가 된다.

  28 B(0x1c)짜리 바이트 루프다. `-O2` 빌드에서는 `000000c0 000000ec T memcpy`, 236 B짜리 word 복사 구현이 들어간다. 앱 코드의 `memcpy 64B`(2.2 µs)가 커널의 64 B 복사보다 훨씬 싼 것은 gcc가 크기가 상수인 앱 쪽 `memcpy`를 인라인으로 펼쳤기 때문이다. **"Zephyr 메시지 큐가 느리다"는 측정의 상당 부분은 `-Os`의 바이트 `memcpy`다.** 메시지가 크고 빈번하면 (1) `CONFIG_SPEED_OPTIMIZATIONS`, (2) `CONFIG_PICOLIBC_SPEED_OPTIMIZATIONS`만 따로 켜기, (3) 포인터 전달(`k_fifo` + 풀)로 바꾸기 중에서 고른다.
- **`k_pipe`는 같은 크기의 `k_msgq`보다 비싸다**(16 B: 14.4 vs 7.3 µs). `ring_buf` 계층, 쓰기 · 읽기 각각의 `sys_timepoint_calc`, `for (;;)` 루프 구조 때문이다. 고정 크기 메시지에 pipe를 쓸 이유는 없다.
- **zbus publish는 커널 큐보다 한 자릿수 비싸다.** 가장 가벼운 구성(boost 끔, msg_sub 끔, listener 1개)이 6.6 µs로 `k_msgq` 16 B 왕복과 비슷하고, 기본값에 가까운 구성(boost 켬)은 10.8 µs다.
- **`CONFIG_ZBUS_MSG_SUBSCRIBER=y` 한 줄이 모든 publish에 약 35 µs를 더한다**(10.8 → 45.6 µs). `_zbus_vded_exec()`가 **채널에 msg_subscriber가 있든 없든** publish마다 `net_buf`를 heap에서 할당하고 메시지를 복사하고 끝에 해제하기 때문이다(소스: `#if defined(CONFIG_ZBUS_MSG_SUBSCRIBER)` 블록이 관찰자 루프 **앞**에 있다). 1 kHz IMU 채널이면 이것만으로 CPU의 3.5%(이 QEMU 기준)다. msg_subscriber가 꼭 필요한 채널이 하나라도 있으면 시스템의 모든 채널이 이 값을 낸다.
- `-O2`로 바꿔도 zbus는 30 µs 대다. heap 할당(`sys_heap`) · net_buf 관리 비용은 `memcpy`처럼 최적화 옵션으로 사라지지 않는다.

### 8.3 예제 10 · 11 — 블록된 수신자에게 넘기는 지연

무엇을 확인하는 코드인지: 우선순위 1 수신자가 기다리는 상태에서 우선순위 5 송신자가 보낼 때, 보내기 직전부터 수신자가 데이터를 쥔 순간까지의 시간. 기준으로 데이터가 없는 `k_sem` give → take도 잰다. `CONFIG_TIMESLICING`을 켜고 끈 두 가지로 돌렸다(C2에서 time slicing이 Zephyr의 context switch 하나에 약 430 명령을 더한다는 것을 쟀다).

```c
/* D10 ex10 — 높은 우선순위 수신자가 블록된 상태에서 보내기: 보낸 순간 → 수신자 반환까지 */
#include <zephyr/kernel.h>
#include "d10.h"

#define N 500
enum { SEM, FIFO, STACK, MSGQ16, MSGQ64, PIPE16, MBOX16, NMODE };
static const char *const nm[] = {"k_sem (ref)", "k_fifo", "k_stack", "k_msgq 16B", "k_msgq 64B",
	"k_pipe 16B", "k_mbox 16B"};
struct item { void *res; uint8_t d[12]; } it;
K_SEM_DEFINE(s, 0, 1); K_SEM_DEFINE(go, 0, 1); K_SEM_DEFINE(fin, 0, 1);
K_FIFO_DEFINE(f); K_STACK_DEFINE(st, 4); K_MBOX_DEFINE(mb);
K_MSGQ_DEFINE(q16, 16, 4, 4); K_MSGQ_DEFINE(q64, 64, 4, 4); K_PIPE_DEFINE(p, 64, 4);
static volatile uint32_t t0, acc;
static int mode;
static uint8_t buf[64], tx[64];

static void rx(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	stack_data_t v;

	for (;;) {
		k_sem_take(&go, K_FOREVER);
		for (int i = 0; i < N; i++) {
			struct k_mbox_msg m = {.size = 16, .rx_source_thread = K_ANY};

			switch (mode) {
			case SEM: k_sem_take(&s, K_FOREVER); break;
			case FIFO: (void)k_fifo_get(&f, K_FOREVER); break;
			case STACK: k_stack_pop(&st, &v, K_FOREVER); break;
			case MSGQ16: k_msgq_get(&q16, buf, K_FOREVER); break;
			case MSGQ64: k_msgq_get(&q64, buf, K_FOREVER); break;
			case PIPE16: k_pipe_read(&p, buf, 16, K_FOREVER); break;
			case MBOX16: k_mbox_get(&mb, &m, buf, K_FOREVER); break;
			}
			acc += FPGA_CNT - t0; /* 수신자가 깨어나 데이터를 손에 쥔 시점 */
		}
		k_sem_give(&fin);
	}
}
K_THREAD_DEFINE(rxt, 1024, rx, NULL, NULL, NULL, 1, 0, 0);

int main(void)
{
	k_thread_priority_set(k_current_get(), 5);
	printk("handoff latency N=%d timeslice=%d\n", N, IS_ENABLED(CONFIG_TIMESLICING));
	for (mode = 0; mode < NMODE; mode++) {
		acc = 0;
		k_sem_give(&go);
		for (int i = 0; i < N; i++) {
			struct k_mbox_msg m = {.size = 16, .tx_data = tx, .tx_target_thread = K_ANY};

			t0 = FPGA_CNT;
			switch (mode) {
			case SEM: k_sem_give(&s); break;
			case FIFO: k_fifo_put(&f, &it); break;
			case STACK: k_stack_push(&st, 1); break;
			case MSGQ16: k_msgq_put(&q16, tx, K_FOREVER); break;
			case MSGQ64: k_msgq_put(&q64, tx, K_FOREVER); break;
			case PIPE16: k_pipe_write(&p, tx, 16, K_FOREVER); break;
			case MBOX16: k_mbox_put(&mb, &m, K_FOREVER); break;
			}
		}
		k_sem_take(&fin, K_FOREVER);
		printk("%-16s %6u ns\n", nm[mode], cnt_ns(acc) / N);
	}
	qemu_exit(0);
	return 0;
}
```

zbus는 관찰자 구성이 달라 따로 잰다. subscriber는 알림을 받은 뒤 `zbus_chan_read(…, K_NO_WAIT)`로 데이터를 읽고, 그 read가 실패한 횟수도 센다.

```c
/* D10 ex11 — zbus 전달 지연: publish 순간 → listener 진입 / subscriber가 데이터를 쥔 순간 */
#include <zephyr/kernel.h>
#include <zephyr/zbus/zbus.h>
#include "d10.h"

#define N 500
enum { ZLIS, ZSUB, ZMSUB, NMODE };
static const char *const nm[] = {"zbus listener", "zbus subscriber", "zbus msg_sub"};
struct m16 { uint8_t d[16]; };
K_SEM_DEFINE(go, 0, 1); K_SEM_DEFINE(fin, 0, 1);
static volatile uint32_t t0, acc;
static int mode, rfail;
static uint8_t buf[16], tx[16];
static void lis_cb(const struct zbus_channel *c) { ARG_UNUSED(c); acc += FPGA_CNT - t0; }
ZBUS_LISTENER_DEFINE(lis, lis_cb);
ZBUS_SUBSCRIBER_DEFINE(sub, 4);
ZBUS_MSG_SUBSCRIBER_DEFINE(msub);
ZBUS_CHAN_DEFINE(c_l, struct m16, NULL, NULL, ZBUS_OBSERVERS(lis), ZBUS_MSG_INIT(0));
ZBUS_CHAN_DEFINE(c_s, struct m16, NULL, NULL, ZBUS_OBSERVERS(sub), ZBUS_MSG_INIT(0));
ZBUS_CHAN_DEFINE(c_m, struct m16, NULL, NULL, ZBUS_OBSERVERS(msub), ZBUS_MSG_INIT(0));

static void rx(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	const struct zbus_channel *ch;

	IF_ENABLED(CONFIG_ZBUS_PRIORITY_BOOST,
		   (zbus_obs_attach_to_thread(&sub); zbus_obs_attach_to_thread(&msub);))
	for (;;) {
		k_sem_take(&go, K_FOREVER);
		for (int i = 0; i < N && mode != ZLIS; i++) {
			if (mode == ZSUB) {
				zbus_sub_wait(&sub, &ch, K_FOREVER);
				if (zbus_chan_read(ch, buf, K_NO_WAIT) != 0) {
					rfail++; /* 채널이 아직 publisher 손에 있다 */
				}
			} else {
				zbus_sub_wait_msg(&msub, &ch, buf, K_FOREVER);
			}
			acc += FPGA_CNT - t0;
		}
		k_sem_give(&fin);
	}
}
K_THREAD_DEFINE(rxt, 1024, rx, NULL, NULL, NULL, 1, 0, 0);

int main(void)
{
	const struct zbus_channel *chs[] = {&c_l, &c_s, &c_m};

	k_thread_priority_set(k_current_get(), 5);
	printk("zbus handoff N=%d boost=%d timeslice=%d msg_sub=%d\n", N,
	       IS_ENABLED(CONFIG_ZBUS_PRIORITY_BOOST), IS_ENABLED(CONFIG_TIMESLICING),
	       IS_ENABLED(CONFIG_ZBUS_MSG_SUBSCRIBER));
	for (mode = 0; mode < NMODE; mode++) {
		acc = 0;
		rfail = 0;
		k_sem_give(&go);
		for (int i = 0; i < N; i++) {
			t0 = FPGA_CNT;
			zbus_chan_pub(chs[mode], tx, K_FOREVER);
		}
		k_sem_take(&fin, K_FOREVER);
		printk("%-16s %6u ns  (read failed %d/%d)\n", nm[mode], cnt_ns(acc) / N, rfail, N);
	}
	qemu_exit(0);
	return 0;
}
```

그림 10 — 전달 지연(µs). 회색은 기본(time slicing 켬), 파랑은 끔. zbus 세 행은 time slicing을 꺼도 커널 객체보다 훨씬 길다.

출력에서 볼 것:

- **time slicing이 모든 handoff에 약 14 µs를 더한다**(k_sem 19.0 → 5.0 µs). C2에서 본 "슬라이스 타이머 재설정" 비용이 context switch마다 붙는다. 같은 우선순위 스레드끼리 시간 분할이 필요 없는 설계라면 `CONFIG_TIMESLICING=n`이 IPC 지연을 3~4배 줄인다. 이하 숫자는 time slicing 끔 기준이다.
- **`k_fifo`(5.8) · `k_stack`(5.5)은 `k_sem`(5.0)과 거의 같다.** "포인터를 넘기는 것"과 "깃발을 세우는 것"의 비용 차이가 1 µs 안이다. 데이터를 넘기면서도 세마포어만큼 싸다.
- **`k_msgq` 16 B 7.9 µs, 64 B 14.1 µs.** 수신자가 기다리고 있으면 `put`이 수신자의 버퍼(`swap_data`)로 **한 번만** 복사한다. 대기자 없는 경로(예제 9)의 2회 복사보다 64 B 증분이 작다(6.2 µs vs 12.3 µs).
- **`k_mbox` 16 B 14.3 µs** — `k_msgq` 16 B의 약 1.8배. 매칭(대기 줄 순회 + `mbox_message_match`), 송신자 pend(context switch가 하나 더 생긴다), dispose(`z_reschedule_unlocked`)가 더해진다.
- **zbus subscriber 58.5 µs, msg_subscriber 67.4 µs.** `k_msgq` 16 B의 7~8배다. publish의 net_buf 할당(약 35 µs) + boost의 우선순위 set 두 번 + subscriber의 `zbus_chan_read`(sem take/give + memcpy)가 들어간다. listener(25.5 µs)는 context switch가 없는데도 net_buf 할당 때문에 `k_msgq` handoff보다 느리다.
- **boost를 끄면 subscriber가 31.9 µs로 "빨라진" 것처럼 보이지만 `read failed 500/500`이다.** 수신자가 `k_msgq_put` 순간 선점해 들어왔지만 채널은 아직 publisher가 쥐고 있어서 `zbus_chan_read(…, K_NO_WAIT)`가 **매번 실패**했다. 즉 데이터를 하나도 받지 못한 채 잰 시간이다. 그림 7 아래쪽의 실측 증거다. timeout을 준 read라면 잠들었다 깨어나 성공하겠지만 그만큼 context switch가 늘어난다. **벤치마크 숫자가 좋아졌을 때 결과값부터 확인하라**는 교훈이기도 하다.
- 드론 FC로 환산: 8 kHz gyro(125 µs 주기)를 zbus subscriber로 넘기면 이 QEMU 기준 주기의 약 47%가 전달 비용이다. rate loop의 hot path는 `k_fifo`/`k_msgq`/직접 호출로, zbus는 그 바깥(상태 · 모드 · 텔레메트리, 수십~수백 Hz)에 쓰는 것이 숫자로 맞다.

### 8.4 예제 12 — footprint

```c
/* D10 ex12 — footprint: 객체 하나만 쓰는 최소 앱 (-DD10_OBJ=<이름>으로 고른다) */
#include <zephyr/kernel.h>
#include "d10.h"
#if defined(OBJ_ZLIS) || defined(OBJ_ZSUB) || defined(OBJ_ZMSUB)
#include <zephyr/zbus/zbus.h>
struct m16 { uint8_t d[16]; };
#endif
static uint8_t b[16] __maybe_unused;
volatile int sink;

#if defined(OBJ_FIFO)
K_FIFO_DEFINE(o);
static struct { void *r; int v; } it;
#define USE() k_fifo_put(&o, &it); sink = (k_fifo_get(&o, K_NO_WAIT) != NULL)
#elif defined(OBJ_STACK)
K_STACK_DEFINE(o, 4);
static stack_data_t v;
#define USE() k_stack_push(&o, 1); sink = k_stack_pop(&o, &v, K_NO_WAIT)
#elif defined(OBJ_MSGQ)
K_MSGQ_DEFINE(o, 16, 4, 4);
#define USE() k_msgq_put(&o, b, K_NO_WAIT); sink = k_msgq_get(&o, b, K_NO_WAIT)
#elif defined(OBJ_PIPE)
K_PIPE_DEFINE(o, 64, 4);
#define USE() k_pipe_write(&o, b, 16, K_NO_WAIT); sink = k_pipe_read(&o, b, 16, K_NO_WAIT)
#elif defined(OBJ_MBOX)
K_MBOX_DEFINE(o);
static struct k_mbox_msg m = {.size = 16, .tx_data = b, .tx_target_thread = K_ANY};
#define USE() sink = k_mbox_put(&o, &m, K_NO_WAIT); k_mbox_async_put(&o, &m, NULL)
#elif defined(OBJ_ZLIS)
static void cb(const struct zbus_channel *c) { ARG_UNUSED(c); sink++; }
ZBUS_LISTENER_DEFINE(l, cb);
ZBUS_CHAN_DEFINE(o, struct m16, NULL, NULL, ZBUS_OBSERVERS(l), ZBUS_MSG_INIT(0));
#define USE() sink = zbus_chan_pub(&o, b, K_NO_WAIT)
#elif defined(OBJ_ZSUB)
ZBUS_SUBSCRIBER_DEFINE(s, 4);
ZBUS_CHAN_DEFINE(o, struct m16, NULL, NULL, ZBUS_OBSERVERS(s), ZBUS_MSG_INIT(0));
static const struct zbus_channel *ch;
#define USE() zbus_chan_pub(&o, b, K_NO_WAIT); sink = zbus_sub_wait(&s, &ch, K_NO_WAIT)
#elif defined(OBJ_ZMSUB)
ZBUS_MSG_SUBSCRIBER_DEFINE(s);
ZBUS_CHAN_DEFINE(o, struct m16, NULL, NULL, ZBUS_OBSERVERS(s), ZBUS_MSG_INIT(0));
static const struct zbus_channel *ch;
#define USE() zbus_chan_pub(&o, b, K_NO_WAIT); sink = zbus_sub_wait_msg(&s, &ch, b, K_NO_WAIT)
#else
#define USE() sink = 0
#endif

int main(void)
{
	USE();
	printk("sink=%d\n", sink);
	qemu_exit(0);
	return 0;
}
```

## 9. user mode 스레드에서는 — syscall이 있는 것만 쓸 수 있다

Zephyr의 `CONFIG_USERSPACE`에서 user 스레드는 커널 메모리에 직접 접근할 수 없고, 커널 객체는 **syscall**(`__syscall`로 선언된 API)로만 다룬다. 자세한 구조는 F 모듈에서 다룬다. 여기서는 이 노트의 객체들이 어느 쪽인지만 본다. v4.4.2 헤더에서 `__syscall` 여부를 확인했다.

| 객체 | user mode에서 | 근거 |
|---|---|---|
| `k_msgq` | ✓ 전부 | `k_msgq_put`/`get`/`put_front`/`peek`/`purge`/`get_attrs` 모두 `__syscall`. verifier가 `K_SYSCALL_MEMORY_READ(data, msg_size)`로 user 버퍼를 검사 |
| `k_stack` | ✓ | `k_stack_push`/`pop`/`alloc_init` `__syscall`. `k_stack_init`(버퍼 직접 지정)은 syscall이 아님 |
| `k_pipe` | ✓ | `k_pipe_init`/`write`/`read`/`reset`/`close` 모두 `__syscall` |
| `k_queue` / `k_fifo` / `k_lifo` | **일부만** | `k_queue_alloc_append`/`alloc_prepend`/`get`/`is_empty`/`peek_*`/`cancel_wait`만 syscall. **`k_fifo_put`이 부르는 `k_queue_append`는 일반 함수** |
| `k_mbox` | ✗ | syscall이 하나도 없다 |
| zbus | ✗ | `zbus.h`에 `__syscall`이 없다 |

`k_fifo_put`이 user mode에서 안 되는 이유는 설계상 당연하다. 커널이 아이템의 첫 word에 쓰는데, 그 아이템은 user 메모리에 있고, 커널 리스트가 user 메모리를 가리키게 되면 user가 커널 자료구조를 조작할 수 있다. 그래서 user는 `k_fifo_alloc_put`(커널이 자기 heap에 노드를 만들고 user 포인터는 `data`로만 들고 있음)만 쓸 수 있다. `queue.c`의 주석: "Data was directly placed in the queue, the first word reserved for the linked list. User mode isn't allowed to do this, although it can get data sent this way."

### 9.1 예제 13 — user 스레드에서 msgq · alloc_put · 그리고 k_fifo_put

무엇을 확인하는 코드인지: user 스레드에 객체 접근 권한과 resource pool을 주고 `k_msgq_put`, `k_fifo_alloc_put`, `k_fifo_put`을 차례로 부른다. 마지막 것이 MPU fault를 내면 fatal handler를 덮어써서 **그 스레드만** 죽게 한다.

```c
/* D10 ex13 — user mode 스레드에서 쓸 수 있는 IPC: syscall이 있는가 */
#include <zephyr/kernel.h>
#include "d10.h"

K_MSGQ_DEFINE(uq, 4, 4, 4);
K_FIFO_DEFINE(uf);
K_HEAP_DEFINE(uheap, 256);
K_THREAD_STACK_DEFINE(ustack, 1024);
static struct k_thread uthr;
static uint32_t token = 0x7777;

void k_sys_fatal_error_handler(unsigned int reason, const struct arch_esf *esf)
{
	ARG_UNUSED(esf);
	printk("fatal handler: reason=%u -> return = abort only the faulting thread\n", reason);
}

static void user_fn(void *a, void *b, void *c)
{
	ARG_UNUSED(a); ARG_UNUSED(b); ARG_UNUSED(c);
	uint32_t v = 7;

	printk("user: k_is_user_context=%d\n", k_is_user_context());
	printk("user: k_msgq_put       -> %d\n", k_msgq_put(&uq, &v, K_NO_WAIT));
	printk("user: k_fifo_alloc_put -> %d\n", k_fifo_alloc_put(&uf, &token));
	printk("user: k_fifo_put (plain function, not a syscall) ...\n");
	k_fifo_put(&uf, &token);
	printk("user: survived\n");
}

int main(void)
{
	uint32_t v;

	k_thread_create(&uthr, ustack, K_THREAD_STACK_SIZEOF(ustack), user_fn, NULL, NULL, NULL,
			2, K_USER, K_FOREVER);
	k_object_access_grant(&uq, &uthr);
	k_object_access_grant(&uf, &uthr);
	k_thread_heap_assign(&uthr, &uheap); /* alloc_put용 resource pool */
	k_thread_start(&uthr);
	int r = k_thread_join(&uthr, K_MSEC(200));

	printk("main: join -> %d\n", r);
	printk("main: msgq got %d", k_msgq_get(&uq, &v, K_NO_WAIT));
	printk(" (v=%u)\n", v);
	uint32_t *p = k_fifo_get(&uf, K_NO_WAIT);

	printk("main: fifo got %p (&token=%p)\n", (void *)p, (void *)&token);
	qemu_exit(0);
	return 0;
}
```

## 10. RTOS 커널 안에서는 무슨 일이 일어나나

### 10.1 공통 패턴 — "대기자에게 직접, 없으면 버퍼에"

다섯 커널 객체(+ zbus가 쓰는 `k_msgq`/`k_fifo`)는 같은 두 함수 쌍으로 만들어져 있다.

- **기다리기**: `_current->base.swap_data = 내 받을 곳` → `z_pend_curr(&obj->lock, key, &obj->wait_q, timeout)`(`kernel/sched.c:691`). `z_pend_curr`는 현재 스레드를 ready queue에서 빼서 wait_q에 우선순위 순으로 넣고, timeout을 걸고, `z_swap`으로 스위치한다(C1 §5.3, C12).
- **깨우기**: `t = z_unpend_first_thread(&obj->wait_q)`(`kernel/include/ksched.h:183`, 대기 줄의 머리 = 가장 높은 우선순위) → 데이터를 `t->base.swap_data`가 가리키는 곳에 넣거나, 반환값으로 꽂고(`z_thread_return_value_set_with_data`) → `z_ready_thread(t)` → `z_reschedule(&obj->lock, key)`.

`swap_data`는 `struct _thread_base`의 `void *` 하나다. 커널은 이 포인터 하나로 "기다리는 스레드가 데이터를 받을 장소"를 객체마다 다르게 해석한다.

| 객체 | 기다리는 쪽이 `swap_data`에 적는 것 | 깨우는 쪽이 하는 일 |
|---|---|---|
| `k_queue` get | (없음) | `prepare_thread_to_run(t, data)` — **아이템 포인터를 반환값으로** |
| `k_stack` pop | (없음) | `z_thread_return_value_set_with_data(t, 0, (void *)data)` — 값을 포인터 자리에 |
| `k_msgq` get | 수신 버퍼 주소 | `memcpy(t->base.swap_data, data, msg_size)` — **수신자 버퍼로 직접 1회 복사** |
| `k_msgq` put (가득 참) | **송신 데이터 주소** | get이 메시지를 하나 꺼낸 뒤 `memcpy(write_ptr, t->base.swap_data)` — 기다리던 송신자의 메시지를 대신 넣어 준다 |
| `k_pipe` read | 수신자 스택의 `struct pipe_buf_spec { data, len, used }` | `copy_to_pending_readers()`가 `used`를 채우고, `used == len`일 때만 깨움 |
| `k_mbox` get / put | `struct k_mbox_msg *` | 매칭 함수가 두 descriptor를 서로 고침, 데이터는 `k_mbox_data_get`의 `memcpy` 한 번 |

### 10.2 객체별로 읽을 곳

| 파일 (v4.4.2) | 먼저 읽을 함수 | 읽으면서 볼 것 |
|---|---|---|
| `kernel/queue.c` | `queue_insert` (133), `z_impl_k_queue_get` (336), `z_queue_node_peek` | `alloc` 가지와 flag 비트 0x1, 대기자 있으면 할당 안 함, `k_queue_remove` (373)에 lock 없음 |
| `kernel/stack.c` | `z_impl_k_stack_push` (119), `z_impl_k_stack_pop` (166) | `CHECKIF` 가득 참 검사, `-EBUSY`/`-EAGAIN` |
| `kernel/msg_q.c` | `put_msg_in_queue` (150), `z_impl_k_msgq_get` (300), `z_impl_k_msgq_purge` (463) | `put_front`의 `read_ptr` 감소, 공용 wait_q, get이 대기 writer 메시지를 대신 넣기 |
| `kernel/pipe.c` | `z_impl_k_pipe_write` (150), `copy_to_pending_readers` (96), `wait_for` (43) | `LOCK_SCHED_SPINLOCK` 안의 직접 복사, `PIPE_FLAG_RESET`과 `waiting` 카운터, `CONFIG_KERNEL_COHERENCE`면 직접 복사 포기 |
| `kernel/mailbox.c` | `mbox_message_put` (213), `k_mbox_get` (385), `mbox_message_dispose` (156) | `_WAIT_Q_FOR_EACH`로 매칭 상대 찾기, 매칭 뒤 `z_pend_curr(..., NULL, K_FOREVER)`, dummy thread |
| `subsys/zbus/zbus.c` | `zbus_chan_pub` (455), `chan_lock` (401), `_zbus_vded_exec` (235), `_zbus_notify_observer` (179) | HLP boost, publish마다 net_buf, `-ENOMEM`이면 조기 return, subscriber = `k_msgq_put(&chan)` |

몇 가지 소스 사실을 더 적어 둔다.

- `k_pipe`의 직접 복사는 `LOCK_SCHED_SPINLOCK` 블록 안에서 한다. 주석: reader의 `pipe_buf_spec`는 reader 스택에 있으므로 "the thread unpended only if it received all the data it wanted, without racing with a potential thread timeout/cancellation event". 즉 reader가 타임아웃으로 깨어나는 순간과 writer가 그 스택에 쓰는 순간이 겹치지 않게 스케줄러 잠금을 잡는다.
- `CONFIG_KERNEL_COHERENCE`(스택이 coherent 메모리에 없는 SMP 시스템, 예: 일부 Xtensa)에서는 pipe가 직접 복사를 포기하고 reader를 전부 깨운다. 같은 API가 하드웨어에 따라 다른 경로를 탄다.
- zbus의 정적 관찰자 순서는 링커가 만든다. `ZBUS_CHAN_DEFINE`이 관찰자마다 `STRUCT_SECTION_ITERABLE(zbus_channel_observation, <채널이름><00..63>)`을 만들고, iterable section은 **이름순으로 정렬**되어 링크된다. `_zbus_init()`(`SYS_INIT(..., APPLICATION, ...)`)이 부팅 때 이 배열을 훑어 채널마다 `observers_start_idx`/`end_idx`를 채운다. 그래서 VDED는 배열 인덱스 범위만 돈다(리스트 순회가 아니다). 인덱스 접두어가 `00`~`63`이므로 정적 관찰자는 채널당 64개까지다.
- zbus subscriber의 큐는 `K_MSGQ_DEFINE(_zbus_observer_queue_<name>, sizeof(struct zbus_channel *), qsize, …)`, msg_subscriber의 큐는 `K_FIFO_DEFINE`이다. zbus는 이 노트의 커널 객체를 조립한 것이다.

## 11. 실무에서 다시 보기

### 11.1 드론 FC — 어디에 무엇을 쓰나

예를 들어 STM32H7급 드론 비행 제어기라면 데이터 흐름을 주기와 성질로 나눈다.

| 흐름 | 주기 · 크기 | 고르는 것 | 이유 (이 노트의 숫자) |
|---|---|---|---|
| IMU DMA 완료 ISR → rate loop | 8 kHz, 버퍼 포인터 | `k_fifo` 또는 `k_sem` + 공유 버퍼 | handoff 5.8 µs로 `k_sem`과 거의 같음, 0 copy |
| DMA 버퍼 반납 | 같은 주기 | `k_stack` free-list | push/pop 1.6 µs, ISR에서 push 가능 |
| rate loop → 모터 출력 | 같은 스레드 안 | 함수 호출 | IPC 없음이 최선 |
| 자세 추정 결과 → 위치 제어 · 텔레메트리 · 로깅 | 100~500 Hz, 32~64 B | zbus 채널 (listener 1 + subscriber 1~2 + msg_sub 1) | 1:N, 생산자가 소비자를 모름. 비용 수십 µs는 이 주기에서 감당 가능 |
| 배터리 · 모드 · arm 상태 | 수 Hz | zbus 채널, 필요한 곳만 listener | failsafe listener가 publish 안에서 즉시 반응 |
| GCS 명령 (MAVLink 파싱 결과) | 가끔, 고정 크기 | `k_msgq` (`put_front`로 긴급 명령) | 순서와 개수가 중요, 큐잉 필요 |
| 텔레메트리 UART TX 바이트 | 연속 바이트 | `k_pipe` (또는 `ring_buf` + UART async API) | 경계 없는 스트림, close로 종료 표현 |
| 펌웨어 업데이트 청크 → 플래시 스레드 | 가끔, 가변 길이 | `k_mbox` 동기 put 또는 `k_msgq` + 응답 `k_sem` | "받았다" 확인 후 다음 청크 |

zbus로 상태 채널을 정의하는 모양은 이렇다(빌드 · 실행은 예제 7과 같은 구조라 생략).

```c
struct att_msg { uint32_t t_us; float q[4]; float rate[3]; };   /* 32 B */
ZBUS_CHAN_DEFINE(att_chan, struct att_msg, NULL, NULL,
		 ZBUS_OBSERVERS(failsafe_lis, posctl_sub, telem_sub, blackbox_msub),
		 ZBUS_MSG_INIT(0));
/* 생산자(추정 스레드): 소비자를 모른다 */
zbus_chan_pub(&att_chan, &att, K_USEC(200));
```

관찰자 순서에 원칙을 둔다: **listener(짧은 것) → 높은 우선순위 subscriber → 낮은 우선순위 subscriber → msg_subscriber(맨 뒤)**. 예제 8에서 본 대로 msg_subscriber가 `-ENOMEM`을 내면 그 뒤가 통지를 못 받기 때문이다. 그리고 `CONFIG_ZBUS_MSG_SUBSCRIBER`는 시스템 전체의 publish 비용을 올리므로(§8.2) 블랙박스 로깅 같은 "전부 받아야 하는" 소비자가 정말 필요할 때만 켠다.

### 11.2 센서 허브 MCU — Linux SoC 옆에서

Linux SoC 옆의 센서 허브(예: IMU 타임스탬프 + 융합 전처리)에서는 SPI/UART로 SoC에 보내는 출력이 **바이트 스트림**이다. 프레이밍 계층이 앞에 있으면 `k_pipe`보다 `k_msgq`(프레임 단위) → 전송 스레드가 직렬화하는 구조가 단순하다. `k_pipe`는 "로그 문자열처럼 길이가 제각각이고 경계가 의미 없는" 것에 남겨 둔다. 그리고 SoC 쪽과 채널 개념을 공유하고 싶다면 4.4의 zbus proxy agent(`CONFIG_ZBUS_PROXY_AGENT`, EXPERIMENTAL)가 IPC로 채널을 다른 도메인에 비추는 기능이다. 실험적 기능이라 제품에 넣기 전에 성숙도를 따져야 한다.

## 13. 면접에서 이렇게 말한다

**Q.** "What is the difference between k_fifo and k_msgq in Zephyr? When would you use each?"

**A.** `k_fifo`는 포인터를 넘기는 intrusive 큐다. 아이템의 첫 word를 커널이 next 포인터로 쓰고, 복사가 없다. 대신 아이템 수명과 재사용 규칙을 앱이 책임진다. `k_msgq`는 고정 크기 메시지를 커널 링버퍼로 복사한다. 작은 메시지는 msgq가 단순하고 안전하며 user mode에서도 된다. 큰 버퍼는 fifo + 메모리 풀이 빠르다. 내 측정에서 fifo handoff는 세마포어와 1 µs 이내였고, msgq는 64 B에서 두 배였다.

> "k_fifo passes pointers: it's an intrusive singly linked list where the kernel uses the first word of each item as the next pointer, so there's no copy, but the application owns the item's lifetime — you can't reuse it or let it go out of scope until the consumer is done. k_msgq copies fixed-size messages into a kernel ring buffer, so ownership is simple and it works from user mode. I use msgq for small fixed messages like commands, and fifo plus a k_mem_slab pool for large buffers like DMA frames. On a QEMU Cortex-M3 the fifo handoff cost about the same as a semaphore, while a 64-byte msgq handoff cost more than twice that, mostly memcpy under -Os."

**꼬리 질문**: "What happens if you put a stack variable into a k_fifo?" → 함수가 끝나면 아이템이 사라지고, 그 자리의 쓰레기가 next 포인터로 읽혀서 소비자 쪽 `k_queue_get` 안에서 fault가 난다. 버그는 생산자에 있는데 backtrace는 커널을 가리킨다.

**Q.** "Can a zbus subscriber miss messages? How do you guarantee delivery?"

**A.** 놓칠 수 있다. subscriber는 채널 포인터만 큐로 받고, 값은 나중에 `zbus_chan_read`로 읽으므로 그 사이 publish가 여러 번이면 최신값만 본다. 큐가 차면 publisher가 timeout까지 막히거나 실패한다. 모든 메시지가 필요하면 msg_subscriber(매 publish의 net_buf 복사본)를 쓰는데, 그 풀이 고갈되면 publish가 `-ENOMEM`을 내고 목록 뒤쪽 관찰자는 통지를 못 받는다. 그래서 msg_subscriber는 목록 맨 뒤, 풀 크기와 소비자 우선순위를 설계한다.

> "Yes. A plain subscriber only receives a pointer to the channel through a message queue and reads the current value later, so if several publishes happen before it runs, it sees only the latest — I reproduced a low-priority subscriber reading sequence number 3 three times. If you need every message, use a message subscriber, which gets a net_buf copy per publish. But those come from a shared pool; when it's exhausted the publish returns -ENOMEM and the dispatcher stops, so observers listed after it miss the notification. So I put message subscribers last, size the pool, and give consumers enough priority."

**Q.** "Explain zbus priority boost. Why does zbus need it?"

**A.** 채널 잠금이 세마포어라 priority inheritance가 없다. 그래서 zbus는 Highest Locker Protocol을 직접 구현한다. 관찰자 스레드 중 가장 높은 우선순위(HOP)보다 한 단계 높게 publisher를 올려서 publish 전체를 선점 없이 끝낸다. 없으면 높은 우선순위 subscriber가 알림 순간 선점해 들어왔다가 아직 잠긴 채널에 막혀 context switch만 늘어난다. 실제로 boost를 끄고 재 보니 `K_NO_WAIT` read가 500번 모두 실패했다.

> "The channel lock is a semaphore, so there's no priority inheritance. zbus implements the Highest Locker Protocol: each channel knows the highest priority among observers attached to threads, and before locking it raises the publisher one level above that, then restores it on unlock. Without it, a high-priority subscriber gets woken by the notification, preempts the publisher, and then blocks on the channel the publisher still holds — extra context switches. I measured it: with boost off, every one of 500 non-blocking reads in the subscriber failed because the channel was still locked. The cost is two priority changes per publish and that unrelated mid-priority threads wait during the boosted section, so listeners must be short."

**꼬리 질문**: "What do you need to do for boost to work?" → 관찰자 스레드에서 `zbus_obs_attach_to_thread()`. 안 부르면 HOP를 모른다. runtime observer는 HOP 계산에 안 들어간다.

**Q.** "The Zephyr pipe API changed. What's different now?"

**A.** 4.1에서 다시 썼고 4.3에서 옛 API를 지웠다. `k_pipe_write`/`read`가 바이트 수를 반환하고 `min_xfer`가 없어졌다. 동적 할당과 남은 바이트 조회가 없어졌고 `k_pipe_reset`과 `k_pipe_close`가 생겼다. 의미는 "len을 다 채울 때까지 기다리고, 타임아웃이면 부분"이다. close 뒤에도 남은 데이터는 읽힌다.

> "It was rewritten in Zephyr 4.1 and the legacy API was removed in 4.3. Now it's k_pipe_write and k_pipe_read returning the byte count, with no min_xfer parameter; dynamic allocation and the read/write-available queries are gone; and there are k_pipe_reset, which drops data and wakes waiters with -ECANCELED, and k_pipe_close, after which readers can still drain what's left and then get -EPIPE. A blocking read waits until the full length is satisfied, and on timeout it returns the partial count — so you must handle short reads. It's a byte stream with no message boundaries."

**Q.** "When would you use k_mbox?"

**A.** 송신자가 "수신자가 받았다"까지 기다려야 하거나, 특정 스레드를 지정해야 하거나, 큰 가변 길이 데이터를 커널 버퍼 없이 한 번에 복사하고 싶을 때다. `info` 값을 서로 바꾸니 짧은 응답 코드를 같이 받을 수 있다. 다만 ISR · user mode에서 안 되고, 매칭 후에는 timeout이 없으며, handoff가 msgq의 두 배 가까이 비싸서 새 코드에서는 드물다.

> "When the sender needs to know the receiver actually took the data, or when you want to target a specific thread, or move a large variable-size block with a single copy from sender buffer to receiver buffer. The two sides also swap an info word, which works as a cheap acknowledgment code. The downsides: no ISR use, no syscalls for user mode, the sender's timeout only covers finding a receiver — after the match it waits forever until the receiver calls k_mbox_data_get — and the async variant can still block when its descriptor pool is empty. In my measurement it cost about 1.8 times a msgq handoff, so I usually prefer a msgq plus a response semaphore."

**Q.** "You're porting FreeRTOS firmware with xQueueSend everywhere to Zephyr. How do you map it?"

**A.** 아이템 크기로 나눈다. 작은 값 복사 큐는 `k_msgq`로 거의 1:1(`xQueueSendToFront` → `k_msgq_put_front`, 단 블록 안 함, `FromISR`는 같은 함수 + `K_NO_WAIT`). 포인터를 넣던 큐는 `k_fifo` + 첫 word 예약 또는 `k_stack`. stream/message buffer는 `k_pipe` 또는 `ring_buf`. 그리고 "여러 태스크에 같은 값을 뿌리려고 큐를 여러 개 만든" 곳이 zbus 후보다. 측정 없이 전부 zbus로 바꾸지는 않는다. A5의 API 대응표가 출발점이다.

> "I classify by what the queue carries. Small by-value queues map almost one-to-one onto k_msgq — send-to-front becomes k_msgq_put_front, which doesn't block, and FromISR variants become the same call with K_NO_WAIT. Queues of pointers become k_fifo with a reserved first word, or k_stack for free-lists. Stream and message buffers become k_pipe or a ring_buf. Places where the code fans one value out through several queues are zbus candidates, but I wouldn't move hot paths to zbus: in my measurement a zbus subscriber handoff was seven times a msgq handoff."

**Q.** "Which of these IPC objects can a user-mode thread use?"

**A.** syscall이 있는 것만: `k_msgq`, `k_stack`, `k_pipe`, 그리고 `k_queue`의 일부(`k_fifo_alloc_put`, get). `k_fifo_put`은 커널 리스트가 user 메모리를 가리키게 되므로 syscall이 아니고, 부르면 MPU fault다. `k_mbox`와 zbus는 syscall이 없다.

> "Only those exposed as syscalls: k_msgq, k_stack, k_pipe, and part of k_queue — get, and alloc_append, which is what k_fifo_alloc_put uses: the kernel allocates the list node from the thread's resource pool so the kernel list never points into user memory. Plain k_fifo_put isn't a syscall; calling it from a user thread faulted on the MPU when the kernel code tried to touch the fifo's tail. k_mbox and zbus have no syscalls at all, so user-mode partitions need to talk through msgq or pipe."

## 14. 직접 해보기

1. **개념**: `k_fifo_put`을 두 번 같은 아이템으로 부르면(사이에 get 없이) 리스트가 어떻게 되는지, 아이템이 (a) 머리, (b) 중간, (c) 꼬리일 때 각각 그림으로 그려라.
   정답/힌트: `sys_sfnode_init`이 next를 0으로 지운 뒤 꼬리에 붙인다. (b)는 예제 2처럼 뒤쪽이 떨어져 나가고, (c)는 tail->next = 자기 자신이 되어 get이 같은 아이템을 무한히 돌려준다.
2. **코드**: 예제 3을 고쳐서 purge 뒤에도 reader가 `-ENOMSG`를 받으면 다시 기다리게 하고, purge 직후 넣은 메시지를 정상으로 받는지 확인하라.
   정답/힌트: `while ((r = k_msgq_get(...)) == -ENOMSG) { }` 루프. `-EAGAIN`(timeout)과 구분한다.
3. **코드**: 크기 0인 pipe(`K_PIPE_DEFINE(p0, 0, 4)`)를 만들고, reader가 기다리지 않을 때 `k_pipe_write(…, K_NO_WAIT)`가 무엇을 돌려주는지, reader가 기다릴 때는 어떻게 되는지 재라.
   정답/힌트: 링버퍼가 없으니 대기자가 없으면 `-EAGAIN`, 있으면 `copy_to_pending_readers` 경로로만 전달된다.
4. **측정**: 예제 10에 `k_lifo`와 `k_queue_alloc_append` 경로(`k_fifo_alloc_put`, 시스템 heap 필요)를 추가해서 handoff 지연을 재고, 대기자가 있으면 할당을 건너뛴다는 소스 주장과 맞는지 확인하라.
   정답/힌트: 수신자가 이미 기다리면 alloc 가지에 도달하지 않으므로 `k_fifo_put`과 거의 같아야 한다. 대기자 없는 경로(예제 9 스타일)에서는 heap 비용만큼 커진다.
5. **측정**: 예제 9의 zbus 3 observers를 `CONFIG_ZBUS_MSG_SUBSCRIBER_BUF_ALLOC_STATIC=y` + `CONFIG_ZBUS_MSG_SUBSCRIBER_NET_BUF_STATIC_DATA_SIZE=16`으로 다시 재라. 동적(heap) 풀과 무엇이 다른가?
   정답/힌트: 고정 풀은 heap 할당이 없지만 `net_buf_fixed_cb`에 `ref`가 없어서 clone마다 데이터를 복사한다(`net_buf_clone`). msg_subscriber가 여럿이면 차이가 커진다.
6. **설계**: 드론 FC의 "arm 상태" 채널에 failsafe listener, 모터 출력 subscriber(우선순위 높음), GCS 텔레메트리 msg_subscriber를 붙이려 한다. 관찰자 순서와 각 스레드의 `zbus_obs_attach_to_thread` 여부, publish timeout을 정하고 이유를 써라.
   정답/힌트: listener → 모터 subscriber(attach) → 텔레메트리 msg_sub(맨 뒤). publish는 상태 스레드에서 짧은 timeout, ISR이면 `K_NO_WAIT`. listener는 플래그만 세운다.
7. **조사**: `kernel/queue.c`의 `k_queue_remove`와 `k_queue_unique_append`가 lock을 잡지 않는 것이 실제로 경쟁을 만드는지, 우선순위가 다른 두 스레드와 `k_timer` ISR로 재현을 시도하라.
   정답/힌트: ISR이 append하는 동안 스레드가 remove로 리스트를 걷게 만들고, 남은 아이템 수가 넣은 수 − 꺼낸 수와 맞는지 검사한다. 재현이 안 되더라도 "안 됐다"를 기록한다.

## 15. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| intrusive list | 아이템 안에 링크를 박는 리스트 | `k_fifo`가 아이템의 첫 word를 next로 쓰는 방식 |
| `sys_sflist` | flagged singly linked list | next 포인터 하위 2비트를 플래그로 쓰는 단일 연결 리스트, `k_queue`의 저장소 |
| `alloc_node` | `k_queue`가 heap에 만드는 8 B 노드 | `k_fifo_alloc_put`이 예약 word 없는 데이터를 넣을 때 사용 |
| resource pool | 스레드에 붙은 `k_heap` | `z_thread_malloc`이 쓰는 heap, 부모 스레드에서 상속 |
| `swap_data` | `struct _thread_base`의 `void *` | 블록된 스레드가 "받을 곳"을 적어 두는 칸, 깨우는 쪽이 여기에 직접 쓴다 |
| `z_pend_curr` / `z_unpend_first_thread` | 기다리기 / 깨울 스레드 고르기 | 모든 IPC 객체가 공유하는 두 커널 함수 (C1, C12) |
| `@isr_ok` | Zephyr Doxygen 태그 | ISR에서 불러도 된다는 공식 표시 |
| `k_pipe_close` | 4.1 신설 | 대기자를 깨우고 쓰기를 막되 남은 데이터는 읽게 한다 |
| rendezvous | 만나서 넘기기 | 송신자와 수신자가 동시에 있어야 전달되는 방식 (`k_mbox`, 크기 0 pipe) |
| dummy thread | `_THREAD_DUMMY` 상태의 가짜 스레드 | `k_mbox_async_put`이 송신자 대신 대기 줄에 세우는 descriptor |
| zbus channel | 타입 있는 메시지 1개 + 잠금 + 관찰자 목록 | publish = 값 바꾸고 알리기 |
| VDED | Virtual Distributed Event Dispatcher | publish 안에서 관찰자에게 차례로 통지하는 zbus 루프 |
| listener / subscriber / msg_subscriber | zbus 관찰자 종류 | 콜백 / 채널 포인터 알림 / 메시지 복사본 |
| HOP | Highest Observer Priority | 채널의 관찰자 스레드 중 가장 높은 우선순위, boost 기준 |
| HLP | Highest Locker Protocol | 잠그는 쪽을 미리 최고 우선순위로 올리는 우선순위 역전 대책 |
| `net_buf` | Zephyr의 참조 계수 버퍼 | zbus msg_subscriber 복사본의 그릇, 풀에서 할당 |
| syscall | user → kernel 호출 경계 | `__syscall`로 선언된 API만 user mode에서 쓸 수 있다 (F 모듈) |

## 16. 요약 & 체크리스트

Zephyr는 FreeRTOS의 "큐 하나"를 성질별로 나눠 놓았다. 포인터를 넘기는 `k_fifo`/`k_lifo`(`k_queue`, 아이템 첫 word 예약, 0 copy, 수명은 앱 책임), word 하나의 `k_stack`(버퍼 free-list), 고정 크기 복사의 `k_msgq`(`put_front`는 블록 안 함, purge는 reader도 `-ENOMSG`로 깨움, 정렬은 4.4.2 문서상 불필요), 4.1에서 다시 쓴 바이트 스트림 `k_pipe`(len을 다 채우거나 타임아웃이면 부분, `reset`/`close`), 송수신자가 만나는 `k_mbox`(대상 지정 · info 교환 · 1회 복사, 매칭 후 timeout 없음, ISR · user mode 불가). 그 위에 zbus가 채널 · 관찰자 모델을 얹는다. listener는 publisher 문맥에서 즉시, subscriber는 알림만 받고 최신값을 읽으며, msg_subscriber는 net_buf 복사본을 받되 풀이 고갈되면 뒤쪽 관찰자까지 굶긴다. 채널 잠금은 세마포어라 zbus가 HLP boost를 직접 구현한다. 측정은 같은 결론을 숫자로 줬다: time slicing을 끈 handoff에서 `k_fifo` 5.8 µs ≈ `k_sem` 5.0 µs, `k_msgq` 16 B 7.9 µs, `k_mbox` 14.3 µs, zbus subscriber 58.5 µs. `CONFIG_ZBUS_MSG_SUBSCRIBER` 한 줄이 모든 publish에 약 35 µs를, `-Os`의 바이트 `memcpy`가 64 B msgq에 약 14 µs를, time slicing이 모든 handoff에 약 14 µs를 더한다(모두 QEMU icount 기준). 커널 안에서는 모든 객체가 `z_unpend_first_thread` → `swap_data`로 직접 전달, 아니면 버퍼에 넣기 / `z_pend_curr`의 같은 골격이다.

- [ ] Zephyr 데이터 전달 객체 7종 + zbus를 "참조/복사 · 크기 · ISR · 수신자 수 · 동기 · 소유권"으로 표 없이 말할 수 있다
- [ ] `k_fifo` 첫 word 예약의 이유(sflist next + 플래그)와 이를 어기는 세 가지 버그를 설명할 수 있다
- [ ] `k_fifo_alloc_put`이 어느 heap을 쓰는지(resource pool, 상속, ISR이면 시스템 heap) 안다
- [ ] `k_stack`의 에러 코드(`-ENOMEM`, `-EBUSY`, `-EAGAIN`)가 `k_msgq`(`-ENOMSG`)와 다르다는 것을 안다
- [ ] `k_msgq_put_front`가 블록하지 않고, `k_msgq_purge`가 빈 큐의 reader까지 깨운다는 것을 소스로 설명할 수 있다
- [ ] 4.1 pipe API 대응표와 "len을 다 채우거나 타임아웃이면 부분" 규칙, `close` 뒤의 동작을 말할 수 있다
- [ ] `k_mbox`의 매칭 조건, info 교환, 매칭 후 timeout 없음, async의 dummy thread · `k_stack` 풀을 설명할 수 있다
- [ ] zbus 관찰자 넷의 실행 문맥과 "놓칠 수 있나"를 구분해 말할 수 있다
- [ ] HLP boost의 동작(HOP - 1), `zbus_obs_attach_to_thread`의 필요성, 끄면 무엇이 일어나는지 안다
- [ ] msg_subscriber 풀 고갈 시 VDED가 조기 return한다는 것과 관찰자 순서 원칙을 안다
- [ ] user mode에서 쓸 수 있는 객체(syscall 여부)를 안다
- [ ] 이 노트의 측정값 중 세 개(`k_fifo` ≈ `k_sem`, zbus msg_subscriber Kconfig +35 µs, time slicing +14 µs)를 근거와 함께 말할 수 있다
