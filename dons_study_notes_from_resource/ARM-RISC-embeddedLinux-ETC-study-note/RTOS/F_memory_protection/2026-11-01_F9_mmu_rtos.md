# F9. MMU를 쓰는 RTOS — 프로세스가 있는 실시간 OS

> **이 노트를 다 읽으면**: "평면 RTOS → MPU 격리 → MMU 프로세스 RTOS → Linux + PREEMPT_RT" 스펙트럼에서 각 단계가 무엇을 사고 무엇을 내주는지(주소 공간, IPC, 결정성 비용, 인증) 표 하나로 말할 수 있다 · NuttX를 kernel build(프로세스마다 주소 공간)로 직접 빌드해 "같은 가상 주소, 다른 내용"과 "한 프로세스만 죽는 결함 격리"를 flat build와 나란히 보여 줄 수 있다 · Zephyr를 Cortex-A53 MMU 위에서 userspace로 돌려 page table을 직접 걷고, 같은 코드의 syscall·전환 비용을 Cortex-M3 MPU와 명령 수로 비교할 수 있다 · QNX 메시지 패싱·VxWorks RTP의 프로세스 모델과 Cortex-R82(EL1 MMU 선택 + MPU)를 공개 자료 범위에서 설명하고, 드론·로봇·차량에서 어느 쪽을 고를지 결정 흐름으로 답할 수 있다
> **왜 필요한가**: 국방·항공 회사는 VxWorks와 INTEGRITY, 차량 회사는 QNX와 AUTOSAR Adaptive, 드론 회사는 PX4(NuttX)를 쓴다. 면접에서 "Why not just use Linux?", "What does an MMU buy you on an RTOS, and what does it cost?"가 나오면 MCU RTOS만 아는 사람과 시야 차이가 바로 드러난다. Don의 SSD 세계(Cortex-R82 기반 차세대 컨트롤러)에서도 "MMU를 켤 것인가"가 실제 설계 질문이다
> **Don 기준 난이도**: MMU·TLB·page table 자체는 EL F11에서, Linux RT 메모리 규칙(mlockall·prefault)은 EL N1·N2에서 이미 봤다 / 새로 배울 부분은 RTOS가 MMU를 쓰는 **세 가지 방식**(보호만, 프로세스마다 주소 공간, 마이크로커널 + 메시지), NuttX kernel build의 빌드 구조(커널과 앱을 따로 빌드, syscall proxy), Zephyr arm64의 domain별 page table과 ASID, MMU가 결정성에 매기는 값(TLB miss·page walk·page fault)을 숫자로 보는 법
> **선행 노트**: A6(RTOS 지형 — QNX·VxWorks·NuttX 시장 사실은 거기), B9(Cortex-R52 MPU 2단계), C8(커널 진입 경로 — M3에서 잰 syscall 비용), C10(Zephyr A53 SMP 실행), C11(ARINC 653 시간 분할), F4(MPU), F5(유저 모드 격리 — 이 노트와 같은 날 작성), EL F11(가상 메모리 깊게), EL N1·N2(PREEMPT_RT, RT 메모리 튜닝)

## 0. 큰 그림 — 이게 왜 필요한가

### 0.1 직관 — 같은 건물, 칸막이의 종류가 다르다

지금까지 RTOS 노트의 펌웨어는 전부 **방 하나짜리 사무실**이었다. FreeRTOS든 Zephyr든 Cortex-M 위에서는 태스크 전부가 같은 주소 공간(address space — CPU가 내는 주소가 가리키는 메모리 세상)을 쓰고, 기본 설정에서는 어느 태스크든 아무 주소나 쓸 수 있다. Don의 SSD 펌웨어도 그랬다. FTL 코드가 잘못된 포인터로 NAND 드라이버의 큐를 덮으면, 그 버그는 몇 분 뒤 전혀 다른 곳에서 assert로 드러난다.

F4·F5는 여기에 **칸막이(MPU)** 를 세웠다. 방은 여전히 하나지만 "이 태스크는 이 책상(리전)만 만진다"를 하드웨어가 검사한다. 이 노트는 그다음 단계다. **MMU(Memory Management Unit)** 가 있는 코어에서는 칸막이 대신 **각자 다른 방(가상 주소 공간)** 을 줄 수 있다. 프로세스(process — 자기 주소 공간을 가진 실행 단위)마다 page table이 따로 있어서, 같은 주소 `0xC0101008`이 프로세스 A에서는 A의 변수, B에서는 B의 변수를 가리킨다. 한 프로세스가 엉뚱한 곳을 쓰면 그 프로세스만 죽고 나머지는 계속 돈다.

문제는 값이다. 방을 바꿀 때마다 CPU는 page table 기준점(RISC-V `satp`, arm64 `TTBR0_EL1`)을 바꾸고, TLB(Translation Lookaside Buffer — 가상→물리 변환 결과 캐시)를 비우거나 태그로 구분해야 한다. TLB에 없는 주소는 page table을 메모리에서 몇 단계 걸어서(page walk) 찾는다. 아직 물리 페이지가 붙지 않은 주소는 page fault로 커널에 들어간다. 이 셋은 전부 **"평소에는 안 보이다가 가끔 튀는" 지연**이다. 실시간 OS가 MMU를 쓸 때 고민하는 것은 결국 "격리를 얼마나 사고, 그 값으로 결정성을 얼마나 내주나"다.

### 0.3 Don의 경험과 연결

SSD 컨트롤러 펌웨어에는 MMU가 없었거나, 있어도 **identity map(가상 주소 = 물리 주소)으로 캐시 속성만 정하는 용도**였다. 이것이 바로 "MMU를 쓰지만 주소 공간은 하나"인 모델이고, RTEMS와 Zephyr(arm64)가 지금도 이렇게 쓴다(§3에서 page table을 걸어 확인한다). 프로세스마다 주소 공간을 나누는 모델은 SSD 세계에서는 낯설지만, Cortex-R82가 선택 MMU를 넣고 "드라이브 위에서 Linux를 돌리는 computational storage"를 겨냥한 이유가 바로 그것이다(§6).

### 실습 환경 한 줄

Lima VM `elinux`(aarch64, Ubuntu, 6 vCPU, 커널 7.0.0-38-generic) 위에서 세 가지를 돌렸다. (1) **Apache NuttX**(A6 클론, 2026-10-25 master 커밋 `de823a7`) + nuttx-apps(2026-11-01 shallow clone)를 `rv-virt:knsh64`(kernel build, RISC-V 64, S-mode + QEMU 기본 OpenSBI)와 `rv-virt:nsh64`(flat build, M-mode)로 빌드, Zephyr SDK 1.0.1 `riscv64-zephyr-elf-gcc`, QEMU 10.2 `virt`. (2) **Zephyr v4.4.2** `qemu_cortex_a53`(단일 코어, `CONFIG_QEMU_ICOUNT=y`, shift 4 = 명령 1개 16 ns, generic timer 62.5 MHz라서 **1 timer cycle = 1 명령**)과 비교용 `mps2/an385`(Cortex-M3 MPU, `CONFIG_QEMU_ICOUNT_SHIFT=5` = 명령당 32 ns). (3) **VM 호스트 C**(gcc 15, `-O2 -Wall -Wextra`) — page fault·TLB 측정. QEMU 숫자는 **QEMU icount 기준이고 실제 칩과 절대값은 다르다**(캐시·TLB·버스·page walk 메모리 접근을 모델링하지 않는다). 특히 QEMU에서 TLB 비우기는 명령 하나로 끝나서 **"TLB를 비운 뒤 다시 채우는 비용"은 QEMU로 보여 줄 수 없다** — 그래서 그 부분은 VM 호스트(Apple silicon 위 하드웨어 가상화)에서 따로 쟀다(§4.3). 호스트 숫자는 "VM 기준"이다.

NuttX 빌드에는 호스트 도구 두 개(`genromfs`, `kconfig-tweak`)가 필요한데 VM에 없고 apt 설치는 금지라서, 이 노트용으로 최소 구현을 직접 썼다: `~/.rtos_scratch/F9/bin/genromfs`(ROMFS 이미지 작성기, Python 70줄 — Linux `Documentation/filesystems/romfs.rst` 형식) · `kconfig-tweak`(`--enable/--disable/--set-str/--set-val`만 하는 셸 20줄). `kconfiglib`은 `/var/tmp/rtos/F9/venv`에 pip로 깔았다. NuttX 소스는 A6 클론을 **하드링크 복사**(`cp -al`, 디스크 거의 0)한 뒤 `.git`만 지우고 빌드했고, 끝난 뒤 A6 쪽 `git status`가 깨끗한 것을 확인했다.

```sh
# NuttX kernel build (knsh64) — 커널과 앱을 따로 빌드한다
export PATH=/Users/donh/.rtos_scratch/F9/bin:/var/tmp/rtos/F9/venv/bin:/var/rtoslab/zephyr-sdk-1.0.1/gnu/riscv64-zephyr-elf/bin:$PATH

./tools/configure.sh -l rv-virt:knsh64
make -j3 CROSSDEV=riscv64-zephyr-elf-                 # 1) 커널 ELF (nuttx)
make export -j3 CROSSDEV=riscv64-zephyr-elf-          # 2) 헤더·libc·syscall proxy를 tar.gz로 내보냄
cd ../apps && ./tools/mkimport.sh -z -x ../nuttx/nuttx-export-*.tar.gz
make import -j3 CROSSDEV=riscv64-zephyr-elf-          # 3) 앱을 각각 독립 ELF로 → apps/bin/
```

`nx_run.sh`는 QEMU를 띄우고 파일에 적은 NSH 명령을 차례로 넣는 스크립트다(kernel build용; flat build용 `nx_run_flat.sh`는 `-bios none`을 붙이고 `nuttx-flat`에서 실행한다는 점만 다르다).

```sh
#!/bin/bash
# nx_run.sh <cmdfile> [timeout] — boot NuttX rv-virt knsh64 in QEMU, feed NSH commands from file, print console
cd /var/tmp/rtos/F9/nuttx || exit 1
CMDS=$1; TO=${2:-20}
( sleep 2; while IFS= read -r l; do printf '%s\r' "$l"; sleep ${STEP:-1}; done < "$CMDS"; sleep 1 ) | \
timeout $TO qemu-system-riscv64 -semihosting -M virt,aclint=on -cpu rv64 -smp 1 \
  -kernel nuttx -nographic ${QEXTRA} 2>&1 | tr -d '\r' | sed 's/\x1b\[[0-9;]*[A-Za-z]//g'
echo "[qemu rc=${PIPESTATUS[1]}]"
```

> 발견 1 — **문서와 실제가 다르다**: NuttX 문서(`Documentation/platforms/risc-v/qemu-rv/boards/rv-virt/index.rst`)는 64비트 구성을 `-bios none`으로 실행하라고 하지만, 이 커밋의 `knsh64`는 S-mode 커널(진입점 `0x80200000`, `CONFIG_ARCH_USE_S_MODE=y`)이라 `-bios none`이면 아무 출력 없이 `0x80000000`에서 illegal instruction 루프에 빠진다(QEMU `-d int`로 확인). QEMU 기본 OpenSBI(v3.0 런타임)를 쓰게 `-bios none`을 빼야 부팅한다. flat `nsh64`는 M-mode(진입점 `0x80000000`)라 `-bios none`이 맞다.

## 1. RTOS가 MMU를 쓰는 세 가지 방식

### 1.1 MMU는 두 가지 일을 한다 — 변환과 권한

EL F11에서 본 대로 MMU는 (a) **주소 변환**(가상 주소 VA → 물리 주소 PA)과 (b) **페이지 단위 권한·속성**(읽기/쓰기/실행, 특권/비특권, 캐시 속성)을 한 page table 항목(descriptor)에 같이 적는다. MPU(F4)는 (b)만 있고, 단위가 "리전 몇 개"다. MMU는 (b)를 4 KiB 페이지 단위로, 개수 제한 없이 할 수 있고, (a)까지 한다.

RTOS가 이 기능을 어디까지 쓰느냐에 따라 세 방식으로 나뉜다.

| 방식 | 변환 | 주소 공간 | 대표 | 한 줄 |
|---|---|---|---|---|
| ① 보호만 (identity map) | VA = PA | 1개 | RTEMS, Zephyr(arm64·x86), 많은 bare-metal | MMU를 "리전이 아주 많은 MPU + 캐시 속성 표"로 쓴다 |
| ② 프로세스마다 주소 공간 | VA ≠ PA, 프로세스별 page table | 프로세스 수만큼 | NuttX kernel build, VxWorks RTP, QNX, INTEGRITY | Unix식 프로세스. 커널은 단일체(monolithic)일 수도, 마이크로커널일 수도 |
| ③ 마이크로커널 + 메시지 | ②와 같음 | 드라이버·파일시스템까지 각자 | QNX Neutrino, seL4, INTEGRITY | 커널은 스케줄링·IPC·타이머만, 나머지는 전부 유저 프로세스 |

①은 이 노트 §3에서 Zephyr로, ②는 §2에서 NuttX로 직접 돌려 본다. ③은 공개 문서로 §5에서 본다.

### 1.2 RTEMS — MMU가 있어도 주소 공간은 하나

RTEMS User Manual은 스스로를 "multi-threaded, single address-space, real-time operating system with no kernel-space/user-space separation"이라고 소개한다. 애플리케이션은 커널과 같은 특권으로 돌고 하드웨어를 직접 만진다. MMU가 있는 칩(Cortex-A, SPARC LEON, PowerPC)에서도 BSP가 MMU를 켜는 이유는 캐시 속성과 영역 구분 때문이지 프로세스 때문이 아니다(RTEMS에는 프로세스가 없고 스레드만 있다). 우주 쪽 RTEMS 사용자가 격리가 필요할 때는 RTEMS 안에서가 아니라 **하이퍼바이저(XtratuM, PikeOS 등)로 파티션을 나눈다** — C11의 ARINC 653 시간 분할과 같은 발상이다.

### 1.3 비교 한 장 — 무엇을 사고 무엇을 내주나

| 항목 | 평면 RTOS | MPU 격리 | MMU 프로세스 RTOS | Linux + PREEMPT_RT |
|---|---|---|---|---|
| 주소 공간 | 1개 | 1개 | 프로세스마다 | 프로세스마다 |
| 보호 단위 | 없음 | 리전 8~16개(크기·정렬 제약) | 4 KiB 페이지, 개수 제한 사실상 없음 | 4 KiB 페이지 |
| 앱 → 커널 | 함수 호출 | `svc`/`ecall` syscall | syscall | syscall |
| 태스크 간 통신 | 공유 변수, 큐 | 큐 + 공유 partition | 메시지 패싱, 공유 메모리 매핑, 파이프 | 같음 + 소켓 등 |
| 결함 격리 | 없음 | 스레드 하나 abort | 프로세스 하나 종료, 재시작 가능 | 같음 |
| 결정성 비용 | 없음 | 리전 재설정(수십 명령) | page table 전환, TLB miss, page walk | 같음 + demand paging, reclaim, THP |
| page fault | 없음 | 없음 | 보통 미리 매핑(정적), 선택적으로 demand paging | 기본이 demand paging → mlockall 필요 |
| 인증 | SafeRTOS 등 | Zephyr(목표), FreeRTOS-MPU 기반 상용 | QNX OS for Safety, VxWorks Cert, INTEGRITY-178 | 어렵다(ELISA 등 진행 중) |
| 대표 하드웨어 | Cortex-M, R | Cortex-M(v7/v8-M), R52 | Cortex-A, R82(선택 MMU), RISC-V Sv39 | Cortex-A |

인증 칸의 구체 사실(QNX OS for Safety 8.0의 ISO 26262 ASIL D 등)은 A6 §4.10 표가 출처다. 다시 적지 않는다.

이 표에서 기억할 한 줄: **MMU 프로세스 RTOS와 Linux의 차이는 "MMU를 쓰느냐"가 아니라 "page fault와 메모리 회수를 기본으로 하느냐"다.** RTOS 쪽은 프로세스를 만들 때 필요한 페이지를 전부 붙여 두고(정적 매핑), 실행 중에는 fault가 나지 않게 설계한다. Linux는 반대로 "처음 만질 때 붙인다"가 기본이라 RT 앱이 `mlockall()`로 거꾸로 돌려야 한다(EL N1 §8, EL N2 §9).

## 2. NuttX — 한 소스, 세 가지 빌드

### 2.1 직관 — 같은 펌웨어를 세 가지 건물에 넣는다

NuttX는 같은 커널 소스를 설정 하나로 세 가지 메모리 모델로 빌드한다. A6 §3.4·I1이 NuttX 자체(POSIX, `/dev`, VFS, PX4)를 다루고, 이 절은 빌드 모드만 판다.

| 빌드 | Kconfig | 하드웨어 | 커널과 앱 | 앱 실행 형태 |
|---|---|---|---|---|
| flat | `CONFIG_BUILD_FLAT` | 아무거나 | 하나의 ELF로 링크 | NSH builtin(함수 이름으로 등록), 전부 특권 |
| protected | `CONFIG_BUILD_PROTECTED` | MPU | 커널 blob + 유저 blob 두 개 (2-pass) | 유저 blob 안의 태스크, 비특권, 커널 메모리 보호 |
| kernel | `CONFIG_BUILD_KERNEL` | MMU | 커널 ELF 따로, 앱은 각자 ELF | 파일 시스템에서 ELF를 읽어 **프로세스**로 실행 |

kernel build에서 앱은 커널과 링크되지 않는다. `make export`가 커널 쪽 헤더, libc, **syscall proxy** 라이브러리를 tar로 내보내고, nuttx-apps가 그것을 import해서 앱마다 독립 ELF(`apps/bin/hello`, `apps/bin/f9va` …)를 만든다. 실행 중에는 NSH가 `posix_spawn()`으로 그 ELF를 읽어 새 주소 공간에 올린다. Linux에서 `/bin/ls`를 실행하는 것과 같은 그림이다.

### 2.2 예제 1 — kernel build 부팅: `/system/bin`의 ELF가 프로세스가 된다

무엇을 확인하나: `rv-virt:knsh64`가 부팅해서 init(=NSH)을 **파일에서 읽은 프로세스**로 띄우는지, `ps`에 PID가 따로 붙는지.

`knsh64` defconfig의 핵심 줄(실제 파일 발췌):

```text

CONFIG_ARCH_ADDRENV=y

CONFIG_ARCH_TEXT_NPAGES=128
```

### 2.3 예제 2 — "같은 가상 주소, 다른 내용": 프로세스마다 주소 공간이 따로 있다

무엇을 확인하나: 같은 ELF를 두 번 실행했을 때 전역 변수 주소는 같은데 값은 서로 간섭하지 않는지(kernel build), 그리고 flat build에서 같은 코드를 돌리면 어떻게 되는지.

```c
/* f9va.c — same virtual address, different contents: one address space per process */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

static volatile int g_counter;          /* .bss of THIS process image */

int main(int argc, char **argv)
{
  int id = argc > 1 ? atoi(argv[1]) : 0;
  int *heap = malloc(sizeof(int));
  int local = id;

  g_counter = id * 1000;
  *heap = id;
  printf("[va%d] pid=%d &g=%p heap=%p stack=%p main=%p\n",
         id, getpid(), (void *)&g_counter, (void *)heap, (void *)&local,
         (void *)main);
  for (int i = 0; i < 3; i++)
    {
      usleep(200 * 1000);
      g_counter++;
      printf("[va%d] pid=%d g=%d\n", id, getpid(), g_counter);
    }
  free(heap);
  return 0;
}
```

앱 등록은 nuttx-apps에 디렉터리 하나(`examples/f9demo/`)를 두고 `Make.defs`에서 무조건 켰다. kernel build에서는 `MODULE = m`(독립 ELF), flat build에서는 빈 값(builtin 함수로 링크)이 되게 했다.

### 2.4 예제 3 — 결함 격리: 한 프로세스가 죽어도 나머지는 계속 돈다

무엇을 확인하나: 잘못된 포인터 쓰기 세 종류(NULL, 커널 RAM, 자기 코드 페이지)가 kernel build와 flat build에서 각각 어떤 결과를 내는지. 옆에서 `f9tick`이 250 ms마다 심장 박동을 찍는다.

```c
/* f9crash.c — three kinds of bad pointer from a user process */
#include <stdio.h>
#include <string.h>
#include <stdint.h>
#include <unistd.h>

int main(int argc, char **argv)
{
  const char *how = argc > 1 ? argv[1] : "null";
  volatile uint32_t *p;

  if (strcmp(how, "kern") == 0)
    p = (volatile uint32_t *)0x80400000;      /* kernel RAM (CONFIG_RAM_START) */
  else if (strcmp(how, "text") == 0)
    p = (volatile uint32_t *)(uintptr_t)main; /* my own code page (R-X) */
  else
    p = (volatile uint32_t *)0;               /* NULL */

  printf("[crash] pid=%d writing 0xdead to %p (%s)\n", getpid(), (void *)p, how);
  fflush(stdout);
  *p = 0xdead;
  printf("[crash] still alive?!\n");
  return 0;
}
```

```c
/* f9tick.c — a "healthy" process that keeps working while others crash */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main(int argc, char **argv)
{
  int n = argc > 1 ? atoi(argv[1]) : 8;

  for (int i = 1; i <= n; i++)
    {
      usleep(250 * 1000);
      printf("[tick] pid=%d beat %d\n", getpid(), i);
    }
  return 0;
}
```

출력에서 볼 것:

- 같은 "page fault"지만 원인이 셋 다 다르다: NULL은 **매핑이 없음**, kern은 **매핑은 있지만 U 비트가 없음**(커널 페이지), text는 **U는 있지만 W가 없음**(코드 페이지 R-X). MMU 하나로 세 종류의 버그를 같은 경로에서 잡는다.
- **flat build**: 커널 RAM 쓰기와 자기 코드 덮어쓰기가 **아무 일 없이 성공했다**(`still alive?!`). 진짜 문제는 그다음이다. 코드가 덮인 `f9crash`를 다시 실행하자 자기 메시지도 찍기 전에 libc 안(`strlen`, EPC `0x800076d8`을 `addr2line`으로 확인)에서 이상한 주소 2를 읽다가 죽었다. **앞의 버그가 다음 실행을 망가뜨린 것**이다. 이게 Don이 SSD 펌웨어에서 겪은 "엉뚱한 곳에서 터지는 버그"의 정체다.
- flat에서 NULL 쓰기는 QEMU `virt`의 0번지에 아무 장치가 없어 access fault(mcause 7)가 났고, 커널은 **죽일 프로세스가 없으니 시스템 전체를 패닉**시켰다. `f9tick`도 같이 멈췄다.

NuttX의 결정 로직은 `arch/risc-v/src/common/riscv_exception.c`의 `riscv_fault_handler()`에 그대로 있다. 요약하면 "fault를 낸 것이 커널 스레드가 아니고, syscall 처리 중도 아니고, 트랩 직전 모드가 user(`STATUS_PPP == 0`)이면 → 복귀 주소를 `_exit(SIGSEGV)`로 바꿔서 그 태스크만 끝낸다. 아니면 PANIC". 즉 **커널 안에서 난 fault는 여전히 시스템 전체를 죽인다**. MMU가 지켜 주는 것은 "user 코드의 실수"이지 커널 버그가 아니다.

### 2.6 예제 5 — 비용: syscall, 스레드 전환, 프로세스 전환, 프로세스 생성

무엇을 확인하나: kernel build와 flat build에서 같은 연산의 **명령 수**. QEMU를 `-icount shift=0,sleep=off`로 띄우면 가상 시간 1 ns = 명령 1개라서, 프로그램이 `clock_gettime()`으로 잰 ns가 곧 명령 수다. 비교를 공정하게 하려고 kernel build도 flat처럼 `CONFIG_DEBUG_ASSERTIONS`를 끄고 다시 빌드했다(예제 1~4는 기본 defconfig, 즉 assertion 켠 빌드로 돌렸다).

```c
/* f9sys.c — cost of a system call vs a plain function call (run under QEMU -icount) */
#include <stdio.h>
#include <stdlib.h>
#include <sched.h>
#include <time.h>
#include <unistd.h>

static long __attribute__((noinline)) plain(long x) { return x + 1; }

static long long now_ns(void)
{
  struct timespec ts;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  return (long long)ts.tv_sec * 1000000000LL + ts.tv_nsec;
}

int main(int argc, char **argv)
{
  int n = argc > 1 ? atoi(argv[1]) : 200000;
  volatile long sink = 0;
  long long t0 = now_ns();
  for (int i = 0; i < n; i++) sink += plain(i);
  long long t1 = now_ns();
  for (int i = 0; i < n; i++) sink += getppid();
  long long t2 = now_ns();
  for (int i = 0; i < n; i++) sched_yield();     /* syscall + scheduler, no switch */
  long long t3 = now_ns();
  printf("[sys] n=%d call %lld ns/op  getppid %lld ns/op  sched_yield %lld ns/op\n",
         n, (t1 - t0) / n, (t2 - t1) / n, (t3 - t2) / n);
  return (int)(sink & 0);
}
```

전환 비용은 `sched_yield()` 핑퐁으로 잰다. 같은 우선순위 둘이 서로 양보하면 yield 한 번 = 전환 한 번이다. 상대를 **자식 프로세스**(`posix_spawn`으로 자기 자신을 `c` 모드로 실행)로 두면 주소 공간 전환이 끼고, **같은 프로세스의 스레드**(`pthread_create`)로 두면 안 낀다. n=0으로 한 번 더 돌려 생성 비용만 따로 본다.

```c
/* f9sw.c — yield ping-pong: two PROCESSES (address-space switch) vs two THREADS */
#include <pthread.h>
#include <sched.h>
#include <spawn.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <time.h>

static int g_n;

static long long now_ns(void)
{
  struct timespec ts;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  return (long long)ts.tv_sec * 1000000000LL + ts.tv_nsec;
}

static void *spin(void *arg)
{
  (void)arg;
  for (int i = 0; i < g_n; i++) sched_yield();
  return NULL;
}

int main(int argc, char **argv)
{
  const char *mode = argc > 1 ? argv[1] : "p";
  g_n = argc > 2 ? atoi(argv[2]) : 20000;
  if (strcmp(mode, "c") == 0) { spin(NULL); return 0; }   /* child process body */

  long long t0 = now_ns(), t1;
  if (strcmp(mode, "p") == 0)
    {
      char nbuf[16];
      snprintf(nbuf, sizeof(nbuf), "%d", g_n);
      char *cargv[] = { "f9sw", "c", nbuf, NULL };
      pid_t pid;
      int st;
      if (posix_spawn(&pid, "/system/bin/f9sw", NULL, NULL, cargv, NULL) != 0)
        { printf("spawn failed\n"); return 1; }
      t1 = now_ns();
      spin(NULL);
      waitpid(pid, &st, 0);
    }
  else
    {
      pthread_t th;
      pthread_create(&th, NULL, spin, NULL);
      t1 = now_ns();
      spin(NULL);
      pthread_join(th, NULL);
    }
  long long t2 = now_ns();
  printf("[sw %s] n=%d create %lld us, loop %lld us, per yield %lld ns\n",
         mode, g_n, (t1 - t0) / 1000, (t2 - t1) / 1000,
         g_n ? (t2 - t1) / (2LL * g_n) : 0);
  return 0;
}
```

- **스레드 전환도 1.8배**(404 → 732). kernel build에서는 `sched_yield()` 자체가 syscall이고, 전환할 때 커널 스택과 유저 스택을 모두 다뤄야 한다.
- **프로세스 전환은 스레드 전환보다 31 명령만 더 든다**(763 vs 732). 그 31 명령 안에 `addrenv_switch()` → `up_addrenv_select()` → `csrw satp` + `sfence.vma x0, x0`가 들어 있다. **명령 수로는 거의 공짜**다. 하지만 이것이 QEMU의 함정이다. `sfence.vma x0, x0`는 **TLB 전체를 비우는** 명령이고(§2.7), 실제 칩에서는 전환 직후 접근마다 TLB miss → page walk가 이어진다. QEMU는 이 비용을 0으로 센다. 실제 크기는 §4.3에서 호스트로 잰다.
- **프로세스 생성은 7 ms(약 700만 명령)**, 스레드 생성은 5 µs. 1,400배다. ELF를 읽어 페이지를 받고 0으로 채우고 page table을 만드는 일이다(이 노트에서 항목별로 분해하지는 않았다). 실시간 시스템에서 **프로세스는 부팅 때 만들어 두고 실행 중에는 만들지 않는다**는 규칙의 근거다. QNX·VxWorks도 같다.

> 발견 2 — **NuttX RISC-V는 ASID를 쓰지 않는다.** `mmu_satp_reg()`에 ASID 인자가 있지만 주소 공간을 만들 때 항상 `0`을 넘기고, `mmu_write_satp()`는 `satp`를 쓴 직후 `sfence.vma x0, x0`(모든 주소, 모든 ASID의 TLB 무효화)를 한다. 즉 **프로세스 전환마다 TLB가 통째로 비워진다.** §3.3에서 볼 Zephyr arm64는 메모리 domain마다 8비트 ASID를 따로 줘서 전환 때 TLB를 비우지 않는다. 같은 "MMU RTOS"라도 구현에 따라 전환 뒤 지연 꼬리가 다르다는 뜻이다.

### 2.8 protected build는 이 노트에서 돌리지 않았다

protected build(MPU)는 F5의 Zephyr userspace와 같은 계열이다. NuttX 문서("NuttX Protected Build")는 커널 blob과 유저 blob을 2-pass로 따로 링크하고 유저 쪽에서 커널을 syscall로만 부르게 한다고 설명한다. QEMU의 RISC-V `virt`·MPS2 보드용 protected 구성(`rv-virt:pnsh64` 같은 이름이 있다)을 시간 안에 돌려 보지는 않았다. PX4에는 TII(Technology Innovation Institute) 쪽에서 기여한 "PX4 protected build" PR(#16931)이 있다 — PX4 모듈을 유저 공간에서, 일부를 `launch_kmod`로 커널 공간에서 돌리는 구조다. PX4 업스트림 보드 대부분이 어떤 빌드 모드로 나가는지는 PX4 소스가 이 랩에 없어 확인하지 못했다.

## 3. Zephyr on Cortex-A53 — MMU를 "보호용"으로 쓰는 RTOS

### 3.1 직관 — 방은 하나, 칸막이가 페이지 단위로 촘촘해졌다

Zephyr의 userspace(F5)는 Cortex-M에서는 MPU 리전으로, Cortex-A(arm64)와 x86에서는 MMU page table로 구현된다. 개념은 같다: **memory domain**(스레드 묶음이 접근할 수 있는 partition 목록)과 **K_USER 스레드**. 차이는 구현이다. arm64에서는 **domain마다 page table 한 벌**이 있고, 스레드 전환 때 domain이 바뀌면 `TTBR0_EL1`을 그 domain의 table로 바꾼다. 그러나 Zephyr는 **identity map**(VA = PA)이라 주소 공간 자체는 하나다. NuttX kernel build처럼 "같은 주소, 다른 내용"은 없다. §1.1 표의 방식 ①이다.

Zephyr arm64가 userspace를 지원하는 조건은 `arch/arm64/core/Kconfig`에 있다: Cortex-A(Armv8-A)는 `select ARCH_HAS_USERSPACE if ARM_MMU`, Armv8-R(Cortex-R82)은 `select ARCH_HAS_USERSPACE if ARM_MPU`. 그리고 `config ARM_MMU`의 기본값은 `default n if CPU_AARCH64_CORTEX_R`이다 — **Zephyr는 Cortex-R82를 MMU가 아니라 MPU로 쓴다**(§6.1).

### 3.2 예제 6 — A53 MMU 위의 결함 격리

무엇을 확인하나: 두 user 스레드를 서로 다른 domain에 넣고, 남의 partition을 쓰거나 커널 데이터를 읽으면 그 스레드만 죽는지. 그리고 domain마다 다른 page table(TTBR0)과 ASID가 붙는지.

```c
/* F9 z1 — Zephyr userspace on Cortex-A53 MMU: per-domain page tables, fault kills one thread */
#include <zephyr/kernel.h>
#include <zephyr/app_memory/app_memdomain.h>
#include <zephyr/sys/printk.h>

K_APPMEM_PARTITION_DEFINE(part_a);
K_APPMEM_PARTITION_DEFINE(part_b);
K_APP_DMEM(part_a) volatile int a_data = 1;
K_APP_DMEM(part_b) volatile int b_data = 2;
static volatile int kernel_only = 7;            /* ordinary kernel .data */
static struct k_mem_domain dom_a, dom_b;
static K_THREAD_STACK_DEFINE(st_a, 2048);
static K_THREAD_STACK_DEFINE(st_b, 2048);
static struct k_thread th_a, th_b;
static int faults;

void k_sys_fatal_error_handler(unsigned int reason, const struct arch_esf *esf)
{
	faults++;
	printk("[fatal] reason %u in '%s' -> only this thread is aborted\n",
	       reason, k_thread_name_get(k_current_get()));
}                                               /* returning = z_fatal_error aborts the thread */

static void user_a(void *p1, void *p2, void *p3)
{
	a_data += 10;
	printk("[A user] a_data=%d (own partition OK) -> now write b_data\n", a_data);
	b_data = 99;                                /* other domain's partition: fault */
	printk("[A user] NOT REACHED\n");
}

static void user_b(void *p1, void *p2, void *p3)
{
	printk("[B user] b_data=%d (own partition OK) -> now read kernel_only\n", b_data);
	printk("[B user] kernel_only=%d NOT REACHED\n", kernel_only);
}

static void run(struct k_thread *t, k_thread_stack_t *s, k_thread_entry_t fn,
		struct k_mem_domain *d, const char *name)
{
	k_thread_create(t, s, 2048, fn, NULL, NULL, NULL, 5, K_USER, K_FOREVER);
	k_mem_domain_add_thread(d, t);
	k_thread_name_set(t, name);
	k_thread_start(t);
	k_thread_join(t, K_FOREVER);
}

int main(void)
{
	struct k_mem_partition *pa[] = { &part_a }, *pb[] = { &part_b };
	uint64_t ttbr0;

	k_mem_domain_init(&dom_a, 1, pa);
	k_mem_domain_init(&dom_b, 1, pb);
	__asm__ volatile("mrs %0, ttbr0_el1" : "=r"(ttbr0));
	printk("kernel  TTBR0=%#llx ASID=%llu\n", ttbr0, ttbr0 >> 48);
	printk("dom_a   TTBR0=%#llx ASID=%llu\n", dom_a.arch.ptables.ttbr0, dom_a.arch.ptables.ttbr0 >> 48);
	printk("dom_b   TTBR0=%#llx ASID=%llu\n", dom_b.arch.ptables.ttbr0, dom_b.arch.ptables.ttbr0 >> 48);
	printk("&a_data=%p &b_data=%p &kernel_only=%p\n", &a_data, &b_data, &kernel_only);

	run(&th_a, st_a, user_a, &dom_a, "A");
	run(&th_b, st_b, user_b, &dom_b, "B");
	printk("[main] still running: faults=%d a_data=%d b_data=%d kernel_only=%d\n",
	       faults, a_data, b_data, kernel_only);
	return 0;
}
```

`prj.conf`는 `CONFIG_USERSPACE=y`, `CONFIG_THREAD_NAME=y` 두 줄이고, `CMakeLists.txt`에 `target_compile_options(app PRIVATE -Wall -Wextra -Wno-unused-parameter)`를 넣었다(Zephyr 커널 전체에 `-Wextra`를 걸면 Zephyr 자신의 `printk.c`가 `-Werror=cast-function-type`으로 깨진다 — 앱에만 건다). 경고 0개.

출력에서 볼 것:

- **TTBR0가 셋**(커널, dom_a, dom_b). 상위 16비트(비트 63:48)가 ASID 1·2·3이고, 아래가 각 page table의 물리 주소다. `arch_mem_domain_init()`이 domain을 만들 때 커널 table을 복제(`dup_table`)하고 ASID를 하나씩 순서대로 준다.

- ESR의 EC `0x24` = "lower EL에서 온 data abort"(EL0 → EL1). ISS `0x4f`의 비트 6(WnR)=1은 **쓰기**, 하위 6비트 DFSC `0x0f` = **permission fault, level 3**(4 KiB 페이지 항목에서 권한 거부). B의 `0x0f`는 WnR=0, 즉 **읽기**였다. FAR이 정확히 `&b_data`, `&kernel_only`다.

### 3.3 예제 7 — page table을 직접 걷기: domain마다 무엇이 다른가

무엇을 확인하나: 커널·dom_a·dom_b 세 page table에서 같은 네 주소(`a_data`, `b_data`, `kernel_only`, `main`의 코드)의 마지막 단계 descriptor를 읽어 권한 비트를 비교한다. 이 보드는 `CONFIG_ARM64_VA_BITS=32`, 4 KiB granule이라 L1(1 GiB) → L2(2 MiB) → L3(4 KiB) 3단계다(EL F11 §1.2의 4단계에서 L0가 빠진 꼴).

```c
/* F9 z3 — walk the Cortex-A53 page tables of the kernel and two memory domains */
#include <zephyr/kernel.h>
#include <zephyr/app_memory/app_memdomain.h>
#include <zephyr/sys/printk.h>

K_APPMEM_PARTITION_DEFINE(part_a);
K_APPMEM_PARTITION_DEFINE(part_b);
K_APP_DMEM(part_a) volatile int a_data = 1;
K_APP_DMEM(part_b) volatile int b_data = 2;
static volatile int kernel_only = 7;
static struct k_mem_domain dom_a, dom_b;

static const char *ap_str[4] = { "EL1 RW / EL0 --", "EL1 RW / EL0 RW",
				 "EL1 RO / EL0 --", "EL1 RO / EL0 RO" };

/* VA_BITS=32, 4 KiB granule: L1 (1 GiB) -> L2 (2 MiB) -> L3 (4 KiB) */
static void walk(const char *who, uint64_t ttbr0, uintptr_t va, const char *what)
{
	uint64_t *t = (uint64_t *)(uintptr_t)(ttbr0 & 0x0000FFFFFFFFF000ULL);
	uint64_t d = 0;
	int lvl;

	for (lvl = 1; lvl <= 3; lvl++) {
		d = t[(va >> (39 - 9 * lvl)) & 0x1ff];
		if ((d & 3) != 3 || lvl == 3) {
			break;                    /* block, page, or invalid */
		}
		t = (uint64_t *)(uintptr_t)(d & 0x0000FFFFFFFFF000ULL);
	}
	printk("%-6s %-11s va=%#lx L%d desc=%#018llx  %s%s%s%s\n", who, what, (unsigned long)va,
	       lvl, d, ap_str[(d >> 6) & 3], (d >> 54) & 1 ? " UXN" : " UX",
	       (d >> 53) & 1 ? " PXN" : " PX", (d >> 11) & 1 ? " nG" : " G");
}

int main(void)
{
	struct k_mem_partition *pa[] = { &part_a }, *pb[] = { &part_b };
	uint64_t kt;

	k_mem_domain_init(&dom_a, 1, pa);
	k_mem_domain_init(&dom_b, 1, pb);
	__asm__ volatile("mrs %0, ttbr0_el1" : "=r"(kt));

	const struct { const char *n; uint64_t t; } pt[] = {
		{ "kernel", kt }, { "dom_a", dom_a.arch.ptables.ttbr0 },
		{ "dom_b", dom_b.arch.ptables.ttbr0 } };
	for (int i = 0; i < 3; i++) {
		walk(pt[i].n, pt[i].t, (uintptr_t)&a_data, "a_data");
		walk(pt[i].n, pt[i].t, (uintptr_t)&b_data, "b_data");
		walk(pt[i].n, pt[i].t, (uintptr_t)&kernel_only, "kernel_only");
		walk(pt[i].n, pt[i].t, (uintptr_t)main, "text(main)");
	}
	return 0;
}
```

identity map이라 descriptor 안의 물리 주소를 그대로 포인터로 따라갈 수 있다(커널 모드인 main에서만). 인덱스 시프트 `39 - 9 × lvl`은 L1 = 30, L2 = 21, L3 = 12다.

출력에서 볼 것:

- **세 table의 차이는 비트 하나다.** `...f13`과 `...f53`의 차이 `0x40` = AP[1] (비트 6, `PTE_BLOCK_DESC_AP_ELx`) = "EL0도 접근 가능". dom_a에서는 `a_data` 페이지만, dom_b에서는 `b_data` 페이지만 이 비트가 켜져 있다. 커널 table에서는 둘 다 꺼져 있다. 그래서 같은 물리 페이지가 table에 따라 "user 접근 가능/불가"로 바뀐다. 이것이 예제 6의 permission fault가 난 이유다.
- 데이터 페이지는 전부 UXN·PXN(실행 금지). 코드 페이지는 `EL1 RO / EL0 RO UX PX` — **커널 코드가 모든 domain에서 user에게 읽기·실행 가능**하다. Zephyr userspace는 코드를 보호하지 않고 데이터만 보호한다(C8 표 "커널 코드 보호 없음"과 같다). user 스레드가 커널 함수로 점프할 수는 있지만, 그 함수가 커널 데이터를 만지는 순간 permission fault가 난다.
- `nG`(not-global) 비트가 켜져 있다. nG 항목은 TLB에 **ASID 태그와 함께** 들어가므로, domain을 바꿔도 다른 domain의 번역과 섞이지 않는다. 그래서 Zephyr arm64는 전환 때 TLB를 비울 필요가 없다(§3.5).

### 3.4 예제 8 — 같은 코드, A53 MMU vs M3 MPU: syscall과 전환 비용

무엇을 확인하나: supervisor 스레드와 user 스레드에서 `k_sem_give()`(user면 syscall)와 `k_yield()` 핑퐁 비용을 잰다. user 핑퐁은 "같은 domain"과 "다른 domain 둘"로 나눈다. 다른 domain이면 A53에서는 TTBR0 교체, M3에서는 MPU 리전 재설정이 끼어든다. **같은 소스를 두 보드로 빌드**한다.

```c
/* F9 z2 — Cortex-A53 MMU userspace cost: syscall and thread switch, user vs supervisor */
#include <zephyr/kernel.h>
#include <zephyr/sys/printk.h>

#define N 2000
static K_THREAD_STACK_DEFINE(st1, 2048);
static K_THREAD_STACK_DEFINE(st2, 2048);
static struct k_thread t1, t2;
static struct k_mem_domain dx, dy;              /* two empty domains = two page tables */
K_SEM_DEFINE(sem, 0, 1000000);

static void give_loop(void *n, void *p2, void *p3)
{
	for (int i = 0; i < (int)(uintptr_t)n; i++) k_sem_give(&sem);
}
static void yield_loop(void *n, void *p2, void *p3)
{
	for (int i = 0; i < (int)(uintptr_t)n; i++) k_yield();
}

/* run fn in 1 or 2 threads; doms: NULL=same as main, else per-thread domain */
static uint64_t run(k_thread_entry_t fn, int nthr, uint32_t opt, int n,
		    struct k_mem_domain *d1, struct k_mem_domain *d2)
{
	uint32_t c0 = k_cycle_get_32();
	k_thread_create(&t1, st1, 2048, fn, (void *)(uintptr_t)n, NULL, NULL, 5, opt, K_FOREVER);
	if (d1) k_mem_domain_add_thread(d1, &t1);
	k_object_access_grant(&sem, &t1);
	if (nthr == 2) {
		k_thread_create(&t2, st2, 2048, fn, (void *)(uintptr_t)n, NULL, NULL, 5, opt, K_FOREVER);
		if (d2) k_mem_domain_add_thread(d2, &t2);
		k_thread_start(&t2);
	}
	k_thread_start(&t1);
	k_thread_join(&t1, K_FOREVER);
	if (nthr == 2) k_thread_join(&t2, K_FOREVER);
	return (uint32_t)(k_cycle_get_32() - c0);
}

static void report(const char *name, k_thread_entry_t fn, int nthr, uint32_t opt,
		   struct k_mem_domain *d1, struct k_mem_domain *d2)
{
	uint64_t base = run(fn, nthr, opt, 0, d1, d2);
	uint64_t full = run(fn, nthr, opt, N, d1, d2);
	uint64_t per = (full - base) / ((uint64_t)N * nthr);
	printk("%-34s %4llu cycles/op = %5llu ns\n", name, per, k_cyc_to_ns_floor64(per));
}

int main(void)
{
	k_mem_domain_init(&dx, 0, NULL);
	k_mem_domain_init(&dy, 0, NULL);
	printk("%s, timer %u Hz, N=%d\n", CONFIG_BOARD_TARGET,
	       sys_clock_hw_cycles_per_sec(), N);
	report("k_sem_give  supervisor (call)", give_loop, 1, 0, NULL, NULL);
	report("k_sem_give  user (svc syscall)", give_loop, 1, K_USER, NULL, NULL);
	report("k_yield x2  supervisor threads", yield_loop, 2, 0, NULL, NULL);
	report("k_yield x2  user, same domain", yield_loop, 2, K_USER, NULL, NULL);
	report("k_yield x2  user, 2 domains", yield_loop, 2, K_USER, &dx, &dy);
	return 0;
}
```

출력에서 볼 것:

- **user syscall은 두 코어 모두 supervisor 호출의 약 7~9배**(A53 26 → 224, M3 30 → 205). 경계를 넘는 비용의 자릿수는 MMU냐 MPU냐보다 "트랩 + 인자 검증 + 스택 교체"가 정한다. M3의 205 명령은 C8에서 잰 Zephyr userspace 진입 비용과 같은 자릿수다.
- **domain이 다른 user 스레드 사이 전환**: M3는 같은 domain보다 **+23 명령**(775 → 798) — 전환할 때마다 MPU 리전을 다시 쓴다. A53은 **차이 없음**(794 → 792) — `TTBR0_EL1`에 ASID가 붙은 새 table 주소를 쓰는 `msr` 하나와 `isb`뿐이고, ASID가 다르니 TLB를 비우지 않는다. 반대로 NuttX(§2.6)는 31 명령 + TLB 전체 무효화였다.

### 3.5 Zephyr arm64 커널 안 — domain = page table 한 벌 + ASID 하나

`arch/arm64/core/mmu.c`에서 확인한 흐름:

- `arch_mem_domain_init(domain)`: `next_asid++`로 ASID를 고르고(8비트, `VM_ASID_BITS 8` — `mmu.h`; 넘치면 1로 돌아감), `dup_table(kernel_ptables.base_xlat_table, BASE_XLAT_LEVEL)`로 커널 table을 복제한 뒤, `ttbr0 = (asid << 48) or table 주소`를 저장한다.
- partition 추가(`private_map`): 그 domain의 table에서 해당 범위를 **사유화**(`privatize_page_range` — 공유하던 하위 table을 복사)한 뒤 `MT_NG`(not-global)와 user 권한을 붙여 매핑한다.
- 스레드 전환: `z_arm64_swap_mem_domains()` → `z_arm64_swap_ptables(incoming)`. 현재 TTBR0와 같으면 아무것도 안 하고, 다르면 `z_arm64_set_ttbr0()`. **두 table의 ASID가 같을 때만** `invalidate_tlb_all()`(`tlbi vmalle1`).
- ASID 8비트 = domain 255개를 넘으면 ASID가 재사용되고, 그때는 같은 ASID 경로로 TLB를 비운다. domain을 수백 개 만드는 설계는 Zephyr에서는 드물지만, "ASID가 모자라면 결정성이 바뀐다"는 것은 Linux(EL F11 §3)와 같은 이야기다.

### 3.6 예제 9 — Zephyr demand paging: RTOS에도 page fault가 있다

무엇을 확인하나: Zephyr는 arm64와 32비트 x86에서 **demand paging**(`CONFIG_DEMAND_PAGING` — 필요할 때 backing store에서 페이지를 읽어 오고 모자라면 내보내는 것)을 지원한다(`arch/Kconfig`: ARM64 블록이 `select ARCH_HAS_DEMAND_PAGING`). 공식 샘플 `samples/subsys/demand_paging`은 RAM 256 KiB 보드에 약 3.9 MiB짜리 함수를 넣고 semihosting 파일을 backing store로 쓴다. 샘플을 내 폴더로 옮겨 **호출마다 page fault 수와 시간**을 찍게 고쳤다.

```c
/* F9 zdp — Zephyr demand paging on Cortex-A53 (based on samples/subsys/demand_paging):
 * a function bigger than RAM, called 3 times; count page faults and time each call */
#include <zephyr/kernel.h>
#include <zephyr/linker/sections.h>
#include <mmu.h>                       /* k_mem_num_pagefaults_get() */

volatile long foo_val1, foo_val2;

static void __ondemand_func huge_evictable_function(void)
{
	foo_val1 = 13131313;
	foo_val2 = 45454545;
#define CODE foo_val1 *= foo_val2; foo_val2 += 1234567; \
	__asm__ __volatile__ (".rep 1000; nop; .endr");
#define REPEAT_10(x) x x x x x x x x x x
#define REPEAT_1000(x) REPEAT_10(REPEAT_10(REPEAT_10(x)))
	REPEAT_1000(CODE)
}

static void __ondemand_func small_function(void)
{
	foo_val1 += 1;
}

static void measure(const char *what, void (*fn)(void))
{
	unsigned long f0 = k_mem_num_pagefaults_get();
	uint32_t c0 = k_cycle_get_32();
	fn();
	uint32_t c = k_cycle_get_32() - c0;
	printk("%-12s free pages %4zu  page faults %4lu  time %8u cycles (%llu us)\n", what,
	       k_mem_free_get() / CONFIG_MMU_PAGE_SIZE, k_mem_num_pagefaults_get() - f0, c,
	       k_cyc_to_us_floor64(c));
}

int main(void)
{
	printk("SRAM %d KiB, page %d B, huge fn ~%u KiB of code\n", CONFIG_SRAM_SIZE,
	       CONFIG_MMU_PAGE_SIZE, 1000U * 4U * 1003U / 1024U);
	measure("small #1", small_function);
	measure("small #2", small_function);
	for (int i = 1; i <= 3; i++) {
		measure(i == 1 ? "huge #1" : i == 2 ? "huge #2" : "huge #3", huge_evictable_function);
	}
	measure("small #3", small_function);
	return 0;
}
```

`prj.conf`는 샘플 그대로(`CONFIG_SRAM_SIZE=256`, `CONFIG_DEMAND_PAGING=y`, `CONFIG_DEMAND_MAPPING=y`, `CONFIG_LINKER_USE_ONDEMAND_SECTION=y`, `CONFIG_BACKING_STORE_ONDEMAND_SEMIHOST=y` 등). `kernel/include/mmu.h`가 내부 헤더라 `-Wextra`에서 그 헤더의 unused parameter 경고가 나와 `-Wno-unused-parameter`를 더했다. 경고 0개.

```text
*** Booting Zephyr OS build v4.4.2 ***
SRAM 256 KiB, page 4096 B, huge fn ~3917 KiB of code
small #1     free pages   35  page faults    1  time      914 cycles (14 us)
small #2     free pages   35  page faults    0  time       10 cycles (0 us)
huge #1      free pages    0  page faults  984  time  2083337 cycles (33333 us)
huge #2      free pages    0  page faults  984  time  2091508 cycles (33464 us)
huge #3      free pages    0  page faults  984  time  2090728 cycles (33451 us)
small #3     free pages    0  page faults    0  time       10 cycles (0 us)
```

`size -A`로 본 `ondemand_text` 섹션은 4,030,464 B(984페이지)였다. 출력에서 볼 것:

- `small_function`은 **처음 부를 때만** page fault 1번에 914 명령, 두 번째부터 10 명령이다. **같은 함수 호출이 91배 차이**난다. 이것이 demand paging이 실시간 경로에서 금지되는 이유를 한 줄로 보여 준다.
- huge 함수는 RAM보다 커서 **부를 때마다 984번 fault**(전 페이지)가 난다. 실행해야 할 명령은 약 100만 개(nop 1000 × 1000 + 연산)인데 실제로는 약 208만 cycle이 걸렸다. 차이 약 108만 ÷ 984 ≈ **fault 하나에 약 1,100 명령**(내보낼 페이지 고르기, page table 고치기, TLB 무효화, 복사)이다. 그리고 이것은 **backing store I/O 시간을 뺀 값**이다. semihosting 파일 읽기는 QEMU 밖에서 일어나 가상 시간에 거의 잡히지 않는다. 실제로는 여기에 플래시 읽기 시간(페이지당 수십 µs 단위)이 더해진다.
- 세 번의 huge 호출 시간이 수천 cycle씩 다르다(icount인데도). `CONFIG_QEMU_ICOUNT_SLEEP=y` 보드라 semihosting 대기가 가상 시간에 일부 섞인 것으로 보인다 — 원인을 더 파지는 않았다.
- `small #3`은 huge 호출로 RAM이 다 찼는데도 fault가 없었다. arm64의 기본 교체 알고리즘은 LRU(`subsys/demand_paging/eviction/Kconfig`: `default EVICTION_LRU if ARM64`, 이 빌드의 `.config`도 `CONFIG_EVICTION_LRU=y`)라서, huge 함수의 페이지들이 서로를 내보내는 동안 따로 쓰인 `small_function` 페이지가 남은 것으로 보인다.

실무 의미: Zephyr의 demand paging은 "코드가 RAM보다 큰 저가 SoC(외부 플래시 XIP가 없는 칩)"를 위한 기능이다. 실시간 경로의 코드와 데이터는 `__pinned_func`, `__pinned_data` 같은 고정(pinned) 섹션에 넣어 절대 내보내지 않게 한다(`include/zephyr/linker/section_tags.h`). Linux의 `mlockall()`이 하는 일을 링커 섹션으로 정적으로 하는 셈이다.

## 4. MMU가 결정성에 매기는 값 — 무엇이, 얼마나

### 4.1 세 가지 비용

| 비용 | 언제 생기나 | 크기(자릿수, 이 노트 측정 기준) | RTOS의 대책 |
|---|---|---|---|
| 주소 공간 전환 | 프로세스(또는 domain) 사이 전환 | 명령 수로 0~31개(QEMU) + TLB를 비우면 그 뒤의 재충전 | ASID, 프로세스 수 줄이기, RT 일은 한 프로세스 안 스레드로 |
| TLB miss → page walk | 작업 집합이 TLB가 덮는 범위를 넘을 때 | 접근당 +1.3 ns(2단계 TLB) ~ +15~30 ns(walk), VM 기준 | 큰 페이지(2 MiB block), 핫 데이터 모으기, 코어 고정 |
| page fault | 처음 만지는 페이지, 내보낸 페이지 | 첫 접근 p50 0.5 µs, max 수백 µs(VM) / Zephyr 1,100 명령 + I/O | 정적 매핑(RTOS 기본), prefault, `mlockall`, pinned 섹션 |

첫 줄은 §2.6·§3.4에서 봤다. 나머지 두 줄을 VM 호스트에서 잰다. QEMU로 못 재는 이유는 §0의 실습 환경에서 말했다 — QEMU는 TLB를 "번역을 빨리 하기 위한 자기 캐시"로만 쓰고 비용을 명령 수에 넣지 않는다.

### 4.2 예제 10 — page fault 한 번의 값: fresh vs prefault vs mlockall (VM 기준)

무엇을 확인하나: "1 kHz 제어 루프가 매 주기 새 페이지 하나를 처음 만진다"는 상황에서 store 하나의 지연 분포. EL N1 §8.1이 같은 주제를 TCG 게스트에서 "반복당 시간"으로 쟀다면, 여기서는 하드웨어 가상화 VM에서 **접근 하나하나의 지연 백분위**를 본다. 설명은 N1·N2에 있고, 여기서는 "MMU 비용의 한 항목"으로 숫자만 본다.

```c
/* pf.c — cost of the FIRST touch of a page inside a periodic loop: fresh vs prefaulted vs mlockall */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <sys/mman.h>
#include <sys/resource.h>

#define PAGES 4096                      /* 16 MiB of 4 KiB pages, 1 page touched per "cycle" */
static double lat[PAGES];

static double now_ns(void)
{
	struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t);
	return t.tv_sec * 1e9 + t.tv_nsec;
}
static long minflt(void) { struct rusage r; getrusage(RUSAGE_SELF, &r); return r.ru_minflt; }
static int cmp(const void *a, const void *b)
{
	double x = *(const double *)a, y = *(const double *)b; return (x > y) - (x < y);
}
static void run(const char *name, int prefault)
{
	long ps = 4096;
	char *p = mmap(NULL, PAGES * ps, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
	if (p == MAP_FAILED) { perror("mmap"); exit(1); }
	madvise(p, PAGES * ps, MADV_NOHUGEPAGE);
	if (prefault) memset(p, 1, PAGES * ps);
	long f0 = minflt();
	for (int i = 0; i < PAGES; i++) {   /* the "control loop": one store per cycle */
		double a = now_ns();
		p[i * ps] = (char)i;
		lat[i] = now_ns() - a;
	}
	long f1 = minflt();
	qsort(lat, PAGES, sizeof lat[0], cmp);
	printf("%-10s faults %5ld  p50 %6.0f ns  p99 %6.0f ns  max %7.0f ns\n", name, f1 - f0,
	       lat[PAGES / 2], lat[PAGES * 99 / 100], lat[PAGES - 1]);
	munmap(p, PAGES * ps);
}
int main(int argc, char **argv)
{
	(void)argv;
	run("fresh", 0);
	run("prefault", 1);
	if (argc > 1 && mlockall(MCL_CURRENT | MCL_FUTURE) == 0) run("mlockall", 0);
	else if (argc > 1) perror("mlockall");
	return 0;
}
```

출력에서 볼 것:

- fresh는 4096 페이지에 4106 fault(앞 10개는 `lat[]` 배열 자체). **p50이 이미 0.5 µs**, 최악은 **0.1~0.23 ms**다. 1 kHz 루프의 예산(1 ms)의 4분의 1을 store 한 번이 먹을 수 있다.
- prefault와 mlockall은 fault 0, p50이 측정 바닥(42 ns)이다. max가 가끔 수 µs로 튀는 것은 VM 스케줄링·인터럽트 같은 다른 원인이다(이 노트의 주제 밖 — EL N2 §6).
- 변동이 크다(fresh p99가 1 µs~108 µs). VM 기준이고, 같은 VM에서 다른 작업자들이 빌드를 돌리고 있었다. 숫자보다 **"한 번 만진 페이지는 0, 처음 만지는 페이지는 수백 µs까지"라는 꼴**을 읽는다.
- MMU RTOS(QNX, VxWorks RTP, NuttX kernel build)는 프로세스를 만들 때 코드·데이터·스택·힙 창을 전부 실제 페이지로 붙여서 시작한다. 예제 1의 `free`에서 init 하나가 이미 150페이지를 쥐고 있던 것이 그것이다. 그래서 **RTOS 프로세스에는 이 표의 "fresh" 줄이 원래 없다.** Linux에서는 앱이 직접 `mlockall` + prefault로 그 상태를 만들어야 한다.

### 4.3 예제 11 — TLB와 page walk: 같은 캐시 줄 수, 다른 페이지 수 (VM 기준)

무엇을 확인하나: 무작위 pointer chase(앞 노드의 값이 다음 주소라서 접근이 하나씩 직렬로 일어남)를 세 가지 배치로 한다. (a) 캐시 줄을 64 B 간격으로 촘촘히 → 페이지 수가 적다. (b) **페이지마다 줄 하나**(간격 4096 + 64 B) → 줄 수 = 페이지 수. (c) (b)와 같은 배치인데 2 MiB THP(huge page)로 받기. 줄 수가 같으니 캐시 효과는 비슷하고, 차이는 **TLB가 덮어야 하는 페이지 수**에서 나온다.

간격을 4096이 아니라 4160으로 한 것은 처음 4096으로 쟀을 때의 실수 때문이다. 4096 간격이면 모든 줄이 L1 캐시의 **같은 set**에 몰려서 32줄만 돼도 느려졌다(1.63 ns) — TLB가 아니라 캐시 associativity 충돌이었다. 64 B씩 밀어 주자 그 효과가 사라졌다.

```c
/* tlb.c — random pointer chase over N cache lines: packed (64 B apart) vs one line per 4 KiB page
 *         vs the same inside 2 MiB huge pages (THP). Same #lines, different #pages.
 *         page stride = 4096 + 64 so lines don't all alias to one L1 cache set. */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <sys/mman.h>

static double now_ns(void)
{
	struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t);
	return t.tv_sec * 1e9 + t.tv_nsec;
}
/* build a random cycle over n slots spaced `stride` bytes apart, then chase it */
static double chase(size_t n, size_t stride, int huge)
{
	size_t bytes = n * stride, al = 2u << 20;
	bytes = (bytes + al - 1) / al * al;
	char *base = mmap(NULL, bytes + al, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
	if (base == MAP_FAILED) { perror("mmap"); exit(1); }
	char *m = (char *)(((unsigned long)base + al - 1) & ~(al - 1));
	madvise(m, bytes, huge ? MADV_HUGEPAGE : MADV_NOHUGEPAGE);
	memset(m, 0, bytes);
	if (huge && n == 65536) {                 /* did THP really back it? */
		char l[128]; FILE *f = fopen("/proc/self/smaps_rollup", "r");
		while (f && fgets(l, sizeof l, f)) if (!strncmp(l, "AnonHugePages", 13)) fputs(l, stderr);
		if (f) fclose(f);
	}
	size_t *ord = malloc(n * sizeof *ord);
	for (size_t i = 0; i < n; i++) ord[i] = i;
	for (size_t i = n - 1; i > 0; i--) { size_t j = (size_t)rand() % (i + 1), t = ord[i]; ord[i] = ord[j]; ord[j] = t; }
	for (size_t i = 0; i < n; i++)
		*(void **)(m + ord[i] * stride) = m + ord[(i + 1) % n] * stride;
	void **p = (void **)(m + ord[0] * stride);
	long steps = 4000000;
	for (long i = 0; i < steps / 4; i++) p = *p;            /* warm up */
	double t0 = now_ns();
	for (long i = 0; i < steps; i++) p = *p;
	double t = (now_ns() - t0) / steps;
	if (p == NULL) printf("x");
	free(ord); munmap(base, bytes + al);
	return t;
}
int main(void)
{
	printf("%8s %12s %12s %12s\n", "lines", "packed64B", "page4K", "page4K+THP");
	for (size_t n = 16; n <= 65536; n *= 2) {
		double a = 1e9, b = 1e9, c = 1e9;
		for (int r = 0; r < 3; r++) {               /* best of 3 (VM noise) */
			double x = chase(n, 64, 0), y = chase(n, 4160, 0), z = chase(n, 4160, 1);
			a = x < a ? x : a;
			b = y < b ? y : b;
			c = z < c ? z : c;
		}
		printf("%8zu %10.2f ns %10.2f ns %10.2f ns\n", n, a, b, c);
	}
	return 0;
}
```

그림 7 — pointer chase 접근당 시간(VM 호스트, Apple silicon 위 Linux 게스트, best of 3). 주황(4 KiB 페이지마다 한 줄)이 파랑(같은 줄 수를 촘촘히)보다 위에 있는 만큼이 TLB·page walk 비용이다.

출력에서 볼 것:

- **128 페이지까지는 세 줄이 같다**(0.63 ns, L1 캐시 적중). 이 범위는 1단계 TLB가 다 덮는다.
- **256~2048 페이지**: 4 KiB 배치만 1.9 ns로 오른다(+1.27 ns). 1단계 TLB는 넘쳤지만 2단계 TLB가 받아 주는 구간으로 읽힌다. 촘촘한 배치는 같은 줄 수가 32~128 KiB에 들어가 페이지 몇십 개면 되므로 0.63 ns 그대로다.
- **4096 페이지(16 MiB) 이상**: 4 KiB 배치가 16~29 ns로 뛴다. 2단계 TLB까지 넘쳐 **매 접근마다 page walk**가 일어나는 구간이다. 촘촘한 배치는 같은 지점에서 2.3 ns(L1 캐시를 넘음 — 4096줄 = 256 KiB)일 뿐이니, 차이 13~23 ns가 거의 다 번역 비용이다. 접근 하나가 **7~10배** 느려진다.
- **THP**(2 MiB 페이지, `AnonHugePages` 260 MiB로 실제로 받았음을 확인)는 같은 배치에서 페이지 수를 512분의 1로 줄여 16 MiB 지점을 3.95 ns로 끌어내린다. 큰 페이지가 실시간 시스템에서 "TLB 압박을 줄이는 도구"인 이유다. 다만 THP를 **실행 중에 만드는 일**(khugepaged, 첫 fault에서 2 MiB를 0으로 채우기)은 반대로 지연 꼬리를 만든다(EL N1 §8.1, EL N2 §9.3). RTOS는 큰 페이지(arm64의 2 MiB block)를 **부팅 때 정적으로** 쓴다 — 예제 7의 Zephyr table은 4 KiB(L3)였지만, Zephyr `mmu.c`도 정렬이 맞는 큰 영역은 block 항목으로 매핑한다.
- VM이라는 것을 잊지 말자. 게스트의 page walk는 하이퍼바이저의 stage-2 번역까지 겹쳐 실제 칩의 bare-metal walk보다 더 비싸다. 이 CPU의 TLB 항목 수를 숫자로 단정하지 않는다 — 꺾이는 지점만 읽는다.

### 4.4 Don의 경험으로 번역

SSD 컨트롤러에서 "DRAM의 L2P 테이블을 무작위로 조회하면 캐시 miss가 난다"는 것은 Don이 이미 아는 비용이다. MMU는 그 위에 **번역 miss**를 한 겹 더 얹는다. 무작위 LBA 조회 1회 = 데이터 캐시 miss 1회 + (TLB miss면) page walk의 메모리 접근 2~4회. 그래서 FTL 테이블처럼 크고 무작위로 읽히는 구조를 MMU 켠 코어에 올리면 **큰 페이지로 매핑**하거나 **TCM·고정 영역에 둔다**. Cortex-R82에서 MMU를 켤지 말지의 판단(§6.1)이 바로 이 표다.

## 5. 상용 MMU RTOS — QNX와 VxWorks (공개 문서 범위)

> 둘 다 소스가 공개되지 않은 상용 제품이다. 이 절은 QNX 공식 문서(qnx.com/developers/docs)와 공개 자료에서 확인한 것만 쓴다. 회사·버전·인증 사실은 A6 §4.2·§4.3에 있고 여기서 반복하지 않는다. 직접 실행하지 않았다.

### 5.1 QNX Neutrino — 마이크로커널 + 메시지 패싱

**구조.** QNX 문서(SDP 8.0 System Architecture, "The QNX OS microkernel")에 따르면 마이크로커널(`procnto` 안에 들어 있다)은 스레드와 프로세스, 스케줄링, POSIX 동기화 원시, 시계·타이머, 인터럽트 처리, 그리고 **메시지 패싱**만 제공한다. 파일 시스템, 네트워크, 장치 I/O는 "optional processes and shared libraries"이고, 장치 드라이버에 해당하는 것은 **resource manager** — 경로 이름(`/dev/ser1` 같은)을 자기에게 등록하고 그 경로로 오는 `open/read/write` 메시지를 처리하는 **유저 프로세스**다. 인터럽트도 커널이 받아서 유저 스레드를 깨우는 "low-latency path"로 넘긴다.

그래서 시리얼 드라이버가 잘못된 포인터로 죽어도 커널은 살아 있고, 그 드라이버 프로세스만 재시작하면 된다. 예제 3의 "프로세스 하나만 죽는다"를 **드라이버와 파일 시스템까지** 넓힌 설계다. 값은 예제 5·8에서 본 syscall·전환 비용을 **드라이버 호출 하나하나가** 낸다는 것이다 — `read()` 하나가 클라이언트 → 커널 → 드라이버 프로세스 → 커널 → 클라이언트로 두 번 전환한다.

**메시지 패싱의 세 동작.** 클라이언트 `MsgSend()` → 서버 `MsgReceive()` → 서버 `MsgReply()`. QNX 문서(Getting Started, 메시지 패싱 장)의 상태 이름을 그대로 쓰면:

- 서버 스레드가 이미 `MsgReceive()`로 기다리고 있으면(**RECEIVE-blocked**) 메시지가 즉시 서버 주소 공간으로 복사되고 클라이언트는 **REPLY-blocked**가 된다.
- 기다리는 서버가 없으면 클라이언트는 **SEND-blocked**로 큐에 선다.
- 서버가 `MsgReply()`하면 답이 클라이언트로 복사되고 클라이언트가 풀린다. 서버가 그 사이 죽으면 클라이언트의 호출은 `ESRCH`로 돌아온다.

**우선순위 상속이 메시지에 붙어 있다.** 서버 스레드는 받은 메시지를 보낸 클라이언트의 우선순위를 물려받는다(기본 동작, `ChannelCreate()`의 `_NTO_CHF_FIXED_PRIORITY`로 끔). D3에서 본 뮤텍스 우선순위 상속을 IPC 차원에서 하는 것이다. 낮은 우선순위 로그 클라이언트가 보낸 요청 때문에 서버가 높은 우선순위 제어 클라이언트를 기다리게 만드는 역전을 막는다. 문서의 주의점: 서버는 `MsgReply()` 후에도 물려받은 우선순위를 유지하다가 다음 메시지에서 바뀐다.

### 5.2 VxWorks — 커널 태스크, DKM, RTP

VxWorks에는 실행 단위가 세 가지 있다. 공개 강의 자료(체코 공대 CTU의 VxWorks 강의)와 벤더 문서 요약에서 확인한 내용이다.

| 단위 | 모드 | 주소 공간 | 무엇과 비슷한가 |
|---|---|---|---|
| kernel task | 커널(특권) | 커널 하나를 모두 공유 | FreeRTOS 태스크 — 빠르지만 보호 없음 |
| DKM (Downloadable Kernel Module, `.out`) | 커널 | 커널 공간에 런타임 적재 | Linux 커널 모듈 — 드라이버 |
| RTP (Real-Time Process, `.vxe`) | 유저 | MMU가 있으면 프로세스마다 보호된 공간 | NuttX kernel build 프로세스, Linux 프로세스 |

- RTP는 syscall로만 커널을 부르고, 공유 라이브러리와 공유 데이터 영역(shared data region)으로 RTP끼리 메모리를 나눌 수 있다.
- **MMU가 없는 칩에서도 RTP를 쓸 수 있다**(벤더 문서 요약 기준): 이때는 RTP가 서로 다른 메모리 영역을 받지만 하드웨어 보호는 없고, 대신 전환이 빠르다. 같은 프로그래밍 모델을 MMU 유무와 상관없이 유지하는 설계다.
- **연혁**: Wind River는 2004년 2월 VxWorks 6.0을 발표하면서 "MMU 기반 메모리 보호"와 "프로세스 기반 프로그래밍 모델"을 내세웠다(Wind River 보도자료, Electronic Design 기사). "RTP"라는 이름이 6.0부터였는지는 1차 문서로 확인하지 못했다. 그 전에는 VxWorks AE(2000)가 "protection domain"으로 MMU 보호를 시도했다(Electronic Design 2000-10-02 기사).
- 실무 패턴: 오래된 VxWorks 코드는 대부분 kernel task + DKM이고, 새 설계는 앱을 RTP로 나누는 쪽으로 간다. 국방·항공 쪽 면접에서 "RTP로 옮길 때 무엇이 깨지나"(커널 전역 변수 직접 접근, 드라이버 함수 직접 호출)가 좋은 꼬리 질문이다. 예제 2b의 "flat에서는 전역이 공유된다"가 거꾸로 된 경우다.
- 시간 분할이 필요한 항공 IMA에는 **VxWorks 653**(ARINC 653 파티션, C11 §5)이 따로 있다(A6 §4.2).

### 5.3 seL4와 INTEGRITY — 한 줄씩

- **seL4**: capability(권한 토큰) 기반 마이크로커널. C 구현의 기능적 정확성이 형식 증명되었다(A6 §4.9, O7). 커널은 메시지 패싱과 capability 관리만 하고 정책은 전부 유저 레벨이다. RTOS라기보다 "격리의 바닥"이고, 그 위에 RTOS·Linux 게스트를 올리는 구성이 많다.
- **INTEGRITY**: 분리 커널(separation kernel). 파티션별 메모리·시간 격리를 보장한다(A6 §4.4).

## 6. Cortex-R82와 Cortex-A 위의 RTOS

### 6.1 Cortex-R82 — MPU와 선택 MMU를 같이 가진 R

B9 §1.2 표에 R82를 "Armv8-R AArch64, PMSAv8-64 + 선택 VMSA"로 한 줄 적었다. 여기서 MMU 관점으로 다시 본다.

- **발표**: 2020-09-03(eeNews Europe, AnandTech). 첫 64비트 Cortex-R. 클러스터 최대 4코어(eeNews: "four cores in a 5nm process", 1.8 GHz), Cortex-R8·R5 대비 약 2배 성능(Arm 주장).
- **메모리 시스템**: Arm 제품 페이지는 "Highest-performance Cortex-R processor with memory management unit (MMU)", "MMU supports rich operating systems, such as Linux", DRAM 최대 1 TB 주소 지정이라고 쓴다. eeNews는 MMU를 "optional", 그리고 "can still be configured with a Memory Protection Unit (MPU) to run bare metal and RTOS"라고 쓴다.
- **어느 EL에 무엇이**: Xen의 Armv8-R64 지원 패치 시리즈(Arm 엔지니어 작성)가 "MPU in EL1 & EL2 is configurable, MMU in EL1 is configurable"이라고 정리한다. 즉 **EL2(하이퍼바이저)는 언제나 MPU**, **EL1은 MPU 또는 MMU를 고른다.** Arm Cortex-R82 TRM(r3p1, 2025-03)이 1차 출처지만 이 노트에서 TRM 본문을 직접 읽지는 못했다 — 세부(리전 수, MMU를 EL1 게스트별로 고르는 방식)는 TRM으로 확인할 것.
- **겨냥하는 곳**: SSD·HDD·computational storage(Arm 제품 페이지). 드라이브 안에서 Linux를 돌려 데이터 근처에서 계산하는 시나리오가 MMU를 넣은 이유다.
- **안전 버전**: **Cortex-R82AE** — Arm Zena CSS(차량용 컴퓨트 서브시스템)의 Safety Island가 "one or more Cortex-R82AE CPU clusters"로 구성된다(Arm Zena CSS 문서). 발표 시점은 2024년으로 보도됐지만(Counterpoint) Arm 1차 보도자료로 날짜를 확인하지 못했다.

**RTOS 지원 현황(소스에서 확인).**

- FreeRTOS V11.3.2: `portable/GCC/ARM_CR82/` — V11.3.0에서 SMP 포트와 MPU 지원이 들어왔다(B9 §9.1, `History.txt`). **MMU 포트가 아니라 MPU 포트**다.

**Don의 SSD 세계로 번역.** 차세대 SSD 컨트롤러가 R82를 쓰면, 실시간 FTL·NAND 경로는 지금처럼 MPU(또는 MMU 끔) + RTOS/실행부로 두고, MMU는 "Linux를 같이 돌릴 때"나 "큰 DRAM을 64비트로 보는 데"만 쓰는 구성이 자연스럽다. §4.3의 TLB 곡선이 이유다 — 무작위 L2P 조회는 TLB를 금방 넘친다. MMU를 켠다면 L2P 테이블은 큰 block으로 매핑한다.

### 6.2 Cortex-A 위의 RTOS — 세 가지 자리

Cortex-A(A53, A55, A7x)에 RTOS가 올라가는 자리는 크게 셋이다.

1. **AMP의 한 코어**: Linux가 도는 A 클러스터의 코어 하나를 떼어 RTOS를 돌리고 OpenAMP(remoteproc/RPMsg)로 묶는다(P5, EL O1~O3). 흔한 것은 오히려 같은 SoC의 Cortex-R5F·M 코어를 쓰는 쪽이다.
2. **하이퍼바이저 게스트**: Zephyr는 `arch/arm64/core/xen`(Xen 게스트 지원)을 갖고 있다. Jailhouse, Xen, 상용 하이퍼바이저(PikeOS, QNX Hypervisor) 위에서 Linux 옆 RTOS 게스트로 돈다. ARINC 653식 분할과 같은 발상이다(C11).
3. **A 코어 전체를 MMU RTOS가**: QNX(콕핏·ADAS), VxWorks·INTEGRITY(항공·국방 미션 컴퓨터). 이때 RTOS는 이 노트의 ② 또는 ③ 방식이다.

안전 섬(safety island)은 보통 A 클러스터 **옆의** 별도 R(또는 M) 코어다 — Arm Zena CSS의 R82AE, 그리고 B9 §11.2에서 본 R5F·R52 안전 섬. A53/A55 클러스터 자체를 lockstep으로 묶은 칩(Cortex-A65AE·A76AE 같은 AE 계열의 split-lock)도 있지만 제품별 구성은 이 노트에서 확인하지 않았다.

**AUTOSAR Classic vs Adaptive.** Classic(I5)은 MCU·R 코어 위의 정적 OSEK 계열 OS다 — MMU 없음, MPU로 SC3/SC4 메모리 보호. Adaptive는 Cortex-A급 위에서 **POSIX OS(PSE51 프로파일 인터페이스)** 를 전제로 하는 플랫폼이고, 그 OS 자리에 QNX나 Linux가 들어간다. 즉 "차량 ECU의 RTOS"라고 할 때 Classic 쪽은 MPU 세계, Adaptive 쪽은 이 노트의 MMU 프로세스 세계다. Rivian 같은 회사의 존 컨트롤러는 Classic, 중앙 컴퓨터는 Adaptive + QNX/Linux라는 분업이 흔한 그림이다(회사별 구성은 확인하지 않았다).

## 8. RTOS 커널 안에서는 무슨 일이 일어나나

이 노트에서 소스로 확인한 경로를 한곳에 모은다. 깊은 설명은 F5(Zephyr userspace 일반), C8(syscall 진입), C2(컨텍스트 스위치)로 미룬다.

**NuttX kernel build** (`/var/tmp/rtos/A6/src/nuttx`, 2026-10-25 master)

- 빌드 구조: `CONFIG_BUILD_KERNEL` → `make export`(`tools/mkexport.sh`)가 `syscall/proxies/PROXY_*.c`(223개, `syscall/syscall.csv`에서 생성)를 유저 libc 쪽으로 내보내고, 커널은 `syscall/stubs/STUB_*.c`로 받는다.
- 프로세스 생성: NSH의 명령 → `posix_spawn()` → `binfmt/`의 ELF 로더(`CONFIG_BINFMT_ELF_EXECUTABLE`) → `up_addrenv_create()`(`arch/risc-v/src/common/riscv_addrenv.c`)가 page pool(`mm/` 의 `CONFIG_MM_PGALLOC`)에서 text·data·heap 페이지와 page table을 만든다.
- 전환: `sched/addrenv/addrenv.c`의 `addrenv_switch()` → `up_addrenv_select()` → `mmu_write_satp()`(`csrw satp` + `sfence.vma x0, x0`, ASID 0).
- 결함: `arch/risc-v/src/common/riscv_exception.c`의 `riscv_exception()` → `riscv_fault_handler()` → user이면 `_exit(SIGSEGV)`로 복귀 주소 변경, 커널이면 PANIC.
- 유저 쪽 `getpid()`는 `libs/libc/sched/task_getpid.c`에서 `task_info`를 읽는다(syscall 아님).

**Zephyr arm64 MMU** (`/var/rtoslab/zephyrproject/zephyr`, v4.4.2)

- `arch/arm64/core/mmu.c`: `arch_mem_domain_init()`(ASID 할당 + `dup_table`), `private_map()`(`privatize_page_range` + `MT_NG`), `z_arm64_swap_ptables()`(TTBR0 교체, 같은 ASID일 때만 `invalidate_tlb_all`), `debug_show_pte()`(`MMU_DEBUG_PRINTS` 1로 바꾸면 table 덤프 — `arch/arm64/core/mmu.h` 9행, 우리는 직접 걷기로 대신했다).
- `arch/arm64/core/mmu.h`: `VM_ASID_BITS 8`, `TTBR_ASID_SHIFT 48`.
- `include/zephyr/arch/arm64/arm_mmu.h`: `struct arm_mmu_ptables { base_xlat_table; ttbr0; }`. `include/zephyr/arch/arm64/arch.h`: `struct arch_mem_domain { ptables; node; }`.
- `include/zephyr/arch/arm64/syscall.h`: `arch_is_user_context()` = `TPIDRRO_EL0` 비트.
- `arch/arm64/core/Kconfig`: `ARM_MMU`(Cortex-R 기본 n), `ARM64_VA_BITS`, `MAX_XLAT_TABLES`(이 보드 16), `MMU_PAGE_SIZE`(0x1000).

**FreeRTOS** — MMU 프로세스 모델이 없다. Cortex-A 포트(`portable/GCC/ARM_CA9`, `ARM_CA53_64_BIT`, `ARM_AARCH64`)는 MMU를 켜도 평면 주소 공간이고, 격리는 Cortex-M·R의 MPU 포트(`*_MPU`, `ARM_CRx_MPU`, `ARM_CR82`)로만 한다.

## 9. 실무에서 다시 보기

### 9.1 드론 회사 — "미션 컴퓨터를 VxWorks로 할까 Linux로 할까"

국방 드론의 미션 컴퓨터(Cortex-A)는 영상 처리·AI·암호화 링크를 돈다. 고객(정부)이 DO-178C나 보안 인증 증거를 요구하면 VxWorks Cert·INTEGRITY가 후보가 되고, 그렇지 않으면 Linux RT가 개발 속도로 이긴다. 펌웨어 엔지니어가 내야 할 숫자는 이 노트의 표다: 제어 경로가 몇 µs 예산인지, syscall·전환·fault 비용이 그 안에 들어가는지. 대부분의 회사는 **비행 제어는 MCU(PX4·NuttX flat)에 두고, 미션 컴퓨터는 Linux로** 해서 이 고민 자체를 피한다. 그러면 질문은 "MCU ↔ 미션 컴퓨터 링크"(P5, K)로 옮겨 간다.

### 9.2 로봇 — 드라이버 하나가 죽어도 로봇은 서 있어야 한다

휴머노이드·AMR의 주 컴퓨터에서 카메라 드라이버가 죽으면? Linux에서는 커널 드라이버 버그가 커널 패닉이고, QNX에서는 그 resource manager 프로세스만 재시작한다(§5.1). 이것이 QNX가 로봇 시장에 들어오는 논리다. 반대로 관절 MCU는 평면 RTOS가 맞다 — 예제 8에서 user syscall 하나가 200 명령이었다. 20 kHz FOC 루프(50 µs, 168 MHz MCU면 약 8,400 cycle)에서 루프마다 syscall 몇 개면 예산의 몇 %가 경계 비용으로 사라진다.

### 9.3 차량 — 같은 차에 세 가지 세계

Rivian 같은 회사에서는 바디·존 ECU(AUTOSAR Classic, MPU), 중앙 컴퓨터(AUTOSAR Adaptive + QNX/Linux, MMU 프로세스), 안전 섬(R52·R82AE, MPU RTOS)이 한 차에 같이 있다. 실리콘 검증 직무라면 "이 코어의 MMU/MPU를 누가 어떤 모드로 쓰나", "EL2 MPU로 게스트를 가뒀을 때 DMA는 어떻게 막나(SMMU)"가 bring-up 질문이다.

### 9.4 SSD — R82로 갈 때 MMU를 켤 것인가

§6.1에서 정리했다. 실행부(executive)를 MPU로 격리하면 F4·F5의 리전 설계가 그대로 쓰이고, MMU를 켜면 L2P 같은 큰 무작위 접근 구조가 TLB 곡선(그림 7)의 오른쪽으로 간다. 펌웨어 엔지니어가 쓸 만한 측정 계획: **실제 칩에서 예제 11을 MMU 켜고/끄고, 4 KiB vs 2 MiB block으로** 돌려 L2P 조회 지연 분포를 보는 것이다.

## 11. 면접에서 이렇게 말한다

**Q.** What does an MMU give you on an RTOS that an MPU doesn't, and what does it cost?

**A.** MPU는 한 주소 공간 안에서 리전 몇 개의 권한만 정한다. MMU는 페이지 단위 권한에 더해 프로세스마다 다른 주소 공간을 줄 수 있어서, 같은 바이너리를 여러 번 띄우고 한 프로세스가 죽어도 나머지가 산다. 대신 syscall이 함수 호출의 10배 이상이고, 주소 공간 전환과 TLB miss·page walk·page fault라는 꼬리 지연이 생긴다. 그래서 RT 경로는 프로세스를 미리 만들고 페이지를 미리 고정한다.

> An MPU gives me a handful of permission regions inside one address space. An MMU gives me page-granular permissions with no practical region limit, and optionally a separate address space per process — so I can run the same binary twice and a crash kills only one process. I built NuttX in kernel mode and showed exactly that: two instances at the same virtual address with independent values, and a null-pointer write that killed one process while another kept running. The cost: a syscall was about 300 instructions versus 19 for a direct call, process creation was milliseconds, and on real hardware you add TLB refills and page walks — up to 7 to 10 times slower per access once the working set outgrows the TLB. So for the real-time path I create processes at boot, prefault and lock memory, and keep hard real-time work inside one address space.

**Q.** Why not just use Linux with PREEMPT_RT instead of QNX or VxWorks?

**A.** 기술적으로 Linux RT는 많은 경우 충분하다. 차이는 세 가지다: 인증 증거(ASIL D·DO-178C를 살 수 있나), 결함 격리 범위(Linux는 드라이버가 커널 안이라 드라이버 버그 = 패닉, QNX는 드라이버가 프로세스), 메모리 기본값(Linux는 demand paging이 기본이라 앱이 mlockall로 되돌려야 하고, RTOS는 처음부터 정적 매핑).

> Often Linux RT is good enough, and it wins on ecosystem. The differences that matter are: certification evidence — you can buy ASIL D or DO-178C evidence for QNX, VxWorks Cert or INTEGRITY, which is very hard for Linux; the fault-isolation boundary — in Linux a driver bug is a kernel panic, while in QNX the driver is a user process you can restart; and memory defaults — Linux demand-pages by default, so a real-time app has to mlockall and prefault, whereas an MMU RTOS maps a process's memory up front. On a drone I'd keep flight control on an MCU RTOS and use Linux RT on the mission computer unless the customer requires certified evidence.

**꼬리 질문**: "What about the latency numbers?" → 환경마다 다르니 자기 보드에서 cyclictest와 최악 경로를 잰다고 답하고, EL N1의 측정 방법을 예로 든다.

**Q.** How does QNX message passing work, and what problem does priority inheritance on messages solve?

**A.** 클라이언트가 MsgSend하면 서버가 MsgReceive로 받을 때까지 SEND-blocked, 받은 뒤 답이 올 때까지 REPLY-blocked다. 서버는 MsgReply로 답한다. 서버 스레드는 메시지를 보낸 클라이언트의 우선순위를 물려받아서, 낮은 우선순위 클라이언트의 요청 때문에 높은 우선순위 클라이언트가 밀리는 역전을 막는다.

> It's synchronous send-receive-reply. The client's MsgSend blocks — SEND-blocked until a server thread receives it, then REPLY-blocked until the server calls MsgReply. Data is copied by the kernel between the two address spaces. The server thread inherits the client's priority when it receives the message, so a high-priority client isn't stuck behind a low-priority request the server happens to be processing — it's priority inheritance applied to IPC instead of to a mutex. Drivers and filesystems are just servers built this way, called resource managers, which is why a driver crash doesn't take down the kernel.

**Q.** Does Zephyr have processes?

**A.** 없다. Zephyr userspace는 스레드 + memory domain이다. arm64에서는 domain마다 page table과 ASID가 따로 있지만 identity map이라 주소 공간은 하나고, 코드는 모든 user 스레드에게 읽기·실행 가능하다. 데이터 격리만 한다. 실제로 page table을 걸어서 domain 사이 차이가 AP 비트 하나라는 것을 확인했다.

> No — it has threads and memory domains. On Cortex-A, each memory domain gets its own page-table copy and its own 8-bit ASID, so switching between domains is just a TTBR0 write and no TLB flush. But it's an identity map, a single address space: the same address means the same memory in every domain, and kernel text is readable and executable from user mode. I walked the A53 page tables and the only difference between two domains was the EL0 access bit on their own partition pages. So it's data isolation, not processes; for real processes on an open-source RTOS you'd look at NuttX's kernel build.

**Q.** Tell me about Cortex-R82. Why would a real-time core have an MMU?

**A.** 첫 64비트 R(Armv8-R AArch64)이고, MPU를 기본으로 가지면서 EL1에 선택 MMU가 있어서 Linux를 돌릴 수 있다. EL2는 MPU로 게스트를 가둔다. 겨냥한 곳은 SSD와 computational storage — 드라이브 안에서 Linux 앱을 돌리면서 NAND 경로는 MPU RTOS로 결정적으로 유지하려는 것이다. Zephyr와 FreeRTOS는 R82를 MPU로 지원한다.

> It's the first 64-bit Cortex-R, Armv8-R AArch64, up to four cores per cluster and DRAM addressing up to a terabyte. It keeps the R-profile MPU — at EL2 always, at EL1 optionally — and adds an optional MMU at EL1 so a guest can run Linux. The target is storage: an SSD controller can keep the NAND and host-command path on an MPU-based RTOS for determinism, and run computational-storage applications in a Linux guest beside it, with the EL2 MPU fencing them apart. In the RTOS world it's supported as an MPU target — FreeRTOS added an ARM_CR82 SMP and MPU port in 11.3, and Zephyr defaults ARM_MMU to off on 64-bit Cortex-R. Coming from SSD firmware, I'd keep the FTL hot tables out of 4 KB-page translation — either MPU, or large block mappings.

**Q.** What is the hidden cost of a process switch that a simulator won't show you?

**A.** TLB다. QEMU에서 NuttX 프로세스 전환은 스레드 전환보다 31 명령만 더 들었다. 그런데 그 안에 TLB 전체 무효화가 있고, 실제 칩에서는 전환 뒤 접근마다 page walk가 붙는다. ASID가 있으면 이걸 피한다 — Zephyr arm64는 domain마다 ASID를 줘서 TLB를 안 비우고, NuttX RISC-V는 ASID 0 하나로 매번 비운다.

> The TLB. In QEMU, a NuttX process switch cost only 31 more instructions than a thread switch, because writing satp and flushing the TLB are one instruction each. On real silicon the flush is cheap but the refill isn't: every access after the switch can miss and walk the page table, and I measured a page walk at 15 to 30 nanoseconds per access on my VM host versus under 1 when it hits. ASIDs avoid the flush — Zephyr on arm64 tags each memory domain with its own ASID, while NuttX on RISC-V currently uses ASID zero and flushes everything on every process switch. So I'd check that in the source before trusting any context-switch number.

**Q.** Your real-time process on Linux occasionally misses its deadline by a few hundred microseconds right after startup. What's your first guess?

**A.** 첫 접근 page fault. 버퍼나 스택을 루프 안에서 처음 만지고 있을 가능성이 크다. 실측으로 첫 접근 store 하나가 최악 0.2 ms였다. `mlockall(MCL_CURRENT | MCL_FUTURE)`와 prefault, 스택 미리 만지기로 fault를 0으로 만들고, `/proc/<pid>/stat`의 minflt나 `getrusage`로 루프 중 fault가 0인지 확인한다.

> First-touch page faults. Something in the loop — a buffer, the stack, a lazily-mapped library page — is being touched for the first time. On my VM a single first-touch store had a median of half a microsecond and a worst case around 200 microseconds, versus 42 nanoseconds once prefaulted. I'd mlockall with MCL_CURRENT and MCL_FUTURE at startup, prefault the buffers and the stack, avoid malloc in the loop, and then verify with getrusage that the minor-fault count doesn't move during steady state.

## 14. 요약 & 체크리스트

RTOS가 MMU를 쓰는 방식은 셋이다: ① identity map으로 권한만(RTEMS, Zephyr arm64), ② 프로세스마다 주소 공간(NuttX kernel build, VxWorks RTP), ③ 마이크로커널 + 메시지 패싱으로 드라이버까지 유저 프로세스(QNX, seL4, INTEGRITY). NuttX를 kernel build로 직접 빌드해 보니 두 프로세스가 같은 가상 주소 `0xc0101008`에 독립된 값을 갖고, NULL·커널 RAM·코드 페이지 쓰기가 전부 그 프로세스만 SIGSEGV로 끝냈다. 같은 코드의 flat build는 전역을 공유했고, 커널 RAM과 자기 코드를 조용히 덮어써서 다음 실행을 망가뜨렸으며, NULL 쓰기로 시스템 전체가 패닉했다. 대가는 QEMU 명령 수로 syscall 314(직접 호출 19), 스레드 전환 732(flat 404), 프로세스 전환 763, 프로세스 생성 7 ms였다. NuttX RISC-V는 ASID 0으로 프로세스 전환마다 TLB를 통째로 비우고, Zephyr arm64는 domain마다 8비트 ASID를 줘서 비우지 않는다 — QEMU는 이 차이를 비용으로 보여 주지 못한다. Zephyr userspace는 A53에서 domain마다 page table을 갖지만 identity map이라 프로세스가 아니며, domain 사이 차이는 AP 비트 하나, 코드는 모든 user에게 실행 가능했다. 같은 Zephyr 코드에서 user syscall은 A53·M3 모두 7~9배, domain 사이 전환은 M3 +23 명령(MPU 재설정), A53 +0이었다. VM 호스트에서 잰 MMU 비용: 첫 접근 page fault p50 0.5 µs·최악 0.2 ms(prefault·mlockall이면 0), 작업 집합이 TLB를 넘으면 접근당 7~10배(THP가 크게 줄임), Zephyr demand paging은 fault 하나에 약 1,100 명령 + I/O. Cortex-R82는 EL2 MPU + EL1 MPU/선택 MMU로 RTOS와 Linux를 한 칩에 둘 수 있고, 오픈소스 RTOS는 R82를 MPU로 지원한다. 고르는 순서는 "격리가 필요한가 → MMU가 있나 → 인증을 사야 하나 → Linux 재사용이 큰가"다.

- [ ] RTOS가 MMU를 쓰는 세 방식을 예와 함께 말할 수 있다
- [ ] 평면 / MPU / MMU 프로세스 / Linux RT를 주소 공간·IPC·결정성·인증으로 비교할 수 있다
- [ ] NuttX flat·protected·kernel build의 빌드 구조 차이(export/import, syscall proxy)를 설명할 수 있다
- [ ] "같은 가상 주소, 다른 값"과 flat build의 전역 공유 함정을 예제로 보여 줄 수 있다
- [ ] MMU가 막는 fault(user 실수)와 못 막는 fault(커널 버그)를 구분할 수 있다
- [ ] syscall·스레드 전환·프로세스 전환·프로세스 생성 비용의 자릿수를 말할 수 있다
- [ ] ASID가 있을 때와 없을 때 주소 공간 전환 뒤 TLB에 무슨 일이 생기는지 설명할 수 있다
- [ ] Zephyr arm64 memory domain이 page table 한 벌 + ASID라는 것과, 프로세스가 아닌 이유를 말할 수 있다
- [ ] TLB miss·page walk·page fault 비용을 측정하는 방법(캐시 set 충돌 피하기 포함)을 안다
- [ ] QNX MsgSend/Receive/Reply와 메시지 우선순위 상속, resource manager를 설명할 수 있다
- [ ] VxWorks kernel task·DKM·RTP의 차이를 말할 수 있다
- [ ] Cortex-R82의 MPU/MMU 배치와 SSD에서의 의미, 드론·로봇·차량별 OS 선택을 설명할 수 있다
