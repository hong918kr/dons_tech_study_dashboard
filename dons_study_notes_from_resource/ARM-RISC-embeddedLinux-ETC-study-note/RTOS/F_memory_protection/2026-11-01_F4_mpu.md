## 0. 큰 그림 — 이게 왜 필요한가

### 0.1 직관 — 주소마다 붙은 "출입 허가증"

Don이 SSD 펌웨어에서 겪은 가장 고약한 버그를 떠올려 보자. 어떤 코드가 잘못된 포인터로 NAND 매핑 테이블 한가운데를 조용히 덮어쓰고, 증상은 몇 시간 뒤 전혀 다른 곳에서 나타난다. 이런 버그는 "쓴 순간"을 잡지 못하면 거의 못 찾는다.

MPU(Memory Protection Unit)는 바로 그 "쓴 순간"을 잡는 장치다. CPU가 내보내는 **모든 주소**를 MPU가 옆에서 보고, 그 주소가 속한 **리전(region)**의 허가증을 확인한다. "이 영역은 읽기만", "이 영역은 실행 금지", "이 영역은 특권 코드만" 같은 규칙에 어긋나면 그 명령을 실행하지 않고 **MemManage fault**를 낸다. 덮어쓰기는 일어나지 않고, fault 핸들러는 "어느 명령(PC)이 어느 주소(MMFAR)를 건드렸는지"를 정확히 받는다.

MMU와 다른 점은 하나다. **MPU는 주소를 바꾸지 않는다.** Linux의 MMU는 가상 주소를 페이지 테이블로 물리 주소로 번역하면서 권한도 확인한다(EL F11). MPU는 번역 없이 권한과 메모리 속성만 확인한다. 그래서 페이지 테이블도, TLB 미스도, 페이지 폴트로 메모리를 늘리는 일도 없다. 대신 규칙의 개수(리전 수)가 8개나 16개로 아주 적고, v7-M에서는 리전 모양에 강한 제약이 있다.

### 0.2 RTOS 펌웨어에서 MPU가 하는 일 다섯 가지

| 용도 | 무엇을 막나 | 리전 비용 | 이 노트의 절 |
|---|---|---|---|
| 널 포인터 가드 | `NULL->field` 읽기·쓰기, NULL 함수 포인터 호출 | 1개 (고정) | §5.1 |
| W^X (쓰기 가능한 곳은 실행 금지) | 상수·코드 덮어쓰기, RAM에 쓴 코드 실행 | 2~3개 (고정) | §5.2 |
| 스택 가드 | 태스크 스택이 이웃 메모리를 덮는 것 | 1개, **태스크마다 다름** | §5.3, F3 |
| 메모리 속성 | 캐시가 DMA 버퍼를 망치는 것 (non-cacheable) | 1~2개 (고정) | §5.4, B8 |
| 태스크 격리 | 비특권 태스크가 남의 메모리를 건드리는 것 | 2~8개, **태스크마다 다름** | §7, F5 |

널 가드·W^X·메모리 속성은 RTOS 없이도 쓰는 "1회 설정"이고, 스택 가드와 태스크 격리는 **태스크마다 리전이 달라서 컨텍스트 스위치 때 리전을 갈아 끼워야** 한다. 이 노트의 뒤쪽(§7)이 그 부분이다.

Don의 SSD 경험과 연결하면: Cortex-R 펌웨어에서 DMA 버퍼 영역을 non-cacheable로 잡고, 코드 영역을 읽기 전용으로 잡던 그 MPU와 같은 물건이다. Cortex-M에서 달라지는 점은 (1) 레지스터 배치와 인코딩, (2) fault가 HardFault로 번지는 규칙, (3) RTOS가 태스크별로 리전을 바꾸는 방식이다.

### 0.3 실습 도구 — "접근해 보고 결과 받기" 하네스

MPU 실험은 fault를 일부러 내는 실험이다. fault 하나마다 QEMU를 다시 띄우면 실험이 느리고 비교가 어렵다. 그래서 **fault를 기록하고 원래 코드로 돌아오는** 핸들러를 만들었다. 데이터 접근 fault(DACCVIOL)는 쌓인 PC를 그 명령 다음으로 옮기고, 실행 fault(IACCVIOL)는 PC 자체가 금지 주소이므로 호출자(쌓인 LR)로 돌려보낸다. 실칩 펌웨어에서 이렇게 "건너뛰고 계속"하면 안 되지만, 실험용으로는 프로그램 하나에서 위반 여러 개를 차례로 볼 수 있다.

공용 헤더 — MPU 레지스터 주소와 RASR 값을 만드는 매크로.

```c
/* F4 공용: Armv7-M(PMSAv7) MPU 레지스터 + "접근해 보고 결과 받기" 프로브 */
#ifndef F4_H
#define F4_H
#include <stdint.h>
#include "board.h"
#define MPU_TYPE   REG32(0xE000ED90u)   /* [15:8] DREGION = 리전 수 */
#define MPU_CTRL   REG32(0xE000ED94u)   /* bit0 ENABLE, bit1 HFNMIENA, bit2 PRIVDEFENA */
#define MPU_RNR    REG32(0xE000ED98u)   /* 지금 보고 있는 리전 번호 */
#define MPU_RBAR   REG32(0xE000ED9Cu)   /* [31:5] ADDR, bit4 VALID, [3:0] REGION */
#define MPU_RASR   REG32(0xE000EDA0u)   /* XN28 AP26:24 TEX21:19 S18 C17 B16 SRD15:8 SIZE5:1 EN0 */
#define SCB_VTOR   REG32(0xE000ED08u)
#define SCB_SHCSR  REG32(0xE000ED24u)   /* bit16 MEMFAULTENA */
#define SCB_CFSR   REG32(0xE000ED28u)   /* [7:0] MMFSR */
#define SCB_HFSR   REG32(0xE000ED2Cu)   /* bit30 FORCED */
#define SCB_MMFAR  REG32(0xE000ED34u)
#define CTRL_EN 1u
#define CTRL_HFNMIENA 2u
#define CTRL_PRIVDEF 4u
/* AP: 특권/비특권 권한 */
enum { AP_NONE = 0, AP_PRW = 1, AP_PRW_URO = 2, AP_FULL = 3, AP_PRO = 5, AP_RO = 6 };
/* lg = log2(바이트), SIZE 필드 = lg - 1 → 크기 2^(SIZE+1) */
#define RASR(...) RASR_(__VA_ARGS__)       /* ATTR_* 매크로를 먼저 펼치려고 한 단계 거친다 */
#define RASR_(xn, ap, tex, s, c, b, srd, lg) \
    (((uint32_t)(xn) << 28) | ((uint32_t)(ap) << 24) | ((uint32_t)(tex) << 19) | ((uint32_t)(s) << 18) | \
     ((uint32_t)(c) << 17) | ((uint32_t)(b) << 16) | ((uint32_t)(srd) << 8) | (((uint32_t)(lg) - 1u) << 1) | 1u)
#define ATTR_NORMAL_WBWA 1, 0, 1, 1   /* TEX S C B */
#define ATTR_NORMAL_NC   1, 0, 0, 0
#define ATTR_NORMAL_WT   0, 0, 1, 0
#define ATTR_DEVICE      0, 1, 0, 1
#define ATTR_SO          0, 0, 0, 0

static inline void mpu_set(uint32_t n, uint32_t base, uint32_t rasr)
{
    MPU_RNR = n; MPU_RBAR = base; MPU_RASR = rasr;
}
static inline void mpu_enable(uint32_t ctrl)
{
    MPU_CTRL = ctrl | CTRL_EN;
    __asm volatile("dsb\n isb" ::: "memory");     /* 이후 명령부터 새 설정이 적용되게 */
}
static inline void mpu_disable(void)
{
    __asm volatile("dmb" ::: "memory");
    MPU_CTRL = 0;
    __asm volatile("dsb\n isb" ::: "memory");
}
typedef struct { uint32_t n, exc, cfsr, hfsr, mmfar, pc; } fault_t;
extern volatile fault_t g_f;
int  probe_rd(uint32_t a);              /* 반환: 그 접근이 낸 fault 수 (0 = 성공) */
int  probe_wr(uint32_t a, uint32_t v);
int  probe_x(uint32_t a);               /* a를 함수로 불러 본다 */
void show(const char *what, int nf);    /* 결과 한 줄 출력 */
void mpu_dump(void);                    /* 켜진 리전 해독표 */
#endif
```

복구하는 fault 핸들러와 프로브. 랩 템플릿의 `startup.c`가 `MemManage_Handler`·`HardFault_Handler`를 weak로 두므로 같은 이름으로 덮어쓴다.

```c
/* F4 공용: 복구하는 MemManage/HardFault 핸들러 + 프로브. 데이터 fault는 그 명령을 건너뛰고,
 * 실행 fault(IACCVIOL)는 호출자(LR)로 돌아간다 → 한 프로그램에서 실험 여러 개를 이어서 돌린다 */
#include "f4.h"
volatile fault_t g_f;

__attribute__((used)) void fault_common(uint32_t *fr, uint32_t exc)
{
    uint32_t cfsr = SCB_CFSR;
    if (cfsr & 0x18u) {                         /* MSTKERR / MUNSTKERR: 프레임이 없다 → 읽지 말고 끝 */
        board_printf_raw("  [exc %u] stacking fault CFSR=0x%x HFSR=0x%x MMARVALID=%u -> stop\n",
                         exc, cfsr, SCB_HFSR, (cfsr >> 7) & 1u);
        board_exit(0);
    }
    g_f.n++; g_f.exc = exc; g_f.cfsr = cfsr; g_f.hfsr = SCB_HFSR; g_f.mmfar = SCB_MMFAR; g_f.pc = fr[6];
    SCB_CFSR = cfsr;                            /* write-1-to-clear */
    SCB_HFSR = SCB_HFSR;
    if (cfsr & 1u) {                            /* IACCVIOL: PC 자체가 금지 주소 */
        fr[6] = fr[5] & ~1u;
    } else {                                    /* 데이터 fault: 16/32비트 Thumb 명령 하나 건너뛰기 */
        uint16_t hw = *(uint16_t *)fr[6];
        fr[6] += ((hw >> 11) >= 0x1Du) ? 4u : 2u;
    }
}
#define ENTRY(name, num) __attribute__((naked)) void name(void) { \
    __asm volatile(" tst lr, #4\n ite eq\n mrseq r0, msp\n mrsne r0, psp\n movs r1, #" #num "\n b fault_common\n"); }
ENTRY(MemManage_Handler, 4)
ENTRY(HardFault_Handler, 3)

__attribute__((noinline)) int probe_rd(uint32_t a)
{
    uint32_t n0 = g_f.n, v;
    __asm volatile("ldr %0, [%1]" : "=r"(v) : "r"(a) : "memory");
    (void)v;
    return (int)(g_f.n - n0);
}
__attribute__((noinline)) int probe_wr(uint32_t a, uint32_t v)
{
    uint32_t n0 = g_f.n;
    __asm volatile("str %0, [%1]" : : "r"(v), "r"(a) : "memory");
    return (int)(g_f.n - n0);
}
__attribute__((noinline)) int probe_x(uint32_t a)
{
    uint32_t n0 = g_f.n;
    ((void (*)(void))(a | 1u))();
    return (int)(g_f.n - n0);
}
static const char *mm_bits(uint32_t c)
{
    return (c & 1u) ? "IACCVIOL" : (c & 2u) ? "DACCVIOL" : "?";
}
void show(const char *what, int nf)
{
    board_printf_raw("  %s -> ", what);
    if (!nf) { board_printf_raw("ok\n"); return; }
    board_printf_raw("%s %s ", g_f.exc == 4 ? "MemManage" : "HardFault", mm_bits(g_f.cfsr));
    if (g_f.cfsr & 0x80u) board_printf_raw("MMFAR=0x%x ", g_f.mmfar);
    else                  board_printf_raw("MMFAR=(invalid) ");
    board_printf_raw("PC=0x%x%s\n", g_f.pc, (g_f.hfsr >> 30) & 1u ? " HFSR.FORCED=1" : "");
}
```

이 핸들러에서 미리 눈여겨볼 두 가지:

- **MSTKERR를 먼저 본다.** 예외 진입 때 프레임을 쌓다가 fault가 났다면(§5.3) 스택에 프레임이 없다. 그 상태에서 `fr[6]`을 읽으면 핸들러 안에서 다시 fault가 나고, 그것이 HardFault로, HardFault 안에서 또 나면 lockup으로 간다. 그래서 CFSR부터 보고 프레임은 그 뒤에 읽는다.
- **CFSR은 write-1-to-clear다.** 읽은 값을 그대로 다시 쓰면 그 비트만 지워진다. 안 지우면 다음 fault 때 이전 비트가 섞여 보인다.

## 1. 리전 수 — 이 칩의 MPU는 몇 칸인가

### 1.1 정의

**리전(region)**은 "시작 주소 + 크기 + 권한 + 속성" 한 묶음이다. MPU는 리전을 고정 개수만 가진다. 그 수는 Arm이 코어마다 고른 선택지 안에서 **칩 회사가 정한다**(구현 옵션). 소프트웨어는 `MPU_TYPE` 레지스터의 `DREGION` 필드(비트 15:8)로 읽는다. `DREGION = 0`이면 MPU가 없다.

| 코어 | 아키텍처 | MPU | 리전 수 (구현 선택) |
|---|---|---|---|
| M0 | Armv6-M | 없음 | 0 |
| M0+ | Armv6-M | 옵션 (PMSAv6) | 0 또는 8 |
| M3, M4 | Armv7-M | 옵션 (PMSAv7) | 0 또는 8 |
| M7 | Armv7E-M | 옵션 (PMSAv7) | 0, 8, 16 |
| M23, M33 | Armv8-M | 옵션 (PMSAv8), Secure·Non-secure 따로 | 0 ~ 16 (각 보안 상태마다) |
| M55, M85 | Armv8.1-M | 옵션 (PMSAv8 + PXN) | 0 ~ 16 |

(코어별 최대값은 B7 §3 표와 각 코어 TRM 기준. 실제 칩은 데이터시트에서, 실행 중에는 `MPU_TYPE`에서 확인한다. 예: STM32F4는 8, STM32H7은 16 — B8 §3.3.)

### 1.2 예제 1 — `MPU_TYPE`로 일곱 보드의 리전 수 조사

무엇을 확인하나: QEMU의 Cortex-M 머신 7개에서 MPU 유무와 리전 수, v8-M에서는 Secure·Non-secure MPU가 따로 있는지. 다른 코어용 빌드는 B7의 다중 코어 하네스를 `~/.rtos_scratch/F4/mc/`로 복사해 쓴다(semihosting 출력, 같은 복구 핸들러).

```c
int main(void)
```

출력에서 볼 것:

- QEMU 보드별 리전 수: M0 = 없음(읽으면 0, fault 아님), M3·M4·M33 = 8, M7·M55 = 16. `SEPARATE=0`은 명령·데이터 MPU가 하나로 통합되어 있다는 뜻이다(Cortex-M은 늘 0).

함정 하나: Zephyr의 `mps2/an386`·`mps2/an500` 보드 정의는 코어에 MPU가 있는데도 MPU 드라이버를 켜지 않는다(B7 §9에서 확인 — 하드웨어 스택 보호가 Kconfig 경고와 함께 꺼짐). "칩에 MPU가 있다"와 "펌웨어가 그것을 쓴다"는 다르다. `.config`의 `CONFIG_ARM_MPU`를 확인한다.

## 2. Armv7-M MPU (PMSAv7) — 레지스터를 손으로 쓰고 읽기

### 2.1 레지스터 한눈에

| 레지스터 | 주소 | 하는 일 |
|---|---|---|
| `MPU_TYPE` | `0xE000ED90` | 리전 수(DREGION) — 읽기 전용 |
| `MPU_CTRL` | `0xE000ED94` | bit0 ENABLE, bit1 HFNMIENA(HardFault·NMI 중에도 MPU 적용), bit2 PRIVDEFENA(특권 코드에 기본 맵을 배경으로) |
| `MPU_RNR` | `0xE000ED98` | 지금 RBAR/RASR가 가리키는 리전 번호 |
| `MPU_RBAR` | `0xE000ED9C` | [31:5] 시작 주소, bit4 VALID, [3:0] REGION |
| `MPU_RASR` | `0xE000EDA0` | XN, AP, TEX·S·C·B, SRD, SIZE, ENABLE |
| `RBAR_A1~A3` / `RASR_A1~A3` | `0xE000EDA4` ~ `0xE000EDB8` | RBAR/RASR의 별칭 — 연속 쓰기로 리전 여러 개를 한 번에 (§7.2) |

리전 하나를 쓰는 기본 순서는 `RNR = n` → `RBAR = base` → `RASR = 속성 | SIZE | ENABLE`이다. RBAR에 `VALID = 1`과 REGION 번호를 같이 쓰면 RNR을 따로 안 써도 된다(예제 2에서 확인).

### 2.2 RASR 필드 — 비트 하나씩

```
 31   29 28 27 26  24 23 22 21  19 18 17 16 15        8 7  6 5     1 0
+-------+--+--+------+-----+------+--+--+--+-----------+-----+-------+--+
|  res  |XN|re|  AP  | res | TEX  |S |C |B |    SRD    | res | SIZE  |EN|
+-------+--+--+------+-----+------+--+--+--+-----------+-----+-------+--+
 크기 = 2^(SIZE+1) 바이트, SIZE >= 4 (32 B) ... 31 (4 GB)
```

**크기와 정렬.** 리전 크기는 `2^(SIZE+1)`이다. SIZE = 4가 최소 32 B, SIZE = 31이 4 GB. 그리고 **시작 주소는 크기의 배수**여야 한다. 64 KB 리전은 0x…0000, 0x…10000처럼 64 KB 경계에서만 시작할 수 있다. 이 규칙이 Cortex-M MPU 설계의 거의 모든 고통의 원인이다. 2의 거듭제곱이 아닌 영역(예: 48 KB 스택 풀, 288 KB SRAM)은 subregion(§3)이나 리전 여러 개로 덮어야 한다.

**AP (Access Permission) — 3비트.** 특권/비특권 각각의 권한이다.

| AP | 특권 | 비특권 | 흔한 용도 |
|---|---|---|---|
| 000 | 금지 | 금지 | 널 가드, 스택 가드 |
| 001 | RW | 금지 | 커널 데이터 (FreeRTOS `privileged_data`) |
| 010 | RW | RO | 비특권이 읽기만 하는 공유 상태 |
| 011 | RW | RW | 일반 RAM, 태스크 스택 |
| 100 | (예약) | | |
| 101 | RO | 금지 | 커널 코드 (FreeRTOS `privileged_functions`) |
| 110 | RO | RO | 플래시 전체 |
| 111 | RO | RO | 110과 같음 |

**XN (eXecute Never).** 1이면 그 리전에서 명령을 가져오면 IACCVIOL. RAM·주변장치 리전에는 항상 켠다(§5.2).

**TEX · S · C · B — 메모리 타입과 캐시 정책.** 인코딩 표와 M7의 "Shareable이면 캐시 안 됨" 규칙은 B8 §3에 자세히 있다. 여기서는 이 노트에서 쓰는 다섯 조합만 다시 적는다.

| 이름 | TEX | S | C | B | 뜻 |
|---|---|---|---|---|---|
| Strongly-ordered | 000 | - | 0 | 0 | 모든 접근 순서 유지, 버퍼 없음 |
| Device (shareable) | 000 | - | 0 | 1 | 주변장치 레지스터 |
| Normal WT | 000 | 0 | 1 | 0 | 플래시 코드 (읽기 위주) |
| Normal non-cacheable | 001 | 0/1 | 0 | 0 | DMA 버퍼 |
| Normal WB-WA | 001 | 0 | 1 | 1 | 일반 SRAM |

**SRD — Subregion Disable 8비트.** §3에서 따로 다룬다.

### 2.3 예제 2 — 전형적인 리전 배치를 쓰고 해독기로 다시 읽기

무엇을 확인하나: (1) 실제 펌웨어에서 쓸 만한 리전 8개를 RASR 매크로로 쓰고, 레지스터를 다시 읽어 사람이 읽는 표로 바꿨을 때 의도대로인지, (2) RBAR에 VALID 비트를 주면 RNR이 바뀌는지, (3) **크기에 정렬되지 않은 base**를 주면 어떻게 되는지.

먼저 해독기다. RBAR/RASR 값만 보고 시작·크기·권한·속성을 다시 계산한다. 디버거에서 MPU 레지스터 덤프를 받았을 때 손으로 하는 일을 코드로 옮긴 것이다.

```c
/* F4: MPU_RBAR/RASR를 읽어 사람이 읽는 표로 바꾸는 해독기 (Armv7-M PMSAv7) */
#include "f4.h"
static const char *const ap_s[8] = { "--/--", "RW/--", "RW/RO", "RW/RW", "res", "RO/--", "RO/RO", "RO/RO" };
static const char *const pol[4] = { "NC", "WB-WA", "WT", "WB" };   /* TEX=1xx일 때 inner/outer 정책 */
static void attr(uint32_t tex, uint32_t c, uint32_t b)
{
    uint32_t cb = (c << 1) | b;
    if (tex == 0) {
        static const char *const t0[4] = { "Strongly-ordered", "Device(S)", "Normal WT", "Normal WB" };
        board_printf_raw("%s", t0[cb]);
    } else if (tex == 1) {
        board_printf_raw("%s", cb == 0 ? "Normal NC" : cb == 3 ? "Normal WB-WA" : "impl/res");
    } else if (tex == 2) {
        board_printf_raw("%s", cb == 0 ? "Device(nS)" : "res");
    } else if (tex & 4u) {
        board_printf_raw("Normal o=%s i=%s", pol[tex & 3u], pol[cb]);
    } else {
        board_printf_raw("res");
    }
}
static void size_s(uint32_t lg)
{
    if (lg >= 30)      board_printf_raw("%uGB", 1u << (lg - 30));
    else if (lg >= 20) board_printf_raw("%uMB", 1u << (lg - 20));
    else if (lg >= 10) board_printf_raw("%uKB", 1u << (lg - 10));
    else               board_printf_raw("%uB", 1u << lg);
}
void mpu_dump(void)
{
    uint32_t n = (MPU_TYPE >> 8) & 0xFFu;
    board_printf_raw("MPU_TYPE=0x%x (%u regions) MPU_CTRL=0x%x\n", MPU_TYPE, n, MPU_CTRL);
    board_printf_raw("  r  RBAR       RASR       base       size  AP(P/U) XN SRD(7..0) S attr\n");
    for (uint32_t i = 0; i < n; i++) {
        MPU_RNR = i;
        uint32_t rbar = MPU_RBAR, rasr = MPU_RASR;
        if (!(rasr & 1u)) continue;
        uint32_t lg = ((rasr >> 1) & 0x1Fu) + 1u, srd = (rasr >> 8) & 0xFFu;
        board_printf_raw("  %u  0x%x 0x%x 0x%x ", i, rbar, rasr, rbar & ~0x1Fu);
        size_s(lg);
        board_printf_raw("  %s   %u  ", ap_s[(rasr >> 24) & 7u], (rasr >> 28) & 1u);
        for (int k = 7; k >= 0; k--) board_putc((srd >> k) & 1u ? 'x' : '.');
        board_printf_raw("  %u ", (rasr >> 18) & 1u);
        attr((rasr >> 19) & 7u, (rasr >> 17) & 1u, (rasr >> 16) & 1u);
        board_putc('\n');
    }
}
```

그리고 배치를 쓰는 쪽:

```c
/* F4 예제 2: 전형적인 리전 배치를 쓰고 해독기로 다시 읽기 + RBAR.VALID 트릭 + 정렬 안 된 base */
#include "f4.h"
static uint8_t dma_pool[1024] __attribute__((aligned(1024)));
int main(void)
{
    mpu_disable();
    /* r0: FLASH 4 MB, 특권/비특권 모두 읽기 전용, 실행 허용 (코드는 Normal WT) */
    mpu_set(0, 0x00000000u, RASR(0, AP_RO, ATTR_NORMAL_WT, 0x00, 22));
    /* r1: SRAM 4 MB, 모두 RW, 실행 금지 (W^X), Normal WB-WA */
    mpu_set(1, 0x20000000u, RASR(1, AP_FULL, ATTR_NORMAL_WBWA, 0x00, 22));
    /* r2: DMA 풀 1 KB, Normal non-cacheable, shareable */
    mpu_set(2, (uint32_t)dma_pool, RASR(1, AP_FULL, 1, 1, 0, 0, 0x00, 10));
    /* r3: 주변장치 512 MB, Device, XN */
    mpu_set(3, 0x40000000u, RASR(1, AP_FULL, ATTR_DEVICE, 0x00, 29));
    /* r4: 널 가드 0x0~0xFF, 아무도 접근 불가 (r0보다 번호가 커서 이긴다) */
    mpu_set(4, 0x00000000u, RASR(1, AP_NONE, ATTR_SO, 0x00, 8));
    /* r5: 64 KB 중 위 2개 subregion(8 KB씩)을 끈 "48 KB" 특권 전용 영역 */
    mpu_set(5, 0x20010000u, RASR(1, AP_PRW, ATTR_NORMAL_WBWA, 0xC0, 16));
    /* r6: RBAR.VALID=1이면 RBAR에 쓴 REGION 값이 RNR을 바꾼다 — RNR=0인 채로 r6을 설정 */
    MPU_RNR = 0;
    MPU_RBAR = 0x20020000u | 0x10u | 6u;
    board_printf_raw("after RBAR write with VALID|6: RNR=%u\n", MPU_RNR);
    MPU_RASR = RASR(1, AP_PRO, ATTR_NORMAL_WBWA, 0x00, 12);
    /* r7: 정렬 안 된 base — 1 KB 리전을 0x20030300에 */
    mpu_set(7, 0x20030300u, RASR(1, AP_NONE, ATTR_NORMAL_WBWA, 0x00, 10));
    mpu_enable(CTRL_PRIVDEF);
    SCB_SHCSR |= 1u << 16;                            /* MEMFAULTENA */
    mpu_dump();
```

### 2.4 Don 경험과 연결, 흔한 함정

SSD의 Cortex-R5 MPU(PMSAv7-R)도 리전 크기·정렬 규칙이 같은 계열이라 감각은 그대로 쓸 수 있다. 다른 점: Cortex-R은 CP15 레지스터(`mcr p15`)로 쓰고, Cortex-M은 메모리 맵 레지스터(`0xE000ED9x`)로 쓴다. 그래서 Cortex-M에서는 C 포인터 하나로 MPU를 만질 수 있고, 반대로 **비특권 코드가 MPU를 못 만지게 하는 장치**도 "PPB는 특권 전용"이라는 버스 규칙이다(C8 §3.8에서 gdb가 비특권 상태에서 MPU를 못 읽은 이유).

- SIZE 필드에 log2(크기)를 그대로 넣는다 → 크기가 두 배가 된다. SIZE = log2 - 1이다. CMSIS는 `ARM_MPU_REGION_SIZE_1KB` 같은 상수를 준다.
- 리전을 바꾸는 동안 MPU를 켜 둔다 → RBAR만 바뀌고 RASR은 옛 값인 순간이 생긴다. 지금 실행 중인 코드·스택을 덮는 리전을 바꿀 때는 끄고 바꾸거나(FreeRTOS PendSV가 그렇게 한다, §7.2), 그 리전을 안 쓰는 순서로 바꾼다.

## 3. subregion, 겹침, 배경 — 2의 거듭제곱 세상에서 원하는 모양 만들기

### 3.1 직관

v7-M 리전은 "2의 거듭제곱 크기, 크기 정렬"이라는 딱딱한 블록이다. 원하는 모양을 만드는 도구가 세 개 있다.

1. **subregion**: 256 B 이상 리전은 8등분되고, SRD 비트로 칸을 하나씩 끌 수 있다. 꺼진 칸은 "이 리전이 없는 것처럼" 동작해 아래(번호가 작은) 리전이나 배경 맵이 보인다.
2. **겹침 우선순위**: 리전이 겹치면 **번호가 큰 리전이 이긴다.** 큰 리전 위에 작은 리전을 얹어 구멍을 내거나 권한을 바꾼다.
3. **배경(background)**: `PRIVDEFENA = 1`이면 어느 리전에도 안 걸리는 주소를 특권 코드는 아키텍처 기본 맵(B8 §3.2)으로 접근한다. 비특권 코드는 배경을 못 쓴다 — 리전이 없으면 무조건 fault.

### 3.2 예제 5 — SRD로 구멍 내기, 48 KB 보호, 작은 리전의 SRD, 겹침 우선순위

무엇을 확인하나: (A) SRD로 리전 가운데에 구멍을 낼 수 있는지, (B) 64 KB + SRD로 48 KB만 보호되는지, (C) 128 B 리전에 SRD를 주면 어떻게 되는지, (D, E) 겹침에서 번호가 큰 리전이 이기는지.

```c
/* F4 예제 5: subregion(SRD)으로 구멍 내기 · 2의 거듭제곱이 아닌 영역 · 작은 리전의 SRD · 겹침 우선순위 */
#include "f4.h"
#define BASE 0x20100000u                                   /* 64 KB 정렬된 실험 영역 */
static void scan(const char *title)
{
    board_printf_raw("%s\n  subregion: ", title);
    for (uint32_t k = 0; k < 8; k++) {                    /* 8 KB씩 8칸, 각 칸 가운데에 써 본다 */
        int f = probe_wr(BASE + k * 0x2000u + 0x1000u, k);
        board_printf_raw("%u:%s ", k, f ? "FAULT" : "ok");
    }
    board_printf_raw("\n");
}
int main(void)
{
    SCB_SHCSR |= 1u << 16;
    mpu_set(0, 0x00000000u, RASR(0, AP_RO, ATTR_NORMAL_WT, 0x00, 22));    /* FLASH */
    mpu_set(1, 0x20000000u, RASR(1, AP_FULL, ATTR_NORMAL_WBWA, 0x00, 22)); /* SRAM 전체 RW */
    mpu_enable(CTRL_PRIVDEF);

    /* r2: 64 KB "쓰기 금지"(RO), SRD=0x3C → subregion 2..5는 꺼져 r1(RW)이 보인다 */
    mpu_set(2, BASE, RASR(1, AP_RO, ATTR_NORMAL_WBWA, 0x3C, 16));
    scan("A) r2 = 64 KB RO, SRD=0b00111100");

    /* 48 KB만 보호하고 싶다: 64 KB 리전 + 위 두 칸(6, 7) 끄기 */
    mpu_set(2, BASE, RASR(1, AP_RO, ATTR_NORMAL_WBWA, 0xC0, 16));
    scan("B) r2 = 64 KB RO, SRD=0b11000000 (48 KB 보호)");

    /* 128 B 리전은 subregion이 없다: SRD=0xFF를 줘도? (아키텍처: 256 B 미만은 SRD=0이어야 함) */
    mpu_set(2, BASE, RASR(1, AP_RO, ATTR_NORMAL_WBWA, 0xFF, 7));
    show("C) 128 B RO region with SRD=0xFF, write BASE+0x10", probe_wr(BASE + 0x10u, 1));

    /* 겹침: 번호가 큰 리전이 이긴다. 큰 RW(r1) 안의 1 KB RO를 r2로 → 쓰기 fault */
    mpu_set(2, BASE, RASR(1, AP_RO, ATTR_NORMAL_WBWA, 0x00, 10));
    show("D) r1=4MB RW, r2=1KB RO : write", probe_wr(BASE + 0x20u, 1));
    /* 번호를 바꾸면: r1 = 1 KB RO, r2 = 4 MB RW → 큰 RW가 이겨서 보호가 사라진다 */
    mpu_set(1, BASE, RASR(1, AP_RO, ATTR_NORMAL_WBWA, 0x00, 10));
    mpu_set(2, 0x20000000u, RASR(1, AP_FULL, ATTR_NORMAL_WBWA, 0x00, 22));
    show("E) r1=1KB RO, r2=4MB RW : write", probe_wr(BASE + 0x20u, 1));
    mpu_dump();
    return 0;
}
```

- A·B: SRD 비트가 1인 칸만 r2의 RO가 빠지고 r1의 RW가 보인다. B는 **64 KB 리전 하나로 48 KB를 보호**했다. 이 기법의 한계: 칸 크기(리전 크기 / 8) 단위로만 자를 수 있고, 시작은 여전히 64 KB 정렬이어야 한다. 그래서 "48 KB를 0x20100000부터"는 되지만 "48 KB를 0x20103000부터"는 리전 하나로 안 된다(§8의 계산기가 이것을 판정한다).

## 4. MemManage fault — 위반이 일어나면

### 4.1 무엇이 기록되나

| | | bit4 MSTKERR | 예외 진입 때 프레임 쌓다 위반 (스택 가드에 닿음) |

| SHPR1 | `0xE000ED18` | byte0 | MemManage 우선순위 |
| HFSR | `0xE000ED2C` | bit30 FORCED | 다른 fault가 HardFault로 승격되었음 |

MMFAR는 **데이터 위반에서만** 유효하다. 실행 위반(IACCVIOL)은 MMARVALID = 0이고, 범인 주소는 쌓인 PC다. 스태킹 위반(MSTKERR)도 MMARVALID = 0이다(예제 7).

### 4.2 예제 6 — MemManage가 HardFault로 번지는 세 경우

무엇을 확인하나: (A) MEMFAULTENA를 안 켰을 때, (C) MemManage보다 높은 우선순위 문맥(ISR)에서 위반했을 때, (D·E) NMI 안에서 위반했을 때 HFNMIENA에 따라 무엇이 다른가.

```c
/* F4 예제 6: MemManage가 HardFault로 번지는 세 경우 — MEMFAULTENA=0, 더 높은 우선순위 문맥, NMI + HFNMIENA */
#include "f4.h"
#define SHPR1_MEM  (*(volatile uint8_t *)0xE000ED18u)   /* MemManage 우선순위 */
#define SHPR3_PSV  (*(volatile uint8_t *)0xE000ED22u)   /* PendSV 우선순위 */
#define ICSR       REG32(0xE000ED04u)
#define GUARD 0x20100000u
static volatile int r_pendsv = -1, r_nmi = -1;
void PendSV_Handler(void) { r_pendsv = probe_wr(GUARD, 1); }
void NMI_Handler(void)    { r_nmi = probe_rd(GUARD); }

int main(void)
{
    mpu_set(0, 0x00000000u, RASR(0, AP_RO, ATTR_NORMAL_WT, 0x00, 22));
    mpu_set(1, GUARD, RASR(1, AP_NONE, ATTR_NORMAL_WBWA, 0x00, 5));      /* 32 B 접근 금지 */
    mpu_enable(CTRL_PRIVDEF);

    show("A) MEMFAULTENA=0, write guard", probe_wr(GUARD, 1));
    SCB_SHCSR |= 1u << 16;
    show("B) MEMFAULTENA=1, write guard", probe_wr(GUARD, 1));

    SHPR1_MEM = 0x80; SHPR3_PSV = 0x40;                /* PendSV(0x40)가 MemManage(0x80)보다 높다 */
    ICSR = 1u << 28;                                     /* PENDSVSET */
    __asm volatile("dsb\n isb");
    show("C) fault inside PendSV (pri 0x40 > MemManage 0x80)", r_pendsv);

    ICSR = 1u << 31;                                     /* NMIPENDSET, HFNMIENA=0 */
    __asm volatile("dsb\n isb");
    board_printf_raw("D) NMI reads guard, HFNMIENA=0 -> faults=%d (NMI 안에서는 MPU가 꺼진 것처럼)\n", r_nmi);

    mpu_enable(CTRL_PRIVDEF | CTRL_HFNMIENA);
    board_printf_raw("E) HFNMIENA=1, NMI reads guard ...\n");
    ICSR = 1u << 31;
    __asm volatile("dsb\n isb");
    board_printf_raw("   back in main, r_nmi=%d\n", r_nmi);
    return 0;
}
```

출력에서 볼 것:

- **A**: 리셋 직후 MEMFAULTENA = 0이라 MPU 위반이 HardFault로 갔다(`HFSR.FORCED=1`). 그래도 CFSR의 MMFSR 비트와 MMFAR는 그대로 남아 있어서 HardFault 핸들러에서 원인을 읽을 수 있다. 실무 규칙: **부팅 초기에 `SHCSR`의 MEMFAULTENA·BUSFAULTENA·USGFAULTENA를 켠다.** 그래야 원인별 핸들러가 돌고, HardFault는 "진짜 이중 사고"만 남는다(M1).
- **C**: MEMFAULTENA가 켜져 있어도, **현재 실행 우선순위가 MemManage 우선순위보다 높거나 같으면** MemManage를 받을 수 없어서 HardFault로 승격된다. 드론 FC에서 IMU ISR(높은 우선순위)이 스택 가드를 건드리면 MemManage가 아니라 HardFault가 난다는 뜻이다. MemManage 우선순위를 가장 높게(0) 두는 프로젝트가 많은 이유다. FreeRTOS의 `configMAX_SYSCALL_INTERRUPT_PRIORITY`와 섞어 생각할 때도 이 규칙을 기억한다(B3).
- **D**: `HFNMIENA = 0`(기본)이면 **HardFault·NMI 핸들러(그리고 FAULTMASK가 켜진 동안)에서는 MPU가 적용되지 않는다.** 가드를 읽어도 fault가 없다. HardFault 핸들러가 망가진 MPU 설정 때문에 또 죽지 않게 하려는 설계다.
- **E**: `HFNMIENA = 1`로 바꾸고 NMI에서 같은 접근을 하자 QEMU가 **lockup**으로 멈췄다. NMI(우선순위 −2)에서 난 fault는 HardFault(−1)로 승격될 수 없기 때문이다. 실칩도 lockup 상태가 되고, 칩의 LOCKUP 신호로 리셋을 걸게 설계되어 있지 않으면 그대로 멈춘다. **HFNMIENA를 켜는 펌웨어는 HardFault·NMI 핸들러가 쓰는 메모리(코드·스택·로그 버퍼)가 리전으로 확실히 열려 있어야 한다.** 보통은 0으로 둔다.

### 4.3 PRIVDEFENA — 배경 맵을 줄까 말까

`PRIVDEFENA = 0`이면 리전에 없는 주소는 **특권 코드도** fault다. 가장 엄격하지만, 펌웨어가 쓰는 모든 메모리(코드, 데이터, 스택, 주변장치, 시스템 메모리)를 리전으로 덮어야 한다. 예제 4가 이 모드로 돈다. 대부분의 RTOS는 `PRIVDEFENA = 1`을 쓴다: 커널(특권)은 배경 맵으로 자유롭게 가고, 리전은 "비특권 태스크가 갈 수 있는 곳"과 "특권도 못 가는 곳(가드)"만 표시한다. FreeRTOS v7-M 포트(C8 §3.8의 `MPU_CTRL=0x5`)와 Zephyr(§7.3)가 그렇다.

예외 없이 항상 지켜지는 두 가지: **PPB(`0xE0000000`~`0xE00FFFFF`, NVIC·SCB·MPU 레지스터)는 MPU 리전과 무관하게 기본 맵을 쓰고 특권 전용**이며, **예외 벡터 읽기도 기본 맵을 쓴다**(예제 3 B에서 확인). 그래서 예제 4에서 배경 없이도 `0xE000ED00` 읽기가 ok였다.

### 4.4 DSB/ISB — 설정을 바꾼 뒤

MPU 레지스터 쓰기는 "저장" 명령이다. 그 쓰기가 끝나기 전에, 혹은 이미 파이프라인에 들어온 다음 명령이 옛 설정으로 검사받을 수 있다. 그래서 Arm의 권장 순서는:

1. 바꾸기 전 `DMB` — 진행 중인 메모리 접근이 옛 설정으로 끝나게.
2. MPU 레지스터 쓰기.
3. `DSB` — 쓰기가 끝날 때까지 기다림.
4. `ISB` — 파이프라인을 비워 다음 명령부터 새 설정으로 가져오게.

예외 진입과 복귀는 그 자체로 컨텍스트 동기화 사건이라서 PendSV 안에서 리전을 바꾸고 **바로 예외 복귀**하는 경우에는 `ISB`가 없어도 된다. FreeRTOS의 v7-M·v8-M PendSV가 `dsb`만 쓰고 `isb` 없이 `bx lr`로 끝나는 이유다(§7.2 디스어셈블). 반대로 Thread 모드에서 리전을 바꾸고 계속 실행하는 초기화 코드는 `DSB; ISB`가 필요하다(CMSIS `ARM_MPU_Enable()`이 그렇게 한다).

**QEMU에서는 이 차이를 보여 줄 수 없다.** QEMU는 MPU 레지스터를 쓰는 순간 내부 TLB를 비우고 바로 새 설정을 쓴다. 배리어를 빼먹은 코드도 QEMU에서는 멀쩡히 돈다 — 실칩에서만 드물게 터지는 종류의 버그다.

### 5.1 예제 3 — 널 포인터 가드

무엇을 확인하나: MPU 없이 NULL 역참조가 어떻게 되는지, 0x0~0xFF를 금지 리전으로 두면 무엇이 잡히는지, 그리고 **벡터 테이블이 0x0에 있을 때** 가드를 걸어도 예외가 동작하는지.

```c
/* F4 예제 3: 널 포인터 가드 — MPU 없이 / 가드 + VTOR=0 / 가드 + 벡터 테이블을 RAM으로 옮김 */
#include <string.h>
#include "f4.h"
extern const uint32_t g_vectors[48];                  /* startup.c의 벡터 테이블 (FLASH 0x0) */
__attribute__((aligned(256))) uint32_t ram_vec[48];  /* VTOR는 128 B 이상 정렬 (벡터 48개 → 256) */
struct imu { uint32_t hdr[16]; uint32_t gyro_x; };   /* gyro_x는 오프셋 0x40 */

static inline uint32_t opaque(uint32_t v) { __asm volatile("" : "+r"(v)); return v; }  /* 컴파일러에게 숨긴다 */

int main(void)
{
    volatile uint32_t *nul = (volatile uint32_t *)opaque(0);   /* 상수 NULL이면 GCC가 udf로 바꿔 버린다 */
    SCB_SHCSR |= 1u << 16;
    board_printf_raw("A) MPU off: *(0)=0x%x (= 초기 SP)\n", nul[0]);
    uint32_t keep = nul[0];
    show("write *(0)=0xBAD (SSRAM이라 그냥 써진다)", probe_wr(0, 0xBADu));
    board_printf_raw("   now *(0)=0x%x\n", nul[0]);
    nul[0] = keep;

    mpu_set(0, 0x00000000u, RASR(1, AP_NONE, ATTR_SO, 0x00, 8));   /* 0x0~0xFF 아무도 못 씀 */
#if PART == 2
    board_printf_raw("B) guard on, VTOR=0x%x (벡터 테이블이 가드 안)\n", SCB_VTOR);
    mpu_enable(CTRL_PRIVDEF);
    show("read *(0)", probe_rd(0));
#else
    struct imu *p = (struct imu *)opaque(0);
    memcpy(ram_vec, g_vectors, sizeof ram_vec);
    SCB_VTOR = (uint32_t)ram_vec;
    __asm volatile("dsb\n isb");
    board_printf_raw("C) guard on, VTOR=0x%x (RAM)\n", SCB_VTOR);
    mpu_enable(CTRL_PRIVDEF);
    show("read *(0)", probe_rd(0));
    show("write *(0)", probe_wr(0, 1));
    show("read p->gyro_x (NULL+0x40)", probe_rd((uint32_t)&p->gyro_x));
    show("read NULL+0x100 (가드 밖)", probe_rd(0x100));
    show("call NULL function pointer", probe_x(0));
#endif
    return 0;
}
```

출력에서 볼 것:

- **A**: Cortex-M에서 주소 0은 보통 **벡터 테이블 또는 플래시 별칭**이다. NULL 읽기는 fault 없이 초기 SP 값(`0x20400000`)을 돌려준다. Linux에서는 0번 페이지가 매핑되지 않아 즉시 segfault인데(EL), MCU에서는 **조용히 쓰레기 값을 읽고 계속 간다.** QEMU AN385의 0x0은 SSRAM이라 쓰기도 그냥 들어간다. 실칩 플래시는 쓰기가 무시되거나 버스 오류가 되는데, 어느 쪽인지는 칩마다 다르다(이 노트에서 확인 못 함).
- **C**: 가드가 켜지자 NULL 읽기·쓰기, `p->gyro_x`(NULL + 0x40), NULL 함수 포인터 호출이 전부 잡혔다. 데이터 위반은 MMFAR가 정확히 0과 0x40이고, 함수 포인터는 IACCVIOL + PC = 0이다. 그러나 NULL + 0x100은 가드(256 B) 밖이라 통과했다. **가드 크기 = 잡을 수 있는 가장 큰 구조체 오프셋**이다. 큰 구조체(예: 4 KB 센서 버퍼 구조체)의 끝쪽 필드까지 잡으려면 가드를 키운다. 단, 0x0부터 그만큼은 코드·데이터를 못 둔다.
- **B**: 벡터 테이블이 가드 안에 있어도 MemManage 핸들러가 정상으로 불렸다. 아키텍처 규칙상 **예외 벡터 읽기는 MPU를 거치지 않고 기본 맵을 쓴다**(Armv7-M·v8-M 공통 — QEMU 구현의 근거로 쓰인 Armv7-M 의사코드 설명에서 확인). 그래도 실무에서는 C처럼 VTOR를 옮기거나, STM32처럼 처음부터 플래시가 `0x08000000`에 있고 0x0은 별칭인 칩에서는 VTOR = `0x08000000`으로 두고 0x0 별칭 영역 전체를 가드로 막는다.

덤 — **컴파일러가 먼저 잡는 NULL**: 처음에는 `volatile uint32_t *nul = 0;`으로 썼더니 프로그램이 이상하게 끝났다. 디스어셈블을 보면:

### 5.2 예제 4 — W^X: 플래시는 읽기 전용, RAM·주변장치는 실행 금지

W^X(Write XOR Execute)는 "쓸 수 있는 메모리는 실행할 수 없고, 실행할 수 있는 메모리는 쓸 수 없다"는 원칙이다. 공격자가 버퍼 오버플로로 RAM에 코드를 써 넣고 실행하는 것, 그리고 버그 포인터가 상수 테이블(예: PID 게인, 모터 극수)을 덮는 것을 동시에 막는다.

무엇을 확인하나: MPU 없이와 W^X 설정 후, 플래시 쓰기·RAM 코드 실행·주변장치 주소 실행이 어떻게 되는지. 이번에는 `PRIVDEFENA = 0`으로 "리전 밖은 특권도 금지"까지 본다.

```c
/* F4 예제 4: W^X — FLASH는 읽기 전용, RAM과 주변장치는 실행 금지 */
#include "f4.h"
static const uint32_t gains[4] = { 100, 200, 300, 400 };   /* .rodata → FLASH(0x0~) */
static uint16_t ram_code[4] __attribute__((aligned(4)));   /* RAM에 기계어를 써 넣는다 */
typedef int (*fn_t)(void);

static int call_ram(void)
{
    ram_code[0] = 0x202A;                       /* movs r0, #42 */
    ram_code[1] = 0x4770;                       /* bx lr */
    __asm volatile("dsb\n isb" ::: "memory");
    return ((fn_t)((uint32_t)ram_code | 1u))();
}

int main(void)
{
    SCB_SHCSR |= 1u << 16;
    board_printf_raw("[MPU off]\n");
    show("write gains[0] in FLASH", probe_wr((uint32_t)&gains[0], 999));
    board_printf_raw("   gains[0] is now %u (상수가 바뀌었다)\n", *(volatile const uint32_t *)&gains[0]);
    board_printf_raw("   RAM code returned %d (기본 맵의 SRAM은 실행 가능)\n", call_ram());
    show("execute at UART 0x40004000", probe_x(0x40004000u));

    mpu_set(0, 0x00000000u, RASR(0, AP_RO, ATTR_NORMAL_WT, 0x00, 22));    /* FLASH: RO, 실행 O */
    mpu_set(1, 0x20000000u, RASR(1, AP_FULL, ATTR_NORMAL_WBWA, 0x00, 22)); /* SRAM: RW, XN */
    mpu_set(2, 0x40000000u, RASR(1, AP_FULL, ATTR_DEVICE, 0x00, 29));      /* 주변장치: RW, XN */
    mpu_enable(0);                              /* PRIVDEFENA=0: 리전 밖은 특권도 금지 */
    board_printf_raw("[MPU on: r0 FLASH RO, r1 SRAM XN, r2 periph XN, no background]\n");
    show("write gains[1] in FLASH", probe_wr((uint32_t)&gains[1], 999));
    show("read  gains[1] in FLASH", probe_rd((uint32_t)&gains[1]));
    show("execute RAM code", probe_x((uint32_t)ram_code));
    show("read  0x60000000 (no region, no background)", probe_rd(0x60000000u));
    show("read  SCB CPUID 0xE000ED00 (PPB)", probe_rd(0xE000ED00u));
    return 0;
}
```

출력에서 볼 것:

- **MPU가 꺼져 있어도 주변장치 주소 실행은 막힌다.** Armv7-M 기본 맵에서 Peripheral·Device·System 영역은 원래 XN이다(B8 §3.2). 반면 **SRAM 영역은 기본 맵에서 실행 가능**이라 RAM에 쓴 코드가 42를 돌려줬다. 그래서 W^X의 핵심은 "SRAM 리전에 XN을 거는 것"이다.
- MPU를 켜자 상수 쓰기는 DACCVIOL(MMFAR = `&gains[1]`), RAM 코드 실행은 IACCVIOL(PC = 버퍼 주소)로 잡혔다. 플래시 읽기는 여전히 된다.
- `PRIVDEFENA = 0`이라 리전에 없는 0x60000000은 특권 코드인데도 fault가 났다. 이 모드에서는 주변장치 리전(r2)을 빼먹으면 UART 출력부터 죽는다. PPB(CPUID)는 리전과 무관하게 접근된다(§4.3).
- 함정: **RAM에서 코드를 실행해야 하는 경우**가 있다 — 플래시 지우기·쓰기 루틴(플래시 컨트롤러가 바쁜 동안 플래시에서 실행 못 함), ITCM으로 옮긴 rate loop 코드(B8 §4). 이때는 그 섹션만 정확히 덮는 리전을 RO + 실행 허용으로 따로 두고, 나머지 RAM은 XN으로 남긴다. 코드를 RAM에 복사하는 순간에만 쓰기를 열고(특권 전용), 복사가 끝나면 RO로 바꾼다.

### 5.3 예제 7 — 스택 가드 리전의 기계적 동작

스택 오버플로를 "어떻게 탐지하고 어떤 크기로 가드를 둘지"는 F3의 주제다. 여기서는 **가드 리전이 하드웨어적으로 어떻게 반응하는지**만 본다. 특히 중요한 차이: 함수 본문의 쓰기가 가드에 닿는 경우와, **예외 진입 때 하드웨어가 프레임을 쌓다가** 가드에 닿는 경우.

```c
/* F4 예제 7: 스택 가드 리전의 기계적 동작 — 본문 쓰기(DACCVIOL) vs 예외 스태킹(MSTKERR) */
#include "f4.h"
static uint32_t tstk[64] __attribute__((aligned(256)));   /* 256 B "태스크 스택", 바닥 32 B = 가드 */
#define GUARD_END ((uint32_t)&tstk[8])

static void on_psp(uint32_t sp)                          /* Thread 모드를 PSP로 (특권 유지) */
{
    __asm volatile("msr psp, %0\n mrs r1, control\n orr r1, r1, #2\n msr control, r1\n isb"
                   : : "r"(sp) : "r1", "memory");
}
int main(void)
{
    SCB_SHCSR |= 1u << 16;
    mpu_set(0, 0x00000000u, RASR(0, AP_RO, ATTR_NORMAL_WT, 0x00, 22));
    mpu_set(1, (uint32_t)tstk, RASR(1, AP_NONE, ATTR_NORMAL_WBWA, 0x00, 5));  /* 32 B 가드 */
    mpu_enable(CTRL_PRIVDEF);
    board_printf_raw("tstk=0x%x guard=0x%x..0x%x\n", (unsigned)tstk, (unsigned)tstk, GUARD_END - 1);

    on_psp((uint32_t)&tstk[64]);                          /* SP = 스택 꼭대기 (가드와 멀다) */
    show("A) store into guard, SP far above", probe_wr((uint32_t)&tstk[3], 0));

    uint32_t sp = GUARD_END + 16;                         /* 예외 프레임(32 B)이 다 안 들어가는 자리 */
    board_printf_raw("B) PSP=0x%x, then svc (needs 32 B frame)\n", sp);
    __asm volatile("msr psp, %0\n isb\n svc 0" : : "r"(sp) : "memory");
    board_printf_raw("not reached\n");
    return 1;
}
```

```text
tstk=0x20000100 guard=0x20000100..0x2000011f
  A) store into guard, SP far above -> MemManage DACCVIOL MMFAR=0x2000010c PC=0x220
B) PSP=0x20000130, then svc (needs 32 B frame)
  [exc 4] stacking fault CFSR=0x10 HFSR=0x0 MMARVALID=0 -> stop
[board_exit] code=0
[rc=0]
```

출력에서 볼 것:

- **A**: 함수 본문의 쓰기가 가드에 닿으면 보통의 DACCVIOL이고, MMFAR가 정확한 주소(`0x2000010c`)를 준다. PC로 범인 함수를 찾을 수 있다.
- **B**: SP가 가드 바로 위 16 B에 있는 상태에서 예외(SVC)가 들어오자, 하드웨어가 8워드(32 B) 프레임을 쌓다가 가드에 닿았다. `CFSR=0x10` = **MSTKERR**, MMARVALID = 0이다. 이때는 **쌓인 프레임이 없다** — 핸들러가 `fr[6]`(PC)을 읽으면 안 된다(§0.3에서 MSTKERR를 먼저 본 이유). 원인 PC를 알 수 없으니 실무에서는 "가드에 닿은 태스크 = 현재 태스크"(RTOS의 `pxCurrentTCB`)로 범인을 정한다.
- 현장에서 스택 오버플로가 대부분 B 모양으로 드러난다는 점이 중요하다. 깊은 호출 중에 인터럽트가 들어오는 순간, 프레임 32 B(FPU 컨텍스트가 있으면 104 B)가 한꺼번에 내려가며 가드를 친다. 그래서 가드 크기는 "예외 프레임이 통째로 가드 안에 떨어질 만큼"이어야 하고, Zephyr가 FPU 공유 빌드에서 가드를 64 B → 128 B로 키우는 이유도 이것이다(`CONFIG_MPU_STACK_GUARD_MIN_SIZE_FLOAT` 기본 128 — §7.3). 크기 산정과 다른 탐지법(카나리, PSPLIM)과의 비교는 F3.

v8-M(M33·M55)에는 **PSPLIM/MSPLIM**(스택 한계 레지스터)이 있어서 스택 가드에 MPU 리전을 쓸 필요가 줄었다(B7 §5). Zephyr는 v8-M에서 기본으로 그것(`CONFIG_BUILTIN_STACK_GUARD`)을 쓰고, MPU 가드는 v7-M용이다 — §7.3의 측정에서 이 차이가 비용으로 보인다.

### 5.4 non-cacheable DMA 리전 — 설명만 (QEMU에는 캐시가 없다)

M7·M55·M85처럼 D-cache가 있는 코어에서 DMA 버퍼를 다루는 세 방법(유지 연산, non-cacheable 리전, write-through)과 그 버그는 B8 §6에 측정·시뮬레이터로 자세히 있다. 여기서는 MPU 쪽 결정만 정리한다.

| 결정 | 규칙 | 이유 |
|---|---|---|
| 속성 | **Normal, non-cacheable** (v7-M TEX = 001, C = 0, B = 0 / v8-M MAIR 0x44) | Device로 잡으면 `memcpy`의 비정렬 접근이 fault, 투기 읽기·병합도 막혀 느려짐 |
| S 비트 | 0 또는 1 (non-cacheable이면 의미 작음) | M7은 Normal + S = 1을 아예 캐시 안 함(B8 §3.1) — 의도치 않은 S = 1이 성능 버그가 된다 |
| 배치 | DMA 버퍼를 **한 섹션(`.dma_nocache`)에 모아** 리전 하나로 | 버퍼마다 리전을 주면 리전이 금방 바닥나고, 정렬 낭비가 커진다 (B8 예제 3에서 1 KB 정렬로 `.bss` 2376 B) |
| 크기 | v7-M: 2의 거듭제곱 + SRD, v8-M: 32 B 단위 | §8 계산기 |
| 순서 | 속성을 바꾸기 전에 그 범위를 clean + invalidate, 바꾼 뒤 DSB + ISB | 캐시에 남은 옛 라인이 나중에 덮어씀 |
| XN | 켠다 | 데이터 영역 |

B8 예제 3(QEMU an500, v7-M)에서 `RASR=0x130c0013`(TEX = 1, C = 0, B = 0, S = 1)인 non-cacheable 리전을 만들었고, B8 예제 Z1(an547, v8-M)에서 Zephyr `__nocache`가 MAIR 속성 `0x44` 리전을 만들고 **v8-M은 겹칠 수 없어서 SRAM 리전을 그 앞뒤로 쪼개는 것**을 확인했다. **두 경우 모두 레지스터 값까지만 확인할 수 있고, 캐시 효과(stale 데이터가 사라지는 것)는 QEMU에 캐시가 없어서 보여 줄 수 없다** — 실칩 Nucleo-H743 등에서 확인할 일이다.

FreeRTOS 쪽 함정 하나(소스에서 확인): `ARM_CM4_MPU` 포트는 플래시·RAM 리전 속성을 `configTEX_S_C_B_FLASH`·`configTEX_S_C_B_SRAM`으로 받는데, 둘 다 기본값이 `0x07`(TEX = 000, **S = 1**, C = 1, B = 1 — 주석: "for backward compatibility")이다. 이 포트를 M7(예: STM32H7)에 쓰면 커널이 만드는 RAM 리전이 Shareable이 되어 **D-cache에 안 들어간다**. M7에서는 `configTEX_S_C_B_SRAM`을 `0x0B`(TEX = 001, S = 0, C = 1, B = 1 = Normal WB-WA, non-shareable)로 정의하는 것을 검토한다. `ARM_CM3_MPU`의 `portMPU_REGION_CACHEABLE_BUFFERABLE`도 `0x07 << 16`으로 S 비트를 켠다(예제 9의 `RASR=0x13070013`).

### 5.5 주변장치 리전

주변장치 영역(`0x40000000`~`0x5FFFFFFF`)은 기본 맵에서 이미 Device + XN이다. 그래도 리전을 두는 이유는 두 가지다: (1) `PRIVDEFENA = 0` 설계에서는 리전이 있어야 접근된다, (2) **비특권 태스크에게 주변장치를 열어 주거나 막을 때** — FreeRTOS v7-M 포트는 리전 4를 주변장치 전체 RW + XN(모두에게)으로 고정한다(C8 §3.8). 더 엄격한 설계는 태스크마다 "자기 UART만" 여는 작은 리전을 준다(F5).

## 6. Armv8-M MPU (PMSAv8) — base/limit, MAIR, 겹침 금지

### 6.1 무엇이 바뀌었나

Armv8-M(M23·M33·M35P)과 Armv8.1-M(M52·M55·M85)의 MPU는 레지스터 이름 일부만 같고 규칙이 다르다. v7-M의 "2의 거듭제곱 + 정렬 + subregion"이 사라지고 **시작(base)과 끝(limit)을 32 B 단위로 직접** 쓴다.

| 항목 | Armv7-M (PMSAv7) | Armv8-M (PMSAv8) |
|---|---|---|
| 리전 모양 | 2^n 크기(32 B~4 GB), 크기에 정렬 | base~limit, **32 B 단위 아무 크기·아무 정렬** |
| subregion | 있음 (256 B 이상, 8칸) | **없음** (필요 없어서) |
| 겹침 | 허용, 번호 큰 리전이 이김 | **겹친 주소에 접근하면 fault** |
| 레지스터 | RBAR + RASR | RBAR(base, SH, AP, XN) + RLAR(limit, AttrIndx, EN) |
| 메모리 속성 | 리전마다 TEX·S·C·B | **MAIR0/1**에 속성 8개를 등록하고 리전은 번호(AttrIndx)로 참조 |
| AP | 3비트 (특권/비특권 조합 6가지) | 2비트: 특권 전용 여부 × 읽기 전용 여부 |
| 실행 금지 | XN | XN + v8.1-M은 **PXN**(특권 실행만 금지, RLAR bit4) |
| 보안 상태 | 하나 | TrustZone이 있으면 **Secure MPU와 Non-secure MPU가 따로** |
| 별칭 레지스터 | RBAR_An에 VALID + REGION을 같이 씀 | RNR의 상위 비트 + n으로 리전 결정 (VALID 없음) |

AP 2비트 표:

| AP[2:1] | 특권 | 비특권 |
|---|---|---|
| 00 | RW | 금지 |
| 01 | RW | RW |
| 10 | RO | 금지 |
| 11 | RO | RO |

v7-M의 "특권 RW·비특권 RO"(AP = 010) 조합이 **v8-M에는 없다**. 비특권이 읽기만 하는 공유 상태를 만들려면 리전을 따로 두어야 한다.

MAIR 속성 바이트는 B8 §3.4에 있다: `0xFF` = Normal WB 읽기·쓰기 allocate, `0xAA` = Normal WT 읽기 allocate, `0x44` = Normal non-cacheable, `0x00` = Device-nGnRnE. 상위 4비트가 outer, 하위 4비트가 inner 정책이고, 상위 4비트가 0이면 Device다.

### 6.2 예제 8 — base/limit, 겹침, MAIR, 별칭 레지스터, PXN

무엇을 확인하나: (A) 2의 거듭제곱이 아니고 크기 정렬도 안 된 672 B 리전이 정확히 32 B 경계로 동작하는지, (B) 두 리전이 **모두 읽기를 허용하는** 겹친 주소를 읽으면 어떻게 되는지, (C) MAIR 간접 속성과 RNR + 별칭 레지스터로 리전 3개를 한 번에 쓰기, (D) v8.1-M PXN. M33(an505)과 M55(an547) 둘 다에서 돌린다. 두 머신 모두 Secure 상태에서 부팅하므로 이 코드는 Secure MPU를 쓴다.

v8-M용 헤더(같은 복구 핸들러 방식, 다중 코어 하네스의 `start.c`에 들어 있다):

```c
/* F4: Armv8-M(PMSAv8) MPU 레지스터 + 프로브 (start.c의 복구 핸들러와 같이 쓴다) */
#ifndef F4V8_H
#define F4V8_H
#include "semi.h"
#define MPU_TYPE  REG32(0xE000ED90u)
#define MPU_CTRL  REG32(0xE000ED94u)
#define MPU_RNR   REG32(0xE000ED98u)
#define MPU_RBAR  REG32(0xE000ED9Cu)   /* [31:5] BASE, [4:3] SH, [2:1] AP, [0] XN */
#define MPU_RLAR  REG32(0xE000EDA0u)   /* [31:5] LIMIT, [4] PXN(v8.1-M), [3:1] AttrIndx, [0] EN */
#define MPU_RBAR_A(n) REG32(0xE000ED9Cu + 8u * (n))   /* n=1..3: 별칭 → 리전 (RNR & ~3) + n */
#define MPU_MAIR0 REG32(0xE000EDC0u)   /* Attr0..3 (바이트 하나씩) */
#define SCB_SHCSR REG32(0xE000ED24u)
/* AP: 0 = 특권 RW, 1 = 모두 RW, 2 = 특권 RO, 3 = 모두 RO */
#define RBAR(base, sh, ap, xn)   (((base) & ~0x1Fu) | ((sh) << 3) | ((ap) << 1) | (xn))
#define RLAR(limit, attr)        (((limit) & ~0x1Fu) | ((attr) << 1) | 1u)
extern volatile uint32_t g_fn, g_fexc, g_fcfsr, g_fmmfar, g_fpc;
static inline void mpu_on(uint32_t privdef)
{
    MPU_CTRL = (privdef << 2) | 1u;
    __asm volatile("dsb\n isb" ::: "memory");
}
__attribute__((noinline)) static int pr_rd(uint32_t a)
{
    uint32_t n0 = g_fn, v; __asm volatile("ldr %0, [%1]" : "=r"(v) : "r"(a) : "memory"); (void)v; return g_fn - n0;
}
__attribute__((noinline)) static int pr_wr(uint32_t a)
{
    uint32_t n0 = g_fn; __asm volatile("str %0, [%0]" : : "r"(a) : "memory"); return g_fn - n0;
}
__attribute__((noinline, unused)) static int pr_x(uint32_t a)
{
    uint32_t n0 = g_fn; ((void (*)(void))(a | 1u))(); return g_fn - n0;
}
static inline void say(const char *what, int nf)
{
```

- **C**: `RNR = 4`를 한 번 쓰고 RBAR/RLAR, RBAR_A1/RLAR_A1, RBAR_A2/RLAR_A2에 연속으로 쓰자 리전 4·5·6이 설정되었고 RNR은 4 그대로다. v8-M 별칭은 **RNR의 하위 2비트를 무시하고 `(RNR & ~3) + n`** 리전을 가리킨다(v7-M처럼 RBAR에 리전 번호를 넣지 않는다). FreeRTOS v8-M PendSV가 `RNR = 4` → `stmia` 8워드, `RNR = 8` → `stmia` …로 4개씩 쓰는 이유다(§7.2).

- **D(M55만)**: XN = 0인 RAM 리전은 실행되지만, **PXN = 1을 주자 특권 코드의 실행만** 막혔다(IACCVIOL, PC = 버퍼). PXN은 "비특권 앱의 코드를 커널(특권)이 실수로·공격으로 실행하는 것"을 막는 v8.1-M의 기능이다. 커널이 비특권 영역으로 점프하는 공격(Linux의 PXN·SMEP와 같은 착상)에 대응한다. M33(v8.0-M)에서는 RLAR bit4가 예약이라 이 실험을 하지 않았다.

### 6.3 Secure·Non-secure MPU (자세히는 F6)

예제 1에서 본 것처럼 TrustZone이 있는 M33·M55는 MPU가 두 벌이다. Secure 코드는 `0xE000ED90`(자기 것)과 `0xE002ED90`(Non-secure 것)을 둘 다 만질 수 있고, Non-secure 코드는 `0xE000ED90`에서 **자기(NS) MPU만** 본다. CMSIS도 `ARM_MPU_SetRegion_NS()`, `ARM_MPU_Enable_NS()` 같은 `_NS` 함수를 따로 준다(`mpu_armv8.h`). Non-secure에서 도는 RTOS(TF-M 위의 FreeRTOS·Zephyr)는 NS MPU만 관리하고, Secure 쪽 메모리는 SAU/IDAU가 막는다. MPU와 SAU의 관계, 어느 쪽이 먼저 검사하는지는 F6에서 다룬다.

## 7. 컨텍스트 스위치 때 리전 교체

### 7.1 왜 태스크마다 다른가

리전 중 일부는 시스템 전체에 하나다(플래시 RO, 주변장치, 널 가드, DMA non-cacheable). 이것들은 부팅 때 한 번 쓰고 끝이다. 하지만 다음 둘은 **지금 도는 태스크가 누구냐**에 따라 달라진다.

- **스택 가드**: 태스크마다 스택 위치가 다르다. 가드는 "지금 태스크 스택의 바닥"에 있어야 한다.
- **격리 리전**: 비특권 태스크 A는 자기 스택과 자기 버퍼만, B는 B의 것만 접근해야 한다(F5).

그래서 RTOS는 컨텍스트 스위치 때 이 "동적 리전"을 다음 태스크 것으로 바꿔 쓴다. 비용 관점에서 질문은 하나다: **리전 값을 언제 계산하나.** 미리(태스크 생성 때) 계산해 TCB에 넣어 두면 스위치 때는 복사만 하면 되고, 스위치 때마다 계산하면 그만큼 느리다. FreeRTOS와 Zephyr가 정확히 이 지점에서 다르다.

### 7.2 FreeRTOS-MPU — 생성 때 계산, 스위치 때 `stm` 한 번

**저장 위치.** MPU 포트의 TCB는 두 번째 멤버가 `xMPU_SETTINGS xMPUSettings`다(`tasks.c`의 `TCB_t`, `portUSING_MPU_WRAPPERS == 1`일 때). 그 안의 `xRegion[]`이 **RBAR·RASR에 그대로 쓸 값** 쌍이다. v7-M 포트(`portable/GCC/ARM_CM3_MPU/portmacro.h`)에서는 태스크마다 리전 4개 = 설정 가능한 3개(`xRegions[]` 인자) + 스택 1개다.

| 리전 번호 (ARM_CM3_MPU) | 내용 | 바뀌나 |
|---|---|---|
| 0~2 | 태스크가 `TaskParameters_t.xRegions`로 준 리전 | 태스크마다 |
| 3 (`portSTACK_REGION`) | 태스크 스택 (특권 태스크면 SRAM 전체) | 태스크마다 |
| 4 | 주변장치 전체 RW + XN | 고정 |
| 5 | 플래시 전체 RO | 고정 |
| 6 | `privileged_functions` 특권 전용 | 고정 |
| 7 | `privileged_data` 특권 전용 + XN | 고정 |

번호 배치가 §3의 규칙 그대로다. 커널 보호(5~7)가 **가장 높은 번호**라서 태스크가 아무 리전을 줘도 커널 영역을 덮어쓸 수 없다. v8-M 포트(`ARM_CM33_NTZ/non_secure/portmacrocommon.h`)는 겹침이 없으니 순서가 상관없어서 반대로 커널 0~3, 스택 4, 설정 가능 5~(`configTOTAL_MPU_REGIONS` − 1)로 둔다. M4F·M7용 `ARM_CM4_MPU`는 `configTOTAL_MPU_REGIONS`(8 또는 16)에 맞춰 커널 리전을 맨 위 4개로, 스택을 그 아래로 계산한다.

**언제 계산하나.** `xTaskCreateRestricted()` → `vPortStoreTaskMPUSettings()`(`port.c`)가 태스크 생성 때 한 번 RBAR 값(`base | VALID | 리전 번호`)과 RASR 값(`AP | XN | 속성 | SIZE | EN`)을 만들어 TCB에 넣는다. `xRegions == NULL`(일반 `xTaskCreate`로 만든 특권 태스크)이면 스택 리전 자리에 **SRAM 전체 RW**를 넣는다. 크기 → SIZE 필드 변환(`prvGetMPURegionSizeSetting()`)도 이때 한다.

**스위치 때.** `ARM_CM3_MPU/port.c`의 `xPortPendSVHandler`(V11.3.2 소스 그대로, 리전 부분만):

```asm
        /*------------ Program MPU. ------------ */
        ldr r3, =pxCurrentTCB                 /* r3 = =pxCurrentTCB. */
        ldr r2, [r3]                          /* r2 = pxCurrentTCB. */
        add r2, r2, #4                        /* r2 = Second item in the TCB which is xMPUSettings. */
        dmb                                   /* Complete outstanding transfers before disabling MPU. */
        ldr r0, =0xe000ed94                   /* MPU_CTRL register. */
        ldr r3, [r0]                          /* Read the value of MPU_CTRL. */
        bic r3, #1                            /* r3 = r3 & ~1 i.e. Clear the bit 0 in r3. */
        str r3, [r0]                          /* Disable MPU. */
        ldr r0, =0xe000ed9c                   /* Region Base Address register. */
        ldmia r2!, {r4-r11}                   /* Read 4 sets of MPU registers [MPU Region # 0 - 3]. */
        stmia r0, {r4-r11}                    /* Write 4 sets of MPU registers [MPU Region # 0 - 3]. */
        ldr r0, =0xe000ed94                   /* MPU_CTRL register. */
        ldr r3, [r0]                          /* Read the value of MPU_CTRL. */
        orr r3, #1                            /* r3 = r3 | 1 i.e. Set the bit 0 in r3. */
        str r3, [r0]                          /* Enable MPU. */
        dsb                                   /* Force memory writes before continuing. */
```

`stmia r0, {r4-r11}`가 핵심이다. 8워드를 `0xE000ED9C`부터 연속으로 쓰면 RBAR, RASR, RBAR_A1, RASR_A1, RBAR_A2, RASR_A2, RBAR_A3, RASR_A3에 차례로 들어간다. 각 RBAR 값에 VALID + 리전 번호가 들어 있으므로(예제 2의 트릭) **리전 4개가 명령 하나로** 바뀐다. 쓰는 동안 MPU를 껐다 켜는 이유는 4개가 반쯤 바뀐 순간(예: 리전 3의 RBAR만 새 값)에 접근이 검사받지 않게 하려는 것이다. Handler 모드 PendSV는 특권이고, 커널 코드·스택은 PRIVDEFENA 배경으로 접근되므로 MPU가 꺼져 있어도 문제없다. `isb`가 없는 이유는 §4.4 — 곧 예외 복귀(`bx lr`)가 동기화를 해 준다.

v8-M(`ARM_CM33_NTZ/non_secure/portasm.c`)은 같은 일을 이렇게 한다: MPU 끄기 → TCB에서 **MAIR0**를 꺼내 쓰기(태스크마다 속성 표가 다를 수 있다) → `RNR = 4` → `ldmia/stmia` 8워드(리전 4~7) → `configTOTAL_MPU_REGIONS == 16`이면 `RNR = 8`, `RNR = 12`로 두 번 더 → MPU 켜기. v8-M 별칭은 RNR 기준이라 4개마다 RNR을 다시 쓴다(예제 8 C).

#### 예제 9 — 같은 yield 핑퐁을 일반 포트와 MPU 포트에서, 그리고 태스크별 리전 확인

무엇을 확인하나: (1) MPU 포트에서 두 태스크가 각각 돌 때 하드웨어 리전 0~3이 실제로 그 태스크 것으로 바뀌는지, (2) 같은 우선순위 두 태스크가 `taskYIELD()`로 핑퐁할 때 스위치 1회 비용이 일반 포트(`ARM_CM3`)와 MPU 포트(`ARM_CM3_MPU`, 특권·비특권 태스크)에서 얼마나 다른지. MPU 빌드는 C8 예제 5의 설정·링커 스크립트·Makefile을 `~/.rtos_scratch/F4/frmpu/`로 복사해 썼다. 복사본의 링커 스크립트에는 랩 `startup.c`가 10-25 이후 요구하는 `.preinit_array`/`.init_array` 섹션을 더했다(없으면 `undefined reference to __preinit_array_start`로 링크 실패).

```c
/* F4 예제 9: 같은 yield 핑퐁을 ARM_CM3 / ARM_CM3_MPU(특권·비특권) 포트에서 — 스위치 비용과 태스크별 리전 */
#include "FreeRTOS.h"
#include "task.h"
#include "board.h"
#define FPGAIO REG32(0x40028018u)                         /* 25 MHz, 1 tick = 40 ns */
#define N 2000
#ifndef UNPRIV
#define UNPRIV 0
#endif
static struct { volatile uint32_t ready, done, t0, t1; uint32_t pad[4]; } sh __attribute__((aligned(32)));
#if portUSING_MPU_WRAPPERS
static StackType_t stk[2][256] __attribute__((aligned(1024)));   /* MPU 포트: 스택 리전 = 크기 정렬 */
#endif

static void worker(void *arg)
{
    uint32_t id = (uint32_t)arg;
#if portUSING_MPU_WRAPPERS && !UNPRIV
    for (uint32_t r = 0; r < 4; r++) {                    /* 특권 태스크라 MPU 레지스터를 읽을 수 있다 */
        REG32(0xE000ED98u) = r;
        board_printf_raw("  task%u r%u RBAR=0x%x RASR=0x%x\n", id, r, REG32(0xE000ED9Cu), REG32(0xE000EDA0u));
    }
#endif
    sh.ready++;
    while (sh.ready < 2) taskYIELD();
    if (id == 0) sh.t0 = FPGAIO;
    for (int i = 0; i < N; i++) taskYIELD();
    if (++sh.done == 2) sh.t1 = FPGAIO;
    vTaskSuspend(NULL);
}
static void monitor(void *arg)                           /* 가장 낮은 우선순위, 특권: 결과 출력·종료 */
{
    (void)arg;
    while (sh.done < 2) vTaskDelay(1);
    uint32_t ns = (sh.t1 - sh.t0) * 40u / (2u * N);
    board_printf_raw("%s: %u switches, %u ns/switch = %u instr\n",
                     portUSING_MPU_WRAPPERS ? (UNPRIV ? "CM3_MPU unpriv" : "CM3_MPU priv") : "CM3 plain",
                     2u * N, ns, ns / 32u);
    board_exit(0);
}
int main(void)
{
    for (uint32_t i = 0; i < 2; i++) {
#if portUSING_MPU_WRAPPERS
        TaskParameters_t p = { .pvTaskCode = worker, .pcName = "w", .usStackDepth = 256,
            .pvParameters = (void *)i, .uxPriority = 2 | (UNPRIV ? 0 : portPRIVILEGE_BIT),
            .puxStackBuffer = stk[i],
            .xRegions = { { &sh, sizeof sh, portMPU_REGION_READ_WRITE | portMPU_REGION_EXECUTE_NEVER },
                          { 0, 0, 0 }, { 0, 0, 0 } } };
        xTaskCreateRestricted(&p, NULL);
#else
        xTaskCreate(worker, "w", 256, (void *)i, 2, NULL);
#endif
    }
    xTaskCreate(monitor, "mon", 256, NULL, 1 | (portUSING_MPU_WRAPPERS ? portPRIVILEGE_BIT : 0), NULL);
    vTaskStartScheduler();
    return 1;
}
```

- **리전 3(스택)이 태스크마다 다르다**: task0 = `0x20008800`, task1 = `0x20008C00` — 각자의 1 KB 스택(`stk[0]`, `stk[1]`)이다. ### 7.3 Zephyr — 스위치 때마다 C로 계산

Zephyr Cortex-M의 PendSV(`arch/arm/core/cortex_m/swap_helper.S`)는 `CONFIG_MPU_STACK_GUARD` 또는 `CONFIG_USERSPACE`가 켜져 있으면 새 스레드를 인자로 C 함수를 부른다:

```asm
#if defined(CONFIG_MPU_STACK_GUARD) || defined(CONFIG_USERSPACE)
    /* Re-program dynamic memory map */
    push {r2,lr}
    mov r0, r2 /* _current thread */
    bl z_arm_configure_dynamic_mpu_regions
    pop {r2,lr}
#endif
```

`z_arm_configure_dynamic_mpu_regions(thread)`(`arch/arm/core/mpu/arm_core_mpu.c`)는 **스위치 때마다** 이 스레드의 동적 리전 목록을 만든다:

1. `CONFIG_USERSPACE`면 스레드가 속한 memory domain의 파티션들 (F5).
2. user 스레드면 그 스레드의 user 스택.
3. `CONFIG_MPU_STACK_GUARD`면 가드: supervisor 스레드는 `stack_info.start - guard_size`, user 스레드는 특권 스택 앞. 속성은 `K_MEM_PARTITION_P_RO_U_NA` — **특권 읽기 전용**이다. 가드에 쓰기만 막고 읽기는 허용한다는 점이 FreeRTOS·일반 설명의 "접근 금지 가드"와 다르다.

그리고 `arm_core_mpu_configure_dynamic_mpu_regions()` → 아키텍처별 `mpu_configure_dynamic_mpu_regions()`가 리전마다 크기를 SIZE·속성으로 인코딩해 쓰고, 남은 리전을 `ARM_MPU_ClrRegion()`으로 끈다. v7-M(`arm_mpu_v7_internal.h`)은 정적 SRAM 리전 **위에 겹쳐** 쓴다. v8-M(`arm_mpu_v8_internal.h`)은 겹칠 수 없으니 `CONFIG_MPU_GAP_FILLING = y`면 배경 SRAM 리전을 동적 리전 앞뒤로 **쪼개서 다시 쓰고**, `n`이면 SRAM 리전을 아예 끄고 특권 코드는 PRIVDEFENA 배경에 맡긴다. `MPU_GAP_FILLING`의 기본값은 `y if !USERSPACE`(`arch/Kconfig`)라서, userspace를 켜면 기본이 "SRAM 리전 끄기"다.

가드 크기는 `MPU_GUARD_ALIGN_AND_SIZE`(`include/zephyr/arch/arm/arch.h`)다. 리전 최소 크기 `CONFIG_ARM_MPU_REGION_MIN_ALIGN_AND_SIZE`가 32 B 이하면 "예외 프레임이 넉넉히 들어가게"(소스 주석) 64 B로 올리고, FPU 공유 + MPU 가드면 최소 크기 자체가 128 B다(`arch/arm/core/mpu/Kconfig`). 예제 10의 an385에서 64 B로 확인된다.

#### 예제 10 — 스레드 전환 때 바뀌는 리전 보기 + k_yield 핑퐁 비용 (v7-M an385, v8-M an521)

무엇을 확인하나: 네 구성(가드 없음, MPU 스택 가드, USERSPACE + supervisor 스레드, USERSPACE + user 스레드)에서 (1) 스레드마다 어떤 리전이 보이는지, (2) `k_yield()` 핑퐁의 스위치 1회 비용. M3(an385)는 예제 9와 같은 시계(FPGAIO, `ICOUNT=1 rtos-run-mps2`)로, M33(an521)은 `CONFIG_QEMU_ICOUNT_SHIFT=5`(같은 32 ns/명령)에서 SysTick 기반 `k_cycle_get_32()`로 잰다. 스레드 생성·join 비용을 빼려고 N = 1000과 3000을 각각 재서 **차분**을 쓴다. `CONFIG_TIMESLICING=n`(B10 예제 10에서 타임 슬라이스 재설정이 yield 비용을 지배한다는 것을 확인했다).

```c
/* F4 예제 10: Zephyr가 스레드 전환마다 바꾸는 MPU 리전 보기 + k_yield 핑퐁 비용 (an385 v7-M / an521 v8-M) */
#include <zephyr/kernel.h>
#define REG(a) (*(volatile uint32_t *)(a))
#ifdef CONFIG_BOARD_MPS2_AN385
#define NOW() REG(0x40028018)                          /* FPGAIO 25 MHz, ICOUNT=1 rtos-run-mps2로 실행 */
#else
#define NOW() k_cycle_get_32()                         /* SysTick 25 MHz (an521) */
#endif
#define STK 1024
K_THREAD_STACK_ARRAY_DEFINE(stk, 2, STK);
static struct k_thread th[2];

static void dump(int id)                               /* supervisor 스레드만: 지금 켜진 리전 */
{
	for (uint32_t r = 0; r < ((REG(0xE000ED90) >> 8) & 0xFF); r++) {
		REG(0xE000ED98) = r;
		uint32_t b = REG(0xE000ED9C), a = REG(0xE000EDA0);
		if (!(a & 1)) continue;
#ifdef CONFIG_ARMV8_M_MAINLINE                        /* RBAR/RLAR: base..limit */
		printk("  t%d r%u 0x%08x..0x%08x AP=%u XN=%u attr=%u\n", id, r, b & ~0x1Fu, a | 0x1F,
		       (b >> 1) & 3, b & 1, (a >> 1) & 7);
#else                                                 /* RBAR/RASR: base + 2^(SIZE+1) */
		printk("  t%d r%u base=0x%08x size=%u AP=%u XN=%u\n", id, r, b & ~0x1Fu,
		       1u << (((a >> 1) & 0x1F) + 1), (a >> 24) & 7, (a >> 28) & 1);
#endif
	}
}
static void worker(void *p1, void *p2, void *p3)
{
	int n = (int)(intptr_t)p1, id = (int)(intptr_t)p2;
	if ((intptr_t)p3) dump(id);
	for (int i = 0; i < n; i++) k_yield();
}
static uint32_t run(int n, uint32_t opt, int show)
{
	uint32_t t0 = NOW();
	for (int i = 0; i < 2; i++)
		k_thread_create(&th[i], stk[i], STK, worker, (void *)(intptr_t)n, (void *)(intptr_t)i,
				(void *)(intptr_t)show, 5, opt, K_NO_WAIT);
	for (int i = 0; i < 2; i++) k_thread_join(&th[i], K_FOREVER);
	return NOW() - t0;
}
int main(void)
{
	uint32_t opt = IS_ENABLED(CONFIG_USERSPACE) && IS_ENABLED(CONFIG_F4_USER) ? K_USER : 0;
	printk("stacks: %p %p  HW_STACK_PROT=%d MPU_GUARD=%d USERSPACE=%d user=%d\n", stk[0], stk[1],
	       IS_ENABLED(CONFIG_HW_STACK_PROTECTION), IS_ENABLED(CONFIG_MPU_STACK_GUARD),
	       IS_ENABLED(CONFIG_USERSPACE), opt == K_USER);
	run(1, 0, 1);                                     /* 리전 덤프 (supervisor) */
	uint32_t a = run(1000, opt, 0), b = run(3000, opt, 0);
	uint32_t ns = (uint32_t)((uint64_t)(b - a) * 40u / (2u * 2000u));   /* 25 MHz = 40 ns; 차분으로 생성·join 제거 */
	printk("k_yield ping-pong: %u ns/switch = %u instr\n", ns, ns / 32u);
	return 0;
}
```

## 8. 리전 계획 — 드론 FC(STM32H7급) 워크시트

### 8.1 예제 11 — "이 범위를 덮는 데 v7-M 리전이 몇 개 드나" 계산기

v7-M에서 리전 계획의 핵심 질문은 "2의 거듭제곱 + 정렬 + SRD로 이 범위를 몇 개에 덮을 수 있나"다. 손으로 하면 틀리기 쉬워서 작은 계산기를 만들었다. (1) 리전 하나 + SRD로 정확히 덮을 수 있으면 그것을, (2) 안 되면 시작 주소에 정렬된 가장 큰 2^n 조각을 떼어 내며 반복한다(최적은 아니지만 실무 판단에는 충분하다).

```python
#!/usr/bin/env python3
"""F4 예제 11: 주소 범위를 Armv7-M MPU 리전(2^n 크기 + 크기 정렬 + SRD 8칸)으로 덮는 데 몇 개가 드나 / v8-M과 비교."""
def v7_cover(start, size):
    end, out = (start + size + 31) & ~31, []       # MPU 최소 단위 32 B로 바깥쪽 확장
    start &= ~31
    while start < end:
        for lg in range(5, 33):                       # 1) 리전 하나 + SRD로 정확히 덮을 수 있나
            base = start & ~((1 << lg) - 1)
            if base + (1 << lg) < end:
                continue
            if lg >= 8:
                sub = 1 << (lg - 3)
                if start % sub == 0 and end % sub == 0:
                    srd = sum(1 << k for k in range(8)
                              if not (start <= base + k * sub and base + (k + 1) * sub <= end))
                    out.append((base, lg, srd)); return out
            if base == start and base + (1 << lg) == end:
                out.append((base, lg, 0)); return out
            break
        lg = 5                                         # 2) 안 되면 start에 정렬된 가장 큰 2^n 조각을 떼어 낸다
        while start % (1 << (lg + 1)) == 0 and start + (1 << (lg + 1)) <= end:
            lg += 1
        out.append((start, lg, 0)); start += 1 << lg
    return out

def fmt(lg):
    return f"{1 << (lg - 20)}MB" if lg >= 20 else f"{1 << (lg - 10)}KB" if lg >= 10 else f"{1 << lg}B"

ranges = [  # 이름, 시작, 크기 (STM32H743급 드론 FC 예시)
    ("flash 2MB",            0x08000000, 2 << 20),
    ("AXI SRAM 512KB",       0x24000000, 512 << 10),
    ("D2 SRAM1+2+3 288KB",   0x30000000, 288 << 10),
    ("DMA pool 48KB",        0x30020000, 48 << 10),
    ("log buffer 20KB",      0x24070000, 20 << 10),
    ("odd 1000B @0x24001020", 0x24001020, 1000),
]
for name, s, n in ranges:
    regs = v7_cover(s, n)
    v8 = "1 (32 B 정렬 아님 → 확장 필요)" if (s % 32 or n % 32) else "1"
    print(f"{name:24s} v7-M: {len(regs)} region(s) " +
          ", ".join(f"[0x{b:08x} {fmt(l)} SRD=0x{d:02x}]" for b, l, d in regs) + f"  | v8-M: {v8}")
```

| r7 | `0x38000000` | 64 KB | RW/RW | 1 | **Normal NC** | SRAM4: BDMA(D3 도메인) 버퍼 |
| r8 | `0x38800000` | 4 KB | RW/금지 | 1 | Normal WB-WA | Backup SRAM: 크래시 기록 (F8, E8 noinit) |
| r9 | `0x40000000` | 512 MB | RW/RW | 1 | Device | 주변장치 |
| r10 | `0x90000000` | 16 MB | RO/RO | 1 | Normal WT | QSPI 플래시: 로그·파라미터 (실행 안 함) |
| r11~r13 | (동적) | | | | | RTOS 태스크별 리전: 비특권 텔레메트리 파서의 버퍼·스택 (F5) |
| r14 | (동적) | 32~128 B | 금지 또는 RO | 1 | | 현재 태스크 스택 가드 (v7-M이라 MPU 가드, F3) |
| r15 | `0x00000000` | 256 B | 금지/금지 | 1 | Strongly-ordered | 널 가드 — r2(ITCM)보다 높은 번호라 이긴다. ITCM 코드 배치는 `0x100`부터 |

이 표를 만들 때 쓴 규칙:

- **번호 순서**: 넓은 허용(r1~r10)은 낮게, 제한(가드)은 높게. r0 배경 금지가 가장 낮다.
- **non-cacheable은 섹션 단위**: DMA 버퍼를 전부 SRAM3·SRAM4에 모아서 리전 2개로 끝낸다. 버퍼마다 리전을 주지 않는다.
- **동적 리전 예산**: 16개 중 고정 12개(r0~r10, r15), 동적 4개(r11~r14). FreeRTOS `ARM_CM4_MPU`(`configTOTAL_MPU_REGIONS = 16`)를 쓰면 배치가 포트에 의해 정해진다 — 커널 리전 4개가 맨 위(12~15), 스택이 11, 태스크 설정 리전이 0~10이다. 그때는 위 표의 고정 리전 대부분을 **태스크 설정 리전(xRegions)으로 넘기거나**, 커널 리전의 속성 매크로(`configTEX_S_C_B_SRAM` 등, §5.4)로 표현해야 한다. 어느 RTOS를 쓰든 "고정 몇 개 + 태스크당 몇 개"의 예산을 먼저 정한다.
- **v8-M(예: STM32H5·U5, M33)으로 가면**: 배경 금지 리전과 겹쳐 쓰는 r15·r14 같은 구조는 불가능하다. 널 가드 대신 "0번지 근처를 어떤 리전도 덮지 않고 PRIVDEFENA = 0"으로, 스택 가드는 PSPLIM으로 한다.

## 10. 실무에서 다시 보기

### 10.1 드론 비행 제어기 (STM32H743)

§8.2의 워크시트가 출발점이다. bring-up 순서는: (1) 캐시를 켜기 **전에** MPU를 설정한다 — 캐시를 먼저 켜면 DMA 영역이 잠깐이라도 WB로 캐시에 들어간다(B8). (2) 배경 금지 r0 + 필요한 리전만 연다. (3) `SHCSR`에서 MemManage·BusFault·UsageFault를 켜고 MemManage 우선순위를 가장 높게. (4) MemManage 핸들러는 CFSR·MMFAR·쌓인 PC·LR·현재 태스크 이름을 Backup SRAM(r8)에 magic + CRC로 남기고(E8 §7) 비행 중이면 failsafe(모터 정지가 아니라 안전 착륙 모드 — 기체 설계에 따라)로, 지상이면 리셋한다. 비행 중 MemManage를 "건너뛰고 계속"하는 것은 예제 하네스에서만 허용되는 일이다.

```c
/* 드론 FC MemManage 기록 예 (설계 스케치 — 빌드만, 실행은 하네스의 fault_common으로 대신 확인) */
typedef struct { uint32_t magic, cfsr, mmfar, pc, lr, task_hash, crc; } mm_rec_t;
extern mm_rec_t g_mm_rec;                       /* .noinit, Backup SRAM (r8) */
void mm_record(const uint32_t *fr, uint32_t cfsr, uint32_t task_hash)
{
    g_mm_rec.cfsr = cfsr;
    g_mm_rec.mmfar = (cfsr & 0x80u) ? REG32(0xE000ED34u) : 0xFFFFFFFFu;
    g_mm_rec.pc = (cfsr & 0x18u) ? 0xFFFFFFFFu : fr[6];   /* MSTKERR면 프레임 없음 */
    g_mm_rec.lr = (cfsr & 0x18u) ? 0xFFFFFFFFu : fr[5];
    g_mm_rec.task_hash = task_hash;
    g_mm_rec.magic = 0x4D504D4Du;               /* 'MPMM' */
    g_mm_rec.crc = 0;                           /* CRC 계산은 E8 rec_seal() 재사용 */
}
```

(빌드만 함: `#include <stdint.h>`, `"board.h"`를 붙여 `arm-none-eabi-gcc -mcpu=cortex-m7 -O2 -Wall -Wextra -c`로 경고 0개, text 80 B. 실행은 하지 않았다 — 같은 판정(MSTKERR면 프레임을 안 읽음)은 하네스 `fault_common`에서 예제 7로 확인했다. CRC 봉인·리셋 루프 처리는 E8의 `rec_seal()`·safe mode 예제를 그대로 쓴다.)

### 10.2 로봇 관절 모터 컨트롤러 (FOC 20 kHz)

여기서는 **동적 리전을 쓰지 않는다.** 20 kHz 전류 루프는 ISR이고(태스크 스위치 없음), 스위치당 +122 명령 같은 비용을 낼 이유가 없다. 고정 리전만: 플래시 RO, RAM XN, 널 가드, ADC DMA 버퍼 non-cacheable(M7급이면). 스택 가드는 메인 스택(MSP) 하나에만 둔다 — ISR은 전부 MSP를 쓰므로 MSP 가드가 실제로 가장 중요한 가드다. v8-M(M33) 칩이면 MSPLIM으로 대체한다.

### 10.3 센서 허브 MCU (Linux SoC 옆, Zephyr)

Linux 쪽에서 내려오는 설정 메시지를 파싱하는 코드를 user 스레드로 두고(F5), 그 스레드의 domain에 "메시지 버퍼 파티션"만 준다. 비용(§7.4)을 감수하는 이유는 신뢰 경계다 — 호스트가 보낸 이상한 메시지로 파서가 망가져도 IMU 타임스탬프 경로는 살아야 한다. v8-M 칩(nRF5340 앱 코어, STM32U5)이면 `MPU_GAP_FILLING`과 리전 수(8)가 domain 파티션 개수 상한을 정한다는 점을 설계 초기에 확인한다.

### 10.4 Don의 SSD 컨트롤러

SSD Cortex-R 펌웨어에서 쓰던 MPU 설계 — 코드 RO, DMA 디스크립터·호스트 버퍼 non-cacheable, 공유 메모리(코어 간 메일박스) non-cacheable 또는 shareable — 는 이 노트의 고정 리전 그대로다. 면접에서 "MPU 써 봤나"에는 이 경험으로 답하고, Cortex-M에서 새로 할 수 있는 것은 "RTOS 태스크마다 리전을 바꾸는 것과 그 비용(FreeRTOS 15 명령 vs Zephyr 120 명령)을 재 봤다"로 덧붙이면 된다.

## 12. 면접에서 이렇게 말한다

**Q.** What's the difference between an MPU and an MMU?

**A.** MMU는 가상 주소를 페이지 테이블로 물리 주소로 번역하면서 권한을 본다. MPU는 번역 없이 주소를 8~16개 리전 레지스터와 병렬로 비교해 권한과 메모리 속성만 정한다. 그래서 MPU는 TLB 미스나 페이지 테이블 메모리가 없고 결정적이지만, 규칙 수가 적고 v7-M에서는 2의 거듭제곱·정렬 제약이 있다. 주소 공간이 하나라서 격리는 "같은 주소, 다른 권한"으로 한다.

> An MMU translates virtual addresses to physical ones through page tables and checks permissions along the way. An MPU does no translation: it compares every address against a small set of region registers — eight or sixteen on Cortex-M — in parallel and decides permission and memory attributes like cacheability. So there are no page tables in RAM and no TLB misses, which keeps timing deterministic, but you only get a handful of rules, and on Armv7-M each region must be a power of two in size and aligned to that size. Everything shares one address space, so isolation means the same addresses with different permissions per task.

**꼬리 질문**: "Can you have virtual memory on a Cortex-M?" → 없다. 주소를 바꾸는 하드웨어가 없으니 프로세스마다 같은 주소에 다른 메모리를 둘 수 없다. 필요하면 MMU가 있는 Cortex-R82·Cortex-A로 간다(F9).

**Q.** How do you catch NULL pointer dereferences on a Cortex-M?

**A.** 주소 0 근처는 보통 벡터 테이블이나 플래시 별칭이라서 NULL을 읽어도 fault가 안 나고 쓰레기 값이 나온다. MPU로 0번지부터 256 B쯤을 특권·비특권 모두 금지·XN으로 막고, 그 리전을 높은 번호에 둔다. 벡터 읽기는 MPU를 거치지 않지만 실무에서는 VTOR를 실제 플래시 주소로 둔다. 가드 크기가 잡을 수 있는 최대 필드 오프셋이다.

> On most Cortex-M parts address zero is the vector table or a flash alias, so a NULL read silently returns the initial stack pointer instead of faulting — I demonstrated that on QEMU. I put a no-access, execute-never MPU region over the first 256 bytes or so, with a high region number so it wins over the flash or ITCM region underneath. Then NULL reads, writes, struct-member accesses within the guard, and calls through a NULL function pointer all raise MemManage, with MMFAR giving the exact address. Vector fetches use the default memory map, but I still point VTOR at the real flash address. The guard size bounds the largest struct offset you'll catch.

**Q.** Why must Armv7-M MPU regions be a power of two, and how do you deal with odd sizes?

**A.** 비교 하드웨어가 "주소의 상위 비트가 base와 같은가"만 보기 때문이다. 크기가 2^n이고 정렬되어 있으면 마스크 비교 하나로 끝난다. 이상한 크기는 256 B 이상 리전의 subregion 8칸을 꺼서 다듬거나, 리전 여러 개로 나누거나, 링커 스크립트에서 객체를 2^n 섹션에 모은다. v8-M은 base/limit 비교라 32 B 단위 아무 크기다.

> Because the comparator just masks the address and compares the upper bits with the base — a power-of-two size aligned to itself makes that a single mask-and-compare per region. For odd sizes I use the eight subregions of a region of 256 bytes or more — for example a 64 KB region with the top two subregions disabled protects exactly 48 KB — or split across regions, but mostly I fix it in the linker script by collecting protected objects into power-of-two, aligned sections. Armv8-M replaced this with base and limit registers at 32-byte granularity, so the problem goes away, but overlapping regions become a fault instead of a priority rule.

**Q.** What happens to the MPU on a context switch in an RTOS?

**A.** 고정 리전은 그대로 두고, 태스크마다 다른 동적 리전(스택, 격리 버퍼, 스택 가드)을 PendSV에서 다음 태스크 것으로 바꾼다. FreeRTOS-MPU는 태스크 생성 때 RBAR/RASR 값을 계산해 TCB에 넣고, 스위치 때 별칭 레지스터에 `stm` 한 번으로 리전 4개를 쓴다 — 리전 몫 15 명령이었다. Zephyr는 스위치 때마다 C 함수로 목록을 만들어 써서 M3에서 스위치 비용이 80에서 202 명령으로 늘었다.

> The static regions — flash, peripherals, NULL guard, DMA buffers — stay put. The per-task ones — the task's stack, its granted buffers, the stack guard — are rewritten in PendSV after the scheduler picks the next task. FreeRTOS-MPU precomputes the RBAR and RASR values at task creation, stores them in the TCB, and on a switch disables the MPU, writes four regions with a single store-multiple into the RBAR/RASR alias registers, and re-enables it — fifteen instructions in the disassembly. Zephyr instead rebuilds the region list in C on every switch; in my QEMU measurement the MPU stack guard took Zephyr's switch from about 80 to about 200 instructions on a Cortex-M3, while on a Cortex-M33 it uses the PSPLIM stack-limit register and the extra cost disappears.

**꼬리 질문**: "Why disable the MPU while reprogramming?" → 4개 중 일부만 바뀐 순간의 접근을 피하려고. PendSV는 특권이고 PRIVDEFENA 배경이 있어 MPU가 꺼진 동안에도 문제없다. ISB가 없는 이유는 곧 예외 복귀가 동기화하기 때문이다.

**Q.** You get a MemManage fault with MSTKERR set and MMARVALID clear. What happened?

**A.** 예외 진입 때 하드웨어가 프레임을 쌓다가 금지 영역(대개 스택 가드)에 닿은 것이다. 프레임이 없어서 쌓인 PC를 믿을 수 없고 MMFAR도 무효다. 범인은 그 순간의 스택 주인 — RTOS라면 현재 태스크, ISR 중첩이면 MSP — 이고 거의 항상 스택 오버플로다. 핸들러는 프레임을 읽지 말고 PSP와 현재 태스크로 보고해야 한다.

> The hardware faulted while stacking the exception frame — the stack pointer was close enough to a protected area, almost always the stack guard, that the eight-word push crossed into it. There's no valid frame, so the stacked PC is garbage and MMFAR isn't valid either. The culprit is whoever owned that stack: the current task for PSP, or the interrupt stack for MSP. It's a stack overflow that happened to surface on an interrupt. The handler must not dereference the frame — I check CFSR first, then report PSP and the current task name, and size the guard so a whole exception frame, 104 bytes with FPU state, lands inside it.

**Q.** How do you make a DMA buffer safe on a Cortex-M7 with the data cache enabled?

**A.** 세 가지가 있는데 MPU 쪽은 DMA 버퍼를 한 섹션에 모아 Normal non-cacheable(TEX = 001, C = B = 0) 리전 하나로 덮는 것이다. Device로 잡지 않는 이유는 비정렬 `memcpy`가 fault가 나기 때문이다. 속성을 바꾸기 전에 그 범위를 clean+invalidate하고, 캐시를 켜기 전에 MPU부터 설정한다. 큰 버퍼는 캐시 유지 연산 쪽이 성능상 나을 수 있다(B8).

> Either keep it cacheable and do explicit clean before TX and invalidate after RX with 32-byte aligned buffers, or put all DMA buffers in one linker section and cover it with a single MPU region marked Normal non-cacheable — TEX 001, C and B zero on Armv7-M, or MAIR attribute 0x44 on Armv8-M. Not Device memory, because memcpy does unaligned accesses that fault on Device. I configure the MPU before enabling the cache, and if I change attributes at runtime I clean and invalidate the range first and follow with DSB and ISB. One M7 gotcha: shareable Normal memory isn't cached at all by default, so an accidental S bit silently disables caching.

**Q.** What changed in the Armv8-M MPU compared to Armv7-M?

**A.** base/limit 32 B 단위로 크기·정렬 제약이 사라졌고 subregion도 없어졌다. 대신 겹치면 우선순위가 아니라 fault다. 속성은 MAIR에 8개 등록하고 리전이 인덱스로 고른다. AP는 2비트로 줄어 "특권 RW·비특권 RO"가 없다. TrustZone이 있으면 Secure·Non-secure MPU가 따로 있고, v8.1-M은 PXN이 추가됐다. 스택 가드는 PSPLIM이 맡는다.

> Regions are now a base and a limit at 32-byte granularity, so no power-of-two or alignment constraints and no subregions. The trade-off is that overlapping regions are an error — an access to an overlapped address faults even if both regions allow it — so where Armv7-M stacked a small region on a big one, you now split the big one. Attributes moved into the MAIR registers, eight entries, and each region just picks an index. Access permissions shrank to two bits. With TrustZone there are separate Secure and Non-secure MPUs, and Armv8.1-M adds privileged-execute-never. And stack overflow detection moved to the PSPLIM and MSPLIM registers, so you no longer burn a dynamic MPU region on a stack guard.

## 15. 요약 & 체크리스트

MPU는 주소를 바꾸지 않고 리전 8~16개로 권한과 메모리 속성만 거는 장치다. Armv7-M(PMSAv7)은 RBAR/RASR로 2^n 크기·크기 정렬 리전을 쓰고, 256 B 이상 리전은 subregion 8칸으로 다듬으며, 겹치면 번호 큰 리전이 이긴다. 정렬이 틀린 리전은 QEMU에서 통째로 무시되었다. Armv8-M(PMSAv8)은 RBAR/RLAR로 32 B 단위 아무 범위를 쓰는 대신 겹침이 fault이고, 속성은 MAIR 인덱스로, TrustZone이 있으면 Secure·Non-secure MPU가 따로, v8.1-M은 PXN이 있다. 위반은 MemManage(CFSR의 IACCVIOL·DACCVIOL·MSTKERR, MMFAR)로 오고, MEMFAULTENA가 꺼져 있거나 더 높은 우선순위 문맥이면 HardFault로 승격되며, NMI 안의 위반은 lockup이다. 대표 용도는 널 가드(NULL 읽기가 원래는 조용히 초기 SP를 돌려준다), W^X(SRAM은 기본 맵에서 실행 가능하므로 XN이 핵심), 스택 가드(실제 오버플로는 대개 스태킹 중 MSTKERR로 드러난다), non-cacheable DMA 리전(QEMU에서는 효과를 볼 수 없다)이다. 태스크마다 다른 리전은 PendSV에서 바꾸는데, FreeRTOS-MPU는 생성 때 계산한 값을 별칭 레지스터로 `stm` 한 번에 써서 리전 몫이 15 명령(스위치 100 → 126), Zephyr는 스위치마다 C로 계산해서 MPU 스택 가드만으로 80 → 202 명령이 되었고, v8-M에서는 PSPLIM 덕분에 그 비용이 사라졌다(64). v7-M 리전 계획은 "고정 몇 개 + 태스크당 몇 개" 예산을 먼저 정하고, 보호할 객체를 2^n 섹션에 모으는 것이 핵심이다.

- [ ] MPU와 MMU의 차이를 번역·리전 수·결정성으로 설명할 수 있다
- [ ] `MPU_TYPE`으로 리전 수를 읽고, 코어 이름이 아니라 칩 구현이 정한다는 것을 안다
- [ ] RASR 값 하나를 XN·AP·TEX/S/C/B·SRD·SIZE로 손으로 해독할 수 있다
- [ ] v7-M 리전의 크기·정렬 규칙과 SRD로 48 KB를 만드는 법을 안다
- [ ] 겹침 규칙(v7-M 번호 큰 쪽 우선, v8-M fault, PMP 번호 작은 쪽 우선)을 구분한다
- [ ] PRIVDEFENA·HFNMIENA·MEMFAULTENA가 각각 무엇을 바꾸는지 실험 결과로 말할 수 있다
- [ ] MemManage에서 IACCVIOL·DACCVIOL·MSTKERR별로 범인 주소를 찾는 법을 안다
- [ ] 널 가드, W^X, 스택 가드, non-cacheable DMA 리전을 직접 설정할 수 있다
- [ ] MPU 설정 뒤 DSB/ISB가 필요한 곳과 PendSV에서는 왜 ISB가 없어도 되는지 안다
- [ ] Armv8-M의 RBAR/RLAR·MAIR·RNR 기준 별칭·PXN을 쓸 수 있다
- [ ] FreeRTOS-MPU와 Zephyr의 리전 교체 방식 차이와 측정 비용을 말할 수 있다
- [ ] STM32H7급 칩의 16리전 계획표를 만들 수 있다
