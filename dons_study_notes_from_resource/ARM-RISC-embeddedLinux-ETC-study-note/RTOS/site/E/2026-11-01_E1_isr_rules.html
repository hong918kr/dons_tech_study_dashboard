0. 큰 그림 — 이게 왜 필요한가#

bare-metal 펌웨어에서 ISR 규칙은 단순했다. "짧게 쓰고, 공유 변수는 volatile로, 메인 루프가 플래그를 보게 하라." Don이 SSD 컨트롤러에서 NVMe doorbell ISR이 커맨드 큐 인덱스만 갱신하고 실제 처리를 executive 루프에 넘긴 것이 정확히 그 모양이다.

RTOS를 올리면 ISR과 메인 루프 사이에 스케줄러라는 제3자가 끼어든다. 이제 ISR은 플래그만 세우는 게 아니라 "자고 있는 태스크를 깨워 달라"고 커널에 부탁해야 한다. 그런데 커널은 자기 자료구조(ready 리스트, 이벤트 리스트, 큐)를 태스크 문맥에서 쓰려고 만들었다. ISR이 그 자료구조를 건드리려면 세 가지가 달라야 한다.

  • 기다릴 수 없다. ISR은 태스크가 아니라서 블록할 "자기 자신"이 없다. 블로킹 API를 부르면 커널은 "지금 돌던 태스크"(= ISR에게 끊긴 태스크)를 재운다. 엉뚱한 태스크가 잔다(§4.3에서 실측).
  • 잠금 방식이 다르다. 태스크용 크리티컬 섹션은 중첩 카운터 하나로 BASEPRI를 0까지 내린다. ISR은 들어올 때의 BASEPRI를 저장했다가 그대로 돌려놓아야 한다(C7 §3).
  • 그 자리에서 컨텍스트 스위치를 할 수 없다. 스위치는 모든 ISR이 끝난 뒤 PendSV가 한다. 그래서 ISR은 "높은 태스크를 깨웠으니 나가면 바꿔 달라"는 요청만 남긴다. 그게 pxHigherPriorityTaskWoken + portYIELD_FROM_ISR이다.

그리고 이 계약은 어느 우선순위의 ISR이 지키는가에 따라 갈린다. 아래 그림이 이 노트 전체의 지도다.

그림 1 — Cortex-M + RTOS에서 코드가 도는 네 층. 문턱(configMAX_SYSCALL_INTERRUPT_PRIORITY, lab 템플릿은 0x20)보다 급한 ISR은 커널이 BASEPRI로 막을 수 없으므로 커널 API를 아예 못 부른다(배치는 E2). 문턱 아래 ISR은 커널 API를 부를 수 있지만 ISR용 변형만, 기다리지 않고, 짧게. 나머지 일은 태스크로 넘긴다(D7, E4).

Linux와 비교하면: Linux에서도 hard IRQ 핸들러는 sleep 금지이고 spin_lock_irqsave, wake_up 같은 "원자 문맥에서 되는" 함수만 쓴다(EL F6, EL F2 §실행 문맥). 차이는 Linux에는 might_sleep() 경고와 lockdep이 런타임에 실수를 잡아 주고, threaded IRQ로 핸들러를 스레드로 바꿀 수 있다는 점이다. MCU RTOS에는 그런 안전망이 configASSERT / CONFIG_ASSERT 하나뿐이고, 그것도 개발 빌드에서만 켜진다. 그래서 규칙을 사람이 외워야 한다.

실습 환경 한 줄#

QEMU mps2-an385(Cortex-M3 @ 25 MHz) 위의 FreeRTOS V11.3.2(lab 템플릿, 1 kHz tick, configMAX_SYSCALL_INTERRUPT_PRIORITY = 0x20)와 Zephyr v4.4.2(같은 보드, 100 Hz tick, tickless). 타이밍은 FreeRTOS는 ICOUNT=1, Zephyr는 -icount shift=5(명령 1개 = 32 ns)로 재고, 시계는 FPGAIO 25 MHz 카운터(0x40028018)다. QEMU icount 기준이라 실제 칩과 절대값은 다르다(캐시, 플래시 wait state, 예외 스태킹 사이클, UART baud 지연이 모델링되지 않는다). 예제 소스는 ~/.rtos_scratch/E1/, 빌드 산출물은 VM의 /var/tmp/rtos/E1/. 공용 헤더 e1.h는 D1의 d1.h와 같은 도우미(TIMER0 시작·정지, 경과 사이클, stat_t)에 IPSR·BASEPRI 읽기와 STIR(소프트웨어 IRQ 트리거)를 더한 것이다.

1. 규칙 한 장 — 먼저 결론#

이 노트에서 하나씩 실험으로 확인할 규칙을 먼저 나열한다. 각 줄 끝의 절 번호가 근거다.

  1. 문턱 아래 우선순위의 ISR만 커널 API를 부른다. 우선순위를 안 정한 IRQ는 리셋값 0 = 가장 급함 = 금지 영역이다 (§5, B3).
  2. ISR에서는 이름이 FromISR로 끝나는 API만 부른다 (FreeRTOS). Zephyr는 같은 이름이지만 timeout은 K_NO_WAIT만 (§2, §6).
  3. BaseType_t woken = pdFALSE;로 시작해서, 모든 FromISR 호출에 같은 &woken을 넘기고, ISR 맨 끝에서 portYIELD_FROM_ISR(woken) 한 번 (§3).
  4. 기다리는 것은 전부 금지: 블로킹 take/receive, vTaskDelay/k_sleep, 뮤텍스, 이벤트 그룹 대기 (§4).
  5. 뮤텍스는 ISR에서 절대 쓰지 않는다 — 소유자가 태스크여야 우선순위 상속이 성립한다 (§4.5).
  6. printf, 동적 할당, 상한 없는 루프, (FPU 코어가 아니면) 부동소수점은 ISR 밖으로 (§4.4, §4.6).
  7. 개발 빌드는 configASSERT / CONFIG_ASSERT=y로 — 위 실수 대부분을 첫 실행에서 잡아 준다. 끄면 같은 실수가 "가끔 나는 이상한 버그"로 바뀐다 (§4.3, §5).

2. FreeRTOS의 ...FromISR API 가족#

2.1 왜 이름이 다른 함수를 따로 두나#

직관: 태스크용 xQueueSend()와 ISR용 xQueueSendFromISR()는 같은 큐에 같은 데이터를 넣는다. 그런데 태스크용은 "자리가 없으면 기다린다"는 경로를 품고 있고, ISR용은 그 경로가 아예 없다. 비유하면 태스크용은 "줄이 길면 줄 서서 기다리는 손님", ISR용은 "줄이 길면 그냥 돌아가는 배달원"이다. 배달원은 다음 집이 기다리고 있으니 줄을 설 수 없다.

정의: FreeRTOS V11.3.2 queue.c의 xQueueGenericSendFromISR() 주석이 이유를 그대로 적어 두었다.

그리고 port.c의 vPortValidateInterruptPriority() 주석에는 "FreeRTOS maintains separate thread and ISR API functions to ensure interrupt entry is as fast and simple as possible."라고 되어 있다. 정리하면 FromISR 변형은 태스크용과 네 가지가 다르다.

2.2 예제 1 — V11.3.2 헤더에 있는 FromISR API 전부 세기#

무엇을 확인하는 코드인지: 공개 헤더에서 이름이 FromISR로 끝나는 식별자를 헤더별로 센다. "무엇이 있고 무엇이 없나"를 외우지 말고 소스에서 뽑는다.

출력에서 볼 것: 고유 이름 56개(헤더 사이 중복 포함 집계는 더 많다 — semphr.h는 queue.h 함수를 매크로로 감싼다). 이 중 vTaskEnterCriticalFromISR/vTaskExitCriticalFromISR는 SMP 빌드(configNUMBER_OF_CORES > 1)용이고, xQueueCR...는 코루틴용이라 실무에서 볼 일이 거의 없다. 헤더 전체 목록에서 실무 쓰임새로 다시 묶으면 아래와 같다.

FromISR 짝이 없는 것 — 즉 ISR에서는 대안이 없는 것:

  • vTaskDelay, xTaskDelayUntil — ISR은 잘 수 없다.
  • 뮤텍스 take (xSemaphoreTake(mutex, …)) — §4.5. (xSemaphoreTakeFromISR은 존재하지만 뮤텍스에는 쓰면 안 된다.)
  • xEventGroupWaitBits, xEventGroupSync — 기다리는 API.
  • xTaskCreate, vTaskDelete, vTaskSuspend, vTaskPrioritySet — 리스트 대수술이라 태스크 문맥 전용.
  • pvPortMalloc, vPortFree — 스케줄러 잠금을 쓴다(§4.2 예제 6의 MODE=5).

xTaskResumeFromISR은 문서에서도 "ISR → 태스크 동기화에 쓰지 말라"고 한다. 태스크가 아직 suspend되기 전에 resume이 오면 사건을 잃기 때문이다. 깨우기는 task notification이나 세마포어로 한다.

2.3 예제 2 — 두 변형의 비용, FromISR을 태스크에서 부르면, 그리고 양쪽에서 쓸 수 있는 도우미#

무엇을 확인하는 코드인지: ① 같은 세마포어에 태스크용 give/take와 FromISR give/take를 1000번씩 해서 한 번 비용을 잰다. ② FromISR을 태스크에서 부르면 어떻게 되나. ③ xPortIsInsideInterrupt()로 문맥을 보고 알맞은 API를 고르는 도우미 sig_give()를 ISR과 태스크 양쪽에서 부른다. ISR은 TIMER0 줄(IRQ 8, 우선순위 0x40)을 STIR로 소프트웨어 트리거한다.

출력에서 볼 것:

  • FromISR give가 태스크용 give보다 싸다: ISR 안에서 1.54 µs, 태스크용 2.50 µs(QEMU icount 기준). 태스크용은 xQueueGenericSend()의 for(;;) 루프 · 타임아웃 구조체 · 중첩 카운터를 거치고, FromISR은 저장/복원 BASEPRI 한 쌍과 리스트 조작뿐이다. "ISR 진입을 가능한 한 빠르고 단순하게"라는 소스 주석의 숫자 버전이다.
  • FromISR을 태스크에서 부르면 assert가 안 터진다(1.28 µs). vPortValidateInterruptPriority()는 IPSR이 16 이상(= 외부 IRQ)일 때만 우선순위를 검사하고, IPSR = 0(thread mode)이면 그냥 지나간다. 태스크 문맥에서는 BASEPRI 저장/복원도 올바르게 동작하므로 이 포트에서는 실제로 문제가 없다. 그래서 ISR 안(1.54 µs)보다 오히려 빠르다 — 검사 함수 본문을 건너뛰기 때문이다. 다만 FreeRTOS 문서는 FromISR을 태스크에서 쓰는 것을 보장하지 않고, 깨운 태스크로의 전환을 woken으로 직접 처리해야 하므로 습관으로 삼지 않는다.
  • xPortIsInsideInterrupt()는 IPSR이 0이 아닌지만 본다(portmacro.h 190행). sig_give()처럼 드라이버 공용 함수가 양쪽 문맥에서 불릴 때 쓰는 표준 방법이다. Zephyr의 k_is_in_isr()도 같은 일을 한다(§6).

Don 경험과 연결: SSD 펌웨어에서 "ISR에서도 불리고 executive 루프에서도 불리는 로그 함수"를 만들 때, 인터럽트를 끌지 말지를 호출자 문맥에 따라 바꿨던 것과 같은 문제다. RTOS에서는 그 분기가 "어느 API를 부르나"로 바뀐다.

함정: xPortIsInsideInterrupt()는 PendSV · SysTick · SVC 안에서도 참이다(IPSR 11, 14, 15). 그리고 문턱 위(zero-latency) ISR에서도 참이므로, "ISR이면 FromISR을 부른다"는 분기만으로는 §5의 우선순위 규칙까지 지켜 주지 않는다.

2.4 예제 3 — 코드 크기와 생성 코드: FromISR에는 무엇이 빠져 있나#

무엇을 확인하는 코드인지: 태스크용과 FromISR 짝을 한 이미지에 모두 링크해(keep[] 표로 참조) nm -S로 크기를 비교하고, xQueueGiveFromISR의 크리티컬 섹션이 어떤 명령으로 컴파일됐는지 본다.

출력에서 볼 것:

  • 큐 계열 FromISR은 태스크용의 절반 남짓(404 → 232, 396 → 188, 352 → 208 B). 빠진 것이 블로킹 경로(이벤트 리스트 등록, 타임아웃 검사, 스케줄러 잠금, 재시도 루프)다.
  • xQueueGiveFromISR 입구: bl vPortValidateInterruptPriority → mrs r6, BASEPRI(이전 값을 r6에 저장) → msr BASEPRI, #32(0x20) → isb · dsb. 함수 뒤쪽 두 곳에서 msr BASEPRI, r6으로 복원한다(같은 objdump를 grep -i basepri하면 1b62, 1b6a에서 보인다). 태스크용 vPortEnterCritical과 달리 0으로 내리는 명령이 없다.
  • 예외 둘. xTaskGenericNotifyFromISR은 오히려 더 크다(292 → 360 B). 스케줄러가 잠겨 있을 때 깨운 태스크를 xPendingReadyList에 넣는 경로와 xYieldPendings를 세우는 경로를 함수 안에 직접 가지고 있기 때문이다. 크기가 아니라 "블록하지 않는다"가 FromISR의 정의다.
  • xEventGroupSetBitsFromISR은 28바이트 — 비트를 세우지 않는다. xTimerPendFunctionCallFromISR()로 "타이머 daemon 태스크가 나중에 vEventGroupSetBitsCallback을 실행하라"는 명령을 보낼 뿐이다(0x24ad가 그 콜백 주소). 이벤트 그룹은 비트를 세울 때 기다리는 태스크를 몇 개든 깨울 수 있어서, 그 상한 없는 작업을 ISR에서 하지 않으려고 daemon에 미룬다. 그래서 이 API는 타이머 명령 큐가 차면 실패하고(pdFAIL), 실제 비트 설정은 daemon 우선순위(템플릿은 configMAX_PRIORITIES - 1 = 7)에서 일어난다. 위임 경로의 자세한 동작은 D7 §3.

3. pxHigherPriorityTaskWoken과 portYIELD_FROM_ISR — "스위치는 나가면서"#

D1 §4는 세마포어 하나로 이 규약을 소개하고, yield를 빼먹었을 때 지연이 0~1 ms에 고르게 퍼지는 히스토그램(n = 200, 1 kHz tick)을 이미 측정했다. 이 절은 그 결과를 반복하지 않고 다른 각도에서 본다: NULL을 넘기는 경우, tick 주파수를 바꾸는 경우, 한 ISR 안에서 여러 API를 부를 때 생기는 플래그 버그.

3.1 직관과 순서#

ISR 안에서는 컨텍스트 스위치를 할 수 없다. 스위치는 "지금 돌던 태스크의 레지스터를 그 태스크 스택에 저장하고 다른 태스크 스택에서 꺼내는" 일인데, ISR이 돌고 있는 동안 CPU는 handler mode에 있고 태스크 스택(PSP) 위에는 하드웨어가 쌓은 예외 프레임이 있다. 그래서 Cortex-M RTOS는 스위치를 가장 낮은 우선순위의 PendSV 예외에 맡긴다(B4, C2). ISR은 PendSV를 pending으로 만들어 두기만 하고, 모든 ISR이 끝나면 하드웨어가 tail-chaining으로 PendSV에 들어간다.

그림 2 — FreeRTOS ISR이 높은 우선순위 태스크를 깨우는 순서. ③의 portYIELD_FROM_ISR은 그 자리에서 스위치하지 않고 ICSR의 PENDSVSET 비트만 쓴다. 그래서 ④처럼 yield 뒤의 ISR 코드도 끝까지 돈다. 스위치는 ⑤ PendSV에서, ISR이 끝난 직후에 일어난다.

V11.3.2 portable/GCC/ARM_CM3/portmacro.h 98~111행이 정의다.

portYIELD()는 portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT; 뒤에 dsb · isb다. 두 이름(portYIELD_FROM_ISR, portEND_SWITCHING_ISR)은 이 포트에서 완전히 같다. 오래된 포트 중에는 한쪽 이름만 정의한 것이 있어서 둘 다 남아 있다. 새 코드는 portYIELD_FROM_ISR을 쓴다.

규약을 정리하면 네 줄이다.

  1. BaseType_t woken = pdFALSE; — 반드시 pdFALSE로 초기화. FromISR API는 깨운 태스크가 지금 돌던 태스크보다 높을 때 pdTRUE로 올리기만 하고 내리지 않는다.
  2. ISR 안의 모든 FromISR 호출에 같은 &woken을 넘긴다. 하나라도 높은 태스크를 깨웠으면 pdTRUE로 남는다.
  3. ISR 맨 끝에서 portYIELD_FROM_ISR(woken); 한 번. 중간에 불러도 동작은 같지만(PENDSVSET은 ISR이 끝나야 효과가 있다), 읽는 사람이 "여기서 전환된다"고 오해하고 그 뒤에 코드를 덧붙이기 쉽다.
  4. woken은 반환값이 아니다. FromISR API의 반환값은 성공/실패(pdPASS, errQUEUE_FULL)다.

"woken이 참"의 정확한 뜻은 "깨운 태스크의 우선순위 > pxCurrentTCB의 우선순위"다(tasks.c xTaskRemoveFromEventList(), 5500행). 같은 우선순위면 거짓이다 — 같은 우선순위 태스크끼리는 tick의 time slicing이 순서를 정한다.

3.2 빼먹어도 "언젠가는" 전환되는 이유 — xYieldPendings#

D1 §4.2에서 소스로 본 안전망을 짧게 다시 짚는다. xTaskRemoveFromEventList()는 깨운 태스크가 더 높으면 xReturn = pdTRUE와 함께 xYieldPendings[ 0 ] = pdTRUE도 세운다(주석: "in case the user is not using the xHigherPriorityTaskWoken parameter"). 그리고 xTaskIncrementTick()(4831행에서 시작) 끝부분, 5020행에서

로 바꿔 SysTick 핸들러가 PendSV를 걸게 한다(port.c 501~507행, configUSE_PREEMPTION == 1일 때). 그러니 yield를 빼먹은 대가는 "다음 tick까지", 또는 그 전에 다른 이유(다른 ISR의 yield, 태스크의 블로킹 호출)로 스위치가 일어나면 그때까지다.

그렇다면 예측: 최악 지연 ≈ tick 주기 1개, 평균 ≈ tick 주기의 절반. tick 주파수를 바꿔서 확인한다.

3.3 예제 4 — NULL을 넘기면: tick 주파수 1000 · 250 · 100 Hz#

무엇을 확인하는 코드인지: xSemaphoreGiveFromISR(sem, NULL)은 API가 허용하는 호출이다. V11.3.2 queue.c(7곳)와 tasks.c(4곳)는 if( pxHigherPriorityTaskWoken != NULL )을 확인한 뒤에만 플래그를 쓴다. NULL을 넘기면 woken을 받을 길이 없으니 yield도 할 수 없다. TIMER0을 tick 주기의 1.37배로 돌려 IRQ 위상이 tick에 대해 고르게 흩어지게 하고, prio 1 busy 태스크가 CPU를 쥔 상태에서 prio 3 waiter가 깨어나는 지연을 100번 잰다. 같은 소스를 configTICK_RATE_HZ만 바꿔 세 번 빌드한다.

출력에서 볼 것:

  • woken + yield는 tick과 무관하게 9.16 µs. 스케줄러의 반응이 tick이 아니라 PendSV로 결정되기 때문이다(1 kHz 한 번만 10.64 µs — IRQ가 SysTick과 겹친 경우).
  • NULL은 평균 ≈ tick/2, 최대 ≈ 1 tick: 1 kHz에서 0.50/1.00 ms, 250 Hz에서 2.01/3.99 ms, 100 Hz에서 5.00/9.95 ms. 정확히 §3.2의 예측이다. 지연이 tick에 비례하므로 "tick을 느리게(100 Hz) 해서 전력을 아끼는" 설계에서는 이 실수가 10 ms 버그가 된다.
  • D1 예제 6은 woken을 받고 yield만 빼먹은 경우였다. NULL을 넘긴 경우도 결과가 같다 — 둘 다 "아무도 PENDSVSET을 쓰지 않는다"는 같은 상태이기 때문이다.

그림 3 — 실측: NULL을 넘겼을 때 ISR → 태스크 지연(로그 축). 초록은 woken + yield(모든 tick 주파수에서 9.16 µs), 주황은 NULL 평균, 빨강은 NULL 최대. 평균은 tick 주기의 절반, 최대는 tick 주기 1개에 붙는다.

그럼 NULL은 언제 넘겨도 되나? 깨울 태스크가 ISR이 끊은 태스크보다 절대 높을 수 없다는 것이 설계상 확실할 때(예: 깨우는 대상이 가장 낮은 우선순위 로깅 태스크)뿐이다. 그때도 같은 woken을 받아 yield를 부르는 비용은 거의 0이므로(거짓이면 분기 하나), 규칙은 "항상 받고 항상 yield"가 낫다.

3.4 예제 5 — 한 ISR에 FromISR이 둘 이상일 때의 플래그 버그#

무엇을 확인하는 코드인지: UART 같은 주변장치 ISR은 흔히 "RX 완료"와 "TX 비었음"을 한 번에 처리하며 FromISR을 두 번 부른다. rx 세마포어에는 prio 3 hi 태스크가 기다리고, tx 세마포어에는 아무도 기다리지 않는다. 네 가지 ISR을 비교한다.

  • A (정답): 한 플래그를 두 호출에 공유하고 마지막에 yield 한 번.
  • B (버그): 호출마다 다른 플래그 w1, w2를 쓰고 마지막 것만 yield에 넘긴다. hi를 깨운 w1이 버려진다.
  • C (버그): API의 반환값(pdPASS)을 woken인 줄 알고 yield에 넘긴다. 아무도 안 깨웠는데 매번 PendSV가 걸린다.
  • D (정답): C와 같은 ISR에서 woken을 제대로 넘긴다.

PendSV가 실제로 몇 번 스위치 판단을 했는지 세려고, 앱 폴더(trace/)에 템플릿 설정을 include하고 trace 매크로 하나만 더한 FreeRTOSConfig.h를 두었다.

traceTASK_SWITCHED_IN()은 vTaskSwitchContext()가 다음 태스크를 고를 때마다 불린다. PendSV 핸들러는 매번 vTaskSwitchContext()를 부르므로(같은 태스크로 "전환"하더라도) PendSV 실행 횟수를 세는 셈이다. busy 태스크는 2 µs(50 사이클) 넘게 CPU를 못 받은 구간을 모두 더해 "빼앗긴 시간"을 잰다.

출력에서 볼 것:

  • A: 10.96 µs로 일정. 스위치 200번 = 깨어날 때 1번 + hi가 다시 블록할 때 1번 × 100.
  • B: 평균 540 µs, 최대 1.0 ms — §3.3의 NULL과 똑같은 "다음 tick까지" 분포다. 두 번째 호출의 w2는 정직하게 pdFALSE(tx에는 대기자가 없다)라서 yield가 안 걸렸다. 코드 리뷰에서 "각 호출의 결과를 따로 받는 게 더 명확하다"며 이렇게 고치는 일이 실제로 있다. 고치려면 portYIELD_FROM_ISR(w1 | w2)로 합치거나 처음부터 하나를 공유한다.
  • C: 100 ms 동안 PendSV가 97번 돌았다(D는 2번 — hi가 잠들 때와 깨어날 때). 아무도 깨우지 않은 IRQ마다 쓸데없는 PendSV가 돌아 busy가 빼앗긴 시간이 452 → 774 µs로 늘었다. 차이 322 µs ÷ 95번 ≈ 헛 PendSV 한 번에 3.4 µs(예제 12에서 계산). 기능은 멀쩡하고 CPU만 조금 더 쓰는 버그라 찾기 어렵다. woken을 초기화하지 않은 경우(스택 쓰레기 값이 0이 아닐 때)도 같은 증상이다.
  • C와 D의 stall 횟수가 97로 같다는 것은 IRQ 수가 같다는 뜻이다. 차이는 IRQ당 길이(평균 7.98 대 4.67 µs)뿐이다.

3.5 Don 경험과 연결, 그리고 함정#

SSD 펌웨어의 "ISR이 이벤트 비트를 세우고, executive 루프가 다음 바퀴에 본다"는 구조에서 executive 루프의 한 바퀴 주기가 곧 최악 반응 시간이었다. FreeRTOS에서 yield를 빼먹으면 tick 주기가 그 바퀴 주기 역할을 한다. 우선순위 선점이라는 RTOS의 핵심 장점을 한 줄 누락으로 잃는 셈이다.

함정 세 가지:

  • "테스트는 다 통과했다": 값은 맞고 지연만 늘어난다. 지연 히스토그램(E3)을 재지 않으면 안 보인다.
  • "다음 tick"이 멀수록 나빠진다: 예제 4처럼 지연은 tick 주기에 비례한다. 안전망이 tick이 아니라 "다음에 우연히 일어나는 스위치 지점"인 커널에서는 더 길어질 수 있다 — Zephyr의 direct ISR에서 같은 종류의 실수가 tickless 때문에 최대 660 ms(이론 상한 671 ms)까지 늘어나는 것을 §6.5에서 본다.
  • SMP FreeRTOS에서는 portYIELD_FROM_ISR이 "이 코어"만 스위치한다. 다른 코어의 태스크를 깨운 경우는 커널이 코어 간 인터럽트로 처리한다(C10).

4.2 예제 6 — assert를 켜고 여덟 가지 실수를 한 번씩#

무엇을 확인하는 코드인지: TIMER0 ISR(우선순위 0x40, MODE 8만 0x10)이 한 번 뜨면서 MODE에 따라 한 가지 실수를 한다. lab 템플릿의 configASSERT는 파일:줄을 찍고 종료코드 253으로 끝난다. assert가 안 터지면 태스크가 살아서 상태를 찍는다.

B3 예제 11(문턱 위 ISR의 FromISR, 우선순위 미설정, PRIGROUP)과 C7 예제 5(ISR에서 taskENTER_CRITICAL)가 이미 assert 두 개를 보여 줬다. 이 예제는 "블로킹 · 지연 · 할당 · 뮤텍스"까지 넓혀서 어느 assert가 무엇을 잡는지 지도를 만든다.

출력에서 볼 것:

  • MODE 1~5가 전부 같은 줄 port.c:438에서 잡힌다. vPortEnterCritical()의 configASSERT( ( portNVIC_INT_CTRL_REG & portVECTACTIVE_MASK ) == 0 ) 하나다. 태스크용 give, timeout 0인 send, 블로킹 take, vTaskDelay, pvPortMalloc — 다섯 가지 실수가 결국 모두 taskENTER_CRITICAL()을 지나기 때문이다. vTaskDelay와 pvPortMalloc은 vTaskSuspendAll()로 스케줄러를 잠근 뒤 xTaskResumeAll() 안에서 taskENTER_CRITICAL()을 부르다 걸린다. 즉 "FromISR이 아닌 커널 함수는 거의 전부 VECTACTIVE 검사 하나에 걸린다". 이 assert가 FreeRTOS ISR 규칙의 문지기다.
  • 이 assert는 uxCriticalNesting == 1일 때만 검사한다(재귀 assert 방지). 그리고 메시지가 파일:줄뿐이라 누가 불렀는지는 안 알려 준다. 실무에서는 configASSERT를 __builtin_return_address(0)이나 LR까지 기록하도록 정의하거나, 디버거에서 콜 스택을 본다(M1).
  • MODE 6 — 태스크가 쥔 뮤텍스를 ISR이 give: queue.c:1360의 configASSERT( ... !( ( pxQueue->uxQueueType == queueQUEUE_IS_MUTEX ) && ( pxQueue->u.xSemaphore.xMutexHolder != NULL ) ) ). 소스 주석: "priority inheritance makes no sense for an interrupt, only tasks."
  • MODE 7이 가장 무섭다 — assert가 없다. 비어 있는 뮤텍스를 ISR이 xSemaphoreTakeFromISR로 가져가면 성공한다. 그런데 소유자 기록(xMutexHolder)은 태스크용 take 경로(xQueueSemaphoreTake)에서만 채워지므로 소유자 NULL인 잠긴 뮤텍스가 된다. 이후 태스크의 take는 timeout까지 기다리다 실패하고, 이 뮤텍스를 돌려줄 "소유자"가 세상에 없다. 우선순위 상속도 상속해 줄 대상이 없다. 증상은 "가끔 영원히 멈추는 태스크"다.
  • MODE 8 — 우선순위 0x10(문턱 0x20보다 급함) ISR의 FromISR: port.c:803. §5에서 이 검사를 자세히 본다.

4.3 예제 7 — assert를 끄면 같은 실수가 무엇이 되나#

assert가 있으면 첫 실행에서 멈춘다. 양산 빌드처럼 configASSERT를 끄면 같은 실수가 무엇으로 바뀌는지가 현장 디버깅에서 중요하다. 그것을 직접 본다.

무엇을 확인하는 코드인지: 앱 폴더(noassert/)에 템플릿 설정을 include하고 configASSERT만 #undef한 FreeRTOSConfig.h를 둔다. prio 1 victim 태스크가 CPU를 쥐고 돌며 "자기가 CPU를 못 받은 가장 긴 구간"을 기록한다. ISR은 victim이 도는 중에 한 번 떠서 MODE에 따라 태스크용 API를 부른다. MODE 3(블로킹 take)은 시스템이 멈출 것으로 예상해, C7 예제 11과 같은 방식의 문턱 위(0x00) 감시 ISR(DUALTIMER, IRQ 10)을 20 ms 뒤에 띄운다. 감시 ISR은 커널을 부르지 않고 MSP 위의 예외 프레임에서 끊긴 문맥의 IPSR과 PC만 읽는다.

(-Wno-unused-... 두 개는 configASSERT가 사라지면서 커널 소스(tasks.c 8564행, port.c 284행)에 생기는 "쓰이지 않는 변수" 경고를 끄려고 붙였다. 예제 코드 자체는 경고 0개다.)

출력에서 볼 것:

  • MODE 1 · 2 (태스크용 give, timeout 0 send): 겉보기에 정상이다. give는 성공했고(count 1), ISR이 끝난 뒤 BASEPRI도 0이다. 단일 코어 Cortex-M3에서 문턱 아래 ISR이 돌 수 있는 순간에는 BASEPRI가 이미 0이고 uxCriticalNesting도 0이므로(태스크가 크리티컬 섹션 안이면 이 ISR은 막혀 있다), "0으로 내린다"가 우연히 맞는 값이 된다. 우연히 동작하는 코드다. 포트가 바뀌거나, 깨운 태스크가 높아서 queueYIELD_IF_USING_PREEMPTION()이 불리거나, 언젠가 이 함수에 블로킹 경로가 생기면 깨진다. 그래서 FreeRTOS는 이것을 assert로 막는다.
  • MODE 3 (블로킹 take, count 0, timeout 10 tick): 20 ms 뒤 감시 ISR이 본 것은 IPSR = 24(= IRQ 8, TIMER0 ISR) 안의 PC 0x1288 = vListInsert()의 list.c:192 — 1 ms에 들어간 ISR이 19 ms 동안 못 나왔다. list.c:192는 FreeRTOS에서 유명한 줄이다. 바로 위 주석이 "If you find your application is crashing here then likely causes are ... 3) Calling an API function from within a critical section or when the scheduler is suspended, or calling an API function that does not end in "FromISR" from an interrupt."이고, 루프 안 주석은 "IF YOU FIND YOUR CODE STUCK HERE, SEE THE NOTE JUST ABOVE."다. 소스를 따라가면 이렇게 해석된다: xQueueSemaphoreTake()는 끊긴 victim을 대기 리스트에 넣고 portYIELD_WITHIN_API()를 부르지만, ISR 안이라 스위치가 일어나지 않고 함수의 for(;;)가 다시 돈다. tick은 이 ISR보다 낮은 SysTick(0xFF)이 세므로 timeout은 영원히 지나지 않는다. 그 상태로 같은 리스트 항목을 다시 넣으면서 리스트가 고리로 꼬여 vListInsert의 정렬 삽입 루프가 끝나지 않는다. 결과: 0x40 이하 모든 IRQ와 모든 태스크가 영원히 멈춘다.
  • MODE 4 (vTaskDelay(5)): ISR은 바로 나왔는데 victim이 5 ms 동안 CPU를 못 받았다(4999 µs). 커널이 pxCurrentTCB(= ISR이 끊은 victim)를 delayed 리스트에 넣었기 때문이다. victim 코드에는 vTaskDelay가 한 줄도 없는데 victim이 잔다. 현장에서 이 증상은 "어떤 태스크가 가끔 이유 없이 몇 ms씩 멈춘다"로 보이고, 멈추는 태스크가 매번 다르다(그때 끊긴 태스크가 다르니까).

그림 4 — assert를 끄고 같은 실수를 했을 때 실제로 일어난 일(예제 7, 예제 10). 주황은 "지금은 동작하지만 보장 없음", 빨강은 실제 고장. 블로킹 계열 실수의 공통점은 엉뚱한 태스크(끊긴 태스크)가 대가를 치른다는 것이다.

Don 경험과 연결: SSD 펌웨어에서 "커맨드 처리 루프가 가끔 수 ms 멈추는데 그 루프 코드에는 아무 문제가 없던" 버그를 떠올리면 된다. 원인이 다른 곳(ISR)에 있고, 피해자가 매번 바뀌는 버그는 가장 찾기 어렵다. 그래서 RTOS에서는 assert를 끈 양산 빌드라도 configASSERT를 "로그 남기고 리셋"으로 정의해 남겨 두는 팀이 많다(코드 크기와 몇 사이클을 대가로).

4.4 예제 8 — "짧게"를 숫자로: 금지된 일 하나가 ISR을 얼마나 늘리나#

무엇을 확인하는 코드인지: 같은 ISR(give 하나)에 금지된 일을 하나씩 더해 ISR 본문 시간을 FPGAIO 카운터로 잰다. 각 모드를 3번 돌려 첫 실행과 최솟값(정상 상태)을 함께 본다. 끝에서 objdump로 ISR이 실제로 부르는 함수를 확인한다.

출력에서 볼 것:

  • give만 하는 ISR 본문은 2.16 µs. 이것이 기준선이다.
  • printf 한 줄(실제로 찍힌 문자열은 줄바꿈 포함 23자 — 소스 주석의 "~24"는 어림이었다)은 12.6 µs = 기준선의 6배. 그런데 이것은 QEMU의 UART가 baud 시간을 모델링하지 않아서 나온 숫자다. 실칩 115200 baud, TX FIFO 1바이트에서 블로킹 putc라면 23자 × 86.8 µs ≈ 2.0 ms(예제 12에서 계산)이고, 그동안 같거나 낮은 우선순위 IRQ와 모든 태스크가 기다린다. 1 kHz rate loop 두 주기다.
  • Cortex-M3에는 FPU가 없어서 x * 1.0001f + 0.5f가 __aeabi_fmul, __addsf3 라이브러리 호출로 컴파일됐다. 16회에 46.9 µs. 드론 FC에서 "ISR에서 자이로 값을 보정까지 해서 넘기자"는 유혹이 이 숫자다. FPU가 있는 M4F/M7에서는 연산 자체는 몇 사이클이지만, ISR이 FPU를 쓰는 순간 예외 프레임이 8워드에서 26워드로 커지고(lazy stacking이 켜져 있으면 실제 저장은 첫 FPU 명령 때) 그 비용이 붙는다. B2 예제 12와 B6 예제 4에서 프레임 크기 변화를 봤다. QEMU는 스태킹 사이클을 모델링하지 않으므로 그 비용은 여기서 재지 못한다.
  • newlib malloc/free는 4.5 µs(첫 호출 6.4 µs — 처음에는 sbrk로 힙을 키운다). 시간보다 재진입이 문제다. newlib은 __malloc_lock/__malloc_unlock 훅으로 보호하는데, 기본 구현은 아무것도 하지 않는다. 태스크가 malloc 안에 있을 때 ISR이 malloc을 부르면 같은 자유 리스트를 동시에 고친다. FreeRTOS pvPortMalloc은 예제 6 MODE=5처럼 assert로 막힌다.
  • 200회 빈 루프(volatile 카운터)는 40.8 µs. "잠깐 기다리는 루프"가 ISR 안에 있으면 이만큼이 그대로 다른 모든 것의 지연이 된다. 하드웨어 레지스터 상태를 폴링하는 루프는 상한조차 없다.

그림 5 — 실측: 금지된 일 하나를 더했을 때 ISR 본문 시간(QEMU icount 기준, 정상 상태). 아래 점선 상자는 실칩 UART에서의 계산값으로, 막대 축의 40배라 막대로 그리지 않았다.

"ISR을 짧게"의 기준은 절대값이 아니라 예산이다. 가장 짧은 마감(예: 20 kHz FOC 전류 루프 = 50 µs 주기)에서 그 ISR보다 낮거나 같은 우선순위의 모든 ISR 최악 길이를 합한 것이 남은 예산을 넘으면 안 된다. 이 계산과 측정 방법은 E3, 배치는 E2에서 한다.

4.5 뮤텍스는 왜 ISR에서 절대 안 되나#

직관: 뮤텍스는 "열쇠"다. 열쇠를 빌려 간 사람(소유자)이 반드시 돌려준다는 약속 위에서 두 가지 기능이 동작한다. ① 소유자만 풀 수 있다. ② 높은 우선순위 태스크가 기다리면 소유자의 우선순위를 잠시 올려 준다(우선순위 상속, D3).

ISR은 둘 다 할 수 없다.

  • ISR은 "소유자"가 될 수 없다. 커널의 소유자 필드는 TaskHandle_t(TCB 포인터)이고, ISR은 TCB가 없다. ISR 안에서 pxCurrentTCB는 끊긴 태스크를 가리킨다.
  • ISR은 우선순위를 상속받을 수 없다. ISR의 우선순위는 NVIC가 정하고 태스크 우선순위와 다른 축이다.
  • ISR은 기다릴 수 없으니, 뮤텍스가 잠겨 있을 때 할 수 있는 일이 없다. 바쁘게 기다리면 뮤텍스를 쥔 태스크가 못 돌아서 영원히 풀리지 않는다(단일 코어 교착).

예제 6에서 본 대로 FreeRTOS는 "소유자가 있는 뮤텍스를 ISR이 give"만 assert로 잡고(queue.c:1360), "ISR이 take"는 막지 않는다(MODE 7: 소유자 없는 잠긴 뮤텍스). Zephyr는 k_mutex_lock()과 k_mutex_unlock() 입구에서 __ASSERT(!arch_is_in_isr(), "mutexes cannot be used inside ISRs")로 둘 다 막는다(kernel/mutex.c 115, 234행, 예제 9).

ISR과 태스크가 같은 자원을 써야 하면 대안은 셋이다.

  1. 짧은 크리티컬 섹션: 태스크 쪽은 taskENTER_CRITICAL(), ISR 쪽은 taskENTER_CRITICAL_FROM_ISR(). 수 µs 이하일 때 (C7).
  2. 소유권을 태스크 하나에: ISR은 큐/스트림 버퍼로 요청만 넣고, 게이트키퍼 태스크가 자원을 독점한다 (D7 §5).
  3. lock-free 구조: SPSC 링버퍼처럼 한쪽만 쓰고 한쪽만 읽는 구조 (D8).

5. 문지기 — configASSERT, vPortValidateInterruptPriority, xPortIsInsideInterrupt#

5.1 vPortValidateInterruptPriority()가 하는 일#

큐의 핵심 FromISR 4개(xQueueGenericSendFromISR, xQueueGiveFromISR, xQueueReceiveFromISR, xQueuePeekFromISR)와 tasks.c의 FromISR 6개(notify, resume, tick count, 우선순위 조회 — 목록은 B3 예제 11)는 입구에서 portASSERT_IF_INTERRUPT_PRIORITY_INVALID()를 부른다. 이벤트 그룹 · 타이머 · 스트림 버퍼의 FromISR은 내부에서 이 함수들을 거쳐 같은 검사에 닿는다. ARM_CM3 portmacro.h에서 이것은 configASSERT_DEFINED == 1일 때만 vPortValidateInterruptPriority()로 정의된다. 함수 본문(port.c 766~820행)의 핵심은 세 줄이다.

  • IPSR로 지금 돌고 있는 예외 번호를 읽고, 그것이 외부 IRQ(16 이상)이면 NVIC IPR 바이트를 직접 읽어 문턱과 비교한다. ucMaxSysCallPriority는 xPortStartScheduler()가 실제 칩의 구현 비트 수에 맞춰 계산해 둔 값이다(B3 예제 8).
  • 두 번째 assert는 PRIGROUP(서브 우선순위 비트)이 0이 아니면 막는다(B3 §5.2).
  • 검사하지 않는 경우: IPSR이 16 미만 — thread mode(0)와 시스템 예외(SVC 11, PendSV 14, SysTick 15). 예제 2에서 태스크가 FromISR을 불러도 assert가 안 터진 이유다.

예제 6 MODE=8 출력(port.c:803)이 이 검사가 잡은 것이다. "우선순위를 안 정한 IRQ = 0 = 무조건 걸림"은 B3 예제 11 MODE=2에서 봤다.

5.2 Zephyr에는 이 검사가 없다 — 대신 빌드 시점에#

Zephyr Cortex-M에는 "지금 ISR의 우선순위가 커널이 막을 수 있는 범위인가"를 런타임에 보는 검사가 없다. 대신 구조가 실수를 어렵게 만든다.

  • IRQ_CONNECT(irq, prio, ...)의 prio는 논리 번호이고, 아키텍처 코드가 커널이 쓰는 영역(_IRQ_PRIO_OFFSET) 아래로만 매핑한다(B3 §8.1). 보통 IRQ는 구조적으로 irq_lock()의 BASEPRI 아래에 놓인다.
  • 커널 밖(zero-latency) IRQ는 IRQ_ZERO_LATENCY 플래그로 명시해야만 만들 수 있다. include/zephyr/arch/arm/irq.h의 ARCH_IRQ_CONNECT는 이 플래그를 보면 BUILD_ASSERT(!(flags_p & IRQ_ZERO_LATENCY), "ZLI interrupts must be registered using IRQ_DIRECT_CONNECT()")로 빌드를 실패시키고, ARCH_IRQ_DIRECT_CONNECT는 CONFIG_ZERO_LATENCY_IRQS가 꺼져 있으면 "ZLI interrupt registered but feature is disabled"로 실패시킨다. 우선순위 범위도 _CHECK_PRIO의 BUILD_ASSERT가 본다.
  • 그래서 Zephyr에서 남는 실수는 "ZLI ISR 안에서 커널 API를 부르는 것"인데, 이것은 런타임 검사가 없다. ISR_DIRECT_DECLARE 주석이 "Any ISRs that serve IRQs configured with the IRQ_ZERO_LATENCY flag must always return 0"이라고 경고하는 것이 전부다. 이 영역 설계는 E2.

6. Zephyr 쪽 규칙 — 같은 이름, K_NO_WAIT, 그리고 direct ISR#

6.1 직관: 이름을 나누는 대신 인자로 나눈다#

Zephyr는 FreeRTOS처럼 ...FromISR을 따로 두지 않는다. ISR에서도 k_sem_give(), k_msgq_put()를 그대로 부른다. 대신 규칙이 인자에 있다.

  • timeout을 받는 API는 ISR에서 K_NO_WAIT만 허용한다. 기다릴 수 없으니 "지금 되면 하고 안 되면 에러 코드"다.
  • 재스케줄은 앱이 요청하지 않는다. 보통 ISR은 공용 _isr_wrapper를 거쳐 불리고, wrapper 끝의 z_arm_int_exit()(별칭 z_arm_exc_exit, arch/arm/core/cortex_m/exc_exit.c)가 _kernel.ready_q.cache != _kernel.cpus->current이면 PendSV를 건다. FreeRTOS의 woken + yield를 커널이 자동으로 한다(D1 §4.4).
  • 문맥 판별은 k_is_in_isr() = arch_is_in_isr() = __get_IPSR() != 0(arch/arm/include/cortex_m/exception.h 93행). FreeRTOS xPortIsInsideInterrupt()와 같은 방법이다.

어떤 API가 ISR에서 되는지는 Doxygen 주석의 @isr_ok 표시로 알 수 있다. v4.4.2 include/zephyr/kernel.h에 72개가 있다. 주석 다음에 오는 함수 이름을 뽑으면 이렇다.

출력에서 볼 것: k_sem_take, k_msgq_get, k_queue_get, k_mem_slab_alloc, k_heap_alloc 처럼 timeout을 받는 함수도 목록에 있다 — 문서 본문에 "K_NO_WAIT일 때만"이라는 조건이 붙는다. 목록에 없는 것: k_mutex_lock/unlock, k_sleep, k_msleep, k_yield, k_thread_create, k_condvar_wait, k_work_flush·k_work_cancel_sync(기다리는 함수). 이 표시가 모든 ISR-안전 함수에 빠짐없이 붙어 있지는 않다(예: k_timer_start에는 표시가 없다). 표시는 "확실히 된다"는 뜻이고, 표시가 없을 때는 소스의 arch_is_in_isr() assert를 확인한다.

v4.4.2 커널 소스에서 ISR 관련 assert는 이렇게 생겼다(grep -n arch_is_in_isr kernel/*.c에서 고름).

6.3 예제 10 — CONFIG_ASSERT=n에서 ISR이 timeout을 넘기면#

무엇을 확인하는 코드인지: 보통 앱 빌드처럼 assert를 끄고, 진짜 TIMER0 IRQ가 prio 7 victim 스레드를 끊은 상태에서 ISR이 k_sem_take(&sem, K_MSEC(10))(MODE 1) 또는 k_sleep(K_MSEC(10))(MODE 2)을 부른다. victim은 FreeRTOS 예제 7처럼 자기 최장 공백을 기록한다. FreeRTOS와 같은 조건으로 재려고 QEMU를 -icount shift=5로 직접 실행했다.

출력에서 볼 것:

  • ISR은 기다리지 않고 17 µs 만에 돌아왔다. 그런데 victim이 19 ms 동안 CPU를 못 받았다. FreeRTOS 예제 7 MODE 4와 같은 현상 — 끊긴 스레드가 대신 잠들었다.
  • .config: 이 빌드는 CONFIG_USE_SWITCH가 꺼져 있다 → z_swap()이 아래의 arch_swap()(PendSV 방식)을 쓴다.
  • 이유를 소스로: z_impl_k_sem_take()는 count가 0이면 z_pend_curr(&lock, key, &sem->wait_q, timeout)을 부른다. _current(= ISR이 끊은 victim)를 대기 큐에 넣고 z_swap() → arch_swap()(arch/arm/include/cortex_m/kernel_arch_func.h 87행)으로 간다. Cortex-M의 arch_swap()은 _current->arch.swap_return_value = -EAGAIN;을 써 두고 PENDSVSET을 세운 뒤 irq_unlock(0)을 하고 바로 반환한다. ISR 안이라 PendSV는 ISR이 끝나야 돌므로, ISR은 -EAGAIN(-11) 을 받고 계속 진행한다. 반환값은 "timeout"처럼 보이지만 실제로 기다린 것은 victim이다. 게다가 irq_unlock(0)은 ISR 한가운데서 BASEPRI를 0으로 내린다.

  • k_sleep()도 마찬가지다(z_tick_sleep()이 unready_thread(_current) 후 z_swap()). 반환값 0은 "다 잤다"는 뜻인데 잔 것은 victim이다.

6.4 IRQ_CONNECT vs IRQ_DIRECT_CONNECT — 커널의 도움을 끄는 스위치#

그림 6 — Zephyr Cortex-M의 두 ISR 경로(v4.4.2). 보통 ISR은 벡터 테이블의 모든 칸이 _isr_wrapper를 가리키고, wrapper가 IPSR로 번호를 구해 _sw_isr_table에서 (함수, 인자)를 꺼내 부른 뒤 z_arm_int_exit()로 재스케줄을 판단한다(B2 예제 15). direct ISR은 벡터 테이블에 함수가 직접 들어가고, 재스케줄 판단은 반환값이 0이 아닐 때만 한다.

arch/arm/core/cortex_m/isr_wrapper.c의 _isr_wrapper()가 매번 하는 일 셋:

  1. CONFIG_PM이면 저전력 idle에서 깨어난 처리(pm_system_resume()).
  2. __get_IPSR() - 16으로 _sw_isr_table을 인덱싱해 entry->isr(entry->arg) 호출 — 인자 전달.
  3. 끝에서 z_arm_exc_exit() — 재스케줄 판단.

direct ISR은 이 셋을 앱이 고른다. include/zephyr/irq.h와 include/zephyr/arch/arm/irq.h(v4.4.2)의 정의:

  • ISR_DIRECT_DECLARE(name) { ... return 0 또는 1; } — 본문을 name_body()로 만들고, 바깥 name()이 HEADER → body → FOOTER(반환값)를 부른다. 반환값이 0이면 z_arm_int_exit()를 건너뛴다.
  • ISR_DIRECT_PM() — CONFIG_PM이면 _arch_isr_direct_pm(), 아니면 빈 매크로. 저전력 idle 중에 이 IRQ로 깰 수 있다면 넣어야 한다. irq.h 주석: "It may be omitted, but be careful!", 그리고 ZLI에서는 쓰면 안 된다.
  • IRQ_DIRECT_CONNECT(irq, prio, isr, flags) — 인자 없음(void name(void)), 스택 전환 없음, 그리고 IRQ_ZERO_LATENCY 플래그와 함께 쓰면 커널 밖 IRQ가 된다(E2).

irq.h의 ISR_DIRECT_DECLARE 주석 예시가 이 계약을 잘 보여 준다: 일이 없으면 return 0; // don't bother checking if we have to z_swap(), k_sem_give()를 했으면 return 1;. 즉 direct ISR의 반환값이 FreeRTOS의 woken 역할이다. 그리고 FreeRTOS와 똑같은 실수를 할 수 있다.

그럼 direct ISR은 언제 0을 반환하나? 스레드를 깨우지 않은 경우(FIFO만 비웠다), 그리고 ZLI(커널 API를 부르면 안 되므로 깨울 일 자체가 없다). 커널 객체를 건드렸으면 1을 반환한다 — FreeRTOS 규칙 "항상 woken을 받아 yield"와 같은 원리다.

6.6 irq_offload() — 테스트에서 ISR 문맥 만들기#

예제 9에서 봤듯이 irq_offload(routine, param)은 routine을 SVC 예외 안에서 동기적으로 실행하고 돌아온다(kernel/irq_offload.c가 offload_sem으로 직렬화, CONFIG_IRQ_OFFLOAD_NESTED면 생략). 용도:

12. 면접에서 이렇게 말한다#

Q. Why does FreeRTOS have separate FromISR versions of its API? (FreeRTOS는 왜 FromISR API를 따로 두나?)

A. 세 가지가 다르기 때문이다. ISR은 블록할 수 없으니 timeout 인자와 대기 경로가 없다. 크리티컬 섹션이 중첩 카운터식이 아니라 BASEPRI 저장/복원식이다. 그리고 높은 태스크를 깨워도 그 자리에서 스위치하지 않고 플래그만 돌려준다. 그 덕에 ISR 경로가 짧다 — 큐 send 기준 코드가 404 B에서 232 B로, give가 2.5 µs에서 1.5 µs로 줄었다(QEMU).

FreeRTOS keeps separate ISR APIs because three things differ in interrupt context. An ISR cannot block, so the FromISR variants have no timeout and no wait path. The critical section must save and restore BASEPRI instead of using the task-level nesting counter, which would drop BASEPRI to zero. And the ISR cannot context-switch on the spot, so the API only reports through pxHigherPriorityTaskWoken that a higher-priority task was woken, and the ISR requests the switch with portYIELD_FROM_ISR at the end. The result is a shorter, simpler path: on my QEMU Cortex-M3 measurements xQueueGenericSendFromISR is about half the code size of xQueueGenericSend.

Q. What is xHigherPriorityTaskWoken for, and what happens if you pass NULL or forget portYIELD_FROM_ISR? (그 플래그는 무엇이고 빼먹으면?)

A. FromISR API가 "지금 돌던 태스크보다 높은 태스크를 깨웠다"는 사실을 알려 주는 플래그다. ISR 끝에서 그것을 portYIELD_FROM_ISR에 넘기면 PendSV가 걸려서 ISR이 끝나자마자 그 태스크로 간다. 빼먹어도 커널이 xYieldPendings로 기억해 두었다가 다음 tick에서 전환하므로 기능은 맞지만, 지연이 최대 1 tick이 된다. 실제로 재 보니 1 kHz에서 평균 0.5 ms, 100 Hz에서 평균 5 ms, 최대 10 ms였고 yield가 있으면 tick과 무관하게 9 µs였다.

It tells the ISR whether the API call unblocked a task with higher priority than the one that was interrupted. You initialise it to pdFALSE, pass the same variable to every FromISR call in the handler, and call portYIELD_FROM_ISR with it at the end, which just pends PendSV so the switch happens right after the ISR returns. If you pass NULL or skip the yield, the kernel still records a pending yield and switches on the next tick, so it works functionally but the wake-up latency becomes uniformly distributed up to one tick period. I measured nine microseconds with the yield, versus an average of half a tick and a worst case of a full tick without it, at 1000, 250 and 100 Hz.

꼬리 질문: "한 ISR에서 FromISR을 두 번 부르면?" → 같은 변수를 넘긴다. 따로 받아서 마지막 것만 넘기면 앞의 pdTRUE가 사라진다.

Q. List the things you must not do in an ISR under an RTOS, and why. (ISR에서 하면 안 되는 것은?)

A. 기다리는 모든 것 — 블로킹 take, delay, sleep, 뮤텍스. ISR에는 블록할 주체가 없어서 커널이 끊긴 태스크를 재운다. 태스크용 API(크리티컬 섹션 방식이 다름), 문턱보다 급한 ISR에서의 커널 API(커널이 막을 수 없음), printf와 malloc(블로킹 · 재진입), 상한 없는 루프, FPU 없는 코어에서의 float. 공통 원리는 "ISR의 길이는 같거나 낮은 우선순위의 모든 것의 지연"이라는 것이다.

Anything that can wait: blocking receives with a timeout, delays, sleeps and mutexes. An ISR has no task identity, so the kernel would put the interrupted task to sleep instead. I demonstrated that with asserts disabled: vTaskDelay in an ISR stalled an unrelated task for five milliseconds, and a blocking take spun forever inside vListInsert. Also non-ISR API variants, any kernel call from an interrupt above the max syscall priority, printf and malloc because they block or are not reentrant, unbounded loops, and floating point on cores without an FPU. The underlying rule is that every microsecond in an ISR is added to the latency of everything at the same or lower priority.

Q. Why can't you use a mutex from an ISR? (ISR에서 뮤텍스를 못 쓰는 이유는?)

A. 뮤텍스는 소유자가 태스크라는 전제 위에 있다. 소유자만 풀 수 있고, 우선순위 상속은 소유자 태스크의 우선순위를 올린다. ISR은 TCB가 없고 우선순위 축도 다르며 기다릴 수도 없다. FreeRTOS에서는 ISR이 빈 뮤텍스를 take하면 assert 없이 성공해서 "소유자 없는 잠긴 뮤텍스"가 되고 태스크가 영원히 못 얻는 것을 실험으로 봤다. Zephyr는 k_mutex_lock에서 assert로 막는다.

A mutex assumes its owner is a task: only the owner may release it, and priority inheritance boosts the owner's priority. An ISR has no task control block, its priority lives in the NVIC rather than the scheduler, and it cannot wait if the mutex is held. In FreeRTOS, taking a free mutex from an ISR actually succeeds with no assert and leaves a locked mutex with a NULL holder, so tasks then time out forever. Zephyr asserts in k_mutex_lock. For data shared between an ISR and a task I use a short ISR-safe critical section, a lock-free single-producer single-consumer buffer, or a gatekeeper task.

Q. How does FreeRTOS catch an ISR that calls the API from the wrong priority? (잘못된 우선순위를 어떻게 잡나?)

A. configASSERT가 정의되어 있으면 FromISR 입구에서 vPortValidateInterruptPriority가 IPSR로 현재 IRQ 번호를 읽고, NVIC의 그 IRQ 우선순위 바이트가 configMAX_SYSCALL_INTERRUPT_PRIORITY보다 급하면 assert한다. 리셋값 0인 IRQ는 무조건 걸린다. thread mode와 시스템 예외는 검사하지 않는다. assert를 끄면 이 함수 자체가 빠진다.

When configASSERT is defined, every core FromISR function calls vPortValidateInterruptPriority on entry. It reads IPSR to get the active exception number, looks up that interrupt's priority byte in the NVIC, and asserts if it is logically higher than configMAX_SYSCALL_INTERRUPT_PRIORITY, because the kernel's BASEPRI critical sections cannot mask it. An interrupt left at its reset priority of zero always fails that check. It also asserts if priority grouping leaves sub-priority bits. With configASSERT undefined the check is compiled out, which is why I keep asserts on in development builds and log-and-reset in production.

Q. In Zephyr, what's the difference between IRQ_CONNECT and IRQ_DIRECT_CONNECT? (Zephyr의 두 연결 방식 차이는?)

A. 보통 ISR은 공용 wrapper가 PM 복귀, 인자 전달, 출구의 재스케줄 판단을 해 준다. direct ISR은 벡터에 바로 들어가서 셋 다 선택이 된다. ISR_DIRECT_PM()을 넣을지, 반환값을 1로 해서 재스케줄을 검사할지 앱이 정한다. 스레드를 깨우고 0을 반환하면 FreeRTOS에서 yield를 빼먹은 것과 같고, tickless에서는 더 나빠서 실측 19 ms(시간 슬라이스), 슬라이스를 끄면 최대 660 ms까지 늦어졌다.

IRQ_CONNECT goes through the common _isr_wrapper, which handles power-management exit, passes the argument from the software ISR table, and on exit checks whether a higher-priority thread became ready and pends PendSV. IRQ_DIRECT_CONNECT puts the handler straight into the vector table and makes those steps optional: you call ISR_DIRECT_PM yourself and the return value of the ISR_DIRECT_DECLARE body decides whether the reschedule check runs. If you give a semaphore and return zero, the woken thread waits for the next ordinary interrupt. On a tickless 100 Hz build I measured about 19 milliseconds, set by the time-slice timer, and up to 660 milliseconds with time slicing disabled.

꼬리 질문: "그럼 direct ISR은 왜 쓰나?" → wrapper 몇십 사이클과 간접 호출을 줄이고, ZLI는 direct여야만 한다(ARCH_IRQ_CONNECT가 BUILD_ASSERT로 거부).

Q. How do you write a function that may be called from both a task and an ISR? (양쪽에서 불리는 함수는?)

A. FreeRTOS는 xPortIsInsideInterrupt(), Zephyr는 k_is_in_isr()로 IPSR을 보고 분기한다. FreeRTOS에서는 ISR 쪽에서 FromISR + woken + yield, 태스크 쪽에서 보통 API. Zephyr에서는 timeout을 k_is_in_isr() ? K_NO_WAIT : K_MSEC(n)으로 고른다. 다만 둘 다 PendSV · SVC 안에서도 참이고, zero-latency ISR인지는 알려 주지 않는다.

Check the execution context at run time: xPortIsInsideInterrupt in FreeRTOS or k_is_in_isr in Zephyr, both of which just test IPSR. In FreeRTOS the ISR branch uses the FromISR call with a woken flag and portYIELD_FROM_ISR, and the task branch uses the normal call. In Zephyr the same call works in both, but the timeout must be K_NO_WAIT in the ISR branch. Note that these helpers return true for any exception, including SVC and PendSV, and they cannot tell you whether you are in a zero-latency interrupt where no kernel call is allowed, so priority discipline is still needed.

15. 요약 & 체크리스트#

RTOS에서 ISR은 "플래그만 세우는 짧은 함수"에 더해 커널과의 계약을 지켜야 한다. FreeRTOS는 그 계약을 이름(FromISR)과 woken 플래그로, Zephyr는 인자(K_NO_WAIT)와 ISR 출구의 자동 재스케줄로 표현한다. 계약의 핵심은 셋이다: ISR은 기다리지 않는다, ISR은 자기 방식(저장/복원)으로만 마스크한다, ISR은 스위치를 요청만 하고 실행은 PendSV에 맡긴다. 이 노트의 측정에서 yield 한 줄을 빼먹으면 지연이 tick 주기만큼(1 kHz에서 최대 1 ms, 100 Hz에서 10 ms), Zephyr direct ISR이 0을 반환하면 최대 SysTick 한 바퀴(660 ms)까지 늘었다. 블로킹 호출은 assert가 있으면 첫 실행에서 port.c:438 / sem.c:136으로 잡히지만, 없으면 끊긴 태스크가 잠들거나 ISR이 vListInsert에서 영원히 돈다. 그래서 개발 빌드는 assert를 켜고, 양산은 "기록하고 리셋"으로 남긴다.
