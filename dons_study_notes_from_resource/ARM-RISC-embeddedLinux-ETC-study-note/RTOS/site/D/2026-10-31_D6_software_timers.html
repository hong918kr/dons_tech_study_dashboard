D6. 소프트웨어 타이머 — 알람 목록과 그 알람을 울려 주는 비서(daemon task)

218분 읽기2352줄61개 절

이 노트를 다 읽으면: FreeRTOS 소프트웨어 타이머가 "명령 큐 + 타이머 서비스 태스크 + 정렬된 알람 목록 두 개"로 돌아가는 구조를 timers.c 함수 이름으로 설명할 수 있다 · 콜백에서 블록하면 왜 모든 타이머가 밀리는지, 데몬 우선순위를 낮추면 무엇이 늦어지는지를 측정 숫자로 말할 수 있다 · auto-reload가 drift 없이 돌고 밀리면 "몰아서" 호출된다는 것을 소스와 실측으로 보여 줄 수 있다 · Zephyr k_timer의 expiry 함수가 ISR에서 돈다는 것과 그 결과(블록 금지, +1 tick이 없는 duration, IRQ 잠금 시 시간 손실)를 설명하고 소프트웨어 타이머 / 주기 태스크 / 하드웨어 타이머 중 하나를 근거와 함께 고를 수 있다 왜 필요한가: "타이머 콜백에서 블록하면?", "소프트웨어 타이머와 하드웨어 타이머는 언제 쓰나?", "RC 링크가 끊긴 걸 어떻게 감지하나?"는 드론·로봇 펌웨어 면접의 단골이다. 실무에서는 "LED가 가끔 멈칫한다", "failsafe가 100 ms가 아니라 113 ms 뒤에 걸렸다", "워치독이 멈춘 태스크를 못 잡았다"로 나타난다. Don 기준 난이도: SSD 펌웨어에서 1 ms 타이머 ISR로 명령 타임아웃 테이블을 훑던 일은 이미 했다 / 그 일을 RTOS가 "데몬 태스크 + 명령 큐"로 일반화한 방식, 명령의 기준 시각, auto-reload의 몰아치기, 데몬 우선순위의 효과, Zephyr의 ISR 문맥 expiry와 SysTick 드라이버의 전제 조건은 새로 배운다 선행 노트: C3(Tmr Svc가 첫 태스크인 이유), C5(tick, delayed list 두 개와 wrap, xTaskDelayUntil), C6(tickless), C9(daemon startup hook, stack overflow 검사), EL F8(timer wheel, hrtimer). 함께 읽을 노트: D7(xTimerPendFunctionCallFromISR, Zephyr workqueue · k_work_delayable), E5(HW 타이머 직접 사용)

0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어에서 쓰던 명령 타임아웃을 떠올려 보자. 호스트가 NVMe 명령을 수백 개 동시에 보내면, 펌웨어는 명령마다 "언제까지 끝나야 하나"를 기록해 두고, 1 ms 타이머 ISR(또는 메인 루프의 주기 작업)이 그 테이블을 훑어 마감이 지난 명령을 abort 경로로 보낸다. 하드웨어 타이머는 몇 개뿐인데 마감은 수백 개다. 그래서 하드웨어 타이머 하나를 시계로 삼고, 소프트웨어로 "알람 목록"을 관리했다.

RTOS의 소프트웨어 타이머(software timer)가 정확히 이것이다. 하드웨어 타이머가 아니라 커널의 tick(C5)을 시계로 쓰는, 개수 제한 없는(RAM이 허락하는 만큼) 알람이다. 알람마다 "언제 울릴지, 울리면 무엇을 부를지(callback), 한 번만인지 반복인지"를 적어 둔다. 그리고 누가 그 콜백을 부르나가 RTOS마다 다르다.

  • FreeRTOS: 콜백을 부르는 전담 태스크가 있다. 이름은 타이머 서비스 태스크(timer service task), 별명은 daemon task, 태스크 이름은 "Tmr Svc"다. 비서 한 명이 알람 목록을 들고 있다가 시각이 되면 콜백을 차례로 부른다고 생각하면 된다.
  • Zephyr: 비서가 없다. 시스템 시계 인터럽트(SysTick ISR)가 알람 목록을 훑다가 ISR 안에서 직접 expiry 함수를 부른다.

그림 1 — 소프트웨어 타이머(왼쪽)는 tick 하나를 시계로 삼아 알람을 몇 개든 만들고, 비서(FreeRTOS의 Tmr Svc)가 콜백을 차례로 부른다. 하드웨어 타이머(오른쪽)는 주변장치 하나가 알람 하나이고 만료가 곧 인터럽트다.

이 비유 하나에서 이 노트의 모든 주제가 나온다.

  1. 비서는 한 명이다 → 콜백 하나가 오래 걸리거나 잠들면(블록하면) 뒤에 줄 선 모든 알람이 늦는다 (§4).
  2. 비서도 태스크다 → 비서보다 우선순위 높은 태스크가 CPU를 쥐고 있으면 알람이 늦는다 (§5).
  3. 비서에게 일을 시키려면 쪽지(명령)를 큐에 넣는다 → xTimerStart()는 타이머를 "시작"하는 게 아니라 "시작해 달라는 명령"을 보낸다. ISR도 마찬가지다 (§2, §3).
  4. 알람 목록의 정밀도는 tick이다 → 1 kHz tick이면 1 ms보다 촘촘한 일은 못 한다. 8 kHz rate loop, 20 kHz FOC는 하드웨어 타이머의 일이다 (§8).

드론 비행 제어기라면 소프트웨어 타이머가 맡는 일은 이런 것들이다: 상태 LED 깜빡임(heartbeat), RC 링크 끊김 감지(패킷마다 타이머 리셋, 만료 = failsafe), 버튼·스위치 debounce, 배터리 전압 저속 샘플링, 텔레메트리 주기 송신 트리거, 통신 재시도 backoff. 공통점은 짧고, 블록하지 않고, ms 단위 정밀도면 충분한 일이라는 것이다.

실습 환경 한 줄#

FreeRTOS 예제는 QEMU mps2-an385(Cortex-M3 @ 25 MHz) + FreeRTOS V11.3.2, ICOUNT=1(명령 1개 = 32 ns 가상 시간, 실행마다 같은 숫자)로 돌렸다. Zephyr 예제는 같은 가상 보드 + Zephyr v4.4.2, CONFIG_SYS_CLOCK_TICKS_PER_SEC=1000을 명시하고 역시 ICOUNT=1로 돌렸다. 시간은 MPS2 FPGAIO 카운터(0x40028018, 25 MHz = 40 ns 단위)로 쟀다. 숫자는 QEMU icount 기준이라 실제 칩과 절대값은 다르다(캐시·플래시 wait state·예외 스태킹 사이클 미모델링). 하지만 "몇 ms 늦는가", "몇 번 몰아서 불리는가" 같은 구조적인 결과는 실칩과 같다.

1. 소프트웨어 타이머의 정의와 첫 예제#

1.1 직관 — 부엌 타이머 여러 개#

부엌 타이머를 생각하자. 하나는 "30분 뒤 한 번 울림"(오븐), 하나는 "20분마다 계속 울림"(물 주기 알림)이다. 앞의 것이 one-shot, 뒤의 것이 auto-reload다. 타이머에는 이름표(ID)를 붙일 수 있어서, 똑같은 "울리면 할 일"(콜백)을 여러 타이머가 같이 쓰면서도 누가 울렸는지 구분할 수 있다.

1.3 예제 1 — one-shot / auto-reload / ID / 콜백이 도는 곳#

무엇을 확인하나: 두 타이머(one-shot 30 ms, auto-reload 20 ms)를 만들고 Start · ChangePeriod · SetReloadMode · Reset을 차례로 부르며, 콜백이 어느 태스크에서, 어떤 우선순위로 도는지와 각 API 뒤의 상태·만료 시각을 찍는다. ID는 호출 횟수 카운터로 쓴다.

출력에서 볼 것:

  • 콜백은 전부 Tmr Svc 태스크, 우선순위 7에서 돌았다. 내 app 태스크(prio 2)가 아니다. 이 템플릿은 configTIMER_TASK_PRIORITY = configMAX_PRIORITIES - 1 = 7로 데몬을 가장 높게 둔다.
  • xTimerStart()가 돌아온 바로 다음 줄에서 이미 active=1이다. app(prio 2)이 명령을 큐에 넣는 순간 높은 데몬(prio 7)이 깨어 선점하고, 명령을 처리한 뒤 다시 막히고 나서야 app이 돌아왔기 때문이다. 데몬이 app보다 낮으면 이 줄은 0이 된다(예제 2).
  • tick 65에 ChangePeriod(5)를 부르자 다음 만료가 70이 됐다. 원래 격자(80)와 상관없이 "지금 + 5"다.
  • tick 77에 reload 모드를 끄자 이미 걸려 있던 80의 만료는 그대로 울리고(reload=0으로 찍힘) 그 뒤로는 다시 걸리지 않았다(tick 89에 active=0).
  • 달리는 one-shot에 Reset을 두 번 부르면 만료가 119 → 129로 밀린다. "계속 리셋해서 안 울리게 한다"가 바로 link-loss 감지와 debounce의 원리다(§10).

1.4 함정#

  • xTimerStart(t, 0)의 0은 "타이머 0 ms"가 아니라 "큐가 차 있으면 기다리지 말고 실패하라"다. 반환값 pdFAIL을 무시하면 타이머가 조용히 안 돈다.
  • 스케줄러 시작 전(main() 안)에 xTimerStart()를 부르면 명령이 큐에 쌓이기만 하고 데몬이 시작될 때 처리된다. 이때 xTicksToWait는 무시되고 0으로 보낸다(xTimerGenericCommandFromTask의 xTaskGetSchedulerState() 분기). 큐 길이보다 많은 타이머를 main()에서 시작하면 넘친다.
  • 콜백 시그니처의 인자는 만료된 타이머의 핸들이다. 같은 콜백을 여러 타이머가 쓰면 pvTimerGetTimerID(xTimer)로 구분한다.
  • period 0은 configASSERT( ( xTimerPeriodInTicks > 0 ) )에 걸린다. pdMS_TO_TICKS(0.5) 같은 값이 0으로 내림되는 경우를 조심한다(C5 §1.4, §8의 예제 13).

2. 타이머 서비스 태스크와 명령 큐#

2.1 왜 ISR이 아니라 태스크인가#

FreeRTOS는 콜백을 tick ISR에서 부르지 않고 일부러 태스크 하나를 세웠다. 이유는 셋이다.

  1. tick ISR을 짧고 일정하게 유지한다. tick ISR이 알람 목록을 훑고 콜백까지 부르면, tick 시간이 "그 순간 만료된 타이머 수 × 콜백 길이"에 비례해 들쭉날쭉해진다. 데몬 방식에서 tick ISR은 "데몬이 기다리던 시각이 됐다"만 알고 데몬을 ready로 옮긴다 — 지연 태스크 하나 깨우는 것과 같은 일이다(C5 §3).
  2. 콜백이 태스크 문맥이다. 일반 API(xQueueSend, xTaskNotify, printf류)를 FromISR 없이 부를 수 있다. 단, 블록만은 하면 안 된다(§4).
  3. 알람 목록을 데몬 혼자만 만진다. timers.c의 주석이 "Only the timer service task is allowed to access these lists."라고 못 박는다. 그래서 목록을 고칠 때 인터럽트를 끌 필요가 없다. 다른 태스크와 ISR은 목록을 직접 못 만지고 명령을 큐에 넣어 부탁한다.

Don의 SSD 경험으로 말하면, ISR에서 플래그만 세우고 실제 처리는 메인 루프의 "타이머 처리 함수"가 하던 구조를 커널이 표준화한 것이다. 그 처리 함수가 독립된 스택과 우선순위를 가진 태스크가 됐을 뿐이다.

2.3 데몬의 한 바퀴#

prvTimerTask()(timers.c 746행)의 몸체는 세 줄이다.

prvProcessTimerOrBlockTask()는 지금 tick이 맨 앞 타이머의 만료 tick 이상이면 prvProcessExpiredTimer()로 콜백을 부르고, 아니면 vQueueWaitForMessageRestricted(xTimerQueue, xNextExpireTime - xTimeNow, ...)로 "명령이 오거나 다음 만료 시각이 되거나, 먼저 오는 쪽까지" 블록한다. 블록 시간이 곧 다음 만료까지의 거리이므로, 타이머가 많아도 데몬은 만료가 없으면 한 번도 깨지 않는다. tick ISR 입장에서 데몬은 "N tick 뒤에 깨울 태스크 하나"일 뿐이다. 그래서 tickless(C6)와도 자연스럽게 맞물린다 — 다음 타이머 만료가 곧 idle이 잘 수 있는 한계가 된다.

2.4 예제 2 — 명령은 언제 처리되나, 만료는 무엇 기준인가#

무엇을 확인하나: app 태스크(prio 3)가 10 ms one-shot에 xTimerStart()를 보낸 뒤 0 / 5 / 15 ms 동안 CPU를 쥔다(바쁜 대기). 데몬 우선순위가 7(호출자보다 높음)일 때와 1(낮음)일 때, 명령이 데몬에게 언제 도착하나(trace 매크로로 측정)와 콜백이 몇 tick에 울리나를 본다.

출력에서 볼 것:

  • 데몬 prio 7: 명령은 보낸 지 14 µs 만에 처리됐다(큐 send → 데몬 선점 → 큐 receive → 리스트 삽입). xTimerStart()가 돌아왔을 때 이미 active=1이다. busy=15일 때 콜백이 tick +10에 울렸는데, 그 순간 app은 아직 바쁜 대기 중이었다 — 높은 데몬이 app을 선점해서 콜백을 불렀다.
  • 데몬 prio 1: 명령은 app이 CPU를 놓을 때까지 큐에서 기다린다(5020 µs, 15020 µs). 그런데 busy=5에서 콜백은 여전히 tick +10이다. 명령이 5 ms 늦게 처리됐는데도 만료는 "명령을 보낸 순간 + 10"으로 계산됐다. xTimerStart() 매크로가 보낼 때의 tick을 같이 싣기 때문이다.
  • busy=15에서는 처리 시점(+15)에 이미 만료 시각(+10)이 지났다. 이때 데몬은 리스트에 넣지 않고 처리하자마자 콜백을 부른다(tick +15). 늦게는 울려도 빼먹지는 않는다.

이 동작이 소스 어디에 있나. include/timers.h의 매크로가 tick을 싣는다.

데몬은 명령을 꺼낸 뒤 prvInsertTimerInActiveList(pxTimer, 명령시각 + period, xTimeNow, 명령시각)을 부른다(timers.c 892행). 만료 tick이 이미 지났고 xTimeNow - 명령시각 >= period면 xProcessTimerNow = pdTRUE를 돌려주고, 호출자(prvProcessReceivedCommands)가 그 자리에서 콜백을 부른다. ChangePeriod만 예외로 xTimeNow + 새 period를 쓴다(소스 주석: "The new period does not really have a reference").

2.5 함정#

  • 데몬이 낮은 우선순위일 때 xTimerStart() 직후 xTimerIsTimerActive()는 0이다. "시작했는데 active가 아니다"를 버그로 착각하기 쉽다. 상태는 데몬이 명령을 처리해야 바뀐다.
  • xTimerStop()도 명령이다. 데몬이 호출자보다 낮아서 Stop이 큐에서 기다리는 동안 만료 시각이 지나면, 데몬은 깨어나서 만료(콜백)를 먼저 처리하고 Stop을 나중에 처리한다(루프 순서가 "만료 처리 → 명령 처리"). 즉 "멈췄는데 한 번 더 울린" 콜백이 나올 수 있다. 콜백 안에서 "지금 이 일을 해도 되는 상태인가"를 한 번 더 확인하는 습관이 안전하다.
  • xTimerDelete() 직후 핸들을 다시 쓰면 안 된다. free는 데몬이 명령을 처리할 때 일어나므로 "지금은 되는 것처럼 보이는" use-after-free가 생긴다.

3. ISR에서 타이머 다루기 — FromISR와 명령 지연#

3.1 왜 ISR도 큐를 거치나#

ISR이 알람 목록을 직접 고칠 수 있다면 빠르겠지만, 그러면 데몬이 목록을 훑는 동안 인터럽트를 꺼야 한다. FreeRTOS는 반대를 택했다. ISR은 xTimerStartFromISR(), xTimerResetFromISR(), xTimerStopFromISR(), xTimerChangePeriodFromISR()로 16바이트짜리 명령 하나를 큐에 넣고(xQueueSendToBackFromISR) 끝난다. 명령의 기준 시각은 ISR이 부른 순간의 xTaskGetTickCountFromISR()다(timers.h 1116행의 xTimerResetFromISR 매크로).

대가는 명령 지연이다. 데몬이 명령을 꺼내기 전까지 타이머 상태는 그대로다. 그리고 큐가 가득 차면 FromISR는 기다릴 수 없으니 즉시 pdFAIL을 돌려준다.

FromISR 계열은 pxHigherPriorityTaskWoken을 받는다. 데몬이 지금 도는 태스크보다 높으면 pdTRUE가 되고, ISR 끝에서 portYIELD_FROM_ISR(woken)를 불러야 ISR이 끝나자마자 데몬으로 전환된다. 부르지 않으면? 예제 7에서 잰다.

3.2 예제 7 — ISR → 데몬 지연, yield 유무, 큐 넘침#

무엇을 확인하나: TIMER0 인터럽트(tick 경계에서 0.37 ms 뒤 한 번)가 xTimerResetFromISR()를 1 / 10 / 12번 보낸다. 그동안 app(prio 2)은 3 ms 바쁜 대기 중이다. ISR 진입부터 데몬이 첫 명령을 꺼낼 때까지의 시간과, 큐 길이 10에서 실패 수를 센다.

출력에서 볼 것:

  • yield=1, 데몬 prio 7: ISR에서 데몬까지 15 µs. ISR이 끝나자마자 PendSV로 데몬에 전환됐다.
  • yield=0: 631 µs. 인터럽트가 tick 시작 뒤 0.37 ms에 왔으니 다음 tick까지 남은 0.63 ms를 기다렸다. 큐 send가 xYieldPendings를 세워 두었기 때문에 다음 tick ISR이 전환을 일으켰다. 즉 portYIELD_FROM_ISR를 빼먹으면 최악 1 tick이 더 붙는다. link-loss 같은 100 ms 타임아웃에서는 티가 안 나지만, 데몬을 "ISR의 뒷일 처리기"로 쓰면(D7) 이 1 tick이 그대로 응답 지연이 된다.
  • burst=12: 큐 길이 10이라 2개가 실패했다(pdFAIL). ISR 안에서 보냈으니 데몬이 중간에 꺼낼 기회가 없다. 10개를 보내는 데 ISR이 약 47 µs(62 − 15) 걸렸다 — 명령 하나에 약 5 µs다.
  • 데몬 prio 1: yield를 하든 말든 2642 µs. app(prio 2)이 3 ms 바쁜 대기를 끝내고 블록할 때까지 데몬이 못 돈다. portYIELD_FROM_ISR는 "더 높은 태스크가 깨어났으면 전환"이지, 낮은 데몬을 앞으로 당겨 주지 않는다.

3.3 큐 길이 정하기#

configTIMER_QUEUE_LENGTH는 "데몬이 한 번 돌기 전까지 쌓일 수 있는 명령의 최대 수"다. 계산하는 순서는 이렇다.

  1. 한 ISR이 한 번에 보내는 명령 수의 최대(예제 7의 burst)를 센다.
  2. 데몬이 못 도는 최장 구간(더 높은 태스크의 최장 실행, 콜백 하나의 최장 실행) 동안 들어올 수 있는 인터럽트 수를 곱한다.
  3. xTimerPendFunctionCallFromISR()(D7)도 같은 큐를 쓴다(음수 명령 ID). 그 몫도 더한다.

메시지 한 칸은 16바이트다. 예제 12의 nm 출력에서 ucStaticTimerQueueStorage가 0xa0 = 160바이트 = 10 × 16으로 확인된다. 큐를 늘리는 RAM 비용은 작으니 아끼지 말고, FromISR 반환값은 반드시 확인해서 실패 카운터라도 올려 둔다.

3.4 함정#

  • FromISR 계열은 configMAX_SYSCALL_INTERRUPT_PRIORITY보다 높은(숫자가 작은) 인터럽트에서 부르면 안 된다(E1). 예제는 TIMER0을 0x40으로 두었다(경계 0x20보다 낮은 우선순위).
  • ISR에서 일반 판(xTimerReset)을 부르면 xTimerGenericCommand 매크로가 명령 ID(태스크용 1~5)를 보고 xTimerGenericCommandFromTask로 보내고, 그 안의 xQueueSendToBack이 블록 경로를 탄다. ARM_CM3 포트에서는 그 앞의 vPortEnterCritical()이 configASSERT( ( portNVIC_INT_CTRL_REG & portVECTACTIVE_MASK ) == 0 )(port.c 438행)로 "ISR에서 불렸다"를 잡아 준다 — configASSERT를 켜 두었을 때만이다.
  • "ISR에서 Reset했으니 이제 100 ms 뒤에 울린다"는 데몬이 명령을 처리한 뒤에야 참이다. 데몬이 처리하기 전에 원래 만료 시각이 와 버리면, 데몬 루프는 만료를 먼저 처리하므로 이미 리셋했어야 할 타이머가 한 번 울릴 수 있다. link-loss 타이머처럼 "울리면 안 되는" 타이머는 만료 직전의 리셋이 이 경쟁에 걸리지 않을 만큼 데몬을 높게 둔다.

4. 콜백 문맥의 규칙 — 블록 금지, 짧게, 스택은 공용#

4.1 직관 — 비서는 한 명이다#

비서가 알람 A의 할 일(콜백)을 하다가 "10분만 기다렸다가 다시 하자"며 의자에 앉아 버리면, 그동안 울려야 할 알람 B, C, D는 아무도 안 울린다. FreeRTOS 데몬이 정확히 이렇다. 콜백은 데몬 태스크의 함수 호출이므로, 콜백이 vTaskDelay()를 부르면 데몬 태스크 자체가 잠든다. 데몬이 잠든 동안 알람 목록은 아무도 보지 않고 명령 큐도 아무도 비우지 않는다.

FreeRTOS 공식 문서(software timer 페이지)도 콜백에서 vTaskDelay(), vTaskDelayUntil(), 0이 아닌 block time의 큐·세마포어 API를 부르지 말라고 명시하고, timers.h의 예제 주석도 "This is called from a timer callback so must not block."라고 적는다(323행). 커널이 막지는 않는다 — 데몬도 태스크이니 블록 API가 "작동"은 한다. 그래서 더 위험하다.

4.2 예제 3 — 콜백 하나가 블록하면 다른 타이머가 얼마나 늦나#

무엇을 확인하나: 착한 타이머 hb(auto-reload 5 ms, 시각만 기록)와 나쁜 타이머 bad(auto-reload 50 ms, 콜백에서 vTaskDelay(blk_ms))를 같이 돌린다. blk_ms를 0 / 1 / 2 / 5 / 10 / 20 / 40 ms로 바꾸며 500 ms 동안 hb의 지연(첫 호출 기준 이상적 시각과의 차이)과 "100 µs 안에 연달아 불린 최대 횟수"를 잰다.

그림 3 — 예제 3 실측. 블록하는 콜백이 잠든 시간만큼 다른 타이머의 최대 지연이 정확히 늘어난다(5 ms → 4998 µs, 40 ms → 39998 µs). 막대 위 ×N은 밀린 heartbeat가 깨어난 뒤 연달아 불린 횟수다.

출력에서 볼 것:

  • 최대 지연이 블록 시간과 µs 단위까지 같다(999, 2001, 4998, 9998 …). 데몬이 잠든 동안 hb는 완전히 멈춘다. 착한 타이머가 나쁜 이웃 하나 때문에 망가진다.
  • 호출 횟수는 거의 그대로 100이다(99는 마지막 주기가 Stop과 겹친 것). 빼먹지는 않는다. 대신 블록이 끝나면 밀린 만큼 연달아 몰아서 불린다(40 ms 블록 → 9번 연속). 5 ms 주기 LED라면 40 ms 멈췄다가 9번을 수 µs 안에 깜빡이는 셈이다 — 눈에는 "멈칫"으로 보인다. 이 몰아치기의 정체는 §6.3에서 소스로 본다.
  • 블록 1 ms만으로도 평균 지연이 99 µs다. "잠깐인데 괜찮겠지"가 다른 모든 타이머에 세금을 매긴다.

4.4 예제 11 — 콜백은 데몬의 스택을 쓴다#

무엇을 확인하나: 콜백 안의 지역 버퍼 크기(64 / 1024 / 1900 / 2000 / 2400 B)를 바꾸며 Tmr Svc의 스택 high-water mark를 본다. 데몬 스택은 configTIMER_TASK_STACK_DEPTH = 512 words = 2048 B이고, 템플릿은 configCHECK_FOR_STACK_OVERFLOW = 2다.

출력에서 볼 것:

  • 데몬 자체는 스택을 124 B(31 words)만 쓴다. 나머지는 전부 콜백 몫이다. 버퍼 1024 B면 1084 B, 1900 B면 1960 B — 거의 "데몬 기본 + 콜백 지역 변수"다.
  • 2000 B에서는 넘쳤고 방식 2 검사(스택 끝 16바이트 패턴)가 다음 문맥 전환 때 잡아 vApplicationStackOverflowHook(..., "Tmr Svc")가 불렸다.
  • 2400 B에서는 아무 메시지 없이 멈췄다(5초 타임아웃). nm -n으로 보면 템플릿에서 uxTimerTaskStack(0x2000006c부터 0x800 B) 바로 아래가 .data의 uxCriticalNesting·_impure_data다. 넘친 쓰기가 패턴 영역을 지나 커널 변수까지 덮어 검사 코드가 돌기 전에 시스템이 망가졌다. "방식 1 · 2 둘 다 놓치는 넘침"은 C9 §5와 같은 현상이다.
  • 결론: 데몬 스택 = 가장 스택을 많이 쓰는 콜백 + 124 B + 여유. 콜백 하나를 추가할 때마다 이 숫자를 다시 봐야 한다. 실제 제품에서는 uxTaskGetStackHighWaterMark(xTimerGetTimerDaemonTaskHandle())를 텔레메트리로 내보내는 것이 싸고 확실하다(C9 §9의 top 태스크).

sizeof(StaticTimer_t) = 44 B가 타이머 하나의 RAM 비용이다(heap에서 만들면 heap_4 헤더가 더 붙는다). 타이머 수십 개는 부담이 아니다. 부담은 데몬 스택 하나다.

4.5 예제 12 — 타이머 서비스를 켜는 비용 (footprint)#

무엇을 확인하나: 타이머 API를 하나도 안 쓰는 최소 앱을 configUSE_TIMERS 1과 0으로 빌드해 크기를 비교하고, nm으로 타이머 관련 심볼의 크기를 본다.

(nm 출력은 타이머 관련 줄 중 큰 것 위주로 남기고 ...로 줄였다.)

출력에서 볼 것: 타이머를 켜면 코드 +3232 B, RAM +2516 B다. RAM의 대부분은 데몬 스택 2048 B(uxTimerTaskStack)이고, TCB 96 B, 큐 제어 블록 84 B, 큐 저장소 160 B(10칸 × 16 B), 리스트 둘 40 B가 뒤따른다. prvTimerTask가 0x250 = 592 B로 가장 큰 함수인데, GCC(-O2)가 prvProcessTimerOrBlockTask, prvProcessReceivedCommands, prvSwitchTimerLists, prvInsertTimerInActiveList, prvReloadTimer, prvSampleTimeNow를 모두 인라인했기 때문이다. 같은 ELF의 nm에서 prv 접두 타이머 함수는 prvProcessExpiredTimer(0x90)와 prvCheckForValidListAndQueue(0x6c)만 남아 있고, 데몬이 블록하는 vQueueWaitForMessageRestricted(0x50)는 queue.c 쪽 심볼이다.

5. 데몬 우선순위 고르기#

5.1 직관#

비서도 회사 서열이 있다. 비서보다 높은 사람이 일하는 동안 비서는 알람이 울려도 못 움직인다. 반대로 비서가 가장 높으면 알람이 울리는 순간 누구의 일이든 끊고 콜백을 부른다. 데몬 우선순위 = 모든 콜백의 우선순위다.

5.2 예제 4 — 데몬 우선순위 vs 앱 부하#

무엇을 확인하나: 제어 루프를 흉내 낸 load 태스크(prio 3, 10 ms마다 6 ms 계산 = CPU 60%)가 도는 동안 7 ms auto-reload 타이머 200번의 지연을 잰다. 지연은 tick hook이 기록한 "그 만료 tick이 시작된 순간"부터 콜백 진입까지다. 데몬 우선순위를 7 / 4 / 3 / 2 / 1로 바꾼다.

그림 4 — 예제 4 실측. 데몬이 부하 태스크보다 높거나 같으면 모든 콜백이 tick 뒤 11 µs에 불렸다. 낮으면 지연이 0~6 ms에 고르게 퍼진다(부하가 6 ms 계산 중 어디쯤에서 만료가 왔느냐에 따라).

출력에서 볼 것:

  • prio 7 / 4 / 3: 지연 11 µs, 흔들림 0. 11 µs가 "SysTick ISR → 데몬 ready → PendSV → 데몬이 리스트를 보고 콜백 진입"의 고정 비용이다(QEMU icount 기준).
  • prio 3(같음)도 11 µs인 것이 흥미롭다. configUSE_TIME_SLICING = 1이라 같은 우선순위의 ready 태스크가 있으면 tick마다 차례가 넘어간다. 데몬은 만료 tick에 ready가 되고 바로 그 tick의 time slicing으로 차례를 받는다. 다만 이것은 "같은 우선순위 태스크가 tick마다 양보한다"에 기대는 것이므로 설계 근거로 쓰기엔 약하다. time slicing을 끄면 load가 블록할 때까지 기다린다.
  • prio 2 / 1: 평균 2.1 ms, 최대 6.02 ms = load의 계산 시간 그대로. 200번 중 80번만 1 ms 안이었다. 7과 10의 최소공배수 70 ms마다 같은 위상이 반복되므로 히스토그램이 고르게 나왔다.

5.3 그럼 몇으로 하나#

데몬 우선순위장점단점이럴 때
가장 높게 (configMAX_PRIORITIES - 1)타이머가 정확(tick + 11 µs). FromISR 명령이 즉시 처리모든 콜백이 사실상 최고 우선순위 코드가 된다. 콜백 하나가 1 ms 걸리면 제어 루프가 1 ms 밀린다콜백이 전부 짧은 "알리고 끝" 형태일 때. 많은 프로젝트의 기본
제어 루프 바로 아래제어 루프는 타이머 때문에 안 밀린다제어 루프가 바쁘면 타이머가 그만큼 늦는다 (예제 4의 prio 2)타이머 일이 LED·로그·텔레메트리처럼 늦어도 되는 것일 때
낮게 (1 근처)시스템에 거의 영향 없음지연이 커지고 예측 불가. link-loss 같은 안전 타이머에는 위험진단·통계용 타이머만 있을 때

실무 규칙은 이렇다. 데몬은 높게 두고, 콜백은 "기록 + notify"만 하게 만든다. 그러면 타이머의 정확도와 제어 루프의 지연을 둘 다 지킬 수 있다. 콜백이 무거워지는 순간 그 일을 태스크로 빼낸다. 데몬을 낮춰서 문제를 숨기면 예제 8(§10.1)처럼 failsafe가 늦어진다.

스케줄 가능성 분석(N1·N2, RTA)으로 말하면, 데몬은 "가장 짧은 주기의 타이머 주기"와 "가장 긴 콜백 실행 시간"을 가진 태스크 하나로 모델링해서 스케줄 가능성 분석에 넣는다. 콜백들을 모두 합한 최악 실행 시간이 그 태스크의 C다.

6. auto-reload의 정확도 — drift는 없고, 밀리면 몰아서 부른다#

6.1 소스 — 다음 만료 = 이전 만료 + period#

prvProcessExpiredTimer()(timers.c 716행)는 만료된 타이머를 리스트에서 빼고, auto-reload면 prvReloadTimer( pxTimer, xNextExpireTime, xTimeNow )를 부른 뒤 콜백을 부른다. prvReloadTimer()(697행)가 핵심이다.

두 가지를 읽을 수 있다.

  1. 다음 만료는 xExpiredTime + period — 원래 울렸어야 할 시각 + 주기다. 콜백이 몇 µs 늦게 불렸든, 데몬이 몇 ms 늦게 깨어났든 격자(grid)는 그대로다. xTaskDelayUntil()(C5)과 같은 성질이다. 누적 drift가 없다.
  2. 그 다음 만료조차 이미 지났으면(prvInsertTimerInActiveList가 pdTRUE) 콜백을 그 자리에서 부르고 한 주기 더 전진한다. 지금보다 미래가 될 때까지 반복한다. 즉 밀린 주기 수만큼 연달아 호출한다. 마지막으로 prvProcessExpiredTimer가 원래 만료분의 콜백을 한 번 더 부른다.

6.2 예제 5 — 10 ms 주기를 네 가지로 만들어 100주기 뒤 비교#

무엇을 확인하나: 매 주기 1 ms 일을 하는 10 ms 주기를 (1) auto-reload 타이머, (2) one-shot을 콜백 끝에서 다시 xTimerStart, (3) 태스크의 vTaskDelay(10), (4) 태스크의 xTaskDelayUntil(10)으로 만든다. 17 ms마다 3 ms CPU를 뺏는 높은 태스크(prio 4)가 방해한다. 데몬과 주기 태스크는 prio 2. 25주기마다 경과 tick을 찍는다.

그림 5 — 예제 5 실측. auto-reload와 xTaskDelayUntil은 100주기 뒤에도 +1 ms(기록을 1 ms 일 뒤에 하기 때문의 고정 오프셋)다. 콜백에서 다시 Start하는 one-shot과 vTaskDelay는 주기마다 "일 1 ms + 방해 지연"이 쌓여 +142 ms(14%)가 됐다.

출력에서 볼 것:

  • auto-reload = xTaskDelayUntil: 1001 tick. 남는 1은 hit()가 1 ms 일을 한 뒤에 tick을 읽기 때문의 고정 오프셋이지 누적이 아니다(25주기 때도 251).
  • one-shot 재무장 = vTaskDelay: 1142 tick, 주기당 평균 1.42 ms씩 밀렸다. 콜백 끝에서 부른 xTimerStart(t, 0)의 기준 시각은 콜백이 끝난 지금이다. 일 1 ms와 방해 지연이 매번 주기에 더해진다. vTaskDelay가 "지금부터 10"인 것과 똑같은 구조다(C5 §5).
  • 그러니 "주기적으로 무언가를 한다"는 소프트웨어 타이머는 auto-reload로 만든다. one-shot 재무장은 "이번 일이 끝난 뒤 최소 N ms 쉬고 다시"(재시도 backoff, 폴링 간격)처럼 간격이 의미일 때만 쓴다.

6.3 예제 6 — 콜백이 여러 주기를 넘겨 버리면 (catch-up)#

무엇을 확인하나: 10 ms auto-reload 타이머의 3번째 콜백만 35 ms 바쁜 대기를 한다. 각 호출의 tick, µs, 직전 호출과의 간격, 그 순간 xTimerGetExpiryTime()이 보여 주는 값을 기록한다.

그림 6 — 예제 6 실측 타임라인. 3번째 콜백이 35 ms 동안 데몬을 붙잡자 40·50·60의 만료가 밀렸고, 콜백이 끝난 65 ms에 #4·#5·#6이 2~3 µs 간격으로 연달아 불렸다. #7은 원래 격자인 70에 울렸다.

출력에서 볼 것:

  • 밀린 세 번(40, 50, 60)이 사라지지 않고 65 ms에 2~3 µs 간격으로 몰아서 불렸다. 그 뒤 #7은 70 — 격자가 그대로다(drift 없음).
  • expiry_seen 열이 소스를 그대로 보여 준다. #4와 #5는 prvReloadTimer의 while 루프 안에서 불린 것이라 그 순간 리스트 항목 값이 "이번 반복의 만료 시각"(50, 60)이다. #6은 루프가 70을 리스트에 넣는 데 성공한 뒤 prvProcessExpiredTimer가 부른 마지막 호출이라 다음 만료(70)가 보인다. 즉 몰아치기 중 콜백이 xTimerGetExpiryTime()으로 "지금이 몇 번째 만료분인가"를 알아내려 하면 값이 일관되지 않다. 필요하면 콜백이 자기 카운터를 직접 세야 한다.
  • 이 동작은 V10.4.4에서 생겼다. History.txt의 V10.4.4 항목: timers.c 리팩터로 데몬이 자기 큐에 명령을 다시 넣던 방식을 없앴고, 그 결과 "auto-reload timers that miss their intended next execution time will execute again immediately rather than executing again the next time the command queue is processed"가 됐다. 오래된 FreeRTOS 책·블로그의 설명과 다를 수 있는 부분이다.

6.4 몰아치기가 문제가 될 때#

몰아치기는 "횟수를 세는 일"(펄스 카운트, 평균 계산의 샘플 수)에는 맞고, "시간 간격이 의미인 일"에는 틀린다. 예를 들어 드론 FC에서 10 ms마다 배터리 ADC를 읽어 저역 통과 필터에 넣는 콜백이 몰아서 세 번 불리면, 같은 순간의 값 세 개가 "10 ms 간격 샘플"로 필터에 들어간다. 대처는 셋 중 하나다.

  1. 콜백 안에서 xTaskGetTickCount()로 직전 호출과의 간격을 보고, 간격이 period보다 많이 작으면 "밀린 호출"로 보고 건너뛴다.
  2. 몰아치기 자체를 막으려면 데몬을 붙잡는 원인(긴 콜백, 높은 태스크)을 없앤다 — 근본 대책.
  3. "놓치면 버린다"가 맞는 일이면 auto-reload 대신 one-shot 재무장을 쓰고 drift를 받아들인다.

Zephyr k_timer는 이 상황에서 FreeRTOS와 다르게 행동한다(§7.6).

7. Zephyr k_timer — expiry 함수는 ISR에서 돈다#

7.1 API 한 장#

Zephyr에는 데몬 태스크가 없다. k_timer의 expiry 함수는 시스템 시계 인터럽트 안에서 불린다. 공식 문서(doc/kernel/services/timing/timers.rst)도 "The function is executed by the system clock interrupt handler."라고 적고, struct k_timer 선언(include/zephyr/kernel.h 1777행)의 주석도 expiry_fn 옆에 "runs in ISR context", stop_fn 옆에 "runs in the context of the thread that calls k_timer_stop()"이라고 적는다.

API하는 일FreeRTOS 대응
K_TIMER_DEFINE(name, expiry_fn, stop_fn)정적으로 정의 + 초기화xTimerCreateStatic
k_timer_init(&t, expiry_fn, stop_fn)런타임 초기화xTimerCreate
k_timer_start(&t, duration, period)첫 만료 = duration 뒤, 그 뒤 period마다. period가 K_NO_WAIT나 K_FOREVER면 one-shotStart + ChangePeriod + reload 모드를 한 번에
k_timer_stop(&t)멈춤. 달리던 중이었으면 호출자 문맥에서 stop_fn 호출xTimerStop (단, 큐 없이 즉시)
k_timer_status_get(&t)지난 읽기 뒤 만료 횟수를 읽고 0으로없음 (콜백에서 직접 세야 함)

명령 큐가 없으니 FromISR 판도 없다. k_timer_start()·k_timer_stop()은 spinlock을 잡고 timeout 리스트를 바로 고친다. k_timer_stop()은 헤더 문서에 @isr_ok로 표시돼 있고(그 경우 stop_fn도 ISR에서 불릴 수 있어야 한다는 note가 붙어 있다), k_timer_start()도 블록하지 않는다. k_timer_status_sync()만 ISR 금지다 — 블록하므로. 대신 expiry 함수가 ISR이라 그 안에서는 아무것도 기다릴 수 없다.

7.2 tick rate부터 명시하자#

kernel/Kconfig 826행의 기본값은 이렇다.

mps2/an385 같은 QEMU 보드는 100 Hz(10 ms 해상도)가 기본이고, 실보드(tickless)는 10 kHz가 기본이다. QEMU에서 잰 숫자를 실보드에 그대로 옮기면 해상도가 100배 다르다. 이 노트의 Zephyr 앱은 prj.conf에 CONFIG_SYS_CLOCK_TICKS_PER_SEC=1000을 명시해서 FreeRTOS 예제(1 kHz)와 맞췄다. 예제 z1만 100 Hz로도 한 번 더 돌려 차이를 본다.

7.3 예제 z1 — ISR 문맥, duration의 tick 수, status_sync / get, stop fn#

무엇을 확인하나: (1) one-shot K_MSEC(10)이 몇 tick 뒤 만료되는지와 expiry 함수 안의 k_is_in_isr(), 같은 10 ms의 k_sleep()과 비교, (2) duration 5 ms · period 20 ms 타이머를 k_timer_status_sync()로 기다리는 루프, (3) 70 ms 자고 나서 k_timer_status_get(), (4) k_timer_stop()이 stop_fn을 어느 문맥에서 부르나.

prj.conf와 CMakeLists.txt(세 Zephyr 예제 공통, 프로젝트 이름만 다르다):

출력에서 볼 것:

  • expiry in ISR=1: expiry 함수는 인터럽트 문맥이다. stop_fn은 ISR=0 — k_timer_stop()을 부른 main 스레드에서 돌았다. 이미 멈춘 타이머를 다시 stop하면 stop_fn은 안 불리고, status_sync는 블록하지 않고 0을 돌려준다(소스: z_abort_timeout()이 실패하면 바로 return).
  • one-shot K_MSEC(10) = 정확히 10 tick인데 k_sleep(K_MSEC(10)) = 11 tick이다. C5 §8에서 본 Zephyr의 "+1 tick 규칙"(z_add_timeout이 상대 타임아웃에 1을 더한다)이 k_sleep에는 적용되고 k_timer의 duration에는 상쇄됐다. 이유는 §7.4.
  • 100 Hz에서 K_MSEC(5)는 올림으로 1 tick = 10 ms가 됐다(첫 sync가 9940 µs). 해상도가 10 ms면 5 ms 타이머는 없다. k_sleep(K_MSEC(10))은 2 tick = 20 ms다. tick rate를 명시하지 않고 QEMU에서 잰 숫자가 엉뚱한 이유다.
  • status_sync 루프는 20 ms 격자(4.9, 24.9, 44.9, 64.9 ms)에서 정확히 깨어났다. 스레드가 k_timer에 맞춰 주기적으로 도는 표준 패턴이다. 70 ms 동안 안 보고 있었으면 status_get이 그 사이 만료 횟수(3)를 알려 준다 — "몇 주기를 놓쳤나"를 공짜로 안다. FreeRTOS에는 이런 카운터가 없다.
  • 100 Hz에서는 status_get=4다. k_msleep(70)이 7 tick + 1 tick = 80 ms를 자서 20 ms 주기 만료가 하나 더 지나갔다. 같은 코드가 tick rate에 따라 "놓친 주기 수"까지 달라진다. user_cnt(expiry 함수가 user data로 센 횟수)도 7 대 8로 다르다.

7.4 duration에는 +1 tick이 없다 — 오히려 1 tick까지 일찍 울린다#

z_impl_k_timer_start()(kernel/timer.c 182행)의 주석과 코드다.

z_add_timeout()(kernel/timeout.c 111행)이 dticks = timeout.ticks + 1 + ticks_elapsed로 1을 더하므로, 여기서 1을 빼 두면 duration N tick은 "지금 tick이 끝난 뒤부터 센 N-1개 + 지금 tick의 남은 부분"이 된다. 즉 tick 경계에서 정확히 시작하면 N tick, tick 중간에서 시작하면 N tick보다 짧다. 커널 주석이 스스로 "unfortunate … historical"이라고 부른다.

예제 z2의 마지막 줄이 이것을 측정한다(아래 §7.6의 코드). tick 안 임의 위상 200번에서 one-shot K_MSEC(10)을 시작했다.

최소 9.017 ms — 요청보다 약 1 ms(1 tick) 짧다. C5에서 잰 k_sleep(K_MSEC(1))이 1.03~2.03 ms였던 것(항상 요청 이상)과 반대 방향이다. 실무 결론: k_timer의 duration으로 "최소 N ms는 기다린다"를 보장하려면 1 tick을 더해 준다. 반대로 period는 ISR이 만료 tick 기준으로 다시 걸기 때문에 이 문제가 없다(§9.2).

7.6 예제 z2 — k_timer 1 ms 주기 지터#

무엇을 확인하나: 1 kHz tick에서 1 ms 주기 k_timer 2001주기의 실제 주기 분포를 expiry 함수 안에서 잰다(ISR이므로 출력하지 않고 히스토그램에만 넣는다). 세 상황: 한가할 때 / 낮은 스레드(prio 5)가 CPU를 다 먹을 때 / 그 스레드가 0~300 µs씩 irq_lock()을 걸 때. 끝에 §7.4의 random-phase one-shot 측정을 붙였다.

그림 8 — 예제 z2 실측. 한가할 때 1 ms 주기는 985~1017 µs에 모인다. 다른 스레드가 irq_lock을 0~300 µs씩 걸면 717~1286 µs로 퍼진다 — 잠금 길이만큼 늦고, 다음 주기는 그만큼 짧아진다(격자는 유지).

출력에서 볼 것:

  • busy thread는 지터를 거의 안 바꿨다(985~1021 µs). expiry 함수가 ISR이라 스레드 우선순위와 무관하다. FreeRTOS 예제 4에서 데몬보다 높은 태스크가 콜백을 6 ms 밀었던 것과 대조적이다. Zephyr 쪽이 "타이머 정확도"에서는 유리하다. 대가는 그 정확도가 ISR이라는 제약과 함께 온다는 것이다.
  • irq_lock은 그대로 지터가 된다(±283 µs). 시계 인터럽트도 막히기 때문이다. 늦게 온 만료 다음 주기는 짧다(717 µs) — 커널이 다음 만료를 "실제로 늦게 불린 시각"이 아니라 "원래 만료 tick" 기준으로 다시 걸기 때문이다. 2001주기 전부 불렸다(빼먹음 없음).
  • 한가할 때도 ±15 µs가 있다. tickless 모드에서 매 만료마다 SysTick LOAD를 다시 계산하고 ISR 진입 위치가 매번 조금씩 다른 것이 원인으로 보인다(QEMU icount 기준의 값이라 실칩 지터 크기로 옮기지 말 것).

7.7 예제 z3(A) — 인터럽트를 35 ms 잠그면 10 ms k_timer는?#

FreeRTOS 예제 6에서는 밀린 만료가 몰아서 불렸다. Zephyr는 어떨까. 무엇을 확인하나: 10 ms 주기 k_timer가 도는 중 main이 25 ms 시점부터 35 ms 동안 irq_lock()을 걸고 바쁜 대기를 한다. 각 expiry의 실제 시각과 그 순간 k_uptime_ticks()가 보여 주는 값, 끝에서 실제 경과 시간과 커널 uptime을 비교한다.

출력에서 볼 것:

  • 몰아치기가 없다. 30·40·50 ms의 만료가 밀렸는데 잠금이 풀린 61 ms에 한 번만 불렸고, 그 순간 커널은 지금이 tick 30이라고 믿고 있었다.
  • 끝에서 실제 92 ms가 지났는데 커널 uptime은 64 tick이다. 커널 시계가 약 28 ms를 잃었다. 이후 만료(#4 이후)는 커널 시계 기준으로는 10 ms 격자(40, 50, 60)지만 실제 시각은 그만큼 뒤로 밀려 있다.
  • 원인은 SysTick 드라이버(drivers/timer/cortex_m_systick.c)의 전제 조건이다. 24비트 SysTick은 tickless 모드에서 LOAD를 "다음 타임아웃까지"(여기서는 최대 10 ms)로 잡고, 지나간 cycle을 elapsed()가 COUNTFLAG로 계산한다. 그 함수 주석의 전제(291행): "no more than one counter-wrap has occurred between the timer reset or the last time the function was called and until the current call". 인터럽트를 35 ms 막아 SysTick이 여러 번 wrap하면 한 번분만 셀 수 있고 나머지 wrap의 시간은 사라진다.
  • FreeRTOS 포트에서도 SysTick을 tick 주기보다 오래 막으면 같은 일이 생긴다. 놓친 SysTick들은 pending 비트 하나로 합쳐지므로 xTickCount가 그만큼 덜 올라간다 — tick 인터럽트로 시간을 세는 RTOS 공통의 성질이다(이 노트에서는 Zephyr 쪽만 실측했다). 다만 FreeRTOS 데몬은 "지금 tick"에서 밀린 auto-reload를 몰아서 부르고(예제 6), Zephyr는 시계 자체가 늦게 가니 몰아칠 것이 없다.

결론: 긴 irq_lock은 Zephyr에서 타이머 지연이 아니라 시간 손실을 만든다. 인터럽트 잠금은 1 tick보다(가능하면 훨씬) 짧게 유지한다. 몰아치기 자체는 Zephyr 소스에도 있다 — z_timer_expiration_handler()가 다음 만료를 K_TIMEOUT_ABS_TICKS(k_uptime_ticks() + 1 + next.ticks)로 걸고, sys_clock_announce 안에서 k_uptime_ticks()는 "지금 처리 중인 타임아웃의 원래 tick"을 돌려주므로, 한 번의 announce로 여러 주기가 지나갔다면 같은 루프 안에서 여러 번 불릴 수 있다. 하지만 SysTick 드라이버는 LOAD를 다음 만료까지로 잡기 때문에 시간을 잃지 않고 여러 주기가 한꺼번에 announce되는 상황을 이 보드에서는 만들지 못했다(소스로 읽은 동작, 실측 재현 못 함).

출력에서 볼 것:

  • 드론 FC의 8 kHz rate loop(125 µs)를 소프트웨어 타이머로 돌리려면 tick부터 8 kHz여야 하고, 타이머 경로만으로 CPU 8.8%를 쓴다. 게다가 이건 tick ISR의 다른 일(C5에서 잰 tick 세금)과 콜백 본체를 빼고 센 것이다. 20 kHz FOC(50 µs)는 고정 비용만 주기의 22%다.
  • 1 kHz tick에서 125 µs 주기는 0 tick이 되어 만들 수조차 없다(configASSERT). 10 kHz tick에서도 125 µs는 100 µs로 잘린다. 2.5 ms는 1 kHz tick에서 2 ms가 된다(pdMS_TO_TICKS의 내림, C5 §1.4).
  • 그래서 고속 루프는 하드웨어 타이머(또는 IMU data-ready 인터럽트)가 직접 ISR을 일으키고, ISR이 계산하거나 최고 우선순위 태스크에 notify한다(E5, E7). 소프트웨어 타이머는 그 루프를 "감시"(타임아웃)하는 쪽에 선다.

그림 9 — 주기적·지연된 일 하나를 어디에 맡길지 고르는 흐름. 정밀도가 tick보다 촘촘하면 하드웨어 타이머, 블록하거나 무거우면 전용 주기 태스크, 짧고 논블로킹이면 소프트웨어 타이머다.

8.3 드론 FC 한 대의 배치 예#

예를 들어 STM32H7급 드론 비행 제어기라면 이렇게 나눈다.

  • IMU data-ready EXTI 인터럽트(8 kHz) → 자이로 읽기 DMA 시작 → 완료 ISR이 rate-loop 태스크(최고 우선순위)에 notify. 하드웨어가 박자를 정한다.
  • ESC 출력(DShot): 타이머 + DMA. 소프트웨어 개입 없음.
  • attitude loop(1 kHz), 센서 퓨전: 주기 태스크(xTaskDelayUntil) 또는 rate-loop의 8번에 한 번.
  • 소프트웨어 타이머: RC link-loss 100 ms, GNSS 타임아웃 1 s, 상태 LED, 배터리 저속 샘플링 트리거 50 ms, arm 스위치 debounce 20 ms, 텔레메트리 송신 트리거. 데몬은 높게, 콜백은 전부 "기록 + notify".

9.2 Zephyr — kernel/timer.c, kernel/timeout.c (v4.4.2)#

struct k_timer(include/zephyr/kernel.h 1777행)의 핵심 필드는 struct _timeout timeout, _wait_q_t wait_q(status_sync로 기다리는 스레드 하나), expiry_fn, stop_fn, k_timeout_t period, uint32_t status, void *user_data다. struct _timeout(kernel_structs.h 299행)은 sys_dnode_t node, _timeout_func_t fn, int64_t dticks(CONFIG_TIMEOUT_64BIT=y, 기본) — 스레드의 k_sleep 타임아웃과 같은 구조체, 같은 리스트다.

흐름은 이렇다.

  1. k_timer_start() → z_add_timeout(&timer->timeout, z_timer_expiration_handler, duration-1). timeout 리스트는 delta list다(timeout.c 120행의 루프: 앞 항목들의 dticks를 빼 가며 자리를 찾는다). C5 §8에서 본 그 리스트다.
  2. SysTick 인터럽트 → sys_clock_isr()(drivers/timer/cortex_m_systick.c 349행)가 지난 tick 수를 계산해 sys_clock_announce(dticks).
  3. sys_clock_announce_locked()(timeout.c 223행)가 맨 앞 타임아웃의 dticks가 남은 tick 이하인 동안 반복: curr_tick += dt → 리스트에서 빼고 → lock을 풀고 t->fn(t) 호출. 이 fn이 z_timer_expiration_handler다. 아직 ISR 안이다.
  4. z_timer_expiration_handler()(timer.c 71행): period가 있으면 다음 만료를 K_TIMEOUT_ABS_TICKS(k_uptime_ticks() + 1 + (period - 1))로 절대 tick에 다시 건다. announce 중에는 elapsed()가 0이고 curr_tick이 "이번 타임아웃의 원래 tick"이므로, 늦게 불렸어도 격자 기준이다(소스 주석: "we still end up calculating the next expiration as a regular stride from where we 'should' have run"). 그다음 status += 1, expiry_fn(timer) 호출(lock 해제 상태), 마지막으로 wait_q에 스레드가 있으면 깨운다(z_ready_thread).
  5. k_timer_status_sync()는 status가 0이면 z_pend_curr(&lock, key, &timer->wait_q, K_FOREVER)로 블록한다. 그래서 ISR에서 부르면 __ASSERT(!arch_is_in_isr(), "")에 걸린다.

k_timer_stop()이 stop_fn을 부르는 조건은 z_abort_timeout()이 성공했을 때, 즉 리스트에 걸려 있던(달리던) 타이머일 때뿐이다(예제 z1의 "stop again" 줄). 그리고 wait_q의 스레드를 깨워 status_sync가 0을 돌려주게 한다.

9.3 다른 노트와의 연결#

  • C3 · C9: Tmr Svc가 첫 태스크가 되는 이유, vApplicationDaemonTaskStartupHook.
  • C5: ListItem_t 정렬 삽입, tick wrap과 리스트 두 개, xTaskDelayUntil과 auto-reload의 같은 격자 성질, Zephyr delta list와 +1 tick.
  • C6: 데몬의 블록 시간 = 다음 만료까지 → tickless idle이 잘 수 있는 시간의 상한. 타이머가 많고 짧으면 tickless의 이득이 줄어든다.
  • D7: 같은 큐를 쓰는 xTimerPendFunctionCall(FromISR), Zephyr의 k_work_delayable(스레드 문맥 타이머).
  • EL F8 §6.5: Linux의 timer wheel은 "만료를 정확히 정렬하지 않고 버킷에 대충 넣는" 대신 O(1) 삽입을 얻었다. FreeRTOS 타이머 리스트는 반대로 정확히 정렬(삽입 O(n))하고 데몬이 맨 앞만 본다. 타이머 수가 수십 개인 MCU에서는 이쪽이 맞다.

10. 실무에서 다시 보기#

10.1 드론 RC 링크 끊김 failsafe — 예제 8#

드론은 RC 수신기에서 50~500 Hz로 조종 패킷을 받는다. 패킷이 일정 시간(보통 100 ms~1 s) 안 오면 failsafe(호버링, RTL, 착륙)로 들어가야 한다. 소프트웨어 타이머로 가장 깔끔하게 만드는 방법은 "패킷이 올 때마다 one-shot 타이머를 리셋하고, 만료되면 failsafe"다. 정상일 때 타이머는 영원히 울리지 않는다. 워치독과 같은 발상이다.

무엇을 확인하나: TIMER0 인터럽트를 RC 프레임 수신 ISR로 삼아 18~22 ms 간격으로 15개의 패킷을 보낸 뒤 끊는다. ISR은 xTimerResetFromISR()로 100 ms one-shot을 미룬다. 만료 콜백은 시각을 기록하고 비행 태스크에 xTaskNotify만 한다. 350 ms부터 60 ms 동안 무거운 일(로그 flush 같은)을 하는 prio 3 태스크가 있다. 데몬 우선순위 7과 1로 돌린다.

출력에서 볼 것:

  • 데몬 prio 7: 마지막 패킷 뒤 99.84 ms에 failsafe. 100 ms보다 조금 짧은 것은 tick 양자화다. 리셋 명령의 기준 시각이 ISR 시점의 tick 값(내림)이라, 마지막 패킷이 tick 경계 뒤 x ms에 왔다면 만료는 그 패킷 뒤 (100 − x) ms + 콜백 경로 시간이 된다. 여기서는 x가 약 0.17 ms였다. 소프트웨어 타이머의 정밀도는 ±1 tick이라는 것을 그대로 보여 준다.
  • 데몬 prio 1: 112.9 ms. 만료 시각(397 ms)에 prio 3 태스크가 무거운 일을 하고 있어 데몬이 410 ms까지 못 돌았다. 100 ms를 요구사항으로 적었다면 요구사항 위반이다. 안전 기능을 맡는 타이머가 있으면 데몬 우선순위는 "그 기능의 마감을 지킬 수 있는가"로 정한다.
  • 콜백은 xTaskNotify 한 줄이다. failsafe 진입 자체(모드 전환, 모터 명령 변경)는 비행 태스크가 자기 루프에서 한다. 콜백에서 직접 모터 출력을 바꾸면 비행 태스크와 경쟁(race)이 생긴다.

실무 보강: 실제 FC는 이 타이머 하나에 기대지 않고, 비행 태스크도 매 루프에서 "마지막 패킷 시각"을 직접 비교하는 이중 감시를 둔다. 데몬이 어떤 이유로든 멈추면(예: 다른 콜백의 버그) 타이머 기반 failsafe도 같이 멈추기 때문이다. §10.3의 워치독 이야기와 같은 이유다.

10.2 버튼 · 스위치 debounce — 예제 9#

기계식 스위치는 누르는 순간 수 ms 동안 0과 1을 수십 번 오간다(bounce). 엣지 인터럽트마다 이벤트를 내면 한 번 누름이 여러 번으로 보인다. 소프트웨어 타이머 debounce는 "엣지마다 10 ms one-shot을 리셋하고, 조용해진 뒤 만료되면 그때 레벨을 한 번 읽는다"다.

무엇을 확인하나: TIMER0으로 엣지 10개(누름 바운스 5개 → 40 ms 유지 → 뗌 바운스 5개)를 흉내 내고, 엣지 ISR마다 xTimerResetFromISR(). 콜백이 몇 번, 어떤 레벨로 불리는지 본다.

출력에서 볼 것: 엣지 10개가 이벤트 2개(PRESSED, RELEASED)가 됐다. 마지막 누름 엣지가 3.4 ms에 왔으니 이론상 13.4 ms에 확정돼야 하는데 실제는 12.99 ms다 — 예제 8과 같은 tick 내림 때문이다. debounce 시간은 "최소 9 ms, 최대 10 ms"로 이해하고 바운스 최대 길이보다 넉넉히 잡는다. 엣지 인터럽트가 매우 잦은 스위치라면 ISR마다 큐에 명령을 넣는 비용(예제 7: 약 5 µs/명령)과 큐 넘침을 계산에 넣는다. 그 경우는 ISR에서 엣지 시각만 기록하고 주기 타이머(예: 5 ms auto-reload)가 샘플링하는 방식이 더 싸다.

10.3 워치독 — 타이머 콜백에서 "무조건" 차면 안 된다 — 예제 10#

흔한 초보 설계: "20 ms auto-reload 타이머를 만들고 콜백에서 IWDG를 kick한다." 이 설계는 데몬 태스크가 살아 있다는 것만 증명한다. 제어 태스크가 무한 루프나 교착에 빠져도, 데몬이 그보다 높은 우선순위로 돌고 있으면 kick은 계속된다.

무엇을 확인하나: tick hook으로 하드웨어 워치독(50 ms 안에 kick 없으면 리셋)을 흉내 낸다. 제어 태스크(prio 3)가 200 ms에 무한 루프로 멈춘다. (1) 콜백이 무조건 kick, (2) 콜백이 "모든 감시 대상 태스크가 체크인 비트를 세웠을 때만" kick하는 두 정책을 비교한다.

출력에서 볼 것: 무조건 kick은 제어 태스크가 400 ms 동안 죽어 있는데도 워치독을 계속 먹였다. 체크인 방식은 마지막 kick(200) 뒤 51 tick에 리셋했다. 체크인 비트는 "각 태스크가 자기 루프 한 바퀴를 돌았다"는 증거이고, 콜백은 그 증거가 다 모였을 때만 kick한다. 더 엄격하게 하려면 kick을 소프트웨어 타이머가 아니라 가장 낮은 우선순위 태스크(또는 idle hook)에서 하고, 체크인 검사도 거기서 한다 — 그러면 "CPU가 굶어서 낮은 태스크가 못 도는 상황"까지 잡힌다. 어느 쪽이든 핵심은 같다: 워치독을 먹이는 코드는 감시하려는 대상이 살아 있다는 것을 확인한 다음에만 먹인다.

10.4 SSD 펌웨어와 비교 — 명령 타임아웃#

Don이 SSD에서 다룬 NVMe 명령 타임아웃을 소프트웨어 타이머로 옮긴다면 선택지는 둘이다.

  1. 명령마다 타이머 하나: 동시에 수백 개가 active가 된다. FreeRTOS 타이머 리스트는 정렬 삽입(O(n))이라 명령 하나를 넣을 때마다 수백 항목을 훑는다. 게다가 시작·정지가 전부 명령 큐를 거친다. 명령 처리 경로(수 µs 단위)에 넣기엔 비싸다.
  2. 주기 타이머 하나 + 명령 테이블: 10 ms auto-reload 콜백이 "마감이 지난 명령이 있나"를 표시만 하고 처리 태스크에 notify한다. 명령 테이블에는 시작 tick만 기록한다(unsigned 뺄셈으로 wrap 안전, C5 §4.4). SSD 펌웨어가 실제로 하던 방식이고, 정밀도가 10 ms면 충분한 타임아웃(보통 수 초)에 맞는다.

Linux 커널이 수만 개의 네트워크·블록 타임아웃을 timer wheel(EL F8 §6.5)로 처리하는 이유도 같다 — 대부분의 타임아웃은 취소되는 것이 정상이고 정확한 만료 시각은 중요하지 않다. RTOS에서 개수가 많아지면 2번 패턴을 쓴다.

12. 면접에서 이렇게 말한다#

Q. "What happens if a FreeRTOS software timer callback blocks?"

A. 콜백은 타이머 서비스 태스크(데몬) 안에서 차례로 불리는 함수다. 콜백이 블록하면 데몬 자체가 잠들어 그동안 다른 모든 타이머의 만료와 명령 큐 처리가 멈춘다. 측정해 보면 다른 타이머의 최대 지연이 블록 시간과 같아지고, 깨어난 뒤 auto-reload 타이머는 밀린 만큼 연달아 불린다. 그래서 콜백은 기록하고 태스크에 notify만 한다.

A software timer callback runs inside the timer service task, one callback after another. If it blocks, the daemon itself sleeps, so every other timer and every pending timer command stalls for that long. When I measured it, a 40 ms vTaskDelay in one callback delayed a 5 ms heartbeat by exactly 40 ms, and then the heartbeat fired nine times back to back. So callbacks must be short and non-blocking — record state, notify a task, return.

꼬리 질문: "How do you size the timer task stack and priority?" → 가장 스택을 많이 쓰는 콜백 + 데몬 기본(약 124 B) + 여유, high-water mark 감시. 우선순위는 높게 두되 콜백을 짧게.

Q. "Why does xTimerStartFromISR go through a queue? What is the cost?"

A. 타이머 리스트는 데몬만 만지게 설계해서 리스트를 고칠 때 인터럽트를 끌 필요가 없다. ISR은 16바이트 명령을 큐에 넣고 끝난다. 대가는 명령 지연이다 — yield를 하면 15 µs, 빼먹으면 다음 tick까지(최대 1 tick), 데몬이 낮으면 높은 태스크가 끝날 때까지. 큐가 차면 FromISR는 즉시 실패하므로 반환값을 확인하고 큐 길이를 계산한다.

Only the daemon task touches the active timer lists, so the kernel never walks them with interrupts disabled. An ISR just posts a 16-byte command to the timer queue. The cost is command latency: about 15 µs with portYIELD_FROM_ISR in my QEMU measurement, up to one tick without it, and arbitrarily long if the daemon priority is below a busy task. If the queue is full the FromISR call fails immediately, so I check the return value and size configTIMER_QUEUE_LENGTH for the worst burst.

Q. "Do auto-reload timers drift?"

A. 안 한다. prvReloadTimer가 다음 만료를 "원래 만료 시각 + 주기"로 계산한다. 100주기 실험에서 auto-reload는 이상값과 같았고, 콜백 끝에서 one-shot을 다시 시작하는 방식은 +142 ms가 쌓였다. 단 여러 주기를 놓치면 밀린 횟수만큼 연달아 부른다 — V10.4.4부터의 동작이다.

No. The next expiry is computed from the previous expiry time, not from when the callback ran, so it behaves like vTaskDelayUntil. Over 100 periods it stayed on the grid, while re-arming a one-shot from the callback drifted by 142 ms. The catch is that if the daemon misses several periods, prvReloadTimer calls the callback once per missed period, back to back — I saw three calls within 5 µs after a 35 ms overrun.

Q. "How is Zephyr's k_timer different from a FreeRTOS software timer?"

A. Zephyr에는 데몬이 없다. expiry 함수는 시스템 시계 ISR 안에서 돈다. 그래서 스레드 부하와 무관하게 정확하지만(1 ms 주기가 985~1021 µs) 블록하면 assert에 걸린다. 대신 k_timer_status_sync로 스레드가 타이머 주기에 맞춰 돌 수 있고, status 카운터로 놓친 주기 수를 안다. 무거운 일은 workqueue로 넘긴다. duration은 +1 tick이 아니라 오히려 최대 1 tick 일찍 울린다.

Zephyr has no daemon: the expiry function runs in the system clock ISR, so it is unaffected by thread load but cannot block — calling k_sem_take with K_FOREVER there trips an assertion. Threads synchronize with k_timer_status_sync, and the status counter tells you how many periods you missed. Heavy work goes to a workqueue. One subtlety: k_timer_start subtracts a tick from the duration, so a 10 ms one-shot can fire after about 9 ms, unlike k_sleep which always waits at least the requested time.

Q. "Would you run an 8 kHz rate loop from a software timer?"

A. 아니다. 해상도가 tick이라 tick을 8 kHz로 올려야 하고, tick → 콜백 경로만 주기마다 약 11 µs(제 측정)라 CPU의 9%가 거기 쓰인다. 지터도 데몬보다 높은 태스크에 좌우된다. IMU data-ready 인터럽트나 하드웨어 타이머가 박자를 정하고, ISR이 최고 우선순위 태스크에 notify한다. 소프트웨어 타이머는 그 루프의 타임아웃 감시 같은 ms급 일에 쓴다.

No. Software timers have tick resolution, so I'd need an 8 kHz tick, and the tick-to-callback path alone cost about 11 µs per period in my measurement — almost 9% CPU before doing any work — with jitter that depends on higher-priority tasks. The loop should be paced by hardware: the IMU data-ready interrupt or a hardware timer, with the ISR notifying the highest-priority task. Software timers are for millisecond-scale housekeeping like link-loss timeouts.

Q. "How do you detect RC link loss?"

A. one-shot 타이머를 failsafe 시간(예: 100 ms)으로 두고 패킷 수신 ISR에서 xTimerResetFromISR로 계속 미룬다. 만료되면 콜백이 비행 태스크에 notify하고 비행 태스크가 failsafe로 전환한다. 측정해 보니 데몬이 높으면 99.8 ms, 낮으면 무거운 태스크 때문에 112.9 ms였다 — 안전 타이머는 데몬 우선순위가 마감을 좌우한다. 그리고 비행 루프에서도 마지막 패킷 시각을 직접 확인해 이중으로 감시한다.

A one-shot timer set to the failsafe timeout, reset from the packet-received ISR with xTimerResetFromISR. If packets stop, the timer expires and the callback notifies the flight task, which switches to failsafe mode. In my test it triggered 99.8 ms after the last packet with a high-priority daemon, but 112.9 ms with a low-priority daemon because a logging task held the CPU. So the daemon priority is part of the safety requirement, and I also check the last-packet timestamp inside the flight loop as a second line of defense.

Q. "Is it OK to kick the watchdog from a timer callback?"

A. 무조건 kick하면 안 된다. 그건 데몬이 살아 있다는 것만 증명한다. 실험에서 제어 태스크가 400 ms 동안 멈췄는데 워치독은 계속 먹었다. 감시 대상 태스크들이 루프마다 체크인 비트를 세우고, 다 모였을 때만 kick한다. 또는 최저 우선순위 태스크에서 kick해서 CPU 굶주림까지 잡는다.

Not unconditionally — that only proves the timer daemon is alive. In my test a control task hung for 400 ms while the timer kept feeding the watchdog. Each monitored task sets a check-in bit every loop, and the kicker feeds the watchdog only when all bits are set, then clears them. Kicking from the lowest-priority task additionally catches CPU starvation.

15. 요약 & 체크리스트#

소프트웨어 타이머는 tick 하나를 시계로 삼은 "알람 목록"이다. FreeRTOS에서는 타이머 서비스 태스크(Tmr Svc)가 정렬된 리스트 두 개(현재 / overflow)를 혼자 관리하고, 다른 태스크와 ISR은 16바이트 명령을 큐에 넣어 부탁한다. 명령의 기준 시각은 보낸 순간이라 늦게 처리돼도 만료는 정확하지만, 상태 변화와 FromISR 처리에는 명령 지연(yield 15 µs, 누락 시 최대 1 tick)이 있다. 콜백은 데몬 안에서 차례로 돌므로 블록하면 모든 타이머가 그만큼 늦고(예제 3), 데몬보다 높은 태스크가 돌면 그 실행 시간만큼 늦다(예제 4). 데몬 스택은 모든 콜백의 공용 스택이다(예제 11). auto-reload는 이전 만료 + 주기로 다시 걸려 drift가 없고, 밀리면 밀린 횟수만큼 몰아서 부른다(예제 5·6, V10.4.4 이후). Zephyr k_timer의 expiry 함수는 SysTick ISR에서 돌아 스레드 부하와 무관하게 정확하지만 블록할 수 없고(assert), duration은 최대 1 tick 일찍 울리며, 긴 IRQ 잠금은 지연이 아니라 시간 손실을 만든다(예제 z1~z3). 1 kHz를 넘는 제어 루프는 하드웨어 타이머가 박자를 정하고, 소프트웨어 타이머는 failsafe·debounce·LED·타임아웃처럼 짧고 논블로킹이며 ms 정밀도면 되는 일을 맡는다.
