0. 큰 그림 — 큐는 "택배", 이 노트의 도구들은 "초인종"이다#

D4의 메시지 큐는 데이터를 복사해서 옮기는 범용 도구다. 큐 하나에는 저장 영역, 보내려는 태스크 리스트, 받으려는 태스크 리스트, 잠금 카운터가 다 들어 있다. FreeRTOS의 binary semaphore조차 "항목 크기 0인 큐"라서 이 무게를 그대로 진다(A5 §7에서 queueYIELD_IF_USING_PREEMPTION 경로를 봤다). 그런데 펌웨어에서 오가는 신호의 대부분은 데이터가 아니라 "일어났다"는 사실 하나다. IMU가 샘플을 준비했다, DMA가 끝났다, 바이트가 몇 개 쌓였다, 센서 세 개가 다 준비됐다.

Don의 SSD 펌웨어로 바꿔 보면 이렇다. 호스트가 NVMe SQ tail doorbell을 쓰면 컨트롤러는 그 레지스터 하나로 "새 명령이 있다"를 안다. 명령 자체는 이미 메모리(SQ)에 있다. NAND 채널 완료는 status 레지스터의 비트로 오고, 펌웨어 메인 루프는 "채널 0~7 중 어느 비트가 섰나"를 본다. 호스트 DMA로 들어오는 데이터는 링버퍼에 쌓이고 head/tail만 움직인다. 이 노트의 네 도구가 정확히 이 세 모양이다.

  • task notification = 태스크마다 붙어 있는 doorbell 레지스터 하나(32비트). 받는 쪽이 정해져 있어서 따로 객체를 만들 필요가 없다.
  • event group / k_event = status 레지스터. 비트 여러 개, 여러 태스크가 서로 다른 비트 조합을 기다릴 수 있다.
  • stream / message buffer = 생산자 1, 소비자 1인 바이트 링버퍼 + "몇 바이트 이상 쌓이면 깨워라"(trigger level).
  • k_poll = 메인 루프의 "여러 소스 중 아무거나 준비되면" — Zephyr에서 세마포어 · FIFO · signal을 한 번에 기다린다.

그림 1 — 이 노트에서 다룰 신호 경로. 왼쪽은 신호를 만드는 쪽(대부분 ISR), 가운데는 RTOS 객체, 오른쪽은 깨어나는 태스크다. 어느 도구를 고르느냐는 "받는 쪽이 몇 개인가, 데이터가 같이 가는가, 비트 조합을 기다리나"로 정해진다(§6).

이 노트의 질문은 셋이다. (1) 의미가 어떻게 다른가 — 누가 기다릴 수 있고, 신호가 쌓이는지(count) 덮이는지(bit), ISR에서 무엇을 할 수 있는지. (2) 얼마나 가벼운가 — 같은 핑퐁을 바꿔 가며 cycle과 바이트로 잰다. (3) 커널 안에서 어떻게 구현됐나 — tasks.c, event_groups.c, stream_buffer.c, Zephyr kernel/events.c·kernel/poll.c.

실습 환경 한 줄#

QEMU mps2-an385(Cortex-M3 25 MHz) + FreeRTOS V11.3.2(ARM_CM3 포트, 랩 템플릿) / Zephyr v4.4.2(mps2/an385, 같은 가상 보드). 타이밍은 전부 ICOUNT=1(명령 1개 = 32 ns 가상 시간, 실행마다 같은 숫자) 로 쟀고, 시계는 MPS2 FPGAIO COUNTER(0x40028018, 25 MHz — 1 cycle = 40 ns = 명령 1.25개)다. QEMU icount 기준이므로 실제 칩과 절대값은 다르다(캐시 · 플래시 wait state · 버스 · 예외 스태킹 사이클을 모델링하지 않는다). 비교는 같은 조건에서의 상대값으로 읽는다. Zephyr는 qemu-system-arm을 직접 -icount shift=5,align=off,sleep=off로 돌려 FreeRTOS와 같은 시간 척도로 맞췄다.

작성 메모: 이 노트를 쓰는 동안 VM 루트 파일시스템이 ext4 오류로 emergency read-only가 되어 /var/tmp/rtos/D5를 만들 수 없었다. 그래서 빌드 산출물은 VM의 tmpfs /tmp/rtos/D5/에 두었다(재부팅하면 사라진다). 명령의 OUT= 경로만 다르고 나머지는 랩 규칙과 같다.

1. Task notification — TCB 안에 박힌 32비트 doorbell#

1.1 직관: 객체를 따로 만들지 않는 신호#

세마포어로 ISR → 태스크 신호를 보내려면 (1) 세마포어 객체를 만들고(heap에서 96 B, §2.3), (2) 태스크는 그 객체의 대기 리스트에 자기를 걸고, (3) ISR은 그 객체를 통해 대기 리스트 맨 앞의 태스크를 깨운다. 받는 태스크가 정해져 있다면 중간 객체는 필요 없다. ISR이 "IMU 태스크야, 일어나"라고 그 태스크의 TCB에 직접 쓰면 된다. 이것이 FreeRTOS의 direct-to-task notification(줄여서 task notification)이다. FreeRTOS 8.2.0에서 들어왔고, 10.4.0부터 태스크마다 값이 하나가 아니라 배열이 되었다(task.h의 Backward compatibility 설명).

비유하면 세마포어는 "공용 우편함"이고 notification은 "그 사람 책상 위 초인종"이다. 우편함은 누구나 열어 볼 수 있지만 초인종은 주인 한 명만 듣는다. 그래서 가볍고, 그래서 한계도 분명하다(§1.6).

1.2 정의: 필드 두 개와 API 묶음#

tasks.c의 TCB 정의(438~439행)에 이 두 줄이 있다.

  • configTASK_NOTIFICATION_ARRAY_ENTRIES: 태스크마다 notification이 몇 개인가. FreeRTOS.h에서 정의하지 않으면 1, 1보다 작으면 #error. 인덱스 하나당 TCB가 값 4 B + 상태 1 B만큼(정렬 포함) 커진다(§2.3에서 96 → 100 → 112 → 132 B로 확인).
  • ulNotifiedValue[i]: 32비트 값. 용법에 따라 카운터 · 비트 집합 · 값(mailbox)이 된다.
  • ucNotifyState[i]: taskNOT_WAITING_NOTIFICATION(0) · taskWAITING_NOTIFICATION(1) · taskNOTIFICATION_RECEIVED(2) (tasks.c 113~115행). 값과 별개로 "알림이 왔는데 아직 안 읽었나"를 기억한다.
  • configUSE_TASK_NOTIFICATIONS: 0으로 두면 이 필드와 API가 통째로 빠진다(태스크당 5 B 절약). 기본 1.

API는 이름이 많아 보이지만 실제 커널 함수는 아래 표 셋째 칸의 7개뿐이고 나머지는 전부 task.h의 매크로다.

1.3 상태 기계#

그림 2 — 인덱스 하나의 상태 전이. 송신자는 값을 바꾸고 상태를 무조건 RECEIVED로 만든다. 원래 상태가 WAITING이었을 때만 태스크를 ready 리스트로 옮긴다. 받는 쪽(Take/Wait)이 값을 읽고 나면 NOT_WAITING으로 돌아간다.

핵심은 값과 상태가 따로 논다는 점이다. ulTaskNotifyTake는 "값이 0인가"로 블록 여부를 정하고, xTaskNotifyWait는 "상태가 RECEIVED인가"로 정한다. 그래서 같은 인덱스를 두 방식으로 섞어 쓰면 헷갈린다(§9 표).

1.4 예제 1 — notification을 semaphore로: pdTRUE와 pdFALSE, 인덱스 독립성#

무엇을 확인하나: 받는 태스크가 아직 블록되기 전에 3번 give하면 값이 3으로 쌓이는지, ulTaskNotifyTake(pdFALSE)(counting)와 pdTRUE(binary)의 반환값 차이, 타임아웃, 인덱스 1에 준 알림이 인덱스 0 대기자를 깨우지 않는지. configTASK_NOTIFICATION_ARRAY_ENTRIES=2로 빌드했다.

출력에서 볼 것: rx가 vTaskDelay로 Blocked인 동안 받은 3번의 give는 값 3으로 쌓였다(binary semaphore였다면 2, 3번째 give는 실패한다 — D1). take(pdFALSE)는 감소 전 값 3을 반환하고 2를 남긴다. 다시 3을 더해 5가 된 뒤 take(pdTRUE)는 5를 반환하고 0으로 만든다. 즉 binary semaphore로 쓸 때도 반환값은 "그동안 몇 번 신호가 왔나"를 알려 준다 — ISR이 두 번 울렸는데 태스크가 한 번만 처리하는 버그를 반환값으로 잡을 수 있다. 타임아웃은 5 tick 뒤(tick 1에서 시작해 6) 0을 반환했다. 인덱스 1에 준 알림은 인덱스 0의 Take를 깨우지 못하고 3 tick 타임아웃 뒤 인덱스 1에서 그대로 1로 읽혔다.

1.5 예제 2 — eAction 다섯 가지와 xTaskNotifyWait의 두 마스크#

무엇을 확인하나: 값 하나를 비트 집합 · 카운터 · mailbox로 바꿔 쓰는 모습, eSetValueWithoutOverwrite가 상태를 보고 실패하는 것, xTaskNotifyWait(ulBitsToClearOnEntry, ulBitsToClearOnExit, ...)의 진입 마스크가 "대기 중인 알림이 없을 때만" 적용되는 것. 값 읽기에는 ulTaskNotifyValueClear(me, 0)(0비트 클리어 = 상태를 안 바꾸고 읽기)를 썼다. xTaskNotifyAndQuery(..., eNoAction, ...)로 읽으면 상태가 RECEIVED로 바뀌어 다음 실험을 망친다 — 처음에 그렇게 짰다가 결과가 이상해서 바꿨다.

출력에서 볼 것:

  1. eSetBits는 OR(0x1 → 0x81), eIncrement는 +1(0x82), eSetValueWithOverwrite는 무조건 덮는다(0x1234).
  2. 바로 뒤의 eSetValueWithoutOverwrite는 ret=0(pdFAIL), 값 0x1234 유지. 상태가 RECEIVED(안 읽음)라서다. 한 번 Wait로 소비한 뒤에는 값이 0이든 아니든 성공한다 — 판단 기준이 값이 아니라 상태다.
  3. wait(exit=0x0F)는 0x567f를 돌려주고 아래 4비트만 지워 0x5670을 남긴다. 이벤트 비트 용법에서 "내가 처리한 비트만 지우고 나머지는 다음 루프에 처리"하는 패턴이다.
  4. 진입 마스크 0xFFFFFFFF: 알림이 pending(RECEIVED)이면 지우지 않고 즉시 반환(0x5770, tick 0). pending이 없으면 블록 전에 값을 지운다 — 그래서 두 번째 호출은 남아 있던 0x5770을 버리고 2 tick 타임아웃 뒤 0을 반환했다. 진입 마스크는 "블록하기 전 오래된 비트를 버리는" 용도이고, 잘못 쓰면 설정됐지만 상태는 이미 소비된 비트를 잃는다.

1.6 한계 — 가벼운 대가#

  • 받는 쪽은 정확히 태스크 1개. 핸들로 지정하므로 "여러 태스크 중 아무나" 같은 일은 못 한다. 두 태스크를 동시에 깨우려면 각각에게 따로 보낸다(브로드캐스트 없음 — event group이나 k_event를 쓴다).
  • ISR은 받는 쪽이 될 수 없다. ISR에는 TCB가 없다. 보내는 것만 가능(...FromISR).
  • 보내는 쪽은 블록하지 못한다. 큐처럼 "자리가 날 때까지 기다리며 보내기"가 없다. eSetValueWithoutOverwrite가 pdFAIL을 돌려줄 뿐이고, 재시도는 보내는 쪽 몫이다.
  • 버퍼링이 없다. 값 하나(32비트)다. 카운터로 쓰면 횟수는 세지만 데이터는 못 쌓는다.
  • 인덱스 0은 공용일 수 있다. FreeRTOS V11.3.2 커널 안에서 notification을 내부적으로 쓰는 곳은 stream_buffer.c 하나뿐이다(커널 소스 전체를 grep — tasks.c·MPU 래퍼 말고 xTaskNotify 계열을 부르는 파일은 이것뿐). stream / message buffer는 블록할 때 xTaskNotifyWaitIndexed(pxStreamBuffer->uxNotificationIndex, ...)로 기다리고, 그 인덱스 기본값이 tskDEFAULT_INDEX_TO_NOTIFY = 0이다(prvInitialiseNewStreamBuffer, 1654행). V11.1.0부터 vStreamBufferSetStreamBufferNotificationIndex()로 바꿀 수 있다(History.txt "Add the ability to change task notification index for stream buffers"). 같은 태스크가 인덱스 0을 직접 쓰면서 stream buffer도 받으면, 버퍼를 기다리다 엉뚱한 알림에 깨어나거나(커널은 깬 뒤 바이트 수를 다시 확인하니 0 반환으로 끝난다) 반대로 stream buffer가 블록 전에 xTaskNotifyStateClearIndexed로 내 알림 상태를 지운다. 커널 밖 라이브러리(FreeRTOS+TCP 등)가 어느 인덱스를 쓰는지는 이 랩에 소스가 없어 확인 못 함 — 쓰는 라이브러리의 문서를 확인하고, 내 용도는 인덱스 1부터 쓰는 습관이 안전하다.

2. 얼마나 가벼운가 — 같은 핑퐁을 세 가지로 재기#

2.1 예제 3 — semaphore / notification / event group, 세 경로 × 세 설정#

무엇을 확인하나: 우선순위 3인 H가 신호를 기다리고 우선순위 1인 L이 계속 신호를 준다. (a) task→task: L이 t0를 찍고 give → H가 깨어나 선점 → H가 CYC() − t0를 잰다(API + 깨움 + PendSV 전환 전부). (b) ISR→task: L이 NVIC ISPR로 TIMER0 IRQ를 pending시키면 ISR이 FromISR로 give, portYIELD_FROM_ISR. (c) give+take: 기다리는 태스크 없이 give 하고 바로 take(0) — 전환 없는 순수 API 비용. 각 1000번 평균. MODE 0/1/2로 같은 코드를 세 객체로 바꾼다.

2.2 "45% 빠르다"는 주장 — 무엇과 비교한 숫자인가#

FreeRTOS 공식 문서는 "unblocking an RTOS task with a direct notification is 45% faster and uses less RAM than unblocking a task using an intermediary object such as a binary semaphore"라고 쓰고, 각주에서 이 45%는 V8.1.2의 binary semaphore와 비교한 값이고 V8.2.0에서 개선된 semaphore와 비교하면 약 35% 라고 밝힌다(참고 자료의 FreeRTOS task notifications 페이지). 2015년 8.2.0 릴리스 당시의 측정이다.

이 랩에서 V11.3.2로 잰 결과는 11~22%다(전환 포함 경로). 차이가 줄어든 이유를 숫자로 나누어 보면 이렇다.

  1. 전환 비용이 공통 분모다. task→task 144~242 cycle 중 PendSV 컨텍스트 스위치와 스케줄러 선택이 대부분이다(C1 예제 6에서 give → H 복귀가 약 192 cycle였다). API 차이(25~46 cycle)가 그 위에 얹히니 비율이 작아진다.
  2. semaphore 경로가 그동안 가벼워졌다. V11의 xQueueSemaphoreTake는 세마포어 전용 함수라 복사 루틴을 타지 않고, ulTaskNotifyTake도 V11.2.0(2025-03)에서 "이미 알림이 있으면 스케줄러를 정지하지 않는" 최적화가 들어갔다(History.txt "Optimize xTaskNotifyWait and ulTaskNotifyTake APIs to suspend the scheduler only if the task is not already notified"). 양쪽이 같이 좋아졌다.
  3. assert가 semaphore 쪽에 더 많이 붙어 있다. give+take에서 assert를 켜면 semaphore는 74.6 → 122.5(+48 cycle), notification은 76.9 → 88.1(+11 cycle)이다. xQueueGenericSend와 xQueueSemaphoreTake에 configASSERT가 많다. 개발 빌드(assert 켬)에서 28%로 보이던 차이가 양산 빌드에서는 0이 된다.
  4. QEMU는 메모리 접근이 공짜다. 실칩에서는 큐 구조체(84 B)를 건드리는 로드/스토어가 캐시 미스나 플래시 wait state로 더 비쌀 수 있다. 그래서 실칩에서는 차이가 이 숫자보다 클 가능성이 있지만, 이 랩에서는 보여 줄 수 없다.

면접에서는 이렇게 말하면 정직하다. "문서는 최대 45%라고 하지만 그건 2015년 semaphore 기준이다. 내가 V11에서 재 보니 깨움 + 전환 경로에서 15~20% 정도, 전환 없는 경로는 거의 같았다. 진짜 이점은 객체 RAM이 0이라는 것과, 받는 쪽이 하나로 고정되는 단순함이다."

2.3 예제 4 — 객체 하나당 RAM, 그리고 코드 크기#

무엇을 확인하나: 각 객체의 static 구조체 크기와, heap_4에서 동적 생성할 때 실제로 빠지는 바이트(블록 헤더 8 B + 8 B 정렬 포함). notification 인덱스 수에 따라 TCB가 얼마나 커지는지.

출력에서 볼 것: binary semaphore 하나가 heap에서 96 B(구조체 84 B + 헤더 8 B, 8 B 정렬), event group 40 B, 64 B stream buffer는 120 B(구조체 40 + 저장 영역 65 + 헤더 8 → 정렬)다. stream buffer는 요청 크기보다 1바이트를 더 잡는다 — head == tail을 "비었음"으로 쓰기 위해 한 칸을 비워 두는 링버퍼의 고전 기법이고, xStreamBufferGenericCreate의 주석이 "this is a quirk of the implementation"이라고 설명한다. notification은 객체가 없으니 0 B이고, 비용은 TCB 쪽에 있다: 인덱스 1 → 4로 늘리면 StaticTask_t가 96 → 112 B, 태스크 생성 시 heap 사용이 624 → 640 B가 된다. 같은 예제를 ENTRIES=2, 8로도 돌렸을 때 StaticTask_t는 각각 100 B, 132 B였다(ENTRIES=2는 예제 1의 마지막 줄에도 나온다). 인덱스 하나당 4 B 값 + 1 B 상태가 정렬되어 붙는다. 태스크 20개짜리 FC에서 semaphore 20개(1920 B)를 notification으로 바꾸면 1.9 KB를 아낀다 — STM32H7(1 MB RAM)에서는 사소하지만 32 KB짜리 Cortex-M0 센서 노드에서는 의미가 있다.

코드 크기도 같이 봤다(예제 3 noassert 빌드의 arm-none-eabi-nm --size-sort -S, 크기는 16진수 바이트).

출력에서 볼 것: semaphore 경로 함수 세 개 = 0x76 + 0x140 + 0x14a = 768 B, notification 세 개 = 0xb8 + 0xf4 + 0x104 = 688 B. 전체 text는 11812 → 11396 B로 416 B 줄었다. 단 이 랩 설정은 타이머 데몬이 큐를 쓰므로 queue.c 자체는 어차피 링크된다 — 큐를 하나도 안 쓰는 시스템이어야 queue.c 전체(수 KB)를 뺄 수 있다. event group의 xEventGroupSetBitsFromISR는 0x1c = 28 B짜리 껍데기로, 하는 일은 xTimerPendFunctionCallFromISR를 부르는 것뿐이다. 콜백 vEventGroupSetBitsCallback도 4 B — xEventGroupSetBits로 꼬리 호출(tail call)만 한다.

3. Event group — 여러 태스크가 보는 status 레지스터#

3.1 직관과 정의#

notification이 "한 사람 책상 위 초인종"이라면 event group은 게시판의 램프 24개다. 아무나 램프를 켜고 끌 수 있고, 여러 태스크가 각자 "0번과 2번이 둘 다 켜지면 깨워 줘"(wait-all) 또는 "1번이나 3번 중 하나라도 켜지면"(wait-any)을 걸어 둘 수 있다. Don의 SSD 펌웨어라면 채널별 완료 status 레지스터를 여러 백그라운드 루틴이 각자 다른 마스크로 보는 것과 같다.

event_groups.c의 구조체는 짧다(54~66행).

비트 하나와 대기 리스트 하나가 전부다(예제 4에서 32 B). 주요 API는 다음과 같다.

3.2 24비트 — 위 8비트는 커널이 쓴다#

EventBits_t는 TickType_t와 같은 타입이다(event_groups.h 113행 typedef TickType_t EventBits_t;). 대기 태스크는 자기 TCB의 xEventListItem 값 칸에 "기다리는 비트 + 제어 플래그"를 넣어 대기 리스트에 걸린다. 그 제어 플래그가 위 8비트를 차지한다.

그림 4 — event_groups.h 43~55행의 정의. 32비트 tick 설정(configTICK_TYPE_WIDTH_IN_BITS = TICK_TYPE_WIDTH_32_BITS, 이 랩 기본)에서 쓸 수 있는 비트는 0~23이다. xEventGroupSetBits는 첫 줄에서 configASSERT( ( uxBitsToSet & eventEVENT_BITS_CONTROL_BYTES ) == 0 )로 위 바이트를 막는다(예제 5 마지막 줄).

이 값 칸은 원래 우선순위 정렬용인데(C1 §2), event group 대기 리스트는 정렬하지 않고 값을 "조건 저장소"로 재활용한다. 그래서 깨울 때 vTaskRemoveFromUnorderedEventList라는 별도 함수를 쓴다.

3.3 예제 5 — 드론 FC의 센서 준비 비트, 랑데부, 제어 바이트#

무엇을 확인하나: gyro(1 tick마다) · acc(2 tick) · baro(5 tick) 세 태스크가 각자 비트를 세우고, fusion 태스크가 세 비트 wait-all + clear-on-exit로 기다린다. gyro가 그 사이 몇 번 비트를 세웠는지 같이 센다. 이어서 wait-any가 아니라 wait-all이 타임아웃되는 모양, 세 태스크가 2·4·8 tick 일한 뒤 xEventGroupSync로 만나는 랑데부, 마지막으로 bit 24를 세우려 할 때 무슨 일이 생기는지.

출력에서 볼 것:

  1. fusion은 baro가 오는 5 tick마다 깨어났다(5, 10, 15). 그 사이 gyro는 비트를 4~5번 세웠지만 fusion이 본 것은 비트 1개다. event bit는 횟수를 세지 않는다 — 세마포어나 notification의 eIncrement와 결정적으로 다르다. "샘플이 몇 개 쌓였나"가 중요하면(예: gyro FIFO 소비) 비트가 아니라 카운트나 큐를 써야 한다.
  2. clear-on-exit(pdTRUE) 덕분에 깨어난 직후 now=0x0이다. 이 클리어는 xEventGroupSetBits 안에서, 대기자를 깨우는 루프가 끝난 뒤 한꺼번에 일어난다(§7). 그래서 같은 비트를 기다리던 다른 태스크도 놓치지 않고 깨어난다.
  3. wait-all 타임아웃의 반환값은 0x3(GYRO|ACC)이다. 0이 아니므로 "뭔가 받았다"로 착각하기 쉽다 — 반드시 (b & BARO) != 0처럼 검사한다.
  4. 랑데부: 2·4·8 tick 일한 세 태스크가 모두 tick 25(시작 17 + 8)에 빠져나갔다. 가장 늦게 도착한 bit4 태스크가 먼저 출력했는데, 마지막 도착자는 블록하지 않고 바로 반환하고(같은 우선순위라 계속 실행), 앞의 둘은 그 Sync 안의 set이 깨운 것이다. xEventGroupSync가 "set 한 번 + wait 한 번"을 따로 부르는 것과 다른 점은 원자성이다. 따로 부르면 내가 set한 순간 다른 태스크가 깨어나 clear-on-exit로 비트를 지워 버려, 내 wait가 영원히 안 끝나는 경쟁이 생긴다.
  5. EventBits_t는 32비트, 제어 마스크 0xff000000. bit 23은 되고 bit 24는 event_groups.c:563의 configASSERT에 걸렸다.

3.4 예제 6 — xEventGroupSetBits 비용은 대기자 수에 비례한다#

무엇을 확인하나: xEventGroupSetBits는 대기 리스트를 처음부터 끝까지 훑으며 각 태스크의 조건을 검사한다. 대기 태스크를 0~32개로 늘리며 (a) 아무도 안 기다리는 비트를 세울 때(훑기만), (b) 전원이 기다리는 비트를 세울 때(전원 깨움) set 호출 하나의 시간을 잰다. 측정 태스크(우선순위 5)가 대기자(우선순위 1)보다 높아서 set 안에서 전환은 일어나지 않는다 — 순수하게 set 호출 비용이다.

그림 5 — 예제 6 실측. 맞는 비트가 없어도 대기자 하나당 8 cycle씩 늘고, 전원을 깨우면 대기자 하나당 약 65 cycle(ready 리스트로 옮기기)씩 는다. 32개를 깨우는 set 하나가 2145 cycle = 86 us(icount 기준)다.

출력에서 볼 것: (328 − 69) / 32 = 8.1 cycle/대기자(훑기), (2145 − 69) / 32 = 64.9 cycle/대기자(깨움). 완전히 선형이다. 이 O(n)이 스케줄러 정지(vTaskSuspendAll) 안에서 돈다는 점이 중요하다. 인터럽트는 막지 않으니 ISR 지연에는 영향이 없지만, 그동안 더 높은 우선순위 태스크가 깨어나도 전환이 미뤄진다. 그리고 ISR에서는 스케줄러를 정지할 수 없다 — ISR에서 이 루프를 돌리려면 인터럽트를 막고(크리티컬 섹션) 돌려야 하는데, 그러면 인터럽트 마스킹 구간이 대기자 수에 비례하게 된다. FreeRTOS가 이것을 거부한 결과가 다음 절이다.

3.5 xEventGroupSetBitsFromISR는 왜 타이머 데몬으로 미루나#

event_groups.c 817~831행이 전부다.

ISR은 "이 event group에 이 비트를 세워 줘"라는 요청을 타이머 명령 큐에 넣을 뿐이다(xTimerPendFunctionCallFromISR, D7에서 자세히). 실제 set은 타이머 서비스 태스크(daemon, D6)가 vEventGroupSetBitsCallback → xEventGroupSetBits로 한다. event_groups.h의 주석이 이유를 그대로 적는다: set은 "not a deterministic operation because there are an unknown number of tasks that may be waiting", 그래서 인터럽트나 크리티컬 섹션 안에서 하지 않는다. 대가는 세 가지다.

  • 지연이 늘어난다: 큐 send(ISR) → 데몬 깨어남 → 콜백 → set → 대상 태스크 깨어남. 전환이 한 번 더 있다.
  • 데몬 우선순위에 묶인다: 데몬보다 높은 우선순위 태스크가 바쁘면 콜백이 그만큼 밀린다.
  • 실패할 수 있다: 타이머 명령 큐(configTIMER_QUEUE_LENGTH, 이 랩은 10)가 꽉 차면 pdFAIL. 반환값을 검사해야 한다.
  • 그리고 configUSE_TIMERS = 1과 INCLUDE_xTimerPendFunctionCall = 1이 필수다. 함수 정의 전체가 #if ( ( INCLUDE_xTimerPendFunctionCall == 1 ) && ( configUSE_TIMERS == 1 ) )(833행) 안에 있다.

3.6 예제 7 — 직접 알림 vs event group FromISR, 데몬 우선순위 바꾸기#

무엇을 확인하나: 우선순위 4인 H가 신호를 기다린다. 우선순위 3인 M이 IRQ를 트리거하고 100 us(2500 cycle) 바쁘게 일한 뒤 1 tick 쉰다(드론 FC라면 자세 추정 같은 중간 우선순위 계산). ISR이 (1) vTaskNotifyGiveFromISR로 H를 직접 깨우는 경우와 (2) xEventGroupSetBitsFromISR로 데몬에 위임하는 경우를, 데몬 우선순위 configTIMER_TASK_PRIORITY(TPRI)를 7, 5, 2, 1로 바꿔 가며 200번 잰다.

그림 6 — TPRI ≥ M일 때의 타임라인. ISR은 타이머 큐에 넣기만 하고, 데몬이 깨어나 set 콜백을 돌린 뒤에야 H가 실행된다. TPRI가 M보다 낮으면 데몬 칸이 M의 바쁜 구간 뒤로 밀린다.

그림 7 — 예제 7 실측(QEMU icount). 직접 알림 202 cycle(8 us), 데몬 경유 879 cycle(35 us), 데몬이 M보다 낮으면 3030 cycle(121 us) = M의 바쁜 구간 2500 cycle이 통째로 더해진다.

출력에서 볼 것: 데몬 경유는 데몬 우선순위가 충분히 높아도 직접 알림의 4.4배다(879 / 202). 데몬이 M보다 낮으면 지연이 M의 실행 시간에 종속된다 — 이것은 우선순위 역전(D3)과 같은 모양이다: H(4)가 기다리는 일을 데몬(2)이 쥐고 있고, 그 사이 M(3)이 돈다. min과 max가 거의 같은 것은 icount가 결정적이기 때문이고, 3277은 SysTick이 끼어든 경우다. 결론: ISR → 태스크 신호에 event group FromISR를 기본으로 쓰지 말 것. 받는 태스크가 하나면 xTaskNotifyFromISR(h, BIT, eSetBits, &w)가 같은 "비트" 의미를 데몬 없이 준다. event group이 꼭 필요하면(여러 태스크가 서로 다른 조합을 기다림) 데몬 우선순위를 신호를 받는 태스크보다 높게 둔다 — 템플릿 기본값 configMAX_PRIORITIES − 1이 그 이유다.

configUSE_TIMERS 0으로 빌드하면 이렇게 된다(D5_NOTIMERS 정의, MODE=2).

함수 선언 자체가 사라져 암시적 선언 오류가 나고, timers.c는 INCLUDE_xTimerPendFunctionCall이 1인데 타이머가 꺼졌다고 #error를 낸다. 타이머를 끄는 저전력 · 초소형 설정에서는 event group을 ISR에서 쓸 방법이 없다는 뜻이다.

4. Stream buffer · message buffer — 1 writer 1 reader 바이트 링#

4.1 직관: SSD의 호스트 데이터 링, UART의 RX FIFO#

stream buffer는 Don이 수없이 짠 SPSC(single-producer single-consumer) 링버퍼에 "몇 바이트 이상 쌓이면 소비자를 깨운다"를 붙인 것이다. 생산자는 head만, 소비자는 tail만 움직이므로 둘 사이에 락이 필요 없다(D8의 lock-free SPSC와 같은 원리). 그 대신 생산자가 둘이면 head를 두 곳에서 움직이게 되어 깨진다(§4.5).

그림 8 — StreamBuffer_t(40 B)와 저장 영역이 한 번에 할당된다(예제 4: 64 B 버퍼 → heap 120 B). 위는 stream buffer의 링, 아래는 message buffer가 메시지마다 붙이는 길이 접두.

  • stream buffer: 바이트 흐름. 경계가 없다. 10바이트를 두 번 보내면 받는 쪽은 7 + 13으로 받을 수도 있다. UART RX, 오디오 샘플, 로그 바이트에 맞다.
  • message buffer: stream buffer 위에 길이 접두(length prefix) 를 붙인 것. 보낸 단위 그대로 받는다. 가변 길이 패킷(MAVLink 프레임, CAN-FD 프레임, 명령 패킷)에 맞다. 구현은 같은 stream_buffer.c이고 ucFlags의 sbFLAGS_IS_MESSAGE_BUFFER 비트만 다르다.
  • stream batching buffer(V11.1.0에서 추가, xStreamBatchingBufferCreate): reader가 비어 있지 않은 버퍼를 읽어도 trigger level을 넘을 때까지 블록한다. 일반 stream buffer는 1바이트라도 있으면 즉시 반환한다.
  • configUSE_STREAM_BUFFERS(기본 1)로 통째로 뺄 수 있다.

trigger level은 송신 쪽에서만 쓰인다. xStreamBufferSend의 끝부분이다.

즉 "쓴 뒤 쌓인 바이트 수 ≥ trigger면 기다리는 reader를 깨운다". reader 쪽 xStreamBufferReceive는 trigger를 보지 않고 "0바이트면 블록"만 한다(batching이면 "trigger 이하면 블록"). 그래서 reader가 일을 마치고 다시 Receive를 불렀을 때 그사이 몇 바이트가 들어와 있으면 trigger 미만이라도 그대로 가져간다 — 예제 8의 stream 결과에서 평균 덩어리가 trigger보다 약간 작은 이유다.

reader가 깨는 또 하나의 길은 타임아웃이다. trigger가 8인데 7바이트만 오고 끝나면(문장 끝, 링크 끊김) reader는 타임아웃까지 기다린 뒤 7바이트를 받는다. UART라면 "idle line" 검출(E6)이 이 역할을 하드웨어로 한다.

"단일 writer · 단일 reader" 가정이 소스에 박힌 곳: StreamBuffer_t에는 기다리는 태스크를 담는 칸이 리스트가 아니라 핸들 하나씩(xTaskWaitingToReceive, xTaskWaitingToSend)이다. 블록하기 전에 configASSERT( pxStreamBuffer->xTaskWaitingToReceive == NULL )(1119행, 주석 "Should only be one reader")와 configASSERT( pxStreamBuffer->xTaskWaitingToSend == NULL )(주석 "Should only be one writer")로 검사한다. 그리고 prvWriteBytesToBuffer는 크리티컬 섹션 없이 memcpy 후 xHead를 갱신한다 — 쓰는 쪽이 하나라는 가정 덕분에 큐보다 가볍다. 깨움도 큐처럼 이벤트 리스트가 아니라 task notification(sbSEND_COMPLETED → xTaskNotifyIndexed(..., eNoAction))이다.

4.3 예제 8 — UART GNSS NMEA 수신: trigger level을 1~82로 바꾸기#

무엇을 확인하나: 115200 baud 8N1 UART는 바이트당 86.8 us다(10비트 / 115200). TIMER0를 25 MHz / 2170 = 11521 Hz로 돌려 RX 인터럽트를 흉내 내고, ISR이 NMEA GGA 문장을 한 바이트씩 xStreamBufferSendFromISR로 넣는다. 파서 태스크는 xStreamBufferReceive로 받고 덩어리마다 20 us 파싱 비용을 쓴다. 2048 바이트를 받는 동안 깨어난 횟수와 덩어리 첫 바이트가 기다린 시간(도착 시각을 ISR이 링에 기록)을 trigger level별로, stream과 batching 두 종류로 잰다. QEMU의 CMSDK UART는 baud 타이밍을 모델링하지 않아 실제 UART 대신 타이머로 바이트 간격을 만들었다.

그림 9 — 예제 8 실측. 깨움 수(왼쪽 log 축)는 trigger에 반비례하고, 첫 바이트가 기다린 평균 시간(오른쪽 축)은 trigger × 86.8 us에 비례한다. "CPU 부담"과 "지연"을 맞바꾸는 손잡이다.

출력에서 볼 것:

  1. trigger 1이면 바이트마다 깨어나 2048번, 지연 17 us(ISR → 전환 → 파서). trigger 16이면 129번, 지연 1.3 ms. trigger 82(NMEA 최대 문장 길이)면 26번, 6.8 ms다. 깨움 하나가 전환 + API로 약 200 cycle(8 us, §2)이니 trigger 1은 초당 11521번 × 8 us = CPU의 9%를 깨움에만 쓴다. 실제 칩(H7 480 MHz)에서는 비율이 훨씬 작지만, 921600 baud GNSS나 여러 UART가 겹치면 무시할 수 없다.
  2. stream은 평균 덩어리가 trigger보다 약간 작고(16 → 15.8, 82 → 78.7) batching은 trigger + 1이다(16 → 16.9, 1 → 2.0). batching은 "초과할 때" 깨우기 때문이다(prvBytesInBufferMeetTriggerLevel의 batching 분기 xBytesInBuffer > pxStreamBuffer->xTriggerLevelBytes). V11.3.2 History.txt에 "Fix batching stream buffers to unblock a receiver only after the buffered byte count exceeds, rather than reaches, the trigger level"이 있다 — 이 동작은 V11.3.x에서 고쳐진 것이다.
  3. 지연은 거의 정확히 (trigger − 1) × 86.8 us + 17 us다: trigger 16 → 15 × 86.8 + 17 = 1319 us(측정 1310). 계산으로 예측 가능하다는 것이 이 도구의 장점이다.
  4. 실무 선택: NMEA처럼 "문장 하나가 와야 의미 있는" 데이터는 trigger를 문장 길이 근처(수십 바이트)로 두고 타임아웃(또는 UART idle 인터럽트에서 xStreamBufferSendCompletedFromISR로 강제 깨움)으로 꼬리를 처리한다. MAVLink 명령처럼 지연이 중요한 링크는 trigger를 작게 둔다.

4.4 예제 9 — message buffer의 길이 접두, 작은 수신 버퍼, batching의 꼬리#

무엇을 확인하나: 64 B message buffer에 3 B, 10 B 메시지를 넣었을 때 줄어드는 공간, 다음 메시지 길이 조회, 2 B짜리 수신 버퍼로 받으면 어떻게 되나, 절대 안 들어가는 크기를 블록하며 보내면, 그리고 trigger 8인 stream / batching buffer에 5 B만 있을 때 Receive(…, 3 tick)의 차이. configMESSAGE_BUFFER_LENGTH_TYPE을 기본(size_t, 4 B)과 uint8_t로 두 번 돌린다.

출력에서 볼 것:

  1. 3 B 메시지는 7 B, 10 B 메시지는 14 B를 썼다 — 길이 접두 sbBYTES_TO_STORE_MESSAGE_LENGTH = sizeof( configMESSAGE_BUFFER_LENGTH_TYPE ) = 4 B. uint8_t로 바꾸면 접두가 1 B가 되어 4 B, 11 B만 쓴다. 메시지가 255 B를 넘지 않는 CAN · 짧은 명령 채널이라면 uint8_t로 바이트를 아낄 수 있다(대신 255 B 초과 메시지는 보낼 수 없다).
  2. 수신 버퍼가 메시지보다 작으면 0을 반환하고 메시지는 그대로 남는다(next=3). 잘라서 주지 않는다. 받는 쪽은 xMessageBufferNextLengthBytes로 길이를 먼저 확인하거나 최대 크기 버퍼를 쓴다. 0을 "비었음"으로 해석하는 루프는 여기서 영원히 같은 메시지를 못 꺼낸다.
  3. 61 B + 접두 4 B = 65 B > 최대 63 B(길이 64 − 1)이면 기다려도 소용없으니 즉시 0을 반환한다(10 tick 블록을 요청했지만 0 tick). xStreamBufferSend의 "The message would not fit even if the entire buffer was empty, so don't wait for space" 분기다. uint8_t 접두면 62 B라 들어간다.
  4. batching buffer의 꼬리 함정: trigger 8에 5 B가 있을 때 stream buffer는 즉시 5 B를 주지만, batching buffer는 3 tick 타임아웃 뒤에도 0을 반환하고 5 B를 버퍼에 남긴다. 타임아웃 뒤 재확인 조건도 "trigger 초과"이기 때문이다(if( xBytesAvailable > xBytesToStoreMessageLength )에서 batching이면 그 값이 trigger). 데이터 흐름이 끊기면 마지막 조각은 다음 바이트가 올 때까지 못 꺼낸다. 처음 예제 8을 "2048 B 보내고 멈추는" ISR로 짰을 때 batching 실행이 끝나지 않았던 이유가 이것이다 — 그래서 예제 8은 ISR이 계속 보내도록 바꿨다.

4.5 예제 10 — single-writer · single-reader 가정을 깨면#

무엇을 확인하나: (A) 태스크와 ISR 두 writer가 같은 message buffer에 8 B 메시지("AAAAAAAA", "BBBBBBBB")를 넣고, 태스크가 꺼내며 "길이 8, 같은 글자 8개"인지 검사한다. ISR은 TIMER0로 약 40 us마다 쏜다. GUARD=1이면 태스크 쪽 send를 taskENTER_CRITICAL()로 감싼다. (B) 빈 버퍼에 reader 두 개가 블록하면.

출력에서 볼 것:

  1. GUARD=0: 메시지 35085개를 넣었는데 온전한 것 30241개, 깨진 것 160개, 나머지(4684개)는 길이 접두가 망가지면서 사라졌다. 태스크의 prvWriteMessageToBuffer가 길이를 쓰고 xHead를 갱신하기 전에 ISR이 같은 xHead에서 자기 메시지를 써 버리기 때문이다. assert도 경고도 없다 — 조용히 데이터가 깨진다. 블록하지 않는 send 두 개는 커널이 검사할 방법이 없다.
  2. GUARD=1: 태스크 쪽 send를 크리티컬 섹션으로 감싸면(이 ISR의 우선순위 0x40은 BASEPRI 0x20으로 가려진다) 37671개 전부 온전하다. stream_buffer.h 머리 주석도 같은 처방을 한다: "If there are to be multiple different writers then the application writer must serialize calls to writing API functions ... One way to achieve such serialization ... is to place each API call inside a critical section and use a block time of 0." 그 순간 stream buffer는 "락 없는 가벼운 도구"가 아니게 된다 — 여러 writer라면 큐(D4)가 맞는 도구다.
  3. (B) reader 두 개: 두 번째 reader가 블록하려는 순간 stream_buffer.c:1119의 configASSERT( pxStreamBuffer->xTaskWaitingToReceive == NULL )에 걸렸다. 블록하는 reader / writer 중복은 assert가 잡아 준다(assert를 끈 양산 빌드에서는 먼저 기다리던 태스크의 핸들이 덮어써져 그 태스크가 영원히 안 깨어난다).

4.6 sbSEND_COMPLETED — 멀티코어(AMP)에서 코어 사이 링으로 쓰기#

stream_buffer.c 146~160행의 기본 sbSEND_COMPLETED는 스케줄러를 정지하고 xTaskWaitingToReceive에 xTaskNotifyIndexed(..., eNoAction)을 보내는 매크로다. #ifndef로 감싸 있어 FreeRTOSConfig.h에서 재정의할 수 있다. 용도는 비대칭 멀티코어(AMP)다. 예를 들어 STM32H745(Cortex-M7 + M4)나 i.MX RT1170에서 각 코어가 자기 FreeRTOS를 돌리고, 공유 SRAM에 stream buffer를 하나 둔다. writer 코어에서는 상대 코어의 reader 태스크 핸들이 의미가 없으니, sbSEND_COMPLETED를 "상대 코어에 하드웨어 인터럽트(MU / HSEM / IPCC)를 건다"로 바꾸고, 받는 코어의 그 ISR에서 xStreamBufferSendCompletedFromISR(sb, &w)를 불러 reader를 깨운다. V10.5.0(2022-09)부터는 버퍼마다 콜백을 따로 줄 수 있다: configUSE_SB_COMPLETED_CALLBACK 1 + xStreamBufferCreateWithCallback(size, trigger, pxSendCompletedCallback, pxReceiveCompletedCallback) — 일부 버퍼는 코어 간, 일부는 코어 안에서 쓰는 구성이 가능하다. 이 랩의 듀얼 코어 보드(mps2-an521)에서 실제로 돌리는 것은 C10(SMP)·후속 모듈 몫으로 남긴다. FreeRTOS 공식 데모의 AMP 예제가 이 방식을 쓴다(참고 자료 — 데모 소스는 이 랩에 없어 확인 못 함).

5. Zephyr — k_event와 k_poll#

Zephyr에는 FreeRTOS task notification에 직접 대응하는 것이 없다(A5 §8의 이식 주의점). 용도별로 k_sem(카운트, D1), k_event(비트), k_poll(여러 소스)을 고른다. k_fifo·k_msgq·k_pipe·zbus는 D10에서 다룬다 — 여기서는 k_poll이 그것들을 "기다리는" 쪽만 본다.

5.2 예제 11 — k_event의 post / set / wait / reset / safe, ISR post#

무엇을 확인하나: 두 스레드가 같은 비트를 기다릴 때 post 한 번에 둘 다 깨는지(브로드캐스트), post(OR)와 set(덮어쓰기)의 차이, wait가 비트를 소비하지 않는 것, k_event_wait_safe의 원자적 소비, reset=true가 기존 비트를 잃게 하는 것, k_timer 콜백(ISR 컨텍스트)에서 직접 post. mps2/an385 보드의 기본 tick이 100 Hz(CONFIG_SYS_CLOCK_TICKS_PER_SEC=100, 빌드의 .config에서 확인)라서 처음 돌렸을 때 2 ms 타이머가 10 ms에 울렸다 — prj.conf에서 1000으로 올렸다.

출력에서 볼 것(QEMU는 timeout 3이 끝낸다 — stderr의 종료 메시지는 이 출력에 없다):

  1. post 한 번에 waiter1, waiter2가 둘 다 깨었다. k_event는 기본이 브로드캐스트이고, _safe가 아닌 wait는 비트를 소비하지 않으니 post 뒤에도 0x20이 남는다.
  2. post는 OR(0x20 → 0x21), set은 덮어쓰기(→ 0x2). set으로 "현재 상태"를 통째로 표현하는 용법(예: 링크 상태 비트 묶음)과 post로 "사건"을 쌓는 용법을 구분한다.
  3. wait_all은 GYRO가 없어 타임아웃 0을 반환했다. Zephyr는 타임아웃이면 0을 준다(FreeRTOS는 그 순간의 비트 값을 준다 — 예제 5의 0x3과 다르다).
  4. timer ISR이 2 ms 뒤 BARO를 post하자 wait_all이 정확히 2 ms에 0x7로 끝났다.
  5. k_event_wait_safe(G|A)는 0x3을 받고 그 두 비트만 지워 0x4를 남겼다. 반면 k_event_wait(BARO, reset=true)는 대기 전에 전부 지워서 이미 서 있던 BARO까지 잃고 3 ms 타임아웃으로 0을 반환했다. kernel.h 주석이 _safe 판을 "mitigates the need for calling k_event_clear, or passing a reset argument, since doing so may result in lost event information"이라고 설명하는 이유다. 신호를 놓치면 안 되는 경로(센서 준비, DMA 완료)는 _safe를 쓴다.

5.3 k_poll — 서로 다른 객체 여러 개를 한 번에 기다리기#

k_poll은 POSIX poll()의 RTOS판이다. struct k_poll_event 배열을 넘기면 그중 하나라도 준비되면 반환한다. CONFIG_POLL=y가 필요하다. 기다릴 수 있는 종류(kernel.h 6540행 근처, v4.4.2):

  • K_POLL_TYPE_SEM_AVAILABLE — k_sem 카운트 > 0
  • K_POLL_TYPE_DATA_AVAILABLE = K_POLL_TYPE_FIFO_DATA_AVAILABLE — k_queue / k_fifo / k_lifo가 비어 있지 않음
  • K_POLL_TYPE_MSGQ_DATA_AVAILABLE — k_msgq에 메시지 있음
  • K_POLL_TYPE_PIPE_DATA_AVAILABLE — k_pipe에 데이터 있음
  • K_POLL_TYPE_SIGNAL — k_poll_signal_raise()로 올린 signal (signal은 값 하나 result를 실어 보낼 수 있다)
  • K_POLL_TYPE_IGNORE — 배열 칸 비활성

중요한 성질 세 가지가 kernel/poll.c에 그대로 있다.

  1. k_poll은 가져가지 않는다. is_condition_met는 k_sem_count_get(event->sem) > 0U처럼 보기만 한다. 반환 후 k_sem_take(…, K_NO_WAIT)나 k_fifo_get(…, K_NO_WAIT)로 직접 꺼내야 하고, 그 사이 다른 스레드가 먼저 가져갈 수 있다(그래서 꺼내기는 반드시 K_NO_WAIT + 실패 처리).
  2. state는 누적되고 커널이 지워 주지 않는다. set_event_ready는 event->state |= state;다. 다음 k_poll 전에 event.state = K_POLL_STATE_NOT_READY로 사용자가 되돌려야 한다. signal도 k_poll_signal_reset()으로 사용자가 내려야 한다(kernel.h: "stays set until the user sets it back to 0 with k_poll_signal_reset()").
  3. 한 객체에 poller가 여럿이면 깨움은 하나에게만 간다. z_impl_k_poll_signal_raise는 sys_dlist_get(&sig->poll_events)로 등록된 poll event를 하나만 꺼내 신호를 준다. add_event가 우선순위 순으로 넣으므로 가장 높은 우선순위 poller다. 다른 poller는 signal이 서 있는데도 계속 잔다.

5.4 예제 12 — sem · fifo · signal 셋을 하나의 k_poll로, 그리고 함정 둘#

무엇을 확인하나: 1 ms마다 timer ISR이 sem give → fifo put → signal raise(result 42)를 차례로 한다. 메인은 k_poll로 셋을 기다리고 준비된 것을 꺼낸다. (A) 매 라운드 state를 NOT_READY로 되돌리는 올바른 코드, (B) 되돌리지 않는 코드, (C) 우선순위 3과 4인 두 스레드가 같은 signal을 poll할 때 raise 한 번의 결과.

출력에서 볼 것:

  1. (A) 라운드마다 준비된 칸 하나만 state가 서 있고(0x2 = SEM_AVAILABLE, 0x4 = FIFO_DATA_AVAILABLE, 0x1 = SIGNALED) 꺼내기가 모두 성공했다.
  2. (B) state를 안 되돌리면 라운드 1에서 sem 칸이 이전 라운드의 0x2를 그대로 들고 있어 코드가 sem을 또 꺼내려 하고 k_sem_take가 −16(-EBUSY)으로 실패했다. 라운드 2에서는 fifo 칸도 낡은 상태라 k_fifo_get이 NULL. 이런 코드가 실무에서는 "가끔 NULL 포인터 역참조" HardFault로 나타난다.
  3. (C) raise 한 번에 poller1(우선순위 3)만 깨어났고, poller2(우선순위 4)는 signal이 서 있는데도 30 ms 타임아웃(rc=-11 = -EAGAIN)까지 잤다. 브로드캐스트가 필요하면 k_poll_signal이 아니라 k_event를 쓴다.

7. RTOS 커널 안에서는 무슨 일이 일어나나#

그림 11 — 이 노트의 개념이 구현된 함수들. 위 두 칸(notification, stream buffer)은 서로 이어져 있다 — stream buffer가 깨움에 notification을 쓴다.

7.1 notification: 이벤트 리스트를 거치지 않는 깨움#

xTaskGenericNotify(tasks.c 8010행~)의 뼈대는 이렇다(위에서 본 소스 그대로, 주석 줄임).

semaphore give(xQueueGenericSend)와 비교하면 차이가 보인다. semaphore는 (1) 큐 구조체의 uxMessagesWaiting 검사와 증가, (2) xTasksWaitingToReceive 이벤트 리스트에서 맨 앞 태스크를 꺼내는 xTaskRemoveFromEventList, (3) 그 태스크를 delayed 리스트에서도 빼고 ready로 — 리스트 두 개를 건드린다. notification은 이벤트 리스트가 없으니(xEventListItem이 어디에도 안 걸려 있다는 assert가 그 증거) 상태 리스트 하나만 옮긴다. 받는 쪽 ulTaskGenericNotifyTake(7797행~)는 값이 0이고 기다릴 의사가 있을 때만 vTaskSuspendAll + 크리티컬 섹션 안에서 ucNotifyState = taskWAITING_NOTIFICATION으로 표시하고 prvAddCurrentTaskToDelayedList로 블록한다. 주석이 "We MUST enter a critical section to atomically check if a notification has occurred and set the flag ... If we do not do so, a notification sent from an ISR will get lost"라고 lost-wakeup을 설명한다.

ISR판 vTaskGenericNotifyGiveFromISR(8316행~)는 portASSERT_IF_INTERRUPT_PRIORITY_INVALID()로 ISR 우선순위를 검사(E1)하고 taskENTER_CRITICAL_FROM_ISR로 들어간다. 스케줄러가 정지돼 있으면(uxSchedulerSuspended != 0) ready 리스트 대신 xPendingReadyList에 넣는다(C1). vTaskSuspend·vTaskResume 쪽에도 notification 대기 상태를 정리하는 루프가 있다(2620, 3239행 근처: 알림을 기다리다 suspend된 태스크의 상태를 NOT_WAITING으로 되돌린다).

7.2 event group: 정렬 안 된 리스트 + 스케줄러 정지#

xEventGroupSetBits(547행~)는 vTaskSuspendAll() → 비트 OR → 대기 리스트 전체를 돌며 각 항목 값에서 제어 바이트(eventEVENT_BITS_CONTROL_BYTES)를 떼어 조건 검사 → 맞으면 vTaskRemoveFromUnorderedEventList(pxListItem, uxEventBits | eventUNBLOCKED_DUE_TO_BIT_SET)로 깨우고 "깨어날 때의 비트 값"을 항목 값에 넣어 준다 → 루프가 끝난 뒤 clear-on-exit 비트를 한꺼번에 지움 → xTaskResumeAll(). 깨어난 태스크는 xEventGroupWaitBits 안에서 uxTaskResetEventItemValue()로 그 값을 읽어 eventUNBLOCKED_DUE_TO_BIT_SET이 있으면 "비트로 깨어남", 없으면 "타임아웃"으로 판단한다. 인터럽트를 막지 않는 대신 O(n)을 스케줄러 정지 아래 두는 설계이고, 그래서 ISR에서는 xTimerPendFunctionCallFromISR로 데몬에 미룬다(예제 7). 콜백 vEventGroupSetBitsCallback은 4 B짜리 b.w xEventGroupSetBits 한 줄이다(objdump로 확인).

7.3 stream buffer: 핸들 두 칸 + notification#

StreamBuffer_t(233~252행)에는 대기 리스트가 없고 xTaskWaitingToReceive·xTaskWaitingToSend 핸들 두 칸뿐이다. 블록은 "핸들 칸에 나를 적고(assert로 비어 있는지 확인) → xTaskNotifyWaitIndexed(uxNotificationIndex, 0, 0, NULL, xTicksToWait)", 깨움은 sbSEND_COMPLETED / sbRECEIVE_COMPLETED 매크로가 xTaskNotifyIndexed(…, eNoAction). 바이트 복사는 prvWriteBytesToBuffer(1488행~)가 링 끝에서 두 번에 나눠 memcpy하고, 이것을 감싸는 prvWriteMessageToBuffer(1012행~)가 message buffer면 길이 접두를 먼저 쓴다. 쓰기 경로에는 크리티컬 섹션이 없다(블록 판단 부분에만 있다) — 이것이 SWSR 가정의 대가이자 이득이다.

7.4 Zephyr: 대기 큐 훑기와 poller 등록#

k_event_post_internal(kernel/events.c 178행~)은 k_spin_lock → 새 값 계산 → z_sched_waitq_walk(&event->wait_q, event_walk_op, …)로 대기 스레드마다 are_wait_conditions_met(any면 current & desired, all이면 전부 일치) 검사 → 맞으면 z_abort_thread_timeout + z_sched_wake_thread_locked → 소비된 비트(K_EVENT_OPTION_CLEAR, 즉 _safe 판)를 지움 → z_reschedule. CONFIG_WAITQ_SCALABLE(rbtree 대기 큐)이면 훑는 동안 지울 수 없어서 리스트를 따로 모았다가 깨운다(event_post_walk_op). 이 랩 빌드는 CONFIG_WAITQ_SIMPLE=y였다.

z_impl_k_poll(kernel/poll.c 283행~)은 register_events로 배열을 돌며 이미 준비된 것은 set_event_ready, 아니면 각 객체의 poll_events 리스트에 이 이벤트를 우선순위 순(add_event)으로 건다 → 하나도 준비 안 됐으면 z_pend_curr로 잔다 → 깨면 clear_event_registrations로 전부 떼어 낸다. 객체 쪽(k_sem_give, k_queue_insert 등)은 z_handle_obj_poll_events를 불러 등록된 poll event 하나를 깨운다. 흥미로운 점은 z_pend_curr에 넘기는 대기 큐가 함수 안의 static _wait_q_t wait_q, 즉 모든 poller가 공유하는 큐 하나라는 것이다 — 깨울 때는 큐를 거치지 않고 signal_poller가 poller 스레드를 직접 unpend하므로 문제가 없다.

8.1 드론 FC — IMU data-ready → rate loop, 센서 준비 비트#

예를 들어 STM32H7 드론 비행 제어기라면 IMU(예: 8 kHz gyro)의 data-ready EXTI가 SPI DMA를 시작하고, DMA 완료 ISR이 rate loop 태스크를 깨운다. 받는 태스크가 하나이고 지연이 곧 제어 품질이므로 notification이 정답이다. 원인을 구분하려면 비트를 쓴다.

(이 코드는 STM32 HAL 없이 구조만 보인 것이라 이 랩에서 빌드하지 않았다. 같은 API 조합은 예제 2와 예제 3에서 실행했다.) 반면 "gyro · accel · baro가 모두 새 샘플을 낸 뒤에 fusion을 한 번 돈다" 같은 저속 경로는 event group wait-all이 자연스럽다(예제 5). 이때 비트는 횟수를 잃는다는 점과, 센서 ISR이 직접 xEventGroupSetBitsFromISR를 부르면 데몬 경유 지연(예제 7, 35 us 이상)이 붙는다는 점을 기억한다. 깔끔한 구조는 ISR → 센서 드라이버 태스크(notification) → 드라이버 태스크가 xEventGroupSetBits(태스크 컨텍스트라 데몬 없음)다.

8.2 DMA half / full 완료 → 드라이버 태스크#

UART나 ADC를 circular DMA로 받으면 half-transfer와 transfer-complete 인터럽트가 번갈아 온다(E6). 두 사건을 notification 비트 두 개로 보내고, 태스크가 처리 도중 둘이 다 서 있으면 "처리가 늦어 반 버퍼를 놓칠 뻔했다"는 overrun 신호로 쓸 수 있다. xTaskNotifyAndQueryFromISR로 이전 값을 받아 보면 ISR 안에서도 "아직 안 읽은 비트가 있었나"를 알 수 있다.

8.3 GNSS NMEA — stream buffer와 trigger level#

예제 8이 그대로 실무 코드의 뼈대다. 실칩에서는 바이트마다 인터럽트 대신 UART RX DMA + idle line 인터럽트로 덩어리를 받고, ISR에서 xStreamBufferSendFromISR(sb, dma_chunk, n, &w)로 한 번에 넣는다. 그러면 trigger level은 "문장 하나쯤"(예: 32~64)으로 두고, idle 인터럽트(문장 사이 공백)에서 xStreamBufferSendCompletedFromISR(sb, &w)로 trigger 미만이어도 파서를 깨운다. 파서 태스크는 하나, ISR writer도 하나 — SWSR 조건이 자연스럽게 맞는다. 만약 같은 UART에 텔레메트리 송신 태스크 두 개가 쓰려 한다면(TX 방향), 그건 writer 둘이므로 큐나 뮤텍스 + stream buffer 조합으로 바꾼다(예제 10).

10. 면접에서 이렇게 말한다#

Q. What is a FreeRTOS task notification and why is it lighter than a binary semaphore?

A. 태스크마다 TCB 안에 32비트 값과 상태 바이트가 있고, 다른 태스크나 ISR이 핸들로 그 태스크에 직접 값을 갱신하며 깨운다. 중간 객체가 없으니 RAM이 0이고(semaphore는 heap 96 B), 깨울 때 이벤트 리스트를 거치지 않아 상태 리스트 하나만 옮긴다. 내가 V11.3.2에서 재 보니 깨움 + 전환 경로가 15~20% 짧았다. 문서의 45%는 2015년 V8.1.2 semaphore 기준이다.

A notification is a 32-bit value plus a state byte inside each task's TCB. The sender writes it directly through the task handle, so there is no intermediate kernel object: zero extra RAM, and on unblock the kernel only moves the task from the delayed list to the ready list instead of going through a queue's event list. The docs say up to 45% faster, but that was measured against the V8.1.2 semaphore; on V11 in QEMU I measured about 15 to 20% on the wake-plus-switch path and no difference on the non-blocking path.

꼬리 질문: "So why not always use notifications?" → 받는 쪽이 정확히 태스크 하나일 때만 된다. 브로드캐스트, ISR 수신, 보내는 쪽 블록, 버퍼링이 없다.

Q. How do you use a notification as a counting semaphore versus a binary semaphore?

A. xTaskNotifyGive는 값을 +1 한다. 받는 쪽 ulTaskNotifyTake(pdTRUE, …)는 0으로 지우는 binary, pdFALSE는 1 감소하는 counting이다. 둘 다 반환값이 "그동안 몇 번 왔나"라서 binary로 써도 놓친 신호를 셀 수 있다.

Give increments the value. Take with clear-on-exit set to pdTRUE behaves like a binary semaphore and resets it to zero; pdFALSE decrements by one, like a counting semaphore. In both cases the return value is the count before the take, which I use to detect when an ISR fired more than once before the task ran.

Q. Why can't you set event group bits directly from an ISR in FreeRTOS?

A. set은 대기 리스트 전체를 훑으며 조건을 검사하고 맞는 태스크를 전부 깨운다 — 대기자 수에 비례하는 O(n)이다(32개에 2145 cycle을 쟀다). FreeRTOS는 이 비결정적 작업을 인터럽트를 막은 채로 하지 않기로 했고, 태스크에서는 스케줄러 정지로 보호한다. ISR판은 xTimerPendFunctionCallFromISR로 타이머 데몬에 미루므로 configUSE_TIMERS가 필요하고, 지연이 늘고(직접 알림 202 vs 879 cycle), 데몬 우선순위가 낮으면 그만큼 밀린다.

Setting bits walks the whole waiting list and may unblock any number of tasks, so its cost is linear in the number of waiters; I measured about 65 cycles per woken task. FreeRTOS refuses to do non-deterministic work with interrupts disabled, so from an ISR it defers the set to the timer daemon with xTimerPendFunctionCallFromISR. That needs configUSE_TIMERS, adds a context switch, can fail if the timer queue is full, and is only as fast as the daemon's priority allows.

꼬리 질문: "How does Zephyr do it?" → k_event_post는 ISR에서 직접 되고 스핀락 안에서 대기 큐를 훑는다. 데몬이 없는 대신 그 O(n)을 인터럽트 잠금 안에서 받아들인 설계다.

Q. What does the trigger level of a stream buffer control, and how would you choose it for a UART?

A. 쓴 뒤 바이트 수가 trigger 이상이면 블록된 reader를 깨운다. 작으면 지연이 짧지만 깨움이 많고, 크면 반대다. 115200 baud에서 trigger 1은 바이트마다(초당 1만 번) 깨우고 지연 17 us, 16이면 129번에 1.3 ms였다. NMEA는 문장 길이 근처로 두고 idle-line에서 xStreamBufferSendCompletedFromISR로 꼬리를 밀어 준다.

The trigger level is checked on the send side: once the buffered byte count reaches it, the blocked reader is woken. It trades wake-ups against latency. For a 115200-baud GNSS link I measured 2048 wake-ups and 17 microseconds with a trigger of 1, versus 129 wake-ups and 1.3 milliseconds with 16. I'd set it near a sentence length and use the UART idle-line interrupt to force a wake for the tail.

Q. Stream buffers are described as single-writer single-reader. What actually breaks with two writers?

A. 쓰기 경로에 락이 없어서 두 writer가 같은 xHead에서 동시에 쓰면 데이터와 길이 접두가 섞인다. 태스크 + ISR 두 writer로 재현했더니 35085개 중 160개가 깨지고 수천 개가 사라졌는데 assert는 없었다. 블록하는 writer · reader가 둘이면 xTaskWaitingToSend/Receive 핸들 칸이 하나라 assert가 잡는다. 여러 writer면 직렬화하거나 큐를 쓴다.

The write path updates the head index without a lock, because it assumes one writer. With a task and an ISR both writing, I reproduced silent corruption: 160 corrupted messages and thousands lost out of 35,000, with no assert. Only the blocking case is caught, since the buffer stores a single waiting-task handle per direction. For multiple writers you either serialize the sends in a critical section with zero block time, or use a queue.

Q. Event bits versus a semaphore — when does each fit?

A. 세마포어는 횟수(자원 수, 사건 수)를 세고 깨어나는 것은 하나다. event bit는 횟수 없이 "상태"이고 여러 태스크가 서로 다른 조합(any / all)을 기다릴 수 있다. 센서 세 개가 다 준비됐나는 bit, 샘플이 몇 개 쌓였나는 count다.

A semaphore counts and wakes one waiter per give. Event bits are level-like state with no count, and several tasks can wait on different any or all combinations. "All three sensors ready" is a bit pattern; "how many samples are pending" is a count, and bits would silently lose that.

Q. In Zephyr, what is k_poll for and what are its pitfalls?

A. sem · fifo · msgq · pipe · signal 여러 개를 한 번에 기다리는 POSIX poll 같은 것이다. 가져가지는 않아서 반환 후 K_NO_WAIT로 직접 꺼내야 하고, state가 누적되므로 매번 NOT_READY로 되돌려야 하며, signal은 reset해야 한다. 같은 객체를 여러 스레드가 poll하면 가장 높은 우선순위 하나만 깬다.

k_poll waits on several heterogeneous objects at once, like POSIX poll. It only reports readiness; you still take the semaphore or get the FIFO item with K_NO_WAIT and handle failure. The kernel ORs readiness into each event's state and never clears it, so you reset state to NOT_READY every loop and reset signals explicitly. And one raise or give wakes only the highest-priority poller, so for broadcast I'd use k_event.

Q. How would you pass "latest altitude" from a baro task to the control task with minimum overhead?

A. 최신 값만 의미 있으니 큐보다 덮어쓰기가 맞다. 받는 태스크가 하나면 xTaskNotify(h, alt_mm, eSetValueWithOverwrite) — 32비트 안에 들어가는 값이면 복사도 객체도 없다. 값이 크면 더블 버퍼 + 시퀀스 번호(D8) 위에 notification으로 깨운다.

Only the newest value matters, so overwrite semantics fit better than a queue. If it fits in 32 bits, xTaskNotify with eSetValueWithOverwrite delivers it with no object and no copy. For a larger struct I'd use a double buffer with a sequence counter and send a notification just to wake the reader.

  7. 설계: 드론 FC에서 IMU(8 kHz) · baro(50 Hz) · GNSS(10 Hz, UART) · RC 입력(SBUS, UART 100 kbaud) · 텔레메트리 TX를 태스크로 나누고, 각 경로에 쓸 신호 도구를 §6 표로 고른 뒤 이유를 한 줄씩 써라. 정답/힌트: IMU = notification, baro → fusion = event group(태스크에서 set), GNSS · SBUS = stream buffer(ISR 1 writer), 텔레메트리 TX = 여러 생산자이므로 큐.

13. 요약 & 체크리스트#

FreeRTOS task notification은 TCB 안의 32비트 값과 상태 바이트로 만든 "수신자 1명짜리 초인종"이다. eAction에 따라 binary / counting semaphore, 이벤트 비트, mailbox가 되고, 객체 RAM이 0이며 깨움 경로가 짧다 — 이 랩의 V11.3.2 측정으로는 전환 포함 경로에서 semaphore보다 11~22% 짧았고(문서의 45%는 2015년 semaphore 기준), 전환 없는 경로는 assert를 끄면 차이가 없었다. 한계는 수신자 1개, ISR 수신 불가, 송신 블록 불가, 버퍼링 없음이고, 인덱스 0은 stream buffer가 기본으로 쓴다. event group은 여러 태스크가 비트 조합을 기다리는 도구인데, 비트는 횟수를 세지 않고, 사용자 비트는 24개이며, set 비용이 대기자 수에 선형(대기자당 8~65 cycle)이라 ISR판은 타이머 데몬으로 미뤄져 지연이 4배 이상 늘고 데몬 우선순위에 묶인다. stream / message buffer는 SWSR 링 + trigger level로, trigger는 깨움 수와 지연을 맞바꾸는 손잡이이며(UART 115200에서 trigger 1 → 2048번 · 17 us, 16 → 129번 · 1.3 ms), writer가 둘이면 assert 없이 조용히 깨진다. Zephyr는 k_event(32비트, ISR 직접 post, 브로드캐스트, _safe 소비)와 k_poll(여러 객체 대기, 가져가지 않음, state 수동 재초기화, 깨움은 최고 우선순위 하나)로 같은 문제를 푼다.
