0. 큰 그림 — 왜 Zephyr에는 "큐"가 일곱 개나 있나#

FreeRTOS에서 태스크끼리 데이터를 넘기는 기본 도구는 사실상 하나다. xQueueSend/xQueueReceive, 즉 고정 크기 아이템을 복사하는 큐다(stream/message buffer는 D5). 포인터를 넘기고 싶으면 "포인터 크기 아이템의 큐"를 만든다. Don이 SSD 펌웨어에서 쓰던 방식도 비슷했을 것이다. 명령 디스크립터는 미리 잡아 둔 풀에서 꺼내고, 큐에는 디스크립터 인덱스나 포인터만 넣고, 링버퍼에는 고정 크기 엔트리를 복사했다.

Zephyr는 이 선택지들을 처음부터 서로 다른 커널 객체로 나눠 두었다. Zephyr의 뿌리인 Wind River 코드에서 온 이름들이다(queue.c · stack.c · msg_q.c · mailbox.c 머리의 저작권이 "Wind River Systems", 2010~2016이다).

  • 포인터를 넘기는 것(0 copy): k_fifo, k_lifo, 그 밑바닥의 k_queue
  • 값 하나(word)를 넘기는 것: k_stack
  • 고정 크기 메시지를 복사하는 것: k_msgq (FreeRTOS 큐와 가장 닮았다 — 기본은 D4)
  • 바이트 스트림을 복사하는 것: k_pipe
  • 보낸 쪽과 받는 쪽이 만나서(rendezvous) 넘기는 것: k_mbox
  • 한 생산자 → 여러 관찰자에게 퍼뜨리는 것: zbus (커널 객체가 아니라 subsys/zbus의 서브시스템)

이 노트는 이 지도를 그리고, 각 객체의 "Zephyr에만 있는 동작"을 실행으로 확인한 뒤, 같은 QEMU 보드에서 비용을 잰다.

그림 1 — Zephyr의 데이터 전달 객체를 두 축에 놓았다. 왼쪽으로 갈수록 복사가 적고(대신 메모리 수명 관리를 앱이 진다), 위로 갈수록 길이가 자유롭다. 점선의 zbus는 커널 객체가 아니라 k_sem · k_msgq · k_fifo · net_buf 위에 세운 서브시스템이다.

SSD 펌웨어에 빗대면 이렇다. k_fifo는 "디스크립터 자체에 next 포인터가 박혀 있는 명령 리스트", k_stack은 "빈 버퍼 인덱스를 쌓아 두는 free-list", k_msgq는 "고정 크기 엔트리 링버퍼", k_pipe는 "UART 로그 바이트 링", k_mbox는 "호스트가 완료 응답을 받을 때까지 기다리는 동기 명령", zbus는 "온도 센서 값을 여러 모듈(열 관리, 로그, SMART)에 동시에 알리는 이벤트 버스"다.

1.4 공통 골격 — 모든 객체는 "버퍼 + wait_q + spinlock"이다#

Zephyr 소스를 열어 보면 여섯 개 객체가 거의 같은 모양이다. 구조체에 데이터를 담는 곳(sflist, 링버퍼, 배열)과 기다리는 스레드 줄(_wait_q_t, C1 §5.3)과 struct k_spinlock 하나가 있다. 보내는 쪽은 "줄 선 사람이 있으면 그 사람에게 직접 주고, 없으면 버퍼에 넣는다". 받는 쪽은 "버퍼에 있으면 꺼내고, 없으면 내 받을 곳 주소를 _current->base.swap_data에 적어 두고 줄을 선다(z_pend_curr)". 이 대칭은 D1의 k_sem, C12에서 읽은 sem.c와 똑같다. 차이는 무엇을 넘기느냐뿐이다. 자세한 내부는 §10에서 함수 단위로 본다.

2. k_fifo · k_lifo · k_queue — 아이템 안에 next 포인터를 박는 intrusive 큐#

2.1 직관 — "명령 디스크립터의 첫 필드가 next"#

SSD 펌웨어의 명령 큐를 떠올리자. 디스크립터 구조체 맨 앞에 struct cmd *next를 두고, 큐에는 head/tail 포인터만 둔다. 데이터는 한 바이트도 복사하지 않는다. 대신 규칙이 하나 생긴다. 큐에 들어가 있는 동안 디스크립터의 next 필드는 큐의 것이다. k_fifo가 정확히 이것이다. 헤더의 문서가 이렇게 말한다.

k_fifo와 k_lifo는 따로 구현이 없다. 둘 다 struct k_queue _queue 하나를 감싼 구조체이고, k_fifo_put은 k_queue_append, k_lifo_put은 k_queue_prepend를 부르는 매크로다. 꺼내는 쪽은 둘 다 k_queue_get(머리에서 꺼냄)이다. 즉 "FIFO냐 LIFO냐"는 넣을 때 꼬리에 붙이느냐 머리에 붙이느냐뿐이다.

k_queue의 리스트는 sys_slist가 아니라 sys_sflist다. "flagged" 단일 연결 리스트로, next 포인터의 하위 2비트를 플래그로 쓴다(SYS_SFLIST_FLAGS_MASK = __alignof__(sys_sfnode_t) - 1, BUILD_ASSERT(... >= 0x3)). 아이템이 word 정렬이어야 하는 이유가 이것이다. 플래그 비트 0은 "이 노드는 커널이 heap에서 만든 alloc_node다"라는 표시다(§2.4).

그림 3 — 위: 예제 1의 실제 주소로 그린 k_fifo 리스트. 아이템 세 개가 서로의 첫 word로 이어져 있고, 마지막 아이템의 첫 word는 0(NULL)이다. 아래: k_fifo_alloc_put은 8 B짜리 alloc_node를 호출 스레드의 resource pool에서 만들어 그것을 리스트에 넣는다.

2.2 예제 1 — 첫 word 예약, 0 copy, 대기자 직접 전달, alloc_put#

무엇을 확인하는 코드인지: (1) put 뒤에 아이템의 첫 word가 실제로 next 포인터가 되는지, (2) 꺼낸 포인터가 넣은 객체 그 자체인지(복사 없음), (3) 이미 기다리는 스레드가 있으면 아이템이 리스트를 거치지 않고 바로 넘어가는지(첫 word가 그대로인지), (4) lifo 순서, (5) k_fifo_alloc_put이 resource pool을 얼마나 먹는지.

prj.conf: CONFIG_PRINTK=y, CONFIG_QEMU_ICOUNT_SHIFT=5, CONFIG_HEAP_MEM_POOL_SIZE=1024.

출력에서 볼 것:

  • after put 줄: s0.res=0x20000330이 &s1과 같고, s1.res가 &s2, 마지막 s2.res=0이다. 0xDEADBEEF로 채워 둔 첫 word를 커널이 next 포인터로 덮어썼다. 그림 3 위쪽 그대로다.
  • fifo get 주소가 s[0..2] 주소 그대로다. 복사가 없다. 같은 객체를 생산자와 소비자가 번갈아 만진다는 뜻이므로, 소비자가 다 쓰고 "돌려주기" 전까지 생산자는 그 아이템을 재사용하면 안 된다(§2.3 버그 2).
  • waiter got ... reserved=0xdeadbeef (untouched): 우선순위 1인 waiter가 이미 fifo_w에서 블록되어 있었으므로, k_fifo_put은 아이템을 리스트에 넣지 않고 waiter의 반환값으로 바로 꽂았다. 그래서 첫 word를 건드리지조차 않았다. 소스로는 queue_insert()가 z_unpend_first_thread()로 대기자를 찾으면 prepare_thread_to_run(thread, data) → z_thread_return_value_set_with_data()로 끝내고 sys_sfnode_init(data, 0)에 도달하지 않는다(§10).
  • lifo get은 102 → 101 → 100. 같은 k_queue를 머리에 붙였을 뿐이다.
  • alloc_put into 128 B heap: 5 ok, then -12: alloc_node는 8 B(sys_sfnode_t 4 B + void *data 4 B)지만 sys_heap의 chunk 헤더와 정렬 때문에 128 B heap에 5개만 들어갔다. 6번째에서 -ENOMEM. 하나를 꺼내면(get이 k_free) 다시 들어간다.

k_fifo_alloc_put의 heap은 "호출 스레드의 resource_pool"이다(z_thread_malloc → z_thread_alloc_helper, kernel/mempool.c). ISR에서 부르면 시스템 heap(_SYSTEM_HEAP)을 쓴다. 기본값을 소스에서 확인하면 이렇다.

  • 부팅 중의 dummy thread는 K_HEAP_MEM_POOL_SIZE > 0이면 k_thread_system_pool_assign(dummy_thread)를 받는다(kernel/thread.c z_dummy_thread_init). 새 스레드는 new_thread->resource_pool = _current->resource_pool로 만든 스레드의 pool을 물려받는다. 그래서 main과 K_THREAD_DEFINE 스레드는 시스템 heap이 있으면 자동으로 그것을 쓴다.
  • CONFIG_HEAP_MEM_POOL_SIZE가 0(기본)이면 pool이 NULL이고 alloc_put은 항상 -ENOMEM이다.
  • 대기자가 있으면 할당 자체를 하지 않는다(소스 주석: "Only need to actually allocate if no threads are pending").

2.3 예제 2 — k_fifo를 부수는 세 가지 방법#

무엇을 확인하는 코드인지: 실무에서 실제로 나오는 세 버그 — (1) 구조체에 예약 word를 안 둠, (2) 아직 큐 안에 있는 아이템을 다시 put, (3) 함수 지역 변수(스택)를 put하고 함수가 끝남.

출력에서 볼 것:

  • (1) b0.seq=0x20000020이 &b1이다. 예약 word가 없으니 첫 필드 seq가 next 포인터로 덮였다. 컴파일러도 런타임 검사도 아무 말 없다. 데이터가 조용히 깨질 뿐이다.
  • (2) A, B, C를 넣고 B를 한 번 더 넣었더니 2개만 나왔다. B를 다시 append하는 순간 sys_sfnode_init(B, 0)이 B의 next(=C)를 0으로 지우고 C의 next에 B를 붙인다. 리스트는 A → B → 끝이 되고 C는 리스트에서 떨어져 나가 영원히 사라진다. 메모리 누수이자 메시지 유실이다. 반대로 꼬리 아이템을 다시 넣으면 자기 자신을 가리키는 고리가 생길 수도 있다. "보낸 아이템은 받은 쪽이 끝낼 때까지 내 것이 아니다"를 지키지 않으면 이렇게 된다.
  • (3) 스택 아이템은 seq=777 대신 쓰레기(536870936 = 0x20000018)가 나왔고, 그 쓰레기가 "next 포인터"로 읽혀서 두 번째 get이 또 쓰레기를 냈고, 세 번째에서 0x29332800을 읽다가 BUS FAULT가 났다. addr2line으로 PC를 보면 커널 안이다.

fault가 소비자 쪽 k_queue_get 안에서 났다는 점이 무섭다. 버그는 생산자에 있는데 backtrace는 커널 큐를 가리킨다. 현장에서 "Zephyr 큐가 HardFault를 낸다"는 보고의 상당수가 이 패턴이다. 진단 요령: fault 주소가 리스트 노드(z_sfnode_next_peek)면 큐에 넣은 아이템의 수명부터 의심한다. 그리고 fault가 난 뒤 QEMU가 끝나지 않고 timeout으로 끝난 것([qemu exit=124])은 기본 k_sys_fatal_error_handler가 시스템을 멈추기 때문이다(§9에서 이것을 바꿔 본다).

2.5 흔한 함정#

  • 아이템 구조체 첫 필드를 void *fifo_reserved;로 두는 것을 잊는다 → 첫 필드 데이터 파괴(예제 2-1).
  • const 테이블이나 플래시에 있는 데이터를 k_fifo_put → 커널이 첫 word에 쓴다. 실칩에서는 플래시 쓰기 fault다. 그런 데이터는 k_fifo_alloc_put으로 넣는다(예제 1의 cfg_word).
  • 같은 아이템을 두 큐에 동시에 넣는다 → next 필드가 하나뿐이니 두 리스트가 섞인다. 두 큐에 걸쳐야 하면 next 필드를 두 개 두고 CONTAINER_OF로 돌아오는 sys_slist를 직접 쓰거나 복사 객체를 쓴다.
  • k_fifo_get이 NULL을 돌려주는 경우는 두 가지다. 타임아웃, 그리고 누군가 k_fifo_cancel_wait을 부른 경우. 둘을 구분하려면 별도 플래그가 필요하다.

3. k_stack — word 하나짜리 LIFO, 버퍼 free-list의 정석#

3.1 정의#

k_stack은 stack_data_t(= uintptr_t, Cortex-M에서 4 B) 배열 위의 LIFO다. K_STACK_DEFINE(name, n)이 배열까지 만든다. 값을 복사하지만 값이 4 B뿐이라 "포인터를 넘기는 가장 싼 방법"이기도 하다. 전형적인 용도는 빈 버퍼 풀(free-list) 이다. DMA 버퍼 N개의 주소를 넣어 두고, 쓰는 쪽이 pop, 다 쓴 쪽(흔히 DMA 완료 ISR)이 push한다. LIFO라서 방금 반납된 버퍼(캐시에 남아 있을 가능성이 큰 버퍼)가 먼저 다시 나간다.

k_mbox의 async 경로도 내부에서 K_STACK_DEFINE(async_msg_free, CONFIG_NUM_MBOX_ASYNC_MSGS)를 descriptor free-list로 쓴다(§6.4). 커널 스스로가 이 패턴의 사용자다.

3.2 예제 6 — DMA 버퍼 free-list#

무엇을 확인하는 코드인지: LIFO 순서, 가득 찼을 때와 비었을 때의 에러 코드, 그리고 ISR(k_timer 콜백)에서 push하면 블록된 pop이 깨어나는지.

출력에서 볼 것:

  • 넣은 순서 0,1,2,3 → 꺼낸 순서 3,2,1,0. LIFO.
  • 가득 찬 stack에 push → -12(-ENOMEM). 이 검사는 CHECKIF(stack->next == stack->top)이다. CHECKIF는 CONFIG_NO_RUNTIME_CHECKS=y면 사라지고, CONFIG_ASSERT_ON_ERRORS=y면 assert가 된다. 런타임 검사를 끈 릴리스 빌드에서 push를 너무 많이 하면 배열 밖에 쓴다. 풀 크기 = stack 크기로 맞추면 넘칠 일이 없다.
  • 빈 stack을 K_NO_WAIT로 pop → -16(-EBUSY), 타임아웃 → -11(-EAGAIN). 같은 "없음"인데 k_msgq는 -ENOMSG, k_stack은 -EBUSY다. 객체마다 에러 코드가 다르다. 반환값을 == -EAGAIN으로만 검사하는 공용 래퍼를 만들면 K_NO_WAIT 경로를 놓친다. != 0으로 검사하는 습관이 안전하다.
  • ISR에서 push한 buf2가 30 ms 뒤 블록된 pop으로 바로 넘어갔다. z_impl_k_stack_push도 대기자가 있으면 배열에 넣지 않고 z_thread_return_value_set_with_data(first_pending_thread, 0, (void *)data)로 직접 준다.

4. k_msgq — Zephyr에만 있는 부분만#

메시지 큐 일반론(복사 vs 포인터, 깊이 설계, 블로킹 send/receive)과 FreeRTOS 큐와의 기본 비교는 D4가 다룬다. 여기서는 Zephyr v4.4.2의 k_msgq에만 있는 동작만 본다.

4.1 정렬 — 4.4.2 문서는 "필요 없다"고 말한다#

예전 Zephyr 문서는 "메시지 크기는 정렬의 배수여야 한다"는 식으로 정렬을 강조했다. v4.4.2 헤더의 K_MSGQ_DEFINE 문서는 이렇게 적는다.

구현을 보면 이유가 분명하다. put_msg_in_queue()와 z_impl_k_msgq_get()은 memcpy(msgq->write_ptr, data, msgq->msg_size)로만 복사하고, 링버퍼 안의 메시지를 구조체 포인터로 캐스팅해 읽는 일이 없다. 그래서 6 B짜리 __packed 구조체도 q_align = 1로 문제없다(예제 3). 다만 성능은 다르다: 기본 -Os 빌드의 picolibc memcpy는 28 B짜리 바이트 루프다(§8.2에서 디스어셈블로 확인). 큰 메시지라면 정렬보다 최적화 옵션이 비용을 좌우한다. K_MSGQ_DEFINE의 버퍼는 __noinit이라 부팅 때 0으로 지워지지 않는다는 점도 알아 둔다.

5.2 새 의미 — "len을 다 채울 때까지 기다린다, 타임아웃이면 부분"#

소스(z_impl_k_pipe_read)의 루프를 그대로 읽으면 규칙은 세 줄이다.

  1. 링버퍼에서 꺼낼 수 있는 만큼 꺼낸다. len을 다 채웠으면 len을 돌려준다.
  2. 덜 채웠는데 pipe가 닫혔으면 지금까지 읽은 수(0이면 -EPIPE).
  3. 아니면 data 대기 줄에서 기다린다. 타임아웃이면 지금까지 읽은 수(0이면 -EAGAIN).

즉 POSIX read()처럼 "있는 만큼 주고 돌아오기"가 아니다. K_FOREVER로 16 B를 읽으면 16 B가 다 올 때까지 안 돌아온다. "있는 만큼"을 원하면 K_NO_WAIT로 읽는다. 쓰기도 대칭이다. 그리고 메시지 경계가 없다. 5 B 프레임 세 개를 써도 reader는 그것을 8 B + 7 B로 읽을 수 있다.

쓰는 쪽에는 최적화가 하나 있다. pipe가 비어 있고 기다리는 reader가 있으면 copy_to_pending_readers()가 링버퍼를 건너뛰고 reader의 버퍼(reader 스택 위의 struct pipe_buf_spec이 가리키는 곳)로 바로 memcpy한다. reader가 원하는 양을 다 받았을 때만 깨운다. 그래서 reader는 깨어나자마자 "다 찼다"를 본다.

그림 5 — 예제 4 후반부. 20 ms의 6 B는 reader 버퍼로 바로 들어갔지만 16 B가 안 차서 reader는 계속 잔다. 40 ms의 10 B가 들어오는 순간 깨어나 16을 돌려준다. 두 번째 read는 6 B만 받고 타임아웃으로 6을 돌려준다(부분 전송). 세 번째 read는 k_pipe_reset으로 -ECANCELED.

5.3 예제 4 — 경계 없음, 부분 전송, reset, close#

무엇을 확인하는 코드인지: 위 규칙을 전부. 32 B pipe에 5 B 프레임 세 개를 쓰고 8 B를 읽기, 빈 pipe K_NO_WAIT, 버퍼보다 큰 쓰기, 블록된 reader에게 6 B + 10 B, 타임아웃 부분 읽기, reset 중의 reader, close 뒤의 쓰기 · 읽기.

출력에서 볼 것:

  • read(8) = 8: a5 01 02 03 5a | a5 01 02: 두 번째 프레임 중간에서 잘렸다. pipe는 메시지 경계를 모른다. UART 프레임처럼 경계가 중요한 데이터면 앱이 길이 헤더나 동기 바이트(여기서는 0xA5 … 0x5A)로 다시 찾아야 한다. 고정 크기 메시지면 k_msgq가 맞다.
  • write(40) into 32 B pipe, NO_WAIT = 32: 들어가는 만큼만 넣고 32를 돌려준다. 반환값이 len보다 작을 수 있다. 반환값을 무시하면 8 B를 조용히 잃는다.
  • 그림 5의 세 결과(16, 6, -140)가 실제 로그 그대로다. 두 번째 read가 6을 돌려준 것은 "타임아웃 → 읽은 만큼"이다. 타임아웃을 0으로 착각해 -EAGAIN만 검사하면 이 6 B를 놓친다.
  • close 뒤: write는 바로 -32(-EPIPE), read는 남은 5 B를 먼저 돌려주고 그다음 -EPIPE. migration guide의 "all data in the pipe is available to readers until the pipe is emptied" 그대로다. 로그 스트림을 닫을 때 "남은 바이트를 다 비운 뒤 EOF"를 표현할 수 있게 된 것이 close의 존재 이유다.

5.4 버퍼 크기 0인 pipe#

k_pipe_init(pipe, NULL, 0)과 K_PIPE_DEFINE(name, 0, align)을 문서가 허용한다("or zero if no ring buffer is used"). 링버퍼가 없으면 ring_buf_put이 항상 0을 넣으므로, writer는 기다리는 reader에게 직접 복사하는 경로로만 데이터를 넘긴다. 즉 "reader가 와서 받을 때까지 writer가 기다리는" 바이트 단위 rendezvous가 된다. k_mbox보다 가벼운 동기 전달이 필요할 때 쓸 수 있다(이 노트에서는 실행하지 않았다).

5.5 흔한 함정#

  • 옛 API 예제를 그대로 붙인다 → v4.3부터 링크 에러가 아니라 컴파일 에러(함수 선언이 없음).
  • k_pipe_read(..., K_FOREVER)를 "들어온 만큼 즉시 반환"으로 착각 → 텔레메트리 스레드가 마지막 몇 바이트를 들고 영원히 잔다.
  • 반환값의 부분 전송을 무시한다.
  • k_pipe_reset은 데이터를 버리고 대기자를 -ECANCELED로 깨운다. reset 진행 중(PIPE_FLAG_RESET, 대기자가 아직 다 안 빠짐)에 새로 부른 read/write도 -ECANCELED다. 이것을 치명 에러로 처리하면 스트림 재동기화 도중 스레드가 죽는다.

6. k_mbox — 송신자와 수신자가 만나서 넘기는 우편함#

6.1 직관 — "등기 우편"#

k_msgq가 우체통(넣고 떠난다)이라면 k_mbox는 등기 우편이다. 보내는 사람(k_mbox_put)은 받는 사람이 서명할 때까지 창구에서 기다린다. 받는 사람(k_mbox_get)은 "누구에게서 온 것만 받겠다"를 정할 수 있고, 보내는 사람은 "누구에게 보낸다"를 정할 수 있다. 그리고 두 사람은 info 값 하나를 서로 맞바꾼다. 데이터는 송신자의 버퍼에서 수신자의 버퍼로 딱 한 번 복사된다. 커널 안에는 데이터 저장소가 아예 없다(구조체에 대기 줄 두 개와 spinlock뿐).

struct k_mbox_msg의 앱이 채우는 필드:

필드송신자가 넣는 값수신자가 넣는 값교환 후
size보낼 바이트 수받을 수 있는 최대수신자: min(둘); 송신자: 수신자가 실제 받은 수

매칭 조건은 mbox_message_match() 그대로다: (송신 target이 K_ANY이거나 수신자 자신) 그리고 (수신 source가 K_ANY이거나 송신자 자신).

6.2 예제 5 — 대상 지정, info 교환, 크기 절단, 지연 수신, async#

무엇을 확인하는 코드인지: (1) 수신자가 없을 때 K_NO_WAIT put, (2) 더 높은 우선순위의 A가 K_ANY로 기다려도 B를 지정한 메시지는 B에게만 가는지, (3) 수신자가 4 B만 받겠다고 하면 송신자의 size가 어떻게 되는지, info 교환, (4) 수신자가 버퍼 없이 get한 뒤 20 ms 일하고 k_mbox_data_get할 때 송신자가 언제 풀려나는지, (5) k_mbox_async_put + 세마포어.

출력에서 볼 것:

  • put before receivers exist, NO_WAIT: -35: 맞는 수신자가 없으면 -ENOMSG.
  • B got "ARM-" size=4: A(우선순위 2)가 B(3)보다 높은 우선순위로 같은 mbox에서 기다렸지만 target이 B라 B가 받았다. 4 B로 잘렸다. 송신자 쪽은 tx.size=4(수신자가 실제로 받은 양), tx.info=0xb(B가 넣어 둔 info)로 바뀌어 돌아왔다. 송신자는 "몇 바이트가 전달됐나"와 "수신자가 답한 값 하나"를 반환값 없이 받는다. 명령 → 짧은 응답 코드 패턴에 딱 맞다.
  • put(ANY)는 A가 받았다. 대기 줄(rx_msg_queue)은 우선순위 순이고, _WAIT_Q_FOR_EACH로 앞에서부터 맞는 사람을 찾는다.
  • B matched, size=6 → 20 ms busy-wait → data_get → 송신자 put(B) ret=0 after 20 ms. 동기 k_mbox_put은 수신자가 데이터를 실제로 가져갈 때까지 돌아오지 않는다. 그리고 소스를 보면 매칭이 된 뒤의 대기는 z_pend_curr(&mbox->lock, key, NULL, K_FOREVER), 즉 put에 준 timeout이 적용되지 않는다. 예제의 K_MSEC(100)은 "수신자를 찾을 때까지"의 한도일 뿐이다. 수신자가 data_get을 잊으면 송신자는 영원히 잔다.
  • async: async_put returned after 0 ms, 세마포어는 B가 실제로 받은 40 ms 뒤(B가 30 ms 자고 tick 경계)에 왔다.

6.3 언제 k_mbox가 값어치를 하나#

장점은 셋이다. 복사가 1회이고(커널 버퍼 없음), 송신자가 "전달 완료"를 동기적으로 알 수 있고, 특정 스레드를 지정할 수 있다. 큰 가변 길이 블록을 "전달 완료 확인과 함께" 넘길 때, 예를 들어 센서 허브에서 펌웨어 업데이트 청크를 플래시 쓰기 스레드에 넘기고 "받았다"를 확인한 뒤 다음 청크를 읽는 경우가 그렇다.

단점이 더 많다.

  • syscall이 없다. user mode 스레드에서 못 쓴다(§9).
  • ISR에서 못 쓴다.
  • 동기 put은 수신자의 처리 시간만큼 송신자를 붙잡는다. 송신자가 수신자보다 높은 우선순위면 우선순위 역전처럼 보이는 지연이 생긴다(D3의 관점으로 보면 "높은 우선순위가 낮은 우선순위의 처리를 기다리는" 구조 자체다).
  • 측정(§8.3)에서 handoff가 k_msgq 16 B보다 2배 가까이 느리다.
  • Zephyr 문서 · 샘플에서도 사용 빈도가 낮다. 새 코드에서는 k_msgq + 응답용 k_sem, 또는 zbus가 흔하다.

6.4 async put의 정체 — dummy thread와 k_stack 풀#

k_mbox_async_put이 "비동기"인 방법이 재미있다. kernel/mailbox.c는 부팅 때 CONFIG_NUM_MBOX_ASYNC_MSGS(기본 10)개의 struct k_mbox_async { struct _thread_base thread; struct k_mbox_msg tx_msg; }를 만들고 K_STACK_DEFINE(async_msg_free, …)에 주소를 쌓는다. async put은 그중 하나를 pop해서 메시지를 복사하고, 가짜 스레드(_THREAD_DUMMY) 를 송신자로 대기 줄에 세운다. 진짜 송신자는 바로 돌아간다. 수신자가 메시지를 다 가져가면 mbox_message_dispose()가 descriptor를 push로 반납하고 세마포어를 준다.

결과 두 가지:

  • footprint: 10개 descriptor가 RAM 800 B(async_msg.0 b 800, §8.4의 nm 출력). k_mbox를 쓰는 순간 async를 안 써도 RAM이 늘어난다. 안 쓰면 CONFIG_NUM_MBOX_ASYNC_MSGS=0.
  • 블록: 풀이 비면 mbox_async_alloc()이 k_stack_pop(&async_msg_free, …, K_FOREVER)로 기다린다. 이름은 async인데 블록할 수 있다.

7. zbus — 한 채널, 여러 관찰자#

7.1 무엇이고 왜 쓰나#

zbus(Zephyr bus)는 subsys/zbus의 publish-subscribe 서브시스템이다. 이 트리의 릴리스 노트로 확인한 이력: 3.3에서 추가, 3.5에서 message subscriber 추가, 3.6에서 채널 잠금을 mutex에서 semaphore로 바꾸고 HLP priority boost 도입, 4.2에서 "stable status with the release of API version v1.0.0", 4.4에서 async listener(CONFIG_ZBUS_ASYNC_LISTENER)와 실험적 proxy agent(CONFIG_ZBUS_PROXY_AGENT, 다른 코어/도메인으로 채널 중계) 추가.

생각의 단위가 "큐"가 아니라 채널이다. 채널은 타입이 정해진 메시지 한 개를 담은 공유 변수 + 잠금 + 관찰자 목록이다. publish는 "채널 값을 바꾸고 관찰자들에게 알린다"이다. 큐처럼 메시지가 쌓이지 않는다(msg_subscriber는 예외). 그래서 앱 구조가 "모듈 A가 모듈 B의 큐에 넣는다"(A가 B를 안다)에서 "A가 IMU 채널에 쓰고, 관심 있는 모듈이 채널을 관찰한다"(A는 B를 모른다)로 바뀐다. Nordic의 Asset Tracker Template(nRF91용, nRF Connect SDK 기반)이 모듈 간 통신을 zbus로, 모듈 동작을 SMF(State Machine Framework)로 짠 것이 대표적인 사례다.

관찰자는 네 종류다(enum zbus_observer_type).

종류정의 매크로받는 것어디서 실행되나Kconfig

publish 한 번의 흐름(VDED — Virtual Distributed Event Dispatcher)은 zbus_chan_pub() → validator → chan_lock()(priority boost + k_sem_take) → memcpy(chan->message, msg) → _zbus_vded_exec()(관찰자 목록을 정의 순서대로 돌며 종류별 통지) → chan_unlock()이다.

7.2 예제 7 — 드론 FC: IMU → failsafe listener + estimator + slow subscriber + logger#

무엇을 확인하는 코드인지: (1) VDED 통지 순서, (2) listener가 어느 스레드 문맥에서 어떤 우선순위로 도는지(priority boost 확인), (3) 높은 우선순위 subscriber와 낮은 우선순위 subscriber가 3샘플 burst에서 각각 무엇을 읽는지, (4) msg_subscriber는 무엇을 받는지.

prj.conf: CONFIG_ZBUS=y, CONFIG_ZBUS_MSG_SUBSCRIBER=y, CONFIG_ZBUS_CHANNEL_NAME=y, CONFIG_ZBUS_OBSERVER_NAME=y, CONFIG_HEAP_MEM_POOL_SIZE=2048, CONFIG_THREAD_NAME=y(+ 공통 두 줄).

출력에서 볼 것:

  • 각 publish마다 L failsafe → S estimator → P pub ret=0 순서다. listener는 ctx=imu, 즉 IMU 스레드 자신이 콜백을 실행했고, 그때 우선순위가 4가 아니라 1이다. estimator가 zbus_obs_attach_to_thread로 자기 우선순위 2를 채널에 알렸으므로, chan_lock()이 publisher를 highest_observer_priority - 1 = 1로 올렸다(HLP, §7.4).
  • estimator(2)는 publisher(원래 4)보다 높지만 boost 때문에 VDED 도중에 끼어들지 못하고, chan_unlock()이 우선순위를 4로 되돌리는 순간 선점해서 읽었다. 그래서 seq 1, 2, 3을 하나씩 정확히 읽었다.
  • slow(7)는 publisher보다 낮아서 burst가 다 끝난 뒤에 돌았다. 알림 3개(큐에 &imu_chan 3개)를 받았지만 세 번 다 seq=3을 읽었다. subscriber는 "채널이 바뀌었다"는 알림만 받는다. 값은 읽는 시점의 최신값이다. seq 1, 2는 이 관찰자에게 영원히 사라졌다. zbus 문서도 "there are no message delivery guarantees for subscribers"라고 적는다.
  • logger(7)도 같은 우선순위로 늦게 돌았지만 seq 1, 2, 3과 각각의 acc_z를 다 받았다. publish마다 net_buf에 복사본이 만들어져 fifo에 쌓였기 때문이다.
  • -> FAILSAFE!는 seq 3의 acc_z=4000을 listener가 publish 안에서 즉시 본 것이다. failsafe 판단처럼 "지금 이 값에 즉시 반응"은 listener, 상태 추정처럼 "최신값만 있으면 된다"는 subscriber, 로깅처럼 "하나도 빠짐없이"는 msg_subscriber — 이것이 세 종류를 고르는 기준이다.

CONFIG_ZBUS_PRIORITY_BOOST=n으로 같은 앱을 다시 빌드하면 출력 순서는 똑같고 listener 줄만 prio=4로 바뀐다(실행 결과, 핵심 줄만).

순서가 같아 보이는 것은 estimator의 zbus_chan_read(…, K_MSEC(5))가 채널이 풀릴 때까지 기다려 주기 때문이다. 속에서 무슨 일이 일어나는지는 §7.4의 그림과 §8.3의 측정(read failed 500/500)이 보여 준다. 덧붙여, 처음에는 zbus_obs_attach_to_thread()를 조건 없이 불렀다가 boost를 끈 빌드에서 error: implicit declaration of function 'zbus_obs_attach_to_thread'를 만났다. 이 함수는 CONFIG_ZBUS_PRIORITY_BOOST일 때만 선언된다. 그래서 예제는 IF_ENABLED(CONFIG_ZBUS_PRIORITY_BOOST, (...))로 감쌌다. Kconfig 하나로 API가 사라지는 Zephyr다운 함정이다.

7.3 예제 8 — zbus의 함정 다섯 개#

무엇을 확인하는 코드인지: (1) 아무도 꺼내 가지 않는 msg_subscriber가 있으면 무슨 일이 생기나, 그리고 그 뒤에 등록된 관찰자는 통지를 받나, (2) 큐가 꽉 찬 subscriber가 publisher를 얼마나 붙잡나, (3) ISR에서 publish, (4) validator, (5) runtime observer 추가 · 제거.

prj.conf: CONFIG_ZBUS=y, CONFIG_ZBUS_MSG_SUBSCRIBER=y, CONFIG_ZBUS_RUNTIME_OBSERVERS=y, CONFIG_HEAP_MEM_POOL_SIZE=2048.

출력에서 볼 것:

  • chan_a pub #15 -> -12, tail_lis notified 15 times. 기본 CONFIG_ZBUS_MSG_SUBSCRIBER_NET_BUF_POOL_SIZE=16이다. 15개가 msub_log의 fifo에 쌓인 상태에서 16번째 publish는 원본 buf(16번째)는 받았지만 clone을 못 받아 -ENOMEM이 됐다. 그리고 _zbus_vded_exec()는 -ENOMEM이면 즉시 return한다. 그래서 목록에서 뒤에 있던 tail_lis는 #15~#19 다섯 번의 통지를 못 받았다. 느린 로거 하나가 같은 채널의 다른 관찰자(listener까지)를 굶긴다. zbus 문서의 "ZBus always delivers the messages to the listeners, message subscribers"는 풀이 남아 있을 때의 이야기다. 대책: msg_subscriber를 목록 맨 뒤에 두고, 풀을 넉넉히(…_POOL_SIZE), 소비 스레드 우선순위를 충분히, 채널마다 풀을 나누려면 CONFIG_ZBUS_MSG_SUBSCRIBER_NET_BUF_POOL_ISOLATION + zbus_chan_set_msg_sub_pool().
  • 그리고 풀은 시스템 전체가 공유한다(isolation을 안 켜면). chan_a의 로거가 풀을 다 먹으면 다른 채널의 msg_subscriber 통지도 실패한다.
  • chan_b pub #2 -> -11 after 60 ms: subscriber 큐(2칸)가 차 있으면 k_msgq_put(obs->queue, &chan, 남은 timeout)이 publisher를 timeout까지 붙잡는다(50 ms → tick 경계로 60 ms). 이 동안 채널 잠금도 쥐고 있다. 다른 publisher와 reader가 모두 막힌다. 문서의 설계 팁 "Try to give consumers a high priority to avoid losses"가 이 뜻이다.
  • ISR(k_timer 콜백)에서 publish: isr_lis: in_isr=1. listener 콜백이 ISR 안에서 돌았다. 그리고 같은 ISR에서 chan_b에 K_MSEC(50)을 줬지만 zbus_chan_pub이 ISR이면 timeout을 K_NO_WAIT로 바꾸므로 꽉 찬 큐에 대해 즉시 -35(-ENOMSG, k_msgq_put의 no-wait 실패 코드)가 나왔다. 문서: "Be careful with publications inside ISR because the scheduler won't preempt the VDED."
  • validator가 거부하면 -ENOMSG, 채널 값은 바뀌지 않는다.
  • zbus_chan_add_obs → 0, 다음 ISR publish에서 late_lis가 1번 통지됨, zbus_chan_rm_obs → 0. runtime observer는 정적 관찰자 다음에 통지된다(_zbus_vded_exec의 두 번째 루프). 문서 경고: "ZBus priority boost does not consider runtime observers on the HOP calculations."

7.4 priority boost(HLP) — 왜 필요하고, 무엇을 대가로 치르나#

zbus의 채널 잠금은 k_sem(초기값 1)이다. 세마포어에는 소유자가 없으니 k_mutex의 priority inheritance(D2, D3)가 없다. 대신 zbus는 Highest Locker Protocol을 손으로 구현한다(chan_lock(), subsys/zbus/zbus.c:401).

  • 채널마다 highest_observer_priority(HOP)를 미리 계산해 둔다. zbus_obs_attach_to_thread()로 스레드에 붙은 관찰자의 우선순위 중 가장 높은 값이다. 붙이지 않은 관찰자는 ZBUS_MIN_THREAD_PRIORITY(= CONFIG_NUM_PREEMPT_PRIORITIES - 1)로 계산된다.
  • publish(또는 notify)하는 스레드의 우선순위가 HOP보다 낮으면 잠그기 전에 k_thread_priority_set(현재, MAX(HOP - 1, 0))로 HOP보다 한 단계 높게 올린다.
  • 잠금을 풀 때 원래 우선순위로 되돌린다. ISR에서는 boost를 하지 않는다.

효과는 "VDED 도중에는 관찰자 스레드도, 그 사이 우선순위의 스레드도 publisher를 선점할 수 없다"이다. 이것이 없으면 아래 그림 아래쪽처럼 된다. 높은 우선순위 subscriber는 k_msgq_put 순간 깨어나 publisher를 선점하고, zbus_chan_read로 채널을 읽으려다가 publisher가 아직 쥐고 있는 잠금에 막힌다. K_NO_WAIT면 -EBUSY, timeout이 있으면 잠들었다가 publisher가 풀어 줄 때 다시 깨어난다. context switch 두 번이 공짜로 더해진다.

그림 7 — HLP boost의 효과. 위: publisher가 HOP-1로 올라가 VDED를 끝까지 하고, 우선순위를 되돌리는 순간 subscriber가 선점한다. 아래: subscriber가 VDED 중간에 끼어들었다가 잠금에 막힌다. §8.3에서 이 아래쪽 경우를 read failed 500/500으로 실측한다.

대가도 있다. (1) publish마다 k_thread_priority_get/set이 두 번씩 돈다(§8.2: listener 하나짜리 채널의 publish가 boost 때문에 6.6 → 10.8 µs). (2) boost 동안 publisher는 자기 우선순위가 아니라 HOP-1로 돈다. 그 사이 우선순위의 무관한 스레드는 publish가 끝날 때까지 못 돈다(문서가 말하는 HLP의 "Inheritance-related Priority Inversion"). listener 콜백이 길면 그 시간 전체가 boost된 우선순위로 실행된다. listener를 ISR처럼 짧게 쓰라는 문서의 규칙이 여기서 나온다. (3) zbus_obs_attach_to_thread를 안 부르면 boost는 HOP를 모르고 사실상 꺼진 것과 같다.

7.5 zbus_chan_claim / finish 와 zbus_chan_notify#

zbus_chan_claim(chan, timeout)은 채널 잠금만 잡는다(boost 없이 k_sem_take). 그 사이 zbus_chan_msg(chan)으로 메시지를 제자리에서 고치거나 user_data를 만지고, zbus_chan_finish(chan)로 푼다. 큰 메시지의 일부 필드만 바꿀 때 복사를 아낀다. 바꾼 뒤 알리려면 zbus_chan_notify(chan, timeout)(memcpy 없이 VDED만). listener 콜백 안에서는 이미 채널이 잠겨 있으므로 zbus_chan_const_msg(chan)으로 직접 읽는다(예제 7의 failsafe). listener 안에서 같은 채널에 zbus_chan_read나 pub을 부르면 자기 자신이 쥔 세마포어를 기다리는 데드락이다(D9).

8. 측정 — 같은 보드에서 객체별 비용 · 지연 · 크기#

8.1 무엇을 어떻게 재나#

세 가지를 잰다.

  1. 대기자 없는 경로의 1회 비용(예제 9): 한 스레드가 보내고 바로 받는다. 블록도 context switch도 없다. "커널 객체 코드 자체 + 복사"의 비용이다. 1000회 평균.
  2. 전달 지연(예제 10, 11): 높은 우선순위 수신자가 이미 블록된 상태에서 낮은 우선순위 송신자가 보낸다. send 직전 카운터(t0)부터 수신자가 받기 함수에서 돌아온 순간까지. context switch 1번이 들어간다. 500회 평균.
  3. footprint(예제 12): 객체 하나만 쓰는 최소 앱의 size − 빈 앱의 size.

모두 -icount shift=5로 결정적이다(같은 바이너리는 몇 번을 돌려도 같은 숫자). 절대값은 실칩과 다르고, 상대 비교와 "어떤 Kconfig가 얼마를 더하나" 를 읽는다.

28 B(0x1c)짜리 바이트 루프다. -O2 빌드에서는 000000c0 000000ec T memcpy, 236 B짜리 word 복사 구현이 들어간다. 앱 코드의 memcpy 64B(2.2 µs)가 커널의 64 B 복사보다 훨씬 싼 것은 gcc가 크기가 상수인 앱 쪽 memcpy를 인라인으로 펼쳤기 때문이다. "Zephyr 메시지 큐가 느리다"는 측정의 상당 부분은 -Os의 바이트 memcpy다. 메시지가 크고 빈번하면 (1) CONFIG_SPEED_OPTIMIZATIONS, (2) CONFIG_PICOLIBC_SPEED_OPTIMIZATIONS만 따로 켜기, (3) 포인터 전달(k_fifo + 풀)로 바꾸기 중에서 고른다.

  • k_pipe는 같은 크기의 k_msgq보다 비싸다(16 B: 14.4 vs 7.3 µs). ring_buf 계층, 쓰기 · 읽기 각각의 sys_timepoint_calc, for (;;) 루프 구조 때문이다. 고정 크기 메시지에 pipe를 쓸 이유는 없다.
  • zbus publish는 커널 큐보다 한 자릿수 비싸다. 가장 가벼운 구성(boost 끔, msg_sub 끔, listener 1개)이 6.6 µs로 k_msgq 16 B 왕복과 비슷하고, 기본값에 가까운 구성(boost 켬)은 10.8 µs다.
  • CONFIG_ZBUS_MSG_SUBSCRIBER=y 한 줄이 모든 publish에 약 35 µs를 더한다(10.8 → 45.6 µs). _zbus_vded_exec()가 채널에 msg_subscriber가 있든 없든 publish마다 net_buf를 heap에서 할당하고 메시지를 복사하고 끝에 해제하기 때문이다(소스: #if defined(CONFIG_ZBUS_MSG_SUBSCRIBER) 블록이 관찰자 루프 앞에 있다). 1 kHz IMU 채널이면 이것만으로 CPU의 3.5%(이 QEMU 기준)다. msg_subscriber가 꼭 필요한 채널이 하나라도 있으면 시스템의 모든 채널이 이 값을 낸다.
  • -O2로 바꿔도 zbus는 30 µs 대다. heap 할당(sys_heap) · net_buf 관리 비용은 memcpy처럼 최적화 옵션으로 사라지지 않는다.

9. user mode 스레드에서는 — syscall이 있는 것만 쓸 수 있다#

Zephyr의 CONFIG_USERSPACE에서 user 스레드는 커널 메모리에 직접 접근할 수 없고, 커널 객체는 syscall(__syscall로 선언된 API)로만 다룬다. 자세한 구조는 F 모듈에서 다룬다. 여기서는 이 노트의 객체들이 어느 쪽인지만 본다. v4.4.2 헤더에서 __syscall 여부를 확인했다.

User mode isn't allowed to do this, although it can get data sent this way."

13. 면접에서 이렇게 말한다#

Q. "What is the difference between k_fifo and k_msgq in Zephyr? When would you use each?"

A. k_fifo는 포인터를 넘기는 intrusive 큐다. 아이템의 첫 word를 커널이 next 포인터로 쓰고, 복사가 없다. 대신 아이템 수명과 재사용 규칙을 앱이 책임진다. k_msgq는 고정 크기 메시지를 커널 링버퍼로 복사한다. 작은 메시지는 msgq가 단순하고 안전하며 user mode에서도 된다. 큰 버퍼는 fifo + 메모리 풀이 빠르다. 내 측정에서 fifo handoff는 세마포어와 1 µs 이내였고, msgq는 64 B에서 두 배였다.

"k_fifo passes pointers: it's an intrusive singly linked list where the kernel uses the first word of each item as the next pointer, so there's no copy, but the application owns the item's lifetime — you can't reuse it or let it go out of scope until the consumer is done. k_msgq copies fixed-size messages into a kernel ring buffer, so ownership is simple and it works from user mode. I use msgq for small fixed messages like commands, and fifo plus a k_mem_slab pool for large buffers like DMA frames. On a QEMU Cortex-M3 the fifo handoff cost about the same as a semaphore, while a 64-byte msgq handoff cost more than twice that, mostly memcpy under -Os."

꼬리 질문: "What happens if you put a stack variable into a k_fifo?" → 함수가 끝나면 아이템이 사라지고, 그 자리의 쓰레기가 next 포인터로 읽혀서 소비자 쪽 k_queue_get 안에서 fault가 난다. 버그는 생산자에 있는데 backtrace는 커널을 가리킨다.

Q. "Can a zbus subscriber miss messages? How do you guarantee delivery?"

A. 놓칠 수 있다. subscriber는 채널 포인터만 큐로 받고, 값은 나중에 zbus_chan_read로 읽으므로 그 사이 publish가 여러 번이면 최신값만 본다. 큐가 차면 publisher가 timeout까지 막히거나 실패한다. 모든 메시지가 필요하면 msg_subscriber(매 publish의 net_buf 복사본)를 쓰는데, 그 풀이 고갈되면 publish가 -ENOMEM을 내고 목록 뒤쪽 관찰자는 통지를 못 받는다. 그래서 msg_subscriber는 목록 맨 뒤, 풀 크기와 소비자 우선순위를 설계한다.

"Yes. A plain subscriber only receives a pointer to the channel through a message queue and reads the current value later, so if several publishes happen before it runs, it sees only the latest — I reproduced a low-priority subscriber reading sequence number 3 three times. If you need every message, use a message subscriber, which gets a net_buf copy per publish. But those come from a shared pool; when it's exhausted the publish returns -ENOMEM and the dispatcher stops, so observers listed after it miss the notification. So I put message subscribers last, size the pool, and give consumers enough priority."

Q. "Explain zbus priority boost. Why does zbus need it?"

A. 채널 잠금이 세마포어라 priority inheritance가 없다. 그래서 zbus는 Highest Locker Protocol을 직접 구현한다. 관찰자 스레드 중 가장 높은 우선순위(HOP)보다 한 단계 높게 publisher를 올려서 publish 전체를 선점 없이 끝낸다. 없으면 높은 우선순위 subscriber가 알림 순간 선점해 들어왔다가 아직 잠긴 채널에 막혀 context switch만 늘어난다. 실제로 boost를 끄고 재 보니 K_NO_WAIT read가 500번 모두 실패했다.

"The channel lock is a semaphore, so there's no priority inheritance. zbus implements the Highest Locker Protocol: each channel knows the highest priority among observers attached to threads, and before locking it raises the publisher one level above that, then restores it on unlock. Without it, a high-priority subscriber gets woken by the notification, preempts the publisher, and then blocks on the channel the publisher still holds — extra context switches. I measured it: with boost off, every one of 500 non-blocking reads in the subscriber failed because the channel was still locked. The cost is two priority changes per publish and that unrelated mid-priority threads wait during the boosted section, so listeners must be short."

꼬리 질문: "What do you need to do for boost to work?" → 관찰자 스레드에서 zbus_obs_attach_to_thread(). 안 부르면 HOP를 모른다. runtime observer는 HOP 계산에 안 들어간다.

Q. "The Zephyr pipe API changed. What's different now?"

A. 4.1에서 다시 썼고 4.3에서 옛 API를 지웠다. k_pipe_write/read가 바이트 수를 반환하고 min_xfer가 없어졌다. 동적 할당과 남은 바이트 조회가 없어졌고 k_pipe_reset과 k_pipe_close가 생겼다. 의미는 "len을 다 채울 때까지 기다리고, 타임아웃이면 부분"이다. close 뒤에도 남은 데이터는 읽힌다.

"It was rewritten in Zephyr 4.1 and the legacy API was removed in 4.3. Now it's k_pipe_write and k_pipe_read returning the byte count, with no min_xfer parameter; dynamic allocation and the read/write-available queries are gone; and there are k_pipe_reset, which drops data and wakes waiters with -ECANCELED, and k_pipe_close, after which readers can still drain what's left and then get -EPIPE. A blocking read waits until the full length is satisfied, and on timeout it returns the partial count — so you must handle short reads. It's a byte stream with no message boundaries."

Q. "When would you use k_mbox?"

A. 송신자가 "수신자가 받았다"까지 기다려야 하거나, 특정 스레드를 지정해야 하거나, 큰 가변 길이 데이터를 커널 버퍼 없이 한 번에 복사하고 싶을 때다. info 값을 서로 바꾸니 짧은 응답 코드를 같이 받을 수 있다. 다만 ISR · user mode에서 안 되고, 매칭 후에는 timeout이 없으며, handoff가 msgq의 두 배 가까이 비싸서 새 코드에서는 드물다.

"When the sender needs to know the receiver actually took the data, or when you want to target a specific thread, or move a large variable-size block with a single copy from sender buffer to receiver buffer. The two sides also swap an info word, which works as a cheap acknowledgment code. The downsides: no ISR use, no syscalls for user mode, the sender's timeout only covers finding a receiver — after the match it waits forever until the receiver calls k_mbox_data_get — and the async variant can still block when its descriptor pool is empty. In my measurement it cost about 1.8 times a msgq handoff, so I usually prefer a msgq plus a response semaphore."

Q. "You're porting FreeRTOS firmware with xQueueSend everywhere to Zephyr. How do you map it?"

A. 아이템 크기로 나눈다. 작은 값 복사 큐는 k_msgq로 거의 1:1(xQueueSendToFront → k_msgq_put_front, 단 블록 안 함, FromISR는 같은 함수 + K_NO_WAIT). 포인터를 넣던 큐는 k_fifo + 첫 word 예약 또는 k_stack. stream/message buffer는 k_pipe 또는 ring_buf. 그리고 "여러 태스크에 같은 값을 뿌리려고 큐를 여러 개 만든" 곳이 zbus 후보다. 측정 없이 전부 zbus로 바꾸지는 않는다. A5의 API 대응표가 출발점이다.

"I classify by what the queue carries. Small by-value queues map almost one-to-one onto k_msgq — send-to-front becomes k_msgq_put_front, which doesn't block, and FromISR variants become the same call with K_NO_WAIT. Queues of pointers become k_fifo with a reserved first word, or k_stack for free-lists. Stream and message buffers become k_pipe or a ring_buf. Places where the code fans one value out through several queues are zbus candidates, but I wouldn't move hot paths to zbus: in my measurement a zbus subscriber handoff was seven times a msgq handoff."

Q. "Which of these IPC objects can a user-mode thread use?"

A. syscall이 있는 것만: k_msgq, k_stack, k_pipe, 그리고 k_queue의 일부(k_fifo_alloc_put, get). k_fifo_put은 커널 리스트가 user 메모리를 가리키게 되므로 syscall이 아니고, 부르면 MPU fault다. k_mbox와 zbus는 syscall이 없다.

"Only those exposed as syscalls: k_msgq, k_stack, k_pipe, and part of k_queue — get, and alloc_append, which is what k_fifo_alloc_put uses: the kernel allocates the list node from the thread's resource pool so the kernel list never points into user memory. Plain k_fifo_put isn't a syscall; calling it from a user thread faulted on the MPU when the kernel code tried to touch the fifo's tail. k_mbox and zbus have no syscalls at all, so user-mode partitions need to talk through msgq or pipe."

16. 요약 & 체크리스트#

Zephyr는 FreeRTOS의 "큐 하나"를 성질별로 나눠 놓았다. 포인터를 넘기는 k_fifo/k_lifo(k_queue, 아이템 첫 word 예약, 0 copy, 수명은 앱 책임), word 하나의 k_stack(버퍼 free-list), 고정 크기 복사의 k_msgq(put_front는 블록 안 함, purge는 reader도 -ENOMSG로 깨움, 정렬은 4.4.2 문서상 불필요), 4.1에서 다시 쓴 바이트 스트림 k_pipe(len을 다 채우거나 타임아웃이면 부분, reset/close), 송수신자가 만나는 k_mbox(대상 지정 · info 교환 · 1회 복사, 매칭 후 timeout 없음, ISR · user mode 불가). 그 위에 zbus가 채널 · 관찰자 모델을 얹는다. listener는 publisher 문맥에서 즉시, subscriber는 알림만 받고 최신값을 읽으며, msg_subscriber는 net_buf 복사본을 받되 풀이 고갈되면 뒤쪽 관찰자까지 굶긴다. 채널 잠금은 세마포어라 zbus가 HLP boost를 직접 구현한다. 측정은 같은 결론을 숫자로 줬다: time slicing을 끈 handoff에서 k_fifo 5.8 µs ≈ k_sem 5.0 µs, k_msgq 16 B 7.9 µs, k_mbox 14.3 µs, zbus subscriber 58.5 µs. CONFIG_ZBUS_MSG_SUBSCRIBER 한 줄이 모든 publish에 약 35 µs를, -Os의 바이트 memcpy가 64 B msgq에 약 14 µs를, time slicing이 모든 handoff에 약 14 µs를 더한다(모두 QEMU icount 기준). 커널 안에서는 모든 객체가 z_unpend_first_thread → swap_data로 직접 전달, 아니면 버퍼에 넣기 / z_pend_curr의 같은 골격이다.
