0. 큰 그림 — 이게 왜 필요한가#

0.1 직관 — 같은 방을 쓰는 다섯 명#

기본 FreeRTOS · Zephyr에서 모든 태스크는 한 주소 공간, 같은 특권으로 돈다(C8 §1). 비유하면 다섯 사람이 칸막이 없는 한 방에서 일하는 것이다. 비행 제어 담당, 무선 패킷 파서 담당, 페이로드 통신 담당, 외주 업체가 준 라이브러리, 그리고 커널(방의 관리인)이 다 같은 책상을 쓴다. 파서 담당이 실수로 책상 위 서류를 쏟으면(버퍼 오버런) 비행 제어 담당의 서류(자세 추정 상태)와 관리인의 장부(TCB · ready list)가 같이 젖는다. 기체가 떨어진다.

유저 모드 격리는 방에 칸막이와 열쇠를 다는 일이다.

  • 칸막이 = MPU: 각 태스크는 자기 칸(스택 + 허락받은 메모리)만 만질 수 있다. 칸 밖을 만지면 하드웨어가 즉시 MemManage 폴트를 낸다.
  • 열쇠 = 특권 레벨 + 시스템 콜: 관리인(커널)에게 일을 시키려면 창구(SVC)로 가서 신청서를 내야 하고, 관리인은 신청서(인자)를 검사한다(C8).
  • 사고 처리 규정 = 폴트 정책: 한 칸에서 사고가 나면 그 칸 사람만 내보내고 새 사람을 앉힌다(재시작). 나머지는 계속 일한다.

그림 1 — 격리가 없는 빌드(왼쪽)에서는 파서의 오버런이 커널 데이터 · 드라이버 상태까지 닿는다. 격리 빌드(오른쪽)에서는 신뢰하기 어려운 코드만 MPU 경계 아래(user 모드)로 내리고, 각자 자기 파티션만 쓰게 한다. 폴트가 나면 그 태스크만 정리한다.

  • 메모리: v7-M MPU는 리전 크기가 2의 거듭제곱이고 크기에 정렬되어야 한다(F4). 300 B짜리 버퍼가 512 B를 먹는다. 시스템 콜 전용 스택도 스레드마다 붙는다. → §7.3에서 v7-M vs v8-M로 잰다.
  • 복잡도: 누가 어떤 메모리 · 어떤 객체를 쓰는지 전부 적어 줘야 한다. 전역 변수 하나 읽는 데도 허락이 필요하다(C8 예제 6에서 이미 부딪혔다).

2. Zephyr userspace ① — 메모리: partition과 domain#

2.1 직관 — 방과 열쇠 꾸러미#

  • partition = 방 하나. "0x20000840부터 32바이트, user RW" 같은 연속 메모리 + 속성. 구조체 struct k_mem_partition { uintptr_t start; size_t size; k_mem_partition_attr_t attr; }.
  • memory domain = 열쇠 꾸러미. 파티션 여러 개의 묶음. 스레드는 정확히 한 도메인에 속하고, user 스레드는 (자기 스택 + 자기 도메인의 파티션)만 만질 수 있다.
  • 같은 방 열쇠를 여러 꾸러미에 넣을 수 있다 → 공유 메모리.
  • 도메인을 지정하지 않은 스레드는 만든 스레드(부모)의 도메인을 물려받는다. 맨 처음에는 모두 k_mem_domain_default(mem_domain.h 109행)에 있다.

SSD 펌웨어로 말하면, 코어마다 접근 가능한 SRAM 창을 버스 방화벽으로 나누던 것과 같다. 차이는 스레드가 바뀔 때마다 그 창을 다시 짠다는 것이다 — Zephyr는 컨텍스트 스위치 때 z_arm_configure_dynamic_mpu_regions()(arch/arm/core/cortex_m/swap_helper.S 222행에서 호출)로 새 스레드의 도메인 파티션 + 스택을 MPU에 올린다.

출력에서 볼 것:

  • 공유가 된다: B는 자기 도메인의 part_sh로 A가 쓴 shared_seq(1, 2, 3, 3, 3, 3)를 읽어 15를 더했다.
  • 도메인당 파티션 최대 5개: arch_mem_domain_max_partitions_get()은 하드웨어가 정한다. 소스(arch/arm/core/mpu/arm_core_mpu.c 352행)는 "MPU 리전 수 − 커널이 고정으로 쓰는 정적 리전 − 스레드 스택 리전 1개"를 돌려준다. 8리전 M3에서 5가 나왔으니 정적 리전이 2개라는 뜻이다. mps2/an521/cpu0(M33)에서도 같은 프로그램이 5를 찍었다. Kconfig CONFIG_MAX_DOMAIN_PARTITIONS의 기본값은 16이지만, 커널은 부팅 때 max_partitions = arch_mem_domain_max_partitions_get()(kernel/mem_domain.c 403행)로 하드웨어 한도를 쓴다.
  • 파티션이 각각 32바이트다. a_private[8]은 32바이트라 딱 맞고, shared_seq 하나(4바이트)도 32바이트를 먹는다 — v7-M MPU 리전의 최소 크기가 32바이트다(F4).

이제 침범을 시킨다.

출력에서 볼 것:

  • MMFAR Address 0x20000860 = b_private(nm), 0x200010d8 = kernel_side. 하드웨어가 정확히 그 주소에서 막았다. r2/a3: 0x0000dead는 쓰려던 값이다.
  • reason 19는 K_ERR_ARM_MEM_DATA_ACCESS다. ARM 아키텍처 에러 코드는 K_ERR_ARCH_START(16)부터 K_ERR_ARM_MEM_GENERIC, ..._STACKING, ..._UNSTACKING, ..._DATA_ACCESS 순이라(include/zephyr/arch/arm/arch.h 61–64행) 16 + 3 = 19다. 로그가 Unknown error라고 찍는 건 공용 reason_to_str()(kernel/fatal.c)이 아키텍처 코드를 모르기 때문이다.
  • A만 죽었다. [fatal] 줄은 f5z.h의 재정의 핸들러가 찍었다. 핸들러가 return하자 커널이 A를 abort했고, B는 still alive, main은 join을 마치고 끝까지 갔다. C8 예제 13은 같은 종류의 위반에서 Halting system으로 시스템 전체가 멈췄다 — 차이는 핸들러 하나다(§5).

2.4 app_smem — 파티션은 링커가 만든다#

K_APP_BMEM(part_b)는 변수에 data_smem_part_b_bss 섹션 이름을 붙일 뿐이다(app_memdomain.h 40행). 진짜 배치는 빌드가 두 번 링크하면서 만든다: 1차 ELF에서 gen_app_partitions.py가 data_smem_* 섹션을 모두 찾고, 파티션마다 정렬 규칙을 넣은 링커 스크립트 조각(app_smem_aligned.ld)을 생성하고, 그걸로 최종 링크를 한다.

(nm 출력은 size/part_start 줄만 남겼다.)

출력에서 볼 것:

  • 파티션마다 앞뒤로 SMEM_PARTITION_ALIGN(크기)가 들어간다. v7-M에서는 "다음 2의 거듭제곱으로 정렬 + 크기도 그만큼"이 된다. part_sh는 실제 데이터 4바이트(bss_size 4)인데 파티션은 32바이트(part_size 0x20)다.
  • 앱이 정의하지 않은 파티션 두 개가 이미 있다. z_malloc_partition(2 KB — libc malloc 아레나)과 z_libc_partition(64 B — libc 전역). libc-hooks.h가 설명하듯 user 스레드가 libc를 쓰려면 이 파티션을 자기 도메인에 넣어야 한다. 이 예제의 dom_a/dom_b에는 넣지 않았는데도 printk가 됐다 — printk는 문자열 출력 시스템 콜(k_str_out)로 커널이 대신 찍기 때문이다. user 스레드에서 snprintf나 malloc을 쓰면 이야기가 다르다.
  • 데이터 영역 전체(_app_smem_size 0x8a0 = 2208 B)가 RAM 맨 앞 0x20000000에 모인다. 정렬이 큰 파티션부터 놓아 구멍을 줄인다.

그림 2 — 예제 1의 실제 배치. 초록 part_sh는 두 도메인에 모두 들어 있어 공유 메모리가 된다. 컨텍스트 스위치 때 커널은 다음 스레드의 도메인 파티션과 스택만 MPU에 올린다.

2.5 흔한 함정 (파티션 · 도메인)#

  • 파티션 6개째: 도메인당 하드웨어 한도(이 보드 5)를 넘기면 k_mem_domain_init/add_partition이 -EINVAL/-ENOSPC로 실패한다(kernel/mem_domain.c 105 · 235행의 CHECKIF). 반환값을 안 보면 "왜 이 스레드만 폴트?"로 하루를 쓴다. 파티션은 기능 단위로 크게 묶는다.
  • 한 도메인 안의 겹치는 파티션: 같은 도메인에 겹치는 두 파티션을 넣으면 거절된다(mem_domain.c 63–78행 overlaps existing 로그). 다른 도메인끼리 같은 파티션을 공유하는 것은 괜찮다(예제 1의 part_sh).
  • libc를 쓰는 user 스레드: z_libc_partition을 도메인에 안 넣으면 libc 전역(예: errno 저장소, 스택 카나리)을 건드리는 순간 폴트. 기본 도메인에는 들어 있다.
  • K_APP_BMEM에 큰 배열 하나와 작은 변수 여러 개를 섞기: 파티션은 통째로 2의 거듭제곱으로 반올림된다. 5000 B + 4 B = 8 KB(§7.3). 크기를 2의 거듭제곱 바로 아래로 맞추거나, v8-M을 쓴다.
  • 도메인 이동은 스레드 단위: k_mem_domain_add_thread는 그 스레드를 옮긴다. 그 스레드가 이미 만든 자식은 따라오지 않는다(자식은 만들어질 때 부모 도메인을 물려받았다).

3. Zephyr userspace ② — 커널 객체 권한#

3.1 직관과 정의#

메모리 격리만으로는 부족하다. user 스레드도 k_sem_give(&sem)처럼 커널 객체의 주소를 시스템 콜로 넘길 수 있다. 커널은 특권으로 그 주소에 쓰므로, 검사가 없으면 user 스레드가 "커널아, 0x20000100에 있는 세마포어를 줘"라고 속여 커널 메모리를 대신 쓰게 할 수 있다(C8 §3.3의 confused deputy).

Zephyr의 답은 두 겹이다.

  1. 이 주소가 정말 커널 객체인가: 빌드 때 gen_kobject_list.py가 ELF에서 모든 커널 객체(k_sem, k_msgq, k_thread, 스레드 스택 …)를 찾아 gperf perfect hash 표를 만든다(C8 §4.1). 런타임에 k_object_find()(kernel/userspace.c 560행)가 이 표에서 주소를 찾는다. 없으면 "not a known kernel object".
  2. 이 스레드가 그 객체의 권한을 가졌나: 객체마다 스레드 권한 비트맵이 있다(스레드마다 0, 1, 2 … 인덱스). 비트가 꺼져 있으면 "does not have permission".

권한을 주는 방법:

API쓰는 곳효과
k_object_access_grant(obj, thread)supervisor 또는 권한을 가진 user (syscall)그 스레드의 비트를 켠다
k_thread_access_grant(thread, obj1, obj2, …)supervisor여러 객체를 한 번에 grant하는 매크로 (kernel.h 489행)
K_INHERIT_PERMS 스레드 옵션스레드를 만들 때부모가 가진 권한을 자식에게 복사 (kernel/thread.c 698행 → k_thread_perms_inherit)
k_object_access_revoke(obj, thread) / k_object_release(obj)supervisor / 자기 권한 반납비트를 끈다
k_object_access_all_grant(obj)supervisor모든 스레드에 공개 (보안상 신중히)

3.2 예제 2 — grant, 상속, 객체가 아닌 포인터, 그리고 스스로 user로 내려가기#

무엇을 확인하나: (1) grant 받은 세마포어는 되고 안 받은 것은 oops, (2) user 스레드가 만든 손자 스레드는 K_INHERIT_PERMS가 있어야 부모의 권한을 갖는다, (3) 커널 객체가 아닌 주소를 넘기면?, (4) supervisor로 시작해 초기화 후 k_thread_user_mode_enter()로 한 방향으로 내려가는 패턴.

(BAD1 · BAD2의 레지스터 덤프 4줄은 BAD0/INHERIT0과 같아서 ...로 줄였다.)

출력에서 볼 것:

  • INHERIT=0: 권한 비트맵이 01 00이다. 스레드 인덱스 0(U1)의 비트만 켜져 있고 U2(인덱스 1)는 꺼져 있다. → Kernel oops(reason 3), U2만 죽고 U1은 child joined으로 계속 간다. U2에 이름을 안 붙여서 thread=가 비었다.
  • INHERIT=1: 같은 코드에서 U2가 세마포어를 쓴다. "필요한 권한을 가진 부모 user 스레드가 일꾼을 만들어 쓰는" 구조에 쓴다. 단, 부모가 가진 모든 권한이 복사되므로 최소 권한 원칙과 부딪힌다 — 자식이 정말 필요한 것만 쓰게 하려면 상속 대신 supervisor가 grant한다.
  • user 스레드가 스레드를 만들려면 스레드 객체(th_u2)와 스택 객체(st_u2)의 권한도 필요하다. 그래서 main이 k_thread_access_grant(u1, &sem_a, &th_u2, &st_u2)로 세 개를 줬다. 스택도 커널 객체다.
  • BAD2: 그냥 배열 주소를 세마포어로 넘기면 address is not a known kernel object. 커널은 그 주소를 건드리지도 않고 거절한다(gperf 표 조회에서 끝남). FreeRTOS v2는 같은 문제를 "핸들 = 인덱스"로 풀었다(C8 예제 9 BAD5).
  • BAD3: k_thread_user_mode_enter 전에는 FPGAIO 카운터를 읽었는데(supervisor), 내려간 뒤에는 같은 주소에서 MPU FAULT. 특권은 한 번 내리면 스스로 못 올린다 — 이게 "초기화는 특권으로, 그 다음 평생 user로" 패턴의 핵심이다. 드라이버를 열고 하드웨어를 설정한 뒤 내려가면, 공격자가 이 스레드를 장악해도 하드웨어 설정을 바꿀 수 없다.

4. Zephyr userspace ③ — 나만의 시스템 콜#

4.1 왜 앱이 시스템 콜을 만드나#

user 스레드가 직접 못 하는 일이 있다: 특권 전용 하드웨어(보정 데이터가 든 OTP, 암호 엔진, 모터 출력) 접근, 커널 쪽 데이터 읽기. 그렇다고 그 스레드를 supervisor로 올리면 격리가 사라진다. 해법은 좁은 문을 하나 더 내는 것이다 — 정확히 필요한 일만 하고, 인자를 철저히 검사하는 시스템 콜. 드라이버 API(i2c_transfer 등)도 Zephyr에서는 이렇게 __syscall로 감싸여 있다.

만드는 순서 (v4.4.2, samples/userspace/prod_consumer의 app_syscall.c와 같은 방식):

  1. 헤더에 __syscall 선언. 헤더 끝에 #include <zephyr/syscalls/<헤더 이름>.h> (빌드가 생성).
  2. prj.conf에 CONFIG_APPLICATION_DEFINED_SYSCALL=y — 앱 소스 폴더도 __syscall을 찾게 한다(Kconfig.zephyr 1015행). 앱 밖 폴더면 CMake의 zephyr_syscall_header()(cmake/modules/extensions.cmake 1781행).
  3. z_impl_<이름>(): 진짜 일. supervisor는 이걸 바로 부른다.
  4. z_vrfy_<이름>(): user에서 왔을 때만 거치는 검사. 그리고 #include <zephyr/syscalls/<이름>_mrsh.c>.

4.2 예제 3 — 보정값 읽기(쓰기 포인터)와 CRC(읽기 버퍼) 시스템 콜#

무엇을 확인하나: 앱 정의 syscall 두 개가 좋은 포인터에서는 동작하고, 커널 주소를 넘기면 z_vrfy_가 막는지. 그리고 "값이 틀린 것"과 "포인터가 틀린 것"을 다르게 처리하는 규칙.

CMakeLists.txt는 target_sources(app PRIVATE src/main.c src/f5_cal.c), prj.conf에는 공통 6줄 + CONFIG_APPLICATION_DEFINED_SYSCALL=y.

출력에서 볼 것:

  • 같은 함수, 다른 대접: main(supervisor)은 f5_crc32(cal_table)을 문제없이 계산했다. user 스레드가 같은 주소를 넘기자 read access denied. 검사는 "이 주소가 나쁜가"가 아니라 "이 호출자가 이 주소를 읽을 수 있나"다.
  • BAD1이 confused deputy 공격의 모양이다: user가 "결과를 커널 주소 0x2000086c(cal_table 자신)에 써 줘"라고 요청한다. z_impl_은 특권이라 그대로 썼다면 보정 테이블을 덮어썼을 것이다. K_SYSCALL_MEMORY_WRITE가 막았다.
  • 값 오류 vs 포인터 오류: idx=9는 -22(-EINVAL)로 돌려주고 스레드는 계속 산다. 나쁜 포인터는 oops로 스레드를 죽인다. Zephyr 문서의 원칙과 같다 — 잘못된 값은 정상적인 에러이고, 접근할 수 없는 메모리나 객체를 넘기는 것은 버그 또는 공격이므로 그 스레드를 끝낸다.

4.3 생성된 코드와 기계어로 확인#

출력에서 볼 것: 앱 syscall도 커널 syscall과 완전히 같은 기계에 올라탄다. 번호(5, 6)를 받고, _k_syscall_table 804–805행에 마샬링 함수가 들어갔다. 번호는 빌드마다 이름순으로 다시 매겨지므로 바이너리 호환 ABI가 아니다 — 커널과 앱을 항상 같이 빌드하는 MCU라서 괜찮은 설계다.

user 쪽 진입과 검사 쪽을 기계어로 본다.

출력에서 볼 것:

  • user 쪽: arch_is_user_context()가 0이면 b.w z_impl_f5_cal_read(꼬리 호출), 1이면 r6 = 5(syscall 번호), svc 3. C8 §4.3의 k_sem_give와 같은 모양이다.
  • 검사 쪽: z_vrfy_가 인라인되어 z_mrsh_ 안에 들어갔다. arch_buffer_validate(out, 4, write=1)이 0이 아니면 로그를 찍고 arch_syscall_oops로 간다. (생략한 가운데 부분은 실패 로그 문자열을 준비하는 코드다.)
  • arch_buffer_validate는 표를 보지 않고 MPU 레지스터를 본다. v7-M 구현(arch/arm/core/mpu/arm_mpu_v7_internal.h 172행 mpu_buffer_validate)은 인터럽트를 잠그고 MPU 리전을 높은 번호부터 훑어, 그 버퍼를 덮는 리전이 user 접근을 허락하는지 본다. 지금 MPU에는 호출한 스레드의 도메인과 스택이 올라와 있으므로, "이 스레드가 직접 접근할 수 있었을 메모리인가"를 하드웨어 규칙 그대로 판정하는 셈이다.

그림 3 — 예제 3의 f5_cal_read가 지나는 두 길. 검사는 user에서 들어온 경우에만 하고, 그 기준은 "호출한 스레드의 MPU 설정"이다.

4.4 검증 함수를 쓸 때의 규칙#

  1. 모든 포인터 인자를 검사한다. 읽을 버퍼는 K_SYSCALL_MEMORY_READ, 쓸 버퍼는 K_SYSCALL_MEMORY_WRITE, 배열은 K_SYSCALL_MEMORY_ARRAY_READ/WRITE(개수 × 크기 곱셈 오버플로까지 본다), 커널 객체는 K_SYSCALL_OBJ(ptr, K_OBJ_SEM), 초기화 전 객체는 K_SYSCALL_OBJ_INIT, 드라이버는 K_SYSCALL_DRIVER_OP(전부 include/zephyr/internal/syscall_handler.h).
  2. TOCTOU를 막는다. 검사한 뒤 z_impl_이 user 메모리를 다시 읽으면, 그 사이에 같은 도메인의 다른 user 스레드가 값을 바꿀 수 있다(검사 시점과 사용 시점이 다르다 — Time Of Check to Time Of Use). 길이 필드처럼 검사에 쓰인 값은 k_usermode_from_copy()로 커널 쪽 지역 변수에 복사한 뒤 그 복사본을 쓴다. 공식 샘플 prod_consumer/src/app_syscall.c가 정확히 이렇게 한다(cookie_copy). 예제 3의 f5_crc32는 결과만 계산하므로 TOCTOU가 문제되지 않지만, "길이를 읽고 그 길이만큼 복사"하는 syscall이라면 반드시 복사본을 써야 한다.

  4. z_impl_은 신뢰하는 쪽에서도 불린다. 그러니 z_impl_에는 값 범위 검사(예제의 idx)를 두고, 포인터 접근성 검사는 z_vrfy_에만 둔다.
  5. 문을 넓히지 않는다. "주소와 길이를 받아 아무 메모리나 읽어 주는 디버그 syscall"은 격리를 통째로 무너뜨린다. syscall 하나하나가 공격 표면이다.

5.1 fatal 핸들러가 정책이다#

z_fatal_error()(kernel/fatal.c 84행 이후)의 흐름:

  1. 로그 >>> ZEPHYR FATAL ERROR <reason>: ...
  2. k_sys_fatal_error_handler(reason, esf) 호출 — 기본 구현은 __weak이고 arch_system_halt()로 시스템을 멈춘다(같은 파일 37–46행).
  3. 핸들러가 return하면 "시스템을 멈추지 않기로 정책을 정했다"고 보고 현재 스레드를 abort한다(119–133행 주석 그대로: "If the system fatal error handler returns, then kill the faulting thread"). 단 ISR 안에서 난 폴트는 무조건 panic이다.

5.2 예제 4 — 파서가 죽으면 감독이 다시 만든다, 비행 제어는 계속 돈다#

무엇을 확인하나: (1) 외부에서 온 패킷의 길이 필드를 믿는 user 파서가 오버런으로 MPU 폴트, (2) 감독(supervisor) 스레드가 k_thread_join으로 죽음을 알아채고 같은 스레드 객체 · 스택으로 다시 만든다, (3) 최고 우선순위 2 ms 비행 제어 루프의 주기가 폴트 없을 때와 같은지. prj.conf에 CONFIG_SYS_CLOCK_TICKS_PER_SEC=1000을 더했다.

(두 번째 폴트의 덤프는 첫 번째와 같아 ...로 줄였다.)

출력에서 볼 것:

  • 폴트 주소가 파티션 끝이다. 파티션은 0x20000840–0x2000087F(64 B: parsed 4 B + frame 32 B → 64로 반올림), 폴트는 0x20000880. r0 = 0xc8(200)은 길이 필드, r3 = 0x3d(61)은 루프 인덱스다. 즉 frame[32]부터 frame[59]까지 28바이트는 폴트 없이 덮어썼다. 파티션의 반올림된 빈 공간이었기에 이번에는 피해가 없었지만, 그 자리에 같은 파티션의 다른 변수가 있었다면 조용히 깨졌을 것이다. MPU는 경계만 지킨다.
  • 파서만 죽고 다시 태어났다: 12개 중 10개 파싱(손상 패킷 2개만 버림), 재시작 2번. 폴트부터 새 파서가 준비되기까지 120 us(QEMU icount, 폴트 로그를 UART로 찍는 시간 포함).
  • 비행 제어 주기는 그대로: 폴트가 있을 때와 없을 때 주기 min/max가 1944/2062 us로 똑같다. 폴트 처리는 우선순위 6짜리 파서의 문맥에서 일어나고, 감독은 우선순위 3이라 우선순위 1인 비행 제어를 밀어내지 않는다. (±60 us 흔들림 자체는 폴트와 무관한 기본 지터다 — 이 QEMU 구성의 Zephyr SysTick 타임키핑에서 주기마다 약 1 us씩 밀리는 현상도 함께 보였다. FreeRTOS 예제 7은 같은 측정에서 1998/2001 us였다.)
  • 한계 하나: Zephyr의 fatal 처리 경로(z_fatal_error)는 arch_irq_lock()을 잡고 로그를 찍는다. 로그가 길면 그동안 모든 인터럽트가 막힌다. 이 실행에서는 마침 비행 제어의 깨어날 시각과 겹치지 않았지만, 실제 제품에서는 폴트 덤프 수준(CONFIG_FAULT_DUMP)과 로그 백엔드를 줄이거나, 고주파 제어를 인터럽트(ISR) 쪽에 두어야 한다. 이 노트는 그 최악 경우를 따로 재지 않았다.

재시작 설계에서 지킨 것:

  • 같은 객체 재사용: k_thread_join이 돌아왔다면 그 스레드는 완전히 죽었으므로 th_p/st_p를 다시 k_thread_create에 넣어도 된다.
  • 권한 · 도메인은 스레드에 붙는다: 새 스레드는 새 권한 인덱스로 시작하므로 k_mem_domain_add_thread와 k_object_access_grant를 매번 다시 한다(start_parser).
  • 상태 초기화: 파서의 작업 버퍼는 어차피 다음 패킷이 덮어쓰지만, 상태 기계가 있는 태스크라면 재시작 때 자기 파티션을 지우고(supervisor가 memset) 시작해야 한다. 죽기 전 상태를 믿지 않는다.
  • 재시작 폭주 방지: 실제로는 "N초 안에 M번 이상 죽으면 그 기능을 끄고 안전 모드" 같은 백오프가 필요하다(E8의 리셋 루프 → safe mode와 같은 생각).

그림 4 — 예제 4(Zephyr)와 예제 7(FreeRTOS)의 폴트 처리 순서. 핵심은 폴트 처리와 재생성이 비행 제어보다 낮은 우선순위에서 일어난다는 것이다. 숫자는 QEMU icount 측정값(폴트 로그 출력 시간 포함).

6.1 C8 빌드 위에서 시작#

빌드는 C8 §3.5를 그대로 복사했다(ARM_CM3_MPU 포트, 래퍼 v2, configPROTECTED_KERNEL_OBJECT_POOL_SIZE 16, configENABLE_ACCESS_CONTROL_LIST 1, 링커 섹션 privileged_functions/freertos_system_calls/privileged_data). 바뀐 것 하나: 랩 템플릿 startup.c가 10-25 수정으로 .preinit_array/.init_array를 돌게 되어, C8의 링커 스크립트로는 undefined reference to '__preinit_array_start'로 링크가 실패했다. 두 줄을 더했다.

restricted 태스크를 만드는 재료(V11.3.2 소스에서 확인):

  • TaskParameters_t(include/task.h 151행): pvTaskCode, pcName, usStackDepth, pvParameters, uxPriority, puxStackBuffer, xRegions[portNUM_CONFIGURABLE_REGIONS], 그리고 정적 할당이 켜져 있으면 pxTaskBuffer. 지정 초기화(.field =)로 쓰자 — 위치 초기화로 쓰면 pxTaskBuffer를 빠뜨려 -Wextra가 missing initializer 경고를 낸다(예제 8 첫 빌드에서 겪었다).
  • xRegions 원소 MemoryRegion_t { pvBaseAddress, ulLengthInBytes, ulParameters }. ARM_CM3_MPU에서 portNUM_CONFIGURABLE_REGIONS는 3이고, 스택이 리전 3(portSTACK_REGION)을 쓴다.
  • ulParameters(ARM_CM3_MPU/portmacro.h 81–87행): portMPU_REGION_READ_WRITE, portMPU_REGION_READ_ONLY, portMPU_REGION_PRIVILEGED_READ_ONLY, portMPU_REGION_PRIVILEGED_READ_WRITE, portMPU_REGION_PRIVILEGED_READ_WRITE_UNPRIV_READ_ONLY, portMPU_REGION_CACHEABLE_BUFFERABLE, portMPU_REGION_EXECUTE_NEVER.
  • 만들기: xTaskCreateRestricted(&params, &handle)(TCB는 힙, 스택은 puxStackBuffer) 또는 xTaskCreateRestrictedStatic(TCB도 pxTaskBuffer). 실행 중 리전 바꾸기: vTaskAllocateMPURegions(handle, regions).

6.2 예제 7 — MemManage 핸들러를 직접 쓰고, 감독 태스크가 지우고 다시 만든다#

FreeRTOS 포트는 MemManage 핸들러를 제공하지 않는다(ARM_CM3_MPU/port.c에서 portNVIC_MEM_FAULT_ENABLE로 폴트를 켜기만 한다, 1183행). 정책은 앱 몫이다. 설계:

  1. MemManage 핸들러(Handler 모드 = 특권)는 CFSR · MMFAR · 쌓인 PC를 기록하고, MMFSR 비트를 지운다(write-1-to-clear).
  2. 쌓인 예외 프레임의 복귀 PC를 parked()로 바꾼다. 그대로 복귀하면 같은 명령을 다시 실행해 무한 폴트가 난다.
  3. 감독 태스크에 vTaskNotifyGiveFromISR로 알린다. 이 호출이 되는 이유가 중요하다: v2에서 ...FromISR API는 SVC 래퍼가 아니라 특권 전용 래퍼(mpu_wrappers.h 74–80행, mpu_wrappers_v2.c 2142행 MPU_vTaskGenericNotifyGiveFromISR, PRIVILEGED_FUNCTION)라서 Handler 모드에서 그냥 함수로 불린다. C8 §3.11의 경고("폴트 핸들러에서 API를 부르면 HardFault로 번진다")는 SVC를 쓰는 일반 API 이야기다.
  4. 감독(특권, 파서보다 높은 우선순위)이 vTaskDelete로 파서를 지우고 같은 스택 버퍼로 xTaskCreateRestricted, ACL을 다시 준다.

출력에서 볼 것:

  • 격리 · 재시작은 됐다: 폴트 2번, 재시작 2번, 폴트 → 새 파서까지 57 us. 비행 제어 주기는 폴트가 있든 없든 1998/2001 us로 같다. 새 파서의 핸들은 다시 2다 — vTaskDelete가 커널 객체 풀의 칸을 돌려줬고, 다음 생성이 같은 칸을 받았다.
  • 그런데 parsed가 이상하다. 폴트가 없으면 12인데, 폴트가 있으면 재시작 때 0, 끝에 3이다. 손상 패킷 2개만 버렸다면 10이어야 한다. 이유: pz는 frame[32] 바로 뒤에 parsed가 붙은 36바이트 구조체(nm 크기 0x24)이고 리전은 64바이트다. 길이 200짜리 패킷이 frame[32..35] = parsed 자리를 0으로 덮어쓴 뒤 리전 끝 0x20009040에서 폴트가 났다. 리전 안의 손상은 MPU가 못 막는다. 예제 4의 Zephyr 버전은 우연히 parsed가 frame 앞에 배치되어(0x20000840 vs 0x20000844) 피해를 피했을 뿐이다.
  • 교훈 두 개: (1) 재시작한 태스크는 자기 리전의 상태를 믿으면 안 된다 — 감독이 리전을 초기화하거나, 지켜야 할 카운터는 다른 리전(또는 커널 쪽)에 둔다. (2) 같은 리전 안에서도 버퍼 뒤에 중요한 변수를 두지 않는다(카나리 · 길이 검사는 여전히 필요하다 — 격리는 길이 검사를 대신하지 않는다).
  • 첫 시도에서 파서가 전역 rxq를 읽다가 매 패킷마다(0x2000881c = rxq) 폴트 → 재시작을 수백 번 반복했다. C8 예제 6과 같은 함정이고, 재시작 루프가 있으면 증상이 "멈춤"이 아니라 "조용히 끝없이 재시작"으로 바뀐다. 재시작 횟수 감시가 필요한 이유다.

7. 비용 — API 한 번이 아니라 앱 전체로 잰다#

C8은 API 한 번의 비용을 쟀다(비특권 xQueueSend 13.2 us vs 특권 6.9 us, Zephyr user k_msgq_put 12.4 us vs supervisor 2.7 us). 그런데 실제 질문은 "내 데이터 흐름이 얼마나 느려지나"다. 그래서 같은 producer/consumer 작업을 격리 없음 / 격리 빌드의 특권 쪽 / 격리 빌드의 비특권 쪽으로 돌리고, 메시지 하나에 항목 1개(배치 1)와 16개(배치 16), 항목당 계산 0회와 100회(work)를 바꿔 본다. 소비자 우선순위가 높아서 배치 1이면 항목마다 컨텍스트 스위치 2번이 일어나는 최악 형태다.

7.3 숫자를 읽는 법 — 차트 두 장#

그림 6 — 예제 5 · 9에서 잰 항목 하나당 시간(work=0, QEMU icount, 실제 칩과 절대값은 다르다). 초록 = 격리 없는 빌드, 파랑 = 격리 빌드의 특권 쪽, 주황 = 격리 빌드의 비특권 쪽. 왼쪽과 오른쪽은 축 눈금이 10배 다르다.

그림 7 — 격리 비용을 "격리 없는 빌드 대비 항목당 추가 시간"으로 본 것(예제 5 · 9의 차이를 계산). 배치 16이 추가 시간을 약 15분의 1로 줄이고, 계산이 많을수록 비율이 작아진다.

읽는 법:

  1. 비특권 쪽 추가 비용의 정체는 시스템 콜 2번이다. 배치 1에서 user − supervisor = 77323 − 53785 = 23.5 us(Zephyr), restricted − 특권 = 46018 − 33326 = 12.7 us(FreeRTOS). 항목 하나가 put 한 번 + get 한 번이므로 시스템 콜 하나에 약 11.8 us / 6.3 us다. C8에서 API 단독으로 잰 차이(Zephyr k_msgq_put +9.8 us, FreeRTOS xQueueSend +6.3 us)와 맞는다.
  2. 격리 빌드는 특권 쪽도 느리다. Zephyr USERSPACE=y의 supervisor 스레드가 =n보다 34% 느리다(53.8 vs 40.0 us). 이유: 컨텍스트 스위치마다 swap_helper.S가 z_arm_configure_dynamic_mpu_regions()를 불러 MPU 리전을 다시 쓰고(CONFIG_USERSPACE면 항상), 모든 API 인라인이 z_syscall_trap() 검사를 한다(C8 §4.3). FreeRTOS-MPU 특권 쪽은 기본 포트보다 15% 느리다(33.3 vs 29.0 us) — 특권 태스크도 MPU_*Impl의 인덱스 변환을 거치고(C8 §5.2), 스위치마다 태스크 리전을 MPU에 올린다.
  3. 배치가 가장 큰 무기다. 배치 16으로 추가 비용이 Zephyr 37.3 → 2.5 us, FreeRTOS 17.0 → 1.1 us로 줄었다. 시스템 콜과 컨텍스트 스위치 수가 1/16이 되니까. 격리 경계를 넘는 데이터는 묶어서 넘긴다.
  4. 진짜 일이 크면 비율이 작아진다. 배치 16 + work 100이면 추가 비용이 Zephyr 13%, FreeRTOS 7%다. 비특권으로 보낼 코드는 "경계를 드물게 넘고, 안에서 오래 계산하는" 코드가 좋다(파서, 퓨전, 압축, 프로토콜 스택).

그림 8 — 예제 6의 실행 출력. 회색 = 요청, 빨강 = v7-M(an385), 초록 = v8-M(an521). v7-M은 300 B가 512 B, 5000 B가 8192 B가 된다.

8. 설계 — 무엇을 user 모드로 보내고, 죽으면 어떻게 하나#

8.1 경계를 긋는 원칙#

  1. 신뢰 경계를 따라 긋는다. 외부 바이트를 처음 만지는 코드(무선 링크 파서, CAN 진단, USB, 네트워크 스택), 서드파티 · 바이너리 라이브러리, 현장 업데이트되는 모듈이 user 쪽이다. 우리가 쓰고 검증한 제어 코드는 특권 쪽이다.
  2. 고주파 경로에는 경계를 두지 않는다. IMU ISR → rate loop → 모터 출력처럼 kHz로 도는 경로는 특권(또는 ISR)에 둔다. §7에서 경계 한 번 넘는 비용이 수 us였다. 8 kHz(125 us 주기)에서 그건 예산의 수 %씩이다.
  3. 경계는 좁고 드물게. user와 특권은 큐 하나 · 시스템 콜 몇 개로만 만나고, 데이터는 배치로 넘긴다(배치 16 → 추가 비용 1/15).
  4. 공유 메모리는 단방향 · 읽기 전용부터. 상태를 공유해야 하면 쓰는 쪽 하나, 읽는 쪽은 RO 파티션/리전(예제 1 · 8). 양방향 공유는 동기화와 TOCTOU 문제를 다시 불러온다.
  5. 권한은 최소로, 상속은 신중히. K_INHERIT_PERMS는 편하지만 부모 권한 전부를 넘긴다. 객체마다 grant가 감사(audit)하기 쉽다.
  6. 설정을 검증한다. v7-M이면 모든 리전 · 스택 크기가 2의 거듭제곱이고 크기 정렬인지, map 파일에서 리전 꼬리에 무엇이 붙었는지 CI에서 검사한다(예제 8의 구멍).

8.4 ARINC 653, 안전 인증과의 관계#

  • ARINC 653은 파티션을 공간 분할(메모리)과 시간 분할(시간 창) 두 축으로 정의한다. C11 §5에서 시간 분할만 FreeRTOS 위에 직접 만들었고, 이 노트의 MPU 도메인이 공간 분할 쪽이다. 둘을 합치면 "IMA식 파티션"의 MCU 버전이 된다. 진짜 ARINC 653 RTOS(VxWorks 653, PikeOS, Deos 등)는 이것을 MMU · 하이퍼바이저 수준에서 인증 가능한 형태로 제공한다(A6, O6).
  • ISO 26262 · IEC 61508의 freedom from interference: 서로 다른 안전 등급의 소프트웨어를 한 MCU에 올리려면 메모리 간섭(이 노트), 시간 간섭(C11, N), 통신 간섭(큐 · 메시지 무결성)이 없음을 보여야 한다. MPU 격리는 메모리 쪽 근거이고, 인증 RTOS(SAFERTOS, Zephyr의 안전 인증 작업 등)는 그 장치가 맞게 동작한다는 증거까지 제공한다. 자세한 것은 O 모듈.
  • 이 노트의 발견을 안전 관점에서 다시 쓰면: 격리 장치의 설정 오류(예제 8의 리전 반올림) 자체가 간섭 경로다. 안전 분석에서 "MPU를 켰다"는 근거가 아니다. "모든 리전이 의도한 범위만 연다"를 검증해야 근거가 된다.

10.1 드론 비행 제어기 — "파서가 죽어도 기체는 난다"를 시험으로 만든다#

격리를 했다고 끝나지 않는다. 예제 4 · 7을 그대로 HIL · CI 시험으로 만든다: 퍼저(fuzzer)가 링크 파서에 손상 패킷을 넣고, 시험은 (1) 파서 재시작 횟수, (2) 비행 제어 주기 min/max(예제의 fc_dmin/fc_dmax), (3) 자세 추정 상태의 CRC가 바뀌지 않았는지를 본다. 면접에서 "격리했다"보다 "격리를 이렇게 시험했다"가 훨씬 강하다.

10.2 로봇 관절 컨트롤러 — 경계의 위치가 곧 성능#

20 kHz FOC 루프는 ADC ISR 안에서 끝나므로 격리 비용이 0이다(ISR은 Handler 모드 = 특권). CAN 명령 파서를 user 쪽에 두면, 파서가 만든 목표값은 큐로 특권 쪽에 넘어간다 — §7의 교훈대로 명령 하나마다가 아니라 CAN 프레임 묶음 단위로 넘긴다. 목표값에는 범위 검사를 특권 쪽에서 다시 한다. 격리는 메모리를 지키지 "토크 1000 Nm" 같은 틀린 값까지 막지는 않는다.

10.3 센서 허브 — 바이너리 라이브러리에 파티션 하나#

벤더가 .a로 준 퓨전 라이브러리의 전역 변수는 소스를 못 고친다. Zephyr에서는 링커 단계에서 그 라이브러리의 .data/.bss를 파티션에 넣을 수 있다 — 생성된 app_smem_aligned.ld에 "*libc.a:*"(.data .data.* ...)가 들어간 것처럼(§2.4), CMake 함수 zephyr_library_app_memory(<partition>)(cmake/modules/extensions.cmake 626행)가 Zephyr 라이브러리 단위로 그 라이브러리의 전역을 파티션에 넣어 준다(이 노트에서 직접 돌려 보지는 않았다). FreeRTOS에서는 링커 스크립트에서 그 .a의 섹션을 별도 정렬 블록에 모으고 그 블록을 xRegions로 준다.

10.4 Don의 SSD 펌웨어와 연결#

SSD 컨트롤러의 호스트 명령 처리에서 "명령의 PRP 주소가 이 네임스페이스의 버퍼 범위 안인가"를 FTL이 검사한 것이 정확히 K_SYSCALL_MEMORY_WRITE다. 그리고 "검사한 길이를 다시 읽지 말고 지역 변수에 복사해서 쓴다"는 TOCTOU 규칙은, DMA가 쓰는 중인 명령 버퍼를 펌웨어가 두 번 읽어 다른 값을 본 버그와 같은 뿌리다. 다른 점은 RTOS에서는 공격자가 같은 칩 안의 다른 스레드일 수 있다는 것이다.

Q. "How would you keep a buggy telemetry parser from taking down the flight controller?"

A. 파서를 비특권(user) 태스크로 만들고 자기 스택과 RX 버퍼 파티션만 주고, 제어 루프와는 큐 하나로만 연결한다. 폴트 정책은 "그 태스크만 정리 후 재시작"으로 하고, 반복되면 기능을 끈다. 제어 루프 · 상태 추정 · 모터 출력은 특권에 둔다. QEMU에서 손상 패킷을 넣어 파서가 두 번 죽고 재시작되는 동안 2 ms 제어 주기의 min/max가 폴트 없을 때와 똑같은 것을 확인했다.

I'd run the parser as an unprivileged task — a Zephyr user thread or a FreeRTOS-MPU restricted task — that can touch only its own stack and its RX buffer partition, and connect it to the control side through a single message queue. The control loop, state estimation and motor output stay privileged. Then I'd make the fault policy explicit: on an MPU fault in that task, kill just that task and have a supervisor recreate it, with a restart counter that disables the feature if it keeps dying. I built exactly this on QEMU: corrupted length fields made the parser fault twice, it was recreated in about 60 to 120 microseconds, and the 2 ms control loop's min and max period were identical to the fault-free run.

꼬리 질문: "What does the MPU NOT protect you from?" → 리전 안쪽의 손상(예제 7에서 카운터가 덮어써졌다), 틀린 값(범위 검사는 따로), 시간 간섭(우선순위 · 예산).

Q. "Explain Zephyr memory domains and partitions."

A. 파티션은 시작 · 크기 · 속성을 가진 연속 메모리 하나, 도메인은 파티션 묶음이다. 스레드는 한 도메인에 속하고, user 스레드는 자기 스택과 도메인의 파티션만 접근한다. 전역 변수는 K_APP_BMEM/K_APP_DMEM으로 파티션에 넣고 링커가 정렬해 배치한다. 같은 파티션을 두 도메인에 넣으면 공유 메모리다. 컨텍스트 스위치 때 커널이 다음 스레드의 도메인을 MPU에 올리고, 도메인당 파티션 수는 MPU 리전 수가 정한다 — M3 QEMU 보드에서 5개였다.

A partition is one contiguous range with access attributes; a domain is a set of partitions. Every thread belongs to one domain, and a user thread can access only its own stack plus its domain's partitions. You place globals into a partition with K_APP_BMEM or K_APP_DMEM, and the build does a two-pass link to generate the aligned layout. Putting the same partition in two domains gives you shared memory. On every context switch the kernel reprograms the MPU with the incoming thread's partitions, so the number of partitions per domain is bounded by free MPU regions — five on the Cortex-M3 board I used.

Q. "How do you add a system call in Zephyr, and what must the verification function do?"

A. 헤더에 __syscall로 선언하고, z_impl_(진짜 일)과 z_vrfy_(검사)를 쓰고, 생성된 _mrsh.c를 include한다. 검사 함수는 모든 포인터를 K_SYSCALL_MEMORY_READ/WRITE로, 커널 객체는 K_SYSCALL_OBJ로 확인하고, 실패하면 K_OOPS로 그 스레드를 끝낸다. 틀린 값은 에러 코드로 돌려준다. 검사에 쓴 user 데이터는 복사본으로 써서 TOCTOU를 막는다.

Declare it with __syscall in a header, write z_impl_ for the real work and z_vrfy_ for validation, and include the generated marshalling file. The verifier must check every pointer with K_SYSCALL_MEMORY_READ or WRITE and every kernel object with K_SYSCALL_OBJ, and on failure K_OOPS kills the calling thread. Bad values, like an out-of-range index, should just return an error code. And anything the check depends on — a length, say — should be copied into kernel memory with k_usermode_from_copy first, otherwise another thread can change it between the check and the use. In my test, passing a kernel address as the output pointer produced "write access denied" and an oops, while the supervisor could call the same function directly.

Q. "In FreeRTOS-MPU, how do you recover from a MemManage fault in one task?"

A. 포트가 핸들러를 주지 않으니 직접 쓴다. 핸들러는 CFSR · MMFAR · 쌓인 PC를 기록하고 MMFSR을 지우고, 쌓인 프레임의 PC를 park 함수로 바꿔 무한 폴트를 막고, vTaskNotifyGiveFromISR로 특권 감독 태스크를 깨운다 — v2에서 FromISR 계열은 SVC가 아닌 특권 함수라 핸들러에서 불러도 된다. 감독은 vTaskDelete 후 같은 스택 버퍼로 xTaskCreateRestricted, ACL을 다시 준다.

The port doesn't provide a handler, so you write one. It records CFSR, MMFAR and the stacked PC, clears the MMFSR bits, rewrites the stacked PC to a parking function so the exception return doesn't re-execute the faulting instruction, and notifies a privileged supervisor task with vTaskNotifyGiveFromISR — in the v2 wrappers the FromISR APIs are plain privileged functions, not SVC calls, so that's legal from handler mode. The supervisor deletes the task, recreates it with xTaskCreateRestricted on the same stack buffer and re-grants its queue access. On QEMU that took about 57 microseconds and the control task's period didn't move.

꼬리 질문: "What about a fault in a privileged task?" → 커널 상태를 믿을 수 없으니 안전 동작 후 리셋.

Q. "What does isolation cost, and how do you reduce it?"

A. 내 측정(QEMU)에서 항목마다 메시지를 주고받는 producer/consumer가 Zephyr user 쪽에서 격리 없는 빌드보다 93%, FreeRTOS restricted에서 59% 느렸다. 원인은 항목마다 시스템 콜 2번과 컨텍스트 스위치마다 MPU 재설정이다. 16개씩 묶어 보내자 추가 비용이 15분의 1로 줄었고, 계산이 많은 작업에서는 7–13%였다. 그리고 v7-M은 RAM을 2의 거듭제곱으로 먹어서 같은 요청이 53% 더 컸다(v8-M은 1%).

On QEMU, a producer-consumer that passes one item per message was 93 percent slower in Zephyr user mode and 59 percent slower with FreeRTOS restricted tasks than with no isolation at all. That's two system calls per item plus MPU reprogramming on every context switch — even the privileged side of an isolated build was 15 to 34 percent slower. Batching sixteen items per message cut the extra cost per item by about fifteen times, and with real computation per item the overhead fell to 7 to 13 percent. Memory is the other cost: on ARMv7-M the same partitions and stacks took 53 percent more RAM because of power-of-two regions, versus about 1 percent on ARMv8-M.

Q. "What's a subtle pitfall with ARMv7-M MPU regions?"

A. 리전이 2의 거듭제곱으로 반올림된다는 것. FreeRTOS에서 600워드(2400 B) 스택을 주면 리전이 4 KB가 되고, 링커가 그 꼬리에 다른 태스크의 변수를 넣으면 그 태스크가 폴트 없이 읽고 쓴다. 스택 리전 번호가 커서 다른 리전의 RO 설정까지 이긴다. 실제로 재현했다. 크기를 2의 거듭제곱으로 맞추고 map 파일을 CI에서 검사한다.

Regions round up to a power of two. When I gave a FreeRTOS-MPU task a 600-word stack, its region became 4 KB, and the linker placed another task's private buffer and a read-only shared buffer in that tail. The task could read the private buffer and write the read-only one with no fault, because the stack region has the highest number and wins on overlap. Interestingly the v2 system-call buffer check still rejected that address, since it uses the exact size stored in the TCB, not the hardware region. The fix is power-of-two sizes and alignment, and a CI check over the map file.

Q. "How does this relate to ARINC 653 or ISO 26262?"

A. ARINC 653 파티션은 공간 분할과 시간 분할 둘 다다. MPU 도메인은 공간 쪽이고, 시간 쪽은 시간 창 스케줄링(직접 만들어 본 C11)이나 예산 · 우선순위로 한다. ISO 26262의 freedom from interference는 메모리 · 시간 · 통신 간섭이 없음을 보이라는 것인데, MPU 격리는 메모리 쪽 근거이고 그 설정이 맞다는 검증까지 있어야 근거가 된다.

ARINC 653 partitioning has two halves: spatial and temporal. MPU domains give you the spatial half on an MCU; the temporal half needs fixed time windows or at least budgets and priorities — I've built a two-level window scheduler on FreeRTOS for that. For ISO 26262 freedom from interference you have to argue memory, timing and communication separately. The MPU is the memory argument, but only if you can show every region opens exactly what you intended — my power-of-two finding is exactly the kind of thing that breaks that argument.

13. 직접 해보기#

  1. 개념: user 스레드가 printk는 되는데 snprintf는 MPU 폴트가 날 수 있다. 왜인가? 어떻게 고치나? 정답/힌트: printk는 시스템 콜(k_str_out)이라 커널이 대신 찍는다. snprintf는 libc 전역(z_libc_partition)을 user 문맥에서 직접 만진다 → 그 파티션을 도메인에 추가(§2.4).
  2. 코드: 예제 1에 도메인 C를 추가해 part_sh를 RO로 보게 하라. K_APPMEM_PARTITION_DEFINE은 RW가 기본이므로 같은 주소 범위를 K_MEM_PARTITION_DEFINE(..., K_MEM_PARTITION_P_RW_U_RO)로 다시 정의해야 한다. 시작 · 크기는 z_data_smem_part_sh_part_start/_size 심볼로 얻는다. 정답/힌트: 같은 도메인 안에서만 겹침이 금지이므로 다른 도메인에서 RO로 보는 것은 된다. C 스레드가 쓰면 MPU FAULT.
  3. 코드: 예제 3에 __syscall int f5_log_write(const char *s, size_t maxlen)을 추가하고 k_usermode_string_copy()로 커널 버퍼에 복사한 뒤 출력하라. user가 커널 주소 문자열을 넘기면? 정답/힌트: 복사 함수가 접근 검사를 하므로 실패를 반환한다. 반환값을 보고 K_OOPS 할지 에러 코드를 돌려줄지 정책을 정하라.
  4. 측정: 예제 5를 배치 4, 8, 32로 늘려 "항목당 추가 비용 vs 배치 크기" 곡선을 그려라. 어디서 꺾이나? 정답/힌트: 추가 비용 ≈ (시스템 콜 2번 + 스위치 비용) / 배치 + 복사 비용 × 1. 배치가 커지면 메시지 복사(k_msgq 메모리 복사) 쪽이 남는다.
  5. 측정: 예제 4에서 CONFIG_FAULT_DUMP=0과 CONFIG_LOG=n(+ CONFIG_LOG_MODE_MINIMAL 제거)으로 바꾸고 "fault → restart" 시간을 다시 재라. 그리고 폴트 시각을 비행 제어 깨어남 직전으로 맞춰(패킷 전송 시각 조정) 최악의 주기 지연을 재라. 정답/힌트: fatal 경로는 irq lock 상태로 로그를 찍는다. 로그가 짧을수록 최악 지연이 줄어든다.
  6. 코드: 예제 8의 F5_FIX=0 구멍을 빌드 단계에서 잡는 스크립트를 써라: arm-none-eabi-nm -S로 restricted 태스크 스택 심볼의 크기가 2의 거듭제곱인지, 주소가 크기에 정렬됐는지 검사. 정답/힌트: size & (size - 1) == 0 그리고 addr % size == 0. 리전 꼬리 [addr+size, roundup)에 다른 심볼이 있으면 실패.
  7. 설계: 로봇 관절 컨트롤러에서 "파라미터 서비스(CAN으로 게인 변경)"를 user로 보냈다. 파라미터가 특권 쪽 제어 루프로 넘어가는 경로를 설계하라 — 공유 메모리, 큐, 시스템 콜 중 무엇을 쓰고, 어떤 검사를 어디서 하나? 정답/힌트: 큐(또는 앱 syscall) + 특권 쪽 범위 검사 + 제어 주기 경계에서 원자적 교체(더블 버퍼). user가 쓴 값을 특권이 검사 없이 쓰면 격리의 의미가 없다.

15. 요약 & 체크리스트#

유저 모드 격리는 MCU 한 칩 안에서 신뢰 수준이 다른 코드를 칸막이로 나누는 일이다. Zephyr는 메모리를 파티션 · 도메인으로, 커널 객체를 스레드 권한 비트맵으로 나누고, 모든 시스템 콜 인자를 z_vrfy_에서 검사해 실패하면 그 스레드를 oops로 끝낸다. 앱도 __syscall로 자기 문을 낼 수 있고, 검사 규칙(포인터는 oops, 값은 에러 코드, TOCTOU는 복사본)이 곧 보안이다. FreeRTOS-MPU v2는 restricted 태스크마다 리전 3개 + 스택, 객체마다 ACL을 주고, 위반은 MemManage나 조용한 pdFAIL로 나타난다. 두 RTOS 모두 폴트 뒤의 정책은 앱 몫이다 — Zephyr는 fatal 핸들러 재정의, FreeRTOS는 MemManage 핸들러 + 감독 태스크로 "그 태스크만 정리하고 다시 만든다"를 직접 만들었고, 비행 제어 주기는 흔들리지 않았다. 격리의 대가는 이 노트 측정으로 항목당 시스템 콜 2번(배치 1에서 59–93% 느림, 배치 16 + 계산 많은 작업에서 7–13%), 격리 빌드 특권 쪽도 15–34%, v7-M RAM +53%였다. 그리고 격리는 설정이 맞을 때만 격리다: MPU는 리전 안쪽 손상을 못 막고, 2의 거듭제곱이 아닌 스택은 남의 변수를 열어 버린다.
