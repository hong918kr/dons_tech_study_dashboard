0. 큰 그림 — 메모리를 "언제" 나눠 주나#

0.1 직관#

메모리 할당은 결국 "이 RAM 조각은 누구 것인가"를 언제 정하느냐의 문제다.

  • 정적 할당: 컴파일·링크할 때 정한다. static uint8_t buf[512];가 그렇다. 링커가 주소를 고르고, .bss나 .data에 자리를 박아 둔다. 실행 중에는 아무 결정도 하지 않는다.
  • 동적 할당: 실행 중에 정한다. malloc(512)가 그렇다. 할당기(allocator)가 빈 조각 목록을 뒤져서 하나를 골라 준다. 언제, 얼마나, 몇 번 부를지는 코드가 돌아 봐야 안다.

Don이 SSD 펌웨어에서 쓰던 방식이 첫 번째다. 명령 슬롯, NAND 페이지 버퍼, 매핑 테이블 캐시를 모두 부팅 때(또는 링크 때) 고정 개수로 잡아 두고, 실행 중에는 "빈 슬롯 목록"에서 꺼내고 돌려줄 뿐이다. 그 목록도 크기가 하나뿐인 고정 블록 풀이다(F2). 이 노트의 결론도 결국 그쪽으로 간다. 다만 RTOS는 기본으로 동적 할당기를 들고 오고(FreeRTOS xTaskCreate는 내부에서 pvPortMalloc을 두 번 부른다, A4), 서드파티 스택(TCP/IP, USB, 파일 시스템)은 malloc을 부른다. 그래서 "안 쓴다"가 아니라 "어디까지 허용하고 어떻게 증명하나"가 실무 질문이 된다.

그림 1 — 같은 앱(태스크 3개, 큐 2개, 뮤텍스, 타이머, 이벤트 그룹)을 동적(heap_4, configTOTAL_HEAP_SIZE 16 KB)과 정적 전용으로 빌드한 .bss(예제 7, arm-none-eabi-size -A와 nm -S 실측). 회색은 idle·timer 태스크 스택과 TCB, 타이머 큐, newlib __sf 등 앱이 고를 수 없는 부분이다(두 빌드 차이 24 B는 heap_4의 관리 변수). 동적 빌드는 heap을 통째로 예약해 두고 그중 5,664 B만 썼다. 정적 빌드는 쓴 만큼만 있고, 각 객체가 이름 있는 심볼이라 map 파일에서 바로 보인다.

0.2 RTOS에서 동적 할당이 문제가 되는 네 가지 이유#

위험무슨 일이 일어나나왜 RTOS·MCU에서 더 나쁜가이 노트에서
시간이 일정하지 않다malloc·free가 빈 블록 목록을 걷는다 → 목록 길이에 비례마감(deadline)이 있는 태스크의 WCET에 들어간다. 그리고 할당 중에는 스케줄러가 멈춘다(vTaskSuspendAll)§3 (예제 3, 4)
단편화빈 공간 합은 충분한데 연속된 조각이 없어서 실패MMU가 없어 페이지를 다시 맞춰 붙일 수 없고, compaction도 없다§4 (예제 2, 5, 6)
실행 중 실패언젠가 NULL이 돌아온다드론 비행 중에 "메모리 부족"은 복구 경로가 없다. 사람이 재부팅해 줄 수 없다§4, §5
메모리 오염이 넓게 번진다overflow·double free가 이웃 블록 헤더를 망가뜨린다보호 장치(MPU) 없이 모든 태스크가 같은 heap을 공유한다§6 (예제 8)

이 넷 중 "시간"과 "단편화"는 할당기 알고리즘의 성질이고, "실행 중 실패"와 "오염"은 heap이라는 공유 자원의 성질이다. 그래서 대책도 두 갈래다. 알고리즘을 바꾸거나(heap_4, 고정 크기 풀), 공유 heap을 실행 중에 아예 안 쓰거나(정적 할당, 초기화 후 잠금).

0.3 Linux 커널 할당기와 무엇이 다른가 (EL F9 재사용)#

buddy 할당자, SLUB, GFP 플래그, 워터마크, compaction은 EL F9에서 다뤘다. MCU RTOS에서 달라지는 점만 정리한다.

실습 환경 한 줄#

QEMU mps2-an385(Cortex-M3 25 MHz) + FreeRTOS V11.3.2(ARM_CM3 포트) / Zephyr v4.4.2(같은 보드). 타이밍은 모두 ICOUNT=1(명령 1개 = 32 ns)로 돌리고 MPS2 FPGAIO COUNTER(0x40028018, 25 MHz → 1 tick = 40 ns)로 쟀다. QEMU icount 기준 값이며, 실제 칩과 절대값은 다르다(캐시·플래시 wait state·버스를 모델링하지 않는다). 다만 이 노트가 보는 것은 "목록 길이에 따른 기울기"와 "분포의 꼬리"라서 모양은 실칩과 같다. 모든 예제는 -Wall -Wextra 경고 0개다(§3.3의 configASSERT를 끈 빌드만 커널 소스에서 경고 3줄이 나오고, 그대로 보여 준다).

랩 템플릿 Makefile은 heap 파일을 하나 골라 링크한다(HEAP=heap_4). 이 노트는 두 가지를 더 해야 해서 템플릿 Makefile을 내 폴더로 복사해 고쳤다. (1) HEAP=none이면 heap 파일을 링크하지 않는다(정적 전용 빌드, 또는 예제가 heap 소스를 직접 #include). (2) LDS=로 링커 스크립트를 바꾼다(RAM 64 KB 실험).

앱 폴더의 FreeRTOSConfig.h는 템플릿 것을 그대로 포함하고, 예제별 스위치만 더한다.

heap 내부(빈 블록 목록)를 직접 걷기 위해, 예제 대부분은 heap_N.c를 예제 파일 안에 #include한다. heap 파일의 변수(xStart, pxEnd)가 static이라 다른 파일에서는 안 보이기 때문이다. 할당기 코드는 한 줄도 바꾸지 않는다.

1. 규칙이 말하는 것 — "금지"가 아니라 "초기화 뒤 금지"#

1.1 코딩 표준과 인증 프로젝트의 정책#

안전 규격과 코딩 표준은 대부분 동적 할당을 막는다. 그런데 문장을 잘 보면 "언제"를 붙인 것이 많다.

출처내용시점
MISRA C:2012 / C:2023 Directive 4.12Dynamic memory allocation shall not be used전체 금지 (deviation으로 허용 가능)
MISRA C:2012 / C:2023 Rule 21.3<stdlib.h>의 메모리 할당·해제 함수(malloc, calloc, realloc, free)를 쓰지 않는다전체 금지 (libc 함수 수준)
JSF AV C++ Rule 206자유 저장소(heap)에서의 할당·해제는 초기화가 끝난 뒤에 일어나면 안 된다초기화 뒤 금지
NASA/JPL "Power of 10" Rule 3초기화가 끝난 뒤 동적 메모리 할당을 쓰지 않는다초기화 뒤 금지
ISO 26262-6 소프트웨어 유닛 설계 원칙동적 객체·변수를 쓰지 않거나, 쓴다면 생성 시 온라인 검사ASIL에 따라 권장 수준이 다르다

MISRA의 두 항목은 겹친다. Dir 4.12는 정책, Rule 21.3은 "libc의 그 함수들"이라는 구체적인 금지다. FreeRTOS 커널 자체도 MISRA 검사를 받는데, pvPortMalloc의 반환값을 TCB 포인터로 바꾸는 줄마다 MISRA Ref 11.5.1 [Malloc memory assignment] deviation 주석이 붙어 있다(V11.3.2 tasks.c). 커널이 "동적 할당 경로가 있다"는 것을 문서로 인정하고, 인증 프로젝트에는 정적 할당 API를 쓰라고 권하는 구조다.

실무 인증 프로젝트(드론 비행 제어 DO-178C, 차량 ECU ISO 26262)에서 흔한 정책은 셋 중 하나다.

  1. 정적 전용: 모든 객체를 링크 시점에 고정한다. FreeRTOS configSUPPORT_DYNAMIC_ALLOCATION 0. 링커가 메모리 예산을 검사한다(§5).
  2. 초기화 시점 할당 + 잠금: 부팅 중에는 xTaskCreate 같은 편한 API를 쓰고, 초기화가 끝나면 heap을 잠근다. 잠근 뒤 할당 시도는 assert. JSF·Power of 10이 허용하는 꼴이다. heap_1이 이 정책의 할당기다(free가 없다).
  3. 동적 할당 허용 + 증명: 서드파티 스택 때문에 실행 중 할당이 불가피하면, 할당기를 정하고(heap_4 또는 고정 블록 풀), 최악 시간과 "실패하지 않음"을 시험·분석으로 보인다(§3, §4). 문서상 deviation이 필요하다.

Don의 SSD 펌웨어는 1번과 2번 사이였을 것이다. 부팅 때 DRAM·SRAM 크기를 보고 풀 개수를 정하고(2번), 그 뒤로는 풀에서 꺼내고 돌려줄 뿐이다.

1.2 예제 1 — 누가 pvPortMalloc을 부르나, 그리고 초기화 후 잠금#

무엇을 확인하는 코드인가: 흔한 앱 초기화에서 커널이 pvPortMalloc을 몇 번, 얼마씩 부르는지 기록하고, 초기화가 끝나면 heap을 잠근다. 그다음 "무해해 보이는" API 하나가 실행 중에 heap을 쓰는 것을 잡는다. 링커의 --wrap=pvPortMalloc을 쓰면 다른 오브젝트 파일에서 pvPortMalloc을 부르는 곳이 모두 __wrap_pvPortMalloc으로 가고, 원래 함수는 __real_pvPortMalloc이 된다. 커널 소스를 고치지 않고 호출자 주소(__builtin_return_address(0))를 얻을 수 있다.

호출자 주소를 함수 이름으로 바꿨다. 반환 주소는 Thumb 비트(1)가 붙어 있어서 1을 빼고 addr2line -i(인라인 펼침)로 본다.

출력에서 볼 것:

  • 태스크 하나 = 할당 두 번. 스택 먼저(tasks.c:1683, 256 words = 1024 B), TCB 나중(:1689, 96 B). 순서의 이유(스택 overflow가 자기 TCB를 덮지 않게)는 A4 §2.5에서 다뤘다. 큐는 Queue_t 84 B + 저장 공간을 한 번에 잡는다: 16 × 4 + 84 = 148, 4 × 64 + 84 = 340. 뮤텍스는 저장 공간이 0인 큐라서 84 B다. 스트림 버퍼는 512 + 1 + 40 = 553 B(용량보다 1바이트 더 잡는 것은 가득 참과 빔을 구별하기 위해서다).
  • 요청 12번의 합은 6,097 B인데 heap에서 줄어든 것은 6,232 B다. 블록마다 8 B 헤더(BlockLink_t)가 붙고 8 B 정렬로 올림하기 때문이다(블록 크기 합 6,216 B). 나머지 16 B는 처음 초기화 때 heap 시작 정렬과 끝 표지 pxEnd가 가져갔다. 작은 객체가 많을수록 헤더 비율이 커진다: 이벤트 그룹 32 B는 40 B 블록이 된다(헤더가 20%).
  • free 0 -> 124840: heap_4의 xPortGetFreeHeapSize()는 첫 할당 전에는 0을 돌려준다. prvHeapInit()이 첫 pvPortMalloc 안에서 늦게 돌기 때문이다. 부팅 직후 "heap이 0"이라고 찍히는 로그는 고장이 아니다.
  • vTaskStartScheduler()는 할당을 하나도 하지 않았다(목록이 12에서 끝난다). 템플릿이 configSUPPORT_STATIC_ALLOCATION 1 + configKERNEL_PROVIDED_STATIC_MEMORY 1이라 idle·timer 태스크와 타이머 명령 큐(timers.c의 xStaticTimerQueue)를 커널이 정적 배열로 만들기 때문이다. 정적 할당을 끄면 이 셋도 heap에서 나온다.
  • 잠근 뒤 걸린 것은 vTaskListTasks()다. 태스크 목록을 문자열로 만드는 이 디버그 API는 안에서 TaskStatus_t 배열(태스크 5개분, 180 B)을 pvPortMalloc으로 잡았다가 푼다(tasks.c:7451, vTaskGetRunTimeStatistics도 같다). 텔레메트리 태스크가 1초마다 이걸 부르면 그것만으로 실행 중 할당이 된다. 대신 uxTaskGetSystemState()에 정적 배열을 넘기면 할당 없이 같은 정보를 얻는다.

2. FreeRTOS heap_1 ~ heap_5 — 다섯 할당기의 내부#

2.1 한눈에#

2.2 공통 자료구조 — BlockLink_t#

heap_2/4/5는 같은 헤더를 쓴다(V11.3.2 heap_4.c).

블록 하나의 모양은 이렇다(주소는 아래에서 위로).

  • xBlockSize의 최상위 비트가 "할당됨" 표시다(heapBLOCK_ALLOCATED_BITMASK). 그래서 한 블록의 최대 크기는 2 GB이고, vPortFree는 이 비트가 서 있는지 assert로 확인한다. 이미 푼 블록을 또 풀면 비트가 0이라 걸린다(예제 8).
  • 할당된 블록의 pxNextFreeBlock은 NULL이다. 이것도 vPortFree가 확인한다. 앞 블록의 버퍼가 넘쳐서 이 칸을 덮으면 대개 걸린다(예제 8에서 "대개"가 아닌 경우를 본다).
  • 헤더 크기 xHeapStructSize는 sizeof(BlockLink_t)를 portBYTE_ALIGNMENT(Cortex-M = 8)로 올림한 값이라 8 B다. 남은 조각이 heapMINIMUM_BLOCK_SIZE(헤더의 2배 = 16 B)보다 크지 않으면 쪼개지 않고 통째로 준다.
  • 목록의 양 끝: xStart(정적 변수, 크기 0인 머리)와 끝 표지. heap_2는 끝 표지도 정적 변수 xEnd이고 그 크기를 heap 전체 크기로 둔다(크기 순 목록이라 "가장 큰 값"이 끝을 뜻한다). heap_4/5는 끝 표지 pxEnd를 heap 영역의 맨 끝 8 B 안에 놓는다. 그래서 heap_4는 heap에서 8 B를 덜 쓸 수 있다.

2.3 heap_1 — 앞으로만 가는 포인터#

pvPortMalloc은 크기를 8로 올림하고 xNextFreeByte를 그만큼 더할 뿐이다. 목록도 헤더도 없다. 할당 시간이 입력과 상관없이 일정하고(예제 3), 단편화가 생길 수 없다. 대신 vPortFree(pv)는 configASSERT(pv == NULL)이다. 태스크·큐를 지우지 않는 앱, 즉 "초기화 때 다 만들고 끝"인 앱에 맞는다. 정책 2번(초기화 시점 할당)을 할당기 수준에서 강제하는 셈이다. vTaskDelete를 쓰는 앱에 heap_1을 넣으면 idle 태스크가 TCB를 회수하다가(A4, C9) assert에 걸린다.

2.4 heap_2 — 크기 순 목록, 병합 없음#

빈 블록 목록이 크기 순이다. prvInsertBlockIntoFreeList는 매크로로 되어 있고, 자기보다 큰 블록을 만날 때까지 목록을 걷는다. pvPortMalloc은 작은 것부터 걸으므로 처음 맞는 블록이 곧 가장 작게 맞는 블록이다(best fit). 그리고 이웃 블록을 합치지 않는다. 소스 머리 주석이 직접 말한다: "does not combine adjacent free blocks into a single larger block (and so will fragment memory)".

그래서 heap_2에서 블록은 쪼개지기만 하고 다시 커지지 않는다. 512 B 블록을 풀면 그 자리는 영원히 512 B 이하 요청에만 쓰인다. 같은 크기로 만들고 지우기를 반복하는 앱(같은 스택 크기의 태스크를 계속 만들고 지우는 앱)에서는 그 블록이 그대로 재사용되니 괜찮다. 크기가 섞이면 무너진다(§4).

2.5 heap_4 — 주소 순 목록, 이웃 병합#

목록이 주소 순이다. vPortFree의 prvInsertBlockIntoFreeList가 자기 자리를 찾을 때까지 걷고, 자리에서 두 가지를 확인한다.

  1. 바로 앞 빈 블록의 끝(pxIterator + xBlockSize)이 내 시작이면 → 앞 블록에 붙는다.
  2. 내 끝이 바로 다음 빈 블록의 시작이면 → 다음 블록을 흡수한다(다음이 pxEnd면 제외).

둘 다 맞으면(구멍 하나를 메운 경우) 세 블록이 하나가 된다. 이 병합 덕분에 이웃끼리 같이 풀린 공간이 다시 큰 블록으로 돌아온다. pvPortMalloc은 낮은 주소부터 처음 맞는 블록을 고른다(first fit). 잘라 낸 나머지는 원래 블록 자리에 그대로 남으니 목록 순서가 저절로 유지된다(삽입 탐색이 필요 없다 — heap_2보다 malloc 쪽이 단순하다).

2.6 예제 2 — 같은 순서로 풀어도 목록 모양이 다르다#

무엇을 확인하는 코드인가: 1 KB heap에 A~E를 할당하고 B, D, C 순으로 푼 뒤, heap_2와 heap_4의 빈 블록 목록을 걸어서 찍는다. 마지막에 500 B를 요청한다. 오프셋은 ucHeap 시작 기준이다.

그림 2 — 예제 2의 마지막 상태를 오프셋 그대로 그렸다. 초록 = 빈 블록(숫자는 바이트), 주황 = heap_4가 병합한 블록, 회색 = 사용 중. 같은 할당·해제 순서에서 heap_2는 빈 블록 4개, heap_4는 2개다.

출력에서 볼 것:

  • A+12: 첫 블록 헤더는 +4에 있다(ucHeap이 4 B 정렬이라 8 B 정렬로 4 B를 버렸다), 사용자 포인터는 그 뒤 8 B인 +12. 100 B 요청이 112 B 블록이 됐다(100 + 8 = 108 → 8의 배수 112).
  • heap_2의 목록은 크기 순이다: 64 → 112 → 208 → 312. 주소는 뒤죽박죽이다. heap_4의 목록은 주소 순이다: +116 → +956.
  • C를 풀 때 heap_4는 B(+116, 208) 뒤에 C(+324)가 바로 붙고 C 뒤에 D(+436)가 바로 붙는 것을 보고 셋을 하나(632 B)로 합쳤다. heap_2는 112 B짜리 블록을 하나 더 늘렸을 뿐이다.
  • 빈 공간 합은 heap_2 696 B, heap_4 688 B로 거의 같다(heap_4는 pxEnd가 끝 8 B를 쓴다). 그런데 500 B 요청은 heap_2에서 실패했다. 이것이 단편화(fragmentation)의 정의 그대로다: 빈 공간의 합은 충분한데, 연속된 한 조각이 없다.

2.7 heap_3 — libc malloc 감싸기#

heap_3은 106줄짜리 파일이다. pvPortMalloc은 vTaskSuspendAll(); malloc(n); xTaskResumeAll();이 전부다. 할당기는 libc의 것이고(랩은 newlib-nano: 주소 순 빈 목록 + 병합), heap 크기는 configTOTAL_HEAP_SIZE가 아니라 링커 스크립트의 heap 영역(_sbrk가 늘리는 __heap_start~__heap_end, B5·B11)이 정한다. 그래서 xPortGetFreeHeapSize()도 없다.

쓸 이유는 하나다. 서드파티 코드가 malloc을 직접 부르는데, 그것과 RTOS 객체가 같은 heap을 나눠 쓰게 하고 싶을 때. 이때 스케줄러 잠금은 pvPortMalloc을 거치는 호출만 보호한다. 서드파티가 malloc을 직접 부르면 보호가 없다 → newlib의 __malloc_lock/__malloc_unlock을 구현해야 한다(F7). 그리고 libc 할당기의 최악 시간은 FreeRTOS가 아니라 libc 구현에 달렸다.

2.8 heap_5 — 떨어진 RAM 여러 개를 한 목록으로#

heap_5는 heap_4와 같은 알고리즘인데, heap 메모리를 ucHeap 배열 하나가 아니라 여러 영역에서 받는다.

vPortDefineHeapRegions()(V11.3.2 heap_5.c)는 영역마다 첫 빈 블록과 끝 표지(크기 0인 블록)를 만들고, 앞 영역의 끝 표지가 다음 영역의 첫 블록을 가리키게 이어서 주소 순 목록 하나로 만든다. 영역은 주소 오름차순이어야 하고(assert로 확인), 두 번 부르면 assert다. heap_4와 다른 점이 몇 가지 있다.

  • heap이 자동으로 초기화되지 않는다. pvPortMalloc이 configASSERT( pxEnd )로 먼저 확인한다. 정적 생성자나 초기화 순서 때문에 vPortDefineHeapRegions 전에 객체를 하나라도 만들면 그 자리에서 assert다.
  • 영역 사이에는 크기 0인 끝 표지가 끼어 있어서 두 영역이 주소상 붙어 있어도 병합되지 않는다. vPortGetHeapStats는 최소 블록 크기를 셀 때 크기 0 블록을 건너뛴다.
  • 블록 포인터 범위 검사(heapVALIDATE_BLOCK_POINTER)가 configENABLE_HEAP_PROTECTOR가 1일 때만 켜진다. heap_4는 이 검사가 protector와 상관없이 configASSERT만 정의되어 있으면 항상 돈다. 영역이 여럿이라 "heap 범위"가 하나의 배열이 아니기 때문이다(protector가 켜지면 가장 낮은·높은 주소를 기록해서 검사한다. configVALIDATE_HEAP_BLOCK_POINTER로 직접 정의할 수도 있다 — V11.2.0에서 추가). 이 차이가 예제 3에서 heap_5가 heap_4보다 빠르게 나오는 이유다.
  • V11.3.1에서 고친 버그: protector를 켠 heap_5에서 할당이 실패하면(목록 끝 표지까지 간 경우) 끝 표지에 범위 검사를 해서 NULL 대신 assert가 났다. V11.3.2 소스에는 if( pxBlock != pxEnd ) 가드가 들어가 있다(History.txt V11.3.1 항목). 그 전 버전으로 heap_5 + protector를 쓰는 프로젝트는 "메모리 부족이 HardFault/assert로 보이는" 증상을 겪는다.

어느 영역에 무엇을 둘지(빠른 SRAM에는 스택, 느린 SDRAM에는 큰 버퍼)는 heap_5가 고르지 못한다. 주소 순 first fit이라 낮은 주소 영역부터 채운다. 스택만 다른 영역에서 받고 싶으면 configSTACK_ALLOCATION_FROM_SEPARATE_HEAP 1로 pvPortMallocStack/vPortFreeStack을 직접 구현한다(portable.h). 메모리 뱅크 배치 실무는 F8에서 다룬다.

3. 할당 시간의 결정성 — "얼마나 걸리나"를 식으로#

3.1 직관 — 목록을 걷는 할당기는 목록 길이만큼 느리다#

heap_2/4/5의 pvPortMalloc은 빈 블록 목록을 처음부터 걸으면서 맞는 블록을 찾는다. vPortFree도 자기 자리를 찾을 때까지 목록을 걷는다. 그러니 시간은 (고정 비용) + (블록 하나당 비용) × (지나간 빈 블록 수)다. 이 "지나간 수"는 요청 크기와 지금까지의 할당·해제 역사에 따라 달라진다. 결정적(deterministic)이란 "항상 같은 시간"이라는 뜻이 아니라 "상한을 미리 말할 수 있다"는 뜻이다. 그러려면 두 가지가 필요하다. 블록 하나당 비용(측정 또는 명령 수 계산)과, 목록 길이의 상한(분석).

heap_1은 목록이 없으니 상수다. 고정 블록 풀(F2)도 "빈 칸 목록의 머리에서 하나 꺼내기"라 상수다. TLSF처럼 크기 등급별 비트맵으로 O(1)을 만드는 범용 할당기도 있다(Zephyr sys_heap도 크기 등급 bucket을 쓴다 — 내부는 F2).

3.2 예제 3 — 같은 무작위 부하에서 heap_1~heap_5의 시간 분포#

무엇을 확인하는 코드인가: 슬롯 64개에 대해 3000번 "슬롯이 비었으면 16~1039 B 할당, 차 있으면 해제"를 같은 난수 순서로 돌린다. 매 호출을 인터럽트를 끈 채(tick 인터럽트가 끼어드는 것을 빼려고) FPGAIO 카운터로 잰다. heap_1은 free가 없으니 작은 크기(16~79 B)로 할당만 한다. heap_5는 32 KB 두 영역(사이에 256 B 틈), 나머지는 64 KB 하나다. heap_3은 newlib-nano malloc이다.

(각 파일은 3000개 값과 END까지 이어진다. 앞 두 줄만 보였다.) ovh는 카운터를 두 번 연달아 읽은 차이(0~2 tick)이고, 40 ns 눈금이 명령 32 ns와 맞지 않아 생기는 양자화라 빼지 않았다. 분포는 Python으로 정리했다.

그림 3 — 예제 3의 분포를 us로 바꿨다(1 tick = 40 ns). heap_1은 선 하나(3.1 us 근처 고정), heap_2는 꼬리가 30 us까지 간다. 같은 부하에서 빈 블록 수 최대값은 heap_2 85개, heap_4 19개, heap_5 20개였다.

출력에서 볼 것:

3.4 예제 4 — 시간 vs 빈 블록 수 N, 그리고 상한 식#

무엇을 확인하는 코드인가: 32 B 블록 2N+1개를 할당하고 짝수 번째만 풀어서 서로 붙지 않은 빈 블록 N개를 만든다(heap_4도 병합할 수 없다). 그 뒤 2048 B를 요청하면 어떤 구멍에도 안 맞으니 N개를 모두 지나 맨 끝 큰 블록까지 가야 한다(최악 경로). 그 블록을 다시 풀면 주소 순 목록의 맨 끝까지 걸어서 끼운다.

그림 4 — 예제 4. 네 선 모두 직선이다. 기울기(N = 0 → 400): heap_4 malloc 8.80 tick/블록(352 ns), free 3.21 tick/블록(128 ns), heap_2 malloc 9.60, free 4.00 tick/블록.

출력에서 볼 것:

  • 완전한 직선이다. heap_4 malloc의 블록당 비용 352 ns ≈ 명령 11개(포인터 따라가기, 크기 비교, 끝 검사, 범위 검사 두 번). free는 128 ns ≈ 명령 4개(주소 비교만).
  • N = 400이면 heap_4 malloc 한 번이 146 us다. 1 kHz 제어 루프(주기 1000 us)의 15%가 할당 한 번에 사라지고, 그동안 스케줄러가 잠겨서 더 높은 우선순위 태스크도 못 돈다.
  • heap_2의 free_blocks가 N+2, N+1처럼 1~2개 더 많다. 앞 단계에서 풀었던 블록이 병합되지 않고 남아 있기 때문이다. 실험을 반복할수록 목록이 길어진다 — heap_2의 시간은 현재 상태가 아니라 역사 전체에 달렸다.

이제 상한을 식으로 쓴다. 측정값으로 heap_4 malloc은

T_malloc(N) ≈ 119 + 8.8 × N tick = 4.8 us + 0.35 us × N

이다(QEMU icount 기준). 남은 질문은 N의 상한이다. heap_4에서는 빈 블록 두 개가 주소상 붙어 있을 수 없다(풀 때 이웃과 병합하므로). 그러니 이웃한 빈 블록 사이에는 반드시 사용 중인 블록이 하나 이상 있다. 동시에 살아 있는 블록이 최대 L개라면

N_free ≤ L + 1

이다. 예제 3은 슬롯이 64개라 L ≤ 64, N_free ≤ 65이고, 상한은 4.8 + 0.35 × 65 ≈ 27.6 us다. 실측 최대는 11.4 us(빈 블록 19개)로 상한 안에 있다. 이 식이 "heap_4의 할당 시간은 결정적인가?"에 대한 답이다. 상한이 있고, 그 상한은 동시에 살아 있는 블록 수로 정해진다. 시스템 설계 단계에서 L을 셀 수 있으면(태스크 수 × 2 + 큐 수 + 버퍼 수 …) WCET를 쓸 수 있다.

heap_2에는 이 상한이 없다. 붙은 빈 블록도 따로 남으니 N_free는 L이 아니라 지금까지 쪼개진 횟수로 자란다. 예제 3에서 L ≤ 64인데 빈 블록이 85개였다. 이것이 heap_2를 새 설계에 쓰지 않는 두 번째 이유다(첫 번째는 §4의 단편화).

3.5 함정#

  • 최악 시간은 "가장 큰 요청"이 만든다. 큰 버퍼는 작은 구멍을 다 지나야 맞는 블록이 나온다. 주기 태스크가 가끔 큰 버퍼를 할당하면 그 주기만 튄다.
  • 할당 중에는 스케줄러가 잠긴다. 낮은 우선순위 태스크의 큰 할당 하나가 높은 우선순위 태스크의 응답 시간에 그대로 더해진다. 이것은 우선순위 역전과 같은 꼴이다(D3). 인터럽트는 계속 들어오므로 ISR 지연에는 영향이 없다. 다만 그 ISR이 깨운 태스크는 할당이 끝날 때까지 못 돈다.
  • QEMU 숫자는 상대값이다. 실칩에서는 heap이 외부 SDRAM이나 캐시 없는 영역에 있으면 포인터를 한 번 따라갈 때마다 수십 사이클이 들 수 있다. 블록당 비용은 실칩에서 다시 잰다(DWT CYCCNT, M 모듈). 식의 꼴(a + b × N)은 같다.

4. 단편화 — 빈 공간은 있는데 실패한다#

4.1 정의 두 가지#

  • 외부 단편화(external fragmentation): 빈 공간이 여러 조각으로 흩어져서, 합은 충분한데 요청 하나를 담을 연속된 조각이 없다. 예제 2의 500 B 실패. 가변 크기 할당기의 문제다.
  • 내부 단편화(internal fragmentation): 블록 안에서 낭비되는 공간. 100 B 요청이 112 B 블록이 되면 12 B가 내부 단편화다. 헤더와 정렬, 그리고 고정 크기 풀에서 "64 B 칸에 40 B 객체"가 만드는 낭비다. 고정 블록 풀은 외부 단편화를 없애는 대신 내부 단편화를 받아들이는 거래다(F2).

측정 지표는 단순하다. 가장 큰 빈 블록 / 전체 빈 공간. 1에 가까우면 건강하고, 0에 가까우면 위험하다. FreeRTOS heap_4/5의 vPortGetHeapStats()가 xSizeOfLargestFreeBlockInBytes와 xAvailableHeapSpaceInBytes를 같이 준다. heap_2에는 이 API가 없어서, 예제는 빈 목록을 직접 걸었다(heapsel.h의 fl_stats).

4.4 "단편화 때문에 실패하지 않는다"를 어떻게 증명하나#

면접 질문 "How do you prove no fragmentation failure?"의 답은 강한 것부터 넷이다.

  1. 구조로 없앤다 — 초기화 뒤 free가 없다. 정적 할당, 또는 heap_1, 또는 초기화 후 잠금(예제 1). 할당 순서가 매 부팅 같으므로 첫 부팅에서 성공하면 영원히 성공한다. 증명이 필요 없는 유일한 방법이고, 인증 프로젝트가 이것을 고르는 이유다.
  2. 구조로 없앤다 — 고정 크기 블록 풀. 크기가 하나뿐인 풀에서는 외부 단편화가 정의상 없다(어떤 빈 칸이든 어떤 요청에 맞는다). 풀마다 "최대 동시 사용 개수"만 세면 된다. 크기 종류가 몇 개면 풀을 몇 개 둔다. Don의 SSD 펌웨어가 쓴 방식이다(F2).
  3. 분석으로 상한을 둔다. 가변 크기 할당기에 대해서는 이론상 최악 경계가 있다. Robson(1974)은 최대 동시 사용량이 M이고 블록 크기가 최대 n배까지 다를 때, 어떤 할당기든 실패하지 않으려면 M의 약 log₂(n)배 수준의 메모리가 필요할 수 있다는 것을 보였다. 실무에서 이 경계는 너무 커서(1500/64 ≈ 23배 → log₂ ≈ 4.5배) heap 크기를 정하는 데 쓰이기보다 "가변 크기는 최악을 보장하기 비싸다"는 근거로 쓰인다.
  4. 시험과 감시로 근거를 쌓는다 — heap_4. 최악 부하(최대 동시 사용, 최대 요청 크기, 가장 긴 수명 섞기)로 오래 돌리는 스트레스 시험(예제 6처럼 실제 시간보다 빠르게), 그리고 필드에서 가장 큰 빈 블록과 최소 여유를 텔레메트리로 보낸다. 기준은 "가장 큰 빈 블록의 최저값 ≥ 가장 큰 요청 × 여유율". 이것은 증명이 아니라 증거다. 인증 문서에는 deviation과 함께 이 시험 결과를 붙인다.

1과 2는 "실패하지 않는다"고 말할 수 있고, 3과 4는 "실패하지 않을 것이라는 근거가 이렇다"고 말할 수 있다. 면접에서는 이 구별을 말하는 것이 핵심이다.

5. 정적 할당 빌드 — 메모리 예산을 링크 시점에 확정한다#

5.1 FreeRTOS의 두 스위치#

설정기본값 (FreeRTOS.h)1이면
configSUPPORT_DYNAMIC_ALLOCATION1xTaskCreate, xQueueCreate, xSemaphoreCreateMutex, xTimerCreate, xEventGroupCreate, xStreamBufferCreate … 이 생긴다. heap 파일이 필요하다
configSUPPORT_STATIC_ALLOCATION0xTaskCreateStatic, xQueueCreateStatic, xSemaphoreCreateMutexStatic, xTimerCreateStatic, xEventGroupCreateStatic, xStreamBufferCreateStatic … 이 생긴다. idle·timer 태스크 메모리를 vApplicationGetIdleTaskMemory()/vApplicationGetTimerTaskMemory()로 받는다
configKERNEL_PROVIDED_STATIC_MEMORY0위 두 콜백을 커널이 정적 배열로 직접 제공한다(MPU 포트에서는 금지 — tasks.c 48줄의 #error)

둘 다 0이면 #error다(FreeRTOS.h 2893줄). 둘 다 1이면 섞어 쓸 수 있고, 커널은 TCB의 ucStaticallyAllocated(A4에서 본 필드)에 "스택과 TCB 둘 다 동적 / 스택만 정적 / 둘 다 정적"을 기록해 뒀다가 prvDeleteTCB()에서 자기가 할당한 것만 vPortFree한다(tasks.c의 tskDYNAMICALLY_ALLOCATED_STACK_AND_TCB = 0, tskSTATICALLY_ALLOCATED_STACK_ONLY = 1, tskSTATICALLY_ALLOCATED_STACK_AND_TCB = 2). 정적으로 만든 태스크를 vTaskDelete해도 메모리는 그대로 내 배열이다. 그 배열을 다시 쓰려면 태스크가 정말 지워진 뒤(idle이 정리한 뒤, C9)여야 한다.

정적 API의 버퍼 타입(StaticTask_t, StaticQueue_t, …)은 커널 내부 구조체와 크기만 같은 공개 구조체다. 커널은 생성할 때 configASSERT( xSize == sizeof( TCB_t ) )처럼 크기가 맞는지 확인한다(A4 §2.1).

5.3 링크 실패는 기능이다#

같은 앱을 RAM 64 KB 칩(작은 STM32급)이라고 치자. 랩 링커 스크립트를 복사해서 RAM LENGTH = 64K로 바꿨다(ram64k.ld). 그리고 ctl 태스크 스택을 실수로 16384 words(64 KB)로 적었다고 하자.

출력에서 볼 것:

  • 정적 빌드는 빌드가 실패했다. 링커가 "RAM을 7,896 B 넘쳤다"고 정확한 숫자까지 말한다(RAM overflow는 랩 링커 스크립트의 ASSERT 메시지, B5). 펌웨어가 장비에 올라가기 전에, CI에서 잡힌다.
  • 동적 빌드는 빌드가 성공했다(.bss 37 KB, 64 KB 안에 들어간다). 실패는 실행 중에 xTaskCreate가 64 KB 스택을 32 KB heap에서 못 받으면서 났다. 이 예제는 부팅 직후라 바로 보였지만, 그 할당이 "특정 모드에 들어갈 때만" 일어나는 코드였다면 필드에서야 드러난다.
  • 이것이 인증 프로젝트가 정적 할당을 고르는 가장 실용적인 이유다. 메모리 예산 검사를 사람과 시험이 아니라 링커가 한다. Don이 SSD 펌웨어에서 "SRAM이 넘치면 링크가 깨진다"를 겪어 봤다면 같은 장치다.

정적 전용 빌드에서는 실수로 동적 API를 부르면 더 일찍 걸린다. xQueueCreate는 configSUPPORT_DYNAMIC_ALLOCATION 1일 때만 매크로로 정의되므로, 0이면 그 이름이 없어서 컴파일 단계에서 implicit declaration 에러가 난다(-Werror=implicit-function-declaration이 기본인 GCC 14 이상). 커널이 아닌 코드가 pvPortMalloc을 직접 부르면 heap 파일이 없으니 링크 에러다.

5.4 정적 할당의 비용#

  • API가 길다. 객체마다 버퍼 두 개(저장 공간 + 제어 블록)를 선언해서 넘긴다. 매크로로 감싸는 것이 보통이다(Zephyr는 처음부터 그렇게 했다, §7).
  • 수명이 고정이다. "가끔만 쓰는 큰 버퍼"도 항상 RAM을 차지한다. 두 모드가 절대 동시에 안 쓰는 버퍼라면 union으로 겹치거나, 그 모드 전용 풀을 둔다. 이 판단을 링크 시점에 사람이 해야 한다.
  • 크기는 여전히 추측이다. 정적 할당은 "총량이 들어가는가"를 보장할 뿐, 스택 512 words가 충분한지는 말해 주지 않는다. 그건 F3(스택 산정)의 일이다.

6.2 configHEAP_CLEAR_MEMORY_ON_FREE#

1이면 vPortFree가 블록의 사용자 영역을 0으로 지운다(heap_2/4/5, V10.5.0(2022-09)에서 추가 — History.txt의 "Heap improvements" 항목). 목적은 두 가지다. 보안(풀린 메모리에 키·개인 정보가 남지 않게)과 디버깅(use-after-free가 0을 읽어 빨리 드러나게). 비용은 해제하는 바이트 수에 비례한다. 1 KB 버퍼 해제가 memset 1 KB만큼 길어지고, 그 memset은 스케줄러를 잠그기 전에 한다(소스상 heapFREE_BLOCK 직후, vTaskSuspendAll 앞). 그래서 다른 태스크를 막지는 않지만 호출한 태스크의 WCET에는 들어간다.

B5에서 heap을 .noinit으로 옮기면 웜 리셋 뒤 heap에 이전 값이 남는다고 했다. 이 설정은 그것과 별개다(해제 시점에 지울 뿐, 부팅 때 지우지 않는다). "받은 메모리가 0"을 원하면 pvPortCalloc을 쓴다(heap_2/4/5에 있다).

6.3 configENABLE_HEAP_PROTECTOR — 포인터 난독화 + 범위 검사#

V11.0.0에서 heap_4/5에 들어왔다(History.txt: "Add bounds checking and obfuscation to internal heap block pointers"). 이름은 protector지만 카나리 바이트를 블록 끝에 두는 방식이 아니다. 소스를 보면 이렇게 동작한다.

  • vApplicationGetRandomHeapCanary(&xHeapCanary)가 heap 초기화 때 한 번 불려 난수를 받는다(앱이 제공해야 한다, 없으면 링크 에러).
  • 헤더의 pxNextFreeBlock을 저장할 때 canary와 XOR해서 저장하고, 읽을 때 다시 XOR한다(heapPROTECT_BLOCK_POINTER). 할당된 블록의 pxNextFreeBlock은 NULL이 아니라 NULL ^ canary = canary 값이 된다(V11.2.0부터: "Add pointer protection to the pxNextFreeBlock member of the allocated block's metadata").
  • 목록을 걸을 때마다 포인터가 heap 범위 안인지 heapVALIDATE_BLOCK_POINTER로 확인한다(heap_4는 protector와 상관없이 항상, heap_5는 protector가 켜졌을 때만, §2.8).

효과: overflow가 헤더를 덮으면, 공격자든 버그든 canary를 모르고는 "그럴듯한" 포인터를 만들 수 없다. 덮인 값은 XOR을 풀면 무작위 주소가 되어 범위 검사에 걸린다. 다음 예제에서 이것이 정확히 어떤 경우를 더 잡는지 본다.

6.4 예제 8 — overflow와 double free, protector 끄고·켜고#

무엇을 확인하는 코드인가: 64 B 블록 a, b를 연달아 할당한다(b의 헤더가 a 바로 뒤). 경우 1은 a를 4바이트 넘쳐 0x41로 쓰고 b를 푼다. 경우 2는 a를 두 번 푼다. 경우 3은 a를 4바이트 넘쳐 0으로 쓰고 b를 푼다. 각각 protector 0/1.

출력에서 볼 것:

  • a와 b의 간격은 0x48 = 72 B = 64 B 데이터 + 8 B 헤더다. 4바이트 overflow는 정확히 b 헤더의 첫 워드 pxNextFreeBlock을 덮는다.
  • 경우 1(0x41로 덮음)은 protector가 없어도 잡혔다. 할당된 블록의 pxNextFreeBlock은 NULL이어야 하는데(370줄) 0x41414141이라서다. 이 검사는 configASSERT만 켜져 있으면 늘 있다.
  • 경우 2(double free)도 둘 다 잡혔다. 첫 free가 xBlockSize의 할당 비트를 지웠으니 두 번째 free에서 369줄 "할당됨이어야 한다"에 걸린다. 다만 첫 free 뒤에 그 블록이 다른 할당에 다시 쓰였다면(할당 비트가 다시 섰다면) 두 번째 free는 남의 블록을 푼다 — 이것은 어떤 설정으로도 못 잡는다.
  • 경우 3(0으로 덮음)이 핵심이다. protector가 없으면 덮인 값 0이 "정상 값 NULL"과 같아서 아무것도 못 잡고 계속 돈다(survived). protector를 켜면 정상 값이 NULL이 아니라 canary라서 0은 틀린 값이 되고 370줄에서 잡힌다. 0으로 넘치는 버그는 흔하다(memset(buf, 0, sizeof buf + 1), 문자열 끝 NUL 하나 더 쓰기). protector가 더 잡는 것은 바로 이 "그럴듯한 값으로 덮인 경우"다.
  • 검출 시점은 해제할 때다. overflow가 일어난 순간이 아니다. 덮은 코드(a의 주인)와 걸린 코드(b를 푼 쪽)가 다른 태스크일 수 있다. 그래서 assert 위치만 보고 범인을 찾으면 안 된다. 범인을 그 자리에서 잡으려면 MPU 가드나 빨간 영역(redzone)이 필요하다(F3, F4).

7. Zephyr — 정적 객체가 기본, heap은 크기를 정한 풀#

7.1 기본 스타일: K_*_DEFINE#

Zephyr는 커널 객체를 매크로로 정적 정의하는 것이 기본 문체다. K_THREAD_DEFINE, K_SEM_DEFINE, K_MUTEX_DEFINE, K_MSGQ_DEFINE, K_HEAP_DEFINE, K_THREAD_STACK_DEFINE(모두 include/zephyr/kernel.h, 스택은 kernel/thread_stack.h). 매크로는 객체를 STRUCT_SECTION_ITERABLE로 정해진 링커 섹션(k_sem_area, k_msgq_area …)에 놓고, 커널은 부팅 때 그 섹션을 훑어 초기화한다. K_THREAD_DEFINE으로 만든 스레드는 main() 전에 이미 존재하고, 지정한 지연 뒤 스스로 시작한다. FreeRTOS의 xTaskCreateStatic + 버퍼 두 개를 한 줄로 줄인 셈이고, 링크 시점 예산 검사가 기본값이다.

동적 쪽도 있다. k_malloc/k_free/k_calloc/k_aligned_alloc은 시스템 heap 하나에서 나온다(kernel/mempool.c). 시스템 heap의 크기는 CONFIG_HEAP_MEM_POOL_SIZE로 정하고, 기본값은 0이다(kernel/Kconfig). 서브시스템이 HEAP_MEM_POOL_ADD_SIZE_*로 최소 크기를 요구하면 그 합으로 올라가고(HEAP_MEM_POOL_IGNORE_MIN으로 무시 가능), 최종값이 0이면 시스템 heap이 아예 없어서 k_malloc은 항상 NULL이다. 즉 Zephyr는 "쓰려면 크기를 명시적으로 정하라"가 기본이다. 최종 크기는 kernel/CMakeLists.txt가 K_HEAP_MEM_POOL_SIZE로 컴파일 정의에 넣고, mempool.c가 K_HEAP_DEFINE(_system_heap, …)으로 정적 배열을 만든다. heap 자체도 정적 배열이다.

libc malloc은 별개의 arena다(CONFIG_COMMON_LIBC_MALLOC_ARENA_SIZE, 기본 −1 = 남은 RAM 전부, 일부 설정에서는 다른 값). 시스템 heap과 libc arena가 두 개의 다른 heap이라는 점을 기억한다. 그 아래의 할당기(sys_heap, k_heap, k_mem_slab)의 구조와 시간 성질은 F2에서 다룬다. 동적 스레드(CONFIG_DYNAMIC_THREAD)는 v4.4.2에서도 EXPERIMENTAL이다.

9.1 드론 비행 제어기#

비행 제어 루프(IMU 1~8 kHz, rate loop, 모터 출력)는 실행 중 할당 0이 원칙이다. 태스크·큐·세마포어는 정적 생성, 센서 샘플은 정적 링버퍼, 로그는 정적 이중 버퍼. 그런데 같은 MCU에 MAVLink 파서, 파일 시스템(SD 카드 로그), 때로는 네트워크 스택이 올라간다. 이들은 가변 크기 버퍼를 원한다. 흔한 구성은 이렇다.

  • 비행 경로: 정적만. 코드 리뷰와 정적 분석(MISRA Dir 4.12)으로 지킨다.
  • 부가 기능: heap_4를 따로 두고, 그 heap을 쓰는 태스크는 비행 태스크보다 낮은 우선순위로 둔다. 다만 §3.5처럼 할당 중에는 스케줄러가 잠긴다는 점 때문에, 비행 태스크의 응답 시간 분석에 "최악 할당 시간"을 블로킹 항으로 넣는다. 예제 4의 식으로 그 값을 정한다. 더 깔끔한 방법은 부가 기능용 할당기를 스케줄러 잠금 대신 뮤텍스(우선순위 상속)로 보호하는 별도 풀로 만드는 것이다(F2).
  • 필드 감시: 1초마다 vPortGetHeapStats()의 가장 큰 빈 블록과 최소 여유를 텔레메트리에 싣는다. 비행 로그를 분석하는 쪽에서 "가장 큰 블록의 최저값"이 비행 시간에 따라 줄어드는지를 본다. 줄어든다면 예제 6의 heap_2처럼 언젠가 실패한다.

PX4(NuttX 위)는 이 구성의 실제 예다. 모듈 시작 때 new로 객체를 만들고 비행 중에는 할당을 피하는 것이 관례다(Q1에서 다룬다).

9.2 로봇 관절 모터 컨트롤러#

FOC 전류 루프 20 kHz는 ISR 안에서 돈다. 여기서는 어떤 할당도 안 되고(FreeRTOS heap은 ISR 금지), 통신(CAN) 쪽도 메시지 크기가 고정(CAN FD 64 B 이하)이라 고정 블록 풀이나 정적 큐로 충분하다. 이런 장비는 정적 전용 빌드(configSUPPORT_DYNAMIC_ALLOCATION 0)가 가장 자연스럽다. RAM이 32~128 KB인 작은 MCU에서는 §5.3의 "링크 실패로 예산 검사"가 그대로 이득이다.

9.3 센서 허브 MCU#

Linux SoC 옆에서 IMU 타임스탬프를 모아 SPI로 넘기는 MCU는 버스트 크기가 들쭉날쭉할 수 있다. 그래도 최대 버스트는 정해져 있다. "최대 크기 버퍼 N개"의 풀을 정적으로 두면, 작은 버스트에서 내부 단편화(빈 칸 낭비)가 생기지만 외부 단편화는 없다. RAM이 넉넉하면 이 거래가 거의 항상 이긴다. Zephyr라면 K_MEM_SLAB_DEFINE이 그 풀이다(F2).

11. 면접에서 이렇게 말한다#

Q. Can you use malloc in an RTOS?

A. 쓸 수는 있지만 조건이 붙는다. 위험은 넷이다: 시간이 빈 블록 수에 비례하고, 단편화로 여유가 있어도 실패하고, 실패가 실행 중에 나고, 오염이 모든 태스크로 번진다. 그래서 비행 제어 같은 핵심 경로는 정적 할당이나 초기화 시점 할당 + 잠금으로 실행 중 할당을 없앤다. 서드파티 때문에 꼭 필요하면 heap_4나 고정 블록 풀을 쓰고, 최악 시간과 가장 큰 빈 블록을 측정·감시한다.

Yes, but with conditions. A general-purpose heap has four problems in a real-time system: allocation time grows with the number of free blocks, fragmentation can make a request fail while plenty of total memory is free, the failure happens at run time, and a single overflow corrupts metadata shared by every task. So on the control path I allocate everything statically or only during initialization and then lock the heap — that's what MISRA, JSF rule 206 and JPL's Power of Ten ask for. Where a third-party stack needs dynamic memory, I use heap_4 or fixed-size pools, bound the worst-case time, and monitor the largest free block in the field. On QEMU I measured a heap_2 server fail after 249 requests with 65 percent of the heap still free.

꼬리 질문: "What about C++ new?" → 같은 heap이다. operator new를 pvPortMalloc으로 바꾸거나 초기화 때만 쓰고, 예외가 꺼진 빌드에서는 실패를 nullptr(new (std::nothrow))로 받는다.

Q. What's the difference between heap_2 and heap_4? Which would you pick?

A. 둘 다 블록 헤더 8 B짜리 빈 목록 할당기다. heap_2는 목록이 크기 순이고 이웃을 합치지 않는다. heap_4는 주소 순이고 풀 때 앞뒤 빈 블록과 합친다. 그래서 heap_2는 크기가 섞이면 큰 블록이 사라져 결국 실패하고, 빈 블록 수에 상한도 없다. 새 설계라면 heap_4다. heap_1은 free가 없고, heap_3은 libc malloc 감싸기, heap_5는 heap_4를 여러 RAM 영역으로 넓힌 것이다.

Both keep a singly linked free list with an eight-byte header per block. heap_2 keeps the list sorted by size and never merges neighbors; heap_4 keeps it sorted by address and coalesces with the blocks before and after on every free. In my test with the same random workload, heap_2 failed a 1 KB request with 18 KB free because its largest block was 16 bytes too small, while heap_4 never dropped below a 13 KB largest block over twenty thousand operations. heap_2 was also slower in the tail, because unmerged fragments made the list 85 entries long versus 19. So heap_4 by default; heap_1 if nothing is ever freed; heap_5 when RAM is split across banks.

Q. Is pvPortMalloc deterministic? What's its worst-case execution time?

A. 상수 시간은 아니지만 상한은 있다. heap_4 malloc은 고정 비용 + 블록당 비용 × 지나는 빈 블록 수다. QEMU에서 블록당 352 ns로 완전한 직선이었다. heap_4는 빈 블록끼리 붙을 수 없어서 빈 블록 수 ≤ 동시 사용 블록 수 + 1이다. 그러니 동시 사용 블록 수를 알면 WCET를 식으로 쓸 수 있다. 그리고 할당 중에는 스케줄러가 잠기므로 그 시간이 다른 태스크의 블로킹 항이 된다.

It isn't constant-time, but it is bounded. heap_4 walks the free list, so the cost is a fixed part plus a per-block part times the number of free blocks it passes. On a Cortex-M3 model I measured an exact straight line, about 350 nanoseconds per free block, so 400 fragments meant 146 microseconds for one allocation. Because heap_4 coalesces, two free blocks can never be adjacent, so the free-block count is at most the number of live allocations plus one — that gives a closed-form bound if you know how many blocks can be live at once. heap_2 has no such bound. And since the allocator suspends the scheduler, that time is blocking for every other task, so it goes into the response-time analysis.

Q. How do you prove you won't get a fragmentation failure?

A. 증명할 수 있는 방법은 둘뿐이다. 초기화 뒤에 free를 안 하거나(정적·heap_1·잠금), 크기가 하나뿐인 고정 블록 풀을 쓴다. 가변 크기 heap에는 Robson의 최악 경계가 있지만 너무 커서 실용적이지 않다. 그래서 heap_4를 쓸 때는 증명이 아니라 증거를 낸다: 최악 부하 스트레스 시험, 그리고 필드에서 가장 큰 빈 블록의 최저값 감시.

Strictly, only two designs let you prove it. Either nothing is freed after initialization — static allocation, heap_1, or a locked heap — so if the first boot succeeds every boot succeeds; or every size class has its own fixed-block pool, where external fragmentation can't exist by construction and you only count peak usage per pool. For a general heap there are theoretical worst-case bounds, like Robson's, but they're too large to size a microcontroller heap. So with heap_4 I give evidence rather than proof: an accelerated stress test with worst-case sizes and lifetimes, and field telemetry of the minimum-ever largest free block compared against the largest request.

Q. Why isn't free heap size enough to monitor heap health?

A. 합계는 단편화를 못 본다. 예제에서 heap의 55%가 비어 있었는데 1 KB 요청이 실패했다. 가장 큰 빈 블록을 봐야 한다. FreeRTOS는 vPortGetHeapStats가 그 값을 준다(heap_4/5). 그리고 부팅 뒤 최저 여유(xPortGetMinimumEverFreeHeapSize)로 heap 크기를 정한다.

Free bytes is a sum; fragmentation is about the largest contiguous piece. I had a heap that was 55 percent free and still failed a one-kilobyte request. So I report the largest free block from vPortGetHeapStats, plus the minimum-ever free size for sizing, and I alert on the largest block trending down over uptime.

Q. How do you build FreeRTOS without any heap?

A. configSUPPORT_DYNAMIC_ALLOCATION 0, configSUPPORT_STATIC_ALLOCATION 1로 하고 heap 파일을 링크하지 않는다. 모든 객체를 xTaskCreateStatic, xQueueCreateStatic 같은 API에 버퍼를 넘겨 만들고, idle·timer 태스크 메모리는 vApplicationGet…TaskMemory 콜백이나 configKERNEL_PROVIDED_STATIC_MEMORY로 준다. 이점은 메모리 예산을 링커가 검사한다는 것이다. 64 KB RAM 설정에서 스택을 잘못 적으면 정적 빌드는 "RAM overflowed by 7896 bytes"로 링크가 실패했고, 동적 빌드는 링크가 통과한 뒤 실행 중에 실패했다.

Set configSUPPORT_DYNAMIC_ALLOCATION to 0 and static allocation to 1, and don't link any heap_x file. Every object is created with the Static variant and buffers I declare, and the idle and timer task memory comes from the vApplicationGet callbacks or configKERNEL_PROVIDED_STATIC_MEMORY. The real win is that the linker enforces the memory budget: with a 64 KB RAM map and an oversized stack, the static build failed to link — region RAM overflowed by 7,896 bytes — while the heap build linked fine and only failed at run time in the malloc-failed hook.

Q. Can you call pvPortMalloc from an ISR?

A. 안 된다. FreeRTOS heap은 스케줄러 잠금으로 보호하는데, 그건 태스크끼리만 막고 ISR은 못 막는다. ISR은 미리 할당한 버퍼(정적 링버퍼, 풀)를 쓰고, 할당이 필요하면 태스크로 미룬다. Zephyr의 k_heap은 스핀락이라 ISR에서 K_NO_WAIT로 가능하지만, 시간 상한은 따로 따져야 한다.

No. The FreeRTOS heaps protect their free list by suspending the scheduler, which stops other tasks but not interrupts, so an ISR could interrupt a task in the middle of a list update. ISRs use pre-allocated buffers — a static ring buffer or a fixed pool — and defer anything that needs allocation to a task. Zephyr's k_heap uses a spinlock, so it is callable from an ISR with K_NO_WAIT, but I'd still bound its time before putting it there.

14. 요약 & 체크리스트#

RTOS에서 범용 heap의 문제는 넷이다: 시간이 빈 블록 수에 비례하고, 단편화로 여유가 있어도 실패하고, 그 실패가 실행 중에 나고, 오염이 모든 태스크로 번진다. 규칙(MISRA Dir 4.12·Rule 21.3, JSF 206, Power of 10)은 그래서 동적 할당을 막거나 "초기화 뒤 금지"로 제한한다. FreeRTOS는 할당기 다섯 개를 준다. heap_1은 free가 없는 bump 할당기라 상수 시간(약 3 us, 그중 대부분이 스케줄러 잠금 비용)이고, heap_2는 크기 순·병합 없음이라 크기가 섞이면 큰 블록이 사라진다(55% 여유에서 1 KB 실패, 서버 부하에서 2.5초 만에 실패, heap 5배로 늘려도 12분). heap_4는 주소 순·병합이라 빈 블록 수 ≤ 동시 사용 블록 수 + 1이 되고, 시간은 4.8 us + 0.35 us × N(QEMU)으로 상한을 쓸 수 있으며, 같은 서버 부하에서 100만 요청 동안 실패가 없었다. heap_3은 libc malloc을 감싸고(락은 F7), heap_5는 heap_4를 여러 RAM 영역으로 넓힌다(범위 검사는 protector일 때만). xPortGetFreeHeapSize는 단편화를 못 보므로 vPortGetHeapStats의 가장 큰 빈 블록을 감시한다. protector는 헤더 포인터를 canary로 XOR해서, 0처럼 "그럴듯한" 값으로 덮인 overflow까지 해제 시점에 잡는다. 정적 전용 빌드(configSUPPORT_DYNAMIC_ALLOCATION 0)는 실행 중 할당을 물리적으로 없애고 메모리 예산을 링커가 검사하게 한다. Zephyr는 K_*_DEFINE 정적 객체가 기본이고, k_malloc의 시스템 heap도 크기를 정한(기본 0) 정적 배열이다. "단편화로 실패하지 않음"을 증명할 수 있는 것은 초기화 뒤 free 없음과 고정 블록 풀뿐이고, heap_4는 스트레스 시험과 필드 감시로 증거를 쌓는다.
