이 노트를 다 읽으면: "평면 RTOS → MPU 격리 → MMU 프로세스 RTOS → Linux + PREEMPT_RT" 스펙트럼에서 각 단계가 무엇을 사고 무엇을 내주는지(주소 공간, IPC, 결정성 비용, 인증) 표 하나로 말할 수 있다 · NuttX를 kernel build(프로세스마다 주소 공간)로 직접 빌드해 "같은 가상 주소, 다른 내용"과 "한 프로세스만 죽는 결함 격리"를 flat build와 나란히 보여 줄 수 있다 · Zephyr를 Cortex-A53 MMU 위에서 userspace로 돌려 page table을 직접 걷고, 같은 코드의 syscall·전환 비용을 Cortex-M3 MPU와 명령 수로 비교할 수 있다 · QNX 메시지 패싱·VxWorks RTP의 프로세스 모델과 Cortex-R82(EL1 MMU 선택 + MPU)를 공개 자료 범위에서 설명하고, 드론·로봇·차량에서 어느 쪽을 고를지 결정 흐름으로 답할 수 있다 왜 필요한가: 국방·항공 회사는 VxWorks와 INTEGRITY, 차량 회사는 QNX와 AUTOSAR Adaptive, 드론 회사는 PX4(NuttX)를 쓴다. 면접에서 "Why not just use Linux?", "What does an MMU buy you on an RTOS, and what does it cost?"가 나오면 MCU RTOS만 아는 사람과 시야 차이가 바로 드러난다. Don의 SSD 세계(Cortex-R82 기반 차세대 컨트롤러)에서도 "MMU를 켤 것인가"가 실제 설계 질문이다 Don 기준 난이도: MMU·TLB·page table 자체는 EL F11에서, Linux RT 메모리 규칙(mlockall·prefault)은 EL N1·N2에서 이미 봤다 / 새로 배울 부분은 RTOS가 MMU를 쓰는 세 가지 방식(보호만, 프로세스마다 주소 공간, 마이크로커널 + 메시지), NuttX kernel build의 빌드 구조(커널과 앱을 따로 빌드, syscall proxy), Zephyr arm64의 domain별 page table과 ASID, MMU가 결정성에 매기는 값(TLB miss·page walk·page fault)을 숫자로 보는 법 선행 노트: A6(RTOS 지형 — QNX·VxWorks·NuttX 시장 사실은 거기), B9(Cortex-R52 MPU 2단계), C8(커널 진입 경로 — M3에서 잰 syscall 비용), C10(Zephyr A53 SMP 실행), C11(ARINC 653 시간 분할), F4(MPU), F5(유저 모드 격리 — 이 노트와 같은 날 작성), EL F11(가상 메모리 깊게), EL N1·N2(PREEMPT_RT, RT 메모리 튜닝)

0. 큰 그림 — 이게 왜 필요한가#

0.1 직관 — 같은 건물, 칸막이의 종류가 다르다#

지금까지 RTOS 노트의 펌웨어는 전부 방 하나짜리 사무실이었다. FreeRTOS든 Zephyr든 Cortex-M 위에서는 태스크 전부가 같은 주소 공간(address space — CPU가 내는 주소가 가리키는 메모리 세상)을 쓰고, 기본 설정에서는 어느 태스크든 아무 주소나 쓸 수 있다. Don의 SSD 펌웨어도 그랬다. FTL 코드가 잘못된 포인터로 NAND 드라이버의 큐를 덮으면, 그 버그는 몇 분 뒤 전혀 다른 곳에서 assert로 드러난다.

F4·F5는 여기에 칸막이(MPU) 를 세웠다. 방은 여전히 하나지만 "이 태스크는 이 책상(리전)만 만진다"를 하드웨어가 검사한다. 이 노트는 그다음 단계다. MMU(Memory Management Unit) 가 있는 코어에서는 칸막이 대신 각자 다른 방(가상 주소 공간) 을 줄 수 있다. 프로세스(process — 자기 주소 공간을 가진 실행 단위)마다 page table이 따로 있어서, 같은 주소 0xC0101008이 프로세스 A에서는 A의 변수, B에서는 B의 변수를 가리킨다. 한 프로세스가 엉뚱한 곳을 쓰면 그 프로세스만 죽고 나머지는 계속 돈다.

문제는 값이다. 방을 바꿀 때마다 CPU는 page table 기준점(RISC-V satp, arm64 TTBR0_EL1)을 바꾸고, TLB(Translation Lookaside Buffer — 가상→물리 변환 결과 캐시)를 비우거나 태그로 구분해야 한다. TLB에 없는 주소는 page table을 메모리에서 몇 단계 걸어서(page walk) 찾는다. 아직 물리 페이지가 붙지 않은 주소는 page fault로 커널에 들어간다. 이 셋은 전부 "평소에는 안 보이다가 가끔 튀는" 지연이다. 실시간 OS가 MMU를 쓸 때 고민하는 것은 결국 "격리를 얼마나 사고, 그 값으로 결정성을 얼마나 내주나"다.

그림 1 — 메모리 격리 스펙트럼. 왼쪽 두 칸은 주소 공간이 하나다(MPU는 권한만 검사). 세 번째 칸부터 프로세스마다 page table이 따로 있다. 오른쪽으로 갈수록 결함 격리와 Linux·POSIX 코드 재사용이 좋아지지만, 최악 지연에 MMU 관련 항목이 더해진다.

0.3 Don의 경험과 연결#

SSD 컨트롤러 펌웨어에는 MMU가 없었거나, 있어도 identity map(가상 주소 = 물리 주소)으로 캐시 속성만 정하는 용도였다. 이것이 바로 "MMU를 쓰지만 주소 공간은 하나"인 모델이고, RTEMS와 Zephyr(arm64)가 지금도 이렇게 쓴다(§3에서 page table을 걸어 확인한다). 프로세스마다 주소 공간을 나누는 모델은 SSD 세계에서는 낯설지만, Cortex-R82가 선택 MMU를 넣고 "드라이브 위에서 Linux를 돌리는 computational storage"를 겨냥한 이유가 바로 그것이다(§6).

1. RTOS가 MMU를 쓰는 세 가지 방식#

1.1 MMU는 두 가지 일을 한다 — 변환과 권한#

EL F11에서 본 대로 MMU는 (a) 주소 변환(가상 주소 VA → 물리 주소 PA)과 (b) 페이지 단위 권한·속성(읽기/쓰기/실행, 특권/비특권, 캐시 속성)을 한 page table 항목(descriptor)에 같이 적는다. MPU(F4)는 (b)만 있고, 단위가 "리전 몇 개"다. MMU는 (b)를 4 KiB 페이지 단위로, 개수 제한 없이 할 수 있고, (a)까지 한다.

RTOS가 이 기능을 어디까지 쓰느냐에 따라 세 방식으로 나뉜다.

1.2 RTEMS — MMU가 있어도 주소 공간은 하나#

RTEMS User Manual은 스스로를 "multi-threaded, single address-space, real-time operating system with no kernel-space/user-space separation"이라고 소개한다. 애플리케이션은 커널과 같은 특권으로 돌고 하드웨어를 직접 만진다. MMU가 있는 칩(Cortex-A, SPARC LEON, PowerPC)에서도 BSP가 MMU를 켜는 이유는 캐시 속성과 영역 구분 때문이지 프로세스 때문이 아니다(RTEMS에는 프로세스가 없고 스레드만 있다). 우주 쪽 RTEMS 사용자가 격리가 필요할 때는 RTEMS 안에서가 아니라 하이퍼바이저(XtratuM, PikeOS 등)로 파티션을 나눈다 — C11의 ARINC 653 시간 분할과 같은 발상이다.

2. NuttX — 한 소스, 세 가지 빌드#

2.1 직관 — 같은 펌웨어를 세 가지 건물에 넣는다#

NuttX는 같은 커널 소스를 설정 하나로 세 가지 메모리 모델로 빌드한다. A6 §3.4·I1이 NuttX 자체(POSIX, /dev, VFS, PX4)를 다루고, 이 절은 빌드 모드만 판다.

flatCONFIG_BUILD_FLAT아무거나하나의 ELF로 링크NSH builtin(함수 이름으로 등록), 전부 특권
protectedCONFIG_BUILD_PROTECTEDMPU커널 blob + 유저 blob 두 개 (2-pass)유저 blob 안의 태스크, 비특권, 커널 메모리 보호

kernel build에서 앱은 커널과 링크되지 않는다. make export가 커널 쪽 헤더, libc, syscall proxy 라이브러리를 tar로 내보내고, nuttx-apps가 그것을 import해서 앱마다 독립 ELF(apps/bin/hello, apps/bin/f9va …)를 만든다. 실행 중에는 NSH가 posix_spawn()으로 그 ELF를 읽어 새 주소 공간에 올린다. Linux에서 /bin/ls를 실행하는 것과 같은 그림이다.

무엇을 확인하나: rv-virt:knsh64가 부팅해서 init(=NSH)을 파일에서 읽은 프로세스로 띄우는지, ps에 PID가 따로 붙는지.

2.7 NuttX 커널 안 — 주소 공간 전환은 addrenv_switch() 한 곳#

스케줄러가 다음 태스크를 고르면 sched/addrenv/addrenv.c의 addrenv_switch(tcb)가 불린다. 다음 태스크의 그룹(=프로세스)이 지금과 다른 주소 공간이면, 지금 공간의 캐시를 정리하고(up_addrenv_coherent) up_addrenv_select()로 새 공간을 건다. RISC-V 구현은 arch/risc-v/src/common/riscv_addrenv.c와 riscv_mmu.h다.

발견 2 — NuttX RISC-V는 ASID를 쓰지 않는다. mmu_satp_reg()에 ASID 인자가 있지만 주소 공간을 만들 때 항상 0을 넘기고, mmu_write_satp()는 satp를 쓴 직후 sfence.vma x0, x0(모든 주소, 모든 ASID의 TLB 무효화)를 한다. 즉 프로세스 전환마다 TLB가 통째로 비워진다. §3.3에서 볼 Zephyr arm64는 메모리 domain마다 8비트 ASID를 따로 줘서 전환 때 TLB를 비우지 않는다. 같은 "MMU RTOS"라도 구현에 따라 전환 뒤 지연 꼬리가 다르다는 뜻이다.

2.8 protected build는 이 노트에서 돌리지 않았다#

protected build(MPU)는 F5의 Zephyr userspace와 같은 계열이다. NuttX 문서("NuttX Protected Build")는 커널 blob과 유저 blob을 2-pass로 따로 링크하고 유저 쪽에서 커널을 syscall로만 부르게 한다고 설명한다. QEMU의 RISC-V virt·MPS2 보드용 protected 구성(rv-virt:pnsh64 같은 이름이 있다)을 시간 안에 돌려 보지는 않았다. PX4에는 TII(Technology Innovation Institute) 쪽에서 기여한 "PX4 protected build" PR(#16931)이 있다 — PX4 모듈을 유저 공간에서, 일부를 launch_kmod로 커널 공간에서 돌리는 구조다. PX4 업스트림 보드 대부분이 어떤 빌드 모드로 나가는지는 PX4 소스가 이 랩에 없어 확인하지 못했다.

3. Zephyr on Cortex-A53 — MMU를 "보호용"으로 쓰는 RTOS#

3.1 직관 — 방은 하나, 칸막이가 페이지 단위로 촘촘해졌다#

Zephyr의 userspace(F5)는 Cortex-M에서는 MPU 리전으로, Cortex-A(arm64)와 x86에서는 MMU page table로 구현된다. 개념은 같다: memory domain(스레드 묶음이 접근할 수 있는 partition 목록)과 K_USER 스레드. 차이는 구현이다. arm64에서는 domain마다 page table 한 벌이 있고, 스레드 전환 때 domain이 바뀌면 TTBR0_EL1을 그 domain의 table로 바꾼다. 그러나 Zephyr는 identity map(VA = PA)이라 주소 공간 자체는 하나다. NuttX kernel build처럼 "같은 주소, 다른 내용"은 없다. §1.1 표의 방식 ①이다.

Zephyr arm64가 userspace를 지원하는 조건은 arch/arm64/core/Kconfig에 있다: Cortex-A(Armv8-A)는 select ARCH_HAS_USERSPACE if ARM_MMU, Armv8-R(Cortex-R82)은 select ARCH_HAS_USERSPACE if ARM_MPU. 그리고 config ARM_MMU의 기본값은 default n if CPU_AARCH64_CORTEX_R이다 — Zephyr는 Cortex-R82를 MMU가 아니라 MPU로 쓴다(§6.1).

3.2 예제 6 — A53 MMU 위의 결함 격리#

무엇을 확인하나: 두 user 스레드를 서로 다른 domain에 넣고, 남의 partition을 쓰거나 커널 데이터를 읽으면 그 스레드만 죽는지. 그리고 domain마다 다른 page table(TTBR0)과 ASID가 붙는지.

3.3 예제 7 — page table을 직접 걷기: domain마다 무엇이 다른가#

무엇을 확인하나: 커널·dom_a·dom_b 세 page table에서 같은 네 주소(a_data, b_data, kernel_only, main의 코드)의 마지막 단계 descriptor를 읽어 권한 비트를 비교한다. 이 보드는 CONFIG_ARM64_VA_BITS=32, 4 KiB granule이라 L1(1 GiB) → L2(2 MiB) → L3(4 KiB) 3단계다(EL F11 §1.2의 4단계에서 L0가 빠진 꼴).

identity map이라 descriptor 안의 물리 주소를 그대로 포인터로 따라갈 수 있다(커널 모드인 main에서만). 인덱스 시프트 39 - 9 × lvl은 L1 = 30, L2 = 21, L3 = 12다.

출력에서 볼 것:

  • 세 table의 차이는 비트 하나다. ...f13과 ...f53의 차이 0x40 = AP[1] (비트 6, PTE_BLOCK_DESC_AP_ELx) = "EL0도 접근 가능". dom_a에서는 a_data 페이지만, dom_b에서는 b_data 페이지만 이 비트가 켜져 있다. 커널 table에서는 둘 다 꺼져 있다. 그래서 같은 물리 페이지가 table에 따라 "user 접근 가능/불가"로 바뀐다. 이것이 예제 6의 permission fault가 난 이유다.
  • 데이터 페이지는 전부 UXN·PXN(실행 금지). 코드 페이지는 EL1 RO / EL0 RO UX PX — 커널 코드가 모든 domain에서 user에게 읽기·실행 가능하다. Zephyr userspace는 코드를 보호하지 않고 데이터만 보호한다(C8 표 "커널 코드 보호 없음"과 같다). user 스레드가 커널 함수로 점프할 수는 있지만, 그 함수가 커널 데이터를 만지는 순간 permission fault가 난다.
  • nG(not-global) 비트가 켜져 있다. nG 항목은 TLB에 ASID 태그와 함께 들어가므로, domain을 바꿔도 다른 domain의 번역과 섞이지 않는다. 그래서 Zephyr arm64는 전환 때 TLB를 비울 필요가 없다(§3.5).

3.6 예제 9 — Zephyr demand paging: RTOS에도 page fault가 있다#

무엇을 확인하나: Zephyr는 arm64와 32비트 x86에서 demand paging(CONFIG_DEMAND_PAGING — 필요할 때 backing store에서 페이지를 읽어 오고 모자라면 내보내는 것)을 지원한다(arch/Kconfig: ARM64 블록이 select ARCH_HAS_DEMAND_PAGING). 공식 샘플 samples/subsys/demand_paging은 RAM 256 KiB 보드에 약 3.9 MiB짜리 함수를 넣고 semihosting 파일을 backing store로 쓴다. 샘플을 내 폴더로 옮겨 호출마다 page fault 수와 시간을 찍게 고쳤다.

prj.conf는 샘플 그대로(CONFIG_SRAM_SIZE=256, CONFIG_DEMAND_PAGING=y, CONFIG_DEMAND_MAPPING=y, CONFIG_LINKER_USE_ONDEMAND_SECTION=y, CONFIG_BACKING_STORE_ONDEMAND_SEMIHOST=y 등). kernel/include/mmu.h가 내부 헤더라 -Wextra에서 그 헤더의 unused parameter 경고가 나와 -Wno-unused-parameter를 더했다. 경고 0개.

size -A로 본 ondemand_text 섹션은 4,030,464 B(984페이지)였다. 출력에서 볼 것:

  • small_function은 처음 부를 때만 page fault 1번에 914 명령, 두 번째부터 10 명령이다. 같은 함수 호출이 91배 차이난다. 이것이 demand paging이 실시간 경로에서 금지되는 이유를 한 줄로 보여 준다.
  • huge 함수는 RAM보다 커서 부를 때마다 984번 fault(전 페이지)가 난다. 실행해야 할 명령은 약 100만 개(nop 1000 × 1000 + 연산)인데 실제로는 약 208만 cycle이 걸렸다. 차이 약 108만 ÷ 984 ≈ fault 하나에 약 1,100 명령(내보낼 페이지 고르기, page table 고치기, TLB 무효화, 복사)이다. 그리고 이것은 backing store I/O 시간을 뺀 값이다. semihosting 파일 읽기는 QEMU 밖에서 일어나 가상 시간에 거의 잡히지 않는다. 실제로는 여기에 플래시 읽기 시간(페이지당 수십 µs 단위)이 더해진다.
  • 세 번의 huge 호출 시간이 수천 cycle씩 다르다(icount인데도). CONFIG_QEMU_ICOUNT_SLEEP=y 보드라 semihosting 대기가 가상 시간에 일부 섞인 것으로 보인다 — 원인을 더 파지는 않았다.
  • small #3은 huge 호출로 RAM이 다 찼는데도 fault가 없었다. arm64의 기본 교체 알고리즘은 LRU(subsys/demand_paging/eviction/Kconfig: default EVICTION_LRU if ARM64, 이 빌드의 .config도 CONFIG_EVICTION_LRU=y)라서, huge 함수의 페이지들이 서로를 내보내는 동안 따로 쓰인 small_function 페이지가 남은 것으로 보인다.

실무 의미: Zephyr의 demand paging은 "코드가 RAM보다 큰 저가 SoC(외부 플래시 XIP가 없는 칩)"를 위한 기능이다. 실시간 경로의 코드와 데이터는 __pinned_func, __pinned_data 같은 고정(pinned) 섹션에 넣어 절대 내보내지 않게 한다(include/zephyr/linker/section_tags.h). Linux의 mlockall()이 하는 일을 링커 섹션으로 정적으로 하는 셈이다.

4.3 예제 11 — TLB와 page walk: 같은 캐시 줄 수, 다른 페이지 수 (VM 기준)#

무엇을 확인하나: 무작위 pointer chase(앞 노드의 값이 다음 주소라서 접근이 하나씩 직렬로 일어남)를 세 가지 배치로 한다. (a) 캐시 줄을 64 B 간격으로 촘촘히 → 페이지 수가 적다. (b) 페이지마다 줄 하나(간격 4096 + 64 B) → 줄 수 = 페이지 수. (c) (b)와 같은 배치인데 2 MiB THP(huge page)로 받기. 줄 수가 같으니 캐시 효과는 비슷하고, 차이는 TLB가 덮어야 하는 페이지 수에서 나온다.

4.4 Don의 경험으로 번역#

SSD 컨트롤러에서 "DRAM의 L2P 테이블을 무작위로 조회하면 캐시 miss가 난다"는 것은 Don이 이미 아는 비용이다. MMU는 그 위에 번역 miss를 한 겹 더 얹는다. 무작위 LBA 조회 1회 = 데이터 캐시 miss 1회 + (TLB miss면) page walk의 메모리 접근 2~4회. 그래서 FTL 테이블처럼 크고 무작위로 읽히는 구조를 MMU 켠 코어에 올리면 큰 페이지로 매핑하거나 TCM·고정 영역에 둔다. Cortex-R82에서 MMU를 켤지 말지의 판단(§6.1)이 바로 이 표다.

5.1 QNX Neutrino — 마이크로커널 + 메시지 패싱#

구조. QNX 문서(SDP 8.0 System Architecture, "The QNX OS microkernel")에 따르면 마이크로커널(procnto 안에 들어 있다)은 스레드와 프로세스, 스케줄링, POSIX 동기화 원시, 시계·타이머, 인터럽트 처리, 그리고 메시지 패싱만 제공한다. 파일 시스템, 네트워크, 장치 I/O는 "optional processes and shared libraries"이고, 장치 드라이버에 해당하는 것은 resource manager — 경로 이름(/dev/ser1 같은)을 자기에게 등록하고 그 경로로 오는 open/read/write 메시지를 처리하는 유저 프로세스다. 인터럽트도 커널이 받아서 유저 스레드를 깨우는 "low-latency path"로 넘긴다.

그래서 시리얼 드라이버가 잘못된 포인터로 죽어도 커널은 살아 있고, 그 드라이버 프로세스만 재시작하면 된다. 예제 3의 "프로세스 하나만 죽는다"를 드라이버와 파일 시스템까지 넓힌 설계다. 값은 예제 5·8에서 본 syscall·전환 비용을 드라이버 호출 하나하나가 낸다는 것이다 — read() 하나가 클라이언트 → 커널 → 드라이버 프로세스 → 커널 → 클라이언트로 두 번 전환한다.

메시지 패싱의 세 동작. 클라이언트 MsgSend() → 서버 MsgReceive() → 서버 MsgReply(). QNX 문서(Getting Started, 메시지 패싱 장)의 상태 이름을 그대로 쓰면:

  • 서버 스레드가 이미 MsgReceive()로 기다리고 있으면(RECEIVE-blocked) 메시지가 즉시 서버 주소 공간으로 복사되고 클라이언트는 REPLY-blocked가 된다.
  • 기다리는 서버가 없으면 클라이언트는 SEND-blocked로 큐에 선다.
  • 서버가 MsgReply()하면 답이 클라이언트로 복사되고 클라이언트가 풀린다. 서버가 그 사이 죽으면 클라이언트의 호출은 ESRCH로 돌아온다.

우선순위 상속이 메시지에 붙어 있다. 서버 스레드는 받은 메시지를 보낸 클라이언트의 우선순위를 물려받는다(기본 동작, ChannelCreate()의 _NTO_CHF_FIXED_PRIORITY로 끔). D3에서 본 뮤텍스 우선순위 상속을 IPC 차원에서 하는 것이다. 낮은 우선순위 로그 클라이언트가 보낸 요청 때문에 서버가 높은 우선순위 제어 클라이언트를 기다리게 만드는 역전을 막는다. 문서의 주의점: 서버는 MsgReply() 후에도 물려받은 우선순위를 유지하다가 다음 메시지에서 바뀐다.

그림 8 — QNX 메시지 패싱 한 번. 아래 띠가 커널이 하는 일의 전부이고, 드라이버·파일 시스템은 오른쪽 같은 서버 프로세스다. 클라이언트는 답이 올 때까지 REPLY-blocked로 멈추고, 서버는 클라이언트의 우선순위를 물려받아 처리한다. 드라이버도 이 모양의 유저 프로세스다.

스케줄링 쪽 특징. QNX는 adaptive partitioning(파티션별 CPU 예산을 보장하되 남는 시간은 다른 파티션이 빌려 쓸 수 있는 스케줄러)을 제공한다. C11의 ARINC 653 고정 시간 창보다 느슨한 "예산 보장"이다. 세부 알고리즘은 공개 문서 범위에서 더 들어가지 않는다.

어디서 쓰나. A6 §4.3: 차량 디지털 콕핏·ADAS·텔레매틱스(BlackBerry FY2026 연차 보고서 기준 2억 7,500만 대 이상). 2026년 Embedded World에서 로봇용 플랫폼(QNX General Embedded Development Platform)도 발표했다.

5.3 seL4와 INTEGRITY — 한 줄씩#

  • seL4: capability(권한 토큰) 기반 마이크로커널. C 구현의 기능적 정확성이 형식 증명되었다(A6 §4.9, O7). 커널은 메시지 패싱과 capability 관리만 하고 정책은 전부 유저 레벨이다. RTOS라기보다 "격리의 바닥"이고, 그 위에 RTOS·Linux 게스트를 올리는 구성이 많다.
  • INTEGRITY: 분리 커널(separation kernel). 파티션별 메모리·시간 격리를 보장한다(A6 §4.4).

6. Cortex-R82와 Cortex-A 위의 RTOS#

6.1 Cortex-R82 — MPU와 선택 MMU를 같이 가진 R#

B9 §1.2 표에 R82를 "Armv8-R AArch64, PMSAv8-64 + 선택 VMSA"로 한 줄 적었다. 여기서 MMU 관점으로 다시 본다.

  • 발표: 2020-09-03(eeNews Europe, AnandTech). 첫 64비트 Cortex-R. 클러스터 최대 4코어(eeNews: "four cores in a 5nm process", 1.8 GHz), Cortex-R8·R5 대비 약 2배 성능(Arm 주장).
  • 메모리 시스템: Arm 제품 페이지는 "Highest-performance Cortex-R processor with memory management unit (MMU)", "MMU supports rich operating systems, such as Linux", DRAM 최대 1 TB 주소 지정이라고 쓴다. eeNews는 MMU를 "optional", 그리고 "can still be configured with a Memory Protection Unit (MPU) to run bare metal and RTOS"라고 쓴다.
  • 어느 EL에 무엇이: Xen의 Armv8-R64 지원 패치 시리즈(Arm 엔지니어 작성)가 "MPU in EL1 & EL2 is configurable, MMU in EL1 is configurable"이라고 정리한다. 즉 EL2(하이퍼바이저)는 언제나 MPU, EL1은 MPU 또는 MMU를 고른다. Arm Cortex-R82 TRM(r3p1, 2025-03)이 1차 출처지만 이 노트에서 TRM 본문을 직접 읽지는 못했다 — 세부(리전 수, MMU를 EL1 게스트별로 고르는 방식)는 TRM으로 확인할 것.
  • 겨냥하는 곳: SSD·HDD·computational storage(Arm 제품 페이지). 드라이브 안에서 Linux를 돌려 데이터 근처에서 계산하는 시나리오가 MMU를 넣은 이유다.
  • 안전 버전: Cortex-R82AE — Arm Zena CSS(차량용 컴퓨트 서브시스템)의 Safety Island가 "one or more Cortex-R82AE CPU clusters"로 구성된다(Arm Zena CSS 문서). 발표 시점은 2024년으로 보도됐지만(Counterpoint) Arm 1차 보도자료로 날짜를 확인하지 못했다.

그림 9 — Cortex-R82에서 가능한 구성 하나. EL2 MPU가 두 게스트를 가두고, 한 게스트는 MPU로 RTOS를, 다른 게스트는 MMU로 Linux를 돌린다. 이 구성은 Arm 자료의 "MPU at EL1/EL2, optional MMU at EL1"을 그림으로 옮긴 것이고, 실제 제품의 구성은 확인하지 못했다.

QEMU에는 Armv8-R AArch64 모델이 없어서 이 노트에서 R82는 실행하지 못했다.

Don의 SSD 세계로 번역. 차세대 SSD 컨트롤러가 R82를 쓰면, 실시간 FTL·NAND 경로는 지금처럼 MPU(또는 MMU 끔) + RTOS/실행부로 두고, MMU는 "Linux를 같이 돌릴 때"나 "큰 DRAM을 64비트로 보는 데"만 쓰는 구성이 자연스럽다. §4.3의 TLB 곡선이 이유다 — 무작위 L2P 조회는 TLB를 금방 넘친다. MMU를 켠다면 L2P 테이블은 큰 block으로 매핑한다.

6.2 Cortex-A 위의 RTOS — 세 가지 자리#

Cortex-A(A53, A55, A7x)에 RTOS가 올라가는 자리는 크게 셋이다.

  1. AMP의 한 코어: Linux가 도는 A 클러스터의 코어 하나를 떼어 RTOS를 돌리고 OpenAMP(remoteproc/RPMsg)로 묶는다(P5, EL O1~O3). 흔한 것은 오히려 같은 SoC의 Cortex-R5F·M 코어를 쓰는 쪽이다.
  2. 하이퍼바이저 게스트: Zephyr는 arch/arm64/core/xen(Xen 게스트 지원)을 갖고 있다. Jailhouse, Xen, 상용 하이퍼바이저(PikeOS, QNX Hypervisor) 위에서 Linux 옆 RTOS 게스트로 돈다. ARINC 653식 분할과 같은 발상이다(C11).
  3. A 코어 전체를 MMU RTOS가: QNX(콕핏·ADAS), VxWorks·INTEGRITY(항공·국방 미션 컴퓨터). 이때 RTOS는 이 노트의 ② 또는 ③ 방식이다.

안전 섬(safety island)은 보통 A 클러스터 옆의 별도 R(또는 M) 코어다 — Arm Zena CSS의 R82AE, 그리고 B9 §11.2에서 본 R5F·R52 안전 섬. A53/A55 클러스터 자체를 lockstep으로 묶은 칩(Cortex-A65AE·A76AE 같은 AE 계열의 split-lock)도 있지만 제품별 구성은 이 노트에서 확인하지 않았다.

AUTOSAR Classic vs Adaptive. Classic(I5)은 MCU·R 코어 위의 정적 OSEK 계열 OS다 — MMU 없음, MPU로 SC3/SC4 메모리 보호. Adaptive는 Cortex-A급 위에서 POSIX OS(PSE51 프로파일 인터페이스) 를 전제로 하는 플랫폼이고, 그 OS 자리에 QNX나 Linux가 들어간다. 즉 "차량 ECU의 RTOS"라고 할 때 Classic 쪽은 MPU 세계, Adaptive 쪽은 이 노트의 MMU 프로세스 세계다. Rivian 같은 회사의 존 컨트롤러는 Classic, 중앙 컴퓨터는 Adaptive + QNX/Linux라는 분업이 흔한 그림이다(회사별 구성은 확인하지 않았다).

9.1 드론 회사 — "미션 컴퓨터를 VxWorks로 할까 Linux로 할까"#

국방 드론의 미션 컴퓨터(Cortex-A)는 영상 처리·AI·암호화 링크를 돈다. 고객(정부)이 DO-178C나 보안 인증 증거를 요구하면 VxWorks Cert·INTEGRITY가 후보가 되고, 그렇지 않으면 Linux RT가 개발 속도로 이긴다. 펌웨어 엔지니어가 내야 할 숫자는 이 노트의 표다: 제어 경로가 몇 µs 예산인지, syscall·전환·fault 비용이 그 안에 들어가는지. 대부분의 회사는 비행 제어는 MCU(PX4·NuttX flat)에 두고, 미션 컴퓨터는 Linux로 해서 이 고민 자체를 피한다. 그러면 질문은 "MCU ↔ 미션 컴퓨터 링크"(P5, K)로 옮겨 간다.

9.2 로봇 — 드라이버 하나가 죽어도 로봇은 서 있어야 한다#

휴머노이드·AMR의 주 컴퓨터에서 카메라 드라이버가 죽으면? Linux에서는 커널 드라이버 버그가 커널 패닉이고, QNX에서는 그 resource manager 프로세스만 재시작한다(§5.1). 이것이 QNX가 로봇 시장에 들어오는 논리다. 반대로 관절 MCU는 평면 RTOS가 맞다 — 예제 8에서 user syscall 하나가 200 명령이었다. 20 kHz FOC 루프(50 µs, 168 MHz MCU면 약 8,400 cycle)에서 루프마다 syscall 몇 개면 예산의 몇 %가 경계 비용으로 사라진다.

9.3 차량 — 같은 차에 세 가지 세계#

Rivian 같은 회사에서는 바디·존 ECU(AUTOSAR Classic, MPU), 중앙 컴퓨터(AUTOSAR Adaptive + QNX/Linux, MMU 프로세스), 안전 섬(R52·R82AE, MPU RTOS)이 한 차에 같이 있다. 실리콘 검증 직무라면 "이 코어의 MMU/MPU를 누가 어떤 모드로 쓰나", "EL2 MPU로 게스트를 가뒀을 때 DMA는 어떻게 막나(SMMU)"가 bring-up 질문이다.

11. 면접에서 이렇게 말한다#

Q. What does an MMU give you on an RTOS that an MPU doesn't, and what does it cost?

A. MPU는 한 주소 공간 안에서 리전 몇 개의 권한만 정한다. MMU는 페이지 단위 권한에 더해 프로세스마다 다른 주소 공간을 줄 수 있어서, 같은 바이너리를 여러 번 띄우고 한 프로세스가 죽어도 나머지가 산다. 대신 syscall이 함수 호출의 10배 이상이고, 주소 공간 전환과 TLB miss·page walk·page fault라는 꼬리 지연이 생긴다. 그래서 RT 경로는 프로세스를 미리 만들고 페이지를 미리 고정한다.

An MPU gives me a handful of permission regions inside one address space. An MMU gives me page-granular permissions with no practical region limit, and optionally a separate address space per process — so I can run the same binary twice and a crash kills only one process. I built NuttX in kernel mode and showed exactly that: two instances at the same virtual address with independent values, and a null-pointer write that killed one process while another kept running. The cost: a syscall was about 300 instructions versus 19 for a direct call, process creation was milliseconds, and on real hardware you add TLB refills and page walks — up to 7 to 10 times slower per access once the working set outgrows the TLB. So for the real-time path I create processes at boot, prefault and lock memory, and keep hard real-time work inside one address space.

Q. Why not just use Linux with PREEMPT_RT instead of QNX or VxWorks?

A. 기술적으로 Linux RT는 많은 경우 충분하다. 차이는 세 가지다: 인증 증거(ASIL D·DO-178C를 살 수 있나), 결함 격리 범위(Linux는 드라이버가 커널 안이라 드라이버 버그 = 패닉, QNX는 드라이버가 프로세스), 메모리 기본값(Linux는 demand paging이 기본이라 앱이 mlockall로 되돌려야 하고, RTOS는 처음부터 정적 매핑).

Often Linux RT is good enough, and it wins on ecosystem. The differences that matter are: certification evidence — you can buy ASIL D or DO-178C evidence for QNX, VxWorks Cert or INTEGRITY, which is very hard for Linux; the fault-isolation boundary — in Linux a driver bug is a kernel panic, while in QNX the driver is a user process you can restart; and memory defaults — Linux demand-pages by default, so a real-time app has to mlockall and prefault, whereas an MMU RTOS maps a process's memory up front. On a drone I'd keep flight control on an MCU RTOS and use Linux RT on the mission computer unless the customer requires certified evidence.

꼬리 질문: "What about the latency numbers?" → 환경마다 다르니 자기 보드에서 cyclictest와 최악 경로를 잰다고 답하고, EL N1의 측정 방법을 예로 든다.

Q. How does QNX message passing work, and what problem does priority inheritance on messages solve?

A. 클라이언트가 MsgSend하면 서버가 MsgReceive로 받을 때까지 SEND-blocked, 받은 뒤 답이 올 때까지 REPLY-blocked다. 서버는 MsgReply로 답한다. 서버 스레드는 메시지를 보낸 클라이언트의 우선순위를 물려받아서, 낮은 우선순위 클라이언트의 요청 때문에 높은 우선순위 클라이언트가 밀리는 역전을 막는다.

It's synchronous send-receive-reply. The client's MsgSend blocks — SEND-blocked until a server thread receives it, then REPLY-blocked until the server calls MsgReply. Data is copied by the kernel between the two address spaces. The server thread inherits the client's priority when it receives the message, so a high-priority client isn't stuck behind a low-priority request the server happens to be processing — it's priority inheritance applied to IPC instead of to a mutex. Drivers and filesystems are just servers built this way, called resource managers, which is why a driver crash doesn't take down the kernel.

Q. Does Zephyr have processes?

A. 없다. Zephyr userspace는 스레드 + memory domain이다. arm64에서는 domain마다 page table과 ASID가 따로 있지만 identity map이라 주소 공간은 하나고, 코드는 모든 user 스레드에게 읽기·실행 가능하다. 데이터 격리만 한다. 실제로 page table을 걸어서 domain 사이 차이가 AP 비트 하나라는 것을 확인했다.

No — it has threads and memory domains. On Cortex-A, each memory domain gets its own page-table copy and its own 8-bit ASID, so switching between domains is just a TTBR0 write and no TLB flush. But it's an identity map, a single address space: the same address means the same memory in every domain, and kernel text is readable and executable from user mode. I walked the A53 page tables and the only difference between two domains was the EL0 access bit on their own partition pages. So it's data isolation, not processes; for real processes on an open-source RTOS you'd look at NuttX's kernel build.

Q. Tell me about Cortex-R82. Why would a real-time core have an MMU?

A. 첫 64비트 R(Armv8-R AArch64)이고, MPU를 기본으로 가지면서 EL1에 선택 MMU가 있어서 Linux를 돌릴 수 있다. EL2는 MPU로 게스트를 가둔다. 겨냥한 곳은 SSD와 computational storage — 드라이브 안에서 Linux 앱을 돌리면서 NAND 경로는 MPU RTOS로 결정적으로 유지하려는 것이다. Zephyr와 FreeRTOS는 R82를 MPU로 지원한다.

It's the first 64-bit Cortex-R, Armv8-R AArch64, up to four cores per cluster and DRAM addressing up to a terabyte. It keeps the R-profile MPU — at EL2 always, at EL1 optionally — and adds an optional MMU at EL1 so a guest can run Linux. The target is storage: an SSD controller can keep the NAND and host-command path on an MPU-based RTOS for determinism, and run computational-storage applications in a Linux guest beside it, with the EL2 MPU fencing them apart. In the RTOS world it's supported as an MPU target — FreeRTOS added an ARM_CR82 SMP and MPU port in 11.3, and Zephyr defaults ARM_MMU to off on 64-bit Cortex-R. Coming from SSD firmware, I'd keep the FTL hot tables out of 4 KB-page translation — either MPU, or large block mappings.

Q. What is the hidden cost of a process switch that a simulator won't show you?

A. TLB다. QEMU에서 NuttX 프로세스 전환은 스레드 전환보다 31 명령만 더 들었다. 그런데 그 안에 TLB 전체 무효화가 있고, 실제 칩에서는 전환 뒤 접근마다 page walk가 붙는다. ASID가 있으면 이걸 피한다 — Zephyr arm64는 domain마다 ASID를 줘서 TLB를 안 비우고, NuttX RISC-V는 ASID 0 하나로 매번 비운다.

The TLB. In QEMU, a NuttX process switch cost only 31 more instructions than a thread switch, because writing satp and flushing the TLB are one instruction each. On real silicon the flush is cheap but the refill isn't: every access after the switch can miss and walk the page table, and I measured a page walk at 15 to 30 nanoseconds per access on my VM host versus under 1 when it hits. ASIDs avoid the flush — Zephyr on arm64 tags each memory domain with its own ASID, while NuttX on RISC-V currently uses ASID zero and flushes everything on every process switch. So I'd check that in the source before trusting any context-switch number.

Q. Your real-time process on Linux occasionally misses its deadline by a few hundred microseconds right after startup. What's your first guess?

A. 첫 접근 page fault. 버퍼나 스택을 루프 안에서 처음 만지고 있을 가능성이 크다. 실측으로 첫 접근 store 하나가 최악 0.2 ms였다. mlockall(MCL_CURRENT | MCL_FUTURE)와 prefault, 스택 미리 만지기로 fault를 0으로 만들고, /proc/<pid>/stat의 minflt나 getrusage로 루프 중 fault가 0인지 확인한다.

First-touch page faults. Something in the loop — a buffer, the stack, a lazily-mapped library page — is being touched for the first time. On my VM a single first-touch store had a median of half a microsecond and a worst case around 200 microseconds, versus 42 nanoseconds once prefaulted. I'd mlockall with MCL_CURRENT and MCL_FUTURE at startup, prefault the buffers and the stack, avoid malloc in the loop, and then verify with getrusage that the minor-fault count doesn't move during steady state.

14. 요약 & 체크리스트#

RTOS가 MMU를 쓰는 방식은 셋이다: ① identity map으로 권한만(RTEMS, Zephyr arm64), ② 프로세스마다 주소 공간(NuttX kernel build, VxWorks RTP), ③ 마이크로커널 + 메시지 패싱으로 드라이버까지 유저 프로세스(QNX, seL4, INTEGRITY). NuttX를 kernel build로 직접 빌드해 보니 두 프로세스가 같은 가상 주소 0xc0101008에 독립된 값을 갖고, NULL·커널 RAM·코드 페이지 쓰기가 전부 그 프로세스만 SIGSEGV로 끝냈다. 같은 코드의 flat build는 전역을 공유했고, 커널 RAM과 자기 코드를 조용히 덮어써서 다음 실행을 망가뜨렸으며, NULL 쓰기로 시스템 전체가 패닉했다. 대가는 QEMU 명령 수로 syscall 314(직접 호출 19), 스레드 전환 732(flat 404), 프로세스 전환 763, 프로세스 생성 7 ms였다. NuttX RISC-V는 ASID 0으로 프로세스 전환마다 TLB를 통째로 비우고, Zephyr arm64는 domain마다 8비트 ASID를 줘서 비우지 않는다 — QEMU는 이 차이를 비용으로 보여 주지 못한다. Zephyr userspace는 A53에서 domain마다 page table을 갖지만 identity map이라 프로세스가 아니며, domain 사이 차이는 AP 비트 하나, 코드는 모든 user에게 실행 가능했다. 같은 Zephyr 코드에서 user syscall은 A53·M3 모두 7~9배, domain 사이 전환은 M3 +23 명령(MPU 재설정), A53 +0이었다. VM 호스트에서 잰 MMU 비용: 첫 접근 page fault p50 0.5 µs·최악 0.2 ms(prefault·mlockall이면 0), 작업 집합이 TLB를 넘으면 접근당 7~10배(THP가 크게 줄임), Zephyr demand paging은 fault 하나에 약 1,100 명령 + I/O. Cortex-R82는 EL2 MPU + EL1 MPU/선택 MMU로 RTOS와 Linux를 한 칩에 둘 수 있고, 오픈소스 RTOS는 R82를 MPU로 지원한다. 고르는 순서는 "격리가 필요한가 → MMU가 있나 → 인증을 사야 하나 → Linux 재사용이 큰가"다.
