F8. 메모리 배치 실무 — 무엇을 어느 RAM에 둘지 링커에게 말하기

210분 읽기2150줄60개 절

이 노트를 다 읽으면: 여러 RAM(ITCM · DTCM · AXI SRAM · DMA SRAM · backup SRAM)을 가진 MCU에서 객체마다 위치를 근거 있게 정하고 표로 설명할 수 있다 · section attribute, 파일 패턴, CMSIS-6 copy/zero table, veneer · long_call로 원하는 배치를 만들고 map · nm · objdump로 증명할 수 있다 · 리셋을 넘어가는 크래시 로그(magic + 버전 + 크기 + CRC, 고정 주소, 부트로더와의 약속)를 설계할 수 있다 · ECC SRAM을 스택보다 먼저 초기화하는 startup을 어셈블리로 쓰고 비용을 잴 수 있다 · FreeRTOS heap_5 · 정적 스택, Zephyr DT 메모리 영역 · zephyr_code_relocate로 같은 일을 할 수 있다 왜 필요한가: STM32H7 · i.MX RT · Corstone-300 같은 고성능 MCU에서 "DMA가 안 와요", "ISR 지터가 커요", "필드 크래시 로그가 비어 있어요", "전원 켤 때만 HardFault" 같은 버그의 상당수가 배치 문제다. 면접에서 "What do you put in TCM?"은 드론 · 로봇 펌웨어 단골 질문이다 Don 기준 난이도: SSD 컨트롤러에서 TCM · DRAM · SRAM 뱅크에 객체를 나눠 넣고 TCM ECC를 지우던 경험이 그대로 쓰인다 / 새로 배울 부분은 Cortex-M 칩별 지도(H7 · RT1060 · AN547), CMSIS-6 표 형식, veneer와 long_call의 실제 비용, RTOS(heap_5 · 정적 스택 · 커널이 제공하는 idle 스택)의 배치, Zephyr의 DT 영역이 초기화되지 않는다는 함정 선행 노트: B5(리셋부터 main까지 — 링커 스크립트 · VMA/LMA · AT> · NOLOAD · copy table 기본 · .ramfunc 기본 — 다시 설명하지 않는다), B8(캐시 · TCM · H7 버스 지도 · 배치 표 초판), B9(Cortex-R TCM · ECC), B11(map 파일 · --gc-sections), E6(DMA + 캐시), E8(리셋 원인 · .noinit 기록 기본), F1(힙 구현). 이어지는 노트: F4(MPU 속성), M5(크래시 사후 분석), Q6(NPU arena 배치) 🔁 Bare-Metal 겹침: BM P2(실행 위치 최적화: flash vs RAM vs TCM 실행, 캐시 켜기, 정렬, ramfunc) · BM G6(저장 클래스 · 배치의 섹션 지정 부분) · BM Q7(메모리 오류 · ECC의 SRAM ECC 초기화 부분) — 이 노트가 주인. Bare-Metal 노트는 이 노트를 링크하고 const → flash · 초기화 순서 같은 C 저장 클래스 기초(G6)와 스크러빙 · 단일/이중 비트 오류 처리 · SEU(Q7)만 더한다

0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 컨트롤러에서 하던 일을 떠올려 보자. FTL의 명령 디스패치와 매핑 캐시는 Cortex-R의 TCM에, NAND 데이터 버퍼는 DRAM에, 컨트롤러 간 메일박스는 공유 SRAM에 두었다. 이유는 셋이었다. 빨라야 하는 것(0 wait, 결정적), 누가 닿아야 하는 것(DMA · 다른 코어 · 하드웨어 엔진), 오래 남아야 하는 것(리셋 뒤에도 남는 로그). 이 세 질문이 MCU에서도 그대로 배치를 정한다.

고성능 Cortex-M MCU는 RAM이 한 덩어리가 아니다. STM32H743에는 ITCM · DTCM · AXI SRAM · SRAM1~3 · SRAM4 · backup SRAM이 있고, 각각 속도, 캐시 여부, DMA 접근 가능 여부, 저전력 유지 여부, ECC 초기화 방식이 다르다. C 컴파일러는 이것을 모른다. "이 변수는 저 RAM에"를 알려 주는 방법은 섹션 이름과 링커 스크립트뿐이다. 이 노트의 부제 그대로 — 무엇을 어느 RAM에 둘지 링커에게 말하는 법이다.

그림 1 — 배치의 큰 그림. 왼쪽은 C 코드가 만든 객체, 오른쪽은 링커 스크립트의 MEMORY 영역. 화살표 위 글자는 "왜 거기인가"다. 이 연결을 만드는 수단이 이 노트의 내용이다.

실습 환경 한 줄#

QEMU mps2-an385(Cortex-M3 25 MHz) bare-metal + FreeRTOS V11.3.2, QEMU mps3-an547(Cortex-M55, ITCM/DTCM 있음) + Zephyr v4.4.2, 일부는 VM 호스트 C 모델과 빌드 전용(H7 모양 맵). 시간은 ICOUNT=1(명령 1개 = 32 ns)과 FPGAIO COUNTER(25 MHz, 1 tick = 40 ns)로 잰 QEMU icount 기준 값이며, 실제 칩과 절대값은 다르다(캐시 · 플래시 wait state · 버스 · TCM 속도 미모델링). QEMU에는 ECC도 없다. 그래서 이 노트에서 "빨라졌다"는 숫자는 명령 수 차이만 보여 줄 수 있고, 메모리 속도 차이는 보여 줄 수 없다 — 그 부분은 매번 정직하게 표시한다.

0.1 실습 보드 — AN385에도 RAM이 네 덩어리 있다#

랩 링커 스크립트(mps2_m3.ld)는 FLASH(0x0)와 RAM(0x2000_0000) 두 영역만 쓴다. 그런데 QEMU의 info mtree를 보면 AN385에는 RAM이 더 있다.

이 노트의 bare-metal 예제는 이 네 덩어리에 "실제 MCU의 역할"을 하나씩 맡긴다. 속도는 모두 같지만(QEMU), 주소가 다르다는 것 — 그래서 링커 배치 · 복사 · 초기화 · veneer가 실제 칩과 똑같이 일어난다는 것 — 이 중요하다.

예제 1 — 무엇을 확인하나: blockram이 정말 16 KB짜리가 반복(alias)되는지, 그리고 QEMU가 SYSRESETREQ 리셋 때 RAM 내용을 지우는지(지운다면 noinit 실험이 불가능하다).

출력에서 볼 것:

  • 0x0100_4000에 쓴 값이 0x0100_0000에서 읽힌다 → blockram은 16 KB가 4번 반복된 창이다. 링커에는 16 KB로만 알려야 한다(더 크게 쓰면 앞부분을 덮어쓴다).
  • QEMU는 SYSRESETREQ(AIRCR에 0x05FA0004) 리셋 때 어느 RAM도 지우지 않는다(ram_hi · psram · blockram 값이 남는다). 실칩의 웜 리셋과 같은 성질이라 noinit 실험을 할 수 있다. 반대로 QEMU를 새로 띄우면 RAM은 0이다 — 실칩의 전원 투입 직후(쓰레기 값)와 다르다. 이 차이는 §5에서 다시 짚는다.
  • 처음 만났던 함정 하나: 첫 버전은 "SSRAM1이 0x40_0000에서 반복되나"를 보려고 *(volatile uint32_t *)0x0을 읽었는데, GCC가 NULL 역참조를 UB로 보고 udf #255(정의되지 않은 명령)를 넣어 HardFault가 났다. 0번지가 정상 메모리인 MCU에서 0번지를 읽으려면 asm이나 링커 심볼을 거쳐야 한다(GCC의 -fno-delete-null-pointer-checks도 방법이다).

1.2 STM32H743 — B8의 지도에 두 가지를 더한다#

B8 §4.2에서 H743의 ITCM 64 KB(0x0000_0000), DTCM 128 KB(0x2000_0000), AXI SRAM 512 KB(0x2400_0000), SRAM1~3 288 KB(0x3000_0000), SRAM4 64 KB(0x3800_0000)와 "DMA1/2는 TCM에 못 닿는다"를 봤다. 여기서 더할 것은 둘이다.

  • backup SRAM 4 KB, 0x3880_0000. Zephyr v4.4.2 dts/arm/st/h7/stm32h7.dtsi의 backup_sram: memory@38800000(compatible = "zephyr,memory-region", "st,stm32-backup-sram")로 확인했다. VBAT 전원으로 내용을 유지할 수 있는 영역이라 POR(주 전원 차단)까지 넘어가는 기록에 쓴다. 유지에 필요한 레귤레이터 · 클럭 설정 순서는 RM0433 원문을 이 노트에서 확인하지 못했다. Zephyr는 이 영역용 섹션 태그 __stm32_backup_sram_section을 준다(include/zephyr/linker/section_tags.h).
  • TCM ECC 초기화. Zephyr v4.4.2 soc/st/stm32/stm32h7x/soc_m7.c의 soc_reset_hook()은 주석에서 ST AN5342 "How to use error correction code (ECC) management for internal memories protection on STM32 MCUs" Rev. 7 §3.1.1을 인용하며, 리셋 직후 TCM 내용은 정의되지 않았고 읽기 · 정렬 안 된 접근 · 부분 크기 접근이 ECC 오류를 낸다고 적고, ITCM은 64비트 쓰기, DTCM은 32비트 쓰기로 전체를 0으로 채운다. 이것이 §6의 실제 사례다.

1.3 i.MX RT1060 — 비율을 바꿀 수 있는 TCM (FlexRAM)#

NXP i.MX RT10xx의 Cortex-M7은 512 KB짜리 FlexRAM을 32 KB 뱅크 16개로 나눠 각 뱅크를 ITCM · DTCM · OCRAM 중 하나로 쓴다. Zephyr v4.4.2에서 확인한 사실:

  • dts/arm/nxp/imxrt/nxp_rt10xx.dtsi: flexram,bank-size = <32>, itcm@0 128 KB, dtcm@20000000 128 KB. nxp_rt1060.dtsi: flexram,num-ram-banks = <16>, FlexRAM의 OCRAM은 ocram@20280000 256 KB, FlexRAM 밖의 ocram2: ocram@20200000 512 KB가 따로 있다. 즉 기본 분할은 ITCM 128 + DTCM 128 + OCRAM 256 KB다.
  • 분할을 런타임에 바꾸는 코드: drivers/misc/nxp_flexram의 flexram_dt_partition()은 DT의 flexram,bank-spec 목록을 뱅크당 2비트로 IOMUXC_GPR->GPR17에 쓰고 GPR16의 FLEXRAM_BANK_CFG_SEL을 세운다. 주석이 "stack 변수를 만들지 말고 RAM의 데이터를 쓰지 말라"고 경고한다 — 자기가 서 있는 RAM의 정체를 바꾸는 코드이기 때문이다. 이 함수는 soc/nxp/imxrt/imxrt10xx/soc.c의 soc_reset_hook()에서 SystemInit()보다 먼저 불린다.
  • RT1060-EVK 보드(boards/nxp/mimxrt1060_evk/mimxrt1060_evk.dtsi)의 zephyr,sram은 외부 SDRAM(sdram0: memory@80000000, 32 MB)이고 zephyr,itcm · zephyr,dtcm은 따로 지정돼 있다. 코드는 FlexSPI 플래시(AHB 0x6000_0000, XIP)에서 돈다. "기본 RAM이 외부 SDRAM"이라는 점 때문에 이 보드에서 성능이 필요한 객체는 명시적으로 DTCM에 옮겨야 한다.

설계 함의: FlexRAM은 "ITCM이 모자라면 DTCM을 줄이자"가 링커 스크립트 + 레지스터 한 줄로 된다. 대신 링커 스크립트의 MEMORY 크기, 부트 ROM이 읽는 fuse(기본 분할), 런타임 GPR17 값이 모두 같은 그림이어야 한다(Zephyr는 BUILD_ASSERT로 DT 노드 크기와 뱅크 합을 대조한다). 부트 ROM이 쓰는 기본 분할의 fuse 이름은 RM 원문으로 확인하지 못했다.

1.5 Cortex-R — TCM이 기본인 세계#

Cortex-R5/R52의 ATCM · BTCM(· CTCM), 위치 레지스터, TCM ECC 켜기와 부팅 초기 TCM 지우기는 B9 §7에 정리했다. Zephyr의 CONFIG_DISABLE_TCM_ECC와 z_arm_tcm_disable_ecc()(arch/arm/core/cortex_a_r/tcm.c, reset.S에서 호출)도 거기서 봤다. 이 노트의 규칙(§6)은 R에도 그대로 적용된다.

그림 2 — 세 칩의 RAM 지도 비교(주소 · 크기는 Zephyr v4.4.2 DTS와 QEMU info mtree, H7 TCM ECC 폭은 Zephyr soc_m7.c 주석이 인용한 AN5342). 주황 = TCM, 초록 = 일반 SRAM, 빨강 = DMA 전용으로 쓸 SRAM, 회색 = 유지 · 외부, 파랑 = 코드 저장소. H7은 영역이 많고 버스 마스터 제약이 강하며, RT1060은 TCM 비율을 바꿀 수 있고, AN547은 TCM이 크고 코드가 ITCM에서 돈다.

1.7 실행 위치와 성능 — flash vs RAM vs TCM, 캐시, 정렬#

BM P2의 질문 "코드를 어디서 실행할까"에 대한 이 노트의 답을 정리한다. 측정은 QEMU가 메모리 속도를 모델링하지 않아 할 수 없으므로, 판단 순서만 적는다.

  1. 먼저 캐시를 켠다. M7 · M55의 I-cache · D-cache를 켜는 것(B8 §2.3)이 코드 위치를 옮기는 것보다 효과가 크고 공짜다. 플래시 가속기(ART 등, B8 §5)도 같다.
  2. 지터가 문제일 때 TCM으로 옮긴다. 캐시는 평균을 줄이지만 최악(miss)을 남긴다. 20 kHz 전류 루프처럼 "최악이 곧 사양"인 코드는 ITCM으로 옮겨 분산을 없앤다.
  3. 플래시 동작 중 실행이 필요할 때 RAM으로 옮긴다(B5 §9.1).
  4. 정렬: 핫 루프 시작을 페치 폭(M7 ITCM은 64비트 — B8 §4.1)에 맞추면 첫 페치가 반으로 잘리지 않는다. GCC는 -falign-functions=8, -falign-loops=8 같은 옵션을 주고, 함수 하나만이면 __attribute__((aligned(8)))를 붙인다. 효과는 칩마다 다르고 QEMU에서는 측정할 수 없다 — 실칩에서 DWT CYCCNT로 확인할 것.
  5. 옮긴 뒤에는 호출 경로를 본다. 함수 본체가 ITCM에 있어도 호출이 플래시의 veneer를 거치면 일부가 여전히 플래시 페치다(§3).

Don 경험과 연결: SSD 펌웨어에서 "핫 경로만 TCM, 나머지는 캐시 붙은 DRAM/플래시"로 나눴던 판단이 그대로다. 차이는 Cortex-M에서는 TCM이 수십~수백 KB라 커널 핫패스와 몇 개 ISR이 들어갈 정도라는 점이다.

2.2 CMSIS-6의 표준 copy/zero table#

B5 §2.7에서는 표 형식을 직접 만들었다({lma, vma, bytes}). CMSIS-6에는 표준 형식과 그 표를 도는 코드가 이미 있다. Zephyr 모듈 modules/hal/cmsis_6(커밋 30a859f, 2025-08)에서 확인한 내용:

  • CMSIS/Core/Include/m-profile/cmsis_gcc_m.h의 __cmsis_start(): __copy_table_t { const uint32_t *src; uint32_t *dest; uint32_t wlen; }와 __zero_table_t { uint32_t *dest; uint32_t wlen; }를 __copy_table_start__~__copy_table_end__, __zero_table_start__~__zero_table_end__ 사이에서 돌고, 끝나면 _start()(C 런타임 진입점)를 부른다. __PROGRAM_START가 정의돼 있지 않으면 이 함수가 __PROGRAM_START가 된다. picolibc를 쓰면 __PROGRAM_START가 picolibc의 _start로 바뀐다.
  • 단위가 워드(wlen)다. B5의 바이트 단위와 다르다. 링커 스크립트에서 SIZEOF(.data) / 4로 쓴다. 섹션 끝을 ALIGN(4)로 맞추지 않으면 마지막 1~3바이트가 복사되지 않는다.
  • 템플릿 링커 스크립트 CMSIS/Core/Template/Device_M/Config/Device_gcc.ld는 .copy.table에 .data 한 줄을, .zero.table은 비워 두고 주석으로 ".bss는 C 런타임 startup이 지운다"고 적는다. 추가 영역은 주석 처리된 .data2 · .bss2 줄을 풀어서 쓴다.

이 노트의 bare-metal 예제는 이 CMSIS 코드를 그대로 쓴다. startup은 벡터 테이블과 Reset_Handler만 만든다.

메모리 영역과 섹션 규칙은 두 파일로 나눴다(B8 §4.3처럼 INCLUDE로 조합한다 — 메모리 지도만 바꿔 끼우면 같은 섹션 규칙으로 다른 보드를 만든다).

이 스크립트에서 객체 종류가 초기화 방식 세 가지로 갈린다는 것을 눈여겨본다: copy table에 오른 것(.fast_text · .ram_text · .data · .psram_data — 초기값 복사), zero table에 오른 것(.bss · .psram_bss — 0), 어디에도 안 오른 것(.fast_bss · .psram_noinit · .noinit — 손대지 않음). 스택과 힙 메모리는 0일 필요가 없으므로 세 번째로 보낸다(B5 §8.3의 부팅 시간 교훈).

3. 메커니즘 ② — 코드를 RAM에서 부르기: veneer, long_call, 함수 포인터#

3.1 직관 — 점프는 거리 제한이 있다#

Thumb-2의 BL은 PC 기준 ±16 MB까지만 간다. H7의 플래시(0x0800_0000)와 ITCM(0x0000_0000)은 128 MB, 플래시와 SRAM(0x2000_0000)은 수백 MB 떨어져 있다. 닿지 않는 호출을 만나면 두 가지 해법이 있다.

해법누가생성 코드비용

B5 §9.2와 B8 §4.3에서 veneer가 생기는 것은 봤다. 여기서는 호출당 비용을 명령 수로 잰다. ICOUNT 모드에서 FPGAIO 카운터 1 tick = 40 ns, 명령 1개 = 32 ns이므로 ticks × 40 / 32 = 실행 명령 수다.

3.2 예제 3 — 같은 함수, 다섯 가지 호출 경로#

무엇을 확인하나: return x + 1 함수를 플래시, FAST(16 MB 안쪽), RAM(0x2000_0000, veneer), RAM + long_call, 함수 포인터로 각각 1만 번 부르고 명령 수를 센다. noipa는 GCC가 함수를 인라인하거나 결과를 미리 계산하지 못하게 한다.

숫자만 보면 "플래시가 제일 빠르다"처럼 보이지만, 루프 코드가 서로 다르다. 그래서 생성 코드를 봤다.

출력에서 볼 것:

  • 같은 모양의 루프(mov r0, rX → 호출 → subs → mov rX, r0 → bne, 5개 + 함수 본체 adds · bx lr 2개 = 7개)끼리 비교해야 한다. f_fast(BL 직접) 7, f_ram_lc(long_call) 7, f_ram(veneer) 8 — veneer는 호출마다 정확히 명령 1개(ldr.w pc, [pc])를 더한다. 플래시의 5는 GCC가 레지스터 이동 두 개를 없앤 다른 루프라서 나온 숫자다(배치와 무관).
  • long_call은 함수 주소 로드(ldr r6, [pc, #264], 0x1a0)를 루프 밖으로 끌어냈다. 그래서 루프 안 비용이 BL과 같다. veneer는 링커가 만든 것이라 컴파일러가 최적화할 수 없다.
  • 함수 포인터(volatile)는 매번 포인터를 메모리에서 읽어(ldr) 8이다.
  • QEMU가 못 보여 주는 것: 실칩에서 veneer는 플래시에 있다(0x1000). ITCM에 넣은 ISR을 플래시 veneer를 거쳐 부르면 그 명령 페치가 플래시 wait state · I-cache miss를 탄다. 명령 1개의 차이보다 이것이 크다. 그래서 Zephyr의 GCC용 __ramfunc는 long_call을 붙인다(include/zephyr/toolchain/gcc.h: Arm + GCC일 때 __attribute__((noinline)) __attribute__((long_call, section(".ramfunc"))), Clang은 long_call이 없어 veneer에 맡긴다는 주석과 LLVM 이슈 39969 링크).

3.3 직접 해 본 경계 — 16 MB#

AN385의 blockram은 0x0100_0000, 플래시 시작에서 정확히 16 MB다. 예제 2 · 3에서 main(0x19e, 0x1ec)이 FAST로 bl을 직접 쓸 수 있었던 것은 오프셋이 16 MB보다 조금 작기 때문이다. 다음 예제에서 FAST 안의 함수가 조금만 뒤로 가도(0x0100_0e31) 플래시 앞부분의 호출자에게는 범위를 넘어서 veneer가 생긴다. 거리 계산은 "호출하는 명령 주소 + 4 → 목적지"이고, 함수마다 · 호출 지점마다 다르다. 링커는 범위를 넘는 호출 지점이 하나라도 있으면 veneer를 만든다.

3.4 예제 4 — FreeRTOS 커널 핫패스를 TCM으로 (소스 수정 없이)#

무엇을 확인하나: FreeRTOS 소스를 한 줄도 고치지 않고 링커 스크립트의 파일 패턴만으로 tasks.o · list.o · port.o · queue.o의 코드를 FAST(TCM 역할) 또는 RAM으로 옮긴다. veneer가 몇 개 생기는지, 태스크 두 개가 알림을 주고받는 왕복(컨텍스트 스위치 2번)이 명령 몇 개인지 본다.

링커 스크립트는 sections_f8.ld에서 패턴 두 줄만 바꿨다.

처음에 *tasks.o *list.o *port.o *queue.o (.text* .rodata*)처럼 파일 이름을 나열하고 괄호를 한 번만 썼다가 고쳤다. GNU ld 문법에서 괄호 없는 파일 이름은 "그 파일의 모든 섹션"이라 tasks.o의 .bss · .data까지 코드 영역으로 끌려온다. 파일마다 (섹션)을 붙여야 한다.

xTaskNotifyGive는 매크로(→ xTaskGenericNotify)라 주소를 찍을 수 없어서 실제 함수 이름을 썼다. 빌드는 커널 파일을 각각 -c로 컴파일하는 fbld.sh(템플릿 FreeRTOSConfig.h, heap_4)로 했다.

어떤 veneer가 생겼는지도 봤다(kfast, 주소 · 이름).

출력에서 볼 것:

  • 커널 핫패스(약 6 KB, .fast_text 0x17b0바이트)가 FAST/RAM으로 옮겨 갔고 동작은 똑같다. PendSV 핸들러 주소도 0x0100_102d — 벡터 테이블은 절대 주소라 veneer 없이 바로 간다.
  • veneer는 양방향으로 생긴다. 플래시 쪽 0x17xx의 veneer는 앱 · timers.o가 커널을 부를 때, FAST 쪽 0x0100_17xx의 veneer는 커널이 플래시의 memcpy · board_now_us(런타임 통계 시계) · 훅을 부를 때 쓴다. 커널이 부르는 libc · 훅 · 시계 함수도 같이 옮기지 않으면 핫패스가 다시 플래시로 나간다.
  • 왕복 642 → 648 명령: 앱이 커널 API를 부르는 두 곳 × 두 태스크 등에서 veneer 명령이 붙었다. QEMU에서는 그것이 전부지만, 실칩에서는 반대로 커널 본체의 플래시 페치가 사라지는 이득이 이것보다 훨씬 크다(측정 불가 — 정직하게 표시). 실칩에서 이 실험을 하면 DWT CYCCNT로 왕복 사이클의 평균과 최대를 같이 본다. TCM의 이득은 최대값(지터)에서 드러난다.

Don 경험과 연결: SSD 펌웨어에서 "스케줄러 · 인터럽트 디스패처는 TCM"으로 두던 것과 같은 판단이다. 차이는 RTOS 커널이 남의 코드라는 것 — 그래서 소스 대신 링커 스크립트로 옮기는 기술이 중요하다.

4. RTOS 객체 배치 — 힙 · 스택 · TCB#

4.1 FreeRTOS heap_5 — 여러 뱅크에 걸친 힙#

F1에서 heap_1~5의 내부 구현을 봤다. 배치 관점에서 heap_5만 다시 본다. V11.3.2 portable/MemMang/heap_5.c 머리 주석의 규칙:

  • vPortDefineHeapRegions()는 어떤 pvPortMalloc()보다도 먼저(큐 · 세마포어 · 태스크 생성 포함) 불러야 한다.
  • HeapRegion_t { uint8_t *pucStartAddress; size_t xSizeInBytes; } 배열은 주소 오름차순이어야 하고 { NULL, 0 }으로 끝난다.
  • 각 영역의 시작은 portBYTE_ALIGNMENT(Cortex-M 포트는 8)로 올림 정렬된다.

예제 5 — 무엇을 확인하나: SRAM 32 KB(.bss) + PSRAM 1 MB(0 채우지 않는 .psram_noinit) 두 뱅크로 heap_5를 만들고, 할당이 어느 뱅크에서 나오는지 본다. 같이 태스크 스택과 TCB를 xTaskCreateStatic으로 FAST(TCM 역할)에 둔다.

출력에서 볼 것:

  • 두 뱅크가 한 힙이 됐다: 32768 + 1048576 = 1081344에서 영역 끝 표식 블록 등 16바이트가 빠진 1081328.
  • heap_5의 빈 블록 목록은 주소 순서이고 할당은 first-fit이다. 그래서 작은 할당은 낮은 주소인 SRAM에서 먼저 나오고, SRAM에 남은 연속 공간(약 3 KB)보다 큰 40 KB 요청만 PSRAM으로 넘어갔다. 그다음 512바이트는 다시 SRAM이다.
  • 이 성질은 우연히 "빠른 뱅크 먼저"처럼 보이지만 보장이 아니다. SRAM이 단편화되면 성능이 중요한 버퍼가 PSRAM으로 갈 수 있다. 위치가 중요한 객체는 heap에서 받지 말고 정적 배열로 두거나, 뱅크마다 따로 관리되는 할당자(F2의 메모리 풀, Zephyr는 뱅크마다 k_heap)를 쓴다.
  • 할당 1024바이트에 free가 1032 줄었다 — 블록 헤더 8바이트(F1).
  • 태스크 스택과 TCB는 FAST(0x0100_xxxx)에 있다. .fast_bss는 NOLOAD이고 zero table에도 없다 — FreeRTOS가 xTaskCreateStatic에서 스택을 tskSTACK_FILL_BYTE(0xa5)로 칠하고 TCB를 직접 초기화하므로 0 채우기가 필요 없다(high water 210/208워드가 칠한 값으로 계산된 것이다).

4.2 정적 할당이 배치의 기본 도구다#

동적 할당(xTaskCreate)은 스택 위치를 힙에 맡긴다. 위치를 정하고 싶으면 정적 할당이다. FreeRTOS는 xTaskCreateStatic, xQueueCreateStatic, xSemaphoreCreateBinaryStatic 등으로 버퍼를 넘기고, Zephyr는 K_THREAD_STACK_DEFINE · K_THREAD_DEFINE이 만드는 스택 배열에 섹션 속성을 붙일 수 있다(스택 영역의 정렬 · MPU 가드 요구는 F3 · F4). 인증 프로젝트의 "동적 할당 금지" 정책(F1)과도 맞는다.

4.3 커널이 제공하는 idle · timer 스택은 어디로 가나#

configKERNEL_PROVIDED_STATIC_MEMORY = 1(랩 기본값)이면 V11.3.2 tasks.c가 vApplicationGetIdleTaskMemory() · vApplicationGetTimerTaskMemory()를 직접 정의하고 그 안의 static 배열(uxIdleTaskStack, uxTimerTaskStack)을 쓴다. 이 배열들은 그냥 .bss다. §8의 H7 모양 빌드에서 nm으로 확인하면 앱 태스크 스택은 DTCM에 있는데 이 두 스택은 .bss가 놓인 AXI SRAM에 있다.

timer 태스크는 우선순위가 가장 높은(랩 설정 configMAX_PRIORITIES - 1) 태스크라 이 스택이 캐시 · 버스 경합을 겪으면 소프트웨어 타이머 콜백의 지터로 나타난다. 고치는 법: configKERNEL_PROVIDED_STATIC_MEMORY = 0으로 두고 두 함수를 앱이 정의해 DTCM 섹션의 배열을 넘긴다. 또는 링커 스크립트에서 *tasks.o(.bss.uxIdleTaskStack*)처럼 심볼 섹션 이름으로 끌어온다(-fdata-sections일 때만 섹션이 따로 생긴다).

4.4 ucHeap 하나짜리 heap_4를 원하는 뱅크에#

heap_1/2/4는 ucHeap[configTOTAL_HEAP_SIZE] 하나다. configAPPLICATION_ALLOCATED_HEAP = 1이면 앱이 정의하므로 __attribute__((section(".axi_noinit")))를 붙여 원하는 뱅크 · 0 채움 없는 섹션에 둔다. 방법과 부팅 시간 효과는 B5 §8.3에서 쟀다.

5. noinit RAM — 리셋을 넘어가는 기록#

5.1 직관 — "startup이 손대지 않는 서랍"#

.noinit은 특별한 하드웨어가 아니다. startup의 copy/zero 표에 오르지 않았고, ELF에 내용이 없어서(NOLOAD) 로더도 쓰지 않는 RAM 구간일 뿐이다. 그래서 그 RAM이 전원을 유지하는 동안의 리셋(소프트웨어 리셋, 워치독, 핀 리셋 대부분)은 넘어가고, 전원이 끊기면 사라진다. E8 §7은 이 구간에 리셋 원인을 남기는 규칙(magic + CRC, 읽고 지우기)을 다뤘다. 여기서는 일반 메커니즘과 크래시 로그 링 버퍼, 그리고 배치에서 생기는 함정 세 가지(주소가 움직인다, 부트로더가 덮는다, ECC가 읽기를 막는다)를 실험한다.

5.2 예제 6 — 크래시 로그 링 버퍼 (magic + 버전 + 크기 + CRC)#

무엇을 확인하나: 고정 크기 링 버퍼를 .noinit(고정 주소 NOINIT 영역)에 두고, 부팅마다 검증 → 항목 추가 → SYSRESETREQ를 반복한다. 세 번째 리셋 전에 봉인하지 않은 1비트 변경을 넣어 CRC가 잡는지 본다. 비교용 .bss 카운터도 둔다.

출력에서 볼 것:

  • 첫 부팅은 bad magic — QEMU를 새로 띄운 RAM은 0이다. 실칩의 POR 직후 RAM은 무작위라 magic이 우연히 맞을 수도 있지만, CRC까지 맞을 확률은 무시할 만하다. 이것이 magic만으로 부족한 이유다(E8 §7.2).
  • boots(noinit)는 1 → 2 → 3으로 늘고 g_bss_boots(.bss)는 매번 1이다. 같은 RAM 칩, 다른 섹션 — 차이는 표에 올랐느냐뿐이다.
  • 1비트를 봉인 없이 바꾸자 다음 부팅이 bad CRC로 거부하고 빈 로그로 다시 시작했다. 실제로 이런 변경은 "로그를 쓰는 도중 리셋"(torn write — E8 §1.5)이나 SRAM 비트 오류에서 온다.
  • version과 size 필드는 새 펌웨어가 구조체를 바꿨을 때 옛 기록을 잘못 해석하지 않게 한다(다음 예제의 부트로더 실험이 이 필드에 걸렸다).
  • 설계 메모: 이 예제는 로그 전체를 CRC 하나로 봉인해서 1비트 손상에 항목 전부를 버렸다. 실무에서는 항목마다 CRC를 두면 손상된 항목만 버리고 나머지를 살린다. 링 버퍼는 head가 계속 증가하는 시퀀스 번호를 겸하므로, 다음 부팅의 수집 태스크는 "마지막으로 플래시로 옮긴 seq" 이후 항목만 옮긴 뒤 로그를 비운다.

5.3 예제 7 — 주소가 움직이는 noinit vs 고정 주소 영역#

무엇을 확인하나: E8 §7.3이 지적한 문제 — 랩 링커 스크립트의 .noinit은 .bss 바로 뒤에 붙기 때문에 .bss가 커지면 주소가 움직인다. "새 펌웨어가 .bss를 1000바이트 늘렸다"를 -DPAD=1000으로 흉내 내고 g_log 주소를 비교한다.

출력에서 볼 것: 랩 스크립트에서는 g_log가 0x2000_01b0 → 0x2000_0598로 1000바이트(+정렬) 움직였다. 옛 펌웨어가 남긴 크래시 기록을 새 펌웨어가 읽으려 하면 엉뚱한 주소의 쓰레기를 보게 된다(magic이 막아 주긴 하지만 기록은 잃는다). MEMORY에 NOINIT 영역을 따로 잘라 둔 쪽은 0x203F_F004로 고정이다. 실무 규칙:

  • noinit 창은 자기 MEMORY 영역으로 만들고, 주소 · 크기를 펌웨어 버전 간 계약으로 문서화한다. 부트로더 링커 스크립트에도 같은 영역을 "쓰지 않음"으로 둔다.
  • 한 영역 안에서도 구조체 순서가 바뀌면 같은 문제가 생긴다. 영역 안에 "헤더 + 버전별 구조체"를 두거나, 섹션 이름을 .noinit.0_hdr · .noinit.1_log처럼 지어 KEEP(*(SORT(.noinit.*)))로 순서를 고정한다.
  • 이 예제에서 g_log가 0x203F_F000이 아니라 0x203F_F004인 것은 같은 영역의 g_step이 먼저 놓였기 때문이다 — 순서가 오브젝트 · 선언 순서에 의존한다는 증거다.

5.4 예제 8 — 부트로더의 스택이 noinit을 덮는다#

무엇을 확인하나: 실제 제품에는 앱 앞에 부트로더(ROM, MCUboot 등 — L1, L2)가 돈다. 부트로더는 자기 링커 스크립트로 빌드되고, 흔히 스택을 SRAM 맨 끝에서 시작한다. 앱이 noinit 창을 SRAM 꼭대기에 두면 둘이 겹친다. early_init() 훅(앱의 RAM 초기화 전에 도는 약한 함수)에서 MSP를 0x2040_0000으로 바꾸고 스택 4 KB를 쓰는 "가짜 부트로더"를 돌린다.

두 번째 메모리 지도 mem_f8_lo.ld는 NOINIT을 SRAM 바닥(0x2000_0000, 4 KB)으로 옮기고 RAM을 0x2000_1000부터 시작하게 한 것만 다르다.

출력에서 볼 것:

  • 꼭대기 배치(f8.ld): 매 부팅이 첫 부팅처럼 보인다. 거부 사유가 bad magic이 아니라 layout changed — 부트로더 스택의 바닥이 g_log의 앞 4바이트(magic)는 건드리지 않고 version/size 필드부터 덮었다. 손상이 부분적이라는 점이 중요하다. magic만 검사했다면 덮어쓴 쓰레기를 기록으로 믿었을 것이다.
  • 바닥 배치(f8_lo.ld): 부트로더가 같은 일을 해도 기록이 산다. 예제 6과 똑같은 출력이다.
  • 처음에는 버퍼를 2 KB로 했다가 겹치지 않아서 4080바이트로 늘렸다. 실제 겹침 여부는 부트로더의 최대 스택 깊이에 달렸고, 부트로더 버전이 바뀌면 달라진다. 그래서 "운 좋게 안 겹친다"가 아니라 두 링커 스크립트가 같은 noinit 창을 예약해야 한다. MCUboot처럼 부트로더 소스가 있으면 그쪽 링커 스크립트에서 RAM 길이를 줄이고, ROM 부트로더면 RM의 "부트 ROM이 쓰는 RAM" 표를 본다.

그림 3 — 예제 8의 두 배치. 왼쪽은 부트로더 스택(빨간 점선)이 noinit 창과 겹쳐 기록이 매번 깨지고, 오른쪽은 noinit 창을 SRAM 바닥으로 옮겨 살아남는다. 앱의 스택은 앱이 시작한 뒤에 쓰이므로 부트로더 스택과 겹쳐도 상관없다.

5.5 RTOS에서 noinit에 무엇을 남기나#

드론 FC라면 HardFault 핸들러(M1)가 스택 프레임의 PC · LR · CFSR · 현재 태스크 이름(pcTaskGetName(NULL) 또는 Zephyr k_thread_name_get(k_current_get()))을 링 버퍼 항목에 쓰고 봉인한 뒤 리셋한다. 다음 부팅에서 낮은 우선순위의 수집 태스크가 항목을 플래시 로그나 텔레메트리로 보내고 지운다. 리셋 직전 경로에서는 noinit 쓰기만 한다 — 플래시 쓰기, printf, 커널 API는 쓰지 않는다(E8 §7.2). Zephyr는 이 역할의 추상화로 retained_mem 드라이버와 subsys/retention(E8에서 언급)을 준다. 리셋 원인과의 결합은 E8, 덤프 내용의 해석은 M5다.

6. ECC RAM 초기화 — 읽기 전에 써라#

🔁 이 절은 Bare-Metal BM Q7(메모리 오류 · ECC)의 SRAM ECC 초기화 부분과 겹친다 (주인: 이 노트).

6.1 직관 — ECC 비트도 쓰레기로 시작한다#

ECC SRAM은 데이터 워드(granule — 32비트 또는 64비트)마다 검사 비트를 같이 저장한다. 쓸 때 하드웨어가 검사 비트를 계산해 넣고, 읽을 때 다시 계산해 비교한다. 전원을 켠 직후에는 데이터도 검사 비트도 쓰레기다. 그 상태에서 읽으면 대부분 "이중 비트 오류"로 판정되어 bus fault나 ECC 오류 인터럽트가 난다. 더 나쁜 것은 일부가 "단일 비트 오류"로 판정되어 하드웨어가 틀린 값으로 고쳐서 돌려준다는 점이다.

여기에 숨은 함정이 하나 더 있다. granule보다 작은 쓰기(STRB, STRH, 32비트 granule에 대한 정렬 안 된 쓰기, 64비트 granule에 대한 32비트 쓰기)는 하드웨어 안에서 읽기 → 병합 → 쓰기(read-modify-write) 가 된다. 새 검사 비트를 계산하려면 나머지 바이트가 필요하기 때문이다. 즉 "아직 안 읽었으니 괜찮다"가 아니다. 초기화 전의 strb도 읽기를 일으킨다. Zephyr의 H7 코드 주석이 "reads, unaligned or sub-sized accesses will trigger an ECC error"라고 쓴 이유다.

6.2 예제 9 — SECDED(39,32) 모델: 초기화 전 읽기와 STRB가 어떻게 되나#

QEMU는 ECC를 모델링하지 않으므로, VM 호스트에서 실제 SECDED 부호(32비트 데이터 + Hamming 6비트 + 전체 패리티 1비트 = 39비트)로 SRAM 한 워드를 흉내 낸다. 무엇을 확인하나: 전원 투입 쓰레기 100만 워드에 대해 (A) 32비트 읽기, (B) STRB(=RMW), (C) 워드 단위로 먼저 지운 뒤 STRB의 결과 분포.

출력에서 볼 것:

  • 무작위 39비트 중 올바른 부호어는 2^32/2^39 = 1/128 = 0.78%, 한 비트 거리(39개 위치)는 39/128 = 30.5%, 나머지 68.75%는 정정 불가다. 시뮬레이션이 이론값과 맞는다. 즉 초기화 안 한 ECC 워드를 읽으면 약 2/3는 fault, 약 1/3은 조용히 틀린 값이다.
  • STRB(B)도 같은 비율로 fault가 나고, fault가 안 난 경우에도 나머지 3바이트는 쓰레기로 "확정"된다(새 ECC가 쓰레기를 정상 데이터로 봉인한다).
  • 워드 단위로 먼저 한 번 쓰면(C) 이후 바이트 쓰기 · 읽기는 모두 정상이다. 이것이 "scrub(초기화) 먼저"의 이유다.
  • 실칩에서 정확히 어떤 비율이 나오는지는 칩의 부호(예: 64비트 granule이면 SECDED(72,64))와 전원 투입 SRAM 패턴에 달렸다. 결론(초기화 전 읽기 금지)은 같다.

그림 4 — 예제 9의 SECDED(39,32) 모델 결과(100만 워드, VM 호스트 C — 실칩 측정이 아니다). 초기화 전 읽기와 STRB는 3분의 2가 fault, 나머지 대부분은 조용히 틀린 데이터다. 워드 단위 scrub 뒤에는 100% 정상.

6.3 규칙 — ECC RAM startup 체크리스트#

  1. 스택보다 먼저. 초기 MSP가 ECC RAM을 가리키면 첫 push(C 함수 프롤로그, 예외 스태킹)가 RMW · 쓰기 없는 읽기를 일으킬 수 있다. scrub 루프는 스택을 쓰지 않는 어셈블리(레지스터만)로 쓰거나, 스택을 이미 초기화된(또는 ECC 없는) 다른 RAM에 두고 C로 쓴다. Zephyr H7의 soc_reset_hook()이 C인 것은 그 시점 MSP(z_main_stack)가 TCM이 아닌 zephyr,sram(nucleo_h743zi에서는 sram0 = AXI SRAM)에 있기 때문이다.
  2. granule 폭 이상, granule 정렬로 쓴다. 32비트 granule이면 STR/STM, 64비트면 STRD/STM(짝수 개). H7 ITCM 64비트, DTCM 32비트(AN5342 인용, §1.2).
  3. 캐시를 켜기 전에. 캐시 가능한 영역을 write-allocate 캐시를 켠 채 부분적으로 쓰면 캐시가 라인 전체를 먼저 읽어 온다(line fill). 그 읽기가 ECC 오류를 낸다. scrub은 D-cache를 켜기 전에 하거나, 캐시 라인 단위(32 B)로 정렬해 통째로 쓴다(B8 §2.3 순서와 함께).
  4. .data 복사 · .bss 0 채우기보다 먼저. memcpy의 꼬리 바이트 처리(strb)가 RMW를 만든다. scrub이 RAM 전체를 0으로 만들었다면 .bss zero table은 중복이므로 빼도 된다(부팅 시간 절약).
  5. noinit 창은 POR일 때만 scrub한다(§6.5).
  6. DMA로 해도 된다. DMA 엔진은 CPU보다 넓은 버스 쓰기를 하므로 빠를 수 있고, 그동안 CPU는 다른 초기화를 한다. 단 DMA 디스크립터 · 소스 버퍼가 아직 초기화 안 된 ECC RAM에 있으면 안 된다. QEMU AN385에는 DMA 컨트롤러가 없어 이 노트에서는 시험하지 못했다.

6.4 예제 10 — 어셈블리 Reset_Handler: 스택 전에 scrub, warm reset이면 noinit 건너뛰기#

무엇을 확인하나: 위 규칙 1 · 2 · 4 · 5를 지키는 startup. 레지스터 8개를 0으로 두고 stmia로 32바이트씩 RAM 전체를 쓴 뒤에야 C로 넘어간다. QEMU AN385에는 리셋 원인 레지스터가 없으므로(E8 §7.1) blockram의 한 워드(FAKE_RSR)를 STM32의 RCC_RSR 역할로 쓴다 — 앱이 소프트웨어 리셋 전에 표시를 남긴다(흉내임을 밝혀 둔다).

링커 스크립트는 메모리 지도와 섹션 사이에 심볼 네 개만 끼웠다(f8_ecc.ld).

출력에서 볼 것:

  • 4092 KB를 stmia 8레지스터로 지우는 데 12.57 ms(QEMU icount). 계산: 4092 × 1024 / 32 = 130944회 × 루프 명령 3개 × 32 ns = 12.57 ms. 실칩 Cortex-M3라면 STM 8워드 = 1 + 8 사이클(TRM)이라 루프 1회 약 12사이클 → 25 MHz에서 약 63 ms다. 큰 SRAM에서 부팅 시간의 큰 몫이 scrub이다.
  • 첫 부팅(RSR=0, "POR")은 NOINIT 4 KB도 지워서 308 tick(12.3 µs) 더 걸렸다. 리셋 뒤(RSR=0x5F7)에는 NOINIT을 건너뛰었고 g_warm이 0 → 1 → 2로 살아남았다.
  • 처음 버전은 g_scrub_ticks를 일반 .bss에 뒀다가 0이 찍혔다. 어셈블리가 값을 쓴 뒤에 CMSIS zero table이 .bss를 다시 지웠기 때문이다. "startup의 어느 단계가 어느 영역을 쓰는가"를 순서대로 그려 보지 않으면 이런 일이 생긴다 — 그래서 측정값을 noinit에 뒀다.

6.5 noinit과 ECC의 충돌 — POR이면 지우고, warm이면 남긴다#

§5의 크래시 로그는 "아무도 쓰지 않는 RAM"이어야 하고, §6.3의 규칙은 "읽기 전에 써라"다. ECC RAM에서는 둘이 충돌한다. POR 직후 noinit 창을 검증하려고 읽는 순간 ECC fault가 난다. 해법은 예제 10의 분기다.

  • 리셋 원인 레지스터를 먼저 읽는다(레지스터라 ECC와 무관). POR · BOR이면 noinit 창도 scrub한다(어차피 내용은 쓰레기다). 소프트웨어 · 워치독 · 핀 리셋이면 noinit 창은 건너뛴다 — 그 RAM은 전원이 유지됐으므로 ECC 비트도 유효하다.
  • 리셋 원인을 지우는 것은 그 뒤다(E8 §7.1의 "읽고, 복사하고, 지운다").
  • 일부 칩은 POR 때 하드웨어가 SRAM을 지우거나 ECC를 초기화해 준다. 이 노트에서 칩별로 확인하지 못했으므로, 쓰는 칩의 RM에서 "SRAM erase on reset" · "ECC initialization" 항목을 찾아본다.

6.6 예제 11 — 어떻게 지우나: 방식별 시간#

무엇을 확인하나: 같은 영역을 지우는 다섯 가지 방법(strb 1바이트, newlib-nano memset, str 4바이트, strd 8바이트, stm 32바이트)의 시간을 1 ~ 256 KB에서 잰다. scrub 루틴은 스택을 쓰지 않는 leaf 함수다(측정 하네스용 stm8만 r4~r9를 보존하려고 push한다).

같은 빌드를 두 번 돌리면 ±1 tick이 다르다(40 ns 카운터와 32 ns 명령 시계의 위상 차이). 모든 방식이 크기에 정확히 비례한다. 256 KB 값을 실칩 모델과 같이 그렸다. 모델은 Cortex-M3 TRM의 명령 사이클 표를 근사한 것이다(0 wait SRAM, STR 2 · STRD 3 · STM 1+N · CMP 1 · 분기 taken 2 사이클 가정, 루프 1회 = strb 5, str 5, strd 6, stm8 12 사이클). 모델이지 측정이 아니다.

그림 5 — 256 KB를 0으로 채우는 시간(로그 눈금). 파랑 = QEMU icount 실측(명령 수 × 32 ns), 주황 = Cortex-M3 TRM 사이클 모델 @ 25 MHz. QEMU는 명령 하나를 32 ns로 세므로 32바이트를 한 명령에 쓰는 stm8이 실제보다 더 좋아 보인다(실측 32배 차이 vs 모델 13배 차이).

출력에서 볼 것:

  • 순서는 두 기준에서 같다: stm8 < strd < str < strb. ECC RAM에서는 strb가 느릴 뿐 아니라 틀렸다(RMW — 예제 9). granule 폭 이상의 정렬된 쓰기만 scrub으로 쓸 수 있다.
  • newlib-nano memset이 str 루프보다 2.4배 빠르다. 라이브러리 memset은 정렬된 몸통을 워드 · 다중 워드로 쓴다. 하지만 시작 · 끝이 정렬되지 않으면 바이트 쓰기를 한다 — scrub 대상이 정렬돼 있다는 보장이 없으면 memset을 쓰지 않는다. 또 memset은 스택을 쓰는 C 함수다.
  • QEMU icount 기준 stm8은 256 KB에 0.79 ms, 모델 기준 3.9 ms(25 MHz). 실칩에서는 클럭이 높고(H7 480 MHz) 버스가 넓지만 SRAM도 크다. 결론: scrub 시간은 RAM 크기에 비례하고, 수 MB면 수~수십 ms다. 부팅 시간 예산(B5 §8)에 넣는다.

7.2 예제 12 — AN547에서 DT 섹션 vs 코드 재배치 vs __noinit vs __ramfunc#

무엇을 확인하나: 같은 ISRAM 영역에 (a) DT 영역 섹션 속성으로 놓은 변수 두 개(하나는 초기값 있음), (b) zephyr_code_relocate로 옮긴 파일의 .data · .bss를 두고, hot.c의 코드는 SRAM 영역으로, __ramfunc 함수 하나를 둔다. 첫 부팅 뒤 sys_reboot(SYS_REBOOT_WARM)으로 한 번 더 부팅해서 무엇이 남는지 본다.

출력에서 볼 것:

  • g_isram_init=0x0 — 소스에 = 0x1234라고 썼는데 0이다. DT 영역 섹션은 NOLOAD라 초기값이 ELF에 실리지 않고, 복사하는 코드도 없다. 빌드는 경고 없이 성공했다. QEMU의 RAM이 0이라 0이 보였을 뿐 실칩에서는 쓰레기다. DT 영역 섹션에는 초기값 없는 버퍼(DMA 버퍼, 프레임 버퍼, 공유 메모리)만 둔다.
  • g_isram_cnt는 1 → 2 — DT 영역 섹션은 사실상 noinit이다. 같은 성질의 __noinit 변수(DTCM 0x3000_10a8)도 남았다. 반면 g_bss_cnt는 매번 1.
  • zephyr_code_relocate로 옮긴 hot.c: 코드는 SRAM 0x1100_0001, hot_data는 ISRAM 0x3100_0000에 42로 복사됐고, hot_bss는 매 부팅 0으로 지워져 두 번 모두 1이다. 같은 ISRAM이라도 재배치 경로는 초기화가 있고 DT 섹션 경로는 없다. ISRAM 섹션 범위(0x3100_0008~0x3100_0010)가 재배치된 8바이트 뒤에 붙은 것도 보인다.
  • __ramfunc는 zephyr,sram(= DTCM 0x3000_0001)으로 갔다. main은 ITCM(0x1000_025d — 이 보드의 "플래시")에서 돈다.

생성된 것을 열어 본다. 재배치는 마법이 아니라 링커 조각과 C 함수 두 개다.

출력에서 볼 것:

  • 생성기는 파일 단위 지시를 입력 섹션 단위(*hot.c.obj(".data.hot_data"))로 풀어 쓴다(-ffunction-sections · -fdata-sections 덕분). KEEP이 붙으므로 안 쓰는 함수도 --gc-sections로 지워지지 않는다(그래서 NOKEEP 옵션이 있다).
  • 복사 · 0 채우기는 arch_early_memcpy · arch_early_memset 호출이고, arch/common/xip.c의 arch_data_copy()와 arch/common/init.c의 arch_bss_zero()가 CONFIG_CODE_DATA_RELOCATION일 때 이 두 함수를 부른다.
  • main(0x1000_028a)에서 hot_step(0x1100_0000)은 16 MB 경계 바로 안이라 bl 직접, __ramfunc 함수는 blx r1 — long_call이 붙은 결과다(§3.2).

7.3 예제 13 — chosen이 없는 보드에서 __dtcm_bss_section을 쓰면#

무엇을 확인하나: section_tags.h의 TCM 매크로는 Cortex-M 링커 스크립트(include/zephyr/arch/arm/cortex_m/scripts/linker.ld)에서 DT_CHOSEN(zephyr_itcm) · DT_CHOSEN(zephyr_dtcm)이 okay일 때만 출력 섹션이 정의된다. AN547 DTS는 ITCM · DTCM 노드가 있지만 chosen으로는 zephyr,flash = &itcm, zephyr,sram = &dtcm만 지정하고 zephyr,itcm · zephyr,dtcm은 지정하지 않는다. 이 보드에서 매크로를 쓰면 어떻게 될까.

출력에서 볼 것:

  • 링커는 정의되지 않은 섹션을 orphan으로 처리해 "적당한 곳"에 붙였다 — 경고만 하고 빌드는 성공한다(경고 4줄 중 같은 내용 2줄은 생략). .dtcm_bss는 DTCM이 아니라 코드 영역(0x1000_3c38, ITCM = 이 보드의 플래시) 끝에 붙었다.
  • 첫 쓰기에서 MPU FAULT — Zephyr가 코드 영역을 MPU로 읽기 전용으로 막아 두었기 때문이다(F4). 쓰기 금지 영역이 아니었다면 더 나쁘다: 조용히 엉뚱한 곳에 쓰고, 0 채우기도 안 된 채로 동작한다.
  • 교훈: 섹션 태그 매크로는 "보드가 그 섹션을 정의했다"는 약속 위에서만 동작한다. 새 보드로 옮길 때 빌드 로그에서 orphan section 경고를 에러로 다룬다(GNU ld --orphan-handling=error). 고치는 법은 보드 overlay에 chosen { zephyr,dtcm = &dtcm; };를 넣는 것이지만, AN547처럼 DTCM이 이미 zephyr,sram이면 그냥 일반 .bss가 DTCM이다.

8. 메모리 예산 — 영역별로 얼마나 찼나#

8.1 예제 14 — 드론 FC 모양의 배치를 H7 지도에 링크하고 예산을 낸다#

QEMU에는 H7 보드가 없으므로 이 예제는 빌드 전용이다. 무엇을 확인하나: 드론 FC가 실제로 가질 법한 객체(커널 핫패스, rate loop, PID 계수, 태스크 스택 5개, IMU · UART DMA 버퍼, 힙 두 뱅크, 블랙박스 스테이징, backup SRAM 크래시 기록)를 B8과 같은 H7 지도(ITCM · DTCM · AXI · D2 · backup)에 배치하고, 링크 결과에서 영역별 사용량을 계산한다. Cortex-M7 + FreeRTOS ARM_CM7/r0p1 포트 + heap_5로 빌드했다.

링커 스크립트 h7.ld의 메모리 지도와 핵심 줄(전체는 copy 3줄 · zero 3줄 표를 포함해 40줄):

첫 링크는 undefined reference to __heap_end로 실패했다 — 랩 board.c의 _sbrk가 libc malloc용 심볼을 요구한다. 이 펌웨어는 libc malloc을 쓰지 않으므로 두 심볼을 같은 값(크기 0)으로 정의해 _sbrk가 항상 실패하게 했다. "libc 힙이 어디 있나"도 배치 결정이다(F7).

.bss(AXI) 4320바이트의 내용을 nm --size-sort로 보면 큰 것이 커널의 idle 스택 1 KB와 timer 스택 2 KB다(§4.3). 이것을 "스택"으로 분류해 영역별 예산을 Python으로 그렸다(분류: 코드 = .vectors + .text + 표; load 이미지 = 복사 원본; data + bss; 스택 = .dtcm_stacks + .stack + 커널 스택 3 KB; DMA = .d2_bss; noinit 버퍼).

예산에서 읽는 것:

  • DTCM 13.7% 중 스택이 17 KB다. 스택 크기는 F3의 high water mark 실측으로 정하고, 여유가 크면 제어 상태 테이블 · 필터 버퍼를 DTCM으로 더 옮긴다.
  • ITCM 8.8%: FOC나 IMU 처리 ISR, memcpy(커널이 부르는 것 — §3.4)를 옮길 공간이 있다.
  • AXI 57%의 대부분은 noinit 버퍼라 부팅 시간(0 채우기)에는 영향이 없다. 단 ECC scrub 대상이라면 전체 512 KB가 부팅 시간에 들어간다(§6.6).
  • D2 27%: DMA 버퍼 14 KB + 힙 2뱅크 64 KB. MPU로 D2를 non-cacheable로 두면 힙의 이 뱅크도 non-cacheable이 된다 — 큰 CPU 작업 버퍼가 여기서 할당되면 느려진다. heap_5 first-fit이 AXI(낮은 주소)부터 쓰므로 평소에는 괜찮지만 보장은 아니다(§4.1).
  • 이런 표를 CI가 매 빌드마다 만들고 영역별 상한을 넘으면 실패시키면 "어느 날 갑자기 DTCM 오버플로"가 사라진다. Zephyr는 빌드 끝에 영역별 사용률을 출력한다(예제 12의 FLASH: · RAM: · SRAM: · ISRAM: 줄 — DT 영역도 자동으로 들어간다).

9. RTOS 커널 안에서는 무슨 일이 일어나나#

9.1 FreeRTOS — 커널은 배치를 모른다#

FreeRTOS 커널에는 "메모리 영역"이라는 개념이 없다. 배치는 전부 커널 밖에서 정해진다.

  • 부팅: 벤더 startup(또는 이 노트의 CMSIS __cmsis_start())이 main 전에 표를 돈다. 커널 코드는 하나도 돌지 않았다(B5 §10.1).
  • 힙: heap_5의 vPortDefineHeapRegions()(portable/MemMang/heap_5.c)가 앱이 준 영역 표로 빈 블록 목록을 만든다. 이후 pvPortMalloc()은 주소 순 first-fit이다(§4.1, F1).
  • 스택 · TCB: xTaskCreateStatic()(tasks.c)은 받은 포인터를 그대로 쓴다. 위치는 배열을 정의한 섹션이 정한다. prvInitialiseNewTask()가 스택을 tskSTACK_FILL_BYTE(0xa5)로 칠하고 TCB를 memset으로 0으로 만든다 — 그래서 스택 · TCB 섹션은 0 채우기가 필요 없다.
  • idle · timer 스택: configKERNEL_PROVIDED_STATIC_MEMORY이면 tasks.c 안의 static 배열(§4.3).
  • 포트: port.c의 xPortPendSVHandler · vPortSVCHandler는 벡터 테이블의 절대 주소로 불리므로 어느 영역에 있어도 veneer가 없다(§3.4).

12. 면접에서 이렇게 말한다#

Q. "On a Cortex-M7 like the STM32H7, what do you put in ITCM, DTCM, and regular SRAM, and why?"

A. ITCM에는 지터가 사양인 코드(고속 ISR, rate loop, 커널 핫패스), DTCM에는 스택 · TCB · 제어 상태, DMA 버퍼는 DMA가 닿는 SRAM(H7은 DMA1/2가 TCM에 못 닿음)에 MPU non-cacheable로, 큰 버퍼와 힙은 AXI SRAM. 기준은 지연 · 캐시 · 버스 마스터 · 유지 · ECC 다섯 가지이고, 결과는 map 파일로 증명한다.

I sort every RAM by five properties: latency, cacheability, which bus masters can reach it, retention, and ECC. ITCM gets the code whose worst case is the spec — the IMU or current-loop ISR, the rate controller, and often the kernel's context-switch path. DTCM gets task stacks, the ISR stack and control state, because there are no cache misses there. DMA buffers go to a DMA-reachable SRAM bank marked non-cacheable, since on the H7 the general-purpose DMAs can't reach the TCMs at all. Big buffers and the heap live in AXI SRAM with the cache on. Then I prove the placement from the map file, not from intentions.

꼬리 질문: "Why not put everything in TCM?" → 크기(H7 ITCM 64 KB), DMA 접근 불가, 그리고 TCM 함수를 플래시에서 부르면 veneer가 생긴다.

Q. "You moved a function to RAM and the linker created something called a veneer. What is it and does it matter?"

A. Thumb-2 BL은 ±16 MB만 가므로 링커가 플래시에 ldr.w pc, [pc] + 주소 한 워드짜리 점프대를 만든다. QEMU icount로 재면 호출당 명령 1개가 늘었다. 실칩에서는 그 veneer가 플래시에 있다는 게 문제다. long_call을 쓰면 컴파일러가 주소를 레지스터로 로드해 blx하고, 루프 밖으로 끌어낼 수 있다. Zephyr의 GCC __ramfunc가 long_call을 붙이는 이유다.

A BL instruction only reaches plus or minus 16 megabytes, and flash and SRAM are hundreds of megabytes apart, so the linker inserts a small trampoline — a load-PC-from-literal — and points the call at it. I measured it as exactly one extra instruction per call, but the real cost on silicon is that the veneer itself lives in flash, so a 'RAM-resident' ISR path still fetches from flash. Using the long_call attribute makes the compiler load the address into a register and BLX, which it can hoist out of loops; Zephyr's GCC ramfunc macro does exactly that.

Q. "How do you keep a crash log across a reset?"

A. startup이 건드리지 않는 noinit 창(고정 주소 MEMORY 영역 또는 backup SRAM)에 magic · 버전 · 크기 · CRC가 있는 링 버퍼를 둔다. 다음 부팅이 검증하고, 플래시로 옮기고, 지운다. 함정 셋: .bss 뒤에 붙이면 주소가 움직이고, 부트로더 스택이 덮을 수 있고, ECC RAM에서는 POR 때 그 창을 읽기 전에 scrub해야 한다.

I reserve a fixed-address no-init window in the linker script — same address in every firmware version, and reserved in the bootloader's linker script too — and keep a ring buffer there with a magic, a version and size field, and a CRC per entry. The fault handler only writes and seals an entry, then resets; a low-priority task on the next boot validates, ships it to flash or telemetry, and clears it. I've seen two ways this silently fails: the address moves when .bss grows, and a bootloader's stack overwrites the top of RAM. On ECC SRAM you also have to read the reset cause first and scrub the window on power-on, because reading it uninitialized faults.

Q. "Why must ECC SRAM be initialized before use, and how do you do it?"

A. 전원 투입 직후 ECC 비트도 쓰레기라 읽으면 약 2/3가 정정 불가 fault, 1/3은 틀린 값으로 "정정"된다(SECDED 모델로 계산). 바이트 쓰기도 RMW라 읽기를 일으킨다. 그래서 스택을 쓰기 전에 어셈블리로 granule 폭 이상의 정렬된 쓰기(stm, strd)로 전체를 채우고, 캐시는 그 뒤에 켠다. 시간은 크기에 비례해 수 MB면 수십 ms라 부팅 예산에 넣는다.

After power-up both the data and the check bits are random, so a read is usually an uncorrectable error and sometimes a silent mis-correction. Sub-word stores are read-modify-writes inside the memory controller, so even a byte store or a C function prologue can trip it. So the very first thing Reset_Handler does, before touching the stack, is fill the ECC regions with aligned stores at least as wide as the ECC granule — STM or STRD — with the D-cache still off. On a warm reset I skip the retained window. It scales linearly with size, so I budget it in boot time.

Q. "How would you split a FreeRTOS heap across two RAM banks?"

A. heap_5의 vPortDefineHeapRegions()에 주소 오름차순 영역 표를 주고, 어떤 할당보다도 먼저 부른다. 할당은 주소 순 first-fit이라 낮은 뱅크부터 쓴다. 하지만 위치 보장은 아니므로 위치가 중요한 객체는 정적 할당이나 뱅크별 풀로 둔다.

heap_5 takes an array of regions in ascending address order, terminated by a NULL entry, and you call vPortDefineHeapRegions before anything allocates — including queues the kernel creates. It's first-fit over an address-ordered free list, so allocations naturally fill the lower bank first; in my test a 40 KB request spilled to PSRAM only when the on-chip bank couldn't fit it. That's not a placement guarantee, though, so anything that must be in fast or DMA-capable memory is statically allocated or comes from a per-bank pool.

Q. "In Zephyr, how do you place a variable or a whole file in a specific memory region?"

A. 변수는 DT의 zephyr,memory-region 노드 + LINKER_DT_NODE_REGION_NAME() 섹션 속성 — 단 NOLOAD라 초기화가 없다. 파일은 zephyr_code_relocate(FILES … LOCATION X_TEXT/_DATA/_BSS) — 생성된 코드가 복사 · 0 채우기를 한다. TCM 매크로는 보드에 chosen zephyr,itcm / zephyr,dtcm이 있을 때만 의미가 있다.

For a buffer, I describe the RAM in devicetree as a zephyr,memory-region node and put the variable in that section with LINKER_DT_NODE_REGION_NAME — but those sections are NOLOAD, so an initializer is silently dropped; I've seen it read zero in QEMU. For a whole file, zephyr_code_relocate in CMake generates linker fragments plus copy and zero routines that the boot path calls. And the ITCM/DTCM section-tag macros only work if the board sets the chosen nodes — otherwise you get an orphan-section warning and the data lands in flash.

Q. "Your board works under the debugger but fails after a power cycle. Where do you look?"

A. 디버거 load는 .data를 VMA에 직접 써 주고 RAM을 이미 쓰인 상태로 둔다. 그래서 (1) copy table 누락, (2) .bss/noinit 0 가정, (3) ECC scrub 누락, (4) 클럭 · 플래시 wait state 순서(B5)를 본다. map에서 LMA ≠ VMA인 섹션이 모두 표에 있는지 확인한다.

A debugger load writes initialized data straight to its run address and leaves RAM in a used state, which hides startup bugs. I check that every section with a load address different from its run address is in the copy table, that nothing assumes zeroed no-init memory, and on ECC parts that the scrub runs before the stack is used. Then I test from a true power-on, not a debugger reset.

15. 요약 & 체크리스트#

고성능 MCU의 RAM은 여러 덩어리이고, 덩어리마다 지연 · 캐시 · 버스 마스터 · 유지 · ECC가 다르다. 배치는 이 다섯 성격으로 정하고, section attribute · 파일 패턴 · copy/zero 표로 링커에게 알리고, map · nm · objdump로 증명한다. 코드를 RAM으로 옮기면 veneer가 생기며 호출 경로 전체를 같이 옮기거나 long_call을 써야 한다(호출당 1명령 실측). noinit 창은 고정 주소 영역으로 만들고 부트로더와 공유 계약을 맺으며, magic · 버전 · 크기 · CRC로 검증한다. ECC RAM은 스택보다 먼저, granule 폭 이상의 정렬 쓰기로, 캐시를 켜기 전에 scrub하고, warm reset이면 noinit 창을 건너뛴다. FreeRTOS는 배치를 모르므로 heap_5 영역 표와 정적 할당으로 앱이 정하고, Zephyr는 DT 영역(NOLOAD — 초기화 없음), 섹션 태그(chosen 필요), zephyr_code_relocate(초기화 생성)로 정한다.
