0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 컨트롤러 펌웨어를 처음 받았을 때를 떠올려 보자. main()은 깔끔한 C 코드였지만, 그 앞에는 누군가 써 둔 어셈블리 reset.S와 링커 스크립트 fw.ld가 있었다. 평소에는 아무도 안 본다. 그런데 새 실리콘이 오거나, SRAM 뱅크가 바뀌거나, 부트 ROM이 펌웨어를 올리는 주소가 바뀌면 그 두 파일을 아는 사람만 일을 진행할 수 있었다.

MCU + RTOS 세계도 똑같다. main() 첫 줄이 실행되려면 다음이 끝나 있어야 한다.

  • 스택 포인터가 RAM 어딘가를 가리킨다 (C 함수 호출이 가능해진다)
  • 초기값 있는 전역 변수(int g_gain = 42;)가 RAM에 그 값을 가지고 있다 (.data)
  • 초기값 없는 전역 변수(int g_count;)가 0이다 (.bss — C 표준이 0을 약속한다)
  • 클럭이 원하는 속도로 돌고, flash wait state가 그 속도에 맞다 (SystemInit)
  • FPU를 쓸 거면 켜져 있다 (CPACR)
  • C++ 전역 객체의 생성자가 돌았다 (__libc_init_array)

이 중 하드웨어가 해 주는 것은 스택 포인터 하나뿐이다. 나머지는 전부 Reset_Handler라는 평범한 함수가 하고, 그 함수가 어디에 무엇을 복사할지는 링커 스크립트가 정한 심볼로 안다. 이 노트는 그 전 과정을 랩 보드(QEMU mps2-an385)에서 한 단계씩 보여 주고, 일부러 망가뜨려 증상을 보고, 시간을 잰다.

1. 리셋 순간 — 하드웨어는 두 워드만 읽는다#

🔁 이 절은 Bare-Metal BM F4와 겹친다 (주인: 이 노트).

1.1 직관#

Cortex-M의 리셋은 놀라울 만큼 단순하다. 코어는 메모리 맨 앞(정확히는 VTOR가 가리키는 곳, 리셋 때 보통 0x0)에서 워드 두 개를 읽는다.

  • 0번 워드 → MSP(Main Stack Pointer)에 넣는다
  • 1번 워드 → PC에 넣는다 (그리고 bit 0을 Thumb 상태 비트로 쓴다)

그리고 그 주소부터 명령을 실행한다. 끝이다. 클럭 설정도, RAM 초기화도, 캐시도 없다. 이것이 Cortex-M을 "C로 리셋 핸들러를 쓸 수 있는 코어"로 만든다 — 첫 명령이 실행될 때 이미 스택이 있으니 컴파일러가 만든 push {r3, lr}가 바로 동작한다. Cortex-A/R이나 RISC-V는 그렇지 않다(§1.5).

벡터 테이블 전체의 구조(예외 번호표, VTOR로 옮기기)는 B2에서 다뤘다. 여기서는 리셋 한 순간만 본다.

1.3 예제 1 — gdb로 리셋 직후 레지스터 보기#

무엇을 확인하나: QEMU를 -S(첫 명령 전에 멈춤)로 띄우고 gdb를 붙여 명령이 하나도 실행되지 않은 상태의 MSP · PC · xPSR · CONTROL · LR을 읽는다. 대상은 §2.4의 ex1 앱(랩 startup.c + mps2_m3.ld 그대로)이다. 여러 작성자가 같은 VM을 쓰므로 gdb 포트는 1234 대신 고유 번호를 쓴다.

같은 상태에서 LR도 읽었다(p/x $lr 한 줄짜리 스크립트).

출력에서 볼 것:

  • 메모리 0x0의 두 워드 0x20400000 0x000000d5가 그대로 MSP = 0x20400000, PC = 0xd4가 됐다. 0xd5의 bit 0(=1)은 PC로 가지 않고 Thumb 비트가 됐다 — xPSR 0x41000000의 bit 24(T)가 1이다(bit 30은 Z 플래그, QEMU 초기값).
  • CONTROL = 0(privileged, MSP 사용), PRIMASK = 0, LR = 0xFFFFFFFF. 표 1.2와 정확히 같다.
  • 첫 stepi 한 번으로 SP가 0x20400000 → 0x203ffff8이 됐다. Reset_Handler의 첫 명령 push {r3, lr}가 리셋 직후에 이미 동작하는 스택에 8바이트를 쌓은 것이다. 이게 "Cortex-M은 startup을 C로 쓸 수 있다"의 증거다.
  • main에 도착했을 때 g_gain = 42. 그 사이에 Reset_Handler가 .data를 복사했다(§2, §4).

Don 경험과 연결: SSD 컨트롤러의 Cortex-R은 리셋 때 SP를 읽어 주지 않는다. 그래서 reset.S의 첫 줄이 모드별 스택 설정(msr cpsr_c, ...; ldr sp, =...)이었다. Cortex-M에서는 그 줄이 벡터 테이블 0번 워드 하나로 대체된다.

1.4 예제 2 — 리셋 벡터의 Thumb 비트를 지우면#

무엇을 확인하나: Cortex-M은 Thumb 명령만 실행한다. 벡터 엔트리의 bit 0이 0이면 "ARM 상태로 가라"는 뜻이 되는데, M 프로파일에는 ARM 상태가 없다. 실제 플래시 이미지(.bin)를 만들어 4번 바이트의 bit 0을 지우고, ELF 없이 원시 이미지만 QEMU의 0x0에 올려서 부팅했다(실제 플래시 프로그래머가 하는 일과 같다). startup은 §4.4의 어셈블리 버전이다.

아무 출력 없이 3초 뒤 timeout으로 죽었다. gdb로 들어가 봤다(같은 이미지를 -device loader로 올리고 -gdb tcp::3358 -S).

출력에서 볼 것:

  • 리셋 직후 xPSR = 0x40000000 — T 비트(bit 24)가 0이다. PC는 0x40으로 맞는데도 상태가 틀렸다.
  • stepi 한 번에 바로 HardFault_Handler. CFSR = 0x20000 = UFSR의 INVSTATE(bit 17), HFSR = 0x40000000 = FORCED(UsageFault가 꺼져 있어서 HardFault로 승격). 첫 명령조차 실행되지 못했다.
  • 그런데 왜 아무것도 안 찍혔나? HardFault 핸들러가 board_hardfault → board_printf_raw로 UART에 쓰려 했지만, UART를 켜는 board_init()은 아직 실행된 적이 없다. TX가 꺼진 UART의 "버퍼 가득" 비트를 영원히 기다린다. 부팅 초기 fault는 "출력이 없다"로 나타나는 경우가 많다 — 그래서 bring-up 때는 디버거(또는 LED 하나)가 먼저다.

함정: 어셈블리로 벡터 테이블을 쓸 때 .thumb_func 없이 라벨만 쓰면 bit 0이 빠진다. GNU as는 .thumb_func가 붙은 심볼을 .word로 쓸 때만 링커가 bit 0을 채운다(실험: .word Reset_Handler - 1도 링커가 | 1을 해서 0x3f가 됐다 — bit 0을 빼려면 이미지를 직접 고쳐야 했다). C 배열로 쓰면 컴파일러가 함수 포인터에 bit 0을 넣어 주므로 이 실수는 거의 어셈블리 startup에서만 생긴다.

무엇을 확인하나: RISC-V rv32를 QEMU virt 머신(-bios none)에서 맨손으로 부팅한다. Zephyr SDK의 riscv64-zephyr-elf-gcc로 빌드했다. startup이 직접 sp와 mtvec를 설정해야 한다는 점, 그리고 그 전에 무엇이 실행되는지를 본다.

리셋 순간 무엇이 실행되는지는 QEMU의 명령 로그(-d in_asm)로 봤다(Ubuntu gdb에는 RISC-V 지원이 없어서).

출력에서 볼 것:

  • 리셋 PC는 0x1000(QEMU virt의 작은 리셋 ROM)이다. 여섯 명령으로 hart ID를 a0에 넣고 0x80000000으로 점프한다. sp는 아무도 설정하지 않았다 — 0x80000000의 첫 명령이 auipc sp · mv sp(= la sp, _estack)다.
  • main에서 본 sp = 0x800ffff0는 _estack(0x80100000)에서 main의 프레임만큼 내려간 값이다. mtvec = 0x80000044 = trap_entry. 둘 다 startup이 직접 넣었다.
  • RISC-V에는 "벡터 테이블 0번 워드 = 스택"이라는 약속이 없다. 그래서 RISC-V startup은 반드시 어셈블리로 시작한다(C 함수는 첫 줄부터 sp를 쓴다). 이 예제는 RAM에서 바로 실행되는 이미지라 .data 복사가 없고, -mrelax가 쓰는 gp(global pointer)도 설정하지 않았다(__global_pointer$를 정의하지 않았으므로 링커가 gp 상대 주소로 바꾸지 않는다). 실제 RISC-V MCU startup은 la gp, __global_pointer$를 sp보다 먼저 넣는다. RISC-V 전반은 B10.

2.1 직관 — "메모리 지도 + 짐 싸는 규칙"#

ELF의 섹션 · 세그먼트 · 재배치는 EL B3에서 봤다. Linux에서는 링커 기본 스크립트와 커널의 ELF 로더가 알아서 주소를 정하지만, MCU에는 로더가 없다. 링커 스크립트가 로더의 일까지 미리 정해 둔다. 두 부분으로 나뉜다.

  • SECTIONS — 오브젝트 파일의 입력 섹션(.text.main, .data.g_gain …)을 어떤 출력 섹션으로 모아서 어느 메모리에 둘지 (짐 싸는 규칙)

2.3 VMA와 LMA — .data만 주소가 두 개인 이유#

  • VMA(Virtual Memory Address): 프로그램이 실행될 때 그 섹션이 있는 주소. 코드가 g_gain을 읽을 때 쓰는 주소다.
  • LMA(Load Memory Address): 이미지가 저장 · 적재되는 주소. 플래시에 구워지는 위치다.

MCU에는 VM이 없으니 "Virtual"은 역사적 이름일 뿐이다. 대부분의 섹션은 VMA = LMA다. .text는 플래시에서 그대로 실행되고(XIP, §9), .bss는 적재할 내용이 없다. .data만 다르다: 초기값 42는 전원이 꺼져도 남아 있어야 하니 플래시(LMA)에 살고, 프로그램은 그 변수를 고쳐 써야 하니 RAM(VMA)에서 쓴다. 둘을 잇는 것이 Reset_Handler의 복사 루프다.

링커 스크립트 문법으로는:

  • > RAM — VMA를 RAM 영역에 배정
  • AT > FLASH — LMA를 FLASH 영역의 다음 빈 곳에 배정 (AT(주소)로 숫자를 직접 줄 수도 있다)
  • LOADADDR(.data) — 그 섹션의 LMA를 돌려준다. ADDR(.data)는 VMA, SIZEOF(.data)는 크기

2.7 예제 6 — RAM 두 영역 + copy table, 그리고 와일드카드 함정#

실제 MCU는 RAM이 여러 덩어리다. STM32H7을 예로 들면 DTCM · AXI SRAM · SRAM1~4 · Backup SRAM이 주소도 성격도 다르다(DMA가 닿는 곳, 캐시되는 곳, 저전력에서 유지되는 곳 — B8, F8). 영역이 늘어나면 .data 복사도 여러 번 해야 한다. 흔한 해법은 링커가 만든 표(copy table)를 startup이 순회하는 것이다(NXP MCUXpresso의 __data_section_table이 이 방식이다).

무엇을 확인하나: RAM을 RAM(2 MB) + RAM2(2 MB, "DMA SRAM"이라고 가정)로 나누고, 초기값 있는 변수와 DMA 버퍼를 RAM2에 둔다. 링커 스크립트가 LONG()으로 표를 FLASH에 박고, startup이 표를 돈다.

버그가 하나 있다. g_motor_kp가 RAM2(0x2020xxxx)가 아니라 RAM(0x20000004)에 있고, .data2는 0바이트다. 이유: .data 출력 섹션의 *(.data*) 와일드카드가 .data2라는 입력 섹션 이름도 매치한다. 링커는 스크립트에 먼저 나온 규칙에 입력 섹션을 배정하므로 .data2 규칙에 닿기 전에 .data가 먹어 버렸다. 에러도 경고도 없다. 섹션 이름을 .data로 시작하지 않게 바꿔서 고쳤다(.ram2_data).

출력에서 볼 것:

  • 고친 뒤 g_motor_kp는 RAM2 0x20200000에 있고 값 250은 FLASH 0xff4(= .data2의 LMA)에서 복사됐다. .data의 LMA(0xf90, 100바이트) 바로 뒤다 — AT > FLASH는 여러 섹션이 줄줄이 이어 붙는다.
  • DMA 버퍼 g_spi_rx는 ALIGN(32)로 32바이트 경계(0x20200020)에 놓였다. 캐시 라인 정렬이 필요한 DMA 버퍼(B8)에 쓰는 방식이다.
  • copy table은 FLASH의 40바이트(0x28)짜리 데이터일 뿐이다. 영역이 다섯 개로 늘어도 startup 코드는 그대로다.
  • 사용한 수정: 링커 스크립트 *(.data2*) → *(.ram2_data*), 소스 section(".data2") → section(".ram2_data"). 실무 규칙: 커스텀 섹션 이름은 표준 이름(.data, .bss, .text)으로 시작하지 않게 짓는다. 피할 수 없으면 .data 규칙에서 EXCLUDE_FILE이나 더 구체적인 패턴으로 순서를 조정한다.

Don 경험과 연결: SSD 컨트롤러에서 "이 테이블은 TCM에, 이 버퍼는 DMA가 닿는 SRAM에"를 섹션 attribute + 링커 스크립트로 나눴던 것과 같다. 섹션 이름 와일드카드가 의도와 다르게 매치되는 사고는 map 파일을 열어 보기 전에는 아무도 모른다 — 그래서 bring-up 체크리스트에 "map 파일에서 핵심 객체 주소 확인"을 넣는다.

3. 링커 스크립트를 망가뜨려 보기 — 네 가지 고전 버그#

🔁 이 절은 Bare-Metal BM F3와 겹친다 (주인: 이 노트).

링커 스크립트 버그는 컴파일 에러가 안 난다. 링크가 되고, 이미지가 나오고, 대부분은 부팅 직후 이상하게 죽거나, 더 나쁘게는 "가끔" 틀린 값을 낸다. 네 가지를 일부러 만들어 증상을 기록한다.

3.1 예제 7 — KEEP을 빠뜨리면: 벡터 테이블이 사라진다#

무엇을 확인하나: 랩 스크립트에서 KEEP(*(.isr_vector))를 *(.isr_vector)로 바꾸고, 벡터 테이블을 아무도 참조하지 않는 가장 작은 앱을 빌드한다.

출력에서 볼 것:

  • .isr_vector 출력 섹션 크기 0. map 파일 60번째 줄 — "Discarded input sections" 목록에 0xc0바이트짜리 .isr_vector가 있다. --gc-sections가 "아무도 안 부르는 데이터"라고 버렸다. g_vectors에 붙인 __attribute__((used))는 컴파일러가 지우지 못하게 할 뿐, 링커의 gc는 막지 못한다.
  • 그 결과 0x0에는 Reset_Handler의 기계어가 왔다(ENTRY(Reset_Handler)가 gc의 뿌리라 함수는 살아남았다). 코어는 기계어를 벡터로 읽는다. 0x0의 바이트 08 b5 10 4a는 little-endian 워드 0x4a10b508 → MSP, 0x4의 10 4b 93 42는 0x42934b10 → PC(bit 0 = 0이라 Thumb 비트도 0).
  • 첫 명령부터 fault(INVSTATE) → HardFault 진입: 쓰레기 MSP에 프레임 32바이트를 쌓아 R13 = 0x4a10b4e8(= 0x4a10b508 − 0x20)이 됐고, HardFault 벡터(0xC의 d2 1a 22 f0 = 0xf0221ad2, 역시 짝수)를 PC로 읽었다 — 덤프의 R15 = 0xf0221ad2. HardFault 안에서 또 fault = Lockup. 실칩이면 코어가 멈추고(LOCKUP 신호), 디버거 없이는 "보드가 죽었다"로만 보인다.
  • 예제 4(ex1)로 같은 실험을 하면 멀쩡히 돈다 — main이 g_vectors를 읽어서 참조가 생기기 때문이다. "우리 보드에서는 되는데"의 전형이다.

3.2 예제 8 — AT > FLASH를 빠뜨리면: QEMU는 되고 실칩은 안 된다#

무엇을 확인하나: .data를 > RAM에만 두면 VMA = LMA = RAM이 된다. 디버거나 QEMU는 ELF를 그 주소에 그대로 올려 주므로 문제가 숨는다. 실제 플래시 프로그래머는 FLASH 영역만 굽는다. 두 방식으로 부팅해 비교한다.

LR = 0x8df가 어디인지 찾고, 같은 이미지를 setvbuf 없이(내 복사본 board.c에 #ifndef B5_NO_SETVBUF를 넣었다) 다시 돌렸다.

출력에서 볼 것:

  • AT>가 없으면 .data의 LMA가 0x20000000(RAM)이 된다. ELF로 부팅하면 QEMU가 RAM에 직접 올려 주므로 g_gain=42 — 버그가 안 보인다. 디버거로 load해서 테스트하는 개발 환경도 똑같다.
  • 플래시 영역만 담은 이미지로 부팅하면 두 가지 증상이 나온다. (1) board_init()의 setvbuf(stdout, ...)가 newlib의 _impure_ptr(역시 .data, 지금은 0)를 따라가다 __sflush_r에서 HardFault(CFSR 0x100 = IBUSERR, PC가 쓰레기). (2) setvbuf를 빼면 죽지는 않지만 g_gain=0, g_name='' — 조용히 틀린 값. 드론 FC라면 PID 게인이 0인 채로 이륙한다.
  • 덤으로 objcopy -O binary로 전체 .bin을 만들면 536,871,020바이트(512 MB)가 나온다. .bin은 가장 낮은 LMA(0x0)부터 가장 높은 LMA(0x20000000+)까지 빈틈을 0으로 채우기 때문이다. ".bin이 512 MB가 됐다"는 AT> 누락의 대표 증상이다.
  • 올바른 스크립트(mps2_m3.ld)의 .bin은 4260바이트이고, ELF로 띄우든 .bin으로 띄우든 같다.

실제 사례 — 공식 데모에도 있다: 랩에 들어 있는 FreeRTOS 공식 데모 CORTEX_MPS2_QEMU_IAR_GCC/build/gcc/의 mps2_m3.ld는 .data를 > RAM에만 두고(AT 없음), startup_gcc.c의 Reset_Handler는 (void) main(); 한 줄뿐이다(.data 복사도 .bss 0도 없다). QEMU가 ELF를 RAM에 올리고 .bss 부분을 0으로 채워 주니 동작하는 것이다. 그 데모를 실제 MPS2 FPGA 보드나 다른 칩의 출발점으로 복사하면 바로 이 절의 버그를 물려받는다.

3.3 예제 9 — .bss를 0으로 채우지 않으면: 콜드 부팅은 되고 웜 리셋에서 틀린다#

무엇을 확인하나: QEMU의 RAM은 전원 켤 때 0이다. 그래서 .bss 0 채우기를 빼도 첫 부팅은 멀쩡하다. 실칩의 SRAM은 전원 직후 임의 값이고, 소프트웨어 리셋(워치독, NVIC_SystemReset) 뒤에는 이전 값이 그대로 남는다. 그 웜 리셋을 QEMU에서 재현한다. AIRCR.SYSRESETREQ로 리셋하면 QEMU는 플래시 이미지는 다시 쓰지만 RAM은 그대로 둔다. 동시에 .noinit 변수(일부러 0으로 안 채우는 영역)가 리셋을 넘어 살아남는지도 본다. startup은 §4.3의 startup_b5.c, 링커는 b5.ld, 이미지는 플래시 .bin으로 부팅했다.

출력에서 볼 것:

  • 정상 startup: 리셋을 두 번 거쳐도 g_events는 매번 0. 0 채우기가 리셋마다 다시 돈다.
  • .bss 0을 빼면: boot #1은 0(QEMU RAM 초기값이 우연히 0이라서), 리셋 뒤에는 100, 200 — 이전 부팅의 값이 그대로 남았다. 실칩에서는 #1부터 쓰레기일 수 있다. "전원 켜고는 되는데 워치독 리셋 뒤에 이상하다"의 정체다.
  • g_boots는 1 → 2 → 3으로 셌다. .noinit은 리셋을 넘어 살아남는다. 매직 넘버로 "콜드 부팅인가"를 판정하는 패턴이다(전원 직후 SRAM이 우연히 매직 값일 확률은 2의 32승분의 1). 리셋 원인 · 크래시 로그 · 부트 카운터를 여기에 둔다(F8에서 실무 설계).
  • .noinit은 거꾸로 큰 버퍼를 0으로 채우는 시간을 아끼는 데도 쓴다(§8의 FreeRTOS heap).

3.4 예제 10 — 스택과 heap이 만나면: fault 없이 데이터가 썩는다#

무엇을 확인하나: 그림 4에서 heap은 위로, MSP 스택은 아래로 자란다. 둘 사이에 하드웨어 벽은 없다(MPU나 v8-M의 MSPLIM을 쓰지 않는 한). RAM을 16 KB로 줄인 small.ld(b5.ld에서 RAM 16K, 스택 0x400, 최소 heap 0x400)로 heap을 끝까지 채우고, 마지막 heap 블록(보정 테이블이라고 하자)을 0xA5로 채운 뒤 재귀를 점점 깊게 한다.

그림 5 — 예제 10의 실제 주소. 재귀 깊이 16에서 SP가 _sstack(0x20003c00) 아래로 내려가 마지막 heap 블록을 덮었다. fault는 없었다.

출력에서 볼 것:

  • malloc은 __heap_end(= _sstack)에서 멈췄다. 랩 _sbrk가 brk + inc > &__heap_end를 검사하기 때문이다. heap → 스택 방향은 막혀 있다.
  • 스택 → heap 방향은 아무도 안 막는다. 깊이 12까지는 SP가 스택 영역 안(0x20003c28)이었고, 깊이 16에서 0x20003b08 — heap 블록(0x20003a80..0x20003b80) 한가운데 — 까지 내려가 6바이트를 덮었다(volatile buf[0]과 저장된 레지스터 몇 개). HardFault도 경고도 없다. 보정 테이블이 몰래 바뀐 채로 계속 돈다.
  • RTOS에서는 태스크 스택마다 같은 문제가 있다. FreeRTOS의 configCHECK_FOR_STACK_OVERFLOW, Zephyr의 MPU 스택 가드 · CONFIG_HW_STACK_PROTECTION이 이것을 잡으려는 장치다(D · K 모듈). v8-M(M33)은 MSPLIM/PSPLIM 레지스터로 하드웨어가 잡아 준다.

3.5 예제 11 — ASSERT와 region overflow, PROVIDE로 고치기#

무엇을 확인하나: 16 KB RAM에 DMA 버퍼 크기를 바꿔 가며 링크한다. 링커가 어떤 메시지로 거절하는지, PROVIDE로 만든 스택 크기를 명령줄에서 바꿔 해결할 수 있는지 본다.

출력에서 볼 것:

  • 14 KB: 섹션들(.data + .bss + 최소 heap 1 KB)은 16 KB 영역 안에 들어가서 영역 overflow는 안 났다. 하지만 스택 1 KB까지는 안 들어간다 — 이건 MEMORY가 모르는 정보라 우리가 쓴 ASSERT만 잡는다. ASSERT가 없었다면 링크가 성공하고 §3.4의 충돌이 런타임에 났을 것이다.
  • 17 KB: .bss가 영역 자체를 넘었다. 링커의 내장 검사(region RAM overflowed by 2488 bytes)와 ASSERT가 함께 나온다.
  • -Wl,--defsym=_Main_Stack_Size=0x200을 주면 PROVIDE의 기본값(0x400) 대신 그 값이 쓰여서(nm의 00000200 A) 링크가 된다. 보드 변형마다 링커 스크립트를 복사하지 않고 빌드 옵션으로 조절하는 방법이다. (물론 스택을 줄여도 되는지는 §3.4의 high-water mark로 따로 확인해야 한다.)
  • size의 bss 열(15704)에는 .noinit · .heap(NOLOAD 섹션)도 들어간다. "bss가 크다"고 보이면 size -A로 섹션별로 나눠 봐야 한다.

4.2 예제 12 — 컴파일러가 startup 루프를 memcpy/memset 호출로 바꾼다#

무엇을 확인하나: 위 C 루프가 실제로 어떤 기계어가 됐는지 본다.

출력에서 볼 것:

  • 우리가 쓴 두 루프가 사라지고 bl memcpy, bl memset이 됐다. GCC의 -ftree-loop-distribute-patterns 최적화(이 GCC 14의 -O2에서 켜져 있다)가 "이 루프는 memcpy와 같다"고 알아본 것이다. 바이트 수는 (end - 1 - start) & ~3 + 4로 계산했다.
  • 이게 문제가 되는 경우: (1) memcpy/memset이 .data나 .bss에 의존하면(예: 어떤 libc는 CPU 기능 표를 전역 변수로 둔다) 아직 초기화 안 된 상태에서 불린다. (2) memset 자체를 .ramfunc로 RAM에 두었다면 아직 복사 전이다. (3) 링크할 libc가 없는 -nostdlib 빌드에서는 undefined reference to memset. newlib-nano의 memcpy/memset은 전역 상태를 안 쓰므로 여기서는 안전하다.
  • 그리고 속도가 바뀐다. newlib-nano의 memset은 strd 두 개로 16바이트씩 쓰는 루프라 우리 C 루프보다 빠르다(§8에서 측정).
  • 막는 법: 함수에 __attribute__((optimize("no-tree-loop-distribute-patterns")))를 붙이거나(§4.3의 COPY_MODE 1), 파일을 -fno-tree-loop-distribute-patterns로 컴파일하거나, 어셈블리로 쓴다. Zephyr는 arch_early_memset() · arch_early_memcpy()라는 별도 이름을 두고 아키텍처가 덮어쓸 수 있게 했다(§10).

4.3 완전판 startup_b5.c — SystemInit · FPU · .data/.bss · 생성자 · exit#

이 노트의 나머지 예제가 쓰는 startup이다. 실제 측정에 쓴 파일 그대로이며, 길어서 두 덩어리로 나눴다. COPY_MODE로 복사 방식을 고르고(§8), g_boot_t[]에 25 MHz 카운터 값을 남긴다. g_boot_t는 .noinit에 있어서 .bss 0 채우기에 지워지지 않는다.

순서가 왜 이런가:

  1. SystemInit이 맨 앞 — 클럭을 먼저 올리면 뒤의 복사 · 0 채우기가 빨라진다. 외부 SDRAM에 .data를 둔 보드라면 SDRAM 컨트롤러를 켜야 복사할 수 있다. 대신 SystemInit 안에서는 .data/.bss 전역 변수를 쓰면 안 된다(§5.1의 함정).
  2. FPU 활성화가 복사 전 — 컴파일러는 -mfloat-abi=hard일 때 어디서든(심지어 memcpy 최적화나 레지스터 저장에) VFP 명령을 쓸 수 있다. CPACR이 꺼진 상태에서 그런 명령이 나오면 NOCP fault다(§5.2).
  3. .data → .bss 순서는 무관하지만 관례다.
  4. __libc_init_array는 .data/.bss 뒤 — 생성자는 전역 변수를 쓴다.
  5. board_init(UART)는 생성자 뒤 — 랩 고유 순서. 그래서 생성자 안에서는 printf를 못 쓴다(§6 예제에서 순서를 배열에 기록한 이유).
  6. exit(main()) — main의 반환값으로 newlib exit 경로를 탄다(§7).

4.4 같은 startup을 어셈블리로#

무엇을 확인하나: C startup이 가능하다고 어셈블리가 쓸모없는 것은 아니다. 벤더 startup(startup_stm32xxx.s)은 대부분 어셈블리이고, §7의 "main이 돌아갈 곳" 실험에도 쓴다. 벡터 테이블까지 전부 어셈블리로 쓴 버전이다.

출력에서 볼 것: .S(대문자)라 C 전처리기가 돌아서 #ifdef를 쓸 수 있다. .thumb_func가 붙은 라벨은 .word에 쓰일 때 bit 0이 1로 채워진다(§1.4). main의 반환값 7이 r0로 board_exit에 그대로 넘어갔다(AAPCS: 반환값 = r0). QEMU 종료코드 1은 board_exit의 "0이 아니면 1" 규칙이다.

5. SystemInit과 FPU 켜기#

🔁 이 절은 Bare-Metal BM F4와 겹친다 (주인: 이 노트).

5.1 SystemInit — 클럭 트리를 세우는 함수 (QEMU에는 없다)#

CMSIS 관례에서 SystemInit()은 main 전에 칩을 "제 속도로" 만드는 함수다. 실제 칩에서 하는 일은 대략 이 순서다.

  1. 리셋 직후 코어는 내부 RC 발진기(STM32의 HSI 16 MHz 같은 것)로 느리게 돈다.
  2. flash wait state를 먼저 올린다. 플래시는 코어보다 느리다. 168 MHz로 올린 뒤에 wait state를 올리면 그 사이 명령 fetch가 틀린 값을 읽는다. 예를 들어 STM32F407은 3.3 V · 168 MHz에서 5 wait state가 필요하다(RM0090의 표).
  3. 외부 크리스털(HSE)을 켜고 안정될 때까지 기다린다.
  4. PLL 배수 · 분주를 설정하고 lock을 기다린다.
  5. 버스 분주(AHB · APB1 · APB2)를 맞추고, 시스템 클럭을 PLL로 전환한다.
  6. (선택) VTOR 설정, 외부 메모리 컨트롤러(FMC/SDRAM) 초기화, 캐시 · ART 가속기 켜기.

QEMU mps2-an385는 클럭 트리를 모델링하지 않는다(25 MHz 고정, wait state 없음). 그래서 이 노트의 SystemInit은 빈 weak 함수다 — 실행해서 보여 줄 수 없는 부분이다.

함정 — SystemInit 안의 전역 변수: CMSIS의 SystemCoreClock은 초기값 있는 전역 변수(.data)다. SystemInit이 클럭을 바꾸고 SystemCoreClock = 168000000;을 쓰면, 바로 다음의 .data 복사가 그 값을 플래시의 초기값으로 덮어쓴다. 그래서 CMSIS는 main에서 SystemCoreClockUpdate()를 다시 부르게 하거나, SystemInit에서는 레지스터만 만진다. SystemInit 안의 .bss 변수도 마찬가지로 곧 0이 된다. 벤더마다 SystemInit을 .data 복사 전에 부르기도 하고 후에 부르기도 하니, 자기 프로젝트의 startup 파일에서 순서를 직접 확인한다.

함정 — 워치독: 일부 칩은 옵션 바이트로 하드웨어 워치독이 리셋부터 켜져 있다. §8처럼 큰 .bss를 0으로 채우는 데 수십 ms가 걸리면 main 전에 워치독 리셋이 난다. 증상은 "부팅 루프, main 첫 줄 브레이크포인트에 안 걸림".

6. 생성자 — __libc_init_array, .preinit_array, .init_array, 그리고 C++#

🔁 이 절은 Bare-Metal BM F4와 겹친다 (주인: 이 노트).

6.1 직관 — 생성자는 "함수 포인터 표"다#

__attribute__((constructor)) 함수나 C++ 전역 객체(static ImuDriver g_imu(1000);)의 생성자는 main 전에 돌아야 한다. 컴파일러는 이것을 함수 포인터 하나를 .init_array 섹션에 넣는 것으로 구현한다. 누군가 그 표를 처음부터 끝까지 돌며 호출해야 하는데, Linux에서는 C 런타임(crt1.o · __libc_start_main)이 한다(EL B3). MCU에서는 startup이 __libc_init_array()를 불러야 한다. newlib의 __libc_init_array는 이 순서로 부른다.

  1. __preinit_array_start ~ __preinit_array_end의 함수들
  2. _init() (원래 crti.o · crtn.o가 만드는 함수)
  3. __init_array_start ~ __init_array_end의 함수들 (우선순위 붙은 것이 먼저 — 링커의 SORT)

이 경계 심볼은 링커 스크립트가 만들어야 한다(§2.6의 PROVIDE_HIDDEN). 랩 템플릿에는 그게 없다.

출력에서 볼 것: 등록의 역순으로 불렸다. C++ 소멸자는 main 전(생성자 안)에 먼저 등록됐고 flush_log는 main 안에서 나중에 등록됐으므로, flush_log가 먼저, 소멸자가 나중이다. 그다음 _exit(3) → board_exit(3). 펌웨어에서 이 경로는 보통 쓸모없거나 위험하다: 드라이버 객체의 소멸자가 하드웨어를 끄고, 그 뒤 _exit가 무한 루프에 빠진다. 많은 팀이 -fno-use-cxa-atexit나 소멸자 없는 전역 객체로 이 코드를 아예 빼서 플래시를 아낀다(B11).

7.2 예제 16 — 돌아갈 곳이 없으면: PC = 0xFFFFFFFF#

무엇을 확인하나: 리셋 벡터가 곧바로 main을 가리키거나, startup이 bl main 대신 b main(꼬리 점프)으로 들어가면 main의 return 주소는 리셋 때의 LR = 0xFFFFFFFF다. startup_asm.S를 -DTAILCALL로 빌드해서 재현했다.

출력에서 볼 것:

  • main의 pop {r3, pc}가 PC에 0xFFFFFFFF를 넣었다. bit 0은 Thumb 비트로 가고 PC = 0xFFFFFFFE. Thread 모드에서는 이 값이 EXC_RETURN이 아니다(EXC_RETURN은 Handler 모드에서만 특별하다, B2 §5). 그냥 그 주소에서 명령을 가져오려다 실패한다.

8. 부팅 시간 — 복사와 0 채우기는 크기에 비례한다#

8.1 직관#

Reset_Handler의 일은 대부분 메모리 쓰기다. 그러니 시간은 (.data 크기 + .bss 크기) ÷ 쓰기 속도다. A7에서 FreeRTOS의 reset → main이 bare-metal보다 88배 길었던 이유(1.37 ms)가 커널이 아니라 heap_4의 ucHeap[128 KB]가 .bss에 있어서였다. A7은 heap을 16 KB로 줄이면 0.22 ms가 되는 것도 쟀다 — 112 KB 차이가 약 1.15 ms, 즉 KB당 약 10 µs다. 이 절에서는 그 숫자를 크기와 복사 방식별로 직접 재서 확인한다.

  • 실칩에서 진짜 상한은 메모리 대역폭이다. 32비트 SRAM 포트에 사이클당 1워드가 최선이다. 그래서 대형 칩(H7 · R52)은 DMA나 하드웨어 메모리 초기화(ECC SRAM의 자동 0 채우기 기능)를 쓰기도 한다.

8.3 예제 18 — FreeRTOS: ucHeap을 .noinit으로 옮기면#

무엇을 확인하나: 측정 결과의 결론을 RTOS에 적용한다. FreeRTOS heap_4의 ucHeap[configTOTAL_HEAP_SIZE]는 기본적으로 heap_4.c 안의 static 배열(.bss)이다. configAPPLICATION_ALLOCATED_HEAP = 1이면 heap_4.c가 extern uint8_t ucHeap[]로 선언만 하고(V11.3.2 portable/MemMang/heap_4.c 89~96줄), 정의는 앱이 한다 — 그 정의를 .noinit에 둔다. heap_4는 prvHeapInit()에서 블록 헤더를 직접 써 넣으므로 heap 메모리가 0일 필요가 없다. 랩 FreeRTOS 템플릿(Makefile, 랩 startup.c, 랩 mps2_m3.ld — 거기에도 .noinit이 있다) 그대로 빌드했다.

  • main → 첫 태스크 구간(약 110 µs)은 그대로다. 그게 진짜 커널 비용(xTaskCreate · idle/timer 태스크 생성 · 첫 컨텍스트 스위치, C3)이다.

9. XIP flash 실행 vs RAM 실행 — .ramfunc#

9.1 직관과 정의#

Cortex-M MCU의 코드는 보통 내부 플래시에서 그대로 실행된다. 이것을 XIP(eXecute In Place)라 한다. RAM으로 복사할 필요가 없어서 RAM을 아끼고 부팅이 빠르다. 대신:

  • 플래시는 코어보다 느려서 wait state가 붙는다(§5.1). 칩은 prefetch 버퍼 · 플래시 캐시(ST의 ART 가속기 등)로 감추지만, 분기가 많은 코드에서는 지연이 드러나고 실행 시간이 흔들린다(지터).
  • 플래시를 지우거나 쓰는 동안에는 같은 뱅크에서 명령을 가져올 수 없다(칩마다 다름). 펌웨어 업데이트 코드 · EEPROM 에뮬레이션은 RAM에서 돌아야 한다.

그래서 일부 함수만 RAM(또는 ITCM)에 둔다. 방법은 .data와 똑같다: VMA는 RAM, LMA는 FLASH, startup이 복사. 차이는 내용이 코드라는 것뿐이다.

9.2 예제 19 — RAM에서 도는 함수와 long-branch veneer#

무엇을 확인하나: section(".ramfunc") 함수를 만들고(b5.ld가 .data 안에 *(.ramfunc*)를 넣는다) 주소, 플래시 안의 원본 위치, 실행 시간을 플래시 버전과 비교한다. noipa는 GCC가 함수 간 분석으로 결과를 미리 계산하거나 호출을 타이머 읽기 앞뒤로 옮기지 못하게 한다(처음 noinline만 붙였을 때 두 함수 모두 "1 cycle"이 나왔다 — 호출이 측정 구간 밖으로 옮겨졌다).

main(플래시, 0x0 근처)에서 RAM(0x20000000 근처)까지는 512 MB 떨어져 있다. Thumb-2 BL의 도달 거리는 ±16 MB다. 그래서 링커가 무엇을 했는지 봤다.

출력에서 볼 것:

  • crc_ram의 주소는 0x20000061(RAM, Thumb 비트 포함), 플래시 원본은 0x117d. 두 함수가 같은 CRC를 냈다 — RAM에서 실제로 실행됐다.
  • 링커가 플래시에 __crc_ram_veneer를 자동으로 만들었다: ldr.w pc, [pc] + 목적지 주소 한 워드(그 뒤 두 워드는 다음 데이터인 문자열이다). main의 BL은 이 veneer로 가고, veneer가 RAM으로 뛴다. 호출마다 명령 하나가 더 붙는다. GCC의 __attribute__((long_call))을 쓰면 컴파일러가 처음부터 ldr r3, =func; blx r3로 부른다(Zephyr의 GCC __ramfunc 매크로가 Arm에서 이 방식을 쓴다).
  • 실행 시간은 96009 vs 96008 — 같다. QEMU는 flash wait state를 모델링하지 않으므로 이 차이는 보여 줄 수 없다. 실칩(예: wait state 5인 STM32F4에서 ART 캐시가 미스 나는 루프)이라면 RAM 쪽이 빠르고 무엇보다 일정하다. 이 부분은 측정하지 못했다고 정직하게 적는다.
  • .data의 플래그에 CODE가 붙었고, size가 data 열에 0을 찍고 그 132바이트를 text에 넣었다. .data와 .ramfunc를 한 출력 섹션에 섞은 부작용이다. 깔끔하게 하려면 .ramfunc를 별도 출력 섹션(> RAM AT > FLASH)으로 나누고 copy table(§2.7)에 한 줄을 추가한다(연습문제 2).
  • 랩 board.c가 .ramfunc를 RAM에서 돌리는 데 추가 설정이 필요 없었던 것은 Cortex-M3의 기본 메모리 맵에서 SRAM 영역(0x20000000~)이 실행 가능이기 때문이다. MPU로 RAM을 XN(실행 금지)으로 막은 시스템에서는 그 영역만 예외로 열어야 한다(K 모듈).

실무에서: 모터 컨트롤러의 20 kHz FOC 전류 루프 ISR(50 µs마다)은 플래시 wait state로 인한 지터를 피하려고 ITCM이나 SRAM에 둔다. STM32G4 같은 칩은 CCM SRAM을, H7은 ITCM을 쓴다. 벡터 테이블까지 RAM으로 옮기는 것(VTOR)은 B2 §2.

10. RTOS 커널 안에서는 무슨 일이 일어나나#

10.1 FreeRTOS — main까지는 아무것도 안 한다#

FreeRTOS 커널은 startup 코드를 갖고 있지 않다. 벡터 테이블 · Reset_Handler · 링커 스크립트는 전부 칩 벤더나 앱이 준다(이 랩에서는 templates/common). 커널 코드는 main 안에서 처음 실행된다.

  • xTaskCreate() → prvCreateTask() → pvPortMalloc()(heap_4) → prvInitialiseNewTask() → pxPortInitialiseStack()이 가짜 예외 프레임을 쌓는다(tasks.c, portable/GCC/ARM_CM3/port.c) — C3.
  • vTaskStartScheduler()(tasks.c) → idle 태스크 · timer 태스크 생성 → xPortStartScheduler()(port.c): PendSV · SysTick 우선순위 설정, SysTick 시작, prvPortStartFirstTask()가 MSP를 벡터 테이블 0번 워드 값으로 되돌리고(main의 스택은 이제 버려지고 인터럽트 스택이 된다) svc 0으로 첫 태스크에 들어간다 — C3.

그래서 FreeRTOS에서 "main 전" 비용은 순수하게 startup의 몫이고(§8: 그중 대부분은 ucHeap), 링커 스크립트의 _Main_Stack_Size는 "main이 쓰는 스택 + 나중에 모든 ISR이 함께 쓰는 스택"이다(랩 ld의 주석이 그렇게 적혀 있다). §3.2에서 본 것처럼 공식 QEMU 데모의 startup은 main() 한 줄이다 — FreeRTOS는 그 부분에 관심이 없다는 뜻이기도 하다.

10.2 Zephyr — 커널이 main을 부른다 (v4.4.2 소스에서 확인한 이름)#

Zephyr는 startup부터 main 호출까지 전부 커널이 갖고 있다. Cortex-M 경로를 v4.4.2 소스에서 따라가면:

  • nm: z_interrupt_stacks와 z_main_stack은 __bss_start..__bss_end(0x200000a8..0x200002f4) 밖이다. Zephyr는 스택을 noinit 섹션에 둔다(map 파일의 noinit 0x200002f8 0x1500). 스택을 0으로 채우는 시간을 아끼는 것이다 — §8의 .noinit 원칙을 커널이 기본으로 쓴다.

  • 교훈: 같은 "128 KB .bss"가 libc · 최적화 설정에 따라 1.3 ms도 되고 17 ms도 된다. 부팅 시간이 이상하면 arch_early_memset/memset을 디스어셈블해 본다. 큰 버퍼는 Zephyr에서도 __noinit(include/zephyr/linker/section_tags.h) 매크로로 0 채우기 대상에서 빼는 것이 정석이다. 아키텍처가 arch_early_memset을 덮어써서 빠른 구현을 줄 수도 있다(weak 함수다).

11. 실무에서 다시 보기#

11.1 드론 비행 제어기 — "리셋에서 모터 재개까지"#

STM32H7급 FC를 예로 들자. 비행 중 브라운아웃 리셋이 나면 다음이 순서대로 돌아야 다시 자세 제어가 된다: 부트로더(서명 검사) → 앱 Reset_Handler → SystemInit(PLL, 수백 µs~ms) → .data/.bss → RTOS 시작 → IMU 초기화 → 필터 수렴. 이 노트에서 손댈 수 있는 것은:

  • 큰 버퍼를 .noinit으로: 블랙박스 로그 링버퍼(수십~수백 KB), DMA 버퍼, RTOS heap. 0 채우기 대상에서 빼면 ms 단위가 줄어든다(예제 18: 25배).
  • 로그 링버퍼를 .noinit에 두면 덤으로 리셋 직전 로그가 살아남는다 — 리셋 원인 분석에 쓴다(예제 9의 매직 넘버 패턴, F8).
  • DTCM에 스택 · 제어 루프 데이터, ITCM에 rate loop ISR: 링커 스크립트에 영역을 추가하고(예제 6), ITCM 코드는 .ramfunc처럼 AT > FLASH로 복사한다(예제 19). H7에서 DTCM은 DMA가 못 닿는 것에 주의(B8).

11.4 Don의 SSD 컨트롤러 — 같은 문제, 큰 스케일#

SSD 컨트롤러는 부트 ROM이 NAND나 SPI NOR에서 펌웨어를 SRAM/TCM으로 통째로 복사한 뒤 점프하는 구조가 흔하다. 그러면 "XIP 플래시 + .data만 복사"가 아니라 전체가 RAM 실행이고, LMA는 NAND 안의 이미지 오프셋, VMA는 SRAM이다. 링커 스크립트의 AT> 개념이 그대로 적용되고, 복사 주체가 Reset_Handler가 아니라 부트 ROM일 뿐이다. 또 ECC SRAM은 한 번도 쓰지 않은 주소를 읽으면 ECC 에러가 나므로, 부팅 초기에 사용 전 전체 SRAM을 한 번 써 주는 루프가 있었을 것이다 — 이 노트의 .bss 0 채우기를 "모든 RAM"으로 넓힌 것이고, §8의 측정이 말하듯 크기에 비례하는 부팅 비용이다(F8에서 ECC RAM 초기화를 따로 다룬다).

13. 면접에서 이렇게 말한다#

Q. "Walk me through what happens on a Cortex-M from power-on reset to the first line of main."

A. 하드웨어는 벡터 테이블 두 워드만 읽는다: 0번은 MSP, 1번은 PC(bit 0은 Thumb). Thread · privileged · MSP 상태로 Reset_Handler가 시작된다. 그다음은 전부 소프트웨어다: 클럭 설정(SystemInit), FPU 켜기, .data를 플래시에서 RAM으로 복사, .bss 0, 생성자 실행, main 호출. 주소는 링커 스크립트 심볼로 안다. 시간은 대부분 복사와 0 채우기이고 크기에 비례한다.

On reset the core reads just two words from the vector table: word 0 goes into MSP and word 1 into the PC, with bit 0 setting the Thumb state. It starts Reset_Handler in privileged Thread mode on the main stack. Everything after that is software: SystemInit sets up clocks and flash wait states, the FPU is enabled through CPACR if present, .data is copied from its load address in flash to RAM, .bss is zeroed, static constructors run through __libc_init_array, and then main is called. The startup code finds those regions through linker-script symbols. In practice the boot time is dominated by the copy and zero loops, which scale linearly with size — I measured about 10 µs per KB of .bss on a 25 MHz M3 model.

꼬리 질문: "Why can Cortex-M startup be written in C but Cortex-R or RISC-V cannot?" → 하드웨어가 SP를 넣어 주는 건 M 프로파일뿐이다.

Q. "What is the difference between VMA and LMA, and why does .data need both?"

A. VMA는 실행할 때의 주소, LMA는 이미지에 저장된 주소다. .data의 초기값은 전원이 꺼져도 남아야 하니 플래시(LMA)에 있고, 변수는 써야 하니 RAM(VMA)에 있다. 링커 스크립트의 > RAM AT > FLASH가 둘을 정하고 startup이 복사한다.

VMA is where a section lives when the program runs; LMA is where it is stored in the image. Initialized data has to survive power-off, so its initial values sit in flash, but the program writes those variables, so they must live in RAM. In the linker script I write > RAM AT > FLASH and export LOADADDR(.data), and Reset_Handler copies from the LMA to the VMA. If you forget the AT part, it still works under a debugger because the debugger loads RAM directly, but it fails when booting from flash — and objcopy produces a 512-megabyte .bin, which is a nice tell.

꼬리 질문: "What does readelf -l show for that?" → 두 번째 LOAD 세그먼트의 PhysAddr(LMA)가 플래시, VirtAddr가 RAM, FileSiz < MemSiz(.bss).

Q. "Our firmware works when flashed with the debugger attached but fails after a power cycle. Where do you look?"

A. 디버거가 대신 해 주던 일이 없어서다. 첫째, 디버거 load가 RAM을 직접 채워 숨긴 .data LMA 문제. 둘째, .bss를 0으로 안 채워서 RAM 잔여값에 의존. 셋째, 디버거가 클럭 · 워치독 · 저전력 디버그 설정을 바꿔 둔 것. 넷째, 부팅 시간이 길어 하드웨어 워치독에 걸림. 플래시만 담은 .bin으로 QEMU나 보드에서 부팅해 재현한다.

I look for things the debugger was silently doing for us. The classic one is .data placed without a flash load address: the debugger writes RAM directly, so initial values look fine, but a flash-only boot sees zeros. Second, .bss not being zeroed, so the code depends on whatever is in RAM. Third, the debugger keeping clocks running in low-power modes or halting the watchdog. And fourth, a slow startup — a big zeroed buffer can take milliseconds and trip an option-byte watchdog before main. I reproduce by booting the raw flash image without the debugger and checking the map file and the .bin size.

Q. "How do C++ global constructors get called on bare metal?"

A. 컴파일러가 생성자 함수 포인터를 .init_array에 넣는다. 링커 스크립트가 그 섹션을 KEEP하고 시작 · 끝 심볼을 만들어야 하고, startup이 __libc_init_array()로 순회해야 한다. -nostartfiles면 _init과 __dso_handle이 없어 링크 에러가 나므로 스텁을 준다. Zephyr는 커널이 POST_KERNEL 뒤에 돌린다.

The compiler emits a pointer to each constructor function into the .init_array section. Two things must be in place: the linker script must KEEP that section and define __init_array_start and end, and the startup code must walk it, usually by calling newlib's __libc_init_array after .data and .bss are ready. With -nostartfiles you also lose _init from crti and __dso_handle from crtbegin, so you either provide stubs or link the crt files. Without the KEEP, gc-sections drops the table and the constructors silently never run. I also avoid relying on cross-file construction order and keep hardware init out of constructors.

Q. "What happens if main returns on a microcontroller?"

A. startup이 main 뒤에 둔 코드가 정한다. newlib exit면 atexit · 소멸자 뒤 _exit, 벤더 startup은 무한 루프가 흔하다. 리셋 벡터가 main을 직접 가리키면 LR = 0xFFFFFFFF로 return해서 HardFault(IACCVIOL)가 난다. FreeRTOS는 스케줄러를 시작한 main이 돌아오지 않고, Zephyr는 main이 스레드라 그 스레드만 끝난다.

It depends entirely on what the startup code put after the call. With newlib's exit you run atexit handlers and static destructors and end in _exit, which on a board is usually a loop or a reset. If main was entered without a proper call — say the reset vector points straight at it — it returns to the reset value of LR, 0xFFFFFFFF, and you get a HardFault on the instruction fetch; I reproduced that on QEMU with IACCVIOL. In FreeRTOS main starts the scheduler and never returns, and in Zephyr main is just the main thread, so returning ends that thread while the rest of the system keeps running.

Q. "Boot time is too long. How would you reduce it?"

A. 먼저 잰다(리셋부터 카운터, 단계별 타임스탬프). 대부분 .bss · .data 크기이므로 큰 버퍼(heap, 로그, DMA)를 .noinit으로 빼고, 0 채우기 루프를 stm이나 좋은 memset으로, 클럭을 먼저 올린다. RTOS 설정(Zephyr의 크기 최적화 libc 같은 것)도 확인한다. 나머지는 드라이버 초기화를 지연시키는 것.

First I measure, with a free-running counter from reset and timestamps per stage. Most of the pre-main time is proportional to .bss and .data size, so the big wins are moving large buffers that don't need to be zero — RTOS heap, log rings, DMA buffers — into a NOLOAD noinit section, making sure the zero loop uses multi-word stores, and raising the clock before the loops. Moving FreeRTOS's heap to noinit cut reset-to-main from 1.37 ms to 55 µs in my measurement. I also check the library: a size-optimized Zephyr build used a byte-wise memset that made 128 KB of .bss cost about 17 ms instead of 1.4 ms. After that it's deferring driver init until it's actually needed.

Q. "Why and how would you run code from RAM on a flash-based MCU?"

A. 이유는 셋: 플래시를 지우거나 쓰는 동안 실행해야 하는 코드, wait state로 인한 지터를 없애야 하는 빠른 ISR, 더 빠른 실행. 방법은 .data와 같다: .ramfunc 섹션을 > RAM AT > FLASH로 두고 startup이 복사. 512 MB 떨어진 호출은 링커가 veneer를 만들거나 long_call을 쓴다.

Three reasons: code that must keep running while flash is being erased or programmed, tight ISRs where flash wait states add jitter, and raw speed on parts without a good flash cache. Mechanically it's the same trick as .data — put the function in its own section, give it a RAM VMA and a flash LMA, and let the startup copy it. Because RAM is hundreds of megabytes away from flash, a plain BL can't reach it, so either the linker inserts a long-branch veneer, which I saw it do automatically, or you mark the function long_call. And you have to make sure everything that function calls is also in RAM.

Q. "What does Zephyr do before main that FreeRTOS doesn't?"

A. FreeRTOS는 startup을 안 가진다 — main이 커널을 시작한다. Zephyr는 z_arm_reset에서 스택을 잡고, z_prep_c에서 VTOR · FPU · arch_bss_zero · arch_data_copy, z_cstart에서 init level EARLY · PRE_KERNEL_1/2 드라이버 초기화, 그다음 main 스레드로 전환해 POST_KERNEL · APPLICATION을 돌리고 main을 부른다.

FreeRTOS owns nothing before main; the vendor startup copies data and zeroes bss, and the kernel only runs once main calls xTaskCreate and vTaskStartScheduler. Zephyr owns the whole path: z_arm_reset sets up the stacks, z_prep_c relocates the vector table, enables the FPU, zeroes .bss and copies .data, then z_cstart runs the EARLY and PRE_KERNEL init levels, switches into the main thread directly without going through PendSV, and bg_thread_main runs POST_KERNEL and APPLICATION before finally calling main. So in Zephyr, main runs as a thread with drivers already initialized.

  5. 버그 찾기 — 동료가 SystemInit()에서 SystemCoreClock = 168000000;을 쓰고, startup은 SystemInit → .data 복사 → main 순서다. main에서 SystemCoreClock을 읽으면? .bss라면? 정답/힌트: .data면 플래시의 초기값(보통 16000000)으로 덮이고, .bss(초기값 없음)면 0이 된다. 둘 다 UART 보율 계산이 틀린다.
  6. Zephyr — CONFIG_SKIP_BSS_CLEAR는 언제 켜나? kernel/Kconfig의 도움말을 읽고, 켰을 때 누가 .bss를 0으로 만들어야 하는지 답하라. 정답/힌트: 부트 ROM · 이전 단계 로더나 하드웨어(ECC 메모리 초기화)가 .bss를 이미 0으로 만들어 주는 플랫폼. 그 책임은 그 외부 주체에게 넘어간다(도움말 원문 "the responsibility for .bss zeroing in all possible scenarios ...").
  7. 포팅 — mps2-an505(Cortex-M33)으로 startup_b5.c를 옮겨라. 메모리 맵(QEMU an505의 코드 · SRAM 주소)을 확인해 MEMORY를 고치고, -mcpu=cortex-m33로 빌드한 뒤 Reset_Handler 첫머리에서 msr msplim, <_sstack>를 설정해 예제 10의 스택 충돌이 이제 fault(STKOF)로 잡히는지 보라. 정답/힌트: v8-M Mainline은 MSPLIM 아래로 SP가 내려가면 UsageFault STKOF. Secure 상태에서 시작한다는 점(TrustZone)도 확인할 것 — B7, K 모듈.

16. 요약 & 체크리스트#

Cortex-M의 리셋에서 하드웨어가 하는 일은 벡터 두 워드(MSP, PC+Thumb)를 읽는 것뿐이고, 나머지는 Reset_Handler가 링커 스크립트 심볼을 보고 한다: SystemInit → FPU → .data를 LMA(플래시)에서 VMA(RAM)로 복사 → .bss 0 → 생성자(.init_array) → main → (return하면) startup이 정한 곳. 링커 스크립트 버그(KEEP · AT> · 와일드카드 · 스택/heap 경계)는 에러 없이 링크되고, QEMU나 디버거가 가려 주며, 실칩 · 웜 리셋 · 깊은 호출에서야 드러난다 — map 파일 · objdump -h · 플래시 단독 부팅으로 잡는다. main 전 시간은 .data/.bss 크기에 정비례(이 모델에서 0 채우기 약 8~25 µs/KB)하고, 가장 큰 개선은 0일 필요 없는 큰 버퍼를 .noinit으로 빼는 것(FreeRTOS 25배)과 libc · 최적화 설정(Zephyr 12배)에서 나왔다. FreeRTOS는 main이 커널을 시작하고, Zephyr는 z_prep_c → z_cstart → bg_thread_main을 거쳐 main을 스레드로 부른다.
