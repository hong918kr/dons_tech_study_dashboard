Bare-Metal 노트는 이 노트를 링크하고 "RTOS 없이 crt0부터 직접 쓰는 최소 런타임(자체 memcpy·printf 구현)" 관점만 더한다

0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어를 하던 Don에게 툴체인은 "벤더가 준 Makefile 안의 한 줄"이었을 가능성이 크다. 그런데 RTOS 펌웨어 엔지니어의 일상에는 툴체인 문제가 생각보다 자주 나온다.

  • 드론 비행 제어기(STM32H7, FLASH 2 MB)에서는 크기는 여유가 있지만 -O2로 바꾸자 IMU 드라이버의 지연 루프가 사라져서 센서 초기화가 실패한다.
  • 로봇 관절 모터 컨트롤러(Cortex-M4, FLASH 128 KB)에서는 디버그 로그에 printf("%f") 하나를 넣자 링크가 region FLASH overflowed by 9 KB로 실패한다.
  • 센서 허브 MCU(Zephyr)에서는 CI가 Zephyr SDK로, 개발자 PC는 Ubuntu의 arm-none-eabi-gcc로 빌드해서 바이너리 크기와 타이밍이 미묘하게 다르다.
  • 새 보드 bring-up 때 printf가 아무것도 안 찍는다 — 알고 보니 --specs=nosys.specs로 링크해서 _write가 "항상 실패"하는 가짜 함수였다.

이 노트는 이 네 장면을 전부 직접 재현하고 숫자로 잰다. 큰 흐름은 "툴체인이 무엇을 링크하나 → libc를 무엇으로 고르나 → 최적화가 크기와 시간을 어떻게 바꾸나 → map 파일로 어떻게 찾아내나"다.

그림 1 — arm-none-eabi-gcc 명령 하나 뒤에서 일어나는 일. 드라이버가 specs 파일과 multilib 규칙으로 어떤 libc·시작 파일을 링크할지 정하고, -nostartfiles / -nodefaultlibs / -nostdlib는 그 재료를 빼는 스위치다.

Don의 SSD 경험으로 비유하면 이렇다. SSD 컨트롤러 펌웨어에서 "코드 영역이 ITCM 256 KB에 안 들어간다"는 문제를 풀 때 map 파일을 열어 큰 함수를 찾고, 디버그 문자열을 빼고, -Os로 일부 파일만 다시 빌드했을 것이다. RTOS MCU에서도 방법은 같다. 다른 점은 libc가 이미지의 가장 큰 덩어리일 때가 많다는 것(A3에서 FreeRTOS 커널 2.4 KB 옆에 printf가 7.7 KB였다)과, RTOS 포트 코드(PendSV 핸들러 같은 asm)가 최적화·LTO와 부딪히는 지점이 있다는 것이다.

1. arm-none-eabi 해부 — triplet 다음 이야기#

🔁 이 절은 Bare-Metal BM F5와 겹친다 (주인: 이 노트).

triplet arm-none-eabi의 뜻(arch-vendor-os-abi, "OS 없음 + Arm EABI")과 크로스 툴체인의 부품 목록(cc1, as, ld, binutils, sysroot)은 EL B1에서 했다. 여기서는 MCU에서만 중요한 두 장치 — multilib과 specs 파일 — 을 본다.

1.1 multilib — 같은 libc를 CPU마다 따로 빌드해 둔 선반#

직관: 툴체인 패키지 안에는 libc가 한 벌이 아니라 수십 벌 들어 있다. Cortex-M0+(Armv6-M, Thumb-1만)용, Cortex-M3(Armv7-M)용, FPU 있는 Cortex-M4F(hard float)용 … 각각 다른 명령어와 다른 부동소수점 호출 규약으로 컴파일된 libc.a가 서로 다른 폴더에 있다. 이걸 multilib이라고 한다. 컴파일러 드라이버는 -mcpu · -march · -mfloat-abi · -mfpu 조합을 보고 그중 한 폴더를 고른다.

39개 중 Cortex-M에 쓰이는 것은 thumb/v6-m/nofp, thumb/v7-m/nofp, thumb/v7e-m/..., thumb/v8-m.base/..., thumb/v8-m.main/..., thumb/v8.1-m.main+mve/hard, +pacbti 계열이다.

예제 1 — 옵션 조합이 어느 선반을 고르나#

무엇을 확인하나: 같은 툴체인에 CPU 옵션만 바꿔 주면 어떤 multilib 폴더(= 어떤 libc.a, libgcc.a)를 쓰는지 본다.

출력에서 볼 것: (1) -mcpu=cortex-m4만 주면 FPU가 있는 칩인데도 nofp 선반을 쓴다 — -mfloat-abi=hard(그리고 -mfpu)를 줘야 FPU 명령과 하드 float ABI로 빌드된 libc가 붙는다. 드론 FC의 자세 제어 루프가 이유 없이 느리다면 제일 먼저 볼 곳이다. (2) Cortex-M55도 -mfloat-abi를 안 주면 nofp다(Helium·FPU 미사용). (3) Cortex-R52는 맞는 선반이 없어서 범용 thumb/v7/nofp로 떨어졌다. Armv8-R 전용 multilib이 이 패키지에 없기 때문이다. 링크는 되지만 R52의 기능을 쓰지 못하는 libc다 — 이런 "조용한 fallback"은 에러가 나지 않으니 -print-multi-directory로 꼭 확인한다(B9 Cortex-R).

함정: 오브젝트마다 -mfloat-abi가 다르면 링커가 uses VFP register arguments, ... does not로 거부한다(EL B1 6절). MCU에서는 컴파일 옵션과 링크 옵션에 같은 CPU 플래그를 넘겨야 링크 때도 같은 선반을 고른다. Makefile에서 링크 줄에 -mthumb -mcpu=를 빼먹으면 어떻게 되는지 직접 해 봤다(오브젝트는 Cortex-M3용으로 컴파일, 링크만 CPU 플래그 없이):

(<lib> = /usr/lib/gcc/arm-none-eabi/14.2.1/../../../arm-none-eabi/lib/ — thumb/v7-m/nofp/가 아닌 기본 선반 ., 즉 ARM 모드 libc다.) Thumb 전용 코어용 오브젝트가 ARM 명령 libc를 부르려 해서 링커가 거부했다. 다행히 이 경우는 링크 에러로 드러난다. "Unknown destination type (ARM/Thumb)"과 "dangerous relocation"은 multilib 불일치의 신호로 기억해 두자. 2.2절의 -nostdlib 에러에도 같은 문구가 나오는데, 그때는 심볼 자체가 없어서 링커가 대상의 명령 집합을 모를 때 나온다.

1.2 specs 파일 — 드라이버의 "링크 레시피"#

직관: gcc 드라이버는 "컴파일러"가 아니라 명령 조립기다(EL B1 3.3의 -###). 어떤 시작 파일(crt0.o)과 어떤 라이브러리를 링크 명령에 붙일지는 GCC 안에 내장된 specs라는 작은 규칙 언어로 정해진다. --specs=파일은 이 규칙을 덮어쓰는 파일을 추가로 읽으라는 뜻이다. MCU 세계에서 자주 보는 것:

specs 파일하는 일 (실제 파일 내용 기준)언제 쓰나
nano.specs-lc → -lc_nano, -lg → -lg_nano로 바꾸고 헤더 경로에 /usr/include/newlib/nano 추가newlib-nano를 쓸 때 (거의 항상)
nosys.specs-lnosys 추가 — "항상 실패하는" syscall 가짜 구현링크만 통과시키고 싶을 때 (위험)
rdimon.specs-lrdimon 추가 + 시작 파일을 rdimon-crt0.o로semihosting으로 printf·파일 I/O
picolibc.specs헤더·라이브러리 경로를 picolibc로, -T 없으면 picolibc.ld, --gc-sections 자동, --printf= 옵션picolibc를 쓸 때

nano.specs의 핵심 줄(VM의 /usr/lib/arm-none-eabi/newlib/nano.specs):

picolibc.specs에는 %{-printf=*:--defsym=vfprintf=__%*_vfprintf} 같은 줄이 있다. --printf=i라고 쓰면 링커에게 "vfprintf라는 이름은 __i_vfprintf(정수 전용판)를 가리켜라"고 시키는 것이다. 이게 3절에서 2 KB짜리 printf를 만드는 장치다.

예제 2 — 옵션마다 링커에 실제로 넘어가는 재료#

무엇을 확인하나: -###로 드라이버가 collect2(ld)에 넘기는 명령을 뽑아서 시작 파일(.o)·라이브러리(-l)·링커 스크립트(-T)만 비교한다.

출력에서 볼 것:

  • nano.specs가 -lc를 -lc_nano로 바꿔치기했다. 라이브러리 그룹이 여러 번 반복되는 것은 specs 파일이 겹쳐 쌓이면서 생긴 것이고 해롭지 않다(--start-group은 서로 부르는 아카이브를 여러 번 훑게 하는 장치 — EL B3 4절).
  • rdimon.specs는 시작 파일까지 rdimon-crt0.o로 바꾼다. 우리 랩처럼 자기 startup.c를 쓰면서 -nostartfiles를 주면 이 crt0이 빠지므로, semihosting 초기화 함수 initialise_monitor_handles()를 직접 불러야 한다(예제 7).
  • picolibc.specs는 -Tpicolibc.ld(picolibc의 기본 링커 스크립트)를 붙인다. 우리가 -T를 주면 specs의 %{!T:...} 조건 때문에 빠진다.
  • 랩 템플릿의 조합 -nostartfiles --specs=nano.specs는 시작 파일 없음 + newlib-nano + libgcc다. crt0.o를 뺀 대신 startup.c의 Reset_Handler가 .data 복사·.bss 0 채우기를 한다(B5).
  • -nodefaultlibs는 라이브러리만, -nostdlib는 시작 파일과 라이브러리를 둘 다 뺀다. -nostdlib이면 libgcc까지 빠진다는 점이 중요하다 — 다음 절.

2. -ffreestanding · -nostdlib는 정확히 무엇을 빼나#

2.1 직관 — 컴파일 단계 옵션 vs 링크 단계 옵션#

두 종류를 섞어서 오해하는 일이 많다.

옵션단계정확한 뜻
-ffreestanding컴파일"표준 라이브러리가 있다고 가정하지 마라" — -fno-builtin을 포함한다. main이 특별하지 않다. printf("x\n") → puts 같은 라이브러리 의미에 기댄 변환을 하지 않는다
-fno-builtin컴파일memcpy·strlen 같은 이름을 컴파일러 내장 함수로 취급하지 않는다
-nostartfiles링크crt0.o·crti.o·crtbegin.o 등 시작 파일을 빼라
-nodefaultlibs링크libc·libgcc 등 기본 라이브러리를 빼라
-nostdlib링크위 둘 다

그리고 GCC 문서가 분명히 적어 두었지만 잘 안 읽히는 문장이 있다: freestanding 환경에서도 GCC는 memcpy, memmove, memset, memcmp가 있다고 가정한다. 구조체 대입·큰 배열 초기화를 컴파일러가 이 함수 호출로 바꿀 수 있기 때문이다. 커널(Linux)도 이 네 함수를 직접 제공한다(EL B1 11절).

2.2 예제 3 — 내가 부르지 않은 memcpy가 생긴다#

무엇을 확인하나: 소스에 memcpy·memset·puts가 하나도 없는데, 컴파일러가 만든 오브젝트는 무엇을 부르는가. 옵션별로 objdump에서 분기 대상만 뽑는다.

출력에서 볼 것:

  • 보통(hosted) -O2: 구조체 대입 → memcpy, 0 채우기 루프 → memset(GCC의 loop distribution 최적화가 "이 루프는 memset이다"를 알아본다), printf("hello\n") → puts(인자가 개행으로 끝나는 상수 문자열이면 같은 동작).
  • -ffreestanding: puts 변환은 사라졌고(라이브러리 의미를 가정 안 함), 이 GCC 14에서는 루프 → memset 변환도 꺼졌다. 그러나 구조체 대입의 memcpy는 그대로다.

그래서 -nostdlib로 링크하면 이렇게 된다. 랩 startup.c의 .data 복사 루프와 .bss 0 채우기 루프(while (dst < &_edata) *dst++ = *src++;)를 -O2(hosted)로 컴파일하고 libc 없이 링크했을 때의 실제 출력이다:

2.3 Don 경험과 연결#

SSD 펌웨어에서 ROM 코드나 부트로더를 만들 때 "libc 없이" 빌드했다면, 아마 벤더 SDK가 memcpy를 이미 넣어 두었을 것이다. 그 memcpy가 왜 필요한지 — 내가 안 불러도 컴파일러가 부르기 때문 — 가 이 절의 요점이다. 그리고 -nostdlib는 libgcc까지 뺀다: Cortex-M0의 정수 나눗셈(__aeabi_uidiv), 64비트 시프트(__aeabi_llsl), 소프트 float(__aeabi_dmul)는 libgcc에 있으므로, -nostdlib를 쓰면 -lgcc를 다시 붙여야 한다(위 명령에도 붙였다).

3. libc 고르기 — newlib · newlib-nano · picolibc · 없음#

3.1 직관 — MCU libc는 "printf 엔진 + malloc + 문자열 함수 묶음"#

Linux의 glibc는 syscall 래퍼·스레드·로케일·동적 로더까지 품은 거대한 층이었다(EL B2). MCU의 libc는 훨씬 단순하다. 실제로 이미지 크기를 좌우하는 것은 세 가지뿐이다.

  1. 포맷 엔진 — printf·snprintf가 공유하는 vfprintf. 정수만이냐, %f(double → 10진 변환 dtoa)까지냐에 따라 2 KB에서 20 KB 이상까지 벌어진다.
  2. stdio 버퍼와 FILE 구조체 — newlib은 stdout에 버퍼를 malloc으로 붙인다. 그래서 printf가 malloc을 끌고 온다(아래에서 확인).
  3. malloc — newlib(full)은 dlmalloc 계열(빈 목록 테이블 __malloc_av_ 1 KB), newlib-nano는 단순 free list, picolibc는 자체 작은 할당기.

그리고 OS가 없으니 libc가 "아래층"에 기대는 부분 — 문자 하나를 어디로 내보내나, 힙 메모리를 어디서 얻나 — 은 내가 채운다. 이게 4절의 syscall stub이다.

3.4 흔한 함정 (libc)#

  • newlib-nano에서 printf("%f")가 아무것도 안 찍거나 빈칸이 나온다 → -u _printf_float(scanf는 -u _scanf_float)을 링크 옵션에 추가. 크기가 13 KB 늘어나는 것을 각오한다.
  • nano.specs를 링크 단계에만 주고 컴파일 단계에는 안 준다 → 헤더(newlib.h의 구성 매크로)는 full newlib 것, 라이브러리는 nano — 대부분 동작하지만 _REENT_SMALL 등 구조체 배치가 달라질 수 있다. 컴파일·링크 양쪽에 같은 specs를 준다.
  • picolibc로 바꾸고 printf가 "undefined reference to stdout" → pico_io.c처럼 stdout을 정의한다.
  • picolibc의 errno는 TLS 변수다(-ftls-model=local-exec가 specs에 들어 있다). 자기 링커 스크립트·시작 코드를 쓰면 .tdata/.tbss 배치와 TLS 포인터 설정(_set_tls)을 직접 챙겨야 한다. 이 노트의 예제는 errno를 쓰는 경로(malloc 실패 등)를 타지 않아서 문제가 드러나지 않았을 뿐이다. Zephyr는 이것을 arch_tls_stack_setup으로 처리한다(예제 16에서 SDK 빌드에만 이 함수가 보인다).

4. syscall stub과 semihosting — printf는 어떻게 핀까지 가나#

🔁 이 절은 Bare-Metal BM F5와 겹친다 (주인: 이 노트).

4.1 직관 — libc의 "아래층 콘센트"#

newlib은 OS 없는 환경을 위해 운영체제가 해 줄 일을 함수 이름 몇 개로 추상화했다. write(2) 대신 _write, brk(2) 대신 _sbrk, exit 대신 _exit … 이 함수들을 libc 안에는 두지 않고 "누군가 제공하라"고 남겨 둔다. 이게 syscall stub이다(Linux의 진짜 syscall이 아니라 이름만 빌린 콘센트). 제공하는 쪽이 libgloss(libnosys, librdimon) 또는 내 코드다.

무엇을 확인하나: (1) stub 없이 newlib-nano printf+malloc을 링크하면 무슨 에러가 나나, (2) --specs=nosys.specs로 "해결"하면 어떻게 되나.

(/build/newlib-Ipb6mw/newlib-4.6.0.20260123/build_nano/arm-none-eabi/thumb/v7-m/nofp/newlib/../../../../../../로 시작하는 긴 경로를 ...로 줄였다.)

출력에서 볼 것:

  • (1) 에러 메시지의 파일 이름이 힌트다: reent/writer.c의 _write_r가 _write를 찾는다. _r이 붙은 재진입 래퍼가 errno를 struct _reent에 담고 진짜 stub을 부르는 구조다. 이 7개를 구현하면 끝난다. _exit이 목록에 없는 것은 이 프로그램이 exit를 부르지 않기 때문이다(시작 코드가 board_exit를 직접 부른다).

4.3 예제 7 — semihosting(rdimon): 디버거를 통해 호스트로 printf#

직관: semihosting은 타깃 CPU가 bkpt 0xab 명령(Thumb; Armv7-M)으로 멈추면, 붙어 있는 디버거(또는 QEMU)가 r0의 "명령 번호"(0x05 = SYS_WRITE, 0x18 = SYS_EXIT …)와 r1의 인자 블록을 읽고 호스트 PC에서 대신 실행해 주는 규약이다. UART 배선 없이 printf와 호스트 파일 열기까지 된다. 랩의 board_exit()도 SYS_EXIT(0x18)으로 QEMU를 끈다.

무엇을 확인하나: UART stub 없이 --specs=rdimon.specs로 printf와 호스트 파일 쓰기를 하고, 디버거가 없는 상황(semihosting 꺼진 QEMU)도 재현한다.

출력에서 볼 것:

  • Cortex-M3 펌웨어가 호스트(VM)의 파일 /var/tmp/rtos/B11/stubs/host.txt를 만들었다. 테스트 벡터를 호스트에서 읽고 결과를 파일로 쓰는 HIL·CI 테스트에 semihosting이 쓰이는 이유다(M9).
  • 크기는 UART stub판(nano, 7~8 KB)보다 약 3 KB 크다 — librdimon에 파일 핸들 테이블과 semihosting 호출 코드가 있다.
  • "20 lines took 743 us"는 QEMU에서만 그렇다. QEMU는 semihosting 처리 시간을 가상 시간에 넣지 않는다. 실제 칩에서는 bkpt마다 CPU가 정지(halt)하고, 디버그 프로브가 USB로 메모리를 읽고, 호스트가 처리한 뒤 재개한다 — 호출당 대략 밀리초 단위다(프로브·소프트웨어에 따라 다르며 이 랩에서는 잴 수 없다). 실시간 태스크 안에서 semihosting printf를 쓰면 deadline이 깨진다. 그동안 인터럽트도 멈춘다.
  • semihosting을 끄고 실행하자 첫 bkpt에서 HardFault가 났다. Armv7-M에서 디버거가 없을 때 bkpt는 HardFault로 승격된다. 그런데 HardFault 핸들러 안의 board_exit()가 또 bkpt를 실행해서 Lockup(HardFault 안에서 또 fault — 더 높일 우선순위가 없음)이 됐다. 실제 칩에서는 lockup → 보통 리셋(칩에 따라 다름)이다. "디버거를 붙이면 되는데 떼면 부팅이 안 된다"의 고전적 원인이다. 양산 빌드에서는 semihosting을 반드시 빼고, 꼭 남겨야 하면 CoreDebug->DHCSR의 C_DEBUGEN 비트로 디버거 연결 여부를 확인한 뒤에만 bkpt를 실행한다.

5. -O 레벨 — 크기와 속도는 한 축이 아니다#

🔁 이 절은 Bare-Metal BM F6와 겹친다 (주인: 이 노트).

5.1 직관과 정의#

-O 레벨은 "최적화 패스 묶음"의 이름이다. MCU에서 의미 있는 차이만 정리하면:

레벨무엇을 켜나 (MCU에서 체감되는 것)쓰는 곳
-O0거의 없음. 모든 변수가 스택 메모리에 있고 매 줄마다 load/store디버그 빌드 (줄 단위 스텝이 정확)
-Og-O1 일부 + 디버그 정보 보존개발 빌드 권장 (GCC 문서)
-O1레지스터 할당, 상수 전파, 간단한 루프 최적화—
-O2-O1 + 인라인, 스케줄링, loop distribution(루프 → memset), 정렬일반 양산 (랩 템플릿 기본)
-O3-O2 + 벡터화·루프 unroll·더 공격적 인라인핫 루프 파일만
-Os-O2에서 크기를 늘리는 것을 끔 (정렬 패딩, unroll, 일부 인라인)플래시가 빠듯한 MCU 양산
-Oz-Os보다 더 공격적으로 크기 (GCC 12부터 지원)극단적 크기 제약

Zephyr는 이것을 Kconfig choice로 고른다: CONFIG_SIZE_OPTIMIZATIONS(기본, -Os), CONFIG_SIZE_OPTIMIZATIONS_AGGRESSIVE(-Oz), CONFIG_SPEED_OPTIMIZATIONS(-O2), CONFIG_DEBUG_OPTIMIZATIONS(-Og), CONFIG_NO_OPTIMIZATIONS(-O0) — Kconfig.zephyr 523~555행과 cmake/compiler/gcc/compiler_flags.cmake의 optimization_size 등 속성이 대응한다. Zephyr 기본이 -Os라는 점이 FreeRTOS 데모 프로젝트들(보통 -O2 또는 벤더 IDE 기본 -O0/-Og)과 다르다.

6. 최적화가 타이밍을 바꾼다 — 지연 루프와 volatile#

🔁 이 절은 Bare-Metal BM F6와 겹친다 (주인: 이 노트).

6.1 직관 — 컴파일러에게 "시간"은 관찰 가능한 동작이 아니다#

C 표준이 정의하는 "관찰 가능한 동작"은 volatile 접근, I/O(라이브러리 호출), 프로그램 종료 시점의 파일 상태뿐이다. "이 루프가 1 ms 걸린다"는 관찰 가능한 동작이 아니다. 그러니 아무 효과 없는 빈 루프는 지워도 된다. 이게 "-O2에서 센서 초기화 지연이 사라졌다"의 정체다.

6.2 예제 10 — 지연 함수 네 가지를 레벨별로#

출력에서 볼 것:

  • delay_bad: -O0 2,241 us → -O1 960 us → -O2 0 us(함수 본문이 bx lr 하나). 같은 소스가 레벨에 따라 2.3배 차이 나다가 결국 사라진다. 이 함수로 "센서 전원 켜고 10 ms 대기"를 했다면, 디버그 빌드에서는 되고 릴리스 빌드에서는 센서가 응답하지 않는다.
  • delay_vol: 지워지지는 않지만 스택 메모리 load/store 루프가 된다(매 반복 ldr·str 2쌍). -O1/-O2 1,920 us, -Os 2,240 us로 레벨마다 여전히 다르다. 그리고 실제 칩에서는 이 load/store가 SRAM·캐시·wait state 영향을 받아 QEMU 숫자와 또 다르다. volatile은 "지우지 마라"이지 "정확한 시간"이 아니다.
  • delay_nop: asm volatile("nop")은 지워지지 않지만 루프 오버헤드는 레벨마다 다르다(1,280~2,561 us). 그리고 Armv7-M 아키텍처 매뉴얼은 NOP에 대해 "실행 시간을 늘린다는 보장이 없다(늘리거나, 그대로이거나, 줄일 수도 있다)"고 적어 두었다 — nop은 지연용이 아니다.
  • delay_timer: 모든 레벨에서 1,000~1,002 us. 하드웨어 시계(여기서는 TIMER1, 실칩에서는 DWT CYCCNT·SysTick·HW 타이머)를 읽는 지연만이 최적화와 무관하다. RTOS에서는 ms 단위면 vTaskDelay/k_msleep(CPU를 양보), us 단위면 타이머 폴링 또는 Zephyr k_busy_wait()(kernel/busy_wait.c에서 k_cycle_get_32()를 읽으며 돈다)를 쓴다.

6.3 volatile이 필요한 다른 곳, 필요 없는 곳#

같은 원리가 RTOS 코드에서 세 군데 나온다.

상황-O2에서 일어나는 일올바른 방법
ISR이 세우는 플래그를 태스크가 while (!flag);로 기다림load를 루프 밖으로 끌어올려 무한 루프volatile + 가능하면 세마포어/알림으로 블로킹 (D 모듈)
주변장치 레지스터 읽기·쓰기같은 레지스터 두 번 쓰기가 한 번으로 합쳐짐레지스터 포인터는 항상 volatile (랩 REG32 매크로)
태스크 간 공유 변수 (락으로 보호)락 함수 호출이 컴파일러 배리어 역할을 하므로 문제 없음volatile은 원자성·순서를 주지 않는다 — 뮤텍스나 C11 atomics (D8)

FreeRTOS도 이 원리를 쓴다: pxCurrentTCB는 TCB_t * volatile로 선언되어 있고(tasks.c 465행), PendSV asm이 메모리에서 직접 읽는다.

7. LTO — 파일 경계를 넘는 최적화와 그 함정#

🔁 이 절은 Bare-Metal BM F6와 겹친다 (주인: 이 노트).

7.1 직관 — "링크 때 한 번 더 컴파일"#

보통 컴파일은 파일 하나씩 한다. queue.c를 컴파일할 때 컴파일러는 tasks.c의 xTaskRemoveFromEventList가 얼마나 짧은지 모르니 인라인할 수 없다. LTO(Link Time Optimization, -flto)는 .o에 기계어 대신(또는 함께) GCC 중간 표현(GIMPLE)을 넣어 두고, 링크 때 프로그램 전체를 한 번에 다시 최적화한다. 효과: 파일을 넘는 인라인, 안 쓰는 함수·인자 제거, 상수 전파(.constprop 복제본).

대가: (1) asm 문자열 안에서만 이름이 불리는 함수는 "아무도 안 부른다"고 판단해 지운다. (2) 빌드 시간·메모리 증가. (3) 디버깅 시 함수가 다른 함수 안으로 녹아들어 백트레이스가 낯설어진다. (4) 링커 스크립트에서 파일 이름으로 섹션을 배치하는 규칙(*foo.o(.text*))이 LTO 뒤에는 파일 이름이 ltrans0.ltrans.o로 바뀌어 맞지 않는다.

그림 5 — LTO 실패의 구조. HardFault_Handler는 naked 함수라 본문이 asm 문자열(b board_hardfault)뿐이다. LTO는 C 호출 그래프만 보므로 board_hardfault를 "아무도 안 부른다"고 지우고, 링커는 asm이 남긴 참조를 풀 수 없다.

7.3 FreeRTOS는 LTO를 어떻게 견디나#

PendSV 핸들러(portable/GCC/ARM_CM3/port.c의 xPortPendSVHandler, naked)는 asm 안에서 bl vTaskSwitchContext를 부르고 ldr r3, =pxCurrentTCB로 TCB 포인터를 읽는다. 둘 다 asm 문자열 안의 이름이다. 그런데도 FreeRTOS + LTO는 링크됐다. 소스를 보면 두 가지 장치가 있다.

pxCurrentTCB는 used로, vTaskSwitchContext는 절대 실행되지 않는 자리에서 C로 한 번 불러서 LTO가 보게 만든다. 우리 랩의 board_hardfault에는 이런 장치가 없었을 뿐이다. 새 포트·새 핸들러를 쓸 때 asm에서만 부르는 C 함수에는 used를 붙인다가 규칙이다.

Zephyr는 Kconfig CONFIG_LTO로 켠다. 조건이 있다: depends on !(GEN_ISR_TABLES ... ) || ISR_TABLES_LOCAL_DECLARATION — ISR 테이블을 빌드 후 단계에서 생성하는 기본 방식은 LTO와 맞지 않아서 CONFIG_ISR_TABLES_LOCAL_DECLARATION=y를 함께 줘야 한다(Kconfig.zephyr 557행). 예제 16의 앱으로 재 보았다:

8. --gc-sections — 안 쓰는 함수 버리기, 그리고 섹션 앵커#

🔁 이 절은 Bare-Metal BM F6와 겹친다 (주인: 이 노트).

8.1 직관#

링커가 버릴 수 있는 최소 단위는 입력 섹션이다. 보통 tasks.c의 모든 함수는 .text 섹션 하나에 들어가므로, xTaskCreate 하나만 써도 tasks.c 전체가 따라온다. -ffunction-sections는 함수마다 .text.함수이름 섹션을, -fdata-sections는 전역 변수마다 .data.이름/.bss.이름을 만든다. 그다음 -Wl,--gc-sections가 뿌리(ENTRY 심볼, KEEP()된 섹션 — 벡터 테이블)에서 참조를 따라가며 닿지 않는 섹션을 버린다. 링커 스크립트에서 벡터 테이블을 KEEP(*(.isr_vector))로 감싸는 이유가 이것이다(B5).

8.2 예제 12 — 무엇이 버려졌나, 그리고 이상한 3%#

출력에서 볼 것: 289개 섹션이 버려졌다. event_groups.o·stream_buffer.o는 통째로(이 앱은 안 쓴다), queue.o에서는 뮤텍스·세마포어·ISR 버전 함수들이 빠졌다. FreeRTOS를 "필요한 파일만 골라 빌드"할 필요가 없는 이유가 이것이다 — 다 넣고 gc에게 맡기면 된다. libc_nano.a에서도 96개가 빠졌다(newlib은 이미 함수 단위 섹션으로 빌드되어 있다).

이제 예제 11의 이상한 숫자 — gc를 끄면 3% 빠르다 — 를 풀어 보자. 가설: -fdata-sections가 ARM의 섹션 앵커(section anchors) 최적화를 끈다. 섹션 앵커는 한 파일의 전역 변수들을 한 블록으로 보고 기준 주소 하나를 레지스터에 올린 뒤 [r3, #오프셋]으로 접근하는 최적화다. 변수마다 섹션이 따로면 링커가 순서를 바꿀 수 있으므로 오프셋을 고정할 수 없어서, 변수마다 주소를 리터럴 풀에서 따로 읽어야 한다.

출력에서 볼 것: 가설이 맞다. -fno-section-anchors만 줘도 정확히 같은 57,108 us가 나오고 코드가 584 B 커진다. -fdata-sections를 켠 빌드는 모두 57,108 us, 끈 빌드는 모두 55,227 us다. 그리고 -ffunction-sections만 쓰고 -fdata-sections를 뺀 빌드가 가장 작고(12,308 B) 빠르다. 이 앱에서는 버릴 전역 변수가 거의 없어서 -fdata-sections의 이득(안 쓰는 변수 제거)보다 손해(앵커 상실)가 컸다. 일반론은 아니다 — 안 쓰는 큰 테이블·버퍼가 많은 코드(벤더 HAL, 프로토콜 스택)에서는 -fdata-sections가 RAM·FLASH를 크게 줄인다. 결론: 둘 다 켜는 것이 안전한 기본값이지만, 크기·속도가 중요하면 두 조합을 재 보라.

8.3 gc의 함정#

  • KEEP 없는 벡터 테이블: gc가 .isr_vector를 버려서 리셋 벡터가 비고, 칩이 부팅하지 않는다. KEEP(*(.isr_vector)) 필수.
  • 링커 스크립트 배열 패턴(Zephyr의 iterable section, initcall 테이블처럼 __start_xxx/__stop_xxx 사이를 순회하는 섹션): 아무도 이름으로 부르지 않으므로 KEEP이 없으면 사라진다. EL B3 11.2의 initcall 흉내와 같은 원리다.
  • __attribute__((used))는 링커 gc를 막지 못한다. used는 "컴파일러야 지우지 마라"이고, 링커의 gc는 섹션 참조만 본다. GCC 11에는 링커 gc까지 막는 retain 속성(ELF 섹션 플래그 SHF_GNU_RETAIN)이 생겼지만, 이 arm-none-eabi 툴체인에서 확인해 보니 받아들이지 않았다:

nm이 아무것도 찍지 않았다 — 두 함수 모두 gc로 사라졌고, retain은 무시됐다(경고는 이 확인의 일부라 일부러 남겼다). 그러니 MCU에서 "참조 없이 남겨야 하는 것"(벡터 테이블, 버전 문자열, 부트로더가 읽는 헤더, iterable 테이블)은 링커 스크립트의 KEEP() 이나 -Wl,--undefined=이름으로 붙잡는다.

9. 스택 사용량 — -fstack-usage, -Wstack-usage=, 그리고 정적 분석이 못 보는 것#

🔁 이 절은 Bare-Metal BM F6와 겹친다 (주인: 이 노트). 태스크 스택 크기 산정 전체(high water mark, 카나리, MPU 가드, PSPLIM)는 F3이 주인이다 — 여기서는 툴체인이 주는 도구만 본다.

9.1 직관#

RTOS에서는 태스크마다 스택을 xTaskCreate(..., 256, ...)(word 단위)나 K_THREAD_DEFINE(..., 1024, ...)(바이트)로 미리 정해 준다. 너무 작으면 오버플로(옆 TCB·힙을 덮어씀), 너무 크면 RAM 낭비다. GCC는 함수마다 "이 함수의 프레임은 몇 바이트"를 계산해서 알려 줄 수 있다.

옵션결과
-fstack-usage오브젝트 옆에 파일.su — 함수별 바이트 static/dynamic/bounded
-Wstack-usage=N프레임이 N 바이트를 넘거나 상한이 없는(VLA·alloca) 함수에 경고
-fcallgraph-info=su파일.ci — 호출 그래프 + 프레임 크기 (VCG 형식). 경로 합산의 재료

중요한 한계: .su는 함수 하나의 프레임이다. 호출 경로 전체(main → fmt → snprintf → vfprintf …)를 더해야 태스크 스택이 되고, libc는 -fstack-usage 없이 빌드되어 있어서 그 부분은 비어 있다. 그리고 인터럽트가 그 위에 쌓는 하드웨어 프레임(Cortex-M 8워드 = 32 B, FPU 사용 시 26워드 = 104 B — B2, B6)도 들어가지 않는다.

11. GCC vs Clang/LLD, 그리고 Arm Toolchain for Embedded#

11.1 Clang으로 Cortex-M 빌드하기#

Clang은 하나의 바이너리가 모든 타깃을 지원한다(EL B1 8절). Cortex-M에는 --target=thumbv7m-none-eabi -mcpu=cortex-m3 -mfloat-abi=soft를 주고, libc와 libgcc는 GCC 툴체인 것을 빌려 쓴다(Ubuntu clang에는 bare-metal Arm용 libc·compiler-rt가 없다). 링커는 LLD(ld.lld)를 직접 부르고 우리 링커 스크립트를 그대로 쓴다.

LLD는 GNU ld와 달리 아카이브 순서·--start-group이 필요 없다(한 번 본 아카이브의 심볼을 기억한다). GNU ld 문법의 링커 스크립트(MEMORY, > RAM AT > FLASH, NOLOAD, ASSERT)는 이 정도 수준이면 그대로 동작했다.

  • Clang에서는 -Os와 -Oz가 크게 다르다(FreeRTOS 13,140 → 11,580 B). GCC 14는 둘이 같았다. Clang -Oz의 FreeRTOS는 GCC -Os보다 1.2% 작고, 시간도 가장 짧았다(55,736 us). 반대로 CRC는 -Oz가 가장 느렸다(9,700 us).
  • 결론: "어느 컴파일러가 낫다"는 코드와 레벨에 따라 뒤집힌다. 툴체인을 바꿀 때는 자기 이미지로 크기·핵심 경로 시간을 재야 한다. 시간 숫자는 QEMU icount(명령 수 비례)라 실제 Cortex-M3의 파이프라인·플래시 wait state 효과는 빠져 있다.

11.3 Arm Toolchain for Embedded (ATfE)#

Arm은 오랫동안 GCC 기반 "GNU Arm Embedded Toolchain"(이 랩 패키지의 원류, 버전 이름 14.2.rel1)과 상용 armclang(Arm Compiler 6)을 냈다. 2025년부터는 LLVM 기반의 Arm Toolchain for Embedded(ATfE) 를 공개 배포한다. 2026-10 웹 확인 내용:

  • ATfE는 Clang/LLD/LLVM binutils + picolibc(C 라이브러리) + LLVM libc++로 구성된다. 무료·커뮤니티 지원판이 ATfE, 같은 기능에 Arm 상용 지원이 붙은 것이 ATfEP(Professional)다.
  • GitHub arm/arm-toolchain 릴리스 페이지 기준 최신은 release-23.1.0-ATfE(9월 10일, "now based on LLVM 23.1.0"), 그 전이 22.1.0(3월 23일), 21.1.1, 21.1.0, 20.1.0이다. 페이지에 연도가 표시되지 않지만 LLVM 22/23 릴리스 시기로 보아 22.1.0이 2026년 3월, 23.1.0이 2026년 9월이다(연도는 추정).
  • ATfEP 22.1.0이 Arm Development Studio 2026.0에 포함되었다(Arm 커뮤니티 블로그, 2026-06-19 게시) — Bare-Metal 나침반 §5의 기록과 일치한다. 같은 글에서 LLVM-libc는 "평가용 선택 오버레이"로 제공된다.
  • Arm 블로그(2026-03-09)는 LLVM-libc가 앞으로 ATfE의 기본 C 라이브러리가 될 예정이며, picolibc를 쓰는 프로젝트는 일부 이전 작업이 불가피하니 미리 옮겨 보라고 권한다. 전환 시점(어느 버전부터인지)은 확인 못 함.
  • Zephyr 문서에는 ATfE를 툴체인 변형으로 쓰는 페이지(develop/toolchains/arm_toolchain_for_embedded.rst)가 v4.4.2 소스 트리에 있다.

이 VM에는 ATfE가 설치되어 있지 않아서 직접 실행하지 않았다. Ubuntu Clang 21 + newlib-nano 조합(예제 15)이 "LLVM 계열 컴파일러로 Cortex-M을 빌드하면 크기·속도가 어떻게 달라지나"의 대리 실험이다.

12. RTOS가 툴체인에 요구하는 것#

12.1 FreeRTOS — 포트 디렉터리가 컴파일러별로 나뉜 이유#

FreeRTOS 커널의 C 코드(tasks.c, queue.c …)는 표준 C라서 어느 컴파일러로도 된다. 컴파일러마다 다른 것은 포트다: 컨텍스트 스위치(PendSV)·첫 태스크 시작(SVC)·크리티컬 섹션은 어셈블리이고, 어셈블리를 C에 섞는 문법이 컴파일러마다 다르기 때문이다. 소스 트리 portable/ 아래 폴더가 컴파일러 이름(GCC, IAR, RVDS, ARMClang, Keil, CCS, Tasking …)인 이유다.

포트 폴더 (ARM_CM3)파일asm을 쓰는 방식
GCC/ARM_CM3port.c, portmacro.h__attribute__((naked)) 함수 안의 GNU 확장 inline asm (__asm volatile("..." :: "i"(...))) — Clang도 받아들인다(예제 15)
IAR/ARM_CM3port.c, portasm.s, portmacro.h핸들러를 별도 어셈블리 파일 portasm.s에 IAR 어셈블러 문법으로
RVDS/ARM_CM3port.c, portmacro.h옛 Arm Compiler 5(armcc)의 __asm void 함수() { ... } 임베디드 어셈블러

실무 함의: (1) Keil/armclang(Arm Compiler 6)은 Clang 기반이라 GCC 포트를 쓴다 — portable/ARMClang/ 폴더에는 코드 없이 Use-the-GCC-ports.txt 한 장만 있고 "The FreeRTOS GCC port layer also builds and works with the ARMClang compiler"라고 적혀 있다. RVDS 포트는 옛 armcc 5 전용이다. (2) 포트를 고르면 portmacro.h의 portDONT_DISCARD, portFORCE_INLINE 같은 컴파일러 속성 매크로도 같이 정해진다. LTO를 견디게 하는 used가 여기서 온다(7.3). (3) 새 컴파일러로 옮길 때 가장 먼저 깨지는 것은 PendSV asm의 레지스터 제약·문법이고, 그다음이 링커 스크립트 문법이다(IAR .icf, Keil scatter file은 GNU ld 스크립트와 완전히 다르다).

12.2 Zephyr — 툴체인 변형(toolchain variant)#

Zephyr는 CMake 변수 ZEPHYR_TOOLCHAIN_VARIANT로 툴체인을 고른다. 소스의 cmake/toolchain/ 아래 폴더가 그 목록이다: zephyr(Zephyr SDK), gnuarmemb(외부 GNU Arm Embedded, GNUARMEMB_TOOLCHAIN_PATH로 위치 지정), armclang, iar, host(native_sim용, host/llvm 포함), cross-compile, arcmwdt, xcc, xt-clang, oneApi. 랩의 rtos-zbuild는 mps2 보드에 기본으로 gnuarmemb(Ubuntu arm-none-eabi-gcc)를 쓰고, ZTC=zephyr면 SDK의 arm-zephyr-eabi-gcc를 쓴다.

출력에서 볼 것 — "툴체인을 바꾸면 컴파일러만 바뀌는 게 아니다":

  1. C 라이브러리의 출처가 바뀐다. gnuarmemb에서는 Zephyr가 picolibc를 모듈 소스에서 직접 빌드하고(PICOLIBC_USE_MODULE, 위치 인자 %1$d 지원 IO_POS_ARGS 켬 → skip_to_arg 284 B), SDK에서는 툴체인에 미리 빌드된 picolibc를 쓴다(PICOLIBC_USE_TOOLCHAIN, POS_ARGS 없음). printf 엔진이 460 B 차이 난다.
  2. TLS 지원이 바뀐다. SDK 툴체인은 thread-local storage를 지원해서 errno가 TLS 변수가 되고, 스레드 생성 때 arch_tls_stack_setup이, 접근 때 __aeabi_read_tp가 들어온다. PendSV(z_arm_pendsv)도 TLS 포인터 교체 때문에 12 B 커졌다. 3.4절의 picolibc TLS 이야기가 여기서 다시 나온다.
  3. 컴파일러 버전(14.2.1 vs 14.3.0)과 성능 차이는 1.4%(cycles 889,027 vs 901,040)로 작다.
  4. 두 빌드 모두 -std=c17 이고 __STDC_VERSION__ = 201710이다. Zephyr 4.4 마이그레이션 가이드: "Zephyr now officially defaults to C17 (ISO/IEC 9899:2018) as its minimum required C standard version", 그보다 낮은 CONFIG_STD_C99·CONFIG_STD_C11은 deprecated(Kconfig.zephyr에서 select DEPRECATED). 오래된 벤더 툴체인(C11까지만 지원)을 쓰던 프로젝트가 4.4로 올릴 때 걸리는 부분이다. 참고로 GCC 15부터는 C 기본값이 gnu23이므로, Zephyr처럼 -std=를 명시하지 않는 빌드는 GCC 15로 올릴 때 bool·true가 키워드가 되는 등의 변화를 만난다(BM F1의 메모).

실무 교훈: 팀에서 CI와 개발자 PC의 툴체인 변형을 하나로 맞춘다(보통 Zephyr SDK). 다르면 크기·printf 기능·errno 구현이 달라서 "내 PC에서는 들어가는데 CI에서는 FLASH 넘침"이 생긴다. Zephyr 4.4가 처음 지원하는 SDK 1.0은 GNU 툴체인을 올렸고 Clang/LLVM을 실험적으로 포함한다(릴리스 노트). 이 랩의 SDK에는 gnu/만 설치되어 있어서 LLVM 변형은 시험하지 못했다.

  • portable/ARMClang/Use-the-GCC-ports.txt — 컴파일러별 포트 폴더 구조의 예외(12.1).

  • Kconfig.zephyr — STD_C choice(기본 STD_C17, C99/C11은 deprecated), 최적화 choice(523~555행), LTO(557행, ISR 테이블 조건).

  • arch/arm/core/tls.c의 arch_tls_stack_setup() — TLS 지원 툴체인일 때 새 스레드 스택 꼭대기에 TLS 블록을 만든다(예제 16에서 SDK 빌드에만 64 B로 등장).

연결: 컨텍스트 스위치 asm은 C3/G2, 첫 태스크 시작은 C3, 링커 스크립트·시작 코드는 B5, 재진입 libc는 F7, 스택 산정은 F3, Zephyr 빌드 시스템은 H2.

14.2 드론 비행 제어기 — -O2로 바꾸자 IMU 초기화 실패#

증상: 디버그 빌드(-O0)는 정상, 릴리스(-O2)에서 IMU WHO_AM_I 읽기 실패. 원인 후보 1순위는 6절의 빈 지연 루프(데이터시트의 "power-on 후 10 ms 대기"를 for 루프로 구현) — -O2에서 0 us가 된다. 2순위는 레지스터 포인터에 volatile이 빠진 드라이버, 3순위는 배리어 누락(J5). 확인법: objdump -d로 지연 함수가 bx lr 하나인지 본다. 수정: vTaskDelay(pdMS_TO_TICKS(10))(스케줄러 시작 후) 또는 HW 타이머 기반 delay_us().

14.3 센서 허브 MCU (Zephyr) — CI와 내 PC의 바이너리가 다르다#

예제 16 그대로다. CI는 Zephyr SDK, 개발자는 gnuarmemb로 빌드해서 336 B 차이와 errno 구현(TLS 여부) 차이가 났다. 해결: west build가 쓰는 변형을 ZEPHYR_TOOLCHAIN_VARIANT=zephyr로 저장소에 고정하고, CI에서 bloaty new.elf -- main.elf(또는 symdiff.py)로 PR마다 크기 변화를 댓글로 단다.

14.4 SSD 펌웨어 경험을 RTOS 말로#

SSD 컨트롤러 펌웨어는 대개 벤더 SDK의 자체 런타임(작은 printf, 자체 memcpy)을 쓰고 libc를 거의 링크하지 않는다 — 이 노트의 "libc 없음(848 B)" 행이다. 면접에서 "우리 SSD FW는 newlib을 안 썼고, 로그는 포맷 문자열 ID만 내보내는 방식이었다"라고 말하면 Zephyr의 딕셔너리 로깅(K6)과 정확히 같은 아이디어다. 또 SSD에서 ITCM/DTCM 예산을 map 파일로 관리했던 경험은 10절의 map 파서와 같은 일이다.

16. 면접에서 이렇게 말한다#

Q. "Our firmware is 2 KB over the flash limit. Walk me through what you would do."

A. 측정부터 한다. map 파일을 오브젝트·아카이브 단위로 합쳐서 상위 항목을 보면 대개 libc(printf·float)가 1위다. 그다음 --gc-sections가 켜져 있는지, -Os와 LTO를 써 봤는지 확인한다. 직접 재 보니 FreeRTOS 데모에서 gc만으로 30 KB → 12.6 KB, -Os+LTO로 다시 12%가 줄었다. 그래도 모자라면 기능을 끄거나 로그를 딕셔너리 방식으로 바꾼다.

I start by measuring, not guessing. I generate the map file and rank input sections by object and archive — in practice the C library, especially printf with float support, is usually at the top. Then I check the cheap global switches: function sections with --gc-sections, -Os, and LTO. On a FreeRTOS demo I measured, gc-sections alone took the image from 30 KB to 12.6 KB, and -Os plus LTO saved another 12%. Only after that do I trim features or move logging to a dictionary-based scheme where format strings stay on the host.

꼬리 질문: "Why not just use -O3?" → 커널·제어 코드에서는 크기만 16% 늘고 시간은 1% 미만 줄었다(예제 9). 핫 루프 파일만 따로.

Q. "What's the difference between newlib, newlib-nano and picolibc?"

A. 셋 다 bare-metal용 C 라이브러리다. newlib은 기능이 완전하지만 printf 하나에 30 KB, RAM 2 KB. nano는 같은 소스를 크기 위주로 빌드한 것으로 float printf를 기본에서 뺐다(7 KB). picolibc는 버퍼 없는 tinystdio라 RAM을 거의 안 쓰고, 정수 전용 printf는 2 KB, double printf도 nano+float보다 12 KB 작다. Zephyr와 Arm의 새 LLVM 툴체인이 picolibc를 기본으로 쓴다.

All three are C libraries for bare-metal targets. Full newlib is feature-complete but heavy: a single printf cost me about 30 KB of flash and 2 KB of RAM on a Cortex-M3. Newlib-nano is the same code built for size, with float formatting removed by default, so printf is around 7 KB. Picolibc uses tinystdio with no stdio buffers, so it uses almost no RAM; its integer-only printf is about 2 KB, and even full double printf is 12 KB smaller than nano with float enabled. Zephyr and Arm's LLVM-based embedded toolchain both default to picolibc.

꼬리 질문: "Is newlib thread-safe under an RTOS?" → 락 훅(__malloc_lock)이 기본으로 빈 함수(2바이트)다. FreeRTOS configUSE_NEWLIB_REENTRANT + 락 구현이 필요하다(F7).

Q. "What are syscall stubs and what is semihosting?"

A. newlib은 출력·힙 같은 OS 기능을 _write, _sbrk 같은 함수 이름으로 남겨 두고 내가 구현하게 한다. _write를 UART에 연결하면 printf가 UART로 나간다. semihosting은 bkpt 0xab로 CPU를 멈추고 디버거가 호스트에서 대신 I/O를 해 주는 방식이라 배선 없이 파일까지 쓸 수 있지만, 호출마다 CPU가 정지하고 디버거가 없으면 HardFault가 난다 — 실제로 QEMU에서 Lockup까지 재현했다. 그래서 테스트 빌드 전용이다.

Newlib leaves the OS-dependent pieces — writing bytes, growing the heap, exiting — as a small set of functions like _write and _sbrk that the firmware provides. If _write sends bytes to a UART, printf goes to the UART. Semihosting instead executes a BKPT 0xAB instruction; an attached debugger services the request on the host, so you even get host file I/O with no wiring. But each call halts the core, and without a debugger the breakpoint escalates to a HardFault — I reproduced that as a lockup in QEMU. So semihosting is for test builds only.

Q. "Why does my busy-wait delay loop disappear at -O2, and is volatile the fix?"

A. 시간은 C의 관찰 가능한 동작이 아니라서 빈 루프는 지워도 된다. 실제로 -O2에서 함수가 bx lr 하나가 됐다. volatile 카운터는 지워지지는 않지만 스택 load/store 루프가 되어 레벨마다 시간이 다르다(1,920~2,241 us). 정답은 하드웨어 시계를 읽는 지연이나 RTOS 지연 API다 — 이건 모든 레벨에서 1,000 us로 같았다.

Elapsed time is not observable behavior in C, so an empty loop is dead code and the compiler may delete it — at -O2 my delay function compiled to a single return. Making the counter volatile keeps the loop but turns it into memory loads and stores whose cost still changes with optimization level and memory speed. The robust fix is to wait on a hardware timer or cycle counter, or use the RTOS delay so the CPU can run other tasks; my timer-based delay measured the same at every optimization level.

Q. "What can go wrong when you enable LTO on RTOS firmware?"

A. LTO는 C 호출 그래프만 보기 때문에 asm 문자열에서만 부르는 함수를 지운다. 랩 템플릿에 -flto를 켜자 HardFault 핸들러가 부르는 C 함수가 사라져 링크가 실패했다. FreeRTOS는 pxCurrentTCB에 used를 붙이고 vTaskSwitchContext를 C에서 한 번 일부러 불러서 이 문제를 피한다. 고친 뒤에는 -Os+LTO로 크기 −12%, 시간 −11%였다. 또 함수가 인라인되어 사라지니 디버깅 중단점 위치가 바뀐다.

LTO only sees the C-level call graph, so a function referenced only from an inline-assembly string looks unused and gets dropped. When I turned on -flto for a lab template, the C function called from the naked HardFault handler disappeared and the link failed. FreeRTOS avoids this by marking pxCurrentTCB as used and calling vTaskSwitchContext once from C in the port. After fixing it with the used attribute, -Os plus LTO gave 12% less flash and 11% faster queue round trips. The other cost is debuggability: functions get inlined away, so breakpoints and backtraces look different.

Q. "How do you size a task stack?"

A. 세 가지를 합친다. -fstack-usage와 호출 그래프(puncover)로 정적 최악 경로, 스택 칠하기나 uxTaskGetStackHighWaterMark로 실측, 그리고 인터럽트·FPU 프레임 여유. 정적 분석은 libc를 모른다 — snprintf 하나 부르는 함수가 정적 120 B, 실측 532 B였다.

I combine three sources: static analysis with -fstack-usage plus the call graph — puncover does the path sum — runtime measurement by painting the stack or reading the high-water mark, and a margin for exception frames, especially the 104-byte FPU frame. Static analysis can't see into a precompiled libc: a function that called snprintf showed 120 bytes statically but used 532 bytes when I measured it.

Q. "GCC or Clang for Cortex-M?"

A. 코드와 레벨에 따라 뒤집힌다. 같은 FreeRTOS 데모에서 Clang -O2는 GCC보다 28% 컸지만 Clang -Oz는 GCC -Os보다 조금 작고 빨랐다. CRC 커널에서는 Clang -O2가 27% 빨랐다. 그래서 툴체인을 바꿀 때는 자기 이미지로 크기와 핵심 경로를 잰다. Arm은 LLVM 기반 ATfE(picolibc 포함)를 배포하고 있고, FreeRTOS GCC 포트는 Clang으로도 그대로 빌드된다.

It depends on the code and the level, and the answer flips. On the same FreeRTOS demo, Clang at -O2 was 28% larger than GCC, but Clang at -Oz was slightly smaller and faster than GCC at -Os, while on a CRC kernel Clang -O2 was 27% faster. So when switching toolchains I measure my own image — size and the critical paths. Arm now ships the LLVM-based Arm Toolchain for Embedded with picolibc, and the FreeRTOS GCC port builds unchanged with Clang.

꼬리 질문: "What does Zephyr require?" → 4.4부터 C17이 최소 표준(C99/C11은 deprecated). 툴체인 변형에 따라 libc 빌드 방식과 TLS 지원이 달라진다(예제 16).

19. 요약 & 체크리스트#

MCU 툴체인은 "컴파일러"가 아니라 드라이버 + specs + multilib + libc + libgloss + libgcc + 링커 스크립트의 묶음이고, -###·-print-multi-directory로 무엇이 실제로 링크되는지 확인할 수 있다. 같은 printf 프로그램이 libc에 따라 0.8 KB(자체 포맷터)·2.9 KB(picolibc 정수)·8.6 KB(newlib-nano)·22 KB(nano + float)·37.5 KB(newlib)로 45배까지 벌어졌다. libc의 아래층은 syscall stub(_write·_sbrk)이고, nosys.specs는 조용히 실패하며 semihosting은 디버거 없이 HardFault가 된다. 최적화에서는 RTOS 이미지 전체가 -O0 → -O2로 크기 −28%·시간 −46%, -Os는 거의 공짜, --gc-sections가 가장 큰 절약(−59%), -Os + LTO가 크기·속도를 함께 12%·11% 줄였다. 대신 LTO는 asm에서만 부르는 함수를 지우고(used로 막는다), 최적화는 빈 지연 루프를 지운다(HW 시계로 기다린다). 크기는 map 파일을 오브젝트·아카이브 단위로 합쳐서(mapsize.py, bloaty, puncover) 찾고, 스택은 .su + 실측으로 정한다. Zephyr에서는 툴체인 변형이 libc 빌드 방식과 TLS까지 바꾸므로 CI와 PC를 맞춘다.
