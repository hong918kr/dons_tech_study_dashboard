이 노트를 다 읽으면: 처음 보는 RTOS 커널을 "자료구조 → 핫 패스 → API 하나 끝까지 → 실행으로 확인" 순서로 읽는 방법을 손에 익힌다 · FreeRTOS의 매크로 미로(configXXX · traceXXX · portXXX · mtCOVERAGE_TEST_MARKER · PRIVILEGED_FUNCTION)를 gcc -E로 걷어 내고 "이 설정에서 실제로 도는 코드"만 읽을 수 있다 · QEMU + gdb 중단점의 backtrace로 xTaskCreate · 블로킹 send · FromISR · tick · PendSV, 그리고 Zephyr의 k_thread_create · k_sem_give · k_sleep · ISR 종료 · sys_clock_announce 경로를 직접 찍고 호출 그래프로 그릴 수 있다 · 함수 크기와 분기 수로 "먼저 읽을 15개"를 고르고 2주 읽기 계획을 세울 수 있다 왜 필요한가: 시니어 펌웨어 면접의 "FreeRTOS에서 xQueueSend가 블록되면 내부에서 무슨 일이 일어나나?", "Zephyr는 PendSV에서 무엇을 하나?" 같은 질문은 소스를 직접 읽어 본 사람만 함수 이름과 순서로 답한다. 입사 후에는 벤더 SDK에 딸려 온 낯선 포트, 수정된 커널, "가끔 태스크가 안 깬다" 같은 버그를 만났을 때 커널 소스를 30분 안에 읽어 내는 능력이 곧 디버깅 속도다 Don 기준 난이도: 큰 C 코드베이스 읽기 · JTAG로 콜 스택 보기 · objdump는 SSD 펌웨어에서 매일 했다 / 새로 배울 부분은 FreeRTOS 특유의 매크로 층, "태스크 쪽 스택"과 "핸들러 쪽 스택"이 끊어진 backtrace를 읽는 법, 두 커널이 스케줄링 결정을 서로 다른 시점에 한다는 사실, 그리고 --gc-sections가 gdb의 함수 이름을 속이는 함정 선행 노트: A3(RTOS 구성 요소 — 소스 트리 줄 수 · footprint는 거기서 끝냈다), A4(태스크 모델), B2(예외 진입 · 복귀 — <signal handler called>의 정체), B4(SysTick · PendSV · SVC), C2(PendSV 19개 명령), C7(크리티컬 섹션). 같은 모듈의 C1(자료구조) · C3(첫 태스크 시작) · C5(tick) · C8(커널 진입 경로)과는 ID로만 연결한다

0. 큰 그림 — 왜 "읽는 법"을 따로 배우나#

Don이 SSD 컨트롤러 팀에 처음 들어갔을 때를 떠올려 보자. 수십만 줄짜리 펌웨어가 있고, 첫 버그 티켓은 "가끔 명령 하나가 타임아웃 난다"였다. 그때 처음부터 끝까지 파일을 읽지 않았을 것이다. 대신 명령 큐 구조체가 어떻게 생겼는지 먼저 보고, 명령이 들어와서 나가는 한 경로(doorbell ISR → 디스패처 → NAND 작업 → 완료 ISR)를 JTAG 중단점으로 따라갔을 것이다. 커널 소스 읽기도 똑같다. 다만 RTOS 커널에는 세 가지 특별한 장애물이 있다.

  1. 매크로 층: FreeRTOS tasks.c는 8967줄인데, 이 노트의 설정에서 실제로 컴파일되는 줄은 3226줄이다(§3에서 잰다). 나머지는 주석, 다른 설정용 #if 가지, 빈 trace 훅이다.
  2. 끊어진 콜 스택: 컨텍스트 스위치는 "함수 호출"이 아니다. 태스크는 PendSV 예외로 빠져나가고, 다른 태스크의 스택으로 돌아온다. 그래서 backtrace가 PendSV에서 뚝 끊긴다. 어디서 끊기는지 알아야 그래프를 이어 붙일 수 있다.
  3. 결정과 실행이 떨어져 있다: "누가 다음에 도나"를 정하는 코드와 레지스터를 바꾸는 코드가 다른 파일, 다른 시점에 있다. FreeRTOS와 Zephyr는 그 시점이 다르다(§8).

이 노트는 소스 트리의 줄 수나 footprint를 다시 세지 않는다(그건 A3이 했다). 대신 안내를 받으며 읽는 투어를 한다. 지도는 실제로 QEMU에서 멈춰 세우고 찍은 gdb backtrace다.

1. 읽기 전략과 도구 상자#

1.1 세 단계 — 왜 이 순서인가#

단계 1: 자료구조 먼저. 커널 함수의 90%는 "전역 자료구조 몇 개를 한 상태에서 다른 상태로 옮기는 일"이다. FreeRTOS라면 pxReadyTasksLists[](우선순위별 ready 리스트), xDelayedTaskList1/2(깨울 시각 순 정렬 리스트), xPendingReadyList(스케줄러 잠금 중에 깬 태스크), 각 TCB의 xStateListItem · xEventListItem 두 고리. 이걸 머리에 그려 두면 listREMOVE_ITEM( &( pxTCB->xStateListItem ) ) 한 줄이 "이 태스크를 지금 있는 상태 리스트(ready든 delayed든)에서 뺀다"로 읽힌다. 깊은 설명은 C1이 맡는다.

단계 2: 핫 패스. 1초에 수천 번 도는 코드가 커널의 심장이다. tick 핸들러, PendSV(컨텍스트 스위치), give/take의 "깨우기" 부분, FromISR. 핫 패스는 짧고(대부분 100줄 안쪽), 여기서 커널의 설계 철학(ISR은 짧게, 결정은 미룬다)이 다 드러난다.

단계 3: API 하나를 끝까지. xQueueSend 하나를 골라 "사용자 호출 → 커널 리스트 변경 → 스위치 요청 → PendSV → 다른 태스크"까지 끊김 없이 따라간다. 이 한 줄을 다 읽으면 나머지 API(세마포어, 뮤텍스, 이벤트 그룹)는 같은 부품의 재조합이라서 빨리 읽힌다.

단계 4: 실행으로 확인. 읽은 대로 도는지 gdb로 한 번 밟는다. Don이 SSD에서 "코드 리뷰만으로는 못 믿고 로직 분석기로 확인"하던 습관 그대로다. 정적으로 읽은 그래프와 실제 backtrace가 다르면, 다른 쪽이 정답이다(§5.4에서 실제로 그런 일이 생긴다).

예제 2 — gdb ptype /o로 TCB와 리스트의 바이트 배치 보기

무엇을 확인하는 코드인지: 실제 빌드(예제 6의 ELF)의 DWARF 정보로 TCB · List_t · ListItem_t의 필드 오프셋을 찍는다. QEMU 없이 ELF만으로 된다.

출력에서 볼 것:

  • pxTopOfStack이 오프셋 0이다. 그래서 PendSV 어셈블리가 ldr r2, [r3](r2 = TCB 주소) 다음에 str r0, [r2] 한 줄로 "스택 꼭대기 저장"을 끝낸다(C2). 소스 주석에 "MUST BE THE FIRST MEMBER"라고 적힌 이유가 이 오프셋이다.
  • TCB 안에 리스트 고리가 두 개다. xStateListItem은 ready/delayed/suspended 중 하나에, xEventListItem은 "무엇을 기다리나"(큐의 xTasksWaitingToSend 등)에 걸린다. 블로킹 send는 두 고리를 동시에 건다(§4.3). 하나는 "언제까지", 하나는 "무엇을".
  • ListItem_t.pvContainer가 "지금 어느 리스트에 있나"를 기억한다. 그래서 listREMOVE_ITEM은 리스트 포인터 인자 없이 항목만 받아도 뺄 수 있다.
  • 이 설정의 TCB는 96바이트다(설정마다 다르다 — A3에서 설정별로 쟀다).

2.2 Zephyr 커널의 전역 상태#

Zephyr는 전역 상태를 struct z_kernel _kernel(kernel/init.c:48) 하나에 모았다. 단일 코어 설정에서 핵심은 두 필드다.

출력에서 볼 것:

  • _kernel.cpus[0].current가 FreeRTOS의 pxCurrentTCB, _kernel.ready_q.runq가 ready 리스트(이 설정은 CONFIG_SCHED_SIMPLE=y — 우선순위 순 이중 연결 리스트 하나)다.
  • _kernel.ready_q.cache 가 FreeRTOS에 없는 필드다. "다음에 돌 스레드"를 미리 골라 둔 캐시다. 이게 두 커널의 가장 큰 구조 차이이고, §5와 §8 전체가 이 한 필드 이야기다.
  • struct _callee_saved(v1~v8 = R4~R11, 그리고 psp)가 TCB 안 오프셋 48에 있다. Zephyr는 R4~R11을 스레드 구조체에 저장하고, FreeRTOS는 태스크 스택에 저장한다(stmdb r0!, {r4-r11}). 같은 Cortex-M3인데 설계가 다르다. 덤프에서 레지스터를 찾을 때 어디를 볼지가 달라진다.
  • base.timeout(오프셋 24)이 스레드마다 하나씩 박혀 있다. k_sleep은 이 노드를 타임아웃 리스트에 꽂는다(§5.3).

그림 2 — 핵심 파일 지도. 왼쪽 FreeRTOS는 "결정"이 tasks.c에 모여 있고 port.c가 그것을 부른다. 오른쪽 Zephyr는 결정이 sched.c에서 끝나고, 어셈블리(swap_helper.S)는 결정을 읽기만 한다. 줄 수는 wc -l.

2.3 Don 경험과 연결#

SSD 펌웨어의 명령 디스패처에도 "ready 큐", "NAND 대기 큐", "완료 큐"가 있고 명령 구조체에 큐 고리가 두세 개 박혀 있었을 것이다. FreeRTOS TCB의 xStateListItem / xEventListItem은 정확히 그 패턴(intrusive list — 항목이 노드를 품는 리스트)이다. 차이는 하나다. SSD 디스패처는 보통 "어느 큐가 비었나"를 루프에서 폴링하지만, RTOS는 리스트 이동이 일어날 때마다 즉시 "스위치가 필요한가"를 판단한다.

3.1 다섯 가족#

예제 5 — xPortPendSVHandler는 ELF 어디에 있나

무엇을 확인하는 코드인지: 소스에는 void xPortPendSVHandler( void )(port.c:455)라고 적혀 있는데, ELF 심볼 표에서 그 이름을 찾고, PendSV 핸들러의 기계어를 본다.

출력에서 볼 것:

  • xPortPendSVHandler · xPortSysTickHandler · vPortSVCHandler라는 심볼은 없다. 템플릿의 FreeRTOSConfig.h가 #define xPortPendSVHandler PendSV_Handler처럼 이름을 CMSIS 벡터 이름으로 바꿨기 때문이다. gdb에서 break xPortPendSVHandler가 "Function not defined"로 실패하면 이걸 의심한다. 소스 이름이 아니라 ELF 이름으로 중단점을 건다.
  • xTaskIncrementTick(0xf80)과 별도로 xTaskIncrementTick.part.0(0x8e8, 소문자 t = 파일 지역)이 있다. GCC가 함수를 "자주 도는 짧은 앞부분"과 "드문 긴 뒷부분"으로 쪼갠 것(부분 인라인 · IPA split)이다. 크기 순위(예제 13)에서 1등이 이 .part.0이다. 소스에는 없는 이름이니 놀라지 말 것.
  • PendSV의 mov.w r0, #32 = configMAX_SYSCALL_INTERRUPT_PRIORITY(0x20)이 인라인 어셈블리의 "i" 제약으로 상수가 되어 박힌 것이다. 소스(port.c:471 mov r0, %0)만 보면 이 값이 무엇인지 모른다. 기계어가 "이 설정의 정답"이다.
  • SysTick의 str.w r2, [r3, #3332] = 0xE000ED04(ICSR)에 1 << 28(PENDSVSET) 쓰기 — port.c:507 portNVIC_INT_CTRL_REG = portNVIC_PENDSVSET_BIT; 한 줄이다. cbz r0가 "xTaskIncrementTick이 pdFALSE면 건너뛴다"다.

3.4 흔한 함정 (매크로)#

  • gcc -E를 다른 플래그로 돌리기: -I 순서가 다르면 다른 FreeRTOSConfig.h를 집는다. 반드시 실제 빌드와 같은 플래그(Zephyr라면 compile_commands.json의 명령)로 돌린다(예제 14).
  • -P 출력의 줄 번호를 원본 줄 번호로 착각: -P는 줄 표지를 지운다. 원본과 대조하려면 -P 없이 돌린다.
  • trace 매크로가 빈 줄이라고 단정: SystemView나 Tracealyzer를 붙인 프로젝트에서는 traceTASK_SWITCHED_IN이 실제 코드(ITM 쓰기)다. 회사 프로젝트의 FreeRTOSConfig.h부터 확인한다.

8. RTOS 커널 안에서는 무슨 일이 일어나나 — 두 커널이 "결정"을 두는 자리#

이 노트는 그 자체가 "커널 안" 투어였으니, 여기서는 투어 전체에서 나온 가장 중요한 한 가지만 정리한다: 스케줄링 결정이 어디서 일어나나.

  • FreeRTOS: 리스트를 바꾸는 쪽(xTaskRemoveFromEventList, xTaskIncrementTick)은 "더 높은 게 깼다"는 표시(xYieldPendings[0], 반환값 pdTRUE)만 남기고 PENDSVSET을 켠다. 결정(taskSELECT_HIGHEST_PRIORITY_TASK)은 PendSV 안의 vTaskSwitchContext에서 한다. 장점: ISR이 아무리 많은 태스크를 깨워도 결정은 한 번. 대가: PendSV 안에서 C 함수 호출과 런타임 통계 · 스택 검사가 돈다(예제 5에서 bl vTaskSwitchContext).
  • Zephyr: 리스트를 바꾸는 순간 update_cache가 결정까지 끝내서 _kernel.ready_q.cache에 넣는다. PendSV(z_arm_pendsv)와 ISR 출구(z_arm_exc_exit)는 cache != current 비교와 레지스터 교체만 한다. 장점: PendSV가 짧고 C 호출이 없다. ISR 출구에서 자동으로 스위치 여부를 안다. 대가: 깨울 때마다 next_up 계산(그리고 time slicing이 켜져 있으면 z_reset_time_slice → z_add_timeout, §5.4).

그림 11 — 같은 "ISR이 높은 우선순위 태스크를 깨움" 장면에서 두 커널이 결정을 내리는 시점. 상자 폭은 개념적 길이다(이 노트는 이 두 경로의 사이클을 따로 재지 않았다 — 같은 보드에서 잰 전환 비용은 A7 · C2).

이 차이를 알면 디버깅 질문이 바뀐다. FreeRTOS에서 "태스크가 안 깬다"면 xYieldPendings와 PENDSVSET이 켜졌는지(ISR의 portYIELD_FROM_ISR 누락이 1순위), Zephyr라면 ready_q.cache가 기대한 스레드인지(협력형 우선순위 · k_sched_lock이 1순위)를 본다. 깊은 설명은 C1(리스트 · 비트맵), C2(PendSV), C4(정책 · 협력형), C5(tick), C7(잠금), C8(syscall 래퍼 · z_impl_), E1(ISR 규칙)이 맡는다.

예를 들어 드론 비행 제어기에서 IMU DMA 완료 ISR이 xQueueSendFromISR로 자세 제어 태스크(최고 우선순위)를 깨우는데, 스코프로 보면 가끔 1 ms 늦게 돈다. §4.5의 투어를 아는 사람은 바로 두 곳을 본다. (1) ISR 끝에 portYIELD_FROM_ISR(woken)이 있나 — 없으면 PENDSVSET이 안 켜져서 다음 tick의 SysTick이 우연히 PendSV를 켤 때까지 기다린다(최대 1 tick 지연, 증상과 정확히 일치). (2) woken을 여러 FromISR 호출에 걸쳐 OR로 모으나 — 두 번째 호출이 pdFALSE로 덮어쓰면 같은 증상. 검증은 gdb 한 줄이다: ISR의 마지막 줄에 중단점, p woken, p/x *(unsigned*)0xE000ED04.

9.2 로봇 관절 모터 컨트롤러 (Zephyr) — CAN ISR 뒤 제어 스레드가 안 도는 순간#

예를 들어 Zephyr 기반 모터 컨트롤러에서 CAN 수신 ISR이 k_sem_give로 제어 스레드를 깨우는데, 가끔 다음 tick까지 안 돈다. §5.5를 읽었다면 z_arm_exc_exit의 비교(ready_q.cache != current)가 핵심임을 안다. ISR 직전에 돌던 스레드가 협력형(음수 우선순위)이거나 k_sched_lock() 중이면 should_preempt가 false라서 cache가 바뀌지 않는다(예제 12에서 확인 — 더 높은 우선순위를 깨워도 비키지 않는다). gdb로 ISR 출구에서 p _kernel.ready_q.cache->base.prio와 p _kernel.cpus[0].current->base.sched_locked를 찍으면 10초 안에 갈린다.

9.3 벤더 SDK의 낯선 포트를 받았을 때#

새 회사에서 받은 MCU SDK의 FreeRTOS가 portable/GCC/ARM_CM7/r0p1이거나, 칩 벤더가 손댄 port.c일 수 있다. 읽는 순서는 이 노트의 15개 목록 중 포트 쪽 4개(5 · 6 · 14 · 15)부터다. nm으로 핸들러 이름이 벡터 테이블과 연결됐는지(예제 5), objdump로 PendSV의 BASEPRI 값이 configMAX_SYSCALL_INTERRUPT_PRIORITY와 같은지, 그리고 vPortValidateInterruptPriority가 켜져 있는지를 본다. 실칩은 NVIC 우선순위 비트가 3~4개라서 QEMU(8비트)와 다르다는 점도 이때 확인한다(E2).

9.4 SSD 펌웨어 경험을 RTOS 말로#

Don이 SSD에서 하던 "명령 경로 따라가기"는 이 노트의 단계 3과 같다. 차이는 SSD 실행부가 보통 협력형 루프 + 이벤트 큐라서 콜 스택이 끊기지 않는 반면, RTOS는 PendSV에서 스택이 바뀐다는 것뿐이다. 면접에서 "큰 낯선 코드베이스를 어떻게 읽나?"라는 질문이 나오면, SSD 경험(자료구조 → 한 명령의 경로 → JTAG로 확인)을 이 노트의 FreeRTOS 예로 번역해서 답하면 된다(§11 Q1).

11. 면접에서 이렇게 말한다#

Q. How do you approach reading an unfamiliar RTOS kernel or a large firmware codebase?

A. 자료구조부터 보고, 핫 패스 몇 개를 고르고, API 하나를 끝까지 따라간 뒤, 디버거로 실제 경로를 확인한다. 매크로가 많으면 실제 빌드 플래그로 전처리한 출력을 읽는다.

I start with the data structures, not the functions — in FreeRTOS that's the TCB with its two list items, the per-priority ready lists with the priority bitmap, and the delayed lists. Then I pick the hot paths: the tick handler, PendSV, and the give/take wake-up path. Then I follow one API end to end, for example xQueueSend from the call all the way to the PendSV that switches tasks. For a macro-heavy codebase I read the preprocessed output with the exact build flags, because in FreeRTOS only about a third of tasks.c survives preprocessing for a given config. Finally I confirm the path with breakpoints and backtraces on QEMU or the target, because the static reading is sometimes wrong — function pointers and exception entry don't show up in a static call graph.

꼬리 질문: "How would you know which functions to read first?" → 크기(nm --size-sort), 분기 수(전처리 뒤 + 기계어), 핫 패스 여부를 합친다(§6).

Q. Walk me through what happens inside FreeRTOS when a task calls xQueueSend on a full queue.

A. 임계 구역에서 큐가 꽉 찬 걸 확인하고 타임아웃 기준을 기록한 뒤, 스케줄러를 잠그고 큐를 잠근 상태에서 자기 TCB를 큐의 send 대기 리스트(우선순위 순)와 지연 리스트에 동시에 건다. 잠금을 풀고 portYIELD로 PendSV를 요청하면 PendSV 안의 vTaskSwitchContext가 다음 태스크를 고른다. 깨어나면 루프 처음부터 다시 검사한다.

xQueueSend maps to xQueueGenericSend. Inside a short critical section it sees the queue is full, records the timeout start, and leaves the critical section. Then it suspends the scheduler and locks the queue, so ISRs can still post but won't touch the event lists — they just bump a lock counter. It calls vTaskPlaceOnEventList, which inserts the task's event list item into the queue's xTasksWaitingToSend list in priority order, and moves its state list item from the ready list to the delayed list — so it's waiting on "what" and "until when" at the same time. It unlocks the queue, resumes the scheduler, and if that didn't already yield it calls taskYIELD_WITHIN_API, which just sets PENDSVSET. The actual decision happens in PendSV, in vTaskSwitchContext. When the task wakes — either a receiver removed it from the event list or the tick timed it out — it loops back and re-checks the queue, because a higher-priority task may have taken the slot first.

꼬리 질문: "Why lock the queue instead of just disabling interrupts for the whole thing?" → 대기 리스트 조작이 길어서 ISR 지연을 늘리지 않으려고. 큐 잠금 중 ISR 쓰기는 cTxLock로 세었다가 prvUnlockQueue가 처리한다.

Q. Why must you call portYIELD_FROM_ISR at the end of an ISR that used a FromISR API?

A. FromISR API는 대기 태스크를 ready로 옮기고 xYieldPendings와 woken 플래그만 세운다. PENDSVSET은 켜지 않는다. ISR 끝에서 portYIELD_FROM_ISR(woken)이 PENDSVSET을 켜야 ISR이 끝나자마자 PendSV가 꼬리 물기로 돈다. 빠뜨리면 다음 tick까지 늦는다.

The FromISR call only moves the waiting task to the ready list and reports back through the woken flag — it never pends PendSV itself. I verified this in gdb: at the last line of the ISR, woken was 1 and xYieldPendings was set, but the PENDSVSET bit in ICSR was still 0. portYIELD_FROM_ISR is what sets PENDSVSET, so PendSV tail-chains right after the ISR returns. If you forget it, the woken task waits until something else pends PendSV — typically the next SysTick — so you get up to one tick of extra latency, which looks like random jitter on a scope.

꼬리 질문: "How does Zephyr handle the same thing?" → 모든 ISR 공통 출구 z_arm_exc_exit가 ready_q.cache != current를 비교해 자동으로 PENDSVSET.

Q. What's the difference between how FreeRTOS and Zephyr decide which thread runs next on Cortex-M?

A. FreeRTOS는 PendSV 안에서 vTaskSwitchContext가 비트맵 + CLZ로 결정한다. Zephyr는 스레드를 ready로 만들거나 빼는 순간 update_cache가 결정해서 _kernel.ready_q.cache에 넣어 두고, PendSV는 그 캐시를 current로 옮기기만 한다. 레지스터 저장 위치도 다르다(태스크 스택 vs 스레드 구조체).

FreeRTOS defers the decision: list operations just mark that a yield is needed, and PendSV calls vTaskSwitchContext, which uses the ready-priority bitmap and count-leading-zeros to pick the next TCB. Zephyr decides eagerly: every time a thread becomes ready or unready, update_cache computes the next thread and stores it in _kernel.ready_q.cache. The PendSV handler, z_arm_pendsv, doesn't call any scheduler C code — it saves callee-saved registers into the outgoing thread struct, loads ready_q.cache into current, and restores. That's also why Zephyr can decide at every ISR exit, in z_arm_exc_exit, whether to pend PendSV just by comparing cache against current.

Q. You set a breakpoint and the backtrace shows a function your firmware never calls. What do you suspect?

A. --gc-sections로 버려진 함수의 DWARF가 주소 0 근처에 남아 gdb가 그 이름을 집은 것을 먼저 의심한다. addr2line과 nm으로 주소를 대조한다. 그 밖에 인라인 프레임, "리턴 주소 − 1" 조회로 앞 함수 이름이 나오는 경우, 최적화로 생긴 .part.0 · .isra.0 이름도 확인한다.

First suspicion is stale debug info from garbage-collected sections: the linker drops the unused function's code, but its DWARF entry stays with low_pc relocated to zero, so it covers low addresses and gdb picks it for a frame there. I hit exactly this — gdb labeled my task function as xQueuePeek. I cross-check with addr2line and nm, or link the debug build with --no-gc-sections. Other usual suspects are inlined frames, gdb's return-address-minus-one lookup landing in the previous function — the bottom PendSV_Handler frame on a FreeRTOS task stack is really the fake return address prvTaskExitError — and compiler-generated names like .part.0 or .isra.0.

Q. How would you find which kernel functions are worth reviewing or optimizing first?

A. 크기(nm), 분기 수(실제 설정으로 전처리한 소스와 기계어 둘 다), 그리고 핫 패스 여부(트레이스나 프로파일)를 함께 본다. 원본 소스의 복잡도는 쓰지 않는 #if 가지까지 세어서 속기 쉽다.

I combine three signals: function size from nm --size-sort, branch count measured both on the preprocessed source for our config and on the generated machine code, and whether the function is on a hot path — from a trace or just by breakpoint counts. Raw source metrics are misleading in RTOS code: in FreeRTOS tasks.c the most complex function in the raw file is SMP-only and doesn't even exist in a single-core build, and in Zephyr a sleep function jumps from 3 to 38 branches after preprocessing because of constant time-conversion macros that the compiler folds away. The machine-code count tells you what actually executes.

14. 요약 & 체크리스트#

커널 소스는 처음부터 읽지 않는다. 자료구조(TCB의 두 고리, ready 리스트 + 비트맵, 지연 리스트 / _kernel.ready_q)를 먼저 펴고, 핫 패스(tick, PendSV, 깨우기)를 읽고, API 하나를 끝까지(xQueueSend → vTaskPlaceOnEventList → portYIELD → PendSV → vTaskSwitchContext) 따라간 뒤, gdb backtrace로 확인한다. FreeRTOS의 매크로 미로는 실제 빌드 플래그의 gcc -E로 걷어 내면 tasks.c 8967줄이 3226줄로 준다. gdb의 bt는 강력하지만 --gc-sections 유령 DWARF, "주소 − 1"로 보이는 바닥의 PendSV_Handler, 인라인 프레임, icount 왜곡을 알고 읽어야 한다. 두 커널의 가장 큰 차이는 결정 시점이다 — FreeRTOS는 PendSV 안에서, Zephyr는 깨우는 순간 update_cache에서 정하고 PendSV는 캐시를 읽기만 한다. 읽을 순서는 크기 · 분기 수(원본 · 전처리 · 기계어) · 핫 패스를 같이 보고 정하며, 이 노트의 15개(FreeRTOS)와 10개(Zephyr) 목록과 2주 계획이 출발점이다.
