0. 큰 그림 — 이게 왜 필요한가#

Linux에서 read()를 부르면 svc #0으로 예외가 나고, 커널이 레지스터를 저장하고, 번호로 sys_call_table을 찾아 커널 함수를 부른다(EL E6 §1). 유저 공간과 커널은 다른 특권 레벨, 다른 주소 공간이고, 그 사이를 넘는 유일한 문이 시스템 콜이다.

RTOS에서는 이야기가 다르다. 기본 FreeRTOS와 기본 Zephyr는 라이브러리형 커널이다(A3 §3). 태스크 코드와 커널 코드가 같은 이미지, 같은 주소 공간, 같은 특권 레벨에서 돈다. 그래서 xQueueSend()는 시스템 콜이 아니라 그냥 C 함수 호출이다. 문이 없으니 넘을 것도 없다.

그런데 MPU를 쓰는 보호 빌드(FreeRTOS-MPU, Zephyr CONFIG_USERSPACE)를 켜면 문이 생긴다. 비특권 태스크는 커널 데이터에 손댈 수 없고, 커널에 일을 시키려면 svc 명령으로 예외를 일으켜 특권 코드에게 부탁해야 한다. 이 노트는 이 세 가지 길을 소스·디스어셈블·gdb·측정으로 끝까지 따라간다.

1. 기본 경로 — 라이브러리형 커널에서 API 호출은 함수 호출이다#

1.1 직관#

기본 FreeRTOS에서 태스크는 처음부터 끝까지 특권(privileged) Thread 모드로 돈다(B1). 커널 코드도 같은 특권이다. 그러니 태스크가 커널에 들어갈 때 넘어야 할 문이 없다. xQueueSend(q, &v, 0)은 queue.h의 매크로가 xQueueGenericSend(q, &v, 0, queueSEND_TO_BACK)로 바꾸고, 컴파일러는 그걸 AAPCS 함수 호출(r0–r3에 인자, bl)로 만든다. 커널 함수는 필요하면 크리티컬 섹션(C7)으로 자기 자료구조를 보호하고, 그냥 bx lr/pop {pc}로 돌아온다.

  • 정의 — 커널 진입 경로(kernel entry path): 애플리케이션 코드가 커널 서비스(큐·세마포어·스케줄러)를 쓰려고 할 때 제어가 커널 코드로 넘어가는 방식. 함수 호출일 수도, 소프트웨어 예외(SVC·ecall·syscall)일 수도 있다.
  • 정의 — 시스템 콜(system call): 특권 경계를 넘어 커널에 서비스를 요청하는 진입 경로. 보통 예외 명령으로 들어가고, 커널이 인자를 검사한다. 기본 RTOS에는 이게 없다.

그림 2 — 기본 FreeRTOS의 xQueueSend 경로. 처음부터 끝까지 같은 모드, 같은 스택이다. "커널 진입"이라고 부를 만한 순간은 사실 vPortEnterCritical이 BASEPRI를 올리는 것뿐이다(C7).

1.2 예제 1 — 기본 FreeRTOS API 한 번의 비용을 잰다#

무엇을 확인하나: 빈 함수 호출, 가장 단순한 API(uxQueueMessagesWaiting), 큐 송신·수신 한 번이 각각 몇 ns(몇 명령)인지. 루프 256회 평균이고 루프 자체 비용(명령 3~4개)이 포함된다.

출력에서 볼 것: CONTROL=0x2 — bit1(SPSEL)=1이라 PSP(태스크 스택)를 쓰고, bit0(nPRIV)=0이라 태스크가 특권으로 돈다. 그리고 큐 송신 한 번이 약 121 명령이다. 이 중 함수 호출 자체(빈 호출 약 8 명령, 루프 포함)는 아주 작은 부분이고, 나머지는 크리티컬 섹션 진입·해제, 큐 상태 검사, memcpy, 대기 리스트 확인이다. "커널 진입 비용"은 사실상 0이고 비용의 대부분은 커널이 하는 일 자체다.

1.3 예제 2 — 호출 지점 디스어셈블: bl 하나, 그리고 이미지 전체에 svc는 딱 하나#

무엇을 확인하나: 컴파일러가 xQueueSend를 어떤 명령으로 만들었는지, 그리고 기본 포트 이미지 안에 svc가 어디 있는지.

출력에서 볼 것:

  • xQueueSend(q, &v, 0)은 r0=핸들, r1=&v(sp), r2=0(timeout), r3=0(queueSEND_TO_BACK)을 채우고 bl xQueueGenericSend 한 줄이다. SVC도, 모드 전환도 없다.
  • 이미지 전체의 svc는 prvPortStartFirstTask의 svc 0 하나뿐이다. 이건 스케줄러를 시작할 때 첫 태스크로 들어가는 용도이고(C3, B4) API 호출과 관계없다.
  • uxQueueMessagesWaiting의 몸통은 cbz r0(NULL 검사 = configASSERT) → 임계 구역 → ldr r4, [r4, #56](Queue_t.uxMessagesWaiting 읽기) → 임계 구역 해제가 전부다. 핸들이 진짜 큐인지는 확인하지 않는다. 다음 예제에서 직접 속여 본다.

1.4 예제 3 — 인자 검사가 없다는 것의 의미: 가짜 핸들을 넘겨 본다#

무엇을 확인하나: 라이브러리형 커널은 핸들을 "믿는다". 아무 메모리 주소를 큐 핸들이라고 넘겨도 커널은 그 주소 + 56을 그대로 읽는다.

출력에서 볼 것: 커널은 가짜 배열을 큐로 믿고 1234를 "대기 중인 메시지 수"로 돌려준다. 0x100을 넘기면 0x138에 있는 코드 바이트(b508 4803 = push {r3, lr}; ldr r0, [pc, #12], 같은 빌드를 objdump -d로 보면 그 자리에 이 두 명령이 있다)를 숫자로 돌려준다. 읽기라서 이 정도지만, xQueueSend에 가짜 핸들을 주면 커널은 그 주소에 쓴다 — 다른 태스크의 스택이나 TCB가 조용히 깨진다. 이게 "인자 검사 없음"의 진짜 의미다. 뒤의 §3.9 예제 9에서 같은 일을 FreeRTOS-MPU에 시키면 0이 돌아온다(핸들 검사에서 거절).

1.5 RTOS 커널 안과 연결, 그리고 Don 경험#

  • 소스 위치: include/queue.h의 #define xQueueSend(...) xQueueGenericSend(..., queueSEND_TO_BACK) → queue.c의 xQueueGenericSend() → taskENTER_CRITICAL() = portENTER_CRITICAL() = vPortEnterCritical()(portable/GCC/ARM_CM3/port.c). 핸들은 typedef struct QueueDefinition * QueueHandle_t이고 커널 안에서 그대로 Queue_t *로 캐스팅된다.
  • Zephyr도 CONFIG_USERSPACE=n이면 똑같다. k_sem_give(&sem)은 생성된 인라인 함수가 곧바로 z_impl_k_sem_give(&sem)을 부른다(§4.2에서 생성 코드로 확인).
  • Don의 SSD 펌웨어에서 FTL이 NAND 드라이버의 nand_program(desc)를 부를 때 디스크립터 포인터를 검사하지 않던 것과 같다. 같은 팀이 짠 같은 이미지 안의 코드끼리는 서로를 믿는 게 기본이고, 그래서 빠르다. 대신 한 모듈의 포인터 버그가 다른 모듈의 상태를 깨면 증상은 엉뚱한 곳에서 나타난다.

1.6 흔한 함정#

  • "RTOS API는 시스템 콜이니까 느리다"는 오해. 기본 빌드에서는 함수 호출이고, 비용은 커널이 하는 일(임계 구역, 리스트 조작, 복사)에서 나온다. 최적화하려면 진입 경로가 아니라 호출 횟수와 임계 구역 길이를 줄여야 한다.
  • 반대로 "함수 호출이니까 ISR에서 아무 API나 불러도 된다"는 오해. ISR에서는 ...FromISR 변형만 써야 한다. 진입 방식이 아니라 블로킹 가능성과 임계 구역 방식(BASEPRI 저장·복원) 때문이다(C7, E1).
  • configASSERT를 끈 릴리스 빌드에서는 NULL 핸들조차 검사하지 않는다. cbz r0가 사라지고, NULL + 56을 읽는다.

2. 보호 빌드의 재료 — 특권 비트, MPU, SVC 세 가지#

보호 빌드가 왜 SVC를 쓰는지는 Cortex-M 하드웨어 규칙 세 개로 설명된다. 자세한 레지스터는 B1(CONTROL), B4(SVC), F4(MPU)에 있고, 여기서는 "커널 진입"에 필요한 부분만 짚는다.

  1. CONTROL.nPRIV(bit0): Thread 모드의 특권 여부. 1이면 비특권이다. 비특권 코드는 이 비트를 0으로 되돌릴 수 없다 — 비특권에서 msr control은 조용히 무시된다(예제 9의 BAD6에서 직접 확인). Handler 모드(예외 처리 중)는 nPRIV와 관계없이 항상 특권이다.
  2. MPU: 비특권 접근은 MPU 리전이 허락한 주소에만 갈 수 있다. 특권 코드는 PRIVDEFENA(MPU_CTRL bit2)가 켜져 있으면 리전이 없는 곳도 기본 메모리 맵으로 접근한다. 그래서 "커널 데이터를 특권 전용 리전에 두면" 비특권 태스크는 그걸 못 건드린다.
  3. SVC: svc #imm8은 동기 예외를 일으킨다. 예외에 들어가면 Handler 모드 = 특권이 되고, 하드웨어가 r0–r3·r12·lr·pc·xPSR 8워드를 현재 스택에 쌓는다(B2). 핸들러는 쌓인 PC에서 2바이트 앞의 명령을 읽어 imm8(서비스 번호)을 꺼낸다.

세 규칙을 합치면 결론이 하나다: 비특권 코드가 특권 코드를 실행시키는 유일한 정상 경로는 예외, 그중에서도 SVC다. 그래서 보호 빌드의 모든 API 호출은 결국 svc가 된다. Linux의 svc #0(EL E6)과 같은 원리이고, RTOS에서 달라지는 점은 (1) 주소 공간이 하나라 "복사"가 필요 없고 포인터를 검사만 한다는 것, (2) MMU가 아니라 MPU라서 리전 수(v7-M 8개)와 정렬 제약이 설계를 좌우한다는 것, (3) 시스템 콜을 Handler 모드가 아니라 특권 Thread 모드로 내려와서 실행한다는 것(§3.7, §4.4 — 인터럽트에 선점될 수 있게)이다.

3.2 예제 4 — 같은 소스 한 줄, 다른 함수 이름: mpu_wrappers.h의 매크로 바꿔치기#

FreeRTOS-MPU의 첫 번째 장치는 놀랍게도 전처리기다. FreeRTOS.h가 끌어오는 mpu_wrappers.h는 portUSING_MPU_WRAPPERS == 1이면 공개 API 이름을 전부 MPU_ 접두어 이름으로 #define한다. 앱 코드는 한 글자도 바꾸지 않아도 래퍼를 부르게 된다. 반면 커널 소스(tasks.c, queue.c …)는 맨 위에서 MPU_WRAPPERS_INCLUDED_FROM_API_FILE을 정의해서 이 바꿔치기를 끈다 — 커널 안에서는 진짜 함수를 불러야 하니까.

무엇을 확인하나: 같은 call.c를 일반 포트와 MPU 포트 헤더로 각각 전처리했을 때 호출되는 함수 이름.

출력에서 볼 것: 매크로 두 단계(xQueueSend → xQueueGenericSend → MPU_xQueueGenericSend)를 거쳐 앱의 호출 대상이 바뀐다. 커널 .c 파일 6개는 모두 이 바꿔치기를 끈다. 그래서 같은 이름 xQueueGenericSend가 앱에서는 래퍼, 커널에서는 진짜 함수를 뜻한다. 같은 헤더가 PRIVILEGED_FUNCTION·PRIVILEGED_DATA·FREERTOS_SYSTEM_CALL을 각각 section("privileged_functions")·section("privileged_data")·section("freertos_system_calls") 속성으로 정의한다(mpu_wrappers.h 283–285행). 커널 함수·변수 선언에 이미 이 매크로가 붙어 있어서, MPU 포트로 빌드하면 커널 코드와 데이터가 자동으로 별도 섹션에 모인다.

3.5 예제 5 — MPU 빌드 만들기: 설정·링커 스크립트·Makefile#

랩 템플릿(freertos-mps2)은 일반 ARM_CM3 포트 전용이라, MPU 빌드는 자기 폴더에 설정·링커 스크립트·Makefile을 새로 만들었다. FreeRTOS 공식 저장소에는 같은 QEMU 보드용 MPU 데모(CORTEX_MPU_M3_MPS2_QEMU_GCC)가 있다고 알려져 있지만, 랩의 데모 트리는 일부만 받아 둔(sparse) 것이라 그 데모는 없다. 그래서 포트 소스가 extern으로 요구하는 링커 심볼을 port.c에서 grep해서 직접 맞췄다.

필요한 심볼은 __FLASH_segment_start__/end__, __privileged_functions_start__/end__, __syscalls_flash_start__/end__, __SRAM_segment_start__/end__, __privileged_data_start__/end__ 다섯 쌍이다(port.c의 prvSetupMPU()·vSystemCallEnter()·vSystemCallExit()·vPortStoreTaskMPUSettings()에서 사용). prvSetupMPU()는 이 심볼로 리전 4개를 고정 설정한다: 리전 5 = FLASH 전체 읽기 전용(모두), 리전 6 = privileged_functions 특권 전용, 리전 7 = privileged_data 특권 전용 + XN, 리전 4 = 주변장치 0x40000000–0x5FFFFFFF 읽기·쓰기 + XN. v7-M MPU 리전은 크기가 2의 거듭제곱이고 시작 주소가 크기에 정렬되어야 하므로(F4), 두 특권 영역을 FLASH·RAM 맨 앞에 두고 크기를 고정했다.

설정 파일 — 랩 기본 설정을 그대로 포함하고 MPU 항목만 더한다.

링커 스크립트 — 랩의 mps2_m3.ld에 특권 섹션 세 개와 심볼을 더했다. startup.c가 _sidata부터 _edata까지 복사하므로 privileged_data를 .data 바로 앞에 붙였다(초기값이 있는 커널 변수도 있어서 FLASH에 실어야 한다).

Makefile — 일반 템플릿과 다른 점은 포트 디렉터리(ARM_CM3_MPU), 래퍼 소스 두 개, 링커 스크립트, 그리고 kstatic.c(idle·timer 태스크 메모리)·fault.c(MemManage 핸들러)다.

빌드하고 섹션 크기와 핵심 심볼 위치를 본다.

출력에서 볼 것:

  • 진짜 커널 함수(xQueueGenericSend, vSystemCallEnter, MPU_xQueueGenericSendImpl)는 전부 0x0–0xFFFF privileged_functions 안에 있다. 래퍼 MPU_xQueueGenericSend는 0x10000–0x10530 freertos_system_calls 섹션(1328바이트 = 래퍼 수십 개)에 있다. 앱 코드 user_task와 board_printf_raw는 그 뒤 .text다.
  • 커널 데이터(pxCurrentTCB, 힙 ucHeap, 시스템 콜 표 uxSystemCallImplementations)는 0x20000000–0x20007FFF privileged_data 안에 있다. TCB와 큐도 힙에서 할당되므로 같은 보호를 받는다.
  • 시행착오 하나: 처음에 _Privileged_Functions_Region_Size = 32K로 했더니 링커가 cannot move location counter backwards (from 000082c0 to 00008000)로 실패했다. 이 설정(-O2 -g3, trace·stats 기능 켬)에서 커널 코드가 약 33.5 KB라 32 KB 리전에 안 들어간 것이다. 2의 거듭제곱 리전이라 다음 크기는 64 KB — 약 30 KB가 낭비된다. v7-M MPU 설계의 전형적인 비용이다(F4).

3.6 예제 6 — restricted 태스크가 큐를 쓴다: 핸들 = 인덱스, ACL, 그리고 비용#

무엇을 확인하나: (1) 비특권 restricted 태스크와 특권 태스크의 CONTROL 값, (2) v2 핸들이 포인터가 아니라 작은 정수라는 것, (3) ACL로 권한을 받기 전에는 xQueueSend가 실패하는 것, (4) 같은 API의 비용이 특권/비특권 경로에서 얼마나 다른지.

  • restricted 태스크: xTaskCreateRestricted()(또는 ...Static)로 만든 태스크. TaskParameters_t에 스택 버퍼와 MPU 리전 3개(xRegions[portNUM_CONFIGURABLE_REGIONS])를 직접 준다. 우선순위에 portPRIVILEGE_BIT가 없으면 비특권으로 시작한다. 접근할 수 있는 메모리는 자기 스택 + 준 리전 + FLASH 읽기 + 주변장치뿐이다.
  • 특권 태스크: 우선순위에 portPRIVILEGE_BIT(0x80000000)를 OR해서 만든다. 이 예제의 priv_task가 그렇다.

출력에서 볼 것:

  • 핸들이 1, 2다. 큐 핸들 q=0x1, 태스크 핸들 user_h=0x2. v2는 xQueueCreate가 만든 진짜 Queue_t *를 커널 객체 풀(mpu_wrappers_v2.c의 xKernelObjectPool[])에 넣고 그 칸 번호를 돌려준다. 비특권 코드는 커널 객체의 주소를 끝내 모른다.
  • user는 CONTROL=0x3(nPRIV=1, PSP), priv는 CONTROL=0x2(nPRIV=0, PSP)다.
  • ACL: 권한을 받기 전 xQueueSend는 0(pdFAIL)이다. 예외도 없이 조용히 실패한다 — MPU_xQueueGenericSendImpl이 xPortIsAuthorizedToAccessKernelObject()에서 걸러 낸다. priv_task가 vGrantAccessToQueue(user_h, g_q)를 부른 뒤에는 1(pdPASS)이다. 스케줄러가 시작되기 전에는 모든 접근이 허용된다(port.c xPortIsAuthorizedToAccessKernelObject의 xSchedulerRunning == pdFALSE 분기).
  • restricted 태스크는 전역 변수 g_q조차 읽을 수 없다(.bss는 이 태스크의 리전에 없다). 그래서 핸들을 pvParameters로 넘겼다. 처음 작성할 때는 user_task가 전역 q를 바로 읽게 짰다가 [MemManage] ... MMFAR=0x20009004로 죽었다 — 0x20009004가 바로 그 전역 변수 주소였다. restricted 태스크를 처음 만들면 거의 누구나 이 벽에 부딪힌다.
  • 비용: 같은 xQueueSend가 특권 태스크에서는 6891 ns, 비특권에서는 13233 ns다. 기본 FreeRTOS(예제 1)는 3878 ns였다. 특권 경로도 기본보다 3 us 비싼 이유는 특권 태스크라도 MPU_xQueueGenericSendImpl(인덱스 → 포인터 변환, 버퍼 검사)을 거치기 때문이다. 비특권 경로의 추가 6.3 us(약 200 명령)가 SVC 진입·스택 교체·SVC 퇴장 비용이다.

같은 소스를 v1 래퍼로도 빌드해서 비교했다(WRAP=v1, configUSE_MPU_WRAPPERS_V1=1, ACL 없음).

출력에서 볼 것: v1에서는 핸들이 진짜 RAM 주소(0x200002e0)이고 ACL이 없어 "권한을 받기 전"에도 송신이 성공한다. 비특권 xQueueSend는 5152 ns로 v2(13233 ns)의 약 40%다. v1이 싼 이유는 검사를 안 하기 때문이고, 그게 곧 v1의 보안 구멍이다. 보호의 강도와 진입 비용이 정확히 맞바꿈이라는 걸 숫자로 볼 수 있다.

3.7 예제 7 — SVC 경로를 디스어셈블과 gdb로 한 단계씩 따라간다#

무엇을 확인하나: 래퍼가 CONTROL을 보고 갈림길을 고르는 코드, SVC 핸들러가 번호로 분기하는 코드, 그리고 실제 실행 중 각 단계의 IPSR·CONTROL·스택 포인터.

출력에서 볼 것:

  • 래퍼는 5개 명령으로 "지금 내가 특권인가"를 본다(mrs r0, CONTROL; tst #1). 특권이면 b MPU_xQueueGenericSendImpl(함수 점프, 예외 없음), 비특권이면 svc 33. 인자 r0–r3는 건드리지 않으니 그대로 예외 프레임에 실려 간다. 래퍼는 naked 함수라 프롤로그도 없다.
  • SVC_Handler는 쌓인 PC([r0, #24])의 2바이트 앞에서 svc 명령의 imm8을 꺼내(ldrb r1, [r2, #-2]) 번호로 세 갈래로 나눈다: 70(NUM_SYSTEM_CALLS) 미만 = 시스템 콜 진입, 103 = 시스템 콜 퇴장, 나머지(100 스케줄러 시작, 101 yield) = vSVCHandler_C.
  • 시스템 콜이 끝나면 vRequestSystemCallExit의 svc 103이 퇴장 예외를 낸다. v2는 호출 한 번에 SVC 예외가 두 번 난다(들어갈 때 1번, 나올 때 1번).

이제 실행 중에 따라가 본다. QEMU를 -s -S로 띄우고 gdb 스크립트로 단계마다 멈춘다. QEMU gdbstub는 M-profile 시스템 레지스터($control, $msp, $psp)를 보여 준다.

(앞쪽의 Reset_Handler·user_task 진입 줄은 생략했다.) 다섯 줄이 이 노트의 핵심 증거다.

  1. 래퍼: Thread 모드, CONTROL=0x3(비특권, PSP). PSP는 restricted 태스크의 스택(user_stack, 0x20008800–0x20008FFF) 안이다.
  2. SVC 진입: IPSR=11(SVCall 예외 번호), 번호 33. Handler 모드라 이 순간 MSP를 쓴다. vSystemCallEnter는 (a) SVC를 낸 PC가 freertos_system_calls 안인지, (b) 이미 시스템 콜 중이 아닌지, (c) 그 API가 설정에서 켜져 있는지 확인하고, 하드웨어 프레임 8워드를 TCB 안의 syscall 스택으로 복사한 뒤 PSP를 그쪽으로 바꾸고, CONTROL.nPRIV를 0으로 만들고, 쌓인 PC를 MPU_xQueueGenericSendImpl, 쌓인 LR을 vRequestSystemCallExit로 고쳐 쓴다(port.c 491–590행).
  3. Impl: IPSR=0 — Handler 모드가 아니라 Thread 모드로 돌아와 있다. CONTROL=0x2 — 이제 특권이다. PSP=0x200009e0은 ucHeap 안, 즉 힙에서 할당된 이 태스크 TCB의 xSystemCallStackInfo.ulSystemCallStackBuffer다. 백트레이스의 #1 = 0x58b0은 vRequestSystemCallExit(LR을 거기로 고쳐 써 두었으니 Impl이 return하면 그리로 간다; gdb가 naked 함수의 디버그 정보 때문에 이름을 prvRestoreContextOfFirstTask로 잘못 붙였다).
  4. SVC 퇴장: 다시 IPSR=11, 번호 103. vSystemCallExit는 PC가 privileged_functions 안인지 확인하고, 프레임을 태스크 스택으로 되돌려 복사하고, nPRIV를 1로 되돌리고, PC를 "래퍼를 부른 곳"(진입 때 저장한 LR)으로 고친다.
  5. 복귀: 다시 Thread 모드, CONTROL=0x3, 반환값 0(권한 받기 전이라 pdFAIL).

그림 3 — FreeRTOS-MPU v2에서 비특권 xQueueSend 한 번의 경로. 원 번호는 gdb 출력의 단계 번호와 같다. 진짜 커널 일(③)은 Handler 모드가 아니라 특권 Thread 모드에서 시스템 콜 전용 스택 위에서 돈다 — 그래서 시스템 콜 도중에도 인터럽트가 들어오고 컨텍스트 스위치가 될 수 있다.

4. Zephyr userspace — __syscall 한 줄에서 생성되는 시스템 콜#

4.1 직관과 정의#

Zephyr의 기본(CONFIG_USERSPACE=n)은 FreeRTOS처럼 라이브러리형이다. CONFIG_USERSPACE=y(MPU가 있는 보드)를 켜면 두 종류의 스레드가 생긴다.

  • supervisor 스레드: 특권으로 도는 보통 스레드. main()이 그렇다. 커널 API를 거의 직접 호출한다.
  • user 스레드: k_thread_create(..., K_USER, ...)로 만들거나 k_thread_user_mode_enter()로 내려간 비특권 스레드. 커널 객체는 권한을 받은 것만, 메모리는 자기 스택 + 속한 memory domain의 파티션만 쓸 수 있다.

FreeRTOS-MPU와 가장 다른 점은 시스템 콜을 손으로 쓰지 않는다는 것이다. 헤더에서 API 선언 앞에 __syscall을 붙이면, 빌드 때 scripts/build/gen_syscalls.py가 진입 인라인·마샬링 함수·디스패치 표를 생성한다. 개발자는 두 함수만 쓴다:

  • z_impl_<이름>(): 진짜 구현. supervisor에서는 이걸 바로 부른다.
  • z_vrfy_<이름>(): user에서 왔을 때만 거치는 검증 함수. 객체 종류·권한(K_SYSCALL_OBJ), 포인터가 가리키는 메모리를 호출자가 읽고/쓸 수 있는지(K_SYSCALL_MEMORY_READ/WRITE)를 검사하고 z_impl_을 부른다. 실패하면 K_OOPS로 그 스레드에 kernel oops를 낸다.

K_SYSCALL_OBJ는 "이 포인터가 정말 커널이 아는 k_sem 객체이고, 지금 스레드가 권한 비트를 가졌나"를 본다. 커널이 아는 객체 목록은 빌드 때 gen_kobject_list.py가 ELF에서 모든 커널 객체를 찾아 gperf로 perfect hash 표를 만든다. 그래서 CONFIG_USERSPACE 빌드에는 호스트에 gperf가 필요하다 — 랩 VM에는 없어서 첫 빌드가 GPERF-NOTFOUND: not found로 실패했고, GNU gperf 3.1 소스를 /var/tmp/rtos/C8/gperf에 직접 빌드해서 -DGPERF=...로 넘겼다(apt 설치는 공용 상태라 하지 않았다).

무엇을 확인하나: 같은 API 네 개의 비용을 (a) CONFIG_USERSPACE=n, (b) =y의 supervisor 스레드(main), (c) =y의 user 스레드에서. user 스레드는 FPGAIO 카운터를 읽어야 하므로 카운터 페이지를 "특권 RW / user RO" 파티션으로 만들어 기본 memory domain에 넣었다(K_MEM_PARTITION_DEFINE, v7-M이라 4 KB 크기·4 KB 정렬). 세마포어와 메시지 큐는 k_object_access_grant로 권한을 준다. sem_secret은 일부러 권한을 주지 않는다(예제 13).

4.4 Zephyr의 진입 경로 — svc 3에서 z_impl_까지#

그림 5 — Zephyr userspace의 k_sem_give 경로(Cortex-M, arch/arm/core/cortex_m/svc.S → arch/arm/core/userspace.S). FreeRTOS-MPU v2처럼 SVC 핸들러가 복귀 주소를 고쳐서 특권 Thread 모드로 떨어뜨린다. 다른 점은 ⑤ — 퇴장 때 SVC를 한 번 더 내지 않고, 특권 코드가 스스로 msr CONTROL로 nPRIV를 1로 쓴다. 검증에 실패하면 ④에서 K_OOPS로 그 스레드에 kernel oops를 낸다.

소스로 확인한 단계별 핵심 줄:

  • ① include/zephyr/arch/arm/syscall.h의 arch_syscall_invoke1(): register r0 = arg1; register r6 = call_id; svc _SVC_CALL_SYSTEM_CALL(= 3, 같은 파일 23행). FreeRTOS와 달리 SVC 번호는 항상 3이고 API 번호는 r6에 실린다(SVC imm8은 8비트라 API 수백 개를 다 담을 수 없다).
  • ② z_arm_svc: SVC 번호 0(context switch), 1(IRQ offload), 2(runtime except), 3(system call)을 나누고, 3이면 예외 프레임을 스레드의 특권 스택(CONFIG_PRIVILEGED_STACK_SIZE=1024, 이 빌드의 .config)으로 옮기고 복귀 PC를 z_arm_do_syscall로 바꾼다(svc.S 175행 이후 주석의 표).
  • ③ z_arm_do_syscall(userspace.S 320행): r6이 K_SYSCALL_BAD면 그쪽으로, 아니면 ldr ip, =_k_syscall_table; lsl r6, #2; add ip, r6; ldr ip, [ip]; blx ip.
  • ⑤ 같은 파일 끝부분: ldr ip, [sp,#12]; msr PSP, ip(user 스택 복원) → _current->arch.mode |= 1 → mrs ip, CONTROL; orrs ip, ip, #1; msr CONTROL, ip.

FreeRTOS v2(ACL 실패 = 조용히 pdFAIL 반환)와 정책이 다르다: Zephyr는 "권한 위반 = 그 스레드의 버그"로 보고 죽인다(기본 fatal 핸들러는 시스템 정지, k_sys_fatal_error_handler를 앱이 재정의하면 스레드만 정리할 수 있다).
  • BAD2: 하드웨어 MPU 폴트. MMFAR Address 0x20000dd8 = kernel_global의 주소(위 nm). FreeRTOS 예제 9의 BAD1과 같다.
  • BAD3: 커널 함수 z_impl_k_sem_give는 실행은 된다 — 폴트 PC 0x4024가 z_impl_k_sem_give(이 빌드에서 0x4014) 시작 + 0x10, 즉 함수 안이다. Zephyr는 커널 코드를 user에게 실행 가능하게 둔다. 하지만 그 함수가 세마포어 객체(커널 데이터, MMFAR 0x20000928 = sem)를 건드리는 순간 MPU 폴트가 난다. FreeRTOS-MPU는 같은 시도를 커널 코드 첫 명령에서 IACCVIOL로 막았다(예제 9 BAD4). 보호의 단위가 다르다: FreeRTOS-MPU는 코드와 데이터 둘 다, Zephyr는 데이터만.

6. 설계 토론 — 왜 대부분의 MCU RTOS는 경계를 두지 않나, 언제 두어야 하나#

6.1 경계를 두지 않는 이유 세 가지 (이 노트에서 잰 숫자로)#

  1. 시간: 비특권 큐 송신 한 번이 기본 3.9 us → FreeRTOS-MPU v2 13.2 us로, Zephyr는 2.3 us(USERSPACE=n) → 12.4 us(user 스레드)로 늘었다(§5). 드론 rate loop가 8 kHz(125 us 주기)에 IMU 샘플을 큐로 넘기고, 모터 출력·로그·텔레메트리로 API를 10번 부른다고 하면, 기본 빌드는 약 40 us, v2 비특권 빌드는 약 130 us다 — 주기 전체를 넘는다(QEMU icount 기준이라 절대값은 다르지만 비율이 이렇게 벌어진다는 점이 중요하다). 실칩에서는 SVC 진입·복귀마다 예외 스태킹 사이클이 더 붙는다.
  2. 메모리: 커널 코드 +49%(19.7 → 29.3 KB), TCB 96 → 788 바이트, 그리고 v7-M MPU의 2의 거듭제곱 정렬 낭비(이 노트의 빌드는 커널 코드 33.5 KB에 64 KB 리전). 256 KB 플래시·64 KB RAM MCU에서는 치명적이다.
  3. 복잡도: 링커 스크립트에 섹션 세 개, 스택 정렬, 리전 설계, 객체마다 ACL 부여, 비특권에서 금지된 API 목록, 폴트 핸들러 설계. 무엇보다 데이터 공유가 어려워진다 — 전역 변수 하나 읽는 데도 리전이 필요하다(예제 6에서 직접 부딪혔다).

그리고 근본적인 이유: MCU 펌웨어는 보통 한 팀이 쓰고, 한 번에 빌드하고, 한 번에 검증하는 한 덩어리다. Linux처럼 서로 모르는 사람이 쓴 프로그램 수백 개를 한 커널 위에서 돌리는 게 아니다. 격리가 막아 줄 위협(악성 앱, 모르는 코드)이 애초에 적다.

6.2 경계가 필요한 경우#

  • 신뢰 수준이 다른 코드가 섞일 때: 외부 입력(무선 링크·CAN·USB·네트워크)을 파싱하는 코드, 서드파티 라이브러리(센서 퓨전, 통신 스택), 현장에서 업데이트되는 앱 모듈. 파서 버그 하나가 제어 루프를 죽이면 안 될 때.
  • 안전 인증에서 "간섭 없음(freedom from interference)"을 보여야 할 때: ISO 26262·IEC 61508은 서로 다른 안전 등급(ASIL/SIL)의 소프트웨어를 한 MCU에 올리려면 낮은 등급 코드가 높은 등급 코드의 메모리를 깨지 못한다는 근거를 요구한다. MPU 격리는 그 근거의 하드웨어 기반이다(O1, O6).
  • 보안 요구가 있을 때: 국방·차량·의료 제품의 위협 모델에서 "원격으로 들어온 공격자가 한 태스크를 장악해도 다른 태스크·키·부트 상태를 못 건드린다"가 요구사항일 때. 이때는 MPU 격리에 TrustZone-M(F6)과 보안 부트가 함께 간다.
  • 결함 격리·재시작: 비필수 태스크가 죽으면 그 태스크만 재시작하고 시스템은 계속 돈다(MemManage 핸들러에서 해당 태스크를 정리). Hubris가 이 설계를 끝까지 밀고 간 예다(A3 §3.3).

SVC 핸들러 안에서 시스템 콜을 실행하지 않고, 쌓인 예외 프레임의 PC를 고쳐 써서 예외 복귀가 특권 Thread 모드의 커널 함수로 떨어지게 만든다. 이유는 둘 다 같다 — Handler 모드에서 오래 일하면 같거나 낮은 우선순위 인터럽트가 전부 막히고, 시스템 콜이 블로킹(xQueueReceive(..., portMAX_DELAY))해야 할 때 컨텍스트 스위치를 할 수 없다. 특권 Thread 모드에서 돌면 시스템 콜도 보통 태스크 코드처럼 선점되고, 블록되고, 깨어난다. 차이는 퇴장이다: FreeRTOS는 프레임을 다시 태스크 스택으로 옮기려고 SVC를 한 번 더 내고, Zephyr는 특권 코드가 스스로 CONTROL.nPRIV를 1로 써서 내려온다(특권은 언제든 자기 특권을 내릴 수 있다 — 올리는 것만 막혀 있다).

Linux(EL E6)와 비교하면: Linux arm64는 svc #0 → el0_svc → invoke_syscall() → sys_call_table[nr]로 같은 모양이지만, (1) 주소 공간이 달라 copy_from_user로 복사하고, (2) 커널 스택이 스레드마다 따로 있고(Zephyr의 특권 스택·FreeRTOS의 syscall 스택이 그 대응물), (3) 시스템 콜이 원래부터 특권 모드에서 선점 가능하다.

8. 실무에서 다시 보기#

8.1 드론 비행 제어기 — 텔레메트리 파서를 비특권으로#

예를 들어 STM32H7급 비행 제어기라면, 자세 제어 rate loop(IMU 8 kHz)와 모터 출력은 특권 태스크에 두고, 무선 링크로 들어오는 MAVLink·CRSF 프레임을 파싱하는 태스크만 restricted로 만든다. 파서는 외부에서 온 바이트를 다루니 버퍼 오버런 버그가 가장 나기 쉬운 곳이다. 파서와 제어 루프는 큐 하나로만 만난다. 파서가 엉뚱한 주소에 쓰면 MemManage가 나고, 핸들러는 파서 태스크만 지우고 다시 만든다 — 기체는 계속 난다.

이 코드는 이 노트에서 돌리지 않은 설계 스케치다(필드 이름과 portMPU_REGION_* 매크로는 V11.3.2 task.h·ARM_CM3_MPU/portmacro.h에 있는 것만 썼다). 원칙은 두 가지다: 고주파 경로에는 SVC를 두지 않는다, 비특권 쪽과의 접점은 큐 하나로 좁힌다.

8.2 로봇 관절 모터 컨트롤러 — 20 kHz 루프에는 커널 진입 자체가 없다#

FOC 전류 루프(20 kHz = 50 us 주기)는 보통 ADC 완료 ISR 안에서 끝난다. RTOS API를 부르지 않고, 부르더라도 ...FromISR 한두 번이다. 여기서 보호 빌드의 비용은 거의 문제가 안 된다 — ISR은 Handler 모드라 원래 특권이고, 래퍼를 지나지 않는다(ISR 안에서 MPU_xQueueGenericSendFromISR도 CONTROL 검사 후 특권 경로를 탄다). 비용이 드는 건 CAN 명령 처리·진단 같은 태스크 쪽이다. 그래서 모터 컨트롤러에서 격리를 한다면 "CAN 진단·부트로더 통신 태스크만 비특권"이 현실적인 선택이다.

8.3 센서 허브 MCU — 서드파티 퓨전 라이브러리를 Zephyr user 스레드로#

Linux SoC 옆의 센서 허브에서 벤더가 바이너리로 준 센서 퓨전 라이브러리를 돌린다면, Zephyr user 스레드 + 그 라이브러리 전용 memory partition이 깔끔하다. 라이브러리가 쓰는 전역 변수는 K_APP_DMEM(part)/K_APP_BMEM(part)로 파티션에 넣고, 쓸 수 있는 커널 객체(입력 k_msgq, 출력 k_msgq)만 k_object_access_grant로 준다. 라이브러리가 IMU 드라이버 상태나 타임스탬프 카운터를 깨는 일이 원천 차단된다. 비용은 메시지 한 번에 수 us 수준이고, 퓨전 주기(수백 Hz)에서는 무시할 만하다.

8.4 Don의 SSD 펌웨어와 연결#

SSD 컨트롤러에서 호스트 인터페이스 코어가 받은 NVMe 명령을 FTL 코어에 넘길 때, FTL은 명령의 LBA 범위·PRP 주소를 검사한 뒤에야 실행했다. 이게 정확히 z_vrfy_*/MPU_*Impl이 하는 일이다 — 신뢰 경계에서 들어오는 요청은 검사하고, 경계 안쪽 코드끼리는 믿는다. SSD에서도 코어 안 함수 호출에는 검사를 넣지 않았다(성능). 경계를 어디에 긋느냐가 설계의 핵심이라는 점이 RTOS와 같다.

10. 면접에서 이렇게 말한다#

Q. "Is calling xQueueSend() in FreeRTOS a system call?"

A. 기본 빌드에서는 아니다. FreeRTOS는 라이브러리형 커널이라 태스크와 커널이 같은 특권·같은 주소 공간에서 돌고, xQueueSend는 bl xQueueGenericSend 한 줄짜리 함수 호출이다. 비용은 진입이 아니라 임계 구역과 큐 조작에서 나온다. MPU 포트를 쓰면 비특권 태스크의 호출이 svc를 거치는 진짜 시스템 콜이 된다.

In a default build, no. FreeRTOS is a library-style kernel: tasks and the kernel run at the same privilege level in one address space, so xQueueSend compiles to a plain bl xQueueGenericSend. I've checked the disassembly — the only svc in the image is the one that starts the first task. The cost is in the critical section and queue bookkeeping, about 120 instructions on a Cortex-M3. It only becomes a real system call when you use an MPU port, where an unprivileged task's call goes through an SVC.

꼬리 질문: "Then what stops a buggy task from corrupting the kernel?" → 기본 빌드에서는 아무것도 없다. 스택 오버플로 검사와 MPU 스택 가드 정도, 진짜 격리는 FreeRTOS-MPU나 Zephyr userspace.

Q. "Walk me through how an unprivileged task calls the kernel in FreeRTOS-MPU."

A. 앱의 xQueueSend는 mpu_wrappers.h 매크로 때문에 MPU_xQueueGenericSend 래퍼를 부른다. 래퍼는 CONTROL.nPRIV를 보고 비특권이면 svc 33을 낸다. SVC 핸들러는 PC가 syscall 섹션 안인지 확인하고, 프레임을 TCB 안의 syscall 스택으로 복사하고, 특권을 올리고, PC를 Impl 함수로 고쳐서 예외 복귀한다. Impl은 특권 Thread 모드에서 핸들 인덱스·ACL·버퍼 권한을 검사하고 진짜 함수를 부른다. 끝나면 svc 103으로 원래 스택·비특권으로 돌아온다.

The application's xQueueSend is macro-renamed to MPU_xQueueGenericSend. That naked wrapper reads CONTROL; if the task is unprivileged it executes svc 33. The SVC handler checks that the SVC came from the system-call section, copies the hardware frame onto a per-task privileged system-call stack, clears nPRIV, and rewrites the stacked PC to the ...Impl function, so the exception return lands in privileged thread mode. The Impl validates the handle index, the access-control list and any buffer pointer, then calls the real xQueueGenericSend. On return a second SVC, number 103, copies the frame back and drops privilege. I traced exactly this in gdb on QEMU — IPSR 11, then IPSR 0 with CONTROL 0x2, then IPSR 11 again.

꼬리 질문: "Why not just run the call inside the SVC handler?" → 그러면 같은 우선순위 이하 인터럽트가 막히고, 블로킹 API가 컨텍스트 스위치를 못 한다.

Q. "Why can't an unprivileged task simply clear CONTROL.nPRIV and become privileged?"

A. 하드웨어가 막는다. 비특권 Thread 모드에서 msr control은 무시된다 — QEMU에서 직접 해 보면 CONTROL이 0x3 그대로다. 특권으로 가는 유일한 길은 예외이고, 예외 핸들러는 커널이 쓴 코드라 거기서 검사한다.

Because the architecture ignores that write. On ARMv7-M an msr control from unprivileged thread mode has no effect — I tried it and CONTROL stayed 0x3. The only way up is an exception, and the exception handlers are kernel code, so that's where the checks live. Lowering privilege, on the other hand, is always allowed, which is why Zephyr can drop back to user mode with a plain msr at the end of a syscall.

Q. "What does Zephyr generate from a __syscall declaration?"

A. 빌드 때 스크립트가 헤더의 __syscall 함수를 모아 번호를 매기고, API 이름의 인라인 함수(유저 컨텍스트면 arch_syscall_invoke로 svc, 아니면 z_impl_ 직접 호출), 인자를 풀어 z_vrfy_를 부르는 z_mrsh_ 마샬링 함수, 그리고 디스패치 표 _k_syscall_table을 만든다. 개발자는 z_impl_(진짜 구현)과 z_vrfy_(검사)만 쓴다.

At build time a script scans headers for __syscall prototypes, assigns each a number, and generates three things: an inline wrapper with the API name — it checks whether the caller is in user context and either traps with svc via arch_syscall_invoke or calls z_impl_ directly; a z_mrsh_ marshalling stub that unpacks the registers and calls the z_vrfy_ verifier; and the _k_syscall_table dispatch table. The developer writes only z_impl_, the real implementation, and z_vrfy_, which checks object permissions and memory ranges before calling z_impl_.

Q. "What does memory protection cost you, and would you enable it on a flight controller?"

A. 내가 잰 숫자로는 비특권 큐 송신이 기본 3.9 us에서 FreeRTOS-MPU v2 13.2 us로 3배 이상, 커널 코드 +49%, TCB 8배다. 비행 제어기라면 rate loop는 특권에 두고, 외부 입력 파서 같은 신뢰 못 할 코드만 비특권으로 만들고, 둘 사이는 큐 하나로 연결하겠다.

On QEMU with deterministic instruction counting, an unprivileged queue send went from 3.9 microseconds in a plain build to 13.2 with FreeRTOS-MPU v2 — over three times — and kernel code grew about 49 percent, the TCB from 96 to 788 bytes, plus MPU alignment waste. So I wouldn't put the rate loop behind the boundary. I'd keep the control loop and drivers privileged, run the parts that touch untrusted input — the telemetry or MAVLink parser, third-party libraries — as restricted tasks, and connect them through a single queue. That gives fault containment where bugs are likely, without paying the syscall cost in the 8 kHz path.

Q. "What problem does FreeRTOS-MPU v2 solve that v1 didn't?"

A. v1은 래퍼가 특권을 올린 채 진짜 API를 불러서, 비특권 태스크가 아무 포인터를 핸들로 넘기면 커널이 그 주소에 대신 써 준다(confused deputy). v2는 핸들을 정수 인덱스로 바꾸고, ACL과 버퍼 권한 검사를 넣고, syscall 전용 스택을 써서 그 구멍을 막았다. 대신 느리다 — 내 측정에서 v1 5.2 us, v2 13.2 us.

v1 just raised privilege and called the real API, so an unprivileged task could pass any pointer as a handle and the kernel would happily write through it — a confused-deputy problem. v2, introduced in 10.6.0, makes handles opaque integer indices into a kernel object pool, adds per-task access-control lists and checks that every buffer pointer is accessible to the caller, and runs the call on a separate privileged stack. In my measurement the unprivileged queue send was 5.2 microseconds with v1 and 13.2 with v2, so the extra validation is not free.

Q. "How would you debug a MemManage fault in a restricted task?"

A. CFSR의 MMFSR 비트로 데이터 접근(DACCVIOL)인지 명령 접근(IACCVIOL)인지 보고, MMARVALID면 MMFAR이 문제 주소다. 쌓인 프레임의 PC로 명령을, MMFAR을 map 파일·nm으로 대조해 어떤 변수인지 찾는다. 그리고 그 순간 MPU 리전을 덤프해서 그 주소가 왜 막혔는지 확인한다.

I read the CFSR: DACCVIOL means a data access, IACCVIOL an instruction fetch, and if MMARVALID is set, MMFAR holds the faulting address. I take the stacked PC from the exception frame for the instruction, and look up MMFAR in the map file — in my lab a fault at 0x20009004 turned out to be a global the restricted task wasn't granted. Then I dump the MPU regions to see which rule blocked it. One gotcha: dump them from privileged context; even the debugger's memory reads go through the MPU with the current privilege on QEMU.

13. 요약 & 체크리스트#

기본 FreeRTOS·Zephyr에서 커널 API는 함수 호출이다. 모드 전환도 인자 검사도 없고, 비용은 커널이 하는 일 자체(임계 구역·리스트·복사)다. 보호 빌드를 켜면 비특권 코드는 스스로 특권을 올릴 수 없으니 SVC 예외로 커널에 부탁해야 한다. FreeRTOS-MPU v2는 매크로로 API 이름을 래퍼로 바꾸고, 래퍼가 svc N을 내고, 핸들러가 syscall 전용 스택·특권 Thread 모드로 Impl을 실행시키며 인덱스 핸들·ACL·버퍼 권한을 검사하고, svc 103으로 돌아온다. Zephyr는 __syscall 선언에서 진입·마샬링·디스패치 코드를 생성하고, svc 3 한 번으로 들어가 z_vrfy_로 객체 권한과 메모리 범위를 검사한 뒤 z_impl_을 부르고, CONTROL을 직접 써서 내려온다. 보호의 대가는 이 노트 측정으로 호출당 수 배의 시간, 커널 코드 +49%, TCB 8배, MPU 정렬 낭비다. 그래서 대부분의 MCU 제품은 경계를 두지 않고, 두더라도 신뢰 못 할 코드만 비특권으로, 고주파 제어는 특권으로 나눈다.
