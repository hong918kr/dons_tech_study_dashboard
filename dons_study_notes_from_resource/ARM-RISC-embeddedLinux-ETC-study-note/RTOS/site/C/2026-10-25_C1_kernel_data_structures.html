0. 큰 그림 — 스케줄러는 "리스트 관리자"다#

RTOS 스케줄러가 매번 하는 질문은 하나다: "지금 Ready인 태스크 중 우선순위가 가장 높은 것은 누구인가?" 이 질문에 빨리, 그리고 항상 같은 시간 안에 답하려고 커널은 몇 개의 리스트와 비트맵 하나를 들고 있다. 태스크가 블록되면 이 리스트에서 저 리스트로 옮기고, 깨어나면 다시 옮기고, 스위치할 때는 맨 앞을 집는다. 그게 전부다. 그래서 RTOS 커널 소스를 읽는 첫 관문이 list.c(FreeRTOS에서 248줄)다.

Don의 SSD 펌웨어로 바꿔 보면 익숙한 모양이다. SSD 컨트롤러 펌웨어는 보통 malloc 없이 고정 SRAM에 미리 잡아 둔 명령 슬롯을 쓰고, 슬롯 구조체 안에 next/prev 포인터를 박아 두어 "호스트 명령 대기 큐", "NAND 다이별 큐", "완료 큐" 사이를 옮긴다(슬롯 복사 없이 포인터만 바꾼다). "어느 다이 큐에 일이 있나"를 비트맵으로 들고 있다가 find-first-set 한 번으로 고르는 것도 흔한 기법이다. RTOS 커널이 정확히 이 일을 한다 — 슬롯 대신 TCB, 큐 대신 ready/delayed/event 리스트, 다이 비트맵 대신 우선순위 비트맵이다.

그림 1 — ex3(예제 3)의 덤프 1을 그대로 옮긴 커널 리스트 지도. 왼쪽은 우선순위별 ready 리스트 배열과 "비어 있지 않은 우선순위" 비트맵, 오른쪽은 블록된 태스크가 걸리는 리스트들. pending 줄은 같은 예제의 덤프 3, 큐 줄은 §2.5의 규칙(값 = 8 − 우선순위)으로 채웠다.

1. 리스트 하나 해부 — list.c#

1.1 직관 — "끼워 넣는" 리스트와 리스트 안의 끝 표시#

교과서의 연결 리스트는 노드를 따로 malloc해서 데이터 포인터를 담는다. 커널은 그렇게 하지 않는다. 리스트 항목(ListItem_t)을 TCB 구조체 안에 박아 두고(intrusive list), 항목에서 주인(TCB)으로 돌아가는 포인터 pvOwner를 둔다. 그래서 태스크를 리스트에 넣거나 뺄 때 메모리 할당이 전혀 없고, 포인터 네 개만 고친다. Don이 SSD 명령 슬롯에 next/prev를 박아 두던 것과 같다. Linux 커널의 struct list_head + container_of도 같은 발상인데, FreeRTOS는 container_of 계산 대신 pvOwner 포인터 한 칸(4 B)을 써서 더 단순하게 간다.

두 번째 특징은 끝 표시 항목(sentinel) 이 리스트 구조체 List_t 안에 들어 있다는 점이다. 리스트는 원형(circular)이고, 끝 표시 xListEnd는 값이 portMAX_DELAY(32비트 tick이면 0xffffffff)로 고정된 가짜 항목이다. 그래서

  • 빈 리스트도 "END → END"로 닫혀 있어서 NULL 검사가 필요 없다.
  • 정렬 삽입 루프는 "다음 항목 값이 내 값보다 크면 멈춘다"만 검사하면 된다 — END의 값이 최댓값이라 반드시 거기서 멈춘다.
  • 맨 끝(=END의 바로 앞)이 xListEnd.pxPrevious로 바로 보이므로 끝 삽입이 O(1)이다.

세 번째 특징은 역방향 포인터 두 개다. 항목은 자기가 어느 리스트에 있는지(pxContainer)를 알고, 리스트는 자기 항목 수(uxNumberOfItems)를 센다. 덕분에 "이 태스크를 지금 있는 리스트에서 빼라"(uxListRemove)가 리스트를 몰라도 O(1)이고, "이 우선순위 ready 리스트가 비었나"가 O(1)이다.

출력에서 볼 것: ListItem_t 20 B, MiniListItem_t 12 B, List_t 20 B(4 + 4 + 12). 소스는 pxContainer인데 gdb는 pvContainer 라고 보여 준다 — FreeRTOS.h의 하위 호환 블록(configENABLE_BACKWARD_COMPATIBILITY, 기본 1)에 #define pxContainer pvContainer가 있어서 컴파일러가 실제로 본 이름은 pvContainer다. 디버거 스크립트(예제 4)를 쓸 때 이 이름을 써야 한다. 전역 리스트는 하나에 20 B(0x14)이고, ready 배열은 configMAX_PRIORITIES × 20 B다: 8단계 = 0xa0(160 B), 4단계 = 0x50(80 B), 64단계 = 0x500(1280 B). 우선순위를 "넉넉하게 32개"로 잡으면 ready 배열만 640 B — 작은 MCU에서는 무시 못 할 RAM이다. 또 하나: 이 빌드의 심볼 타입이 대문자 B(전역)인 것은 -DportREMOVE_STATIC_QUALIFIER로 빌드했기 때문이다. 보통 빌드(아래 두 줄)는 소문자 b(파일 static)다(§2.3).

1.4 예제 2 — list.c만 떼어서 돌려 보기#

무엇을 확인하나: 스케줄러 없이 List_t 두 개를 직접 만들어서 (1) vListInsert의 정렬 삽입과 같은 값의 순서, (2) vListInsertEnd + listGET_OWNER_OF_NEXT_ENTRY의 round-robin, (3) pxIndex가 가리키는 항목을 지울 때 인덱스가 어떻게 되는지를 주소와 함께 찍는다. 항목의 owner로는 TCB 대신 이름 문자열을 넣었다.

출력에서 볼 것: 빈 리스트는 END의 next/prev가 자기 자신(0x200000f4)이다. 30, 10, 20, 20 순서로 넣으면 B(10) → C(20) → D(20) → A(30)로 정렬되고, 같은 값 20은 먼저 들어온 C가 앞이다(FIFO). round-robin 리스트에서 NEXT_ENTRY는 A B C A B로 돌고, 인덱스가 B에 있을 때 D를 끝 삽입하면 D는 리스트의 물리적 끝이 아니라 인덱스(B) 바로 앞에 들어가서 C → A → D → B 순서로 나온다 — "지금 바퀴의 맨 마지막 차례"에 끼는 것이다. 인덱스가 가리키던 B를 지우면 pxIndex는 B의 이전 항목 D로 물러나고, 지워진 항목의 pxContainer는 0이 된다.

그림 2 — 예제 2에서 네 번 정렬 삽입한 뒤의 리스트 S(주소는 출력 그대로, 앞의 0x2000_00 생략). 끝 표시 xListEnd는 List_t 안(@ec + 8 = @f4)에 박혀 있고, 실선이 pxNext, 점선이 pxPrevious다.

1.5 네 함수를 줄 단위로#

list.c는 함수 다섯 개(초기화 두 개 + 삽입 두 개 + 제거 한 개)가 전부다. 트레이스 매크로를 빼면 이렇다.

vListInitialise(pxList) — pxIndex와 END의 next/prev를 전부 END 자신으로, END의 값을 portMAX_DELAY로, 항목 수를 0으로. 리스트가 "END 하나짜리 원"이 된다. listLIST_IS_INITIALISED()는 "END 값이 portMAX_DELAY인가"로 초기화 여부를 판단한다.

vListInsertEnd(pxList, pxNewListItem) — O(1). 새 항목을 pxIndex 바로 앞에 넣는다.

pxIndex가 END에 있으면(한 번도 순회하지 않은 리스트) "END 앞 = 물리적 끝"이라 이름 그대로 끝 삽입이다. 순회 중이면 "다음 바퀴에서 가장 늦게 나올 자리"다. ready 리스트에 태스크를 넣는 prvAddTaskToReadyList()가 이 함수(정확히는 같은 일을 하는 인라인 매크로 listINSERT_END)를 쓴다 — 그래서 막 깨어난 태스크는 같은 우선순위 줄의 맨 뒤에 선다.

vListInsert(pxList, pxNewListItem) — O(n). 값 오름차순 자리를 찾아 넣는다.

두 가지 세부가 중요하다. 첫째, 비교가 <=라서 같은 값은 기존 항목 뒤로 간다(예제 2의 C, D). 소스 주석도 "같은 값이면 뒤에 넣어야 ready 리스트의 태스크들이 CPU를 나눠 쓴다"고 설명한다. 둘째, 값이 portMAX_DELAY면 루프를 건너뛴다. 끝 표시도 같은 값이라 <= 루프가 END를 지나쳐 영원히 돌기 때문이다.

같은 함수 안에 FreeRTOS에서 가장 유명한 주석이 있다: "If you find your application is crashing here then likely causes are listed below." 원인으로 꼽힌 다섯 가지는 (1) 스택 오버플로, (2) Cortex-M 인터럽트 우선순위 설정 오류(configMAX_SYSCALL_INTERRUPT_PRIORITY보다 높은 ISR에서 API 호출), (3) 크리티컬 섹션 안이나 스케줄러 정지 중에 API 호출, 또는 ISR에서 FromISR가 아닌 API 호출, (4) 초기화 전 큐·세마포어 사용(스케줄러 시작 전에 인터럽트가 뜨는 경우), (5) 중첩 인터럽트 포트에서 tick 인터럽트 우선순위가 configMAX_SYSCALL_INTERRUPT_PRIORITY보다 높은 경우다. 전부 "리스트가 동시에 두 곳에서 고쳐져서 원이 깨졌다"는 한 가지 증상의 다른 원인이다. 원이 깨지면 이 빈 for 루프가 END를 영영 못 만나서 CPU가 여기서 멈춘다 — 디버거를 붙였을 때 PC가 vListInsert에 있으면 99% 이 경우다(§8).

uxListRemove(pxItemToRemove) — O(1). 이웃끼리 서로 잇고, 지우는 항목이 pxIndex였으면 인덱스를 이전 항목으로 물린다(그래야 다음 NEXT_ENTRY가 지운 항목의 다음 태스크를 고른다). pxContainer를 NULL로 만들고 남은 항목 수를 반환한다. 이 반환값이 중요하다 — 0이면 "이 우선순위 ready 리스트가 막 비었다"는 뜻이라 호출자가 비트맵의 해당 비트를 지운다(§3.2).

1.6 흔한 함정#

  • 한 항목을 두 리스트에 넣기: 항목에는 pxNext/pxPrevious가 한 쌍뿐이다. 빼지 않고 다른 리스트에 넣으면 앞 리스트의 원이 깨진다. 커널이 prvAddCurrentTaskToDelayedList()에서 먼저 uxListRemove(&xStateListItem)를 부르는 이유("the same list item is used for both lists")다.
  • portMAX_DELAY 값의 의미 혼동: 리스트 입장에선 "가장 큰 값"일 뿐이다. "무한 대기"라는 의미는 tasks.c가 붙인다(INCLUDE_vTaskSuspend == 1이면 무한 대기 태스크를 delayed 리스트가 아니라 suspended 리스트에 넣는다 — A4 §3.2).
  • 리스트를 직접 걷기: 애플리케이션이 커널 리스트를 걸으면(예제 3처럼) 반드시 크리티컬 섹션 안에서 해야 한다. 걷는 도중 tick ISR이 항목을 옮기면 엉뚱한 리스트로 넘어가 무한 루프가 된다.

2.5 이벤트 리스트 — 왜 값이 configMAX_PRIORITIES − 우선순위인가#

큐에 대기자가 여럿이면 가장 높은 우선순위가 먼저 받아야 한다. 리스트는 값 오름차순으로 정렬되고 맨 앞을 꺼내니, 높은 우선순위가 작은 값이 되도록 뒤집으면 된다. 태스크를 만들 때 prvInitialiseNewTask()가

Therefore, the event list is sorted in descending priority order." 깨울 때는 listGET_OWNER_OF_HEAD_ENTRY로 맨 앞 하나 — O(1)이다. 비용은 넣을 때(대기자 수만큼) 치르고 꺼낼 때(ISR에서 give할 때) 안 치르는 설계다. ISR 쪽 경로를 짧게 하려는 선택이다.

예외가 둘 있다.

  • 이벤트 그룹: vTaskPlaceOnUnorderedEventList()는 이벤트 항목 값에 기다리는 비트 패턴을 넣고 최상위 비트 taskEVENT_LIST_ITEM_VALUE_IN_USE(32비트 tick에서 0x80000000)를 켠다. 정렬하지 않고 끝 삽입한다(이벤트 그룹은 set할 때 대기자 전부를 훑어야 하니 순서가 의미 없다 — D7).
  • 우선순위 변경: vTaskPrioritySet()과 우선순위 상속(xTaskPriorityInherit())은 IN_USE 비트가 꺼져 있을 때만 이벤트 항목 값을 새 우선순위로 고친다. 그리고 ready 리스트에 있으면 새 우선순위 리스트로 옮기지만, 이벤트 리스트 안의 위치는 다시 정렬하지 않는다(소스: "If the task is in the blocked or suspended list we need do nothing more than change its priority variable"). 대기 중에 우선순위가 바뀐 태스크는 옛 자리에 남는다 — 드물지만 알아 둘 만한 비대칭이다(D3).

2.7 tick wrap 트릭 — 구조만 (시간 로직은 C5)#

delayed 리스트를 하나만 쓰면 "깨울 tick = 지금 + 대기"가 32비트를 넘쳐 작은 수가 될 때 정렬이 망가진다(0xfffffff5보다 24가 먼저 깨는 것으로 보인다). FreeRTOS의 해법은 리스트 두 개 + 포인터 두 개다.

  • 넘치지 않은 깨울 시각 → pxDelayedTaskList가 가리키는 리스트에 정렬 삽입
  • 넘친 깨울 시각 → pxOverflowDelayedTaskList가 가리키는 리스트에 정렬 삽입
  • tick이 0으로 넘어가는 순간(xTaskIncrementTick() 안 if( xConstTickCount == ( TickType_t ) 0U )) → taskSWITCH_DELAYED_LISTS(): 현재 리스트가 비었는지 configASSERT로 확인하고(넘치기 전 시각은 모두 지났으니 비어 있어야 한다) 두 포인터를 맞바꾼 뒤 xNextTaskUnblockTime을 다시 계산

그래서 리스트 안의 비교는 항상 "같은 바퀴 안의 절댓값"끼리만 일어나고, 비교 한 번 늘리지 않고 wrap을 처리한다. 리스트를 복사하지 않고 포인터만 바꾸는 게 핵심이다. Zephyr는 아예 다른 길(64비트 tick + delta 리스트)을 간다(§5.4). 언제 깨우는지, vTaskDelay와 vTaskDelayUntil의 차이, tick 카운터 폭(16/32/64비트) 선택은 C5에서 다룬다.

2.8 삭제 대기 리스트#

xTasksWaitingTermination은 자기 삭제(vTaskDelete(NULL))한 태스크가 들어가는 곳이다. 자기 스택 위에서 도는 중이라 스스로 free할 수 없으니 상태 항목만 이 리스트에 넣고, idle 태스크의 prvCheckTasksWaitingTermination()이 나중에 TCB와 스택을 회수한다. A4 예제 2에서 idle이 굶으면 heap이 안 돌아오는 것을 이미 측정했으니 여기서는 "구조상 또 하나의 끝 삽입 리스트"로만 기억한다(자세히는 C9).

3. "다음은 누구?" — 최고 우선순위 Ready 태스크 고르기#

3.1 직관 — 층별 대기줄과 "사람 있는 층" 표시등#

ready 리스트 배열은 우선순위마다 하나씩 있는 대기줄이다. 스케줄러는 "사람이 서 있는 가장 높은 층"을 찾아서 그 줄의 다음 사람을 부른다. 찾는 방법이 둘이다: 꼭대기 층부터 한 층씩 내려가며 줄을 들여다보거나(generic), 층마다 "사람 있음" 표시등을 한 비트씩 켜 둔 판을 보고 맨 위 켜진 등을 한 번에 읽거나(port-optimised). 후자가 비트맵 + CLZ다.

FreeRTOS에서 이 선택은 vTaskSwitchContext()(PendSV 핸들러가 부른다, C2) 안의 매크로 taskSELECT_HIGHEST_PRIORITY_TASK() 하나다. 어느 쪽 구현을 쓸지는 configUSE_PORT_OPTIMISED_TASK_SELECTION이 정한다.

3.2 두 구현 — 소스 그대로#

generic (configUSE_PORT_OPTIMISED_TASK_SELECTION 0, tasks.c):

uxTopReadyPriority는 "이보다 높은 우선순위에는 확실히 아무도 없다"는 상한이다. 태스크가 ready가 될 때 더 높으면 올리고(O(1)), 블록될 때는 아무것도 안 한다. 내리는 일은 다음 선택 때 빈 리스트를 하나씩 내려가며 한다(lazy). 그래서 비용은 "방금 비워진 최고 우선순위"와 "실제 최고 ready 우선순위" 사이의 빈 층 수에 비례한다. 최악은 configMAX_PRIORITIES − 1층 전부.

port-optimised (portable/GCC/ARM_CM3/portmacro.h):

이때 같은 변수 uxTopReadyPriority가 비트맵으로 쓰인다(비트 p = "우선순위 p ready 리스트가 비어 있지 않음"). 예제 3의 top=0x43이 그 비트맵이었다. 선택은 31 − clz(비트맵) 한 번, 그 다음 listGET_OWNER_OF_NEXT_ENTRY. 비트를 지우는 taskRESET_READY_PRIORITY()는 해당 ready 리스트 길이가 0이 될 때만 부른다 — 그래서 uxListRemove()가 남은 항목 수를 반환하는 것이다.

제약도 소스에 그대로 있다: configMAX_PRIORITIES > 32이면 #error("It is very rare that a system requires more than 10 to 15 difference priorities as tasks that share a priority will time slice"). 비트맵이 32비트 한 워드라서다. 포트별 기본값은 V11.3.2 기준으로 이렇다.

3.3 예제 5 — 역어셈블로 clz 확인하기#

무엇을 확인하나: 예제 6의 두 빌드(configMAX_PRIORITIES 8, 선택 방식 0/1)에서 vTaskSwitchContext의 기계어를 비교한다. 템플릿 FreeRTOSConfig.h는 이 값을 #ifndef 없이 1로 박아 두었으므로, 예제 6의 앱 폴더에 템플릿을 include한 뒤 #undef하는 설정 파일을 두었다(예제 6 참고).

출력에서 볼 것: port-optimised 빌드에는 ldr r3, [r3, #0](비트맵 로드) → clz r3, r3 → uxtb → rsb r3, r3, #31(31 − clz)이 일직선으로 있고 반복이 없다. 그 뒤 add.w r3, r3, r3, lsl #2 / lsls r2, r3, #2는 우선순위 × 20(= List_t 크기)으로 배열 주소를 만드는 계산이다(5 × 4). generic 빌드에는 0x750~0x75a에 빈 리스트 한 개당 명령 5개짜리 루프가 있다: cbz r3(= configASSERT(uxTopPriority), 0까지 내려가면 assert) → ldr.w r1, [r2, #-20]!(한 칸 아래 리스트의 uxNumberOfItems, 주소를 20 B 내리며 읽음) → subs r3, #1 → cmp r1, #0 → beq. 두 빌드 모두 앞부분에 run-time stats(board_now_us)와 스택 오버플로 검사(0xa5a5a5a5 비교, A4 §5.5)가 들어 있다 — 이 랩 설정에서는 그쪽이 선택보다 더 비싸다는 것도 보인다.

3.4 예제 6 — 선택 비용을 우선순위 개수별로 재기#

무엇을 확인하나: 우선순위 configMAX_PRIORITIES − 1인 H와 우선순위 1인 L 두 태스크(+ idle)가 태스크 알림으로 핑퐁한다. H가 ulTaskNotifyTake(portMAX_DELAY)로 블록하면 스케줄러는 꼭대기에서 우선순위 1까지 내려가야 L을 찾는다 — generic의 최악에 가까운 상황이다. "H 블록 → L 실행 시작"(block->L)과 "L의 give → H 복귀"(give->H)를 FPGAIO 카운터로 2000번 재서 평균을 낸다. 우선순위 개수 4~64, 선택 방식 0/1을 바꿔 가며 빌드한다(1은 32까지만 허용). 타이머 태스크는 꺼서 리스트를 단순하게 했다.

출력에서 볼 것: port-optimised는 우선순위가 4개든 32개든 231.5 cycle로 한 자리도 안 변한다. generic은 4개일 때 235.6에서 64개일 때 474.6으로 늘어난다. 기울기 (474.6 − 235.6) / 60 = 3.98 cycle / 빈 우선순위 = 명령 4.98개(1 cycle = 명령 1.25개) — 예제 5에서 센 루프 명령 5개와 정확히 맞는다. 반대 방향(give->H, 192 cycle 근처)은 두 방식이 같다. 깨울 때는 generic도 if (p > top) top = p 한 번이라 O(1)이고, 비용은 블록하는 쪽(최고 우선순위가 비는 순간)에만 붙는다.

그림 6 — 예제 6의 측정값. 25 MHz 칩이라고 치면 템플릿 기본값 8단계에서 generic의 추가 비용은 18 cycle(0.7 us), 32단계에서 115 cycle(4.6 us), 64단계에서 239 cycle(9.6 us)이다. 절대값은 QEMU icount 기준.

실무 해석: 우선순위 8~16단계에서 generic의 추가 비용은 컨텍스트 스위치 전체(이 랩에서 약 230 cycle)의 10% 안팎이다. "CLZ라서 O(1)"이 중요한 이유는 평균 속도보다 상한이 우선순위 개수와 무관하다는 데 있다. Cortex-M0(CLZ 없음)에서는 generic만 가능하니 우선순위 개수를 작게(5~8) 잡는 게 그 자체로 최적화다.

3.5 같은 우선순위끼리 — pxIndex round-robin#

최고 우선순위를 정한 뒤 그 리스트의 "누구"를 고르는 것이 listGET_OWNER_OF_NEXT_ENTRY다.

리스트에서 태스크를 빼거나 끝으로 옮기지 않고 커서만 한 칸 민다. 예제 2의 "NEXT_ENTRY x5: A B C A B"가 이 동작이다. 같은 우선순위 태스크가 여럿이면 tick마다(time slicing, configUSE_TIME_SLICING 1) 또는 yield할 때마다 커서가 돌아서 공평하게 돈다. 새로 ready가 된 태스크는 listINSERT_END로 커서 바로 앞, 즉 "이번 바퀴의 맨 마지막"에 들어간다(예제 2의 D). 정책 차원의 이야기(time slicing 켜고 끄기, 협력형, 지터)는 C4에서 한다.

3.6 흔한 함정#

  • "우선순위를 넉넉히 32개": RAM(ready 배열 640 B)과 generic 선택 비용이 같이 는다. 포트 최적화가 꺼진 칩(M0·M23)에서 특히 손해다. 실제로 쓰는 단계 수 + 여유 1~2개면 충분하다.
  • 비트맵 직접 해석 실수: uxTopReadyPriority는 설정에 따라 "숫자"(generic)이기도 하고 "비트맵"(optimised)이기도 하다. 디버거로 볼 때 어느 쪽인지 먼저 확인해야 한다(예제 3의 0x43은 우선순위 67이 아니다).
  • 우선순위 0 리스트가 비는 상황: idle 태스크가 항상 ready[0]에 있으므로 generic 루프는 0에서 반드시 멈춘다. idle을 지우거나 블록시키면(idle hook에서 블록 API 호출) configASSERT(uxTopPriority)가 터진다 — idle hook에서 블록 금지 규칙의 구조적 이유다(C9).

4.3 예제 8 — 같은 tick에 K개가 깨어나면 tick ISR이 길어진다#

무엇을 확인하나: 태스크 K개가 모두 tick 100에 깨도록 잠들게 하고, SysTick ISR 하나하나의 길이를 잰다. 포트의 SysTick 핸들러 이름을 앱 설정에서 c1_port_systick으로 바꾸고, 진짜 벡터 SysTick_Handler는 앱이 정의해서 카운터로 감싼다. 평소 tick(10~89번째)의 평균·최대와 깨움 tick(100번째)의 길이를 출력한다.

출력에서 볼 것: 깰 태스크가 없는 평소 tick ISR은 항상 39 cycle — xTaskIncrementTick()이 xConstTickCount >= xNextTaskUnblockTime 비교 한 번으로 끝난다(delayed 리스트를 보지도 않는다. 맨 앞 값을 xNextTaskUnblockTime에 캐시해 둔 덕분이다). 깨움 tick은 K에 비례해 늘어서 K=64면 2567 cycle = 102.7 us, 기울기 (2567 − 39) / 64 ≈ 39.5 cycle(명령 약 49개) / 태스크다. 깨어나는 태스크마다 delayed 리스트에서 빼고, 이벤트 리스트에 있으면 거기서도 빼고, ready 리스트에 넣고, 비트맵을 켜고, 선점이 필요한지 비교한다. 이 전부가 BASEPRI가 올라간 상태에서 일어난다.

그림 8 — 예제 8. 같은 tick에 64개가 깨면 그 tick 동안 커널 인터럽트 우선순위 이하의 ISR은 최대 약 100 us 늦게 들어온다(QEMU icount 기준).

4.4 그래서 결정적인가 — 실무 규칙#

O(n)이 있다고 RTOS가 비결정적인 것은 아니다. 태스크 수 n은 설계 시점에 정해진 상한이 있으므로 최악 시간도 상한이 있다(bounded). 문제는 그 상한이 n과 함께 커진다는 것, 그리고 어느 O(n)이 인터럽트를 막느냐다. 실무 규칙으로 정리하면:

  • 태스크 수를 적게 유지한다. 드론 FC급 시스템도 태스크 10~20개면 충분하다. 128개를 만들면 정렬 삽입·tick 일괄 깨움의 최악이 그만큼 커진다.
  • 같은 tick에 많은 태스크를 깨우지 않는다. 주기가 같은 태스크 여럿을 vTaskDelayUntil로 같은 위상에 두면 매 주기 같은 tick에 일괄 깨움이 생긴다. 위상을 엇갈리거나, 한 태스크가 큐·알림으로 나머지를 깨우는 구조가 낫다.
  • 긴 timeout을 가진 대기자가 많으면 delayed 리스트가 길어진다. 무한 대기(portMAX_DELAY)는 delayed가 아니라 suspended 리스트로 가니(O(1) 끝 삽입) 대기 시간에 의미가 없다면 무한 대기가 정렬 비용도 없다.
  • 한 큐에 대기자를 많이 두지 않는다. 이벤트 리스트 삽입이 대기자 수에 비례한다. 여러 소비자가 한 큐를 기다리는 구조라면 대기자는 보통 2~3개를 넘기지 않는다.
  • 측정한다. tick ISR 길이와 PendSV 길이는 GPIO 토글이나 사이클 카운터(DWT CYCCNT)로 쉽게 잴 수 있다. 이 노트의 예제 8을 실제 보드에서 GPIO로 바꾸면 그대로 쓸 수 있다.

Don에게 익숙한 말로: "핫패스는 O(1), O(n)은 인터럽트를 열어 둔 백그라운드에서, 그리고 n의 상한을 문서로 남겨라" — SSD 펌웨어에서 명령 디스패치 경로를 다루던 규칙과 같다.

5. Zephyr — 같은 문제, 다른 답#

5.1 _kernel과 sys_dlist_t#

Zephyr 커널의 전역 상태는 구조체 하나 struct z_kernel _kernel(include/zephyr/kernel_structs.h)에 모여 있다.

리스트 기본형은 sys_dlist_t(include/zephyr/sys/dlist.h)다. 노드 struct _dnode는 포인터 두 개뿐이고(union으로 head/next, tail/prev를 겸한다), 리스트 머리도 같은 구조체라서 FreeRTOS의 xListEnd처럼 머리 자체가 센티널인 원형 리스트다. SMP에서는 현재 스레드를 queue에서 빼 둔다(C10).

5.3 wait_q — 대기자 리스트#

커널 객체(세마포어·뮤텍스·큐 …)의 대기자 리스트는 _wait_q_t이고, 구현은 choice WAITQ_ALGORITHM이 정한다: CONFIG_WAITQ_SIMPLE(기본, sys_dlist_t + z_priq_simple_add = 우선순위 정렬 삽입) 또는 CONFIG_WAITQ_SCALABLE(rbtree). 깨울 때는 z_unpend_first_thread() → _priq_wait_best() = 머리 하나. FreeRTOS 이벤트 리스트와 정확히 같은 정책(넣을 때 정렬, 꺼낼 때 O(1))이다.

대기 진입 경로는 z_pend_curr() → pend_locked() → add_to_waitq_locked()(_priq_wait_add) + add_thread_timeout()(z_add_thread_timeout → z_add_timeout)이다. 여기서 FreeRTOS와 결정적인 차이가 하나 있다: Zephyr는 이 정렬 삽입들을 _sched_spinlock을 쥔 채 한다. 단일 코어에서 k_spin_lock()은 arch_irq_lock(), 즉 인터럽트 마스크다. FreeRTOS가 O(n) 삽입을 "스케줄러 정지 + 인터럽트 허용"으로 하는 것과 달리, Zephyr의 wait_q·timeout 정렬 삽입 길이는 인터럽트 지연에 더해진다. 대기자·timeout 수가 적은 일반적인 시스템에서는 몇 노드짜리라 문제가 안 되지만, "스레드 수 상한을 문서로 남겨라"는 규칙이 Zephyr에서 더 중요한 이유다.

5.4 timeout 리스트 — delta 리스트와 64비트 tick#

kernel/timeout.c는 timeout을 하나의 sys_dlist_t timeout_list(static)에 넣는다. 각 노드(struct _timeout)의 dticks는 절대 시각이 아니라 바로 앞 노드와의 차이다(delta list). z_add_timeout()이 앞에서부터 dticks를 빼 가며 자리를 찾고(O(n)), 끼운 뒤 다음 노드의 dticks에서 자기 몫을 뺀다. 시간이 흐르면 sys_clock_announce() → sys_clock_announce_locked()가 머리 노드의 dticks만 줄이고, 0이 된 머리들을 꺼내 콜백(t->fn, 스레드면 깨우기)을 부른다. 시계는 static uint64_t curr_tick 64비트라 FreeRTOS 같은 wrap 대비 리스트 두 개가 필요 없다.

5.5 예제 9 — Zephyr 커널 큐를 살아 있는 채로 덤프하기#

무엇을 확인하나: 같은 앱을 세 ready queue 구현으로 빌드해서, main(우선순위 0)이 5 ms 자고 일어난 순간 (1) _kernel.ready_q의 내용(구현별로 걷는 법이 다르다), (2) 세마포어 sem.wait_q의 순서, (3) timeout 리스트를 찍는다. 스레드 구성: A5·B5(우선순위 5, 무한 루프), C7(7, 무한 루프 — 영원히 ready로 굶는다), W2·W4·W3(세마포어를 무한 대기), W3t(3, 500 ms timeout 대기), S30·S10·S20(1, 각각 30·10·20 ms 수면). _kernel은 kernel_structs.h가 extern으로 공개하므로 C에서 바로 볼 수 있지만, timeout_list는 static이라 S10의 timeout 노드에서 출발해 원을 한 바퀴 돌며 찍는다(우리 스레드가 아닌 노드는 ?). tick은 1 kHz로 맞췄다.

출력에서 볼 것:

  • SIMPLE: runq가 main(p0) → A5(p5) → B5(p5) → C7(p7)로 우선순위순 정렬되어 있다(Kconfig 도움말의 "unordered"와 달리). 지금 돌고 있는 main도 runq 안에 있고(UP), ready_q.cache가 main이다. 같은 우선순위 A5·B5는 먼저 add된 A5가 앞. 굶고 있는 C7은 계속 ready로 남아 있다. idle은 어느 구현에서도 runq에 없다.
  • SCALABLE: 같은 순서를 rbtree in-order로 걸었다. order_key는 add될 때마다 1씩 늘어난 번호다 — A5=1, B5=2, C7=3은 생성 순서이고, main=11은 자고 일어나며 다시 add되는 사이에 다른 스레드들의 add가 쌓인 결과다. 같은 우선순위끼리는 이 키가 작은 쪽이 먼저(FIFO).
  • MULTIQ: bitmask=0x00a10000 = 비트 16·21·23. 큐 인덱스는 prio − K_HIGHEST_THREAD_PRIO(−16)이라 prio 0 → 16, prio 5 → 21, prio 7 → 23. cached_queue_index=16이 곧 다음 스레드(main)다. 32개 큐 머리(8 B × 32 = 256 B) 때문에 _kernel이 288 B로 SIMPLE(32 B)의 9배다.
  • wait_q: 생성 순서는 W2·W4·W3·W3t였지만 대기 리스트는 W2(p2) → W3(p3) → W3t(p3) → W4(p4) — 우선순위순, 같으면 먼저 기다린 순서. ready queue 설정과 무관하게 세 빌드 모두 같다(wait_q는 별도 Kconfig WAITQ_SIMPLE 기본값).
  • timeout 원: 마지막 nm이 답을 준다. ?@0x20000088이 리스트 머리 timeout_list(그래서 그 dticks 16777472는 timeout이 아닌 메모리를 읽은 쓰레기 값)이고, ?@0x200008d8은 커널의 slice_timeouts(타임슬라이스 타이머, TIMESLICE_SIZE 기본 20 ms)다. 머리부터 읽으면 S10(5) → S20(10) → 슬라이스(5) → S30(5) → W3t(470), 누적하면 5·15·20·25·495 tick. main이 tick 6에 깼으니(5 ms + z_add_timeout이 붙이는 1 tick) S10은 11 − 6 = 5, S20은 21 − 6 = 15, S30은 31 − 6 = 25, W3t는 501 − 6 = 495 tick 남았다는 뜻이고, 정확히 맞는다. 시간이 가면 머리의 5만 줄어든다 — delta 리스트의 요점이다.
  • sizeof(struct k_thread)가 SCALABLE에서만 168 B(나머지 160 B)인 것은 order_key(4 B, CONFIG_SCHED_SCALABLE 또는 CONFIG_WAITQ_SCALABLE일 때만 있음)와 정렬 패딩 때문이다.

5.6 예제 10 — ready queue 구현별 전환 비용과 크기#

무엇을 확인하나: 같은 우선순위(5) worker N개가 k_yield()만 반복할 때 전환 1회의 비용을 잰다. 각 worker는 돌기 시작하자마자 "직전 worker가 돈 시각"과의 차이를 기록하니, 그 차이가 곧 yield → 다음 worker 실행까지의 시간이다. main(우선순위 0)이 worker를 2·4·8·16·32·64개로 늘려 가며 20 ms씩 자는 동안 worker들만 돈다(main이 끼어든 창 경계의 샘플은 버린다). yield는 "현재 스레드를 같은 우선순위 줄의 맨 뒤로"라서 SIMPLE에서는 같은 우선순위 스레드를 전부 지나가야 자리가 나오고(O(N)), MULTIQ는 dequeue + append(O(1)), SCALABLE은 rbtree remove + insert(O(log N))다. ready queue 비용만 보려고 CONFIG_TIMESLICING=n으로 한 번, 기본값(y, TIMESLICE_SIZE 20 ms)으로 한 번 빌드했다.

출력에서 볼 것 (평균 avg를 본다. min은 가장 싼 전환 한 번):

  • MULTIQ (타임슬라이스 끔): N = 2든 64든 72.8 cycle로 평평하다. O(1)이다. 이 랩에서 Zephyr의 yield → 다음 스레드 전환은 명령 약 90개다(QEMU는 예외 스태킹 사이클을 모델링하지 않으니 실칩에선 더 든다).
  • SIMPLE (기본값): N = 2에서 76.8로 MULTIQ와 거의 같지만 N = 64에서 523.0. (523.0 − 76.8) / 62 ≈ 7.2 cycle(명령 약 9개) / 같은 우선순위 스레드 — z_priq_simple_yield가 같은 우선순위 스레드를 하나씩 z_sched_prio_cmp로 비교하며 지나가는 비용이다. N이 4 이하인 보통 앱에서는 차이가 없다.
  • SCALABLE: N = 2에서 이미 210.4(MULTIQ의 2.9배)이고 N이 두 배가 될 때마다 약 70~80 cycle씩 는다 — O(log N) + 큰 상수. 이 측정 범위(N ≤ 64)에서는 SIMPLE보다 항상 비싸다. Kconfig 도움말이 "Most applications don't want this"라고 하는 이유다.
  • 타임슬라이스 켬(기본값): 모든 구현에서 전환 한 번에 약 190~200 cycle이 더 붙는다(MULTIQ 72.8 → 262~276). 다른 스레드로 바뀔 때마다 update_cache() → z_reset_time_slice()가 z_abort_timeout() + z_add_timeout()으로 슬라이스 timeout을 delta 리스트에서 빼고 다시 넣고, 그것이 머리가 되면 sys_clock_set_timeout()으로 SysTick을 다시 설정하기 때문이다. 창마다 262와 276이 번갈아 나오는 원인은 확인하지 못했다(main의 timeout과 슬라이스 timeout 중 무엇이 머리인지에 따라 SysTick 재설정 여부가 달라지는 것으로 추정한다). ready queue 선택보다 타임슬라이스 설정이 전환 비용에 더 크게 작용한다는 것이 이 측정의 부수 결과다 — 같은 우선순위 round-robin이 필요 없으면 CONFIG_TIMESLICING=n 또는 CONFIG_TIMESLICE_SIZE=0을 검토할 만하다.
  • 크기(타임슬라이스 끔): text가 SIMPLE 12808 B, MULTIQ 12996 B(+188 B), SCALABLE 14440 B(+1632 B — Kconfig 도움말의 "약 2 KB"와 같은 규모). _kernel은 32 / 40 / 288 B.

7.1 드론 비행 제어기 — "1 kHz에 깨는 태스크가 몇 개인가"#

STM32H7급 FC에서 IMU 읽기·자세 추정·rate PID·모터 출력은 보통 IMU 데이터 준비 인터럽트(1~8 kHz)에 묶여 하나의 체인으로 돈다. 흔한 실수는 이 체인을 태스크 여러 개로 쪼개고 각자 vTaskDelayUntil(&last, 1)로 1 ms 주기를 주는 것이다. 그러면 매 tick마다 같은 tick에 K개가 깨면서(예제 8) tick ISR이 그만큼 길어지고, 그동안 BASEPRI 아래의 ISR(UART 텔레메트리, ESC 텔레메트리 DMA 완료 …)이 밀린다. 더 나은 구조는 IMU 인터럽트가 한 태스크에 알림(vTaskNotifyGiveFromISR)을 주고, 그 태스크가 체인을 순서대로 돌리거나 다음 단계를 직접 알림으로 깨우는 것이다 — 깨움이 tick ISR이 아니라 ISR 한 번 + O(1) 이벤트 경로로 간다. 우선순위는 "IMU 체인 > 제어 > 텔레메트리 > 로깅 > idle"처럼 5~8단계면 충분하고, H7(Cortex-M7)이면 CLZ 선택이 기본으로 켜진다.

7.2 로봇 관절 모터 컨트롤러 — Cortex-M0+에서#

FOC 전류 루프(20 kHz)는 ISR에서 돌고 RTOS는 CAN 통신·상태 기계·진단 정도를 맡는 작은 MCU(M0+)가 많다. 여기는 CLZ가 없어 generic 선택만 가능하다. 대응은 간단하다: configMAX_PRIORITIES를 실제로 쓰는 4~5로 줄인다. 예제 6에서 보듯 generic 비용은 "빈 우선순위 수"에 비례하니 단계 수를 줄이는 게 곧 최적화이고, ready 배열 RAM(단계당 20 B)도 준다.

7.3 센서 허브 MCU (Zephyr) — 기본값 SIMPLE이 맞나#

Linux SoC 옆에서 IMU 타임스탬프와 센서 융합 전처리를 하는 Zephyr 센서 허브는 스레드가 5~10개, 그중 동시에 runnable한 것은 1~3개가 보통이다. 이 경우 기본값 SCHED_SIMPLE이 코드 크기와 상수 비용 모두에서 가장 낫다(예제 10). 같은 우선순위 스레드가 많아 round-robin을 자주 돈다면 SCHED_MULTIQ, 수십 개 이상이 동시에 runnable하거나 SCHED_DEADLINE(EDF, C11)을 쓴다면 SCHED_SCALABLE을 검토한다. 결정 근거는 "동시에 runnable한 스레드의 최대 수"이고, 그 숫자를 설계 문서에 남긴다.

9. 면접에서 이렇게 말한다#

Q. "How does FreeRTOS find the highest-priority ready task? Is it O(1)?"

A. 우선순위마다 ready 리스트가 하나씩 있다. Cortex-M3 이상에서는 "비어 있지 않은 우선순위" 비트맵을 들고 있다가 31 − clz(비트맵)로 한 번에 찾으니 O(1)이고, CLZ가 없는 M0 같은 포트는 최고 후보에서 한 칸씩 내려가며 빈 리스트를 건너뛰는 generic 방식이라 빈 우선순위 수에 비례한다. 같은 우선순위 안에서는 리스트의 인덱스 커서를 한 칸 밀어 round-robin한다. QEMU에서 재 보니 CLZ 방식은 우선순위 4~32개에서 비용이 완전히 같았고, generic은 빈 우선순위 하나당 명령 5개씩 늘었다.

FreeRTOS keeps one ready list per priority. On Cortex-M3 and up, the port keeps a 32-bit bitmap of non-empty priorities, so selection is 31 - clz(bitmap) followed by advancing the list's round-robin index — O(1), independent of the number of priorities, limited to 32 priorities. On cores without CLZ, like Cortex-M0, it uses the generic path: a cached upper bound, walking down past empty lists, so the cost is proportional to the number of empty priority levels. I measured both on QEMU: the CLZ path was flat from 4 to 32 priorities, and the generic path added about five instructions per empty level — exactly the loop in the disassembly.

꼬리 질문: "So is the whole scheduler O(1)?" → 선택은 O(1)이지만 delayed 리스트·이벤트 리스트 정렬 삽입과 같은 tick의 일괄 깨움은 O(n)이다(다음 질문).

Q. "Where are the O(n) operations in FreeRTOS, and do they affect interrupt latency?"

A. 정렬 삽입 두 곳(delayed 리스트, 큐·세마포어의 대기자 리스트)과 tick에서 여러 태스크를 한꺼번에 깨우는 경우다. 정렬 삽입은 스케줄러만 멈추고 인터럽트는 열어 둔 채 하므로 인터럽트 지연엔 영향이 없고 태스크 응답 시간에만 영향이 있다. 반면 tick ISR 안의 일괄 깨움은 BASEPRI를 올린 채 도니까 인터럽트 지연에 바로 더해진다. 실측으로 태스크 64개가 같은 tick에 깨면 그 ISR이 약 2,500 cycle이었다.

Two sorted inserts — into the delayed list and into an object's waiter list — are O(n) in the number of delayed tasks or waiters. FreeRTOS does those with the scheduler suspended but interrupts enabled, so they don't add to interrupt latency; they only delay other tasks. The one that does hurt interrupt latency is the tick handler waking many tasks on the same tick: each wake is O(1), but K of them run with BASEPRI raised. On QEMU I saw the tick ISR go from 39 cycles to about 2,500 cycles with 64 tasks waking on one tick. The design rule is to keep task counts small and avoid lining up many periodic tasks on the same phase.

Q. "Why does FreeRTOS have two delayed task lists?"

A. 깨울 시각을 절댓값 tick으로 정렬하는데, "지금 + 대기"가 32비트를 넘으면 작은 숫자가 되어 정렬이 깨진다. 그래서 넘친 시각은 overflow 리스트에 따로 넣고, tick이 0으로 넘어가는 순간 두 리스트 포인터를 맞바꾼다. 복사 없이 포인터 교환 한 번이고, 그 순간 현재 리스트는 반드시 비어 있어야 하니 assert로 확인한다.

Wake times are stored as absolute tick values and the list is sorted ascending. When "now plus timeout" overflows the tick type, the wake time becomes a small number and would sort before tasks that wake earlier. So FreeRTOS puts overflowed wake times in a second list. When the tick count wraps to zero, the current list must be empty, and the kernel just swaps the two list pointers and recomputes the next unblock time — no copying, one pointer swap.

Q. "Why is the event list item value set to configMAX_PRIORITIES minus the priority?"

A. 리스트는 값 오름차순으로 정렬되고 맨 앞을 꺼낸다. 우선순위를 뒤집어 값으로 넣으면 가장 높은 대기자가 맨 앞에 서서, give 쪽(ISR일 수도 있다)은 머리 하나만 O(1)로 꺼내면 된다. 비용을 짧아야 하는 깨우는 쪽이 아니라 블록하는 쪽에 둔 설계다. 같은 우선순위는 먼저 블록한 순서(FIFO)다.

The list code only knows ascending sort by item value, and wakers take the head. Storing configMAX_PRIORITIES - priority makes the highest-priority waiter sort first, so the give path — which may be an ISR — just removes the head in O(1). The O(n) cost is paid by the task that blocks, not by the waker. Equal priorities stay FIFO because insert places equal values after existing ones.

Q. "What is the pending ready list for?"

A. 스케줄러 정지(vTaskSuspendAll)는 인터럽트를 막지 않는다. 그 사이 ISR이 대기자를 깨우면 ready 리스트를 건드리면 안 되니, 태스크의 이벤트 리스트 항목만 pending 리스트 끝에 붙여 두고, xTaskResumeAll()이 나중에 진짜 ready 리스트로 옮긴다. 내 덤프에서 같은 TCB의 상태 항목은 아직 suspended에, 이벤트 항목은 pending에 걸린 순간을 직접 봤다.

Suspending the scheduler keeps interrupts enabled, so an ISR can unblock a task while task code is in the middle of manipulating the kernel lists. The ISR must not touch the ready lists then, so it appends the task's event list item to xPendingReadyList in O(1), and xTaskResumeAll() later moves those tasks to their ready lists. In a live dump I could see one TCB with its state item still in the suspended list and its event item in the pending list.

Q. "How is Zephyr's ready queue different, and which option would you pick?"

A. Zephyr는 Kconfig로 세 가지를 고른다. 기본 SIMPLE은 우선순위 정렬된 이중 연결 리스트 하나라서 다음 스레드는 머리 O(1), 넣기는 O(n). SCALABLE은 rbtree라 O(log n)이지만 코드가 2 KB쯤 크고 상수가 크다. MULTIQ는 FreeRTOS처럼 우선순위별 리스트 + 비트맵이라 O(1)인데 리스트 머리만큼 RAM이 들고 deadline 스케줄링과 같이 못 쓴다. 동시에 runnable한 스레드가 몇 개 안 되는 일반적인 MCU 앱이면 SIMPLE이 맞고, 같은 우선순위 스레드가 많으면 MULTIQ, 수십 개 이상이면 SCALABLE이다.

Zephyr makes it a Kconfig choice. The default, SCHED_SIMPLE, is one priority-sorted doubly linked list: picking the next thread is the head, inserting is O(n). SCHED_SCALABLE is a red-black tree, O(log n) but with more code and a higher constant. SCHED_MULTIQ is the classic array of per-priority lists plus a bitmap — O(1), costs RAM for the list heads, and can't be combined with deadline scheduling. For a typical MCU app with a handful of runnable threads I'd keep SIMPLE; with many equal-priority threads that yield or time-slice, MULTIQ; with dozens of runnable threads, SCALABLE. I measured yield cost per configuration to back that choice.

Q. "Your device hangs and the debugger shows the PC inside vListInsert. What do you check?"

A. 리스트 원이 깨져서 정렬 삽입 루프가 끝 표시를 못 만나는 전형적인 증상이다. 소스 주석이 꼽은 순서대로 본다: 스택 오버플로(오버플로 검사 2 켜기), ISR 우선순위가 syscall 상한보다 높은데 FromISR API를 부르는지, 크리티컬 섹션·스케줄러 정지 중 API 호출이나 ISR에서 일반 API 호출, 초기화 전 객체 사용, tick 인터럽트 우선순위. configASSERT와 리스트 무결성 바이트를 켜면 더 일찍 잡힌다.

That's the classic symptom of a corrupted list: the sorted-insert loop never reaches the end marker. I'd go through the causes listed in the source comment: stack overflow (enable overflow checking method 2 and look at high-water marks), an ISR above configMAX_SYSCALL_INTERRUPT_PRIORITY calling FreeRTOS APIs, calling non-FromISR APIs from an ISR or APIs inside a critical section, using a queue before it's created or before the scheduler starts, and the tick interrupt priority. Turning on configASSERT and configUSE_LIST_DATA_INTEGRITY_CHECK_BYTES catches it closer to the cause.

Q. "Is the running task in the ready list?"

A. FreeRTOS에서는 그렇다. Running은 ready 리스트에 그대로 있는 태스크 중 pxCurrentTCB가 가리키는 것일 뿐이고, 블록할 때 거기서 뺀다. Zephyr도 단일 코어에서는 현재 스레드를 runq에 남겨 두고, SMP에서는 뺀다.

In FreeRTOS, yes — the running task stays in its ready list and is simply the one pxCurrentTCB points to; it's removed only when it blocks, suspends or is deleted. My live dump shows the monitor task in pxReadyTasksLists[6] while it was the one printing. Zephyr does the same on uniprocessor builds, but on SMP the current thread is taken out of the run queue.

12. 요약 & 체크리스트#

RTOS 커널의 스케줄러는 결국 리스트 관리자다. FreeRTOS는 20 B짜리 끼워 넣는 리스트 항목(ListItem_t)을 TCB에 두 개 박아 두고, 끝 표시를 리스트 안에 내장한 원형 이중 연결 리스트로 ready(우선순위별 배열)·delayed(두 개, tick wrap 때 포인터 교환)·pending·suspended·삭제 대기·객체 대기자 리스트를 만든다. ready 리스트는 끝 삽입 O(1), delayed와 대기자 리스트는 정렬 삽입 O(n)이고, 대기자 리스트는 값을 configMAX_PRIORITIES − 우선순위로 뒤집어 높은 우선순위가 머리에 오게 한다. 최고 우선순위 선택은 Cortex-M3 이상에서 비트맵 + clz로 우선순위 개수와 무관한 O(1)이고, generic은 빈 층당 명령 5개다. O(n) 정렬 삽입은 스케줄러 정지(인터럽트 허용) 아래에서 돌아 인터럽트 지연에 영향이 없지만, 같은 tick의 일괄 깨움은 BASEPRI 아래 O(K)라 인터럽트 지연에 더해진다. Zephyr는 Kconfig로 ready queue(정렬 dlist·rbtree·multi-queue)를 고르고, timeout은 64비트 시계의 delta 리스트 하나로 처리하며, 정렬 삽입은 스핀락(단일 코어에서는 인터럽트 마스크) 아래에서 한다.
