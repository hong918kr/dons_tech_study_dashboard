0. 큰 그림 — 코어가 둘이면 "누가 다음 일을 고르나"가 두 번 결정된다#

Don이 SSD 컨트롤러에서 본 구조를 떠올려 보자. 컨트롤러 안에 Cortex-R 코어가 여러 개 있었고, 보통 코어마다 맡은 일이 정해져 있었다. 호스트 인터페이스(NVMe) 코어, FTL 코어, NAND 채널 코어 — 각 코어에 실행부(executive) 하나가 돌고, 코어끼리는 공유 메모리의 큐와 doorbell 인터럽트로 일을 넘겼다. 이게 AMP(Asymmetric Multiprocessing)다. 코어마다 독립 펌웨어가 돌고, 코어 사이 경계가 곧 소프트웨어 모듈 경계다.

RTOS가 SMP(Symmetric Multiprocessing)로 돌면 그림이 완전히 달라진다. 커널 하나, 이미지 하나, ready queue 하나가 코어 둘을 같이 관리한다. 태스크는 "어느 코어"에 속하지 않는다. 스케줄러가 매 순간 "지금 ready인 태스크 중 어떤 것들을 어느 코어에 올릴지"를 고른다. 단일 코어 RTOS의 규칙 "가장 높은 우선순위 태스크 하나가 돈다"가 "가장 높은 우선순위 태스크 N개(N = 코어 수)가 돈다"로 바뀐다.

그 중간이 BMP(Bound Multiprocessing)다. 커널은 SMP 커널 하나인데, 태스크를 전부 특정 코어에 고정(pin)해서 AMP처럼 예측 가능하게 쓴다.

그림 1 — AMP · SMP · BMP. AMP는 코어마다 커널(또는 bare-metal)이 따로, SMP는 커널 하나가 코어 둘을 같이, BMP는 SMP 커널 위에서 태스크를 전부 코어에 고정한다.

SMP 커널 안에서는 다음 다섯 가지가 단일 코어와 다르다. 이 노트는 이 다섯 가지를 차례로 직접 돌려 본다.

  1. ready queue가 공유된다 — 두 코어가 같은 자료구조를 동시에 만질 수 있다. 그래서 커널 자료구조를 만지는 구간(크리티컬 섹션)은 인터럽트 마스크만으로는 부족하고 스핀락이 필요하다 (§5).
  2. 스케줄링 결정이 전역이다 — "가장 높은 N개"를 고르고, 어느 코어를 선점할지도 골라야 한다 (§2, §4).
  3. 다른 코어에게 "다시 골라"라고 알려야 한다 — 코어 0에서 깨운 태스크가 코어 1의 지금 태스크보다 높으면 코어 1을 인터럽트해야 한다. 이게 IPI(Inter-Processor Interrupt)다 (§6).
  4. 우선순위가 배제 수단이 아니다 — 단일 코어에서는 "높은 우선순위가 도는 동안 낮은 것은 못 돈다"가 사실이었다. SMP에서는 둘이 동시에 돈다. k_sched_lock() · vTaskSuspendAll()도 의미가 달라진다 (§3, §4).
  5. 어디서 도는지가 성능과 결정성을 바꾼다 — migration(코어 이동), 캐시 · 버스 공유, false sharing. 그래서 affinity(코어 고정) API가 생겼다 (§7, §8, §9).

2. SMP 커널에서 무엇이 바뀌나#

그림 2 — 두 커널의 SMP 핵심 자료구조. 공통 원리: 큐는 하나, "지금 실행 중" 포인터는 코어 수만큼, 큐를 만질 땐 스핀락, 다른 코어에 결정을 전할 땐 IPI.

2.1 전역 ready queue vs 코어별 ready queue#

  • 전역(global) 스케줄링: ready queue가 하나다. 어떤 코어든 스케줄링할 때 같은 큐에서 "지금 가장 높은 것"을 꺼낸다. FreeRTOS SMP(pxReadyTasksLists[] 하나)와 Zephyr SMP 기본(_kernel.ready_q 하나)이 이 방식이다. 장점: 부하가 자동으로 고르게 퍼지고, 항상 "가장 높은 N개"가 돈다. 단점: 모든 코어가 큐 하나를 두고 락 경쟁을 한다.
  • 코어별(partitioned) 스케줄링: 코어마다 ready queue가 있고 태스크는 한 큐에만 산다. Zephyr의 CONFIG_SCHED_CPU_MASK_PIN_ONLY=y가 이 방식이다 — struct _cpu 안에 ready_q가 생긴다(include/zephyr/kernel_structs.h). 락 경쟁이 적고 예측하기 쉽지만, 한 코어가 바쁘고 다른 코어가 놀아도 일을 옮기지 않는다.

이론(어느 쪽이 스케줄 가능성 면에서 유리한가, Dhall 효과)은 N8이 다룬다. 이 노트는 구현만 본다.

2.2 "가장 높은 우선순위 N개가 돈다"#

단일 코어 규칙: ready인 태스크 중 가장 높은 하나가 돈다. SMP 규칙: ready인 태스크 중 가장 높은 N개가 돈다(N = 코어 수, affinity가 허락하는 범위에서).

이 한 줄이 모든 차이를 만든다. 예를 들어 드론 비행 제어기가 듀얼코어 MCU에서 SMP로 돈다면, 자세 제어 태스크(높음)와 로그 태스크(낮음)는 동시에 돈다. 단일 코어였다면 로그 태스크는 자세 제어 태스크가 잠들 때만 돌았다. 코드가 그 사실에 기대고 있었다면(예: "로그 태스크가 도는 동안엔 제어 루프가 공유 버퍼를 안 만진다") SMP에서 깨진다(§3.3).

FreeRTOS는 이 규칙을 끄는 옵션까지 준다: configRUN_MULTIPLE_PRIORITIES = 0이면 서로 다른 우선순위 태스크는 동시에 돌지 않는다. 높은 태스크가 ready면 낮은 태스크를 다른 코어에서도 내린다. 그 대가로 코어가 논다. §4.2에서 실제로 돌려 본다.

2.4 arch_curr_cpu()->id를 읽을 때 왜 인터럽트를 막았나#

my_cpu()가 arch_irq_lock()으로 감싼 이유: SMP에서 스레드는 언제든 다른 CPU로 옮겨질 수 있다. CPU 구조체 포인터를 읽은 직후 선점되어 다른 CPU로 옮겨지면, 이미 "옛 CPU"의 id를 들고 있게 된다. Zephyr는 이 실수를 잡으려고 _current_cpu 매크로에 __ASSERT_NO_MSG(!z_smp_cpu_mobile())를 넣어 뒀다(include/zephyr/kernel_structs.h) — "지금 이 스레드가 옮겨질 수 있는 상태면 CPU 포인터를 쓰지 마라". 인터럽트가 막혀 있으면 이 CPU에서 선점이 안 되니 안전하다.

이 문제는 단일 코어에 없다. 그리고 FreeRTOS SMP도 똑같다: portGET_CORE_ID() 값은 그 순간에만 맞다. FreeRTOS 커널 코드가 prvCheckForRunStateChange() 안에서 락을 다시 잡은 뒤 xCoreID = portGET_CORE_ID()를 다시 읽는 것(§5.2)도 같은 이유다.

함정: "현재 코어 번호"로 배열(per_cpu_buf[core])을 고르는 코드는 그 배열을 쓰는 동안 migration이 없어야 한다. 인터럽트를 막거나, 스레드를 그 코어에 pin하거나, 배열 원소 접근 자체를 atomic으로 만든다.

3. 단일 코어에서 안전하던 것이 2코어에서 깨진다#

스핀락 · atomic의 정의, _irqsave 변형, 메모리 배리어는 EL F4 · F5에서 다뤘다. 여기서는 RTOS · MCU에서 달라지는 점만 본다.

3.2 생성 코드로 보기 — 예제 3: k_spin_lock은 aarch64에서 무엇이 되나#

무엇을 확인하나: Zephyr의 k_spin_lock()이 실제로 "인터럽트 마스크 + atomic CAS 루프"라는 것.

(# 뒤 설명은 덧붙인 것이다. 출력 앞부분 프롤로그는 생략했다.)

출력에서 볼 것:

  • k_spin_lock = ① 이 CPU의 IRQ 마스크(msr daifset, #2) → ② 락 변수에 CAS → 임계 구역 → ③ release 저장 → ④ IRQ 상태 복원. 소스(include/zephyr/spinlock.h)의 k.key = arch_irq_lock(); 다음 while (!atomic_cas(&l->locked, 0, 1)) { do { arch_spin_relax(); } while (atomic_get(&l->locked) != 0); }가 그대로 보인다. 실패하면 CAS를 반복하지 않고 읽기만 하며 기다렸다가(ldar 루프, test-and-test-and-set) 풀린 것 같을 때만 CAS를 다시 한다 — 캐시 라인을 덜 흔든다.
  • atomic 연산이 __aarch64_cas8_acq_rel 같은 함수 호출이다. GCC의 outline atomics: 실행 시점에 CPU가 LSE(casal 명령)를 지원하면 그것을, 아니면 LDXR/STXR 루프를 쓴다. Cortex-A53은 Armv8.0이라 LSE가 없어서 LL/SC 루프로 간다. (랩 README가 말한 "Ubuntu gcc로 Zephyr를 빌드하면 outline atomics 때문에 링크 안 됨"이 바로 이 함수들이다 — Zephyr SDK 툴체인은 이걸 libgcc에 넣어 준다.)
  • 왜 IRQ를 먼저 막나: 락을 쥔 채 같은 CPU의 ISR이 같은 락을 잡으려 하면 영원히 돈다(self-deadlock, EL F4 §4). Zephyr의 k_spin_lock은 항상 irqsave 버전이다. 그래서 Zephyr에서는 같은 k_spinlock을 스레드와 ISR이 함께 써도 된다.
  • 단일 코어 빌드에서는 ②③이 사라지고(#ifdef CONFIG_SMP) k_spin_lock = irq_lock이다. 같은 소스가 UP에서는 "인터럽트 끄기", SMP에서는 "인터럽트 끄기 + 스핀락"이 된다. 이게 이 노트 제목의 "SMP에서 크리티컬 섹션 = 스핀락"이다.

3.3 예제 4 — 우선순위와 k_sched_lock으로 배제하던 코드 (SMP에서만 깨진다)#

단일 코어 RTOS에서 흔한 두 관용구가 있다.

  • "나보다 높은 건 없다": 가장 높은 우선순위 태스크는 다른 태스크에게 선점되지 않으니, 공유 데이터를 락 없이 고친다. 낮은 쪽만 조심하면 된다.
  • "스케줄러 잠금 = 가벼운 뮤텍스": 낮은 태스크는 k_sched_lock()(FreeRTOS는 vTaskSuspendAll())으로 스케줄러를 잠그고 고친다. 그동안 어떤 스레드도 끼어들 수 없다(ISR은 예외).

단일 코어에서는 이 둘을 합치면 정말로 안전하다. SMP에서는?

무엇을 확인하나: 같은 코드를 단일 코어와 2코어에서 돌렸을 때, 2코어에서만 값이 사라지는지. 그리고 "둘 다 k_sched_lock"과 "둘 다 k_spinlock"은 어떤지.

(빈 줄 몇 개를 빼고 실은 것 말고는 실행한 소스 그대로다. h_cpus의 |=는 스레드 하나만 쓰므로 경쟁이 없다.)

출력에서 볼 것:

  • 단일 코어: 세 방식 모두 0 — 우선순위와 스케줄러 잠금만으로 진짜 안전했다. 이 코드는 단일 코어 시절에 몇 년이고 테스트를 통과했을 것이다.
  • 2코어: 앞의 두 방식은 매번 1만~2만 개를 잃는다. H(prio 2)와 L(prio 8)이 서로 다른 CPU에서 동시에 돈다(H cpus, L cpus 마스크가 서로 다른 비트). k_sched_lock()은 "이 CPU에서 지금 스레드를 선점하지 마라"(현재 스레드의 base.sched_locked 카운트)일 뿐, 다른 CPU를 멈추지 않는다. 둘 다 k_sched_lock()을 걸어도 마찬가지다.
  • k_spinlock만 2코어에서 정확하다. SMP에서 상호 배제 수단은 스핀락(짧은 구간)과 뮤텍스 · 세마포어(긴 구간) 뿐이다. 우선순위 · 스케줄러 잠금 · 인터럽트 끄기(irq_lock)는 "이 코어 안에서만" 효과가 있다.

함정 — Zephyr의 irq_lock(): SMP 빌드에서 irq_lock()은 이 CPU 인터럽트 마스크 + 전역 락(kernel/smp.c의 z_smp_global_lock(), 스레드별 재진입 카운트)이다. 그래서 irq_lock끼리는 코어를 넘어 배제가 되지만, 무거운 전역 락이라 성능이 나쁘고 Zephyr 문서도 새 코드에서는 k_spinlock을 쓰라고 한다. 반대로 arch_irq_lock()은 이 CPU만 막는다.

FreeRTOS에서 같은 실험을 하면 결과가 조금 다르다(§4.5): vTaskSuspendAll()은 SMP에서 전역 task lock을 쥐기 때문에 "둘 다 SuspendAll"은 안전하다. 하지만 "H는 잠금 없음"인 경우는 똑같이 깨진다.

5. SMP에서 크리티컬 섹션 = 인터럽트 마스크 + 스핀락#

단일 코어 크리티컬 섹션(BASEPRI, 중첩 카운트)은 C7이 다룬다. 스핀락 개념은 EL F4. 여기서는 FreeRTOS SMP가 두 락을 어떻게 쓰는지만 소스로 읽는다.

5.1 왜 인터럽트 마스크만으로는 부족한가#

단일 코어에서 taskENTER_CRITICAL()은 "BASEPRI를 올려 커널 인터럽트를 막는다"였다. 이 코어에서 커널 자료구조를 만질 수 있는 다른 주체는 ISR뿐이니 그걸로 충분했다. 코어가 둘이면 다른 코어의 태스크와 ISR이 같은 pxReadyTasksLists를 만질 수 있다. 내 코어의 인터럽트 마스크는 저쪽 코어에 아무 효과가 없다. 그래서 둘 다 해야 한다.

  • 인터럽트 마스크: 내 코어의 ISR이 끼어드는 것을 막는다 (그리고 락을 쥔 채 ISR에서 같은 락을 잡는 self-deadlock을 막는다).
  • 스핀락: 다른 코어가 같은 자료구조에 들어오는 것을 막는다.

읽는 법:

  • 락이 둘인 이유: 커널 상태 중에는 태스크만 만지는 것(태스크 생성 · 삭제, 스케줄러 일시 정지 상태)과 ISR도 만지는 것(ready list, 이벤트 리스트)이 섞여 있다. task lock은 "태스크 쪽 커널 작업을 한 번에 한 코어만", ISR lock은 "ISR까지 포함해서 한 번에 한 코어만"이다.   • 잡는 순서가 항상 task → ISR이다. 순서가 고정되어야 두 코어가 서로 반대 순서로 잡아 데드락하는 일이 없다(락 순서 규칙, EL F4).
  • 중첩 카운트가 코어별이다(portGET_CRITICAL_NESTING_COUNT( xCoreID )). 처음 들어갈 때(0 → 1)만 락을 잡고, 마지막에 나갈 때(1 → 0)만 놓는다. 그래서 락 자체는 같은 코어에서 다시 잡을 필요가 없다 — 그래도 포트의 락 함수는 재진입(recursive)으로 만들어져 있다(아래 vPortRecursiveLock). Zephyr k_spinlock은 재진입이 안 된다(Zephyr SMP 문서: 같은 스핀락을 중첩해 잡으면 안 된다) — 두 커널의 차이다.
  • prvCheckForRunStateChange(): 크리티컬 섹션에 막 들어왔는데, 그 사이 다른 코어가 "너 양보해"(xTaskRunState == taskTASK_SCHEDULED_TO_YIELD)를 걸어 뒀으면? 락을 쥔 채로는 양보할 수 없으니, 락을 모두 놓고 → 인터럽트를 잠깐 켜서 대기 중인 IPI를 받아 양보하고 → 다시 돌아와 인터럽트를 끄고 → 코어 번호를 다시 읽고(이제 다른 코어일 수 있다) → 락을 다시 잡는다. 이 루프가 없으면 양보 요청을 받은 태스크가 크리티컬 섹션 안에서 계속 돌아, 더 높은 태스크가 그 코어를 못 얻는다.
  • 나갈 때(vTaskExitCritical): 중첩이 0이 되면 xYieldPendings[ xCoreID ]를 락을 쥔 상태에서 읽어 두고, ISR lock → task lock 순으로 놓고, 인터럽트를 켠 뒤, 양보가 미뤄져 있었으면 portYIELD(). prvYieldCore()가 자기 코어에 대해 IPI 대신 xYieldPendings만 세우는 이유가 이것이다 — 크리티컬 섹션 안에서는 양보할 수 없으니 나갈 때 한다.
  • vTaskSuspendAll()(SMP): 인터럽트 마스크 → portGET_TASK_LOCK → (필요하면 prvCheckForRunStateChange) → portGET_ISR_LOCK → ++uxSchedulerSuspended → ISR lock만 놓고 인터럽트 복원. task lock은 쥔 채로 돌아온다. xTaskResumeAll()에서야 놓는다(tasks.c 4089행 부근). 예제 7에서 "둘 다 SuspendAll"이 안전했던 이유이고, 동시에 "SuspendAll 구간이 길면 다른 코어의 모든 커널 API가 멈춘다"는 비용이다.

6. IPI — 다른 코어에게 "다시 골라"라고 알리기#

6.1 왜 필요한가#

코어 0의 태스크가 세마포어를 give해서, 코어 1에서만 돌 수 있는(또는 코어 1이 가장 낮은 태스크를 돌리고 있는) 높은 태스크가 ready가 됐다고 하자. 커널은 이 사실을 코어 0에서 알았다. 코어 1은 지금 낮은 태스크를 신나게 돌리는 중이고 커널에 들어올 일이 없다. 코어 1을 인터럽트하지 않으면 코어 1은 다음 tick(그나마 tick이 그 코어에 있다면)까지, 또는 지금 태스크가 스스로 블록할 때까지 모른다. 그래서 커널은 코어 1에 인터럽트를 건다 — IPI(Inter-Processor Interrupt). Arm GIC에서는 SGI(Software Generated Interrupt), Cortex-M 멀티코어 칩에서는 MHU doorbell · 코어 간 FIFO 같은 칩 고유 장치다.

6.3 Zephyr의 IPI 경로#

ipi_mask_create()(kernel/ipi.c)가 누구에게 보낼지를 정한다. CONFIG_IPI_OPTIMIZE=n(기본)이면 그냥 "나 빼고 전부"(IPI_ALL_CPUS_MASK). =y이면 각 CPU에 대해 "그 CPU의 현재 스레드가 새 스레드보다 낮고 선점 가능하고, 새 스레드의 cpu_mask가 그 CPU를 허락하는가"를 따져 필요한 CPU만 고른다. 관련 Kconfig(kernel/Kconfig.smp에서 확인): SCHED_IPI_SUPPORTED(아키텍처가 선택), IPI_OPTIMIZE, SCHED_IPI_CASCADE(CPU mask 사용 시 연쇄 IPI로 국소적 스케줄 오류 보정), TRACE_SCHED_IPI(테스트용: z_sched_ipi() 안에서 z_trace_sched_ipi() 훅 호출).

  • 설계 교훈: 지연에 민감한 "깨우는 쪽 · 깨어나는 쪽" 쌍(예: IMU ISR → 자세 제어 태스크)은 같은 코어에 두는 것이 지연과 지터 모두에 유리하다. 그리고 hard RT 코어에 쓸데없는 IPI가 가지 않게 한다(IPI_OPTIMIZE, 그 코어에 다른 스레드를 안 둠).

8.2 예제 13 — "스레드별 카운터"인데 왜 두 배가 안 되나: false sharing#

예제 12의 per-thread가 ×1.15밖에 안 나온 것이 이상하다. 공유가 없는데? 심볼 주소를 보자:

mode(0x...528)와 local[0].v(0x...530)가 같은 64바이트 줄(0x...500–0x...53F)에 있다. 두 스레드는 매 반복 mode를 읽고, 스레드 0은 같은 줄의 local[0].v에 쓴다. 쓸 때마다 다른 코어의 그 줄 사본이 무효화된다 — false sharing(논리적으로 공유하지 않는 변수가 같은 캐시 라인에 있어 생기는 공유).

QEMU는 게스트 캐시를 모델링하지 않는데 왜 보이나? 게스트 메모리는 결국 호스트 메모리이고, 두 vCPU 스레드는 호스트의 진짜 코어 두 개에서 돈다. 호스트 캐시 일관성 비용이 그대로 드러난다. 깨끗하게 확인하는 실험:

출력에서 볼 것: 카운터가 4바이트 떨어져(같은 줄) 있으면 2코어가 1코어보다 느리다(21.8 vs 17.0 ms). 64바이트 이상 떨어뜨리면 정확히 두 배(8.3 ms). 이 호스트에서 경계가 64바이트라는 것도 보인다. 실제 MCU에서도 원리는 같다 — Cortex-M7의 D-cache 라인은 32바이트, Cortex-A53은 64바이트다(다른 코어는 TRM에서 확인). 코어마다 쓰는 데이터는 캐시 라인 경계로 정렬 · 분리한다(Zephyr __aligned(CONFIG_DCACHE_LINE_SIZE) 같은 식으로). 단, 캐시 없는 M0+ · M33 듀얼코어(RP2040 · RP2350)에서는 false sharing이 캐시 문제로는 없고 버스 경쟁만 남는다.

9. 설계 지침 — hard real-time 일을 SMP에 올려도 되나#

그림 9 — 멀티코어에서 실행 방식을 고르는 흐름. 이론적 근거(global vs partitioned 스케줄 가능성, 공유 자원 간섭)는 N8.

9.1 SMP(global)의 실시간 약점#

  • 응답 시간 분석이 어렵다. 단일 코어 RTA(N3)는 "나보다 높은 태스크만 나를 막는다"에서 출발한다. global SMP에서는 태스크가 어느 코어에서 돌지, 언제 옮겨질지가 다른 모든 태스크에 달려 있다. global 고정 우선순위 스케줄링은 이용률이 낮아도 마감을 놓치는 경우가 있다(Dhall 효과, N8).
  • migration 비용이 WCET에 들어간다 — 캐시가 식고, 실제 칩에서는 수 µs~수십 µs가 될 수 있다(칩마다 다름, 이 노트에서 실측 못 함).
  • 스핀락 대기가 WCET에 들어간다 — 다른 코어가 커널 락을 쥐고 있으면 내 코어의 커널 호출 · ISR(FromISR API)이 기다린다. FreeRTOS SMP에서 다른 코어의 긴 vTaskSuspendAll 구간이 그렇다(§5.2).
  • IPI 지터 — 관계없는 코어 간 깨움이 내 코어에 IPI를 보내 매번 스케줄러를 돌게 한다(예제 10의 IPI_OPTIMIZE=n).
  • 공유 캐시 · 버스 · 메모리 컨트롤러 간섭 — 다른 코어가 메모리를 세게 쓰면 내 루프의 실행 시간이 늘어난다. 이건 pin을 해도 사라지지 않는다(N8: MemGuard 같은 대역폭 조절, 캐시 파티셔닝).

9.2 그래서 실무 규칙#

  1. hard RT 루프는 코어 하나에 pin한다(BMP). 그 코어에는 그 루프와 그 루프의 ISR만 둔다. 예제 11처럼 pin한 스레드는 한 번도 끊기지 않았다.
  2. 그 루프를 깨우는 쪽(ISR · 생산자)도 같은 코어에 둔다 — 깨움에 IPI가 끼지 않게(예제 10: 같은 코어 p50 약 5 µs vs 다른 코어 약 32 µs, QEMU 기준 순서).
  3. IRQ affinity도 정리한다 — hard RT 코어에는 그 루프의 IRQ만 라우팅한다(GIC · 칩 인터럽트 라우터 설정).
  4. 나머지(통신, 로깅, 파일 시스템, 추론 같은 throughput 일)는 다른 코어(들)에서 global하게 돌린다.
  5. 공유 데이터는 짧은 스핀락 또는 lock-free 큐(SPSC 링버퍼)로 넘긴다. hard RT 쪽이 블로킹 뮤텍스에서 기다리는 일이 없게.
  6. 안전 등급이 다른 일을 섞어야 하면(예: ASIL D 제어 + QM 텔레매트리) SMP 하나로 묶지 않는다 — 커널 하나의 버그가 둘 다 죽인다. AMP(코어마다 다른 이미지), lockstep 코어, 하이퍼바이저 분할을 검토한다(O5 · O6 · P6).
  7. 코어 종류가 다르면(M7 + M4) 선택지는 AMP뿐이다(P4).

11.1 드론 비행 제어기를 듀얼코어 MCU로 옮길 때#

예를 들어 단일 코어 STM32F4급에서 FreeRTOS로 돌던 비행 제어기를 RP2350 같은 듀얼 M33으로 옮긴다고 하자. 흔한 계획: "core1은 IMU 읽기 + 자세 rate loop, core0은 나머지(텔레메트리, GNSS, 로그)".

  • 이건 BMP다. FreeRTOS SMP라면 rate loop 태스크와 IMU 처리를 vTaskCoreAffinitySet(h, 1 << 1)로 core1에 고정하고, 나머지 태스크는 configTASK_DEFAULT_CORE_AFFINITY를 core0으로. IMU 데이터 준비 인터럽트도 core1로 라우팅한다(칩의 인터럽트 라우팅 기능).

  • configRUN_MULTIPLE_PRIORITIES=0으로 "일단 옛 가정대로" 돌리면 버그는 숨지만, rate loop가 도는 동안 core0의 낮은 태스크들이 다 멈춘다(예제 6) — 듀얼코어로 옮긴 의미가 없다. 과도기 진단용으로만 쓴다.

11.2 로봇 관절 모터 컨트롤러 — 20 kHz FOC는 어디에#

  • FOC 전류 루프(50 µs 주기)는 보통 ISR 안에서 돈다(A7, E1). 듀얼코어라면 그 ISR을 한 코어에 고정하고 그 코어에는 RTOS 태스크를 거의 안 둔다 — 사실상 bare-metal 코어 + RTOS 코어의 AMP/BMP다.
  • CAN 통신 · 상태 머신 · 진단은 다른 코어에서. 두 코어 사이 setpoint 전달은 SPSC 링버퍼(Anduril C 문제은행의 그것)나 메일박스.
  • 피할 것: 전류 루프 ISR에서 FreeRTOS FromISR API를 부르는 것 — SMP에서는 ISR lock을 잡아야 하고(§5.2), 다른 코어가 그 락을 쥐고 있으면 50 µs 예산 안에서 기다리게 된다.

11.3 SSD 컨트롤러 — Don의 경험과 Cortex-R82#

  • Don이 본 SSD 펌웨어는 코어별 역할 분담(AMP)이었다. Cortex-R82는 클러스터 안 하드웨어 일관성을 제공하고 FreeRTOS ARM_CR82 포트가 SMP를 지원한다(V11.3.0). 즉 "FTL 작업을 코어 여러 개가 하나의 작업 풀에서 꺼내 처리"하는 SMP 설계가 RTOS 수준에서 가능해졌다.
  • 그래도 NAND 채널 타이밍처럼 hard한 부분은 여전히 코어 고정이 맞다. 혼합(BMP + 일부 global 풀)이 현실적이다.
  • 면접에서 이렇게 연결할 수 있다: "SSD 펌웨어에서 코어마다 실행부를 돌리고 doorbell로 일을 넘겼다 — 그게 AMP이고, SMP RTOS에서는 그 doorbell이 커널 IPI(portYIELD_CORE)가 되고, 공유 큐의 하드웨어 세마포어가 커널 스핀락이 된다."

11.4 AI 가속기 SoC의 제어 클러스터#

AI 가속기 SoC에는 보통 큰 Linux 클러스터(Cortex-A) 옆에 실시간 제어 코어(Cortex-R/M 또는 RISC-V) 몇 개가 있어 가속기 명령 큐, DMA, 전원 · 클럭, 안전 감시를 맡는다. 이름 있는 제품의 내부 구성은 공개 자료로 확인하지 못했다. 구조적으로는:

  • Linux ↔ 제어 코어는 AMP(remoteproc/RPMsg, P5).
  • 제어 코어들끼리는 SMP RTOS 하나로 묶을 수도, 코어마다 기능을 나눌 수도 있다. 가속기 작업 디스패치처럼 throughput이 중요한 일은 SMP, 안전 감시는 별도 코어(가능하면 lockstep).
  • Rivian 실리콘 검증 같은 직무에서 "이 제어 코어 펌웨어가 SMP인가 AMP인가, IPI는 무엇으로 하나, 코어 간 큐는 어떻게 보호하나"는 bring-up 체크리스트 질문이다.

13. 면접에서 이렇게 말한다#

Q. "What's the difference between AMP and SMP on a multicore MCU, and when would you pick each?"

A. AMP는 코어마다 독립 펌웨어(다른 RTOS나 bare-metal)가 돌고 메일박스 · 공유 메모리로 통신한다. SMP는 커널 하나가 같은 종류의 코어 여러 개를 하나의 ready queue로 스케줄한다. 코어 종류가 다르거나(M7 + M4), 안전 등급이 다르거나, 각 코어를 따로 검증해야 하면 AMP. 같은 코어이고 throughput 일을 자동 분산하고 싶으면 SMP. hard RT 루프는 SMP에서도 코어에 고정(BMP)한다.

AMP runs an independent image per core — different RTOSes or bare-metal — talking through mailboxes and shared memory; SMP runs one kernel image that schedules all identical cores from a shared ready queue. I pick AMP when the cores are heterogeneous, like an M7 plus an M4, or when I need isolation between criticality levels. I pick SMP for throughput work that benefits from load balancing, and even then I pin the hard real-time loop and its interrupt to one core, which is effectively bound multiprocessing.

꼬리 질문: "Why can't you run SMP on an STM32H747?" → 코어가 M7과 M4로 ISA · 캐시 · FPU가 달라 같은 이미지를 둘 다에서 돌릴 수 없다.

Q. "In FreeRTOS SMP, how is a critical section implemented?"

A. 단일 코어에서는 인터럽트 마스크(BASEPRI)뿐이었지만 SMP에서는 다른 코어도 커널 자료구조를 만지므로 스핀락이 필요하다. vTaskEnterCritical은 이 코어 인터럽트를 끄고, 코어별 중첩 카운트가 0이면 task lock과 ISR lock을 순서대로 잡는다. ISR 버전은 ISR lock만 잡는다. 락 둘로 나눈 이유는 한 코어가 스케줄러를 일시 정지(task lock 보유)해도 다른 코어 ISR이 FromISR API를 쓸 수 있게 하려는 것. 들어올 때 다른 코어가 양보를 요청해 뒀으면 prvCheckForRunStateChange가 락을 풀고 양보한 뒤 다시 잡는다.

On a single core it's just masking interrupts, but with SMP another core can touch the ready lists, so it becomes interrupt masking plus spinlocks. vTaskEnterCritical disables interrupts on this core and, on the first nesting level, takes the task lock and then the ISR lock — always in that order to avoid deadlock. The FromISR variant only takes the ISR lock, so a core that has suspended the scheduler, holding the task lock, doesn't block interrupt handlers on other cores. The port supplies the locks — LDREX/STREX with WFE/SEV on Armv8-M, hardware spinlocks on the RP2040.

꼬리 질문: "Is the lock recursive?" → FreeRTOS 포트 락(vPortRecursiveLock)은 소유 코어를 기록해 재진입을 허용한다. Zephyr k_spinlock은 재진입이 안 된다.

Q. "If a high-priority task is running, can a low-priority task run at the same time?"

A. 단일 코어에서는 아니다. SMP에서는 기본적으로 그렇다 — 가장 높은 N개가 돈다. 그래서 우선순위를 상호 배제 수단으로 쓰던 코드가 깨진다. 직접 Zephyr로 재현했을 때 단일 코어에서는 0, 2코어에서는 매번 1만 개 넘게 값을 잃었다. FreeRTOS는 configRUN_MULTIPLE_PRIORITIES=0으로 다른 우선순위의 동시 실행을 막을 수 있지만 코어가 논다 — 실험에서 높은 태스크가 도는 동안 다른 코어는 idle이었다.

On a single core, no. On SMP, yes by default — the scheduler runs the N highest-priority ready tasks, so priority is no longer mutual exclusion. I reproduced it in Zephyr: code that relied on priority plus k_sched_lock lost zero updates on one core and over ten thousand per run on two. FreeRTOS has configRUN_MULTIPLE_PRIORITIES set to zero to keep the old guarantee, but in my test that left the second core idle while the high-priority task ran, so it's a migration crutch, not a design.

Q. "What is an IPI and why does an SMP RTOS need it?"

A. 다른 코어에 거는 인터럽트다. 코어 0에서 깨운 태스크가 코어 1의 현재 태스크보다 높으면, 코어 1은 커널에 들어올 일이 없으니 인터럽트로 재스케줄을 시켜야 한다. FreeRTOS에서는 prvYieldForTask가 선점할 코어를 고르고 portYIELD_CORE로 IPI를 보낸다. Cortex-M33 SMP 포트에서 IPI를 비워 둔 채 돌려 보니 다른 코어의 높은 태스크가 20번 중 한 번도 못 깨어났다 — 보조 코어에는 tick도 없었다.

It's an interrupt one core sends to another. When core 0 readies a task that should preempt what core 1 is running, core 1 has no reason to enter the kernel, so the kernel interrupts it — on FreeRTOS, prvYieldForTask picks the lowest-priority eligible core and calls portYIELD_CORE; on Zephyr, flag_ipi plus signal_pending_ipi end in a GIC SGI on arm64. When I brought up FreeRTOS SMP on a dual Cortex-M33 in QEMU and left the IPI hook empty, a high-priority task on the second core woke zero times out of twenty, because that core didn't even have a tick. So IPIs are about correctness, not just latency.

꼬리 질문: "How do you reduce IPI overhead?" → 필요한 코어에만 보낸다(Zephyr CONFIG_IPI_OPTIMIZE: 실험에서 불필요한 IPI 370 → 21회), 깨우는 쪽과 깨어나는 쪽을 같은 코어에 둔다.

Q. "Would you put a hard real-time control loop on an SMP RTOS?"

A. 넣을 수는 있지만 global 스케줄링에 맡기지 않는다. 루프 태스크와 그 IRQ를 한 코어에 고정하고, 그 코어에는 관계없는 태스크 · IRQ · IPI가 안 가게 한다. 생산자 ISR도 같은 코어에 둬서 깨움에 IPI가 끼지 않게 한다. 그래도 공유 캐시 · 버스 간섭은 남으므로 최악 실행 시간은 다른 코어에 부하를 건 상태에서 측정한다. 안전 등급이 다르면 AMP나 lockstep을 쓴다.

Yes, but not under global scheduling. I'd pin the loop task and its interrupt to one core, keep unrelated tasks, IRQs and IPIs off that core, and put the producer ISR on the same core so the wake-up never needs an IPI — in my measurements a same-core wake was several times faster than a cross-core one. Pinning doesn't remove shared cache and bus interference, so I'd measure worst-case execution time with the other cores loaded. If the loop has a different safety level from the rest, I'd rather use AMP or a lockstep core than share one SMP kernel.

Q. "Two threads each increment their own counter on different cores, yet it's slower than one core. Why?"

A. false sharing이다. 두 카운터가 같은 캐시 라인에 있으면 쓸 때마다 라인이 두 코어 사이를 오간다. 실험에서 4바이트 간격이면 2코어가 1코어보다 느렸고(×0.78), 64바이트 이상 떨어뜨리자 정확히 두 배가 됐다. 코어별 데이터는 캐시 라인 크기로 정렬 · 패딩한다.

False sharing: the counters are logically private but sit on the same cache line, so every write invalidates the other core's copy and the line ping-pongs. In my test, counters four bytes apart made two cores slower than one — about 0.78x — and spacing them 64 bytes apart gave a clean 2x. Per-core data should be aligned and padded to the cache line size of the actual part, 32 bytes on a Cortex-M7, 64 on an A53.

Q. "How does vTaskSuspendAll behave differently on FreeRTOS SMP compared to Zephyr's k_sched_lock?"

A. FreeRTOS SMP의 vTaskSuspendAll은 전역 task lock을 잡고 xTaskResumeAll까지 쥔다. 그래서 둘 다 SuspendAll을 쓰는 코드는 코어 사이에서도 직렬화된다(실험에서 손실 0). Zephyr k_sched_lock은 현재 스레드의 카운트만 올려 이 CPU에서의 선점만 막는다 — 둘 다 써도 다른 CPU에서 동시에 돈다(손실 발생). 둘 다 "잠금 없이 들어오는 코드" 하나만 있으면 깨진다.

On FreeRTOS SMP, vTaskSuspendAll takes the global task lock and holds it until xTaskResumeAll, so two tasks that both use it are serialized across cores — I measured zero lost updates. Zephyr's k_sched_lock only bumps a per-thread count that stops preemption on the current CPU, so two threads using it on different CPUs still run concurrently and I lost updates every run. In both kernels, a single path that skips the lock breaks it, and on FreeRTOS holding the task lock for long stalls every kernel call on the other cores.

16. 요약 & 체크리스트#

코어가 둘 이상인 MCU에서 실행 방식은 AMP(코어마다 독립 이미지), SMP(커널 하나 · ready queue 하나), BMP(SMP + 전부 고정) 중 하나다. SMP 커널은 "가장 높은 우선순위 N개"를 돌리기 위해 전역 ready queue를 공유하고, 그 때문에 크리티컬 섹션이 인터럽트 마스크 + 스핀락이 되며(FreeRTOS: task lock + ISR lock, Zephyr: k_spin_lock = IRQ 마스크 + CAS), 다른 코어의 결정을 바꾸려면 IPI를 보낸다. QEMU에서 직접 재현한 핵심 사실: 우선순위 · k_sched_lock으로 배제하던 코드는 단일 코어에서 손실 0, 2코어에서 매번 1만 개 이상을 잃었고, FreeRTOS SMP에서 configRUN_MULTIPLE_PRIORITIES=0은 한 코어를 놀렸으며, IPI를 비워 두자 다른 코어의 높은 태스크가 한 번도 깨어나지 못했다. 성능 면에서는 공유가 없으면 거의 선형으로 확장되지만 경쟁하는 atomic · 스핀락 · false sharing은 2코어를 1코어보다 느리게 만들었다(QEMU TCG 기준, 모양만 믿을 것). hard real-time 루프는 SMP에 올리더라도 그 루프와 그 IRQ, 그 생산자를 한 코어에 고정하고, 공유 자원 간섭은 측정으로 확인한다.
