## 0. 큰 그림 — 이 노트를 쓰는 법

### 0.1 왜 "개념 질문"을 따로 연습하나

1차 기술 면접의 질문은 대부분 짧다. "spinlock과 mutex 차이는?", "probe는 언제 불리나?", "copy_to_user는 왜 필요한가?" 같은 한 줄 질문이다. 문제는 답이 짧으면 얕아 보이고, 길면 핵심을 잃는다는 것이다. 그래서 이 노트는 모든 질문을 같은 틀로 준비한다.

| 단계 | 길이 | 목표 |
|---|---|---|
| 30초 답 | 3~5문장 | 정의 + 핵심 메커니즘 + "그래서 언제 쓰나". 여기서 끝나도 합격선 |
| 2분 답 | 30초 답 + 2~4개 디테일 | 커널 함수·구조체 이름, 직접 잰 숫자, 실무 장면, Don 경험 연결 |
| 꼬리 질문 | 1~3개 | 면접관이 다음에 물을 가능성이 큰 것. 짧은 답을 미리 준비 |
| 함정 | 1줄 | 자주 나오는 오답. 이것만 피해도 "아는 사람"으로 보인다 |
| 출처 | 노트 ID § | 더 깊이 볼 곳. 숫자는 그 노트에서 실측한 것 |

말하는 순서 원칙은 하나다: **먼저 30초 답을 말하고 멈춘다.** 면접관이 "more detail?"이나 꼬리 질문을 던지면 그때 2분 답으로 내려간다. 처음부터 2분을 쏟으면 면접관이 준비한 다음 질문을 못 하게 되고, 대화가 아니라 강의가 된다.

### 0.2 번호 읽는 법

본문의 **Q1–Q50**(또는 "문항 N")은 이 노트의 질문 번호다. 각 문항 끝 **출처** 줄의 `A1 §3`, `F6 §8` 같은 표기는 원본 노트 ID와 절 번호이고, 거기에 나오는 `Q1 §4`·`Q2 §5`처럼 **§가 붙은 Q 번호는 모듈 Q 노트**(Q1 카메라 HW, Q2 카메라 파이프라인, Q3 멀티센서 동기, Q4 CAN 실무, Q5 IMU·GNSS·LiDAR, Q6 ROS 2, Q7 데이터 품질)를 뜻한다. 질문 번호에는 §가 붙지 않는다.

답에 붙인 숫자(예: "getpid 약 125 ns")는 모두 앞선 노트에서 Lima VM(arm64, 커널 7.0)이나 QEMU TCG 게스트(Linux 6.18.55)로 직접 잰 값이고, 출처 노트 ID를 달아 두었다. 면접에서는 이렇게 말한다: "On an arm64 VM I measured roughly …" — **에뮬레이터 숫자는 절대값이 아니라 비율과 경향**으로만 쓴다. TCG는 실제 하드웨어 타이밍이 아니다. 실제 보드 숫자를 물으면 "그건 보드에서 PMU나 scope로 다시 재야 한다"고 답하는 것이 정답이다.

## 1. 유저 공간 · 프로세스 · 메모리 (Q1–Q7)

모든 드라이버 질문은 결국 "유저가 부른 syscall이 커널의 어떤 구조체로 이어지나"로 돌아온다. 이 그룹은 그 출발점이다.

### Q1 ★★★ — User space vs kernel space, 그리고 syscall 경로

**Q.** "What is the difference between user space and kernel space, and what actually happens when a program makes a system call on arm64?"

**한국어로**: 유저 공간과 커널 공간은 무엇이 다르고, arm64에서 시스템 콜을 부르면 실제로 무슨 일이 일어나나?

**30초 답.** 같은 CPU에서 도는 코드를 **특권 레벨과 MMU 권한**으로 나눈 것이다. arm64에서 앱은 EL0, 커널은 EL1에서 돌고, 커널 매핑은 page table에 privileged-only로 표시되어 앱은 커널 메모리나 장치 레지스터를 직접 만질 수 없다. 하드웨어가 필요하면 syscall로 부탁한다: libc가 x8에 syscall 번호, x0–x5에 인자를 넣고 `svc #0`을 실행하면 EL1 동기 예외로 들어가 syscall 테이블의 핸들러가 불리고, 결과는 x0로 돌아온 뒤 `eret`으로 복귀한다. 그래서 앱 버그는 SIGSEGV로 끝나지만 드라이버 버그는 시스템 전체를 죽인다.

**2분 답.** 경로를 이름으로 말하면 `el0t_64_sync` → `el0_svc` → `do_el0_svc` → `invoke_syscall` → `sys_call_table[nr]`, 예를 들어 `read`는 63번 `__arm64_sys_read`다. 인자는 레지스터에서 직접 받지 않고 저장된 `pt_regs`에서 꺼낸다 — 유저가 통제하는 레지스터 값이 커널 C 코드로 흘러드는 것을 줄이기 위해서다. 커널은 `-errno`를 돌려주고 libc 래퍼가 그것을 `-1` + `errno`로 바꾼다. 비용은 예외 진입, 레지스터 저장, 투기 실행 완화 코드, 복귀 직전의 재스케줄·시그널 검사에서 온다. 내가 arm64 VM에서 재 보니 함수 호출 약 1 ns, `getpid` 약 125 ns, `open+close` 약 670 ns였고, vDSO로 처리되는 `clock_gettime`은 약 19 ns였다. 그래서 고빈도 경로는 배치 I/O, `mmap` 공유 버퍼, `epoll`로 대기 묶기, vDSO로 커널 진입 자체를 줄인다. 펌웨어로 치면 SVC 예외 + 핸들러 테이블과 같은 구조이고, 차이는 프로세스마다 주소 공간이 따로라는 것이다.

> User and kernel space are separated by CPU privilege and the MMU: apps run at EL0, the kernel at EL1, and a syscall is an `svc #0` trap that dispatches through the syscall table using the saved `pt_regs`.

**꼬리 질문**
- "How does the kernel access a user buffer safely?" → `copy_from_user`/`copy_to_user`가 범위를 검사하고 fault를 `-EFAULT`로 바꾼다. 자세히는 Q21.
- "What is the vDSO?" → 커널이 모든 프로세스에 매핑하는 작은 공유 라이브러리. `clock_gettime` 같은 읽기 전용 호출을 syscall 없이 처리한다.
- "Why do syscall handlers take `pt_regs`?" → 유저가 넣은 다른 레지스터 값이 커널 함수 인자로 새지 않게(투기 실행 공격 표면 축소) 하고, 래퍼에서 타입별로 잘라 넘기기 위해서.

**함정**: "커널은 별도 프로세스로 돌고 syscall은 그 프로세스에 메시지를 보낸다"고 말하는 것. syscall 동안 커널 코드는 **호출한 태스크의 문맥에서** 그 태스크의 커널 스택 위에서 돈다(그래서 `current`가 의미 있다).

**출처**: → A1 §1·§3·§5, E6 §1·§5·§8, B2 §4

### Q2 ★★★ — Process vs thread, fork·exec·COW

**Q.** "What is the difference between a process and a thread in Linux? How does fork work and why is it fast?"

**한국어로**: Linux에서 프로세스와 스레드는 무엇이 다른가? fork는 어떻게 동작하고 왜 빠른가?

**30초 답.** 프로세스는 자기 주소 공간, fd 테이블, 시그널 핸들러 같은 **자원의 묶음**이고, 스레드는 그 자원을 공유하면서 스택과 레지스터만 따로 가진 **실행 흐름**이다. 커널 안에서는 둘 다 `task_struct`이고, `clone()` 플래그(`CLONE_VM`, `CLONE_FILES`, `CLONE_THREAD` …)가 무엇을 공유할지 정할 뿐이다. 그래서 스케줄러는 스레드 하나하나를 독립된 task로 스케줄한다. fork는 메모리를 복사하지 않고 page table만 복사한 뒤 양쪽을 읽기 전용으로 만드는 **copy-on-write**라서 빠르다 — 누가 쓰는 순간 그 페이지만 page fault 경로에서 복사된다.

**2분 답.** 이름이 헷갈리는 부분을 정리하면 `getpid()`는 TGID(스레드 그룹 = 프로세스 ID)라 스레드마다 같고, 스레드마다 다른 것은 `gettid()`다. fork가 "공짜"는 아니다: page table 복사 비용이 남아서 내가 재 보니 부모 RSS가 0에서 1 GiB로 늘면 `fork+wait`가 약 73 µs에서 300 µs로 늘었다. fork와 exec가 분리된 이유는 그 사이에서 자식이 fd 리다이렉션, 시그널 마스크, uid, CPU affinity를 준비할 수 있기 때문이고, 셸의 파이프가 이 틈으로 구현된다. 그 준비를 표준화한 것이 `posix_spawn`이다. 종료 쪽은 좀비(이미 끝났지만 부모가 `wait`하지 않아 `task_struct`가 남은 상태 — kill로 못 없애고 부모가 회수하거나 init이 입양)와, `kill -9`로도 안 죽는 D 상태(uninterruptible sleep — 드라이버가 시그널에 깨지 않는 대기를 하는 중)를 구분한다. RTOS로 치면 스레드는 같은 주소 공간의 태스크이고, 프로세스는 "MPU로 격리된 태스크 + 자기만의 주소 공간"이다.

> In the kernel both are `task_struct`s created by `clone()`; the flags decide what is shared, and fork is cheap because it copies page tables and marks pages copy-on-write.

**꼬리 질문**
- "A process is stuck and `kill -9` doesn't work. Why?" → D 상태. `ps`의 STAT/WCHAN, `/proc/<pid>/stack`, hung task 경고로 어느 드라이버의 어느 대기인지 찾는다. 해결은 드라이버를 killable + timeout으로.
- "What do voluntary vs nonvoluntary context switches tell you?" → 스스로 block한 횟수 vs 선점당한 횟수. 측정에서 CPU hog는 2초에 0/약 800, sleeper는 1550/1이었다.
- "Are Linux threads user-level threads?" → 아니다. NPTL은 1:1 모델이라 pthread 하나가 커널 task 하나다.

**함정**: 좀비를 `kill`로 없앤다고 말하는 것. 좀비는 이미 죽었다. 부모를 고치거나 부모를 끝내 init이 회수하게 한다.

**출처**: → A2 §2·§4·§5·§6·§8·§10, F1 §2, F3 §3

### Q3 ★★★ — `open("/dev/xyz")`에서 드라이버까지, fd의 3단 구조

**Q.** "Walk me through what happens when a program calls open() on a device file. What is the difference between a file descriptor and an open file description?"

**한국어로**: 장치 파일을 `open()`하면 무슨 일이 일어나나? file descriptor와 open file description은 무엇이 다른가?

**30초 답.** `openat` syscall에서 VFS가 경로를 따라 inode를 찾는다. 장치 파일이면 inode에 major:minor(`dev_t`)가 들어 있어서 `chrdev_open`이 그 번호로 등록된 `cdev`를 찾고, `struct file`의 `f_op`를 드라이버의 `file_operations`로 바꾼 뒤 드라이버의 `.open`을 부른다. 마지막으로 프로세스 fd 테이블의 가장 작은 빈 번호에 그 `struct file`을 넣고 번호를 돌려준다. 이후 `read`/`write`는 fd → `struct file` → `f_op->read`로 곧장 드라이버에 간다. 구조는 3단이다: fd(프로세스별 인덱스) → `struct file`(open file description: offset, 상태 플래그) → inode(파일 자체).

**2분 답.** 드라이버 입장에서 두 가지 상태 저장소를 구분한다: 장치마다의 상태는 `container_of(inode->i_cdev, struct my_dev, cdev)`로 찾고, open마다의 상태는 `.open`에서 `file->private_data`에 건다. fork나 dup은 같은 `struct file`을 참조 카운트로 공유하므로 offset도 공유하고, 드라이버의 `.release`는 **마지막** 참조가 사라질 때만 불린다 — close마다 해야 할 일이 있으면 `.flush`다. 따로 open한 두 프로세스는 `struct file`이 달라 offset도 따로라 서로 덮어쓸 수 있고, 로그처럼 여러 writer면 `O_APPEND`가 매 write를 원자적으로 끝에 붙인다. major/minor는 "어느 드라이버, 그 안의 몇 번째"이고(`/dev/null` 1:3, `/dev/zero` 1:5), 노드는 devtmpfs가 만들고 udev가 권한을 다듬는다. 어떤 드라이버가 `/dev/ttyS0` 뒤에 있는지는 `stat`으로 번호를 얻고 `/sys/dev/char/<major>:<minor>`를 따라가 `driver` 링크를 보면 된다.

> `chrdev_open` looks up the `cdev` by major/minor, swaps `file->f_op` to the driver's `file_operations`, calls its `.open`, and installs the `struct file` in the lowest free fd slot.

**꼬리 질문**
- "After fork, the child closes the device fd but `release()` isn't called. Why?" → 부모와 같은 `struct file`을 공유하고 있어서. release는 마지막 close에서만.
- "Where is close-on-exec stored?" → fd 쪽(fdtable 비트맵). 그래서 `dup`은 그 비트를 복사하지 않는다.
- "Where does a driver keep per-open state?" → `file->private_data`.

**함정**: "`.release`는 `close()`마다 불린다"고 말하는 것. 그리고 fd를 커널 객체 자체로 설명하는 것 — fd는 인덱스일 뿐이다.

**출처**: → A1 §10, A3 §1·§2·§9, F12 §2·§4, G4 §2·§7

### Q4 ★★ — select vs poll vs epoll, level vs edge

**Q.** "What is the difference between select, poll and epoll? Explain level-triggered versus edge-triggered."

**한국어로**: select, poll, epoll은 무엇이 다른가? level-triggered와 edge-triggered를 설명하라.

**30초 답.** 셋 다 여러 fd 중 준비된 것을 기다리는 방법이다. select는 1024비트 고정 비트맵이라 fd 번호 제한이 있고 매번 다시 채워야 한다. poll은 배열이라 제한은 없지만 호출마다 N개를 커널에 복사하고 N개 모두의 `.poll`을 부르므로 O(N)이다. epoll은 관심 목록을 커널에 **한 번 등록**하고, 이벤트가 난 fd만 콜백이 ready list에 넣기 때문에 대기 비용이 준비된 fd 수에만 비례한다. 내가 재 보니 fd 5000개 중 하나만 활성일 때 poll 한 번이 약 220 µs, epoll은 약 0.6 µs였다.

**2분 답.** LT와 ET는 펌웨어의 level/edge 인터럽트와 같다. LT는 데이터가 남아 있는 동안 매번 알려 주고, ET는 상태가 바뀔 때(새 데이터 도착) 한 번만 알려 준다. 고전적인 버그는 ET에서 버퍼를 다 비우지 않는 것이다 — 남은 데이터는 다음 패킷이 올 때까지 알림이 없어서 지연이나 멈춤이 생긴다. 그래서 ET는 반드시 non-blocking fd로 `EAGAIN`이 나올 때까지 읽는다. 실무 데몬 구조는 "모든 것을 fd로 만들어 epoll 하나에": IMU는 IIO 버퍼 fd, LiDAR는 UDP 소켓, 주기는 timerfd, 종료는 signalfd, 다른 스레드의 완료 알림은 eventfd. 드라이버 쪽에서는 셋이 전혀 다르지 않다 — 모두 같은 `.poll`(`poll_wait` + 마스크 반환)을 부른다(Q36).

> select and poll rescan every fd on every call, while epoll registers interest once and its wakeup callback puts only ready fds on a ready list, so the cost scales with ready fds, not watched fds.

**꼬리 질문**
- "With only 5 fds, which would you use?" → poll로 충분하다. 차이가 1 µs 미만이고 코드가 단순하다.
- "How do you run a 100 Hz loop and detect missed deadlines?" → timerfd(`CLOCK_MONOTONIC`, 10 ms interval)를 epoll에 넣고, read한 만료 횟수가 1보다 크면 그만큼 놓친 것.
- "Can you epoll a regular file?" → 안 된다. `epoll_ctl`이 `EPERM`. 파일 I/O는 worker 스레드나 io_uring.

**함정**: "epoll이 항상 빠르다"고만 말하는 것. fd가 적으면 차이가 없다. 그리고 ET를 blocking fd로 쓰는 것.

**출처**: → A4 §2·§3·§4·§5·§6·§8·§9, G6 §1·§4

### Q5 ★★★ — 가상 메모리, page fault, overcommit, OOM

**Q.** "Explain virtual memory in Linux. What is a page fault — minor versus major? What happens when you malloc more than physical RAM?"

**한국어로**: Linux의 가상 메모리를 설명하라. page fault란 무엇이고 minor와 major는 어떻게 다른가? 물리 RAM보다 큰 malloc을 하면 어떻게 되나?

**30초 답.** 프로세스마다 자기 page table(arm64는 TTBR0)과 VMA 목록(`mm_struct`, `vm_area_struct`)을 가진다. `malloc`이나 `mmap`은 VMA, 즉 "이 주소 범위를 써도 된다"는 약속만 만들고, 물리 페이지는 **처음 접근할 때 page fault로** 붙는다(demand paging). minor fault는 데이터가 이미 RAM에 있어(0 페이지 할당, page cache 히트) PTE만 채우면 되는 경우이고, major fault는 디스크나 swap에서 읽어야 하는 경우다. 기본 overcommit 모드에서는 큰 malloc이 성공해도 실제로 다 쓰면 OOM killer가 badness 점수가 가장 큰 프로세스를 죽인다.

**2분 답.** 내가 VM에서 재 보니 4 KiB 익명 페이지의 minor fault가 약 0.5 µs, readahead를 끈 cold 파일의 major fault가 약 39 µs였다. 512 MB 장비에서 `malloc(1 GB)` 한 번은 "명백히 큰" 요청이라 보통 거절되지만, 작은 덩어리로 나누면 전부 성공한다 — 받은 것은 가상 주소뿐이기 때문이다. 장비에서 중요한 프로세스는 `oom_score_adj`로 보호하고, 부가 서비스는 memory cgroup 한도로 묶는다. 메모리 예산은 RSS가 아니라 **PSS**로 잡는다: 4개 프로세스가 32 MiB를 공유하는 실험에서 RSS는 각 32 MiB, PSS는 각 8 MiB였다(`/proc/<pid>/smaps_rollup`). 임베디드 장비는 보통 swap이 없고, 쓴다면 zram이다. "free가 적다"는 대개 page cache 때문이고 회수 가능하다. 커널 쪽 경로는 MMU abort → `do_page_fault` → `handle_mm_fault`이고, Don의 말로는 "page fault = MMU abort를 커널이 정상 경로로 처리하는 것"이다.

> `malloc` only creates a VMA; physical pages arrive on first touch through page faults, and with overcommit the bill comes later from the OOM killer.

**꼬리 질문**
- "How do you prevent page faults in a real-time thread?" → `mlockall(MCL_CURRENT | MCL_FUTURE)` + 스택·버퍼 prefault. 실측: 루프 안에서 64 MiB를 처음 쓰면 fault 16384번, mlockall 후 0번(N1 §8).
- "RSS vs PSS for budgeting?" → PSS. RSS는 공유 페이지를 중복 계산한다.
- "Why does `free` show so little free memory?" → page cache가 빈 메모리를 쓰고 있을 뿐, `MemAvailable`을 본다.

**함정**: "malloc이 성공했으니 메모리를 확보했다"고 말하는 것. 그리고 page cache를 메모리 누수로 오해하는 것.

**출처**: → A5 §1·§2·§3·§4·§8·§9, F11 §4·§5·§6·§8·§9·§10, N1 §8

### Q6 ★★ — mmap, MAP_SHARED vs MAP_PRIVATE, zero-copy

**Q.** "What does mmap do? MAP_SHARED versus MAP_PRIVATE? How would you get camera frames to user space without copying, and how does a driver implement mmap?"

**한국어로**: mmap은 무엇을 하나? SHARED와 PRIVATE의 차이는? 카메라 프레임을 복사 없이 유저에게 주려면? 드라이버는 mmap을 어떻게 구현하나?

**30초 답.** mmap은 파일이나 장치 메모리를 내 주소 공간에 직접 매핑한다. `MAP_SHARED`는 모든 매핑이 같은 물리 페이지를 가리켜 쓰기가 다른 프로세스와 파일에 보이고, `MAP_PRIVATE`는 copy-on-write라 쓰는 순간 내 사본이 생기고 파일에는 반영되지 않는다(실행 파일 로딩이 PRIVATE, 공유 메모리·장치 버퍼가 SHARED). 드라이버는 `file_operations.mmap(file, vma)`에서 크기와 offset을 검사하고, 캐시 속성(`vm_page_prot`)을 정한 뒤 `remap_pfn_range`로 PTE를 채운다. DMA coherent 버퍼면 `dma_mmap_coherent`, 지연 매핑이면 `vm_ops->fault`다. 카메라는 V4L2 MMAP 스트리밍(REQBUFS → QUERYBUF → mmap → QBUF/DQBUF)으로 복사 없이 받는다.

**2분 답.** mmap의 이점은 **복사 제거**다. 4 MB 카메라 프레임에서는 확실히 이기지만, 32 B IMU 샘플은 복사가 싸서 mmap 링을 바쁜 폴링으로 긁으면 오히려 블로킹 `read()`보다 CPU를 더 쓰는 것을 G5에서 측정했다 — mmap 링은 `poll()`과 묶어 써야 제값을 한다. 보안이 중요하다: `remap_pfn_range`는 요청한 크기만큼 그냥 매핑하므로 크기 검사를 빼면 버퍼 뒤의 커널 페이지가 유저에게 노출된다(G5 §6에서 uid 1000이 커널 페이지의 비밀을 읽고 덮어썼다). 공유 링이면 커널은 `smp_store_release`로 head를 올리고 유저는 `smp_load_acquire`로 읽는다. 다른 장치(인코더, GPU, NPU)로 넘길 때는 `VIDIOC_EXPBUF`로 dma-buf fd를 내보내고, 다른 프로세스로는 UNIX socket `SCM_RIGHTS`로 fd를 보낸다. 버퍼가 cacheable이면 CPU 접근 전후에 캐시 동기화(`DMA_BUF_IOCTL_SYNC`)가 필요하다.

> mmap removes the copy, not the synchronization: the driver validates the VMA, picks cache attributes, and fills PTEs with `remap_pfn_range` or `dma_mmap_coherent`.

**꼬리 질문**
- "Is mmap always faster than read?" → 아니다. 큰 버퍼에서 이기고, 작은 샘플은 측정해서 정한다.
- "What flags does `remap_pfn_range` set on the VMA?" → `VM_IO`, `VM_PFNMAP`(+ dontexpand/dontdump).
- "Why not `/dev/mem`?" → 드라이버와 HW 상태 충돌, 인터럽트·전원 관리 불가, 보안 구멍. UIO나 정식 드라이버로.

**함정**: mmap 핸들러에서 `vma->vm_end - vma->vm_start`를 버퍼 크기와 비교하지 않는 것. 그리고 "mmap이면 캐시 문제가 없다"는 말.

**출처**: → A5 §6·§7·§12, G5 §4·§5·§6, A7 §5, I5 §5·§8, O4 §4

### Q7 ★★ — IPC 고르기 (그리고 시그널 한 줄)

**Q.** "What IPC mechanisms does Linux provide, and how do you choose between them?"

**한국어로**: Linux의 IPC 수단은 무엇이 있고, 어떻게 고르나?

**30초 답.** 네 부류다: 바이트 스트림(pipe, FIFO, UNIX stream socket), 메시지(UNIX SEQPACKET/DGRAM, POSIX message queue), 공유 메모리(POSIX shm, memfd, dma-buf), 그리고 그 위의 버스(D-Bus). 고르는 기준은 복사 횟수, 메시지 경계, 깨우기 비용, 다수 수신자, 상대가 죽었을 때의 동작이다. 실무 기본값은 제어는 UNIX socket, 고속 데이터는 shm 링 + eventfd, 큰 버퍼는 fd 전달(`SCM_RIGHTS`), 시스템 서비스와의 대화는 D-Bus다.

**2분 답.** 공유 메모리가 빠른 이유는 커널이 MMU 설정만 하고 데이터 경로에서 빠지기 때문이고, 대가는 동기화·메모리 순서·통지·크래시 처리를 내가 다 해야 한다는 것이다. 그리고 A7에서 측정해 보면 상대를 futex로 깨우는 순간 지연은 pipe와 같아진다 — 빠른 것은 복사가 없어서지 wakeup이 빨라서가 아니다. pipe는 커널 안의 페이지 링(기본 16페이지 = 64 KiB)이고 `PIPE_BUF`(Linux 4096) 이하 write는 원자적이라 여러 writer가 있어도 안 섞인다 — 4097바이트에서 바로 찢어지는 것을 확인했다. 스트림 소켓은 경계가 없으니 길이 프리픽스로 framing한다. 시그널은 IPC로 데이터를 나르는 데 쓰지 않는다: 핸들러 안에서는 async-signal-safe 함수만(printf·malloc 금지) 부를 수 있으니, 데몬은 시그널을 block하고 signalfd로 이벤트 루프에서 받는다. 시그널에 깨진 syscall은 `EINTR`을 받거나 `SA_RESTART`면 자동 재시작된다.

> I choose by copies, message boundaries, wakeup cost and crash behavior: UNIX sockets for control, a shared-memory ring plus eventfd for high-rate data, and fd passing for big buffers.

**꼬리 질문**
- "Why not TCP on localhost?" → 동작은 하지만 IP 스택 비용이 있고 `SO_PEERCRED`·`SCM_RIGHTS`·파일 권한 기반 접근 제어가 없다.
- "What if the process holding a shared-memory lock dies?" → robust mutex(`EOWNERDEAD` → 검증 → `pthread_mutex_consistent`) 또는 락 없는 SPSC 링.
- "Can you call printf in a signal handler?" → 안 된다. 플래그만 세우거나 `write()`처럼 async-signal-safe 함수만.

**함정**: "공유 메모리가 항상 최고"라고 말하는 것. 통지·동기화·크래시 처리 비용을 같이 말해야 한다.

**출처**: → A7 §1·§2·§3·§5·§7·§8, A6 §5·§6, A4 §5

### Q8 ★★ — Cross toolchain, triplet, sysroot

**Q.** "What is a cross compiler and why do we use one for embedded Linux? What is a sysroot, and what goes wrong if it's wrong?"

**한국어로**: 크로스 컴파일러란 무엇이고 왜 쓰나? sysroot는 무엇이고, 틀리면 무엇이 깨지나?

**30초 답.** 컴파일러가 도는 기계(host)와 결과물이 도는 기계(target)가 다른 컴파일러다. 보드는 느리고 저장공간이 작고 rootfs에 개발 도구가 없어서, 빠른 PC에서 보드용 바이너리를 만든다. Linux 타깃이면 컴파일러와 binutils만이 아니라 **타깃 libc, 동적 로더, 커널 UAPI 헤더가 든 sysroot**까지가 툴체인이다 — 이게 bare-metal 크로스 컴파일과 다른 점이다. triplet `aarch64-linux-gnu`나 `arm-linux-gnueabihf`는 arch-os-libc/ABI를 뜻하고, `arm-none-eabi`는 OS 없이 newlib을 정적으로 쓰는 bare-metal용이다.

**2분 답.** sysroot는 타깃 rootfs의 개발용 축소판이고, 컴파일러가 헤더와 라이브러리를 호스트가 아닌 여기서 찾게 하는 기준 경로다. 틀리면 호스트 헤더가 섞여 링크 실패나 런타임 구조체 불일치가 나고, sysroot의 glibc가 보드보다 새로우면 보드에서 `version GLIBC_2.xx not found`가 난다. 툴체인의 커널 헤더는 보드 커널 **이하**로 맞춘다 — UAPI는 하위 호환만 보장하므로 새 헤더로 빌드한 앱은 보드에 없는 syscall·ioctl을 써서 `ENOSYS`/`EINVAL`을 받는다. `-march`/`-mcpu`를 보드보다 높게 잡으면 `Illegal instruction`이 난다 — ARMv8.1 LSE atomic으로 빌드한 바이너리가 Cortex-A53 에뮬레이션에서 SIGILL로 죽는 것을 B1에서 재현했다(`-mtune`은 틀려도 느려질 뿐). 커널은 `ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-`를 모든 make에 주고, 모듈은 반드시 그 커널을 빌드한 툴체인·같은 빌드 트리로 만든다. Clang은 한 바이너리가 `--target`으로 모든 아키텍처를 다루지만 `--sysroot`가 필수이고, 커널은 `LLVM=1`로 빌드한다.

> A Linux cross toolchain is compiler plus binutils plus a sysroot with the target's libc, dynamic loader and kernel headers; most "works on my PC, fails on the board" problems are sysroot or libc-version mismatches.

**꼬리 질문**
- "How is building a kernel module different from building a user program?" → libc·crt·로더가 없다. Kbuild가 `-nostdinc`, arm64 `-mgeneral-regs-only`, `ld -r` + `module.lds`로 재배치 가능한 `.ko`를 만들고, 미해결 심볼은 insmod 때 커널 export 표로 해결된다.
- "Hard-float vs soft-float — can you mix them?" → 호출 규약이 달라 못 섞는다. 링커가 ELF 속성으로 거부한다.
- "Kernel headers newer than the board kernel?" → 문제가 될 수 있다. 보드 커널 이하로.

**함정**: "크로스 컴파일 = 컴파일러 이름만 바꾸면 된다"는 답. 그리고 커널 `menuconfig`를 `ARCH` 없이 돌려 호스트 아키텍처 설정으로 덮어쓰는 실수(E2 §11에서 재현).

### Q9 ★ — 정적 vs 동적 링크, glibc vs musl, "파일이 있는데 No such file"

**Q.** "A binary you cross-compiled says 'No such file or directory' on the target, but the file is clearly there. What's going on? And glibc versus musl — how do you choose?"

**한국어로**: 크로스 컴파일한 바이너리가 분명히 있는데 "No such file or directory"가 난다. 왜인가? glibc와 musl은 어떻게 고르나?

**30초 답.** 동적 링크된 ELF에는 `PT_INTERP`에 로더 경로(예: `/lib/ld-linux-aarch64.so.1`)가 박혀 있고, 커널이 `execve` 때 그 로더를 연다. 로더가 보드에 없으면 `execve`가 `ENOENT`를 돌려주고 셸은 "not found"라고만 한다. `readelf -l`로 interpreter를 확인하고, 보드 libc와 맞는 툴체인으로 다시 빌드하거나 정적으로 빌드한다. glibc vs musl은 먼저 벤더 바이너리를 본다 — GPU·NPU·ISP 라이브러리는 거의 항상 glibc 전용이라 하나라도 있으면 glibc, 없고 플래시가 작거나 정적 도구가 많으면 musl이다.

**2분 답.** 로더는 `DT_NEEDED` 라이브러리를 RPATH(RUNPATH가 없을 때만) → `LD_LIBRARY_PATH` → RUNPATH → `/etc/ld.so.cache` → 기본 경로 순으로 찾고, 심볼 버전을 확인하고, 재배치와 RELRO를 한 뒤 `_start` → `__libc_start_main` → `main`으로 간다. `GLIBC_2.38 not found`는 새 glibc로 링크해서 바이너리가 새 버전 태그를 요구하는 것이다(`objdump -T`로 확인). 크기는 B2·B3에서 정적 hello가 glibc 약 550~700 KiB, musl 약 33~80 KiB였고, 대신 musl은 멀티스레드 malloc이 느리고 기본 스레드 스택이 128 KiB라 스택 크기를 명시해야 한다. glibc 정적 링크는 피한다: NSS·iconv·dlopen이 실행 중에 공유 libc를 끌고 와서 버전이 다르면 깨진다(strace로 정적 바이너리가 `libnss_systemd.so.2`와 `libc.so.6`을 여는 것을 봤다). `ldd`는 로더를 실행하는 스크립트라 신뢰할 수 없는 바이너리에는 `readelf -d`를 쓴다. 다른 아키텍처면 "Exec format error"다.

> "No such file" for a file that exists almost always means the ELF's `PT_INTERP` loader is missing on the target; check it with `readelf -l` and build against the board's libc.

**꼬리 질문**
- "What happens before main()?" → 커널이 ELF와 로더를 매핑하고 스택에 argc/argv/envp/auxv를 쌓는다 → 로더가 라이브러리 로드·재배치 → `_start` → `__libc_start_main`(TLS, 생성자) → `main`.
- "You get a crash address from the field — how to a source line?" → 로드 기준 주소를 빼서 오프셋을 만들고, Build ID가 같은 debug 파일로 `addr2line -f -i -e`.
- "Explain PLT/GOT." → 외부 호출은 PLT 스텁 → GOT의 주소로 간다. lazy binding이면 첫 호출 때 ld.so가 GOT를 채운다.

**함정**: "정적 링크면 어디서나 돈다"고 말하는 것 — glibc 정적은 NSS 때문에 아니다. 그리고 크로스 바이너리에 `ldd` 결과를 믿는 것.

**출처**: → B2 §2·§3·§5·§6·§7·§8, B3 §5·§6·§8·§9

그림 2 — arm64 보드의 부트 사슬. 윗줄은 펌웨어(ROM → SPL/BL2 → BL31 → U-Boot), 아랫줄은 커널(head.S → start_kernel → initcall → PID 1)이다. 각 단계는 다음 단계를 메모리에 올리고 서명을 검증해 chain of trust를 잇는다(Q43). 숫자는 QEMU TCG 값이라 비율로만 본다.

**30초 답.** 전원이 들어오면 SoC의 BootROM이 boot pin·eFuse로 부트 미디어를 고르고 첫 로더(SPL 또는 TF-A BL2)를 **내부 SRAM**에 올린다. SPL이 DDR·PMIC·클럭을 초기화하고 TF-A BL31과 U-Boot를 DRAM에 올린다. BL31은 EL3에 상주해 PSCI 같은 서비스를 맡고, U-Boot가 커널 Image·DTB·initramfs를 RAM에 놓고 x0에 DTB 주소를 담아 점프한다. 커널은 DTB로 하드웨어를 알고, 드라이버를 probe하고, initramfs나 rootfs를 마운트한 뒤 PID 1 init을 실행하고, init(systemd 등)이 서비스와 getty를 띄운다.

**2분 답.** "각 단계가 왜 있는가"를 붙인다. ROM은 수정 불가라 최소 기능만 갖고, DDR은 보드마다 타이밍·배선이 달라서 SRAM에 들어가는 작은 SPL이 초기화한다(U-Boot proper는 수백 KB~MB라 SRAM에 안 들어간다). TF-A는 Secure/Non-secure 세계를 나누는 EL3 펌웨어로 BL1/BL2/BL31(+BL32 OP-TEE)로 나뉘고, 부팅 후에도 BL31이 남아 2차 CPU 켜기(`CPU_ON`), suspend, reset을 SMC로 처리한다 — 그래서 Linux는 SoC마다 다른 전원 코드 없이 DT의 `enable-method = "psci"`만 보고 코어를 켠다. U-Boot는 `bootcmd`로 이미지를 읽어 DT `/chosen`에 `bootargs`와 initrd 위치를 쓰고 MMU·D-cache를 끈 채 커널로 넘긴다. 커널은 `head.S`에서 MMU를 켜고 `start_kernel` → `setup_arch`에서 DT로 메모리와 cmdline을 잡고, initcall 레벨 순으로 드라이버를 probe하고, `/init`을 실행한다. QEMU에서 8번씩 재 보니 TF-A 약 30 ms, U-Boot 약 0.17 s, 커널→/init이 전체 1.1 s의 약 70%였다. 각 단계가 다음 단계의 서명을 검증하면 secure boot이 된다.

> BootROM loads SPL into SRAM, SPL brings up DDR and loads TF-A BL31 and U-Boot, U-Boot hands the kernel the DTB address in x0, and the kernel probes drivers from the DT and execs PID 1.

**꼬리 질문**
- "Why can't the boot ROM load U-Boot directly?" → ROM이 쓸 수 있는 곳은 SRAM뿐이고 DDR은 아직 꺼져 있다. U-Boot는 SRAM에 안 들어간다. SRAM이 더 작으면 TPL을 하나 더 둔다.
- "What does BL31 do after Linux has booted?" → EL3에 상주. PSCI(CPU on/off, suspend, `SYSTEM_RESET`/`SYSTEM_OFF`)와 OP-TEE가 있으면 세계 전환.
- "Walk me through the ARMv8 exception levels." → EL0 앱, EL1 커널, EL2 하이퍼바이저, EL3 secure monitor(BL31). OP-TEE는 S-EL1, TA는 S-EL0.

**함정**: "U-Boot가 DDR을 초기화한다"고만 말하는 것(대부분의 SoC에서 SPL이 한다). 그리고 "Linux가 2차 CPU를 직접 켠다"는 말 — PSCI로 펌웨어에 부탁한다.

### Q11 ★★ — U-Boot → 커널 핸드오프: bootcmd, bootargs, DTB, FIT

**Q.** "What's the difference between bootcmd and bootargs? How does the kernel receive its command line and device tree on arm64? Why use a FIT image?"

**한국어로**: bootcmd와 bootargs는 무엇이 다른가? arm64에서 커널은 커맨드라인과 DT를 어떻게 받나? FIT 이미지는 왜 쓰나?

**30초 답.** `bootcmd`는 U-Boot가 autoboot 때 **실행할 명령 스크립트**이고, `bootargs`는 **커널에 넘길 커맨드라인 문자열**이다. U-Boot가 Image·DTB·initrd를 RAM에 읽고, `booti`가 Image 헤더를 확인하고 겹침을 검사한 뒤 DTB의 `/chosen`에 `bootargs`와 `linux,initrd-start/end`를 써 넣는다. 그다음 arm64 부트 프로토콜대로 MMU·D-cache를 끈 상태에서 **x0 = DTB 물리 주소, x1–x3 = 0**으로 Image 시작에 점프한다. FIT는 커널·DTB·initramfs를 해시와 함께 한 컨테이너에 담고 configuration으로 조합을 정의해, 짝이 맞는 버전과 서명 검증(verified boot)을 준다.

**2분 답.** 커널 쪽에서 cmdline은 `early_init_dt_scan_chosen()`이 읽고, 결과는 `/proc/cmdline`과 `/sys/firmware/devicetree/base/chosen`에서 확인한다. U-Boot 환경은 config가 정한 곳(eMMC 고정 오프셋, SPI NOR 섹터, FAT 파일, UBI 볼륨)에 CRC32 + `key=value` 목록으로 저장되고, redundant 설정이면 두 벌이다. Linux에서는 `fw_env.config`에 같은 위치를 적고 `fw_printenv`/`fw_setenv`로 읽고 쓴다 — A/B 업데이트의 슬롯 선택과 bootcount가 바로 이 방식이다(Q43). U-Boot가 initrd와 DTB를 옮기는 이유는 커널이 초기에 쓰는 메모리(BSS, 초기 page table)와 겹치지 않게 하고 DT를 고칠 여유를 만들기 위해서다. FIT 검증은 공짜가 아니다 — C3에서 43 MB sha256이 QEMU에서 3초를 넘었다. 개발 루프는 U-Boot env에 `dhcp; tftp kernel; tftp dtb; booti`를 넣고 NFS root를 쓰면 빌드 → 리셋이 1분 안이다.

> `bootcmd` is what U-Boot runs; `bootargs` is what the kernel gets — U-Boot writes it into `/chosen/bootargs` of the DTB and jumps to the Image with the DTB's physical address in x0.

**꼬리 질문**
- "Why sign the FIT configuration rather than each image?" → 이미지별 서명은 "부품이 정품"만 보장한다. 공격자가 서명된 옛 커널 + 디버그 DT를 섞을 수 있다. configuration 서명은 조합을 고정한다(L5 §5에서 실측).
- "What is Falcon mode?" → SPL이 U-Boot proper를 건너뛰고 커널을 바로 부팅하는 기능.
- "How do you change U-Boot env from Linux?" → `fw_setenv` + `fw_env.config`.

**함정**: bootcmd와 bootargs를 섞어 말하는 것, "x0에 cmdline 문자열 주소가 들어간다"고 말하는 것(DTB 주소다).

**출처**: → C3 §4·§5·§9·§10·§12·§13, C1 §4, L5 §2·§5

### Q12 ★★★ — 커널 시작부터 init까지, 그리고 "Starting kernel ..." 이후 무소식

**Q.** "Walk me through what happens from the moment the bootloader jumps to the kernel until init runs. The board prints 'Starting kernel ...' and then nothing — how do you debug it?"

**한국어로**: 부트로더가 커널로 점프한 순간부터 init이 돌 때까지 무슨 일이 일어나나? 보드가 "Starting kernel ..."만 찍고 멈추면 어떻게 디버그하나?

**30초 답.** `head.S`가 identity map을 만들고 MMU를 켠 뒤 커널을 가상 주소로 옮겨 `start_kernel()`을 부른다. `start_kernel`은 `setup_arch`에서 DTB로 메모리와 early 파라미터(earlycon)를 처리하고, 메모리·스케줄러·인터럽트·타이머·콘솔을 초기화한 뒤 `rest_init`에서 PID 1(`kernel_init`)과 PID 2(`kthreadd`)를 만든다. `kernel_init`은 initcall을 레벨 순으로 돌려 드라이버를 probe하고, initramfs를 풀거나 `root=`를 마운트하고, `.init` 메모리를 해제한 뒤 `/init`을 execve한다. 멈춤 디버그의 첫 수는 **`earlycon`**이다 — 커널이 살아 있는지부터 가른다.

**2분 답.** initcall은 `module_init`·`subsys_initcall` 같은 매크로가 함수 포인터를 `.initcallN.init` 링커 섹션에 넣어 만든 표이고, 0 pure → 1 core → 2 postcore → 3 arch → 4 subsys → 5 fs → rootfs → 6 device → 7 late 순으로 돈다. built-in 드라이버의 `module_init`은 레벨 6이다 — C6에서 잰 defconfig 커널은 1,887개 중 1,183개가 device 레벨이었다. "Starting kernel ..." 뒤 무소식은 이렇게 가른다: earlycon을 넣었더니 커널 로그가 나오면 `console=` 이름이나 UART 드라이버 문제이고, 그래도 안 나오면 커널 진입 전후 문제라 DTB 주소·정렬, Image·initrd·DTB 겹침(헤더의 `image_size`), 그 SoC를 지원하는 Kconfig를 본다. 로그가 어딘가에서 끊기면 `initcall_debug`로 돌아오지 않은 initcall을 찾는다. 마지막 수단은 JTAG으로 PC를 보고 `__log_buf`를 메모리에서 덤프하는 것이다. 로그가 끝까지 나오는데 셸이 없으면 "unable to open an initial console"과 `/dev/console`을, "VFS: Unable to mount root fs on unknown-block(0,0)"이면 루트 장치 드라이버가 없거나 `root=` 오타를 의심한다. PID 1이 exit하면 "Attempted to kill init!"으로 panic한다.

> I first add `earlycon` to split "kernel never ran" from "console never registered", then use `initcall_debug` to find the initcall that never returns, and fall back to JTAG plus a `__log_buf` dump.

**꼬리 질문**
- "earlycon vs console?" → earlycon은 `setup_arch`에서 켜지는 폴링 UART 출력(정식 드라이버·IRQ·클럭 프레임워크 없이 레지스터에 직접). 정식 console이 등록되면 꺼진다.
- "Why does output appear all at once when the console comes up?" → printk는 링 버퍼에 쓰고, console 등록 때 쌓인 내용을 재생한다.
- "initramfs vs `root=` directly?" → 스토리지 드라이버가 built-in이고 암호화·A/B 선택이 없으면 `root=PARTUUID=… rootwait`가 더 빠르다. dm-verity, LUKS, 모듈 로드, 슬롯 선택이 필요하면 initramfs → `switch_root`.

**함정**: "로그가 안 나왔으니 커널이 안 돌았다"고 단정하는 것. 콘솔만 아직 등록되지 않았을 수 있다. 그리고 probe 함수에 `__init`을 붙이는 실수(부팅 후 해제된 메모리로 점프 → oops, modpost section mismatch 경고).

## 3. Device Tree (Q13–Q17)

Don이 "센서가 안 보인다"를 디버그할 때 가장 먼저 열 곳이다. DT는 데이터이고, 드라이버는 그 데이터를 이름으로 꺼내 쓴다는 원칙 하나로 다섯 질문이 다 풀린다.

### Q13 ★★★ — Device Tree는 왜 있나

**Q.** "What is a Device Tree and why does Linux use it? How is it different from ACPI?"

**한국어로**: Device Tree란 무엇이고 Linux는 왜 쓰나? ACPI와는 무엇이 다른가?

**30초 답.** PCIe·USB처럼 스스로 정체를 밝히지 못하는(non-discoverable) 하드웨어 — SoC 안의 MMIO 주변장치, I2C/SPI 센서, GPIO·인터럽트 배선 — 를 커널에 알려 주는 **데이터 구조**다. 예전 ARM은 이걸 보드마다 C 코드(board file)로 커널에 박아 보드마다 커널을 따로 빌드했는데, DT는 그 설명을 커널 밖의 `.dtb`로 빼서 부트로더가 넘기게 했다. 그래서 커널 하나로 수많은 보드를 지원한다. DT에는 하드웨어 사실만 적고 드라이버 정책은 적지 않는다.

**2분 답.** 흐름은 `.dts`/`.dtsi` → C 전처리(`dt-bindings` 헤더 상수 공유) → `dtc` → big-endian FDT 바이너리 `.dtb`(매직 `0xd00dfeed`) → 부트로더가 `/chosen`을 고쳐 x0로 전달 → 커널 `unflatten_device_tree()`가 `device_node` 트리로 펼침 → GIC·클럭·타이머는 `*_OF_DECLARE`로 먼저 → `of_platform_populate()`가 compatible 있고 `status = "okay"`인 노드마다 `platform_device`를 만든다. PCIe 장치는 config space가 스스로 답하므로 DT 노드가 없고 host bridge 노드 하나만 있다(D1에서 e1000을 꽂아도 DT 노드 수가 그대로인 것을 확인). ACPI는 펌웨어가 주는 테이블에 AML 실행 코드까지 들어 있어 전원 관리 절차를 펌웨어가 정의하고, x86과 arm64 서버에서 쓴다. 드라이버가 `device_property_*` fwnode API를 쓰면 둘 다 지원된다. 커널이 실제로 받은 DT는 소스가 아니라 `/proc/device-tree`(= `/sys/firmware/devicetree/base`)와 원본 blob `/sys/firmware/fdt`에서 확인한다 — 부트로더가 다른 DTB를 주거나 고쳐 넣는 일이 흔하다.

> Device Tree is data, not code: it describes the non-discoverable hardware so one kernel binary can boot many boards, and the bootloader hands it over in x0.

**꼬리 질문**
- "Can you change the hardware description without rebuilding the kernel?" → 예. `.dtb`만 다시 만들거나, `fdtput`으로 고치거나, overlay(Q17).
- "Why don't PCIe devices need DT nodes?" → discoverable. 다만 host bridge(ECAM, 주소 창, INTx 매핑, MSI 컨트롤러)는 DT에 있다.
- "Why doesn't embedded use ACPI?" → SoC마다 수백 개의 비발견 장치를 펌웨어 벤더가 AML까지 맞춰야 하고, 커널 트리와 함께 진화하는 DT가 개발 흐름에 맞다.

**함정**: DT에 "기본 샘플링 주기" 같은 정책을 넣겠다고 말하는 것. 그리고 dts를 고친 뒤 소스만 보고 "반영됐다"고 판단하는 것.

**출처**: → D1 §1·§2·§3·§4·§5·§7·§8·§9, D2 §8·§10, D5 §4·§7

### Q14 ★★★ — compatible 매칭과 probe

**Q.** "How does a driver get bound to a device on a Device Tree based system? If a node has compatible = "vendor,chip-v3", "vendor,chip", which driver entry wins?"

**한국어로**: DT 기반 시스템에서 드라이버는 어떻게 장치에 붙나? compatible이 `"vendor,chip-v3", "vendor,chip"`이면 어느 드라이버 항목이 이기나?

**30초 답.** 부팅 때 `of_platform_populate()`가 루트와 simple-bus 밑의 compatible 있는 노드마다 `platform_device`를 만든다. 드라이버는 `of_match_table`을 가진 `platform_driver`를 등록한다. 장치든 드라이버든 **나중에 등록되는 쪽에서** 버스의 `match`(`platform_match` → `of_driver_match_device`)가 compatible 문자열을 비교하고, 맞으면 `really_probe()`가 pinctrl·DMA 설정을 한 뒤 드라이버의 `probe()`를 부른다. compatible 목록은 구체적인 것부터 쓰고, 커널은 노드 목록의 앞쪽 문자열과 맞을수록 높은 점수를 줘서 v3 전용 항목이 있으면 그게, 없으면 generic 항목이 이긴다 — 드라이버 테이블 순서와는 무관하다.

**2분 답.** I2C·SPI 자식 노드는 platform 장치가 되지 않고, 컨트롤러 드라이버가 probe될 때 `of_i2c_register_devices()`가 `i2c_client`로 만들고 I2C 버스의 match가 같은 OF 매칭을 한다. 순서는 상관없다: 드라이버 등록 때 `driver_attach()`가 기존 장치를, 장치 추가 때 `__device_attach()`가 기존 드라이버를 훑어 같은 `match` → `really_probe` 경로로 합류한다. 자동 로드는 `MODULE_DEVICE_TABLE(of, …)`가 테이블을 `.ko`의 alias로 내보내고 depmod가 색인하며, 장치가 생길 때 uevent의 `MODALIAS`로 udev가 modprobe하는 구조다 — 빠뜨려도 insmod로는 잘 붙어서 개발 중엔 모르고 제품에서 자동 로드 실패로 드러난다. 손으로 다시 붙이려면 sysfs `drivers/<drv>/unbind`·`bind`, 특정 드라이버를 강제하려면 장치의 `driver_override`(VFIO가 쓰는 방법). 매칭 여부는 dynamic debug로 `drivers/base/dd.c`를 켜면 "matched device with driver" 줄로 바로 보인다.

> Whichever side registers last triggers the bus `match`, which compares the node's compatible list against `of_match_table`; earlier strings in the node's list score higher, so the most specific match wins.

**꼬리 질문**
- "What breaks if you forget `MODULE_DEVICE_TABLE`?" → 매칭은 되지만 udev 자동 로드가 안 된다.
- "Does it matter whether the module is loaded before or after the device is created?" → 상관없다. 두 경로가 같은 곳에서 만난다.
- "How do you force a driver onto a device?" → `driver_override` + `drivers_probe`.

**함정**: "테이블에서 먼저 나온 항목이 이긴다"거나 "모듈 로드 순서가 중요하다"고 말하는 것.

**출처**: → D3 §2·§3·§4·§5·§6·§7·§8·§9, G2 §6·§7, G9 §4

### Q15 ★★ — `#address-cells`, `reg`, `ranges`, phandle, `interrupts` 해독

**Q.** "What do #address-cells and #size-cells mean, and how is reg parsed? What does ranges do? Decode interrupts = <0 80 4>."

**한국어로**: `#address-cells`와 `#size-cells`는 무엇이고 `reg`는 어떻게 읽나? `ranges`는 무엇을 하나? `interrupts = <0 80 4>`를 해독하라.

**30초 답.** 둘 다 **자식 노드의 `reg`를 어떻게 끊어 읽을지** 정하는 부모의 프로퍼티다. 64비트 SoC 루트는 보통 2/2라서 `reg = <0x0 0x9000000 0x0 0x1000>`이 주소 0x9000000, 크기 4 KiB 한 쌍이고, I2C 버스는 1/0이라 `reg = <0x68>`은 슬레이브 주소만이다. `ranges`는 버스 브리지의 주소 디코더 표(자식 주소, 부모 주소, 길이)라서 커널이 `reg`를 루트까지 번역해 CPU 물리 주소를 얻는다 — 빈 `ranges;`는 1:1, `ranges`가 없으면 번역 불가(I2C/SPI처럼 자식 주소가 메모리 주소가 아님). `interrupts = <0 80 4>`는 부모가 GIC일 때 SPI, 번호 80(GIC INTID 112), level-high다.

**2분 답.** 셀 수는 항상 **provider 쪽 `#xxx-cells`**가 정한다: 인터럽트는 부모의 `#interrupt-cells`, 클럭은 `#clock-cells`, GPIO는 `#gpio-cells`. 커널은 `of_parse_phandle_with_args()` 하나로 "phandle + 인자"를 파싱하고 각 프레임워크의 xlate 콜백이 해석한다. phandle은 노드의 32비트 ID로, 소스에서 `uart0:` label을 붙이고 `<&uart0>`으로 참조하면 dtc가 숫자로 바꾼다. 인터럽트 번호는 세 개가 따로 있다는 점이 핵심이다: DT의 80, GIC hwirq 112(SPI는 32부터), 그리고 Linux virq(F6에서는 22). 드라이버는 `platform_get_irq()`로 virq를 받고 숫자를 하드코딩하지 않는다. `dma-ranges`는 반대 방향(장치가 버스 마스터로 본 주소 ↔ CPU 물리 주소)이고 DMA API가 자동 반영한다. 보드 `.dts`에서 SoC `.dtsi` 노드를 바꿀 때는 `&i2c1 { status = "okay"; clock-frequency = <400000>; };`처럼 label로 다시 열고, 끌 때는 `status = "disabled"`(노드가 남아 phandle 참조가 안 깨짐), 지울 때는 `/delete-node/`.

> The parent's `#address-cells`/`#size-cells` define how a child's `reg` is split, `ranges` translates bus addresses up to CPU physical addresses, and the provider's `#…-cells` defines every phandle specifier.

**꼬리 질문**
- "Why does PCI use 3 address cells?" → 첫 셀이 I/O·32비트 MEM·64비트 MEM을 구분하는 공간 플래그(phys.hi), 나머지 두 셀이 64비트 주소.
- "Empty `ranges` vs no `ranges`?" → 1:1 매핑 vs 번역 불가.
- "Why does the kernel run cpp on `.dts`?" → `dt-bindings` 헤더 상수를 드라이버 C 코드와 공유하려고(`-undef`가 없으면 `linux`가 매크로로 치환되는 사고).

**함정**: `interrupts`의 둘째 셀을 GIC INTID나 Linux IRQ 번호로 그대로 쓰는 것.

**출처**: → D2 §3·§5·§6·§7·§8, D4 §1·§4, F6 §3, D8 §6

### Q16 ★★★ — 자원 프로퍼티, 그리고 "DT에 있는데 probe가 안 된다"

**Q.** "How does a driver get its clocks, regulators and GPIOs from the device tree? Your sensor node is in the device tree but probe is never called — how do you debug it?"

**한국어로**: 드라이버는 DT에서 클럭·레귤레이터·GPIO를 어떻게 얻나? 센서 노드가 DT에 있는데 probe가 안 불리면 어떻게 디버그하나?

**30초 답.** 전부 같은 패턴이다. DT에는 `clocks`/`clock-names`, `vdd-supply`, `reset-gpios`, `resets`, `pinctrl-0`, `dmas`처럼 "phandle + 인자"로 provider를 가리키고, 드라이버는 **이름으로** `devm_clk_get_enabled(dev, "core")`, `devm_regulator_get_enable(dev, "vdd")`, `devm_gpiod_get(dev, "reset", GPIOD_OUT_HIGH)`을 부른다. probe가 안 불리면 사슬을 순서대로 끊어 본다: (1) `/proc/device-tree`에 노드가 있고 `status`가 okay인가, (2) `/sys/bus/<bus>/devices`에 장치가 생겼나(없으면 부모 컨트롤러가 disabled이거나 probe 실패), (3) 드라이버가 로드됐고 modalias가 맞나, (4) `/sys/kernel/debug/devices_deferred`에 걸려 있나, (5) dmesg에 probe 에러가 있나.

**2분 답.** 함정 몇 개를 같이 말한다. `vdd-supply`가 없는데 드라이버가 `vdd`를 요청하면 레귤레이터 코어가 dummy regulator를 주고 경고만 남긴다 — probe는 성공하고 나중에 I2C NACK로 나타난다(선택 전원이면 `regulator_get_optional`로 `-ENODEV` 분기). `GPIO_ACTIVE_LOW`는 보드 배선 극성을 DT에 적는 것이고 gpiolib이 반전해 주므로 드라이버는 항상 "1 = assert"로 쓴다 — 실제로 logical 1일 때 raw 0이다. pinmux는 `pinctrl-names = "default"` 상태를 driver core가 probe 직전에 `pinctrl_bind_pins()`로 자동 적용하므로 드라이버는 보통 아무것도 안 한다. 센서 INT가 active-low면 GIC SPI는 rising/level-high만 받으므로 GPIO 컨트롤러를 `interrupt-parent`로 쓰고 `IRQ_TYPE_EDGE_FALLING`을 준다. deferred의 흔한 원인은 provider 노드가 disabled이거나 provider 드라이버가 모듈인데 initramfs에 없는 경우다. 드라이버는 `dev_err_probe()`로 사유를 `devices_deferred`에 남긴다. 회로도의 net을 DT 프로퍼티로 옮기는 규칙은 P4에 있다.

> Every resource is "phandle plus specifier" resolved by name through the provider's framework; for a node that never probes I walk the chain — node and status, device object, driver and modalias, `devices_deferred`, then dmesg.

**꼬리 질문**
- "What happens if a node has no `vdd-supply` but the driver requests `vdd`?" → dummy regulator + 경고. probe 성공, 실제 전원은 없다.
- "Where does pinmux get applied?" → probe 직전 driver core가 default 상태 적용. suspend의 sleep 상태나 I2C 버스 복구 때만 드라이버가 직접 바꾼다.
- "Why do `*-supply` and `pinctrl-0` have no argument cells?" → 노드 하나가 자원 하나라서.

**함정**: 드라이버에서 극성을 한 번 더 뒤집는 이중 반전, 그리고 dmesg부터 보는 것(장치 객체가 아예 없으면 dmesg에 드라이버 로그가 없다).

**출처**: → D4 §5·§6·§7·§8·§9·§11·§12, D3 §10·§13, G3 §9, H4 §5, P4 §2·§8, R4

### Q17 ★★ — 드라이버에서 DT 읽기, 그리고 overlay

**Q.** "How does a driver read a configuration value like a sample rate from the device tree? What is a device tree overlay and where can it be applied?"

**한국어로**: 드라이버는 샘플링 주기 같은 설정값을 DT에서 어떻게 읽나? DT overlay란 무엇이고 어디서 적용하나?

**30초 답.** probe에서 `device_property_read_u32(dev, "sample-rate", &val)`을 부른다 — `fwnode` 위의 통합 API라 DT, ACPI `_DSD`, software node 모두에서 동작한다(DT 전용이면 `of_property_read_u32`). 반환값 0은 성공, `-EINVAL`은 속성 없음, `-EOVERFLOW`는 길이 불일치다. optional이면 기본값을 먼저 넣고 반환값을 무시하고(실패해도 출력 변수는 안 바뀐다), required면 `dev_err_probe()`로 probe를 실패시킨다. overlay는 base DTB(SoC + 캐리어 보드) 위에 확장 보드·카메라·공장 변형을 얹는 조각이고, 빌드 시간(`fdtoverlay`), 부팅 시간(U-Boot `fdt apply`), 런타임(커널 `of_overlay_fdt_apply()`)에 적용한다.

**2분 답.** 칩 변형은 `of_device_id`의 `.data`에 변형별 상수 구조체를 달고 `device_get_match_data(dev)`로 꺼낸다 — probe 곳곳에서 compatible 문자열을 비교하지 않는다. 노드 포인터를 돌려주는 OF 함수(`of_parse_phandle`, `of_get_child_by_name` 등)는 참조를 올려 주므로 `of_node_put()`이 필요하고, `for_each_child_of_node`에서 `break`로 나가면 현재 child를 put 해야 한다(최신 커널은 `_scoped` 매크로가 자동화). `of_property_read_bool`은 값 없는 진짜 boolean용이고 존재 여부는 `of_property_present`. 레거시 `of_get_named_gpio`는 전역 번호를 돌려주고 극성을 무시해서 deprecated이고 `devm_gpiod_get`을 쓴다. overlay는 링커처럼 동작한다: base는 `-@`로 컴파일해 `__symbols__`를 내보내고, overlay의 label 참조는 `__fixups__`로 남았다가 적용 때 채워진다. mainline에는 유저 공간 overlay 인터페이스가 없다(configfs는 RPi·BeagleBoard 다운스트림 패치). U-Boot `fdt apply`가 실패하면 base까지 망가지므로(D6에서 `FDT_ERR_BADMAGIC` 재현) 부트 스크립트에 폴백을 둔다.

> New drivers use `device_property_read_*` with an explicit default for optional properties and `device_get_match_data()` for variants; overlays patch a `-@` base DTB at build, boot, or — from a driver — at runtime.

**꼬리 질문**
- "A property exists in the DTS but your driver reads 0. Why?" → `/proc/device-tree`에서 실제 바이트를 hexdump(다른 DTB를 받았을 수 있음), `of_node` 링크, 이름 오타, 타입 불일치.
- "When do you need `of_node_put()`?" → 노드를 돌려받은 OF 함수 뒤, 순회 중 조기 탈출 때.
- "Can you load an overlay from user space on mainline?" → 없다. 드라이버가 `.dtbo`를 링크해 `of_overlay_fdt_apply()`.

**함정**: 런타임 configfs overlay가 mainline 기능이라고 말하는 것.

## 4. 커널 기초 · 모듈 (Q18–Q22)

여기서부터 "커널 코드를 써 본 사람인가"를 본다. Q20(제약)과 Q21(유저 포인터)은 펌웨어 출신에게 꼭 묻는다.

### Q18 ★★★ — Monolithic 커널과 모듈

**Q.** "Linux is described as a monolithic kernel. What does that mean, and how do loadable modules fit in? What happens when you insmod a module?"

**한국어로**: Linux는 monolithic 커널이라고 한다. 무슨 뜻이고, 모듈은 어떻게 들어맞나? insmod하면 커널 안에서 무슨 일이 일어나나?

**30초 답.** 스케줄러·메모리 관리·파일시스템·네트워크·드라이버가 전부 **한 커널 주소 공간에서 같은 권한(EL1)**으로 돌고 서로를 직접 함수 호출한다는 뜻이다. 빠르고 드라이버 생태계가 거대하지만 드라이버 버그 하나가 커널 전체를 죽인다. 모듈(`.ko`)은 런타임에 커널에 링크하는 장치일 뿐 **격리가 아니다** — 들어가면 빌트인과 같은 권한이다. `insmod`는 파일 하나를 넣고, `modprobe`는 이름이나 alias로 `/lib/modules/$(uname -r)`에서 찾아 `modules.dep`의 의존 모듈을 먼저 넣는다.

**2분 답.** insmod 내부는 `finit_module` → `load_module()`: 서명 검사, ELF 검증, vermagic 비교, core·init 영역 할당과 섹션 복사, 미해결 심볼을 커널·모듈 심볼 표에서 해석(GPL·네임스페이스 검사), 재배치, 메모리 권한 설정, 파라미터 파싱, sysfs 생성, 마지막으로 `do_init_module()`이 init을 부르고 성공하면 init 영역을 해제한다. 요컨대 **커널 안의 런타임 링커 + 로더**다. init이 음수를 돌려주면 exit은 불리지 않으므로 init 안에서 역순 정리(goto 사다리)를 해야 한다. `EXPORT_SYMBOL_GPL` 심볼은 비GPL 모듈에 안 보여 "Unknown symbol"이 되고, 서브시스템 내부 API는 `EXPORT_SYMBOL_NS_GPL` + `MODULE_IMPORT_NS("NS")`(6.13부터 문자열)로 막는다. 언로드는 refcount가 막는다 — 장치 파일을 열면 `try_module_get(fops->owner)`가 되므로 `.owner = THIS_MODULE`이 중요하다. taint O(트리 밖), P(독점 라이선스), E(서명 없음)는 버그 리포트용 이력이다. 규모 감각: 6.18 소스 약 3,600만 줄 중 69%가 `drivers/`(E1 §3). rootfs 전에 필요한 것(스토리지, 콘솔, 인터럽트 컨트롤러)은 built-in, 나머지는 모듈.

> Monolithic means one address space and one privilege level for everything; a module is linked into that space at runtime by an in-kernel loader, so it gives flexibility, not isolation.

**꼬리 질문**
- "What if a module has no exit function?" → 로드는 되지만 `[permanent]`가 되어 rmmod가 `-EBUSY`.
- "How does a microkernel differ?" → QNX·seL4는 드라이버·FS를 유저 프로세스로 돌려 장애를 격리하고 IPC 비용을 낸다.
- "What does 'tainted' mean?" → 지원 범위 밖의 일이 있었다는 비트마스크(`/proc/sys/kernel/tainted`, Oops의 `Tainted:` 줄).

**함정**: "모듈은 별도 보호 영역에서 돈다"고 말하는 것. 그리고 화이트보드 hello 모듈에서 `MODULE_LICENSE`를 빼먹는 것(R3에서 연습).

**출처**: → E1 §1·§3, E3 §1·§3·§6·§7·§8·§9·§10·§11·§12·§13, B3 §12

### Q19 ★★ — Kconfig와 Kbuild

**Q.** "How do you add a new driver to the kernel source tree so it builds as a module or built-in? What is the difference between depends on and select?"

**한국어로**: 새 드라이버를 커널 트리에 넣어 모듈이나 built-in으로 빌드되게 하려면? `depends on`과 `select`는 무엇이 다른가?

**30초 답.** 세 곳을 고친다. 드라이버 디렉터리 Kconfig에 `tristate` 항목을 만들고 필요한 버스를 `depends on`으로 건다. 같은 디렉터리 Makefile에 `obj-$(CONFIG_FOO) += foo.o`(파일이 여러 개면 `foo-y := a.o b.o`). 그리고 부모 Kconfig에 `source`, 부모 Makefile에 `obj-$(CONFIG_FOO) += foo/`. `.config`가 y면 `built-in.a`를 거쳐 vmlinux에, m이면 modpost를 거쳐 `foo.ko`가 된다. `depends on`은 내 심볼의 **상한**이고, `select`는 대상을 내 값까지 **강제로 끌어올린다** — 대상의 depends를 보지 않으므로 라이브러리 심볼(`REGMAP_I2C` 같은)에만 쓴다.

**2분 답.** select의 위험은 대상이 의존하는 서브시스템이 꺼져 있어도 켜 버리고 "unmet direct dependencies" 경고만 남기는 것이다 — 그래서 BMI270 I2C 드라이버처럼 `depends on I2C`와 `select REGMAP_I2C`를 같이 쓰는 것이 정석이고, 사용자가 끌 수 있어야 하는 추천은 `imply`다. 코드에서는 `#ifdef CONFIG_FOO` 대신 `IS_ENABLED(CONFIG_FOO)`를 쓴다: m이면 `autoconf.h`에 `CONFIG_FOO_MODULE`만 정의되어 `#ifdef`가 거짓이 되고, `if (IS_ENABLED(...))`는 꺼져 있어도 컴파일러 검사를 받는다. 제품 설정은 `make savedefconfig`로 줄인 defconfig + 기능별 fragment(`merge_config.sh`)로 관리하고, 커널을 올릴 때 `olddefconfig` 후 `diffconfig`로 리뷰한다. 트리 밖 모듈은 `obj-m := foo.o` 한 줄짜리 Makefile과 `make -C <커널 빌드 트리> M=$PWD modules`. 산출물: `vmlinux`(심볼·디버그 정보 ELF, 보드에 안 올림), `Image`(64바이트 arm64 헤더가 붙은 평평한 바이너리, `booti`가 적재), `Image.gz`(arm64는 스스로 압축을 못 풀어 부트로더가 푼다).

> Kconfig declares the option, Kbuild's `obj-$(CONFIG_FOO)` decides built-in versus module; `depends on` limits my symbol, `select` forces another one on and ignores its dependencies, so I only select library symbols.

**꼬리 질문**
- "Why `IS_ENABLED` instead of `#ifdef`?" → m일 때 `_MODULE` 접미사, 그리고 꺼진 코드도 문법·타입 검사를 받는다.
- "One Kconfig change rebuilt one file, one header touch rebuilt hundreds. Why?" → fixdep이 `include/config/<심볼>` 단위로 의존성을 바꿔 쓰지만 헤더 의존성은 파일 단위다.
- "Common cross-compile mistakes?" → `ARCH` 없이 menuconfig, 설정과 빌드의 컴파일러 불일치, `CROSS_COMPILE` 누락.

**함정**: `.config` 전체를 git에 커밋하는 것, 사용자 기능을 `select`로 강제하는 것.

**출처**: → E2 §1·§2·§3·§4·§6·§8·§9·§10·§11, B4 §7

### Q20 ★★★ — 커널 코드는 유저 코드와 무엇이 다른가

**Q.** "What are the main differences between writing kernel code and writing a user-space application? What does 'sleeping in atomic context' mean?"

**한국어로**: 커널 코드를 쓰는 것과 유저 공간 앱을 쓰는 것은 무엇이 다른가? "atomic context에서 잠든다"는 무슨 뜻인가?

**30초 답.** 일곱 가지다. libc가 없고(printk, kmalloc), FP/SIMD를 못 쓰고(arm64는 `-mgeneral-regs-only`, 꼭 필요하면 `kernel_neon_begin/end` 구간), 스택이 작고 고정이며(arm64 태스크당 16 KiB, KASAN이면 32 KiB), 잠들 수 없는 문맥이 있고, 할당이 실패할 수 있고(GFP로 "기다려도 되나"를 알림), 유저 포인터를 직접 역참조하면 안 되고(Q21), 커널 내부에는 메모리 보호가 없다. 근본 차이는 실수 하나가 프로세스가 아니라 시스템 전체를 죽인다는 것이다. atomic context는 spinlock을 쥐었거나 선점·IRQ가 꺼졌거나 인터럽트·softirq 안이라 `schedule()`을 부르면 안 되는 상태이고, 거기서 `msleep`, `mutex_lock`, `GFP_KERNEL` 할당, I2C 전송을 부르면 데드락이나 크래시가 난다.

**2분 답.** 탐지는 두 단계다. 실제로 잠들면 스케줄러가 "scheduling while atomic"을 찍지만, `GFP_KERNEL`처럼 가끔만 잠드는 경우는 `CONFIG_DEBUG_ATOMIC_SLEEP`을 켜야 `might_sleep()`이 "sleeping function called from invalid context"로 미리 잡는다 — 개발·CI 커널에 lockdep과 함께 켠다. 스택은 `CONFIG_VMAP_STACK`이면 vmalloc 영역 + guard page라 넘치는 순간 "kernel stack overflow" panic이고, 없으면 옆 메모리를 조용히 덮는다. 예방은 `-Wframe-larger-than`과 큰 배열을 스택에 두지 않는 것. kmalloc 버퍼 넘침은 fault 없이 옆 객체를 깨므로 `slab_debug`나 KASAN으로 잡는다. 예외가 없으니 모든 에러는 음수 errno나 `ERR_PTR`로 손으로 전파하고 goto 사다리나 devm으로 정리한다. 선점 커널이면 busy loop가 "soft lockup"(watchdog 스레드가 `2 × watchdog_thresh` = 기본 20초 못 돎)으로 잡힌다. 이식성은 `__le32` 같은 타입과 sparse로 강제한다. 펌웨어 경험으로 말하면 "bare-metal 규칙 + 수많은 이웃 + 선점 + SMP + 믿을 수 없는 유저"다.

> No libc, no FPU, a fixed 16 KiB stack, contexts where you must not sleep, allocations that can fail, untrusted user pointers, and no memory protection — a single bug takes down the whole system.

**꼬리 질문**
- "Can you take a mutex in an interrupt handler?" → 안 된다. hardirq는 잠들 수 없다. threaded IRQ 핸들러에서는 된다.
- "Why no floating point?" → 커널 진입 때 FP/SIMD 레지스터를 저장하지 않으므로 유저 FP 상태가 깨진다.
- "What is a soft lockup?" → 한 CPU에서 선점을 끄고 오래 도는 코드. hrtimer 기반 감시가 "BUG: soft lockup - CPU#N stuck for Xs!"를 찍는다.

**함정**: "printk/kmalloc이 있으니 유저 코드와 비슷하다" 수준에서 끝내는 답. 문맥 규칙을 반드시 말한다.

**출처**: → E4 §2·§3·§4·§5·§6·§7·§8·§9·§10·§12, F2 §9·§11, M8 §2

### Q21 ★★★ — 유저 포인터와 copy_to_user

**Q.** "Why can't a driver just dereference a pointer it got from user space? What does copy_to_user return, and how do you handle a partial copy?"

**한국어로**: 드라이버는 왜 유저에게서 받은 포인터를 그냥 역참조하면 안 되나? `copy_to_user`는 무엇을 돌려주고, 일부만 복사되면 어떻게 처리하나?

**30초 답.** 그 주소는 매핑이 없을 수도, 아직 페이지가 없을 수도, 아예 커널 주소일 수도 있고, ARMv8.1 이상은 **PAN**이 커널의 일반 load/store로 유저 메모리에 접근하는 것을 하드웨어로 막는다. `copy_from_user`/`copy_to_user`는 `access_ok`로 범위가 유저 영역인지 검사하고, 유저 권한 접근 명령(LDTR/STTR)으로 복사하며, 그 명령들이 exception table에 등록돼 있어서 fault가 나면 page fault 핸들러가 정상 처리하거나 fixup으로 점프해 **못 복사한 바이트 수**를 돌려준다. 그래서 나쁜 포인터가 Oops가 아니라 `-EFAULT`가 된다. 반환값 0이 성공이다 — 음수 에러가 아니다.

**2분 답.** `read()`에서는 `left = copy_to_user(buf, kbuf, n)`이 n이면(한 바이트도 못 줌) `-EFAULT`, 아니면 `n - left`만큼 `*ppos`를 전진시키고 그 값을 돌려준다. 고정 크기 구조체는 0이 아니면 그냥 `-EFAULT`. `copy_from_user`는 못 복사한 꼬리를 커널 버퍼에서 0으로 채워 정보 누출을 막는다. E4·E6에서 같은 모듈이 PAN 없는 Cortex-A57 에뮬레이션에서는 직접 역참조가 "돌아가 버리고", PAN 있는 `-cpu max`에서는 Oops 나는 것을 확인했다 — "내 보드에선 됐다"가 위험한 이유다. sparse의 `__user` 주석(`make C=1`)은 주소 공간을 섞으면 경고하는데, `copy_to_user` 인자 순서를 바꾸는 버그는 gcc는 조용하고 sparse만 잡는다. 관련 규약도 같이 말한다: 모르는 ioctl은 `-EINVAL`이 아니라 `-ENOTTY`, 시그널로 깨면 `-ERESTARTSYS`(512)를 돌려주고 syscall 복귀 경로가 `SA_RESTART`면 재시작, 아니면 `EINTR`로 바꾼다. `count == 0`이면 그냥 0. 그리고 `copy_to_user`는 page fault로 잠들 수 있어서 **spinlock 안에서 부르면 안 된다**.

> User pointers may be unmapped, not yet faulted in, or point into the kernel, and PAN blocks direct access; `copy_to_user` checks the range, uses unprivileged loads/stores with exception-table fixups, and returns the number of bytes it could not copy.

**꼬리 질문**
- "How do you design an ioctl struct for 32-bit user space on a 64-bit kernel?" → 고정 폭 타입만, 포인터는 `__u64` + `u64_to_user_ptr`, 암묵적 패딩 없음(pahole), `compat_ioctl = compat_ptr_ioctl`.
- "What is `-ERESTARTSYS` and when does the user see `EINTR`?" → 커널 내부 코드. 핸들러에 `SA_RESTART`가 없으면 `EINTR`.
- "Which errno for an unknown ioctl?" → `-ENOTTY`.

**함정**: "`copy_to_user`가 실패하면 `-EFAULT`를 돌려준다"고 말하는 것(그건 드라이버가 만드는 값이다). 그리고 spinlock을 쥔 채 `copy_to_user`.

**출처**: → E6 §2·§3·§4·§5·§6, E4 §7, E5 §6, G4 §6·§7, F3 §4

### Q22 ★★ — `container_of`, `list_head`, `ERR_PTR`, 에러 정리

**Q.** "What does container_of do, and how is it implemented? Why does the kernel use intrusive linked lists? How does ERR_PTR work?"

**한국어로**: `container_of`는 무엇을 하고 어떻게 구현되나? 커널은 왜 intrusive 리스트를 쓰나? `ERR_PTR`는 어떻게 동작하나?

**30초 답.** `container_of(ptr, type, member)`는 구조체에 내장된 멤버의 포인터에서 바깥 구조체의 포인터를 돌려준다 — 멤버 주소에서 `offsetof(type, member)`를 빼는 것이고, 오프셋이 컴파일 타임 상수라 런타임엔 빼기 한 번이다(커널판은 `static_assert`로 타입까지 검사). `list_head`는 링크를 객체 안에 넣는 원형 이중 리스트라, 넣을 때 할당이 없어서 `list_add`가 실패할 수 없고(spinlock 안이나 IRQ 문맥에서도 OK), 한 객체가 여러 리스트에 동시에 있을 수 있다. `ERR_PTR`는 커널 주소 공간 맨 위 4095바이트에 유효 객체가 없다는 점을 이용해 `-errno`를 포인터로 실어, 반환값 하나에 "객체 또는 실패 이유"를 담는다. `IS_ERR`는 비교 한 번이다.

**2분 답.** 순회 중 삭제는 `list_for_each_entry_safe`로 — 다음 원소를 미리 저장해 둔다. 그냥 `list_for_each_entry`로 지우면 `list_del`이 써 둔 `LIST_POISON1`(`0xdead000000000100`) 근처 주소에서 oops가 난다. 에러 정리는 세 세대가 있다: 획득 역순으로 레이블을 놓는 goto 사다리, 드라이버 core가 역순 해제해 주는 `devm_*`(devm이 없는 건 `devm_add_action_or_reset`), 6.5부터의 scope 기반 `__free(kfree)`·`guard(mutex)`. 한 함수에서 goto와 cleanup 헬퍼를 섞지 않는다. API마다 NULL을 주는지 `ERR_PTR`을 주는지 확인해야 한다 — `devm_kzalloc`은 NULL, `devm_clk_get`은 `ERR_PTR`이고, `IS_ERR`는 NULL을 잡지 않는다. 로그에 에러 이름을 찍을 때는 `%pe`. 레지스터 필드는 `GENMASK`/`FIELD_PREP`/`FIELD_GET`으로 쓴다. 화이트보드에서 직접 구현하는 연습은 R3에 있다.

> `container_of` subtracts the member's compile-time offset, intrusive lists need no allocation and let one object live on many lists, and `ERR_PTR` encodes `-errno` in the top 4095 bytes of the address space.

**꼬리 질문**
- "Why not a back-pointer instead of `container_of`?" → 객체마다 8바이트 절약, 초기화 누락 버그 없음, 한 객체가 여러 부품(device, kref, list_head, work)을 내장해도 각각에서 돌아올 수 있다.
- "How do you delete while iterating?" → `_safe` 변형. 동시 수정은 별도로 락이나 RCU.
- "Write a single-linked-list remove without special-casing the head." → 포인터의 포인터(E5 §10.1, `hlist_node.pprev`의 아이디어).

**함정**: `IS_ERR`로 NULL을 검사하는 것, 포인터 멤버(내장이 아닌)에 `container_of`를 쓰는 것.

**출처**: → E5 §1·§2·§3·§4·§5·§10, R3

### Q23 ★★★ — 실행 문맥: process vs interrupt vs atomic

**Q.** "What's the difference between process context and interrupt context? What is atomic context — is holding a spinlock in process context atomic? Why can't you sleep in an interrupt handler?"

**한국어로**: process context와 interrupt context의 차이는? atomic context란 무엇이고, process context에서 spinlock을 쥐고 있으면 atomic인가? 인터럽트 핸들러에서는 왜 잠들 수 없나?

**30초 답.** process context는 어떤 태스크를 대신해 도는 코드(syscall, kthread, workqueue, threaded IRQ 스레드)라 `current`가 의미 있고 잠들 수 있다. interrupt context(hardirq, softirq, NMI)는 비동기로 끼어든 코드라 잠들 수 없다 — 재울 태스크가 없기 때문이다: `current`는 가로채인 남의 태스크이고, 핸들러는 CPU당 하나인 IRQ 스택 위에서 IRQ가 꺼진 채 돈다. atomic context는 잠들면 안 되는 **모든** 구간이다: interrupt context 전부 + spinlock 보유, `preempt_disable`, `local_bh_disable`, `local_irq_disable`, RCU 읽기 구간. 그러니 spinlock을 쥔 process 코드는 atomic이다.

**2분 답.** 커널은 문맥을 태스크별 32비트 `preempt_count`의 칸으로 기록한다: bit 0~7 선점 금지 깊이, 8~15 softirq(실행 중이면 0x100, BH 금지면 0x200씩), 16~19 hardirq, 20~23 NMI. 경고 로그에 찍힌 `0x101`은 "softirq 실행 중 + spinlock 하나"라는 뜻이다. `in_task()`, `in_hardirq()`, `in_serving_softirq()`가 이 칸을 읽는다. softirq는 보통 hardirq가 끝나는 `irq_exit` 길목에서 가로챈 태스크 위에서 돌고, 한 번에 2 ms·10회를 넘기면 CPU별 `ksoftirqd/N`이 이어받는다 — 어디서 돌든 softirq 문맥이라 잠들 수 없다. hrtimer 콜백은 non-RT에서 기본 hardirq, `_SOFT` 모드면 softirq이고, PREEMPT_RT에서는 `_HARD`를 명시하지 않으면 softirq로 옮겨진다. 잠복 버그(메모리가 넉넉할 때만 안 잠드는 `GFP_KERNEL` 같은)는 `CONFIG_DEBUG_ATOMIC_SLEEP` + lockdep을 켠 개발 커널에서 `might_sleep()`이 잡는다. F2에서 같은 함수를 모든 문맥에서 불러 보고 실측 표를 만들었다.

> Interrupt context borrows whatever task it interrupted, so there is nothing to put to sleep; atomic context is anything that must not call `schedule()` — interrupts plus spinlocks, preempt/BH/IRQ-disabled regions and RCU read sections.

**꼬리 질문**
- "Where do softirqs run? What is ksoftirqd?" → `irq_exit` 직후, 또는 예산 초과·process 문맥에서 raise됐을 때 `ksoftirqd/N`.
- "Does `in_atomic()` catch every atomic region?" → 아니다. IRQ만 끈 구간과 PREEMPT_RCU의 RCU 구간을 못 본다.
- "Which context is an hrtimer callback?" → 기본 hardirq, `HRTIMER_MODE_*_SOFT`면 softirq.

**함정**: "ksoftirqd는 스레드니까 softirq 핸들러가 잠들 수 있다"는 답.

**출처**: → F2 §2·§3·§5·§6·§7·§9·§11, F7 §3·§5, E4 §5

### Q24 ★★★ — spinlock vs mutex, 그리고 `_irqsave`

**Q.** "What's the difference between a spinlock and a mutex? When do you need spin_lock_irqsave instead of spin_lock?"

**한국어로**: spinlock과 mutex는 무엇이 다른가? `spin_lock` 대신 `spin_lock_irqsave`가 필요한 때는?

**30초 답.** spinlock은 못 잡으면 그 자리에서 돌며 기다리고, 쥔 동안 선점이 꺼져서 **잠들 수 없다**. 그래서 IRQ 핸들러를 포함한 어떤 문맥에서도 쓸 수 있지만 구간이 아주 짧아야 한다. mutex는 못 잡으면 잠들고, owner가 있어 잡은 태스크만 풀 수 있고, process context에서만 쓴다 — 쥔 채로 I2C 전송, `GFP_KERNEL` 할당, `copy_to_user` 같은 잠드는 일을 해야 하면 mutex다. 같은 데이터를 hardirq 핸들러도 만지면 process 쪽은 `spin_lock_irqsave`를 쓴다 — 안 그러면 락을 쥔 CPU에 그 IRQ가 들어와 핸들러가 같은 락을 기다리며 영원히 돈다(락을 풀 코드가 핸들러 밑에 깔려 있다). softirq·tasklet·timer와 공유하면 `_bh`.

**2분 답.** 핸들러 쪽은 이미 IRQ가 꺼져 있으니 그냥 `spin_lock`이다. `_irq`는 호출자가 IRQ가 켜진 상태임을 확신할 때만, 모르면 `_irqsave`. 요즘 mutex는 owner가 다른 CPU에서 실행 중이면 잠깐 돌다가(optimistic spinning) 잠들어서 짧은 구간에서도 생각보다 싸다. 유저 공간 pthread mutex는 futex라 경합이 없으면 syscall이 없다. 실무 패턴: IRQ(또는 hrtimer)가 채우고 `read()`가 비우는 링버퍼는 spinlock으로 보호하되, `copy_to_user`는 잠들 수 있으니 락 안에서 커널 임시 버퍼로 복사하고 락을 푼 뒤 유저로 복사한다(G4 §7, lockdep·DEBUG_ATOMIC_SLEEP 커널에서 경고 0 확인). 데드락은 전역 락 순서로 예방하고, lockdep이 락 클래스 그래프로 사이클·IRQ 안전성 위반·잘못된 wait context를 **실제 데드락 없이** 보고한다. PREEMPT_RT에서는 `spinlock_t`가 rt_mutex 기반의 잠드는 락(PI 포함)으로 바뀌고 `spin_lock_irqsave`는 IRQ를 끄지 않는다 — 6.18.55 `spinlock_rt.h`에서 `flags = 0; spin_lock(lock);`으로 정의된 것을 §11에서 확인했다. 진짜로 돌아야 하는 곳만 `raw_spinlock_t`다.

> A spinlock busy-waits with preemption off and works in any context but must be short; a mutex sleeps and is process-context only; if an interrupt handler shares the data, the process side uses `spin_lock_irqsave` or it can deadlock against its own CPU.

**꼬리 질문**
- "Can you take a mutex in an interrupt handler?" → 안 된다. threaded IRQ의 스레드 함수에서는 된다.
- "What does a spinlock do on a uniprocessor kernel?" → 실제 스핀 없이 선점(과 `_irq`면 IRQ) 금지만 남는다.
- "What changes with PREEMPT_RT?" → `spinlock_t`/`rwlock_t`가 sleeping PI lock, IRQ 핸들러 스레드화, `raw_spinlock_t`만 진짜 스핀.

**함정**: spinlock 안에서 `kmalloc(GFP_KERNEL)`이나 `copy_to_user`를 부르는 코드를 그대로 쓰는 것.

**출처**: → F4 §3·§4·§5·§13·§14, A8 §2·§6·§8, G4 §7, N1 §5

### Q25 ★★ — 락 말고: atomic, refcount, per-CPU, RCU, seqlock

**Q.** "What is RCU and when would you use it? What's the difference between atomic_t and refcount_t? What are per-CPU variables for?"

**한국어로**: RCU는 무엇이고 언제 쓰나? `atomic_t`와 `refcount_t`는 무엇이 다른가? per-CPU 변수는 무엇에 쓰나?

**30초 답.** RCU(Read-Copy-Update)에서 reader는 `rcu_read_lock()`/`rcu_dereference()`만 하고 락도 원자 명령도 없이 읽는다. writer는 새 사본을 만들어 `rcu_assign_pointer()`로 포인터를 바꿔 공개하고, 옛 객체는 그 전부터 읽던 reader가 모두 끝날 때까지(grace period) 기다렸다가 해제한다(`synchronize_rcu` 또는 `call_rcu`/`kfree_rcu`). 읽기가 압도적이고 잠깐 옛 값을 봐도 되는 데이터(설정 테이블, 장치 목록)에 쓴다. `refcount_t`는 객체 수명 전용이라 overflow·underflow·0에서 증가를 감지해 경고하고 포화시켜 use-after-free 대신 누수로 끝나게 한다(일반 `atomic_t`는 조용히 감싼다). per-CPU 변수는 CPU마다 사본을 둬서 공유 자체를 없앤다 — 캐시 라인이 오가지 않고 락이 필요 없어 통계 카운터에 맞다.

**2분 답.** RCU writer끼리는 여전히 락이 필요하고, 일반 RCU 읽기 구간에서는 잠들 수 없다(필요하면 SRCU). seqlock은 시퀀스 카운터 + writer용 spinlock으로, reader는 락 없이 읽고 카운터가 바뀌었으면 다시 읽는다 — writer가 절대 reader를 기다리지 않는 작은 값(`jiffies_64`, timekeeping)에 쓰고, 포인터를 따라가는 데이터에는 안 맞는다(그건 RCU). per-CPU는 남는 위험이 같은 CPU의 선점·IRQ뿐이라 `this_cpu_inc()` 같은 단일 연산이나 `get_cpu()`/`put_cpu()`로 막고, 읽을 때 모든 CPU를 합산한다. F4는 카운터 하나를 CPU 넷이 올리는 같은 문제를 다섯 가지 정답(spinlock, mutex, atomic, per-CPU, RCU류)으로 풀어 비용을 쟀고, 결정 표(§14)로 정리했다. 수명 관리는 `kref`(`refcount_t` 위) + `release()` 패턴이 드라이버 모델 전체(Q32)의 기반이다.

> RCU makes readers free — no locks, no atomics — by deferring frees until a grace period; writers still serialize among themselves, and readers must not sleep in classic RCU.

**꼬리 질문**
- "Can you sleep inside an RCU read-side critical section?" → 일반 RCU는 안 된다. SRCU를 쓴다.
- "Where is seqlock used?" → `jiffies_64`, timekeeping.
- "Why per-CPU for statistics?" → 캐시 라인 핑퐁 제거, 정확한 순간값이 필요 없으니까.

**함정**: "RCU는 lock-free라 writer도 락이 필요 없다"는 답, 그리고 참조 카운트에 맨 `atomic_t`를 쓰는 것.

**출처**: → F4 §8·§9·§10·§11·§12·§14, G2 §5

### Q26 ★★ — 메모리 배리어와 MMIO 순서

**Q.** "What's the difference between a compiler barrier and a memory barrier? Is volatile enough? Walk me through posting a DMA descriptor and ringing the doorbell — which barriers and why?"

**한국어로**: 컴파일러 배리어와 메모리 배리어는 무엇이 다른가? `volatile`이면 충분한가? DMA 디스크립터를 쓰고 doorbell을 울리는 순서에서 어떤 배리어가 왜 필요한가?

**30초 답.** 재배치하는 주체가 둘이다. 컴파일러는 load/store를 옮기고 합치고 지우는데, `barrier()`(명령 0개)나 `READ_ONCE`/`WRITE_ONCE`가 그걸 막는다. CPU는 store buffer와 out-of-order로 다른 코어·장치가 보는 순서를 바꾸는데, arm64는 weakly ordered라 `dmb`/`dsb` 같은 진짜 명령이 필요하다. `volatile`은 CPU 순서를 못 막는다. DMA 디스크립터는 주소·길이를 쓰고 → `dma_wmb()` → OWN 비트를 장치로 넘기고 → `writel()`로 doorbell. `dma_wmb()`가 없으면 장치가 OWN은 새 값, 주소는 옛 값으로 볼 수 있다.

**2분 답.** arm64에서 `smp_wmb()`는 `dmb ishst`(CPU끼리), `dma_wmb()`는 `dmb oshst`(CPU와 DMA 장치가 공유하는 coherent 메모리), `wmb()`는 `dsb st`(MMIO 포함 모든 store, 완료까지 파이프라인을 세움)이고, F5에서 재 보니 `dsb`가 `dmb`보다 7~8배 비쌌다(TCG). `writel()`은 store 앞에 `dmb oshst`가 있어 앞선 메모리 쓰기가 장치에 먼저 보이고, `readl()`은 load 뒤에 `dmb oshld`가 있다. `_relaxed` 버전은 같은 장치 MMIO끼리의 순서만 보장하므로 FIFO 연속 읽기 같은 hot path에만 쓴다. 완료 경로는 반대로 status를 읽고 `dma_rmb()` 후 데이터를 읽는다. posted write 함정: `writel()` 직후 `udelay()`는 장치 도착과 무관하다 — 같은 장치 레지스터를 `readl()`로 read-back해야 앞선 쓰기가 도착했음을 보장한다(`wmb()`로는 안 됨, CPU 쪽 완료만 기다리니까). 검증은 LKMM litmus(herd7), 실제 하드웨어 stress, KCSAN으로 하고, QEMU는 믿지 않는다 — MTTCG에서는 하드웨어가 금지하는 재배치도 보였다. SSD 펌웨어의 "데이터 → DMB → owner → doorbell"과 같은 것이고 Linux는 범위별로 배리어 이름이 다를 뿐이다.

> Compilers and CPUs both reorder; `volatile` only tames the compiler. For a descriptor ring it's fields, `dma_wmb()`, ownership bit, then a non-relaxed `writel()` to the doorbell.

**꼬리 질문**
- "When is `readl_relaxed()` safe?" → 일반 메모리(DMA 버퍼)와 순서가 필요 없는 MMIO끼리. DMA 시작·완료 확인에는 non-relaxed.
- "What is a posted write and how do you make sure it reached the device?" → 완료 응답 없는 쓰기. 같은 장치 `readl()` read-back.
- "Why do drivers tested only on x86 break on arm64?" → x86은 TSO라 `smp_wmb()`·`dma_wmb()`가 컴파일러 배리어뿐이다.

**함정**: "`wmb()`를 넣었으니 장치에 도착했다"는 답, `volatile` 포인터로 MMIO를 만지는 것.

### Q27 ★★★ — 인터럽트 처리: GIC부터 threaded IRQ까지

**Q.** "Walk me through what happens on an arm64 Linux system when a peripheral raises an interrupt. Explain top half and bottom half — when do you use a threaded IRQ?"

**한국어로**: arm64 Linux에서 주변장치가 인터럽트를 올리면 무슨 일이 일어나나? top half와 bottom half를 설명하고, threaded IRQ는 언제 쓰나?

**30초 답.** 장치가 선을 올리면 GIC Distributor가 pending으로 잡고 대상 CPU interface가 IRQ를 건다. CPU는 IRQ 벡터로 들어가 레지스터를 저장하고 IRQ 스택으로 바꿔 `gic_handle_irq`를 부른다. GIC 드라이버는 IAR을 읽어 hwirq를 얻고, irq_domain에서 Linux IRQ 번호의 `irq_desc`를 찾아 flow handler(`handle_fasteoi_irq`)가 등록된 handler를 부르고 EOI를 쓴다. top half는 hardirq 문맥(IRQ off, 짧게, 잠들 수 없음)이고, 나머지는 bottom half로 미룬다. 처리에 잠드는 일이 필요하면(I2C/SPI 센서 읽기) `request_threaded_irq`: hard handler는 타임스탬프만 찍고 `IRQ_WAKE_THREAD`를 돌려주고, thread_fn이 `irq/N-name` 커널 스레드(SCHED_FIFO 50)에서 버스를 읽는다.

**2분 답.** 번호가 셋이다: DT의 SPI 80, GIC hwirq 112, Linux virq(F6에서는 22). virq는 동적이라 드라이버는 `platform_get_irq()`로 받는다. primary handler를 NULL로 주면 `IRQF_ONESHOT`이 필수다 — 기본 핸들러는 스레드만 깨우고 장치를 ack하지 못하므로 level 인터럽트면 EOI 직후 다시 들어와 폭풍이 된다. 6.18.55 `manage.c`가 "Threaded irq requested with handler=NULL and !ONESHOT"을 찍고 `-EINVAL`로 거부하는 것을 §11에서 확인했다(MSI처럼 `IRQCHIP_ONESHOT_SAFE`인 칩은 예외). 핸들러가 계속 `IRQ_NONE`이면 `note_interrupt`가 10만 번 중 99,900번 넘게 미처리일 때 "irq N: nobody cared"를 찍고 라인을 끈다 — 보통 level IRQ를 ack하지 않았거나 트리거 타입이 틀린 경우다. 공유 라인(`IRQF_SHARED`)에서는 각 핸들러가 자기 장치인지 확인하고 아니면 `IRQ_NONE`. `disable_irq()`를 자기 핸들러·스레드 안에서 부르면 자기를 기다리는 데드락이라 `disable_irq_nosync()`를 쓴다. affinity는 `/proc/irq/N/smp_affinity`로, 디버그는 `/proc/interrupts`, ftrace `irq_handler_entry/exit` + `sched_wakeup`, irqsoff tracer.

> The GIC driver reads the IAR, maps hwirq to a Linux virq through the irq_domain, and the flow handler runs my handler; if I need to sleep, the hard half timestamps and returns `IRQ_WAKE_THREAD` and the FIFO-50 IRQ thread does the bus I/O.

**꼬리 질문**
- "Linux IRQ number vs hardware IRQ number?" → hwirq는 컨트롤러 안 번호, virq는 커널 전역 번호. irq_domain이 매핑한다.
- "Downsides of threaded IRQs?" → 스케줄링 지연(다른 RT 태스크에 밀림), 컨텍스트 스위치, ONESHOT이면 그동안 라인 마스크.
- "What does `IRQ_NONE` repeated lead to?" → spurious 감지 → "nobody cared" → 라인 disable.

**함정**: hardirq 핸들러에서 `i2c_transfer`나 `msleep`을 부르는 것, DT 숫자로 `request_irq`하는 것.

**출처**: → F6 §1·§3·§4·§5·§8·§9·§10, H6 §1·§2·§3, F2 §7

### Q28 ★★★ — 지연 작업 고르기: softirq, tasklet, workqueue, threaded IRQ

**Q.** "What's the difference between softirq, tasklet and workqueue? Tasklets are deprecated — what replaces them? Why can't you read an I2C sensor in the ISR, and where do you do it instead?"

**한국어로**: softirq, tasklet, workqueue는 무엇이 다른가? tasklet은 deprecated인데 대체는? I2C 센서를 ISR에서 못 읽는 이유와, 대신 어디서 읽나?

**30초 답.** softirq는 컴파일 시점에 고정된 10개의 bottom half로, hardirq 탈출 직후 같은 CPU에서 IRQ를 켠 채 돌고, 잠들 수 없고, 같은 종류가 여러 CPU에서 동시에 돈다(네트워크 RX, 타이머, 블록 완료). tasklet은 softirq 위에서 동적으로 만드는 bottom half이고 같은 tasklet은 동시에 두 CPU에서 돌지 않는다. workqueue는 kworker 스레드에서 도는 process context라 잠들 수 있다. I2C 전송은 잠들기 때문에(버스 락, 완료 대기) ISR에서는 못 하고, top half에서 타임스탬프만 찍은 뒤 threaded IRQ의 스레드 함수에서 읽는다(`IRQF_ONESHOT`으로 그동안 라인 마스크).

**2분 답.** tasklet 대체는 잠들어야 하면 threaded IRQ, softirq 수준의 지연이 정말 필요하면 6.9에 들어온 BH workqueue(`system_bh_wq`, `WQ_BH`)다 — workqueue API(`queue_work`, `cancel_work_sync`, `disable_work`)를 그대로 쓴다. workqueue가 아니라 threaded IRQ인 이유는 지연 꼬리다: 공유 nice 0 kworker라 F7에서 부하를 걸었을 때 p90이 10 ms를 넘었고, threaded IRQ는 IRQ 전용 RT 스레드다. CMWQ는 CPU별·속성별 worker pool을 공유하고, `WQ_UNBOUND`(CPU 비고정), `WQ_HIGHPRI`(nice −20 pool), `WQ_MEM_RECLAIM`(메모리 부족에도 진행 보장하는 rescuer) 플래그가 있다. RT 우선순위·CPU 고정·영구 루프가 필요하면 `kthread_worker` + `sched_set_fifo`(SPI 코어 메시지 펌프가 그렇게 한다). teardown이 실무 함정이다: rmmod 몇 초 뒤 크래시는 예약된 work·timer가 모듈보다 오래 산 것이라 remove에서 IRQ를 먼저 끄고 `cancel_delayed_work_sync`로 취소·대기한다. `flush_work`는 기다릴 뿐 취소하지 않는다.

> softirqs and tasklets run in atomic context right after the hardirq; workqueues and threaded IRQs run in task context and can sleep — for a bus-attached sensor I timestamp in the hard half and read in the IRQ thread.

**꼬리 질문**
- "Why not a workqueue for the sensor?" → 공유 kworker라 부하 시 지연이 튄다(p90 > 10 ms 실측).
- "Your driver crashes a few seconds after rmmod. What do you look for?" → 남은 work·timer·tasklet. remove에서 `cancel_delayed_work_sync()` 등으로 취소·대기.
- "flush_work vs cancel_work_sync?" → flush는 끝나길 기다림, cancel_sync는 pending 취소 + 실행 중 대기 + 재큐잉 방지.

**함정**: "workqueue면 실시간으로 충분하다"는 답, softirq에서 잠들 수 있다는 답.

**출처**: → F7 §1·§3·§4·§6·§7·§8·§9·§11·§12, F6 §5

### Q29 ★★ — 잠과 깨움: wait queue, completion, lost wakeup

**Q.** "Implement a blocking read in a character driver — walk me through it. What is the lost-wakeup problem? When would you use a completion instead of a wait queue?"

**한국어로**: char 드라이버의 blocking read를 구현한다면? lost-wakeup 문제란? wait queue 대신 completion은 언제 쓰나?

**30초 답.** 장치 구조체에 링버퍼, 그걸 지키는 락, `wait_queue_head_t`를 둔다. `read`는 버퍼가 비었으면 `O_NONBLOCK`이면 `-EAGAIN`, 아니면 `wait_event_interruptible(dev->rq, !kfifo_is_empty(...))`로 잔다 — 0이 아니면(시그널) `-ERESTARTSYS`를 그대로 돌려준다. 깨어나면 다른 리더가 먼저 가져갔을 수 있으니 락 아래서 다시 확인하고 `copy_to_user`한다. 생산자(IRQ, write)는 버퍼에 넣고 `wake_up(&dev->rq)`. completion은 "이 한 번의 일이 끝났다"(DMA 완료, 펌웨어 응답)를 알릴 때 쓴다 — 내부 `done` 카운트가 있어 `complete()`가 대기보다 먼저 와도 사라지지 않는다.

**2분 답.** lost wakeup은 조건을 검사하고 잠들기 사이에 깨우기가 오면, 그 순간 대기열에 아무도 없어서 깨우기가 사라지고 태스크는 조건이 이미 참인데 잠드는 것이다. `wait_event`는 먼저 대기열에 등록하고 `set_current_state(TASK_INTERRUPTIBLE)`(배리어 포함)로 상태를 바꾼 뒤 조건을 검사해서 이 창을 없앤다. F3에서 `mdelay`로 창을 벌려 재현했을 때 버그 버전은 데이터가 50 ms에 왔는데도 2초 타임아웃까지 잤다. 상태 셋: `TASK_INTERRUPTIBLE`(S, 아무 시그널이나 깨움), `TASK_UNINTERRUPTIBLE`(D, loadavg에 잡히고 hung task 감지 대상 — 짧고 반드시 끝나는 대기만), `TASK_KILLABLE`(D로 보이지만 SIGKILL은 받음). 여러 리더가 한 이벤트에 전부 깨는 thundering herd는 `wait_event_interruptible_exclusive`로 줄인다(리더 8개 실측: 조건 평가 15번 → 1번). completion 함정: 하드웨어 시작 전에 `reinit_completion`, 타임아웃이면 하드웨어를 멈추고 IRQ를 동기화한다 — 안 그러면 늦게 온 IRQ가 다음 요청을 완료로 속인다(F3에서 다음 전송이 78 µs 만에 "완료"). `wake_up()`/`complete()`는 IRQ에서 불러도 되고, `wait_event*`/`wait_for_completion*`은 안 된다.

> Register on the wait queue and set the task state before testing the condition — that's what `wait_event` does to avoid lost wakeups; a completion carries a count, so a `complete()` that arrives first isn't lost.

**꼬리 질문**
- "Why not loop with `msleep(1)`?" → 지연이 최소 1 jiffy(HZ=250이면 4 ms) 이상, 계속 깨어나 전력 낭비, poll과 연결 불가.
- "A process is stuck in D state. How do you debug it?" → `/proc/<pid>/stack`, `wchan`, `echo w > /proc/sysrq-trigger`.
- "Can you call `wake_up()` from an interrupt handler?" → 된다. 내부는 `irqsave` spinlock뿐.

**함정**: 깨어난 뒤 조건을 다시 확인하지 않는 것, completion을 재사용하면서 `reinit_completion`을 빼먹는 것.

### Q30 ★★ — 타이머와 지연: jiffies, timer_list, hrtimer, msleep

**Q.** "What is the difference between jiffies-based timers and hrtimers? Why does msleep(1) sleep much longer than 1 ms, and what should you use instead?"

**한국어로**: jiffies 기반 타이머와 hrtimer는 무엇이 다른가? `msleep(1)`은 왜 1 ms보다 훨씬 오래 자고, 대신 무엇을 써야 하나?

**30초 답.** `timer_list`는 jiffies(tick) 단위로 timer wheel에 들어가서 넣고 빼기가 O(1)로 싸지만, HZ=250이면 4 ms 단위로 반올림되고 절대 일찍 울리지 않게 올림까지 한다 — 대부분 취소되는 타임아웃(응답 대기, 워치독)용이고 콜백은 softirq에서 돈다. hrtimer는 ns 단위 만료를 rbtree에 넣고 클럭 이벤트 하드웨어에 바로 프로그램해서 정확하다 — 주기 샘플링, 짧은 sleep용이고 콜백은 기본 hardirq다. `msleep`은 jiffies 기반이라 1 ms가 HZ=250에서 4~8 ms가 된다(F8에서 평균 6.4 ms). 짧은 지연은 hrtimer 기반 `usleep_range(min, max)`, 잠들 수 없으면 `udelay`(수 µs까지만), 모르겠으면 `fsleep()`이 크기에 따라 골라 준다.

**2분 답.** 정밀 주기 작업(예: 1 kHz 샘플링)은 hrtimer를 `HRTIMER_MODE_ABS_HARD`로 걸고 콜백에서 `hrtimer_forward_now(timer, period)`로 "이전 만료 + 주기"를 잡은 뒤 `HRTIMER_RESTART` — 콜백이 늦어도 드리프트가 쌓이지 않고 반환값으로 놓친 주기를 센다. "now + 주기"로 재무장하면 누적된다(F8에서 부하 시 44% 느려짐). 콜백은 atomic이라 SPI/I2C는 스레드에서. jiffies wraparound는 `time_after()`로 비교한다 — 커널은 `INITIAL_JIFFIES`를 일부러 부팅 5분 뒤 wrap되게 시작한다. 하드웨어 쪽은 clocksource(읽기만 하는 free-running 카운터, arm64 `CNTVCT_EL0`, `ktime_get()`의 원천)와 clockevent(CPU별 비교기 `CNTV_CVAL_EL0`, hrtimer와 tick이 프로그램)로 나뉜다 — MCU의 free-running 카운터와 compare-match 인터럽트다. 센서 타임스탬프는 `CLOCK_MONOTONIC`(`ktime_get()`)을 hardirq 맨 앞에서 찍는다 — REALTIME은 NTP·GNSS로 점프한다(IIO·evdev 기본이 REALTIME이라 바꿔야 한다). NO_HZ_IDLE은 idle CPU의 tick을 멈추고(QEMU idle 2초에 tick 500번 → 30여 번), 제어 루프 코어는 `nohz_full`로 tick 간섭을 없앤다.

> `timer_list` is cheap and jiffy-granular for timeouts; hrtimers are nanosecond-precise for periodic work; `msleep(1)` rounds up to jiffies, so short delays use `usleep_range()` or `fsleep()`.

**꼬리 질문**
- "Can you call `mdelay()` or `msleep()` in an interrupt handler?" → `msleep`은 절대 안 됨. `mdelay`는 기술적으로 되지만 ms 단위 busy-wait은 그 CPU를 막는 지연 스파이크.
- "Which clock for sensor timestamps?" → `CLOCK_MONOTONIC`, suspend하는 장비면 BOOTTIME 고려.
- "Clocksource vs clockevent?" → 지금 시각 읽기 vs 이 시각에 인터럽트.

**함정**: `jiffies > timeout`으로 비교하는 것, `msleep(1)`을 "1 ms 쉬기"로 설명하는 것.

**30초 답.** `kmalloc`은 slab(작은 크기)이나 buddy에서 **물리적으로 연속**인 메모리를 linear map 주소로 준다 — 빠르고(수백 ns), `GFP_ATOMIC`이면 atomic 문맥에서도 쓸 수 있지만 크기 상한(4 KiB 페이지에서 `KMALLOC_MAX_SIZE` = 4 MiB)이 있고 큰 크기는 단편화로 실패한다. `vmalloc`은 페이지를 낱장으로 모아 vmalloc 영역에 이어 붙이므로 **가상으로만 연속**이다 — 큰 크기도 잘 되지만 느리고(page table 작업 + TLB), 잠들 수 있고, DMA에 그대로 못 쓴다. IRQ 핸들러에서는 `GFP_ATOMIC`: `GFP_KERNEL`은 direct reclaim 중 I/O를 기다리며 잠들 수 있기 때문이다. 스택이나 vmalloc 버퍼로는 DMA하지 않는다 — arm64는 `VMAP_STACK`이라 스택도 vmalloc 영역이고, 둘 다 물리 연속이 아니다.

**2분 답.** `GFP_ATOMIC`은 잠들지 않는 대신 min 워터마크 아래 예비분 일부를 쓸 수 있지만 **회수를 못 하므로** 실패하기 쉽다 — F9에서 버퍼 캐시가 300 MiB 있어도 `GFP_ATOMIC`은 free 90 MiB까지만 받고 실패했고, `GFP_KERNEL`은 캐시를 회수해 351 MiB를 받았다. 그래서 진짜 정답은 "IRQ에서 할당하지 않도록 미리 잡거나 mempool·workqueue를 쓴다"이다. buddy는 2^order 블록(order 0~10)을 쪼개고 합치며, 빈 메모리는 많은데 큰 연속 블록이 없는 외부 단편화가 생긴다. 고빈도 고정 크기 객체는 전용 `kmem_cache`(크기 반올림 낭비 없음, `/proc/slabinfo`에 이름으로 보임). 블록·FS 경로는 `GFP_NOIO`/`GFP_NOFS`(요즘은 `memalloc_noio_save()` 구간 표시). 카메라·디스플레이처럼 IOMMU 없이 수 MiB 연속 DMA 버퍼가 필요하면 CMA — 부팅 때 영역을 잡고 평소엔 movable 페이지만 빌려 주며, 할당 때 migration하므로 느릴 수 있어(F10에서 64 MiB가 빈 CMA 58 ms, 차 있으면 276 ms) 스트리밍 전 설정 단계(`REQBUFS`)에서 할당하고 재사용한다. `kvmalloc`은 kmalloc을 먼저 시도하고 안 되면 vmalloc. 디버그는 `slab_debug`, KASAN, kmemleak, `page_owner`.

> kmalloc gives physically contiguous, linearly mapped memory and can be atomic with `GFP_ATOMIC`; vmalloc gives virtually contiguous memory, may sleep and isn't DMA-able as is — and in an interrupt handler the best allocation is the one you made earlier.

**꼬리 질문**
- "What if you call `virt_to_phys` on a vmalloc address?" → linear map 주소가 아니라 틀린 값. `vmalloc_to_page`로 페이지마다.
- "kmalloc failed but `/proc/meminfo` shows plenty of free memory. Why?" → 크기 상한, 단편화(해당 order 이상 블록 없음), free가 CMA 블록뿐, 또는 ATOMIC이라 회수 못 함.
- "Why do camera drivers need CMA?" → 수 MiB 물리 연속 버퍼, buddy 상한 4 MiB, 오래 돈 시스템의 단편화.

**함정**: IRQ 핸들러에서 `GFP_KERNEL`, vmalloc 버퍼를 `dma_map_single`에 넘기는 것.

### Q32 ★★★ — Linux device model과 probe 시점

**Q.** "Explain the Linux device model: what are bus, device, driver and class? When exactly is a driver's probe() called?"

**한국어로**: Linux device model을 설명하라 — bus, device, driver, class는 무엇인가? 드라이버의 `probe()`는 정확히 언제 불리나?

**30초 답.** 버스(`bus_type`)는 장치 목록과 드라이버 목록을 갖고 둘을 짝짓는 `match`·`probe` 규칙을 정한다. 장치(`struct device`)는 하드웨어 인스턴스 하나로 부모·버스·현재 드라이버를 가리키고, 드라이버(`struct device_driver`)는 다룰 수 있는 장치를 밝힌다. 클래스는 버스와 무관하게 "rtc", "input" 같은 기능으로 장치를 묶어 유저 인터페이스를 준다. 모두 kobject 위에 만들어져 객체 하나가 sysfs 디렉터리 하나다(진짜 디렉터리는 `/sys/devices`, `/sys/bus`·`/sys/class`는 링크). `probe()`는 장치와 드라이버 중 **나중에 등록되는 쪽에서** 불린다: `driver_register()` → `driver_attach()`가 모든 장치에, 또는 `device_add()` → `__device_attach()`가 모든 드라이버에 대해 `bus->match`를 부르고, 맞으면 `really_probe()` → `bus->probe` → 드라이버 probe.

**2분 답.** `really_probe()`는 드라이버 probe 전에 공급자 링크(fw_devlink)를 확인하고, pinctrl default 상태를 적용하고, sysfs 링크를 만든다. 기본은 insmod나 부팅 스레드 문맥에서 동기 실행이고, sysfs `bind`, deferred probe 재시도, `drivers_probe`도 같은 길로 들어온다(G2에서 직접 만든 버스의 ftrace 스택으로 두 경로를 확인). `struct device`의 수명은 등록한 코드가 아니라 내장 kref가 정하므로 메모리 해제는 마지막 `put_device()` 때 불리는 `release()`에서만 한다 — release가 없으면 "does not have a release() function" WARN과 누수, `device_unregister()` 직후 `kfree`하면 use-after-free다(slab poison `0x6b6b6b6b`를 읽는 것을 재현). device link는 consumer–supplier 의존을 driver core에 알리는 것이고, fw_devlink가 DT의 `*-supply`, `clocks`, `gpios`, `interrupts` phandle로 자동으로 만든다 — supplier가 bind되기 전에는 consumer probe를 미리 막는다. platform 버스는 여러 `bus_type` 중 하나이고 `platform_device`/`platform_driver`는 `struct device`/`device_driver`를 임베드한 래퍼다. 전원 관리는 runtime PM(usage count가 0이 되면 `runtime_suspend`)과 system sleep 콜백이 이 모델 위에 얹힌다.

> A bus matches devices to drivers; whichever registers last triggers `match`, and `really_probe()` sets up supplier links and pinctrl before calling my probe — and a `struct device` is freed only from its `release()` when the last reference drops.

**꼬리 질문**
- "What are kobject, kset and ktype?" → kobject = 이름·부모·kref·sysfs 디렉터리, ktype = release와 sysfs ops vtable, kset = kobject 묶음(uevent 필터링).
- "What are device links and fw_devlink?" → consumer–supplier 의존. fw_devlink가 DT phandle로 자동 생성.
- "`pm_runtime_get_sync` vs `pm_runtime_resume_and_get`?" → get_sync는 실패해도 usage를 올려 누수 위험. resume_and_get은 성공 시에만(N6 §7에서 usage 5까지 새는 것을 재현).

**함정**: 장치 구조체를 unregister 직후 직접 `kfree`하는 것.

### Q33 ★★★ — devm과 `-EPROBE_DEFER`

**Q.** "What is devm, and how does it work internally? When is it dangerous? What is -EPROBE_DEFER and how do you debug a device stuck in deferred probe?"

**한국어로**: devm은 무엇이고 내부적으로 어떻게 동작하나? 언제 위험한가? `-EPROBE_DEFER`는 무엇이고, deferred에 걸린 장치는 어떻게 디버그하나?

**30초 답.** devm은 device-managed 자원이다. devm 함수는 자원을 얻으면서 "해제 함수 + 데이터"를 노드로 만들어 `struct device`의 devres 리스트 꼬리에 붙이고, probe가 실패하거나 unbind되면 driver core가 `devres_release_all()`로 리스트를 꼬리부터(LIFO) 해제한다. 그래서 획득의 역순 해제가 자동으로 보장되고 probe에 에러 사다리가 필요 없다. `-EPROBE_DEFER`(517)는 공급자(클럭, 레귤레이터, GPIO, IRQ 컨트롤러, PHY)가 아직 준비되지 않았으니 나중에 다시 불러 달라는 반환값이다. driver core가 장치를 deferred 목록에 두고 다른 드라이버가 bind될 때마다 재시도한다. 디버그는 `/sys/kernel/debug/devices_deferred`(사유 문자열)가 첫 단계이고, 드라이버는 `dev_err_probe()`로 사유를 남긴다.

**2분 답.** devm의 위험은 **해제 시점이 `remove()` 이후**라는 것이다. remove에서 손으로 푼 데이터를 아직 살아 있는 devm IRQ 핸들러가 그 틈에 읽으면 use-after-free다 — G3에서 QEMU로 핸들러가 SLUB poison `0x6b6b6b6b`를 읽는 것을 재현했다. 규칙은 "전부 devm으로, 의존 순서대로 얻는다". 또 open/ioctl 같은 probe 밖에서 devm 할당하면 unbind까지 안 풀려 누수이고, devm 자원을 손으로 또 풀면 double free다. probe의 획득 순서: private 구조체 → MMIO 매핑 → 전원 → 클럭 → 리셋 해제 → 칩 ID 확인 → 초기화 → drvdata → IRQ → 서브시스템 등록. defer 가능한 자원은 하드웨어를 만지기 전에 다 얻고, 외부가 나를 부를 수 있는 단계(IRQ, 등록)는 맨 끝이다. 자식 장치를 등록한 뒤에는 defer를 돌려주면 안 된다(무한 재시도). 요즘은 fw_devlink가 DT 참조로 링크를 미리 만들어 대부분의 defer 자체를 막고, `/sys/class/devlink`로 누가 누구를 기다리는지 본다. 누수 검증은 실패 주입 + sysfs unbind/bind 100회 루프로 `/proc/interrupts`, `clk_summary`, `regulator_summary`, slab 사용량이 기준값으로 돌아오는지 본다. 6.11부터 platform driver의 `.remove`는 `void`를 반환한다(§11에서 6.18.55 헤더 확인).

> devm pushes a release action onto the device's devres list and the core unwinds it in reverse on probe failure or unbind — after `remove()`, which is exactly where IRQ-versus-teardown races hide.

**꼬리 질문**
- "When must you not return `-EPROBE_DEFER`?" → 자식 장치를 이미 등록했거나 하드웨어를 이미 건드린 뒤.
- "What's the difference between `remove()`, `shutdown()` and `suspend()`?" → 헤어질 때 전부 반납 / 재부팅 직전 DMA·IRQ만 조용히 / 돌아올 전제로 상태 저장.
- "Why `dev_err_probe()`?" → defer면 로그를 남기지 않고 사유를 `devices_deferred`에 기록, 아니면 에러 로그 + 에러 값 반환.

**함정**: `request_irq`를 devm 없이 쓰고 remove를 안 쓰는 것, defer를 `dev_err`로 시끄럽게 찍는 것.

### Q34 ★★★ — Character driver

**Q.** "Walk me through a minimal character driver. What are major and minor numbers and how should a new driver get them? What does .owner = THIS_MODULE do?"

**한국어로**: 최소한의 char 드라이버를 설명하라. major/minor 번호는 무엇이고 새 드라이버는 어떻게 받아야 하나? `.owner = THIS_MODULE`은 무엇을 하나?

**30초 답.** 세 단계다. 번호 받기(`alloc_chrdev_region` — 동적 major), cdev 등록(`cdev_init` + `cdev_add` — **이 순간부터 open이 가능**하니 상태 초기화는 그 전에), 노드 만들기(`class_create` + `device_create` — devtmpfs가 `/dev` 노드를 만들고 uevent로 udev가 권한을 다듬는다). `file_operations`에는 `.owner`, `.open`, `.read`, `.write`, `.release`, 필요하면 `.unlocked_ioctl`, `.poll`, `.mmap`, `.llseek`를 채운다. `read`는 `*ppos` 기준으로 남은 만큼 `copy_to_user`하고 복사한 만큼 돌려주며, 0은 EOF일 때만이다. exit은 정확히 역순. 단순한 장치면 `misc_register()` 한 번(major 10, minor 동적)으로 끝난다.

**2분 답.** `dev_t`는 상위 12비트 major, 하위 20비트 minor다(6.18.55 `MINORBITS 20` 확인) — `MAJOR`/`MINOR`/`MKDEV`로만 다룬다. 정적 major는 충돌한다: 랩 커널에서 "실험용" 240조차 이미 `ttyOWL`이 가져가 `-EBUSY`였다. 같은 칩 세 개면 인스턴스 구조체에 `struct cdev`를 박아 minor 하나씩 `cdev_add`하고, open에서 `container_of(inode->i_cdev, struct my_dev, cdev)`로 인스턴스를 찾는다. per-open 상태는 `file->private_data`, 읽기 위치는 VFS가 `struct file`마다 관리하는 `f_pos`다. `.owner = THIS_MODULE`은 open 경로가 그 모듈의 참조를 잡게 해서 열린 fd가 있으면 rmmod가 거부된다(G4에서 fd 하나에 `lsmod`가 2). 빼고 실험하면 언로드가 성공하고, 그 fd를 닫는 순간 해제된 모듈 메모리의 fops를 읽다가 Oops가 났다. 반대로 USB 분리처럼 모듈은 남고 장치만 사라지는 경우는 `.owner`로 못 막으니 kref로 상태 수명을 마지막 release까지 늘리고 `removed` 플래그로 이후 read를 `-ENODEV`로 돌린다. `.llseek`가 NULL이면 `-ESPIPE`(스트림이면 맞다, `stream_open`), 6.18에는 옛 `no_llseek`가 없다. 화이트보드 40줄 버전은 G4 §10과 R3에 있다.

> Allocate a dynamic `dev_t`, initialize state, `cdev_add` (now it's live), then `device_create` so devtmpfs makes the node; `.owner = THIS_MODULE` pins the module while any fd is open.

**꼬리 질문**

- "What should read() return with less data than requested? With none?" → 있는 만큼(short read 정상). 없으면 block 또는 `-EAGAIN`. 0은 EOF만.
- "How does `/dev/foo` get created?" → `device_create()` → sysfs `dev` 속성 + devtmpfs 노드 + uevent → udev rule이 권한.

**함정**: `register_chrdev()`(minor 256개를 한 fops로 다 가져감)를 쓰는 것, `cdev_add` 뒤에 상태를 초기화하는 것.

### Q35 ★★ — 인터페이스 고르기: read/write · ioctl · sysfs · debugfs · mmap

**Q.** "When would you use ioctl versus sysfs versus a read/write interface for a device? What's the difference between sysfs, debugfs and configfs?"

**한국어로**: 장치 인터페이스로 ioctl, sysfs, read/write를 각각 언제 쓰나? sysfs, debugfs, configfs는 무엇이 다른가?

**30초 답.** 데이터의 모양·빈도·원자성으로 가른다. 순차 스트림은 read/write, 사람이 셸로 만지는 단일 튜닝 값은 sysfs 한 파일(값 하나 = 파일 하나, 문서화된 ABI), 여러 값을 원자적으로 바꾸거나 START/STOP 같은 트랜잭션은 ioctl, 대량 고속 데이터는 mmap. debugfs는 ABI가 없는 개발자용 창문(레지스터 덤프, 통계, 결함 주입)이라 양산에서 꺼질 수 있고, configfs는 반대로 유저가 `mkdir`로 커널 객체를 만들고 설정하는 곳(USB gadget, nvmet)이다. 가능하면 새 ioctl을 만들지 말고 IIO·V4L2 같은 서브시스템을 쓴다.

**2분 답.** ioctl 번호는 32비트에 방향 2 + 크기 14 + type 8 + nr 8비트를 `_IO/_IOR/_IOW/_IOWR`로 넣고, 방향은 유저 관점이다(`_IOR`은 커널이 유저 버퍼에 쓴다) — `BLKGETSIZE64`는 `_IOR(0x12, 114, size_t)` = `0x80081272`. 모르는 명령은 `-ENOTTY`. 32비트 앱과 64비트 커널이 같이 쓰려면 고정 폭 타입만, 포인터는 `__u64`, 명시적 패딩으로 모든 ABI에서 같은 크기(pahole 확인)로 만들면 `.compat_ioctl = compat_ptr_ioctl` 하나로 끝난다. 확장은 끝에만 덧붙이고 `copy_struct_from_user()`로 크기 차이를 처리한다. sysfs 규칙: show는 `sysfs_emit`, store는 `kstrto*`로 파싱해 실패면 음수 errno, 성공이면 `count`를 반환한다. 속성은 `.dev_groups`로 선언해야 driver core가 uevent 전에 만들어 udev가 볼 수 있다. 값 변화 알림은 `sysfs_notify()` + 유저 `poll(POLLPRI)`. 레지스터 덤프는 `debugfs_create_regset32`(I2C/SPI면 regmap이 debugfs를 자동으로 준다). 새 드라이버에 `/proc` 파일은 만들지 않는다. 그리고 센서 스트림을 sysfs로 내지 않는다 — G8에서 값 하나 open/read/close가 char device `read()`보다 수십 배 비쌌다.

> Streams go through read/write, one human-tunable value per sysfs file, atomic multi-field transactions through a fixed-width ioctl, bulk data through mmap, and anything without ABI promises into debugfs.

**꼬리 질문**
- "Why does the community discourage new ioctls?" → 드라이버마다 제각각이라 도구 검사가 안 되고, compat을 손으로 챙겨야 하고, 한 번 공개하면 영원히 못 깬다.
- "How can user space wait for a sysfs value to change?" → 드라이버 `sysfs_notify()`, 유저는 한 번 읽고 `POLLPRI`로 poll, 깨면 offset 0부터 다시 읽기.
- "When would you use a binary sysfs attribute?" → 커널이 해석하지 않는 blob(보정 데이터, EEPROM).

**함정**: 센서 데이터를 sysfs로 폴링하게 만드는 것, debugfs 파일을 제품 앱이 의존하게 두는 것.

**출처**: → G5 §1·§2·§3, G8 §1·§2·§3·§6·§7·§8·§9·§10·§12, A3 §8, E6 §6

### Q36 ★★ — 드라이버의 `.poll` 구현

**Q.** "Implement poll for your character driver. Does poll_wait sleep? What does edge-triggered epoll require from a driver?"

**한국어로**: char 드라이버의 `poll`을 구현하라. `poll_wait`는 잠드나? edge-triggered epoll은 드라이버에 무엇을 요구하나?

**30초 답.** `.poll(file, wait)`는 두 단계다. 먼저 마스크에 영향을 주는 wait queue 전부에 `poll_wait()`를 부른다 — 이건 **잠드는 게 아니라 호출자의 엔트리를 등록**하는 것이다. 그다음 락 아래서 상태를 보고 마스크를 만든다: 데이터가 있으면 `EPOLLIN | EPOLLRDNORM`, 쓸 자리가 있으면 `EPOLLOUT | EPOLLWRNORM`, 예외 이벤트면 `EPOLLPRI`, 장치가 사라졌으면 `EPOLLHUP | EPOLLERR`. 생산자(IRQ, write)는 상태를 바꾼 뒤 `wake_up_interruptible_poll(&q, EPOLLIN)`을 부른다. 같은 wait queue를 blocking `read`도 쓰므로 select, poll, epoll, blocking I/O가 한 번에 지원된다.

**2분 답.** `poll_wait`를 상태 검사보다 먼저 부르는 이유는 lost event다 — 반대 순서면 검사와 등록 사이에 온 `wake_up`이 아무도 깨우지 못한다. 실제로 잠드는 곳은 VFS의 `do_select`/`do_poll`이나 epoll의 `ep_poll`이고, 깨어나면 드라이버의 `.poll`을 다시 불러 실제 상태를 확인한다. ET epoll은 **새 데이터가 들어올 때마다** 깨우기를 요구한다: 빈→찬 전이 때만 깨우면 덜 읽은 ET 사용자는 epitem이 ready list에 다시 올라갈 계기가 없어 영원히 안 깬다 — G6에서 FIFO가 11개까지 차는 동안 `epoll_wait`이 계속 timeout인 것을 재현했다. 깨울 때 key(`EPOLLIN` 등)를 실으면 관심 없는 poller를 거른다(이벤트만 기다리는 poller의 `.poll` 호출이 데이터 100개에 102번 → 2번). 장치가 사라질 때는 모든 queue를 `EPOLLHUP | EPOLLERR`로 깨우고, epoll 엔트리가 내 wait queue에 매달려 있으므로 장치 구조체를 kref로 마지막 `release`까지 살려 둔다. 새 설계에서 비동기 알림은 SIGIO(`.fasync`)보다 유저가 넘긴 eventfd에 `eventfd_signal(ctx)`(6.8부터 인자 하나)가 낫다 — 횟수가 보존되고 이벤트 루프에 그대로 들어간다.

> `.poll` registers on every relevant wait queue with `poll_wait()` — which never sleeps — and returns the current mask; the producer wakes the queue with the event key, and for edge-triggered users it must wake on every new item.

**꼬리 질문**
- "What does the driver do differently for select, poll and epoll?" → 아무것도. 셋 다 `vfs_poll()`로 같은 `.poll`을 부른다.
- "What happens if `.poll` always returns `EPOLLIN`?" → 유저 epoll 루프가 busy loop가 된다.
- "What happens to pollers when the device is unplugged?" → HUP|ERR로 전부 깨우고, `read`/`write`는 `-ENODEV`, 구조체는 kref로 유지.

**함정**: "`poll_wait`에서 프로세스가 잠든다"고 설명하는 것.

**출처**: → G6 §1·§2·§3·§4·§5·§6·§7·§8·§10·§12, A4 §10

### Q37 ★★ — MMIO: ioremap, readl/writel, 폴링

**Q.** "Why can't a Linux driver just cast the physical register address to a volatile pointer like in bare-metal firmware? How do you wait for a hardware status bit?"

**한국어로**: bare-metal처럼 물리 레지스터 주소를 volatile 포인터로 캐스트하면 왜 안 되나? 하드웨어 상태 비트는 어떻게 기다리나?

**30초 답.** 커널도 MMU를 켠 가상 주소로 돈다. 장치 레지스터는 linear map에 없으니 `ioremap`으로 vmalloc 영역에 Device-nGnRE 속성 PTE를 만들어야 접근할 수 있다. 주소는 하드코딩하지 않고 DT `reg`나 PCI BAR에서 받고, `request_mem_region`으로 소유권을 표시한다 — 보통 `devm_platform_ioremap_resource(pdev, 0)` 한 줄이 이걸 다 한다. 접근은 `__iomem` 포인터에 `readl`/`writel`(배리어·접근 폭·엔디안 보장)로만 한다. 상태 비트는 `readl_poll_timeout(addr, val, cond, sleep_us, timeout_us)`로 기다리고, IRQ 핸들러나 spinlock 안이면 `_atomic` 변형을 쓴다.

**2분 답.** `__iomem`을 직접 역참조하면 arm64에서 "돌아가는 것처럼" 보여도 다섯 가지가 깨진다: 컴파일러가 접근을 합치거나 지우고, 배리어가 없고, 다른 아키텍처로 이식이 안 되고, KVM에서 ISV 없는 명령으로 트랩되고, MMIO tracing을 우회한다(H1 §8). `readl_poll_timeout`은 만료 여부를 먼저 계산하고 한 번 더 읽은 뒤 판정해서 선점돼 늦게 깨어나도 거짓 타임아웃이 안 난다 — 실패하면 `-ETIMEDOUT`과 마지막 값을 로그에 남기고, timeout 0(무한)은 쓰지 않는다. 인터럽트가 있으면 폴링 대신 completion. 같은 제어 레지스터의 다른 비트를 두 경로가 고치면 read-modify-write 경쟁으로 비트가 사라진다 — H1에서 `-smp 2`로 락 없이 돌리니 2만 번 중 약 8~10%가 유실됐고 spinlock을 거니 0이었다. 해결은 `spin_lock_irqsave`로 감싼 update-bits 헬퍼, `regmap_update_bits`, 또는 하드웨어 SET/CLR 레지스터. 레지스터가 `0xFFFFFFFF`를 돌려주면 PCIe 링크 다운·Memory Space Enable 꺼짐, SoC IP면 클럭 게이트·리셋·전원 도메인을 본다. 메모리 속성: `ioremap`은 Device-nGnRE(posted), `ioremap_wc`는 쓰기 결합(프레임버퍼), RAM은 `memremap`.

> Registers live behind `ioremap()` in vmalloc space with Device attributes; I take the address from DT or a BAR, access it only with `readl`/`writel`, and wait with `readl_poll_timeout()` instead of a hand-rolled loop.

**꼬리 질문**
- "`readl` vs `readl_relaxed`?" → Q26. relaxed는 같은 장치 MMIO끼리만 순서.
- "Why is `/dev/mem` bad in production?" → 드라이버의 소유권·락·배리어 우회, IRQ 불가, DMA 엔진으로 커널 메모리를 쓸 수 있는 보안 구멍. 필요하면 UIO/VFIO.
- "UIO vs VFIO?" → UIO는 매핑 + IRQ 통지만, VFIO는 IOMMU로 장치 DMA를 프로세스에 가둔다.

**함정**: 타임아웃 없는 `while (!(readl(...) & BIT))` 루프, MMIO에 `memcpy`.

### Q38 ★★★ — I2C, SPI, 그리고 regmap

**Q.** "Explain the Linux I2C subsystem — adapter, algorithm, client, driver. How do you read a register with a repeated start? What's the SPI equivalent, and why would you use regmap?"

**한국어로**: Linux I2C 서브시스템을 설명하라 — adapter, algorithm, client, driver. repeated START로 레지스터를 읽으려면? SPI는 어떻게 대응되고, regmap은 왜 쓰나?

**30초 답.** I2C는 네 객체다. adapter는 버스 하나(`i2c-N`), algorithm은 그 버스를 구동하는 함수 표(`.xfer`, `.functionality`)로 컨트롤러 드라이버가 제공한다. client는 (버스, 주소, 이름)으로 정해진 장치 하나로 DT 자식 노드에서 만들어지고, driver는 그 장치 종류를 다루는 `i2c_driver`로 `probe(client)`를 가진다. 둘은 i2c-core를 사이에 두고 `i2c_msg` 배열로만 대화한다. 레지스터 읽기는 write(레지스터 번호) + read(`I2C_M_RD`) 두 메시지를 **한 번의** `i2c_transfer()`로 보내면 사이가 repeated START가 된다. SPI는 `spi_controller`/`spi_device`/`spi_driver`이고, `spi_message`(= `spi_transfer` 리스트, CS 경계의 단위)를 `spi_sync()`로 보낸다. 레지스터형 칩이면 버스 함수를 직접 부르기보다 regmap을 먼저 쓴다.

**2분 답.** I2C 에러 코드는 `-ENXIO`(주소 NACK), `-EREMOTEIO`(데이터 NACK에 흔함), `-EAGAIN`(arbitration lost, core가 재시도), `-ETIMEDOUT`(clock stretching·고착). SDA가 LOW로 고착되면 SCL을 최대 9번 토글해 target이 비트를 다 내보내게 하고 STOP을 만든다 — Linux는 `bus_recovery_info` + `i2c_recover_bus()`. SMBus는 I2C의 부분집합이라 SMBus 전용 컨트롤러에서는 임의 `i2c_transfer`가 안 되므로 functionality를 확인한다. SPI 함정 셋: 스택 버퍼를 `spi_sync`에 넘기면 안 된다(DMA가 캐시라인을 다른 지역 변수와 공유하고, `VMAP_STACK`이면 물리 연속도 아님 — kmalloc 버퍼, `____cacheline_aligned` 버퍼, 또는 `spi_write_then_read`), CPOL/CPHA가 틀리면 0x00/0xFF가 아니라 "그럴듯하게 틀린" 값이 나오고, `spi_async`가 빠르다는 건 오해다(H7에서 RT 펌프 선점 때문에 8배 느렸다). regmap은 버스와 무관한 레지스터 API다: 같은 드라이버가 I2C·SPI·MMIO판 칩을 지원하고, 캐시로 버스 트랜잭션을 줄이고(H2의 전형적 워크로드에서 8회 → 3회), 락·RMW(`regmap_update_bits`)·bulk·폴링·debugfs 덤프·tracepoint가 공짜이며, suspend 후 복원이 `regcache_sync()` 한 줄이다. 상태·데이터 레지스터는 반드시 volatile로 분류한다 — 빠뜨리면 첫 읽기 값이 캐시돼 상태 비트가 영원히 0이고 IRQ 핸들러가 `IRQ_NONE`을 돌려 IRQ가 꺼진다. I2C/SPI regmap은 잠들므로 hard IRQ에서 못 부른다. i2c-dev·spidev는 bring-up 도구다(DT에 `compatible = "spidev"`는 커널이 거부, `driver_override`로 bind).

> Controller drivers provide the adapter and algorithm, client drivers bind to `i2c_client`s from DT and speak `i2c_msg` arrays — two messages in one `i2c_transfer` give a repeated start; for register chips I put regmap on top for caching, locking and suspend restore.

**꼬리 질문**
- "The bus is hung — SDA stuck low. What do you do?" → 9 클럭 recovery, SCL까지 LOW면 target 전원·리셋.
- "Why can't you pass a stack buffer to `spi_sync`?" → DMA 캐시라인 공유와 VMAP_STACK.
- "What is a volatile register in regmap, and what happens if you get it wrong?" → 캐시하지 않는 레지스터. 틀리면 상태가 얼어붙는다.
- "How do you debug I2C without a logic analyzer?" → i2c/smbus tracepoint(메시지·주소·데이터·반환값).

**함정**: hard IRQ 핸들러에서 I2C `regmap_read`, 레지스터 번호 쓰기와 읽기를 `i2c_transfer` 두 번으로 나눠 STOP이 끼게 하는 것.

### Q39 ★★ — GPIO와 pinctrl

**Q.** "What is pin multiplexing and how does Linux handle it? How does gpiod handle active-low signals? Why was the sysfs GPIO interface deprecated?"

**한국어로**: 핀 먹스란 무엇이고 Linux는 어떻게 다루나? gpiod는 active-low를 어떻게 처리하나? sysfs GPIO는 왜 deprecated됐나?

**30초 답.** SoC 패드 하나에 여러 내부 신호(UART TX, GPIO, PWM …)가 연결돼 있고 먹스 레지스터로 하나를 고른다. Linux에서는 pin controller 드라이버가 패드를 핀·그룹·함수로 등록하고, 장치 노드는 DT의 `pinctrl-names`/`pinctrl-0`으로 상태를 정의하며, **driver core가 probe 직전에 default 상태를 자동 적용**한다(풀업·구동 세기 같은 패드 설정도 함께). GPIO는 descriptor API로 쓴다: `devm_gpiod_get(dev, "reset", GPIOD_OUT_HIGH)`. DT 플래그 `GPIO_ACTIVE_LOW`를 gpiolib이 기록해 두고 `gpiod_set_value`가 논리값을 물리값으로 반전하므로, 드라이버는 "1 = assert"만 말한다.

**2분 답.** H4에서 리셋 assert가 logical 1, raw 0으로 나오는 것을 확인했다 — 드라이버가 극성을 또 처리하면 이중 반전 버그다(극성을 무시해야 할 때만 `_raw_` 함수). `gpiod_set_value`는 SoC 내장 MMIO GPIO처럼 atomic 문맥에서 쓸 수 있는 칩용이고, I2C/SPI 확장기는 전송이 필요해 잠들므로 `gpiod_set_value_cansleep`이다 — process 문맥에서는 `_cansleep`을 기본으로 쓰면 하드웨어가 바뀌어도 안전하다. GPIO 인터럽트는 `gpiod_to_irq()` + `devm_request_threaded_irq()`이고, 확장기 뒤라면 nested threaded IRQ라 스레드 핸들러가 필수다. sysfs GPIO가 죽은 이유: 전역 번호가 동적이라 불안정하고, 소유권이 프로세스에 묶이지 않아 죽어도 export가 남고, 다중 라인 원자 조작·바이어스·디바운스 설정이 없고, 이벤트에 timestamp와 큐가 없다. 대체인 char device uAPI v2는 line request fd가 소유권이고 닫히면 해제되며 이벤트에 timestamp와 seqno가 붙는다. 같은 GPIO를 두 드라이버가 원해 `-EBUSY`면 `/sys/kernel/debug/gpio`의 consumer 이름과 `pinmux-pins`의 owner를 본다. 하드웨어 없이는 gpio-sim으로 가짜 칩을 만들어 IRQ까지 테스트한다. 레거시 `of_get_named_gpio`는 쓰지 않는다.

> Pin state is declared in DT and applied by the driver core before probe; GPIOs are descriptors whose active-low flag gpiolib applies, so drivers speak logical values and use the `_cansleep` variants on expanders.

**꼬리 질문**
- "When would a driver select a pinctrl state itself?" → suspend의 `sleep` 상태, I2C 버스 복구용 GPIO 상태.
- "`gpiod_set_value` vs `gpiod_set_value_cansleep`?" → 칩이 잠들 수 있느냐.
- "How would you test GPIO handling without hardware?" → gpio-sim(configfs나 DT), sim 쪽 `pull`로 외부 신호 흉내.

**함정**: 전역 GPIO 번호를 하드코딩하는 것, 드라이버에서 극성을 다시 뒤집는 것.

### Q40 ★★★ — DMA: coherent vs streaming, 캐시, IOMMU

**Q.** "What is the difference between coherent and streaming DMA mappings? Why do you need dma_sync_single_for_cpu? What does an IOMMU buy you?"

**한국어로**: coherent와 streaming DMA 매핑은 무엇이 다른가? `dma_sync_single_for_cpu`는 왜 필요한가? IOMMU는 무엇을 주나?

**30초 답.** 주소가 셋이다: CPU 가상 주소, 물리 주소, 장치가 보는 `dma_addr_t`(IOMMU가 있으면 IOVA). coherent(`dma_alloc_coherent`)는 새로 할당하는 메모리로 CPU와 장치가 언제든 동시에 봐도 일관성이 보장된다 — 비코히어런트 SoC에서는 캐시를 끈 매핑을 준다. 디스크립터 링·상태 블록용이다. streaming(`dma_map_single/page/sg`)은 이미 있는 버퍼를 **한 번의 전송 동안 장치에 빌려 주는** 것이고, 방향(`DMA_TO_DEVICE`/`FROM_DEVICE`/`BIDIRECTIONAL`)과 소유권 규칙이 있으며 map/unmap/sync 때 캐시 관리나 bounce가 일어난다. 데이터 버퍼용이다. `sync_for_cpu`는 매핑을 유지한 채 소유권을 CPU로 가져올 때 — 장치가 쓴 데이터 위의 옛 캐시 라인을 invalidate한다(재사용 RX 링).

**2분 답.** arm64 비코히어런트에서 map과 `sync_for_device`는 모든 방향에서 clean(`dc cvac`), unmap과 `sync_for_cpu`는 FROM/BIDI일 때 invalidate(`dc ivac`, 양 끝 부분 라인은 `dc civac`)다. FROM_DEVICE인데도 map 때 clean하는 이유는 dirty 라인이 DMA 뒤에 evict되어 데이터를 덮는 것을 막기 위해서다. 그래서 DMA 버퍼는 `ARCH_DMA_MINALIGN` 정렬이 필요하고, 최근 arm64는 작은 kmalloc 버퍼를 SWIOTLB로 bounce한다(H9에서 실측). DMA mask(`dma_set_mask_and_coherent`)는 장치가 낼 수 있는 주소 폭이고, 버퍼가 그 위에 있으면 IOMMU가 아래쪽 IOVA를 주거나 SWIOTLB가 복사한다 — mask를 과장하면 장치가 상위 비트를 버려 조용히 다른 메모리를 망가뜨린다. IOMMU는 격리(나쁜 DMA는 translation fault), 흩어진 페이지를 연속 IOVA로, VFIO 패스스루를 주고, 대가는 map/unmap 때 page table 갱신과 IOTLB 무효화다 — H9에서 strict 모드 4 KiB map/unmap 한 쌍이 direct의 약 17배(6849 대 401 ns, TCG)였다. SoC 범용 DMA는 dmaengine(`dma_request_chan` → `dmaengine_slave_config` → `prep_slave_sg`/cyclic → `submit` → `dma_async_issue_pending`), 장치 사이 공유는 dma-buf(exporter가 importer 장치용 sg_table을 매핑, `dma_resv` fence로 순서). 개발 중에는 `CONFIG_DMA_API_DEBUG`가 방향 불일치·unmap 누락을 잡는다. SSD 펌웨어의 PRP/SGL + 캐시 관리와 같은 일이고, Linux에서는 **소유권 경계가 API 호출**이라는 것이 차이다.

> Coherent memory is shared all the time, streaming mappings lend an existing buffer to the device for one transfer with explicit ownership hand-offs, and on non-coherent arm64 those hand-offs are the cache clean and invalidate points.

**꼬리 질문**
- "Why not make data buffers coherent too?" → 비코히어런트 SoC에선 uncached라 CPU 접근이 느리고, 이미 있는 버퍼(skb, page cache)를 복사해야 한다.
- "How would a camera frame get to the GPU without a copy?" → V4L2 `VIDIOC_EXPBUF` → dma-buf fd → GPU 드라이버 import(`dma_buf_attach`/`map_attachment`).
- "What is an IOMMU group?" → 서로 격리할 수 없는 장치 묶음. VFIO는 그룹 단위로 넘긴다.

**함정**: `virt_to_phys()` 값을 장치에 쓰는 것, unmap(또는 `sync_for_cpu`) 전에 CPU가 버퍼를 읽는 것.

### Q41 ★★ — 왜 프레임워크(IIO·input·hwmon)에 붙이나, IMU 드라이버 설계

**Q.** "Why shouldn't I just write a char device with an ioctl for my sensor? Design a Linux driver for a 6-axis IMU on I2C with a data-ready interrupt."

**한국어로**: 센서용으로 그냥 char device + ioctl을 짜면 안 되는 이유는? data-ready 인터럽트가 있는 I2C 6축 IMU의 Linux 드라이버를 설계하라.

**30초 답.** char device를 직접 만들면 커널 코드 양은 비슷해도 나머지 전부를 새로 만들어 영원히 유지해야 한다 — 전용 ioctl ABI, 전용 유저 툴, 락, 권한, PM, 문서. 프레임워크에 등록하면 표준 인터페이스, 표준 툴, core 락을 공짜로 받는다: I1에서 같은 온도계를 두 방식으로 짜 보니 커널 쪽은 88줄 대 85줄로 같았고 유저 쪽은 33줄 대 0줄이었다. IMU는 IIO다 — 표준 단위(raw/scale/offset), 고속 버퍼와 타임스탬프, 트리거로 샘플링 시점 제어가 IIO에만 있다. 구조: I2C client driver + regmap, WHO_AM_I 확인·리셋·기본 ODR 설정, IIO 장치 하나에 가속도·자이로 XYZ + 온도 + 타임스탬프 채널, data-ready 트리거 + triggered buffer.

**2분 답.** 채널 속성은 raw는 separate, scale은 shared_by_type, ODR은 shared_by_all로 두고 available 목록을 준다. INT1을 트리거로 등록하고, triggered buffer의 top half(hardirq)에서 타임스탬프를 찍고 bottom half(IRQ 스레드)에서 burst 한 번으로 읽어 `iio_push_to_buffers_with_timestamp()`한다. 버퍼가 켜진 동안에는 단발 읽기와 full-scale 변경을 막는다. 1 kHz 이상이면 칩의 HW FIFO + watermark IRQ로 배치 읽기를 하고 샘플 시각은 IRQ 시각과 ODR로 보간한다. 타임스탬프 시계는 IIO 기본값인 realtime이 아니라 monotonic으로 바꾼다 — NTP·PTP가 realtime을 점프시키고, 카메라·CAN 타임스탬프와 같은 축이어야 융합할 수 있다. mount matrix는 DT에서 읽어 노출하고 회전은 유저가 한다. 유저는 `/dev/iio:deviceN`을 읽고 데이터 배치는 `scan_elements/`의 `_en`·`_index`·`_type`(예: `le:s12/16>>4`)으로 안다. 버퍼가 차면 kfifo는 새 샘플을 버리므로 길이는 ODR × 소비자의 최악 정지 시간으로 잡는다. sysfs 폴링은 I2에서 7채널 500 Hz 기준 버퍼 방식보다 리더 CPU가 5~18배였다. 실제 업스트림 IMU(`bmi160`, `st_lsm6dsx`, `inv_mpu6050`)를 i2c-stub으로 붙여 읽는 연습은 노트 Q5 §1–§4(IMU·GNSS·LiDAR)에 있다.

> A framework gives you the ABI, the tools and the locking for free; for an IMU that means IIO with a data-ready trigger, a top half that timestamps, a threaded bottom half that burst-reads, and monotonic timestamps.

**꼬리 질문**
- "Your IMU runs at 1 kHz but the app sees 880 Hz with gaps. How do you debug it?" → 단계별로 센다: IRQ 수(`/proc/interrupts`) vs pollfunc 수 vs push 실패 vs 유저가 읽은 수. IRQ > pollfunc면 bottom half가 주기보다 오래 걸림(400 kHz 16바이트 burst ≈ 0.43 ms) → 버스 속도, HW FIFO 배치, IRQ 스레드 우선순위.
- "What is an IIO trigger and why is it separate from the device?" → "지금 샘플을 잡아라"는 독립 신호원. 하나의 HW 타이머로 여러 ADC를 동시에, DRDY 없는 센서에 hrtimer.
- "When is a char device still right?" → 맞는 프레임워크가 없을 때(커스텀 FPGA 가속기). 그때도 misc + 문서화된 ABI.

**함정**: 센서마다 커스텀 char device를 만드는 것, IIO 타임스탬프를 기본 realtime으로 두는 것.

### Q42 ★★ — 플래시와 전원 차단: raw NAND vs eMMC, UBI, fsync

**Q.** "What is the difference between raw NAND and eMMC from the Linux kernel's point of view? How do you guarantee a config file survives a sudden power loss?"

**한국어로**: 커널 관점에서 raw NAND와 eMMC는 무엇이 다른가? 설정 파일이 갑작스러운 전원 차단에도 살아남게 하려면?

**30초 답.** raw NAND는 FTL이 없어서 커널이 MTD 장치로 보고, ECC·배드 블록·wear leveling을 MTD + UBI가 맡고 그 위에 UBIFS를 올린다. eMMC·SD·UFS는 장치 안에 컨트롤러와 FTL이 있어서 MMC 코어 위의 `mmc_blk`가 만든 블록 장치이고, 커널은 명령과 discard·flush 같은 힌트만 준다 — 파일시스템은 ext4나 F2FS. 설정 파일은 **같은 디렉터리의 temp 파일에 쓰고 → `fsync(temp)` → `rename()`으로 교체 → 디렉터리 `fsync`**한다. rename은 원자적이라 재부팅 후엔 옛것 아니면 새것만 보이고, temp fsync는 "데이터가 rename보다 먼저 디스크에", 디렉터리 fsync는 "rename 자체의 내구성"을 준다.

**2분 답.** fsync는 그 파일의 dirty page를 writeback하고 저널 커밋을 기다리는데, jbd2는 커밋 블록을 `REQ_PREFLUSH | REQ_FUA`로 보내고 block layer가 이를 "FLUSH 명령 → FUA 쓰기"로 쪼갠다(eMMC면 CMD6 FLUSH_CACHE, NVMe면 Flush + FUA 비트) — SSD 펌웨어에서 처리하던 Flush/FUA의 반대편이다. `fflush`는 stdio 버퍼를 커널로 넘길 뿐이고, `O_DIRECT`와 `sync_file_range`는 내구성을 주지 않는다(J5의 tracefs에서 평범한 쓰기 하나만 나감). fsync가 `EIO`를 돌려주면 다시 불러도 소용없다 — Linux는 에러 난 page를 clean으로 표시하고 에러를 fd당 한 번만 보고한다(errseq, 2018 fsyncgate). 비용 감각: A3에서 4 KiB write만 0.6 µs, fdatasync 약 75 µs, fsync 약 110 µs(VM). raw NAND 쪽 함정: mtdblock 위 ext4는 512 B 쓰기가 erase 1 + program 64가 되고 WL·배드 블록 보호가 없다. UBI 이미지는 `nandwrite`가 아니라 `ubiformat`으로 굽는다(EC 헤더 = erase 횟수 보존, J4에서 25/15 대 1/0). UBI attach가 느리면 fastmap(J4: 4.4 s → 0.7 s). 비트 플립은 MTD가 `-EUCLEAN`을 주고 UBI가 scrub한다 — SSD의 read reclaim. 필드 로그는 append-only 고정 레코드 + seq + CRC, fsync는 N개나 100 ms마다 묶는다. rootfs는 읽기전용(squashfs/EROFS) + overlayfs 쓰기층이 흔한 패턴이다.

> raw NAND needs MTD plus UBI as the FTL and UBIFS on top, managed flash is a block device with ext4 or F2FS; durability is write-temp, fsync, rename, fsync-directory — and an EIO from fsync is final.

**꼬리 질문**
- "What does fsync actually send to the device?" → writeback + 저널 커밋, PREFLUSH(이전 쓰기를 매체로) + FUA(이 쓰기 자체를 매체로).
- "fsync returned EIO. Can you call fsync again?" → 안 된다. 두 번째는 0을 주지만 디스크엔 옛 데이터. 치명적으로 처리.
- "How do you flash a UBI image?" → `ubiformat` 또는 U-Boot `ubi write`. `nandwrite`는 0xFF page를 program하고 EC를 지운다.

**함정**: rename만 하고 fsync를 빼먹는 것, "O_DIRECT면 안전하다"는 답.

### Q43 ★★ — OTA 업데이트와 secure boot

**Q.** "Design an OTA update system for a fleet of field units — what happens if power dies during the update? And walk me through secure boot on an ARM SoC: where is the root of trust?"

**한국어로**: 현장 장비 무리를 위한 OTA 업데이트를 설계하라 — 업데이트 중 전원이 나가면? 그리고 ARM SoC의 secure boot을 설명하라 — 신뢰의 뿌리는 어디인가?

**30초 답.** OTA는 "업데이트"가 아니라 **되돌릴 수 있는 전환**이다. A/B 슬롯(커널 + rootfs, 읽기전용 + dm-verity), RAUC·SWUpdate·Mender 같은 검증된 클라이언트가 서명된 번들을 비활성 슬롯에 설치, redundant U-Boot env에 슬롯·시험 플래그·bootcount, 재부팅 후 health check가 통과하면 commit, 실패하면 `bootcount > bootlimit`에서 `altbootcmd`로 롤백한다. 활성 슬롯은 건드리지 않고 슬롯 전환은 env 쓰기 한 번(두 벌 + flag)이라 어느 순간 전원이 나가도 안전하다. secure boot의 뿌리는 **BootROM + OTP eFuse에 태운 ROTPK 해시**다: ROM(또는 BL1)이 인증서의 공개키 해시를 fuse와 비교하고, 그 키로 다음 단계를 검증하고, U-Boot은 자기 control DTB에 박힌 공개키로 서명된 FIT configuration을 검증해 커널까지 사슬을 잇는다.

**2분 답.** L4에서 슬롯 기록 도중 QEMU를 `kill -9`해 보니 기존 슬롯이 그대로 부팅됐고, 반쯤 쓴 슬롯은 fsck로는 clean이었지만 bad로 표시돼 있었다 — 판정은 파일시스템이 아니라 업데이터 메타데이터가 한다. 부트로더 업데이트는 되돌려 줄 주체가 없으니 하드웨어 이중화(eMMC boot0/boot1 + EXT_CSD 전환, ROM secondary image)와 "쓰기 → 읽기 검증 → 원자적 전환"을 쓰고 빈도를 최소화한다. "good"의 기준은 부팅이 아니라 제품 기능(카메라 열림, IMU 데이터 흐름, 앱 자체 진단)이고 그동안 HW watchdog을 켜 둔다. 서명만으로는 롤백(옛 취약 이미지)을 못 막으므로 eFuse·RPMB·TPM NV의 단조 카운터를 commit **후에** 올린다. delta 업데이트는 L4 실측에서 full 147 MiB 대 8.4 MiB였고, 정확한 출발 이미지(읽기전용 rootfs, 재현 가능한 빌드)가 전제다. secure boot 쪽: TF-A의 TBBR은 ROT 키 → world 키 → 이미지별 키 인증서 → content 인증서로 나뉘어 U-Boot 서명 키가 BL31을 서명할 수 없다. FIT는 이미지별이 아니라 **configuration을 서명**해야 서명된 부품을 섞는 mix-and-match(옛 커널 + 디버그 DT)를 막는다(L5에서 실측). 양산 U-Boot은 프롬프트·env·옆길 부트 명령을 닫는다(`BOOTDELAY=-2`, `ENV_IS_NOWHERE`, `booti` 제거). 커널 다음 고리는 모듈 서명 강제(`MODULE_SIG_FORCE`)와 lockdown, rootfs는 dm-verity. secure boot은 검증 실패 시 멈추고, measured boot은 TPM PCR에 기록만 하고 나중에 attestation으로 판단한다.

> OTA is a reversible switch: install into the inactive A/B slot, flip one redundant env variable, health-check, then commit — or let bootcount roll back; secure boot chains signatures from the ROM's fused key hash through TF-A and U-Boot to a signed FIT configuration.

**꼬리 질문**
- "What can secure boot NOT protect against?" → 런타임 침해, 카운터 없는 롤백, JTAG·DMA 공격, 사슬을 잇지 않은 rootfs 변조, 기밀성, 키 유출.
- "Your signing key leaked — what now?" → 어느 키냐로 나눈다. 상위 키로 새 키 배포 → 부팅 확인 → 옛 키 revoke + 롤백 카운터.
- "A/B or single copy with recovery?" → 공간 vs 다운타임·롤백. 원격 장비면 A/B, 실패 비용이 크면 A/B + recovery.

**함정**: "서명했으니 다운그레이드 공격은 막힌다"는 답, health check를 "부팅됐다"로만 정의하는 것.

### Q44 ★★ — Buildroot vs Yocto (그리고 rootfs·systemd 한 줄씩)

**Q.** "Buildroot or Yocto for a new robotics product — how do you choose? What's the difference between DEPENDS and RDEPENDS? What does a minimal root filesystem need?"

**한국어로**: 새 로봇 제품에 Buildroot와 Yocto 중 무엇을 쓰나? DEPENDS와 RDEPENDS는 무엇이 다른가? 최소 rootfs에는 무엇이 필요한가?

**30초 답.** Buildroot는 Make + Kconfig로 된 이미지 생성기다 — defconfig 하나로 툴체인·패키지·rootfs 이미지를 통째로 만들고, 단순하고 빠르지만 패키지 피드가 없고 설정 변경을 추적하지 않는다(패키지 `-rebuild`가 필요). Yocto는 BitBake 엔진 + OE-Core 메타데이터(레이어·레시피·클래스)로 MACHINE·DISTRO·IMAGE를 분리하고, 패키지 단위로 빌드하며, sstate 캐시로 큰 팀과 여러 제품을 감당한다. 실제 결정 요인은 대개 **벤더 BSP 지원**이다 — NXP·TI는 BSP를 Yocto 레이어로 준다. 팀이 작고 제품 하나에 이미지를 통째로 OTA하면 Buildroot, 벤더 BSP가 Yocto거나 제품 라인이 여럿이면 Yocto.

**2분 답.** Buildroot의 staging은 크로스 툴체인의 sysroot(헤더·정적 라이브러리·심볼 있는 라이브러리)이고 target은 strip된 실제 rootfs다 — 원격 gdb의 sysroot를 staging으로 두는 이유. 회사 패키지·보드 파일은 `BR2_EXTERNAL` 트리에 두어 Buildroot를 업스트림 그대로 유지하고, 정적 파일은 rootfs overlay, 로직은 post-build, 디스크 이미지·서명은 post-image(genimage). 드라이버 개발 루프는 `<PKG>_OVERRIDE_SRCDIR`. Yocto의 DEPENDS는 빌드 시점·레시피 사이 의존(B의 sysroot가 A의 recipe-sysroot에 들어옴), RDEPENDS는 실행 시점·패키지 사이 의존(이미지에 같이 설치). 남의 레시피는 bbappend로 고치고, local.conf에서는 `IMAGE_INSTALL:append = " foo"`(`+=`는 파싱 순서 때문에 기본 목록을 덮는다). 현재 LTS는 6.0 Wrynose(2030-04까지), 이전 LTS는 5.0 Scarthgap(2028-04까지)이다(K4 기준). 라이선스 산출물(legal-info, SPDX SBOM)이 출하 요건이다(K7). 최소 rootfs는 PID 1이 될 `/init` 또는 `/sbin/init`, 동적 링크면 로더 + libc, `/dev/console`(devtmpfs), init이 마운트하는 `/proc`·`/sys`·`/dev`, 그리고 `/etc`의 몇 파일이다(K1). systemd 한 줄: `Requires=`/`Wants=`는 끌어오기, `After=`는 순서라 보통 짝으로 쓰고, 자가 회복은 `Restart=on-failure` + `Type=notify`/`WatchdogSec=`, 시스템 수준은 `RuntimeWatchdogSec=`로 HW watchdog(L1). 이 스터디에서 Buildroot·Yocto 전체 빌드는 가이드로만 다뤘다(K3–K5).

> Buildroot is one Kconfig-driven build of a whole image — simple and fast; Yocto is a layered metadata system with packages and shared sstate — and the vendor BSP usually decides.

**꼬리 질문**
- "You changed an option in menuconfig and ran make, but the change isn't in the image. Why?" → Buildroot는 stamp 파일만 본다. `<pkg>-reconfigure`/`-rebuild` 후 `make`, 툴체인 변경은 `make clean all`.
- "What is sstate and why are Yocto rebuilds fast?" → 태스크 입력 해시로 결과물을 캐시하고, 해시가 같으면 setscene으로 풀기만 한다.
- "`Requires=` vs `After=` in systemd?" → 의존성 vs 순서. `Requires=`만 쓰면 동시에 시작된다.

**함정**: local.conf에 `IMAGE_INSTALL +=`, 남의 레이어 레시피를 직접 수정하는 것.

### Q45 ★★★ — Kernel Oops 읽기

**Q.** "Here's a kernel oops. Walk me through how you read it. The faulting address is 0x10 — what does that tell you?"

**한국어로**: 여기 커널 Oops가 있다. 어떻게 읽나? fault 주소가 0x10이면 무엇을 알 수 있나?

**30초 답.** 순서대로 읽는다. 첫 Oops인지(`[#1]`, `Tainted:`) 확인 → 첫 줄과 ESR로 종류(커널 data abort, 읽기/쓰기, translation fault)와 FAR(fault 주소) → `Modules linked in`으로 용의자 → `pc`를 `scripts/faddr2line`(같은 빌드의 vmlinux나 `.ko`)으로 file:line과 인라인 체인까지 → `lr`과 Call trace로 호출 경로 → 레지스터와 `Code:` 줄로 어느 포인터가 NULL이었는지. FAR 0x10처럼 첫 페이지 안의 작은 주소는 **NULL 포인터 + 멤버 오프셋**이다 — 오프셋 16의 멤버를 `pahole`로 찾고, "왜 그 포인터가 NULL이었나"(대개 조회·할당 함수의 실패 반환을 확인하지 않음)를 묻는다.

**2분 답.** Call trace에서 크래시 함수의 호출자가 빠지는 경우가 있다: arm64 unwinder는 x29 frame record 체인을 따라가는데 leaf 함수는 frame record를 만들지 않아 호출자 위치가 x30(lr)에만 있다. 인라인된 함수는 faddr2line의 "inlined by" 체인으로만 보인다. KASLR이면 panic 로그의 `Kernel Offset`을 빼서 System.map 주소로 바꾸고, 모듈은 `/sys/module/<m>/sections/`의 시작 주소를 빼서 섹션 오프셋으로 만든다. `/size`가 다르면 빌드가 다르다는 뜻이라 faddr2line이 거절해 준다. 종류 구분: Oops는 현재 태스크만 죽이고 계속 간다(taint D, 인터럽트 문맥이면 panic), panic은 모든 CPU를 멈추고, `BUG_ON`은 일부러 Oops를 내고, WARN은 스택만 찍고 계속 간다(taint W) — 정책은 `panic_on_oops`/`panic_on_warn`. 크래시 지점이 버그 지점이 아닐 수 있다: M3에서 pc가 printk의 `string()` 안이었지만 FAR이 ASCII 'A' − 8이었고, 실제 버그는 문자열로 리스트 포인터를 덮은 다른 코드였다. 필드에서는 pstore/ramoops로 다음 부팅에 회수하거나 kdump, 개발 중에는 KASAN·KFENCE·`DEBUG_LIST`로 더 일찍 잡는다. Cortex-M HardFault와 1:1이다: CFSR ↔ ESR, BFAR/MMFAR ↔ FAR, stacked PC/LR ↔ pc/lr, map 파일 ↔ System.map + KASLR 보정.

> I read the ESR and FAR first, decode `pc` with faddr2line against the exact build, then use the registers and `Code:` to see which pointer was bad — a FAR of 0x10 is a NULL struct pointer plus a 16-byte member offset.

**꼬리 질문**
- "Why might the caller be missing from the call trace?" → leaf 함수는 frame record가 없어 호출자가 lr에만 있다. 인라인도 안 보인다.
- "You only have a raw address from a field log with KASLR on. How do you map it?" → `Kernel Offset`(또는 런타임 `_text` 차이)을 빼고, 모듈은 섹션 시작 주소를 뺀다.
- "Oops vs panic vs BUG vs WARN?" → 위 2분 답.

**함정**: "크래시 난 함수에 버그가 있다"고 단정하는 것, 다른 빌드의 vmlinux로 디코드하는 것.

### Q46 ★★ — 트레이싱 도구 상자: printk, dynamic debug, ftrace, perf, eBPF

**Q.** "A sensor read usually takes 50 µs but occasionally 5 ms. How do you find out why? How can ftrace have near-zero overhead when it's off?"

**한국어로**: 센서 read가 보통 50 µs인데 가끔 5 ms 걸린다. 원인을 어떻게 찾나? ftrace는 꺼져 있을 때 어떻게 오버헤드가 거의 0인가?

**30초 답.** 먼저 숫자로 재현한다 — 앱에서 read 시간을 재고 느린 것만 `trace_marker`로 표시한다. 그다음 같은 ring buffer에 드라이버 `.read` 입구·출구(fprobe), 같은 버스를 쓰는 다른 경로, `sched_switch`/`sched_wakeup`, IRQ 이벤트를 함께 기록하고 느린 read 주변을 본다. 대개 "다른 스레드가 같은 mutex를 쥐고 있었다", "IRQ가 늦게 왔다", "깨워졌는데 CPU를 못 받았다" 중 하나가 보인다. ftrace가 꺼져 있을 때 싼 이유는 컴파일러가 모든 함수 입구에 NOP 자리(arm64 `-fpatchable-function-entry`)를 만들어 두고, 켤 때 커널이 필터에 맞는 함수의 NOP만 `bl ftrace_caller`로 고쳐 쓰기 때문이다. tracepoint도 static key NOP이다.

**2분 답.** M5 랩에서 이 방법으로 5 ms짜리 calibration 스레드가 같은 mutex를 쥐고 있어서 reader가 spin하다 잠드는 것을 `mutex_spin_on_owner`와 `schedule`로 확인했다. 경로가 의심되면 `function_graph`에 `tracing_thresh`를 걸어 느린 호출만 트리로 본다. 도구를 층으로 고른다: printk·`dev_dbg` + dynamic debug(`/proc/dynamic_debug/control`에 `module foo +p` — 재빌드 없이), `/proc`·`/sys`·debugfs 상태 덤프(M2), ftrace(function, function_graph, tracepoint, kprobe/fprobe, irqsoff·wakeup_rt latency tracer), perf(PMU 샘플링, flame graph, `perf sched`), eBPF(bpftrace, libbpf CO-RE — 재부팅·재빌드 없이 커널 안에서 히스토그램으로 집계). kprobe는 arm64에서 BRK 예외라 비싸고(M5 측정 3.3배), 함수 입구면 ftrace 자리를 쓰는 fprobe가 싸다. 작은 타깃에서 bcc는 LLVM 때문에 200 MB급이라 맞지 않고 CO-RE 정적 바이너리를 쓴다(M7). ring buffer는 CPU별 고정 크기에 기본 overwrite라 필터·크기·`snapshot` 트리거로 다룬다. "printk를 넣으면 버그가 사라진다"는 타이밍·레이스 신호라 `trace_printk`나 tracepoint로 바꾸고 lockdep·KCSAN을 켠다. 하드웨어와 맞출 때는 GPIO를 토글하고 로직 분석기로 IRQ 지연을 잰다(M11). 콘솔 레벨(`console_loglevel`)은 콘솔 출력 필터일 뿐 dmesg에는 전부 남는다.

> I reproduce with timestamps, mark the slow calls with `trace_marker`, and record the driver's entry and exit with fprobes plus scheduler and IRQ events in the same ring buffer; ftrace is nearly free when off because every function entry is just a patched NOP.

**꼬리 질문**
- "Tracepoint vs kprobe vs function tracer?" → 미리 박아 둔 의미 있는 지점(안정) vs 아무 명령(비쌈) vs 모든 함수 입구(이름·호출자만).
- "How do you find what's disabling interrupts for too long?" → `irqsoff` tracer: 최장 구간, 시작·끝 함수, 콜스택.
- "Production device, can't reboot or add printk. What do you do?" → eBPF: runqlat → offcputime → 의심 함수에 kprobe/fentry 지연 히스토그램.

**함정**: "printk를 넣고 다시 빌드하겠다"를 첫 답으로 하는 것.

### Q47 ★★★ — Linux는 실시간인가: PREEMPT_RT, 스케줄링, 우선순위 역전

**Q.** "Is Linux real-time? What does PREEMPT_RT actually change? Our 1 kHz control loop sometimes misses its deadline — where do you start?"

**한국어로**: Linux는 실시간인가? PREEMPT_RT는 실제로 무엇을 바꾸나? 1 kHz 제어 루프가 가끔 deadline을 놓친다 — 어디서부터 보나?

**30초 답.** 기본 커널은 soft real-time이다 — 평균은 빠르지만 최악 지연의 상한이 관리되지 않는다. PREEMPT_RT(6.12부터 mainline)를 켜면 `spinlock_t`/`rwlock_t`가 우선순위 상속이 있는 rt_mutex 기반 잠드는 락이 되고, IRQ handler와 softirq가 스레드에서 돌고, printk 콘솔 출력이 전용 스레드로 가서 선점 불가 구간이 아주 작아진다. 그래도 WCET 증명은 아니므로 "부하 상태에서 **측정한 최악값**이 deadline보다 충분히 작은가"로 판단하고, 진짜 hard RT·안전 기능은 MCU에 둔다. 1 kHz 루프는 먼저 매 주기 깨어남 지연과 실행 시간을 히스토그램으로 남겨 스케줄링 문제인지 실행 시간 문제인지 가른다.

**2분 답.** 앱 위생: SCHED_FIFO, CPU 격리(`isolcpus` 또는 cpuset 파티션 + `nohz_full` + `rcu_nocbs` + `irqaffinity`), IRQ affinity, `mlockall` + prefault(N1에서 64 MiB 첫 접근 fault 16384 → 0), `clock_nanosleep(TIMER_ABSTIME)` 주기 루프(다음 목표 = 이전 목표 + period), PI mutex, 루프 안에 printf·malloc·blocking I/O 금지. 플랫폼 최악값은 부하를 걸고 cyclictest·rtla timerlat으로 재고, 원인은 ftrace irqsoff/wakeup_rt·osnoise로 찾는다. 스케줄러 감각: 클래스 순서 stop > deadline > RT > fair(6.6부터 EEVDF) > idle, nice는 비율이고 RT 우선순위는 절대 순서다. 우선순위 역전은 낮은 태스크가 쥔 락을 높은 태스크가 기다리는 동안 중간 태스크가 낮은 태스크를 밀어내는 것이고, `PTHREAD_PRIO_INHERIT`(PI futex → rt_mutex)가 소유자를 부스트한다 — N1 실측에서 PI 없이 65~99 ms 막히던 높은 스레드가 PI를 켜면 22~33 ms(낮은 스레드의 남은 임계 구역)만 기다렸다(QEMU). RT 폭주 방지: 6.12+ fair_server가 굶는 일반 태스크에게 1초당 50 ms를 준다(F1에서 정확히 4.9% 측정) — RT 설계에서 "1초에 한 번 최대 50 ms 끊길 수 있다"를 알고 있어야 한다. 우선순위 배치는 "데이터 흐름 순서 = 우선순위": 루프가 기다리는 센서 IRQ 스레드를 루프보다 위에. 드라이버를 RT로 옮기면 hardirq나 raw lock 안에서 `spin_lock()`·`kmalloc`을 부르던 코드가 "sleeping function called from invalid context"로 터진다. 숫자는 모두 TCG라 실제 보드에서 다시 잰다.

> Stock Linux is soft real-time; PREEMPT_RT turns most spinlocks into PI sleeping locks and threads the interrupts, which bounds latency well enough to measure — I decide from worst-case histograms under load, and keep hard deadlines on an MCU.

**꼬리 질문**
- "What happens if a SCHED_FIFO thread goes into an infinite loop?" → 그 CPU의 fair 태스크가 굶는다. 6.12+ fair_server가 1초에 50 ms만 준다.
- "Hard vs soft real-time?" → 보장의 강도. hard는 놓치면 실패, soft는 품질 저하. 속도와는 별개.
- "When would you use SCHED_DEADLINE?" → 작업마다 CPU 예산을 강제하고 싶을 때(2 ms / 10 ms 예약, admission control). WCET를 알아야 한다.

**함정**: "RT = 빠르다"고 말하는 것, 지연 문제를 nice로 고치려는 것, 평균값만 보고하는 것.

### Q48 ★★ — Linux와 MCU 나누기, remoteproc/rpmsg

**Q.** "What would you put on the MCU versus Linux in our robot? How does Linux load and start firmware on the Cortex-M core of an i.MX8 or STM32MP1, and how do the cores talk?"

**한국어로**: 우리 로봇에서 무엇을 MCU에, 무엇을 Linux에 두겠나? i.MX8이나 STM32MP1의 Cortex-M 코어 펌웨어를 Linux는 어떻게 올리고 시작하며, 코어끼리는 어떻게 통신하나?

**30초 답.** 기능별로 deadline, 놓쳤을 때의 결과, 안전 등급, **Linux가 죽어도 살아야 하는지**를 본다. 전류 루프·PWM·엔코더·E-stop 감시·부팅 직후 출력 상태는 MCU, 1 kHz 관절 제어는 MCU나 (측정해서 여유가 있으면) PREEMPT_RT 격리 코어, 인지·계획·네트워크·OTA는 Linux. 경계로는 setpoint와 상태만 보내고 제어 루프는 경계를 넘지 않게 한다. 이종 SoC에서는 remoteproc 프레임워크가 `request_firmware`로 ELF를 읽고, resource table을 파싱해 carveout·vring·trace 버퍼를 준비하고, `PT_LOAD` 세그먼트를 `da_to_va`로 번역한 주소에 복사한 뒤 `ops->start`로 리셋을 푼다. 통신은 rpmsg — virtio vring(공유 메모리) + mailbox doorbell(알림)이다.

**2분 답.** Linux가 죽으면: MCU가 Linux heartbeat를 deadline으로 감시하다 끊기면 스스로 safe state(램프다운 → PWM off → 브레이크)로 가고 래치한다 — N4 랩에서 앱 SIGSTOP, SIGKILL, 커널 panic 세 경우 모두 마지막 heartbeat 후 50~51 ms(deadline 50 ms)에 SAFE로 갔다. 안전 등급 정지는 하드와이어 E-stop/STO가 따로 있다. rpmsg 경로: `/dev/rpmsgN`에 write → TX 풀의 512 B 버퍼에 16 B 헤더 + 데이터 → vring avail → `virtqueue_kick` → mailbox doorbell, 응답은 반대 방향 vring으로 와서 endpoint 콜백 → `read()`. 새 채널은 name service(주소 53)로 생긴다. 버퍼가 512 B(payload 496 B)라 카메라 버퍼나 1 kHz IMU 스트림은 carveout 링에 두고 rpmsg로는 "인덱스 N까지 썼다" 같은 디스크립터만 보낸다 — NVMe가 데이터는 PRP로 가리키고 큐에는 명령만 넣는 것과 같다. 원격 코어 크래시는 `rproc_report_crash` → coredump → 재로드로 복구되고 rpmsg 채널은 다시 생기니 앱이 재연결해야 한다. 부트로더가 먼저 띄운 코어에는 attach 모드로 리셋 없이 붙는다. 외부 MCU 링크(UART/SPI/CAN)면 COBS 프레이밍 + CRC-32 + seq/ACK, 시간 동기는 4-타임스탬프 PING에서 RTT 최소 샘플만 쓰는 필터(O3에서 전 샘플 사용 시 drift 46% 틀림, 필터로 ±5%).

> Anything that must stay safe when Linux dies goes on the MCU; on a heterogeneous SoC remoteproc loads the ELF using its resource table and rpmsg moves small messages over virtio rings with a mailbox doorbell — bulk data goes in shared carveouts.

**꼬리 질문**
- "Linux crashes — what happens to the motors?" → MCU heartbeat watchdog → 래치된 safe state, 그리고 하드와이어 E-stop.
- "What is the resource table and who writes which fields?" → 펌웨어 ELF의 `.resource_table`. 펌웨어가 필요한 자원을 적고(주소는 ANY), Linux가 vring 주소·notifyid·carveout 주소를 채운다.
- "Why not PREEMPT_RT for everything?" → 최악값 보장이 아니라 측정 기반이고, 부팅 시간·Linux 장애 시 출력·인증 문제가 남는다.

**함정**: 고속 제어 루프를 Linux 유저 공간 ↔ MCU 경계 너머로 닫는 설계, "remoteproc이 Linux 장애도 처리한다"는 답.

### Q49 ★★ — CAN과 SocketCAN

**Q.** "Explain the SocketCAN architecture. A CAN bus on our robot keeps going bus-off — how do you debug it?"

**한국어로**: SocketCAN 구조를 설명하라. 로봇의 CAN 버스가 계속 bus-off가 된다 — 어떻게 디버그하나?

**30초 답.** SocketCAN은 CAN 컨트롤러를 네트워크 인터페이스(`can0`)로 만든 것이다. 유저는 `PF_CAN` 소켓(RAW, BCM, ISO-TP, J1939)을 쓰고, af_can 코어가 장치별 수신 필터로 프레임을 소켓에 나눠 주며, 송신은 qdisc를 거쳐 드라이버의 `ndo_start_xmit`으로 간다. 드라이버는 can_dev 라이브러리로 비트 타이밍 계산, netlink 설정(`ip link set can0 type can bitrate 500000`), 에러 상태(error-active → warning → passive → bus-off), restart, echo skb를 공유한다. bus-off는 먼저 데이터를 모은다: `ip -details -statistics link show can0`의 bus-off·error 카운터와 TEC/REC, `candump -e`의 에러 프레임 종류(bit/stuff/form/ACK/CRC). **TEC만 오르면 이 노드의 송신 문제, REC가 오르면 남의 프레임을 못 읽는 문제**다.

**2분 답.** 그다음 물리: 양 끝 120 Ω 두 개 = 60 Ω 종단, 접지·차동 전압, scope로 비트 폭과 에러 플래그 위치. 타이밍: 모든 노드의 bitrate·샘플 포인트·클럭 정확도 일치 — Linux `can_calc_bittiming()`은 CiA 권장 샘플 포인트(≤ 500 kbit/s 87.5%, ≤ 800 k 80%, 그 이상 75%)를 목표로 고르고, 예를 들어 40 MHz 클럭 500 k면 brp 1, tq 25 ns, 80 tq, 87.5%다(I10). 모터 구동 때만 나면 EMI. `restart-ms`는 원인을 찾는 동안 증상을 가리므로 끄거나 카운터를 기록한다. 케이블을 뽑으면 bus-off가 될까? 아니다 — 혼자 남은 송신자는 ACK 에러만 받고, error-passive에서 ACK 에러는 TEC를 올리지 않아 passive에 머문다(I10 §6 실측). echo skb는 드라이버가 **TX-complete 인터럽트에서** 로컬 소켓에 올려서 로컬 앱이 보는 순서가 버스의 실제 순서와 같다. SPI CAN 컨트롤러(MCP2518FD)는 threaded IRQ + 프레임당 SPI 왕복 여러 번이라 고부하에서 RX overflow가 나기 쉽다. 필터 함정: id `0x123`, mask `0x7FF`는 29비트 0x123과 RTR 프레임도 통과시키므로 mask에 `CAN_EFF_FLAG | CAN_RTR_FLAG`를 넣는다. 10 ms 주기 송신은 BCM이 6.18에서 "지금 + 간격"으로 누적돼 평균 10.11 ms였고, `clock_nanosleep(TIMER_ABSTIME)` + SCHED_FIFO 루프는 평균 10.000 ms였다(VM). 300 B 펌웨어 조각은 ISO-TP(`CAN_ISOTP` 소켓)로. 하드웨어 없이는 vcan·vxcan·canplayer로 테스트하되, vcan에는 에러 상태가 없다.

> SocketCAN makes the controller a netdev and frames go through sockets with kernel-side filters; for bus-off I read TEC/REC and error-frame classes first, then check termination, bit timing and EMI on the wire.

**꼬리 질문**
- "What does the echo skb do?" → TX 완료 시점에 로컬 루프백 → 실제 버스 순서·시각과 일치, 중재에 진 프레임은 안 보임.
- "How would you send a CAN message every 10 ms reliably?" → BCM은 프로세스 스케줄링과 무관하지만 누적 지연, 정밀하면 ABSTIME 루프.
- "How do you test without hardware?" → vcan/vxcan/can-gw/canplayer, 에러 처리는 slcan 주입이나 HIL.

**함정**: `restart-ms`로 bus-off를 "해결"했다고 말하는 것, vcan으로 에러 처리까지 검증했다고 말하는 것.

### Q50 ★ — 카메라 파이프라인: CSI-2, V4L2, media controller

**Q.** "Walk me through how a frame gets from an image sensor into DRAM on an embedded Linux SoC. STREAMON returns EPIPE — how do you debug it?"

**한국어로**: 임베디드 Linux SoC에서 이미지 센서의 프레임이 DRAM까지 가는 과정을 설명하라. STREAMON이 EPIPE를 돌려주면 어떻게 디버그하나?

**30초 답.** 센서가 행마다 노출·ADC를 하고 행마다 CSI-2 long packet(헤더 DI·WC·ECC, payload, CRC-16)으로 만들어 D-PHY lane으로 보낸다(프레임은 FS short packet으로 시작해 FE로 끝). SoC의 CSI-2 수신기가 ECC·CRC를 검사하고 VC/DT로 스트림을 나눠 ISP나 DMA로 넘기고, ISP가 RAW Bayer를 YUV로 만들어 DMA가 DRAM 버퍼에 쓴다. CPU는 I2C로 센서 모드·노출·게인을 쓰고 ISP 통계로 3A를 돌릴 뿐 픽셀 경로에는 없다. Linux에서는 센서·수신기·ISP가 `v4l2_subdev`, DMA 끝단이 video node(`/dev/videoN`, vb2 큐)이고 media controller가 그래프로 엮는다. `EPIPE`는 link validation 실패다 — 켜진 링크의 양끝 pad 포맷(크기, mbus code, field)이 다른 곳을 `media-ctl -p`로 찾는다.

**2분 답.** lane과 link frequency 계산: 필요한 lane 비트레이트 = pixel_rate × bpp ÷ lane 수(pixel_rate = HTS × VTS × fps), D-PHY는 DDR이라 link frequency는 그 절반이다 — IMX219 1080p30 RAW10은 182.4 Mpix/s × 10 ÷ 2 lane = 912 Mb/s, link freq 456 MHz(노트 Q1 §4). 이 값을 DT endpoint의 `link-frequencies`에, 레인은 `data-lanes`에 쓰고, 양쪽 `remote-endpoint`로 엮으면 수신기가 v4l2-async notifier로 센서 subdev를 기다렸다가 링크를 만든다. EPIPE 디버그는 `v4l2-subdev.c`·`mc-entity.c` dynamic debug로 어느 링크가 어떤 값으로 실패했는지 보고 센서부터 하류로 `media-ctl -V`·`v4l2-ctl -v`로 맞춘다 — I5에서 재현했을 때 두 번째 원인은 스트리밍하지 않는 다른 video node가 같은 센서에 켜진 링크로 붙어 파이프라인에 포함된 것이었다. vb2 버퍼 소유권은 DEQUEUED(유저) → QUEUED(vb2) → ACTIVE(드라이버·DMA) → DONE → DQBUF로, SSD 디스크립터 링과 같은 개념이다. 드롭은 DQBUF 개수가 아니라 `sequence` 틈으로 세고, 버퍼 수는 소비자의 최악 멈춤으로 정한다(노트 Q2 §5: 느린 소비자에서 버퍼 2개 17%, 8개 2.6% 손실). 인코더·GPU·NPU로는 `VIDIOC_EXPBUF` dma-buf로 복사 없이 넘기되 버퍼를 가장 제약이 큰 장치(연속 메모리 필요) 기준으로 CMA/dma-heap에서 할당한다. ISP가 있는 SoC는 매 프레임 3A가 필요해서 libcamera(pipeline handler + IPA)가 유저 공간에서 맡는다. 타임스탬프는 `CLOCK_MONOTONIC`, 플래그로 프레임 시작(SoE)인지 끝(EoF)인지 확인한다. 빠른 드론의 VIO에는 global shutter가 기본이다(rolling은 1080p30에서 위아래 약 20 ms 차이).

> Pixels flow sensor → CSI-2 receiver → ISP → DMA without the CPU; Linux models each block as a subdev in a media graph, and EPIPE on STREAMON means two linked pads disagree on format.

**꼬리 질문**
- "The camera driver probes but you get no frames. How do you debug?" → 층별로: data lane을 scope로(LP-11에 머물면 센서가 안 보냄), 수신기 ECC/CRC 카운터, DT `data-lanes`·`link-frequencies`·continuous clock, 그다음 포맷과 링크 검증.
- "How do you detect dropped frames?" → `v4l2_buffer.sequence` 틈. 버퍼를 늘려 줄면 소비자, 그대로면 센서·CSI·ISP 쪽.
- "Why libcamera if V4L2 exists?" → V4L2는 블록을 노출만 한다. ISP 3A 루프와 SoC별 그래프 설정을 유저 공간에서 표준화.

**함정**: `link-frequencies`에 lane 비트레이트를 그대로 쓰는 것(DDR이라 절반), DQBUF 개수로 드롭을 세는 것.

| `device_node` / `fwnode_handle` | 펼쳐진 DT 노드, 펌웨어 중립 핸들 | 13–17 | D8 §2·§7 |
| `irq_desc` + `irq_domain` + `irqaction` | Linux IRQ 하나, hwirq ↔ virq 표, 등록된 핸들러 | 27, 28 | F6 §3·§11, H6 §1 |
| `wait_queue_head_t` + `completion` | 잠든 태스크 목록, 한 번 끝남 알림 | 29, 36 | F3 §2·§7 |
| `spinlock_t` / `mutex` / RCU | 동시성 도구 | 24, 25 | F4 §3·§5·§11 |
| `dma_addr_t` + `sg_table` + `dma_buf` | 장치 주소, 흩어진 버퍼, 공유 버퍼 | 31, 40, 50 | H9 §1·§6·§11 |

그림으로 다시 연결하면: 유저의 `read()`(문항 1)는 `struct file`(3)을 거쳐 드라이버 `.read`(34)로 가고, 데이터가 없으면 wait queue(29)에서 잠들고, 장치 IRQ(27)의 스레드가 I2C(38)로 데이터를 읽어 링에 넣고 깨운다. 그 링은 spinlock(24)으로 보호되고, 버퍼가 크면 DMA(40)와 mmap(6)으로 복사를 없앤다. 장치와 드라이버의 짝은 DT(14)와 device model(32)이 맺고, 자원은 devm(33)이 정리한다. 이 한 문단이 R2 "무슨 일이 일어나나" 시리즈의 뼈대다.

```text
	} else if (new->handler == irq_default_primary_handler &&
		   !(desc->irq_data.chip->flags & IRQCHIP_ONESHOT_SAFE)) {
		/*
		 * The interrupt was requested with handler = NULL, so
		 * we use the default primary handler for it. But it
		 * does not have the oneshot flag set. In combination
		 * with level interrupts this is deadly, because the
		 * default primary handler just wakes the thread, then
		 * the irq lines is reenabled, but the device still
		 * has the level irq asserted. Rinse and repeat....
		 *
		 * While this works for edge type interrupts, we play
		 * it safe and reject unconditionally because we can't
		 * say for sure which type this interrupt really
		 * has. The type flags are unreliable as the
		 * underlying chip implementation can override them.
		 */
		pr_err("Threaded irq requested with handler=NULL and !ONESHOT for %s (irq %d)\n",
		       new->name, irq);
		ret = -EINVAL;
		goto out_unlock;
	}
```

출력에서 볼 것: 예외는 칩이 `IRQCHIP_ONESHOT_SAFE`(MSI 같은)일 때뿐이다. 주석이 문항 27의 "level IRQ 폭풍" 설명 그대로다.

## 14. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| atomic context | 잠들면 안 되는 구간 | 인터럽트 문맥 + spinlock·preempt/IRQ/BH 금지·RCU 읽기 구간 |
| threaded IRQ | 스레드에서 도는 IRQ 처리 | `request_threaded_irq`, `irq/N-name` FIFO 50, 잠들 수 있음 |
| devres / devm | 장치 관리 자원 | probe 실패·unbind 때 역순 자동 해제 |
| deferred probe | 미뤄진 probe | 공급자가 없어 `-EPROBE_DEFER`, 다른 bind 때 재시도 |
| fw_devlink | 펌웨어 기반 장치 링크 | DT phandle로 consumer–supplier 의존을 자동 생성 |
| PAN | Privileged Access Never | 커널의 일반 load/store로 유저 메모리 접근을 HW가 차단 |
| COW | copy-on-write | 쓰는 순간에만 페이지를 복사(fork, MAP_PRIVATE) |
| PSS | proportional set size | 공유 페이지를 공유자 수로 나눈 메모리 사용량 |
| PSCI | Power State Coordination Interface | OS가 EL3 펌웨어에 CPU on/off·reset을 요청하는 표준 |
| CMA | Contiguous Memory Allocator | 큰 물리 연속 DMA 버퍼를 위해 영역을 빌려 주고 돌려받음 |
| PREEMPT_RT | 실시간 선점 모델 | spinlock → PI sleeping lock, IRQ 스레드화, 6.12 mainline |
| echo skb | CAN 송신 루프백 | TX 완료 시점에 로컬 소켓에 송신 프레임을 올림 |
| link validation | media 링크 검증 | STREAMON 때 연결된 pad 포맷 비교, 불일치면 `-EPIPE` |
| bootcount | 부팅 시도 카운터 | `bootlimit` 초과 시 `altbootcmd`로 롤백 |

## 15. 요약 & 체크리스트

1차 기술 면접의 개념 질문은 결국 다섯 갈래로 모인다: 유저와 커널의 경계(문항 1–7, 21), 부팅과 하드웨어 기술(8–17), 커널 코드의 규칙과 문맥(18–31), 드라이버 프레임워크와 버스(32–41), 시스템 단위 주제와 디버깅(42–50). 모든 답은 같은 틀 — 30초 정의와 결정 기준, 그다음 커널 이름과 직접 잰 숫자, 그다음 꼬리 질문 — 으로 말한다. 가장 많이 떨어지는 지점은 지식이 아니라 문맥 규칙("그거 IRQ에서 불러도 되나?")과 측정 습관("어떻게 확인하나?")이므로, 그림 3과 §10 표를 마지막에 한 번 더 본다.

- [ ] ★★★ 24문항의 30초 답을 영어로, 각각 30초 안에 말할 수 있다
- [ ] syscall 경로를 `svc #0`부터 `f_op->read`까지 함수 이름으로 말할 수 있다
- [ ] 부트 사슬(ROM → SPL → BL31 → U-Boot → kernel → PID 1)과 각 단계의 존재 이유를 말할 수 있다
- [ ] "DT에 있는데 probe가 안 된다"를 5단계 사슬로 진단할 수 있다
- [ ] 모든 커널 API에 "잠들 수 있나 / 어느 문맥에서 부르나" 꼬리표를 붙일 수 있다
- [ ] spinlock vs mutex, `_irqsave`가 필요한 이유를 데드락 시나리오로 설명할 수 있다
- [ ] threaded IRQ + `IRQF_ONESHOT`이 왜 필요한지 level IRQ 폭풍으로 설명할 수 있다
- [ ] probe 자원 획득 순서와 devm 해제 시점의 함정을 설명할 수 있다
- [ ] coherent vs streaming DMA와 arm64 캐시 clean/invalidate 지점을 말할 수 있다
- [ ] Oops를 ESR·FAR·faddr2line·레지스터 순서로 읽을 수 있다
- [ ] "Linux는 실시간인가"에 측정 기반 판단 + MCU 분할로 답할 수 있다
- [ ] 각 답에 출처 노트의 실측 숫자 하나를 "TCG/VM 기준"이라는 단서와 함께 붙일 수 있다
