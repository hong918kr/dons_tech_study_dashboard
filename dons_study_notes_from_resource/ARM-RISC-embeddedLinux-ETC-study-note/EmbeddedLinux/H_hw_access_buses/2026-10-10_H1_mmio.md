# H1. MMIO — `ioremap`, `readl`/`writel`(+`_relaxed`), 배리어, `/dev/mem`이 나쁜 이유 (bare-metal `volatile` 포인터를 Linux 어휘로)

> **이 노트를 다 읽으면**: 물리 레지스터 주소가 DT/BAR → `request_mem_region` → `ioremap`(Device-nGnRE PTE) → 커널 VA → `readl`로 이어지는 길을 그림과 실제 출력으로 설명할 수 있다 · `devm_platform_ioremap_resource`/`devm_ioremap`/`pcim_iomap_region`과 `readl`/`_relaxed`/`__raw_readl`/`ioread32be` 중 맞는 것을 고르고 각각이 arm64에서 어떤 명령이 되는지 objdump로 보일 수 있다 · `readl_poll_timeout`으로 "비트 기다리기"를 타임아웃과 함께 짜고, 공유 레지스터 RMW를 락으로 지킬 수 있다 · `/dev/mem`(devmem)이 왜 위험한지, STRICT_DEVMEM·`IORESOURCE_EXCLUSIVE`·UIO가 각각 무엇을 막고 허용하는지 실험 결과로 말할 수 있다
> **왜 필요한가**: 레지스터 드라이버의 첫 줄이 매핑이고, 면접에서는 "왜 포인터로 바로 못 읽나요?", "`readl`과 `readl_relaxed` 차이?", "`/dev/mem`으로 하면 안 되나요?", "레지스터 비트를 어떻게 기다리나요?"가 나온다. bring-up 현장에서는 `devmem`으로 레지스터를 찔러 보는 일이 매일 있다
> **Don 기준 난이도**: 레지스터 맵·비트 조작·폴링·접근 폭·PCIe posted write·read-back은 SSD/RF 펌웨어에서 매일 하던 일이다 / 새로 배울 것은 "물리 주소는 직접 못 쓴다(MMU)", 주소 공간 소유권(`/proc/iomem`), `__iomem`과 sparse, 접근자 가족, 커널의 대기 규칙(잘 수 있나 없나)
> **선행 노트**: D4(DT `reg` → resource), E3(커널 모듈), F4(spinlock), F5(배리어 — `readl`/`writel` 내부의 `dmb`, posted write, doorbell 패턴은 F5 §5·§6에서 다 했다), G3(platform driver·devres) — H2(regmap), H9(DMA), H11(PCIe 깊게)로 이어진다

## 0. 큰 그림 — 이게 왜 필요한가

Don이 SSD 컨트롤러 펌웨어에서 레지스터를 만지던 코드는 대략 이랬다.

```c
#define NAND_CTRL_BASE  0x40010000u
#define NAND_STATUS     (*(volatile uint32_t *)(NAND_CTRL_BASE + 0x20))

while (NAND_STATUS & BUSY)      /* 비트 기다리기 */
	;
```

물리 주소 상수를 `volatile` 포인터로 캐스팅해서 바로 읽는다. MPU가 그 영역을 "Device"로 설정해 두었으니 캐시도 안 타고 순서도 지켜진다. 이게 bare-metal MMIO의 전부다.

Linux 커널 드라이버에서는 같은 일을 이렇게 한다.

```c
base = devm_platform_ioremap_resource(pdev, 0);   /* 주소는 DT가 주고, 매핑은 커널이 */
if (IS_ERR(base))
	return PTR_ERR(base);
ret = readl_poll_timeout(base + STATUS, val, !(val & BUSY), 10, 1000);
```

달라진 것이 네 가지다.

1. **주소를 하드코딩하지 않는다.** 물리 주소는 Device Tree의 `reg`(D4)나 PCI BAR(H11)에서 온다. 같은 드라이버가 다른 보드에서 그대로 돈다.
2. **물리 주소를 바로 쓸 수 없다.** 커널도 MMU를 켜고 가상 주소로 돈다. 그래서 물리 레지스터를 가상 주소 공간 어딘가에 **매핑**(`ioremap`)해야 한다. 이 매핑의 페이지 테이블 엔트리에 "Device 메모리" 속성이 들어간다 — Don이 MPU로 하던 설정을 이제 페이지 테이블이 한다.
3. **주소 공간에 주인이 있다.** 커널은 "0x09010000~0x09010fff는 rtc-pl031 드라이버 것"이라는 소유권 트리(`/proc/iomem`)를 관리한다. 남의 레지스터를 매핑하려 하면 `-EBUSY`가 난다.
4. **포인터를 직접 역참조하지 않는다.** `readl()`/`writel()` 같은 접근자를 쓴다. 접근 폭·엔디언·배리어·(가상화 환경의) 명령 형태를 접근자가 책임진다. 그리고 "기다리기"는 무한 루프가 아니라 타임아웃이 있는 `readl_poll_timeout()`이다.

그림 1 — bare-metal은 물리 주소를 바로 쓰고 MPU가 속성을 준다. Linux는 DT/BAR에서 주소를 얻고, 소유권을 확인하고, 페이지 테이블에 Device 속성으로 매핑한 **가상 주소**로 접근한다. 오른쪽의 VA와 MAIR 값은 이 노트의 실험(§1.3, §2)에서 나온 실제 값이다.

Embedded Linux 엔지니어가 이 주제를 만나는 장면:

- **SoC IP 블록 드라이버**: 타이머, PWM, 워치독, ADC, 자체 FPGA 레지스터 블록 — `devm_platform_ioremap_resource` + `readl`/`writel` + `readl_poll_timeout`이 코드의 대부분이다.
- **PCIe 장치 드라이버**: NVMe, Wi-Fi, AI 가속기의 BAR — `pcim_iomap_region` + doorbell 쓰기(F5 §6).
- **bring-up**: 드라이버를 쓰기 전에 `devmem 0x30200000`으로 레지스터 값부터 확인한다. "칩 ID가 0xffffffff로 읽혀요"는 클럭 게이트(H3)나 PCIe 링크 다운의 신호다.
- **코드 리뷰**: `*(u32 *)base` 같은 직접 역참조, 타임아웃 없는 `while (readl(..) & BUSY);`, 락 없는 공유 레지스터 RMW를 잡아낸다.

QEMU `edu` 장치의 레지스터(VM의 `/usr/share/doc/qemu-system-common/specs/edu.html`에서 확인, PCI ID `1234:11e8`, BAR0 = 1 MB MMIO):

| 오프셋 | 접근 | 이름 | 동작 |
|---|---|---|---|
| 0x00 | RO | identification | `0xRRrr00ed` (RR = major, rr = minor) |
| 0x04 | RW | liveness | 쓴 값의 비트 반전(`~`)이 읽힌다 |
| 0x08 | RW | factorial | n을 쓰면 계산 후 n!로 바뀐다 |
| 0x20 | RW | status | bit0 = 계산 중(RO), bit7 = 끝나면 IRQ |
| 0x24 | RO | IRQ status | 올라간 인터럽트 값들의 OR |
| 0x60 / 0x64 | WO | IRQ raise / ack | 값을 OR해서 올림 / 지움 |
| 0x80~0x98 | RW | DMA src/dst/count/cmd | DMA 엔진 (H9) |

그리고 문서의 한 줄: **"Only size == 4 accesses are allowed for addresses < 0x80. size == 4 or size == 8 for the rest."** §3.5에서 이걸 어겨 본다.

## 1. 물리 주소를 가상 주소로 — `ioremap` 가족

### 1.1 직관 — "커널도 MMU 뒤에 산다"

Cortex-R/M에서는 CPU가 내는 주소가 곧 버스 주소였다. Cortex-A에서 Linux가 돌면 커널 코드도 **가상 주소**로 실행된다. 커널이 직접 쓸 수 있는 주소는 페이지 테이블에 있는 것뿐이다.

- RAM은 부팅 때 **linear map**(물리 RAM 전체를 고정 오프셋으로 매핑한 구간)에 다 올라가 있다. `kmalloc`이 돌려주는 `ffff0000...` 주소가 여기다. `virt_to_phys()`는 오프셋 빼기다.
- **장치 레지스터는 linear map에 없다.** 필요할 때 드라이버가 `ioremap(phys, size)`을 불러, vmalloc 영역의 빈 가상 주소 구간을 잡고, 그 PTE들이 물리 레지스터 페이지를 가리키게 하면서 Device 속성을 박는다. 돌려받는 것은 `void __iomem *` — "MMIO 주소 공간의 포인터"라는 표시가 붙은 가상 주소다.

비유: bare-metal에서 MPU region 하나를 "base 0x09010000, size 4 KB, Device, XN"으로 설정하던 일을, Linux에서는 `ioremap()` 한 번이 페이지 테이블 엔트리로 한다. 차이는 주소가 **바뀐다**는 것이다 — 물리 0x09010000이 커널 VA `ffff80008002d000`으로 보인다.

### 1.2 API 지도 — 무엇을 언제 쓰나

| API | 하는 일 | 소유권(request) | 해제 | 언제 |
|---|---|---|---|---|
| `ioremap(phys, size)` | 매핑만 | 안 함 | `iounmap()` 직접 | 아주 이른 부팅 코드, 특수 경우 |
| `devm_ioremap(dev, phys, size)` | 매핑만 | 안 함 | 장치 해제 때 자동 | 남과 공유하는 레지스터 (주의해서) |
| `devm_ioremap_resource(dev, res)` | request + 매핑 | 함 → 충돌 시 `-EBUSY` | 자동 | `struct resource`를 이미 갖고 있을 때 |
| `devm_platform_ioremap_resource(pdev, i)` | resource i를 찾아 위와 같이 | 함 | 자동 | **platform 드라이버의 표준** |
| `devm_platform_get_and_ioremap_resource(pdev, i, &res)` | 위 + resource 포인터도 돌려줌 | 함 | 자동 | 물리 주소(DMA용 FIFO 주소 등)도 필요할 때 |
| `of_iomap(np, i)` | DT 노드에서 바로 매핑 | 안 함 | `iounmap()` | 드라이버 모델 밖(irqchip, clk 초기화) |
| `pcim_iomap_region(pdev, bar, name)` | BAR request + 매핑 | 함 | 자동 | **PCI 드라이버의 표준 (6.x)** |
| `pci_iomap(pdev, bar, max)` / `pcim_iomap()` | BAR 매핑만 | 안 함 | 직접 / 자동 | request를 따로 할 때 |

반환값 규칙이 다르다는 것을 기억한다. `ioremap()`/`devm_ioremap()`/`pci_iomap()`/`pcim_iomap()`은 실패 시 **NULL**, `devm_ioremap_resource()` 계열과 `pcim_iomap_region()`은 **`ERR_PTR`**(`IS_ERR()`로 검사)이다. 섞어서 검사하면 실패를 놓친다.

PCI 쪽 주의: 예전 코드와 블로그에 많이 나오는 `pcim_iomap_regions(pdev, mask, name)` + `pcim_iomap_table()`은 랩 커널 6.18의 `drivers/pci/devres.c`에 "DEPRECATED. Do not use it in new code. Use pcim_iomap_region() instead."라고 적혀 있다. 6.11 무렵 PCI devres를 정리하면서 바뀐 부분이다(정확한 버전은 확인하지 않았다 — 랩 소스에서 확인한 것은 6.18의 상태다). 그래도 드라이버 트리에는 아직 `pcim_iomap_regions(`가 90줄 남아 있다(§11.3).

### 1.3 예제 1 — 이미 주인이 있는 PL031을 두 번째 드라이버로 매핑 (`h1_rtc`)

무엇을 확인하나: `devm_platform_ioremap_resource()`가 `-EBUSY`로 실패하는 이유, `devm_ioremap()`로 우회하면 무엇이 되는지, 매핑이 진짜 PL031을 가리키는지(PrimeCell ID와 RTC 값).

QEMU virt의 PL031 RTC(0x09010000)는 부팅 때 커널의 `rtc-pl031` 드라이버가 이미 잡고 있다. D4가 PL061 GPIO로 했던 실험을 RTC로 다시 한다. DT에 **같은 주소를 가리키는 노드를 하나 더** 넣어 우리 platform 드라이버를 매칭시킨다.

```sh
#!/bin/sh
# mkdtb.sh — virt.dts에 "h1-rtc@9010000" 노드를 하나 더 넣어 h1.dtb를 만든다
set -e
W=/var/tmp/H1; mkdir -p $W
head -n -1 /var/lab/out/virt.dts > $W/h1.dts       # 마지막 "};" 제거
cat >> $W/h1.dts <<'DTS'

	h1-rtc@9010000 {
		compatible = "h1,rtc-peek";
		reg = <0x00 0x9010000 0x00 0x1000>;
	};
};
DTS
dtc -q -I dts -O dtb -o $W/h1.dtb $W/h1.dts && ls -l $W/h1.dtb
```

`compatible`에 `"arm,primecell"`을 넣지 않았으니 이 노드는 AMBA 버스가 아니라 platform 버스의 장치가 된다(D3).

```c
// SPDX-License-Identifier: GPL-2.0
/* h1_rtc: rtc-pl031이 이미 쓰고 있는 PL031을 "두 번째 드라이버"로 매핑해 본다 */
#include <linux/module.h>
#include <linux/mod_devicetable.h>
#include <linux/platform_device.h>
#include <linux/io.h>

#define RTCDR     0x000		/* Data: 현재 시각(초) */
#define RTCLR     0x008		/* Load */
#define RTCCR     0x00c		/* Control: bit0 = start */
#define PERIPHID0 0xfe0		/* PrimeCell ID: fe0..fec, ff0..ffc (각 하위 8비트) */

static int h1_rtc_probe(struct platform_device *pdev)
{
	struct device *dev = &pdev->dev;
	struct resource *res = platform_get_resource(pdev, IORESOURCE_MEM, 0);
	void __iomem *base;
	u32 pid = 0, cid = 0;
	int i;

	if (!res)
		return -EINVAL;
	base = devm_platform_ioremap_resource(pdev, 0);	/* request + ioremap */
	if (IS_ERR(base)) {
		dev_info(dev, "devm_platform_ioremap_resource: %pe\n", base);
		base = devm_ioremap(dev, res->start, resource_size(res)); /* ioremap만 */
		if (!base)
			return -ENOMEM;
	}
	dev_info(dev, "%pR -> VA %px\n", res, base);
	for (i = 0; i < 4; i++) {
		pid |= (readl(base + PERIPHID0 + 4 * i) & 0xff) << (8 * i);
		cid |= (readl(base + PERIPHID0 + 0x10 + 4 * i) & 0xff) << (8 * i);
	}
	dev_info(dev, "PeriphID=0x%08x (part 0x%03x, designer 0x%02x, rev %u) PCellID=0x%08x\n",
		 pid, pid & 0xfff, (pid >> 12) & 0xff, (pid >> 20) & 0xf, cid);
	dev_info(dev, "RTCDR=%u RTCLR=%u RTCCR=0x%x\n",
		 readl(base + RTCDR), readl(base + RTCLR), readl(base + RTCCR));
	return 0;
}

static const struct of_device_id h1_rtc_of[] = {
	{ .compatible = "h1,rtc-peek" },
	{ }
};
MODULE_DEVICE_TABLE(of, h1_rtc_of);

static struct platform_driver h1_rtc_drv = {
	.probe = h1_rtc_probe,
	.driver = { .name = "h1_rtc", .of_match_table = h1_rtc_of },
};
module_platform_driver(h1_rtc_drv);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H1: read PL031 registers through a second mapping");
```

`%px`는 포인터를 해시하지 않고 그대로 찍는다(`%p`는 보안상 해시한다). 학습용으로만 쓴다 — 실제 드라이버에서 커널 주소를 로그에 내보내면 KASLR이 무력해진다.

그림 2 — 커널의 물리 주소 소유권 트리. 버스·장치가 등록한 자원 아래에 드라이버가 `request_mem_region`으로 BUSY 깃발을 꽂는다. 겹치는 BUSY가 있으면 두 번째 request는 `-EBUSY`. `ioremap`/`devm_ioremap`은 이 트리를 보지 않는다 — 깃발은 **약속**이지 하드웨어 보호가 아니다.

핵심 정리:

- `request_mem_region(start, n, name)` = 트리에 BUSY 노드 추가. `release_mem_region()` = 제거. `devm_` 버전은 장치 해제 때 자동 제거.
- 이 깃발은 **협조적 잠금**이다. 같은 레지스터를 두 드라이버가 몰래 건드리는 사고(Don이 펌웨어에서 "두 태스크가 같은 페리페럴을 init"하던 버그)를 probe 시점에 잡아 준다. 하지만 `ioremap()`만 하는 코드나 `/dev/mem`(STRICT 설정에 따라)은 막지 못한다.
- 그래서 **`devm_ioremap()`으로 우회하는 것은 정당한 이유가 있을 때만**이다. 예: 한 레지스터 블록을 여러 드라이버가 나눠 쓰는 SoC(시스템 컨트롤러)에서는 우회 대신 syscon + regmap(H2)으로 한 주인이 매핑하고 나머지가 빌려 쓰는 것이 정석이다.
- `/proc/iomem`은 bring-up 첫날 볼 파일이다. "내 드라이버가 probe에서 -EBUSY"면 여기서 누가 먼저 잡았는지 본다. 유저가 root가 아니면 주소가 0으로 가려진다.

### 1.5 함정

- `devm_ioremap_resource()`가 실패했는데 `if (!base)`로 검사 — `ERR_PTR`은 NULL이 아니라서 통과한다. 그 다음 `readl(base)`에서 이상한 주소 접근으로 oops. **`IS_ERR()`로 검사하고 `PTR_ERR()`을 돌려준다.**
- DT `reg` 크기를 레지스터 맵보다 작게 적음 — 매핑 범위 밖 오프셋 접근은 다른 매핑(또는 guard page)을 친다. 4 KB 단위로 매핑되니 대개 우연히 동작하다가, 블록이 페이지 경계를 넘을 때 터진다.
- 두 드라이버가 같은 블록을 각자 `devm_ioremap()` — 둘 다 성공하고, 동시에 RMW하면 §6의 경쟁이 생긴다.

## 2. 메모리 속성 — Device-nGnRE와 친척들

### 2.1 `ioremap` 변형과 arm64 속성 (랩 소스에서 확인)

랩 소스 `arch/arm64/include/asm/io.h`(6.18.55):

```c
#define ioremap(addr, size)	\
	__ioremap_prot((addr), (size), __pgprot(PROT_DEVICE_nGnRE))
#define ioremap_wc(addr, size)	\
	__ioremap_prot((addr), (size), __pgprot(PROT_NORMAL_NC))
#define ioremap_np(addr, size)	\
	__ioremap_prot((addr), (size), __pgprot(PROT_DEVICE_nGnRnE))
...
static inline void __iomem *ioremap_cache(phys_addr_t addr, size_t size)
{
	if (pfn_is_map_memory(__phys_to_pfn(addr)))
		return (void __iomem *)__phys_to_virt(addr);

	return __ioremap_prot(addr, size, __pgprot(PROT_NORMAL));
}
```

`PROT_DEVICE_nGnRE`는 `arch/arm64/include/asm/pgtable-prot.h`에서 `PROT_DEFAULT | PTE_PXN | PTE_UXN | PTE_WRITE | PTE_ATTRINDX(MT_DEVICE_nGnRE)`이고, `MT_DEVICE_nGnRE = 4`(`asm/memory.h`), `MAIR_ATTR_DEVICE_nGnRE = 0x04`(`asm/sysreg.h`)이다. 즉 PTE의 AttrIndx 필드에 4를 넣고, 부팅 때 `MAIR_EL1`의 Attr4 바이트에 0x04(Device-nGnRE)를 넣어 둔다(`arch/arm64/mm/proc.S`의 `MAIR_EL1_SET`). PXN/UXN이 켜져 있어 레지스터 영역에서 명령을 실행할 수 없다 — Don이 MPU에서 XN을 켜던 것과 같다.

| 함수 | arm64 속성 (MAIR) | 합치기(G) / 재배치(R) / early ack(E) | 쓰임 |
|---|---|---|---|
| `ioremap()` | Device-nGnRE (0x04) | 금지 / 같은 장치끼리 금지 / 허용 | **레지스터 — 기본값** |
| `ioremap_np()` | Device-nGnRnE (0x00) | 금지 / 금지 / 금지 (non-posted) | 쓰기 완료 응답이 장치에서 와야 하는 플랫폼 (Apple M1 등) |
| `ioremap_wc()` | Normal Non-Cacheable (0x44) | 허용 / 허용 / — | 프레임버퍼, 큰 쓰기 버퍼 (write-combining) |
| `ioremap_cache()` | Normal WB (0xff) | 캐시됨 | 펌웨어 테이블 같은 "메모리처럼 쓰는" 영역. RAM이면 linear map 주소를 그대로 돌려준다 |

nGnRE의 세 글자 의미와 posted write는 F5 §5.1에서 자세히 했다. 여기서는 하나만 다시 짚는다: **E(early write acknowledgement)** 때문에 `writel()`이 끝났다는 것이 "장치에 도착했다"는 뜻이 아니다. 장치 도착을 확인하려면 같은 장치를 `readl()`로 읽는다(F5 §5.4).

`ioremap_np()`는 DT에서 오기도 한다. `lib/devres.c`의 `__devm_ioremap_resource()`는 resource에 `IORESOURCE_MEM_NONPOSTED` 플래그가 있으면 자동으로 `DEVM_IOREMAP_NP` 타입을 고른다. 이 플래그는 DT 노드(또는 부모 버스 노드)의 `nonposted-mmio` 속성에서 온다 — 랩 소스 `drivers/of/address.c`의 `of_mmio_is_nonposted()`가 그 속성을 본다. Apple Silicon 지원 때 들어온 것으로 기억한다(이 노트에서 실행해 보지는 않았다).

### 2.2 유저 매핑의 속성 — `/dev/mem`과 sysfs는 다르다

유저스페이스가 레지스터를 `mmap`할 때도 같은 질문이 있다. 랩 소스에서 확인한 것:

```c
/* arch/arm64/mm/mmu.c — /dev/mem의 mmap이 쓰는 속성 */
pgprot_t phys_mem_access_prot(struct file *file, unsigned long pfn,
			      unsigned long size, pgprot_t vma_prot)
{
	if (!pfn_is_map_memory(pfn))
		return pgprot_noncached(vma_prot);
	else if (file->f_flags & O_SYNC)
		return pgprot_writecombine(vma_prot);
	return vma_prot;
}
```

```c
/* arch/arm64/include/asm/pgtable.h */
#define pgprot_noncached(prot) \
	__pgprot_modify(prot, PTE_ATTRINDX_MASK, PTE_ATTRINDX(MT_DEVICE_nGnRnE) | PTE_PXN | PTE_UXN)
#define pgprot_device(prot) \
	__pgprot_modify(prot, PTE_ATTRINDX_MASK, PTE_ATTRINDX(MT_DEVICE_nGnRE) | PTE_PXN | PTE_UXN)
```

- `/dev/mem`으로 RAM이 아닌 주소를 `mmap`하면 **Device-nGnRnE**(non-posted)다. 커널 드라이버의 `ioremap()`(nGnRE)보다 엄격하다.
- PCI sysfs `resourceN` 파일의 `mmap`은 `drivers/pci/mmap.c`에서 `pgprot_device()` → **Device-nGnRE**. `resourceN_wc` 파일이면 write-combine.
- 같은 물리 레지스터가 커널에서는 nGnRE, 유저 `/dev/mem`에서는 nGnRnE로 동시에 매핑될 수 있다. Arm 아키텍처는 같은 물리 주소에 서로 다른 메모리 속성으로 매핑하는 것(mismatched attributes)을 경계한다 — Device 유형끼리의 차이는 비교적 무해하지만, 한쪽이 Normal Cacheable이면 캐시 일관성이 깨질 수 있다. `/dev/mem`이 RAM을 막는 이유 중 하나다(§9).

### 2.3 예제 2 — RAM을 `ioremap()`하면? (`h1_ram`)

무엇을 확인하나: arm64 `ioremap()`이 RAM을 거부한다는 것, RAM을 "다른 이름으로" 보고 싶으면 `memremap()`을 쓴다는 것.

```c
// SPDX-License-Identifier: GPL-2.0
/* h1_ram: RAM을 ioremap()하면? — arm64는 거부한다. RAM은 memremap() */
#include <linux/module.h>
#include <linux/io.h>
#include <linux/slab.h>

static int __init h1_ram_init(void)
{
	u32 *buf = kmalloc(PAGE_SIZE, GFP_KERNEL);
	phys_addr_t pa;
	void __iomem *io;
	void *wb;

	if (!buf)
		return -ENOMEM;
	buf[0] = 0xcafef00d;
	pa = virt_to_phys(buf);
	io = ioremap(pa, PAGE_SIZE);
	pr_info("h1_ram: buf %px pa %pa ioremap -> %px\n", buf, &pa, io);
	wb = memremap(pa, PAGE_SIZE, MEMREMAP_WB);
	pr_info("h1_ram: memremap(WB) -> %px (same as linear map: %s) val=0x%x\n",
		wb, wb == (void *)buf ? "yes" : "no", wb ? *(u32 *)wb : 0);
	if (wb)
		memunmap(wb);
	kfree(buf);
	return -EAGAIN;
}
module_init(h1_ram_init);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H1: ioremap on RAM is refused on arm64");
```

`-EAGAIN`을 돌려 로드를 일부러 실패시킨다. 측정·관찰만 하는 모듈을 `rmmod` 없이 반복 실행하는 요령이다. (게스트 스크립트 `t3.sh`의 일부, 출력은 WARN 스택을 줄였다.)

## 3. `__iomem`과 접근자 가족

### 3.1 `__iomem` — 컴파일러는 모르고 sparse만 아는 표시

랩 소스 `include/linux/compiler_types.h`:

```c
#ifdef __CHECKER__
# define __iomem	__attribute__((noderef, address_space(__iomem)))
...
#else /* __CHECKER__ */
# define __iomem
```

gcc로 빌드할 때 `__iomem`은 **빈 매크로**다. 아무 효과가 없다. 정적 분석기 **sparse**가 돌 때만(`__CHECKER__` 정의) 두 속성이 붙는다.

- `noderef`: 이 포인터를 `*p`로 역참조하면 경고 — "dereference of noderef expression".
- `address_space(__iomem)`: 일반 포인터와 다른 주소 공간. 캐스트로 공간을 바꾸면 경고 — "cast removes address space '__iomem'". 일부러 바꿀 때는 `__force`를 붙인다(접근자 내부 구현이 그렇게 한다).

즉 `__iomem`은 **"이 주소는 접근자로만 만져라"는 타입 표시**이고, 그 규칙을 지키게 하는 것은 리뷰어와 sparse다. 커널 빌드에서 `make C=1`(바뀐 파일만) 또는 `make C=2`(전부)로 sparse를 돌린다. §8에서 실제로 돌린다.

규칙 몇 가지:

- **엔디언**: `readl`은 "장치 레지스터는 리틀엔디언"이라고 가정하고 CPU 엔디언으로 바꾼다. arm64 리틀엔디언에서는 변환이 없다. 빅엔디언 커널(드묾)에서는 `rev`가 들어간다. 반대로 레지스터가 빅엔디언인 IP(일부 네트워크·PowerPC 계열 IP, 일부 FPGA 블록)는 `ioread32be`를 쓴다.
- **폭**: `readb/w/l/q` = 8/16/32/64비트. 레지스터 맵이 32비트면 `readl`만 쓴다. 장치가 허용하지 않는 폭은 버스 에러가 된다(§3.5).
- **`readq` 주의**: 32비트 아키텍처에는 원자적 64비트 MMIO가 없다. 이식성 있는 코드는 `<linux/io-64-nonatomic-lo-hi.h>`를 include해 `lo_hi_readq()`(두 번의 32비트 읽기)를 쓴다. arm64에서는 `ldr x`가 원자적이다.
- **포인터 산술**: `base + 0x20`은 `void __iomem *`에 대한 바이트 단위 산술이다(GNU C 확장). `u32 __iomem *`로 선언하면 `base + 8`이 32바이트 뒤라는 점에 주의. 드라이버 대부분은 `void __iomem *base` + 바이트 오프셋 `#define`으로 쓴다.

### 3.3 예제 3 — 접근자 하나당 함수 하나, objdump (`h1_acc`)

무엇을 확인하나: 각 접근자가 arm64에서 정확히 어떤 명령이 되는지. F5 §2.4가 `readl`/`readl_relaxed`/`writel`/`writel_relaxed`를 했으니, 여기서는 폭·`__raw_`·`ioread32`·빅엔디언까지 넓힌다.

```c
// SPDX-License-Identifier: GPL-2.0
/* h1_acc: MMIO 접근자 하나당 함수 하나 — objdump로 명령을 본다 */
#include <linux/module.h>
#include <linux/io.h>

extern void __iomem *h1_reg;
extern u64 h1_v;
extern void (*const h1_fns[])(void);
void __iomem *h1_reg;		/* 전역: 컴파일러가 값을 가정하지 못하게 */
u64 h1_v;
#define F(name, body) static noinline void name(void) { body; }

F(a_readb,          h1_v = readb(h1_reg))
F(a_readw,          h1_v = readw(h1_reg))
F(a_readl,          h1_v = readl(h1_reg))
F(a_readq,          h1_v = readq(h1_reg))
F(a_readl_relaxed,  h1_v = readl_relaxed(h1_reg))
F(a_raw_readl,      h1_v = __raw_readl(h1_reg))
F(a_ioread32,       h1_v = ioread32(h1_reg))
F(a_ioread32be,     h1_v = ioread32be(h1_reg))
F(a_writel,         writel(0x5a, h1_reg))
F(a_writel_relaxed, writel_relaxed(0x5a, h1_reg))
F(a_raw_writel,     __raw_writel(0x5a, h1_reg))
F(a_iowrite32be,    iowrite32be(0x5a, h1_reg))

void (*const h1_fns[])(void) = {
	a_readb, a_readw, a_readl, a_readq, a_readl_relaxed, a_raw_readl,
	a_ioread32, a_ioread32be, a_writel, a_writel_relaxed, a_raw_writel,
	a_iowrite32be,
};

static int __init h1_acc_init(void)
{
	pr_info("h1_acc: %zu accessor stubs at %ps..%ps\n",
		ARRAY_SIZE(h1_fns), h1_fns[0], h1_fns[ARRAY_SIZE(h1_fns) - 1]);
	return 0;	/* h1_reg는 NULL — 호출하지 않는다. 디스어셈블리 전용 */
}
static void __exit h1_acc_exit(void) { }
module_init(h1_acc_init);
module_exit(h1_acc_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H1: MMIO accessor disassembly stubs");
```

처음에는 `h1_reg`, `h1_v`, `h1_fns`를 `static`으로 선언했다. 그러자 gcc가 "`h1_reg`는 한 번도 대입되지 않으니 항상 NULL"이라고 추론해서 `a_readb`를 `mov x0, #0x0; ldrb w0, [x0]`으로 만들고, 나머지 함수 대부분은 아예 지워 버렸다. 컴파일러는 MMIO를 모른다 — **접근자가 `volatile` asm이어도, 그 주소를 계산하는 코드는 평범한 C로 최적화된다.** 전역으로 바꾸고 `extern` 선언을 두어(sparse의 "should it be static?" 경고 방지) 다시 빌드했다.

| 접근자 | 실제 MMIO 명령 | 앞 | 뒤 | 비고 |
|---|---|---|---|---|
| `readb` / `readw` | `ldrb` / `ldrh` | — | `dmb oshld` + `eor`/`cbnz` | 폭만 다르다, 결과를 0 확장 |
| `readl` | `ldr w` | — | `dmb oshld` + `eor`/`cbnz` | F5 §5.2의 4·5번 보장 |
| `readq` | `ldr x` | — | `dmb oshld` + `eor`/`cbnz` | 64비트 한 번 (arm64) |
| `ioread32` | `ldr w` | — | `readl`과 **완전히 같음** | arm64는 `GENERIC_IOMAP` 없음 |
| `ioread32be` | `ldr w` | — | `dmb oshld` + `rev` + 의존 | 바이트 순서 뒤집기 1개 |
| `readl_relaxed` | `ldr w` | — | 없음 | |
| `__raw_readl` | `ldr w` | — | 없음 | arm64 LE에서는 `_relaxed`와 같은 명령 |
| `writel` | `str w` | `dmb oshst` | — | F5 §5.2의 3번 보장 |
| `writel_relaxed` / `__raw_writel` | `str w` | — | — | |
| `iowrite32be` | `str w` | `dmb oshst` | — | `0x5a` → `0x5a000000`: 상수라서 바이트 뒤집기를 컴파일 타임에 끝냈다 |

볼 것 두 가지 더:

- `.text` 끝의 `ldarb`/`ldarh`/`ldar` 8개는 함수가 아니라 **대체 명령**이다. `__raw_readX()`가 `ALTERNATIVE("ldr ...", "ldar ...", ARM64_WORKAROUND_DEVICE_LOAD_ACQUIRE)`로 되어 있어서, 부팅 때 CPU가 ARM erratum 832075를 가진 Cortex-A57 초기 리비전이면 모든 MMIO `ldr`이 `ldar`로 패치된다. 그리고 **이 랩의 QEMU cortex-a57이 바로 그 경우**다 — 부팅 로그에 `CPU features: detected: ARM erratum 832075`가 찍힌다(§7 출력). 그래서 이 노트의 게스트에서 실행되는 `readl`은 실제로 `ldar`다(§3.5의 oops 코드 바이트에서도 보인다).
- `readl_relaxed`와 `__raw_readl`이 같은 명령이라면 왜 둘이 있나? `__raw_`는 엔디언 변환도 없다. 빅엔디언 커널에서는 둘이 달라진다. 그리고 `readl_relaxed`에는 MMIO tracing 훅(`CONFIG_TRACE_MMIO_ACCESS`)이 걸릴 수 있지만 `__raw_`에는 없다. **드라이버는 `readl` 또는 `readl_relaxed`를 쓰고, `__raw_`는 쓰지 않는다**가 규칙이다.

### 3.4 `ioread32` 가족은 왜 있나

x86에는 메모리 주소 공간 말고 별도의 **I/O 포트 공간**(`in`/`out` 명령)이 있다. 오래된 PCI 장치는 BAR가 I/O 공간일 수 있다. `pci_iomap()`/`ioport_map()`이 돌려주는 "cookie"는 MMIO 주소일 수도, I/O 포트를 인코딩한 값일 수도 있고, `ioread32()`가 런타임에 그걸 구분해 `readl` 또는 `inl`을 부른다(`CONFIG_GENERIC_IOMAP`, `lib/iomap.c`). arm64는 I/O 포트 공간이 없고(PCI I/O 공간도 MMIO 창으로 보인다) `GENERIC_IOMAP`을 쓰지 않으니 `ioread32 = readl`이다(랩 소스 `include/asm-generic/io.h` 904행: `return readl(addr);`). 위 objdump가 그것을 보여 준다.

실무 판단: platform 드라이버는 `readl`/`writel`. `pci_iomap` 계열로 매핑한 PCI 드라이버는 관례상 `ioread32`/`iowrite32`도 많이 쓴다(드라이버 트리에서 `ioread32(`가 2,173줄). arm64에서는 둘이 같으니 **주변 코드의 관례를 따른다.**

```c
static int __init h1_width_init(void)
```

## 4. PCI BAR 매핑 — edu 장치 드라이버 (`h1_edu`)

PCIe 깊이(enumeration, config space, MSI)는 H11에서 한다. 여기서는 "BAR도 결국 물리 주소 창이고, 매핑해서 `readl`로 읽는다"만 확인한다. Don에게 BAR는 익숙하다 — SSD 컨트롤러가 호스트에 BAR0로 NVMe 레지스터를 내보내던 그 반대편, **호스트 드라이버 쪽**을 짜는 것이다.

### 4.1 예제 5(a) — 레지스터 정의와 factorial 헬퍼

무엇을 확인하나: `pcim_enable_device` → `pcim_iomap_region` → `readl`/`writel` → `readl_poll_timeout`이라는 PCI 드라이버의 최소 뼈대, 그리고 장치 쪽 동작(ID, 비트 반전, 계산 + busy 비트).

```c
// SPDX-License-Identifier: GPL-2.0
/* h1_edu: QEMU edu PCI 장치의 BAR0를 매핑하고 ID·liveness·factorial을 돌린다 */
#include <linux/module.h>
#include <linux/pci.h>
#include <linux/iopoll.h>
#include "h1.h"

#define EDU_ID      0x00	/* RO 0xRRrr00ed */
#define EDU_LIVE    0x04	/* RW 쓴 값의 ~ */
#define EDU_FACT    0x08	/* RW n 쓰면 n! */
#define EDU_STATUS  0x20	/* bit0 = 계산 중(RO) */
#define EDU_ST_BUSY BIT(0)

void __iomem *h1_edu_base;		/* 뒤 실험 모듈(h1_bench 등)이 같이 쓴다 */
EXPORT_SYMBOL_GPL(h1_edu_base);
static bool excl;
module_param(excl, bool, 0444);

static u32 h1_rd_count(void __iomem *a, int *n)
{
	(*n)++;
	return readl(a);
}

static void h1_edu_fact(struct device *dev, void __iomem *b, u32 n, bool tight)
{
	ktime_t t0 = ktime_get();
	int ret, polls = 0;
	u32 st;

	writel(n, b + EDU_FACT);			/* 쓰는 순간 busy=1 */
	if (tight)	/* 잠들지 않고 돌며 몇 번 읽었는지 센다 */
		ret = read_poll_timeout_atomic(h1_rd_count, st, !(st & EDU_ST_BUSY),
					       0, 10000, false, b + EDU_STATUS, &polls);
	else		/* = readl_poll_timeout(b + EDU_STATUS, st, ..., 10, 10000) + 카운터 */
		ret = read_poll_timeout(h1_rd_count, st, !(st & EDU_ST_BUSY),
					10, 10000, false, b + EDU_STATUS, &polls);
	dev_info(dev, "fact(%u): ret=%d st=0x%x result=%u polls=%d (%lld us)\n", n, ret,
		 st, readl(b + EDU_FACT), polls, ktime_us_delta(ktime_get(), t0));
}
```

`readl_poll_timeout(addr, val, cond, sleep, timeout)`은 `read_poll_timeout(readl, val, cond, sleep, timeout, false, addr)`의 줄임이다(§5.2). 폴링 횟수를 세려고 `readl` 대신 카운터를 올리는 래퍼 `h1_rd_count`를 op로 넘겼다 — 일반형 `read_poll_timeout()`은 "인자를 받아 값을 돌려주는 아무 함수"를 op로 받는다. 실무에서 I2C 레지스터 읽기 함수나 `regmap_read` 래퍼를 넣는 것도 이 형태다.

### 4.2 예제 5(b) — probe와 등록

```c
static int h1_edu_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct device *dev = &pdev->dev;
	void __iomem *b;
	u32 v;
	int ret = pcim_enable_device(pdev);		/* Command.MEM=1 (BAR 디코딩 켜기) */

	if (ret)
		return ret;
	if (excl) {					/* /dev/mem·sysfs mmap까지 막는 버전 */
		ret = pci_request_regions_exclusive(pdev, "h1_edu");
		b = ret ? NULL : pcim_iomap(pdev, 0, 0);
	} else {
		b = pcim_iomap_region(pdev, 0, "h1_edu");	/* request + iomap, devres */
	}
	if (IS_ERR_OR_NULL(b))
		return b ? PTR_ERR(b) : -ENOMEM;
	v = readl(b + EDU_ID);
	dev_info(dev, "BAR0 %pR -> VA %px, ID=0x%08x (v%u.%u)\n",
		 &pdev->resource[0], b, v, v >> 24, (v >> 16) & 0xff);
	writel(0x12345678, b + EDU_LIVE);
	dev_info(dev, "liveness: wrote 0x12345678 read 0x%08x\n", readl(b + EDU_LIVE));
	h1_edu_fact(dev, b, 5, false);
	h1_edu_fact(dev, b, 12, false);
	h1_edu_fact(dev, b, 12, true);
	h1_edu_fact(dev, b, 12, true);
	h1_edu_fact(dev, b, 12, true);
	h1_edu_base = b;
	return 0;
}

static void h1_edu_remove(struct pci_dev *pdev)
{
	h1_edu_base = NULL;
	if (excl)
		pci_release_regions(pdev);
}

static const struct pci_device_id h1_edu_ids[] = {
	{ PCI_DEVICE(0x1234, 0x11e8) },
	{ }
};
MODULE_DEVICE_TABLE(pci, h1_edu_ids);
static struct pci_driver h1_edu_drv = {
	.name = "h1_edu", .id_table = h1_edu_ids,
	.probe = h1_edu_probe, .remove = h1_edu_remove,
};
module_pci_driver(h1_edu_drv);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H1: QEMU edu BAR0 MMIO demo");
```

`excl` 파라미터는 §9에서 쓴다. 기본 경로는 `pcim_iomap_region()` 한 줄 — BAR0 영역 request + `pci_iomap()` + devres 등록이다(랩 소스 `drivers/pci/devres.c` 607행). 6.18에서는 `pci_request_region()`이 더 이상 "pcim이면 자동 관리"되는 하이브리드 동작을 하지 않는다. 그래서 `excl` 경로는 직접 `pci_release_regions()`를 부른다.

## 5. 비트 기다리기 — `readl_poll_timeout`

### 5.1 직관 — bare-metal의 `while`과 무엇이 다른가

Don의 펌웨어에서 `while (STATUS & BUSY);`는 괜찮았다. 그 코어에는 그 일밖에 없었고, 하드웨어가 안 끝나면 워치독이 리셋했다. 커널에서는 세 가지가 다르다.

1. **타임아웃이 없으면 CPU 하나가 영원히 멈춘다.** 장치가 리셋 상태거나 클럭이 꺼져 있으면(H3) 비트는 영원히 안 바뀐다. 선점이 꺼진 문맥(스핀락 안, 인터럽트 핸들러)이면 그 CPU 전체가 멈추고 soft lockup 경고가 뜬다.
2. **잘 수 있는 문맥이면 자야 한다.** 다른 태스크에게 CPU를 넘겨야 한다. 잘 수 없는 문맥(원자 문맥, F2)이면 `udelay`로 바쁜 대기를 한다.
3. **타임아웃을 판정하는 순서가 중요하다.** "시간이 다 됐으니 실패"라고 판단하기 직전에 한 번 더 읽어야 한다. 그렇지 않으면 선점이나 인터럽트로 오래 끌려갔다 돌아온 직후, 실제로는 이미 끝난 장치를 실패로 처리한다.

`<linux/iopoll.h>`가 이 셋을 해결한 표준 매크로를 준다.

### 5.2 매크로 해부 (랩 소스 6.18)

6.18의 `include/linux/iopoll.h`에서 모든 변형은 `poll_timeout_us()`(잘 수 있음)와 `poll_timeout_us_atomic()`(잘 수 없음) 두 개로 모인다. 잘 수 있는 쪽의 몸통:

```c
#define poll_timeout_us(op, cond, sleep_us, timeout_us, sleep_before_op) \
({ \
	u64 __timeout_us = (timeout_us); \
	unsigned long __sleep_us = (sleep_us); \
	ktime_t __timeout = ktime_add_us(ktime_get(), __timeout_us); \
	int ___ret; \
	might_sleep_if((__sleep_us) != 0); \
	if ((sleep_before_op) && __sleep_us) \
		usleep_range((__sleep_us >> 2) + 1, __sleep_us); \
	for (;;) { \
		bool __expired = __timeout_us && \
			ktime_compare(ktime_get(), __timeout) > 0; \
		/* guarantee 'op' and 'cond' are evaluated after timeout expired */ \
		barrier(); \
		op; \
		if (cond) { \
			___ret = 0; \
			break; \
		} \
		if (__expired) { \
			___ret = -ETIMEDOUT; \
			break; \
		} \
		if (__sleep_us) \
			usleep_range((__sleep_us >> 2) + 1, __sleep_us); \
		cpu_relax(); \
	} \
	___ret; \
})
```

```c
#define read_poll_timeout(op, val, cond, sleep_us, timeout_us, \
			  sleep_before_read, args...) \
	poll_timeout_us((val) = op(args), cond, sleep_us, timeout_us, sleep_before_read)
...
#define readl_poll_timeout(addr, val, cond, delay_us, timeout_us) \
	readx_poll_timeout(readl, addr, val, cond, delay_us, timeout_us)
```

읽는 법:

- **만료 여부를 먼저 계산하고(`__expired`), 그 다음에 읽고 조건을 본다.** 만료였어도 이번 읽기에서 조건이 맞으면 성공이다. 위 3번 문제의 정답이 이 순서다. `barrier()`는 컴파일러가 읽기를 시간 확인보다 앞으로 옮기지 못하게 한다(F5 §1.4).
- 잠은 `usleep_range(sleep/4 + 1, sleep)` — hrtimer 기반이라 짧은 대기에도 쓸 만하다. `sleep_us = 0`이면 자지 않고 `cpu_relax()`만 하며 돈다(arm64에서 `yield` 명령).
- `timeout_us = 0`은 **"타임아웃 없음(영원히)"** 이다. 실수로 0을 넣으면 bare-metal `while`로 돌아간다.
- 끝나면 `val`에는 **마지막으로 읽은 값**이 남는다. 실패 로그에 반드시 찍는다 — "-ETIMEDOUT, status=0x81" 같은 정보가 디버깅의 반이다.
- `_atomic` 변형은 시계(`ktime_get`)도 쓰지 않는다. 남은 시간을 `delay_us`만큼씩 빼며 세고 `udelay()`로 기다린다(주석: "safe to call even when timekeeping is suspended"). 인터럽트 핸들러, 스핀락 안, 시계가 멈춘 suspend/resume 경로에서 쓴다.

### 5.3 실험 결과 읽기 — 폴링 횟수

§4.2의 출력에서 factorial 줄만 다시 보면:

```text
fact(5): ret=0 st=0x0 result=120 polls=2 (528 us)
fact(12): ret=0 st=0x0 result=479001600 polls=2 (386 us)
fact(12): ret=0 st=0x0 result=479001600 polls=8 (30 us)
fact(12): ret=0 st=0x0 result=479001600 polls=75 (26 us)
fact(12): ret=0 st=0x0 result=479001600 polls=74 (25 us)
```

- 앞 두 줄(잠자는 버전, `sleep_us = 10`): 첫 읽기에서 busy였고, 한 번 자고 깨서 두 번째 읽기에 끝나 있었다(`polls=2`). 그런데 걸린 시간이 **수백 us**다. 요청한 잠은 3~10 us였다. TCG 에뮬레이터에서 hrtimer 잠 한 번의 실제 비용이 그만큼 크다. 실제 하드웨어에서도 `usleep_range`의 최소 비용은 컨텍스트 스위치 + 타이머 인터럽트라 수 us~수십 us 단위이다(이 노트에서 실측하지 않음). **"짧게 끝날 게 확실한 대기"는 잠들지 않는 편이 빠를 수 있다** — 하지만 대가로 CPU를 태운다.
- 뒤 세 줄(바쁜 대기 `_atomic`, `delay_us = 0`): 8번, 75번, 74번 읽은 끝에 끝났다. 25~30 us. edu 모델의 factorial은 QEMU의 별도 스레드가 계산하고 status 비트를 내리므로, 그 스레드가 스케줄되기까지 vCPU가 MMIO 읽기를 수십 번 한다.
- 같은 실험을 여러 번 돌리면 숫자가 달라진다. 앞선 실행에서는 첫 읽기에 이미 끝나 있던 경우(`polls=1`)도, 166번 읽은 경우도 있었다. 하드웨어가 비동기라는 것 — **busy 비트를 확인하지 않고 결과 레지스터를 바로 읽는 코드는 "대개 동작하는" 버그**가 된다.

### 5.4 타임아웃 경로 — 예제 4의 앞부분

§3.5의 `h1_width`는 먼저 절대 참이 될 수 없는 조건(ID 레지스터 == 0)을 2 ms 타임아웃, 100 us 간격으로 기다렸다.

```text
[    1.319934] h1_width: poll ID==0: ret=-110 last=0x010000ed after 2277 us
```

`-110` = `-ETIMEDOUT`. 마지막 값 `0x010000ed`가 `val`에 남았다. 걸린 시간 2277 us는 타임아웃 2000 us + 마지막 잠 하나 + 마지막 읽기다 — **타임아웃은 "최소 이만큼은 기다린다"이지 "정확히 이만큼"이 아니다.**

### 5.5 고르는 법과 함정

| 문맥 | 쓸 것 | 이유 |
|---|---|---|
| probe, ioctl, workqueue, threaded IRQ | `readl_poll_timeout(…, sleep_us, timeout_us)` | 잘 수 있다 — CPU를 넘긴다 |
| hardirq 핸들러, 스핀락 안, `local_irq_disable` 구간 | `readl_poll_timeout_atomic(…, delay_us, timeout_us)` | 자면 안 된다(F2) — `usleep`은 "scheduling while atomic" |
| 몇 ms 이상 걸리는 대기(PLL lock, 리셋 완료) | 위 + 큰 `sleep_us`(수십~수백 us) | 폴링 횟수를 줄인다 |
| 완료 인터럽트가 있는 장치 | 폴링 대신 `wait_for_completion_timeout()` + IRQ | F3·F6 — 폴링 자체를 없앤다 |
| regmap을 쓰는 드라이버 | `regmap_read_poll_timeout()` | 같은 패턴, H2 |

함정:

- `readl_poll_timeout(base + STATUS, val, val & DONE, 0, 0)` — 둘 다 0이면 타임아웃 없는 바쁜 대기다. 정적 분석에서 잘 걸리는 패턴이다.
- 원자 문맥에서 non-atomic 변형 — `might_sleep_if()`가 있어서 `CONFIG_DEBUG_ATOMIC_SLEEP` 커널(랩의 `Image-dbg`)에서는 즉시 경고가 뜬다. 일반 커널에서는 가끔 터지는 버그가 된다.
- `_atomic` 변형에 큰 타임아웃(수십 ms) — 그 시간 동안 CPU 하나를 인터럽트까지 막고 태운다.
- 조건식에 부작용이 있는 매크로 인자 — 매크로라서 여러 번 평가된다.

## 6. 공유 레지스터의 read-modify-write와 락

### 6.1 직관 — Don이 이미 아는 버그

### 6.2 예제 6 — 두 CPU가 같은 레지스터를 RMW (`h1_race`)

무엇을 확인하나: 락 없는 RMW가 실제로 비트를 잃는지, 스핀락이 그걸 0으로 만드는지. edu의 DMA source 레지스터(0x80, 그냥 값을 저장하는 RW 레지스터)를 "공유 제어 레지스터"로 빌려 쓴다. CPU0은 bit0, CPU1은 bit1만 켰다 끈다. 끄려고 읽었을 때 내 비트가 이미 꺼져 있으면 누군가의 옛 값 쓰기가 지운 것이다.

```c
// SPDX-License-Identifier: GPL-2.0
/* h1_race: 공유 레지스터의 read-modify-write를 두 CPU가 동시에 — 락 없이/있이 */
#include <linux/module.h>
#include <linux/io.h>
#include <linux/kthread.h>
#include <linux/spinlock.h>
#include <linux/completion.h>

#include "h1.h"
#define REG  0x80			/* edu DMA src 레지스터를 "공유 제어 레지스터"로 빌린다 */
#define N    20000
static bool locked;
module_param(locked, bool, 0444);
static DEFINE_SPINLOCK(h1_lock);
static DECLARE_COMPLETION(h1_done);
static int lost[2];

static void rmw(u32 bit, bool set, int id)
{
	unsigned long flags = 0;
	u32 v;

	if (locked)
		spin_lock_irqsave(&h1_lock, flags);
	v = readl(h1_edu_base + REG);
	if (!set && !(v & bit))
		lost[id]++;		/* 내가 켠 비트가 누군가의 옛 값 쓰기로 사라졌다 */
	writel(set ? v | bit : v & ~bit, h1_edu_base + REG);
	if (locked)
		spin_unlock_irqrestore(&h1_lock, flags);
}

static int worker(void *arg)
{
	int id = (long)arg, i;

	for (i = 0; i < N; i++) {
		rmw(BIT(id), true, id);
		rmw(BIT(id), false, id);
	}
	complete(&h1_done);
	return 0;
}

static int __init h1_race_init(void)
{
	long id;

	if (!h1_edu_base)
		return -ENODEV;
	writel(0, h1_edu_base + REG);
	for (id = 0; id < 2; id++)
		kthread_run_on_cpu(worker, (void *)id, id, "h1_race/%u");
	wait_for_completion(&h1_done);
	wait_for_completion(&h1_done);
	pr_info("h1_race: locked=%d lost: cpu0=%d cpu1=%d (of %d each)\n",
		locked, lost[0], lost[1], N);
	return -EAGAIN;
}
module_init(h1_race_init);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H1: unlocked RMW on a shared MMIO register");
```

- 첫 실행은 0이었다. 두 kthread가 거의 겹치지 않고 하나가 먼저 끝났을 것이다. **경쟁 버그는 "테스트에서 한 번 통과"가 아무 의미 없다**는 예다.
- `locked=1`이면 세 번 모두 0. 스핀락 + `irqsave`로 다른 CPU와 같은 CPU의 인터럽트 핸들러를 모두 막았다.

sparse를 돌리면(§8) 이 파일에서 `warning: context imbalance in 'rmw' - different lock contexts for basic block`이 나온다. `if (locked) spin_lock(...)` 같은 **조건부 락**은 sparse의 락 문맥 검사기가 추적하지 못한다. 실제 드라이버에서는 조건부 락 자체를 피하는 것이 좋은 신호로 받아들인다.

### 6.3 실무 패턴

```c
/* 실무형: 비트 갱신 헬퍼 하나로 모든 RMW를 통과시킨다 */
static void foo_update_bits(struct foo *fd, u32 reg, u32 mask, u32 val)
{
	unsigned long flags;
	u32 v;

	spin_lock_irqsave(&fd->reg_lock, flags);
	v = readl(fd->base + reg);
	v = (v & ~mask) | (val & mask);
	writel(v, fd->base + reg);
	spin_unlock_irqrestore(&fd->reg_lock, flags);
}
```

(이 코드는 패턴 설명용이고 따로 빌드하지 않았다.)

- 이 헬퍼가 바로 regmap의 `regmap_update_bits()`다(H2). regmap은 락, 레지스터 캐시, 디버그fs 덤프까지 준다. 레지스터가 많은 드라이버는 처음부터 regmap-mmio를 쓴다.
- 락 종류: IRQ 핸들러에서도 그 레지스터를 만지면 `spin_lock_irqsave`, 프로세스 문맥에서만이면 `mutex`도 된다(하지만 MMIO RMW는 짧으니 스핀락이 보통).
- 하드웨어가 **SET/CLR 레지스터 쌍**(쓰면 1인 비트만 켜고 끄는 레지스터, W1S/W1C)을 제공하면 RMW 자체가 필요 없다. Don이 아는 대로 좋은 IP는 이걸 준다. 인터럽트 상태 레지스터의 W1C도 같은 이유로 존재한다.
- 락을 잡은 채 한 `writel()`이 락을 푼 뒤 다른 CPU의 `writel()`보다 장치에 먼저 도착하는지는 F5 §5.3의 2번 보장이다(arm64는 별도 처리가 필요 없다).

### 7.1 예제 7 — 접근 한 번의 비용 (`h1_bench`)

무엇을 확인하나: RAM 읽기와 MMIO 읽기·쓰기의 비용 차이, 그리고 `readl`과 `readl_relaxed`의 차이가 보이는가.

```c
// SPDX-License-Identifier: GPL-2.0
/* h1_bench: 접근 한 번에 몇 ns? RAM vs MMIO, readl vs _relaxed (QEMU TCG 안에서) */
#include <linux/module.h>
#include <linux/io.h>
#include <linux/ktime.h>
#include <linux/math64.h>

#include "h1.h"
#define N 20000
static u32 h1_ram_word;
static u32 sink;

#define LOOP(name, expr) do {						\
	u64 t0 = ktime_get_ns();					\
	for (i = 0; i < N; i++) { expr; }				\
	pr_info("h1_bench: %-16s %6llu ns/op\n", name,			\
		div_u64(ktime_get_ns() - t0, N));			\
} while (0)

static int __init h1_bench_init(void)
{
	void __iomem *edu = h1_edu_base;
	void __iomem *rtc = ioremap(0x09010000, SZ_4K);	/* PL031, 읽기만 */
	int i;

	if (!edu || !rtc)
		return -ENODEV;
	LOOP("ram READ_ONCE",  sink += READ_ONCE(h1_ram_word));
	LOOP("edu readl",      sink += readl(edu + 0x00));
	LOOP("edu readl_rlx",  sink += readl_relaxed(edu + 0x00));
	LOOP("edu writel",     writel(i, edu + 0x04));
	LOOP("edu writel_rlx", writel_relaxed(i, edu + 0x04));
	LOOP("pl031 readl",    sink += readl(rtc + 0x00));
	LOOP("pl031 readl_rlx", sink += readl_relaxed(rtc + 0x00));
	iounmap(rtc);
	return -EAGAIN;		/* 측정만 하고 로드 실패로 끝낸다 → 반복 insmod 가능 */
}
module_init(h1_bench_init);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H1: MMIO access latency micro-benchmark");
```

### 7.2 해석 — 정직하게

- **RAM 5 ns vs MMIO 300~500 ns.** TCG에서 MMIO 접근은 번역된 코드에서 빠져나와 QEMU의 장치 모델 함수(C 코드)를 부르고, 전역 락(BQL)을 잡는다. 그 비용이다. 실제 실리콘의 숫자가 아니다.
- **`readl` vs `readl_relaxed`는 구분되지 않는다.** 차이(`dmb oshld` 하나)는 TCG에서 거의 공짜이고, MMIO 한 번의 비용과 잡음(최소~최대 폭 200 ns)에 묻힌다. 게다가 이 게스트는 erratum 832075 때문에 **둘 다 `ldar`**(load-acquire)로 패치되어 있다(§3.3). 이 측정으로 "relaxed가 빠르다/느리다"는 결론을 내리면 안 된다.
- 그래도 남는 교훈 두 개는 실제 하드웨어에서도 성립한다. (1) **MMIO 읽기는 비싸다** — 특히 PCIe 읽기는 non-posted라 completion이 돌아올 때까지 CPU가 기다린다. Don이 SSD에서 보던 대로 PCIe MMIO 읽기 왕복은 대개 µs 단위 수준이라고 알려져 있다(이 노트에서 실측하지 않음). 그래서 고성능 드라이버는 hot path에서 MMIO **읽기**를 피하고(상태를 DMA로 메모리에 써 달라고 한다 — NVMe completion queue의 phase bit가 그 예), 쓰기는 posted라 상대적으로 싸다. (2) `_relaxed`의 이득은 "배리어 비용 / 전체 접근 비용"이 클 때, 즉 **같은 장치에 대한 짧은 MMIO가 연달아 많을 때**(FIFO 채우기, 레지스터 수십 개 초기화)만 의미가 있다. 실제 SoC에서 측정할 때는 `ktime_get_ns()` 루프에 더해 `perf stat`이나 PMU 사이클 카운터를 쓴다(M 모듈).

## 8. `__iomem`을 직접 역참조하면 — "arm64에선 돌아가는데 왜 틀렸나"

### 8.1 예제 8 — bare-metal 습관 그대로 쓴 모듈 (`h1_bug`)

무엇을 확인하나: `*(u32 *)base` 스타일이 (1) sparse에 어떻게 잡히는지, (2) 실제로 어떤 명령이 되는지, (3) 실행하면 어떻게 되는지.

```c
// SPDX-License-Identifier: GPL-2.0
/* h1_bug: __iomem 포인터를 직접 역참조하는 "bare-metal 습관" — sparse와 objdump로 본다 */
#include <linux/module.h>
#include <linux/io.h>

#define PL031_PHYS 0x09010000
#define PERIPHID0  0xfe0

static noinline u32 bad_read(u32 __iomem *r)		/* sparse: noderef */
{
	return *r;
}

static noinline void bad_read2(u32 __iomem *r, u32 *out)	/* 캐스트로 sparse 입막음 */
{
	u32 *p = (u32 *)r;

	out[0] = p[0];
	out[1] = p[1];
}

static noinline u32 bad_sum(u32 __iomem *r)		/* 인접 레지스터 두 개 */
{
	u32 *p = (u32 *)r;

	return p[0] + p[1];
}

static noinline void bad_wait(u32 __iomem *r)		/* bit0가 0이 될 때까지 */
{
	while (*(u32 *)r & 1)
		;
}

static noinline void good_wait(u32 __iomem *r)
{
	while (readl(r) & 1)
		cpu_relax();
}
```

```c
static int __init h1_bug_init(void)
{
	u32 __iomem *b = ioremap(PL031_PHYS, SZ_4K);	/* request 없이 — 읽기 전용 실험 */
	u32 two[2];

	if (!b)
		return -ENOMEM;
	bad_read2(b + PERIPHID0 / 4, two);
	pr_info("h1_bug: deref=0x%02x readl=0x%02x pair={0x%02x,0x%02x} sum=0x%02x\n",
		bad_read(b + PERIPHID0 / 4), readl(b + PERIPHID0 / 4), two[0], two[1],
		bad_sum(b + PERIPHID0 / 4));
	good_wait(b + 0x18 / 4);	/* RTCRIS = 0 → 즉시 통과 */
	bad_wait(b + 0x18 / 4);
	pr_info("h1_bug: both waits returned\n");
	iounmap(b);
	return 0;
}
static void __exit h1_bug_exit(void) { }
module_init(h1_bug_init);
module_exit(h1_bug_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H1: dereferencing __iomem directly (bug demo)");
```

`u32 __iomem *b`이므로 `b + PERIPHID0 / 4`는 4바이트 단위 산술이다(§3.2의 주의). gcc는 경고 0개로 빌드한다 — gcc에게 `__iomem`은 빈 매크로이기 때문이다.

출력에서 볼 것 — 컴파일러는 이 주소가 레지스터라는 것을 모르고 **평범한 메모리로 최적화**했다.

- **`bad_wait.isra.0`: 무한 루프.** `tbz w0, #0, 70` → 비트가 0이면 return, 아니면 `b 6c`(자기 자신으로 점프). 루프 안에 **load가 없다.** 컴파일러는 "`*r`은 루프 안에서 안 바뀐다"고 보고 읽기를 한 번만 하도록 루프 밖으로 뺐고, 그 읽기마저 호출자 쪽으로 옮겼다(`.isra` = interprocedural scalar replacement — 포인터 대신 값을 넘기도록 함수 시그니처를 바꾼 것). init의 `ldr w0, [x19, #24]`(오프셋 0x18 = RTCRIS)가 그 읽기다. 우리 실험에서는 RTCRIS가 0이라 바로 빠져나왔지만, 비트가 1이었다면 **장치가 비트를 내려도 영원히 못 빠져나온다.** Don이 펌웨어에서 `volatile`을 빼먹었을 때 보던 바로 그 버그다.
- `bad_read.isra.0`: 함수 몸통이 `ret` 하나. 읽기(`ldr w0, [x19, #4064]`, 0xfe0)가 호출자로 옮겨졌다. MMIO 접근이 어디서 일어날지 컴파일러 마음이다.
- **`bad_sum`: `ldp w1, w0, [x0]`** — 인접한 두 레지스터를 **한 명령(load pair)** 으로 읽었다. `readl` 두 번이었다면 `ldr` 두 개였을 것이다. 장치 입장에서는 접근 순서·폭이 프로그래머의 의도와 다를 수 있다.
- `good_wait`: 루프마다 `bl readl`(이 파일에서는 cold 섹션이라 `readl`이 인라인되지 않고 함수로 나왔다) + `yield`(`cpu_relax`). 매번 다시 읽는다.
- `bad_read2`는 이번에는 `ldr` 두 개였다. 컴파일러가 언제 `ldp`로 합칠지는 주변 코드에 달렸다. **"지금 빌드에서 괜찮았다"가 보장이 아니다.**

### 8.4 실행 결과 — 그런데 값은 맞다

`t3.sh`의 첫 줄들:

```text
[    1.178226] h1_bug: loading out-of-tree module taints kernel.
[    1.182241] h1_bug: deref=0x31 readl=0x31 pair={0x31,0x10} sum=0x41
[    1.182318] h1_bug: both waits returned
```

직접 역참조(`deref=0x31`)와 `readl`(`0x31`)이 같은 값을 읽었다. `ldp`로 읽은 두 레지스터도 PeriphID0·1(`0x31`, `0x10`)로 맞고, 합 `0x41`도 맞다. **arm64에서 ioremap된 VA는 진짜 가상 주소이고 Device 속성으로 매핑되어 있으니, 평범한 `ldr`도 레지스터에 도달한다.** 그래서 "돌아가는데요?"라는 말이 나온다.

### 8.5 그래도 틀린 이유 (면접 답변 재료)

1. **컴파일러 재배치·병합·제거** — §8.3에서 본 그대로. 루프 밖으로 빠진 읽기, 합쳐진 `ldp`, 호출자로 옮겨진 접근. `volatile`을 붙이면 이 중 일부는 막지만 2·3·4번은 남는다.
2. **배리어가 없다** — `readl`/`writel`이 주는 "일반 메모리(DMA 버퍼)와의 순서"(F5 §5.3의 3·4·5번 보장)가 없다. doorbell 버그가 된다.
3. **아키텍처 이식성** — `__iomem` 쿠키가 진짜 포인터가 아닌 아키텍처가 있다. x86의 `ioread32()` 쿠키는 I/O 포트일 수 있고(§3.4), s390 같은 아키텍처는 MMIO를 특수 명령으로 한다. 빅엔디언 아키텍처에서는 엔디언 변환이 빠진다.
4. **가상화에서 깨진다 (실행하지 않음, 소스 근거)** — KVM 게스트에서 MMIO 접근은 stage-2 fault로 하이퍼바이저에 트랩되고, 하이퍼바이저는 CPU가 준 syndrome(ESR의 ISV 비트와 접근 크기·레지스터 번호)으로 명령을 **디코딩 없이** 에뮬레이트한다. 그런데 `ldp`나 post-index 같은 writeback 형태의 load/store는 ISV = 0(syndrome 없음)으로 보고된다. 랩 소스의 호스트 쪽 코드 `arch/arm64/kvm/mmio.c`의 `io_mem_abort()`는 그 경우 "No valid syndrome? Ask userspace for help if it has volunteered to do so, and bail out otherwise."라는 주석과 함께 `-ENOSYS`를 돌려준다(VMM이 `KVM_CAP_ARM_NISV_TO_USER`로 자원하지 않았다면). 즉 **같은 `bad_sum` 코드가 KVM 위의 게스트에서는 VM을 멈추게 할 수 있다.** 이 노트의 QEMU는 TCG라서 모든 명령을 에뮬레이트하므로 문제가 드러나지 않았다. arm64의 `__raw_readl`이 `ldr %w0, [%1]`처럼 **writeback 없는 단일 load 하나**로 asm을 고정한 이유 중 하나가 이것이다.
5. **도구가 못 본다** — MMIO tracing(`CONFIG_TRACE_MMIO_ACCESS`의 rwmmio 트레이스포인트)은 접근자 안에 있다. 직접 역참조는 트레이스에 안 잡힌다.

결론: **커널에서는 `__iomem` 포인터를 접근자 밖에서 역참조하지 않는다. `volatile` 캐스팅도 답이 아니다.** Don의 bare-metal 습관 중 고쳐야 할 첫 번째다.

## 9. 유저스페이스에서 레지스터 — `/dev/mem`, devmem, UIO

### 9.1 직관 — 편리한 뒷문

`/dev/mem`은 물리 주소 공간 전체를 파일처럼 보여 주는 문자 장치다(`drivers/char/mem.c`). `mmap(fd, ..., offset = 물리 주소)`을 하면 그 물리 페이지가 내 프로세스에 매핑된다. busybox `devmem ADDR [WIDTH [VALUE]]`이 그 래퍼다. bring-up에서 레지스터를 빠르게 찍어 볼 때 정말 편하다 — JTAG 없이 Don이 J-Link로 메모리 창을 보던 일을 셸에서 한다.

문제는 "편한 뒷문"이 **커널의 모든 규칙을 우회한다**는 것이다. 실험으로 확인한다.

### 9.2 예제 9 — devmem으로 같은 레지스터를

```sh

echo "=== [1] 드라이버 없음 (Command.MEM=0)"; devmem $B 32
echo "=== [2] h1_edu 로드 후"; insmod /h1_edu.ko
```

출력에서 볼 것:

- **[1]** 드라이버가 없어 PCI Command의 Memory Space Enable이 0이다. 장치가 응답하지 않는 주소를 읽으니 `0xFFFFFFFF` — PCIe에서 Unsupported Request/master abort 때 all-ones가 돌아오는 그 관례를 QEMU가 흉내 낸다. Don이 "링크가 죽으면 모든 레지스터가 FFFFFFFF"라고 기억하는 바로 그것이다. 드라이버에서 `readl()`이 `0xffffffff`를 돌려주면 "장치가 사라졌다(surprise removal, 링크 다운)"를 의심하는 코드(`if (val == ~0U)`)가 PCI 드라이버에 흔한 이유다.
- **[2]** 드라이버가 로드되어 BAR0를 BUSY로 잡고 있는데도 devmem은 ID를 읽었고, **liveness 레지스터에 0을 써 버렸다**(읽으면 `~0` = `0xFFFFFFFF`). 드라이버가 써 둔 `0x12345678`이 드라이버 모르게 바뀌었다. 커널의 BUSY 깃발은 `/dev/mem`을 막지 않는다(이 커널 설정에서는 — 아래 9.3).
- **[3]** rtc-pl031 드라이버가 소유한 RTC 레지스터도 그냥 읽힌다. `0x6ACB0827` = 1791690791 = `date +%s`. 쓰기였다면 시스템 시계를 드라이버 몰래 바꿨을 것이다.
- **[4]** RAM(0x40000000)은 거부 — `mmap: Operation not permitted`. `CONFIG_STRICT_DEVMEM=y` 때문이다.
- **[5]** 드라이버가 `pci_request_regions_exclusive()`로 잡으면(dmesg의 두 번째 `ID=` 줄이 `excl=1` 로드) devmem도 거부된다.
- **[6]** `rmmod` 후에도 읽힌다. 6.18의 `pci_disable_device()`(`do_pci_disable_device()`)는 Bus Master 비트만 끄고 Memory Space Enable은 그대로 둔다(랩 소스 `drivers/pci/pci.c` 2184행). 드라이버가 떠난 뒤에도 BAR가 살아 있다.

### 9.3 커널은 무엇을 막나 — STRICT_DEVMEM의 실제 규칙

랩 커널 설정: `CONFIG_DEVMEM=y`, `CONFIG_STRICT_DEVMEM=y`, `# CONFIG_IO_STRICT_DEVMEM is not set`. 그리고 판정 함수(랩 소스 `lib/devmem_is_allowed.c`, arm64가 쓰는 일반 구현):

```c
int devmem_is_allowed(unsigned long pfn)
{
	if (iomem_is_exclusive(PFN_PHYS(pfn)))
		return 0;
	if (!page_is_ram(pfn))
		return 1;
	return 0;
}
```

`iomem_is_exclusive()` → `resource_is_exclusive()`(`kernel/resource.c`)의 핵심:

```c
		if (!strict_iomem_checks || !(p->flags & IORESOURCE_BUSY))
			continue;
		if (IS_ENABLED(CONFIG_IO_STRICT_DEVMEM)
				|| p->flags & IORESOURCE_EXCLUSIVE) {
			err = true;
			break;
		}
```

정리하면:

| 대상 | STRICT_DEVMEM만 (이 랩) | + IO_STRICT_DEVMEM | 부팅 인자 `iomem=relaxed` |
|---|---|---|---|
| System RAM | 거부 | 거부 | 거부 |
| 드라이버가 안 잡은 MMIO | 허용 | 허용 | 허용 |
| 드라이버가 잡은(BUSY) MMIO | **허용** (실험 [2], [3]) | 거부 | 허용 |
| `IORESOURCE_EXCLUSIVE`로 잡은 MMIO | 거부 (실험 [5]) | 거부 | 허용 (단 RAM+EXCLUSIVE는 거부) |

`request_mem_region_exclusive()`나 `pci_request_regions_exclusive()`가 `IORESOURCE_EXCLUSIVE`를 붙인다(`include/linux/ioport.h`: "Userland may not map this resource"). 이 플래그는 sysfs PCI `resourceN` 파일의 mmap도 막는다(`drivers/pci/pci-sysfs.c` 1121행이 `iomem_is_exclusive()`를 본다). `IO_STRICT_DEVMEM`이 켜진 커널에서는 드라이버가 나중에 영역을 잡는 순간 이미 열려 있던 `/dev/mem` 매핑까지 회수한다(`revoke_iomem()` — 랩 소스 주석이 "iomem=relaxed says 'go ahead, what's the worst that can happen?'"라며 `*cringe*`라고 적어 둔 부분).

### 9.4 그래서 `/dev/mem`이 나쁜 이유

1. **소유권이 없다.** 실험 [2]처럼 드라이버가 쓰는 레지스터를 드라이버 모르게 바꾼다. 드라이버의 소프트웨어 상태(캐시해 둔 레지스터 값, 상태 머신)와 하드웨어가 어긋난다.
2. **락이 없다.** 드라이버의 스핀락(§6)을 유저 프로그램이 잡을 방법이 없다. RMW 경쟁이 보장된다.
3. **배리어·폭 API가 없다.** 유저 코드는 `volatile` 포인터로 접근한다 — §8의 문제(병합, `ldp`, 순서)가 그대로 온다. 접근 폭은 devmem의 WIDTH 인자가 정한다(잘못 주면 §3.5의 버스 에러가 유저 프로세스의 SIGBUS가 된다).
4. **메모리 속성 불일치.** §2.2: `/dev/mem`은 nGnRnE, 드라이버는 nGnRE. RAM을 막는 이유는 Normal Cacheable과의 불일치 + 커널 메모리 노출이다.
5. **보안.** root가 `/dev/mem`으로 DMA 엔진 레지스터를 프로그래밍하면 커널 메모리를 아무 데나 쓸 수 있다(STRICT_DEVMEM도 DMA를 통한 우회는 못 막는다 — IOMMU가 필요하다, H9). Secure boot·lockdown(`lockdown=integrity`)이 켜진 시스템은 `/dev/mem` 자체를 막는다(L 모듈 — 이 노트에서 실행하지 않음).
6. **인터럽트를 못 받는다.** 레지스터는 읽어도 IRQ는 커널 것이다. 결국 폴링만 하게 된다.
7. **이식성·생명주기.** 물리 주소가 코드에 박힌다. 장치 전원·클럭 관리(runtime PM, H3)를 모른다 — 클럭이 꺼진 블록을 읽으면 버스가 멈추는 SoC도 있다.

**언제 써도 되나**: bring-up 첫날 레지스터를 "읽어 보는" 용도, 드라이버가 없는 블록의 1회성 확인, 디버그 빌드의 진단. 제품 이미지에서는 `CONFIG_DEVMEM=n` 또는 최소한 STRICT + IO_STRICT를 권한다.

### 9.5 예제 10 — UIO: 유저스페이스 드라이버를 제대로 하는 법

유저스페이스에서 장치를 다뤄야 할 정당한 경우(FPGA 레지스터 블록, 산업용 I/O 카드, DPDK 같은 고성능 경로)를 위해 커널은 **UIO**(Userspace I/O)와 **VFIO**를 준다. UIO는 작은 커널 드라이버가 (1) 장치를 소유하고(probe), (2) 매핑할 수 있는 영역을 `/dev/uioN`의 mmap으로 내보내고, (3) 인터럽트를 받아 `read()`/`poll()`로 유저에게 알린다. 레지스터 로직은 유저가 짠다.

랩 커널은 `CONFIG_UIO`가 꺼져 있다. 그래서 랩 소스의 `drivers/uio/uio.c`와 `uio_pci_generic.c` 두 파일만 복사해 out-of-tree로 빌드했다.

```c
/* h1_uio.c — 유저스페이스 드라이버: uio_pci_generic이 준 /dev/uio0로 edu를 다룬다 */
#include <fcntl.h>
#include <poll.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <unistd.h>

#define CFG "/sys/class/uio/uio0/device/config"
static void die(const char *m) { perror(m); exit(1); }

static void intx_unmask(int cfd)	/* PCI Command bit10(INTx Disable)을 0으로 */
{
	uint16_t cmd;

	if (pread(cfd, &cmd, 2, 4) != 2)
		die("pread");
	cmd &= ~(1u << 10);
	if (pwrite(cfd, &cmd, 2, 4) != 2)
		die("pwrite");
}

int main(void)
{
	int ufd = open("/dev/uio0", O_RDWR), cfd = open(CFG, O_RDWR);
	uint32_t cnt;
	struct pollfd p = { .events = POLLIN };

	if (ufd < 0 || cfd < 0)
		die("open");
	/* map N은 offset N * pagesize — map0 = BAR0 */
	volatile uint32_t *r = mmap(NULL, 1 << 20, PROT_READ | PROT_WRITE, MAP_SHARED, ufd, 0);
	if (r == MAP_FAILED)
		die("mmap");
	printf("ID=0x%08x\n", r[0x00 / 4]);
	r[0x04 / 4] = 0xa5a5a5a5;
	printf("liveness ~0xa5a5a5a5 = 0x%08x\n", r[0x04 / 4]);
	r[0x60 / 4] = 0x1234;				/* 인터럽트 올리기 */
	p.fd = ufd;
	if (poll(&p, 1, 1000) != 1 || read(ufd, &cnt, 4) != 4)
		die("wait irq");
	printf("irq event count=%u, irq status(0x24)=0x%x\n", cnt, r[0x24 / 4]);
	r[0x64 / 4] = 0x1234;				/* ack: 장치 쪽 라인 내리기 */
	__asm__ __volatile__("dmb osh" ::: "memory");	/* 유저에겐 writel이 없다 */
	intx_unmask(cfd);				/* 커널 핸들러가 막아 둔 INTx 다시 열기 */
	printf("after ack status=0x%x\n", r[0x24 / 4]);
	return 0;
}
```

출력에서 볼 것:

- `new_id`에 "1234 11e8"을 쓰면 `uio_pci_generic`이 edu에 바인드된다. `/dev/uio0`이 생기고 map0 = BAR0(0x10000000, 1 MB).
- 유저 프로그램이 BAR0를 mmap해서 ID와 liveness를 읽고 썼다 — 여기까지는 devmem과 같다.
- 다른 점은 **인터럽트**다. 0x60에 쓰자 edu가 INTx를 올렸고, 커널의 `uio_pci_generic` 핸들러가 받아서 `pci_check_and_mask_intx()`로 PCI 레벨에서 INTx를 막은 뒤 유저를 깨웠다. 유저는 `poll()` → `read()`로 이벤트 수 1을 받았다. `/proc/interrupts`의 `22: 1 ... uio_pci_generic`(GIC SPI 37, level)이 그 인터럽트다. 유저가 장치 쪽 원인을 지우고(0x64 ack) PCI Command의 INTx Disable 비트(bit10)를 풀어 다음 인터럽트를 받을 준비를 한다. `uio_pci_generic`에는 `irqcontrol` 콜백이 없어서 `write(/dev/uio0)`로 다시 켜는 방식은 안 된다 — 처음 시도에서 `write: Function not implemented`(`ENOSYS`, `uio.c` 660행)가 나와 config 공간 쓰기로 바꿨다.
- `/proc/iomem`에 `0000:00:02.0` 아래 BUSY 항목이 **없다.** `uio_pci_generic`은 BAR를 request하지 않는다. 그러니 다른 드라이버나 devmem과의 충돌을 막아 주지 않는다 — UIO가 "제대로"라고 했지만 소유권 면에서는 이 일반 드라이버가 느슨하다. VFIO(`vfio-pci`)는 IOMMU로 DMA까지 격리하고 영역도 잡는다(H9·H11에서 다룬다, 이 노트에서는 실행하지 않음).
- 유저 코드에는 `readl`/`writel`이 없어서 `volatile` 포인터 + 직접 넣은 `dmb osh`로 순서를 챙겼다. 유저스페이스 드라이버가 짊어지는 몫이다.

단계별로 랩 소스에서 확인한 것:

1. `platform_get_resource()` — DT `reg`가 부팅 때 `struct resource`로 바뀌어 `pdev->resource[]`에 들어가 있다(D4). PCI면 `pdev->resource[bar]`가 enumeration 때 채워진다(H11).
2. `__devm_ioremap_resource()`(`lib/devres.c` 124행) — 이름을 만들고(`dev_name` + resource 이름), `devm_request_mem_region()` 실패 시 `dev_err_probe(dev, -EBUSY, "can't request region for resource %pR\n", res)`. 실험 1의 메시지 그대로다. resource에 `IORESOURCE_MEM_NONPOSTED`가 있으면 매핑 타입을 NP로 바꾼다(§2.1).
3. `__request_region()`(`kernel/resource.c`) — `resource_lock` 아래에서 부모 자원을 따라 내려가며 겹치는 자식을 찾는다. 겹치는 것이 BUSY면 실패. (`IORESOURCE_MUXED` 같은 공유 예외도 있다.) 성공하면 BUSY 플래그를 단 새 노드를 트리에 넣는다. 이 트리가 `/proc/iomem`이다.
4. `ioremap()` → `__ioremap_prot()`(`arch/arm64/mm/ioremap.c`) — `PHYS_MASK` 밖이면 거부, RAM이면 `WARN_ON` + NULL(실험 2), confidential computing용 훅이 있으면 호출.
5. `generic_ioremap_prot()`(`mm/ioremap.c` 15행) — 페이지 정렬(오프셋은 나중에 더해서 돌려준다), `__get_vm_area_caller(size, VM_IOREMAP, IOREMAP_START, IOREMAP_END, caller)`로 vmalloc 영역의 빈 구간을 잡고(이게 `/proc/vmallocinfo`의 `ioremap` 줄, caller = `__ioremap_prot+0x64`), `ioremap_page_range()`로 PTE를 채운다. 이때 PTE의 AttrIndx = `MT_DEVICE_nGnRE`. 큰 영역이면 블록 매핑(2 MB 등)을 쓸 수도 있다.
6. 접근: `readl(base + off)` → `ldr`(이 게스트에서는 `ldar`) → MMU가 VA → PA 변환, Device 속성 → 버스 트랜잭션.
7. 해제: devres가 역순으로 `iounmap()`(vm 영역 해제 + TLB 무효화)과 `release_mem_region()`.

드라이버를 짤 때 다시 만나는 지점:

- `devm_platform_ioremap_resource()` — G3의 정석 probe 순서에서 "자원 → 매핑" 단계.
- `IS_ERR()` vs NULL 검사 — E5의 에러 처리 관례.
- `/proc/iomem`, `/proc/vmallocinfo` — M 모듈의 디버깅 도구.
- regmap-mmio(H2)는 이 매핑 위에 락·캐시를 얹은 것이고, syscon은 "한 주인이 매핑하고 여럿이 regmap으로 공유"하는 해법이다.
- DMA를 하는 장치(H9)는 레지스터는 `ioremap`, 버퍼는 `dma_alloc_coherent`로 — 두 세계 사이의 순서를 `writel`의 배리어가 잇는다(F5 §6).

## 11. Embedded 실무에서 다시 보기

### 11.1 센서 키트 — FPGA 타임스탬프 블록을 UIO로 할까 드라이버로 할까

예를 들어 센서 키트라면, 카메라·IMU·LiDAR 트리거를 하나의 하드웨어 시계로 맞추는 작은 FPGA 블록(레지스터 몇 개 + "트리거 발생" 인터럽트)이 SoC의 AXI 버스에 붙어 있다고 하자.

- **빠른 시작**: DT에 `compatible = "generic-uio"` 노드를 두고 `uio_pdrv_genirq`를 모듈 파라미터 `of_id=generic-uio`로 로드하면(이 드라이버는 매칭할 compatible을 `of_id` 파라미터로 받는다) 커널 코드 0줄로 유저 프로그램이 레지스터와 IRQ를 쓸 수 있다. 시제품 단계에서 흔하다(이 노트에서는 PCI용 `uio_pci_generic`만 실행했다).
- **제품화**: 타임스탬프를 다른 커널 서브시스템(V4L2 버퍼 타임스탬프, IIO 트리거, PTP 시계)과 엮어야 하면 커널 드라이버가 필요하다. 이때 이 노트의 뼈대 — `devm_platform_ioremap_resource` + `readl_poll_timeout` + 공유 레지스터 락 — 가 그대로 쓰인다.

### 11.2 "칩 ID가 0xffffffff예요" — bring-up 진단 순서

1. `cat /proc/iomem` — 그 주소를 누가 잡았나, DT `reg`가 맞게 들어왔나.
2. `devmem <base+ID_OFFSET> 32` — 드라이버를 거치지 않고 읽어 본다(디버그 이미지에서). `0xFFFFFFFF`면 PCIe 링크 다운·디코딩 꺼짐(§9 실험 [1]), `0x00000000`이나 버스 hang이면 클럭 게이트·리셋 유지(H3)를 의심한다.
3. 클럭·전원·리셋 확인: `/sys/kernel/debug/clk/clk_summary`, regulator, reset 상태(H3).
4. 접근 폭 확인: 레지스터 맵이 32비트 전용인데 `readb`/`readw`나 `memcpy`를 쓰고 있지 않나(§3.5).
5. 드라이버에 `readl_poll_timeout` 실패 시 마지막 값 로그가 있는지 확인 — 없으면 추가한다.

### 11.4 코드 리뷰 체크리스트 (MMIO 부분)

- 매핑 반환값 검사 방식(`IS_ERR` vs NULL)이 API와 맞나.
- `__iomem` 포인터를 접근자 밖에서 역참조하거나 `__force` 없이 캐스팅하지 않았나 — `make C=1`.
- 모든 대기에 타임아웃이 있고, 실패 시 마지막 값을 로그로 남기나. 문맥(원자/수면)에 맞는 변형인가.
- 여러 경로(IRQ 포함)에서 RMW하는 레지스터에 락이 있나.
- `_relaxed`를 쓴 곳마다 "같은 장치끼리만 순서가 필요하다"는 이유가 있나(F5 §5.5).
- 레지스터 맵의 폭을 지키나, `memcpy` 대신 `memcpy_fromio`인가.

## 13. 면접에서 이렇게 말한다

**Q.** Why can't a Linux driver just cast the physical register address to a volatile pointer like in bare-metal firmware?

**A.** 커널도 MMU를 켠 가상 주소로 돈다. 장치 레지스터는 linear map에 없으니 `ioremap`으로 vmalloc 영역에 Device-nGnRE 속성 PTE를 만들어야 접근할 수 있다. 주소는 하드코딩하지 않고 DT `reg`나 PCI BAR에서 받고, `request_mem_region`으로 소유권을 표시한다. 보통은 `devm_platform_ioremap_resource` 한 줄이 이걸 다 한다.

> The kernel runs with the MMU on, so a physical address isn't directly usable. Device registers aren't in the linear map, so the driver calls ioremap, which reserves a chunk of vmalloc space and creates page-table entries with the Device-nGnRE attribute on arm64. The physical address comes from the device tree or the PCI BAR, not a constant, and request_mem_region marks ownership so two drivers can't silently share a block. In a platform driver, devm_platform_ioremap_resource does the request, the mapping and the cleanup in one call.

**꼬리 질문**: "ioremap 주소를 그냥 역참조하면 arm64에서 동작하던데요?" → §8.5의 다섯 가지(컴파일러 병합·제거, 배리어 없음, 이식성, KVM의 ISV, tracing).

**Q.** What's the difference between readl and readl_relaxed? When would you use the relaxed version?

**A.** arm64에서 `readl`은 `ldr` 뒤에 `dmb oshld`와 가짜 의존을 붙여서, 뒤따르는 일반 메모리 읽기(DMA 버퍼)와 delay가 MMIO 읽기를 앞지르지 못하게 한다. `writel`은 앞에 `dmb oshst`를 붙여 앞선 메모리 쓰기를 먼저 보이게 한다. `_relaxed`는 접근만 있고, 같은 장치에 대한 MMIO끼리의 순서만 Device 속성으로 보장된다. 그래서 FIFO 연속 읽기나 레지스터 초기화 시퀀스처럼 메모리와 엮이지 않는 hot path에만 쓰고, DMA 시작이나 완료 확인에는 non-relaxed를 쓴다.

> On arm64, readl is a load followed by a dmb oshld plus a fake control dependency, so later normal-memory reads, like reading a DMA buffer, and delay loops can't overtake it. writel puts a dmb oshst before the store so earlier memory writes, like descriptors, are visible to the device first. The relaxed variants are just the load or store; they're only ordered against other MMIO to the same device, which the Device memory type guarantees. I default to readl/writel and switch to relaxed only in measured hot paths that don't interact with DMA memory, like draining a FIFO, with a comment explaining why.

**꼬리 질문**: "그 차이를 측정해 봤나요?" → TCG에선 잡음에 묻혔다(§7), 실제 하드웨어에선 PMU로 재야 하고, MMIO 읽기 자체가 비싸서 대개 읽기 횟수를 줄이는 게 더 큰 이득이다.

**Q.** How do you wait for a hardware status bit in a Linux driver?

**A.** `readl_poll_timeout(addr, val, cond, sleep_us, timeout_us)`을 쓴다. 잘 수 있는 문맥이면 이것, IRQ 핸들러나 스핀락 안이면 `_atomic` 변형이다. 이 매크로는 만료 여부를 먼저 계산하고 한 번 더 읽은 뒤 판정하므로, 선점돼서 늦게 깨어나도 거짓 타임아웃이 안 난다. 실패하면 `-ETIMEDOUT`과 마지막 값을 로그에 남긴다. timeout 0은 무한대기라 쓰지 않는다. 인터럽트가 있으면 폴링 대신 completion으로 기다린다.

> I use readl_poll_timeout with a sleep interval and a timeout, or the _atomic variant if I'm in interrupt context or holding a spinlock. The macro computes whether the deadline passed before doing the final read, so being preempted doesn't cause a false timeout. On failure it returns -ETIMEDOUT and leaves the last value in val, which I always log. A zero timeout means wait forever, so I never pass zero. If the device has a completion interrupt, I'd rather wait on a completion than poll at all.

**Q.** Why is using /dev/mem (or devmem) to control hardware a bad idea in production?

**A.** 커널의 소유권·락·배리어를 전부 우회한다. 실험에서 드라이버가 BAR를 잡고 있는데도 devmem으로 레지스터를 덮어쓸 수 있었다 — STRICT_DEVMEM은 RAM만 막고, 드라이버가 EXCLUSIVE로 잡거나 IO_STRICT_DEVMEM이 켜져야 MMIO가 막힌다. 인터럽트도 못 받고, 메모리 속성도 드라이버와 다르고, DMA 엔진을 통해 커널 메모리를 쓸 수 있는 보안 구멍이다. 유저스페이스 드라이버가 정말 필요하면 UIO나 VFIO를 쓴다.

> It bypasses everything the kernel provides: ownership, locking, barriers, power management and interrupts. With STRICT_DEVMEM, only RAM is blocked; MMIO that a driver has claimed is still accessible unless the driver requested it exclusive or IO_STRICT_DEVMEM is enabled — I verified that devmem could overwrite a register while my driver held the BAR. It's also a security hole, since programming a DMA engine from user space can write kernel memory. For bring-up it's a great peek tool; for production I'd write a driver, or use UIO or VFIO if the logic really belongs in user space.

**꼬리 질문**: "UIO와 VFIO 차이는?" → UIO는 매핑 + IRQ 통지만, DMA 격리가 없다. VFIO는 IOMMU로 장치의 DMA를 프로세스 주소 공간에 가둔다(H9·H11).

**Q.** Two code paths update different bits of the same control register. What can go wrong and how do you fix it?

**A.** RMW 경쟁으로 한쪽 비트가 사라진다. QEMU `-smp 2`에서 락 없이 돌리니 2만 번 중 약 8~10%가 유실됐고 스핀락을 거니 0이었다. 같은 레지스터를 만지는 모든 경로가 `spin_lock_irqsave`로 감싼 update-bits 헬퍼를 지나게 하거나 regmap의 `regmap_update_bits`를 쓴다. 하드웨어에 SET/CLR 레지스터가 있으면 RMW 자체를 없앤다.

> It's a read-modify-write race: both paths read the old value and the later write wipes out the other's bit. I reproduced it on a two-CPU QEMU guest — without a lock about eight to ten percent of the updates were lost, with a spinlock zero. The fix is to route every access to that register through one update-bits helper under spin_lock_irqsave, since interrupt handlers may touch it too, or use regmap_update_bits. If the hardware offers set/clear registers, I use those and avoid the read-modify-write entirely.

**Q.** What memory attributes does ioremap use on arm64, and what are ioremap_wc and ioremap_np for?

**A.** `ioremap`은 Device-nGnRE — 합치기·재배치 금지, early write ack 허용(posted). `ioremap_np`는 nGnRnE로 쓰기 응답이 장치에서 와야 하는 플랫폼용(PCI BAR에는 쓰지 않는다). `ioremap_wc`는 Normal Non-cacheable로 쓰기를 합칠 수 있어 프레임버퍼 같은 큰 버퍼에 쓴다. `ioremap_cache`는 Normal WB. 그리고 arm64는 RAM에 `ioremap`을 거부하므로 RAM은 `memremap`이다.

> Plain ioremap maps the region as Device-nGnRE: no gathering, no reordering to the same device, but early write acknowledgement is allowed, so writes are posted. ioremap_np uses nGnRnE for platforms that need non-posted writes, like Apple Silicon, and it's not for PCI BARs. ioremap_wc uses Normal non-cacheable so writes can be combined, which suits framebuffers. ioremap_cache is normal write-back. And arm64 refuses to ioremap RAM — for RAM you use memremap.

**Q.** A register read returns 0xFFFFFFFF. What do you check?

**A.** PCIe면 링크 다운이나 Memory Space Enable이 꺼진 상태(실험에서 드라이버 없이 BAR를 읽으니 정확히 이 값)이고, surprise removal 판정에도 쓰인다. SoC IP면 클럭 게이트·리셋·전원 도메인을 본다. `/proc/iomem`으로 주소·소유권을, devmem으로 드라이버를 거치지 않은 값을 확인하고, 접근 폭도 확인한다.

> On PCIe, all-ones usually means the device didn't respond — link down, the function was removed, or memory decoding isn't enabled; I saw exactly that reading the BAR before pci_enable_device. For an SoC block, I check that its clock is enabled, its reset is released and its power domain is on. Then I verify the address in /proc/iomem, peek with devmem on a debug build to rule out the driver, and make sure the access width matches the register map.

## 14. 직접 해보기

1. **개념**: `devm_ioremap()`와 `devm_ioremap_resource()`의 차이를 `/proc/iomem`에 남는 흔적으로 설명하라. 실험 1에서 `h1_rtc`가 매핑에 성공한 뒤 `/proc/iomem`에 `h1_rtc` 항목이 있을까?
   정답/힌트: 없다. `devm_ioremap()`은 request를 하지 않으므로 BUSY 노드를 만들지 않는다 — vmallocinfo에만 매핑이 보인다.
2. **코드**: `h1_rtc`에 PL031 Match 레지스터(0x04)를 `writel`로 바꾸는 코드를 넣지 말고, 대신 "같은 블록을 두 드라이버가 쓰면 위험한 이유"를 rtc-pl031 소스(`drivers/rtc/rtc-pl031.c`)에서 Match 레지스터를 쓰는 함수를 찾아 설명하라.
   정답/힌트: `pl031_set_alarm()` 계열이 알람 시각을 쓴다. 우리가 몰래 쓰면 알람 상태가 드라이버의 소프트웨어 상태와 어긋난다.
3. **코드**: `h1_edu`의 factorial을 IRQ 방식으로 바꿔라 — status에 0x80(끝나면 IRQ)을 켜고, `request_irq`로 핸들러를 달아 0x24를 읽고 0x64로 ack한 뒤 `complete()`, probe에서는 `wait_for_completion_timeout()`. 폴링 버전과 지연을 비교하라.
   정답/힌트: `pci_alloc_irq_vectors(pdev, 1, 1, PCI_IRQ_INTX)` → `pci_irq_vector()`. INTx는 공유 가능하니 `IRQF_SHARED`와 "내 인터럽트인지" 확인(0x24 == 0이면 `IRQ_NONE`).
4. **관찰**: 게스트에서 `cat /proc/vmallocinfo` 전체에서 `ioremap` 줄을 세어 보고, 각 caller가 어느 드라이버인지(`pl011`, `pl061`, `pcie` ECAM 등) 크기로 추정하라. ECAM 창은 몇 MB인가?
   정답/힌트: caller가 모두 `__ioremap_prot`로 보이니 크기와 `phys=`로 `/proc/iomem`과 맞춘다. ECAM은 버스당 1 MB.
5. **sparse**: `h1_acc.c`에서 `extern` 선언 세 줄을 지우고 `make C=2`를 돌려 경고를 확인하라. 왜 export하는 전역 변수는 헤더에 선언해야 하나?
   정답/힌트: "symbol 'h1_reg' was not declared. Should it be static?" — 선언과 정의의 타입이 다른 버그를 링커가 못 잡기 때문이다.
6. **devmem**: 부팅 인자에 `iomem=relaxed`를 넣고 `h1_edu excl=1` 실험 [5]를 다시 하라. 결과가 어떻게 바뀌나?
   정답/힌트: `strict_iomem_checks = 0`이 되어 EXCLUSIVE MMIO도 허용된다(RAM은 여전히 `page_is_ram`으로 거부). §9.3의 표 마지막 열.
7. **측정**: `h1_bench`의 N을 200,000으로 늘리고 `-smp 1`과 `-smp 2`에서 돌려 분산이 줄어드는지 보라. 측정 루프 앞뒤에 `local_irq_save`를 넣으면?
   정답/힌트: 인터럽트가 끼어드는 몫이 줄어 최대값이 내려간다. 그래도 TCG의 숫자는 실리콘의 숫자가 아니다.

## 15. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| MMIO | Memory-Mapped I/O | 장치 레지스터를 메모리 주소로 읽고 쓰는 방식 |
| `ioremap` | I/O remap | 물리 레지스터를 커널 가상 주소에 Device 속성으로 매핑 |
| `__iomem` | MMIO 주소 공간 표시 | gcc에겐 빈 매크로, sparse에겐 noderef + 별도 주소 공간 |
| sparse | 커널 정적 분석기 | `make C=1/2`로 실행, 주소 공간·엔디언·락 문맥 검사 |
| Device-nGnRE | arm64 메모리 타입 | 합치기·재배치 금지, early write ack 허용 — `ioremap` 기본값 |
| Device-nGnRnE | arm64 메모리 타입 | non-posted — `ioremap_np`, `/dev/mem` 매핑 |
| MAIR_EL1 | Memory Attribute Indirection Register | PTE의 AttrIndx가 가리키는 속성 표 (Attr4 = 0x04) |
| `request_mem_region` | 소유권 요청 | `/proc/iomem` 트리에 BUSY 노드 삽입, 충돌 시 실패 |
| `IORESOURCE_EXCLUSIVE` | 배타 자원 플래그 | `/dev/mem`·sysfs mmap까지 금지 |
| `readl` / `writel` | 32비트 MMIO 접근자 | LE 변환 + 일반 메모리와의 순서 배리어 포함 |
| `_relaxed` | 배리어 없는 접근자 | 같은 장치 MMIO끼리 순서만 보장 |
| `readl_poll_timeout` | 폴링 매크로 | 조건이 맞을 때까지 읽기, 수면 간격·타임아웃 |
| posted write | 응답 없는 쓰기 | CPU는 끝났다고 보지만 장치 도착은 미확인 — read-back으로 확인 |
| BAR | Base Address Register | PCI 장치가 요구하는 주소 창, OS가 배정 |
| Memory Space Enable | PCI Command bit1 | 꺼져 있으면 BAR 주소에 응답 안 함 (`0xFFFFFFFF`) |
| `/dev/mem` | 물리 메모리 문자 장치 | 물리 주소를 mmap — STRICT_DEVMEM이 RAM 차단 |
| UIO | Userspace I/O | 커널은 매핑·IRQ 통지만, 레지스터 로직은 유저 |
| VFIO | Virtual Function I/O | IOMMU로 DMA까지 격리한 유저스페이스 장치 접근 |
| ISV | Instruction Syndrome Valid | data abort가 접근 정보를 제공하는지 — `ldp`는 0, KVM MMIO 에뮬레이션 불가 |
| erratum 832075 | Cortex-A57 결함 | Device load 순서 문제 — 커널이 MMIO `ldr`을 `ldar`로 패치 |

## 16. 요약 & 체크리스트

bare-metal에서 `*(volatile u32 *)ADDR` 한 줄이던 MMIO는 Linux에서 네 단계가 된다. 주소는 DT `reg`나 PCI BAR에서 받고(하드코딩 금지), `request_mem_region`으로 소유권을 표시하고(`/proc/iomem`, 충돌 시 `-EBUSY`), `ioremap`으로 Device-nGnRE 속성의 커널 가상 주소를 얻고(RAM은 거부, `memremap` 사용), `readl`/`writel` 같은 접근자로만 만진다. 이 세 단계를 `devm_platform_ioremap_resource()`(PCI는 `pcim_iomap_region()`) 한 줄이 해 주고 해제도 자동이다. 접근자는 폭·엔디언·배리어를 책임지며 arm64에서 `readl` = `ldr` + `dmb oshld` + 가짜 의존, `writel` = `dmb oshst` + `str`, `_relaxed`는 접근만이다. `__iomem`을 직접 역참조하면 arm64에서 값은 맞게 읽혀도 컴파일러가 읽기를 루프 밖으로 빼거나 `ldp`로 합치고, KVM 게스트에서는 에뮬레이트할 수 없는 명령이 된다 — sparse(`make C=1`)가 잡는다. 하드웨어를 기다릴 때는 `readl_poll_timeout`(원자 문맥은 `_atomic`)으로 타임아웃을 걸고, 공유 레지스터 RMW는 락으로 감싼다(실험에서 락 없이 약 8~10% 유실). `/dev/mem`은 RAM만 막을 뿐 드라이버가 잡은 레지스터도 덮어쓸 수 있으니 bring-up 확인용으로만 쓰고, 유저스페이스 드라이버가 필요하면 UIO/VFIO를 쓴다.

- [ ] 물리 레지스터 → `request_mem_region` → `ioremap` → PTE(AttrIndx/MAIR) → VA → `readl`의 경로를 그림으로 그릴 수 있다
- [ ] `ioremap`/`devm_ioremap`/`devm_ioremap_resource`/`devm_platform_ioremap_resource`/`pcim_iomap_region`의 차이와 반환값 검사법(NULL vs `IS_ERR`)을 말할 수 있다
- [ ] `/proc/iomem`에서 `-EBUSY`의 원인을 찾고, BUSY 깃발이 협조적 잠금이라는 것을 설명할 수 있다
- [ ] `ioremap`/`ioremap_np`/`ioremap_wc`/`ioremap_cache`의 arm64 속성과 RAM에 `memremap`을 쓰는 이유를 말할 수 있다
- [ ] `readl`·`readl_relaxed`·`__raw_readl`·`ioread32`·`ioread32be`가 arm64에서 되는 명령을 objdump로 보일 수 있다
- [ ] `__iomem` 직접 역참조가 왜 틀렸는지 다섯 가지 이유(컴파일러, 배리어, 이식성, KVM ISV, tracing)로 설명할 수 있다
- [ ] `readl_poll_timeout`/`_atomic`을 문맥에 맞게 골라 쓰고, 만료 판정 순서와 timeout 0의 의미를 설명할 수 있다
- [ ] 공유 레지스터 RMW 경쟁을 재현하고 스핀락 헬퍼(또는 regmap)로 고칠 수 있다
- [ ] 접근 폭 위반이 synchronous external abort(또는 SError)가 되는 과정을 설명할 수 있다
- [ ] PCI 드라이버에서 `pcim_enable_device`가 Memory Space Enable을 켠다는 것과 `0xFFFFFFFF`의 의미를 말할 수 있다
- [ ] STRICT_DEVMEM·IO_STRICT_DEVMEM·`IORESOURCE_EXCLUSIVE`·`iomem=relaxed`가 `/dev/mem`에 미치는 효과를 표로 말할 수 있다
- [ ] UIO로 유저스페이스에서 레지스터와 IRQ를 다루는 흐름과 그 한계(소유권, DMA 격리)를 설명할 수 있다
