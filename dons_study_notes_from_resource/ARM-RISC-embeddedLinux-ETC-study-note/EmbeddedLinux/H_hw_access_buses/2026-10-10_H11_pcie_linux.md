# H11. PCIe (Linux 관점) — enumeration, config space, BAR, pci_driver, MSI/MSI-X, 디버그

> **이 노트를 다 읽으면**: Linux가 부팅 때 host bridge(DT의 `pci-host-ecam-generic`, SoC의 DWC 컨트롤러)에서 출발해 버스를 스캔하고 BAR·bridge window를 배정하는 과정을 dmesg 한 줄 한 줄로 읽을 수 있다 · `struct pci_dev` ↔ sysfs ↔ config space를 오가며 lspci 없이도 장치를 해부할 수 있다 · `pcim_enable_device` → `pcim_iomap_region` → `pci_alloc_irq_vectors` → `dma_set_mask_and_coherent`로 이어지는 현대식 `pci_driver`를 직접 짜서 MSI/INTx로 인터럽트를 받을 수 있다 · AER 복구, remove/rescan, SR-IOV, VFIO 유저 공간 드라이버가 커널의 어디에 걸리는지 설명할 수 있다
> **왜 필요한가**: NVMe·Wi-Fi·5G 모뎀·AI 가속기(Hailo, Jetson의 NVMe, i.MX8의 PCIe Wi-Fi)는 전부 PCIe로 붙는다. 면접에서는 "probe에서 뭘 하나요?", "MSI-X가 왜 좋나요?", "BAR 할당이 실패하면?", "VFIO는 뭐고 왜 IOMMU가 필요한가요?"가 나온다
> **Don 기준 난이도**: PCIe 프로토콜·LTSSM·config space·BAR·MSI-X 테이블·AER 레지스터는 SSD 펌웨어(장치 쪽)에서 이미 몸에 붙어 있다 / 새로 배울 부분은 **호스트 쪽 Linux 소프트웨어**: PCI core가 그 레지스터들을 언제 누가 읽고 쓰는지, 드라이버가 쓰는 managed API, irq_domain을 통한 MSI 배선, IOMMU와 DMA mask, VFIO
> **선행 노트**: D1(discoverable vs DT), G2·G3(디바이스 모델·probe 수명주기), H1(MMIO), H6(irq_domain), H9(DMA) — H6·H9는 없어도 읽을 수 있게 필요한 만큼 다시 설명한다

## 0. 큰 그림 — Don이 서 있던 자리의 반대편

Don이 SSD 펌웨어에서 본 PCIe는 **엔드포인트 쪽**이었다. 호스트가 config space를 읽으면 대답하고, BAR에 주소가 써지면 그 주소로 들어오는 TLP를 받고, MSI-X 테이블에 호스트가 써 둔 주소·데이터로 메모리 쓰기를 날리면 인터럽트가 됐다. 그 "호스트"가 바로 이 노트의 주인공인 **Linux PCI 서브시스템**이다. 이번에는 반대편 자리에 앉아서, 그 config read를 누가 언제 보내는지, BAR 주소를 누가 정하는지, MSI-X 테이블에 무슨 값을 써 넣는지를 본다.

bare-metal 비유로 말하면 이렇다.

D1에서는 QEMU 기본 장치만 봤다. 이번에는 Don의 실무 토폴로지에 가깝게 **Root Port 3개 + 그 뒤의 엔드포인트**를 꽂는다. 모든 예제는 아래 스크립트 하나로 부팅한다 (VM `elinux`, Ubuntu 26.04, 호스트 커널 `uname -r` = `7.0.0-38-generic`, QEMU 10.2.1; 게스트는 랩 커널 **6.18.55**).

## 1. Host bridge — 모든 것은 DT 노드 하나에서 시작한다

### 1.1 직관

D1에서 봤듯 PCIe 아래의 장치들은 스스로 말하지만, **Root Complex 자체**는 그렇지 않다. CPU 주소 공간의 어디에 ECAM이 있는지, 어느 CPU 주소 구간을 PCI 메모리 공간으로 쓸지(window), INTx A~D가 GIC의 몇 번으로 가는지, MSI는 어느 컨트롤러가 받는지 — 이 네 가지를 DT가 알려 주고, host bridge 드라이버가 그걸로 `struct pci_host_bridge`를 만든 뒤 PCI core에 "이제 스캔해"라고 넘긴다.

```dts
pcie@10000000 {
    compatible = "pci-host-ecam-generic";
    device_type = "pci";
    reg = <0x40 0x10000000 0x00 0x10000000>;          /* ECAM 256 MiB = 256 버스 x 1 MiB */
    bus-range = <0x00 0xff>;
    ranges = <0x01000000 0x00 0x00 0x00 0x3eff0000 0x00 0x10000>,        /* I/O */
             <0x02000000 0x00 0x10000000 0x00 0x10000000 0x00 0x2eff0000>, /* 32-bit MEM */
             <0x03000000 0x80 0x00 0x80 0x00 0x80 0x00>;                  /* 64-bit MEM */
    interrupt-map = < ... >;                           /* INTx A-D → GIC SPI */
    msi-map = <0x00 &v2m 0x00 0x10000>;                /* RID → MSI 컨트롤러 */
};
```
(랩 `out/virt.dts`의 해당 노드를 줄여 옮긴 것 — `interrupt-map`의 32줄은 생략.)

`ranges`의 첫 셀(`0x02000000` 등)은 PCI 주소 공간 종류다: `01` = I/O, `02` = 32비트 MEM, `03` = 64비트 MEM (prefetchable이면 `0x43000000`처럼 bit 30이 선다). 이 3셀 PCI 주소 → 2셀 CPU 주소 → 2셀 크기 형식은 D4에서 다뤘다.

출력에서 볼 것: `IO 0x3eff0000 -> 0x0`은 CPU 주소 0x3eff0000에 쓰면 PCI I/O 공간 0번지로 간다는 뜻(ARM에는 x86 `in/out` 명령이 없어서 I/O 공간도 MMIO 창으로 흉내 낸다). 32비트 창은 CPU 주소 = PCI 주소(1:1)이고, 64비트 창은 512 GiB짜리다. ### 1.3 ECAM과 DWC — 임베디드에서 실제로 만나는 쪽

| 항목 | `pci-host-ecam-generic` (QEMU, 서버 SoC) | DesignWare 기반 (`pcie-designware-host.c` + glue) |
|---|---|---|
| config 접근 | ECAM: `base + (bus<<20 + dev<<15 + fn<<12 + reg)` 그대로 MMIO | 자기 버스(RC)는 DBI 레지스터, 하위 버스는 **iATU 창 하나를 매번 다시 프로그램**해서 CfgRd0/CfgRd1 생성 |
| 링크 업 | 펌웨어/모델이 이미 올려 둠 | glue 드라이버가 PHY·클럭·리셋(PERST#)·LTSSM enable을 직접 하고 `dw_pcie_wait_for_link()`로 기다림 |
| MSI | GICv2m / GICv3 ITS (`msi-map`) | DWC 내장 MSI 컨트롤러(`dw_pcie_msi`, iMSI-RX) 또는 ITS |
| 드라이버 예 | `pci-host-generic` | `pci-imx6.c`(i.MX6/8), `pcie-dw-rockchip.c`, `pcie-tegra194.c`, `pcie-qcom.c` |
| 진입 함수 | `pci_host_common_probe` → `pci_host_common_init` → `pci_host_probe` | glue의 probe → `dw_pcie_host_init()` → `pci_host_probe` |

Don의 bring-up 경험이 가장 빛나는 곳이 오른쪽 열이다. i.MX8 보드에서 "Wi-Fi 카드가 안 보인다"의 90%는 PCI core가 아니라 glue 드라이버 단계 — REFCLK, PERST# 타이밍, PHY 전원, `dw_pcie_wait_for_link` 타임아웃("Phy link never came up") — 에서 끝난다. 랩 커널에도 `CONFIG_PCIE_DW_HOST=y`, `CONFIG_PCI_IMX6_HOST=y`, `CONFIG_PCIE_ROCKCHIP_DW_HOST=y`가 켜져 있다 (QEMU에 DWC 모델이 없어 실행은 못 함). 어느 쪽이든 결국 `pci_host_probe()`를 부르고, 거기서부터는 같은 PCI core다.

> 함정: DWC SoC에서 `lspci`에 Root Port만 보이고 엔드포인트가 없으면 "링크가 안 올라왔다"는 뜻이다. Root Port 자체는 SoC 안에 있으니 링크와 무관하게 항상 보인다. dmesg에서 glue 드라이버의 "Link up"/"Phy link never came up" 줄부터 찾는다.

그림 2 — 부팅 enumeration. 스캔 단계(2~5)에서는 BAR "크기"만 알고 주소는 0으로 찍힌다. 주소는 전부 스캔이 끝난 뒤 6단계에서 한꺼번에 정해진다.

Don이 펌웨어에서 경험한 것과 다른 점 두 가지:

1. **스캔과 배정이 분리돼 있다.** 스캔 중의 `BAR 0 [mem 0x00000000-0x000fffff]`는 "크기 1 MiB"라는 뜻일 뿐 주소가 아니다. 모든 장치의 크기를 알아야 브리지 창 크기를 정할 수 있기 때문이다.
2. **x86 PC와 달리 펌웨어가 아무것도 안 해 놓는다.** x86에서는 BIOS가 이미 BAR를 배정해 두고 Linux는 대부분 "claim"만 한다. QEMU `-kernel` 부팅이나 대부분의 ARM 보드는 U-Boot가 PCI를 건드리지 않거나 건드려도 Linux가 다시 하므로 `bridge configuration invalid ([bus 00-00]), reconfiguring`이 찍힌다 — 에러가 아니라 "버스 번호가 비어 있어서 내가 정한다"는 뜻이다.

### 3.2 예제 4 — sysfs로 edu 해부하기

## 4. Config space 직접 해독하기 — 미니 `lspci -vvv`

### 4.1 예제 5 — `h11_cfg`: 헤더·BAR·capability 리스트

무엇을 확인하나: sysfs `config` 파일만으로 Header Type, BAR 원시값, capability 체인(PM, MSI, MSI-X, PCIe cap의 Link 속도/폭), extended capability(0x100~)를 읽는다. Don이 SSD 펌웨어에서 장치 쪽으로 채워 넣던 그 구조를 호스트 쪽에서 읽어 보는 것이다.

```c
/* h11_cfg: sysfs config 파일을 읽어 헤더·BAR·capability 리스트를 해석하는 미니 lspci -vvv */
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <fcntl.h>
#include <unistd.h>
static uint8_t c[4096];
static unsigned r16(int o) { return c[o] | c[o + 1] << 8; }
static unsigned r32(int o) { return r16(o) | (unsigned)r16(o + 2) << 16; }
static const char *spd[] = { "?", "2.5GT/s", "5GT/s", "8GT/s", "16GT/s", "32GT/s", "64GT/s" };

int main(int argc, char **argv)
{
    char p[256];
    if (argc < 2) { fprintf(stderr, "usage: %s DDDD:BB:DD.F\n", argv[0]); exit(1); }
    snprintf(p, sizeof p, "/sys/bus/pci/devices/%s/config", argv[1]);
    int fd = open(p, O_RDONLY);
    if (fd < 0) { perror(p); exit(1); }
    ssize_t n = pread(fd, c, sizeof c, 0);
    if (n < 64) { perror("pread"); exit(1); }
    close(fd);
    unsigned ht = c[0x0e] & 0x7f;
    printf("%s [%04x:%04x] class %06x hdr type %u, cfg %zd B, cmd %04x sts %04x\n",
           argv[1], r16(0), r16(2), r32(8) >> 8, ht, n, r16(4), r16(6));
    for (int i = 0; i < (ht ? 2 : 6); i++) {
        unsigned v = r32(0x10 + 4 * i);
        if (!v) continue;
        int is64 = !(v & 1) && (v & 6) == 4;
        printf("  BAR%d %s%s%s raw=%08x\n", i, v & 1 ? "I/O" : "MEM",
               is64 ? " 64bit" : "", !(v & 1) && (v & 8) ? " pref" : "", v);
        i += is64;
    }
    if (ht == 1) printf("  bus pri=%02x sec=%02x sub=%02x\n", c[0x18], c[0x19], c[0x1a]);
    if (c[0x3d]) printf("  INTx pin %c (line %u)\n", 'A' + c[0x3d] - 1, c[0x3c]);
    for (int o = (r16(6) & 0x10) ? c[0x34] & 0xfc : 0; o; o = c[o + 1] & 0xfc) {
        unsigned id = c[o], ctl = r16(o + 2);
        printf("  [%02x] cap %02x ", o, id);
        if (id == 0x01) printf("PM v%u, state D%u\n", ctl & 7, r16(o + 4) & 3);
        else if (id == 0x05) printf("MSI: enable=%u count=%u/%u 64bit=%u\n", ctl & 1,
                                   1 << ((ctl >> 4) & 7), 1 << ((ctl >> 1) & 7), (ctl >> 7) & 1);
        else if (id == 0x11) printf("MSI-X: enable=%u size=%u table BAR%u+0x%x PBA BAR%u+0x%x\n",
                                   ctl >> 15, (ctl & 0x7ff) + 1, r32(o + 4) & 7, r32(o + 4) & ~7u,
                                   r32(o + 8) & 7, r32(o + 8) & ~7u);
        else if (id == 0x10) {
            unsigned lc = r32(o + 12), ls = r16(o + 18);
            printf("PCIe v%u type %u: LnkCap %s x%u, LnkSta %s x%u\n", ctl & 0xf, (ctl >> 4) & 0xf,
                   spd[(lc & 0xf) < 7 ? lc & 0xf : 0], (lc >> 4) & 0x3f,
                   spd[(ls & 0xf) < 7 ? ls & 0xf : 0], (ls >> 4) & 0x3f);
        } else printf("(other)\n");
    }
    for (int o = n > 256 ? 0x100 : 0; o && r32(o); o = r32(o) >> 20)
        printf("  [%03x] ext cap %04x v%u\n", o, r32(o) & 0xffff, (r32(o) >> 16) & 0xf);
    return 0;
}
```

출력에서 볼 것:

- **cmd 레지스터가 드라이버 상태를 말해 준다.** 드라이버가 붙은 Root Port·e1000e·virtio는 `0406`/`0407`(bit1 Memory, bit2 Bus Master, bit10 INTx Disable), 드라이버가 없는 edu·NVMe는 `0000`. Linux는 enumeration 때 BAR 주소는 쓰지만 **decode는 켜지 않는다** — `pci_enable_device()`가 켠다.
- **bit10(INTx Disable)이 선 장치는 MSI/MSI-X를 쓰는 중**이다. MSI를 켜면 커널이 INTx를 끈다.
- 엔드포인트의 `INTx pin A (line 0)`: Interrupt Line 레지스터(0x3C)는 x86 BIOS 시절 유물이라 ARM에서는 의미가 없다. 진짜 INTx virq는 커널이 DT `interrupt-map`으로 계산해 `pdev->irq`에 넣는다 (예제 7에서 15).
- edu는 `cfg 256 B` — conventional PCI 장치라 extended config가 없다. Root Port 뒤에 붙어 있어도 PCIe cap이 없다 (QEMU가 허용하는 구성).
- NVMe의 MSI-X 테이블이 **BAR0+0x2000**: Don이 SSD에서 구현하던 바로 그 배치(doorbell 영역 뒤에 MSI-X table/PBA). size=65 = admin 1 + I/O 64.
- 확장 cap `0001` = AER, `000d` = ACS, `0003` = Device Serial Number. QEMU Root Port의 `LnkCap 16GT/s x32`는 모델 기본값이라 의미 없다.
- `cap 09`(Vendor Specific) 5개는 virtio 1.0의 common/notify/isr/device/pci-cfg 구조 위치 표시다.

### 4.2 예제 6 — BAR 크기 재기 (all-ones 쓰기)를 손으로

무엇을 확인하나: 그림 2의 4단계(`__pci_read_base`)가 하는 일을 유저 공간에서 그대로 해 본다. **드라이버가 없는 장치에서만** 한다 — 측정 중에는 BAR 주소가 망가져 있으므로 드라이버가 그 BAR로 접근하면 안 된다. 커널도 똑같이 측정 중에는 Command의 decode 비트를 끈다.

```c
/* h11_barsize: config space의 BAR에 all-ones를 써서 크기를 읽는다 (드라이버 없는 장치에서만!) */
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <fcntl.h>
#include <unistd.h>

static int fd;
static uint32_t rd32(off_t o) { uint32_t v; if (pread(fd, &v, 4, o) != 4) { perror("pread"); exit(1); } return v; }
static void wr32(off_t o, uint32_t v) { if (pwrite(fd, &v, 4, o) != 4) { perror("pwrite"); exit(1); } }
static uint16_t rd16(off_t o) { uint16_t v; if (pread(fd, &v, 2, o) != 2) { perror("pread"); exit(1); } return v; }
static void wr16(off_t o, uint16_t v) { if (pwrite(fd, &v, 2, o) != 2) { perror("pwrite"); exit(1); } }

int main(int argc, char **argv)
{
    char p[256];
    if (argc < 3) { fprintf(stderr, "usage: %s BDF barN\n", argv[0]); exit(1); }
    snprintf(p, sizeof p, "/sys/bus/pci/devices/%s/config", argv[1]);
    if ((fd = open(p, O_RDWR)) < 0) { perror(p); exit(1); }
    off_t bar = 0x10 + 4 * atoi(argv[2]);
    uint16_t cmd = rd16(0x04);
    wr16(0x04, cmd & ~0x3);                 /* 1) I/O·Memory decode 끄기 */
    uint32_t orig = rd32(bar);
    wr32(bar, 0xffffffff);                  /* 2) all-ones 쓰기 */
    uint32_t mask = rd32(bar);              /* 3) 하드와이어된 0 비트가 크기를 알려 준다 */
    wr32(bar, orig);                        /* 4) 원래 주소 복구 */
    wr16(0x04, cmd);                        /* 5) decode 복구 */
    uint32_t m = mask & ((orig & 1) ? ~0x3u : ~0xfu);
    printf("cmd=%04x orig=%08x after-ones=%08x -> size=0x%x (%u KiB) restored=%08x\n",
           cmd, orig, mask, ~m + 1, (~m + 1) / 1024, rd32(bar));
    close(fd);
    return 0;
}
```

```sh
/h11_barsize 0000:02:00.0 0     # nvme BAR0 (64비트 BAR의 하위 dword만)
/h11_barsize 0000:03:00.0 2     # e1000e BAR2 (I/O)
```


출력에서 볼 것: `fff00000` → 하위 20비트가 0으로 고정 = 1 MiB. NVMe는 `...c004`: 하위 4비트 `0100`이 "64비트 MEM, non-pref" 타입 비트로 남는다 (64비트 BAR라면 정식으로는 상위 dword도 all-ones를 써 봐야 한다 — 커널 `__pci_read_base`가 그렇게 한다). I/O BAR는 하위 2비트만 플래그라 32바이트(KiB로 나누면 0). 세 번째 줄은 **e1000e 드라이버가 붙어 있는 상태**에서 돌렸다 — 측정하는 몇 µs 동안 decode가 꺼지므로 실제 장비에서는 하면 안 된다 (QEMU라 무사했다).

> BusyBox에는 `setpci`가 없다. 정식 `pciutils`가 있으면 `setpci -s 01:00.0 COMMAND` (읽기), `setpci -s 01:00.0 BASE_ADDRESS_0=ffffffff` 처럼 쓴다. 없을 때는 위처럼 sysfs `config`에 `pwrite`하거나 `dd ... of=config bs=1 seek=<offset> conv=notrunc`를 쓴다. 어느 쪽이든 **커널 몰래 레지스터를 바꾸는 것**이라 드라이버의 캐시된 상태와 어긋날 수 있다.

## 5. `pci_driver` 쓰기 — probe에서 무엇을 어떤 순서로 하나

### 5.1 직관 — Don의 펌웨어 init을 커널 API로 번역

SSD 펌웨어가 호스트 드라이버였다면 이렇게 했을 것이다: 장치 ID 확인 → BAR 주소 얻기 → 메모리 decode·bus master 켜기 → 레지스터 매핑 → DMA 가능한 주소 범위 확인 → 인터럽트 벡터 배정·핸들러 등록 → 장치 초기화. Linux `probe()`도 정확히 이 순서이고, 각 단계에 API가 하나씩 있다.

| 단계 | API (6.18 기준 권장) | 뒤에서 하는 일 |
|---|---|---|
| 매칭 | `struct pci_device_id` 테이블 + `MODULE_DEVICE_TABLE(pci, ...)` | PCI core가 vendor/device/class 비교 후 `probe(pdev, id)` 호출. modalias로 udev 자동 로드 |
| 켜기 | `pcim_enable_device(pdev)` | Command의 Memory/I/O decode ON, 상위 브리지도 enable, D0로. `pcim_`이라 detach 때 자동 disable |
| BAR 매핑 | `pcim_iomap_region(pdev, bar, name)` | `pci_request_region` + `pci_iomap`. `/proc/iomem`에 이름 등록. 실패 시 `IOMEM_ERR_PTR` |
| DMA 허가 | `pci_set_master(pdev)` | Command bit2 Bus Master Enable. **없으면 DMA도 MSI도 안 나간다** (MSI는 메모리 쓰기다) |
| DMA 범위 | `dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(n))` | 장치가 낼 수 있는 주소 비트 수를 DMA API에 알림 (§8) |
| 인터럽트 | `pci_alloc_irq_vectors(pdev, min, max, PCI_IRQ_MSIX or MSI or INTX)` | MSI-X → MSI → INTx 순으로 시도, 벡터 개수 반환. managed 장치면 자동 해제 |
| 핸들러 | `devm_request_irq(dev, pci_irq_vector(pdev, i), ...)` | i번째 벡터의 Linux virq를 얻어 등록 |
| 저장 | `pci_set_drvdata(pdev, priv)` | remove·PM·AER 콜백에서 `pci_get_drvdata()`로 꺼냄 |

### 5.2 API 버전 함정 — `pcim_iomap_regions()`는 deprecated

인터넷의 드라이버 예제(LDD3, 블로그, 많은 in-tree 드라이버)는 이렇게 쓴다.

```c
/* 옛 방식 — 6.18 소스 주석: "This function is DEPRECATED. Do not use it in new code." */
ret = pcim_iomap_regions(pdev, BIT(0), "drv");
base = pcim_iomap_table(pdev)[0];
```

6.18의 `drivers/pci/devres.c`에서 직접 확인했다: `pcim_iomap_regions()`와 `pcim_iomap_table()`은 둘 다 **DEPRECATED** 주석이 붙어 있고, 대체는 `pcim_iomap_region()`(단수, 6.11 무렵 공개 API가 됨 — 버전은 기억 기반)이다. 반환값이 포인터라 BAR마다 한 번씩 부르고 `IS_ERR()`로 검사한다. 해제가 필요하면 `pcim_iounmap_region()`. 비관리형(`pci_enable_device` + `pci_request_regions` + `pci_iomap` + 수동 해제)도 여전히 동작하지만, 새 코드는 managed(`pcim_`/`devm_`)로 쓰는 것이 리뷰어 기대치다. 면접에서 "pcim_iomap_regions는 deprecated 됐고 지금은 pcim_iomap_region을 쓴다"는 말 한마디가 "최근 커널을 실제로 만져 봤다"는 신호가 된다.

ID 테이블 매크로:

| 매크로 | 매칭 |
|---|---|
| `PCI_DEVICE(0x1234, 0x11e8)` | vendor+device, subsystem은 아무거나 |
| `PCI_DEVICE_DATA(VENDOR, DEV, data)` | `PCI_VENDOR_ID_<VENDOR>`·`PCI_DEVICE_ID_<VENDOR>_<DEV>` 상수 이름으로 + `driver_data` |
| `PCI_DEVICE_SUB(v, d, sv, sd)` | subsystem ID까지 (같은 칩, 다른 보드) |
| `PCI_DEVICE_CLASS(PCI_CLASS_STORAGE_EXPRESS, 0xffffff)` | 클래스로 — `nvme`가 이걸로 모든 NVMe 장치를 잡는다 |
| `PCI_VDEVICE(INTEL, 0x10d3)` | `PCI_VENDOR_ID_INTEL` 축약형 |

`driver_data`는 칩 변형별 설정 구조체 포인터를 실어 보내는 데 쓴다 (`(const struct chip_info *)id->driver_data`).

### 5.3 예제 7 — `h11_edu`: BAR0, MSI/INTx, IRQ 왕복 측정

무엇을 확인하나: 5.1 표의 순서를 그대로 구현한 드라이버. probe에서 edu ID를 읽고, MSI(가능하면) 또는 INTx(`intx=1`) 벡터 하나를 받아, edu의 "인터럽트 올리기" 레지스터를 1000번 써서 핸들러까지의 시간을 잰다. 세 조각으로 나눠 싣는다 (한 파일 `h11_edu.c`, 116줄).

```c
// SPDX-License-Identifier: GPL-2.0
/* h11_edu: QEMU edu(1234:11e8) PCI 드라이버 — BAR0 매핑, MSI/INTx, IRQ 왕복 지연 측정 */
#include <linux/module.h>
#include <linux/pci.h>
#include <linux/interrupt.h>
#include <linux/completion.h>
#include <linux/ktime.h>
#include <linux/sort.h>

#define EDU_ID 0x00
#define EDU_LIVE 0x04
#define EDU_IRQ_STATUS 0x24
#define EDU_IRQ_RAISE 0x60
#define EDU_IRQ_ACK 0x64
#define NLAT 1000

static bool intx;                       /* 1 → MSI를 쓰지 않고 INTx만 */
module_param(intx, bool, 0444);

struct h11 {
	void __iomem *bar;
	struct completion done;
	u64 t_irq;
	unsigned int count;
	u64 lat[NLAT];
};

static irqreturn_t h11_irq(int irq, void *arg)
{
	struct h11 *h = arg;
	u32 st = readl(h->bar + EDU_IRQ_STATUS);

	if (!st)
		return IRQ_NONE;                /* INTx 공유 라인: 내 것이 아님 */
	h->t_irq = ktime_get_ns();
	writel(st, h->bar + EDU_IRQ_ACK);       /* level INTx라면 여기서 라인이 내려간다 */
	h->count++;
	complete(&h->done);
	return IRQ_HANDLED;
}

static int cmp_u64(const void *a, const void *b)
{
	u64 x = *(const u64 *)a, y = *(const u64 *)b;

	return x < y ? -1 : x > y;
}
```

```c
static int h11_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct h11 *h;
	int ret, nvec, i;

	h = devm_kzalloc(&pdev->dev, sizeof(*h), GFP_KERNEL);
	if (!h)
		return -ENOMEM;
	ret = pcim_enable_device(pdev);         /* devres: remove 때 자동 disable */
	if (ret)
		return ret;
	h->bar = pcim_iomap_region(pdev, 0, "h11_edu");  /* request + ioremap BAR0 */
	if (IS_ERR(h->bar))
		return PTR_ERR(h->bar);
	pci_set_master(pdev);
	writel(0x12345678, h->bar + EDU_LIVE);
	dev_info(&pdev->dev, "id=%08x live=%08x BAR0 %pR\n", readl(h->bar + EDU_ID),
		 readl(h->bar + EDU_LIVE), &pdev->resource[0]);

	nvec = pci_alloc_irq_vectors(pdev, 1, 1,
				     intx ? PCI_IRQ_INTX : PCI_IRQ_MSIX | PCI_IRQ_MSI | PCI_IRQ_INTX);
	if (nvec < 0)
		return nvec;
	init_completion(&h->done);
	ret = devm_request_irq(&pdev->dev, pci_irq_vector(pdev, 0), h11_irq,
			       pdev->msi_enabled ? 0 : IRQF_SHARED, "h11_edu", h);
	if (ret)
		return ret;
	dev_info(&pdev->dev, "irq %d via %s\n", pci_irq_vector(pdev, 0),
		 pdev->msix_enabled ? "MSI-X" : pdev->msi_enabled ? "MSI" : "INTx");

	for (i = 0; i < NLAT; i++) {            /* raise → handler 까지 걸린 시간 */
		u64 t0 = ktime_get_ns();

		reinit_completion(&h->done);
		writel(1 << (i % 8), h->bar + EDU_IRQ_RAISE);
		if (!wait_for_completion_timeout(&h->done, HZ))
			return dev_err_probe(&pdev->dev, -ETIMEDOUT, "no irq at %d\n", i);
		h->lat[i] = h->t_irq - t0;
	}
	sort(h->lat, NLAT, sizeof(u64), cmp_u64, NULL);
	dev_info(&pdev->dev, "%u irqs, latency ns min=%llu p50=%llu p90=%llu p99=%llu\n",
		 h->count, h->lat[0], h->lat[NLAT / 2], h->lat[NLAT * 9 / 10], h->lat[NLAT * 99 / 100]);
	pci_set_drvdata(pdev, h);
	return 0;
}
```

```c
}   /* 나머지(IRQ, 벡터, BAR, enable)는 devres가 역순으로 정리 */
```

### 5.4 probe 작성 체크리스트와 함정

- probe에서 실패하면 **이미 한 일을 되돌리는 코드가 필요 없다**(devres). 비관리형 API를 섞으면 그 부분만 직접 되돌려야 한다 — 섞지 말 것.
- `pci_set_master()`를 빼먹으면 MMIO는 되는데 DMA와 MSI가 조용히 안 된다. 예제 14(VFIO)에서 정확히 이 증상을 다시 만난다.
- `pdev->irq`를 직접 `request_irq`에 넣는 옛 코드는 MSI-X 다중 벡터에서 틀린다. 항상 `pci_irq_vector(pdev, i)`.
- INTx는 공유될 수 있으니 `IRQF_SHARED` + "내 장치가 올린 게 아니면 `IRQ_NONE`". MSI는 장치 전용이라 공유 플래그가 필요 없다.
- probe는 sleep 가능한 프로세스 컨텍스트다 (F 모듈). 긴 초기화(펌웨어 로드 G10, 링크 대기)는 괜찮지만, 부팅 시간을 줄이려면 `.driver.probe_type = PROBE_PREFER_ASYNCHRONOUS`를 고려한다.

### 7.3 이 숫자를 어떻게 읽어야 하나 — **실제 HW와 반대일 수 있다**

에뮬레이터에서는 **INTx가 MSI보다 빠르거나 같게** 나왔다. 실제 실리콘에서 이 결론을 내리면 안 된다. 이유:

- QEMU TCG에서 INTx는 `pci_set_irq()` → GIC 상태 비트 변경으로 끝나는 함수 호출이다. MSI는 edu가 "메모리 쓰기"를 에뮬레이트해 GICv2m 프레임 → GIC로 가거나, ITS면 **게스트 메모리에 있는 ITS 테이블(디바이스·인터럽트 변환 테이블)과 LPI pending 테이블을 에뮬레이터가 읽고 쓰는** 경로라 훨씬 길다 (ITS 100 µs대).
- smp 2에서 MSI가 느린 건 위 taskset 실험이 보여 주듯 **raise를 쓴 vCPU와 인터럽트를 받는 vCPU가 다를 때** 생기는 vCPU 스레드 간 깨우기 비용으로 보인다 (MSI 대상 CPU0, insmod가 CPU1이면 느림). INTx가 왜 같은 영향을 덜 받는지는 QEMU 내부까지 확인하지 않았다 — 추정으로만 남긴다.
- 실제 HW에서 MSI가 유리한 이유는 지연 수 µs 차이가 아니라 구조다: (1) INTx는 Assert 메시지와 데이터 DMA 쓰기 사이의 순서가 보장되지 않아 핸들러가 장치 레지스터를 **읽어서 flush**해야 하지만, MSI는 같은 posted write 스트림이라 데이터가 먼저 도착해 있다. (2) 공유 라인이 없어 다른 장치 핸들러를 돌지 않는다. (3) MSI-X는 큐마다·CPU마다 벡터를 나눠 락 없이 처리한다(NVMe). (4) level 선 ack을 위한 MMIO 쓰기가 없다.
- 측정 방법 자체는 실 보드에서 그대로 쓸 수 있다: 장치 레지스터 쓰기 직전 타임스탬프와 핸들러 진입 타임스탬프. 실 보드라면 scope로 GPIO 토글을 함께 찍어 교차 검증하는 것이 Don 방식이다.

## 8. DMA — mask, IOMMU, 그리고 조용한 데이터 손상

### 8.1 직관

장치가 DMA로 쓸 주소는 CPU 물리 주소가 아니라 **버스(DMA) 주소**다. 둘이 같으려면 IOMMU가 없고 오프셋도 없어야 한다. 그리고 장치가 낼 수 있는 주소 비트 수(DMA mask)가 메모리가 있는 곳까지 닿아야 한다. edu는 28비트(256 MiB 미만)만 낼 수 있는데, QEMU virt의 RAM은 0x4000_0000(1 GiB)부터 시작한다 — **RAM 어디에도 닿을 수 없는 장치**다. 실무에서 32비트 DMA만 되는 오래된 Wi-Fi·USB 칩을 4 GiB 넘는 RAM이 있는 SoC에 붙일 때와 같은 문제다.

### 8.2 예제 11 — `h11_dma`: mask를 정직하게/거짓으로, IOMMU 없이/있이

무엇을 확인하나: `dma_set_mask_and_coherent()`의 반환값, `dmam_alloc_coherent()`가 준 DMA 주소, edu DMA 엔진으로 RAM→장치→RAM 왕복한 데이터가 일치하는지.

```c
// SPDX-License-Identifier: GPL-2.0
/* h11_dma: edu의 DMA 엔진으로 RAM→장치→RAM 왕복. DMA mask와 IOMMU의 효과를 본다 */
#include <linux/module.h>
#include <linux/pci.h>
#include <linux/dma-mapping.h>
#include <linux/delay.h>

#define EDU_DMA_SRC 0x80
#define EDU_DMA_DST 0x88
#define EDU_DMA_CNT 0x90
#define EDU_DMA_CMD 0x98
#define EDU_BUF 0x40000                         /* edu 내부 4 KiB 버퍼의 "장치 주소" */

static unsigned int mask_bits = 28;             /* edu 기본 DMA 능력 = 28비트 */
module_param(mask_bits, uint, 0444);

static int edu_dma(void __iomem *bar, u64 src, u64 dst, u32 cnt, u32 dir)
{
	int i;

	writeq(src, bar + EDU_DMA_SRC);
	writeq(dst, bar + EDU_DMA_DST);
	writeq(cnt, bar + EDU_DMA_CNT);
	writeq(1 | dir, bar + EDU_DMA_CMD);     /* bit0 start, bit1 = 1 이면 EDU→RAM */
	for (i = 0; i < 100 && (readq(bar + EDU_DMA_CMD) & 1); i++)
		msleep(5);
	return (readq(bar + EDU_DMA_CMD) & 1) ? -ETIMEDOUT : 0;
}
```

```c
static int h11_dma_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	void __iomem *bar;
	dma_addr_t h;
	u8 *buf;
	int ret, i;

	ret = pcim_enable_device(pdev);
	if (ret)
		return ret;
	bar = pcim_iomap_region(pdev, 0, "h11_dma");
	if (IS_ERR(bar))
		return PTR_ERR(bar);
	pci_set_master(pdev);                           /* Bus Master Enable: 없으면 DMA가 막힌다 */
	ret = dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(mask_bits));
	dev_info(&pdev->dev, "dma_set_mask_and_coherent(%u bits) = %d, iommu=%s\n",
		 mask_bits, ret, device_iommu_mapped(&pdev->dev) ? "yes" : "no");
	if (ret)
		return ret;
	buf = dmam_alloc_coherent(&pdev->dev, PAGE_SIZE, &h, GFP_KERNEL);
	if (!buf)
		return -ENOMEM;
	for (i = 0; i < 1024; i++)
		buf[i] = i ^ 0x5a;
	ret = edu_dma(bar, h, EDU_BUF, 1024, 0);               /* RAM → edu */
	if (!ret)
		ret = edu_dma(bar, EDU_BUF, h + 2048, 1024, 2);  /* edu → RAM(+2 KiB) */
	dev_info(&pdev->dev, "cpu va=%px dma handle=%pad ret=%d match=%s\n", buf, &h, ret,
		 memcmp(buf, buf + 2048, 1024) ? "NO" : "yes");
	return ret;
}

static const struct pci_device_id h11_dma_ids[] = {
	{ PCI_DEVICE(0x1234, 0x11e8) },
	{ }
};
MODULE_DEVICE_TABLE(pci, h11_dma_ids);
static struct pci_driver h11_dma_driver = {
	.name = "h11_dma", .id_table = h11_dma_ids, .probe = h11_dma_probe,
};
module_pci_driver(h11_dma_driver);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H11 edu DMA demo");
```

```sh

insmod /h11_dma.ko                 # 정직하게 28비트
rmmod h11_dma; insmod /h11_dma.ko mask_bits=32    # 거짓말: 32비트라고 주장
# (2) SMMUv3 켬
MACH=virt,iommu=smmuv3 ./run.sh g_dma.sh
# (3) 거짓말 케이스를 QEMU 게스트 에러 로그와 함께
```

출력에서 볼 것 — 이 노트에서 가장 중요한 출력 중 하나다:

- **정직한 28비트 mask는 `-EIO`(-5)로 거부된다.** IOMMU가 없으면 DMA 주소 = 물리 주소인데, 28비트 안에 RAM이 한 바이트도 없으니 DMA API가 "이 장치는 이 시스템에서 DMA 불가"라고 정확히 말해 준 것이다. 드라이버는 여기서 멈추는 게 맞다.
- **32비트라고 거짓말하면 모든 API가 성공(ret=0)하고 데이터만 틀린다(match=NO).** 장치는 상위 비트를 잘라 0x036a5000 — RAM도 아닌 곳 — 에 썼다. 실제 HW였다면 다른 장치 레지스터나 다른 프로세스의 메모리를 조용히 덮어썼을 것이다. "DMA mask는 장치 데이터시트의 주소 비트 수를 그대로 적는다"가 규칙이다.
- **SMMUv3를 켜면 28비트로 성공한다.** 장치가 보는 주소(IOVA) `0x0ffff000`은 28비트 안이고, SMMU가 이를 실제 RAM(1 GiB 위)으로 번역한다. IOMMU의 실용적 가치 중 하나: 주소 능력이 부족한 장치를 살린다. 또 하나는 격리 — 장치가 매핑되지 않은 메모리를 건드리면 SMMU fault가 난다(§12의 VFIO가 이걸 전제로 한다).
- `iommu_groups/5`: SMMU가 있으면 장치마다 IOMMU 그룹이 생긴다 (그룹 = 서로 격리할 수 없는 장치 묶음).

DMA API의 나머지(streaming `dma_map_single`/`dma_map_sg`, 캐시 동기화, `dma_sync_*`)는 H9에서 다룬다. PCI 드라이버 입장에서 기억할 것: `dma_set_mask_and_coherent()`는 probe에서 `pci_set_master()` 뒤, 버퍼 할당 전에. 64비트를 먼저 시도하고 실패하면 32비트로 내려가는 패턴이 흔했지만, 현재 커널에서는 64비트 mask 설정이 사실상 실패하지 않으므로 "64비트 가능한 장치는 `DMA_BIT_MASK(64)` 한 번"이 권장이다.

## 9. 수명주기 — enable, reset, remove/rescan, bind/unbind

### 9.1 예제 12 — sysfs로 장치를 끄고 켜고 지우고 다시 찾기

무엇을 확인하나: G3에서 본 driver core의 bind/unbind가 PCI에서는 어떻게 보이는지, 그리고 PCI만의 `enable`, `reset`, `remove`, `rescan`.

```sh

cat enable; echo 1 > enable; cat enable; /h11_cfg 0000:01:00.0 | head -1; echo 0 > enable; cat enable
```

- `reset`: 드라이버가 붙은 상태에서도 된다. PCI core가 config를 저장 → 드라이버의 `reset_prepare` → 리셋(여기서는 `reset_method`=bus, Root Port의 Secondary Bus Reset) → config 복원 → `reset_done`. 리셋 후 cmd가 `0406`으로 **복원**된 게 그 증거다. Don의 SSD 세계로 말하면 호스트가 FLR/Hot Reset을 날리고 config를 다시 써 주는 그 시퀀스다.
- `remove`: 드라이버 `remove()` → `pci_dev` 삭제. 디렉터리 목록에서 `0000:01:00.0`이 사라졌다. 장치는 물리적으로 그대로 있다 — 커널이 잊었을 뿐.
- `rescan`: 전체 버스를 다시 스캔해서 **새로 보이는** 장치만 추가한다. 같은 BAR 주소를 다시 배정받았고 `h11_edu`가 자동으로 probe됐다. 핫플러그 슬롯이 없는 보드에서 "부팅 후 늦게 전원이 들어오는 PCIe 장치(예: 모뎀)"를 붙이는 실전 기법이다 (FPGA 비트스트림 로드 후 rescan도 같은 패턴).
- `unbind`/`bind`: `pci_dev`는 남기고 드라이버만 떼었다 붙인다 (G3의 driver core 경로). §12에서 `driver_override`와 함께 VFIO로 넘길 때 쓴다.

### 9.2 Hotplug

진짜 PCIe 핫플러그(Slot Capabilities의 Presence Detect, Attention Button)는 `pciehp`(`CONFIG_HOTPLUG_PCI_PCIE`) 서비스가 Root Port/Downstream Port에 붙어 처리한다 — 랩 커널은 이 옵션이 꺼져 있어 실행하지 못했다 (`# CONFIG_HOTPLUG_PCI_PCIE is not set`). 동작 원리는 같다: 장치 등장 → `pci_rescan_bus()` 경로, 장치 제거 → `pci_stop_and_remove_bus_device()` 경로. 드라이버 입장에서 중요한 점은 **surprise removal**: 장치가 사라진 뒤 MMIO 읽기는 `0xffffffff`를 돌려준다. 그래서 견고한 드라이버는 `readl() == ~0`을 "장치 사라짐"으로 의심하고 `pci_device_is_present()`로 확인한다 (NVMe 드라이버가 그렇게 한다).

## 10. AER — 에러를 커널이 받고 드라이버가 복구한다

### 10.1 흐름

Don은 AER 레지스터(Uncorrectable/Correctable Status, Mask, Severity, Header Log)를 장치 쪽에서 세팅해 본 사람이다. 호스트 쪽 이야기는 이렇다: 장치가 ERR_COR/ERR_NONFATAL/ERR_FATAL 메시지를 올려 보냄 → Root Port가 Root Error Status에 기록하고 인터럽트(위에서 본 `aerdrv` MSI-X 벡터) → **`aerdrv`**(drivers/pci/pcie/aer.c)가 소스 장치를 찾아 상태 레지스터를 읽고 로그 → correctable이면 기록 후 클리어, uncorrectable이면 `pcie_do_recovery()`가 해당 브리지 아래 모든 드라이버의 `pci_error_handlers`를 순서대로 부른다.

```c
/* 드라이버 쪽 — 형태만 보이는 스케치 (실행하지 않음, e1000e·nvme·igb가 이 구조를 갖는다) */
static pci_ers_result_t drv_error_detected(struct pci_dev *pdev, pci_channel_state_t state)
{
	/* state: pci_channel_io_normal(비치명) / io_frozen(치명, MMIO 막힘) / io_perm_failure */
	if (state == pci_channel_io_perm_failure)
		return PCI_ERS_RESULT_DISCONNECT;
	/* 큐 정지, 진행 중 I/O 중단. frozen이면 MMIO 하지 말 것 */
	return PCI_ERS_RESULT_NEED_RESET;
}
static pci_ers_result_t drv_slot_reset(struct pci_dev *pdev)
{
	/* 링크 리셋 후: pci_restore_state(), 다시 enable, 장치 재초기화 */
	return PCI_ERS_RESULT_RECOVERED;
}
static void drv_resume(struct pci_dev *pdev) { /* 큐 재시작 */ }

static const struct pci_error_handlers drv_err_handler = {
	.error_detected = drv_error_detected,
	.slot_reset = drv_slot_reset,
	.resume = drv_resume,
};
/* struct pci_driver 안에: .err_handler = &drv_err_handler, */
```

6.18의 `struct pci_error_handlers`에는 이 외에 `mmio_enabled`, `reset_prepare`/`reset_done`(예제 12의 sysfs reset이 부르는 쪽), `cor_error_detected`가 있다.

## 11. 전원 관리 — D-state, runtime PM, ASPM (짧게, 깊은 내용은 N5)

| 층 | 무엇 | Linux에서 보이는 곳 |
|---|---|---|
| 장치 D-state | D0(동작) / D3hot(전원 유지, config만 응답) / D3cold(전원 차단) | `power_state` 파일, `pci_set_power_state()`, PM cap의 PMCSR |
| runtime PM | 사용하지 않을 때 드라이버가 D3로 보내고 쓸 때 깨움 | `power/control`(on/auto), `power/runtime_status`, 드라이버의 `pm_runtime_*` (N5) |
| 시스템 suspend | 전체 suspend 때 `pci_pm_suspend` → 드라이버 `.driver.pm` 콜백 | `struct dev_pm_ops`, `DEFINE_SIMPLE_DEV_PM_OPS` |
| 링크 ASPM | 링크 유휴 시 L0s/L1(+L1 substates) | `/sys/module/pcie_aspm/parameters/policy`, 장치 `link/` 디렉터리의 `l0s_aspm`, `l1_aspm` 등 |

예제 8 출력이 이걸 보여 줬다: NVMe는 `D0`, runtime `active`, 링크 `2.5 GT/s` x1, `link/l0s_aspm` 파일 하나(장치가 L0s만 광고 — 부팅 로그의 `ASPM: default states L0s`), 정책은 `[default]`. 실무 함정: 일부 Wi-Fi/모뎀 칩은 ASPM L1에서 깨어나는 지연 때문에 패킷 드롭·링크 다운이 생겨 드라이버가 `pci_disable_link_state(pdev, PCIE_LINK_STATE_L1)`로 끄는 quirk를 넣는다. 반대로 배터리 장비는 L1.2를 켜야 대기 전력이 맞는다 — 둘 다 bring-up 때 자주 맞닥뜨린다.

## 12. VFIO — 유저 공간 드라이버 (SPDK·DPDK의 세계)

### 12.1 직관

SPDK는 NVMe를 커널 `nvme` 드라이버 없이 **유저 공간 폴링 드라이버**로 돌린다. Don이 SSD 펌웨어 쪽에서 "호스트 IOPS가 커널 스택 오버헤드로 묶인다"는 얘기를 들었다면 그 해결책이 이것이다. 그러려면 유저 프로세스가 (1) BAR를 mmap하고, (2) 인터럽트를 받고(또는 폴링), (3) **안전하게** DMA할 수 있어야 한다. (3)이 핵심이다: 유저 프로세스가 장치에 아무 물리 주소나 DMA하라고 시키면 커널 메모리를 덮어쓸 수 있다. 그래서 VFIO는 **IOMMU로 장치의 DMA를 그 프로세스가 등록한 메모리로만 제한**하고, MSI도 장치별로 격리(ITS의 DeviceID)될 때만 허락한다.

### 12.2 예제 14 — `h11_vfio`: edu를 유저 공간에서 구동

무엇을 확인하나: `driver_override`로 edu를 `vfio-pci`에 넘기고, 정적 C 프로그램이 VFIO 컨테이너/그룹/장치 API로 BAR0를 mmap해 ID를 읽고, MSI를 eventfd로 3번 받는다. 랩 커널은 `CONFIG_VFIO_PCI=y`, `CONFIG_VFIO_IOMMU_TYPE1=y`, `CONFIG_IOMMUFD`는 꺼져 있으므로 전통적인 group/container API를 쓴다.

```c
/* h11_vfio: VFIO로 edu를 유저 공간에서 구동 — BAR0 mmap, MSI를 eventfd로 받기 */
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <sys/eventfd.h>
#include <linux/vfio.h>
#define DIE(m) do { perror(m); exit(1); } while (0)

int main(int argc, char **argv)
{
    if (argc < 3) { fprintf(stderr, "usage: %s /dev/vfio/N BDF\n", argv[0]); exit(1); }
    int ctr = open("/dev/vfio/vfio", O_RDWR);                     /* 1) container */
    if (ctr < 0) DIE("vfio");
    printf("api=%d type1=%d\n", ioctl(ctr, VFIO_GET_API_VERSION),
           ioctl(ctr, VFIO_CHECK_EXTENSION, VFIO_TYPE1_IOMMU));
    int grp = open(argv[1], O_RDWR);                              /* 2) group */
    if (grp < 0) DIE(argv[1]);
    struct vfio_group_status gs = { .argsz = sizeof gs };
    if (ioctl(grp, VFIO_GROUP_GET_STATUS, &gs) || !(gs.flags & VFIO_GROUP_FLAGS_VIABLE))
        DIE("group not viable (모든 장치가 vfio에 bind 되어야 함)");
    if (ioctl(grp, VFIO_GROUP_SET_CONTAINER, &ctr)) DIE("SET_CONTAINER");
    if (ioctl(ctr, VFIO_SET_IOMMU, VFIO_TYPE1_IOMMU)) DIE("SET_IOMMU");
    int dev = ioctl(grp, VFIO_GROUP_GET_DEVICE_FD, argv[2]);       /* 3) device */
    if (dev < 0) DIE("GET_DEVICE_FD");
    struct vfio_device_info di = { .argsz = sizeof di };
    if (ioctl(dev, VFIO_DEVICE_GET_INFO, &di)) DIE("GET_INFO");
    struct vfio_region_info ri = { .argsz = sizeof ri, .index = VFIO_PCI_BAR0_REGION_INDEX };
    if (ioctl(dev, VFIO_DEVICE_GET_REGION_INFO, &ri)) DIE("REGION_INFO");
    printf("regions=%u irqs=%u flags=%x  BAR0 size=0x%llx offset=0x%llx flags=%x\n",
           di.num_regions, di.num_irqs, di.flags, ri.size, ri.offset, ri.flags);
    volatile uint32_t *bar = mmap(NULL, ri.size, PROT_READ | PROT_WRITE, MAP_SHARED, dev, ri.offset);
    if (bar == MAP_FAILED) DIE("mmap BAR0");
    bar[1] = 0xcafe0000;                                          /* liveness: 반전되어 돌아옴 */
    printf("edu id=%08x live=%08x (user-space MMIO)\n", bar[0], bar[1]);

    struct vfio_region_info cr = { .argsz = sizeof cr, .index = VFIO_PCI_CONFIG_REGION_INDEX };
    uint16_t cmd;                                                 /* 4) Bus Master Enable */
    if (ioctl(dev, VFIO_DEVICE_GET_REGION_INFO, &cr) || pread(dev, &cmd, 2, cr.offset + 4) != 2) DIE("cfg");
    cmd |= 0x4;
    if (pwrite(dev, &cmd, 2, cr.offset + 4) != 2) DIE("cfg write");
    int efd = eventfd(0, 0);                                      /* 5) MSI → eventfd */
    char b[sizeof(struct vfio_irq_set) + sizeof(int)];
    struct vfio_irq_set *is = (struct vfio_irq_set *)b;
    *is = (struct vfio_irq_set){ .argsz = sizeof b, .index = VFIO_PCI_MSI_IRQ_INDEX, .start = 0,
        .count = 1, .flags = VFIO_IRQ_SET_DATA_EVENTFD | VFIO_IRQ_SET_ACTION_TRIGGER };
    *(int *)is->data = efd;
    if (ioctl(dev, VFIO_DEVICE_SET_IRQS, is)) DIE("SET_IRQS");
    for (int i = 0; i < 3; i++) {
        uint64_t cnt;
        bar[0x60 / 4] = 1u << i;                                  /* raise */
        if (read(efd, &cnt, 8) != 8) DIE("read eventfd");
        printf("irq #%d: eventfd=%llu status=%x\n", i, (unsigned long long)cnt, bar[0x24 / 4]);
        bar[0x64 / 4] = bar[0x24 / 4];                            /* ack */
    }
    return 0;
}
```

출력에서 볼 것:

- `api=0`: `VFIO_API_VERSION`은 원래 0이다 (에러 아님). `type1=1`: Type1 IOMMU 백엔드 사용 가능.
- `regions=9`: BAR0~5, ROM, config, VGA 순의 고정 인덱스(`VFIO_PCI_*_REGION_INDEX`). `irqs=5`: INTx, MSI, MSI-X, ERR, REQ. BAR0 `flags=7` = READ, WRITE, MMAP 가능. BAR0의 offset이 0인 건 "device fd 안에서 이 region이 시작하는 위치"이고, 인덱스별로 `index << 40` 오프셋을 쓰는 게 vfio-pci 구현이다 (BAR0는 0).
- `live=3501ffff` = `~0xcafe0000`. 유저 프로세스의 store가 장치 레지스터에 닿았다 — 커널 드라이버 한 줄 없이.
- `vfio-pci`가 open 시점에 장치를 **리셋**했다 (이전 사용자의 상태를 지우기 위해). 리셋 후 Command는 decode만 켜진 `0002`라 BME를 유저가 직접 켜야 했다.
- 이 상태에서 DMA를 하려면 `VFIO_IOMMU_MAP_DMA`로 내 버퍼(vaddr)를 IOVA에 매핑하고, 장치에는 그 IOVA를 준다 — SPDK가 hugepage를 IOVA로 등록하는 것이 바로 이것이다. (이 예제에서는 하지 않았다. 예제 11에서 SMMU가 IOVA `0x0ffff000`을 준 것과 같은 원리다.)
- 유저 드라이버의 비용: 커널의 에러 처리(AER 복구), 전원 관리, 다른 서브시스템 통합(블록 계층, netdev)을 포기하고 직접 만든다. 그래서 SPDK/DPDK처럼 "장치를 통째로 한 앱이 쓰는" 경우와 가상머신 패스스루(QEMU/KVM이 VFIO 사용자)에 쓴다. 단순히 레지스터 몇 개를 만지려는 용도라면 UIO(`uio_pci_generic`: IOMMU 없이 INTx만, DMA 안전 보장 없음)도 있지만 새 설계에서는 VFIO가 표준이다.

## 15. Embedded 실무에서 다시 보기

**장면 1 — i.MX8M Plus 보드의 PCIe Wi-Fi가 안 잡힌다.** `lspci`에 Root Port(`16c3:abcd` 같은 Synopsys ID)만 있고 엔드포인트가 없다. PCI core 문제가 아니라 링크 문제다. 확인 순서: dmesg의 `imx6q-pcie` 메시지("Phy link never came up") → DT의 `reset-gpio`(PERST#) 극성·지연, `clocks`(REFCLK 소스: 내부/외부), `vpcie-supply`(카드 3.3V) → 카드 쪽 `W_DISABLE#`. Don의 scope로 REFCLK와 PERST# 타이밍을 찍는 것이 가장 빠르다. 링크가 올라오고 나면 그 뒤는 이 노트의 enumeration 그대로다.

**장면 2 — Jetson Orin + NVMe에서 "BAR 0: no space".** 큰 BAR(수십 MB의 CMB/PMR이 있는 엔터프라이즈 NVMe, 또는 AI 가속기 카드)를 꽂으면 SoC의 32비트 non-pref 창이 모자라 예제 3과 같은 로그가 난다. 대응은 DT `ranges`의 창 확인, 64비트 prefetchable 창 존재 확인, 핫플러그 여유분 조정. 장치가 64비트 BAR이면서 non-prefetchable이면 브리지 뒤에서 32비트 창에 들어가야 한다는 규칙이 가장 자주 발목을 잡는다.

**장면 3 — 로봇 센서 키트의 FPGA 프레임 그래버(PCIe).** 직접 `pci_driver`를 쓴다. 이 노트의 `h11_edu` 골격 그대로: `PCI_DEVICE(0x10ee, 0x7024)`(Xilinx) → `pcim_iomap_region` → MSI-X 벡터를 DMA 채널마다 하나씩 → `dma_set_mask_and_coherent(64)` → 프레임 버퍼는 `dma_alloc_coherent` 또는 V4L2 videobuf2(I 모듈)로. FPGA를 부팅 후 프로그래밍한다면 그 뒤 `echo 1 > /sys/bus/pci/rescan`(예제 12).

**장면 4 — 현장 장비의 간헐적 링크 문제 모니터링.** 차량·드론 진동 환경에서 커넥터 문제로 correctable 에러가 쌓인다. 예제 13의 `aer_dev_correctable` 카운터를 주기적으로 수집하는 데몬 하나가 "현장 리턴 원인 분석"을 몇 주 앞당긴다. `current_link_speed`/`current_link_width`가 기대보다 낮으면(Gen3 x4 기대인데 Gen1 x1) 링크 트레이닝 강등이다 — Don의 LTSSM 경험이 그대로 쓰이는 지점이다.

## 16. 흔한 실수와 증상

| 실수 | 증상 | 원인 | 고치는 법 |
|---|---|---|---|
| `pci_set_master()` 누락 | MMIO는 되는데 DMA 결과가 비어 있고 MSI가 안 옴 | Command bit2(BME) 꺼짐 — MSI도 메모리 쓰기 | probe에서 enable 직후 `pci_set_master` (VFIO면 유저가 config로 켬) |

| 관리형·비관리형 API 혼용 | remove 후 double free / 언바인드 시 WARN | devres가 이미 해제한 것을 수동으로 또 해제 | 한쪽(pcim/devm)으로 통일 |
| 장치 사라짐(`0xffffffff`) 미처리 | surprise removal·AER 후 무한 루프, 잘못된 상태값 처리 | 장치 없는 MMIO 읽기는 all-ones | `readl()==~0`이면 `pci_device_is_present()` 확인 |

## 17. 면접에서 이렇게 말한다

**Q.** "Walk me through what a PCI driver's probe function does."

**A.** ID 테이블 매칭으로 probe가 불리면, 장치를 켜고(`pcim_enable_device`), 쓸 BAR를 요청·매핑하고(`pcim_iomap_region`), bus mastering을 켜고, DMA mask를 장치 주소 능력에 맞게 설정하고, `pci_alloc_irq_vectors`로 MSI-X→MSI→INTx 순으로 벡터를 받아 `pci_irq_vector`로 핸들러를 등록한 뒤, 장치를 초기화하고 drvdata를 저장한다. managed API를 써서 실패나 remove 때 자동 역순 정리가 되게 한다.

> "Probe is called after the PCI core matches the device against my id_table. I enable the device with pcim_enable_device, request and map the BARs I need with pcim_iomap_region — the plural pcim_iomap_regions is deprecated now — set bus mastering, set the DMA mask to what the hardware can actually address, then allocate interrupt vectors with pci_alloc_irq_vectors, preferring MSI-X, and request each one through pci_irq_vector. Then I initialize the hardware and store my private struct with pci_set_drvdata. Because everything is devres-managed, an error path or remove unwinds automatically in reverse order."

**꼬리 질문**: "Why must pci_set_master be called?" → BME가 꺼져 있으면 장치가 DMA도 MSI도 못 낸다. MSI는 메모리 쓰기이기 때문이다.

**Q.** "How does Linux enumerate PCIe devices on an ARM SoC with no BIOS?"

**A.** DT의 host bridge 노드에서 시작한다. host bridge 드라이버(ECAM generic이나 DWC glue)가 ECAM·주소 창·인터럽트 매핑을 받아 `pci_host_probe`를 부르면, PCI core가 버스 0부터 깊이 우선으로 Vendor ID를 읽어 장치를 찾고, BAR에 all-ones를 써 크기를 재고, 브리지를 만나면 버스 번호를 주고 재귀한다. 스캔이 끝나면 아래에서 위로 브리지 창 크기를 합산하고 위에서 아래로 주소를 배정한 다음, 장치를 등록해 드라이버 매칭을 일으킨다.

> "On ARM there's usually no firmware doing enumeration, so the kernel does it. The host bridge is described in the device tree — ECAM base, the memory and I/O windows in ranges, interrupt-map and msi-map. The host driver, pci-host-generic or a DesignWare glue driver, calls pci_host_probe. The core scans depth-first: reads the vendor ID, sizes each BAR by writing all ones, assigns bus numbers to bridges and recurses. Only after the whole scan does it size the bridge windows bottom-up and assign addresses top-down, then it adds the devices so drivers can bind."

**Q.** "What's the difference between MSI and MSI-X, and why does NVMe use MSI-X?"

**A.** 둘 다 장치가 메모리 쓰기로 인터럽트를 보내는 방식이다. MSI는 주소 하나에 연속된 최대 32개 벡터, MSI-X는 BAR 안의 테이블로 최대 2048개 벡터를 각각 다른 주소·데이터·마스크로 갖는다. 그래서 MSI-X는 큐마다 벡터를 주고 각 벡터를 다른 CPU에 고정할 수 있다. NVMe는 CPU당 submission/completion 큐 쌍을 두고 completion 인터럽트를 그 CPU로 보내 락과 캐시 이동을 없앤다. 랩에서도 nvme가 CPU 2개에 I/O 큐 2개 + admin 1개 = MSI-X 3벡터를 썼다.

> "Both are in-band memory writes, so there's no shared wire and the interrupt is ordered behind the device's DMA writes. MSI gives one address and up to 32 contiguous vectors; MSI-X has a table in a BAR with up to 2048 entries, each with its own address, data and mask bit. That lets NVMe give every CPU its own queue pair and its own interrupt vector with managed affinity, so completions are handled on the submitting CPU without locks. In my QEMU lab, the nvme driver took exactly three vectors on a two-CPU guest: one admin queue and one I/O queue per CPU."

**꼬리 질문**: "How does the MSI address get programmed?" → `pci_alloc_irq_vectors`가 PCI-MSI irq_domain → GICv2m/ITS domain을 거치며 `irq_compose_msi_msg`가 doorbell 주소·데이터를 만들고, PCI core가 그 값을 MSI-X 테이블 엔트리에 쓴다.

**Q.** "A device shows up in lspci but the driver fails with 'BAR 0: no space'. How do you debug?"

**A.** 부팅 로그에서 그 BAR의 크기와 64비트/prefetchable 여부, 상위 브리지의 창, root bus resource를 본다. 대부분 host bridge의 창(DT `ranges`)이 작거나, 64비트 non-pref BAR가 32비트 창에 안 들어가거나, 핫플러그 여유분이 공간을 먹은 경우다. `/proc/iomem`으로 실제 배치를 보고, 창을 키우거나 `pci=realloc`, `hpmemsize`를 조정한다.

> "First I read the enumeration log: the BAR size and type, the parent bridge windows, and the root bus resources from the host bridge. Then /proc/iomem to see what's actually placed. Typical causes are a too-small window in the device tree ranges, a 64-bit non-prefetchable BAR that has to fit in the 32-bit window behind a bridge, or hotplug padding. Fixes are enlarging the window, adding a 64-bit prefetchable window, pci=realloc to let the kernel redo bridge windows, or tuning hpmemsize."

**Q.** "What is VFIO and why does it require an IOMMU?"

**A.** VFIO는 PCI 장치를 유저 공간 프로세스에 안전하게 넘기는 프레임워크다. BAR를 mmap하게 해 주고, 인터럽트를 eventfd로 전달하고, DMA는 프로세스가 등록한 메모리만 IOMMU 페이지 테이블에 매핑한다. IOMMU 없이 장치가 아무 물리 주소에 DMA할 수 있으면 유저가 커널 메모리를 덮어쓸 수 있으니 안전을 보장할 수 없다. 같은 이유로 MSI도 장치별로 격리돼야 한다 — 실제로 GICv2m에서는 "No interrupt remapping support"로 거부됐고 GICv3 ITS에서 동작했다. SPDK·DPDK·VM 패스스루가 이걸 쓴다.

> "VFIO hands a device to user space safely. The process gets the BARs through mmap, interrupts through eventfds, and does DMA only to memory it explicitly maps with VFIO_IOMMU_MAP_DMA, which programs the IOMMU. Without an IOMMU the device could DMA anywhere, so user space could corrupt the kernel. MSI has to be isolated too: in my lab VFIO refused to attach on GICv2m with 'no interrupt remapping support' and worked once I switched to GICv3 with the ITS, which identifies the device by its requester ID. SPDK, DPDK and VM passthrough are the main users."

**꼬리 질문**: "What is an IOMMU group?" → IOMMU가 서로 구분할 수 없는 장치 묶음(예: ACS 없는 스위치 뒤). 그룹 안의 모든 장치가 vfio에 bind되거나 드라이버가 없어야 group이 viable하다.

**Q.** "How does Linux handle a PCIe uncorrectable error?"

**A.** 장치가 ERR_NONFATAL/FATAL 메시지를 보내면 Root Port의 AER 서비스가 인터럽트를 받아 소스 장치의 AER 레지스터를 읽어 로그를 남기고, `pcie_do_recovery`가 그 아래 드라이버들의 `error_detected`를 부른다. 드라이버가 리셋이 필요하다고 답하면 링크(Secondary Bus) 리셋 후 `slot_reset`, 그리고 `resume`. Correctable은 로그와 카운터만 남는다. 랩에서 QEMU로 에러를 주입해 e1000e가 링크 리셋 후 복구되는 것을 확인했다.

> "The device sends an error message upstream; the root port's AER service gets the interrupt, finds the source, logs the status and header log, and for uncorrectable errors runs pcie_do_recovery. Every driver below that port gets error_detected; if one asks for a reset, the core resets the link, calls slot_reset so the driver can restore state, then resume. Correctable errors are just logged and counted in sysfs. I injected all three kinds into a QEMU root port and watched e1000e recover through a secondary bus reset."

**Q.** "Kernel driver or user-space driver for a custom PCIe FPGA?"

**A.** 다른 커널 서브시스템(V4L2, netdev, 블록)과 통합해야 하거나, 전원 관리·AER 복구·여러 프로세스 공유가 필요하면 커널 드라이버. 장치 하나를 한 앱이 독점하고 최저 지연·폴링이 목표면 VFIO 유저 드라이버. 개발 초기 bring-up에는 VFIO가 빠르게 레지스터를 만져 볼 수 있어 편하고, 제품화 단계에서 커널 드라이버로 옮기는 경우가 많다.

> "If the device needs to plug into kernel frameworks — V4L2 for a camera, netdev, block — or needs power management, error recovery and sharing across processes, it's a kernel driver. If one application owns the device and wants minimum latency with polling, a VFIO user-space driver is attractive. For early bring-up I like VFIO because I can poke registers and test DMA from a C program without rebooting, then move the proven sequence into a kernel driver."

## 18. 직접 해보기

1. **개념**: 예제 2에서 rp1의 MEM 창이 2 MiB인 이유를 두 가지 요인(장치 BAR, 핫플러그 여유분)으로 설명하라. 정답/힌트: edu BAR 1 MiB + `add_size 100000` 여유분, 1 MiB 정렬.
2. **개념**: 64비트 non-prefetchable BAR를 가진 장치가 Root Port 뒤에 있을 때 어느 브리지 창에 들어가야 하나, 왜? 정답/힌트: 브리지의 non-pref 창은 32비트(Memory Base/Limit)뿐이다 — 64비트 창은 prefetchable 전용.
3. **코드**: `h11_cfg`에 extended capability 이름(0x0001 AER, 0x000d ACS, 0x0010 SR-IOV, 0x0003 DSN, 0x000e ARI)을 출력하도록 고치고, AER cap이면 Uncorrectable/Correctable Status 레지스터(+0x04, +0x10)도 출력하라. 예제 13 직후 Root Port에서 돌려 보라. 정답/힌트: 커널은 로그 후 상태를 클리어하므로 0이 정상이다 — 클리어 전에 보려면 어떻게? (`aer_dev_*` 카운터)
4. **코드**: `h11_edu`를 MSI-X만 허용(`PCI_IRQ_MSIX`)으로 바꿔 insmod하면 무슨 일이? 정답/힌트: edu는 MSI-X cap이 없으므로 `pci_alloc_irq_vectors`가 음수 에러 코드를 돌려주고 probe가 실패한다 (어떤 에러 코드인지는 직접 확인해 볼 것 — 이 노트에서는 실행하지 않았다).
5. **코드**: `h11_dma`에 IRQ 완료 통지(DMA cmd bit2 = 완료 시 인터럽트 0x100)를 추가해 `msleep` 폴링을 completion으로 바꿔라. SMMUv3 부팅에서 확인. 정답/힌트: `EDU_DMA_CMD`에 `1 | dir | 4`, 핸들러에서 status `0x100` ack.
6. **관찰**: 예제 12의 `reset`을 드라이버 없이 했을 때와 있을 때 cmd 레지스터 값이 어떻게 다른지 `h11_cfg`로 비교하고 이유를 설명하라. 정답/힌트: 리셋은 config를 0으로 만들지만 PCI core가 저장했던 상태를 복원한다 — 저장 시점의 값이 무엇이었나.
7. **VFIO**: `h11_vfio`에 `VFIO_IOMMU_MAP_DMA`로 4 KiB 버퍼를 IOVA `0x100000`에 매핑하고, edu DMA로 버퍼 내용을 장치 → 버퍼로 복사해 확인하라. 정답/힌트: `struct vfio_iommu_type1_dma_map { .vaddr, .iova, .size, .flags = READ|WRITE }`, edu DMA 주소에는 IOVA를 쓴다. 28비트 안이어야 한다.

## 19. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| ECAM | Enhanced Configuration Access Mechanism | config space를 MMIO 한 덩어리로 매핑하는 표준 (버스당 1 MiB) |
| host bridge | Root Complex의 소프트웨어 표현 | `struct pci_host_bridge`, DT 노드 하나에서 생성 |
| DWC | Synopsys DesignWare PCIe 컨트롤러 | 대부분의 ARM SoC PCIe의 IP. `pcie-designware` + SoC별 glue |
| iATU | internal Address Translation Unit | DWC에서 CPU 주소 창을 PCI 주소·config 요청으로 번역하는 창 |
| BAR | Base Address Register | 장치 레지스터/메모리 창의 위치. 크기는 all-ones 쓰기로 측정 |
| bridge window | 브리지가 하위로 전달하는 주소 범위 | I/O, 32비트 MEM, 64비트 pref MEM 세 종류 |
| `struct pci_dev` | 커널의 PCI 함수 객체 | ID, 위치, resource, irq, DMA mask, 상태 |
| `pci_driver` | PCI 드라이버 구조체 | `id_table`, `probe`, `remove`, `err_handler`, `sriov_configure` |
| devres / managed API | 장치 수명에 묶인 자원 | `pcim_*`, `devm_*` — detach 때 역순 자동 해제 |
| MSI / MSI-X | 메시지 시그널 인터럽트 | 장치의 메모리 쓰기로 인터럽트. MSI-X는 벡터별 테이블 |
| GICv2m | GICv2용 MSI 프레임 | SPI를 MSI로 재사용. 장치 격리 없음 |
| ITS | GICv3 Interrupt Translation Service | DeviceID/EventID → LPI 번역. 장치별 격리 |
| irq_domain | 하드웨어 IRQ 번호 → Linux virq 매핑 계층 | PCI-MSI → v2m/ITS → GIC 계층 |
| DMA mask | 장치가 낼 수 있는 DMA 주소 비트 수 | `dma_set_mask_and_coherent` — 거짓이면 조용한 메모리 손상 |
| IOMMU / SMMU | 장치용 MMU | IOVA → 물리 주소 번역, DMA 격리 |
| AER | Advanced Error Reporting | PCIe 에러 상태 레지스터와 Linux 복구 프레임워크 |
| DPC | Downstream Port Containment | fatal 에러 시 포트가 링크를 끊어 오염 차단 |
| SR-IOV | Single Root I/O Virtualization | PF 하나에서 VF 여러 개 생성 |
| VFIO | Virtual Function I/O | 장치를 IOMMU 보호 아래 유저 공간에 넘기는 프레임워크 |
| IOMMU group | 격리 불가능한 장치 묶음 | VFIO 할당의 최소 단위 |
| `driver_override` | sysfs 파일 | 이 장치는 지정한 드라이버에만 매칭 |
| ASPM | Active State Power Management | 링크 유휴 시 L0s/L1 진입 |
| D-state | 장치 전원 상태 | D0, D3hot, D3cold |

## 20. 요약 & 체크리스트

Linux PCI는 DT의 host bridge 노드(ECAM generic 또는 DWC glue)에서 출발해 `pci_host_probe` → 스캔(Vendor ID, BAR 크기, 버스 번호) → 자원 배정(브리지 창 합산, 주소 배정) → 장치 등록 → id_table 매칭 → `probe()`로 이어진다. 드라이버는 `pcim_enable_device`, `pcim_iomap_region`(복수형은 deprecated), `pci_set_master`, `dma_set_mask_and_coherent`, `pci_alloc_irq_vectors` + `pci_irq_vector`라는 정해진 순서를 managed API로 쓴다. MSI는 irq_domain 계층(PCI-MSI → GICv2m/ITS → GIC)을 거쳐 virq가 되고, `/proc/interrupts`의 칩 이름이 그 경로를 말해 준다. DMA mask는 장치 능력 그대로 — 거짓이면 조용한 손상이고, IOMMU는 주소 능력 부족과 격리를 해결한다. sysfs(`config`, `resource`, `enable`, `reset`, `remove`, `rescan`, `driver_override`, `sriov_numvfs`, `aer_dev_*`)만으로 대부분의 디버그와 실험이 가능하고, VFIO는 IOMMU와 격리된 MSI를 전제로 장치를 유저 공간 드라이버에 넘긴다.

- [ ] DT host bridge 노드의 `reg`, `ranges`, `interrupt-map`, `msi-map`이 각각 무엇인지 설명할 수 있다
- [ ] ECAM host와 DWC host의 차이, DWC 보드에서 "엔드포인트가 안 보임"의 첫 확인 지점을 말할 수 있다
- [ ] 부팅 enumeration 로그에서 스캔 단계와 배정 단계를 구분하고, bridge window·`add_size`를 읽을 수 있다
- [ ] "BAR N: can't assign; no space"의 원인 후보와 대응(`ranges`, 64비트 pref 창, `pci=realloc`, `hpmemsize`)을 말할 수 있다
- [ ] sysfs와 C 프로그램으로 config space의 헤더·BAR·capability 체인을 해독할 수 있다
- [ ] BAR 크기 측정 절차(decode 끄기 → all-ones → 읽기 → 복구)를 코드로 짤 수 있다
- [ ] 현대식 `pci_driver` probe를 managed API로 처음부터 짤 수 있고, `pcim_iomap_regions`가 deprecated임을 안다
- [ ] `pci_alloc_irq_vectors`/`pci_irq_vector`로 MSI-X → MSI → INTx 폴백을 구현하고 `/proc/interrupts`로 확인할 수 있다
- [ ] MSI 메시지가 irq_domain 계층을 통해 virq가 되는 경로와 GICv2m/ITS의 차이를 설명할 수 있다
- [ ] DMA mask와 IOMMU의 관계를 예제 11의 세 결과(거부, 손상, 성공)로 설명할 수 있다
- [ ] AER 복구 순서(`error_detected` → reset → `slot_reset` → `resume`)와 sysfs 카운터 위치를 말할 수 있다
- [ ] VFIO group/container/device 흐름으로 BAR mmap과 MSI eventfd를 구현할 수 있고, IOMMU·격리 MSI·BME가 왜 필요한지 안다
