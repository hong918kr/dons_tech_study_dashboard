# H12. USB (Linux 관점) — host / gadget, usbcore, usb_driver, URB, configfs gadget, 디버그

> **이 노트를 다 읽으면**: USB 디스크립터 계층(device → configuration → interface → endpoint)과 sysfs 이름(`1-4.1:1.0`)을 읽고 "어느 드라이버가 어느 interface에 붙었나"를 바로 말할 수 있다 · `usb_driver`를 `new_id`로 기존 장치에 붙이고 interrupt URB를 제출·재제출하고, 핫 언플러그(`device_del`)에서 `disconnect`가 안전하게 정리되는 것을 실측으로 보여 줄 수 있다 · URB completion이 어떤 문맥(실측: softirq/BH)에서 도는지, 그래서 왜 `GFP_ATOMIC`인지 설명할 수 있다 · `dummy_hcd` + configfs로 ACM + mass storage gadget을 조립해 **같은 커널 안의 host 쪽에서** `/dev/ttyACM0`·`/dev/sdb`로 끝까지 시험할 수 있다
> **왜 필요한가**: Embedded Linux 장비는 거의 다 USB를 양쪽으로 쓴다. 위로는 PC에 붙는 디버그 콘솔·펌웨어 업데이트·Ethernet-over-USB(gadget), 아래로는 USB 카메라·LTE 모뎀·FTDI 시리얼(host). 면접에서는 "USB 드라이버는 왜 interface에 붙나?", "URB completion에서 하면 안 되는 일은?", "configfs gadget 만드는 순서는?", "장치가 갑자기 뽑히면 드라이버는?"으로 나온다
> **Don 기준 난이도**: NVMe/PCIe 경험 덕분에 "호스트가 주도하는 큐 기반 프로토콜", "Identify 같은 자기소개 데이터", "DMA 버퍼 소유권", "핫플러그 시 in-flight 명령 정리"는 이미 몸에 있다 / 새로 배울 부분은 USB 고유 용어(endpoint·interface·class), Linux의 usbcore·URB API, gadget 프레임워크(UDC·composite·configfs)
> **선행 노트**: G2(디바이스 모델·bus/driver 매칭), G8(configfs — 거기서 UDC가 없어 멈춘 gadget 조립을 여기서 끝낸다), G9(hotplug·uevent·modalias), F4(인터럽트 문맥·softirq), F8(메모리 할당 GFP 플래그), H8(TTY — `ttyACM`·`ttyGS`·`ttyUSB`), H9(DMA)

## 0. 큰 그림 — 이게 왜 필요한가

SSD 시절의 NVMe를 떠올려 보자. 호스트가 Submission Queue에 명령을 넣고, 드라이브는 처리 후 Completion Queue에 결과를 넣고 MSI-X로 알린다. 드라이브는 **스스로 말을 걸지 못한다**. 항상 호스트가 시킨 일만 한다. 그리고 처음 붙으면 호스트가 Identify로 "너 누구냐"를 묻는다.

USB도 똑같은 성격의 버스다. **모든 전송은 호스트가 시작한다**(장치는 호스트가 "데이터 있어?" 하고 물어볼 때만 답한다). 처음 꽂히면 호스트가 **디스크립터**(USB판 Identify 데이터)를 읽어서 장치가 무엇인지 알아낸다. 다른 점은 버스가 hub를 통해 나무 모양으로 퍼지고, 장치가 아무 때나 **뽑힌다**는 것이다.

Embedded Linux 엔지니어는 USB를 두 방향으로 만난다.

- **Host 역할**: 센서 키트 SoC에 USB 카메라(UVC), LTE 모뎀, FTDI USB-시리얼(GNSS), USB 메모리가 꽂힌다. Linux가 PC처럼 호스트가 된다. 드라이버는 `usb_driver`다.
- **Device(gadget) 역할**: 같은 SoC의 OTG 포트를 개발자 PC에 꽂으면 SoC가 "USB 장치"가 된다. PC에는 시리얼 포트(디버그 콘솔), 네트워크 카드(Ethernet-over-USB), USB 디스크(펌웨어 업데이트)로 보인다. Linux에서는 이걸 **gadget**이라 부르고, configfs로 조립한다.

## 1. USB 기본 — 토폴로지, 전송 종류, 디스크립터

### 1.1 직관 — "호스트가 모든 것을 묻는 나무"

- **토폴로지**: 호스트 컨트롤러 안에 **root hub**가 있고, 거기에 장치나 hub가 붙고, hub 아래 또 붙는다(tiered star). 최대 7계층, 버스 하나에 주소 127개.
- **주소**: 꽂힌 순간 장치는 주소 0이다. 호스트가 `SET_ADDRESS`로 1~127 중 하나를 준다. 그래서 `devnum`은 꽂을 때마다 바뀐다. 변하지 않는 것은 **포트 경로**(어느 hub의 몇 번 포트)이고, Linux sysfs 이름은 이 경로로 짓는다.
- **endpoint**: 장치 안의 "우편함". 번호(0~15)와 방향(IN = 장치→호스트, OUT = 호스트→장치)이 있다. endpoint 0은 모든 장치에 있는 **제어용 양방향 채널**이다. NVMe로 치면 endpoint 0 = Admin Queue, 나머지 endpoint = I/O Queue다.
- **pipe**: 호스트 쪽에서 본 "특정 장치의 특정 endpoint로 가는 통로". Linux 코드의 `usb_rcvintpipe(udev, 0x81)` 같은 매크로가 이 통로 값을 만든다.

### 1.2 전송 종류 4가지

| 종류 | 보장 | 대역폭·지연 | 대표 용도 | endpoint 예 |
|---|---|---|---|---|
| control | 신뢰(재시도), 셋업 8바이트 + 데이터 + 상태 | 작고 느림 | 디스크립터 읽기, 설정 명령 | 0 (모든 장치) |
| bulk | 신뢰(재시도), 남는 대역폭을 씀 | 크지만 지연 보장 없음 | 저장장치, 시리얼 데이터, 네트워크 | 0x81 IN, 0x02 OUT |
| interrupt | 신뢰, **주기적으로 폴링** (`bInterval`) | 작지만 지연 상한 보장 | 키보드·마우스, 상태 알림 | 0x81 IN (HID) |
| isochronous | **재시도 없음**, 대역폭 예약 | 일정한 속도 | 오디오, 웹캠 영상 | 0x82 IN (UVC) |

"interrupt 전송"이라는 이름이 헷갈리는데, 장치가 인터럽트를 거는 게 아니다. **호스트가 정해진 주기로 "새 데이터 있어?" 하고 묻는 것**이다(polling). 장치가 할 말이 없으면 NAK로 답하고, 호스트 컨트롤러가 하드웨어로 다음 주기에 다시 묻는다. 드라이버 입장에서는 "URB를 하나 걸어 두면 데이터가 왔을 때 completion이 불린다"로 보이니, 결과적으로 인터럽트처럼 쓰인다.

속도 등급: Low 1.5 Mb/s, Full 12 Mb/s, High 480 Mb/s(USB 2.0), SuperSpeed 5 Gb/s(USB 3.x Gen1) 이상. sysfs `speed` 파일은 이 값을 Mb/s로 보여 준다(`12`, `480`, `5000`).

### 1.3 디스크립터 계층

장치는 자기소개를 **디스크립터**라는 정해진 형식의 바이트열로 들고 있다. 모든 디스크립터의 첫 두 바이트는 `bLength`, `bDescriptorType`이라서, 바이트열을 처음부터 길이만큼씩 건너뛰며 읽으면 된다(§3에서 직접 디코드한다).

- **Device descriptor**(타입 1, 18바이트): `idVendor`/`idProduct`, USB 버전, endpoint 0 최대 패킷, configuration 개수.
- **Configuration descriptor**(타입 2): 전력(`MaxPower`), 자가 전원 여부, interface 개수, 그리고 `wTotalLength` — 이 configuration에 딸린 모든 디스크립터를 합친 길이. 장치는 configuration 하나를 골라(`SET_CONFIGURATION`) 쓴다. 실제로는 거의 다 configuration이 1개다.
- **Interface descriptor**(타입 4): **기능 하나**. class/subclass/protocol(예: 03/01/01 = HID 부트 키보드, 08/06/50 = Mass Storage SCSI BOT). 같은 interface에 **alternate setting**이 여러 개 있을 수 있다(예: 웹캠의 대역폭별 설정).
- **Endpoint descriptor**(타입 5): 주소(0x81 = 1번 IN), 전송 종류, `wMaxPacketSize`, `bInterval`.
- 그 외: String(타입 3, UTF-16LE 문자열), IAD(타입 0x0b, interface 여러 개를 한 기능으로 묶음), class-specific(0x21 HID, 0x24 CDC), SuperSpeed endpoint companion(0x30), OTG(0x09).

**Don 경험과 연결**: NVMe Identify Controller 데이터에 VID/모델명/큐 개수가 들어 있듯, USB device descriptor에는 VID/PID/configuration 개수가 들어 있다. 차이는 USB가 "한 장치 = 여러 기능(interface)"을 기본으로 한다는 점이다. 하나의 USB 장치가 시리얼 포트이면서 동시에 디스크일 수 있고, Linux는 각 interface에 서로 다른 드라이버를 붙인다. NVMe로 치면 namespace마다 다른 드라이버가 붙는 셈이다.

그림 3 — Linux USB host 스택. interface 드라이버는 HW를 직접 만지지 않는다. URB를 usbcore에 주면 HCD가 컨트롤러의 링(xHCI의 TRB ring)에 넣는다.

- **HCD(Host Controller Driver)**: 컨트롤러 HW를 다루는 드라이버. USB 3.x는 xHCI(`xhci-hcd`) 하나로 모든 속도를 다룬다. USB 2.0 시대에는 EHCI(High) + OHCI/UHCI(Full/Low) 짝이었다. SoC에서는 DWC3의 host 모드가 내부적으로 xHCI다. HCD는 `struct hc_driver`(`urb_enqueue`, `urb_dequeue`, `hub_control` …)를 구현한다.
- **usbcore**: `usb_bus_type`을 등록하고, 장치(`struct usb_device`)와 interface(`struct usb_interface`)를 driver core에 올린다. URB 제출·취소·완료를 중개한다. 장치 드라이버 입장의 "OS"다.
- **hub 드라이버**: root hub와 외부 hub 모두를 다루는 usbcore 안의 드라이버. 포트 상태 변화(연결/해제)를 `hub_wq` 워크큐에서 처리한다.

### 2.2 열거(enumeration) — 꽂는 순간 일어나는 일

1. hub가 포트 상태 변화를 알린다(root hub는 HCD 인터럽트, 외부 hub는 hub의 interrupt endpoint).
2. hub 드라이버가 포트를 **리셋**한다. 장치는 주소 0, 기본 상태가 된다. 속도가 이때 정해진다.
3. 주소 0으로 `GET_DESCRIPTOR(DEVICE)` 앞부분을 읽어 endpoint 0의 최대 패킷 크기를 안다.
4. `SET_ADDRESS`로 새 주소를 준다(xHCI에서는 컨트롤러가 Address Device 명령으로 대신 한다).
5. Device descriptor 전체, Configuration descriptor(먼저 9바이트, 그다음 `wTotalLength`만큼 전체), String descriptor를 읽는다.
6. `struct usb_device`를 만들고 `device_add` → usbcore의 "generic" 장치 드라이버(`usb`)가 configuration을 고르고 `SET_CONFIGURATION`을 보낸다.
7. configuration 안의 interface마다 `struct usb_interface`를 만들고 `device_add` → **uevent(MODALIAS=usb:v…p…ic…)** → 맞는 interface 드라이버의 `probe(intf, id)` 호출. 모듈이 없으면 udev/mdev가 modalias로 `modprobe`.

NVMe 비유: 1~2는 PCIe 링크 업 + 컨트롤러 리셋, 5는 Identify, 6은 "Set Features로 큐 개수 설정", 7은 namespace 스캔 후 블록 장치 등록이다.

## 3. 디스크립터를 직접 읽기 — `lsusb -v`를 손으로 짜 보기

### 3.1 어디서 읽나

- `/sys/bus/usb/devices/<장치>/descriptors` — usbcore가 열거 때 읽어 **캐시해 둔 원본 바이트**. device descriptor(18바이트) 뒤에 configuration 디스크립터 묶음이 붙어 있다. 읽어도 버스 트래픽이 생기지 않는다.
- `/dev/bus/usb/BBB/DDD`(usbfs 노드)를 `read()`해도 같은 바이트가 나온다(§9). 데스크톱 `lsusb -v`는 이걸 읽는다.
- `/sys/kernel/debug/usb/devices` — 모든 장치를 사람이 읽는 텍스트로 요약(예전 `/proc/bus/usb/devices` 형식).

### 3.2 예제 2 — 정적 C 디코더 `h12_desc`

무엇을 확인하나: `descriptors` 파일을 `bLength`만큼씩 건너뛰며 타입별로 해석한다. BusyBox 게스트에는 공유 libc가 없으므로 VM에서 `gcc -static`으로 빌드해 initramfs에 넣었다.

```c
/* h12_desc.c - decode /sys/bus/usb/devices/<dev>/descriptors (raw USB descriptors) */
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <fcntl.h>
#include <unistd.h>

static const char *xfer[] = { "control", "isoc", "bulk", "interrupt" };

int main(int argc, char **argv)
{
	char path[256];
	uint8_t b[4096];
	if (argc != 2) { fprintf(stderr, "usage: %s <sysfs-dev e.g. 1-1>\n", argv[0]); exit(1); }
	snprintf(path, sizeof(path), "/sys/bus/usb/devices/%s/descriptors", argv[1]);
	int fd = open(path, O_RDONLY);
	if (fd < 0) { perror(path); exit(1); }
	ssize_t n = read(fd, b, sizeof(b));
	if (n < 18) { perror("read"); exit(1); }
	close(fd);
	printf("%s: %zd bytes\n", path, n);
	for (ssize_t i = 0; i + 2 <= n && b[i] >= 2; i += b[i]) {
		uint8_t *d = &b[i];
		switch (d[1]) {
		case 1: /* DEVICE */
			printf("DEVICE  bcdUSB=%x.%02x class=%02x mps0=%u idVendor=%04x idProduct=%04x nConf=%u\n",
			       d[3], d[2], d[4], d[7], d[8] | d[9] << 8, d[10] | d[11] << 8, d[17]);
			break;
		case 2: /* CONFIGURATION */
			printf(" CONFIG  value=%u wTotalLength=%u nIf=%u attr=0x%02x MaxPower=%umA\n",
			       d[5], d[2] | d[3] << 8, d[4], d[7], d[8] * 2);
			break;
		case 4: /* INTERFACE */
			printf("  IF    num=%u alt=%u nEP=%u class=%02x sub=%02x proto=%02x\n",
			       d[2], d[3], d[4], d[5], d[6], d[7]);
			break;
		case 5: /* ENDPOINT */
			printf("   EP   0x%02x %-3s %-9s wMaxPacket=%u bInterval=%u\n",
			       d[2], (d[2] & 0x80) ? "IN" : "OUT", xfer[d[3] & 3],
			       d[4] | d[5] << 8, d[6]);
			break;
		case 0x21: printf("   (class-specific 0x21, HID or CDC functional, len %u)\n", d[0]); break;
		case 0x24: printf("   (CS_INTERFACE 0x24, CDC functional, len %u)\n", d[0]); break;
		case 0x09: printf("  OTG   bmAttributes=0x%02x (HNP/SRP capable bits)\n", d[2]); break;
		case 0x30: printf("    SS-EP-companion bMaxBurst=%u\n", d[2]); break;
		case 0x0b: printf("  IAD   firstIf=%u count=%u class=%02x\n", d[2], d[3], d[4]); break;
		default: printf("   (type 0x%02x len %u)\n", d[1], d[0]);
		}
	}
	return 0;
}
```


출력에서 볼 것:

- 크기 계산이 맞는다: 키보드 52 = device 18 + `wTotalLength` 34. 그 34 = config 9 + interface 9 + HID 9 + endpoint 7.
- **장치 class가 00**("interface에서 정한다")이고, 진짜 정체는 interface class에 있다: 키보드 03/01/01(HID, boot, keyboard), 디스크 08/06/50(Mass Storage, SCSI, Bulk-Only Transport), FTDI ff/ff/ff(vendor-specific — 그래서 class 드라이버가 아니라 VID:PID로 매칭하는 `ftdi_sio`가 필요하다).
- `mps0=9`인 디스크: USB 3에서는 endpoint 0 최대 패킷을 2의 지수로 적는다(2^9 = 512). bulk `wMaxPacket`도 USB 2 High-Speed는 512, SuperSpeed는 1024, Full-Speed FTDI는 64다. 같은 "bulk"라도 속도 등급마다 패킷 크기가 다르다.
- `bInterval=7`(High-Speed interrupt): 주기 = 2^(7-1) × 125 µs = 8 ms. debugfs가 아래에서 `Ivl=8ms`로 계산해 보여 준다. Full/Low-Speed에서는 `bInterval`이 그냥 ms 단위다. 이 해석 차이는 실무에서 자주 틀린다.
- `attr=0xa0`: bit7(항상 1) + bit5 **remote wakeup** 지원(키보드로 시스템 깨우기). `0xc0`: bit6 자가 전원.

### 4.2 예제 5 — FTDI USB-시리얼: VM의 socat과 대화

무엇을 확인하나: QEMU `usb-serial`은 FTDI FT232(`0403:6001`)를 흉내 내고, 반대쪽 끝은 QEMU chardev(여기서는 VM의 유닉스 소켓)에 연결된다. 게스트에서 `ftdi_sio`를 넣으면 `/dev/ttyUSB0`이 생기고, 그 포트로 쓴 바이트가 VM의 socat에 도착한다. 센서 키트에서 GNSS 모듈이 FTDI 칩으로 붙는 상황과 같다.

```sh
stty -F /dev/ttyUSB0 115200 raw -echo
cat /dev/ttyUSB0 > /tmp/rx & P=$!; sleep 1
echo "hello-from-guest" > /dev/ttyUSB0; sleep 2; kill $P; echo "guest received: $(cat /tmp/rx)"
```

## 5. `usb_driver` — 드라이버는 interface에 붙는다

### 5.1 왜 interface인가

USB 장치 하나가 여러 기능을 가질 수 있기 때문이다. 웹캠 하나 = 영상(interface 0, 1) + 마이크(interface 2, 3). 영상은 `uvcvideo`, 마이크는 `snd-usb-audio`가 가져가야 한다. 그래서 usbcore는 **interface마다 `struct device`를 만들고**, 일반 드라이버는 `struct usb_driver`로 interface에 붙는다. 장치 전체에 붙는 `struct usb_device_driver`도 있지만, 일반 드라이버가 쓸 일은 거의 없다(usbcore의 generic 드라이버와 일부 특수 드라이버용).

| 구조체 | 무엇 | 어디서 얻나 |
|---|---|---|
| `struct usb_device` | 물리 장치 하나 (주소, 속도, ep0, 디스크립터 캐시) | `interface_to_usbdev(intf)` |
| `struct usb_interface` | 기능 하나 (`dev`, `altsetting[]`, `cur_altsetting`) | `probe()`의 첫 인자 |
| `struct usb_host_interface` | alternate setting 하나 (`desc`, `endpoint[]`) | `intf->cur_altsetting` |
| `struct usb_host_endpoint` / `usb_endpoint_descriptor` | endpoint (주소, 종류, maxp, interval) | `alt->endpoint[i].desc` 또는 `usb_find_int_in_endpoint()` |
| `struct usb_driver` | interface 드라이버 (`probe`, `disconnect`, `id_table`, `suspend`/`resume`) | 직접 정의 |

### 5.2 `id_table` 매크로

| 매크로 | 무엇으로 매칭 | 쓰는 곳 |
|---|---|---|
| `USB_DEVICE(vid, pid)` | VID:PID | 특정 칩 드라이버 (`ftdi_sio`, `cp210x`) |
| `USB_DEVICE_AND_INTERFACE_INFO(vid, pid, cl, sc, pr)` | VID:PID + interface class | 한 장치 여러 interface 중 하나만 (LTE 모뎀의 특정 포트) |
| `USB_DEVICE_INTERFACE_NUMBER(vid, pid, num)` | VID:PID + interface 번호 | 모뎀의 n번 interface만 |
| `USB_INTERFACE_INFO(cl, sc, pr)` | interface class/subclass/protocol | class 드라이버 (`usb-storage`, `cdc_acm`, `usbhid`) |
| `USB_DEVICE_INFO(cl, sc, pr)` | 장치 class | hub 등 |

`MODULE_DEVICE_TABLE(usb, ids)`를 쓰면 모듈에 `usb:v…p…` alias가 들어가서 §2.4의 `modalias`와 매칭되어 자동 로드된다. `driver_info` 필드에 칩별 quirk 포인터를 넣어 `probe`에서 `id->driver_info`로 꺼내 쓰는 것이 관용구다.

### 5.3 동적 바인딩 — `new_id`, `bind`, `unbind`

`id_table`에 없는 장치를 개발 중에 붙여 보고 싶을 때(새 PID 시제품, 다른 드라이버가 이미 잡은 장치) 다시 빌드할 필요가 없다.

- `/sys/bus/usb/drivers/<drv>/new_id`에 `"VID PID [intf-class]"`를 쓰면 동적 id가 추가되고 즉시 매칭을 다시 돈다.
- `/sys/bus/usb/drivers/<drv>/unbind`에 interface 이름(`1-1:1.0`)을 쓰면 그 드라이버를 떼어 낸다. `bind`는 반대.
- 이미 다른 드라이버가 잡고 있는 interface는 매칭 대상이 아니다. 그래서 순서가 **unbind → new_id**다.

### 5.4 드라이버 코드 `h12_drv` (1/3) — 상태와 completion 핸들러

무엇을 확인하나: QEMU USB 키보드의 interrupt IN endpoint(0x81)에 URB를 걸어 두고, 키를 누를 때마다 completion에서 8바이트 boot report를 출력한다. completion이 어떤 문맥에서 도는지도 같이 찍는다.

```c
// SPDX-License-Identifier: GPL-2.0
/* h12_drv: minimal usb_driver for a HID boot keyboard interface (bound via new_id) */
#include <linux/module.h>
#include <linux/usb.h>
#include <linux/slab.h>

struct h12 {
	struct usb_interface *intf;
	struct urb *urb;
	struct usb_anchor anchor;
	u8 *buf;
	dma_addr_t dma;
	int count;
};

static void h12_irq(struct urb *urb)		/* completion: atomic context */
{
	struct h12 *h = urb->context;
	int ret;

	switch (urb->status) {
	case 0:
		break;
	case -ENOENT: case -ECONNRESET: case -ESHUTDOWN:	/* killed / unplugged */
		dev_info(&h->intf->dev, "urb stopped, status=%d after %d reports\n",
			 urb->status, h->count);
		return;
	default:					/* transient error: retry */
		goto resubmit;
	}
	h->count++;
	dev_info(&h->intf->dev, "report#%d [%*ph] hardirq=%d softirq=%d in_interrupt=%d irqs_off=%d\n",
		 h->count, urb->actual_length, h->buf, !!in_hardirq(),
		 !!in_serving_softirq(), !!in_interrupt(), irqs_disabled());
resubmit:
	usb_anchor_urb(urb, &h->anchor);		/* giveback unanchored it */
	ret = usb_submit_urb(urb, GFP_ATOMIC);		/* no sleeping here */
	if (ret) {
		usb_unanchor_urb(urb);
		dev_err(&h->intf->dev, "resubmit failed %d\n", ret);
	}
}
```

### 5.5 드라이버 코드 (2/3) — `probe(intf, id)`

```c
static int h12_probe(struct usb_interface *intf, const struct usb_device_id *id)
{
	struct usb_device *udev = interface_to_usbdev(intf);
	struct usb_host_interface *alt = intf->cur_altsetting;
	struct usb_endpoint_descriptor *ep;
	struct h12 *h;
	u8 *rd;
	int ret, len;

	if (alt->desc.bInterfaceClass != USB_CLASS_HID || alt->desc.bInterfaceProtocol != 1)
		return -ENODEV;				/* only boot keyboards */
	ret = usb_find_int_in_endpoint(alt, &ep);
	if (ret)
		return ret;
	/* synchronous control transfer: HID GET_DESCRIPTOR(Report), may sleep */
	rd = kmalloc(128, GFP_KERNEL);			/* DMA-able, never the stack */
	if (!rd)
		return -ENOMEM;
	len = usb_control_msg(udev, usb_rcvctrlpipe(udev, 0), USB_REQ_GET_DESCRIPTOR,
			      USB_DIR_IN | USB_RECIP_INTERFACE, 0x22 << 8,
			      alt->desc.bInterfaceNumber, rd, 128, USB_CTRL_GET_TIMEOUT);
	dev_info(&intf->dev, "report descriptor: %d bytes, starts [%*ph]\n",
		 len, len > 8 ? 8 : max(len, 0), rd);
	kfree(rd);

	h = devm_kzalloc(&intf->dev, sizeof(*h), GFP_KERNEL);
	if (!h)
		return -ENOMEM;
	h->intf = intf;
	init_usb_anchor(&h->anchor);
	h->urb = usb_alloc_urb(0, GFP_KERNEL);
	if (!h->urb)
		return -ENOMEM;
	h->buf = usb_alloc_coherent(udev, 8, GFP_KERNEL, &h->dma);
	if (!h->buf) {
		usb_free_urb(h->urb);
		return -ENOMEM;
	}
	usb_fill_int_urb(h->urb, udev, usb_rcvintpipe(udev, ep->bEndpointAddress),
			 h->buf, 8, h12_irq, h, ep->bInterval);
	h->urb->transfer_dma = h->dma;
	h->urb->transfer_flags |= URB_NO_TRANSFER_DMA_MAP;
	usb_set_intfdata(intf, h);
	usb_anchor_urb(h->urb, &h->anchor);
	ret = usb_submit_urb(h->urb, GFP_KERNEL);
	if (ret) {
		usb_unanchor_urb(h->urb);
		usb_free_coherent(udev, 8, h->buf, h->dma);
		usb_free_urb(h->urb);
		return ret;
	}
	dev_info(&intf->dev, "bound: ep 0x%02x maxp %d bInterval %d, int URB submitted\n",
		 ep->bEndpointAddress, usb_endpoint_maxp(ep), ep->bInterval);
	return 0;
}
```

### 5.6 드라이버 코드 (3/3) — `disconnect`와 등록

```c
static void h12_disconnect(struct usb_interface *intf)
{
	struct h12 *h = usb_get_intfdata(intf);

	dev_info(&intf->dev, "disconnect: state=%d, killing anchored URBs\n",
		 interface_to_usbdev(intf)->state);
	usb_kill_anchored_urbs(&h->anchor);		/* waits for completion to finish */
	usb_free_coherent(interface_to_usbdev(intf), 8, h->buf, h->dma);
	usb_free_urb(h->urb);
	dev_info(&intf->dev, "disconnect done, %d reports total\n", h->count);
}

static const struct usb_device_id h12_ids[] = {
	{ }	/* empty: we bind only through /sys/bus/usb/drivers/h12_drv/new_id */
};
MODULE_DEVICE_TABLE(usb, h12_ids);

static struct usb_driver h12_driver = {
	.name = "h12_drv",
	.probe = h12_probe,
	.disconnect = h12_disconnect,
	.id_table = h12_ids,
};
module_usb_driver(h12_driver);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H12 demo usb_driver: interrupt URB on a HID keyboard");
```

코드에서 볼 것:

- `probe`는 **process 문맥**이라 잠들 수 있다 — `usb_control_msg`(동기, 잠듦), `GFP_KERNEL` 할당이 모두 여기서는 괜찮다. completion(`h12_irq`)은 **원자 문맥**이라 `GFP_ATOMIC`만 쓴다.
- 버퍼는 `usb_alloc_coherent`(DMA coherent 메모리) + `URB_NO_TRANSFER_DMA_MAP`. 매번 매핑하지 않아도 되는 작은 주기 버퍼의 관용구다. `kmalloc` 버퍼를 줘도 된다(usbcore가 streaming DMA 매핑을 해 준다). **스택 버퍼는 절대 안 된다** — DMA 불가(`VMAP_STACK`이면 스택이 vmalloc 영역이라 물리적으로 연속이 아니다). 그래서 report descriptor 읽기도 `kmalloc`을 썼다.
- `h` 자체는 `devm_kzalloc` — interface `dev`에 묶여 unbind 때 자동 해제된다. 그러나 URB와 coherent 버퍼는 `disconnect`에서 직접 정리한다. URB는 **completion이 끝났음이 보장된 뒤에만** 해제할 수 있기 때문이다(§6.4).
- `id_table`이 비어 있으므로 insmod만으로는 아무것에도 붙지 않는다. `new_id`로만 붙는다.

## 6. URB — USB의 "명령 하나"

### 6.1 직관

**URB(USB Request Block)** = "이 장치의 이 endpoint로 이 버퍼만큼 보내/받아 줘, 끝나면 이 함수를 불러 줘"라는 요청서다. NVMe의 SQ entry + 완료 콜백에 해당한다. 드라이버는 URB를 usbcore에 맡기고(`usb_submit_urb`) 바로 돌아온다(비동기). 전송이 끝나면(성공·실패·취소) HCD가 URB를 돌려주고 usbcore가 `urb->complete(urb)`를 부른다.

`struct urb`의 주요 필드:

| 필드 | 뜻 |
|---|---|
| `dev`, `pipe` | 대상 장치와 endpoint(방향·종류 포함). `usb_sndbulkpipe`, `usb_rcvintpipe`, `usb_rcvctrlpipe` … |
| `transfer_buffer`, `transfer_buffer_length` | 데이터 버퍼(DMA 가능한 메모리)와 길이 |
| `transfer_dma` + `URB_NO_TRANSFER_DMA_MAP` | 드라이버가 이미 DMA 주소를 갖고 있을 때(`usb_alloc_coherent`) |
| `actual_length` | 실제로 옮겨진 바이트 수 (짧은 패킷이면 요청보다 작다) |
| `status` | 완료 상태 (0 = 성공, 음수 errno) |
| `complete`, `context` | 완료 콜백과 그 인자 |
| `interval` | interrupt/isoc 폴링 주기 |
| `transfer_flags` | `URB_SHORT_NOT_OK`, `URB_ZERO_PACKET`, `URB_NO_TRANSFER_DMA_MAP` … |
| `setup_packet` | control 전송의 8바이트 셋업 |

### 6.3 완료 상태 코드

| `urb->status` | 뜻 | completion에서 할 일 |
|---|---|---|
| `0` | 성공 (`actual_length` 확인) | 데이터 처리, 필요하면 재제출 |
| `-ENOENT` | `usb_kill_urb`로 취소됨 | 재제출 금지, 그냥 반환 |
| `-ECONNRESET` | `usb_unlink_urb`(비동기 취소) | 재제출 금지 |
| `-ESHUTDOWN` (-108) | 장치 제거, endpoint 비활성, HC 정지 | 재제출 금지 (§5.7 실측) |
| `-EPIPE` | endpoint STALL (장치가 거부) | `usb_clear_halt()` — 잠드는 함수라 workqueue에서 |
| `-EPROTO`, `-EILSEQ`, `-ETIME` | 비트 스터핑·CRC·응답 없음 (잡음, 뽑히는 중) | 몇 번 재시도 후 포기, 보통 곧 disconnect가 온다 |
| `-EOVERFLOW` | babble — 장치가 요청보다 더 보냄 | 버퍼 크기·maxpacket 확인 |
| `-EREMOTEIO` | `URB_SHORT_NOT_OK`인데 짧은 패킷 | 프로토콜 오류로 처리 |

### 6.4 취소와 정리 — kill, unlink, poison, anchor

- `usb_kill_urb(urb)`: 취소하고 **completion이 끝날 때까지 기다린다**. 그래서 잠들 수 있는 문맥(disconnect, release, suspend)에서만 쓴다. 돌아온 뒤에는 그 URB를 안전하게 해제·재사용할 수 있다. kill이 진행되는 동안의 재제출은 실패한다.
- `usb_unlink_urb(urb)`: 비동기 취소. 원자 문맥에서도 쓸 수 있지만 돌아왔을 때 아직 끝나지 않았을 수 있다.
- `usb_poison_urb(urb)`: kill + 이후 재제출을 영구히 막음(`usb_unpoison_urb`로 해제). suspend/reset 경로에서 쓴다.
- **anchor**(`struct usb_anchor`): URB 여러 개를 묶는 리스트. 제출 전에 `usb_anchor_urb()`, giveback 시 usbcore가 자동으로 떼어 낸다(그래서 h12_drv는 재제출 전에 다시 anchor했다). `usb_kill_anchored_urbs()`, `usb_wait_anchor_empty_timeout()`, `usb_scuttle_anchored_urbs()`로 한 번에 정리한다. 네트워크·시리얼 드라이버처럼 **bulk OUT URB가 여러 개 떠 있는** 드라이버에서 특히 유용하다.

**Don 경험과 연결**: SSD 펌웨어에서 PCIe 링크가 끊기거나 컨트롤러 리셋이 오면 "in-flight 명령을 전부 abort 상태로 완료시키고, 완료 콜백이 다 돈 다음에 버퍼를 반납"했을 것이다. `usb_kill_anchored_urbs`가 정확히 그 "drain"이다. 그리고 "완료 콜백 안에서는 블로킹 금지"도 ISR에서 블로킹 금지와 같은 규칙이다.

### 6.5 completion 문맥 — 실측이 말해 준 것

§5.7의 측정은 `hardirq=0 softirq=1 in_interrupt=1`이었다. 정리하면:

- completion은 **항상 원자 문맥**이라고 가정하고 짠다. 문서(`usb_hcd_giveback_urb` 주석)도 "Context: atomic"이다.
- 실제 문맥은 HCD에 따라 다르다. `HCD_BH` 플래그가 있는 HCD(xHCI, EHCI — 랩 소스에서 확인)와 모든 root hub URB는 BH 문맥(6.18 소스에서는 `system_bh_highpri_wq`/`system_bh_wq` BH 워크큐), 그렇지 않은 HCD는 HCD가 giveback을 부른 문맥 그대로(하드 IRQ일 수도 있다). `dummy_hcd`는 `HCD_BH`가 없지만 giveback을 `HRTIMER_MODE_REL_SOFT` 타이머 콜백에서 하므로 역시 softirq다(소스 읽기로 확인, 측정은 xHCI에서만 함).
- 그러므로 completion에서는: 잠드는 함수(`mutex_lock`, `usb_control_msg`, `msleep`, `GFP_KERNEL`, `copy_to_user`) 금지. 데이터는 링버퍼에 넣고 `wake_up`하거나, 무거운 일은 `schedule_work`로 넘긴다. 공유 상태는 `spin_lock_irqsave`로 보호한다.

## 7. 동기 헬퍼 — `usb_control_msg`, `usb_bulk_msg`

URB를 직접 다루기 번거로운 "한 번 묻고 답 받기"에는 동기 헬퍼를 쓴다. 내부에서 URB를 하나 만들어 제출하고 completion을 **잠들어 기다린다**.

| 함수 | 용도 | 반환 |
|---|---|---|
| `usb_control_msg(udev, pipe, bRequest, bmRequestType, wValue, wIndex, data, size, timeout_ms)` | ep0 control 전송 (설정 쓰기, 상태 읽기, vendor 명령) | 전송 바이트 수 또는 음수 errno |
| `usb_control_msg_recv()` / `usb_control_msg_send()` | 위의 편의판: 내부에서 DMA 가능 버퍼를 할당·복사, 짧은 응답을 에러로 처리 | 0 또는 음수 errno |
| `usb_bulk_msg(udev, pipe, data, len, &actual, timeout_ms)` | bulk 한 번 | 0 또는 음수 errno (`-ETIMEDOUT`) |
| `usb_interrupt_msg()` | interrupt endpoint 한 번 | 위와 같음 |
| `usb_get_descriptor()`, `usb_string()`, `usb_clear_halt()`, `usb_set_interface()`, `usb_reset_device()` | 표준 요청 래퍼 | 상황별 |

규칙:

- process 문맥에서만(probe, `read`/`write`/`ioctl` 구현, workqueue). completion·타이머·spinlock 안에서 부르면 "scheduling while atomic" BUG다.
- 데이터 버퍼는 `kmalloc`(DMA 가능). 스택 변수 주소를 넘기는 것은 고전적 버그다 — 그래서 `_recv/_send` 변형이 생겼다.
- timeout은 ms(`USB_CTRL_GET_TIMEOUT` = 5000, `include/linux/usb.h`). 실시간성이 필요한 데이터 경로에는 동기 헬퍼 대신 URB를 여러 개 띄워 둔다(파이프라이닝).

h12_drv의 probe에서 `usb_control_msg(GET_DESCRIPTOR, wValue=0x2200, wIndex=interface)`로 HID report descriptor 63바이트를 읽은 것이 예다(§5.7 출력).

## 8. 버스 들여다보기 — usbmon, 그리고 이 랩의 대안

### 8.1 usbmon (랩 커널에서는 꺼져 있음)

`usbmon`은 usbcore 안의 훅으로 **모든 URB의 제출·완료**를 기록하는 커널 내장 "버스 분석기"다. HW 분석기(Beagle, Ellisys)처럼 패킷 단위는 아니고 URB 단위지만, 대부분의 드라이버 디버깅에는 충분하다.

```sh
ls /sys/kernel/debug/usb; uname -r
```

```text
devices  ehci     ohci     xhci
6.18.55-dbg
```

랩 커널은 `# CONFIG_USB_MON is not set`이라 `usbmon` 디렉터리가 없다(일반 커널·디버그 커널 둘 다 `.config`에서 확인). usbmon은 usbcore의 훅이 `CONFIG_USB_MON`으로 컴파일되어야 동작하므로 out-of-tree로 붙일 수 없다. 켜진 커널에서의 사용법은 다음과 같다(**이 랩에서 실행하지 않음**, Documentation/usb/usbmon.rst 기준):

```sh
modprobe usbmon                             # =m일 때
cat /sys/kernel/debug/usb/usbmon/1u         # 버스 1, 텍스트 'u' 형식 (0u = 모든 버스)
# 바이너리 인터페이스 /dev/usbmonN 은 Wireshark·tcpdump(-i usbmon1)가 읽는다
```

텍스트 한 줄의 구성은 `URB 태그, 타임스탬프(µs), 이벤트(S=submit, C=callback, E=error), 주소 "Bo:1:002:2"(종류 B/I/C/Z + 방향 i/o : 버스 : 장치 : endpoint), 상태, 길이, 데이터 앞부분`이다. 예를 들어 저장장치 읽기는 `Bo`(bulk OUT)로 31바이트 CBW `55534243…`("USBC"), `Bi`로 데이터, `Bi`로 13바이트 CSW `55534253…`("USBS")가 S/C 쌍으로 보인다.

### 8.2 예제 7 — 대안: xHCI tracepoint로 storage 읽기 한 번 보기

무엇을 확인하나: 랩의 디버그 커널(`Image-dbg`, `CONFIG_TRACING=y`)에는 xHCI 드라이버의 tracepoint가 있다. URB가 xHCI 링에 들어가고(`xhci_urb_enqueue`) 돌아오는(`xhci_urb_giveback`) 순간을 찍으면 usbmon과 비슷한 그림을 얻는다. QEMU USB 디스크에서 4 KiB를 `O_DIRECT`로 한 번 읽는다.

```sh
mount -t tracefs none /sys/kernel/tracing; cd /sys/kernel/tracing
ls events | grep -i -E "xhci|usb" | tr '\n' ' '; echo
ls events/xhci-hcd | grep urb | tr '\n' ' '; echo
echo 1 > events/xhci-hcd/xhci_urb_enqueue/enable; echo 1 > events/xhci-hcd/xhci_urb_giveback/enable
echo > trace
dd if=/dev/sda of=/dev/null bs=4096 count=1 skip=100 iflag=direct 2>&1 | tail -1
echo 0 > tracing_on
grep -v "^#" trace | sed 's/^ *//' | cut -c1-230
```

출력에서 볼 것:

- **Bulk-Only Transport 3단계**가 그대로 보인다: ① `ep2out-bulk 31/31` = CBW(Command Block Wrapper, SCSI READ(10) 명령을 담은 31바이트) → ② `ep1in-bulk 4096/4096` = 데이터(scatter-gather 1개) → ③ `ep1in-bulk 13/13` = CSW(Command Status Wrapper). 이 부팅에는 디스크만 꽂아서 장치 이름이 `2-1`이다(§2.3과 다름).
- 제출 주체는 `usb-storage-58` 커널 스레드(usb-storage의 제어 스레드)다. 이 스레드가 한 단계씩 제출하고(`usb_sg_init`/`usb_sg_wait` 등) 잠들어 기다린다. 포인터 값(`urb 0000…`)은 해시된 값이고 실행마다 다르다.
- **giveback 줄의 플래그 `d.h2.`**: `d` = IRQ 꺼짐, `h` = **하드 IRQ 안**. xHCI는 하드 IRQ(`xhci_irq` → 이벤트 링 처리 → `xhci_giveback_urb_in_irq`)에서 URB를 돌려주고, 이 tracepoint는 그 안에서 `usb_hcd_giveback_urb()` 바로 앞에 있다(`drivers/usb/host/xhci-ring.c`). 그다음 usbcore가 completion을 BH로 미루기 때문에 드라이버의 completion은 §5.7처럼 softirq에서 돈다. **"HCD는 hardirq, 드라이버 completion은 BH"** 두 단계를 두 실험으로 모두 확인했다.

### 8.3 그 밖의 도구

- `dmesg` + dynamic debug(랩 커널 `CONFIG_DYNAMIC_DEBUG=y`, 예: 커널 인자 `dyndbg="module xhci_hcd +p"`) — 열거 실패, 리셋, 대역폭 오류의 상세 로그.
- `/sys/kernel/debug/usb/xhci/<pci>/` — xHCI 링·포트 상태 덤프(위 `ls`에서 `xhci` 디렉터리).
- HW 프로토콜 분석기 — 신호 품질, 타이밍, LPM 문제처럼 소프트웨어로 안 보이는 것. Don이 scope·로직 분석기로 PCIe/I2C를 보던 자리다.

## 9. 유저 공간 USB 드라이버 — usbfs와 libusb

### 9.1 언제 쓰나

커널 드라이버가 필요 없는 장치가 많다: 펌웨어 업데이트 툴(DFU, 벤더 부트로더), 시험 지그, 저속 계측기. 이럴 때 **libusb**로 유저 공간에서 디스크립터 읽기, control/bulk/interrupt 전송을 한다. libusb는 Linux에서 **usbfs**(`/dev/bus/usb/BBB/DDD` 문자 장치, 메이저 189)의 ioctl을 감싼 라이브러리다. 커널 쪽은 usbcore 안의 `usbfs` 드라이버(§5.7 드라이버 목록의 `usbfs`)가 "interface를 claim한 유저 프로세스"를 대신하는 interface 드라이버 역할을 한다.

장점: 크래시해도 커널이 안전, 배포·디버그가 쉬움. 단점: 지연이 크고 다른 커널 서브시스템(input, net, tty)에 장치를 노출할 수 없다.

### 9.2 예제 8 — libusb 없이 usbfs ioctl로 키보드 읽기

무엇을 확인하나: usbfs 노드 `read()`(캐시된 디스크립터), `USBDEVFS_CONTROL`(문자열 디스크립터), 커널 드라이버 떼기(`USBDEVFS_DISCONNECT`), interface claim, interrupt endpoint 읽기, 원래 드라이버 되돌리기(`USBDEVFS_CONNECT`). libusb의 `libusb_detach_kernel_driver`, `libusb_claim_interface`, `libusb_interrupt_transfer`가 내부에서 하는 일이다.

```c
/* h12_usbfs.c - user-space USB driver via usbfs (what libusb does underneath) */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <linux/usbdevice_fs.h>
#include <linux/usb/ch9.h>

int main(int argc, char **argv)
{
	unsigned char buf[255];
	if (argc != 2) { fprintf(stderr, "usage: %s /dev/bus/usb/BBB/DDD\n", argv[0]); exit(1); }
	int fd = open(argv[1], O_RDWR);
	if (fd < 0) { perror(argv[1]); exit(1); }

	/* 0. read() on a usbfs node returns the cached device(+config) descriptors */
	if (read(fd, buf, 18) != 18) { perror("read"); exit(1); }
	printf("idVendor=%02x%02x idProduct=%02x%02x iProduct=%u\n", buf[9], buf[8], buf[11], buf[10], buf[15]);
	/* 1. control transfer on ep0: GET_DESCRIPTOR(STRING, iProduct) */
	struct usbdevfs_ctrltransfer ct = {
		.bRequestType = USB_DIR_IN, .bRequest = USB_REQ_GET_DESCRIPTOR,
		.wValue = (USB_DT_STRING << 8) | buf[15], .wIndex = 0x0409,
		.wLength = sizeof(buf), .timeout = 1000, .data = buf };
	int n = ioctl(fd, USBDEVFS_CONTROL, &ct);
	if (n < 0) { perror("USBDEVFS_CONTROL"); exit(1); }
	printf("iProduct (%d bytes UTF-16LE): ", n);
	for (int i = 2; i < n; i += 2) putchar(buf[i]);
	putchar('\n');

	/* 2. claim interface 0: fails while a kernel driver owns it */
	unsigned int ifnum = 0;
	if (ioctl(fd, USBDEVFS_CLAIMINTERFACE, &ifnum) < 0)
		printf("CLAIMINTERFACE: %s -> detaching kernel driver\n", strerror(errno));
	struct usbdevfs_ioctl dc = { .ifno = 0, .ioctl_code = USBDEVFS_DISCONNECT };
	if (ioctl(fd, USBDEVFS_IOCTL, &dc) < 0) perror("USBDEVFS_DISCONNECT");
	if (ioctl(fd, USBDEVFS_CLAIMINTERFACE, &ifnum) < 0) { perror("CLAIM"); exit(1); }
	puts("interface 0 claimed by user space");

	/* 3. read interrupt IN ep 0x81 (USBDEVFS_BULK also handles interrupt eps) */
	for (int k = 0; k < 4; k++) {
		struct usbdevfs_bulktransfer bt = { .ep = 0x81, .len = 8, .timeout = 5000, .data = buf };
		n = ioctl(fd, USBDEVFS_BULK, &bt);
		if (n < 0) { perror("USBDEVFS_BULK"); break; }
		printf("report %d:", k);
		for (int i = 0; i < n; i++) printf(" %02x", buf[i]);
		putchar('\n');
	}
	ioctl(fd, USBDEVFS_RELEASEINTERFACE, &ifnum);
	struct usbdevfs_ioctl cn = { .ifno = 0, .ioctl_code = USBDEVFS_CONNECT };
	if (ioctl(fd, USBDEVFS_IOCTL, &cn) < 0) perror("USBDEVFS_CONNECT");
	close(fd);
	return 0;
}
```

```sh

h12_usbfs /dev/bus/usb/001/002 & sleep 2
# (VM에서 QEMU 모니터로 sendkey x, sendkey y)
sleep 2; wait; basename $(readlink /sys/bus/usb/devices/1-1:1.0/driver)
```

출력에서 볼 것:

- 노드 이름 `001/002` = 버스 1, devnum 2. 메이저 189가 usbfs 장치 노드다(devtmpfs가 자동으로 만든다). 양산 장비에서는 udev 규칙으로 권한을 열어 줘야 일반 유저 프로세스가 쓸 수 있다(`crw-------` 상태로는 root만).
- `CLAIMINTERFACE: Device or resource busy` — 커널 드라이버(`usbhid`)가 잡은 interface는 유저가 claim할 수 없다. `USBDEVFS_DISCONNECT`로 떼어 낸 뒤에야 claim됐다. 끝나고 `USBDEVFS_CONNECT`로 돌려주자 다시 `usbhid`가 붙었다.
- `1b`, `1c` = HID usage 'x', 'y'. §5.7의 커널 드라이버와 똑같은 report를 유저 공간에서 받았다.
- 함정(실제로 겪음): 처음 버전은 문자열 index를 `2`로 고정했더니 `iProduct (30 bytes UTF-16LE): QEMU USB Mouse`가 나왔다. QEMU의 HID 장치들은 문자열 테이블을 공유하고 키보드의 `iProduct`는 4다. **index는 반드시 device descriptor에서 읽는다.**

### 10.2 composite와 function

- **gadget driver**: UDC에 바인딩되는 "장치 전체"의 드라이버. 한 UDC에는 gadget driver 하나만 붙는다. configfs가 만드는 gadget, 레거시 `g_serial`·`g_ether`·`g_mass_storage`·`g_multi`·`g_zero`가 모두 composite 기반 gadget driver다.
- **function**: 기능 하나의 구현. `usb_function`이 자기 interface·endpoint 디스크립터와 `set_alt`(호스트가 SET_CONFIGURATION/SET_INTERFACE 했을 때 endpoint를 켜는 콜백), `setup`(class 요청 처리)을 제공한다.

| function (configfs 이름) | 모듈 | 호스트에서 보이는 것 | 제품에서의 용도 |
|---|---|---|---|
| `acm` | `usb_f_acm` + `u_serial` | `/dev/ttyACM0` (Windows 10+ 기본 드라이버) | **디버그 콘솔**, 명령 셸, 로그 |
| `gser` | `usb_f_serial` | vendor 시리얼 | 레거시 |
| `ncm` / `ecm` / `rndis` / `eem` | `usb_f_ncm` 등 + `u_ether` | 네트워크 인터페이스 (`usb0`, `enx…`) | **Ethernet-over-USB**: ssh·scp·웹 UI. NCM은 macOS·Linux·Windows 11 기본 지원, RNDIS는 구형 Windows용(보안 문제로 퇴출 중) |
| `mass_storage` | `usb_f_mass_storage` | USB 디스크 | 이미지·로그 내보내기, 업데이트 파일 받기 |
| `ffs` (FunctionFS) | `usb_f_fs` | 유저 공간이 정한 무엇이든 | ADB, MTP, 벤더 프로토콜, DFU를 유저 데몬으로 |
| `uvc`, `uac2`, `hid`, `midi`, `printer` | 각 `usb_f_*` | 웹캠, 오디오, HID 등 | 장치를 웹캠처럼 보이게 |

랩 커널의 `.config`: `CONFIG_USB_GADGET=y`, `CONFIG_USB_LIBCOMPOSITE=m`, `CONFIG_USB_F_ACM=m`, `CONFIG_USB_F_NCM=m`, `CONFIG_USB_F_MASS_STORAGE=m`, `CONFIG_USB_F_FS=m`, `CONFIG_USB_CONFIGFS=m` 등. 그러나 `CONFIG_USB_DUMMY_HCD`는 꺼져 있고 QEMU `virt`에는 진짜 UDC가 없다. G8 예제 13이 "`ls /sys/class/udc`가 비어 있어서 마지막 한 줄(`echo … > UDC`)을 못 했다"에서 멈춘 이유다. 여기서는 `dummy_hcd.c`를 out-of-tree로 빌드해서 그 자리를 채운다.

### 10.4 예제 10 — configfs로 ACM + mass storage gadget 조립 → 같은 커널이 host로 인식

- 이 구조가 그림 2의 예 그대로다: `3-1:1.0`, `3-1:1.1` → `cdc_acm`, `3-1:1.2` → `usb-storage`.
- **루프백**: host 쪽 `/dev/ttyACM0`에 쓴 줄이 gadget 쪽 `/dev/ttyGS0`에서 읽히고, 반대 방향도 된다. 실제 제품의 "PC에 꽂으면 시리얼 콘솔이 뜨는" 기능이 이 한 쌍이다. 보드 쪽에서는 `ttyGS0`에 getty를 붙인다(systemd `serial-getty@ttyGS0.service`).
- **디스크**: host가 `sdb`를 FAT로 마운트해 파일을 쓰고, 케이블을 뽑은 뒤(UDC 해제) gadget 쪽에서 원본 이미지를 loop 마운트하니 그 파일이 있다. **주의**: gadget이 연결된 동안 gadget 쪽에서 같은 이미지를 rw로 마운트하면 안 된다. 두 OS가 같은 FAT를 동시에 쓰는 것이라 파일시스템이 깨진다. 펌웨어 업데이트를 이 방식으로 할 때는 "연결 해제 → 검사 → 적용" 순서를 지킨다.
- **뽑기**: `UDC`에 빈 문자열을 쓰자 host 쪽에 `USB disconnect`가 나고 `3-1` 노드들이 사라졌다. 그런데 `udc-state`는 여전히 `configured`로 읽혔다. dummy_udc에서 관찰한 값이고, 이 sysfs 속성이 언바인드 때 갱신되지 않는 것으로 보인다 — 상태 판단은 `UDC` 파일과 host 쪽 결과로 하자.
- `bInterval=9`(HS) → `Ivl=32ms` = 2^(9-1) × 125 µs. ACM 알림 endpoint는 거의 쓰이지 않으니 느슨하게 잡혀 있다.

### 10.6 예제 12 — 레거시 `g_mass_storage` 한 줄, 그리고 BusyBox `lsusb -t`

configfs 이전에는 기능 조합마다 `g_*` 모듈이 있었고, 모듈 파라미터로 설정했다. 지금도 간단한 시험이나 initramfs 안 업데이트 모드에서 쓴다.


### 10.7 FunctionFS — 유저 공간 function (실행하지 않음)

`usb_f_fs`(configfs 이름 `ffs.<인스턴스>`)를 쓰면 function을 유저 공간 데몬이 구현한다. 순서(Documentation/usb/functionfs.rst 기준, **이 노트에서 실행하지 않음**):

```sh
mkdir functions/ffs.h12; ln -s functions/ffs.h12 configs/c.1/
mkdir -p /dev/ffs-h12 && mount -t functionfs h12 /dev/ffs-h12
# 데몬이 /dev/ffs-h12/ep0 에 디스크립터 + 문자열 블롭을 write() → ep1, ep2 … 파일이 생김
# 그다음에야 echo <udc> > UDC  (디스크립터가 준비되기 전에 바인딩하면 실패)
```

Android의 ADB, MTP 데몬과 많은 벤더의 DFU/업데이트 데몬이 이 방식이다. 커널 모듈을 새로 쓰지 않고 USB 프로토콜을 구현할 수 있다는 것이 장점이다.

## 11. OTG와 dual-role — 임베디드 SoC의 현실

### 11.1 하나의 포트, 두 역할

임베디드 SoC의 USB 컨트롤러는 대부분 **dual-role**(DRD)이다. 같은 IP가 host(xHCI/EHCI)도 되고 device(UDC)도 된다. 대표 IP:

| IP | 쓰는 SoC (예) | Linux 드라이버 |
|---|---|---|
| Synopsys DWC3 | i.MX8M Plus, AM62, Rockchip, Qualcomm, Jetson 일부 | `dwc3` (host 모드는 내부적으로 `xhci-plat`) |
| ChipIdea | i.MX6/7, i.MX8M Mini/Nano | `ci_hdrc` + `ci_hdrc_imx` |
| Synopsys DWC2 | Raspberry Pi(BCM2835), STM32MP1 | `dwc2` |
| Cadence USBSS | TI J7/AM64 | `cdns3` |
| NVIDIA XUSB | Jetson Orin | `xhci-tegra` + `tegra-xudc` |

역할을 정하는 방법:

- **Device Tree 고정**: `dr_mode = "host" | "peripheral" | "otg";` (DWC3, ChipIdea, DWC2 공통 속성). 개발 보드의 Type-C 디버그 포트는 `peripheral`로 고정하는 일이 많다.
- **role switch**: `usb-role-switch;` 속성 + Type-C 포트 컨트롤러(TCPM, `tps6598x`, `fusb302` …)나 ID 핀(`usb-conn-gpio`)이 케이블 방향을 감지해 `usb_role_switch_set_role()`을 부른다. sysfs `/sys/class/usb_role/<스위치>/role`에서 현재 역할을 보고, 드라이버가 허용하면 써서 바꿀 수 있다. 랩 커널에는 `CONFIG_USB_ROLE_SWITCH=y`, `CONFIG_USB_CONN_GPIO=y`가 켜져 있지만 QEMU에 해당 HW가 없어 실행하지 않았다.
- "OTG"는 원래 USB 2.0 OTG 스펙(HNP/SRP로 역할을 협상)을 뜻하지만, 실무에서는 대부분 "dual-role 포트"라는 뜻으로 쓴다. HNP는 거의 쓰이지 않는다.

```dts
/* 예: DWC3를 device 전용으로 (i.MX8M Plus EVK 스타일, 형식만 — 실행하지 않음) */
&usb_dwc3_0 {
	dr_mode = "peripheral";
	status = "okay";
};
```

### 11.2 제품에서 USB를 쓰는 장면

- **디버그 콘솔**: ACM function + `serial-getty@ttyGS0`. UART 핀이 없는 양산 케이스에서도 USB 케이블 하나로 셸에 들어간다. 보안상 양산 이미지에서는 끄거나 인증을 건다.
- **Ethernet-over-USB**: NCM(또는 RNDIS+ECM 조합)으로 `usb0`에 고정 IP(관례상 `192.168.7.2` 같은 사설 대역)를 주고 ssh·scp·웹 UI. BeagleBone, Jetson 개발 키트가 이 방식이다(Jetson은 RNDIS + ECM + ACM + mass storage 조합을 기본 제공).
- **펌웨어 업데이트**: ① 부트로더 단계 — U-Boot의 `ums`(USB mass storage), `dfu`, `fastboot` 명령(이건 커널이 아니라 U-Boot의 gadget 스택이다). ② SoC ROM 리커버리 — i.MX의 SDP(`uuu` 도구), Jetson RCM 모드, Rockchip maskrom: SoC ROM 코드가 USB 장치가 되어 PC에서 이미지를 받는다. ③ Linux 실행 중 — mass storage 노출 후 PC가 파일을 놓으면 검증·적용, 또는 FunctionFS 데몬.
- **Host 쪽**: USB 카메라(UVC) — isochronous 대역폭 예약 실패(`-ENOSPC`, "not enough bandwidth")가 흔한 함정, LTE 모뎀(`option`/`qmi_wwan`/`cdc_mbim` + ModemManager), USB 허브 뒤 여러 장치의 전력 예산(`bMaxPower` 합계), 그리고 udev 규칙으로 포트 경로 기반 고정 이름(`/dev/gnss0`).

## 12. 처리량 측정 — dummy_hcd bulk, 그리고 에뮬레이터의 한계

### 12.1 예제 13 — `O_DIRECT` 순차 읽기 벤치마크

무엇을 확인하나: 요청 크기(4 KiB~1 MiB)별로 블록 장치를 16 MiB씩 `O_DIRECT` + `pread`로 읽어 MB/s와 요청당 시간을 잰다. 페이지 캐시를 우회하므로 매 요청이 실제로 USB(가상)를 지난다.

```c
/* h12_bw.c - O_DIRECT sequential read throughput of a block device per request size */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <time.h>

static double now(void)
{
	struct timespec t;
	clock_gettime(CLOCK_MONOTONIC, &t);
	return t.tv_sec + t.tv_nsec / 1e9;
}

int main(int argc, char **argv)
{
	static const size_t sizes[] = { 4096, 16384, 65536, 262144, 1048576 };
	const size_t total = 16 << 20;			/* 16 MiB per size */
	if (argc != 3) { fprintf(stderr, "usage: %s /dev/sdX label\n", argv[0]); exit(1); }
	int fd = open(argv[1], O_RDONLY | O_DIRECT);
	if (fd < 0) { perror(argv[1]); exit(1); }
	void *buf;
	if (posix_memalign(&buf, 4096, 1 << 20)) { perror("posix_memalign"); exit(1); }
	for (unsigned i = 0; i < sizeof(sizes) / sizeof(sizes[0]); i++) {
		size_t bs = sizes[i], done = 0;
		double t0 = now();
		while (done < total) {
			ssize_t n = pread(fd, buf, bs, done);
			if (n <= 0) { perror("pread"); exit(1); }
			done += n;
		}
		double dt = now() - t0;
		printf("%s bs=%7zu  %6.1f MB/s  (%.0f us/req)\n", argv[2], bs,
		       total / dt / 1e6, dt / (total / bs) * 1e6);
	}
	close(fd);
	return 0;
}
```

그림 6 — 요청 크기별 순차 읽기 처리량(로그 축). 직접 측정한 값, VM(M2 위 Lima) 안의 QEMU TCG 게스트에서.

출력에서 볼 것:

- **요청 크기가 커질수록 처리량이 오른다**: 작은 요청은 "요청당 고정 비용"(SCSI 명령 → CBW → 데이터 → CSW, 그리고 dummy_hcd의 125 µs 타이머 틱 대기)이 지배한다. 4 KiB에서 HS가 요청당 약 1~1.7 ms — 실제 하드웨어에서도 USB 저장장치는 작은 I/O에 약하다. 센서 로그를 USB 디스크에 쓸 때 큰 단위로 묶어 쓰는 이유다.
- **속도 등급 순서는 맞지만 절대값은 믿으면 안 된다**: Full-Speed(12 Mb/s) gadget이 4 MB/s 넘게 나왔다. 실제 Full-Speed bulk는 프로토콜 오버헤드 포함 약 1.2 MB/s가 상한이다. `dummy_hcd`의 대역폭 모델은 "틱마다 속도별 바이트 예산"(`dummy_timer()`: FS `64 × 19`바이트, HS `512 × 13 × 8`바이트, SS `490000`바이트)인데 틱이 1 ms가 아니라 125 µs(`DUMMY_TIMER_INT_NSECS`)마다 돌 수 있어 실제보다 빨라진다. 소스 주석도 "simplistic model for one frame's bandwidth"라고 밝힌다.
- gadget 쪽 상한은 USB가 아니라 **CPU**(TCG 에뮬레이션, 한 커널이 host·gadget 양쪽 일을 다 함, `f_mass_storage`의 16 KiB 버퍼 `FSG_BUFLEN` 2개 사이의 복사)가 정한다. QEMU usb-storage가 훨씬 빠른 것은 QEMU가 디스크 이미지를 직접 복사해 주기 때문이다(실제 USB 3 디스크도 아니다).
- 같은 설정의 반복 측정이 ±30~50% 흔들렸다(VM을 다른 작업과 공유). 그래서 3회 중앙값을 그렸다. **에뮬레이터 처리량 숫자로 실제 보드 성능을 말하면 안 된다** — 실제 보드에서는 `dd`/`fio`로 다시 재고, 높게는 HS에서 35~40 MB/s, USB 3 Gen1에서 300~400 MB/s 정도가 일반적인 실측 범위다(경험적 범위, 이 노트에서 측정하지 않음).

- `ttyUSB`/`ttyACM`/`ttyGS` → H8(TTY). usb-storage → `sd` → J(스토리지).
- configfs gadget → G8(configfs 일반론). FunctionFS 데몬, udev 규칙 → L(유저스페이스 시스템).

## 14. Embedded 실무에서 다시 보기

### 14.1 센서 키트의 GNSS가 "가끔 `ttyUSB1`이 된다"

FTDI가 둘 이상이면 `ttyUSB` 번호는 열거 순서로 정해진다. 해결은 **포트 경로나 시리얼 번호로 udev 고정 이름**을 주는 것이다(udev 규칙 형식, 이 랩 BusyBox에는 udev가 없어 실행하지 않음):

```text
# /etc/udev/rules.d/70-sensorkit.rules
SUBSYSTEM=="tty", KERNELS=="1-4.1:1.0", SYMLINK+="gnss0"
SUBSYSTEM=="tty", ATTRS{idVendor}=="0403", ATTRS{serial}=="FT9XYZ12", SYMLINK+="imu-uart"
```

`KERNELS=="1-4.1:1.0"`는 §2.3의 경로 이름이다 — "보드의 내장 hub 4번 포트 뒤 1번 포트"는 항상 GNSS라는 하드웨어 사실을 이름으로 고정한다.

### 14.2 PC에 꽂으면 콘솔 + 네트워크가 뜨는 개발 보드

부팅 스크립트(systemd 서비스)에서 configfs gadget을 조립한다. §10.4와 같은 순서에 NCM을 더한 형태다(형식, 이 랩에서는 ACM + mass storage만 실행):

```sh
modprobe libcomposite
G=/sys/kernel/config/usb_gadget/kit
mkdir -p $G/strings/0x409 $G/configs/c.1/strings/0x409 $G/functions/acm.usb0 $G/functions/ncm.usb0
echo 0x1d6b > $G/idVendor; echo 0x0104 > $G/idProduct     # 제품에서는 회사 VID/PID
cat /sys/devices/soc0/serial_number > $G/strings/0x409/serialnumber 2>/dev/null
ln -s $G/functions/acm.usb0 $G/configs/c.1/; ln -s $G/functions/ncm.usb0 $G/configs/c.1/
ls /sys/class/udc > $G/UDC                                 # 첫 UDC에 바인딩
ip addr add 192.168.7.2/24 dev usb0; ip link set usb0 up
systemctl start serial-getty@ttyGS0
```

함정: `1d6b:0104`(Linux Foundation "Multifunction Composite Gadget")는 개발용이다. 양산 제품은 자기 VID/PID를 써야 하고, Windows 호환을 위해 `bDeviceClass 0xEF/02/01` + IAD(§10.4)를 지킨다. 시리얼 번호를 SoC 고유값으로 채워야 PC가 보드마다 같은 COM 포트를 기억한다(§10.6).

### 14.3 USB 카메라가 두 대째부터 안 열린다

UVC 카메라는 isochronous endpoint로 대역폭을 **예약**한다. 같은 버스(같은 root hub, 혹은 같은 USB 2 hub의 TT)에 두 대를 높은 해상도로 열면 예약이 실패해 `VIDIOC_STREAMON`이 `-ENOSPC`로 실패하고 dmesg에 대역폭 부족이 찍힌다. 해결: 압축 포맷(MJPEG)으로 바꿔 작은 alternate setting을 쓰게 하거나, 카메라를 서로 다른 컨트롤러/root 포트에 나눠 꽂는다. 이 문제는 debugfs `usb/devices`의 `I:` 줄(현재 alternate setting)과 `E:` 줄(`MxPS`)로 확인한다.

### 14.4 현장 장비에서 USB 장치가 "가끔 끊긴다"

dmesg에 `usb 1-1: USB disconnect` 직후 같은 장치가 다시 붙는 패턴이 반복되면: ① 전원 — hub 전력 예산 초과나 VBUS 강하(`bMaxPower` 합계 확인, 셀프 파워 hub), ② autosuspend — `power/control`이 `auto`인 장치가 깨어날 때 실패(`echo on > /sys/bus/usb/devices/1-1/power/control`로 시험), ③ EMI·케이블 — `-EPROTO`/`-EILSEQ`가 completion에 찍힌다(§6.3). 드라이버 쪽은 §5.7처럼 disconnect가 언제 와도 안전해야 하고, 유저 공간 데몬은 장치 노드가 사라졌다 다시 생기는 것을 udev 이벤트로 처리해야 한다(G9).

| 실수 | 증상 | 원인 | 고치는 법 |

## 16. 면접에서 이렇게 말한다

**Q.** Why do Linux USB drivers bind to interfaces rather than devices?

**A.** USB 장치 하나가 여러 기능(interface)을 가질 수 있기 때문이다. 웹캠의 영상과 마이크는 서로 다른 드라이버가 맡아야 한다. 그래서 usbcore는 interface마다 `struct device`를 만들고 `usb_driver`는 `probe(intf, id)`로 interface에 붙는다. sysfs에서도 `1-1`(장치)과 `1-1:1.0`(interface)이 따로 있고, `driver` 링크는 interface에 있다.

> Because a USB device is a container of functions. Each interface descriptor is one function with its own class, subclass and protocol — a webcam exposes video interfaces for uvcvideo and audio interfaces for snd-usb-audio. usbcore creates a struct usb_interface, which is a struct device, per interface in the active configuration, and usb_driver's probe gets that interface. You reach the parent with interface_to_usbdev. In sysfs that's bus-port.port:config.interface, like 1-4.1:1.0, and the driver symlink lives on the interface node.

**꼬리 질문**: "그럼 interface 두 개를 한 드라이버가 써야 하면?" → 하나에 probe되고 `usb_driver_claim_interface()`로 다른 interface도 claim한다(cdc_acm이 제어+데이터 interface를 이렇게 잡는다).

**Q.** Walk me through what happens when a USB device is plugged in.

**A.** hub가 포트 변화를 알리고, hub_wq가 포트를 리셋해 속도를 정하고, 주소 0으로 device descriptor를 읽어 ep0 크기를 알고, 주소를 주고, device·configuration·string 디스크립터를 읽는다. `usb_device`를 등록하면 generic 드라이버가 configuration을 고르고 SET_CONFIGURATION, 그다음 interface마다 device_add → uevent의 modalias로 모듈이 로드되고 probe가 불린다.

> The hub reports a port status change — for the root hub that's the host controller interrupt. hub_wq debounces, resets the port, which fixes the speed, reads the first bytes of the device descriptor at address 0 to learn ep0's max packet size, assigns an address — on xHCI the controller does that with an Address Device command — then reads the full device, configuration and string descriptors. usb_new_device registers the usb_device; the generic usb device driver picks a configuration and sends SET_CONFIGURATION; each interface becomes a device, the uevent carries a modalias like usb:v0627p0001…ic03isc01ip01, udev or modprobe loads the matching module, and usb_probe_interface calls the driver's probe.

**Q.** What is a URB and what are the rules in its completion handler?

**A.** URB는 endpoint 하나에 대한 비동기 전송 요청이다. alloc → fill → submit 하면 소유권이 HCD로 넘어가고, 끝나면 completion이 불린다. completion은 원자 문맥이다 — 내가 xHCI에서 재 보니 softirq(BH)였고 HCD에 따라 hardirq일 수도 있다. 그래서 잠들면 안 되고 재제출은 GFP_ATOMIC, status가 -ENOENT/-ECONNRESET/-ESHUTDOWN이면 재제출하지 않는다.

> A URB is an asynchronous request block for one endpoint: you allocate it, fill it with the pipe, a DMA-able buffer and a completion callback, and submit it; from then until the callback the HCD owns it. The callback runs in atomic context — I measured in_serving_softirq true on xHCI because xHCI sets HCD_BH and usbcore defers giveback to a BH workqueue, but you must assume it could be hard IRQ. So no sleeping, GFP_ATOMIC for resubmission, spinlocks only, hand heavy work to a workqueue. Check urb->status: zero means process actual_length; -ENOENT, -ECONNRESET or -ESHUTDOWN mean it was killed or the device is gone, so don't resubmit; -EPIPE is a stall that needs usb_clear_halt from process context.

**Q.** How do you make a USB driver safe against surprise removal?

**A.** disconnect는 언제든 온다. 순서는 (1) 새 제출 경로 막기(플래그, mutex), (2) `usb_kill_urb`/`usb_kill_anchored_urbs`로 남은 URB와 completion이 끝나길 기다리기, (3) 그다음 해제. 열린 파일이 있으면 kref로 객체 수명을 늘리고 이후 호출은 -ENODEV. QEMU에서 device_del로 실제 뽑아 보니 URB가 -ESHUTDOWN으로 먼저 돌아오고 그다음 disconnect가 불렸다.

> Disconnect can come at any time, including while userspace holds the device open. In disconnect I first stop every submission path — set a disconnected flag under the I/O mutex so read, write and workqueues bail out — then usb_kill_urb or usb_kill_anchored_urbs, which waits for any running completion, and only then free URBs and buffers. If file handles can outlive the interface, the state is refcounted with a kref and released on the last close; later calls return -ENODEV. I tested it with a QEMU monitor device_del: the interrupt URB completed with -ESHUTDOWN, then disconnect ran and cleaned up without warnings. Also, usbcore itself flushes the interface's endpoints before calling disconnect unless soft_unbind is set, but that doesn't cover your own workqueues or other endpoints.

**Q.** Explain the Linux USB gadget stack and how you would expose a serial console and Ethernet over USB.

**A.** UDC 드라이버(DWC3, ChipIdea)가 HW, libcomposite가 ep0와 디스크립터 조립, function 드라이버(acm, ncm, mass_storage, ffs)가 기능이다. configfs에서 gadget 디렉터리를 만들고 VID/PID·문자열, configuration, function을 만들어 링크하고 마지막에 UDC 이름을 쓴다. 보드 쪽은 ttyGS0에 getty, usb0에 IP. 나는 QEMU에서 dummy_hcd로 ACM + mass storage를 만들어 같은 커널이 ttyACM0와 sdb로 인식하는 것까지 시험했다.

> Three layers: the UDC driver for the device controller — dwc3, chipidea, dwc2 — the composite framework in libcomposite that answers standard ep0 requests and assembles descriptors, and function drivers like acm, ncm, mass_storage, or FunctionFS for userspace functions. With configfs I mkdir a gadget under /sys/kernel/config/usb_gadget, set idVendor, idProduct and the strings including a per-board serial number, create a configuration, create acm.usb0 and ncm.usb0, symlink them into the configuration, and finally write the UDC name to UDC — that's the cable-plug moment. On the board, a getty on ttyGS0 and an address on usb0. I verified the whole flow in QEMU using dummy_hcd, which loops a virtual UDC back into a virtual host controller in the same kernel: the host side bound cdc_acm and usb-storage, and ttyACM0 to ttyGS0 loopback worked both ways.

**꼬리 질문**: "Windows에서 composite ACM이 안 잡히면?" → 장치 class를 0xEF/02/01(IAD)로, 그리고 고유 시리얼 번호.

**Q.** When would you write a userspace USB driver with libusb instead of a kernel driver?

**A.** 커널의 다른 서브시스템(input, net, tty, block)에 장치를 노출할 필요가 없고, 지연 요구가 느슨하고, 크래시 격리와 배포 편의가 중요할 때 — 펌웨어 업데이트 툴, 시험 지그, 계측기. libusb는 usbfs ioctl을 감싼 것이고, 커널 드라이버가 잡은 interface는 detach 후 claim해야 한다.

> When the device doesn't need to appear as a standard kernel interface — no input device, netdev, tty or block device — and latency needs are modest: firmware updaters, DFU tools, test fixtures, lab instruments. It's easier to ship and a bug can't crash the kernel. libusb on Linux is a wrapper over usbfs: open /dev/bus/usb/BBB/DDD, USBDEVFS_CONTROL, claim the interface, USBDEVFS_BULK or async URBs with USBDEVFS_SUBMITURB. If a kernel driver already owns the interface, claim fails with EBUSY and you detach it first — I did exactly that against a keyboard and then reattached usbhid. For streaming, high-rate or shared devices, a kernel driver is the right answer.

**Q.** How do you debug a USB device that enumerates but doesn't work?

**A.** 1) debugfs `usb/devices`나 `lsusb -t`로 드라이버가 interface에 붙었는지, 2) `lsusb -v`/sysfs `descriptors`로 class·endpoint가 기대대로인지, 3) dmesg와 dynamic debug, 4) usbmon(또는 Wireshark)으로 URB 단위 트래픽 — STALL, 짧은 패킷, 타임아웃, 5) 필요하면 HW 분석기. 이 랩은 usbmon이 꺼져 있어 xHCI tracepoint로 BOT의 CBW/데이터/CSW를 봤다.

> First, is a driver bound to the right interface — /sys/kernel/debug/usb/devices or lsusb -t shows Driver= per interface. Second, do the descriptors say what I think — class, alternate settings, endpoint types and max packet sizes, via lsusb -v or the sysfs descriptors file. Third, dmesg with dynamic debug on the class driver and the HCD. Fourth, usbmon with Wireshark to see every URB submit and completion — stalls, short packets, -EPROTO, timeouts. On a kernel without usbmon, the xhci-hcd tracepoints give enqueue and giveback per URB; I used them to see the CBW, data and CSW of a mass-storage read. Last, a hardware analyzer for signal integrity or link power management issues.

**Q.** What's the difference between dr_mode host, peripheral and otg, and what is a role switch?

**A.** 임베디드 SoC USB 컨트롤러는 대부분 dual-role이다. DT `dr_mode`로 host 전용, peripheral(gadget) 전용, otg(둘 다)를 정한다. otg/dual-role이면 Type-C 컨트롤러나 ID 핀이 `usb_role_switch`로 역할을 바꾸고, sysfs `/sys/class/usb_role/*/role`에 보인다.

> Most SoC controllers — DWC3, ChipIdea, DWC2 — are dual-role. The device tree property dr_mode fixes the role: host instantiates the xHCI or EHCI side, peripheral registers a UDC for gadgets, otg allows both. In practice "OTG" means dual-role; HNP is rarely used. With usb-role-switch in DT, a Type-C port controller or a GPIO ID pin driver calls usb_role_switch_set_role when the cable or data role changes, and the current role is visible under /sys/class/usb_role. A typical dev board keeps its debug Type-C port in peripheral mode for the ACM console and NCM networking.

## 17. 직접 해보기

1. (개념) `1-4.1:1.0`과 `2-0:1.0`의 각 숫자가 무엇인지 말하라. 왜 `devnum`이 아니라 이 경로 이름으로 udev 규칙을 쓰는가? 정답/힌트: 버스 1 → 포트 4(hub) → 포트 1, configuration 1, interface 0 / 버스 2의 root hub interface. `devnum`은 열거 순서로 바뀐다.
2. (계산) High-Speed interrupt endpoint의 `bInterval=4`, Full-Speed의 `bInterval=4`는 각각 몇 ms 주기인가? 정답/힌트: HS 2^(4-1) × 125 µs = 1 ms, FS 4 ms.
3. (코드) `h12_drv`를 고쳐 report를 64개짜리 링버퍼에 넣고, misc device(G7)의 `read()`가 `wait_event_interruptible`로 기다렸다가 돌려주게 하라. completion에서는 spinlock + `wake_up`만 쓴다. 정답/힌트: disconnect에서 `disconnected=true` 후 `wake_up`, `read()`는 `-ENODEV`.
4. (관찰) §5.7을 다시 하되 `device_del` 직전에 게스트에서 `cat /sys/bus/usb/devices/1-1/urbnum`을 두 번(키 입력 전후) 읽어 보라. report 하나당 urbnum이 얼마씩 느는가? 정답/힌트: 재제출 1회 = 1 증가.
5. (gadget) §10.4의 gadget에 `ncm.usb0`을 추가하고(`usb_f_ncm.ko`, `u_ether.ko`, host 쪽 `usbnet.ko`·`cdc_ncm.ko`는 `/var/lab/build/linux`에 있다), 같은 게스트에서 gadget 쪽 `usb0`과 host 쪽 새 인터페이스에 서로 다른 IP를 주고 `ping`이 되는지 보라. 정답/힌트: 같은 커널 안의 두 인터페이스라 라우팅이 로컬로 빠질 수 있으니 네트워크 네임스페이스(`unshare -n`)로 한쪽을 분리해야 실제 USB를 탄다.
6. (관찰) 디버그 커널에서 §8.2의 tracepoint를 켠 채 `h12_bw`로 64 KiB 읽기 한 번을 하고, CBW/데이터/CSW의 길이와 sg 개수를 확인하라. 정답/힌트: 데이터 URB `length 0/65536`, 사이의 enqueue→giveback 간격이 요청 시간 대부분.
7. (설계) 센서 키트 양산 이미지에서 USB ACM 콘솔을 남겨야 한다면 보안상 무엇을 해야 하나? 정답/힌트: getty 대신 인증 필요한 로그인, 혹은 공장 모드에서만 gadget 조립, 시리얼 번호·VID/PID 정책.

## 19. 요약 & 체크리스트

USB는 호스트가 모든 전송을 시작하는 나무 모양 버스이고, 장치는 디스크립터(device → configuration → interface → endpoint)로 자신을 소개한다. Linux host 쪽은 HCD(xHCI) → usbcore(+hub 드라이버의 열거) → interface 드라이버(`usb_driver`) 3층이며, 드라이버는 **interface**에 붙고 sysfs 이름은 포트 경로(`1-4.1:1.0`)다. 데이터는 URB로 비동기 제출하고, completion은 원자 문맥(이 랩 xHCI에서 실측 softirq; HCD는 hardirq에서 giveback)이라 `GFP_ATOMIC`과 spinlock만 쓴다. 핫 언플러그에서 URB는 `-ESHUTDOWN`으로 돌아오고, `disconnect`는 제출 경로 차단 → kill → 해제 순서를 지킨다. gadget 쪽은 UDC → composite → function이고 configfs로 조립하며, `dummy_hcd`로 같은 커널 안에서 ACM 루프백과 mass storage를 end-to-end로 시험할 수 있다. 에뮬레이터 처리량은 순서만 믿고 절대값은 믿지 않는다.

- [ ] 디스크립터 계층과 class/subclass/protocol로 장치 정체를 읽어 낼 수 있다
- [ ] sysfs 이름 `버스-포트.포트:config.interface`를 해석하고 udev 규칙에 쓸 수 있다
- [ ] 열거 과정을 리셋부터 probe까지 단계별로 설명할 수 있다
- [ ] `usb_driver`의 id_table 매크로를 골라 쓰고, `new_id`/`unbind`로 동적 바인딩할 수 있다
- [ ] interrupt URB를 alloc/fill/submit/재제출하는 드라이버를 코드로 짤 수 있다
- [ ] completion이 원자 문맥인 이유와 status별 처리를 설명할 수 있다
- [ ] disconnect에서 안전한 정리 순서를 말하고 hot-unplug로 검증할 수 있다
- [ ] `usb_control_msg`/`usb_bulk_msg`를 언제 쓰고 언제 쓰면 안 되는지 말할 수 있다
- [ ] usbmon(또는 xHCI tracepoint)으로 BOT의 CBW/데이터/CSW를 찾아낼 수 있다
- [ ] usbfs ioctl(libusb 내부)로 interface를 detach·claim하고 전송할 수 있다
- [ ] configfs로 ACM + mass storage(+NCM) gadget을 조립하고 UDC에 바인딩할 수 있다
- [ ] dr_mode와 role switch, 그리고 제품에서 USB 콘솔·네트워크·업데이트를 어떻게 쓰는지 설명할 수 있다
