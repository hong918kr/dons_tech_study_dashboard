# H2. regmap — 레지스터 접근 추상화, 캐시, regmap_field, 왜 쓰나 (센서·PMIC 드라이버의 표준 레지스터 계층)

> **이 노트를 다 읽으면**: `struct regmap_config`를 칩 데이터시트의 레지스터 표에서 바로 써 내려갈 수 있다(readable/writeable/volatile/precious 분류, `max_register`, `cache_type`) · `regmap_read`/`update_bits`/`bulk_read`/`noinc_read`/`read_poll_timeout`/`regmap_field`로 드라이버를 짜고, 각 호출이 버스에 실제로 몇 번 나가는지 설명할 수 있다 · `regcache_cache_only` + `regcache_mark_dirty` + `regcache_sync`로 suspend/resume을 구현하고 ftrace로 증명할 수 있다 · `/sys/kernel/debug/regmap/<dev>/`로 레지스터를 들여다보고, volatile·precious를 잘못 표시했을 때 생기는 버그를 증상으로 알아볼 수 있다
> **왜 필요한가**: I2C/SPI 센서, PMIC, 오디오 코덱, 클럭 칩 드라이버는 거의 전부 regmap 위에 쓴다. 면접에서는 "regmap을 왜 쓰죠?", "volatile register가 뭐죠?", "resume 때 레지스터를 어떻게 복원하죠?"로 나오고, 입사 후에는 기존 드라이버를 읽는 첫날부터 만난다
> **Don 기준 난이도**: 레지스터 맵·RMW·shadow register·clear-on-read 상태 레지스터·전원 차단 후 재설정은 PMIC/RF 칩 bring-up에서 매일 하던 일이다 / 새로 배울 것은 그걸 **커널이 표준 라이브러리로 제공한다**는 것과 그 라이브러리의 규칙(캐시가 언제 버스를 건너뛰는지, 어떤 레지스터를 어떻게 표시해야 하는지)
> **선행 노트**: E5(`GENMASK`/`FIELD_PREP`/`FIELD_GET`, 엔디안 헬퍼), G3(probe 생명주기, `devm_*`, `dev_err_probe`), G8(debugfs), H1(MMIO, `readl`/`writel`) — H5(I2C 서브시스템), H7(SPI), H6(인터럽트 컨트롤러, regmap-irq), N(전원 관리)으로 이어진다

## 0. 큰 그림 — 이게 왜 필요한가

Don이 PMIC나 RF 칩을 bring-up할 때 가장 먼저 만든 코드는 아마 이런 모양이었을 것이다.

```c
/* 버스가 무엇이든 위에서는 똑같이 보이게 하는 얇은 계층 */
int  pmic_reg_read(uint8_t reg, uint8_t *val);          /* 내부: SPMI ext read */
int  pmic_reg_write(uint8_t reg, uint8_t val);          /* 내부: SPMI ext write */
int  pmic_reg_update(uint8_t reg, uint8_t mask, uint8_t val);  /* read → 수정 → write */
static uint8_t pmic_shadow[256];                        /* 마지막으로 쓴 값 (읽기 절약) */
```

그리고 시간이 지나면 그 계층에 기능이 붙는다. "이 레지스터는 쓰기 금지", "상태 레지스터는 shadow를 쓰면 안 됨", "전원이 꺼졌다 켜지면 shadow 값을 다시 써 넣기", "디버그용 레지스터 덤프 명령", "버스 트랜잭션 로그". 회사마다, 칩마다, 사람마다 이걸 다시 만든다.

Linux는 이 계층을 **한 번만** 만들어 두었다. 그게 **regmap**이다. 드라이버는 "이 칩의 레지스터는 8비트 주소에 8비트 값, 0x3e까지 있고, 이것들은 읽기 전용, 이것들은 읽을 때마다 값이 바뀜(volatile), 이건 읽으면 지워짐(precious)"이라는 **설명서(`struct regmap_config`)**만 넘긴다. 그러면 regmap이 버스 포맷, 락, 범위 검사, 캐시, RMW, 디버그 덤프, 트레이스, 전원 복원을 대신 해 준다.

### 0.1 QEMU에는 I2C 센서가 없다 — 그래서 직접 만든다

QEMU `virt` 보드에는 I2C 컨트롤러가 없고, 랩 커널은 `CONFIG_I2C_STUB`(커널이 제공하는 가짜 I2C 칩)도 꺼져 있다. 그리고 i2c-stub은 "읽으면 지워지는" 레지스터 같은 **칩의 행동**을 흉내 내지 못한다. regmap의 volatile·precious 규칙은 바로 그 행동 때문에 존재하므로, 이 노트에서는 **가짜 I2C 어댑터 모듈 `h2_fakebus`**를 직접 만들어 그 위에 가짜 IMU 하나(주소 0x6a)를 산다. 이 IMU는 진짜 칩처럼:

- `WHO_AM_I`는 항상 0x6c (읽기 전용)
- `INT_STATUS`는 **읽으면 0으로 지워진다** (clear-on-read)
- 마지막 데이터 바이트(`OUTZ_H`)를 읽으면 `STATUS.XLDA`가 지워진다
- `FIFO_DATA`는 주소가 증가하지 않는 포트이고, 읽을 때마다 FIFO에서 1바이트가 빠진다
- `CTRL3.SW_RESET`을 쓰면 잠시 후 스스로 0이 되며 모든 레지스터가 POR 값으로 돌아간다
- 전원을 끄면 NACK, 다시 켜면 **레지스터 내용을 잃고** POR 값으로 깨어난다

그리고 어댑터는 버스 트랜잭션 수·바이트 수를 세고(`stats`), 원하면 메시지마다 로그를 찍는다(`log=1`) — 로직 분석기 대용이다. 그래서 "캐시가 버스를 몇 번 아꼈나"를 **숫자로** 볼 수 있다.

## 1. 왜 regmap인가

### 1.1 직관 — "레지스터를 가진 칩"이라는 공통점

센서, PMIC, 코덱, 클럭 칩, 디스플레이 브리지. 버스는 I2C, SPI, SPMI, MMIO로 제각각이지만 드라이버 입장에서 하는 일은 같다: **주소 N에 값을 쓰고, 주소 M에서 값을 읽고, 일부 비트만 바꾸고, 한 번에 여러 바이트를 읽는다.** 버스 차이는 "주소와 값을 몇 바이트로, 어떤 순서로, 어떤 프레임에 실어 보내느냐"뿐이다.

regmap 이전에는 드라이버마다 `foo_read_reg()`/`foo_write_reg()`를 직접 짰다. 그러다 보니 같은 칩이 I2C 버전과 SPI 버전으로 나오면 드라이버 두 벌이 생겼고, 캐시·락·디버그 덤프는 드라이버마다 품질이 달랐다. regmap은 원래 ASoC(오디오 코덱) 쪽 레지스터 캐시 코드를 일반화해서 Mark Brown이 3.1 무렵 `drivers/base/regmap/`로 만든 것이다.

### 1.2 regmap이 주는 것 — 기능 표

| 기능 | 드라이버가 하는 일 | regmap이 대신 하는 일 |
|---|---|---|
| 버스 독립 API | `devm_regmap_init_i2c/spi/mmio/spmi_ext(...)` 한 줄 | 주소·값 직렬화, 버스 호출 |
| 범위 검사 | `max_register`, `rd_table`/`wr_table` | 범위 밖·권한 없는 접근을 `-EIO`로 거절 |
| 캐시 | `cache_type`, `reg_defaults`, `volatile_table` | 읽기는 캐시에서, RMW는 캐시 값으로, 같은 값이면 쓰기 생략 |
| 락 | (보통 아무것도 안 함) | 접근마다 mutex(슬립 가능한 버스) 또는 spinlock(MMIO) |
| RMW | `regmap_update_bits`/`set_bits`/`clear_bits` | 원자적(락 안에서) read-modify-write |
| 비트필드 | `REG_FIELD` + `devm_regmap_field_alloc` | 마스크·시프트 계산 |
| 대량 전송 | `regmap_bulk_read`/`raw_read`/`noinc_read` | 주소 자동 증가 burst 또는 FIFO 포트 반복 읽기를 한 트랜잭션으로 |
| 폴링 | `regmap_read_poll_timeout` | sleep·timeout이 있는 폴링 루프 |
| 초기화 시퀀스 | `regmap_multi_reg_write`, `regmap_register_patch` | 순서대로 쓰기(지연 포함 가능), patch는 sync 때마다 재적용 |
| 전원 복원 | `regcache_cache_only`, `regcache_mark_dirty`, `regcache_sync` | 기본값과 다른 레지스터만 다시 쓰기 |
| 페이징 | `ranges` (`struct regmap_range_cfg`) | 페이지 선택 레지스터를 자동으로 바꿔 가며 접근 |
| 인터럽트 | `devm_regmap_add_irq_chip` | 상태 레지스터를 읽고 하위 IRQ를 디스패치 (H6) |
| 디버그 | 아무것도 안 함 | `/sys/kernel/debug/regmap/<dev>/` 덤프, `regmap:*` tracepoint |

## 2. 실습 준비 — 가짜 IMU와 가짜 I2C 어댑터

### 2.1 레지스터 맵 — 데이터시트의 표를 먼저 그린다

regmap 드라이버를 쓰는 첫 단계는 코드가 아니라 **표**다. 데이터시트의 레지스터 표에서 레지스터마다 네 가지 질문에 답한다.

- **readable**: 읽을 수 있나? (쓰기 전용 레지스터, 구멍(reserved)은 아니다)
- **writeable**: 쓸 수 있나?
- **volatile**: 칩이 **스스로** 값을 바꾸나? (상태, 데이터, 카운터, 자동 해제 비트) → 캐시하면 안 된다
- **precious**: **읽는 것 자체가 부작용**이 있나? (clear-on-read, FIFO pop) → 드라이버가 아닌 누구도(debugfs 덤프 포함) 함부로 읽으면 안 된다

### 2.2 예제 2 — 레지스터 헤더와 가짜 어댑터 `h2_fakebus`

무엇을 확인하나: 칩 쪽 레지스터 맵(헤더)과, 그 행동을 흉내 내는 I2C 어댑터. 어댑터는 `struct i2c_algorithm`의 `.xfer` 하나로 진짜 컨트롤러 행세를 한다(H5에서 자세히).

```c
/* h2_imu_regs.h — 가짜 IMU 레지스터 맵 (LSM6 계열을 단순화) */
#define H2_ADDR		0x6a
#define H2_INT_CTRL	0x0d	/* RW: bit0 DRDY 인터럽트, bit1 FIFO 워터마크 인터럽트 */
#define H2_WHO_AM_I	0x0f	/* RO: 0x6c */
#define H2_WHOAMI_VAL	0x6c
#define H2_CTRL1	0x10	/* RW: ODR[7:4] FS[3:2] */
#define H2_CTRL2	0x11	/* RW: 아날로그 튜닝(패치 대상) */
#define H2_CTRL3	0x12	/* RW: bit0 SW_RESET(자동 해제) bit2 IF_INC */
#define H2_CTRL3_SW_RESET 0x01
#define H2_CTRL3_IF_INC	0x04
#define H2_INT_STATUS	0x1a	/* RO, clear-on-read: bit0 DRDY bit1 FIFO_WTM */
#define H2_STATUS	0x1e	/* RO: bit0 XLDA (새 데이터 있음) */
#define H2_ST_XLDA	0x01
#define H2_OUTX_L	0x22	/* RO: X/Y/Z 16비트 LE 6바이트, OUTZ_H 읽으면 XLDA 해제 */
#define H2_OUTZ_H	0x27
#define H2_FIFO_STATUS	0x3a	/* RO: FIFO에 쌓인 바이트 수 */
#define H2_FIFO_DATA	0x3e	/* RO, no-increment: 읽을 때마다 FIFO에서 1바이트 pop */
#define H2_MAX_REG	0x3e

void h2_fakebus_set_power(bool on);	/* h2_fakebus.ko가 export: 전원 레일 흉내 */
```

어댑터 앞부분 — 칩 내부 상태와 **읽기의 부작용**:

```c
// h2_fakebus.c — 가짜 I2C 어댑터 + 그 위에 사는 가짜 IMU(주소 0x6a)의 레지스터 파일
#include <linux/module.h>
#include <linux/i2c.h>
#include <linux/mutex.h>
#include "h2_imu_regs.h"

static struct i2c_adapter h2_adap;
static DEFINE_MUTEX(h2_lock);
static u8 regs[256];		/* 칩 내부 레지스터 파일 */
static u8 fifo[192];
static int fifo_n, sample, powered = 1, ctrl3_reads;
static unsigned long n_xfer, n_msg, n_rbytes, n_wbytes;
static bool log_xfer;
module_param_named(log, log_xfer, bool, 0644);

static void h2_por(void)	/* power-on reset: 데이터시트의 기본값 */
{
	memset(regs, 0, sizeof(regs));
	regs[H2_WHO_AM_I] = H2_WHOAMI_VAL;
	regs[H2_CTRL3] = H2_CTRL3_IF_INC;
	fifo_n = 0;
}

static u8 h2_rd(u8 r)		/* 읽기의 부작용까지 흉내 낸다 */
{
	u8 v = regs[r];

	switch (r) {
	case H2_INT_STATUS: regs[r] = 0; break;		/* clear-on-read */
	case H2_OUTZ_H: regs[H2_STATUS] &= ~H2_ST_XLDA; break;
	case H2_FIFO_DATA:
		if (!fifo_n) return 0;
		v = fifo[0]; memmove(fifo, fifo + 1, --fifo_n);
		regs[H2_FIFO_STATUS] = fifo_n; break;
	case H2_CTRL3:					/* SW_RESET은 3번째 읽기에 끝난다 */
		if ((v & H2_CTRL3_SW_RESET) && ++ctrl3_reads >= 3) {
			h2_por(); ctrl3_reads = 0; v = regs[r];
		}
		break;
	}
	return v;
}

static void h2_wr(u8 r, u8 v)
{
	if (r == H2_INT_CTRL || r == H2_CTRL1 || r == H2_CTRL2 || r == H2_CTRL3)
		regs[r] = v;		/* 나머지(읽기 전용)는 칩이 무시한다 */
}
```

`.xfer` — I2C 메시지 배열을 받아 "쓰기 메시지의 첫 바이트 = 레지스터 포인터, 나머지 = 데이터(주소 자동 증가)", "읽기 메시지 = 포인터부터 연속 읽기(단 `FIFO_DATA`는 고정)"로 해석한다. 진짜 IMU의 I2C 프로토콜과 같다.

```c
static int h2_xfer(struct i2c_adapter *a, struct i2c_msg *msgs, int num)
{
	int i, j;
	u8 ptr = 0;

	guard(mutex)(&h2_lock);
	n_xfer++;
	for (i = 0; i < num; i++) {
		struct i2c_msg *m = &msgs[i];

		n_msg++;
		if (m->addr != H2_ADDR || !powered)
			return -ENXIO;			/* NACK */
		if (m->flags & I2C_M_RD) {
			for (j = 0; j < m->len; j++) {
				m->buf[j] = h2_rd(ptr);
				if (ptr != H2_FIFO_DATA) ptr++;
			}
			n_rbytes += m->len;
		} else {
			ptr = m->buf[0];
			for (j = 1; j < m->len; j++)
				h2_wr(ptr++, m->buf[j]);
			n_wbytes += m->len;
		}
		if (log_xfer)		/* 로직 분석기 흉내: 메시지 하나 = 한 줄 */
			pr_info("h2_fakebus: %s %*ph\n",
				m->flags & I2C_M_RD ? "R" : "W", min_t(int, m->len, 8), m->buf);
	}
	return num;
}
```

뒷부분 — 어댑터 등록, 전원 레일 흉내(`h2_fakebus_set_power`, 드라이버의 suspend/resume이 부른다), 그리고 실험 손잡이 두 개: `stats`(읽으면 카운터, 쓰면 리셋)와 `tick`(쓰면 샘플 N개 생성).

```c
static u32 h2_func(struct i2c_adapter *a)
{
	return I2C_FUNC_I2C | I2C_FUNC_SMBUS_EMUL;	/* 진짜 I2C 컨트롤러처럼 */
}

static const struct i2c_algorithm h2_algo = {
	.xfer = h2_xfer,
	.functionality = h2_func,
};

/* 전원 레일 흉내: 끄면 NACK, 켜면 POR 값으로 돌아온다 (레지스터 내용 소실) */
void h2_fakebus_set_power(bool on)
{
	guard(mutex)(&h2_lock);
	powered = on;
	pr_info("h2_fakebus: power %s\n", on ? "ON (POR defaults)" : "OFF");
	if (on)
		h2_por();
}
EXPORT_SYMBOL_GPL(h2_fakebus_set_power);

static int stats_get(char *buf, const struct kernel_param *kp)
{
	return sysfs_emit(buf, "xfers=%lu msgs=%lu rbytes=%lu wbytes=%lu\n",
			  n_xfer, n_msg, n_rbytes, n_wbytes);
}

static int stats_set(const char *val, const struct kernel_param *kp)
{
	n_xfer = n_msg = n_rbytes = n_wbytes = 0;	/* 아무 값이나 쓰면 리셋 */
	return 0;
}

static int tick_set(const char *val, const struct kernel_param *kp)
{
	int n, i, k;

	if (kstrtoint(val, 0, &n))
		return -EINVAL;
	guard(mutex)(&h2_lock);
	for (i = 0; i < n; i++) {	/* 샘플 n개 생성: OUT 갱신, FIFO push, 상태 비트 */
		sample++;
		for (k = 0; k < 6; k++) {
			regs[H2_OUTX_L + k] = (sample * (k + 1)) & 0xff;
			if (fifo_n < (int)sizeof(fifo))
				fifo[fifo_n++] = regs[H2_OUTX_L + k];
		}
		regs[H2_STATUS] |= H2_ST_XLDA;
		regs[H2_INT_STATUS] |= 0x01;
		if (fifo_n >= 48)
			regs[H2_INT_STATUS] |= 0x02;
	}
	regs[H2_FIFO_STATUS] = fifo_n;
	return 0;
}
```

```c
static const struct kernel_param_ops stats_ops = { .get = stats_get, .set = stats_set };
static const struct kernel_param_ops tick_ops = { .set = tick_set };
module_param_cb(stats, &stats_ops, NULL, 0644);
module_param_cb(tick, &tick_ops, NULL, 0200);

static int __init h2_init(void)
{
	h2_por();
	h2_adap.owner = THIS_MODULE;
	h2_adap.algo = &h2_algo;
	strscpy(h2_adap.name, "h2-fakebus", sizeof(h2_adap.name));
	return i2c_add_adapter(&h2_adap);	/* 번호는 동적: virt에는 다른 I2C가 없어 i2c-0 */
}

static void __exit h2_exit(void)
{
	i2c_del_adapter(&h2_adap);
}
module_init(h2_init);
module_exit(h2_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H2: fake I2C adapter emulating an IMU register map");
```

함정: 이 어댑터는 "칩이 하나만 붙은 버스"다. 다른 주소로 오는 메시지는 NACK(`-ENXIO`)으로 답한다 — `i2cdetect`가 0x6a 하나만 찾게 된다.

## 3. `struct regmap_config` — 칩의 설명서

### 3.1 직관 — 데이터시트 레지스터 표를 C 구조체로

`regmap_config`는 "이 칩의 레지스터는 어떻게 생겼나"를 적는 구조체다. 함수 포인터 몇 개를 빼면 거의 **데이터**다. Don이 bring-up 문서 맨 앞에 적던 "주소 폭, 데이터 폭, 엔디안, 레지스터 범위, 접근 권한" 표와 똑같다.

### 3.2 필드 정리 (6.18 `include/linux/regmap.h` 기준, 자주 쓰는 것만)

| 필드 | 뜻 | 예 / 메모 |
|---|---|---|
| `name` | 같은 장치에 regmap이 여럿일 때 구분 이름 | debugfs 디렉터리가 `<dev>-<name>`이 된다 |
| `reg_bits` | 레지스터 **주소** 폭(비트) | I2C 센서 8, 큰 PMIC 16, MMIO 32 |
| `val_bits` | 레지스터 **값** 폭 | 8, 16, 32 |
| `reg_stride` | 유효 주소 간격 | MMIO 32비트 레지스터면 4 |
| `pad_bits` | 주소와 값 사이 패딩 | 일부 SPI 칩 |
| `max_register` | 가장 큰 유효 주소 | 범위 검사·debugfs·캐시 크기 기준 |
| `rd_table` / `wr_table` | 읽기·쓰기 가능한 주소 범위 표 | `struct regmap_access_table` (yes/no 범위) |
| `volatile_table` | 캐시하면 안 되는 주소 | 상태·데이터·자동 해제 비트 |
| `precious_table` | 드라이버만 읽어야 하는 주소 | clear-on-read, FIFO pop |
| `rd_noinc_table` / `wr_noinc_table` | 주소가 증가하지 않는 포트 | FIFO 데이터 레지스터 |
| `readable_reg` 등 콜백 | 표 대신 함수로 판단 | `switch (reg)` 한 덩어리. 콜백이 표보다 우선 |
| `reg_defaults` / `num_reg_defaults` | POR 기본값 | 캐시 초기값, sync 때 "기본값과 같으면 생략" 기준 |
| `cache_type` | `REGCACHE_NONE`/`RBTREE`/`FLAT`/`MAPLE` | §5 |
| `val_format_endian` / `reg_format_endian` | 바이트 순서 | `REGMAP_ENDIAN_BIG`/`LITTLE`/`NATIVE`/`DEFAULT` |
| `read_flag_mask` / `write_flag_mask` | 주소 바이트에 OR할 비트 | SPI 센서의 R/W 비트(읽기 0x80) |
| `use_single_read` / `use_single_write` | bulk를 한 레지스터씩 쪼갬 | auto-increment가 없는 칩 |
| `can_multi_write` | 여러 (reg, val) 쌍을 한 전송에 | 일부 SPI 코덱 |
| `disable_locking` | regmap 내부 락을 끔 | 드라이버가 이미 자기 락으로 감쌀 때만 |
| `fast_io` | spinlock 사용 | MMIO 백엔드는 자동으로 켜진다 |
| `ranges` / `num_ranges` | 페이지(뱅크) 레지스터 | 페이지 선택 레지스터 자동 조작 |
| `max_raw_read` / `max_raw_write` | 한 번에 보낼 최대 바이트 | 어댑터 quirk(`max_read_len`)와 맞춘다 |

표(`rd_table` 등)와 콜백(`readable_reg` 등)은 같은 일을 한다. 범위로 깔끔하게 끊어지면 표, 규칙이 복잡하면 콜백(`switch`)을 쓴다. 판단 순서는 regmap.c의 `regmap_readable()`/`regmap_volatile()`/`regmap_precious()`에 있다 — **콜백이 있으면 콜백, 없으면 표, 둘 다 없으면 기본값**. 기본값이 중요하다: volatile 기본값은 **캐시가 있으면 "아니다"(false), 캐시가 없으면 "그렇다"(true)**다. 즉 캐시를 켜는 순간 표시하지 않은 모든 레지스터가 캐시 대상이 된다(§7의 버그 1).

### 3.3 예제 4(a) — 드라이버의 `regmap_config` (`h2_imu.c` 1/4)

무엇을 확인하나: 그림 2의 표를 범위 표 다섯 개로 옮긴 것. `regmap_reg_range(min, max)`는 양 끝 포함 범위다. `bug_nv`/`no_precious`는 §7에서 버그를 일부러 넣는 스위치다.

```c
// h2_imu.c — regmap 기반 IMU 클라이언트 드라이버 (1/4: 접근 표)
#include <linux/module.h>
#include <linux/i2c.h>
#include <linux/regmap.h>
#include <linux/bitfield.h>
#include <linux/ktime.h>
#include "h2_imu_regs.h"

static int cache = REGCACHE_MAPLE;	/* 0 NONE, 1 RBTREE, 2 FLAT, 3 MAPLE */
module_param(cache, int, 0444);
static bool bug_nv;			/* 1 = 상태 레지스터를 volatile에서 빠뜨림 */
module_param(bug_nv, bool, 0444);
static bool no_precious;		/* 1 = clear-on-read 레지스터를 precious로 표시 안 함 */
module_param(no_precious, bool, 0444);

static const struct regmap_range h2_rd_ranges[] = {
	regmap_reg_range(H2_INT_CTRL, H2_INT_CTRL),
	regmap_reg_range(H2_WHO_AM_I, H2_CTRL3),
	regmap_reg_range(H2_INT_STATUS, H2_INT_STATUS),
	regmap_reg_range(H2_STATUS, H2_STATUS),
	regmap_reg_range(H2_OUTX_L, H2_OUTZ_H),
	regmap_reg_range(H2_FIFO_STATUS, H2_FIFO_STATUS),
	regmap_reg_range(H2_FIFO_DATA, H2_FIFO_DATA),
};
static const struct regmap_range h2_wr_ranges[] = {
	regmap_reg_range(H2_INT_CTRL, H2_INT_CTRL),
	regmap_reg_range(H2_CTRL1, H2_CTRL3),
};
static const struct regmap_range h2_vol_ranges[] = {
	regmap_reg_range(H2_CTRL3, H2_CTRL3),		/* SW_RESET이 스스로 꺼진다 */
	regmap_reg_range(H2_OUTX_L, H2_OUTZ_H),
	regmap_reg_range(H2_FIFO_STATUS, H2_FIFO_STATUS),
	regmap_reg_range(H2_FIFO_DATA, H2_FIFO_DATA),
	regmap_reg_range(H2_INT_STATUS, H2_INT_STATUS),	/* bug_nv면 여기부터 */
	regmap_reg_range(H2_STATUS, H2_STATUS),		/*   두 줄을 뺀다 */
};
static const struct regmap_range h2_prec_ranges[] = {
	regmap_reg_range(H2_INT_STATUS, H2_INT_STATUS),	/* 읽으면 지워진다 */
	regmap_reg_range(H2_FIFO_DATA, H2_FIFO_DATA),	/* 읽으면 pop */
};
static const struct regmap_range h2_noinc_ranges[] = {
	regmap_reg_range(H2_FIFO_DATA, H2_FIFO_DATA),
};
```

### 3.4 예제 4(b) — 표를 묶고, 기본값을 적고, config 완성 (`h2_imu.c` 2/4)

```c
static const struct regmap_access_table h2_rd = { h2_rd_ranges, ARRAY_SIZE(h2_rd_ranges) };
static const struct regmap_access_table h2_wr = { h2_wr_ranges, ARRAY_SIZE(h2_wr_ranges) };
static struct regmap_access_table h2_vol = { h2_vol_ranges, ARRAY_SIZE(h2_vol_ranges) };
static const struct regmap_access_table h2_prec = { h2_prec_ranges, ARRAY_SIZE(h2_prec_ranges) };
static const struct regmap_access_table h2_noinc = { h2_noinc_ranges, ARRAY_SIZE(h2_noinc_ranges) };

static const struct reg_default h2_defaults[] = {	/* POR 값 (쓰기 가능한 것만) */
	{ H2_INT_CTRL, 0x00 }, { H2_CTRL1, 0x00 }, { H2_CTRL2, 0x00 },
};

static struct regmap_config h2_regmap_cfg = {
	.reg_bits = 8,
	.val_bits = 8,
	.max_register = H2_MAX_REG,
	.rd_table = &h2_rd,
	.wr_table = &h2_wr,
	.volatile_table = &h2_vol,
	.precious_table = &h2_prec,
	.rd_noinc_table = &h2_noinc,
	.reg_defaults = h2_defaults,
	.num_reg_defaults = ARRAY_SIZE(h2_defaults),
};
```

- `regmap_access_table`의 두 필드는 `yes_ranges`/`n_yes_ranges`(그리고 생략한 `no_ranges`/`n_no_ranges`)다. "no"가 "yes"보다 우선한다.
- `h2_vol`과 `h2_regmap_cfg`가 `const`가 아닌 이유는 실험 스위치(모듈 인자)로 probe에서 고치기 때문이다. **실제 드라이버에서는 전부 `static const`**로 둔다(칩이 여러 개 붙어도 config는 공유되므로 probe에서 고치면 안 된다).
- `reg_defaults`에는 **쓰기 가능하고 캐시되는** 레지스터의 POR 값만 넣는다. 여기 없는 캐시 대상(`WHO_AM_I`)은 MAPLE/RBTREE에서는 "처음 읽을 때 칩에서 가져와 캐시", FLAT에서는 "0으로 초기화된 칸"이 된다 — §5.4의 함정.

### 3.5 버스 백엔드는 어떻게 고르나 — `regmap_get_i2c_bus()`

`devm_regmap_init_i2c(client, &cfg)` 한 줄 안에서 regmap-i2c는 **어댑터의 능력**을 보고 백엔드를 고른다. 6.18 `drivers/base/regmap/regmap-i2c.c`에서 확인한 순서:

```text
static const struct regmap_bus *regmap_get_i2c_bus(struct i2c_client *i2c,
					const struct regmap_config *config)
{
...
	if (i2c_check_functionality(i2c->adapter, I2C_FUNC_I2C))
		bus = &regmap_i2c;
	else if (config->val_bits == 8 && config->reg_bits == 8 &&
		 i2c_check_functionality(i2c->adapter,
					 I2C_FUNC_SMBUS_I2C_BLOCK))
		bus = &regmap_i2c_smbus_i2c_block;
...
	else if (config->val_bits == 8 && config->reg_bits == 8 &&
		 i2c_check_functionality(i2c->adapter,
					 I2C_FUNC_SMBUS_BYTE_DATA))
		bus = &regmap_smbus_byte;
```

(가운데 16비트 조합 분기는 `...`로 생략했다.) 우리 어댑터는 `I2C_FUNC_I2C`를 광고하므로 **raw I2C 백엔드 `regmap_i2c`**가 선택된다. 이 백엔드에서 읽기는 `i2c_transfer()`로 "쓰기 메시지(레지스터 주소) + 읽기 메시지(값)" 두 개를 repeated START로 붙여 보내고, 쓰기는 `i2c_master_send()`로 "주소 + 값" 메시지 하나를 보낸다. 같은 드라이버가 SMBus만 되는 컨트롤러에 붙으면 `regmap_smbus_byte`가 골라지고, 드라이버 코드는 한 줄도 안 바뀐다 — 대신 bulk read가 바이트 단위로 쪼개진다. 어댑터의 `quirks`(최대 읽기 길이)도 여기서 `max_raw_read`로 반영된다.

## 4. regmap API — 읽기·쓰기·RMW·폴링·초기화 시퀀스

### 4.1 API 한눈에

| 함수 | 하는 일 | 메모 |
|---|---|---|
| `regmap_read(map, reg, &val)` | 한 레지스터 읽기 | 캐시 히트면 버스 안 감 |
| `regmap_write(map, reg, val)` | 한 레지스터 쓰기 | 캐시도 갱신 |
| `regmap_update_bits(map, reg, mask, val)` | RMW | 결과가 같으면 **쓰기 생략** |
| `regmap_write_bits(...)` | RMW, 항상 쓰기 | write-1-to-clear 비트 등 |
| `regmap_set_bits` / `regmap_clear_bits` | `update_bits`의 줄임 | 6.x에서 많이 씀 |
| `regmap_test_bits(map, reg, bits)` | 비트가 전부 1인가 | 1/0 또는 음수 에러 |
| `regmap_bulk_read/write(map, reg, buf, count)` | 연속 레지스터 count개 | 값을 `val_bits` 단위로 CPU 엔디안으로 변환 |
| `regmap_raw_read/write(map, reg, buf, len)` | 버스 바이트 그대로 | 변환 없음, 바이트 수 기준 |
| `regmap_noinc_read/write(map, reg, buf, len)` | 같은 주소를 len번 | FIFO 포트, `rd_noinc_table` 필요 |
| `regmap_read_poll_timeout(map, reg, val, cond, sleep_us, timeout_us)` | 조건까지 폴링 | 매크로. `_atomic` 변형은 MMIO용 |
| `regmap_multi_reg_write(map, seq, n)` | (reg, val, delay_us) 순서대로 | 초기화 시퀀스 |
| `regmap_register_patch(map, seq, n)` | 즉시 쓰고, **sync 때마다 재적용** | errata·튜닝 값. 캐시 우회 |
| `regmap_field_read/write/update_bits` | 비트필드 | §6 |

반환값은 전부 0 또는 음수 errno다. 실무 코드는 반환값을 확인한다(예제는 지면 때문에 워크로드 함수에서 생략했다).

### 4.2 예제 6(a) — probe와 칩 초기화 (`h2_imu.c` 3/4 앞부분)

무엇을 확인하나: Don의 bring-up 순서 "ID 확인 → 소프트 리셋 → 리셋 완료 폴링 → errata 패치 → 설정 쓰기"를 regmap API로.

```c
/* (3/4) 필드, 초기화, 워크로드 */
struct h2_imu {
	struct regmap *map;
	struct regmap_field *odr, *fs;
};

static const struct reg_field h2_odr_f = REG_FIELD(H2_CTRL1, 4, 7);
static const struct reg_field h2_fs_f  = REG_FIELD(H2_CTRL1, 2, 3);
static const struct reg_sequence h2_patch[] = {	/* "errata": 아날로그 튜닝 값 */
	{ H2_CTRL2, 0x80 },
};
static const struct reg_sequence h2_init_seq[] = {
	{ H2_INT_CTRL, 0x01 },				/* DRDY 인터럽트 켜기 */
};

static int h2_chip_init(struct h2_imu *h)
{
	unsigned int v;
	int ret;

	ret = regmap_set_bits(h->map, H2_CTRL3, H2_CTRL3_SW_RESET);
	if (ret)
		return ret;
	ret = regmap_read_poll_timeout(h->map, H2_CTRL3, v,
				       !(v & H2_CTRL3_SW_RESET), 100, 10000);
	if (ret)
		return ret;
	ret = regmap_register_patch(h->map, h2_patch, ARRAY_SIZE(h2_patch));
	if (ret)
		return ret;
	ret = regmap_multi_reg_write(h->map, h2_init_seq, ARRAY_SIZE(h2_init_seq));
	if (ret)
		return ret;
	ret = regmap_field_write(h->odr, 4);		/* 104 Hz */
	return ret ?: regmap_field_write(h->fs, 2);	/* ±8 g */
}
```

probe 본체(`h2_imu.c` 4/4에서 발췌):

```c
static int h2_probe(struct i2c_client *client)
{
	struct device *dev = &client->dev;
	struct h2_imu *h;
	unsigned int id;
	int ret;

	h = devm_kzalloc(dev, sizeof(*h), GFP_KERNEL);
	if (!h)
		return -ENOMEM;
	h2_regmap_cfg.cache_type = cache;
	if (bug_nv)
		h2_vol.n_yes_ranges = ARRAY_SIZE(h2_vol_ranges) - 2;
	if (no_precious)
		h2_regmap_cfg.precious_table = NULL;
	h->map = devm_regmap_init_i2c(client, &h2_regmap_cfg);
	if (IS_ERR(h->map))
		return dev_err_probe(dev, PTR_ERR(h->map), "regmap init\n");
	h->odr = devm_regmap_field_alloc(dev, h->map, h2_odr_f);
	h->fs = devm_regmap_field_alloc(dev, h->map, h2_fs_f);
	if (IS_ERR(h->odr) || IS_ERR(h->fs))
		return -ENOMEM;
	i2c_set_clientdata(client, h);

	ret = regmap_read(h->map, H2_WHO_AM_I, &id);
	if (ret)
		return dev_err_probe(dev, ret, "WHO_AM_I read\n");
	if (id != H2_WHOAMI_VAL)
		return dev_err_probe(dev, -ENODEV, "WHO_AM_I 0x%02x != 0x%02x\n",
				     id, H2_WHOAMI_VAL);
	ret = h2_chip_init(h);
	if (ret)
		return dev_err_probe(dev, ret, "chip init\n");
	dev_info(dev, "h2_imu ready: cache_type=%d might_sleep=%d\n",
		 cache, regmap_might_sleep(h->map));
	return 0;
}
```

- `devm_regmap_init_i2c`는 devres(G3)라서 remove 때 regmap이 자동으로 해제된다(debugfs 디렉터리도 같이 사라진다).
- `regmap_read_poll_timeout`의 인자 순서: `(map, reg, val 변수, 조건식, sleep_us, timeout_us)`. 내부에서 `read_poll_timeout()`(include/linux/iopoll.h)을 쓰므로 sleep_us가 0이 아니면 잠든다 — 원자 문맥에서는 `regmap_read_poll_timeout_atomic`(MMIO 같은 fast_io regmap 전용).
- `ret ?: x`는 GNU C 확장(`ret ? ret : x`)으로, 커널에서 흔하다(E5).

한 줄씩 읽으면:

| 버스 로그 | 드라이버 호출 | 왜 이렇게 나갔나 |
|---|---|---|
| `W 0f` + `R 6c` | `regmap_read(WHO_AM_I)` | 캐시에 아직 없음 → 버스(쓰기+읽기 메시지 2개, repeated START) |
| `W 12` + `R 04` | `regmap_set_bits(CTRL3)`의 read | CTRL3는 volatile → 캐시를 못 믿으니 버스에서 읽음 |
| `W 12 05` | 같은 함수의 write | 0x04 OR 0x01 = 0x05 |
| `R 05`, `R 05`, `R 04` | `regmap_read_poll_timeout` | 세 번째 읽기에서 리셋 완료(비트 0 해제) |
| `W 11 80` | `regmap_register_patch` | 캐시를 건너뛰고 칩에 직접 |
| `W 0d 01` | `regmap_multi_reg_write` | 시퀀스 항목 1개 |
| `W 10 40` | `regmap_field_write(odr, 4)` | CTRL1 값은 캐시(기본값 0x00)에 있으니 **read 없이** write |
| `W 10 48` | `regmap_field_write(fs, 2)` | 캐시의 0x40에 FS 비트를 더해 0x48 |

출력에서 볼 것: CTRL1 RMW 두 번에 **읽기가 한 번도 없다.** `reg_defaults`가 "POR 직후 CTRL1은 0x00"이라고 알려 줬기 때문이다. 펌웨어에서 shadow 배열을 POR 값으로 초기화해 두던 것과 같은 효과다. 반대로 volatile인 CTRL3의 RMW는 매번 읽는다.

함정: soft reset은 칩의 레지스터를 POR 값으로 되돌리지만 **regmap 캐시는 그걸 모른다.** 여기서는 probe 맨 앞(아직 아무것도 캐시하지 않은 시점)이라 괜찮았다. 동작 중에 리셋을 한다면 리셋 뒤에 `regcache_mark_dirty()`(그리고 필요하면 `regcache_sync()`) 또는 `regcache_drop_region()`으로 캐시를 칩 상태와 맞춰야 한다.

## 5. 캐시 — regmap이 버스를 건너뛰는 규칙

### 5.1 직관 — shadow register를 커널이 관리한다

I2C 400 kHz에서 레지스터 하나 읽기는 대략 "START + 주소 + 레지스터 + repeated START + 주소 + 값 + STOP" ≈ 40비트 ≈ 0.1 ms다. CPU에게는 영원에 가깝다. 그리고 그동안 버스는 다른 칩이 못 쓴다. 그래서 펌웨어에서도 "내가 마지막으로 쓴 설정 값"은 RAM shadow에 두고, RMW를 할 때 shadow를 읽었다.

regmap 캐시가 바로 그 shadow다. 규칙은 단순하다: **volatile이 아닌 레지스터는 한 번 알게 된 값(읽었거나 썼거나 기본값)을 캐시에 두고, 다음 읽기는 캐시에서 끝낸다.** 칩이 스스로 값을 바꾸지 않는다고 약속한 레지스터이니 캐시가 곧 진실이다.

그림 3 — `_regmap_read()`/`_regmap_write()`(6.18 `drivers/base/regmap/regmap.c`)의 판단 순서를 그대로 옮긴 것. 읽기의 ②가 캐시 히트, 쓰기의 ③이 suspend 중의 "캐시에만 쓰기"다. 쓰기에서 "같은 값이면 생략"은 `regmap_write`가 아니라 `regmap_update_bits`가 하는 일이라는 점에 주의.

그림에서 놓치기 쉬운 두 가지:

- 쓰기의 ②에서 **volatile 레지스터는 캐시에 기록되지 않는다.** 그런데 ③의 cache_only 검사는 그 뒤에 있으므로, cache_only 상태에서 volatile 레지스터에 쓰면 캐시에도 버스에도 안 남고 0(성공)이 반환된다(6.18 소스를 읽고 내린 결론이며 실행해 보지는 않았다). suspend 중에 volatile 레지스터를 써야 한다면 설계가 잘못된 것이다.
- 읽기는 캐시에 없으면 버스에서 읽어 **캐시를 채운다.** 그래서 `reg_defaults`에 없는 비휘발 레지스터(`WHO_AM_I`)도 두 번째부터는 공짜다(예제 7의 `whoami x2`).

### 5.2 캐시 종류 (6.18)

| `cache_type` | 자료구조 | 장점 | 단점·함정 | 언제 |
|---|---|---|---|---|
| `REGCACHE_NONE` | 없음 | 단순, 항상 칩의 진짜 값 | 모든 접근이 버스. suspend 복원 불가 | MMIO(버스가 싸다), 레지스터가 전부 volatile |
| `REGCACHE_RBTREE` | red-black tree, 연속 레지스터를 블록으로 | 희소 맵에 메모리 효율 | 오래된 방식, 새 코드에선 MAPLE 권장 | 기존 드라이버에 많다 |
| `REGCACHE_FLAT` | `max_register` 크기 배열 | O(1), 가장 빠름 | **"값 없음" 개념이 없다**(6.18): 안 읽은 레지스터도 0(또는 기본값)이 캐시 값 | 작고 조밀한 맵, 기본값을 전부 아는 칩 |
| `REGCACHE_MAPLE` | maple tree (커널의 범위 트리) | 희소 맵에 좋고, 블록 단위 sync | 노드 할당이 필요 | **새 드라이버의 기본 선택** |

FLAT의 함정은 6.18 `regcache-flat.c`에서 바로 보인다 — 읽기 함수가 "값이 있나?"를 검사하지 않는다:

```text
static int regcache_flat_read(struct regmap *map,
			      unsigned int reg, unsigned int *value)
{
	unsigned int *cache = map->cache;
	unsigned int index = regcache_flat_get_index(map, reg);

	*value = cache[index];

	return 0;
}
```

반면 MAPLE/RBTREE는 값이 없으면 `-ENOENT`를 돌려주고, `_regmap_read()`가 버스로 내려간다. 예제 7에서 이 차이가 probe 실패로 드러난다. (FLAT의 이 동작은 커널 버전에 따라 바뀔 수 있으니, 다른 버전에서는 그 버전의 `regcache-flat.c`를 직접 확인하라.)

### 5.3 예제 7(a) — 워크로드 함수와 sysfs 손잡이 (`h2_imu.c` 3/4 뒷부분)

무엇을 확인하나: 센서 드라이버가 샘플마다 하는 전형적인 일 — 설정 확인 몇 번, "혹시 몰라" 다시 쓰는 설정, 상태 확인, 데이터 burst, 인터럽트 상태 읽기. 이걸 N번 돌리는 sysfs 속성 `workload`.

```c
static void h2_workload_once(struct h2_imu *h, u8 *out)
{
	unsigned int v;

	regmap_read(h->map, H2_CTRL1, &v);		/* 설정 확인 */
	regmap_read(h->map, H2_INT_CTRL, &v);
	regmap_field_read(h->odr, &v);
	regmap_update_bits(h->map, H2_CTRL1, GENMASK(7, 4), 4 << 4); /* 같은 값 */
	regmap_field_write(h->fs, 2);			/* 같은 값 */
	regmap_read(h->map, H2_STATUS, &v);		/* 데이터 경로 */
	regmap_bulk_read(h->map, H2_OUTX_L, out, 6);
	regmap_read(h->map, H2_INT_STATUS, &v);
}

static ssize_t workload_store(struct device *dev, struct device_attribute *a,
			      const char *buf, size_t n)
{
	struct h2_imu *h = dev_get_drvdata(dev);
	u8 out[6];
	int i, cnt;
	ktime_t t0;

	if (kstrtoint(buf, 0, &cnt))
		return -EINVAL;
	t0 = ktime_get();
	for (i = 0; i < cnt; i++)
		h2_workload_once(h, out);
	dev_info(dev, "workload x%d: %lld us\n", cnt,
		 ktime_us_delta(ktime_get(), t0));
	return n;
}
static DEVICE_ATTR_WO(workload);
```

### 5.5 예제 8 — 같은 워크로드 1회의 버스 로그: NONE vs MAPLE

무엇을 확인하나: 그림 4의 8 대 3이 어떤 메시지로 이루어지는지. 한 번 워크로드를 돌려 캐시를 데운 뒤, 로그를 켜고 1회를 더 돌린다. 한 줄 = 트랜잭션 하나(쓰기 메시지 + 읽기 메시지).

```sh
# t3b.sh (게스트, $A = cache 종류)

insmod /h2_fakebus.ko; insmod /h2_imu.ko cache=$A

echo 1 > $B/log; echo 1 > $D/workload
dmesg | grep "h2_fakebus: [RW]" | sed 's/^\[[ 0-9.]*\] //' | paste - - | sed 's/h2_fakebus: //g'
```

`ARGS=0`(NONE)으로 부팅:

```text
W 10	R 48
W 0d	R 01
W 10	R 48
W 10	R 48
W 10	R 48
W 1e	R 00
W 22	R 01 02 03 04 05 06
```

`ARGS=3`(MAPLE)으로 부팅:

```text
W 1e	R 00
```

### 5.6 예제 9 — `register_patch`는 캐시를 건너뛴다

무엇을 확인하나: probe의 `regmap_register_patch()`가 CTRL2에 0x80을 썼다(예제 6의 `W 11 80`). 그런데 debugfs 덤프(예제 5)에서 CTRL2는 `00`이었다. 어느 쪽이 맞나?

```sh

up
echo "캐시가 말하는 CTRL2: $(grep ^11 $R/registers)"

```

```text
캐시가 말하는 CTRL2: 11: 00
칩에 실제로 있는 CTRL2: 0x80
cache_bypass=Y 로 다시 덤프: 11: 80
```

출력에서 볼 것: 칩은 0x80, 캐시는 기본값 0x00. `regmap_register_patch`는 **캐시를 우회해서** 쓰고, 패치 목록을 기억해 두었다가 `regcache_sync()` 때마다 맨 먼저 다시 쓴다(예제 14에서 확인). 패치는 "드라이버가 평소에 건드리지 않는 숨은 튜닝 레지스터"용이라는 전제다. 그 레지스터를 드라이버가 `regmap_read`로 읽으면 캐시의 기본값을 받는다 — **패치 대상 레지스터는 드라이버에서 읽지도 쓰지도 않는다**가 규칙이다. `i2cget -f`는 커널 드라이버가 잡고 있는 주소에 강제로(`-f`) 접근하는 것으로, 디버깅용이다(H5). debugfs의 `cache_bypass`도 마찬가지로 디버깅 전용 스위치다.

## 6. `regmap_field` — 비트필드를 이름으로

### 6.1 직관

E5에서 `FIELD_PREP(GENMASK(7, 4), odr)`와 RMW로 비트필드를 다뤘다. 레지스터 하나에 필드가 여러 개 있으면 드라이버 곳곳에 마스크와 시프트가 흩어진다. `regmap_field`는 "CTRL1의 7..4비트 = ODR"이라는 **위치 정보를 객체 하나에 묶어 두고**, 이후엔 `regmap_field_write(odr, 4)`처럼 값만 다룬다.

```
 CTRL1 (0x10)   bit:  7   6   5   4   3   2   1   0
                    +---+---+---+---+---+---+---+---+
                    |     ODR[3:0]  | FS[1:0]| -  - |
                    +---+---+---+---+---+---+---+---+
 REG_FIELD(0x10, 4, 7) -> odr     REG_FIELD(0x10, 2, 3) -> fs
 regmap_field_write(odr, 4) == regmap_update_bits(map, 0x10, GENMASK(7,4), 4 << 4)
```

### 6.2 정의

```c
struct reg_field {		/* include/linux/regmap.h (6.18) — 필드 위치 */
	unsigned int reg;
	unsigned int lsb;
	unsigned int msb;
	unsigned int id_size;	/* 같은 필드가 채널마다 반복될 때 */
	unsigned int id_offset;
};
#define REG_FIELD(_reg, _lsb, _msb) { .reg = _reg, .lsb = _lsb, .msb = _msb }
```

(위 블록은 헤더를 요약해 옮긴 것이다. 실제 `REG_FIELD` 매크로는 줄바꿈된 형태다.)

| 함수 | 하는 일 |
|---|---|
| `devm_regmap_field_alloc(dev, map, reg_field)` | 필드 객체 하나 (devres) |
| `devm_regmap_field_bulk_alloc(dev, map, fields[], reg_fields[], n)` | 여러 개를 배열로 한 번에 |
| `regmap_field_read(f, &val)` | 필드 값(0번 비트로 내려서) |
| `regmap_field_write(f, val)` | `update_bits`로 필드만 바꿈 → 같으면 생략 |
| `regmap_field_force_write(f, val)` | 같아도 씀 |
| `regmap_field_set_bits` / `clear_bits` / `test_bits` | 필드 안의 비트 조작 |
| `regmap_fields_read/write(f, id, val)` | `REG_FIELD_ID`로 만든 채널별 반복 필드 |
| `regmap_field_read_poll_timeout(f, val, cond, sleep, timeout)` | 필드 폴링 |

### 6.3 예제 4(d) — sysfs로 ODR 필드 다루기 (`h2_imu.c` 4/4 발췌)

```c
static ssize_t odr_show(struct device *dev, struct device_attribute *a, char *buf)
{
	struct h2_imu *h = dev_get_drvdata(dev);
	unsigned int v;
	int ret = regmap_field_read(h->odr, &v);

	return ret ? ret : sysfs_emit(buf, "%u\n", v);
}
static ssize_t odr_store(struct device *dev, struct device_attribute *a,
			 const char *buf, size_t n)
{
	struct h2_imu *h = dev_get_drvdata(dev);
	unsigned int v;
	int ret;

	if (kstrtouint(buf, 0, &v) || v > 15)
		return -EINVAL;
	ret = regmap_field_write(h->odr, v);	/* suspend 중이면 캐시에만 기록 */
	return ret ? ret : n;
}
static DEVICE_ATTR_RW(odr);
```

이 속성은 예제 13·14에서 쓴다. `echo 7 > odr`가 버스에 어떻게 나가는지는 예제 15의 trace에 있다(`regmap_reg_read_cache reg=10 val=38` → `regmap_reg_write reg=10 val=78`: 캐시에서 읽고 쓰기만 버스로).

함정: 실제 IIO 드라이버에서는 ODR을 sysfs 원시 숫자로 노출하지 않고 IIO의 `sampling_frequency` 속성(Hz)으로 노출한다(I 모듈). 여기서는 regmap만 보려고 단순화했다.

## 7. volatile과 precious — 분류를 틀리면 생기는 일

### 7.1 직관

- **volatile**: "이 레지스터는 칩이 스스로 바꾼다 → regmap아, 캐시를 믿지 마라." 틀리면(빠뜨리면) **오래된 값(stale)**을 읽는다. 증상은 "인터럽트가 왔는데 상태가 0", "데이터 준비 비트가 영원히 안 선다".
- **precious**: "이 레지스터는 읽는 순간 칩의 상태가 바뀐다 → 드라이버가 의도할 때만 읽어라." 틀리면(빠뜨리면) **디버그 덤프나 다른 경로의 읽기가 이벤트를 먹어 버린다.** 증상은 "debugfs를 cat하면 가끔 인터럽트를 놓친다" — 재현이 어려운 최악의 종류다.

precious와 volatile은 서로 독립인 표시다. clear-on-read 레지스터는 보통 **둘 다**다(값이 스스로 바뀌고, 읽으면 지워진다).

### 7.2 예제 10 — 버그 1: 상태 레지스터를 volatile에서 빠뜨림

무엇을 확인하나: `bug_nv=1`이면 INT_STATUS와 STATUS가 volatile 표에서 빠진다. 부팅 직후 한 번 읽어(0이 캐시됨) 두고, 칩에 새 샘플을 만든 뒤 다시 읽는다.

```sh
# t7.sh (게스트, $A = bug_nv)
. /common.sh
up bug_nv=$A
grep -E "^(1a|1e)" $R/access
echo "부팅 직후: status=$(cat $D/status) irqstat=$(cat $D/irqstat)"
echo 1 > $B/stats; echo 1 > $B/tick; echo "tick 1 → 칩에 새 샘플 + DRDY"
echo "드라이버가 읽은 값: status=$(cat $D/status) irqstat=$(cat $D/irqstat)"
st reads; echo "버스에서 직접 읽은 STATUS: $(i2cget -f -y 0 0x6a 0x1e)"
```

`ARGS=1`(버그):

```text
1a: y n n y
1e: y n n n
부팅 직후: status=0x00 irqstat=0x00
tick 1 → 칩에 새 샘플 + DRDY
드라이버가 읽은 값: status=0x00 irqstat=0x00
[reads] xfers=0 msgs=0 rbytes=0 wbytes=0
버스에서 직접 읽은 STATUS: 0x01
```

`ARGS=0`(정상):

```text
1a: y n y y
1e: y n y n
부팅 직후: status=0x00 irqstat=0x00
tick 1 → 칩에 새 샘플 + DRDY
드라이버가 읽은 값: status=0x01 irqstat=0x01
[reads] xfers=2 msgs=4 rbytes=2 wbytes=2
버스에서 직접 읽은 STATUS: 0x01
```

출력에서 볼 것: 버그 판에서는 `access`의 volatile 열이 `n`이고, 드라이버가 두 레지스터를 읽었는데 **버스 트랜잭션이 0번**이다. 부팅 직후 캐시된 0x00을 계속 돌려준다. 칩은 0x01(`i2cget`)인데 드라이버는 영원히 "데이터 없음"이라고 믿는다. 정상 판은 같은 읽기가 버스로 2번 나가서 0x01을 본다. 인터럽트 기반 드라이버라면 버그 판의 IRQ 핸들러는 "내 인터럽트 아님"(`IRQ_NONE`)을 반환하고, 그게 반복되면 커널이 그 IRQ 라인을 꺼 버린다("nobody cared", F6). 게다가 진짜 칩의 INT_STATUS는 실제로 읽히지 않으니 지워지지도 않아서 레벨 인터럽트가 계속 걸려 있다 — **IRQ 폭주 + 데이터 없음**이라는, 원인과 증상이 멀리 떨어진 버그가 된다.

함정: 이 버그는 **캐시 없이 개발하다가 마지막에 `cache_type`만 켰을 때** 잘 생긴다. 캐시가 없으면 volatile 기본값이 "전부 volatile"이라(§3.2) 표가 틀려도 증상이 없기 때문이다. 캐시를 켜는 순간이 volatile 표를 검증할 때다.

### 7.3 예제 11 — 버그 2: precious 표시가 없으면 debugfs 덤프가 인터럽트를 지운다

무엇을 확인하나: `no_precious=1`이면 INT_STATUS·FIFO_DATA가 precious가 아니다. 인터럽트가 걸린 상태에서 누군가 "디버깅하려고" `registers`를 덤프한 뒤, 드라이버가 INT_STATUS를 읽는다.

```sh
# t8.sh (게스트, $A = no_precious)
. /common.sh
up no_precious=$A
echo 1 > $B/tick; echo "tick 1 → DRDY 인터럽트 발생 (INT_STATUS=0x01)"
echo "누군가 디버깅하려고 registers를 덤프한다:"
grep -E "^(1a|1e|3e)" $R/registers
echo "드라이버의 IRQ 처리가 읽은 INT_STATUS = $(cat $D/irqstat)"
```

`ARGS=1`(precious 표시 없음):

```text
tick 1 → DRDY 인터럽트 발생 (INT_STATUS=0x01)
누군가 디버깅하려고 registers를 덤프한다:
1a: 01
1e: 01
3e: 01
드라이버의 IRQ 처리가 읽은 INT_STATUS = 0x00
```

`ARGS=0`(정상):

```text
tick 1 → DRDY 인터럽트 발생 (INT_STATUS=0x01)
누군가 디버깅하려고 registers를 덤프한다:
1e: 01
드라이버의 IRQ 처리가 읽은 INT_STATUS = 0x01
```

출력에서 볼 것: precious 표시가 없으면 debugfs 덤프가 0x1a를 **읽어서 지웠고**(덤프에는 01이 찍혔다), 정작 드라이버는 0x00을 받아 인터럽트를 놓쳤다. 0x3e(FIFO_DATA)도 덤프가 읽어서 FIFO에서 1바이트가 사라졌다 — 이후 FIFO 데이터의 X/Y/Z 정렬이 1바이트씩 밀린다. 정상 판에서는 덤프가 precious 레지스터를 아예 건너뛰고, 드라이버가 0x01을 받는다.

그럼 precious는 regmap 안에서 어디에 쓰일까? 6.18 소스에서 `grep -n precious drivers/base/regmap/regmap.c regcache.c`를 해 보면 정의(`regmap_precious()`)와 config 복사 외에는 나오지 않는다. 즉 **현재 코어에서 precious를 실제로 존중하는 곳은 debugfs 덤프**이고, 나머지는 "이 주소는 드라이버의 의도된 읽기 외에는 건드리지 마라"는 **표시(문서)** 역할이다. 그래도 반드시 표시한다 — 현장에서 레지스터 덤프는 debugfs로 가장 많이 하고, 그 한 번이 위 버그를 만든다. 6.18 `regmap-debugfs.c`의 해당 부분:

```text
static bool regmap_printable(struct regmap *map, unsigned int reg)
{
	if (regmap_precious(map, reg))
		return false;

	if (!regmap_readable(map, reg) && !regmap_cached(map, reg))
		return false;

	return true;
}
```

## 8. 대량 전송 — bulk, raw, noinc (FIFO burst)

### 8.1 세 가지 대량 읽기

| 함수 | 주소 | 단위 | 엔디안 변환 | 쓰는 곳 |
|---|---|---|---|---|
| `regmap_bulk_read(map, reg, buf, count)` | reg, reg+stride, … | 레지스터 count개 | 함 (`val_bits` > 8일 때) | 연속 데이터 레지스터(OUTX_L..OUTZ_H) |
| `regmap_raw_read(map, reg, buf, len)` | 연속 | 바이트 len개 | 안 함 (버스 바이트 그대로) | 칩 포맷 그대로 넘길 때 |
| `regmap_noinc_read(map, reg, buf, len)` | **reg 고정** | 바이트 len개 | 안 함 | FIFO 데이터 포트 |

`regmap_bulk_read`는 범위 전체가 volatile이거나 캐시가 NONE일 때만 raw 한 덩어리로 읽고, 캐시가 있는데 비휘발 레지스터가 섞여 있으면 **레지스터별로 쪼개서** 읽는다(일부는 캐시에서) — 6.18 `regmap_bulk_read()`의 `vol ... REGCACHE_NONE` 조건. 전부 volatile인 데이터 레지스터 묶음은 한 트랜잭션이 된다(예제 8의 `W 22 / R 01 02 03 04 05 06`).

`noinc`는 "주소를 증가시키지 않는 포트"를 regmap에 알리는 것이다. 칩 입장에서는 같은 레지스터를 len번 읽는 것이고, I2C에서는 "레지스터 주소 한 번 쓰고 len바이트 연속 읽기" 한 트랜잭션이다. 6.18의 `regmap_noinc_read()`는 그 주소가 **volatile이면서 `rd_noinc_table`에 있어야** 동작하고, 아니면 `-EINVAL`을 돌려준다(캐시된 FIFO 포트는 말이 안 되니까).

### 8.2 예제 12 — FIFO 60바이트를 한 번에

무엇을 확인하나: 샘플 10개(6바이트씩 = 60바이트)를 FIFO에 쌓고, 드라이버의 `fifo` 속성이 `FIFO_STATUS`를 읽은 뒤 `regmap_noinc_read`로 한 번에 비운다.

```c
static ssize_t fifo_show(struct device *dev, struct device_attribute *a, char *buf)
{
	struct h2_imu *h = dev_get_drvdata(dev);
	unsigned int n;
	u8 data[192];
	int ret;

	ret = regmap_read(h->map, H2_FIFO_STATUS, &n);
	if (ret || !n)
		return ret ? ret : sysfs_emit(buf, "empty\n");
	ret = regmap_noinc_read(h->map, H2_FIFO_DATA, data, n);	/* 한 번의 burst */
	if (ret)
		return ret;
	return sysfs_emit(buf, "%u bytes: %*ph ...\n", n, 12, data);
}
static DEVICE_ATTR_RO(fifo);
```

```sh
# t6.sh (게스트)
. /common.sh
up
echo 10 > $B/tick
echo 1 > $B/log; echo 1 > $B/stats
cat $D/fifo
st fifo; cat $D/fifo
dmesg | grep "h2_fakebus: [RW]" | sed 's/^\[[ 0-9.]*\] //'
```

```text
60 bytes: 01 02 03 04 05 06 02 04 06 08 0a 0c ...
[fifo] xfers=2 msgs=4 rbytes=61 wbytes=2
empty
h2_fakebus: W 3a
h2_fakebus: R 3c
h2_fakebus: W 3e
h2_fakebus: R 01 02 03 04 05 06 02 04
h2_fakebus: W 3a
h2_fakebus: R 00
```

출력에서 볼 것: FIFO_STATUS 읽기 1번(0x3c = 60) + FIFO 읽기 **1번에 60바이트**(rbytes 61 = 1 + 60). 어댑터 로그는 앞 8바이트만 찍는다. 두 번째 `cat`은 FIFO_STATUS가 0이라 `empty`. 샘플 1(01 02 … 06), 샘플 2(02 04 … 0c) 순서가 보존됐다. 실제 IMU 드라이버(예: `drivers/iio/imu/st_lsm6dsx/`)도 FIFO를 이렇게 큰 덩어리로 읽는데, 어댑터의 최대 전송 길이(`max_read_len` quirk)를 넘으면 regmap이 `max_raw_read` 단위로 쪼갠다.

함정: `u8 data[192]`를 스택에 둔 것은 예제라서다. SPI 백엔드에서 `regmap_noinc_read`/`bulk_read`의 버퍼는 DMA될 수 있으므로 **스택 버퍼를 쓰면 안 된다**(SPI 컨트롤러가 DMA로 직접 쓰는 메모리는 kmalloc 메모리여야 함, H7·H9). I2C regmap은 내부에서 복사하는 경우가 많지만 습관적으로 `devm_kmalloc`한 버퍼나 private 구조체 안의 `____cacheline_aligned` 버퍼를 쓴다.

## 9. 전원 관리 — cache_only, mark_dirty, sync

### 9.1 직관 — "꺼지기 전에 장부를 덮고, 켜진 뒤 장부대로 다시 쓴다"

센서 키트가 suspend로 들어가면 센서의 전원 레일이 꺼지는 경우가 많다(레귤레이터 off, H3). 깨어나면 칩은 **POR 값**이다. 펌웨어라면 "설정 복원 함수"가 shadow 배열을 칩에 다시 썼을 것이다. regmap 캐시가 그 shadow이므로, 세 함수로 끝난다.

- `regcache_cache_only(map, true)`: 지금부터 쓰기는 캐시에만(dirty 표시), 캐시에 없는 읽기는 `-EBUSY`. 꺼진 칩에 버스 트랜잭션을 보내지 않게 막는다.
- `regcache_mark_dirty(map)`: "칩이 POR 값으로 돌아갈 것이다"라고 알린다. 다음 sync가 **기본값과 다른 레지스터만** 쓰게 하는 스위치이기도 하다.
- `regcache_sync(map)`: 패치(`register_patch`)를 먼저 쓰고, 캐시에서 기본값과 다른 비휘발·쓰기 가능 레지스터를 칩에 쓴다.

### 9.2 예제 13(a) — suspend/resume 콜백 (`h2_imu.c` 4/4 발췌)

```c
/* 전원 관리: 끄기 전에 캐시 전용 모드, 켠 뒤에 캐시를 칩에 다시 쓴다 */
static int h2_suspend(struct device *dev)
{
	struct h2_imu *h = dev_get_drvdata(dev);

	regcache_cache_only(h->map, true);	/* 이제부터 쓰기는 캐시에만 */
	regcache_mark_dirty(h->map);		/* 칩이 리셋될 것이니 전부 dirty */
	h2_fakebus_set_power(false);		/* "레귤레이터 off" */
	return 0;
}

static int h2_resume(struct device *dev)
{
	struct h2_imu *h = dev_get_drvdata(dev);

	h2_fakebus_set_power(true);		/* 칩은 POR 값으로 깨어난다 */
	regcache_cache_only(h->map, false);
	return regcache_sync(h->map);		/* patch → 기본값과 다른 레지스터 */
}
static DEFINE_SIMPLE_DEV_PM_OPS(h2_pm, h2_suspend, h2_resume);

static ssize_t pm_store(struct device *dev, struct device_attribute *a,
			const char *buf, size_t n)
{
	int ret = sysfs_streq(buf, "suspend") ? h2_suspend(dev) :
		  sysfs_streq(buf, "resume") ? h2_resume(dev) : -EINVAL;
	return ret ? ret : n;
}
static DEVICE_ATTR_WO(pm);
```

드라이버 구조체에는 `.pm = pm_sleep_ptr(&h2_pm)`로 연결한다(`CONFIG_PM_SLEEP`이 꺼진 커널에서는 NULL이 되어 코드가 빠진다). `pm` 속성은 suspend 상태를 오래 붙잡고 관찰하려고 만든 실험용 손잡이다 — 진짜 시스템 suspend는 예제 14에서 한다.

순서가 중요하다. suspend에서는 **cache_only를 먼저** 켠 뒤 전원을 끈다(반대면 그 사이 다른 스레드의 접근이 꺼진 칩으로 간다). resume에서는 **전원을 먼저** 켠 뒤 cache_only를 끄고 sync한다. 실제 드라이버라면 전원을 켠 뒤 칩의 부팅 시간(데이터시트의 turn-on time)만큼 기다린다.

### 9.3 예제 13(b) — 꺼진 칩, 캐시에만 쓰기, 복원

무엇을 확인하나: suspend 상태에서 debugfs의 `cache_only`/`cache_dirty`, 캐시에만 들어가는 쓰기, `-EBUSY`, 버스 NACK, 그리고 resume의 sync 비용.

### 9.4 예제 14 — 진짜 시스템 suspend(s2idle) + ftrace

무엇을 확인하나: sysfs 손잡이가 아니라 **커널의 시스템 suspend 경로**가 우리 `dev_pm_ops`를 부르는지, 그리고 regmap tracepoint로 sync가 쓴 레지스터를 본다. QEMU `virt`에서는 `/sys/power/state`에 `freeze`(suspend-to-idle)가 있고, PL031 RTC의 알람으로 깨울 수 있다(BusyBox `rtcwake`).

- 8.18초에 `cache_only flag=1`과 power OFF, 약 3초 뒤(알람 2초 + 진입·복귀) cache_only 해제와 power ON. 콜백이 `kworker`에서 불린 것은 PM core가 장치들의 suspend/resume을 **비동기로** 돌리기 때문이다(N 모듈).
- `regcache_sync start` → **패치(0x11=0x80)가 먼저**, 그다음 캐시에서 기본값과 다른 레지스터 0x0d=0x01, 0x10=0x78 → `stop`. 기본값과 같은 0x11의 캐시 값(0x00)은 쓰지 않았다(패치가 대신 썼다). volatile인 CTRL3, 데이터 레지스터는 대상이 아니다.

## 10. ftrace로 regmap 들여다보기

### 10.1 regmap tracepoint 목록 (6.18 `drivers/base/regmap/trace.h`)

| 이벤트 | 언제 |
|---|---|
| `regmap_reg_read` | 버스에서 읽은 값 (캐시 미스·volatile) |
| `regmap_reg_read_cache` | 캐시에서 읽은 값 (버스 0회) |
| `regmap_reg_write` | 버스에 쓴 값 (성공 후) |
| `regmap_bulk_read` / `regmap_bulk_write` | bulk 전송 |
| `regmap_hw_read_start/done`, `regmap_hw_write_start/done` | 버스 백엔드 호출 직전·직후 (지연 측정용) |
| `regcache_sync` | sync 시작·끝 (캐시 종류 포함) |
| `regmap_cache_only` / `regmap_cache_bypass` | 모드 전환 |
| `regcache_drop_region` | 캐시 구간 버림 |
| `regmap_async_*` | 비동기 쓰기(SPI) |

`i2c:*` 이벤트(`i2c_write`, `i2c_read`, `i2c_reply`, `i2c_result`)와 같이 켜면 "regmap 호출 → I2C 메시지 → 결과"를 한 화면에서 본다. Don에게는 **로직 분석기 캡처를 커널 이벤트 타임라인으로 보는 것**과 같다.

## 11. regmap-mmio — 같은 API로 SoC 레지스터

### 11.1 직관 — MMIO에서도 쓸 이유가 있나?

MMIO는 `readl`/`writel` 한 줄인데 왜 regmap을? H1에서 본 `readl`은 빠르지만, regmap-mmio를 쓰면 같은 블록을 **I2C 버전 칩과 같은 드라이버**로 다룰 수 있고(일부 PMIC·오디오 코덱은 SoC 내장판과 외장 I2C판이 있다), debugfs 덤프·트레이스·`regmap_field`·범위 검사·`syscon`(여러 드라이버가 공유하는 시스템 컨트롤 레지스터 블록) 공유가 공짜로 따라온다. 그래서 `devm_regmap_init_mmio`를 쓰는 파일이 320개다(예제 1).

차이점: MMIO 백엔드는 `fast_io`라서 **spinlock**으로 잠근다 → 원자 문맥(하드 IRQ 핸들러)에서도 부를 수 있다. 캐시는 보통 NONE(MMIO 읽기가 싸고, SoC 블록 레지스터는 상태가 많다).

### 11.2 예제 16 — QEMU edu PCI 장치의 BAR0

QEMU의 교육용 PCI 장치 `edu`(`-device edu`, vendor 0x1234 device 0x11e8)는 BAR0에 간단한 레지스터를 가진다: 0x00 ID(읽기 전용 0x010000ed), 0x04 liveness(쓴 값의 비트 반전이 읽힘), 0x08 팩토리얼(n을 쓰면 n!을 계산), 0x20 상태(bit0 = 계산 중). PCI 드라이버 골격은 H11에서 다루고, 여기서는 regmap 부분만 본다.

```c
// h2_edu.c — regmap-mmio: QEMU edu PCI 장치의 BAR0를 regmap으로 다루기
#include <linux/module.h>
#include <linux/pci.h>
#include <linux/regmap.h>

#define EDU_ID		0x00	/* RO 0x010000ed */
#define EDU_LIVE	0x04	/* RW: 쓴 값의 비트 반전이 읽힌다 */
#define EDU_FACT	0x08	/* RW: n을 쓰면 n!을 계산 */
#define EDU_STATUS	0x20	/* bit0 = 계산 중 */

static const struct regmap_range edu_rd_r[] = {
	regmap_reg_range(EDU_ID, EDU_FACT), regmap_reg_range(EDU_STATUS, EDU_STATUS),
};
static const struct regmap_range edu_wr_r[] = {
	regmap_reg_range(EDU_LIVE, EDU_FACT), regmap_reg_range(EDU_STATUS, EDU_STATUS),
};
static const struct regmap_access_table edu_rd = { edu_rd_r, ARRAY_SIZE(edu_rd_r) };
static const struct regmap_access_table edu_wr = { edu_wr_r, ARRAY_SIZE(edu_wr_r) };

static const struct regmap_config edu_cfg = {
	.name = "bar0",
	.reg_bits = 32, .val_bits = 32, .reg_stride = 4,	/* 32비트 레지스터, 4바이트 간격 */
	.max_register = EDU_STATUS,
	.rd_table = &edu_rd, .wr_table = &edu_wr,
	.cache_type = REGCACHE_NONE,			/* 전부 volatile 취급 */
};
```

```c
static int edu_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct device *dev = &pdev->dev;
	void __iomem *bar;
	struct regmap *map;
	unsigned int v;
	int ret;

	ret = pcim_enable_device(pdev);
	if (ret)
		return ret;
	bar = pcim_iomap_region(pdev, 0, "h2_edu");
	if (IS_ERR(bar))
		return PTR_ERR(bar);
	map = devm_regmap_init_mmio(dev, bar, &edu_cfg);
	if (IS_ERR(map))
		return PTR_ERR(map);

	regmap_read(map, EDU_ID, &v);
	dev_info(dev, "id=0x%08x might_sleep=%d\n", v, regmap_might_sleep(map));
	regmap_write(map, EDU_LIVE, 0x12345678);
	regmap_read(map, EDU_LIVE, &v);
	dev_info(dev, "liveness: wrote 0x12345678 read 0x%08x\n", v);
	regmap_write(map, EDU_FACT, 10);
	ret = regmap_read_poll_timeout(map, EDU_STATUS, v, !(v & 1), 10, 100000);
	regmap_read(map, EDU_FACT, &v);
	dev_info(dev, "10! = %u (poll ret %d)\n", v, ret);
	return 0;
}

static const struct pci_device_id edu_ids[] = { { PCI_DEVICE(0x1234, 0x11e8) }, { } };
MODULE_DEVICE_TABLE(pci, edu_ids);
static struct pci_driver edu_driver = {
	.name = "h2_edu", .id_table = edu_ids, .probe = edu_probe,
};
module_pci_driver(edu_driver);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H2: regmap-mmio on QEMU edu BAR0");
```

```sh

dmesg | grep h2_edu

P=$(ls -d /sys/kernel/debug/regmap/*bar0); cat $P/access; cat $P/registers
```

출력에서 볼 것:

함정: MMIO regmap에서 `val_bits`와 실제 레지스터 접근 폭이 다르면 버스 에러가 난다(어떤 IP는 32비트 접근만 허용). regmap-mmio는 `val_bits`에 맞춰 `readb/readw/readl/readq` 중 하나를 고른다. 그리고 regmap-mmio는 기본적으로 배리어가 있는 `readl`/`writel`을 쓴다 — 관계없는 순서가 중요치 않은 블록이면 `use_relaxed_mmio = true`로 `_relaxed` 접근을 쓸 수 있다(H1).

## 12. 미리 보기 — regmap-irq (H6에서 자세히)

INT_STATUS 같은 **인터럽트 상태 레지스터**를 가진 칩(PMIC가 대표적: 전원 버튼, 과열, 충전기 연결 등 수십 개의 하위 인터럽트)은 "칩의 IRQ 핀 하나 → 상태 레지스터 읽기 → 어떤 하위 이벤트인지 판별 → 하위 IRQ 디스패치"를 해야 한다. 이걸 regmap-irq가 해 준다. 하위 이벤트마다 **진짜 Linux IRQ 번호**(virq)가 생겨서, 다른 드라이버(예: 전원 버튼 input 드라이버)가 그냥 `request_threaded_irq()`로 받는다.

아래는 우리 가짜 IMU에 붙인다면의 모양이다. **이 코드는 실행하지 않았다**(QEMU에서 가짜 칩의 IRQ 핀을 만들려면 irq_sim 등이 필요해서 H6에서 다룬다). 구조체·함수 이름은 6.18 `include/linux/regmap.h`에서 확인했다.

```c
/* 실행하지 않은 스케치 — regmap-irq로 INT_STATUS(clear-on-read) 처리 */
static const struct regmap_irq h2_irqs[] = {
	REGMAP_IRQ_REG(0, 0, BIT(0)),		/* virq 0: DRDY */
	REGMAP_IRQ_REG(1, 0, BIT(1)),		/* virq 1: FIFO 워터마크 */
};

static const struct regmap_irq_chip h2_irq_chip = {
	.name = "h2_imu",
	.status_base = H2_INT_STATUS,		/* 읽으면 지워지므로 ack 레지스터 없음 */
	.unmask_base = H2_INT_CTRL,		/* 1 = 켜짐 (mask_base는 1 = 꺼짐) */
	.num_regs = 1,
	.irqs = h2_irqs,
	.num_irqs = ARRAY_SIZE(h2_irqs),
};

/* probe에서: client->irq = 칩의 IRQ 핀 (DT의 interrupts) */
ret = devm_regmap_add_irq_chip(dev, h->map, client->irq, IRQF_ONESHOT, 0,
			       &h2_irq_chip, &h->irq_data);
virq = regmap_irq_get_virq(h->irq_data, 0);	/* DRDY의 Linux IRQ 번호 */
ret = devm_request_threaded_irq(dev, virq, NULL, h2_drdy_thread,
				IRQF_ONESHOT, "h2-drdy", h);
```

regmap-irq는 상태 레지스터를 **스레드 문맥에서** regmap으로 읽는다(I2C는 잠들 수 있으니까). 그래서 INT_STATUS가 precious·volatile로 올바르게 표시되어 있어야 한다는 §7의 교훈이 그대로 이어진다.

### 13.2 `struct regmap` 안에 무엇이 있나

`struct regmap`은 `drivers/base/regmap/internal.h`에 정의된 **불투명(opaque) 구조체**다. 드라이버는 포인터만 들고 있다. 주요 멤버를 역할별로 묶으면:

| 묶음 | 멤버 (6.18 internal.h) | 역할 |
|---|---|---|
| 락 | `lock`, `unlock`, `mutex` / `spinlock` | `fast_io`면 spinlock, 아니면 mutex (`regmap_might_sleep()`) |
| 버스 | `bus`, `bus_context`, `reg_read`, `reg_write`, `format` | 백엔드와 직렬화 함수 |
| 분류 | `rd_table`, `wr_table`, `volatile_table`, `precious_table`, 콜백들, `max_register` | §3 |
| 캐시 | `cache_ops`, `cache`, `cache_only`, `cache_bypass`, `cache_dirty`, `no_sync_defaults`, `reg_defaults`, `patch` | §5, §9 |
| 페이징 | `range_tree` | `regmap_range_cfg`의 rbtree |
| 디버그 | `debugfs`, `debugfs_name` | `/sys/kernel/debug/regmap/<name>/` |

새 백엔드는 `struct regmap_bus`(`.read`, `.write`, `.reg_read`, `.reg_write`, `.fast_io`, `.max_raw_read` …)를 채워서 `__devm_regmap_init()`에 넘긴다. 버스 레벨 API가 없는 "칩 같은 것"(예: 펌웨어가 중계하는 레지스터, 다른 칩을 통한 간접 접근)은 `regmap_config`의 `.reg_read`/`.reg_write` 콜백으로 **버스 없는 regmap**(`devm_regmap_init(dev, NULL, ctx, &cfg)`)을 만든다 — 그러면 캐시·debugfs·field가 그대로 따라온다.

## 14. Embedded 실무에서 다시 보기

### 14.1 센서 키트 — IMU 드라이버 리뷰 체크

예를 들어 센서 키트의 LSM6DSO IMU 드라이버를 리뷰한다면, 코드보다 먼저 이걸 본다.

- `cat /sys/kernel/debug/regmap/<bus>-<addr>/access`를 데이터시트 레지스터 표와 줄 단위로 대조한다. 상태·데이터·FIFO·자동 해제 비트가 전부 volatile인가? clear-on-read는 precious인가?
- `cache_type`이 MAPLE(또는 RBTREE)인가? FLAT이면 `reg_defaults`가 캐시되는 모든 레지스터를 덮는가?
- suspend/resume에 `cache_only` → `mark_dirty` → (전원 복귀) → `sync` 순서가 있는가? 칩 리셋 직후 `mark_dirty`가 있는가?
- FIFO 읽기가 `noinc_read`/`bulk_read` 한 번이고, 버퍼가 DMA 안전한가(SPI판)?
- 하드 IRQ 핸들러에서 I2C regmap을 부르지 않는가(threaded IRQ인가)?

실제 커널의 `drivers/iio/imu/st_lsm6dsx/`는 I2C·SPI·I3C 세 백엔드를 regmap으로 받고(`st_lsm6dsx_i2c.c`, `_spi.c`, `_i3c.c`가 각각 `devm_regmap_init_*`만 다르다), 코어(`st_lsm6dsx_core.c`)는 버스를 모른다. regmap이 "칩 하나에 드라이버 하나"를 가능하게 한 전형이다.

### 14.2 Don의 PMIC·RF 칩 — SPMI는 regmap이 있다, RFFE는 없다

Don이 Apple에서 다루는 PMIC·RF 프런트엔드는 SPMI와 MIPI RFFE 버스다. Linux에서:

- **SPMI**: 버스 서브시스템(`drivers/spmi/`)과 regmap 백엔드(`regmap-spmi.c`: `devm_regmap_init_spmi_base`(8비트 주소), `devm_regmap_init_spmi_ext`(16비트 확장 주소))가 있다. 예제 1의 5개 파일 중 `drivers/mfd/qcom-spmi-pmic.c`(Qualcomm PMIC), `drivers/mfd/hi6421-spmi-pmic.c`, `drivers/regulator/mt6315-regulator.c`, 그리고 **`drivers/nvmem/apple-spmi-nvmem.c`**(Apple Silicon Mac의 PMIC NVMEM, Asahi Linux 작업)가 보인다. Qualcomm PMIC는 MFD 부모가 SPMI regmap 하나를 만들고 regulator·RTC·GPIO·ADC 자식 드라이버가 그 regmap을 공유한다(§13.3).
- **RFFE**: 6.18 `drivers/base/regmap/` 목록(예제 1)에 RFFE 백엔드는 없다. RF 프런트엔드는 보통 모뎀/RF 펌웨어가 직접 제어하고, Linux 쪽은 펌웨어와의 메시지 인터페이스만 본다. 만약 Linux가 RFFE를 직접 몰아야 한다면 RFFE 컨트롤러 드라이버 위에 `regmap_bus`를 하나 쓰거나, 버스 없는 regmap(`.reg_read`/`.reg_write` 콜백)으로 감싸면 캐시·debugfs·field를 그대로 얻는다(§13.2).

Don이 면접에서 쓸 수 있는 연결: "PMIC bring-up에서 SPMI 레지스터 shadow, 상태 레지스터 예외, 전원 복귀 후 재설정을 펌웨어로 직접 짰다 — Linux에서는 그게 regmap의 cache/volatile/regcache_sync이고, 그래서 regmap_config의 분류를 데이터시트와 대조하는 리뷰를 가장 먼저 한다."

### 14.3 bring-up 첫날 — debugfs가 레지스터 덤프 도구

새 보드에서 "센서가 데이터를 안 준다"면 드라이버를 고치기 전에:

```sh
# 실행 예시(이 노트의 QEMU 환경과 경로가 같다; 실제 보드에서는 버스·주소가 다르다)
cat /sys/kernel/debug/regmap/0-006a/registers     # 설정이 의도대로 들어갔나
echo Y > /sys/kernel/debug/regmap/0-006a/cache_bypass
cat /sys/kernel/debug/regmap/0-006a/registers     # 캐시가 아닌 칩의 진짜 값
echo N > /sys/kernel/debug/regmap/0-006a/cache_bypass
```

캐시 값과 칩 값이 다르면(예제 9처럼) 누군가 regmap을 우회해서 썼거나(패치, `i2cset -f`, 칩 리셋, 전원 글리치) volatile 분류가 틀린 것이다. debugfs `registers`는 기본적으로 **읽기 전용**이다 — 쓰기는 `regmap-debugfs.c`의 `#undef REGMAP_ALLOW_WRITE_DEBUGFS`를 직접 고쳐 커널을 다시 빌드해야 열린다(Kconfig 옵션이 없다 — 의도적으로 어렵게 해 둠). 쓰기 실험은 `i2cset -f`나 드라이버의 sysfs로 한다.

## 16. 면접에서 이렇게 말한다

**Q.** Why would you use regmap instead of calling i2c_smbus_read_byte_data() directly?

**A.** regmap은 버스와 무관한 레지스터 API다. 같은 드라이버가 I2C·SPI·MMIO판 칩을 다 지원하고, 캐시로 버스 트랜잭션을 줄이며(내 측정에서 전형적 워크로드가 8회→3회), 락·범위 검사·RMW·bulk·폴링을 표준으로 주고, debugfs 덤프와 tracepoint가 공짜다. 무엇보다 suspend/resume 레지스터 복원이 `regcache_sync` 한 줄이다.

> regmap gives me one register API regardless of the bus, so the same driver handles the I2C, SPI or MMIO variant of a chip. On top of that I get a register cache that cuts bus traffic — in a test I did, a typical config-check-plus-data-read loop went from eight I2C transactions to three — plus locking, range checks, atomic read-modify-write, bulk and FIFO reads, polling helpers, a debugfs register dump and tracepoints for free. And register restore on resume is just regcache_sync.

**꼬리 질문**: "어떤 경우엔 안 쓰나?" → 레지스터 모델이 아닌 장치(명령/응답 프로토콜, 스트리밍 전용), 또는 극도로 핫한 MMIO 경로에서 오버헤드가 문제일 때.

**Q.** What is a volatile register in regmap, and what happens if you get it wrong?

**A.** 하드웨어가 스스로 값을 바꾸는 레지스터(상태, 데이터, 카운터, 자동 해제 비트)다. regmap은 이걸 캐시하지 않고 매번 버스로 읽는다. 빠뜨리면 첫 읽기 값이 캐시돼서 그 뒤로는 버스에 안 나간다 — 상태 비트가 영원히 0이고, 인터럽트 핸들러가 IRQ_NONE을 반환해 결국 IRQ가 꺼진다. 캐시를 켜기 전에는 기본값이 "전부 volatile"이라 증상이 숨어 있다가, 캐시를 켜는 순간 터진다.

> A volatile register is one the hardware changes on its own — status, data, counters, self-clearing bits — so regmap bypasses the cache and always goes to the bus. If you forget to mark one, the first value read gets cached and every later read returns that stale value with zero bus traffic; a status bit looks permanently clear and the IRQ handler keeps returning IRQ_NONE. It often hides during bring-up because without a cache everything is treated as volatile, and it shows up the moment someone enables the cache.

**Q.** What's the difference between volatile and precious?

**A.** volatile은 "캐시하지 마라", precious는 "읽는 것 자체가 부작용이 있으니 드라이버의 의도된 읽기 외에는 읽지 마라"다. clear-on-read 인터럽트 상태나 FIFO 데이터 포트가 precious다. 6.18 코어에서 precious를 존중하는 곳은 debugfs 덤프로, precious 표시가 없으면 덤프 한 번이 인터럽트 상태를 지워 이벤트를 놓친다 — 직접 재현해 봤다.

> Volatile means don't cache it; precious means reading it has side effects, so nothing except the driver's intentional read should touch it — clear-on-read interrupt status, FIFO data ports. In practice the debugfs register dump skips precious registers; without the flag, a single cat of the debugfs registers file can clear a pending interrupt or pop a FIFO byte. Clear-on-read status registers are usually both volatile and precious.

**Q.** How do you restore a sensor's configuration after its power rail was turned off during suspend?

**A.** suspend에서 `regcache_cache_only(true)`로 버스 접근을 막고 `regcache_mark_dirty()`로 칩이 POR로 돌아간다고 알린 뒤 전원을 끈다. resume에서는 전원을 켜고 칩이 준비될 때까지 기다린 뒤 `cache_only(false)`, `regcache_sync()`. sync는 등록된 패치를 먼저 쓰고, 기본값과 다른 비휘발 레지스터만 쓴다. 내 실험에서 resume 비용은 I2C 쓰기 3번이었고, suspend 중에 바꾼 설정도 sync로 반영됐다.

> In suspend I put the regmap into cache-only mode so nothing hits the bus, mark the cache dirty because the chip will come back with reset defaults, then cut power. In resume I power up, wait the chip's turn-on time, leave cache-only mode and call regcache_sync. Sync re-applies the register patch first and then writes only the cached registers that differ from their defaults — in my test that was three I2C writes — and any config change made while suspended lands in the cache and gets synced too.

**꼬리 질문**: "mark_dirty를 빼먹으면?" → dirty가 아니면 sync가 아무것도 안 쓴다. 칩은 POR 값인 채로 남는다.

**Q.** Which cache type would you choose for a new I2C sensor driver?

**A.** `REGCACHE_MAPLE`. 희소한 레지스터 맵에 맞고, 값이 없으면 버스로 가서 채운다. FLAT은 배열이라 빠르지만 6.18에서는 "값 없음" 개념이 없어서, 기본값을 안 준 비휘발 레지스터는 0을 돌려준다 — WHO_AM_I가 0으로 읽혀 probe가 실패하는 걸 재현했다. RBTREE는 기존 드라이버에 많고, MMIO는 보통 NONE.

> REGCACHE_MAPLE — it handles sparse maps well and falls back to the bus on a miss. FLAT is a plain array and fast, but in the 6.18 kernel I tested it has no notion of "not cached", so any non-volatile register without a default reads back as zero; I reproduced a probe failure where WHO_AM_I came back as 0x00 without a single bus transaction. RBTREE is common in older drivers, and MMIO regmaps usually use no cache at all.

**Q.** Can you call regmap_read() from a hard IRQ handler?

**A.** 버스에 따라 다르다. MMIO regmap은 `fast_io`라 spinlock이고 원자 문맥에서 된다(`regmap_might_sleep()`이 0). I2C/SPI regmap은 mutex를 쓰고 전송 자체가 잠드므로 안 된다 — threaded IRQ나 regmap-irq를 쓴다. 실험에서 I2C는 might_sleep=1, MMIO는 0이었다.

> It depends on the backend. An MMIO regmap is fast_io, uses a spinlock, and is safe in atomic context; regmap_might_sleep returns false. I2C and SPI regmaps take a mutex and the transfer itself sleeps, so you do that work in a threaded handler — or let regmap-irq do it, which reads the status register from its IRQ thread.

**Q.** How do you debug "the driver wrote the register but the chip doesn't behave"?

**A.** 먼저 `/sys/kernel/debug/regmap/<dev>/access`로 분류가 데이터시트와 맞는지 보고, `registers`로 캐시가 아는 값을, `cache_bypass=Y`로 칩의 진짜 값을 본다. 다르면 누가 regmap을 우회했거나(패치, 리셋, i2cset) volatile 분류가 틀린 것. 그다음 `regmap:*`와 `i2c:*` tracepoint를 켜서 실제로 버스에 나갔는지, 캐시에서 끝났는지 본다.

> First I check the access file in the regmap debugfs directory against the datasheet, then compare the registers dump with cache_bypass off and on — the cached value versus what the chip actually holds. A mismatch means something bypassed regmap or a register is misclassified. Then I enable the regmap and i2c tracepoints to see whether the write really went out on the bus or was skipped because the cache thought the value was unchanged.

## 17. 직접 해보기

1. (개념) 데이터시트에 "STATUS_REG: bit0 DRDY — cleared when OUTZ_H is read"라고 되어 있다. 이 레지스터는 volatile인가 precious인가? OUTZ_H는? 정답/힌트: STATUS는 volatile(칩이 바꿈), precious는 아님(읽어도 안 지워짐). OUTZ_H는 volatile이고, 읽으면 다른 레지스터의 비트를 지우므로 엄밀히는 precious로 표시하는 게 안전하다.

4. (관찰) 예제 13에서 `regcache_mark_dirty()`를 지우고 다시 빌드해 돌려라. resume 뒤 `i2cget 0x10`과 `[resume]` 카운터는? 정답/힌트: suspend 중 `odr=9` 쓰기가 dirty를 세우므로 sync는 돌지만 `no_sync_defaults`가 꺼져 기본값과 같은 레지스터까지 다 쓴다(카운터 증가). 쓰기도 안 했다면 아무것도 안 쓴다. 덤으로 sync가 0x11의 캐시 값(0x00)을 패치 뒤에 다시 써서 패치를 덮어쓰는지도 확인해 보라(소스상 그렇게 동작할 것으로 보이지만 이 노트에서는 실행하지 않았다).

## 18. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| regmap | register map | 버스와 무관한 레지스터 접근 계층 (`drivers/base/regmap/`) |
| `regmap_config` | 칩 설명서 | 주소·값 폭, 범위, 분류 표, 캐시 종류 |
| regmap bus | 백엔드 | `regmap-i2c`, `regmap-spi`, `regmap-mmio`, `regmap-spmi` … |
| readable / writeable | 접근 권한 | 아니면 `-EIO` |
| volatile | 휘발성 레지스터 | 칩이 스스로 바꿈 → 캐시 안 함 |
| precious | 소중한 레지스터 | 읽으면 부작용 → debugfs 덤프 제외 |
| noinc | no increment | 주소 고정 포트(FIFO) |
| regcache | 레지스터 캐시 | NONE · RBTREE · FLAT · MAPLE (6.18) |
| `reg_defaults` | POR 기본값 | 캐시 초기값이자 sync 생략 기준 |
| cache_only | 캐시 전용 모드 | 쓰기는 캐시에만, 미스 읽기는 `-EBUSY` |
| cache_bypass | 캐시 우회 | 읽기·쓰기를 버스로 직행 (디버그용) |
| `regcache_sync` | 캐시 → 칩 복원 | 패치 → 기본값과 다른 레지스터 |
| register patch | 칩 패치 | 캐시 우회 쓰기 + sync 때 재적용 |
| `regmap_field` | 비트필드 객체 | `REG_FIELD(reg, lsb, msb)` |
| regmap-irq | 인터럽트 칩 | 상태 레지스터 → 하위 virq 디스패치 |
| syscon | 시스템 컨트롤러 | 여러 드라이버가 공유하는 MMIO regmap |
| fast_io | 빠른 버스 | spinlock 사용, 원자 문맥 가능 |

## 19. 요약 & 체크리스트

regmap은 Don이 펌웨어에서 칩마다 다시 만들던 "레지스터 계층"(버스 래퍼, shadow, RMW, 권한 표, 덤프, 전원 복귀 복원)을 커널이 표준으로 제공하는 것이다. 드라이버는 `regmap_config`에 칩을 설명하고(주소·값 폭, readable/writeable/volatile/precious, 기본값, 캐시 종류), `devm_regmap_init_*` 한 줄로 버스를 고른 뒤, 버스와 무관한 API만 쓴다. 캐시는 비휘발 레지스터의 읽기와 같은 값 RMW를 없애서 전형적 워크로드의 I2C 트랜잭션을 8회에서 3회로 줄였고, `cache_only`/`mark_dirty`/`sync`로 suspend/resume 복원이 몇 줄이 된다. 대가는 **분류의 정확성**이다: volatile을 빠뜨리면 stale 값, precious를 빠뜨리면 덤프가 이벤트를 먹고, FLAT 캐시는 기본값 없는 레지스터를 0으로 돌려준다. 그래서 regmap 드라이버 리뷰는 debugfs `access`와 데이터시트 대조로 시작하고, 동작 확인은 `registers`(+`cache_bypass`)와 `regmap:*` tracepoint로 한다.

- [ ] regmap이 주는 기능(버스 독립, 캐시, 락, 범위 검사, RMW, bulk/noinc, 폴링, 패치, sync, debugfs, trace)을 1분 안에 말할 수 있다
- [ ] 데이터시트 레지스터 표를 readable/writeable/volatile/precious로 분류하고 `regmap_access_table`로 쓸 수 있다
- [ ] `regmap_config`의 `reg_bits`, `val_bits`, `reg_stride`, `max_register`, `cache_type`, `reg_defaults`를 설명할 수 있다
- [ ] 6.18의 캐시 종류 네 가지와 FLAT의 함정을 설명할 수 있다
- [ ] `regmap_read`가 캐시 히트로 끝나는 조건과 버스로 가는 조건을 그림 3대로 설명할 수 있다
- [ ] `regmap_update_bits`가 쓰기를 생략하는 조건을 말할 수 있다
- [ ] `regmap_bulk_read`·`raw_read`·`noinc_read`의 차이와 FIFO 읽기 방법을 코드로 짤 수 있다
- [ ] `REG_FIELD` + `devm_regmap_field_alloc`으로 비트필드를 다룰 수 있다
- [ ] `regcache_cache_only` + `regcache_mark_dirty` + `regcache_sync`로 suspend/resume을 구현하고 순서를 설명할 수 있다
- [ ] `register_patch`가 캐시를 우회하고 sync 때 재적용된다는 것을 설명할 수 있다
- [ ] `/sys/kernel/debug/regmap/<dev>/`의 `access`, `registers`, `cache_bypass`로 문제를 진단할 수 있다
- [ ] `regmap:*`·`i2c:*` tracepoint로 레지스터 접근을 추적할 수 있다
