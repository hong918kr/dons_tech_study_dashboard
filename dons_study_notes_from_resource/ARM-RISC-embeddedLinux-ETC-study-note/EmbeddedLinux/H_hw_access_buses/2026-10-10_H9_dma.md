# H9. DMA — coherent vs streaming, dma_map_single/sg, 캐시 관리, DMA mask, IOMMU/SMMU, dmaengine, dma-buf

> **이 노트를 다 읽으면**: CPU 가상 주소·물리 주소·버스 주소(`dma_addr_t`/IOVA) 세 공간을 구분하고 "장치에게는 `dma_addr_t`만 준다"를 코드로 지킬 수 있다 · coherent(`dma_alloc_coherent`, `dma_pool`)와 streaming(`dma_map_single/page/sg` + 방향 + `dma_sync_*`)을 골라 쓰고, 비코히어런트 arm64에서 그 아래 캐시 clean/invalidate가 어디서 일어나는지 소스로 말할 수 있다 · DMA mask와 SWIOTLB bounce, IOMMU/SMMU의 IOVA·병합·fault·보안을 QEMU `edu` 장치로 직접 보여 줄 수 있다 · dmaengine 클라이언트 순서(`prep` → `submit` → `issue_pending` → 콜백)와 dma-buf exporter/importer 구조를 설명할 수 있다
> **왜 필요한가**: "coherent와 streaming 매핑의 차이는?", "`dma_sync_single_for_cpu`는 왜 부르나요?", "IOMMU가 주는 이점은?"은 Embedded Linux·드라이버 면접의 **고급 단골 질문**이고, 카메라(V4L2)·NPU·네트워크 드라이버 bring-up에서 "데이터가 가끔 깨진다"의 절반이 이 노트의 규칙 위반이다
> **Don 기준 난이도**: 디스크립터 링, PRP/SGL, 캐시 clean/invalidate, doorbell 순서는 SSD 컨트롤러에서 매일 하던 일이다 / 새로 배울 것은 그 일을 **Linux가 대신 해 주는 방식** — `dma_addr_t`라는 추상화, 소유권(ownership) 규칙, SWIOTLB, IOMMU 도메인, 그리고 dmaengine·dma-buf 같은 프레임워크
> **선행 노트**: F5(메모리 배리어, `dma_wmb()` + doorbell), F9(페이지·zone·GFP), F10(CMA, `dma_alloc_coherent()` → CMA 경로), G5(`dma_mmap_coherent`), H1(MMIO `readl`/`writel`) — H11(PCIe), I5(V4L2 videobuf2), I8(DRM)로 이어진다

## 0. 큰 그림 — 이게 왜 필요한가

Don이 SSD 펌웨어에서 호스트 DMA를 걸 때를 떠올려 보자. 호스트 드라이버가 SQE의 PRP1/PRP2(또는 SGL)에 **호스트 메모리 주소**를 적어 주면, 컨트롤러의 DMA 엔진은 그 주소로 PCIe 메모리 읽기/쓰기 TLP를 날렸다. 이때 컨트롤러가 받은 주소는 호스트 CPU의 가상 주소가 아니었다. 호스트 쪽 IOMMU가 켜져 있으면 그건 IOVA였고, 꺼져 있으면 물리 주소였다. 컨트롤러는 그 차이를 몰랐고 몰라도 됐다.

이 노트는 그 그림의 **호스트 쪽**, 즉 Linux 드라이버가 "장치에게 줄 주소"를 어떻게 만들고, 그 사이 캐시와 메모리 소유권을 어떻게 관리하는지를 다룬다. 핵심은 세 개의 주소 공간이다.

그림 1 — DMA의 세 주소 공간. CPU는 가상 주소(VA)로 버퍼를 만지고, 장치는 `dma_addr_t`(버스 주소)로 DRAM을 읽고 쓴다. IOMMU가 없으면 `dma_addr_t`는 물리 주소(PA)와 같거나 고정 오프셋만 다르고, 있으면 장치 전용 페이지 테이블을 거치는 IOVA다. 둘을 잇는 것이 DMA API다.

Don의 경험을 Linux 어휘로 바꾸면 이렇다.

| SSD 펌웨어에서 하던 일 | Linux 드라이버에서 | 이 노트 |
|---|---|---|
| 디스크립터 링을 non-cacheable 영역에 둔다 | `dma_alloc_coherent()`, 작은 건 `dma_pool` | §2 |
| 데이터 버퍼를 넘기기 전 D-cache clean | `dma_map_single(..., DMA_TO_DEVICE)` | §3, §4 |
| DMA 끝난 버퍼를 읽기 전 D-cache invalidate | `dma_unmap_*` 또는 `dma_sync_*_for_cpu(..., DMA_FROM_DEVICE)` | §3, §4 |
| 컨트롤러가 32비트 주소만 낼 수 있다 | DMA mask, SWIOTLB bounce buffer | §5 |
| PRP 리스트 / SGL로 흩어진 페이지 설명 | `struct scatterlist`, `sg_table`, `dma_map_sgtable()` | §6 |
| 호스트 IOMMU가 컨트롤러 접근 범위를 제한 | IOMMU/SMMU, IOVA, iommu_group, translation fault | §7 |
| 디스크립터 쓰고 `DMB` → owner 비트 → doorbell | `dma_wmb()` → `writel()` (F5) | §1.4 |
| SoC의 범용 DMA 컨트롤러로 UART/SPI FIFO 채우기 | dmaengine slave API | §10 |
| 같은 버퍼를 NAND 엔진과 호스트 DMA가 공유 | dma-buf (카메라 → GPU/NPU) | §11 |

이 노트의 핵심 규칙을 미리 다섯 줄로 쓴다.

1. 장치에게는 **`dma_addr_t`만** 준다. `virt_to_phys()`나 `__pa()` 값을 레지스터에 쓰면 IOMMU·bounce·주소 오프셋이 있는 시스템에서 깨진다.
2. 오래 사는 공유 구조(디스크립터 링)는 **coherent**, I/O 한 번에 쓰이는 데이터 버퍼는 **streaming**.
3. streaming 매핑에는 **소유권**이 있다. map하면 장치 것, unmap 또는 `sync_for_cpu` 후에만 CPU 것. 장치 것일 때 CPU가 만지면 비코히어런트 SoC에서 데이터가 깨진다.
4. **DMA mask**는 장치가 실제로 낼 수 있는 주소 폭을 정직하게 적는다. 거짓말하면 오류 없이 엉뚱한 메모리를 읽고 쓴다(§5에서 실제로 본다).
5. IOMMU는 장치를 **격리**하고(보안), 흩어진 페이지를 **연속 IOVA로 이어 붙이고**, 주소 폭 제한을 **풀어 준다**. 대가는 매핑 비용이다(§8 측정).

> 실행 환경: 모든 출력은 Lima VM `elinux`(aarch64, 호스트 커널 `uname -r` = `7.0.0-38-generic`) 안의 공용 QEMU 랩에서 실제로 돌린 결과다. 게스트는 QEMU 10.2.1 `virt` 머신(cortex-a57, 2 CPU, TCG 에뮬레이션)에 QEMU 교육용 PCI 장치 `edu`(`-device edu`)를 꽂았다. 커널은 대부분 랩 기본 커널 **6.18.55**(`/var/lab/out/Image`)이고, §3.5·§9·§10의 일부는 랩 설정에 `CONFIG_DMA_API_DEBUG`·`CONFIG_FUNCTION_TRACER`·`CONFIG_KPROBE_EVENTS`·`CONFIG_DMATEST`를 더해 `/var/tmp/H9/build`에 다시 빌드한 **6.18.55-h9dma**다(그 절에서 다시 밝힌다). 주소·타임스탬프는 실행마다 다르다. 시간 값은 KVM 없는 에뮬레이션 값이라 비교(상대값)만 의미가 있다.

## 1. 세 개의 주소 공간과 `dma_addr_t`

### 1.1 직관 — 장치는 CPU의 MMU를 거치지 않는다

CPU가 `buf[0] = 1`을 실행하면 `buf`(가상 주소)는 MMU의 페이지 테이블을 거쳐 물리 주소가 된다. DMA 엔진은 이 MMU를 거치지 않는다. 장치는 자기가 받은 주소를 그대로 버스(PCIe, AXI)에 싣는다. 그 주소가 DRAM 컨트롤러에 닿기 전에 바뀔 수 있는 곳은 두 군데다.

- **버스 브리지의 고정 변환**: SoC에 따라 "장치가 보는 0번지 = DRAM의 0x8000_0000" 같은 오프셋이 있다. DT의 `dma-ranges`가 이것을 적는다.
- **IOMMU**(Arm에서는 SMMU): 장치마다(정확히는 스트림 ID마다) 페이지 테이블을 두고 주소를 번역한다. CPU의 MMU를 장치 앞에 하나 더 둔 것이다.

그래서 Linux는 장치용 주소에 **별도의 타입** `dma_addr_t`를 쓴다. 드라이버는 이 값을 계산하지 않는다. DMA API(`dma_map_*`, `dma_alloc_coherent`)가 위 두 변환과 bounce buffer까지 고려해서 **돌려준다.**

### 1.2 정의

| 이름 | C 타입 | 누가 쓰나 | 이 랩에서 예 |
|---|---|---|---|
| 가상 주소 (VA) | `void *` | CPU (커널 코드) | `ffff00003cc60000`(선형 매핑), `ffff80008006d000`(vmalloc 영역) |
| 물리 주소 (PA) | `phys_addr_t` | MMU 출력, DRAM | `0x7cc60000` (virt의 RAM은 `0x4000_0000`부터) |
| 버스 주소 / IOVA | `dma_addr_t` | 장치 (레지스터·디스크립터에 기록) | IOMMU 없음: `0x7cc60000`(=PA), SMMU: `0x0fffc000` |

- `dma_addr_t`는 `CONFIG_ARCH_DMA_ADDR_T_64BIT`이면 64비트다(arm64는 항상). 출력할 때는 `%pad`에 **포인터**를 넘긴다(`&dma`).
- `phys_addr_t`는 `%pa`(역시 포인터)로 찍는다.
- 실패 값은 `DMA_MAPPING_ERROR`(모든 비트 1)이고, 직접 비교하지 말고 `dma_mapping_error(dev, addr)`로 검사한다.

### 1.3 실습 장치 — QEMU `edu`

QEMU의 `edu`(PCI ID `1234:11e8`)는 교육용 가상 장치인데, **진짜 DMA 엔진**을 갖고 있다. 레지스터는 BAR0(1 MiB MMIO)에 있다. 아래 표는 QEMU의 `docs/specs/edu.rst`·`hw/misc/edu.c` 내용(기억에 의존, 이 VM에는 QEMU 소스가 없다)을 이 노트의 실험으로 확인한 것이다. 확인하지 못한 항목은 따로 표시했다.

| 오프셋 | 크기 | 이름 | 동작 |
|---|---|---|---|
| `0x24` | 32 | interrupt status | 올라간 인터럽트 비트 (DMA 완료 = `0x100`) |
| `0x64` | 32 | interrupt ack | 쓴 비트를 status에서 지움 |
| `0x80` | 64 | DMA source | 원본 주소 |
| `0x88` | 64 | DMA destination | 목적지 주소 |
| `0x90` | 64 | DMA count | 바이트 수 |
| `0x98` | 64 | DMA command | bit0 시작(끝나면 0), bit1 방향(0: RAM→edu, 1: edu→RAM), bit2 완료 시 IRQ |

- 장치 쪽 메모리는 **`0x40000`부터 4 KiB** 버퍼 하나뿐이다. RAM→edu면 목적지가, edu→RAM이면 원본이 이 범위 안이어야 한다. 넘으면 QEMU가 `hw_error()`로 **에뮬레이터 전체를 죽인다**고 알고 있다(소스 기억, 일부러 실행해 보지는 않았다). 그래서 헬퍼에서 길이를 먼저 검사한다.
- DMA는 즉시 끝나지 않는다. QEMU가 타이머로 **약 100 ms 뒤에** 복사를 수행한다(§8에서 측정으로 확인). 진짜 하드웨어처럼 "시작 → 나중에 완료 IRQ" 순서를 볼 수 있다.
- 장치의 주소 폭은 QEMU 속성 `dma_mask`로 정하고, 기본값은 **28비트**(`0x0fffffff`, 256 MiB)다. 넘는 비트는 **조용히 잘라 버린다**(§5.3).
- 인터럽트는 MSI가 켜져 있으면 MSI, 아니면 INTx다.

예제 1 — `edu` 장치가 PCI에 어떻게 보이는지. 게스트를 부팅하는 스크립트(Lima VM 안에서 실행)와 게스트 안 관찰 스크립트다.

```sh
#!/bin/sh
# boot.sh <guest-script> — env: K=lab|h9 (kernel), MACH=virt opts, MEM=MiB, EDU=edu opts, APP=extra cmdline, DTB=dtb
set -e
DTBARG=""; [ -n "$DTB" ] && DTBARG="-dtb $DTB"
W=/var/tmp/H9; S=/Users/donh/.elinux_scratch/H9
K=${K:-h9}; MACH=${MACH:-virt}; MEM=${MEM:-1024}; EDU=${EDU:-edu}; APP=${APP:-}
if [ "$K" = lab ]; then IMG=/var/lab/out/Image; MODD=$W/mod_lab; else IMG=$W/build/arch/arm64/boot/Image; MODD=$W/mod; fi
rm -rf $W/r && mkdir -p $W/r && cp -a /var/lab/build/rootfs/. $W/r/
cp $S/*.sh $W/r/ 2>/dev/null; cp $MODD/*.ko $W/r/ 2>/dev/null || true
(cd $W/r && find . | cpio -o -H newc --quiet | gzip) > $W/i.gz
timeout 300 qemu-system-aarch64 -machine $MACH -cpu cortex-a57 -m $MEM -smp 2 -nographic \
  -kernel $IMG -initrd $W/i.gz -device $EDU $DTBARG \
  -append "console=ttyAMA0 quiet $APP LAB_CMD=sh~/$1"
```

```sh
#!/bin/sh
# ex_lspci.sh — edu 장치의 BAR, IRQ, IOMMU 그룹
for d in /sys/bus/pci/devices/*; do echo "$(basename $d) $(cat $d/vendor):$(cat $d/device) class=$(cat $d/class)"; done
E=/sys/bus/pci/devices/0000:00:02.0

  cat /sys/kernel/iommu_groups/$G/reserved_regions
else
  echo "edu: no iommu_group"
fi
dmesg | grep -E "smmu|iommu:|software IO TLB: mapped"
```

출력에서 볼 것:

- `00:02.0 1234:11e8`이 edu다. BAR0가 `0x10000000`부터 1 MiB(PCIe MMIO 창 안). `00:01.0`(`1af4:1000`)은 QEMU가 기본으로 꽂는 virtio-net이다.
- SMMU가 있으면 장치마다 **iommu_group**이 생기고 `type=DMA`(DMA API가 IOVA를 관리하는 변환 도메인)다. `reserved_regions`의 `msi` 구간(`0x08000000`, GICv2m의 MSI doorbell)은 IOVA 할당에서 빠진다. 장치가 MSI를 쏘려면 그 주소가 매핑되어 있어야 하기 때문이다.
- SMMU의 명령 큐(cmdq)와 이벤트 큐(evtq)가 보인다. SSD 컨트롤러의 SQ/CQ와 같은 구조다. 커널이 cmdq로 "TLB 무효화" 같은 명령을 넣고, SMMU는 fault를 evtq로 올린다(§7.4).
- `software IO TLB: mapped ... (1MB)` — SWIOTLB(§5)가 1 MiB로 잡혔다.

### 1.4 공용 헤더 — edu 레지스터와 DMA 한 번

이후 모든 모듈이 쓰는 헤더다. 앞부분은 레지스터 정의, IRQ 핸들러, "DMA 한 번" 함수다.

```c
/* h9_edu.h (1/2) — QEMU edu PCI 장치(1234:11e8) 레지스터와 공용 헬퍼 */
#include <linux/module.h>
#include <linux/pci.h>
#include <linux/dma-mapping.h>
#include <linux/dma-map-ops.h>	/* dev_is_dma_coherent */
#include <linux/interrupt.h>
#include <linux/completion.h>
#include <linux/iopoll.h>

#define EDU_IRQ_STATUS 0x24
#define EDU_IRQ_ACK    0x64
#define EDU_DMA_SRC    0x80		/* 64-bit */
#define EDU_DMA_DST    0x88
#define EDU_DMA_CNT    0x90
#define EDU_DMA_CMD    0x98
#define EDU_CMD_START  0x1		/* 끝나면 장치가 0으로 내린다 */
#define EDU_CMD_TO_RAM 0x2		/* 0: RAM→edu, 1: edu→RAM */
#define EDU_CMD_IRQ    0x4		/* 끝나면 IRQ(status 0x100) */
#define EDU_BUF        0x40000		/* 장치 내부 4 KiB 버퍼의 "주소" */
#define EDU_BUF_SZ     4096

struct edu { struct pci_dev *pdev; void __iomem *bar; struct completion done; };

static irqreturn_t edu_isr(int irq, void *p)
{
	struct edu *e = p;
	u32 st = readl(e->bar + EDU_IRQ_STATUS);

	if (!st)
		return IRQ_NONE;
	writel(st, e->bar + EDU_IRQ_ACK);
	complete(&e->done);
	return IRQ_HANDLED;
}

/* 한 번의 DMA. ram = 장치에게 줄 dma_addr_t, off = edu 버퍼 안 오프셋 */
static inline int edu_dma(struct edu *e, dma_addr_t ram, u32 off, u32 len, bool to_ram, bool irq)
{
	u64 v, cmd = EDU_CMD_START | (to_ram ? EDU_CMD_TO_RAM : 0) | (irq ? EDU_CMD_IRQ : 0);

	if (off + len > EDU_BUF_SZ)	/* 넘으면 QEMU가 hw_error로 죽는다 */
		return -EINVAL;
	reinit_completion(&e->done);
	writeq(to_ram ? EDU_BUF + off : ram, e->bar + EDU_DMA_SRC);
	writeq(to_ram ? ram : EDU_BUF + off, e->bar + EDU_DMA_DST);
	writeq(len, e->bar + EDU_DMA_CNT);
	writeq(cmd, e->bar + EDU_DMA_CMD);	/* doorbell: writeq 안에 배리어 (F5) */
	if (irq)
		return wait_for_completion_timeout(&e->done, 2 * HZ) ? 0 : -ETIMEDOUT;
	return readq_poll_timeout(e->bar + EDU_DMA_CMD, v, !(v & EDU_CMD_START), 20, 2000000);
}
```

뒷부분은 probe 공통 처리다.

```c
/* h9_edu.h (2/2) — probe 공통: BAR0 매핑 + bus master + DMA mask + IRQ 1개 */
static int edu_setup(struct pci_dev *pdev, struct edu *e, int mask_bits)
{
	int ret = pcim_enable_device(pdev);

	if (ret)
		return ret;
	e->pdev = pdev;
	init_completion(&e->done);
	e->bar = pcim_iomap_region(pdev, 0, KBUILD_MODNAME);
	if (IS_ERR(e->bar))
		return PTR_ERR(e->bar);
	pci_set_master(pdev);			/* PCI_COMMAND_MASTER — 없으면 DMA가 안 나간다 */
	ret = dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(mask_bits));
	dev_info(&pdev->dev, "dma_set_mask_and_coherent(%d bits) = %d, coherent=%d\n",
		 mask_bits, ret, dev_is_dma_coherent(&pdev->dev));
	if (ret)
		return ret;
	ret = pci_alloc_irq_vectors(pdev, 1, 1, PCI_IRQ_ALL_TYPES);
	if (ret < 0)
		return ret;
	return devm_request_irq(&pdev->dev, pci_irq_vector(pdev, 0), edu_isr, 0, KBUILD_MODNAME, e);
}

static const struct pci_device_id edu_ids[] = { { PCI_DEVICE(0x1234, 0x11e8) }, { } };
MODULE_DEVICE_TABLE(pci, edu_ids);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H9 DMA API demo on QEMU edu");
```

읽는 법:

- `edu_dma()`의 마지막 `writeq(cmd, ...)`가 **doorbell**이다. F5에서 본 것처럼 arm64의 `writeq()`(= `writel()` 계열)는 쓰기 전에 `dmb oshst`(`__iowmb()`)를 넣는다. 그래서 그 앞의 일반 메모리 쓰기(버퍼 채우기)가 장치에게 먼저 보인다. 디스크립터를 coherent 메모리에 쓰고 owner 비트를 넘기는 링 구조라면 그 사이에 `dma_wmb()`가 하나 더 필요하다(F5 §6).
- `pci_set_master()`를 빼면 PCI command 레지스터의 Bus Master Enable이 0이라서 장치가 DMA를 낼 수 없다. QEMU도 이것을 흉내 낸다. Don이 PCIe bring-up에서 "BME 안 켜서 DMA가 안 나감"을 겪었다면 같은 비트다.
- `pcim_*`, `devm_*`는 드라이버가 떠날 때 자동 해제된다(G3). `pcim_iomap_region()`은 6.x 후반의 이름이고, 예전 코드의 `pcim_iomap_regions()`는 폐기 예정이다.
- `PCI_IRQ_ALL_TYPES`는 MSI-X → MSI → INTx 순서로 시도한다(H11).

### 1.5 흔한 함정

- **`virt_to_phys(buf)`를 장치 레지스터에 쓰기**: IOMMU가 없고 오프셋도 없는 보드에서는 우연히 동작한다. 같은 코드를 IOMMU가 켜진 보드(i.MX8, Jetson, 대부분의 서버)에 올리면 SMMU fault가 나고(§7.4), 32비트 장치에 4 GiB 위 메모리를 주면 주소가 잘린다(§5.3).
- **`dma_addr_t`를 `u32`에 담기**: 레지스터가 32비트라도 변수는 `dma_addr_t`로 두고, 레지스터에 쓸 때 `lower_32_bits()`/`upper_32_bits()`로 나눈다. mask가 32비트면 상위가 0임이 보장된다.
- **`%llx`로 `dma_addr_t` 찍기**: 32비트 아키텍처에서 크기가 달라 경고·쓰레기 값이 난다. `%pad` + 포인터.

## 2. coherent DMA — `dma_alloc_coherent()`와 `dma_pool`

### 2.1 직관 — "양쪽이 언제든 보는 공유 칠판"

디스크립터 링, 완료 큐, 상태 블록처럼 **CPU와 장치가 동시에, 오래, 수시로** 읽고 쓰는 메모리가 있다. Don의 SSD 펌웨어에서는 이런 것을 MPU로 non-cacheable 영역에 두었다. Linux의 답이 `dma_alloc_coherent()`다.

- 반환값: CPU가 쓸 **가상 주소**. 인자 `dma_handle`: 장치에게 줄 **`dma_addr_t`**. 한 번에 두 주소를 준다.
- 보장: CPU가 쓴 값이 (배리어 순서만 맞으면) 장치에게 보이고, 장치가 쓴 값이 CPU에게 보인다. **sync 호출이 필요 없다.**
- 어떻게: 하드웨어가 코히어런트(캐시 스누핑)면 보통 캐시 가능한 메모리를 그대로 준다. 아니면 **캐시를 끈 별도 매핑**(arm64에서 Normal Non-Cacheable)을 만들어 준다(F10 §6.3).
- 단위: 페이지 단위로 할당된다. 64바이트짜리를 여러 개 원하면 `dma_pool`을 쓴다.

메모리를 어디서 가져오는지(장치 전용 풀 → IOMMU → CMA → 버디)는 F10 §9.1에서 다뤘다. 여기서는 **장치와 주고받는 쪽**을 본다.

### 2.2 예제 2 — coherent 버퍼로 RAM → edu → RAM 왕복 (IRQ 완료)

무엇을 확인하나: coherent 버퍼 2페이지를 받아 앞 페이지를 패턴으로 채우고, edu DMA로 RAM → 장치 → 뒤 페이지로 옮긴 뒤 비교한다. 완료는 IRQ(MSI)로 받는다. 뒤에서 `dma_pool`로 64바이트 디스크립터 3개를 받아 주소를 찍는다.

```c
// h9_coh.c — coherent 버퍼로 RAM→edu→RAM 왕복 + dma_pool 디스크립터
#include "h9_edu.h"
#include <linux/dmapool.h>

static int bits = 32;
module_param(bits, int, 0444);

static int h9_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct device *dev = &pdev->dev;
	struct edu *e = devm_kzalloc(dev, sizeof(*e), GFP_KERNEL);
	struct dma_pool *pool;
	dma_addr_t dma, d[3];
	void *desc[3];
	u8 *buf;
	int i, ret;

	if (!e)
		return -ENOMEM;
	ret = edu_setup(pdev, e, bits);
	if (ret)
		return ret;
	dev_info(dev, "irq %d (%s)\n", pci_irq_vector(pdev, 0), pdev->msi_enabled ? "MSI" : "INTx");
	buf = dma_alloc_coherent(dev, 2 * PAGE_SIZE, &dma, GFP_KERNEL);	/* [src | dst] */
	if (!buf)
		return -ENOMEM;
	for (i = 0; i < PAGE_SIZE; i++)
		buf[i] = i ^ 0x5a;
	memset(buf + PAGE_SIZE, 0, PAGE_SIZE);
	dev_info(dev, "coherent va=%px dma=%pad\n", buf, &dma);
	ret = edu_dma(e, dma, 0, PAGE_SIZE, false, true);		/* RAM → edu (IRQ) */
	if (!ret)
		ret = edu_dma(e, dma + PAGE_SIZE, 0, PAGE_SIZE, true, true);	/* edu → RAM */
	dev_info(dev, "round trip ret=%d, dst %s src\n", ret,
		 memcmp(buf, buf + PAGE_SIZE, PAGE_SIZE) ? "!=" : "==");
	dma_free_coherent(dev, 2 * PAGE_SIZE, buf, dma);

	/* 작은 디스크립터는 dma_pool: 64 B, 64 B 정렬 */
	pool = dma_pool_create("h9_desc", dev, 64, 64, 0);
	if (!pool)
		return -ENOMEM;
	for (i = 0; i < 3; i++) {
		desc[i] = dma_pool_alloc(pool, GFP_KERNEL, &d[i]);
		dev_info(dev, "desc[%d] va=%px dma=%pad\n", i, desc[i], &d[i]);
	}
	for (i = 0; i < 3; i++)
		dma_pool_free(pool, desc[i], d[i]);
	dma_pool_destroy(pool);
	return 0;
}

static void h9_remove(struct pci_dev *pdev) { }
static struct pci_driver h9_drv = {
	.name = "h9_coh", .id_table = edu_ids, .probe = h9_probe, .remove = h9_remove,
};
module_pci_driver(h9_drv);
```

edu의 주소 폭을 32비트로 늘려서(`-device edu,dma_mask=0xffffffff`) 돌린다. 이유는 §5에서 본다.

### 2.4 coherent를 언제 쓰나 — 그리고 비용

| 쓰면 좋은 곳 | 이유 |
|---|---|
| 디스크립터 링, 완료 큐, 이벤트 링 | CPU와 장치가 수시로 같은 줄을 읽고 씀. sync를 매번 부르면 오히려 비쌈 |
| 장치가 폴링하는 상태 블록·mailbox | "장치가 언제 읽을지 모름" — 소유권을 넘길 시점이 없음 |
| 작은 명령 버퍼 (`dma_pool`) | 페이지 단위 할당 낭비를 피함 |

| 쓰지 말아야 할 곳 | 이유 |
|---|---|
| 큰 데이터 버퍼(프레임, 패킷 payload)를 CPU가 많이 읽을 때 | 비코히어런트 SoC에서는 **캐시 안 되는 메모리**라 CPU 읽기가 느리다. memcpy·체크섬이 수 배 느려진다 |
| 유저 버퍼·페이지 캐시처럼 이미 있는 메모리 | coherent는 "새로 할당"하는 API. 기존 메모리는 streaming으로 매핑 |
| 인터럽트 문맥에서 큰 할당 | `GFP_ATOMIC`이면 CMA를 못 쓰고 atomic pool(랩: 128 KiB)에서만 나온다 |

그래서 실제 드라이버는 거의 항상 **둘을 섞는다**: 링은 coherent, 각 디스크립터가 가리키는 데이터 버퍼는 streaming. NVMe 드라이버가 SQ/CQ는 `dma_alloc_coherent()`, PRP 리스트는 `dma_pool`, 데이터는 블록 계층이 매핑해 준 streaming 주소를 쓰는 것이 정확히 이 모양이다.

### 2.5 흔한 함정

- **coherent 메모리에서도 순서는 보장되지 않는다.** "캐시 문제 없음"이지 "순서 문제 없음"이 아니다. 디스크립터 내용을 쓰고 owner 비트를 쓰기 전에 `dma_wmb()`, 장치가 쓴 상태 비트를 읽고 나서 내용을 읽기 전에 `dma_rmb()`(F5).
- **`dma_free_coherent()`를 인터럽트 문맥에서 부르기**: vunmap이 필요할 수 있어 금지다(`WARN_ON(irqs_disabled())` 류 경고).
- **coherent 버퍼를 `remap_pfn_range`로 유저에 노출**: 커널 쪽 매핑과 캐시 속성이 어긋난다. `dma_mmap_coherent()`를 쓴다(G5).

## 3. streaming DMA — map/unmap, 방향, 소유권

### 3.1 직관 — "버퍼를 장치에게 잠깐 빌려 준다"

패킷 하나, 카메라 프레임 하나, 블록 I/O 하나처럼 **한 번의 전송에 쓰이고 끝나는** 버퍼는 이미 어딘가에 있다(`kmalloc` 버퍼, 페이지 캐시, 유저 페이지). 이걸 coherent 메모리로 복사하는 대신, **그 자리에서 장치에게 빌려 준다**. 이것이 streaming 매핑이다.

빌려 주는 동안의 규칙이 **소유권(ownership)**이다. Don의 SSD 펌웨어에서 "DMA가 도는 동안 그 버퍼는 건드리지 않는다, 끝나면 invalidate하고 읽는다"를 지켰다면 이미 아는 규칙이다. Linux는 그걸 API 호출 순서로 강제한다.

### 3.2 정의 — API와 방향

| API | 무엇을 매핑하나 | 비고 |
|---|---|---|
| `dma_map_single(dev, va, size, dir)` | 선형 매핑 주소(`kmalloc`, `__get_free_pages`) | vmalloc·스택 주소는 **안 된다** |
| `dma_map_page(dev, page, off, size, dir)` | `struct page` + 오프셋 | highmem·유저 페이지 등 |
| `dma_map_sg` / `dma_map_sgtable` | 흩어진 페이지 목록 | §6 |
| `dma_map_resource(dev, phys, size, dir, attrs)` | 다른 장치의 MMIO(예: FIFO 레지스터) | 슬레이브 DMA·P2P, 캐시 작업 없음 |
| `dma_unmap_*` | 위와 짝 | **같은 size, 같은 dir** 로 |
| `dma_sync_single_for_cpu` / `_for_device` | 매핑을 유지한 채 소유권만 넘김 | 재사용 버퍼(RX 링) |

방향(`enum dma_data_direction`)은 **데이터가 흐르는 방향**이다. 캐시 작업을 고르는 근거라서 정확해야 한다.

| 방향 | 의미 | 예 | map 때 (비코히어런트) | unmap/for_cpu 때 |
|---|---|---|---|---|
| `DMA_TO_DEVICE` | 메모리 → 장치 (장치는 읽기만) | TX 패킷, 쓰기 I/O, 디스플레이 | clean(write-back) | 아무것도 안 함 |
| `DMA_FROM_DEVICE` | 장치 → 메모리 (장치는 쓰기만) | RX 패킷, 읽기 I/O, 카메라 | clean (arm64 구현) | invalidate |
| `DMA_BIDIRECTIONAL` | 둘 다 | 장치가 읽고 고쳐 쓰는 버퍼 | clean | invalidate |
| `DMA_NONE` | 디버그용 | — | 쓰면 `BUG_ON` | — |

`DMA_FROM_DEVICE`인데 map 때 왜 invalidate가 아니라 clean인가? 그 버퍼에 dirty 캐시 라인이 남아 있으면, DMA가 메모리에 쓴 **뒤에** 캐시가 그 라인을 evict하면서 옛 값으로 덮어쓸 수 있다. 먼저 clean해서 dirty 라인을 없애 두고, DMA 뒤 `for_cpu`에서 invalidate해서 (투기적 로드로 다시 들어온) 옛 라인을 버린다. 이 두 단계가 arm64 `arch/arm64/mm/dma-mapping.c`의 실제 구현이다(§4.2).

### 3.3 예제 4 — 일회성 map/unmap과 재사용 버퍼의 sync

무엇을 확인하나: (1) TX 버퍼를 채우고 `DMA_TO_DEVICE`로 map → 장치가 읽음 → unmap. (2) RX 버퍼를 `DMA_FROM_DEVICE`로 **한 번만** map하고, 세 번 반복하며 `sync_for_cpu`(CPU가 검사) ↔ `sync_for_device`(다시 장치에게)로 소유권만 넘긴다. 네트워크 드라이버의 RX 링이 이 모양이다.

```c
// h9_stream.c — streaming 매핑: map → DMA → unmap, 그리고 재사용 버퍼의 sync
#include "h9_edu.h"
#include <linux/slab.h>

static int bits = 32;
module_param(bits, int, 0444);

static int h9_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct device *dev = &pdev->dev;
	struct edu *e = devm_kzalloc(dev, sizeof(*e), GFP_KERNEL);
	u8 *tx = devm_kmalloc(dev, PAGE_SIZE, GFP_KERNEL);
	u8 *rx = devm_kmalloc(dev, PAGE_SIZE, GFP_KERNEL);
	dma_addr_t dtx, drx;
	int i, n, ret;

	if (!e || !tx || !rx)
		return -ENOMEM;
	ret = edu_setup(pdev, e, bits);
	if (ret)
		return ret;
	/* (1) 일회성: TX 버퍼를 채운 뒤 map(TO_DEVICE) → 장치가 읽음 → unmap */
	memset(tx, 0xa5, PAGE_SIZE);
	dtx = dma_map_single(dev, tx, PAGE_SIZE, DMA_TO_DEVICE);
	if (dma_mapping_error(dev, dtx))
		return -ENOMEM;
	dev_info(dev, "tx va=%px phys=%pa dma=%pad\n", tx, &(phys_addr_t){virt_to_phys(tx)}, &dtx);
	ret = edu_dma(e, dtx, 0, PAGE_SIZE, false, true);
	dma_unmap_single(dev, dtx, PAGE_SIZE, DMA_TO_DEVICE);	/* 이제 CPU가 다시 주인 */

	/* (2) 재사용: RX를 한 번만 map(FROM_DEVICE)하고 매 회 sync로 소유권을 넘긴다 */
	drx = dma_map_single(dev, rx, PAGE_SIZE, DMA_FROM_DEVICE);
	if (dma_mapping_error(dev, drx))
		return -ENOMEM;
	for (i = 0; i < 3 && !ret; i++) {		/* 여기서 주인 = 장치 */
		ret = edu_dma(e, drx, 0, PAGE_SIZE, true, true);		/* edu → rx */
		dma_sync_single_for_cpu(dev, drx, PAGE_SIZE, DMA_FROM_DEVICE);    /* → CPU */
		for (n = 0; n < PAGE_SIZE && rx[n] == 0xa5; n++)
			;
		dev_info(dev, "round %d: ret=%d rx[0]=%#x, %d/%lu bytes ok\n", i, ret, rx[0], n, PAGE_SIZE);
		memset(rx, 0, PAGE_SIZE);	/* CPU가 주인일 때만 만진다 */
		dma_sync_single_for_device(dev, drx, PAGE_SIZE, DMA_FROM_DEVICE); /* → 장치 */
	}
	dma_unmap_single(dev, drx, PAGE_SIZE, DMA_FROM_DEVICE);
	return ret;
}

static void h9_remove(struct pci_dev *pdev) { }
static struct pci_driver h9_drv = {
	.name = "h9_stream", .id_table = edu_ids, .probe = h9_probe, .remove = h9_remove,
};
module_pci_driver(h9_drv);
```

- streaming은 **CPU 주소가 바뀌지 않는다.** coherent=0이어도 `tx`는 선형 매핑 그대로(`ffff0000…`)다. coherent API와 달리 새 매핑을 만들지 않고, 대신 map/sync 때 **캐시 작업**으로 일관성을 맞춘다. 그 작업이 실제로 불리는 것을 §3.5에서 트레이스로 본다.
- `tx`의 주소가 `…080`으로 끝난다. `devm_kmalloc()`은 앞에 devres 헤더를 두지만 데이터를 `ARCH_DMA_MINALIGN`(arm64: 128바이트) 경계에 맞춘다. 그래서 이 버퍼는 다른 객체와 **캐시 라인을 공유하지 않는다**. 이게 왜 중요한지는 §4.3.
- 각 라운드가 0.1초 간격 — edu의 DMA 지연이다.
- 두 실행 모두 데이터가 맞다. 그런데 QEMU TCG는 **캐시를 모델링하지 않는다**(CPU 쓰기가 즉시 "메모리"에 반영된다). 그래서 이 랩에서는 sync를 빼먹어도 데이터가 맞게 나온다. 이게 §3.6의 함정이다.

### 3.4 sync 패턴 네 가지

| 패턴 | 순서 | 쓰는 곳 |
|---|---|---|
| 일회성 TX | 채우기 → `map(TO)` → DMA → 완료 → `unmap(TO)` | 패킷 송신, 블록 쓰기 |
| 일회성 RX | `map(FROM)` → DMA → 완료 → `unmap(FROM)` → 읽기 | 블록 읽기 |
| 재사용 RX 링 | `map(FROM)` 한 번 → [DMA → 완료 → `sync_for_cpu` → 읽기/복사 → `sync_for_device`] 반복 → 종료 때 `unmap` | NIC RX 링, 센서 FIFO 링 |
| 재사용 TX 버퍼 | `map(TO)` 한 번 → [`sync_for_cpu` → 채우기 → `sync_for_device` → DMA → 완료] 반복 | 고정 명령 버퍼, 오디오 링 |

`map`/`unmap`은 IOMMU 페이지 테이블 갱신·IOTLB 무효화·SWIOTLB 슬롯 할당 같은 비싼 일을 포함할 수 있다(§8 측정에서 4 KiB 한 쌍이 0.4~6.8 µs). `sync`는 캐시 작업(또는 bounce 복사)만 한다. 그래서 고속 경로에서는 **한 번 매핑해 두고 sync로 소유권만 넘기는** 재사용 패턴을 쓴다. 네트워크 드라이버의 page_pool이 이 일을 대신 해 준다.

부분 sync도 된다. 64바이트 헤더만 먼저 보고 싶으면 `dma_sync_single_for_cpu(dev, drx, 64, DMA_FROM_DEVICE)`. 범위가 작을수록 캐시 작업이 싸다. 오프셋이 있으면 `dma_sync_single_range_for_cpu(dev, drx, off, len, dir)`.

출력에서 볼 것:

- 6.18에서는 `dma_map_single()`/`dma_map_page()`가 모두 **`dma_map_phys()`**로 모인다(이벤트 이름도 `dma_map_phys`). 예전 커널(6.16 무렵까지)의 이벤트·함수 이름은 `dma_map_page`였다 — 버전에 따라 다르다.
- 그림 2의 화살표가 그대로 보인다: map → `arch_sync_dma_for_device`(clean), `sync_for_cpu` → `arch_sync_dma_for_cpu`(invalidate), `sync_for_device` → 다시 clean, unmap → `arch_sync_dma_for_cpu`.
- TO_DEVICE unmap에서도 `arch_sync_dma_for_cpu`가 **불리기는** 한다. 다만 함수 첫머리에서 `if (dir == DMA_TO_DEVICE) return;`으로 바로 돌아온다(§4.2 소스).
- `dma_map_phys` 이벤트가 `arch_sync_dma_for_device` **뒤에** 찍힌다. tracepoint가 매핑을 다 만든 다음에 호출되기 때문이다.
- 코히어런트 장치는 이벤트만 있고 캐시 작업이 없다. "코히어런트면 sync가 공짜"의 실측이다. 그래도 호출 자체는 빼면 안 된다 — SWIOTLB가 끼면 바로 이 자리에서 복사가 일어난다(§5.4).

### 3.6 소유권 위반은 이 랩에서 재현되지 않는다 — 정직한 한계

가장 유명한 버그는 "map한 뒤에 CPU가 버퍼를 고친다"이다.

```c
d = dma_map_single(dev, buf, len, DMA_TO_DEVICE);	/* 여기서 clean */
buf[0] = 0x99;						/* 장치가 주인인데 CPU가 씀 */
start_dma(d);						/* 장치는 메모리의 옛 값을 읽을 수 있다 */
```

실제 비코히어런트 SoC에서는 `buf[0] = 0x99`가 **캐시에만** 들어가고 DRAM에는 옛 값이 있으므로 장치가 옛 값을 읽는다. FROM_DEVICE에서는 반대다. DMA 도중 CPU가 그 버퍼를 읽으면(또는 투기적 로드가 일어나면) 옛 값이 캐시 라인으로 들어온다. `sync_for_cpu`/unmap의 invalidate가 그 라인을 버려 주므로 규칙대로 하면 괜찮지만, **sync 없이** 읽으면 그 옛 값을 본다.

이 랩에서 이걸 직접 보여 줄 수 없는 이유 두 가지:

1. **QEMU TCG는 데이터 캐시를 모델링하지 않는다.** CPU 쓰기가 즉시 게스트 RAM에 반영되고 edu는 그 RAM을 읽는다. 그래서 DT를 비코히어런트로 바꿔도(§2.3, §3.3) 캐시 작업 함수는 불리지만, 빼먹어도 데이터는 맞게 나온다. 아래 §9의 `bug=6` 실행에서도 경고 없이 끝났다.
2. **`CONFIG_DMA_API_DEBUG`도 이 버그는 못 잡는다.** DMA API 디버그는 "API 호출의 짝과 인자"를 검사하지, CPU의 메모리 접근을 감시하지 않는다(§9에서 `bug=6`은 `error_count=0`).

그래서 실제로는 (1) 코드 리뷰에서 "map 뒤 CPU 접근"을 찾는 습관, (2) 진짜 비코히어런트 보드(예: 많은 i.MX·Rockchip·STM32MP 계열의 일부 마스터)에서의 테스트, (3) KCSAN/KMSAN 같은 도구 일부(KMSAN은 `kmsan_handle_dma()` 훅이 있다)가 답이다. 이 문단의 "실제 SoC에서는 깨진다"는 **랩에서 실행해 확인한 것이 아니라** 아키텍처 규칙에서 나온 설명이다.

## 4. 캐시 관리 — 비코히어런트 arm64에서 실제로 하는 일

### 4.1 직관 — clean과 invalidate

- **clean**(write-back): dirty 캐시 라인을 메모리에 내려 쓴다. 라인은 캐시에 남아도 된다. "장치가 읽기 전에 CPU가 쓴 걸 메모리로".
- **invalidate**: 캐시 라인을 버린다. "장치가 쓴 뒤 CPU가 옛 캐시 값을 보지 않게".
- **PoC**(Point of Coherency): 모든 관찰자(CPU, DMA 마스터)가 같은 값을 보는 지점. 보통 DRAM 컨트롤러 직전. DMA용 캐시 작업은 PoC까지 해야 한다(`dc cvac`, `dc ivac`의 `c`가 PoC).

Don이 Cortex-R에서 쓰던 `SCB_CleanDCache_by_Addr` / `SCB_InvalidateDCache_by_Addr`(CMSIS)와 같은 일이다. 다른 점은 드라이버가 직접 부르지 않고 **DMA API가 방향을 보고 골라 부른다**는 것.

### 4.2 소스 — `arch/arm64/mm/dma-mapping.c`와 `cache.S`

랩 소스(6.18.55)에서 그대로 옮긴다.

```c
/* arch/arm64/mm/dma-mapping.c */
void arch_sync_dma_for_device(phys_addr_t paddr, size_t size,
			      enum dma_data_direction dir)
{
	unsigned long start = (unsigned long)phys_to_virt(paddr);

	dcache_clean_poc(start, start + size);
}

void arch_sync_dma_for_cpu(phys_addr_t paddr, size_t size,
			   enum dma_data_direction dir)
{
	unsigned long start = (unsigned long)phys_to_virt(paddr);

	if (dir == DMA_TO_DEVICE)
		return;

	dcache_inval_poc(start, start + size);
}

void arch_dma_prep_coherent(struct page *page, size_t size)
{
	unsigned long start = (unsigned long)page_address(page);

	dcache_clean_poc(start, start + size);
}
```

```text
/* arch/arm64/mm/cache.S 발췌 — dcache_inval_poc */
	tst	x1, x3				// end cache line aligned?
	bic	x1, x1, x3
	b.eq	1f
	dc	civac, x1			// clean & invalidate D / U line
1:	tst	x0, x3				// start cache line aligned?
	bic	x0, x0, x3
	b.eq	2f
	dc	civac, x0			// clean & invalidate D / U line
	b	3f
2:	dc	ivac, x0			// invalidate D / U line
3:	add	x0, x0, x2
	cmp	x0, x1
	b.lo	2b
	dsb	sy
/* dcache_clean_poc는 dcache_by_line_op cvac, sy — 줄마다 dc cvac, 끝에 dsb sy */
```

그리고 이 함수들을 부르는 쪽(`kernel/dma/direct.h`의 `dma_direct_map_phys()` 발췌):

```c
	if (!dev_is_dma_coherent(dev) &&
	    !(attrs & (DMA_ATTR_SKIP_CPU_SYNC | DMA_ATTR_MMIO)))
		arch_sync_dma_for_device(phys, size, dir);
	return dma_addr;
```

| DMA API 호출 | 비코히어런트 arm64 | 실제 명령 |
|---|---|---|
| `dma_map_*`, `sync_*_for_device` (모든 방향) | `arch_sync_dma_for_device` | 줄마다 `dc cvac` + `dsb sy` |
| `dma_unmap_*`, `sync_*_for_cpu` (TO_DEVICE) | `arch_sync_dma_for_cpu` → 즉시 return | 없음 |
| `dma_unmap_*`, `sync_*_for_cpu` (FROM, BIDI) | `arch_sync_dma_for_cpu` | 줄마다 `dc ivac`, 양 끝이 걸치면 `dc civac` + `dsb sy` |
| `dma_alloc_coherent` (비코히어런트) | `arch_dma_prep_coherent` + 캐시 끈 재매핑 | `dc cvac` 후 Normal-NC 매핑 |
| 코히어런트 장치 | 전부 생략 | — |

`dcache_inval_poc`가 **양 끝 부분 라인을 `civac`(clean+invalidate)로** 처리하는 데 주목하자. 버퍼가 캐시 라인 중간에서 시작하면 그 라인의 앞부분은 다른 객체의 데이터다. 그냥 invalidate하면 그 객체의 dirty 데이터를 날려 버린다. 그래서 clean도 같이 하는데, 그러면 이번엔 DMA가 쓴 버퍼 쪽 데이터 일부가 CPU의 옛 값으로 덮일 수 있다. 결론: **DMA 버퍼는 캐시 라인을 다른 것과 공유하면 안 된다.** 이게 §4.3이다.

### 4.3 예제 6 — 작은 `kmalloc` 버퍼는 bounce된다

무엇을 확인하나: 비코히어런트 장치에 크기가 다른 `kmalloc` 버퍼를 `DMA_FROM_DEVICE`로 map하면 어떤 것은 그 자리에서, 어떤 것은 SWIOTLB로 bounce되는지.

배경: 예전 arm64는 `kmalloc`의 최소 정렬을 128바이트(`ARCH_DMA_MINALIGN`)로 강제해서 "kmalloc 버퍼는 DMA-safe"를 보장했다. 6.5 무렵부터 메모리 낭비를 줄이려고 `kmalloc-8`, `kmalloc-16`… 같은 작은 캐시를 다시 허용하고, 대신 `CONFIG_DMA_BOUNCE_UNALIGNED_KMALLOC=y`(랩 설정에 있음)로 **캐시 라인에 맞지 않는 작은 kmalloc 버퍼를 비코히어런트 장치에 FROM/BIDI로 매핑할 때 SWIOTLB로 bounce**한다. 판단 함수(`include/linux/dma-map-ops.h`):

```c
static inline bool dma_kmalloc_needs_bounce(struct device *dev, size_t size,
					    enum dma_data_direction dir)
{
	return !dma_kmalloc_safe(dev, dir) && !dma_kmalloc_size_aligned(size);
}
/* dma_kmalloc_safe: 코히어런트 장치이거나 DMA_TO_DEVICE면 true
 * dma_kmalloc_size_aligned: size >= 2 * ARCH_DMA_MINALIGN 이거나
 *   kmalloc_size_roundup(size)가 dma_get_cache_alignment()의 배수면 true */
```

```c
// h9_kmalloc.c — 작은 kmalloc 버퍼를 map하면 bounce되나? (DMA_BOUNCE_UNALIGNED_KMALLOC)
#include "h9_edu.h"
#include <linux/slab.h>

static const int sizes[] = { 8, 64, 96, 128, 192, 256 };

static void h9_try(struct device *dev, size_t sz, enum dma_data_direction dir)
{
	void *p = kmalloc(sz, GFP_KERNEL);
	phys_addr_t pa;
	dma_addr_t d;

	if (!p)
		return;
	pa = virt_to_phys(p);
	d = dma_map_single(dev, p, sz, dir);
	if (!dma_mapping_error(dev, d)) {
		dev_info(dev, "%-4s kmalloc(%3zu) phys=%pa dma=%pad %s\n",
			 dir == DMA_TO_DEVICE ? "TO" : "FROM", sz, &pa, &d,
			 pa == d ? "direct" : "BOUNCED");
		dma_unmap_single(dev, d, sz, dir);
	}
	kfree(p);
}

static int h9_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct edu *e = devm_kzalloc(&pdev->dev, sizeof(*e), GFP_KERNEL);
	int i, ret;

	if (!e)
		return -ENOMEM;
	ret = edu_setup(pdev, e, 32);
	if (ret)
		return ret;
	dev_info(&pdev->dev, "dma_get_cache_alignment()=%d cache_line_size()=%d\n",
		 dma_get_cache_alignment(), cache_line_size());
	for (i = 0; i < ARRAY_SIZE(sizes); i++)
		h9_try(&pdev->dev, sizes[i], DMA_FROM_DEVICE);
	h9_try(&pdev->dev, 64, DMA_TO_DEVICE);
	return 0;
}

static void h9_remove(struct pci_dev *pdev) { }
static struct pci_driver h9_drv = {
	.name = "h9_kmalloc", .id_table = edu_ids, .probe = h9_probe, .remove = h9_remove,
};
module_pci_driver(h9_drv);
```

### 4.4 `dma-coherent` DT 속성

장치가 코히어런트인지는 **드라이버가 아니라 플랫폼이** 알려 준다.

- DT: 장치 노드(또는 부모 버스 노드)에 `dma-coherent;`. 커널은 `of_dma_is_coherent()` → `of_dma_configure()` → `arch_setup_dma_ops(dev, coherent)`에서 `dev->dma_coherent`를 정한다. 드라이버는 `dev_is_dma_coherent(dev)`로 읽기만 한다(진단용).
- ACPI: `_CCA` 메서드.
- 반대 표시 `dma-noncoherent;`도 있다(기본이 코히어런트인 아키텍처용, 예: RISC-V 일부).

```dts
/* 예시 (실행 안 함): SoC의 PCIe RC가 CCI/CMN 인터커넥트로 스누핑되는 경우 */
pcie@40000000 {
	compatible = "vendor,soc-pcie";
	dma-coherent;
	/* ... */
};
```

함정: 하드웨어는 비코히어런트인데 DT에 `dma-coherent`를 잘못 넣으면 캐시 작업이 전부 생략되어 **간헐적 데이터 깨짐**이 난다. 반대로 코히어런트 장치에 빠뜨리면 데이터는 맞지만 불필요한 캐시 작업과 non-cacheable coherent 버퍼 때문에 **느려진다**. 둘 다 BSP bring-up에서 실제로 만나는 버그다. 이 랩의 §2.3이 두 번째 경우를 일부러 만든 것이다.

## 5. DMA mask와 SWIOTLB bounce buffer

### 5.1 직관

장치의 주소선이 N비트면 그 장치는 `2^N` 아래만 DMA할 수 있다. Don의 SSD 컨트롤러가 호스트 64비트 주소를 지원하지 않았다면 호스트 드라이버가 32비트 아래 버퍼만 줘야 했던 것과 같다. Linux에서 이것이 **DMA mask**다.

- `dma_set_mask_and_coherent(dev, DMA_BIT_MASK(N))`: streaming mask와 coherent mask를 같이 정한다. probe 초반에 부르고 **반환값을 확인**한다. 실패하면 더 작은 값으로 재시도하는 것이 관례(`64 → 32`).
- 기본값: PCI 장치는 32비트, 플랫폼 장치도 대개 32비트(`dev->coherent_dma_mask` 기본).
- 주소가 mask를 넘는 버퍼를 map하면? IOMMU가 있으면 mask 아래 IOVA를 주면 끝. 없으면 **SWIOTLB**: 부팅 때 낮은 주소에 잡아 둔 bounce 영역에 슬롯을 받아 **복사**한다. TO_DEVICE면 map 때 원본 → bounce, FROM_DEVICE면 unmap/`sync_for_cpu` 때 bounce → 원본.

### 5.2 예제 7 — 28비트 장치: IOMMU 없이는 거절

```c

{
	u64 min_mask = (max_pfn - 1) << PAGE_SHIFT;

	if (mask >= DMA_BIT_MASK(32))
		return 1;
	if (IS_ENABLED(CONFIG_ZONE_DMA))
		min_mask = min_t(u64, min_mask, zone_dma_limit);
	return mask >= phys_to_dma_unencrypted(dev, min_mask);
}
```

(주석을 뺀 발췌.) 32비트 이상이면 무조건 OK(ZONE_DMA32나 SWIOTLB로 감당하라는 약속), 그 아래면 "**ZONE_DMA의 끝까지**는 닿아야" OK다. 여기서 ZONE_DMA 끝은 `0x7fffffff`이고 28비트 mask `0x0fffffff`는 거기에 못 미친다. 커널이 정직하게 "이 장치는 이 시스템에서 DMA를 못 한다"고 말한 것이다. 같은 모듈을 SMMU를 붙여 돌리면 성공한다(§7.2).

### 5.4 예제 9 — 32비트 장치 + 4 GiB 넘는 RAM: SWIOTLB bounce

이번엔 정직하게: edu를 32비트로(`dma_mask=0xffffffff`), 드라이버도 32비트 mask. RAM은 4 GiB(`-m 4096`, 즉 `0x4000_0000`~`0x1_3fff_ffff`)로 늘려서 버퍼가 4 GiB 위에 놓이게 한다.

```c
// h9_mask.c — DMA mask와 SWIOTLB bounce: phys vs dma, unmap 전후의 CPU 시야
#include "h9_edu.h"

static int bits = 32;
module_param(bits, int, 0444);
static bool dma32;			/* 1이면 GFP_DMA32 (4 GiB 아래) 페이지 */
module_param(dma32, bool, 0444);
static bool hold;			/* 1이면 remove()까지 매핑 유지 (debugfs 관찰용) */
module_param(hold, bool, 0444);
static struct page *pg;
static dma_addr_t ds, dd;

static int h9_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct device *dev = &pdev->dev;
	struct edu *e = devm_kzalloc(dev, sizeof(*e), GFP_KERNEL);
	phys_addr_t ps, pd;
	u8 *src, *dst;
	int ret;

	if (!e || (ret = edu_setup(pdev, e, bits)))
		return e ? ret : -ENOMEM;
	pg = alloc_pages(GFP_KERNEL | (dma32 ? GFP_DMA32 : 0), 1);	/* 2 페이지: src, dst */
	if (!pg)
		return -ENOMEM;
	src = page_address(pg);
	dst = src + PAGE_SIZE;
	memset(src, 0x3c, PAGE_SIZE);
	memset(dst, 0, PAGE_SIZE);
	ds = dma_map_page(dev, pg, 0, PAGE_SIZE, DMA_TO_DEVICE);
	dd = dma_map_page(dev, pg + 1, 0, PAGE_SIZE, DMA_FROM_DEVICE);
	if (dma_mapping_error(dev, ds) || dma_mapping_error(dev, dd))
		return -EIO;
	ps = page_to_phys(pg);
	pd = ps + PAGE_SIZE;
	dev_info(dev, "src phys=%pa dma=%pad %s\n", &ps, &ds, ps == ds ? "direct" : "REMAPPED");
	dev_info(dev, "dst phys=%pa dma=%pad %s\n", &pd, &dd, pd == dd ? "direct" : "REMAPPED");
	ret = edu_dma(e, ds, 0, PAGE_SIZE, false, false) ?: edu_dma(e, dd, 0, PAGE_SIZE, true, false);
	dev_info(dev, "dma ret=%d; CPU sees dst[0]=%#x before unmap\n", ret, dst[0]);
	if (hold)
		return 0;
	dma_unmap_page(dev, ds, PAGE_SIZE, DMA_TO_DEVICE);
	dma_unmap_page(dev, dd, PAGE_SIZE, DMA_FROM_DEVICE);	/* bounce면 여기서 복사 */
	dev_info(dev, "CPU sees dst[0]=%#x after unmap\n", dst[0]);
	__free_pages(pg, 1);
	pg = NULL;
	return 0;
}
/* h9_remove(): pg가 남아 있으면(hold=1) 두 매핑을 unmap하고 __free_pages — 생략 */
```

(아래 출력은 probe 첫머리의 `!e`/`edu_setup()` 검사를 두 문장으로 나눠 쓴 처음 버전으로 얻었고, 위처럼 한 줄로 합친 버전으로 다시 빌드해 (b)를 재실행해서 같은 결과 — `REMAPPED`, unmap 전 `0x0` → 후 `0x3c`, `hiwater=4` — 를 확인했다.) (지면 때문에 `h9_remove()`와 `pci_driver` 등록부는 생략했다. 빌드·실행한 원본에는 들어 있다: `if (!pg) return;` → `dma_unmap_page` 두 번 → `__free_pages(pg, 1)`.)

- `dma32=1`이면 처음부터 장치가 닿는 메모리라 `direct`, SWIOTLB 사용 0. **bounce를 피하는 가장 싼 방법은 장치가 닿는 곳에서 할당하는 것**이다. arm64에서는 `ZONE_DMA`가 4 GiB 아래 전부(`DMA [mem 0x40000000-0xffffffff]`, `DMA32 empty`)라 `GFP_DMA32`가 `ZONE_DMA`로 떨어졌다.

### 5.5 흔한 함정

- **mask 설정 반환값 무시**: 실패를 모르고 기본 32비트로 돌다가 64비트 장치가 bounce 비용을 낸다(성능 버그), 또는 반대로 거짓 mask(§5.3).
- **SWIOTLB 고갈**: 큰 I/O가 몰리면 `swiotlb buffer is full (sz: ... bytes)` 경고와 함께 map이 실패한다. 이때 `dma_mapping_error()` 검사가 없으면 `DMA_MAPPING_ERROR`(모든 비트 1)를 장치에 쓴다. `swiotlb=` 부트 인자로 크기를 늘리거나, 근본적으로는 mask를 넓히거나 IOMMU를 쓴다.
- **`dma_max_mapping_size()` 무시**: SWIOTLB 한 번 매핑은 최대 256 KiB(연속 슬롯 128개)다. 블록·네트워크 계층은 이 값을 보고 요청을 쪼갠다.

## 6. scatter-gather — `sg_table`과 `dma_map_sgtable()`

### 6.1 직관 — Linux판 PRP 리스트

큰 버퍼는 물리적으로 흩어져 있는 경우가 많다(vmalloc, 유저 버퍼, 페이지 캐시). 이걸 장치에게 설명하는 목록이 scatter-gather 리스트다. Don에게는 NVMe의 PRP 리스트·SGL이 정확히 같은 개념이다.

- `struct scatterlist`: CPU 쪽 정보 `(page, offset, length)` + 매핑 후 장치 쪽 정보 `(dma_address, dma_length)`.
- `struct sg_table`: `sgl`(첫 엔트리), `orig_nents`(CPU 쪽 엔트리 수), `nents`(매핑 후 **장치 쪽** 세그먼트 수).
- `dma_map_sgtable(dev, sgt, dir, attrs)`: 성공 0, 실패 음수. 내부에서 `nents`를 채운다. 옛 API `dma_map_sg()`는 매핑된 개수를 반환하고 실패 시 0이다 — 혼동 주의.
- 순회: CPU 쪽은 `for_each_sgtable_sg()`, 장치 쪽은 `for_each_sgtable_dma_sg()` + `sg_dma_address()`/`sg_dma_len()`. **장치에게 줄 때는 반드시 dma 쪽 순회**를 쓴다. IOMMU가 병합하면 두 개수가 다르다.

### 6.2 예제 10 — vmalloc 버퍼를 sg로 매핑하고 세그먼트별로 DMA

무엇을 확인하나: vmalloc한 32 KiB(가상 연속, 물리 불연속)를 `vmalloc_to_page()`로 페이지 배열로 만들고 → `sg_alloc_table_from_pages()` → `dma_map_sgtable()`. CPU 쪽 엔트리(pfn)와 장치 쪽 세그먼트(dma 주소)를 찍고, edu로 src → dst를 4 KiB씩 복사한 뒤 비교한다. edu는 디스크립터 체인이 없으므로 세그먼트마다 DMA를 따로 건다(드라이버가 "SG 엔진" 역할).

앞부분 — 오프셋→버스 주소 변환과 매핑:

```c
// h9_sg.c (1/2) — vmalloc 버퍼 → sg_table → dma_map_sgtable, 세그먼트별 DMA 복사
#include "h9_edu.h"
#include <linux/vmalloc.h>
#include <linux/scatterlist.h>

static int bits = 32, npages = 8;
module_param(bits, int, 0444);
module_param(npages, int, 0444);

static dma_addr_t sg_dma_at(struct sg_table *t, size_t off)	/* 바이트 오프셋 → 버스 주소 */
{
	struct scatterlist *sg;
	int i;

	for_each_sgtable_dma_sg(t, sg, i) {
		if (off < sg_dma_len(sg))
			return sg_dma_address(sg) + off;
		off -= sg_dma_len(sg);
	}
	return DMA_MAPPING_ERROR;
}

static int h9_map(struct device *dev, struct sg_table *t, u8 *va, enum dma_data_direction dir)
{
	struct page **pages = kcalloc(npages, sizeof(*pages), GFP_KERNEL);
	struct scatterlist *sg;
	int i, ret;

	if (!pages)
		return -ENOMEM;
	for (i = 0; i < npages; i++)
		pages[i] = vmalloc_to_page(va + i * PAGE_SIZE);
	ret = sg_alloc_table_from_pages(t, pages, npages, 0, npages * PAGE_SIZE, GFP_KERNEL);
	kfree(pages);
	ret = ret ?: dma_map_sgtable(dev, t, dir, 0);
	if (ret || dir != DMA_TO_DEVICE)
		return ret;
	dev_info(dev, "orig_nents=%u (CPU 쪽 덩어리) nents=%u (장치 쪽 세그먼트)\n", t->orig_nents, t->nents);
	for_each_sgtable_sg(t, sg, i)
		dev_info(dev, "  cpu[%d] pfn=%#lx len=%u\n", i, page_to_pfn(sg_page(sg)), sg->length);
	for_each_sgtable_dma_sg(t, sg, i)
		dev_info(dev, "  dev[%d] dma=%pad len=%u\n", i, &sg_dma_address(sg), sg_dma_len(sg));
	return 0;
}
```

뒷부분 — probe:

```c
// h9_sg.c (2/2)
static int h9_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct device *dev = &pdev->dev;
	struct edu *e = devm_kzalloc(dev, sizeof(*e), GFP_KERNEL);
	size_t sz = npages * PAGE_SIZE, off;
	u8 *src = vmalloc(sz), *dst = vzalloc(sz);
	struct sg_table ts, td;
	int ret = -ENOMEM;

	if (!e || !src || !dst || (ret = edu_setup(pdev, e, bits)))
		goto out;
	for (off = 0; off < sz; off++)
		src[off] = off * 7;
	ret = h9_map(dev, &ts, src, DMA_TO_DEVICE) ?: h9_map(dev, &td, dst, DMA_FROM_DEVICE);
	if (ret)
		goto out;
	for (off = 0; !ret && off < sz; off += EDU_BUF_SZ)	/* edu 버퍼가 4 KiB라 조각 단위 */
		ret = edu_dma(e, sg_dma_at(&ts, off), 0, EDU_BUF_SZ, false, false) ?:
		      edu_dma(e, sg_dma_at(&td, off), 0, EDU_BUF_SZ, true, false);
	dma_unmap_sgtable(dev, &ts, DMA_TO_DEVICE, 0);
	dma_unmap_sgtable(dev, &td, DMA_FROM_DEVICE, 0);
	sg_free_table(&ts);
	sg_free_table(&td);
	dev_info(dev, "%zu bytes copied via edu, ret=%d, dst %s src\n", sz, ret, memcmp(src, dst, sz) ? "!=" : "==");
out:
	vfree(src);
	vfree(dst);
	return ret;
}
```

대응을 말로 정리하면:

- PRP는 "페이지 단위 + 첫 엔트리만 오프셋"이라는 **정렬 제약**이 있다. Linux 쪽 대응이 `dma_set_seg_boundary()`·`max_segment_size`·블록 계층의 `virt_boundary_mask`다. NVMe 드라이버는 블록 큐에 "세그먼트가 페이지 경계를 넘어 끊기면 안 된다(virt boundary)"를 알려서, PRP로 표현 못 하는 요청이 애초에 오지 않게 한다.
- SGL은 정렬 제약이 없는 대신 디스크립터가 16바이트로 크다. NVMe 드라이버는 평균 세그먼트 크기가 `sgl_threshold`(모듈 파라미터) 이상이고 컨트롤러가 SGL을 지원할 때 SGL을 고른다.
- 버전 차이(중요): 랩 소스 6.18.55의 `drivers/nvme/host/pci.c`는 **`sg_table`을 쓰지 않는다**. `nvme_map_data()`가 `blk_rq_dma_map_iter_start()`/`_next()`로 블록 요청을 바로 순회하며 `nvme_pci_setup_data_prp()` 또는 `nvme_pci_setup_data_sgl()`로 PRP/SGL을 채운다. 그 아래는 새 IOVA API(`dma_iova_try_alloc()`, `dma_iova_link()`, `dma_iova_sync()` — `include/linux/dma-mapping.h`에 있음)라서, IOMMU가 있으면 요청 전체에 IOVA 한 덩어리를 잡고 페이지를 이어 붙인다. 예전 커널(6.16 이하로 기억)은 `blk_rq_map_sg()` → `dma_map_sgtable()` → `nvme_pci_setup_prps()`/`nvme_pci_setup_sgls()` 순이었다 — **이 "예전" 함수 이름은 기억에 의한 것이고 랩에서 확인하지 않았다.** 다른 대부분의 드라이버(MMC, SPI, V4L2, DRM)는 지금도 `sg_table` 기반이다.

### 6.4 흔한 함정

- **`nents` 대신 `orig_nents`로 장치 디스크립터 채우기**: IOMMU가 병합한 시스템에서 남는 엔트리의 `sg_dma_address`는 쓰레기다. `for_each_sgtable_dma_sg()`를 쓰면 자동으로 맞다.
- **`dma_map_sg()` 반환값을 0과 비교하지 않기** / `dma_unmap_sg()`에 **매핑 결과 개수**를 넘기기: unmap에는 원래 `orig_nents`를 넘겨야 한다. `_sgtable` 버전은 이 혼동을 없애 준다.
- **vmalloc 버퍼를 비코히어런트 장치에**: 페이지를 sg로 매핑하는 것은 맞지만, 캐시 작업은 선형 매핑 주소로 되므로 vmalloc 별칭 쪽 캐시는 `flush_kernel_vmap_range()`/`invalidate_kernel_vmap_range()`로 따로 챙겨야 한다(VIPT 별칭 문제가 있는 아키텍처). arm64는 PIPT 데이터 캐시라 실제 문제는 적지만 이식성 있는 코드는 부른다.

## 7. IOMMU / SMMU — 격리, IOVA, fault, 보안

### 7.1 직관 — 장치 앞의 MMU

IOMMU는 **장치용 MMU**다. 장치(정확히는 PCI requester ID → SMMU의 StreamID)마다 페이지 테이블을 고르고, 장치가 낸 주소(IOVA)를 PA로 번역한다. 매핑이 없는 주소에 접근하면 **fault**가 난다. 이것이 주는 것 세 가지:

1. **격리(보안)**: 장치는 드라이버가 매핑해 준 페이지만 만질 수 있다. 펌웨어가 오염된 NIC, 악성 Thunderbolt/PCIe 장치, 버그 있는 DMA 엔진이 커널 메모리를 덮어쓰지 못한다(§7.4에서 실측).
2. **주소 변환**: 흩어진 페이지를 연속 IOVA로(§6.2), 28비트 장치에게 4 GiB 위 메모리를(§7.2) 줄 수 있다. bounce 불필요.
3. **가상화**: VFIO로 장치를 VM이나 유저 공간 드라이버에 통째로 넘길 수 있다. 랩 커널에도 `CONFIG_VFIO_PCI=y`가 있다(이 노트에서는 다루지 않는다).

단위는 **iommu_group**이다. 서로 격리할 수 없는 장치들(같은 StreamID를 쓰거나 ACS 없는 PCIe 스위치 뒤에서 P2P가 가능한 장치들)은 한 그룹으로 묶이고, 그룹 단위로 도메인(페이지 테이블)을 공유한다. §1.3 출력에서 edu는 혼자 그룹 2였다.

도메인 종류(`/sys/kernel/iommu_groups/N/type`):

| type | 뜻 | 설정 |
|---|---|---|
| `DMA` | DMA API가 IOVA를 관리, IOTLB 무효화 즉시(strict) | 랩 기본 (`CONFIG_IOMMU_DEFAULT_DMA_STRICT=y`) |
| `DMA-FQ` | 같지만 무효화를 모아서(flush queue, lazy) — 빠르지만 해제 직후 짧은 창 동안 옛 매핑이 살아 있음 | `iommu.strict=0` |
| `identity` | 패스스루. IOVA = PA, 격리 없음 | `iommu.passthrough=1` |
| `blocked` | 아무 DMA도 못 함 | 드라이버 없는 장치 등 |

### 7.3 IOVA는 어떻게 할당되나

`drivers/iommu/dma-iommu.c`의 `iommu_dma_alloc_iova()`가 도메인의 IOVA 할당기(`iova_domain`, rbtree + CPU별 캐시)에서 `min(dma_mask, bus_dma_limit)` **아래쪽 끝부터 위에서 아래로** 빈 구간을 찾는다. 그래서 첫 할당이 `0x0fffc000`, 다음이 `0x0fffb000`처럼 내려온다(예제 11). `reserved_regions`(MSI doorbell `0x08000000` 등)는 피한다.

map/unmap 비용의 정체:

- map: IOVA 할당 + 페이지 테이블 엔트리 쓰기(+ 비코히어런트 SMMU면 테이블 캐시 작업).
- unmap: 엔트리 지우기 + **IOTLB 무효화**(SMMU cmdq에 `TLBI` + `CMD_SYNC` 넣고 완료 대기). strict 모드는 매번, lazy(flush queue)는 모아서. §8에서 strict 6.8 µs vs lazy 2.7 µs로 측정된다.

### 7.4 예제 12 — 악성/버그 DMA: IOMMU 없으면 커널 데이터가 덮이고, 있으면 fault

```c
// h9_fault.c — "나쁜 장치": 매핑하지 않은 물리 주소(커널 데이터)에 DMA 쓰기
#include "h9_edu.h"
#include <linux/slab.h>

static int bits = 32;
module_param(bits, int, 0444);

static int h9_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct device *dev = &pdev->dev;
	struct edu *e = devm_kzalloc(dev, sizeof(*e), GFP_KERNEL);
	char *victim = devm_kmalloc(dev, PAGE_SIZE, GFP_KERNEL);	/* 커널의 "비밀" 데이터 */
	phys_addr_t pv;
	dma_addr_t dma;
	char *buf;
	int ret;

	if (!e || !victim)
		return -ENOMEM;
	ret = edu_setup(pdev, e, bits);
	if (ret)
		return ret;
	strscpy(victim, "kernel secret", PAGE_SIZE);
	pv = virt_to_phys(victim);

	/* 정상 경로: 'X'로 채운 coherent 버퍼를 edu 내부 버퍼로 */
	buf = dma_alloc_coherent(dev, PAGE_SIZE, &dma, GFP_KERNEL);
	if (!buf)
		return -ENOMEM;
	memset(buf, 'X', PAGE_SIZE);
	ret = edu_dma(e, dma, 0, 64, false, false);
	dma_free_coherent(dev, PAGE_SIZE, buf, dma);

	/* 공격 경로: 매핑 없이 victim의 물리 주소를 그대로 목적지로 */
	dev_info(dev, "victim phys=%pa before: \"%s\"\n", &pv, victim);
	ret = ret ?: edu_dma(e, (dma_addr_t)pv, 0, 64, true, false);
	dev_info(dev, "dma ret=%d, victim after: \"%.13s\"\n", ret, victim);
	return 0;
}

static void h9_remove(struct pci_dev *pdev) { }
static struct pci_driver h9_drv = {
	.name = "h9_fault", .id_table = edu_ids, .probe = h9_probe, .remove = h9_remove,
};
module_pci_driver(h9_drv);
```

출력에서 볼 것:

- **SMMU 있음**: 같은 주소가 장치 입장에서는 "매핑 안 된 IOVA"다. SMMU가 쓰기를 막고 이벤트 큐에 `F_TRANSLATION`(이벤트 ID `0x10`)을 올렸다. `sid: 0x10` = StreamID(PCI BDF `00:02.0` → `0x10`), `iova` = 장치가 낸 주소, `unpriv data write s1` = stage 1 변환 중 쓰기. victim은 무사하다.
- 장치는 fault를 모른다(`ret=0`). 실제 하드웨어에서는 PCIe 쪽에 Unsupported Request/Completer Abort가 돌아가 장치가 에러 상태가 되는 경우가 많다. 드라이버는 이 로그를 보고 "누가 어느 주소를 잘못 냈나"를 역추적한다. Don이 bring-up에서 버스 장애 root cause를 찾던 그 작업의 Linux판 첫 단서가 이 `F_TRANSLATION` 줄이다.

### 7.5 흔한 함정

- **"IOMMU가 있으니 `virt_to_phys` 써도 된다"**: 정반대. IOMMU가 있으면 PA는 장치에게 **무의미한 주소**다(위 실험).
- **SMMU fault 폭주**: 잘못된 링 주소로 장치가 계속 DMA하면 이벤트 큐가 넘치고 로그가 rate limit에 걸린다. 첫 이벤트가 중요하다.
- **성능 문제를 패스스루로 덮기**: `iommu.passthrough=1`은 격리를 버린다. 먼저 `iommu.strict=0`(lazy), 매핑 재사용(§3.4), 큰 매핑(huge IOVA 페이지)을 시도한다.
- **같은 그룹의 장치를 따로 VFIO에 넘기려다 실패**: 그룹 단위로만 넘길 수 있다.

## 8. 측정 — edu DMA vs CPU memcpy, 그리고 매핑 비용

### 8.1 예제 13 — 벤치 모듈

무엇을 확인하나: (a) 64 B ~ 4 KiB를 edu DMA(폴링)로 옮기는 시간과 CPU `memcpy` 시간, (b) 4 KiB 페이지 하나의 `dma_map_page` + `dma_unmap_page` 한 쌍의 CPU 비용(2000회 평균).

```c
// h9_bench.c — (a) edu DMA vs CPU memcpy 시간, (b) dma_map+unmap 한 쌍의 CPU 비용
#include "h9_edu.h"
#include <linux/ktime.h>

static int bits = 32;
module_param(bits, int, 0444);

static int h9_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct device *dev = &pdev->dev;
	struct edu *e = devm_kzalloc(dev, sizeof(*e), GFP_KERNEL);
	struct page *pg = alloc_page(GFP_KERNEL);
	u8 *va, *dst = devm_kmalloc(dev, PAGE_SIZE, GFP_KERNEL);
	dma_addr_t dma;
	u64 t, tdma, tcpu;
	int sz, i, ret;

	if (!e || !pg || !dst)
		return -ENOMEM;
	ret = edu_setup(pdev, e, bits);
	if (ret)
		goto out;
	va = page_address(pg);
	dma = dma_map_page(dev, pg, 0, PAGE_SIZE, DMA_TO_DEVICE);
	if (dma_mapping_error(dev, dma)) {
		ret = -EIO;
		goto out;
	}
	for (sz = 64; sz <= PAGE_SIZE; sz *= 4) {
		t = ktime_get_ns();
		for (i = 0; i < 3; i++)
			edu_dma(e, dma, 0, sz, false, false);		/* polling */
		tdma = (ktime_get_ns() - t) / 3;
		t = ktime_get_ns();
		for (i = 0; i < 1000; i++) {
			memcpy(dst, va, sz);
			barrier_data(dst);	/* 컴파일러가 복사를 지우지 못하게 */
		}
		tcpu = (ktime_get_ns() - t) / 1000;
		dev_info(dev, "size %4d: edu DMA %8llu us, CPU memcpy %6llu ns\n", sz, tdma / 1000, tcpu);
	}
	dma_unmap_page(dev, dma, PAGE_SIZE, DMA_TO_DEVICE);

	t = ktime_get_ns();
	for (i = 0; i < 2000; i++) {
		dma = dma_map_page(dev, pg, 0, PAGE_SIZE, DMA_TO_DEVICE);
		dma_unmap_page(dev, dma, PAGE_SIZE, DMA_TO_DEVICE);
	}
	dev_info(dev, "map+unmap 4 KiB: %llu ns/pair (phys %#llx -> dma %pad)\n",
		 (ktime_get_ns() - t) / 2000, (u64)page_to_phys(pg), &dma);
out:
	__free_page(pg);
	return ret;
}
/* h9_remove + pci_driver 등록(.name = "h9_bench")은 다른 예제와 같다 */
```

읽는 법:

- **direct·coherent(0.4 µs)**: 주소 계산과 디버그 훅 정도. 매핑은 거의 공짜다.
- **non-coherent(1.0 µs)**: + 4 KiB `dc cvac` 64줄. 실제 하드웨어에서는 캐시에 dirty 데이터가 얼마나 있느냐에 따라 더 커진다.
- **SWIOTLB(4.5 µs)**: 슬롯 할당 + 4 KiB 복사(TO_DEVICE라 map 때 한 번). 큰 버퍼일수록 복사 비용이 지배한다.
- **SMMU strict(6.8 µs) vs lazy(2.7 µs)**: 차이의 대부분이 unmap 때마다 cmdq로 IOTLB를 무효화하고 `CMD_SYNC`를 기다리는 비용이다. lazy는 IOVA가 재사용되지 않는 것도 보인다(`0x0ff57000` — 해제된 IOVA가 flush queue에 들어가 있어 다른 자리를 받는다).
- 결론: 고속 경로(NIC 10 Gbps, 카메라 4K60)에서 **매 패킷/프레임 map/unmap은 비싸다.** 버퍼를 미리 매핑해 두고 sync로 소유권만 넘기는 이유(§3.4), page_pool·videobuf2가 매핑을 캐시하는 이유다.

### 9.2 예제 14 — 규칙 위반 여섯 가지

```c
// h9_bug.c — DMA API 규칙 위반 6가지 (CONFIG_DMA_API_DEBUG 커널에서 확인)
#include "h9_edu.h"
#include <linux/slab.h>

static int bug;
module_param(bug, int, 0444);

static int h9_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
	struct device *dev = &pdev->dev;
	struct edu *e = devm_kzalloc(dev, sizeof(*e), GFP_KERNEL);
	u8 *buf = devm_kmalloc(dev, PAGE_SIZE, GFP_KERNEL), stackbuf[64];
	dma_addr_t d;
	int ret;

	if (!e || !buf || (ret = edu_setup(pdev, e, 32)))
		return -ENODEV;
	memset(buf, 0x11, PAGE_SIZE);
	switch (bug) {
	case 1:	/* 스택 버퍼를 매핑 (VMAP_STACK이면 물리 연속도 아님) */
		d = dma_map_single(dev, stackbuf, sizeof(stackbuf), DMA_TO_DEVICE);
		if (!dma_mapping_error(dev, d))
			dma_unmap_single(dev, d, sizeof(stackbuf), DMA_TO_DEVICE);
		break;
	case 2:	/* dma_mapping_error() 확인을 빼먹음 */
		d = dma_map_single(dev, buf, PAGE_SIZE, DMA_TO_DEVICE);
		dma_unmap_single(dev, d, PAGE_SIZE, DMA_TO_DEVICE);
		break;
	case 3:	/* map과 unmap의 방향이 다름 */
	case 4:	/* TO_DEVICE 매핑을 for_cpu로 sync (장치는 읽기만 했는데?) */
	case 5:	/* 매핑을 풀지 않고 드라이버가 떠남 */
	case 6:	/* map 뒤에 CPU가 버퍼를 고침 (소유권 위반) */
		d = dma_map_single(dev, buf, PAGE_SIZE, DMA_TO_DEVICE);
		if (dma_mapping_error(dev, d))
			return -EIO;
		if (bug == 6)
			buf[0] = 0x99;		/* 장치가 주인인데 CPU가 씀 */
		ret = edu_dma(e, d, 0, PAGE_SIZE, false, false);
		if (bug == 4)
			dma_sync_single_for_cpu(dev, d, PAGE_SIZE, DMA_FROM_DEVICE);
		if (bug != 5)
			dma_unmap_single(dev, d, PAGE_SIZE, bug == 3 ? DMA_FROM_DEVICE : DMA_TO_DEVICE);
		break;
	}
	dev_info(dev, "bug %d done\n", bug);
	return 0;
}
/* h9_remove + pci_driver 등록(.name = "h9_bug")은 다른 예제와 같다 */
```

## 10. dmaengine — SoC의 범용 DMA 컨트롤러 쓰기

### 10.1 직관 — 두 종류의 DMA

지금까지는 **장치 자신이 버스 마스터**인 경우(edu, NVMe, NIC)였다. 임베디드 SoC에는 또 하나가 있다: UART·SPI·I2S 같은 단순 주변장치는 DMA 엔진이 없고, **SoC의 공용 DMA 컨트롤러**(Arm PL330, i.MX SDMA, TI EDMA/UDMA, STM32 DMA…)가 그 FIFO 레지스터와 메모리 사이를 옮겨 준다. Linux에서 이 공용 컨트롤러를 쓰는 프레임워크가 **dmaengine**이다.

| 역할 | 누구 | 예 |
|---|---|---|
| provider | DMA 컨트롤러 드라이버 (`drivers/dma/`) | `pl330.c`, `imx-sdma.c`, `ti/k3-udma.c` |
| client | 주변장치 드라이버 | `amba-pl011`(UART), `spi-imx`, ASoC PCM |
| 연결 | DT의 `dmas = <&dma 5>; dma-names = "rx";` | 채널·요청선 번호 |

### 10.2 클라이언트 순서

```c
/* slave(주변장치) 클라이언트의 전형 — 예시, 이 랩에서는 실행 안 함 (virt에 DMA 컨트롤러가 없다) */
chan = dma_request_chan(dev, "rx");			/* DT dma-names로 채널 받기 */
cfg.direction = DMA_DEV_TO_MEM;
cfg.src_addr = res->start + UART_RX_FIFO;		/* 주변장치 FIFO의 물리 주소 */
cfg.src_addr_width = DMA_SLAVE_BUSWIDTH_1_BYTE;
cfg.src_maxburst = 8;
dmaengine_slave_config(chan, &cfg);
nents = dma_map_sg(chan->device->dev, sgl, n, DMA_FROM_DEVICE);	/* DMA 컨트롤러 기준으로 매핑 */
desc = dmaengine_prep_slave_sg(chan, sgl, nents, DMA_DEV_TO_MEM, DMA_PREP_INTERRUPT);
desc->callback = rx_done;
cookie = dmaengine_submit(desc);			/* 큐에 넣기만 */
dma_async_issue_pending(chan);				/* 실제 시작 */
/* ... 콜백 또는 dmaengine_tx_status(chan, cookie, &state) — 남은 바이트(residue) */
dmaengine_terminate_sync(chan);				/* 중단 (UART RX 타임아웃 등) */
```

핵심 포인트:

- **매핑은 DMA 컨트롤러의 `struct device`로** 한다(`chan->device->dev`). 버스 마스터가 컨트롤러이기 때문이다. 주변장치 장치로 매핑하는 실수가 흔하다.
- `submit`은 큐에만 넣고 **`issue_pending`을 불러야 시작**한다. Don의 SSD 큐로 말하면 SQE를 쓰는 것(`submit`)과 doorbell(`issue_pending`)이 분리된 것.
- 콜백은 보통 tasklet/BH 문맥에서 불린다 — 잠들면 안 된다(F7).
- cyclic 전송(`dmaengine_prep_dma_cyclic`)은 오디오·UART RX 링 버퍼용이다.

### 10.3 예제 15 — memcpy 클라이언트와 dmatest (이 머신에는 채널이 없다)

```c
// h9_dmaeng.c — dmaengine 클라이언트: memcpy 채널을 찾아 4 KiB 복사 한 번
#include <linux/module.h>
#include <linux/dmaengine.h>
#include <linux/dma-mapping.h>
#include <linux/completion.h>

static void h9_done(void *arg) { complete(arg); }

static int __init h9_init(void)
{
	DECLARE_COMPLETION_ONSTACK(done);
	struct dma_async_tx_descriptor *tx;
	struct dma_chan *ch;
	dma_cap_mask_t mask;
	dma_addr_t ds, dd;
	struct device *dev;
	u8 *src, *dst;
	dma_cookie_t ck;

	dma_cap_zero(mask);
	dma_cap_set(DMA_MEMCPY, mask);
	ch = dma_request_chan_by_mask(&mask);		/* 슬레이브면 dma_request_chan(dev, "rx") */
	if (IS_ERR(ch)) {
		pr_info("h9_dmaeng: no DMA_MEMCPY channel (%ld)\n", PTR_ERR(ch));
		return -ENODEV;
	}
	dev = ch->device->dev;				/* 매핑은 "DMA 컨트롤러"의 장치로 */
	src = dma_alloc_coherent(dev, PAGE_SIZE, &ds, GFP_KERNEL);
	dst = dma_alloc_coherent(dev, PAGE_SIZE, &dd, GFP_KERNEL);
	if (!src || !dst)
		goto out;
	memset(src, 0x77, PAGE_SIZE);
	tx = dmaengine_prep_dma_memcpy(ch, dd, ds, PAGE_SIZE, DMA_PREP_INTERRUPT | DMA_CTRL_ACK);
	if (!tx)
		goto out;
	tx->callback = h9_done;				/* 완료 시 tasklet/BH 문맥에서 호출 */
	tx->callback_param = &done;
	ck = dmaengine_submit(tx);			/* 큐에 넣기만 */
	dma_async_issue_pending(ch);			/* 이제 실제로 시작 */
	wait_for_completion_timeout(&done, HZ);
	pr_info("h9_dmaeng: %s status=%d dst[0]=%#x\n", dma_chan_name(ch),
		dma_async_is_tx_complete(ch, ck, NULL, NULL), dst[0]);
out:
	if (src)
		dma_free_coherent(dev, PAGE_SIZE, src, ds);
	if (dst)
		dma_free_coherent(dev, PAGE_SIZE, dst, dd);
	dma_release_channel(ch);
	return 0;
}
module_init(h9_init);
static void __exit h9_exit(void) { }
module_exit(h9_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("H9 dmaengine memcpy client");
```

## 11. dma-buf — 장치 사이에 버퍼 공유하기

### 11.1 직관

카메라(ISP)가 쓴 프레임을 GPU가 렌더링하고, NPU가 추론하고, 디스플레이가 스캔아웃한다. 각 장치 드라이버가 자기 버퍼를 따로 가지면 프레임마다 복사가 생긴다. **dma-buf**는 "버퍼 하나를 여러 장치가 각자 매핑해서 쓰는" 커널 공용 객체다. 유저 공간에는 **fd** 하나로 보인다(V4L2 `VIDIOC_EXPBUF`, DRM PRIME). Don의 SSD에서 같은 DRAM 버퍼를 NAND 엔진과 PCIe DMA가 번갈아 쓰던 구조를 "서로 다른 드라이버 사이의 약속"으로 일반화한 것이다.

- **exporter**: 버퍼를 가진 쪽(카메라 드라이버, dma-buf heap). `struct dma_buf_ops` 구현 — 핵심은 `map_dma_buf`: **importer의 장치를 위해** sg_table을 만들어 매핑해 준다.
- **importer**: 버퍼를 빌려 쓰는 쪽(GPU, NPU, 인코더). `dma_buf_attach(buf, dev)` → `dma_buf_map_attachment()` → 받은 sg_table의 dma 주소를 장치에 프로그래밍.
- 동기화: `dma_resv`의 fence로 "카메라가 다 쓸 때까지 GPU는 기다려라"를 표현한다(I5·I8에서).

### 11.2 예제 16 — 한 모듈 안의 exporter("카메라")와 importer(edu "GPU")

앞부분 — exporter:

```c
// h9_dmabuf.c (1/2) — 작은 dma-buf exporter("카메라") + importer(edu, "GPU") 한 모듈에
#include "h9_edu.h"
#include <linux/dma-buf.h>
#include <linux/slab.h>
MODULE_IMPORT_NS("DMA_BUF");
#define NP 4

struct h9x { struct page *pg[NP]; };

/* exporter: importer의 장치(at->dev)를 위해 sg_table을 만들어 매핑해 준다 */
static struct sg_table *h9x_map(struct dma_buf_attachment *at, enum dma_data_direction dir)
{
	struct h9x *x = at->dmabuf->priv;
	struct sg_table *t = kzalloc(sizeof(*t), GFP_KERNEL);

	if (!t)
		return ERR_PTR(-ENOMEM);
	if (sg_alloc_table_from_pages(t, x->pg, NP, 0, NP * PAGE_SIZE, GFP_KERNEL) ||
	    dma_map_sgtable(at->dev, t, dir, 0)) {
		kfree(t);
		return ERR_PTR(-EIO);
	}
	return t;
}

static void h9x_unmap(struct dma_buf_attachment *at, struct sg_table *t, enum dma_data_direction dir)
{
	dma_unmap_sgtable(at->dev, t, dir, 0);
	sg_free_table(t);
	kfree(t);
}

static void h9x_release(struct dma_buf *buf)
{
	struct h9x *x = buf->priv;
	int i;

	for (i = 0; i < NP; i++)
		__free_page(x->pg[i]);
	kfree(x);
}

static const struct dma_buf_ops h9x_ops = {
	.map_dma_buf = h9x_map, .unmap_dma_buf = h9x_unmap, .release = h9x_release,
};

static struct dma_buf *h9x_export(void)		/* "카메라 드라이버"가 프레임 버퍼를 내보낸다 */
{
	DEFINE_DMA_BUF_EXPORT_INFO(info);
	struct h9x *x = kzalloc(sizeof(*x), GFP_KERNEL);
	int i;

	for (i = 0; x && i < NP; i++) {
		x->pg[i] = alloc_page(GFP_KERNEL);
		memset(page_address(x->pg[i]), 'A' + i, PAGE_SIZE);	/* "프레임 데이터" */
	}
	info.exp_name = "h9_cam";
	info.ops = &h9x_ops;
	info.size = NP * PAGE_SIZE;
	info.flags = O_RDWR;
	info.priv = x;
	return dma_buf_export(&info);
}
```

뒷부분 — importer(edu 드라이버):

```c
// h9_dmabuf.c (2/2)
static struct dma_buf *buf;
static struct dma_buf_attachment *at;
static struct sg_table *sgt;

static int h9_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{	/* importer: edu가 버퍼에 attach → map → 각 세그먼트를 DMA로 읽는다 */
	struct device *dev = &pdev->dev;
	struct edu *e = devm_kzalloc(dev, sizeof(*e), GFP_KERNEL);
	struct scatterlist *sg;
	u8 *chk;
	dma_addr_t dchk;
	int i, ret;

	if (!e || (ret = edu_setup(pdev, e, 32)))
		return e ? ret : -ENOMEM;
	buf = h9x_export();
	if (IS_ERR(buf))
		return PTR_ERR(buf);
	at = dma_buf_attach(buf, dev);
	sgt = IS_ERR(at) ? ERR_CAST(at) : dma_buf_map_attachment_unlocked(at, DMA_TO_DEVICE);
	if (IS_ERR(sgt))
		return PTR_ERR(sgt);
	chk = dmam_alloc_coherent(dev, PAGE_SIZE, &dchk, GFP_KERNEL);
	if (!chk)
		return -ENOMEM;
	for_each_sgtable_dma_sg(sgt, sg, i) {
		ret = edu_dma(e, sg_dma_address(sg), 0, 16, false, false) ?:	/* 버퍼 → edu */
		      edu_dma(e, dchk, 0, 16, true, false);			/* edu → 확인용 */
		dev_info(dev, "seg %d dma=%pad len=%u -> read '%.4s' ret=%d\n",
			 i, &sg_dma_address(sg), sg_dma_len(sg), chk, ret);
	}
	return 0;
}

static void h9_remove(struct pci_dev *pdev)
{
	dma_buf_unmap_attachment_unlocked(at, sgt, DMA_TO_DEVICE);
	dma_buf_detach(buf, at);
	dma_buf_put(buf);		/* 마지막 참조 → h9x_release */
}
static struct pci_driver h9_drv = {
	.name = "h9_dmabuf", .id_table = edu_ids, .probe = h9_probe, .remove = h9_remove,
};
module_pci_driver(h9_drv);
```

## 12. 커널 안에서는 무슨 일이 일어나나

`dma_map_single()`부터 장치가 받는 주소까지(6.18.55 소스 기준):

```
dma_map_single(dev, va, size, dir)                   include/linux/dma-mapping.h
  -> WARN + DMA_MAPPING_ERROR if is_vmalloc_addr(va)   (bug=1)
  -> dma_map_page_attrs() -> dma_map_phys()          kernel/dma/mapping.c
       if dma_map_direct(dev, ops):                   no IOMMU / passthrough
           dma_direct_map_phys()                      kernel/dma/direct.h
             is_swiotlb_force_bounce?   -> swiotlb_map()
             !dma_capable(mask) or dma_kmalloc_needs_bounce?
                                        -> swiotlb_map()  (bounce slot, copy if TO/BIDI)
             !dev_is_dma_coherent       -> arch_sync_dma_for_device() -> dcache_clean_poc
             return phys_to_dma(phys)   (+ dma-ranges offset)
       else if use_dma_iommu(dev):
           iommu_dma_map_phys()                       drivers/iommu/dma-iommu.c
             (cache sync if non-coherent, swiotlb for untrusted/unaligned)
             iommu_dma_alloc_iova() -> iommu_map() -> page table entries
             return IOVA
       trace_dma_map_phys(); debug_dma_map_phys()     (events/dma, DMA_API_DEBUG)
```

핵심 자료구조와 필드:

| 무엇 | 어디 | 누가 채우나 |
|---|---|---|
| `dev->dma_mask`, `dev->coherent_dma_mask` | `struct device` | `dma_set_mask_and_coherent()` |
| `dev->bus_dma_limit`, `dev->dma_range_map` | `struct device` | `of_dma_configure()` (DT `dma-ranges`) |
| `dev->dma_coherent` | `struct device` | `arch_setup_dma_ops()` (DT `dma-coherent`) |
| `dev->dma_io_tlb_mem` | `struct device` | SWIOTLB 풀 (기본 또는 DT `restricted-dma-pool`) |
| `dev->dma_parms->max_segment_size` | `struct device_dma_parameters` | `dma_set_max_seg_size()` (PCI 기본 64 KiB) |
| iommu 도메인, `iova_domain` | `drivers/iommu/dma-iommu.c` | `iommu_setup_dma_ops()` |

드라이버를 쓸 때 다시 만나는 곳:

- **H11 (PCIe)**: `pci_set_master()`, MSI, BAR — 이 노트의 `edu_setup()`.
- **I5 (V4L2)**: `vb2_dma_contig_memops`(연속 버퍼, F10 CMA)와 `vb2_dma_sg_memops`(sg_table), `VIDIOC_EXPBUF` → dma-buf export, `VIDIOC_QBUF` with `V4L2_MEMORY_DMABUF` → import.
- **I8 (DRM)**: GEM DMA/SHMEM 헬퍼, PRIME = dma-buf import/export, `dma_resv` fence.
- **네트워크**: `page_pool`이 RX 페이지를 미리 매핑해 두고 `dma_sync_single_range_for_cpu()`로 헤더만 sync.
- **F5**: coherent 링에서 `dma_wmb()`/`dma_rmb()`, doorbell은 `writel()`.

## 13. Embedded 실무에서 다시 보기

### 13.1 센서 키트의 카메라 RX 링

Jetson/i.MX8 같은 SoC의 CSI-2 수신기 드라이버를 쓴다고 하자. 전형적인 구조:

- 디스크립터 링(엔트리 16개 × 32바이트): `dma_alloc_coherent()` 한 번, probe에서.
- 프레임 버퍼 6개(각 3 MiB): videobuf2가 `vb2_dma_contig`로 할당(CMA, F10) 또는 SMMU가 있으면 `vb2_dma_sg`로 흩어진 페이지 + IOVA.
- 프레임 완료 IRQ: 디스크립터의 상태 비트를 읽고 `dma_rmb()` 후 길이·타임스탬프를 읽는다. 버퍼가 streaming이면 `vb2_buffer_done()` 경로가 `sync_for_cpu`를 처리한다.
- 앱 → GPU/NPU: `VIDIOC_EXPBUF`로 dma-buf fd → EGL/CUDA/NPU 런타임이 import. 복사 0회.

"가끔 프레임 아래쪽에 이전 프레임이 섞여 보인다"는 버그 리포트가 오면 의심 순서: (1) DT의 `dma-coherent`가 하드웨어와 맞는가(§4.4), (2) 드라이버가 완료 전에 버퍼를 앱에 넘기지 않는가(소유권), (3) 앱이 CPU로 버퍼를 읽을 때 `DMA_BUF_IOCTL_SYNC`로 begin/end를 감쌌는가(dma-buf의 유저 공간 sync).

### 13.2 SPI IMU를 DMA로 읽기

SPI 컨트롤러 드라이버는 큰 전송(보통 수십 바이트 이상)에서 dmaengine으로 전환한다(`can_dma` 콜백). 이때 IMU 드라이버의 버퍼가 스택이나 구조체 중간에 있으면 §4.3·§9 bug=1 문제가 난다. IIO 드라이버들이 `u8 buf[16] __aligned(IIO_DMA_MINALIGN);`(= `ARCH_DMA_MINALIGN`)을 구조체 끝에 두는 이유다(H7).

### 13.3 PCIe NPU / 가속기 bring-up 체크리스트

1. `dma_set_mask_and_coherent(64)` 실패 시 32로 내려가는가, 장치 데이터시트의 실제 주소 폭과 맞는가(§5.3의 조용한 손상).
2. `lspci -vvv`의 `BusMaster+`(= `pci_set_master()`), 그리고 `/sys/kernel/iommu_groups/`에 장치가 있는가.
3. 첫 DMA에서 `arm-smmu-v3 ... F_TRANSLATION ... iova: X`가 뜨면: X가 드라이버가 준 `dma_addr_t`인가? 아니면 PA·VA가 새어 나갔나? 이미 unmap한 IOVA를 장치가 아직 쓰나(use-after-unmap)?
4. 성능: 매 요청 map/unmap인가(그림 6), strict/lazy, 큰 버퍼면 IOVA 연속성 덕에 디스크립터 수가 줄었는가.
5. 개발 커널에 `CONFIG_DMA_API_DEBUG=y`로 한 번은 돌려 본다(§9).

## 15. 면접에서 이렇게 말한다

**Q.** What is the difference between coherent and streaming DMA mappings?

**A.** coherent(`dma_alloc_coherent`)는 새로 할당하는 메모리로, CPU와 장치가 언제든 동시에 봐도 일관성이 보장된다 — 비코히어런트 SoC에서는 캐시를 끈 매핑을 준다. 디스크립터 링·상태 블록에 쓴다. streaming(`dma_map_single/page/sg`)은 이미 있는 버퍼를 한 번의 전송 동안 장치에 빌려 주는 것이고, 소유권 규칙과 방향이 있으며 map/unmap/sync 때 캐시 관리나 bounce가 일어난다. 데이터 버퍼에 쓴다. 보통 둘을 섞는다.

> Coherent mappings come from dma_alloc_coherent: freshly allocated memory that both the CPU and the device can access at any time without explicit synchronization — on a non-coherent SoC that means an uncached mapping. I use them for long-lived shared structures like descriptor rings and completion queues. Streaming mappings, dma_map_single, map_page or map_sg, lend an existing buffer to the device for one transfer. They have a direction and an ownership rule, and the cache maintenance or bounce copying happens at map, unmap and sync time. They're for data buffers. A typical driver uses both: a coherent ring whose descriptors point at streaming-mapped buffers.

**꼬리 질문**: "그럼 데이터 버퍼도 그냥 coherent로 하면 안 되나요?" — 비코히어런트 SoC에서는 캐시 안 되는 메모리라 CPU 접근이 느리고, 이미 있는 버퍼(skb, 페이지 캐시)를 복사해야 한다.

**Q.** Why do you need dma_sync_single_for_cpu? When do you call it?

**A.** streaming 매핑을 유지한 채 버퍼 소유권을 CPU로 가져올 때 부른다. 비코히어런트 시스템에서는 장치가 쓴 데이터 위에 남은 옛 캐시 라인을 invalidate하고, SWIOTLB가 끼어 있으면 bounce 버퍼에서 원래 버퍼로 복사한다. 코히어런트 하드웨어여도 bounce 때문에 필요하다. 다시 장치에 넘길 때는 `sync_for_device`. 매번 map/unmap하는 것보다 싸서 RX 링처럼 재사용 버퍼에 쓴다.

> It transfers ownership of a still-mapped streaming buffer back to the CPU. On a non-coherent system it invalidates stale cache lines so the CPU sees what the device wrote; if SWIOTLB bounced the mapping, it copies from the bounce buffer into the real buffer. So it's needed even on coherent hardware. Before handing the buffer back, I call sync_for_device. That pattern — map once, then sync back and forth — is much cheaper than map and unmap per transfer, which is why RX rings use it. In my lab, an unmap-before-read on a bounced buffer showed zero before and the real data after.

**꼬리 질문**: "TO_DEVICE 버퍼에 for_cpu sync를 하면?" — 방향 의미상 장치는 읽기만 했으니 invalidate할 것이 없다. arm64 구현은 바로 return하고, DMA-API debug는 방향 불일치를 경고한다.

**Q.** What does an IOMMU buy you, and what does it cost?

**A.** 세 가지: 격리(장치는 매핑해 준 페이지만 접근, 나쁜 DMA는 translation fault로 막힘 — 보안), 주소 변환(흩어진 페이지를 연속 IOVA로 이어 붙여 단순 DMA 엔진도 쓸 수 있고, 주소 폭이 좁은 장치도 bounce 없이 높은 메모리 사용), 가상화(VFIO로 장치 패스스루). 비용은 map/unmap 때 페이지 테이블 갱신과 IOTLB 무효화 — 측정해 보면 strict 모드에서 4 KiB 한 쌍이 direct의 약 17배(6849 대 401 ns). lazy 모드나 매핑 재사용으로 줄인다.

> Three things. Isolation: a device can only reach pages the driver mapped, so a buggy or malicious DMA hits a translation fault instead of corrupting kernel memory — I reproduced that with an SMMU in QEMU. Address translation: scattered pages become one contiguous IOVA range, so simple DMA engines don't need CMA, and devices with narrow address masks can reach high memory without bounce buffers. And virtualization through VFIO. The cost is map and unmap overhead — page-table updates and IOTLB invalidation. In my measurements strict mode was about seventeen times the direct-mapping cost per 4 KiB pair, lazy mode about forty percent of strict. You mitigate with lazy invalidation and by reusing mappings.

**꼬리 질문**: "iommu group은 왜 있나요?" — 서로 격리할 수 없는 장치(ACS 없는 스위치 뒤 P2P 등)는 같은 도메인을 공유해야 해서, 그룹 단위로만 VFIO에 넘길 수 있다.

**Q.** What is a DMA mask and what happens if a buffer is above it?

**A.** 장치가 낼 수 있는 주소 폭이다. `dma_set_mask_and_coherent()`로 정하고 실패하면 줄여서 재시도한다. 버퍼가 mask 위에 있으면 IOMMU가 있을 때는 mask 아래 IOVA를 주고, 없으면 SWIOTLB bounce buffer로 복사한다. mask가 시스템 RAM 어디에도 닿지 못하면 설정 자체가 실패한다. mask를 과장하면 장치가 상위 비트를 버려 오류 없이 다른 메모리를 망가뜨린다.

> The DMA mask is the range of bus addresses the device can generate. I set it with dma_set_mask_and_coherent, check the return value, and fall back to a smaller mask. If a buffer is above the mask, the DMA layer either allocates an IOVA below it through the IOMMU or bounces through SWIOTLB, which costs a copy and limited slots. If the mask can't reach any RAM — like a 28-bit device on a board whose RAM starts at 1 GB — the call fails. Over-claiming the mask is worse: the device truncates the address and silently corrupts other memory.

**Q.** How does the DMA API handle cache coherency on a non-coherent ARM64 SoC?

**A.** map과 `sync_for_device`는 모든 방향에서 `arch_sync_dma_for_device` → `dcache_clean_poc`(줄마다 `dc cvac`). unmap과 `sync_for_cpu`는 FROM/BIDI일 때 `dcache_inval_poc`(`dc ivac`, 양 끝 부분 라인은 `dc civac`). FROM_DEVICE에서도 map 때 clean하는 이유는 dirty 라인이 DMA 뒤에 evict되어 데이터를 덮는 것을 막기 위해서다. coherent 할당은 `arch_dma_prep_coherent`로 clean 후 non-cacheable로 재매핑한다. 코히어런트 여부는 DT의 `dma-coherent`가 정한다.

> For a non-coherent device, map and sync_for_device call arch_sync_dma_for_device, which cleans to the point of coherency — dc cvac per line — for every direction. Unmap and sync_for_cpu invalidate with dc ivac for FROM_DEVICE and bidirectional, using clean-and-invalidate on partial lines at the edges. Cleaning before a FROM_DEVICE transfer prevents a dirty line from being evicted on top of the DMA data later. Coherent allocations get cleaned and then remapped non-cacheable. Whether a device is coherent comes from the dma-coherent property in the device tree, not from the driver.

**꼬리 질문**: "그래서 DMA 버퍼 정렬이 왜 중요하죠?" — invalidate는 라인 단위라 이웃 데이터와 라인을 공유하면 둘 중 하나가 망가진다. 그래서 `ARCH_DMA_MINALIGN` 정렬, 그리고 최근 arm64는 작은 kmalloc 버퍼를 SWIOTLB로 bounce한다(실측했다).

**Q.** Walk me through using dmaengine for a UART RX.

**A.** DT의 `dmas`/`dma-names`로 `dma_request_chan(dev, "rx")`, `dmaengine_slave_config`에 FIFO 물리 주소·폭·burst, 버퍼는 **DMA 컨트롤러 장치로** 매핑, `dmaengine_prep_slave_sg` 또는 cyclic, 콜백 설정, `dmaengine_submit`으로 큐에 넣고 `dma_async_issue_pending`으로 시작. 완료는 콜백(BH 문맥), 부분 수신은 `dmaengine_tx_status`의 residue로 계산, 중단은 `dmaengine_terminate_sync`.

> Request the channel by name from the device tree with dma_request_chan, configure the slave side — FIFO physical address, width, burst — with dmaengine_slave_config, map the buffer against the DMA controller's device, not the UART's, prepare a slave_sg or cyclic descriptor, set the callback, submit, and then issue_pending to actually start. The callback runs in softirq context. For idle-line timeouts I read the residue from dmaengine_tx_status to know how many bytes arrived, and terminate_sync to stop.

**Q.** What is dma-buf and how would a camera frame get to the GPU without a copy?

**A.** 장치 간 버퍼 공유 객체. exporter(카메라 드라이버/videobuf2)가 `dma_buf_export`로 내보내고 유저에게는 `VIDIOC_EXPBUF` fd로 준다. GPU 드라이버(importer)는 fd로 `dma_buf_get` → `attach` → `map_attachment`로 **자기 장치용** sg_table을 받는다. exporter가 importer의 장치(IOMMU 포함)를 위해 매핑해 준다. 순서는 `dma_resv` fence로 맞춘다.

> dma-buf is the kernel's object for sharing a buffer between drivers. The camera's videobuf2 queue exports the frame with VIDIOC_EXPBUF, which gives user space a file descriptor. The GPU driver imports that fd: dma_buf_get, attach its own device, and map_attachment returns a scatter table mapped for the GPU — the exporter does the mapping per importer, so each side gets addresses valid for its own IOMMU. Fences in the reservation object make the GPU wait until the camera finishes writing. No copies.

## 16. 직접 해보기

1. (개념) DMA_FROM_DEVICE 매핑에서 arm64가 map 때 invalidate가 아니라 clean을 하는 이유를 "dirty 라인 evict" 시나리오로 설명하라.
   정답/힌트: §3.2. map 전 CPU가 그 버퍼에 썼다면 dirty 라인이 남아 있고, DMA 후 evict되면 DMA 데이터를 덮는다. invalidate는 unmap 때.
2. (코드) `h9_stream`의 재사용 RX 루프를 바꿔, 각 라운드에서 첫 64바이트만 `dma_sync_single_range_for_cpu()`로 sync해 검사하게 하고, §3.5 트레이스로 `size=64`가 찍히는지 확인하라.
   정답/힌트: `dma_sync_single_range_for_cpu(dev, drx, 0, 64, DMA_FROM_DEVICE)` — 이벤트의 `size`가 64로 바뀐다.
3. (관찰) `MEM=4096`, `hold=1`로 `h9_mask`를 넣은 상태에서 `/sys/kernel/debug/swiotlb/io_tlb_used`가 4인 이유를 슬롯 크기로 설명하라. 8 KiB 매핑 하나면 몇이 될까?
   정답/힌트: 슬롯 = 2 KiB(`IO_TLB_SHIFT` 11). 4 KiB × 2 = 4슬롯. 8 KiB 하나면 4슬롯.
4. (코드) `h9_sg`에 `dma_set_max_seg_size(dev, SZ_1M)`를 추가하고 SMMU + `npages=40`으로 돌려 `nents`가 몇이 되는지 예측하고 확인하라.
   정답/힌트: 64 KiB 한도가 사라지므로 IOVA가 연속이면 `nents=1`, `len=163840`이 예상된다(직접 확인할 것).
5. (관찰) SMMU 부팅에서 `iommu.strict=0`을 줬을 때 `/sys/kernel/iommu_groups/2/type`이 무엇으로 바뀌는지 확인하라.
   정답/힌트: `DMA-FQ` 예상(§7.1 표). `ex_lspci.sh`를 `APP=iommu.strict=0`으로.
6. (보안) `h9_fault`를 `iommu.passthrough=1`로 돌리면 victim은 어떻게 될까? 이유는?
   정답/힌트: 패스스루는 IOVA = PA, 격리 없음 → IOMMU 없는 경우처럼 덮인다(28비트가 아닌 `dma_mask=0xffffffff` edu로).
7. (DMA-API debug) `6.18.55-h9dma` 커널에서 `echo 1 > /sys/kernel/debug/dma-api/all_errors` 후 bug=4를 돌려 두 번째 오류 메시지를 확인하라.
   정답/힌트: `syncs device read-only DMA memory for cpu` (`kernel/dma/debug.c`의 `check_sync()`).

## 18. 요약 & 체크리스트

장치는 CPU의 MMU를 거치지 않으므로 드라이버는 장치에게 **DMA API가 준 `dma_addr_t`만** 넘긴다. 오래 공유하는 링은 coherent(`dma_alloc_coherent`, 작은 건 `dma_pool`), 한 번 쓰는 데이터 버퍼는 streaming(`dma_map_*` + 방향)이고, streaming 버퍼는 map 후 장치 것, unmap 또는 `sync_for_cpu` 후에만 CPU 것이다. 비코히어런트 arm64에서 그 경계마다 `dcache_clean_poc`/`dcache_inval_poc`가 돌고, 주소 제약이나 정렬 문제가 있으면 같은 자리에서 SWIOTLB 복사가 일어난다 — 그래서 코히어런트 하드웨어에서도 순서를 지킨다. DMA mask는 정직해야 하고(거짓말하면 조용히 메모리가 깨진다), IOMMU는 격리·연속 IOVA·주소 확장을 주는 대신 매핑 비용을 받는다. SoC의 공용 DMA 컨트롤러는 dmaengine(`prep` → `submit` → `issue_pending` → 콜백)으로, 장치 간 버퍼 공유는 dma-buf로 한다.

- [ ] CPU VA, PA, `dma_addr_t`(IOVA)의 차이와 "장치에게는 `dma_addr_t`만"의 이유를 설명할 수 있다
- [ ] coherent와 streaming을 언제 쓰는지, 둘을 섞는 실제 드라이버 구조를 말할 수 있다
- [ ] streaming 매핑의 소유권 상태도를 그리고 `sync_for_cpu`/`sync_for_device`가 필요한 이유를 설명할 수 있다
- [ ] 비코히어런트 arm64에서 방향별로 어떤 캐시 작업(`dc cvac`/`dc ivac`/`dc civac`)이 일어나는지 소스로 말할 수 있다
- [ ] `dma-coherent` DT 속성이 바뀌면 `dma_alloc_coherent`의 CPU 주소가 왜 vmalloc 영역으로 바뀌는지 설명할 수 있다
- [ ] DMA mask를 설정·확인하고, SWIOTLB bounce가 언제 일어나며 unmap 전후에 무엇이 달라지는지 보여 줄 수 있다
- [ ] `sg_table`을 만들어 `dma_map_sgtable`로 매핑하고 `nents`와 `orig_nents`의 차이를 IOMMU 병합으로 설명할 수 있다
- [ ] NVMe PRP/SGL과 Linux scatterlist를 대응시켜 말할 수 있다
- [ ] IOMMU/SMMU가 주는 격리·변환·가상화와 그 비용(strict vs lazy)을 측정값과 함께 말할 수 있다
- [ ] SMMU `F_TRANSLATION` 로그를 읽고 StreamID·IOVA로 원인을 추적할 수 있다
- [ ] `CONFIG_DMA_API_DEBUG`가 잡는 버그와 못 잡는 버그를 구분할 수 있다
- [ ] dmaengine 슬레이브 전송 순서와 dma-buf exporter/importer 구조를 코드 수준으로 설명할 수 있다
