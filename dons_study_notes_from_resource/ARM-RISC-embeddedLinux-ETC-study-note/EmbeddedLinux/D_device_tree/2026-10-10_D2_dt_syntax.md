# D2. Device Tree 문법 — 노드·프로퍼티·셀, phandle, `ranges` 주소 번역, 그리고 `.dtb` 바이너리 한 바이트씩

> **이 노트를 다 읽으면**: `.dts`의 노드·프로퍼티·값 타입·label·phandle·`/chosen`·`/aliases`를 읽고 고칠 수 있다 · `#address-cells`/`#size-cells`로 `reg`를 해석하고 `ranges`를 따라 버스 주소를 CPU 물리 주소로 손으로 번역할 수 있다 · `dtc`/`fdtdump`/`fdtget`/`fdtput`으로 컴파일·역컴파일·수정하고, dtc 경고의 뜻을 알고 고칠 수 있다 · `.dtb`(FDT) 헤더·structure 토큰·strings 블록을 hexdump로 읽고 C로 파서를 짤 수 있다
> **왜 필요한가**: 보드 bring-up 첫날 벤더 BSP의 `.dts`를 열어 "이 UART 주소가 왜 이거지?", "I2C에 센서 노드를 어떻게 추가하지?"를 바로 답해야 하고, 면접에서는 "`#address-cells`가 뭔가요?", "phandle이 뭔가요?", "`ranges`는 무슨 일을 하나요?"가 나온다
> **Don 기준 난이도**: 메모리 맵·버스 주소 변환(PCIe BAR, AXI 브리지)·big-endian 레지스터 덤프는 이미 안다 / 새로 배울 부분은 DT라는 "언어" 자체 — 셀 단위 값, phandle, label 덮어쓰기, 그리고 dtc가 하는 일
> **선행 노트**: D1(왜 DT인가) — C1(부팅 흐름)을 읽었으면 `/chosen`과 부트로더 부분이 더 잘 보인다

## 0. 큰 그림 — 이게 왜 필요한가

Don이 SSD 컨트롤러 펌웨어를 쓸 때 하드웨어 정보는 어디 있었나? `soc_regs.h` 같은 헤더에 `#define UART0_BASE 0x40001000`, `#define NAND_IRQ 37`이 박혀 있고, 보드가 바뀌면 헤더를 바꿔 **펌웨어를 다시 빌드**했다. 하드웨어 기술(description)과 코드가 한 덩어리였다.

Linux는 이걸 갈라놓는다. 커널 이미지 하나(`Image`)는 i.MX8, AM62, Jetson, QEMU virt 어디서나 같다. "이 보드에는 UART가 0x9000000에 있고 인터럽트는 SPI 1번이며 클록은 24 MHz다" 같은 정보는 **Device Tree(DT)** 라는 별도의 데이터 파일이 들고 온다. 사람이 쓰는 텍스트가 `.dts`/`.dtsi`(Device Tree Source), 이걸 `dtc`(Device Tree Compiler)로 컴파일한 바이너리가 `.dtb`(Device Tree Blob, 형식 이름은 FDT = Flattened Device Tree)다. 부트로더가 `.dtb`를 RAM에 올리고 그 주소를 커널에 넘긴다(arm64는 레지스터 `x0`).

### 1.2 정의 — 노드 이름 규칙

- 형식: `node-name@unit-address`. `node-name`은 1~31자, 영문 대소문자·숫자·`, . _ + -`. **기능을 나타내는 generic 이름**을 쓰라는 것이 DT 스펙 권고다(`serial`, `i2c`, `ethernet`, `gpio`, `memory`, `cpu`). 칩 이름(`pl011`)이 아니다. 단, QEMU가 만든 virt DT는 이 권고를 안 지키고 `pl011@9000000`처럼 쓴다 — 동작에는 문제없다.
- `@unit-address`: 노드가 **부모 버스 주소 공간에서 차지하는 첫 주소**. `reg`의 첫 주소와 같아야 한다(다르면 dtc 경고, §9). 주소가 없는 노드(`chosen`, `aliases`, `cpus`)는 `@` 없이 쓴다.
- 같은 부모 아래에서 이름(+unit-address)은 유일해야 한다. `serial@9000000`과 `serial@9040000`은 공존 가능.
- **경로(path)**: 루트 `/`부터 이름을 `/`로 이은 것. 예: `/soc@10000000/i2c@1000/imu@68`. 커널 로그·sysfs·`fdtget`이 다 이 경로로 노드를 가리킨다.
- **unit-address는 16진수, `0x` 없이**: `serial@9000000`(O), `serial@0x9000000`(X).

### 1.3 파일 맨 위 두 줄

```dts
/dts-v1/;            /* 이 파일은 DTS 버전 1 문법이다 — 반드시 첫 줄 */
/memreserve/ 0x48000000 0x1000;   /* (선택) 커널이 건드리면 안 되는 물리 메모리 */

/ {                  /* 루트 노드 */
	...
};
```

`/dts-v1/;`이 없으면 dtc는 옛 문법(v0)으로 읽으려 하고 경고를 낸다. `/memreserve/`는 FDT 헤더 뒤의 "memory reservation block"으로 들어간다(§10). 요즘은 `/reserved-memory` 노드를 더 많이 쓴다(D4).

## 2. 프로퍼티와 값 타입

### 2.1 직관 — "dtb에는 타입이 없다"

DT 프로퍼티 값은 결국 **바이트 배열**이다. `.dts` 문법이 여러 가지 모양(문자열, 셀, 바이트)을 제공하지만, `.dtb`에 들어가는 것은 "이름, 길이, 바이트들"뿐이다. **어떻게 해석할지는 읽는 쪽(드라이버, 바인딩 문서)이 안다.** Don의 레지스터 덤프와 같다 — 0x12345678이 주소인지 비트 필드인지는 데이터시트를 봐야 안다.

| 문법 | 예 | dtb 안 바이트 | 용도 |
|---|---|---|---|
| 값 없음 | `dma-coherent;` | 0바이트 | boolean (있으면 true) |
| `<u32 ...>` 셀 | `<0x12345678>` | `12 34 56 78` (big-endian) | 숫자, 주소, phandle |
| 64비트 | `/bits/ 64 <0x1122334455667788>` | 8바이트 BE | 64비트 값 (= 셀 2개) |
| 8/16비트 | `/bits/ 8 <0x01 0xff>` | `01 ff` | 작은 배열 |
| 문자열 | `"hello"` | `68 65 6c 6c 6f 00` | 이름, 모드 |
| 문자열 목록 | `"first", "second"` | NUL로 이어 붙임 | `compatible` |
| 바이트열 | `[de ad be ef]` | `de ad be ef` | MAC 주소, 보정값 |
| 혼합 | `"ab", <0x1>, [ff]` | 이어 붙임 (정렬 없음) | 드물다 |
| 참조 | `<&label>` | 4바이트 phandle | 다른 노드 가리키기 |
| 경로 참조 | `&label` (꺾쇠 없이) | 경로 문자열 | `/aliases`, `/chosen` |

**모든 셀은 big-endian**이다. 리틀엔디언 ARM 위에서도 그렇다. FDT가 원래 PowerPC/Open Firmware(IEEE 1275) 출신이기 때문이다. 커널 API(`of_property_read_u32()` 등, D8)가 `be32_to_cpu()`로 바꿔 준다.

### 2.2 예제 1 — 모든 타입을 컴파일하고 되돌려 보기

무엇을 확인하나: 타입별 문법을 dtc로 컴파일한 뒤, `fdtdump`와 `dtc -I dtb -O dts`(역컴파일)로 되돌리면 무엇이 남고 무엇이 사라지는지 본다.

```dts
/dts-v1/;

/ {
	#address-cells = <1>;
	#size-cells = <1>;
	model = "d2 demo board";

	d2_props: d2-props {
		flag-empty;                          /* 빈 값 = boolean true */
		u32-one = <0x12345678>;              /* 32비트 셀 1개 */
		u32-many = <1 2 0xff>;               /* 셀 배열 */
		u64-two-cells = /bits/ 64 <0x1122334455667788>;
		u64-manual = <0x11223344 0x55667788>;/* 같은 값을 셀 2개로 */
		u8-bits = /bits/ 8 <0x01 0x02 0xff>;
		str = "hello";
		str-list = "first", "second";
		bytes = [de ad be ef];
		mixed = "ab", <0x1>, [ff];
	};
};
```

```text
		u8-bits = [01 02 ff];
		str = "hello";
		str-list = "first", "second";
		bytes = <0xdeadbeef>;
		mixed = <0x61620000 0x1ff>;
	};
};
```

출력에서 볼 것:

- `u64-two-cells`(`/bits/ 64`)와 `u64-manual`(셀 2개)이 **완전히 같은 바이트**가 됐다. 64비트 값 = 상위 셀 + 하위 셀. `reg`에서 64비트 주소를 셀 2개로 쓰는 이유다(§5).
- `bytes = [de ad be ef]`가 `<0xdeadbeef>`로 돌아왔다. 길이가 4의 배수이면 역컴파일러는 셀이라고 **추측**한다. 타입 정보가 없다는 증거다.
- `mixed`는 `61 62 00 | 00 00 00 01 | ff` 8바이트가 그냥 이어졌다. 문자열 뒤에 **정렬 패딩이 없다**. 그래서 역컴파일러는 이걸 셀 2개 `<0x61620000 0x1ff>`로 오해한다. 혼합 프로퍼티는 가능하지만 쓰지 않는 게 좋다.
- label `d2_props:`가 사라졌다. label은 **소스 전용**이다(`-@` 옵션을 주면 `__symbols__` 노드로 남길 수 있다, §3.3).
- 숫자는 dtb에 `0x1`이든 `1`이든 똑같이 들어간다. 10진수도 쓸 수 있다: `clock-frequency = <400000>;`.

### 2.3 프로퍼티 이름 관례

| 형태 | 예 | 뜻 |
|---|---|---|
| 일반 이름 | `reg`, `status`, `compatible` | DT 스펙(Devicetree Specification)이 정의한 표준 프로퍼티 |
| `#`로 시작 | `#address-cells`, `#interrupt-cells`, `#gpio-cells` | "이 노드를 가리키는 쪽이 셀 몇 개를 써야 하나" |
| `벤더,이름` | `brcm,enable-ssc`, `linux,code` | 벤더(또는 linux) 전용 프로퍼티 |
| `-supply` 접미사 | `vdd-supply = <&reg_3v3>;` | regulator 연결 (D4) |
| `-gpios` 접미사 | `reset-gpios = <&gpio1 5 0>;` | GPIO 연결 (D4) |
| `-names` 짝 | `clock-names = "uartclk", "apb_pclk";` | 같은 순서의 배열에 이름 붙이기 |

`compatible`처럼 **문자열 목록은 앞쪽이 가장 구체적**이다: `"arm,pl011", "arm,primecell"` — 커널은 앞에서부터 맞는 드라이버를 찾는다(D3).

## 3. label, phandle, 경로 — 노드끼리 연결하기

### 3.1 직관 — "포인터가 필요하다"

인터럽트 컨트롤러는 하나인데 디바이스 여러 개가 그걸 가리켜야 한다. 클록 공급자 하나를 UART·SPI·I2C가 공유한다. 트리 구조만으로는 이 "다대일 연결"을 표현할 수 없다. 그래서 DT에는 **포인터**가 있다:

- **phandle**: 노드에 붙는 32비트 정수 ID. 노드 안에 `phandle = <N>;` 프로퍼티로 저장된다. 다른 노드는 이 숫자를 셀로 적어 가리킨다. C로 치면 "주소 대신 쓰는 핸들".
- **label**: 소스에서 사람이 쓰는 이름 `uart0:`. dtc가 컴파일할 때 phandle 숫자로 바꿔 준다.
- `<&label>` (꺾쇠 안) → **phandle 숫자** (4바이트).
- `&label` (꺾쇠 밖, 값 자리) → **경로 문자열** (예 `"/soc@10000000/serial@2000"`).
- `&{/full/path}` → label이 없는 노드를 경로로 지정.

### 3.2 예제 2 — label·phandle·경로 참조가 dtb에서 무엇이 되나

무엇을 확인하나: 같은 label을 `<&...>`와 `&...`로 썼을 때 하나는 숫자, 하나는 문자열이 되는 것과, phandle이 **참조된 노드에만** 자동 생성되는 것을 본다.

```dts
/dts-v1/;

/ {
	#address-cells = <2>;
	#size-cells = <2>;
	compatible = "d2,board";

	chosen {
		bootargs = "console=ttyAMA0 loglevel=7";

	};

	aliases {
		serial0 = &uart0;               /* 경로 참조 → 문자열 */
		d2-imu = "/soc@10000000/i2c@1000/imu@68";/* 경로를 직접 써도 된다 */
	};

	memory@40000000 {
		device_type = "memory";
		reg = <0x0 0x40000000 0x0 0x20000000>;
	};

	cpus {
		#address-cells = <1>;
		#size-cells = <0>;
		cpu0: cpu@0 { device_type = "cpu"; reg = <0>; };
		cpu1: cpu@1 { device_type = "cpu"; reg = <1>; };
	};

	soc@10000000 {
		compatible = "simple-bus";
		#address-cells = <1>;
		#size-cells = <1>;
		ranges = <0x0 0x0 0x10000000 0x100000>;

		intc: interrupt-controller@0 {
			reg = <0x0 0x1000>;
			interrupt-controller;
			#interrupt-cells = <1>;
		};
		uart0: serial@2000 {
			reg = <0x2000 0x100>;
			interrupt-parent = <&intc>;  /* phandle 참조 → u32 */
			interrupts = <5>;
		};
		i2c@1000 {
			reg = <0x1000 0x100>;
			#address-cells = <1>;
			#size-cells = <0>;
			status = "disabled";
			imu@68 { reg = <0x68>; };
		};
	};
};
```

### 3.3 예제 3 — `dtc -@`: label을 dtb에 남기기

무엇을 확인하나: overlay(D6)가 base dtb의 label을 찾을 수 있도록 dtc가 `__symbols__` 노드를 만드는 것을 본다.



출력에서 볼 것: `__symbols__`는 "label → 경로" 표다. 크기가 1122 → 1351바이트로 20% 늘었다. 커널 빌드가 overlay를 붙일 base dtb에만 `-@`를 주는 이유다(§15에서 실제 보드 dtb로 측정).

### 3.4 phandle 셀 뒤에 붙는 "인자" — 미리 보기

`clocks = <&clk 3>`, `gpios = <&gpio1 5 0>`처럼 phandle 뒤에 숫자가 더 붙는 경우가 많다. 그 개수는 **가리켜지는 쪽**의 `#clock-cells`, `#gpio-cells`가 정한다. QEMU virt의 `pl061@9030000`은 `#gpio-cells = <0x02>`라서 `gpio-keys`의 `gpios = <0x8004 0x03 0x00>`은 "phandle 0x8004(= pl061) + 셀 2개(핀 3, 플래그 0)"로 읽는다. 이 "specifier" 패턴은 D4에서 자세히 본다.

## 4. 특별한 노드들 — `/`, `/chosen`, `/aliases`, `/memory`, `/cpus`

| 노드 | 필수? | 주요 프로퍼티 | 누가 읽나 |
|---|---|---|---|
| `/` (루트) | 필수 | `compatible`, `model`, `#address-cells`, `#size-cells` | 커널 machine 식별, 하위 `reg` 해석 |
| `/chosen` | 사실상 필수 | `bootargs`, `stdout-path`, `linux,initrd-start/-end`, `rng-seed`, `kaslr-seed` | 커널 초기화 (펌웨어→커널 파라미터 전달) |
| `/aliases` | 선택 | `serial0 = "/path"`, `ethernet0`, `i2c1` … | 디바이스 번호 고정 (ttyAMA0, eth0 순서) |
| `/memory@...` | 필수 | `device_type = "memory"`, `reg` | 커널 메모리 초기화 (System RAM) |
| `/cpus` | 필수 | `#address-cells = <1>`, `#size-cells = <0>`, 자식 `cpu@N` | SMP, PSCI, cpufreq |
| `/reserved-memory` | 선택 | 자식 노드별 `reg`, `no-map` | 펌웨어·코프로세서 전용 메모리 (D4) |

`/chosen`은 **실제 하드웨어가 아니다**. 부트로더가 커널에 넘기는 파라미터 상자다. Don의 펌웨어로 치면 부트 ROM이 메인 펌웨어에 넘기던 "boot info 구조체"다. U-Boot와 QEMU는 dtb를 넘기기 직전에 `/chosen`을 **고쳐 쓴다**:

### 4.1 예제 4 — QEMU가 `/chosen`에 무엇을 써 넣었나 (게스트 안)

무엇을 확인하나: 랩의 기본 virt DT로 부팅한 뒤 게스트에서 `/chosen`과 `/memory`를 읽는다. 원래 `virt.dts`의 `/chosen`에는 `stdout-path`, `rng-seed`, `kaslr-seed`만 있었다.

### 4.2 `/aliases`와 `stdout-path`

`/aliases`의 이름은 커널 드라이버가 디바이스 번호를 정할 때 쓴다: `serial0 = "/pl011@9000000"`이면 그 UART가 `ttyAMA0`이 된다(`of_alias_get_id()`). 센서 키트 보드에서 "UART 순서가 바뀌어서 GNSS가 ttyS2에서 ttyS1이 됐다" 같은 사고는 aliases로 막는다.

`stdout-path`는 "콘솔로 쓸 디바이스"다. 경로 대신 alias 이름을 쓰고 뒤에 옵션을 붙일 수 있다: `stdout-path = "serial0:115200n8";`. 커널은 `console=` 인자가 없으면 이걸로 earlycon/콘솔을 정한다.

## 5. `#address-cells` / `#size-cells` — `reg` 해석하기

### 5.1 직관 — "숫자를 몇 개씩 끊어 읽나"

`reg = <0x0 0x9000000 0x0 0x1000>`만 보면 이게 "주소 4개"인지, "주소 1개 + 크기 1개가 두 쌍"인지, "64비트 주소 + 64비트 크기 한 쌍"인지 알 수 없다. 셀은 그냥 32비트 숫자들의 나열이기 때문이다. 그래서 **부모 노드**가 끊는 법을 알려 준다:

- `#address-cells = <N>`: 내 **자식**의 `reg`에서 주소 하나가 셀 N개.
- `#size-cells = <M>`: 크기 하나가 셀 M개.
- `reg`는 `(주소, 크기)` 쌍의 배열. 길이는 반드시 `(N+M) × 4 × 쌍 개수` 바이트.

핵심은 **"자식의 reg를 해석하는 규칙은 부모가 갖고 있다"** 는 것이다. 내 노드에 쓴 `#address-cells`는 내 `reg`가 아니라 **내 자식들의** `reg`를 위한 것이다. 이걸 헷갈리면 `reg_format` 경고(§9)를 만난다.

Don의 경험으로 번역하면: 부모 = 버스. **버스마다 주소 폭이 다르다.** AXI는 64비트 주소(2셀), APB 슬레이브 내부 오프셋은 32비트(1셀), I2C는 7비트 슬레이브 주소(1셀, 크기 없음 0셀), PCI는 "공간 종류 플래그 + 64비트"(3셀)이다.

### 5.2 손으로 읽어 보기 — QEMU virt에서

`virt.dts`에서 실제로 뽑은 줄들이다(§0의 `/var/lab/out/virt.dts`):

```dts
/ {
	#size-cells = <0x02>;
	#address-cells = <0x02>;
	memory@40000000 { reg = <0x00 0x40000000 0x00 0x20000000>; ... };
	pl011@9000000   { reg = <0x00 0x9000000 0x00 0x1000>; ... };
	intc@8000000 {
		reg = <0x00 0x8000000 0x00 0x10000 0x00 0x8010000 0x00 0x10000>;
		#address-cells = <0x02>; #size-cells = <0x02>; ranges;
		...
	};
	flash@0 { reg = <0x00 0x00 0x00 0x4000000 0x00 0x4000000 0x00 0x4000000>; ... };
	cpus {
		#size-cells = <0x00>;
		#address-cells = <0x01>;
		cpu@0 { reg = <0x00>; ... };
	};
};
```

| 노드 | 부모 cells | `reg` 셀 수 | 해석 |
|---|---|---|---|
| `memory@40000000` | 2/2 | 4 | 1쌍: 0x40000000, 크기 0x20000000 |
| `pl011@9000000` | 2/2 | 4 | 1쌍: 0x09000000, 크기 0x1000 (4 KiB 레지스터 창) |
| `intc@8000000` (GICv2) | 2/2 | 8 | **2쌍**: distributor 0x08000000+64K, CPU interface 0x08010000+64K |
| `flash@0` | 2/2 | 8 | 2쌍: flash 뱅크 0(0x0)과 뱅크 1(0x4000000), 각 64 MiB |
| `cpu@0` | 1/0 | 1 | 주소만: MPIDR affinity 값 0. 크기 없음 |

`reg`에 쌍이 여러 개 들어갈 수 있다는 것이 중요하다. GIC처럼 레지스터 창이 둘인 블록은 쌍 두 개를 쓰고, 드라이버는 인덱스(0, 1)로 꺼낸다(`platform_get_resource(pdev, IORESOURCE_MEM, 1)`, `devm_platform_ioremap_resource(pdev, 1)`). 이름을 붙이고 싶으면 `reg-names = "dist", "cpu";`를 함께 쓴다.

`cpus`의 `reg`는 메모리 주소가 아니라 **CPU ID(MPIDR)** 다. "주소 공간"은 꼭 메모리 맵일 필요가 없다. I2C 버스 아래 `reg = <0x68>`은 I2C 슬레이브 주소, SPI 아래 `reg = <0>`은 칩 셀렉트 번호다. **부모 버스가 무엇이냐에 따라 "주소"의 뜻이 바뀐다.**

### 5.3 기본값 — 안 쓰면 2/1

`#address-cells`가 없으면 기본 **2**, `#size-cells`가 없으면 기본 **1**이다(DT 스펙). 하지만 **기본값에 기대지 말라**는 것이 dtc와 커널의 입장이다 — `avoid_default_addr_size` 경고(§9)가 뜬다. 버스 노드를 만들면 두 프로퍼티를 항상 쓴다.

## 6. `ranges` — 버스를 넘는 주소 번역

### 6.1 직관 — "브리지의 주소 디코더"

Don은 PCIe에서 이걸 매일 봤다: 디바이스 BAR 주소(PCI 버스 주소)와 CPU가 보는 물리 주소가 다를 수 있고, 루트 컴플렉스의 outbound window가 그 사이를 변환한다. SoC 내부도 마찬가지다. AXI → APB 브리지, 서브시스템 인터커넥트, 레거시 VideoCore 버스(Raspberry Pi) — **자식 버스 주소 공간이 부모 주소 공간의 어딘가에 매핑된다.**

`ranges`는 그 매핑 표다. 버스 노드(자식들을 가진 노드)에 쓴다:

```text
ranges = < child-bus-address  parent-bus-address  length >  (반복)
            ^ 셀 수 = 이 노드의 #address-cells
                                ^ 셀 수 = 부모 노드의 #address-cells
                                                    ^ 셀 수 = 이 노드의 #size-cells
```

읽는 법: "내 안쪽 주소 `child`부터 `length`만큼은, 바깥 주소 `parent`부터에 해당한다". 번역식은 `parent_addr = addr - child + parent`.

세 가지 경우를 구분해야 한다:

| `ranges` 상태 | 뜻 | 예 |
|---|---|---|
| `ranges = <...>;` (값 있음) | 표대로 번역 | SoC 버스, PCI 호스트 |
| `ranges;` (빈 값) | **1:1 매핑** — 주소 그대로 통과 | GIC 노드(v2m 자식), i.MX `bus@30800000` |
| 없음 | **번역 불가** — 자식 주소는 CPU 주소 공간이 아니다 | I2C·SPI 버스 (자식 reg = 슬레이브 주소) |

마지막 줄이 중요하다. I2C 컨트롤러 노드에는 `ranges`가 없다. 그래서 `imu@68`의 0x68은 CPU가 load/store할 수 있는 주소가 아니다 — 커널도 이 노드에는 MMIO 자원을 만들지 않는다. "번역 가능한가"가 곧 "메모리 매핑된 디바이스인가"다.

### 6.2 손으로 번역해 보기 — 2단 버스

QEMU 랩에서 부팅할 테스트 DT에 이런 2단 버스를 넣었다(§14에서 전체 파일). 바깥 `d2-bus`는 안쪽 주소 0x80000000부터를 CPU 주소 0x0b000000으로 내리고, 그 안의 `d2-sub`는 자기 주소 0부터를 `d2-bus` 주소 0x80040000으로 올린다.

```dts
/ {                                     /* #address-cells = 2, #size-cells = 2 (virt) */
	d2-bus@b000000 {
		compatible = "simple-bus";
		#address-cells = <1>;
		#size-cells = <1>;
		ranges = <0x80000000  0x0 0x0b000000  0x100000>;
		/*         child(1셀)  parent(루트 2셀)  size(1셀) */

		d2-sub@80040000 {
			compatible = "simple-bus";
			#address-cells = <1>;
			#size-cells = <1>;
			ranges = <0x0  0x80040000  0x1000>;
			/*        child  parent(d2-bus 1셀)  size */

			d2-dev@100 {
				compatible = "d2,dev";
				reg = <0x100 0x10>;
			};
		};
	};
};
```

`d2-dev`의 `reg` 주소 0x100을 CPU 물리 주소로 올려 보자.

1. `d2-dev`의 부모 `d2-sub`가 1/1이므로 `reg = <0x100 0x10>`은 주소 0x100, 크기 0x10.
2. `d2-sub`의 `ranges = <0x0 0x80040000 0x1000>`: 0x100은 [0x0, 0x1000) 안에 있다 → `0x100 - 0x0 + 0x80040000 = 0x80040100` (이제 `d2-bus` 주소 공간).
3. `d2-bus`의 `ranges = <0x80000000 0x0 0x0b000000 0x100000>`: 0x80040100은 [0x80000000, 0x80100000) 안 → `0x80040100 - 0x80000000 + 0x0b000000 = 0x0b040100` (이제 루트 = CPU 물리 주소 공간).
4. 루트에 도달. **CPU 물리 주소 = 0x0b040100.**

### 6.3 진짜 보드 예 1 — Raspberry Pi 4의 "0x7e 주소"

RPi 문서와 데이터시트(BCM2711 ARM Peripherals)는 레지스터 주소를 **0x7e...** 로 적는다. VideoCore 시절의 "레거시 버스 주소"다. 하지만 ARM 코어가 보는 물리 주소는 0xfe...다. 이 간극을 DT의 `ranges`가 메운다. 커널 트리의 `bcm2711-rpi-4-b.dts`를 컴파일해서(§15) 역컴파일한 `soc` 노드:

```text
	soc {
		compatible = "simple-bus";
		#address-cells = <0x01>;
		#size-cells = <0x01>;
		ranges = <0x7e000000 0x00 0xfe000000 0x1800000 0x7c000000 0x00 0xfc000000 0x2000000 0x40000000 0x00 0xff800000 0x800000>;
		dma-ranges = <0xc0000000 0x00 0x00 0x40000000>;
```

`soc`가 1/1, 루트가 2셀이므로 한 항목은 1+2+1 = 4셀:

| child (버스 주소) | parent (ARM 물리) | 크기 | 의미 |
|---|---|---|---|
| 0x7e000000 | 0x0_fe000000 | 0x1800000 (24 MiB) | 메인 주변장치 |
| 0x7c000000 | 0x0_fc000000 | 0x2000000 (32 MiB) | 추가 주변장치 |
| 0x40000000 | 0x0_ff800000 | 0x800000 (8 MiB) | ARM local (GIC 등) |

그래서 `serial@7e201000`(PL011 UART0)의 ARM 물리 주소는 `0x7e201000 - 0x7e000000 + 0xfe000000 = 0xfe201000`이다. 데이터시트 주소를 그대로 노드 이름에 쓰고, 번역은 DT에 맡긴 설계다.

### 6.4 진짜 보드 예 2 — PCI 호스트 브리지 (3셀 child)

QEMU virt의 `pcie@10000000`은 `#address-cells = <0x03>`, `#size-cells = <0x02>`이고 부모(루트)는 2셀이라 한 항목이 3+2+2 = 7셀이다:

```text
ranges = <0x1000000 0x00 0x00        0x00 0x3eff0000   0x00 0x10000
          0x2000000 0x00 0x10000000  0x00 0x10000000   0x00 0x2eff0000
          0x3000000 0x80 0x00        0x80 0x00         0x80 0x00>;
```

(원본은 한 줄이다. 읽기 쉽게 항목별로 줄을 나눴다.) PCI 주소의 첫 셀 `phys.hi`는 주소가 아니라 **공간 종류 플래그**다(비트 25:24 = `ss`: 01 = I/O, 10 = 32비트 MMIO, 11 = 64비트 MMIO). 나머지 두 셀이 64비트 PCI 주소다.

| phys.hi | 공간 | PCI 주소 | CPU 물리 주소 | 크기 |
|---|---|---|---|---|
| 0x01000000 | I/O | 0x0 | 0x3eff0000 | 64 KiB |
| 0x02000000 | 32비트 MEM | 0x10000000 | 0x10000000 | 0x2eff0000 (약 752 MiB) |
| 0x03000000 | 64비트 MEM | 0x80_00000000 | 0x80_00000000 | 0x80_00000000 (512 GiB) |

예제 4와 같은 부팅에서 PCI 호스트 드라이버가 이 표를 읽고 찍은 로그와 `/proc/iomem`:

```sh
dmesg | grep -E "pci-host-generic.*(IO|MEM|ecam)"
grep -v "^ " /proc/iomem
```

### 6.5 `dma-ranges` — 반대 방향 (짧게)

`ranges`는 **CPU → 디바이스**(CPU가 레지스터에 접근할 때) 방향이다. 반대로 **디바이스가 버스 마스터로 메모리에 접근할 때**(DMA) 디바이스가 보는 주소와 CPU 물리 주소가 다를 수 있다. 이걸 `dma-ranges`가 같은 형식(child, parent, size)으로 적는다.

RPi 4의 `dma-ranges = <0xc0000000 0x00 0x00 0x40000000>`: "이 버스의 DMA 마스터가 0xc0000000을 내보내면 ARM 물리 0x0이다, 1 GiB까지". 레거시 DMA 엔진은 RAM 첫 1 GiB만 볼 수 있고 그것도 0xc0000000 별칭으로 본다는 뜻이다. 커널은 이걸 `of_dma_get_range()`(drivers/of/address.c)로 읽어 `dev->dma_range_map`에 넣고, `dma_map_single()`이 돌려주는 DMA 주소에 자동으로 반영한다. Don이 SSD에서 "DMA 엔진은 SRAM을 다른 주소로 본다"며 매크로로 변환하던 일을 커널 DMA API가 DT 정보로 해 준다. 자세한 건 DMA 노트(F/H 모듈)에서 다룬다.

## 7. `status`, 덮어쓰기, `/delete-node/`, `/delete-property/`

### 7.1 `status`

| 값 | 뜻 |
|---|---|
| 없음 | 사용 가능 (= `"okay"`) |
| `"okay"` (또는 옛 표기 `"ok"`) | 사용 가능 → 커널이 디바이스를 만든다 |
| `"disabled"` | 하드웨어는 있지만 지금은 안 씀 → 디바이스를 만들지 않는다 |
| `"reserved"` | 다른 소프트웨어(보안 펌웨어 등)가 쓰는 중 |
| `"fail"`, `"fail-sss"` | 고장 |

커널의 판정 함수는 `__of_device_is_available()`(drivers/of/base.c)이고, 소스 주석 그대로 "status가 없거나 `"okay"` 또는 `"ok"`이면 true"다. **SoC `.dtsi`는 대부분의 주변장치를 `"disabled"`로 두고, 보드 `.dts`가 실제로 배선된 것만 `"okay"`로 켜는 것**이 표준 패턴이다(D5). 그래서 "센서가 안 보인다" 디버깅의 1번 확인 사항이 `status`다.

### 7.2 예제 5 — label로 덮어쓰기와 삭제

```dts
	i2c1: i2c@30a20000 {
		compatible = "fsl,imx8mp-i2c";
		reg = <0x30a20000 0x10000>;
		clock-frequency = <100000>;
		status = "disabled";
	};
	spi2: spi@30830000 {
		reg = <0x30830000 0x10000>;
```

| | `status = "disabled"` | `/delete-node/` |

## 8. `/include/` vs `#include` — 미리 보기 (D5)

- `/include/ "file.dtsi"`: **dtc 자체 문법**. 텍스트를 그 자리에 넣을 뿐이다. 매크로가 없다.
- `#include <dt-bindings/...>`: **C 전처리기(cpp)** 문법. dtc는 이걸 모른다. 커널 빌드는 `.dts`를 먼저 cpp로 돌린 다음 dtc에 넘긴다. 덕분에 `#define`, `GIC_SPI`, `IRQ_TYPE_LEVEL_HIGH`, `GPIO_ACTIVE_LOW` 같은 헤더 상수를 쓸 수 있다(헤더는 커널 `include/dt-bindings/`에 있고 드라이버 C 코드와 공유된다).

### 8.1 예제 6 — dtc만으로는 `#include`가 안 된다

무엇을 확인하나: `#include`와 매크로가 있는 파일을 dtc에 바로 넣으면 실패하고, 커널과 같은 cpp 옵션으로 전처리하면 성공하는 것을 본다.

```dts
/dts-v1/;

	#address-cells = <1>;

```

## 9. dtc 경고 — 실제로 하나씩 일으켜 보기

dtc는 단순한 컴파일러가 아니라 **린터**다. 컴파일은 되지만 커널이 잘못 해석할 만한 것을 경고한다. 경고는 무시하기 쉽지만 대부분 진짜 버그다.

### 9.1 예제 7 — 다섯 가지 실수를 한 파일에

무엇을 확인하나: `unit_address_vs_reg`, `reg_format`, `avoid_default_addr_size`를 실제로 일으키고 메시지를 읽는다.

```dts
/dts-v1/;

/ {
	#address-cells = <1>;
	#size-cells = <1>;

	/* (1) unit-address는 있는데 reg가 없다 */
	d2-a@1000 {
		compatible = "d2,a";
	};

	/* (2) reg는 있는데 unit-address가 없다 */
	d2-b {
		reg = <0x2000 0x100>;
	};

	d2-bus@3000 {
		reg = <0x3000 0x1000>;
		/* #address-cells / #size-cells 를 빼먹었다 */
		/* (3) 자식 reg 해석에 기본값(2/1)이 쓰인다 */
		d2-c@10 {
			reg = <0x10 0x4>;
		};
	};

	/* (4) reg 길이가 (2+... 셀) 배수가 아니다: 3셀 */
	d2-d@4000 {
		reg = <0x4000 0x100 0x5>;
	};

	/* (5) 같은 unit-address 두 개 */
	d2-e@5000 { reg = <0x5000 0x10>; };
	d2-f@5000 { reg = <0x5000 0x10>; };
};
```

## 10. FDT 바이너리 포맷 — `.dtb` 한 바이트씩

### 10.1 직관 — 왜 "flattened"인가

메모리 안의 트리는 포인터로 연결되지만, 부트로더가 커널에 넘기려면 **포인터 없는 한 덩어리**여야 한다(커널이 어디에 올릴지 모르고, MMU도 아직 꺼져 있다). FDT는 트리를 **깊이 우선 순회한 토큰 스트림**으로 직렬화한 것이다. Don의 펌웨어로 치면 "TLV(type-length-value) 레코드를 이어 붙인 설정 블롭"과 거의 같다.

구조는 네 블록:

1. **header** (40바이트, v17): 매직·크기·각 블록 오프셋. 모든 필드 big-endian u32.
2. **memory reservation block**: (address u64, size u64) 쌍들, (0, 0)으로 끝. `/memreserve/`가 들어간다.
3. **structure block**: 토큰 스트림 — `FDT_BEGIN_NODE`(1) + 이름, `FDT_PROP`(3) + len + nameoff + 값, `FDT_END_NODE`(2), `FDT_NOP`(4), `FDT_END`(9). 모두 4바이트 정렬.
4. **strings block**: 프로퍼티 **이름**들을 NUL로 이어 붙인 것. PROP 토큰은 이름 대신 이 블록 안의 오프셋(nameoff)을 쓴다 — `compatible`, `reg` 같은 이름이 수백 번 나와도 한 번만 저장된다.

| 오프셋 | 필드 | 뜻 |
|---|---|---|
| 0x00 | `magic` | 0xd00dfeed |
| 0x04 | `totalsize` | 전체 크기 (빈 공간 포함) |
| 0x08 | `off_dt_struct` | structure 블록 오프셋 |
| 0x0c | `off_dt_strings` | strings 블록 오프셋 |
| 0x10 | `off_mem_rsvmap` | reservation 블록 오프셋 |
| 0x14 | `version` | 17 |
| 0x18 | `last_comp_version` | 16 (이 버전 이상을 읽을 줄 알면 읽을 수 있다) |
| 0x1c | `boot_cpuid_phys` | 부팅 CPU의 `reg` 값 |
| 0x20 | `size_dt_strings` | strings 블록 길이 |
| 0x24 | `size_dt_struct` | structure 블록 길이 |

- **모든 정수가 big-endian**. 0x88이 `00 00 00 88`로 저장된다.

- 노드 이름은 structure 블록 안에 인라인, 프로퍼티 이름은 strings 블록으로 빠져 있다. 노드 이름은 거의 다 다르지만 프로퍼티 이름은 반복되기 때문이다.
- `FDT_NOP`(4)은 이 파일엔 없다. 커널이 `rng-seed`를 지울 때(§4.1) 쓰는 `fdt_nop_property()`는 데이터를 옮기지 않고 그 자리를 NOP 토큰으로 덮어쓴다 — 플래시의 "invalidate 마킹"과 같은 발상이다.

## 11. 예제 10 — libfdt 없이 C로 FDT 파서 짜기

무엇을 확인하나: §10의 포맷 설명만으로 `.dtb`를 걸어 다니며 `dtc -O dts`와 같은 모양으로 트리를 출력할 수 있는지 본다. 값의 타입은 dtc 역컴파일러와 같은 규칙으로 추측한다(인쇄 가능한 NUL 종료 문자열 → 문자열, 길이가 4의 배수 → 셀, 나머지 → 바이트).

```c
/* d2_fdtparse: libfdt 없이 FDT(.dtb)를 직접 걸으며 트리를 출력한다 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdint.h>
#include <ctype.h>
#include <arpa/inet.h>                       /* ntohl: big-endian → host */

enum { BEGIN_NODE = 1, END_NODE = 2, PROP = 3, NOP = 4, END = 9 };
static uint32_t be(const uint8_t *p) { uint32_t x; memcpy(&x, p, 4); return ntohl(x); }
#define ALIGN4(x) (((x) + 3) & ~3u)

static void print_val(const uint8_t *v, uint32_t len)
{
    int str = len > 0 && v[len - 1] == '\0' && isprint(v[0]);
    for (uint32_t i = 0; str && i < len; i++)
        if (!isprint(v[i]) && v[i] != '\0') str = 0;
    if (len == 0) printf(";\n");
    else if (str) {                          /* 문자열(목록) */
        printf(" = \"");
        for (uint32_t i = 0; i < len - 1; i++) v[i] ? putchar(v[i]) : printf("\", \"");
        printf("\";\n");
    } else if (len % 4 == 0) {               /* u32 셀 배열 */
        printf(" = <");
        for (uint32_t i = 0; i < len; i += 4) printf(i ? " 0x%x" : "0x%x", be(v + i));
        printf(">;\n");
    } else {                                 /* 바이트열 */
        printf(" = [");
        for (uint32_t i = 0; i < len; i++) printf(i ? " %02x" : "%02x", v[i]);
        printf("];\n");
    }
}

int main(int argc, char **argv)
{
    static uint8_t b[2 << 20];               /* 2 MiB 이하 dtb 가정 */
    FILE *f = argc == 2 ? fopen(argv[1], "rb") : NULL;
    if (!f) { perror("usage: d2_fdtparse file.dtb"); exit(1); }
    size_t n = fread(b, 1, sizeof b, f); fclose(f);
    if (n < 40 || be(b) != 0xd00dfeed) { fprintf(stderr, "not a dtb\n"); exit(1); }
    uint32_t off_struct = be(b + 8), off_str = be(b + 12);
    printf("// magic 0x%x totalsize %u ver %u struct@0x%x(%u) strings@0x%x(%u)\n",
           be(b), be(b + 4), be(b + 20), off_struct, be(b + 36), off_str, be(b + 32));
    const uint8_t *p = b + off_struct;
    for (int depth = 0;;) {
        uint32_t tok = be(p); p += 4;
        if (tok == BEGIN_NODE) {
            const char *name = (const char *)p;
            printf("%*s%s {\n", depth++ * 4, "", *name ? name : "/");
            p += ALIGN4(strlen(name) + 1);
        } else if (tok == PROP) {
            uint32_t len = be(p), nameoff = be(p + 4);
            printf("%*s%s", depth * 4, "", (const char *)b + off_str + nameoff);
            print_val(p + 8, len);
            p += 8 + ALIGN4(len);
        } else if (tok == END_NODE) printf("%*s};\n", --depth * 4, "");
        else if (tok == END) break;
        else if (tok != NOP) { fprintf(stderr, "bad token 0x%x\n", tok); exit(1); }
    }
    return 0;
}
```

## 12. 예제 11 — libfdt로 노드 찾고 `ranges` 번역하기

### 12.1 libfdt는 어디 있나

libfdt는 dtc 프로젝트의 C 라이브러리로, U-Boot·커널·QEMU·TF-A가 모두 같은 코드를 포함한다. VM에는 런타임(`libfdt1` = `libfdt.so.1`)만 있고 개발 헤더(`/usr/include/libfdt.h`, 패키지 `libfdt-dev`)는 없다:

설치하는 대신 **커널 소스 안의 복사본**을 쓴다: `scripts/dtc/libfdt/`에 `.c`와 헤더가 다 있다(커널 빌드가 호스트용 dtc를 만들 때 쓰는 것). 정적 라이브러리로 묶어서 링크한다.

### 12.2 코드 — §6.2의 손 계산을 C로

무엇을 확인하나: libfdt API(`fdt_path_offset`, `fdt_parent_offset`, `fdt_address_cells`, `fdt_size_cells`, `fdt_getprop`, `fdt_get_path`)로 노드의 `reg`를 읽고, 부모를 타고 올라가며 `ranges`를 적용해 CPU 물리 주소를 계산한다. 커널 `of_translate_address()`의 단순화 버전이다(셀 2개 이하만, PCI 플래그 무시).

```c
/* d2_libfdt: libfdt로 노드를 찾고, reg를 ranges로 CPU 주소까지 번역한다 */
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <libfdt.h>

static uint64_t cells(const fdt32_t *p, int n)    /* n셀(최대 2) → 64비트 */
{
    uint64_t v = 0;
    for (int i = 0; i < n; i++) v = (v << 32) | fdt32_to_cpu(p[i]);
    return v;
}

int main(int argc, char **argv)
{
    static char buf[2 << 20];
    FILE *f = argc == 3 ? fopen(argv[1], "rb") : NULL;
    if (!f) { perror("usage: d2_libfdt file.dtb /node/path"); exit(1); }
    if (fread(buf, 1, sizeof buf, f) < 40) { fprintf(stderr, "short\n"); exit(1); }
    fclose(f);
    int err = fdt_check_header(buf);
    if (err) { fprintf(stderr, "fdt_check_header: %s\n", fdt_strerror(err)); exit(1); }

    int node = fdt_path_offset(buf, argv[2]), len;
    if (node < 0) { fprintf(stderr, "%s: %s\n", argv[2], fdt_strerror(node)); exit(1); }
    int parent = fdt_parent_offset(buf, node);
    int na = fdt_address_cells(buf, parent), ns = fdt_size_cells(buf, parent);
    const fdt32_t *reg = fdt_getprop(buf, node, "reg", &len);
    if (!reg) { fprintf(stderr, "no reg\n"); exit(1); }
    uint64_t addr = cells(reg, na), size = cells(reg + na, ns);
    printf("%-40s reg addr=0x%llx size=0x%llx (na=%d ns=%d)\n", argv[2],
           (unsigned long long)addr, (unsigned long long)size, na, ns);

    for (int bus = parent; bus > 0; bus = fdt_parent_offset(buf, bus)) {
        char path[256];
        int cna = fdt_address_cells(buf, bus);                 /* 버스 안쪽 */
        int pna = fdt_address_cells(buf, fdt_parent_offset(buf, bus));
        int cns = fdt_size_cells(buf, bus);
        const fdt32_t *r = fdt_getprop(buf, bus, "ranges", &len);
        fdt_get_path(buf, bus, path, sizeof path);
        if (!r) { printf("%s: no ranges -> not translatable\n", path); exit(1); }
        if (len == 0) { printf("%-40s ranges; (1:1)\n", path); continue; }
        int ent = cna + pna + cns, hit = 0;
        for (int i = 0; i + ent <= len / 4; i += ent) {
            uint64_t cb = cells(r + i, cna), pb = cells(r + i + cna, pna);
            uint64_t sz = cells(r + i + cna + pna, cns);
            if (addr >= cb && addr < cb + sz) {
                printf("%-40s 0x%llx in [0x%llx,+0x%llx) -> 0x%llx\n", path,
                       (unsigned long long)addr, (unsigned long long)cb,
                       (unsigned long long)sz, (unsigned long long)(addr - cb + pb));
                addr = addr - cb + pb; hit = 1; break;
            }
        }
        if (!hit) { printf("%s: 0x%llx outside ranges\n", path, (unsigned long long)addr); exit(1); }
    }
    printf("CPU physical address = 0x%llx\n", (unsigned long long)addr);
    return 0;
}
```

## 13. 예제 12 — `fdtget` / `fdtput`: 컴파일 없이 dtb 고치기

무엇을 확인하나: dts로 돌아가지 않고 dtb를 직접 읽고 고친다. 보드에서 U-Boot의 `fdt` 명령, 또는 제조 라인에서 시리얼 번호·MAC 주소를 dtb에 찍을 때 같은 일을 한다. 원본(`/var/lab/out/virt.dtb`, 읽기 전용)을 복사해서 쓴다.

```sh
cp /var/lab/out/virt.dtb d2_edit.dtb
fdtget -t x d2_edit.dtb /pl011@9000000 reg              # x = 16진 셀
fdtget d2_edit.dtb /pl011@9000000 compatible           # 문자열 목록
fdtget -t i d2_edit.dtb /apb-pclk clock-frequency      # i = 10진
fdtget -t bx d2_edit.dtb /pl011@9000000 reg            # bx = 바이트 단위 16진
fdtget d2_edit.dtb /chosen bootargs
fdtget -d none d2_edit.dtb /chosen bootargs            # 없을 때 기본값
fdtput -t s d2_edit.dtb /chosen bootargs "console=ttyAMA0 d2_from_fdtput"
fdtget d2_edit.dtb /chosen bootargs
fdtput -c d2_edit.dtb /d2-fdtput                        # 노드 생성
fdtput -t x d2_edit.dtb /d2-fdtput d2-val 0xcafe 0x1
fdtput -t s d2_edit.dtb /d2-fdtput compatible "d2,a" "d2,b"
fdtget -p d2_edit.dtb /d2-fdtput                        # 프로퍼티 목록
fdtget -t x d2_edit.dtb /d2-fdtput d2-val
fdtget -t bx d2_edit.dtb /d2-fdtput compatible
fdtput -d d2_edit.dtb /flash@0 bank-width               # 프로퍼티 삭제
fdtput -r d2_edit.dtb /gpio-keys                        # 노드 삭제
fdtget d2_edit.dtb /gpio-keys compatible
ls -l /var/lab/out/virt.dtb d2_edit.dtb
```

출력에서 볼 것:

- `fdtget`은 타입을 모르니 `-t`로 알려 줘야 한다: `-t x`(16진 셀), `-t i`(10진), `-t s`(문자열), 접두어 `b`/`h`는 바이트/16비트 단위. 24000000 = 0x16e3600 = 24 MHz `clk24mhz`.

- `fdtput -t s` 인자를 여러 개 주면 **문자열 목록**(`d2,a\0d2,b\0`)이 된다. 정확히 `compatible`이 원하는 모양이다.

## 14. 예제 13 — QEMU 랩: 직접 고친 virt dtb로 부팅해서 커널 눈으로 확인

### 14.1 테스트 DT

무엇을 확인하나: 원본 `virt.dts`를 `/include/`로 통째로 가져오고, (1) 모든 타입의 프로퍼티를 가진 테스트 노드, (2) §6.2의 2단 버스, (3) label 없는 노드의 경로 기반 덮어쓰기·삭제를 더한 dtb로 부팅한다. 게스트에서 `/proc/device-tree`를 hexdump해서 커널이 받은 값이 바이트 그대로인지 본다.

```dts
/dts-v1/;

		compatible = "d2,test";

	};

	d2-bus@b000000 {
		compatible = "simple-bus";
		#address-cells = <1>;
		#size-cells = <1>;
		ranges = <0x80000000  0x0 0x0b000000  0x100000>;

			compatible = "simple-bus";

			#size-cells = <1>;
```

- **big-endian 셀**: `d2-cells = <1 2 3>`이 `00 00 00 01 00 00 00 02 00 00 00 03`. 리틀엔디언 ARM64 커널 위에서도 그대로다. 드라이버가 `of_property_read_u32_array()`(D8)로 읽으면 그때 CPU 엔디언으로 바뀐다.

- `bootargs`에는 QEMU `-append` 문자열이 들어 있다. `-dtb`로 넘긴 dtb에도 QEMU가 `/chosen`을 고쳐 쓴다.
- `pl061@9030000` 노드는 남아 있고 `status`가 `disabled`라서 amba 디바이스 목록에 `9030000.pl061`이 **없다**(pl011, pl031만). `gpio-keys`는 노드 자체가 없다.
- **`b040100.d2-dev`**: 커널이 만든 platform device 이름이 §6.2 손 계산·§12 libfdt 결과와 같은 0xb040100이다. 커널의 `of_device_make_bus_id()`(drivers/of/device.c)가 `reg`를 `of_translate_address()`로 번역해서 "번역된 주소.노드이름"으로 이름을 짓는다. `reg`가 없는 버스 노드는 `d2-bus@b000000`, `d2-bus@b000000:d2-sub@80040000`처럼 경로 조각으로 이름이 붙는다. 루트 바로 아래 `compatible`이 있는 `d2-test`도 디바이스가 됐다(드라이버가 없으니 probe는 안 됨).
- **`bank-width`를 지웠더니 `physmap-flash ... failed with error -22`(EINVAL)**. 필수 프로퍼티를 빠뜨렸을 때 커널 로그에 나타나는 전형적인 모습이다 — 드라이버가 DT에서 값을 못 읽으면 probe가 `-EINVAL`로 실패한다.
- `/sys/firmware/fdt`는 커널이 받은 **원본 blob**이다. 그런데 크기가 8054가 아니라 36108이다. QEMU가 `-dtb` 파일을 읽을 때 `/chosen` 수정을 위해 버퍼를 (파일 크기 + 10000) × 2 = (8054 + 10000) × 2 = 36108바이트로 늘리기 때문이다 (QEMU 소스 `system/device_tree.c`의 `load_device_tree()`: `dt_size += 10000; dt_size *= 2;` — "Expand to 2x size to give enough room for manipulation"). 헤더를 dtc가 만든 원본(`fdtdump d2_virt.dtb`: `size_dt_struct` 0x1d2c, `size_dt_strings` 0x212, `off_dt_strings` 0x1d64)과 비교하면 structure 블록이 0x1e6c로 320바이트, strings 블록이 0x23f로 45바이트 늘었다. 45 = `"bootargs"`(9) + `"linux,initrd-start"`(19) + `"linux,initrd-end"`(17) — QEMU가 `/chosen`에 추가한 세 프로퍼티 이름의 NUL 포함 길이와 정확히 같다. 커널이 보는 blob은 "내가 빌드한 dtb"가 아니라 "부트로더가 고친 dtb"다.

## 15. 예제 14 — 진짜 보드 dtb는 얼마나 크고, 무엇으로 채워져 있나

무엇을 확인하나: 커널 트리의 보드 `.dts` 네 개(RPi 4, TI AM625 SK, NXP i.MX8MP EVK, NVIDIA Jetson Orin Nano devkit)를 커널과 같은 cpp+dtc 2단계로 직접 빌드하고, 헤더로 블록별 크기를 잰다. 커널 빌드 결과물과 바이트 단위로 같은지도 확인한다.

```sh
#!/bin/sh
# d2_mkdtb.sh — 커널 트리의 보드 .dts → cpp 전처리 → dtc  (커널 Makefile의 cmd_dtc를 손으로)
K=/var/lab/src/linux-6.18.55
dts=$1; out=$2
cpp -nostdinc -I $K/include -I $K/arch/arm64/boot/dts -I $(dirname $K/arch/arm64/boot/dts/$dts) \
    -I $K/scripts/dtc/include-prefixes -undef -D__DTS__ -x assembler-with-cpp \
    -o $out.pre.dts $K/arch/arm64/boot/dts/$dts || exit 1
dtc -I dts -O dtb -W no-unit_address_vs_reg -o $out $out.pre.dts 2>$out.warn || exit 1
echo "$dts -> $out ($(stat -c %s $out) bytes, $(wc -l < $out.pre.dts) preprocessed lines, $(grep -c Warning $out.warn) warnings)"
```

그림 7 — 커널이 FDT를 받아 쓰는 길. 왼쪽은 부팅 초기 순서, 오른쪽은 그 결과가 드러나는 곳.

단계별로(6.18 기준 `drivers/of/`):

1. **진입**: arm64 커널은 `x0`에 dtb 물리 주소를 받는다(docs.kernel.org "Booting AArch64 Linux"). 이 시점엔 아직 포인터 트리가 없어서, 커널은 libfdt(커널 안에 들어 있는 같은 코드)로 **flat 상태 그대로** 읽는다.
2. **early scan** (`drivers/of/fdt.c`): `early_init_dt_scan_chosen()`이 `/chosen`의 `bootargs`(→ `boot_command_line`), `linux,initrd-start/-end`, `rng-seed`(쓰고 NOP으로 지움)를 처리하고, `/memory` 노드의 `reg`로 memblock에 RAM을 등록한다. `/memreserve/`와 `/reserved-memory`도 이때 반영된다. 메모리 할당자가 생기기 전이라 flat 상태로 읽을 수밖에 없다.
3. **unflatten** (`unflatten_device_tree()`): 토큰 스트림을 한 번 훑어 필요한 크기를 재고, 메모리를 받아 `struct device_node`(이름, `full_name`, `parent`/`child`/`sibling` 포인터, `phandle`)와 `struct property`(`name`, `length`, `value`, `next`) 트리로 복사한다. **`value`는 dtb의 big-endian 바이트를 그대로 가리킨다** — §14에서 hexdump가 원본 바이트를 보여 준 이유다. 이때 `name` 프로퍼티도 합성된다.
4. **sysfs** (`drivers/of/kobj.c`): 노드마다 kobject 디렉터리, 프로퍼티마다 `bin_attribute` 파일(`__of_add_property_sysfs()`)을 만든다 → `/sys/firmware/devicetree/base`. 파일 크기 = `property->length`. `of_fdt_raw_init()`은 원본 blob을 `/sys/firmware/fdt`로 노출한다.
5. **디바이스 생성** (`drivers/of/platform.c`): `of_platform_default_populate_init()` → `of_platform_populate()`가 루트의 자식 중 `compatible`이 있는 노드, 그리고 `simple-bus` 같은 버스 노드의 자식들을 재귀적으로 `platform_device`(ARM PrimeCell은 `amba_device`)로 만든다. `status`가 `disabled`면 건너뛴다(`of_device_is_available()`). 이름은 `of_device_make_bus_id()`가 번역된 주소로 짓는다.
6. **드라이버 쪽**: probe에서 `platform_get_resource()`/`devm_platform_ioremap_resource()`를 부르면 내부에서 `of_address_to_resource()` → `__of_translate_address()`가 `ranges`를 따라 올라간다(§12 코드의 커널판, PCI·ISA 같은 특수 버스는 `struct of_bus`의 콜백으로 처리). phandle 참조는 `of_find_node_by_phandle()`(해시 캐시 사용), 값 읽기는 `of_property_read_u32()` 계열이 `be32_to_cpu()`를 해 준다.

드라이버를 쓸 때 다시 만나는 지점:

| 이 노트에서 | 드라이버에서 | 노트 |
|---|---|---|
| `compatible` 문자열 목록 | `of_match_table` → `probe()` | D3 |
| `reg` + `ranges` | `devm_platform_ioremap_resource(pdev, 0)` | D3, G2 |
| `interrupts`, phandle + specifier | `platform_get_irq()` | D4, H |
| `clocks`, `-supply`, `-gpios` | `devm_clk_get()`, `devm_regulator_get()`, `devm_gpiod_get()` | D4 |
| 커스텀 프로퍼티 | `of_property_read_u32()`, `device_property_read_u32()` | D8 |
| `status = "disabled"` | probe가 안 불림 — "드라이버가 안 뜬다" 1순위 원인 | D3, M1 |
| `dma-ranges` | `dma_map_single()` 결과 주소에 자동 반영 | F/H 모듈 |

## 17. Embedded 실무에서 다시 보기

### 17.1 장면 1 — "I2C IMU를 보드에 붙였는데 `/sys/bus/i2c/devices`에 없다"

센서 키트 보드에 ICM-42688 IMU를 I2C3에 달았다. 보드 `.dts`에 노드를 넣었는데 디바이스가 안 생긴다. DT 문법 레벨에서 확인할 순서:

```sh
# 1) 커널이 받은 DT에 노드가 있나? (경로는 보드에 따라 다르다)
ls /proc/device-tree/soc@0/bus@30800000/i2c@30a40000/
# 2) 부모 I2C 컨트롤러가 켜져 있나? 없으면 "okay"
cat /proc/device-tree/soc@0/bus@30800000/i2c@30a40000/status
# 3) 주소가 맞나? (1셀, big-endian)
hexdump -C /proc/device-tree/soc@0/bus@30800000/i2c@30a40000/imu@68/reg
# 4) 내가 빌드한 dtb가 진짜 올라갔나? 원본 blob과 비교
cmp /sys/firmware/fdt /boot/my-board.dtb
```

가장 흔한 원인은 (a) SoC `.dtsi`에서 `disabled`인 `&i2c3`에 `status = "okay"`를 안 넣음, (b) I2C 컨트롤러 노드에 `#address-cells = <1>; #size-cells = <0>;`이 없어서 `reg = <0x68>`이 잘못 해석됨(`reg_format` 경고를 무시함), (c) 부트로더가 다른 dtb를 올림(파티션의 옛 파일) — 4번의 `cmp`가 바로 잡는다. 단, 부트로더가 `/chosen`을 고치므로 `/sys/firmware/fdt`는 원본 파일과 정확히 같지 않을 수 있다. 그럴 땐 `dtc -I dtb -O dts`로 둘 다 풀어서 `diff`한다.

### 17.2 장면 2 — 데이터시트 주소와 DT 주소가 다르다

Raspberry Pi 계열이나 일부 FPGA SoC(Zynq PL 영역, AXI 인터커넥트 뒤)를 쓰면, 데이터시트·Vivado 주소 편집기의 주소와 `/proc/iomem`의 주소가 다르다. 이때 Don이 할 일은 **노드에서 루트까지 `ranges`를 따라가는 것**이다(§6). `ranges`가 없는 중간 버스가 있으면 그 아래는 CPU에서 MMIO로 접근 불가 — "devmem으로 읽으면 버스 에러"의 DT판이다.

### 17.3 장면 3 — 제조 라인에서 MAC 주소·보정값 넣기

보드마다 다른 이더넷 MAC, IMU 보정 행렬을 rootfs에 넣지 않고 dtb에 넣는 경우가 많다. 이미지 빌드 후 제조 스테이션에서:

```sh
fdtput -t bx board.dtb /soc@0/bus@30800000/ethernet@30be0000 local-mac-address 00 04 9f 01 02 03
```

U-Boot에서는 같은 일을 `fdt set` 명령이나 보드 코드의 `ft_board_setup()`이 부팅 때마다 한다(C 모듈). 이 경우 dtb에 여유 공간(§10.3)이 있어야 한다.

### 17.4 장면 4 — 런타임에 DT 상태 덤프해서 버그 리포트에 붙이기

보드에서 dtc가 없어도 `/sys/firmware/fdt`를 복사해 오면 된다. 호스트에서 `dtc -I dtb -O dts fdt.bin > board-runtime.dts`. 보드에 dtc가 있다면 `dtc -I fs -O dts /proc/device-tree`가 sysfs 트리를 바로 dts로 만든다(`-I fs` 입력 형식). "부트로더가 무엇을 고쳤는지"까지 포함된 진짜 상태라서 필드 이슈 분석에 가장 정확한 자료다.

## 19. 면접에서 이렇게 말한다

**Q.** What do `#address-cells` and `#size-cells` mean, and how is `reg` parsed?

**A.** 둘 다 **자식 노드의 `reg`** 를 어떻게 끊어 읽을지 정하는 부모의 프로퍼티다. `#address-cells`는 주소 하나가 32비트 셀 몇 개인지, `#size-cells`는 크기가 몇 개인지. `reg`는 (주소, 크기) 쌍의 배열이다. 64비트 SoC 루트는 보통 2/2라서 `reg = <0x0 0x9000000 0x0 0x1000>`이 주소 0x9000000, 크기 4 KB 한 쌍이다. I2C 버스는 1/0이라 `reg = <0x68>`은 슬레이브 주소만이다. 기본값은 2/1이지만 기대지 말고 항상 쓴다.

> `#address-cells` and `#size-cells` live on the parent and tell you how to slice the children's `reg` property — how many 32-bit big-endian cells make up one address and one size. `reg` is just an array of address/size pairs. On a 64-bit SoC the root is usually 2 and 2, so `<0x0 0x9000000 0x0 0x1000>` is one region at 0x9000000, 4 KB long. Under an I2C controller it's 1 and 0, so `reg = <0x68>` is just the slave address with no size. The key point is that the cells belong to the bus, not to the node itself.

**꼬리 질문**: "PCI는 왜 3셀인가?" → 첫 셀이 I/O·32비트 MEM·64비트 MEM을 구분하는 공간 플래그(phys.hi)이고 나머지 두 셀이 64비트 주소라서.

**Q.** What does the `ranges` property do? What's the difference between an empty `ranges` and no `ranges`?

**A.** 버스 브리지의 주소 디코더 표다. (자식 버스 주소, 부모 버스 주소, 길이) 항목들로, 자식 주소가 부모 주소 공간의 어디에 매핑되는지 적는다. 커널은 디바이스 `reg`를 루트까지 `ranges`를 따라 번역해서 CPU 물리 주소를 얻는다. 빈 `ranges;`는 1:1 매핑, `ranges`가 아예 없으면 번역 불가 — I2C·SPI 버스처럼 자식 주소가 메모리 주소가 아니라는 뜻이다. RPi 4는 버스 주소 0x7e201000이 ARM 물리 0xfe201000으로 번역되는 실제 예다.

> `ranges` is the address decoder of a bus bridge: a table of child-bus-address, parent-bus-address, length. To get a CPU physical address, the kernel walks from the device up to the root and applies each bus's `ranges` — `addr - child_base + parent_base`. An empty `ranges` means identity mapping; a missing `ranges` means the child addresses aren't memory-mapped at all, like I2C or SPI chip selects. Raspberry Pi 4 is a good example: the datasheet says the UART is at 0x7e201000, but `ranges` maps that to 0xfe201000 on the ARM side.

**꼬리 질문**: "`dma-ranges`는?" → 반대 방향. 디바이스가 버스 마스터로 메모리에 접근할 때 보는 주소와 CPU 물리 주소의 관계. 커널 DMA API가 자동 반영한다.

**Q.** What is a phandle? How is `&label` turned into one?

**A.** 노드를 가리키는 32비트 정수 ID다. 트리 구조로는 다대일 연결(여러 디바이스가 한 인터럽트 컨트롤러·클록을 공유)을 표현할 수 없어서 쓴다. 소스에서는 `uart0:` 같은 label을 붙이고 `<&uart0>`으로 참조하면, dtc가 대상 노드에 `phandle = <N>` 프로퍼티를 만들고 참조 자리에 N을 넣는다. 꺾쇠 없이 `&uart0`을 쓰면 숫자가 아니라 경로 문자열이 된다. label 자체는 dtb에 남지 않고, `-@`로 컴파일해야 `__symbols__`로 남아 overlay가 쓸 수 있다.

> A phandle is a 32-bit integer handle that identifies a node, so other nodes can point to it — that's how many devices share one interrupt controller or clock provider. In source you put a label on the node and reference it as `<&label>`; dtc assigns a number, adds a `phandle` property to the target, and writes that number in the referencing cell. Without the angle brackets, `&label` expands to the node's path string instead. Labels themselves are gone in the dtb unless you compile with `-@`, which emits a `__symbols__` node for overlays.

**Q.** Walk me through the structure of a `.dtb` file.

**A.** 40바이트 헤더(매직 0xd00dfeed, totalsize, 각 블록 오프셋, 버전 17), memory reservation 블록((u64 주소, u64 크기) 쌍, 0/0으로 끝), structure 블록(BEGIN_NODE 1 + 이름, PROP 3 + 길이 + 이름 오프셋 + 값, END_NODE 2, END 9 토큰 스트림, 4바이트 정렬), strings 블록(프로퍼티 이름을 한 번씩만 저장). 모든 정수는 big-endian. 저는 60줄 C 파서로 직접 걸어 보고 fdtdump와 결과가 같은지 확인해 봤다.

> It's a 40-byte header — magic 0xd00dfeed, total size, offsets to the other blocks, version 17 — followed by the memory reservation block, the structure block, and the strings block. The structure block is a depth-first token stream: BEGIN_NODE with the inline name, PROP with length, an offset into the strings block for the name, and the value, END_NODE, and finally END, all 4-byte aligned and big-endian. Property names are deduplicated in the strings block. I wrote a 60-line parser that walks it and matched fdtdump's output byte for byte on the QEMU virt tree.

**Q.** How does the kernel get the device tree, and how can you inspect what it actually used?

**A.** 부트로더가 dtb를 RAM에 올리고 arm64에서는 `x0`에 물리 주소를 넣어 커널로 점프한다. 부트로더는 그 전에 `/chosen`에 bootargs·initrd 주소를 써 넣는다. 커널은 초기에 flat 상태로 `/chosen`과 `/memory`를 읽고, `unflatten_device_tree()`로 `device_node` 트리를 만든 뒤 `of_platform_populate()`로 디바이스를 만든다. 실제로 쓰인 것은 `/proc/device-tree`(= `/sys/firmware/devicetree/base`)에서 프로퍼티별 파일로 보고, 원본 blob은 `/sys/firmware/fdt`에 있다. 그래서 "내 dts 수정이 반영됐나"는 소스가 아니라 이 두 곳에서 확인한다.

> The bootloader loads the dtb into RAM, patches `/chosen` with bootargs and the initrd location, and on arm64 passes its physical address in x0. Early boot code reads `/chosen` and `/memory` straight from the flat blob, then `unflatten_device_tree` builds the `device_node` tree and `of_platform_populate` creates platform devices for nodes that are enabled. To see what the kernel really used, I look at `/proc/device-tree`, where each property is a file with the raw big-endian bytes, or grab `/sys/firmware/fdt` and decompile it with dtc. I never trust the source tree alone, because the bootloader may have loaded a different dtb or modified it.

**Q.** How would you disable or modify a node defined in the SoC `.dtsi` from a board `.dts`?

**A.** label로 다시 열어서 덮어쓴다: `&i2c1 { status = "okay"; clock-frequency = <400000>; };`. dtc는 같은 노드 정의를 병합하고 나중 값이 이긴다. 끌 때는 `status = "disabled"`가 기본이고, 노드를 아예 없애야 하면 `/delete-node/ &label;`, 프로퍼티만 지우려면 `/delete-property/ name;`. label이 없으면 `&{/path}`로 지정한다. 차이는 disabled는 노드가 남아 다른 노드의 phandle 참조가 깨지지 않는다는 것.

> I reopen the node by its label in the board file, for example `&i2c1 { status = "okay"; clock-frequency = <400000>; };` — dtc merges multiple definitions of the same node and the last value wins. To turn something off I prefer `status = "disabled"`, because the node stays in the tree and any phandle references to it remain valid. If the hardware really isn't there, I use `/delete-node/`, and `/delete-property/` to drop a single inherited property. If there's no label, `&{/full/path}` works.

**Q.** Why does the kernel run the C preprocessor on `.dts` files?

**A.** `#include <dt-bindings/...>` 헤더의 상수(`GIC_SPI`, `IRQ_TYPE_LEVEL_HIGH`, 클록 ID, GPIO 플래그)를 드라이버 C 코드와 공유하기 위해서다. dtc 자체의 `/include/`는 텍스트 삽입만 하고 매크로가 없다. 커널은 `cpp -nostdinc -undef -D__DTS__ -x assembler-with-cpp`로 먼저 전처리한 뒤 dtc에 넘긴다. `-undef`가 없으면 `linux,code` 같은 이름의 `linux`가 매크로로 치환되는 사고가 난다. 손으로 같은 명령을 돌려서 커널 빌드 결과와 바이트 단위로 같은 dtb를 만들어 본 적이 있다.

> So the device tree and the drivers can share the same numeric constants — interrupt types, clock IDs, GPIO flags — from `include/dt-bindings`. dtc's own `/include/` is just textual inclusion with no macros. Kbuild runs cpp with `-nostdinc -undef -D__DTS__ -x assembler-with-cpp` first, then dtc on the result; `-undef` matters because otherwise the predefined `linux` macro would mangle names like `linux,code`. I reproduced that pipeline by hand and got dtbs byte-identical to the kernel build.

## 20. 직접 해보기

1. **개념**: 루트가 `#address-cells = <2>; #size-cells = <1>;`이고 자식에 `reg = <0x0 0x10000000 0x1000 0x0 0x20000000 0x2000>;`이 있다. 영역은 몇 개이고 각각 어디서 몇 바이트인가?
   정답/힌트: 쌍당 3셀 → 6셀이니 2쌍. 0x10000000부터 0x1000바이트, 0x20000000부터 0x2000바이트.
2. **개념**: `ranges = <0x0 0x0 0xf0000000 0x10000000>;`이 있는 버스(자식 1셀, 부모 2셀, 크기 1셀) 아래 `gpio@4000`의 `reg` 주소는 CPU 물리로 얼마인가? 그 버스에서 `ranges`를 지우면 어떻게 되나?
   정답/힌트: 0xf0004000. `ranges`가 없으면 번역 불가 — 커널이 MMIO 자원을 못 만들어 probe에서 ioremap이 실패한다.
3. **코드**: §11의 `d2_fdtparse`에 memory reservation 블록 출력(`/memreserve/ 0x... 0x...;`)을 추가해서 `d2_tiny.dtb`도 fdtdump와 IDENTICAL이 되게 하라.
   정답/힌트: `off_mem_rsvmap`부터 16바이트씩 (u64 BE address, u64 BE size)를 읽고 둘 다 0이면 멈춘다. `be()`를 두 번 불러 `((uint64_t)hi << 32) | lo`.
4. **코드**: §12의 `d2_libfdt`를 확장해 `reg`에 쌍이 여러 개면(GIC의 `intc@8000000`) 모두 번역하게 하라. 그리고 `fdt_node_offset_by_phandle()`로 `d2-test`의 `d2-clk` phandle을 따라가 대상 노드 경로(`/apb-pclk`)를 출력하라.
   정답/힌트: `len / 4 / (na + ns)`개 쌍을 루프. phandle은 `fdt32_to_cpu(*(const fdt32_t *)fdt_getprop(...))`로 읽고 `fdt_get_path()`.
5. **dtc**: §9의 `d2_warn.dts`를 경고 0개가 될 때까지 고쳐라. 고칠 때마다 다시 돌려서 "Failed prerequisite"로 숨어 있던 경고가 새로 나타나는 것을 관찰하라.
   정답/힌트: `d2-bus@3000`에 cells 추가 → `d2-d`의 `reg`를 2셀로 → `d2-a`에 `reg` 추가 또는 `@` 삭제 → `d2-b` 이름에 `@2000` → 마지막으로 `unique_unit_address`가 드러난다.
6. **QEMU 관찰**: §14의 `d2_virt.dts`에서 `d2-sub`의 `ranges`를 지우고 부팅해 `/sys/bus/platform/devices`의 `d2-dev` 이름이 어떻게 바뀌는지 보라. 빈 `ranges;`로 바꾸면 또 어떻게 되나?
   정답/힌트: 두 경우 모두 이름이 `d2-bus@b000000:d2-sub@80040000:d2-dev@100`이 된다(직접 부팅해 확인한 결과). `ranges`가 없으면 번역 불가, 빈 `ranges;`면 0x100이 그대로 `d2-bus` 공간으로 넘어가지만 [0x80000000, +0x100000) 밖이라 역시 실패 — `of_device_make_bus_id()`는 번역에 실패하면 경로 조각을 `:`로 이어 이름을 만든다. 디바이스 자체는 simple-bus 자식이라 여전히 생긴다.
7. **/proc 관찰**: 게스트에서 `hexdump -C /sys/firmware/fdt | head -3`의 헤더를 손으로 해석하고, `off_dt_strings`부터 몇 바이트를 덤프해 `compatible`, `reg` 같은 이름이 strings 블록에 들어 있는 것을 확인하라.
   정답/힌트: busybox `hexdump -s <offset> -n 128 -C /sys/firmware/fdt`. §14 출력에서 `off_dt_strings` = 0x1ea4.

## 21. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| DT (Device Tree) | 하드웨어 기술 데이터 | 커널 코드와 분리된 "이 보드에 무엇이 어디 있나" |
| DTS / DTSI | Device Tree Source | 사람이 쓰는 텍스트. `.dtsi`는 include용(SoC 공통) |
| DTB / FDT | Device Tree Blob / Flattened DT | dtc가 만든 바이너리. 부트로더가 커널에 넘김 |
| dtc | Device Tree Compiler | dts ↔ dtb 변환기 겸 린터 |
| node | 노드 | 트리의 디렉터리. `name@unit-address` |
| property | 프로퍼티 | 노드의 이름=값. 값은 바이트 배열 |
| cell | 셀 | 32비트 big-endian 정수, `<...>` 안의 한 칸 |
| unit-address | 유닛 주소 | `@` 뒤의 16진수. `reg` 첫 주소와 같아야 함 |
| phandle | 노드 핸들 | 노드를 가리키는 32비트 ID |
| label | 레이블 | 소스 전용 별명 `uart0:`. `&uart0`으로 참조 |
| `#address-cells` / `#size-cells` | 셀 개수 | 자식 `reg`의 주소/크기가 몇 셀인지 |
| `reg` | 레지스터 영역 | (주소, 크기) 쌍 배열, 부모 버스 주소 공간 기준 |
| `ranges` | 주소 번역 표 | (자식 주소, 부모 주소, 길이). 빈 값 = 1:1 |
| `dma-ranges` | DMA 주소 번역 | 디바이스가 보는 메모리 주소 ↔ CPU 물리 주소 |
| `/chosen` | 선택된 파라미터 | bootargs·initrd·stdout-path. 부트로더가 고쳐 씀 |
| `/aliases` | 별칭 | `serial0` 등 → 디바이스 번호 고정 |
| `status` | 상태 | `okay`/없음이면 디바이스 생성, `disabled`면 안 함 |
| `__symbols__` | 심볼 노드 | `dtc -@`가 만드는 label → 경로 표 (overlay용) |
| libfdt | FDT 라이브러리 | dtc 프로젝트의 C 라이브러리. U-Boot·커널·QEMU가 공유 |
| unflatten | 펼치기 | 커널이 FDT를 `device_node` 포인터 트리로 바꾸는 것 |
| `struct device_node` | 커널 노드 구조체 | 이름·부모·자식·phandle·프로퍼티 목록 |

## 22. 요약 & 체크리스트

DT는 커널 밖에 있는 하드웨어 기술 데이터다. 문법은 단순하다: 노드 트리 + 바이트 배열 프로퍼티. 값 문법(`<셀>`, `"문자열"`, `[바이트]`)은 dtb에서 타입을 잃고 big-endian 바이트만 남으며, 해석은 바인딩과 드라이버의 몫이다. 노드끼리는 phandle(`<&label>`)로 연결하고, label은 소스 전용이다. 주소는 **부모의** `#address-cells`/`#size-cells`로 `reg`를 끊어 읽고, 버스마다 `ranges`를 따라 `addr - child + parent`로 번역해 루트(CPU 물리 주소)까지 올라간다 — `ranges`가 없으면 MMIO가 아니다. SoC `.dtsi`는 꺼 두고 보드 `.dts`가 label로 열어 `status = "okay"`로 켜는 것이 기본 패턴이고, dtc 경고는 대부분 진짜 버그다. `.dtb`는 헤더 + 예약 블록 + 토큰 스트림 + 이름 문자열 블록이라 60줄 C로도 읽을 수 있다. 커널은 이걸 `device_node` 트리로 펼쳐 `/proc/device-tree`에 그대로 보여 주고, 번역된 주소로 platform device를 만든다 — 실제로 쓰인 DT는 항상 거기서 확인한다.

- [ ] 노드 이름의 세 부분(label, node-name, unit-address)과 unit-address 규칙을 설명할 수 있다
- [ ] 문자열·문자열 목록·셀·64비트·바이트열·boolean 프로퍼티를 쓰고, dtb에서 각각 어떤 바이트가 되는지 말할 수 있다
- [ ] `<&label>`(phandle)과 `&label`(경로)의 차이를 설명하고, 역컴파일된 숫자 phandle을 따라갈 수 있다
- [ ] `/chosen`, `/aliases`, `/memory`, `/cpus`의 역할과 부트로더가 `/chosen`에 쓰는 것을 말할 수 있다
- [ ] 부모의 `#address-cells`/`#size-cells`로 임의의 `reg`를 손으로 해석할 수 있다
- [ ] `ranges`를 따라 여러 단의 버스 주소를 CPU 물리 주소로 번역하고, 빈 `ranges`와 없는 `ranges`를 구분할 수 있다
- [ ] label 덮어쓰기, `status`, `/delete-node/`, `/delete-property/`로 SoC 정의를 보드에서 고칠 수 있다
- [ ] `/include/`와 `#include`의 차이, 커널의 cpp + dtc 명령을 설명하고 손으로 재현할 수 있다
- [ ] `unit_address_vs_reg`, `reg_format`, `avoid_default_addr_size` 경고를 보고 원인을 찾을 수 있다
- [ ] FDT 헤더 필드와 structure 토큰(1, 2, 3, 4, 9)을 hexdump에서 읽을 수 있다
- [ ] libfdt 또는 직접 짠 C 코드로 dtb에서 노드·프로퍼티를 읽을 수 있다
- [ ] `fdtget`/`fdtput`/`/proc/device-tree`/`/sys/firmware/fdt`로 런타임 DT를 확인하고 고칠 수 있다
