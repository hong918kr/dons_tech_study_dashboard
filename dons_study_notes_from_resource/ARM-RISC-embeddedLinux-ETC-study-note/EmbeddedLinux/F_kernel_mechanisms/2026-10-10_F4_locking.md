# F4. 동시성과 락 — spinlock · mutex · semaphore · rwlock · atomic · RCU · seqlock · per-CPU

> **이 노트를 다 읽으면**: 커널 안의 동시성이 어디서 오는지(SMP·선점·hardirq·softirq) 그림으로 설명하고, "이 데이터를 누가 또 만지나"로 `spin_lock`/`_bh`/`_irq`/`_irqsave`/mutex를 고를 수 있다 · spinlock vs mutex, raw_spinlock vs spinlock(PREEMPT_RT), atomic·refcount·per-CPU의 차이를 실제 측정값으로 말할 수 있다 · RCU의 reader/updater/grace period와 seqlock의 retry를 코드로 짜고 설명할 수 있다 · lockdep 경고(circular dependency, inconsistent lock state, invalid wait context, sleeping in atomic)와 `/proc/lock_stat`을 직접 읽을 수 있다
> **왜 필요한가**: "spinlock과 mutex의 차이는?", "인터럽트 핸들러와 공유하는 데이터는 어떻게 보호하나?", "RCU가 뭔가?"는 Linux 드라이버 면접의 **최빈출 질문**이고, 실무 드라이버 버그(가끔 멈춤, 가끔 값이 틀림, 부팅 때 lockdep 경고)의 절반이 여기서 나온다
> **Don 기준 난이도**: ISR과 메인 루프 사이 공유 변수를 IRQ 마스크로 지키는 법, 멀티코어 SSD 펌웨어의 공유 메모리 락, RTOS mutex·semaphore는 이미 안다 / 새로 배울 부분은 "선점·softirq까지 포함한 4가지 동시성 원천", spinlock 변형 고르기, sleep 가능 여부 규칙, RCU·seqlock·per-CPU 같은 Linux 고유 도구, 그리고 lockdep이라는 "일어나지 않은 deadlock까지 잡는" 검사기
> **선행 노트**: A8(유저스페이스 동기화 — futex·pthread mutex·C11 atomics), E4 §5·§10(atomic context, `int++` 레이스) — F2(실행 컨텍스트)·F5(메모리 배리어)·F6(인터럽트)·F7(지연 작업)·M7(커널 디버그 도구)로 이어진다

## 0. 큰 그림 — 커널 안의 동시성은 어디서 오나

A8에서는 유저 프로세스의 스레드끼리 경쟁했다. 거기서는 "스레드를 만들지 않으면 동시성이 없다." 커널 코드는 다르다. 드라이버 함수 하나는 **내가 아무것도 하지 않아도** 네 방향에서 동시에 찔린다.

Don의 SSD 펌웨어로 비유하면 이렇다. 펌웨어에서는 "메인 루프 ↔ ISR" 두 주체만 신경 쓰면 됐고, 멀티코어 컨트롤러면 "코어 0 ↔ 코어 1" 공유 메모리가 하나 더 있었다. 커널에서는 여기에 **선점(preemption)** 이 붙는다. 같은 CPU에서도 내 함수가 아무 명령 사이에서나 멈추고 다른 태스크가 같은 함수를 실행할 수 있다(RTOS의 preemptive 스케줄러와 같다). 그리고 ISR이 두 층이다. 진짜 하드웨어 인터럽트(**hardirq**)와, hardirq가 끝날 때 이어서 도는 **softirq**(네트워크 수신, 블록 완료, 타이머 콜백 등 "나중에 처리할 일"; F7).

### 0.1 이 노트의 지도

| 도구 | 한 줄 정의 | 기다리는 방식 | 잠들어도 되는 곳에서만? | 절 |
|---|---|---|---|---|
| `spinlock_t` | 짧은 구간 상호 배제, 선점 꺼짐 | busy-wait (돈다) | 아니다, 어디서나 (IRQ 포함) | §3, §4 |
| `raw_spinlock_t` | PREEMPT_RT에서도 진짜로 도는 spinlock | busy-wait | 아니다 | §4.4 |
| `struct mutex` | 주인(owner) 있는 잠드는 락 | 잠깐 돌다가 잠든다 | **예** (process context만) | §5 |
| `struct semaphore` | 개수 세는 잠드는 락 (legacy) | 잠든다 | 예 | §6 |
| `rwlock_t` / `rw_semaphore` | 읽기 여럿·쓰기 하나 | 돈다 / 잠든다 | 아니다 / 예 | §7 |
| `atomic_t`, `refcount_t`, bitops | 변수 하나를 락 없이 원자적으로 | 없음 (하드웨어 명령) | 어디서나 | §8 |
| per-CPU 변수 | CPU마다 따로 가진 사본 | 없음 (공유 자체를 없앰) | 어디서나 (선점만 주의) | §9 |
| RCU | 읽기는 락 없이, 쓰기는 복사 후 교체 + 나중에 해제 | 읽기 쪽 없음, 쓰기 쪽이 grace period를 기다림 | 읽기는 어디서나 | §11 |
| `seqlock_t` | 쓰기 우선, 읽기는 "바뀌었으면 다시" | 읽기 쪽이 retry | 읽기는 어디서나 | §12 |
| lockdep | 락 사용 규칙 위반을 런타임에 증명하는 검사기 | — | — | §13 |

### 1.1 예제 1 — 두 커널의 락 관련 설정 비교

무엇을 확인하나: 랩에는 커널이 두 개 있다. `out/Image`(defconfig 기반, 양산 커널과 비슷)와 `out/Image-dbg`(lockdep·lock_stat·atomic sleep 검사 켬). 같은 버그가 어느 커널에서 보이고 어느 커널에서 숨는지가 이 노트의 교재다.

```sh
uname -r      # VM 호스트 커널 (랩 모듈은 여기 넣지 않는다)
for f in linux-build linux-build-dbg; do echo "== $f"
  grep -E "^(# )?CONFIG_(PREEMPT|PREEMPT_RT|PROVE_LOCKING|LOCK_STAT|DEBUG_ATOMIC_SLEEP|PROVE_RAW_LOCK_NESTING|PROVE_RCU|SMP|QUEUED_SPINLOCKS|QUEUED_RWLOCKS|MUTEX_SPIN_ON_OWNER|PREEMPT_RCU|RCU_CPU_STALL_TIMEOUT)[= ]" /var/lab/out/$f/.config
done
```

```text

CONFIG_PREEMPT_RCU=y
CONFIG_SMP=y
CONFIG_MUTEX_SPIN_ON_OWNER=y
```

출력에서 볼 것:

- 두 커널 다 `CONFIG_PREEMPT=y`(완전 선점)이고 `PREEMPT_RT`는 아니다. 그래서 `spinlock_t`는 진짜 spinlock이다(§4.4에서 RT라면 무엇이 바뀌는지 본다).
- `QUEUED_SPINLOCKS`(qspinlock), `MUTEX_SPIN_ON_OWNER`(mutex의 optimistic spinning), `PREEMPT_RCU`(선점 가능한 RCU reader)가 켜져 있다. 이 셋이 §3·§5·§11의 측정값을 설명한다.
- 디버그 커널에만 `PROVE_LOCKING`(lockdep), `LOCK_STAT`, `DEBUG_ATOMIC_SLEEP`, `PROVE_RAW_LOCK_NESTING`이 있다. 양산 커널(왼쪽)에서는 같은 버그가 **아무 말 없이** 지나간다.

### 1.2 예제 2 — 게스트 실행기 `run_guest.sh`

무엇을 확인하나: `.ko`와 테스트 스크립트를 랩 initramfs 사본에 넣고, `LAB_CMD=sh~/t.sh`로 실행 후 자동 종료하는 스크립트. 이 노트의 모든 게스트 출력은 이것으로 얻었다 (E4의 실행기와 같은 구조, 기본 커널만 `Image-dbg`, 기본 CPU 수만 4).

```sh
#!/bin/bash
# usage: run_guest.sh <tag> <test.sh> [extra kernel args] ; env KIMG, FILES, SMP, TMO
set -e
tag=$1; t=$2; extra=$3
W=/var/tmp/F4/run_$tag
rm -rf "/var/tmp/F4/run_${tag:?}" && mkdir -p "$W/r"
cp -a /var/lab/build/rootfs/. $W/r/
for f in $FILES; do cp $f $W/r/; done
cp $t $W/r/t.sh
(cd $W/r && find . | cpio -o -H newc --quiet | gzip) > $W/i.gz
KIMG=${KIMG:-/var/lab/out/Image-dbg}
timeout ${TMO:-180} qemu-system-aarch64 -machine virt -cpu cortex-a57 -smp ${SMP:-4} -m 512M -nographic -no-reboot \
  -kernel $KIMG -initrd $W/i.gz -append "console=ttyAMA0 quiet $extra LAB_CMD=sh~/t.sh" 2>&1 | tr -d '\r'
```

모듈 빌드는 커널마다 빌드 트리가 다르다. 디버그 커널용 모듈(vermagic `6.18.55-dbg`)을 일반 커널에 넣으면 로드가 거부되므로 두 벌을 만든다.

```sh
# build.sh <mod> [dbg|std]  →  /var/tmp/F4/<dbg|std>/<mod>/<mod>.ko
KB=/var/lab/out/linux-build-dbg        # std 이면 /var/lab/out/linux-build
D=/var/tmp/F4/$k/$m
mkdir -p $D && cp /Users/donh/.elinux_scratch/F4/$m.c $D/ && echo "obj-m += $m.o" > $D/Kbuild
make -s -C $KB M=$D -j2 modules
```

출력에서 볼 것: 모든 모듈은 `-Wall` 계열 Kbuild 기본 경고에서 **경고 0개**로 빌드됐다(`make -s`는 경고가 있으면 그대로 찍는다). 게스트 출력에서 `Flash device refused suspend ...` 같은 poweroff 잡음 줄과, 콘솔과 `dmesg`에 같은 줄이 두 번 찍히는 중복은 노트에서 지웠다.

> QEMU는 KVM 없이 TCG(소프트웨어 에뮬레이션)로 돈다. 아래 처리량 숫자는 **상대 비교용**이다. 실제 Cortex-A 칩의 절대값과 다르고, 특히 원자 명령·배리어 비용은 TCG가 실리콘과 다르게 흉내 낸다. 같은 VM에서 다른 작업이 동시에 돌아서 실행마다 흔들리므로 3회 실행의 중앙값을 쓴다.

## 2. 문제를 먼저 보자 — 카운터 하나, CPU 넷

### 2.1 직관

E4 §10에서 `int++`가 SMP에서 원자적이지 않다는 것을 봤다. 여기서는 같은 레이스를 **여섯 가지 방법으로 고치고, 각각의 비용을 잰다.** 이 숫자 하나가 "spinlock vs mutex vs atomic vs per-CPU"를 고르는 감각을 준다.

`plain++`는 arm64에서 `ldr` → `add` → `str` 세 명령이다. 두 CPU가 같은 값을 읽고 각자 +1을 쓰면 하나가 덮인다(lost update). Don이 아는 말로 하면 read-modify-write가 버스 트랜잭션 하나가 아니라는 것이다.

### 2.2 예제 3 — `f4_race`: 여섯 가지 보호 방법

무엇을 확인하나: CPU마다 kthread 하나(`kthread_bind`로 고정), 각자 `loops`번 증가. 보호 방법만 바꿔 가며 결과 값과 걸린 시간을 찍는다. (모듈이 길어서 두 조각으로 나눴다. 실제로는 한 파일이다.)

```c
// SPDX-License-Identifier: GPL-2.0
/* f4_race: 4 kthreads x loops increments, one shared counter, 6 ways to protect it */
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/kthread.h>
#include <linux/mutex.h>
#include <linux/percpu.h>
#include <linux/ktime.h>
#include <linux/delay.h>

enum { M_NONE, M_SPIN, M_IRQSAVE, M_MUTEX, M_ATOMIC, M_PCPU, M_NR };
static const char * const name[] = { "none", "spinlock", "spin_irqsave", "mutex", "atomic", "percpu" };
static int loops = 200000;
module_param(loops, int, 0444);
static int mask = 0x3f;		/* bit i = run mode i */
module_param(mask, int, 0444);
static DEFINE_SPINLOCK(f4_spin);
static DEFINE_MUTEX(f4_mutex);
static unsigned long plain;
static atomic_long_t f4_atomic;
static DEFINE_PER_CPU(unsigned long, f4_pcpu);
static atomic_t ready, go, running;
static DECLARE_COMPLETION(f4_done);
static int mode;

static int f4_worker(void *arg)
{
	unsigned long flags;
	int i;

	atomic_inc(&ready);
	while (!atomic_read(&go))
		cpu_relax();
	for (i = 0; i < loops; i++) {
		switch (mode) {
		case M_NONE:    WRITE_ONCE(plain, READ_ONCE(plain) + 1); break;
		case M_SPIN:    spin_lock(&f4_spin); plain++; spin_unlock(&f4_spin); break;
		case M_IRQSAVE: spin_lock_irqsave(&f4_spin, flags); plain++;
				spin_unlock_irqrestore(&f4_spin, flags); break;
		case M_MUTEX:   mutex_lock(&f4_mutex); plain++; mutex_unlock(&f4_mutex); break;
		case M_ATOMIC:  atomic_long_inc(&f4_atomic); break;
		case M_PCPU:    this_cpu_inc(f4_pcpu); break;
		}
	}
	if (atomic_dec_and_test(&running))
		complete(&f4_done);
	return 0;
}
```

```c
/* f4_race.c (계속) — 모드마다 스레드 4개를 만들어 동시에 출발시키고 시간을 잰다 */
static int __init f4_race_init(void)
{
	unsigned int n = num_online_cpus(), i, cpu;
	unsigned long total, exp = (unsigned long)n * loops;
	s64 us;
	ktime_t t0;

	for (mode = 0; mode < M_NR; mode++) {
		if (!(mask & BIT(mode)))
			continue;
		plain = 0; atomic_long_set(&f4_atomic, 0);
		for_each_possible_cpu(cpu)
			per_cpu(f4_pcpu, cpu) = 0;
		atomic_set(&ready, 0); atomic_set(&go, 0); atomic_set(&running, n);
		reinit_completion(&f4_done);
		for (i = 0; i < n; i++) {
			struct task_struct *t = kthread_create(f4_worker, NULL, "f4_race/%u", i);

			if (IS_ERR(t))
				return PTR_ERR(t);
			kthread_bind(t, i);
			wake_up_process(t);
		}
		while (atomic_read(&ready) < n)
			msleep(1);
		t0 = ktime_get();
		atomic_set(&go, 1);
		wait_for_completion(&f4_done);
		us = ktime_us_delta(ktime_get(), t0);
		total = mode == M_ATOMIC ? atomic_long_read(&f4_atomic) : plain;
		if (mode == M_PCPU) {
			total = 0;
			for_each_possible_cpu(cpu)
				total += per_cpu(f4_pcpu, cpu);
		}
		pr_info("%-12s total=%lu lost=%lu time=%lldus Mops/s=%llu.%02llu\n",
			name[mode], total, exp - total, us,
			div64_s64(exp, us), div64_s64(exp * 100, us) % 100);
	}
	return 0;
}

static void __exit f4_race_exit(void) { }
module_init(f4_race_init);
module_exit(f4_race_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("F4: counter race and its fixes");
```

## 3. spinlock — "잠깐이면 서서 기다린다"

### 3.1 직관

화장실 앞에서 문 손잡이를 계속 돌려 보는 사람을 떠올리자. 안에 있는 사람이 금방 나온다면 자리를 뜨는 것(잠들기)보다 서서 기다리는 편이 빠르다. 이것이 spinlock이다. 펌웨어로 치면 멀티코어 SoC의 하드웨어 세마포어 레지스터를 `while (HWSEM_LOCK != 0);`으로 폴링하는 것과 같다.

### 3.2 정의와 규칙

`spinlock_t`를 잡으면 커널은 두 가지를 한다.

1. **이 CPU의 선점을 끈다** (`preempt_disable()`). 락을 쥔 태스크가 선점당하면 다른 CPU들이 그 태스크가 다시 돌 때까지 헛돌기 때문이다. 단일 코어 커널(`CONFIG_SMP=n`)에서는 spinlock이 사실상 이것만 남는다.
2. **다른 CPU와 경쟁해 락 변수를 원자적으로 얻는다.** arm64에서는 qspinlock(MCS 큐 기반, 대기자가 각자 자기 캐시 라인에서 돈다)으로 구현된다.

그래서 spinlock을 쥔 구간은 **atomic context**다(F2). 규칙은 펌웨어 ISR 규칙과 같다.

- 잠들 수 있는 것은 아무것도 부르지 않는다: `msleep`, `mutex_lock`, `kmalloc(GFP_KERNEL)`, `copy_to_user`/`copy_from_user`(page fault로 잠들 수 있음), I2C/SPI 동기 전송.
- 구간은 짧게: 수십~수백 ns 수준의 포인터 조작·카운터·리스트 연결. 루프로 하드웨어를 폴링하지 않는다.
- 같은 CPU에서 같은 락을 두 번 잡으면 그 자리에서 영원히 돈다(재귀 금지).

### 3.3 API 한눈에

| API | 추가로 막는 것 | 언제 |
|---|---|---|
| `spin_lock` / `spin_unlock` | 선점 (+ 다른 CPU) | process context끼리, 또는 IRQ 핸들러 **안에서** 쓸 때 |
| `spin_lock_bh` / `spin_unlock_bh` | + 이 CPU의 softirq | process context ↔ softirq·tasklet·timer_list 공유 데이터 |
| `spin_lock_irq` / `spin_unlock_irq` | + 이 CPU의 IRQ (끝나면 **무조건 켬**) | IRQ가 켜져 있다고 **확신**할 때만 |
| `spin_lock_irqsave(l, flags)` / `spin_unlock_irqrestore(l, flags)` | + 이 CPU의 IRQ (끝나면 **원래 상태로 복원**) | process ↔ hardirq 공유, 또는 호출자 상태를 모를 때 |
| `spin_trylock` | — | 못 잡으면 바로 0 반환 (기다리지 않음) |
| `DEFINE_SPINLOCK(x)` / `spin_lock_init(&x)` | — | 정적 / 동적(구조체 안) 초기화 |

`_irqsave`의 `flags`는 포인터가 아니라 **변수 이름**을 넘긴다(매크로다). 펌웨어의 `primask = __get_PRIMASK(); __disable_irq(); ... __set_PRIMASK(primask);` 패턴과 정확히 같다.

### 3.4 함정

- **"단일 코어니까 spinlock 필요 없다"** — 선점과 IRQ는 단일 코어에도 있다. 그리고 같은 드라이버가 4코어 i.MX8에서도 돈다.
- **락으로 보호하는 것은 코드가 아니라 데이터다.** "이 락은 `fifo_head`, `fifo_tail`, `count`를 보호한다"고 구조체 옆에 주석으로 적는 것이 커널 관행이다.
- **IRQ 끄는 시간도 지연이다.** `_irqsave` 구간이 길면 다른 장치의 인터럽트 지연(latency)이 늘어난다. 측정은 `irqsoff` tracer(M5)로 한다.

### 4.1 직관 — 같은 CPU의 인터럽트가 같은 락을 원하면

### 4.3 예제 4 — 진짜 self-deadlock (lockdep 없는 일반 커널)

무엇을 확인하나: process context에서 `raw_spin_lock`(IRQ 켜진 채)으로 락을 쥐고, 같은 CPU에 0.5 ms 뒤 터지는 hardirq 모드 hrtimer를 건 다음 5 ms 바쁘게 기다린다. 타이머 콜백도 같은 락을 잡는다. 모듈 전체(`mode` 0~3)는 아래와 같다. 이 절에서는 `mode=2`를 쓴다. `HRTIMER_MODE_REL_HARD`는 콜백을 softirq로 미루지 않고 **타이머 인터럽트 안에서 바로** 실행하라는 뜻이라, 장치 IRQ 없이도 "hardirq 핸들러"를 만들 수 있다. (`raw_spinlock_t`를 쓴 이유는 §4.5에서 본다.)

```c
// SPDX-License-Identifier: GPL-2.0
/* f4_irqlock: a lock shared with a hardirq-context hrtimer callback */
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/hrtimer.h>
#include <linux/spinlock.h>
#include <linux/delay.h>

/* 0 = raw_spin_lock in process ctx (BUG)   1 = raw_spin_lock_irqsave (OK)
 * 2 = real self-deadlock                   3 = spinlock_t inside hard hrtimer */
static int mode;
module_param(mode, int, 0444);
static DEFINE_RAW_SPINLOCK(f4_raw_lock);
static DEFINE_SPINLOCK(f4_stat_lock);
static unsigned long f4_samples;
static struct hrtimer f4_timer;

static enum hrtimer_restart f4_tick(struct hrtimer *t)	/* runs in hardirq */
{
	if (mode == 3) {
		spin_lock(&f4_stat_lock);
		f4_samples++;
		spin_unlock(&f4_stat_lock);
	} else {
		raw_spin_lock(&f4_raw_lock);	/* IRQs already off here: fine */
		f4_samples++;
		raw_spin_unlock(&f4_raw_lock);
	}
	return HRTIMER_NORESTART;
}
```

```c
/* f4_irqlock.c (계속) */
static int __init f4_irqlock_init(void)
{
	unsigned long flags;

	hrtimer_setup(&f4_timer, f4_tick, CLOCK_MONOTONIC, HRTIMER_MODE_REL_HARD);
	if (mode == 2) {	/* hold the lock (IRQs ON) while the timer fires here */
		raw_spin_lock(&f4_raw_lock);
		hrtimer_start(&f4_timer, us_to_ktime(500), HRTIMER_MODE_REL_HARD);
		pr_info("cpu%d holds f4_raw_lock, IRQs ON, timer due in 500us\n",
			smp_processor_id());
		mdelay(5);
		raw_spin_unlock(&f4_raw_lock);
		pr_info("never printed\n");
		return 0;
	}
	hrtimer_start(&f4_timer, us_to_ktime(500), HRTIMER_MODE_REL_HARD);
	msleep(20);		/* let lockdep record the hardirq-side usage first */
	if (mode == 1) {
		raw_spin_lock_irqsave(&f4_raw_lock, flags);	/* local IRQs OFF */
		f4_samples = 0;
		raw_spin_unlock_irqrestore(&f4_raw_lock, flags);
	} else {
		raw_spin_lock(&f4_raw_lock);			/* local IRQs ON  */
		f4_samples = 0;
		raw_spin_unlock(&f4_raw_lock);
	}
	pr_info("mode=%d done\n", mode);
	return 0;
}

static void __exit f4_irqlock_exit(void) { hrtimer_cancel(&f4_timer); }
module_init(f4_irqlock_init);
module_exit(f4_irqlock_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("F4: lock shared with hardirq - irqsave or deadlock");
```

### 4.6 `_irq` vs `_irqsave`

`spin_unlock_irq`는 IRQ를 **무조건 켠다.** 호출자가 이미 IRQ를 끈 상태였다면(다른 `_irqsave` 구간 안에서 내 함수가 불렸다면) 내 함수가 끝나는 순간 호출자의 IRQ 보호가 몰래 풀린다. 그래서:

- 함수가 항상 IRQ 켜진 process context(예: `ioctl`, `probe`)에서만 불린다고 확신하면 `_irq` (flags 저장·복원 비용이 조금 적다).
- 여러 곳(다른 락 안, IRQ 핸들러, 타이머)에서 불릴 수 있는 헬퍼 함수면 `_irqsave`. 확신이 없으면 `_irqsave`.

### 4.7 raw_spinlock vs spinlock, 그리고 PREEMPT_RT — 예제 7 (`mode=3`)

일반 커널에서 `spinlock_t`는 `raw_spinlock_t`를 감싼 것에 불과하다. 차이는 **PREEMPT_RT** 커널(실시간 패치, 6.12부터 메인라인에 통합)에서 생긴다.

| | 일반 커널 (`PREEMPT`) | PREEMPT_RT 커널 |
|---|---|---|
| `spinlock_t` | 진짜 spinlock (선점 끔) | **잠드는 rt_mutex** (priority inheritance, 선점 가능) |
| `raw_spinlock_t` | 진짜 spinlock | 진짜 spinlock (그대로) |
| `request_irq` 핸들러 | hardirq에서 실행 | 기본적으로 **스레드**로 실행 (force-threaded) |
| HARD hrtimer 콜백, irqchip 코드, 스케줄러 내부 | hardirq | 여전히 hardirq |

그래서 규칙은 이렇다. 드라이버는 거의 항상 `spinlock_t`를 쓴다. **RT에서도 진짜 hardirq로 남는 곳**(irqchip 드라이버, `HRTIMER_MODE_HARD` 콜백, `IRQF_NO_THREAD` 핸들러, 스케줄러·printk 내부)에서만 `raw_spinlock_t`를 쓴다. RT가 아닌 커널에서도 디버그 옵션 `PROVE_RAW_LOCK_NESTING`이 이 규칙을 검사한다. 위 모듈의 `mode=3`은 HARD hrtimer 콜백에서 `spinlock_t`를 잡는다.

## 5. mutex — "오래 걸리면 자리를 비우고 잔다"

### 5.1 정의

`struct mutex`는 **잠드는(sleeping) 락**이다. 못 잡으면 태스크를 대기 리스트에 넣고 `schedule()`로 CPU를 양보한다. 락이 풀리면 깨어난다. RTOS의 mutex와 같은 개념이고, A8의 pthread mutex(futex)의 커널판이다.

| 규칙 (`Documentation/locking/mutex-design.rst`) | 이유 |
|---|---|
| 한 번에 한 태스크만 쥔다, **잡은 태스크만 푼다** | owner 필드에 `task_struct` 포인터를 기록한다. 디버그·optimistic spinning·PI가 이것을 쓴다 |
| 재귀 잠금 금지 | 같은 태스크가 두 번 잡으면 자기 자신을 영원히 기다린다 |
| **process context에서만** (hardirq·softirq·tasklet·timer 콜백 금지) | 잠들 수 없는 문맥이다 |
| 쥔 채로 태스크가 종료되면 안 된다, 쥔 동안 메모리를 해제하면 안 된다 | 디버그 커널이 검사한다 |
| 반드시 API로 초기화 (`DEFINE_MUTEX`, `mutex_init`) | lockdep 클래스 등록 |

API는 네 가지 맛이 있다.

```c
/* 실행하지 않은 코드 조각 — 드라이버 .write 에서의 전형적인 모양 */
static ssize_t f4_write(struct file *f, const char __user *buf, size_t n, loff_t *pos)
{
	struct f4_dev *d = f->private_data;
	ssize_t ret;

	if (mutex_lock_interruptible(&d->lock))	/* Ctrl-C로 깨면 -EINTR */
		return -ERESTARTSYS;			/* 시그널 처리 후 syscall 재시작 */
	ret = f4_i2c_write_cfg(d, buf, n);		/* 잠들어도 되는 구간 */
	mutex_unlock(&d->lock);
	return ret;
}
/* mutex_lock(&l)            : 시그널로 못 깸 (D 상태) — 짧게 확실히 끝날 때
 * mutex_lock_interruptible  : 시그널로 깸 → 0이 아니면 실패 — 유저가 부른 syscall 경로
 * mutex_lock_killable       : SIGKILL 같은 치명적 시그널로만 깸
 * mutex_trylock(&l)         : 성공하면 1 (pthread_mutex_trylock은 성공이 0 — 반대!)
 * guard(mutex)(&l);         : 스코프 끝에서 자동 unlock (linux/cleanup.h, 6.5+) */
```

### 5.2 mutex는 바로 잠들지 않는다 — 세 단계 경로

1. **fast path**: owner가 0이면 `cmpxchg`로 owner = current. 경합 없으면 원자 명령 하나로 끝(futex의 fast path와 같은 생각).
2. **optimistic spinning (mid path)**: owner가 **지금 다른 CPU에서 실행 중**이면 곧 풀 가능성이 높다. 잠들고 깨는 비용(수 µs)보다 잠깐 도는 게 싸므로, owner가 실행 중인 동안만 돈다. 여러 대기자가 한꺼번에 owner를 폴링하지 않도록 MCS 큐(`osq`)로 한 명씩 줄을 세운다. (`CONFIG_MUTEX_SPIN_ON_OWNER=y`, 예제 1에서 확인)
3. **slow path**: owner가 잠들었거나 선점됐으면 `wait_list`에 들어가 `schedule()`.

그래서 "mutex = 무조건 context switch"는 틀린 말이다. 짧은 구간이면 mutex도 사실상 spin으로 끝난다.

### 5.3 예제 8 — spinlock 안에서 mutex를 잡으면

무엇을 확인하나: 실무에서 가장 흔한 버그. "FIFO는 spinlock으로 보호하는데, 그 안에서 I2C로 레지스터 하나만 더 읽자" — I2C 어댑터는 내부에서 mutex(버스 락)를 잡는다. 이 모양을 그대로 만든다.

```c

#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/spinlock.h>
#include <linux/mutex.h>

static DEFINE_SPINLOCK(f4_fifo_lock);
static DEFINE_MUTEX(f4_i2c_mutex);	/* think: i2c adapter bus lock */

static int __init f4_sleep_init(void)
{
	spin_lock(&f4_fifo_lock);	/* atomic context starts: preempt_count++ */
	mutex_lock(&f4_i2c_mutex);	/* may sleep -> BUG even if uncontended */
	mutex_unlock(&f4_i2c_mutex);
	spin_unlock(&f4_fifo_lock);
	pr_info("returned (the bug did not hang this time)\n");
	return 0;
}

static void __exit f4_sleep_exit(void) { }
module_init(f4_sleep_init);
module_exit(f4_sleep_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("F4: sleeping lock inside spinlock");
```

출력에서 볼 것:

- 디버그 커널은 **두 검사기가 따로** 잡았다. ① `DEBUG_ATOMIC_SLEEP`: `mutex_lock` 첫머리의 `might_sleep()`이 `preempt_count: 1`(spinlock이 올린 값)을 보고 `BUG: sleeping function called from invalid context`를 찍었다. ② lockdep: 쥐고 있는 `f4_fifo_lock`의 wait type `{3:3}`(spin 계열)보다 새로 잡으려는 `f4_i2c_mutex`의 `{4:4}`(LD_WAIT_SLEEP)가 커서 `Invalid wait context`.
- **mutex가 비어 있어서 실제로 잠들지 않았는데도** 잡았다. `might_sleep()`은 "잠들 수도 있는 함수"가 입구에서 외치는 것이라 경합 여부와 상관없다.
- 일반 커널은 조용히 성공했다. 경합이 없으면 mutex fast path가 잠들지 않기 때문이다. 양산에서 경합이 생기는 순간 spinlock(선점 꺼짐)을 쥔 채 `schedule()`로 들어가 `scheduling while atomic` 또는 멈춤이 된다. **새 드라이버는 반드시 디버그 커널로 한 번 돌린다.**

### 5.4 측정 해석 — 왜 이 실험에서 mutex가 spinlock보다 빨랐나

§2의 표에서 mutex(7.8 Mops/s)가 spinlock(1.7)보다 빨랐다. 교과서는 "짧은 구간이면 spinlock이 싸다"고 한다. 둘 다 맞다.

- 교과서의 말은 **경합이 적을 때**다. 경합이 없으면 둘 다 원자 명령 하나지만, mutex는 잠들 가능성 때문에 process context에서만 쓸 수 있고, 경합 시 잠들고 깨는 비용이 크다.
- 이 실험은 **4개 CPU가 쉬지 않고 같은 락을 두드리는 최악의 경합**이다. qspinlock은 공정(FIFO)해서 락이 매번 **다른 CPU로 넘어가고**, 그때마다 락 변수와 `plain`의 캐시 라인이 CPU 사이를 이동한다. mutex는 불공정하다. 방금 푼 CPU가 바로 다시 잡을 수 있고(optimistic spinning·lock stealing), 나머지는 잠들어 경쟁에서 빠진다. 같은 CPU가 연속으로 잡으니 캐시 라인이 이동하지 않는다.
- 이 해석은 §10의 lock_stat 숫자(spinlock은 획득의 79%가 경합, mutex는 slow path까지 간 경합이 거의 없음)와 맞는다. 다만 QEMU TCG는 원자 명령(LL/SC)을 비싸게 흉내 내므로 실제 칩에서는 차이 크기가 다를 수 있다.
- 교훈: **락 하나를 4개 CPU가 두드리는 설계 자체가 문제다.** 정답은 락 종류 바꾸기가 아니라 공유를 없애는 것(per-CPU, §9)이나 읽기 쪽 락을 없애는 것(RCU, §11)이다.

## 6. semaphore — 개수 세는 열쇠 (legacy)

`struct semaphore`는 카운터 + 대기 리스트다. `down()`은 카운터를 줄이고 0이면 잠들고, `up()`은 카운터를 늘리고 대기자를 깨운다. RTOS의 counting semaphore와 같다.

```c
/* 실행하지 않은 코드 조각 — API 모양 */
#include <linux/semaphore.h>
static struct semaphore f4_slots;
sema_init(&f4_slots, 4);			/* DMA 디스크립터 4개 */
if (down_interruptible(&f4_slots))		/* 0이면 획득, -EINTR이면 시그널 */
	return -ERESTARTSYS;
/* ... 디스크립터 하나 사용 ... */
up(&f4_slots);					/* up()은 IRQ 문맥에서도 호출 가능 */
/* down_trylock(): 획득하면 0 반환 — mutex_trylock/spin_trylock(성공 1)과 반대! */
```

새 코드에서 semaphore를 쓸 일은 드물다.

| 하려는 일 | 쓸 것 | semaphore 대신인 이유 |
|---|---|---|
| 상호 배제 (카운트 1) | `mutex` | owner 추적, optimistic spinning, lockdep 검사, 디버그 |
| "일이 끝나면 알려 줘" (IRQ가 process를 깨움) | `completion` (F3) | 의도가 명확, 수명 문제 없음 |
| 이벤트 대기 | `wait_queue` + `wait_event_*` (F3) | 조건식을 직접 표현 |
| 진짜로 N개 자원 세기 | semaphore 또는 atomic + wait_queue | 이 경우만 semaphore가 자연스럽다 |

semaphore는 owner가 없어서 "누가 쥐고 있나"를 디버그 도구가 알려 주지 못한다. 그래서 커널 커뮤니티는 binary semaphore를 mutex로 바꾸는 작업을 오래 해 왔다.

## 7. 읽기는 여럿, 쓰기는 하나 — rwlock과 rw_semaphore

### 7.1 정의

| | `rwlock_t` | `struct rw_semaphore` |
|---|---|---|
| 기다리는 방식 | spin | sleep |
| 읽기 | `read_lock` / `read_unlock` (+ `_bh`, `_irq`, `_irqsave`) | `down_read` / `up_read` |
| 쓰기 | `write_lock` / `write_unlock` | `down_write` / `up_write`, `downgrade_write` |
| 쓰는 곳 | 드물다. 대부분 RCU로 대체됨 | `mm->mmap_lock`(주소 공간), 파일시스템 메타데이터 |

직관은 A8 §5의 pthread rwlock과 같다. 함정도 같다. **읽기 락도 락 변수에 쓴다**(reader 카운트 증가). 그래서 읽기만 하는 CPU 4개도 같은 캐시 라인을 두고 싸운다.

### 7.2 예제 9 — 쓰기 없이 읽기만, 다섯 가지 방법의 비용

무엇을 확인하나: 쓰는 쪽이 전혀 없을 때 각 읽기 방법이 얼마나 비싼가. 구조는 `f4_race`와 같고(CPU마다 kthread, `go` 신호로 동시 출발) 스레드 함수만 다르다. 아래는 다른 부분만 발췌했다.

```c
/* f4_rmostly.c 발췌 — 실행 골격(kthread 4개 생성·bind·go·completion·시간 측정)은 f4_race와 동일 */
static DEFINE_SPINLOCK(f4_sl);
static DEFINE_RWLOCK(f4_rw);
static DECLARE_RWSEM(f4_rwsem);
static DEFINE_SEQLOCK(f4_sq);
static struct { u64 a, b; } f4_cfg = { 1, 2 }, *f4_cfgp = &f4_cfg;

static int f4_rd(void *arg)
{
	u64 s = 0;
	unsigned int seq;
	int i;

	atomic_inc(&ready);
	while (!atomic_read(&go))
		cpu_relax();
	for (i = 0; i < loops; i++) {
		switch (mode) {
		case R_SPIN:   spin_lock(&f4_sl); s += f4_cfg.a; spin_unlock(&f4_sl); break;
		case R_RWLOCK: read_lock(&f4_rw); s += f4_cfg.a; read_unlock(&f4_rw); break;
		case R_RWSEM:  down_read(&f4_rwsem); s += f4_cfg.a; up_read(&f4_rwsem); break;
		case R_SEQ:    do { seq = read_seqbegin(&f4_sq); s += f4_cfg.a; }
			       while (read_seqretry(&f4_sq, seq)); break;
		case R_RCU:    rcu_read_lock(); s += rcu_dereference(f4_cfgp)->a;
			       rcu_read_unlock(); break;
		}
	}
	if (atomic_dec_and_test(&running))
		complete(&f4_done);
	return s == 0;		/* use s so the loop is not optimized away */
}
```

출력에서 볼 것:

- **rwlock·rw_semaphore는 읽기 전용인데도 spinlock보다 별로 낫지 않다.** 네 CPU가 모두 같은 reader 카운트 변수를 원자적으로 증감하니 그 캐시 라인이 계속 CPU 사이를 오간다. "읽기가 많으니 rwlock"은 직관과 달리 대개 이득이 없다. 구간이 길 때(읽는 동안 오래 머무를 때)만 의미가 있다.
- seqlock reader는 시퀀스 번호를 **읽기만** 하고(`read_seqbegin` → 읽기 → `read_seqretry`), RCU reader는 공유 변수에 아무것도 쓰지 않는다. 그래서 CPU가 늘어도 서로 방해하지 않는다.
- 여기서는 seqlock이 RCU보다 빨랐다. 이 커널은 `PREEMPT_RCU`라서 `rcu_read_lock()`이 현재 태스크의 `rcu_read_lock_nesting` 카운터를 올리고 내리고, unlock 때 "특별 처리 필요?" 검사를 한다(태스크 로컬이라 CPU 간 경합은 없다). 비선점 커널(`PREEMPT_NONE`)에서는 `rcu_read_lock()`이 사실상 아무 명령도 아니다. 둘의 차이보다 "락 계열과 100배 차이"가 핵심이다.

### 7.3 함정

- `read_lock` 안에서 `write_lock`으로 올리면(upgrade) 자기 자신을 기다리는 deadlock이다. rw_semaphore에도 upgrade는 없다(반대 방향 `downgrade_write`만 있다).
- 쓰기가 드물게라도 길면, rw_semaphore는 쓰는 쪽이 기다리는 동안 새 reader를 막는다(writer starvation 방지). 그래서 "읽기는 절대 안 막힌다"고 가정하면 안 된다.

## 8. atomic_t · refcount_t · atomic bitops — 변수 하나면 락이 필요 없다

### 8.1 정의

| 타입·API | 하는 일 | 순서 보장(F5) |
|---|---|---|
| `atomic_t`(int), `atomic64_t`, `atomic_long_t` | `atomic_read/set`, `atomic_inc/dec/add/sub` | 값을 반환하지 않는 연산은 **순서 보장 없음**(relaxed) |
| `atomic_inc_return`, `atomic_dec_and_test`, `atomic_cmpxchg`, `atomic_try_cmpxchg` | 결과를 돌려주는 RMW | **fully ordered** (`_relaxed`·`_acquire`·`_release` 변형 있음) |
| `refcount_t` | `refcount_set/inc/dec_and_test` | 객체 수명 관리 전용. overflow·underflow·0에서 증가를 **잡아서 경고** |
| `set_bit`, `clear_bit`, `test_and_set_bit`, `test_and_clear_bit` | `unsigned long` 비트맵의 한 비트를 원자적으로 | `test_and_*`는 fully ordered |
| `__set_bit`, `__clear_bit` | 같은 일, **비원자** | 이미 락을 쥐었을 때만 |

arm64에서 atomic은 두 방식 중 하나로 실행된다. ARMv8.0의 LL/SC(`ldxr`/`stxr` 루프, 실패하면 다시)와 ARMv8.1 LSE(`ldadd`, `stadd`, `cas` 같은 한 방 명령)다. 커널은 `CONFIG_ARM64_LSE_ATOMICS=y`로 둘 다 넣어 두고 부팅 때 CPU 기능을 보고 패치한다(alternatives). 이 랩의 `-cpu cortex-a57`은 ARMv8.0이라 LL/SC로 돈다. Don이 SSD 펌웨어에서 Cortex-R의 `LDREX`/`STREX`로 짜던 그 루프다.

### 8.2 예제 10 — `atomic_t`는 조용히 넘치고, `refcount_t`는 거부한다

무엇을 확인하나: 참조 카운트를 `atomic_t`로 짜면 생기는 문제와, `refcount_t`가 그것을 어떻게 잡는지. 덤으로 `test_and_set_bit`을 "바쁨" 플래그로 쓰는 관용구.

```c
// SPDX-License-Identifier: GPL-2.0
/* f4_atom: atomic_t wraps silently, refcount_t refuses; atomic bitops as a busy flag */
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/atomic.h>
#include <linux/refcount.h>
#include <linux/bitops.h>

#define F4_BUSY 0			/* bit number in f4_flags */
static unsigned long f4_flags;

static int __init f4_atom_init(void)
{
	atomic_t a = ATOMIC_INIT(INT_MAX);
	refcount_t r = REFCOUNT_INIT(1);
	int old;

	atomic_inc(&a);				/* no check: wraps */
	pr_info("atomic_t   INT_MAX + 1 = %d\n", atomic_read(&a));

	old = atomic_cmpxchg(&a, INT_MIN, 7);	/* if (a == INT_MIN) a = 7 */
	pr_info("cmpxchg    old=%d new=%d\n", old, atomic_read(&a));

	pr_info("refcount   dec_and_test -> %d (last put: free the object)\n",
		refcount_dec_and_test(&r));
	refcount_inc(&r);			/* get() on a freed object: bug */
	pr_info("refcount   after inc on 0 = 0x%x (saturated)\n", refcount_read(&r));

	pr_info("bitops     1st test_and_set_bit -> %d\n", test_and_set_bit(F4_BUSY, &f4_flags));
	pr_info("bitops     2nd test_and_set_bit -> %d (already busy)\n",
		test_and_set_bit(F4_BUSY, &f4_flags));
	clear_bit(F4_BUSY, &f4_flags);
	return 0;
}

static void __exit f4_atom_exit(void) { }
module_init(f4_atom_init);
module_exit(f4_atom_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("F4: atomic_t vs refcount_t, atomic bitops");
```

출력에서 볼 것:

- `atomic_t`는 `INT_MAX + 1`에서 **경고 없이** 음수로 넘어갔다. 참조 카운트를 `atomic_t`로 쓰면, 버그로 get이 넘치거나 put이 한 번 더 불릴 때 카운트가 0을 지나 객체가 해제되고 다른 사용자는 해제된 메모리를 쓴다(use-after-free, 보안 취약점의 단골).
- `refcount_t`는 0에서 증가하려 하자 **일반 커널에서도** `refcount_t: addition on 0; use-after-free.` 경고를 내고, 값을 `0xc0000000`(`REFCOUNT_SATURATED`)에 고정했다. 이후로는 증가도 감소도 안 되므로 객체가 해제되지 않는다(메모리를 새게 두는 쪽이 해제된 메모리를 쓰는 쪽보다 안전하다는 설계).
- `test_and_set_bit`은 이전 비트 값을 돌려준다. 0이면 "내가 처음 세웠다 → 일을 시작", 1이면 "누가 이미 하는 중"이다. 락 없이 "한 번만 실행" 보장을 만드는 관용구다.
- 객체 수명은 `refcount_t`, 그 위의 표준 래퍼는 `struct kref`(`kref_get`/`kref_put(ref, release_fn)`)다. 드라이버 모델(`struct device`)이 전부 이걸로 수명을 센다(G 모듈).

### 8.3 함정

- **atomic 변수 두 개는 원자적이지 않다.** `atomic_inc(&head); atomic_dec(&free);` 사이에 다른 CPU가 끼어들 수 있다. 여러 변수의 일관성이 필요하면 락이다.
- `atomic_read`/`atomic_set`은 그냥 `READ_ONCE`/`WRITE_ONCE`다. 원자적 RMW가 아니다.
- 반환값 없는 `atomic_inc`는 순서를 보장하지 않는다. "데이터를 쓰고 플래그를 올린다"류 publish에는 `smp_store_release`나 `atomic_set_release` 같은 순서 있는 API를 쓴다(F5).

## 9. per-CPU 변수 — 공유를 없애면 락도 필요 없다

### 9.1 직관과 정의

통계 카운터를 CPU마다 따로 두고, 읽을 때만 합친다. 펌웨어에서 코어별 로그 버퍼를 따로 두고 호스트가 읽을 때 합치던 것과 같다. 쓰는 쪽은 자기 CPU 사본만 만지므로 다른 CPU와 경쟁이 없다. 남은 위험은 **같은 CPU의 선점과 IRQ**뿐이다.

```c
/* 실행하지 않은 코드 조각 — per-CPU API 모양 (§2의 f4_race가 this_cpu_inc를 실제로 썼다) */
static DEFINE_PER_CPU(u64, f4_rx_pkts);

this_cpu_inc(f4_rx_pkts);		/* 한 번의 연산: 선점·IRQ에 안전 */

int cpu = get_cpu();			/* preempt_disable() + 현재 CPU 번호 */
struct f4_stats *s = per_cpu_ptr(&f4_stats, cpu);
s->bytes += len; s->pkts++;		/* 여러 필드: 이 사이 다른 CPU로 옮겨 가면 안 됨 */
put_cpu();				/* preempt_enable() */

u64 sum = 0;
for_each_possible_cpu(cpu)		/* 읽는 쪽: 모든 사본을 합친다 (근사값이어도 되는 통계) */
	sum += per_cpu(f4_rx_pkts, cpu);
```

| API | 의미 |
|---|---|
| `DEFINE_PER_CPU(type, name)` / `alloc_percpu(type)` | 정적 / 동적 per-CPU 변수 |
| `this_cpu_inc/add/read/write(var)` | 현재 CPU 사본에 **한 번의** 연산. 선점·IRQ에 안전 |
| `__this_cpu_*` | 같은 일, 보호 없음. 이미 선점·IRQ가 꺼진 곳에서만 |
| `get_cpu()` / `put_cpu()` | 선점 끄고 CPU 번호 / 선점 켬. 여러 단계 갱신용 |
| `per_cpu(var, cpu)`, `per_cpu_ptr(p, cpu)` | 특정 CPU의 사본 (보통 합산할 때) |

### 9.2 함정

- `get_cpu()`와 `put_cpu()` 사이에서 잠들면 안 된다(선점이 꺼져 있다). 즉 이 구간도 atomic context다.
- 같은 per-CPU 변수를 IRQ 핸들러도 여러 단계로 갱신하면 `get_cpu()`만으로는 부족하다. `local_irq_save()`가 필요하다.
- 합산은 순간 스냅샷이 아니다. 다른 CPU가 더하는 중에 읽으므로 "대략"이다. 정확한 값이 매번 필요하면 per-CPU가 맞는 도구가 아니다. 커널은 이 절충을 `percpu_counter`(로컬에 모아 두다가 임계값을 넘으면 전역에 반영)로 포장해 둔다.

## 11. RCU — 읽는 쪽은 아무것도 하지 않는다

### 11.1 직관 — 게시판 비유

회사 게시판의 공지를 바꾼다고 하자. 지우고 다시 쓰는 동안 읽던 사람이 반쯤 지워진 글을 보면 안 된다. RCU(Read-Copy-Update)의 방법은 이렇다.

1. **Copy**: 새 공지를 따로 써서 완성한다.
2. **Update(publish)**: 게시판의 핀 하나를 새 종이로 옮겨 꽂는다. 포인터 하나 바꾸기라 원자적이다. 이제부터 오는 사람은 새 공지를 본다.
3. **기다리기(grace period)**: 핀을 옮기기 **전부터** 옛 공지를 읽고 있던 사람이 모두 자리를 뜰 때까지 기다린다.
4. **해제**: 그다음 옛 종이를 버린다.

읽는 사람은 아무것도 하지 않는다. 락도 원자 명령도, 기다림도 없다. 대가는 쓰는 쪽이 치른다(복사 + 기다림). 그래서 **읽기가 압도적으로 많고, 잠깐 옛 값을 봐도 괜찮은 데이터**(라우팅 테이블, 설정, 장치 목록, 파일 시스템 dentry 캐시)에 쓴다.

### 11.2 API — 다섯 개면 된다

| 쪽 | API | 하는 일 |
|---|---|---|
| reader | `rcu_read_lock()` / `rcu_read_unlock()` | 읽기 구간 표시. 이 안에서 잠들면 안 된다(일반 RCU) |
| reader | `rcu_dereference(p)` | 공유 포인터 읽기. 컴파일러·CPU가 순서를 바꾸지 않게 하고, lockdep(`PROVE_RCU`)이 "RCU 구간 안인가"를 검사 |
| updater | `rcu_assign_pointer(p, v)` | 새 객체 공개. release 순서(객체 초기화가 포인터 공개보다 먼저 보이게) |
| updater | `synchronize_rcu()` | grace period가 끝날 때까지 **잠들어** 기다림 (process context만) |
| updater | `call_rcu(&obj->rcu, fn)` / `kfree_rcu(obj, rcu)` | 기다리지 않고 "grace period 뒤에 fn 실행 / kfree" 예약 (atomic context에서도 가능) |

리스트용 래퍼: `list_add_rcu`, `list_del_rcu`, `list_replace_rcu`, `list_for_each_entry_rcu`. **updater끼리는 여전히 서로 배제해야 한다**(보통 spinlock이나 mutex). RCU는 reader와 updater 사이만 풀어 준다.

grace period를 커널은 어떻게 아나? 간단히 말하면, 모든 CPU가 한 번씩 **quiescent state**(RCU reader 구간 밖에 있음이 확실한 지점: context switch, idle, 유저 모드 실행)를 지나가면 그 이전에 시작한 reader는 모두 끝났다. 커널은 CPU마다 이 통과를 기록하고, RCU grace-period kthread가 모두 통과했는지 확인한다. reader 쪽 코드에는 아무 표시도 필요 없다 — 그래서 reader가 공짜다. (§4.3의 RCU stall 경고는 이 통과를 21초 동안 못 한 CPU를 보고한 것이다.)

### 11.3 예제 12 — reader 3개는 락 없이, writer는 항목을 계속 교체

무엇을 확인하나: 센서 보정값 8개가 든 리스트를 reader kthread 3개가 쉬지 않고 훑는다. 각 항목에는 검증 필드(`check == gain ^ 0xA5A5A5A5`)가 있어서, 해제된 항목을 보면 `bad`가 오른다. writer는 2000번 항목을 새것으로 교체한다. `mode=0`은 `kfree_rcu`, `mode=1`은 일부러 버그(교체 직후 바로 `kfree`, 그 전에 재사용을 흉내 내 검증 필드를 망가뜨림).

```c
// SPDX-License-Identifier: GPL-2.0
/* f4_rcu: lock-free readers vs a writer that replaces list entries */
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/kthread.h>
#include <linux/rculist.h>
#include <linux/slab.h>
#include <linux/delay.h>

static int mode;	/* 0 = kfree_rcu   1 = BUG: kfree right away */
module_param(mode, int, 0444);
struct f4_cfg { struct list_head node; u32 gain, check; struct rcu_head rcu; };
static LIST_HEAD(f4_list);
static DEFINE_SPINLOCK(f4_wlock);		/* writers only */
static atomic_long_t reads, bad;
static struct task_struct *rd[3];
static struct f4_cfg *slot[8];		/* writer-side index of entries */

static int f4_reader(void *arg)
{
	struct f4_cfg *c;

	while (!kthread_should_stop()) {
		rcu_read_lock();			/* no lock, no atomic, no wait */
		list_for_each_entry_rcu(c, &f4_list, node)
			if (READ_ONCE(c->check) != (READ_ONCE(c->gain) ^ 0xA5A5A5A5))
				atomic_long_inc(&bad);	/* saw a freed/poisoned entry */
		rcu_read_unlock();
		atomic_long_inc(&reads);
		cond_resched();
	}
	return 0;
}

static void __exit f4_rcu_exit(void)
{
	int i;

	for (i = 0; i < 8; i++) {
		list_del_rcu(&slot[i]->node);
		kfree_rcu(slot[i], rcu);
	}
}
module_exit(f4_rcu_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("F4: RCU-protected list");
```

```c
/* f4_rcu.c (계속) — 초기 리스트, reader 시작, writer 루프 */
static int __init f4_rcu_init(void)
{
	struct f4_cfg *c, *old;
	ktime_t t0;
	int i;

	for (i = 0; i < 8; i++) {
		c = kmalloc(sizeof(*c), GFP_KERNEL);
		if (!c)
			return -ENOMEM;
		c->gain = i; c->check = i ^ 0xA5A5A5A5;
		list_add_tail(&c->node, &f4_list);
		slot[i] = c;
	}
	for (i = 0; i < 3; i++)
		rd[i] = kthread_run(f4_reader, NULL, "f4_rcu_rd/%d", i);
	for (i = 0; i < 2000; i++) {		/* writer: replace entries in turn */
		c = kmalloc(sizeof(*c), GFP_KERNEL);
		if (!c)
			break;
		c->gain = 100 + i; c->check = c->gain ^ 0xA5A5A5A5;
		spin_lock(&f4_wlock);
		old = slot[i % 8];
		list_replace_rcu(&old->node, &c->node);	/* publish (release) */
		slot[i % 8] = c;
		spin_unlock(&f4_wlock);
		if (mode == 0) {
			kfree_rcu(old, rcu);		/* free after a grace period */
		} else {
			WRITE_ONCE(old->check, 0xdead);	/* what reuse would look like */
			kfree(old);			/* readers may still hold it! */
		}
		usleep_range(50, 100);
	}
	for (i = 0; i < 3; i++)
		kthread_stop(rd[i]);
	t0 = ktime_get();
	synchronize_rcu();
	pr_info("mode=%d reads=%ld bad=%ld synchronize_rcu=%lldus\n", mode,
		atomic_long_read(&reads), atomic_long_read(&bad),
		ktime_us_delta(ktime_get(), t0));
	return 0;
}
module_init(f4_rcu_init);
```

(노트에서는 읽기 좋게 `module_init` 위치만 옮겼다. 실제 파일은 init 뒤에 exit가 온다. 데모라서 `kthread_run`의 `IS_ERR` 검사는 생략했다 — 실제 드라이버에서는 반드시 검사한다.)

일반 커널, `mode=0` 두 번 + 같은 부팅에서 다음 절의 `f4_seq`도 함께, 그리고 `mode=1` 두 번:

출력에서 볼 것:

- `mode=0`: reader 3개가 약 600만 번 리스트를 훑는 동안 writer가 2000번 교체했는데 **`bad=0`**. reader 코드에는 락이 하나도 없다. 교체 중인 항목을 읽던 reader는 옛 항목을 끝까지 안전하게 읽었다.
- `mode=1`: 같은 실험에서 600만 번 중 **2~3번** 해제된 항목을 읽었다. 확률이 100만분의 1 수준이라 테스트에서는 거의 안 보이고 양산에서 가끔 터진다. 더 나쁜 경우 해제된 메모리를 slab이 재사용해 `node.next`가 쓰레기가 되면 reader가 Oops를 낸다. 이 버그는 디버그 커널에서 KASAN(`use-after-free`)으로 잡는다(M7).
- `synchronize_rcu()` 한 번에 5~18 ms가 걸렸다. **grace period는 비싸다.** 그래서 writer가 매번 기다리지 않도록 `kfree_rcu`/`call_rcu`로 해제를 예약하고 바로 다음 일을 한다. 커널은 예약된 콜백을 모아서 한 grace period에 한꺼번에 처리한다.
- 디버그 커널에서 reads가 10분의 1로 줄었다. `PROVE_RCU`가 `rcu_read_lock()`도 lockdep에 기록하기 때문이다.

### 11.4 RCU 함정

- **reader 구간 안에서 잠들기 금지**(일반 RCU). 잠들어야 하면 SRCU(`srcu_read_lock`)를 쓴다.
- **reader 구간 밖으로 포인터를 들고 나가지 않는다.** `rcu_read_unlock()` 뒤에는 그 객체가 언제든 해제될 수 있다. 오래 쓸 거면 구간 안에서 `refcount_inc_not_zero()`로 참조를 잡고 나온다.
- RCU는 "옛 값을 잠깐 봐도 되는" 데이터에만 맞다. 읽은 값으로 다시 쓰기를 결정하는 read-modify-write에는 맞지 않는다.
- 모듈을 내릴 때 `call_rcu` 콜백이 남아 있으면 모듈 코드가 사라진 뒤 콜백이 불린다. exit에서 `rcu_barrier()`로 대기한다(`kfree_rcu`는 모듈 코드를 부르지 않아 이 문제가 없다).

## 12. seqlock — 쓰는 쪽은 절대 기다리지 않는다

### 12.1 직관과 정의

seqlock은 **시퀀스 번호 + writer용 spinlock**이다. writer는 시작할 때 번호를 홀수로, 끝날 때 짝수로 올린다. reader는 락을 잡지 않고 ① 번호를 읽고(홀수면 기다림) ② 데이터를 복사하고 ③ 번호가 그대로인지 확인해서, 바뀌었으면 처음부터 다시 읽는다.

- **writer 우선**: reader가 몇 명이든 writer는 기다리지 않는다. 대신 reader가 retry한다.
- 데이터가 작고(복사가 싸고), 쓰기가 잦지 않고, **포인터가 아닌 값**일 때 맞는다. (reader가 읽는 도중 writer가 객체를 해제하면 retry 전에 이미 잘못된 메모리를 읽는다 — 포인터면 RCU를 쓴다.)
- 대표 사용처: 시간. `jiffies_64`(`kernel/time/jiffies.c`의 `jiffies_seq`, 32비트 CPU에서 64비트 값을 찢어지지 않게 읽기)와 timekeeping(`kernel/time/timekeeping.c`의 `struct tk_data` 안 `seq`, `ktime_get()`이 매번 이 retry 루프를 돈다). 타이머 IRQ가 시간을 갱신하고, 수많은 reader가 읽기만 한다.

### 12.2 예제 13 — 두 단어짜리 타임스탬프, seqlock 있이·없이

무엇을 확인하나: writer가 `(sec, ~sec)` 쌍을 2만 번 갱신하는 동안 reader 3개가 같은 쌍을 보호 없이 한 번, seqlock으로 한 번 읽어 **찢어진 읽기**(sec와 ~sec가 짝이 안 맞음)를 센다.

```c
// SPDX-License-Identifier: GPL-2.0
/* f4_seq: a 2-word timestamp pair read with and without a seqlock */
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/kthread.h>
#include <linux/seqlock.h>
#include <linux/delay.h>

static DEFINE_SEQLOCK(f4_ts_lock);
static u64 f4_sec, f4_nsec_x;		/* invariant: f4_nsec_x == ~f4_sec */
static atomic_long_t torn_raw, torn_seq, retries, reads;

static int f4_reader(void *arg)
{
	unsigned int seq;
	u64 a, b;

	while (!kthread_should_stop()) {
		a = READ_ONCE(f4_sec); b = READ_ONCE(f4_nsec_x);	/* no protection */
		if (b != ~a)
			atomic_long_inc(&torn_raw);
		do {						/* seqlock reader */
			seq = read_seqbegin(&f4_ts_lock);
			a = READ_ONCE(f4_sec); b = READ_ONCE(f4_nsec_x);
		} while (read_seqretry(&f4_ts_lock, seq) && atomic_long_inc_return(&retries));
		if (b != ~a)
			atomic_long_inc(&torn_seq);
		atomic_long_inc(&reads);
		cond_resched();
	}
	return 0;
}

static int __init f4_seq_init(void)
{
	struct task_struct *rd[3];
	int i, j;

	f4_nsec_x = ~0ULL;
	for (i = 0; i < 3; i++)
		rd[i] = kthread_run(f4_reader, NULL, "f4_seq_rd/%d", i);
	for (i = 0; i < 20000; i++) {		/* writer never waits for readers */
		write_seqlock(&f4_ts_lock);
		WRITE_ONCE(f4_sec, i);
		for (j = 0; j < 50; j++)	/* widen the update window */
			cpu_relax();
		WRITE_ONCE(f4_nsec_x, ~(u64)i);
		write_sequnlock(&f4_ts_lock);
		if (!(i % 64))
			cond_resched();
	}
	for (i = 0; i < 3; i++)
		kthread_stop(rd[i]);
	pr_info("reads=%ld torn_without_seqlock=%ld torn_with_seqlock=%ld retries=%ld\n",
		atomic_long_read(&reads), atomic_long_read(&torn_raw),
		atomic_long_read(&torn_seq), atomic_long_read(&retries));
	return 0;
}

static void __exit f4_seq_exit(void) { }
module_init(f4_seq_init);
module_exit(f4_seq_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("F4: seqlock reader retry");
```

```text
lab initramfs: 6.18.55 up 0.89s
[    1.763510] f4_seq: reads=110729 torn_without_seqlock=26011 torn_with_seqlock=0 retries=601
lab initramfs: 6.18.55-dbg up 5.93s
```

출력에서 볼 것:

- 보호 없는 읽기는 **약 24%가 찢어졌다**(sec는 새 값, ~sec는 옛 값). 64비트 변수 두 개, 또는 32비트 CPU의 64비트 변수 하나가 정확히 이 모양이다.
- seqlock 읽기는 **0번** 찢어졌고, 그 대가로 0.5% 정도 다시 읽었다(`retries`). writer는 한 번도 reader를 기다리지 않았다.
- 같은 retry 루프가 `ktime_get()` 안에 있다. 드라이버에서 타임스탬프를 찍을 때마다 이 패턴을 공짜로 쓰고 있는 것이다(F8).

## 13. lock ordering과 lockdep — 일어나지 않은 deadlock 잡기

### 13.1 ABBA deadlock

락이 두 개 이상이면 **잡는 순서**가 문제다. 경로 1은 A → B, 경로 2는 B → A로 잡으면, 두 CPU가 동시에 각자 첫 락을 잡은 순간 서로의 두 번째 락을 영원히 기다린다(A8 §10에서 유저 공간판을 봤다). 처방은 단순하다. **모든 경로가 같은 순서로 잡는다**, 그리고 그 순서를 주석·문서로 남긴다(예: `mm/rmap.c` 첫머리의 락 순서 주석).

lockdep은 개별 락이 아니라 **락 클래스**(같은 곳에서 초기화된 락들의 묶음, 보통 변수 이름)를 노드로 하는 그래프를 런타임에 그린다. "B를 쥔 채로 A를 잡았다"를 볼 때마다 B → A 간선을 추가하고, 새 간선이 **사이클**을 만들면 경고한다. 실제 deadlock이 일어날 필요가 없다. 두 경로가 **각각 한 번씩, 다른 시간에** 실행되기만 하면 된다.

### 13.2 예제 14 — `f4_abba`: 겹치지 않아도 잡힌다

무엇을 확인하나: 같은 태스크가 두 경로를 **순서대로** 한 번씩 실행한다. 동시 실행이 아니므로 실제 deadlock은 절대 일어나지 않는다.

```c
// SPDX-License-Identifier: GPL-2.0
/* f4_abba: two code paths take the same two mutexes in opposite order */
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/mutex.h>

static DEFINE_MUTEX(f4_cfg_mutex);	/* protects sensor config  */
static DEFINE_MUTEX(f4_buf_mutex);	/* protects sample buffer  */

static void f4_ioctl_path(void)		/* ioctl(SET_RATE): cfg -> buf */
{
	mutex_lock(&f4_cfg_mutex);
	mutex_lock(&f4_buf_mutex);
	pr_info("ioctl path: cfg -> buf ok\n");
	mutex_unlock(&f4_buf_mutex);
	mutex_unlock(&f4_cfg_mutex);
}

static void f4_read_path(void)		/* read(): buf -> cfg  (BUG) */
{
	mutex_lock(&f4_buf_mutex);
	mutex_lock(&f4_cfg_mutex);
	pr_info("read path : buf -> cfg ok\n");
	mutex_unlock(&f4_cfg_mutex);
	mutex_unlock(&f4_buf_mutex);
}

static int __init f4_abba_init(void)
{
	f4_ioctl_path();	/* lockdep records cfg -> buf      */
	f4_read_path();		/* buf -> cfg closes a cycle       */
	return 0;
}

static void __exit f4_abba_exit(void) { }
module_init(f4_abba_init);
module_exit(f4_abba_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("F4: ABBA lock order, caught by lockdep");
```

- `{+.+.}-{4:4}`: 앞은 IRQ 사용 상태(이 mutex는 IRQ 켜진 process context에서만 쓰였다), 뒤는 wait type(4 = sleeping lock).



출력에서 볼 것:

- `f4_cfg_mutex -> f4_buf_mutex` 간선 하나만 있다. 사이클을 만드는 buf → cfg 간선은 경고와 함께 **추가가 거부됐다.** `FD`(forward dependencies)·`BD`(backward)는 그 클래스에서 앞뒤로 닿는 클래스 수다.
- 부팅만 했는데 커널 전체에 락 클래스 715개, 직접 의존 3330개가 이미 기록돼 있다. lockdep은 내 모듈만이 아니라 **커널 전체의 락 순서**를 검사한다. 내 드라이버의 락이 I2C 코어나 네트워크 스택의 락과 엮인 사이클도 잡힌다.
- **`debug_locks: 0`** — 첫 경고를 낸 순간 lockdep은 스스로 꺼진다. 망가진 상태에서 계속 검사하면 거짓 경고가 쏟아지기 때문이다. 그래서 **첫 lockdep 경고가 가장 중요하고**, 하나를 고친 뒤 다시 부팅해야 다음 문제가 보인다. CI에서 부팅 로그에 lockdep 경고가 하나라도 있으면 실패로 처리하는 이유다.

### 13.4 lockdep이 잡는 것 정리

| 경고 제목 | 뜻 | 이 노트 예제 |
|---|---|---|
| `possible circular locking dependency detected` | 락 순서 사이클 (ABBA) | 예제 14 |
| `inconsistent {IN-HARDIRQ-W} -> {HARDIRQ-ON-W} usage` | IRQ 안에서 쓰는 락을 IRQ 켠 채 잡음 | 예제 5 |
| `inconsistent {IN-SOFTIRQ-W} -> {SOFTIRQ-ON-W} usage` | softirq 안에서 쓰는 락을 BH 켠 채 잡음 → `_bh` 필요 | (같은 원리) |
| `Invalid wait context` | 문맥이 허용하는 것보다 "더 잠드는" 락을 잡음 | 예제 7, 8 |
| `possible recursive locking detected` | 같은 클래스 락을 또 잡음 (중첩이 정당하면 `mutex_lock_nested`·`spin_lock_nested`로 subclass 지정) | — |
| `suspicious RCU usage` (`PROVE_RCU`) | RCU 구간 밖에서 `rcu_dereference` 등 | — |
| `BUG: sleeping function called from invalid context` (`DEBUG_ATOMIC_SLEEP`, lockdep과 별개) | atomic context에서 잠들 수 있는 함수 호출 | 예제 8 |

코드에서 lockdep에게 가정을 알려 주는 방법도 있다. `lockdep_assert_held(&d->lock)`를 "이 함수는 락을 쥔 채 불려야 한다"는 헬퍼 맨 앞에 두면, 락 없이 부른 호출자를 디버그 커널이 잡는다. 일반 커널에서는 코드가 사라진다.

모듈 연결:

- **F2(실행 컨텍스트)**: "잠들어도 되나"의 근거인 `preempt_count`. spinlock이 이것을 올리고, `might_sleep()`이 이것을 읽는다.
- **F3(잠자기와 깨우기)**: mutex의 slow path가 쓰는 `schedule()`, 그리고 wait queue·completion.
- **F5(메모리 배리어)**: `rcu_assign_pointer`(release), `rcu_dereference`(dependency ordering), seqlock의 `smp_rmb`, atomic의 relaxed/ordered 구분.
- **F6·F7(인터럽트·지연 작업)**: `_irqsave`와 `_bh`를 고르는 근거가 되는 hardirq·softirq·threaded IRQ.
- **H 모듈(char 드라이버)·I 모듈(I2C·SPI)**: 실제 드라이버에서 이 노트의 결정 표를 적용하는 곳.
- **M7(커널 디버그 도구)**: lockdep·KCSAN·KASAN을 켠 커널 빌드와 CI.

## 16. Embedded 실무에서 다시 보기

### 16.1 장면 1 — IMU FIFO: IRQ 핸들러와 `read()`가 같은 링버퍼를 쓴다

1 kHz IMU의 data-ready IRQ가 샘플을 링버퍼에 넣고, 유저 프로세스의 `read()`가 꺼낸다. 핸들러 쪽은 `spin_lock`, `read()` 쪽은 `spin_lock_irqsave`. 그리고 **`copy_to_user`는 락 밖에서** 한다(page fault로 잠들 수 있다).

```c
/* 실행하지 않은 코드 조각 — 구조만 */
static irqreturn_t imu_isr(int irq, void *p)		/* hardirq */
{
	struct imu *d = p;

	spin_lock(&d->lock);				/* 이 CPU의 IRQ는 이미 꺼짐 */
	ring_push(&d->ring, imu_read_fifo_mmio(d));	/* MMIO만, I2C 금지 */
	spin_unlock(&d->lock);
	wake_up_interruptible(&d->wq);			/* F3 */
	return IRQ_HANDLED;
}

static ssize_t imu_read(struct file *f, char __user *ubuf, size_t n, loff_t *pos)
{
	struct imu *d = f->private_data;
	struct imu_sample tmp[16];
	unsigned long flags;
	size_t cnt;

	spin_lock_irqsave(&d->lock, flags);		/* IRQ가 경쟁자 */
	cnt = ring_pop_many(&d->ring, tmp, min(n / sizeof(tmp[0]), ARRAY_SIZE(tmp)));
	spin_unlock_irqrestore(&d->lock, flags);
	if (copy_to_user(ubuf, tmp, cnt * sizeof(tmp[0])))	/* 락 밖에서 */
		return -EFAULT;
	return cnt * sizeof(tmp[0]);
}
```

IMU가 I2C 장치라서 IRQ에서 바로 읽을 수 없다면? 핸들러에서 읽지 말고 threaded IRQ(`request_threaded_irq`)의 스레드 함수에서 I2C로 읽는다. 그 스레드는 process context라 mutex를 쓸 수 있다(F6, F7).

### 16.2 장면 2 — 카메라 드라이버의 "가끔 멈춤"

V4L2 카메라 드라이버의 `stop_streaming`(process context)이 `buf_lock`을 `spin_lock`으로 잡는데, 프레임 완료 IRQ도 같은 락을 잡는다. 테스트에서는 멀쩡하고, 현장에서 며칠에 한 번 멈춘다(예제 4의 RCU stall 메시지가 로그에 남아 있다면 행운이다). 디버그 커널로 한 번만 돌렸으면 예제 5의 `inconsistent {IN-HARDIRQ-W} -> {HARDIRQ-ON-W}`로 첫날 잡혔다. **팀 CI에 `PROVE_LOCKING` 커널 부팅 + 기능 테스트를 넣는 것**이 가장 싼 보험이다.

### 16.3 장면 3 — CAN 모터 컨트롤러 설정 테이블

모터 8개의 보정 파라미터 테이블을 제어 루프(1 kHz, RT 스레드)가 매 주기 읽고, 가끔(분 단위) 유저 공간 튜닝 도구가 `ioctl`로 바꾼다. 제어 루프가 mutex를 기다리면 지터가 생긴다. 예제 12처럼 **새 테이블을 할당해 채우고 `rcu_assign_pointer`로 교체, 옛 것은 `kfree_rcu`**. 제어 루프는 `rcu_read_lock` + `rcu_dereference`로 읽어서 절대 기다리지 않는다.

### 16.4 장면 4 — PREEMPT_RT 커널로 가는 드론

지연 요구 때문에 PREEMPT_RT 커널로 바꿨더니 `BUG: sleeping function called from invalid context`가 쏟아진다. 원인은 대개 ① `local_irq_disable()`이나 `preempt_disable()` 뒤에 `spinlock_t`를 잡는 코드(RT에서는 그 락이 잠드는 락), ② HARD 모드 hrtimer나 `IRQF_NO_THREAD` 핸들러 안의 `spinlock_t`(예제 7). 일반 커널에서 `PROVE_RAW_LOCK_NESTING`을 켜 두면 RT로 옮기기 전에 같은 문제를 미리 본다.

## 18. 면접에서 이렇게 말한다

**Q.** What's the difference between a spinlock and a mutex? When do you use each?

**A.** spinlock은 못 잡으면 그 자리에서 돌며 기다리고, 쥔 동안 선점이 꺼져서 잠들 수 없다. 그래서 IRQ 핸들러를 포함한 어떤 문맥에서도 쓸 수 있지만 구간이 아주 짧아야 한다. mutex는 못 잡으면 잠든다. owner가 있고, 잡은 태스크만 풀 수 있고, process context에서만 쓴다. 쥔 채로 I2C 전송·메모리 할당·`copy_to_user` 같은 잠드는 일을 해야 하면 mutex다. 요즘 mutex는 owner가 다른 CPU에서 실행 중이면 잠깐 돌다가(optimistic spinning) 잠드니 짧은 구간에서도 생각보다 싸다.

> A spinlock busy-waits and disables preemption while held, so the holder must never sleep — but it can be used from any context, including hard IRQ handlers, as long as the critical section is very short. A mutex puts the waiter to sleep, has an owner, can only be released by that owner, and is only usable in process context. If I need to sleep while holding the lock — an I2C transfer, a GFP_KERNEL allocation, copy_to_user — I must use a mutex. Modern mutexes also spin optimistically while the owner is running on another CPU, so they're cheaper than people expect. In my measurements on a 4-CPU QEMU guest, a heavily contended mutex even beat the spinlock because the mutex let the same CPU re-acquire it, while the fair qspinlock bounced the cache line every time — but the real fix there was per-CPU counters, which were about 60x faster than either.

**꼬리 질문**: "Can you take a mutex in an interrupt handler?" → 안 된다. 잠들 수 있기 때문이다. threaded IRQ의 스레드 함수에서는 된다.

**Q.** When do you need spin_lock_irqsave instead of spin_lock?

**A.** 같은 데이터를 hardirq 핸들러도 만질 때, process 쪽에서 `_irqsave`를 쓴다. 안 그러면 락을 쥔 CPU에 그 IRQ가 들어와 핸들러가 같은 락을 기다리며 영원히 돈다. 락을 풀 코드가 핸들러 밑에 깔려 있기 때문이다. 핸들러 쪽은 이미 IRQ가 꺼져 있으니 그냥 `spin_lock`이다. softirq·tasklet·타이머와 공유하면 `_bh`. `_irq`는 호출자가 IRQ 켠 상태임을 확신할 때만, 모르면 `_irqsave`.

> Use the irqsave variant on the process-context side whenever the same lock is also taken from a hard IRQ handler on any CPU. Otherwise the interrupt can arrive on the CPU that already holds the lock, and the handler spins forever, because the code that would release the lock is underneath it on the same CPU. Inside the handler a plain spin_lock is enough since local interrupts are already disabled. For data shared with softirqs, tasklets or timers it's spin_lock_bh. And I prefer irqsave over spin_lock_irq unless I'm certain interrupts are enabled on entry, because spin_unlock_irq unconditionally re-enables them. I reproduced this on a QEMU guest: lockdep reported "inconsistent IN-HARDIRQ-W to HARDIRQ-ON-W usage" before any hang happened, and without lockdep the real deadlock only showed up as an RCU stall 21 seconds later.

**Q.** What is RCU and when would you use it?

**A.** Read-Copy-Update. reader는 `rcu_read_lock`/`rcu_dereference`만 하고 락도 원자 명령도 없이 읽는다. writer는 새 사본을 만들어 `rcu_assign_pointer`로 포인터를 바꿔 공개하고, 옛 객체는 그 전부터 읽던 reader가 모두 끝날 때까지(grace period) 기다렸다가 해제한다 — `synchronize_rcu`로 기다리거나 `call_rcu`/`kfree_rcu`로 예약. 읽기가 압도적이고 잠깐 옛 값을 봐도 되는 데이터, 예를 들어 설정 테이블·장치 목록·라우팅 테이블에 쓴다. writer끼리는 여전히 락이 필요하다.

> RCU lets readers run with essentially zero overhead — no locks, no atomic writes to shared memory — inside rcu_read_lock and rcu_read_unlock, fetching pointers with rcu_dereference. An updater builds a new copy, publishes it with rcu_assign_pointer, and defers freeing the old version until a grace period has elapsed, meaning every reader that might have seen the old pointer has finished. You either block in synchronize_rcu or defer with call_rcu or kfree_rcu. The kernel detects the end of a grace period by waiting for every CPU to pass through a quiescent state, like a context switch or idle. It fits read-mostly data where briefly seeing the old version is fine — routing tables, config tables, device lists. Updaters still need their own lock. In my test, three lock-free readers did six million list walks while a writer replaced entries two thousand times with zero bad reads; switching to an immediate kfree produced two or three use-after-free reads per run.

**꼬리 질문**: "Can you sleep inside an RCU read-side critical section?" → 일반 RCU에서는 안 된다. 필요하면 SRCU.

**Q.** What is a seqlock and where is it used?

**A.** 시퀀스 카운터 + writer용 spinlock이다. writer는 시작·끝에서 카운터를 올리고 reader는 락 없이 읽은 뒤 카운터가 바뀌었으면 다시 읽는다. writer가 절대 reader를 기다리지 않는 writer 우선 구조라, 자주 읽히고 가끔 쓰이는 작은 값, 대표적으로 jiffies_64와 timekeeping에 쓴다. 포인터를 따라가는 데이터에는 안 맞는다(그건 RCU).

> A seqlock is a sequence counter plus a spinlock for writers. Writers bump the counter to odd before updating and to even after; readers take no lock, read the data, and retry if the counter changed or was odd. Writers never wait for readers, so it's ideal for small, frequently read values with an occasional writer — the classic users are jiffies_64 on 32-bit and the timekeeping core behind ktime_get. It doesn't work for data you dereference through pointers, because a reader could follow a freed pointer before it gets the chance to retry; that's RCU's job.

**Q.** How do you prevent and debug deadlocks in the kernel?

**A.** 예방은 락 순서를 전역으로 정해서 문서화하고, 락을 쥔 채 다른 서브시스템을 부르는 일을 줄이는 것. 검증은 lockdep — 락 클래스 그래프를 런타임에 그려서 사이클, IRQ 안전성 위반, 잘못된 wait context를 **실제 deadlock 없이** 보고한다. 이미 멈춘 시스템에서는 hung task 경고, SysRq `w`(blocked task 덤프), RCU stall·soft lockup 메시지의 스택을 본다.

> Prevention is mostly discipline: a documented global lock order, short critical sections, and not calling into other subsystems while holding my locks. For verification I run a kernel with PROVE_LOCKING. Lockdep tracks lock classes and builds a dependency graph at runtime, so it reports an ABBA cycle as "possible circular locking dependency detected" even if the two paths ran at different times and never actually deadlocked — I demonstrated exactly that with a module that took two mutexes in opposite orders sequentially. It also catches IRQ-unsafe usage and invalid wait contexts. One caveat: lockdep disables itself after the first splat, so you fix them one at a time. For a box that's already hung, I look at hung-task warnings, SysRq-w output, and RCU stall or soft-lockup backtraces.

**Q.** What's the difference between atomic_t and refcount_t?

**A.** 둘 다 원자 카운터지만 `atomic_t`는 일반 정수라 넘쳐도 아무 말 없이 감싼다. `refcount_t`는 객체 수명 전용이라 overflow·underflow·0에서 증가를 감지해 경고하고 값을 포화시켜, use-after-free 대신 메모리 누수로 끝나게 한다. 참조 카운트는 `refcount_t`나 그 위의 `kref`를 쓴다.

> atomic_t is a general-purpose atomic integer — it wraps silently on overflow. refcount_t is meant only for reference counts: it detects overflow, underflow and increment-from-zero, warns, and saturates the counter so the object leaks instead of being freed while still in use. On my test kernel, refcount_inc after the count hit zero printed "refcount_t: addition on 0; use-after-free" and pinned the value at 0xc0000000, while atomic_inc on INT_MAX just wrapped to INT_MIN. For object lifetimes I use refcount_t or kref on top of it.

**Q.** What are per-CPU variables and why are they fast?

**A.** CPU마다 따로 가진 사본이다. 각 CPU가 자기 사본만 갱신하니 캐시 라인이 CPU 사이를 오가지 않고 락도 필요 없다. 남는 위험은 같은 CPU의 선점·IRQ뿐이라 `this_cpu_inc` 같은 한 번 연산이나 `get_cpu`/`put_cpu`로 막는다. 읽을 때 모든 CPU를 합산하므로 정확한 순간값이 필요 없는 통계에 맞는다.

> Per-CPU variables give each CPU its own copy, so updates never contend and the cache line never bounces between cores. The only remaining hazards are preemption and interrupts on the same CPU, which this_cpu operations handle in a single instruction, or get_cpu and put_cpu for multi-step updates. Readers sum across all CPUs, so the value is approximate at any instant — perfect for statistics like packet counters. In my four-CPU test, per-CPU increments were roughly sixty times faster than a spinlock-protected counter and faster than even the unprotected, incorrect version.

**Q.** What changes with PREEMPT_RT regarding locks?

**A.** `spinlock_t`와 `rwlock_t`가 priority inheritance가 있는 잠드는 락(rt_mutex 기반)으로 바뀌고, 대부분의 IRQ 핸들러가 스레드로 돈다. 그래서 진짜로 돌아야 하는 곳(irqchip, 스케줄러, HARD hrtimer 콜백)만 `raw_spinlock_t`를 쓴다. `local_irq_disable()` 뒤에 `spinlock_t`를 잡는 코드는 RT에서 깨진다. 일반 커널에서도 `PROVE_RAW_LOCK_NESTING`으로 미리 검사할 수 있다.

> Under PREEMPT_RT, spinlock_t and rwlock_t become sleeping, priority-inheriting locks built on rt_mutex, and most interrupt handlers run as threads, so critical sections become preemptible. Code that truly has to spin — irqchip drivers, scheduler internals, hrtimer callbacks in hard mode — must use raw_spinlock_t. Patterns like disabling interrupts and then taking a spinlock_t break on RT. You can catch those on a non-RT kernel with PROVE_RAW_LOCK_NESTING; I hit exactly that as an "Invalid wait context" splat when I took a spinlock_t in a hard-mode hrtimer callback.

## 19. 직접 해보기

1. **개념** — 단일 코어(`CONFIG_SMP=n`), `CONFIG_PREEMPT=y` 커널에서 `spin_lock()`은 무엇으로 줄어드나? 그래도 `_irqsave`가 필요한 경우는?
   정답/힌트: 선점 끄기(`preempt_disable`)만 남는다. IRQ 핸들러와 공유하는 데이터면 단일 코어에서도 IRQ를 꺼야 한다(선점 끄기는 IRQ를 막지 않는다).
2. **코드** — `f4_irqlock`에 `mode=4`를 추가해 hrtimer를 `HRTIMER_MODE_REL_SOFT`(softirq에서 콜백)로 바꾸고 process 쪽은 `raw_spin_lock`을 쓴다. lockdep 경고의 제목이 어떻게 바뀌는지 예측하고 확인하라. 그다음 `_bh`로 고쳐라.
   정답/힌트: `inconsistent {IN-SOFTIRQ-W} -> {SOFTIRQ-ON-W} usage`가 예상된다. process 쪽을 `raw_spin_lock_bh`로 바꾸면 사라진다. (이 과제는 노트 작성 때 실행하지 않았다 — 직접 돌려서 확인할 것)
3. **측정** — `f4_race`를 `-smp 1`과 `-smp 2`로도 돌려 spinlock·mutex·atomic의 처리량이 CPU 수에 따라 어떻게 변하는지 표로 만들어라. `none`의 손실은 `-smp 1`에서 0이 되나? 0이면 안전하다는 뜻인가?
   정답/힌트: 경합이 줄어 락 비용이 급격히 낮아진다. `-smp 1`에서 손실이 0으로 나와도 선점이 load와 store 사이에 끼면 잃을 수 있으므로 안전하지 않다(E4 §10).
4. **관찰** — 디버그 커널 게스트에서 `cat /proc/lockdep_stats`, `head -50 /proc/lockdep`, `grep -c "" /proc/lockdep_chains`를 보고, 부팅만으로 락 클래스가 몇 개 생기는지 세라. 그다음 `f4_abba`를 넣기 전후로 `debug_locks` 값이 어떻게 바뀌는지 확인하라.
   정답/힌트: 예제 15에서 클래스 715개, 경고 후 `debug_locks: 0`. 경고 전에는 1이다.
5. **코드** — 예제 12의 writer를 `mode=2`로 확장해 `synchronize_rcu()` 후 `kfree()`(동기 방식)로 바꾸고 전체 실행 시간을 `kfree_rcu`와 비교하라.
   정답/힌트: 교체 2000번 × grace period(수 ms)라 writer가 수 초 이상 걸린다. 결과는 같이 `bad=0`이다. 그래서 대량 교체에는 `kfree_rcu`/`call_rcu`를 쓴다.
6. **설계** — 1 kHz IRQ가 갱신하는 `struct imu_state { s32 ax, ay, az; u64 ts; }`를 여러 유저 스레드가 `ioctl`로 최신값을 읽어 간다. spinlock_irqsave, seqlock, RCU 중 무엇을 고를지 근거와 함께 써라.
   정답/힌트: 작은 값 묶음 + writer가 IRQ라 기다리면 안 됨 + reader 다수 → seqlock. writer는 IRQ 핸들러 하나뿐이라 IRQ 안에서 `write_seqlock`, reader는 process context에서 `read_seqbegin`/`read_seqretry` 루프(IRQ가 끼어들면 그냥 한 번 더 읽는다). process 쪽에도 writer가 생기면 그쪽은 `write_seqlock_irqsave`. spinlock_irqsave도 정답이지만 reader가 읽는 동안 IRQ를 막아 IMU 지연이 늘어난다.
7. **관찰** — 일반 커널 게스트에서 예제 4(`mode=2`)를 `-smp 1`로 돌리면 RCU stall 메시지가 나올까? 예측하고 확인하라.
   정답/힌트: 멈춘 CPU를 보고해 줄 다른 CPU가 없고, 유일한 CPU는 IRQ가 꺼진 채 돈다. 메시지 없이 그냥 멈출 가능성이 높다(직접 확인할 것 — 노트 작성 때 실행하지 않았다). 양산 장비에서 하드웨어 워치독이 필요한 이유다.

|---|---|---|
| critical section | 임계 구역 | 공유 데이터를 만지는, 한 번에 하나만 실행돼야 하는 코드 구간 |

| qspinlock | 큐 스핀락 | MCS 큐 기반의 공정한 spinlock 구현 (arm64·x86 기본) |
| raw_spinlock_t | 원시 스핀락 | PREEMPT_RT에서도 진짜 spin하는 락 |
| mutex | 뮤텍스 | owner 있는 잠드는 락, process context 전용 |
| optimistic spinning | 낙관적 스핀 | owner가 실행 중이면 잠들기 전에 잠깐 도는 mutex 최적화 |
| semaphore | 세마포어 | 개수를 세는 잠드는 락 (legacy) |
| rwlock / rw_semaphore | 읽기·쓰기 락 | 읽기 여럿, 쓰기 하나 (spin / sleep) |
| atomic_t | 원자 정수 | 락 없이 원자적 RMW 가능한 정수 |
| refcount_t | 참조 카운트 | overflow·underflow·0에서 증가를 잡는 수명 전용 카운터 |
| per-CPU variable | CPU별 변수 | CPU마다 따로 둔 사본, 공유가 없어 락 불필요 |
| RCU | Read-Copy-Update | 읽기는 락 없이, 쓰기는 복사·교체·지연 해제 |
| grace period | 유예 기간 | 교체 전에 시작한 모든 RCU reader가 끝날 때까지의 시간 |
| quiescent state | 휴지 상태 | CPU가 RCU reader 구간 밖임이 확실한 지점 (context switch, idle) |
| seqlock | 시퀀스 락 | 시퀀스 번호로 reader가 retry하는 writer 우선 락 |
| lockdep | 락 검증기 | 락 클래스 의존 그래프로 deadlock 가능성을 런타임에 증명 |
| lock class | 락 클래스 | lockdep이 같은 것으로 보는 락들의 묶음 (보통 초기화 위치·변수 이름) |
| lock_stat | 락 통계 | 경합 횟수·대기·보유 시간 (`/proc/lock_stat`) |
| ABBA deadlock | 순서 역전 교착 | 두 경로가 두 락을 반대 순서로 잡아 서로 기다림 |
| PREEMPT_RT | 실시간 선점 | spinlock을 잠드는 락으로, IRQ를 스레드로 바꾸는 커널 설정 |
| wait type | 대기 유형 | lockdep이 락·문맥에 매기는 "얼마나 잠드나" 등급 (spin·config·sleep) |

## 21. 요약 & 체크리스트

커널 코드는 SMP·선점·hardirq·softirq라는 네 방향에서 동시에 실행되므로, 공유 데이터마다 "누가 또 만지나"를 먼저 묻는다. 변수 하나면 atomic(수명이면 refcount_t), CPU별로 쪼갤 수 있으면 per-CPU, 읽기가 압도적이면 RCU나 seqlock, 그 밖에는 락이다. 락은 잠들어야 하면 mutex, 아니면 spinlock이고, spinlock은 경쟁자가 hardirq면 `_irqsave`, softirq면 `_bh`를 쓴다. 측정해 보면 락 종류보다 **공유를 줄이는 설계**가 수십 배 차이를 낸다(per-CPU 97 Mops/s vs spinlock 1.7). 이 규칙 위반은 일반 커널에서 조용히 숨었다가 현장에서 "가끔 멈춤"으로 나타나므로, lockdep·`DEBUG_ATOMIC_SLEEP` 커널로 반드시 한 번 돌린다. lockdep은 실제 deadlock 없이도 사이클·IRQ 안전성·wait context 위반을 증명하고, 첫 경고 뒤에는 꺼진다.

- [ ] 커널 동시성의 네 원천과 각각을 막는 장치를 그림으로 설명할 수 있다
- [ ] spinlock과 mutex의 차이를 문맥·잠듦·owner·비용으로 30초 안에 영어로 말할 수 있다
- [ ] "이 데이터를 또 누가 만지나"로 `spin_lock`/`_bh`/`_irq`/`_irqsave`/mutex를 고를 수 있다
- [ ] IRQ self-deadlock이 왜 같은 CPU에서만 생기는지 설명하고 재현할 수 있다
- [ ] `raw_spinlock_t`가 필요한 곳과 PREEMPT_RT에서 바뀌는 것을 말할 수 있다
- [ ] mutex의 fast path·optimistic spinning·slow path를 설명할 수 있다
- [ ] `atomic_t`와 `refcount_t`의 차이를 실제 경고 메시지와 함께 설명할 수 있다
- [ ] per-CPU 변수를 `this_cpu_inc`/`get_cpu`로 쓰고 합산할 수 있다
- [ ] RCU의 reader·updater·grace period를 타임라인으로 그리고, `kfree_rcu`로 리스트 항목을 교체하는 코드를 짤 수 있다
- [ ] seqlock reader의 retry 루프를 짜고 언제 RCU 대신 seqlock인지 말할 수 있다
- [ ] lockdep의 `circular dependency`, `inconsistent lock state`, `Invalid wait context` 경고를 위에서부터 읽을 수 있다
- [ ] `/proc/lock_stat`에서 contentions·acq-bounces·호출 위치로 병목 락을 찾을 수 있다
