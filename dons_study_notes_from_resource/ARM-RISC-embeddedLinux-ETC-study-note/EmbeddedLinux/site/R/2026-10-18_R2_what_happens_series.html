이 노트를 다 읽으면: 전원 ON → 셸, open("/dev/x") → .open, 인터럽트 → 잠든 read() 깨어남, insmod → probe()를 함수 이름으로 끊김 없이 말할 수 있다 · page fault, fork()+exec(), 패킷 → recv()를 1분 안에 설명한다 · 모든 단계를 ftrace/kprobe 실측 줄로 뒷받침한다 · 면접관이 어느 단계에서 끊고 "거기서 더 깊이"를 물어도 해당 모듈 노트로 내려갈 수 있다 왜 필요한가: 시니어 Embedded Linux 면접의 "깊이 확인" 질문은 거의 이 일곱 개의 변형이다. 개념 정의(R1)를 아는지보다 경계를 넘을 때마다 누가 무엇을 넘겨주는지를 아는지를 본다 Don 기준 난이도: 예외 진입·IRQ·DMA·리셋 시퀀스는 펌웨어로 이미 안다 / 새로 외울 것은 Linux가 붙인 함수 이름, 그리고 "잠든다 = runqueue에서 빠진다"는 스케줄러 쪽 연결 선행 노트: C1, C6, C7, E3, E6, F3, F6, F7, F11, F12, G3, G4 (이 노트는 종합 노트라 각 절에서 해당 노트·절을 가리킨다)

0. 큰 그림 — 일곱 경로는 같은 부품을 돌려 쓴다#

0.1 면접관이 이 질문으로 보는 것#

"open("/dev/x")를 하면 무슨 일이 일어나죠?"는 지식 퀴즈가 아니다. 면접관은 지원자가 추상화 경계(유저 ↔ 커널, VFS ↔ 드라이버, hardirq ↔ 프로세스 문맥)를 넘을 때 무엇이 넘어가는지(fd 번호, struct file, dev_t, pt_regs, wait queue 엔트리)를 아는지 본다. 그래서 답은 세 단으로 준비한다.

  1. 30초 버전 — 경계 5~6개를 한 문장씩. 끊기지 않고 끝까지 가는 것이 목표다.
  2. 전체 walk — 번호 붙은 단계, 각 단계에 실제 커널 함수 이름. 면접관이 중간에 끊으면 그 번호에서 내려간다.
  3. 꼬리 질문 — 각 경로에서 단골로 나오는 "그럼 X면요?" 3~5개.

Don의 펌웨어 경험으로 바꾸면 이렇다. SSD 펌웨어에서 "호스트가 NVMe Read를 보내면 무슨 일이 일어나나"를 doorbell 쓰기 → SQ fetch → FTL 조회 → NAND 읽기 → DMA → CQ → MSI-X까지 막힘없이 말할 수 있었을 것이다. 같은 능력을 Linux 커널 함수 이름으로 하는 것이 이 노트다.

0.4 실험용 드라이버 r2_demo — DT 매칭 platform driver + char device#

무엇을 확인하는 코드인가: §2(open/read)와 §4(insmod → probe)를 같은 모듈로 추적하기 위한 최소 드라이버. compatible = "r2,demo" 노드와 매칭되면 probe()에서 char device /dev/r2_demo를 만든다(G3·G4 패턴의 축소판).

출력에서 볼 것: MODULE_DEVICE_TABLE(of, …)가 of:N*T*Cr2,demo modalias를 만든다. udev/modprobe가 DT 노드의 uevent MODALIAS와 이 문자열을 맞춰 모듈을 자동 로드한다(D3 §9). (트레이스는 공백만 다른 직전 버전으로 찍었고, 두 .o의 objdump -d 출력을 cmp로 비교해 .text가 바이트 단위로 같음을 확인했다.)

1. 전원 ON → 셸 프롬프트#

1.1 30초 버전#

"SoC BootROM이 boot pin/fuse로 매체를 골라 첫 단계 로더(TF-A BL1 또는 SPL)를 SRAM에 올린다. BL2가 DRAM을 초기화하고 BL31(EL3 상주 펌웨어, PSCI)과 BL33(U-Boot)을 올린다. U-Boot는 커널 Image·DTB·initramfs를 DRAM에 읽고 booti로 x0=DTB 주소, MMU off 상태로 EL2/EL1 커널 진입점에 점프한다. head.S가 페이지 테이블을 만들고 MMU를 켠 뒤 start_kernel()을 부르고, setup_arch가 DT를 풀고, 각종 서브시스템 초기화 뒤 rest_init이 PID 1 커널 스레드 kernel_init을 만든다. kernel_init은 initcall 레벨 순으로 드라이버를 등록·probe하고 rootfs를 마운트한 뒤 /sbin/init을 exec한다. systemd가 unit 의존성 그래프를 풀어 serial-getty@ttyAMA0을 띄우고, agetty → login → 셸이 프롬프트를 찍는다."

1.2 전체 walk#

  1. 리셋 → BootROM (마스크 ROM, EL3). boot pin/eFuse로 부트 매체 선택, 첫 이미지를 on-chip SRAM에 올리고 (secure boot면) 서명 검증. → C2 §1–§3
  2. TF-A BL1 (EL3, ROM 또는 플래시). FIP에서 BL2를 읽어 검증·실행. 로그 BL1: Booting BL2. → C5 §2
  3. TF-A BL2 (S-EL1). DRAM 초기화(실 보드), BL31·BL32(OP-TEE)·BL33(U-Boot)을 DRAM에 로드·검증, BL1에 SMC로 BL31 실행 요청. QEMU 랩에서 BL33은 DRAM+512 MiB에 올라가서 -m 512로는 data abort가 난다(C5 §3, README).
  4. TF-A BL31 (EL3 상주). PSCI·SMC 런타임 서비스 설치 후 ERET으로 BL33을 EL2(non-secure)에서 시작. 커널이 나중에 CPU on/off·reset을 PSCI SMC로 이 코드에 요청한다. → C5 §4
  5. U-Boot (BL33). board_init_f(재배치 전) → relocate_code → board_init_r → main_loop → bootcmd(bootdelay, bootflow/extlinux 스캔) → load로 Image·initrd·DTB → booti: DTB에 /chosen/bootargs, linux,initrd-start/end, memory 노드를 고쳐 쓰고 x0=DTB 물리 주소, x1..x3=0, MMU·D-cache off로 커널 진입점 점프. → C3, C1 §4
  6. 커널 head.S (arch/arm64/kernel/head.S): primary_entry → record_mmu_state → preserve_boot_args → __pi_create_init_idmap → init_kernel_el(EL2면 hyp stub 설치 후 EL1) → __cpu_setup → __primary_switch → __enable_mmu → __pi_early_map_kernel(KASLR 재배치) → __primary_switched(VBAR_EL1, __fdt_pointer=x21) → bl start_kernel. → C6 §3 (랩 소스 grep 결과가 거기 있다)
  7. start_kernel() (init/main.c): setup_arch(setup_machine_fdt → memblock, paging_init, unflatten_device_tree) → trap_init/mm_core_init → sched_init → init_IRQ(GIC 등록) → time_init(arch timer) → console_init … → rest_init. → C6 §4
  8. rest_init(): user_mode_thread(kernel_init) = PID 1, kernel_thread(kthreadd) = PID 2, 그리고 부트 CPU 자신은 cpu_startup_entry → do_idle로 들어가 PID 0(idle)이 된다. §3·§7의 실측 스택 맨 아래에 do_idle ← cpu_startup_entry ← rest_init ← start_kernel ← __primary_switched가 찍혀 있는 것이 바로 이 사실의 증거다.
  9. kernel_init() → kernel_init_freeable(): do_basic_setup() → driver_init() + do_initcalls()(early → core → postcore → arch → subsys → fs → rootfs → device → late, module_init된 built-in 드라이버는 device_initcall). 이때 DT 노드에서 만들어진 platform_device와 드라이버가 만나 probe된다(§4와 같은 really_probe). 이어서 wait_for_initramfs() → console_on_rootfs()(/dev/console을 fd 0/1/2로) → (initramfs가 없거나 /init이 없으면) prepare_namespace()로 root= 마운트. → C6 §7–§8
  10. free_initmem() — "Freeing unused kernel memory: 4224K" 줄. .init.text가 사라진다. → C6 §9
  11. run_init_process() — 순서: rdinit=(initramfs /init) → init= → CONFIG_DEFAULT_INIT → /sbin/init, /etc/init, /bin/init, /bin/sh. 전부 실패하면 panic("No working init found"). 내부는 kernel_execve = §6의 exec 경로 그대로다. → C7 §1
  12. PID 1 systemd: generator 실행(console=ttyAMA0 → serial-getty@ttyAMA0.service), sysinit.target(udev coldplug, apparmor, tmpfiles) → basic.target → multi-user.target/getty.target. → L1 §2, C7 §2
  13. serial-getty@ttyAMA0 = agetty → (autologin) exec login → login이 PAM 세션을 열고 셸을 fork해서 기다린다 → bash가 프롬프트를 쓴다. BusyBox에서는 login이 셸을 exec해서 PID가 이어진다(C7 §2.2 실측). 아래 실측 ps에서 util-linux 판은 login(283)이 bash(320)의 부모로 남는다.

1.3 실측 1 — 리셋에서 initramfs까지 (M10 §1.4 재사용)#

TF-A → U-Boot → 커널 전 체인은 M10 §1.4에서 호스트 시각 스탬프(m10_ts.py)로 이미 찍었다. 그 로그의 핵심 줄을 그대로 인용한다(왼쪽 = 캡처 시작 후 초).

출력에서 볼 것: BL1: Booting BL31이 BL2 다음에 BL1에서 찍힌다 — BL2가 SMC로 BL1에게 "BL31 실행"을 부탁하는 AArch64 TF-A 흐름(C5 §2)의 증거다. Starting kernel(2.906)과 printk 0점 사이 약 0.36 s는 "시계 없는 커널 초기" 구간(head.S, setup_arch)이다(M10 §1.4의 분석).

1.4 실측 2 — 커널에서 systemd → getty → 셸까지 (이 노트에서 실행)#

무엇을 확인하나: Image-trace + rootfs-trace overlay를 -m 1G로 부팅해 호스트 시각 스탬프를 붙이고, 자동 로그인된 셸에 명령을 보낸다. 캡처기는 M10의 m10_ts.py와 같은 원리(pty + 줄마다 time.monotonic())의 r2_ts.py다.

(색 제어 문자와 중간 줄은 지웠다.) 프롬프트에서 보낸 systemd-analyze, critical-chain, ps 세 명령의 출력(일부 줄만, ps는 두 번 부른 결과를 합쳤다):

출력에서 볼 것:

  • [ T1](PID 1 = kernel_init)이 rootfs 마운트, Freeing unused kernel memory, Run /sbin/init을 찍는다. walk 9–11단계가 이 세 줄이다. T0는 부트 CPU의 start_kernel 문맥(PID 0)이다.
  • 커널은 2.2 s, 유저 공간은 31 s. 그중 sysinit.target 대기 27 s는 apparmor 프로필 로드와 udev coldplug가 dev-ttyAMA0.device를 늦게 알려 준 것이다 — L2 §8(coldplug 74초 사례)과 같은 모양이고 TCG 부하 탓이 크다.
  • bash(320)의 부모가 login(283)이다. util-linux login은 셸을 fork하고 남는다. "getty가 셸을 띄운다"는 말은 정확히는 getty → exec login → fork/exec 셸이다.

그림 2 — 전원 ON → 셸의 두 실측 타임라인. A는 펌웨어 체인을 포함한 M10 실측, B는 이 노트의 systemd 부팅. 실제 제품에서도 "부팅이 느리다"의 범인은 대개 커널이 아니라 bootdelay와 유저 공간 의존성 대기다.

1.5 꼬리 질문#

  • "커널이 콘솔에 아무것도 안 찍어요. 어디부터 봅니까?" — earlycon=pl011,0x9000000(또는 DT stdout-path)로 console_init 전 단계부터 본다. 아무것도 안 나오면 U-Boot→커널 계약(DTB 주소 x0, Image 로드 주소 2 MiB 정렬, MMU off)을 의심. 그다음 __log_buf를 JTAG로 덤프. → C6 §5, M1
  • "initramfs는 왜 쓰나요?" — root 장치 드라이버가 모듈이거나, 암호화·A/B 선택·fsck를 루트 마운트 전에 해야 할 때. 커널은 populate_rootfs로 cpio를 rootfs(tmpfs)에 풀고 /init을 실행한다. → C7 §3
  • "PSCI는 언제 다시 쓰이나요?" — 보조 CPU 기동(CPU_ON), CPU idle(CPU_SUSPEND), reboot/poweroff(SYSTEM_RESET/SYSTEM_OFF). 전부 EL3 BL31로 SMC. → C5 §4
  • "initcall 순서가 왜 중요하죠?" — 공급자(clock, regulator, GPIO, pinctrl)가 소비자보다 먼저 준비돼야 한다. 순서가 어긋나면 -EPROBE_DEFER로 미뤄졌다가 late_initcall의 deferred probe 재시도에서 붙는다. → C6 §7, G3 §9
  • "부팅 시간을 줄이라면?" — 실측 먼저(bootstage, initcall_debug, systemd-analyze critical-chain). 그림 2의 가장 긴 막대부터. → C7 §5, M10

2. open("/dev/x") → 드라이버의 .open, 그리고 read()#

2.1 30초 버전#

"유저가 svc #0으로 커널에 들어오면 el0_svc → invoke_syscall이 openat 핸들러를 부르고 do_sys_openat2로 간다. 먼저 빈 fd 번호를 예약하고, path_openat이 dcache에서 /, dev, r2_demo를 한 성분씩 찾는다(RCU-walk). 찾은 inode가 char device면 inode의 i_fop은 범용 def_chr_fops이고, do_dentry_open이 그 .open인 chrdev_open을 부른다. chrdev_open은 inode의 dev_t로 cdev_map에서 드라이버의 cdev를 찾아 file->f_op을 드라이버 fops로 바꿔 끼우고 드라이버 .open을 부른다. 성공하면 fd_install로 fd 테이블에 struct file을 꽂고 fd 번호를 돌려준다. 이후 read(fd)는 fd → struct file → f_op->read로 바로 드라이버에 간다."

2.2 전체 walk#

  1. 유저: openat(AT_FDCWD, "/dev/r2_demo", O_RDONLY) → svc #0, x8 = __NR_openat(56). → E6 §1
  2. el0t_64_sync → el0t_64_sync_handler → el0_svc → do_el0_svc → el0_svc_common → invoke_syscall → __arm64_sys_openat → do_sys_open → do_sys_openat2. (이 체인은 §4의 실측 스택에 그대로 찍혀 있다.)
  3. getname_flags — 유저 문자열을 커널 struct filename으로 복사(strncpy_from_user). 나쁜 포인터면 여기서 -EFAULT. → E6 §3–§4
  4. get_unused_fd_flags → alloc_fd — fd 번호를 먼저 예약(아직 struct file은 꽂지 않는다). 실측 ret=0x3.
  5. do_filp_open → path_openat → alloc_empty_file(새 struct file, LSM security_file_alloc) → path_init(루트에서 시작) → link_path_walk(/dev 성분: inode_permission → walk_component → lookup_fast/__d_lookup_rcu → step_into, 마운트 포인트면 __lookup_mnt로 devtmpfs로 건너감) → 마지막 성분 lookup_fast → complete_walk(try_to_unlazy: RCU-walk를 ref-walk로 확정). → F12 §3
  6. may_open → inode_permission + devcgroup_check_permission(컨테이너의 장치 cgroup) + LSM.
  7. vfs_open → do_dentry_open: file->f_op = inode->i_fop. char device inode는 생성될 때 init_special_inode가 i_fop = &def_chr_fops, i_rdev = dev_t로 만들어 둔다. 그래서 여기서 불리는 .open은 chrdev_open이다. → F12 §4
  8. chrdev_open: inode->i_cdev가 비었으면 kobj_lookup(cdev_map, inode->i_rdev, &idx)로 cdev_add 때 등록된 cdev를 찾고(exact_match), try_module_get(owner)으로 모듈 참조를 잡고, replace_fops(filp, cdev->ops) → 드라이버 .open(r2_open) 호출. → G4 §2
  9. security_file_post_open(IMA) → terminate_walk(경로 참조 해제) → fd_install(3, file) → 반환값 3이 x0으로 유저에게.

2.3 실측 — function_graph로 본 open과 read (1회차 부팅)#

3. HW 인터럽트 → read()에서 잠든 유저 스레드가 깨어난다#

3.1 30초 버전#

"스레드는 evdev_read 안의 wait_event_interruptible에서 상태를 TASK_INTERRUPTIBLE로 바꾸고 wait queue에 자기를 건 뒤 schedule()로 runqueue에서 빠져 있다. 핀이 바뀌면 GPIO 컨트롤러가 GIC에 SPI를 올리고, CPU는 IRQ 예외로 el1h_64_irq(유저 실행 중이었다면 el0t_64_irq) → gic_handle_irq에서 IAR을 읽어 hwirq를 얻고, generic_handle_domain_irq가 irq_domain으로 Linux IRQ 번호를 찾아 flow handler와 드라이버 ISR을 부른다. ISR은 짧게 끝내고 나머지는 bottom half(여기서는 hrtimer debounce, 일반적으로는 threaded IRQ나 workqueue)로 미룬다. bottom half가 데이터를 버퍼에 넣고 wake_up_interruptible을 부르면 try_to_wake_up이 태스크를 runqueue에 넣고 need_resched를 세운다. IRQ에서 나올 때(또는 다음 스케줄 지점에서) schedule()이 그 스레드로 전환하고, 스레드는 wait_event의 조건을 다시 확인한 뒤 copy_to_user로 데이터를 복사하고 eret으로 유저에 돌아간다."

3.2 무엇으로 증명했나 — QEMU 전원 키 = 진짜 GPIO 인터럽트#

QEMU virt의 전원 버튼은 PL061 GPIO 핀 3에 연결되어 있고, DT의 gpio-keys 노드가 그 핀을 KEY_POWER(116)로 보고한다(I3 §1과 같은 장치). 호스트에서 QEMU 모니터에 system_powerdown을 보내면 핀이 올라갔다가 약 100 ms 뒤 내려간다. 즉 에뮬레이션된 하드웨어가 GIC로 진짜 SPI를 올리는 경로다. gpio-sim(irq_sim)과 달리 GIC → 체인 핸들러 → ISR이 전부 실제 코드다.

무엇을 확인하는 코드인가: /dev/input/event0를 열고 read()에서 잠들어 있다가 키 이벤트를 받는다.

게스트 쪽 트레이스 설정(발췌)과 호스트 쪽 주입:

evdev_pass_values는 GCC가 쪼갠 .part.0 이름으로만 존재했다 — 첫 시도의 p:evpass evdev_pass_values는 write error: Invalid argument로 실패했다. 트레이스할 함수 이름은 available_filter_functions나 System.map에서 확인한다(§6의 .isra.0도 같은 함정).

3.3 실측 — 잠에서 깨어날 때까지 (2회차 부팅, 발췌)#

(각 스택의 맨 위 kprobe 자체 프레임 8줄 — kprobe_trace_func … el1h_64_sync — 과, 두 번째·세 번째 스택의 gic_handle_irq 아래 공통 부분을 지웠다. 그 사이의 arch_timer 틱, rcu 스레드 줄도 지웠다.)

출력에서 볼 것:

  • 잠: 2.227 s에 r2_evread가 prev_state=S로 CPU를 내놓았다. 1.4 s 동안 runqueue에 없다(CPU는 idle).
  • 하드웨어 경로(첫 스택, 아래에서 위로): idle 루프(default_idle_call → WFI) 중에 IRQ 예외 → el1h_64_irq → gic_handle_irq(GIC IAR에서 SPI 번호) → generic_handle_domain_irq(GIC 도메인) → pl061_irq_handler(chained handler: GPIO 칩 자체의 IRQ) → 다시 generic_handle_domain_irq(PL061 도메인, hwirq 3) → handle_edge_irq(엣지 flow) → handle_irq_event → (__handle_irq_event_percpu, 스택에서는 빠짐) → gpio_keys_gpio_isr.   • ISR은 짧다: 3.592858 → 3.595083. gpio_keys_gpio_isr는 이벤트를 보고하지 않고 5 ms debounce hrtimer만 건다(PL061이 gpiod_cansleep() == false라 workqueue 대신 hrtimer를 고른다 — drivers/input/keyboard/gpio_keys.c:567).
  • bottom half: 7.4 ms 뒤 다른 IRQ(irq 11 = arch timer)의 hrtimer_interrupt → gpio_keys_debounce_timer → input_event → input_pass_values → evdev_pass_values(이벤트 2개 = EV_KEY + EV_SYN)가 버퍼에 넣고 wake_up_interruptible_poll(&client->wait, …)을 부른다(drivers/input/evdev.c:289). 그 결과가 sched_waking: comm=r2_evread다. 깨우는 쪽은 hardirq 문맥(h 플래그)이다.
  • 빠진 한 칸: 첫 스택에 __handle_irq_event_percpu(실제로 action->handler를 부르는 함수)가, evpass 스택에 evdev_events가 없다. gk_tmr 스택에는 __hrtimer_run_queues가 없는데 evpass 스택(더 깊은 곳에서 찍힌)에는 있다. 모두 §4.3의 "+0x0 kprobe는 직전 호출자를 빠뜨린다" 규칙이다.
  • N 플래그: dNh5.의 N = need_resched가 섰다. IRQ에서 나온 직후(먼저 runqueue에 있던 kworker 다음) sched_switch ==> next_comm=r2_evread.
  • 유저 복귀: evdev_read가 24(= sizeof(struct input_event))를 반환. IRQ부터 read 반환까지 11.2 ms 중 5 ms는 debounce 설정값, 나머지는 TCG 비용이다.

그림 4 — 인터럽트 하나가 잠든 스레드를 깨우기까지. 하드웨어 IRQ(빨강)는 2 ms 만에 끝나고, 실제 "깨우기"는 5 ms 뒤 다른 IRQ(타이머)의 bottom half에서 일어난다. 유저 스레드는 그동안 runqueue에 없다(점선).

3.5 꼬리 질문#

  • "wake_up과 wait_event 사이에 lost wakeup이 안 생기나요?" — wait_event는 상태를 TASK_INTERRUPTIBLE로 먼저 바꾸고 wait queue에 건 다음 조건을 검사한다. 그 사이 wake_up이 오면 상태가 TASK_RUNNING으로 돌아가 schedule()이 바로 돌아온다. 깨우는 쪽은 조건 변수를 먼저 쓰고 깨운다. → F3 §5
  • "깨어난 스레드가 바로 도나요?" — 아니다. runqueue에 들어가고 need_resched가 설 뿐이다. 실제 전환은 IRQ 복귀 시 preemption 지점이나 현재 태스크의 다음 schedule(). 실측에서도 먼저 깨어 있던 kworker가 한 번 돈 뒤 전환됐다. SCHED_FIFO면 바로 선점. → F1 §7–§8
  • "IRQ가 유저 코드 실행 중에 오면?" — 진입이 el0t_64_irq → el0_interrupt가 되고, 복귀 때 exit_to_user_mode 에서 need_resched·시그널을 처리한다. 이 실측은 CPU가 idle이라 el1h_64_irq였다. → E6 §1, F6 §1
  • "hwirq와 Linux IRQ 번호는?" — 실측: GIC 위 PL061 칩의 hwirq 3 → Linux IRQ 18, virtio는 GIC-0 79 → IRQ 15. 매핑은 irq_domain이 한다. → F6 §3
  • "poll/epoll이면 뭐가 다르죠?" — 같은 wake_up_interruptible_poll이 wait queue의 ep_poll_callback 엔트리를 부른다. 드라이버는 .poll에서 poll_wait로 같은 wait queue를 등록만 하면 된다. → G6 §1, §13

4. insmod foo.ko → probe()가 돌기까지#

4.1 30초 버전#

"kmod insmod는 .ko를 열어 finit_module(fd)를 부른다(BusyBox insmod는 파일을 읽어 init_module(buf)). 커널은 load_module에서 ELF를 검사하고(vermagic, 서명, 라이선스), 모듈 메모리를 할당해 섹션을 복사하고 재배치·심볼 해결을 한 뒤 sysfs에 모듈을 등록한다. do_init_module이 module_init 함수를 do_one_initcall로 부르는데, module_platform_driver면 그게 platform_driver_register다. driver_register → bus_add_driver → driver_attach가 버스의 모든 장치에 대해 __driver_attach를 돌며 platform_match로 DT compatible을 of_match_table과 비교하고, 맞는 장치에 대해 driver_probe_device → really_probe → platform_probe → 드라이버 probe()를 부른다. 장치가 나중에 생기면 반대 방향(device_add → bus_probe_device)으로 같은 really_probe에 도착한다."

4.2 전체 walk#

  1. 유저: kmod insmod → finit_module(fd, "", 0). (BusyBox insmod는 init_module(image, len, "") — 아래 실측이 둘 다 보여 준다.) → E3 §3
  2. el0_svc → invoke_syscall → __arm64_sys_finit_module → idempotent_init_module(같은 파일 동시 로드 중복 제거) → init_module_from_file(커널이 파일을 읽음) → load_module. init_module이면 __do_sys_init_module → copy_module_from_user → load_module.
  3. load_module 내부(대부분 static이라 트레이스에 이름이 안 나온다, kernel/module/main.c:3370): module_sig_check(서명 — 실측 "module verification failed … tainting kernel") → elf_validity_cache_copy → early_mod_check(vermagic, 이미 로드됐는지) → layout_and_allocate(core/init 영역 할당, 섹션 복사) → simplify_symbols(EXPORT_SYMBOL 해결) → apply_relocations → post_relocation → complete_formation(RO/NX 권한) → prepare_coming_module → parse_args(모듈 파라미터) → mod_sysfs_setup(/sys/module/r2_demo). → E3 §2, §10, §13
  4. do_init_module → do_one_initcall(mod->init) → r2_driver_init (module_platform_driver 매크로가 만든 함수) → __platform_driver_register(drv->driver.bus = &platform_bus_type) → driver_register → bus_add_driver(드라이버 kobject, /sys/bus/platform/drivers/r2_demo).
  5. driver_attach → bus_for_each_dev(&platform_bus_type, …, __driver_attach) — 버스에 이미 있는 모든 장치를 순회. 실측 45개.
  6. __driver_attach → driver_match_device → platform_match: driver_override → of_driver_match_device(DT compatible vs of_match_table) → ACPI → id_table → 이름 비교 순서. → D3 §4
  7. 매치(=1)면 driver_probe_device → __driver_probe_device → really_probe: dev->driver = drv → pinctrl 기본 상태 적용, dma_configure → call_driver_probe → platform_probe(clock 기본 설정, PM domain attach) → drv->probe(pdev) = r2_probe. 실패하면 devres 해제, -EPROBE_DEFER면 deferred 목록. → G3 §13, G2 §6
  8. probe 성공 → driver_bound(/sys/bus/platform/drivers/r2_demo/r2_demo 링크, uevent BIND). do_init_module이 init 섹션을 해제하고 상태를 MODULE_STATE_LIVE로.
  9. 유저: finit_module = 0 반환. 이후 /dev/r2_demo는 device_create → devtmpfs가 이미 만들었다.

  • 이 BusyBox insmod는 init_module을 불렀다. 실제 배포판의 kmod는? 다음 실측.

4.4 실측 2 — kmod insmod는 finit_module (systemd 게스트, §1.4와 같은 부팅)#

출력에서 볼 것: kmod는 파일 fd를 넘긴다(finit_module(3, …)). 커널이 파일을 직접 읽으므로 IMA·LoadPin 같은 "어느 파일에서 왔나" 정책을 걸 수 있다(L5·L6). 두 시스템 콜은 load_module에서 합류한다.

그림 5 — 들여쓰기가 호출 깊이다. 주황 줄이 "어느 장치와 맞는가"를 정하는 버스 match, 초록 줄이 드라이버 코드다. 장치가 나중에 생기는 경우(hotplug, overlay)는 device_add → bus_probe_device → __device_attach로 올라와 같은 really_probe에서 만난다(G2 §6).

4.5 꼬리 질문#

  • "probe가 안 불려요. 순서대로 무엇을 보나요?" — ① 모듈이 로드됐나(lsmod) ② 장치가 있나(/sys/bus/platform/devices/에 노드 이름, DT status = "okay") ③ compatible 철자(/proc/device-tree/.../compatible와 of_match_table) ④ probe가 deferred인가(/sys/kernel/debug/devices_deferred) ⑤ probe가 에러를 냈나(dmesg의 probe ... failed with error). → D3 §13, G3 §9, M1
  • "DT 노드는 언제 platform_device가 되나요?" — 부팅 때 of_platform_default_populate_init(arch_initcall_sync)이 루트 아래 compatible 있는 노드와 simple-bus 자식을 platform_device로 만든다. I2C/SPI 자식은 해당 버스 컨트롤러 드라이버가 probe에서 만든다. → D3 §2, §8
  • "built-in이면 무엇이 다른가요?" — load_module이 없고, module_init이 device_initcall이 되어 §1의 do_initcalls에서 같은 driver_register를 부른다. → E3 §12, C6 §10
  • "modprobe는 insmod와 무엇이 다른가요?" — modules.dep로 의존 모듈을 먼저 넣고, alias(of:N*T*Cr2,demo)로 이름을 찾는다. udev가 uevent의 MODALIAS로 modprobe를 부르는 것이 자동 로드다. → E3 §11, D3 §9
  • "probe에서 잠들어도 되나요?" — 된다. 프로세스 문맥(insmod 태스크 또는 부팅 때 kernel_init/async 워커)이다. 다만 오래 걸리면 부팅을 막으므로 PROBE_PREFER_ASYNCHRONOUS를 검토한다. → G3 §11

5. malloc한 메모리를 처음 건드리면 — page fault#

5.1 30초 버전#

"malloc(8 MiB)는 glibc가 mmap(MAP_ANONYMOUS)로 VMA만 만들 뿐 물리 페이지도 PTE도 없다. 첫 store에서 MMU가 translation fault를 내고, EL0 동기 예외로 el0t_64_sync → el0_da → do_mem_abort가 ESR의 fault 종류로 do_translation_fault → do_page_fault를 부른다. 커널은 lock_vma_under_rcu로 주소가 속한 VMA를 찾고 권한을 확인한 뒤 handle_mm_fault → __handle_mm_fault에서 익명 페이지를 할당·0으로 채우고 PTE를 설치한다. THP가 켜져 있고 2 MiB 정렬 범위가 VMA 안에 있으면 4 KiB 대신 2 MiB 한 장을 PMD로 매핑한다. 예외에서 돌아오면 같은 store가 다시 실행되어 성공한다. VMA 밖이면 SIGSEGV다."

5.2 전체 walk#

  1. glibc malloc(8 MiB) > M_MMAP_THRESHOLD(기본 128 KiB) → mmap(NULL, …, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS) → 커널은 vm_area_struct만 추가. RSS 증가 없음. → A5 §5
  2. p[4096] = 1 → MMU 테이블 워크 실패(PTE 없음) → Data Abort from EL0, ESR_EL1.EC = 0x24, DFSC = translation fault level N, FAR_EL1 = 주소.
  3. el0t_64_sync → el0t_64_sync_handler → el0_da → do_mem_abort(far, esr, regs) → fault_info[] 표에서 DFSC로 do_translation_fault → (유저 주소면) do_page_fault. → F11 §5
  4. do_page_fault: mm_flags 계산(write fault) → lock_vma_under_rcu(per-VMA lock, mmap_lock 없이) → VMA 권한 검사 → handle_mm_fault(vma, addr, flags, regs).
  5. __handle_mm_fault: pgd/p4d/pud/pmd 할당 → (THP 조건 충족) do_huge_pmd_anonymous_page 또는 → handle_pte_fault → do_pte_missing → do_anonymous_page: vma_alloc_zeroed_movable_folio → memcg charge → set_pte_at → folio_add_new_anon_rmap → LRU 추가. (6.18 lab 커널에서 이 세 함수는 __handle_mm_fault에 인라인돼 트레이스에 안 보인다.)
  6. 반환 → ret_to_user → eret → 같은 store 명령을 다시 실행 → 이번엔 TLB miss 후 테이블 워크 성공.
  7. 결과: ru_minflt가 1 증가(디스크 I/O 없는 minor fault). 읽기 먼저였다면 공유 zero page를 읽기 전용으로 매핑했다가 쓰기 때 COW.

5.3 실측 — 4 KiB 경로 (3회차, MADV_NOHUGEPAGE)#

무엇을 확인하는 코드인가: 8 MiB를 malloc하고 한 바이트만 쓴다. trace_marker로 그 store 앞뒤에 표시를 남기고, minor fault 수 차이를 출력한다. nothp 인자면 madvise(MADV_NOHUGEPAGE)로 THP를 끈다.

이 코드도 두 번 고쳤다. 첫 판은 madvise(p, …)가 EINVAL이었다 — malloc 포인터는 mmap 시작 + 16바이트라 페이지 정렬이 아니다. 두 번째 판은 delta=2였다 — before를 읽은 뒤 첫 fprintf가 stdio 버퍼를 malloc해 fault가 하나 더 났다. "start" 마커를 먼저 써서 해결했다.

(kprobe 브레이크포인트 처리 줄과 스택의 kprobe 프레임 8줄, 하위 함수 줄을 지웠다. do_mem_abort 361 µs에는 kprobe + 스택 저장 비용 약 130 µs가 들어 있다.)

출력에서 볼 것:

  • 두 마커 사이에 do_mem_abort가 정확히 한 번, delta=1. 한 번의 store = 한 번의 minor fault.
  • 스택: el0t_64_sync → el0t_64_sync_handler → el0_da → do_mem_abort → do_translation_fault → handle_mm_fault. do_page_fault가 안 보인다 — §4.3에서 본 "+0x0 kprobe는 바로 위 호출자를 빠뜨린다"는 규칙 때문이다(handle_mm_fault를 부르는 것은 do_page_fault다, arch/arm64/mm/fault.c). function_graph에도 do_translation_fault/do_page_fault가 안 보이는 것은 다른 이유다: fault.c의 이 함수들은 __kprobes/noinstr 계열이라 available_filter_functions에 없다(실측 grep에서 do_page_fault, do_translation_fault, el0_da 모두 없음).
  • __handle_mm_fault 바로 아래가 vma_alloc_zeroed_movable_folio다. handle_pte_fault → do_anonymous_page가 전부 인라인된 것이다(do_anonymous_page도 available_filter_functions에 없다). 0으로 채운 4 KiB 한 장 할당 → memcg 과금 → PTE 락 → rmap → LRU 순서가 그대로 보인다.
  • flags=0x1255 = FAULT_FLAG_WRITE(1<<0) + ALLOW_RETRY(1<<2) + KILLABLE(1<<4) + USER(1<<6) + INTERRUPTIBLE(1<<9) + VMA_LOCK(1<<12) (include/linux/mm_types.h:1651-1663). 쓰기 fault이고, 유저 모드이고, mmap_lock이 아니라 per-VMA lock으로 처리 중이라는 뜻이다.

5.4 실측 — THP 경로 (1회차, THP always)#

같은 바이너리를 nothp 없이 돌린 1회차에서는 다른 일이 일어났다.

출력에서 볼 것:

  • 주소 0xffffb9200010의 2 MiB 정렬 시작 0xffffb9200000이 VMA 안에 있었기 때문에 2 MiB 한 장이 할당되었다(do_huge_pmd_anonymous_page). 0 채우기만 830 µs, fault 전체 3.05 ms — 4 KiB 경로의 약 8배.
  • 3회차의 "thp" 모드 실행(위 출력 아님)에서는 주소가 0xffffbdc43010이었고 그 2 MiB 정렬 시작은 VMA 시작보다 앞이라 4 KiB 경로로 갔다. THP 여부는 ASLR이 준 주소에 따라 실행마다 달라졌다. RT 루프에서 첫 접근 지연이 들쭉날쭉한 원인 중 하나다 — 그래서 mlockall(MCL_CURRENT|MCL_FUTURE) + 미리 건드리기(prefault)를 한다(A5 §8).

그림 6 — 첫 접근 fault의 두 갈래. 어느 쪽으로 갈지는 THP 설정과 주소 정렬이 정한다.

5.5 꼬리 질문#

  • "minor와 major fault 차이?" — major는 디스크(파일 page cache 미스, swap-in) I/O가 필요하다. 익명 메모리의 첫 접근은 minor. → A5 §3
  • "커널 코드가 유저 포인터를 건드리다 fault 나면?" — copy_from_user 같은 함수의 명령 주소가 예외 테이블에 있어 fixup_exception이 -EFAULT로 바꾼다. 테이블에 없으면 Oops. → E6 §4
  • "fork 뒤 쓰기는?" — 같은 handle_mm_fault지만 PTE가 있고 읽기 전용이라 do_wp_page(COW)로 간다. → A2 §2, §6
  • "RT 루프에서 fault를 없애려면?" — mlockall(MCL_CURRENT|MCL_FUTURE), 스택·힙 prefault, THP는 madvise로 통제, 실행 중 malloc 금지. → A5 §8, N1
  • "page fault와 MMU abort, 펌웨어와 뭐가 다르죠?" — 펌웨어에서는 MPU fault = 버그 → HardFault 핸들러에서 리셋. Linux에서는 "아직 안 채운 것"이 정상 경로다. demand paging이 메모리 과다 약정(overcommit)을 가능하게 하고, 그 대가가 OOM killer다. → A5 §4, F11 §9

6. fork() + exec()#

6.1 30초 버전#

"fork()는 glibc에서 clone(SIGCHLD)이고 커널 kernel_clone → copy_process가 task_struct와 커널 스택을 복제하고, 파일 테이블·fs·시그널 핸들러를 복사하거나 공유하고, dup_mmap으로 VMA를 복사하면서 쓰기 가능한 사설 페이지의 PTE를 양쪽 모두 읽기 전용으로 바꾼다(COW). alloc_pid로 PID를 받고 wake_up_new_task로 런큐에 넣는다. 자식은 ret_from_fork에서 x0=0으로 유저에 돌아온다. execve는 do_execveat_common → bprm_execve → load_elf_binary가 새 mm을 만들고 begin_new_exec에서 옛 mm을 버리고(여기서 COW 공유가 끝난다) ELF 세그먼트를 mmap하고 스택에 argv/envp/auxv를 쌓은 뒤 START_THREAD로 PC와 SP를 새 진입점으로 바꾼다. 부모는 wait4에서 잠들었다가 자식의 exit → SIGCHLD + wake로 깨어난다."

6.2 실측 — kernel_clone과 execve (3회차, max_graph_depth=3)#

무엇을 확인하는 코드인가: fork → 자식은 execv("/bin/true") → 부모는 waitpid.

(copy_process 아래 약 60개 함수 중 주요 줄만 남겼다.)

출력에서 볼 것:

  • 첫 execve는 셸이 exec /r2_fe한 것 — 같은 PID(86)가 프로그램만 바꿨다(old_pid=86).
  • kernel_clone ret=0x57 = 87 = 자식 PID. 부모 쪽 fork 반환값이다. 자식 쪽 0은 copy_thread가 자식 pt_regs의 x0을 0으로 만들어서 생긴다.
  • copy_process 1.49 ms 중 dup_mmap 0.73 ms — fork 비용의 절반이 주소 공간 복사(VMA + PTE 쓰기 금지 표시)다. 그래서 큰 프로세스에서 fork+exec 대신 posix_spawn/vfork를 쓴다(A2 §10에 실측 비교).
  • sched_process_wait 다음 r2_fe-86 => true-87: 부모가 wait4에서 잠들고 자식이 돈다. 자식 exit 후 true-87 => r2_fe-86.
  • do_execveat_common을 set_graph_function에 넣으면 실패했다 — 실제 심볼은 do_execveat_common.isra.0이다(GCC IPA-SRA 최적화 접미사). 그래서 __arm64_sys_execve로 잡았다.

그림 7 — fork와 exec의 역할 분담. 주황 두 칸이 COW의 시작과 끝이다. fork 직후 exec하면 COW로 공유한 페이지는 거의 복사되지 않고 버려진다.

6.3 꼬리 질문#

  • "스레드 생성과 fork의 차이?" — 같은 kernel_clone, 플래그만 다르다. pthread_create는 CLONE_VM|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD…라 dup_mmap 대신 mm을 공유한다. → A2 §8
  • "exec 후 열린 fd는?" — 기본은 유지된다. O_CLOEXEC 붙은 것만 begin_new_exec → do_close_on_exec에서 닫힌다. 데몬이 장치 fd를 자식에게 새는 버그의 원인. → A3 §2
  • "좀비는 언제 생기나?" — 자식 exit 후 부모가 wait하기 전. task_struct 일부와 종료 코드만 남는다. 실측의 prev_state=Z. → A2 §4
  • "exec가 실패하면 원래 프로그램은?" — begin_new_exec(point of no return) 전에 실패하면 원래 프로그램으로 -1/errno 반환. 그 뒤 실패면 SIGSEGV/kill. → A2 §3

7. 네트워크 패킷 도착 → recv()#

7.1 30초 버전#

"NIC가 패킷을 RX 링 버퍼에 DMA하고 인터럽트를 올린다. hardirq 핸들러(virtio-net은 vring_interrupt → skb_recv_done)는 그 큐의 인터럽트를 끄고 napi_schedule로 NET_RX softirq만 예약하고 끝난다. IRQ 복귀 시 softirq net_rx_action이 드라이버 poll(virtnet_poll)을 budget만큼 불러 skb를 만들고 netif_receive_skb → ip_rcv → ip_local_deliver → udp_rcv로 올린다. UDP는 4-튜플로 소켓을 찾아 __udp_enqueue_schedule_skb로 소켓 수신 큐에 넣고 sk_data_ready = sock_def_readable로 wait queue를 깨운다. recvfrom()에서 __skb_wait_for_more_packets로 잠들어 있던 스레드가 스케줄되어 udp_recvmsg가 skb에서 유저 버퍼로 복사한다. 부하가 높으면 softirq가 ksoftirqd로 넘어간다."

7.2 실측 (2회차 부팅, 호스트 → QEMU user-net hostfwd UDP 한 개)#

무엇을 확인하는 코드인가: UDP 5000번에 bind하고 recvfrom()에서 잠든다.

+112는 struct sk_buff의 len 오프셋이다 — gdb -batch -ex "print &((struct sk_buff *)0)->len" vmlinux-trace가 0x70을 돌려줬다.

(이 앞의 7.654459 virtio IRQ + NET_RX에서 들어온 첫 46바이트 프레임은 UDP 소켓까지 가지 않았다 — slirp의 ARP 요청으로 보이며 확인하지 않았다. 스택 아래쪽 idle 루프와 kprobe 프레임, vri 반복 줄을 지웠다.)

출력에서 볼 것:

  • 플래그 D.H3: 이 virtio IRQ는 softirq 처리 도중(앞 프레임의 NET_RX)에 들어왔다. hardirq는 softirq를 선점한다. 그 IRQ가 다시 NET_RX를 올렸다.
  • napi_poll ... work 1 budget 64 — poll 한 번에 최대 64개, 이번엔 1개.
  • netif_receive_skb len=46: Ethernet 헤더를 뗀 길이. UDP 9바이트 + IP 20 + UDP 8 = 37, 최소 프레임 패딩으로 46. 소켓 큐에 들어갈 때(udpq)는 페이로드 9바이트.
  • 스택: softirq는 별도 스레드가 아니라 IRQ 출구(irq_exit_rcu → __irq_exit_rcu → do_softirq_own_stack)에서 돈다. virtnet_poll → napi_complete_done → GRO 목록 flush → netif_receive_skb_list_internal → ip_list_rcv → … → udp_rcv → sock_def_readable. 그다음 줄이 sched_waking: comm=r2_udp — §3과 같은 wait queue 깨우기다.
  • sdr 스택 맨 위가 udp_queue_rcv_one_skb다. 실제 직전 호출자 __udp_enqueue_schedule_skb는 빠졌지만, 그 함수의 kprobe(udpq)가 바로 앞 줄에서 발화해 순서를 보충한다.
  • softirq 출구에서 아직 NET_RX가 남아 ksoftirqd/0이 깨어났고, 그 뒤 r2_udp로 전환 → udp_recvmsg ret=9. UDP IRQ에서 반환까지 5.3 ms(TCG).

그림 8 — 패킷 하나가 거치는 세 문맥. hardirq는 "알림"만 하고, 프로토콜 처리는 softirq, 복사는 받는 스레드가 한다. 부하가 높으면 주황 층이 ksoftirqd로 옮겨 간다.

7.3 꼬리 질문#

  • "NAPI는 왜 쓰나요?" — 패킷마다 IRQ면 고부하에서 IRQ 폭풍(livelock). 첫 IRQ 후 인터럽트를 끄고 polling으로 budget만큼 처리, 비면 napi_complete_done으로 IRQ를 다시 켠다. Don의 SSD 펌웨어 CQ 처리에서 interrupt coalescing과 같은 아이디어. → I6 §5
  • "패킷이 버려지는 지점은?" — RX 링 가득(드라이버 rx_dropped), backlog(netdev_max_backlog), 소켓 수신 버퍼(SO_RCVBUF 초과 → UdpRcvbufErrors), 체크섬. nstat/ethtool -S로 층별 카운터. → A9 §5, I6 §12
  • "LiDAR UDP 스트림에서 지연을 줄이려면?" — IRQ affinity와 수신 스레드 CPU 일치(RSS/RPS), SO_RCVBUF 확대, busy polling(SO_BUSY_POLL), PREEMPT_RT에서 threaded NAPI. → A9 §8, N4
  • "TCP면?" — tcp_v4_rcv → tcp_rcv_established → 수신 큐 + ACK 생성, tcp_recvmsg. 깨우기는 같은 sk_data_ready(TCP는 sock_def_readable 계열). → A9 §13

9. Embedded 실무에서 다시 보기#

  • "버튼 눌렀는데 앱 반응이 300 ms 늦다" (센서 키트의 E-stop 버튼): §3의 타임라인을 실제 보드에서 그대로 찍는다. irq_handler_entry → (debounce) → sched_waking → sched_switch → 앱의 read 반환. 지연이 debounce 설정(debounce-interval)인지, 앱 스레드가 SCHED_OTHER라 늦게 스케줄되는지(F1 §8), IRQ가 다른 CPU에 가서 IPI가 끼는지(F6 §7) 구간별로 갈린다.
  • "부팅 후 /dev/imu0가 없다": §4의 walk 순서대로 본다 — of_platform_populate가 장치를 만들었나 → 모듈이 로드됐나(modalias) → platform_match가 맞나 → really_probe에서 -EPROBE_DEFER인가 → device_create가 불렸나(§2의 devtmpfs). 각 단계에 sysfs 증거가 있다(D3 §6, G3 §9).
  • "카메라 프레임 처리 루프가 처음 몇 프레임만 느리다": §5. 버퍼를 처음 건드릴 때 page fault(THP면 2 MiB 0 채우기 830 µs도 실측)가 루프 안에서 일어난다. mlockall + prefault, 또는 dma-buf로 커널이 미리 할당한 버퍼를 mmap(A5 §12, H9).
  • "LiDAR 패킷이 가끔 빠진다": §7의 층별 드롭 카운터 + napi_poll 이벤트의 work/budget. budget을 계속 다 쓰면 softirq가 ksoftirqd로 밀려 수신 스레드와 같은 CPU에서 경쟁한다.
  • "부팅 3초 목표": §1 그림 2의 막대 순서대로. M10이 실측한 bootdelay 2 s, 이 노트가 실측한 apparmor·udev coldplug 대기가 제일 크다.

11. 면접에서 이렇게 말한다#

Q. "Walk me through what happens from power-on until you get a shell prompt on an ARM64 Linux board."

A. BootROM → TF-A BL1/BL2/BL31 → U-Boot → booti(x0=DTB) → head.S가 MMU를 켜고 start_kernel → rest_init이 PID 1 kernel_init → initcall로 드라이버 probe → rootfs 마운트 → /sbin/init exec → systemd → getty → login → 셸. 실측으로 커널 2.2 s, 유저 공간 31 s였고 대부분 apparmor·udev 대기였다고 덧붙인다.

"The boot ROM picks the boot device from straps or fuses and loads the first stage — on our ARM64 boards that's TF-A BL1, which loads BL2. BL2 brings up DRAM and loads BL31, the EL3 runtime that provides PSCI, plus U-Boot as BL33. U-Boot loads the kernel Image, the DTB and the initramfs, patches the chosen node, and jumps to the kernel with the DTB address in x0 and the MMU off. head.S builds the identity map, enables the MMU, relocates, and calls start_kernel, which parses the device tree, sets up memory, the scheduler, the GIC and the timer, and then rest_init creates PID 1, kernel_init. kernel_init runs the initcalls — that's where built-in drivers register and get probed against the device tree — mounts the root filesystem, frees init memory and execs /sbin/init. systemd then walks its dependency graph to getty.target; agetty execs login, and login starts the shell. When I measured it in QEMU, the kernel took about two seconds and user space thirty, almost all of it waiting on AppArmor and udev coldplug — which is typical: the kernel is rarely the bottleneck."

꼬리 질문: "콘솔에 아무것도 안 나오면?" → earlycon, DTB 주소·정렬, __log_buf JTAG 덤프 (§1.5).

Q. "What happens in the kernel when a user calls open() on /dev/mydevice?"

A. syscall → do_sys_openat2 → fd 번호 예약 → path_openat의 dcache 탐색 → char device inode의 def_chr_fops → chrdev_open이 dev_t로 cdev를 찾아 f_op을 드라이버 fops로 교체 → 드라이버 .open → fd_install. 실측에서 struct file 주소가 open 결과와 read의 fdget_pos에서 같았다.

"The svc instruction traps into el0_svc, which dispatches to do_sys_openat2. It first reserves a free fd number, then path_openat walks the path component by component through the dentry cache, mostly lock-free in RCU mode. The device node's inode only carries the dev_t, and its file operations are the generic def_chr_fops, so do_dentry_open calls chrdev_open. chrdev_open looks up the cdev registered for that major/minor in cdev_map, takes a reference on the owning module, swaps the file's f_op to the driver's file_operations, and calls the driver's open. On success fd_install puts the struct file into the fd table and the number goes back to user space. After that, read() is cheap: fd to struct file to f_op->read, straight into the driver — I verified with function_graph that the struct file pointer returned by path_openat is the same one fdget_pos finds on read."

꼬리 질문: "노드는 있는데 드라이버가 없으면?" → -ENXIO, 노드가 없으면 -ENOENT (§2.4).

Q. "A hardware interrupt fires. How does a user thread blocked in read() end up running again?"

A. 잠: wait_event_interruptible = 상태 변경 + wait queue + schedule(). 깨움: GIC → gic_handle_irq → irq_domain → flow handler → ISR → bottom half → wake_up → try_to_wake_up → need_resched → IRQ 출구 또는 다음 스케줄 지점에서 전환 → 조건 재확인 → copy_to_user → eret.

"The reader went to sleep in the driver's read with wait_event_interruptible: it set itself TASK_INTERRUPTIBLE, added itself to the device's wait queue and called schedule, so it's off the run queue. When the line toggles, the GPIO controller raises an SPI on the GIC; the CPU takes the IRQ exception, gic_handle_irq reads the acknowledge register, and generic_handle_domain_irq maps the hardware number through the irq domain — in my trace it went through two domains, the GIC and then the PL061 GPIO chip's chained handler — to the edge flow handler and the driver's ISR. The ISR does the minimum and defers; in gpio-keys that's a 5 ms debounce hrtimer, in an I2C sensor driver it would be a threaded IRQ. The deferred part pushes the event into the buffer and calls wake_up_interruptible, which runs try_to_wake_up: the task goes back on the run queue and need_resched is set. On the way out of the interrupt, or at the next scheduling point, schedule switches to the reader, which rechecks its condition, copies the data to user space and returns. In QEMU I measured about 11 ms from IRQ to read returning, of which 5 ms was the debounce."

꼬리 질문: "lost wakeup은?" → 상태 먼저 바꾸고 조건 확인, 깨우는 쪽은 조건 먼저 쓰기 (§3.5).

Q. "You run insmod on your driver. What has to happen before your probe() is called?"

A. finit_module → load_module(서명·vermagic·재배치·심볼) → do_init_module → module_init = platform_driver_register → bus_add_driver → driver_attach가 버스 장치를 순회하며 platform_match(OF compatible) → 맞으면 really_probe → platform_probe → probe(). 실측: 45개 장치 중 1개 매치.

"insmod opens the .ko and calls finit_module — BusyBox uses init_module with a buffer, but both end in load_module. load_module checks the signature and vermagic, allocates module memory, copies the sections, resolves symbols against the exported symbol table, applies relocations, sets page permissions and creates the sysfs entries. Then do_init_module calls the module's init function through do_one_initcall. With module_platform_driver that's platform_driver_register, which goes driver_register, bus_add_driver, driver_attach. driver_attach iterates over every device already on the platform bus and calls platform_match on each — the OF match compares the device tree compatible strings against the driver's of_match_table. In my trace it tried 45 devices and only my node matched. For the match it calls driver_probe_device, really_probe — which binds the device, applies the default pinctrl state and DMA configuration — then platform_probe, and finally my probe. If the device shows up later instead, device_add triggers the same match from the other side and ends in the same really_probe."

꼬리 질문: "probe가 안 불리면 무엇부터?" → 장치 존재 → compatible → deferred → probe 에러 (§4.5).

Q. "What happens on the first write to memory you just got from malloc?"

A. malloc은 VMA만 만든다 → 첫 store에서 translation fault → el0_da → do_mem_abort → do_translation_fault → lock_vma_under_rcu → handle_mm_fault → 0으로 채운 페이지 할당 + PTE → store 재실행. THP면 2 MiB, 주소 정렬에 따라 달라진다.

"A large malloc is just an anonymous mmap: the kernel creates a VMA but no page and no page-table entry. The first store takes a translation fault from EL0; el0_da calls do_mem_abort, which uses the fault status in ESR to dispatch to do_translation_fault and the page-fault handler. It finds the VMA under the per-VMA RCU lock, checks permissions, and calls handle_mm_fault, which allocates a zeroed page, charges it to the memory cgroup, installs the PTE and puts the page on the LRU. Then we return and the same store re-executes and succeeds — that's one minor fault. One thing I saw in traces: with THP set to always, if the 2 MB-aligned region fits in the VMA you get a 2 MB huge page instead, and zeroing it took ten times longer — and whether that happens depended on the randomized address. That's why real-time code locks and pre-faults its memory."

꼬리 질문: "커널이 유저 포인터에서 fault 나면?" → 예외 테이블 fixup → -EFAULT (§5.5).

Q. "Explain fork() and exec() at the kernel level."

A. kernel_clone → copy_process(task_struct, fd 테이블, dup_mmap + COW) → alloc_pid → wake_up_new_task; 자식은 ret_from_fork에서 0 반환. exec는 bprm_execve → load_elf_binary → begin_new_exec(옛 mm 버림, CLOEXEC) → START_THREAD. 실측: fork의 절반이 dup_mmap.

"fork is clone with SIGCHLD; kernel_clone calls copy_process, which duplicates the task_struct and kernel stack, copies the fd table and fs info, and dup_mmap copies the VMAs and write-protects private pages in both parent and child for copy-on-write. It allocates a PID and wake_up_new_task puts the child on a run queue; the child returns from ret_from_fork with zero in x0. exec goes through do_execveat_common and bprm_execve to the ELF loader, which builds a new mm, and begin_new_exec is the point of no return: the old address space is dropped — ending any COW sharing — close-on-exec fds are closed, the segments are mapped, argv and the aux vector go on the new stack, and start_thread points the PC at the entry. In my trace about half of fork's time was dup_mmap, which is why posix_spawn or vfork is preferred for big processes."

Q. "A UDP packet arrives at the NIC. How does it get to recv()?"

A. DMA → IRQ → 드라이버 ISR이 napi_schedule → softirq net_rx_action → 드라이버 poll → netif_receive_skb → ip_rcv → udp_rcv → 소켓 큐 + sock_def_readable → 잠든 recvfrom 깨어남 → udp_recvmsg 복사.

"The NIC DMAs the frame into a pre-posted RX buffer and raises an interrupt. The hard IRQ handler does almost nothing — it masks that queue's interrupt and schedules NAPI, which raises the NET_RX softirq. On interrupt exit, net_rx_action calls the driver's poll function with a budget; the driver builds skbs and hands them up through netif_receive_skb, IP receive, and udp_rcv, which looks up the socket by its four-tuple, appends the skb to the socket's receive queue and calls sk_data_ready — sock_def_readable — which wakes the thread sleeping in recvfrom. That thread then copies the payload out in udp_recvmsg. In my trace on virtio-net the whole softirq stack ran on the interrupt exit path, and a second interrupt even preempted the softirq; under load that work moves to ksoftirqd."

꼬리 질문: "패킷이 어디서 버려질 수 있나?" → 링, backlog, 소켓 버퍼 (§7.3).

Q. "How would you prove any of this on a real board?"

A. ftrace function_graph + set_graph_function, kprobe + stacktrace 트리거, sched/irq tracepoint. 이 노트의 모든 경로를 그렇게 찍었다.

"I'd trace it. function_graph with set_graph_function scoped to the entry point and a PID filter gives the call tree with durations; a kprobe with a stacktrace trigger on the leaf — the driver's probe, the ISR, sock_def_readable — gives the whole path from the exception vector; and the sched_waking and sched_switch tracepoints give the wakeup timing. The two gotchas are that inlined functions and compiler clones like .isra.0 don't show up under their source names, and that a kprobe on a function's first instruction fires before the prologue, so the stack trace skips the immediate caller — I always cross-check against the source."

14. 요약 & 체크리스트#

일곱 "무슨 일이 일어나나" 질문은 같은 부품의 조합이다: 예외로 들어와서(svc, data abort, IRQ), 테이블을 따라 간접 호출하고(f_op, drv->probe, handle_irq, sk_data_ready), 잠들거나 깨우고(wait queue + try_to_wake_up + schedule), eret으로 나간다. 이 노트는 각 경로를 6.18.55 커널에서 function_graph·kprobe 스택·sched 이벤트로 실제 찍었다: alloc_fd ret=0x3과 같은 struct file 주소, PL061 체인 핸들러를 거치는 두 겹 irq_domain, 45개 장치 중 하나만 platform_match = 1, delta=1 page fault와 주소에 따라 달라지는 THP, dup_mmap이 절반인 fork, softirq가 IRQ 출구에서 도는 UDP 수신. 면접에서는 30초 버전으로 끝까지 간 다음, 면접관이 멈춘 번호에서 이 실측 줄 하나를 근거로 내려가면 된다.
