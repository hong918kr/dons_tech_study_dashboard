0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어에서 DMA 디스크립터를 넘길 때 한 일을 떠올려 보자. 디스크립터에 주소와 길이를 쓰고, DMB(또는 DSB)를 넣고, owner 비트를 장치 쪽으로 넘기고, 마지막으로 doorbell 레지스터를 쳤다. 배리어를 빼면 컨트롤러가 owner 비트는 보지만 주소는 옛 값을 읽는 일이 생긴다. 이 노트는 그 경험을 Linux 커널의 어휘로 옮긴다.

A8에서는 유저스페이스 C11 atomic으로 "arm64는 순서를 지켜 주지 않는다"를 MP litmus 하나로 확인했다(약 5천만 번에 3~7번). 이 노트는 그 다음 단계다.

  • 순서를 바꾸는 주체는 둘이다: 컴파일러와 CPU. 막는 도구도 따로다.
  • 커널은 C11 <stdatomic.h>를 쓰지 않는다. 대신 READ_ONCE, smp_mb(), smp_store_release() 같은 자체 매크로와 LKMM이라는 자체 메모리 모델이 있다.
  • 관찰자도 여럿이다: 다른 CPU(inner shareable), DMA 엔진(outer shareable), MMIO 장치. 관찰자에 따라 배리어 종류가 달라진다(smp_* vs dma_* vs mb()/readl()).

그림 1 — 순서를 바꾸는 두 주체와 막는 도구. 컴파일러 단계는 barrier()/READ_ONCE로, CPU 단계는 dmb/ldar/stlr로, 장치까지 가는 순서는 dma_*·mb()·readl/writel로 다룬다. CPU 배리어 매크로는 전부 "memory" clobber를 가진 asm이라 컴파일러 배리어 역할도 겸한다.

0.1 실습 준비 — 커널 매크로를 유저스페이스로 옮기기#

유저스페이스 litmus 실험을 커널과 같은 명령으로 하려고, 랩 소스(arch/arm64/include/asm/barrier.h, include/asm-generic/rwonce.h, include/linux/compiler.h)의 정의를 그대로 옮긴 헤더를 만든다. (smp_store_release/smp_load_acquire는 4바이트 경우만 남겼다.)

이 VM의 CPU가 ldapr를 지원하는지는 /proc/cpuinfo의 lrcpc 플래그로 확인한다.

출력에서 볼 것: atomics(LSE, ldadd/stadd 같은 단일 명령 atomic), lrcpc(ldapr), uscat(LSE2, 정렬 조건이 완화된 single-copy atomicity)이 있다. QEMU의 cortex-a57(ARMv8.0)에는 셋 다 없다 — 이 차이가 §2.5에서 커널 atomic의 alternative 패치로 드러난다.

커널 모듈은 E5와 같은 방식으로 랩 rootfs를 복사해 .ko와 게스트 스크립트를 넣고 부팅한다. 이번엔 SMP 실험을 위해 -smp 4, 그리고 TCG의 스레드 모드(thread=multi는 vCPU마다 호스트 스레드 하나, thread=single은 호스트 스레드 하나가 vCPU를 돌아가며 실행)를 인자로 받는다.

1. 첫 번째 재배치자 — 컴파일러#

1.1 직관: 컴파일러는 "다른 스레드"를 모른다#

C 표준의 as-if 규칙: 컴파일러는 이 스레드 하나만 보고 관찰 가능한 결과가 같다면 코드를 마음대로 바꿔도 된다. 그런데 "관찰 가능한 결과"에 다른 CPU, ISR, DMA 장치는 들어가지 않는다. 그래서 컴파일러 입장에서는 정당한 최적화가, 다른 관찰자에게는 순서 위반이 된다. 게다가 C11 이후 표준은 data race(락이나 atomic 없이 두 스레드가 같은 변수에 접근하고 하나 이상이 쓰기)를 정의되지 않은 동작(UB)으로 본다. 컴파일러가 "race는 없다"고 가정해도 되는 근거다.

Don에게 익숙한 장면: Cortex-M에서 ISR이 세우는 플래그를 while (!flag);로 기다렸는데 -O2에서 무한 루프가 된 경험. 그게 이 절의 전부다. 커널은 그 문제를 volatile 변수 선언이 아니라 READ_ONCE 접근 지점 표시로 푼다.

1.2 예제 1 — 폴링 루프: 평범한 load vs READ_ONCE#

다른 스레드가 100 ms 뒤 ready = 1을 쓰는 동안 메인 스레드가 기다린다. 차이는 루프 조건 한 줄뿐이다.

출력에서 볼 것: 평범한 버전은 ready를 딱 한 번 읽고(af0), 0이면 afc: b afc — 자기 자신으로 점프하는 무한 루프로 간다. load가 루프 밖으로 끌어올려진(hoisting) 것이다. 실제로 3초 timeout에 걸려 종료 코드 124로 죽었다. READ_ONCE 버전은 루프 안에 ldr이 있어(b00 ↔ b04) 100 ms 뒤 정상 종료한다. 이건 CPU와 무관한, 순수한 컴파일러 문제다 — x86에서도 똑같이 걸린다.

커널에서는 이런 대기를 직접 짜기보다 smp_cond_load_acquire(ptr, cond)나 readl_poll_timeout()(MMIO, H 모듈)을 쓴다. arm64의 smp_cond_load_*는 READ_ONCE/smp_load_acquire로 읽고, 조건이 안 맞으면 __cmpwait_relaxed()(exclusive monitor + wfe)로 그 캐시 라인이 바뀔 때까지 잠깐 잠든다 — 랩 소스 arch/arm64/include/asm/barrier.h에서 확인했다. 바쁜 대기의 전력 소모를 줄이는 arm64식 최적화다.

1.3 예제 2 — 컴파일러가 평범한 접근에 하는 일 네 가지#

LKMM 문서(tools/memory-model/Documentation/access-marking.txt)와 Documentation/memory-barriers.txt가 경고하는 변환을 gcc 15 -O2로 직접 확인한다.

(함수 사이 패딩 nop 줄은 grep으로 뺐다. 주소 0은 아직 재배치 전인 .o라서다.)

출력에서 볼 것, 네 가지:

  • (a) store fusing: fuse_plain은 str 하나(값 2)뿐이다. flag = 1은 사라졌다. 장치나 다른 CPU가 1을 보는 순간은 영영 오지 않는다. WRITE_ONCE 버전은 str 두 개를 그대로 낸다.
  • (b) load fusing: load2_plain은 ldr 하나 + lsl #1(= 두 배). "두 번 읽어 비교"하는 코드(예: seqlock 스타일, 하드웨어 카운터 두 번 읽기)가 무력화된다. READ_ONCE 버전은 ldr 두 개.
  • (c) store tearing: tear_plain은 64비트 상수를 32비트 레지스터 하나로 만들고 stp w1, w1 — 32비트 store 두 개짜리 pair로 쓴다. 상수 만드는 명령을 하나 아끼려는 최적화다. Arm 아키텍처는 stp의 두 원소 각각만 single-copy atomic이라고 보장하므로(LSE2가 조건을 넓히긴 하지만 그걸 기대하면 안 된다), 다른 CPU가 상위만 바뀐 값을 볼 수 있다. WRITE_ONCE 버전은 64비트 레지스터를 만들어 str x1 하나로 쓴다.
  • (d) 재배치 + dead store 제거: order_plain은 flag를 먼저 쓰고(b0) data는 마지막 값 하나만 쓴다(b4). 소스의 data = v는 사라졌다. barrier()를 넣은 order_barrier는 data=v(c8) → flag=1(d0) → data=v+1(d8) 소스 순서 그대로다. 그리고 barrier() 자체는 명령을 하나도 만들지 않았다.

한 가지 더, invented load(없던 load 만들기)도 있다. 레지스터가 모자라면 컴파일러가 지역 변수에 담아 둔 값을 버리고 공유 변수를 다시 읽을 수 있다. int t = p; if (t) use(t->x);가 if (p) use(p->x);처럼 두 번 읽는 코드가 되면, 그 사이 다른 CPU가 p = NULL을 쓸 경우 NULL 역참조가 난다. 짧은 예제로는 재현이 어려워 이 노트에서는 실행하지 않았다. 대책은 같다: 공유 변수는 READ_ONCE로 한 번 읽어 지역 변수에 담는다.

1.4 barrier() — 명령 0개짜리 컴파일러 배리어#

빈 inline asm에 "memory" clobber를 붙인 것이다. gcc에게 "이 asm은 아무 메모리나 읽고 쓸 수 있다"고 말하는 셈이라, gcc는

  • 이 지점 앞에서 레지스터에 들고 있던 메모리 값을 버리고(뒤에서 다시 읽고),
  • 앞의 store는 이 지점 전에 실제로 메모리에 쓰고,
  • 메모리 접근을 이 지점 너머로 옮기지 않는다.

CPU에게는 아무 영향이 없다. 그래서 barrier()가 충분한 경우는 관찰자가 같은 CPU일 때뿐이다 — 같은 CPU의 인터럽트 핸들러, preemption 경계, CONFIG_SMP=n 커널. 실제로 include/asm-generic/barrier.h는 CONFIG_SMP가 꺼지면 smp_mb()/smp_rmb()/smp_wmb()를 barrier()로 정의한다(랩 소스 110~122행). 단일 코어에서는 CPU가 자기 자신의 접근 순서를 항상 프로그램 순서대로 관찰하기 때문이다.

1.5 READ_ONCE / WRITE_ONCE — 접근 지점에 붙이는 표시#

핵심은 volatile 캐스트다. gcc는 volatile 접근을 지우거나, 합치거나, 개수를 바꾸지 않는다. 그리고 compiletime_assert_rwonce_type()이 크기를 검사한다 — char/short/int/long/long long 크기가 아니면 컴파일 에러. 그래서 machine word 크기의 정렬된 접근이 되고 tearing이 없다.

언제 쓰나 — 커널 규칙(LKMM access-marking.txt의 요지):

  • 락 없이 동시에 접근될 수 있는 공유 변수는 양쪽 다 READ_ONCE/WRITE_ONCE로 표시한다. 표시하지 않은 동시 접근은 data race이고, KCSAN(Kernel Concurrency Sanitizer, M 모듈)이 잡는다.
  • 락으로 보호된 변수는 필요 없다. 락이 컴파일러·CPU 배리어를 다 품고 있다(F4).
  • READ_ONCE는 배리어가 아니다. 다른 CPU에 대한 순서는 §2의 도구로 따로 만든다(§3.5 실험의 "MP relaxed"가 정확히 READ_ONCE/WRITE_ONCE만 쓴 경우다 — 순서가 깨진다).

arm64 특이점 하나: arch/arm64/include/asm/rwonce.h는 CONFIG_LTO일 때 READ_ONCE를 ldar(또는 RCpc가 있으면 ldapr)로 바꾼다. LTO가 주소 의존(address dependency)을 컨트롤 의존으로 바꿔 버릴 위험이 있어서, 아예 acquire load로 만들어 순서를 지킨다는 주석이 붙어 있다. 랩 커널은 LTO가 아니므로 READ_ONCE는 평범한 ldr이다(§2.4 objdump에서 확인).

1.6 함정#

  • volatile 변수 선언으로 때우기: 커널 코딩 스타일 문서(Documentation/process/volatile-considered-harmful.rst)가 명시적으로 반대한다. volatile은 컴파일러만 막고 CPU 순서는 못 막으며, 락으로 보호된 구간에서는 최적화만 방해한다. 예외는 jiffies 같은 극소수와 MMIO 접근자 내부.
  • "READ_ONCE를 붙였으니 순서도 맞다": 아니다. 두 READ_ONCE 사이 순서는 컴파일러만 지키고 arm64 CPU는 바꿀 수 있다.
  • 구조체 통째로 READ_ONCE: 크기 검사에 걸려 컴파일 에러가 나거나(8바이트 초과), 통과해도 필드별 일관성은 보장되지 않는다. 여러 필드를 일관되게 읽으려면 락, seqlock, RCU(F4).
  • barrier()로 SMP 순서 맞추기: 단일 코어 테스트에선 통과하고 멀티코어 양산에서 깨진다.

2. 두 번째 재배치자 — CPU (arm64는 weakly ordered)#

2.1 직관: 코어 하나에는 순서대로, 남에게는 뒤죽박죽#

A8 §7.2에서 본 것처럼 arm64 코어는 성능을 위해

  • store를 store buffer에 넣어 두고 다음 명령을 계속 실행한다(캐시에 반영되기 전에 뒤의 load가 먼저 끝날 수 있다 → store→load 재배치, SB 패턴).
  • load를 out-of-order로 실행한다(뒤의 load가 먼저 캐시를 읽을 수 있다 → load→load 재배치, MP 읽는 쪽).
  • 서로 다른 캐시 라인의 store가 다른 순서로 다른 코어에 보일 수 있다(store→store 재배치, MP 쓰는 쪽).

같은 코어에서 자기 접근을 보면 항상 프로그램 순서대로 보인다. 문제는 다른 관찰자다. 그리고 Armv8은 other-multi-copy atomic이다: 어떤 store가 자기 코어 밖의 관찰자 하나에게 보이면 모든 다른 관찰자에게도 동시에 보인다. 그래서 "CPU A와 B가 같은 두 store를 서로 다른 순서로 보는" IRIW 결과는 arm64 하드웨어에선 안 나온다(Power는 나온다 — LKMM이 IRIW를 "Sometimes"로 두는 이유, §3.7).

2.2 arm64 배리어 명령 — 종류 × 범위#

DMB <option>(Data Memory Barrier)의 option은 두 축으로 이뤄진다.

  • 어떤 접근을 순서 짓나: (없음) = load와 store 전부, LD = 앞의 load ↔ 뒤의 load·store, ST = 앞의 store ↔ 뒤의 store.
  • 누구에게(shareability domain): ISH(inner shareable — 같은 OS 아래의 모든 CPU), OSH(outer shareable — DMA 마스터 같은 장치까지 포함하는 넓은 도메인), SY(full system).

그 밖의 명령:

  • DSB(Data Synchronization Barrier): 앞의 메모리 접근이 완료될 때까지 뒤의 모든 명령을 멈춘다. DMB는 "보이는 순서"만 정하고 실행은 계속하는 반면, DSB는 실행 자체를 막는다. 캐시·TLB 유지보수 완료 대기, 시스템 레지스터 쓰기 전, WFI 전에 필요하다.
  • ISB: 파이프라인을 비워 뒤 명령을 새로 fetch한다(시스템 레지스터 변경 반영, self-modifying code).
  • LDAR/STLR: acquire load / release store. 배리어를 접근 자체에 붙인 형태라 dmb보다 가볍다. Arm은 STLR 뒤의 LDAR도 순서를 지킨다(RCsc, sequentially consistent acquire/release).
  • LDAPR(ARMv8.3 LRCPC): RCpc acquire. 앞의 STLR과의 순서를 보장하지 않는다. §3.6에서 측정으로 차이를 본다.

2.5 atomic과 smp_mb__before_atomic() / __after_atomic()#

커널 atomic API의 순서 규칙(Documentation/atomic_t.txt):

  • 값을 돌려주지 않는 RMW(atomic_inc(), atomic_add(), set_bit())는 relaxed — 순서 보장 없음.
  • 값을 돌려주는 RMW(atomic_inc_return(), atomic_xchg(), 성공한 atomic_cmpxchg(), test_and_set_bit())는 fully ordered — 앞뒤로 smp_mb()가 있는 것처럼.
  • _relaxed/_acquire/_release 접미사로 약하게 만들 수 있다.
  • relaxed RMW에 순서가 필요하면 smp_mb__before_atomic()/smp_mb__after_atomic()을 붙인다. x86처럼 모든 locked 명령이 이미 full barrier인 아키텍처에선 이게 barrier()로 사라지고, arm64에선 진짜 dmb ish가 된다 — 그래서 별도 매크로가 있다.

두 번째 덩어리:

출력에서 볼 것, 이 객체 코드엔 두 갈래가 같이 있다:

  • 각 함수 첫머리의 b 120(또는 b 164, b 1b0) 다음에 LSE 경로(stadd, ldaddal 한 명령)가 있고, 점프 대상에는 LL/SC 경로(ldxr/stxr 루프)가 있다. 기본은 LL/SC로 점프하는 것이고, 부팅 때 CPU가 LSE를 지원하면 커널이 그 b를 nop으로 패치한다(alternative). 아래 .altinstructions 재배치가 그 패치 목록이다 — 각 함수의 b 주소(0x104, 0x144, 0x18c, 0x1e0)가 alt_cb_patch_nops 콜백과 짝지어져 있다.
  • smp_mb__before_atomic() → dmb ish 후 stadd. __after_atomic() → stadd 후 dmb ish.
  • atomic_inc_return()(값 반환 = fully ordered): LSE 경로는 ldaddal — a(acquire) + l(release)이 붙은 단일 명령. LL/SC 경로는 ldxr … stlxr(release store-exclusive) + 끝의 dmb ish. "release + 뒤에 full barrier"로 fully ordered를 만든다.

3. LKMM과 litmus 테스트 — 순서를 "증명"하는 언어#

3.1 LKMM이란#

LKMM(Linux Kernel Memory Model)은 커널 소스 tools/memory-model/에 들어 있는 형식 메모리 모델이다. linux-kernel.cat(cat 언어로 쓴 공리들), linux-kernel.bell, linux-kernel.def(smp_mb() 같은 매크로를 모델 이벤트로 매핑)로 이뤄지고, 외부 도구 herd7이 litmus 테스트의 모든 가능한 실행을 열거해 "이 결과가 허용되나?"를 답한다. klitmus7은 같은 litmus를 커널 모듈로 바꿔 실제 하드웨어에서 돌린다.

LKMM은 모든 아키텍처의 공통 분모다. arm64에서 우연히 안 나는 결과라도 Power나 Alpha에서 나면 LKMM은 "허용(Sometimes)"이라고 답한다. 드라이버는 그 약한 보장에만 기대야 이식성이 있다.

출력에서 볼 것: 모델 파일과 문서가 있다. 특히 Documentation/simple.txt(입문), recipes.txt(패턴별 처방), cheatsheet.txt(한 장 요약), explanation.txt(형식 정의 해설). herd7은 설치돼 있지 않고, 이 노트에서는 설치하지 않았다. 아래는 README에 실린 herd7 실행 예시를 인용한 것이다(실행 결과 아님).

읽는 법: 가능한 최종 상태가 3개이고, exists 조건(둘 다 0)을 만족하는 상태는 0개(Positive: 0) → Never. 대신 우리는 §3.5에서 실제 하드웨어로 같은 질문을 던진다.

litmus 파일 이름에는 규칙이 있다: MP+pooncerelease+poacquireonce = MP 패턴, P0는 "po(프로그램 순서) + once(WRITE_ONCE) → release", P1은 "acquire → once". fencewmb는 smp_wmb(), fencemb는 smp_mb(), ctrl은 컨트롤 의존.

3.2 MP (message passing) — "데이터 쓰고 플래그"#

출력에서 볼 것: 배리어 없는 MP는 "Sometimes", smp_wmb()+smp_rmb() 짝이나 release+acquire 짝이면 "Never". 그리고 주석 그대로 "usually better to use smp_store_release() and smp_load_acquire()".

그림 4 — MP 패턴. 빨간 화살표(rf, reads-from)는 P1이 P0의 flag 쓰기를 읽었다는 뜻이다. 그런데도 P1이 buf의 옛 값(0)을 읽으면(회색 점선, fr = from-read) 깨진 전달이다. 막으려면 쓰는 쪽의 store→store와 읽는 쪽의 load→load를 둘 다 막아야 한다.

이건 Don의 DMA 디스크립터 패턴과 똑같은 모양이다. P0 = CPU, P1 = DMA 엔진, buf = 디스크립터 내용, flag = owner 비트. 그때 쓰는 배리어만 dma_wmb()로 바뀐다(§6).

3.3 SB (store buffering) — "나는 쓰고 너를 읽는다"#

출력에서 볼 것: SB는 full barrier(smp_mb())만 막는다고 주석이 말한다("Locking and RCU can also suffice, but not much else"). smp_wmb()/smp_rmb()는 store→load 순서를 다루지 않으므로 소용없다.

그림 5 — SB 패턴과 store buffer. 각 CPU는 자기 store를 store buffer에 넣고 곧바로 load를 실행한다. 자기 store는 store forwarding으로 자기에게는 보이지만, 상대에게는 아직 안 보인다. 두 CPU가 동시에 그러면 둘 다 0을 읽는다. 막는 방법은 store buffer를 비울 때까지 load를 기다리게 하는 full barrier뿐이다.

SB가 커널 어디에 나오나: "나는 잠들겠다고 표시하고(store) → 깨울 조건을 다시 본다(load)" vs "조건을 만들고(store) → 자는 사람이 있나 본다(load)". set_current_state() + 조건 검사 vs 조건 설정 + wake_up()(F3)이 정확히 SB다. 그래서 set_current_state()가 smp_store_mb()(store + smp_mb())이고, waker 쪽도 full barrier를 쓴다. 이걸 놓치면 lost wakeup이 난다.

3.4 LB (load buffering)와 의존성#

출력에서 볼 것: LB는 "각자 상대가 나중에 쓸 값을 먼저 읽는" 결과(둘 다 1)다. 시간 역행처럼 보이지만, CPU가 load가 끝나기 전에 뒤의 독립적인 store를 먼저 내보내면 가능하다. LKMM과 Arm 아키텍처는 이를 허용한다. 그런데 두 번째 파일처럼 P0의 store가 load 결과에 컨트롤 의존(if (r0))하고 P1이 smp_mb()를 쓰면 Never다. 투기 실행된 store는 다른 CPU에게 보이지 않으므로, 하드웨어는 컨트롤 의존 load→store 순서를 지킨다.

의존성 순서(dependency ordering)는 배리어 없이 얻는 순서다.

  • 주소 의존: p = READ_ONCE(gp); v = READ_ONCE(p->x); — 두 번째 load의 주소가 첫 load 결과에 달려 있다. Alpha를 뺀 모든 CPU가 이 순서를 지킨다. RCU의 rcu_dereference()가 여기에 기댄다(F4).
  • 컨트롤 의존: if (READ_ONCE(x)) WRITE_ONCE(y, 1); — load→store만 순서가 생긴다(load→load는 아님). 컴파일러가 분기를 없애면(양쪽 분기에 같은 store가 있을 때 등) 의존이 사라지므로 매우 깨지기 쉽다. Documentation/control-dependencies.txt 참고. 드라이버에서는 기대지 말 것.

3.6 stlr→ldar는 순서를 지키고 stlr→ldapr는 안 지킨다 — 그리고 LKMM은 둘 다 믿지 말라고 한다#

SB release+acquire 결과가 갈린 이유:

  • Arm의 LDAR은 RCsc(release consistency, sequentially consistent): 프로그램 순서상 앞에 있는 STLR이 완료되기 전에 LDAR이 끝나지 않는다. 그래서 stlr x; ldar y는 SB를 막는다 — 측정 0.
  • LDAPR(ARMv8.3 LRCPC)은 RCpc: 앞의 STLR과의 순서를 보장하지 않는다. 그래서 store buffer에 stlr이 머무는 동안 ldapr이 먼저 끝난다 — 측정 3만 번.

그럼 커널 코드에서 smp_store_release(); smp_load_acquire();로 SB를 막을 수 있나? 아니다. LKMM에서 release→acquire(다른 변수)는 store→load 순서를 주지 않는다. 지금 arm64 커널의 smp_load_acquire()가 ldar이라서 우연히 막히는 것뿐이다. 실제로 arm64 커널은 CONFIG_LTO에서 READ_ONCE를 ldapr로 바꾸고, RCpc를 쓰는 아키텍처(Power의 lwsync 기반 acquire 등)에선 SB가 그대로 일어난다. SB에는 smp_mb(). 측정이 이 규칙의 이유를 보여 준다.

5. MMIO 순서 — readl/writel vs _relaxed#

5.1 Device 메모리 속성부터#

ioremap()이 돌려준 가상 주소는 페이지 테이블에 Device-nGnRE 속성으로 매핑된다(랩 소스 arch/arm64/include/asm/io.h 285행: __ioremap_prot(..., PROT_DEVICE_nGnRE)). Don이 Cortex-R/M에서 MPU로 설정하던 "Device" 영역과 같은 개념이다.

글자뜻결과
nG (non-Gathering)여러 접근을 하나로 합치지 않음레지스터 두 번 쓰기가 한 번이 되지 않는다
nR (non-Reordering)같은 장치(주변장치 블록)에 대한 접근끼리 순서 유지같은 장치의 레지스터 쓰기·읽기가 프로그램 순서대로 도착
E (Early write ack)쓰기 완료 응답을 중간(인터커넥트)에서 일찍 줄 수 있음posted write — CPU는 "끝났다"고 보지만 장치에는 아직 안 도착

변형: ioremap_wc()는 Normal-NC(write-combining, 합치기·재배치 허용 — 프레임버퍼), ioremap_np()는 Device-nGnRnE(non-posted — 일부 플랫폼 전용, Documentation/driver-api/device-io.rst: PCI BAR에는 쓰면 안 된다, PCI 메모리 쓰기는 항상 posted이므로).

중요한 것: Device 속성이 주는 순서는 같은 장치에 대한 MMIO끼리뿐이다. 일반 메모리(DMA 버퍼) 접근과 MMIO 접근 사이의 순서는 아무도 보장하지 않는다. 그걸 메워 주는 게 readl/writel 안의 배리어다.

5.2 readl/writel의 해부 — 랩 소스와 objdump#

즉 arm64에서

  • writel = dma_wmb()(dmb oshst) + str. 앞의 일반 메모리 쓰기(예: 디스크립터)가 장치에 보이기 전에 MMIO 쓰기가 나가지 않게 한다.
  • readl = ldr + dma_rmb()(dmb oshld) + 가짜 컨트롤 의존(eor x, v, v → 항상 0, cbnz). 뒤의 일반 메모리 읽기(예: DMA로 들어온 데이터)가 MMIO 읽기보다 먼저 실행되지 않게 하고, 뒤에 오는 udelay()가 읽기 완료 뒤에 시작되게 한다.
  • __raw_readl의 ldr은 ARM erratum 832075(Cortex-A57 초기 리비전, cpu_errata.c의 설명 문자열 "ARM erratum 832075")가 있는 CPU에서 부팅 시 ldar로 패치된다. §2.5의 .altinstructions 마지막 두 쌍이 그것이다.

5.3 memory-barriers.txt의 다섯 가지 보장#

랩 소스 Documentation/memory-barriers.txt의 "KERNEL I/O BARRIER EFFECTS" 절은 ioremap() 매핑에 대한 readX()/writeX()의 보장을 다섯 개로 정리한다(요약).

  1. 같은 장치에 대한 readX()/writeX()는 서로 순서가 지켜진다.
  2. 스핀락을 잡고 한 writeX()는, 같은 락을 나중에 잡은 다른 CPU의 writeX()보다 장치에 먼저 도착한다.
  3. writeX()는 같은 스레드가 앞서 한(또는 그 스레드에 전파된) 모든 메모리 쓰기의 완료를 먼저 기다린다 — dma_alloc_coherent() 버퍼에 쓴 내용이 DMA 시작 레지스터 쓰기보다 먼저 보인다.
  4. readX()는 같은 스레드의 뒤따르는 메모리 읽기가 시작되기 전에 완료된다 — DMA 완료 상태 레지스터를 읽은 뒤 coherent 버퍼를 읽으면 옛 데이터가 아니다.
  5. readX()는 뒤따르는 delay() 루프가 시작되기 전에 완료된다.

readX_relaxed()/writeX_relaxed()는 1번만 보장한다. 2~5번이 필요하면 직접 배리어를 넣거나 non-relaxed를 쓴다.

§5.2의 명령이 정확히 이 보장을 구현한다: 3번 = writel의 dmb oshst, 4번 = readl의 dmb oshld, 5번 = 가짜 컨트롤 의존(+ get_cycles() 안의 isb). 2번은 아키텍처마다 구현이 다르다. arm64는 스핀락 unlock의 stlr(release)이 앞의 MMIO 쓰기까지 순서 지어 준다고 보고 별도 처리가 없다. 반면 랩 소스에서 riscv와 ppc64는 ARCH_HAS_MMIOWB를 선택해, 스핀락 unlock 때 include/asm-generic/mmiowb.h의 추적 장치가 필요한 경우에만 MMIO 쓰기 배리어를 넣는다. 예전 드라이버 코드에 보이는 mmiowb() 호출이 이 일을 드라이버가 직접 하던 흔적이다.

에서 첫 쓰기가 아직 스위치나 브리지 버퍼에 있는 동안 udelay(10)이 시작되고 끝날 수 있다. 장치 입장에선 리셋과 enable 사이 간격이 10 us보다 짧다. 해결은 Don이 알던 그대로 같은 장치에서 아무 레지스터나 읽는 것(read-back)이다. PCIe 순서 규칙상 Memory Read 요청은 같은 경로의 앞선 posted write를 추월할 수 없고, 읽기는 non-posted라 completion이 돌아와야 끝난다.

memory-barriers.txt의 5번 보장 예시가 정확히 이 모양이다(writel(42, DEVICE_REGISTER_0); readl(DEVICE_REGISTER_0); udelay(1); writel(42, DEVICE_REGISTER_1);). 같은 이유로 인터럽트 마스크 레지스터에 쓴 직후 free_irq()나 락 해제를 하기 전에도 read-back을 넣는다 — 그렇지 않으면 "마스크했는데 인터럽트가 하나 더 들어오는" 경쟁이 생긴다.

주의: read-back은 같은 장치여야 한다. 다른 장치를 읽어도 다른 경로라 앞의 posted write를 밀어내지 않는다. 그리고 wmb()(dsb st)는 posted write를 장치까지 밀어내지 않는다 — DSB는 "CPU 쪽에서 완료"를 기다릴 뿐이고, Early write ack 때문에 그 "완료"가 인터커넥트 어딘가에서 이미 났을 수 있다.

예제로 확인한다. 진짜 PCIe 장치가 없으니 QEMU virt의 PL031 RTC Match 레지스터(0x09010004, 쓰기·읽기 가능, 알람을 켜지 않으면 무해)를 빌려 쓴다. §6의 모듈 f5_doorbell이 doorbell 쓰기 뒤 같은 레지스터를 readl로 다시 읽어 값을 확인한다(출력은 §6.2). TCG 에뮬레이션이라 posted write의 시간 효과는 측정할 수 없다. 여기서 확인하는 건 패턴과 명령뿐이다.

6. DMA 순서 — 디스크립터, owner 비트, doorbell#

6.1 고전 패턴#

memory-barriers.txt의 dma_wmb() 설명에 실린 예시(랩 소스 1928~1945행)가 Don이 SSD 펌웨어에서 매일 쓰던 패턴이다.

순서를 지켜야 하는 곳이 세 군데다.

  • owner를 확인한 뒤에 내용을 읽기: dma_rmb(). 장치가 내용을 쓰고 status를 바꿨어도 CPU가 내용을 먼저(투기적으로) 읽었다면 옛 내용이다. MP의 읽는 쪽.
  • 내용을 쓴 뒤에 owner 넘기기: dma_wmb(). MP의 쓰는 쪽.
  • owner를 넘긴 뒤에 doorbell: writel() 안의 dmb oshst가 해 준다. writel_relaxed()를 쓴다면 그 앞에 wmb() 또는 dma_wmb()가 필요하다.

같은 문서의 경고: dma_*() 배리어는 MMIO에 대한 순서는 주지 않는다. 그건 readl/writel 또는 필수 배리어 몫이다.

그림 9 — 디스크립터 넘기기의 전체 순서. ②가 없으면 장치가 ⑤에서 OWN을 보고 옛 addr/len을 읽는다(MP의 쓰는 쪽). ④의 writel 안 배리어가 없으면 doorbell이 status보다 먼저 도착할 수 있다. ⑦의 dma_rmb()가 없으면 CPU가 결과 데이터를 status보다 먼저 읽어 옛 값을 쓴다(MP의 읽는 쪽). 장치 쪽 ⑤·⑥의 순서는 장치 하드웨어의 책임이다.

그래서 coherent 메모리의 배리어가 왜 dmb osh*면 충분한가: Normal-NC 메모리는 캐시를 안 거치니 "완료"를 기다릴 필요 없이 장치(outer shareable 관찰자)에게 보이는 순서만 정하면 된다. 반대로 coherent 장치(dma-coherent, 하드웨어 snoop — 예: 일부 SoC의 PCIe RC나 CCI에 붙은 마스터)에서는 coherent 버퍼가 cacheable이고, 그래도 dma_wmb()는 같은 dmb oshst다 — 관찰자가 OSH 도메인 안에 있기 때문이다.

6.4 함정#

  • dma_wmb() 대신 smp_wmb(): dmb ishst는 inner shareable — CPU끼리의 순서만 정한다. 많은 SoC에서 우연히 동작하지만(ISH와 OSH가 같은 하드웨어 경로인 경우) 이식성 없는 버그다.
  • writel_relaxed()로 doorbell: 앞의 status store와 순서가 없다. 장치가 doorbell을 받고 status를 읽었는데 아직 OWN이 아니면 장치는 "할 일 없음"으로 잠든다 — 타임아웃 후 재시도로 가려져 성능 저하로만 보인다.
  • dma_rmb() 빼먹기(완료 경로): if (d->status == DONE) use(d->data) — status와 data 읽기가 재배치되면 옛 데이터. 특히 NAPI 폴링 루프처럼 인터럽트 없이 링을 읽는 경로에서 터진다.
  • streaming 버퍼를 map한 뒤 CPU가 다시 쓰기: map 시점에 clean했으니 그 뒤 쓰기는 캐시에만 남는다. 쓰기는 map 전에, 또는 dma_sync_single_for_device()로 소유권을 다시 넘긴다.
  • 배리어로 캐시 문제를 풀려는 시도: dsb를 아무리 넣어도 cacheable 버퍼의 dirty 라인은 메모리에 안 간다. 순서(barrier)와 가시성(cache maintenance)은 다른 문제다.

10. 면접에서 이렇게 말한다#

Q. What's the difference between a compiler barrier and a memory barrier? Is volatile enough?

A. 재배치하는 주체가 둘이다. 컴파일러는 싱글 스레드 관점의 as-if 규칙으로 load/store를 옮기고, 합치고, 지운다. barrier()는 빈 asm에 "memory" clobber를 붙인 것이라 명령은 0개이고 컴파일러만 막는다. CPU는 store buffer와 out-of-order 실행으로 다른 코어가 보는 순서를 바꾸는데, 그건 dmb 같은 진짜 명령이 있어야 막힌다. volatile(커널에선 READ_ONCE/WRITE_ONCE)은 접근을 지우거나 쪼개지 않게 할 뿐 CPU 순서는 못 막는다. 실제로 gcc -O2에서 평범한 폴링 루프가 b . 무한 루프로 컴파일되는 걸 objdump로 봤고, READ_ONCE만 쓴 MP 테스트가 arm64에서 1천만 번에 수백 번 깨지는 걸 측정했다.

There are two reorderers. The compiler can move, merge, or delete plain accesses because it only has to preserve single-threaded behavior; barrier() is an empty asm with a memory clobber, so it emits zero instructions and only constrains the compiler. The CPU reorders through store buffers and out-of-order loads, and that needs a real instruction like dmb. volatile, or READ_ONCE/WRITE_ONCE in the kernel, prevents tearing, fusing, and hoisting, but gives no cross-CPU ordering. I've seen a plain polling loop compile to a branch-to-self at -O2, and a message-passing test with only READ_ONCE/WRITE_ONCE fail several hundred times per ten million on arm64.

꼬리 질문: "그럼 READ_ONCE는 언제 필요 없나?" → 락으로 보호된 변수. 락이 컴파일러·CPU 배리어를 다 품고 있다.

Q. Explain smp_wmb() vs wmb() vs dma_wmb(). What do they compile to on arm64?

A. 세 가족이다. smp_wmb()는 CPU끼리 일반 메모리 store 순서 — arm64에서 dmb ishst, UP 커널에선 barrier(). dma_wmb()는 CPU와 DMA 장치가 공유하는 coherent 메모리의 store 순서 — dmb oshst, outer shareable 도메인까지. wmb()는 필수 배리어로 MMIO까지 포함한 모든 store — dsb st라서 앞의 store가 완료될 때까지 파이프라인을 세운다. 모듈을 빌드해 objdump로 확인했고, 측정하면 dsb가 dmb보다 7~8배 비쌌다. 그래서 디스크립터 owner 비트 앞에는 dma_wmb(), CPU 간 플래그엔 smp_wmb()나 release, wmb()는 _relaxed MMIO와 메모리를 섞을 때만 쓴다.

They're three families. smp_wmb() orders stores to normal memory between CPUs — dmb ishst on arm64, and just a compiler barrier on a UP kernel. dma_wmb() orders stores to coherent DMA memory as seen by a device — dmb oshst, the outer-shareable domain. wmb() is the mandatory barrier that also covers MMIO — it's dsb st, which stalls until prior stores complete. I verified the mapping by disassembling a test module, and in a microbenchmark dsb cost roughly seven to eight times a dmb. So: dma_wmb() before handing a descriptor's OWN bit to the device, smp_wmb() or release for CPU-to-CPU flags, and wmb() only when mixing relaxed MMIO with memory.

꼬리 질문: "x86에서는 이게 다 뭐가 되나?" → TSO라서 smp_wmb()/smp_rmb()/dma_wmb()는 컴파일러 배리어, smp_mb()는 locked 명령이나 mfence 계열. 그래서 x86에서만 테스트한 드라이버가 arm64에서 깨진다.

Q. Walk me through posting a DMA descriptor and ringing the doorbell. Which barriers, and why?

A. 디스크립터 주소·길이를 쓰고, dma_wmb(), 그다음 OWN 비트를 장치로 넘기고, writel()로 doorbell. dma_wmb()가 없으면 장치가 OWN은 새 값, 주소는 옛 값으로 볼 수 있다 — MP 패턴의 쓰는 쪽이다. doorbell은 writel()이어야 하는데, arm64 writel()은 store 앞에 dmb oshst가 있어 앞의 OWN 쓰기가 장치에 먼저 보이게 한다. writel_relaxed()를 쓰면 그 보장이 없어 wmb()를 따로 넣어야 한다. 완료 경로에선 반대로 status를 읽고 dma_rmb() 후 데이터를 읽는다. 모듈로 이 함수를 컴파일해 보면 str, str, dmb oshst, str(OWN), dmb oshst, str(doorbell) 여섯 줄이 나온다. SSD 펌웨어에서 하던 "데이터 → DMB → owner → doorbell"과 같은데, Linux는 범위별로 배리어 이름이 다를 뿐이다.

Write the descriptor fields, dma_wmb(), then flip the OWN bit, then writel() the doorbell. Without dma_wmb() the device can observe OWN set but stale address or length — the writer side of message passing. The doorbell must be writel(), not the relaxed variant: on arm64 writel() puts a dmb oshst before the store, so the OWN write is visible to the device before the doorbell arrives. On completion it's the mirror image: read status, dma_rmb(), then read the data. When I compiled that function, it was literally str, str, dmb oshst, str OWN, dmb oshst, str doorbell. It's the same thing I did in SSD firmware with DMB and owner bits — Linux just names the barrier by who the observer is.

꼬리 질문: "링이 dma_alloc_coherent()가 아니라 streaming이면?" → 그땐 순서가 아니라 캐시가 문제다. dma_map_single()/dma_sync_single_for_device()가 dc cvac + dsb sy로 clean해 주고, 그 호출이 소유권 경계다.

Q. When is it safe to use readl_relaxed()/writel_relaxed()?

A. 같은 장치의 MMIO끼리는 Device-nGnRE 매핑이 순서를 지켜 주므로, 레지스터 초기화 시퀀스나 FIFO 반복 읽기처럼 일반 메모리와 순서가 필요 없는 곳에선 relaxed가 안전하다. 반대로 DMA 버퍼와 엮이는 곳 — DMA를 시작하는 레지스터 쓰기, DMA 완료 상태 읽기 — 은 non-relaxed가 필요하다. arm64 소스를 보면 writel은 dmb oshst + str, readl은 ldr + dmb oshld + 가짜 컨트롤 의존이고 relaxed는 str/ldr 하나뿐이다. 실무에선 기본은 non-relaxed, 프로파일로 hot path가 확인된 곳만 relaxed로 바꾸고 주석을 단다.

Accesses to the same device are already ordered by the Device-nGnRE mapping, so relaxed accessors are fine for register init sequences or draining a FIFO — anywhere you don't need ordering against normal memory. Anything that pairs with a DMA buffer — the register write that starts DMA, or the status read that says DMA finished — needs the non-relaxed version. On arm64, writel is dmb oshst plus the store, readl is the load plus dmb oshld plus a fake control dependency for udelay, and the relaxed ones are a single instruction. My default is non-relaxed, and I switch a hot path to relaxed only after profiling, with a comment explaining why.

Q. What is a posted write, and how do you make sure a register write has reached the device?

A. PCIe 메모리 쓰기는 completion이 없는 posted 트랜잭션이고, arm64 ioremap()의 Device-nGnRE도 E(early ack) 속성이라 CPU는 쓰기가 끝났다고 보고 진행한다. 그래서 writel() 직후 udelay()나 free_irq()는 장치 도착과 순서가 없다. 해결은 같은 장치 레지스터를 readl()로 읽는 read-back이다 — read는 non-posted라 completion을 기다리고, PCIe 순서 규칙상 앞선 posted write를 추월하지 못한다. wmb()(dsb)로는 안 된다, CPU 쪽 완료만 기다리니까. 커널 memory-barriers.txt에 writel; readl; udelay(1); writel 예시가 그대로 있다.

PCIe memory writes are posted — no completion — and on arm64 ioremap() gives Device-nGnRE, where the E means early write acknowledgment. The CPU considers the store done long before the device sees it, so a udelay() or free_irq() right after writel() isn't ordered against arrival. The fix is a read-back from the same device: the read is non-posted, must wait for its completion, and can't pass the earlier posted write on the same path. A wmb() doesn't help because dsb only waits for completion from the CPU's point of view. memory-barriers.txt literally shows writel, readl, udelay(1), writel as the pattern.

Q. What are litmus tests and the LKMM? Give me MP and SB and how to fix each.

A. LKMM은 커널 tools/memory-model에 있는 형식 메모리 모델이고, herd7이 litmus 테스트의 모든 실행을 열거해 결과가 허용되는지 답한다. MP는 데이터 쓰고 플래그, 반대편은 플래그 읽고 데이터 — 쓰는 쪽 smp_wmb와 읽는 쪽 smp_rmb 짝, 또는 release/acquire 짝으로 막는다. 한쪽만 고치면 안 되는 것도 측정했다(wmb만이면 1천만에 수백, rmb만이면 수십). SB는 각자 자기 변수 쓰고 상대 변수 읽기 — store buffer 때문에 둘 다 옛 값을 볼 수 있고, smp_mb()만 막는다. 흥미로운 점은 arm64 stlr→ldar는 SB를 막는데(측정 0) ldapr로 바꾸면 3만 번 깨졌다. LKMM은 release/acquire로 SB가 막힌다고 보장하지 않으니 커널 코드에선 반드시 smp_mb()를 쓴다. 실무 예가 sleep/wakeup — set_current_state()가 smp_store_mb()인 이유다.

The LKMM is the formal model in tools/memory-model; herd7 enumerates every execution of a litmus test and says whether an outcome is allowed. Message passing is "write data, then flag" versus "read flag, then data" — fixed with a paired smp_wmb/smp_rmb, or better, release/acquire. I measured that fixing only one side isn't enough. Store buffering is each CPU writing its own variable and reading the other's; both can read zero because of store buffers, and only a full smp_mb() forbids it. On arm64, stlr followed by ldar happened to forbid it — zero in thirty million runs — but with ldapr it failed thirty thousand times, and the LKMM doesn't promise release/acquire fixes SB, so kernel code uses smp_mb(). That's exactly why set_current_state() is smp_store_mb().

꼬리 질문: "LB는?" → 각자 읽고 나서 상대 변수를 쓴다. 둘 다 1을 읽는 결과를 LKMM과 Arm 아키텍처는 허용하지만 실제 코어에서 거의 안 보인다(측정 3천만 번 0). 컨트롤 의존 + smp_mb()나 acquire/release로 막는다.

Q. How would you test memory-ordering code? Would you trust QEMU?

A. 세 겹으로 한다. 첫째 LKMM으로 논증 — 핵심 패턴을 litmus로 써서 herd7으로 돌린다. 둘째 실제 하드웨어에서 stress — 두 스레드를 다른 코어에 고정하고 슬롯마다 출발을 맞춰 수백만 번 돌리면 드문 재배치가 잡힌다. 셋째 KCSAN으로 표시 안 된 동시 접근을 찾는다. QEMU는 믿지 않는다 — 직접 해 보니 MTTCG에서는 호스트의 약한 순서가 비쳐서 relaxed 재배치가 보이긴 하지만, 하드웨어가 금지하는 stlr→ldar SB도 수천 번 깨졌고, 단일 스레드 TCG에선 아무것도 재배치되지 않았다. 에뮬레이터는 하드웨어보다 약할 수도 강할 수도 있다.

Three layers. Reason with the LKMM — write the core pattern as a litmus test and run herd7. Stress on real hardware — pin two threads to different cores, synchronize the start of every iteration, and run millions of iterations; that's how rare reorderings show up. And run KCSAN to catch unmarked concurrent accesses. I wouldn't trust QEMU: when I tried, multi-threaded TCG leaked the host's weak ordering so relaxed reorderings showed up, but it also broke a store-release/load-acquire SB case that real arm64 forbids, and single-threaded TCG reordered nothing at all. An emulator can be weaker or stronger than the hardware.

13. 요약 & 체크리스트#

메모리 순서는 컴파일러와 CPU 두 단계에서 바뀐다. 컴파일러 단계는 barrier()(명령 0개)와 READ_ONCE/WRITE_ONCE(volatile 접근 — 실측: 폴링 루프가 b .로 컴파일되는 걸 막음)로 다룬다. CPU 단계는 관찰자에 따라 세 가족을 쓴다: CPU끼리는 smp_*(arm64 dmb ish*, ldar/stlr), DMA coherent 메모리는 dma_*(dmb osh*), MMIO까지 포함하면 mb()/rmb()/wmb()(dsb, 7~8배 비쌈). MP는 쓰는 쪽과 읽는 쪽의 짝(smp_wmb+smp_rmb 또는 release+acquire)으로, SB는 smp_mb()로만 막는다 — 실제 M2 코어에서 relaxed MP가 1천만 번에 수백 번, SB가 1만 번 넘게 깨졌고, 올바른 짝에서는 0이었다. MMIO는 writel = dmb oshst + str, readl = ldr + dmb oshld + 가짜 의존이며, _relaxed는 같은 장치끼리만 순서를 준다. DMA 디스크립터는 "내용 → dma_wmb() → OWN → writel(doorbell)", 완료는 "status → dma_rmb() → 데이터", posted write는 같은 장치 readl로 flush한다. QEMU TCG는 순서 검증 도구가 아니다(stlr→ldar SB가 깨지고, 단일 스레드 모드는 아무것도 재배치하지 않는다).
