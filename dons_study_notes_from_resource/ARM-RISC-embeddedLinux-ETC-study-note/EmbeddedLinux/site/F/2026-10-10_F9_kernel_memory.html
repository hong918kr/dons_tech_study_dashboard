0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어에서 메모리는 보통 이렇게 나뉘어 있었다: 링커 스크립트로 고정된 영역, 부팅 때 한 번 잘라 두는 고정 크기 버퍼 풀(NAND 페이지 버퍼, 명령 슬롯), 그리고 가끔 쓰는 큰 연속 영역(DMA 디스크립터 링). malloc은 거의 쓰지 않았다. 런타임에 아무 크기나 잡고 풀면 언젠가 조각나서 큰 버퍼를 못 잡게 되는 걸 알기 때문이다.

Linux 커널도 똑같은 문제를 푼다. 다만 규모가 크고(수 GB, 수천 개 드라이버), 메모리 주인이 계속 바뀌고(프로세스, 페이지 캐시, 드라이버), 실패해도 시스템이 살아 있어야 한다. 그래서 층을 나눴다.

  • 맨 아래 — 페이지 프레임: 물리 RAM을 4 KiB 페이지로 자르고, 페이지마다 관리 구조체 struct page를 하나씩 둔다. 페이지 번호가 pfn(page frame number)이다.
  • buddy 할당자: 페이지를 2의 거듭제곱 묶음(order 0 = 1장, order 10 = 1024장 = 4 MiB)으로 주고받는다. 이게 커널의 "진짜" 물리 메모리 할당자다. API는 alloc_pages().
  • slab 할당자(SLUB): buddy에서 페이지를 받아 같은 크기 객체로 잘라 쓴다. 펌웨어의 고정 크기 버퍼 풀 그 자체다. kmem_cache_alloc(), 그리고 크기별 공용 풀을 쓰는 kmalloc().
  • vmalloc: buddy에서 페이지를 낱장으로 받아 커널 가상 주소 공간의 vmalloc 영역에 이어 붙여 매핑한다. 가상으로는 연속, 물리로는 흩어져 있다.
  • GFP 플래그: 모든 할당에 "이걸 얻으려고 무엇까지 해도 되나(잠들기, 디스크 I/O, 비상 예비분 사용)"를 붙인다.

그림 1 — 커널 메모리 할당자의 층. 모든 길은 결국 buddy 할당자의 페이지로 끝난다. kmalloc은 slab을 거치고(8 KiB 초과면 buddy 직행), vmalloc은 낱장 페이지를 가상 주소로 이어 붙이고, alloc_pages는 buddy를 직접 부른다. DMA 버퍼는 이 노트 범위 밖(F10, H8)이다.

이 노트는 그림 1을 아래에서 위로 올라간다: 물리 메모리 구성(§1) → 커널 가상 주소 지도(§2) → 주소 변환(§3) → buddy(§4, §5) → slab(§6) → API 비교(§7) → GFP와 메모리 압박(§8) → 디버깅(§9).

1. 커널은 물리 메모리를 어떻게 나눠 보나 — node, zone, page#

1.1 직관#

펌웨어의 메모리 맵은 보통 "SRAM 0x2000_0000 ~, DDR 0x8000_0000 ~" 같은 표 하나다. Linux는 같은 물리 메모리를 세 단계로 나눠 본다.

  • node (pg_data_t): NUMA 노드. 멀티 소켓 서버에서 "CPU에 가까운 메모리 묶음". 임베디드 SoC는 거의 항상 node 0 하나뿐이다.
  • zone (struct zone): 한 노드 안에서 "어떤 장치가 이 주소에 닿을 수 있나"로 나눈 구간. 오래된 DMA 엔진이 32비트(또는 30비트) 주소만 낼 수 있으면, 그 장치용 버퍼는 낮은 주소에서 잡아야 한다. 그래서 낮은 구간을 ZONE_DMA/ZONE_DMA32로 따로 관리한다. 나머지가 ZONE_NORMAL, 메모리 핫플러그·CMA처럼 "옮길 수 있는 페이지만" 두는 구간이 ZONE_MOVABLE이다.
  • page (struct page): 4 KiB 페이지 하나. 모든 물리 페이지에 하나씩 있다.

zone은 할당 정책의 단위다. 각 zone은 자기만의 free 목록(buddy), 워터마크(min/low/high), 통계를 가진다.

1.2 예제 1 — 부팅 로그와 /proc으로 zone 보기#

무엇을 확인하나: 512 MiB QEMU 게스트에서 zone이 어떻게 잡혔는지, 페이지가 몇 장이고 워터마크가 얼마인지.

출력에서 볼 것:

  • RAM 전부가 ZONE_DMA다. QEMU virt의 RAM은 물리 0x4000_0000부터 512 MiB라 전부 4 GiB 아래다. arm64는 ZONE_DMA의 상한을 부팅 때 정한다 — DT의 dma-ranges/ACPI IORT에서 "가장 제한이 심한 장치가 닿는 주소"를 찾고, 없으면 32비트(4 GiB)로 둔다. 그래서 여기서는 ZONE_DMA가 4 GiB까지 덮고 DMA32·Normal은 비었다. Raspberry Pi 4처럼 30비트 DMA 장치가 있는 보드라면 ZONE_DMA는 처음 1 GiB, DMA32는 4 GiB까지, 그 위가 Normal이 된다. "arm64에서 ZONE_DMA는 고정 16 MiB"(x86의 ISA DMA)라고 외우면 틀린다.
  • Total pages: 131072 = 512 MiB / 4 KiB. spanned/present가 131072, managed는 112640이다. 차이 18432 페이지(72 MiB)는 커널 이미지, memblock이 부팅 때 잡은 예약분(페이지 테이블, struct page 배열 자체 등)이라 buddy가 관리하지 않는다. Memory: 줄의 80800K reserved가 그 내역이고, 32768K cma-reserved는 CMA 영역(F10)이다 — CMA는 managed에 포함되지만 일반 커널 할당은 못 쓴다(§4.4에서 실제로 부딪친다).
  • 워터마크 min 665 / low 831 / high 997(페이지). free가 low 아래로 떨어지면 kswapd가 깨어나 회수하고, min 아래는 특별한 할당만 들어갈 수 있다(§8).
  • high: 4161 / high_min / high_max 두 쌍은 CPU별 pcp(per-CPU pageset — 작은 order 페이지를 CPU마다 캐시해 두는 목록)의 상한이다(-smp 2라 두 개).
  • Virtual kernel memory layout 줄은 없다. arm64는 이 출력을 오래전에 없앴다(6.18 소스에서 이 문자열은 arch/riscv/mm/init.c에만 남아 있다). §2에서 직접 찍는다.

1.3 함정#

  • MemTotal(450560 kB = managed 112640 × 4)은 RAM 크기(512 MiB)가 아니다. 예약분이 빠진 값이다. 보드 bring-up 때 "RAM이 덜 잡혔다"고 착각하기 쉬운 숫자다.
  • ZONE_DMA/GFP_DMA는 "DMA에 쓸 메모리"라는 뜻이 아니다. "주소 제한이 있는 장치용 낮은 메모리"라는 뜻이다. 드라이버의 DMA 버퍼는 GFP 플래그가 아니라 DMA API(dma_alloc_coherent, dma_map_single)로 만든다(H8).

2. arm64 커널 가상 주소 지도#

2.1 직관 — TTBR0과 TTBR1, 두 개의 주소 공간#

A5에서 본 유저 프로세스 주소 공간은 0x0000_xxxx_xxxx_xxxx, 즉 아래쪽이었다. arm64 MMU는 가상 주소의 bit 55를 보고 번역 테이블 베이스를 고른다: 0이면 TTBR0_EL1(프로세스마다 다름 — context switch 때 바뀜), 1이면 TTBR1_EL1(커널 전용 swapper_pg_dir, 모든 프로세스가 공유). 그래서 커널 주소는 전부 0xffff...로 시작한다. Cortex-R의 MPU 영역 설정을 "유저용 표 하나 + 커널용 표 하나"로 나누고, 커널 표는 절대 안 바꾸는 구조라고 생각하면 된다.

커널 쪽 절반은 용도별 구역으로 나뉜다.

  • vmemmap: struct page가 fffffdffc0171000에 있다. pfn 0x40000(DRAM 첫 페이지)의 struct page를 fffffdffc0000000이라 하면 0x5c40 × 64 = 0x171000으로 정확히 맞는다 — struct page는 64바이트다. 두 실행의 차이로도 확인된다: pfn 차 0x84f(2127) × 64 = 0x213c0 = 0x171000 - 0x14fc40. 4 KiB 페이지당 64 B니 RAM의 1.56%가 struct page에 쓰인다(512 MiB → 8 MiB).

2.4 함정#

  • "커널 주소는 물리 주소 + 상수"는 linear map에서만 맞다. vmalloc 버퍼, 커널 스택(VMAP_STACK), 모듈의 전역 변수, ioremap 주소에 virt_to_phys()를 쓰면 엉뚱한 물리 주소가 나온다. 이 랩 커널은 CONFIG_DEBUG_VIRTUAL이 꺼져 있어서 경고조차 없다. 커널 스택 위의 지역 배열을 DMA 버퍼로 넘기는 오래된 드라이버 코드가 VMAP_STACK 도입 후 줄줄이 깨진 이유가 이것이다.
  • 주소를 로그에 찍을 때 %p는 해시된 값을 찍는다. 디버깅용 실주소는 %px(이 노트처럼), 양산 코드에서는 %p를 쓴다.

3. struct page, pfn, 물리 주소, 가상 주소 — 네 가지 이름 사이 오가기#

3.1 직관#

같은 4 KiB 물리 페이지를 커널은 네 가지 이름으로 부른다.

  • 물리 주소 phys_addr_t: 버스에 나가는 주소. DMA 엔진, 데이터시트, DT reg가 쓰는 숫자.
  • pfn unsigned long: 물리 주소 >> 12. "몇 번째 페이지인가". 페이지 단위 장부의 인덱스.
  • struct page *: 그 페이지의 관리 구조체 포인터. 참조 카운트, 플래그, 어느 slab/페이지 캐시에 속했는지, buddy 목록 링크가 들어 있다. buddy·slab·페이지 캐시 API는 전부 이걸 주고받는다.
  • 커널 가상 주소 void *: CPU가 load/store할 때 쓰는 주소. linear map에 있으면 물리 주소와 상수 차이다.

SPARSEMEM_VMEMMAP 덕분에 struct page 배열은 가상 주소상 하나의 큰 배열(vmemmap)이라 pfn ↔ page 변환이 포인터 산술 한 번이다.

그림 3 — virt ↔ phys ↔ pfn ↔ struct page. 위 네 변환은 전부 덧셈·뺄셈·시프트라 비용이 거의 없다. 대신 linear map 주소에만 유효하다. 숫자는 예제 3의 실제 kmalloc 버퍼 값이다.

3.2 예제 3 — kmalloc / alloc_pages / vmalloc / kvmalloc 버퍼의 pfn (f9_mem)#

무엇을 확인하나: (1) 네 변환이 서로 맞물리는지, (2) kmalloc(16 KiB)와 alloc_pages(order 2)는 물리적으로 연속인지, (3) vmalloc(32 KiB)의 페이지들은 물리적으로 어디에 있는지, (4) kvmalloc이 크기에 따라 어느 쪽으로 가는지.

출력에서 볼 것:

  • 네 이름이 맞물린다: va ffff000005ea4000 → pa 0x45ea4000 → pfn 0x45ea4 → page fffffdffc017a900 → page_address = 다시 ffff000005ea4000. struct page 주소도 계산과 일치한다: fffffdffc0000000 + (0x45ea4 - 0x40000) × 64 = fffffdffc017a900.
  • kmalloc(16 KiB)의 4 페이지는 pfn 0x45ea4~0x45ea7로 물리 연속이다. 16 KiB는 8 KiB를 넘으므로 slab이 아니라 buddy에서 order-2 블록을 직접 받은 것이고(§6.4), 바로 다음 alloc_pages(order 2)가 이웃 블록 0x45ea8을 받았다.
  • vmalloc(32 KiB)의 8 페이지는 pfn이 0x46124, 0x46123, 0x4611c, 0x4603c, …로 순서도 없고 흩어져 있다. 가상 주소로만 연속이다. virt_addr_valid=0 — linear map 주소가 아니라는 뜻이고, 그래서 virt_to_phys가 아니라 vmalloc_to_pfn(페이지 테이블 walk)으로 물었다.
  • kvmalloc: 1 MiB는 kmalloc으로 성공해서 linear 주소(ffff0000...), 8 MiB는 KMALLOC_MAX_SIZE(4 MiB, E4 §6.2에서 측정)를 넘으므로 vmalloc으로 대체됐다(ffff8000...). 해제는 둘 다 kvfree.

그림 4 — 예제 3에서 잰 "버퍼 안의 n번째 페이지 → 물리 pfn". kmalloc은 직선(연속), vmalloc은 들쭉날쭉(흩어짐). DMA 엔진은 물리 주소로 움직이므로, 주황색 버퍼를 하나의 DMA 디스크립터로 넘길 수 없다. scatter-gather 목록을 만들어야 한다(H8).

3.3 예제 4 — /proc/vmallocinfo로 vmalloc 할당 보기#

무엇을 확인하나: 커널 전체의 vmalloc 영역 사용 내역에서 예제 3의 두 vmalloc 할당(32 KiB, 8 MiB)을 찾는다.

출력에서 볼 것: 크기가 요청보다 한 페이지 크다 — 32 KiB 요청이 36864(9 페이지), 8 MiB 요청이 8392704(2049 페이지). 각 vmalloc 영역 뒤에 매핑하지 않은 guard page를 하나 두어서, 버퍼를 넘쳐 쓰면 바로 page fault(Oops)가 나게 한 것이다(E4의 VMAP_STACK guard와 같은 원리). vpages는 2048개짜리 struct page * 배열 자체도 vmalloc으로 잡았다는 표시다. 시작 주소와 호출자가 해시값으로 나온 것은 kptr_restrict 정책 때문이다(이 게스트 설정 그대로 둠).

3.4 함정#

  • virt_to_page(vmalloc_ptr)는 에러 없이 엉뚱한 struct page를 돌려준다. CONFIG_DEBUG_VIRTUAL이 켜진 커널이면 경고가 나지만 양산 커널에선 조용히 메모리를 망가뜨린다. 버퍼가 어디서 왔는지 모르는 공용 함수라면 is_vmalloc_addr()로 갈라서 처리한다(kvfree가 내부에서 하는 일).
  • page_address()는 linear map에 매핑된 페이지에만 의미가 있다. 32비트 ARM의 HIGHMEM 페이지는 linear map 밖이라 kmap_local_page()가 필요했다. arm64는 HIGHMEM이 없지만, 32비트 ARM SoC(i.MX6 등) 코드를 볼 때 이 차이를 기억한다.

4. buddy 할당자 — 2의 거듭제곱으로 쪼개고 합치기#

4.1 직관#

펌웨어의 고정 크기 풀은 크기가 하나라 단편화가 없다. 하지만 커널은 4 KiB부터 4 MiB까지 다양한 크기의 물리 연속 블록을 줘야 한다. buddy 할당자의 답은 단순하다.

  • 블록 크기를 2^order 페이지로만 허용한다(order 0 = 4 KiB … order 10 = 4 MiB).
  • order마다 free 블록 목록 free_area[order]를 둔다.
  • order-n이 필요한데 그 목록이 비었으면, 더 큰 블록을 반으로 쪼개고(split) 남는 반쪽("버디")을 아래 order 목록에 넣는다.
  • 해제할 때는 버디(pfn XOR 2^order인 이웃 블록)가 free인지 본다. free면 합쳐서(merge) order+1로 올리고 다시 반복한다.

버디의 위치가 계산(XOR)으로 바로 나오니 합치기가 O(1)이고, 블록은 항상 자기 크기로 정렬돼 있다(order-10 블록은 4 MiB 정렬). Don이 NAND 블록 관리에서 썼던 "정렬된 2의 거듭제곱 단위 + 비트맵" 감각 그대로다.

그림 5 — buddy 분할과 병합. 할당은 위에서 아래로 쪼개고, 해제는 아래에서 위로 버디를 찾아 합친다.

4.2 /proc/buddyinfo 읽기#

예제 1의 Node 0, zone DMA 2 1 3 2 3 1 3 3 2 2 96은 order 0부터 10까지 free 블록 개수다. 마지막 96은 "4 MiB 블록 96개 = 384 MiB"로, 부팅 직후 메모리 대부분이 가장 큰 블록으로 뭉쳐 있다는 뜻이다. free 메모리 총량은 Σ count × 4 KiB × 2^order이다.

MAX_PAGE_ORDER(옛 이름 MAX_ORDER - 1)가 10이라 order 10이 최대다. 커널 버전마다 이 매크로 이름이 바뀌었다 — 6.4 무렵 MAX_ORDER의 의미가 "포함하는 최대 order"로 바뀌었고, 6.8에서 MAX_PAGE_ORDER로 이름이 바뀌었다. 오래된 드라이버 코드에서 MAX_ORDER - 1을 보면 같은 뜻이다.

4.3 예제 5 — order-N 블록을 잡아서 buddyinfo 바꾸기, 그리고 실패할 때까지 (f9_buddy)#

무엇을 확인하나: (1) order-9 블록 3개를 잡으면 buddyinfo가 어떻게 변하나, (2) order-10(4 MiB)을 계속 잡으면 몇 개에서 실패하고 그 경고는 어떻게 생겼나, (3) order-0을 많이 잡고 절반만 돌려주면(단편화) 어떻게 되나.

(경고 덩어리는 ... 자리에서 콜 트레이스 하단·노드 상세·hugepages 줄을 생략했다.)

출력에서 볼 것:

  • order-9 × 3: order-9 열(4)은 그대로인데 order-10이 98 → 96으로 두 개 줄었다. 기존 order-9 free 블록이 있는데도 order-10을 쪼갰다 — 다음 예제 6에서 이유(migratetype)를 본다.
  • order-10 고갈: 200개를 요청해서 91개(364 MiB)에서 실패했다. 실패 순간 커널이 warn_alloc()으로 경고를 찍었다. 아래 세 줄이 읽는 법이다.
  • 경고 첫 줄 page allocation failure: order:10, mode:0xcc0(GFP_KERNEL) — 누가(insmod), 몇 order를, 어떤 GFP로 요청했나. 0xcc0 = __GFP_IO(0x40) + __GFP_FS(0x80) + __GFP_DIRECT_RECLAIM(0x400) + __GFP_KSWAPD_RECLAIM(0x800) = GFP_KERNEL(6.18의 비트 배치, §8 표). 커널이 괄호 안에 이름으로 풀어 준다.
  • 콜 트레이스의 f9_buddy_init+0x6c — 실패한 호출 지점. Mem-Info 아래는 실패 순간의 메모리 상태 스냅숏이다.
  • Node 0 DMA: 41*4kB (UME) … 7*4096kB (C) = 51772kB — order별 free 블록 수와 그 블록들의 migratetype 문자(U=Unmovable, M=Movable, E=Reclaimable, C=CMA).
  • 결정적인 단서: 실패한 순간에도 4 MiB free 블록이 7개 있었다 — 전부 (C), 즉 CMA 영역이다. free_cma:31744kB. GFP_KERNEL로 잡는 커널 메모리는 "옮길 수 없는(unmovable)" 페이지라 CMA 블록을 쓸 수 없다. CMA는 나중에 카메라 드라이버 같은 곳이 큰 연속 버퍼를 달라고 할 때 비워 줄 수 있어야 하므로 옮길 수 있는 페이지(유저 페이지, 페이지 캐시)만 빌려준다(F10).
  • frag: order-0 2만 장(78 MiB)을 잡고 홀수 번째 1만 장을 돌려줬다. MemFree는 다시 380 MiB로 넉넉한데 order-0 free 블록이 9187개로 폭증했고 order-10은 79개다. 돌려준 페이지들의 버디(짝수 번째)가 아직 사용 중이라 합칠 수 없기 때문이다. 이 상태에서 order-1 이상 요청은 이 9187장을 하나도 쓸 수 없다. 이것이 외부 단편화(external fragmentation)다.

그림 6 — 예제 5의 /proc/buddyinfo를 order별 free 메모리(MiB, 로그 축)로 환산했다. 파랑(부팅 직후)은 거의 전부 order-10에 몰려 있고, 주황(order-10 고갈 후)은 order-10이 CMA 7개(28 MiB)만 남았고, 초록(단편화 후)은 order-0에 36 MiB가 쌓였는데 큰 블록은 줄어든 채 돌아오지 않는다.

4.4 예제 6 — migratetype: 왜 order-9이 아니라 order-10을 쪼갰나#

무엇을 확인하나: free 블록이 migratetype별로 따로 관리되는지, 그리고 GFP_KERNEL(Unmovable) 요청이 자기 타입에 블록이 없을 때 무엇을 하는지.

출력에서 볼 것:

  • buddy의 free 목록은 실제로 free_area[order].free_list[migratetype] — order × migratetype 2차원이다. Unmovable의 order-9 열은 0이다. order-9 free 블록 4개는 Movable(2)·Reclaimable(1)·CMA(1) 소속이었다.
  • 그래서 Unmovable 요청은 fallback으로 다른 타입의 블록을 "훔친다"(steal). 여기서는 Movable의 order-10이 89 → 87로 두 개 줄었다. 큰 블록을 통째로 가져와 pageblock(512 페이지 = order 9) 단위로 Unmovable로 바꿔 쓰는 것이 단편화를 덜 만든다는 정책이다.
  • Number of blocks type: 512 페이지(2 MiB) pageblock 256개 중 Unmovable 16, Movable 218, CMA 16. 이 분리가 있어서 compaction(옮길 수 있는 페이지를 한쪽으로 몰아 큰 빈 블록을 만드는 일)이 Movable 블록 안에서 효과를 낼 수 있다.
  • 작은 order 숫자(order-0 2 → 24 등)는 같은 시간에 다른 커널 활동이 쪼갠 결과라 매 실행 다르다.

4.5 예제 7 — 단편화는 compaction으로 고쳐지나?#

무엇을 확인하나: 예제 5의 단편화 상태에서 수동 compaction(/proc/sys/vm/compact_memory)을 돌리면 큰 블록이 돌아오는지, 그리고 모듈이 전부 해제하면 어떻게 되는지.

출력에서 볼 것:

  • compaction은 15만 페이지를 훑었지만(compact_migrate_scanned 155648) order-0 9929장은 그대로다. 구멍 사이에 박힌 짝수 번째 페이지가 커널이 alloc_pages(GFP_KERNEL)로 잡은 unmovable 페이지라서 옮길 수 없다. compaction은 유저 페이지·페이지 캐시처럼 페이지 테이블만 고치면 되는 페이지만 옮긴다. 커널 포인터가 직접 가리키는 메모리는 주소가 바뀌면 안 되니까.
  • rmmod로 전부 돌려주면 order-10이 90개로 회복되지만 order-0이 3330장 남는다. 해제된 페이지 일부가 CPU별 pcp 목록에 머물러 있어서 그 버디들이 아직 buddy에 안 돌아왔기 때문이다. pcp는 order-0 할당을 빠르게 하려고 CPU마다 페이지를 쌓아 두는 캐시이고, 나중에 일괄 반납된다.
  • 교훈: 오래 도는 장비에서 큰 물리 연속 버퍼가 필요하면 부팅 직후(probe()) 미리 잡아 두거나 CMA/reserved-memory를 쓴다(F10). "메모리는 충분한데 order-4 할당이 실패한다"는 현장 장애의 정체가 이것이다.

6. slab 할당자 (SLUB) — 고정 크기 객체 풀#

6.1 직관 — SSD 펌웨어의 버퍼 풀#

NVMe 명령 컨텍스트 구조체를 매번 범용 힙에서 잡지 않고, 부팅 때 "명령 슬롯 256개" 배열을 만들어 free 목록으로 돌려 쓰던 것을 떠올리면 된다. 크기가 같으니 단편화가 없고, 할당·해제가 목록 머리에서 꺼내고 넣는 O(1)이다.

slab 할당자는 이것을 커널 전체에 일반화했다.

  • 캐시 struct kmem_cache: "크기 X짜리 객체 풀" 하나. task_struct, inode, dentry, skbuff_head_cache처럼 커널의 주요 구조체마다 전용 캐시가 있다.
  • slab: 캐시가 buddy에서 받아 온 페이지 묶음(order 0 이상). 그 안을 객체 크기로 잘라 쓴다. free 객체는 자기 몸 안에 "다음 free 객체 포인터"를 품는다(freelist) — Don이 펌웨어에서 쓰던 intrusive free list 그대로다.
  • per-CPU slab: CPU마다 "지금 꺼내 쓰는 slab"을 하나씩 들고 있어서, 대부분의 할당·해제가 락 없이(인터럽트·선점만 막고 cmpxchg로) 끝난다.
  • partial 목록: 일부만 찬 slab들의 목록(노드별). per-CPU slab이 다 차면 여기서 하나 가져온다. 여기도 없으면 buddy에서 새 slab을 받는다(new_slab → alloc_pages).
  • kmalloc: 크기별 공용 캐시 묶음(kmalloc-8, -16, -32, -64, -96, -128, -192, -256, -512, -1k, -2k, -4k, -8k)에서 요청 크기를 덮는 가장 작은 캐시를 골라 꺼낸다. 8 KiB를 넘으면 slab을 거치지 않고 buddy로 간다.

Linux에는 한때 slab 구현이 셋(SLAB, SLUB, SLOB) 있었지만 SLOB은 6.4, SLAB은 6.8에서 제거됐다. 지금은 SLUB 하나다. 그래서 API 이름은 여전히 "slab"(kmem_cache_*, /proc/slabinfo, 부팅 인자 slab_debug=)이고 구현은 mm/slub.c다.

그림 7 — SLUB 구조. 왼쪽은 예제 8의 전용 캐시, 오른쪽은 예제 9에서 측정한 kmalloc 크기 등급이다. 대부분의 할당은 CPU별 freelist에서 락 없이 끝나고, 거기가 비었을 때만 partial 목록(락)과 buddy(더 비쌈)로 내려간다.

6.2 예제 8 — 센서 샘플용 전용 캐시 (f9_cache)#

무엇을 확인하나: IMU 샘플 구조체용 kmem_cache를 만들고 1000개를 할당했을 때 /proc/slabinfo·/sys/kernel/slab에 어떻게 보이는지. 그리고 slab merge(크기·플래그가 같은 캐시를 하나로 합치는 기본 동작) 때문에 이름이 사라지는 현상.

출력에서 볼 것:

  • 구조체는 8 + 12 + 12 + 2 + 1 + 1 = 36 B인데 sizeof=40 — u64 정렬 때문에 끝에 4 B 패딩이 붙었다. 객체 주소가 …5000, …5028, …5050으로 정확히 0x28(40) 간격이다. 페이지 정렬된 slab의 첫 객체부터 빈틈없이 깔린다.
  • objs_per_slab=102, order=0: 4 KiB 페이지 하나에 40 B × 102 = 4080 B, 16 B만 남는다. 1000개를 잡으니 slab 10장, 객체 1020개(마지막 slab에 20개 여유).
  • nomerge=0(기본): /proc/slabinfo에 f9_sample 줄이 없다. sysfs에서는 f9_sample -> :0000040 심볼릭 링크다. 크기 40, 같은 플래그인 기존 캐시와 합쳐져서(aliases=2) 이름 없는 공용 캐시 :0000040의 별칭이 된 것이다. 메모리는 아끼지만 "내 드라이버가 객체를 몇 개 쓰고 있나"를 이름으로 볼 수 없다.
  • SLAB_NO_MERGE(6.5부터): 독립 캐시가 되어 /proc/slabinfo에 f9_sample 1020 1020 40 102 1(활성 객체, 전체 객체, 객체 크기, slab당 객체, slab당 페이지)로 보인다. 부팅 인자 slab_nomerge로 전체 merge를 끌 수도 있고, slab_debug로 디버그 플래그가 붙은 캐시도 merge되지 않는다.
  • 전용 캐시의 이점은 메모리만이 아니다: 객체 수를 이름으로 추적하고(누수 확인), 생성자(ctor)로 초기 상태를 보장하고, SLAB_HWCACHE_ALIGN으로 캐시 라인 정렬을 받고, SLAB_TYPESAFE_BY_RCU 같은 수명 정책을 줄 수 있다.

6.3 예제 9 — kmalloc 크기 등급과 ksize, slabtop처럼 보기 (f9_ksize)#

무엇을 확인하나: kmalloc(n)이 실제로 몇 바이트를 주는지(ksize()), 그 경계가 어디인지, 그리고 시스템 전체에서 어느 캐시가 메모리를 가장 많이 쓰는지(BusyBox에는 slabtop이 없어서 awk로 흉내).

출력에서 볼 것:

  • 등급은 2의 거듭제곱이 기본이고 96과 192가 끼어 있다(65~96 B, 129~192 B 요청이 많아서 낭비를 줄이려고). 최소 등급은 kmalloc-8 — arm64는 6.5부터 ARCH_KMALLOC_MINALIGN이 8이다. 그 전에는 비코히어런트 DMA 안전을 위해 캐시 라인(128 B) 정렬이 최소였고 kmalloc(1)이 128 B를 먹었다. 6.5 이후 작은 kmalloc 버퍼를 DMA에 쓰면 필요할 때 swiotlb bounce buffer로 처리한다 — 그래서 작은 kmalloc 버퍼를 DMA에 직접 쓰는 설계는 피한다(H8).
  • 최악의 낭비는 2의 거듭제곱 + 1 바이트(257 → 512, 4097 → 8192)에서 ~50%다. 구조체 크기가 등급 경계를 살짝 넘으면 메모리가 두 배로 든다. 센서 샘플(40 B)을 kmalloc으로 잡으면 64 B 등급에서 37%가 버려진다(그림 8). 전용 캐시(예제 8)는 40 B를 그대로 쓴다: 페이지당 102개 vs kmalloc-64의 64개.
  • 8193 이상은 (page allocator) — ksize가 16384, 32768, 131072로 order 단위(2^order 페이지)로 반올림된다. kmalloc(100000)은 order-5(128 KiB) 블록 하나를 통째로 받는다.
  • kmalloc-8k는 slab당 8 페이지(order 3)를 쓴다. 큰 객체 캐시는 slab 하나에 객체 여러 개를 담으려고 높은 order 페이지를 받는다 — 그래서 단편화가 심하면 slab 확장 자체가 실패할 수 있다(그때는 더 낮은 order로 재시도한다).
  • slabtop 흉내: 이 작은 게스트에서는 sysfs/kernfs 노드(kernfs_node_cache 3 MiB)가 1위다. 실제 장비에서 메모리 누수를 찾을 때 이 목록을 시간 간격을 두고 두 번 찍어 계속 커지는 캐시를 찾는다. kmalloc-*가 커지면 누가 그 크기로 잡는지는 §9의 도구로 좁힌다.
  • :0000040의 별칭은 ext4_system_zone과 f9_sample이다 — 예제 8의 merge 상대가 ext4 내부 캐시였다.

그림 8 — 예제 9에서 측정한 kmalloc 낭비율. 등급 경계 바로 위(9, 17, 33, 257, 513, 1025, …)에서 낭비가 50%에 가깝다. 파랑은 slab 등급, 주황은 8 KiB를 넘어 페이지 할당자로 간 요청이다.

6.4 함정#

  • /proc/slabinfo에서 내 캐시가 안 보인다 → merge됐다. sysfs 심볼릭 링크로 확인하거나 SLAB_NO_MERGE/slab_nomerge.
  • 모듈 언로드 때 kmem_cache_destroy 전에 객체를 전부 돌려주지 않으면 "Objects remaining … on __kmem_cache_shutdown()" 경고가 뜬다(이 노트에서 실행하지 않음 — 메시지 문구는 mm/slub.c 기준). kmem_cache_free에 다른 캐시의 객체를 넘기는 실수도 디버그 옵션에서 잡힌다.
  • ksize()로 얻은 "여분"을 쓰는 건 금지에 가깝다. 6.x에서는 ksize가 KASAN 등과 충돌해서 "할당 크기를 키우려면 kmalloc_size_roundup()으로 미리 반올림해서 요청하라"는 방향으로 바뀌었다. 이 노트는 관찰용으로만 썼다.

8. GFP 플래그와 메모리 압박 — "이 할당을 위해 무엇까지 해도 되나"#

8.1 직관#

할당자가 free 페이지가 부족할 때 할 수 있는 일은 여러 가지다: kswapd(백그라운드 회수 스레드)를 깨우기, 직접 회수(direct reclaim — 페이지 캐시를 버리거나 dirty 페이지를 디스크에 쓰고 버리기), compaction(페이지를 옮겨 큰 블록 만들기), 비상 예비분 쓰기, OOM killer 부르기. 이 중 일부는 잠들어야 하고(디스크 I/O를 기다림), 일부는 재귀 위험이 있다(파일시스템이 메모리를 할당하다가 회수가 같은 파일시스템을 다시 부르면 데드락). GFP 플래그는 호출자가 이 중 무엇을 허락하는지 비트로 알리는 것이다.

8.3 예제 10 — 같은 할당, 다른 GFP: NOWAIT vs ATOMIC vs KERNEL (f9_gfp)#

무엇을 확인하나: order-0 페이지를 플래그만 바꿔 실패할 때까지(또는 상한까지) 잡으면 몇 장을 받는지. (A) 회수할 것이 없는 상태와 (B) 깨끗한 버퍼 캐시 300 MiB가 있는 상태에서 비교한다. B 상태는 300 MiB 가상 디스크(DISK=/var/tmp/F9/disk.img, truncate -s 300M)를 dd로 읽어 만든다.

그림 10 — 예제 10 결과. 회수할 캐시가 있을 때(B) 잠들 수 없는 두 플래그는 "지금 free인 것"만 가져가고 멈춘다. GFP_KERNEL은 직접 회수로 캐시를 밀어내고 상한(90000 페이지 = 351 MiB)을 다 채웠다.

출력에서 볼 것:

  • A (회수할 것 없음): NOWAIT 93123장, ATOMIC 95192장 — ATOMIC이 2069장(8 MiB) 더 받았다. 남은 free를 보면 NOWAIT은 9132, ATOMIC은 8182 페이지에서 멈췄다. 이 중 7936장은 CMA(unmovable 요청이 못 쓰는 영역, 예제 5)이므로 non-CMA 기준으로는 NOWAIT ≈ 1196, ATOMIC ≈ 246이다. 246은 그림 9의 계산값 250과 맞는다 — GFP_ATOMIC은 일반 요청이 못 들어가는 min 아래 예비분을 실제로 파먹는다. NOWAIT이 min(665)보다 위인 ≈1196에서 멈춘 정확한 조건은 이 실험으로 확정하지 않았다(pcp 목록에 남은 페이지와 검사 시점 차이로 추정).
  • B (버퍼 캐시 300 MiB): 같은 NOWAIT/ATOMIC이 77 MiB, 74 MiB밖에 못 받았다. free가 90 MiB뿐이었고, 둘 다 __GFP_DIRECT_RECLAIM이 없어서 캐시를 직접 버리지 못한다. 할 수 있는 건 kswapd를 깨우는 것뿐인데 kswapd가 회수하는 속도보다 루프가 빨랐다.
  • GFP_KERNEL은 같은 상황에서 351 MiB를 다 받았다. Buffers가 307200 → 25688 kB로 줄었고, pgsteal_direct 24073(할당하던 스레드가 직접 회수한 페이지), pgsteal_kswapd 46583(kswapd가 회수한 페이지)이 그 증거다. 대신 시간이 들었다(8.7초, TCG 기준). 잠들어도 되는 문맥이라서 가능한 일이다.
  • compact_stall 0 — order-0이라 compaction이 필요 없었다. compaction은 order > 0 요청에서 회수만으로 연속 블록이 안 생길 때 끼어든다.
  • 여기서 ATOMIC으로 바닥까지 판 것은 실험이라서 괜찮았다. 실제 장비에서 IRQ 경로가 예비분을 다 쓰면, 진짜로 예비분이 필요한 곳(네트워크 RX, 블록 I/O 완료 처리)이 실패한다.

8.4 IRQ 핸들러에서는 왜 GFP_ATOMIC인가#

hardirq·softirq·spinlock 보유 구간은 잠들 수 없다(F2). GFP_KERNEL은 __GFP_DIRECT_RECLAIM 때문에 회수 중 I/O를 기다리며 schedule()할 수 있으므로, atomic 문맥에서 쓰면 "BUG: sleeping function called from invalid context"(디버그 커널의 DEBUG_ATOMIC_SLEEP, E4 §5에서 실제로 재현) 또는 데드락이 된다. 그래서:

  • atomic 문맥에서 꼭 할당해야 하면 GFP_ATOMIC(실패 시 손해가 큰 경우 — 예비분 사용) 또는 GFP_NOWAIT(실패해도 되는 경우).
  • 그리고 반드시 실패를 처리한다. 위 실험처럼 GFP_ATOMIC은 B 상태에서 메모리가 300 MiB "있는데도" 실패한다.
  • 가장 좋은 답은 IRQ 핸들러에서 할당하지 않는 것이다: probe()에서 링버퍼를 미리 잡거나, mempool(최소 개수를 예약해 둔 풀)을 쓰거나, 할당이 필요한 일을 threaded IRQ나 workqueue(F6, F7)로 넘겨 GFP_KERNEL로 처리한다.

8.5 GFP_NOIO / GFP_NOFS와 범위 API#

블록 드라이버가 쓰기 요청을 처리하다 GFP_KERNEL로 할당하면, 할당자가 메모리를 만들려고 dirty 페이지를 디스크에 쓰려 하고 → 그 쓰기가 같은 블록 드라이버로 들어와 → 자기 자신을 기다리는 데드락이 될 수 있다. 그래서 I/O 경로는 GFP_NOIO, 파일시스템 내부는 GFP_NOFS를 쓴다. 요즘 권장은 호출 경로 깊숙이까지 플래그를 전달하는 대신 구간을 표시하는 것이다:

8.6 할당 실패를 다루는 법#

  • 반환값은 항상 검사하고, goto 되감기(또는 devm)로 앞서 잡은 것을 푼다. 실패 메시지(pr_err("out of memory"))는 붙이지 않는다 — 할당자가 이미 예제 5 같은 경고를 찍고, checkpatch도 이걸 지적한다.
  • 실패해도 되는 큰 할당(성능용 캐시 등)은 __GFP_NOWARN | __GFP_NORETRY로 가볍게 시도하고 작은 크기로 물러선다.
  • 반드시 필요한 큰 할당은 __GFP_RETRY_MAYFAIL(열심히 하되 OOM killer는 안 부름) 또는 kvmalloc.
  • __GFP_NOFAIL은 "실패를 처리할 방법이 정말 없을 때"만. 무한 재시도라 데드락·지연의 원인이 된다.
  • 반드시 진행해야 하는 경로(블록 I/O 완료, 네트워크 스토리지)는 mempool_create()로 최소 개수를 예약해 둔다.

11.1 센서 키트 — 1 kHz IMU 샘플을 어디에 담나#

IMU 드라이버가 인터럽트마다 샘플 노드를 kmalloc(sizeof(struct sample), GFP_ATOMIC)로 잡아 리스트에 붙이는 설계를 흔히 본다. 문제가 셋이다: (1) IRQ 경로 할당은 실패할 수 있고(예제 10의 B 상태), 실패하면 샘플이 빠진다, (2) 40 B 구조체가 kmalloc-64에서 나와 37%를 버린다(예제 9), (3) 할당·해제가 초당 수천 번이라 slab 경로 비용이 누적된다.

더 나은 순서: probe()에서 링버퍼를 한 번에 잡는다(devm_kcalloc, 또는 kfifo). 샘플 객체를 동적으로 꼭 다뤄야 하면 전용 kmem_cache(예제 8) + mempool로 최소 개수를 보장한다. 할당은 IRQ가 아니라 threaded IRQ/workqueue에서 GFP_KERNEL로.

11.2 카메라 · LiDAR 버퍼 — "4 MiB면 kmalloc으로 되지 않나?"#

1080p NV12 프레임은 약 3 MiB다. kmalloc 상한(4 MiB) 안이지만, 예제 5처럼 장비가 며칠 돌고 나면 order-10 블록이 남아 있으리라는 보장이 없다. 게다가 일반 커널 할당은 CMA를 못 쓴다. vmalloc은 물리적으로 흩어져 있어 IOMMU 없는 ISP/DMA 엔진이 못 쓴다. 정답은 DMA API(dma_alloc_coherent)가 CMA 영역에서 잡게 하는 것 — V4L2에서는 videobuf2의 vb2_dma_contig가 이걸 해 준다(F10, Q 모듈). 버퍼 개수는 스트리밍 시작 전에 정하고 한 번에 할당한다.

13. 면접에서 이렇게 말한다#

Q. What is the difference between kmalloc and vmalloc? When would you use each?

A. kmalloc은 slab(작으면)이나 buddy(8 KiB 초과)에서 물리적으로 연속인 메모리를 linear map 주소로 준다. 빠르고(수백 ns), atomic 문맥에서도 GFP_ATOMIC으로 쓸 수 있지만, 크기 상한(4 MiB)이 있고 큰 크기는 단편화 때문에 실패한다. vmalloc은 페이지를 낱장으로 모아 vmalloc 영역에 이어 붙이므로 가상으로만 연속이다. 큰 크기도 잘 되지만 느리고(페이지 테이블 작업 + TLB), 잠들 수 있고, DMA에 그대로 못 쓴다. 기본은 kmalloc, CPU만 쓰는 큰 테이블은 kvmalloc, 장치 버퍼는 둘 다 아니고 DMA API다.

kmalloc returns physically contiguous memory from the slab caches, or straight from the buddy allocator above 8 KiB, mapped in the linear map. It's fast, usable in atomic context with GFP_ATOMIC, but capped at a few MiB and large requests can fail due to fragmentation. vmalloc stitches together individual pages in the vmalloc area, so it's only virtually contiguous: good for large CPU-only buffers, but slower, may sleep, and not directly usable for DMA. My default is kzalloc, kvmalloc for big tables, and the DMA API for anything a device touches.

꼬리 질문: "vmalloc 주소에 virt_to_phys를 쓰면?" → linear map 주소가 아니라서 틀린 값. vmalloc_to_page로 페이지마다 구해야 한다(예제 3).

Q. Which GFP flag do you use in an interrupt handler, and why?

A. GFP_ATOMIC. IRQ 문맥은 잠들 수 없는데 GFP_KERNEL은 direct reclaim 중 I/O를 기다리며 잠들 수 있다. GFP_ATOMIC은 잠들지 않고 대신 min 워터마크 아래 예비분 일부를 쓸 수 있다. 그래도 실패할 수 있으므로 반드시 처리해야 하고, 실제로는 IRQ에서 할당하지 않도록 미리 잡거나 mempool·workqueue를 쓰는 게 더 좋은 답이다. 제 실험에서는 버퍼 캐시가 300 MiB 있어도 GFP_ATOMIC은 free 90 MiB까지만 받고 실패했고, GFP_KERNEL은 캐시를 회수해서 351 MiB를 받았다.

GFP_ATOMIC, because interrupt context cannot sleep, and GFP_KERNEL may enter direct reclaim and block. GFP_ATOMIC never sleeps and is allowed to dip into part of the reserve below the min watermark. It can still fail, so the error path is mandatory. Better still is not allocating in the IRQ at all: preallocate in probe, use a mempool, or defer to a threaded IRQ or workqueue where GFP_KERNEL is fine.

꼬리 질문: "GFP_NOWAIT과의 차이는?" → 둘 다 안 잠들지만 NOWAIT은 예비분을 안 쓰고(실패해도 되는 할당용), 6.18부터는 NOWARN도 기본 포함.

Q. How does the buddy allocator work, and what is external fragmentation?

A. 물리 페이지를 2^order 블록(order 0~10)으로 관리하고, order마다 free 목록이 있다. 요청 order가 비면 큰 블록을 반씩 쪼개고 남는 반쪽을 아래 목록에 넣는다. 해제할 때 버디(pfn XOR 2^order)가 free면 합친다. 외부 단편화는 free 메모리 총량은 충분한데 작은 블록으로 흩어져 큰 연속 블록이 없는 상태다 — 예제에서 380 MiB가 free인데 order-0 블록이 9천 개 넘게 쌓였다. 커널은 migratetype 분리와 compaction으로 완화하지만, 커널이 잡은 unmovable 페이지는 옮길 수 없다.

It manages physical memory in power-of-two blocks, order 0 to 10 here, with a free list per order and migrate type. A request splits a larger block in halves, putting the unused buddy on the lower list; on free, if the buddy at pfn XOR 2^order is also free, they merge upward. External fragmentation is when plenty of memory is free but only in small blocks, so a high-order request fails. Migrate types and compaction help, but unmovable kernel pages can't be moved, so for big contiguous buffers I preallocate early or use CMA.

Q. Why does the kernel have a slab allocator, and when would you create your own kmem_cache?

A. 커널은 같은 크기 객체(inode, task_struct, skb)를 엄청나게 자주 만들고 버린다. slab은 페이지를 객체 크기로 미리 잘라 두고 CPU별 free 목록에서 락 없이 꺼내 주므로 빠르고 단편화가 없다. 고빈도·고정 크기 객체가 있으면 전용 캐시를 만든다: 크기 등급 반올림 낭비가 없고(40 B 객체가 kmalloc-64에서 37% 낭비), /proc/slabinfo에 이름으로 보여서 누수를 추적할 수 있고, ctor·정렬 옵션을 줄 수 있다. 단, 기본으로 merge되므로 이름으로 보려면 SLAB_NO_MERGE.

Because the kernel allocates and frees the same fixed-size objects constantly. Slab pre-carves pages into objects and serves them from per-CPU freelists without locks, so it's fast and doesn't fragment. I create a dedicated cache for high-frequency fixed-size objects: no size-class rounding waste, it shows up by name in slabinfo for leak tracking, and I get constructor and alignment options. Note caches get merged by default, so I'd use SLAB_NO_MERGE if I want to observe it.

Q. kmalloc failed but /proc/meminfo shows plenty of free memory. What's going on?

A. 세 가지를 먼저 본다. (1) 크기: KMALLOC_MAX_SIZE 초과는 무조건 실패. (2) 단편화: 경고의 order와 Node 0 DMA: … 줄에서 해당 order 이상 블록이 있는지. (3) 타입: free가 CMA 블록뿐이면 unmovable 커널 할당은 못 쓴다 — 실제로 order-10 할당이 4 MiB CMA 블록 7개를 두고 실패했다. 그리고 GFP: ATOMIC이면 회수를 못 해서 캐시가 많아도 실패한다.

I check the size first — anything above KMALLOC_MAX_SIZE always fails. Then the warning's order and the per-order free list line: plenty of order-0 pages but none at the requested order means fragmentation. Then the migrate type: if the only free high-order blocks are CMA, unmovable kernel allocations can't use them — I reproduced exactly that. And the GFP flags: an atomic allocation can't reclaim page cache, so it fails even when MemAvailable looks large.

Q. Can you DMA into a buffer on the kernel stack or from vmalloc?

A. 안 된다. arm64는 VMAP_STACK이라 스택도 vmalloc 영역에 있고, 둘 다 물리 연속이 아니며 linear map 밖이라 virt_to_phys/dma_map_single이 틀린 주소를 만든다. DMA 버퍼는 dma_alloc_coherent나 kmalloc 버퍼를 dma_map_single로 매핑해서 쓴다. vmalloc 버퍼를 꼭 써야 하면 페이지마다 SG 목록을 만든다.

No. With VMAP_STACK the stack lives in the vmalloc area, and vmalloc memory is neither physically contiguous nor in the linear map, so virt_to_phys or dma_map_single would produce a wrong address. Use dma_alloc_coherent, or a kmalloc buffer mapped with the streaming DMA API; for a vmalloc buffer you'd have to build a scatter-gather list page by page.

Q. When do you use GFP_NOIO or GFP_NOFS?

A. 할당이 메모리 회수를 부를 때 그 회수가 지금 내가 처리 중인 I/O나 파일시스템으로 다시 들어오면 데드락이 될 수 있는 경로다. 블록 드라이버의 요청 처리·스왑 경로는 NOIO, 파일시스템 내부는 NOFS. 요즘은 플래그를 깊이 전달하는 대신 memalloc_noio_save()/memalloc_nofs_save()로 구간을 표시한다.

When reclaim triggered by my allocation could recurse into the I/O or filesystem path I'm currently servicing and deadlock — block driver request handling or swap paths use NOIO, filesystem internals use NOFS. Modern code prefers marking the region with memalloc_noio_save or memalloc_nofs_save instead of threading flags through every call.

Q. How would you debug memory corruption or a leak in your driver?

A. 손상이면 slab_debug=FZPU(캐시 한정 가능)로 부팅해서 redzone·poison 리포트를 받는다 — 덮어쓴 바이트 위치, 할당·해제 스택이 나온다. 개발 커널이면 KASAN이 쓰는 순간을 잡는다. 누수면 /proc/slabinfo·SUnreclaim 추세로 캐시를 좁히고, 페이지 단위면 page_owner로 할당 스택을 본다. kmemleak도 있다.

For corruption I boot with slab_debug=FZPU, optionally limited to one cache: red zones and poisoning report the exact overwritten bytes plus alloc and free stacks. On a dev kernel KASAN catches the bad access at the instruction. For leaks I trend slabinfo and SUnreclaim to find the growing cache, use page_owner for page-level leaks, and kmemleak where it's enabled.

16. 요약 & 체크리스트#

커널 메모리는 층으로 되어 있다. 물리 RAM은 node → zone → 4 KiB 페이지로 나뉘고, 페이지마다 64 B struct page가 vmemmap 배열에 있다. arm64 커널 주소 공간에서 linear map만 물리와 고정 오프셋 관계이고(__pa/__va/virt_to_page는 여기서만 유효), vmalloc·스택·모듈·ioremap은 페이지 테이블로 매핑된다. 물리 페이지를 실제로 나눠 주는 것은 buddy 할당자로, 2^order 블록을 쪼개고 합치며, migratetype과 compaction으로 단편화를 줄이지만 커널이 잡은 unmovable 페이지는 옮길 수 없어 오래 돈 장비에서 큰 연속 할당이 실패한다. SLUB는 buddy 페이지를 고정 크기 객체로 잘라 CPU별 freelist에서 빠르게 내주며, kmalloc은 8 B~8 KiB 등급 캐시를 쓰고 그보다 크면 buddy로 간다. vmalloc은 가상으로만 연속이라 크게 잡을 수 있지만 느리고 DMA에 못 쓴다. 모든 할당은 GFP로 "잠들어도 되나, 예비분을 써도 되나"를 밝히며, process context는 GFP_KERNEL(회수까지 해서 성공시킴), atomic 문맥은 GFP_ATOMIC(예비분까지 쓰지만 회수 못 함)이다. 버그는 slab_debug(redzone·poison·추적)와 page_owner로 잡는다.
