0. 큰 그림 — 이게 왜 필요한가#

Cortex-M에서 인터럽트는 단순했다. 핀이 올라가면 NVIC가 벡터 테이블에서 EXTI9_5_IRQHandler 주소를 꺼내 바로 점프한다. ISR이 플래그를 지우고, 링버퍼에 넣고, RTOS 세마포어를 give 하면 끝이다. 번호 하나(IRQn), 함수 하나, 우선순위 하나.

Linux SoC에서는 같은 일이 세 층으로 나뉜다.

  • 하드웨어 층: GIC(Generic Interrupt Controller)가 수백 개의 입력선을 받아 우선순위·대상 CPU를 정하고 CPU에 IRQ 예외를 건다. NVIC + 외부 인터럽트 라우터를 합친 물건이다.
  • 커널 공통 층 (genirq): 예외 벡터는 딱 하나(el1h_64_irq)다. 거기서 GIC 드라이버가 "몇 번이냐"를 읽고, 그 번호를 irq_domain으로 Linux IRQ 번호로 바꾸고, irq_desc라는 디스크립터의 flow handler를 부른다. 벡터 테이블에 드라이버 함수가 직접 들어가는 일은 없다.
  • 드라이버 층: 드라이버는 request_irq()로 "이 번호가 오면 이 함수를 불러 달라"고 등록만 한다. 무거운 일은 threaded handler(커널 스레드)로 보낸다 — RTOS에서 "ISR은 세마포어만 give하고 실제 일은 태스크에서"와 같은 구조를 커널이 표준으로 제공하는 것이다.

이 노트는 QEMU virt(GICv2, CPU 4개) 위에서 가짜 장치 하나(f6-irq, GIC SPI 80)를 DT에 붙이고, 드라이버가 GIC의 pending 비트를 직접 세워 인터럽트를 만든다 (D4에서 쓴 irq_set_irqchip_state(..., IRQCHIP_STATE_PENDING, true) 기법). 그 위에서 hard/threaded handler, ftrace, 지연 측정, affinity, 인터럽트 폭풍과 "nobody cared", disable_irq deadlock, irqsoff tracer를 전부 실제로 돌려 본다.

주의 (H6에서 발견): QEMU virt의 GICv2m(MSI 프레임)은 SPI 80–143을 MSI용으로 예약한다. 이 노트의 SPI 80은 그 범위 안이라, PCI 장치가 MSI를 많이 쓰는 구성에서는 MSI 벡터와 겹칠 수 있다. 이 노트의 실습은 MSI를 거의 쓰지 않아 충돌이 없었을 뿐이다. 직접 따라 할 때는 SPI 120처럼 v2m 범위 밖 또는 /sys/kernel/debug/irq/domains에서 v2m 범위를 확인한 뒤 번호를 고르자 (H6 노트 참고).

1. 하드웨어 경로 — GIC와 arm64 예외#

1.1 GIC 인터럽트 종류와 INTID#

GIC는 인터럽트를 번호 대역으로 나눈다. 이 번호(INTID)가 GIC 드라이버 irq_domain의 hwirq가 된다.

1.2 GIC 한 번의 처리 — IAR 읽기와 EOI 쓰기#

  • Distributor (GICD): 모든 SPI의 enable/pending/우선순위/트리거 타입/대상 CPU(GICD_ITARGETSR, v3는 GICD_IROUTER)를 가진다. "pending 비트 세우기"(GICD_ISPENDR)를 소프트웨어가 할 수도 있다 — 이 노트의 인터럽트 생성 방법이다.
  • CPU interface (GICC, v2) / ICC 시스템 레지스터 (v3): CPU별 창구. 가장 높은 우선순위의 pending을 CPU에 IRQ 신호로 올린다. CPU는 IAR(Interrupt Acknowledge Register)을 읽어 INTID를 얻고(이때 pending → active), 처리가 끝나면 EOI 레지스터에 그 값을 써서 active를 해제한다.

NVIC는 이 "ack/EOI"를 하드웨어가 예외 진입/복귀 때 자동으로 해 줬다. GIC에서는 소프트웨어(GIC 드라이버)가 명시적으로 한다. 그래서 커널의 irq_chip에 .irq_eoi, .irq_mask 같은 콜백이 있다.

arm64의 예외 벡터 테이블(VBAR_EL1)에는 IRQ 엔트리가 상황별로 4개뿐이다(EL1t, EL1h, EL0 64-bit, EL0 32-bit). 커널 코드 실행 중이면 VBAR_EL1 + 0x280(EL1h IRQ), 유저 코드 실행 중이면 + 0x480(EL0 64-bit IRQ)으로 들어온다. 랩 커널 arch/arm64/kernel/entry.S에서 kernel_ventry 1, h, 64, irq가 만드는 el1h_64_irq가 그것이다.

코드 읽는 법:

  • handler 시그니처는 irqreturn_t fn(int irq, void *dev_id). 두 번째 인자는 등록 때 넘긴 쿠키(&f6)가 그대로 돌아온다. 공유 IRQ에서는 이 쿠키가 "어느 등록을 지울지" 식별자라서 장치마다 달라야 한다.

3. 번호가 두 개 — Linux IRQ 번호 vs hwirq (irq_domain)#

3.1 직관#

Cortex-M에서 EXTI15_10_IRQn = 40은 하드웨어 번호이자 소프트웨어 번호였다. SoC에는 인터럽트 컨트롤러가 여러 개 계층으로 있다: GIC 아래에 GPIO 컨트롤러(핀 32개가 GIC SPI 하나로 묶임), 그 아래 I2C GPIO expander, PCIe MSI 컨트롤러… 각자 자기 0번부터 번호를 매긴다. "GPIO3의 21번"과 "GIC의 21번"은 다른 인터럽트다.

그래서 커널은 두 번호를 구분한다.

  • hwirq: 그 컨트롤러 안에서의 번호. GIC라면 INTID(112), GPIO 컨트롤러라면 핀 번호(21).
  • Linux IRQ 번호 (virq): 커널 전체에서 유일한 번호. 실행 중에 동적으로 할당된다(CONFIG_SPARSE_IRQ). request_irq()·/proc/interrupts 첫 칸·/proc/irq/N이 쓰는 번호다.
  • irq_domain: 컨트롤러마다 하나씩 있는 "hwirq ↔ virq 변환표". DT를 파싱할 때(irq_of_parse_and_map → irq_create_fwspec_mapping) GIC 드라이버의 translate 콜백이 3셀을 hwirq + 트리거 타입으로 풀고, 빈 virq를 하나 잡아 매핑을 만든다.

그림 2 — irq_domain은 "컨트롤러 안 번호(hwirq)"와 "커널 전역 번호(virq)"를 잇는 표다. 등록할 때는 DT → hwirq → virq 방향, 인터럽트가 올 때는 IAR의 hwirq → virq → irq_desc 방향으로 쓴다.

5. top half / bottom half 와 threaded IRQ#

5.1 용어 정리#

  • top half (hard handler, hardirq): 인터럽트 컨텍스트에서 그 CPU의 IRQ가 꺼진 채로 돈다(arm64 Linux는 hardirq 중첩을 허용하지 않는다). sleep 금지, mutex 금지, GFP_KERNEL 금지 (F2).
  • bottom half: "나중에, 덜 급한 컨텍스트에서" 할 일. 커널에 여러 종류가 있다 — softirq, tasklet(폐지 진행 중), workqueue, 그리고 threaded IRQ. 앞의 셋은 F7에서 다룬다.
  • threaded IRQ: genirq가 등록마다 커널 스레드 irq/<virq>-<name>을 하나 만들고(kthread_create(irq_thread, ...)), hard handler가 IRQ_WAKE_THREAD를 반환하면 그 스레드를 깨운다. 스레드는 SCHED_FIFO 우선순위 50(sched_set_fifo() = MAX_RT_PRIO / 2)으로 돈다. 일반 태스크(SCHED_NORMAL)보다 항상 먼저, 그러나 다른 RT 태스크와는 우선순위로 경쟁한다.

RTOS 비유: hard handler = ISR, threaded handler = "ISR이 세마포어를 give하면 깨어나는 최고 우선순위급 태스크". 차이는 커널이 그 태스크·세마포어·ONESHOT mask/unmask까지 다 만들어 준다는 점이다.

7. IRQ affinity — 어느 CPU가 받나#

7.1 정의#

  • /proc/irq/N/smp_affinity (16진 비트마스크), smp_affinity_list (CPU 목록 0-1,3): "이 IRQ를 받아도 되는 CPU" — 사용자가 쓰는 값.
  • /proc/irq/N/effective_affinity(_list): 컨트롤러가 실제로 설정한 대상. GICv2 SPI는 한 CPU만 가능하므로(IRQD_SINGLE_TARGET) 드라이버가 마스크에서 하나를 고른다.
  • threaded handler의 스레드도 effective affinity를 따라간다(affinity가 바뀌면 플래그 IRQTF_AFFINITY가 서고, 스레드가 다음에 깨어날 때 irq_thread_check_affinity()가 스레드의 CPU 마스크를 맞춘다). 그래서 hard와 thread가 같은 CPU에서 돌아 캐시가 따뜻하다.

8. IRQ_NONE, spurious 감지, 인터럽트 폭풍#

8.1 커널의 감시 규칙 (kernel/irq/spurious.c의 note_interrupt)#

handler가 IRQ_NONE을 반환할 때마다(공유 라인이면 모든 handler가 NONE일 때) irqs_unhandled를 센다. 랩 소스 기준 규칙:

  • 직전 unhandled로부터 HZ/10(100 ms)보다 오래 지났으면 카운터를 1로 리셋한다 — 가끔 오는 가짜 인터럽트는 봐준다.
  • unhandled가 생긴 뒤부터 인터럽트를 10만 개 단위 창(irq_count)으로 센다. 창이 끝났을 때 unhandled가 99,900개 초과면 "고장"으로 판정한다.
  • 판정되면 irq N: nobody cared (try booting with the "irqpoll" option) + 스택 + 등록된 handler 목록을 찍고, Disabling IRQ #N 후 그 라인을 꺼 버린다(IRQS_SPURIOUS_DISABLED). 이후 그 장치는 인터럽트를 못 받는다.

Cortex-M에서 플래그를 안 지운 level 인터럽트는 ISR에 무한 재진입하며 시스템을 멈춘다. Linux는 이걸 감지해서 한 장치를 희생하고 시스템을 살린다.

8.2 예제 8 — 폭풍 만들기와 "nobody cared"#

무엇을 확인하나: mode=2에서 hard handler가 IRQ_NONE을 반환하면서 자기 자신을 다시 pending 시킨다. 플래그를 안 지운 level 인터럽트가 계속 다시 들어오는 상황을 흉내 낸 것이다.

출력에서 볼 것:

  • 이 call trace가 그림 1의 실물 증명이다. 아래에서 위로: 유저 sh의 write() syscall(el0t_64_sync → ... → fire_set) → irq_set_irqchip_state가 락을 풀며 IRQ를 다시 켜는 순간(_raw_spin_unlock_irqrestore, (P)) 인터럽트가 걸려 → el1h_64_irq → el1h_64_irq_handler → el1_interrupt → do_interrupt_handler → call_on_irq_stack → gic_handle_irq → generic_handle_domain_irq → handle_irq_desc → handle_fasteoi_irq → handle_irq_event → note_interrupt → 보고. 커널 모드(EL1)에서 인터럽트를 받았으니 el1h 벡터다.

8.3 예제 9 — 공유 라인이면 한 명만 IRQ_HANDLED여도 산다#

무엇을 확인하나: mode=3에서 같은 줄에 f6_a(항상 NONE + 재-pending)와 f6_b(항상 HANDLED)를 IRQF_SHARED로 등록하고 12만 번 폭풍을 일으킨다.

출력에서 볼 것: /proc/interrupts의 이름 칸이 f6_a, f6_b, /proc/irq/22/ 아래에 이름별 디렉터리 두 개. 12만 번 동안 두 handler가 매번 둘 다 불렸고(n_hard = n_b = 120000), 반환값을 OR한 결과가 HANDLED라 unhandled 0, "nobody cared" 0건이다. (fire가 3초 타임아웃 에러를 낸 것은 폭풍이 12만 번을 채우는 데 3초 넘게 걸렸기 때문이고, 결과에는 영향이 없다.)

교훈 두 가지. 공유 라인에서는 "내 장치가 낸 게 맞는지" 상태 레지스터를 먼저 확인하고 아니면 IRQ_NONE을 반환해야 한다(아니면 고장 난 이웃을 커널이 못 찾는다). 그리고 반대로, 고장 난 장치가 정상 장치와 라인을 공유하면 커널의 폭풍 감지가 작동하지 않고 CPU만 계속 태운다.

9. disable_irq vs disable_irq_nosync — 자기 자신을 기다리는 deadlock#

9.1 정의#

함수하는 일기다리나어디서 불러도 되나
disable_irq(irq)depth++ 후 mask, 실행 중인 hard handler와 thread_fn이 끝날 때까지 대기(synchronize_irq)예 (sleep 가능)process context, 자기 handler 밖에서만
disable_irq_nosync(irq)depth++ 후 mask, 바로 반환아니오handler 안을 포함해 어디서나
disable_hardirq(irq)mask + hard handler만 기다림hard만특수 용도
enable_irq(irq)depth--, 0이 되면 unmask아니오호출 횟수를 disable과 맞춰야 함
synchronize_irq(irq)mask 없이 "지금 도는 handler 끝나길" 대기예process context

disable_irq는 중첩 카운트다(debugfs의 ddepth). 두 번 disable 했으면 두 번 enable 해야 켜진다. NVIC의 NVIC_DisableIRQ는 카운트가 없다 — Don이 bare-metal 습관대로 쓰면 틀리는 곳이다.

9.2 예제 10 — thread_fn 안에서 disable_irq()를 부르면#

무엇을 확인하나: 먼저 thread_fn 안에서 disable_irq_nosync()(정상), 그다음 disable_irq()(deadlock)를 부른다. hung task 감지 시간을 5초로 줄여 둔다.

(hung task 보고가 5초·10초에 두 번 찍혀 중복 줄과 "Showing all locks held" 블록을 ...로 줄였다.)

출력에서 볼 것:

  • nosync는 즉시 돌아왔고 ddepth: 1 — 라인은 꺼진 상태로 남았다. (그 뒤 rmmod → free_irq가 디스크립터를 정리하고 재등록 때 다시 켜진다.)
  • disable_irq를 부른 스레드는 D 상태로 영원히 멈췄다. 스택이 정확히 말해 준다: f6_thread → disable_irq → __synchronize_irq → schedule. synchronize_irq는 "이 IRQ의 스레드가 다 끝나길" 기다리는데, 기다리는 주체가 바로 그 스레드다. 자기 자신의 종료를 기다리는 꼴이다.
  • lockdep(디버그 커널에 켜져 있음)은 이걸 못 잡는다 — 락이 아니라 wait queue 대기이기 때문이다. hung task 감지기(khungtaskd)만 알려 준다. 기본값 120초라 실무에서는 "장치가 2분 뒤부터 이상해요"로 나타난다.
  • hard handler 안에서 disable_irq()를 부르면 더 나쁘다: synchronize_irq가 IRQD_IRQ_INPROGRESS가 풀리길 스핀하므로 그 CPU가 그대로 굳는다. 이건 실행하지 않았다(게스트가 멈춰 출력을 얻기 어렵다). 소스(kernel/irq/manage.c의 __synchronize_hardirq) 근거의 설명이다.

10. IRQ가 막혀 있는 시간 — irqsoff tracer와 IRQ 시간 회계#

10.1 예제 13 — irqsoff tracer로 "누가 인터럽트를 오래 막았나" 찾기#

무엇을 확인하나: irqsoff tracer는 CPU에서 IRQ가 꺼져 있던 가장 긴 구간을 자동으로 기록한다. 드라이버가 local_irq_save() 후 300 ms를 busy-wait 하는 최악의 코드를 CPU1에서 돌린다.

(트레이스 646줄 중 머리, mdelay 루프의 처음과 끝, 마지막 스택만 남겼다.)

출력에서 볼 것:

  • 헤더 한 줄이 답이다: latency: 316757 us ... CPU#1, started at: irqsoff_set, ended at: simple_attr_write_xsigned. 어떤 함수가 IRQ를 끄고 어디서 켰는지가 그대로 나온다. 실무에서 "가끔 수 ms 지터"의 범인을 찾는 1순위 도구다.
  • 끝 지점이 irqsoff_set이 아니라 호출자인 이유: local_irq_restore()가 인라인되어 호출자 쪽 주소로 기록됐다.
  • 기다리는 동안 1 ms마다 __delay()가 보인다 — mdelay(300)이 udelay(1000)을 300번 부르는 구현이다.
  • 아무것도 안 해도 baseline 최대값이 14 ms였다. TCG + lockdep 환경에서 커널 자체의 IRQ-off 구간이 길게 측정된 것이다(앞선 실행에서는 69 ms까지 나왔다). 그래서 데모는 300 ms로 크게 잡았다. 실제 보드에서 baseline이 수백 µs를 넘으면 조사 대상이다.
  • 이 300 ms 동안 CPU1에 affinity된 IRQ는 전부 대기했다. 다른 CPU는 영향이 없다 — local_irq_disable()은 이 CPU만 막는다(F4의 "spin_lock_irqsave가 다른 CPU는 못 막는다"와 같은 이야기).

12. Embedded 실무에서 다시 보기#

12.1 I2C IMU의 data-ready 인터럽트#

예를 들어 센서 키트의 IMU가 INT 핀(GPIO, level-low)으로 "샘플 준비됨"을 알린다면, 인터럽트를 끄려면 I2C로 상태 레지스터를 읽어야 한다. I2C 전송은 sleep하므로 hard handler에서 못 한다. 그래서 표준형은 다음과 같다 (실행하지 않은 구조 예시 — H6에서 실제 드라이버로 다룬다).

IRQF_ONESHOT이 있으므로 thread가 I2C로 상태를 읽어 INT를 내릴 때까지 라인이 mask되어 폭풍이 안 난다. hard handler를 둔 이유는 오로지 타임스탬프다.

12.2 "가끔 샘플이 수 ms 늦어요"#

진단 순서: (1) /proc/interrupts로 IRQ가 어느 CPU로 가는지, 다른 시끄러운 IRQ(이더넷, eMMC)와 같은 CPU인지 (2) irqsoff tracer로 IRQ-off 최대 구간과 범인 함수 (3) irq_handler_entry → sched_wakeup → sched_switch 이벤트로 스레드가 늦게 뜨는 이유(더 높은 RT 태스크?) (4) 필요하면 chrt -f -p 80 <irq 스레드 PID>로 IMU 스레드 우선순위를 올리고, affinity를 한 CPU에 고정.

12.3 부팅하자마자 CPU 하나가 100%#

top에서 %irq/%hi가 높고 /proc/interrupts의 한 줄이 초당 수만씩 늘면 폭풍이다. DT의 트리거 타입(극성 포함), 장치 초기화 순서(IRQ를 먼저 켜고 장치 리셋을 나중에 하면 플로팅 핀), 공유 라인의 IRQ_NONE 규칙을 확인한다. 공유가 아니면 대개 몇 초 뒤 "nobody cared"가 나와 단서가 된다.

12.4 suspend 중 깨우기 (참고, 실행하지 않음)#

버튼·RTC·모뎀 IRQ로 시스템을 깨우려면 enable_irq_wake()(또는 device_init_wakeup + dev_pm_set_wake_irq)를 쓴다. 예제 4의 /sys/kernel/irq/22/wakeup disabled가 이 상태를 보여 주는 칸이다. 깊이는 PM 모듈에서 다룬다.

14. 면접에서 이렇게 말한다#

Q. Walk me through what happens on an ARM64 Linux system when a peripheral raises an interrupt.

A. 장치가 선을 올리면 GIC Distributor가 pending으로 잡고 대상 CPU의 CPU interface가 IRQ를 건다. CPU는 VBAR_EL1의 IRQ 벡터(el1h_64_irq 또는 el0t_64_irq)로 들어가 레지스터를 저장하고, el1_interrupt가 IRQ 스택으로 바꿔 handle_arch_irq, 즉 gic_handle_irq를 부른다. GIC 드라이버는 IAR을 읽어 hwirq를 얻고 generic_handle_domain_irq로 irq_domain에서 Linux IRQ 번호의 irq_desc를 찾는다. 그 디스크립터의 flow handler(handle_fasteoi_irq)가 등록된 handler들을 부르고 EOI를 쓴다. 나갈 때 softirq와 선점 검사가 돈다.

The device asserts its line, the GIC distributor marks it pending and signals the target CPU. The CPU takes the IRQ exception through the vector table, the arm64 entry code saves registers, switches to the IRQ stack and calls handle_arch_irq, which is gic_handle_irq. That reads the IAR to get the hardware IRQ number, maps it through the irq_domain to the Linux IRQ descriptor, and calls the flow handler — handle_fasteoi_irq for GIC SPIs — which runs the driver's handlers and writes EOI. On exit, the kernel runs pending softirqs and checks for preemption, which is when a woken IRQ thread gets to run.

꼬리 질문: "GICv2와 v3의 차이는?" → v3는 CPU interface를 시스템 레지스터(ICC_IAR1_EL1 등)로, CPU별 Redistributor, MSI용 LPI/ITS, 8개 넘는 CPU 지원.

Q. What's the difference between a Linux IRQ number and a hardware IRQ number?

A. hwirq는 인터럽트 컨트롤러 안의 번호(GIC INTID, GPIO 핀 번호)이고, Linux IRQ 번호는 커널 전체에서 유일한 가상 번호다. 컨트롤러가 계층으로 여러 개라 hwirq만으로는 겹치기 때문에, 컨트롤러마다 irq_domain이 hwirq ↔ virq 매핑을 들고 있다. virq는 동적으로 할당되니 드라이버는 platform_get_irq()로 받아야 하고 하드코딩하면 안 된다. 예를 들어 DT의 SPI 80은 GIC hwirq 112였고 virq는 22였다.

The hwirq is the number local to one interrupt controller — a GIC INTID or a GPIO pin. The Linux IRQ number is a global, dynamically allocated number. Each controller has an irq_domain that maps its hwirqs to Linux IRQs, typically created when the device tree is parsed. Drivers should always get the number from platform_get_irq or gpiod_to_irq, never hard-code it.

Q. Explain top half and bottom half. When do you use a threaded IRQ?

A. top half는 hardirq 컨텍스트에서 IRQ가 꺼진 채 도는 부분이라 짧아야 하고 sleep할 수 없다. bottom half는 나머지 일을 나중에 하는 것으로, softirq·tasklet·workqueue·threaded IRQ가 있다. 처리에 sleep이 필요하면(I2C/SPI 장치 읽기) threaded IRQ를 쓴다. request_threaded_irq로 hard handler와 thread_fn을 주면 커널이 irq/N-name SCHED_FIFO 50 스레드를 만들고 hard가 IRQ_WAKE_THREAD를 반환하면 깨운다. 실측에서 hard는 수 µs, 깨우기는 그보다 훨씬 길어서, 타임스탬프는 hard에서 찍는다.

The top half runs in hard interrupt context with interrupts disabled on that CPU, so it must be short and can't sleep. The bottom half defers the rest — softirqs, workqueues, or a threaded handler. I use a threaded IRQ whenever handling needs to sleep, like reading an I2C sensor: the hard handler captures a timestamp and returns IRQ_WAKE_THREAD, and the kernel wakes a dedicated SCHED_FIFO thread to do the bus transaction. It's also what PREEMPT_RT does for almost every interrupt.

꼬리 질문: "threaded IRQ의 단점은?" → 스케줄링 지연(다른 RT 태스크에 밀릴 수 있음), 컨텍스트 스위치 비용, ONESHOT이면 그동안 라인이 mask되어 다음 인터럽트도 늦어짐.

Q. Why does request_threaded_irq with a NULL primary handler require IRQF_ONESHOT?

A. handler가 NULL이면 기본 hard handler가 그냥 스레드만 깨우고 장치는 ack하지 못한다. level 인터럽트라면 EOI 직후 다시 들어오고, 스레드가 돌 틈 없이 폭풍이 된다. ONESHOT은 thread_fn이 끝날 때까지 라인을 mask해 두었다가 끝나면 unmask하므로 이 문제를 막는다. 그래서 커널이 그 조합을 -EINVAL로 거부한다.

With a NULL primary handler, the default one just wakes the thread and can't quiet the device. For a level-triggered line the interrupt would fire again immediately after EOI, before the thread ever runs. IRQF_ONESHOT keeps the line masked until the thread function returns, so the kernel rejects the combination without it.

Q. What happens if an interrupt handler keeps returning IRQ_NONE?

A. genirq의 note_interrupt가 unhandled 횟수를 센다. 10만 번 창에서 99,900번 넘게 처리되지 않으면 "irq N: nobody cared"와 스택, handler 목록을 찍고 그 라인을 disable한다. 시스템을 살리려고 장치 하나를 희생하는 것이다. 보통 원인은 level 인터럽트를 ack 안 했거나 트리거 타입이 틀린 경우다. 공유 라인에서는 다른 handler가 HANDLED를 반환하면 감지가 안 된다는 점도 주의한다.

The core counts unhandled interrupts in note_interrupt. If more than 99,900 out of a 100,000-interrupt window go unhandled, it prints "irq N: nobody cared" with a stack trace and the handler list, then disables the line. Root causes are usually a level interrupt that isn't acknowledged in the device, or a wrong trigger type in the device tree.

Q. disable_irq versus disable_irq_nosync — what's the trap?

A. disable_irq는 mask 후 실행 중인 hard handler와 thread가 끝날 때까지 기다린다. 그래서 그 IRQ의 handler나 thread 안에서 부르면 자기 자신을 기다리는 deadlock이 된다. 실험에서 thread_fn 안에서 불렀더니 스레드가 __synchronize_irq에서 D 상태로 굳고 hung task 경고만 나왔다. lockdep도 못 잡는다. handler 안에서는 disable_irq_nosync를 써야 하고, disable은 중첩 카운트라 enable 횟수를 맞춰야 한다.

disable_irq masks the line and then waits for any running handler and thread to finish. Calling it from that IRQ's own handler or thread waits on itself and deadlocks — lockdep won't catch it, only the hung-task detector. Inside the handler use disable_irq_nosync. Also, disables nest, so every disable needs a matching enable.

Q. How do you control which CPU handles an interrupt, and why would you?

A. /proc/irq/N/smp_affinity(마스크)나 smp_affinity_list에 쓰고, 실제 적용 값은 effective_affinity로 확인한다. GIC SPI는 한 번에 한 CPU로만 가므로 마스크 중 하나가 골라진다. threaded handler의 스레드도 그 CPU를 따라간다. 실시간 CPU를 IRQ에서 격리하거나, 센서 IRQ를 처리 태스크와 같은 CPU에 두려고 쓴다. 임베디드에서는 irqbalance를 끄고 정적으로 지정하는 편이 지터가 적다.

I write a CPU mask to /proc/irq/N/smp_affinity and confirm what the controller actually programmed in effective_affinity — a GIC SPI targets a single CPU. The IRQ thread follows that CPU. I'd use it to keep interrupts off an isolated real-time core, or to co-locate a sensor IRQ with the task that consumes the data. On embedded systems I usually disable irqbalance and set affinities statically.

Q. How would you debug interrupt latency or jitter on an embedded Linux board?

A. 먼저 /proc/interrupts로 횟수와 CPU 분포를 보고, ftrace의 irq_handler_entry/exit와 sched_wakeup/sched_switch로 hard 처리와 스레드 실행 시점의 간격을 잰다. IRQ-off 구간이 의심되면 irqsoff tracer로 최대 구간과 시작·끝 함수를 찾는다. 스레드가 늦게 뜨면 RT 우선순위와 affinity를 조정한다. 전체 시스템 지연은 cyclictest로 기준선을 잡는다.

Start with /proc/interrupts for counts and CPU distribution. Then ftrace: irq_handler_entry/exit plus sched_wakeup and sched_switch show the gap between the hard handler and the thread actually running. If something is masking interrupts, the irqsoff tracer reports the worst interrupts-off section and the functions that started and ended it. Then tune the IRQ thread priority and affinity, and use cyclictest for a system-wide baseline.

17. 요약 & 체크리스트#

arm64 Linux에서 인터럽트는 GIC가 받아 CPU에 IRQ 예외를 걸고, 하나뿐인 벡터에서 gic_handle_irq가 IAR로 hwirq를 읽어 irq_domain으로 virq의 irq_desc를 찾고, flow handler(handle_fasteoi_irq)가 드라이버가 등록한 irqaction handler를 부른 뒤 EOI를 쓴다. 드라이버는 devm_request_irq(짧은 MMIO 처리) 또는 devm_request_threaded_irq(sleep이 필요한 처리, SCHED_FIFO 50 스레드)를 고르고, handler는 IRQ_HANDLED/IRQ_NONE/IRQ_WAKE_THREAD로 결과를 알린다. 실측에서 top half는 수 µs, 스레드 깨우기는 그보다 수십 배 길고 꼬리가 길었으므로 타임스탬프는 hard에서 찍는다. IRQ_NONE 폭풍은 "nobody cared"로 라인이 꺼지고, handler 안의 disable_irq는 자기 자신을 기다리는 deadlock이다. affinity는 /proc/irq/N/smp_affinity로 옮기고 effective_affinity로 확인하며, IRQ-off 지연은 irqsoff tracer로 찾는다.
