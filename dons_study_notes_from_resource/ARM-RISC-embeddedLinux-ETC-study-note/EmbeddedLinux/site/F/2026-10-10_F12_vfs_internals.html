이 노트를 다 읽으면: VFS의 네 객체(super_block·inode·dentry·file)와 각각의 ops 테이블이 무엇을 담당하는지 그림으로 그릴 수 있다 · open("/dev/foo")가 do_sys_openat2 → path_openat → vfs_open → chrdev_open → 드라이버 .open까지 가는 경로를 실제 ftrace 출력으로 설명할 수 있다 · dcache와 RCU-walk/ref-walk가 경로 탐색을 어떻게 빠르게 하는지 말할 수 있다 · libfs로 50줄짜리 pseudo filesystem을 만들어 mount 할 수 있다 왜 필요한가: 드라이버 면접의 단골 "What happens when you open /dev/foo?"는 이 노트 한 장이고, 실무에서 "release가 안 불려요", "두 번째 open에서 상태가 섞여요", "sysfs 파일 하나 읽는 데 왜 이렇게 느려요" 같은 질문의 답이 전부 VFS 객체의 수명과 공유 관계에 있다 Don 기준 난이도: 함수 포인터 테이블로 HW 차이를 숨기는 HAL은 펌웨어에서 늘 했다 / 새로 배울 부분은 "이름(dentry) · 실체(inode) · 열린 세션(file)이 분리된 객체이고 각각 캐시와 참조 카운트로 따로 산다"는 것, 그리고 char device에서 f_op가 open 도중 바뀐다는 것 선행 노트: A3(fd → OFD → inode, 유저 시점), E3(커널 모듈), E6(ksys_read → vfs_read → f_op->read) — G4(char device), G7(misc device), G8(sysfs·debugfs), J2·J3(블록·메모리 파일시스템)으로 이어진다

0. 큰 그림 — 이게 왜 필요한가#

A3에서는 유저 시점에서 "fd → open file description → inode" 3단 구조를 봤다. 이 노트는 그 3단이 커널 안에서 실제로 어떤 구조체이고, 누가 만들고, 어떤 함수 포인터를 거쳐 드라이버까지 가는지를 본다.

VFS(Virtual File System)는 한 문장으로 "파일처럼 보이는 모든 것에 대한 공통 인터페이스 + 함수 포인터 테이블"이다. ext4 파일, /proc/cpuinfo, /sys/class/gpio/export, /dev/ttyAMA0, pipe, socket이 모두 같은 read()로 읽히는 이유는 VFS가 공통 객체를 만들고, 실제 동작은 각 구현이 채운 ops 테이블로 넘기기 때문이다.

그림 1 — VFS는 다형성(polymorphism) 계층이다. 위쪽 syscall 코드는 하나이고, 아래쪽 구현은 자기 ops 테이블만 채운다.

Don의 SSD 펌웨어 경험으로 옮기면 정확히 이렇다. FTL은 nand->ops->read_page(die, page, buf)만 부르고, 벤더 A·B의 NAND 차이는 ops 테이블 구현 안에 숨는다. 커널도 vfs_read()는 file->f_op->read(...)만 부르고, 그게 ext4인지 /dev/null인지 Don이 쓴 드라이버인지 모른다. 차이는 두 가지다.

  1. 테이블이 네 종류다 — 마운트 단위(super_operations), 파일 실체 단위(inode_operations), 이름 단위(dentry_operations), 열린 세션 단위(file_operations).
  2. 객체마다 수명이 다르고 캐시된다. inode와 dentry는 파일을 닫아도 메모리에 남아(캐시) 다음 open을 빠르게 하고, struct file은 open마다 새로 생겼다가 마지막 참조가 사라지면 없어진다.

이 노트의 실습은 전부 랩의 debug 커널(/var/lab/out/Image-dbg, 6.18.55-dbg: ftrace function_graph, kprobe_events, lockdep 포함)을 QEMU virt(cortex-a57, -smp 2, 512 MB, TCG)로 부팅해서 돌렸다.

0.1 실습 준비 — 모듈 빌드와 게스트 부팅 스크립트#

모듈 두 개(f12_vfs, f12fs)는 debug 커널 빌드 트리로 빌드한다 (vermagic 6.18.55-dbg, 일반 out/Image에 넣으면 안 된다).

게스트 안에서 돌릴 셸 스크립트를 하나 받아 initramfs에 넣고 부팅하는 스크립트(boot.sh, VM에서 실행). initramfs의 /init이 LAB_CMD를 실행한 뒤 전원을 끈다.

랩 initramfs의 /init은 proc, sysfs, devtmpfs(/dev), debugfs를 mount 한다. tracefs는 직접 mount 해야 한다(mount -t tracefs none /sys/kernel/tracing).

1. 네 객체와 ops 테이블#

1.1 직관 — 도서관을 다시 보자#

A3의 도서관 비유를 커널 쪽으로 한 단계 넓힌다.

  • super_block = 도서관 분관 하나. "이 분관은 ext4 방식으로 책을 꽂는다, 블록 크기는 4 KiB, 루트 서가는 여기". mount 한 번에 하나 생긴다.
  • inode = 책 그 자체(메타데이터 카드 포함). 크기, 권한, 소유자, 장치 번호, 데이터 위치. 파일 하나에 하나.
  • dentry = 서가 안내판의 한 줄 "/dev 아래 f12_vfs → 이 책". 이름과 부모 디렉터리, 그리고 inode를 잇는다. 하드 링크가 있으면 책 하나에 안내판 줄이 여러 개다.
  • file = 대출 기록 카드. 누가 어떤 모드로 빌렸고 몇 쪽까지 읽었나. open()마다 하나.

핵심은 이름(dentry)과 실체(inode)가 다른 객체라는 점이다. FAT 같은 단순한 파일시스템은 디렉터리 엔트리에 파일 정보를 같이 담지만, VFS는 둘을 분리했다. 그래서 하드 링크(이름 둘, 실체 하나), rename(이름만 바꿈), "열어 둔 채로 unlink"(이름은 사라졌지만 실체와 열린 세션은 살아 있음)가 자연스럽게 된다.

그림 2 — 실습 §5의 실제 상태. fd 4와 fd 6(dup)은 같은 struct file을 가리키고, file은 f_path.dentry와 f_inode로 이름과 실체를 붙잡고, inode는 i_sb로 자기가 속한 마운트의 super_block을 안다. /dev는 devtmpfs이므로 s_type이 devtmpfs다.

1.3 예제 1 — 함수 이름은 소스와 심볼에서 확인한다#

무엇을 확인하나: 이 노트가 쓰는 open 경로 함수들이 랩 커널 6.18.55에 실제로 있는지, 그리고 VM 호스트 커널 7.0과 이름이 다른지.

같은 이름을 VM 호스트 커널 7.0의 /proc/kallsyms와 랩 6.18의 System.map에서 찾아본다.

출력에서 볼 것:

  • 6.18에서는 do_filp_open, 7.0에서는 do_file_open이다. A1·C1 노트에서 7.0 호스트로 본 이름이 do_file_open이었던 이유가 이것이다 — 같은 역할의 함수가 이름만 바뀌었다. 면접에서는 "do_filp_open (renamed do_file_open in recent kernels)"처럼 말하면 안전하다.
  • open_last_lookups는 System.map에 없다. 그리고 6.18의 do_open 심볼은 namei.c의 do_open이 아니다. 아래처럼 gdb로 보면 namei.c의 do_open 본문은 path_openat 안에 inline 되었고, 심볼 do_open은 NFS(fs/nfs/dir.c)의 다른 static 함수다.

함정: 소스의 함수 이름이 그대로 ftrace·kprobe 대상이 되는 것은 아니다. static 함수는 inline 되면 심볼이 사라진다. 추적할 함수는 System.map이나 /sys/kernel/tracing/available_filter_functions에서 먼저 확인한다.

1.4 예제 2 — struct file의 실제 레이아웃 (pahole)#

무엇을 확인하나: struct file에 A3에서 말로만 했던 필드(f_pos, f_flags, f_op, private_data, f_ref)가 실제로 어디 있는지. 이 오프셋은 §6 kprobe에서 그대로 쓴다.

출력에서 볼 것:

  • f_lock(spinlock)이 72바이트, f_pos_lock(mutex)이 160바이트를 차지한다. lockdep(PROVE_LOCKING) 때문에 락 구조체가 커진 debug 커널이라서다. 일반 커널에서 struct file은 이보다 훨씬 작고 오프셋도 다르다(소스 주석에는 f_path가 cacheline 1 = 64바이트 근처로 적혀 있다). pahole이 일부 타입 크기를 0으로 찍는 것은 DWARF 표현 문제이고, 오프셋은 맞다(§6에서 실제로 읽어서 검증한다).
  • 참조 카운트가 atomic_long_t f_count가 아니라 file_ref_t f_ref다. A3 §11.4에서 말한 대로 6.13부터 바뀌었다. 드라이버는 이 필드를 직접 만지지 않고 get_file()/fput()/file_count()를 쓴다.
  • 소스 정의는 } __randomize_layout이다. CONFIG_RANDSTRUCT를 켜면 필드 순서가 빌드마다 섞인다(랩은 CONFIG_RANDSTRUCT_NONE=y). 드라이버가 오프셋을 하드코딩하면 안 되는 이유다.

같은 방식으로 dentry와 inode의 필요한 필드만 본다.

출력에서 볼 것: dentry의 이름은 struct qstr(hash + len + name 포인터)다. 해시를 미리 계산해 들고 있어서 dcache 비교가 빠르다(§3). dentry 앞부분(d_flags, d_seq, d_hash, d_parent, d_name, d_inode)은 소스 주석대로 "RCU lookup touched fields"로 묶여 있다 — 경로 탐색이 가장 자주 읽는 필드를 같은 캐시라인에 모은 것이다. Don이 SSD 펌웨어에서 hot 필드를 TCM이나 같은 캐시라인에 모으던 것과 같은 설계다.

2. open()의 경로 — do_sys_openat2부터 fd_install까지#

2.1 직관 — "번호 예약 → 이름 따라가기 → 세션 만들기 → 번호에 꽂기"#

open()이 하는 일을 펌웨어식으로 쓰면 네 단계다.

  1. 빈 fd 번호를 예약한다 (아직 아무것도 안 꽂음).
  2. 경로 문자열을 따라가 마지막 이름의 dentry와 inode를 찾는다 (§3).
  3. struct file을 만들고 inode의 i_fop를 복사한 뒤 f_op->open을 부른다 (드라이버가 처음 불리는 지점).
  4. 성공하면 예약한 번호에 file을 꽂는다(fd_install). 실패하면 예약을 취소한다.

번호를 먼저 예약하고 맨 마지막에 꽂는 이유: 다른 스레드가 아직 반쯤 만들어진 file을 그 fd로 보면 안 되기 때문이다. fd_install() 전까지 이 file은 이 스레드만 안다.

그림 3 — open()의 커널 경로 (6.18.55 기준 이름). 초록은 준비, 주황은 경로 탐색, 빨강은 file 생성과 드라이버 호출, 파랑은 fd 테이블.

2.2 소스로 보기 — 랩 커널 그대로#

do_sys_openat2()는 위 1·4단계를 그대로 보여 준다.

do_filp_open()은 같은 탐색을 최대 세 번 시도한다. 먼저 락 없이(RCU-walk), 안 되면 참조 카운트를 잡으면서(ref-walk), NFS 같은 곳에서 캐시가 낡았으면(-ESTALE) 재검증하면서.

path_openat()의 핵심 부분 — struct file은 경로 탐색 전에 할당된다.

while 루프는 심볼릭 링크 때문이다. 마지막 성분이 symlink면 open_last_lookups()가 링크 내용을 새 경로로 돌려주고, 다시 link_path_walk()가 그것을 따라간다.

마지막으로 do_dentry_open()(fs/open.c)이 file을 채우고 드라이버를 부른다. 드라이버 작성자에게 중요한 줄만 남겼다.

여기서 드라이버 작성자가 알아야 할 것 세 가지:

  • fops_get()은 try_module_get(fops->owner)다. .owner = THIS_MODULE을 빼먹으면 열린 fd가 있는데 rmmod가 성공하고, 다음 read에서 사라진 코드로 점프한다.
  • FMODE_CAN_READ/FMODE_CAN_WRITE는 open이 끝난 뒤의 f_op 를 보고 정한다. 그래서 char device처럼 open 도중 f_op를 바꿔도 결과가 맞다. 그리고 .write가 없는 파일에 write 하면 vfs_write()가 -EINVAL을 돌려준다 (§7 f12fs에서 실제로 본다).
  • .open이 실패하면(음수 반환) file은 버려지고 .release는 불리지 않는다. open에서 할당한 것은 open의 에러 경로에서 직접 풀어야 한다.

7. 파일시스템 타입, mount, 그리고 pseudo filesystem#

7.1 file_system_type → super_block → root dentry#

파일시스템 "종류"는 struct file_system_type 하나로 커널에 등록된다. 핵심 필드(6.18 include/linux/fs.h):

  • register_filesystem()은 이것을 전역 단일 연결 리스트(file_systems, next 필드)에 넣는다. 같은 이름이 있으면 -EBUSY. /proc/filesystems는 이 리스트를 그대로 출력하고, FS_REQUIRES_DEV가 없는 것(블록 장치가 필요 없는 것) 앞에 nodev를 붙인다.
  • mount -t X는 이름으로 타입을 찾고 init_fs_context()로 struct fs_context를 만든 뒤 fc->ops->get_tree()를 부른다. 새 mount API(fs_context)는 5.x부터의 방식이고, 옛 .mount 콜백은 남아 있지만 새 코드에서는 쓰지 않는다.
  • get_tree는 보통 헬퍼 하나로 끝난다: get_tree_nodev()(mount마다 새 super_block, tmpfs·f12fs), get_tree_single()(시스템에 super_block 하나, 예: 일부 pseudo FS), get_tree_bdev()(블록 장치 기반, ext4). 헬퍼가 super_block을 할당하고 파일시스템의 fill_super를 불러 s_op, s_magic, s_root를 채우게 한다.
  • kill_sb는 umount 때 super_block을 정리한다. 메모리에만 있는 FS는 kill_litter_super()(남은 dentry를 정리)를 쓴다.

그림 6 — f12fs가 등록되고 mount 되는 과정. 타입은 리스트에 한 번, super_block은 mount마다 하나.

8. dcache와 inode cache의 크기 — 측정#

8.1 예제 11 — /sys 전체를 세 번 걷기#

무엇을 확인하나: 경로를 처음 걸을 때 dentry·inode가 얼마나 생기는지, 두 번째부터 얼마나 빨라지는지, drop_caches로 회수되는지. /proc/sys/fs/dentry-state의 앞 두 숫자는 nr_dentry(전체 dentry 수)와 nr_unused(참조 0으로 LRU에 있는 수), /proc/sys/fs/inode-nr은 nr_inodes와 nr_free_inodes다.

(주석의 "두 번"은 실제로는 세 번이다 — 두 번째와 세 번째가 같은지도 보려고 늘렸다.)

(slabinfo 열: 이름, active 객체 수, 전체 객체 수, 객체 크기(바이트).)

그림 7 — 예제 11의 측정값. 왼쪽: /sys를 한 번 걸으면 dentry·inode가 약 2만 7천 개로 늘고, drop_caches(2)로 2288개까지 회수된다(막대 위 숫자는 nr_dentry). 오른쪽: 같은 걷기가 두 번째부터 약 29% 빨라진다.

출력에서 볼 것:

  • dentry +26684, inode +26683: 걸은 항목 27266개마다 거의 하나씩 생겼다. 단, 이 숫자는 sysfs만이 아니다. nftw에 FTW_MOUNT를 주지 않았으므로 /sys/kernel/debug(debugfs, 그 아래 tracefs 자동 mount 포함)까지 넘어가서 걸었다.
  • inode_cache 26 → 17134, kernfs_node_cache는 17138 그대로: sysfs(kernfs) inode는 일반 inode_cache slab에서 나오고, 늘어난 수(약 1만 7천)가 kernfs 노드 수와 거의 같다 — kernfs 노드 하나당 VFS inode 하나가 생겼다. 나머지 약 1만 개는 debugfs·tracefs inode로, 이 FS들은 자기 전용 slab(debugfs_inode_cache 등, 위 grep에는 넣지 않았다)을 쓴다. kernfs 노드(원본 데이터)는 장치가 등록될 때 이미 있고, VFS의 dentry/inode는 누가 볼 때 만들어지는 캐시일 뿐이다(§3.3의 kernfs_iop_lookup). 메모리로 보면 dentry 328바이트 + inode 1216바이트(debug 빌드 크기) × 약 2만 7천 ≈ 40 MB. 512 MB 보드에서 무시할 수 없는 양이고, 그래서 이 캐시들은 shrinker로 회수 가능하게 만들어져 있다.
  • nr_unused 26690: 걷기가 끝나면 대부분 참조 0(누구도 열고 있지 않음)이 되어 LRU에 남는다. 이것이 "캐시"이고, drop_caches나 메모리 압박 때 회수 대상이다. 회수 후 2288개는 열려 있거나 mount 점처럼 고정된 것 + 이후 다시 만들어진 것이다.
  • 시간 22.8 s → 16.2 s: 2차부터 kernfs_iop_lookup과 dentry·inode 할당이 빠진 만큼 빨라졌다. 그래도 2차가 여전히 오래 걸리는 것은 매 항목마다 newfstatat/getdents64 syscall, sysfs의 ref-walk(§3.3), 그리고 TCG + lockdep 비용이 남기 때문이다. 실제 보드에서는 절대값이 수십 배 작다.

함정: /proc/sys/vm/drop_caches는 전역 상태를 바꾸는 운영 도구이지 튜닝 손잡이가 아니다. 공유 장비에서 쓰면 다른 프로세스의 성능이 출렁인다. 이 측정도 랩 VM 호스트가 아니라 내 QEMU 게스트 안에서만 했다.

10. Embedded 실무에서 다시 보기#

10.1 센서 키트의 IMU char device — open마다 컨텍스트#

IMU 드라이버를 char device로 만들면 보통 두 프로세스가 동시에 연다: 센서 퓨전 데몬(고속 FIFO read)과 진단 툴(가끔 상태 ioctl). §5처럼 open마다 private_data에 컨텍스트(읽기 위치, 구독 설정)를 두고, 장치 전역 상태(FIFO, 레지스터 캐시)는 container_of(inode->i_cdev, ...)로 찾은 장치 구조체에 두고 mutex로 보호한다. 둘을 섞으면 "진단 툴을 켜면 퓨전 데몬의 데이터가 튄다" 같은 버그가 된다. 그리고 "하나만 열 수 있는 장치"(예: 펌웨어 업데이트 채널)는 .open에서 atomic 플래그로 두 번째 open에 -EBUSY를 돌려준다 — 이것도 file이 open마다 따로 생긴다는 사실 위에서 설계하는 것이다.

10.2 sysfs 폴링 데몬이 CPU를 먹는다#

GPIO 값, 온도, 배터리 잔량을 sysfs에서 100 Hz로 읽는 데몬이 흔하다. 매번 open + read + close를 하면 §3.3에서 본 것처럼 경로 성분마다 ref-walk(kernfs가 RCU-walk를 거부)와 kernfs 콜백, file 할당·해제가 반복된다. 해법은 fd를 한 번 열어 두고 pread(fd, buf, n, 0) 으로 다시 읽기다. sysfs 속성은 오프셋 0에서 다시 읽으면 show()가 새로 불린다. 값 변화를 기다려야 하면 poll()(sysfs_notify, G6·G8) 또는 GPIO character device(/dev/gpiochipN)의 이벤트를 쓴다.

10.3 "release가 안 불려서 장치 전원이 안 꺼져요"#

카메라나 LiDAR처럼 "열려 있는 동안만 전원 ON" 하는 드라이버에서 자주 나온다. 원인은 거의 항상 file의 참조가 남아 있는 것이다: 데몬이 fork()/system()으로 자식을 띄웠는데 fd에 O_CLOEXEC가 없었다, mmap한 영역이 남아 있다(VMA가 file 참조를 잡는다), 다른 스레드가 dup 해 갔다. 확인은 ls -l /proc/*/fd | grep 장치명과 /proc/<pid>/maps. 드라이버 쪽에서는 §6.2의 kprobe처럼 f12_release(여기서는 드라이버의 release)에 탐침을 걸어 언제 불리는지 본다.

10.4 디버그 인터페이스는 debugfs에, 제품 인터페이스는 sysfs/char에#

bring-up 중에는 레지스터 덤프, 내부 카운터, 강제 상태 전이를 노출하고 싶다. 이것을 sysfs에 넣으면 유저스페이스 ABI가 되어 나중에 지울 수 없다. debugfs에 넣는다(debugfs_create_regset32, debugfs_create_file). 제품 빌드에서는 debugfs mount 자체를 막을 수 있고(debugfs=off 커널 인자, 또는 CONFIG_DEBUG_FS 끄기), 그때 드라이버가 깨지지 않도록 debugfs 함수의 실패를 무시하는 것이 관례다 — debugfs API는 에러를 확인하지 않아도 되게 설계됐다.

12. 면접에서 이렇게 말한다#

Q. What happens when you call open("/dev/foo", O_RDWR)?

A. 커널이 빈 fd 번호를 예약하고, 경로를 dcache로 따라가 foo의 dentry와 inode를 찾는다. struct file을 할당하고 f_op = inode->i_fop로 시작하는데, 장치 inode의 i_fop는 def_chr_fops라서 chrdev_open이 불린다. chrdev_open이 i_rdev(major:minor)로 cdev_add 때 등록된 cdev를 찾아 f_op를 드라이버의 file_operations로 바꾸고 드라이버 .open을 부른다. 성공하면 fd_install로 fd 번호에 file을 꽂고 번호를 돌려준다.

The kernel reserves an unused fd, then walks the path through the dentry cache to find the dentry and inode for "foo". It allocates a struct file and initializes f_op from inode->i_fop. For a character device that's def_chr_fops, whose open is chrdev_open: it looks up the cdev registered for the inode's major:minor, swaps file->f_op to the driver's file_operations, and calls the driver's open. If that succeeds, fd_install publishes the file in the process's fd table and the fd is returned. After that, read, ioctl and friends go straight through file->f_op.

꼬리 질문: "misc device면 뭐가 달라요?" → major 10 전체가 misc의 cdev 하나라서 misc_open이 minor로 한 번 더 찾아 fops를 두 번째로 바꾸고, private_data에 struct miscdevice *를 넣어 준다.

Q. What's the difference between an inode, a dentry, and a file?

A. inode는 파일 실체(메타데이터, 장치 번호, 데이터 위치)로 파일당 하나, dentry는 "부모 디렉터리 안의 이름 → inode" 연결로 이름당 하나, file은 열린 세션(오프셋, 플래그, f_op, private_data)으로 open마다 하나다. 하드 링크는 dentry 둘·inode 하나, 같은 파일을 두 번 open 하면 file 둘·inode 하나다.

An inode is the object itself — metadata, size, device number, where the data lives — one per file. A dentry is a name: it links a name in a parent directory to an inode, and it's what the dcache caches for path lookup. A struct file is an open instance — position, flags, f_op, private_data — created on every open. Two opens of the same device give two struct files and one inode; dup or fork shares the same struct file.

Q. When is a driver's release called?

A. close 할 때가 아니라 그 struct file의 마지막 참조가 사라질 때다. dup, fork로 물려받은 fd, mmap이 참조를 잡고 있으면 close 해도 안 불린다. close마다 불리는 것은 .flush다.

Release is called when the last reference to the struct file goes away, not on every close. Dup'ed fds, children that inherited the fd across fork, and mmaps all hold references. If you need a hook on every close, that's flush.

Q. How does path lookup stay fast?

A. 성분마다 (부모 dentry, 이름) 해시로 dcache를 찾는다. 대부분은 RCU-walk로 락도 refcount도 안 잡고 seqcount로만 검증하며 걷는다. 잠들어야 하는 콜백을 만나면 ref-walk로 내려가고, 캐시에 없을 때만 파일시스템의 ->lookup을 부른다. 없는 이름도 negative dentry로 캐시한다.

Each component is a hash lookup in the dcache keyed by parent dentry and name. The common case is RCU-walk: no locks, no refcount changes, validated with per-dentry sequence counts. If something needs to sleep — a permission check, revalidation, or a cache miss — it drops to ref-walk, and only a miss calls the filesystem's lookup. Negative dentries cache "doesn't exist" too.

꼬리 질문: "sysfs도 RCU-walk 되나요?" → 6.18 기준 kernfs의 permission 콜백이 MAY_NOT_BLOCK에서 -ECHILD를 돌려주므로 /sys 아래는 ref-walk로 걷는다(함수 추적으로 확인).

Q. Where would you expose a driver's tuning knobs vs debug info vs data stream?

A. 데이터 스트림과 명령은 char device(또는 서브시스템 프레임워크), 장치 속성 하나하나는 sysfs 속성(ABI, 한 파일 한 값), 개발용 덤프는 debugfs(ABI 아님). procfs에는 새 드라이버 정보를 넣지 않는다.

Streaming data and commands go through a character device — or better, the right subsystem like IIO or input. Per-device attributes go in sysfs, one value per file, and that's ABI. Debug dumps and knobs go in debugfs, which isn't ABI and may be disabled in production. New driver info doesn't go in procfs.

Q. What does f_pos vs *ppos mean in a driver's read?

A. ppos는 VFS가 넘기는 위치 포인터다. 일반 read에서는 ksys_read가 f_pos를 지역 변수로 복사해 그 주소를 넘기고 성공하면 다시 반영한다. pread면 유저가 준 오프셋이다. 그래서 드라이버는 file->f_pos가 아니라 *ppos만 읽고 갱신해야 한다.

ppos is the position the VFS hands you. For plain read, ksys_read copies f_pos into a local, passes its address, and writes it back on success; for pread it's the caller's offset. A driver should only use and update *ppos, never touch file->f_pos directly.

Q. How do you add a new filesystem type to the kernel?

A. struct file_system_type에 이름, init_fs_context, kill_sb를 채워 register_filesystem한다. mount 때 get_tree가 get_tree_nodev/get_tree_bdev 같은 헬퍼로 super_block을 만들고 fill_super에서 s_op, 루트 inode, root dentry를 채운다. 메모리 기반이면 libfs(simple_fill_super 등)로 수십 줄이면 된다.

Fill in a file_system_type with a name, init_fs_context and kill_sb, and call register_filesystem. At mount time get_tree uses a helper like get_tree_nodev or get_tree_bdev to create the super_block and calls your fill_super, which sets s_op and creates the root inode and dentry. For an in-memory filesystem, libfs helpers like simple_fill_super get you there in a few dozen lines.

13. 직접 해보기#

  1. (개념) 같은 파일에 하드 링크 a, b가 있다. open("a"), open("b"), dup()을 하면 file·dentry·inode는 각각 몇 개인가? 정답/힌트: file 2개, dentry 2개, inode 1개. dup은 새 객체를 만들지 않는다.
  1. (코드) f12_vfs에 "동시에 한 번만 열 수 있음" 정책을 넣어라. 두 번째 open은 -EBUSY, release에서 해제. t_open의 두 번째 open이 실패하는지 확인하라. 정답/힌트: static atomic_t busy; open에서 if (atomic_cmpxchg(&busy, 0, 1)) return -EBUSY; release에서 atomic_set(&busy, 0). 실패한 open에서는 release가 안 불리므로 kzalloc 전에 검사한다.
  1. (관찰) function_graph를 vfs_open 대신 __fput에 걸고 t_open을 돌려라. close(fd1) 때는 __fput이 없고 close(fd3) 때 __fput → f12_release가 보이는지 확인하라. 정답/힌트: 6.18의 close()는 file_close_fd → filp_flush(.flush) → fput_close_sync이고, 마지막 참조일 때만 __fput → .release까지 간다. 같은 스레드 안에서 실행되므로 pid 필터에 잡힌다.
  1. (코드) f12fs에 쓰기 가능한 파일 note를 추가하라. write는 64바이트 버퍼에 저장, read는 그 내용을 돌려준다. 모드는 0644. 정답/힌트: tree_descr에 [5] = {"note", &note_fops, 0644}, .write에서 simple_write_to_buffer. 여러 프로세스가 쓰면 mutex가 필요하다.
  1. (관찰) kprobe로 do_dentry_open의 첫 인자에서 f_flags(오프셋 112)를 찍고, cat, echo x >, dd oflag=... 각각의 플래그를 비교하라. 정답/힌트: p:f12/dopen do_dentry_open flags=+112($arg1):x32. O_LARGEFILE(0400000)이 항상 붙는 것을 확인한다. O_CREAT·O_TRUNC는 do_dentry_open 끝에서 지워지므로 진입 시점 값으로 봐야 한다.
  1. (관찰) /proc/sys/fs/dentry-state를 보면서 존재하지 않는 경로 1만 개를 stat 하는 프로그램을 돌려라. 다섯 번째 숫자(nr_negative)가 어떻게 변하나? 정답/힌트: negative dentry가 그만큼 늘어난다. 이 게스트처럼 / 가 tmpfs(rootfs)이면 tmpfs가 negative dentry를 남기는지 먼저 확인하라 — 파일시스템마다 d_delete 정책이 다르다. 결과는 직접 실행해서 확인할 것(이 노트에서는 돌리지 않았다).
  1. (설계) IMU 드라이버의 "샘플링 주파수 설정", "FIFO 데이터", "레지스터 덤프"를 각각 어디로 노출할지 정하고 이유를 한 줄씩 써라. 정답/힌트: sysfs 속성(또는 IIO의 sampling_frequency), char device read(또는 IIO buffer), debugfs.

15. 요약 & 체크리스트#

VFS는 super_block(마운트) · inode(실체) · dentry(이름) · file(열린 세션)이라는 네 객체와 각각의 ops 테이블로 이루어진 다형성 계층이다. open()은 빈 fd를 예약하고, dcache를 RCU-walk로 걸어 dentry/inode를 찾고(없으면 ->lookup), struct file을 만들어 f_op = i_fop로 시작한 뒤 f_op->open을 부르고, 성공하면 fd_install한다. 장치 파일은 i_fop = def_chr_fops라서 chrdev_open이 i_rdev로 cdev를 찾아 f_op를 드라이버 것으로 바꾸고(misc는 한 번 더), 이후 read/ioctl은 그 f_op만 따른다. 같은 장치를 두 번 열면 file 둘·inode 하나, dup·fork는 file을 공유하고, 드라이버의 .release는 마지막 참조에서만 불린다. 파일시스템은 register_filesystem으로 등록되고 mount마다 super_block을 만들며, procfs·sysfs·debugfs·devtmpfs는 디스크 없이 read 시점에 내용을 만드는 pseudo FS다 — 드라이버는 그 API로 파일을 노출한다. 이 모든 것을 6.18.55-dbg 게스트에서 function_graph, function 트레이서, kprobe_events, /proc/sys/fs/dentry-state로 직접 확인했다.
