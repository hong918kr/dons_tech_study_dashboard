0. 큰 그림 — "우리 팀은 어떤 툴체인을 쓰나, 왜?"#

Don이 SSD 펌웨어 팀에 있을 때를 떠올려 보자. 컴파일러는 아마 Arm Compiler나 arm-none-eabi-gcc 특정 버전으로 고정되어 있었고, 그 버전을 바꾸는 일은 "전체 회귀 테스트를 다시 돌리는 이벤트"였다. 바이너리는 하나의 이미지로 링크되어 플래시에 그대로 올라갔다. 컴파일러가 만든 코드가 의존하는 것은 libgcc와 내가 넣은 startup 코드 정도였다.

Embedded Linux에서는 여기에 세 가지 계약이 더 붙는다.

  1. libc 계약: 내 앱은 타깃 rootfs에 있는 libc.so(glibc 또는 musl)를 실행 시점에 불러 쓴다. 빌드할 때 본 libc보다 타깃의 libc가 오래되면 실행이 안 된다.
  2. 커널 계약: 툴체인 안의 커널 헤더(UAPI 헤더, linux/*.h)가 syscall 번호·ioctl 번호·구조체 모양을 정한다. 헤더가 타깃 커널보다 새로우면 "컴파일은 되는데 실행하면 ENOSYS"가 된다.
  3. ABI 계약: float ABI(hard/soft), 명령어 집합(-march), 동적 로더 경로(/lib/ld-linux-armhf.so.3)가 타깃과 맞아야 한다.

그래서 Linux 팀의 툴체인 선택은 "어떤 gcc 버전이 좋나"가 아니라 "우리 타깃 rootfs와 계약이 맞는 툴체인을 어디서 얻나"의 문제다. 선택지는 크게 7가지이고, 위에서 아래로 갈수록 "받아서 그대로 쓰기"에서 "직접 빌드하기"로 옮겨 간다.

그림 1 — 툴체인을 얻는 7가지 길. 초록은 "rootfs와 같은 빌드에서 나와 계약이 자동으로 맞는" 경우, 주황은 "툴체인과 rootfs를 사람이 맞춰야 하는" 경우다.

실무에서 이 선택은 대개 rootfs를 누가 만드느냐로 결정된다.

  • rootfs를 Yocto로 만드는 팀(NXP i.MX8, TI AM62 양산 제품에서 흔함): 앱 개발자는 Yocto가 만든 SDK(5번)를 설치해서 쓴다. 커널·부트로더도 같은 툴체인으로 빌드된다.
  • rootfs가 Ubuntu 계열인 팀(NVIDIA Jetson의 L4T가 대표적): 앱은 보드에서 직접(native) 빌드하거나, 같은 Ubuntu 버전의 배포판 크로스 패키지(1번) 또는 Docker 안의 sysroot로 빌드한다. 커널은 벤더가 지정한 툴체인(4번)으로 크로스 빌드한다.
  • rootfs를 Buildroot로 만드는 팀(작은 장비, 부팅 시간·크기 중시): Buildroot가 툴체인을 직접 빌드(7번)하거나 Bootlin 툴체인(3번)을 external로 가져다 쓴다.
  • 특수 요구가 있는 팀(오래된 커널·특정 gcc 버전·특이 아키텍처): crosstool-NG(6번)로 직접 만든다.

이 노트는 각 출처를 실제로 받아 보고, 뜯어 보고, 빌드해 보고, 일부러 깨뜨려 본다.

실행 환경: 모든 출력은 Lima VM elinux(aarch64, uname -r = 7.0.0-34-generic, Ubuntu 26.04, gcc 15.2, Apple Silicon 위 가상화, 4 vCPU를 다른 작업과 공유)에서 실제로 돌린 결과다. 32-bit ARM 바이너리는 qemu-arm(QEMU 10.2.1 user mode)으로 실행했다. PID·시간·해시는 실행마다 다르다.

1. 툴체인을 뜯어 보면 — 4개 부품 + sysroot#

1.1 직관 — "컴파일러 한 개"가 아니라 "타깃 rootfs의 축소판 + 도구 상자"#

B1에서 본 것처럼 크로스 툴체인은 gcc 하나가 아니다. 다음 다섯 덩어리가 한 디렉터리에 묶인 것이다.

부품어디서 실행되나하는 일버전이 틀리면
binutils (as, ld, objcopy, readelf)호스트어셈블·링크·ELF 조작새 명령어를 어셈블 못 함, 링커 옵션 차이
gcc (gcc 드라이버 + cc1 + collect2 + lto1)호스트C → 어셈블리, 기본 -march/-mfpu/float ABI 결정코드 생성 차이, 기본 CPU가 타깃보다 높으면 SIGILL
C 라이브러리 (glibc / musl / uClibc-ng)타깃 (sysroot에 사본)printf, pthread, syscall 래퍼, 동적 로더GLIBC_2.xx not found, 로더 없음

여기서 sysroot(타깃 루트 파일시스템의 개발용 사본 — 헤더·.so·crt1.o가 들어 있는 디렉터리)가 핵심이다. 컴파일러는 #include <stdio.h>를 호스트 /usr/include가 아니라 <sysroot>/usr/include에서 찾고, 링커는 -lc를 <sysroot>/lib에서 찾는다. bare-metal에 비유하면 "벤더가 준 CMSIS 헤더 + 링커 스크립트 + startup 코드 묶음"이 타깃 OS 전체로 커진 것이다.

1.2 triplet 이름 읽기 — vendor 칸은 장식이다#

같은 "32-bit ARM, Linux, hard-float" 타깃이라도 출처마다 이름이 다르다.

출처triplet (prefix)해석

Arm GNU Toolchainarm-none-linux-gnueabihfvendor = none

crosstool-NG 샘플arm-unknown-linux-musleabivendor = unknown, musl, soft-float ABI

vendor 칸(buildroot, none, unknown, poky)은 이름일 뿐 ABI에 영향이 없다. 중요한 것은 마지막 칸(gnueabihf, musleabi, gnu)이 말하는 libc와 float ABI다. 그리고 Yocto처럼 triplet이 gnueabi인데 실제로는 -mfloat-abi=hard 옵션으로 hard-float를 쓰는 경우도 있으니, 이름을 믿지 말고 §3의 방법으로 직접 확인한다.

2.1 배포판 패키지 — gcc-arm-linux-gnueabihf#

가장 쉬운 길이다. Ubuntu/Debian에서 apt install gcc-arm-linux-gnueabihf(64-bit면 gcc-aarch64-linux-gnu) 한 줄이면 된다. 이 VM에는 이미 깔려 있다. 어떤 패키지들이 무엇을 들고 오는지 보자.

무엇을 확인하나: 배포판 크로스 툴체인의 구성 패키지와 각 버전.

출력에서 볼 것: 툴체인이 네 개의 배포판 패키지(gcc, binutils, libc6-dev-armhf-cross = glibc 2.43, linux-libc-dev-armhf-cross = 커널 7.0 헤더)로 쪼개져 있다. 그리고 sysroot는 /usr/arm-linux-gnueabihf/다. 즉 이 툴체인이 만든 바이너리는 "Ubuntu 26.04 armhf rootfs"를 가정한다. 타깃이 Ubuntu 26.04 armhf면 완벽하고, 그보다 오래된 glibc를 가진 보드면 §4.1처럼 깨진다.

장점은 설치가 쉽고 보안 업데이트가 배포판을 따라온다는 것, 단점은 버전을 고를 수 없다는 것이다. 호스트를 Ubuntu 24.04에서 26.04로 올리는 순간 gcc와 glibc가 함께 바뀐다. 그래서 팀 단위로는 "빌드는 특정 Ubuntu 버전의 Docker 이미지 안에서"로 고정하는 것이 보통이다(§7).

2.2 Arm GNU Toolchain — Linaro 바이너리의 후계#

Arm이 직접 빌드해 배포하는 GCC 툴체인이다. 예전에는 Linaro가 gcc-linaro-7.5.0-2019.12-... 같은 이름으로 바이너리를 냈는데, 이후 Arm이 "GNU Toolchain for the A-profile Architecture"로 이어받았고 지금은 Arm GNU Toolchain이라는 이름으로 developer.arm.com에서 받는다. 오래된 BSP 문서에서 "Linaro 툴체인을 받으세요"라는 문장을 보면 지금은 이것을 뜻한다고 생각하면 된다.

파일 이름 규칙은 arm-gnu-toolchain-<버전>-<호스트>-<타깃>.tar.xz다. 실제로 어떤 조합이 있는지 HEAD 요청으로 확인했다(받지는 않았다).

출력에서 볼 것:

  • 버전 이름은 <gcc 메이저>.<마이너>.rel<N> 형식이고, 모든 gcc 릴리스마다 나오는 것은 아니다(15.1은 없다). 2026-10-10에 위 후보들을 찔러 본 범위에서 가장 새 것은 15.2.rel1이었다(목록에 없는 버전은 확인하지 않았다).
  • 같은 페이지에 .sha256asc 체크섬 파일이 있다. 받은 뒤 sha256sum -c로 검증하는 것이 기본이다.
  • 호스트가 x86_64와 aarch64 둘 다 있다. Apple Silicon 위 Linux VM이나 Jetson 같은 arm64 호스트에서도 네이티브로 돈다는 뜻이다. 이것이 §2.3의 Bootlin과 다른 점이다.
  • 타깃은 Linux용(aarch64-none-linux-gnu, arm-none-linux-gnueabihf)과 bare-metal용(arm-none-eabi, aarch64-none-elf)이 한 사이트에 있다. Don이 펌웨어에서 쓰던 arm-none-eabi-gcc가 바로 여기서 나온다.

Arm GNU Toolchain은 커널·U-Boot·TF-A처럼 libc를 쓰지 않는 코드를 빌드할 때 특히 무난하다. 유저스페이스 앱에 쓸 때는 번들된 glibc 버전이 타깃 rootfs보다 새롭지 않은지 §3 방법으로 꼭 확인한다(이 노트에서는 받지 않았으므로 번들 glibc 버전은 확인하지 않았다).

2.3 Bootlin prebuilt — 아키텍처 × libc × 안정도를 고르는 카탈로그#

Bootlin(프랑스의 임베디드 Linux 교육·컨설팅 회사, elixir.bootlin.com 운영)은 Buildroot로 수백 개의 툴체인을 빌드해 toolchains.bootlin.com에 공개한다. 장점은 libc 종류(glibc/musl/uClibc-ng)와 안정도(stable/bleeding-edge)를 골라서 받을 수 있다는 것이다. 페이지에 박혀 있는 JSON을 파싱해서 최신 릴리스의 조합을 세어 보자.

무엇을 확인하나: Bootlin 카탈로그의 최신 릴리스(2026.08-1)가 몇 개 툴체인을 내는지, 각 툴체인의 부품 버전.

출력에서 볼 것:

  • 한 릴리스에 218개 툴체인(43개 아키텍처 변형 × 최대 3 libc × 2 안정도)이 있다.
  • stable은 한 단계 앞의 gcc(15.3) + 오래된 커널 헤더(5.10), bleeding-edge는 최신 gcc(16.2) + 새 헤더(6.12)다. stable의 헤더가 5.10인 것은 의도된 선택이다. 커널 헤더는 "타깃 커널보다 오래되면 안전"하므로(§4.3), 헤더를 낮게 잡아 두면 5.10 이상인 거의 모든 보드에서 쓸 수 있다.
  • glibc 버전은 2.44 릴리스 브랜치의 git 스냅샷(2.44-36-g...)이다.

이제 실제로 하나 받아 보자. 크기가 작은 armv7-eabihf--musl--stable(81 MB)을 고른다.

무엇을 확인하나: 다운로드 + sha256 검증. 파일 이름과 체크섬 URL은 위 JSON의 tarball-name과 같은 규칙이다.

출력에서 볼 것: OK가 나와야 다음 단계로 간다. 팀 스크립트에서는 이 해시 값을 저장소에 박아 두고(sha256sum -c가 실패하면 빌드 중단) 다운로드 서버가 바뀌거나 파일이 교체되는 것을 막는다(§7).

압축을 풀고 안을 들여다보자.

무엇을 확인하나: 툴체인 tarball의 디렉터리 구조와 크기, 그리고 컴파일러가 어떤 CPU에서 도는 프로그램인지.

(실제로는 ls와 du를 나눠 실행했고 출력은 순서대로 이어 붙였다.)

출력에서 볼 것:

  • 81 MB tarball이 풀면 381 MB다. 가장 큰 것은 libexec(111 MB — cc1 하나가 35 MB)와 lib(96 MB — gdb용 Python 3.14 포함)다. 타깃으로 가는 것(sysroot)은 36 MB뿐이다.
  • arm-buildroot-linux-musleabihf/bin/에 prefix 없는 as, ld가 또 있다. gcc 드라이버가 내부적으로 부르는 사본이다.
  • gcc가 x86-64 프로그램이다. 이 VM은 aarch64라서 그대로는 실행되지 않는다. Bootlin 툴체인은 x86_64 호스트용으로 빌드되어 있다(적어도 이 tarball은 그렇다). Apple Silicon Mac이나 arm64 빌드 서버를 쓰는 팀이 실제로 부딪히는 문제다.

이 VM에서는 해결책으로 qemu-user가 x86-64 프로그램을 에뮬레이션하게 했다. binfmt_misc에 qemu-x86_64가 이미 등록되어 있으니, x86-64용 glibc 런타임만 따로 풀어 주면 된다(apt install이 아니라 .deb를 받아 dpkg-deb -x로 /tmp/B5/x86root에 풀었다).

(실제로는 .deb 받기·풀기와 심볼릭 링크 만들기를 두 번에 나눠 실행했고, 출력은 그대로 이었다.)

출력에서 볼 것: 커널이 ELF 헤더의 machine 필드(3e00 = x86-64)를 보고 qemu-x86_64를 끼워 실행한다. QEMU_LD_PREFIX는 qemu가 /lib64/ld-linux-x86-64.so.2 같은 경로를 찾을 때 앞에 붙이는 루트다. 이제 x86-64 gcc가 aarch64 VM에서 armv7 코드를 만든다 — 에뮬레이션 위의 크로스 컴파일이다. 단 느리다(§7.3에서 약 11배로 측정).

2.4 툴체인 tarball 해부도#

그림 2 — Bootlin 툴체인 tarball 해부도(크기는 위 du 실측). 파랑은 호스트에서 실행되는 것, 초록은 타깃으로 가거나 타깃 코드에 링크되는 것, 주황은 재현·이동용 메타데이터다. 381 MB 중 타깃 쪽은 36 MB뿐이다.

Buildroot 계열 툴체인은 arm-...-gcc가 진짜 gcc가 아니라 toolchain-wrapper라는 작은 프로그램이다. 래퍼는 --sysroot와 Buildroot가 정한 보안 플래그를 덧붙여 gcc.br_real을 부른다. 환경 변수 BR2_DEBUG_WRAPPER=1을 주면 실제로 무엇을 붙이는지 보여 준다.

무엇을 확인하나: 래퍼가 내 명령에 몰래 덧붙이는 옵션.

출력에서 볼 것:

  • 래퍼가 자기 위치 기준으로 계산한 --sysroot를 붙인다. 그래서 tarball을 어느 디렉터리에 풀어도 동작한다(relocatable).
  • -fstack-protector-strong -fPIE -pie -Wl,-z,now -Wl,-z,relro가 기본으로 들어간다. 이 툴체인으로 만든 바이너리는 내가 지정하지 않아도 PIE + stack protector다. "왜 내 바이너리 크기·성능이 배포판 gcc와 다르지?"의 답이 여기 있을 수 있다.
  • arm-linux-gcc라는 짧은 이름도 같은 래퍼다. 오래된 Makefile이 CROSS_COMPILE=arm-linux-를 가정할 때 쓴다.

Don의 경험과 연결: 펌웨어 팀에서 "컴파일러가 몰래 넣는 옵션"은 보통 IDE 프로젝트 설정에 숨어 있었다. Linux에서는 래퍼(Buildroot), 스펙 파일(gcc -dumpspecs), 환경 변수(CC에 붙은 옵션, Yocto)에 숨어 있다. 바이너리가 이상하면 실제로 실행된 명령줄부터 확인한다(-v, BR2_DEBUG_WRAPPER=1, make V=1).

2.5 Buildroot — internal 툴체인 vs external 툴체인#

Buildroot(K 모듈에서 자세히)는 rootfs 이미지를 만드는 빌드 시스템인데, 툴체인을 두 방식으로 다룬다.

방식설정동작장단점
internal (Buildroot toolchain)BR2_TOOLCHAIN_BUILDROOT=ybinutils·gcc·libc를 소스에서 빌드한 뒤 패키지 빌드 시작버전·옵션 완전 통제 / 첫 빌드가 수십 분 더 걸림
external (미리 빌드된 것)BR2_TOOLCHAIN_EXTERNAL=y + BR2_TOOLCHAIN_EXTERNAL_BOOTLIN 또는 ..._CUSTOM지정한 tarball을 풀고 libc .so를 rootfs로 복사빠름 / 툴체인의 libc·헤더 버전을 받아들여야 함

external을 쓸 때 Buildroot는 "이 툴체인의 libc는 glibc인가 musl인가, 커널 헤더는 몇 버전인가, C++/스레드를 지원하나"를 설정으로 알려 달라고 하고, 빌드 시작 때 실제 툴체인과 대조해서 틀리면 멈춘다. §3의 "신원 조회"를 Buildroot가 자동으로 하는 셈이다.

그리고 Buildroot는 make sdk로 자기가 쓴 툴체인 + 지금 만든 rootfs의 sysroot를 하나의 relocatable tarball로 묶어 준다. Bootlin 툴체인의 README.txt가 바로 그 과정이다.

(위는 tarball 안 README.txt의 일부를 그대로 옮긴 것이다.) 즉 Bootlin 툴체인 = "rootfs 없이 툴체인만 만드는 Buildroot 설정"으로 make sdk를 한 결과물이고, relocate-sdk.sh도 그 SDK 기능에서 온다. 재현 방법(git 태그 + defconfig)까지 적혀 있다는 점이 §7의 재현성 이야기와 이어진다.

3. 처음 보는 툴체인 "신원 조회" — 5분 체크리스트#

3.1 무엇을 알아내야 하나#

인수인계받은 프로젝트에 toolchain/ 디렉터리가 있다. 이것이 무엇인지 알려면 다음 여섯 가지를 확인한다.

  1. triplet — gcc -dumpmachine
  2. gcc 버전 — gcc -dumpfullversion
  3. sysroot 위치 — gcc -print-sysroot
  4. configure 플래그 — gcc -v의 Configured with: 줄. 특히 --with-arch, --with-cpu, --with-fpu, --with-float, --with-sysroot
  5. 기본 타깃 옵션 — gcc -Q --help=target의 -march=, -mcpu=, -mfpu=, -mfloat-abi=
  6. libc 종류·버전과 커널 헤더 버전 — sysroot의 linux/version.h, features.h, 그리고 libc를 직접 실행

3.2 스크립트로 만들기#

무엇을 확인하나: 위 여섯 가지를 한 번에 뽑는 스크립트를 Bootlin 툴체인과 Ubuntu 배포판 툴체인에 각각 돌린다.

출력에서 볼 것 — 두 툴체인은 "armv7 hard-float"라는 겉모습은 같지만 속은 꽤 다르다.

항목Bootlin armv7-eabihf muslUbuntu arm-linux-gnueabihf

FPUvfpv3-d16 (D0~D15만 사용)auto (+fp = VFPv3-D16 상당)

그리고 두 가지 함정이 숨어 있다.

  • --with-sysroot가 빌드 서버 경로(/builds/buildroot.org/...)다. 이 경로는 우리 머신에 없다. 그런데도 동작하는 것은 §2.4의 래퍼가 --sysroot를 덮어 주기 때문이다. 래퍼 없이 gcc.br_real을 직접 부르면 헤더를 못 찾는다.
  • 커널 헤더가 5.10.255로 나오지만 실제는 5.10.269다(JSON 요약 참고). LINUX_VERSION_CODE는 (major << 16) + (minor << 8) + sublevel인데 sublevel이 8비트라서, 4.4.256 / 4.9.256 stable 릴리스에서 오버플로 문제가 생긴 뒤로 커널이 sublevel을 255로 고정(clamp)해서 넣는다. LINUX_VERSION_CODE로는 255 이상의 stable 버전을 구분할 수 없다는 것을 알아 두자.

툴체인 하나로 armv7 CPU 전부를 지원하는 것은 아니다. Bootlin의 기본 -mcpu=cortex-a9는 Cortex-A7/A8/A9/A15 계열에서 대부분 돌지만, NEON이 없는 Cortex-A9 변형(예: 일부 저가 SoC)이나 VFPv3-D16조차 없는 코어에서는 -mfpu를 다시 지정해야 한다. 기본값을 확인하는 이유가 이것이다.

3.3 실제로 빌드하고 실행하기 — sysroot와 동적 로더#

무엇을 확인하나: 툴체인이 정한 값(컴파일 타임 매크로)과 타깃이 정한 값(런타임 uname)을 한 프로그램에서 같이 찍는다.

출력에서 볼 것:

  • 바이너리는 "내 로더는 /lib/ld-musl-armhf.so.1이다"라고 ELF의 PT_INTERP에 적어 둔다(B3). 그 파일이 없으면 커널이(여기서는 qemu가) 실행 자체를 못 한다. 보드에서는 이것이 그 유명한 -sh: ./app: not found(파일이 있는데 not found) 증상이다.
  • qemu-arm -L <sysroot>는 "이 디렉터리를 타깃의 /로 생각하라"는 뜻이다. sysroot = 타깃 rootfs의 축소판이라는 말이 문자 그대로 성립한다.
  • 런타임 uname은 7.0.0-34-generic armv7l이다. qemu-user는 syscall을 호스트 커널로 넘기고 machine 이름만 armv7l로 바꿔 보여 준다. 즉 "빌드는 5.10 헤더로, 실행은 7.0 커널에서" — 헤더 ≤ 커널이므로 안전한 조합이다.

4. 툴체인 ↔ 타깃 rootfs 호환 규칙 — 일부러 깨뜨려 보기#

4.1 직관 — "빌드 때 본 것"은 "실행 때 있는 것"보다 새로우면 안 된다#

그림 3 — 툴체인과 타깃 사이의 여섯 가지 계약. 왼쪽이 빌드 때 툴체인이 정한 것, 오른쪽이 실행 때 타깃이 가진 것이다. 빨강은 이 노트에서 실제로 재현했거나(1, 3행 — §4.2, §5) 실무에서 자주 보는 실패 증상이다.

규칙을 한 줄로 줄이면 "빌드 때 본 것 ≤ 실행 때 있는 것, 종류(ABI·libc)는 같게"다. bare-metal에서 "새 HAL 헤더로 빌드했는데 ROM에 구 버전 함수가 박혀 있어 hard fault" 같은 상황과 같은 구조다. 다만 Linux에서는 그 "ROM"이 rootfs의 .so 파일들과 커널이라서, 보드마다·이미지 버전마다 다르다는 것이 차이다.

4.2 glibc가 오래된 rootfs — GLIBC_2.34 not found 재현#

glibc는 심볼 버전(symbol versioning)을 쓴다. 함수마다 "이 동작은 glibc 2.34부터"라는 태그(GLIBC_2.34)가 붙고, 링크할 때 바이너리에 "나는 __libc_start_main@GLIBC_2.34가 필요하다"가 기록된다. 실행 때 타깃 glibc가 그 태그를 모르면 로더가 거부한다. 그래서 새 glibc로 빌드한 바이너리는 옛 glibc에서 돌지 않지만, 그 반대는 된다(backward compatible).

무엇을 확인하나: Ubuntu 26.04 크로스 gcc(glibc 2.43)로 만든 바이너리가 요구하는 glibc 버전, 그리고 glibc 2.31 rootfs(Ubuntu 20.04의 armhf libc6를 /tmp/B5/oldroot에 풀어서 흉내)에서의 실행 결과.

출력에서 볼 것:

  • 가장 단순한 hello 프로그램도 GLIBC_2.34를 요구한다. glibc 2.34에서 프로그램 시작 코드(crt1.o가 부르는 방식)가 바뀌며 __libc_start_main에 새 심볼 버전이 생겼고, 새 glibc로 링크하면 그 버전에 묶이기 때문이다. 즉 "Ubuntu 22.04(glibc 2.35) 이상에서 빌드한 바이너리는 Ubuntu 20.04(glibc 2.31) 기반 rootfs에서 거의 다 안 돈다". 예를 들어 Ubuntu 20.04 기반 Jetson 이미지에 새 PC에서 크로스 빌드한 앱을 올리면 바로 이 메시지를 본다.
  • -static으로 링크하면 libc가 바이너리 안에 들어가므로 rootfs의 glibc와 무관하게 돈다. 하지만 glibc static은 getaddrinfo·NSS·dlopen에서 경고나 제약이 있고 크기가 크다(아래). 근본 해결은 타깃과 같은(또는 더 오래된) glibc를 가진 sysroot로 빌드하는 것이다 — Yocto SDK나 벤더 SDK를 쓰는 이유다.

무엇을 확인하나: 같은 소스의 동적/정적 × glibc/musl 크기.

출력에서 볼 것:

  • musl static은 40 KB, glibc static은 490 KB. "그냥 static으로 빌드해서 libc 문제를 피하자"는 전략은 musl에서 특히 매력적이다. 컨테이너 없는 작은 장비의 진단 도구를 musl static으로 배포하는 팀이 많은 이유다.
  • 동적 바이너리 파일 크기 차이(69 KB vs 7.5 KB)는 코드 차이가 아니다(text 2048 vs 2355 바이트). Ubuntu 툴체인은 LOAD 세그먼트를 64 KB 정렬(0x10000, 64K 페이지 커널 대비)로 링크해서 파일에 패딩이 들어가고, Bootlin은 4 KB 정렬이다. 툴체인마다 링커 기본값도 다르다는 예다.

무엇을 확인하나: 두 동적 바이너리의 LOAD 세그먼트 정렬.

4.3 커널 헤더 — "헤더 ≤ 커널"과 musl의 함정#

커널 헤더는 syscall 번호, ioctl 번호, 구조체 레이아웃을 정한다. 리눅스 커널은 유저 ABI를 깨지 않는다(새 syscall·필드는 추가만 한다)는 원칙을 지키므로,

  • 헤더가 커널보다 오래되면: 새 기능을 못 쓸 뿐 안전하다. → Bootlin stable이 5.10 헤더를 쓰는 이유.
  • 헤더가 커널보다 새로우면: 새 syscall이 컴파일은 되지만, 실행하면 옛 커널이 그 번호를 모르므로 -ENOSYS(Function not implemented)가 돌아온다. 새 ioctl 구조체 필드도 옛 드라이버가 무시하거나 -EINVAL/-ENOTTY를 준다.

무엇을 확인하나: syscall을 번호로 직접 불러서 "커널이 아는 번호"와 "모르는 번호"의 반응 차이를 본다. 그리고 툴체인마다 같은 번호가 헤더에 있는지 본다.

출력에서 볼 것 — 예상과 다른 점이 두 가지 있어서 오히려 좋은 공부거리다.

  • 5.10 헤더인 Bootlin 툴체인에서도 __NR_cachestat(6.5에서 추가)이 정의되어 있다. 이유: musl은 syscall 번호를 커널 헤더(asm/unistd.h)에서 가져오지 않고 자기 소스(arch/arm/bits/syscall.h.in)에 직접 들고 있다. 그래서 musl 1.2.6이 아는 syscall이면 커널 헤더 버전과 무관하게 <sys/syscall.h>에 나온다. glibc는 반대로 커널 헤더의 번호를 쓴다. "커널 헤더 버전 = 쓸 수 있는 syscall 목록"이라는 등식은 glibc에서만 대략 맞다.
  • cachestat은 두 바이너리 모두 ENOSYS가 나왔다. 호스트 커널은 7.0이라 cachestat을 지원하지만, 여기서는 qemu-user(10.2.1)가 커널 역할을 하면서 이 syscall을 번역하지 못해 ENOSYS를 돌려준 것이다. 결과적으로 "헤더(또는 libc)는 아는데 실행 환경이 모르는 syscall → ENOSYS"라는 상황을 정확히 재현했다. 실제 보드에서는 옛 커널이 같은 역할을 한다.
  • 존재하지 않는 번호(999)도 같은 ENOSYS다. 커널 입장에서 "모르는 syscall"은 전부 sys_ni_syscall로 간다(§8).
  • statx는 커널이 아는 syscall이므로 잘못된 인자에 EFAULT(Bad address)로 반응했다. ENOSYS냐 다른 errno냐가 "커널이 이 기능을 아는가"를 판별하는 방법이다. 새 syscall을 쓰는 코드는 ENOSYS일 때 옛 방식으로 돌아가는 fallback을 둬야 한다(glibc의 statx → fstatat fallback이 그 예).
  • 첫 줄의 errno=0 (No error information) vs (Success)는 musl과 glibc의 strerror(0) 문자열 차이다. 이런 작은 차이도 libc가 바뀌면 로그 파서를 깨뜨릴 수 있다.

4.4 ABI와 CPU — float ABI, -march, 로더 이름#

32-bit ARM에는 float ABI가 세 가지 있다.

-mfloat-abiFPU 명령 사용함수 인자로 float 전달로더 (glibc)로더 (musl)
soft안 씀 (라이브러리 호출)정수 레지스터/lib/ld-linux.so.3/lib/ld-musl-arm.so.1
softfp씀정수 레지스터 (soft와 호환)/lib/ld-linux.so.3/lib/ld-musl-arm.so.1
hard씀VFP 레지스터 (s0, d0)/lib/ld-linux-armhf.so.3/lib/ld-musl-armhf.so.1

hard와 soft는 함수 호출 규약이 달라서 섞어 링크할 수 없고, 그래서 로더 이름까지 다르다. armhf rootfs에 soft-float 바이너리를 올리면 로더가 없어서 not found가 나온다. §5에서 crosstool-NG 샘플(arm-unknown-linux-musleabi, soft-float)로 만든 바이너리로 이것을 직접 확인한다.

aarch64는 float ABI가 하나뿐이라 이 문제는 없다. 대신 -march/-mcpu가 타깃보다 높으면 문제가 된다. 예를 들어 Cortex-A76용(-mcpu=cortex-a76, ARMv8.2)으로 빌드한 코드가 LSE atomics나 dot-product 명령을 쓰면, Cortex-A53(ARMv8.0) 보드에서는 그 명령을 만나는 순간 SIGILL로 죽는다. 툴체인의 기본값이 무엇인지(§3.2의 -Q --help=target) 확인하는 이유다.

5. crosstool-NG — 툴체인을 직접 빌드해 보기#

5.1 직관 — "툴체인 = 닭과 달걀 문제를 단계로 푸는 빌드"#

gcc를 타깃용으로 빌드하려면 타깃 libc가 필요하고(crt1.o, libc.so에 링크하는 libgcc_s), libc를 빌드하려면 타깃용 gcc가 필요하다. 닭과 달걀이다. 툴체인 빌더는 이것을 단계로 푼다.

  1. 호스트 도우미 라이브러리(gmp, mpfr, isl, mpc, zlib, zstd) — gcc가 호스트에서 쓰는 수학·압축 라이브러리
  2. binutils — 타깃용 as, ld
  3. 커널 헤더 — make headers_install (§8.1)
  4. core gcc (pass 1) — libc 없이 C만 컴파일할 수 있는 최소 gcc (--without-headers, libgcc.a만)
  5. C 라이브러리 — 4번 gcc로 musl/glibc를 빌드해 sysroot에 설치
  6. final gcc — 이제 libc가 있으니 완전한 gcc(+ libgcc_s, 선택한 언어 런타임)
  7. 마무리 — strip, 심볼릭 링크, 설정 파일 저장

bare-metal 비유: 부트로더를 만들려면 부트로더가 필요한 상황에서, ROM 코드 → 1차 로더 → 2차 로더로 단계를 쌓는 것과 같은 구조다.

5.2 crosstool-NG 설치와 샘플 고르기#

crosstool-NG는 그 자체도 소스에서 설치한다(대부분 셸 스크립트 + Kconfig라 빠르다). 릴리스 tarball과 sha512를 받아 검증한다.

5.5 만든 툴체인 써 보기 — 그리고 soft-float의 함정#

무엇을 확인하나: §3의 신원 조회 스크립트로 방금 만든 툴체인을 확인한다.

(file과 du는 따로 실행한 결과를 이어 붙였다.)

출력에서 볼 것:

  • 이 툴체인의 gcc는 aarch64 호스트용이다(file 출력의 ELF 64-bit LSB executable, ARM — 64-bit ARM = aarch64, 뒤는 cut으로 잘랐다). 내가 빌드한 머신에서 네이티브로 돈다 — Bootlin의 x86-64 문제(§2.3)가 없다. 이것이 crosstool-NG를 쓰는 실용적 이유 중 하나다.
  • 기본값이 -march=armv5t, -mfloat-abi=soft다. 샘플이 CPU를 지정하지 않아(CT_ARCH_CPU="", CT_ARCH_FLOAT="auto") gcc의 ARM 기본값(ARMv5T, soft-float)이 그대로 들어왔다. 거의 모든 32-bit ARM에서 돌지만 FPU를 안 쓴다. 샘플 이름만 보고 쓰면 이런 기본값을 놓친다.
  • 커널 헤더는 우리가 고른 6.1.175, --with-sysroot가 실제 설치 경로(/tmp/B5/x-tools/...)다. Buildroot 래퍼가 없으므로 이 툴체인을 다른 경로로 옮기면 sysroot 경로가 어긋날 수 있다(ct-ng 툴체인도 대부분 relocatable하게 동작하지만, 확인이 필요하다).
  • 전체 약 210 MB로 Bootlin(381 MB)보다 작다. C++·gdb·Python을 뺐기 때문이다.

무엇을 확인하나: soft-float 툴체인으로 만든 바이너리, 그리고 hard-float로 바꾸려고 할 때 일어나는 일.

출력에서 볼 것:

  • 로더 이름이 /lib/ld-musl-arm.so.1(soft)이다. Bootlin 것은 ld-musl-armhf.so.1(hard)이었다. §4.4 표 그대로다.
  • -mfloat-abi=hard를 명령줄에서 주면 내 오브젝트는 hard, 툴체인의 musl·crt 파일은 soft라서 링커가 "uses VFP register arguments, ... does not"로 거부한다. float ABI는 옵션 하나로 바꿀 수 있는 것이 아니라 툴체인(정확히는 sysroot의 libc) 전체의 속성이다. hard-float가 필요하면 ct-ng 설정에서 CT_ARCH_FLOAT_HW/CT_ARCH_ARCH/CT_ARCH_FPU를 정해 다시 빌드하거나 arm-...-musleabihf 툴체인을 쓴다.

무엇을 확인하나: 두 ABI의 바이너리를 서로의 sysroot(= 서로 다른 rootfs)에서 실행.

(실제로는 Bootlin tarball을 다시 받아 sha256 확인 후 풀고 hello_bootlin을 다시 빌드한 뒤 실행했다.)

출력에서 볼 것: 같은 musl 1.2.6, 같은 32-bit ARM인데도 float ABI가 다르면 서로의 rootfs에서 시작조차 못 한다. 보드 셸에서는 -sh: ./hello_ctng: not found로 보인다(그림 3의 3행).

출력에서 볼 것: CPU(BR2_cortex_a9), float ABI(BR2_ARM_EABIHF), libc(MUSL), 커널 헤더(5_10) 네 줄이 §3.2에서 조회한 신원과 정확히 대응한다. init·셸·busybox·rootfs 이미지는 꺼서 "rootfs 없이 툴체인만" 만든다. 즉 crosstool-NG와 Buildroot internal 툴체인은 같은 일을 하는 두 도구이고, 차이는 Buildroot는 그 툴체인으로 곧바로 rootfs까지 만든다는 것이다.

Yocto SDK를 설치하고 source environment-setup-...을 하면, 그 셸에서는 평범한 make, cmake, ./configure가 갑자기 ARM용 바이너리를 만든다. 마법이 아니라 환경 변수다. 빌드 시스템들은 원래 CC, CFLAGS, PKG_CONFIG_PATH 같은 변수를 읽도록 약속되어 있고, SDK 스크립트는 그 변수들을 타깃용으로 채워 줄 뿐이다.

그림 5 — environment-setup 스크립트의 정체. 변수를 export할 뿐이고, 각 빌드 도구가 약속된 변수를 읽어 크로스 빌드로 바뀐다.

6.2 스크립트 직접 쓰기#

Yocto SDK 대신 §2.3의 Bootlin 툴체인을 쓰되, 타깃 sysroot를 따로 복사해서 "우리 이미지의 sysroot"처럼 쓴다(/tmp/B5/sdk-sysroot). 여기에 "벤더가 준 센서 라이브러리" 역할의 libimu를 설치해서 pkg-config까지 확인한다.

CMake용 툴체인 파일은 Yocto SDK의 OEToolchainConfig.cmake에 해당한다.

"벤더 라이브러리" libimu(헤더, 소스, .pc)는 다음과 같다.

.pc 파일의 prefix=/usr가 포인트다. 이 파일은 타깃 기준 경로로 쓰여 있다(보드에서 라이브러리는 /usr/lib에 있으니까). 호스트에서 크로스 빌드할 때 pkg-config가 그 앞에 sysroot를 붙여 주는 것이 PKG_CONFIG_SYSROOT_DIR의 역할이다.

무엇을 확인하나: sysroot 사본에 libimu를 크로스 빌드해서 설치하고, SDK 환경과 일반 환경에서 pkg-config 결과를 비교한다.

출력에서 볼 것: .pc 안에는 /usr/include/imu라고 적혀 있지만 pkg-config가 /tmp/B5/sdk-sysroot를 앞에 붙여서 돌려준다. SDK 변수가 없으면 호스트 경로만 뒤지므로 못 찾는다. 반대로 더 위험한 경우는 호스트에도 같은 이름의 .pc가 있을 때다. PKG_CONFIG_LIBDIR로 호스트 기본 경로를 막지 않으면 호스트(aarch64 또는 x86)용 -L/usr/lib/...가 섞여 들어가 "file in wrong format" 링크 에러가 난다.

6.3 Make 프로젝트 — 크로스를 모르는 Makefile#

앱 소스(main.c, filter.c, filter.h)와 Makefile은 크로스 빌드에 대해 아무것도 모른다. CC, CFLAGS, LDFLAGS, PKG_CONFIG를 환경에서 받을 뿐이다. 이것이 좋은 Makefile의 조건이다(B4).

(filter.h와 filter.c는 실제로는 두 파일이다. 지면을 아끼려고 한 블록에 붙였다.)

무엇을 확인하나: source 한 번으로 평범한 make가 ARM 바이너리를 만들고, 그 바이너리가 sysroot의 libimu를 물고 실행되는지.

출력에서 볼 것:

  • Makefile에는 arm이라는 글자가 하나도 없는데, 실행된 명령은 전부 arm-buildroot-linux-musleabihf-gcc ... --sysroot=...이다. 크로스 빌드의 책임이 Makefile이 아니라 환경에 있다.
  • NEEDED에 libimu.so.1(우리가 준 soname)과 libc.so(musl의 libc 이름)가 들어갔다. 보드 rootfs에 libimu.so.1이 없으면 실행이 안 된다 — 그래서 Yocto는 "앱 레시피의 RDEPENDS"로 그 라이브러리를 이미지에 함께 넣는다.
  • -lm이 링크 명령에 있는데 NEEDED에 libm이 없다. musl은 libm이 libc 안에 들어 있고, --as-needed가 필요 없는 의존성을 빼 준다.

6.4 CMake 프로젝트 — 환경 변수 CMAKE_TOOLCHAIN_FILE#

무엇을 확인하나: -DCMAKE_TOOLCHAIN_FILE=...을 명령줄에 쓰지 않아도 환경 변수만으로 CMake가 크로스 설정을 잡는지.

출력에서 볼 것:

  • "Check for working C compiler ... skipped": 크로스 모드라서 CMake가 테스트 프로그램을 실행하지 않는다(CMAKE_SYSTEM_NAME을 지정하면 CMAKE_CROSSCOMPILING이 켜진다). try_run()을 쓰는 오래된 CMake 프로젝트가 크로스에서 깨지는 이유다.
  • C_FLAGS 앞부분 -O2 -pipe -g는 환경 변수 CFLAGS에서 왔고, -mcpu...는 툴체인 파일의 CMAKE_C_FLAGS_INIT에서 왔다. --sysroot는 CMAKE_SYSROOT에서 왔다. 세 경로가 합쳐진 것이다.
  • pkg-config가 찾은 libimu.so가 sysroot 안의 절대 경로로 링크된다. CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY가 호스트 /usr/lib를 막는다.

함정 메모: CMake는 CC·CFLAGS·CMAKE_TOOLCHAIN_FILE 환경 변수를 첫 configure 때만 읽고 캐시에 저장한다. SDK 환경을 source하지 않고 한 번 configure한 빌드 디렉터리는, 나중에 source해도 호스트 컴파일러를 계속 쓴다. 증상이 이상하면 빌드 디렉터리를 지우고 다시 configure한다.

7.2 빌드 경로가 바이너리에 새는 문제#

무엇을 확인하나: 같은 소스를 다른 디렉터리에서 -g로 빌드하면 오브젝트가 달라지는지, -ffile-prefix-map으로 같아지는지.

출력에서 볼 것: DWARF의 DW_AT_comp_dir에 빌드 디렉터리 절대 경로가 박혀서 해시가 달라진다. -ffile-prefix-map=<빌드경로>=.을 주면 두 오브젝트가 비트 단위로 같아진다. Yocto와 Buildroot는 이 옵션을 기본으로 넣어 재현 가능한 빌드(reproducible builds)를 만든다. ccache 적중률에도 영향을 준다(경로가 다르면 캐시 키가 달라질 수 있다).

7.3 ccache — cold vs warm 측정#

ccache는 "전처리된 소스 + 컴파일 옵션 + 컴파일러 자체의 해시"를 키로 오브젝트 파일을 캐시한다. 컴파일러 바이너리가 바뀌면(툴체인 업그레이드) 키가 바뀌므로 잘못된 캐시를 쓰지 않는다.

무엇을 확인하나: zstd 1.5.7 라이브러리(C 파일 26개, ct-ng가 받아 둔 tarball)를 make -j2로 빌드할 때, 캐시 없음 / ccache 첫 빌드(cold) / ccache 재빌드(warm) 시간. 세 툴체인(Ubuntu 크로스, Bootlin, §5에서 만든 ct-ng)으로 비교한다.

(ccache -s의 Hits/Misses 줄은 ccache 4.12 출력이 두 섹션에 같은 값을 반복해서 두 번씩 나온다. 측정 시 VM의 다른 작업 때문에 load average가 0.6~1.6 정도였다. speedup 값은 반올림 전 시간으로 나눈 것이라 그림의 "약 N배"와 조금 다르다. ct-ng 측정은 §5에서 툴체인을 만든 뒤 따로 돌렸다.)

그림 6 — ccache 측정 결과(툴체인마다 1회 측정, 막대 길이는 Python으로 비례 계산). warm 빌드는 세 툴체인 모두 0.03~0.04 s로, 막대가 보이지 않을 정도다.

출력에서 볼 것:

  • cold는 캐시 없음보다 약간 느리다(8.05 → 8.22 s, 88.47 → 91.43 s). 첫 빌드에서는 해시 계산·캐시 저장 비용만 더해진다. ccache의 이득은 오직 "두 번째부터"다.
  • warm은 0.04 s. 26개 파일 모두 적중(Hits 26)해서 컴파일러를 한 번도 띄우지 않았다. 브랜치를 오가거나 make clean이 잦은 개발 루프, CI의 반복 빌드에서 차이가 크다.
  • 같은 gcc 계열인데 에뮬레이션 툴체인은 네이티브보다 약 11배 느렸다(88.47 / 8.05). 직접 빌드한 ct-ng gcc 16.2(네이티브)는 8.74 s로 Ubuntu gcc 15.2와 비슷했다. x86 전용 툴체인을 arm64 호스트에서 쓰면 이 비용을 낸다. ccache가 이 비용을 가리는 데 특히 효과적이지만, 근본 해결은 호스트 arch에 맞는 툴체인(Arm GNU의 aarch64 호스트 빌드, §5처럼 직접 빌드한 ct-ng 툴체인, 또는 x86 빌드 서버)을 쓰는 것이다.
  • 커널 빌드에도 그대로 쓸 수 있다: make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- CC="ccache aarch64-linux-gnu-gcc".

7.4 팀에서 쓰는 재현 가능한 툴체인 세팅 — 실전 패턴#

  1. 툴체인 tarball을 내부 아티팩트 저장소(Artifactory, S3 등)에 올리고 URL + sha256을 저장소의 toolchain.lock 같은 파일에 기록한다. 외부 사이트가 사라져도 빌드가 된다.
  2. 빌드는 Docker 이미지 안에서 한다. Dockerfile에서 툴체인을 받아 sha256 검증 후 /opt/toolchains/에 풀고, 이미지는 digest(@sha256:...)로 고정한다. 개발자 노트북(Apple Silicon 포함)과 CI가 같은 환경을 쓴다.
  3. Yocto 팀은 SDK 설치 스크립트 자체를 아티팩트로 관리하고, 이미지 릴리스 버전과 SDK 버전을 짝지어 태깅한다(v2.3.0-image ↔ v2.3.0-sdk).
  4. 컴파일러 업그레이드는 별도 PR로, 전체 테스트 + 바이너리 크기·성능 비교 후 머지한다. Don의 펌웨어 팀 문화와 똑같다.

8. 커널 안에서는 무슨 일이 일어나나#

8.1 커널 헤더는 어디서 오나 — make headers_install#

툴체인 sysroot의 usr/include/linux/*.h, usr/include/asm/*.h는 커널 소스의 include/uapi/와 arch/<arch>/include/uapi/에서 온다. 커널 빌드 시스템의 headers_install 타깃이 커널 내부 전용 부분을 걷어 내고(__KERNEL__ 블록 제거 등) 유저용 헤더만 설치한다. crosstool-NG·Buildroot·Yocto 모두 툴체인을 만들 때 이 명령을 부른다.

무엇을 확인하나: §5의 crosstool-NG 빌드를 준비하면서 손질한 커널 6.1 소스에서 headers_install이 동작하는지, 결과 version.h의 값.

출력에서 볼 것: 393647 = 6 × 65536 + 1 × 256 + 175 → 6.1.175. drivers/, fs/, net/ 같은 커널 본체를 빼고도 헤더 설치가 된다(이 손질 버전은 §5에서 쓴다). drm, mtd, scsi, sound, video 같은 디렉터리는 드라이버가 유저에게 공개하는 ioctl 인터페이스다. Don이 나중에 드라이버에 ioctl을 추가하면(G5), 그 구조체 정의는 include/uapi/linux/<내 드라이버>.h에 두고, 그것이 이 경로를 따라 툴체인 sysroot와 앱으로 흘러간다.

8.2 모르는 syscall은 어떻게 ENOSYS가 되나#

그림 7 — 커널 헤더가 빌드 때 syscall 번호를 정하고, 실행 때 커널이 그 번호를 아는지에 따라 실제 함수 또는 sys_ni_syscall(-ENOSYS)로 간다. arm64 커널에서는 arch/arm64/kernel/syscall.c의 invoke_syscall()이 이 분기를 한다(32-bit ARM 커널은 arch/arm/kernel/entry-common.S의 테이블 점프).

연결 고리:

  • 커널 설정에서 기능을 끈 syscall(CONFIG_ 옵션으로 제외된 것)도 테이블 칸이 sys_ni_syscall로 채워진다. 그래서 같은 커널 버전이라도 .config에 따라 ENOSYS가 날 수 있다. "헤더 ≤ 커널" 규칙 + "그 기능이 .config에 켜져 있나"까지 봐야 한다(E 모듈).
  • §4.3에서 본 EFAULT는 커널이 syscall을 알고 copy_from_user()로 인자를 읽다 실패한 것이다(A1, E6).

8.3 커널과 모듈은 "같은 컴파일러"로#

유저 앱은 libc 계약만 맞으면 다른 gcc로 빌드해도 된다. 하지만 커널 모듈(.ko)은 커널을 빌드한 것과 같은 툴체인으로 빌드하는 것이 원칙이다.

  • 커널 .config에는 CONFIG_CC_VERSION_TEXT(커널을 빌드한 컴파일러 문자열)가 기록된다. 외부 모듈을 빌드할 때 Kbuild는 지금 컴파일러가 그것과 다르면 경고를 낸다.
  • gcc 버전에 따라 켜지는 커널 기능(스택 보호, 구조체 레이아웃 랜덤화 플러그인, -fzero-call-used-regs 같은 하드닝 옵션)이 달라서, 다른 컴파일러로 만든 모듈은 ABI가 미묘하게 어긋날 수 있다.
  • 모듈에는 vermagic 문자열(커널 버전, SMP, preempt, modversions 등)이 박히고, 맞지 않으면 insmod가 거부한다(G1, E 모듈).

그래서 벤더 BSP가 "커널은 이 툴체인으로 빌드하라"고 지정하고(§2.7), Yocto는 커널·모듈·앱을 같은 툴체인으로 빌드한다. Don이 out-of-tree 드라이버를 들고 다른 팀 보드에 올릴 때 첫 질문은 "이 커널을 어떤 툴체인으로 빌드했나요? 커널 빌드 트리(/lib/modules/$(uname -r)/build)는 어디 있나요?"가 된다.

11. 면접에서 이렇게 말한다#

Q. "How did your team obtain the cross toolchain, and why that one?"

A. 툴체인은 rootfs를 만드는 쪽을 따라간다. Yocto로 이미지를 만들면 같은 빌드에서 populate_sdk로 SDK를 뽑아 쓰고, 그러면 sysroot의 glibc·라이브러리·헤더가 이미지와 정확히 같다. Ubuntu 기반 보드면 같은 Ubuntu 버전의 크로스 패키지나 컨테이너를 쓰고, 커널은 벤더가 지정한 툴체인으로 빌드한다. 체크섬과 컨테이너로 고정한다.

We pick the toolchain based on who builds the root filesystem. With Yocto we generate the SDK from the same build with populate_sdk, so the sysroot's glibc, libraries and headers exactly match the image. For Ubuntu-based boards we build in a container of the same Ubuntu release, and the kernel is built with the vendor-specified toolchain. Everything is pinned by version and checksum.

꼬리 질문: "What if you need a different GCC version than the SDK provides?" → crosstool-NG나 Buildroot로 같은 libc 버전·커널 헤더를 지정해 빌드하고, glibc는 타깃보다 새롭지 않게 맞춘다.

Q. "A binary built on a developer laptop fails on the board with 'GLIBC_2.34 not found'. Explain."

A. glibc 심볼 버전 때문이다. 바이너리가 링크될 때 빌드 sysroot의 glibc에 있는 __libc_start_main@GLIBC_2.34 같은 버전 태그가 기록되는데, 보드의 glibc가 더 오래돼서 그 태그가 없다. glibc는 하위 호환만 보장하므로 타깃과 같거나 오래된 glibc로 빌드해야 한다. objdump -T로 요구 버전을 확인하고 SDK sysroot로 다시 빌드하거나, 도구성 바이너리면 musl static으로 만든다.

glibc uses symbol versioning. At link time the binary records versioned symbols from the build sysroot, like __libc_start_main@GLIBC_2.34, and the board's older glibc doesn't provide that version. glibc is only backward compatible, so you must build against a sysroot whose glibc is the same or older than the target's. I check the required versions with objdump -T and rebuild with the SDK sysroot, or ship a static musl binary for small tools.

Q. "What's in a cross toolchain besides the compiler?"

A. binutils(어셈블러·링커), gcc 본체(cc1)와 libgcc, 타깃 C 라이브러리와 동적 로더, 커널 UAPI 헤더, 그리고 그것들을 담은 sysroot다. 호스트 쪽에는 gmp/mpfr/mpc 같은 gcc 의존 라이브러리가 있다. 타깃으로 가는 것은 sysroot 부분뿐이고, 그것이 rootfs와 맞아야 한다.

Binutils for assembling and linking, the GCC driver and cc1 plus libgcc, the target C library with its dynamic loader, the kernel UAPI headers, all arranged in a sysroot, plus host-side libraries like GMP and MPFR that GCC itself needs. Only the sysroot content relates to the target, and it has to match the root filesystem.

Q. "Why do kernel headers in the toolchain need to be older than or equal to the target kernel?"

A. 헤더가 syscall 번호, ioctl 번호, 구조체 레이아웃을 정한다. 커널은 유저 ABI를 깨지 않고 추가만 하므로, 옛 헤더로 빌드한 앱은 새 커널에서 잘 돈다. 반대로 새 헤더로 새 syscall을 쓰면 옛 커널은 그 번호를 몰라 ENOSYS를 준다. 그래서 Bootlin stable은 일부러 5.10 헤더를 쓴다. 단 musl은 syscall 번호표를 자체적으로 들고 있어서 헤더 버전만 보고 판단하면 안 된다.

The headers define syscall numbers, ioctl numbers and struct layouts. Linux never breaks the user ABI, it only adds, so an app built with older headers runs fine on a newer kernel. The reverse fails: a new syscall from newer headers returns ENOSYS on an older kernel. That's why prebuilt stable toolchains often ship old headers. One caveat: musl carries its own syscall number table, so header version alone doesn't tell you what's callable.

Q. "What does the Yocto SDK environment-setup script actually do?"

A. 환경 변수만 export한다. PATH에 크로스 도구를 넣고, CC에 --sysroot와 CPU 튜닝 옵션까지 넣고, CFLAGS/LDFLAGS, pkg-config가 sysroot를 보도록 PKG_CONFIG_SYSROOT_DIR/PKG_CONFIG_PATH, 커널용 ARCH/CROSS_COMPILE, autotools용 CONFIGURE_FLAGS, CMake용 툴체인 설정을 준다. 그래서 Makefile은 $(CC)를 그대로 써야 하고 덮어쓰면 안 된다.

It just exports environment variables: PATH to the cross tools, CC including --sysroot and CPU tuning flags, CFLAGS and LDFLAGS, PKG_CONFIG_SYSROOT_DIR and PKG_CONFIG_PATH so pkg-config resolves inside the sysroot, ARCH and CROSS_COMPILE for kernel builds, CONFIGURE_FLAGS for autotools, and a CMake toolchain configuration. That's why Makefiles must use $(CC) rather than hardcoding gcc.

Q. "When would you use crosstool-NG instead of a prebuilt toolchain?"

A. 미리 빌드된 것으로 안 되는 조합이 필요할 때다. 예를 들어 오래된 커널에 맞춘 낮은 헤더 버전, 특정 glibc 버전, 특이 CPU 튜닝이나 아키텍처, 사내 패치가 들어간 gcc, 또는 aarch64 호스트용 툴체인이 필요할 때. 대신 툴체인 자체가 우리 산출물이 되어 유지보수 책임이 생긴다. 이미지를 Buildroot로 만든다면 Buildroot internal 툴체인이 더 자연스럽다.

When no prebuilt toolchain has the combination we need: specific kernel header or glibc versions to match an old target, unusual CPU tuning or architecture, patched GCC, or a different host architecture. The cost is that the toolchain becomes our own artifact to maintain. If the image is built with Buildroot, its internal toolchain is usually the more natural choice.

Q. "How do you make builds reproducible across the team?"

A. 툴체인을 URL + sha256으로 고정하고 내부 미러에 둔다. 빌드는 digest로 고정한 컨테이너 안에서 한다. -ffile-prefix-map으로 빌드 경로를 바이너리에서 지운다. 컴파일러 업그레이드는 별도 변경으로 검증한다. ccache는 속도용이지만 키에 컴파일러 해시가 들어가 안전하다.

Pin the toolchain by URL and SHA-256 and mirror it internally, build inside a container pinned by digest, strip build paths with -ffile-prefix-map so outputs are bit-identical, and treat compiler upgrades as a separate, fully tested change. ccache speeds things up safely because the compiler's own hash is part of the cache key.

14. 요약 & 체크리스트#

Embedded Linux 툴체인은 컴파일러 하나가 아니라 타깃 rootfs와 맺는 계약 묶음(libc 버전, 커널 헤더, float ABI, 기본 CPU)이다. 그래서 "어떤 툴체인을 쓰나"는 "rootfs를 누가 만드나"로 결정된다. Yocto·Buildroot·벤더 SDK처럼 rootfs와 같은 빌드에서 나온 툴체인은 계약이 자동으로 맞고, 배포판·Arm GNU·Bootlin·crosstool-NG는 사람이 맞춰야 한다. 맞출 때의 규칙은 "빌드 때 본 것 ≤ 실행 때 있는 것, 종류는 같게"다. 처음 보는 툴체인은 -dumpmachine, -v, -Q --help=target, -print-sysroot, sysroot의 version.h와 libc 실행으로 5분 안에 신원을 조회한다. 팀 환경은 URL + 체크섬 + 컨테이너 + -ffile-prefix-map으로 고정하고, ccache로 반복 빌드를 줄인다.
