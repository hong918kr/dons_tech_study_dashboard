0. 큰 그림 — 이게 왜 필요한가#

Don의 SSD 펌웨어 빌드를 떠올려 보자. x86 리눅스 서버(또는 Windows PC)에서 arm-none-eabi-gcc로 Cortex-R 이미지를 만들고, 그 .elf를 JTAG으로 보드에 올렸다. 컴파일러가 도는 기계(PC)와 결과물이 도는 기계(SSD 컨트롤러)가 다른 것 — 이것이 크로스 컴파일(cross compilation)이다. Don은 이미 8년 동안 크로스 컴파일을 해 왔다.

Embedded Linux에서도 똑같다. 센서 키트의 i.MX8이나 Jetson에서 직접 gcc를 돌릴 수도 있지만(native build), 보드는 느리고 메모리가 작고 rootfs에 컴파일러가 없는 경우가 대부분이다. 그래서 개발 PC에서 보드용 바이너리를 만든다. 달라지는 점은 하나다: 결과물이 OS 위에서 돌기 때문에, 툴체인이 타깃 OS의 C 라이브러리(glibc/musl), 동적 로더, 커널 헤더까지 함께 들고 있어야 한다. 이 묶음이 sysroot(타깃 루트 파일시스템의 개발용 축소판)다.

그림 1 — 하나의 빌드 머신에 타깃별 툴체인이 여러 벌 깔린다. Linux 타깃용(초록)은 libc·동적 로더·커널 헤더를 담은 sysroot가 필요하고, MCU용(주황)은 newlib만 있으면 된다.

Embedded Linux 엔지니어가 툴체인을 만나는 장면은 이렇다.

  • 센서 데몬 빌드: IMU를 읽는 C 데몬을 PC에서 aarch64-linux-gnu-gcc로 빌드해 scp로 보드에 올린다. 보드에서 ./imud가 not found로 실패한다 → 동적 로더 경로·glibc 버전 문제 (§5, §12.1).
  • 커널·U-Boot 빌드: make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- — 이 두 변수가 무엇인지 모르면 커널 빌드 첫 줄부터 막힌다 (§10, C3, E2).
  • 성능 튜닝: 같은 코드가 Cortex-A53 보드에서 느리다 → -mcpu를 맞췄는지, NEON이 쓰였는지 objdump로 확인 (§7).
  • 이종 코어 SoC: i.MX8M의 Cortex-A53(Linux)과 Cortex-M4(펌웨어)를 한 프로젝트에서 빌드 → aarch64-linux-gnu와 arm-none-eabi 두 툴체인을 동시에 쓴다 (§4, O 모듈).

실행 환경: 모든 출력은 Lima VM elinux(aarch64, uname -r = 7.0.0-34-generic, Ubuntu 26.04)에서 실제로 돌린 결과다. 크로스 툴체인은 Ubuntu 패키지 gcc-arm-linux-gnueabihf·gcc-riscv64-linux-gnu·gcc-x86-64-linux-gnu(GCC 15.2), gcc-arm-none-eabi(14.2.rel1) + libnewlib-arm-none-eabi, clang/lld 21.1.8, qemu-user 10.2.1. 아래 명령은 VM 안에서 cd /tmp/B1; S=/Users/donh/.elinux_scratch/B1(소스 위치)를 한 상태로 친 것이다. 해시·주소·임시 파일 이름은 실행마다 다르다.

1. 크로스 컴파일이란 — build / host / target#

1.1 직관 — "컴파일러가 도는 곳"과 "결과물이 도는 곳"#

컴파일러 하나에는 기계가 세 개 얽혀 있다. GNU 빌드 시스템(autoconf, GCC의 configure)은 이것을 정확한 용어로 부른다.

용어뜻Don의 SSD FW 예
build컴파일러(또는 프로그램) 자체를 빌드한 기계Arm이 GNU toolchain 패키지를 빌드한 서버
host그 컴파일러가 실행되는 기계Don의 x86 리눅스 서버
target그 컴파일러가 만든 코드가 실행되는 기계Cortex-R SSD 컨트롤러

일반 프로그램(예: 센서 데몬)을 configure로 빌드할 때는 target이 의미가 없고 build와 host만 쓴다: ./configure --host=aarch64-linux-gnu는 "이 프로그램은 aarch64 Linux에서 돌 것이다"라는 뜻이다. target이 의미를 갖는 것은 컴파일러·binutils·디버거처럼 "코드를 만드는 프로그램"을 빌드할 때다.

1.2 세 가지 조합#

그림 2 — native는 셋이 같고, cross는 target만 다르고, Canadian cross는 셋이 모두 다르다.

  • native: build = host = target. 지금 VM의 gcc가 그렇다.
  • cross: build = host ≠ target. Embedded Linux 개발의 기본형.
  • Canadian cross: build ≠ host ≠ target. 예를 들어 Arm이 Windows용 arm-none-eabi-gcc.exe를 배포하려면, Linux 빌드 서버(build)에서 MinGW 크로스 컴파일러로, Windows(host)에서 돌고, Cortex-M(target)용 코드를 내는 GCC를 빌드해야 한다. 이름은 당시 캐나다에 정당이 셋이었던 데서 왔다는 이야기가 전해진다. 실무에서 직접 할 일은 드물고, crosstool-NG나 Yocto의 nativesdk(다른 호스트용 SDK 만들기)에서 이 개념을 만난다 (B5, K).

1.3 코드로 확인 — 컴파일러에게 "너는 누구냐" 묻기#

무엇을 확인하나: 각 gcc가 스스로 어떤 target용인지(-dumpmachine), Debian식 multiarch 이름이 무엇인지, multilib(§9)가 몇 벌인지 본다.

출력에서 볼 것: 그냥 gcc도 사실 aarch64-linux-gnu용 컴파일러다 — native 컴파일러는 "target이 자기 자신인 크로스 컴파일러"일 뿐이다. arm-none-eabi는 multiarch가 비어 있고(OS가 없으니 Debian 라이브러리 경로 개념도 없다) multilib이 39벌이나 된다 (§9).

2. Target triplet 해독#

2.1 구조 — arch-vendor-os-abi#

툴체인 이름 앞에 붙는 arm-linux-gnueabihf- 같은 접두어가 target triplet이다. 이름은 "세 쌍"이지만 실제로는 네 칸까지 쓴다.

그림 3 — triplet은 "어떤 CPU에서, 어떤 OS 위에서, 어떤 C 라이브러리·호출 규약으로 도는 코드인가"를 한 줄로 적은 것이다.

칸별 의미를 하나씩 보자.

  • arch: aarch64, arm, armv7a, riscv64, x86_64. 32-bit ARM은 그냥 arm이라 쓰고 세부 아키텍처는 컴파일러 기본값(--with-arch)과 -march로 정한다.
  • vendor: unknown, pc, none, poky(Yocto), buildroot 등. 코드 생성에는 거의 영향이 없고 "누가 만든 툴체인인가" 표시다. 그래서 Debian/Ubuntu는 아예 생략한다. 단, arm-none-eabi의 none은 위치상 vendor 칸이지만 관례적으로 "OS 없음"으로 읽힌다 (정식형으로 쓰면 arm-unknown-none-eabi에 가깝다).
  • os: linux, none(없음), elf, w64(Windows) 등. 이것이 바뀌면 syscall 방식, 실행 파일 형식의 세부, 시작 코드가 바뀐다.
  • abi(환경): gnu(glibc), musl, gnueabi(glibc + ARM EABI, soft-float), gnueabihf(glibc + EABI + hard-float), eabi(bare-metal EABI). 이것이 바뀌면 함수 호출 규약과 C 라이브러리가 바뀐다.

함정 메모: Clang은 triplet을 내부적으로 정규화한다. --target=arm-linux-gnueabihf를 주면 내부 triple은 armv7-unknown-linux-gnueabihf로 바뀐다(§8의 출력). 반대로 GCC는 triplet 하나당 컴파일러 바이너리 한 벌이 따로 설치된다. 이 차이가 §8의 주제다.

2.2 코드로 확인 — 한 소스, 네 아키텍처#

무엇을 확인하나: 같은 hello.c를 네 툴체인으로 빌드하고 file과 readelf -h로 ELF 헤더가 어떻게 다른지 본다.

출력에서 볼 것 (네 가지):

  1. interpreter: 동적 링크된 실행 파일마다 "나를 메모리에 올려 줄 동적 로더(dynamic loader) 경로"가 박혀 있다. 아키텍처·ABI마다 이름이 다르다 (ld-linux-armhf.so.3, ld-linux-riscv64-lp64d.so.1). §5에서 이게 왜 중요한지 본다.
  2. ELF e_flags: ARM은 Version5 EABI, hard-float ABI, RISC-V는 RVC, double-float ABI처럼 ABI가 헤더 플래그에 기록된다. 링커는 이 플래그가 다른 오브젝트를 섞지 않는다 (§6).
  3. armhf 엔트리 0x579가 홀수: Ubuntu armhf 툴체인은 기본이 Thumb-2(--with-mode=thumb)라서, 주소 최하위 비트 1 = "Thumb 상태로 점프"라는 Cortex-M 시절의 그 규칙이 그대로 보인다.
  4. for GNU/Linux 3.2.0: glibc가 요구하는 최소 커널 버전(ELF note NT_GNU_ABI_TAG)이다. riscv64는 4.15부터 지원되므로 4.15.0이다. 커널 헤더 이야기(§9)와 이어진다.

3. 툴체인 안에는 무엇이 있나#

3.1 부품 목록#

"툴체인"은 컴파일러 하나가 아니라 여러 프로그램과 라이브러리의 묶음이다. Don이 쓰던 arm-none-eabi 패키지도 마찬가지였다 — 다만 Linux용에는 libc와 커널 헤더가 더 무겁게 들어간다.

3.2 코드로 확인 — gcc에게 부품 위치를 물어보기#

무엇을 확인하나: -v로 빌드 설정을, -print-* 옵션으로 각 부품의 실제 경로를 꺼낸다.

출력에서 볼 것:

  • 기본값이 configure 때 박힌다: --with-arch=armv7-a+fp --with-float=hard --with-mode=thumb. 그래서 -march를 안 줘도 ARMv7-A + VFP + Thumb-2 + hard-float 코드가 나온다. 벤더 SDK 툴체인은 여기에 보드 CPU(--with-cpu=cortex-a53 등)를 박아 두는 경우가 많다.
  • sysroot가 /: Debian/Ubuntu 크로스 패키지는 특이하게 sysroot를 /로 두고, 타깃 파일을 /usr/arm-linux-gnueabihf/{include,lib}라는 multiarch 디렉터리에 넣는다. Buildroot·Yocto·Arm GNU Toolchain 같은 일반적인 툴체인은 sysroot가 별도 디렉터리(예: .../arm-buildroot-linux-gnueabihf/sysroot)다. 원리는 같고 레이아웃만 다르다 (B5, K).
  • 실제 파일 경로를 따라가면 cc1·collect2는 gcc 쪽(libexec/gcc-cross), as·ld는 binutils 쪽(/usr/arm-linux-gnueabihf/bin), libc·crt1.o는 sysroot 쪽이다. 세 출처가 합쳐진 것이 툴체인이다.

3.3 코드로 확인 — -###로 driver가 실제로 부르는 명령 보기#

무엇을 확인하나: gcc -###는 아무것도 실행하지 않고 "실행할 명령"만 출력한다. Don이 bare-metal Makefile에서 직접 쓰던 as·ld 호출이 driver 뒤에 숨어 있는 것을 확인한다.

collect2 줄이 너무 길어서, LTO 플러그인 옵션과 -L 경로를 빼고 다시 보자.

출력에서 볼 것:

  • cc1에 몰래 붙는 매크로: -D_TIME_BITS=64 -D_FILE_OFFSET_BITS=64는 Ubuntu가 32-bit ARM에서 time_t·off_t를 64-bit로 바꾼 정책(2038년 문제 대비)이다. -D_FORTIFY_SOURCE=3은 배포판 보안 기본값이다. "같은 GCC 15인데 Buildroot 툴체인과 결과가 다르다"는 일이 이런 배포판 기본값 때문에 생긴다.
  • 링크 줄 = Don의 bare-metal 링크 + OS 부품: Scrt1.o(여기 _start가 있다, PIE용 S 버전) → crti.o → crtbeginS.o → 내 오브젝트 → -lgcc -lc -lgcc → crtendS.o → crtn.o. 그리고 -dynamic-linker /lib/ld-linux-armhf.so.3 — §2.2의 "interpreter" 문자열이 여기서 박힌다. bare-metal에서는 이 자리에 Don의 startup.s와 링커 스크립트(-T)가 있었다.

3.4 컴파일 4단계 — -save-temps#

그림 4 — 왼쪽 driver가 cc1·as·collect2/ld를 차례로 부르고, 오른쪽 sysroot가 헤더(컴파일 단계)와 crt·libc(링크 단계)를 공급한다.

무엇을 확인하나: -save-temps로 각 단계의 중간 산출물을 남기고, 단계마다 무엇이 생기는지 본다.

(hello.s는 main의 앞부분만 남기고 ...로 줄였다. head -40 출력의 일부다.)

출력에서 볼 것:

  • hello.i (1240줄, 39KB): 23줄짜리 소스가 sysroot의 stdio.h·sys/utsname.h를 펼쳐 1240줄이 됐다. 여기 들어간 헤더가 타깃용이어야 한다. 호스트 헤더가 섞이면 구조체 크기가 틀어진다 (§12.2의 zlib 예).
  • hello.s: bl uname(PLT), bl __printf_chk(PLT) — 라이브러리 호출이 PLT(동적 링크 점프 테이블, B3)를 거친다. printf가 __printf_chk로 바뀐 것은 _FORTIFY_SOURCE 효과다. sp, #404에 넣는 값은 stack protector canary다.
  • hello.o의 U 심볼: 아직 해결 안 된 외부 참조 (uname, __printf_chk). 링커가 sysroot의 libc에서 찾아 연결한다. _start는 아직 없다 — Scrt1.o가 링크 때 붙인다.

4. arm-none-eabi vs arm-linux-gnueabihf — Don의 세계와 새 세계#

4.1 같은 ARM, 다른 "아래층"#

4.2 코드로 확인 — newlib printf의 끝은 어디인가#

무엇을 확인하나: arm-none-eabi-gcc로 printf를 쓰는 프로그램을 (1) 스텁 없이, (2) nosys.specs로, (3) rdimon.specs(semihosting)로 링크해 보고, 마지막 것을 qemu-arm으로 실제 실행한다.

출력에서 볼 것: newlib은 OS 기능 8개(_write, _sbrk, _read …)를 외부에 맡긴다. Don이 펌웨어에서 _write를 UART 송신 함수로 구현해 printf를 살렸던 그 지점이다. nosys.specs는 "전부 실패를 반환하는 가짜"를 넣어 링크만 되게 한다. Linux 툴체인에서는 이 8개 자리에 syscall이 있고, 그 너머에 커널이 있다.

이번에는 semihosting(디버거·에뮬레이터가 호스트의 파일·콘솔을 대신 처리해 주는 ARM 규약) 버전을 만들어 실제로 돌린다.

출력에서 볼 것:

  • soft-float ABI, INTERP 0개, statically linked: none-eabi 기본값은 soft-float이고, 동적 로더가 없다. 같은 ARM ELF라도 헤더 플래그가 Linux용(hard-float ABI)과 다르다.
  • 첫 실행 실패: 기본 링커 스크립트가 코드를 0x8000에 놓는데, 이 VM의 vm.mmap_min_addr가 32768(=0x8000)이라 유저 프로세스가 그 주소를 매핑할 수 없다 (NULL 근처 매핑 금지, 커널 보안 설정). -Ttext-segment=0x400000으로 옮기자 돌았다. bare-metal 이미지의 주소 감각과 Linux 프로세스의 주소 규칙이 부딪친 장면이다.
  • svc 0xab: newlib의 _write → _swiwrite가 Thumb semihosting 호출(svc 0xab)을 한다. qemu-arm(user 모드)이 이것을 잡아 호스트 콘솔에 찍어 줬다. 진짜 보드에서는 JTAG 디버거(OpenOCD 등)가 같은 일을 한다. Cortex-M에서는 bkpt 0xab를 쓴다.

함정 메모: 이 실험은 "none-eabi ELF를 Linux 유저 프로세스처럼 실행"한 것이라 qemu가 관대하게 처리해 준 결과다. 실제 MCU 펌웨어는 벡터 테이블·링커 스크립트가 있어야 하고 qemu-system-arm -M <보드>나 실물 보드에서 돌린다.

5. 크로스 바이너리 실행하기 — qemu-user와 sysroot#

5.1 직관 — "명령어 번역기 + syscall 중계기"#

qemu-user(qemu-arm, qemu-riscv64 …)는 다른 아키텍처의 유저 프로세스 하나를 돌린다. 명령어는 동적 번역(TCG)으로 호스트 명령어로 바꾸고, syscall은 번호·구조체를 호스트 커널 형식으로 변환해서 호스트 커널에 넘긴다. 커널까지 에뮬레이션하는 qemu-system-*과 달리 커널은 호스트 것을 그대로 쓴다. 그래서 가볍고 빠르지만 드라이버·/dev 실험은 못 한다.

남은 문제가 하나 있다. 동적 링크된 armhf 바이너리는 실행되자마자 /lib/ld-linux-armhf.so.3를 찾고, 그 로더는 libc.so.6을 찾는다. 이 파일들은 호스트의 /lib에 없다 — sysroot에 있다. 그래서 qemu에게 "타깃의 /는 여기다"라고 알려 줘야 한다: -L <sysroot> 또는 환경 변수 QEMU_LD_PREFIX.

5.2 코드로 확인 — 네 가지 실패와 성공#

무엇을 확인하나: §2.2의 네 바이너리를 그냥 실행했을 때와 -L을 줬을 때를 비교한다.

출력에서 볼 것:

  • riscv64·x86_64는 ./만으로 qemu가 떴다: binfmt_misc(커널이 ELF 헤더의 magic 바이트를 보고 "이 형식은 이 인터프리터로 실행하라"고 정하는 기능)에 qemu가 31개 등록돼 있다. magic의 f300은 ELF e_machine = 0xF3(RISC-V)이다. 커널의 execve가 이 표를 보고 qemu-riscv64를 대신 실행한다.
  • armhf만 Exec format error: binfmt 목록에 qemu-arm이 없다. Debian 계열은 arm64 호스트에서 qemu-arm을 등록하지 않는다 — 많은 arm64 CPU가 32-bit ARM(AArch32) 유저 코드를 하드웨어로 직접 돌릴 수 있기 때문이다. 그런데 Apple Silicon은 AArch32를 지원하지 않아서 커널이 거절한다. 그래서 qemu-arm을 명시적으로 불러야 한다.
  • Could not open '/lib/ld-linux-...': 번역은 됐지만 동적 로더를 호스트 /lib에서 찾다가 실패했다. -L /usr/arm-linux-gnueabihf를 주자 성공했다. 이 메시지가 바로 "sysroot가 왜 필요한가"의 실행 시점 버전이다.
  • uname -m says armv7l: qemu가 uname syscall 결과의 machine 필드를 타깃 것으로 바꿔 준다. 커널 버전(release)은 호스트 것 그대로다 (§9에서 다시 본다).

5.3 코드로 확인 — QEMU_LD_PREFIX와 정적 링크#

무엇을 확인하나: binfmt로 자동 실행될 때는 -L 대신 환경 변수로 sysroot를 알려 준다. 정적 링크하면 로더가 필요 없다는 것도 확인한다.

출력에서 볼 것: 정적 바이너리는 -L 없이 돌았다 — INTERP가 없으니 찾을 파일이 없다. 동적 바이너리는 PT_INTERP(로더 경로)와 NEEDED(필요한 공유 라이브러리) 두 가지를 sysroot에서 찾아야 한다. 보드 rootfs가 바로 이 sysroot의 "실물"이다. 보드에서 같은 문제가 나면 qemu 메시지 대신 셸이 ./hello: not found처럼 아주 헷갈리는 메시지를 낸다 (파일은 있는데 INTERP가 없어서). 자세한 디버깅은 B2, B3.

6. ABI — EABI, hard-float, soft-float#

6.1 직관 — "함수를 부를 때 인자를 어디에 두기로 약속했나"#

ABI(Application Binary Interface)는 이미 컴파일된 코드끼리 지켜야 하는 약속이다: 인자를 어느 레지스터에 넣나, 구조체는 어떻게 정렬하나, 스택은 몇 바이트 정렬인가, long은 몇 비트인가. Don이 Cortex-R 펌웨어에서 어셈블리 함수와 C 함수를 섞을 때 "r0~r3에 인자, r0에 리턴, r4~r11은 callee-saved"를 지켰던 것이 ARM의 AAPCS(Procedure Call Standard for the Arm Architecture)이고, 이 AAPCS를 포함한 ARM의 바이너리 규약 묶음이 EABI(Embedded ABI)다. arm-none-eabi와 arm-linux-gnueabihf 둘 다 EABI를 따른다 — 그래서 둘 다 이름에 eabi가 들어간다.

32-bit ARM에서 가장 자주 문제가 되는 ABI 차이는 float 인자를 어디에 넣는가다.

그림 6 — 32-bit ARM의 세 가지 float ABI. softfp는 FPU 명령을 쓰지만 인자는 정수 레지스터로 주고받아 soft와 호환되고, hard는 VFP 레지스터로 직접 넘긴다.

  • soft: FPU 명령을 아예 안 쓴다. float 연산은 libgcc의 __aeabi_fadd 같은 함수가 정수 연산으로 흉내 낸다. FPU 없는 Cortex-M0/M3, ARM9 시절의 기본.
  • softfp: FPU 명령(vadd.f32)은 쓰되, 함수 경계에서는 soft와 똑같이 r0~r3으로 주고받는다. soft로 빌드된 라이브러리와 섞을 수 있다는 장점, 레지스터 복사(vmov) 비용이 단점.
  • hard: float 인자를 s0~s15/d0~d7로 바로 넘긴다. 가장 빠르다. 이것이 gnueabihf의 hf이고, Debian/Ubuntu armhf 포트, Raspberry Pi OS 32-bit, 대부분의 Cortex-A 32-bit 보드 BSP가 이것이다.

Don이 Cortex-M4F 펌웨어에서 -mfloat-abi=hard -mfpu=fpv4-sp-d16을 썼다면 이미 같은 선택을 해 본 것이다. 차이는 Linux에서는 이 선택이 "배포판 전체"에 걸린다는 것이다. rootfs의 모든 라이브러리가 한 ABI로 빌드되어 있어서, 앱 하나만 다른 ABI로 빌드할 수 없다.

6.2 코드로 확인 — 세 ABI의 기계어와 섞었을 때의 실패#

무엇을 확인하나: 같은 fadd()를 세 float ABI로 컴파일해 기계어와 ELF 속성을 비교하고, hard와 softfp를 섞어 링크해 본다.

(softfp 디스어셈블은 tail로 잘려 첫 줄 0: vmov s14, r0이 빠졌다. 따로 보면 ee07 0a10 vmov s14, r0이다.)

출력에서 볼 것:

  • 기계어가 ABI를 그대로 보여 준다: hard는 vadd.f32 s0, s0, s1 한 줄, softfp는 vmov로 r↔s 복사가 앞뒤로 붙고, soft는 __aeabi_fadd 호출이다.
  • ABI는 ELF 속성(.ARM.attributes)에 기록된다: Tag_ABI_VFP_args: VFP registers가 hard의 표시다. 링커는 이 태그가 다른 오브젝트를 만나면 uses VFP register arguments, fadd_softfp.o does not으로 거부한다. 고마운 실패다 — 그냥 링크됐다면 실행 중 float 인자가 엉뚱한 레지스터에서 읽혀 쓰레기 값이 나왔을 것이다.
  • soft로 통째 빌드도 안 된다: sysroot의 glibc가 hard로 빌드되어 있어서, glibc 헤더가 gnu/stubs-soft.h를 요구하다가 실패한다. "ABI는 툴체인+sysroot 단위로 정해진다"는 증거다. soft-float가 필요하면 arm-linux-gnueabi(armel) 툴체인과 armel rootfs를 통째로 써야 한다.

7. -march / -mcpu / -mtune / -mfpu — 같은 triplet, 다른 코드#

7.1 직관 — triplet은 "가족", -mcpu는 "개인"#

arm-linux-gnueabihf는 "32-bit ARM Linux 가족" 전체를 뜻한다. 그 안에서도 Cortex-A7, A9, A15, A53(32-bit 모드)은 쓸 수 있는 명령어(NEON, 정수 나눗셈 sdiv, crypto)와 파이프라인 특성이 다르다. 그것을 고르는 것이 이 옵션들이다.

옵션정하는 것결과 바이너리가 도는 범위예
-march=쓸 수 있는 명령어 집합 (ISA + 확장)그 아키텍처 이상의 모든 코어-march=armv8-a, -march=armv8.2-a+dotprod
-mtune=명령어 스케줄링·비용 모델만 (명령어 집합은 그대로)-march 범위 그대로-mtune=cortex-a53
-mcpu=-march + -mtune를 그 코어에 맞게 한 번에그 코어(와 상위 호환 코어)-mcpu=cortex-a72
-mfpu= (ARM 32만)FPU/NEON 종류그 FPU가 있는 코어-mfpu=neon-vfpv4, 기본 auto = -mcpu에서 추론

규칙 하나: -march(또는 -mcpu)를 실제 보드보다 높게 잡으면 SIGILL, 낮게 잡으면 느릴 뿐 돈다. -mtune은 틀려도 절대 죽지 않는다. 그래서 배포판은 낮은 -march + 흔한 코어 -mtune으로 빌드하고, 보드 전용 이미지(Yocto DEFAULTTUNE, Buildroot BR2_cortex_a53)는 -mcpu를 정확히 맞춘다.

7.2 코드로 확인 — -mcpu가 켜는 기능 매크로#

무엇을 확인하나: -mcpu를 바꾸면 컴파일러가 정의하는 ACLE 기능 매크로(__ARM_NEON, __ARM_FEATURE_*)가 어떻게 바뀌는지 본다. 소스의 #ifdef __ARM_NEON 분기가 이것으로 결정된다.

출력에서 볼 것:

  • ARM 32 기본값에는 NEON이 없다 (__ARM_FP 12 = 단정·배정밀 VFP만, __ARM_NEON 없음). -mcpu=cortex-a7만 줘도 __ARM_NEON과 하드웨어 정수 나눗셈(IDIV)이 켜진다 — 최신 GCC는 -mfpu=auto가 기본이라 -mcpu에서 FPU를 추론한다. 예전 튜토리얼처럼 -mfpu=neon-vfpv4를 꼭 같이 쓸 필요는 없다(같이 써도 결과는 같다).
  • AArch64 기본값(armv8-a)에는 CRC32도 LSE atomics도 없다. Cortex-A53/A72는 ARMv8.0이라 CRC32만, Cortex-A78(ARMv8.2)은 LSE atomics(__ARM_FEATURE_ATOMICS)와 dot product까지 켜진다. Jetson Orin의 Cortex-A78AE가 이쪽이다.

7.3 코드로 확인 — NEON 자동 벡터화 (ARM 32)#

무엇을 확인하나: 정수 덧셈 루프와 float saxpy 루프가 옵션에 따라 NEON으로 벡터화되는지 -fopt-info-vec-optimized(컴파일러가 "이 루프를 벡터화했다"고 보고하는 옵션)로 확인한다.

출력에서 볼 것:

  • 기본 armhf(-O2, -O3)는 NEON이 없어서 아무것도 벡터화하지 않는다. -mfpu=vfpv4처럼 NEON 없는 FPU를 명시해도 마찬가지다.
  • -mcpu=cortex-a7이면 int 루프가 vld1.32/vadd.i32 q8(128-bit, 4개씩)로 바뀐다. float 루프는 -ffast-math를 줘야만 벡터화된다. ARMv7 NEON의 float 연산은 IEEE 754를 완전히 따르지 않기 때문(denormal을 0으로 처리)에, GCC는 "정확도를 포기해도 된다"(-funsafe-math-optimizations, -ffast-math에 포함)는 허락이 있어야 NEON float를 쓴다.
  • 벡터 루프(q 레지스터, 4개씩) 뒤에 남은 1~3개를 처리하는 스칼라 꼬리(vldr s15, vfma.f32 s15)가 붙는다. Don이 DMA 버스트 뒤에 나머지 바이트를 따로 처리하던 것과 같은 구조다.

출력에서 볼 것:

  • AArch64에서는 -ffast-math 없이도 float가 벡터화된다 (fmla v5.4s). AArch64 Advanced SIMD는 IEEE 754를 따르기 때문이다. ARM 32와의 큰 차이다.
  • -O2(이 GCC에서는 아주 보수적인 "very cheap" 벡터화 비용 모델)는 반복 횟수 n을 모르는 이 루프를 벡터화하지 않았다. -O3에서 코드 크기가 96 → 336 바이트로 3.5배가 됐다 — 벡터 본체 + 스칼라 꼬리 + 겹침 검사. 플래시가 작은 보드에서는 이 크기도 비용이다.
  • -mcpu=cortex-a53(in-order 코어)과 cortex-a72(out-of-order 코어)는 같은 명령어 집합에서 순서·꼬리 처리 방식만 다르게 골랐다. 이것이 -mtune 효과다.

7.5 코드로 확인 — -march를 너무 높게 잡으면: SIGILL#

무엇을 확인하나: ARMv8.1의 LSE atomic(ldadd)을 쓰도록 빌드한 바이너리를 qemu로 Cortex-A53/A72(ARMv8.0) 흉내를 내며 돌려 본다. Jetson(A78)용으로 빌드한 바이너리를 i.MX8M(A53)에 올리는 실수의 재현이다.

출력에서 볼 것:

  • -march=armv8.1-a 빌드는 ldaddal을 직접 박아서, ARMv8.0인 A53·A72에서 SIGILL(signal 4)로 죽고 ARMv8.2인 A76에서만 돈다. 보드에서는 Illegal instruction으로 보인다.
  • 기본 빌드는 __aarch64_ldadd8_acq_rel이라는 outline atomics 도우미를 부른다. 시작 시 CPU 기능(HWCAP)을 보고 플래그를 세워 두고, LSE가 있으면 ldaddal, 없으면 ldaxr/stlxr 루프(Don이 아는 LDREX/STREX 방식)로 간다. 런타임 디스패치로 "낮은 -march의 호환성 + 높은 코어의 성능"을 둘 다 얻는 장치다.

7.6 측정 — native vs qemu-user, 옵션별 실행 시간#

무엇을 확인하나: 같은 saxpy 벤치마크를 native(-O0/-O2/-O3/-mcpu)와 qemu-user(armhf, x86_64, riscv64)로 돌려 시간을 잰다. "qemu로 기능 테스트는 되지만 성능 측정은 안 된다"를 숫자로 본다.

그림 7 — 직접 측정한 실행 시간. native 벡터 코드(초록)와 qemu-user(주황·파랑·빨강) 사이에 60~320배 차이가 난다. 로그 축이다.

출력에서 볼 것:

  • native -O2 = -O3: 앞 절에서 -O2는 saxpy를 벡터화하지 않았는데 여기서는 같은 속도다. saxpy.constprop.0이 답이다 — 이 프로그램에서는 n이 항상 4096이라 GCC가 상수를 넣은 복제본을 만들었고, 반복 횟수를 알게 되자 -O2에서도 벡터화했다(fmla .4s 1개). "최적화 결과는 호출 맥락에 따라 달라진다", 그래서 추측하지 말고 objdump로 확인해야 한다.
  • -O0는 32배 느리다. 디버그 빌드를 보드에 올려 놓고 "보드가 느리다"고 결론 내리는 실수가 흔하다.
  • qemu-user는 native보다 60~320배 느리다. 같은 qemu-arm 안에서는 NEON 버전이 1.4배 빨랐지만, 이 비율도 실제 Cortex-A7과는 무관하다 (qemu가 NEON 명령을 호스트 명령으로 번역하는 비용이 섞여 있다). riscv64는 기본 rv64gc에 벡터 확장(RVV)이 없어 스칼라 코드라 가장 느렸다. qemu는 "돌아가나?"를 보는 도구지, "얼마나 빠른가?"를 재는 도구가 아니다. 성능은 실물 보드에서 잰다 (M, N 모듈).

8. Clang — 컴파일러 하나로 모든 타깃#

8.1 GCC와 Clang의 구조 차이#

GCC는 configure할 때 target이 하나로 고정된다. 그래서 arm-linux-gnueabihf-gcc, riscv64-linux-gnu-gcc가 각각 다른 실행 파일이다. Clang(LLVM)은 모든 백엔드를 한 바이너리에 넣고 실행할 때 --target=으로 고른다. 대신 Clang은 C 라이브러리·crt 파일·libgcc를 직접 갖고 있지 않아서, sysroot와 (보통은) GCC 크로스 설치본을 빌려 쓴다.

무엇을 확인하나: 같은 clang으로 armhf·riscv64·x86_64 hello를 만들고, 내부적으로 어떤 triple·링커·헤더 경로를 쓰는지 본다.

출력에서 볼 것:

  • clang 한 바이너리에 47개 타깃이 들어 있다. --target만 바꿔 세 아키텍처 바이너리를 만들었고, riscv64 결과물이 qemu에서 돌았다.
  • 내부 triple은 armv7-unknown-linux-gnueabihf로 정규화됐고, float ABI(hard)와 동적 로더 경로도 triple에서 유도됐다.
  • Selected GCC installation: clang이 GCC 크로스 설치본을 찾아 crt 파일·libgcc·헤더 경로를 빌렸다. .comment 섹션에 GCC: (Ubuntu 15.2.0…)이 섞여 있는 것이 그 흔적이다(crt 오브젝트가 GCC로 빌드된 것). 링커는 LLD 21.1.8이다.
  • --sysroot=/nonexistent를 주자 stdio.h를 못 찾았다 — clang에게 sysroot는 필수 입력이다. Yocto/Buildroot SDK에서 clang을 쓸 때 --sysroot=$SDKTARGETSYSROOT를 반드시 넘기는 이유다.

9. 커널 헤더·glibc 버전·multilib — sysroot 안의 "버전" 문제#

9.1 커널 헤더(UAPI)는 무엇이고 왜 툴체인에 있나#

유저 프로그램은 커널과 syscall 번호, ioctl 번호, 구조체 레이아웃으로 대화한다(A1, A3). 이 정의가 커널 소스의 include/uapi/와 arch/<arch>/include/uapi/에 있고, make headers_install로 뽑아낸 것이 커널 헤더(UAPI headers)다. Debian/Ubuntu에서는 linux-libc-dev(native), linux-libc-dev-armhf-cross(크로스) 패키지다. glibc는 이 헤더를 보고 빌드되고, 앱도 #include <linux/i2c-dev.h>, <linux/spi/spidev.h>, <linux/videodev2.h>로 직접 쓴다 — 센서 키트 코드의 핵심 헤더들이다.

규칙은 하나다: 툴체인의 커널 헤더 버전 ≤ 보드에서 실제로 도는 커널 버전. 커널은 옛 ABI를 유지하므로(새 syscall·필드는 추가만 한다) 옛 헤더로 빌드한 앱은 새 커널에서 돈다. 반대로 헤더가 더 새로우면 앱이 커널에 없는 syscall이나 ioctl을 써서 ENOSYS, EINVAL, ENOTTY가 난다. 벤더 BSP 커널이 5.10인데 최신 배포판 툴체인(헤더 7.0)으로 빌드하면 이 위험이 있다. 그래서 Yocto/Buildroot는 보드 커널과 같은 버전의 헤더로 툴체인을 만든다(Buildroot의 "Kernel Headers" 옵션).

9.2 코드로 확인 — 헤더 버전과 syscall 번호#

무엇을 확인하나: 각 sysroot의 LINUX_VERSION_CODE와 syscall 번호를 출력해, 아키텍처마다 syscall 번호가 다르다는 것과 "헤더 버전 ≠ 실행 커널 버전"을 본다.

출력에서 볼 것:

  • syscall 번호는 아키텍처마다 다르다: openat이 arm64·riscv64는 56(둘 다 새 "generic" 번호표 사용), 32-bit ARM은 322, x86_64는 257. 그래서 커널 헤더는 반드시 타깃 아키텍처용이어야 한다. 호스트 헤더로 빌드한 ARM 바이너리는 엉뚱한 syscall을 부른다.
  • 헤더 버전은 패키지마다 다르다: native linux-libc-dev는 7.0.14, 크로스 패키지는 7.0.0. 둘 다 실행 커널(7.0.0-34)과 별개로 설치된 파일이다. 보드에서는 "툴체인 헤더 버전"과 "보드 커널 uname -r"을 따로 확인해야 한다.
  • qemu-user 아래의 running kernel은 호스트 커널이다 — qemu-user는 커널을 흉내 내지 않는다(§5).

9.3 glibc 버전 — "GLIBC_2.xx not found"의 정체#

무엇을 확인하나: 우리 armhf hello가 요구하는 glibc 심볼 버전과 sysroot의 glibc 버전을 본다. 보드에서 가장 자주 보는 에러 version 'GLIBC_2.38' not found의 원인이다.

출력에서 볼 것: sysroot의 glibc는 2.43인데, 바이너리가 실제로 요구하는 심볼 버전은 최대 GLIBC_2.34다 (__libc_start_main@GLIBC_2.34). 보드 rootfs의 glibc가 2.34 이상이면 돌고, 2.31이면 동적 로더가 version 'GLIBC_2.34' not found로 거부한다. 규칙: sysroot의 glibc ≤ 보드의 glibc. 그래서 "최신 Ubuntu 툴체인으로 빌드해서 옛 BSP rootfs에 올리는 것"이 위험하고, 팀은 보드 rootfs와 짝이 맞는 SDK(Yocto populate_sdk, Buildroot make sdk)를 쓴다 (B2, B5). libc.so.6을 실행 파일처럼 돌리면 버전을 알려 주는 것도 기억해 둘 요령이다.

9.4 multilib vs multiarch#

  • multilib(GCC 개념): 컴파일러 하나가 옵션 조합별로 미리 빌드된 라이브러리 여러 벌을 갖고, -m 옵션에 맞는 디렉터리를 골라 링크한다. arm-none-eabi는 Cortex-M0(v6-m, soft)부터 M4F(v7e-m+fp, hard), Cortex-A까지 39벌이다. x86_64 gcc는 64-bit, -m32, -mx32 3벌.
  • multiarch(Debian 개념): 한 시스템에 여러 아키텍처의 라이브러리를 나란히 설치하는 디렉터리 규칙(/usr/lib/aarch64-linux-gnu, /usr/lib/arm-linux-gnueabihf). 이 VM의 크로스 패키지 레이아웃(/usr/arm-linux-gnueabihf/)도 같은 이름 규칙을 쓴다.

무엇을 확인하나: arm-none-eabi가 -mcpu·-mfloat-abi 조합에 따라 어느 newlib 디렉터리를 고르는지 본다.

출력에서 볼 것: Cortex-M4F + hard는 thumb/v7e-m+fp/hard의 newlib을, M0는 thumb/v6-m/nofp를 쓴다. Don이 펌웨어 Makefile에서 -mcpu와 -mfloat-abi를 컴파일과 링크 양쪽에 똑같이 줘야 했던 이유가 이것이다 — 링크 때 안 주면 기본(.) 라이브러리가 섞여 들어가 ABI 불일치가 난다. 반면 Linux 크로스 툴체인은 대개 multilib 1벌이고, 다른 ABI가 필요하면 툴체인과 sysroot를 통째로 바꾼다.

10. 빌드 시스템과의 접점 — CROSS_COMPILE, ARCH, --host#

10.1 CROSS_COMPILE 관례#

커널, U-Boot, BusyBox, 그리고 많은 펌웨어 Makefile이 쓰는 관례: 툴 이름 앞에 붙일 접두어를 변수 하나로 받는다. 커널 최상위 Makefile에는 실제로 이렇게 적혀 있다 (이 VM의 /lib/modules/$(uname -r)/build/Makefile에서 확인).

그리고 LLVM=1이면 같은 자리에 clang, ld.lld, llvm-objcopy가 들어가는 분기가 있다. ARCH=는 컴파일러가 아니라 커널 소스의 어느 arch/<ARCH>/ 디렉터리를 쓸지를 정한다 (arm64, arm, riscv, x86). 그래서 커널 빌드는 항상 둘을 짝으로 준다.

(위 커널·U-Boot 명령은 형식 소개다. 이 노트에서는 실행하지 않았다.)

무엇을 확인하나: 같은 관례를 쓰는 최소 Makefile로 접두어 하나만 바꿔 세 아키텍처를 빌드한다.

출력에서 볼 것: 접두어가 하이픈으로 끝난다(arm-linux-gnueabihf-). CROSS_COMPILE=arm-linux-gnueabihf(하이픈 없음)로 주면 arm-linux-gnueabihfgcc를 찾다가 실패한다 — 처음 커널 빌드할 때 누구나 한 번 한다.

10.2 C++와 C 라이브러리 선택이 결과물에 주는 영향#

무엇을 확인하나: C++ 크로스 빌드는 libstdc++도 타깃용이 있어야 한다는 것과, C 라이브러리·링크 방식에 따라 크기가 얼마나 달라지는지 본다.

C++ 바이너리는 보드 rootfs에 같은 GCC 계열의 libstdc++.so.6이 있어야 돈다. GLIBCXX_3.4.xx not found가 glibc 버전 문제의 C++ 판이다.

이제 크기. musl은 aarch64 native용 musl-gcc 래퍼만 설치돼 있어서 크기 비교는 aarch64에서 한다 (fs는 §11의 freestanding 프로그램).

그림 8 — 같은 hello의 코드 크기. 정적 glibc는 정적 musl의 17배다. 동적 glibc가 작아 보이는 것은 libc 본체(libc.so.6, 1MB대)가 rootfs에 따로 있기 때문이다.

출력에서 볼 것: "작은 정적 바이너리가 필요하면 musl"이 숫자로 보인다(33KB vs 566KB). 정적 glibc는 printf 하나에도 locale·NSS·스레드 지원이 딸려 온다. newlib-nano(Cortex-M4)는 4KB — Don이 펌웨어에서 --specs=nano.specs를 쓰던 이유다. C 라이브러리 비교는 B2에서 깊게 한다.

11. 커널 안에서는 무슨 일이 일어나나 — 같은 컴파일러, libc 없는 세계#

11.1 커널은 "OS가 없는 프로그램"이다#

이 노트 전체에서 Linux 툴체인은 "libc + crt + 동적 로더"를 얹은 bare-metal 툴체인이라고 설명했다. 그런데 커널 자신은 그 위가 아니라 아래에 있다. 커널이 부팅할 때 그 아래에는 glibc도, crt1.o도, ld-linux.so도 없다. 그래서 커널은 같은 aarch64-linux-gnu-gcc로 빌드하되, 유저 공간용 부품을 전부 빼고 빌드한다. Don에게는 익숙한 세계로 돌아가는 셈이다 — 커널 빌드는 arm-none-eabi로 펌웨어를 빌드하던 방식에 훨씬 가깝다.

그림 9 — 같은 컴파일러로 두 세계를 빌드한다. 오른쪽(커널)은 libc·crt·동적 로더 없이 자기가 필요한 것을 직접 갖춘다. Don의 bare-metal 빌드와 같은 모양이다.

11.2 코드로 확인 — libc 없이 도는 유저 프로그램 (커널 빌드 흉내)#

무엇을 확인하나: -ffreestanding -nostdlib로 libc·crt 없이 빌드하면 무엇이 빠지는지, 그리고 컴파일러가 스스로 memcpy를 부를 수 있다는 것을 확인한다. 커널이 lib/string.c에 memcpy·memset을 직접 갖고 있는 이유다.

출력에서 볼 것:

  • 소스에는 memcpy 호출이 한 줄도 없는데 링커가 memcpy를 찾았다. 1KB 구조체를 문자열 리터럴로 초기화하는 코드를 컴파일러가 memcpy(+memset) 호출로 바꿨기 때문이다. -ffreestanding은 "printf 같은 libc 함수의 의미를 가정하지 마라"는 뜻이지, "memcpy를 절대 부르지 마라"는 뜻이 아니다. GCC 문서도 freestanding 환경에서 memcpy, memmove, memset, memcmp는 제공되어야 한다고 적고 있다.
  • 직접 제공하자 링크되고 실행됐다. 결과물은 심볼 3개, .text 1,308바이트(§10.2 차트)다. _start가 진입점이고, svc #0(A1에서 본 그 syscall)으로 직접 커널을 불렀다. Don의 펌웨어에서 Reset_Handler가 진입점이고 레지스터를 직접 만지던 것과 같은 구조다.

Makefile은 한 줄이다: obj-m := hello_mod.o.

출력에서 볼 것:

  • "The kernel was built by: aarch64-linux-gnu-gcc": Ubuntu의 arm64 커널조차 triplet 접두어가 붙은 이름의 gcc로 빌드됐다. 접두어 없이 gcc로 빌드하자 Kbuild가 "컴파일러가 다르다"고 경고했고, CROSS_COMPILE=aarch64-linux-gnu-을 주자 경고가 사라졌다(/usr/bin/aarch64-linux-gnu-gcc는 같은 GCC 15의 다른 이름이다). 모듈은 커널을 빌드한 것과 같은 컴파일러로 빌드해야 한다 — 플러그인·구조체 레이아웃 옵션이 맞아야 하기 때문이다. 보드용 모듈이면 BSP 커널을 빌드한 그 크로스 툴체인이다.
  • 커널 플래그: -nostdinc(시스템·sysroot 헤더 금지, 커널 include/만), -mgeneral-regs-only(FP/SIMD 레지스터 금지 — 커널은 진입 시 유저의 FP 상태를 저장하지 않으므로, NEON이 필요하면 kernel_neon_begin()/kernel_neon_end()로 감싼다), -fno-PIE, -mstack-protector-guard=sysreg(canary를 libc의 TLS가 아니라 sp_el0가 가리키는 현재 태스크에서 읽음), -D__KERNEL__. -ffreestanding은 arm64 공통 플래그에 없다 — arm64 Makefile은 NEON intrinsic을 쓰는 파일에만 CC_FLAGS_FPU := -ffreestanding을 붙인다(이 VM의 arch/arm64/Makefile 36~41행에서 확인). 링크는 libc 없이 ld -r(재배치 가능 오브젝트) + module.lds 스크립트다.
  • .ko는 REL 파일이고 미해결 심볼이 _printk다. 유저 프로그램의 U printf를 실행 시 동적 로더가 libc에서 해결했다면, 모듈의 U _printk는 insmod 때 커널이 자기 심볼 테이블(EXPORT_SYMBOL)에서 해결한다. vermagic이 커널 버전·설정과 맞아야 로드된다 (E4, E5).

무엇을 확인하나 (실패 예): arm64용으로 configure된 커널 빌드 트리에 32-bit ARM 컴파일러를 들이대면?

출력에서 볼 것: 커널 빌드 트리(.config, 생성된 헤더, 플러그인 설정)는 한 아키텍처·한 컴파일러에 묶여 있다. 모듈만 다른 툴체인으로 빌드하는 것은 불가능하다. 보드용 모듈은 보드 커널 소스 트리 + 그 커널을 빌드한 크로스 툴체인으로 빌드한다 (E4, S 모듈의 out-of-tree 모듈 실습).

14. 면접에서 이렇게 말한다#

Q. "What is a cross compiler, and why do we use one for embedded Linux?"

A. 컴파일러가 도는 기계(host)와 결과물이 도는 기계(target)가 다른 컴파일러다. 보드는 느리고 메모리·저장공간이 작고 rootfs에 개발 도구가 없어서, 빠른 PC에서 보드용 바이너리를 만든다. Linux 타깃이면 컴파일러만이 아니라 타깃용 libc, 동적 로더, 커널 헤더가 담긴 sysroot까지 툴체인에 포함되어야 한다는 점이 bare-metal 크로스 컴파일과 다르다.

A cross compiler runs on one machine — the host — and generates code for a different target. We use it because the target board is slow, memory-limited and usually has no compiler in its rootfs, so we build on a fast workstation. For a Linux target the toolchain isn't just gcc and binutils: it also needs a sysroot with the target's C library, dynamic loader, crt files and kernel UAPI headers, so the binary links against exactly what will be on the board.

꼬리 질문: "What's a Canadian cross?" → build, host, target이 모두 다른 경우. 예: Linux 서버에서 Windows에서 도는 arm-none-eabi-gcc를 빌드.

Q. "Decode the triplet arm-linux-gnueabihf. How is it different from arm-none-eabi?"

A. arch=arm(32-bit), os=linux, 환경=gnueabihf — glibc + ARM EABI + hard-float(float 인자를 VFP 레지스터로). arm-none-eabi는 OS가 없어서 newlib을 정적으로 링크하고, printf의 끝이 _write 같은 스텁이라 내가 UART나 semihosting으로 채워야 한다. Linux 쪽은 printf가 write() syscall로 커널에 넘어가고, 동적 로더가 libc.so를 붙여 준다.

It's arm, Linux, GNU libc, ARM EABI with the hard-float calling convention — floating-point arguments go in VFP registers. arm-none-eabi targets no OS: you link newlib statically, provide your own startup code and linker script, and the bottom of printf is a stub like _write that you implement over a UART or semihosting. With the Linux triplet, printf ends in a write system call into the kernel, and the program is dynamically linked against glibc via ld-linux-armhf.so.3.

Q. "What is a sysroot and what goes wrong if it's wrong?"

A. 타깃 루트 파일시스템의 개발용 축소판이다 — 타깃 libc 헤더·라이브러리, crt 파일, 커널 헤더, 그리고 앱이 쓰는 타깃 라이브러리. 컴파일러가 헤더와 라이브러리를 호스트가 아닌 여기서 찾게 하는 기준 경로다. 틀리면 호스트 헤더가 섞여 링크 실패나 런타임 구조체 불일치가 나고, sysroot의 glibc가 보드보다 새로우면 보드에서 GLIBC_2.xx not found가 난다.

The sysroot is a directory that looks like the target's root filesystem, trimmed for development: the target libc headers and libraries, crt objects, kernel UAPI headers and any target libraries the app depends on. The compiler and linker resolve includes and libraries relative to it instead of the host's /usr. If it's wrong you get host headers leaking in, link failures like "cannot find -lz", or — if the sysroot's glibc is newer than the board's — "GLIBC_2.34 not found" at runtime. That's why teams use the SDK generated from the same Yocto or Buildroot build as the image.

Q. "Explain hard-float vs soft-float on ARM. Can you mix them?"

A. soft는 FPU 명령 없이 libgcc 함수로 float를 흉내 내고, softfp는 FPU 명령은 쓰되 인자는 정수 레지스터로 넘겨 soft와 호환되며, hard는 float 인자를 VFP 레지스터로 직접 넘긴다. soft/softfp와 hard는 호출 규약이 달라서 섞을 수 없고, 링커가 ELF 속성을 보고 거부한다. Linux에서는 배포판 전체가 한 ABI로 빌드되므로 armhf rootfs면 모든 것을 hard로 빌드해야 한다.

Soft-float emulates floating point in libgcc with no FPU instructions; softfp uses the FPU but still passes float arguments in core registers, so it's link-compatible with soft; hard-float passes them in VFP registers, which is faster. Soft and softfp can't be mixed with hard because the calling convention differs — the linker checks the Tag_ABI_VFP_args build attribute and refuses with "uses VFP register arguments". On Linux the whole distribution picks one: armhf means every library is hard-float, so your app must be too.

Q. "What's the difference between -march, -mcpu and -mtune?"

A. -march는 쓸 수 있는 명령어 집합을 정하고, -mtune은 명령어 집합은 그대로 두고 스케줄링만 특정 코어에 맞추고, -mcpu는 둘을 그 코어에 맞게 한 번에 정한다. -march/-mcpu를 보드보다 높게 잡으면 Illegal instruction이 나고, -mtune은 틀려도 느려질 뿐이다. 실제로 ARMv8.1 LSE atomic을 쓰도록 빌드한 바이너리가 Cortex-A53 에뮬레이션에서 SIGILL로 죽는 것을 확인했다.

-march sets which instructions the compiler may emit; -mtune keeps the instruction set but optimises scheduling and cost decisions for a particular core; -mcpu sets both for that core. Overshooting -march or -mcpu gives you SIGILL on older cores — for example, -march=armv8.1-a inlines LSE atomics like ldaddal, which a Cortex-A53 doesn't have. A wrong -mtune only costs performance. For a fleet with mixed cores you build for the lowest -march and rely on runtime dispatch, like GCC's outline atomics on AArch64.

Q. "The kernel headers in your toolchain are newer than the kernel on the board. Is that a problem?"

A. 문제가 될 수 있다. 커널 UAPI는 하위 호환만 보장해서, 옛 헤더로 빌드한 앱은 새 커널에서 돌지만 반대로 새 헤더로 빌드한 앱은 보드 커널에 없는 syscall·ioctl·구조체 필드를 써서 ENOSYS나 EINVAL이 날 수 있다. 그래서 툴체인의 커널 헤더 버전은 보드 커널 이하로 맞춘다. 또 syscall 번호는 아키텍처마다 달라서(openat이 arm64 56, arm 322) 헤더는 반드시 타깃 아키텍처용이어야 한다.

It can be. The kernel only guarantees backward compatibility of its user ABI, so binaries built against older headers run on newer kernels, but headers newer than the running kernel let the program use syscalls, ioctls or struct fields the board's kernel doesn't know, which surface as ENOSYS, EINVAL or ENOTTY. The rule is toolchain headers less than or equal to the oldest kernel you deploy on — Buildroot and Yocto pin the header version to the BSP kernel for that reason. The headers must also be for the target architecture: syscall numbers differ, openat is 56 on arm64 and 322 on 32-bit ARM.

Q. "How is building a kernel module different from building a user-space program?"

A. 같은 크로스 gcc를 쓰지만 libc·crt·동적 로더가 전혀 없다. Kbuild가 -nostdinc로 커널 헤더만 쓰게 하고, arm64에서는 -mgeneral-regs-only로 FP/SIMD를 막고, ld -r과 module.lds로 재배치 가능한 .ko를 만든다. 미해결 심볼은 insmod 때 커널의 export 심볼 테이블로 해결된다. 그리고 반드시 커널을 빌드한 것과 같은 툴체인과 같은 커널 트리로 빌드해야 한다.

It uses the same cross compiler, but there's no libc, no crt and no dynamic loader. Kbuild passes -nostdinc so only kernel headers are visible, -mgeneral-regs-only on arm64 so the compiler never touches FP or SIMD registers, and links with ld -r and module.lds to produce a relocatable .ko. Its undefined symbols, like _printk, are resolved at insmod time against the kernel's exported symbols, and vermagic has to match. You must build it against the same configured kernel tree and with the same toolchain that built the kernel.

꼬리 질문: "Can you use floating point in a driver?" → 기본은 금지. arm64에서는 kernel_neon_begin()/kernel_neon_end() 구간 안에서만, 그 파일은 CC_FLAGS_FPU로 빌드.

Q. "GCC or Clang for cross compiling — what's the practical difference?"

A. GCC는 target마다 컴파일러 바이너리가 따로 있고, Clang은 한 바이너리가 --target으로 모든 아키텍처를 지원한다. 대신 Clang은 libc·crt·libgcc를 sysroot와 GCC 설치본에서 빌려 쓰므로 --sysroot가 필수다. 커널은 둘 다 지원하며 Clang은 LLVM=1로 빌드한다. 벤더 BSP와 U-Boot는 아직 GCC가 기준인 경우가 많다.

GCC is configured for one target per installation, so you get arm-linux-gnueabihf-gcc, aarch64-linux-gnu-gcc and so on. Clang is a single binary with all backends and picks the target with --target, but it doesn't ship a C library or crt files — it borrows them from the sysroot and usually from an installed GCC cross toolchain, so you must pass --sysroot. The kernel builds with both; for Clang you use LLVM=1. In practice vendor BSPs and U-Boot are still GCC-first, while Clang is handy for sanitizers, static analysis and one-compiler CI.

17. 요약 & 체크리스트#

크로스 컴파일은 Don이 이미 하던 일이다. 새로운 것은 Linux 타깃이 OS 위에서 돈다는 사실 하나에서 나온다. 결과물이 타깃 libc와 동적 로더에 링크되므로 툴체인은 sysroot(타깃 libc·crt·커널 UAPI 헤더)를 함께 들고 있어야 한다. triplet은 그 조합(arch, OS, libc, ABI)의 이름이다. 실행 문제는 네 갈래로 나뉜다. 아키텍처가 다르면 Exec format error, 로더나 libc가 없으면 not found·GLIBC_x not found, -march가 너무 높으면 Illegal instruction, ABI가 다르면 링크 거부다. 32-bit ARM의 hard/soft-float는 배포판 단위로 정해진다. -mcpu는 NEON·LSE 같은 기능과 코드 모양을 바꾸고, 그 결과는 objdump로 직접 확인한다. Clang은 컴파일러 하나로 모든 타깃을 다루지만 sysroot를 빌려 쓴다. 커널과 모듈은 같은 크로스 gcc로 빌드하되 libc 없이(-nostdinc, -mgeneral-regs-only, ld -r) 빌드하고, ARCH와 CROSS_COMPILE로 툴체인을 고른다. bare-metal에 가장 가까운 Linux 코드가 바로 커널이다.
