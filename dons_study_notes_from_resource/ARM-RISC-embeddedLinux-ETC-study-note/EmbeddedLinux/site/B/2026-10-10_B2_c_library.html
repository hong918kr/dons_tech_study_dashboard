0. 큰 그림 — libc는 앱과 커널 사이의 "번역층"#

Don이 SSD 펌웨어에서 printf를 쓸 때를 떠올려 보자. 대개 newlib(또는 newlib-nano)이 링크되고, printf는 결국 _write()라는 stub 함수를 부른다. 그 stub은 Don(또는 BSP)이 직접 써서 UART 레지스터에 바이트를 밀어 넣는다. malloc은 _sbrk() stub을 불러 링커 스크립트가 정한 heap 영역을 잘라 준다. 즉 newlib의 아래쪽 끝은 "Don이 채우는 함수 몇 개"다.

Linux에서는 그 아래쪽 끝이 커널이다. C 라이브러리(libc)는 printf의 포맷팅·버퍼링을 한 뒤 write syscall로 커널에 넘기고, malloc은 brk/mmap syscall로 커널에게 페이지를 받는다. 그리고 Linux libc는 newlib에는 없는 일을 잔뜩 한다: 스레드(NPTL), 동적 라이브러리 로딩(ld.so), 사용자·호스트 이름 조회(NSS, DNS resolver), 로케일·문자 변환(locale, iconv), 그리고 프로그램 시작·종료 처리(crt1.o, __libc_start_main, atexit).

그림 1 — Linux libc는 앱과 커널 사이의 번역층이다. newlib의 "stub 함수" 자리에 Linux에서는 커널 syscall이 있고, 그 위에 스레드·동적 로딩·NSS 같은 OS 기능이 더 얹힌다.

Embedded Linux 엔지니어가 libc를 신경 써야 하는 장면은 이렇다.

  • 이미지 크기: 32 MB SPI-NOR에 rootfs를 넣어야 하는 게이트웨이라면 glibc(공유 라이브러리만 약 2 MB, 로케일·gconv까지 넣으면 훨씬 큼) 대신 musl(약 0.8 MB 파일 하나)로 가는 결정이 바로 나온다 (§3, §9).
  • 호환성: Jetson이나 i.MX8의 GPU/NPU 드라이버 유저 공간 라이브러리는 대부분 glibc용 바이너리로만 온다. musl rootfs에서는 붙지 않는다 (§9).
  • 배포 사고: 개발 PC(Ubuntu 최신)에서 빌드한 진단 툴을 보드에 scp했더니 version 'GLIBC_2.38' not found. 원인은 심볼 버전 (§7).
  • 성능·안정성: musl로 옮겼더니 멀티스레드 로깅 데몬이 느려졌다(malloc), 또는 스레드 안의 깊은 재귀가 segfault 났다(기본 스레드 스택 128 KiB) (§4).

실행 환경: 모든 출력은 Lima VM elinux(aarch64, uname -r = 7.0.0-34-generic, gcc 15.2, glibc 2.43, musl 1.2.5)에서 실제로 돌린 결과다. PID·주소·시간은 실행마다 다르다. 바이너리는 /tmp/B2/에 만들었다.

1. libc가 실제로 하는 일#

"C 라이브러리"라고 하면 strlen, printf 같은 함수 모음을 떠올리기 쉽다. 그건 일부일 뿐이고, Linux에서 libc는 POSIX API를 커널 syscall 위에 구현한 런타임이다. 하나씩 본다.

1.1 syscall 래퍼와 errno#

직관: 커널은 C 함수가 아니다. 커널에 일을 시키려면 레지스터에 번호와 인자를 넣고 svc #0 예외를 일으켜야 한다(A1). libc의 close(), read() 같은 함수는 이 일을 대신해 주는 얇은 래퍼다.

정의: arm64에서 커널은 결과를 x0에 돌려주는데, 실패하면 음수 에러 번호(-EBADF = -9 같은)를 준다. POSIX는 "실패하면 -1을 반환하고 원인은 errno에"라는 규약이다. 이 둘을 맞춰 주는 게 libc 래퍼다: 반환값이 -4095~-1 범위면 errno = -반환값, 반환은 -1로 바꾼다. 그리고 errno는 전역 변수가 아니라 스레드마다 따로 있는 변수(TLS, thread-local storage)다. glibc 헤더는 errno를 (*__errno_location ())로 정의한다.

무엇을 확인하나: 인라인 svc #0으로 커널을 직접 부른 결과(-9)와, libc close()·syscall()의 결과(-1 + errno 9)를 비교하고, errno 주소가 스레드마다 다른지 본다.

출력에서 볼 것: 커널의 원래 답은 -9이고, glibc든 musl이든 래퍼가 -1 + errno=9로 바꾼다. &errno가 스레드마다 다르다 — 그래서 멀티스레드에서도 errno가 섞이지 않는다. 번호 57과 9는 libc가 정한 게 아니라 커널 UAPI 헤더에서 온다 (§10).

Don 경험과 연결: newlib에서 errno는 struct _reent 안에 있고, RTOS 태스크마다 _impure_ptr를 바꿔 주는 방식으로 "태스크별 errno"를 흉내 냈다. Linux libc는 같은 목적을 CPU의 스레드 포인터 레지스터(arm64 TPIDR_EL0)가 가리키는 TLS 블록으로 해결한다.

함정: 성공한 호출은 errno를 지우지 않는다. "반환값이 -1일 때만 errno를 본다"가 규칙이다 (A1 §12).

1.2 stdio 버퍼링 — printf 한 번 ≠ write 한 번#

직관: newlib에서 UART로 printf하면 바로 나가는 경우가 많았다. Linux libc의 stdout은 버퍼를 가진다. 출력 대상이 터미널이면 줄 단위(line buffered), 파일·파이프면 블록 단위(fully buffered)로 모았다가 write syscall을 한 번에 한다. 블록 크기는 libc마다 다르다.

무엇을 확인하나: 같은 printf 1000줄(47,000바이트)이 glibc와 musl에서, 파일과 터미널(pty)로 보낼 때 각각 write syscall 몇 번이 되는지 센다.

musl 쪽 write 크기 분포도 보자 (strace 출력 일부를 ... 없이 앞 4줄만 남겼다).

출력에서 볼 것: 파일로 보낼 때 glibc는 4096바이트(파일의 st_blksize) 단위로 12번, musl은 1024바이트 버퍼 + 새 데이터를 writev로 묶어 47번 쓴다. 터미널이면 둘 다 줄마다 1000번이다. musl은 첫 출력 때 ioctl(TIOCGWINSZ)로 "터미널인가"를 확인하고 그때까지는 줄 단위로 동작해서 첫 줄은 따로 나갔다.

함정: 센서 로그를 파이프(./daemon | logger)로 넘기면 블록 버퍼링 때문에 로그가 몇 KB씩 늦게 나온다. setvbuf(stdout, NULL, _IOLBF, 0) 또는 fflush, 아니면 stderr(기본 unbuffered)를 쓴다. 그리고 fork() 전에 fflush하지 않으면 버퍼 내용이 두 번 출력된다(A2).

1.3 malloc — 커널에서 페이지를 받아 잘게 나눠 주는 할당기#

newlib의 malloc은 _sbrk로 고정 heap을 늘려 가는 단순한 할당기였다. Linux libc의 malloc도 원리는 같지만 커널에서 메모리를 받는 방법이 두 가지다: 작은 할당은 brk(데이터 세그먼트 끝을 올림)로 늘린 heap에서, 큰 할당(glibc 기본 128 KiB 이상)은 mmap으로 따로 받는다(A5).

  • glibc malloc (ptmalloc2): 스레드별 arena와 tcache(스레드별 작은 캐시)를 둬서 스레드끼리 잠금 경쟁이 적다. 빠르지만 메모리를 넉넉히 쓰고 단편화가 생길 수 있다. mallopt, GLIBC_TUNABLES로 조정한다.
  • musl malloc (mallocng, 1.2.1부터): 메모리 효율·보안(메타데이터 분리, 해제 검증)을 우선한 설계라 단일 스레드에서도 느리고, 잠금이 사실상 전역이라 스레드가 늘면 더 느려진다. 그래서 musl 기반 이미지에서 할당이 많은 서비스는 mimalloc·jemalloc 같은 할당기를 따로 링크하기도 한다.

§4.1에서 직접 잰다.

1.4 pthread와 NPTL#

NPTL(Native POSIX Thread Library)은 glibc의 pthread 구현이다. 스레드 하나 = 커널 태스크 하나(1:1 모델)이고, pthread_create는 스택을 mmap으로 만들고 clone() syscall을 부른다. 뮤텍스는 경쟁이 없으면 유저 공간 원자 연산만으로 끝나고, 경쟁이 생길 때만 futex syscall로 커널에서 잠든다(A8). glibc 2.34부터는 libpthread가 libc.so.6 안으로 합쳐졌다. musl도 같은 1:1 모델이고 처음부터 libc 하나에 다 들어 있다. 차이는 기본 스레드 스택 크기(§4.2)와 세부 기능(예: 일부 _np 확장 함수 지원 여부)이다.

1.5 locale·iconv, NSS·DNS resolver — glibc가 커지는 이유#

  • locale: 숫자·날짜 포맷, 문자 분류(isalpha), 멀티바이트 변환을 언어별로 바꾸는 기능. glibc는 로케일 데이터를 /usr/lib/locale/locale-archive(이 VM에서 3 MB)에 두고, 문자셋 변환(iconv)은 gconv 모듈(이 VM의 /usr/lib/aarch64-linux-gnu/gconv에 256개 파일, 약 20 MB)을 dlopen으로 불러 쓴다. musl은 사실상 C와 UTF-8만 지원하고 iconv 변환표를 libc 안에 넣었다.
  • NSS(Name Service Switch): getpwnam("root"), getaddrinfo("imu-gw") 같은 "이름 → 정보" 조회를 /etc/nsswitch.conf가 정한 순서(files, dns, systemd, ldap …)대로 플러그인 .so를 dlopen해서 처리하는 glibc 구조다. 유연하지만 정적 링크와 궁합이 나쁘다(§8). musl은 NSS가 없고 /etc/passwd, /etc/hosts, DNS만 직접 읽는다.
  • DNS resolver: getaddrinfo 안의 DNS 클라이언트. musl은 여러 네임서버에 동시에 질의하는 등 동작이 다르고, TCP fallback은 1.2.4에서야 들어왔다. 이 차이로 "glibc에선 되는데 Alpine 컨테이너에선 이름이 안 풀린다" 같은 이슈가 생긴다.

1.6 시작 코드와 atexit#

newlib 프로젝트에서 crt0.s(또는 startup_stm32xxx.s)가 .data 복사, .bss 0 채우기, __libc_init_array() 호출, 그리고 main 호출을 했다. Linux에서는 .data/.bss 준비를 커널의 ELF 로더(와 동적 로더)가 해 주고, libc의 시작 코드는 crt1.o(PIE면 Scrt1.o)의 _start → __libc_start_main이다. 이 함수가 TLS·스택 가드·init_array(C++ 전역 생성자, __attribute__((constructor)))를 처리하고 main을 부르며, main이 돌아오면 exit()이 atexit 핸들러 → fini_array → stdio flush → exit_group syscall 순서로 정리한다. §5에서 gdb로 따라간다.

2.2 지금 어떤 libc인가 확인하기#

무엇을 확인하나: 컴파일 시점(__GLIBC__ 매크로)과 실행 시점(gnu_get_libc_version())에 libc 종류·버전을 알아내는 방법.

출력에서 볼 것: 보드에 셸로 들어가서 libc 버전을 모를 때 가장 확실한 방법은 libc 파일 자체를 실행하는 것이다(getconf·ldd가 없는 BusyBox rootfs에서도 된다). musl은 "기능을 검사하라, 버전을 검사하지 말라"는 철학이라 __MUSL__ 같은 매크로가 없다. 그래서 #ifdef __GLIBC__ ... #else /* musl 등 */처럼 쓴다.

2.3 musl-gcc는 무엇인가#

Ubuntu의 musl-tools가 주는 musl-gcc는 별도 컴파일러가 아니라 시스템 gcc에 specs 파일을 끼워 헤더·crt·libc 경로만 musl 쪽으로 바꾸는 래퍼 스크립트다.

libm.a, libpthread.a 등이 있지만 musl에서는 전부 빈 껍데기이고 실제 코드는 libc.a/libc.so 하나에 들어 있다. C++이나 다른 라이브러리(OpenSSL 등)까지 musl로 빌드하려면 이 래퍼로는 부족하고, musl 기반 크로스 툴체인(Buildroot·Yocto가 만든 것, musl.cc 계열, aarch64-linux-musl-gcc)을 쓴다 (B1, B5).

3. 측정 1 — 크기와 시작 비용#

3.1 hello 4종 — 바이너리 크기#

무엇을 확인하나: 같은 hello를 glibc/musl × 동적/정적으로 빌드해 파일 크기와 실제 코드·데이터 크기(size)를 비교한다.

출력에서 볼 것: 파일 크기(ls)만 보면 이상하다 — strip한 musl 정적 hello(66,952)가 동적 hello(67,128)와 비슷하다. 이유는 arm64 링커의 기본 max-page-size가 64 KiB라서 세그먼트 사이가 0으로 채워지기 때문이다. 진짜 크기는 size의 text+data다: glibc 정적은 532 KB의 코드를 끌고 오고, musl 정적은 32 KB다.

64 KiB 정렬을 빼고(-Wl,-z,max-page-size=4096) 다시 재면 차이가 그대로 보인다. 더 현실적인 프로그램 두 개(§8의 NSS 조회 프로그램, §4.1의 malloc+pthread 벤치)도 함께 쟀다.

그림 2 — glibc vs musl 크기 실측. 정적 바이너리는 10~16배 차이, 동적 바이너리는 거의 같다(코드가 공유 라이브러리에 있으므로). rootfs에 들어갈 libc 런타임 자체는 2.5배 차이다. 막대 길이는 같은 선형 축.

해석: 동적 링크면 앱 바이너리 크기는 libc와 거의 무관하고, 차이는 rootfs에 한 번 들어가는 libc 런타임(glibc 1.90 MiB vs musl 0.77 MiB, glibc는 로케일·gconv·NSS 모듈을 넣으면 더 커진다)에서 난다. 정적 링크면 바이너리마다 libc가 복사되니 musl의 작은 크기가 결정적이다. 이 VM에서 패키지 단위로 보면 libc6 패키지 파일 합계가 4,934,351바이트, musl 패키지가 804,564바이트였다(dpkg -L 목록의 일반 파일 크기 합).

3.2 시작할 때 syscall 몇 번?#

무엇을 확인하나: main에 닿기 전에 libc·로더가 커널에 무엇을 부탁하는지 strace로 본다.

순서까지 보려면 strace 전체 출력이 낫다. glibc 동적 hello의 전체 트레이스를 주석과 함께 본다 (전체 37줄 그대로).

줄별로 읽는 법:

  1. faccessat("/etc/ld.so.preload") ~ close(3): 동적 로더가 일하는 구간. preload 목록 확인, /etc/ld.so.cache(라이브러리 이름 → 경로 색인)를 mmap해서 libc.so.6 위치를 찾고, libc를 열어 ELF 헤더 832바이트를 읽은 뒤 세그먼트별로 mmap한다. 마지막 PROT_EXEC|0x10의 0x10은 arm64의 PROT_BTI(Branch Target Identification 보호)다.
  2. set_tid_address, set_robust_list, rseq: NPTL 초기화. 스레드 종료 시 futex를 깨울 주소, 뮤텍스 소유자가 죽었을 때를 위한 robust list, restartable sequences 등록.
  3. mprotect(..., PROT_READ): RELRO — 재배치가 끝난 GOT 등을 읽기 전용으로 잠근다(B3).
  4. prlimit64(RLIMIT_STACK): glibc가 기본 스레드 스택 크기를 정하려고 스택 rlimit을 읽는다 (§4.2의 8 MiB가 여기서 온다).
  5. getrandom(8 bytes): malloc 내부 보호용 난수 키 초기화(glibc malloc.c의 tcache key로 알고 있다).
  6. fstat(1), ioctl(1, TCGETS2): stdio가 stdout이 터미널인지 확인해 버퍼링 방식을 고른다 (§1.2).
  7. brk: printf가 stdout 버퍼를 malloc하면서 heap이 처음 생긴다.

musl 정적 hello는 execve → set_tid_address → ioctl(TIOCGWINSZ) → writev → exit_group이 전부다. 로더 단계도 없고, robust list·rseq도 필요해질 때까지 미룬다.

3.3 시작~종료 시간#

무엇을 확인하나: 프로그램을 2000번 posix_spawn → waitpid해서 1회 평균 시간(fork·exec·로딩·종료 포함)을 잰다. 셸 스크립트에서 작은 툴을 수천 번 부르거나, 이벤트마다 helper를 실행하는 장비에서 체감되는 숫자다.

그림 3 — hello 1회 실행 비용(3회 측정 평균)과 시작 syscall 수. 진한 막대는 동적, 옅은 막대는 정적. 동적 → 정적, glibc → musl로 갈수록 로더·초기화 작업이 줄어든다.

출력에서 볼 것: 75~190 µs 중 상당 부분은 libc와 무관한 fork/exec/종료 비용이다. 그 위에 동적 로딩이 약 60 µs(glibc 동적 vs 정적), glibc 초기화가 약 50 µs(glibc 정적 vs musl 정적) 얹힌다. 한 번 뜨고 계속 도는 데몬에는 의미 없는 차이지만, 부팅 중 스크립트가 작은 툴을 수백 번 부르는 장비에선 부팅 시간에 드러난다.

4. 측정 2 — 런타임 성격: malloc, 스레드 스택, vDSO#

4.1 malloc 마이크로벤치#

무엇을 확인하나: 16~255바이트 블록을 무작위로 할당·해제하는 루프(스레드당 200만 회)를 1개, 4개 스레드에서 돌려 glibc와 musl의 할당기 비용을 비교한다.

출력에서 볼 것: ns/op (wall)은 "전체 경과 시간 ÷ 전체 연산 수"라서 스레드가 늘면 작아지는 게 정상이다(4코어 VM). glibc는 1 → 4 스레드에서 7.3 → 3.2 ns로 처리량이 늘었고(스레드별 tcache·arena), musl은 39.9 → 93.9 ns로 오히려 느려졌다 — 4개 스레드가 할당기 잠금을 두고 싸우기 때문이다. 단일 스레드에서도 약 5배 차이다.

4.2 기본 스레드 스택 크기 — 8 MiB vs 128 KiB#

직관: RTOS에서 태스크를 만들 때 스택 크기를 반드시 지정했다. pthread는 지정하지 않으면 libc 기본값을 쓰는데, 그 기본값이 glibc와 musl에서 60배 이상 다르다. glibc는 ulimit -s(RLIMIT_STACK, 보통 8 MiB) 값을 쓰고, musl은 128 KiB 고정이다.

무엇을 확인하나: 스레드 안에서 프레임당 약 1 KiB를 쓰는 재귀를 N단계 하고, 기본 스택 크기를 출력한다. 두 번째 인자를 주면 스택 크기를 명시한다.

출력에서 볼 것: 같은 코드가 glibc에선 통과, musl에선 SIGSEGV(exit 139). 스택 끝의 guard page를 넘어서 죽은 것이다(bash의 "Segmentation fault" 메시지는 stderr라 출력 순서가 뒤로 밀렸다). glibc의 기본값은 ulimit -s를 따라 512 KiB로도 바뀐다 — §3.2 strace의 prlimit64(RLIMIT_STACK)이 이 값을 읽는 장면이었다. musl의 pthread_getattr_np는 130 KiB로 보고했다(128 KiB에 약간의 여유가 붙은 값).

musl은 링크 시점에 기본값을 바꾸는 방법도 지원한다: PT_GNU_STACK 프로그램 헤더의 크기 필드를 기본 스레드 스택 크기로 쓴다.

Don 경험과 연결: RTOS에서 "태스크 스택은 항상 명시하고, 워터마크로 사용량을 잰다"가 습관이었다면 그대로 가져오면 된다. 제품 코드에서는 libc 기본값에 기대지 말고 pthread_attr_setstacksize로 명시한다. 그러면 glibc(8 MiB 가상 예약 × 스레드 수 → 32-bit 보드에서 주소 공간 부족)와 musl(128 KiB → 재귀·큰 지역 배열에서 segfault) 양쪽 함정을 다 피한다.

4.3 vDSO와 clock_gettime — 이 VM에서 발견한 차이#

vDSO(virtual dynamic shared object)는 커널이 모든 프로세스에 자동으로 매핑해 주는 작은 공유 라이브러리다. clock_gettime, gettimeofday 같은 "읽기만 하는" 호출을 커널 진입 없이 유저 공간에서 처리한다(A1). libc는 시작할 때 auxv의 AT_SYSINFO_EHDR로 vDSO 위치를 받아 심볼을 찾아 둔다.

무엇을 확인하나: vDSO가 어디 매핑되는지, 그리고 clock_gettime 10만 번이 실제 syscall이 되는지를 glibc와 musl에서 본다.

glibc는 10만 번 호출에 clock_gettime syscall이 0번, musl은 10만 번 전부 커널로 갔다. 비용으로도 확인한다.

(순서대로 glibc 동적, musl 동적, musl 정적.) 왜 그럴까? 이 VM 커널의 vDSO를 덤프해 보면 심볼 해시 테이블이 DT_GNU_HASH만 있고 고전적인 DT_HASH(SysV hash)가 없다.

musl 1.2.5의 vDSO 심볼 조회 코드(src/internal/vdso.c의 __vdsosym)는 DT_HASH만 읽는다. 그래서 vDSO 심볼을 못 찾고 매번 진짜 syscall로 fallback한 것이다. musl git 이력으로 확인한 사실: GNU hash 지원은 2026-03-19 커밋 "vdso: add support for GNU hash tables"에서야 추가됐다(그 뒤 코드는 DT_HASH가 없으면 DT_GNU_HASH로 심볼 수를 센다). 즉 이 커밋이 들어간 musl 릴리스로 올리면 이 차이는 사라진다 — 어떤 musl 버전을 쓰는지 ldd --version(musl은 로더를 실행하면 버전을 출력)으로 꼭 확인하자. 실무 교훈: "libc를 바꾸면 커널 버전과의 조합까지 바뀐다". 타임스탬프를 초당 수만 번 찍는 센서 파이프라인이라면 이런 차이가 CPU 사용률로 드러난다.

그림 4 — 런타임 비용 실측. musl은 크기·시작에서 이기고, 할당이 많은 멀티스레드 코드와 (이 커널 조합에서) 시간 조회에서 진다.

5. 프로그램이 main에 닿기까지#

5.1 전체 흐름#

그림 5 — 동적 링크된 프로그램의 시작 순서. 주황 = 커널, 초록 = 동적 로더, 회색 = crt 시작 코드, 파랑 = libc와 사용자 코드. 정적 바이너리면 로더 단계가 없고 커널이 바로 프로그램의 _start로 들어간다.

bare-metal과 비교하면: 리셋 벡터 → Reset_Handler(crt0) → SystemInit → .data/.bss 준비 → __libc_init_array → main의 흐름에서, Linux는 "리셋 벡터"가 execve, ".data 복사"가 커널의 mmap(파일에서 페이지 단위로 매핑, 실제 복사는 page fault 때), "__libc_init_array"가 __libc_start_main 안의 init_array 처리다.

5.2 코드로 확인 — constructor, atexit, destructor 순서#

무엇을 확인하나: main 전후에 libc가 실행하는 사용자 코드의 순서.

출력에서 볼 것: 두 libc 모두 같은 순서다. atexit로 나중에 등록한 핸들러가 먼저 실행되고(LIFO), 그 뒤 destructor가 돈다. 주의: _exit()나 시그널로 죽으면 [4], [5]와 stdio flush가 전부 생략된다 (A6).

5.3 gdb로 시작 체인 따라가기#

무엇을 확인하나: 첫 명령어가 실행되는 곳(로더의 _start), 프로그램의 _start, 그리고 main의 호출 스택.

출력에서 볼 것: starti(첫 명령에서 멈춤)의 위치는 프로그램이 아니라 /lib/ld-linux-aarch64.so.1의 _start다. 커널이 먼저 로더를 실행한다는 증거다. _start라는 이름이 로더와 프로그램 두 곳에 있어서 "2 locations"가 나왔다. bt는 _start → __libc_start_main_impl → __libc_start_call_main → main 체인을 보여 준다. [PAC]는 arm64 Pointer Authentication으로 서명된 반환 주소라는 표시다. 같은 걸 musl로 하면 #1 0x... in ?? () from /lib/ld-musl-aarch64.so.1처럼 디버그 심볼 없는 한 단계로 끝난다(musl의 __libc_start_main이 libc.so 안에 있다).

6. 동적 로더 ld-linux-aarch64.so.1#

6.1 PT_INTERP와 DT_NEEDED — 누가 로더를 고르고, 로더는 무엇을 붙이나#

정의: 동적 링크된 ELF에는 두 가지 표시가 있다.

  • PT_INTERP 프로그램 헤더: "이 프로그램은 이 로더로 실행하라"는 절대 경로. 커널의 ELF 로더(fs/binfmt_elf.c)가 이걸 보고 로더도 함께 매핑한 뒤 로더의 진입점으로 점프한다.
  • DT_NEEDED 동적 섹션 항목: "이 라이브러리들이 필요하다"는 이름(soname). 로더가 검색 경로에서 찾아 붙인다.

그림 6 — 동적 로딩 흐름. 커널은 PT_INTERP만 보고 로더를 붙여 주고, 나머지(DT_NEEDED 검색, 버전 확인, 재배치)는 전부 유저 공간의 로더가 한다. vDSO는 파일 없이 커널이 넣어 준 라이브러리다.

무엇을 확인하나: 실제 ELF의 PT_INTERP와 DT_NEEDED를 읽고, 로더를 직접 실행 파일처럼 써서 프로그램을 돌려 본다.

출력에서 볼 것: glibc 바이너리는 libc.so.6, musl 바이너리는 libc.so를 요구한다 — soname부터 다르니 서로의 rootfs에서 섞일 수 없다. musl은 로더와 libc가 같은 파일이다(libc.so => /lib/ld-musl-aarch64.so.1). 로더를 직접 실행하는 기법은 실무에서 쓸모가 많다: 보드의 /lib에 로더가 없거나 경로가 다를 때 /opt/sdk/lib/ld-linux-aarch64.so.1 --library-path /opt/sdk/lib ./tool처럼 다른 libc 세트로 프로그램을 띄울 수 있다.

6.2 LD_DEBUG — 로더가 하는 일을 말로 듣기#

glibc 로더는 환경 변수 LD_DEBUG로 내부 동작을 출력한다(musl은 이 기능이 없다).

libs (빈 줄은 생략했다):

bindings 중 프로그램 자신의 심볼만, 그리고 versions, statistics:

출력에서 볼 것:

  • libs: libc.so.6을 /etc/ld.so.cache에서 찾았다. 새 라이브러리를 /usr/local/lib에 넣고 ldconfig를 안 돌리면 "not found"가 나는 이유가 이것이다.
  • bindings: printf가 아니라 __printf_chk에 결합됐다 — Ubuntu gcc는 기본으로 _FORTIFY_SOURCE를 켜서 버퍼 검사판 함수로 바꾼다. malloc, calloc, free, realloc, _r_debug는 프로그램이 부른 게 아니라, 로더가 자기 초기 할당기를 libc의 malloc으로 갈아 끼우고 디버거용 _r_debug를 찾느라 생긴 결합이다. 대괄호 안의 [GLIBC_2.17]이 심볼 버전이다 (§7).
  • versions: 로더가 "이 프로그램이 요구하는 GLIBC_2.17, GLIBC_2.34가 libc에 있나"를 실제로 검사한다. 여기서 없으면 §7의 에러가 난다.
  • BIND_NOW: Ubuntu는 기본으로 -z now(시작 시 모든 심볼 결합)라서 지연 결합(lazy binding)이 없다. 시작은 조금 느려지지만 GOT 전체를 RELRO로 잠글 수 있다 (B3).

ltrace도 같은 결합 지점(PLT)을 가로채 라이브러리 호출을 보여 준다.

6.3 ldd는 왜 위험할 수 있나 — 그리고 대안#

ldd는 ELF 분석기가 아니라 셸 스크립트다. 로더에 LD_TRACE_LOADED_OBJECTS=1을 주고 대상 프로그램을 로딩시켜서, 로더가 찍는 목록을 보여 준다.

ldd(1) man 페이지는 "일부 버전의 ldd는 프로그램이 지정한 ELF 인터프리터를 직접 실행해 정보를 얻으려 할 수 있으니, 신뢰할 수 없는 실행 파일에 ldd를 쓰지 말라"고 경고한다. PT_INTERP가 공격자가 만든 파일을 가리키면 ldd만 했는데 그 코드가 실행된다는 뜻이다. 이 VM에서 직접 실험해 본다.

무엇을 확인하나: PT_INTERP를 가짜 로더로 바꾼 "트로이 목마" 바이너리를 만들고, 직접 실행할 때와 ldd할 때 각각 무슨 일이 생기는지 본다.

출력에서 볼 것:

  1. 직접 실행하면 커널은 PT_INTERP에 적힌 아무 파일이나 로더로 실행한다. 프로그램의 main은 한 줄도 돌지 않았다. "로더는 그냥 프로그램"이라는 증거다.
  2. 이 VM의 glibc 2.43 ldd는 가짜 로더를 실행하지 않았다 — 스크립트가 항상 시스템 로더(RTLDLIST)로 대상을 로딩한다. 대신 /tmp/B2/evil_ld => /lib/ld-linux-aarch64.so.1이라는 사실과 다른 줄을 보여 준다. 즉 최신 glibc의 ldd도 "실행해 보고 결과를 듣는" 방식이라 정확한 분석이 아니고, 다른 구현·오래된 버전에서는 man 페이지 경고대로 직접 실행될 수 있다.

외부 바이너리(크로스 빌드 결과물, musl 바이너리)에서도 ldd는 엉뚱한 답을 한다.

musl 바이너리는 glibc 로더가 libc.so라는 이름으로 glibc의 개발용 링커 스크립트 텍스트 파일을 집어 들고 "invalid ELF header"를 냈고, x86_64 바이너리는 멀쩡히 동적 링크된 파일인데 "not a dynamic executable"이라고 한다. 규칙: 의존성은 readelf -d/objdump -p로 정적으로 읽는다. 실제 로딩 결과가 필요하면 타깃 보드에서 그 보드의 로더로 --list를 쓴다.

6.4 vDSO 다시 보기#

§6.2의 bindings 출력 맨 앞에는 이런 줄들이 있었다 (전체 94줄 중 앞 4줄).

vDSO도 로더 입장에선 평범한 공유 라이브러리이고, 심볼 버전(LINUX_2.6.39)까지 가진다. 커널 7.0의 arm64 vDSO는 __kernel_getrandom도 제공한다. glibc는 이것을 찾아 두고 clock_gettime·getrandom을 커널 진입 없이 처리한다. 디스크에 파일이 없으므로 rootfs에서 지울 수도, 버전을 섞을 수도 없다.

7. 심볼 버저닝과 "version `GLIBC_2.38' not found"#

7.1 직관 — 함수 이름에 "생년"이 붙어 있다#

glibc는 하위 호환을 위해 같은 이름의 함수를 여러 버전으로 들고 다닌다. 예를 들어 어떤 함수의 동작을 바꿔야 하면 옛 버전(foo@GLIBC_2.17)은 그대로 두고 새 버전(foo@@GLIBC_2.38)을 추가한다. 새로 링크하는 프로그램은 새 버전에 묶이고, 옛 프로그램은 옛 버전을 계속 쓴다. 덕분에 옛날에 빌드한 바이너리는 새 glibc에서 돈다(하위 호환). 반대 방향은 보장되지 않는다: 새 glibc로 빌드한 바이너리는, 그 버전 태그가 없는 옛 glibc에서 실행 전에 거부된다.

7.2 코드로 확인 — 평범한 코드가 요구하는 태그#

무엇을 확인하나: 센서 주기를 파싱하는 평범한 코드가 어떤 GLIBC_2.xx 태그를 요구하는지 objdump -T로 본다.

출력에서 볼 것 세 가지:

  1. strtol이 __isoc23_strtol@GLIBC_2.38로 바뀌었다. gcc 15의 기본 언어 표준이 C23(__STDC_VERSION__ 202311L)이고, C23에서 strtol이 0b 접두사를 받도록 바뀌어 glibc 2.38이 새 진입점을 만들었기 때문이다. 코드는 C89 시절 그대로인데 컴파일러 기본값 때문에 요구 버전이 올라갔다.
  2. strlcpy는 glibc 2.38에서 처음 들어온 함수라 당연히 2.38을 요구한다.
  3. __libc_start_main@GLIBC_2.34: glibc 2.34 이상에서 빌드한 모든 동적 바이너리가 요구한다(그 버전에서 libpthread 통합과 함께 시작 코드 인터페이스가 바뀌었다). 즉 hello조차 glibc 2.33 이하 rootfs에서는 돌지 않는다. arm64의 최소 태그가 GLIBC_2.17인 이유는 glibc가 aarch64를 처음 지원한 버전이 2.17이기 때문이다.

7.3 에러 재현 — "옛 rootfs" 흉내#

이 VM에는 오래된 glibc가 없으므로, GLIBC_2.17과 GLIBC_2.34만 정의한 가짜 libc.so.6을 만들어 LD_LIBRARY_PATH로 먼저 잡히게 해서 "glibc 2.34~2.37 rootfs"를 흉내 낸다. 에러 문구는 진짜 로더가 낸 것이다.

이것이 임베디드에서 가장 흔한 libc 에러의 정체다. 로더는 §6.2의 versions 단계에서 프로그램의 Version References(요구 목록)와 libc의 Version definitions(제공 목록)를 대조하고, 하나라도 없으면 main 근처에도 가지 않고 끝낸다.

그림 7 — "빌드는 새 glibc, 실행은 옛 glibc"가 에러의 원인이다. glibc는 옛 바이너리 → 새 libc 방향만 보장한다.

7.4 고치기 — 요구 태그 낮추기#

무엇을 확인하나: C17 모드로 빌드하고 strlcpy를 피하면 요구 태그가 2.34로 내려가는지 본다. 그리고 시스템 바이너리들의 최고 요구 버전을 비교한다.

출력에서 볼 것: strtol이 옛 GLIBC_2.17 버전으로 돌아왔다. snprintf는 gcc가 상수 문자열 복사로 최적화해 아예 사라졌다. 이 VM의 /bin/ls는 GLIBC_2.43을 요구한다 — 배포판 바이너리를 다른 rootfs로 복사하는 것도 같은 이유로 실패한다.

-std=gnu17은 응급처치일 뿐이다. 근본 해결은 타깃 rootfs와 같은 glibc 버전의 sysroot로 빌드하는 것이다(B1의 --sysroot, Yocto populate_sdk, Buildroot의 host/ 툴체인). 그러면 링커가 애초에 타깃 libc에 없는 버전에는 묶지 않는다.

8. 정적 링크 — glibc에서의 함정#

"정적 링크하면 libc 의존성이 사라지니 아무 보드에서나 돈다"는 musl에선 대체로 맞고, glibc에선 반만 맞다. glibc의 일부 기능은 정적 바이너리 안에서도 실행 중에 공유 라이브러리를 dlopen하기 때문이다: NSS(getpwnam, getaddrinfo의 일부 경로), iconv(gconv 모듈), dlopen 자체.

무엇을 확인하나: 사용자·호스트 이름 조회를 정적 링크할 때 링커 경고, 그리고 실제 실행 중에 무엇을 여는지.

경고 문장이 핵심이다: "정적 링크했지만 실행할 때 링크에 쓴 것과 같은 버전의 glibc 공유 라이브러리가 필요하다". 이번엔 root가 /etc/passwd(files 모듈, glibc 2.34부터 libc에 내장)에서 바로 찾아져서 아무것도 dlopen하지 않았다. 그럼 files에 없는 이름을 조회하면?

(이후 systemd userdb 조회용 openat 수십 줄은 생략했다. 마지막 줄은 no_such_user: not found.)

출력에서 볼 것: "정적" 바이너리가 실행 중에 libnss_systemd.so.2를 열고, 그것이 의존하는 공유 libc.so.6과 로더까지 끌어왔다. 한 프로세스 안에 정적으로 박힌 glibc 2.43과 공유 glibc가 함께 있는 셈이고, 두 버전이 다르면(다른 rootfs로 복사하면) 내부 자료구조가 안 맞아 크래시하거나 조회가 조용히 실패한다. musl 정적 바이너리는 NSS가 없어서 이 문제가 없는 대신, LDAP·systemd 사용자 같은 NSS 확장도 쓸 수 없다.

glibc 정적 링크의 다른 주의점:

  • LGPL: glibc를 정적 링크한 바이너리를 배포하면, 사용자가 다른 glibc로 다시 링크할 수 있도록 오브젝트 파일 등을 제공해야 하는 의무가 생긴다(LGPL-2.1 6절). 상용 제품에서 법무 검토가 필요하다. musl(MIT)은 이 부담이 없다.
  • 보안 업데이트: libc 취약점이 고쳐져도 정적 바이너리는 다시 빌드해야 반영된다.
  • dlopen: 정적 glibc 바이너리에서 dlopen은 같은 경고가 나오고, 같은 버전의 공유 glibc가 rootfs에 있어야 한다.

언제 정적 링크가 좋은가: initramfs 안의 복구 툴, 공장 테스트 툴처럼 "어떤 rootfs에서도 돌아야 하는" 작은 프로그램 — 이때는 musl 정적이 정답에 가깝다. BusyBox도 흔히 이렇게 빌드한다.

10. 커널 안에서는 무슨 일이 일어나나#

10.1 libc가 경계다#

libc와 커널 사이의 계약은 세 가지 숫자 체계뿐이다: syscall 번호, 인자·반환 레지스터 규약, 그리고 구조체 레이아웃(예: struct stat, struct i2c_msg). 이 계약은 커널 소스의 include/uapi/와 arch/arm64/include/uapi/에 정의되고, make headers_install로 뽑혀 배포판의 linux-libc-dev 패키지(/usr/include/linux, /usr/include/asm-generic, /usr/include/asm)가 된다. §1.1에서 __NR_close 57, EBADF 9, linux/i2c-dev.h가 모두 이 패키지에서 왔다.

그림 8 — libc는 유저 공간 쪽 경계다. 번호·에러 코드·구조체는 커널의 UAPI 헤더에서 오고, 커널 자신은 libc 없이 자체 lib/ 함수로 산다. 드라이버가 돌려준 음수 에러 코드가 그대로 유저의 errno가 된다.

10.2 단계별로#

  1. 유저의 close(fd) → libc 래퍼가 x8 = __NR_close(57), x0 = fd를 넣고 svc #0.
  2. EL1 예외 벡터 → el0t_64_sync → el0_svc(arch/arm64/kernel/entry-common.c) → invoke_syscall(arch/arm64/kernel/syscall.c)이 sys_call_table[57]을 호출 → __arm64_sys_close → close_fd.
  3. 실패하면 커널 함수가 -EBADF를 반환하고, 그 값이 x0에 실린 채 eret으로 유저에 돌아온다.
  4. libc가 -4095 ≤ x0 ≤ -1을 보고 TLS의 errno에 9를 쓰고 -1을 반환한다.

10.3 커널은 libc를 쓰지 않는다#

커널은 glibc도 musl도 링크하지 않는다. Kbuild는 -nostdinc(시스템 헤더 금지)와 freestanding 모드로 컴파일하고, 필요한 함수는 직접 들고 있다: lib/string.c(memcpy, strlen, strscpy), lib/vsprintf.c(snprintf, printk의 포맷팅), mm/slab(kmalloc — malloc이 아니다). arm64는 arch/arm64/lib/에 최적화된 memcpy 등을 따로 둔다. 커널 코드에서 printf나 errno를 찾으면 없다 — 에러는 음수 반환값으로만 전달한다. 이 관례가 그대로 syscall 반환값이 되고, libc가 그걸 errno로 옮겨 담는 것이다. Don의 bare-metal 펌웨어가 newlib 없이 자체 memcpy·uart_printf를 들고 다니던 것과 같은 처지다.

10.4 드라이버를 쓸 때 다시 만나는 지점#

  • 에러 코드 규약: 드라이버의 .read/.write/.unlocked_ioctl이 -EINVAL, -EAGAIN, -ENOTTY를 돌려주면 유저 앱은 errno로 그 값을 본다. "유저가 무엇을 보게 될지"를 생각하고 에러 코드를 고른다 (G4, G5).
  • UAPI 헤더 설계: 드라이버가 새 ioctl이나 구조체를 유저에게 노출하면 include/uapi/linux/xxx.h에 넣어야 하고, 그 레이아웃은 영원히 바뀌면 안 되는 ABI가 된다. 32/64비트 겸용을 위해 __u32, __u64 고정 폭 타입과 명시적 패딩을 쓴다 (G5).
  • 커널 lib/ 함수: 드라이버 안에서 strcpy 대신 strscpy, sprintf 대신 scnprintf/sysfs_emit을 쓴다 — 커널판 "libc"의 관례다 (E4, G 모듈).
  • vDSO: 커널이 유저 공간에 코드를 넣어 주는 유일한 일반 경로다. 시간 관련 드라이버(PTP 하드웨어 클록 등)를 볼 때 "어떤 시계는 vDSO로 읽히고 어떤 건 syscall이 필요한가"가 다시 나온다 (E 모듈).

커널 내부의 libc 대체물과 빌드 방식은 E4(커널 소스 구조·빌드)에서 더 본다.

11. Embedded 실무에서 다시 보기#

11.1 "보드에서 툴이 안 돌아요" 트리아지 순서#

예를 들어 센서 키트의 진단 툴 imu_diag를 개발 PC에서 크로스 빌드해 보드에 복사했는데 실행이 안 된다. 증상별로 이 순서로 본다.

1번의 "No such file or directory"는 Linux에서 가장 헷갈리는 메시지 중 하나다. 실행 파일은 있는데 PT_INTERP의 로더가 없어서 execve가 ENOENT를 돌려준 것이다. musl 보드에 glibc 바이너리를 올렸거나, 32비트 ARM 로더(/lib/ld-linux-armhf.so.3)만 있는 보드에 64비트 바이너리를 올렸을 때 나온다.

11.2 벤더 SDK와 rootfs 버전 맞추기#

Jetson L4T나 NXP Yocto BSP는 특정 glibc 버전으로 고정돼 있다. 팀 개발 환경은 그 SDK의 sysroot로 빌드하거나(B5), BSP와 같은 배포판 버전 컨테이너에서 빌드한다. CI에 "산출물의 최고 GLIBC_2.xx 태그가 타깃 버전 이하인지" 검사하는 스크립트를 넣으면 §7의 사고를 출고 전에 잡는다.

11.3 musl로 옮길 때 체크리스트#

  • 스레드를 만드는 모든 곳에 pthread_attr_setstacksize 명시 (§4.2), 또는 -Wl,-z,stack-size=.
  • 할당이 많은 멀티스레드 서비스(로깅, 메시지 브로커)는 벤치마크 후 필요하면 대체 할당기 (§4.1).
  • 고빈도 타임스탬프 경로가 vDSO를 타는지 strace -c로 확인 (§4.3).
  • DNS·사용자 조회 동작 차이(NSS 없음, resolver 동작 차이) 확인.
  • 벤더 블롭이 하나라도 있으면 포기하고 glibc.

11.4 initramfs 복구 툴은 musl 정적으로#

eMMC의 rootfs가 깨졌을 때 initramfs에서 도는 업데이트·복구 툴은 rootfs의 libc에 의존하면 안 된다. musl 정적 빌드면 툴 하나가 수십~수백 KB이고(§3.1), 로더·.so가 필요 없으니 initramfs를 작게 유지할 수 있다.

13. 면접에서 이렇게 말한다#

Q. "What does the C library actually do on Linux? Where does it sit?"

A. libc는 앱과 커널 사이의 유저 공간 런타임이다. 커널 syscall 위에 POSIX API를 구현하고(래퍼가 -errno를 -1과 TLS errno로 바꾼다), stdio 버퍼링, brk/mmap 위의 malloc, NPTL 스레드와 futex 기반 동기화, 로케일·iconv, NSS와 DNS resolver, 그리고 _start부터 main과 exit까지의 시작·종료 코드를 제공한다. 동적 링크면 로더 ld-linux도 libc 프로젝트의 일부다. bare-metal의 newlib과 달리 아래쪽 끝이 stub 함수가 아니라 커널이다.

It's the user-space runtime between applications and the kernel. It implements POSIX on top of raw system calls — the wrappers turn the kernel's negative error return into -1 plus a thread-local errno — and adds stdio buffering, malloc on top of brk and mmap, NPTL threads with futex-based locks, locale and iconv, name resolution through NSS and the DNS resolver, and the startup and shutdown path from _start through main to exit. With dynamic linking, the loader ld-linux comes from the same project. Compared with newlib on bare metal, the bottom edge is the kernel's syscall ABI instead of stub functions you write yourself.

꼬리 질문: "Is errno a global variable?" → 스레드별 TLS, glibc는 (*__errno_location()) 매크로.

Q. "glibc vs musl — how do you choose for an embedded product?"

A. 먼저 벤더 바이너리를 본다. GPU·NPU·카메라 ISP 라이브러리는 거의 항상 glibc 전용이라 하나라도 있으면 glibc다. 없고 플래시가 작거나 정적 툴이 많으면 musl이 좋다 — 내가 재 보니 정적 hello가 550 KiB 대 33 KiB, 시작 시간 126 대 75 µs였다. 대신 musl은 malloc이 멀티스레드에서 느리고(4스레드에서 3 대 94 ns/op), 기본 스레드 스택이 128 KiB라서 스택 크기를 명시해야 한다. 라이선스도 LGPL 대 MIT라 정적 배포 때 차이가 난다.

First I check for vendor binaries: GPU, NPU and ISP user-space stacks are almost always built against glibc, so if there's even one, it's glibc. Otherwise, if flash is tight or we ship many static tools, musl is attractive — in my measurements a static hello was 550 KiB with glibc versus 33 KiB with musl, and start-up was about 126 versus 75 microseconds. The trade-offs are musl's slower allocator under threads — roughly 3 versus 94 ns per malloc/free with four threads — and its 128 KiB default thread stack, so you set stack sizes explicitly. Licensing matters too: glibc is LGPL, musl is MIT, which simplifies static distribution.

Q. "What happens before main() is called?"

A. execve에서 커널이 ELF를 매핑하고 PT_INTERP가 있으면 로더도 매핑해 로더 진입점으로 간다. 스택에는 argc, argv, envp, auxv가 쌓인다. 로더는 자기 재배치 후 DT_NEEDED 라이브러리를 찾아 매핑하고, 심볼 버전 확인, 재배치, RELRO, 라이브러리 init을 한 뒤 프로그램의 _start(crt1.o)로 점프한다. _start는 argc/argv를 꺼내 __libc_start_main을 부르고, 이 함수가 TLS·스택 가드·init_array(생성자)를 처리하고 main을 부른다. main이 리턴하면 exit가 atexit 핸들러, 소멸자, stdio flush, exit_group 순으로 정리한다.

On execve the kernel maps the ELF and, if there's a PT_INTERP, maps the dynamic loader too and starts executing at the loader's entry, with argc, argv, envp and the auxiliary vector on the stack. The loader relocates itself, finds and maps every DT_NEEDED library, checks symbol versions, applies relocations, write-protects the RELRO region and runs library initializers, then jumps to the program's _start from crt1.o. _start pulls argc and argv off the stack and calls __libc_start_main, which sets up TLS and the stack protector, runs the init_array constructors and calls main. When main returns, exit runs atexit handlers, destructors, flushes stdio and finally calls exit_group.

꼬리 질문: "Where does the very first user-space instruction execute?" → 동적 바이너리면 로더의 _start(gdb starti로 확인 가능).

Q. "A binary fails on the target with 'version GLIBC_2.38 not found'. Explain and fix."

A. glibc는 심볼마다 버전 태그를 붙여 하위 호환을 유지한다. 새 glibc로 링크하면 바이너리가 새 태그(예: C23 모드의 __isoc23_strtol@GLIBC_2.38)를 요구하게 되고, 타깃의 옛 glibc에는 그 정의가 없으니 로더가 버전 확인 단계에서 실행을 거부한다. objdump -T로 요구 태그를 확인하고, 근본적으로는 타깃과 같은 glibc의 sysroot·SDK로 빌드한다. 임시로는 새 API와 C23 기본값을 피하거나, musl 정적 링크로 libc 의존을 없앤다.

glibc versions its symbols so old binaries keep working on newer libraries, but not the other way round. Linking on a newer host binds to newer versions — gcc 15 defaults to C23, so even strtol becomes __isoc23_strtol at GLIBC_2.38 — and the target's older libc.so.6 doesn't define that version, so the dynamic loader refuses to start the program during version checking. I'd confirm with objdump -T to see the highest GLIBC tag required, and fix it properly by building against the target's sysroot or SDK so the linker can only bind to versions the target has. Short-term options are avoiding the new APIs, compiling with -std=gnu17, or linking statically against musl.

Q. "Why is static linking with glibc discouraged?"

A. NSS, iconv, dlopen 같은 기능은 정적 바이너리에서도 실행 중 공유 라이브러리를 불러오고, 그 라이브러리는 공유 glibc를 끌고 온다. 실제로 getpwnam으로 없는 사용자를 조회하는 정적 바이너리가 libnss_systemd.so.2와 libc.so.6, 로더까지 여는 걸 strace로 봤다. 링크한 버전과 rootfs 버전이 다르면 깨진다. 거기에 바이너리가 크고, 보안 패치가 재빌드 없이 반영되지 않고, LGPL 재링크 의무가 생긴다. 정적이 필요하면 musl을 쓴다.

Because parts of glibc still load shared objects at run time even in a static binary — NSS, iconv and dlopen. I traced a static binary looking up an unknown user and it opened libnss_systemd.so.2, which pulled in the shared libc.so.6 and the loader; if those don't match the glibc you linked against, lookups fail or crash. On top of that the binaries are large, security fixes need a rebuild, and LGPL adds relinking obligations for static distribution. If I need a truly self-contained binary, I use musl.

Q. "How does the dynamic loader find libraries, and how do you debug 'cannot open shared object file'?"

A. 로더는 DT_NEEDED의 이름을 RUNPATH가 없을 때의 DT_RPATH, LD_LIBRARY_PATH, DT_RUNPATH, /etc/ld.so.cache, 기본 경로(/lib, /usr/lib) 순으로 찾는다. 디버그는 readelf -d로 NEEDED·RUNPATH를 보고, glibc면 LD_DEBUG=libs로 실제로 어디를 뒤졌는지 본다. 새 라이브러리를 넣었으면 ldconfig로 캐시를 갱신한다.

The loader resolves each DT_NEEDED name by checking DT_RPATH when there's no RUNPATH, then LD_LIBRARY_PATH, then DT_RUNPATH, then the /etc/ld.so.cache index, then the default directories. To debug, I read NEEDED and RUNPATH with readelf -d, and on glibc I run with LD_DEBUG=libs to see exactly which paths it tried. If a library was just installed, running ldconfig to refresh the cache is often the fix.

Q. "Why can ldd be dangerous?"

A. ldd는 분석기가 아니라 로더를 LD_TRACE_LOADED_OBJECTS=1로 돌리는 스크립트다. man 페이지는 일부 구현이 프로그램의 PT_INTERP를 직접 실행할 수 있다고 경고한다 — 그러면 가짜 인터프리터를 넣은 바이너리에 ldd만 해도 코드가 실행된다. 내가 실험해 보니 최신 glibc의 ldd는 시스템 로더를 써서 실행은 안 했지만 가짜 로더를 진짜 로더로 표시했고, musl·크로스 바이너리에도 틀린 답을 냈다. 그래서 readelf -d나 objdump -p로 본다.

ldd isn't a parser — it's a script that runs the loader with LD_TRACE_LOADED_OBJECTS set, so it actually loads the program. The man page warns that some implementations may execute the program's own ELF interpreter, so a crafted binary could run code just by being inspected. When I tested a binary with a fake PT_INTERP, modern glibc's ldd used the system loader and didn't execute it, but it misreported the interpreter, and it also gives wrong answers for musl or cross-compiled binaries. For untrusted or foreign binaries I use readelf -d or objdump -p instead.

Q. "What is the vDSO?"

A. 커널이 모든 프로세스에 매핑하는 작은 공유 라이브러리로, clock_gettime 같은 읽기 전용 호출을 syscall 없이 처리한다. libc가 auxv의 AT_SYSINFO_EHDR로 위치를 받아 심볼을 찾는다. 내 측정에서 glibc의 clock_gettime은 20 ns였고, vDSO를 못 쓰는 경우(이 커널 조합의 musl)는 실제 syscall이 돼서 170 ns였다.

It's a small shared object the kernel maps into every process so that read-mostly calls like clock_gettime can run without entering the kernel. The C library finds it through AT_SYSINFO_EHDR in the auxiliary vector and resolves its symbols like any other library. I measured clock_gettime at about 20 ns through glibc's vDSO path versus about 170 ns when it fell back to a real system call, which is what happened with musl on that kernel.

  2. 코드: §4.2의 stack.c를 musl로 빌드해서, 재귀 깊이를 이분 탐색으로 늘려 가며 segfault가 나는 최소 깊이를 찾아라. 그 값이 128 KiB와 어떻게 맞는지 설명하라. 정답/힌트: 이 VM에서는 125단계는 통과, 130단계에서 SIGSEGV였다. 프레임당 1 KiB 배열 + 프레임 오버헤드에, TLS·스레드 구조체가 같은 매핑을 나눠 쓰기 때문에 128보다 약간 작은 곳에서 죽는다.
  3. strace 관찰: strace -f ./mb_glibc 4 2>&1 | grep -E "clone|mmap"과 musl판을 비교해, 스레드 스택이 어떤 크기로 mmap되는지 확인하라. 정답/힌트: 이 VM에서 glibc는 mmap(NULL, 8454144, ..., MAP_STACK)(8 MiB + 64 KiB guard), musl은 mmap(NULL, 143360, PROT_NONE, ...) 뒤 mprotect로 사용 부분을 여는 방식이었다(스택 + guard + TLS). musl은 clone, glibc는 clone3를 쓴다.
  4. 심볼 버전: ver.c를 -std=gnu17로만 빌드하면(strlcpy는 그대로) 요구 태그 목록이 어떻게 바뀌나? objdump -T로 확인하라. 정답/힌트: __isoc23_strtol이 strtol@GLIBC_2.17로 돌아가지만 strlcpy@GLIBC_2.38 때문에 최고 태그는 여전히 2.38이다.
  5. LD_DEBUG: LD_DEBUG=libs LD_LIBRARY_PATH=/tmp/B2/oldroot ./hello_glibc_dyn을 실행해 로더가 어떤 순서로 경로를 시도하는지 보고, §7.3의 가짜 libc가 왜 먼저 잡히는지 설명하라. 정답/힌트: search path=/tmp/B2/oldroot 줄이 cache보다 먼저 나온다. LD_LIBRARY_PATH는 ld.so.cache보다 우선한다. 이 hello는 가짜 libc에 __printf_chk가 없어 "symbol lookup error"로 끝난다.
  6. 크기: nss.c를 musl 정적으로 빌드한 뒤 nm --size-sort로 가장 큰 심볼 10개를 뽑고, glibc 정적판과 비교해 어떤 기능이 크기를 차지하는지 찾아라. 정답/힌트: glibc 쪽은 NSS·로케일·vfprintf 관련 심볼과 ifunc로 고르는 여러 CPU용 memcpy 변종이 크다.
  7. 실무 스크립트: 디렉터리 안의 모든 ELF에 대해 최고 GLIBC_2.xx 요구 태그를 출력하고, 지정한 타깃 버전보다 높으면 실패하는 CI 스크립트를 셸로 짜라. 정답/힌트: file로 ELF를 거르고 objdump -T의 태그를 sort -t. -k2 -n으로 정렬한다. 버전 비교는 마이너 번호만 정수로 비교하면 된다(GLIBC_2.x 체계).

16. 요약 & 체크리스트#

Linux의 C 라이브러리는 newlib의 "stub 함수" 자리에 커널 syscall을 두고, 그 위에 syscall 래퍼와 TLS errno, stdio 버퍼링, brk/mmap 기반 malloc, NPTL 스레드, locale·iconv, NSS·resolver, 그리고 _start → __libc_start_main → main → exit의 시작·종료 코드를 제공한다. 동적 바이너리는 PT_INTERP의 로더가 먼저 실행되어 DT_NEEDED 라이브러리를 찾고, 심볼 버전을 확인하고, 재배치한 뒤 프로그램으로 넘긴다. 그래서 새 glibc로 빌드한 바이너리는 옛 rootfs에서 "version GLIBC_2.xx' not found"로 거부된다. 이 VM 실측으로 musl은 정적 크기(33 KiB 대 550 KiB)·시작 비용(75 대 126 µs)·syscall 수(4 대 15)에서 이기고, 멀티스레드 malloc(94 대 3 ns/op)·기본 스레드 스택(128 KiB 대 8 MiB)·vDSO 사용(이 커널에서 170 대 20 ns)에서 불리했다. 제품 선택은 벤더 바이너리(대개 glibc 전용)가 먼저 결정하고, 그다음이 플래시 크기다. 커널 자신은 libc를 쓰지 않고, 번호·에러 코드·구조체를 UAPI 헤더로 libc와 공유하며, 드라이버가 돌려준 음수 에러 코드가 그대로 유저의 errno`가 된다.
