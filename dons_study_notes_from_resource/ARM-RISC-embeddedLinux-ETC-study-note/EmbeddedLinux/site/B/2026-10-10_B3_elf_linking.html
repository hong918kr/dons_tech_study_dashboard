0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어를 빌드하던 장면을 떠올려 보자. arm-none-eabi-gcc로 .c를 .o로 만들고, 링커 스크립트(MEMORY { FLASH ..., RAM ... })를 주고 ld가 모든 .o를 하나의 firmware.elf로 합친다. 이 순간 모든 주소가 확정된다. .map 파일을 열면 함수마다 절대 주소가 박혀 있고, objcopy -O binary로 뽑은 이미지를 플래시에 굽는다. 리셋 핸들러가 .data를 플래시에서 RAM으로 복사하고 .bss를 0으로 채운 뒤 main()으로 뛴다. 링크는 빌드할 때 한 번, 끝.

Linux 유저 공간은 다르다. 링크가 두 번 일어난다.

  1. 빌드 시간 링크(static link): ld가 .o들과 .a를 합쳐 실행 파일을 만든다. 여기까지는 펌웨어와 같다. 하지만 printf 같은 libc 함수는 실행 파일에 들어가지 않는다. "나중에 libc.so.6에서 printf를 찾아라"라는 메모만 남긴다.
  2. 실행 시간 링크(dynamic link): 커널이 execve()로 프로그램을 메모리에 올리면, 먼저 동적 로더(ld-linux-aarch64.so.1, 줄여서 ld.so)가 돌아서 필요한 .so를 찾아 mmap하고, 메모 남겨진 자리(GOT)에 진짜 주소를 써 넣은 뒤에야 main()이 시작된다.

그리고 주소도 확정되지 않는다. 요즘 실행 파일은 PIE(Position-Independent Executable)라서 실행할 때마다 커널이 무작위 기준 주소에 올린다(ASLR). Don의 .map 파일에 적힌 주소는 "기준 주소로부터의 오프셋"일 뿐이다.

그림 1 — Linux 유저 프로그램은 빌드 시간(1·2)과 실행 시간(3·4)에 걸쳐 두 번 링크된다. 펌웨어는 2에서 모든 주소가 끝난다.

Embedded Linux 엔지니어가 이 그림을 머릿속에 갖고 있어야 하는 장면:

  • "파일이 있는데 not found": 크로스 빌드한 앱을 보드에 올렸더니 ./sensord: not found. 파일은 분명히 있다. 3단계에서 커널이 PT_INTERP에 적힌 로더를 못 찾은 것이다 (§8).
  • 라이브러리 업데이트 사고: libimu.so를 새 버전으로 올렸더니 다른 앱이 undefined symbol로 죽는다. 4단계 이야기다 (§5, §8).
  • 크래시 덤프 해석: 필드에서 받은 로그에 pc=0xaaaab2c40cf0만 있다. 이걸 소스 줄로 바꾸려면 ASLR 기준 주소를 빼고 debug 정보를 따로 보관하고 있어야 한다 (§9).
  • 커널 모듈: .ko는 .o와 같은 ET_REL 파일이고, 커널이 4단계(링크)를 직접 한다 (§11). 드라이버를 쓰는 Don에게 이 노트의 마지막 목적지다.

실행 환경: 모든 출력은 Lima VM elinux(aarch64, uname -r = 7.0.0-34-generic, gcc 15.2, GNU ld 2.46, Apple Silicon 위 가상화)에서 실제로 돌린 결과다. 주소·PID·Build ID는 실행마다 다르다. Ubuntu gcc는 기본이 PIE + -z now + -z relro 라는 점을 기억해 두자(§6에서 중요).

1. ELF 파일 한 장 — 헤더와 세 가지 타입#

1.1 직관 — "같은 포장, 다른 내용물"#

ELF(Executable and Linkable Format)는 Linux의 모든 바이너리 포장 형식이다. .o, 실행 파일, .so, 커널 모듈 .ko, 심지어 vmlinux와 코어 덤프도 ELF다. Don이 펌웨어에서 쓰던 firmware.elf와 같은 형식이다. 차이는 헤더의 e_type 필드 하나와, 그에 따라 어떤 테이블이 채워져 있느냐다.

e_type이름예주소가 정해졌나누가 소비하나
ET_REL (1)relocatablehello.o, b3_elfmod.ko아니오 (섹션마다 0부터)링커 ld, 커널 모듈 로더
ET_EXEC (2)executable-no-pie로 만든 실행 파일, 펌웨어 .elf예 (절대 주소, 기본 0x400000)커널 execve
ET_DYN (3)shared object.so, PIE 실행 파일기준 주소 0, 로드 시 결정커널 + ld.so
ET_CORE (4)core코어 덤프—gdb

PIE 실행 파일이 .so와 같은 ET_DYN이라는 것이 첫 번째 놀라운 점이다. PIE는 "main이 있는 공유 라이브러리"라고 생각하면 정확하다.

1.3 ELF 헤더 읽기#

64바이트짜리 헤더가 말하는 것은 딱 세 가지다.

  1. 이 파일을 누가 실행할 수 있나: Magic 7f 45 4c 46(\x7fELF), Class(32/64), Data(엔디언), Machine(AArch64). 커널은 여기서 하나라도 안 맞으면 ENOEXEC("Exec format error")를 돌려준다 (§8).
  2. 어디서 시작하나: Entry point 0x6c0 — PIE라서 기준 주소 0 기준 오프셋이다. 실제 주소는 "로드 기준 + 0x6c0"이다. 이 값이 main이 아니라 _start(crt1의 시작 코드)라는 것도 펌웨어의 리셋 벡터 → Reset_Handler → main과 같은 구조다.
  3. 두 개의 지도가 어디 있나: Program headers는 파일 offset 64부터 10개, Section headers는 68760부터 29개. 이 두 지도가 다음 절의 주제다.

2. 섹션 vs 세그먼트 — 링커의 지도, 로더의 지도#

2.1 직관#

Don의 펌웨어 링커 스크립트에서 .text, .rodata, .data, .bss는 섹션이다. 그리고 그것들을 > FLASH, > RAM AT> FLASH로 어느 메모리 영역에 둘지 정했다. Linux ELF도 똑같이 두 층이다.

  • 섹션(section): 링커와 디버거가 쓰는 세밀한 단위. .text, .rodata, .data, .bss, .symtab, .debug_info … readelf -S로 본다. 섹션 헤더 테이블이 목차다.
  • 세그먼트(segment): 커널과 ld.so가 쓰는 굵은 단위. "파일의 이 범위를 이 권한(R/W/X)으로 이 가상 주소에 매핑하라". readelf -l로 본다. 프로그램 헤더 테이블이 목차다. 비유하자면 링커 스크립트의 MEMORY 영역 + MPU 리전 설정이다.

여러 섹션이 권한이 같으면 하나의 PT_LOAD 세그먼트로 묶인다. 커널은 섹션 헤더를 아예 보지 않는다. 실행에 필요한 것은 프로그램 헤더뿐이다.

그림 2 — 하나의 ELF 파일에 두 개의 목차가 있다. 왼쪽 섹션은 링커·디버거용, 오른쪽 세그먼트는 실행용. 실행에 필요 없는 섹션(.symtab, .debug_info 등)은 어떤 세그먼트에도 속하지 않는다.

2.2 예제 2 — readelf -S와 readelf -l을 나란히#

무엇을 확인하나: 같은 hello_pie의 섹션 29개가 세그먼트 10개로 어떻게 묶이는지 본다.

(Key to Flags 설명 줄은 생략했다.)

읽는 법: Flg의 A(alloc)가 붙은 섹션만 메모리에 올라간다. .comment, .symtab, .strtab은 A가 없고 Address가 0이다 — 실행에 필요 없다. .bss는 Type이 NOBITS라 파일 offset만 있고 공간을 차지하지 않는다(펌웨어에서 .bss가 이미지 크기에 안 잡히는 것과 같다).

출력에서 볼 것:

  • LOAD 두 개가 전부다. 02번(R E) = 코드+읽기 전용 데이터 17개 섹션, 03번(RW) = 쓰기 가능한 6개 섹션. 커널은 이 두 줄만 보고 mmap을 두 번 한다.
  • 03번 LOAD의 FileSiz 0x284 < MemSiz 0x290: 차이 0xc 바이트가 .bss다. 커널이 파일에 없는 뒷부분을 0으로 채운다. 펌웨어 리셋 핸들러의 .bss 0 채우기를 커널이 대신하는 것이다.
  • Align 0x10000(64K): aarch64 툴체인은 16K·64K 페이지 커널에서도 돌도록 기본 max-page-size를 64K로 잡는다. 그래서 두 LOAD 사이에 파일 offset 0x934 → 0xfd90의 빈 공간이 생긴다(§10의 크기 차트에서 다시 본다).
  • GNU_RELRO는 .init_array~.got: 재배치가 끝나면 읽기 전용으로 바꿔 달라는 요청이다(§6.4).
  • GNU_STACK의 RW(E 없음): 스택은 실행 불가(NX). 펌웨어에서 MPU로 스택에 XN을 걸던 것과 같다.

2.3 예제 3 — .o 안의 relocation: "여기는 나중에 채워 주세요"#

무엇을 확인하나: hello.o(ET_REL)에서 main이 전역 변수와 printf를 가리키는 자리가 아직 0이고, relocation 엔트리가 그 자리를 표시하고 있다는 것.

출력에서 볼 것:

  • adrp x0, 0, bl 0 — 모든 주소가 0이다. 그 아래 R_AARCH64_... 줄이 "이 명령의 이 필드를 나중에 채워라"라는 메모다. ADR_PREL_PG_HI21 + ADD_ABS_LO12_NC 쌍은 aarch64에서 PC 기준 ±4GB 주소를 만드는 adrp+add 패턴이고, CALL26은 bl의 26비트 오프셋이다. Cortex-M 펌웨어에서 보던 R_ARM_THM_CALL과 같은 종류다.
  • printf가 __printf_chk로 바뀌어 있다. Ubuntu gcc는 -O2에서 _FORTIFY_SOURCE를 기본으로 켜서 버퍼 검사판 함수로 바꾼다. 크로스 툴체인마다 기본값이 다르다는 예다.
  • main이 .text가 아니라 .text.startup에 들어갔다. GCC가 "한 번만 불리는 시작 코드"를 따로 모은다. 섹션 이름은 컴파일러가 마음대로 만들 수 있고, 링커 스크립트가 그걸 *(.text .text.*)로 모은다.

정적 링커 ld는 이 relocation 중 해결할 수 있는 것은 모두 해결하고(.data, .rodata의 위치는 이제 안다), libc에 있는 __printf_chk처럼 해결 못 하는 것은 PLT 스텁 + GOT 슬롯 + 동적 relocation(.rela.plt) 으로 바꿔 실행 시간으로 넘긴다(§6).

3. PIE와 ASLR — 주소는 실행할 때 정해진다#

3.1 직관#

PIC(Position-Independent Code)는 "어느 주소에 올려도 돌아가는 코드"다. aarch64에서는 adrp(PC 기준 페이지 주소)가 기본이라 PIC가 거의 공짜다. PIE는 실행 파일 전체를 PIC로 만든 것이고, 덕분에 커널이 실행할 때마다 다른 기준 주소에 올릴 수 있다. 이것이 ASLR(Address Space Layout Randomization)이다. 공격자가 "system()은 항상 0x400a10에 있다" 같은 가정을 못 하게 만드는 보안 기능이다.

3.2 예제 5 — 실행할 때마다 바뀌는 주소#

무엇을 확인하나: PIE vs non-PIE에서 코드·데이터·libc·힙·스택 주소가 실행마다 바뀌는지, 그리고 setarch -R로 ASLR을 끌 수 있는지.

출력에서 볼 것:

  • randomize_va_space = 2: 스택·mmap·힙(brk)까지 전부 무작위화.
  • PIE: main이 매번 다르다. 그런데 끝 세 자리(a40)는 항상 같다 — 기준 주소는 페이지 단위로만 바뀌고, 오프셋(main은 파일 기준 0xa40)은 고정이다. 크래시 주소를 소스 줄로 바꿀 때 이 성질을 쓴다(§9).
  • non-PIE: main=0x400940이 고정. 기본 링커 스크립트의 SEGMENT_START("text-segment", 0x400000) 그대로다. 그래도 printf(libc), 힙, 스택은 바뀐다 — .so는 원래 PIC라서 늘 무작위 위치다.
  • setarch -R(= personality(ADDR_NO_RANDOMIZE)): 두 번 다 0xaaaaaaaa0a40. gdb가 기본으로 이걸 켜서 디버깅 중 주소가 안 바뀐다.
  • /proc/self/maps: 파일 offset 0 → r-xp, offset 0xf000 → r--p, 0x10000 → rw-p. 세그먼트는 두 개였는데 매핑은 세 개다. 가운데 r--p는 RELRO 영역을 ld.so가 mprotect로 읽기 전용으로 바꾼 것이다(§6.4). 이 VM 커널은 4K 페이지라서 64K 정렬된 세그먼트도 4K 단위로 쪼개 매핑된다.

펌웨어와의 연결: Don의 SSD 펌웨어 크래시 로그는 PC 값을 그대로 .map에서 찾으면 됐다. Linux에서는 "PC − 그 모듈의 로드 기준 주소 = 파일 오프셋" 을 먼저 계산해야 한다. 기준 주소는 /proc/<pid>/maps나 크래시 핸들러의 dladdr()로 얻는다.

4. 정적 링킹 — .a 아카이브와 순서 함정#

4.1 직관#

.a(static archive)는 .o 파일들을 ar로 묶은 zip 같은 상자일 뿐이다. GNU ld(BFD)는 명령줄을 왼쪽에서 오른쪽으로 한 번만 훑는다. .a를 만나면 "지금까지 미해결인 심볼을 정의하는 멤버만" 꺼내 넣고 지나간다. 나중에 다른 멤버가 그 아카이브의 심볼을 필요로 해도 되돌아가지 않는다. 그래서 규칙은 "쓰는 쪽이 왼쪽, 제공하는 쪽이 오른쪽"이다.

4.2 예제 6 — 센서 라이브러리 순서 사고#

무엇을 확인하나: main → sensor_read()(libsensor.a) → i2c_xfer()(libi2c.a)일 때 -l 순서에 따라 링크가 성공/실패하는지.

출력에서 볼 것:

  • 잘못된 순서: -li2c를 지나갈 때는 아직 아무도 i2c_xfer를 원하지 않아서 아무것도 안 꺼냈다. 그 뒤 sensor.o가 i2c_xfer를 원했지만 이미 지나간 뒤다. 에러 메시지 "undefined reference"는 빌드 시간(정적 링크) 에러다. 실행 시간의 "undefined symbol"(§5.5)과 구분하자.
  • --start-group ... --end-group: 그룹 안 아카이브를 해결될 때까지 반복해서 훑는다. 상호 의존(A↔B) 아카이브에 필요하다. 느려질 수 있어서 기본값은 아니다.
  • .map 파일의 "Archive member included to satisfy reference by file" 표는 왜 이 멤버가 들어왔는지를 보여 준다. 펌웨어에서 "이 함수가 왜 이미지에 들어왔지?"를 추적하던 그 표다. Linux에서도 -Wl,-Map=은 똑같이 쓴다.

LLVM의 lld는 이 순서에 관대하다(아카이브 심볼을 기억해 둔다). 같은 잘못된 순서로 -fuse-ld=lld를 주면 성공한다.

그래서 "내 PC(lld)에서는 되는데 CI(GNU ld)에서 안 된다"가 생긴다. 이식성 있는 빌드는 항상 의존 순서대로 쓴다.

4.3 정적 링크된 실행 파일#

gcc -static은 libc까지 실행 파일 안에 넣는다. INTERP도 DT_NEEDED도 없으니 로더 문제가 원천적으로 없다 — initramfs의 복구 도구, 부트 직후 도는 작은 init, 컨테이너의 scratch 이미지에 자주 쓴다. 대가는 크기(§10의 차트에서 glibc 정적 hello가 712KB)와 보안 업데이트(libc 버그가 고쳐져도 다시 빌드해야 함), 그리고 glibc 정적 링크에서 getpwnam/dlopen 같은 NSS·동적 로딩 기능이 제한된다는 점이다. 임베디드에서 정적 링크가 필요하면 musl(B2)이 훨씬 작다.

5. 공유 라이브러리 — soname, 심볼릭 링크 체인, 탐색 순서#

5.1 직관 — 이름이 세 개인 이유#

공유 라이브러리 하나에는 이름이 세 개 붙는다.

이름예누가 쓰나언제 바뀌나
real namelibimu.so.1.2.3실제 파일릴리스마다
sonamelibimu.so.1런타임 ld.so (DT_NEEDED에 기록)ABI가 깨질 때만 (major)
linker namelibimu.so빌드 시 ld의 -limu거의 안 바뀜 (dev 패키지)

핵심은 앱이 기억하는 것은 soname이라는 점이다. 1.2.3 → 1.3.0으로 올라가도 soname libimu.so.1이 그대로면 앱을 다시 빌드할 필요가 없다. ABI가 깨지면 libimu.so.2로 올려서 옛 앱은 계속 .so.1을 쓰게 한다. 두 버전이 한 rootfs에 공존할 수 있다.

그림 3 — 위: 공유 라이브러리의 이름 체인. 아래: ld.so의 탐색 순서. RPATH는 LD_LIBRARY_PATH보다 먼저, RUNPATH는 나중이라는 점이 실무에서 자주 문제가 된다.

5.2 예제 7 — libimu.so.1.2.3 만들고 "cannot open shared object file" 만나기#

무엇을 확인하나: -fPIC -shared -Wl,-soname으로 라이브러리를 만들고 심볼릭 링크 체인을 구성한 뒤, 앱의 DT_NEEDED에 soname이 기록되는 것과, 표준 경로 밖에 있으면 실행이 실패하는 것.

출력에서 볼 것:

  • -limu로 링크했는데(링커는 libimu.so를 읽음) 앱의 NEEDED에는 libimu.so.1 이 적혔다. 라이브러리 안의 SONAME이 복사된 것이다.
  • "error while loading shared libraries: ... cannot open shared object file" — 메시지 앞부분이 ./app:이 아니라 ld.so가 출력한 것이다. exit 127. 커널은 실행을 성공시켰고, 그 뒤 ld.so가 실패했다.
  • ldd는 "누가 not found인지"를 한눈에 보여 준다. 첫 줄 linux-vdso.so.1은 파일이 아니라 커널이 모든 프로세스에 끼워 넣는 vDSO(A1 참고)다.

주의: ldd는 내부적으로 대상 프로그램을 ld.so로 실행하는 방식이다(LD_TRACE_LOADED_OBJECTS=1). 신뢰할 수 없는 바이너리에 ldd를 쓰지 말고 readelf -d나 objdump -p로 NEEDED만 보는 습관을 들이자. 크로스 바이너리에는 어차피 ldd가 안 통한다(§8.4).

흔한 함정 — dev 링크가 없으면 링크가 안 된다: 처음에 lib_new/에 libimu.so.1만 두고 -Llib_new -limu로 링크했더니 실패했다.

-limu는 libimu.so(또는 libimu.a)만 찾는다. Yocto/Buildroot가 런타임 패키지(libimu1: .so.1, .so.1.2.3)와 dev 패키지(libimu-dev: 헤더 + libimu.so 링크)를 나누는 이유가 이것이다. 타깃 rootfs에는 dev 링크가 필요 없다.

5.3 예제 8 — rpath vs runpath, $ORIGIN, LD_DEBUG=libs#

무엇을 확인하나: 앱 바이너리 안에 "내 옆의 ../lib을 보라"($ORIGIN)를 박아 넣는 두 가지 방법과 LD_LIBRARY_PATH와의 우선순위 차이.

출력에서 볼 것:

  • 요즘 GNU ld의 -rpath는 기본으로 RUNPATH를 만든다. 옛 RPATH는 --disable-new-dtags로만 나온다.
  • $ORIGIN은 ld.so가 "실행 파일이 있는 디렉터리"로 치환한다. /opt/sensorkit/bin/app + /opt/sensorkit/lib/libimu.so.1 같은 재배치 가능한 설치 디렉터리를 만들 때 정석이다. 셸에서 $가 확장되지 않도록 작은따옴표로 감싼다.
  • LD_DEBUG=libs는 ld.so가 어떤 경로를 어떤 이유로 시도했는지 보여 준다. "왜 이 라이브러리를 못 찾지?"의 1순위 도구다. LD_DEBUG=help로 다른 옵션(bindings, symbols, statistics, files)도 볼 수 있다.
  • 마지막 "calling init" 순서: 의존성이 없는 것부터(ld.so → libc → libimu) 초기화된다. 라이브러리의 __attribute__((constructor))가 이 시점에 돈다.

이제 우선순위 차이를 본다. 디버그용 libimu.so.1(버전 999)을 다른 디렉터리에 두고 LD_LIBRARY_PATH로 가리킨다.

출력에서 볼 것: RUNPATH 앱은 LD_LIBRARY_PATH의 디버그 라이브러리(999)를 썼고, RPATH 앱은 LD_LIBRARY_PATH를 무시하고 자기 rpath(123)를 썼다. "LD_LIBRARY_PATH를 줬는데 왜 안 바뀌지?"의 대표 원인이다. 또 하나의 차이(실행하지 않음, glibc 문서 기준): RUNPATH는 그 바이너리의 직접 의존성에만 적용되고, RPATH는 의존성의 의존성 탐색에도 쓰인다.

5.4 예제 9 — ldconfig와 /etc/ld.so.cache#

무엇을 확인하나: 표준 경로의 라이브러리를 빠르게 찾기 위한 캐시와, ldconfig가 soname 링크를 만드는 역할.

출력에서 볼 것:

  • 캐시는 "soname → 경로" 색인이다. ld.so는 디렉터리를 하나하나 뒤지는 대신 이 파일을 mmap해서 찾는다.
  • ldconfig -n lib2는 캐시는 건드리지 않고 그 디렉터리만 처리했다. .so.1.2.3 안의 SONAME을 읽고 libimu.so.1 링크를 스스로 만들었다. 패키지 설치 후 ldconfig를 부르는 이유: 새 디렉터리의 라이브러리를 캐시에 넣고 soname 링크를 맞추기 위해서다. (전역 sudo ldconfig는 이 노트에서 실행하지 않았다.)
  • 임베디드 rootfs에서는 /etc/ld.so.cache가 아예 없을 수 있다. Buildroot 같은 빌드 시스템 구성에서는 캐시 없이 표준 경로(/lib, /usr/lib)에만 라이브러리를 두는 경우가 흔하고, musl의 로더는 캐시 개념이 없고 /etc/ld-musl-<arch>.path 파일을 쓴다(B2). 그래서 /usr/local/lib에 넣었는데 못 찾는 일이 생긴다.

5.5 예제 10 — "undefined symbol": 같은 soname, 다른 ABI#

무엇을 확인하나: 새 라이브러리(1.3.0, imu_read_gyro 추가)로 빌드한 앱을 옛 라이브러리(1.2.3)가 깔린 보드에서 돌리면 어떻게 되는지. 그리고 -z now와 -z lazy에서 언제 터지는지.

출력에서 볼 것:

  • BIND_NOW(Ubuntu 기본): main 전에 모든 심볼을 해결하다가 즉시 실패. "start:" 줄조차 안 나온다. 실패가 빠르고 확실하다.
  • lazy: 프로그램이 일단 시작해서 "start: libimu v123"까지 찍고, imu_read_gyro를 처음 부르는 순간 죽는다. 필드에서 이 함수가 드문 경로(에러 처리, 캘리브레이션)에만 있다면 몇 주 뒤에 터진다. 임베디드 제품에서 -z now가 권장되는 이유 중 하나다.
  • nm -D --undefined-only: 앱이 밖에서 가져와야 하는 심볼 목록. U imu_read_gyro에는 버전 태그가 없고 libc 심볼에는 @GLIBC_2.17 같은 심볼 버전이 붙어 있다. glibc는 심볼 버전으로 "이 앱은 GLIBC_2.34의 __libc_start_main이 필요하다"를 기록해서, 더 오래된 glibc에서는 시작 시 version 'GLIBC_2.34' not found로 명확하게 실패하게 만든다(B2).
  • 진짜 원인은 ABI를 바꿨는데(함수 추가는 하위 호환이지만 앱이 그것을 요구하게 됨) 배포 시 라이브러리를 함께 올리지 않은 것이다. soname은 "major 호환"만 표현한다. "1.3 이상 필요"는 심볼 버전(version script)으로 표현하는 것이 정석이다.

6. 동적 링킹의 심장 — PLT, GOT, lazy binding, RELRO#

6.1 직관 — "간접 점프 테이블을 RAM에 두고 부팅 때 채운다"#

Don이 펌웨어에서 ROM 함수 테이블(벡터 테이블, 부트 ROM API 테이블)이나 "패치 가능한 함수 포인터 테이블"을 RAM에 두고 호출을 그 테이블을 거쳐 하게 만든 적이 있다면, 그것이 바로 GOT다.

  • GOT(Global Offset Table): 쓰기 가능한 데이터 영역에 있는 주소 배열. 외부 함수·변수의 실제 주소를 ld.so가 채워 넣는다.
  • PLT(Procedure Linkage Table): 코드 영역의 작은 스텁 함수들. puts@plt는 "GOT[puts]에서 주소를 읽어 점프"하는 4개 명령이다.
  • 코드(.text)는 읽기 전용이고 여러 프로세스가 공유하므로 고칠 수 없다. 그래서 고쳐야 하는 주소는 모두 프로세스별 데이터(GOT)로 몰아 놓는다. 이것이 PIC의 핵심 아이디어다.
  • lazy binding: GOT를 시작할 때 다 채우지 않고, 처음 호출할 때 해석한다. 처음에는 GOT 슬롯이 "해석기로 가는 길"(PLT0)을 가리키고 있다.

그림 4 — lazy binding 시퀀스. 첫 호출만 ld.so 해석기를 거치고, 그 뒤는 PLT 스텁 → GOT → 진짜 함수로 바로 간다.

6.2 예제 11 — PLT 스텁을 디스어셈블하고, gdb로 GOT 슬롯이 바뀌는 순간 보기#

무엇을 확인하나: -z lazy로 빌드한 프로그램에서 puts의 GOT 슬롯이 첫 호출 전에는 PLT0을, 후에는 libc의 puts를 가리키는 것. -z now(기본)에서는 처음부터 채워져 있는 것.

(가운데 __cxa_finalize@plt, __gmon_start__@plt, abort@plt 스텁 세 개는 같은 모양이라 생략했다.)

출력에서 볼 것:

  • puts@plt: adrp x16 + ldr x17, [x16, #32] → 주소 0x20020(= .rela.plt의 puts 엔트리 Offset)에서 8바이트를 읽어 br x17. x16·x17은 AAPCS64가 "veneer·PLT용으로 링커가 마음대로 쓸 수 있다"고 정해 둔 IP0·IP1 레지스터다. Cortex-M 펌웨어에서 링커가 넣던 long-branch veneer와 같은 역할이다.
  • PLT0(.plt 첫 엔트리): 스텁에서 넘어온 x16(= puts의 GOT 슬롯 주소)과 x30(LR)을 스택에 저장하고, GOT의 예약 슬롯(0x1fff8 = .got.plt[2])에 있는 해석기 주소로 점프한다. 해석기는 스택에 저장된 x16을 보고 "어떤 슬롯을 채워야 하는지" 안다.
  • main의 두 호출 모두 bl 650 <puts@plt> — 코드는 PLT만 안다. 실제 주소는 GOT가 안다.

이제 gdb로 GOT 슬롯을 직접 본다. 슬롯 주소는 "로드 기준 + 0x20020"이고, 로드 기준은 &main − 0x7a8로 계산한다.

출력에서 볼 것:

  • lazy: 첫 호출 전 GOT[puts] = 0xaaaaaaaa05f0 = 로드 기준 0xaaaaaaaa0000 + 0x5f0 = PLT0. 첫 호출 후 0xfffff7e56b60 = libc의 puts. 그림 4의 1~6단계가 next 한 번 안에서 일어났다.
  • now: main에 도착했을 때 이미 puts의 주소가 들어 있다. ld.so가 시작 전에 다 채웠다.
  • -z now 빌드는 GOT 슬롯 위치(0x1ffc8)가 다르다. .got.plt가 따로 없고 .got에 합쳐져 RELRO 범위 안으로 들어가기 때문이다. 각 바이너리의 슬롯 오프셋은 readelf -r <bin> | grep puts로 얻었다.

파일 안에서 lazy GOT의 초기값도 확인할 수 있다. 슬롯마다 0x5f0(PLT0)이 들어 있고, 로드할 때 기준 주소만 더해진다.

6.3 예제 12 — LD_DEBUG=bindings로 "언제 무엇이 묶이나" 보기#

무엇을 확인하나: lazy에서는 호출하지 않은 함수(abort)가 바인딩되지 않고, now/LD_BIND_NOW=1에서는 바인딩된다는 것.

출력에서 볼 것: lazy에는 abort 바인딩 줄이 없다 — 한 번도 안 불렸으니 해석도 안 했다. 환경 변수 LD_BIND_NOW=1은 재빌드 없이 lazy 바이너리를 now처럼 동작시킨다. 위 §5.5의 "드문 경로에서 터지는 undefined symbol"을 테스트 단계에서 미리 잡는 가장 싼 방법이다. (stdbuf -o0은 stdout 버퍼링을 꺼서 바인딩 로그와 출력의 순서를 맞추려고 썼다.)

6.4 예제 13 — RELRO: GOT를 덮어쓸 수 있나?#

RELRO(RELocation Read-Only)는 "재배치가 끝난 뒤에는 바뀔 일 없는 영역(.init_array, .dynamic, .got)을 mprotect로 읽기 전용으로 만든다"는 링커+로더 협약이다. 공격자가 버퍼 오버플로로 GOT의 함수 주소를 덮어써서 실행 흐름을 빼앗는 공격(GOT overwrite)을 막는다.

빌드 옵션이름.got.plt(함수 슬롯)lazy 가능
-z norelroRELRO 없음쓰기 가능예
-z relro (+ lazy)partial RELRO쓰기 가능 (lazy가 써야 하므로)예
-z relro -z nowfull RELRO읽기 전용아니오

무엇을 확인하나: 실행 중인 프로그램이 자기 GOT의 puts 슬롯을 찾아서 덮어쓰려고 하면 세 가지 빌드에서 각각 어떻게 되는지.

출력에서 볼 것:

  • full RELRO만 GOT 덮어쓰기가 SIGSEGV로 막혔다. partial RELRO는 GNU_RELRO 세그먼트가 있는데도 함수 슬롯이 쓰기 가능하다. RELRO 범위가 0x1fda8 + 0x258 = 0x20000에서 끝나고, .got.plt(0x1ffe8~)의 puts 슬롯(파일 기준 0x20050)은 그 바깥이기 때문이다.
  • 처음 버전에서는 p[k] == (void *)puts로 비교했더니 partial에서도 SIGSEGV가 났다. C 코드에서 puts의 주소를 취하면 컴파일러가 .got(RELRO 안쪽)에 별도 슬롯을 만들어서 그걸 먼저 찾았기 때문이다. 그래서 dlsym으로 바꿨다. "함수 호출용 슬롯(.got.plt)"과 "주소 참조용 슬롯(.got)"이 따로 있다는 것을 보여 주는 실수였다.
  • 실무 결론: 보안 요구가 있는 장비(국방, 차량, 카메라)는 -Wl,-z,relro,-z,now + PIE가 기본 체크 항목이다. Ubuntu·Fedora gcc는 이미 기본이지만, 벤더 SDK의 크로스 gcc는 기본값이 다를 수 있으니 반드시 readelf -d의 BIND_NOW, readelf -l의 GNU_RELRO로 확인한다.

6.5 예제 14 — 측정: lazy vs now, 시작 시간은 얼마나 다른가#

lazy binding이 존재하는 이유는 시작 시간이다. 큰 GUI 앱이 수천 개 함수를 참조하지만 시작할 때는 일부만 쓴다. 정말 차이가 나는지 직접 잰다.

무엇을 확인하나: N개 함수를 가진 libmany.so와 그 N개를 참조는 하지만 1개만 실제 호출하는 앱을 만들어, lazy와 now의 실행 시간(fork+exec → 종료)을 300번 재서 중앙값을 비교.

(주석에는 "평균"이라고 썼지만 코드는 중앙값(statistics.median)을 쓴다.)

같은 측정을 한 번 더 돌렸을 때는 N=20000에서 lazy 288µs / now 1540µs였다(실행마다 ±10% 정도 흔들린다). 아래 차트는 위 표의 값이다. LD_DEBUG=statistics로 ld.so가 처리한 relocation 수도 확인했다.

그림 5 — 직접 측정한 시작 시간. 참조 심볼 1000개 정도까지는 차이가 수십 µs로 무시할 만하고, 2만 개에서 now가 약 1.1ms 더 든다. 대략 심볼 하나당 50~55ns.

출력에서 볼 것:

  • 시작 시 relocation 수: lazy 97개 vs now 20,101개. lazy에서도 함수가 아닌 relocation(데이터 참조, RELATIVE)은 시작 시 다 처리한다. 미뤄지는 것은 JUMP_SLOT(함수 호출)뿐이다.
  • 센서 데몬 같은 임베디드 앱은 참조 심볼이 많아야 수백~수천 개다. 수십~수백 µs 손해로 "시작 시 즉시 실패 + full RELRO"를 얻는 것은 거의 항상 좋은 거래다. 부팅 시간을 ms 단위로 깎아야 하는 제품이라면 그때 측정해서 판단한다(N 모듈의 부팅 최적화).
  • 이 VM은 Apple Silicon 위 가상화라 절대값은 실제 Cortex-A53 보드보다 훨씬 빠르다. 보드에서는 몇 배 커질 수 있다. 비율과 경향을 보자.

7. 심볼 가시성, 인터포지션, LD_PRELOAD, dlopen#

7.1 직관 — 공유 라이브러리의 "전역"은 프로세스 전체의 전역이다#

펌웨어에서 static이 아닌 함수는 "링크 단위 전체에서 보인다". 공유 라이브러리에서는 한 단계 더 나간다. 기본 가시성(default)인 심볼은 동적 심볼 테이블(.dynsym)에 올라가서 프로세스 안 모든 모듈과 경쟁한다. ld.so는 심볼을 찾을 때 "로드 순서(실행 파일 → LD_PRELOAD → DT_NEEDED 순)에서 처음 찾은 것"을 쓴다. 이를 interposition(끼어들기)이라고 한다.

결과 두 가지:

  1. 좋은 쪽: LD_PRELOAD로 malloc, open 같은 libc 함수를 재빌드 없이 바꿔 끼울 수 있다 (디버깅, 계측, 테스트용 가짜 하드웨어).
  2. 나쁜 쪽: 라이브러리 내부 함수끼리 부를 때도 "누가 끼어들었을지 모르니" PLT를 거쳐야 한다. 느리고, 내부 함수 이름이 ABI로 새어 나간다.

해결책이 -fvisibility=hidden + 공개 API에만 __attribute__((visibility("default")))다.

7.2 예제 15 — -fvisibility=hidden의 효과#

무엇을 확인하나: 같은 소스를 기본 가시성과 hidden으로 빌드했을 때 내보내는 심볼과 내부 호출 방식이 어떻게 달라지는지.

출력에서 볼 것:

  • default: 내부 헬퍼 두 개까지 export되었고, 같은 .so 안의 함수를 부르는데도 crc_step@plt를 거친다. 누군가 crc_step을 interpose할 수 있으니 컴파일러가 인라인도 못 했다.
  • hidden: export는 crc_calc 하나. 헬퍼는 인라인되어 사라졌다(호출 명령 자체가 없다). 더 작고, 더 빠르고, ABI 표면이 좁다.
  • (ldrb 줄은 grep "b\s" 패턴에 우연히 걸린 것이라 무시한다.)
  • 라이브러리를 만들 때 규칙: -fvisibility=hidden을 기본으로 하고 공개 API만 매크로로 연다. 커널도 같은 철학이다 — 모듈 안의 함수는 기본으로 모듈 밖에 안 보이고, EXPORT_SYMBOL로 연 것만 다른 모듈이 쓸 수 있다(§11).

7.3 예제 16 — LD_PRELOAD로 open()/fopen() 가로채기#

무엇을 확인하나: 앱 소스 수정 없이 어떤 파일을 여는지 로그를 찍는 shim 라이브러리. dlsym(RTLD_NEXT, ...)로 "다음 순서의 진짜 함수"를 찾아 넘긴다.

출력에서 볼 것:

  • binding file ./sensord ... to /tmp/B3/liblogopen.so: normal symbol 'fopen' — 앱의 fopen·open이 libc가 아니라 내 shim에 묶였다. 그 뒤 shim 안의 dlsym(RTLD_NEXT)가 libc의 진짜 fopen·open에 묶였다.
  • fopen은 내부적으로 open을 부르지만 [logopen] open("/etc/hostname") 로그는 없다. glibc 내부 호출은 PLT를 거치지 않는 내부 별칭으로 가서 interpose되지 않는다. "LD_PRELOAD는 모듈 경계를 넘는 호출만 가로챈다"를 기억하자.
  • 같은 shim으로 cat /etc/hostname을 돌렸을 때는 로그가 하나도 안 나왔다. 이 VM의 cat은 Rust로 쓴 uutils coreutils(/usr/lib/cargo/bin/coreutils/cat)이고, nm -D로 보면 open, open64, openat, openat64를 모두 import한다. 실제로 그중 내가 감싸지 않은 쪽을 쓰는 것으로 보인다. 진지한 shim은 open64·openat·openat64·fopen64까지 감싸야 한다. 더 확실한 관찰이 필요하면 LD_PRELOAD 대신 strace -e trace=openat(syscall 수준, A10)을 쓴다.
  • malloc을 감쌀 때는 함정이 하나 더 있다: dlsym 자체가 내부에서 메모리를 할당할 수 있어서 무한 재귀가 생길 수 있다. 그래서 glibc는 __libc_malloc 같은 내부 진입점을 제공하고, 실무에서는 LD_PRELOAD=libjemalloc.so처럼 완성된 할당자를 통째로 바꾸거나 ltrace -e malloc을 쓴다(이 노트에서는 malloc shim을 실행하지 않았다).

임베디드 활용 예: 센서 키트의 데몬이 /dev/i2c-1을 여는데 개발 PC에는 장치가 없다. LD_PRELOAD shim이 open("/dev/i2c-1")을 가로채 녹화된 데이터를 내주는 가짜 fd(예: memfd나 pipe)를 돌려주면 하드웨어 없이 데몬을 테스트할 수 있다.

보안 메모: setuid 프로그램에서는 ld.so가 LD_PRELOAD·LD_LIBRARY_PATH를 무시하거나 제한한다(secure-execution 모드). 그렇지 않으면 누구나 root 프로세스에 코드를 주입할 수 있기 때문이다.

7.4 예제 17 — dlopen/dlsym 플러그인 로더#

무엇을 확인하나: 빌드 시에 링크하지 않은 .so를 실행 중에 골라 불러오는 플러그인 패턴. 센서 키트에서 "설정 파일에 적힌 IMU 모델에 맞는 드라이버 플러그인을 로드"하는 구조다.

(마지막 nm 출력: 000000000001fe30 D sensor_plugin — 플러그인이 내보내는 심볼은 이것 하나뿐이다.)

출력에서 볼 것:

  • host의 NEEDED에는 플러그인이 없다. 빌드 시에는 플러그인을 전혀 모른다. glibc 2.34부터 dlopen이 libc에 들어와서 -ldl도 필요 없다.
  • bmi088.so(슬래시 없음)는 실패했다. 슬래시가 없으면 dlopen은 현재 디렉터리가 아니라 그림 3의 라이브러리 탐색 순서로 찾는다. 플러그인 경로는 항상 절대 경로나 ./로 준다.
  • 플러그인 ABI는 함수 하나 대신 구조체 하나를 내보내는 방식이 좋다. 버전 필드를 넣어 호환성을 검사할 수 있고, dlsym 호출이 한 번이다. 커널 드라이버의 struct file_operations, struct i2c_driver가 정확히 이 패턴이다(G 모듈).
  • RTLD_NOW: dlopen 시점에 모든 심볼을 해결해서, 플러그인에 빠진 심볼이 있으면 dlopen이 바로 실패한다(lazy의 "나중에 터짐" 회피). RTLD_LOCAL: 플러그인의 심볼이 다음 플러그인의 심볼 해석에 끼어들지 않게 한다.

8.2 예제 18 — 로더가 없을 때: "No such file or directory"의 정체#

무엇을 확인하나: patchelf --set-interpreter로 존재하지 않는 로더 경로를 박아 넣으면 실행 파일이 멀쩡히 있어도 ENOENT가 난다는 것. 크로스 컴파일한 바이너리를 다른 libc의 보드에 올렸을 때 정확히 이 상황이다.

출력에서 볼 것:

  • 셸마다 메시지가 다르다: 최신 bash는 "required file not found"로 힌트를 주지만, 임베디드 보드의 busybox는 그냥 "not found" 다. 보드에서 이걸 보면 반사적으로 readelf -l(또는 호스트에서 file)로 interpreter를 확인한다.

덤으로, 이 VM에는 musl 로더(/lib/ld-musl-aarch64.so.1)가 있어서 "glibc로 빌드한 바이너리를 musl 로더로 돌리면?"도 실행해 봤다.

로더는 찾았지만 glibc 전용 심볼(__printf_chk)이 musl에 없다. Alpine 기반 컨테이너에 glibc 바이너리를 넣으면 보는 바로 그 에러다(B2에서 자세히).

8.3 예제 19 — 다른 아키텍처: "Exec format error"와 qemu-user#

무엇을 확인하나: 32비트 ARM(armhf), x86_64, RISC-V 바이너리를 aarch64 VM에서 실행하면 각각 어떻게 되는지.

출력에서 볼 것 — 세 개가 전부 다르게 실패/성공했다.

  • armhf → ENOEXEC: 커널의 ELF 로더가 Machine: ARM, ELF32를 보고 거절했다. 이 커널은 CONFIG_COMPAT=y(32비트 유저 지원)로 빌드됐지만, Apple Silicon CPU가 AArch32 EL0를 지원하지 않기 때문에 32비트 바이너리를 못 돌린다. Cortex-A53/A72 같은 실제 SoC에서는 COMPAT로 armhf 바이너리가 돌 수 있다(그 경우엔 armhf 로더·라이브러리가 rootfs에 있어야 한다). 반대로 Cortex-A715, Cortex-X2 같은 일부 Armv9 코어는 AArch32를 아예 빼서 다시 ENOEXEC가 난다.
  • x86_64 → qemu가 받았다: 이 VM에는 binfmt_misc에 qemu-x86_64가 등록되어 있어서, 커널이 ELF 헤더의 매직을 보고 qemu로 넘겼다. qemu-user는 x86 로더(/lib64/ld-linux-x86-64.so.2)를 못 찾아서 실패했다 — §8.2와 같은 "로더 없음"이 한 단계 위에서 일어난 것이다.
  • RISC-V static → 성공: binfmt로 qemu-riscv64가 실행했고, 정적 링크라 로더가 필요 없었다. "크로스 바이너리를 빨리 테스트하려면 static으로"가 실용 팁이다.

sysroot를 주면 armhf 동적 바이너리도 qemu-user로 돌릴 수 있다.

-L은 "타깃의 /는 이 디렉터리라고 생각하라"는 뜻이다. 크로스 툴체인의 sysroot(B1)가 정확히 이 용도다. Yocto/Buildroot SDK도 같은 방식으로 호스트에서 타깃 유닛 테스트를 돌린다.

12. 커널 안에서는 무슨 일이 일어나나#

12.1 execve() — 커널이 ELF를 올리는 길#

Don이 ./app을 실행하면 커널에서 이런 일이 일어난다(함수 이름은 fs/exec.c, fs/binfmt_elf.c 기준).

  1. execve() → do_execveat_common() → 파일을 열고 첫 바이트들을 읽어 struct linux_binprm에 담는다.
  2. 등록된 바이너리 형식 핸들러(struct linux_binfmt)를 차례로 시도한다: ELF(load_elf_binary), 스크립트(#!, binfmt_script), binfmt_misc(qemu 같은 사용자 등록 형식). 아무도 못 받으면 ENOEXEC → "Exec format error". §8.3에서 x86 바이너리가 qemu로 간 것은 binfmt_misc가 받았기 때문이다.
  3. load_elf_binary(): ELF 헤더 검사(e_machine, class) → 프로그램 헤더 읽기 → PT_INTERP가 있으면 그 경로를 open_exec() (여기서 실패하면 ENOENT — §8.2의 정체) → PT_LOAD마다 vm_mmap()으로 매핑(권한은 p_flags에서), .bss 부분은 0 페이지 → PIE면 무작위 기준 주소 선택(ASLR).
  4. create_elf_tables(): 새 스택에 argv, envp, 그리고 auxv(보조 벡터)를 쌓는다. auxv는 커널이 ld.so에게 주는 쪽지다.
  5. 시작 PC를 인터프리터(ld.so)의 엔트리로 설정하고 유저 모드로 복귀. (정적 바이너리면 프로그램 자신의 e_entry.)

auxv는 LD_SHOW_AUXV=1로 볼 수 있다.

AT_PHDR = 로드 기준 0xbea714800000 + 0x40(§2.2의 PHDR offset), AT_ENTRY = 기준 + 0x6c0(§1.3의 Entry point). ld.so는 커널이 이미 매핑해 둔 프로그램 헤더를 AT_PHDR로 찾고, 자기 위치를 AT_BASE로 알고, 다 끝나면 AT_ENTRY로 점프한다. AT_SYSINFO_EHDR는 vDSO(ELF 이미지 하나를 커널이 매핑해 준 것), AT_RANDOM은 스택 카나리 등에 쓰는 16바이트 난수 주소다.

12.2 예제 24 — 커널 모듈 .ko는 ET_REL이고, 링커는 커널이다 (E3 미리보기)#

  • .rela.init.text의 relocation 종류(ADR_PREL_PG_HI21, ADD_ABS_LO12_NC, CALL26)가 §2.3의 hello.o와 똑같다. _printk에 대한 CALL26은 커널이 로드 시 _printk의 실제 주소로 채운다. 모듈과 커널 이미지가 ±128MB 밖에 떨어지면 bl이 닿지 않으므로 arm64 모듈 로더는 PLT(veneer)를 만든다 — .plt, .init.plt 섹션이 그 자리다.
  • UND _printk: 모듈이 커널에서 가져오는 심볼. 커널은 이것을 EXPORT_SYMBOL로 내보낸 심볼 테이블(__ksymtab)에서 찾는다. __versions는 그 심볼들의 CRC(modversions)로, 커널과 ABI가 맞는지 검사한다 — 유저 공간 심볼 버전(GLIBC_2.17)의 커널판이다.
  • .gnu.linkonce.this_module의 __this_module(1280바이트)은 struct module 초기값이고, init_module/cleanup_module 별칭이 module_init() 매크로로 만들어졌다. .modinfo는 modinfo가 읽는 key=value 문자열들, vermagic은 "이 커널 버전·설정에서만 로드하라"는 꼬리표다.

이제 실제로 로드해서 커널이 각 섹션을 어디에 놓았는지 본다(모듈 이름 b3_elfmod, 확인 후 바로 언로드).

출력에서 볼 것:

  • counter=8: .data의 7이 ++되었다. relocation이 제대로 .data의 실제 주소로 채워졌다는 증거다.
  • init fn at ...e030 = .init.text 시작 ...e028 + 8. 심볼 테이블의 b3_elfmod_init 값 0x8과 정확히 맞는다(앞 8바이트는 ftrace용 __patchable_function_entries 자리).

  • sysfs의 섹션 파일 이름이 .으로 시작해서 ls만 하면 안 보인다(ls -A 필요). 이 디렉터리는 gdb에서 add-symbol-file b3_elfmod.ko -s .text <addr> ...로 모듈 심볼을 올릴 때 쓰인다(M 모듈).

15. 면접에서 이렇게 말한다#

Q. "What's the difference between sections and segments in an ELF file?"

A. 섹션은 링커와 디버거를 위한 세밀한 단위(.text, .data, .symtab)이고, 세그먼트는 로더를 위한 단위로 "파일의 이 범위를 이 권한으로 이 주소에 매핑하라"는 지시다. 권한이 같은 섹션들이 하나의 PT_LOAD로 묶인다. 커널은 프로그램 헤더만 보고, 섹션 헤더를 지워도 실행된다.

Sections are the linker's and debugger's view — fine-grained units like .text, .data, .symtab, described by the section header table. Segments are the loader's view — program headers saying "map this file range at this address with these permissions." Sections with the same permissions are grouped into one PT_LOAD. The kernel only reads program headers; you can strip the section headers entirely and the binary still runs.

꼬리 질문: "Where does .bss live in the file?" → 파일에는 공간이 없고 PT_LOAD의 MemSiz > FileSiz 차이로 표현되며, 커널이 0 페이지로 채운다.

Q. "Explain PLT and GOT. How does lazy binding work?"

A. 코드는 읽기 전용이라 외부 함수 주소를 직접 고칠 수 없으니, 외부 호출은 PLT 스텁을 거쳐 GOT라는 쓰기 가능한 주소 테이블에서 목적지를 읽는다. lazy binding에서는 GOT 슬롯이 처음에 해석기 경로(PLT0)를 가리키고, 첫 호출 때 ld.so가 심볼을 찾아 GOT에 써 넣는다. 이후 호출은 PLT → GOT → 함수로 바로 간다.

Code is read-only and shared, so calls to external functions go through a small PLT stub that loads the target from the GOT, a writable per-process table of addresses. With lazy binding, each GOT slot initially points back into PLT0, which jumps to the dynamic linker's resolver; on the first call it looks up the symbol, patches the GOT slot, and jumps to the real function. Later calls go PLT → GOT → function directly. With -z now, all of that happens before main and the GOT can be made read-only.

꼬리 질문: "How would you demonstrate it?" → gdb에서 첫 호출 전후의 GOT 슬롯 값 비교, 또는 LD_DEBUG=bindings.

Q. "What is RELRO, and what's the difference between partial and full RELRO?"

A. 재배치가 끝난 뒤 바뀔 필요가 없는 영역(.got, .dynamic, .init_array)을 ld.so가 mprotect로 읽기 전용으로 바꾸는 것이다. partial RELRO는 lazy binding을 위해 함수용 GOT(.got.plt)를 쓰기 가능하게 남겨서 GOT overwrite 공격이 여전히 가능하고, full RELRO(-z relro -z now)는 모든 심볼을 시작 시 해석한 뒤 GOT 전체를 잠근다.

RELRO makes relocation-only data — .got, .dynamic, .init_array — read-only after the dynamic linker finishes relocating. Partial RELRO leaves the function GOT writable so lazy binding can patch it, which still allows GOT-overwrite exploits. Full RELRO, -z relro -z now, resolves everything at startup and then mprotects the whole GOT read-only. I measured the cost: about 50 nanoseconds per imported symbol at startup, so for typical embedded daemons it's negligible.

Q. "A binary you cross-compiled says 'No such file or directory' on the target, but the file is clearly there. What's going on?"

A. 동적 링크된 ELF에는 PT_INTERP로 로더 경로가 박혀 있고, 커널이 execve 때 그 로더를 연다. 로더가 없으면 execve가 ENOENT를 돌려주고 셸은 "not found"라고만 한다. readelf -l로 interpreter를 확인하고, 보드의 libc와 맞는 툴체인으로 다시 빌드하거나 정적으로 빌드한다.

A dynamically linked ELF has a PT_INTERP header naming its dynamic loader, like /lib/ld-linux-aarch64.so.1. The kernel opens that path during execve; if it's missing — typical when a glibc-built binary lands on a musl or differently-laid-out rootfs — execve returns ENOENT and busybox just prints "not found." I check readelf -l for the interpreter and ls the target's /lib. The fix is building with the target's SDK, or statically linking for a quick test.

꼬리 질문: "And 'Exec format error'?" → 커널의 binfmt 핸들러가 형식을 거절한 것(다른 아키텍처·32/64비트). file로 확인.

Q. "How does the dynamic linker find shared libraries? What's the difference between RPATH and RUNPATH?"

A. 순서는 RPATH(RUNPATH가 없을 때만) → LD_LIBRARY_PATH → RUNPATH → ld.so.cache → 기본 경로다. RPATH는 LD_LIBRARY_PATH보다 우선해서 덮어쓸 수 없고, RUNPATH는 나중이라 LD_LIBRARY_PATH로 바꿀 수 있다. 앱 번들에는 $ORIGIN 기반 RUNPATH를 쓴다.

Search order is DT_RPATH if there's no DT_RUNPATH, then LD_LIBRARY_PATH, then DT_RUNPATH, then /etc/ld.so.cache, then the default directories. RPATH beats LD_LIBRARY_PATH so you can't override it, while RUNPATH comes after, so you can — modern ld emits RUNPATH by default. For relocatable app bundles I use -rpath '$ORIGIN/../lib'. To debug it I run LD_DEBUG=libs, which prints every path tried.

Q. "Static vs dynamic linking — which would you choose for an embedded product?"

A. 바이너리가 많은 rootfs라면 동적이 libc 하나를 공유해 전체 크기와 보안 패치 면에서 유리하다. initramfs 도구, 복구 이미지, 로더 의존을 없애야 하는 작은 데몬은 정적이 낫고, 그때는 glibc보다 musl이 훨씬 작다. 측정해 보면 glibc 정적 hello가 700KB, musl 정적이 80KB였다.

For a rootfs with many binaries, dynamic linking wins: one copy of libc, smaller total image, and you patch a library CVE once. Static makes sense for initramfs tools, recovery images, or a single critical daemon where you want zero loader dependencies — and then musl, not glibc: a static hello was about 700 KB with glibc and 80 KB with musl when I measured it. I also check page-size alignment, since aarch64 defaults to 64K and that dominates tiny binaries.

Q. "How is a kernel module loaded? How is it different from loading a shared library?"

A. .ko는 ET_REL, 즉 프로그램 헤더 없는 재배치 가능 오브젝트다. finit_module로 넘기면 커널 모듈 로더가 vermagic과 서명을 검사하고, 섹션별로 메모리를 잡고, UND 심볼을 EXPORT_SYMBOL 테이블에서 찾아, arch별 apply_relocate_add로 재배치를 적용한 뒤 init을 부르고 .init 섹션을 해제한다. ld.so가 하는 일을 커널이 섹션 단위로 하는 것이다.

A .ko is an ET_REL object — no program headers, unresolved symbols like _printk. insmod passes it to finit_module; the kernel checks vermagic and the signature, lays out sections into module memory, resolves undefined symbols against exported kernel symbols, applies relocations with the arch's apply_relocate_add, calls the init function, and frees the .init sections. It's the same job ld.so does for a shared library, but done in the kernel at section granularity, and symbol visibility is controlled by EXPORT_SYMBOL instead of .dynsym.

Q. "You get a crash address from the field. How do you get to a source line?"

A. PIE와 .so는 로드 위치가 매번 다르니, 그 모듈의 로드 기준 주소를 빼서 파일 오프셋을 만든다. 그 크래시를 낸 빌드와 Build ID가 같은 debug 파일로 addr2line -f -i -e를 돌린다. 그래서 보드에는 stripped 바이너리를, 서버에는 Build ID로 색인한 .debug를 보관한다.

First turn the PC into a module-relative offset by subtracting the load base from /proc/pid/maps or dladdr — with PIE and ASLR the absolute address changes every run but the offset doesn't. Then run addr2line -f -i against the debug info from exactly that build, matched by GNU build ID. Our process ships stripped binaries and stores the objcopy --only-keep-debug output indexed by build ID, which gdb and debuginfod understand natively.

  1. (코드) 예제 16의 shim을 malloc/free 로깅 버전으로 바꿔라. dlsym 재귀 문제를 피하기 위해 glibc의 __libc_malloc/__libc_free를 쓰는 방식과, 첫 호출 동안 정적 버퍼에서 할당하는 방식 중 하나를 골라 구현하라. 정답/힌트: extern void *__libc_malloc(size_t);를 선언해 직접 부르면 dlsym이 필요 없다. 출력은 write(2, ...)로.
  1. (관찰) 예제 24의 모듈에 EXPORT_SYMBOL(b3_counter_get)로 함수를 하나 내보내고, 두 번째 모듈(b3_user)에서 그것을 호출하라. 로드 순서를 바꿔(b3_user 먼저) 어떤 에러가 나는지, /proc/kallsyms와 Module.symvers에 무엇이 생기는지 보라. 모듈 이름은 꼭 b3_로 시작하고 끝나면 rmmod한다. 정답/힌트: 먼저 로드하면 Unknown symbol b3_counter_get(dmesg). KBUILD_EXTRA_SYMBOLS로 첫 모듈의 Module.symvers를 알려 줘야 modpost 경고도 사라진다.
  1. (개념) 예제 23에서 KEEP()을 빼고 -Wl,--gc-sections로 링크하면 어떤 일이 생길지 예측하고 실행해서 확인하라. 커널 vmlinux.lds.h가 initcall에 KEEP을 쓰는 이유와 연결하라. 정답/힌트: 아무도 참조하지 않는 섹션이라 gc 대상이 되어 0 initcalls가 될 수 있다. 커널은 CONFIG_LD_DEAD_CODE_DATA_ELIMINATION에서도 initcall을 살려야 한다.
  1. (측정) 예제 14의 벤치마크를 -fvisibility=hidden으로 빌드한 libmany.so와 기본 빌드로 비교하라(앱이 쓰는 함수는 default로 열어 둔다). 동적 심볼 수와 시작 시간이 어떻게 달라지나? 정답/힌트: nm -D --defined-only | wc -l로 export 수부터 비교. 앱이 참조하는 심볼 수가 같으면 now 비용은 거의 같고, 라이브러리 자체의 내부 relocation이 줄어든다.

18. 요약 & 체크리스트#

Linux에서 ELF는 펌웨어의 .elf와 같은 형식이지만, 링크가 빌드 시간(ld)과 실행 시간(ld.so) 두 번에 걸쳐 일어나고 주소는 로드할 때(PIE+ASLR) 정해진다는 점이 다르다. 커널은 프로그램 헤더(세그먼트)만 보고 PT_LOAD를 mmap하고 PT_INTERP의 로더를 함께 올린다 — 로더가 없으면 "not found"다. ld.so는 DT_NEEDED의 soname을 RPATH → LD_LIBRARY_PATH → RUNPATH → ld.so.cache → 기본 경로 순으로 찾고, PLT/GOT를 통해 외부 함수를 연결한다. Ubuntu 기본은 -z now + RELRO(full RELRO)이고, 그 비용은 측정상 심볼당 약 50ns다. 정적 링크는 GNU ld가 아카이브를 한 번만 훑으므로 순서가 중요하다. 크래시 분석은 오프셋 + Build ID + 분리된 debug 파일이 핵심이다. 마지막으로 커널 모듈 .ko는 ET_REL이고, 커널이 ld.so의 일을 섹션 단위로 직접 한다 — 이 지식이 E3(모듈)과 C6(initcall)로 이어진다.
