0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어를 빌드하던 장면을 떠올려 보자. 회사 레포에는 Makefile(또는 그것을 감싼 사내 스크립트) 하나가 있고, make를 치면 ARM 크로스 컴파일러가 수백 개 .c를 컴파일해서 링커 스크립트대로 하나의 바이너리 이미지를 만든다. 외부 라이브러리는 거의 없고, 있어도 소스째 레포에 들어 있다. 빌드 시스템은 "우리 회사 것" 하나뿐이다.

Embedded Linux는 사정이 다르다. 보드에 올라가는 rootfs 하나에 수백 개의 오픈소스 패키지가 들어가고, 각 패키지는 작성자가 고른 빌드 시스템을 쓴다. BusyBox와 커널은 Make + Kconfig, systemd와 GStreamer는 Meson, OpenCV와 ROS 2 패키지는 CMake, 오래된 GNU 도구들(예: libmodbus, can-utils의 옛 버전)은 autotools다. 엔지니어는 이 모두를 같은 크로스 툴체인과 같은 sysroot로 빌드할 줄 알아야 하고, 그걸 수백 번 자동으로 해 주는 것이 Buildroot와 Yocto다(K3, K4).

그림 1 — Embedded Linux 빌드의 세 갈래. 앱은 메타 빌드 시스템(CMake·Meson·autotools)이 Ninja/Make 파일을 생성하고, 드라이버와 커널은 Kconfig + Kbuild가 맡는다. 모두 같은 툴체인과 sysroot 위에 서 있고, Buildroot/Yocto가 이 전체를 호출한다.

1. Make 기초 — 규칙, prerequisite, 타임스탬프#

1.1 직관 — "결과물이 재료보다 오래됐으면 다시 만든다"#

Make의 핵심 아이디어는 딱 하나다. 타깃 파일의 수정 시각(mtime)이 재료(prerequisite) 중 하나보다 오래됐거나, 타깃이 아예 없으면 레시피를 실행한다. 그 외의 모든 기능(변수, 패턴 규칙, 함수)은 이 규칙을 짧게 쓰기 위한 문법이다.

Don에게 익숙한 말로 바꾸면 Make는 의존성 그래프(DAG)를 DFS 후위 순회(post-order)하면서 "dirty" 노드만 다시 계산하는 스케줄러다. 펌웨어에서 "NAND 매핑 테이블 중 dirty 비트가 선 블록만 flush"하는 것과 같은 발상이다. dirty 판정 기준이 "mtime 비교"일 뿐이다.

1.2 규칙의 문법#

  • target: 만들 파일 이름 (보통 .o, 실행 파일).
  • prerequisite: target을 만드는 데 필요한 파일. 이것들이 먼저 최신이 되도록 Make가 재귀적으로 처리한다.
  • recipe: 셸 명령. 반드시 TAB 문자로 시작한다 (스페이스면 missing separator 에러).
  • 레시피의 각 줄은 별도의 셸에서 실행된다. 그래서 cd dir 다음 줄에서는 원래 디렉터리로 돌아와 있다 (cd dir && cmd로 한 줄에 써야 한다).

1.3 예제 ex1 — 타임스탬프로 다시 빌드할 것을 고른다#

무엇을 확인하나: 처음 빌드, 아무것도 안 바꾼 빌드, .c 하나 수정, 헤더 수정 각각에서 Make가 어떤 명령만 다시 돌리는지 본다.

imu.h에는 #define IMU_ODR_HZ 400과 int imu_read_accel(int axis);, imu.c는 return 1000 + axis;, main.c는 둘을 출력한다.

출력에서 볼 것: imu.c만 건드리면 main.o는 다시 컴파일하지 않는다. make -n(dry-run)은 실행하지 않고 실행할 명령만 보여 준다. make --trace(GNU Make 4.0+)는 왜 각 타깃을 다시 만드는지(due to: imu.h)까지 알려 준다 — "왜 이게 매번 다시 빌드되지?" 디버깅의 1번 도구다.

그림 2 — Make가 걷는 의존성 DAG. 루트(imu_app)에서 출발해 잎까지 내려간 뒤, 올라오면서 "타깃이 prerequisite보다 오래됐나"를 검사한다. imu.h를 건드리면 빨간 간선을 따라 위쪽 노드가 모두 다시 만들어진다.

1.4 phony 타깃 — "파일이 아닌 타깃"#

clean, all, install, test 같은 타깃은 파일을 만들지 않는다. 그런데 Make는 기본적으로 타깃을 파일 이름으로 본다. 그래서 우연히 clean이라는 파일이 생기면 "이미 최신"이라며 아무것도 안 한다. .PHONY:에 적어 두면 Make는 그 이름의 파일을 보지 않고 항상 레시피를 실행한다.

무엇을 확인하나: clean이라는 파일이 있을 때 .PHONY가 있는 Makefile과 없는 Makefile의 차이.

출력에서 볼 것: .PHONY가 없으면 "clean is up to date" 한 줄로 끝나고 아무것도 지워지지 않는다. 빌드 산출물을 넣는 디렉터리 이름을 build, test로 짓는 경우가 많아서 실제로 자주 걸린다.

=recursive (지연)참조할 때마다 다시 전개나중에 정의될 변수를 참조해야 할 때

무엇을 확인하나: =와 :=의 전개 시점 차이, 환경 변수와 명령행 변수가 ?=·+=와 만났을 때의 우선순위.

출력에서 볼 것이 세 가지다.

  1. LAZY는 나중에 바뀐 OPT = -O2를 반영했고, NOW는 정의 시점의 -O0에 고정됐다.
  2. 환경 변수 CROSS_COMPILE이 있으면 ?=는 아무 일도 안 한다. 반면 명령행 변수 CFLAGS=-O3는 Makefile 안의 += -Wall까지 무시하게 만든다 (명령행 변수가 가장 우선). 그래서 커널·패키지 Makefile은 사용자가 덮어쓰는 CFLAGS와 자기가 꼭 넣어야 하는 플래그를 다른 변수(KBUILD_CFLAGS, EXTRA_CFLAGS, ccflags-y)로 나눈다. 꼭 붙여야 하면 override CFLAGS += -Wall을 쓴다.
  3. 줄 끝 주석 앞의 공백이 값에 들어갔다 ([-O2 -g ]). DIR := build # 출력 폴더 같은 줄이 build 가 되어 $(DIR)/foo가 build /foo로 깨지는 고전적 버그다. 변수 정의 줄에는 줄 끝 주석을 달지 않는다.

2.2 자동 변수와 패턴 규칙#

파일이 수백 개면 규칙을 하나씩 쓸 수 없다. 패턴 규칙 %.o: %.c는 "어떤 X.o든 X.c에서 만든다"는 뜻이고, 레시피 안에서는 자동 변수로 이번에 매칭된 이름을 가리킨다.

자동 변수뜻ex2b에서 값
$@지금 만드는 타깃build/imu.o
$<첫 번째 prerequisitesrc/imu.c
$^모든 prerequisite (중복 제거)build/gnss.o build/imu.o ...
$?타깃보다 새로운 prerequisite만(변경된 것만)
$*패턴의 %에 매칭된 부분(stem)imu
$(@D) / $(@F)$@의 디렉터리 / 파일 부분build / imu.o

무엇을 확인하나: wildcard·patsubst로 소스 목록을 만들고, 패턴 규칙 하나로 모든 .o를 빌드하며 자동 변수 값을 직접 찍어 본다. | build는 order-only prerequisite로, "디렉터리가 존재하기만 하면 되고 mtime은 비교하지 않는다"는 뜻이다(디렉터리 mtime은 안에 파일이 생길 때마다 바뀌어서 일반 prerequisite로 두면 매번 다시 빌드된다).

출력에서 볼 것: 레시피 앞의 @는 명령 자체를 출력하지 않게 한다(커널의 CC [M] foo.o 같은 짧은 출력이 이 방식이다). $$는 셸에 $ 한 글자를 넘기는 이스케이프다.

2.3 내장 규칙 — Makefile이 없어도 빌드된다#

Make에는 %.o: %.c, %: %.c 같은 내장 규칙(built-in rules)과 CC, CFLAGS, LDLIBS 같은 기본 변수가 이미 들어 있다. make -p(print data base)로 전부 볼 수 있다.

무엇을 확인하나: Makefile 없이 make hello가 되는 이유를 make -p로 확인한다.

출력에서 볼 것: 내장 규칙 덕분에 CC=arm-linux-gnueabihf-gcc make hello만으로도 크로스 빌드가 된다. 관례적인 변수 역할도 여기서 나온다 — CPPFLAGS는 전처리기(-I, -D), CFLAGS는 컴파일러, LDFLAGS는 링커 옵션(-L, -Wl,...), LDLIBS는 라이브러리(-lm). -r(--no-builtin-rules)을 주면 내장 규칙이 꺼져서 같은 명령이 실패한다. 커널 Kbuild는 예측 가능성을 위해 내장 규칙과 내장 변수를 꺼 놓고(MAKEFLAGS += -rR) 모든 규칙을 직접 정의한다.

3. 헤더 의존성 — "헤더를 바꿨는데 다시 빌드가 안 된다"#

3.1 문제#

Make는 Makefile에 적힌 의존성만 안다. .c가 #include하는 헤더는 컴파일러만 알고 Make는 모른다. 그래서 패턴 규칙을 %.o: %.c로만 써 두면, 헤더를 바꿔도 그 헤더를 쓰는 .o들이 다시 컴파일되지 않는다. 결과는 단순한 "옛 값"이 아니라 구조체 레이아웃이 서로 다른 오브젝트가 한 바이너리에 섞이는 ABI 불일치다. 펌웨어로 치면 공유 메모리 구조체의 정의를 바꿨는데 한쪽 코어 펌웨어만 다시 빌드된 상황이다.

3.3 -M 계열 플래그 정리#

플래그뜻
-M의존성 규칙만 출력하고 컴파일은 안 함 (시스템 헤더 포함)
-MM-M과 같되 시스템 헤더(<stdio.h>) 제외
-MD컴파일하면서 부산물로 .d 파일 생성 (시스템 헤더 포함)
-MMD-MD와 같되 시스템 헤더 제외 — 가장 많이 쓴다
-MP각 헤더에 대해 레시피 없는 빈 규칙(imu.h:)을 추가
-MF file.d 파일 이름 지정
-MT target.d 안의 타깃 이름 지정 (CMake/Meson이 -MT·-MF를 같이 쓴다)

.d 파일을 컴파일과 동시에 만드는 것이 핵심이다. 첫 빌드에는 .d가 없지만 어차피 .o도 없어서 전부 컴파일되므로 문제없다. -include의 -는 "파일이 없어도 에러 내지 말라"는 뜻이다.

3.4 -MP는 왜 필요한가 — 헤더를 지웠을 때#

무엇을 확인하나: imu.c에서 #include "old.h"를 지우고 old.h 파일도 삭제했을 때, -MP 유무에 따른 차이.

출력에서 볼 것: 옛 .d가 아직 "imu.o는 old.h가 필요하다"고 말하고 있는데 old.h가 없으니 Make는 그걸 만들 규칙을 찾다 멈춘다. -MP가 만든 빈 규칙 old.h:가 있으면 "만들 방법은 있고 결과는 항상 새것"으로 취급되어 imu.o가 다시 컴파일되고, 새 .d에서는 old.h가 사라진다. 헤더를 지우거나 이름을 바꾸는 리팩터링 뒤 "No rule to make target xxx.h"가 나오면 -MP 누락이다.

4. 병렬 빌드 -j 와 누락 의존성 race#

4.1 -j가 하는 일#

make -jN은 DAG에서 서로 의존하지 않는 노드를 최대 N개 동시에 실행한다. 직렬(-j1)일 때 Make는 prerequisite를 왼쪽부터 차례대로 처리하기 때문에, 의존성이 빠져 있어도 "우연히 순서가 맞아서" 동작하는 경우가 많다. -j는 그 우연을 없앤다. RTOS에서 우선순위 덕분에 우연히 지켜지던 실행 순서가 멀티코어로 옮기자 깨지는 것과 같다.

4.2 예제 ex5 — 생성 헤더 의존성 누락#

무엇을 확인하나: 빌드 중에 만들어지는 version.h(펌웨어 빌드에서 git describe로 버전 헤더를 생성하는 흔한 패턴)를 main.o의 prerequisite에서 빠뜨리면 -j1은 되고 -j4는 깨진다.

출력에서 볼 것: -j4에서는 version.h 생성과 main.o 컴파일이 동시에 시작돼서 컴파일러가 아직 없는 헤더를 찾는다. 고치는 법은 "순서를 맞추는 것"이 아니라 진짜 의존성을 적는 것(main.o: main.c version.h)이다. 생성 헤더는 -MMD로도 해결되지 않는다는 점에 주의 — .d는 첫 컴파일이 성공한 뒤에야 생기므로 첫 빌드에서는 아무 도움이 안 된다. 실무 증상은 "CI에서 가끔 빌드가 깨지는데 다시 돌리면 된다"다.

4.3 재귀 make vs 비재귀 make#

큰 프로젝트를 디렉터리별로 나눌 때 두 방식이 있다.

  • 재귀(recursive) make: 최상위 Makefile이 $(MAKE) -C subdir로 하위 디렉터리마다 별도의 make 프로세스를 띄운다. 각 make는 자기 디렉터리의 DAG만 안다.
  • 비재귀(non-recursive) make: 최상위 make 하나가 모든 하위 디렉터리의 규칙 조각을 include해서 전체 DAG 하나를 만든다.

Peter Miller의 1997년 논문 "Recursive Make Considered Harmful"이 지적한 문제는, 재귀 make에서는 디렉터리 경계를 넘는 의존성이 보이지 않는다는 것이다.

무엇을 확인하나: app/이 ../lib/libsensor.a에 의존하는데 최상위에서 lib와 app을 독립 phony 타깃으로 두면 -j2에서 깨진다.

lib/Makefile은 sensor.o로 libsensor.a를 만들고(느린 단계를 흉내 내려고 sleep 0.5), app/Makefile은 app: main.o ../lib/libsensor.a다.

출력에서 볼 것: app 쪽 make는 ../lib/libsensor.a를 만드는 규칙을 모르기 때문에 "No rule to make target"으로 멈춘다(그 직후에 lib 쪽 ar이 끝나는 것이 보인다). 디렉터리 간 순서(app: lib)를 최상위에 적어야 한다. 그리고 재귀 make는 lib 안의 파일이 바뀌었는지 app 쪽 make가 정확히 판단하지 못하는 문제도 남는다.

커널 Kbuild는 겉보기에는 디렉터리마다 $(MAKE) -f scripts/Makefile.build obj=<dir>로 내려가는 재귀 구조지만, 디렉터리 간 의존(링크 순서, modpost)을 최상위에서 단계별로 묶어 관리한다. CMake·Meson은 프로젝트 전체를 하나의 build.ninja로 생성해서 이 문제를 구조적으로 피한다 — 비재귀가 기본이다.

5. 측정 — -j 스케일링과 증분 빌드 비용#

말로만 하지 않고 숫자로 보자. Python 스크립트로 200개 모듈(각 .c 약 43줄, 함수 40개짜리) + main.c의 프로젝트를 생성했다. 모든 mod_NNN.c는 공통 헤더 common.h와 자기 헤더 mod_NNN.h를 include하고, main.c는 200개 mod_NNN.h를 모두 include한다. Makefile은 DEPS=1이면 -MMD -MP + -include, DEPS=0이면 헤더 의존성 없음이다.

측정 스크립트(핵심부):

VM은 4 vCPU이고 다른 에이전트가 같은 VM에서 동시에 작업 중이었다(측정 시작 load average 0.56, 끝 3.15). 그래서 각 조건을 3번 돌려 중앙값을 쓴다.

그림 3 — 같은 200 모듈 프로젝트의 전체 빌드 시간. -j2까지는 거의 선형(1.93배)이지만 -j4는 2.53배에 그친다. 4 vCPU를 다른 에이전트와 나눠 쓰고 있었고, 마지막 링크 한 번은 병렬화되지 않기 때문이다. -j8이 코어 수보다 많은데도 조금 더 빨라진 것은 한 컴파일이 파일 I/O·프로세스 생성을 기다리는 사이 다른 작업이 CPU를 채우기 때문이다.

그림 4 — 헤더 하나를 건드린 뒤의 증분 빌드. 의존성이 있으면 common.h 수정은 200개 재컴파일(3.01 s), mod_017.h 수정은 그 헤더를 쓰는 mod_017.c와 main.c 2개만 재컴파일(132 ms)한다. 의존성이 없으면 항상 몇 ms로 끝나지만 다시 컴파일해야 할 것을 0개 컴파일한 것이므로 결과물이 틀렸다(§3의 stack smashing).

숫자에서 읽을 것:

  • -MMD의 비용은 작다. 변경 없는 빌드에서 .d 201개를 읽고 판단하는 데 37 ms(의존성 없음은 6 ms). 30 ms를 아끼려고 정확성을 버릴 이유가 없다.
  • 헤더 설계가 빌드 시간을 정한다. 모두가 include하는 "god header"(common.h) 한 줄 수정 = 전체 재빌드다. 헤더를 잘게 나누고 필요한 것만 include하는 것이 증분 빌드를 빠르게 하는 가장 큰 레버다. 커널이 #include <linux/kernel.h> 남용을 줄이려는 이유도 같다.
  • -j는 코어 수 근처에서 포화된다. 관례는 make -j$(nproc), CI에서는 메모리가 허락하면 그보다 조금 크게.

5.1 ccache — 같은 컴파일을 다시 하지 않는다#

ccache는 컴파일러 앞에 끼워 넣는 캐시다. 전처리 입력·컴파일 옵션·컴파일러를 해시해서, 같은 조합이면 저장해 둔 .o를 돌려준다. 브랜치를 오가거나 make clean을 자주 하는 Yocto/커널 빌드에서 효과가 크다.

무엇을 확인하나: 같은 200 모듈 프로젝트를 CC="ccache gcc"로 clean 빌드 두 번.

출력에서 볼 것: 두 번째 clean 빌드는 201개 전부 캐시 hit라서 3.96 s → 0.12 s다. Uncacheable 2개는 링크 호출이다(ccache는 링크를 캐시하지 않는다). 크로스 컴파일에도 그대로 쓴다: CC="ccache arm-linux-gnueabihf-gcc", 커널은 make CC="ccache aarch64-linux-gnu-gcc". Buildroot는 BR2_CCACHE, Yocto는 INHERIT += "ccache"(또는 sstate 캐시가 더 큰 단위로 같은 일을 한다)로 켠다.

6. Make로 크로스 컴파일 — CROSS_COMPILE 관례#

커널, U-Boot, BusyBox, 많은 사내 Makefile이 공유하는 관례가 있다. 툴체인 접두사(prefix)를 변수 하나로 받고, 모든 도구 이름을 거기서 만든다.

접두사 끝의 -까지 포함한다는 점이 함정이다(CROSS_COMPILE=arm-linux-gnueabihf라고 쓰면 arm-linux-gnueabihfgcc를 찾는다). 커널은 여기에 ARCH=arm64 같은 아키텍처 변수가 하나 더 필요하다(E2).

6.1 예제 ex6 — 한 Makefile로 세 아키텍처#

무엇을 확인하나: 같은 소스를 CROSS_COMPILE과 출력 디렉터리 O만 바꿔 aarch64(네이티브), armhf, riscv64로 빌드하고, file과 qemu-user로 결과를 검증한다.

출력에서 볼 것: file의 ELF 32-bit ... ARM, EABI5와 interpreter /lib/ld-linux-armhf.so.3가 "진짜 armhf 바이너리"라는 증거다. qemu-arm -L <dir>은 동적 로더와 libc를 <dir> 아래에서 찾게 하는 user-mode 에뮬레이터다(armhf에서 uname이 armv7l을 보고하는 것도 qemu가 흉내 낸 값). 직접 실행하면 Exec format error다 — 이 VM(Apple Silicon 위 aarch64)은 AArch32 실행을 지원하지 않고, binfmt_misc에 qemu-arm도 등록돼 있지 않다. 출력 디렉터리를 O=로 나누는 것도 커널 관례(make O=build-imx8)와 같다: 한 소스 트리로 여러 보드를 동시에 빌드할 수 있다.

7. Kbuild · Kconfig 미리보기 — 커널은 자기 빌드 시스템을 쓴다#

커널은 일반 Makefile이 아니라 Kbuild라는 Make 기반 프레임워크로 빌드된다. 드라이버 작성자가 쓰는 Makefile은 "무엇을 빌드할지"만 선언하고, "어떻게"(컴파일 플래그, 링크, modpost, 서명, 설치)는 커널 트리의 scripts/Makefile.*가 전부 한다. 그리고 "무엇을 켤지"는 Kconfig로 정한다. 여기서는 미리보기만 하고, 깊은 내용은 E2(커널 빌드·Kconfig·defconfig)에서 다룬다.

7.1 예제 ex7 — out-of-tree 모듈을 VM 커널 헤더로 빌드#

out-of-tree 모듈은 커널 소스 트리 바깥(내 레포)에 있는 드라이버를 이미 빌드된 커널에 맞춰 .ko로 빌드하는 방식이다. 벤더 Wi-Fi 드라이버, 개발 중인 센서 드라이버가 이 형태로 시작한다. 필요한 것은 커널 소스 전체가 아니라 그 커널을 빌드할 때의 설정과 헤더, Makefile들이며, Ubuntu에서는 linux-headers-$(uname -r) 패키지가 /lib/modules/$(uname -r)/build → /usr/src/linux-headers-...로 제공한다.

무엇을 확인하나: obj-m 한 줄짜리 Kbuild 파일과 위임만 하는 바깥 Makefile로 모듈을 빌드하고, 모듈 파라미터를 주어 로드·언로드한다. 소스에서 CONFIG_HZ, CONFIG_ARM64 같은 Kconfig 매크로를 그대로 쓸 수 있는지도 본다.

출력에서 볼 것:

  • make -C $(KDIR)로 커널 헤더 트리의 최상위 Makefile이 실행되고(Entering directory '/usr/src/linux-headers-...'), M=이 "외부 모듈 디렉터리는 여기"라고 알려 준다. 그러면 Kbuild가 M 디렉터리의 Kbuild(없으면 Makefile)를 읽어 obj-m을 찾는다. 우리 Makefile은 사실상 두 번 읽힌다: 한 번은 우리가 make를 칠 때, 한 번은 Kbuild가 obj-m을 찾을 때. 그래서 Kbuild 파일을 따로 두는 편이 깔끔하다.
  • compiler differs 경고: 커널은 aarch64-linux-gnu-gcc로, 우리는 gcc로 빌드했다. 이 VM에서는 같은 gcc 15.2라 문제없지만, 보드 커널과 다른 버전의 컴파일러로 모듈을 빌드하면 구조체 레이아웃·플러그인 플래그 차이로 로드 실패나 오동작이 날 수 있다. 실무에서는 보드 커널을 빌드한 바로 그 툴체인(Yocto SDK, 벤더 툴체인)을 쓴다.
  • vermagic: 모듈이 맞춰 빌드된 커널 릴리스와 핵심 설정(SMP preempt mod_unload modversions aarch64)이다. 로드할 때 실행 중인 커널과 다르면 거부된다(§13).

이제 로드해 보자. 모듈 이름은 다른 작업과 겹치지 않게 b4_ 접두사를 쓰고, 끝나면 반드시 내린다.

출력에서 볼 것: module_param이 /sys/module/b4_hello/parameters/odr_hz로 노출됐다(0444 = 읽기 전용). CONFIG_HZ와 CONFIG_ARM64는 우리가 정의한 적이 없는데 쓸 수 있었다 — Kbuild가 모든 커널 소스 컴파일에 Kconfig 결과 헤더를 강제로 include하기 때문이다. make V=1로 실제 컴파일 명령을 보면 확인된다(관련 부분만 발췌).

같은 명령줄에는 -nostdinc(유저 공간 libc 헤더 금지), -D__KERNEL__, -DMODULE, -DKBUILD_MODNAME='"b4_hello"', -mgeneral-regs-only(커널에서는 FP/SIMD 레지스터 사용 금지)도 들어 있다. 드라이버 코드에서 <stdio.h>를 include할 수 없는 이유가 이 -nostdinc다.

Kconfig는 "어떤 기능을 켤 수 있고, 무엇에 의존하고, 기본값이 무엇인가"를 적는 설정 언어다. make menuconfig의 메뉴가 이 파일들에서 생성된다.

무엇을 확인하나: 센서 키트를 흉내 낸 작은 Kconfig를 VM 커널 헤더에 들어 있는 진짜 scripts/kconfig/conf 도구로 처리해서 .config → auto.conf · autoconf.h가 생기는 과정을 본다.

출력에서 볼 것:

  • select REGMAP_I2C 때문에 사용자가 고를 수 없는(프롬프트 없는) REGMAP_I2C가 IMU 드라이버와 같은 m으로 켜졌다.
  • GNSS_UBLOX는 SERIAL_SUPPORT가 꺼져 있어서 .config에 아예 나타나지 않는다.
  • =y는 #define CONFIG_X 1, =m은 #define CONFIG_X_MODULE 1이 된다. 그래서 C 코드에서 #ifdef CONFIG_IMU_BMI270은 모듈로 빌드할 때 거짓이다. 이 함정 때문에 커널 코드는 IS_ENABLED(CONFIG_X)(y 또는 m이면 참)와 IS_BUILTIN(), IS_MODULE() 매크로를 쓴다(include/linux/kconfig.h).
  • IMU 드라이버를 끄고 olddefconfig를 돌리면 그것에 의존하던 IMU_ODR_HZ와 select로 끌려왔던 REGMAP_I2C가 함께 사라진다. 처음에 MODULES 심볼(modules 속성)을 빼고 돌렸을 때는 default m이 y로 올라갔다 — 모듈 지원이 없는 설정에서 tristate는 bool처럼 동작한다.

실제 커널의 .config와 autoconf.h도 같은 관계다.

그리고 Kbuild Makefile 쪽에서는 auto.conf의 값이 Make 변수가 되어 이렇게 쓰인다(커널 drivers/ 아래 Makefile의 전형적인 모양).

그림 5 — Kconfig → .config → 두 개의 생성 파일 → Kbuild. 같은 설정이 Make 쪽(auto.conf: 무엇을 컴파일할지)과 C 쪽(autoconf.h: 코드 안의 조건부 컴파일)으로 동시에 흘러간다.

8. 메타 빌드 시스템 — configure → generate → build#

Make는 "명령을 실행하는 엔진"이다. 하지만 이식성 있는 프로젝트는 빌드 전에 물어야 할 것이 많다. 컴파일러가 무엇인가? termios.h가 있나? libz는 어디 있고 어떤 플래그가 필요한가? 크로스 빌드인가? 이 질문에 답하고 그 결과로 Makefile이나 build.ninja를 생성하는 도구가 메타 빌드 시스템이다. 세 가지 모두 같은 3단계 구조를 가진다.

그림 6 — 세 메타 빌드 시스템의 같은 3단계. 입력(파란색)을 설정 단계(주황)가 읽어 시스템을 검사하고, 생성물(초록)로 Ninja/Make 파일을 만든 뒤, 실제 컴파일은 Ninja나 Make가 한다. 크로스 정보(컴파일러, sysroot, 타깃 CPU)는 설정 단계에 한 번만 넣는다.

핵심 공통점 두 가지:

  • 설정과 빌드가 분리된다. 설정 단계에서 내린 결정(컴파일러 경로, 찾은 라이브러리)은 캐시(CMakeCache.txt, meson-info, config.status)에 저장된다. 그래서 툴체인을 바꿀 때는 빌드 디렉터리를 지우고 다시 설정해야 한다. 같은 빌드 디렉터리에서 컴파일러만 바꾸려 하면 옛 캐시가 이긴다.
  • out-of-tree 빌드: 소스 디렉터리와 빌드 디렉터리를 분리한다. build-native/, build-armhf/를 나란히 두고 같은 소스를 두 타깃으로 빌드할 수 있다. Meson은 in-tree 빌드를 아예 허용하지 않는다.

9. CMake — 타깃 중심 빌드와 toolchain file#

9.1 타깃과 속성 전파#

현대 CMake(3.x 이후)의 핵심은 타깃(target)이다. add_library·add_executable로 타깃을 만들고, include 경로·정의·링크 라이브러리를 타깃의 속성으로 붙인다. 속성에는 전파 범위가 있다.

키워드이 타깃 자신이 타깃을 링크하는 쪽
PRIVATE적용전파 안 됨
PUBLIC적용전파됨
INTERFACE적용 안 됨전파됨 (헤더 전용 라이브러리)

Don의 말로 바꾸면 "헤더에 노출되는 것은 PUBLIC, .c 안에서만 쓰는 것은 PRIVATE"이다. 전역 변수 CMAKE_C_FLAGS나 include_directories()를 쓰는 옛 스타일은 이 전파가 안 되어 큰 프로젝트에서 플래그가 엉킨다.

9.2 예제 ex9 — 라이브러리 + 실행 파일, out-of-tree 네이티브 빌드#

무엇을 확인하나: imu 정적 라이브러리의 PUBLIC include 경로는 sensord에도 전파되고, PRIVATE 정의(IMU_ODR_HZ)는 imu.c에만 붙는지 실제 컴파일 명령으로 확인한다.

출력에서 볼 것:

  • main.c의 컴파일에도 -I/tmp/B4/ex9/include가 붙었다(PUBLIC 전파). -DIMU_ODR_HZ=400은 imu.c에만 있다(PRIVATE).
  • CMake도 -MD -MT ... -MF ...d로 헤더 의존성을 자동 생성한다(§3). 손으로 Makefile을 쓰지 않는 큰 이유다.
  • 소스 디렉터리에는 아무것도 생기지 않았다(out-of-tree). -G Ninja를 빼면 Unix Makefiles 생성기가 기본이다.

9.3 toolchain file — CMake에 "타깃이 무엇인가"를 알려 주는 파일#

CMake로 크로스 빌드할 때는 CMakeLists.txt를 고치지 않는다. 대신 toolchain file을 -DCMAKE_TOOLCHAIN_FILE=로 넘긴다. 이 파일은 project()가 컴파일러를 검사하기 전에 읽힌다.

변수뜻
CMAKE_SYSTEM_NAME타깃 OS (Linux, bare-metal이면 Generic). 이걸 설정하면 CMAKE_CROSSCOMPILING이 TRUE
CMAKE_SYSTEM_PROCESSOR타깃 CPU (arm, aarch64) — 프로젝트가 분기용으로 참조
CMAKE_C_COMPILER크로스 컴파일러 (ar·ranlib·strip은 접두사로 자동 추정)
CMAKE_SYSROOT컴파일·링크에 --sysroot=로 넘길 타깃 루트
CMAKE_FIND_ROOT_PATHfind_library·find_path·find_package가 뒤질 루트들
CMAKE_FIND_ROOT_PATH_MODE_PROGRAMNEVER: 실행할 도구는 호스트에서 찾는다
CMAKE_FIND_ROOT_PATH_MODE_LIBRARY / _INCLUDE / _PACKAGEONLY: 라이브러리·헤더·패키지는 타깃 루트 안에서만 찾는다

첫 시도로 Debian/Ubuntu 크로스 패키지가 설치한 /usr/arm-linux-gnueabihf를 그대로 sysroot로 써 봤다.

(중간 출력은 ...로 생략.) 이 실패가 sysroot의 의미를 잘 보여 준다. libc.so는 실제로는 텍스트 링커 스크립트이고 안에 /usr/arm-linux-gnueabihf/lib/libc.so.6 같은 절대 경로가 적혀 있다. 링커는 sysroot 안에 있는 스크립트의 절대 경로 앞에 sysroot를 붙이므로 /usr/arm-linux-gnueabihf/usr/arm-linux-gnueabihf/lib/...를 찾다 실패한다("inside"). 즉 Debian의 /usr/arm-linux-gnueabihf는 타깃 rootfs 모양의 진짜 sysroot가 아니다 — 크로스 gcc에 경로가 내장된 "multiarch 크로스 설치"일 뿐이다.

진짜 sysroot는 타깃 보드의 /를 복사한 것처럼 usr/include, usr/lib가 있는 디렉터리다. Yocto SDK의 sysroots/cortexa53-poky-linux/, Buildroot의 output/staging/이 그 모양이다. 여기서는 그 구조를 심볼릭 링크로 흉내 냈다.

최종 toolchain file:

무엇을 확인하나: 같은 CMakeLists.txt를 toolchain file만 바꿔서 armhf로 빌드하고 file·qemu-arm으로 검증한다.

출력에서 볼 것: 모든 컴파일에 --sysroot=가 자동으로 붙었고, sizeof(void*)=4로 32-bit 타깃임이 확인된다. 소스와 CMakeLists.txt는 한 글자도 안 바꿨다. 이것이 "toolchain file은 보드 팀이 한 번 만들어 배포하고, 앱 개발자는 -DCMAKE_TOOLCHAIN_FILE만 붙인다"는 실무 구조의 이유다.

9.4 예제 ex15 — FIND_ROOT_PATH_MODE가 막아 주는 것#

무엇을 확인하나: 개발자 PC에 호스트용(aarch64) libbmi.so가 /tmp/B4/hostprefix에, 타깃용(armhf) libbmi.so가 sysroot에 있을 때, CMAKE_PREFIX_PATH에 호스트 경로가 섞여 들어오면 find_library가 무엇을 고르는가. (libbmi는 §11에서 만든다.)

출력에서 볼 것: ONLY일 때는 CMAKE_PREFIX_PATH도 sysroot 아래로 다시 뿌리내려서(re-root) armhf 라이브러리를 찾았다. NEVER로 바꾸면 aarch64 라이브러리를 armhf 빌드에 집어 온다 — 설정 단계는 조용히 성공하고 링크 단계에서야 터진다. PYTHON_EXE는 두 경우 모두 호스트 것이다(PROGRAM NEVER, 빌드 중에 실행할 도구이므로 맞다). 호스트 zlib는 두 경우 모두 못 찾았는데, armhf 컴파일러 기준 라이브러리 아키텍처 디렉터리(arm-linux-gnueabihf)만 보기 때문이다. 처음에는 -DCMAKE_FIND_ROOT_PATH_MODE_LIBRARY=NEVER를 명령행으로 줘 봤는데 결과가 같았다 — toolchain file 안의 set()이 일반 변수로 캐시 변수를 가리기 때문이다. toolchain file에 적힌 값은 명령행으로 덮어쓰기 어렵다는 것도 기억해 둔다.

10. Meson + Ninja — cross file#

Meson은 Python 비슷한(그러나 튜링 완전하지 않은) 선언형 언어로 빌드를 기술하고 Ninja 파일을 생성한다. Ninja는 사람이 쓰기보다 생성기가 쓰도록 만든 저수준 빌드 실행기로, 시작이 빠르고 기본으로 nproc + 2개쯤 병렬 실행하며, 명령줄이 바뀌어도 다시 빌드한다(Make는 명령줄 변경을 모른다).

Meson은 세 가지 기계를 구분한다. 이 용어는 autotools의 --build/--host/--target과 같다.

용어뜻예
build machine빌드를 실행하는 기계개발 PC (이 VM의 aarch64)
host machine만든 프로그램이 돌아갈 기계보드 (armv7)
target machine(컴파일러를 빌드할 때만) 그 컴파일러가 코드를 생성할 대상보통 host와 같음

10.1 예제 ex10 — meson.build와 cross file#

무엇을 확인하나: pkg-config 의존성(bmi)을 가진 작은 앱을 cross file로 armhf 빌드하고, Meson이 build/host machine을 어떻게 보고하는지 본다.

app.c는 <bmi.h>를 include하고 bmi_chip_id()를 출력한다.

출력에서 볼 것:

  • Build type: cross build와 build/host machine 구분. Meson은 크로스 빌드 중에도 build machine용 컴파일러를 따로 찾는다(빌드 중에 실행할 코드 생성기를 컴파일하기 위해). 그 컴파일러로 ccache cc를 자동으로 골랐다 — Meson은 ccache가 PATH에 있으면 자동으로 끼운다.
  • Run-time dependency bmi found: YES 0.3.0: cross file의 pkg_config_libdir(§11의 PKG_CONFIG_LIBDIR) 덕분에 sysroot 안의 bmi.pc를 찾았고, -I/tmp/B4/sysroot-armhf/usr/include는 sys_root가 PKG_CONFIG_SYSROOT_DIR 역할을 해서 붙은 것이다.
  • exe_wrapper는 크로스 빌드에서 meson test나 빌드 중 실행이 필요할 때 qemu로 돌리게 해 준다.
  • 기본 빌드 타입은 debug(-O0 -g)다. 보드용 릴리스는 --buildtype=release를 준다.

11. autotools — ./configure가 하는 일#

11.1 직관#

autotools(autoconf + automake + libtool)는 1990년대 다양한 유닉스 사이에서 이식성을 확보하려고 만들어졌다. 개발자가 쓰는 것은 configure.ac(무엇을 검사할지, m4 매크로)와 Makefile.am(무엇을 빌드할지)이고, autoreconf -i가 이것으로부터 수천 줄짜리 POSIX 셸 스크립트 configure와 Makefile.in을 생성한다. 사용자는 ./configure && make && make install만 한다.

./configure가 실제로 하는 일은 단순하다. 작은 테스트 프로그램(conftest.c)을 수십 개 컴파일·링크해 보고, 성공 여부로 config.h의 #define HAVE_XXX 1과 Makefile 변수를 결정한다. 펌웨어로 치면 부팅 시 하드웨어 레지스터를 하나씩 probe해서 기능 비트맵을 채우는 것과 같다. 크로스 빌드에서 문제가 되는 건 "실행해 봐야 알 수 있는 검사"다 — 타깃 바이너리는 호스트에서 실행할 수 없기 때문이다.

11.2 예제 ex11 — 작은 autotools 프로젝트#

무엇을 확인하나: configure.ac·Makefile.am으로 프로젝트를 만들고 autoreconf -i, 네이티브 configure, --host=arm-linux-gnueabihf 크로스 configure, 그리고 실패한 검사를 config.log로 추적한다.

출력에서 볼 것: 개발자가 쓴 두 파일에서 configure, Makefile.in, config.h.in과 보조 스크립트(depcomp는 헤더 의존성 추적용 — §3의 역할)가 생겼다. 각 checking ... 줄이 conftest 컴파일 한 번이다.

11.3 --host로 크로스 configure#

autotools의 크로스 빌드는 --host=<triplet> 하나로 시작한다. configure는 <triplet>-gcc, <triplet>-strip 등을 PATH에서 찾는다.

출력에서 볼 것: whether we are cross compiling... yes — configure는 conftest 바이너리를 실행해 보고 실패하면 크로스 빌드로 판단한다. 이후 AC_RUN_IFELSE 같은 "실행해야 아는" 검사는 기본값으로 대체되거나 에러가 난다. 그때는 캐시 변수(ac_cv_xxx=yes ./configure ...)로 답을 미리 주는데, Buildroot·Yocto 레시피에 ac_cv_ 변수가 잔뜩 있는 이유가 이것이다.

11.4 config.log로 실패 원인 찾기#

무엇을 확인하나: --with-zlib을 요청했지만 armhf용 zlib가 없을 때 configure의 에러 메시지와 config.log의 실제 원인.

출력에서 볼 것: 화면의 "zlib requested but not found"만으로는 원인을 모른다. config.log에는 실제로 실행한 컴파일 명령과 컴파일러의 에러 메시지, 실패한 conftest 소스 전체가 남는다. 여기서는 armhf용 libz.so가 sysroot에 없다는 것이 명확하다(호스트 aarch64용 zlib는 설치돼 있지만 크로스 링커는 그걸 보지 않는다 — 올바른 동작이다). config.log 맨 위에는 configure를 어떤 인자로 실행했는지도 기록된다. 실무 디버그 순서는 "에러 메시지의 checking ... 문구로 config.log를 검색 → 바로 아래의 컴파일 명령과 에러 확인"이다.

12. pkg-config와 크로스 빌드 함정#

12.1 pkg-config는 무엇인가#

라이브러리를 쓰려면 -I(헤더 경로), -L(라이브러리 경로), -l(라이브러리 이름), 때로는 -D나 의존 라이브러리까지 알아야 한다. 라이브러리가 설치될 때 이 정보를 .pc 파일로 함께 설치하고, 사용하는 쪽은 pkg-config --cflags --libs <이름>으로 조회한다. CMake의 pkg_check_modules, Meson의 dependency(), autotools의 PKG_CHECK_MODULES가 모두 내부적으로 pkg-config를 호출한다. Ubuntu 26.04의 pkg-config는 pkgconf 구현(2.5.1)이다.

pkg-config가 .pc를 찾는 경로를 정하는 환경 변수 세 개가 크로스 빌드의 핵심이다.

환경 변수효과크로스 빌드에서
PKG_CONFIG_PATH기본 검색 경로 앞에 추가호스트 기본 경로(/usr/lib/aarch64-linux-gnu/pkgconfig 등)가 여전히 살아 있다 → 누수 위험
PKG_CONFIG_LIBDIR기본 검색 경로를 통째로 교체sysroot의 pkgconfig 디렉터리만 보게 한다
PKG_CONFIG_SYSROOT_DIR출력되는 -I·-L 경로 앞에 sysroot를 붙인다.pc의 prefix=/usr(보드 기준 경로)를 빌드 머신의 실제 경로로 바꿔 준다

12.2 예제 ex12 — 호스트 .pc가 타깃 빌드로 새는 사고와 수정#

무엇을 확인하나: 같은 libbmi를 호스트(aarch64)용으로 /tmp/B4/hostprefix에, 타깃(armhf)용으로 sysroot에 설치한다. 셸에 PKG_CONFIG_PATH가 호스트 경로로 남아 있는 개발자가 크로스 빌드를 하면 무슨 일이 생기는지, 그리고 PKG_CONFIG_LIBDIR + PKG_CONFIG_SYSROOT_DIR로 어떻게 고치는지 본다.

DESTDIR과 prefix를 나눈 것이 핵심이다. 타깃용은 prefix=/usr(보드에서의 경로)로 빌드하되 실제 파일은 DESTDIR=$S(sysroot) 아래에 놓는다 — make install DESTDIR=...의 관례와 같다.

출력에서 볼 것:

  • 누수 상태에서 pkg-config는 호스트 헤더 경로(-I/tmp/B4/hostprefix/include)와 호스트 라이브러리 경로를 타깃 컴파일러에 넘겼다. 이번에는 aarch64 ELF를 armhf 링커가 읽지 못해서 "file format not recognized"로 바로 터졌으니 운이 좋은 경우다. 더 나쁜 경우는 헤더만 새는 것이다: 호스트 헤더의 구조체 정의·매크로가 타깃 라이브러리와 다르면 빌드는 성공하고 보드에서 이상하게 동작한다.
  • PKG_CONFIG_PATH만 쓰면 호스트 기본 경로가 살아 있어서 호스트 zlib(1.3.1)가 "있다"고 답한다. configure·CMake·Meson은 이걸 믿고 zlib 기능을 켠다.
  • 수정 후에는 sysroot 안의 bmi.pc만 보이고, prefix=/usr가 PKG_CONFIG_SYSROOT_DIR 덕분에 /tmp/B4/sysroot-armhf/usr로 바뀌어 출력됐다. 호스트 zlib는 "없다"고 정직하게 답한다 — 타깃에 zlib가 필요하면 타깃용으로 빌드해서 sysroot에 넣어야 한다는 신호다.

그림 7 — 크로스 빌드에서 호스트와 타깃의 분리. 빌드 도구는 호스트에서 찾고(초록), 헤더·라이브러리·.pc는 sysroot에서만 찾는다(파랑). 빨간 점선이 이 예제에서 재현한 누수 경로이고, PKG_CONFIG_LIBDIR이 그 길을 막는다.

pkg-config 쪽 크로스 설정을 하는 또 다른 방법은 triplet 접두사 래퍼다. Meson·autotools는 크로스 빌드에서 arm-linux-gnueabihf-pkg-config가 PATH에 있으면 그것을 우선 쓰는데, 이 래퍼 안에서 위 환경 변수를 설정해 두면 개발자 셸 환경에 덜 휘둘린다(Yocto·Buildroot가 내부적으로 이런 래퍼나 환경 변수를 준비한다).

13. Buildroot · Yocto는 이것들을 어떻게 몰고 가나 (K3 · K4 미리보기)#

Buildroot와 Yocto는 "빌드 시스템의 빌드 시스템"이다. 패키지마다 위에서 본 빌드 시스템 중 하나를 고르고, 같은 툴체인·sysroot·pkg-config 설정을 주입한 뒤 configure → build → install(DESTDIR=staging/sysroot)을 반복한다. 패키지 A가 설치한 헤더와 .pc가 sysroot에 들어가면, 그다음 패키지 B가 그것을 찾는다. 위의 예제에서 손으로 한 것을 수백 번 자동으로 하는 셈이다.

패키지의 빌드 시스템Buildroot (package/<pkg>/<pkg>.mk)Yocto (<pkg>.bb 레시피)내부에서 주입하는 것

autotools$(eval $(autotools-package))inherit autotools--host, --build, --prefix=/usr, ac_cv_ 캐시 변수

Yocto로 만든 SDK(bitbake <image> -c populate_sdk)를 설치하면 environment-setup-<target> 스크립트가 생긴다. 이를 source하면 CC(이미 --sysroot=...와 CPU 플래그가 붙은), CONFIGURE_FLAGS(--host=... 포함), PKG_CONFIG_SYSROOT_DIR, PKG_CONFIG_PATH(SDK sysroot만 가리키게), OECORE_NATIVE_SYSROOT 같은 변수가 설정되고, SDK에 CMake toolchain file과 Meson cross file도 들어 있다. 앱 개발자는 그 셸에서 cmake/meson/./configure $CONFIGURE_FLAGS를 치기만 하면 된다. 정확한 변수 목록과 파일 위치는 Yocto 버전에 따라 다르므로 K4·B5에서 실제 SDK로 확인한다.

14. 커널 안에서는 무슨 일이 일어나나#

빌드 시스템은 유저 공간 도구지만, Don의 목표인 드라이버에서는 빌드 결과물이 커널과 직접 만난다. ex7에서 만든 b4_hello.ko가 빌드되고 로드되는 경로를 따라가 보자.

빌드 쪽 (Kbuild):

  1. make -C $(KDIR) M=$PWD modules → 커널 최상위 Makefile이 M을 보고 외부 모듈 모드로 들어간다.
  2. scripts/Makefile.build가 M 디렉터리의 Kbuild를 읽어 obj-m := b4_hello.o를 얻고, 커널과 똑같은 플래그(-nostdinc, -include kconfig.h, -D__KERNEL__ -DMODULE, -mgeneral-regs-only …)로 b4_hello.o를 컴파일한다.
  3. scripts/Makefile.modpost → modpost가 모듈의 미해결 심볼(printk 등)을 커널의 Module.symvers(내보낸 심볼과 CRC 목록)와 대조하고, b4_hello.mod.c를 생성한다. 여기에 MODULE_INFO(vermagic, ...), 모듈 이름, 의존 모듈, 심볼 CRC(__versions 섹션)가 들어간다.
  4. b4_hello.o + b4_hello.mod.o(+ 공통 오브젝트)를 ld -r로 묶어 재배치 가능한 ELF인 b4_hello.ko를 만든다.

로드 쪽 (커널):

  1. insmod는 파일을 열어 finit_module(fd, "odr_hz=800", 0) syscall을 호출한다(구형 경로는 init_module로 메모리 버퍼를 넘긴다).
  2. 커널의 load_module()(kernel/module/main.c)이 ELF를 검사하고, .modinfo의 vermagic을 실행 중인 커널과 비교하고, CONFIG_MODVERSIONS가 켜져 있으면 __versions의 심볼 CRC를 비교한다. 다르면 disagrees about version of symbol 또는 version magic ... should be ...를 dmesg에 남기고 거부한다. 서명 검증(CONFIG_MODULE_SIG)도 여기서 한다.
  3. 섹션을 커널 메모리에 배치하고 재배치(relocation)를 적용한다 — B3에서 본 링커 일을 커널이 런타임에 한다.
  4. 모듈 파라미터를 파싱해 odr_hz에 800을 넣고, /sys/module/b4_hello/를 만들고, module_init으로 등록된 b4_hello_init()을 호출한다.

그림 8 — out-of-tree 모듈의 빌드와 로드. 빌드 쪽에서 Kbuild가 심은 vermagic과 심볼 CRC를, 로드 쪽에서 커널의 load_module()이 실행 중인 커널과 대조한다. "모듈은 정확히 그 커널의 빌드 트리로 빌드해야 한다"는 규칙의 근거다.

드라이버를 쓸 때 이 지식이 다시 나오는 곳:

  • E2 (커널 빌드): make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- imx_v8_defconfig, menuconfig, savedefconfig, 설정 조각(fragment) 병합.
  • E3·E4 (모듈·심볼): EXPORT_SYMBOL_GPL, Module.symvers, 모듈 간 의존, modprobe와 depmod.
  • G (드라이버 모델): 실제 드라이버 디렉터리의 Kconfig/Makefile 항목 추가 — obj-$(CONFIG_...) += ... 한 줄을 넣는 것이 드라이버 업스트림 패치의 일부다.
  • K3·K4: 같은 모듈을 Buildroot kernel-module / Yocto inherit module로 이미지에 넣기.

17. 면접에서 이렇게 말한다#

Q. How does make decide what to rebuild?

A. Makefile의 규칙으로 타깃→prerequisite 의존성 그래프를 만들고, 루트에서 DFS로 내려가 잎부터 올라오며 "타깃이 없거나 prerequisite보다 mtime이 오래됐으면" 레시피를 실행한다. 그래서 Makefile에 적히지 않은 의존성(헤더, 생성 파일)은 Make가 모른다.

make builds a dependency graph from the rules and walks it depth-first. A target is rebuilt if it doesn't exist or if any prerequisite has a newer modification time. The key limitation is that make only knows the dependencies you declare, so header dependencies have to be generated by the compiler with -MMD -MP.

꼬리 질문: .PHONY는 왜 필요한가? → 파일이 아닌 타깃이 같은 이름의 파일 때문에 "up to date"가 되는 것을 막는다.

Q. I changed a header and the binary started crashing until I ran make clean. What happened?

A. 헤더 의존성이 없어서 그 헤더를 쓰는 오브젝트 일부만 다시 컴파일됐고, 구조체 레이아웃이 다른 오브젝트가 한 바이너리에 섞였다. 실제로 재현하면 stack smashing으로 죽는다. -MMD -MP로 컴파일하면서 .d 파일을 만들고 -include로 읽게 하면 해결된다. -MP는 헤더를 지웠을 때 "No rule to make target"을 막는다.

Classic missing header dependency. Only some objects were recompiled, so you ended up linking objects that disagree on a struct layout — an ABI mismatch inside one binary. The fix is to have the compiler emit dependency files with -MMD -MP and include them in the Makefile. CMake and Meson do this automatically.

Q. Why does a build pass with -j1 but fail randomly with -j8?

A. 의존성이 빠져 있는데 직렬 실행 순서가 우연히 맞아서 돌던 것이다. 대표적으로 빌드 중에 생성되는 헤더(version.h, 레지스터 맵 헤더)를 쓰는 .o가 그 헤더를 prerequisite로 갖지 않는 경우와, 재귀 make에서 디렉터리 간 의존성이 없는 경우다. 순서를 강제하지 말고 진짜 의존성을 적어야 한다.

The graph is missing an edge, and serial execution happened to run things in a working order. Typical cases are generated headers not listed as prerequisites, and recursive make where one subdirectory depends on another's output. The fix is to declare the real dependency, not to serialize the build.

Q. How do you cross-compile a CMake project for an ARM board?

A. CMakeLists.txt는 그대로 두고 toolchain file을 넘긴다. CMAKE_SYSTEM_NAME(이걸 설정하면 크로스 모드), 크로스 컴파일러, CMAKE_SYSROOT, 그리고 CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER, LIBRARY/INCLUDE/PACKAGE ONLY로 도구는 호스트에서, 라이브러리와 헤더는 sysroot에서만 찾게 한다. 빌드 후 file로 아키텍처를 확인하고 qemu-user로 간단히 실행해 본다.

You don't touch CMakeLists.txt — you pass a toolchain file. It sets CMAKE_SYSTEM_NAME, the cross compiler, CMAKE_SYSROOT, and the find-root-path modes: programs from the host, libraries, headers and packages only from the sysroot. Then I check the output with file and smoke-test it under qemu-user before deploying.

꼬리 질문: sysroot가 무엇인가? → 타깃 보드의 /처럼 생긴 디렉터리. 컴파일러는 --sysroot로 그 아래의 usr/include, usr/lib만 본다.

Q. What is pkg-config and what goes wrong with it when cross-compiling?

A. 라이브러리가 .pc 파일로 자기 cflags/libs를 알려 주는 조회 도구다. 크로스 빌드에서 PKG_CONFIG_PATH만 설정하면 호스트 기본 경로가 살아 있어서 호스트용 헤더·라이브러리가 타깃 빌드에 들어간다. PKG_CONFIG_LIBDIR로 검색 경로를 sysroot로 교체하고, PKG_CONFIG_SYSROOT_DIR로 -I/usr/include 같은 경로 앞에 sysroot를 붙인다.

pkg-config reads .pc files to give you compile and link flags for a library. When cross-compiling, PKG_CONFIG_PATH only prepends to the default search path, so host .pc files can leak into the target build. You set PKG_CONFIG_LIBDIR to replace the search path with the sysroot's pkgconfig directory, and PKG_CONFIG_SYSROOT_DIR so the returned -I and -L paths are prefixed with the sysroot.

Q. How do you build an out-of-tree kernel module?

A. Kbuild 파일에 obj-m := foo.o를 쓰고, make -C <커널 빌드 트리> M=$PWD modules로 커널의 빌드 시스템에 위임한다. 크로스면 ARCH와 CROSS_COMPILE을 같이 준다. 빌드 트리는 보드에서 돌고 있는 그 커널을 빌드한 트리여야 한다. 그렇지 않으면 vermagic이나 심볼 CRC 불일치로 로드가 거부된다.

A Kbuild file with obj-m, and then make -C pointing at the kernel build directory with M set to the module source. For a board you add ARCH and CROSS_COMPILE. The build tree has to match the running kernel's config and Module.symvers, otherwise the loader rejects it on vermagic or symbol CRC mismatch.

꼬리 질문: CONFIG_FOO=m이면 C 코드에서 #ifdef CONFIG_FOO가 참인가? → 아니다. CONFIG_FOO_MODULE이 정의된다. 그래서 IS_ENABLED(CONFIG_FOO)를 쓴다.

Q. Make vs CMake vs Meson — when would you use which?

A. Make는 실행기다. 작은 펌웨어·데몬이나 커널처럼 이미 Make 기반인 곳에서 쓴다. CMake와 Meson은 컴파일러·라이브러리 검사와 크로스 설정을 표준화한 메타 빌드 시스템이고, 헤더 의존성·out-of-tree 빌드·Ninja 생성을 기본으로 해 준다. 실무에서는 업스트림 프로젝트가 쓰는 것을 따르고, 새 C/C++ 앱이면 생태계가 넓은 CMake, systemd·GStreamer 계열과 붙는다면 Meson을 고른다.

Make is the executor; CMake and Meson are generators that standardize toolchain detection, dependency discovery and cross-compilation, and emit Ninja files with header dependency tracking built in. In practice you follow whatever upstream uses. For a new C or C++ application I'd default to CMake for ecosystem reasons, or Meson if it sits next to systemd or GStreamer-style projects.

18. 직접 해보기#

  1. 개념: =와 :=의 차이를 $(shell date +%s%N)를 이용해 보여 주는 Makefile을 쓰고, 한 레시피에서 두 변수를 세 번씩 찍어 보라. 정답/힌트: =는 참조할 때마다 date를 다시 실행해 값이 매번 달라지고, :=는 한 번만 실행돼 같은 값이 나온다. 그래서 무거운 $(shell ...)은 :=로 받는다.
  2. 코드 과제: ex4의 Makefile.good에서 -include를 include(대시 없음)로 바꾸고 make clean && make를 해 보라. 무슨 일이 생기고 왜 그런가? 정답/힌트: 첫 빌드에서 .d가 없으니 GNU Make는 그 파일을 만들 규칙을 찾다가 Makefile.inc:8: main.d: No such file or directory / No rule to make target 'main.d'. Stop.으로 멈춘다(VM에서 확인). -include는 없는 파일을 조용히 넘긴다.
  3. 관찰: §5의 200 모듈 프로젝트에서 make --trace -j4로 mod_017.h를 touch한 뒤 빌드하고, 재컴파일 이유가 찍힌 두 줄을 찾아라. 정답/힌트: update target 'obj/mod_017.o' due to: src/mod_017.h와 obj/main.o에 대한 같은 줄이 나온다.
  4. 코드 과제: ex9의 CMake 프로젝트를 RISC-V(riscv64-linux-gnu-gcc)용 toolchain file로 빌드하고 qemu-riscv64 -L /usr/riscv64-linux-gnu로 실행하라. sysroot는 §9.3처럼 심볼릭 링크로 만든다. 정답/힌트: CMAKE_SYSTEM_PROCESSOR riscv64, sysroot 링크는 arm-linux-gnueabihf를 riscv64-linux-gnu로 바꾸면 된다. file에 UCB RISC-V가 보여야 한다.
  5. Kconfig 과제: ex8의 Kconfig에서 IMU_BMI270의 select REGMAP_I2C를 depends on REGMAP_I2C로 바꾸고 --alldefconfig를 돌려라. IMU 드라이버는 어떻게 되는가? 정답/힌트: REGMAP_I2C는 프롬프트가 없고 기본값도 없어 n이므로 IMU 드라이버도 켤 수 없게 되어 .config에서 사라진다. "숨은 라이브러리 심볼은 select, 사용자가 고르는 기능은 depends on"이 관례인 이유다.
  6. autotools 관찰: ex11에서 ./configure --host=arm-linux-gnueabihf CC=gcc처럼 일부러 컴파일러를 호스트 것으로 덮어쓰고 configure를 돌려 보라. whether we are cross compiling 결과와 file gnssd의 결과를 보고, 왜 위험한지 설명하라. 정답/힌트: CC가 이기므로 호스트 바이너리가 만들어진다. configure 출력의 컴파일러 이름과 config.log의 명령줄을 확인하는 습관이 필요하다.
  7. pkg-config 과제: §12 상태에서 PKG_CONFIG_SYSROOT_DIR만 빼고 pkg-config --cflags --libs bmi를 실행하면 어떤 출력이 나오며 빌드는 되는가? 그리고 bmi.pc의 prefix를 /opt/sensor로 바꾸면 어떻게 달라지는가? 정답/힌트: pkgconf는 /usr/include, /usr/lib 같은 "시스템 디렉터리" 플래그를 기본으로 걸러 내므로 출력은 -lbmi뿐이고(VM에서 확인), --sysroot 덕분에 gcc가 sysroot의 usr/include/bmi.h를 찾아 빌드는 된다. 하지만 prefix가 /opt/sensor면 -I/opt/sensor/include처럼 빌드 머신에 없는(또는 엉뚱한) 경로가 그대로 나와 실패한다. 벤더 라이브러리는 대개 /opt 같은 비표준 prefix를 쓰므로 PKG_CONFIG_SYSROOT_DIR은 생략하지 않는다.

20. 요약 & 체크리스트#

Make는 의존성 그래프와 mtime으로 "다시 만들 것"을 고르는 실행기이고, 그래프에 빠진 간선(헤더, 생성 파일, 디렉터리 간 의존)이 빌드 버그의 대부분을 만든다 — -MMD -MP와 정확한 prerequisite가 처방이다. 커널은 Make 위에 Kbuild(obj-y/obj-m)와 Kconfig(.config → auto.conf/autoconf.h)를 얹었고, out-of-tree 모듈은 make -C KDIR M=$PWD로 그 시스템을 빌려 쓴다. CMake·Meson·autotools는 모두 "설정 → 생성 → 빌드" 구조의 메타 빌드 시스템이고, 크로스 정보는 설정 단계에 toolchain file·cross file·--host로 한 번만 넣는다. 크로스 빌드의 핵심은 호스트와 타깃의 분리이며, sysroot와 PKG_CONFIG_LIBDIR·PKG_CONFIG_SYSROOT_DIR이 그 경계를 지킨다. 이 노트의 측정에서 200 모듈 빌드는 -j4로 2.5배 빨라졌고, 헤더 의존성 추적 비용은 무변경 빌드 기준 약 30 ms였다 — 정확성을 버릴 이유가 없다.
