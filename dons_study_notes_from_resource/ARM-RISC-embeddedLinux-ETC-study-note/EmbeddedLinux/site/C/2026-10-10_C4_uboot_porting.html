0. 큰 그림 — "포팅"이란 무엇을 하는 일인가#

Don이 SSD 컨트롤러의 새 리비전을 bring-up하던 장면을 떠올려 보자. 코어(Cortex-R)와 대부분의 펌웨어는 그대로다. 바뀌는 것은 보드·칩마다 다른 부분 — 클럭 트리 설정값, DRAM 타이밍 테이블, 핀 배치, 어느 UART로 로그를 낼지, NAND 채널 수 — 이고, 이것들은 보통 "보드 설정 헤더 + 초기화 함수 몇 개 + 타이밍 테이블"에 모여 있었다.

U-Boot 포팅도 정확히 같다. U-Boot는 수천 개 보드를 하나의 소스 트리로 지원한다(이 트리에만 defconfig가 1537개다). 그래서 코드가 공통 코드(명령, 환경 변수, 파일시스템, 네트워크, 부팅 로직, CPU 아키텍처 코드)와 보드별 데이터·훅(defconfig, Device Tree, board/<vendor>/<board>/ 안의 C 파일, 기본 환경 변수 파일)으로 깔끔하게 나뉘어 있다. 포팅 = 보드별 부분을 새로 만드는 일이고, 대개 가장 비슷한 기존 보드(보통 칩 벤더의 EVK)를 복사해서 시작한다.

그림 1 — U-Boot 소스 트리의 층. 초록은 보드 포트마다 새로 만드는 파일, 주황은 칩이나 주변장치가 새로울 때만, 회색은 모든 보드가 공유하는 공통 코드다.

새 보드 bring-up에서 U-Boot 포팅이 차지하는 위치는 이렇다.

  • SoC는 지원되고 보드만 새것 (가장 흔한 경우: i.MX8MP 위에 회사 자체 carrier board): EVK 디렉터리를 복사 → DDR 타이밍 교체(메모리 칩이 다르면) → DT에서 핀·PMIC·eMMC·이더넷 PHY 수정 → defconfig에서 필요 없는 것 끄기 → 환경 변수 위치와 bootcmd 정하기.
  • SoC도 새것 (실리콘 벤더 쪽 일): arch/arm/mach-<soc>/에 클럭·핀먹스·SPL 부트 경로, drivers/에 DDR 컨트롤러·클럭 드라이버까지 쓴다. 대부분의 회사는 벤더 BSP U-Boot fork를 받아서 시작한다.
  • 주변장치 하나가 미지원 (예: 센서 키트 보드의 I2C GPIO expander로 이더넷 PHY 리셋을 풀어야 함): drivers/gpio/에 DM 드라이버 하나 추가.

이 노트는 실물 보드 대신 QEMU virt 머신의 qemu_arm64 보드로 손을 움직인다. 이 "보드"는 U-Boot에서 가장 작은 보드 포트라 구조가 한눈에 보인다. 그리고 실물 보드에서만 의미가 있는 SPL·DDR training은 i.MX8MP와 TI AM62 소스를 직접 읽어서 설명한다(§6).

실행 환경: Lima VM elinux(aarch64, Ubuntu 26.04, uname -r = 7.0.0-38-generic, gcc 15.2.0, GNU ld 2.46, QEMU 10.2.1). U-Boot 소스는 공용 랩의 v2026.10(/var/lab/src/u-boot, 읽기 전용)을 /var/tmp/C4/src로 복사해서 수정했고, 빌드 출력은 모두 O=/var/tmp/C4/...다. QEMU는 -machine virt -cpu cortex-a57 -m 512M -nographic -bios u-boot.bin으로 돌렸고, U-Boot 콘솔 조작은 expect 스크립트로 했다. 아래 출력의 빌드 시각·주소·RTC 값은 실행마다 다르다. 출력에서 터미널 제어 문자(ESC 시퀀스)는 sed로 지웠다.

1.3 defconfig 한 줄이 보드 디렉터리를 고르는 사슬#

make qemu_arm64_defconfig가 어떻게 board/emulation/qemu-arm/을 찾아가는지 따라가 보자. 핵심은 Kconfig 심볼 네 개 SYS_ARCH·SYS_CPU·SYS_VENDOR·SYS_BOARD다. 최상위 Makefile이 이 값으로 board/$(VENDOR)/$(BOARD)/와 arch/$(ARCH)/cpu/$(CPU)/를 빌드 대상에 넣는다.

무엇을 확인하나: defconfig의 CONFIG_ARCH_QEMU=y에서 출발해 보드 디렉터리 이름이 정해지는 과정.

출력에서 볼 것: defconfig에는 CONFIG_ARCH_QEMU=y만 있고(§2 참고), TARGET_QEMU_ARM_64BIT는 choice의 기본값으로, SYS_BOARD="qemu-arm"은 그 아래 if 블록의 default로 정해진다. SYS_CONFIG_NAME은 include/configs/qemu-arm.h를 고른다. 새 보드를 추가할 때 만드는 사슬도 똑같다: arch/arm/mach-<soc>/Kconfig에 config TARGET_MYBOARD 항목을 추가하고, board/<vendor>/<board>/Kconfig에서 SYS_BOARD/SYS_VENDOR/SYS_CONFIG_NAME 기본값을 주고, defconfig에 CONFIG_TARGET_MYBOARD=y를 쓴다.

include/configs/qemu-arm.h는 이제 거의 비어 있다.

예전 U-Boot는 보드 설정을 전부 이 헤더의 #define CONFIG_...로 했다. 지금은 거의 모두 Kconfig로 옮겨졌고, 남은 것은 CFG_ 접두어로 이름이 바뀌었다. 옛 BSP(2018년 이전 벤더 fork)를 다루면 이 헤더가 수백 줄인 것을 보게 된다 — 그게 "Kconfig 이전 시대"의 흔적이다.

2. Kconfig와 defconfig — Linux와 같은 언어, 같은 흐름#

2.1 직관#

Kconfig는 "이 빌드에 무엇을 넣을지"를 정하는 설정 언어 + 도구다. U-Boot는 Linux 커널의 Kconfig를 그대로 가져왔다(scripts/kconfig/가 커널 것과 같은 계열). 그래서 여기서 배우는 것은 E2(커널 설정·빌드)에 그대로 쓰인다.

  • Kconfig 파일: 심볼 정의. config CMD_DATE / bool "date" / default y if DM_RTC / select LIB_DATE / depends on ... / imply ....
  • defconfig: 보드가 기본값과 다르게 고른 심볼만 적은 최소 목록.
  • .config: 모든 심볼의 최종 값(이 빌드에서 1879줄). 사람이 직접 고치기보다 도구가 만든다.
  • include/generated/autoconf.h: C 코드가 쓰는 #define CONFIG_X 1.
  • include/config/auto.conf: Makefile이 쓰는 CONFIG_X=y. obj-$(CONFIG_X) += x.o가 이것으로 obj-y 또는 obj-가 된다.

그림 2 — Kconfig 흐름. defconfig와 fragment가 Kconfig 트리의 규칙(depends on, select, default)을 거쳐 .config가 되고, 거기서 C용 헤더와 make용 파일이 생성된다. savedefconfig는 반대 방향으로 최소본을 뽑는다.

select와 imply의 차이는 면접 단골이다. ARCH_QEMU는 DM과 OF_CONTROL 없이는 아예 동작이 불가능하니 select, RTC 드라이버는 있으면 좋지만 빼도 되니 imply다. 아래 §2.4에서 imply가 실제로 어떤 흔적을 남기는지 본다.

U-Boot만의 추가 규칙이 하나 있다. 같은 소스가 U-Boot proper, SPL, TPL 세 번 빌드되므로 심볼도 단계별로 따로 있다: CONFIG_MISC(proper), CONFIG_SPL_MISC, CONFIG_TPL_MISC. C 코드에서는 CONFIG_IS_ENABLED(MISC)가 "지금 빌드 중인 단계의 MISC"를 뜻한다. Makefile에서도 obj-$(CONFIG_$(PHASE_)MISC) 같은 패턴이 보인다. 그냥 IS_ENABLED(CONFIG_MISC)를 쓰면 SPL 빌드에서도 proper의 값을 보게 되는 버그가 생긴다.

2.3 실습 — defconfig fragment로 기본값 바꾸기#

보드 기본값을 바꾸는 방법은 세 가지다. (1) configs/<board>_defconfig를 직접 고친다 — 자기 보드라면 정답. (2) make menuconfig 후 savedefconfig — 탐색할 때. (3) fragment — 같은 보드의 변형(디버그 빌드, 생산 빌드, 고객별 빌드)을 만들 때. 여기서는 (3)으로 QEMU 보드를 바꾼다.

U-Boot의 scripts/kconfig/Makefile은 make <이름>.config를 받으면 kernel/configs/, arch/$(SRCARCH)/configs/, 그리고 board/ 아래 전체에서 같은 이름의 파일을 찾아 merge_config.sh로 합친다.

그래서 fragment를 board/emulation/qemu-arm/c4.config에 둔다(복사한 트리 안). 내용은 이렇다.

CMD_C4HELLO와 C4_WIDGET은 §4·§7에서 직접 추가하는 심볼이다. ENV_SOURCE_FILE="c4"는 기본 환경 변수 파일을 board/emulation/qemu-arm/c4.env로 바꾼다(§3.4).

출력에서 볼 것: merge_config.sh가 바뀌는 값마다 "Previous / New"를 보여 준다. 그 뒤 oldconfig가 새로 보이게 된 심볼(MISC를 켜자 나타난 misc 드라이버 14개, (NEW))에 yes ""로 기본값을 답한다. 결과 확인은 이렇게 한다.

함정 (이 VM에서 실제로 겪음): 처음에 make O=... qemu_arm64_defconfig c4.config처럼 두 타깃을 한 줄에 줬더니, 병합 메시지는 다 나왔는데 최종 .config에는 BOOTDELAY=2, CMD_C4HELLO is not set 등 원래 값이 남아 있었다. 두 번의 make로 나눠 실행하니 위처럼 정상 적용됐다. config 타깃은 한 번에 하나씩 실행하고, 결과는 항상 .config를 grep해서 확인한다.

C와 Makefile이 실제로 보는 값도 확인해 두자.

2.4 savedefconfig — 바뀐 것만 남긴 defconfig 만들기#

.config는 1879줄이라 리뷰할 수 없다. 보드 defconfig로 커밋할 때는 make savedefconfig로 기본값과 다른 줄만 뽑아 configs/에 넣는다.

무엇을 확인하나: fragment 적용 후의 최소 defconfig가 원래 defconfig와 어떻게 다른지.

출력에서 볼 것이 두 가지 있다.

  • 끈 심볼(CMD_TPM, CMD_EFIDEBUG)은 # ... is not set으로 남지 않고 줄이 사라졌다. 이 심볼들의 기본값이 원래 n이기 때문이다. 원래 defconfig에서 =y로 켜던 줄이 없어지면 기본값 n으로 돌아간다.
  • 내가 건드리지 않은 CMD_BOOTEFI_HELLO=y, CMD_POWEROFF=y가 새로 생겼다. 원인을 Kconfig에서 찾아보면:

CMD_BOOTEFI_HELLO의 기본값은 CMD_BOOTEFI_SELFTEST를 따라가고, CMD_POWEROFF는 EFI selftest가 imply로 켜 주던 것이다. selftest를 끄면 둘의 기본값이 n으로 바뀌는데, oldconfig는 이미 y였던 값을 유지했다. 그래서 savedefconfig가 "기본값(n)과 다르다"며 명시적으로 =y를 적었다. 이것이 imply/default의 흔적이다. 실무 교훈: defconfig diff 리뷰에서 "건드리지 않은 줄"이 나타나면 Kconfig 의존성 변화 때문이니, 그 줄이 의도한 것인지(여기서는 QEMU를 끄는 poweroff 명령이 필요하니 의도대로다) 확인하고 커밋한다.

3.2 init 시퀀스 — 훅은 어디서 불리나#

U-Boot proper의 init은 두 단계다. board_init_f("f" = flash에서 도는 단계, relocation 전)와 board_init_r("r" = RAM으로 relocation한 뒤). 이 버전(v2026.10)은 common/board_f.c·board_r.c에서 함수 배열 대신 INITCALL() 매크로를 줄줄이 부른다. 보드 훅이 어디 끼는지 실제 소스에서 뽑아 보자.

무엇을 확인하나: pre-reloc 단계에서 불리는 초기화 함수의 순서.

출력에서 볼 것: fdtdec_setup(control DT 찾기) → initf_dm(pre-reloc DM: bootph-* 노드만 bind) → serial_init(콘솔) → dram_init(RAM 크기) → setup_dest_addr 이하 reserve_*들(relocation 목적지 계산, §8). 순서가 곧 의존성이다: DT 없이는 DM이 없고, DM 없이는 시리얼이 없고, 시리얼 없이는 아무 것도 못 찍는다. 그래서 bring-up 초기에 화면이 깜깜하면 이 앞부분을 의심한다(§11.2의 DEBUG_UART).

post-reloc 쪽은 이렇다(같은 방식으로 common/board_r.c에서 발췌, 줄 번호는 함수 안 순번).

(사이사이의 #if 조건부 INITCALL은 생략했다.)

4. 실습 1 — 사용자 명령 c4hello 추가 (U_BOOT_CMD)#

4.1 무엇을 만드나#

bring-up 때 가장 먼저 만드는 도구가 "레지스터 하나 읽어 보는 명령"이다. U-Boot에는 md(memory display)가 있지만, DT에서 주소를 찾아 읽는 명령을 만들면 U-Boot가 DT·레지스터·relocation을 어떻게 다루는지 한 번에 보인다. c4hello는:

  1. DT 루트의 compatible 속성을 읽고,
  2. 인자로 받은 compatible(기본 arm,pl011)을 가진 노드를 찾아 reg 주소를 얻고,
  3. 그 주소의 AMBA PrimeCell ID 레지스터(base + 0xFE0..0xFEC) 4개를 읽어 부품 번호를 해독하고,
  4. 시스템 레지스터 MIDR_EL1(CPU 종류)을 읽고,
  5. relocation 정보를 출력한다.

4.2 코드#

cmd/c4hello.c (복사한 트리에 추가):

U_BOOT_CMD(이름, 최대 인자 수, 반복 가능 여부, 함수, 짧은 도움말, 긴 도움말)이다. 반복 가능(_rep=1)이면 프롬프트에서 Enter만 눌러도 다시 실행된다(md가 그렇다). gd는 global data 포인터로, AArch64에서는 레지스터 x18에 고정되어 있다(DECLARE_GLOBAL_DATA_PTR). relocation 전에는 BSS·전역 변수를 못 쓰므로 U-Boot는 모든 단계에서 살아남아야 하는 상태를 이 구조체에 모은다.

Kconfig와 Makefile에 한 항목씩 추가한다(복사한 트리 기준 diff).

4.4 QEMU에서 실행#

expect 스크립트(run.exp)는 QEMU를 띄우고, autoboot 카운트다운에서 키를 눌러 멈춘 뒤, 인자로 받은 명령들을 차례로 치고 poweroff한다.

무엇을 확인하나: c4hello가 DT에서 UART·RTC 주소를 찾고, 실제 레지스터 값을 읽는지.

(c4_virt.dtb는 §7.4에서 만드는 DT다. 이 명령에는 원래 DT로도 충분하다. 이 한 번의 실행 출력을 §4.4, §5, §7.5에서 나눠 보여 준다. 여기서는 c4hello 부분만.)

출력에서 볼 것:

  • PeriphID: 0x00141011의 하위 12비트 0x011은 PL011, 0x00141031은 PL031(RTC)이다. 비트 [19:12] 0x41은 설계사 Arm('A'), [23:20]은 리비전이다. QEMU가 실제 PrimeCell 레지스터를 흉내 내고 있다는 증거다. 실물 보드 bring-up에서 "이 주소에 정말 그 IP가 있나"를 ID 레지스터로 확인하는 것과 같다.
  • MIDR_EL1 0x411fd070: implementer 0x41(Arm), part 0xd07 = Cortex-A57(QEMU -cpu cortex-a57), variant 1 → r1p0.
  • link addr 0x2a70c vs 실행 주소 0x5f4ea70c: 함수는 0x2a70c에 링크됐지만(TEXT_BASE=0), 지금은 0x5f4c0000만큼 올라간 DRAM에서 돌고 있다. relocation의 직접 증거다(§8).

4.5 명령은 어떻게 "등록"되나 — linker list#

U-Boot에는 명령 등록 함수가 없다. U_BOOT_CMD는 struct cmd_tbl 하나를 __u_boot_list_2_cmd_2_<이름>이라는 특별한 섹션에 놓을 뿐이고, 링커 스크립트가 이 섹션들을 이름순으로 정렬해 하나의 배열로 이어 붙인다. 명령 파서는 그 배열을 처음부터 끝까지 훑는다. 드라이버(U_BOOT_DRIVER)도 똑같은 방식이다.

6. SPL·TPL과 DDR 초기화 — QEMU에 없는 단계#

6.1 왜 U-Boot가 여러 번 나뉘나#

전원이 들어온 순간 SoC가 쓸 수 있는 메모리는 칩 안의 작은 SRAM(i.MX8MP OCRAM, TI AM62 MSRAM 등, 수백 KB 수준)뿐이다. DRAM은 컨트롤러와 PHY를 설정하고 training(신호 타이밍 보정)을 끝내야 쓸 수 있다. 그런데 U-Boot proper는 1 MB가 넘는다. 그래서:

  • SPL(Secondary Program Loader): 같은 U-Boot 소스를 최소 기능으로 다시 빌드한 작은 바이너리. BootROM이 SRAM에 올려 실행한다. 할 일은 클럭·PMIC·콘솔 → DDR 초기화 → 다음 단계(TF-A, U-Boot proper)를 부트 미디어에서 DRAM으로 로드.
  • TPL(Tertiary PL): SRAM이 SPL조차 못 담을 만큼 작을 때 그 앞에 하나 더 (일부 Rockchip 등).
  • VPL(Verifying PL): 어느 이미지를 부팅할지 검증·선택하는 단계(VBE).

빌드 결과물도 나뉜다: spl/u-boot-spl.bin, tpl/u-boot-tpl.bin, u-boot.bin. 같은 .c 파일이 단계마다 다른 CONFIG_SPL_*/CONFIG_TPL_*로 다시 컴파일된다(§2.2의 CONFIG_IS_ENABLED). Don에게 익숙한 말로 하면, SSD 컨트롤러의 ROM 부트로더 → SRAM 로더(DRAM init) → DRAM에서 도는 메인 펌웨어와 똑같은 3단 구조다.

그림 4 — 실물 SoC는 "ROM → SRAM의 SPL → DDR training → DRAM의 U-Boot" 순서를 거친다. QEMU는 DRAM이 처음부터 있으므로 빨간 단계가 통째로 없다.

6.2 i.MX8MP — SPL의 board_init_f와 DDR 타이밍 테이블#

i.MX8MP EVK의 SPL 진입점(board/nxp/imx8mp_evk/spl.c 발췌, 공용 랩 소스에서 읽음):

SPL에서는 보드가 board_init_f를 직접 구현한다(U-Boot proper의 board_init_f는 공통 코드였던 것과 대비). 주석 "Do not use BSS area in this phase"가 핵심이다 — DRAM이 아직 없으니 BSS를 SRAM에 두지 않은 이상 전역 변수를 쓸 수 없다. spl_dram_init()은 ddr_init(&dram_timing)을 부르고, dram_timing이 2048줄짜리 lpddr4_timing.c에 있다.

{레지스터 주소, 값} 쌍이 1884개다(grep -c "{ 0x"로 셌다). 이 파일은 사람이 쓰지 않는다. NXP의 DDR Tool(구 RPA 엑셀 + config tool)에 메모리 칩 데이터시트 값과 보드 배선을 넣고 stress test를 돌려 생성한다. 그래서 carrier board에서 LPDDR4 칩 용량이나 벤더를 바꾸면 이 파일을 새로 생성하는 것이 포팅의 첫 번째 일이다.

그리고 DDR PHY training에는 벤더 바이너리 펌웨어가 필요하다. PHY 안의 작은 마이크로컨트롤러가 돌리는 코드다. U-Boot는 이것을 binman 이미지 조립 단계에서 SPL 뒤에 붙인다(arch/arm/dts/imx8mp-u-boot.dtsi 발췌).

blob-ext는 "U-Boot 트리 밖에서 가져오는 바이너리"라는 뜻이다. NXP firmware-imx 패키지(라이선스 동의 후 배포)에서 받아 빌드 디렉터리에 넣어야 한다. 실제로 빌드해 보면 binman이 이 파일들을 요구하는 것을 확인할 수 있다.

무엇을 확인하나: i.MX8MP EVK용 U-Boot(SPL 포함)를 빌드하면 binman이 어떤 외부 blob을 요구하는지, SPL이 얼마나 작은지. 이 VM은 arm64라 CROSS_COMPILE 없이 네이티브 gcc로 빌드된다. blob이 없으면 binman이 에러를 내므로 BINMAN_ALLOW_MISSING=1로 "가짜 blob을 넣고 계속"하게 했다(결과 이미지는 동작하지 않는다).

출력에서 볼 것: 최종 flash.bin에 들어가야 하는 외부 조각이 정확히 보인다 — DDR training firmware 4개(1D/2D training × 명령 메모리 imem / 데이터 메모리 dmem), TF-A bl31.bin(필수), OP-TEE tee.bin(선택). 실물 보드용 빌드에서는 NXP firmware 패키지의 .bin 4개와 직접 빌드한 TF-A를 빌드 디렉터리에 두거나 BL31=로 지정한다. 이 메시지 목록이 곧 "i.MX8MP 부팅 이미지의 부품 목록"이다.

산출물 크기와 SPL 메모리 배치도 보자.

출력에서 볼 것:

  • SPL은 122240바이트로 SPL_MAX_SIZE(0x26000 = 155648) 안에 들어가야 한다. OCRAM 0x920000에서 실행되고, 스택(0x960000)과 BSS(0x98fc00)도 전부 OCRAM 안이다. U-Boot proper(1 MB, 링크 주소 0x40200000 = DRAM)와 비교하면 SPL이 왜 따로 있어야 하는지 숫자로 보인다.
  • SPL용 DT는 8712바이트, proper용은 67880바이트다. 빌드 때 fdtgrep이 bootph-* 태그가 없는 노드를 지웠다(§8.4). 루트에 남은 것은 클럭 소스, soc@0, SD 전원 레귤레이터, 와치독 리셋이다. dtc -I dtb -O dts spl/u-boot-spl.dtb로 soc@0 아래를 펼쳐 보면 GPIO, 와치독, 핀먹스(그룹은 i2c1grp·pmicgrp·uart2grp·usdhc2grp·usdhc3grp 등 태그 붙은 것만), 클럭 컨트롤러, UART2(serial@30890000), CAAM 암호 엔진, I2C(PMIC pmic@25 포함), MMC 컨트롤러만 남아 있다 — SPL이 PMIC로 전압을 맞추고 DDR을 켠 뒤 SD/eMMC에서 다음 이미지를 읽는 데 필요한 것들이다.

6.3 TI AM62 — 또 다른 방식#

TI K3 계열(AM62, AM64, J721E)은 구조가 다르다.

  • 부팅은 Cortex-R5 코어가 먼저 시작한다. 같은 U-Boot 소스를 R5용(32-bit ARM)으로 한 번, A53용(64-bit)으로 한 번 빌드한다(am62x_evm_r5_defconfig, am62x_evm_a53_defconfig).
  • R5 SPL이 담긴 tiboot3.bin에 TIFS 펌웨어(TI Foundational Security, 흔히 "sysfw"라 부름 — 보안·전원·클럭·리소스 관리를 맡는 별도 코어의 펌웨어)와 보드 설정 데이터가 함께 들어간다. arch/arm/dts/k3-am625-sk-binman.dtsi의 ti-fs-enc.bin, tifs-rm-cfg.yaml 같은 항목이 그것이다.
  • DDR 초기화는 R5 SPL 안의 k3-ddrss DM 드라이버가 하고, 타이밍 값은 C 테이블이 아니라 DT(k3-am62x-sk-ddr4-1600MTs.dtsi)에 있다. TI의 SysConfig DDR 툴이 이 .dtsi를 생성한다.

즉 "DDR 타이밍을 툴로 생성해 넣는다"는 본질은 같고, 그릇이 C 배열이냐 DT냐가 다르다.

6.4 QEMU에는 왜 DDR init이 없나#

QEMU virt의 "DRAM"은 호스트 프로세스의 메모리(-m 512M)일 뿐이라 컨트롤러도 training도 없다. 리셋 순간부터 0x4000_0000에 RAM이 있다. 그래서 qemu-arm 보드의 dram_init()은 QEMU가 만든 DT의 memory 노드에서 크기만 읽는다(fdtdec_setup_mem_size_base()). 실물 보드라면 같은 자리에서 "SPL이 이미 초기화한 DRAM의 크기"를 DT 또는 고정값, 또는 DDR 컨트롤러 레지스터로 알아낸다. QEMU로 배울 수 있는 것은 "DDR 이후"의 모든 것이고, DDR 단계는 위처럼 소스를 읽어 이해해야 한다.

7. Driver Model (DM) — U-Boot의 드라이버 프레임워크#

7.1 세 객체#

DM은 2014년쯤부터 U-Boot에 들어온 드라이버 프레임워크로, 지금은 사실상 모든 새 드라이버가 DM이다. 객체는 셋이다.

  • driver (struct driver): 코드. U_BOOT_DRIVER(name)으로 linker list에 등록된다. of_match(compatible 표), bind, of_to_plat, probe, remove, ops, 그리고 priv_auto(장치마다 자동 할당할 private 구조체 크기)를 가진다.
  • uclass (struct uclass + struct uclass_driver): 같은 종류 장치들의 공통 API. UCLASS_SERIAL, UCLASS_MMC, UCLASS_I2C, UCLASS_GPIO, UCLASS_MISC … 상위 코드는 uclass API(misc_read(), dm_i2c_read())만 부르고, uclass가 driver의 ops로 넘긴다.
  • udevice (struct udevice): 인스턴스. 보통 DT 노드 하나 = udevice 하나. driver·uclass·부모·private 데이터 포인터를 가진다.

이건 Linux의 driver model(G2/G3)과 거의 1:1이다.

그림 5 — U-Boot DM과 Linux driver model의 대응. 구조는 거의 같고, 가장 큰 차이는 맨 아래 "언제 probe하나"다.

7.2 bind와 probe — 두 단계로 나눈 이유#

  • bind: "이 DT 노드에 이 드라이버를 짝지어 udevice를 만든다". udevice 구조체 하나를 malloc할 뿐 하드웨어 접근은 없다. 부팅 때 DT 전체를 스캔해 한꺼번에 한다(initr_dm → dm_init_and_scan → dm_extended_scan).
  • probe: "하드웨어를 실제로 깨운다". 클럭 켜기, 리셋 풀기, 레지스터 초기화. 누가 그 장치를 처음 쓸 때 한다(uclass_get_device*() 계열이 내부에서 device_probe()를 부름).

부트로더는 빨리 끝나야 하고, 부팅에 쓰지 않는 장치(HDMI, 카메라 등)는 아예 건드릴 필요가 없다. 그래서 U-Boot는 bind만 다 해 두고 probe는 미룬다. Linux는 반대로 match되면 바로 probe하고, 아직 준비되지 않은 의존성(클럭·레귤레이터)이 있으면 -EPROBE_DEFER로 나중에 재시도한다.

device_probe()(drivers/core/device.c)의 실제 순서는 이렇다(소스에서 순서만 뽑음).

  1. device_of_to_plat(dev) — DT 속성을 읽어 plat/priv에 채움 (드라이버의 of_to_plat)
  2. device_probe(dev->parent) — 부모 먼저 probe (I2C 장치면 I2C 컨트롤러가 먼저)
  3. power domain 켜기, pinctrl_select_state(dev, "default") — DT의 pinctrl-0 적용
  4. uclass_pre_probe_device(), 부모의 child_pre_probe
  5. clk_set_defaults() — DT의 assigned-clocks/assigned-clock-rates 적용
  6. 드라이버의 probe()
  7. uclass_post_probe_device()

2·3·5는 Linux의 really_probe()가 하는 일(pinctrl default 상태 적용, 부모 우선)과 같다. 드라이버가 직접 하지 않아도 프레임워크가 DT를 보고 해 준다는 점이 핵심이다.

7.4 DT 노드 추가 — qemu_arm64의 control DT는 QEMU가 만든다#

드라이버를 붙이려면 DT 노드가 있어야 한다. 그런데 qemu_arm64는 특이하다: .config에 CONFIG_OF_BOARD=y, CONFIG_OF_OMIT_DTB=y가 켜져 있다. U-Boot가 쓰는 DT(control DT)를 빌드 때 만들지 않고, QEMU가 런타임에 생성해 RAM 시작(0x4000_0000)에 놓은 DT를 쓴다(§1.2의 board_fdt_blob_setup). 그래서 노드를 추가하려면 QEMU에 -dtb로 수정한 DT를 넘긴다. 공용 랩의 virt.dts(QEMU가 만든 DT를 덤프한 것)에 노드 두 개를 붙였다.

7.8 U-Boot 전용 DT 조각 — <board>-u-boot.dtsi#

실물 보드의 control DT는 Linux와 같은 .dts 를 쓰는 것이 원칙이다(요즘은 dts/upstream/에 Linux DT를 미러링하고 CONFIG_OF_UPSTREAM으로 그걸 쓴다. i.MX8MP EVK의 defconfig가 CONFIG_DEFAULT_DEVICE_TREE="freescale/imx8mp-evk"인 것이 그 형태다). U-Boot만 필요한 속성(bootph-*, binman 이미지 레이아웃, U-Boot 전용 노드)은 Linux DT를 더럽히지 않도록 arch/arm/dts/<board>-u-boot.dtsi 에 따로 두고, 빌드 시스템이 자동으로 #include한다.

qemu_arm64는 런타임 DT를 쓰지만, 빌드 시스템은 여전히 qemu-arm64.dts를 컴파일하므로 이 자동 include 동작을 확인할 수 있다. 복사한 트리에 arch/arm/dts/qemu-arm64-u-boot.dtsi를 만들었다.

무엇을 확인하나: 이 파일을 어디서도 include하지 않았는데 빌드된 dtb에 노드가 들어갔는지, 그리고 그 메커니즘.

출력에서 볼 것: 기본 빌드(base)의 dtb에는 smbios만, C4 빌드에는 c4-build-marker가 추가됐다. 빌드 명령(.cmd 파일)을 보면 Kbuild가 .dts를 임시 파일로 복사하고 끝에 #include "qemu-arm64-u-boot.dtsi"를 덧붙인 뒤 cpp → dtc를 돌린다. 어떤 파일을 찾는지는 scripts/Makefile.lib의 u_boot_dtsi_options에 있다: <dts이름>-u-boot.dtsi, <SYS_SOC>-u-boot.dtsi, <SYS_CPU>-u-boot.dtsi, <SYS_VENDOR>-u-boot.dtsi, u-boot.dtsi 순서로 후보를 보고 처음 존재하는 것을 쓴다. 다만 qemu_arm64에서는 OF_OMIT_DTB 때문에 이 dtb가 u-boot.bin에 붙지 않는다 — u-boot.bin과 u-boot-nodtb.bin이 1204392바이트로 같다. 실물 보드(OF_SEPARATE)라면 u-boot.bin = u-boot-nodtb.bin + u-boot.dtb가 된다.

8. Pre-relocation과 relocation#

8.1 직관 — 부트로더가 자기를 옮기는 이유#

Don의 SSD 부트 코드는 ROM이나 SPI flash에서 시작해 자기 자신(또는 다음 단계)을 SRAM/DRAM으로 복사한 뒤 거기로 점프했다. U-Boot도 같다.

  1. 처음엔 링크된 주소(CONFIG_TEXT_BASE) 에서 돈다. qemu_arm64는 TEXT_BASE=0 — 즉 flash(0x0)에서 바로 실행(XIP)한다. 실물 보드에서는 SPL이 DRAM의 어떤 고정 주소(i.MX8MP: 0x40200000)에 올려 준 곳이다.
  2. board_init_f가 DRAM 크기를 알아낸 뒤, DRAM 꼭대기부터 아래로 필요한 영역(MMU 테이블, 프레임버퍼, U-Boot 자신, malloc, global data, DT 복사본, 스택)을 예약한다(reserve_* INITCALL들).
  3. relocate_code()가 U-Boot를 그 자리로 복사하고, 코드 안의 절대 주소들을 고친 뒤 점프한다.
  4. board_init_r부터는 새 위치에서 돈다.

왜 꼭대기로 가나? DRAM 아래쪽(0x4000_0000~)은 커널·initramfs·DT를 로드할 자리(kernel_addr_r=0x40400000, ramdisk_addr_r=0x44000000)라 비워 둬야 하고, 어느 보드든 "RAM 끝"은 런타임에 알 수 있으니 같은 바이너리가 RAM 크기가 다른 보드에서도 동작한다.

8.3 relocation은 어떻게 주소를 고치나 — PIE와 R_AARCH64_RELATIVE#

U-Boot ARM64는 position-independent로 링크된다(-pie). 대부분의 코드는 PC-상대 주소(adrp/add)로 동작하므로 옮겨도 그대로 돈다. 문제는 데이터 안에 박힌 절대 주소 — 함수 포인터 테이블(U_BOOT_CMD의 cmd, U_BOOT_DRIVER의 probe/ops), 문자열 포인터 등이다. 링커는 이런 위치를 .rela.dyn 섹션에 목록으로 남긴다.

무엇을 확인하나: 수정해야 할 위치가 몇 개이고 어떤 종류인지, ELF 섹션 배치.

출력에서 볼 것:

  • 재배치 항목이 전부 R_AARCH64_RELATIVE 3833개다(.rela.dyn의 0x165a8/0x18 = 3815개 + .efi_runtime_rel의 18개). RELATIVE 하나는 "이 위치에 (addend + 새 base)를 써라"라는 뜻이라, 심볼 테이블 없이 덧셈 하나로 처리된다.
  • .bss와 .rela.dyn이 같은 주소(0x10fb00)에서 시작한다. 복사 범위는 __image_copy_end(= 0x10fb00)까지라 .rela.dyn은 새 위치로 복사되지 않는다. 원래 자리에서 읽기만 하고 버리며, 새 위치에서는 그 자리가 BSS가 된다. 공간을 아끼는 트릭이다. u-boot.bin(1204392 = 0x1260a8바이트)이 __rel_dyn_end에서 끝나는 것도 이 때문이고, bdinfo의 flashoffset = 0x1260a8이 바로 그 값이다.

수정 루프는 arch/arm/lib/relocate_64.S에 있다(발췌).

Don에게는 익숙한 코드다: 16바이트씩 ldp/stp로 복사하고, 24바이트짜리 Elf64_Rela(offset, info, addend)를 순회하며 *(new_base + offset) = addend + new_base를 쓴다. 동적 로더(ld.so)가 공유 라이브러리를 로드할 때 하는 일(B3)의 가장 단순한 버전이다.

10. 커널 안에서는 무슨 일이 일어나나 — U-Boot DM에서 Linux driver model로#

U-Boot는 커널이 아니지만, 이 노트에서 만든 것들은 커널 드라이버를 쓸 때 거의 그대로 다시 나온다.

U-Boot가 커널에 넘겨주는 것도 정리해 두자. ARM64에서는 x0 레지스터에 DT 주소 하나만 넘긴다(커널 Documentation의 arm64 booting 규약). U-Boot는 부팅 직전 그 DT에 /chosen/bootargs(커널 명령줄), /chosen/linux,initrd-start/end, memory 노드의 실제 RAM 크기를 채운다(boot/image-fdt.c의 image_setup_libfdt() → 보드의 ft_board_setup()). 커널이 "U-Boot가 알려 준 메모리 크기가 틀렸다"며 이상하게 뜬다면 이 단계를 본다.

11. Embedded 실무에서 다시 보기#

11.1 센서 키트 carrier board — EVK에서 갈라져 나오기#

예를 들어 센서 키트가 i.MX8MP SoM 위에 자체 carrier board(IMU용 SPI, GNSS용 UART3, CAN 2개, 이더넷 PHY 1개, eMMC)를 얹었다면, U-Boot 포트는 보통 이렇게 진행한다.

  1. board/nxp/imx8mp_evk/ → board/acme/sensorkit/ 복사, Kconfig의 SYS_BOARD/SYS_VENDOR/SYS_CONFIG_NAME 변경, arch/arm/mach-imx/imx8m/Kconfig에 TARGET_IMX8MP_SENSORKIT 추가.
  2. configs/imx8mp_evk_defconfig → imx8mp_sensorkit_defconfig, CONFIG_TARGET_...과 DEFAULT_DEVICE_TREE 변경.
  3. DDR: SoM 벤더가 준 lpddr4_timing.c를 받는다(SoM을 쓰면 DDR은 SoM 벤더 몫이라 대개 그대로 쓴다).
  4. DT: Linux용 imx8mp-sensorkit.dts를 먼저 쓰고, imx8mp-sensorkit-u-boot.dtsi에 콘솔 UART·PMIC I2C·eMMC에 bootph-*.
  5. 이더넷 PHY 리셋 GPIO·PHY 주소를 DT에 반영, ping으로 확인.
  6. env를 eMMC user 영역 특정 오프셋에(ENV_IS_IN_MMC, ENV_OFFSET), A/B 업데이트를 하면 bootcmd를 RAUC/SWUpdate 규칙에 맞춘 스크립트로 (P 모듈).
  7. 생산용: BOOTDELAY=0 또는 -2(키 입력 확인 안 함), AUTOBOOT_KEYED, ENV_IS_NOWHERE나 env 쓰기 제한, 디버그 명령 제거(§9 측정처럼 크기도 준다).

11.2 "SPL이 아무 것도 안 찍어요"#

bring-up 첫날 가장 흔한 장면이다. 원인 후보는 거의 정해져 있다: (a) DDR 이전이라 콘솔 UART 핀먹스·클럭 노드에 bootph-pre-ram이 없다, (b) 다른 UART를 쓰는데 stdout-path/serial alias가 EVK 것 그대로다, (c) DDR training 실패로 SPL이 멈췄다(로그가 "DDRINFO" 근처에서 끊김). 이럴 때 쓰는 것이 이 defconfig에도 켜져 있던 CONFIG_DEBUG_UART다 — DM·DT 없이 고정 주소(DEBUG_UART_BASE)의 UART 레지스터에 직접 쓰므로, DT가 틀려도 글자가 나온다. Don이 JTAG 없이 GPIO 토글로 위치를 찾던 것과 같은 최후의 수단이다.

11.3 보드에 새 칩이 하나 있을 때#

센서 키트의 이더넷 PHY 리셋이 I2C GPIO expander(예: PCA9555 계열)에 물려 있다면, U-Boot가 그 expander를 알아야 네트워크 부팅이 된다. drivers/gpio/에 지원 드라이버가 이미 있는지 dm compat이나 소스 grep으로 찾고, 있으면 DT 노드 + CONFIG_ 하나로 끝난다. 없으면 이 노트의 c4_widget과 같은 모양으로 UCLASS_GPIO 드라이버(dm_gpio_ops)를 쓴다. 이때 부모(I2C 컨트롤러) 노드가 DT에 있고 probe 가능해야 자식이 probe된다(§7.2의 부모 우선).

11.4 벤더 fork에서 upstream으로#

벤더 BSP U-Boot(예: NXP lf_v20xx.xx 브랜치)는 upstream보다 기능이 앞서지만 보안 패치는 늦다. 장기 유지보수 제품이라면 upstream U-Boot로 옮기는 프로젝트를 하게 되고, 그때 부딪히는 것이 u-boot,dm-pre-reloc → bootph-* 이름 변경, include/configs/*.h의 매크로 → Kconfig 이전, 보드 전용 DT → OF_UPSTREAM 전환이다. 이 노트의 §2·§7.8·§8.4가 그 체크리스트다.

Q. "How would you port U-Boot to a new custom board based on an SoC that's already supported?"

A. 가장 가까운 기존 보드(보통 EVK)를 복사해서 시작한다. Kconfig에 TARGET 심볼과 board 디렉터리를 추가하고, defconfig를 만들고, Device Tree를 우리 보드의 핀·UART·eMMC·PMIC·PHY에 맞춘다. 메모리 칩이 다르면 벤더 툴로 DDR 타이밍을 다시 생성한다. 그다음 보드 C 파일의 훅(dram_init, board_late_init 등), env 저장 위치와 bootcmd를 정한다. 콘솔 → DDR → 부트 미디어 → 네트워크 → 커널 부팅 순서로 하나씩 확인한다.

I start from the closest existing board, usually the SoC vendor's EVK. I add a TARGET symbol and a board directory, create a defconfig, and adapt the device tree to our pinmux, console UART, eMMC, PMIC and Ethernet PHY, with a board-u-boot.dtsi for U-Boot-only properties like bootph tags. If the memory part differs I regenerate the DDR timing with the vendor's tool and run a memory stress test. Then I fill in the board hooks — dram_init, board_late_init, maybe ft_board_setup — pick the environment location and the boot command. I bring it up in order: console, DDR, boot media, network, then booting the kernel.

꼬리 질문: "What goes in the -u-boot.dtsi rather than the main dts?" → bootph-* 태그, binman 이미지 레이아웃, U-Boot 전용 노드. 메인 .dts는 Linux와 공유하므로 깨끗하게 둔다.

Q. "What is SPL and why does it exist?"

A. Secondary Program Loader. 리셋 직후에는 칩 내부 SRAM 수백 KB만 쓸 수 있는데 U-Boot proper는 1 MB가 넘는다. 그래서 같은 소스를 최소 기능으로 다시 빌드한 SPL을 BootROM이 SRAM에 올리고, SPL이 클럭·PMIC·콘솔을 켠 뒤 DDR을 초기화하고 training한 다음, TF-A와 U-Boot proper를 DRAM에 로드한다. SRAM이 더 작으면 그 앞에 TPL을 둔다.

SPL is a stripped-down build of U-Boot from the same source tree. At reset only a few hundred kilobytes of on-chip SRAM are usable, and full U-Boot is over a megabyte, so the boot ROM loads SPL into SRAM. SPL brings up clocks, the PMIC and a console, initialises and trains DRAM — on i.MX8M that includes loading the vendor's DDR PHY training firmware — and then loads TF-A and U-Boot proper into DRAM. If SRAM is even smaller, a TPL stage runs before SPL. Each stage has its own CONFIG_SPL_ and CONFIG_TPL_ options and its own filtered device tree.

Q. "Explain U-Boot's driver model. How does it compare to Linux's?"

A. driver, uclass, udevice 세 객체다. driver는 U_BOOT_DRIVER로 링커 리스트에 등록되고 compatible로 DT 노드에 매칭된다. uclass는 같은 종류 장치의 공통 API(예: misc_read, dm_i2c_read)를 제공하고, udevice는 DT 노드 하나의 인스턴스다. Linux의 platform_driver, subsystem/class, struct device와 거의 1:1이다. 큰 차이는 probe 시점이다: U-Boot는 부팅 때 전부 bind만 하고 probe는 처음 쓸 때 하고, Linux는 match되면 즉시 probe하며 의존성이 없으면 -EPROBE_DEFER로 재시도한다. 또 U-Boot는 인터럽트 없이 폴링, 단일 스레드다.

It has three objects: drivers, registered with U_BOOT_DRIVER into a linker list and matched to device-tree nodes by compatible; uclasses, which define the common API for a class of device like misc_read or dm_i2c_read; and udevices, one per bound node. That maps almost one-to-one onto Linux's platform_driver, subsystem or class, and struct device. The main difference is timing: U-Boot binds everything at startup but probes lazily on first use, while Linux probes as soon as a driver matches and uses -EPROBE_DEFER when a dependency isn't ready. U-Boot is also single-threaded and polled — no interrupts. In practice I check it with dm tree, which shows the hierarchy and which devices are actually probed.

Q. "What's the difference between bind and probe in U-Boot?"

A. bind는 DT 노드와 드라이버를 짝지어 udevice 구조체를 만드는 것뿐이라 하드웨어를 건드리지 않는다. probe는 DT 속성을 읽고(of_to_plat), 부모를 먼저 probe하고, pinctrl·clock 기본값을 적용한 뒤 드라이버의 probe로 하드웨어를 깨운다. QEMU에서 직접 해 보니 내 misc 드라이버는 부팅 때 bind만 되고 dm tree에서 probed 표시가 없다가, misc list로 처음 접근할 때 probe 로그가 찍혔다.

Bind just pairs a node with a driver and allocates the udevice — no hardware access, and it's done for the whole tree at startup. Probe is when the device is actually brought up: of_to_plat reads the DT properties, the parent is probed first, default pinctrl and assigned clocks are applied, then the driver's probe runs. I verified this in QEMU with a small UCLASS_MISC driver: it showed up in dm tree unprobed after boot, and the probe message only appeared the first time something accessed the misc uclass.

Q. "What is relocation in U-Boot and why is it needed?"

A. U-Boot는 링크 주소(flash나 SPL이 올려 준 곳)에서 시작하고, DRAM 크기를 알아낸 뒤 DRAM 꼭대기로 자신을 복사해서 옮긴다. 아래쪽 DRAM을 커널·initrd용으로 비워 두고, RAM 크기가 달라도 같은 바이너리가 동작하게 하기 위해서다. PIE로 링크되어 코드는 PC-상대라 그대로 돌고, 데이터 안의 절대 주소는 .rela.dyn의 R_AARCH64_RELATIVE 항목을 돌며 오프셋을 더해 고친다. QEMU 빌드에서는 3833개였다. relocation 전에는 BSS를 못 쓰고 작은 early malloc과 gd만 쓴다.

U-Boot starts at its link address — in flash, or wherever SPL put it — and once board_init_f knows the DRAM size it reserves space from the top of RAM down and copies itself there. That keeps low memory free for the kernel and initrd and makes the same binary work regardless of RAM size. The ARM64 build is position-independent, so code just runs; absolute addresses stored in data, like function pointers in driver and command tables, are fixed up by walking the R_AARCH64_RELATIVE entries in .rela.dyn — about 3800 in the QEMU build. Before relocation you can't use BSS or globals; you only have global data in x18 and a small early malloc pool.

꼬리 질문: "How do you debug code before relocation?" → DEBUG_UART로 DM 없이 직접 출력, bdinfo의 relocaddr로 심볼 주소 보정해 gdb에 add-symbol-file u-boot <relocaddr>.

Q. "What are bootph tags (formerly u-boot,dm-pre-reloc)?"

A. DT 노드가 어느 부팅 단계에 포함될지 표시하는 속성이다. 태그가 없으면 마지막 단계(U-Boot proper의 relocation 후)에서만 bind된다. bootph-all은 모든 단계, bootph-pre-ram은 SPL, bootph-pre-sram은 TPL이다. SPL 빌드는 fdtgrep으로 태그 없는 노드를 지운 작은 DT를 만든다. 부모 노드에도 태그를 달아야 하고, 콘솔 UART에 빠뜨리면 SPL이 아무것도 안 찍는다.

They mark which boot phases need a device-tree node. Untagged nodes only exist in the final phase, after relocation. bootph-all means every phase, bootph-pre-ram means SPL, bootph-pre-sram means TPL, and bootph-some-ram covers U-Boot proper before relocation. The SPL build runs fdtgrep to drop everything untagged, which keeps the SPL DTB tiny. The classic bug is forgetting to tag the console UART, its pinmux, or a parent bus node — SPL then prints nothing. They replaced the u-boot,dm-pre-reloc style properties in 2023, which matters when porting an old vendor BSP to mainline.

Q. "How do you manage U-Boot configuration for several product variants?"

A. 보드 defconfig 하나를 기준으로 두고, 변형(디버그·생산·고객별)은 fragment로 덮어쓴다. U-Boot는 make <name>.config로 board 디렉터리의 fragment를 찾아 merge_config.sh로 합치고, defconfig 안에서 #include로 공유 fragment를 쓸 수도 있다. 바꾼 뒤엔 savedefconfig로 최소본을 뽑아 diff를 리뷰한다. 이때 건드리지 않은 줄이 나타나면 imply·default 의존성 변화이니 의도한 것인지 확인한다.

One base defconfig per board, and variants — debug, production, customer-specific — as small fragments. U-Boot's kconfig Makefile finds a fragment named on the make command line anywhere under board/ and merges it with merge_config.sh, and defconfigs can also #include shared fragments, like qemu_arm64_acpi_defconfig including acpi.config. After changes I run savedefconfig and review the diff. If lines appear that I didn't touch, that's an imply or default dependency shifting, so I decide whether to keep them explicitly. For production I'd also check the binary size impact of each option.

Q. "Where does the environment live, and what happens on a fresh board?"

A. 기본 환경은 바이너리에 들어 있고(.env 파일 + Kconfig 값), 저장된 환경은 ENV_IS_IN_MMC/SPI_FLASH 등으로 정한 위치에 있다. 부팅 때 저장된 env를 읽어 CRC가 맞으면 그것을 쓰고, 아니면 "bad CRC, using default environment"를 띄우고 기본값을 쓴다. 새 보드나 env 영역이 지워진 보드에서 정상이다. 반대로 기본값을 바꿨는데 안 바뀌면 저장된 env가 이기고 있는 것이다. 생산 제품은 이중화 env나 env 쓰기 제한을 고려한다.

There are two layers: the default environment compiled into the binary, built from the board's .env file plus Kconfig values like BOOTDELAY, and a saved environment at a location chosen with ENV_IS_IN_MMC, SPI_FLASH and so on. At boot U-Boot loads the saved copy and uses it if the CRC is valid; otherwise it prints "bad CRC, using default environment", which is normal on a fresh board. The flip side is that a saved environment overrides a new default, so after an update you may need env default -a and saveenv. For products you'd use a redundant environment for power-fail safety, and often restrict or disable writes.

16. 요약 & 체크리스트#

U-Boot 포팅은 공통 코드는 두고 보드별 부분을 새로 만드는 일이다. 보드별 부분은 defconfig(Kconfig 값), Device Tree(Linux와 공유하는 .dts + U-Boot 전용 -u-boot.dtsi), board/<vendor>/<board>/의 훅(dram_init, board_late_init …)과 .env, 그리고 실물 SoC라면 SPL의 board_init_f와 툴로 생성한 DDR 타이밍·벤더 training 펌웨어다. 설정은 Linux와 같은 Kconfig로 하고, fragment로 변형을 만들고, savedefconfig diff로 리뷰한다. 드라이버는 driver/uclass/udevice의 DM으로 쓰며, Linux driver model과 1:1로 대응하되 bind는 전부, probe는 처음 쓸 때라는 점이 다르다. U-Boot는 링크 주소에서 시작해 DRAM 꼭대기로 자신을 relocate하며(PIE + R_AARCH64_RELATIVE 수정), relocation 전에는 bootph-* 태그가 붙은 노드만 bind하고 BSS 없이 gd와 작은 malloc으로 버틴다. QEMU에서 직접 명령과 드라이버를 추가해 이 흐름을 모두 로그로 확인했다.
