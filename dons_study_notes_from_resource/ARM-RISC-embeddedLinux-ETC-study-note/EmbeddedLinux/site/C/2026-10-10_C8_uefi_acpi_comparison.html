0. 큰 그림 — 이게 왜 필요한가#

C1~C7에서 본 임베디드 arm64 부팅은 이랬다: BootROM → SPL/TF-A → U-Boot → booti로 Image + DTB를 메모리에 놓고 점프 → 커널. Don의 SSD 펌웨어와 크게 다르지 않다. 부트로더가 하드웨어 설명(DTB)을 손에 쥐여 주고 커널로 점프한다.

그런데 PC와 서버는 전혀 다른 세계에서 자랐다. 수십 개 회사가 만든 메인보드에 같은 OS 설치 USB 하나가 그대로 부팅되어야 한다. 그래서 PC 세계는 "펌웨어가 표준 인터페이스(UEFI)를 제공하고, 하드웨어 설명도 펌웨어가 표준 형식(ACPI)으로 들고 있다"는 방식을 택했다. 보드마다 커널·DTB를 맞춰 빌드하는 임베디드 방식과 정반대다.

최근에는 두 세계가 섞인다. arm64 서버는 x86처럼 UEFI + ACPI로 부팅하고, U-Boot는 UEFI API를 흉내 내서(EBBR) 배포판 설치 이미지를 그대로 부팅하며, NVIDIA Jetson Orin은 UEFI 펌웨어로 부팅하지만 하드웨어 설명은 DT를 쓴다. 지금 Don이 쓰는 Lima VM 자체도 UEFI + ACPI로 부팅한 arm64 머신이다.

그림 1 — 네 가지 부팅 사슬. 위 두 줄은 PC·서버 세계, 아래 두 줄은 임베디드 세계다. 맨 아래 줄(U-Boot가 UEFI API를 구현)은 두 세계를 잇는 다리로, 커널 입장에서는 둘째 줄과 같은 "EFI stub" 입구로 들어온다.

1. 레거시 BIOS에서 UEFI로 — 무엇이 바뀌었나#

1.1 레거시 BIOS — 1981년의 인터페이스#

x86 CPU는 리셋되면 물리 주소 0xFFFFFFF0(리셋 벡터)에서 실행을 시작한다. 거기 매핑된 SPI NOR 플래시의 BIOS 코드가 POST(Power-On Self Test: DRAM·칩셋 초기화, 장치 검사)를 하고, 부팅 디스크의 첫 섹터 512바이트(MBR)를 메모리 0x7C00에 읽어 16비트 real mode로 점프한다. 디스크 읽기는 BIOS가 제공하는 소프트웨어 인터럽트 INT 13h로 한다.

이 구조의 한계는 Don이 보면 바로 보인다.

  • 446바이트 부트 코드: MBR에는 파티션 테이블(64B)과 시그니처(2B)를 빼면 코드가 446바이트밖에 안 들어간다. 그래서 GRUB은 1단계(boot.img) → 파티션 사이 빈틈에 숨긴 core.img로 여러 번 뛰어야 했다.
  • 16비트 real mode + INT 호출: 1 MB 주소 공간, 펌웨어 서비스가 소프트웨어 인터럽트 번호로만 노출된다. 드라이버를 추가할 표준 방법이 없다(Option ROM 정도).
  • MBR 파티션 2 TiB 한계: 32비트 LBA × 512B.
  • 하드웨어 설명 없음: 그래서 ACPI(1996)가 별도로 생겨 BIOS에 붙었다.

1.2 UEFI — "펌웨어가 OS 로더에게 주는 C API"#

UEFI(Unified Extensible Firmware Interface)는 Intel의 EFI(Itanium용, 1990년대 말)를 업계 표준으로 만든 것이다. 핵심 발상은 펌웨어가 C 함수 포인터 테이블(System Table)을 OS 로더에게 넘겨준다는 것이다.

UEFI 규격은 두 개로 나뉜다는 점을 기억해 두면 면접에서 깊이가 드러난다.

  • UEFI Specification: 펌웨어가 OS 로더에게 보여 주는 바깥 인터페이스(System Table, 프로토콜, 변수, 이미지 형식). Linux EFI stub·GRUB·shim이 의존하는 것은 이것뿐이다.
  • PI(Platform Initialization) Specification: 펌웨어 내부 구조(SEC/PEI/DXE 단계). EDK2(TianoCore)가 이 구조로 구현되어 있고 AMI·Insyde·Phoenix 같은 상용 펌웨어도 대부분 EDK2 기반이다. U-Boot는 PI를 따르지 않고 UEFI 바깥 인터페이스만 구현한다(§8).

2. UEFI의 단계 — SEC · PEI · DXE · BDS · TSL · RT#

2.1 직관 — Don의 SSD 부트와 1:1로 맞춰 보기#

그림 2 — PI 단계. 빨간 점선(ExitBootServices()) 왼쪽에서는 펌웨어가 기계의 주인이고, 오른쪽에서는 OS가 주인이며 펌웨어는 몇 개의 Runtime Services만 남긴다. 임베디드 쪽에서 "부팅 후에도 남는 펌웨어"에 해당하는 것은 TF-A BL31(PSCI)이다.

UEFI의 "프로토콜"은 Don에게 익숙한 패턴이다. GUID(128비트 ID)로 찾는 함수 포인터 구조체다. 예를 들어 블록 장치 드라이버는 EFI_BLOCK_IO_PROTOCOL(ReadBlocks/WriteBlocks 함수 포인터)을 자기 핸들에 설치하고, FAT 드라이버는 그 위에 EFI_SIMPLE_FILE_SYSTEM_PROTOCOL을 얹는다. OS 로더는 HandleProtocol(handle, &guid, &iface)로 인터페이스를 얻어 iface->Read(...)를 부른다. 리눅스 커널의 file_operations와 같은 vtable이고, 다른 점은 이름 대신 GUID로 찾는다는 것뿐이다.

2.2 Boot Services와 Runtime Services — ExitBootServices()가 경계#

  • Boot Services: AllocatePages, GetMemoryMap, LoadImage/StartImage, HandleProtocol, 타이머·이벤트. OS 로더가 쓰는 "작은 OS". ExitBootServices(image, map_key)를 부르면 전부 사라지고 해당 메모리는 OS 것이 된다. 호출할 때 최신 메모리 맵의 map_key를 넘겨야 해서, 맵을 다시 읽고 재시도하는 루프가 필요하다 (커널 stub의 efi_exit_boot_services()에 그 루프가 있다).
  • Runtime Services: GetVariable/SetVariable(NVRAM), GetTime/SetTime(RTC), ResetSystem, UpdateCapsule(펌웨어 업데이트), SetVirtualAddressMap. OS가 실행 중에도 호출한다. 리눅스의 efivarfs, rtc-efi, efibootmgr, fwupd가 이것을 쓴다.

함정: Runtime Services 코드는 펌웨어 코드가 커널 권한(EL1/ring 0)에서 도는 것이다. 펌웨어 버그가 커널을 죽일 수 있어서, 리눅스는 별도 페이지 테이블(efi_mm)에서 호출하고 arm64에서는 전용 스택·워크큐로 감싼다(CONFIG_EFI_RUNTIME_WRAPPERS). 아래 랩 커널 config에서 그 옵션을 볼 수 있다.

3.3 ESP와 부트 엔트리 — efibootmgr -v#

무엇을 확인하나: NVRAM의 부트 옵션이 ESP의 어떤 파일을 가리키는지 본다. efibootmgr는 VM에 이미 설치되어 있었다.

출력에서 볼 것:

  • Boot0003의 디바이스 패스(device path)는 "디스크의 GPT 15번 파티션(vda15, 시작 LBA 0x800) 안의 \EFI\ubuntu\shimaa64.efi"다. UEFI는 파일 경로로 부트 대상을 찾는다. MBR처럼 "디스크 첫 섹터"가 아니다.
  • dp: 바이트는 노드의 연속이다: 04 01(Media/HardDrive) → 04 04(Media/FilePath, UTF-16 문자열) → 7f ff(End). §3.4에서 C로 직접 디코드한다.
  • ESP는 그냥 FAT(vfat) 파티션이다(PARTTYPENAME "EFI System"). EFI/BOOT/BOOTAA64.EFI는 NVRAM에 엔트리가 없을 때 쓰는 제거식 미디어 경로(removable media path, arm64 이름은 BOOTAA64.EFI, x86-64는 BOOTX64.EFI)다. fbaa64.efi(fallback)는 BOOTAA64.CSV를 읽어 Boot####를 다시 만들어 주고, mmaa64.efi는 MOK 관리자(§4)다.
  • ESP의 grub.cfg는 3줄짜리 "점프대"다. 진짜 설정은 /boot(ext4)의 grub/grub.cfg에 있다.
  • 이 VM은 Secure Boot를 지원하지 않는다(Apple Virtualization의 UEFI). 그래도 shim은 그대로 사슬에 끼어 있다.

그림 3 — UEFI 부트 매니저. NVRAM 변수가 ESP의 파일을 가리키고(shim), shim은 같은 디렉터리의 GRUB을, GRUB은 ext4 /boot의 설정·커널·initrd를 읽는다. 펌웨어는 ext4를 몰라도 된다 — FAT만 읽으면 된다.

3.4 C로 UEFI 변수 디코드하기 — efivarfs 파일 형식#

무엇을 확인하는 코드인가: /sys/firmware/efi/efivars/<이름>-<GUID> 파일은 "4바이트 속성 + 변수 데이터"다. Boot####의 데이터는 EFI_LOAD_OPTION 구조체(속성 u32, 디바이스 패스 길이 u16, UTF-16 설명, 디바이스 패스, 옵션 데이터)다. 이걸 직접 풀어 본다.

출력에서 볼 것: 경고 0개로 빌드되고, efibootmgr와 같은 내용이 나온다. 변수 속성 비트는 NON_VOLATILE=1, BOOTSERVICE_ACCESS=2, RUNTIME_ACCESS=4다. BootOrder는 0x7(NV + BS + RT: 재부팅 후에도 남음), BootCurrent는 0x6(휘발성 — 이번 부팅에서 펌웨어가 만든 값)이다. type 2/1은 ACPI 노드(PciRoot), 1/1은 PCI 노드(Pci(dev,fn))다. 이 경로 표현은 x86 PC와 완전히 같다 — 그것이 표준의 힘이다.

4. Secure Boot — PK · KEK · db · dbx, 그리고 shim#

4.1 키 계층#

Don이 SSD에서 한 FW 서명 검증(ROM에 공개키 해시를 퓨즈하고, 로더가 다음 이미지를 검증)을 변수 저장소 안의 키 계층으로 표준화한 것이 UEFI Secure Boot다.

펌웨어는 LoadImage()로 .efi를 실행하기 전에 PE 파일의 Authenticode 서명을 db/dbx로 검증한다.

4.2 shim — 리눅스 배포판이 Microsoft 서명을 받는 방법#

PC 메인보드의 db에는 대개 Microsoft 키만 있다. 배포판이 모든 GRUB·커널 빌드를 Microsoft에 서명받을 수는 없으므로 shim이라는 작은 1단계 로더를 둔다.

  1. shim은 Microsoft UEFI CA로 서명된다 → 펌웨어 db 검증 통과.
  2. shim 안에는 배포판(Canonical·Red Hat …)의 인증서가 내장되어 있다. shim은 자기 검증 프로토콜로 grubaa64.efi를 검증한다.
  3. GRUB은 shim의 검증 프로토콜을 이용해 커널(vmlinuz, 배포판 키로 서명된 PE)을 검증한다.
  4. 커널은 모듈 서명(CONFIG_MODULE_SIG)과 lockdown으로 사슬을 이어 간다.
  5. 사용자가 직접 빌드한 커널·모듈은 MOK에 자기 키를 등록(mokutil --import, 재부팅 시 mmaa64.efi MokManager에서 확인)해서 통과시킨다.
  6. SBAT: 취약한 GRUB 세대를 해시 하나하나 dbx에 넣는 대신 "세대 번호"로 폐기하는 장치. 위 efivars 목록의 SbatLevelRT, MokListRT가 shim이 OS에 노출한 값이다.

그림 4 — Secure Boot 키 계층과 실행 사슬. 점선은 "펌웨어가 db를 참조해 shim을 검증한다"는 뜻이다. 임베디드 secure boot는 키가 퓨즈(OTP)에 있다는 점만 다르고 사슬의 생각은 같다.

4.3 직접 확인 — 서명 없는 랩 커널을 Secure Boot 펌웨어가 거부한다#

무엇을 확인하나: Ubuntu의 EDK2 패키지에는 Microsoft 키가 미리 등록된 Secure Boot 변수 템플릿(AAVMF_VARS.ms.fd)이 있다. 랩 Image(서명 없음)를 ESP의 \EFI\BOOT\BOOTAA64.EFI로 넣은 디스크를 만들어 이 펌웨어로 부팅해 본다. 디스크 이미지는 root 없이 sgdisk + mtools로 만든다.

출력에서 볼 것: BDS가 virtio 디스크에 엔트리를 자동 생성(Boot0002 "UEFI Misc Device")해 제거식 미디어 경로를 열었지만, LoadImage()가 Access Denied를 돌려준다. 같은 디스크를 Secure Boot 없는 펌웨어(AAVMF_CODE.no-secboot.fd)로 돌리면 커널이 로드된다(§5.2, §7.4). 참고로 QEMU의 -kernel 옵션(fw_cfg로 커널 전달)을 Secure Boot 펌웨어와 함께 쓰면 이 메시지 대신 Not Found로 끝났다 — 직접 커널 로더 경로 자체가 막혀 있는 것으로 보인다(동작만 확인했고 EDK2 소스로 원인을 확인하지는 않았다).

5. GRUB과 systemd-boot — UEFI 위의 OS 로더#

5.1 OS 로더는 그냥 "EFI 애플리케이션"이다#

UEFI 세계에서 GRUB, shim, systemd-boot, 그리고 Linux 커널 자신은 모두 같은 형식의 파일이다: PE/COFF 실행 파일(Windows .exe와 같은 포맷, MZ로 시작)이고 Optional Header의 Subsystem 필드가 10(EFI_APPLICATION)이다. 펌웨어는 ELF를 모른다.

5.2 GRUB을 직접 만들어 EDK2 → GRUB → 랩 커널로 부팅#

무엇을 확인하나: GRUB이 펌웨어 위의 EFI 앱으로서 FAT를 읽고 커널을 "EFI 앱으로" 실행하는 과정을 본다. grub-mkstandalone은 모듈과 설정을 메모리 디스크로 한 .efi에 묶는다(VM에 grub-efi-arm64-bin이 이미 설치되어 있다).

GRUB 2.12 이후 arm64에서는 GRUB이 커널을 직접 해부하지 않고 LoadImage/StartImage로 커널의 EFI stub을 실행하며, initrd는 LoadFile2 프로토콜(§6.2)로 건넨다 — stub의 "Loaded initrd from LINUX_EFI_INITRD_MEDIA_GUID device path"가 그 증거다. 처음 시도에서 insmod part_gpt/fat 없이 search를 하자 error: no such device: /Image., 따옴표 없이 ;·|를 쓰자 error: syntax error.가 났다 — GRUB 스크립트도 셸처럼 파싱한다.

6. Linux EFI stub — arm64 Image는 동시에 PE/COFF EFI 앱이다#

6.1 하나의 파일, 두 개의 입구#

출력에서 볼 것 — 이 64바이트 헤더는 Linux arm64의 작은 걸작이다.

  • 첫 2바이트 4d 5a는 DOS/PE 매직 MZ다. 그런데 첫 4바이트 fa405a4d를 AArch64 명령으로 해석하면 ccmp x18, #0, #0xd, pl — 레지스터 x18과 플래그만 건드리는 사실상 NOP이다. 일부러 "MZ이면서 실행해도 무해한 명령"을 골랐다.
  • 다음 명령 b 0x1fea0f0은 primary_entry(= _text + 0x1fea0f0)로 점프한다. booti는 파일 오프셋 0으로 점프하므로 이 경로로 들어간다 (Documentation/arch/arm64/booting.rst의 code0/code1).
  • 오프셋 0x38의 ARMd(= ARM\x64)는 arm64 boot protocol 매직, 0x3c의 0x40은 PE 헤더 위치(e_lfanew). 그래서 0x40에 PE\0\0이 온다.
  • PE의 EntryPoint RVA=0x2075fe8 = _text + 0x2075fe8 = __efistub_efi_pe_entry. UEFI 펌웨어(또는 GRUB, U-Boot bootefi)는 이 입구로 들어온다. stub 코드는 커널 안에 __efistub_ 접두어로 격리되어 링크된다.
  • flags=0xa: bit0=0(리틀 엔디안), bit1-2=01(4K 페이지), bit3=1(물리 주소 어디에 놓아도 됨).

6.2 stub이 하는 일 — 펌웨어 세계에서 커널 세계로 건너가기#

그림 5 — EFI stub 핸드오버. 왼쪽 경로에서 stub은 "작은 부트로더"로서 U-Boot가 booti 전에 하던 일(cmdline·initrd·DTB 준비)을 UEFI API로 직접 한 뒤 같은 primary_entry로 들어간다. ACPI 머신에서도 커널은 항상 FDT 하나를 받는다 — /chosen만 있는 빈 DTB다.

lab 소스(drivers/firmware/efi/libstub/)로 따라가면: efi-stub-entry.c의 efi_pe_entry() → efi-stub.c의 efi_stub_common()(여기서 efi_load_initrd()) → fdt.c의 efi_boot_kernel() → allocate_new_fdt_and_exit_boot()(DTB 선택: "Using DTB from command line" / "Using DTB from configuration table" / "Generating empty DTB", 그리고 efi_exit_boot_services() 재시도 루프) → arm64.c의 efi_enter_kernel().

initrd 전달 방식이 중요하다. 예전에는 커널 cmdline initrd=\path\file을 stub이 같은 장치의 파일시스템에서 직접 읽었다(CONFIG_EFI_GENERIC_STUB_INITRD_CMDLINE_LOADER, 이 랩 config에는 꺼져 있다). 지금 권장 방식은 로더(GRUB·U-Boot·EDK2)가 LINUX_EFI_INITRD_MEDIA_GUID 디바이스 패스에 EFI_LOAD_FILE2_PROTOCOL을 설치하고, stub이 "initrd를 달라"고 그 프로토콜을 부르는 것이다. 로더가 파일 위치·검증을 책임지고 stub은 단순해진다.

6.3 로그 레벨 함정 — EFI stub: 줄은 efi=debug를 줘야 보인다#

랩 커널을 bootefi로 처음 부팅했을 때는 EFI stub: 줄이 하나도 안 나왔다. 소스를 보면 이유가 있다.

출력에서 볼 것: stub의 기본 출력 레벨은 NOTICE(5)라서 efi_info()(INFO=6) 메시지가 숨는다. cmdline에 efi=debug가 있으면 DEBUG로 올라가고, quiet이면 더 내려간다. 그래서 이 노트의 모든 bootefi 실험은 efi=debug를 붙였다.

6.4 VM 호스트에서 본 stub의 흔적 — ACPI 머신의 "빈 DTB"#

§3.1에서 VM에 /proc/device-tree가 없는데 /sys/firmware/fdt는 있었다. 이것이 바로 stub이 만든 "빈 DTB"다.

출력에서 볼 것: 하드웨어 노드가 하나도 없고 /chosen만 있다. stub은 "EFI System Table 주소, EFI 메모리 맵 위치, cmdline"을 이 FDT에 적어 커널에 넘긴다 — arm64 커널의 입구 규약은 항상 "x0 = FDT"이고, ACPI 머신에서도 그 규약을 유지하려고 빈 DTB를 만든다. 커널은 이 FDT가 /chosen뿐이면(dt_is_stub()) ACPI를 쓰기로 결정한다(§9). linux,uefi-secure-boot는 VM의 7.0 커널이 넣은 속성으로 랩 6.18 소스에는 없다. 값 2는 커널 enum efi_secureboot_mode의 순서(unset, unknown, disabled, enabled)로 보면 "disabled"이고 mokutil 결과와 맞는다.

8. U-Boot가 UEFI를 구현한다 — EBBR과 bootefi#

8.1 왜 U-Boot에 UEFI가?#

배포판(Debian, Fedora, Ubuntu, openSUSE)은 arm64 설치 이미지를 하나만 만들고 싶다. 서버는 UEFI로 그 이미지를 부팅한다. 임베디드 보드도 같은 이미지를 쓰게 하려면 U-Boot가 UEFI 인터페이스를 제공하면 된다. 그래서 U-Boot에 CONFIG_EFI_LOADER가 생겼고(2016년경, Alexander Graf가 시작한 것으로 기억), Arm의 EBBR(Embedded Base Boot Requirements)이 "임베디드 보드가 제공해야 할 UEFI 부분집합 + DT 허용"을 규정했다. U-Boot는 PI 단계(SEC/PEI/DXE) 없이 바깥 인터페이스만 구현한다: Boot/Runtime Services 일부, 블록·파일시스템·콘솔·네트워크 프로토콜, 변수(파일 또는 플래시), 부트 매니저, Secure Boot 일부, capsule 업데이트.

Q. Walk me through how a UEFI arm64 server boots Linux, and contrast it with a typical embedded ARM board.

A. 서버는 TF-A 뒤에 UEFI 펌웨어(EDK2 계열)가 DRAM·PCIe를 초기화하고, BDS가 NVRAM의 BootOrder/Boot####를 따라 ESP(FAT)의 shim → GRUB을 실행한다. GRUB은 커널을 EFI 앱으로 실행하고, 커널의 EFI stub이 initrd·cmdline을 받아 ExitBootServices() 후 커널로 들어간다. 하드웨어 설명은 펌웨어가 들고 있는 ACPI 테이블이다. 임베디드 보드는 BootROM → SPL → TF-A → U-Boot가 booti로 Image와 보드 전용 DTB를 메모리에 놓고 바로 점프한다. 차이는 "표준 펌웨어 인터페이스 + 펌웨어 소유 HW 설명" 대 "보드별 부트로더 + 커널과 같이 빌드하는 DT"다.

A server goes TF-A, then UEFI firmware that brings up DRAM and PCIe; the boot manager reads BootOrder and Boot#### variables and launches shim and GRUB from the FAT ESP. GRUB starts the kernel as an EFI application — the kernel's EFI stub collects the command line and initrd, calls ExitBootServices and jumps into the kernel, and hardware is described by ACPI tables owned by the firmware. An embedded board goes BootROM, SPL, TF-A, U-Boot, and U-Boot's booti places the Image and a board-specific DTB in memory and jumps directly. So it's a standardized firmware interface with firmware-owned hardware description, versus a board-specific bootloader with a device tree built alongside the kernel.

꼬리 질문: "What happens at ExitBootServices?" → Boot Services 메모리를 OS가 회수하고, 이후 펌웨어는 Runtime Services(변수·시간·리셋·capsule)만 남는다. 최신 메모리 맵 키가 필요해 재시도 루프가 있다.

Q. ACPI versus Device Tree — what's the difference, and when is each used?

A. 둘 다 열거할 수 없는 장치를 OS에 알려 주는 수단이다. DT는 정적 자료 구조라 compatible, reg, interrupts만 있고, 클럭·전원·핀 제어는 커널 드라이버가 직접 한다. ACPI는 테이블 + AML 바이트코드라서 장치를 _HID로 식별하고 _CRS로 자원을, _PS0/_PS3 같은 메서드로 전원 처리를 펌웨어에 숨긴다. 그래서 OS 하나로 많은 서버를 지원해야 하는 x86·arm64 서버(SBBR)는 ACPI, 커널이 SoC를 세밀하게 제어해야 하는 임베디드·Jetson은 DT를 쓴다. 같은 arm64 커널이 둘 다 지원하고, arm64에서는 DT에 실제 노드가 있으면 DT를, /chosen만 있는 stub DT면 ACPI를 고른다.

Both describe non-discoverable hardware. Device tree is a static data structure — compatible, reg, interrupts — and the kernel drivers themselves control clocks, regulators and pins. ACPI is tables plus AML bytecode: devices are identified by _HID, resources come from _CRS, and power sequencing is hidden behind firmware methods like _PS0 and _PS3. That's why servers, which must run one OS image across many platforms, use ACPI under SBBR, while embedded SoCs and Jetson use device tree for fine-grained control. The same arm64 kernel supports both; it picks DT if the tree has real nodes and ACPI if it only got a stub tree with /chosen.

꼬리 질문: "How do you make one driver work on both?" → of_match_table과 acpi_match_table을 둘 다 두고, 속성은 device_property_read_*()로 읽는다. ACPI에서 PRP0001 + _DSD compatible로 DT 매칭을 재사용할 수도 있다.

Q. What is the EFI stub? How can the same arm64 Image be booted by both U-Boot's booti and a UEFI firmware?

A. arm64 Image의 첫 64바이트는 두 헤더를 겹쳐 놓았다. 첫 바이트가 MZ인데 그 4바이트를 명령으로 실행하면 무해한 ccmp이고, 다음 명령이 primary_entry로 분기한다 — booti는 오프셋 0으로 점프해서 이 길로 간다. 한편 0x3c의 PE 오프셋이 PE/COFF 헤더를 가리키고 Subsystem이 EFI_APPLICATION, 진입점이 efi_pe_entry라서 UEFI 펌웨어는 이것을 일반 EFI 앱으로 실행한다. stub은 LoadOptions에서 cmdline, LoadFile2에서 initrd, config table에서 DTB를 얻거나 빈 DTB를 만들고, /chosen에 EFI 시스템 테이블·메모리 맵 위치를 적은 뒤 ExitBootServices()를 하고 같은 primary_entry로 들어간다.

The first 64 bytes of the arm64 Image overlay two headers. It starts with "MZ", but those four bytes decode to a harmless ccmp instruction, followed by a branch to primary_entry — that's the path booti takes by jumping to offset zero. Offset 0x3c points to a PE/COFF header whose subsystem is EFI application and whose entry point is efi_pe_entry, so UEFI firmware runs it as a normal EFI app. The stub gets the command line from LoadOptions, the initrd through LoadFile2, the DTB from the configuration table or generates an empty one, records the EFI system table and memory map in /chosen, calls ExitBootServices and enters the same primary_entry.

Q. How does UEFI Secure Boot work for Linux?

A. 펌웨어 변수에 키 계층이 있다: OEM의 PK가 KEK 변경을 서명하고, KEK가 허용 목록 db와 폐기 목록 dbx를 서명한다. 펌웨어는 .efi를 로드하기 전에 Authenticode 서명을 db/dbx로 검증한다. PC의 db에는 보통 Microsoft 키만 있어서 배포판은 Microsoft가 서명한 shim을 쓰고, shim은 내장된 배포판 인증서와 MOK로 GRUB·커널을 검증한다. 커널은 모듈 서명과 lockdown으로 이어 간다. 폐기는 dbx와 SBAT 세대 번호로 한다. 임베디드 secure boot와 생각은 같고 키가 퓨즈 대신 인증된 변수에 있다는 점이 다르다.

The firmware holds a key hierarchy in authenticated variables: the OEM's PK signs KEK updates, and KEK signs the allow list db and the deny list dbx. Before loading any EFI binary the firmware checks its Authenticode signature against db and dbx. PCs usually only trust Microsoft keys, so distributions ship a Microsoft-signed shim, which embeds the distro certificate and Machine Owner Keys and verifies GRUB and the kernel; the kernel continues with module signing and lockdown. Revocation is via dbx and SBAT generation numbers. It's the same chain-of-trust idea as embedded secure boot, but the root keys live in authenticated variables rather than fuses.

Q. What are UEFI runtime services and why would an embedded Linux engineer care?

A. ExitBootServices() 뒤에도 남는 펌웨어 함수들이다: GetVariable/SetVariable, GetTime/SetTime, ResetSystem, UpdateCapsule, SetVirtualAddressMap. 리눅스는 efivarfs, rtc-efi, 재부팅, capsule 기반 펌웨어 업데이트(fwupd)에 쓴다. 펌웨어 코드가 커널 권한으로 도는 것이라 버그가 커널을 죽일 수 있어 커널은 별도 efi_mm에서 래퍼로 호출한다. 임베디드에서 U-Boot의 EFI 구현을 쓸 때 변수 저장소(파일·SPI·RPMB/OP-TEE)와 capsule 업데이트가 OTA 설계에 직접 걸린다.

They're the firmware functions that survive ExitBootServices: Get/SetVariable, Get/SetTime, ResetSystem, UpdateCapsule and SetVirtualAddressMap. Linux uses them for efivarfs, the rtc-efi driver, reboot, and capsule-based firmware updates through fwupd. Since it's firmware code running at kernel privilege, Linux calls it through wrappers in a separate efi_mm. On embedded boards using U-Boot's EFI implementation, the variable store — a file, SPI flash, or RPMB through OP-TEE — and capsule updates feed directly into the OTA design.

Q. Why did U-Boot implement the UEFI API, and what are EBBR and SystemReady?

A. 배포판이 arm64 설치 이미지 하나로 서버와 보드를 모두 부팅하게 하려고다. U-Boot는 PI 단계 없이 UEFI의 바깥 인터페이스(Boot/Runtime Services 일부, 블록·파일 프로토콜, 변수, 부트 매니저)를 구현하고 bootefi로 EFI 앱을 실행한다. EBBR은 임베디드 보드가 제공해야 할 UEFI 부분집합을 정하고 DT를 허용한다. 서버용은 SBBR로 ACPI를 요구한다. SystemReady는 Arm의 인증 프로그램으로, ACS 테스트로 SBSA/BSA 하드웨어와 SBBR/EBBR 펌웨어 준수를 확인한다. 나는 QEMU에서 U-Boot efidebug boot add로 Boot0001을 만들고 bootefi bootmgr로 커널 EFI stub을 띄워 initrd가 LoadFile2로 넘어가는 것까지 확인했다.

So distributions can boot one arm64 install image on both servers and boards. U-Boot implements the outward-facing UEFI interface — a subset of boot and runtime services, block and file protocols, variables and a boot manager — without the PI phases, and bootefi runs EFI apps. EBBR defines the UEFI subset an embedded board must provide and allows device tree; SBBR is the server counterpart and requires ACPI. SystemReady is Arm's certification program that checks hardware and firmware compliance with the ACS test suites. I've exercised this in QEMU: created a Boot0001 option with efidebug, ran bootefi bootmgr, and watched the kernel's EFI stub receive the initrd through LoadFile2.

Q. Jetson Orin boots with UEFI but uses a device tree. How does that work?

A. UEFI와 ACPI는 독립된 축이다. 펌웨어가 ACPI 대신 DTB를 UEFI configuration table로 설치하면 커널 stub이 "Using DTB from configuration table"로 그것을 받아 DT 모드로 부팅한다. 나는 QEMU에서 같은 EDK2와 같은 커널로 acpi=on이면 "Generating empty DTB" + ACPI, acpi=off면 config table의 DTB + Machine model 줄이 나오는 것을 확인했다. Orin은 그 DT 쪽 조합이고, 그래서 overlay 같은 DT 작업은 그대로 하면서 부트 관리는 UEFI 방식(L4TLauncher, 변수, capsule)으로 한다.

UEFI and ACPI are independent axes. If the firmware installs a DTB as a UEFI configuration table instead of ACPI tables, the kernel's stub reports "Using DTB from configuration table" and the kernel boots in DT mode. I reproduced this in QEMU with the same EDK2 and the same kernel: with ACPI on, the stub generates an empty DTB and the kernel uses ACPI; with ACPI off, it picks up the DTB from the config table and prints the machine model. Orin is the DT flavor of that, so device-tree work like overlays stays the same while boot management follows UEFI conventions.

  1. 관찰 과제: VM 호스트에서 sudo cat /sys/firmware/acpi/tables/DSDT > dsdt.aml로 뽑고, c8_acpi의 _HID 스캔을 확장해 _UID와 _CRS의 Memory32Fixed(태그 0x86) 주소도 출력하라. (iasl은 설치되어 있지 않으니 설치하지 말고 바이트로 풀어 본다.) 정답/힌트: ACPI 스펙의 "Large Resource Data Type" — Memory32Fixed는 86 09 00 <rw> <base u32> <len u32>.
  1. 설계 문제: 센서 키트 보드를 SystemReady Devicetree band(EBBR)로 만들어 Fedora 공식 이미지를 부팅하려면 U-Boot에서 무엇을 켜고 무엇을 확인해야 하는가? 5개 이상 적어라. 정답/힌트: EFI_LOADER, BOOTSTD/bootflow, 변수 저장소 위치, EFI_LOAD_FILE2_INITRD, Runtime ResetSystem·GetTime, capsule 업데이트, 메인라인 호환 DT, 콘솔 stdout-path.
  1. 도전 과제: EDK2 Secure Boot 펌웨어(§4.3)에서 거부된 랩 Image를 통과시키려면 무엇이 필요한가? (VM에 sbsigntool이 없다면 설치하지 말고 절차만 설계하라.) 정답/힌트: 자체 PK/KEK/db 키 생성 → 빈 VARS(AAVMF_VARS.fd)에 등록(Setup Mode) → sbsign으로 Image 서명 → 재부팅. 또는 Microsoft 서명 shim + MOK 경로.

17. 요약 & 체크리스트#

UEFI는 "펌웨어가 OS 로더에게 주는 표준 C API"이고, 내부적으로는 PI 단계(SEC→PEI→DXE→BDS→TSL→RT)로 동작한다. 부트 대상은 NVRAM의 Boot#### 변수가 가리키는 ESP(FAT)의 PE/COFF 파일이며, Secure Boot는 PK/KEK/db/dbx 키 계층으로 그 파일들의 서명을 검증한다(리눅스는 shim + MOK). arm64 Image는 MZ로 시작하는 PE 헤더와 arm64 부트 헤더를 겹쳐 놓아 booti(오프셋 0)와 UEFI(efi_pe_entry)의 두 입구를 가지며, EFI stub은 cmdline·initrd(LoadFile2)·DTB(config table 또는 빈 DTB)를 모아 ExitBootServices() 후 같은 primary_entry로 들어간다. 하드웨어 설명은 UEFI와 별개의 축으로, 서버는 ACPI(_HID, AML), 임베디드·Jetson은 DT(compatible)를 쓰고, 같은 커널이 dt_is_stub() 판단으로 둘 중 하나를 고르며 드라이버는 of_match_table/acpi_match_table로 각각 매칭된다. U-Boot는 EBBR을 위해 UEFI 바깥 인터페이스를 구현해 bootefi·bootmgr로 배포판 이미지를 부팅한다.
