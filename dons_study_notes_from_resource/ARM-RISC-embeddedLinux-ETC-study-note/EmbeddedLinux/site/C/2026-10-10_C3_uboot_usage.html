0. 큰 그림 — 이게 왜 필요한가#

Don의 SSD 컨트롤러를 떠올려 보자. 전원이 들어오면 ROM 코드가 NAND(또는 SPI NOR)에서 부트로더를 읽고, 부트로더가 DRAM을 초기화하고, 메인 펌웨어 이미지를 찾아 CRC를 확인한 뒤 엔트리 포인트로 점프했다. 개발 중에는 UART에 "디버그 셸"이 있어서 레지스터를 읽고 쓰고, 이미지를 다른 슬롯에서 올려 보았다.

U-Boot는 그 부트로더 + 디버그 셸을 Linux용으로 일반화한 것이다. 하는 일은 딱 네 가지로 요약된다.

  1. 보드를 "Linux를 올릴 수 있을 만큼" 초기화한다 (DRAM, 시리얼, 스토리지·네트워크 드라이버).
  2. 커널(Image), Device Tree(DTB), initramfs를 어딘가(SD/eMMC/USB/네트워크)에서 DRAM의 정해진 주소로 읽어 온다.
  3. 커널에 넘길 정보(커널 명령줄 bootargs, initrd 위치)를 DTB의 /chosen 노드에 써 넣는다.
  4. Linux arm64 부트 프로토콜대로 레지스터를 맞추고(x0 = DTB 물리 주소) 커널로 점프한다.

그리고 이 모든 과정이 콘솔 명령과 환경변수로 노출되어 있어서, 사람이 프롬프트에서 한 줄씩 칠 수도 있고 bootcmd라는 변수에 넣어 자동으로 돌릴 수도 있다. 이 노트는 그 "콘솔에서 하는 일"을 전부 직접 해 본다.

그림 1 — 부트 체인에서 U-Boot의 위치와, 이 노트가 다루는 U-Boot 안의 다섯 가지 일. 이 랩의 -bios u-boot.bin 경로는 TF-A(점선)를 건너뛰고 QEMU가 바로 U-Boot를 실행한다 (TF-A 경로는 C5).

Embedded Linux 엔지니어가 U-Boot 프롬프트를 만나는 장면은 이렇다.

  • 보드 bring-up 첫날: JTAG 대신 U-Boot 콘솔에서 md로 SoC 레지스터(클럭·핀먹스·UART)를 읽어 데이터시트와 비교한다 (§3).
  • 개발 루프: 커널을 고칠 때마다 SD 카드를 뺐다 꽂지 않고, 개발 PC의 TFTP 서버에서 tftp로 받아 부팅한다 (§8).
  • 양산 이미지: 커널·DTB·initramfs를 FIT 하나로 묶고 해시(나중에는 서명)로 검증한다 (§10, C5).
  • 현장 장애: "Starting kernel ... 다음에 아무것도 안 나와요" — 로드 주소 겹침, 잘못된 DTB, initrd 크기 누락을 U-Boot 메시지로 가른다 (§11).

실행 환경: 모든 출력은 Lima VM elinux(aarch64, uname -r = 7.0.0-38-generic) 안에서 공용 랩 /var/lab/의 U-Boot v2026.10(out/u-boot.bin, qemu_arm64 defconfig) → Linux 6.18.55(out/Image) → BusyBox initramfs(out/initramfs.cpio.gz)를 QEMU 10.2.1(-machine virt -cpu cortex-a57 -m 512M, KVM 없는 TCG)로 돌려 얻은 실제 결과다. 시리얼 로그는 expect로 받았고 ANSI escape와 \r만 지웠다. 주소 중 일부(fdtcontroladdr, rng-seed, MAC 이외의 임시 값, 시간)는 실행마다 다를 수 있다. 작업 디렉터리는 VM의 /var/tmp/C3/, 스크립트는 Mac의 ~/.elinux_scratch/C3/.

1. 랩 준비 — QEMU에서 U-Boot 프롬프트 띄우기#

1.1 -bios u-boot.bin이 하는 일#

QEMU virt 머신은 실제 보드처럼 "리셋 벡터 0x0에 펌웨어가 있는" 구조다. -bios u-boot.bin을 주면 QEMU가 U-Boot를 flash 0번(주소 0x00000000)에 올리고 CPU를 거기서 출발시킨다. 즉 U-Boot가 BootROM 다음 단계 부트로더 역할을 한다. 동시에 QEMU는 자기가 만든 Device Tree를 DRAM 맨 앞 0x40000000에 넣어 준다 — 실제 보드라면 U-Boot가 자기 이미지에 DTB를 내장하지만, QEMU는 "하드웨어가 DT를 들고 오는" 특이한 보드다(§6.4에서 이 차이가 실패 원인이 되는 것을 본다).

2. 콘솔 기본 — help · version · bdinfo · coninfo#

2.1 직관 — RTOS 디버그 셸과 같다#

U-Boot 콘솔은 Don이 SSD 펌웨어에 넣었던 UART 디버그 셸과 같은 구조다: 명령 테이블(struct cmd_tbl)에 이름·최대 인자 수·핸들러 함수가 등록되어 있고, 셸이 한 줄을 읽어 토큰으로 나눈 뒤 핸들러를 부른다. 다른 점은 셸이 hush(BusyBox에서 가져온 작은 POSIX 셸 문법: 변수, if, for, &&, ||)라는 것이다(§5).

2.2 예제 2 — 버전, 보드 정보, 콘솔 장치#

무엇을 확인하나: 빌드 정보, DRAM 범위, U-Boot 자신이 어디에 재배치(relocate)되었는지, 콘솔이 어떤 장치에 붙었는지.

출력에서 볼 것:

  • DRAM bank start 0x40000000, size 0x20000000 — QEMU virt의 DRAM은 1 GiB 경계(0x4000_0000)에서 시작해 512 MiB. 이후 모든 로드 주소는 이 범위 안이어야 한다.
  • relocaddr = 0x5f48f000 — U-Boot는 flash(주소 0)에서 출발하지만, 초기화 후 자기 코드를 DRAM 꼭대기로 복사(relocation)하고 거기서 계속 돈다. Don의 SSD 부트로더가 SRAM/TCM으로 자신을 복사하고 점프한 것과 같은 일이다. 그래서 reloc off만큼 링크 주소와 실행 주소가 다르고, U-Boot를 gdb로 디버깅할 때 add-symbol-file u-boot <relocaddr>가 필요하다(C4).
  • lmb_dump_all — LMB(Logical Memory Blocks)는 U-Boot의 간단한 물리 메모리 예약 장부다. 0x5d32dff0-0x5fdfffff(U-Boot 코드·heap·stack)가 no-overwrite로 예약되어 있다. 파일을 이 영역에 읽어 들이려 하면 거부된다 (§11.1에서 확인).
  • fdt_blob = 0x5e34ed80 — U-Boot 자신이 쓰는 DT(control DT). QEMU가 0x40000000에 준 DT를 복사한 것이다. 환경변수 fdtcontroladdr와 같은 값이다.
  • serial addr = 0x09000000 — 콘솔 UART(PL011)의 MMIO 주소. 다음 절에서 직접 찌른다.

3. 메모리와 레지스터 찌르기 — md · mw · mm · cp · cmp#

3.1 문법 — 크기 접미사#

명령뜻예

.b=8비트, .w=16비트, .l=32비트, .q=64비트. 레지스터를 읽을 때는 반드시 레지스터 폭에 맞는 접미사를 쓴다 — 32비트 레지스터를 .b로 읽으면 SoC에 따라 바이트 접근이 버스 에러가 되거나 다른 값이 읽힌다. 숫자는 기본이 16진수다(md.l 40000000도 된다). 0x를 붙이는 습관이 안전하다.

3.2 예제 3 — DRAM에 쓰고, 읽고, 비교하기#

무엇을 확인하나: 메모리 명령의 동작과 little-endian 배치. 0x50000000은 DRAM 중간(U-Boot 예약 영역 아래)의 빈 곳이다.

출력에서 볼 것:

  • 0x40000000의 첫 워드가 edfe0dd0 — DTB 매직 0xd00dfeed는 big-endian으로 저장되므로, little-endian CPU가 32비트로 읽으면 바이트가 뒤집혀 보인다. 두 번째 워드 00001000도 big-endian 0x00100000 = totalsize 1 MiB. fdt header가 해석해 준 값과 맞는다. 즉 QEMU가 DRAM 맨 앞에 DTB를 넣어 둔 것을 메모리 덤프로 증명했다.
  • mw.b 0x50000004 0x55 후 두 번째 워드가 deadbe55 — 주소가 가장 낮은 바이트가 워드의 최하위 바이트(little-endian). Don에게는 익숙한 그림이다.
  • cmp는 첫 불일치에서 멈추고 몇 개가 같았는지 알려 준다. 이미지 두 벌(예: TFTP로 받은 것과 eMMC에서 읽은 것)을 비교할 때 쓴다.

무엇을 확인하나: 주소를 하나씩 넘기며 값을 써 넣는 mm. JTAG 디버거의 memory view에서 값을 고치는 것과 같다.

3.4 예제 5 — PL011 UART 레지스터 직접 읽고 쓰기#

무엇을 확인하나: 지금 콘솔로 쓰고 있는 UART의 레지스터를 U-Boot에서 직접 찌른다. ARM PrimeCell PL011의 레지스터 맵(ARM DDI 0183): UARTDR(0x000, 데이터), UARTFR(0x018, 플래그), UARTCR(0x030, 제어), UARTPeriphID0-3(0xFE0-0xFEC), UARTPCellID0-3(0xFF0-0xFFC).

출력에서 볼 것:

  • PeriphID = 0x11, 0x10, 0x14, 0x00 → part number 0x011(PL011), designer 0x41('A' = ARM; ID1 상위 니블 1 + ID2 하위 니블 4 → 0x41), revision 1. PCellID = 0x0d, 0xf0, 0x05, 0xb1 — 모든 PrimeCell이 공유하는 고정 패턴(0xB105F00D). Linux의 AMBA 버스 드라이버(amba_read_periphid())가 부팅 때 바로 이 값을 읽어 어떤 드라이버를 붙일지 정한다 — §11.4에서 이 읽기가 커널 패닉을 내는 장면을 본다.
  • UARTFR = 0x90 → bit7 TXFE(송신 FIFO 비었음) = 1, bit4 RXFE(수신 FIFO 비었음) = 1. 지금 보낼 것도 받은 것도 없다.
  • UARTCR = 0xb01 → bit0 UARTEN, bit8 TXE, bit9 RXE, bit11 RTS 가 1. UART 켜짐, 송수신 켜짐.
  • mw.b 0x09000000 0x41 → 데이터 레지스터에 'A'(0x41)를 쓰자 화면에 A가 찍혔다(프롬프트 => 앞). 0x0a(LF)를 쓰자 줄바꿈. Don이 bare-metal에서 *(volatile uint32_t *)UART_DR = 'A'로 첫 "hello"를 찍던 것을 셸 명령 하나로 한 것이다.

Don 경험과 연결: 새 SoC bring-up에서 U-Boot md는 "JTAG 없이 쓰는 memory view"다. 클럭 컨트롤러의 PLL lock 비트, 핀먹스 레지스터, PMIC가 붙은 I2C 컨트롤러 상태를 데이터시트와 대조한다. 단, U-Boot는 MMU를 켜고 돌 수 있으므로(arm64 U-Boot는 캐시를 위해 MMU를 켠다) 장치 영역이 device memory로 매핑되어 있어야 레지스터 접근이 안전하다. 보드 코드의 mem_map이 이걸 정한다(C4).

3.5 예제 6 — 없는 장치를 찌르면: U-Boot의 Synchronous Abort#

(레지스터 덤프 중간 x4~x25는 생략했다.)

출력에서 볼 것:

  • esr 0x96000010 — ESR_EL1을 해석하면 EC = 0x25(Data Abort taken without a change in EL — U-Boot 자신이 낸 abort), IL=1, DFSC = 0x10 = synchronous external abort. 즉 "MMU 변환은 됐지만 버스(인터커넥트)가 에러 응답을 돌려줬다". Don이 SSD 컨트롤러에서 본 "AXI DECERR/SLVERR → data abort"와 똑같다.
  • far 0x9030fe0 — 문제의 주소(FAR = Fault Address Register).
  • elr ... (reloc) — 링크 주소 기준 ELR. u-boot.map이나 aarch64-linux-gnu-addr2line -e u-boot 0xa5618로 어떤 함수였는지 찾는다. relocation 때문에 두 줄(링크 주소/실제 주소)을 찍어 준다.
  • Code: ... (b9400343) — 괄호 안이 abort를 낸 명령어 ldr w3, [x26](x26 = 0x9030fe0). U-Boot는 abort 후 리셋한다 — 그래서 세션 로그에 배너가 다시 나온다.

함정: "md 한 번에 보드가 리셋됐다"는 대개 클럭 게이팅된 블록이나 존재하지 않는 주소 접근이다. 블록의 클럭·리셋을 먼저 풀어야(CCM/CRU 레지스터) 그 블록 레지스터를 읽을 수 있다.

4. 환경변수 — printenv · setenv · saveenv, 그리고 env가 사는 곳#

4.1 직관 — "부트로더의 설정 파일 = NVRAM의 key=value 테이블"#

SSD 펌웨어에도 "부팅 파라미터 블록"이 있었을 것이다 — 어느 슬롯의 이미지를 올릴지, 디버그 레벨, 시리얼 번호. U-Boot의 환경변수(environment)가 그것이다: 문자열 key=value 쌍의 집합이고, 부팅 동작 전체가 이 변수들로 조정된다.

  • RAM에는 해시 테이블(env_htab)로 산다. setenv/printenv는 이 RAM 사본만 다룬다.
  • 비휘발 저장소에는 "CRC32 4바이트 + key=value\0key=value\0...\0\0" 블롭으로 산다. 어디냐는 config가 정한다: CONFIG_ENV_IS_IN_MMC(eMMC의 특정 오프셋), ENV_IS_IN_SPI_FLASH, ENV_IS_IN_FAT(uboot.env 파일), ENV_IS_IN_UBI, ENV_IS_NOWHERE(저장 안 함). 이 랩은 CONFIG_ENV_IS_IN_FLASH=y, ENV_ADDR=0x4000000, ENV_SIZE=0x40000(256 KiB) — QEMU virt의 두 번째 NOR flash(pflash1)의 맨 앞이다.
  • 기본값(default env)은 U-Boot 바이너리 안에 컴파일되어 있다. 보드의 .env 파일(board/emulation/qemu-arm/qemu-arm.env)과 config 값(CONFIG_BOOTCOMMAND, BOOTDELAY)에서 만들어진다. 저장소의 CRC가 틀리면(처음 부팅, 지워진 flash) 이것을 쓴다 — 배너의 bad CRC, using default environment가 그 뜻이다.

그림 2 — 환경변수의 세 장소와 수명주기. 부팅 때 저장소에서 RAM으로 읽고(CRC가 틀리면 내장 기본값), 콘솔 명령은 RAM만 바꾸며, saveenv가 RAM 사본을 저장소에 쓴다. Linux에서는 fw_printenv/fw_setenv가 같은 저장소를 직접 읽고 쓴다.

5. 변수 · run · 스크립트 — U-Boot를 프로그래밍하기#

5.1 hush 문법 한 장 요약#

U-Boot 콘솔은 hush 셸이다. 알아야 할 것은 다섯 가지뿐이다.

  • ${name} — 변수 확장. 확장은 명령이 실행될 때 일어난다. setenv a '${b}'처럼 작은따옴표로 넣으면 ${b}가 문자 그대로 저장되고, run a 때 확장된다.
  • ; — 명령 구분. 그래서 setenv x 'cmd1; cmd2'로 여러 명령을 변수에 담는다(작은따옴표 필수 — 없으면 ;에서 setenv가 끝난다).
  • run var1 var2 — 변수의 내용을 명령으로 실행. 함수 호출과 같다.
  • if test ...; then ...; else ...; fi, for i in ...; do ...; done, &&, || — 셸과 같다. 명령의 반환값이 0이면 성공.
  • setexpr — 산술·문자열 연산 결과를 변수에. echo $?로 직전 명령의 반환값.

  • bootz는 32비트 ARM zImage용, booti는 arm64/RISC-V Image용, bootm은 legacy uImage와 FIT용이다.
  • 2번째 인자의 ${filesize}는 직전에 읽은 파일의 크기다. 그래서 initrd를 마지막에 읽어야 한다. 커널을 나중에 읽으면 filesize가 커널 크기가 되어, 커널은 initramfs 뒤의 쓰레기까지 풀려고 한다.
  • DTB 인자는 QEMU에서만 ${fdt_addr}(QEMU가 준 DT)이다. 실제 보드에서는 보통 load mmc 0:1 ${fdt_addr_r} imx8mp-sensorkit.dtb 후 ${fdt_addr_r}를 쓴다. 3번째 인자를 아예 생략하면 U-Boot는 fdtcontroladdr의 control DT를 넘길 수 있는데, 이것은 "U-Boot용으로 다듬어진 DT"라서 커널이 기대하는 노드와 다를 수 있다 — 양산 보드에서는 커널 트리에서 빌드한 DTB를 명시적으로 넘기는 것이 원칙이다.

6.4 DRAM 지도 — 누가 어디에 놓이나#

그림 3 — 이 랩의 DRAM 배치. 왼쪽은 주소와 환경변수 이름, 가운데는 내용, 오른쪽은 누가 왜 그곳을 쓰는지. 파일을 읽어 오는 곳(*_addr_r)과 커널에 실제로 넘어가는 곳(위쪽 꼭대기로 옮긴 DTB·initrd 사본)이 다르다는 것이 핵심이다.

booti 출력의 이 두 줄이 그림의 아래쪽 화살표다:

U-Boot는 기본적으로 initrd와 DTB를 DRAM 꼭대기 쪽(U-Boot 자신 바로 아래)으로 복사하고, 복사본의 주소를 DT /chosen에 써서 넘긴다. 이유는 (1) 커널이 압축 해제·BSS로 덮어쓸 수 있는 낮은 주소를 피하고, (2) DT를 고칠 여유 공간(/chosen 추가)을 확보하기 위해서다. 위치는 bootm_size·bootm_low·initrd_high·fdt_high 변수로 조정한다. 예를 들어 setenv initrd_high 0xffffffffffffffff(64비트에서 "옮기지 마")로 두면 initrd를 읽은 자리에서 그대로 넘긴다 — 부팅 시간을 몇 ms 아끼는 트릭이지만, 그 자리가 커널이 쓰는 영역과 겹치지 않는다는 것을 직접 보장해야 한다.

로드 주소 고르는 규칙 (실제 보드의 kernel_addr_r 등을 정할 때): ① 커널은 DRAM 시작에서 2 MiB 정렬 + text_offset. ② 커널 영역은 파일 크기가 아니라 image_size(+ 여유)로 잡는다. ③ initrd·DTB·FIT·스크립트는 커널 영역 밖, U-Boot 예약 영역(bdinfo의 LMB reserved) 밖. ④ 압축 커널(Image.gz)을 booti로 풀 때는 kernel_comp_addr_r/kernel_comp_size에 압축본 자리가 따로 필요하다. 커널이 커지면(드라이버 추가) ②가 깨져 initrd와 겹친다 — §11.2.

9. Standard boot — bootcmd · bootflow · extlinux.conf#

9.1 직관 — "어떤 장치에서 무엇을 부팅할지 U-Boot가 찾게 하기"#

예전 보드는 bootcmd에 손으로 쓴 스크립트(run mmcboot || run netboot)를 넣었다. 보드마다 제각각이라 배포판(Fedora, Debian, Yocto)이 하나의 이미지로 여러 보드를 부팅하기 어려웠다. 그래서 나온 것이:

  • distro boot (2016~): config_distro_bootcmd.h의 거대한 env 스크립트(distro_bootcmd, scan_dev_for_boot ...)가 boot_targets 순서대로 장치를 훑으며 extlinux/extlinux.conf나 boot.scr를 찾는다.
  • standard boot (bootstd) (2022~, 현재 기본): 같은 일을 C 코드 + driver model로 한다. 핵심 개념 세 가지:
  • bootdev — 부팅 가능한 장치(MMC, USB, virtio, 이더넷, QEMU fw_cfg ...).
  • bootmeth — 부팅 방법(extlinux, script, efi, efi_mgr, pxe, qfw ...). 장치에서 무엇을 찾을지.
  • bootflow — bootdev × bootmeth 조합으로 찾아낸 "부팅 가능한 것 하나". bootflow scan이 목록을 만들고 bootflow boot가 실행한다.

이 랩의 bootcmd=bootflow scan -lb = "목록을 찍으면서(-l) 훑다가 찾는 대로 부팅 시도(-b)".

그림 4 — U-Boot의 autoboot 결정 흐름. env를 읽고, 카운트다운 중 키가 없으면 bootcmd를 실행한다. standard boot는 global bootmeth(efi_mgr)를 먼저 시도한 뒤 boot_targets 순서로 bootdev를 훑고, 각 파티션에서 bootmeth 순서(extlinux → script → efi ...)로 부팅할 것을 찾는다. 하나가 실패하면 다음 후보로 넘어간다.

10. FIT 이미지 — 커널 + DTB + initrd를 하나로, 해시까지#

10.1 직관 — Don의 "펌웨어 패키지 헤더"#

SSD 펌웨어 업데이트 파일을 떠올려 보자. 여러 구성요소(부트로더, 메인 FW, 설정 테이블)를 하나로 묶고, 각각의 길이·로드 주소·CRC(나중에는 서명)를 헤더에 적고, 부트로더가 헤더를 보고 검증·배치했다. FIT(Flattened Image Tree)가 정확히 그것이다. 특이한 점은 그 "헤더 형식"으로 Device Tree 바이너리 포맷(FDT)을 재사용한다는 것이다 — 그래서 .its 소스는 DTS 문법이고, .itb는 dtc/fdtdump로 열어 볼 수 있는 DTB다.

  • images 노드 아래에 구성요소(kernel, fdt, ramdisk, 펌웨어, FPGA 비트스트림 ...)를 각각 data + 메타데이터(type, arch, compression, load, entry) + hash 서브노드로 둔다.
  • configurations 노드 아래에 "어떤 커널 + 어떤 DTB + 어떤 ramdisk를 함께 부팅할지" 조합을 둔다. 한 이미지에 여러 보드 리비전용 DTB를 넣고 bootm addr#conf-revB로 고를 수 있다.
  • 해시(crc32/sha1/sha256)로 무결성을, 서명(signature 노드 + RSA/ECDSA, U-Boot DT에 공개키)으로 진위를 검증한다 — verified boot(C5, L 모듈).

그림 5 — FIT의 구조. mkimage -f가 .its의 /incbin/으로 지정한 파일들을 하나의 FDT 형식 파일에 넣고 해시를 계산해 채운다. configuration이 이미지들을 이름으로 가리키며, bootm은 configuration을 골라 각 이미지를 검증한 뒤 배치한다.

(각 서브이미지의 속성 반복 출력은 ...으로 줄였다.)

  • Loading Kernel Image to 40400000 — FIT 안의 커널을 load 주소로 복사했다(booti는 제자리 실행이었다).
  • Booting using the fdt blob at 0x5e4c4730 — DTB 데이터 시작 0x4a8c2be4는 8바이트 정렬이 아니라서(libfdt는 정렬된 DTB를 요구한다) U-Boot가 정렬된 곳으로 먼저 옮겼다. 그 뒤는 booti와 똑같이 꼭대기로 복사.
  • bootm ${c3_fit}#conf-1 — #conf-1을 생략하면 default configuration. 특정 이미지만 지정하는 문법(bootm addr:kernel-1 addr:ramdisk-1 addr:fdt-1)도 있다.

왜 FIT를 쓰나 (면접 답변 포인트): ① 커널·DTB·initrd 버전이 항상 짝이 맞는다(원자적 업데이트 단위). ② 해시로 깨진 이미지를 부팅 전에 거부한다. ③ 서명으로 secure boot 체인을 커널까지 잇는다(U-Boot SPL → U-Boot → FIT 모두 서명 검증). ④ 한 이미지에 여러 보드용 DTB를 넣고 configuration으로 고른다. 단점은 이미지를 만드는 단계가 하나 더 생기고, 검증 시간이 든다는 것.

12.3 해석#

  • 디스크 직접 load가 압도적으로 빠르다(43 ms) — QEMU virtio-blk는 호스트 page cache에서 읽으므로 1.5 GiB/s가 넘는다. 실제 eMMC(HS200 ~150 MB/s)라면 40 MiB에 0.3초쯤, SD 카드(~20 MB/s)라면 2초쯤 걸린다. 실제 보드에서는 저장장치 대역폭 × 이미지 크기가 U-Boot 구간을 지배한다.
  • FIT의 대가는 해시 계산이다: 같은 디스크에서 FIT는 3.4초. 읽기는 수십 ms이니, 나머지 3초 이상이 43 MB에 대한 sha256이다(TCG는 ARMv8 Crypto Extension의 SHA 명령을 소프트웨어로 흉내 내고, 이 U-Boot가 그것을 쓰는지도 확인하지 않았다 — 실제 Cortex-A53 하드웨어라면 훨씬 빠르다). 그래도 "보안·무결성은 공짜가 아니다"는 결론은 같다: 양산 보드에서 FIT 검증이 부팅 시간의 큰 덩어리가 되는 일이 실제로 있고, 그래서 해시 대상(커널만? 전부?)과 알고리즘·하드웨어 가속(CAAM, CE)을 고른다.
  • 압축 FIT가 비압축 FIT보다 빠르다(1.2초 vs 3.4초): 해시할 데이터가 43 MB → 15 MB로 줄어든 효과가 gunzip 비용보다 컸다. 저장장치가 느린 실제 보드에서는 이 효과가 더 커진다(읽기도 줄어든다). 반대로 아주 빠른 NVMe + 느린 CPU라면 비압축이 이길 수 있다 — 측정해서 고른다.
  • TFTP는 디스크보다 느리지만 개발 루프에서는 이긴다: 1.7초가 걸려도 SD 카드를 뺐다 꽂는 30초보다 훨씬 빠르다. 그리고 TFTP 속도는 부하에 민감하다 — §8.2 세션은 VM이 다른 빌드로 바빴던 때라 4.6 MiB/s(40 MiB에 약 9초)였다. 같은 측정을 여러 번 해야 하는 이유다.
  • extlinux의 1초는 설정 실수다: timeout 1이 1초 대기가 되었다. 메뉴가 필요 없으면 timeout 0(또는 줄 삭제)으로 바로 부팅한다. 이것이 부팅 시간 최적화(C7)의 전형적인 첫 발견이다 — "기다리는 시간"부터 없앤다(bootdelay, 메뉴 timeout, 없는 장치 스캔, 네트워크 PXE 시도).

13. 커널 안에서는 무슨 일이 일어나나#

13.1 U-Boot 쪽: booti/bootm이 점프 직전에 하는 일#

U-Boot 소스(/var/lab/src/u-boot)에서 경로를 따라가면 이렇다.

bootm(FIT)은 앞부분만 다르다: FIT를 파싱하고 configuration을 골라 해시·서명을 검증한 뒤, 커널을 load 주소로 복사(필요하면 압축 해제)하고 같은 image_setup_linux() → boot_jump_linux()로 합류한다. 그래서 FIT로 부팅해도 "Loading Ramdisk to 5d206000"이 똑같이 찍혔다.

13.2 arm64 부트 프로토콜 — 커널이 기대하는 CPU 상태#

커널 문서 Documentation/arch/arm64/booting.rst가 부트로더에게 요구하는 것:

이 랩의 QEMU는 virtualization을 켜지 않아 CPU가 EL1에서 시작한다 — 그래서 커널이 CPU: All CPU(s) started at EL1, kvm [1]: HYP mode not available이라고 찍었다(§9.4 세션의 커널 로그 — 노트에서는 생략한 부분). 실제 보드에서는 TF-A가 EL3, U-Boot가 EL2에서 돌고 커널을 EL2로 넘기는 것이 보통이다(C5).

13.3 커널 쪽: DT의 /chosen이 커널 변수가 되기까지#

그림 7 — U-Boot 변수가 커널 상태가 되는 경로. U-Boot가 DTB /chosen에 써 넣은 값을 커널이 early boot에서 읽어 boot_command_line(커맨드라인), phys_initrd_start(initramfs), of_root(DT 트리 — /proc/device-tree의 원본)로 바꾼다.

  • arch/arm64/kernel/head.S가 진입 시 x0를 저장하고, arch/arm64/kernel/setup.c의 setup_machine_fdt(__fdt_pointer)가 DTB를 매핑해 검증한다. DTB가 깨졌으면 여기서 멈춘다(콘솔도 없어 무소식 — earlycon도 DT를 못 읽으면 소용없다).
  • drivers/of/fdt.c의 early_init_dt_scan_chosen()이 bootargs를 boot_command_line으로, rng-seed를 엔트로피로(그리고 지움), linux,initrd-start/end를 phys_initrd_start/phys_initrd_size로 가져간다. 커널이 모르는 파라미터(LAB_CMD=...)는 Unknown kernel command line parameters "LAB_CMD=...", will be passed to user space.라고 알리고 init 환경에 넘긴다 — 이 랩의 모든 부팅 로그에 실제로 찍힌다(노트에서는 커널 로그를 생략했다).
  • unflatten_device_tree()가 평평한 DTB를 struct device_node 트리(of_root)로 펼치고, of_platform_default_populate_init()이 compatible이 있는 노드를 platform device로 만든다. §7의 /c3_marker와 §11.4의 pl061@9030000이 정확히 이 경로를 탔다(후자는 AMBA 경로 amba_device_add() → amba_read_periphid()에서 죽었다).

드라이버를 쓸 때 다시 만나는 곳: DT 노드 → platform device → 드라이버의 of_match_table과 compatible 매칭 → probe() (G 모듈). 드라이버가 of_property_read_u32()로 읽는 속성은 바로 U-Boot가 fdt set으로 고칠 수 있는 그 속성이다(D 모듈). 커맨드라인 파라미터는 모듈 파라미터(module_param, <모듈>.<파라미터>=값)로 이어진다(E 모듈).

14.1 센서 키트 bring-up 첫날의 U-Boot 체크리스트#

  4. dhcp; tftp로 개발 PC에서 커널·DTB를 받아 부팅 → 매일의 개발 루프.

14.2 A/B 업데이트와 bootcount#

필드에 나간 드론에서 OTA 업데이트가 실패해 벽돌이 되면 회수 비용이 크다. 그래서 U-Boot env에 boot_slot, upgrade_available, bootcount를 두고(§4.4의 fw_setenv), U-Boot 스크립트가 "업데이트 후 첫 부팅이 N번 실패하면 이전 슬롯으로" 되돌린다. U-Boot의 CONFIG_BOOTCOUNT_LIMIT + bootlimit + altbootcmd가 이 기능이고, Linux 쪽에서 부팅 성공을 확인하면 fw_setenv upgrade_available 0(그리고 bootcount=0)으로 확정한다. SWUpdate·RAUC·Mender가 이 패턴을 쓴다(L 모듈).

14.3 보드 리비전별 DTB 선택#

센서 키트 rev A는 IMU가 I2C, rev B는 SPI라면 DTB가 다르다. 방법: (1) FIT에 DTB 두 개와 configuration 두 개를 넣고 U-Boot가 GPIO strap/EEPROM으로 리비전을 읽어 bootm ${addr}#conf-revB; (2) 공통 DTB + 리비전별 DT overlay(fdtoverlays in extlinux, 또는 fdt apply); (3) U-Boot 보드 코드가 ft_board_setup()에서 노드의 status를 고친다(§7의 fdt set을 C로 하는 것).

14.4 양산 보안 설정#

양산 U-Boot는 콘솔이 공격면이다: md/mw로 메모리를 읽고, setenv bootargs init=/bin/sh로 루트 셸을 얻을 수 있다. 그래서 bootdelay=-2, CONFIG_AUTOBOOT_KEYED(비밀 문자열을 쳐야 멈춤), 환경을 읽기 전용으로(CONFIG_ENV_IS_NOWHERE 또는 env 쓰기 제한 ENV_WRITEABLE_LIST), 서명된 FIT만 부팅(CONFIG_FIT_SIGNATURE + required key) 같은 조치를 한다(C5, L 모듈).

16. 면접에서 이렇게 말한다#

Q. Walk me through how U-Boot boots a Linux kernel on an arm64 board.

A. U-Boot는 DRAM과 콘솔·스토리지 드라이버를 초기화하고 자신을 DRAM 꼭대기로 재배치한 뒤, env를 읽고 bootdelay가 지나면 bootcmd를 실행한다. 요즘은 bootflow scan이 장치(bootdev)와 방법(bootmeth: extlinux, script, EFI, PXE)을 훑어 부팅할 것을 찾는다. 커널 Image, DTB, initramfs를 정해진 주소로 읽고, booti가 Image 헤더를 확인하고 겹침을 검사한 뒤 initrd와 DTB를 안전한 위치로 옮기고 /chosen에 bootargs와 initrd 위치를 써 넣는다. 마지막으로 캐시를 끄고 x0에 DTB 주소를 넣어 커널로 점프한다.

U-Boot initializes DRAM, the console and storage/network drivers, relocates itself to the top of RAM, loads its environment, and after the bootdelay runs bootcmd. On current U-Boot that's standard boot: bootflow scan iterates boot devices and boot methods — extlinux, boot scripts, EFI, PXE — until it finds something bootable. It loads the kernel Image, the DTB and the initramfs into RAM, and booti checks the arm64 Image header, makes sure the regions don't overlap, relocates the initrd and DTB, and writes bootargs and the initrd range into the DT's /chosen node. Then it disables the caches and MMU and jumps to the kernel with x0 holding the physical address of the DTB.

꼬리 질문: "Where does the kernel command line come from?" → bootargs env → fdt_chosen()이 /chosen/bootargs로 → 커널 early_init_dt_scan_chosen().

Q. What's the difference between bootcmd and bootargs?

A. bootcmd는 U-Boot가 실행할 명령(autoboot 때 돌리는 스크립트)이고, bootargs는 커널에게 넘길 커맨드라인 문자열이다. bootcmd는 U-Boot 안에서 끝나고, bootargs는 DT /chosen/bootargs를 거쳐 /proc/cmdline이 된다.

bootcmd is the U-Boot command sequence that runs automatically when the autoboot countdown expires — it's how U-Boot decides what to load and boot. bootargs is just a string: the kernel command line. U-Boot writes it into /chosen/bootargs in the device tree before jumping, and the kernel parses it into boot_command_line, which you then see in /proc/cmdline.

Q. Where is the U-Boot environment stored, and how would you change it from Linux?

A. config가 정한다 — eMMC의 고정 오프셋, SPI NOR 섹터, FAT 파일, UBI 볼륨 등. 형식은 CRC32 + key=value\0 목록이고, redundant 설정이면 두 벌이다. Linux에서는 fw_env.config에 같은 위치를 적고 fw_printenv/fw_setenv로 읽고 쓴다. A/B 업데이트의 슬롯 선택과 bootcount가 이 방식이다.

It depends on the board config — commonly a fixed offset on eMMC or a sector in SPI NOR, sometimes a uboot.env file on FAT or a UBI volume. The format is a CRC32 followed by NUL-separated key=value strings, optionally redundant with two copies. From Linux you use fw_printenv and fw_setenv from libubootenv with an fw_env.config that points to exactly the same device, offset and size. That's how A/B update agents flip the boot slot and manage bootcount.

Q. What is a FIT image and why would you use it over a plain Image plus DTB?

A. FIT는 DTB 형식의 컨테이너로 커널, DTB, initramfs 등을 각각 해시와 함께 담고, configuration으로 조합을 정의한다. 장점은 구성요소 버전이 항상 짝이 맞고, 해시로 손상을 검출하고, 서명으로 verified boot를 구현할 수 있고, 여러 보드용 DTB를 한 이미지에 넣을 수 있다는 것이다. 대가는 검증 시간 — 직접 재 보니 43 MB sha256이 QEMU에서 3초가 넘었다.

A FIT is a container that reuses the flattened device tree format: an images node holds the kernel, DTBs and ramdisk, each with metadata and hashes, and a configurations node defines which combination boots together. You get atomic versioning of kernel+DTB+initrd, integrity checking before you jump, the ability to sign configurations for verified boot, and multiple board variants in one file. The cost is verification time — hashing a 43 MB image took over three seconds in my emulated setup, so in production you pick hash algorithms and hardware acceleration carefully.

Q. The board prints "Starting kernel ..." and then nothing. How do you debug it?

A. 먼저 커널 쪽 콘솔이 살아 있는지 — earlycon을 bootargs에 넣고 console=이 맞는 UART인지 확인한다. 다음으로 U-Boot에서 로드 주소와 크기(image_size 기준 겹침, DTB가 덮이지 않았는지 fdt addr/fdt header), DTB가 이 보드용인지 확인한다. 실제로 하드웨어에 없는 장치가 DTB에 있어서 커널이 PeriphID를 읽다 external abort로 죽는 것을 earlycon으로 잡은 적이 있다. 그래도 안 나오면 JTAG으로 PC를 보고 __log_buf를 메모리에서 덤프한다.

First I make sure I can see kernel output at all: add earlycon and confirm console= matches the right UART, since a crash before the serial driver registers is completely silent. Then I check what U-Boot handed over — load addresses against the Image header's image_size, that the DTB is still valid at the address I pass, and that the DTB actually matches the hardware. I hit exactly that once: the DT described a PL061 that didn't exist, and the kernel took a synchronous external abort reading its peripheral ID; earlycon showed it immediately. If earlycon shows nothing, I attach a debugger and dump the kernel log buffer from memory.

꼬리 질문: "What's earlycon?" → 일반 콘솔 드라이버 전에 최소한의 MMIO 쓰기로 UART에 출력하는 early console. DT stdout-path나 earlycon=pl011,0x9000000 형식.

Q. How do you set up a fast development loop for kernel work on a new board?

A. 개발 PC에 TFTP(필요하면 NFS) 서버를 두고, U-Boot env에 dhcp; tftp kernel; tftp dtb; booti 스크립트를 넣어 리셋만 하면 최신 빌드가 부팅되게 한다. rootfs는 NFS root나 initramfs로. 커널 빌드 → TFTP 디렉터리 복사 → 리셋이 1분 안에 끝난다.

I put a TFTP server — and usually an NFS export for the root filesystem — on my workstation, and store a netboot script in the U-Boot environment: dhcp, tftp the Image and DTB into the standard load addresses, booti. Then iterating is build, copy to the TFTP directory, reset the board. No SD card swapping, and with NFS root I can update user-space binaries without reflashing either.

Q. Why does U-Boot relocate the initrd and DTB before jumping?

A. 커널이 부팅 중 쓰는 낮은 메모리(이미지 뒤의 BSS, 초기 페이지 테이블)와 겹치지 않게 하고, DT를 고칠 여유 공간을 확보하기 위해서다. 위치는 initrd_high, fdt_high, bootm_size로 조정하고, 옮기지 않게 할 수도 있지만 그러면 안전한 배치를 직접 보장해야 한다.

So they end up somewhere the kernel won't clobber during early boot — away from the image and its BSS — and so the DTB has room to grow when U-Boot adds /chosen properties and fixups. You can control or disable that with initrd_high, fdt_high and bootm_size, which saves a copy, but then guaranteeing a safe layout is on you.

17. 직접 해보기#

  1. 개념: bootdelay가 0, -1, -2일 때 각각 어떻게 동작하나? 양산 보드에는 무엇을 쓰고 그 이유는? 정답/힌트: 0 = 기다리지 않지만 이미 눌린 키는 확인, -1 = autoboot 안 함, -2 = 키 확인도 안 하고 바로 부팅. 양산은 -2 또는 AUTOBOOT_KEYED(보안·부팅 시간).
  2. 레지스터: §3.4의 방법으로 QEMU virt의 PL031 RTC(0x09010000)를 md로 읽어 PeriphID를 해독하고, RTCDR(0x000)을 두 번 읽어 초 단위로 증가하는지 확인하라. 정답/힌트: PeriphID0이 0x31이면 part 0x031. md.l 0x09010000 1을 sleep 2 사이에 두 번.
  3. env: §4.4처럼 fw_setenv로 bootcmd를 echo C3-from-linux로 바꾸고, U-Boot가 autoboot 때 그것을 실행하는지 확인하라(ub.exp 없이 timeout 20 qemu ... -drive if=pflash,unit=1,...). 정답/힌트: 카운트다운 후 C3-from-linux가 찍히고 프롬프트로 돌아온다.
  4. 스크립트: boot.cmd를 고쳐 c3_slot 변수가 B이면 파티션 2(ext4)의 /boot/Image를, 아니면 파티션 1을 부팅하게 하라. mkimage를 다시 하는 것을 잊지 말 것. 정답/힌트: if test "${c3_slot}" = "B"; then setenv p 2; setenv prefix /boot/; else setenv p 1; fi 후 load virtio 0:${p} ....
  5. FIT: .its에 configuration conf-2를 추가해 같은 커널 + 다른 커맨드라인용 DTB(/chosen/bootargs를 넣은 DTB)를 쓰고, bootm 0x48000000#conf-2로 부팅해 /proc/cmdline을 비교하라. bootargs env가 비어 있을 때와 있을 때 무엇이 이기나? 정답/힌트: fdt_chosen()은 bootargs env가 있으면 DT 값을 덮어쓴다. env를 setenv bootargs로 지운 뒤 비교.
  6. 관찰: 게스트에서 /proc/device-tree/chosen/의 파일 목록을 보고, U-Boot의 fdt print /chosen(booti 전) 출력과 비교해 누가 무엇을 더하고 지웠는지 표로 정리하라. 정답/힌트: U-Boot가 bootargs, linux,initrd-start/end를 더함. 커널은 rng-seed를 지움(fdt_nop_property).
  7. 측정: extlinux.conf의 timeout을 0으로 바꾸고 §12의 측정을 다시 해 extlinux 막대가 디스크 직접 load 수준으로 내려오는지 확인하라. 정답/힌트: 약 1초가 사라져야 한다. 남는 차이가 bootflow 스캔 비용이다.

19. 요약 & 체크리스트#

U-Boot는 "보드 초기화 + 디버그 셸 + 커널 로더"다. 콘솔에서 md/mw로 메모리·레지스터를 직접 다루고, 환경변수(RAM 해시 테이블 ↔ CRC32 붙은 비휘발 블록 ↔ Linux의 fw_setenv)로 동작을 조정한다. Linux 부팅은 결국 "Image·DTB·initrd를 겹치지 않는 주소로 읽고, /chosen에 bootargs와 initrd 위치를 쓰고, x0 = DTB로 점프"이며, 디스크 load, tftp, extlinux(standard boot), FIT bootm은 모두 이 한 경로의 다른 포장이다. 이 랩에서 측정하니 차이는 전부 U-Boot 구간(읽기·검증·대기)에서 났다: 디스크 43 ms, extlinux 1.05초(메뉴 timeout), 압축 FIT 1.24초, TFTP 1.75초, 비압축 FIT 3.4초(sha256). 실패 메시지(Wrong Ramdisk Image Format, RD image overlaps OS image, Bad Data Hash, FDT_ERR_BADMAGIC)는 각자 원인을 정확히 가리키며, "Starting kernel 후 무소식"은 earlycon으로 보면 대개 DTB와 하드웨어의 불일치나 주소 문제다.
