0. 큰 그림 — 이게 왜 필요한가#

Don이 만든 SSD 컨트롤러를 떠올려 보자. Cortex-R 코어가 리셋되면 ROM 코드가 돌고, ROM이 NAND나 SPI NOR에서 펌웨어를 읽어 서명을 확인한 뒤 점프한다. 펌웨어 안에서는 특권 모드(SVC)와 비특권 모드가 나뉘고, MPU가 영역을 막는다. 여기까지는 "한 세계" 이야기다.

Cortex-A 기반 Linux SoC(i.MX8, AM62, Jetson Orin)는 여기에 두 가지를 더 얹는다.

  • Exception Level(EL) 4단계: EL0(앱) · EL1(OS 커널) · EL2(하이퍼바이저) · EL3(secure monitor). 숫자가 클수록 특권이 높다. Cortex-R의 USR/SVC 구분이 두 층 더 깊어진 것이라고 보면 된다.
  • 두 개의 세계(TrustZone): 같은 코어가 Non-secure 세계(Linux가 사는 곳)와 Secure 세계(키·DRM·지문 같은 비밀이 사는 곳)를 시간 나눠 쓴다. 버스 트랜잭션에 NS 비트가 붙어서, Secure 메모리는 Linux가 아무리 특권을 가져도 읽지 못한다.

이 두 축이 만나는 꼭대기, EL3에는 단 하나의 펌웨어가 상주한다. Arm 레퍼런스 구현이 TF-A(Trusted Firmware-A)의 BL31이다. Linux가 "CPU1 켜 줘", "시스템 꺼 줘", "Spectre 완화 적용해 줘", "보안 세계의 TA 불러 줘"를 요청할 때마다 smc 명령으로 EL3에 들어가고, BL31이 처리해서 돌려준다.

그림 1 — AArch64의 EL × 세계 행렬. Linux는 왼쪽 EL1에 살고, EL3의 BL31을 거쳐야만 오른쪽(보안 세계)으로 넘어갈 수 있다.

Embedded Linux 엔지니어가 이 층을 만나는 장면은 이렇다.

  • SMP bring-up: 새 보드에서 smp: Brought up 1 node, 1 CPU만 뜨고 나머지 코어가 안 켜진다 → DT의 enable-method = "psci", TF-A의 PSCI 구현, 보조 코어가 대기하는 hold pen 주소를 본다 (§4).
  • 전원 관리: poweroff가 안 꺼지거나, suspend가 PSCI_FEATURES에서 거부된다 → BL31의 플랫폼 PM 훅 (§4.5).
  • 보안 요구사항: "부트 체인 전체가 서명돼야 한다", "롤백 공격을 막아라" → TBBR 인증서 트리 + OTP fuse + U-Boot FIT 서명 (§7, L5).
  • TEE 연동: 카메라 영상 암호화 키나 기기 인증 키를 Linux 밖에 두라 → OP-TEE + TA + /dev/tee0 (§6).

실행 환경: 호스트는 Lima VM elinux(aarch64, uname -r = 7.0.0-38-generic). 게스트는 공용 랩 /var/lab의 QEMU 10.2.1 virt 머신(-cpu cortex-a57, TCG 에뮬레이션)에서 TF-A v2.15.0 → U-Boot 2026.10 → Linux 6.18.55 → BusyBox initramfs. TF-A는 /var/lab/src/tfa를 /var/tmp/C5/c5_tfa로 복사해 다시 빌드했고, OP-TEE OS 4.7.0과 Mbed TLS 3.6.6은 이 노트를 위해 /var/tmp/C5에 받아서 빌드했다. 아래 명령은 별도 표시가 없으면 VM 안에서 cd /var/tmp/C5한 상태다. 타임스탬프·주소 일부는 실행마다 다르다.

1. Exception Level과 두 세계 — Cortex-R/M 지식에서 출발하기#

1.1 직관 — "특권 모드가 4층 건물이 되고, 옆에 똑같은 건물이 하나 더 생겼다"#

Cortex-M에서 Don은 Thread mode/Handler mode, privileged/unprivileged를 썼다. RTOS 커널은 privileged Handler mode에서, 태스크는 unprivileged Thread mode에서 돌고, 태스크가 커널 서비스를 원하면 SVC로 예외를 일으켰다. Cortex-R(ARMv7-R)은 USR/SVC/IRQ/FIQ/ABT/UND/SYS 모드가 있었다.

AArch64는 이것을 숫자 하나(EL)로 정리했다. 예외가 나면 같은 EL이나 더 높은 EL로만 올라가고, ERET으로만 내려온다. 그리고 각 EL로 올라가는 "문" 명령이 따로 있다.

핵심 차이는 마지막 줄이다. Cortex-A에서는 Linux가 첫 번째 소프트웨어가 아니고, Linux가 도는 동안에도 Linux보다 높은 곳에 펌웨어가 살아 있다. SSD 펌웨어에서 "부트로더는 점프하고 사라진다"였다면, 여기서는 BL31이 사라지지 않는다.

1.3 왜 EL3 펌웨어가 따로 있어야 하나#

  1. 세계 전환은 누군가 해야 한다. SCR_EL3.NS 비트는 EL3에서만 쓸 수 있다. Linux(NS-EL1)와 OP-TEE(S-EL1) 사이를 오가려면 둘 다 믿는 제3자가 레지스터를 저장·복원하고 세계를 바꿔야 한다. 그게 secure monitor다.
  2. 전원·리셋은 보안 문제다. CPU 전원을 끄고 켜는 레지스터, 시스템 리셋, DRAM 컨트롤러 설정을 Linux가 직접 만지면, Linux를 장악한 공격자가 보안 세계 코어를 끄거나 메모리를 덮어쓸 수 있다. 그래서 이런 레지스터는 Secure 전용으로 두고, Linux는 EL3에 표준화된 요청(PSCI)만 보낸다.
  3. 표준 인터페이스로 커널을 SoC에서 분리한다. PSCI 덕분에 arm64 mainline 커널은 SoC마다 "코어 켜는 코드"를 갖지 않는다. 32-bit ARM 시절에는 arch/arm/mach-<soc>/platsmp.c가 SoC마다 있었다. 지금은 DT에 enable-method = "psci" 한 줄이면 끝이다.
  4. CPU 에라타·Spectre 완화. 일부 완화는 EL3에서만 할 수 있는 설정(예: 내부 레지스터 비트)이 필요해서 SMCCC_ARCH_WORKAROUND_1 같은 SMC로 노출된다(§5에서 직접 호출한다).

1.4 코드로 확인 — BL33이 EL1로 들어가나 EL2로 들어가나#

TF-A의 디버그 로그는 다음 단계로 넘어갈 때 SPSR를 찍는다. SPSR의 하위 4비트 M[3:0]이 "ERET하면 어느 EL로 가는지"다: 0b0101(5)=EL1h, 0b1001(9)=EL2h, 0b1101(0xd)=EL3h. 같은 펌웨어를 QEMU의 virtualization=on 유무만 바꿔 부팅했다.

출력에서 볼 것: 세 개의 SPSR은 순서대로 BL2 진입(0x3c5 = S-EL1), BL31 진입(0x3cd = EL3), BL33 진입이다. EL2가 없으면 BL33(U-Boot)은 0x3c5로 NS-EL1에 들어가고 Linux도 EL1에서 시작해 KVM을 못 쓴다. EL2가 있으면 BL31이 0x3c9(EL2)로 넘기고, Linux가 EL2에서 시작해 KVM이 켜진다. 위쪽 4비트 0x3c0은 DAIF(인터럽트 마스크) 4개가 모두 켜진 상태다. (출력의 ---- (2) ---- 줄은 두 실행을 구분하려고 넣은 것이고, kvm 줄 일부는 생략했다.)

함정: "Linux는 EL1에서 돈다"는 반만 맞다. EL2가 있으면 arm64 커널은 EL2에서 시작해, VHE가 있으면 EL2에 머물고 없으면 EL1로 내려가며 EL2에 작은 스텁(nVHE)을 남긴다. 부트로더가 커널을 EL3에서 넘기면 arm64 부트 프로토콜 위반이다(커널 문서 arch/arm64/booting.rst: EL2 또는 non-secure EL1).

2. TF-A 부트 단계 — BL1 · BL2 · BL31 · BL32 · BL33 와 FIP#

2.1 이름부터 — "BL = Boot Loader stage"#

TF-A는 부팅을 번호 붙은 단계로 나눈다. Arm의 TBBR(Trusted Board Boot Requirements) 문서에서 온 이름이다.

2.2 FIP — 펌웨어 묶음 파일#

BL2·BL31·BL32·BL33과 인증서들은 FIP(Firmware Image Package)라는 한 파일로 묶여 플래시에 들어간다. 맨 앞에 목차(ToC)가 있고, 항목마다 UUID·오프셋·크기가 있다. Don이 SSD에서 만들던 "헤더 + 여러 펌웨어 섹션" 이미지와 같은 발상이다. BL1은 FIP의 위치만 알면 되고(이 랩은 PLAT_QEMU_FIP_BASE = 0x00040000), 그 안에서 UUID로 이미지를 찾는다. 소스에서는 이미지마다 image ID라는 번호를 쓴다.

(헤더의 두 열을 한 블록에 나란히 옮겨 적은 것이다.) 부팅 로그의 Loading image id=5는 "BL33을 읽는 중"이라는 뜻이다.

2.3 코드로 확인 — 랩의 release 이미지 부팅 (-smp 4)#

공용 랩의 flash.bin(BL1 + FIP, release 빌드)을 4코어로 부팅해 U-Boot 프롬프트까지 본다.

출력에서 볼 것: release 빌드는 LOG_LEVEL=20(NOTICE)이라 단계 이름만 나온다. 이상한 줄이 하나 있다 — BL2 다음에 BL1: Booting BL31. BL2는 S-EL1에서 돌기 때문에 EL3인 BL31로 직접 점프할 수 없다. 그래서 BL2가 일을 마치면 smc(BL1_SMC_RUN_IMAGE, include/bl1/bl1.h에서 0x4)로 BL1의 예외 벡터에 다시 들어가고, BL1이 BL31로 ERET한다. "낮은 EL은 높은 EL로 점프할 수 없고, 예외로만 올라간다"의 실제 사례다.

2.4 코드로 확인 — TF-A를 INFO 로그로 다시 빌드하기#

로드 주소와 image ID를 보려면 LOG_LEVEL=40(INFO)으로 다시 빌드한다. DEBUG=1이면 assert와 디버그 심볼도 켜진다. 랩 소스는 읽기 전용이므로 복사해서 빌드하고, 출력은 BUILD_BASE로 따로 둔다.

출력에서 볼 것: 빌드는 9초면 끝난다(앞부분 컴파일 줄은 생략). 마지막에 fiptool이 FIP 목차를 찍는다 — BL33(U-Boot)이 0x16F3D0 = 1,504,208바이트로 /var/lab/out/u-boot.bin 크기와 같다. --tb-fw, --soc-fw, --nt-fw는 fiptool create/update에서 그 항목을 넣을 때 쓰는 옵션 이름이다. qemu_fw.bios는 BL1과 FIP를 이어 붙인 파일로, -bios에 그대로 쓴다.

FIP는 언제든 fiptool info로 열어 볼 수 있다. 랩의 release FIP와 비교하면 같은 BL33에 BL2·BL31 크기만 다르다(디버그 코드와 로그 문자열 때문).

2.5 코드로 확인 — 로드 주소 읽기 (BL1 → BL2 → BL31 → BL33 → Linux)#

디버그 빌드로 부팅하면서 -kernel/-initrd를 같이 주면, QEMU가 커널을 fw_cfg 장치에 실어 두고 U-Boot의 qfw bootmeth가 그것을 읽어 부팅한다.

출력에서 볼 것: 디버그 빌드는 CPU 에라타 적용 여부를 BL1·BL31에서 줄마다 찍는데(cortex_a57: CPU workaround for erratum ... was applied/missing), 길어서 grep -v로 뺐다. 남은 줄이 부트 체인의 메모리 지도 그 자체다: BL2 → 0x0e05b000, BL31 → 0x0e090000(id=3), BL33 → 0x60000000(id=5), 커널 → 0x40400000, initrd → 0x44000000. BL31이 "normal world로 나간다"고 말한 다음 줄부터 U-Boot이고, 마지막 Linux 줄은 BL31이 PSCI v1.1과 SMCCC v1.5를 제공한다는 것을 커널이 SMC로 물어 확인한 결과다.

이 주소들은 모두 소스에 정해져 있다. plat/qemu/qemu/include/platform_def.h를 읽으면 로그의 숫자가 계산된다.

(주석의 계산값은 내가 덧붙인 것이다. 로그의 0xe090000, 0xe05b000, 0x60000000과 일치한다 — FW_HANDOFF_SIZE는 이 빌드에서 0이다.)

그림 2 — 부트 단계 시퀀스. 실선은 실행 이동(ERET/SMC), 점선은 "메모리에 복사만 함". BL32(⑦)는 OP-TEE를 넣은 빌드에서만 있다(§6).

2.6 흔한 함정#

  • BL33 주소를 커널 주소로 착각. 0x60000000은 U-Boot가 처음 놓이는 곳일 뿐이고, U-Boot은 곧 RAM 꼭대기로 자기 자신을 옮긴다(relocation, C3·C4). 위 로그의 using memory 0x8054f000-...가 옮겨 간 뒤의 malloc 영역이다.
  • -bios에 fip.bin만 넣기. BL1이 없으면 아무것도 안 뜬다. qemu_fw.bios 또는 flash.bin(BL1 + 0x40000 위치의 FIP)을 쓴다.
  • release 빌드에서 로그가 없다고 멈춘 줄 알기. release는 NOTICE만 찍는다. 원인을 찾을 땐 DEBUG=1 LOG_LEVEL=40으로 다시 빌드하는 게 첫 단계다.

3. "-m 512에서 멈춘다" — 메모리 지도를 소스로 증명하기#

랩 README에는 "secure 경로는 RAM이 넉넉해야 하고 -m 512면 BL2: Built 뒤에 조용히 멈춘다"고 적혀 있다. 추측하지 말고 확인해 보자.

3.1 코드로 확인 — 증상 재현과 예외 추적#

QEMU의 -d int,guest_errors는 게스트가 받은 예외를 로그 파일에 남긴다. JTAG 없이 "어디서 터졌나"를 보는 가장 싼 방법이다.

출력에서 볼 것: 첫 줄은 BL1이 BL2로 ERET한 것(정상). 그다음 BL2(S-EL1)가 주소 0x60000000에 쓰다가 Data Abort를 맞았다. ESR을 풀면: EC=0x25(같은 EL의 data abort), ISS의 WnR=1(쓰기), DFSC=0x10(synchronous external abort) — "그 주소엔 아무것도 없다"는 버스 에러다. Don이 SSD에서 보던 "존재하지 않는 주소에 AXI 쓰기 → SLVERR/DECERR"과 같은 종류다.

3.2 왜 0x60000000인가 — 소스#

QEMU virt의 DRAM은 0x40000000에서 시작한다. -m 512면 DRAM은 0x40000000 ~ 0x5fffffff다. 그런데 TF-A의 qemu 플랫폼은 BL33을 다음 주소에 고정해 둔다.

즉 BL33 로드 주소는 DRAM 시작 + 정확히 512 MB, -m 512의 바로 끝 다음 바이트다. 그리고 "조용히" 멈추는 이유도 소스에 있다. BL2의 예외 벡터(common/aarch64/early_exceptions.S)는 plat_report_exception → plat_panic_handler를 부르는데, qemu 플랫폼은 둘 다 기본(weak) 구현을 쓴다.

에러 메시지 없이 wfi 무한 루프 — Don의 펌웨어에서 HardFault 핸들러가 while(1);이던 것과 똑같다.

3.3 그럼 얼마가 필요한가 — 측정#

README는 "≥ 1057 MB"라고 적었지만, 원인이 "0x60000000 + U-Boot 크기"라면 512 MB를 조금만 넘어도 될 것이다. 7개 크기를 동시에 돌려 봤다(release flash.bin, 18초 제한).

(aborts 수는 18초 동안 리셋을 몇 번 반복했느냐라 실행마다 다르다. 540 근처는 따로 다시 돌려 530·535·545·550은 정상, 540만 재현됨을 확인했다.)

출력에서 볼 것:

  • 513 MB: DRAM 끝이 0x60100000인데 U-Boot은 0x60000000 ~ 0x6016f3d0(1.43 MB)이라 끝부분이 DRAM 밖 → BL2에서 같은 Data Abort. 1 MB로는 모자란다.
  • 514 MB 이상: U-Boot 전체가 DRAM 안에 들어가 U-Boot 프롬프트까지 간다. 600·1024·1056·1057도 모두 정상이었다.
  • 540 MB만 예외: TF-A는 통과하고, U-Boot이 relocation 직후 "Synchronous Abort" handler, esr 0x02000000으로 죽은 뒤 리셋을 반복한다(로그 발췌는 아래). U-Boot은 RAM 꼭대기 쪽으로 자기 코드를 옮기는데, 꼭대기가 처음 로드 위치(0x60000000) 바로 위에 있으면 옮길 자리와 다른 데이터가 꼬일 수 있다. 정확한 원인 분석은 U-Boot 내부(C3·C4)의 일이라 여기선 "여유 없는 메모리 배치는 위험하다"까지만 말한다.

결론: "TF-A 경로는 1057 MB가 필요하다"가 아니라 "BL33을 0x60000000에 놓도록 컴파일됐으니 DRAM이 0x60000000 + BL33 크기를 덮어야 하고, U-Boot relocation 여유까지 생각하면 넉넉히 주는 게 안전하다"가 정확한 설명이다. 랩에서는 계속 -m 1057을 쓴다.

그림 3 — 같은 FIP, 다른 RAM 크기. BL33 로드 주소는 컴파일 시점에 NS_DRAM0_BASE + 0x20000000으로 박혀 있으므로, -m 512에서는 정확히 DRAM 바로 바깥을 가리킨다.

Don 연결: SSD 펌웨어에서 "링커 스크립트의 섹션 주소가 실제 SRAM 크기를 넘어서 부팅 직후 bus fault"를 겪었다면 같은 문제다. 실제 보드에서는 DRAM 크기를 BL2가 DDR 트레이닝 후 알게 되므로, 이런 고정 주소는 BSP의 platform_def.h와 보드 DRAM 구성을 맞추는 작업으로 나타난다(256 MB 보드에 1 GB 가정 TF-A를 올리면 똑같이 멈춘다).

4. PSCI — OS가 펌웨어에게 "전원"을 요청하는 표준 API#

4.1 직관 — 전원 관리용 syscall#

4.2 커널은 PSCI를 어떻게 찾나 — Device Tree#

커널은 PSCI 펌웨어가 있다는 것을 DT로 안다. 두 가지가 필요하다: 루트의 /psci 노드(어떤 명령으로 부를지 method = "smc" 또는 "hvc"), 그리고 각 CPU 노드의 enable-method = "psci". 이 노드를 누가 넣는지가 재미있다 — TF-A 경로에서는 BL2가 QEMU가 만든 DT(0x40000000)를 고쳐서 넣는다.

4.4 secondary CPU는 어떻게 켜지나 — hold pen#

리셋이 풀리면 모든 코어가 동시에 BL1의 리셋 벡터에서 출발한다. BL1은 MPIDR을 보고 "나는 primary(코어 0)인가"를 판단하고, 아니면 plat_secondary_cold_boot_setup으로 보내 hold pen(대기 우리)에 가둔다. qemu 플랫폼에서는 Secure SRAM 맨 앞 4 KB(PLAT_QEMU_HOLD_BASE = 0x0e000000)의 코어별 슬롯을 wfe로 기다리며 계속 확인한다. Don이 멀티코어 MCU에서 "코어 1은 메일박스 레지스터를 폴링하다가 주소가 써지면 점프"로 짰던 것과 정확히 같은 구조다.

그리고 커널 쪽은 이것이 전부다.

그림 4 — PSCI CPU_ON의 실제 동작. SMC 자체는 금방 돌아오고(CPU0), 진짜 일은 CPU1이 EL3에서 자기 초기화를 마친 뒤 Linux의 secondary_entry로 ERET하면서 일어난다. OP-TEE가 있으면 그 사이에 BL32의 CPU on 훅을 먼저 거친다(§6).

4.6 측정 — secondary CPU online/offline 지연#

핫플러그 한 번이 얼마나 걸리는지 재 보자. 실제 제품에서 이 숫자는 "코어를 내려 전력을 아끼는 정책이 지연 요구사항을 깨는가"를 판단할 때 쓴다(N5).

세 가지 펌웨어 구성(QEMU 내장 PSCI / TF-A / TF-A + OP-TEE)에서 LAB_CMD=/c5_hotplug~50으로 하나씩 순서대로 두 번씩 부팅했다(OP-TEE 구성은 §6의 expect 스크립트로 부팅).

그림 5 — 핫플러그 지연(중앙값). 막대 높이는 위 출력의 두 실행 중앙값을 평균한 값이다.

출력에서 볼 것:

  • online이 offline보다 훨씬 빠르다(약 2 ms vs 15~18 ms). offline은 그 코어의 태스크·타이머·IRQ를 다른 코어로 옮기고, RCU 등 여러 hotplug 상태 콜백을 거꾸로 밟은 뒤에야 CPU_OFF를 부르고, 그 후 AFFINITY_INFO로 꺼졌는지 확인한다(아직 ON이면 usleep_range(100, 1000)으로 쉬며 다시 묻는다). 지연의 대부분은 PSCI가 아니라 커널의 hotplug 상태 머신이다.
  • 펌웨어 차이는 작다. QEMU 내장 PSCI(펌웨어 코드 없음)와 TF-A의 차이는 수백 µs 수준이고, 두 실행 사이 흔들림과 비슷한 크기다. OP-TEE를 넣으면 online이 조금 늘어난다(BL31이 BL32의 CPU on 훅을 먼저 부른다 — §6에서 OP-TEE 로그로 확인).
  • 측정 함정: 처음엔 c5_test.sh 안에서 같은 측정을 했는데 online 중앙값이 22~27 ms로 10배 느렸다. 그때는 QEMU 두 개를 동시에 돌렸고 같은 VM에서 다른 작업도 돌고 있었다. TCG 에뮬레이션은 호스트 CPU 경쟁에 매우 민감하다 — 숫자를 비교할 때는 하나씩, 같은 조건에서 돌린다. 그리고 이것은 에뮬레이터 숫자다. 실제 실리콘의 절댓값을 이 그래프로 말하면 안 된다.

4.7 시스템 전원 — SYSTEM_OFF, SYSTEM_RESET, suspend#

LAB_CMD가 끝나면 init이 poweroff -f를 부른다. 커널은 psci_sys_poweroff() → SYSTEM_OFF SMC를 보내고, BL31은 돌아오지 않는다. 디버그 BL31은 끄기 직전에 전원 도메인 지도를 찍는다(c5_test 실행의 마지막 줄들, MPID 0xffff... 빈 슬롯 줄은 생략).

출력에서 볼 것: BL31이 관리하는 PSCI 전원 트리 — 클러스터(Level 1) 2개, 그 아래 CPU 노드. qemu 플랫폼(AArch64)은 PLATFORM_CLUSTER_COUNT = 2, 클러스터당 16코어 슬롯(PLATFORM_CPU_PER_CLUSTER_SHIFT = 4)으로 총 32개 CPU 노드를 잡아 두고, -smp 4라 첫 클러스터의 MPID 0~3만 실제 코어다. 마지막 줄은 qemu_system_off()가 QEMU의 secure GPIO(SECURE_GPIO_BASE = 0x090b0000) 핀을 토글해 QEMU에 전원 차단을 알리는 것이다(ERROR 레벨로 찍히는 것은 그냥 로그 레벨 선택이다). 실제 보드에서는 이 자리가 PMIC에 I2C/SPMI로 "전원 꺼"를 보내는 코드다 — Don이 SPMI 버스를 디버깅했던 바로 그 PMIC다.

suspend는 이 플랫폼에서 지원하지 않는다. §5의 모듈이 PSCI_FEATURES(SYSTEM_SUSPEND64)에 -1(NOT_SUPPORTED)을 받는데, 소스를 보면 이유가 명확하다: qemu_pwr_domain_suspend()의 본문이 assert(0);이다. 실제 SoC의 TF-A는 여기서 DDR self-refresh 진입, 웨이크업 소스 설정을 한다. 리눅스 쪽 CPU_SUSPEND는 cpuidle 드라이버(CONFIG_ARM_PSCI_CPUIDLE)가 DT의 idle-states(arm,idle-state, arm,psci-suspend-param)를 보고 부른다(N5).

5. SMC Calling Convention — Linux에서 EL3를 직접 불러 보기#

5.1 function ID의 구조#

PSCI는 SMCCC(SMC Calling Convention, Arm 문서 DEN0028) 위에 정의된 "서비스 하나"다. SMCCC는 32비트 function ID를 이렇게 나눈다.

OEN(Owning Entity Number)이 "어느 서비스에 보내는 요청인가"다. BL31의 디스패처는 이 6비트로 서비스 핸들러를 고른다. 칩 벤더가 자기 SoC 전용 서비스(예: 클럭 설정, eFuse 읽기)를 만들 땐 SiP(2) 영역을 쓴다. 디코더로 확인해 보자.

출력에서 볼 것: PSCI는 OEN 4, SMCCC 자체 정보는 OEN 0이다. OP-TEE의 실제 TA 호출(CALL_WITH_ARG)만 yielding call(bit 31 = 0)이다 — 오래 걸릴 수 있어서 보안 세계 실행 중에 Linux 인터럽트가 오면 중단됐다가 다시 이어진다. fast call은 원자적으로 끝나야 하는 짧은 요청이다. (이 두 OP-TEE ID는 커널 drivers/tee/optee/optee_smc.h의 매크로 정의에서 계산했다.)

6. OP-TEE — BL32로 들어가는 보안 세계 OS#

6.1 직관 — "Linux 옆의 작은 RTOS"#

OP-TEE OS는 S-EL1에서 도는 작은 OS다. 그 위 S-EL0에서 Trusted Application(TA)이 돈다. TA는 UUID로 구분되는 작은 프로그램으로, 키를 들고 서명하거나, 암호화된 저장소를 관리하거나, 펌웨어 TPM(fTPM)을 구현한다. Linux 앱은 GlobalPlatform TEE Client API(libteec의 TEEC_OpenSession, TEEC_InvokeCommand)로 TA를 부르고, 커널의 optee 드라이버가 이를 SMC로 바꿔 BL31에 넘기고, BL31의 SPD(Secure Payload Dispatcher, opteed)가 세계를 바꿔 OP-TEE에 전달한다.

Don의 경험으로 치면: SSD 컨트롤러 안에서 암호 엔진과 키를 담당하던 별도 보안 코어(또는 보안 펌웨어 영역)를, 같은 Cortex-A 코어를 시간 나눠 쓰는 별도 OS로 만든 것이다.

그림 8 — OP-TEE 호출 경로. Linux 쪽은 문자 디바이스 + 커널 드라이버라는 익숙한 구조이고(G4), 보안 세계로 넘어가는 유일한 길은 EL3의 SPD다.

OP-TEE OS를 QEMU armv8a 플랫폼용으로 빌드한다(1분 정도 걸렸다). 64-bit TA 개발 키트만 만든다.

7. Secure boot — chain of trust를 직접 만들고 깨 보기#

7.1 직관 — "앞 단계가 다음 단계의 지문을 확인하고서야 넘겨준다"#

Don이 SSD에서 했던 "서명된 펌웨어 다운로드"를 떠올리자. 호스트가 새 펌웨어를 보내면 현재 펌웨어가 서명을 확인하고 나서야 NAND에 쓴다. secure boot는 이것을 부팅의 모든 단계에 연쇄로 적용한 것이다.

  1. 뿌리(Root of Trust): 칩 안의 바꿀 수 없는 것 — BootROM 코드와, OTP fuse에 태운 ROTPK(Root Of Trust Public Key)의 해시. 공개키 자체는 커서 fuse에 다 못 넣으므로 해시(SHA-256, 32바이트)만 넣는다.
  2. BL1(또는 BootROM)이 FIP에서 공개키가 든 인증서를 읽고, 그 공개키의 해시가 fuse 값과 같은지 확인한다. 같으면 그 키로 인증서 서명을 검증하고, 인증서 안의 BL2 해시와 실제 BL2 이미지 해시를 비교한다.
  3. BL2가 같은 방식으로 BL31·BL32·BL33을 검증한다.
  4. BL33(U-Boot)이 FIT 이미지 서명으로 커널·DTB·initramfs를 검증한다(L5).
  5. 커널이 dm-verity로 rootfs 블록 해시를 검증한다(L6).

한 고리라도 검증 없이 넘기면 그 아래는 전부 신뢰할 수 없다. 그래서 "chain"이다.

7.2 TBBR 인증서 트리 — 키를 왜 여러 개로 나누나#

TF-A가 구현하는 Arm TBBR(Trusted Board Boot Requirements) CoT는 X.509v3 인증서를 쓴다. 인증서마다 서명용 키가 다르고, 해시·공개키·카운터를 확장 필드(OID 1.3.6.1.4.1.4128.2100.x)에 담는다.

그림 9 — TBBR chain of trust. 화살표는 "이 인증서/키가 다음 것을 보증한다". 점선(BL32)은 이번 TBB 빌드에 OP-TEE를 넣지 않아 생기지 않은 고리다. 아래 주황색은 TF-A 밖, U-Boot가 이어받는 고리다.

키를 층층이 나누는 이유는 운영이다. ROT 개인키는 칩 수명 동안 바꿀 수 없으니 HSM 금고에 넣고 거의 쓰지 않는다. 그 키로는 "Trusted world 키"와 "Non-trusted world 키"만 한 번 서명한다. 이후 BL31 업데이트는 TW 키로, U-Boot 업데이트는 NTW 키로 서명하면 된다. U-Boot 팀이 BL31을 서명할 수는 없고, NTW 키가 새도 BL31·OP-TEE는 안전하다. 마지막의 "key cert → content cert" 두 단도 같은 이유다(content cert의 키는 자주 바꿔도 된다).

7.3 코드로 확인 — Trusted Board Boot 빌드#

TRUSTED_BOARD_BOOT=1 GENERATE_COT=1이면 TF-A가 cert_create 도구를 빌드해 키·인증서를 만들고 FIP에 넣는다. 암호 라이브러리로 Mbed TLS가 필요하다. TF-A v2.15의 default_mbedtls_config.h가 MBEDTLS_CONFIG_VERSION 0x03060600을 요구해서, 처음 받은 3.6.4는 #error "Invalid config version"으로 실패했고 3.6.6으로 바꿔 성공했다.

출력에서 볼 것: FIP에 인증서 6개가 추가됐다. BL2는 0x8204 → 0x133AC로 두 배 넘게 커졌다 — Mbed TLS의 RSA·X.509 파서가 들어갔기 때문이다(BL1도 마찬가지). 부트 ROM 크기 예산이 빠듯한 실제 칩에서는 이것이 진짜 제약이 된다. 그리고 Creating new key: 개발 빌드라 빌드할 때마다 키를 새로 만든다. 제품에서는 절대 이렇게 하지 않는다 — ROT_KEY=, TRUSTED_WORLD_KEY= 같은 변수로 HSM에서 관리하는 고정 키를 넘기거나, 서명은 별도 서명 서버에서 한다.

ROTPK 해시는 어디서 오나? qemu 플랫폼 Makefile이 ROT 키 공개부를 DER로 뽑아 SHA-256을 내고, 그 32바이트를 BL1·BL2에 .incbin으로 박는다. 실제 칩이라면 이 32바이트를 공장에서 OTP fuse에 태운다.

출력에서 볼 것: BL1에 박힌 32바이트와 ROT 키 공개부의 SHA-256이 같다. 이 값이 이 "가상 칩"의 신뢰 뿌리다. 플랫폼은 plat_get_rotpk_info()로 이 값을 ROTPK_IS_HASH 플래그와 함께 넘기고, 인증 모듈은 인증서에서 꺼낸 공개키를 해시해 비교한다.

  • BL1은 BL2보다 id=6(TB FW cert)을 먼저 읽는다. 인증서도 BL2와 같은 주소 0xe05b000에 먼저 올려서 검증한 다음, 그 자리에 BL2를 덮어 올리고 해시를 비교한다(메모리가 귀한 SRAM에서 쓰는 기법).
  • BL31(id 3)을 얻기 위해 BL2는 7 → 9 → 13 → 3 순서로 읽는다: Trusted Key cert(ROT 키로 검증) → SoC FW key cert(TW 키) → SoC FW content cert(BL31 해시) → BL31 본체.
  • BL33(id 5)은 11 → 15 → 5: NT FW key cert(NTW 키) → NT FW content cert(BL33 해시) → U-Boot. 인증서들은 다음 이미지가 놓일 주소(0x60000000)에 잠깐 올라갔다가 덮인다. id 7(Trusted Key cert)은 BL31 경로에서 이미 검증했고, 로그에서도 BL33 경로에서 다시 읽지 않는다.
  • 로그에 "verified" 같은 말은 없다. 검증 실패가 없으면 조용히 진행한다. 실패하면 어떻게 되는지는 7.6에서 본다.

7.8 TF-A 다음 고리 — U-Boot FIT 서명 (L5 미리 보기)#

BL2가 검증한 것은 BL33(U-Boot)까지다. 커널부터는 U-Boot이 검증해야 체인이 이어진다. U-Boot의 verified boot는 이렇게 동작한다.

  • 커널·DTB·initramfs를 하나의 FIT(Flattened Image Tree, .itb)로 묶고, mkimage -k <키 디렉터리> -K u-boot.dtb -r로 configuration 노드에 서명한다. -K는 공개키를 U-Boot의 control DTB의 /signature 노드에 넣고, -r은 그 키를 required로 표시한다.
  • 그 U-Boot 바이너리(공개키 포함)의 해시가 바로 위 nt_fw_content.crt의 .1201 칸에 들어간다. 그래서 "BL2가 U-Boot을 검증 → U-Boot에 박힌 공개키가 FIT를 검증"으로 체인이 이어진다.
  • CONFIG_FIT_SIGNATURE=y인 U-Boot은 bootm 때 서명을 확인하고, 실패하면 부팅을 거부한다. 서명되지 않은 booti/bootz 경로나 U-Boot 콘솔(환경 변수로 bootcmd를 바꾸기)을 열어 두면 체인이 그 자리에서 끊긴다 — 제품에서는 콘솔을 막고 환경을 고정한다.

FIT 이미지 만들기와 서명 실습은 L5에서, rootfs까지 잇는 dm-verity는 L6에서 한다.

8. 커널 안에서는 무슨 일이 일어나나#

그림 10 — 커널이 펌웨어 서비스를 발견하고 쓰는 구조. 모두 "DT 노드 → 드라이버 초기화 → 함수 포인터/디바이스 등록"이라는 드라이버의 기본 패턴이다.

  • PSCI 드라이버 (drivers/firmware/psci/psci.c): 부팅 초기에 psci_dt_init()이 /psci 노드를 찾아 method에 따라 invoke_psci_fn을 __invoke_psci_fn_smc 또는 __invoke_psci_fn_hvc로 정한다. 버전에 맞춰 psci_ops(struct psci_operations: cpu_on, cpu_off, cpu_suspend, affinity_info, migrate_info_type…)를 채우고, psci_init_smccc()가 SMCCC_VERSION을 물어 v1.1 이상이면 arm_smccc_version_init()으로 전역 conduit을 등록한다. §5에서 QEMU가 conduit NONE이었던 이유가 바로 이 함수다.
  • arm64 SMP (arch/arm64/kernel/psci.c): cpu_psci_ops가 cpu_operations 인터페이스(.cpu_boot, .cpu_die, .cpu_kill)를 PSCI로 구현한다. DT의 enable-method = "psci"가 이 ops를 고른다. 다른 값("spin-table")이면 펌웨어 없이 메모리 주소를 폴링하는 방식이다 — §4.4의 hold pen을 커널과 부트로더가 직접 약속하는 형태다.
  • SMCCC 라이브러리 (include/linux/arm-smccc.h, drivers/firmware/smccc/): struct arm_smccc_res(a0~a3), arm_smccc_smc()(asm 함수 __arm_smccc_smc, arch/arm64/kernel/smccc-call.S), 인라인 arm_smccc_1_1_invoke(). Spectre 완화(arch/arm64/kernel/proton-pack.c), SMCCC_ARCH_SOC_ID로 SoC 정보를 sysfs에 내보내는 soc_id 드라이버, 펌웨어 TRNG 등이 이것을 쓴다.
  • SoC 벤더 드라이버의 SiP 호출: 일부 SoC는 클럭·전원·eFuse 같은 Secure 자원을 SiP SMC로만 노출한다. 예: Xilinx ZynqMP 펌웨어 드라이버(drivers/firmware/xilinx/zynqmp.c), Intel Stratix10 서비스 드라이버(drivers/firmware/stratix10-svc.c). 드라이버를 쓰다가 "이 레지스터는 Linux에서 쓰면 abort가 난다"를 만나면, 그 SoC는 SiP 서비스를 거쳐야 한다는 뜻일 가능성이 높다.
  • TEE 서브시스템 (drivers/tee/): tee_core.c가 tee_device를 문자 디바이스(/dev/teeN, G4의 cdev 패턴)로 등록하고, optee/ 드라이버가 SMC 전송을 구현한다. TA를 커널 드라이버로 쓰는 tee_client_* API와 TEE bus(G2의 bus/device/driver 모델)가 있다.
  • reserved-memory: 펌웨어가 쓴 no-map 영역은 memblock에서 빠져서 커널 선형 매핑에도 안 들어간다(F9). BL31이 DRAM에 사는 SoC는 반드시 DT에 그 영역을 예약해야 한다 — 빼먹으면 Linux가 BL31을 덮어쓰고, 다음 PSCI 호출에서 시스템이 사라진다.

드라이버를 쓸 때 다시 만나는 지점: probe에서 펌웨어 서비스 존재를 확인할 때(arm_smccc_1_1_get_conduit()가 NONE인지), 전원 관리 콜백(N6)에서 suspend가 결국 CPU_SUSPEND/SYSTEM_SUSPEND로 내려갈 때, 그리고 보안 키를 다루는 드라이버가 TEE를 통해야 할 때(L6).

9. Embedded 실무에서 다시 보기#

9.1 "CPU1: failed to come online" — 새 보드 bring-up#

예를 들어 센서 키트용 4코어 SoC를 새 보드에 올렸는데 smp: Brought up 1 node, 1 CPU만 나온다. 볼 순서:

  1. dmesg | grep -i psci — PSCI 버전이 찍혔나? 안 찍히면 DT /psci 노드나 method가 틀렸다.
  2. /proc/device-tree/cpus/cpu@N/enable-method가 psci인가, reg(MPIDR)가 실제 코어와 맞나? CPU_ON의 첫 인자가 바로 이 값이다. 클러스터가 있는 SoC는 MPIDR이 0x100, 0x101처럼 생겨서 자주 틀린다.
  3. failed to boot CPU1 (-2)처럼 에러 코드가 찍히면 펌웨어가 INVALID_PARAMETERS로 거부한 것 — TF-A의 PLATFORM_CORE_COUNT, plat_core_pos_by_mpidr()를 본다.
  4. 에러 없이 CPU1: failed to come online이면 SMC는 성공했는데 코어가 Linux로 안 돌아온 것 — 전원 컨트롤러, 코어 리셋 벡터 설정(RVBAR), hold pen 주소, BL31 영역이 DT에서 예약돼 있는지.
  5. TF-A를 DEBUG=1 LOG_LEVEL=40으로 다시 빌드하고 secure UART(있다면)를 본다.

9.2 키 관리와 공장 — fuse는 한 번뿐이다#

secure boot를 켠다는 것은 공장에서 ROTPK 해시를 OTP에 태우고, 서명 안 된 부팅을 막는 fuse(예: i.MX의 HAB "closed" 설정)를 태운다는 뜻이다. 되돌릴 수 없다. 그래서 실무 순서는: (1) 개발 키로 open 상태에서 서명된 이미지가 실제로 검증되는지 로그로 확인(i.MX라면 HAB 이벤트가 없는지) → (2) 제품 키를 HSM에 생성, 서명은 빌드 서버가 아니라 서명 서버에서 → (3) 소량을 close해서 검증 → (4) 생산. 키를 잃어버리면 그 칩에는 영원히 새 펌웨어를 못 넣는다. 국방·로보틱스 회사 면접에서 "키는 누가 어디에 보관하나"를 묻는 이유다.

9.3 OTA와 anti-rollback의 순서#

필드 장비의 A/B 업데이트(L4)에서: 새 이미지 기록 → 재부팅 → 새 이미지가 부팅·헬스체크 통과 → "accepted" 표시 → 그때서야 NV counter 증가. §7.7에서 본 것처럼 TF-A 기본 동작은 "더 큰 카운터의 인증서를 처음 검증한 순간 올린다"이므로, 롤백 가능한 기간을 두려면 이 정책을 설계에 넣어야 한다.

9.4 SoC 전용 펌웨어 서비스를 부르는 드라이버#

예를 들어 센서 키트 SoC가 장치 고유 ID(eFuse)를 Secure 전용으로 두고 SiP SMC로만 읽게 한다면, 드라이버 코드는 이런 모양이 된다(패턴 예시 — 함수 ID와 의미는 SoC 문서에 따라 다르다).

§5의 교훈 두 가지가 들어 있다: conduit NONE을 먼저 확인하고, 결과 a0의 음수를 에러로 본다.

11. 면접에서 이렇게 말한다#

Q. "Walk me through the ARMv8-A exception levels. Where does each piece of firmware run?"

A. EL0은 앱, EL1은 OS 커널, EL2는 하이퍼바이저, EL3는 secure monitor다. 여기에 TrustZone으로 Secure/Non-secure 두 세계가 있다. Linux는 NS-EL1(또는 EL2), 앱은 NS-EL0, OP-TEE 같은 Trusted OS는 S-EL1, TA는 S-EL0, TF-A의 BL31은 EL3에 상주한다. 부팅 중에는 BL1이 EL3, BL2가 S-EL1에서 돌고, U-Boot은 BL33으로 NS-EL1/EL2에서 돈다. 직접 TF-A 디버그 로그의 SPSR 값으로 BL2 0x3c5(EL1), BL31 0x3cd(EL3), BL33 0x3c5/0x3c9(EL1/EL2)를 확인해 봤다.

EL0 is applications, EL1 the OS kernel, EL2 the hypervisor and EL3 the secure monitor, and TrustZone splits the system into a Secure and a Non-secure world. Linux runs at non-secure EL1, or EL2 if virtualization is available; a trusted OS like OP-TEE runs at secure EL1 with trusted applications at secure EL0; and TF-A's BL31 stays resident at EL3. During boot, BL1 runs at EL3, BL2 at secure EL1, and U-Boot is BL33 in the non-secure world. You can see it in the TF-A debug log: the SPSR it programs before each ERET encodes the target level — 0x3c5 is EL1h, 0x3cd is EL3h, 0x3c9 is EL2h.

꼬리 질문: "How is that different from Cortex-M TrustZone?" → Cortex-M은 Secure/Non-secure 상태 전환을 하드웨어가 SG 명령과 NSC 영역으로 직접 하고 EL3 같은 모니터 소프트웨어가 없다. Cortex-A는 세계 전환이 EL3 펌웨어를 거친다.

Q. "Why does ARM need EL3 firmware like TF-A at all? Why can't Linux turn CPUs on by itself?"

A. 세 가지 이유다. 첫째, 전원·리셋·DRAM 보호 같은 레지스터는 보안상 Secure 전용이어야 한다 — Linux가 직접 만지면 Linux를 장악한 공격자가 보안 세계를 무력화할 수 있다. 둘째, 세계 전환은 SCR_EL3를 쓸 수 있는 EL3만 할 수 있다. 셋째, PSCI라는 표준 인터페이스 덕분에 커널이 SoC마다 다른 전원 코드를 갖지 않아도 된다 — arm64 커널은 DT에 enable-method = "psci"만 있으면 어느 SoC에서든 같은 코드로 코어를 켠다.

Three reasons. Power, reset and memory-protection controls need to be secure-only, otherwise a compromised kernel could switch off or corrupt the secure world. Switching worlds requires writing SCR_EL3, which only EL3 can do. And PSCI gives the kernel one standard interface instead of SoC-specific SMP and power code — on arm64 the same cpu_psci_ops boots secondary cores on any SoC as long as the device tree says enable-method = "psci". The cost is that a firmware bug now lives below the kernel, so you need TF-A debug builds and a secure UART in your bring-up toolbox.

Q. "How are secondary cores brought up on an arm64 Linux system?"

A. 리셋 직후 모든 코어가 BL1에서 출발하고, primary가 아닌 코어는 hold pen에서 wfe로 대기한다. Linux의 smp_init이 각 CPU마다 cpu_psci_cpu_boot()를 부르면 PSCI CPU_ON(x0=0xC4000003, x1=대상 MPIDR, x2=secondary_entry 물리주소)이 SMC로 BL31에 간다. BL31은 그 코어의 hold pen 슬롯에 warm entry를 쓰고 SEV한 뒤 SUCCESS를 돌려준다. 깨어난 코어는 BL31에서 자기 EL3 상태를 초기화하고 Linux의 secondary_entry로 ERET한다. QEMU TF-A에서 핫플러그로 직접 확인했고, online은 약 2 ms였는데 대부분이 커널 hotplug 상태 머신 비용이었다.

All cores come out of reset into BL1; the non-primary ones park in a holding pen, waiting with WFE. When Linux brings up CPUs, cpu_psci_cpu_boot issues a PSCI CPU_ON SMC — function ID 0xC4000003 in x0, the target MPIDR in x1 and the physical address of secondary_entry in x2. BL31 writes the warm-boot entry into that core's pen slot, cleans it to memory, sends SEV and returns success. The woken core initialises its EL3 state and ERETs into the kernel's secondary_entry. Hotplug uses the same path: offlining calls CPU_OFF on the dying core and the survivor polls AFFINITY_INFO until it reports OFF, which is the "CPU1 killed (polled 0 ms)" message.

꼬리 질문: "What if the board has no PSCI firmware?" → enable-method = "spin-table": 부트로더가 코어를 메모리 주소 폴링 루프에 두고, 커널이 cpu-release-addr에 주소를 써서 깨운다. 대신 hotplug로 코어를 끌 수 없다.

Q. "What is the SMC Calling Convention? What goes in x0?"

A. Arm이 정한 SMC/HVC 호출 규약이다. x0에 32비트 function ID를 넣는데, bit 31이 fast/yielding, bit 30이 SMC32/SMC64, bit 29:24가 OEN(서비스 주인 — 0 Arm, 2 SiP, 4 PSCI 같은 표준, 50~63 Trusted OS), 하위 16비트가 함수 번호다. 인자는 x1부터, 결과는 x0~x3(v1.2부터 x17까지)로 돌아온다. v1.1부터 결과로 안 쓰는 x4~x17을 보존해서 커널이 인라인으로 싸게 부를 수 있다. 커널에서는 arm_smccc_1_1_invoke()를 쓰는데, 펌웨어가 v1.0이면 conduit이 NONE이라 호출 없이 -1을 돌려준다는 걸 모듈로 확인했다.

SMCCC defines how software calls into EL3 or EL2 with SMC or HVC. x0 holds a 32-bit function ID: bit 31 says fast or yielding, bit 30 SMC32 or SMC64, bits 29 to 24 the owning entity — Arm architecture, SiP, OEM, standard services like PSCI, or a trusted OS — and the low 16 bits the function number. Arguments go in x1 onward and results come back in x0 to x3, extended to x17 from v1.2. Since v1.1 the callee preserves x4 to x17 unless they're results, which is what makes the kernel's inline arm_smccc_1_1_invoke cheap. One gotcha: if firmware only implements SMCCC 1.0, the 1.1 helpers don't issue the call at all and return NOT_SUPPORTED, so drivers check arm_smccc_1_1_get_conduit first.

Q. "Explain secure boot on an ARM SoC. Where is the root of trust, and how do you prevent rollback?"

A. 뿌리는 BootROM과 OTP fuse에 태운 ROTPK 해시다. BootROM 또는 BL1이 인증서의 공개키를 해시해 fuse 값과 비교하고, 그 키로 다음 단계 인증서를 검증하고, 인증서 속 이미지 해시와 실제 이미지를 비교한다. TF-A의 TBBR CoT는 ROT 키 → Trusted/Non-trusted world 키 → 이미지별 key cert → content cert로 나뉘어 있어서, U-Boot 서명 키가 BL31을 서명할 수 없다. U-Boot은 자기 DTB에 박힌 공개키로 FIT 이미지를 검증해 커널까지 체인을 잇는다. 롤백은 인증서의 NV counter와 OTP 카운터를 비교해서 막는다. 직접 FIP의 U-Boot을 1바이트 바꿔 -80(EAUTH)으로 거부되는 것과, 카운터를 올린 인증서가 거부되는 것을 확인했다.

The root of trust is the boot ROM plus a hash of the root public key burned into OTP fuses. The ROM or BL1 hashes the public key in the first certificate, compares it to the fuses, verifies the certificate signature with it, and then compares the image hash in the certificate with the image it loaded. TF-A's TBBR chain splits keys into a trusted-world key and a non-trusted-world key, each delegating to per-image key and content certificates, so the team that signs U-Boot can't sign BL31. U-Boot continues the chain by verifying a signed FIT image with a public key embedded in its own device tree, and dm-verity carries it into the root filesystem. Rollback protection comes from NV counters: every certificate carries a version counter that must be at least the value in OTP, and the OTP counter is bumped when a newer image is accepted. I tested it in QEMU — flipping one byte of U-Boot inside the FIP makes BL2 fail with EAUTH.

꼬리 질문: "What's the difference between secure boot and measured boot?" → secure boot은 검증 실패 시 부팅을 막는다. measured boot은 각 단계의 해시를 TPM PCR이나 이벤트 로그에 기록만 하고, 나중에 원격 증명(attestation)으로 판단한다. 둘은 같이 쓴다.

Q. "What is OP-TEE, and how does a Linux application use a TEE?"

A. OP-TEE는 S-EL1에서 도는 오픈소스 Trusted OS이고, 그 위 S-EL0에서 UUID로 식별되는 TA가 돈다. Linux 앱은 GlobalPlatform Client API(libteec)로 세션을 열고 명령을 보내며, 커널 optee 드라이버가 /dev/tee0를 통해 받은 요청을 공유 메모리와 SMC로 바꿔 EL3의 SPD(opteed)에 넘기면 SPD가 세계를 바꿔 OP-TEE로 전달한다. 파일 저장 같은 일은 tee-supplicant가 /dev/teepriv0로 대행한다. 키 보관, 기기 인증, fTPM, DRM에 쓴다. QEMU에서 OP-TEE 4.7을 BL32로 넣어 /dev/tee0과 DT의 reserved-memory, /firmware/optee 노드가 생기는 것을 확인했다.

OP-TEE is an open-source trusted OS running at secure EL1, hosting trusted applications at secure EL0 identified by UUID. A Linux application uses the GlobalPlatform client API in libteec to open a session and invoke commands; the kernel's optee driver turns that into an SMC with arguments in shared memory, the secure payload dispatcher in BL31 switches worlds, and OP-TEE runs the TA. tee-supplicant serves OP-TEE's requests back into Linux, such as storing encrypted objects in the filesystem. Typical uses are key storage, device identity and attestation, firmware TPM and DRM. When I added it as BL32 in QEMU, OP-TEE patched the device tree with no-map reserved memory and a /firmware/optee node, and the kernel created /dev/tee0 and /dev/teepriv0.

Q. "A new board boots Linux on one core only. How do you debug it?"

A. 먼저 dmesg | grep psci로 PSCI가 감지됐는지 보고, DT의 /psci method와 CPU 노드 enable-method, reg(MPIDR)를 확인한다. failed to boot CPU1 (-2) 같은 에러 코드가 있으면 펌웨어가 인자를 거부한 것이고, 에러 없이 안 올라오면 SMC는 성공했는데 코어가 돌아오지 못한 것이라 전원 컨트롤러·리셋 벡터·BL31 메모리 예약을 본다. TF-A를 디버그 로그로 다시 빌드하고 /sys/kernel/debug/psci로 펌웨어가 무엇을 지원하는지 확인한다.

First check dmesg for the psci probe lines and the device tree: the /psci method, each CPU's enable-method and its reg value, which is the MPIDR passed to CPU_ON — cluster affinity bits are a classic mistake. An error code like "failed to boot CPU1 (-2)" means firmware rejected the arguments; if CPU_ON succeeded but the core never shows up, the problem is after the SMC — power controller, reset vector, or BL31's memory not being reserved so Linux overwrote it. Then rebuild TF-A with DEBUG=1 and LOG_LEVEL=40, watch the secure console, and use /sys/kernel/debug/psci to see which functions the firmware actually advertises.

14. 요약 & 체크리스트#

AArch64는 특권을 EL0~EL3로 나누고 TrustZone으로 두 세계를 나눈다. 두 축의 꼭대기 EL3에는 TF-A의 BL31이 상주하면서, Linux가 smc로 보내는 PSCI(CPU 켜기·끄기, 전원 끄기, 리셋)와 SMCCC 서비스를 처리하고, Trusted OS(OP-TEE)로 가는 세계 전환을 맡는다. 부팅은 BL1(ROM, EL3) → BL2(S-EL1, 다음 이미지 로드·검증) → BL31(EL3 상주) → BL32(OP-TEE) → BL33(U-Boot) → Linux 순이고, 각 이미지의 위치는 플랫폼의 platform_def.h에 고정돼 있어서 RAM 구성과 어긋나면 -m 512처럼 조용히 멈춘다. Linux의 secondary CPU 부팅과 핫플러그는 cpu_psci_ops → psci_ops → arm_smccc_smc → BL31 디스패처 → 플랫폼 PM 훅 → hold pen으로 이어지고, 이 지연의 대부분은 펌웨어가 아니라 커널 hotplug 상태 머신이다. secure boot는 OTP의 ROTPK 해시에서 시작해 TBBR 인증서 트리로 BL2·BL31·BL32·BL33을 검증하고, U-Boot의 FIT 서명이 커널까지 잇는다. 1바이트 변조는 EAUTH(-80)로, 카운터 문제는 NV counter 검사로 거부된다.
