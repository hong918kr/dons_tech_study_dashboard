0. 큰 그림 — "부팅 완료"는 커널이 아니라 PID 1이 정한다#

SSD 펌웨어에서 "부팅 완료"는 명확했다. 리셋 벡터 → C 런타임 초기화 → HW 초기화 → NVMe 컨트롤러 Ready(CSTS.RDY=1). 이 시간은 스펙(예: CAP.TO)으로 정해져 있고, Don은 GPIO 토글과 scope로 구간을 쟀을 것이다.

Linux 보드에서는 "부팅 완료"를 커널이 정하지 않는다. 커널은 드라이버를 probe하고 rootfs를 준비한 다음 유저 공간 프로그램 하나(PID 1, init) 를 실행하고 손을 뗀다. 그 뒤 파일시스템 마운트, 모듈 로드, 네트워크, 센서 데몬, 카메라 파이프라인을 띄우는 건 전부 init의 일이다. 그래서 "부팅 12초"라고 할 때 그 12초는 보통 펌웨어 + 커널 + init이 띄운 유저 공간 셋의 합이고, 셋 중 어디가 큰지 재 보기 전에는 아무것도 줄일 수 없다.

그림 1 — 부트 체인에서 이 노트가 맡는 구간. C1~C5가 펌웨어, C6이 커널 내부, C7은 커널이 /init을 실행한 순간부터 "앱 준비 완료"까지와, 전체 구간의 시간 측정을 다룬다.

이 노트에서 하는 일:

  • PID 1이 무엇을 책임지는지 C로 직접 init을 만들어 확인한다 (exit하면 커널이 panic하는 것까지 실제로 본다).
  • init 구현 세 가지 — 직접 쓴 /init 스크립트, BusyBox init + /etc/inittab, systemd — 를 비교한다. systemd는 VM 호스트(Ubuntu)의 실제 부팅 데이터로 본다.
  • initramfs가 진짜 rootfs(virtio 디스크의 ext4)를 찾아 switch_root하는 과정을 QEMU에서 처음부터 만든다.
  • U-Boot → 커널 → 유저 공간 "READY" 마커까지 전 구간을 재는 하네스를 만들고, 부팅 시간 단축 기법을 하나씩 켜면서 실제로 몇 초가 줄어드는지 잰다.

실행 환경: VM 호스트는 Lima elinux(aarch64, uname -r = 7.0.0-38-generic, systemd 259). 게스트는 공용 랩 /var/lab의 QEMU virt(cortex-a57, 512 MB, KVM 없이 TCG) + Linux 6.18.55 + U-Boot v2026.10 + BusyBox 1.37 static. 작업물은 /var/tmp/C7/에 만들었다. PID·주소·시간은 실행마다 다르다 (단, §4.3의 icount 모드는 일부러 결정적으로 만든 것이다).

1. PID 1이 해야 하는 일#

1.1 직관 — RTOS의 "idle 태스크 + 태스크 매니저"를 유저 공간에 둔 것#

RTOS에서 main()은 태스크를 만들고 스케줄러를 시작하면 다시는 돌아오지 않는다. 돌아오면? 보통 while(1)이나 HardFault다. PID 1도 같다. 커널이 처음 만드는 유저 프로세스이고, 절대 끝나면 안 된다. 다른 점은 PID 1에는 커널이 몇 가지 특별한 역할을 떠넘겼다는 것이다.

그림 2 — PID 1의 여섯 가지 책임. 왼쪽 셋은 "해야 하는 일", 오른쪽 셋은 커널이 PID 1을 특별 취급해서 생기는 규칙이다.

정의:

  • PID 1(init): 커널이 부팅 마지막에 run_init_process()로 실행하는 첫 유저 프로세스. initramfs가 있으면 /init(커널 인자 rdinit=로 바꿀 수 있음), 없으면 root=를 마운트한 뒤 init= 또는 /sbin/init.
  • 좀비(zombie): 끝났지만 부모가 wait()로 종료 상태를 거둬 가지 않아 task_struct가 남아 있는 프로세스(A2). PID와 커널 메모리를 계속 차지한다.
  • 고아(orphan): 부모가 먼저 죽은 프로세스. 커널은 고아의 부모를 PID 1(또는 PR_SET_CHILD_SUBREAPER로 지정된 조상)으로 바꾼다. 그래서 고아가 끝나면 PID 1이 wait()해 줘야 좀비가 사라진다.

1.2 VM 호스트의 PID 1부터 보자#

무엇을 확인하나: 일반 Ubuntu에서 PID 1이 무엇인지, /sbin/init이 실제로 무엇을 가리키는지.

출력에서 볼 것: --switched-root. 이 systemd는 initramfs 안에서 먼저 PID 1로 시작했다가 진짜 루트로 switch_root한 뒤 자기 자신을 다시 exec한 것이다(§3에서 같은 일을 BusyBox로 직접 한다). PID는 끝까지 1로 유지된다.

1.3 PID 1이 exit하면 — "Attempted to kill init!"#

무엇을 확인하나: PID 1이 할 일을 다 했다고 exit하면 무슨 일이 생기는지. 랩 rootfs를 /var/tmp/C7/r_pid1로 복사하고 아래 스크립트를 /c7_exit로 넣은 뒤 rdinit=/c7_exit로 부팅한다.

출력에서 볼 것:

  • exitcode=0x00000300 — wait() 상태 형식이다. 상위 바이트 0x03이 exit 3의 값이다. 시그널로 죽었다면 하위 바이트에 시그널 번호가 찍힌다(예: segfault면 0x0000000b).
  • 콜 스택이 el0_svc → __arm64_sys_exit_group → do_group_exit로 들어간다. 즉 유저가 부른 exit_group syscall 안에서 커널이 panic한다(A1의 svc #0 경로 그대로).
  • 패닉 후 보드는 멈춘다. 실제 제품이라면 panic=5 커널 인자로 5초 뒤 자동 리부트하게 하거나, HW 워치독이 리셋한다. Don의 SSD 경험으로 말하면 "assert 실패 후 무한 루프 → 워치독 리셋"과 같은 구조다.

함정: 셸 스크립트 /init의 마지막 줄에 exec /bin/sh나 exec switch_root …를 빠뜨리면 스크립트가 끝나는 순간 바로 이 panic이다. 또 /init이 set -e를 쓰면 명령 하나만 실패해도 스크립트가 끝나 panic으로 이어진다.

1.4 좀비 회수와 고아 입양 — C로 만든 최소 PID 1#

무엇을 확인하나: PID 1이 wait()를 안 하면 좀비가 쌓이는지, 고아가 정말 PID 1에 입양되는지, 그리고 PID 1이 끝내는 올바른 방법(exit가 아니라 reboot())이 무엇인지.

정적 링크로 빌드한다(initramfs에 libc가 없어도 돌게). VM이 arm64라 크로스 컴파일러가 필요 없다. 커널 인자 중 -- 뒤의 단어는 init의 argv로 넘어간다.

출력에서 볼 것:

  • ppid=0 — PID 1의 부모는 없다(커널의 PID 0, swapper).
  • grandchild pid=56 now ppid=1 — 부모(55)가 먼저 죽자 손자가 PID 1에 입양됐다. 그리고 그 손자가 끝나자 PID 1의 좀비가 됐다(56이 좀비 목록에 있다). PID 1은 자기가 만들지도 않은 프로세스의 좀비까지 치워야 한다.
  • noreap 모드에서는 좀비 5개가 그대로 남는다. 실제 제품에서 이게 몇 주 쌓이면 pid_max에 닿아 fork: Resource temporarily unavailable이 난다.
  • 끝낼 때 exit가 아니라 sync() + reboot(RB_POWER_OFF). 그래서 panic 없이 reboot: Power down으로 끝났다. BusyBox poweroff, systemd systemctl poweroff도 결국 이 syscall이다.

실무 연결: Docker 컨테이너 안에서 셸 스크립트나 Python 앱이 PID 1이 되면 같은 문제가 생긴다. 그래서 tini나 dumb-init 같은 "reap만 하는 작은 init"을 앞에 둔다. 센서 키트의 감독 데몬이 자식 프로세스를 많이 띄운다면 prctl(PR_SET_CHILD_SUBREAPER, 1)로 자기를 subreaper로 지정해 고아를 직접 거둘 수도 있다.

1.5 PID 1에게는 시그널 기본 동작이 없다#

무엇을 확인하나: PID 1에게 kill -9를 보내면 어떻게 되는지. 랩의 LAB_CMD 기능(명령 하나 실행 후 poweroff)으로 아래 스크립트를 실행한다. 이때 PID 1은 랩 initramfs의 /init 셸 스크립트다.

출력에서 볼 것: kill은 성공(rc=0)했지만 PID 1은 멀쩡하다. 커널은 PID 1의 signal_struct에 SIGNAL_UNKILLABLE 플래그를 두고, PID 1이 핸들러를 등록하지 않은 시그널은 같은 PID 네임스페이스 안에서 보낸 경우 버린다(kernel/signal.c의 sig_task_ignored()). SIGKILL·SIGSTOP은 핸들러를 걸 수 없고, 전역 init에게는 아예 전달되지 않는다. SigCgt 비트맵 0x10002는 비트 1(SIGINT=2)과 비트 16(SIGCHLD=17)이다 — 이 셸은 SIGTERM을 잡지 않으므로 SIGTERM도 무시됐다.

그래서 init 구현은 종료 요청을 시그널 핸들러로 받는다. BusyBox init은 SIGUSR1=halt, SIGUSR2=poweroff, SIGTERM=reboot, SIGINT=Ctrl-Alt-Del, SIGHUP=inittab 다시 읽기를 잡는다(§2.2). systemd도 SIGTERM, SIGINT 등을 잡아 각각 다른 동작에 매핑한다.

2.1 직접 쓴 /init — 랩 initramfs의 예#

랩의 /var/lab/build/rootfs/init이 가장 작은 실전 예다.

PID 1의 책임 ①(가상 FS 마운트)과 ⑥(끝나지 않기: 마지막에 exec /bin/sh, 또는 poweroff -f)을 지킨다. 셸이 PID 1이니 ②(좀비 회수)는 셸이 wait하는 자기 자식에 한해서만 된다. 커널 인자를 직접 파싱하는 for a in $(cat /proc/cmdline) 패턴은 initramfs 스크립트에서 매우 흔하다(root=, rescue 같은 인자를 읽는다).

2.2 BusyBox init과 /etc/inittab#

직관: BusyBox init은 "inittab에 적힌 표를 보고 프로세스를 띄우고, 죽으면 다시 띄우고, 끄라는 시그널이 오면 정리하는" 작은 슈퍼바이저다. RTOS에서 태스크 테이블을 돌면서 태스크를 생성하는 부트 코드와 비슷하다.

그림 3 — BusyBox init의 처리 순서. inittab 줄 순서가 아니라 액션 종류 순서(sysinit → wait → once → respawn/askfirst)로 실행된다. 종료 시그널을 받으면 shutdown 액션 → 모든 프로세스에 SIGTERM, SIGKILL → reboot().

형식은 <tty>::<action>:<process>이다. tty 칸이 비어 있으면 /dev/console을 쓴다. 센서 키트를 흉내 낸 inittab을 만든다.

/etc/init.d/rcS(sysinit)와 가짜 센서 데몬:

/etc/passwd에는 root::0:0:root:/root:/bin/sh 한 줄(비밀번호 없음 — 실습용)을 넣고, 랩 rootfs 복사본에 이 파일들을 얹어 cpio로 묶는다. /sbin/init은 ../bin/busybox 심볼릭 링크이고, rdinit=/sbin/init으로 initramfs의 /init 대신 BusyBox init을 PID 1로 쓴다. 대화형 콘솔은 expect로 자동화한다: 로그인 → 데몬을 죽여 respawn 확인 → 셸 exit로 getty respawn 확인 → poweroff로 shutdown 액션 확인.

출력에서 볼 것:

  • C7_READY가 getty보다 먼저 찍혔다 — sysinit이 끝나야 respawn 단계로 간다.
  • 데몬(PID 60)을 죽이자 곧바로 c7_sensord: started pid=69. respawn이 새 PID로 다시 띄웠다. 셸(PID 62)을 exit하자 getty가 다시 login:을 띄웠고, 다시 로그인한 셸은 PID 72다. getty는 login을 exec하고 login은 셸을 exec하므로 PID가 이어진다(login[72] → new shell pid=72).
  • poweroff(=init에 SIGUSR2) → shutdown 액션 두 줄 실행 → Sent SIGTERM/SIGKILL to all processes → reboot(). 그림 3의 아래 줄 그대로다.

함정: respawn 대상이 즉시 죽는 프로그램이면(예: 경로 오타) BusyBox init은 빠르게 다시 띄우기를 반복한다. 로그가 콘솔을 덮어 원인을 못 보는 일이 흔하다. 개발 중에는 respawn 대신 once로 먼저 확인한다.

2.3 systemd — unit, target, 의존성 그래프#

직관: BusyBox init이 "표를 위에서부터 실행"이라면 systemd는 "의존성 그래프를 만들고 병렬로 실행"한다. 각 서비스는 unit 파일로 기술하고, 여러 unit을 묶는 동기화 지점이 target이다. RTOS 비유로는 이벤트 플래그를 기다리는 태스크들 — network-online.target이라는 플래그가 서면 그것을 After=로 기다리던 서비스들이 동시에 출발한다.

핵심 용어:

지시어뜻주의
Wants=같이 시작해 달라 (실패해도 나는 계속)순서는 정하지 않는다
Requires=같이 시작, 그게 실패·중지되면 나도순서는 정하지 않는다
After= / Before=시작 순서끌어오지는 않는다 — 보통 Wants와 같이 쓴다
WantedBy= ([Install])systemctl enable 때 그 target의 .wants/에 링크부팅 때 끌려 들어가는 방법
Type=notify서비스가 sd_notify("READY=1") 해야 "시작됨"진짜 준비 완료 시점을 알려 준다

3. initramfs — 진짜 rootfs를 찾아서 switch_root#

3.1 initramfs가 뭔가#

직관: 부트로더가 커널과 함께 메모리에 올려 주는 작은 임시 루트 파일시스템이다. 커널은 이것을 RAM 위의 rootfs(tmpfs/ramfs)에 풀고 그 안의 /init을 PID 1로 실행한다. 진짜 rootfs(eMMC, NVMe, 네트워크)를 마운트하기 위해 필요한 "준비 작업"을 유저 공간 도구로 할 수 있게 해 주는 early userspace다.

정의:

  • 형식: cpio 아카이브(newc 형식)를 원하는 압축기로 압축한 것. 커널 이미지에 내장(CONFIG_INITRAMFS_SOURCE)하거나 부트로더가 따로 넘긴다(-initrd, U-Boot booti의 두 번째 인자).
  • 옛 initrd(블록 장치 이미지 + /linuxrc + pivot_root)와 다르다. initramfs는 파일시스템 드라이버 없이 커널이 cpio를 직접 tmpfs에 풀기만 한다. 랩 rootfs의 linuxrc 심볼릭 링크는 그 시절 흔적이다.

3.4 switch_root가 실제로 하는 일, pivot_root와의 차이#

BusyBox switch_root NEWROOT NEW_INIT의 동작:

  1. 현재 /가 rootfs(ramfs/tmpfs)인지, 자기가 PID 1인지 확인한다.
  2. initramfs 안의 파일을 전부 지운다(같은 파일시스템 안에서만, 재귀). initramfs는 RAM에 있으니 지워야 메모리가 돌아온다.
  3. chdir(NEWROOT) → mount --move NEWROOT / → chroot(".").
  4. exec NEW_INIT.

왜 pivot_root(2)를 안 쓰나: rootfs는 커널이 처음 만든 특별한 마운트라 떼어 낼(unmount) 수 없다. 그래서 pivot_root가 동작하지 않고, 대신 "내용을 지우고 그 위에 새 루트를 덮는" 방식을 쓴다(커널 문서 ramfs-rootfs-initramfs.rst). 반대로 옛 initrd(블록 장치)나 컨테이너 런타임은 pivot_root를 쓴다. util-linux에도 같은 이름의 switch_root가 있고 동작이 같다.

함정:

  • exec 없이 switch_root를 부르면 PID 1이 아니라서 거부된다.
  • initramfs의 프로그램이 파일을 열어 둔 채(예: 백그라운드 데몬) switch_root하면 그 파일이 지워져도 메모리가 해제되지 않고, 데몬은 사라진 루트를 계속 본다. initramfs에서 띄운 데몬은 넘어가기 전에 정리하거나, systemd처럼 "initrd에서 시작해 새 루트로 넘겨 받는" 규약을 따라야 한다.
  • /dev를 옮기지 않으면 진짜 루트의 init이 콘솔을 못 열 수 있다(can't open /dev/ttyAMA0).

4.2 리셋 이후 시간 — CNTVCT_EL0 읽기#

무엇을 확인하나: 유저 공간에서 arm64 가상 카운터를 직접 읽어 "리셋 이후 경과 시간"을 얻고, /proc/uptime과의 차이로 "커널 이전 시간(펌웨어 + 커널 초기)"을 구한다. Linux arm64는 vDSO 때문에 EL0에서 CNTVCT_EL0 읽기를 허용한다.

§3.3의 출력 마지막 줄 since_reset=1.117 uptime=1.000 pre_kernel=0.117 (cntfrq=62500000 Hz)가 이 프로그램이다. -kernel로 직접 부팅하면 펌웨어가 없으니 pre_kernel은 커널이 시계를 켜기 전까지의 초기 부팅(0.12 s)뿐이다. U-Boot를 거치면 여기에 U-Boot 시간이 더해진다(§4.4).

주의: 이 방법은 카운터가 리셋 때 0에서 시작하고(QEMU는 그렇다), 펌웨어가 CNTVOFF_EL2(가상 카운터 오프셋)를 건드리지 않을 때만 맞다. 실제 SoC에서는 카운터가 전원 도메인과 함께 리셋되는지 데이터시트로 확인하고, 가장 확실한 방법은 여전히 GPIO 토글 + scope(리셋 핀과 "READY" GPIO 사이)다. Don에게 가장 익숙한 그 방법이 업계 표준이기도 하다.

icount: -icount shift=3을 주면 QEMU가 게스트 시계를 실행한 명령어 수로 진행시킨다. shift=3이면 명령어 하나 = 2^3 = 8 ns, 즉 "초당 1억 2500만 명령어짜리 CPU"를 흉내 낸다. 호스트가 바쁘면 실시간으로는 느려지지만 게스트가 보는 시간은 변하지 않는다. 사이클 정확 시뮬레이터에서 사이클을 세는 것과 비슷한 발상이다.

(이 출력은 c7_cntvct를 넣기 전 rcS로 잰 것이라 READY 줄 형식이 짧다.) Run /init이 세 번 모두 2.454~2.458 s — 4 ms 안에서 일치한다. 남은 흔들림(READY 2.75~2.96)은 디스크 I/O 완료처럼 실시간에 묶인 이벤트 때문이다.

icount의 한계(숫자를 읽을 때 꼭 기억할 것):

  • 명령어 수만 센다. 캐시 미스, 분기 예측, 메모리 대역폭, 저장장치 속도, UART 속도는 반영되지 않는다. QEMU의 virtio 디스크와 PL011 UART는 사실상 무한히 빠르다.
  • 125 MIPS는 실제 Cortex-A53/A72 코어보다 한 자릿수 느리다. 절대값이 아니라 설정 간 상대 비교에 쓴다.

효과는 icount −20 ms, 실시간 −60 ms(실시간에서 더 큰 이유: CFI 탐색은 MMIO 접근이 많고, QEMU에서 MMIO 에뮬레이션은 명령어 수가 아니라 호스트 시간을 쓴다). 같은 VM이 붐빌 때 실시간으로 잰 initcall_debug에서는 physmap_init이 282 ms로 1위였다 — 측정 조건에 따라 순위가 바뀐다는 점도 교훈이다.

주의: initcall_blacklist=는 CONFIG_KALLSYMS가 있어야 동작하고(없으면 "initcall_blacklist requires CONFIG_KALLSYMS" 경고), 디버깅용 도구다. 양산에서는 그 드라이버를 Kconfig에서 빼는 것이 정답이다. 그리고 그게 진짜 큰 레버다: 랩 커널은 defconfig(수백 개 SoC의 드라이버 포함)라 840개 initcall과 param_sysfs_builtin_init(빌트인 모듈 수에 비례) 같은 비용을 낸다. 보드에 필요한 드라이버만 남긴 설정은 이 745 ms의 대부분과 커널 크기(42.7 MB → 수 MB, §5.1의 읽기 시간)를 같이 줄인다. 이 노트에서는 커널을 다시 빌드하지 않았으므로 이 효과는 측정하지 않았다.

lpj=: 옛 ARM 보드에서는 Calibrating delay loop가 수백 ms를 먹어 lpj= 지정이 고전적 기법이었다. arm64에서는 아키텍처 타이머 주파수로 계산하므로 이미 건너뛴다.

첫 줄이 기본, 둘째 줄이 lpj=250000을 준 경우다. 둘 다 "skipped"라 효과가 없어야 한다. 표의 K3이 K2보다 50 ms 빠르게 나왔지만 calibration과는 무관하다 — icount에서도 설정을 바꾸면 수십 ms의 차이가 생길 수 있다는 측정 잡음의 크기로 읽어야 한다. 그러니 이 보드에서 50 ms 이하 차이는 "효과 없음"으로 판단한다.

driver_async_probe=: drivers/base/dd.c의 driver_async_probe=drv1,drv2(*이면 전부)는 지정한 드라이버의 probe를 비동기로 돌려 다른 initcall과 겹치게 한다. 효과는 느린 probe(예: 펌웨어 로드·PHY 링크 대기)가 있고 CPU가 여럿일 때 나온다. QEMU 단일 코어·빠른 probe뿐인 여기서는 잡음 수준(K4 ≈ K2)이었다. 드라이버 쪽에서는 probe_type = PROBE_PREFER_ASYNCHRONOUS로 같은 효과를 낸다(G 모듈).

5.3 initramfs 압축 — 일곱 가지 비교#

무엇을 확인하나: 같은 내용의 initramfs를 압축 방식만 바꿨을 때 크기와 "커널이 풀고 /init에 도달하는 시간"이 어떻게 달라지는지. 내용은 랩 rootfs + 커널 모듈(drivers/net, drivers/media의 .ko를 strip --strip-debug)로 23.3 MB — 실제 제품 initramfs에 모듈과 펌웨어가 들어가는 상황을 흉내 낸 것이다. /init은 C7_READY initramfs uptime=…을 찍고 바로 poweroff -f.

VM에는 lz4 명령이 없어서, 자기 폴더의 venv에 pip install lz4를 하고 커널 unlz4가 읽는 legacy 형식(lz4 -l과 같은 것: 매직 0x184C2102 + 8 MiB 블록마다 4바이트 길이)을 직접 쓰는 작은 스크립트를 만들었다.

5.4 유저 공간 단계#

이 노트의 QEMU 보드는 유저 공간이 0.3 s뿐이라 측정할 거리가 적지만, 실제 장비에서는 여기가 보통 가장 크다(§2.4의 VM에서도 userspace 5.0 s > kernel 0.15 s).

  • critical path만 남긴다: "READY"에 필요 없는 서비스는 READY 뒤로 미룬다(systemd라면 After=를 정리하고, 늦은 일은 별도 target이나 timer로). BusyBox라면 rcS에서 &로 백그라운드.
  • 장치 노드: 전체 udev 대신 devtmpfs(이미 커널이 만들어 줌) + 필요한 것만 mdev/정적 규칙.
  • 앱 자체: 거대한 동적 링크 바이너리는 로딩·재배치 비용이 크다(B2·B3). 정적 링크나 라이브러리 정리.
  • 파일시스템: 읽기 전용 squashfs/erofs 루트 + 쓰기 영역 분리는 fsck를 없앤다(J, K 모듈).

6. 양산에서 쓰는 큰 기법들#

부팅 시간이 정말 중요한 제품(차량 후방 카메라 2 s 규정, 드론 전원 투입 후 즉시 링크)은 위의 미세 조정보다 구조를 바꾼다.

  • U-Boot Falcon 모드(SPL OS boot): SPL(DDR 초기화를 하는 작은 1단 로더, C4)이 U-Boot 본체를 건너뛰고 커널을 직접 올린다(CONFIG_SPL_OS_BOOT). 미리 spl export로 만들어 둔 DTB·인자를 쓰고, 특정 키·GPIO가 눌려 있을 때만 U-Boot 본체로 간다. U-Boot 본체의 초기화·스캔 시간이 통째로 사라진다. arm64에서 TF-A를 쓰는 경우 BL31이 BL33으로 U-Boot 대신 커널을 바로 넘기는 구성도 같은 발상이다(C5).
  • 콜드 부팅을 안 한다 — suspend-to-RAM: "전원 버튼 = 부팅"이 아니라 "전원 버튼 = resume"으로 만든다. DRAM self-refresh로 상태를 유지하고 PSCI SYSTEM_SUSPEND(C5)로 들어갔다가, 깨어날 때 드라이버 resume만 돈다. 차량 인포테인먼트가 흔히 쓴다. 대가는 대기 전력과 드라이버들의 suspend/resume 품질(N 모듈).
  • 스냅샷 부팅(hibernation 계열): 부팅이 끝난 메모리 이미지를 저장장치에 써 두고 다음 부팅 때 그 이미지를 복원한다. 저장장치가 빠르고 RAM이 작을수록 유리하다.
  • 타깃에서 계속 잰다: systemd 이미지면 systemd-analyze를 CI의 하드웨어 테스트 단계에서 돌려 회귀를 잡는다. BusyBox 이미지면 /proc/uptime과 CNTVCT_EL0를 READY 시점에 로그로 남긴다. 측정이 CI에 없으면 6개월 뒤 부팅 시간은 반드시 다시 늘어 있다.
  • "READY" GPIO: 앱이 준비되는 순간 GPIO 하나를 올리게 하고, 리셋 핀과 함께 scope·로직 분석기로 찍는다. 펌웨어·커널·유저 공간 어디에도 의존하지 않는 유일한 측정이다.

7. 커널 안에서는 무슨 일이 일어나나#

그림 8 — 커널이 PID 1을 만드는 경로(init/main.c)와 PID 1이 죽을 때의 경로(kernel/exit.c). 6.18.55 소스로 확인했다.

  • start_kernel()(C6)의 끝에서 rest_init()이 kernel_init을 PID 1 커널 스레드로 만든다. 이 스레드는 kernel_init_freeable() 안에서 do_basic_setup() → 모든 initcall(드라이버 등록, probe)을 돌린다. §5.2의 initcall_debug가 재는 것이 바로 이 구간이다.
  • wait_for_initramfs(): 비동기로 풀던 initramfs가 끝나기를 기다린다(§5.3의 "거의 일정한 0.9 s 차이"의 이유).
  • init_eaccess(ramdisk_execute_command): /init(또는 rdinit=)이 실행 가능한지 본다. 없으면 prepare_namespace()(init/do_mounts.c)가 root=를 마운트한다. 이때 rootwait, rootfstype=, root=PARTUUID= 같은 인자가 쓰인다.
  • async_synchronize_full() → free_initmem()("Freeing unused kernel memory: 3264K" 메시지) → run_init_process("/init"). run_init_process는 커널 스레드 안에서 kernel_execve()를 불러, 같은 task(PID 1)가 유저 프로그램으로 바뀐다. 그래서 PID 1의 부모는 0이다.
  • 모두 실패하면 init= → /sbin/init → /etc/init → /bin/init → /bin/sh 순서로 시도하고, 다 안 되면 panic("No working init found. ...").
  • PID 1이 exit_group을 부르면 do_exit()에서 스레드 그룹의 마지막 스레드일 때 is_global_init(tsk)를 검사해 panic("Attempted to kill init! exitcode=0x%08x"). §1.3에서 본 콜 스택(do_group_exit → make_task_dead/vpanic)이 이것이다.
  • 다른 프로세스가 죽으면 exit_notify() → forget_original_parent() → find_child_reaper()가 고아들의 새 부모를 고른다: 가장 가까운 subreaper, 없으면 그 PID 네임스페이스의 init(PID 1). §1.4의 ppid=1.
  • 시그널: signal_struct->flags의 SIGNAL_UNKILLABLE(init에게 설정)이 있으면 sig_task_ignored()가 기본 동작(SIG_DFL)인 시그널을 버린다. §1.5의 kill -9 1이 무시된 이유.

드라이버를 쓸 때 다시 만나는 지점:

  • 내 드라이버의 module_init()은 빌트인이면 이 initcall 목록의 한 줄이다(device_initcall 레벨). probe에서 수백 ms를 기다리면 initcall_debug에 그대로 찍히고 부팅 전체가 늦어진다. 느린 HW 초기화(펌웨어 다운로드, PHY 링크)는 PROBE_PREFER_ASYNCHRONOUS, 지연 작업(workqueue), 또는 -EPROBE_DEFER로 다룬다(F, G 모듈).
  • rootfs가 있는 스토리지 드라이버를 모듈로 만들면 initramfs가 필수가 된다. 빌트인(=y)이면 initramfs 없이 root=로 바로 간다 — 부팅 시간과 이미지 구조를 결정하는 Kconfig 선택이다(K 모듈).
  • 콘솔 드라이버가 nbcon(write_atomic/write_thread)인지에 따라 printk가 부팅을 막는 정도가 달라진다(M 모듈 printk).

장면 4 — BusyBox 센서 노드의 데몬이 죽으면 다시 살아나야 한다. ::respawn:으로 감시하고, 더 엄격하게는 데몬이 /dev/watchdog을 주기적으로 쓰게 해서 데몬이 멈추면(죽지는 않고 hang) HW 워치독이 보드를 리셋하게 한다. systemd라면 WatchdogSec= + sd_notify("WATCHDOG=1")이 SW 단계, RuntimeWatchdogSec=가 HW 워치독 연동이다(L1).

10. 면접에서 이렇게 말한다#

Q. What does PID 1 have to do, and what happens if it exits?

A. PID 1은 커널이 마지막에 실행하는 첫 유저 프로세스다. 가상 파일시스템을 마운트하고 서비스를 띄우고, 고아가 된 프로세스를 입양해 wait()로 좀비를 거둬야 한다. 핸들러가 없는 시그널은 커널이 버리므로 종료 요청도 핸들러로 받는다. PID 1이 exit하면 커널은 "Attempted to kill init!"으로 panic한다. 끄려면 exit가 아니라 sync 후 reboot() syscall을 쓴다.

PID 1 is the first user process the kernel starts. It mounts /proc, /sys and /dev, starts and supervises services, and it inherits every orphaned process, so it must keep calling wait() or zombies pile up. The kernel drops signals PID 1 hasn't installed a handler for, so even SIGKILL is ignored. And it must never exit: if it does, do_exit() sees it's the global init and panics with "Attempted to kill init!". To shut down you sync and call reboot(), you don't exit.

꼬리 질문: "Why do Docker images use tini?" → 앱이 PID 1이 되면 좀비 회수와 시그널 전달을 안 하므로, 그 일만 하는 작은 init을 앞에 둔다.

Q. Why would you use an initramfs? When can you skip it?

A. 진짜 루트를 마운트하기 전에 유저 공간 도구가 필요할 때 쓴다: 스토리지 드라이버가 모듈일 때, dm-crypt 해독이나 dm-verity 검증, LVM, A/B 슬롯 선택, 복구 셸. 그 일을 마치면 switch_root로 진짜 루트의 init에 넘긴다. 스토리지 드라이버가 빌트인이고 암호화가 없으면 root=PARTUUID=… rootwait로 건너뛸 수 있고, 그게 부팅도 더 빠르다.

An initramfs is early userspace: a cpio archive the kernel unpacks into a tmpfs and runs /init from. You need it when mounting the real root requires userspace work: loading storage modules, unlocking dm-crypt with a key from the TPM or OP-TEE, setting up dm-verity, picking an A/B slot, or offering a recovery shell. Then it mounts the real root and exec's switch_root, which deletes the initramfs contents to free the RAM, chroots, and execs the real init, still as PID 1. If the storage driver is built in and there's no encryption, I skip it and boot with root=PARTUUID and rootwait.

꼬리 질문: "Why switch_root and not pivot_root?" → initramfs의 rootfs는 unmount할 수 없는 특별한 마운트라 pivot_root가 안 되고, 내용을 지운 뒤 새 루트를 그 위로 move하고 chroot한다.

Q. BusyBox init or systemd for an embedded product?

A. 서비스가 몇 개뿐이고 rootfs를 수 MB로 줄여야 하면 BusyBox init과 inittab: 작고 동작이 뻔하다. 서비스가 많고 의존성·재시작·워치독·로그 관리가 필요하면 systemd: 의존성 그래프로 병렬 시작하고 systemd-analyze로 부팅을 해부할 수 있다. 대가는 크기와 학습 비용이다.

For a small sensor node with a handful of daemons and a few-megabyte rootfs, BusyBox init with an inittab is enough: sysinit runs rcS, respawn supervises the daemons, shutdown actions clean up. For a gateway with dozens of services I'd use systemd: dependency-ordered parallel startup, Restart= and WatchdogSec= per service, journald, and systemd-analyze to profile boot. The cost is footprint and complexity, which on a Jetson or i.MX8-class board is usually fine.

Q. How would you cut boot time from 12 seconds to 3?

A. 먼저 "부팅 완료"를 정의하고(앱 READY GPIO), 리셋부터 그 GPIO까지 scope로 12 s를 확인한 뒤 펌웨어·커널·유저 공간으로 나눈다. 그다음 큰 것부터: U-Boot는 bootdelay 0, 스캔 대신 직접 부팅, 필요하면 Falcon 모드. 커널은 quiet, initcall_debug로 느린 드라이버를 찾아 Kconfig에서 빼고, 보드용 최소 설정으로 이미지를 줄인다. 유저 공간은 systemd-analyze critical-chain으로 READY까지의 경로만 남기고 나머지를 뒤로 미룬다. 매 단계 다시 재고, 측정을 CI에 넣어 회귀를 막는다. 그래도 안 되면 suspend-to-RAM으로 콜드 부팅 자체를 없앤다.

First I'd define "booted" — say, the app raising a READY GPIO — and measure reset-to-GPIO on a scope, then split the 12 seconds into firmware, kernel and userspace using U-Boot timestamps, the dmesg time of "Run /init", and systemd-analyze. Then I attack the biggest chunk first. In U-Boot: bootdelay=0, boot the known image directly instead of scanning devices, and if needed Falcon mode so SPL loads the kernel. In the kernel: quiet, because a synchronous 115200 console alone can cost over a second; initcall_debug to find slow probes; and a board-specific defconfig instead of the generic one. In userspace: critical-chain to see what's actually on the path to the app, and move everything else after it. I re-measure after each change — in my QEMU lab, bootdelay alone was 2 seconds while lpj did nothing — and I put the measurement in CI. If 3 seconds still isn't reachable, suspend-to-RAM instead of cold boot.

꼬리 질문: "What did you measure that surprised you?" → 압축이 항상 이득이 아니라는 것: 같은 initramfs가 xz로는 14.9 s, lz4로는 2.8 s였다(QEMU icount). 저장장치 대역폭과 CPU 해제 속도를 같이 봐야 한다.

Q. How do you measure boot time accurately?

A. 하나의 기준 시계로 마커를 잡는다. 가장 확실한 건 리셋 핀과 READY GPIO를 scope로 찍는 것이다. 소프트웨어로는 리셋부터 도는 arm64 generic timer를 READY 시점에 읽으면 펌웨어 시간까지 포함된다. dmesg 타임스탬프나 /proc/uptime은 커널이 시계를 켠 뒤부터라 펌웨어가 빠진다. 같은 측정을 여러 번 하고 분포를 본다.

I want one clock for all markers. The gold standard is a scope on the reset line and a READY GPIO. In software, on arm64 I read CNTVCT_EL0 at the READY point — the generic timer counts from reset, so it includes firmware time that dmesg and /proc/uptime miss. For the kernel part I use printk timestamps and initcall_debug, for userspace systemd-analyze. And I repeat runs and look at the spread; in emulation I even used QEMU's icount mode to make the timing deterministic.

Q. A board panics with "Attempted to kill init! exitcode=0x00000100" only sometimes. How do you debug it?

A. exitcode의 상위 바이트가 1이니 PID 1(보통 initramfs /init 스크립트)이 exit 1로 끝났다. "가끔"이면 타이밍 문제일 가능성이 높다 — 루트 장치가 늦게 나타나 mount가 실패하는 경우가 대표적이다. 스크립트에 set -x나 echo를 넣어 어디서 끝나는지 보고, 장치 대기 루프와 실패 시 exec sh를 넣는다.

The exit code is in wait-status format, so 0x100 means PID 1 called exit(1) — no signal involved. Usually that's the initramfs /init script falling off the end after a failed command. "Sometimes" smells like a race: the root device or a USB stick appearing late. I'd add tracing to the script, add a wait loop for the device, never let the script exit — exec a rescue shell on failure — and set panic=5 so the field unit reboots instead of hanging.

Q. What's the difference between Wants=, Requires= and After= in systemd?

A. Wants와 Requires는 "같이 시작하라"는 끌어오기이고 순서는 정하지 않는다. Requires는 상대가 실패하거나 멈추면 나도 멈춘다. After는 순서만 정하고 끌어오지는 않는다. 그래서 보통 Wants= + After=를 짝으로 쓴다.

Wants= and Requires= pull another unit into the transaction; Requires= also stops me if it fails or stops. Neither orders anything. After= only orders startup and doesn't pull anything in. So the normal pattern is Wants=network-online.target plus After=network-online.target. Getting this wrong gives you services that start "too early" only on some boots.

13. 요약 & 체크리스트#

커널은 드라이버를 올리고 rootfs를 준비한 뒤 PID 1 하나를 실행하고 물러난다. PID 1은 가상 FS를 마운트하고, 서비스를 띄우고 감시하며, 고아의 좀비를 거두고, 절대 exit하지 않는다(exit하면 커널이 "Attempted to kill init!"으로 panic한다 — 직접 봤다). 구현은 직접 쓴 /init, BusyBox init + inittab, systemd 중에서 장비 크기와 서비스 수에 맞춰 고른다. initramfs는 진짜 루트를 마운트하기 위한 early userspace이고, 할 일을 마치면 switch_root로 같은 PID 1을 진짜 init으로 바꾼다 — QEMU에서 virtio 디스크의 ext4로 직접 만들었다. 부팅 시간은 리셋부터 READY까지 하나의 시계로 재야 하고(CNTVCT_EL0, GPIO+scope), QEMU에서는 icount로 재현성을 확보했다. 측정해 보니 이 보드에서는 bootdelay 2 s, 커널 압축 4.8 s, initramfs 압축 선택 최대 36 s가 큰 덩어리였고, quiet·initcall_blacklist·lpj·async probe는 수십 ms 이하였다 — 그래서 "재고, 큰 것부터, 다시 잰다"가 유일한 규칙이다.
