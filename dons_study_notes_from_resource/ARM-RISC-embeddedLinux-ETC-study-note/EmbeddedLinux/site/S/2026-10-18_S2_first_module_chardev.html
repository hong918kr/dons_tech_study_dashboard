0. 큰 그림 — 무엇을 만들고, 왜 이 순서인가#

이 노트는 이론 노트가 아니라 작업 지시서다. E·G 노트가 "왜"를 이미 설명했으니, 여기서는 Don이 키보드 앞에서 그대로 따라 치면 같은 결과가 나오는 순서만 쓴다. 이론이 필요한 곳은 노트 ID와 절 번호로만 연결한다.

최종 산출물은 다음과 같다.

  • 드라이버 s2chr.ko 하나(479줄)가 장치 노드 두 개를 만든다. /dev/s2chr0은 seek 가능한 메모리 버퍼(read/write/llseek/ioctl, O_APPEND), /dev/s2chr1은 타이머가 "센서 샘플"을 밀어 넣는 stream FIFO(blocking read, poll)다.
  • 사용자 도구 4개(정적 링크): s2_rw(read/write 계약), s2_ioctl(ioctl 번호와 errno), s2_poll(non-blocking·poll·blocking·EINTR), s2_race(두 프로세스 동시 append).
  • TAP 13 형식 selftest tests/s2chr_selftest.sh 16개 항목, 그리고 일부러 망가뜨린 빌드 10개(bugs/*.patch)로 "테스트가 버그를 잡는다"를 보여 주는 회귀 실행.

1. 준비 — 랩, 저장소 레이아웃, 스크립트 4개#

1.1 전제 조건#

  • Lima VM elinux(호스트 커널 uname -r = 7.0.0-38-generic, gcc 15.2). 모듈은 VM 호스트에 절대 넣지 않는다. 게스트 커널만 쓴다.
  • 랩 커널 /var/lab/out/Image-trace(6.18.55-trace, ftrace·kprobes·BTF 포함)와 그 빌드 트리 /var/lab/out/linux-build-trace(Module.symvers 있음). 게스트는 BusyBox 1.37 initramfs(/var/lab/build/rootfs)를 복사해 우리 .ko와 정적 도구를 넣어 다시 묶는다. S1이 이 랩을 처음부터 만드는 과정이다.
  • 이 커널 설정에서 결과에 영향을 주는 값: CONFIG_DEVTMPFS=y, CONFIG_DYNAMIC_DEBUG=y, CONFIG_DEBUG_FS=y, CONFIG_PREEMPT=y, CONFIG_HZ=250, CONFIG_INIT_STACK_ALL_ZERO=y, CONFIG_HARDENED_USERCOPY 꺼짐, CONFIG_PROVE_LOCKING 꺼짐, CONFIG_LOCALVERSION="-trace". 이 값들이 §6·§5의 버그 증상을 바꾼다(그때 다시 설명한다).
  • QEMU는 KVM 없이 TCG로 돈다. 이 노트의 모든 시간 값은 에뮬레이션 수치이고 실제 보드 숫자가 아니다.

1.2 저장소 레이아웃#

Mac 쪽 ~/.elinux_scratch/S2/s2-chardev/에 git 저장소를 만들고, VM에서는 읽기 전용으로 보이므로 빌드는 VM의 /var/tmp/S2/build에 복사해서 한다.

1.3 빌드 파일 — Kbuild와 Makefile#

무엇을 확인하나: out-of-tree 모듈은 커널 트리의 Makefile을 -C로 부르고 M=으로 우리 디렉터리를 알려 준다(E3 §1.3). 같은 Makefile에서 정적 사용자 도구도 만든다.

W=1은 커널이 기본으로 끈 추가 경고(-Wmissing-prototypes, -Wunused-but-set-variable 등)를 켠다. 이 프로젝트의 규칙은 모든 마일스톤에서 W=1 경고 0개다. 도구를 -static으로 만드는 이유는 BusyBox initramfs에 glibc가 없기 때문이다.

1.4 스크립트 4개 — 빌드, initramfs, 부팅, 버그 빌드#

게스트의 /init은 커널 인자 LAB_CMD=의 ~를 공백으로 바꿔 명령 하나를 실행하고 poweroff -f 한다. 그래서 "부팅 1번 = 시나리오 1개"다. -smp 2는 M7의 race에 필요하고, -no-reboot + panic=1은 M6에서 일부러 낸 커널 패닉이 180초 타임아웃까지 매달리지 않고 1초 뒤 QEMU를 끝내게 한다. 모든 단계의 루프는 이것 하나다.

체크포인트: scripts/ 네 파일과 Kbuild, Makefile이 생겼고 git init이 끝났다. 아직 s2chr.c가 없으니 빌드는 실패한다.

2. M1 — hello 모듈 (init/exit, printk 레벨, modinfo)#

2.1 코드#

무엇을 확인하나: 가장 작은 모듈의 네 부품 — module_init/exit, MODULE_LICENSE, printk 레벨, pr_fmt. 이론은 E3 §1, 레벨과 콘솔은 M1 노트 §1–2.

pr_fmt을 #include보다 먼저 정의해야 모든 pr_*에 s2chr: 접두어가 붙는다. 커널 릴리스는 컴파일 시점 상수(UTS_RELEASE) 대신 실행 중인 커널 값(init_utsname()->release)을 찍었다 — 로드된 커널이 무엇인지가 궁금한 것이기 때문이다.

2.2 빌드 — W=1, 경고 0개#

출력에서 볼 것: BTF [M]은 이 커널이 CONFIG_DEBUG_INFO_BTF_MODULES라서 모듈에도 BTF가 붙는다는 뜻이다(M7 노트의 bpftrace가 모듈 구조체를 읽을 수 있게 된다). vermagic의 6.18.55-trace가 게스트 커널의 uname -r과 정확히 같아야 한다.

2.3 게스트에서 실행#

출력에서 볼 것:

  • quiet로 부팅하면 콘솔 로그 레벨이 4라서 pr_err(3)만 콘솔에 바로 나오고, pr_warn(4)·pr_info(6)는 dmesg에만 있다. 첫 줄이 두 번 보이는 이유다.
  • taint OE = out-of-tree(O, 4096) + unsigned(E, 8192) → 12288. 이 랩은 MODULE_SIG가 강제가 아니라 경고만 낸다(E3 §9).
  • pr_debug는 기본으로 꺼져 있다가, insmod ... dyndbg=+p로 로드 시점에 켜졌다. 마일스톤 M8에서 런타임에 켜는 법을 본다(M1 노트 §4).
  • 주소 0xffffa3e25d1b2000은 KASLR 때문에 부팅마다 다르다.

체크포인트: insmod 후 /sys/module/s2chr/initstate가 live, rmmod 후 bye가 dmesg에 있어야 한다. 커밋하고 git tag m1.

2.4 FAIL-1 재현 — 다른 커널 트리로 빌드한 모듈#

무엇을 확인하나: "같은 6.18.55인데 왜 안 올라가나"의 실제 모습. 같은 소스를 다른 랩 트리 두 개로 빌드해서 Image-trace 게스트에 넣었다.

출력에서 볼 것: 유저가 보는 말은 둘 다 invalid module format(-ENOEXEC)뿐이고, 진짜 이유는 dmesg에만 있다. 그리고 이유가 두 가지로 갈렸다.

  • defconfig 트리(linux-build, vermagic 6.18.55)로 만든 모듈은 vermagic 검사까지 가지도 못했다. trace 설정은 ftrace·kprobes 등으로 struct module이 더 커서, 로더가 ELF 섹션 .gnu.linkonce.this_module의 크기를 실행 중인 커널의 sizeof(struct module)과 비교하는 더 이른 검사에서 거절했다. (linux-build-sec로 빌드한 것도 같은 메시지였다 — 확인함.)
  • RT 트리(6.18.55-rt)는 struct module 크기가 우연히 같아서 그 검사를 통과했고, 고전적인 version magic 메시지가 나왔다(E3 §10.1과 같은 메시지).

고치는 법은 하나다: 장비에 올라간 그 커널의 빌드 트리(.config + Module.symvers)로 빌드한다. BSP를 받으면 uname -r, /proc/config.gz, 벤더가 준 Module.symvers를 먼저 맞춘다.

3. M2 — 모듈 파라미터 (타입, 권한, 범위 검사)#

3.1 코드 (M1에서 바뀐 부분)#

무엇을 확인하나: module_param(이름, 타입, 권한)의 세 번째 인자가 /sys/module/s2chr/parameters/ 파일의 권한이 된다는 것, 그리고 값 검증은 드라이버 책임이라는 것(E3 §5).

secret(권한 0)은 sysfs 파일이 없다는 것을 보여 주는 M2 전용 예시라서 M3에서 지웠다. buf_size는 M4에서 버퍼 크기가 되므로 로드 후 바뀌면 안 된다 → 0444.

3.2 실행#

(bad values 부분은 pr_err가 콘솔과 dmesg에 두 번 찍힌 줄을 하나씩 지웠다.)

출력에서 볼 것:

  • secret은 parameters/에 없다(권한 0). bool은 Y/N으로 보인다.
  • root도 0444 파일에는 못 쓴다. 일반 파일이라면 root는 CAP_DAC_OVERRIDE로 통과하지만, sysfs(kernfs)는 open 시점에 "쓰기 권한 비트나 store가 없으면 거절"을 따로 검사해서 EACCES를 낸다.
  • 범위 밖 값은 우리 init이 -EINVAL을 돌려 거절했고, verbose=maybe는 커널 파서(param_set_bool)가 우리 코드에 오기도 전에 거절했다. 둘 다 유저에게는 invalid parameter다.
  • 모르는 파라미터는 실패가 아니다: 경고 한 줄 남기고 로드된다(exit=0). 오타 난 파라미터가 조용히 무시되는 사고가 여기서 난다 — 항상 dmesg를 본다.

체크포인트: parameters/에 파일 3개, buf_size=10이면 로드 실패. git tag m2.

4. M3 — char device: alloc_chrdev_region + cdev + class/device → /dev/s2chr0#

4.1 무엇을 만드나 — 객체 그래프#

장치 노드 하나가 생기려면 네 가지가 필요하다: (1) 번호 dev_t를 빌리고, (2) 그 번호에 file_operations를 묶는 cdev를 등록하고, (3) sysfs에 class와 device를 만들어 uevent를 내고, (4) devtmpfs가 그 uevent로 /dev 노드를 만든다. 이론은 G4 §1–3이다. 아래 그림은 M6까지 끝난 최종 모습이다.

그림 2 — char device 객체 그래프. 사용자 fd → struct file(열 때마다 하나) → struct inode(노드 하나에 하나) → cdev → 우리 s2_dev. 드라이버는 container_of(inode->i_cdev, struct s2_dev, fifo_cdev)로 자기 구조체를 찾고 file->private_data에 저장해 이후 read/write/ioctl이 쓴다. 왼쪽 아래의 번호 지도와 오른쪽 아래의 class/device는 등록 시점에만 쓰인다.

4.2 코드 (M2에서 바뀐 부분)#

무엇을 확인하나: 등록 4단계와, 실패하면 거꾸로 정리하는 goto 사다리(E3 §6). 아직 .read가 없으므로 open/release만 있다.

class_create()는 6.4부터 owner 인자가 없어졌다(G4 §3.2). 예전 블로그의 class_create(THIS_MODULE, "x")를 그대로 쓰면 6.18에서 컴파일 에러다. 그리고 순서: cdev_add가 성공하는 순간 같은 번호로 노드를 가진 사람은 open할 수 있다 — 그래서 실제 버퍼 같은 상태는 cdev_add 전에 준비한다(M4에서 kzalloc을 맨 앞에 둔 이유, G4 §2.3).

4.3 실행#

출력에서 볼 것:

  • 동적 major가 510이다. 이 랩 커널은 빌트인 드라이버들이 234~254를 다 가져가고 확장 구간의 511은 rpmb가 가져가서 510이 나온다(G4 예제 2). config와 로드 순서에 따라 바뀌므로 하드코딩하지 말 것.
  • 노드는 mknod 없이 생겼다: device_create → uevent(MAJOR=510 MINOR=0 DEVNAME=s2chr0) → devtmpfs. 부모가 없으므로 /sys/devices/virtual/s2chr/ 아래에 붙었다.
  • 권한이 crw-------(root만)인 이유: devtmpfs 기본값 0600. 바꾸려면 class의 devnode 콜백이나 udev 규칙(G7 §4.5).
  • .read가 없으면 VFS가 -EINVAL을 돌려준다. open/release는 정상으로 불렸다.

체크포인트: /dev/s2chr0이 c 510,0으로 생기고, rmmod 후 사라지고, 다시 insmod가 된다. git tag m3.

5. M4 — read/write: 커널 버퍼, copy_to_user/copy_from_user, *ppos#

5.1 코드 (M3에서 바뀐 부분)#

무엇을 확인하나: read/write의 계약 — 반환값은 실제로 옮긴 바이트 수, 0은 EOF, 음수는 -errno, 그리고 *ppos를 직접 전진시킨다(E6 §3, G4 §6). 버퍼는 buf_size 파라미터 크기로 kzalloc한다.

copy_to_user는 못 옮긴 바이트 수를 돌려준다(0이면 성공). 그래서 if (copy_to_user(...)) return -EFAULT;가 정석이다. 이 단계는 아직 락이 없다 — 동시에 두 명이 쓰면 깨진다는 것을 M7에서 실제로 보여 준다.

5.2 계약 테스트 도구 s2_rw#

무엇을 확인하나: 셸 명령으로는 보기 어려운 경계값 — short read, EOF, SEEK_END, pread, short write, ENOSPC, 범위 밖 seek, 나쁜 사용자 포인터.

char *volatile bad인 이유: 처음에 read(fd, (char *)1, 4)라고 썼더니 glibc _FORTIFY_SOURCE가 "주소 0 근처에 4바이트 쓰기"를 컴파일 시점에 알아채고 -Wstringop-overflow 경고 4개를 냈다. 경고 0개 규칙 때문에 컴파일러가 값을 추적하지 못하게 volatile로 막았다.

6.18의 include/linux/timer.h에는 옛 이름 from_timer()와 del_timer_sync()가 더 이상 없다(grep으로 확인). 각각 timer_container_of(), timer_delete_sync()로 바뀌었으므로 블로그 예제의 옛 이름은 이 커널에서 컴파일되지 않는다. exit에서는 timer_shutdown_sync()를 쓴다 — 지우는 동시에 "다시는 무장되지 않음"을 보장한다(F8).

7.3 코드 (2/2) — 소비자: blocking read와 .poll#

핵심 규칙 세 개:

  • copy_to_user는 page fault로 잠들 수 있다. 그래서 spinlock 안에서 부르지 않는다: 락 안에서는 kfifo_out_spinlocked로 스택 버퍼에 꺼내기만 하고, 락을 푼 뒤 복사한다(F2, F4 §3.4). 대가: 복사가 EFAULT로 실패하면 꺼낸 데이터는 사라진다. 사용자 포인터를 먼저 검사하고 싶으면 kfifo_to_user를 mutex 아래에서 쓰는 설계로 바꾼다.
  • wait_event_interruptible은 조건을 다시 검사하고 잔다. 조건과 깨우기 사이의 lost-wakeup 경쟁을 매크로가 막아 준다(F3 §5). 깨어났다고 데이터가 있다는 보장은 없으므로 while로 다시 꺼낸다.
  • .poll은 잠들지 않는다. "이 wait queue에 나를 등록해 두라"(poll_wait)와 "지금 상태"(mask) 두 가지만 한다(G6 §1.3).

그림 3 — blocking read 시퀀스. 리더는 큐에 자신을 걸고 TASK_INTERRUPTIBLE로 잔다(그동안 CPU를 쓰지 않는다). 생산자는 데이터를 넣고 wake_up_interruptible을 부른다. 깨어난 리더는 조건을 다시 보고 꺼낸다. 펌웨어로 말하면 "RTOS 세마포어 pend/post"이고, 차이는 시그널로 잠을 깰 수 있다는 점이다.

8. M7 — 동시성: mutex, 여러 opener, 두 프로세스 테스트#

8.1 코드 (M6에서 바뀐 부분)#

무엇을 확인하나: mem 버퍼의 buf/len은 프로세스 컨텍스트에서만 만지므로 잠들 수 있는 mutex가 맞다(copy_from_user가 락 안에서 잠들 수 있어야 한다, F4 §5). O_APPEND는 "len을 읽고 → 그 위치에 쓰고 → len을 갱신"하는 read-modify-write라서 락 없이는 깨진다.

함수 안에 return이 여러 개면 unlock을 빼먹기 쉬우므로 ret에 값을 넣고 goto out 한 곳에서 푸는 모양으로 바꿨다. mutex_lock_interruptible은 락을 기다리다 시그널을 받으면 -EINTR을 주는데, 드라이버는 이것을 -ERESTARTSYS로 바꿔 돌려준다(시스템 콜 재시작 규칙, F3 §4). VFS는 char device에 O_APPEND를 자동으로 해 주지 않는다 — 일반 파일에서는 generic_write_checks()가 하지만 우리 .write는 직접 처리해야 한다.

  • 손실은 2~3%로 작고 실행마다 다르다. 실제 SoC에서는 더 드물게 날 수 있고, 그래서 "테스트에서 한 번도 안 났다"가 증거가 되지 못한다 — lockdep(Image-dbg)이나 KCSAN 같은 도구, 그리고 이런 스트레스 테스트를 CI에 넣는 이유다.
  • 실행 시간 15~18 s는 TCG 에뮬레이션 비용이 지배한다. 락 유무로 시간이 거의 같다는 것도 이 환경에서는 의미 있는 비교가 아니다(실제 보드에서 다시 재야 한다).
  • open_count=4 = 백그라운드 sleep 두 개(각 minor) + s2_ioctl이 연 fd 두 개. 두 minor를 합산하는 카운터다.

체크포인트: mutex 빌드는 세 번 다 lost=0, 락 없는 빌드는 lost>0. git tag m7.

9. M8 — sysfs 속성, debugfs, dynamic debug, goto 사다리 증명, selftest#

9.1 sysfs 속성 — "값 하나 = 파일 하나"#

무엇을 확인하나: 사용자가 셸로 바꿀 손잡이(period_ms)와 읽기 전용 상태(len)를 sysfs 속성으로 낸다. device_create_with_groups로 넘기면 uevent보다 먼저 속성이 생긴다(G8 §8 — udev가 속성을 읽는 경쟁을 피함).

ioctl의 SET_PERIOD와 sysfs store가 같은 검증 함수 s2_set_period()를 부른다 — 인터페이스가 두 개여도 규칙은 하나여야 한다. len_show는 엄밀히는 "값 하나" 규칙을 어긴다(두 값). 학습용으로 둔 것이고, 업스트림이라면 mem_len과 fifo_len으로 나눈다(G8 §1.2).

9.2 debugfs — 약속 없는 개발자 창문#

debugfs 함수의 반환값은 검사하지 않는 것이 커널 규칙이다(debugfs가 없거나 실패해도 드라이버는 동작해야 하고, 실패한 dentry를 다음 호출에 넘겨도 안전하게 무시된다). drops만 0644인 것은 테스트 중 카운터를 0으로 되돌리기 위해서다.

9.3 dynamic debug — 재빌드 없이 디버그 줄 켜기#

M3에서 넣은 pr_info open/release 로그를 dev_dbg로 바꿨다. dev_dbg는 장치 이름을 자동으로 붙이고, CONFIG_DYNAMIC_DEBUG=y 커널에서는 기본 꺼짐 + 런타임 스위치다(M1 노트 §4).

9.4 goto 사다리를 "증명"하기 — fail_at 결함 주입#

무엇을 확인하나: init의 7단계 각각에서 실패했을 때 그 앞 단계까지만 정확히 거꾸로 풀리는지. 손으로 리뷰하는 대신 모듈 파라미터로 실패를 주입하고 남은 흔적을 센다.

a ?: b는 GCC 확장(커널 전체에서 쓰는 관용구, E5)으로 "a가 0이 아니면 a, 아니면 b"다. 실제 함수 호출 앞에 주입을 끼워 넣어 원래 코드 모양을 거의 바꾸지 않았다. 커널에는 범용 결함 주입(CONFIG_FAULT_INJECTION, failslab, J 모듈에서 사용)도 있지만, 단계 번호로 정확히 찌르는 데는 이 방식이 단순하다.

그림 5 — goto 사다리. 왼쪽 단계가 실패하면 화살표의 라벨로 점프하고, 거기서부터 오른쪽 열을 위로 타고 올라가며(코드에서는 아래로 fall-through) 앞 단계를 푼다. exit 함수는 7단계 전부를 같은 역순으로 푼다(+ 맨 앞에 debugfs, 중간에 타이머).

9.5 실행 — 속성, debugfs, dynamic debug, 결함 주입#

출력에서 볼 것:

  • 범위 밖 store는 우리 -EINVAL이 그대로 셸의 write error: Invalid argument가 됐다. 1초 동안 period_ms=100이 tick 10개(seq=10, 201바이트)를 만들었다.
  • dynamic debug 제어 파일의 =_는 "꺼짐", 켠 뒤 +pfl의 f(함수 이름)·l(줄 번호)이 접두어 s2_open:102:로 붙었다. 끄는 것은 -p. 제품 빌드에 디버그 줄을 남겨 두고 현장에서 켜는 방식이다(M1 노트 §4.6).
  • flags=0x20000 = O_LARGEFILE(arm64 64비트 프로세스에서 VFS가 붙임). O_RDONLY는 0이다.
  • 7단계 모두에서 insmod가 실패했고(1) 남은 것이 0이었으며, 그 뒤 정상 insmod가 됐다. 이것이 "goto 사다리가 맞다"의 증거다. 리뷰어에게 "init의 모든 실패 경로를 테스트했다"고 말할 수 있다.

9.6 goto 사다리 vs devm_* — 왜 여기서는 goto인가#

항목goto 사다리 (이 드라이버)devm_* (platform/I2C/SPI 드라이버)
해제 시점init 실패 시 직접, exit에서 직접probe 실패 시 또는 remove/unbind 후 devres가 역순으로
필요 조건없음 (어떤 모듈이든)bus가 probe한 struct device가 있어야 함
흔한 실수라벨 순서 틀림, 하나 건너뜀devm 자원을 수동으로 또 해제(double free), IRQ가 다른 자원보다 늦게 풀려 해제된 데이터 접근

s2chr은 bus에 붙은 장치가 아니라 "모듈 = 장치" 구조라서 devres를 매달 probe된 struct device가 없다. device_create가 만드는 device에 devm을 매다는 것은 가능은 하지만, 그 device는 우리가 device_destroy로 지우는 대상이라 순서가 뒤엉킨다. 실제 센서 드라이버(S4)는 platform/I2C driver로 쓰고 devm_kzalloc, devm_request_irq, devm_regmap_init_i2c, misc/cdev는 devm_add_action_or_reset로 묶는다 — 그러면 이 goto 사다리 대부분이 사라진다. 면접에서는 둘 다 말할 수 있어야 한다: "모듈 init이면 goto, probe면 devm, 섞으면 순서를 반드시 그림으로 그려 본다."

9.7 selftest — kselftest 스타일 TAP 스크립트#

무엇을 확인하나: 지금까지의 확인을 사람이 눈으로 보는 대신 기계가 판정하게 만든다. kselftest의 출력 형식(TAP 13: ok N - 설명, not ok N, 마지막 # Totals)을 따르므로 CI가 그대로 파싱할 수 있다. 이 커널은 CONFIG_KUNIT이 꺼져 있어(KUnit은 Image-dom에만 있다) 사용자 공간 end-to-end 테스트로 했다.

처음 돌렸을 때는 not ok 8과 not ok 4가 나왔다 — 테스트 스크립트 쪽 버그였다(기본 buf_size=4096에 64000바이트를 쓰려 해서 ENOSPC, s2_rw에 버퍼 크기를 안 넘김). 테스트도 코드다. 실패하면 "드라이버가 틀렸나, 테스트가 틀렸나"부터 가른다.

11. Embedded 실무에서 다시 보기#

11.1 센서 키트의 IMU 데이터 경로#

로봇 센서 키트에서 IMU가 FIFO watermark 인터럽트를 주는 경우, s2chr1의 구조가 그대로 쓰인다: 타이머 자리에 threaded IRQ 핸들러(I2C/SPI로 FIFO를 읽으니 잠들 수 있어야 함, F6·F7), kfifo에 타임스탬프 붙은 샘플, 유저는 poll + read. 다만 업스트림이라면 직접 char device를 만들지 않고 IIO buffer(/dev/iio:deviceN)를 쓴다 — IIO가 이 노트의 M6를 프레임워크로 만들어 둔 것이다. S4가 그 다음 단계다.

11.2 "가끔 데이터가 안 온다"#

현장 증상 → 첫 명령: cat /proc/<pid>/wchan, cat /proc/<pid>/stack(M6 출력), debugfs의 큐 길이. 리더가 잔다 + 큐에 데이터가 있다 = wake_up 누락(FAIL-7). 리더가 잔다 + 큐가 비었다 + ticks가 안 늘어난다 = 생산자(IRQ)가 죽음. 카운터를 debugfs에 미리 넣어 두는 습관이 이 분류를 30초로 만든다.

11.3 벤더 BSP 모듈 업데이트#

커널을 패치해서 다시 빌드하면 -dirty·git 해시가 uname -r에 붙고, out-of-tree 모듈이 FAIL-1처럼 전부 안 올라간다. 빌드 시스템(Yocto의 module.bbclass, S6)이 모듈을 커널과 함께 빌드하게 만드는 이유다. 그리고 CONFIG_*가 달라 struct module 크기가 바뀌면 vermagic보다 앞의 검사에서 막힌다는 것도 이번에 직접 봤다.

11.4 제품 펌웨어의 디버그 손잡이#

dev_dbg는 빌드에 남기고 기본은 꺼 둔다. 현장에서는 echo 'module s2chr +p' > /proc/dynamic_debug/control, 부팅 문제라면 s2chr.dyndbg=+p 커널 인자. debugfs는 양산 이미지에서 마운트하지 않는 경우가 많으므로(보안), 꼭 필요한 상태는 sysfs, 개발용은 debugfs로 나눈다.

13. 확장 과제 — 포트폴리오를 한 단계 더#

15. 면접에서 이렇게 말한다#

Q. Walk me through what happens between insmod and the device node showing up in /dev.

A. 로더가 ELF를 검사하고(구조체 크기, vermagic) 재배치·파라미터 파싱 후 init을 부른다. init은 alloc_chrdev_region으로 번호를 빌리고, cdev_add로 번호와 file_operations를 묶고, class_create·device_create로 sysfs 객체를 만들어 uevent를 낸다. devtmpfs가 그 uevent의 MAJOR/MINOR/DEVNAME으로 노드를 만들고, udev가 있으면 권한·심볼릭 링크를 덧붙인다.

The loader validates the ELF — struct module size and vermagic — relocates it, parses parameters, and calls init. Init reserves a dev_t range, binds it to my file_operations with cdev_add, then creates a class and a device, which emits a uevent. devtmpfs creates the node from MAJOR, MINOR and DEVNAME; udev, if present, only adjusts permissions and links. I order it so everything the fops touch is initialized before cdev_add, because the device is live the moment it is added.

꼬리 질문: 동적 major는 왜 쓰나? → 충돌 방지, /proc/devices나 sysfs dev 파일에서 읽는다(G4 §1.3).

Q. Your read handler returns a value. What are the rules?

A. 옮긴 바이트 수(짧아도 됨), 0은 EOF, 음수는 -errno. *ppos를 직접 전진시킨다. copy_to_user는 못 옮긴 바이트 수를 주므로 0이 아니면 -EFAULT. 실제로 *ppos를 빼먹으면 cat이 끝나지 않고, copy_to_user 결과를 돌려주면 0바이트가 나오는 것을 재현해 봤다.

Return the number of bytes copied — a short count is fine — zero for end of file, and a negative errno on error. I advance *ppos myself. copy_to_user returns the bytes it could not copy, so non-zero means -EFAULT. I reproduced the two classic bugs: forgetting to advance the position makes cat loop forever, and returning copy_to_user's result returns zero, which userspace reads as EOF.

Q. How does your blocking read work, and what happens on a signal?

A. 비어 있고 O_NONBLOCK이면 -EAGAIN, 아니면 wait_event_interruptible로 조건을 다시 검사하며 잔다. 생산자(타이머 softirq)는 spinlock으로 kfifo에 넣고 wake_up_interruptible. 시그널이 오면 -ERESTARTSYS를 돌려주고 커널이 SA_RESTART에 따라 재시작하거나 EINTR로 바꾼다. 복사는 spinlock 밖에서 한다 — copy_to_user는 잠들 수 있으니까.

If the FIFO is empty I return -EAGAIN for non-blocking files, otherwise I sleep in wait_event_interruptible, which re-checks the condition to avoid lost wakeups. The producer, a timer in softirq context, pushes under a spinlock and calls wake_up_interruptible. On a signal I return -ERESTARTSYS and the kernel either restarts the syscall or returns EINTR depending on SA_RESTART. I pop into a stack buffer under the lock and do copy_to_user after releasing it, since it can fault and sleep.

꼬리 질문: .poll은 무엇을 하나? → poll_wait로 등록, 현재 마스크 반환, 절대 잠들지 않음(G6 §1).

Q. Why a mutex for one buffer and a spinlock for the other?

A. mem 버퍼는 프로세스 컨텍스트에서만 만지고, 락을 쥔 채 copy_from_user(잠들 수 있음)를 해야 하므로 mutex. FIFO는 타이머 softirq도 만지므로 잠들 수 없는 spinlock(irqsave/bh)이고, 대신 락 안에서는 사용자 메모리를 건드리지 않는다. 락을 빼면 두 프로세스 append에서 2~3% 레코드를 잃는 것을 측정했다.

The memory buffer is only touched from process context and I need to hold the lock across copy_from_user, which may sleep, so it's a mutex. The FIFO is also touched from a timer in softirq context, which cannot sleep, so it's a spinlock, and I never touch user memory while holding it. Without the mutex, two processes appending with O_APPEND lost two to three percent of records in my test — lost updates on the length field.

Q. How do you make sure your error paths are correct?

A. goto 사다리를 init 순서의 정확한 역순으로 쓰고, fail_at 파라미터로 7단계 각각에서 실패를 주입한 뒤 sysfs·/proc/devices·debugfs에 남은 것이 없는지 selftest로 확인한다. 라벨 하나를 잘못 건너뛴 빌드는 정상 테스트는 모두 통과하고 결함 주입 항목에서만 잡혔다. probe 기반 드라이버라면 devm_*으로 대부분을 없앤다.

I write the unwind ladder in exact reverse order of init, and I prove it: a fail_at module parameter injects -ENOMEM at each of the seven steps, and the selftest checks that nothing is left in sysfs, /proc/devices or debugfs and that a clean insmod still works. A build where one goto jumped to the wrong label passed every functional test and failed only the injection test. In a probe-based driver I'd use devm to remove most of the ladder.

Q. A customer reports the kernel panics in the idle task a few hundred milliseconds after an update script. Where do you look?

A. Comm: swapper, 인터럽트/softirq 스택(__run_timers), [last unloaded: xxx]를 본다. 모듈 언로드 후 남은 타이머·work·IRQ가 해제된 메모리를 실행하는 전형이다. exit에서 timer_shutdown_sync, cancel_work_sync, free_irq를 했는지 확인한다. 실제로 타이머 정지를 빼서 똑같은 Oops를 재현했다.

The idle task plus a softirq backtrace in __run_timers plus "last unloaded: s2chr" points to a timer, work item or IRQ that outlived its module. I check that exit stops every asynchronous path first — timer_shutdown_sync, cancel_work_sync, free_irq — before freeing anything. I reproduced exactly this: removing timer_shutdown_sync gives a level-3 translation fault on a write inside __run_timers and "Fatal exception in interrupt".

Q. Why should unknown ioctl commands return -ENOTTY, and how do you version an ioctl struct?

A. 커널 관례이고 libc·isatty 같은 판단이 ENOTTY에 의존한다. 구조체 크기가 번호에 들어가므로 크기가 바뀐 옛 앱은 자동으로 ENOTTY를 받는다. 고정 폭 타입, 예약 필드, version 필드, 그리고 반드시 memset 후 채운다 — 빼먹으면 스택 주소가 새는 것을 auto-init을 끈 빌드에서 확인했다.

-ENOTTY is the convention that libc and callers like isatty rely on. Because _IOR/_IOW encode the argument size, an old binary built with a 12-byte struct sends a different number and gets ENOTTY instead of silently corrupting memory. I use fixed-width types, a version field and reserved words, and I memset the struct before filling it — with stack auto-init disabled, skipping the memset leaked a kernel stack address in the reserved words.
