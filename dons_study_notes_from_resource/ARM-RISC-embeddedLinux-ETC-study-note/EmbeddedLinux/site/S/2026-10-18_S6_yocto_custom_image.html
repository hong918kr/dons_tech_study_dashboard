이 노트를 다 읽으면: 제품 layer(meta-donlab)를 처음부터 끝까지 직접 만들 수 있다 · out-of-tree 드라이버 레시피(inherit module + KERNEL_MODULE_AUTOLOAD), CMake + systemd 데몬 레시피, 커널 .bbappend(config fragment + DT overlay 패치), 이미지 레시피를 BitBake 파서로 검증할 수 있다 · 같은 소스를 Yocto 밖에서 빌드해 QEMU(initramfs + systemd 게스트)에서 동작을 증명할 수 있다 · kas lock + CI로 "누가 언제 빌드해도 같은 이미지"를 설명하고 GitHub에 보여 줄 수 있다 왜 필요한가: JD의 "Yocto/BitBake experience"를 면접에서 증명하는 가장 빠른 방법은 직접 만든 layer 저장소 링크다. 질문도 대부분 이 프로젝트 안에서 나온다 — "드라이버를 이미지에 어떻게 넣었나", "커널 설정은 어디서 바꿨나", "빌드를 어떻게 재현하나" Don 기준 난이도: 펌웨어 릴리스 파이프라인 · 패치 큐 · 드라이버 bring-up은 익숙하다 / 새로 손에 익힐 부분은 layer 파일 배치 규칙, override 문법의 함정, kernel-yocto의 KMACHINE, QA 에러를 읽는 법 선행 노트: K4(Yocto 기초 — 문법·태스크·이미지), K5(Yocto 실무 — BSP layer, devtool, 커널 레시피, sstate, kas), E3(커널 모듈), D6(DT overlay), L1(systemd), L4(OTA), K7(라이선스·SBOM). 이론은 K4·K5에 있고, 이 노트는 그 이론을 프로젝트 하나로 묶는 실습 절차다

0. 큰 그림 — 무엇을 만들고, 무엇을 실제로 돌렸나#

0.1 실행 원칙 (먼저 읽기)#

Don의 결정(heavy build 규칙)에 따라 이 노트에서 bitbake로 빌드를 돌리지 않는다. 이미지 한 번에 수 시간 · 수십 GB가 들고, 이 공용 VM(Ubuntu 26.04)은 AppArmor가 비특권 user namespace를 막아 BitBake 태스크가 시작조차 못 한다(K4 10.2절에서 원인을 코드로 확인했다). 그래서 블록은 세 종류다.

  • 실행함: layer 파일 작성, kas checkout/kas lock/kas dump, bitbake-layers show-layers, bitbake-getvar, BitBake 파서(tinfoil)로 레시피 하나씩 파싱, 정적 lint, yamllint, bash -n, DT 패치 git apply --check, merge_config.sh + olddefconfig(설정만), 그리고 같은 소스를 Yocto 밖에서 빌드해 QEMU에서 실행. 출력은 전부 VM(uname -r = 7.0.0-38-generic, aarch64)에서 나온 그대로다.
  • 가이드(실행 안 함): bitbake donlab-image, runqemu, devtool, testimage, CI의 build 잡. 명령과 "무엇이 나와야 하는지"만 적고 출력은 쓰지 않는다.
  • 기억 기반: 빌드 시간 · 디스크 수치처럼 이 환경에서 잴 수 없는 값. 그렇게 표시한다.

파서만 돌려도 꽤 많은 것을 잡는다 — 문법 오류, 없는 class, override가 안 먹는 문제, COMPATIBLE_MACHINE 때문에 레시피가 건너뛰어지는 문제, 변수의 최종 값. 못 잡는 것은 태스크를 실제로 돌려야 나오는 것(컴파일 에러, QA 에러, 패키지 의존성 해석)이고, 이 노트는 그 부분을 "Yocto 밖 빌드 + QEMU"와 "QA 에러 표"(12절)로 메운다.

0.3 layer 스택 — 우리 layer는 어디에 얹히나#

그림 1 — 이 프로젝트의 layer 스택. 실선은 항상 쓰는 layer, 점선은 조건부(실제 보드 BSP, OTA). 오른쪽은 각 layer가 이 프로젝트에서 맡는 역할이다.

bare-metal 비유로 말하면: oe-core는 벤더 SDK의 HAL + 빌드 스크립트, meta-poky는 레퍼런스 프로젝트의 기본 설정, BSP layer는 보드 지원 패키지, meta-donlab은 우리 제품 펌웨어 저장소다. 제품 저장소는 SDK 파일을 직접 고치지 않고 "덮어쓰기 규칙"(bbappend, override)으로만 바꾼다 — SSD 펌웨어에서 벤더 코드를 fork하지 않고 패치 큐로 관리하던 것과 같은 원칙이다.

1. 준비물과 저장소 구조#

1.1 준비물#

  • Lima VM elinux (aarch64 Ubuntu 26.04) — 레시피 파싱 · Yocto 밖 빌드 · QEMU.
  • 공용 랩: 커널 빌드 트리 /var/lab/out/linux-build-trace(6.18.55-trace), 커널 Image-trace, BusyBox initramfs, systemd 게스트 rootfs-trace.ext4(qcow2 overlay로만 사용).
  • /var/tmp/S6/venv — kas 5.5, yamllint 1.38 (pip install kas yamllint, 자기 venv에만 설치).
  • 소스는 Mac 쪽 ~/.elinux_scratch/S6/meta-donlab/(VM에서는 읽기 전용으로 보인다). 그래서 git 작업은 Mac에서, 빌드 산출물은 VM의 /var/tmp/S6/에 둔다.

나중에 실제 빌드를 할 때(가이드): Yocto 6.0이 지원하는 호스트 배포판, 디스크 여유 100 GB 이상, RAM 16 GB 이상(기억 기반 권장치), 그리고 user namespace를 허용한 호스트 — 회사 빌드 서버나 클라우드 VM이 일반적이다.

1.2 완성된 저장소 트리#

git에 들어간 파일 기준으로 그린 트리다 (Mac에 tree가 없어서 git ls-files를 Python으로 트리 모양으로 찍었다).

출력에서 볼 것: 저장소 루트가 곧 layer다(conf/layer.conf가 루트에 있다). 그래서 kas 파일에서 이 저장소를 layers: .:로 가리킨다. 소스(C, CMake, Makefile)가 레시피 옆 files/에 있는 것은 포트폴리오용 단순화다 — 실무에서는 드라이버와 데몬이 각자 git 저장소에 있고 레시피는 SRC_URI = "git://...;branch=main" + SRCREV로 가리킨다(5.2절).

이 단계가 끝나면: 빈 디렉터리 골격과 git init이 된 저장소가 있어야 한다. VM에서 git init을 하면 Read-only file system으로 실패한다 — Mac 쪽에서 한다.

2. Step 1 — layer 뼈대와 kas 프로젝트#

2.1 conf/layer.conf#

K4 9절의 layer.conf와 달라진 점만 짚는다.

  • LAYERSERIES_COMPAT = "wrynose": 현재 LTS는 Yocto 6.0 "Wrynose"(bitbake 2.18 짝)다. 기억이 아니라 K5 0.2절에서 저장소 태그로 확인한 값이고, 아래 lint가 oe-core의 LAYERSERIES_CORENAMES와 다시 맞춰 본다.
  • BBFILES_DYNAMIC: 컬렉션이름:경로 형식. 그 컬렉션(rauc, swupdate)이 BBLAYERS에 있을 때만 경로가 BBFILES에 붙는다. 그래서 meta-rauc가 없는 빌드에서 inherit bundle이 "class를 찾을 수 없음"으로 터지지 않는다(10절에서 실제로 확인).
  • LAYERRECOMMENDS: meta-oe는 "있으면 좋은" layer다. 반드시 필요한 것은 LAYERDEPENDS(core 하나)뿐이다.

2.2 kas/donlab.yml — 빌드 전체를 파일 하나로#

(저장소 파일에는 각 줄 설명 주석이 더 있다.) kas 문법 자체는 K5 1.2절에 있다. 이 파일에서 새로 볼 것: meta-donlab에 url이 없으므로 "이 kas 파일이 든 저장소 자신"이고, layers: .:는 저장소 루트가 layer라는 뜻이다. rm_work는 레시피가 끝나면 WORKDIR을 지워 디스크를 크게 줄이고, buildhistory는 이미지마다 "무엇이 들어갔나"를 git으로 기록한다(13절).

2.3 실행 — kas checkout#

kas checkout은 저장소를 받고 bblayers.conf·local.conf만 만든다. bitbake는 실행하지 않는다.

출력에서 볼 것: kas가 경고를 먼저 띄운다 — 브랜치 이름만 적으면 다음 주에 다른 커밋을 받는다는 뜻이다. 그래서 2.5절에서 lock 파일을 만든다. 얕은 clone(--depth 1)이라 메타데이터 전체가 120 MB 남짓이다. 실제 빌드에서 크는 것은 메타데이터가 아니라 downloads/, sstate-cache/, tmp/다(11.4절).

2.4 설정 파싱 — layer가 제대로 붙었나#

BitBake 환경을 잡는 셸 조각이다. HOSTTOOLS 검사에서 걸리는 chrpath/diffstat은 이 공용 VM에 없어서(apt 설치 금지) 파싱 전용 가짜 스크립트를 PATH 끝에 붙였다 — 실제 빌드에서는 절대 이렇게 하면 안 된다(K4 2.2절).

출력에서 볼 것: 컬렉션 이름 donlab, priority 10. 이 명령은 전역 설정 전체(bitbake.conf → layer.conf 4개 → local.conf → MACHINE=donlab-qemu의 machine conf → DISTRO=donlab의 distro conf)를 파싱한다. 즉 3절의 machine/distro 파일에 문법 오류가 있으면 여기서 이미 실패한다. LAYERSERIES_COMPAT가 맞지 않으면 BitBake(lib/bb/cookerdata.py)가 Layer %s is not compatible with the core layer which only supports these series: ...로 bb.fatal을 낸다.

2.5 kas lock — 브랜치를 커밋으로 박제#

VM에서는 저장소가 읽기 전용이라 lock 파일을 쓸 수 없다. 사본에서 만들고 Mac 쪽으로 가져왔다.

출력에서 볼 것: kas는 donlab.yml 옆의 donlab.lock.yml을 자동으로 겹쳐 읽는다. 이 파일을 커밋하면 "meta-donlab v0.1 = 이 해시 4개 + 우리 커밋"이 된다. 벤더 layer를 올리는 일은 이 lock 파일을 바꾸는 PR이 된다(K5 1.3).

이 단계가 끝나면: bitbake-layers show-layers에 donlab 10이 보이고, kas/donlab.lock.yml이 커밋돼 있어야 한다.

3. Step 2 — machine과 distro#

3.1 conf/machine/donlab-qemu.conf#

핵심은 MACHINEOVERRIDES =. "qemuarm64:" 한 줄이다. 기존 machine을 require해서 새 machine을 만들면 변수 값은 다 가져오지만, override 이름은 MACHINE 값(donlab-qemu)으로 바뀐다. oe-core 곳곳의 :qemuarm64 override(linux-yocto의 KBRANCH:qemuarm64, SRCREV_machine:qemuarm64, COMPATIBLE_MACHINE)가 전부 꺼지는 것이다. 6.4절에서 이 줄을 지웠을 때 커널 레시피가 실제로 건너뛰어지는 것을 보인다.

3.2 conf/distro/donlab.conf#

INIT_MANAGER = "systemd"를 꼭 적어야 하는 이유를 소스에서 확인했다.

출력에서 볼 것: oe-core 기본(nodistro)은 systemd지만 poky는 아직 sysvinit이다. poky를 require한 우리 distro는 명시하지 않으면 sysvinit 이미지가 된다 — 그러면 5절의 systemd unit이 설치는 되어도 아무도 실행하지 않는다. 하드닝 플래그와 SPDX는 이미 기본이라 다시 적지 않았다(주석으로만 남김). INCOMPATIBLE_LICENSE는 주석으로 둔 이유가 있다: GPLv3를 막으면 bash처럼 GPL-3.0인 패키지를 끌어오는 경로가 전부 "nothing provides" 에러가 된다. 켜기 전에 의존성 정리가 먼저다(K7).

3.3 실행 — 최종 값 확인 (bitbake-getvar)#

출력에서 볼 것:

  • MACHINEOVERRIDES의 맨 앞에 qemuarm64, 맨 끝에 donlab-qemu. 뒤에 있을수록 우선순위가 높다 — 같은 변수에 :qemuarm64와 :donlab-qemu override가 둘 다 있으면 우리 것이 이긴다.
  • DISTRO_FEATURES에서 x11 wayland vulkan opengl ptest가 빠졌고 systemd가 들어왔다. INIT_MANAGER = "systemd"가 고르는 conf/distro/include/init-manager-systemd.inc의 첫 줄이 DISTRO_FEATURES:append = " systemd usrmerge"다 — 그래서 usrmerge가 두 번 보인다(무해하지만 우리 append는 사실 군더더기다).
  • KERNEL_DEVICETREE에 qemuarm64 원본에는 없던 .dtbo 하나. QEMU는 DT를 스스로 만들기 때문에 qemuarm64는 원래 dtb가 없다(6.5절).

이 단계가 끝나면: bitbake-getvar --value MACHINEOVERRIDES의 첫 항목이 qemuarm64, INIT_MANAGER가 systemd여야 한다.

4. Step 3 — 드라이버와 out-of-tree 모듈 레시피#

4.1 드라이버 — 이 프로젝트의 "센서"#

S2(char device)나 S4(IIO 드라이버)가 끝나면 그 소스로 바꿔 끼우면 된다. 이 노트를 쓸 때 S2/S4 소스가 아직 없어서, 레시피 모양을 보여 주기에 충분한 작은 드라이버를 직접 썼다: DT compatible = "donlab,temp-sensor"로 바인딩되는 platform driver가 misc device /dev/donlab_sensor를 만들고, read() 한 번에 샘플 한 줄(seq=<n> temp_mC=<t>)을 준다. 값은 가짜(삼각파)지만 platform_driver + of_match_table + device property + miscdevice라는 뼈대는 실제 메모리 맵 센서 드라이버와 같다(G1, G2). 핵심 부분만 옮긴다(전체 132줄은 저장소에).

나머지는 platform_driver 등록과, DT 노드가 없는 보드를 위한 fake_device=1 모듈 파라미터(켜면 platform_device_register_simple()로 장치를 직접 만든다)다. QEMU의 runqemu는 DT overlay를 적용하지 않으므로, donlab-qemu 이미지에서는 이 파라미터로 장치를 만든다(4.3절의 module_conf_*). misc.mode = 0444라서 udev 규칙 없이도 일반 사용자가 읽을 수 있다 — 5절의 DynamicUser 서비스가 이 덕을 본다.

Makefile은 module.bbclass가 넘기는 KERNEL_SRC를 받는 표준 Kbuild 래퍼다(K5 4.3과 같은 모양).

4.2 레시피 donlab-sensor-mod_0.1.bb#

새로 볼 변수 세 개:

  • KERNEL_MODULE_AUTOLOAD: kernel-module-split.bbclass가 do_package에서 modules-load.d/donlab_sensor.conf(내용 = 모듈 이름 한 줄)를 만들어 kernel-module-donlab-sensor 패키지에 넣는다. 부팅 때 systemd-modules-load.service가 이 파일을 읽어 modprobe한다. 이 디렉터리는 systemd distro면 /usr/lib/modules-load.d, 아니면 /etc/modules-load.d다.

4.3 실행 — BitBake 파서로 레시피 검증#

tools/s6_parse.py는 tinfoil로 설정 파싱 + 레시피 하나 파싱만 하고 변수를 찍는다(태스크 실행 없음, K4 4.3과 같은 방식). 레시피가 SkipRecipe로 건너뛰어지면 그 이유를 찍고 종료 코드 3을 낸다.

출력에서 볼 것:

  • module_conf_donlab_sensor에 :donlab-qemu override가 적용된 값이 보인다 — override가 실제로 먹었다는 증거.
  • PACKAGE_ARCH = 'donlab_qemu': 커널 모듈은 machine 전용 패키지다(커널 버전·설정에 묶이니까). 일반 앱(cortexa57)과 패키지 피드가 다르다.

4.4 실행 — Yocto 밖에서 같은 방식으로 빌드#

module.bbclass는 결국 make KERNEL_SRC=<커널 빌드 트리>와 make modules_install MODLIB=<D>/... DEPMOD=echo를 부른다(K5 4.3에서 bbclass를 grep했다). CMake 레시피도 cmake -G Ninja → ninja → DESTDIR=<D> ninja install이다. tests/build-outside-yocto.sh는 이 두 흐름을 랩 커널 빌드 트리(6.18.55-trace)로 그대로 재현하고, 마지막에 KERNEL_MODULE_AUTOLOAD·module_conf_*가 만들 파일 두 개도 같은 경로에 만든다.

출력에서 볼 것:

이 단계가 끝나면: modinfo에 vermagic 6.18.55-trace와 of: alias가 보이고, 설치 트리에 파일 5개가 있어야 한다.

5. Step 4 — 센서 데몬: CMake + systemd 레시피#

5.1 데몬과 unit#

데몬은 /dev/donlab_sensor를 주기적으로 읽어 창(window)마다 min/avg/max를 stdout에 찍는다. systemd 아래에서는 stdout이 그대로 journal로 간다 — 로그 파일·syslog 코드가 필요 없다(L1). 메인 루프만 옮긴다(전체 88줄).

fflush(stdout)가 중요하다: stdout이 파이프(journald)면 C 라이브러리가 4 KB 단위로 버퍼링해서, 플러시하지 않으면 로그가 몇 분씩 늦게 나타난다. SIGTERM 핸들러는 stop 플래그만 세운다 — systemctl stop이 깔끔하게 끝난다.

이것이 첫 버전이다. 8.3절에서 systemd-analyze security로 노출 점수를 재고 줄을 더 추가한다(저장소에는 최종본이 있다). 순서와 조건이 드라이버와 맞물린다: After=systemd-modules-load.service(모듈이 먼저 올라오고) + ConditionPathExists=/dev/donlab_sensor(장치가 없으면 실패가 아니라 "조건 불충족으로 건너뜀"). 하드닝은 L1·L6의 내용을 그대로 적용했다 — 매번 바뀌는 임시 uid, OS 읽기 전용, 네트워크 없음, 장치는 우리 노드 하나만 읽기.

CMakeLists.txt는 unit 설치 위치를 캐시 변수로 받는다. 레시피가 Yocto의 ${systemd_system_unitdir}를 넘겨 주기 위해서다 — 경로를 하드코딩하면 usrmerge QA에 걸릴 수 있다(12절).

5.2 레시피 donlab-sensord_0.1.bb#

  • LIC_FILES_CHKSUM의 md5는 md5 -q files/LICENSE로 구한 값이다. 라이선스 파일이 한 글자라도 바뀌면 do_populate_lic가 실패한다 — 의도된 동작이다(라이선스가 바뀌었는지 사람이 확인하라는 뜻, K7).
  • inherit systemd + SYSTEMD_SERVICE: 패키지에 postinst를 넣어 이미지 생성 때 systemctl enable과 같은 심볼릭 링크를 만든다. 그래서 rootfs가 읽기 전용이어도 첫 부팅부터 서비스가 켜져 있다.
  • RRECOMMENDS(약한 의존성): 드라이버를 뺀 이미지도 빌드는 되게 한다. 꼭 있어야 하면 RDEPENDS.

5.3 실행 — 파서로 확인#

출력에서 볼 것: inline Python(bb.utils.contains)이 ON으로 풀렸다 — distro에 systemd가 있다는 뜻. B가 .../build로 S와 갈렸다(cmake class의 out-of-tree 빌드). DEPENDS에 우리가 적지 않은 systemd-systemctl-native가 들어 있다 — inherit systemd가 이미지 생성 때 쓸 호스트용 systemctl을 끌어온 것이다. WORKDIR 경로의 cortexa57-poky-linux에서 poky는 TARGET_VENDOR다 — 우리 distro가 poky를 require했으니 그대로 남는다.

이 단계가 끝나면: EXTRA_OECMAKE에 /usr/lib/systemd/system과 ON이 보여야 한다. OFF면 distro에 systemd가 없다는 뜻이다(3절로 돌아간다).

세 가지 함정을 막는 줄이다.

6.3 DT overlay 패치 만들기#

overlay 소스는 D6에서 배운 형식 그대로다. 루트에 노드 하나를 붙인다.

패치는 랩 커널 소스(읽기 전용)의 arch/arm64/boot/dts/Makefile만 임시 git 저장소에 복사해서 git format-patch로 만든다. 커널 트리 전체를 복사하지 않아도 된다.

출력에서 볼 것: git apply --check는 아무것도 쓰지 않고 적용 가능 여부만 본다 — 읽기 전용 랩 소스에도 쓸 수 있다. 패치 본문에는 Upstream-Status: 줄이 있다. oe-core는 패치마다 이 태그를 요구하고, 없으면 patch-status QA로 경고·에러를 낸다(우리 layer에 적용되는 수준은 설정에 따라 다르다). 실무에서 리뷰어가 가장 먼저 보는 줄이다: "이 패치를 upstream에 보낼 건가, 못 보내면 왜인가".

주의: 이 패치는 랩 소스 6.18.55 기준으로 만들었고, wrynose의 linux-yocto는 6.18.52(LINUX_VERSION, 6.6절)다. 우리가 고친 Makefile 문맥(subdir-y += cix 근처)은 두 버전에서 같을 가능성이 높지만, 실제 빌드 전에 devtool modify linux-yocto 트리에서 다시 만드는 것이 정석이다 — K5 3.5절의 "패치는 레시피의 SRCREV 기준으로" 원칙.

6.4 config fragment 검증 — 설정만, 빌드 없이#

kernel-yocto가 하는 일을 손으로 재현한다: 기준 .config에 fragment를 병합하고(merge_config.sh), Kconfig 의존성을 풀고(olddefconfig), 요청한 값이 살아남았는지 확인한다(do_kernel_configcheck에 해당). 기준은 랩 defconfig 커널의 .config 사본이다(linux-yocto의 qemuarm64 standard 설정과는 다르다 — 그래서 "이 fragment가 Kconfig 의존성상 성립하는가"를 보는 검사로 쓴다).

출력에서 볼 것: 기준 설정에 없던 3개(SQUASHFS_ZSTD, EROFS_FS, SOFT_WATCHDOG)는 "redefined"로 보고되고, 나머지 7개는 이미 켜져 있어 조용하다. 10개 모두 OK. 3개를 켰는데 .config는 16줄이 바뀌었다 — 켠 옵션이 select/default로 끌어온 하위 옵션까지 함께 바뀐 것이다. 이 fragment는 각 줄이 왜 필요한지 주석으로 적어 두었다(디버그용 /proc/config.gz, read-only rootfs용 squashfs/erofs/overlayfs, systemd watchdog, bring-up용 i2c-dev).

6.5 일부러 실패시키기 — 의존성 때문에 사라지는 옵션#

fragment에서 가장 흔한 사고는 "적었는데 안 켜진" 옵션이다. Kconfig는 depends on이 안 맞는 옵션을 에러 없이 조용히 버린다.

출력에서 볼 것: merge_config.sh도 olddefconfig도 에러를 내지 않았다 — 검사 스크립트가 없었다면 옵션이 빠진 커널이 그대로 나간다. Yocto에서는 do_kernel_configcheck가 같은 비교를 하고(symbol_why.py --mismatches), 우리 bbappend의 KMETA_AUDIT_WERROR = "1" 덕분에 경고가 아니라 빌드 실패가 된다. 고치는 법은 depends on을 읽고 빠진 부모 옵션을 함께 적는 것이다. menuconfig에서 /로 심볼을 검색하면 "Depends on:" 줄에 지금 값이 [=n]으로 보인다(E4).

6.6 실행 — linux-yocto를 우리 bbappend와 함께 파싱#

출력에서 볼 것: SRC_URI 끝에 우리 파일 두 개가 붙었고, KMACHINE이 qemuarm64, KBRANCH가 qemuarm64용 브랜치로 풀렸다(MACHINEOVERRIDES에 qemuarm64가 있어서 KBRANCH:qemuarm64가 적용됐다). type=kmeta인 두 번째 git이 yocto-kernel-cache — .scc/.cfg 저장소다. 우리 .cfg는 SRC_URI에 넣기만 하면 kernel-yocto가 fragment로 인식한다.

이제 3.1절의 MACHINEOVERRIDES 줄을 주석 처리하고 같은 명령을 다시 돌린다(확인 후 원상 복구했다).

출력에서 볼 것: 에러가 아니라 SKIPPED다. 실제 빌드에서는 이게 더 헷갈린다 — 커널 레시피가 조용히 빠지고, 이미지를 빌드할 때 "virtual/kernel을 제공하는 레시피가 없다"는 식의 에러로 엉뚱한 곳에서 터진다(정확한 문구는 기억 기반이라 생략). linux-yocto의 COMPATIBLE_MACHINE = "^(qemuarm|...|qemuarm64|...)$"는 정규식으로 MACHINEOVERRIDES 항목과 비교된다. 우리 machine이 qemuarm64 override를 가져야 통과한다.

태스크 목록에서 커널 전용 태스크만 추린 것이다.

shared_workdir가 4.3절에서 본 "커널 빌드 트리를 work-shared에 공개"하는 태스크다. 우리 모듈 레시피의 make-mod-scripts:do_compile 의존성이 결국 이것을 기다린다.

이 단계가 끝나면: 패치가 apply-check: OK, fragment 10개가 OK, linux-yocto 파싱의 SRC_URI에 우리 파일 두 개, KMACHINE = 'qemuarm64'가 보여야 한다.

7. Step 6 — 이미지 레시피#

7.1 donlab-image.bb와 packagegroup#

설계 포인트:

  • IMAGE_INSTALL =(덮어쓰기)는 이미지 레시피 안에서만 쓴다. local.conf에서 IMAGE_INSTALL +=를 쓰면 기본값을 날리는 유명한 함정(K4 3.6)이 생긴다 — 9절 lint가 conf 파일에서 이 패턴을 경고한다.
  • 제품 기능 vs 개발 기능을 분리: 이미지에는 ssh-server-openssh만. 빈 root 암호·root 로그인·디버그 도구는 EXTRA_IMAGE_FEATURES로 kas/dev.yml에서만 켠다. bitbake.conf에 IMAGE_FEATURES += "${EXTRA_IMAGE_FEATURES}"가 있어서 이 변수가 그대로 합쳐진다. 예전의 debug-tweaks는 없어졌고 allow-empty-password · empty-root-password · allow-root-login · post-install-logging으로 쪼개졌다(core-image.bbclass 주석에 그렇게 적혀 있다).
  • read-only rootfs는 스위치 하나: read-only-rootfs feature가 켜지면 rootfs 후처리 훅이 붙고 커널 인자에 ro가 들어간다(7.3절에서 실제로 확인).
  • users: extrausers class가 rootfs 후처리에서 useradd/usermod를 돌린다. 암호 해시의 $는 \$로 이스케이프한다 — EXTRA_USERS_PARAMS가 셸 함수 안의 큰따옴표 문자열로 풀리기 때문이다. 이스케이프를 빠뜨리면 $6이 빈 문자열로 확장되어 틀린 해시가 조용히 들어가고 로그인이 안 된다.

7.2 실행 — 이미지 레시피 파싱#

출력에서 볼 것:

  • PACKAGE_INSTALL(실제로 opkg에 넘길 목록)에 우리가 적지 않은 것들이 붙었다: packagegroup-core-ssh-openssh(IMAGE_FEATURES에서), base-passwd shadow(extrausers가 EXTRA_USERS_PARAMS가 있으면 추가), run-postinsts. kernel-module-donlab-sensor는 여기 없다 — packagegroup의 RDEPENDS와 machine의 MACHINE_EXTRA_RRECOMMENDS를 통해 do_rootfs의 의존성 해석 때 들어온다.
  • ROOTFS_POSTPROCESS_COMMAND 첫 항목 set_user_group이 extrausers의 훅, zap_empty_root_password는 empty-root-password feature가 없을 때 root 빈 암호를 지우는 훅이다(제품 이미지의 안전장치).
  • 이미지 태스크는 형식별로 image_ext4, image_tar 두 개다. .zst는 별도 태스크가 아니라 같은 태스크 안의 "변환(conversion)" 단계로 처리된다.

7.3 실행 — 변형: read-only rootfs와 dev#

kas overlay는 includes로 기본 파일을 겹친다. RO 변형은 local.conf에 한 줄만 더한다.

출력에서 볼 것: 스위치 하나로 세 군데가 바뀌었다 — feature 목록, rootfs 후처리에 read_only_rootfs_hook(쓰기 필요한 /etc 항목을 volatile로 돌리는 훅), 커널 인자 APPEND에 ro. 실제 기기에서 RO rootfs를 쓰면 쓰기가 필요한 것(ssh host key, machine-id, 로그, 설정)을 어디에 둘지 결정해야 한다 — overlayfs /etc, 별도 data 파티션, tmpfs. 이 설계는 L4(A/B 업데이트)와 한 세트다.

dev 변형도 같은 방법으로 확인했다.

출력에서 볼 것: feature 이름이 틀렸다면 image.bbclass가 파싱 단계에서 '...' in IMAGE_FEATURES (added via EXTRA_IMAGE_FEATURES) is not a valid image feature로 레시피를 건너뛴다. 4개 모두 통과했고 tools-debug가 packagegroup-core-tools-debug로 풀렸다.

이 단계가 끝나면: 기본 · RO · dev 세 변형의 IMAGE_FEATURES가 각각 1개 · 2개 · 5개여야 한다.

8. Step 7 — 소스가 실제로 동작하는지 QEMU에서 증명#

Yocto 빌드를 못 하는 대신, 레시피가 패키징할 바로 그 파일들(4.4절 설치 트리)을 랩 커널 6.18.55-trace 위에서 돌린다. 두 단계다: BusyBox initramfs에서 드라이버 경로 두 가지(fake / DT)를, systemd 게스트에서 "이미지처럼 설치된 상태"를 확인한다. 모든 QEMU는 TCG(에뮬레이션)라 시간은 실제 하드웨어 수치가 아니다.

8.1 initramfs 스모크 테스트 — fake 장치와 DT overlay 두 경로#

tests/initramfs-smoke.sh는 랩 rootfs 사본에 .ko와 정적 링크한 데몬을 넣고, LAB_CMD로 테스트 스크립트 하나를 돌리고 꺼진다. MODE=dt이면 커널 패치 안의 .dtso를 그대로 잘라 내 dtc로 컴파일하고 fdtoverlay로 랩 virt.dtb에 합친다 — 패치가 유일한 원본이 되도록.

출력에서 볼 것:

  • 장치 번호 a:102(16진) = major 10(misc), minor 258(동적 할당). 권한 cr--r--r--는 드라이버의 misc.mode = 0444 그대로다.
  • 두 경로의 차이는 base와 node=뿐이다. fake 경로는 기본값 25000, DT 경로는 overlay의 donlab,base-millicelsius = <30000>을 device_property_read_u32()로 읽었다 — DT 속성이 드라이버까지 왔다는 증거다. 장치 이름도 fake는 등록 이름, DT는 노드 이름(donlab-sensor)이다.
  • 데몬의 첫 창이 seq=13에서 끝난다 — head -n 3이 샘플 3개를 먼저 소비했기 때문이다(seq는 드라이버 전역 카운터).
  • module verification failed: 랩 커널은 MODULE_SIG가 켜져 있지만 강제는 아니다. Yocto에서 서명하려면 커널 레시피의 서명 키로 모듈도 서명해야 한다(L5).
  • 타임스탬프는 실행마다 다르다.

8.2 systemd 게스트 — "이미지에 설치된 상태"를 두 번의 부팅으로#

이번에는 실제 systemd가 도는 랩 게스트(rootfs-trace.ext4, qcow2 overlay — 원본은 건드리지 않는다)에서 확인한다. 4.4절의 설치 트리를 ext4 이미지로 만들어 두 번째 디스크로 붙이고, systemd.mount-extra=로 /mnt에 마운트한다.

  • 부팅 1 (systemd.run=으로 설치 스크립트 실행 후 종료): 설치 트리를 /에 복사, depmod, systemctl enable. Yocto의 do_rootfs가 패키지를 풀고 postinst를 돌리는 것에 해당한다.
  • 부팅 2 (보통 부팅): systemd-modules-load가 모듈을 올리고, 서비스가 자동으로 뜨는지 본다. 결과는 테스트 전용 oneshot unit(s6-report.service, layer에는 없음)이 시리얼에 찍고 끈다.

출력에서 볼 것:

  • KERNEL_MODULE_AUTOLOAD가 만들 파일(modules-load.d) → systemd-modules-load active → lsmod에 모듈. module_conf_*가 만들 파일(modprobe.d)의 fake_device=1이 modprobe 때 적용돼 장치가 생겼다. 아무도 modprobe를 손으로 부르지 않았다.
  • 서비스가 enabled / active이고 journal에 데몬 출력이 그대로 들어갔다(stdout → journald).
  • 프로세스 사용자가 이름 없는 숫자 uid 63144 — DynamicUser=yes가 부팅마다 임시 uid를 배정한 것이다. root가 아니어도 0444 장치를 읽는다.
  • 부팅 한 번에 약 1분 — TCG 에뮬레이션 + 1 GB 게스트라서다. 실제 Cortex-A 보드라면 수 초다.

처음 돌렸을 때는 두 가지가 실패했다. 그대로 적어 둔다 — 둘 다 실무에서 흔한 실수다.

8.3 숫자 하나 만들기 — 서비스 노출 점수 7.6 → 0.5#

systemd-analyze security는 unit의 하드닝 수준을 0(안전)~10(노출)으로 매긴다. 게스트 안 점수(7.6)는 VM에서 오프라인으로도 똑같이 나온다(--offline=true는 unit 파일만 읽는다). 그래서 VM에서 바로 고치면서 쟀다.

[Service]에 다음 줄을 더했다 (각 항목의 뜻은 L1·L6). 데몬이 실제로 쓰는 것은 open/read/nanosleep/write와 장치 하나뿐이라 거의 다 막을 수 있다.

남은 항목은 의도한 것이다: 장치 접근(PrivateDevices를 켜면 우리 장치도 못 본다), char-rtc는 ProtectClock이 자동으로 넣은 읽기 ACL이다. 하드닝이 동작을 깨지 않았는지는 같은 2-부팅 테스트를 다시 돌려 확인했다 — 보고 내용은 위와 같고 마지막 줄만 바뀌었다.

그림 2 — 같은 데몬, unit 파일만 바꿔서 잰 노출 점수(VM에서 --offline=true, 게스트 안에서도 같은 값). 동작은 2-부팅 테스트로 다시 확인했다. GitHub README에 넣기 좋은 숫자다.

이 단계가 끝나면: 두 initramfs 모드가 rmmod ok로 끝나고, systemd 게스트 보고에 enabled / active, 0.5 SAFE가 보여야 한다.

9. Step 8 — 정적 검사: lint · yamllint · bash -n#

9.1 왜 BitBake 밖 lint가 필요한가#

BitBake 파서(tinfoil)는 레시피 하나씩 돌려야 하고 환경 준비가 필요하다. 커밋 전 훅이나 CI 첫 단계에서는 1초 안에 끝나는 검사가 유용하다. K5 11.1의 lint가 "vendor layer와의 연결"(require 경로, dangling bbappend)을 봤다면, 이 lint는 우리 파일 안의 문법·관례를 본다: 옛 override 문법, 따옴표 짝, S = "${WORKDIR}", 라이선스 md5 대조, SRC_URI 파일 존재, bbappend의 FILESEXTRAPATHS :=, override 없는 SRC_URI 변경. 전체 63줄 중 검사 본체만 옮긴다(앞 19줄은 인자 처리와 LAYERSERIES_COMPAT 대조).

9.2 실행 — 깨끗한 layer와 일부러 망가뜨린 사본#

yamllint은 저장소의 .yamllint(기본 규칙 + 줄 길이 120 + on: 키 허용)로 kas 파일 7개와 CI 워크플로를 검사했다. 이제 사본(/var/tmp/S6/badlayer)에 흔한 실수 6개를 심는다.

9.3 lint가 BitBake보다 나은 지점 — 조용히 무시되는 옛 문법#

같은 실수 두 개를 진짜 BitBake 파서에 넣어 봤다(원본 레시피를 잠시 고치고 확인 후 되돌렸다).

출력에서 볼 것: 첫 번째는 BitBake도 파싱 단계에서 막는다. 두 번째는 에러 없이 통과한다 — RDEPENDS_${PN}은 이제 override가 아니라 RDEPENDS_donlab-sensord라는 아무도 읽지 않는 새 변수일 뿐이다. 옛 레시피를 복사해 오면 런타임 의존성이 조용히 사라지고, 기기에서 "bash: not found"로 터진다. (BitBake는 _append/_prepend/_remove 같은 옛 연산자 문법은 에러로 잡지만, 패키지 이름 override는 일반 변수 이름과 구별할 방법이 없다.) 이런 것이 정적 lint를 CI에 두는 이유다.

이 단계가 끝나면: 원본 layer는 0 error, 망가뜨린 사본은 6 error가 나와야 한다.

10. Step 9 — OTA 훅 자리 (RAUC / SWUpdate)#

OTA 설계 자체(A/B 슬롯, bootcount, 서명)는 L4에 있다. 이 프로젝트는 "OTA layer를 붙이면 바로 bundle을 만들 수 있는 자리"만 만든다. 핵심은 2.1절의 BBFILES_DYNAMIC이다 — meta-rauc가 없는 빌드에서는 inherit bundle 레시피를 아예 파싱하지 않는다.

DISTRO_FEATURES += "rauc"는 meta-rauc README의 1번 단계다(README.rst 62행에서 확인). SWUpdate 쪽(donlab-swu.bb + sw-description)도 같은 구조로 넣었다.

그리고 BBFILES_DYNAMIC이 실제로 조건부인지 — 기본 빌드와 rauc 빌드의 최종 BBFILES 중 우리 layer 항목만 비교했다.

출력에서 볼 것: meta-rauc의 컬렉션 이름 rauc(priority 6)가 BBLAYERS에 있을 때만 dynamic-layers/rauc 경로가 붙는다. 기본 빌드는 RAUC 레시피를 보지도 않는다. 이 placeholder로 실제 bundle을 만들려면 L4 6절의 키 체계, rauc-conf의 system.conf(슬롯 정의), 부트로더 연동(U-Boot bootcount)이 더 필요하다 — 그래서 이름이 placeholder다.

이 단계가 끝나면: OTA overlay 두 개에서 placeholder 레시피가 exit 0으로 파싱되고, 기본 빌드의 BBFILES에는 dynamic-layers가 없어야 한다.

  • lint: 사람의 실수(옛 문법, md5, 경로)를 1분 안에 돌려준다. PR마다 돈다.
  • parse: bitbake -p(전체 파싱)는 빌드 없이 "모든 레시피가 이 조합에서 파싱되는가"를 본다 — 의존 layer의 브랜치가 움직였을 때 가장 먼저 깨지는 곳이다. GitHub의 Ubuntu 24.04 runner에도 이 VM과 같은 AppArmor 제한이 있으면 sysctl로 푼다(runner VM은 일회용이라 괜찮다. 이 랩 VM에서는 하지 않는다). 이 잡이 runner에서 실제로 통과하는지는 확인하지 않았다(가이드).
  • build: GitHub 호스트 runner는 디스크(수십 GB)와 시간 제한 때문에 Yocto 첫 빌드에 맞지 않는다(기억 기반). 그래서 runs-on: [self-hosted, linux, yocto]. kas/ci.yml이 공유 캐시 경로와 testimage(runqemu로 부팅해 ping · ssh · systemd 검사)를 켠다.

워크플로 파일의 build 잡 부분이다.

kas dump로 overlay가 제대로 겹쳐지는지는 실제로 확인했다(앞부분 생략).

14. 커널 안에서는 무슨 일이 일어나나 — 부팅부터 journal까지#

이미지가 부팅되면 레시피가 남긴 파일들이 이 순서로 맞물린다. 8.2절의 두 번째 부팅이 정확히 이 경로를 탔다.

그림 5 — 부팅 시 경로. 파랑은 systemd 쪽, 주황은 커널 쪽, 초록은 둘이 만나는 장치 노드. 레시피 변수 두 개(KERNEL_MODULE_AUTOLOAD, module_conf_*)와 unit 파일 하나가 이 경로 전체를 정한다.

단계별로 커널 구조체와 연결하면:

  1. modprobe는 modules.dep(이미지 생성 때 depmod가 만든 것)에서 경로를 찾고 finit_module() syscall로 .ko를 넘긴다. 커널은 ELF를 재배치하고 vermagic을 확인한 뒤 module_init 함수(donlab_init)를 부른다(E3). vermagic이 다르면 여기서 Invalid module format — Yocto에서는 모듈 레시피가 같은 커널 빌드 트리로 빌드되므로 일어나지 않는다. 이 프로젝트가 out-of-tree 모듈을 레시피로 만든 가장 큰 이유다.
  2. platform_driver_register()가 드라이버를 platform 버스에 올리면 버스의 match가 기존 장치들과 짝을 찾는다: DT에서 온 장치는 of_match_table의 compatible 문자열로, fake 장치는 이름("donlab-sensor")으로 맞는다(G2). 짝이 맞으면 probe.
  3. misc_register()는 동적 minor를 받고 device_create()로 struct device를 만든다. devtmpfs가 즉시 /dev/donlab_sensor를 만들고, uevent가 udev로 간다(G9). 그래서 ConditionPathExists가 확인하는 시점에 노드가 있다.
  4. 데몬의 read()는 VFS → misc_open이 바꿔 끼운 file_operations의 .read(donlab_read)로 간다. f->private_data가 struct miscdevice를 가리키도록 misc 코어가 넣어 주기 때문에 container_of로 드라이버 상태를 찾는다(F 모듈, A3).
  5. systemd의 DeviceAllow=는 cgroup v2의 BPF device 프로그램으로 구현된다 — 커널이 open() 때 (char, 10, 258, read) 접근을 검사한다. DevicePolicy=closed면 목록 밖 장치는 EPERM.

15.2 장면 — "새 보드에서 센서 서비스가 안 뜬다"#

15.3 장면 — "보안 감사에서 데몬이 root로 돈다고 지적받았다"#

8.3절이 답이다. DynamicUser와 하드닝 줄을 넣고 systemd-analyze security 점수를 감사 보고서에 붙인다. 장치 접근은 udev 규칙으로 그룹을 주거나(L2), 이 프로젝트처럼 드라이버가 노드 권한을 정한다. 이미지에 들어간 버전을 증명하는 것은 SPDX SBOM이다(K7).

19. 면접에서 이렇게 말한다#

Q. How did you add your out-of-tree driver to the Yocto image?

A. inherit module 레시피로 만들었다. module.bbclass가 커널 레시피가 공개한 같은 빌드 트리로 빌드하니까 vermagic이 항상 맞는다. .ko 이름에서 kernel-module-donlab-sensor 패키지가 자동으로 생기고, KERNEL_MODULE_AUTOLOAD가 modules-load.d 파일을 만들어 부팅 때 systemd가 로드한다. machine conf의 MACHINE_EXTRA_RRECOMMENDS로 이미지가 따로 적지 않아도 들어가게 했다.

I packaged it as a recipe that inherits module, so it is built against the exact kernel build tree the kernel recipe exports — vermagic can never mismatch. The .ko becomes a kernel-module-* package automatically, KERNEL_MODULE_AUTOLOAD generates the modules-load.d entry so systemd loads it at boot, and the machine pulls it in through MACHINE_EXTRA_RRECOMMENDS.

꼬리 질문: "DT가 있는데 왜 autoload가 필요한가?" → modalias로 udev가 로드할 수도 있지만, QEMU처럼 노드가 없는 machine을 위해 명시적 경로를 뒀다(module_conf로 fake 장치).

Q. How do you change the kernel configuration in Yocto without forking the defconfig?

A. 커널 레시피에 bbappend를 달고 기능 단위 .cfg fragment를 SRC_URI에 넣는다. kernel-yocto가 BSP 설정 위에 병합하고 do_kernel_configcheck가 "요청한 값이 살아남았는지" 감사한다. 의존성 때문에 조용히 빠지는 옵션이 있어서 KMETA_AUDIT_WERROR로 경고를 빌드 실패로 바꿨다. 모든 변경은 machine override로 감쌌다 — layer를 추가만 해서 다른 보드 커널이 바뀌면 안 되니까.

A bbappend on the kernel recipe adds a feature-sized .cfg fragment. kernel-yocto merges it on top of the BSP config and do_kernel_configcheck audits that every requested value survived; I set KMETA_AUDIT_WERROR so a silently dropped option fails the build. Everything is guarded by the machine override so the layer is inert for other machines.

Q. What is the difference between a BSP layer, a distro layer and a product layer?

A. BSP는 "어떤 하드웨어인가"(machine conf, 커널·부트로더 레시피, DT), distro는 "어떤 OS 정책인가"(init 시스템, DISTRO_FEATURES, 패키지 형식, 라이선스 정책), product는 "무엇을 싣나"(앱·드라이버 레시피, 이미지). 셋을 나누면 같은 이미지를 여러 보드에 빌드하고, 보드를 바꿀 때 BSP만 바꾼다.

BSP answers "what hardware" — machine, kernel, bootloader, device tree. Distro answers "what OS policy" — init system, distro features, package format, license policy. Product answers "what we ship" — our recipes and images. Keeping them separate means one image recipe builds for the EVK, the prototype and the production board.

Q. How do you make a Yocto build reproducible for your team and CI?

A. kas 파일 하나에 layer와 브랜치를 적고 kas lock으로 커밋을 박제해 lock 파일을 커밋한다. 레시피는 SRCREV로 고정한다. CI는 lint → 전체 파싱 → self-hosted runner의 빌드로 나누고, DL_DIR · sstate를 runner에 영구 보관해 증분 빌드를 분 단위로 만든다. buildhistory와 SPDX로 "무엇이 들어갔나"를 남긴다.

One kas file describes the layers, kas lock pins every repo to a commit and the lock file is committed, recipes pin SRCREV. CI runs lint, a full parse, then the image build on a self-hosted runner with persistent downloads and sstate. buildhistory and SPDX record exactly what went into each image.

Q. You derived a machine from qemuarm64 and the kernel recipe disappeared. Why?

A. require로 값은 가져오지만 override 이름은 새 MACHINE 이름이 된다. linux-yocto의 COMPATIBLE_MACHINE과 KBRANCH:qemuarm64가 맞지 않아 레시피가 SKIPPED 됐다. MACHINEOVERRIDES =. "qemuarm64:"로 부모 override를 살리고, kernel-cache 조회용 KMACHINE도 부모 이름으로 맞춘다. 파서로 SKIPPED 이유를 직접 확인했다.

require copies the values but the override name becomes the new MACHINE, so COMPATIBLE_MACHINE and the :qemuarm64 overrides stop matching and linux-yocto is skipped. Prepending qemuarm64: to MACHINEOVERRIDES and setting KMACHINE fixes it; I confirmed the skip reason with the BitBake parser.

Q. How do you handle a do_package_qa error?

A. 메시지가 QA 이름을 알려 준다. ldflags면 빌드 시스템이 LDFLAGS를 안 쓰는 것, file-rdeps면 RDEPENDS 누락, installed-vs-shipped면 FILES 누락, usrmerge면 하드코딩 경로. 원인을 고치는 게 원칙이고 INSANE_SKIP은 고칠 수 없는 바이너리에만, 이유를 주석으로 남겨서 쓴다.

The message names the check. ldflags means the build ignores our LDFLAGS, file-rdeps a missing RDEPENDS, installed-vs-shipped a missing FILES entry, usrmerge a hard-coded /lib path. I fix the cause; INSANE_SKIP is only for prebuilt blobs and always comes with a comment.

Q. How did you test the image content without hardware?

A. 두 겹이다. 빌드 전에는 파서와 lint, 그리고 레시피가 쓰는 make/cmake 명령을 Yocto 밖에서 같은 커널 트리로 돌려 QEMU initramfs에서 DT 경로와 fake 경로를 둘 다 확인했다. 이미지 수준에서는 systemd 게스트에 설치 트리를 깔고 재부팅해서 자동 로드 · 서비스 · journal을 확인했다. 빌드 서버에서는 같은 확인을 testimage로 자동화한다.

Two layers. Before building, the parser, a lint, and the recipes' own make/cmake steps run outside Yocto against the same kernel tree, booted in QEMU for both the device-tree and the fallback path. At image level I installed the package tree into a systemd guest and rebooted to verify autoload, service and journal. On the build server the same checks become a testimage suite.

  1. donlab-qemu.conf에서 MACHINEOVERRIDES 줄을 지우고 bitbake-getvar --value KBRANCH -r linux-yocto를 해 보라(빌드 호스트에서). 무엇이 나오나? 정답/힌트: 레시피가 SKIPPED라 값을 못 얻는다. 파서 스크립트로는 6.6절의 SKIPPED 메시지.
  2. donlab.cfg에 CONFIG_IIO_ST_LSM6DSX=y를 넣고 check-kernel-fragment.sh를 돌려라. 살아남나? I2C 쪽 드라이버(IIO_ST_LSM6DSX_I2C)는? 정답/힌트: 핵심 옵션은 OK(랩 defconfig에 I2C · SPI가 있음). I2C 인터페이스 옵션은 default I2C && IIO_ST_LSM6DSX라 자동으로 켜진다 — Kconfig에서 default가 하는 일.
  3. 데몬 레시피를 inherit cmake 대신 손 Makefile + do_compile() { ${CC} -o ... }로 바꿨을 때 어떤 QA 에러가 날지 예측하고, 고친 do_compile을 써라. 정답/힌트: ldflags(GNU_HASH). ${CC} ${CFLAGS} ${LDFLAGS} ....
  4. module_conf_donlab_sensor를 지우고 KERNEL_MODULE_PROBECONF만 남기면 어떻게 되나? 반대로 하면? 정답/힌트: 4.2절 grep의 136행 — module_conf_*만 있으면 에러. PROBECONF만 있고 conf가 없으면 modprobe.d 파일이 안 생긴다.
  5. systemd 게스트 테스트에서 ConditionPathExists를 지우고, modules-load.d 파일도 지운 상태로 부팅하면 서비스 상태는? Restart=on-failure가 무엇을 하나? 정답/힌트: open 실패로 exit 1 → RestartSec=2마다 재시작 → 기본 start limit(StartLimitBurst/StartLimitIntervalSec)을 넘으면 failed. Condition이 있으면 "건너뜀"으로 끝난다.
  6. systemd-analyze security --offline=true로 SystemCallFilter= 줄만 지웠을 때 점수가 얼마나 오르는지 재 보라. 정답/힌트: VM에서 바로 잴 수 있다. 어느 항목이 가장 무거운지 출력 목록에서 찾는다.
  7. kas/donlab.lock.yml을 지우고 kas checkout 출력의 경고를 다시 보라. lock이 있을 때와 무엇이 다른가? 정답/힌트: "Using branch without commit ... is unsafe" 경고가 lock이 있으면 사라진다.

22. 요약 & 체크리스트#

meta-donlab은 Yocto 6.0 "wrynose" 위의 제품 layer 하나에 machine(donlab-qemu) · distro(donlab) · out-of-tree 드라이버 레시피 · CMake/systemd 데몬 레시피 · 커널 bbappend(fragment + DT overlay) · 이미지 레시피 · OTA 자리 · kas 프로젝트와 lock · lint · 테스트 · CI를 담았다. 이미지 빌드는 하지 않았지만, BitBake 파서로 모든 레시피와 변형(RO · dev · OTA)을 파싱했고, 레시피가 패키징할 파일을 Yocto 밖에서 같은 방식으로 빌드해 QEMU initramfs(DT · fake 두 경로)와 systemd 게스트(재부팅 후 자동 로드 · 서비스 · journal)에서 동작을 확인했다. 그 과정에서 파생 machine의 override 함정(SKIPPED), fragment 옵션 탈락, 옛 문법이 조용히 무시되는 문제, unit의 [Install] 누락을 실제로 재현했고, 서비스 하드닝으로 노출 점수를 7.6에서 0.5로 낮췄다.
