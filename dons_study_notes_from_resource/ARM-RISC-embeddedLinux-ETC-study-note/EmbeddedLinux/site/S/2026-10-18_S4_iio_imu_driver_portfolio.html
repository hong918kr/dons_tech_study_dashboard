0.1 왜 실제 칩이 아니라 가상의 칩인가#

실제 부품(BMI160, ICM-42688 등)을 흉내 내면 Don이 데이터시트와 다른 값을 "그 칩의 사양"처럼 쓰게 될 위험이 있다. 그래서 S4IMU라는 가상의 칩을 정의하고 레지스터 맵을 docs/register_map.md에 문서로 고정했다. WHO_AM_I, burst로 읽는 little-endian 데이터 블록, 프레임 단위 FIFO + watermark, clear-on-read 상태 레지스터 같은 흔한 패턴만 빌려 왔다. 실제 칩으로 옮길 때 바뀌는 것은 10절에 정리했다.

2. 단계 1 — regmap 설정: 칩의 성격을 표로 적는다#

H2 7절에서 배운 분류를 이 칩에 그대로 적용한다. 핵심은 "어느 레지스터가 칩 스스로 바뀌는가(volatile), 어느 레지스터를 읽으면 부작용이 있는가(precious), 어느 레지스터가 FIFO 포트인가(noinc)"다.

(rd_table/wr_table도 같은 regmap_reg_range 표다. 쓰기 전용 CMD는 rd 표에 없다.)

이 표가 주는 효과 세 가지는 3절 smoke 테스트 출력에서 눈으로 확인된다: (1) in_accel_scale을 읽을 때 ACC_RANGE를 캐시에서 읽으므로 I2C 트랜잭션이 0회다. (2) debugfs의 registers 덤프가 0x03과 0x32를 건너뛴다(precious라서 덤프가 INT_STATUS를 지워 버리거나 FIFO를 비우는 사고가 안 난다). (3) regmap_noinc_read(FIFO_DATA, buf, n * 14)가 한 번의 I2C 읽기로 FIFO를 통째로 가져온다.

FIFO_CTRL이 volatile인 이유도 한 줄 적어 둔다: FLUSH 비트가 self-clearing이라 캐시에 FLUSH=1이 남으면 다음 update_bits가 FIFO를 다시 비워 버린다.

흔한 실패: INT_STATUS를 volatile에만 넣고 precious에 안 넣으면 cat registers 한 번에 래치된 인터럽트가 사라져 스트림이 멈춘다(7.3절과 같은 증상). FIFO_DATA를 noinc로 표시하지 않으면 regmap이 주소를 증가시키며 읽어 0x32, 0x33, 0x34…를 읽는다.

3. 단계 2 — 채널, sysfs, probe, 그리고 첫 부팅#

3.1 채널 정의#

accel x/y/z, anglvel x/y/z (scan 0–5), temp(raw·scale·offset, scan 6), IIO_CHAN_SOFT_TIMESTAMP(7). ODR은 accel과 gyro가 공유하므로 shared_by_all → 파일 이름이 in_accel_sampling_frequency가 아니라 그냥 sampling_frequency다. scale 값은 IIO_VAL_INT_PLUS_NANO로 돌려준다: ±2 g에서 1 LSB = 9.80665 × 2 / 32768 = 0.000598550 m/s², ±2000 dps에서 1 LSB = 2000/32768 × π/180 = 0.001065264 rad/s (MICRO 정밀도면 0.000598로 잘려 0.05 % 오차가 난다). 온도는 (raw + offset) × scale = (raw + 6400) × 3.90625 m°C (6400 = 25 °C × 256).

3.2 probe의 순서와 에러 처리#

규칙 세 가지:

  • 모든 자원이 devm이다(iio_dev, mutex, regulator, IRQ, trigger, buffer, PM enable, iio 등록, 그리고 devm_add_action_or_reset(s4imu_power_off)). remove 함수가 없다. devm 해제는 등록의 역순이므로 "iio 장치 해제 → PM disable → 칩 suspend → regulator off" 순서가 자동으로 맞는다(G3 수명 주기).
  • 모든 실패 경로가 dev_err_probe()다. 메시지에 에러 코드 이름이 붙고(error -ENODEV: ...), -EPROBE_DEFER면 로그 대신 deferred 사유로 기록된다(/sys/kernel/debug/devices_deferred).
  • chip_init에서 soft reset 직후 regcache_mark_dirty()를 부른다. 칩이 기본값으로 돌아갔으니 캐시를 믿으면 안 된다는 표시다.

s4imu_chip_init은 soft reset → WHO_AM_I 확인 → ODR 100 Hz, ±2 g, ±2000 dps, INT 극성 → PWR normal + 첫 DRDY 대기 순서다. WHO_AM_I가 다르면 dev_err_probe(dev, -ENODEV, "unexpected WHO_AM_I 0x%02x\n", id).

3.3 실행 — DT overlay로 probe하고 sysfs 읽기#

QEMU의 -kernel 부팅에는 bootloader가 없으니, overlay를 빌드 시점에 base DTB에 병합한다(U-Boot의 fdt apply나 RPi 펌웨어의 dtoverlay=가 부팅 때 하는 일을 미리 하는 것, D6).

가짜 칩 노드가 I2C 버스이면서 인터럽트 컨트롤러다. IMU 노드는 실제 보드와 똑같이 reg, interrupts, mount-matrix를 가진다. 드라이버 입장에서는 실제 보드와 구별할 방법이 없다 — 이것이 이 하네스의 핵심 설계다(4절).

run.sh는 BusyBox initramfs를 복사해 .ko·도구·게스트 스크립트를 넣고, LAB_CMD=sh~/s4/guest_smoke.sh로 부팅한다. smoke 테스트 출력(핵심 부분, 실행마다 raw 값은 다르다):

출력에서 볼 것:

  • /proc/interrupts에 irq_sim 0 Edge s4imu — DT의 interrupts가 가짜 칩의 irq_sim 도메인으로 해석되어 virq 22가 됐다. 버퍼를 켜기 전이라 카운트는 0이다.
  • supply vdd not found, using dummy regulator는 정상이다. DT에 vdd-supply가 없을 때 regulator core가 dummy를 준다. 실제 보드에서는 이 줄이 없어야 한다(10절).
  • accel z = 16400 ≈ 1 g × 16384 LSB/g. ±8 g로 바꾸면 4102 ≈ 16384/4. 온도 raw 1280 → (1280 + 6400) × 3.90625 = 30000 m°C = 30 °C(가짜 칩 값).
  • 표에 없는 scale(0.5)은 -EINVAL로 거절된다.

(가운데 11:–16: 줄은 생략.) 0x03(INT_STATUS)이 목록에 없다 — precious라서 regmap debugfs가 덤프에서 뺐다. 0x32(FIFO_DATA)도 마찬가지다. 0x38 = 0x10은 INT_CTRL의 active-high 비트만 켜진 상태(버퍼 off), 0x3e = 1은 normal 모드다.

체크포인트: 이 단계가 끝나면 /sys/bus/iio/devices/iio:device0/name이 s4imu이고, in_accel_z_raw가 16384 근처이며, /proc/interrupts에 s4imu 줄이 보여야 한다.

3.4 runtime PM — 쓰지 않으면 잠든다#

probe 직후 active → 2 s 동안 아무도 안 쓰면 runtime_suspend 콜백이 PWR_CTRL=0을 쓰고 suspended. cat in_accel_z_raw가 pm_runtime_resume_and_get()으로 깨우고(PWR normal + 2 ms start-up + 첫 DRDY 대기), pm_runtime_put_autosuspend()로 타이머를 다시 건다. 다시 잠든 뒤 1 s 간격으로 가짜 칩의 samples 카운터가 508에서 멈춰 있다 — 칩이 실제로 샘플링을 멈췄다는 증거다. 버퍼가 켜져 있는 동안은 preenable에서 get, postdisable에서 put이라 잠들지 않는다. 시스템 슬립은 SYSTEM_SLEEP_PM_OPS(pm_runtime_force_suspend, pm_runtime_force_resume)로 같은 콜백을 재사용한다(N6).

이 칩은 suspend 중에도 레지스터가 유지되므로 regcache를 건드리지 않는다. 전원 자체를 끄는 보드라면 H2 9절의 regcache_cache_only() + regcache_mark_dirty() + regcache_sync()가 필요하다(10절 표).

3.5 드라이버를 우회해 같은 칩 보기#

i2ctransfer -f -y 0 w1@0x68 0x00 r2 — 포인터 0x00을 쓰고 2바이트 읽기(WHO_AM_I, REV_ID). -f는 드라이버가 붙어 있어도 강제로. bring-up 때 "드라이버 문제인가 버스 문제인가"를 가르는 첫 도구다(P3 7절). 마지막으로 rmmod s4imu_i2c s4imu_core s4imu_emul이 경고 없이 끝난다 — devm 정리가 맞다는 최소한의 확인이다.

4. 단계 3 — 테스트 하네스: 하드웨어 없이 "살아 있는" IMU#

4.1 i2c-stub으로는 왜 안 되나#

Q5 2절과 P3 4절은 i2c-stub에 레지스터 값을 미리 써 두고 upstream 드라이버를 probe했다. probe와 단위 변환을 확인하기에는 충분하지만, 값이 변하지 않고 인터럽트가 없다. 버퍼·트리거·FIFO·타임스탬프는 시험할 수 없다. 선택지는 세 가지였다.

방법장점단점

4.2 가짜 칩의 세 부품#

① I2C adapter — i2c_algorithm.xfer(6.18에서 master_xfer는 deprecated 별칭) 하나로 레지스터 포인터 모델을 구현한다. 쓰기 메시지의 첫 바이트가 포인터, 나머지는 쓰기 데이터. 읽기는 포인터부터 auto-increment, 단 FIFO_DATA에서는 증가하지 않는다. 주소가 0x68이 아니면 -ENXIO(NACK).

emul_read()가 레지스터별 부작용을 구현한다: STATUS 읽으면 DRDY 클리어, INT_STATUS 읽으면 전체 클리어 + WTM 래치 해제, FIFO_DATA 읽으면 1바이트 pop(14바이트마다 프레임 하나 감소). 스핀락은 irqsave — hrtimer 콜백(hard IRQ 컨텍스트)과 같은 상태를 공유하기 때문이다(F4).

② irq_sim 인터럽트 컨트롤러 — devm_irq_domain_create_sim(dev, dev_fwnode(dev), 1)로 자기 DT 노드를 fwnode로 하는 irq 도메인을 만든다. 그러면 IMU 노드의 interrupts = <0 ...>이 일반 of_irq_get() 경로로 이 도메인의 hwirq 0에 매핑된다. irq_sim 도메인에는 xlate가 없어서 irq_domain_translate()가 param[0]을 hwirq로 쓰고 트리거 타입은 무시한다 — 그래서 드라이버는 타입이 NONE이면 rising으로 요청한다. 라인을 올리는 것은 irq_set_irqchip_state(virq, IRQCHIP_STATE_PENDING, true)이고, irq_sim이 irq_work로 generic_handle_irq()를 불러 드라이버의 hard IRQ 핸들러가 실제 hard IRQ 컨텍스트에서 돈다(H6, F6).

③ hrtimer = 센서 발진기 — HRTIMER_MODE_ABS_HARD 타이머가 ODR 주기로 돈다. 콜백이 늦게 깨어나도 그 사이 칩이 만들었어야 할 샘플을 모두 만든다(catch-up 루프). 각 샘플의 "진짜 시각"은 콜백이 깨어난 시각이 아니라 이상적 발진기 시각 e->next다. 실제 센서도 자기 시계로 샘플링하고, CPU가 늦게 알아챌 뿐이니까.

emul_sample()는 1 Hz 사인파(accel x, 0.5 g 진폭, fixp_sin32_rad()), 1 g + 노이즈(accel z), 0.5 Hz 사인(gyro z, 90 dps)을 range 레지스터에 맞는 LSB로 만들어 데이터 레지스터와 FIFO에 넣고, truth 링(8192개)에 (seq, 이상적 시각 ns)를 적는다. 모듈 파라미터:

설계 원칙 하나: 가짜 칩은 드라이버의 표를 공유하지 않는다. ODR 표, 레지스터 의미를 자기 코드로 따로 가진다. 처음에는 s4imu_odr_period_ns()를 가져다 썼는데, 그러면 드라이버 표가 틀려도 테스트가 통과한다. 테스트 대상과 테스트 오라클을 분리하는 것은 Don이 SSD 검증에서 "펌웨어가 쓴 로그로 펌웨어를 검증하지 않는다"고 하던 원칙과 같다.

트리거는 devm_iio_trigger_alloc() + devm_request_irq(..., iio_trigger_generic_data_rdy_poll, flags 그리고 IRQF_NO_THREAD, ...)로 만든다. hard IRQ는 트리거를 poll만 하고, 트리거에 붙은 pollfunc의 top half iio_pollfunc_store_time이 hard IRQ 안에서 시각을 찍는다. 실제 I2C 읽기는 pollfunc의 스레드(s4imu_trigger_handler)에서 한다 — I2C는 잠들 수 있으니 hard IRQ에서 못 한다(F2, F7). 트리거에 .validate_device = iio_trigger_validate_own_device를 걸어 다른 장치가 이 트리거를 못 쓰게 한다.

FIFO 모드로 들어가는 스위치는 표준 ABI buffer/watermark다. IIO core가 버퍼를 켤 때 info->hwfifo_set_watermark(indio_dev, watermark)를 부르고, 드라이버는 값을 저장했다가 트리거의 set_trigger_state(true)에서 1이면 DRDY, 2 이상이면 FIFO_WTM 설정 + FLUSH + 래치 해제 + WTM_EN을 쓴다. 이 순서(preenable → update_scan_mode → hwfifo_set_watermark → 버퍼 enable → 트리거 attach(set_trigger_state) → postenable)는 drivers/iio/industrialio-buffer.c의 iio_enable_buffers()에서 확인했다.

그림 3 — FIFO 모드의 시간축. 칩은 자기 시계로 샘플링하고, W번째 샘플에서 WTM이 래치되고, CPU는 지연 L 뒤에 hard IRQ에서 시각을 하나 찍는다. 스레드가 n개를 꺼내면 추정기가 n개의 시각을 만든다. 아래 두 상자는 7절에서 찾은 두 가지 예외 경로다.

5.2 트리거 핸들러와 FIFO drain#

레지스터 맵에서 INT_STATUS(0x03)와 FIFO_CNT(0x04–05)를 붙여 놓은 이유가 여기서 보인다: 3바이트 burst 하나로 "왜 깨었나 + 몇 개 있나"를 한 번에 읽는다. 실제 칩을 고를 때도 이런 배치를 보면 배치당 I2C 트랜잭션 수를 줄일 수 있다. fifo_buf는 __aligned(IIO_DMA_MINALIGN) — I2C 컨트롤러가 DMA로 쓸 수 있는 버퍼는 캐시라인 정렬이 필요하다(H9).

irq_ns == 0인 호출과 ovr 분기는 처음 버전에는 없었다. 7절에서 실측으로 찾은 버그 두 개의 수정이다.

5.3 타임스탬프 추정기 (Q5 방법 D의 커널 정수 버전)#

Q5 4.2절은 double로 네 방법을 비교했고 "측정 주기 + 앵커 평활(D)"이 간격 오차 1 µs로 가장 좋았다. 커널에는 부동소수점이 없으니 s64 ns와 shift로 옮긴다.

프레임 i(0 = 가장 오래됨)의 시각은 anchor − (n − 1 − i) × period. 32비트 ARM(BeagleBone 등)에서도 빌드되게 64비트 나눗셈은 전부 div_s64()다. 4)번 단조성 규칙은 첫 캡처에서 nonmono=1이 한 번 나온 뒤 추가했다. upstream inv_sensors_timestamp.c가 같은 생각(IRQ 간격 ÷ 샘플 수로 칩 주기 추정, 허용 범위 밖 값은 버림, 앵커를 조금씩만 당김)을 쓴다는 것은 Q5 4.3절에 정리돼 있다.

결과에서 읽을 것:

  • FIFO가 지터와 드롭 모두 이긴다. DRDY는 샘플마다 IRQ → 스레드 → I2C 읽기를 해야 하고, 스레드가 다음 IRQ 전에 끝나지 않으면 그 IRQ가 버려진다(7.3절의 메커니즘) → 드롭. FIFO는 칩이 버퍼링하므로 CPU가 늦어도 샘플이 안 사라지고, 간격은 추정기가 매끈하게 만든다.
  • DRDY의 ts−truth 평균 = IRQ 지연이다. 50 Hz에서 4 ms라는 큰 값은 최종 실행 당시 VM이 다른 게스트로 바빴던 결과다(저부하 실행에서는 317 µs). 이 숫자는 하드웨어 성능이 아니라 TCG + 공유 VM의 성능이다.
  • hrtimer 폴링은 드롭과 중복을 동시에 만든다. 트리거 타이머와 칩 발진기가 같은 공칭 주기지만 위상이 독립이라, 한 주기에 두 번 읽으면 같은 샘플(dup), 한 번도 못 읽으면 drop이 된다. 200 Hz에서 ts−truth가 0~5 ms(한 주기)에 고르게 퍼지는 것도 같은 이유다 — 타임스탬프는 "읽은 시각"이지 "샘플된 시각"이 아니다. 음수 오차는 트리거 시각을 먼저 찍고 레지스터를 나중에 읽는 사이에 새 샘플이 들어온 경우다. IRQ 없는 보드에서 hrtimer는 "동작은 하는" 폴백일 뿐이고, 정확도가 필요하면 IRQ 핀을 배선해야 한다는 근거다.
  • period_est: 800 Hz에서 1247992 ns(공칭 1250000), 1600 Hz에서 622364 ns(공칭 625000). TCG의 시계 흔들림을 추정기가 그대로 따라간 값이다.

7.2 발진기 오차 추적 (clk_ppm=10000)#

(커널 명령줄의 알 수 없는 KEY=VALUE는 init의 환경 변수가 된다 — 게스트 스크립트에 값을 넘기는 간단한 방법.)

칩이 1 % 빠르면 실제 주기는 1250000 / 1.01 = 1237624 ns이고 공칭과의 차이는 −12.4 µs다. dt-T mean=-12.4가 정확히 그 값이고, 추정기 period_est=1237129는 진짜 주기와 0.04 % 차이다. Q5 4.2의 방법 B(공칭 주기로 채우기)였다면 배치 앞쪽 프레임이 15 × 12.4 = 186 µs씩 틀렸을 것이다.

7.3 버그 1 — 잃어버린 edge가 스트림을 멈춘다#

첫 캡처 매트릭스는 FIFO 1600 Hz에서 멈췄다.

원인은 IIO core 코드에 있다(drivers/iio/industrialio-trigger.c, 6.18.55):

이전 배치의 스레드가 아직 iio_trigger_notify_done()을 안 불렀으면(use_count != 0) 새 IRQ는 조용히 버려진다. DRDY(펄스) 모드에서는 그 샘플 하나가 드롭될 뿐이지만(7.1의 DRDY drops가 바로 이것), WTM은 래치라서: 스레드가 INT_STATUS를 읽어 래치를 푼 뒤 → notify_done 전에 다음 W개가 차서 WTM이 다시 래치되고 IRQ가 올라옴 → 버려짐 → 래치는 INT_STATUS를 읽을 때까지 안 풀림 → 그런데 INT_STATUS는 다음 IRQ의 핸들러만 읽음 → 영원히 멈춤. 1600 Hz에서 배치 간격(10 ms)이 TCG의 핸들러 시간에 가까워지며 드러났다.

고친 방법: 트리거의 .reenable 콜백. iio_trigger_notify_done()이 use_count를 0으로 만들 때 이것을 동기적으로(스레드 컨텍스트에서) 부른다. 여기서 INT_STATUS의 WTM 비트를 보고 켜져 있으면 바로 drain한다. 그 배치에는 IRQ 시각이 없으니 s4imu_ts_batch_no_irq()로 anchor + n × period 외삽하고, 다음 진짜 IRQ에서 pending 프레임 수까지 합쳐 주기를 잰다.

수정 후 같은 1600 Hz가 drops=0으로 끝나고 debugfs lost_edges가 1~26을 보고한다(실행마다 다름). 이 카운터가 0이 아니라는 것 자체가 "이 버그가 실제로 일어나는 조건"이라는 증거다. 실제 칩에서도 같은 일이 생긴다: 래치형 인터럽트 + edge IRQ + 처리 중 무시하는 상위 계층의 조합. upstream FIFO IMU 드라이버(st_lsm6dsx, inv_icm42600)가 IIO trigger 대신 request_threaded_irq() + IRQF_ONESHOT으로 FIFO를 직접 읽는 이유 중 하나로 볼 수 있다(그들의 설계 의도를 문서로 확인한 것은 아니다).

7.4 버그 2 — overflow 뒤의 타임스탬프 20 ms 오차#

watermark 48(FIFO 여유 16 프레임 = 800 Hz에서 20 ms)로 돌렸을 때 TCG 정체 한 번에 overflow가 났다:

드롭 16개는 정상이지만(칩이 버렸다), ts−truth max = 20 ms는 드라이버 잘못이다. 그때 코드는 overflow를 보면 추정기를 리셋하고 IRQ 시각으로 다시 앵커했다. 그런데 이 칩은 최신 프레임을 버린다 — FIFO 안의 64개는 직전 배치 바로 다음 프레임들이고, IRQ 시각은 버려진 16개 뒤의 시각이다. IRQ에 앵커하면 64개 전부가 16 × 1.25 ms = 20 ms 늦게 찍힌다. 수정: overflow 배치는 직전 체인에서 외삽하고, 그 다음 IRQ에서 새로 앵커(5.2절 코드의 ovr 분기). drop-oldest 칩이었다면 반대로 IRQ 앵커가 맞다 — 칩의 overflow 정책이 타임스탬프 알고리즘을 결정한다. 데이터시트에서 반드시 확인할 줄이다(P3 1절).

결정적으로 재현하려고 가짜 칩에 inject_stall_ms를 넣었다(1 s 뒤 200 ms 동안 IRQ 정지):

200 ms 정지 동안 160개가 만들어지고 64개가 FIFO에 남아 102개가 버려졌다(가짜 칩 fifo_overflow_frames 102와 도구의 seq 기반 drops=102가 정확히 일치 — 측정 도구와 하네스가 서로를 검증한다). 간격에는 128 ms 구멍이 정직하게 보이고(dt-T max), 살아남은 프레임의 절대 오차는 최대 0.67 ms에 머문다.

7.5 버그 3 — IIO core demux가 타임스탬프를 엉뚱한 곳에서 복사한다#

처음 버전은 "칩이 항상 14바이트 전체를 주니까" available_scan_masks = { 0x7f, 0 }을 선언하고 일부 채널만 켠 경우는 IIO core의 demux에 맡겼다(upstream 여러 드라이버가 쓰는 방식). 9절에서 libiio로 accel_x accel_z timestamp만 캡처했더니 시각 간격이 4.29 s(= 2^32 ns 근처)로 나왔다. 커널 자체를 의심해 sysfs로 같은 세 채널만 켜고 /dev/iio:device0을 직접 덤프했다:

16바이트 scan의 8–15(타임스탬프 자리)에 00 00 | a4 02 | 10 00 | 00 00가 들어 있다 — 전체 scan의 gyro_y(0), gyro_z(0x02a4 = 676), temp = seq 0x10, 0x11, 0x12, 0x13(seq_in_temp), 패딩이다. 즉 전체 24바이트 scan의 offset 8을 타임스탬프로 복사했다. 진짜 타임스탬프는 offset 16에 있다(iio_push_to_buffers_with_ts()가 scan_bytes / 8 − 1번째 s64에 넣는다).

iio_buffer_update_demux()(industrialio-buffer.c, 6.18.55)를 읽으면 이유가 보인다: 요청 채널을 도는 루프는 마지막 요청 채널(z, index 2)에서 끝나고, 그 뒤 활성(active) 채널 3–6을 in_loc에 더하지 않은 채 "Relies on scan_timestamp being last" 블록이 in_loc = roundup(6, 8) = 8에서 타임스탬프를 복사한다. 활성 마스크의 꼬리 채널이 꺼져 있고 타임스탬프가 켜진 경우에 생기는 문제다. 최신 mainline에서 고쳐졌는지는 확인하지 않았다 — 업스트림에 보고하기 전에 할 일은 mainline 코드 확인과 iio_dummy 같은 in-tree 드라이버로 재현하는 것이다(P7).

드라이버 쪽 해결은 단순하다: available_scan_masks를 없애고 활성 채널만 직접 채운다(upstream bmi160이 iio_for_each_active_channel로 하는 방식).

수정 후 같은 덤프:

타임스탬프 0x7dd3a5f0 → 0x7e6810f0, 차이 9728768 ns ≈ 10 ms(100 Hz 기본 ODR). 이 시나리오는 ci.sh의 회귀 테스트가 됐다.

이 절의 교훈(면접용): 세 버그 모두 "정상 경로"에서는 안 보였다. 실측 도구가 시퀀스 번호와 ground truth를 갖고 있었기 때문에 증상(멈춤, 20 ms 오차, 4.29 s 간격)을 숫자로 잡았고, 원인을 커널 소스 줄까지 따라갔다.

8. 단계 7 — 폴백과 실패 경로: DT 없이, IRQ 없이, 칩이 틀려도#

standalone=1이면 가짜 칩이 DT 없이 adapter만 만들고, 클라이언트는 new_device로 만든다 — 이 경우 client->irq = 0이다(H5: new_device는 이름·주소만 받는다).

(콘솔과 dmesg가 같은 줄을 두 번 찍은 부분은 하나만 남겼다.) 볼 것: IRQ가 없으면 드라이버는 자기 트리거를 만들지 않고 안내 메시지를 남긴 뒤, drdy 요청은 스크립트가 "no device trigger"로 거절하고 hrtimer 트리거로는 정상 캡처된다. 잘못된 ID는 -ENODEV, 없는 주소는 첫 쓰기(soft reset)에서 NACK → -ENXIO. 두 경우 모두 dev_err_probe()가 에러 코드 이름까지 찍고, devm 덕분에 이미 켠 regulator 등은 자동으로 정리된다. 실패한 probe 뒤에 드라이버가 붙어 있지 않다(bound driver: none).

9. 단계 8 — 진짜 유저 공간: udev 자동 로드와 libiio#

BusyBox에는 udev도 libiio도 없다. rootfs-dom(Ubuntu 24.04, systemd, libiio-utils 0.25) qcow2 overlay로 부팅하고, 산출물은 mkfs.ext4 -d로 만든 두 번째 디스크로 넣었다(tests/qemu/run_rootfs.py, pexpect). 게스트 셸까지 35 s 걸렸다(apparmor=0).

MODULE_DEVICE_TABLE(of, ...) 한 줄이 이 체인을 만든다(G9). /etc/modprobe.d/s4imu.conf의 options s4imu_emul seq_in_temp=1도 자동 로드에 적용됐다.

libiio 0.25가 in_mount_matrix를 "mount"라는 채널로 오인해 경고를 낸다(채널 9개로 셈) — libiio 쪽 해석 문제이고 커널 ABI는 표준 이름이다. iio_attr -c s4imu accel_z raw, iio_attr -d s4imu sampling_frequency 400이 동작한다.

(hexdump 4줄은 생략. 디코드는 게스트의 python3 struct.unpack_from("<hh4xq", ...).) 두 가지가 보인다:

12. 커널 안에서는 무슨 일이 일어나나#

샘플 하나가 칩에서 유저 버퍼까지 가는 경로를 함수 이름으로 따라가면:

  1. 가짜 칩 emul_tick()(hrtimer hard IRQ) → emul_sample() → FIFO push, WTM 래치 → irq_set_irqchip_state(PENDING) → irq_work_queue().
  2. irq_work → irq_sim_handle_irq() → generic_handle_domain_irq() → 드라이버가 devm_request_irq로 건 iio_trigger_generic_data_rdy_poll() → iio_trigger_poll()(use_count 검사!) → 트리거의 sub-IRQ → pollfunc top half iio_pollfunc_store_time()이 pf->timestamp = iio_get_time_ns().
  3. pollfunc 스레드(IRQ 스레드, SCHED_FIFO) → s4imu_trigger_handler() → s4imu_fifo_drain() → regmap_bulk_read()/regmap_noinc_read() → regmap_i2c → i2c_transfer() → emul_xfer().
  4. s4imu_push_frame() → iio_push_to_buffers_with_ts() → (demux가 있으면 iio_demux()) → iio_push_to_buffer() → kfifo 저장 → watermark 이상이면 wake_up_interruptible_poll().
  5. iio_trigger_notify_done() → use_count 0 → .reenable(s4imu_trig_reenable).
  6. 유저 read(/dev/iio:device0) → iio_buffer_read()가 watermark만큼 찰 때까지 대기 → kfifo에서 복사.

드라이버 작성 때 다시 만나는 지점: 2번의 hard IRQ에서는 잠들 수 없고(I2C 불가), 3번 스레드에서만 버스를 만진다(F2·F6·F7). 4번의 scan 레이아웃(정렬, 타임스탬프 위치)은 I2 4절. 5번 reenable은 IIO 고유의 "트리거 재무장" 훅. runtime PM은 1번 앞 단계(preenable → pm_runtime_resume_and_get → s4imu_runtime_resume → PWR normal)에서 칩을 깨운다(N6).

  • IRQ 핀이 없는 하네스 보드: 기구 제약으로 INT 핀을 안 뽑은 보드가 실제로 있다. 7.1의 hrtimer 결과(drop + dup, 0~1 주기 오차)는 "INT 핀 하나 배선하는 비용 vs 데이터 품질" 논의의 정량 근거가 된다.
  • FIFO watermark 고르기: 크면 IRQ·전력이 줄지만 지연(read_latency)이 늘고 overflow 여유가 준다. 7.4의 W48 사례처럼 "watermark + 최악 지연 × ODR < depth"를 검사한다. 실제 칩이 hwfifo_watermark_max를 알려 주면 그 ABI로 노출한다.
  • 양산 회귀 테스트: 가짜 칩 하네스는 하드웨어 랩 없이 CI에서 도는 드라이버 회귀 테스트다. 실제 칩용 드라이버라도 같은 방식으로 레지스터 모델을 만들어 두면, 커널 업그레이드(P5) 때 1분 만에 확인할 수 있다.

15.1 Q&A#

Q. Walk me through a sensor driver you wrote.

A. I2C IMU를 IIO 드라이버로 처음부터 썼다. regmap으로 칩 성격(volatile/precious/noinc)을 표로 적고, 채널·scale·ODR을 sysfs로, DRDY IRQ 트리거와 FIFO watermark 모드로 버퍼를 냈다. 하드웨어가 없어서 I2C adapter + irq_sim + hrtimer로 가짜 칩을 커널 모듈로 만들고 진짜 샘플 시각을 debugfs로 내보내 지터·드롭·타임스탬프 오차를 쟀다. FIFO가 간격 지터를 DRDY 대비 한 자릿수 이상 줄였다.

I wrote an IIO driver for an I2C 6-axis IMU from scratch: regmap with volatile, precious and no-increment registers, standard channels with scale and sampling_frequency, a data-ready trigger and a FIFO watermark mode with per-sample timestamp estimation, runtime PM, devm and dev_err_probe throughout. Since I had no hardware, I wrote an in-kernel chip model — an I2C adapter that's also an irq_sim interrupt controller, clocked by an hrtimer — that exposes ground-truth sample times. With that I measured jitter, drops and absolute timestamp error, and found three real bugs.

꼬리 질문: "그 세 버그가 뭐였나?" → 7.3–7.5를 30초씩.

Q. How do you timestamp samples that come out of a hardware FIFO?

A. IRQ 시각 하나가 배치의 마지막 샘플에 대응한다. 주기는 IRQ 간격 ÷ 프레임 수로 추정하고(±20 % 밖은 버림), 앵커는 예측값을 1/8씩만 측정값으로 당긴다. 인과성(IRQ보다 미래 금지)과 단조성 규칙을 두고, 잃은 edge·overflow 때는 외삽한다. 1 % 빠른 발진기에서 추정 주기가 진짜와 0.04 % 차이였다.

One interrupt timestamp per batch belongs to the newest frame. I estimate the real period from interrupt interval over frame count, rejecting outliers, and move the anchor only an eighth of the way toward each new measurement, like a simple PLL. Then I enforce causality and monotonicity and extrapolate across lost edges or overflow. With a 1 % fast oscillator the estimate landed within 0.04 % of the true period.

Q. Your IRQ handler — what runs in hard IRQ context and what doesn't?

A. hard IRQ에서는 트리거 poll과 타임스탬프만(iio_pollfunc_store_time). I2C는 잠들 수 있어서 pollfunc 스레드에서 읽는다. 처리 중에 다음 IRQ가 오면 IIO core가 버리는데, 래치형 인터럽트에서는 그게 영구 정지가 되므로 .reenable에서 상태를 다시 본다.

Only the timestamp and the trigger poll run in hard IRQ context; bus I/O happens in the poll function's thread because I2C can sleep. IIO drops a trigger that fires while the previous one is still being handled, and with a latched watermark interrupt that can stall the stream forever — so the trigger's reenable callback re-checks the status register and drains if needed.

Q. How did you test without hardware, and why not i2c-stub?

A. i2c-stub은 값이 안 변하고 IRQ가 없다. 그래서 레지스터 의미(clear-on-read, FIFO pop)를 구현한 adapter, 자기 DT 노드를 fwnode로 하는 irq_sim 도메인, 이상적 발진기 시각을 기록하는 hrtimer를 가진 테스트 모듈을 만들었다. 드라이버는 수정 없이 DT로 probe한다. 정적 검사(W=1, checkpatch, dt-validate)와 KUnit, QEMU 시나리오를 ci.sh 하나로 돌린다.

i2c-stub only stores bytes — no changing data, no interrupt. My test module is an I2C adapter that implements the register semantics, plus an irq_sim domain registered on its own DT node so the IMU's interrupts property resolves normally, plus an hrtimer acting as the sensor oscillator that logs ideal sample times. The driver probes from DT unmodified. One script runs W=1, checkpatch, dt-validate, KUnit and the QEMU scenarios.

Q. What changes when you move this to a real board?

A. 레지스터 맵(데이터시트), DT overlay 적용 방식, IRQ 극성·level/edge와 핀 pull, 실제 레귤레이터와 power-up 지연, 전원 차단 시 regcache 동기화, 버스 전송 길이 제한. 그리고 지터를 다시 잰다 — TCG 숫자는 의미가 없다.

The register map from the datasheet, how the overlay gets applied, interrupt polarity and edge versus level plus pin bias, real supplies and power-up timing, regcache sync if the rail is cut in suspend, and the controller's transfer limits. Then re-measure — emulator timings aren't hardware numbers.

Q. What's runtime PM doing in your driver?

A. 2 s autosuspend. sysfs 읽기는 resume_and_get/put_autosuspend로 감싸고, 버퍼는 preenable/postdisable에서 참조를 잡는다. resume에서 PWR normal + start-up + 첫 DRDY 대기. 가짜 칩 샘플 카운터가 멈추는 것으로 실제 suspend를 확인했다.

Two-second autosuspend: direct reads take a reference with resume_and_get and drop it with put_autosuspend, the buffer holds one from preenable to postdisable, and resume waits for start-up plus the first data-ready. I verified it by watching the emulator's sample counter stop while suspended.

Q. Did you find anything in the kernel itself?

A. 6.18.55의 IIO demux가 활성 마스크의 꼬리 채널이 꺼져 있을 때 타임스탬프를 잘못된 offset에서 복사하는 것을 hexdump로 확인하고 코드 줄을 짚었다. 드라이버는 활성 채널만 직접 채우도록 바꿨고, mainline 확인과 in-tree 재현이 업스트림 보고 전 다음 단계다.

Yes — with available_scan_masks covering all channels and only a prefix plus the timestamp enabled, the 6.18.55 demux copies the timestamp from the wrong offset because it doesn't advance past the trailing active channels. I showed it with a raw hexdump and pointed at the line. I worked around it in the driver; next step before reporting is reproducing on mainline with an in-tree driver.

18. 요약 & 체크리스트#

가상의 S4IMU 레지스터 맵을 문서로 고정하고, upstream 구조(코어 + I2C glue)의 IIO 드라이버를 썼다: regmap 분류(volatile·precious·noinc + maple 캐시), 표준 채널과 NANO scale, DRDY 트리거·hrtimer 폴백·FIFO watermark 세 경로, 정수 타임스탬프 추정기, runtime PM, devm, dev_err_probe. i2c-stub 대신 I2C adapter + irq_sim + hrtimer 가짜 칩을 모듈로 만들어 DT로 수정 없이 probe시키고, 시퀀스 번호와 진짜 샘플 시각을 debugfs로 내보내 지터·드롭·절대 오차를 쟀다. FIFO 모드가 간격 지터를 DRDY 대비 한 자릿수 이상 줄이고 드롭 0을 냈으며, 하네스가 잃은 edge로 인한 영구 정지, overflow 뒤 20 ms 앵커 오차, 6.18.55 IIO demux의 타임스탬프 offset 문제를 찾아 각각 수정했다. W=1·checkpatch·dt-validate·KUnit 7개·QEMU 시나리오가 ci.sh 한 번에 통과한다. 모든 시간 수치는 TCG 값이다.
