2. 저장소 레이아웃#

핵심 설계: 저장소(입력)는 읽기 전용이어도 된다. VM에서 Mac 홈은 읽기 전용으로 마운트되는데, 그래도 빌드가 된다는 것이 "소스와 산출물이 완전히 분리됐다"는 증거다. Makefile 맨 위의 변수들이 이 분리를 정의한다.

.DELETE_ON_ERROR는 레시피가 중간에 실패하면 반쯤 만들어진 타깃 파일을 지운다. 이게 없으면 §6의 Kconfig 실패 뒤 망가진 .config가 "최신"으로 남아 다음 make가 그냥 지나간다 — 실제로 이 랩을 만들면서 처음에 빠뜨렸던 줄이다.

그림 2 — 빌드 파이프라인. 각 행이 컴포넌트 하나이고, 점선은 컴포넌트 사이 의존성(U-Boot가 TF-A FIP의 BL33으로 들어가고, 커널 Image가 ext4의 /boot로 들어간다).

3. Step 1 — 소스 받기와 검증#

3.1 왜 검증하나#

공급망 공격(빌드 서버가 받은 tarball이 바꿔치기된 경우)과 단순 손상(잘린 다운로드)을 막는 두 단계가 있다.

단계무엇을 보장도구
해시 (sha256)"내가 고정한 바로 그 바이트"인지sha256sum -c SHA256SUMS
서명 (GPG)"그 바이트를 릴리스 담당자가 만들었는지"gpg --verify x.tar.sign

해시는 저장소에 고정해 두면 이후 빌드에서 인터넷 없이도 검사된다(Buildroot의 .hash 파일, Yocto의 SRC_URI[sha256sum]이 같은 개념, K3 §5). 서명은 해시를 처음 고정할 때 한 번 확인한다.

3.2 Makefile — 캐시가 있으면 링크, 없으면 다운로드#

/var/lab/dl의 tarball은 읽기 전용 캐시로 symlink만 건다(복사하면 220 MB 낭비). .part로 받고 mv하는 것은 다운로드가 중간에 끊겨도 잘린 파일이 완성품처럼 남지 않게 하려는 것이다. U-Boot·TF-A URL은 git 태그 아카이브인데, 이 형식은 서버가 즉석에서 만들어서 해시가 영원히 같다는 보장이 약하다 — 그래서 실무에서는 git 커밋 해시를 같이 고정한다.

출력에서 볼 것: 두 번째 실행은 Nothing to be done — 스탬프 파일 .stamp/verified가 SHA256SUMS보다 새것이라서다.

3.3 고정한 해시가 업스트림과 같은지 — 처음 한 번#

3.4 GPG 서명 — 격리된 keyring으로#

kernel.org의 .tar.sign은 압축을 푼 .tar 에 대한 서명이다(xz 압축 결과는 xz 버전마다 바이트가 달라질 수 있어서). 그래서 xz -cd로 풀면서 파이프로 검증한다. 공용 VM의 ~/.gnupg를 건드리지 않도록 GNUPGHOME을 내 디렉터리로 돌린다.

출력에서 볼 것:

  • Good signature from "Greg Kroah-Hartman" — 안정판(6.18.y)은 stable 메인테이너가 서명한다. WARNING: not certified는 "이 키를 내가 직접 신뢰한다고 표시한 적이 없다"는 뜻이지 서명이 틀렸다는 뜻이 아니다. 지문(647F 2865 …)을 kernel.org 서명 안내 페이지와 대조하는 것이 마지막 단계다.
  • sha256sums.asc는 kernel.org 자동 서명 키(B886…)로 서명돼 있어서 그 키를 받지 않으면 No public key가 나온다. 해시 목록 자체의 출처 검증까지 하려면 그 키도 WKD로 받는다.
  • BusyBox는 .sig(DSA, keyid 47B70C55ACC9965B)를 제공한다. U-Boot·TF-A 태그 아카이브에는 서명이 없다 — 이 경우 git 태그 서명(git tag -v)이 대안이다.

체크포인트: sha256sum -c가 4개 모두 OK, 커널 tarball에 Good signature.

5. Step 3 — U-Boot (qemu_arm64_defconfig)#

U-Boot은 이 랩에서 두 번 쓰인다: (1) -bios u-boot.bin으로 단독 실행(EL1/EL2, 비보안), (2) TF-A FIP 안의 BL33. 같은 바이너리가 두 역할을 다 한다 — qemu_arm64_defconfig가 CONFIG_POSITION_INDEPENDENT=y, CONFIG_TEXT_BASE=0이라서 어디에 올라가도 스스로 재배치하기 때문이다(C4에서 본 relocation).

출력에서 볼 것:

  • 27초, 1,504,208 바이트 — 랩의 /var/lab/out/u-boot.bin과 크기가 바이트 단위로 같다. 그런데 cmp하면 다르다(아래). 빌드 날짜 문자열 U-Boot 2026.10 (Oct 18 2026 - 16:29:47 -0700)이 바이너리에 박히기 때문이다. 완전히 같은 바이너리(reproducible build)를 원하면 SOURCE_DATE_EPOCH를 고정한다(B5 §7).
  • 기본 부트 명령이 bootflow scan -lb — 모든 boot device를 훑어서 처음 찾은 것으로 부팅한다. §9에서 이게 QEMU fw_cfg에서 커널을 찾는 걸 본다.

체크포인트: out/u-boot.bin 약 1.5 MB.

6. Step 4 — TF-A (PLAT=qemu)와 flash.bin#

TF-A의 단계(BL1 → BL2 → BL31 → BL33)와 FIP는 C5 §2에서 배웠다. 여기서는 만드는 법만 본다.

결정마다 이유가 있다.

결정이유
BL33=$(OUT)/u-boot.binFIP에 U-Boot를 넣는다. 의존성에 u-boot.bin이 있어서 U-Boot가 바뀌면 FIP도 다시 만든다
BUILD_BASE=TF-A는 O=가 아니라 이 변수로 출력 위치를 바꾼다 (build/<plat>/<release or debug>/)
bl1.bin을 offset 0QEMU virt에서 -bios 파일은 flash0(주소 0x0)에 매핑되고, secure=on이면 CPU가 EL3에서 0x0부터 실행한다 = Boot ROM 자리
fip.bin을 seek=64 × 4 KiB = 0x40000TF-A qemu 플랫폼의 BL2가 FIP를 flash의 256 KiB 위치에서 찾는다 (TF-A qemu 플랫폼 문서의 dd 레시피와 같다)
64 MiB로 패딩QEMU flash 장치는 64 MiB 크기 이미지를 기대한다
.tmp 후 mvdd 중간 실패 시 반쪽 flash.bin이 남지 않게

출력에서 볼 것: 2.7초. BL1 22 KB, BL31 49 KB — EL3 펌웨어는 SSD FW의 ROM 코드처럼 작다. FIP의 BL33 크기 0x16F3D0 = 1,504,208 = u-boot.bin 크기 그대로. FIP는 "UUID로 이름 붙은 이미지들의 목차 + 본문"이다 (Don에게는 SSD 펌웨어 패키지의 섹션 헤더와 같은 것).

체크포인트: out/flash.bin 정확히 67,108,864 바이트, fiptool info에 BL2/BL31/BL33 세 줄.

11.1 ext4 rootfs — mkfs.ext4 -d (root 권한 불필요)#

mkfs.ext4 -d <dir>는 디렉터리 내용을 채운 채로 파일시스템을 만든다 — sudo mount -o loop가 필요 없다. 처음 버전은 rootfs/boot/에 Image를 직접 복사했는데, 그러면 다음에 initramfs를 다시 만들 때 6 MB 커널이 initramfs 안에도 들어간다. 그래서 디스크용 사본 rootfs-disk/를 따로 만든다.

출력에서 볼 것: 루트 디렉터리(.., inode 2)는 root_owner=0:0 덕에 0:0이지만, 그 아래 파일은 내 uid 501:1000 그대로다. -d는 파일 소유자를 복사하기 때문이다. BusyBox 랩에서는 상관없지만, 제품 이미지에서는 fakeroot 또는 Buildroot의 device table로 소유자를 고친다(K3 §7).

TF-A 경로 전에, 디스크 자체가 좋은지 -kernel로 먼저 확인한다(한 번에 한 변수만 바꾸는 bring-up 습관). 사본에 쓰고, 꺼진 뒤 VM에서 읽어서 영속성을 확인한다.

출력에서 볼 것: -initrd 없이 root=/dev/vda로 부팅했다. init=/init이 필요한 이유는 BusyBox 기본 init(/sbin/init)이 /etc/inittab을 찾기 때문이다 — 우리는 같은 /init 스크립트를 쓴다. 게스트가 쓴 note.txt를 VM에서 debugfs로 읽었고, e2fsck -fn이 깨끗하다(sync 후 poweroff 덕).

11.3 TF-A 경로 — expect로 U-Boot 조작#

결정 메모:

  • -m 1024: TF-A qemu 플랫폼은 BL33(U-Boot)을 DRAM 시작 + 512 MiB = 0x60000000에 올린다. -m 512면 그 주소에 RAM이 없다(C5 §3에서 소스로 증명). 랩 README는 1057을 썼지만 1024로도 된다 — 게스트 ≤ 1 GB 규칙을 지키는 값.
  • snapshot=on: 쓰기를 임시 파일로 보내서 out/rootfs.ext4가 변하지 않는다. make의 타임스탬프도 유지된다.
  • booti ${kernel_addr_r} - ${fdtcontroladdr}: 가운데 -는 "initrd 없음". DT는 U-Boot가 QEMU에게서 받은 것(fdtcontroladdr)을 그대로 넘긴다. 랩 README 경고대로 /var/lab/out/virt.dtb는 -kernel 부팅 전용이라 여기에 쓰면 안 된다.

11.4 첫 시도의 실패 — 빈 커맨드라인#

처음 스크립트는 setenv bootargs console=... LAB_CMD=cat~a;echo;...처럼 따옴표 없이 보냈다.

U-Boot의 hush 셸은 ;를 명령 구분자로, |를 문법 오류로 본다. setenv가 실패해서 bootargs가 비었고, 커널은 root= 없이 떠서 panic했다. 그런데 panic 뒤 QEMU가 꺼지지 않아 expect가 240초 timeout까지 기다렸다 → (1) 값을 큰따옴표로 감싸고, (2) "Kernel panic" 패턴을 추가해 즉시 실패하게 고쳤다. 자동화 스크립트는 성공 패턴만이 아니라 실패 패턴도 기다려야 한다.

12.2 실행 — 한 번에 4가지 확인#

출력에서 볼 것:

  • 첫 줄: VM에서 curl 127.0.0.1:43100이 게스트의 httpd가 9p로 서빙한 파일을 받았다 (VM → hostfwd → 게스트 80 → 9p → VM 디렉터리, 한 바퀴).
  • 게스트가 uname -r을 /mnt/host/from_guest.txt에 썼고 VM에서 그대로 읽혔다 — ssh도 scp도 없이 양방향 파일 전송.
  • nslookup kernel.org가 실제 주소를 받았다 — slirp가 DNS를 VM의 리졸버로 중계한다.
  • -device virtio-net-device(MMIO)를 명시하면 §9의 기본 PCI NIC는 생기지 않는다.

이게 드라이버 개발 루프의 핵심이다: VM에서 .ko나 테스트 바이너리를 빌드해 share/에 두면, 게스트를 다시 만들지 않고 /mnt/host/x.ko로 바로 insmod한다(S2에서 쓴다).

체크포인트: s1-lab: 9p host0 -> /mnt/host와 from_guest.txt.

13. Step 11 — gdbstub: 이 랩의 JTAG#

M4 §3에서 개념(QEMU gdbstub = JTAG 프로브)을 배웠다. 여기서는 내 커널로 "reset halt → 첫 명령 → start_kernel → 드라이버 probe" 순서를 따라간다. 실제 보드에서 Lauterbach/OpenOCD로 하는 첫 세션과 같은 순서다.

출력에서 볼 것:

  • -S로 리셋 직후 멈춘 CPU의 PC는 0x40000000 — §9에서 말한 QEMU 부트 스텁이다. ldr x0, 0x40000018(DTB 주소 로드), mov x1, xzr, mov x2, xzr가 arm64 부팅 프로토콜(x0=DTB, x1–x3=0)을 그대로 보여 준다(C6 §2).
  • hbreak(하드웨어 브레이크포인트)를 쓴 이유: MMU가 켜지기 전에는 가상 주소 0xffff8000...에 소프트웨어 브레이크(메모리에 BRK 명령 쓰기)를 걸 수 없다. JTAG에서 flash 코드에 HW breakpoint를 쓰는 것과 같은 이유.
  • bt: bus_for_each_drv → __device_attach_driver → driver_probe_device → really_probe → call_driver_probe → amba_probe → pl011_probe — G 모듈의 driver model 매칭 경로가 실물 스택으로 나왔다(G3, D3).
  • lx-version, init_task.comm — scripts_gdb 타깃으로 만든 vmlinux-gdb.py가 커널 자료구조를 읽는다. nokaslr은 이 커널엔 RANDOMIZE_BASE가 없어 사실 필요 없지만, defconfig 커널에서도 같은 명령이 되도록 습관으로 넣는다.
  • detach 후 게스트가 정상 부팅해서 꺼졌다 — 디버거가 상태를 망가뜨리지 않았다.

체크포인트: Breakpoint 2, pl011_probe와 8단 backtrace. Makefile의 run-gdb 타깃이 QEMU 쪽 명령을 담고 있다.

커널·U-Boot·TF-A·BusyBox 컴파일은 하나도 없다. 4.7초.

14.3 fragment를 touch하면 → 설정은 다시, 컴파일은 0개#

(GEN Makefile 반복 줄은 하나만 남겼다.)

출력에서 볼 것: Make 입장에서는 fragment가 새로워져서 .config를 다시 만들었지만, 내용이 같으므로 Kbuild의 syncconfig가 auto.conf를 비교해서 다시 컴파일한 오브젝트가 0개다(E2 §8의 fixdep 이야기). 두 겹의 증분 판단 — Make는 파일 시각, Kbuild는 설정 내용과 헤더 의존성.

18.4 면접 Q&A#

Q. "You don't have the board yet. How do you start the BSP work?"

A. QEMU virt로 같은 아키텍처의 부트 체인을 먼저 세운다. TF-A BL1/BL2/BL31, U-Boot, 최소 커널, BusyBox까지 소스에서 빌드하고, 세 가지 부팅 경로로 각 단계를 따로 검증했다. 보드가 오면 바뀌는 건 플랫폼 포트(TF-A PLAT, U-Boot defconfig, DT, 커널 fragment)뿐이고 파이프라인·검증 스크립트·디버그 방식은 그대로 쓴다.

I build the same boot chain on QEMU virt first: TF-A BL1/BL2/BL31, U-Boot as BL33, a minimal kernel and a static BusyBox, all from checksum-verified sources through one Makefile. I boot it three ways — direct kernel, U-Boot, and the full secure-world chain — so each stage is validated in isolation. When silicon arrives, only the platform ports change: the TF-A platform, U-Boot defconfig, device tree and kernel fragment. The pipeline, smoke tests and gdb workflow carry over.

꼬리 질문: "What does QEMU's -kernel skip?" → 펌웨어 전체와 커널 로딩, PSCI 제공자(QEMU가 hvc로 대신), DT의 /chosen 패치까지.

Q. "How do you keep a minimal kernel config maintainable?"

A. 전체 .config를 커밋하지 않고 tinyconfig 위에 얹는 fragment로 관리한다. 병합 후 olddefconfig가 의존성 때문에 옵션을 조용히 끌 수 있어서, fragment의 모든 줄이 최종 .config에 살아남았는지 검사하고 아니면 빌드를 멈춘다. 실제로 TMPFS가 SHMEM 의존성 때문에 사라진 걸 이렇게 잡았다.

I keep a small fragment on top of tinyconfig instead of a full .config, merge it with merge_config.sh, and then verify that every fragment line survived olddefconfig — Kconfig silently drops options whose dependencies aren't met. That check caught CONFIG_TMPFS disappearing because SHMEM was off in tinyconfig.

Q. "How can you tell which firmware handles PSCI on a running system?"

A. DT의 /psci 노드 method 속성과 부팅 로그의 SMCCC 버전을 본다. QEMU 직접 부팅에서는 hvc와 SMCCC v1.0이고, TF-A 경로에서는 smc와 v1.5였다. hvc는 EL2(여기서는 QEMU 에뮬레이션), smc는 EL3 secure monitor로 트랩한다.

Read /proc/device-tree/psci/method and the "SMC Calling Convention" line in dmesg. In my lab the direct boot shows hvc and SMCCC 1.0 — QEMU emulates PSCI — while the TF-A boot shows smc and SMCCC 1.5, meaning BL31 at EL3 services CPU_ON and SYSTEM_OFF.

Q. "Why did your TF-A boot hang with 512 MB?"

A. TF-A qemu 플랫폼이 BL33을 DRAM 시작 + 512 MiB인 0x60000000에 로드하도록 고정돼 있어서, RAM이 512 MB면 그 주소가 존재하지 않는다. BL2가 BL33을 복사하다 data abort로 조용히 멈춘다. 1 GB로 올리면 된다. 실제 보드에서도 "부트로더 로드 주소와 실장 DRAM 크기 불일치"는 흔한 bring-up 버그다.

The qemu TF-A port loads BL33 at DRAM base plus 512 MiB, 0x60000000. With 512 MB of RAM that address doesn't exist, so BL2 aborts while copying U-Boot and the console just stops after "BL2: Built". Giving the guest 1 GB fixes it. On real boards the same class of bug is a load address that doesn't match the populated DRAM.

Q. "How do you debug the kernel before the console comes up?"

A. QEMU gdbstub를 JTAG처럼 쓴다. -S로 리셋 직후 멈추고, vmlinux를 심볼로 로드한 뒤 하드웨어 브레이크포인트로 start_kernel이나 문제 드라이버의 probe에 건다. MMU 켜기 전에는 소프트웨어 브레이크를 못 쓰기 때문이다. 콘솔 전에는 earlycon=pl011,0x9000000으로 UART를 직접 찌른다.

I treat the QEMU gdbstub as a JTAG probe: start halted with -S, load vmlinux symbols, and use hardware breakpoints on start_kernel or the driver's probe, since software breakpoints don't work before the MMU is on. For output before the console driver binds, earlycon pokes the PL011 directly.

Q. "What makes your build reproducible and incremental?"

A. 입력은 해시로 고정한 tarball과 저장소 파일, 출력은 전부 별도 디렉터리의 파일 타깃이다. 두 번째 make는 아무것도 하지 않고(make -q 종료 코드 0), /init을 고치면 rootfs와 이미지만 4.7초에 다시 만든다. 바이트 단위 재현성은 빌드 타임스탬프를 고정해야 해서 다음 단계로 남겨 뒀다 — U-Boot 바이너리가 날짜 문자열 때문에 다르다는 걸 확인했다.

Inputs are pinned tarballs plus repo files; every output is a file target in a separate build directory. A second make is a no-op, editing /init rebuilds only the rootfs and images in under five seconds, and touching the kernel fragment re-runs Kconfig but recompiles zero objects. Bit-for-bit reproducibility is the next step: my U-Boot differs from the lab's only in the embedded build date, so pinning SOURCE_DATE_EPOCH is the fix.

Q. "Buildroot or hand-rolled Makefile?"

A. 학습과 bring-up 초기에는 손으로 만든 파이프라인이 각 컴포넌트의 빌드 관례를 드러내서 좋다. 제품으로 가면 Buildroot(또는 Yocto)가 툴체인, 라이선스, 소유권(fakeroot), 패키지 해시를 관리해 준다. 내 저장소에는 같은 설정을 BR2_EXTERNAL 트리로 옮긴 골격이 있다.

Hand-rolled first, because it exposes each component's build conventions — O=, BUILD_BASE=, CONFIG_PREFIX=, FIP packing. For a product I'd move to Buildroot or Yocto for toolchain management, license reports, fakeroot ownership and per-package hashes; my repo already carries a BR2_EXTERNAL skeleton with the same kernel fragment.

19. 직접 해보기#

  1. /var/tmp/<내 ID>를 지우고 make B=... all을 처음부터 돌려 그림 4의 숫자를 자기 측정으로 바꿔라. 정답/힌트: 다른 작업이 없으면 커널이 더 빨라야 한다.
  2. fragment에서 CONFIG_PACKET=y를 지우고 부팅해 s1-lab: eth0 줄이 사라지는 이유를 설명하라. 정답/힌트: udhcpc는 AF_PACKET raw socket으로 DHCP를 보낸다.
  3. tfa-booti.exp에서 -m 1024를 -m 600으로 바꿔 어디서 멈추는지 기록하라(랩 README는 540에서 U-Boot reset loop를 봤다). 정답/힌트: BL33 로드 주소와 U-Boot 재배치 주소(RAM 꼭대기 근처)를 둘 다 생각한다.
  4. ②번 부팅에서 bootdelay를 0으로 만들어 wall time이 몇 초 줄어드는지 재라. 정답/힌트: QEMU를 -S로 두지 않고, U-Boot 프롬프트에서 setenv bootdelay 0; saveenv는 flash 환경이 필요하다 — 대신 defconfig에 CONFIG_BOOTDELAY=0.
  5. gdb로 hbreak do_one_initcall을 걸고 continue를 10번 하며 p fn을 찍어 initcall 순서를 관찰하라. 정답/힌트: C6 §7의 initcall 레벨 순서와 비교.
  6. mkfs.ext4 -d가 만든 이미지의 파일 소유자를 0:0으로 만드는 방법 두 가지를 찾아라. 정답/힌트: fakeroot로 chown 후 mkfs.ext4 -d, 또는 debugfs -w의 set_inode_field.
  7. 9p 대신 mkfs.ext4 -d로 만든 두 번째 virtio 디스크로 파일을 넘기는 방식과 장단점을 비교하라. 정답/힌트: 디스크 방식은 게스트 실행 중 호스트가 쓰면 안 된다(파일시스템 캐시 불일치).

21. 요약 & 셀프 체크#

S1은 /var/lab을 "빌려 쓰는 랩"에서 "내가 다시 만들 수 있는 랩"으로 바꾼다. 해시로 고정한 4개 tarball에서 출발해 U-Boot(27 s), TF-A(3 s), tinyconfig + 46줄 fragment 커널(294 s, 6.2 MB), static BusyBox(43 s)를 하나의 Makefile로 만들고, 같은 커널을 QEMU 직접·U-Boot(fw_cfg)·TF-A secure(ext4 + booti) 세 경로로 띄워 PSCI 제공자가 hvc에서 smc로 바뀌는 것까지 증거로 남겼다. virtio-blk ext4, user 네트워크 + hostfwd + 9p, gdbstub 하드웨어 브레이크포인트로 개발 루프를 갖췄고, 두 번째 make가 아무것도 안 하는 증분 빌드와, 빌드 중 실제로 부딪친 7가지 실패(옵션 증발, BusyBox 3종, U-Boot 따옴표, TF-A 메모리, expect timeout)를 고친 기록이 포트폴리오의 핵심 내용이다. Buildroot 경로는 BR2_EXTERNAL 골격까지만 만들고 빌드는 가이드로 남겼다.
