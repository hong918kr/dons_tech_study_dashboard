0. 큰 그림 — Don이 서 있던 자리의 반대편#

Don이 SSD 펌웨어에서 본 PCIe는 엔드포인트 쪽이었다. 호스트가 config space를 읽으면 대답하고, BAR에 주소가 써지면 그 주소로 들어오는 TLP를 받고, MSI-X 테이블에 호스트가 써 둔 주소·데이터로 메모리 쓰기를 날리면 인터럽트가 됐다. 그 "호스트"가 바로 이 노트의 주인공인 Linux PCI 서브시스템이다. 이번에는 반대편 자리에 앉아서, 그 config read를 누가 언제 보내는지, BAR 주소를 누가 정하는지, MSI-X 테이블에 무슨 값을 써 넣는지를 본다.

0.1 이 노트의 랩 구성#

D1에서는 QEMU 기본 장치만 봤다. 이번에는 Don의 실무 토폴로지에 가깝게 Root Port 3개 + 그 뒤의 엔드포인트를 꽂는다. 모든 예제는 아래 스크립트 하나로 부팅한다 (VM elinux, Ubuntu 26.04, 호스트 커널 uname -r = 7.0.0-38-generic, QEMU 10.2.1; 게스트는 랩 커널 6.18.55).

edu는 QEMU가 교육용으로 만든 가짜 장치다(docs/specs/edu.rst). BAR0 1 MiB 안에 ID 레지스터(0x00 = 0x010000ed), liveness(0x04, 쓴 값의 비트 반전을 돌려줌), 인터럽트 상태/올리기/ack(0x24/0x60/0x64), DMA 엔진(0x80~0x98, 내부 버퍼는 장치 주소 0x40000)이 있고, MSI 1벡터와 INTx를 지원한다. DMA 주소 능력이 28비트라는 점이 나중에 중요해진다. 드라이버 연습에는 완벽한 장치다.

1. Host bridge — 모든 것은 DT 노드 하나에서 시작한다#

1.1 직관#

D1에서 봤듯 PCIe 아래의 장치들은 스스로 말하지만, Root Complex 자체는 그렇지 않다. CPU 주소 공간의 어디에 ECAM이 있는지, 어느 CPU 주소 구간을 PCI 메모리 공간으로 쓸지(window), INTx A~D가 GIC의 몇 번으로 가는지, MSI는 어느 컨트롤러가 받는지 — 이 네 가지를 DT가 알려 주고, host bridge 드라이버가 그걸로 struct pci_host_bridge를 만든 뒤 PCI core에 "이제 스캔해"라고 넘긴다.

(랩 out/virt.dts의 해당 노드를 줄여 옮긴 것 — interrupt-map의 32줄은 생략.)

ranges의 첫 셀(0x02000000 등)은 PCI 주소 공간 종류다: 01 = I/O, 02 = 32비트 MEM, 03 = 64비트 MEM (prefetchable이면 0x43000000처럼 bit 30이 선다). 이 3셀 PCI 주소 → 2셀 CPU 주소 → 2셀 크기 형식은 D4에서 다뤘다.

무엇을 확인하나: pci-host-generic이 DT의 ranges와 ECAM을 어떻게 해석했는지.

출력에서 볼 것: IO 0x3eff0000 -> 0x0은 CPU 주소 0x3eff0000에 쓰면 PCI I/O 공간 0번지로 간다는 뜻(ARM에는 x86 in/out 명령이 없어서 I/O 공간도 MMIO 창으로 흉내 낸다). 32비트 창은 CPU 주소 = PCI 주소(1:1)이고, 64비트 창은 512 GiB짜리다. Don의 bring-up 경험이 가장 빛나는 곳이 오른쪽 열이다. i.MX8 보드에서 "Wi-Fi 카드가 안 보인다"의 90%는 PCI core가 아니라 glue 드라이버 단계 — REFCLK, PERST# 타이밍, PHY 전원, dw_pcie_wait_for_link 타임아웃("Phy link never came up") — 에서 끝난다. 랩 커널에도 CONFIG_PCIE_DW_HOST=y, CONFIG_PCI_IMX6_HOST=y, CONFIG_PCIE_ROCKCHIP_DW_HOST=y가 켜져 있다 (QEMU에 DWC 모델이 없어 실행은 못 함). 어느 쪽이든 결국 pci_host_probe()를 부르고, 거기서부터는 같은 PCI core다.

함정: DWC SoC에서 lspci에 Root Port만 보이고 엔드포인트가 없으면 "링크가 안 올라왔다"는 뜻이다. Root Port 자체는 SoC 안에 있으니 링크와 무관하게 항상 보인다. dmesg에서 glue 드라이버의 "Link up"/"Phy link never came up" 줄부터 찾는다.

2. Enumeration과 자원 배정 — dmesg를 순서대로 읽는 법#

2.1 흐름#

그림 2 — 부팅 enumeration. 스캔 단계(2~5)에서는 BAR "크기"만 알고 주소는 0으로 찍힌다. 주소는 전부 스캔이 끝난 뒤 6단계에서 한꺼번에 정해진다.

Don이 펌웨어에서 경험한 것과 다른 점 두 가지:

  1. 스캔과 배정이 분리돼 있다. 스캔 중의 BAR 0 [mem 0x00000000-0x000fffff]는 "크기 1 MiB"라는 뜻일 뿐 주소가 아니다. 모든 장치의 크기를 알아야 브리지 창 크기를 정할 수 있기 때문이다.
  2. x86 PC와 달리 펌웨어가 아무것도 안 해 놓는다. x86에서는 BIOS가 이미 BAR를 배정해 두고 Linux는 대부분 "claim"만 한다. QEMU -kernel 부팅이나 대부분의 ARM 보드는 U-Boot가 PCI를 건드리지 않거나 건드려도 Linux가 다시 하므로 bridge configuration invalid ([bus 00-00]), reconfiguring이 찍힌다 — 에러가 아니라 "버스 번호가 비어 있어서 내가 정한다"는 뜻이다.

출력에서 볼 것:

  • type 00/type 01은 Header Type(엔드포인트/브리지). class 0x010802는 NVMe(01 mass storage, 08 NVM, 02 NVMe 인터페이스).
  • 버스 번호는 깊이 우선으로 매겨진다. 처음엔 [bus 01-ff]로 하위 전부를 잡았다가 스캔이 끝나면 end is updated to 01로 줄인다 (subordinate bus number 확정).
  • add_size 200000: Root Port 아래에는 나중에 핫플러그될 장치를 위한 여유분을 더 잡는다 (pci=hpmemsize=, hpiosize=로 조정). 그래서 edu는 1 MiB인데 rp1의 MEM 창은 2 MiB(0x10000000-0x101fffff)가 됐다. 브리지 창은 1 MiB 단위 정렬이다(PCI-to-PCI bridge 규격).
  • 브리지에 창이 세 개다: I/O, 32비트 non-prefetchable MEM, 64비트 prefetchable MEM. NVMe의 BAR0처럼 64비트지만 non-prefetchable인 BAR는 32비트 non-pref 창에 들어가야 한다 (브리지의 non-pref 창은 32비트뿐이다). 큰 GPU·가속기 BAR가 pref여야 하는 이유다.

무엇을 확인하나: BAR 배정 실패가 어떻게 보이는지. 64비트 창을 없애는 highmem=off 머신에 1 GiB BAR를 가진 ivshmem-plain을 꽂는다 (32비트 창은 0x10000000-0x3efeffff = 약 752 MiB).

출력에서 볼 것: 장치는 여전히 enumeration되어 lspci에 보인다. BAR 2만 0으로 남는다. 커널이 한 번 실패한 뒤 이미 배정한 BAR를 releasing 하고 다시 시도(재배정 패스)했지만 그래도 안 된다. 드라이버가 이 장치에 붙으면 pcim_iomap_region(pdev, 2, ...)가 실패하고, 드라이버마다 "BAR 2 is not assigned" 류의 에러로 probe가 실패한다. 실제 보드에서 이 증상은 "DT ranges의 MEM 창이 장치 BAR 합보다 작다"가 1순위 원인이다. 3.2 예제 4 — sysfs로 edu 해부하기#

무엇을 확인하나: 드라이버가 없는 상태의 edu를 sysfs만으로 읽기. BusyBox lspci는 -k, -m만 되고 -v/-t/-x는 없다 — 그래서 sysfs와 아래 예제 5의 C 디코더를 쓴다.

출력에서 볼 것:

  • driver 링크가 없다 = 아직 아무 드라이버도 안 붙음. irq = 0, enable = 0 (Command 레지스터의 Memory Space도 꺼져 있다 — 예제 5에서 cmd 0000).
  • resource의 셋째 열 0x40200은 IORESOURCE_MEM(0x200) + IORESOURCE_SIZEALIGN(0x40000) 플래그다. resource0은 BAR0를 mmap할 수 있는 파일이다 (/dev/mem 대신 쓰는 유저 공간 MMIO 창. VFIO가 나오기 전의 UIO식 접근).
  • 경로 /sys/devices/platform/4010000000.pcie/pci0000:00/0000:00:10.0/0000:01:00.0가 곧 토폴로지다. lspci -t가 없어도 경로가 트리를 말해 준다. 부모가 Root Port 00:10.0, 그 부모가 DT에서 만든 platform device다 (D1 §7).
  • /proc/iomem에서 bridge window가 "PCI Bus 0000:01" 이름으로 계층을 이룬다. 02:00.0(NVMe)는 드라이버가 없어서 BAR가 아직 claim되지 않아 이름 줄이 없다.
  • reset_method가 bus다: edu는 FLR도 PM reset도 없지만, 혼자 Root Port 아래에 있으므로 Secondary Bus Reset을 쓸 수 있다.
  • lspci -k의 마지막 열이 드라이버다. NVMe(02:00.0)는 nvme가 모듈(=m)이라 아직 비어 있다.

4. Config space 직접 해독하기 — 미니 lspci -vvv#

4.1 예제 5 — h11_cfg: 헤더·BAR·capability 리스트#

무엇을 확인하나: sysfs config 파일만으로 Header Type, BAR 원시값, capability 체인(PM, MSI, MSI-X, PCIe cap의 Link 속도/폭), extended capability(0x100~)를 읽는다. Don이 SSD 펌웨어에서 장치 쪽으로 채워 넣던 그 구조를 호스트 쪽에서 읽어 보는 것이다.

출력에서 볼 것:

  • cmd 레지스터가 드라이버 상태를 말해 준다. 드라이버가 붙은 Root Port·e1000e·virtio는 0406/0407(bit1 Memory, bit2 Bus Master, bit10 INTx Disable), 드라이버가 없는 edu·NVMe는 0000. Linux는 enumeration 때 BAR 주소는 쓰지만 decode는 켜지 않는다 — pci_enable_device()가 켠다.
  • bit10(INTx Disable)이 선 장치는 MSI/MSI-X를 쓰는 중이다. MSI를 켜면 커널이 INTx를 끈다.
  • 엔드포인트의 INTx pin A (line 0): Interrupt Line 레지스터(0x3C)는 x86 BIOS 시절 유물이라 ARM에서는 의미가 없다. 진짜 INTx virq는 커널이 DT interrupt-map으로 계산해 pdev->irq에 넣는다 (예제 7에서 15).
  • edu는 cfg 256 B — conventional PCI 장치라 extended config가 없다. Root Port 뒤에 붙어 있어도 PCIe cap이 없다 (QEMU가 허용하는 구성).
  • NVMe의 MSI-X 테이블이 BAR0+0x2000: Don이 SSD에서 구현하던 바로 그 배치(doorbell 영역 뒤에 MSI-X table/PBA). size=65 = admin 1 + I/O 64.
  • 확장 cap 0001 = AER, 000d = ACS, 0003 = Device Serial Number. QEMU Root Port의 LnkCap 16GT/s x32는 모델 기본값이라 의미 없다.
  • cap 09(Vendor Specific) 5개는 virtio 1.0의 common/notify/isr/device/pci-cfg 구조 위치 표시다.

5.4 probe 작성 체크리스트와 함정#

  • probe에서 실패하면 이미 한 일을 되돌리는 코드가 필요 없다(devres). 비관리형 API를 섞으면 그 부분만 직접 되돌려야 한다 — 섞지 말 것.
  • pci_set_master()를 빼먹으면 MMIO는 되는데 DMA와 MSI가 조용히 안 된다. 예제 14(VFIO)에서 정확히 이 증상을 다시 만난다.
  • pdev->irq를 직접 request_irq에 넣는 옛 코드는 MSI-X 다중 벡터에서 틀린다. 항상 pci_irq_vector(pdev, i).
  • INTx는 공유될 수 있으니 IRQF_SHARED + "내 장치가 올린 게 아니면 IRQ_NONE". MSI는 장치 전용이라 공유 플래그가 필요 없다.
  • probe는 sleep 가능한 프로세스 컨텍스트다 (F 모듈). 긴 초기화(펌웨어 로드 G10, 링크 대기)는 괜찮지만, 부팅 시간을 줄이려면 .driver.probe_type = PROBE_PREFER_ASYNCHRONOUS를 고려한다.

7.3 이 숫자를 어떻게 읽어야 하나 — 실제 HW와 반대일 수 있다#

에뮬레이터에서는 INTx가 MSI보다 빠르거나 같게 나왔다. 실제 실리콘에서 이 결론을 내리면 안 된다. 이유:

  • QEMU TCG에서 INTx는 pci_set_irq() → GIC 상태 비트 변경으로 끝나는 함수 호출이다. MSI는 edu가 "메모리 쓰기"를 에뮬레이트해 GICv2m 프레임 → GIC로 가거나, ITS면 게스트 메모리에 있는 ITS 테이블(디바이스·인터럽트 변환 테이블)과 LPI pending 테이블을 에뮬레이터가 읽고 쓰는 경로라 훨씬 길다 (ITS 100 µs대).
  • smp 2에서 MSI가 느린 건 위 taskset 실험이 보여 주듯 raise를 쓴 vCPU와 인터럽트를 받는 vCPU가 다를 때 생기는 vCPU 스레드 간 깨우기 비용으로 보인다 (MSI 대상 CPU0, insmod가 CPU1이면 느림). INTx가 왜 같은 영향을 덜 받는지는 QEMU 내부까지 확인하지 않았다 — 추정으로만 남긴다.
  • 실제 HW에서 MSI가 유리한 이유는 지연 수 µs 차이가 아니라 구조다: (1) INTx는 Assert 메시지와 데이터 DMA 쓰기 사이의 순서가 보장되지 않아 핸들러가 장치 레지스터를 읽어서 flush해야 하지만, MSI는 같은 posted write 스트림이라 데이터가 먼저 도착해 있다. (2) 공유 라인이 없어 다른 장치 핸들러를 돌지 않는다. (3) MSI-X는 큐마다·CPU마다 벡터를 나눠 락 없이 처리한다(NVMe). (4) level 선 ack을 위한 MMIO 쓰기가 없다.
  • 측정 방법 자체는 실 보드에서 그대로 쓸 수 있다: 장치 레지스터 쓰기 직전 타임스탬프와 핸들러 진입 타임스탬프. 실 보드라면 scope로 GPIO 토글을 함께 찍어 교차 검증하는 것이 Don 방식이다.

8. DMA — mask, IOMMU, 그리고 조용한 데이터 손상#

8.1 직관#

장치가 DMA로 쓸 주소는 CPU 물리 주소가 아니라 버스(DMA) 주소다. 둘이 같으려면 IOMMU가 없고 오프셋도 없어야 한다. 그리고 장치가 낼 수 있는 주소 비트 수(DMA mask)가 메모리가 있는 곳까지 닿아야 한다. edu는 28비트(256 MiB 미만)만 낼 수 있는데, QEMU virt의 RAM은 0x4000_0000(1 GiB)부터 시작한다 — RAM 어디에도 닿을 수 없는 장치다. 실무에서 32비트 DMA만 되는 오래된 Wi-Fi·USB 칩을 4 GiB 넘는 RAM이 있는 SoC에 붙일 때와 같은 문제다.

8.2 예제 11 — h11_dma: mask를 정직하게/거짓으로, IOMMU 없이/있이#

무엇을 확인하나: dma_set_mask_and_coherent()의 반환값, dmam_alloc_coherent()가 준 DMA 주소, edu DMA 엔진으로 RAM→장치→RAM 왕복한 데이터가 일치하는지.

출력에서 볼 것 — 이 노트에서 가장 중요한 출력 중 하나다:

  • 정직한 28비트 mask는 -EIO(-5)로 거부된다. IOMMU가 없으면 DMA 주소 = 물리 주소인데, 28비트 안에 RAM이 한 바이트도 없으니 DMA API가 "이 장치는 이 시스템에서 DMA 불가"라고 정확히 말해 준 것이다. 드라이버는 여기서 멈추는 게 맞다.
  • 32비트라고 거짓말하면 모든 API가 성공(ret=0)하고 데이터만 틀린다(match=NO). 장치는 상위 비트를 잘라 0x036a5000 — RAM도 아닌 곳 — 에 썼다. 실제 HW였다면 다른 장치 레지스터나 다른 프로세스의 메모리를 조용히 덮어썼을 것이다. "DMA mask는 장치 데이터시트의 주소 비트 수를 그대로 적는다"가 규칙이다.
  • SMMUv3를 켜면 28비트로 성공한다. 장치가 보는 주소(IOVA) 0x0ffff000은 28비트 안이고, SMMU가 이를 실제 RAM(1 GiB 위)으로 번역한다. IOMMU의 실용적 가치 중 하나: 주소 능력이 부족한 장치를 살린다. 또 하나는 격리 — 장치가 매핑되지 않은 메모리를 건드리면 SMMU fault가 난다(§12의 VFIO가 이걸 전제로 한다).
  • iommu_groups/5: SMMU가 있으면 장치마다 IOMMU 그룹이 생긴다 (그룹 = 서로 격리할 수 없는 장치 묶음).

DMA API의 나머지(streaming dma_map_single/dma_map_sg, 캐시 동기화, dma_sync_*)는 H9에서 다룬다. PCI 드라이버 입장에서 기억할 것: dma_set_mask_and_coherent()는 probe에서 pci_set_master() 뒤, 버퍼 할당 전에. 64비트를 먼저 시도하고 실패하면 32비트로 내려가는 패턴이 흔했지만, 현재 커널에서는 64비트 mask 설정이 사실상 실패하지 않으므로 "64비트 가능한 장치는 DMA_BIT_MASK(64) 한 번"이 권장이다.

9.1 예제 12 — sysfs로 장치를 끄고 켜고 지우고 다시 찾기#

무엇을 확인하나: G3에서 본 driver core의 bind/unbind가 PCI에서는 어떻게 보이는지, 그리고 PCI만의 enable, reset, remove, rescan.

(rescan 직후 probe의 latency 줄은 grep -v latency로 걸렀다. 마지막 ../bus/pci/drivers/h11_edu는 ls -l driver 결과다.)

출력에서 볼 것:

  • enable에 1을 쓰면 pci_enable_device()가 불려 cmd가 0002(Memory decode)가 된다. 드라이버 없이 장치를 켜는 디버그용 스위치다 (resource0 mmap 전에 필요).
  • reset: 드라이버가 붙은 상태에서도 된다. PCI core가 config를 저장 → 드라이버의 reset_prepare → 리셋(여기서는 reset_method=bus, Root Port의 Secondary Bus Reset) → config 복원 → reset_done. 리셋 후 cmd가 0406으로 복원된 게 그 증거다. Don의 SSD 세계로 말하면 호스트가 FLR/Hot Reset을 날리고 config를 다시 써 주는 그 시퀀스다.
  • remove: 드라이버 remove() → pci_dev 삭제. 디렉터리 목록에서 0000:01:00.0이 사라졌다. 장치는 물리적으로 그대로 있다 — 커널이 잊었을 뿐.
  • rescan: 전체 버스를 다시 스캔해서 새로 보이는 장치만 추가한다. 같은 BAR 주소를 다시 배정받았고 h11_edu가 자동으로 probe됐다. 핫플러그 슬롯이 없는 보드에서 "부팅 후 늦게 전원이 들어오는 PCIe 장치(예: 모뎀)"를 붙이는 실전 기법이다 (FPGA 비트스트림 로드 후 rescan도 같은 패턴).
  • unbind/bind: pci_dev는 남기고 드라이버만 떼었다 붙인다 (G3의 driver core 경로). §12에서 driver_override와 함께 VFIO로 넘길 때 쓴다.

9.2 Hotplug#

진짜 PCIe 핫플러그(Slot Capabilities의 Presence Detect, Attention Button)는 pciehp(CONFIG_HOTPLUG_PCI_PCIE) 서비스가 Root Port/Downstream Port에 붙어 처리한다 — 랩 커널은 이 옵션이 꺼져 있어 실행하지 못했다 (# CONFIG_HOTPLUG_PCI_PCIE is not set). 동작 원리는 같다: 장치 등장 → pci_rescan_bus() 경로, 장치 제거 → pci_stop_and_remove_bus_device() 경로. 드라이버 입장에서 중요한 점은 surprise removal: 장치가 사라진 뒤 MMIO 읽기는 0xffffffff를 돌려준다. 그래서 견고한 드라이버는 readl() == ~0을 "장치 사라짐"으로 의심하고 pci_device_is_present()로 확인한다 (NVMe 드라이버가 그렇게 한다).

10. AER — 에러를 커널이 받고 드라이버가 복구한다#

10.1 흐름#

Don은 AER 레지스터(Uncorrectable/Correctable Status, Mask, Severity, Header Log)를 장치 쪽에서 세팅해 본 사람이다. 호스트 쪽 이야기는 이렇다: 장치가 ERR_COR/ERR_NONFATAL/ERR_FATAL 메시지를 올려 보냄 → Root Port가 Root Error Status에 기록하고 인터럽트(위에서 본 aerdrv MSI-X 벡터) → aerdrv(drivers/pci/pcie/aer.c)가 소스 장치를 찾아 상태 레지스터를 읽고 로그 → correctable이면 기록 후 클리어, uncorrectable이면 pcie_do_recovery()가 해당 브리지 아래 모든 드라이버의 pci_error_handlers를 순서대로 부른다.

6.18의 struct pci_error_handlers에는 이 외에 mmio_enabled, reset_prepare/reset_done(예제 12의 sysfs reset이 부르는 쪽), cor_error_detected가 있다.

10.2 예제 13 — QEMU 모니터로 AER 에러 주입#

무엇을 확인하나: correctable, uncorrectable non-fatal, fatal 에러를 Root Port rp3(그 아래 e1000e)에 주입하고 커널 로그·복구·sysfs 카운터를 본다. 출력에서 볼 것:

  • Correctable(RxErr)은 로그만 남기고 끝났다. 실무에서 수천 개씩 쌓이면 링크 신호 품질(SI) 문제의 신호다 — Don이 scope로 잡던 그 영역. 레이트 리밋이 걸려 있어 로그는 줄어들 수 있지만 sysfs 카운터는 정확하다.
  • Uncorrectable은 non-fatal도, fatal도 Root Port 링크 리셋(Secondary Bus Reset) → e1000e의 error_detected → slot_reset → resume을 거쳐 "device recovery successful", 그리고 e1000e가 링크를 다시 올렸다(NIC Link is Up). 인터페이스는 UP으로 살아 있다. (non-fatal인데도 링크 리셋을 한 것은 e1000e의 error_detected가 NEED_RESET을 돌려주기 때문이다 — 6.18 drivers/pci/pcie/err.c의 pcie_do_recovery는 status가 NEED_RESET이거나 state가 frozen이면 reset_subordinates를 부른다.)
  • 처음엔 e1000e 자체에 주입했는데 아무 일도 없었다. 조사해 보니 QEMU e1000e 모델은 DEVCTL의 에러 보고 enable 비트가 쓰기 불가(읽으면 항상 0)라 메시지를 올리지 못한다. 그래서 Root Port(이 비트가 0x000f로 켜져 있음)에 주입했다. 실 장비에서도 "AER가 안 찍힌다"의 첫 확인은 장치 DEVCTL의 CERE/NFERE/FERE/URRE 비트와 Root Port의 Root Error Command다.
  • aer_dev_* sysfs 파일은 장치마다 있고, Root Port에는 aer_rootport_total_*이 더 있다. 현장 장비 모니터링 스크립트가 읽기 좋은 위치다.
  • 랩 커널에는 CONFIG_PCIE_DPC(Downstream Port Containment)가 꺼져 있다. DPC가 켜진 하드웨어에서는 fatal 에러 때 포트가 스스로 링크를 끊어 오염 전파를 막고, 복구 경로가 DPC 쪽으로 간다.

12. VFIO — 유저 공간 드라이버 (SPDK·DPDK의 세계)#

12.1 직관#

SPDK는 NVMe를 커널 nvme 드라이버 없이 유저 공간 폴링 드라이버로 돌린다. Don이 SSD 펌웨어 쪽에서 "호스트 IOPS가 커널 스택 오버헤드로 묶인다"는 얘기를 들었다면 그 해결책이 이것이다. 그러려면 유저 프로세스가 (1) BAR를 mmap하고, (2) 인터럽트를 받고(또는 폴링), (3) 안전하게 DMA할 수 있어야 한다. (3)이 핵심이다: 유저 프로세스가 장치에 아무 물리 주소나 DMA하라고 시키면 커널 메모리를 덮어쓸 수 있다. 그래서 VFIO는 IOMMU로 장치의 DMA를 그 프로세스가 등록한 메모리로만 제한하고, MSI도 장치별로 격리(ITS의 DeviceID)될 때만 허락한다.

그림 6 — 커널 드라이버와 VFIO 유저 드라이버. 데이터 경로(MMIO·DMA)는 둘 다 장치에 직접 닿는다. 차이는 누가 그 경로를 쥐고 있고, 무엇이 안전을 보장하느냐다.

Q. "Walk me through what a PCI driver's probe function does."

A. ID 테이블 매칭으로 probe가 불리면, 장치를 켜고(pcim_enable_device), 쓸 BAR를 요청·매핑하고(pcim_iomap_region), bus mastering을 켜고, DMA mask를 장치 주소 능력에 맞게 설정하고, pci_alloc_irq_vectors로 MSI-X→MSI→INTx 순으로 벡터를 받아 pci_irq_vector로 핸들러를 등록한 뒤, 장치를 초기화하고 drvdata를 저장한다. managed API를 써서 실패나 remove 때 자동 역순 정리가 되게 한다.

"Probe is called after the PCI core matches the device against my id_table. I enable the device with pcim_enable_device, request and map the BARs I need with pcim_iomap_region — the plural pcim_iomap_regions is deprecated now — set bus mastering, set the DMA mask to what the hardware can actually address, then allocate interrupt vectors with pci_alloc_irq_vectors, preferring MSI-X, and request each one through pci_irq_vector. Then I initialize the hardware and store my private struct with pci_set_drvdata. Because everything is devres-managed, an error path or remove unwinds automatically in reverse order."

꼬리 질문: "Why must pci_set_master be called?" → BME가 꺼져 있으면 장치가 DMA도 MSI도 못 낸다. MSI는 메모리 쓰기이기 때문이다.

Q. "How does Linux enumerate PCIe devices on an ARM SoC with no BIOS?"

A. DT의 host bridge 노드에서 시작한다. host bridge 드라이버(ECAM generic이나 DWC glue)가 ECAM·주소 창·인터럽트 매핑을 받아 pci_host_probe를 부르면, PCI core가 버스 0부터 깊이 우선으로 Vendor ID를 읽어 장치를 찾고, BAR에 all-ones를 써 크기를 재고, 브리지를 만나면 버스 번호를 주고 재귀한다. 스캔이 끝나면 아래에서 위로 브리지 창 크기를 합산하고 위에서 아래로 주소를 배정한 다음, 장치를 등록해 드라이버 매칭을 일으킨다.

"On ARM there's usually no firmware doing enumeration, so the kernel does it. The host bridge is described in the device tree — ECAM base, the memory and I/O windows in ranges, interrupt-map and msi-map. The host driver, pci-host-generic or a DesignWare glue driver, calls pci_host_probe. The core scans depth-first: reads the vendor ID, sizes each BAR by writing all ones, assigns bus numbers to bridges and recurses. Only after the whole scan does it size the bridge windows bottom-up and assign addresses top-down, then it adds the devices so drivers can bind."

Q. "What's the difference between MSI and MSI-X, and why does NVMe use MSI-X?"

A. 둘 다 장치가 메모리 쓰기로 인터럽트를 보내는 방식이다. MSI는 주소 하나에 연속된 최대 32개 벡터, MSI-X는 BAR 안의 테이블로 최대 2048개 벡터를 각각 다른 주소·데이터·마스크로 갖는다. 그래서 MSI-X는 큐마다 벡터를 주고 각 벡터를 다른 CPU에 고정할 수 있다. NVMe는 CPU당 submission/completion 큐 쌍을 두고 completion 인터럽트를 그 CPU로 보내 락과 캐시 이동을 없앤다. 랩에서도 nvme가 CPU 2개에 I/O 큐 2개 + admin 1개 = MSI-X 3벡터를 썼다.

"Both are in-band memory writes, so there's no shared wire and the interrupt is ordered behind the device's DMA writes. MSI gives one address and up to 32 contiguous vectors; MSI-X has a table in a BAR with up to 2048 entries, each with its own address, data and mask bit. That lets NVMe give every CPU its own queue pair and its own interrupt vector with managed affinity, so completions are handled on the submitting CPU without locks. In my QEMU lab, the nvme driver took exactly three vectors on a two-CPU guest: one admin queue and one I/O queue per CPU."

꼬리 질문: "How does the MSI address get programmed?" → pci_alloc_irq_vectors가 PCI-MSI irq_domain → GICv2m/ITS domain을 거치며 irq_compose_msi_msg가 doorbell 주소·데이터를 만들고, PCI core가 그 값을 MSI-X 테이블 엔트리에 쓴다.

Q. "A device shows up in lspci but the driver fails with 'BAR 0: no space'. How do you debug?"

A. 부팅 로그에서 그 BAR의 크기와 64비트/prefetchable 여부, 상위 브리지의 창, root bus resource를 본다. 대부분 host bridge의 창(DT ranges)이 작거나, 64비트 non-pref BAR가 32비트 창에 안 들어가거나, 핫플러그 여유분이 공간을 먹은 경우다. /proc/iomem으로 실제 배치를 보고, 창을 키우거나 pci=realloc, hpmemsize를 조정한다.

"First I read the enumeration log: the BAR size and type, the parent bridge windows, and the root bus resources from the host bridge. Then /proc/iomem to see what's actually placed. Typical causes are a too-small window in the device tree ranges, a 64-bit non-prefetchable BAR that has to fit in the 32-bit window behind a bridge, or hotplug padding. Fixes are enlarging the window, adding a 64-bit prefetchable window, pci=realloc to let the kernel redo bridge windows, or tuning hpmemsize."

Q. "What is VFIO and why does it require an IOMMU?"

A. VFIO는 PCI 장치를 유저 공간 프로세스에 안전하게 넘기는 프레임워크다. BAR를 mmap하게 해 주고, 인터럽트를 eventfd로 전달하고, DMA는 프로세스가 등록한 메모리만 IOMMU 페이지 테이블에 매핑한다. IOMMU 없이 장치가 아무 물리 주소에 DMA할 수 있으면 유저가 커널 메모리를 덮어쓸 수 있으니 안전을 보장할 수 없다. 같은 이유로 MSI도 장치별로 격리돼야 한다 — 실제로 GICv2m에서는 "No interrupt remapping support"로 거부됐고 GICv3 ITS에서 동작했다. SPDK·DPDK·VM 패스스루가 이걸 쓴다.

"VFIO hands a device to user space safely. The process gets the BARs through mmap, interrupts through eventfds, and does DMA only to memory it explicitly maps with VFIO_IOMMU_MAP_DMA, which programs the IOMMU. Without an IOMMU the device could DMA anywhere, so user space could corrupt the kernel. MSI has to be isolated too: in my lab VFIO refused to attach on GICv2m with 'no interrupt remapping support' and worked once I switched to GICv3 with the ITS, which identifies the device by its requester ID. SPDK, DPDK and VM passthrough are the main users."

꼬리 질문: "What is an IOMMU group?" → IOMMU가 서로 구분할 수 없는 장치 묶음(예: ACS 없는 스위치 뒤). 그룹 안의 모든 장치가 vfio에 bind되거나 드라이버가 없어야 group이 viable하다.

Q. "How does Linux handle a PCIe uncorrectable error?"

A. 장치가 ERR_NONFATAL/FATAL 메시지를 보내면 Root Port의 AER 서비스가 인터럽트를 받아 소스 장치의 AER 레지스터를 읽어 로그를 남기고, pcie_do_recovery가 그 아래 드라이버들의 error_detected를 부른다. 드라이버가 리셋이 필요하다고 답하면 링크(Secondary Bus) 리셋 후 slot_reset, 그리고 resume. Correctable은 로그와 카운터만 남는다. 랩에서 QEMU로 에러를 주입해 e1000e가 링크 리셋 후 복구되는 것을 확인했다.

"The device sends an error message upstream; the root port's AER service gets the interrupt, finds the source, logs the status and header log, and for uncorrectable errors runs pcie_do_recovery. Every driver below that port gets error_detected; if one asks for a reset, the core resets the link, calls slot_reset so the driver can restore state, then resume. Correctable errors are just logged and counted in sysfs. I injected all three kinds into a QEMU root port and watched e1000e recover through a secondary bus reset."

Q. "Kernel driver or user-space driver for a custom PCIe FPGA?"

A. 다른 커널 서브시스템(V4L2, netdev, 블록)과 통합해야 하거나, 전원 관리·AER 복구·여러 프로세스 공유가 필요하면 커널 드라이버. 장치 하나를 한 앱이 독점하고 최저 지연·폴링이 목표면 VFIO 유저 드라이버. 개발 초기 bring-up에는 VFIO가 빠르게 레지스터를 만져 볼 수 있어 편하고, 제품화 단계에서 커널 드라이버로 옮기는 경우가 많다.

"If the device needs to plug into kernel frameworks — V4L2 for a camera, netdev, block — or needs power management, error recovery and sharing across processes, it's a kernel driver. If one application owns the device and wants minimum latency with polling, a VFIO user-space driver is attractive. For early bring-up I like VFIO because I can poke registers and test DMA from a C program without rebooting, then move the proven sequence into a kernel driver."

20. 요약 & 체크리스트#

Linux PCI는 DT의 host bridge 노드(ECAM generic 또는 DWC glue)에서 출발해 pci_host_probe → 스캔(Vendor ID, BAR 크기, 버스 번호) → 자원 배정(브리지 창 합산, 주소 배정) → 장치 등록 → id_table 매칭 → probe()로 이어진다. 드라이버는 pcim_enable_device, pcim_iomap_region(복수형은 deprecated), pci_set_master, dma_set_mask_and_coherent, pci_alloc_irq_vectors + pci_irq_vector라는 정해진 순서를 managed API로 쓴다. MSI는 irq_domain 계층(PCI-MSI → GICv2m/ITS → GIC)을 거쳐 virq가 되고, /proc/interrupts의 칩 이름이 그 경로를 말해 준다. DMA mask는 장치 능력 그대로 — 거짓이면 조용한 손상이고, IOMMU는 주소 능력 부족과 격리를 해결한다. sysfs(config, resource, enable, reset, remove, rescan, driver_override, sriov_numvfs, aer_dev_*)만으로 대부분의 디버그와 실험이 가능하고, VFIO는 IOMMU와 격리된 MSI를 전제로 장치를 유저 공간 드라이버에 넘긴다.
