0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어에서 UART를 쓸 때는 구조가 단순했다. RX ISR이 데이터 레지스터에서 바이트를 꺼내 링버퍼에 넣고, 디버그 셸 태스크가 그 링버퍼에서 한 줄씩 꺼내 명령을 파싱한다. 층은 둘뿐이다: 드라이버(ISR + 링버퍼)와 소비자(셸).

Linux에서 UART는 다섯 층이다. 바이트 하나가 앱에 닿기까지 이 층을 모두 지난다.

그림 1 — UART 수신 데이터가 올라가는 층. 왼쪽 기둥이 보통의 tty 경로(/dev/ttyAMA1), 오른쪽이 serdev 경로다. serdev가 붙은 포트는 TTY core까지는 같이 쓰지만 line discipline과 /dev/tty* 노드를 건너뛰고 커널 드라이버가 바이트를 직접 받는다(§8).

각 층을 펌웨어 감각으로 번역하면 이렇다.

왜 이렇게 많은 층이 있나. TTY는 원래 1970년대 텔레타이프(teletype) 터미널이 시리얼 선으로 유닉스에 붙던 구조다. 사람이 타이핑하는 글자를 줄 단위로 모으고(Backspace 처리), 화면에 다시 찍고(echo), Ctrl-C면 프로그램을 죽이는 일을 커널이 해 줬다. 그 "사람용 처리" 층이 line discipline이고, 오늘날 GNSS나 MCU처럼 기계가 말하는 바이너리 스트림에는 그 처리가 오히려 독이 된다. 이 노트의 절반은 그 독을 빼는 법(§5, §6)이다.

이 노트의 순서: §1 실습 장치 만들기 → §2 /proc·/sys로 층 들여다보기 → §3 UART 드라이버 층과 baud → §4 TTY core와 RX 경로 → §5 line discipline → §6 termios → §7 콘솔 → §8 serdev와 GNSS 서브시스템 → §9 RS-485 → §10 처리량·지연 측정.

실행 환경: Lima VM elinux(aarch64, 호스트 커널 uname -r = 7.0.0-38-generic, QEMU 10.2.1) 안에서 공용 랩 커널 Linux 6.18.55(BusyBox initramfs)를 QEMU virt(cortex-a57, 512 MB, TCG)로 부팅해 실험했다. 게스트 바이너리는 VM에서 gcc -static -Wall -Wextra -O2로 빌드(경고 0개), 커널 모듈은 make -C /var/lab/out/linux-build M=$PWD로 빌드했다. 랩은 읽기 전용으로만 썼고 산출물은 VM의 /var/tmp/H8/에 만들었다. 소스 줄 번호는 /var/lab/src/linux-6.18.55 기준이다. 시각·주소·타이밍 값은 실행마다 다르다.

1. 실습 장치 만들기 — 두 번째 UART와 가짜 GNSS 모듈#

1.1 직관#

E1에서는 콘솔 UART(ttyAMA0)를 읽었다. 콘솔은 커널 로그와 셸이 쓰고 있어서 실험용으로 쓰기 곤란하다. 실제 보드라면 GNSS 모듈은 별도 UART(예: i.MX8의 ttymxc1)에 붙는다. 그래서 QEMU에 UART를 하나 더 달고, 그 반대쪽 끝(선로 건너편)을 VM 호스트의 Python 스크립트로 만든다. 이 스크립트가 "GNSS 모듈" 역할을 해서 NMEA 문장을 보낸다.

그림 2 — 실습 배선. 두 번째 PL011의 "선로"가 VM 호스트의 unix socket이고, 그 끝에서 Python이 GNSS 모듈 흉내를 낸다. 실제 보드라면 이 자리에 u-blox나 MediaTek GNSS 칩이 TX/RX 두 가닥으로 붙는다.

1.2 예제 1 — QEMU virt에 PL011을 하나 더 달 수 있나#

무엇을 확인하나: -serial을 두 번 주면 virt 머신이 두 번째 PL011을 DT에 넣는지 DTB를 덤프해서 본다(QEMU 버전에 따라 다르므로 직접 확인해야 한다).

출력에서 볼 것:

  • QEMU 10.2의 virt는 -serial이 두 개면 두 번째 PL011을 0x9040000, SPI 8에 만든다(옛 QEMU는 이 주소의 UART를 secure=on일 때 Secure 월드용으로만 썼다). aliases의 serial1이 리눅스에서 ttyAMA1이라는 번호가 된다(pl011_probe_dt_alias, amba-pl011.c:2776).
  • 이 노드는 진짜 DT 노드이므로 자식 노드를 달아 serdev 장치를 기술할 수 있다(§8). PCI 16550(-device pci-serial)이나 virtio-console은 DT 노드가 없어 serdev 실험에 못 쓴다.

참고로 다른 두 방법도 이 랩 커널에서 동작은 한다(예제 1b). 무엇을 확인하나: -device pci-serial(PCI에 붙은 16550, 드라이버 8250_pci, CONFIG_SERIAL_8250_PCI=y)과 virtio 시리얼 포트가 어떤 장치 노드가 되는지.

(LAB_CMD 에코 줄과 ls의 색 제어 문자는 지웠다.) PCI 16550은 ttyS0(16550A, base_baud = 115200 = 1.8432 MHz / 16)이 되고, ttyS1~3은 CONFIG_SERIAL_8250_RUNTIME_UARTS=4 때문에 미리 만들어진 빈 자리다. virtio 포트는 TTY가 아니라 /dev/vport0p1이라는 단순 문자 장치다(termios가 없다). 이 노트는 실제 SoC와 가장 닮은 두 번째 PL011을 쓴다.

1.3 예제 2 — 가짜 GNSS 모듈 (VM 호스트 쪽 Python)#

무엇을 확인하나: 선로 건너편 장치를 흉내 낸다. NMEA 문장은 $로 시작해 * 뒤에 체크섬($와 * 사이 모든 바이트의 XOR, 16진 두 자리), 끝에 \r\n이 붙는다. 송신 속도는 "8N1에서 1바이트 = 10비트"로 계산해 9600 baud인 척 문장마다 쉬어 준다.

동작 규칙: 게스트가 한 줄(예: MediaTek GNSS의 설정 명령 $PMTK220,1000*1F = "1초마다 출력")을 보내면 그때부터 한 "세션" 동안 스트림을 보낸다. 실제 GNSS 모듈은 전원을 켜면 그냥 쏟아내지만, 실험마다 시작점을 맞추려고 이렇게 했다. 세션 동안 게스트가 보낸 바이트는 "echo"로 센다 — §6에서 쓴다.

에뮬레이터 주의: 이 스크립트는 문장 단위로 몰아서 보내고 문장 사이를 쉰다. 진짜 9600 baud 선로는 바이트마다 1.04 ms 간격으로 들어온다. 그리고 QEMU의 PL011은 baud 설정과 상관없이 소켓에 들어온 만큼 바로 RX FIFO에 넣는다(§10에서 측정). 그래서 타이밍 숫자는 "실제 보드에서도 이렇다"가 아니라 "커널 경로가 이렇게 동작한다"를 보는 용도다.

1.4 실행 도구 — h8_run.sh#

무엇을 하나: initramfs에 게스트 프로그램을 넣고, Python 생성기를 띄운 뒤, 두 번째 시리얼을 그 소켓에 연결해 부팅한다. 이후 모든 예제가 이 스크립트로 돈다.

게스트 C 프로그램은 VM에서 gcc -std=gnu11 -Wall -Wextra -O2 -static X.c -o /var/tmp/H8/bin/X로 빌드해 bin/에 두면 initramfs 루트에 들어간다. 호출 예: limactl shell elinux -- bash -lc 'bash /Users/donh/.elinux_scratch/H8/h8_run.sh modes /Users/donh/.elinux_scratch/H8/g_modes.sh nmea 9600 6'.

2. 층 들여다보기 — /proc/tty, /sys/class/tty, stty#

2.1 예제 3 — 게스트에서 TTY 계층 훑어보기#

무엇을 확인하나: 커널에 등록된 tty 드라이버와 line discipline 목록, ttyAMA1의 sysfs 속성, 기본 termios, 포트별 카운터.

출력에서 볼 것 — 층마다 하나씩:

  • /proc/tty/drivers = 등록된 tty_driver 목록. 한 줄이 "이름, 노드 접두어, major, minor 범위, 종류"다. ttyAMA 204 64-77은 PL011 드라이버가 uart_register_driver()로 등록한 것이고, 그 안에서 serial core가 tty_driver를 만들었다. 하드웨어가 없는 tegra_hsuart, IMX-uart(/dev/ttymxc, i.MX 보드의 이름이 여기서 온다)까지 보이는 건 defconfig가 여러 SoC 드라이버를 빌트인으로 넣었고, uart_register_driver()는 장치가 없어도 모듈 init에서 불리기 때문이다. pty(가상 터미널 쌍, ssh·tmux가 쓰는 것)도 같은 TTY 계층의 드라이버다.
  • /proc/tty/ldiscs = 등록된 line discipline. 기본 n_tty(번호 0)와 오류 처리용 n_null(27)뿐이다. N_GSM0710은 이 커널에서 # CONFIG_N_GSM is not set, BT용 N_HCI(15)는 hci_uart 모듈이 로드돼야 등록된다.
  • sysfs ttyAMA1: type=32는 PORT_AMBA, io_type=2는 MMIO(UPIO_MEM), xmit_fifo_size=16은 드라이버가 알려 준 하드웨어 FIFO 깊이다. 부모 장치가 9040000.pl011:0.0이고 드라이버가 serial-base 버스의 port인 것은 E1에서 본 6.x serial core의 "포트 장치" 계층이다.
  • uartclk=0, 그리고 /proc/interrupts에 IRQ 14가 없다. ttyAMA1은 아직 아무도 연 적이 없다. PL011 드라이버는 포트를 처음 열 때 uart_ops.startup(pl011_startup, 1905행)에서 클럭을 켜고 uartclk를 읽으며(pl011_hwinit 1795행 clk_get_rate) IRQ를 요청한다(pl011_allocate_irq, 1916행). 펌웨어의 "UART init은 부팅 때 한 번"과 다르다. 안 쓰는 UART는 클럭도 IRQ도 안 잡는다 — 전력 관리 관점에서 당연한 설계다. stty가 잠깐 열었다 닫은 뒤라 지금은 다시 닫힌 상태다.
  • stty -a의 기본 termios: icanon(줄 단위), echo(받은 글자를 되돌려 보냄), isig(^C를 신호로), icrnl(CR을 LF로), ixon(^S/^Q 흐름 제어), opost onlcr(보낼 때 LF를 CRLF로). 전부 사람 터미널용 기본값이다. GNSS 모듈 앞에서 이게 무슨 일을 하는지가 §5–§6의 주제다. (stty: standard input 한 줄은 BusyBox stty가 창 크기 ioctl에 실패하며 찍는 메시지로, 결과와 무관하다.)
  • /proc/tty/driver/ttyAMA: serial core가 포트마다 보여 주는 카운터(tx, rx, 그리고 에러가 있으면 fe(framing)·pe(parity)·oe(overrun)·brk)와 모뎀 선 상태(RTS|DTR). 현장에서 "데이터가 깨진다"고 하면 가장 먼저 보는 파일이다. oe가 늘면 FIFO 넘침(ISR 지연), fe가 늘면 baud 불일치나 노이즈다. root만 읽을 수 있다.

3. ① UART 드라이버 층 — uart_driver, uart_port, uart_ops#

3.1 세 구조체의 역할#

  • struct uart_driver — "이 종류의 UART 전체"를 대표한다. 이름(ttyAMA), major/minor, 포트 개수(nr), 콘솔 구조체. 드라이버 init에서 uart_register_driver()로 한 번 등록한다. 이때 serial core가 tty_driver를 만든다(§2의 /proc/tty/drivers 한 줄).
  • struct uart_port — 포트 하나. 레지스터 베이스(membase, mapbase), IRQ, uartclk, fifosize, 카운터(icount), 그리고 아래 ops를 가리킨다. probe에서 채워 uart_add_one_port()로 등록하면 /dev/ttyAMA1(또는 serdev 컨트롤러)이 생긴다.
  • struct uart_ops — 하드웨어를 만지는 함수 표. serial core가 "지금 TX를 시작해", "baud를 바꿔"를 이 표로 부른다.

3.2 TX 경로와 kfifo#

write(fd, buf, n)의 흐름: VFS → tty_write → ldisc의 n_tty_write(OPOST면 LF→CRLF 변환) → tty->ops->write = serial core의 uart_write(serial_core.c:610) → 포트의 TX 링버퍼에 복사 → uart_start → uart_ops.start_tx. 드라이버는 TX 인터럽트(또는 DMA 완료)마다 링버퍼에서 꺼내 FIFO를 채운다.

이 TX 링버퍼가 6.10부터 kfifo로 바뀌었다(그 전에는 struct circ_buf xmit이 uart_state에 있었다). 6.18.55에서 확인하면:

TX 링버퍼는 이제 tty_port.xmit_fifo이고, serial core의 uart_write가 kfifo_in으로 넣고(631행), PL011의 TX 루프가 kfifo_peek → FIFO에 쓰기 → kfifo_skip(1541–1547행)으로 꺼낸다. kfifo_len < WAKEUP_CHARS(256)면 uart_write_wakeup으로 "더 써도 된다"고 위층을 깨운다. Don이 짜던 TX 링버퍼 + "반 이상 비면 producer 깨우기" 그대로다. 오래된 드라이버 코드나 블로그에서 xmit->buf[xmit->tail], uart_circ_empty()가 보이면 6.10 이전 코드다.

3.3 baud와 클럭 — 예제 4#

PL011의 baud는 UARTCLK / (16 × baud)를 16.6 고정소수점(IBRD 정수부 16비트 + FBRD 소수부 6비트)으로 넣는다. 커널은 이렇게 계산한다.

무엇을 확인하나: 같은 계산을 Python으로 해서 QEMU virt의 24 MHz 클럭(/sys/class/tty/ttyAMA1/uartclk, 예제 6)에서 baud 오차를 본다.

출력에서 볼 것: 24 MHz에서 921600은 +0.16% 오차, 1 Mbaud·1.5 Mbaud는 정확하다. UART는 보통 양쪽 합쳐 2~3% 오차까지 견디므로 문제없다. 최대 baud = uartclk/16 = 1.5 Mbaud — 예제 7에서 B3000000을 요청하면 커널이 거부하는 이유다. 실무에서 "3 Mbaud BT 모듈이 안 붙는다"면 DT의 UART 클럭(assigned-clock-rates)부터 본다(H3). Don이 RF 칩 bring-up에서 보던 "레퍼런스 클럭이 틀리면 모든 게 조금씩 어긋난다"와 같은 이야기다.

한 가지 함정: /sys/.../uartclk는 포트가 한 번 열리기 전엔 0이었다(예제 3). 클럭 값을 확인하려면 포트를 연 뒤에 본다.

4. ③ TTY core — tty_struct, tty_port, flip buffer#

4.1 두 구조체#

  • struct tty_port — 물리 포트의 수명과 같다. 장치가 있는 동안 계속 존재한다. RX flip buffer(buf), TX xmit_fifo, 열린 횟수, 모뎀 선 대기(carrier) 처리, 그리고 client_ops(받은 데이터를 누구에게 줄지 — ldisc냐 serdev냐, §8)를 가진다.
  • struct tty_struct — 열린 터미널 세션. 누군가 open()하면 생기고 마지막 close()에 사라진다. termios, 걸린 line discipline(ldisc), 세션·프로세스 그룹(Ctrl-C를 누구에게 보낼지), read_wait/write_wait 대기 큐를 가진다.

펌웨어 비유: tty_port는 "UART 채널 제어 블록(정적)", tty_struct는 "그 채널을 지금 쓰고 있는 셸 세션 컨텍스트(동적)"다.

4.2 flip buffer — ISR과 소비자 사이의 버퍼#

드라이버의 RX ISR은 바이트를 tty_insert_flip_char()/tty_insert_flip_string()으로 tty_port.buf에 넣고 마지막에 tty_flip_buffer_push()를 부른다. 이 버퍼가 flip buffer다. 이름은 옛날 구현(두 버퍼를 번갈아 뒤집던 더블 버퍼)에서 왔고, 지금은 struct tty_buffer 조각들의 연결 리스트다. 조각 하나는 최대 TTY_BUFFER_PAGE(4 KB 페이지에서 약 2 KB), 포트당 메모리 한도는 TTYB_DEFAULT_MEM_LIMIT = 640 KB다(tty_buffer.c:24-41). 바이트마다 "플래그"(정상·패리티 에러·프레이밍 에러·break·overrun)도 같이 저장돼서, ldisc가 에러 바이트를 다르게 처리할 수 있다(PARMRK, INPCK).

tty_flip_buffer_push()는 인터럽트 컨텍스트에서 워크큐에 일을 넘기고 끝난다(queue_work(system_unbound_wq, ...), E1 §6.4). 실제로 ldisc에 데이터를 넘기는 flush_to_ldisc()는 kworker 스레드(프로세스 컨텍스트)에서 돈다. 그래서 ldisc와 serdev의 receive_buf는 잘 수 있다(mutex를 써도 된다).

4.3 예제 5 — kprobe로 RX 경로를 실제로 찍기#

E1은 이 경로를 소스로만 따라갔다(랩 기본 커널에 ftrace가 없어서). 지금은 랩에 Image-dbg(kprobe·ftrace 포함)가 있으니 실제로 찍어 본다. 무엇을 확인하나: tty_flip_buffer_push(ISR 쪽)와 n_tty_receive_buf2(ldisc 쪽)에 kprobe를 걸고 각각의 커널 스택을 stacktrace 트리거로 남긴다.

부팅은 h8_run.sh와 같되 -kernel /var/lab/out/Image-dbg로 했다(h8_nmea는 §6의 예제). 생성기는 nmea 9600 2(문장 4개).

출력에서 볼 것:

  • 위 7줄(kprobe_trace_func … el1h_64_sync)은 kprobe 자체의 브레이크포인트 예외 처리라 무시한다.
  • tty_flip_buffer_push는 <idle>-0 컨텍스트, 플래그 d.h1.(h = hardirq)에서 불렸다. CPU가 놀다가 UART IRQ를 받았고, 스택이 generic_handle_domain_irq(GIC, H6) → handle_fasteoi_irq → __handle_irq_event_percpu(등록된 handler 호출)다. 그 사이에 있어야 할 pl011_int가 안 보이는 것은 함수 진입 지점의 kprobe라서 호출자(pl011_int)의 복귀 주소가 아직 링크 레지스터에만 있고 스택 프레임에 안 쌓였기 때문이다(arm64 프레임 포인터 unwinder의 알려진 모양). E1 §6.4 표의 4~7단계가 이 줄들이다.
  • n_tty_receive_buf2는 kworker/u4:2 스레드, 플래그 d....(인터럽트 아님)에서 process_one_work → flush_to_ldisc → tty_port_default_receive_buf → ldisc로 불렸다. IRQ에서 워크큐로 넘어가는 "top half / bottom half" 분리(F6, F7)가 눈에 보인다.
  • push 16번 vs ldisc 호출 5번: IRQ마다 push가 일어나지만, 워크가 이미 큐에 있으면 다시 넣지 않으므로 여러 번의 push가 한 번의 flush_to_ldisc로 합쳐진다. 문장 4개가 ldisc 호출 5번으로 처리됐다 — 대략 문장당 한 번이다(정확히 어느 push들이 어느 호출로 묶였는지는 타임스탬프를 전부 대조하지 않아 확인하지 않았다). 펌웨어에서 "ISR은 버퍼에 넣고 이벤트만 세팅, 태스크가 몰아서 처리"와 같은 구조다.

4.4 throttle — 위층이 못 따라올 때#

ldisc의 읽기 버퍼(N_TTY_BUF_SIZE = 4096바이트, n_tty.c:59)가 거의 차면 n_tty가 tty_throttle_safe()를 부르고, serial core는 uart_ops.throttle(PL011이면 pl011_throttle_rx)로 RX 인터럽트를 끄고 하드웨어 흐름 제어가 켜져 있으면 RTS를 내려 상대방을 멈춘다. 앱이 다시 읽어서 버퍼가 비면 unthrottle. 흐름 제어가 꺼져 있으면? 하드웨어 FIFO가 넘치고 /proc/tty/driver/*의 oe(overrun) 카운터가 오른다. 흐름 제어 없는 고속 UART에서 데이터가 사라지는 전형적인 경로다.

5. ④ line discipline — N_TTY와 친구들#

5.1 무엇을 하나#

5.2 N_TTY가 받은 바이트에 하는 일#

n_tty_receive_buf_common → 바이트마다 termios 플래그를 보고 처리한다. 사람이 타이핑할 때 편리한 기능들이다.

  • ICRNL: CR(0x0D)을 LF(0x0A)로 바꾼다. IGNCR면 CR을 버린다. INLCR은 반대.
  • ICANON(canonical, 줄 단위): LF·EOF·EOL을 받을 때까지 read()를 깨우지 않는다. 그 사이 VERASE(0x7F, Backspace)는 앞 글자를 지우고 VKILL(^U, 0x15)은 줄 전체를, VWERASE(^W)는 단어를 지운다. VEOF(^D, 0x04)는 지금까지를 바로 돌려준다(빈 줄이면 0 = EOF). VLNEXT(^V)는 다음 글자를 문자 그대로 받는다.
  • ISIG: VINTR(^C 0x03) → SIGINT, VQUIT(^\ 0x1C) → SIGQUIT, VSUSP(^Z 0x1A) → SIGTSTP를 tty의 foreground 프로세스 그룹에 보내고, 입력 큐를 비운다(NOFLSH가 아니면).
  • IXON: ^S(0x13, XOFF)를 받으면 우리 쪽 송신을 멈추고, ^Q(0x11, XON)에 재개. 두 바이트는 앱에 전달되지 않는다.
  • ECHO: 받은 바이트를 송신 쪽으로 다시 내보낸다. ECHOCTL이면 제어 문자를 ^M처럼 두 글자로.
  • ISTRIP: 8번째 비트를 지운다(7비트 시절 유물).

GNSS가 보내는 NMEA, u-blox UBX 바이너리, MCU 프로토콜에서는 이 모든 기능이 데이터 손상 장치가 된다.

5.3 예제 6 — 바이너리 0x00~0xFF가 "기본 tty"를 지나면#

무엇을 확인하나: 장치가 0x00~0xFF 256바이트와 \n을 보낼 때, 새로 열린 tty의 기본값(ECHO만 끔)과 raw 모드에서 앱이 받는 바이트를 비교한다.

게스트에서 /h8_bin /dev/ttyAMA1 cooked, 이어서 /h8_bin /dev/ttyAMA1 raw를 실행했다(h8_run.sh bin g_bin.sh nmea 9600 5).

출력에서 볼 것:

  • raw: 257바이트가 그대로 왔다(0x0A가 두 번인 것은 데이터 속 0x0A와 끝의 \n이다). 이것이 바이너리 프로토콜에 필요한 상태다.
  • cooked: 31바이트가 사라졌다. 범인을 차례로 짚으면, 0x03(^C)·0x1A(^Z)·0x1C(^\)가 ISIG 문자라 받는 순간 입력 큐 전체를 비웠다. 마지막 비우기가 0x1C에서 일어났으므로 그 앞의 0x00~0x1C가 통째로 날아갔다(중간의 0x0A 줄바꿈으로 완성됐던 줄까지). 그래서 결과가 0x1D부터 시작한다. 끝 쪽에서는 0x7F(VERASE)가 바로 앞의 0x7E를 지우고 자기도 사라졌다. 남은 0x0A 하나는 마지막 \n이다. 0x11/0x13(XON/XOFF)은 이미 날아간 구간에 있었지만, 살아남았더라도 IXON이 먹었을 것이다.
  • 그리고 read()가 1번에 226바이트를 줬다. canonical 모드는 "줄"을 돌려주기 때문이다.

결론: 바이너리를 다루는 앱은 반드시 raw 모드를 설정한다. "대부분 잘 되는데 가끔 패킷이 깨진다"는 버그는 데이터에 0x03·0x0D·0x11·0x13·0x7F가 섞였을 때만 터지므로 찾기 어렵다. Don이 SSD에서 봤을 법한 "특정 데이터 패턴에서만 나는 버그"의 리눅스판이다.

6.2 read()는 언제 돌아오나 — canonical vs non-canonical#

그림 3 — read()의 반환 조건. canonical이면 "줄"이 단위다. non-canonical(raw)이면 VMIN(최소 바이트 수)과 VTIME(0.1초 단위 타이머)의 조합 네 가지로 갈린다. 오른쪽 아래 경우의 타이머는 "전체 타임아웃"이 아니라 바이트 사이 간격 타이머다.

6.3 예제 7 — 같은 NMEA 스트림을 다섯 가지 설정으로 읽기#

무엇을 확인하나: 같은 GNSS 스트림(9600 baud 속도, 문장 12개 = 840바이트)을 canonical / raw의 VMIN·VTIME 조합 / ECHO 켬으로 읽으며 read()가 매번 무엇을 돌려주는지 시각과 함께 찍는다. 시간 제한은 alarm() + SA_RESTART 없는 SIGALRM으로 블록된 read()를 EINTR로 깨우는 방식이다.

출력에서 볼 것 — 다섯 가지 교훈:

  • A (canonical, 기본 ICRNL): 문장 하나가 read() 두 번이 됐다. NMEA 끝의 \r\n에서 ICRNL이 \r을 \n으로 바꿔 줄 끝이 둘이 됐기 때문이다(71바이트 줄 + 빈 줄 1바이트, 24 reads). 문장 사이 간격 약 75 ms = 71바이트 × 10비트 / 9600 baud(74 ms). 생성기의 페이싱이 보인다.
  • B (raw, VMIN=1): 데이터가 있으면 바로 돌아오므로 read() 경계가 문장 경계와 무관하다. 이번 실행에서는 대부분 문장 단위로 왔지만 마지막 문장이 70 + 2바이트로 잘렸다(같은 프로그램의 이전 실행에서는 n= 16, n= 56처럼 더 잘게 잘렸다 — 19 reads). 생성기가 문장 단위로 몰아 보내서 그나마 이 정도이고, 실제 9600 baud 선로에서는 바이트가 1 ms마다 하나씩 오므로 훨씬 잘게 쪼개진다. raw 모드 앱은 반드시 자기 버퍼에 이어 붙여 줄(프레임)을 다시 조립해야 한다(예제 8).
  • C (VMIN=0, VTIME=5): 데이터가 오면 즉시, 안 오면 0.5초 뒤 0을 반환한다. 840바이트를 12번에 받고, 스트림이 끝난 뒤 3초 창의 남은 시간 동안 0을 3번 돌려받았다(15 reads). "타임아웃이 있는 블로킹 read"가 필요할 때 쓴다(GNSS가 죽었는지 감지).
  • D (VMIN=64, VTIME=2): 64바이트가 모이거나 바이트 사이가 0.2초 이상 비면 반환. 시스템콜 횟수가 가장 적다(12 reads, 평균 70바이트). 고속 스트림에서 CPU를 아끼는 설정이다.
  • E (ECHO 켬): 앱은 똑같이 읽었지만 생성기 로그에 "guest가 852바이트를 되돌려 보냈다"가 찍혔다. 받은 NMEA를 그대로 GNSS 모듈 쪽으로 송신한 것이다. 852 = 840 + 12인 것은 ECHOCTL이 문장마다 \r을 ^M 두 글자로 echo했기 때문이다. 실제 GNSS 모듈은 이 쓰레기를 명령으로 해석하려다 무시하거나, 최악이면 설정이 바뀐다. 포트 카운터 tx:943도 그 증거다(명령 18바이트 × 5회 = 90, echo 852, 합 942. 남는 1바이트의 출처는 확인하지 않았다).

E에는 함정이 하나 더 숨어 있다. E는 A와 같은 "canonical" 설정인데 줄 길이가 71+1이 아니라 72다. termios는 포트에 남는다. B~D가 cfmakeraw로 ICRNL을 꺼 놓았고, E는 ICANON만 다시 켰으므로 \r이 그대로 통과했다. 앱은 열 때마다 필요한 플래그를 전부 명시적으로 설정해야 한다. "이전 프로세스가 무엇을 해 놓았는지"에 기대면 재부팅 직후와 그 후의 동작이 달라진다.

그리고 이 노트를 준비하며 실제로 겪은 일: 생성기를 "명령 없이 바로 송신" 모드로 띄워 놓고 stty -a < /dev/ttyAMA1을 실행했더니, stty가 포트를 여는 순간의 기본 termios(ECHO 켜짐) 때문에 생성기 로그에 bytes sent back by guest after cmd=430이 찍혔다. 읽기 전용으로 상태만 본다고 생각한 명령도 포트를 열면 echo가 동작한다. 실제 장비에서 GNSS·MCU 포트를 열 때는 열자마자 raw로 바꾸거나, 부팅 때 stty -F /dev/ttyX raw -echo를 먼저 걸어 둔다.

6.5 흐름 제어 — RTS/CTS와 XON/XOFF#

  • 하드웨어 흐름 제어(RTS/CTS, CRTSCTS): 받는 쪽이 RTS 선을 내리면 보내는 쪽이 멈춘다. PL011·i.MX·16550 대부분은 하드웨어가 CTS를 보고 바이트 단위로 자동 멈춘다(드라이버가 set_termios에서 auto-RTS/CTS 비트를 켠다). BT 모듈(3 Mbaud급)은 거의 필수다. 보드에 RTS/CTS 선이 실제로 연결돼 있어야 하고, DT에 uart-has-rtscts;(또는 SoC별 속성)가 있어야 드라이버가 핀을 쓴다.
  • 소프트웨어 흐름 제어(XON/XOFF, IXON/IXOFF): 데이터 스트림 안에 0x13(정지)·0x11(재개)을 섞는다. 선이 2가닥뿐일 때 쓰지만 바이너리 데이터와 공존할 수 없다(예제 6에서 본 대로 0x11/0x13이 사라진다).
  • 둘 다 없으면 받는 쪽의 FIFO + ISR 지연 + flip buffer로 버텨야 하고, 넘치면 oe 카운터가 오른다. 9600 baud GNSS는 흐름 제어 없이도 충분하다.

7. 콘솔 UART — console=, earlycon, printk#

7.1 콘솔은 tty와 다른 경로다#

커널 로그(printk)는 tty 계층을 거치지 않는다. 드라이버가 struct console을 등록하면 printk가 그 write 함수로 직접 레지스터에 쓴다(인터럽트 핸들러 안에서도, 패닉 중에도 찍혀야 하니까). PL011의 콘솔은 amba_console(amba-pl011.c 2630행 부근)이고, 6.18에서는 새 nbcon(non-blocking console) 인터페이스인 .write_atomic/.write_thread를 구현한다. 같은 UART가 /dev/ttyAMA0(tty 경로)과 콘솔(printk 경로) 두 얼굴을 갖는 셈이다.

  • console=ttyAMA0,115200 — 커널 인자로 어느 tty 드라이버의 콘솔을 쓸지 정한다. 여러 개 줄 수 있고 마지막 것이 /dev/console이 된다. 없으면 DT /chosen/stdout-path를 쓴다.
  • earlycon=pl011,mmio32,0x9000000 — 드라이버 모델이 뜨기 전(DT 파싱 직후)부터 쓰는 아주 단순한 콘솔. 레지스터 주소만 알면 된다. 부팅 초반 크래시를 볼 때 필수다. 인자 없이 earlycon만 쓰면 stdout-path에서 찾는다. 펌웨어로 치면 "C 런타임 초기화 전에 UART 레지스터에 직접 쓰는 putc"다.

8. serdev — UART 위 장치를 커널 드라이버로#

8.1 직관 — 왜 필요한가#

GNSS·BT·보조 MCU는 UART에 붙지만 "UART"가 아니라 장치다. 이 장치에는 전원 레귤레이터, 리셋·wake GPIO, 클럭, 그리고 "부팅 직후 baud를 바꾸는 절차" 같은 것이 딸려 있다. 옛날 방식은 이랬다.

  • 커널은 /dev/ttyS2만 만든다.
  • 부팅 스크립트가 GPIO로 BT 칩 전원을 켜고(sysfs GPIO), hciattach /dev/ttyS2 bcm43xx 3000000을 실행한다. hciattach가 baud를 바꾸고 펌웨어를 올리고 TIOCSETD로 N_HCI ldisc를 건다.
  • GNSS는 gpsd가 /dev/ttyS2를 열어 파싱한다.

문제: 하드웨어 기술이 DT가 아니라 스크립트에 흩어진다. 부팅 순서 경합, 서스펜드/리줌 때 전원 처리 불가(유저 데몬은 커널 PM을 모른다), 보드마다 다른 스크립트. 그래서 4.11(2017)에 serdev(serial device bus)가 들어왔다. UART 노드 아래 DT 자식 노드로 장치를 기술하면, 커널이 그 UART를 /dev/tty로 내보내는 대신 serdev 컨트롤러로 만들고, 자식 노드와 매칭되는 serdev_device_driver를 probe한다. I2C/SPI 장치와 똑같은 모델이 된다(H5, H7).

그림 4 — 같은 UART 위 장치를 다루는 두 방식. serdev는 UART 드라이버와 TTY core를 그대로 재사용하면서, line discipline과 /dev/tty 노드 자리에 커널 드라이버를 꽂는다.

8.2 어떻게 갈라지나 — 소스 두 군데#

serial core가 포트를 등록할 때(uart_add_one_port → serial_core.c:3157) 이 함수를 부른다.

UART의 DT 노드에 자식이 있으면 serdev 컨트롤러가 등록되고 문자 장치(/dev/ttyAMA1)는 만들지 않는다. 자식이 없으면 -ENODEV가 돌아와 평소처럼 tty 노드를 만든다. 그리고 serdev 컨트롤러(serdev-ttyport.c)는 tty_port의 client_ops를 자기 것으로 바꿔 끼운다. 그래서 flush_to_ldisc가 ldisc 대신 ttyport_receive_buf → 드라이버의 receive_buf를 부른다.

드라이버가 serdev_device_open()을 부르면 ttyport_open(95행)이 tty를 커널 안에서 열고 raw 8비트 + 하드웨어 흐름 제어로 초기화한다.

§6.1의 cfmakeraw와 똑같다 — 커널도 기계 대 기계 통신에는 raw를 쓴다. 단 CRTSCTS가 기본으로 켜진다. RTS/CTS 선이 없는 GNSS라면 드라이버가 serdev_device_set_flow_control(serdev, false)를 불러야 한다(안 그러면 CTS가 안 올라와 송신이 멈출 수 있다).

8.3 예제 11 — 커널에 이미 있는 GNSS 드라이버를 DT로 붙이기#

무엇을 확인하나: 두 번째 PL011 노드 아래에 MediaTek GNSS(GlobalTop PA6H) 자식 노드를 넣으면 /dev/ttyAMA1이 사라지고 /dev/gnss0이 생기는지, 그리고 거기서 NMEA가 읽히는지. 이 커널에는 CONFIG_GNSS=m, CONFIG_GNSS_SERIAL=m, CONFIG_GNSS_MTK_SERIAL=m이 있다.

DT 수정 — 예제 1에서 덤프한 h8_two.dts의 두 번째 PL011에 자식 하나를 넣었다(VM에서 Python으로 문자열 치환 후 dtc로 컴파일).

출력에서 볼 것:

  • /dev/ttyAMA1이 없다. 대신 serdev 버스에 컨트롤러 serial0과 장치 serial0-0이 생겼고, 부팅 로그에 serial serial0: tty port ttyAMA1 registered가 찍혔다. 장치 이름 serial0-0은 "컨트롤러 0번의 0번 자식"이다(DT alias serial1과 번호가 다르니 헷갈리지 말 것).
  • 모듈을 넣자 gnss-mtk가 DT의 compatible = "globaltop,pa6h"로 매칭돼 probe됐다. vcc-supply를 DT에 안 적었으므로 regulator 프레임워크가 dummy regulator를 줬다(H3). 실제 보드라면 GNSS 전원 레귤레이터를 vcc-supply = <&reg_gnss>;로 연결하고, 드라이버가 /dev/gnss0을 열 때 켜고 닫을 때 끈다(gnss-mtk의 mtk_set_active).
  • /dev/gnss0은 NMEA 바이트를 그대로 전달하는 단순 문자 장치다(termios 없음, baud는 DT의 current-speed로 드라이버가 설정). 우리가 쓴 $PMTK220 명령도 그대로 모듈에 전달돼 생성기가 스트림을 시작했다. type=MTK로 프로토콜 종류를 알려 주므로 gpsd 같은 유저 프로그램이 장치를 자동 인식할 수 있다. 이것이 GNSS 서브시스템(drivers/gnss/, 4.19부터)의 전부다: 파싱은 유저 공간에 맡기고, 커널은 전원·baud·장치 수명만 책임진다. 지원 칩: gnss-mtk(MediaTek), gnss-ubx(u-blox neo-6m/neo-8/neo-m8), gnss-sirf, USB GNSS.
  • Terminated는 timeout 2 cat이 2초 후 cat을 죽이며 셸이 찍은 메시지다.

8.5 serdev를 못 쓸 때 — 자기 line discipline#

serdev는 UART가 DT(또는 ACPI)로 기술된 경우에만 쓸 수 있다. USB-UART(ttyUSB0)나 PCI 16550처럼 DT 노드가 없는 포트에 붙은 장치를 커널에서 처리하려면 옛 방식인 ldisc 모듈을 쓴다: struct tty_ldisc_ops에 .receive_buf2(받은 바이트 처리), .open/.close를 채워 tty_register_ldisc()로 등록하고, 유저 프로그램이 포트를 열어 ioctl(fd, TIOCSETD, &num)으로 건다(N_HCI가 이 방식이다. 트리 밖 실험은 번호 N_DEVELOPMENT = 29). 이 노트에서는 serdev가 동작했으므로 ldisc 모듈은 만들지 않았다. 단점은 분명하다: 누군가 유저 공간에서 포트를 열고 TIOCSETD를 걸어 줘야 하고, 그 프로세스가 죽으면 ldisc도 풀린다.

9. RS-485 — 산업용 반이중 버스#

RS-485는 차동 신호 두 가닥(A/B)에 여러 장치가 매달리는 반이중 버스다(모터 드라이버, PLC, Modbus RTU 센서). UART 신호 자체는 같고, 바깥의 트랜시버 칩이 "지금 송신 중"일 때만 드라이버를 켠다(DE 핀). 보통 그 DE 핀을 UART의 RTS 선으로 제어한다. 문제는 타이밍이다: 마지막 바이트의 정지 비트가 선로를 다 빠져나간 직후 DE를 내려야 한다. 너무 빨리 내리면 마지막 바이트가 잘리고, 너무 늦으면 상대의 응답 첫 바이트와 충돌한다. 유저 공간에서 tcdrain() 후 GPIO를 내리는 방식은 스케줄링 지연 때문에 수 ms씩 늦는다.

그래서 serial core가 이것을 커널(드라이버의 TX 완료 인터럽트)에서 처리하는 RS-485 모드를 제공한다.

  • ioctl: TIOCSRS485 / TIOCGRS485, 구조체 struct serial_rs485(include/uapi/linux/serial.h). 플래그 SER_RS485_ENABLED, SER_RS485_RTS_ON_SEND(송신 중 RTS=1), SER_RS485_RTS_AFTER_SEND, SER_RS485_RX_DURING_TX, 그리고 delay_rts_before_send/delay_rts_after_send(ms).
  • DT: linux,rs485-enabled-at-boot-time;, rs485-rts-delay = <before after>;, rs485-rts-active-low;, rs485-term-gpios(종단 저항 스위치) — Documentation/devicetree/bindings/serial/rs485.yaml.
  • 드라이버 쪽: uart_port.rs485_config 콜백과 rs485_supported. PL011은 6.x에서 지원이 들어왔고(pl011_rs485_tx_stop_now 등, amba-pl011.c:1272), 예제 9에서 TIOCSRS485가 받아들여졌다(flags now 0x3 = ENABLED | RTS_ON_SEND). 지원하지 않는 드라이버면 ENOTTY가 돌아온다.

이 노트에서는 RTS 핀의 실제 파형은 볼 수 없었다(QEMU PL011은 RTS 타이밍을 모델링하지 않는다). 실제 보드에서는 로직 분석기로 TX와 RTS를 같이 찍어 정지 비트 끝과 RTS 하강의 간격을 확인한다 — Don이 늘 하던 방식이다.

10. 처리량과 지연 — 에뮬레이터에서 재 본 tty 경로#

10.1 예제 13 — baud를 바꾸면 빨라지나?#

무엇을 확인하나: termios baud를 9600 / 115200 / 921600으로 바꿔 가며 (a) 생성기가 쉬지 않고 256 KB를 쏟아낼 때의 수신 처리량, (b) 1바이트를 보내고 생성기가 되돌려 준 1바이트를 받기까지의 왕복 지연(RTT)을 잰다.

처리량은 baud별로 2회(첫 부팅) + 4회(둘째 부팅) = 6회, RTT는 생성기를 echo 모드로 띄운 부팅에서 baud별 500회 쟀다. 게스트 스크립트는 for b in 9600 115200 921600; do /h8_tput /dev/ttyAMA1 $b tput 262144; sleep 1.5; done(처리량)와 for b in 9600 115200 921600; do /h8_tput /dev/ttyAMA1 $b rtt 500; done(RTT).

(== boot 머리줄은 세 번의 실행을 구분하려고 붙였다. 나머지는 출력 그대로다.)

그림 5 — 수신 처리량(로그 축). 회색은 실제 UART 선로가 낼 수 있는 상한(baud / 10비트), 주황은 QEMU에서 잰 6회의 중앙값(세로선 = 최소~최대). 9600 baud 설정에서도 선로 한계의 약 60배가 나왔다 — QEMU PL011이 baud를 흉내 내지 않기 때문이다.

그림 6 — 1바이트 왕복 지연. 회색은 실제 선로에서 2바이트(가고 오고)가 걸리는 시간, 파랑은 QEMU에서 잰 중앙값. 실제 9600 baud에서는 선로 시간(2.1 ms)이 지배하지만, 115200 이상에서는 소프트웨어 경로(IRQ → 워크큐 → ldisc → 깨우기 → 유저 복귀)가 지배하는 영역으로 넘어간다.

출력에서 볼 것:

  • baud 설정과 처리량 사이에 관계가 없다. 6회 중앙값이 9600에서 약 58 KB/s, 115200에서 약 56 KB/s, 921600에서 약 89 KB/s이고 회차마다 2배 넘게 흔들린다(9600 한 번은 149 KB/s). 이 VM에서 다른 작업 11개가 동시에 돌고 있었으므로 이 흔들림은 호스트 부하다. 결론은 하나: QEMU의 PL011은 IBRD/FBRD를 무시하고 소켓에 들어온 속도대로 받는다. 그래서 에뮬레이터에서 "9600인데 잘 된다"는 실제 보드에서 아무것도 보장하지 않는다.
  • 그래도 이 숫자는 쓸모가 있다. 약 50~100 KB/s는 tty 경로 자체(TCG 에뮬레이션 위의 IRQ·워크큐·ldisc 복사)의 상한에 가깝다. 실제 SoC는 TCG보다 수십 배 빠르므로 tty 경로는 수 Mbaud UART도 따라간다. 실제 병목은 대개 FIFO 깊이 대비 IRQ 지연(→ overrun)이고, 그래서 고속 UART는 DMA(pl011_dma_rx_irq, H9)를 쓴다.
  • RTT 중앙값 약 230 µs, p99 약 3 ms. 실제 921600 baud 선로라면 2바이트 왕복이 22 µs인데, 소프트웨어 경로가 그 10배 이상이다. 실제 보드에서도 tty 경로의 지연은 수십~수백 µs이고, 워크큐 스레드가 늦게 스케줄되면 ms 단위가 된다(p99). UART로 1 ms 이하의 응답이 필요한 제어 루프(예: MCU와 명령·응답)라면 이 꼬리 지연을 측정해 봐야 하고, 필요하면 PREEMPT_RT, 워크큐 우선순위, 또는 프로토콜 쪽에서 응답을 기다리지 않는 설계(파이프라이닝)로 간다. 이 측정은 TCG 위라 절대값은 실제 하드웨어와 다르다.
  • 첫 부팅의 rx:1572864 = 262144 × 6. 바이트 손실 없이 전부 받았다(에뮬레이터는 소켓 역압으로 흐름이 자동 제어되어 overrun이 생기지 않는다 — 실제 하드웨어와 다른 점).

12. Embedded 실무에서 다시 보기#

12.1 센서 키트의 GNSS — i.MX8 + u-blox#

예를 들어 센서 키트가 i.MX8M Plus에 u-blox NEO-M8을 UART2(ttymxc1)로 붙였다고 하자. 선택지는 둘이다.

  • 유저 공간(gpsd 또는 자체 데몬): DT에는 UART만 켜 두고(status = "okay"), 앱이 /dev/ttymxc1을 열어 raw + 9600(또는 설정 후 115200) + CLOCAL으로 설정한다. NMEA만 쓰면 예제 8처럼, UBX 바이너리를 쓰면 반드시 raw. 앱 시작 시 tcflush(fd, TCIFLUSH)로 부팅 중 쌓인 반쪽 문장을 버린다.
  • 커널 GNSS 서브시스템: UART 노드에 gnss { compatible = "u-blox,neo-m8"; vcc-supply = <&reg_gnss>; current-speed = <9600>; };를 넣으면 /dev/gnss0이 생기고, 전원은 드라이버가 open/close에 맞춰 켜고 끈다. gpsd는 /dev/gnss0을 연다. 저전력 장비에서 유리하다.

어느 쪽이든 PPS(1초 펄스) 핀은 UART가 아니라 GPIO → pps-gpio(/dev/pps0)로 따로 받는다. 시간 동기(chrony)에 GNSS를 쓸 때 NMEA 문장의 도착 시각은 tty 지연(예제 13의 꼬리 지연) 때문에 ms 단위로 흔들리므로 정밀 시각은 PPS가 준다.

12.2 BT/Wi-Fi 콤보 칩 — serdev + hci_uart#

Jetson이나 i.MX 보드의 BT는 거의 다 UART(H4, 3~4 Mbaud, RTS/CTS 필수)다. DT에 §8.4의 bluetooth { compatible = "brcm,..."; } 노드를 넣으면 hci_uart의 serdev 드라이버(hci_bcm, hci_qca 등. 이 랩 커널은 CONFIG_BT_HCIUART_SERDEV=y, BCM·QCA·LL·MRVL가 켜져 있다)가 칩 전원을 켜고, 기본 baud로 펌웨어를 올리고, 고속으로 바꾼 뒤 hci0을 등록한다. hciattach나 btattach를 부팅 스크립트에서 부르고 있다면 레거시다. "BT가 가끔 안 올라온다"의 단골 원인: RTS/CTS 미배선인데 uart-has-rtscts를 넣었거나 그 반대, UART 클럭이 3 Mbaud를 못 만듦(§3.3), 전원 시퀀스 타이밍.

12.3 보조 MCU (모터·전원 관리)와의 프로토콜#

로봇에서는 Cortex-M MCU가 모터·배터리를 맡고 Linux SoC와 UART로 통신하는 구조가 흔하다. 체크리스트:

  • raw 모드, 그리고 프레이밍: 길이 필드 + CRC, 또는 COBS/SLIP처럼 구분 바이트를 쓰는 인코딩. "줄바꿈으로 구분"은 바이너리에서 깨진다.
  • 수신은 poll()/epoll(A5)로 기다리고 VMIN=0·VTIME=0 + 논블로킹 read로 있는 만큼 가져와 자기 버퍼에서 프레임을 찾는다.
  • 응답 시간 요구가 있으면 꼬리 지연을 잰다(예제 13 방식). 필요하면 커널 serdev 드라이버로 내려서 응답 처리를 워크큐 안에서 끝낸다.
  • MCU 펌웨어 업데이트 경로(부트로더가 다른 baud·패리티를 쓰는 경우, 예: STM32 시스템 부트로더는 8E1)를 termios로 바꿀 수 있게 설계한다.

12.4 RS-485 모터 드라이버 / Modbus RTU#

산업용 액추에이터는 RS-485 Modbus RTU를 쓴다. DT에 linux,rs485-enabled-at-boot-time;과 rs485-rts-delay를 넣거나 앱에서 TIOCSRS485를 설정한다(§9). Modbus RTU는 프레임 사이 3.5문자 무음 구간으로 프레임을 구분하므로 VTIME은 너무 거칠다(0.1초 단위). 앱은 poll() 타임아웃이나 타이머로 직접 구간을 잰다. libmodbus가 이 처리를 해 준다.

14. 면접에서 이렇게 말한다#

Q. Walk me through the Linux serial/TTY stack. What happens between the UART hardware and an application's read()?

A. 다섯 층이다. 맨 아래 UART 드라이버가 uart_port와 uart_ops로 하드웨어를 다루고, serial core가 모든 UART에 공통인 TX kfifo·termios·모뎀 선을 처리한다. 그 위 TTY core가 tty_port의 flip buffer로 RX를 받고, line discipline(기본 N_TTY)이 줄 편집·echo·신호를 처리한 뒤 앱의 read()에 넘긴다. RX는 IRQ에서 flip buffer에 넣고 워크큐에서 ldisc로 올리는 top/bottom half 구조다.

There are roughly five layers. At the bottom, the UART driver fills in a uart_port and uart_ops — startup, set_termios, start_tx and so on. The serial core sits on top of every UART driver and handles the TX ring buffer, which is a kfifo since 6.10, termios translation, modem lines and the console. Above that is the TTY core: tty_port owns the RX flip buffer, tty_struct represents the open session. Then the line discipline, normally N_TTY, does canonical line editing, echo and signal characters before data reaches read(). On receive, the ISR pushes bytes into the flip buffer and calls tty_flip_buffer_push, and a kworker runs flush_to_ldisc to hand the data to the line discipline in process context. I've actually traced that with kprobes: the push runs in hardirq context, the ldisc call runs in a kworker.

꼬리 질문: "Why is the receive path split into IRQ and workqueue?" → ISR을 짧게 유지하고, ldisc 처리(echo 송신, 신호, 잠든 reader 깨우기, mutex)는 잘 수 있는 컨텍스트에서 하기 위해서다.

Q. Why do embedded applications need to put a serial port into raw mode?

A. 기본 termios는 사람 터미널용이라 CR을 LF로 바꾸고(ICRNL), ^C·^Z·^\를 신호로 처리하며 입력 큐를 비우고(ISIG), 0x11/0x13을 흐름 제어로 먹고(IXON), 받은 걸 echo한다. 바이너리 프로토콜에서는 이게 데이터 손상이다. 실험에서 0x00~0xFF를 기본 설정으로 받았더니 257바이트 중 226바이트만 왔고 raw로는 전부 왔다.

The default termios settings are designed for a human at a terminal. ICRNL turns carriage returns into newlines, ISIG turns 0x03, 0x1A and 0x1C into signals and flushes the input queue, IXON swallows 0x11 and 0x13 as flow control, ECHO sends everything back to the device, and canonical mode holds data until a newline. For a GNSS module or an MCU protocol that's silent data corruption that only shows up with certain byte values. When I sent all 256 byte values through a default-configured port, 31 bytes disappeared; in raw mode all 257 arrived. So I always call cfmakeraw, set CLOCAL and CREAD explicitly, set the baud rate, and then read the settings back to verify.

Q. What do VMIN and VTIME do?

A. non-canonical 모드에서 read()가 언제 돌아올지 정한다. 0/0은 폴링, MIN>0/TIME=0은 MIN 바이트까지 블록, MIN=0/TIME>0은 전체 타임아웃(0.1초 단위), 둘 다 양수면 첫 바이트 이후의 바이트 간 타이머다.

They only matter in non-canonical mode. VMIN is the minimum byte count and VTIME is a timer in tenths of a second. Zero and zero means poll — return whatever is there, possibly zero. VMIN greater than zero with VTIME zero blocks until that many bytes arrive. VMIN zero with VTIME positive is an overall timeout: return as soon as one byte arrives, or zero after the timeout — handy for detecting a dead GNSS. Both positive means an inter-byte timer that starts after the first byte. Either way, read boundaries don't match message boundaries, so the application must reassemble frames itself.

Q. What is serdev, and why is it better than running hciattach or a user-space daemon?

A. UART에 붙은 장치(BT·GNSS·MCU)를 DT의 UART 자식 노드로 기술하고 serdev_device_driver로 커널 드라이버를 붙이는 버스다. 전원·GPIO·baud 절차를 드라이버가 PM과 함께 관리하고, 보드 정보가 스크립트가 아니라 DT에 있게 된다. 자식 노드가 있으면 serial core가 tty 노드 대신 serdev 컨트롤러를 등록하고, 데이터는 ldisc 대신 드라이버의 receive_buf로 간다.

serdev is a bus for devices that sit behind a UART. You describe the device as a child node of the UART in the device tree, and a serdev_device_driver binds to it like an I2C or SPI client driver. When the serial core registers a port that has a child node, it creates a serdev controller instead of a /dev/tty node, and incoming data goes from flush_to_ldisc straight to the driver's receive_buf callback — no line discipline. The driver opens the port in the kernel, sets the baud rate and flow control, and owns the regulators, reset and wake GPIOs, so power sequencing and suspend/resume are handled properly. With hciattach, that knowledge lived in boot scripts, raced with other services, and the kernel's power management couldn't see it. I wrote a small serdev GNSS driver bound to a second PL011 in QEMU to see it end to end.

꼬리 질문: "What default does serdev apply when it opens the port?" → raw 8N1에 CRTSCTS를 켠다. RTS/CTS 선이 없는 장치는 드라이버가 흐름 제어를 꺼야 한다.

Q. How would you debug "the GNSS data is occasionally corrupted"?

A. 숫자부터 본다: /proc/tty/driver/<drv>나 TIOCGICOUNT의 fe/pe/oe. framing이면 baud·클럭·배선·노이즈, overrun이면 IRQ 지연·흐름 제어·DMA, 둘 다 0이면 소프트웨어 — termios(raw 여부, echo)와 앱의 프레임 재조립을 본다. 그 다음 로직 분석기로 선로를 찍어 기준 데이터를 확보한다.

First I'd separate hardware from software using the counters in /proc/tty/driver or TIOCGICOUNT. Framing errors point to baud mismatch, clock error or signal integrity — I'd compute the divisor error and put a logic analyzer on the line. Overruns point to interrupt latency or missing flow control, and the fix is RTS/CTS, DMA or tuning IRQ thread priority. If the counters are clean, it's software: check that the app set raw mode and disabled echo, that it doesn't assume one read equals one sentence, and that it validates checksums and resyncs on the start character.

Q. How does the kernel console differ from a TTY, and what is earlycon?

A. printk는 tty 계층을 거치지 않고 드라이버가 등록한 struct console의 write로 직접 레지스터에 쓴다. console=가 어느 콘솔을 쓸지 정한다. earlycon은 드라이버 모델 이전부터 레지스터 주소만으로 동작하는 부트 콘솔로, 진짜 콘솔이 등록되면 꺼진다.

Kernel messages don't go through the TTY layer. A serial driver registers a struct console, and printk calls its write function directly, so it works from interrupt context and during a panic. console= on the command line picks which console devices are used, and the last one becomes /dev/console. earlycon is a minimal boot console that only needs the register address, so it works right after the device tree is parsed, long before the real driver probes. In QEMU I saw the earlycon at time zero and the switch to the real ttyAMA0 console at about 0.45 seconds — any crash before that is invisible without earlycon.

Q. How does RS-485 direction control work in Linux?

A. 트랜시버의 DE를 보통 RTS로 제어하고, serial core의 RS-485 모드(TIOCSRS485, DT linux,rs485-enabled-at-boot-time, rs485-rts-delay)가 드라이버의 TX 완료 시점에 RTS를 내린다. 유저 공간에서 tcdrain 후 GPIO를 내리면 스케줄링 지연 때문에 응답과 충돌한다.

RS-485 is half-duplex, so the transceiver's driver-enable has to be asserted only while we transmit, usually wired to RTS. The serial core has an RS-485 mode — set with the TIOCSRS485 ioctl or the device-tree properties — where the UART driver raises RTS before sending and drops it when the last stop bit has left the shifter, with optional delays. Doing it from user space with tcdrain and a GPIO adds scheduling latency and you collide with the slave's reply. I'd verify the timing with a logic analyzer on TX and RTS.

17. 요약 & 체크리스트#

Linux에서 UART는 UART 드라이버(uart_port/uart_ops) → serial core(TX kfifo, termios, 콘솔) → TTY core(tty_port의 flip buffer, tty_struct) → line discipline(N_TTY) → /dev/ttyXXX의 다섯 층이다. RX는 IRQ에서 flip buffer에 넣고 워크큐(kworker)에서 ldisc로 올리며, 이 노트에서는 kprobe로 그 두 컨텍스트를 실제로 찍었다. 기본 termios는 사람 터미널용이라 바이너리·기계 프로토콜에서는 ICRNL·ISIG·IXON·ECHO가 데이터를 바꾸거나 먹거나 되돌려 보낸다. 그래서 앱은 cfmakeraw + CLOCAL/CREAD + baud를 전부 명시하고, read() 경계와 무관하게 프레임을 재조립하며, 설정을 다시 읽어 확인한다. UART 뒤의 장치(GNSS·BT·MCU)는 DT 자식 노드 + serdev 드라이버로 커널이 전원·baud·수명을 관리하는 것이 현재의 표준이고, 그러면 tty 노드 대신 serdev 컨트롤러가 생긴다. 콘솔은 tty와 별개의 printk 경로이고 earlycon이 부팅 초반을 책임진다. 에뮬레이터는 baud를 흉내 내지 않으므로 타이밍·처리량 결론은 실제 보드와 로직 분석기로 확인한다.
