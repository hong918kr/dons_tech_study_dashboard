G5. ioctl과 mmap — 유저 인터페이스 설계, remap_pfn_range, 그리고 sysfs가 나은 경우

106분 읽기1032줄44개 절

이 노트를 다 읽으면: 한 드라이버에서 "제어는 어디로, 데이터는 어디로"를 read/write · ioctl · sysfs · mmap · netlink 중에 근거를 대고 고를 수 있다 · 수년간 32/64비트 앱과 따로 업데이트돼도 안 깨지는 ioctl UAPI 헤더(고정 폭 타입 · 예약 비트 0 검사 · size 필드 · copy_struct_from_user 확장 패턴)를 설계하고 compat_ptr_ioctl로 32비트 앱을 받을 수 있다 · 센서 샘플 링버퍼를 .mmap + remap_pfn_range/vm_insert_pages/.fault로 유저에 zero-copy 공유하고, 크기·offset 검사를 빼면 왜 커널 메모리가 새는지 직접 보고 고칠 수 있다 왜 필요한가: "How would you expose this device to user space?"와 "Why is a bad mmap handler a security hole?"는 드라이버 면접 단골이고, V4L2 카메라·IMU FIFO·DMA 링을 Linux SoC에 올릴 때 매 bring-up마다 직접 짜는 코드다 Don 기준 난이도: 링버퍼·DMA·레지스터 매핑·캐시 속성은 SSD 펌웨어에서 이미 했다 / 새로 배울 부분은 그걸 "유저에게 안전하게 노출"하는 커널 쪽 약속 — VMA·vm_page_prot·remap_pfn_range·vm_operations_struct, 그리고 인터페이스 선택의 관례 선행 노트: A5(유저 관점 mmap·VMA·page fault), E6(ioctl 번호 인코딩·copy_to/from_user·errno·compat 진입 경로), F5(READ_ONCE/smp_store_release 순서), F9(페이지 할당·split_page), F10(dma_alloc_coherent·reserved-memory) — G4(char device file_operations), G6(poll), G8(sysfs), H9(dma-buf), UIO로 이어진다

0. 큰 그림 — 이게 왜 필요한가#

드라이버 하나를 열면 유저에게 보여 줄 "구멍"이 여러 개다. IMU(sensorkit) 하나를 예로 들면 유저 공간이 하는 일은 네 종류다.

  • 제어/설정: "ODR(출력 데이터율)을 1 kHz로, 레인지를 ±8 g로, accel만 켜라" — 가끔, 작은 데이터, 원자적으로.
  • 상태 조회: "지금 몇 Hz로 돌고 있나, 칩 ID는, 드롭된 샘플 수는" — 사람이 cat으로 보고 싶을 때도 있다.
  • 대량 데이터: 초당 수천~수백만 개의 샘플 — 빠르고, 복사 비용이 아까운.
  • 비동기 통지: "FIFO가 찼다", "워터마크 넘었다" — 이벤트.

이걸 전부 read()/write() 하나에 욱여넣으면 "두 번째 바이트가 3이면 설정, 아니면 데이터" 같은 괴물이 된다. Linux의 관례는 각 구멍에 맞는 인터페이스를 따로 고르는 것이다: 제어는 ioctl(또는 sysfs), 상태는 sysfs, 대량 데이터는 read()나 mmap 링, 이벤트는 poll/fasync. 이 노트는 그중 ioctl 설계와 mmap을 깊게 판다.

Don의 bare-metal 비유로 깔면 쉽다. SSD 펌웨어에서 호스트(NVMe)가 컨트롤러에게 말을 거는 통로는 두 가지였다: admin/IO 커맨드(SQE — 작고, 구조가 정해진 명령, 가끔)와 data DMA(호스트 메모리와 NAND 버퍼 사이 대량 전송, PRP/SGL로 주소만 넘기고 복사는 엔진이). ioctl이 바로 SQE다 — 번호(opcode) + 고정 구조체. mmap 링이 바로 data DMA다 — 유저와 커널이 같은 물리 페이지를 보게 해 놓고, 복사 없이 포인터만 오간다. "커맨드 구조체를 호스트/디바이스 양쪽이 같은 레이아웃으로 봐야 한다"는 NVMe ABI 문제가 여기서는 "32비트 앱과 64비트 커널이 같은 ioctl 구조체를 봐야 한다"는 compat 문제로 돌아온다.

그림 1 — 한 장치, 네 통로. 작고 가끔인 제어는 ioctl/sysfs로 복사해 넘기고, 초당 수천 개의 샘플은 mmap 링으로 복사 없이 공유한다. 이 노트는 가운데 위(ioctl)와 맨 아래(mmap)를 다룬다.

이 노트의 실습 커널 버전은 uname -r 기준 6.18.55(공용 랩, QEMU virt/Cortex-A57)다. 유저 쪽 비유는 A5, ioctl 번호의 비트 구조와 compat 진입 경로는 E6에서 이미 했으니 반복하지 않고 참조한다. 여기서는 "번호를 어떻게 인코딩하나"가 아니라 "어떤 인터페이스를 고르고, UAPI를 어떻게 설계하고, mmap을 어떻게 안전하게 구현하나"를 본다.

1. 인터페이스 선택 — read/write · ioctl · sysfs · mmap · netlink · configfs#

1.1 직관 — "모양 · 빈도 · 크기 · 누가 보나"로 가른다#

새 장치를 올릴 때 제일 먼저 하는 결정이다. 네 가지 축으로 생각한다.

  • 데이터 모양: 바이트 스트림인가(오디오·시리얼), 정해진 구조체인가(설정 블록), 그냥 숫자 하나인가(온도).
  • 빈도·크기: 초당 한 번 몇 바이트인가, 초당 수만 번 수 MB인가.
  • 누가 조작하나: 사람이 셸에서 cat/echo 하나, 전용 데몬이 바이너리로 하나.
  • 원자성·트랜잭션: 여러 값을 "한 번에" 바꿔야 하나(ODR+레인지+플래그), 하나씩 바꿔도 되나.

1.4 "ioctl은 최후의 수단" — 커뮤니티 관례#

커널 커뮤니티는 ioctl을 좋아하지 않는다. 이유: (1) 번호·구조체가 드라이버마다 제각각이라 툴로 자동 검사가 안 되고, (2) 32/64비트 호환을 손으로 챙겨야 하고, (3) 한 번 UAPI로 공개하면 영원히 깨면 안 된다. 그래서 순서가 이렇다.

  1. 맞는 서브시스템이 있으면 그걸 쓴다(IIO·V4L2·hwmon·input·gpiod). 유저 ABI를 새로 발명하지 않는다.
  2. 사람이 만지는 단일 튜닝 값은 sysfs(G8).
  3. 디버그용 덤프는 debugfs(G8) — ABI 보장 없음.
  4. 위로 안 되는 여러 값 원자 설정·트랜잭션·START/STOP만 ioctl.
  5. 대량 데이터는 mmap 또는 dma-buf(H9).

"그냥 ioctl로 다 하면 안 되나?" — 된다. 하지만 면접에서 "왜 sysfs가 아니고 ioctl인가"에 답을 못 하면 설계를 안 해 본 티가 난다. 기준은 원자성과 데이터 크기다: ODR·레인지·플래그를 "셋 다 같이, 스트리밍 멈춘 상태에서" 바꿔야 하면 ioctl 한 방이 맞다. 각각을 따로 echo 하는 sysfs면 중간 상태(새 ODR + 옛 레인지)가 잠깐 생긴다.

2. 안정적인 UAPI 헤더 설계 — 고정 폭 타입 · 예약 필드 · size · 확장#

2.1 직관 — "이 헤더는 10년 뒤 32비트 레거시 앱도 include 한다"#

UAPI(user API) 헤더는 유저와 커널이 같은 파일을 include하는 계약서다. 실제 드라이버면 include/uapi/linux/에 들어가고, 한 번 릴리스되면 영원히 깨면 안 된다(Linus의 "we do not break userspace"). E6 §6에서 ioctl 번호 비트 구조와 패딩/32·64비트 함정은 이미 다뤘다. 여기서는 그 위에 버전·크기·확장을 얹는다.

규칙 다섯 개:

  • 고정 폭 타입만: __u32/__u64/__s16. long·int·size_t·enum·포인터 금지(크기가 ABI마다 다르다). 유저 포인터는 __u64로 싣는다.
  • 명시적 패딩과 정렬: 구멍이 없게 큰 필드부터, 또는 reserved 필드를 둔다. E6 §6.5의 pahole로 구멍을 확인한다.
  • 예약 비트/필드는 0 강제: 지금 안 쓰는 플래그 비트와 reserved 필드는 커널이 "0이 아니면 -EINVAL"로 거절한다. 그래야 나중에 그 비트에 의미를 줄 때, 옛 커널이 모르고 통과시킨 쓰레기 값과 구분된다.
  • size/version 필드로 확장: 구조체 맨 뒤에만 필드를 덧붙이고, 커널은 copy_struct_from_user로 "유저가 보낸 크기"를 받아 호환을 맞춘다(§2.3).
  • magic + 번호 등록: type 문자는 Documentation/userspace-api/ioctl/ioctl-number.rst에서 안 겹치게 고른다.

2.2 g5_sensorkit.h — sensorkit IMU의 UAPI#

이게 이 노트의 모든 예제가 유저·커널 양쪽에서 include하는 헤더다. 실제 include/uapi/linux/에 둘 모양으로 짰다.

여기서 핵심은 reserved0/1/2와 flags의 "안 쓰는 비트"다. odr_hz를 __u32로, range_g를 __u16로 두고 그 뒤에 reserved0 __u16을 박아 4바이트 경계를 맞췄다 — 그래야 arm64/arm32/i386에서 구멍이 안 생긴다(E6 §6.5가 pahole로 증명한 그 문제). 유저 포인터는 이 구조체에 안 넣었다. 넣어야 하면 __u64로 싣고 u64_to_user_ptr()로 받는다(E6 §6.2 e6_cfg.name_ptr 패턴).

3. ioctl 핸들러 설계 — compat · ENOTTY · 권한 · START/STOP#

3.1 unlocked_ioctl vs compat_ioctl — compat_ptr_ioctl#

file_operations에는 ioctl이 두 개다. .unlocked_ioctl은 64비트(native) 앱용, .compat_ioctl은 32비트 앱이 64비트 커널을 부를 때용. E6 §6.6에서 진입 경로(el0t_32_sync → do_el0_svc_compat → __arm64_compat_sys_ioctl)를 이미 봤다. 핵심은 32비트 앱의 arg는 32비트 포인터라 상위 비트가 비어 있고, 커널은 이걸 compat_ptr()로 64비트 포인터로 넓혀야 한다는 것.

우리 UAPI는 구조체 안에 포인터도 long도 없게(전부 __u32/__u64) 설계했으므로, 변환 코드가 필요 없다. 그럴 때 쓰는 커널 제공 헬퍼가 compat_ptr_ioctl이다. 랩 소스에서 확인:

3.2 모르는 명령은 -ENOTTY, 권한 검사는 capable()#

  • 알 수 없는 cmd → -ENOTTY("not a typewriter" — 역사적 이름). switch의 default에서 돌려준다. 커널이 내부적으로 -ENOIOCTLCMD를 쓰면 VFS가 -ENOTTY로 바꿔 유저에게 준다(E6 §5.3, fs/ioctl.c의 vfs_ioctl). 유저가 isatty()나 다른 드라이버의 ioctl을 잘못 부르면 여기로 떨어진다.
  • 특권 명령 → capable(CAP_SYS_ADMIN). "공장 캘리브레이션 쓰기"처럼 장치를 망가뜨릴 수 있는 명령은 권한을 본다. capable()은 플래그 복사·데이터 접근 전에 호출한다 — 권한 없는 호출이 side effect를 남기면 안 된다.
  • 파일 모드 검사: _IOW(유저→커널 쓰기)인데 O_RDONLY로 연 fd면 거절한다. 위 g5_set_config가 f->f_mode & FMODE_WRITE로 본다.

3.3 START/STOP — 스트리밍 상태 기계#

ioctl이 "트랜잭션"을 하는 전형이 START/STOP다. IMU를 켜고 끄는 건 여러 내부 상태(hrtimer, ODR, base 인덱스)를 원자적으로 바꾸는 일이라 sysfs 한 값으로는 부족하다.

STOP은 멱등(이미 멈춰 있어도 0)으로 뒀다. 설정 변경은 스트리밍 중이면 -EBUSY로 막는다("멈추고 바꿔라"). 이게 bare-metal의 "레지스터 쓰기 전에 엔진 disable" 패턴 그대로다.

4. mmap — 왜, 그리고 .mmap 핸들러 안에서 하는 일#

4.1 왜 mmap인가 — zero-copy 링/프레임#

read()로 샘플을 받으면 커널 버퍼 → 유저 버퍼로 매번 복사한다(E6의 copy_to_user). 초당 수백만 샘플이면 이 복사와 syscall 자체가 비용이다. mmap은 유저와 커널이 같은 물리 페이지를 보게 해서 복사를 없앤다 — 유저는 그냥 포인터로 읽는다. 쓰이는 곳:

  • V4L2 카메라: VIDIOC_REQBUFS + mmap(fd, offset=버퍼쿠키) — A5 §12.5에서 유저 쪽을 봤다. 커널 쪽 .mmap이 이 노트다.
  • DMA 링/프레임버퍼: 네트워크 RX 링, GPU/디스플레이 프레임버퍼.
  • IMU FIFO: 하드웨어 FIFO를 미러링한 링을 유저에 노출.

Don의 비유: NVMe의 PRP가 "호스트 메모리 물리 주소를 디바이스에 알려 주고 복사는 DMA 엔진이" 였던 것처럼, mmap은 "커널 버퍼의 물리 페이지를 유저 page table에 꽂아 주고 접근은 유저가 직접".

4.2 .mmap이 받는 것 — VMA#

유저의 mmap(addr, len, prot, flags, fd, offset)은 커널에서 ksys_mmap_pgoff → vm_mmap_pgoff → do_mmap → mmap_region을 거쳐(A5 §11, F11) VMA(struct vm_area_struct)를 하나 만들고, 그 fd가 장치 파일이면 드라이버의 .mmap(file, vma)을 부른다. 랩 소스에서 호출 지점:

6.x 최신 커널은 .mmap 외에 .mmap_prepare(VMA가 완성되기 전 vm_area_desc로 받는 새 훅)도 생겼다 — 둘은 상호 배타(can_mmap_file이 둘 다 있으면 WARN). 아직 대부분의 드라이버는 .mmap을 쓰므로 이 노트도 .mmap으로 간다.

.mmap이 받은 VMA에서 드라이버가 쓰는 필드:

  • vma->vm_start, vma->vm_end: 유저가 받은 주소 범위. vma_pages(vma) = 페이지 수.
  • vma->vm_pgoff: 유저가 준 offset을 페이지 단위로. 파일 offset이 아니라 "어느 버퍼/무슨 방식"을 고르는 쿠키로 쓴다(A5 §12.5의 V4L2처럼).
  • vma->vm_page_prot: PTE에 들어갈 캐시·권한 속성. MMIO면 여기를 pgprot_noncached로 바꾼다.
  • vma->vm_flags: VMA 종류 플래그. remap_pfn_range가 VM_IO|VM_PFNMAP|VM_DONTEXPAND|VM_DONTDUMP를 세운다.

5.4 숫자 읽는 법 — "zero-copy가 항상 이긴다"는 틀렸다#

이 측정의 교훈이 면접에서 그대로 통한다.

  • 낮은~중간 ODR(≤400k): 둘 다 손실 0. CPU는 read()가 오히려 낮다(ns/sample 8.1 vs 23.5). 왜? 이 장치의 샘플은 32 B라 복사가 싸고, mmap 쪽은 1 ms마다 깨서 head를 폴링하는 폴링 오버헤드가 있다. read()는 커널이 깨워 줄 때(wake queue)만 돈다.
  • 높은 ODR(≥1M): mmap 폴링은 1 ms 간격 × 1920슬롯으로는 다 못 퍼내서 덮어쓰기 손실이 난다(2M에서 mmap 손실 21%, torn=덮어쓰는 중 읽은 슬롯). read()는 블로킹이라 커널 페이스에 맞춰 깨서 손실이 적다.
  • 그래서 mmap의 진짜 이점은 "복사 제거"가 아니라 "큰 프레임"이다. 4 MB 카메라 프레임을 read()로 받으면 4 MB 복사가 매 프레임 생기지만, mmap이면 0. 32 B 샘플에선 복사가 애초에 싸서 이점이 안 보인다. mmap 링은 또 poll()과 묶어 폴링 대신 블로킹 대기로 써야 CPU가 안 샌다(G6).

정직한 결론: mmap은 "큰 버퍼 + 이벤트 통지(poll)"와 함께 쓸 때 이긴다. 작은 레코드를 바쁜 폴링으로 긁으면 read()보다 나쁠 수 있다. 측정 없이 "mmap이 빠르다"고 말하면 안 된다 — Don의 측정 기반 디버깅 습관이 여기서 맞다. (TCG 에뮬레이션 값이라 절대 수치가 아니라 경향만 본다.)

6.2 안전한 .mmap 체크리스트#

  • size = vm_end - vm_start가 버퍼 크기 이하인지(> G5_RING_BYTES → -EINVAL).
  • vm_pgoff(offset)가 유효 범위인지 — 유저가 임의 offset으로 버퍼 밖을 가리키지 못하게.
  • 쓰기가 필요 없으면 VM_WRITE 거절 + vm_flags_clear(VM_MAYWRITE).
  • MMIO를 매핑할 땐 pgprot_noncached, 그리고 매핑할 레지스터 영역만 — 옆 장치 레지스터가 같은 페이지에 있으면 통째로 노출된다.
  • remap_pfn_range에 넘기는 pfn이 내가 소유한 메모리인지. virt_to_phys/page_to_pfn을 유저가 준 값으로 계산하지 않는다.

6.3 왜 UIO가 존재하나 (미리보기)#

레지스터 전체를 유저에 매핑해 "유저 공간 드라이버"를 짜고 싶을 때가 있다(산업 I/O, 고속 거래). 그걸 안전하게 하라고 UIO(Userspace I/O) 프레임워크가 있다 — /dev/uioN를 mmap하면 정해진 MMIO 영역만 노출하고, 인터럽트는 read()로 받는다. 랩 커널엔 CONFIG_UIO가 꺼져 있다(# CONFIG_UIO is not set). 직접 .mmap으로 MMIO를 노출하는 것보다 UIO가 영역 경계·인터럽트 전달을 표준화해 안전하다. /dev/mem은 CONFIG_STRICT_DEVMEM=y라 RAM 영역 접근이 막혀 있어 범용 통로가 못 된다. 자세한 건 UIO 노트에서.

8. Embedded 실무에서 다시 보기#

8.1 IMU FIFO를 mmap 링으로 (IIO가 하는 일)#

현장에서 IMU는 보통 IIO 서브시스템으로 노출한다. IIO의 버퍼가 바로 이 노트의 mmap 링이다 — /dev/iio:deviceN를 열고 read() 또는 mmap으로 샘플 블록을 받고, 워터마크 인터럽트를 poll()로 기다린다. 우리가 손으로 짠 head/tail·remap_pfn_range·배리어를 IIO가 내부에서 한다. 직접 char device로 짤 일은 드물지만, IIO 드라이버를 디버깅하거나 성능 튜닝할 때 이 내부를 알아야 한다.

8.2 카메라 프레임 — V4L2 MMAP과 dma-buf#

Jetson/i.MX8 카메라는 VIDIOC_REQBUFS로 버퍼를 잡고 mmap(fd, offset=버퍼쿠키)로 각 프레임을 유저에 노출한다(A5 §12.5). 커널 쪽 .mmap이 dma_mmap_coherent(DMA 버퍼라 캐시 속성 일치 필수, F10)로 매핑한다. 4 MB 프레임을 read()로 복사하면 프레임당 4 MB 복사 + 지연 — 여기서 §5.4의 "큰 버퍼라 mmap이 확실히 이긴다"가 성립한다. GPU/NPU로 넘길 땐 VIDIOC_EXPBUF로 dma-buf fd를 받아 복사 없이 공유한다(H9).

8.3 캘리브레이션 ioctl — 버전·예약·권한#

E6 §9.2에서 본 캘리브레이션 업로드가 여기서 G5_IOC_FACTORY_CALIB다. 설계 그대로: CAP_SYS_ADMIN 검사 먼저 → reserved[] 0 검사 → 길이 상한을 memdup_user 전에. 몇 년간 앱과 커널이 따로 업데이트되니 copy_struct_from_user로 뒤에만 확장한다.

8.4 "개발 보드에선 됐는데 양산 SoC에서 유저가 커널을 덮어썼다"#

§6의 크기 검사 누락이 현장에서 나는 전형이다. 개발 중엔 유저가 정확한 크기로만 mmap해서 안 터지다가, 악의적(또는 버그 있는) 앱이 큰 크기로 매핑하면 커널 메모리가 샌다. 보안 리뷰에서 .mmap 핸들러의 크기·offset 검사는 1순위 점검 항목이다.

10. 면접에서 이렇게 말한다#

Q. When would you use ioctl versus sysfs versus a read/write interface for a device?

A. 데이터 모양·빈도·원자성으로 가른다. 순차 스트림은 read/write, 사람이 셸로 만지는 단일 튜닝 값은 sysfs 한 파일, 여러 값을 원자적으로 바꾸거나 START/STOP 같은 트랜잭션은 ioctl, 대량 고속 데이터는 mmap. 가능하면 ioctl을 새로 만들지 말고 IIO·V4L2 같은 서브시스템을 쓴다.

I pick by data shape and atomicity. A byte stream is read/write. A single human-tunable value is one sysfs file. Several fields that must change together, or a start/stop transaction, is an ioctl. Bulk high-rate data is mmap. And before inventing an ioctl I check whether a subsystem like IIO or V4L2 already defines the ABI.

꼬리 질문: Why does the community discourage new ioctls? → 번호·구조체가 드라이버마다 제각각이라 툴 검사가 안 되고, 32/64 compat을 손으로 챙겨야 하고, 한 번 공개하면 영원히 못 깬다.

Q. How do you design an ioctl struct that won't break when a 32-bit app talks to a 64-bit kernel?

A. 고정 폭 타입(__u32/__u64)만 쓰고, long·포인터·enum·size_t는 금지, 유저 포인터는 __u64로 싣는다. 명시적 패딩으로 구멍을 없애 모든 ABI에서 같은 레이아웃·같은 크기가 되게 하고, pahole로 확인한다. 그러면 .compat_ioctl = compat_ptr_ioctl 하나로 32비트 앱을 받는다.

Fixed-width types only, no long or pointers or enums in the struct, user pointers carried as __u64. Explicit padding so there are no holes and the layout is identical on arm64, arm32 and i386 — I verify with pahole. Then compat_ptr_ioctl handles 32-bit callers because the struct is ABI-independent.

꼬리 질문: What if the struct must contain a pointer or a timespec? → compat_ptr_ioctl로는 안 되고 .compat_ioctl에 직접 변환 함수를 짠다.

Q. How do you make an ioctl ABI extensible?

A. 새 필드는 반드시 구조체 맨 뒤에만 덧붙이고, "0 = 옛 동작"이 되게 의미를 준다. 커널은 copy_struct_from_user(dst, ksize, src, usize)로 유저가 보낸 크기를 받아, 작으면 나머지를 0으로 채우고 크면 꼬리가 0인지 검사해 아니면 -E2BIG. ioctl이면 번호의 size 필드(_IOC_SIZE)가 usize를 준다.

New fields only at the tail, with zero meaning the old behavior. The kernel uses copy_struct_from_user with the user-supplied size: it zero-fills when the user struct is smaller and rejects with E2BIG when the extra tail bytes aren't zero. For ioctls the size lives in the command number, read with _IOC_SIZE.

Q. What does a driver's mmap handler actually do, and what are the ways to populate the mapping?

A. VMA를 받아 크기·offset을 검사하고 캐시 속성(vm_page_prot)을 정한 뒤 PTE를 채운다. page 할당 버퍼나 MMIO는 remap_pfn_range(pfn 넘김, VMA에 VM_IO/VM_PFNMAP), struct page 있는 RAM은 vm_insert_pages, DMA 버퍼는 캐시 속성을 맞춰 주는 dma_mmap_coherent. 지연 매핑은 vm_ops->fault로 접근할 때 페이지를 하나씩 준다.

It receives the VMA, validates size and offset, sets vm_page_prot, and populates page tables. For page-allocated or MMIO memory, remap_pfn_range by pfn, which marks the VMA VM_IO and VM_PFNMAP. For normal pages with a struct page, vm_insert_pages. For coherent DMA buffers, dma_mmap_coherent so kernel and user mappings share cache attributes. For lazy mapping, a vm_ops fault handler supplies pages on demand.

Q. Why is a missing size check in an mmap handler a security hole?

A. remap_pfn_range는 넘긴 pfn부터 요청한 크기만큼 그냥 매핑한다. 유저가 버퍼보다 크게 매핑 요청하면 버퍼 뒤의 커널 페이지가 유저 주소 공간에 들어오고, 쓰기까지 열려 있으면 권한 없는 유저가 커널 메모리를 읽고 쓴다. size > buffer 검사와 offset 범위 검사, 필요 없으면 VM_WRITE 거절이 필수다. 직접 봤는데 uid 1000이 링 뒤 커널 페이지의 비밀을 읽고 덮어썼다.

remap_pfn_range maps exactly the size you give starting at that pfn. If you don't clamp the requested size to the buffer, the user maps kernel pages past the buffer, and if writable, an unprivileged user reads and writes kernel memory. I demonstrated this — uid 1000 read and overwrote a secret page just past the ring. The fix is a size check, offset validation, and rejecting VM_WRITE when not needed.

Q. Is mmap always faster than read for a device?

A. 아니다. mmap의 이점은 복사 제거라 샘플이 클 때(카메라 4 MB 프레임) 확실히 이긴다. 32 B IMU 샘플은 복사가 싸서, mmap을 바쁜 폴링으로 긁으면 오히려 read() 블로킹보다 CPU가 더 들고 손실도 날 수 있다 — 직접 측정했다. mmap 링은 poll()과 묶어 블로킹 대기로 써야 제값을 한다. 측정 없이 "mmap이 빠르다"고 말하면 안 된다.

No. The win is eliminating the copy, so it clearly helps for large payloads like a 4MB camera frame. For a 32-byte IMU sample the copy is cheap, and busy-polling an mmap ring can cost more CPU than a blocking read and even drop samples — I measured exactly that. An mmap ring pays off when paired with poll() for blocking wakeups, not busy polling.

Q. Why return ENOTTY for an unknown ioctl command?

A. 관례다. -ENOTTY("inappropriate ioctl for device")가 "이 장치는 그 명령을 모른다"를 뜻하고, -EINVAL은 "명령은 알지만 인자가 틀렸다"를 뜻한다. 유저 라이브러리가 둘을 구분해 "이 기능 지원 안 함 vs 호출 잘못"을 판단한다. 커널 내부 -ENOIOCTLCMD는 VFS가 -ENOTTY로 바꿔 유저에 준다.

Convention. ENOTTY means the device doesn't know that command, while EINVAL means it knows the command but the argument is wrong. User libraries rely on that to distinguish "feature unsupported" from "bad call." Internally the driver can return ENOIOCTLCMD and the VFS translates it to ENOTTY.

Q. How do user and kernel stay consistent on a shared mmap ring buffer?

A. 단일 생산자(커널)/단일 소비자(유저) 링이면 head/tail 인덱스를 공유 페이지에 두고, 커널은 샘플을 다 쓴 뒤 smp_store_release로 head를 올리고, 유저는 smp_load_acquire로 head를 읽은 뒤 그 아래 슬롯만 읽는다. 이 release/acquire가 "슬롯 내용이 head보다 먼저 보이는" 순서를 보장한다. 유저가 느려 head-tail이 링 크기를 넘으면 덮어쓰기(overrun)니 유저가 tail을 점프하고 손실을 기록한다.

Single-producer single-consumer: head and tail live in the shared page. The kernel writes the slot then does smp_store_release on head; the user does smp_load_acquire on head then reads only slots below it. That release/acquire pair orders the slot contents before the head update. If the user falls behind and head minus tail exceeds the ring size, that's an overrun, so the user jumps tail forward and counts the loss.

13. 요약 & 체크리스트#

한 장치를 유저에 노출할 때 "제어는 어디로, 데이터는 어디로"를 먼저 가른다: 순차 스트림은 read/write, 단일 튜닝 값은 sysfs, 여러 값 원자 설정·START/STOP은 ioctl, 대량 고속 데이터는 mmap, 이벤트는 poll. 가능하면 IIO·V4L2 같은 서브시스템을 쓴다. ioctl UAPI는 고정 폭 타입·명시적 패딩·예약 비트 0 검사·copy_struct_from_user로 10년 뒤 32비트 레거시 앱도 안 깨지게 설계하고, ABI 독립이면 compat_ptr_ioctl 하나로 32비트를 받는다. mmap .mmap 핸들러는 크기·offset을 반드시 검사하고(안 하면 커널 메모리 누수) 캐시 속성을 정한 뒤 remap_pfn_range/vm_insert_pages/dma_mmap_coherent/.fault 중에 메모리 출처에 맞게 PTE를 채운다. "mmap이 항상 빠르다"는 틀렸다 — 큰 버퍼 + poll일 때 이기고, 작은 레코드 바쁜 폴링은 read()보다 나쁠 수 있다(직접 측정).
