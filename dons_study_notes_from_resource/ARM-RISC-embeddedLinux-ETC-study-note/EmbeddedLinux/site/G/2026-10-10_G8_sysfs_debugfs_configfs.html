0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어 시절을 떠올려 보자. 호스트가 드라이브와 대화하는 길은 여러 갈래였다. 정식 NVMe 명령(Get/Set Features)은 스펙에 박힌 약속이라 함부로 바꿀 수 없다. 반면 사내 디버그 툴이 쓰는 vendor-specific 명령이나 UART 디버그 셸은 팀 안에서만 쓰는 도구라 펌웨어 버전마다 형식이 바뀌어도 아무도 뭐라 하지 않는다. 그리고 "네임스페이스 만들기"처럼 호스트가 드라이브 안에 새 객체를 생성하는 명령이 따로 있다.

Linux 드라이버도 똑같이 세 갈래(+ 레거시 하나)를 갖고 있고, 각각 별도의 가상 파일시스템이다.

그림 1 — 드라이버가 유저에게 무언가를 보여 주는 네 개의 가상 파일시스템. 핵심 차이는 "누가 객체를 만드나"와 "ABI로 약속하나"다. sysfs·configfs 파일은 한 번 내보내면 사실상 영원히 지켜야 하는 약속이고, debugfs는 언제 바꿔도 되는 개발자 도구다.

Don의 펌웨어 경험에 대응시키면 이렇다.

1. sysfs의 규칙 — "값 하나 = 텍스트 파일 하나, 그리고 그것은 ABI다"#

1.1 직관#

sysfs(/sys)는 G2에서 본 것처럼 커널의 객체 트리(kobject)를 디렉터리로 보여 주는 파일시스템이다. 디렉터리 = 객체(디바이스, 드라이버, 버스), 파일 = 그 객체의 속성(attribute) 하나. 드라이버가 할 일은 자기 디바이스 디렉터리에 속성 파일을 몇 개 더 붙이는 것이다.

펌웨어로 치면 "레지스터 맵을 유저에게 노출하는데, 레지스터 대신 이름 붙은 텍스트 값으로 노출한다"고 보면 된다. odr 파일에 104가 들어 있고, 416을 쓰면 ODR이 바뀐다.

1.2 규칙 (Documentation/filesystems/sysfs.rst의 요지)#

규칙뜻어기면
값 하나 = 파일 하나한 파일에 한 값. 같은 타입의 배열(예: 선택 가능한 값 목록)만 공백으로 나열 허용유저가 파싱해야 하고, 필드 추가가 ABI 깨기가 된다
ASCII 텍스트숫자는 10진수 텍스트 + 줄바꿈. 바이너리는 binary attribute로 분리cat으로 못 보고, 엔디안·구조체 패딩이 ABI가 된다
PAGE_SIZE 이하show 버퍼는 한 페이지(arm64 기본 4 KiB)잘린다 (§3)
문서화새 속성은 Documentation/ABI/에 항목 추가리뷰에서 거절된다
영원히 유지한 번 나간 이름·형식·단위는 바꾸지 않는다유저 스크립트가 깨진다 ("We don't break userspace")

"값 하나" 규칙이 왜 이렇게 강조될까? /proc/meminfo처럼 여러 값을 한 파일에 넣으면, 다음 커널에서 줄 하나만 추가해도 파싱 코드를 대충 짠 유저 프로그램이 깨진다. 파일 하나에 값 하나면 새 값은 새 파일로 추가하면 되므로 기존 유저는 영향이 없다.

1.3 예제 1 — 진짜 ABI 문서 하나 읽기#

무엇을 확인하나: 랩 커널 소스의 Documentation/ABI/testing/sysfs-bus-iio에서 IIO 센서의 sampling_frequency 항목을 본다. 우리 odr 속성의 "정식 버전"이다.

출력에서 볼 것:

  • 항목 형식은 What:(경로) / KernelVersion:(처음 들어간 버전) / Contact: / Description:이다. 2.6.35(2010년)에 들어간 파일이 지금도 같은 이름·의미로 있다. 이것이 "sysfs는 ABI"의 실체다.
  • 바로 다음 항목이 sampling_frequency_available이다. "설정 가능한 값의 목록은 _available 접미사 파일로 따로 준다"는 관례다. 우리 드라이버도 odr_available을 만든다.
  • Documentation/ABI/ 아래는 stable/, testing/, obsolete/, removed/로 나뉜다. 새 드라이버 속성은 보통 testing/에 들어간다 (testing이라도 유저가 쓰기 시작하면 깨면 안 된다).

우리 sensorkit 드라이버를 업스트림에 낸다면 이런 파일을 같이 낸다 (형식 예시 — 실행 결과 아님).

실무 판단: 사실 진짜 IMU라면 sysfs 속성을 직접 만들지 않고 IIO 서브시스템(모듈 I)에 등록한다. 그러면 sampling_frequency, in_accel_scale, 버퍼·트리거가 표준 이름으로 공짜로 생긴다. "커스텀 sysfs 속성은 서브시스템이 표현 못 하는 것만" — 이게 리뷰어들이 기대하는 감각이다. 이 노트는 메커니즘을 보려고 platform driver에 직접 붙인다.

2. 속성 만들기 — DEVICE_ATTR_RW/RO/WO와 show/store#

2.1 정의#

디바이스 속성은 struct device_attribute다.

  • show: 유저가 read()하면 불린다. buf는 커널이 준비한 PAGE_SIZE 버퍼(페이지 정렬). 텍스트를 쓰고 쓴 바이트 수를 돌려준다.
  • store: 유저가 write()하면 불린다. buf는 유저 데이터 복사본(NUL로 끝남 보장), count는 길이. 성공하면 count를 돌려준다 (다 소비했다는 뜻). 실패하면 음수 errno.

매크로 세 개가 이름 규칙으로 함수를 연결해 준다.

매크로만드는 변수요구하는 함수모드
DEVICE_ATTR_RW(odr)dev_attr_odrodr_show, odr_store0644
DEVICE_ATTR_RO(temperature)dev_attr_temperaturetemperature_show0444
DEVICE_ATTR_WO(self_test)dev_attr_self_testself_test_store0200
DEVICE_ATTR_ADMIN_RW(x)dev_attr_xx_show, x_store0600
DEVICE_ATTR(x, mode, show, store)dev_attr_x임의 이름직접 지정

2.2 실습 대상 — sensorkit 드라이버와 DT#

실습용 DT 노드 두 개를 랩의 virt.dts에 붙인다. a는 온도 센서가 있는 변형(variant), b는 없는 변형이다. 이 차이를 §6의 is_visible이 사용한다.

DTB 만들기와 부팅 스크립트 (D8과 같은 방식: 랩 rootfs 복사 → .ko와 유저 바이너리, 게스트 스크립트 /g8.sh 추가 → -dtb로 부팅 → LAB_CMD로 스크립트 실행 후 자동 poweroff).

(마지막 sed는 BusyBox ls의 색 코드를 지운다.)

2.3 드라이버 코드 (1/9) — 상태와 가짜 레지스터 뱅크#

드라이버 g8_sensorkit.c는 길어서 아홉 조각으로 나눠 싣는다. 조각을 순서대로 이으면 실제로 빌드한 파일 그대로다. 실제 하드웨어가 없으니 u32 regs[6] 배열을 "MMIO 레지스터 뱅크"로 쓰고 readl/writel로 접근한다 (arm64에서 일반 메모리에 readl을 써도 동작한다. 실제 드라이버라면 devm_platform_ioremap_resource()로 얻은 주소다).

포인트:

  • 모든 상태는 디바이스마다 하나인 struct g8_priv에 있다. 전역 변수는 debugfs 루트 디렉터리 하나뿐이다. 장치가 두 개(a, b)여도 섞이지 않는다.
  • lock(mutex)이 레지스터와 통계를 보호한다. sysfs show/store는 프로세스 컨텍스트에서 불리고 여러 프로세스가 동시에 같은 파일을 읽고 쓸 수 있으므로, 공유 상태를 건드리면 락이 필요하다. 펌웨어로 치면 "디버그 셸 태스크와 센서 태스크가 같은 레지스터 미러를 만지는 상황"이다.

2.4 드라이버 코드 (2/9) — odr: 검증하는 RW 속성#

odr_store의 흐름이 store 함수의 교과서 형태다.

  1. 파싱: kstrtouint(buf, 0, &hz) — 끝의 \n 하나는 허용한다 (echo가 붙이니까). 숫자가 아니면 -EINVAL, 범위를 넘으면 -ERANGE를 돌려준다.
  2. 검증: 하드웨어가 지원하는 값인지 표에서 찾는다. 없으면 -EINVAL. 가장 가까운 값으로 반올림하지 않는다 — 그건 유저가 모르는 사이 다른 값이 설정되는 것이라, 이 드라이버에서는 거부를 택했다 (IIO 드라이버 중에는 반올림하는 것도 있다. 어느 쪽이든 ABI 문서에 적는다).
  3. 적용: 락 잡고 레지스터 read-modify-write.
  4. return count; — "다 썼다". 0이나 count보다 작은 값을 돌려주면 유저 write()가 남은 바이트로 다시 store를 부르는 등 이상하게 동작한다.

2.5 드라이버 코드 (3/9) — range(enum), temperature(RO), alarm, self_test(WO)#

  • range_store의 sysfs_match_string(range_str, buf)는 문자열 배열에서 일치하는 인덱스를 찾는다. 끝의 \n을 무시해 주므로 echo 8g > range가 바로 된다. 직접 strcmp하면 "8g\n"이 안 맞아서 초보자가 반드시 한 번 막히는 부분이다.
  • self_test는 쓰기 전용 트리거다. 모드 0200 — root도 읽을 수 없다 (§5). "1"만 받고 "0"은 -EINVAL. kstrtobool은 1/0/y/n/on/off를 받는다.
  • temperature는 milli-degC 정수다. sysfs 관례: 소수점 대신 정수 + 단위가 파일 이름이나 ABI 문서에 있다 (hwmon의 temp1_input도 milli-degC).

게스트 스크립트:

출력에서 볼 것:

  • 모드가 매크로대로다: odr/range 0644, temperature/alarm/odr_available 0444, self_test 0200, calibration 0600.

3. sysfs_emit / sysfs_emit_at — 왜 sprintf가 아닌가#

3.1 문제#

옛 드라이버는 show에서 return sprintf(buf, "%d\n", val);을 썼다. buf가 PAGE_SIZE라는 건 암묵적 약속일 뿐 sprintf는 크기를 모른다. 리스트를 출력하다 길어지면 페이지 밖을 덮어쓴다(커널 메모리 오염). snprintf(buf, PAGE_SIZE, ...)로 바꿔도 함정이 있다: snprintf는 "잘리지 않았다면 썼을" 길이를 돌려줘서, len += snprintf(buf + len, PAGE_SIZE - len, ...)를 반복하면 len이 PAGE_SIZE를 넘고 다음 호출의 크기 인자가 음수(→ 거대한 size_t)가 된다.

3.2 해결 — Linux 5.10부터#

랩 소스 fs/sysfs/file.c의 구현은 짧다.

  • vscnprintf는 실제로 쓴 길이를 돌려준다 (snprintf와 다름). 그래서 len += sysfs_emit_at(...)를 반복해도 PAGE_SIZE - 1을 넘지 않는다.
  • buf가 페이지 시작이 아니면 WARN하고 0을 돌려준다. "sysfs show 버퍼에만 써라"를 런타임에 강제하는 장치다. checkpatch.pl도 show 함수 안의 sprintf/snprintf에 경고를 낸다.

6. attribute group, is_visible, binary attribute#

6.1 직관#

속성을 하나씩 device_create_file()로 만들면 에러 처리·제거가 속성 수만큼 늘어난다. 그래서 커널은 속성 배열 + 옵션을 묶은 struct attribute_group을 한 번에 등록·제거하게 한다. 펌웨어로 치면 "레지스터 하나씩 초기화하지 말고 {addr, value} 테이블을 루프로 적용"하는 것과 같다.

  • is_visible: 그룹을 만들 때 속성마다 한 번 불린다. 0을 돌려주면 그 파일은 만들어지지 않고, 모드를 돌려주면 그 모드로 만든다 (모드를 바꿔 RO로 만드는 것도 가능). "이 변형 칩에는 온도 센서가 없다", "이 펌웨어 버전은 이 기능이 없다"를 표현하는 표준 방법이다.
  • 6.18에서 bin_attrs는 const struct bin_attribute *const * 타입이다. bin attribute 콜백의 세 번째 인자도 const struct bin_attribute *다. 이 const화는 6.13~6.16 무렵 진행된 변경이라 옛 커널 예제의 시그니처(비 const)와 다르다 — 블로그 코드를 복사하면 경고가 난다.

6.2 드라이버 코드 (4/9) — binary attribute + group + is_visible#

  • BIN_ATTR_ADMIN_RW(calibration, 32): calibration_read/calibration_write를 연결하고 크기 32, 모드 0600. 크기를 주면 sysfs가 off/count를 미리 잘라서 넘겨준다 — read/write 콜백에서 범위 검사를 다시 할 필요가 없다.
  • binary attribute는 sysfs의 "값 하나 = 텍스트" 규칙의 공식 예외다. 펌웨어 blob, EEPROM 내용(at24 드라이버의 eeprom 파일), PCI config space(/sys/bus/pci/devices/.../config), 보정 테이블처럼 "커널이 해석하지 않고 그대로 전달하는 바이트"에만 쓴다.
  • is_visible은 DT 속성을 직접 읽었다. probe()에서 채운 p->has_temp를 쓰지 않은 이유는 §8에서 나온다: .dev_groups는 probe가 끝난 뒤 만들어지므로 drvdata를 써도 되지만, 같은 그룹을 dev->groups(device_add 시점)로 옮기면 그때는 drvdata가 아직 없다. 펌웨어 속성(device_property_*, D8)은 언제나 읽을 수 있으므로 안전하다.
  • __ATTRIBUTE_GROUPS(g8)는 g8_groups[] = { &g8_group, NULL }을 만든다. 속성만 있다면 ATTRIBUTE_GROUPS(g8) 한 줄이 그룹 정의까지 해 주지만, bin_attrs와 is_visible을 넣으려고 그룹은 직접 정의했다.

6.3 예제 7 — binary attribute 읽고 쓰기, 크기 넘기기#

무엇을 확인하나: 32바이트 보정 blob을 읽고, 일부를 쓰고, 40바이트를 써서 크기 제한이 어떻게 걸리는지 본다.

출력에서 볼 것:

  • 바이너리(\001\002\003)가 그대로 저장·반환된다. 텍스트 변환 없음.
  • 40바이트 쓰기: sysfs가 count를 32로 잘라 store에 넘겼고(32 bytes copied), 나머지 8바이트를 쓰려는 두 번째 write()에서 오프셋 32 = 크기 → -EFBIG(File too large). 오프셋 32부터 쓰기(seek=4, bs=8)는 처음부터 -EFBIG. 커널 sysfs_kf_bin_write()의 if (size <= pos) return -EFBIG; 그대로다.
  • 그래서 binary attribute에서는 드라이버가 범위 검사를 안 해도 버퍼 오버플로가 없다. 단, 크기 0으로 선언하면(가변 크기) 이 보호가 꺼지므로 직접 검사해야 한다.

7. 변화 알리기 — sysfs_notify + poll(POLLPRI)#

7.1 직관#

"온도가 임계값을 넘으면 앱이 알게 해 주세요." 앱이 alarm 파일을 100 ms마다 읽는 폴링은 CPU를 낭비하고 반응이 느리다. 펌웨어라면 "상태 레지스터를 폴링하지 말고 인터럽트를 받아라"다. sysfs에도 그런 장치가 있다: 드라이버가 sysfs_notify()를 부르면, 그 파일을 poll()로 기다리던 프로세스가 깨어난다.

규칙(랩 소스 fs/kernfs/file.c의 주석 요지):

  1. 유저는 먼저 파일을 한 번 읽는다 (그때의 이벤트 번호가 기록된다).
  2. poll()의 events에 POLLPRI(또는 POLLERR)을 넣고 기다린다. sysfs 파일은 늘 "읽을 수 있음"이라 POLLIN은 의미가 없다.
  3. 깨어나면 revents에 POLLERR|POLLPRI가 켜져 있다. lseek(0) 후 다시 읽거나(pread(fd, .., 0)), 닫고 다시 연다.
  4. 이 메커니즘은 드라이버가 sysfs_notify를 부르는 속성에서만 동작한다. 지원하지 않는 속성을 poll하면 영원히 안 깨어난다 (에러도 없다) — 타임아웃을 꼭 건다.

그림 2 — sysfs 속성 변화 통지 순서. kernfs는 열린 파일마다 "마지막으로 본 event 번호"를 기억하고, kernfs_notify()가 노드의 event 번호를 올리고 대기 큐를 깨운다. 번호가 다르면 poll이 POLLERR|POLLPRI를 돌려준다.

7.2 드라이버 코드 (5/9) — 주기적 샘플링과 임계값 통지#

진짜 센서라면 data-ready 인터럽트의 threaded handler에서 할 일을, 여기서는 50 ms 주기 delayed work로 흉내 낸다. 온도 = 25.000 °C + debugfs knob으로 주입한 값(§9).

  • 통지는 상태가 바뀔 때만(0→1, 1→0) 보낸다. 매 샘플마다 보내면 유저가 쓸데없이 깨어난다.
  • sysfs_notify()는 내부에서 kernfs_find_and_get()으로 이름 검색을 하고 이는 잠들 수 있는 락을 쓴다. 그래서 hard IRQ 핸들러에서 부르면 안 된다. IRQ에서 알려야 하면 probe 때 sysfs_get_dirent()로 kernfs 노드를 미리 잡아 두고 sysfs_notify_dirent()(= kernfs_notify, IRQ 안전)를 쓰거나, threaded IRQ·workqueue로 넘긴다. (이 노트는 workqueue를 썼다.)
  • 락 밖에서 notify한다. notify가 깨운 유저가 바로 alarm_show를 부를 수 있으므로, 락을 잡은 채 부를 이유가 없다.

7.3 예제 8 — poller 프로그램#

무엇을 확인하나: alarm 파일을 poll(POLLPRI)로 기다리는 정적 링크 프로그램. 처음 값을 읽고, 두 번의 변화를 기다린다.

출력에서 볼 것:

  • revents=0xa = POLLERR(0x8) | POLLPRI(0x2). kernfs가 돌려주는 값 그대로다.
  • poller는 CPU를 쓰지 않고 잠들어 있다가 셸이 온도를 올린 지 약 1 work 주기(최대 50 ms) 안에 깨어났다. (poller의 시각은 CLOCK_MONOTONIC, dmesg는 printk 시계라 두 열을 ms 단위로 직접 비교하지는 말자.)

8. 속성은 uevent 전에 존재해야 한다 — .dev_groups가 이기는 이유#

8.1 문제#

udev(또는 mdev, systemd-udevd)는 커널 uevent를 받는 즉시 규칙을 실행한다. 규칙은 흔히 sysfs 속성을 읽어 판단하거나(ATTR{model}=="..."), 권한을 바꾼다(예제 5). 그런데 드라이버가 uevent를 보낸 다음에 속성을 만들면, udev가 먼저 달려가서 "파일이 없다"를 본다. 타이밍에 따라 되기도 하고 안 되기도 하는, 가장 나쁜 종류의 버그다. Greg Kroah-Hartman이 "sysfs 파일을 올바르게 만드는 법"으로 여러 번 강조한 문제다.

언제 uevent가 나가는지 driver core 코드(랩 소스)를 보면:

  • device_add() (drivers/base/core.c): device_add_attrs(dev) — 여기서 class·type·dev->groups의 그룹을 만들고 → … → kobject_uevent(&dev->kobj, KOBJ_ADD) → bus_probe_device(dev).
  • really_probe() (drivers/base/dd.c): driver_sysfs_add() → call_driver_probe()(우리 probe()) → device_add_groups(dev, drv->dev_groups) → … → driver_bound() 안에서 kobject_uevent(&dev->kobj, KOBJ_BIND).

그림 3 — 속성이 만들어지는 시점과 uevent의 순서. A는 uevent가 속성보다 먼저 나가는 경쟁(race), B는 device_add() 안에서 그룹을 먼저 만드는 올바른 방법, C는 드라이버가 붙이는 속성이 KOBJ_BIND 전에 생기는 흐름이다.

정리하면:

  • 장치를 직접 만드는 코드(class 디바이스, device_create, 서브시스템 코어)는 속성을 device_create_with_groups(), dev->groups, class->dev_groups, device_type->groups로 넘겨서 device_add() 안에서 만든다. → KOBJ_ADD 전에 존재.
  • 드라이버(platform/i2c/spi driver)는 장치를 만들지 않는다. 장치는 DT populate 때 이미 KOBJ_ADD를 보냈다. 드라이버 속성은 driver.dev_groups로 넘긴다. → driver core가 probe 성공 후, KOBJ_BIND 전에 만들고, unbind 때 자동으로 지운다. udev 규칙은 ACTION=="bind"로 건다.
  • probe 안에서 sysfs_create_group()/device_add_group()을 부르면 순서는 C와 비슷하지만 제거를 직접 해야 하고, 에러 경로·remove에서 빼먹기 쉽다. 그리고 probe가 그룹을 만든 뒤 나중 단계에서 실패하면 "속성이 잠깐 보였다가 사라지는" 상태가 유저에게 노출된다. .dev_groups는 probe가 성공한 뒤에만 만든다. 그래서 새 코드는 .dev_groups를 쓰라는 것이 리뷰 표준이다 (devm_device_add_group()은 차선책).

출력에서 볼 것:

  • /class/g8race, /module/g8_race에 대해서도 uevent가 나간다(클래스·모듈도 kobject). 거기에는 gain이 원래 없으니 MISSING이 정상이다.
  • platform 드라이버: unbind 이벤트 시점엔 odr가 이미 지워졌고(driver core가 .dev_groups를 자동 제거), bind 이벤트 시점엔 PRESENT. .dev_groups를 쓰면 bind 규칙이 언제나 속성을 본다.
  • 덤: probe에서 만든 misc 장치(/devices/virtual/misc/g8-sensorkit-a)도 자기 add/remove uevent를 보낸다. /dev 노드는 이 이벤트로 생긴다 (G7, G9).

9. debugfs — "개발자만 쓰는, 약속 없는 창문"#

9.1 직관과 규칙#

debugfs(/sys/kernel/debug)는 규칙이 없는 것이 규칙이다. 값 여러 개, 표, 레지스터 덤프, 바이너리 — 뭐든 된다. 대신:

  • ABI가 아니다. 다음 커널에서 파일 이름·형식이 바뀌어도 아무도 보장하지 않는다. 그러니 제품의 유저스페이스 서비스가 debugfs에 의존하면 안 된다.
  • 기본적으로 root만 접근한다(마운트 디렉터리 0700, 예제 5).
  • 보안: 커널 lockdown(lockdown=integrity / confidentiality, Secure Boot 시스템에서 흔함)이 켜지면 debugfs 접근이 막힌다 (LOCKDOWN_DEBUGFS). CONFIG_DEBUG_FS_ALLOW_NONE이나 커널 인자 debugfs=off로 아예 끈 양산 커널도 많다. 랩 커널은 CONFIG_DEBUG_FS_ALLOW_ALL=y, lockdown LSM 없음이다. "양산 이미지에서 debugfs가 없을 수 있다"를 전제로 설계한다.
  • 그래서 debugfs 생성 함수의 반환값은 검사하지 않는 것이 커널 관례다. debugfs가 실패해도 드라이버는 정상 동작해야 하고, 실패한 dentry(ERR_PTR)를 다른 debugfs 함수에 넘겨도 안전하게 무시된다.

SSD 비유: 펌웨어 디버그 UART 셸. 양산 펌웨어에서 꺼지고, 명령 형식은 팀 마음대로 바꾼다. 그 대신 bring-up 때 가장 많이 쓰는 도구다.

9.3 regset32 — 레지스터 맵을 이름과 함께 덤프#

Don이 보드 bring-up 때 JTAG로 레지스터 창을 띄워 보던 것을, 드라이버가 스스로 파일 하나로 제공하는 기능이다. 드라이버는 {이름, 오프셋} 표와 base 주소만 주면 된다. 읽을 때마다 커널이 readl(base + offset)을 하고 이름 = 0x%08x 형식으로 출력한다 (debugfs_print_regs32()). regset.dev를 채우면 읽는 동안 runtime PM으로 장치를 깨워 준다 — 전원이 꺼진 블록의 레지스터를 읽다가 bus fault 나는 사고를 막는다.

그림 4 — debugfs_create_regset32의 구조. 드라이버는 이름·오프셋 표와 base만 준다. 오른쪽 값은 예제 10에서 sysfs로 odr=416, range=8g, self_test=1을 쓴 뒤 실제로 읽은 값이다.

9.4 드라이버 코드 (6/9) — debugfs 디렉터리, regset32, knob, seq_file#

  • DEFINE_SHOW_ATTRIBUTE(g8_stats)는 g8_stats_show(struct seq_file *, void *)를 받아 g8_stats_open(= single_open)과 g8_stats_fops를 만들어 준다. debugfs_create_file에 넘긴 p는 inode의 i_private → single_open의 data → s->private로 전달된다. seq_file은 출력이 PAGE_SIZE를 넘어도 알아서 버퍼를 키우므로 sysfs보다 자유롭다.
  • temp_offset_mC는 0600 u32 knob이다. 테스트 코드가 "가짜 열"을 주입하는 결함 주입(fault injection) 훅이다 — 이런 건 절대 sysfs(ABI)에 두지 않는다.
  • threshold_mC는 x32라 16진수로 보인다(0x00009c40 = 40000). 데모용으로 일부러 x32를 썼다. 사람이 읽을 값은 u32가 낫다.
  • debugfs_remove(p->dbg)(remove에서 호출)는 디렉터리를 재귀로 지운다. 옛 이름 debugfs_remove_recursive는 이제 같은 함수의 별칭이다.

10. configfs — 유저가 커널 객체를 만드는 곳#

10.1 직관#

sysfs의 디렉터리는 커널이 만든다. 유저는 mkdir /sys/...를 할 수 없다. 그런데 "유저가 원하는 만큼 객체를 만들고 설정한 뒤 활성화"해야 하는 경우가 있다.

  • USB gadget: 보드가 USB 장치 역할을 할 때 어떤 기능(ACM 시리얼, 이더넷 NCM, mass storage)을 몇 개 묶을지 유저가 조립한다. 드론·로봇 컨트롤러가 USB로 PC에 "시리얼 + 네트워크" 복합 장치로 보이게 하는 게 이것이다.
  • nvmet(NVMe over Fabrics target): 서브시스템, 네임스페이스, 포트를 mkdir로 만든다. Don이 SSD에서 본 NVMe 개념(subsystem/namespace/port)이 그대로 디렉터리가 된다.
  • iSCSI/LIO target, IIO software trigger(configfs-iio), netconsole 대상 등.
  • DT overlay 적용: 업스트림 커널에는 configfs로 overlay를 올리는 인터페이스가 없다. Raspberry Pi 등 다운스트림 커널에 /sys/kernel/config/device-tree/overlays/<name>/dtbo에 blob을 써서 적용하는 패치가 있다 (D6 참조). 업스트림에서 이 방식은 보안·수명 문제로 받아들여지지 않았다.

configfs의 모델: mkdir → 커널의 make_item()/make_group() 호출 → 새 객체 + 속성 파일 생성. 속성에 값을 쓰고, 마지막에 "활성화" 속성(예: gadget의 UDC)에 쓰면 커널이 그 설정으로 동작한다. rmdir → drop_item() → 참조가 0이 되면 release(). 객체 생명주기를 유저가 결정한다는 점이 sysfs와 정반대다.

SSD 비유: NVMe Namespace Management(Create) + Attachment. 호스트가 "이 크기로 namespace 하나 만들어" → 펌웨어가 객체 생성 → Attach해서 활성화.

10.2 예제 12 — sensorkit 채널을 mkdir로 만드는 configfs 서브시스템#

무엇을 확인하나: 랩 커널은 CONFIG_CONFIGFS_FS=y다. /sys/kernel/config/g8_sensorkit/ 아래에서 mkdir하면 "채널" 객체가 생기고 axis, enable 속성이 붙는 모듈을 만든다. 코드는 두 조각이다.

  • configfs 속성 show/store는 struct config_item *를 받는다 (sysfs는 struct device *). CONFIGFS_ATTR(g8_chan_, axis)는 g8_chan_axis_show/_store를 연결해 g8_chan_attr_axis를 만든다. configfs의 page도 get_zeroed_page()로 받은 페이지 하나라서(fs/configfs/file.c) sysfs_emit을 그대로 쓸 수 있다. 업스트림 USB gadget configfs 코드도 sysfs_emit을 쓴다.
  • make_item이 config_item_init_type_name()으로 객체를 초기화하면, configfs가 디렉터리와 속성 파일을 만든다.
  • drop_item에서 config_item_put() → 참조가 0이 되면 release()에서 kfree. 처음에는 release()에서 config_item_name()을 찍었더니 (null)이 나왔다 — release 시점에는 이름이 이미 해제돼 있다. 이름이 필요한 로그는 drop_item에서 남긴다.

출력에서 볼 것:

  • 랩 initramfs는 configfs를 자동 마운트하지 않는다(/init은 proc, sysfs, devtmpfs, debugfs만 마운트). 일반 배포판에서는 systemd가 /sys/kernel/config에 마운트한다.
  • mkdir accel_x 한 번에 make_item이 불리고 axis, enable 파일이 생겼다. 파일 이름(=객체 이름)을 유저가 정했다.
  • 잘못된 값(axis에 7)은 sysfs와 똑같이 -EINVAL → write error.
  • 채널 gyro_z가 살아 있는 동안 rmmod는 실패한다(참조 카운트 2 — 채널 객체가 모듈을 붙잡고 있다). 객체를 rmdir한 뒤에야 내려간다. (BusyBox rmmod는 이때도 종료 코드 0을 돌려줘서 lsmod로 확인했다.)

11. procfs — 장치 파일을 새로 만들지 않는다#

/proc은 원래 이름 그대로 프로세스 정보(/proc/<pid>/maps, status, fd/)를 위한 곳이다. 리눅스 초기에 sysfs가 없어서 드라이버들이 /proc/driver/..., /proc/<무언가>에 장치 정보를 넣었고, 그 흔적이 /proc/interrupts, /proc/devices, /proc/misc(예제 11), /proc/bus/..., /proc/scsi/...로 남아 있다. 이미 유저가 쓰는 것이라 지우지는 못하지만:

  • 새 드라이버가 procfs 파일을 추가하는 패치는 리뷰에서 거절된다. 장치 설정·상태는 sysfs, 디버그는 debugfs로 간다.
  • 시스템 전역 튜닝은 /proc/sys(sysctl)이 맞는 자리지만, 이것도 드라이버 개별 설정에는 쓰지 않는다 (모듈 파라미터 /sys/module/<mod>/parameters/나 장치 속성이 맞다).
  • procfs에는 형식 규칙이 없어서 "값 여러 개를 한 파일에" 넣은 레거시 파일이 많다. 그걸 파싱하는 유저 코드 때문에 형식을 못 바꾸는 고통이, 바로 sysfs가 "값 하나 = 파일 하나"를 고집하는 이유다.

12. 측정 — 값 하나 읽는 비용: sysfs vs read() vs ioctl#

12.1 드라이버 코드 (7/9) — 비교용 문자 디바이스#

공정한 비교를 위해 같은 드라이버에 misc 장치(G7)를 붙였다. read()는 온도를 4바이트 바이너리로, ioctl(G8_IOC_GET_TEMP)는 put_user로 돌려준다.

12.2 드라이버 코드 (8/9, 9/9) — probe, remove, 등록#

  • probe에는 sysfs 코드가 한 줄도 없다. 속성은 .driver.dev_groups = g8_groups 한 줄로 끝났다.
  • misc.name = dev_name(dev)로 장치마다 다른 /dev 이름을 만들었다 (/dev/g8-sensorkit-a, -b).
  • remove 순서: 샘플링 work 정지(cancel_delayed_work_sync) → debugfs → misc. work가 돌면서 sysfs_notify를 부르는 중에 장치가 사라지지 않게 work부터 멈춘다. sysfs 쪽 순서는 driver core가 보장한다: 랩 소스 drivers/base/dd.c의 device_remove()는 먼저 device_remove_groups(dev, drv->dev_groups)로 속성을 지우고(kernfs가 실행 중인 show/store가 끝날 때까지 기다린다) 그다음 drv->remove()를 부르며, devm 자원(p)은 그 뒤 device_unbind_cleanup()에서 해제된다. 그래서 remove 안에서는 더 이상 show/store가 불리지 않는다.

그림 5 — 예제 14의 세 번 실행 중앙값. 절대값은 KVM 없는 TCG 에뮬레이션이라 실제 하드웨어보다 수십 배 크다. 봐야 할 것은 비율이다.

출력에서 볼 것:

  • cat처럼 매번 open/close하는 방식이 압도적으로 비싸다 (중앙값 210 µs, 나머지의 6~10배). 경로 이름 해석(/sys/bus/platform/devices/... 디렉터리 7단계 탐색), kernfs open 파일 구조 할당, seq_file 준비가 매번 일어난다. 셸 스크립트로 1 kHz 센서를 읽는 설계가 왜 안 되는지 보여 준다.
  • fd를 열어 두고 pread(fd, buf, n, 0)로 다시 읽으면 35 µs로 6배 빨라진다. sysfs를 자주 읽어야 하는 데몬은 이렇게 한다 (예제 8의 poller도 같은 방식).
  • 그래도 read() 4바이트(21 µs)와 ioctl(20 µs)보다 느리다. sysfs 경로는 seq_file 버퍼 준비 + PAGE 0 채우기 + sprintf류 포맷 + 유저 쪽 파싱이 더 붙는다. read()와 ioctl은 거의 같다 — 둘 다 syscall 1번 + copy_to_user 4바이트다.
  • 실행마다 20~40% 흔들린다 (같은 VM에서 다른 작업이 돌고, TCG는 호스트 부하에 민감). 결론(순서와 대략의 비율)은 세 번 모두 같다.
  • 정리: 설정·가끔 읽는 상태 → sysfs(비용 무관, 사람·스크립트 친화), 고속 반복 데이터 → 문자 디바이스 read/mmap 또는 IIO 버퍼. 이 측정은 G5의 "ioctl vs sysfs" 판단의 숫자 근거다.

13. 커널 안에서는 무슨 일이 일어나나#

echo 416 > odr와 cat odr이 우리 함수에 도달하는 경로다 (랩 소스 6.18.55 기준 함수 이름).

그림 6 — sysfs 속성 read/write의 커널 경로. 점선 위가 유저 공간이다. 아래로 갈수록 범용(VFS, kernfs)에서 구체(우리 드라이버)로 내려간다.

층별로 정리하면:

  1. kernfs (fs/kernfs/): sysfs·cgroupfs가 공유하는 "커널 객체를 위한 가상 파일시스템" 엔진. 디렉터리·파일 노드(struct kernfs_node)와 열린 파일(struct kernfs_open_file)을 관리하고, poll 대기 큐·event 번호(§7)도 여기 있다. active reference로 "show/store 실행 중에는 노드 제거를 기다리게" 해서, 속성 제거와 동시 접근을 안전하게 만든다.
  2. sysfs (fs/sysfs/file.c): kernfs 노드를 kobject와 struct attribute에 연결한다. sysfs_kf_seq_show()는 PAGE_SIZE 버퍼를 0으로 채운 뒤 kobj->ktype->sysfs_ops->show를 부르고, 결과가 PAGE_SIZE 이상이면 경고 후 자른다. 쓰기는 sysfs_kf_write() → ops->store.
  3. driver core (drivers/base/core.c): device kobject의 sysfs_ops가 dev_sysfs_ops = { dev_attr_show, dev_attr_store }다. container_of로 struct attribute → struct device_attribute를 얻어 우리 odr_show/odr_store를 부른다.
  4. binary attribute는 sysfs_kf_bin_read/write(크기 클리핑, §6.3), configfs는 kernfs가 아닌 자체 구현(fs/configfs/), debugfs도 자체 구현(fs/debugfs/)이다. debugfs는 파일 연산 앞뒤로 lockdown 검사와 "파일 제거 중이면 대기" 보호(debugfs_file_get/put)를 끼운다.

드라이버 작성 때 다시 만나는 곳

  • G2(디바이스 모델): kobject → kernfs 노드 → /sys 디렉터리. device_add() 순서가 §8의 근거.
  • G3(platform driver): .dev_groups, devm 자원과 속성 수명.
  • G5(ioctl과 mmap): §11.1 결정표와 §12 측정.
  • G6(poll): sysfs poll은 kernfs가 .poll을 대신 구현한 것. 드라이버 .poll + poll_wait와 같은 대기 큐 패턴.
  • G9(udev): bind/add 규칙이 속성을 읽는 시점.
  • 모듈 I(IIO), hwmon, LED, power_supply 같은 서브시스템은 표준 sysfs 이름을 만들어 준다 — 커스텀 속성은 마지막 수단.

16. 면접에서 이렇게 말한다#

Q. What's the difference between sysfs, debugfs, and configfs? When would you use each?

A. sysfs는 커널이 만든 객체(장치·드라이버)의 속성을 값 하나당 파일 하나로 보여 주고, 문서화된 ABI라 유지 의무가 있다. debugfs는 ABI가 없는 개발자용 창문이라 레지스터 덤프, 통계, 결함 주입에 쓰고 양산에서 꺼질 수 있다. configfs는 반대로 유저가 mkdir로 커널 객체를 만들고 설정하는 곳이고 USB gadget, nvmet이 대표다.

sysfs exposes attributes of kernel-created objects — one value per file, text, and it's a stable ABI that must be documented under Documentation/ABI. debugfs is a no-rules debug interface with no ABI guarantee: register dumps, stats, fault injection; it may be disabled or locked down in production, so nothing in the product should depend on it. configfs is the inverse of sysfs: userspace creates kernel objects with mkdir and configures them — USB gadget composition and the NVMe target are the classic users. And procfs is legacy for device stuff; new drivers shouldn't add files there.

꼬리 질문: "그럼 센서 데이터 스트림은?" → sysfs가 아니라 문자 디바이스 read/mmap 또는 IIO 버퍼. 값 하나 open/read/close가 실측으로 수십 배 비싸다 (§12).

Q. What are the rules for a sysfs attribute's show and store functions?

A. show는 페이지 정렬된 PAGE_SIZE 버퍼에 sysfs_emit으로 쓰고 길이를 돌려준다. store는 kstrto*나 sysfs_match_string으로 파싱·검증하고, 실패하면 음수 errno, 성공하면 count를 돌려준다. 공유 상태는 락으로 보호한다 — 여러 프로세스가 동시에 부를 수 있다.

show gets a page-sized, page-aligned buffer; use sysfs_emit or sysfs_emit_at, never sprintf, and return the length. store gets a NUL-terminated copy of the user data, possibly with a trailing newline; parse it with kstrtouint or sysfs_match_string, validate against what the hardware supports, return -EINVAL or the parse error on failure — that shows up as a write error and non-zero exit code in the shell — and return count on success. Both run in process context concurrently, so take a lock around hardware state.

Q. Why should you use the driver's dev_groups instead of calling sysfs_create_group in probe?

A. 속성이 생기는 시점과 정리 때문이다. .dev_groups는 driver core가 probe 성공 후, KOBJ_BIND uevent 전에 만들고 unbind 때 자동으로 지운다. 수동 생성은 에러 경로·remove에서 빼먹기 쉽고, 장치를 직접 만드는 코드에서 device_add 뒤에 만들면 udev가 KOBJ_ADD를 받는 순간 파일이 없다. 미니 udev로 재현하면 잘못된 방법은 MISSING, 올바른 방법은 PRESENT가 나온다.

Timing and lifetime. With driver.dev_groups the driver core creates the attributes right after probe succeeds and before the KOBJ_BIND uevent, and removes them automatically on unbind — no cleanup code. If you create a device yourself and add attributes after device_add, the KOBJ_ADD uevent has already gone out and udev may run its rules before the files exist — a race that only fails sometimes. For devices you create, pass the groups in: device_create_with_groups, dev->groups, or class->dev_groups. I reproduced it with a netlink uevent listener: attribute missing at the add event in the racy version, present in the correct one.

Q. How can userspace get notified when a sysfs value changes?

A. 드라이버가 값이 바뀔 때 sysfs_notify(&dev->kobj, NULL, "attr")를 부르고, 유저는 파일을 한 번 읽은 다음 poll을 POLLPRI로 기다린다. 깨어나면 POLLERR|POLLPRI가 오고, 오프셋 0부터 다시 읽는다. sysfs_notify는 잠들 수 있어서 hard IRQ에서 부르면 안 된다.

The driver calls sysfs_notify on the attribute when the value changes. Userspace opens the file, reads it once to arm it, then polls with POLLPRI; on change poll returns POLLERR|POLLPRI and you pread from offset zero to get the new value. It only works for attributes whose driver actually calls sysfs_notify, so always use a timeout. sysfs_notify can sleep, so from an IRQ you either defer to a thread or work item, or cache the kernfs node and use sysfs_notify_dirent. For high-rate events I'd use a proper subsystem event interface like IIO events instead.

Q. How would you expose a register dump of your device for debugging?

A. debugfs의 debugfs_create_regset32를 쓴다. 이름·오프셋 표와 ioremap한 base만 주면 읽을 때마다 readl해서 NAME = 0x%08x로 출력한다. regset.dev를 채우면 runtime PM으로 장치를 깨워서 읽는다. I2C/SPI 장치라면 regmap이 debugfs에 registers 파일을 자동으로 만든다. 절대 sysfs에 두지 않는다 — ABI가 돼 버린다.

debugfs, with debugfs_create_regset32: a table of name/offset pairs plus the ioremapped base, and every read does readl and prints NAME = 0x%08x. Set regset.dev and it takes a runtime PM reference so you don't read a powered-off block. For I2C or SPI devices regmap already gives you a registers file in debugfs. I'd never put a raw register dump in sysfs, because then the register layout becomes ABI. In bring-up this is how I compare what I wrote through the user interface with what's actually in the hardware.

Q. When would you use a binary sysfs attribute?

A. 커널이 해석하지 않는 바이트 덩어리일 때 — 보정 blob, EEPROM 내용, PCI config space. BIN_ATTR_RW(name, size)로 크기를 주면 sysfs가 offset·count를 잘라 주고, 크기를 넘는 쓰기는 -EFBIG가 된다. 텍스트 값을 바이너리로 내보내는 데 쓰면 안 된다.

Only for opaque byte blobs the kernel doesn't interpret — calibration data, EEPROM contents, PCI config space, firmware-related blobs. You declare it with BIN_ATTR_RW or the ADMIN variant with a size, and sysfs clips offset and count for you; writes past the end get -EFBIG. Since 6.13-ish the callbacks and the group's bin_attrs take const struct bin_attribute pointers. It's not a way to dodge the one-value-per-file rule for normal settings.

Q. Can you add a /proc file for your driver's status?

A. 새 드라이버에는 안 된다. procfs는 프로세스 정보용이고 장치 관련 파일은 레거시로 유지만 한다. 상태는 sysfs, 디버그 정보는 debugfs로 간다.

Not in a new driver — it would be rejected upstream. procfs is meant for process information; the device-related files there are legacy kept for compatibility. Device state goes into sysfs, ideally via a subsystem's standard attributes, and anything debug-only goes into debugfs.

19. 요약 & 체크리스트#

드라이버가 유저에게 무언가를 보여 주는 자리는 네 곳이다. sysfs는 커널이 만든 객체의 속성을 "값 하나 = 텍스트 파일 하나"로 보여 주는 ABI이고, 드라이버는 DEVICE_ATTR_RW/RO/WO + sysfs_emit으로 속성을 만들어 .driver.dev_groups에 넘긴다. 그러면 driver core가 probe 성공 후 KOBJ_BIND 전에 만들고 unbind 때 지운다. 변형별 속성은 is_visible, 바이트 blob은 binary attribute, 변화 통지는 sysfs_notify + poll(POLLPRI). debugfs는 ABI 없는 개발자 도구라 레지스터 덤프(debugfs_create_regset32), knob, seq_file 통계를 마음껏 두되, 제품은 절대 의존하지 않는다. configfs는 유저가 mkdir로 객체를 만드는 곳(USB gadget, nvmet)이고, procfs에는 새 장치 파일을 만들지 않는다. 그리고 sysfs는 설정·상태용이지 데이터 경로가 아니다 — 값 하나 open/read/close는 ioctl의 10배 비용이었다.
