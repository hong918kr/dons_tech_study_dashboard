G9. 핫플러그와 udev — 장치가 생기면 누가 /dev 노드를 만들고 드라이버를 올리나

이 노트를 다 읽으면: device_add() → kobject_uevent() → netlink/uevent_helper → udev·mdev → /dev 권한·심볼릭 링크·modprobe로 이어지는 핫플러그 사슬을 함수 이름 그대로 그릴 수 있다 · 드라이버에서 add_uevent_var()로 uevent 변수를 넣고(bus·class·device_type 세 자리), MODULE_DEVICE_TABLE이 어떻게 자동 로딩으로 이어지는지 설명할 수 있다 · udev rule(==/=/+=, ATTRS{} 부모 탐색, SYMLINK+=, MODE=, RUN+=)을 쓰고 udevadm test로 검증해 적용·제거할 수 있다 · BusyBox mdev(/etc/mdev.conf, 데몬·helper 모드)로 같은 일을 하는 임베디드 구성을 만들 수 있다 왜 필요한가: "같은 IMU 두 개가 부팅마다 /dev 번호가 바뀐다", "USB GNSS를 꽂았는데 드라이버가 안 올라온다", "앱이 /dev/xxx를 열 권한이 없다"는 실무 첫 달 단골이고, 면접에서는 "How does a kernel module get loaded automatically when a device appears?"로 나온다 Don 기준 난이도: "이벤트가 생기면 상위 계층에 메시지를 보낸다"는 펌웨어의 인터럽트 → 메일박스 → 상위 태스크 구조와 같다 / 새로 배울 부분은 그 메시지가 문자열 KEY=VALUE 목록이고, 정책(이름·권한·모듈 로드)을 커널이 아니라 유저 공간 데몬이 규칙 파일로 정한다는 점 선행 노트: A9(netlink uevent 리스너), D3(modalias·modprobe coldplug), E3(커널 모듈·depmod), G2(디바이스 모델), G4(문자 디바이스) — G8(sysfs)·G10(펌웨어 로딩)과 이웃이다

0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어에서 PCIe 링크가 올라오거나 NAND 다이가 응답하지 않는 일이 생기면, 인터럽트 핸들러는 일을 다 하지 않는다. 이벤트를 메일박스(큐)에 적어 상위 태스크에 넘기고, 정책 판단(재시도할지, 호스트에 알릴지)은 상위 태스크가 한다. "빠르고 단순한 쪽은 사실만 알리고, 느리고 복잡한 쪽이 정책을 정한다"는 분리다.

Linux 핫플러그가 정확히 이 구조다.

  • 커널(사실을 아는 쪽): USB 장치가 꽂히거나, I2C 센서가 probe되거나, 모듈이 로드되거나, 우리가 sysfs에 뭔가 쓰면 driver core가 struct device를 만들고 device_add()를 부른다. 그 안에서 kobject_uevent(KOBJ_ADD)가 "add@/devices/... + KEY=VALUE 목록" 메시지를 만든다. 이것이 uevent다.
  • 배달: 메시지는 netlink 멀티캐스트(NETLINK_KOBJECT_UEVENT, A9에서 직접 들었다)로 방송되고, 설정돼 있으면 /proc/sys/kernel/hotplug에 적힌 프로그램(uevent_helper)도 이벤트마다 실행된다.
  • 유저 공간(정책을 정하는 쪽): 데스크톱·Yocto의 systemd-udevd, 작은 임베디드의 BusyBox mdev가 메시지를 받아 규칙 파일대로 권한·소유자·안정된 이름(심볼릭 링크)·모듈 자동 로드(modprobe $MODALIAS)·프로그램 실행을 한다.
  • /dev 노드 자체는 요즘 커널이 직접 만든다(devtmpfs). 그래서 udev가 없어도 노드는 생긴다. udev·mdev는 그 위에 정책을 얹는다.

그림 1 — 핫플러그 사슬. 커널은 사실(uevent)만 알리고, 노드 생성은 devtmpfs가, 권한·이름·모듈 로드·프로그램 실행 같은 정책은 유저 공간 데몬이 한다.

1. uevent — 커널이 보내는 "장치 생김/사라짐" 메시지#

1.1 직관#

uevent는 문자열 메시지 한 통이다. 첫 줄은 ACTION@DEVPATH(예: add@/devices/platform/g9-imu.0), 그 뒤는 \0으로 구분된 KEY=VALUE 목록이다. 펌웨어로 치면 "이벤트 코드 + TLV 페이로드"를 사람이 읽을 수 있는 텍스트로 만든 것이다. 정수 구조체가 아니라 문자열이라서, 커널이 새 키를 추가해도 옛 udev가 깨지지 않는다.

1.2 이 노트의 실험 장치 — g9_hot + g9_imu#

진짜 USB 장치를 QEMU에 꽂지 않고도 핫플러그를 마음대로 일으키려고 모듈 두 개를 만들었다.

  • g9_hot.ko: /sys/kernel/g9_hot/add에 "front SN1001"을 쓰면 "g9-imu"라는 이름의 platform device를 하나 만든다(= 센서가 꽂힘). remove에 번호를 쓰면 지운다(= 센서가 빠짐). 장치마다 device_type.uevent로 G9_POSITION, G9_SERIAL 변수를 uevent에 덧붙인다.
  • g9_imu.ko: "g9-imu" 장치를 다루는 드라이버. MODULE_DEVICE_TABLE(platform, ...)으로 자동 로딩 별칭을 내보내고, probe에서 class g9에 char device g9_imuN을 만든다(G4). class의 dev_uevent로 노드 쪽 이벤트에도 위치를 실어 준다.

예제 1 — g9_hot.c (장치를 만들고 지우는 쪽)#

무엇을 확인하는 코드인가: platform device를 런타임에 만들고 지우는 법, 그리고 device_type.uevent에서 add_uevent_var()로 변수를 넣는 법. (길어서 두 조각으로 나눴다. 두 조각을 이어 붙이면 파일 하나다.)

코드에서 볼 것:

  • add_uevent_var(env, fmt, ...)는 env->buf(2048바이트, UEVENT_BUFFER_SIZE)에 KEY=VALUE\0을 붙이고 env->envp[](최대 64개, UEVENT_NUM_ENVP)에 포인터를 단다. 넘치면 -ENOMEM을 돌려준다. 그래서 반환값을 그대로 위로 올린다.
  • 콜백 시그니처의 const struct device *는 6.3 무렵 driver core 전체가 const화되면서 바뀐 것이다. 옛 드라이버 예제(struct device *dev)를 그대로 붙이면 6.x에서 경고·에러가 난다.

예제 4 — 장치 두 개를 꽂고 하나를 뽑기 (QEMU 게스트, mdev 없이 devtmpfs만)#

무엇을 확인하나: add 한 번에 uevent가 몇 개, 어떤 순서로 나오는지, 각 이벤트에 어떤 변수가 실리는지, 그리고 /dev 노드가 누구 손으로 생기는지.

게스트 실행 방법(이후 모든 게스트 예제가 같다): 랩 rootfs를 /var/tmp/G9/rootfs로 복사해 /g9/에 .ko·바이너리·스크립트를 넣고 cpio로 묶은 뒤, LAB_CMD=sh~/g9/t1.sh로 부팅한다.

출력에서 볼 것 (ls의 날짜, 타임스탬프, SEQNUM, major 510은 실행마다 다르다):

  • 꽂기 한 번 = uevent 세 통: platform device add(#2206) → 드라이버 probe가 만든 class 장치 add(#2207) → probe 성공 후 platform device bind(#2208). 뽑기는 역순: class remove → unbind → platform remove.
  • /dev/g9_imu0은 아무 데몬도 없는데 생겼다. devtmpfs가 device_add() 안에서 직접 만들었다. 권한 crw-r-----(0640)은 class의 devnode 콜백이 정한 값이고, 같은 값이 uevent의 DEVMODE=0640으로도 나갔다. 소유자는 root:root(0:0) — 그룹을 바꾸는 건 유저 공간 몫이다.
  • platform device 이벤트에는 MAJOR/MINOR/DEVNAME이 없다(노드가 없는 장치). 노드는 class 장치(g9_imu0)에 붙는다. udev rule을 쓸 때 "어느 이벤트에 매칭하나"가 여기서 갈린다.
  • unbind 이벤트에는 MODALIAS가 빠졌다. kobject_uevent_env()가 KOBJ_UNBIND일 때 zap_modalias_env()로 지운다 — 드라이버가 떨어졌다고 udev가 모듈을 다시 로드하지 않게 하려는 것이다.
  • sysfs의 uevent 파일을 읽으면 같은 변수 목록(ACTION·DEVPATH·SUBSYSTEM·SEQNUM 제외)을 볼 수 있다. 리스너 없이 디버깅할 때 제일 빠른 방법이다.
  • class 장치 이벤트에는 G9_POSITION만 있고 G9_SERIAL은 없다. 각 uevent에는 그 kobject의 콜백이 넣은 변수만 실린다 — 부모의 변수는 자동으로 따라오지 않는다. 그래서 g9_imu의 class 콜백이 부모 platform_data에서 위치를 꺼내 따로 넣었다(§7에서 이 차이가 실제로 드러난다).

2. uevent 변수 해부 — 누가 어떤 KEY를 넣나#

그림 2 — 예제 4의 실제 변수들과 그 변수를 넣은 함수. 위에서 아래가 add_uevent_var() 호출 순서다.

kobject_uevent_env()(lib/kobject_uevent.c, v6.18)가 하는 일을 순서대로 적으면:

  1. kobject에서 부모로 올라가며 kset을 찾는다. struct device는 전부 devices_kset에 속하고, 그 kset의 uevent_ops가 driver core의 device_uevent_ops(dev_uevent_filter, dev_uevent_name, dev_uevent)다.
  2. uevent_suppress가 켜져 있거나 filter()가 0을 돌려주면 조용히 버린다. dev_uevent_filter()는 bus도 class도 없는 장치를 거른다.
  3. 버퍼 struct kobj_uevent_env(envp 64칸 + buf 2048바이트)를 kzalloc하고 기본 키 ACTION, DEVPATH, SUBSYSTEM을 넣는다. SUBSYSTEM은 dev_uevent_name() — bus가 있으면 bus 이름, 없으면 class 이름.
  4. 호출자가 준 추가 변수(kobject_uevent_env(kobj, action, envp_ext)의 envp_ext)를 넣는다.
  5. kset의 uevent() = dev_uevent()를 부른다. 이 안에서 MAJOR/MINOR/DEVNAME/DEVMODE(devt가 있을 때, device_get_devnode()), DEVTYPE(dev->type->name), DRIVER, OF_NAME/OF_FULLNAME/OF_COMPATIBLE_N/OF_COMPATIBLE_x(DT 노드가 있을 때, D3 예제 8에서 봤다), 그다음 bus->uevent(platform이면 platform_uevent() → MODALIAS=platform:<name>, DT 장치면 of_device_uevent_modalias()가 of:N...T...C...를 넣는다), class->dev_uevent, dev->type->uevent 순으로 부른다.
  6. SEQNUM을 전역 카운터 uevent_seqnum에서 atomic64_inc_return()으로 받아 붙인다.
  7. kobject_uevent_net_broadcast()로 netlink 방송, CONFIG_UEVENT_HELPER가 켜져 있고 uevent_helper[0]이 비어 있지 않으면 HOME=/, PATH=...를 더해 helper를 call_usermodehelper_exec(..., UMH_NO_WAIT)로 실행한다.

2.2 변수 이름 규칙과 함정#

  • 키는 대문자 + 밑줄이 관례다. udev rule의 ENV{G9_POSITION}으로 그대로 매칭된다.
  • 값에 공백이 있어도 되지만, uevent_helper로 실행되는 셸 스크립트에서 따옴표를 안 쓰면 깨진다.
  • 한 이벤트의 변수 총합이 2048바이트를 넘거나 64개를 넘으면 add_uevent_var()가 WARN(1, "add_uevent_var: buffer size too small")(또는 too many keys)을 찍고 -ENOMEM을 돌려준다. 긴 문자열(펌웨어 버전 목록 등)을 uevent에 싣지 말고 sysfs 속성(G8)으로 노출하자.

3. 유저 공간으로 가는 두 길 — netlink와 uevent_helper#

앱이 "장치 노드가 권한까지 준비된 뒤" 알림을 받아야 한다면 group 1이 아니라 group 2(libudev monitor)를 들어야 한다. group 1 시점에는 udev가 아직 MODE/GROUP을 적용하지 않았을 수 있다. §8.1의 호스트 실측에서 같은 add 이벤트가 KERNEL → UDEV로 약 80 ms 뒤에 다시 나온다.

3.2 uevent_helper — /proc/sys/kernel/hotplug#

옛날(2.4~2.6 초) 방식은 이벤트마다 커널이 프로그램을 하나 실행하는 것이었다. 경로는 /proc/sys/kernel/hotplug(= sysctl kernel.hotplug, = /sys/kernel/uevent_helper)에 적는다. 커널 쪽 코드는 §2의 7단계 — call_usermodehelper_setup() + call_usermodehelper_exec(info, UMH_NO_WAIT). argv는 [helper, SUBSYSTEM], 환경 변수는 uevent 변수 전체 + HOME=/ + PATH=/sbin:/bin:/usr/sbin:/usr/bin이다.

  • 장점: 데몬이 필요 없다. 부팅 아주 초기(initramfs)에도 동작한다. BusyBox mdev가 이 방식으로 설계됐다.
  • 단점: 이벤트마다 fork+exec. 부팅 때 수천 개의 이벤트가 쏟아지면 프로세스 폭주가 나고(fork bomb에 가깝다), UMH_NO_WAIT라서 실행 순서가 SEQNUM 순서와 다를 수 있다(add보다 remove가 먼저 처리되는 레이스). mdev는 이를 /dev/mdev.seq 파일로 직렬화한다(§7.3).
  • 그래서 drivers/base/Kconfig의 UEVENT_HELPER 도움말은 "This should not be used today" — 부팅 때 짧은 시간에 이벤트가 몰리면 이벤트당 프로세스 하나가 부하를 만들고, 작은 시스템에서는 부팅 중 OOM까지 난다고 적는다. arm64 defconfig 기반인 랩 커널은 꺼져 있다.

예제 5 — 랩 커널에는 helper가 없다 + sysfs uevent 파일에 쓰기#

무엇을 확인하나: (1) 공용 랩 커널(arm64 defconfig 기반)에 CONFIG_UEVENT_HELPER가 있는지, (2) sysfs의 uevent 파일에 쓰면 커널이 이벤트를 다시 만들어 보내는지(합성 uevent).

  • 그런데 devtmpfs가 만든 원래 노드 /dev/g9_imu0(0640, gid 0)도 그대로 남아 있다. >path는 "옮기고 원래 이름에 링크"인데, 원래 이름이 이미 devtmpfs 노드로 존재해서 mdev가 링크를 만들지 못했다. devtmpfs + mdev 조합에서 이름 바꾸기 규칙은 사본을 하나 더 만드는 셈이고, 원래 노드의 권한은 바뀌지 않는다. 보안 목적이라면 원래 노드 권한도 다뤄야 한다(이름을 바꾸지 말고 권한만 주는 줄을 쓰는 게 단순하다).
  • 훅의 MDEV는 옮겨진 이름(sensorkit/imu0)이다. 처음 버전 스크립트는 MDEV가 g9_imu0이라고 가정했다가 링크가 sensorkit/imusensorkit/imu0으로 깨졌다(실제로 겪은 실수, 위는 고친 뒤 결과).
  • serial=이 비어 있다. 노드 이벤트(class 장치)에는 class 콜백이 넣은 G9_POSITION만 있고 G9_SERIAL은 부모 platform device의 이벤트에만 있었다(예제 4). mdev 스크립트는 그 이벤트의 환경만 본다. udev라면 ATTRS{}로 부모를 올라가 볼 수 있지만(§8), uevent 변수는 상속되지 않는다. 필요하면 드라이버가 class 쪽에도 넣거나, 스크립트가 /sys/$DEVPATH/../../를 직접 읽어야 한다.

  • mdev 경로는 50~70 ms. 대부분은 프로세스 생성과 셸 실행(mdev가 system()으로 /bin/sh -c /etc/g9_link.sh를 띄우고, 그 셸이 ln·cut을 또 fork)이다. TCG 에뮬레이션에서 fork·exec이 특히 비싸서 실제 Cortex-A 보드보다 크게 나온다 — 절대값이 아니라 "노드 vs 정책 적용"의 차이를 보라.
  • 이 측정에서는 helper가 데몬보다 약간 빨랐다. 데몬은 한 프로세스가 이벤트를 차례로 처리하지만, helper는(이 측정에서는 /dev/mdev.seq를 만들지 않아) 이벤트마다 별도 프로세스가 병렬로 뜨므로 노드 이벤트가 앞 이벤트를 기다리지 않는다. 대신 순서 보장이 없다. 다른 노트 작성자들의 빌드로 VM 부하가 높을 때 미리 돌려 본 실행에서는 mdev -d 중앙값이 245 ms까지 늘었다 — 이런 수치는 부하에 민감하다.
  • 비교용으로, VM 호스트(네이티브 aarch64, systemd-udevd)에서 예제 14의 rule을 둔 채 losetup 직후부터 /dev/g9/sensorlog 링크가 보일 때까지 20번 잰 결과는 다음과 같다(Python 스크립트, losetup 실행 시간은 제외).

13. 면접에서 이렇게 말한다#

Q. What happens, end to end, when you plug in a USB device on a Linux system?

A. USB 코어가 enumerate해서 usb_device/usb_interface를 만들고 device_add()를 부른다. 그 안에서 devtmpfs가 노드를 만들고, kobject_uevent(KOBJ_ADD)가 ACTION, DEVPATH, SUBSYSTEM, MODALIAS=usb:v...p... 같은 변수를 담은 uevent를 netlink로 방송한다. udevd가 받아 rule을 돌린다 — 80-drivers.rules가 MODALIAS로 kmod를 불러 modules.alias에서 드라이버를 찾아 로드하고, 드라이버가 probe되면 tty·video 같은 class 장치가 생기며 또 uevent가 온다. 그 이벤트에서 udev가 권한·그룹·/dev/serial/by-id 같은 링크를 만들고, systemd 태그가 있으면 .device 유닛을 활성화한다.

The USB core enumerates the device and registers it with device_add(). devtmpfs creates the node, and kobject_uevent sends an add event over netlink with ACTION, DEVPATH, SUBSYSTEM and a MODALIAS string built from the vendor, product and interface IDs. udevd runs its rules: the drivers rule calls kmod with the MODALIAS, which looks it up in modules.alias and loads the matching driver. When the driver probes, it registers a class device like a tty, which generates another uevent, and on that one udev applies ownership, permissions and persistent symlinks such as /dev/serial/by-id, and tags it for systemd so a device unit becomes active.

꼬리 질문: "Where does modules.alias come from?" → MODULE_DEVICE_TABLE → modpost(file2alias)가 .mod.c에 MODULE_ALIAS → .modinfo → depmod.

Q. How does a kernel module get loaded automatically when its device appears?

A. 드라이버의 매칭 테이블에 MODULE_DEVICE_TABLE을 붙이면 빌드 때 modpost가 테이블을 alias 문자열로 바꿔 .ko의 .modinfo에 넣는다. depmod가 모든 alias를 modules.alias로 모은다. 장치가 생기면 버스의 uevent 콜백이 같은 형식의 MODALIAS를 만들어 보내고, udev나 mdev가 modprobe $MODALIAS를 실행해 glob 매칭으로 모듈을 찾는다. 커널이 request_module()로 직접 modprobe를 부르는 경로는 별개다.

The driver annotates its ID table with MODULE_DEVICE_TABLE. At build time modpost turns each entry into an alias string and stores it in the module's modinfo, and depmod collects all aliases into modules.alias. When a device appears, the bus's uevent callback emits a MODALIAS in the same format, and udev or mdev runs modprobe with it; modprobe glob-matches it against the alias index and loads the module. That's separate from request_module, where the kernel itself execs modprobe, for example for a socket family or filesystem.

Q. What's the difference between devtmpfs and udev? Do I need udev?

A. devtmpfs는 커널이 device_add() 안에서 직접 노드를 만드는 파일시스템이다. 이름과 기본 권한은 커널(드라이버의 devnode)이 정한다. udev는 그 위에 정책 — 소유자·그룹·권한, 안정된 심볼릭 링크, 모듈 로드, 프로그램 실행 — 을 얹는다. 작은 장비는 devtmpfs만, 또는 devtmpfs + mdev로 충분하다. 핫플러그 장치·모듈 자동 로드·권한 정책이 필요하면 udev나 mdev가 있어야 한다.

devtmpfs is the kernel creating device nodes itself, synchronously inside device_add, with the name and default mode coming from the driver. udev adds policy on top: ownership and permissions, persistent symlinks, module autoloading and running programs. A small fixed-function device can run on devtmpfs alone, or devtmpfs plus BusyBox mdev. If you have hotplug devices or need autoloading and permission policy, you want udev or mdev.

Q. We have two identical IMUs (or cameras). How do you make sure the application always opens the right one?

A. 커널이 붙이는 번호(iio:device0, video0)는 probe 순서에 따라 바뀔 수 있으니 쓰지 않는다. 바뀌지 않는 속성 — I2C 버스 번호와 주소(DT가 고정), USB 물리 포트 경로(ID_PATH), 일련번호 — 로 udev rule을 써서 /dev/sensorkit/imu-front 같은 역할 이름 링크를 만들고, 앱은 그것만 연다. udevadm info -a로 키를 고르고 udevadm test로 검증한다. 드라이버를 우리가 쓴다면 위치 정보를 uevent 변수로 내보내는 것도 방법이다.

I never rely on kernel enumeration numbers like video0 because probe order can change. I write udev rules that match stable attributes — the I2C bus and address fixed by the device tree, the USB physical port path via ID_PATH, or a serial number — and create role-based symlinks like /dev/sensorkit/imu-front. The application only opens those. I pick the keys with udevadm info -a and verify the rule with udevadm test before deploying it.

꼬리 질문: "Why can't you combine ATTRS from two different parents?" → udev는 한 규칙 줄의 복수 키들을 부모 하나에서 같이 맞아야 하는 것으로 평가한다.

Q. How would you add custom information to a device's uevent from a driver?

A. add_uevent_var()를 세 군데 중 하나에서 부른다: 버스 공통이면 bus_type.uevent, class 공통이면 class.dev_uevent, 특정 장치 종류면 device_type.uevent. driver core의 dev_uevent()가 이 순서로 부른다. 상태 변화를 알릴 때는 kobject_uevent_env(&dev->kobj, KOBJ_CHANGE, envp)로 change 이벤트를 보낸다. 다만 uevent는 버퍼 2 KB·64개 제한이 있고 비싼 경로라 고빈도 데이터 통지에는 쓰지 않는다.

I'd call add_uevent_var from the right hook: the bus_type uevent callback for bus-wide keys like MODALIAS, the class dev_uevent for keys common to a class, or a device_type uevent for one kind of device. dev_uevent in the driver core calls them in that order. For state changes I'd send a change event with kobject_uevent_env and an extra envp array. I keep it small — the environment is limited to 2 KB and 64 keys — and I don't use uevents for high-rate notifications; that's what poll or IIO buffers are for.

Q. What is coldplug and how does it work?

A. 커널은 유저 공간이 뜨기 전에 대부분의 장치를 만들기 때문에 그때 uevent는 아무도 못 들었다. udevd가 뜬 뒤 udevadm trigger가 /sys의 모든 장치의 uevent 파일에 add를 써서 커널이 같은 이벤트를 다시 보내게 하고, 그래서 모듈 로드·권한·링크가 적용된다. mdev는 mdev -s로 /sys/dev를 훑지만 이벤트를 재생하지는 않아서 모듈 로드는 따로 해야 한다.

Most devices are created before userspace starts, so their uevents had no listener. After udevd starts, udevadm trigger writes "add" into every device's uevent file in sysfs, and the kernel re-emits a synthetic event with the same variables, so rules and module loading get applied. BusyBox mdev -s only scans /sys/dev to create nodes; it doesn't replay events, so module autoloading needs a separate modalias loop.

Q. What is /proc/sys/kernel/hotplug and why isn't it used anymore?

A. uevent_helper 경로다. 설정되면 커널이 이벤트마다 그 프로그램을 call_usermodehelper로 실행한다. 데몬이 필요 없어 초기 initramfs나 mdev에 쓰였지만, 이벤트마다 fork·exec라 부팅 때 부하·OOM 위험이 있고 비동기 실행이라 순서가 뒤섞일 수 있다. 지금은 netlink를 듣는 데몬(udevd, mdev -d)이 표준이고 많은 커널이 CONFIG_UEVENT_HELPER를 끈다.

It's the uevent helper path. If set, the kernel execs that program for every uevent through call_usermodehelper, with the event variables as its environment. It needs no daemon, so it was used in early initramfs and by mdev, but it forks a process per event, which can overload or even OOM a small system at boot, and since it's asynchronous the events can be processed out of order. Today a daemon listening on the netlink socket — udevd or mdev -d — is the norm, and many kernels disable CONFIG_UEVENT_HELPER.

  1. (코드) g9_imu.c에서 MODULE_DEVICE_TABLE 줄을 지우고 다시 빌드해 modinfo -F alias g9_imu.ko와 예제 9의 lsmod 결과를 비교하라. 정답/힌트: alias가 비고, mdev의 modprobe "platform:g9-imu"가 실패해 g9_imu가 올라오지 않는다. /dev/sensorkit/도 생기지 않는다.
  1. (관찰) 호스트에서 udevadm monitor --kernel --udev --property를 켜 두고 sudo losetup -f --show <파일>을 실행해, KERNEL 이벤트와 UDEV 이벤트의 키 차이를 표로 정리하라. 끝나면 losetup -d. 정답/힌트: UDEV 쪽에만 DEVLINKS, ID_LOOP_*, TAGS, USEC_INITIALIZED. 예제 13의 Properties와 비교.
  1. (rule) 예제 13의 rule을 ATTR{loop/backing_file} 대신 ENV{ID_LOOP_BACKING_FILENAME}으로 매칭하도록 바꾸고 udevadm test -v -D로 확인하라. 어느 쪽이 더 이른 시점에도 동작하나? 정답/힌트: ID_LOOP_*는 앞선 rule(60-persistent-storage 계열)이 만든 속성이라 우리 파일이 그보다 뒤 번호여야 보인다. 99번이면 된다. sysfs 속성은 순서와 무관.
  1. (mdev) /etc/mdev.conf의 두 줄 순서를 바꿔($MODALIAS=.*를 먼저) 예제 9를 돌리면 어떻게 되나? 예상하고 실행해 보라. 정답/힌트: mdev는 첫 매칭에서 멈춘다. class 장치 이벤트에는 MODALIAS가 없으므로 g9 줄까지 내려가 결과는 같을 것으로 예상되지만, MODALIAS가 있는 장치 이벤트(platform bind 등)에서 modprobe가 다시 불린다. 실행해서 ps/hook log로 확인.
  1. (측정) 예제 16을 -smp 2로 다시 돌려 mdev helper와 mdev -d의 차이가 어떻게 바뀌는지 그래프로 그려라. 정답/힌트: 이 VM은 TCG 에뮬레이션이라 fork·exec 비용이 실제 하드웨어보다 훨씬 크다. 절대값보다 비율을 보라.

16. 요약 & 체크리스트#

장치가 생기면 driver core의 device_add()가 (노드가 있으면) devtmpfs로 /dev 노드를 먼저 만들고, kobject_uevent(KOBJ_ADD)로 ACTION/DEVPATH/SUBSYSTEM에 dev_uevent()·bus·class·device_type 콜백이 add_uevent_var()로 붙인 변수(MAJOR/MINOR/DEVNAME, DRIVER, OF_*, MODALIAS, 드라이버 고유 키)와 SEQNUM을 담은 uevent를 만든다. 이 메시지는 netlink 멀티캐스트로 방송되고, 설정돼 있으면 uevent_helper(/proc/sys/kernel/hotplug, 이벤트마다 fork)로도 전달된다. 유저 공간의 udevd 또는 mdev가 이를 받아 rule대로 권한·소유자·안정 이름 링크를 만들고, MODALIAS로 modprobe를 불러 MODULE_DEVICE_TABLE → file2alias → .modinfo → depmod 색인으로 이어진 사슬을 통해 드라이버를 자동 로드한다. 부팅 전 생긴 장치는 sysfs uevent 파일 쓰기(coldplug)로 이벤트를 재생한다. udev rule은 파일 이름순·줄 단위로 모두 평가하고 복수 키는 부모 하나에서 맞아야 하며, mdev.conf는 첫 매칭에서 멈춘다. 이 노트의 실측으로는 devtmpfs 노드가 데몬보다 훨씬 먼저 생기고, 이벤트마다 셸을 띄우는 mdev는 그 위에 수십 ms(TCG 에뮬레이션, 부하가 높으면 수백 ms)를 더한다.
