D1. 왜 Device Tree인가 — 물어볼 수 없는 하드웨어를 커널에 알려 주는 데이터

200분 읽기2180줄68개 절

이 노트를 다 읽으면: discoverable 버스(PCIe·USB)와 non-discoverable 장치(MMIO UART·I2C 센서·GPIO·IRQ 배선)의 차이로 "DT가 왜 필요한가"를 30초 안에 설명할 수 있다 · board file(arch/arm/mach-*, C 코드 속 platform_device) 시대가 왜 무너졌고 DT가 "커널 하나, 보드 여러 개"를 어떻게 가능하게 했는지 말할 수 있다 · .dts → dtc → .dtb → 부트로더 → 커널(unflatten) → platform_device → driver 경로를 QEMU 랩에서 직접 따라가며 /proc/device-tree, of_node·driver 심볼릭 링크, uevent로 보여 줄 수 있다 · DT가 아닌 것(코드, 정책)과 ACPI와의 차이를 말할 수 있다 왜 필요한가: Embedded Linux 면접의 단골 첫 질문이 "Device Tree가 뭐고 왜 쓰나요?"이고, 실무 첫 주에 만나는 "커널은 떴는데 센서(UART·I2C)가 안 보인다"의 절반은 DT 문제다 Don 기준 난이도: PCIe enumeration·config space·BAR, MMIO 레지스터 맵, 인터럽트 배선은 이미 몸에 붙어 있다 / 새로 배울 부분은 "그 정보를 커널 바이너리 밖의 데이터로 빼서 부팅 때 넘긴다"는 발상, 그리고 그 데이터가 커널 안에서 디바이스 모델(device_node → platform_device → driver)로 바뀌는 과정 선행 노트: C1(부팅 흐름 개관), C3(U-Boot) — 없어도 읽을 수 있다. 0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 컨트롤러 펌웨어를 짤 때를 떠올려 보자. NAND 채널 컨트롤러가 0x4000_0000에, UART가 0x5000_1000에, 타이머 인터럽트가 NVIC 15번에 있다는 사실은 헤더 파일에 #define으로 박혀 있었다. 칩이 바뀌면 헤더를 바꾸고 다시 빌드한다. 펌웨어는 그 칩 하나만 위해 존재하니까 아무 문제가 없다.

Linux 커널은 사정이 다르다. 같은 Image 하나가 i.MX8MP 보드에서도, TI AM62 보드에서도, Raspberry Pi에서도, QEMU에서도 떠야 한다. 그런데 커널이 부팅하자마자 알아야 하는 것들 — "RAM은 어디부터 얼마나 있나", "콘솔 UART는 어느 주소인가", "인터럽트 컨트롤러는 GICv2인가 v3인가", "I2C 버스 3번의 0x68에 IMU가 붙어 있고 그 인터럽트는 GPIO 1-12에 물려 있다" — 이 정보 대부분은 하드웨어에 물어볼 방법이 없다.

반면 PCIe는 물어볼 수 있다. Don이 매일 보던 그 config space다. 루트 컴플렉스가 Bus/Device/Function을 하나씩 읽어 보면 Vendor ID가 0xFFFF가 아닌 곳에 장치가 있고, 장치가 직접 "나는 8086:100e, class 0200(이더넷), BAR0는 128KB 필요"라고 답한다. 이게 discoverable 버스다. SoC 안의 UART나 I2C에 매달린 센서는 그런 표준 질의 방법이 없다. 이게 non-discoverable 장치다.

그림 1 — 왼쪽은 장치가 스스로 정체를 밝히는 버스, 오른쪽은 누군가 "어디에 무엇이 어떻게 붙어 있다"를 알려 줘야 하는 장치들. 왼쪽 숫자는 이 노트 §7에서 QEMU 게스트가 실제로 enumeration한 값이다.

"누군가 알려 줘야 한다"의 답이 시대마다 달랐다.

  • 2011년 무렵까지의 ARM: 커널 소스 안의 board file(arch/arm/mach-omap1/board-osk.c 같은 C 파일)에 struct platform_device와 struct resource로 주소·IRQ를 하드코딩했다. 보드마다 C 파일 하나, 그리고 대개 보드마다 다른 커널 빌드.
  • 지금의 ARM/arm64/RISC-V: 하드웨어 설명을 커널 밖의 데이터 파일(Device Tree)로 뺐다. 부트로더가 그 데이터의 메모리 주소를 커널에 넘기고(arm64는 레지스터 x0), 커널은 그걸 읽어 디바이스를 만든다. 커널 바이너리는 보드를 몰라도 된다.
  • x86 PC·서버, 일부 arm64 서버: 펌웨어(UEFI)가 ACPI 테이블로 알려 준다 (§9, C8).

커널 문서 Documentation/devicetree/usage-model.rst(Grant Likely 작성)는 Linux가 DT를 쓰는 목적을 세 가지로 정리한다: (1) platform identification(어떤 기계인지 — 루트의 compatible), (2) runtime configuration(/chosen의 bootargs, initrd 위치 등), (3) device population(디바이스를 만들어 드라이버와 짝지어 주기). 이 노트는 세 가지를 모두 랩에서 확인한다.

Embedded Linux 엔지니어가 이 그림을 머릿속에 갖고 있어야 하는 장면:

  • 새 보드 bring-up: 벤더 EVK의 .dts를 복사해 우리 보드(센서 키트)의 배선대로 고친다. 커널 C 코드는 거의 손대지 않는다. Don이 Apple에서 새 실리콘 bring-up 때 하던 "이 블록은 어느 주소, 어느 IRQ"를 정리하는 일이 그대로 .dts 작성이다.
  • "커널은 떴는데 장치가 없다": /sys/bus/i2c/devices에 IMU가 없다. 드라이버가 없는 걸까, DT 노드가 없는 걸까, status = "disabled"일까, compatible 오타일까? §6, §10의 도구로 5분 안에 가른다.
  • 면접: "DT가 뭐고 왜 쓰나요?", "PCI 장치는 왜 DT에 안 적나요?", "ACPI랑 뭐가 달라요?" — §15에 답이 있다.

실행 환경: 모든 출력은 실제 실행 결과다. 두 곳에서 돌렸다. (1) Lima VM elinux(aarch64, uname -r = 7.0.0-38-generic, Apple Virtualization 위 — ACPI로 부팅하는 머신이라 §9의 대조군이 된다). (2) 그 VM 안의 공용 QEMU 랩: qemu-system-aarch64 -machine virt -cpu cortex-a57 -m 512M, 커널 Linux 6.18.55 LTS(/var/lab/out/Image), BusyBox initramfs, DT는 QEMU가 만든 virt 머신 DT(/var/lab/out/virt.dts). 게스트 명령은 랩 initramfs의 LAB_CMD=로 실행했고, ls의 색상 escape 코드만 지웠다. 타임스탬프·KASLR·주소는 실행마다 다르다.

1. Discoverable 버스 — PCIe와 USB는 스스로 말한다#

1.1 직관 — "전화번호부가 아니라 호출 응답"#

Don에게 PCIe enumeration은 설명할 필요가 없지만, "왜 DT가 필요 없나"의 관점으로 다시 보자. 커널(또는 펌웨어)은 다음만 알면 된다.

  1. config space에 접근하는 방법 — ECAM 영역의 물리 주소. addr = ECAM_base + (bus << 20 | dev << 15 | fn << 12) + offset.
  2. 그다음은 전부 장치가 답한다: offset 0x00의 Vendor/Device ID, 0x08의 Class Code, 0x0E의 Header Type, BAR에 0xFFFFFFFF를 써서 읽는 크기, Capability 리스트(MSI/MSI-X, PCIe Cap) …

그래서 PCI 드라이버는 "내가 다룰 장치는 8086:100e"라고 ID 테이블(struct pci_device_id)만 선언하면 되고, 어떤 주소에 있을지는 enumeration이 정한 BAR에서 받아 간다. 장치의 위치·자원은 런타임에 발견된다.

USB도 같다. 호스트가 새 장치를 address 0에서 만나 GET_DESCRIPTOR를 보내면 장치가 Device Descriptor(idVendor, idProduct, bDeviceClass), Configuration/Interface/Endpoint Descriptor를 돌려준다. 커널은 이 값으로 usb_device_id 테이블과 짝짓는다. 핫플러그까지 된다.

1.2 그런데 "발견"에도 출발점이 필요하다#

여기서 Don이 놓치기 쉬운 점이 있다. PCIe Root Complex 자체는 discoverable이 아니다. ECAM이 물리 주소 어디에 있는지, 레거시 INTx가 GIC의 몇 번 SPI로 연결되는지, MSI는 어느 컨트롤러로 가는지, CPU 주소 공간의 어느 창(window)을 PCI 메모리 공간으로 쓸지 — 이건 SoC 설계가 정한 것이고 PCIe 프로토콜로 물어볼 수 없다. 그래서 랩의 DT에도 PCIe 장치는 하나도 없지만 host bridge 노드 pcie@10000000은 있다 (§4.1, §7). USB도 마찬가지로 xHCI 컨트롤러 자체(MMIO 주소, IRQ)는 SoC에 박힌 non-discoverable 장치다.

1.3 무엇을 알려 줘야 하나 — 드라이버가 probe()에서 필요한 것#

센서 키트의 IMU 드라이버가 일하려면 다음을 알아야 한다. 이 목록이 곧 DT 노드에 적히는 속성 목록이다 (자세한 문법은 D2, 자원 기술은 D4).

  • 무엇인가: compatible = "st,lsm6dso" — 어떤 드라이버를 붙일지.
  • 어디 있나: MMIO 장치라면 reg = <주소 크기>, I2C 장치라면 reg = <0x6a>(버스 위 주소). 그리고 어느 버스 밑에 있나(트리 구조 자체).
  • 인터럽트: interrupts/interrupt-parent — "GPIO1의 12번 핀, falling edge".
  • 클록·리셋·전원: clocks, resets, vdd-supply — Don이 bring-up 때 "클록 게이트 열고, 리셋 풀고, 레일 올리고"를 하던 바로 그 순서의 재료.
  • 핀: pinctrl-0 — 그 패드를 I2C 기능으로 mux.
  • 보드 고유 사실: 센서 장착 방향(mount-matrix), 크리스털 주파수(clock-frequency) 같은 것.

이것들은 보드마다 다르고, 하드웨어에 물어볼 수 없고, 드라이버 코드가 알 수 없다. 이 세 조건이 모두 참인 정보를 담는 그릇이 DT다.

2. Non-discoverable 장치 — 왜 "그냥 찔러 보기"가 안 되나#

2.1 MMIO UART — 없는 주소를 읽으면?#

"주소를 모르면 후보 주소를 다 읽어 보면 되지 않나?" bare-metal 감각으로는 그럴듯하다. 하지만:

  • 없는 주소를 읽으면 bus error가 난다. AXI 인터커넥트가 DECERR/SLVERR를 돌려주면 Cortex-A는 동기/비동기 External Abort(arm64에서는 SError)로 커널을 죽인다. Don이 SSD 펌웨어에서 잘못된 주소를 찔러 Data Abort를 봤던 것과 같다.
  • 있는 주소라도 읽기에 부작용이 있다. UART의 수신 FIFO(DR)를 읽으면 문자 하나가 사라지고, 많은 인터럽트 상태 레지스터는 read-to-clear다.
  • 클록이 꺼진 블록은 접근하면 버스가 멈출(hang) 수 있다. 클록·전원 도메인을 먼저 켜야 하는데, 어떤 클록인지는 또 물어볼 수 없다.

2.2 I2C 센서 — 스캔은 "추측"이다#

i2cdetect로 버스를 스캔하면 ACK하는 주소는 보인다. 하지만 이건 증거가 아니라 추측이다.

  • 0x68에서 ACK가 오면 그게 MPU-6050인지, DS1307 RTC인지 모른다 (둘 다 0x68을 쓴다).
  • 일부 칩은 "읽기 시도"만으로도 상태가 바뀐다. 그래서 i2cdetect도 기본 동작에서 특정 주소 범위는 조심스럽게 다루고 경고 문구를 띄운다.
  • 인터럽트 핀이 어느 GPIO에 물렸는지, 리셋 핀은 어디인지, 레귤레이터는 무엇인지 — 버스 스캔으로는 절대 알 수 없다. PCB 회로도에만 있는 사실이다.

2.3 AMBA PrimeCell — "반쯤 discoverable"한 예외#

랩의 UART(PL011), RTC(PL031), GPIO(PL061)는 ARM의 PrimeCell IP다. 이 블록들은 레지스터 맵의 끝(오프셋 0xFE0~0xFFC)에 Peripheral ID / PrimeCell ID 레지스터가 있어서, 주소만 알면 "나는 PL011 rev1"이라고 답한다. 그래서 Linux에는 amba 버스가 따로 있고, 드라이버는 compatible 문자열이 아니라 이 ID로 매칭된다. §6에서 보듯 9000000.pl011은 /sys/bus/platform이 아니라 /sys/bus/amba에 있고, uevent에 AMBA_ID=00141011이 찍힌다.

그래도 주소는 알려 줘야 한다. DT 노드의 compatible = "arm,pl011", "arm,primecell" 중 "arm,primecell"이 커널에게 "이건 platform device 말고 amba device로 만들어라"라고 알려 주는 표시다 (drivers/of/platform.c의 of_platform_bus_create()에서 of_device_is_compatible(bus, "arm,primecell")이면 of_amba_device_create()로 간다 — §12에서 소스로 본다). 정체는 물어볼 수 있어도 위치는 물어볼 수 없다 — non-discoverable의 정의가 "정체를 모른다"보다 "어디 있는지·어떻게 배선됐는지 모른다"에 가깝다는 좋은 예다.

3. DT 이전의 ARM — board file 시대#

3.1 board file이란 — 예제 1: 지금도 남아 있는 board file 읽기#

무엇을 확인하나: 6.18 커널 트리에 아직 남아 있는 옛 방식 board file을 직접 열어, 하드웨어 설명이 C 코드로 어떻게 적혔는지 본다.

출력에서 볼 것: TI OSK5912 보드의 SMC91x 이더넷 칩 위치(OMAP_OSK_ETHR_START)와 IRQ가 C 구조체로 적혀 있고, osk_init() 안에서 platform_add_devices()로 커널에 등록된다(같은 파일 422행). 부트로더는 "나는 OSK 보드다"라는 machine type 번호를 레지스터 r1에 넣어 넘겼고(ARM 32비트 ATAGS 부팅 규약), 커널은 이 번호로 MACHINE_START(OMAP_OSK, ...) 블록을 골랐다. 보드 하나 = C 파일 하나 = MACHINE_START 하나.

struct platform_device와 struct resource는 지금도 쓰는 구조체다. 달라진 것은 누가 이걸 만드느냐뿐이다. 예전엔 board file의 정적 변수였고, 지금은 커널이 DT 노드를 읽어 런타임에 만든다 (§6, §12).

3.2 무엇이 문제였나#

board file 하나는 무해하다. 문제는 수였다.

  • 보드 수만큼 C 코드: 2000년대 후반 ARM SoC 벤더(TI, Samsung, Freescale, Marvell, Qualcomm, NVIDIA …)가 폭발했고, SoC마다 arch/arm/mach-<soc>/ 디렉터리, 보드마다 board-*.c가 쌓였다. 같은 SMC91x 칩을 쓰는 보드 수십 개가 비슷한 struct resource를 각자 복사했다.
  • 보드마다 다른 커널: 많은 mach-*가 서로 배타적인 Kconfig 선택이어서, "OMAP용 커널"과 "i.MX용 커널"을 따로 빌드해야 했다. 배포판(Debian, Ubuntu)이 ARM 보드를 지원하려면 보드마다 커널 패키지를 만들어야 했다.
  • merge window마다 충돌과 churn: 매 릴리스마다 arch/arm에 막대한 양의 보드 코드 변경이 들어왔다.

이 상황이 2011년 3월 LKML에서 폭발했다. v2.6.39 merge window에 들어온 OMAP 쪽 pull request 스레드에서 Linus Torvalds가 ARM 플랫폼 코드의 끝없는 churn에 강하게 불만을 터뜨렸는데, 자주 인용되는 첫 문장이 "Gaah. Guys, this whole ARM thing is a f*cking pain in the ass."(욕설 일부 가림)이다. 요지는 "보드마다 중복된 코드와 서로 밟는 변경을 그만 보내라, 공통화하라"였다. 이 사건 이후 ARM 커뮤니티는 Linaro를 중심으로 arm-soc 트리(Arnd Bergmann, Olof Johansson 등이 관리)로 SoC 코드를 모아 리뷰하는 체계를 만들고, 새 플랫폼은 DT로만 받는다는 방향을 굳혔다. (원문: [LKML 2011-03-17, "Re: [GIT PULL] omap changes for v2.6.39 merge window"](https://lkml.org/lkml/2011/3/17/492). 당시 상황은 LWN.net의 2011년 기사 "ARM wrestling"에도 정리돼 있다.)

인용은 조심해서 쓰자. 면접에서는 "2011년에 Linus가 ARM 보드 코드의 중복과 churn을 공개적으로 비판했고, 그게 DT 전면 도입과 arm-soc 정리의 계기가 됐다" 정도면 충분하다. 정확한 문장을 외울 필요는 없다.

3.3 DT는 어디서 왔나#

DT는 ARM이 발명한 것이 아니다. 커널 문서 usage-model.rst의 History 절에 따르면:

  • 원래 Open Firmware(IEEE 1275, Sun SPARC·Apple PowerPC Mac의 펌웨어)가 OS에 하드웨어 토폴로지를 넘기던 자료 구조다.
  • 2005년 PowerPC Linux가 32/64비트를 합치면서 Open Firmware가 없는 임베디드 PowerPC 보드에도 DT를 강제했고, 이를 위해 펌웨어 없이 바이너리 덩어리로 넘길 수 있는 FDT(Flattened Device Tree) 형식을 만들었다. U-Boot와 kexec가 dtb를 넘기고 고칠 수 있게 바뀌었다.
  • 이후 FDT 인프라가 아키텍처 공통 코드(drivers/of/)로 일반화됐고, ARM 32비트가 2011년 무렵부터 본격적으로 옮겨 왔다.
  • arm64(2012년 메인라인 진입)는 처음부터 board file 개념이 없다. 하드웨어 설명은 DT 또는 ACPI로만 받는다.

예제 2에서 이 역사가 지금 트리에 어떻게 남아 있는지 센다.

3.4 예제 2 — 6.18 트리에 남은 board file 세기#

무엇을 확인하나: 32비트 ARM에는 board file이 소수 남아 있고, arm64에는 mach-* 디렉터리 자체가 없다는 것.

출력에서 볼 것: 이름이 board-*.c인 파일 20개 중 상당수가 이름에 -dt(board-dt.c, board-generic.c)가 붙어 있다 — 이름만 board file이고 실제로는 "DT를 쓰는 SoC 공통 초기화"다. 진짜 옛 방식은 OMAP1(board-osk.c 등), Nokia N8x0, Orion5x 몇 개 같은 오래된 32비트 보드뿐이다. arm64 디렉터리 목록에는 mach-*가 아예 없다.

3.5 같은 칩, 세 가지 설명 방식 — smc91x 드라이버#

무엇을 확인하나: 한 드라이버가 board file(이름 매칭), DT(compatible 매칭), ACPI(_HID 매칭)를 동시에 지원하는 모습. 드라이버 코드는 하드웨어가 어떻게 설명됐는지와 무관하게 platform_get_resource()로 같은 자원을 받는다.

출력에서 볼 것: CARDNAME은 "smc91x"로, §3.1 board file의 .name = "smc91x"와 이름으로 매칭된다. ARM Versatile 보드의 DT 노드 4줄(compatible, reg, interrupts)이 board file의 struct resource 배열 + struct platform_device 20줄을 대체한다. 그리고 그 4줄은 커널 바이너리 밖에 산다. 드라이버 쪽 probe()는 셋 중 어느 경로로 왔든 platform_get_resource(pdev, IORESOURCE_MEM, 0)과 platform_get_irq(pdev, 0)으로 똑같이 자원을 받는다 — 매칭 우선순위와 상세는 D3.

그림 2 — board file 시대에는 보드 설명이 커널 바이너리 안의 C 코드였다. DT 시대에는 공용 커널 하나에 보드마다 .dtb 하나를 짝지어 부트로더가 넘긴다.

3.6 예제 3 — "커널 하나, 보드 여러 개"를 직접 보기#

무엇을 확인하나: 바이트 하나 다르지 않은 같은 커널 Image가, DT가 다른 두 "보드"(CPU 1개·RAM 512MB vs CPU 4개·RAM 1GB)에서 각자 맞게 뜬다. QEMU virt는 명령행 옵션에 따라 DT를 다르게 생성한다 — 실제 보드에서 .dtb를 바꿔 끼우는 것과 같은 상황이다.

출력에서 볼 것: uname -v의 빌드 시각이 같다 — 같은 커널이다. 그런데 DT의 /cpus 아래 cpu@N 노드 수가 1 → 4로, /memory@40000000/reg의 크기 칸이 0x20000000(512MB) → 0x40000000(1GB)로 바뀌었고, 커널은 그대로 따른다. 펌웨어로 치면 #define NUM_CORES와 #define DRAM_SIZE를 바꾸고 재빌드 없이 다른 보드에서 돌린 셈이다. (MemTotal이 512MB보다 작은 것은 커널 이미지·예약 영역을 뺀 값이라서다.)

출력에서 볼 것: QEMU가 덤프한 blob은 정확히 1 MiB(1048576)지만 실제 내용은 7.5KB다. 나머지는 빈 공간이다 — 부트로더·QEMU가 부팅 직전에 /chosen에 bootargs나 initrd 주소를 제자리에서 추가할 수 있도록 남겨 둔 여유다. U-Boot에서도 fdt resize로 같은 일을 한다 (C3). fdtget은 컴파일 없이 blob에서 속성 하나를 꺼내는 도구로, 보드 위에서 디버깅할 때 유용하다.

4.4 FDT 바이너리 구조#

.dtb는 Devicetree Specification(v0.4) 5장의 FDT 형식이다. 모든 정수는 big-endian이다 (Don의 PCIe config space는 little-endian이었다 — 헷갈리기 쉬운 지점).

속성 이름은 strings block에 한 번만 저장되고, 각 속성은 그 문자열의 offset(nameoff)만 들고 있다. compatible이 48번 나와도 문자열 "compatible"은 한 번만 있다.

4.5 예제 5 — FDT 헤더를 C로 직접 파싱#

무엇을 확인하나: 커널이 부팅 직후 가장 먼저 보는 40바이트 헤더를 직접 읽는다. 같은 프로그램을 게스트에서 돌리면 커널이 실제로 받은 blob(/sys/firmware/fdt)을 읽는다.

출력에서 볼 것: magic 0xd00dfeed("dood feed")가 FDT의 서명이다. 부트로더가 넘긴 주소에서 이 값이 안 보이면 커널은 DT를 못 찾았다고 판단한다. 두 파일의 structure block(7048)·strings block(462) 크기는 같고 totalsize만 다르다 — 내용은 같고 여유 공간만 다르다는 증거다. 이 프로그램을 게스트에서 인자 없이 돌린 결과는 §5.2에 있다.

5. 게스트 안에서 DT 보기 — /proc/device-tree와 /sys/firmware#

5.1 직관 — 커널이 펼친 트리를 파일 시스템으로 보여 준다#

커널은 받은 FDT를 부팅 초기에 unflatten한다 — 평평한 바이트 덩어리를 struct device_node(노드)와 struct property(속성)의 포인터 트리로 바꾼다. 그 트리를 sysfs에 그대로 비춘 것이 /sys/firmware/devicetree/base이고, /proc/device-tree는 옛 사용자 공간 호환용 심볼릭 링크다. 규칙은 단순하다.

  • 노드 = 디렉터리, 속성 = 파일, 파일 내용 = 속성 값 바이트 그대로 (big-endian 정수, NUL로 끝나는 문자열).
  • 원본 FDT(부트로더가 넘긴 blob)는 /sys/firmware/fdt에 읽기 전용으로 남는다 (root만 읽기 가능).

5.2 예제 7 — /proc/device-tree 둘러보기#

무엇을 확인하나: 게스트 커널이 본 DT의 최상위, 머신 식별(compatible, model), 그리고 부트로더(여기선 QEMU)가 런타임에 채워 넣은 /chosen.

출력에서 볼 것: /chosen에 원본 virt.dts에는 없던 bootargs, linux,initrd-start, linux,initrd-end가 생겼다. QEMU가 -append와 -initrd를 보고 부팅 직전에 DT에 써 넣은 것이다 — U-Boot의 bootm/booti도 똑같이 한다 (C3). 반대로 원본에 있던 rng-seed는 사라졌다: 커널이 early scan에서 난수 시드로 쓴 뒤 fdt_nop_property()로 지운다(drivers/of/fdt.c, "try to clear seed so it won't be found"). 이게 usage-model의 둘째 목적, runtime configuration이다.

5.3 예제 8 — 노드 하나를 바이트 단위로, 그리고 unflatten 전후 비교#

무엇을 확인하나: UART 노드의 속성 파일이 big-endian 바이트 그대로라는 것, 커널이 실제로 받은 FDT 헤더(§4.5 프로그램을 게스트에서 실행), 그리고 unflatten된 트리의 노드·속성 수가 FDT와 맞는지.

출력에서 볼 것:

  • reg 16바이트 = 주소 2셀(00000000 09000000 → 0x0900_0000) + 크기 2셀(00000000 00001000 → 4KB). 루트의 #address-cells = 2, #size-cells = 2가 이 해석을 정한다 (D2).
  • interrupts 12바이트 = 3셀 <0 1 4> = SPI, 1번, level-high.
  • 게스트의 FDT는 structure block이 7048 → 7152, strings가 462 → 507바이트로 커졌다. QEMU가 /chosen에 속성을 추가했기 때문이고, 속성 수도 221 → 223(+bootargs, +initrd 2개, −rng-seed)이다.
  • unflatten된 트리는 디렉터리 57개 = FDT 노드 57개로 정확히 일치한다. 파일은 280개 = 223 + 57인데, 커널이 노드마다 옛 Open Firmware 호환용 name 속성을 하나씩 만들어 붙이기 때문이다 (FDT에는 없다).

5.4 예제 9 — DT의 인터럽트가 /proc/interrupts가 되기까지#

무엇을 확인하나: DT의 <0 1 4>가 커널에서 어떤 번호가 되는지, 그리고 DT 배선(SPI, GPIO)과 PCIe가 스스로 협상한 MSI-X의 차이.

출력에서 볼 것: 한 줄에 번호가 두 개다. 왼쪽 13은 커널 내부의 가상 IRQ 번호(virq), GIC-0 33은 하드웨어 번호(hwirq)다. DT의 SPI 1 → GIC hwirq 33(SPI는 32부터), RTC의 SPI 2 → 34. arch_timer의 27은 PPI 11(PPI는 16부터) — DT /timer의 <1 0x0b ...> 항목이다. GPIO Key Poweroff는 /gpio-keys/poweroff의 gpios = <pl061 3 0>에서 왔다: GIC가 아니라 GPIO 컨트롤러가 인터럽트 부모다. 반면 virtio-net의 MSI-X 3줄은 DT에 한 글자도 없다 — PCI capability로 장치가 스스로 알린 것이다. Don이 펌웨어에서 NVIC_EnableIRQ(33)처럼 다루던 번호를, Linux에서는 DT가 hwirq로 적고 irq domain이 virq로 바꿔 드라이버에 준다 (H 모듈).

5.5 예제 10 — DT로 보드 메모리 맵 만들기#

무엇을 확인하나: /proc/device-tree를 유저 공간 C로 읽어 Don에게 익숙한 "주소 → 장치" 메모리 맵을 만든다. #address-cells/#size-cells를 읽어서 reg를 해석하는 연습이기도 하다.

출력에서 볼 것: SSD 펌웨어의 memory_map.h와 같은 정보가 DT에서 나온다. flash@0과 intc@8000000은 reg에 영역이 2개 있지만 이 프로그램은 첫 번째만 출력한다. 재미있는 점: pcie@10000000 노드의 이름(unit-address 0x1000_0000)과 실제 reg(0x40_1000_0000, 4GB 위의 "highmem ECAM")가 다르다 — QEMU가 생성한 DT의 특이점이다. 커널은 이름이 아니라 reg를 믿고, 그래서 §6의 platform device 이름이 4010000000.pcie가 된다.

6. DT 노드 ↔ platform_device ↔ driver — sysfs로 고리 확인하기#

6.1 직관 — 세 개의 객체, 두 개의 포인터#

DT 노드는 데이터일 뿐 그 자체로는 아무 일도 안 한다. 커널은 노드마다(조건이 맞으면) 디바이스 객체를 만들고, 디바이스는 노드를 가리키는 포인터(dev->of_node)를 갖는다. 드라이버가 등록되면 버스가 디바이스와 드라이버를 짝짓고(compatible ↔ of_match_table, 또는 AMBA ID), 성공하면 dev->driver가 채워지고 probe()가 불린다. sysfs는 이 두 포인터를 심볼릭 링크로 보여 준다.

그림 4 — 위 줄은 커널 메모리 안의 세 객체와 두 포인터, 아래 줄은 그것이 sysfs에 비친 모습이다. 디바이스 디렉터리 안의 of_node·driver 심볼릭 링크가 곧 dev->of_node·dev->driver 포인터다.

6.2 예제 11 — of_node·driver 링크와 uevent 따라가기#

7. 대조: PCI 장치에는 DT 노드가 없다#

7.1 직관#

§1에서 "PCIe는 스스로 말한다"고 했다. 그렇다면 랩에 PCI 장치를 더 꽂아도 DT는 한 글자도 바뀌지 않아야 하고, 커널은 그 장치를 enumeration으로 찾아야 하며, 그 장치의 of_node는 없어야 한다. DT가 아는 것은 host bridge 하나뿐이다.

그림 5 — DT는 출발점(host bridge의 ECAM 주소, 주소 창, 인터럽트 매핑)만 준다. 그 아래 장치들은 커널이 config space를 읽어 스스로 찾는다.

7.2 예제 14 — -device e1000 -device virtio-rng-pci로 장치를 꽂고 config space 읽기#

무엇을 확인하나: QEMU에 PCI 장치 두 개를 더 꽂고, 게스트에서 BusyBox lspci, sysfs, 그리고 config space를 직접 해석하는 C 프로그램으로 들여다본다. 각 장치에 of_node가 있는지도 본다.

출력에서 볼 것:

  • 우리가 꽂은 8086:100e(e1000)와 1af4:1005(virtio-rng) 외에 1af4:1000(virtio-net)이 있다 — QEMU가 -nic을 따로 안 주면 기본으로 넣는 NIC이다. 1b36:0008은 QEMU의 PCIe host bridge 기능(function)이다.
  • 네 장치 모두 of_node: none. root bus(pci0000:00) 디렉터리에도 of_node 링크가 없다(grep 결과 빈 줄). DT 노드를 가진 것은 그 위의 platform 디바이스 4010000000.pcie → /pcie@10000000 하나뿐이다.
  • config space 첫 줄 f4 1a 00 10은 little-endian으로 Vendor 0x1af4, Device 0x1000이다. 같은 게스트의 DT 속성은 big-endian이었다(§5.3). 오프셋 0x20의 0c 00 00 00 + 0x24의 80 00 00 00이 64비트 prefetchable BAR4 = 0x80_0000_0000 — DT의 ranges가 열어 준 64비트 MMIO 창 안에 커널이 배치했다.
  • uevent의 MODALIAS=pci:v...d...는 DT의 of:N...C...와 같은 역할이다. 매칭 키가 compatible 문자열이냐 Vendor/Device ID냐의 차이일 뿐 드라이버 모델은 같다.

예외도 알아 두자. 보드에 납땜된 PCIe 칩(예: 이더넷 MAC)에 MAC 주소나 리셋 GPIO처럼 물어볼 수 없는 정보를 줘야 할 때는 DT의 pcie 노드 아래 자식 노드를 bus/device/function 주소로 적어 연결할 수 있다. 또 6.x에는 CONFIG_PCI_DYNAMIC_OF_NODES(이 랩 커널에서 =y)가 있어 PCI 브리지와 일부 quirk 장치에 DT 노드를 동적으로 만들어 준다 — 대표적인 예가 Raspberry Pi 5의 RP1처럼 "PCIe로 붙지만 내부에 UART·I2C·GPIO 같은 non-discoverable 장치를 잔뜩 품은 칩"이다(drivers/pci/quirks.c에 PCI_DEVICE_ID_RPI_RP1_C0용 of_pci_make_dev_node fixup이 있다). 우리 랩에는 브리지가 없어서 노드가 생기지 않았다.

7.3 예제 15 — PCI 장치를 꽂아도 DT는 그대로#

무엇을 확인하나: 장치 2개를 추가한 부팅에서도 커널이 받은 FDT의 노드 수가 같고, pcie 노드에 자식이 없다는 것.

8. DT가 아닌 것 — 코드도 아니고 정책도 아니다#

8.1 DT는 코드가 아니다#

DT에는 조건문도 반복문도 함수 호출도 없다. 순수한 선언형 데이터다. "리셋 핀을 10ms 내렸다가 올려라" 같은 절차는 DT에 적지 않는다 — DT에는 "리셋 핀은 GPIO1-5, active-low"(reset-gpios = <&gpio1 5 GPIO_ACTIVE_LOW>)라는 사실만 적고, 절차(얼마나 내릴지)는 드라이버 코드가 칩 데이터시트를 보고 정한다. (데이터시트마다 다른 타이밍을 드라이버가 몰라서 속성으로 받는 경우 — 예: reset-assert-us — 도 있지만, 그것도 "하드웨어 사실"의 범주로 binding에 정의된 것이다.)

이 점이 ACPI와 가장 크게 다르다. ACPI의 DSDT에는 AML 바이트코드(메서드 _ON, _OFF, _STA …)가 들어 있고 커널의 AML 인터프리터가 그걸 실행한다. 펌웨어가 OS에 코드를 준다. DT는 그러지 않는다 (§9).

8.2 DT는 드라이버 동작 정책이 아니다#

DT 메인테이너들이 리뷰에서 가장 자주 하는 말이 "DT describes hardware, not configuration"이다. 판단 기준은 "이 값이 보드의 물리적 사실인가, 아니면 소프트웨어가 어떻게 동작할지에 대한 선택인가"다.

8.3 status = "disabled"는 전원 끄기가 아니다#

status = "disabled"는 "커널아, 이 노드로 디바이스를 만들지 마라"라는 뜻이다. 하드웨어 블록의 클록이나 전원을 끄는 것이 아니다. 블록은 부트로더가 켜 둔 상태 그대로 살아 있을 수 있고, 누군가(earlycon처럼) 주소를 직접 알면 여전히 쓸 수 있다. §10에서 실험으로 확인한다. 보통 SoC .dtsi가 모든 블록을 disabled로 선언하고 보드 .dts가 실제로 쓰는 것만 "okay"로 켠다 (D5).

8.4 DT는 드라이버가 아니다#

DT 노드를 아무리 잘 써도 드라이버가 커널에 없으면 아무 일도 안 일어난다(§6.3의 fw-cfg). 반대로 드라이버만 있고 노드가 없으면 probe()가 불리지 않는다. 면접에서 "DT를 고쳤는데 장치가 안 떠요"라고 하면 "드라이버가 빌드됐나(CONFIG_), 모듈이 로드됐나, compatible이 드라이버 테이블과 글자 하나까지 같은가"를 같이 봐야 한다.

9.2 예제 16 — Lima VM은 ACPI 머신이다#

무엇을 확인하나: 이 노트를 쓰는 Lima VM(Apple Virtualization 위 arm64 Ubuntu)은 UEFI + ACPI로 부팅한다. 같은 arm64인데 /proc/device-tree가 없다.

출력에서 볼 것 — 이 출력에는 놀라운 점이 세 개 있다.

  • ACPI 머신에도 FDT가 있다. /sys/firmware/fdt가 560바이트다. arm64의 UEFI 부팅에서 커널의 EFI stub이 UEFI 메모리 맵 위치·명령행을 넘기려고 /chosen만 있는 최소 DT를 만든다. 하드웨어 설명은 하나도 없다.
  • 그런데 /proc/device-tree가 없다. arch/arm64/kernel/setup.c의 setup_arch()는 if (acpi_disabled) unflatten_device_tree(); — ACPI가 켜져 있으면 FDT를 펼치지 않는다. 그래서 of_root가 없고, drivers/of/base.c의 of_core_init()은 /sys/firmware/devicetree 디렉터리만 만들고(그래서 비어 있다) if (of_root) 조건 때문에 /proc/device-tree 링크를 만들지 않는다.
  • 같은 PL061 GPIO, 같은 드라이버, 다른 설명서. QEMU 랩에서는 DT 노드 /pl061@9030000이 9030000.pl061을 만들었고, 여기서는 ACPI 장치 \_PR_.GPIO(_HID = ARMH0061)가 ARMH0061:00을 만들었다. 둘 다 /sys/bus/amba에 있고 둘 다 pl061_gpio 드라이버가 잡았다. 링크만 of_node 대신 firmware_node다(마지막 readlink는 링크가 없어서 아무것도 출력하지 않았다). PCIe host bridge도 DT의 pcie@... 노드 대신 PNP0A08(+ ECAM은 MCFG 테이블)로 설명된다.

DSDT 전체가 974바이트, virt.dtb는 7.5KB다. 숫자만 보면 ACPI가 작지만 ACPI는 장치 대부분을 PCI로 꽂는(lspci로 보면 virtio-net·blk·console·rng 모두 PCI다) 가상 머신이라 설명할 non-discoverable 장치가 거의 없을 뿐이다. 임베디드 SoC는 반대로 non-discoverable 장치 수백 개를 설명해야 하고, ACPI로 그걸 하려면 펌웨어 벤더가 AML까지 맞춰 줘야 한다. 이것이 임베디드 SoC가 DT를 쓰는 현실적 이유다. 서버급 arm64(Ampere, Graviton 등)는 OS 하나로 여러 벤더 하드웨어를 지원해야 해서 ACPI를 택했다 — 자세한 비교는 C8.

10.1 예제 17 — 노드 하나 끄기: .dts 수정과 dtc#

무엇을 확인하나: 랩의 DT를 복사해 UART 노드 하나에 status = "disabled";를 넣고 다시 컴파일한다.

출력에서 볼 것: 컴파일은 성공(rc=0)했지만 경고가 5개씩 나온다. 원인은 우리 수정이 아니라 역변환된 .dts의 한계다. 원래 사람이 clocks = <&apb_pclk>처럼 label로 썼을 자리가 <0x8000>이라는 숫자로 굳어 있어서, dtc가 "이 셀이 phandle이어야 하는데 참조(&label)가 아니라 숫자다"라고 경고한다. 값 자체는 대상 노드의 phandle = <0x8000>과 맞으므로 동작에는 문제가 없다. 실무에서는 역변환한 .dts를 고쳐 쓰지 말고 원본 .dts/.dtsi를 고치는 것이 원칙이다 (D2, D5). 한 줄 수정만 필요하면 컴파일 없이 fdtput -t s d1_virt_small.dtb /pl011@9000000 status disabled로 blob을 직접 고쳐도 된다.

무엇을 확인하나: 대조군 DTB로는 평소처럼 콘솔이 나오고, UART를 끈 DTB로는 무슨 일이 일어나는지.

12. 커널 안에서는 무슨 일이 일어나나#

12.1 부팅부터 probe()까지 — 함수 경로#

이 노트의 실험들이 커널 소스의 어디에 대응하는지 6.18.55 기준으로 정리한다. 함수 이름은 모두 랩의 소스 트리에서 확인했다.

그림 8 — 커널 진입부터 드라이버 probe()까지 DT가 거치는 함수. 주황은 평평한 blob을 직접 읽는 단계, 초록은 트리를 만들고 early 장치를 초기화하는 단계, 파랑·빨강은 디바이스 모델 단계다.

단계별로 보면:

  1. 진입: arm64 부팅 규약(Documentation/arch/arm64/booting.rst)은 "x0 = 시스템 RAM에 있는 DTB의 물리 주소"를 요구한다. head.S가 이 값을 __fdt_pointer에 저장하고, setup_arch()가 setup_machine_fdt(__fdt_pointer) → early_init_dt_scan()을 부른다. 여기서 early_init_dt_verify()가 헤더(magic d00dfeed, 버전)를 검사하고 blob의 CRC를 계산해 둔다.
  2. early scan (drivers/of/fdt.c): 아직 메모리 할당자도 없는 시점이라 평평한 blob을 직접 훑는다. early_init_dt_scan_root()(루트의 cells), early_init_dt_scan_chosen()(bootargs → boot_command_line, initrd 위치, rng-seed 사용 후 NOP 처리), early_init_dt_scan_memory()(device_type = "memory" 노드 → memblock). usage-model의 "runtime configuration"이 여기다.
  3. unflatten: if (acpi_disabled) unflatten_device_tree(); — __unflatten_device_tree()가 blob을 두 번 훑어(크기 계산, 실제 생성) struct device_node/struct property 트리를 만들고 전역 of_root에 매단다. /aliases도 이때 스캔된다(of_alias_scan()).
  4. early 장치: 인터럽트 컨트롤러·클록·타이머는 드라이버 모델이 준비되기 전에 필요하다. 그래서 IRQCHIP_DECLARE, CLK_OF_DECLARE, TIMER_OF_DECLARE 매크로로 링커 섹션에 (compatible, init 함수) 표를 만들어 두고, irqchip_init() → of_irq_init(), of_clk_init(), timer_probe()가 DT를 뒤져 직접 초기화한다. 초기화된 노드에는 OF_POPULATED 표시가 붙어 나중에 platform device가 중복 생성되지 않는다(§6.3의 넷째 부류).
  5. sysfs: driver_init() → of_core_init()이 노드마다 kobject를 만들어 /sys/firmware/devicetree/base를 채우고, of_root가 있으면 /proc/device-tree 링크를 만든다.
  6. populate: arch_initcall_sync(of_platform_default_populate_init) → of_platform_populate() → 노드마다 of_platform_bus_create(). 여기서 걸러진다: compatible 없음 → 건너뜀, of_device_is_available() 거짓(status = "disabled") → 건너뜀, OF_POPULATED → 건너뜀, "arm,primecell" → of_amba_device_create(), 그 밖 → of_platform_device_create_pdata() → of_device_alloc()(노드의 reg·interrupts를 struct resource로 변환 — board file이 손으로 쓰던 그 배열) → of_device_add() → device_add(). 노드가 simple-bus 같은 버스면 자식으로 재귀한다.
  7. 매칭: device_add()든 드라이버 등록(platform_driver_register())이든, 나중에 온 쪽이 버스의 match를 부른다. platform_match()의 순서는 driver_override → OF(of_driver_match_device) → ACPI → id_table → 이름 비교 — §3.5의 smc91x가 세 테이블을 다 가진 이유다. AMBA 버스의 amba_match()는 이때 처음으로 하드웨어의 Peripheral ID 레지스터를 읽는다(amba_read_periphid()). 맞으면 really_probe() → 드라이버의 probe(). 자세한 우선순위와 -EPROBE_DEFER는 D3, G2.

13.1 장면 1 — 센서 키트 bring-up: "IMU가 /sys/bus/iio에 안 보인다"#

i.MX8MP 기반 센서 키트에 ST IMU를 I2C3에 붙였다. 커널은 뜨는데 /sys/bus/iio/devices가 비어 있다. 이 노트의 사슬을 그대로 따라간다.

(이 블록은 실제 보드용 점검 순서다. 랩에는 I2C 장치가 없어 출력은 싣지 않는다.) 판정표: 1)에서 노드가 없으면 .dts 문제, 노드는 있는데 status가 disabled면 보드 .dts에서 okay로 켜야 한다(부모 버스 노드도!). 2)에서 디바이스가 없으면 부모 I2C 컨트롤러 드라이버가 probe 안 됐을 가능성. 3)에서 driver 링크가 없으면 드라이버 미빌드(CONFIG_IIO_ST_LSM6DSX), 모듈 미로드, 또는 compatible 오타. 4)에서 probe 실패 메시지(예: WHO_AM_I 불일치)가 보이면 이제야 하드웨어·배선 문제다 — Don의 로직 분석기가 나설 차례.

13.2 장면 2 — 같은 제품, 보드 리비전 두 개#

센서 키트 Rev A는 IMU 인터럽트가 GPIO1_IO12, Rev B는 GPIO4_IO03으로 바뀌었다. board file 시대라면 커널을 두 벌 빌드했겠지만, 지금은 sensorkit-reva.dts와 sensorkit-revb.dts(공통 부분은 sensorkit.dtsi)를 만들고 커널 이미지는 하나로 간다. 부트로더가 보드의 EEPROM이나 strap 핀으로 리비전을 읽어 맞는 .dtb를 고르거나(U-Boot의 FIT 이미지 configuration), 공통 .dtb에 리비전별 overlay를 얹는다 (D6). 펌웨어로 치면 "보드 ID GPIO를 읽어서 핀맵 테이블을 고르는 것"을 부트로더 + 데이터로 하는 셈이다.

13.3 장면 3 — "부팅 로그가 아예 안 나온다"#

§10의 실험이 그대로 현장 시나리오다. 새 보드에서 시리얼이 조용하면:

  • 먼저 earlycon(또는 earlycon=<드라이버>,<주소>)을 커널 명령행에 넣는다. 이걸로 로그가 나오면 커널은 살아 있고 DT의 UART 노드(status, compatible, /chosen/stdout-path, /aliases의 serial0)나 pinctrl 쪽 문제다.
  • earlycon으로도 안 나오면 더 앞 단계다 — 부트로더가 DTB 주소를 제대로 넘겼나(x0), DTB magic이 맞나, 커널 이미지 로드 주소가 맞나 (C1, C3).
  • U-Boot 프롬프트에서 fdt addr ${fdt_addr_r}; fdt print /serial@...로 커널에 넘기기 직전의 DT를 확인할 수 있다 (C3).

13.4 장면 4 — PCIe 칩이 보드에 납땜돼 있을 때#

Don이 잘 아는 영역과의 접점이다. Jetson Orin 캐리어 보드에 PCIe Wi-Fi/5G 모듈이나 NVMe를 붙이면 그 장치 자체는 DT가 필요 없다(§7). 하지만 그 장치의 전원 레일·PERST# 리셋 GPIO·CLKREQ#·레퍼런스 클록은 SoC 쪽 PCIe 컨트롤러 노드의 속성(reset-gpios, vpcie3v3-supply 같은 이름 — 컨트롤러 binding마다 다르다)으로 DT에 적어야 한다. "링크가 안 올라온다(LTSSM이 Detect에서 멈춘다)"는 증상의 상당수가 이 DT 속성 누락이다. enumeration은 discoverable이지만, enumeration이 시작될 수 있는 조건은 non-discoverable이다.

15. 면접에서 이렇게 말한다#

Q. What is a Device Tree and why does Linux use it?

A. 하드웨어 중 PCIe·USB처럼 스스로 정체를 밝히지 못하는 장치 — SoC 안의 MMIO 주변장치, I2C/SPI 센서, GPIO·인터럽트 배선 — 를 커널에 알려 주는 데이터 구조다. 예전 ARM은 이걸 보드마다 C 코드(board file)로 커널에 박아서 보드마다 커널을 따로 빌드했는데, DT는 그 설명을 커널 밖의 .dtb로 빼서 부트로더가 넘기게 했다. 그래서 커널 하나로 수많은 보드를 지원한다.

A Device Tree is a data structure that describes the hardware the kernel cannot discover by itself — memory-mapped SoC peripherals, I2C and SPI devices, GPIO and interrupt wiring, clocks and regulators. Before DT, 32-bit ARM hard-coded this in per-board C files under arch/arm/mach-*, which meant lots of duplicated code and often a separate kernel per board. With DT the description lives outside the kernel: the .dts is compiled by dtc into a .dtb, the bootloader passes its address to the kernel — x0 on arm64 — and the kernel unflattens it and creates platform devices that drivers bind to via compatible strings. One kernel image, many boards.

꼬리 질문: "그럼 DT에는 뭘 적고 뭘 안 적나요?" → 하드웨어 사실만, 드라이버 정책은 안 적는다(§8).

Q. Why don't PCIe devices need Device Tree nodes?

A. PCIe는 discoverable이라서다. 커널이 config space를 읽으면 장치가 Vendor/Device ID, class, BAR 크기, MSI capability를 직접 답한다. 다만 host bridge 자체 — ECAM 주소, 주소 창, INTx 매핑, MSI 컨트롤러 — 는 물어볼 수 없어서 DT에는 pcie 노드 하나가 있다. QEMU 랩에서 e1000을 꽂아도 DT 노드 수는 그대로였고 PCI 장치들의 of_node는 없었다.

PCIe is self-describing: once the kernel can reach config space it enumerates bus, device and function, reads vendor and device IDs, the class code, sizes the BARs and finds MSI capabilities, so drivers match on PCI IDs. What is not discoverable is the root complex itself — where ECAM lives, the memory and I/O windows, how legacy INTx maps to the GIC, which MSI controller to use — so the DT has one host-bridge node and nothing below it. The exception is soldered-down PCIe chips that need extra non-discoverable info like a MAC address or a reset GPIO; those can get child nodes.

꼬리 질문: "PCIe 링크가 안 올라올 때 DT에서 뭘 보나요?" → 컨트롤러 노드의 reset GPIO(PERST#), 전원 레일, 클록, status(§13.4).

Q. Walk me through what happens from the .dts file to a driver's probe() being called.

A. .dts/.dtsi를 dtc가 big-endian 바이너리 .dtb로 컴파일한다. 부트로더가 그걸 RAM에 올리고 /chosen에 bootargs·initrd를 써 넣은 뒤 주소를 x0로 넘긴다. 커널은 early scan으로 메모리와 명령행을 읽고, unflatten_device_tree()로 device_node 트리를 만들고, GIC·클록·타이머는 *_OF_DECLARE로 먼저 초기화한다. arch_initcall_sync에서 of_platform_populate()가 compatible이 있고 status가 okay인 노드마다 platform_device(PrimeCell이면 amba_device)를 만들고 reg·interrupts를 resource로 바꾼다. 버스의 match가 compatible과 드라이버의 of_match_table을 비교해 맞으면 probe()가 불린다.

dtc compiles the source into a flattened blob. The bootloader loads it, patches /chosen with bootargs and the initrd location, and jumps to the kernel with the blob's physical address in x0. Early in setup_arch the kernel scans the flat blob for memory and the command line, then unflattens it into a tree of device_node structures. Interrupt controllers, clocks and timers are initialized early through IRQCHIP_DECLARE, CLK_OF_DECLARE and TIMER_OF_DECLARE. At arch_initcall_sync, of_platform_populate walks the tree and creates a platform device for every available node with a compatible string, converting reg and interrupts into resources. When the device and driver meet on the bus, platform_match tries the OF match first, and on success the driver's probe runs. In sysfs you can see the result as the of_node and driver symlinks.

꼬리 질문: "status = "disabled"면 어디서 걸러지나요?" → populate 단계의 of_device_is_available() (§10.3, §12.1).

Q. How would you debug a device that is in the Device Tree but whose driver never probes?

A. 사슬을 순서대로 끊어 본다. /proc/device-tree에 노드가 있고 status가 okay인지, /sys/bus/<bus>/devices에 디바이스가 만들어졌는지, of_node 링크가 맞는 노드를 가리키는지, driver 링크가 있는지, uevent의 OF_COMPATIBLE이 드라이버 테이블과 글자까지 같은지, 드라이버가 빌드·로드됐는지 본다. 그다음에야 dmesg의 probe 에러나 -EPROBE_DEFER(의존 자원 대기)를 본다.

I walk the chain. First, is the node in /proc/device-tree and is its status okay — including its parent bus. Second, was a device created under /sys/bus/platform or i2c, and does its of_node link point to the right node. Third, does it have a driver link; if not, compare OF_COMPATIBLE in the uevent with the driver's of_device_id table, and check that the driver is actually built and loaded. Only then do I look at dmesg for probe errors or deferred probing, and at /sys/kernel/debug/devices_deferred. That order separates DT problems from driver problems from hardware problems quickly.

Q. What's the difference between Device Tree and ACPI?

A. 둘 다 non-discoverable 하드웨어를 OS에 알려 주는 방법이다. DT는 순수 데이터이고 보드 개발자가 쓰며 임베디드 ARM·RISC-V에서 쓴다. ACPI는 펌웨어가 제공하는 테이블에 AML이라는 실행 코드까지 들어 있어서 전원 관리 같은 절차를 펌웨어가 정의하고, x86과 arm64 서버에서 쓴다. 장치 식별도 compatible 대 _HID다. 드라이버는 device_property_* fwnode API로 쓰면 둘 다 지원할 수 있다.

Both describe non-discoverable hardware to the OS. Device Tree is pure declarative data, usually written by the board developer and shipped with the kernel or BSP; it dominates embedded ARM and RISC-V. ACPI comes from the platform firmware and includes AML bytecode the OS executes, so firmware can own procedures like power-state transitions; it is the norm on x86 and on arm64 servers. Devices are identified by compatible strings in DT and by _HID in ACPI. A driver written against the fwnode device_property API can support both. On an ACPI-booted arm64 machine Linux does not even unflatten the tiny FDT from the EFI stub, so there is no /proc/device-tree.

꼬리 질문: "임베디드에서 ACPI를 안 쓰는 이유는?" → SoC마다 수백 개의 비발견 장치를 펌웨어 벤더가 AML까지 맞춰야 하고, 커널 트리와 함께 진화하는 DT가 개발·디버깅 흐름에 맞다(§9.2).

Q. What is the history behind Device Tree on ARM?

A. DT는 Open Firmware에서 왔고, 2005년 PowerPC가 FDT 형식을 만들어 펌웨어 없이도 쓰게 했다. ARM은 board file로 버티다가 SoC·보드가 폭발하면서 arch/arm이 감당이 안 됐고, 2011년 Linus가 ARM 플랫폼 코드의 중복과 churn을 공개적으로 강하게 비판한 것을 계기로 arm-soc 정리와 DT 전면 도입이 진행됐다. arm64는 처음부터 board file 없이 DT 또는 ACPI만 쓴다.

DT comes from Open Firmware on SPARC and PowerPC. In 2005 PowerPC Linux introduced the flattened form so boards without Open Firmware could pass a blob. ARM meanwhile relied on board files, and by around 2011 the explosion of SoCs made arch/arm unmaintainable — Linus publicly complained about the churn and duplication, which pushed the community to consolidate through the arm-soc tree and require DT for new platforms. arm64 never had board files; it boots with DT or ACPI only.

Q. Can you change the hardware description without rebuilding the kernel?

A. 예. 그게 DT의 핵심 가치다. .dts만 고쳐 dtc로 .dtb를 다시 만들고 부트로더가 그걸 넘기면 된다. 한 줄이면 fdtput으로 blob을 직접 고칠 수도 있고, 확장 보드는 overlay로 얹는다. 랩에서 같은 Image로 UART 노드만 끈 DTB를 부팅해 차이를 확인했다.

Yes, that is the whole point. You edit the .dts, recompile just the .dtb with dtc, and have the bootloader pass the new blob — the kernel image is unchanged. For a one-line tweak you can even patch the blob with fdtput, and for add-on boards you apply overlays. In my QEMU lab I booted the identical kernel with a DTB where only the UART node was disabled: the system booted fine but the UART device was never created, so there was no ttyAMA0 and no user-space console — while earlycon still printed kernel logs because it writes the registers directly.

18. 요약 & 체크리스트#

PCIe·USB 장치는 config space와 descriptor로 정체와 자원을 스스로 밝히지만, SoC 안의 MMIO 주변장치, I2C·SPI 센서, GPIO·인터럽트 배선, 클록·전원 같은 것들은 물어볼 방법이 없다. 32비트 ARM은 이 정보를 보드마다 C 코드(board file의 platform_device·resource)로 커널에 박았고, 보드 폭발과 2011년 Linus의 공개 비판을 거치며 Open Firmware·PowerPC에서 온 Device Tree로 옮겨 갔다. DT는 순수 데이터다: .dts를 dtc가 big-endian FDT(.dtb)로 만들고, 부트로더가 /chosen을 채워 그 주소를 x0로 넘기면, 커널이 early scan → unflatten → early 장치 초기화 → populate(platform_device/amba_device) → 드라이버 매칭 → probe()로 디바이스 모델을 세운다. sysfs의 of_node·driver 링크와 uevent가 이 사슬을 보여 주고, status = "disabled"는 하드웨어를 끄는 게 아니라 디바이스 생성을 막을 뿐이다. ACPI는 같은 문제를 펌웨어 테이블 + AML 코드로 푸는 x86·서버 쪽 답이다.
