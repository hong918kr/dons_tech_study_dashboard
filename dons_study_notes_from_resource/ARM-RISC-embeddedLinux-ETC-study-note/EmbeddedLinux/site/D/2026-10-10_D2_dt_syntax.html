0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 컨트롤러 펌웨어를 쓸 때 하드웨어 정보는 어디 있었나? soc_regs.h 같은 헤더에 #define UART0_BASE 0x40001000, #define NAND_IRQ 37이 박혀 있고, 보드가 바뀌면 헤더를 바꿔 펌웨어를 다시 빌드했다. 하드웨어 기술(description)과 코드가 한 덩어리였다.

Linux는 이걸 갈라놓는다. 커널 이미지 하나(Image)는 i.MX8, AM62, Jetson, QEMU virt 어디서나 같다. "이 보드에는 UART가 0x9000000에 있고 인터럽트는 SPI 1번이며 클록은 24 MHz다" 같은 정보는 Device Tree(DT) 라는 별도의 데이터 파일이 들고 온다. 사람이 쓰는 텍스트가 .dts/.dtsi(Device Tree Source), 이걸 dtc(Device Tree Compiler)로 컴파일한 바이너리가 .dtb(Device Tree Blob, 형식 이름은 FDT = Flattened Device Tree)다. 부트로더가 .dtb를 RAM에 올리고 그 주소를 커널에 넘긴다(arm64는 레지스터 x0).

그림 1 — DT는 빌드 호스트에서 컴파일되고, 부팅 때 부트로더가 커널에 넘긴다. 커널은 그걸 포인터 트리로 풀어서 디바이스를 만들고 sysfs로 보여 준다.

이 노트(D2)는 그 데이터 파일의 문법을 다룬다. "드라이버가 어떻게 매칭되나"(D3), "인터럽트·클록·GPIO를 어떻게 기술하나"(D4), ".dtsi/.dts 계층과 빌드"(D5)는 뒤 노트의 일이다. 여기서는 언어 자체를 손에 익힌다:

  • 노드·프로퍼티·값 타입을 읽고 쓴다 (§1–§2)
  • label·phandle·경로로 노드끼리 연결한다 (§3), 특별한 노드들 (§4)
  • 주소: #address-cells/#size-cells로 reg를 읽고 (§5), ranges로 버스를 넘어 번역한다 (§6) — Don의 버스 주소 맵 경험이 그대로 쓰이는 부분
  • 덮어쓰기·삭제·include (§7–§8), dtc 경고 (§9)
  • .dtb 바이너리를 hexdump로 뜯고, C로 직접 파싱하고, libfdt를 쓴다 (§10–§13)
  • QEMU 랩에서 직접 고친 dtb로 부팅해 커널이 본 값을 확인한다 (§14)

실행 환경: 모든 출력은 Lima VM elinux(aarch64, uname -r = 7.0.0-38-generic, gcc 15.2, DTC 1.7.2(device-tree-compiler 1.7.2-2ubuntu1))와 그 안의 공용 QEMU 랩(QEMU 10.2.1 virt, cortex-a57, 512 MB, 게스트 커널 Linux 6.18.55)에서 실제로 돌린 결과다. 작업 디렉터리는 VM의 /var/tmp/D2/, 소스는 Mac의 ~/.elinux_scratch/D2/(VM에서 /Users/donh/.elinux_scratch/D2/로 보인다). 이후 명령에서 S=/Users/donh/.elinux_scratch/D2로 줄여 쓴다.

1. 노드 — 트리의 뼈대#

1.1 직관#

DT는 이름 붙은 노드들의 트리이고, 각 노드에 이름=값 프로퍼티가 매달려 있다. 파일 시스템과 똑같이 생각하면 된다: 노드 = 디렉터리, 프로퍼티 = 파일. 실제로 커널은 부팅 후 DT를 정확히 그 모양으로 /proc/device-tree(= /sys/firmware/devicetree/base)에 보여 준다(§14).

노드 하나의 해부도:

그림 2 — 노드 한 개의 해부도. 윗줄은 노드 이름의 세 부분, 아래는 프로퍼티와 그 의미. 값 <...>는 32비트 셀 배열이고, 몇 개씩 묶어 읽을지는 부모 노드가 정한다(§5).

1.2 정의 — 노드 이름 규칙#

  • 형식: node-name@unit-address. node-name은 1~31자, 영문 대소문자·숫자·, . _ + -. 기능을 나타내는 generic 이름을 쓰라는 것이 DT 스펙 권고다(serial, i2c, ethernet, gpio, memory, cpu). 칩 이름(pl011)이 아니다. 단, QEMU가 만든 virt DT는 이 권고를 안 지키고 pl011@9000000처럼 쓴다 — 동작에는 문제없다.
  • @unit-address: 노드가 부모 버스 주소 공간에서 차지하는 첫 주소. reg의 첫 주소와 같아야 한다(다르면 dtc 경고, §9). 주소가 없는 노드(chosen, aliases, cpus)는 @ 없이 쓴다.
  • 같은 부모 아래에서 이름(+unit-address)은 유일해야 한다. serial@9000000과 serial@9040000은 공존 가능.
  • 경로(path): 루트 /부터 이름을 /로 이은 것. 예: /soc@10000000/i2c@1000/imu@68. 커널 로그·sysfs·fdtget이 다 이 경로로 노드를 가리킨다.
  • unit-address는 16진수, 0x 없이: serial@9000000(O), serial@0x9000000(X).

1.3 파일 맨 위 두 줄#

/dts-v1/;이 없으면 dtc는 옛 문법(v0)으로 읽으려 하고 경고를 낸다. /memreserve/는 FDT 헤더 뒤의 "memory reservation block"으로 들어간다(§10). 요즘은 /reserved-memory 노드를 더 많이 쓴다(D4).

2. 프로퍼티와 값 타입#

2.1 직관 — "dtb에는 타입이 없다"#

DT 프로퍼티 값은 결국 바이트 배열이다. .dts 문법이 여러 가지 모양(문자열, 셀, 바이트)을 제공하지만, .dtb에 들어가는 것은 "이름, 길이, 바이트들"뿐이다. 어떻게 해석할지는 읽는 쪽(드라이버, 바인딩 문서)이 안다. Don의 레지스터 덤프와 같다 — 0x12345678이 주소인지 비트 필드인지는 데이터시트를 봐야 안다.

2.2 예제 1 — 모든 타입을 컴파일하고 되돌려 보기#

무엇을 확인하나: 타입별 문법을 dtc로 컴파일한 뒤, fdtdump와 dtc -I dtb -O dts(역컴파일)로 되돌리면 무엇이 남고 무엇이 사라지는지 본다.

출력에서 볼 것:

  • u64-two-cells(/bits/ 64)와 u64-manual(셀 2개)이 완전히 같은 바이트가 됐다. 64비트 값 = 상위 셀 + 하위 셀. reg에서 64비트 주소를 셀 2개로 쓰는 이유다(§5).
  • bytes = [de ad be ef]가 <0xdeadbeef>로 돌아왔다. 길이가 4의 배수이면 역컴파일러는 셀이라고 추측한다. 타입 정보가 없다는 증거다.
  • mixed는 61 62 00 | 00 00 00 01 | ff 8바이트가 그냥 이어졌다. 문자열 뒤에 정렬 패딩이 없다. 그래서 역컴파일러는 이걸 셀 2개 <0x61620000 0x1ff>로 오해한다. 혼합 프로퍼티는 가능하지만 쓰지 않는 게 좋다.
  • label d2_props:가 사라졌다. label은 소스 전용이다(-@ 옵션을 주면 __symbols__ 노드로 남길 수 있다, §3.3).
  • 숫자는 dtb에 0x1이든 1이든 똑같이 들어간다. 10진수도 쓸 수 있다: clock-frequency = <400000>;.

3. label, phandle, 경로 — 노드끼리 연결하기#

3.1 직관 — "포인터가 필요하다"#

인터럽트 컨트롤러는 하나인데 디바이스 여러 개가 그걸 가리켜야 한다. 클록 공급자 하나를 UART·SPI·I2C가 공유한다. 트리 구조만으로는 이 "다대일 연결"을 표현할 수 없다. 그래서 DT에는 포인터가 있다:

  • phandle: 노드에 붙는 32비트 정수 ID. 노드 안에 phandle = <N>; 프로퍼티로 저장된다. 다른 노드는 이 숫자를 셀로 적어 가리킨다. C로 치면 "주소 대신 쓰는 핸들".
  • label: 소스에서 사람이 쓰는 이름 uart0:. dtc가 컴파일할 때 phandle 숫자로 바꿔 준다.
  • <&label> (꺾쇠 안) → phandle 숫자 (4바이트).
  • &label (꺾쇠 밖, 값 자리) → 경로 문자열 (예 "/soc@10000000/serial@2000").
  • &{/full/path} → label이 없는 노드를 경로로 지정.

3.2 예제 2 — label·phandle·경로 참조가 dtb에서 무엇이 되나#

무엇을 확인하나: 같은 label을 <&...>와 &...로 썼을 때 하나는 숫자, 하나는 문자열이 되는 것과, phandle이 참조된 노드에만 자동 생성되는 것을 본다.

출력에서 볼 것:

  • interrupt-parent = <&intc>가 <0x01>이 되고, 대상 노드 interrupt-controller@0에 phandle = <0x01>;이 새로 생겼다. <&...>로 참조되지 않은 uart0, cpu0에는 phandle이 없다. dtc는 필요한 노드에만 1부터 번호를 매긴다.
  • stdout-path = &uart0와 serial0 = &uart0은 문자열 경로가 됐다. 같은 label이라도 꺾쇠가 있느냐 없느냐로 결과 타입이 다르다.
  • 역컴파일 결과에는 label이 없다. 사람이 다시 읽기 어려운 이유다 — 벤더 보드에서 /proc/device-tree를 역컴파일하면 clocks = <0x8000> 같은 숫자 투성이가 된다. 그 숫자를 따라가려면 phandle = <0x8000>인 노드를 grep한다.

3.3 예제 3 — dtc -@: label을 dtb에 남기기#

무엇을 확인하나: overlay(D6)가 base dtb의 label을 찾을 수 있도록 dtc가 __symbols__ 노드를 만드는 것을 본다.

출력에서 볼 것: __symbols__는 "label → 경로" 표다. 크기가 1122 → 1351바이트로 20% 늘었다. 커널 빌드가 overlay를 붙일 base dtb에만 -@를 주는 이유다(§15에서 실제 보드 dtb로 측정).

3.4 phandle 셀 뒤에 붙는 "인자" — 미리 보기#

clocks = <&clk 3>, gpios = <&gpio1 5 0>처럼 phandle 뒤에 숫자가 더 붙는 경우가 많다. 그 개수는 가리켜지는 쪽의 #clock-cells, #gpio-cells가 정한다. QEMU virt의 pl061@9030000은 #gpio-cells = <0x02>라서 gpio-keys의 gpios = <0x8004 0x03 0x00>은 "phandle 0x8004(= pl061) + 셀 2개(핀 3, 플래그 0)"로 읽는다. 이 "specifier" 패턴은 D4에서 자세히 본다.

/chosen은 실제 하드웨어가 아니다. 부트로더가 커널에 넘기는 파라미터 상자다. Don의 펌웨어로 치면 부트 ROM이 메인 펌웨어에 넘기던 "boot info 구조체"다. U-Boot와 QEMU는 dtb를 넘기기 직전에 /chosen을 고쳐 쓴다:

4.1 예제 4 — QEMU가 /chosen에 무엇을 써 넣었나 (게스트 안)#

무엇을 확인하나: 랩의 기본 virt DT로 부팅한 뒤 게스트에서 /chosen과 /memory를 읽는다. 원래 virt.dts의 /chosen에는 stdout-path, rng-seed, kaslr-seed만 있었다.

출력에서 볼 것:

  • bootargs, linux,initrd-start, linux,initrd-end는 원래 virt.dts에 없었다. QEMU가 -append와 -initrd를 보고 써 넣었다. U-Boot도 bootm/booti 때 똑같이 한다(C 모듈). initrd는 0x48000000부터 0x48128284까지 올라와 있다(값은 initramfs 크기에 따라 다르다).
  • rng-seed가 사라졌다. 커널은 early_init_dt_scan_chosen()(drivers/of/fdt.c)에서 rng-seed를 엔트로피로 쓰고 fdt_nop_property()로 지운다 — 같은 시드가 /proc로 새지 않게.
  • memory@40000000/reg는 16바이트 = 셀 4개 = 주소 2셀(0x0_40000000) + 크기 2셀(0x0_20000000 = 512 MiB). §5의 주제다.
  • name 파일은 dtb에 없는 프로퍼티다. 커널이 unflatten할 때 노드 이름으로 만들어 넣는다(옛 Open Firmware 호환).

4.2 /aliases와 stdout-path#

/aliases의 이름은 커널 드라이버가 디바이스 번호를 정할 때 쓴다: serial0 = "/pl011@9000000"이면 그 UART가 ttyAMA0이 된다(of_alias_get_id()). 센서 키트 보드에서 "UART 순서가 바뀌어서 GNSS가 ttyS2에서 ttyS1이 됐다" 같은 사고는 aliases로 막는다.

stdout-path는 "콘솔로 쓸 디바이스"다. 경로 대신 alias 이름을 쓰고 뒤에 옵션을 붙일 수 있다: stdout-path = "serial0:115200n8";. 커널은 console= 인자가 없으면 이걸로 earlycon/콘솔을 정한다.

5. #address-cells / #size-cells — reg 해석하기#

5.1 직관 — "숫자를 몇 개씩 끊어 읽나"#

reg = <0x0 0x9000000 0x0 0x1000>만 보면 이게 "주소 4개"인지, "주소 1개 + 크기 1개가 두 쌍"인지, "64비트 주소 + 64비트 크기 한 쌍"인지 알 수 없다. 셀은 그냥 32비트 숫자들의 나열이기 때문이다. 그래서 부모 노드가 끊는 법을 알려 준다:

  • #address-cells = <N>: 내 자식의 reg에서 주소 하나가 셀 N개.
  • #size-cells = <M>: 크기 하나가 셀 M개.
  • reg는 (주소, 크기) 쌍의 배열. 길이는 반드시 (N+M) × 4 × 쌍 개수 바이트.

핵심은 "자식의 reg를 해석하는 규칙은 부모가 갖고 있다" 는 것이다. 내 노드에 쓴 #address-cells는 내 reg가 아니라 내 자식들의 reg를 위한 것이다. 이걸 헷갈리면 reg_format 경고(§9)를 만난다.

Don의 경험으로 번역하면: 부모 = 버스. 버스마다 주소 폭이 다르다. AXI는 64비트 주소(2셀), APB 슬레이브 내부 오프셋은 32비트(1셀), I2C는 7비트 슬레이브 주소(1셀, 크기 없음 0셀), PCI는 "공간 종류 플래그 + 64비트"(3셀)이다.

그림 3 — reg 해석의 실제 예. 루트가 2/2이므로 memory의 reg 셀 4개는 64비트 주소 하나 + 64비트 크기 하나. 아래 표는 부모 버스 종류별 셀 개수.

6. ranges — 버스를 넘는 주소 번역#

6.1 직관 — "브리지의 주소 디코더"#

Don은 PCIe에서 이걸 매일 봤다: 디바이스 BAR 주소(PCI 버스 주소)와 CPU가 보는 물리 주소가 다를 수 있고, 루트 컴플렉스의 outbound window가 그 사이를 변환한다. SoC 내부도 마찬가지다. AXI → APB 브리지, 서브시스템 인터커넥트, 레거시 VideoCore 버스(Raspberry Pi) — 자식 버스 주소 공간이 부모 주소 공간의 어딘가에 매핑된다.

ranges는 그 매핑 표다. 버스 노드(자식들을 가진 노드)에 쓴다:

읽는 법: "내 안쪽 주소 child부터 length만큼은, 바깥 주소 parent부터에 해당한다". 번역식은 parent_addr = addr - child + parent.

세 가지 경우를 구분해야 한다:

ranges 상태뜻예
ranges = <...>; (값 있음)표대로 번역SoC 버스, PCI 호스트
ranges; (빈 값)1:1 매핑 — 주소 그대로 통과GIC 노드(v2m 자식), i.MX bus@30800000
없음번역 불가 — 자식 주소는 CPU 주소 공간이 아니다I2C·SPI 버스 (자식 reg = 슬레이브 주소)

마지막 줄이 중요하다. I2C 컨트롤러 노드에는 ranges가 없다. 그래서 imu@68의 0x68은 CPU가 load/store할 수 있는 주소가 아니다 — 커널도 이 노드에는 MMIO 자원을 만들지 않는다. "번역 가능한가"가 곧 "메모리 매핑된 디바이스인가"다.

6.2 손으로 번역해 보기 — 2단 버스#

QEMU 랩에서 부팅할 테스트 DT에 이런 2단 버스를 넣었다(§14에서 전체 파일). 바깥 d2-bus는 안쪽 주소 0x80000000부터를 CPU 주소 0x0b000000으로 내리고, 그 안의 d2-sub는 자기 주소 0부터를 d2-bus 주소 0x80040000으로 올린다.

d2-dev의 reg 주소 0x100을 CPU 물리 주소로 올려 보자.

  1. d2-dev의 부모 d2-sub가 1/1이므로 reg = <0x100 0x10>은 주소 0x100, 크기 0x10.
  2. d2-sub의 ranges = <0x0 0x80040000 0x1000>: 0x100은 [0x0, 0x1000) 안에 있다 → 0x100 - 0x0 + 0x80040000 = 0x80040100 (이제 d2-bus 주소 공간).
  3. d2-bus의 ranges = <0x80000000 0x0 0x0b000000 0x100000>: 0x80040100은 [0x80000000, 0x80100000) 안 → 0x80040100 - 0x80000000 + 0x0b000000 = 0x0b040100 (이제 루트 = CPU 물리 주소 공간).
  4. 루트에 도달. CPU 물리 주소 = 0x0b040100.

그림 4 — ranges를 따라 두 번 번역해 CPU 물리 주소에 도달한다. 커널의 of_translate_address()가 정확히 이 루프를 돈다.

이 결과는 §12에서 libfdt로 짠 C 번역기로, §14에서 실제 커널이 만든 디바이스 이름 b040100.d2-dev로 두 번 확인한다.

6.5 dma-ranges — 반대 방향 (짧게)#

ranges는 CPU → 디바이스(CPU가 레지스터에 접근할 때) 방향이다. 반대로 디바이스가 버스 마스터로 메모리에 접근할 때(DMA) 디바이스가 보는 주소와 CPU 물리 주소가 다를 수 있다. 이걸 dma-ranges가 같은 형식(child, parent, size)으로 적는다.

RPi 4의 dma-ranges = <0xc0000000 0x00 0x00 0x40000000>: "이 버스의 DMA 마스터가 0xc0000000을 내보내면 ARM 물리 0x0이다, 1 GiB까지". 레거시 DMA 엔진은 RAM 첫 1 GiB만 볼 수 있고 그것도 0xc0000000 별칭으로 본다는 뜻이다. 커널은 이걸 of_dma_get_range()(drivers/of/address.c)로 읽어 dev->dma_range_map에 넣고, dma_map_single()이 돌려주는 DMA 주소에 자동으로 반영한다. Don이 SSD에서 "DMA 엔진은 SRAM을 다른 주소로 본다"며 매크로로 변환하던 일을 커널 DMA API가 DT 정보로 해 준다. 자세한 건 DMA 노트(F/H 모듈)에서 다룬다.

  • rc=0: 경고만으로는 dtb가 만들어진다. 이게 함정이다 — 잘못된 dtb가 조용히 보드에 올라간다.

10. FDT 바이너리 포맷 — .dtb 한 바이트씩#

10.1 직관 — 왜 "flattened"인가#

메모리 안의 트리는 포인터로 연결되지만, 부트로더가 커널에 넘기려면 포인터 없는 한 덩어리여야 한다(커널이 어디에 올릴지 모르고, MMU도 아직 꺼져 있다). FDT는 트리를 깊이 우선 순회한 토큰 스트림으로 직렬화한 것이다. Don의 펌웨어로 치면 "TLV(type-length-value) 레코드를 이어 붙인 설정 블롭"과 거의 같다.

구조는 네 블록:

  1. header (40바이트, v17): 매직·크기·각 블록 오프셋. 모든 필드 big-endian u32.
  2. memory reservation block: (address u64, size u64) 쌍들, (0, 0)으로 끝. /memreserve/가 들어간다.
  3. structure block: 토큰 스트림 — FDT_BEGIN_NODE(1) + 이름, FDT_PROP(3) + len + nameoff + 값, FDT_END_NODE(2), FDT_NOP(4), FDT_END(9). 모두 4바이트 정렬.
  4. strings block: 프로퍼티 이름들을 NUL로 이어 붙인 것. PROP 토큰은 이름 대신 이 블록 안의 오프셋(nameoff)을 쓴다 — compatible, reg 같은 이름이 수백 번 나와도 한 번만 저장된다.

손으로 해석:

그림 5 — FDT의 네 블록과 structure 블록 토큰. 노드 이름은 structure 블록 안에 직접, 프로퍼티 이름은 strings 블록에 한 번만 두고 오프셋으로 가리킨다.

10.3 왜 virt.dtb는 1 MiB인가 — totalsize와 빈 공간#

내용은 struct 7048바이트 + strings 462바이트뿐인데 totalsize가 1 MiB다. QEMU가 virt DT를 1 MiB 버퍼 안에서 만들고, 그 버퍼 크기를 그대로 totalsize로 기록했기 때문이다. 끝의 빈 공간은 나중에 프로퍼티를 추가할 여유다 — 부트로더가 /chosen에 bootargs를 넣으려면 dtb 안에 공간이 있어야 한다. U-Boot도 fdt resize나 fdt_open_into()로 공간을 늘린 다음 고친다. dtc에는 -p <바이트>(padding)나 -S <크기> 옵션이 같은 목적이다. 또 off_mem_rsvmap이 dtc 출력처럼 0x28(40)이 아니라 0x30(48)인 것은 QEMU가 쓰는 libfdt의 fdt_create()가 reservation 블록을 16바이트(엔트리 크기) 경계에 맞추기 때문이다. 둘 다 스펙상 유효하다 — 읽는 쪽은 반드시 헤더의 오프셋을 따라가야 하고, "헤더 바로 뒤"라고 가정하면 안 된다.

14.1 테스트 DT#

Q. What do #address-cells and #size-cells mean, and how is reg parsed?

A. 둘 다 자식 노드의 reg 를 어떻게 끊어 읽을지 정하는 부모의 프로퍼티다. #address-cells는 주소 하나가 32비트 셀 몇 개인지, #size-cells는 크기가 몇 개인지. reg는 (주소, 크기) 쌍의 배열이다. 64비트 SoC 루트는 보통 2/2라서 reg = <0x0 0x9000000 0x0 0x1000>이 주소 0x9000000, 크기 4 KB 한 쌍이다. I2C 버스는 1/0이라 reg = <0x68>은 슬레이브 주소만이다. 기본값은 2/1이지만 기대지 말고 항상 쓴다.

#address-cells and #size-cells live on the parent and tell you how to slice the children's reg property — how many 32-bit big-endian cells make up one address and one size. reg is just an array of address/size pairs. On a 64-bit SoC the root is usually 2 and 2, so <0x0 0x9000000 0x0 0x1000> is one region at 0x9000000, 4 KB long. Under an I2C controller it's 1 and 0, so reg = <0x68> is just the slave address with no size. The key point is that the cells belong to the bus, not to the node itself.

꼬리 질문: "PCI는 왜 3셀인가?" → 첫 셀이 I/O·32비트 MEM·64비트 MEM을 구분하는 공간 플래그(phys.hi)이고 나머지 두 셀이 64비트 주소라서.

Q. What does the ranges property do? What's the difference between an empty ranges and no ranges?

A. 버스 브리지의 주소 디코더 표다. (자식 버스 주소, 부모 버스 주소, 길이) 항목들로, 자식 주소가 부모 주소 공간의 어디에 매핑되는지 적는다. 커널은 디바이스 reg를 루트까지 ranges를 따라 번역해서 CPU 물리 주소를 얻는다. 빈 ranges;는 1:1 매핑, ranges가 아예 없으면 번역 불가 — I2C·SPI 버스처럼 자식 주소가 메모리 주소가 아니라는 뜻이다. RPi 4는 버스 주소 0x7e201000이 ARM 물리 0xfe201000으로 번역되는 실제 예다.

ranges is the address decoder of a bus bridge: a table of child-bus-address, parent-bus-address, length. To get a CPU physical address, the kernel walks from the device up to the root and applies each bus's ranges — addr - child_base + parent_base. An empty ranges means identity mapping; a missing ranges means the child addresses aren't memory-mapped at all, like I2C or SPI chip selects. Raspberry Pi 4 is a good example: the datasheet says the UART is at 0x7e201000, but ranges maps that to 0xfe201000 on the ARM side.

꼬리 질문: "dma-ranges는?" → 반대 방향. 디바이스가 버스 마스터로 메모리에 접근할 때 보는 주소와 CPU 물리 주소의 관계. 커널 DMA API가 자동 반영한다.

Q. What is a phandle? How is &label turned into one?

A. 노드를 가리키는 32비트 정수 ID다. 트리 구조로는 다대일 연결(여러 디바이스가 한 인터럽트 컨트롤러·클록을 공유)을 표현할 수 없어서 쓴다. 소스에서는 uart0: 같은 label을 붙이고 <&uart0>으로 참조하면, dtc가 대상 노드에 phandle = <N> 프로퍼티를 만들고 참조 자리에 N을 넣는다. 꺾쇠 없이 &uart0을 쓰면 숫자가 아니라 경로 문자열이 된다. label 자체는 dtb에 남지 않고, -@로 컴파일해야 __symbols__로 남아 overlay가 쓸 수 있다.

A phandle is a 32-bit integer handle that identifies a node, so other nodes can point to it — that's how many devices share one interrupt controller or clock provider. In source you put a label on the node and reference it as <&label>; dtc assigns a number, adds a phandle property to the target, and writes that number in the referencing cell. Without the angle brackets, &label expands to the node's path string instead. Labels themselves are gone in the dtb unless you compile with -@, which emits a __symbols__ node for overlays.

Q. Walk me through the structure of a .dtb file.

A. 40바이트 헤더(매직 0xd00dfeed, totalsize, 각 블록 오프셋, 버전 17), memory reservation 블록((u64 주소, u64 크기) 쌍, 0/0으로 끝), structure 블록(BEGIN_NODE 1 + 이름, PROP 3 + 길이 + 이름 오프셋 + 값, END_NODE 2, END 9 토큰 스트림, 4바이트 정렬), strings 블록(프로퍼티 이름을 한 번씩만 저장). 모든 정수는 big-endian. 저는 60줄 C 파서로 직접 걸어 보고 fdtdump와 결과가 같은지 확인해 봤다.

It's a 40-byte header — magic 0xd00dfeed, total size, offsets to the other blocks, version 17 — followed by the memory reservation block, the structure block, and the strings block. The structure block is a depth-first token stream: BEGIN_NODE with the inline name, PROP with length, an offset into the strings block for the name, and the value, END_NODE, and finally END, all 4-byte aligned and big-endian. Property names are deduplicated in the strings block. I wrote a 60-line parser that walks it and matched fdtdump's output byte for byte on the QEMU virt tree.

Q. How does the kernel get the device tree, and how can you inspect what it actually used?

A. 부트로더가 dtb를 RAM에 올리고 arm64에서는 x0에 물리 주소를 넣어 커널로 점프한다. 부트로더는 그 전에 /chosen에 bootargs·initrd 주소를 써 넣는다. 커널은 초기에 flat 상태로 /chosen과 /memory를 읽고, unflatten_device_tree()로 device_node 트리를 만든 뒤 of_platform_populate()로 디바이스를 만든다. 실제로 쓰인 것은 /proc/device-tree(= /sys/firmware/devicetree/base)에서 프로퍼티별 파일로 보고, 원본 blob은 /sys/firmware/fdt에 있다. 그래서 "내 dts 수정이 반영됐나"는 소스가 아니라 이 두 곳에서 확인한다.

The bootloader loads the dtb into RAM, patches /chosen with bootargs and the initrd location, and on arm64 passes its physical address in x0. Early boot code reads /chosen and /memory straight from the flat blob, then unflatten_device_tree builds the device_node tree and of_platform_populate creates platform devices for nodes that are enabled. To see what the kernel really used, I look at /proc/device-tree, where each property is a file with the raw big-endian bytes, or grab /sys/firmware/fdt and decompile it with dtc. I never trust the source tree alone, because the bootloader may have loaded a different dtb or modified it.

Q. How would you disable or modify a node defined in the SoC .dtsi from a board .dts?

A. label로 다시 열어서 덮어쓴다: &i2c1 { status = "okay"; clock-frequency = <400000>; };. dtc는 같은 노드 정의를 병합하고 나중 값이 이긴다. 끌 때는 status = "disabled"가 기본이고, 노드를 아예 없애야 하면 /delete-node/ &label;, 프로퍼티만 지우려면 /delete-property/ name;. label이 없으면 &{/path}로 지정한다. 차이는 disabled는 노드가 남아 다른 노드의 phandle 참조가 깨지지 않는다는 것.

I reopen the node by its label in the board file, for example &i2c1 { status = "okay"; clock-frequency = <400000>; }; — dtc merges multiple definitions of the same node and the last value wins. To turn something off I prefer status = "disabled", because the node stays in the tree and any phandle references to it remain valid. If the hardware really isn't there, I use /delete-node/, and /delete-property/ to drop a single inherited property. If there's no label, &{/full/path} works.

Q. Why does the kernel run the C preprocessor on .dts files?

A. #include <dt-bindings/...> 헤더의 상수(GIC_SPI, IRQ_TYPE_LEVEL_HIGH, 클록 ID, GPIO 플래그)를 드라이버 C 코드와 공유하기 위해서다. dtc 자체의 /include/는 텍스트 삽입만 하고 매크로가 없다. 커널은 cpp -nostdinc -undef -D__DTS__ -x assembler-with-cpp로 먼저 전처리한 뒤 dtc에 넘긴다. -undef가 없으면 linux,code 같은 이름의 linux가 매크로로 치환되는 사고가 난다. 손으로 같은 명령을 돌려서 커널 빌드 결과와 바이트 단위로 같은 dtb를 만들어 본 적이 있다.

So the device tree and the drivers can share the same numeric constants — interrupt types, clock IDs, GPIO flags — from include/dt-bindings. dtc's own /include/ is just textual inclusion with no macros. Kbuild runs cpp with -nostdinc -undef -D__DTS__ -x assembler-with-cpp first, then dtc on the result; -undef matters because otherwise the predefined linux macro would mangle names like linux,code. I reproduced that pipeline by hand and got dtbs byte-identical to the kernel build.

20. 직접 해보기#

  1. 개념: 루트가 #address-cells = <2>; #size-cells = <1>;이고 자식에 reg = <0x0 0x10000000 0x1000 0x0 0x20000000 0x2000>;이 있다. 영역은 몇 개이고 각각 어디서 몇 바이트인가? 정답/힌트: 쌍당 3셀 → 6셀이니 2쌍. 0x10000000부터 0x1000바이트, 0x20000000부터 0x2000바이트.
  2. 개념: ranges = <0x0 0x0 0xf0000000 0x10000000>;이 있는 버스(자식 1셀, 부모 2셀, 크기 1셀) 아래 gpio@4000의 reg 주소는 CPU 물리로 얼마인가? 그 버스에서 ranges를 지우면 어떻게 되나? 정답/힌트: 0xf0004000. ranges가 없으면 번역 불가 — 커널이 MMIO 자원을 못 만들어 probe에서 ioremap이 실패한다.
  3. 코드: §11의 d2_fdtparse에 memory reservation 블록 출력(/memreserve/ 0x... 0x...;)을 추가해서 d2_tiny.dtb도 fdtdump와 IDENTICAL이 되게 하라. 정답/힌트: off_mem_rsvmap부터 16바이트씩 (u64 BE address, u64 BE size)를 읽고 둘 다 0이면 멈춘다. be()를 두 번 불러 ((uint64_t)hi << 32) | lo.
  4. 코드: §12의 d2_libfdt를 확장해 reg에 쌍이 여러 개면(GIC의 intc@8000000) 모두 번역하게 하라. 그리고 fdt_node_offset_by_phandle()로 d2-test의 d2-clk phandle을 따라가 대상 노드 경로(/apb-pclk)를 출력하라. 정답/힌트: len / 4 / (na + ns)개 쌍을 루프. phandle은 fdt32_to_cpu(*(const fdt32_t *)fdt_getprop(...))로 읽고 fdt_get_path().
  5. dtc: §9의 d2_warn.dts를 경고 0개가 될 때까지 고쳐라. 고칠 때마다 다시 돌려서 "Failed prerequisite"로 숨어 있던 경고가 새로 나타나는 것을 관찰하라. 정답/힌트: d2-bus@3000에 cells 추가 → d2-d의 reg를 2셀로 → d2-a에 reg 추가 또는 @ 삭제 → d2-b 이름에 @2000 → 마지막으로 unique_unit_address가 드러난다.
  6. QEMU 관찰: §14의 d2_virt.dts에서 d2-sub의 ranges를 지우고 부팅해 /sys/bus/platform/devices의 d2-dev 이름이 어떻게 바뀌는지 보라. 빈 ranges;로 바꾸면 또 어떻게 되나? 정답/힌트: 두 경우 모두 이름이 d2-bus@b000000:d2-sub@80040000:d2-dev@100이 된다(직접 부팅해 확인한 결과). ranges가 없으면 번역 불가, 빈 ranges;면 0x100이 그대로 d2-bus 공간으로 넘어가지만 [0x80000000, +0x100000) 밖이라 역시 실패 — of_device_make_bus_id()는 번역에 실패하면 경로 조각을 :로 이어 이름을 만든다. 디바이스 자체는 simple-bus 자식이라 여전히 생긴다.
  7. /proc 관찰: 게스트에서 hexdump -C /sys/firmware/fdt | head -3의 헤더를 손으로 해석하고, off_dt_strings부터 몇 바이트를 덤프해 compatible, reg 같은 이름이 strings 블록에 들어 있는 것을 확인하라. 정답/힌트: busybox hexdump -s <offset> -n 128 -C /sys/firmware/fdt. §14 출력에서 off_dt_strings = 0x1ea4.

22. 요약 & 체크리스트#

DT는 커널 밖에 있는 하드웨어 기술 데이터다. 문법은 단순하다: 노드 트리 + 바이트 배열 프로퍼티. 값 문법(<셀>, "문자열", [바이트])은 dtb에서 타입을 잃고 big-endian 바이트만 남으며, 해석은 바인딩과 드라이버의 몫이다. 노드끼리는 phandle(<&label>)로 연결하고, label은 소스 전용이다. 주소는 부모의 #address-cells/#size-cells로 reg를 끊어 읽고, 버스마다 ranges를 따라 addr - child + parent로 번역해 루트(CPU 물리 주소)까지 올라간다 — ranges가 없으면 MMIO가 아니다. SoC .dtsi는 꺼 두고 보드 .dts가 label로 열어 status = "okay"로 켜는 것이 기본 패턴이고, dtc 경고는 대부분 진짜 버그다. .dtb는 헤더 + 예약 블록 + 토큰 스트림 + 이름 문자열 블록이라 60줄 C로도 읽을 수 있다. 커널은 이걸 device_node 트리로 펼쳐 /proc/device-tree에 그대로 보여 주고, 번역된 주소로 platform device를 만든다 — 실제로 쓰인 DT는 항상 거기서 확인한다.
