0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어를 만들 때를 떠올려 보자. 컨트롤러 칩 하나로 여러 제품(SKU)을 만든다. 칩 레지스터 맵은 칩 팀이 준 헤더 하나, 그 위에 패키지·NAND 구성별 설정, 그 위에 제품(폼팩터·용량)별 설정이 얹힌다. 보통 chip_regs.h → platform_xxx.h → product_yyy.h처럼 공통에서 구체로 층을 나누고, 위층이 아래층의 기본값을 #define으로 덮는다.

Device Tree도 똑같은 문제를 똑같은 방식으로 푼다. 다만 대상이 "C 상수"가 아니라 "하드웨어 설명 트리"다.

  • SoC 층 (imx8mp.dtsi) — 칩 안에 있는 모든 블록(UART 4개, CAN 2개, I2C 6개 …)을 주소·인터럽트·클록까지 적어 두고, 거의 전부 status = "disabled"로 꺼 둔다. 칩 벤더(NXP)가 쓴다.
  • SoM 층 (imx8mp-verdin.dtsi) — 칩을 얹은 모듈 위에 납땜된 것: DRAM 크기, PMIC, eMMC, 그리고 "어느 핀을 어느 기능에 쓰는지"(pinctrl). 모듈 벤더(Toradex)가 쓴다.
  • 캐리어 보드 층 (imx8mp-verdin-dev.dtsi + imx8mp-verdin-nonwifi-dev.dts) — 모듈을 꽂는 보드: 커넥터, CAN 트랜시버, 센서. 여기서 실제로 쓰는 장치를 status = "okay"로 켠다. 보드를 만드는 회사(= 입사하면 우리 팀)가 쓴다.

그림 1 — 물리적 계층과 DT 파일 계층이 1:1로 대응한다. 위층 파일이 아래층 파일을 #include하고, 같은 노드를 다시 열어 값을 덮는다. 줄 수와 dtb 크기는 이 노트에서 실제로 잰 값이다.

1. 실제 체인 하나 고르기 — Toradex Verdin iMX8M Plus#

1.1 왜 이 보드인가#

교과서 예제로 흔히 NXP imx8mp-evk.dts를 쓰지만, EVK는 "SoC 벤더의 평가 보드"라서 SoC dtsi → 보드 dts 두 층뿐이다. 실무에서 Don이 만날 구조는 대개 세 층이다. 센서 키트 같은 장비 회사는 칩을 직접 PCB에 올리기보다 SoM(System on Module)을 사서 자기 캐리어 보드에 꽂는다. 그래서 업스트림 커널에서 SoM 층이 따로 있는 체인을 골랐다. Toradex Verdin iMX8M Plus는 같은 SoM에 Wi-Fi 유무 변형 2개, 캐리어 보드 5종이 있어서 BSP 정리법을 보기에도 좋다.

1.2 예제 1 — 파일 목록과 include 관계 확인#

무엇을 확인하나: Verdin 관련 파일이 어떤 이름 규칙으로 몇 개 있고, 보드 dts가 무엇을 include하는지 본다.

출력에서 볼 것: SoM 공통 imx8mp-verdin.dtsi 하나, SoM 변형 -wifi/-nonwifi.dtsi 둘, 캐리어 -dev/-dahlia/-ivy/-mallow/-yavia.dtsi 다섯, 그리고 그 조합인 .dts 열 개다. 보드 .dts는 겨우 18줄이고 include 세 줄 + model/compatible뿐이다. 반면 EVK는 SoM 층이 없어서 보드 .dts 하나에 1193줄이 몰려 있다.

실제 보드 파일 전체는 이렇다.

compatible이 가장 구체적인 것 → 가장 일반적인 것 순서(보드 → SoM 변형 → SoM → SoC)인 점을 눈여겨보자. 커널과 U-Boot는 앞에서부터 매칭을 시도하므로, 보드 전용 처리가 없으면 SoC 공통 처리로 내려간다(D3에서 드라이버 쪽 매칭으로 다시 나온다).

2. include — cpp가 먼저, dtc가 나중#

2.1 직관 — #include는 그냥 텍스트 붙여넣기다#

.dts의 #include는 C와 완전히 같은 C 전처리기(cpp) 가 처리한다. dtc(Device Tree Compiler)는 #include를 모른다. 커널 빌드는 먼저 gcc -E로 모든 include를 펼치고 매크로를 숫자로 바꾼 하나의 거대한 텍스트 파일(.dts.tmp)을 만든 다음, 그 파일을 dtc에 넘긴다.

그래서 include 계층의 의미는 오직 "텍스트가 어떤 순서로 이어 붙느냐"다. 보드 dts가 imx8mp-verdin.dtsi를 먼저, imx8mp-verdin-dev.dtsi를 나중에 include하면, 펼친 결과에서 SoC 내용 → SoM 내용 → 캐리어 내용 → 보드 / { } 순서로 나온다. 3절의 "나중 것이 이긴다" 규칙은 이 순서에 대해 적용된다.

그림 2 — 실제 보드 imx8mp-verdin-nonwifi-dev.dts의 include 트리. 4.4절 의존성 파일(.d.pre.tmp)에서 뽑은 그대로다. 번호는 펼쳐지는 순서다.

2.2 dt-bindings 헤더 — DT와 드라이버가 같은 번호를 쓰게 하는 장치#

DT에서 clocks = <&clk IMX8MP_CLK_CAN1_ROOT>;라고 쓰면 cpp가 매크로를 숫자로 바꾼다. 이 숫자는 클록 드라이버(drivers/clk/imx/clk-imx8mp.c)가 "233번 클록 = CAN1 루트 게이트"로 해석한다. 둘이 어긋나면 엉뚱한 클록이 켜진다. 그래서 숫자를 한 헤더에 두고 DT와 C 드라이버가 같이 include한다. 이 헤더들이 include/dt-bindings/ 아래에 있고, 한번 정해진 번호는 바꾸면 안 되는 ABI다(이미 출시된 dtb가 그 숫자를 품고 있으므로).

예제 2 — 무엇을 확인하나: 자주 쓰는 매크로 정의, 드라이버도 같은 헤더를 쓰는지, dtc가 헤더를 찾는 경로를 본다.

출력에서 볼 것: IMX8MP_CLK_CAN1_ROOT = 233을 클록 드라이버 clk-imx8mp.c도 같은 헤더로 쓴다. 커널 빌드는 scripts/dtc/include-prefixes/를 include 경로로 주는데, 그 안의 dt-bindings는 include/dt-bindings로 가는 심볼릭 링크다. 그래서 #include <dt-bindings/...>가 찾아진다. 같은 폴더에 arm, arm64, riscv 링크도 있어서 다른 아키텍처의 dtsi를 <arm64/...> 꼴로 include할 수도 있다.

Don에게 익숙한 말로: SSD 펌웨어에서 호스트 드라이버와 펌웨어가 같은 nvme_spec.h를 공유해 opcode 번호를 맞추는 것과 똑같다.

2.3 예제 3 — 3층짜리 작은 트리를 직접 만들어 cpp 결과 보기#

실제 BSP는 너무 커서 규칙을 눈으로 확인하기 어렵다. 그래서 같은 구조의 작은 트리를 직접 만든다. 이 예제는 3절에서도 계속 쓴다. 노드 이름·라벨에는 노트 ID 접두어 d5_를 붙였다.

SoC 층 — 칩 안의 블록을 전부 적고 기본은 꺼 둔다. GPU만 SoC 기본값이 okay다.

SoM 층 — 모듈 위의 DRAM, PMIC, 콘솔 UART를 켠다.

캐리어 보드 층 — 센서 키트 rev B. IMU를 I2C에 달고, 버스 속도를 바꾸고, 없는 GPU를 지운다.

빌드는 커널 scripts/Makefile.dtbs의 cmd_dtc(4절)와 같은 두 단계를 셸 스크립트로 흉내 낸다.

먼저 cpp 단계의 결과(.dts.tmp)만 들여다본다. 무엇을 확인하나: include가 어떤 순서로 펼쳐지고 매크로가 어떤 숫자가 되는지.

출력에서 볼 것: # 1 "파일" 1(파일 진입)과 # N "파일" 2(복귀)는 cpp의 linemarker다. dtc는 이것을 읽어서 에러 메시지에 원래 파일 이름과 줄 번호를 찍는다(3.7절 에러 출력에서 bad_label.dts:3.1-10처럼 나오는 이유). GIC_SPI 10 IRQ_TYPE_LEVEL_HIGH는 0 10 4로, GPIO_ACTIVE_LOW는 1로 바뀌었다. 반면 &d5_gic 같은 라벨 참조는 cpp가 건드리지 않고 dtc에게 그대로 넘어간다. 즉 매크로는 cpp의 몫, 라벨은 dtc의 몫이다.

2.4 커널이 cpp에 주는 옵션의 의미 — 특히 -undef#

옵션왜 필요한가
-nostdinc/usr/include 같은 호스트 시스템 헤더를 실수로 끌어오지 않게 한다
-I scripts/dtc/include-prefixes<dt-bindings/...>, <arm64/...>를 찾는 유일한 경로
-undefgcc가 미리 정의하는 시스템 매크로(linux, unix 등)를 없앤다
-D__DTS__공용 헤더 안에서 "지금 DT에서 include됐다"를 구분할 때 쓴다
-x assembler-with-cpp입력을 C가 아니라 "cpp를 거치는 어셈블리"로 취급. C 문법 검사를 하지 않고, #로 시작하는 DT 문법(#address-cells)과 충돌을 줄인다

-undef가 왜 필요한지는 실행해 보면 바로 보인다. 예제 4 — 무엇을 확인하나: DT 속성 이름에 흔한 linux, 접두어가 cpp를 지나면서 어떻게 되는지.

출력에서 볼 것: GNU 모드 gcc는 Linux 호스트에서 linux를 1로 미리 정의한다. -undef가 없으면 linux,code(키 코드 속성, 실제로 imx8mp-verdin.dtsi:75에 linux,code = <KEY_WAKEUP>;가 있다)가 1,code로 망가진다. 커널 아래 arm64 dts 중 linux,가 들어간 파일이 719개다. 사내 빌드 스크립트로 dts를 직접 cpp에 돌릴 때 이 옵션을 빼먹으면 이런 이상한 에러를 만난다.

2.5 /include/ — dtc 자체 include (매크로 없음)#

dtc에도 자체 include 문법 /include/ "file"이 있다. cpp가 생기기 전의 옛 방식이다. 차이는 하나다: /include/로 읽은 파일은 cpp를 거치지 않는다. 커널 빌드에서 cpp는 dtc보다 먼저 한 번만 돌기 때문이다.

예제 5 — 무엇을 확인하나: rev C 보드 차이분을 /include/로 붙이면 매크로가 해석되지 않아 실패하고, #include로 바꾸면 성공하는 것.

출력에서 볼 것: /include/ 쪽은 3행 29열, 즉 GPIO_ACTIVE_LOW 글자에서 syntax error가 난다. #include로 바꾸면 rev C dtb의 IMU 인터럽트 핀이 3번에서 4번으로 바뀐다(3 4 1 = phandle 3인 pinctrl의 4번 핀, active-low). 커널 arm64 트리에서 /include/는 6개 파일 8곳(apm, amd, cavium의 오래된 보드)에만 남아 있다. 새 코드에서는 항상 #include를 쓴다. 단, /include/는 dtc가 처리하므로 cpp 없이 dtc만 쓰는 환경(일부 오버레이 빌드 스크립트)에서는 여전히 보인다.

주의: /include/ 경로는 dtc가 읽는 파일(.dts.tmp) 기준으로 찾는다. 이 tmp 파일은 빌드 출력 폴더에 있으므로, 커널은 dtc -i $(dir $<)로 원래 소스 폴더를 검색 경로에 추가해 준다. 위 스크립트의 -i $(dirname $SRC)도 같은 이유다.

3. Override — 라벨로 노드를 다시 열어 덮어쓰기#

3.1 직관 — 같은 노드를 여러 번 열면 dtc가 합친다#

DT 소스에서 같은 노드를 여러 번 정의해도 에러가 아니다. dtc는 같은 경로의 노드 정의를 차례로 병합한다. 규칙은 네 줄이다.

  1. 처음 보는 속성은 그 노드의 속성 목록 끝에 추가된다.
  2. 이미 있는 속성을 다시 쓰면 값만 바뀌고 자리는 그대로다. 나중에 나온 값이 이긴다.
  3. 자식 노드도 같은 규칙으로 재귀 병합된다.
  4. "나중"의 기준은 cpp가 펼친 텍스트 순서다 (파일 계층이 아니라).

노드를 다시 여는 방법은 세 가지다.

문법뜻언제 쓰나
&label { ... };라벨이 붙은 노드를 다시 연다 (루트 레벨에 쓴다)가장 흔한 방식. SoC dtsi의 uart4: 라벨을 보드에서 연다
&{/soc/serial@2000} { ... };전체 경로로 다시 연다라벨이 없는 노드. U-Boot -u-boot.dtsi에서 자주 보인다
/ { soc { serial@2000 { ... }; }; };트리를 루트부터 다시 써 내려간다옛 스타일. 경로가 길고 오타에 약해서 요즘은 잘 안 쓴다

지우거나 빼는 지시어도 있다.

지시어뜻
/delete-node/ &label;라벨이 붙은 노드를 통째로 지운다 (루트 레벨)
/delete-node/ name@addr;현재 노드 안에서 이름으로 자식을 지운다
/delete-property/ prop;현재 노드에서 속성 하나를 지운다
/omit-if-no-ref/노드 정의 앞에 붙인다. 최종 트리에서 아무도 phandle로 참조하지 않으면 그 노드를 dtb에서 뺀다

3.2 예제 6 — 3층 트리를 컴파일해 병합 결과 보기#

무엇을 확인하나: 2.3절의 세 파일을 dtb로 만든 뒤 다시 소스로 풀어서(decompile) 위 규칙들이 실제로 어떻게 적용됐는지 본다.

출력에서 하나씩 짚어 보자.

  • 값 덮어쓰기: i2c@3000의 clock-frequency는 SoC 100000 → 보드 400000 → 같은 보드 파일 아래쪽 1000000을 거쳐 0xf4240(= 1,000,000)이 됐다. 같은 파일 안에서도 텍스트상 나중 것이 이긴다.
  • 자리 유지 + 끝에 추가: serial@1000에서 status = "okay"는 SoC에서 정의된 자리(interrupts 다음)에 있고, SoM이 새로 넣은 pinctrl-names, pinctrl-0은 그 뒤에 붙었다. 루트의 model도 SoM이 처음 넣었으므로 SoC의 속성들 뒤에 있다.
  • 자식 병합: i2c@3000 아래에 SoM의 pmic@32와 보드의 imu@68이 나란히 들어갔다.
  • /delete-node/: SoC에서 okay였던 gpu@4000이 아예 없다.
  • /omit-if-no-ref/: uart1-grp는 pinctrl-0이 참조하므로 남았고, 아무도 참조하지 않은 uart2-grp는 빠졌다.
  • 라벨은 사라진다: d5_uart1: 같은 라벨은 dtb에 없다. 참조되는 노드에는 phandle = <N> 숫자가 붙고, &d5_pins_uart1 참조는 <0x02>로 바뀌었다. stdout-path = &d5_uart1처럼 문자열 자리에 쓴 참조는 경로 문자열 "/soc/serial@1000"이 됐다.
  • 매크로도 사라진다: interrupts는 <0x00 0x0a 0x04>다. decompile로는 GIC_SPI를 되살릴 수 없다.

3.5 지우기와 경로로 열기 — /delete-property/, /delete-node/, &{/path}#

예제 10 — 무엇을 확인하나: 라벨 대신 이름·경로로 지우고 여는 방법.

출력에서 볼 것: clock-frequency가 없어졌고 PMIC 자식을 지워서 I2C 노드에 자식이 0개다. dtc가 "자식에 reg가 없는데 #address-cells가 왜 있나"라고 경고하면서 이 노드가 정의된 세 곳(also defined at)을 모두 알려 준다. 이 목록이 "이 노드를 누가 건드렸나"를 찾는 가장 빠른 단서다. 커널 빌드는 이 경고를 기본으로 끈다(-Wno-avoid_unnecessary_addr_size, 4.3절). &{/soc/serial@2000}로 라벨 없는 UART2도 켰다.

실제 트리에서는 이렇게 쓰인다.

k3-am62d2.dtsi는 AM62A7 SoC dtsi를 include한 뒤, 그 파생 칩에 실제로 없는 비디오 코덱과 JPEG 인코더를 지운다. 파생 칩 = 부모 칩 dtsi + 삭제라는 흔한 패턴이다. imx8mp-verdin.dtsi는 SoC dtsi가 잡아 둔 CMA 영역을 지우고 커널 설정값을 쓰게 한다. 커널 arm64 트리 전체에서 /delete-node/는 163개 파일 514곳, /delete-property/는 132개 파일 254곳에 쓰인다.

status = "disabled"와 /delete-node/의 차이: disabled는 노드가 dtb에 남아 있고 드라이버만 붙지 않는다. 다른 노드가 그 노드를 phandle로 참조해도 문제없다. delete는 노드가 사라지므로 누가 참조하면 빌드 에러다(3.6절). 그래서 보드에서 장치를 끌 때는 거의 항상 status = "disabled"를 쓰고, 칩에 물리적으로 없는 블록처럼 "존재 자체가 틀린" 경우에만 delete를 쓴다.

3.6 /omit-if-no-ref/ — 안 쓰는 핀 그룹을 dtb에서 빼기#

SoC 벤더는 "이 칩의 UART2는 이 핀 조합 A, B, C 중 하나로 낼 수 있다"를 전부 pinctrl 그룹 노드로 미리 적어 둔다. 보드는 그중 하나만 참조한다. 나머지가 dtb에 다 들어가면 크기만 커진다. /omit-if-no-ref/를 붙인 노드는 최종 트리에서 아무도 참조하지 않으면 dtc가 뺀다(3.2절 uart2-grp).

커널 arm64 트리에서 /omit-if-no-ref/는 12개 파일에 2011번 쓰이고, 상위는 전부 Rockchip pinctrl dtsi다(rk3576-pinctrl.dtsi 690, rk3588-base-pinctrl.dtsi 433, rk3568-pinctrl.dtsi 335). 이 지시어는 라벨로 참조되는 것을 전제로 한다. 오버레이(D6)가 나중에 그 핀 그룹을 참조할 예정이라면 베이스 dtb에서 이미 빠져 버려서 오버레이 적용이 실패한다. 그래서 오버레이를 쓰는 플랫폼은 이 지시어를 조심해서 쓴다.

4.5 -@와 __symbols__ — 오버레이를 위한 라벨 보존#

3.2절에서 라벨은 dtb에 남지 않는다고 했다. 그런데 오버레이(D6)는 "베이스 dtb의 &flexcan1을 고쳐라"처럼 라벨로 대상을 가리킨다. 그래서 오버레이를 받을 베이스 dtb는 dtc -@로 빌드해서 라벨 → 경로 표(/__symbols__ 노드)를 dtb 안에 남긴다. 커널은 Makefile에 <합성>-dtbs += <베이스>.dtb <오버레이>.dtbo가 있는 베이스에만 자동으로 -@를 붙인다(4.1절 base-dtb-y).

6.2 예제 18 — 라벨이 살아 있는 평탄화 소스와 변형 비교#

dtb끼리 비교하는 dtdiff가 있다. /usr/bin/dtdiff는 셸 스크립트로, 두 입력(dts, dtb, 또는 /proc/device-tree 같은 디렉터리)을 각각 dtc -O dts -s(노드·속성 이름순 정렬)로 풀어서 diff -u 한다. 무엇을 확인하나: Wi-Fi 변형과 non-Wi-Fi 변형 보드가 실제로 무엇이 다른지.

출력에서 볼 것: diff가 1530줄이다. 그런데 대부분은 진짜 차이가 아니다. Wi-Fi 변형에 노드가 몇 개 더 있어서 phandle 번호가 전부 5씩 밀렸고(0xa3 → 0xa8), 그 번호를 참조하는 모든 속성이 diff에 나온다. dtb 비교의 고질적인 문제다.

해결책은 라벨이 살아 있는 상태에서 비교하는 것이다. 빌드 폴더의 .dts.tmp(cpp만 거친 소스)를 dtc -I dts -O dts -s로 한 번 평탄화하면, 병합·삭제는 다 적용됐지만 참조는 &label로 남는다. phandle 줄만 빼고 비교한다.

출력에서 볼 것: 진짜 차이는 37줄이다. Wi-Fi 변형은 (1) Wi-Fi 전원 레귤레이터를 추가하고, (2) GPIO 4개(SODIMM_164/152/116/128)를 Wi-Fi 제어에 쓰므로 GPIO 이름에서 빼고 hog를 바꾸고, (3) SDIO 컨트롤러(usdhc1)를 켜서 Wi-Fi 칩을 붙이고, (4) UART4를 Bluetooth용 핀으로 바꿔 켜고 bluetooth 자식(Marvell 88W8997)을 단다. 3.4절 표에서 UART4가 Wi-Fi 변형에서만 okay였던 이유가 여기 있다. 리뷰나 디버깅에서 두 보드를 비교할 때는 dtb가 아니라 .dts.tmp 평탄화 소스를 비교하라가 이 예제의 교훈이다.

7. 런타임 DT 읽기 — 보드 위에서 "실제로 돌고 있는 DT" 확인#

7.2 예제 20 — QEMU 게스트에서 런타임 DT 들여다보기#

무엇을 확인하나: 랩 커널(6.18.55)을 QEMU virt로 부팅해서, 게스트 안에서 DT 노드·속성을 읽고, /sys/firmware/fdt blob을 콘솔로 꺼낸다. BusyBox에는 dtc가 없으므로 게스트에서는 cat·hexdump만 쓰고, blob과 디렉터리 트리는 base64로 콘솔에 찍어 호스트에서 되살린다(실제 보드에서 네트워크가 없을 때도 쓰는 방법이다).

출력에서 볼 것:

  • /proc/device-tree는 /sys/firmware/devicetree/base를 가리키는 링크다.
  • 노드는 디렉터리라 ls로 속성 목록이 보인다. 커널이 만든 가짜 속성 name(노드 이름)도 있다.
  • reg 파일을 hexdump하면 #address-cells = 2, #size-cells = 2라서 64-bit 주소 0x0000_0000_0900_0000과 크기 0x1000이 big-endian으로 나온다. 셀 수를 모르면 이 바이트를 해석할 수 없다(D2의 #address-cells 이야기).
  • QEMU virt DT에는 status 속성이 하나도 없다(모두 켜짐). 실제 SoC dtsi와 정반대다.
  • /sys/firmware/fdt는 QEMU가 넘긴 1 MiB(0x00100000) blob이다. 헤더의 첫 4바이트 d0 0d fe ed가 FDT magic, 다음 4바이트가 totalsize다. root만 읽을 수 있다(-r--------).
  • md5는 부팅마다 바뀐다(아래 7.3절 이유).

7.3 예제 21 — 꺼낸 blob과 디렉터리 트리를 호스트에서 비교#

무엇을 확인하나: 콘솔에서 받은 base64를 되살려 dtc -I dtb와 dtc -I fs로 각각 풀고, 둘이 같은지, 그리고 랩에 저장된 virt.dts와 무엇이 다른지.

출력에서 볼 것:

  • md5가 게스트에서 찍은 값과 같으므로 콘솔 전송이 깨지지 않았다.
  • dtc -I fs(디렉터리 트리)와 dtc -I dtb(blob)가 정렬 후 완전히 같다. 디렉터리 입력에서는 속성 순서가 디렉터리 순서라 달라지므로 -s로 정렬해서 비교했다. 디렉터리 입력일 때 dtc가 clocks 셀을 phandle로 연결하지 못해 경고를 내지만 내용에는 영향이 없다.
  • 랩의 virt.dts(QEMU dumpdtb로 저장한 것, -append/-initrd 없이)와 비교하면 /chosen만 다르다. bootargs와 linux,initrd-*는 QEMU가 이번 부팅 인자로 채운 것이다(실제 보드에서는 U-Boot가 bootm/booti 때 채운다).
  • kaslr-seed는 0으로 덮였고 rng-seed는 사라졌다. 커널이 부팅 직후 씨앗 값을 쓰고 지우기 때문이다. arm64 arch/arm64/kernel/pi/kaslr_early.c의 get_kaslr_seed()는 값을 읽은 뒤 *prop = 0;으로 덮고, drivers/of/fdt.c의 early_init_dt_scan_chosen()은 rng-seed를 fdt_nop_property()로 지운다. 그래서 /sys/firmware/fdt는 "부트로더가 준 그대로"가 아니다. NOP 처리는 태그만 바꾸고 값 바이트는 blob 안에 남기 때문에, 매 부팅 다른 난수가 들어간 blob의 md5가 매번 달라진다.

8.2 정리 규칙 (업스트림과 잘 관리된 BSP에서 공통으로 보이는 것)#

  1. SoC dtsi는 정의만, 켜지 않는다. 칩 내부 블록은 전부 status = "disabled"로 두고, 실제로 항상 쓰이는 것(인터럽트 컨트롤러, 타이머, 클록 컨트롤러)만 status 없이 둔다. 5절 실측에서 SoC 층의 okay가 0개였다.
  2. SoM dtsi는 "모듈 위의 사실"만. DRAM, PMIC, eMMC, 그리고 SoM 커넥터 핀 → SoC 기능의 pinctrl. 캐리어에 따라 달라지는 장치는 pinctrl만 붙여 두고 꺼 둔다(3.3절 flexcan1).
  3. 캐리어 dtsi가 켠다. 트랜시버·커넥터가 실제로 있는 인터페이스를 okay로, 캐리어 위의 센서·EEPROM·GPIO 확장기를 자식 노드로.
  4. 보드 dts는 조합만. include 몇 줄 + model + compatible. 내용이 생기면 그건 SoM 변형이나 캐리어 dtsi로 올린다.
  5. 하드웨어 리비전은 별도 dts 또는 오버레이. rev B → rev C에서 핀 하나가 바뀌면 -revc.dts가 rev B dts를 include하고 차이만 덮는다(2.5절 예제와 같은 구조). 옵션 보드(카메라 모듈, 디스플레이)는 오버레이 .dtso로 분리한다(D6).
  6. compatible은 구체 → 일반 순서. 보드, 변형, SoM, SoC 순서로 나열해 소프트웨어가 가장 구체적인 것부터 매칭하게 한다.
  7. 라벨로 재정의한다. 경로를 다시 써 내려가는 옛 방식은 SoC dtsi의 버스 구조가 바뀌면 깨진다. 라벨은 위치가 바뀌어도 그대로다.
  8. 부트로더 전용 내용은 부트로더 쪽에. U-Boot는 arch/arm/dts/<board>-u-boot.dtsi가 있으면 빌드 때 자동으로 덧붙인다(scripts/Makefile.lib의 u_boot_dtsi_options가 <보드>-u-boot.dtsi, <SoC>-u-boot.dtsi, … 순서로 찾아 첫 번째를 쓴다). 예를 들어 imx8mp-evk-u-boot.dtsi는 SPL 단계에서도 PMIC 노드가 살아 있도록 bootph-all;을 붙인다. 커널 dts를 건드리지 않고 부트로더 요구를 만족시키는 장치다.

(위는 랩의 U-Boot 소스 arch/arm/dts/imx8mp-evk-u-boot.dtsi의 한 부분. 라벨이 없는 노드를 경로로 다시 연다 — 3.1절의 &{/path} 문법이다.)

8.3 업스트림 트리의 규모 — 벤더별로 얼마나 많은가#

예제 24 — 무엇을 확인하나: arm64 dts 폴더의 벤더별 .dts/.dtsi/.dtso 개수.

그림 8 — 벤더 폴더별 파일 수(실측, 상위 10). .dtsi가 .dts보다 많은 벤더(freescale, renesas, ti)는 SoM 층이나 도메인별 분할을 많이 쓴다. TI는 오버레이(.dtso) 비중이 크다 — 확장 보드·카메라를 오버레이로 다루는 문화다.

벤더 BSP 트리(NXP linux-imx, TI ti-linux-kernel 등)는 업스트림과 파일 이름·노드가 다를 수 있다. 업스트림 기준으로 이 구조를 익혀 두면 벤더 트리를 읽을 때 "어디가 벤더가 덧댄 부분인지"가 보인다. 회사 보드 dts를 업스트림 커널로 옮길 때 가장 많이 하는 일이 바로 이 차이를 정리하는 것이다.

9. 커널 안에서는 무슨 일이 일어나나#

DT 파일 구조(층, 라벨, include, 매크로)는 빌드 타임 개념이다. 커널이 받는 것은 그 결과인 평평한 dtb 하나뿐이고, 커널 안에는 라벨도 include도 없다. 커널 쪽 경로를 따라가면 다음과 같다(6.18 기준, 함수 이름은 drivers/of/와 arch/arm64/kernel/에서 확인).

  1. 진입: 부트로더가 arm64 커널에 x0 = dtb 물리 주소를 넘긴다. setup_arch() → setup_machine_fdt(__fdt_pointer)가 blob을 매핑하고 /chosen(커맨드라인, initrd 위치), /memory를 먼저 읽는다. 이때 early_init_dt_scan_chosen()이 rng-seed를 엔트로피로 쓰고 지운다(7.3절). 이 시점의 blob 포인터가 initial_boot_params다. (kaslr-seed는 그보다 더 이른 arch/arm64/kernel/pi/의 초기 매핑 코드 kaslr_early_init() → get_kaslr_seed()가 읽고 0으로 덮는다.)
  2. 펼치기: unflatten_device_tree()가 blob을 걸어 struct device_node(이름, phandle, properties 연결 리스트, parent/child/sibling, fwnode) 트리를 만들고 루트를 of_root에 둔다. 속성은 struct property(이름, 길이, 값 포인터)다. 5절의 fdtstat.py가 한 일이 축소판이다.
  3. sysfs 노출: of_core_init()이 /sys/firmware/devicetree kset을 만들고 각 노드를 kobject로 붙인 뒤(__of_attach_node_sysfs()), proc_symlink("device-tree", NULL, "/sys/firmware/devicetree/base")로 /proc/device-tree 링크를 만든다. late_initcall인 of_fdt_raw_init()은 blob의 CRC가 부팅 초기 값과 같을 때만 /sys/firmware/fdt(root 전용 bin attribute)를 만든다 — 누가 blob을 몰래 고쳤으면 원본이라고 내보내지 않는다.
  4. 디바이스 생성: of_platform_default_populate()가 루트 아래 simple-bus 등을 따라 내려가며 노드마다 platform_device를 만든다. 이때 of_device_is_available()을 검사하는데, 이 함수는 status가 없거나 "okay" 또는 "ok"일 때만 참이다(drivers/of/base.c). 그래서 SoC dtsi의 "disabled" 노드나 3.7절의 "okey" 노드에는 디바이스가 생기지 않는다.
  5. 드라이버 매칭: 만들어진 platform_device의 compatible이 드라이버의 of_match_table과 맞으면 probe()가 불린다(D3, G2). 드라이버는 of_property_read_u32() 등으로 이 노드의 속성을 읽는다(D8). 3.3절에서 SoC·SoM·캐리어가 나눠 쓴 flexcan1 속성은 이 시점에 한 노드의 속성 리스트로 드라이버(drivers/net/can/flexcan/)에게 보인다. 드라이버는 그 값이 어느 파일에서 왔는지 모르고 알 필요도 없다.
  6. 런타임 변경: 오버레이(CONFIG_OF_OVERLAY, 랩 커널에 켜져 있음)는 device_node 트리를 실행 중에 고치고, 바뀐 노드에 대해 디바이스를 추가·제거한다(D6). 이때 라벨 해석을 위해 베이스에 __symbols__가 필요하다(4.5절).

드라이버를 쓸 때 이 지식이 다시 나오는 지점은 셋이다. (1) probe()가 안 불리면 먼저 "노드가 /proc/device-tree에 있고 사용 가능 상태인가"를 확인한다 — 파일 구조 문제(이 노트)인지 매칭 문제(D3)인지 가르는 첫 질문이다. (2) 속성을 읽을 때 -EINVAL/-ENODATA가 나오면 최종 트리에서 그 속성이 덮이거나 지워지지 않았는지 본다. (3) dt-bindings 헤더의 숫자는 드라이버와 공유하는 ABI이므로, 새 클록·리셋 ID를 추가할 때 헤더·드라이버·dts를 한 패치 시리즈로 바꾼다.

10. Embedded 실무에서 다시 보기#

10.1 "CAN 2가 안 올라온다" — 캐리어마다 다르다#

센서 키트를 Verdin + Yavia 캐리어로 만들었는데 ip link에 can1이 없다. SoC 매뉴얼에는 FlexCAN이 둘이고, SoM 문서에도 CAN_2 핀이 있다. 3.4절 표처럼 최종 dtb를 보면 Yavia에서는 flexcan2가 disabled다. 고치는 곳은 SoC dtsi도 SoM dtsi도 아니고 우리 캐리어 dts다.

단, 캐리어가 그 핀을 다른 용도(GPIO 등)로 이미 쓰고 있으면 pinctrl 충돌로 probe가 실패한다. okay만 켜고 끝내지 말고 그 핀이 캐리어 dtsi에서 무엇으로 쓰였는지 확인해야 한다.

10.2 rev C에서 IMU 인터럽트 핀이 바뀌었다#

하드웨어 팀이 rev C에서 IMU INT를 다른 GPIO로 옮겼다. 선택지는 둘이다. (1) sensorkit-revc.dts가 sensorkit-revb.dts를 include하고 &imu { interrupts-extended = ...; };만 덮는다(2.5절 예제). (2) 부트로더가 보드 EEPROM의 리비전을 읽어 맞는 dtb를 고르거나(fdtfile 환경 변수), fdt set으로 고친다(7.5절). 생산 라인에서 두 리비전이 섞여 돌 때는 (2)가 흔하다. 어느 쪽이든 "이 보드에서 실제로 어떤 DT가 돌고 있나"는 /proc/device-tree/model과 해당 속성을 읽어 확인한다.

10.3 "dts를 고쳤는데 반영이 안 된다"#

가장 흔한 신고다. 원인은 거의 항상 빌드가 아니라 배포다. 부트 파티션에 dtb가 여러 개 있고 U-Boot가 다른 이름을 읽거나, Yocto 이미지가 커널 레시피의 KERNEL_DEVICETREE에 없는 dtb는 설치하지 않거나, 부트로더가 FIT 이미지 안의 dtb를 쓰는 경우다. 아래 흐름으로 좁힌다.

12. 면접에서 이렇게 말한다#

Q. What is the difference between a .dtsi and a .dts file?

A. .dtsi는 include용 조각이고 단독으로 dtb가 되지 않는다. 보통 SoC 전체(칩 벤더), SoM(모듈 벤더)처럼 여러 보드가 공유하는 하드웨어를 기술한다. .dts는 보드 하나에 대응하고 /dts-v1/;로 시작해 dtb 하나가 된다. 보드 dts가 SoC·SoM dtsi를 include하고, 라벨로 노드를 다시 열어 실제로 쓰는 장치만 okay로 켠다.

A .dtsi is a shared fragment that's never compiled on its own — typically the SoC description from the silicon vendor, or the SoM description from the module vendor. A .dts describes one board and produces one .dtb. The board file includes the SoC and SoM .dtsi files and then re-opens nodes by label to enable just the peripherals that are actually wired up on that board.

꼬리 질문: SoC dtsi에서 장치를 왜 disabled로 두나? → 칩에 블록이 있어도 보드에 핀·트랜시버가 연결됐는지는 보드만 안다. 꺼 두고 보드가 켜야 불필요한 드라이버 probe와 핀 충돌을 막는다.

Q. How do you enable or change a peripheral for your board without touching the SoC file?

A. 보드 파일에서 그 노드의 라벨로 &uart2 { status = "okay"; pinctrl-0 = <...>; };처럼 다시 연다. dtc는 같은 노드의 정의를 텍스트 순서대로 병합하고, 같은 속성은 나중 값이 이긴다. 속성을 없애려면 /delete-property/, 칩에 없는 블록이면 /delete-node/ &label;을 쓰지만, 단순히 끄는 것은 status = "disabled"가 맞다.

In the board file I re-open the node by its label, like &uart2 { status = "okay"; }, and add pinctrl or child nodes there. dtc merges all definitions of the same node in the order they appear after preprocessing, and the last value for a property wins. I'd use /delete-property/ or /delete-node/ only when something truly doesn't exist; to just turn a device off I set status to disabled.

Q. How are device tree files built in the kernel?

A. make dtbs나 make <vendor>/<board>.dtb. Kbuild의 scripts/Makefile.dtbs에 있는 cmd_dtc가 먼저 gcc -E로 #include와 dt-bindings 매크로를 펼치고(-nostdinc -undef -D__DTS__ -x assembler-with-cpp), 그 결과를 커널 동봉 dtc로 컴파일한다. 의존성 파일 덕분에 dtsi나 헤더를 고치면 영향받는 dtb만 다시 빌드된다. 오버레이 베이스 dtb에는 자동으로 -@가 붙는다.

With make dtbs, or make vendor/board.dtb for a single one. The rule in scripts/Makefile.dtbs runs the C preprocessor first to expand includes and the dt-bindings macros, then the in-tree dtc compiles the result into a blob. Dependency files are generated, so touching a .dtsi only rebuilds the boards that include it. Boards used as overlay bases are built with -@ so the labels survive as __symbols__.

Q. Why does the device tree use C preprocessor headers like dt-bindings?

A. 클록·리셋·인터럽트·GPIO 플래그 같은 숫자 ID를 DT와 C 드라이버가 같은 헤더로 공유하려고다. 예를 들어 IMX8MP_CLK_CAN1_ROOT는 233이고 클록 드라이버도 같은 헤더를 include한다. 숫자는 출시된 dtb에 박히므로 ABI이고 바꾸면 안 된다. 다만 cpp가 처리하므로 decompile하면 숫자만 남는다.

They give the DT and the C driver one shared source of truth for numeric IDs — clock indices, reset lines, interrupt types, GPIO flags. The clock driver includes the same header as the .dtsi, so they can't drift apart. Once a dtb ships, those numbers are ABI. The macros vanish after preprocessing, so a decompiled dtb shows raw numbers.

Q. How do you check which device tree is actually running on a board?

A. /proc/device-tree(= /sys/firmware/devicetree/base)에서 model과 문제 노드를 읽는다. 전체가 필요하면 dtc -I fs -O dts /proc/device-tree, 또는 /sys/firmware/fdt blob을 복사해서 dtc -I dtb로 푼다. 빌드한 dtb와는 dtdiff로 비교한다. 부트로더가 /chosen이나 다른 속성을 고쳤을 수 있고, 커널도 kaslr-seed·rng-seed를 지우므로 blob이 빌드 결과와 바이트 단위로 같지는 않다.

I read /proc/device-tree — model first, then the node in question. For the whole tree, dtc -I fs -O dts /proc/device-tree, or copy /sys/firmware/fdt and decompile it. Then dtdiff it against the dtb I built. Expect /chosen to differ: the bootloader fills in bootargs and initrd addresses, and the kernel wipes kaslr-seed and rng-seed, so it's never byte-identical.

꼬리 질문: 보드에 dtc가 없으면? → cat/hexdump로 속성을 읽거나, /sys/firmware/fdt를 base64로 콘솔에 찍어 호스트에서 되살린다.

Q. You changed the .dts, rebuilt, and nothing changed on the board. How do you debug?

A. 먼저 보드에서 /proc/device-tree/model이 내 dts인지 본다. 다르면 배포 문제다 — U-Boot fdtfile, Yocto KERNEL_DEVICETREE, FIT 이미지. 같으면 dtdiff로 빌드 dtb와 런타임 트리를 비교해 부트로더 fixup이나 오버레이를 찾는다. 그것도 같으면 빌드 결과가 소스 의도와 다른 것이므로 .dts.tmp를 평탄화해서 나중 층이 덮었는지, 라벨 오타가 있는지 본다.

I start on the board, not in the source. If /proc/device-tree/model isn't my board, it's a deployment problem — wrong fdtfile, the dtb not in the image, or a FIT with an old blob. If it is, I dtdiff the built dtb against the live tree to catch bootloader fixups or overlays. If those match, I flatten the preprocessed source to see whether a later include overrode my property.

Q. How would you organize device trees for one SoM used on several carrier boards and hardware revisions?

A. SoC dtsi는 업스트림 그대로 두고, SoM 공통 dtsi 하나, SoM 변형(예: Wi-Fi 유무) dtsi, 캐리어마다 dtsi 하나를 두고, 조합마다 include 몇 줄짜리 얇은 dts를 둔다. Toradex Verdin이 2 × 5 = 10개 dts를 이렇게 관리한다. 리비전 차이는 이전 리비전 dts를 include하고 차이만 덮는 dts나 오버레이로, 옵션 보드는 오버레이로 분리한다.

Keep the SoC .dtsi untouched, one .dtsi for what's on the SoM, one per SoM variant, one per carrier, and then a tiny .dts per combination that's just includes, model and compatible. Toradex's Verdin does exactly that — two module variants times five carriers gives ten board files. Board revisions get a .dts that includes the previous revision and overrides only the delta, and add-on boards become overlays.

15. 요약 & 체크리스트#

DT 파일 구조는 하드웨어 계층(SoC → SoM → 캐리어 → 보드)을 파일 계층(.dtsi → .dtsi → .dtsi → .dts)으로 옮긴 것이다. #include는 cpp가 처리하는 텍스트 붙여넣기라서 계층의 의미는 결국 "펼친 텍스트의 순서"이고, dtc는 같은 노드의 정의를 그 순서대로 병합한다(같은 속성은 나중 값, 자리는 처음 위치, 새 속성은 끝에). 위층은 &label { }로 아래층 노드를 다시 열어 status = "okay"로 켜고, 필요하면 /delete-property/·/delete-node/로 지우며, SoC 벤더는 /omit-if-no-ref/로 안 쓰는 핀 그룹을 뺀다. 커널은 scripts/Makefile.dtbs의 cmd_dtc로 gcc -E → dtc를 돌려 dtb를 만들고, 의존성 파일로 증분 빌드하며, 오버레이 베이스에만 -@로 __symbols__를 남긴다. 런타임에는 라벨·매크로·include가 모두 사라지고 device_node 트리만 남는다. 그 트리는 /proc/device-tree(= /sys/firmware/devicetree/base)로, 원본 blob은 /sys/firmware/fdt로 볼 수 있으며, 디버깅은 항상 보드 → 빌드 결과 → 소스 순서로 좁힌다. Verdin iMX8M Plus 실측에서 SoC 층은 노드 280개를 정의만 하고 okay가 0개였고, 캐리어 층이 okay 35개를 켰다.
