0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어를 만들 때 "이 보드는 NAND 채널이 8개, 저 보드는 4개"를 어떻게 처리했는지 떠올려 보자. 아마 board_config.h에 #define NUM_CH 8을 두거나, 플래시의 특정 섹터에 있는 설정 블록(구조체)을 부팅 때 읽어서 전역 변수에 채웠을 것이다. 코드와 보드 설정을 분리하는 것, 그리고 설정 블록은 정해진 바이트 형식으로 저장돼 있어서 읽는 쪽이 파싱해야 한다는 것 — 이게 Device Tree를 읽는 드라이버의 본질이다.

Linux에서는 그 "설정 블록"이 DTB(Device Tree Blob)이고, 드라이버는 probe() 안에서 자기 노드의 속성(property)을 읽어 동작을 정한다. 예를 들어 센서 키트의 IMU 드라이버라면:

  • reg = <0x68> — I2C 주소 (버스 코어가 대신 읽어 준다, D4)
  • interrupts, reset-gpios, vdd-supply — 자원 (각 서브시스템 API가 대신 읽어 준다, D4)
  • sample-rate = <1000>, mount-matrix = ..., label = "imu-left" — 드라이버 자신이 직접 읽어야 하는 설정값. 이 노트의 주제다.

그림 1 — DTS가 DTB로 컴파일되고, 커널이 부팅 초기에 이를 device_node 트리로 풀어 놓는다(unflatten). 드라이버는 probe()에서 두 가지 API 계열 중 하나로 그 트리를 읽는다.

이 노트는 그림 1의 마지막 줄을 끝까지 판다. 순서는 이렇다.

  1. 실습용 "풍부한" 노드를 QEMU virt DT에 추가한다 (§1).
  2. 커널이 그 노드를 메모리에 어떤 구조체로 들고 있는지 본다 (§2).
  3. OF API로 모든 타입을 읽는다 (§3) → 일부러 에러를 낸다 (§4) → 자식 노드와 refcount (§5) → phandle (§6).
  4. 같은 것을 device_property_*로 읽고, DT가 없는 "보드"(software node)에서도 같은 드라이버가 도는 걸 본다 (§7).
  5. 유저스페이스에서 같은 바이트를 본다 (§8).

실행 환경: 커널 모듈은 Lima VM elinux(호스트 커널 uname -r = 7.0.0-38-generic) 안에서 공용 랩의 Linux 6.18.55 빌드 트리로 컴파일하고, QEMU virt(cortex-a57, 512 MB, TCG) 게스트에서 insmod해서 확인했다. 아래 모든 출력은 실제 실행 결과다. dmesg 타임스탬프는 실행마다 다르다. 모듈 빌드는 -Wall 포함 커널 기본 경고 옵션에서 경고 0개다.

2. 커널 안의 DT — FDT blob에서 device_node 트리로#

2.1 직관: "플래시의 설정 블록을 RAM의 연결 리스트로 파싱해 둔다"#

DTB는 flattened 형식이다. 바이트를 순서대로 읽어야만 구조를 알 수 있는 토큰 스트림이다 (D5). 매번 이걸 처음부터 스캔하면 느리니까, 커널은 부팅 초기에 unflatten_device_tree()로 한 번 쭉 파싱해서 포인터로 연결된 트리를 만들어 둔다. 펌웨어로 치면 "부팅 때 설정 섹터를 한 번 읽어서 struct board_cfg 배열을 채워 두는 것"과 같다.

2.2 예제 2 — blob 안의 노드를 바이트 단위로 보기#

무엇을 확인하나: DTB의 struct 블록에서 d8-sensor-a의 시작 토큰과 첫 두 속성을 직접 디코딩한다. (Python은 VM에서 -I로 실행)

출력에서 볼 것:

  • 노드는 FDT_BEGIN_NODE(1) + 이름(NUL 포함, 4바이트 정렬), 속성은 FDT_PROP(3) + len + nameoff + 값(4바이트 정렬). 모든 정수 필드가 빅엔디안이다.
  • 속성 이름은 struct 블록에 없고 strings 블록의 오프셋(nameoff)으로만 나온다. compatible, reg 같은 이름이 수백 번 반복돼도 문자열은 한 번만 저장된다.
  • sample-rate의 값 4바이트는 00 00 03 e8 = 1000. ARM64는 리틀엔디안이므로 이 4바이트를 u32로 그냥 캐스팅하면 0xe8030000이 된다. API가 변환해 주는 이유다 (§3.6).

2.4 of_find_property — 모든 읽기 함수의 출발점#

drivers/of/base.c의 실제 코드 (6.18.55):

공개 함수 of_find_property()는 이걸 devtree_lock(raw spinlock)으로 감싼 것이다. 핵심 세 가지:

  • 선형 탐색이다. 노드당 속성이 많아야 수십 개라 해시 테이블을 둘 이유가 없다. 그래도 인터럽트 핸들러나 hot path에서 DT를 반복해서 읽지 말고, probe()에서 한 번 읽어 드라이버 private 구조체에 저장하는 게 원칙이다. 펌웨어에서 "설정 섹터를 매번 읽지 않고 부팅 때 RAM에 캐시"하는 것과 같다.
  • of_prop_cmp는 strcmp(대소문자 구분)다.
  • np == NULL이면 그냥 NULL을 돌려준다. 그래서 dev->of_node가 없는(DT 없이 만든) 디바이스에서 OF 함수를 불러도 크래시하지 않고 "속성 없음"(-EINVAL)이 된다.

2.5 예제 3 — 커널 모듈로 노드와 속성 리스트 직접 걷기, 그리고 OF API로 모든 타입 읽기#

무엇을 확인하나: dev.of_node의 필드를 찍고, properties 리스트를 손으로 걸은 다음, 각 타입을 해당 OF 함수로 읽는다. compatible = "d8,sensor-v2"에 매칭되는 platform 드라이버다 (매칭 원리는 D3).

게스트 스크립트는 두 줄이다: insmod /d8_of.ko 와 dmesg | grep d8_of.

출력에서 볼 것:

  • %pOF는 노드의 전체 경로(/d8-sensor-a)를, full_name 필드는 한 단계 이름만 준다. 로그에는 %pOF를 쓰는 게 관례다. (%pOFn은 유닛 주소 없는 이름, %pOFP는 유닛 주소 포함 이름 — §5에서 사용.)
  • 속성 리스트 끝에 DTS에 없던 name(len 12 = "d8-sensor-a" + NUL)이 있다. 옛 OpenFirmware 호환을 위해 unflatten이 붙이는 의사 속성이다. /proc/device-tree에도 name 파일로 보인다.
  • d8,invert-x와 d8,empty-name은 length 0. bool 속성은 "값 없는 속성"이다.
  • d8,timeout-ms는 없으므로 ret=-22(-EINVAL)이고 tmo는 미리 넣어 둔 50 그대로다. OF 읽기 함수는 실패하면 출력 변수를 건드리지 않는다(drivers/of/property.c 문서 주석: "pointer to return value, modified only if no error"). 이게 §4의 "optional + default" 관용구의 근거다.

3. OF API 정리 — 이름 체계만 알면 외울 게 없다#

3.1 이름 규칙#

of_property_ + 동작(read, count, match, present) + 타입(u8/u16/u32/u64, string) + 형태(_array, _index, _elems). 모두 첫 인자가 const struct device_node *다.

함수반환내부에서 하는 일
of_property_read_u32(np, name, &v)0 / 음수 errnoof_property_read_u32_array(np, name, &v, 1) 의 inline wrapper
of_property_read_u32_array(np, name, buf, n)0 / 음수길이 ≥ 4·n 확인 후 be32_to_cpup() n번
of_property_read_variable_u32_array(np, name, buf, min, max)읽은 개수 / 음수위 두 함수의 실제 구현. max=0이면 상한 없음
of_property_read_u32_index(np, name, i, &v)0 / 음수i번째 cell 하나
of_property_read_u64(np, name, &v)0 / 음수길이 ≥ 8 확인 후 of_read_number(val, 2)
of_property_count_u32_elems(np, name)개수 / 음수length / 4 (나눠떨어지지 않으면 -EINVAL + pr_err)
of_property_read_string(np, name, &s)0 / 음수s가 DTB 안을 가리키는 포인터. 복사 아님

u8/u16 배열 버전도 있다 (DTS에서 /bits/ 8 <...> 또는 [01 02 03] 바이트 문자열로 쓴 속성용). 그리고 of_property_for_each_u32(np, name, u), of_property_for_each_string(np, name, prop, s) 순회 매크로가 있다.

3.2 정수와 배열 — "최소 길이"만 본다#

of_property_read_u32()는 내부적으로 sz_min = 1, sz_max = 0(상한 없음)으로 부른다. 즉 속성이 4바이트보다 길어도 에러가 아니고 첫 cell만 돌려준다. of_property_read_u32(np, "gains", &v)는 1을 돌려줄 것이다. 반대로 of_property_read_u32_array(np, "gains", buf, 8)은 길이 16 < 32라 -EOVERFLOW다 (§4에서 실측).

3.3 64비트 값#

DTB엔 64비트 타입이 없다. /bits/ 64 <X>나 <hi lo>나 똑같이 cell 2개(상위 cell 먼저)다. of_property_read_u64()는 of_read_number(val, 2) = (be32(val[0]) << 32) | be32(val[1])로 조립한다. 예제 3에서 0x123456789abcdef0이 제대로 나왔다. reg의 주소처럼 #address-cells에 따라 1 또는 2 cell인 값은 직접 읽지 말고 of_address_to_resource()/platform_get_resource()에 맡긴다 (D4, F 모듈).

3.4 문자열과 문자열 리스트#

문자열 리스트는 "a\0b\0c\0"처럼 NUL로 이어 붙인 바이트열이다 (modes의 length 23 = 10 + 7 + 6). of_property_read_string()이 돌려주는 포인터는 DTB 내부를 가리키므로:

  • kfree() 하면 안 된다.
  • 노드가 사라지지 않는 한(보통 DT는 부팅 내내 고정) 계속 유효하다. 단 overlay(D6)로 붙었다 떨어지는 노드라면 devm_kstrdup()으로 복사해 두는 게 안전하다.

of_property_match_string()은 "이 문자열이 리스트 몇 번째에 있나"를 준다. clock-names/reg-names/interrupt-names에서 이름으로 인덱스를 찾을 때 서브시스템 코드가 내부에서 이걸 쓴다.

5. 자식 노드 순회와 refcount#

5.1 왜 자식 노드인가#

한 칩이 여러 개의 "채널·포트·LED·레귤레이터 출력"을 가질 때 DT는 자식 노드로 표현한다. 예: 다채널 ADC의 channel@N, PMIC의 regulators { buck1 {...}; ldo2 {...}; }, LED 컨트롤러의 led@N, 이더넷 스위치의 ports { port@0 ... }. 드라이버는 자식을 순회하며 채널마다 설정을 읽는다.

5.2 refcount 규칙 — Don이 아는 "핸들 빌리기/반납"#

device_node는 kobj 안의 kref로 참조 카운트를 가진다(CONFIG_OF_DYNAMIC일 때만 실제로 카운트한다 — overlay·핫플러그로 노드가 사라질 수 있기 때문. 정적 DT만 쓰는 구성에서는 of_node_get/put이 빈 inline 함수다). 규칙은 RTOS의 "객체 핸들을 얻으면 반드시 release"와 같다.

  • 노드를 돌려주는 OF 함수는 참조를 +1 한 채로 돌려준다: of_get_child_by_name, of_find_node_by_*, of_parse_phandle, of_get_parent, of_parse_phandle_with_args의 args.np 등. 다 쓰면 of_node_put().
  • for_each_child_of_node(parent, child)는 내부에서 of_get_next_child(parent, prev)를 부르는데, 이 함수가 다음 노드를 get 하고 이전 노드를 put 한다 (__of_get_next_child: next = prev ? prev->sibling : node->child; of_node_get(next); of_node_put(prev);). 그래서 루프를 끝까지 돌면 균형이 맞는다.
  • 루프를 break/return/goto로 빠져나가면 현재 child의 참조가 +1로 남는다. 그 노드를 계속 쓸 거면 나중에 put, 아니면 즉시 of_node_put(child).
  • 6.x 커널은 이 실수를 없애려고 _scoped 매크로를 추가했다. 랩 6.18.55의 include/linux/of.h에 실제로 있다:

__free(device_node)는 GCC/Clang의 cleanup 속성으로, 변수가 스코프를 벗어날 때(break, return 포함) DEFINE_FREE(device_node, ..., if (_T) of_node_put(_T))에 정의된 put을 자동 호출한다. C++의 RAII, 또는 펌웨어에서 "함수 탈출 지점마다 unlock을 매크로로 강제"하던 것의 컴파일러 버전이다. 같은 계열로 for_each_available_child_of_node_scoped, device_for_each_child_node_scoped, fwnode_for_each_available_child_node_scoped가 있다. 루프 변수는 매크로 안에서 선언되므로 바깥에 따로 선언하지 않는다.

  • 전역 번호는 GPIO 컨트롤러 probe 순서에 따라 바뀐다 (D4, H 모듈).
  • DT의 GPIO_ACTIVE_LOW 플래그를 무시한다. gpiod는 "논리값 1 = assert"로 추상화해서 극성을 DT가 결정한다.

7. 통합 device property API (fwnode) — 새 드라이버의 기본값#

7.1 왜 또 다른 API가 있나#

같은 IMU 칩이 ARM 보드(DT)에도, x86 산업용 PC(ACPI)에도 붙는다. OF API로 쓴 드라이버는 dev->of_node가 없는 ACPI 시스템에서 모든 읽기가 -EINVAL이 된다. 그래서 커널은 firmware node(fwnode) 라는 추상 계층을 만들었다. struct fwnode_handle은 ops(함수 테이블) 포인터를 가진 작은 구조체이고, device_node 안에 하나(np->fwnode), ACPI 디바이스 안에 하나, software node 안에 하나 들어 있다. 드라이버는 device_property_read_u32(dev, ...)만 부르고, 실제 데이터 소스는 ops가 결정한다. 펌웨어로 치면 "설정값을 EEPROM에서 읽든 OTP에서 읽든 cfg_get_u32(key) 하나로 읽게 만든 HAL"이다.

호출 경로 (DT 위에서):

dev_fwnode(dev)는 dev->of_node가 있으면 &dev->of_node->fwnode, 없으면 dev->fwnode를 준다. 마지막 줄의 secondary fallback이 실무에서 중요하다: DT에 없는 속성을 보드 코드나 다른 드라이버가 software node로 "덧붙일" 수 있다(primary가 -EINVAL일 때만 secondary를 본다).

그림 6 — 두 API 계열의 관계. DT 위에서는 결국 같은 함수에 도착하므로 성능·결과 차이는 없다. 차이는 "ACPI와 software node에서도 동작하느냐"다.

Q. How does a driver read a configuration value like a sample rate from the device tree?

A. probe에서 device_property_read_u32(dev, "sample-rate", &val)(또는 DT 전용이면 of_property_read_u32(dev->of_node, ...))를 부른다. 반환값 0이면 성공, -EINVAL이면 속성 없음, -EOVERFLOW면 길이 불일치다. 값은 DT에서 빅엔디안 cell이고 API가 CPU 엔디안으로 바꿔 준다. 읽은 값은 범위 검사 후 private 구조체에 저장하고, 이후엔 DT를 다시 읽지 않는다.

In probe I call device_property_read_u32(dev, "sample-rate", &val) — or of_property_read_u32 on dev->of_node if the driver is DT-only. Zero means success, -EINVAL means the property is absent, -EOVERFLOW means the length doesn't match. DT cells are big-endian and the helper converts them. I range-check the value, store it in the driver's private struct, and never touch the DT again in the hot path.

꼬리 질문: "속성이 없으면?" → optional이면 미리 기본값을 넣어 두고 반환값을 무시(실패 시 출력은 안 바뀐다), required면 dev_err_probe()로 probe 실패.

Q. What is the difference between the of_* API and the device_property_* API? Which one would you use for a new driver?

A. of_*는 struct device_node를 직접 받는 DT 전용 API이고, device_property_*는 struct fwnode_handle 추상화 위의 통합 API라서 DT, ACPI _DSD, software node 모두에서 동작한다. DT 위에서는 내부적으로 같은 OF 코드를 부르므로 결과는 같다. 새 드라이버는 device_property_*를 쓰고, of_graph나 phandle-args map처럼 DT 전용 기능이 필요할 때만 of_*를 쓴다.

The of_* helpers take a struct device_node and only work with device tree. The device_property_* helpers sit on top of the fwnode abstraction, so the same driver works with DT, ACPI _DSD properties, and software nodes; on a DT system they end up in the same OF code. For a new driver I'd use device_property_* and device_get_match_data, and only drop to of_* for DT-specific things like of_graph.

Q. When do you need of_node_put()?

A. 노드 포인터를 돌려주는 OF 함수는 참조를 올려서 준다 — of_parse_phandle, of_get_child_by_name, of_find_node_by_*, phandle args의 np. 다 쓰면 put 해야 한다. for_each_child_of_node는 반복마다 다음을 get, 이전을 put 하므로 끝까지 돌면 균형이 맞지만 break나 return으로 나가면 현재 child를 put 해야 한다. 최신 커널은 __free(device_node)를 쓰는 _scoped 매크로로 이걸 자동화한다.

Any OF function that returns a node pointer returns it with an elevated refcount — of_parse_phandle, of_get_child_by_name, of_find_node_by_*, and the np in of_phandle_args — so I put it when done. for_each_child_of_node gets the next and puts the previous on each iteration, so a full loop is balanced, but breaking out leaves the current child held. Recent kernels have for_each_child_of_node_scoped, which uses the cleanup attribute to put it automatically.

꼬리 질문: "정적 DT인데 refcount가 왜 필요?" → overlay와 dynamic DT(CONFIG_OF_DYNAMIC)에서 노드가 해제될 수 있다. 정적 구성에선 get/put이 no-op이지만 코드는 항상 맞게 써야 한다.

Q. How does of_parse_phandle_with_args work? Give an example.

A. clocks = <&clkc 3> 같은 속성에서 첫 cell은 phandle, 이후 인자 개수는 대상 노드의 #clock-cells가 정한다. 함수는 phandle로 노드를 찾고, 그 노드의 cells 속성을 읽어 그만큼 인자를 of_phandle_args에 채워 준다. index로 리스트의 몇 번째 항목인지 고르고, 범위를 넘으면 -ENOENT. 반환된 np는 put 해야 한다. clk, gpio, dma, pwm 프레임워크가 내부에서 다 이걸 쓴다.

In clocks = <&clkc 3>, the first cell is a phandle and the number of argument cells is defined by the provider's #clock-cells. The helper resolves the phandle to a node, reads that cells property, and fills of_phandle_args with the node and the arguments. The index selects which entry in the list; past the end it returns -ENOENT. The returned np holds a reference. The clk, gpio, dma and pwm frameworks all build on it.

Q. A property exists in the DTS but your driver reads 0 / garbage. How do you debug it?

A. 먼저 /proc/device-tree에서 커널이 실제로 받은 바이트를 hexdump로 본다 — 부트로더가 다른 DTB를 주거나 고쳐 넣는 일이 많다. 그다음 of_node 심볼릭 링크로 디바이스가 맞는 노드에 붙었는지, 속성 이름 오타, 타입 불일치(문자열을 u32로 읽어도 에러가 안 남)를 확인하고, 반환값을 로그로 찍는다. 근본 대책은 YAML 바인딩과 dtbs_check.

First I check what the kernel actually received: hexdump the file under /proc/device-tree, because the bootloader may have loaded or patched a different DTB. Then I confirm the device's of_node symlink points at the node I expect, look for a typo in the property name, and check for a type mismatch — reading a string as u32 succeeds silently. I log the return codes. The long-term fix is a YAML binding and dtbs_check.

Q. How do you support two variants of a chip in one driver?

A. of_device_id 테이블에 compatible마다 .data로 변형별 상수 구조체(최대 ODR, 레지스터 맵, 기능 플래그)를 달고, probe에서 device_get_match_data(dev)로 꺼낸다. ACPI match table이나 I2C/platform id_table의 driver_data도 같은 구조체를 가리키게 하면 펌웨어 종류에 상관없이 한 경로로 처리된다. probe 곳곳에서 compatible 문자열을 비교하지 않는다.

I attach a const per-variant struct — max ODR, register layout, feature flags — to each compatible via the .data field of the of_device_id table, and fetch it with device_get_match_data in probe. The ACPI table and the bus id_table point to the same structs, so every firmware path ends in one code path. I avoid sprinkling of_device_is_compatible checks through the driver.

Q. What's the difference between of_property_read_bool and of_property_present?

A. 둘 다 존재 여부를 bool로 돌려주지만, read_bool은 "값이 없는 진짜 boolean 속성"용이고 값이 있는 속성에 쓰면 6.x 커널은 경고를 찍는다. present는 타입과 상관없이 "이 속성이 있나"를 묻는 용도다. 예를 들어 clocks가 있는지 볼 때는 present.

Both return whether the property exists. read_bool is meant for real boolean flags with no value, and recent kernels warn if you use it on a property that has a value. of_property_present is the type-agnostic presence check — for example, checking whether a clocks property exists.

Q. Why is of_get_named_gpio deprecated?

A. 전역 GPIO 번호를 돌려주는 legacy integer API라서 컨트롤러 probe 순서에 따라 번호가 바뀌고, DT의 active-low 플래그를 무시하며, DT 전용이다. 대신 devm_gpiod_get(dev, "reset", flags)로 디스크립터를 받으면 극성은 DT가 정하고 ACPI에서도 동작한다. 선택 핀은 _optional로 받아 NULL이면 그냥 생략된다.

It returns a global integer GPIO number, which depends on controller probe order, ignores the active-low flag in the DT, and only works with device tree. The descriptor API — devm_gpiod_get(dev, "reset", flags) — handles polarity from firmware and works with ACPI too. For optional pins, devm_gpiod_get_optional returns NULL when absent, and gpiod calls on NULL are no-ops.

15. 요약 & 체크리스트#

DT는 부팅 초기에 struct device_node 트리로 풀리고, 각 노드는 struct property의 단일 연결 리스트를 가진다. 속성 값은 DTB 안을 가리키는 빅엔디안 바이트열이고 타입 정보가 없다 — 타입은 읽는 함수가 정한다. OF API(of_property_read_*)는 device_node를 직접 받고, 통합 API(device_property_*)는 fwnode ops를 거쳐 DT 위에서는 같은 코드에 도착하지만 ACPI와 software node에서도 동작하므로 새 드라이버의 기본값이다. 에러는 -EINVAL(없음), -EOVERFLOW(길이 불일치), -ENODATA(주로 문자열에서 값 없음)이고, 실패 시 출력 변수가 안 바뀌는 성질로 "optional + default"를 짠다. 노드 포인터를 돌려주는 함수는 참조를 올리므로 put 해야 하고, 순회 중 탈출은 _scoped 매크로로 안전하게 한다. phandle 참조의 인자 개수는 provider의 #xxx-cells가 정한다. 변형별 차이는 .data + device_get_match_data()로 처리한다.
