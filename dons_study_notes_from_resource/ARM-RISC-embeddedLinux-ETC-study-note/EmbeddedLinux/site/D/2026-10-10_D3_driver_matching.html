D3. 드라이버 매칭 — compatible에서 probe()까지

138분 읽기1420줄51개 절

이 노트를 다 읽으면: DT 노드가 platform_device가 되고 of_match_table과 만나 probe()가 불리기까지의 함수 경로를 소스 이름 그대로 말할 수 있다 · fallback compatible 목록에서 어느 항목이 왜 이기는지(점수 규칙) 설명할 수 있다 · sysfs의 driver/of_node/modalias/driver_override/bind/unbind로 결합 상태를 보고 바꿀 수 있다 · "센서가 안 보인다"를 노드 없음 / device 없음 / 매칭 실패 / probe 실패 / defer 다섯 갈래로 나눠 진단할 수 있다 왜 필요한가: 드라이버 면접의 거의 모든 질문은 "How does a driver get bound to a device?"로 시작하거나 끝나고, 실무 첫 달에는 "DT에 센서를 넣었는데 probe가 안 불린다"를 반드시 만난다 Don 기준 난이도: 레지스터 주소·버스·초기화 순서는 펌웨어에서 이미 한다 / 새로 배울 부분은 "누가 init 함수를 부르나"를 커널이 문자열 매칭으로 정한다는 점, 그리고 그 결과가 sysfs 링크로 다 보인다는 점 선행 노트: D1(왜 DT인가), D2(DT 문법), E3(커널 모듈) — G2(디바이스 모델)·G3(platform driver)로 이어진다

0. 큰 그림 — 이게 왜 필요한가#

Don의 SSD 펌웨어에서 NAND 컨트롤러를 초기화하는 장면을 떠올려 보자. main()이 nand_init(NAND_BASE)를 부른다. 누가 어떤 초기화 함수를 어떤 주소로 부를지는 소스에 하드코딩되어 있다. 보드가 바뀌면 #ifdef BOARD_REV_B가 늘어난다.

Linux는 이 결정을 런타임 매칭으로 바꿨다.

  • 하드웨어 쪽: "이 주소에 이런 칩이 있다"는 사실은 Device Tree에 데이터로 적는다 (compatible = "don,imu-v2", reg = <...>).
  • 소프트웨어 쪽: 드라이버는 "나는 이런 칩을 다룰 수 있다"는 문자열 표(of_match_table)만 내놓는다.
  • 커널(driver core)이 둘을 짝지어서, 짝이 맞으면 드라이버의 probe()를 그 장치 하나에 대해 부른다. 장치가 3개면 probe()는 3번 불린다.

펌웨어 비유로 말하면, probe()는 "커널이 대신 불러 주는 nand_init()"이고, 매칭은 "부트 때 칩 ID 레지스터를 읽어서 함수 포인터 테이블에서 init 함수를 고르는 코드"를 커널이 일반화해 둔 것이다. 다만 SoC 내부 IP는 ID 레지스터로 스스로를 알리지 못하므로(non-discoverable, D1), ID 역할을 DT의 compatible 문자열이 대신한다.

그림 1 — 왼쪽(장치)과 오른쪽(드라이버)은 서로를 모른 채 따로 만들어지고, 버스(platform bus)의 match가 둘을 짝지어 probe()를 부른다. 어느 쪽이 먼저 와도 된다 (§8).

이 노트는 그림 1의 모든 상자를 QEMU에서 실제로 돌려 본다. 순서는 이렇다.

1.3 예제 2 — 드라이버 d3_sensor (platform driver, compatible 2개 + match data)#

무엇을 확인하나: 최소한의 platform driver가 갖춰야 할 것 — of_match_table, MODULE_DEVICE_TABLE(of, ...), probe()/remove() — 과 match data(.data)로 칩 세대별 정보를 넘기는 관용구.

출력에서 볼 것: 경고 0개. MODULE_DEVICE_TABLE(of, d3_of_match) 한 줄이 .ko 안에 alias: 4줄을 만들었다 (§9에서 이 alias가 자동 로딩의 열쇠가 된다). d3_hub.c는 §8에서 쓴다. 코드에서 기억할 관용구 네 가지:

  • struct of_device_id는 name, type, compatible, data 필드를 가진다. 현대 드라이버는 거의 compatible과 data만 쓴다. 마지막 { }(sentinel)가 없으면 매칭 루프가 배열 끝을 넘어 읽는다.
  • .data에는 칩별 차이(레지스터 맵, FIFO 크기, 기능 플래그)를 담은 구조체 포인터를 넣는다. probe()에서 of_device_get_match_data(dev)로 꺼내면 "어느 compatible로 매칭됐나"를 if-else 문자열 비교 없이 안다. ACPI까지 고려하는 새 코드는 device_get_match_data()(linux/property.h, D8)를 쓴다.
  • module_platform_driver(x)는 module_init에서 platform_driver_register(&x), module_exit에서 platform_driver_unregister(&x)를 부르는 매크로다(E3).
  • 6.18의 platform_driver.remove는 void를 돌려준다(예전 커널은 int). 오래된 BSP 코드를 옮길 때 컴파일 에러로 바로 보인다.

2. 1단계 — DT 노드가 platform_device가 되기까지#

2.1 직관 — "명단은 부팅 때 미리 만든다"#

드라이버가 하나도 없어도, 커널은 부팅 중에 DT를 훑어서 "여기 장치가 있다"는 객체(struct platform_device)를 먼저 만들어 둔다. 드라이버는 나중에 와서 그 명단에서 자기 짝을 찾는다. 펌웨어로 치면 부트 코드가 하드웨어 구성표를 RAM에 테이블로 만들어 두고, 각 모듈 init이 그 테이블을 검색하는 구조다.

2.2 정의 — 세 단계#

  1. unflatten: 부트로더가 넘긴 FDT(평평한 바이너리 블롭)를 unflatten_device_tree()가 struct device_node의 트리(부모·자식·형제 포인터, 속성 리스트)로 펼친다. arm64에서는 setup_arch()(arch/arm64/kernel/setup.c)가 부른다. 이 트리가 /proc/device-tree = /sys/firmware/devicetree/base로 보인다.
  2. populate: of_platform_default_populate_init()가 arch_initcall_sync 레벨(C6)에서 돈다. 이 함수는 결국 of_platform_default_populate(NULL, ...) → of_platform_populate(root, match_table, ...)를 부르고, 루트의 각 자식에 대해 of_platform_bus_create(child, ..., strict=true)를 재귀로 부른다.
  3. device 생성: of_platform_device_create_pdata()가 of_device_alloc()으로 platform_device를 만들고(reg→struct resource, interrupts→IRQ 리소스) of_device_add() → device_add()로 등록한다.

of_platform_bus_create()의 규칙을 랩 소스에서 그대로 옮기면:

핵심 결론 두 가지:

  • 루트 직속 노드와 simple-bus 계열 노드의 자식만 자동으로 platform device가 된다.
  • I2C 컨트롤러 밑의 센서 노드는 컨트롤러 노드가 simple-bus가 아니므로 여기서 만들어지지 않는다. 컨트롤러 드라이버가 probe될 때 I2C 코어가 자식들을 i2c_client로 만든다 (§8, H5).

출력에서 볼 것:

  • probe()가 5번 불렸다. 같은 드라이버 코드가 장치 인스턴스마다 한 번씩 — 펌웨어의 "init 함수에 base 주소 인자를 다르게 넘겨 여러 번 호출"과 같다. 그래서 드라이버는 전역 변수가 아니라 장치별 구조체(platform_set_drvdata)에 상태를 둔다(G3).
  • 장치 이름 9100000.d3-sensor는 of_device_make_bus_id()가 "CPU 주소로 번역한 reg + . + 노드 이름"으로 지은 것이다. simple-bus 밑 reg = <0x100 ...>이 ranges를 거쳐 9200100이 된 것도 보인다. 주소 번역이 안 되는 노드(d3-hub)는 노드 이름만 쓴다.
  • %pR이 [mem 0x09100000-0x09100fff] — reg가 struct resource로 변환되어 있다. 실제 드라이버는 여기서 devm_platform_ioremap_resource(pdev, 0)(H1)를 부른다. 이 실습 주소에는 실제 하드웨어가 없으므로 일부러 ioremap/접근은 하지 않았다.

3.1 드라이버는 "자기소개서"를 버스에 제출한다#

3.2 compatible 문자열 규칙#

  • 형식은 "vendor,device". vendor 접두어는 Documentation/devicetree/bindings/vendor-prefixes.yaml에 등록된 것(예: bosch, st, ti, nxp, invensense)을 쓴다. 이 노트의 don은 실습용 가짜 접두어다 (upstream이라면 dtbs_check가 경고한다, D7).
  • 목록은 가장 구체적인 것부터 쓴다: "don,imu-v3", "don,imu". 뜻은 "나는 정확히 v3이고, v3 전용 드라이버가 없으면 v1 드라이버로 돌려도 된다". 그러므로 fallback 항목은 진짜로 하위 호환일 때만 넣는다. v3에서 레지스터 맵이 바뀌었는데 "don,imu"를 fallback으로 적으면, 드라이버가 v1 레지스터를 써서 조용히 쓰레기 값을 읽는다.
  • SoC IP는 흔히 "fsl,imx8mm-i2c", "fsl,imx21-i2c"처럼 "이 SoC의 인스턴스" + "처음 나온 호환 IP" 쌍으로 쓴다. 드라이버는 대개 오래된 이름 하나만 테이블에 두고, 새 SoC에서 버그 회피가 필요해지면 구체적 이름을 테이블에 추가해서 다른 .data를 준다.
  • 와일드카드("don,imu-*")나 대소문자 무시 같은 것은 없다. of_compat_cmp()는 정확한 문자열 비교다(대부분의 아키텍처에서 대소문자 구분).

5. 4단계 — really_probe()에서 probe()까지#

5.1 두 입구, 하나의 길#

매칭 시도는 두 방향에서 시작될 수 있다.

  • 드라이버가 나중에 올 때 (insmod): driver_register() → bus_add_driver() → driver_attach() → bus_for_each_dev()로 모든 장치에 __driver_attach(dev, drv).
  • 장치가 나중에 생길 때 (부팅 populate, hub의 자식 생성, 핫플러그): device_add() → bus_probe_device() → device_initial_probe() → __device_attach() → bus_for_each_drv()로 모든 드라이버에 __device_attach_driver().

둘 다 driver_match_device(drv, dev)를 부르는데, 이것은 drivers/base/base.h의 인라인 함수로 drv->bus->match(dev, drv) — 즉 platform_match()다. 일치하면 driver_probe_device() → __driver_probe_device() → really_probe().

really_probe()가 하는 일(drivers/base/dd.c, 6.18):

  1. device_links_check_suppliers() — fw_devlink가 만든 공급자(클럭·레귤레이터·GPIO 컨트롤러 등) 링크 중 아직 준비 안 된 것이 있으면 바로 -EPROBE_DEFER.
  2. device_set_driver(dev, drv) — dev->driver를 채운다.
  3. pinctrl_bind_pins() — DT의 pinctrl-0("default" 상태)을 probe 전에 적용한다 (H4).
  4. bus->dma_configure — platform_dma_configure()가 of_dma_configure()로 DMA mask·IOMMU 설정 (H9).
  5. driver_sysfs_add() — sysfs driver 링크 생성.
  6. call_driver_probe() → bus->probe = platform_probe() → of_clk_set_defaults(), dev_pm_domain_attach() → drv->probe(pdev) = d3_probe().
  7. 성공하면 driver_bound() — 장치를 드라이버의 장치 목록에 넣고, 대기 중인 deferred 장치 재시도를 트리거한다.

call_driver_probe()의 반환값 처리도 외워 둘 만하다:

probe() 반환driver core의 반응로그
0bound(dev_dbg) "bound device to driver"
-EPROBE_DEFERdeferred 목록에 넣고 나중에 재시도(dev_dbg) "Driver ... requests probe deferral"
-ENODEV / -ENXIO"이 장치는 내 것이 아님" — 조용히 포기(dev_dbg) "probe with driver ... rejects match"
그 밖의 음수실패dev_err "probe with driver ... failed with error N"

-ENODEV가 조용한 이유: 드라이버가 칩 ID 레지스터를 읽어 보고 "내 칩이 아니네"라고 판단하는 정상 경로이기 때문이다. 반대로 진짜 실패를 -ENODEV로 돌려주면 아무 로그 없이 장치가 사라진다 — 디버깅을 어렵게 하는 흔한 실수다.

9.1 직관 — "장치가 자기 드라이버 이름을 외친다"#

드라이버가 모듈일 때 누가 insmod를 해 주나? 장치가 생기면 커널은 uevent(KOBJ_ADD)를 유저 공간으로 보낸다. 그 안에 MODALIAS=of:Nd3-sensorT(null)Cdon,imu-v2Cdon,imu가 있다. udev(또는 BusyBox mdev)가 이걸 받아 modprobe "$MODALIAS"를 실행한다. modprobe는 modules.alias(depmod가 모든 .ko의 alias:를 모아 만든 색인)에서 패턴 매칭을 해 d3_sensor를 찾는다.

10. deferred probe 미리보기#

10.1 직관#

센서 드라이버의 probe가 레귤레이터(전원), 클럭, GPIO, IRQ 컨트롤러가 필요하다고 하자. 그 공급자 드라이버가 아직 probe되지 않았다면? 펌웨어라면 init 순서를 손으로 맞춘다. Linux는 probe에서 -EPROBE_DEFER를 돌려주면 "나중에 다시 불러 줘" 로 처리한다. driver core는 그 장치를 deferred 목록에 넣고, 다른 드라이버가 하나 bind될 때마다(driver_bound() → driver_deferred_probe_trigger()) 목록 전체를 다시 시도한다. 그리고 late_initcall 시점에 한 번 더 몰아서 시도한다.

요즘 커널은 fw_devlink(기본 fw_devlink=on)가 DT의 phandle 참조(clocks, *-supply, gpios, interrupts…)를 보고 공급자→소비자 링크를 미리 만든다. 그래서 공급자가 준비되기 전에는 아예 probe를 시도하지 않는다(really_probe()의 device_links_check_suppliers(), 예제 8의 waiting_for_supplier 파일). 드라이버의 -EPROBE_DEFER는 그래도 필요하다 — DT에 표현되지 않은 의존성이나 fw_devlink가 모르는 속성이 있기 때문이다. 깊은 이야기는 G3.

14. 면접에서 이렇게 말한다#

Q. How does a driver get bound to a device on a Device Tree based system?

A. 부팅 때 커널이 DTB를 device_node 트리로 펼치고, of_platform_default_populate_init()가 루트와 simple-bus 밑의 compatible 있는 노드마다 platform_device를 만든다. 드라이버는 of_match_table을 가진 platform_driver를 등록한다. 장치든 드라이버든 나중에 추가되는 쪽에서 버스의 match(platform_match → of_driver_match_device)가 compatible 문자열을 비교하고, 맞으면 really_probe()가 pinctrl·DMA 설정 후 드라이버의 probe()를 장치마다 부른다. 결과는 sysfs의 driver 링크로 보인다.

At boot the kernel unflattens the DTB into a tree of device_nodes, and of_platform_populate creates a platform_device for every node with a compatible under the root or a simple-bus. A driver registers a platform_driver with an of_match_table. Whenever either side is added, the bus match function — platform_match, which calls of_driver_match_device — compares the compatible strings. On a match, really_probe sets up pinctrl and DMA and calls the driver's probe once per device. You can see the result as the driver symlink in sysfs.

꼬리 질문: "I2C 센서는요?" → I2C 노드는 컨트롤러 드라이버가 probe될 때 of_i2c_register_devices()가 i2c_client로 만들고, I2C 버스의 i2c_device_match가 같은 OF 매칭을 한다.

Q. A node has compatible = "vendor,chip-v3", "vendor,chip". What does that mean, and which driver entry wins?

A. 목록은 구체적인 것부터 쓴다. "정확히는 v3이고, v3 전용이 없으면 generic chip 드라이버로 돌려도 호환된다"는 뜻이다. 커널은 드라이버 테이블 전체에 점수를 매기는데, 노드 목록에서 앞쪽 문자열과 맞을수록 점수가 높다. 그래서 테이블에 v3 항목이 있으면 그게 이기고, 없으면 generic 항목으로 붙는다. 테이블 순서와는 무관하다 — 직접 테이블을 뒤집어 확인했다.

The list goes from most specific to most generic: it is exactly a v3, but it is compatible with the generic chip binding. The kernel scores every entry in the driver's table, and a match earlier in the node's list scores higher. So a v3 entry wins if the driver has one; otherwise it falls back to the generic one. The order of the driver table does not matter — I verified that by reversing the table.

Q. Your sensor node is in the device tree but probe is never called. How do you debug it?

A. 다섯 고리로 나눈다. /proc/device-tree에 노드가 있고 status가 okay인지, /sys/bus/<bus>/devices에 장치 객체가 있는지(없으면 부모 컨트롤러가 disabled이거나 probe 실패), 드라이버가 로드돼 있고 modalias와 modinfo alias가 맞는지, devices_deferred에 걸려 있는지, dmesg에 probe 실패가 있는지. 매칭 여부는 dyndbg로 drivers/base/dd.c를 켜면 "matched device with driver" 줄로 바로 보인다.

I split it into five links. Is the node in /proc/device-tree with status okay? Does a device object exist under the bus's devices directory in sysfs — if not, the parent controller is probably disabled or failed to probe. Is the driver loaded, and does the modalias match the module aliases? Is the device listed in devices_deferred? Is there a probe error in dmesg? Turning on dynamic debug for drivers/base/dd.c shows "matched device with driver" lines, which tells me immediately whether matching happened.

Q. What is MODULE_DEVICE_TABLE for? What breaks if you forget it?

A. 매칭 테이블을 .ko의 alias로 내보내는 매크로다. depmod가 이걸 색인으로 모으고, 장치가 생길 때 uevent의 MODALIAS로 udev가 modprobe해서 자동 로드한다. 빠뜨려도 insmod하면 매칭은 정상이라 개발 중엔 모르고, 제품에서 자동 로드가 안 되는 형태로 드러난다.

It exports the match table as module aliases in the .ko. depmod indexes them, and when a device appears udev runs modprobe with the MODALIAS from the uevent, which autoloads the right module. If you forget it, insmod still works because matching happens in the kernel, so you don't notice during development — it shows up later as a driver that never autoloads on the product.

Q. What is -EPROBE_DEFER and when do you return it?

A. probe에 필요한 공급자(레귤레이터, 클럭, GPIO, PHY 등)가 아직 준비되지 않았을 때 돌려준다. driver core가 장치를 deferred 목록에 넣고, 다른 드라이버가 bind될 때마다 다시 시도한다. 보통 devm_regulator_get() 같은 함수가 이 값을 돌려주면 그대로 전파하고, dev_err_probe()를 쓰면 이유가 devices_deferred에 남는다. 요즘은 fw_devlink가 DT 참조로 공급자 링크를 만들어서 대부분 미리 막아 준다.

It means a resource the probe needs — a regulator, clock, GPIO, or PHY — isn't available yet. The driver core puts the device on the deferred list and retries whenever another driver binds. Usually you just propagate it from calls like devm_regulator_get, and using dev_err_probe records the reason in debugfs devices_deferred. Nowadays fw_devlink creates supplier links from the DT references, so most of these are avoided up front.

Q. How can you force a specific driver onto a device, or rebind a driver without rebooting?

A. sysfs의 drivers/<drv>/unbind와 bind에 장치 이름을 쓰면 remove와 probe가 다시 돈다. 매칭 규칙을 무시하고 특정 드라이버만 붙게 하려면 장치의 driver_override에 드라이버 이름을 쓰고 drivers_probe를 친다. VFIO로 장치를 넘길 때 쓰는 방법이다. 다만 override는 match만 우회하므로 probe가 OF match data에 의존하는 드라이버는 거절할 수 있다.

Writing the device name to the driver's unbind and bind files in sysfs reruns remove and probe. To force a particular driver regardless of the match tables, write the driver name to the device's driver_override and then trigger drivers_probe — that's how devices are handed to VFIO. Override only bypasses match, though: a driver whose probe relies on OF match data can still reject the device.

Q. Does it matter whether the driver module is loaded before or after the device is created?

A. 상관없다. 드라이버가 등록될 때 driver_attach()가 기존 장치를 모두 훑고, 장치가 추가될 때 device_add() → __device_attach()가 기존 드라이버를 모두 훑는다. 둘 다 같은 match → really_probe 경로로 합류한다. 직접 hub 드라이버로 자식 장치를 런타임에 만들어 두 순서를 다 확인했다.

No. When a driver registers, driver_attach walks all existing devices; when a device is added, device_add calls into __device_attach, which walks all registered drivers. Both converge on the same match and really_probe path. I checked both orders with a small hub driver that creates child devices at runtime.

  3. 관찰: 커널 인자에 dyndbg="file drivers/base/dd.c +p"를 넣고(QEMU -append에서 따옴표 주의) 부팅해 d3-soc@9200000이 simple-pm-bus에 묶이는 줄을 찾아라. — 정답/힌트: "matched device with driver simple-pm-bus".
  4. 코드: d3_probe()가 -EIO를 돌려주게 바꾸고 dmesg를 보라. -ENODEV일 때와 무엇이 다른가? — 정답/힌트: -EIO는 dev_err로 "probe with driver d3_sensor failed with error -5"가 찍히고, -ENODEV는 dyndbg 없이는 아무것도 안 찍힌다.
  5. sysfs: baro 장치에 driver_override를 걸지 않고 /sys/bus/platform/drivers/d3_sensor/bind에 써 보고, override를 건 뒤에도 써 보라. 결과가 왜 다른가? — 정답/힌트: 첫째는 match 실패로 -ENODEV, 둘째는 match는 통과하지만 probe가 match data NULL로 거절(예제 10).
  6. I2C 미리보기: d3_hub를 고쳐 자식의 reg를 "슬레이브 주소"로 읽어 dev_info로 찍게 하라(of_property_read_u32(child, "reg", &addr)). 왜 진짜 I2C에서는 이 방식 대신 i2c_client를 쓰는가? — 정답/힌트: 주소가 CPU 메모리 주소가 아니므로 struct resource/ioremap 대상이 아니고, 전송은 어댑터의 i2c_transfer()를 거쳐야 하기 때문(H5).
  7. modalias: of:Nd3-sensorT(null)Cdon,imu-v3Cdon,imu(9102000) 문자열이 d3_sensor의 alias 중 어느 것과 맞는지 손으로 glob 매칭해 보라. — 정답/힌트: of:N*T*Cdon,imu(끝이 Cdon,imu로 끝남)와 맞는다. C*가 붙은 버전은 뒤에 다른 compatible이 더 올 때를 위한 것이다.

17. 요약 & 체크리스트#

드라이버 바인딩은 "장치 명단"과 "드라이버 자기소개서"를 버스가 짝짓는 일이다. 장치 쪽은 부팅 때 unflatten_device_tree()와 of_platform_default_populate_init()가 루트·simple-bus 밑의 compatible 있고 status가 okay인 노드마다 platform_device를 만든다(I2C/SPI 자식은 컨트롤러 드라이버가 만든다). 드라이버 쪽은 of_match_table을 가진 platform_driver를 등록한다. 어느 쪽이 나중에 오든 driver_match_device() → platform_match()가 driver_override → OF → ACPI → id_table → 이름 순으로 판정하고, OF 매칭은 노드 compatible 목록의 앞쪽일수록 높은 점수를 주어 가장 구체적인 항목을 고른다(테이블 순서 무관). 일치하면 really_probe()가 공급자 링크·pinctrl·DMA·sysfs를 준비하고 probe()를 부르며, -EPROBE_DEFER는 재시도, -ENODEV는 조용한 거절, 그 밖은 에러다. 결과는 sysfs의 driver·of_node 링크로 보이고, bind/unbind/driver_override/drivers_probe로 손으로 바꿀 수 있다. 모듈 자동 로딩은 MODULE_DEVICE_TABLE이 만든 alias와 장치의 modalias가 만나 일어난다.
