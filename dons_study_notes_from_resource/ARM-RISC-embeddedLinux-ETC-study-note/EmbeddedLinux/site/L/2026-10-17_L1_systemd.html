0. 큰 그림 — 장비의 "태스크 매니저 + 이벤트 로그 + 워치독 관리자"#

펌웨어에서 Don이 만들던 것을 떠올려 보자. SSD 펌웨어의 메인에는 보통 이런 것들이 있다.

  • 태스크 테이블: 어떤 태스크를 어떤 순서로 만들지 (NAND 초기화가 끝나야 FTL 태스크 시작).
  • 태스크 감시: 태스크가 죽거나(assert) 멈추면(heartbeat 없음) 그 태스크만 재시작하거나, 안 되면 전체 리셋.
  • 이벤트 로그: 링버퍼에 남기고, 중요한 것만 NAND의 로그 영역에 flush (쓰기 수명 때문에).
  • HW watchdog kick: 메인 루프가 살아 있을 때만 kick.

Linux 장비에서 이 네 가지를 한 번에 해 주는 것이 systemd다. 정확히는 PID 1로 도는 systemd manager와, 그 옆에서 도는 작은 데몬 묶음(journald, udevd, networkd, logind …)이다.

그림 1 — 센서 키트 장비에서 systemd가 맡는 일. 가운데 PID 1이 unit 파일과 udev가 알려 준 장치 정보로 그래프를 만들고 서비스를 띄운다. 서비스는 NOTIFY_SOCKET으로 "준비됨/살아 있음"을 보고하고, 로그는 journald로 간다. PID 1 자신의 생존은 HW watchdog이 감시한다.

C7과 K2에서 BusyBox init(/etc/inittab을 위에서부터 실행)을 봤다. 같은 장비를 두 방식으로 만든다고 해 보자.

결론은 이렇다. 수 MB 플래시, 서비스 2~3개, 부팅 1초 미만이 요구사항이면 BusyBox init(또는 직접 쓴 /init)이 맞다. 서비스가 10개 이상, 서로 의존하고, 필드에서 스스로 복구해야 하고, 로그를 원격으로 올려야 하는 장비(로봇·드론 컴패니언 컴퓨터, 카메라, Jetson)라면 systemd가 이미 만들어 둔 것을 쓰는 편이 싸다. 셸 스크립트로 재시작 제한·watchdog·cgroup 정리를 다시 만들면 결국 버그 많은 작은 systemd가 된다.

sysvinit(/etc/init.d/ 스크립트 + 런레벨)은 BusyBox init보다 조금 더 구조가 있지만 "직렬 스크립트 실행 + PID 파일로 추적"이라는 본질은 같다. 신규 제품에서 고를 이유는 거의 없다.

0.2 이 노트의 실습 환경#

  • VM 호스트: Lima elinux (Ubuntu 26.04, 커널 7.0.0-38-generic, systemd 259) — C 프로그램 static 빌드만 한다. 호스트의 systemd 상태는 바꾸지 않는다.
  • 게스트: QEMU virt (TCG, Cortex-A57 2코어, 1 GiB) + 랩 커널 Image-sec(6.18.55-sec) + 랩 rootfs rootfs-sysd.ext4(Ubuntu Base 24.04.5 + systemd 255). 내 복사본 /var/tmp/L1/l1_root.ext4에 unit 파일과 테스트 스크립트를 넣고 부팅한다.
  • 자동화 방식: 이미지에 l1-runner.service를 넣었다. 커널 인자 l1step=N을 읽어 /usr/local/bin/l1_step_N.sh를 실행하고 결과를 /root/l1out/N.txt에 쓴 뒤 poweroff한다. 끝나면 VM에서 이미지를 loop 마운트해서 결과를 읽는다. 아래 출력은 전부 이 결과 파일에서 그대로 옮겼다.
  • TCG는 실제 하드웨어가 아니다. CPU 명령을 소프트웨어로 번역하므로 모든 시간이 실제 Cortex-A78AE(Orin)나 i.MX8보다 수 배~수십 배 느리다. 시간 숫자는 "같은 환경에서 전후 비교"로만 읽는다.

러너 unit과 러너 스크립트는 이렇다 (이 자체가 systemd 사용 예제다).

두 가지 작은 설계 포인트가 있다. 첫째, Type=simple이다. Type=oneshot으로 하면 스크립트가 끝날 때까지 이 unit의 start job이 끝나지 않고, systemd는 job이 하나라도 남아 있으면 "Startup finished"를 찍지 않는다 — 부팅 시간 측정이 러너 때문에 망가진다. 둘째, 스크립트가 systemctl is-system-running --wait로 부팅 완료를 기다린 뒤에야 측정한다. "부팅 끝"을 sleep으로 추측하지 않는 것, 이것이 systemd 방식의 핵심이다.

1. unit, job, transaction — PID 1 안의 엔진#

1.1 직관 — "상태를 가진 객체 + 그래프 + 작업 큐"#

systemd가 관리하는 모든 것은 unit이다. unit은 이름(imu.service), 설정(unit 파일), 그리고 현재 상태(active, failed …)를 가진 객체다. 서비스만 unit이 아니다 — 마운트 지점, 장치, 소켓, 타이머, 그리고 "여기까지 왔다"는 동기화 지점(target)도 unit이다.

누군가(부팅 시의 PID 1 자신, 또는 systemctl start) "이 unit을 start해 줘"라고 요청하면 systemd는 바로 실행하지 않는다. 먼저 transaction(트랜잭션)을 만든다.

  1. 요청한 unit에 job(start/stop/restart 같은 작업 하나)을 만든다.
  2. 그 unit의 Wants=/Requires=를 따라가며 끌려오는 unit들에도 start job을 붙인다. Conflicts=가 있으면 상대에 stop job을 붙인다.
  3. 모인 job들을 After=/Before=로 정렬한다. 순서 고리(cycle)가 있으면 Wants=로만 끌려온 job 하나를 버려서 고리를 끊고 경고를 찍는다.
  4. 모순이 없으면 transaction 전체를 job queue에 넣는다. 이후 이벤트 루프가 "앞 순서 job이 끝난 것"부터 실행한다.

Don이 아는 말로 하면: unit = 태스크 제어 블록(TCB), job = 태스크에 보내는 명령 메시지, transaction = "이 명령을 실행하려면 같이 필요한 명령 전부"를 미리 계산해서 한 번에 큐에 넣는 것, 이벤트 루프 = epoll 기반 단일 스레드 스케줄러다. PID 1은 멀티스레드가 아니다 — 모든 것이 sd-event(epoll 래퍼) 하나의 루프에서 돈다. 그래서 PID 1 안의 블로킹 호출 하나가 시스템 전체를 멈출 수 있고, 그래서 HW watchdog을 PID 1이 먹이는 것이 의미가 있다(§7).

1.3 unit의 상태#

unit의 상태는 두 층이다. LoadState(파일을 읽었나: loaded, not-found, masked, error)와 ActiveState(지금 돌고 있나: inactive, activating, active, deactivating, failed, reloading, 그리고 드물게 maintenance·refreshing). 서비스에는 더 세밀한 SubState(running, exited, auto-restart, start-pre …)가 있다. systemctl status의 Active: active (running)이 ActiveState(SubState)다.

그림 2 — service unit의 ActiveState 전이. Type=notify면 activating에서 active로 넘어가는 순간이 서비스가 READY=1을 보낸 때다. failed는 "끝났는데 결과가 나빴다"를 기억하는 상태이고, systemctl reset-failed나 성공한 재시작이 지운다.

2. unit 파일 — 어디에 두고, 어떻게 덮어쓰나#

2.1 위치와 우선순위#

같은 이름의 unit 파일이 여러 곳에 있으면 앞에 있는 것 하나만 쓴다. 실제 검색 경로는 systemd-analyze unit-paths가 보여 준다.

정리하면 우선순위가 높은 순서로:

2.2 drop-in — 통째로 복사하지 말고 몇 줄만 덮기#

/etc/systemd/system/<unit>.d/*.conf 파일은 원래 unit 위에 덧붙여진다(drop-in). 파일 전체를 /etc에 복사하면 패키지 업데이트로 원본이 바뀌어도 반영되지 않는 문제가 생기는데, drop-in은 바꾼 줄만 들고 있으니 그 문제가 없다. 리스트형 설정(ExecStart=, After= 등)은 drop-in에서 추가된다 — 지우려면 먼저 빈 값(ExecStart=)을 한 줄 쓰고 새 값을 쓴다.

systemctl edit <unit>은 /etc/systemd/system/<unit>.d/override.conf를 편집기로 열고, 저장하면 daemon-reload까지 해 준다. 대화형 명령이라 자동화 스크립트 안에서는 tty가 없어 거부된다 — 그래서 이미지 빌드·테스트 스크립트에서는 같은 파일을 직접 만들고 daemon-reload 한다. 아래는 §6의 데모 서비스에 "3번 ping한 뒤 멈춰라"를 drop-in으로 넣는 장면이다 (게스트, 러너 스크립트 안).

출력에서 볼 것: systemctl cat은 원본 + drop-in을 파일 경로 주석과 함께 순서대로 보여 준다. "이 서비스는 실제로 어떤 설정으로 도나"를 확인하는 첫 명령이다. systemd-delta는 시스템 전체에서 덮어쓰기·확장·마스킹된 unit을 나열한다 — 남의 장비를 디버깅할 때 "누가 무엇을 바꿨나"를 한 번에 본다.

2.3 enable, preset, mask#

  • enable: [Install]의 WantedBy=multi-user.target을 읽어 /etc/systemd/system/multi-user.target.wants/<unit> 심볼릭 링크를 만든다. 그게 전부다. 부팅 때 multi-user.target이 .wants/ 디렉터리 안의 링크를 Wants=처럼 취급해 끌고 온다. 이미지 빌드에서는 systemctl --root=<rootfs> enable foo 또는 링크를 직접 만든다(Yocto의 SYSTEMD_AUTO_ENABLE, Buildroot의 패키지 .mk가 하는 일).
  • preset: /usr/lib/systemd/system-preset/*.preset의 enable foo.service / disable * 규칙. systemctl preset-all이 이 정책대로 enable 상태를 일괄 맞춘다. "첫 부팅"(ConditionFirstBoot=yes가 참인 부팅)에 systemd가 자동으로 preset을 적용한다 — 이미지 정책을 "어떤 패키지를 깔았나"가 아니라 preset 파일 하나로 관리할 수 있다. 주의: machine-id(5)에 따르면 첫 부팅으로 치는 것은 /etc/machine-id가 없거나 uninitialized라는 글자를 담고 있을 때다. 이 노트의 이미지처럼 빈 파일이면 ID는 새로 만들지만 첫 부팅으로 치지 않는다 — §10.1의 첫 부팅 로그에서 systemd-firstboot.service ... skipped because of an unmet condition check (ConditionFirstBoot=yes)로 실제로 확인된다. 공장 이미지에서 첫 부팅 동작(preset, 키 생성)을 원하면 uninitialized를 써 둔다(K6의 machine-id 이야기와 연결).
  • mask: /etc/systemd/system/<unit> → /dev/null 링크. 수동 start도, 다른 unit의 Requires=도 막는다. disable은 "부팅 때 자동으로 안 띄움"일 뿐 다른 unit이 끌어오면 뜬다. 확실히 죽이려면 mask다. §10에서 부팅 시간 줄이기에 쓴다.

2.4 unit 파일 문법 한 장#

unit 파일은 INI 형식이다. 이 노트의 데모 서비스 하나에 자주 쓰는 섹션이 다 들어 있다.

  • [Unit]: 모든 unit 공통 — 설명, 의존성(§3), 시작 제한, 실패 훅. StartLimit*가 [Service]가 아니라 [Unit]에 있는 것에 주의한다(옛 문서의 StartLimitInterval=은 [Service]였다 — 지금은 [Unit]의 StartLimitIntervalSec=).
  • [Service]: 서비스 전용 — 실행 방법, 재시작, watchdog.
  • [Install]: enable 때만 쓰인다. 이 데모는 수동으로 start하므로 없다.
  • %n은 specifier다: unit 전체 이름(l1-notifyd.service)으로 치환된다. %i는 템플릿 인스턴스 이름(foo@bar.service의 bar). l1-onfailure@.service는 템플릿이고, OnFailure=l1-onfailure@%n.service는 "실패한 unit 이름을 인스턴스로 넘겨라"라는 뜻이다.
  • $HANG은 Environment=의 값으로 치환된다. ExecStart=는 셸이 아니다 — 파이프·리다이렉션·$(...)가 안 된다. 필요하면 /bin/sh -c '...'로 감싸거나 스크립트 파일로 뺀다(이 노트는 스크립트로 뺐다).

2.5 generator — 부팅 때 unit을 "생성"하는 작은 프로그램#

PID 1은 unit 파일을 읽기 전에 /usr/lib/systemd/system-generators/의 실행 파일들을 돌린다. generator는 /etc/fstab, 커널 커맨드라인, GPT 파티션 타입 같은 것을 읽어 /run/systemd/generator*/에 unit 파일을 만든다. 그래서 /etc/fstab 한 줄이 .mount unit이 되고, console=ttyAMA0이 serial-getty@ttyAMA0.service가 된다.

출력에서 볼 것: 루트 파일시스템의 -.mount(이름 -는 경로 /를 unit 이름으로 바꾼 것 — systemd-escape --path /), 그리고 getty.target.wants/ 아래 콘솔 getty. generator는 로그를 잘 남기지 않고, 부팅 아주 초기에 sandbox 안에서 돈다. 커스텀 generator를 쓰면 "장비 모델을 EEPROM에서 읽어 해당 센서 서비스만 enable" 같은 것도 가능하지만, 단순한 경우는 ConditionPathExists=(§3.5)가 더 낫다.

3. 의존성(끌어오기)과 순서(기다리기)는 다른 축이다#

3.1 직관#

systemd에서 가장 많이 틀리는 지점이다. 두 질문을 분리해야 한다.

  • "B를 켤 때 A도 켜야 하나?" → 의존성 (Wants=, Requires=, BindsTo=, Requisite=, PartOf=). A의 job을 transaction에 넣을지를 정한다.
  • "A가 다 켜질 때까지 B는 기다려야 하나?" → 순서 (After=, Before=). 둘 다 transaction에 있을 때 어느 job을 먼저 끝낼지를 정한다.

둘은 서로 독립이다. Requires=A만 쓰고 After=A를 안 쓰면, systemd는 A와 B를 동시에 시작한다. RTOS로 말하면 "태스크 A도 만들어라"와 "A의 이벤트 플래그를 기다려라"는 다른 API인 것과 같다.

그림 3 — 의존성(위쪽, 무엇을 끌고 오나·무엇이 같이 멈추나)과 순서(아래쪽, 누가 먼저 끝나야 하나). 실선 화살표는 이 노트 §3.3 실험에서 측정한 실제 타임스탬프다.

3.2 지시어 정리#

지시어끌어오나상대가 실패/정지하면 나는상대가 이미 없으면대표 용도

Requires=A예A가 명시적으로 stop되면 나도 stop. A의 start job이 실패하면 나도 실패 (After=도 있을 때)A를 시작해 봄강한 의존

After=의 "끝난 뒤"는 상대 unit의 start job이 완료된 뒤다. 서비스라면 Type=이 정한 "시작 완료" 시점(§5.1)이다 — Type=simple이면 fork 직후, Type=notify면 READY=1 후, Type=oneshot이면 프로세스 종료 후. 그래서 After=는 Type=과 같이 봐야 의미가 있다. stop 때는 순서가 거꾸로 적용된다(B가 먼저 멈추고 A가 멈춘다).

3.3 실험 — Requires=만 쓰면 생기는 경주(race)#

무엇을 확인하나: B가 Requires=A일 때 After=A가 있고 없음에 따라 (1) B가 A보다 먼저 시작하는지, (2) A가 실패하면 B가 실행되는지. A는 3초 걸리는 oneshot이고, 성공하면 /run/l1_a_done을 만든다. B는 그 파일이 있는지 ls로 확인한다 — "A가 만든 장치 노드·설정 파일을 B가 쓰는" 실제 상황의 축소판이다.

실험 스크립트(게스트, l1_step_3.sh의 앞부분):

출력에서 볼 것 (타임스탬프는 short-precise, 마이크로초):

  • After= 없음, A 성공: Starting l1-a(41.843)와 Starting l1-b-noafter(41.893)가 50 ms 차이로 거의 동시에 찍힌다. B의 ls는 0.36초 시점에 실행되어 /run/l1_a_done이 없다고 실패한다. A는 그 3초 뒤에야 끝난다. 의존성은 "A도 켜라"였지 "A를 기다려라"가 아니었다.
  • After= 없음, A 실패: B는 A의 실패와 무관하게 실행됐다(B의 echo와 ls가 찍힘). Requires=의 "상대가 실패하면 나도 실패"는 순서가 있어야만 적용된다 — 순서가 없으면 B의 start job은 A의 결과를 기다리지 않으니 볼 수가 없다.
  • After= 있음, A 성공: Finished l1-a(59.172) 뒤에 Starting l1-b-after(59.390)가 나오고, ls가 성공한다.
  • After= 있음, A 실패: B는 아예 실행되지 않는다. Dependency failed for l1-b-after.service, job 결과 dependency. systemctl start도 "A dependency job ... failed"로 rc=1.

그림 3이 첫 번째와 세 번째 경우를 시간축에 그린 것이다. 실제 장비에서는 이 경주가 부팅마다 다르게 나타난다는 것이 무섭다 — A가 빨리 끝나는 날은 우연히 성공하고, flash가 느린 날·CPU가 바쁜 날만 실패한다. 그래서 "가끔 부팅 후 센서 데몬이 설정 파일을 못 찾는다" 같은 버그 리포트를 보면 가장 먼저 Requires=/Wants=에 짝 After=가 있는지 본다.

systemctl show -p Requires -p After의 결과에서 내가 쓰지 않은 sysinit.target, basic.target, system.slice, systemd-journald.socket이 보인다 — §3.5의 기본 의존성이 자동으로 들어간 것이다.

3.4 BindsTo / PartOf / Requisite — 정지가 어떻게 번지나#

무엇을 확인하나: 부모 서비스(l1-parent, 카메라 파이프라인이라고 하자)를 (1) systemctl stop, (2) systemctl restart, (3) 프로세스가 혼자 죽게(kill -9) 했을 때, PartOf=와 BindsTo= 자식이 어떻게 반응하나. 세 서비스 모두 ExecStart=/bin/sleep infinity이고 자식은 After=l1-parent.service를 같이 가진다.

정리하면:

상황PartOf= 자식BindsTo= 자식
systemctl stop l1-parent같이 정지같이 정지
systemctl restart l1-parent같이 재시작 (MainPID 569 → 579)active 유지 (출력상 active)
부모 프로세스가 혼자 죽음 (kill -9)영향 없음 (active)정지 (inactive)
  • PartOf=는 systemctl 명령(job)만 전파한다. 부모가 스스로 죽는 것은 job이 아니라서 전파되지 않는다. 그래서 "sensors.target을 restart하면 묶음 전체가 재시작"에 맞다.
  • BindsTo=는 부모의 상태를 본다. 부모가 어떤 이유로든 inactive/failed가 되면 자식을 멈춘다. 장치에 묶는 데 맞다 — USB 카메라가 뽑혀 dev-video0.device가 사라지면 카메라 서비스도 멈춘다.
  • restart 때 BindsTo 자식이 active로 보이는 것은 부모 restart가 stop→start를 한 job으로 처리하는 동안 BindsTo 자식이 정지 대상이 되지 않았기 때문으로 보인다(이 실험에서 BindsTo 자식의 PID 변화는 기록하지 않았다).
  • Requisite=는 끌어오지 않는다. 부모가 inactive일 때는 "A dependency job ... failed"로 즉시 실패, 부모를 먼저 띄우면 성공한다. "이미 떠 있어야만 의미가 있는" 진단 도구 등에 쓴다.

3.5 기본 의존성과 Condition#

모든 service unit에는 DefaultDependencies=yes가 기본으로 붙어 다음이 자동으로 들어간다: Requires=sysinit.target, After=sysinit.target basic.target, Conflicts=shutdown.target, Before=shutdown.target. 그래서 평범한 서비스는 /proc·/sys·로컬 파일시스템·udev 준비가 끝난 뒤에 뜨고, 종료 때는 먼저 멈춘다. 부팅 아주 초기에 돌아야 하는 서비스(예: 루트 마운트 전에 eMMC 파티션을 고치는 도구)는 DefaultDependencies=no를 쓰고 필요한 순서를 직접 적는다. 이걸 모르고 Before=sysinit.target만 쓰면 순서 고리(ordering cycle)가 생겨 systemd가 job 하나를 버린다.

Condition*= / Assert*=는 의존성이 아니라 "시작할 조건"이다. 조건이 거짓이면 unit은 실패가 아니라 "건너뜀(skipped)"이 된다 (K6 부팅 로그의 ConditionPathExists=/proc/sys/fs/binfmt_misc 줄이 그 예). 장비에서 유용한 것들:

4. target — 부팅의 이정표와 "모드"#

4.1 target은 runlevel의 후계자다#

target은 실행 내용이 없는 unit이다. 다른 unit들을 Wants=로 묶고, 다른 unit들이 After=로 기다리는 동기화 지점 역할만 한다. 부팅은 "default.target을 start하는 transaction 하나"다. default.target은 보통 multi-user.target(헤드리스) 또는 graphical.target(화면 있음)을 가리키는 심볼릭 링크다.

4.2 network-online.target 함정#

After=network.target은 "네트워크 관리자가 시작됐다"는 뜻이지 "IP를 받았다"가 아니다. 서버에 접속해야 하는 서비스는 Wants=network-online.target + After=network-online.target을 쓴다. 대신 이 target은 systemd-networkd-wait-online.service가 모든 링크가 설정될 때까지(기본 최대 2분) 기다리기 때문에, 케이블이 빠진 장비는 부팅이 2분 늦어진다. §10에서 이 이미지의 critical chain에 실제로 나타나는지 본다. 해결은 (1) 정말 필요한 서비스만 network-online을 기다리게 하고, (2) systemd-networkd-wait-online --any 또는 --interface=eth0으로 범위를 좁히고, (3) 가능하면 서비스가 스스로 재접속하게 만드는 것이다.

After=가 기다리는 "시작 완료" 시점을 정하는 설정이다. 잘못 고르면 §3.3의 경주가 After=를 써도 다시 생긴다.

  • RestartSteps= / RestartMaxDelaySec= (v254+): 재시작할 때마다 대기를 늘려 가는 지수 백오프. 원격 서버 접속 데몬에 좋다.

5.3 시작 제한 — boot loop 대신 "포기하고 알리기"#

무한 재시작은 펌웨어의 "assert → 리셋 → assert → 리셋" 루프와 같다. CPU·flash(로그)·배터리를 태우고, 원인 로그는 덮어써진다. systemd는 unit별 시작 횟수 제한을 둔다.

  • StartLimitIntervalSec= (기본 DefaultStartLimitIntervalSec=10s) 안에 StartLimitBurst= (기본 5)번보다 많이 start하면, unit은 failed(Result start-limit-hit)에 머물고 더 이상 자동 재시작하지 않는다.
  • 주의: 기본값 10초/5회는 RestartSec=100ms일 때를 위한 것이다. RestartSec=1s, burst 5면 5초에 5번이라 10초 창 안에서 거의 안 걸린다. RestartSec × Burst < IntervalSec가 되게 같이 설계해야 제한이 실제로 걸린다. 이 노트의 데모는 120초/3회로 했다.
  • StartLimitAction= (기본 none): 제한에 걸렸을 때 reboot, reboot-force, poweroff 등을 할 수 있다. "이 서비스 없이는 장비가 의미 없다" + "재부팅하면 고쳐질 수 있다"일 때만 쓴다. 재부팅 루프 위험은 bootcount(L4)로 막는다.
  • FailureAction= / SuccessAction=: unit이 실패/성공하면 시스템 동작(reboot 등). 공장 테스트 이미지에서 "테스트 서비스가 끝나면 poweroff"에 쓴다.

5.4 OnFailure= — 실패했을 때 할 일#

OnFailure=X는 unit이 failed 결과로 끝날 때 X를 start한다. 여기서 주의할 점을 §6.3 실험에서 확인했다: systemd 255에서는 Restart=로 자동 재시작될 실패에도 매번 OnFailure=가 불린다(journal에 "Triggering OnFailure= dependencies"가 실패마다 찍히고, 훅이 본 ActiveState는 첫 번째엔 activating, 시작 제한에 걸린 마지막엔 failed였다). 그래서 훅 안에서 systemctl show -p ActiveState를 보고 "재시작 중인 일시 실패"와 "최종 포기"를 구분해야 한다 — 최종 포기일 때만 fault LED를 켜는 식이다. 템플릿과 %n을 쓰면 실패 훅 하나를 모든 서비스가 공유할 수 있다.

제품에서는 이 자리에 "journal 마지막 200줄을 /data/crash/에 저장", "텔레메트리에 실패 이벤트 전송", "fault LED 켜기", "안전 상태로 전환(모터 정지)"이 들어간다. 모든 서비스에 일일이 쓰기 싫으면 /etc/systemd/system/service.d/onfailure.conf 같은 최상위 타입 drop-in(모든 .service에 적용)으로 넣을 수 있다 — 단 훅 서비스 자신에게도 적용되어 무한 호출이 되지 않게 훅 쪽에서 OnFailure=를 비운다.

6. sd_notify와 서비스 watchdog — 프로토콜을 C로 직접 구현#

6.1 프로토콜은 "UNIX 데이터그램 한 개"다#

Type=notify 서비스를 시작할 때 PID 1은 환경 변수 NOTIFY_SOCKET에 소켓 주소를 넣어 준다(systemd 255에서는 /run/systemd/notify). 서비스는 그 주소로 AF_UNIX + SOCK_DGRAM 데이터그램을 보낸다. 내용은 줄바꿈으로 구분한 KEY=VALUE 텍스트다. 그게 전부다. libsystemd의 sd_notify()는 이 일을 하는 편의 함수일 뿐이고, 의존성을 늘리기 싫은 작은 장비 데몬(또는 Rust·Go·Python 서비스)은 직접 보내도 된다.

메시지뜻

STATUS=...사람이 읽는 상태 문자열 (systemctl status의 Status: 줄)

수신 측 보안: PID 1은 데이터그램과 함께 SCM_CREDENTIALS(보낸 프로세스의 PID·UID — 커널이 채워 줌, 위조 불가)를 받아서, NotifyAccess=main(기본)이면 서비스의 메인 PID가 보낸 메시지만 받아들인다. 메인 프로세스가 아닌 워커 스레드는 같은 PID라서 괜찮지만, fork한 자식이 보내려면 NotifyAccess=all이 필요하다.

그림 4 — l1_notifyd가 PID 1과 주고받는 것(§6.3 실측 타임스탬프). 정상 구간에는 1초마다 WATCHDOG=1이 가고, ping을 멈추면 마지막 ping 2초 뒤 PID 1이 SIGABRT를 보낸다. 재시작이 StartLimitBurst=3을 넘으면 failed에 머물고 OnFailure= 훅이 돈다.

6.2 코드 — libsystemd 없이 NOTIFY_SOCKET에 직접 보내기#

무엇을 확인하는 코드인가: 환경 변수에서 소켓 주소와 watchdog 주기를 읽고, 준비가 끝나면 READY=1, 이후 주기의 절반마다 WATCHDOG=1을 보낸다. 인자 N을 주면 N번 ping한 뒤 "메인 루프가 멈춘 것처럼" ping을 끊는다.

포인트:

  • 주소가 @로 시작하면 Linux 추상(abstract) 소켓이다 — 파일시스템에 노드가 없고 sun_path[0] = '\0'로 표현한다. systemd는 파일 경로를 주지만 컨테이너 런타임 등은 추상 주소를 쓰기도 해서 두 경우를 다 처리한다. 주소 길이는 offsetof(sun_path) + n으로 정확히 준다(추상 소켓은 뒤쪽 NUL까지 이름에 포함되기 때문).
  • NOTIFY_SOCKET이 없으면 아무것도 안 한다. 같은 바이너리를 systemd 없이(BusyBox init, 개발 PC 터미널) 돌려도 동작한다.
  • MSG_NOSIGNAL: 받는 쪽이 없을 때 SIGPIPE로 죽지 않게.
  • 매번 소켓을 열고 닫는다(libsystemd의 sd_notify도 그렇게 한다). 1초 주기면 비용은 무시할 만하다.
  • ping은 "진짜 일이 진행됐을 때"만 보내야 한다. 별도 스레드에서 무조건 ping하면 메인 루프가 데드락에 걸려도 watchdog이 못 잡는다. 펌웨어에서 "타이머 ISR에서 WDT를 kick하면 안 된다"는 규칙과 똑같다.

빌드 (VM 호스트, static — 게스트 rootfs의 glibc 버전과 무관하게 돈다):

경고 0개. 만든 바이너리는 내 이미지 복사본의 /usr/local/bin/에 넣었다.

6.3 실행 — 정상 READY, watchdog timeout, 시작 제한, OnFailure#

무엇을 확인하나: (1) Type=notify에서 READY=1 전후 상태, PID 1이 넣어 준 환경 변수, STATUS= 반영. (2) drop-in으로 HANG=3을 주고 재시작하면 watchdog timeout → SIGABRT → 재시작이 반복되다가 StartLimitBurst=3을 넘어 failed가 되고 OnFailure= 훅이 도는지.

출력에서 볼 것:

  • Status: "sensors open, streaming" — 서비스가 보낸 STATUS= 문자열이 systemctl status에 그대로 나온다. 몇 초 뒤 StatusText=ping 2 → ping 9로 바뀐 것은 WATCHDOG=1과 함께 보낸 STATUS=ping N이 계속 도착하고 있다는 뜻이다.
  • 환경 변수: NOTIFY_SOCKET=/run/systemd/notify(파일 경로 소켓), WATCHDOG_USEC=2000000(= WatchdogSec=2s), WATCHDOG_PID=515(이 PID가 ping해야 한다는 뜻 — fork한 자식이 이 변수를 물려받아도 자기 PID와 다르면 무시하라는 신호).

  • CPU: 436ms — 0.5초 sleep뿐인 프로그램인데 이만큼 쓴 것은 TCG에서 static 바이너리를 처음 실행하며 번역하는 비용이다. 실제 HW 숫자가 아니다.

한 줄씩 읽으면 §5의 정책이 전부 보인다 (그림 4가 같은 내용을 시간 순으로 그린 것):

7. RuntimeWatchdogSec — PID 1이 HW watchdog을 먹인다#

7.1 누가 PID 1을 감시하나#

§6의 서비스 watchdog은 PID 1이 서비스를 감시한다. 그럼 PID 1이 멈추면? 커널 데드락, 메모리 고갈로 PID 1이 스케줄되지 못함, PID 1 자체의 버그. 이때는 아무도 서비스를 재시작해 주지 못한다. 그래서 PID 1 자신은 하드웨어 watchdog이 감시하게 한다. I9에서 본 /dev/watchdog API를 PID 1이 직접 쓰는 것이다.

/etc/systemd/system.conf(또는 system.conf.d/*.conf)의 [Manager] 설정:

설정기본 (systemd 255)의미
RuntimeWatchdogSec=off평상시 HW watchdog timeout. 설정하면 PID 1이 /dev/watchdog0을 열고 WDIOC_SETTIMEOUT, 이후 대략 절반 주기로 ping
RuntimeWatchdogPreSec=offpretimeout (I9 §5.7) — 리셋 전에 경고 인터럽트 (드라이버가 지원할 때)
RebootWatchdogSec=10minreboot/poweroff 경로에서 PID 1이 HW watchdog을 이 값으로 바꿔 두고 넘김 — 종료가 멈추면 이 시간 뒤 강제 리셋
KExecWatchdogSec=offkexec(L7의 kdump) 때 새 커널로 watchdog을 켠 채 넘김 — 새 커널이 시간 안에 급식을 이어받아야 함

장비에서는 보통 RuntimeWatchdogSec= 를 10~30초 정도로 켠다. 너무 짧으면 부하가 큰 순간(대량 flash 쓰기, 메모리 압박)에 오탐 리셋이 나고, 너무 길면 멈춘 장비가 오래 멈춰 있는다. 별도 watchdog 데몬(watchdog 패키지)과 같이 쓰면 안 된다 — /dev/watchdog0은 한 번에 한 프로세스만 열 수 있어서 늦게 연 쪽이 EBUSY를 받는다.

그림 5 — watchdog 3단. 서비스는 PID 1이 감시하고(소프트웨어, 서비스만 재시작), PID 1은 HW watchdog이 감시한다(보드 리셋). 재부팅 경로 자체가 멈추는 경우는 RebootWatchdogSec=가 맡는다. 펌웨어의 "태스크 heartbeat → 메인 루프 → WDT kick" 계층 구조와 같다.

7.2 실험 — i6300esb에 붙여 보고, PID 1을 멈춰서 보드 리셋 보기#

준비: 이미지에 drop-in /etc/systemd/system.conf.d/l1-wdt.conf를 넣고, QEMU에 -device i6300esb를 추가해 부팅한다. i6300esb는 Intel 6300ESB 칩셋의 watchdog을 흉내 내는 PCI 장치이고, QEMU의 기본 동작은 timeout 시 머신 리셋이다(I9 §5.4).

먼저 PID 1이 watchdog을 잡았는지 확인한다.

출력에서 볼 것:

  • 커널 로그 i6300ESB timer ... initialized. heartbeat=30 sec — 드라이버 기본 timeout은 30초다. 약 3.6초 뒤 PID 1이 Using hardware watchdog 'i6300ESB timer' ... device /dev/watchdog0, Watchdog running with a timeout of 10s — WDIOC_SETTIMEOUT으로 10초로 바꿨다.
  • /dev/watchdog1도 있다. 이 커널은 CONFIG_SOFT_WATCHDOG=y(softdog, 커널 타이머로 흉내 내는 watchdog)도 built-in이라 두 개가 생긴다. i6300esb가 PCI 탐색 때 먼저 등록되어 0번을 받았다. 장치 번호는 probe 순서에 달려 있다 — 제품에서는 WatchdogDevice=를 명시하거나 udev 심볼릭 링크(L2)를 쓴다. /dev/watchdog(10,130)은 첫 번째 watchdog의 옛 호환 노드다.
  • /proc/1/fd/13 -> /dev/watchdog0 — PID 1이 장치를 열고 있다. 이 상태에서 다른 프로세스가 열면 EBUSY.
  • WatchdogLastPingTimestampMonotonic=193634525 — 마지막 ping이 부팅 후 193.6초. systemd는 이 값을 D-Bus 속성으로 내보내므로 원격 진단에서 "PID 1이 최근에 급식했나"를 볼 수 있다.
  • cat .../{identity,timeout,...}가 실패한 것은 절반은 내 실수다 — 러너 스크립트가 sh(Ubuntu에서는 dash)로 돌아 중괄호 확장이 안 됐다. 그래서 리셋 후 확인 단계에서 ls /sys/class/watchdog/watchdog0/로 다시 봤고, dev power subsystem uevent만 있었다(§7.3 끝). 이 커널은 CONFIG_WATCHDOG_SYSFS가 꺼져 있어 속성 파일이 아예 없다(I9에서도 같은 상황). 켜면 timeout, timeleft, bootstatus, state 등이 생긴다.
  • State: S (sleeping), TracerPid: 0 — 정상 상태의 PID 1. 이벤트 루프의 epoll_wait()에서 자고 있다.

kill()은 0을 반환하지만(권한 검사는 통과) 시그널은 큐에 들어가기 전에 무시된다. K1·C7에서 본 "PID 1에게는 기본 시그널 동작이 없다"의 커널 쪽 코드다.

멈추는 정당한 방법은 ptrace다. 디버거가 프로세스를 세우는 경로는 시그널 무시 규칙과 별개라, root(CAP_SYS_PTRACE)는 PID 1에 PTRACE_SEIZE + PTRACE_INTERRUPT를 걸어 tracing-stop 상태로 만들 수 있다. gdb -p 1이 PID 1을 세울 수 있는 것과 같은 원리다. 이 상태에서는 PID 1의 이벤트 루프가 돌지 않으니 HW watchdog ping도 끊긴다 — "PID 1이 데드락에 걸린 상황"의 충실한 재현이다. (다른 방법인 SysRq는 PID 1만 골라 세우는 기능이 없다. echo c > /proc/sysrq-trigger로 커널을 panic시키면 panic=0일 때 커널이 멈춰 있으니 역시 HW watchdog이 리셋하지만, 그건 "커널 hang" 시나리오다.)

무엇을 확인하는 코드인가: kill(1, SIGSTOP)이 성공을 반환해도 효과가 없음을 보이고, ptrace로 PID 1을 세운 뒤 /proc/1/stat의 상태를 1초마다 찍는다. 보드가 리셋되면 출력이 거기서 끊긴다.

출력에서 볼 것 (QEMU 콘솔 로그, boot_5C.log에서 해당 줄):

  • kill(1, SIGSTOP) returned 0 (but init ignores it) — 시스템 호출은 0을 돌려줬지만 커널이 시그널을 큐에 넣기 전에 버렸다(§7.3의 sig_task_ignored).
  • waitpid 상태 0x80057f = (PTRACE_EVENT_STOP(128) << 16) | (SIGTRAP << 8) | 0x7f — PTRACE_INTERRUPT로 생긴 ptrace event stop이다.
  • /proc/1/stat 상태 t = tracing stop. PID 1의 이벤트 루프가 완전히 멈췄다.
  • t= 9까지 찍힌 직후 Booting Linux on physical CPU 0x0 — 10초 timeout이 지나 i6300esb가 QEMU 머신을 리셋했다. 마지막 ping은 freeze 직전 5초 안쪽(PID 1이 timeout의 절반쯤 주기로 ping한다)이었으므로, 리셋은 "마지막 ping 후 약 10초"와 맞다. 아무도 reboot을 부르지 않았고, 커널은 panic하지 않았다 — 하드웨어가 리셋했다.

PID 1만 멈췄을 뿐 커널과 다른 프로세스(journald, 내 freeze 프로그램)는 계속 돌고 있었다는 점이 중요하다. 이런 "부분 hang"은 커널 soft-lockup 감지기로도 안 잡힌다. PID 1 데드락은 HW watchdog만 잡는다.

8. journald — 구조화 로그, 저장 정책, flash 수명#

8.1 직관 — "메타데이터가 붙은 링버퍼"#

펌웨어 로그 링버퍼를 생각하자. 항목마다 타임스탬프·모듈 ID·심각도가 있고, RAM 버퍼가 차면 오래된 것부터 덮어쓰고, 중요한 것만 NAND에 flush한다. journald가 정확히 그것이다. 차이는 (1) 입력이 여러 경로(서비스 stdout, syslog(), 네이티브 API, 커널 printk)이고, (2) 항목마다 커널이 보증하는 메타데이터(_PID, _UID, _SYSTEMD_UNIT, _BOOT_ID …)가 붙고, (3) 인덱스가 있는 바이너리 파일이라 journalctl -u imu.service -p err -b -1 같은 질의가 빠르다는 것이다.

그림 6 — journald의 입력과 저장소. 서비스는 그냥 stdout에 printf하면 된다 — 파일 열기·로테이션·타임스탬프 붙이기를 서비스가 할 필요가 없다. 저장 위치는 Storage=가 정한다.

  1. Storage=volatile + 원격 전송(systemd-journal-upload, 또는 텔레메트리 에이전트): flash 쓰기 0. 대신 리셋하면 직전 로그가 사라진다 — 크래시 분석에는 L7의 pstore(/sys/fs/pstore, RAM에 남는 마지막 커널 로그)로 보완한다.
  2. Storage=persistent + 작은 SystemMaxUse= + 긴 SyncIntervalSec=: 쓰기는 배치로 몰리고 총량은 상한. 디버깅이 쉽다(journalctl -b -1로 직전 부팅). 저널 파일은 append + 인덱스 갱신이라 쓰기 증폭이 있다는 점을 알고 쓴다.
  3. 혼합: journald는 volatile, 중요한 이벤트만 앱이 별도 작은 파일(또는 전용 파티션)에 남김.

SSD 펌웨어 관점으로 말하면, journald의 fsync 빈도가 곧 FTL에 들어오는 작은 랜덤 쓰기 빈도다. eMMC 쓰기 수명(TBW)과 저널의 하루 쓰기량을 곱해 보는 습관이 필요하다 — 이것을 재는 법은 J 모듈(J2)과 연결된다.

무엇을 확인하나: (1) 현재 저장 설정과 사용량, (2) 5,000줄을 한 번에 쏟는 서비스가 unit별 rate limit(LogRateLimitBurst=200/10s)에 잘리는 모습, (3) Storage=volatile과 persistent 전환, SystemMaxUse=·--vacuum-size.

출력에서 볼 것:

  • --list-boots에 이전 부팅(-1)이 있다 — Ubuntu 이미지는 /var/log/journal이 미리 있어서 Storage=auto가 persistent로 동작한다. 그런데 ls -ld /run/log/journal도 있다: flush 전 부팅 초기 로그는 항상 /run에 먼저 쓴다(그림 6 아래 설명).
  • cat-config가 ForwardToSyslog=yes를 보여 준다 — Ubuntu가 /usr/lib/systemd/journald.conf.d/에 넣은 drop-in이다. 그런데 이 이미지에는 rsyslog가 없다. 받는 쪽 없는 소켓으로 보내는 셈이니, 장비 이미지라면 ForwardToSyslog=no로 끄는 편이 깔끔하다. 배포판 기본값을 그대로 믿지 말고 cat-config로 최종값을 본다.
  • 두 부팅 만에 9.6M. 파일 하나가 정확히 8 MiB(8388608바이트)인 것은 journald가 파일을 큰 단위로 미리 늘려 두기 때문이다(아래 ls -la). 작은 파티션에서 "로그 몇 줄인데 왜 8 MB?"의 답이다.
  • rate limit: 5,000줄 중 journal에 남은 것은 881줄. Suppressed 282 messages, Suppressed 442 messages 두 번이 보고됐다. 합이 5,000이 안 되는 이유는, 억제 보고가 다음 구간에 그 서비스의 메시지가 다시 올 때 찍히기 때문이다 — 서비스가 마지막 구간에서 끝나 버리면 그 구간의 억제 수는 보고되지 않는다(아래 JSON의 마지막 저장 줄이 spam line 3555다). TCG가 느려서 5,000줄을 쓰는 데 여러 10초 구간이 걸렸고, 구간마다 200줄씩 들어갔다.
  • rate limit은 flash와 CPU를 지키는 안전장치다. 센서 드라이버 에러를 루프에서 찍는 서비스 하나가 eMMC를 갉아먹는 일을 막는다. 대신 정말 중요한 줄이 잘릴 수 있으니, 에러 로그는 "처음 N번 + 이후 요약" 식으로 앱에서 먼저 줄인다.

journal 항목 하나를 JSON으로 보면 메타데이터가 어떻게 붙는지 보인다.

출력에서 볼 것: 밑줄(_)로 시작하는 필드는 journald가 커널에서 직접 얻은 신뢰할 수 있는 값이다(SCM_CREDENTIALS, /proc/<pid>/, cgroup 경로). 서비스가 위조할 수 없다. MESSAGE, PRIORITY, SYSLOG_IDENTIFIER처럼 밑줄 없는 필드는 보낸 쪽이 정한 값이다. _BOOT_ID가 journalctl -b의 기준이다.

출력에서 볼 것:

  • volatile로 바꾸고 재시작하자 /run/log/journal/<machine-id>/system.journal이 생겼고 새 메시지(volatile-test)는 거기로 갔다. --disk-usage가 10.6M인 것은 이 명령이 /run과 /var의 journal을 합쳐서 보고하기 때문이다(기존 /var 파일은 지워지지 않는다).

9. timer · socket activation · tmpfiles.d — 작은 도구들#

9.1 timer — cron 대체#

cron 대신 .timer unit을 쓰면 (1) 실행 결과·출력이 journal에 unit 이름으로 남고, (2) 실행이 겹치지 않으며(같은 서비스가 아직 돌고 있으면 새로 띄우지 않음), (3) 자원 제한·샌드박스 같은 서비스 설정을 그대로 쓰고, (4) 장비가 꺼져 있던 동안 놓친 실행을 Persistent=true로 따라잡을 수 있다. 별도 crond 데몬이 필요 없다.

출력에서 볼 것:

  • systemd-analyze calendar는 표현식을 정규화하고 다음 실행 시각을 보여 준다 — cron 문법 실수를 배포 전에 잡는 도구다. *:0/15는 "매시 0분부터 15분마다"로 펼쳐졌다.
  • 타이머를 start한 시점(부팅 후 약 285초)에는 OnBootSec=20s가 이미 지났으므로 즉시 한 번 실행됐다(LAST ... 2s ago, NEXT -는 서비스가 막 돌고 있어서 다음 시각이 아직 계산 전). 이후 약 15.5초 간격으로 실행됐다. 15초가 아니라 15.5초인 것은 OnUnitActiveSec=가 서비스가 활성화된 시각 기준이고, oneshot 서비스가 시작·종료되는 데 TCG에서 시간이 걸리기 때문이다. 정확한 벽시계 주기가 필요하면 OnCalendar=를 쓴다.
  • 이미지에 원래 있던 apt-daily*.timer, fstrim.timer, e2scrub_all.timer가 보인다. 장비에서 apt-daily-upgrade는 필드에서 몰래 패키지를 올리는 위험한 타이머다 — OTA(L4)로 업데이트를 관리한다면 이미지에서 mask한다. fstrim.timer는 eMMC/SSD에 유익하니 남긴다(J2).

9.2 socket activation — 연결이 올 때만 띄운다#

PID 1이 소켓을 미리 만들어 listen하고 있다가, 연결이 오면 서비스를 띄우며 그 소켓 fd를 넘겨준다(fd 3부터, 환경 변수 LISTEN_FDS/LISTEN_PID). 효과는 세 가지다.

  1. 부팅 병렬화: 소켓은 부팅 초기에 다 만들어지므로, 클라이언트는 서버가 아직 안 떠도 connect()할 수 있다(커널 backlog에 쌓임). After= 없이도 순서 문제가 사라진다 — journald의 /dev/log가 이 방식이라 모든 서비스가 journald보다 먼저 떠도 로그가 안 사라진다.
  2. 온디맨드: 거의 안 쓰는 진단 서비스(공장 테스트 포트, 디버그 셸)는 연결이 올 때만 메모리를 쓴다.
  3. 무중단 재시작: 서비스가 재시작하는 동안에도 소켓은 PID 1이 들고 있어서 연결이 거부되지 않는다.

Accept=yes면 연결마다 서비스 인스턴스를 하나씩 띄운다(inetd 방식, stdin/stdout이 그 연결). Accept=no(기본)면 리스닝 소켓 자체를 넘기고 서비스가 accept()한다(성능상 이쪽이 일반적).

출력에서 볼 것: 소켓을 start했을 때 ACTIVATES 칸이 -다 — 아직 서비스는 하나도 안 떴다. 연결이 올 때마다 l1-echo@0-127.0.0.1:7777-127.0.0.1:48406.service처럼 연결 번호와 양 끝 주소를 인스턴스 이름으로 가진 서비스가 하나씩 뜨고, tr이 끝나면(클라이언트가 shutdown(SHUT_WR)으로 EOF를 보냄) 사라졌다. tr은 소켓 프로그래밍을 전혀 모르는 프로그램이다 — stdin/stdout이 곧 TCP 연결이다. 공장 테스트용 "포트 하나에 연결하면 센서 값 한 줄 덤프" 같은 기능을 수십 줄로 만들 수 있다.

9.3 tmpfiles.d와 path unit#

  • tmpfiles.d: 부팅 때(systemd-tmpfiles-setup.service) /run, /var 아래 디렉터리·파일·심볼릭 링크를 만들고 권한을 맞추고, 오래된 파일을 정리한다. 한 줄 형식 타입 경로 모드 사용자 그룹 나이 인자. read-only rootfs 장비에서 "쓰기 가능한 /var/lib/imu를 매 부팅 만들기"에 쓴다. 서비스 하나에만 필요한 디렉터리는 unit의 RuntimeDirectory=imu(→ /run/imu, 서비스 종료 시 삭제)나 StateDirectory=imu(→ /var/lib/imu)가 더 간단하다.
  • .path unit: inotify로 경로를 감시하다가 조건(PathExists=, PathChanged=, DirectoryNotEmpty=)이 맞으면 짝 서비스를 띄운다. 예: /data/upload/에 파일이 생기면 upload.service 실행. 폴링 루프 데몬을 없앤다.

10. systemd-analyze와 부팅 시간 줄이기#

C7 §2.4에서 VM 호스트로 systemd-analyze의 기본을 봤다. 여기서는 장비 이미지(QEMU 게스트)에서 재고, 실제로 깎아 본다.

10.1 첫 부팅 — 무엇이 시간을 먹나#

무엇을 확인하나: 랩 rootfs를 복사해 처음 부팅했을 때의 kernel/userspace 구간, 오래 걸린 unit, critical chain, 그리고 첫 부팅 특유의 동작. (첫 부팅 측정 스크립트 l1_step_1.sh에서 실행.)

TCG 경고부터. userspace 3분 14초는 실제 장비 숫자가 아니다. 이 측정 때 VM에서는 다른 노트 작성자들의 QEMU·빌드가 함께 돌아 load average가 14였다(VM 6코어). 같은 이미지를 덜 바쁠 때 부팅하면 1분대가 나왔다(§10.3). Cortex-A78AE급 실기라면 수 초다. 그래서 절대값이 아니라 같은 조건의 상대 비교만 한다.

출력에서 볼 것:

  • blame과 critical-chain은 다른 질문에 답한다. blame 1위는 systemd-networkd-wait-online.service(2분 3.8초)지만, 이것은 "그 unit이 activating 상태였던 시간"이다. 병렬로 도는 동안 다른 일도 진행됐으므로 이 시간이 그대로 부팅을 늦춘 것은 아니다. 부팅을 늦춘 경로는 critical-chain이 보여 준다: graphical.target ← podman-restart.service ← network-online.target(2분 48.8초). network.target은 49초에 이미 도달했는데 network-online까지 2분이 더 걸렸다 — §4.2의 함정이 그대로 나왔다.
  • systemd-networkd-wait-online.service는 결국 실패했다(degraded의 원인). 2분 기본 timeout 안에 "모든 링크 configured"가 안 됐다. 그런데도 network-online.target은 도달했다 — target이 이 서비스를 Wants=로만 끌기 때문이다. 즉 2분은 순수한 기다림이었다.
  • podman-restart.service가 graphical.target 바로 앞에 있다. 컨테이너 런타임 패키지가 "부팅 때 restart-policy 컨테이너 재기동"을 network-online.target 뒤에 걸어 둔 것이다. 컨테이너를 안 쓰는 장비라면 순수 비용이다(L8).
  • dev-vda.device 1분 49초, systemd-udev-trigger.service 1분 16초: udev coldplug(부팅 시 모든 장치에 uevent를 다시 보내 규칙을 적용)가 무겁다. K6에서도 1위였다.
  • Initializing machine ID from random generator — 빈 /etc/machine-id라서 새 ID를 만들었다. 그러나 systemd-firstboot.service ... skipped ... (ConditionFirstBoot=yes) — 빈 파일은 첫 부팅으로 치지 않는다(§2.3). preset도 적용되지 않았다.
  • plot은 260,080바이트 SVG를 만들었다(가로 19,912 px — 초당 100 px로 그리는 간트 차트). 브라우저로 열어 unit별 막대를 본다. 두 번째 부팅(기준 측정)의 plot은 가로 21,384 px, activating/active 막대 301개였다.

10.3 깎아 보기 — mask, default target#

무엇을 확인하나: 이 장비(헤드리스, 컨테이너 안 씀, 인터넷 연결이 부팅 완료 조건이 아님)에 필요 없는 것을 이미지 빌드 단계에서 끄면 얼마나 줄어드나. 부팅하지 않고 VM 호스트에서 이미지 루트에 대해 systemctl --root=로 작업했다 — Yocto·Buildroot·K6의 이미지 생성 스크립트가 하는 방식과 같다.

고른 이유: wait-online — 부팅 완료가 네트워크 연결을 기다릴 이유가 없다(필요한 서비스가 스스로 재시도). podman 3종 — 컨테이너 미사용. e2scrub_reap — ext4 온라인 검사 스냅샷 정리, 장비에선 불필요. swupdate — §6.3에서 본 반복 실패 루프(이 이미지의 OTA는 L4에서 따로 설정). 일부러 남긴 것: apparmor.service(13~44초로 크지만 보안 기능 — L6), udev(장치 관리의 핵심).

10.4 systemd의 비용 — 크기와 메모리#

Installed-Size는 KiB 단위다. systemd 관련 7개 패키지 합이 약 34.5 MB(udev의 hwdb가 큰 몫)이다. PID 1 실행 파일 자체는 133 KB지만 거의 모든 코드가 libsystemd-shared-255.so(3.9 MB)에 있다. 부팅 후 사용 메모리는 약 130 MB, 프로세스 80여 개(networkd·resolved·timesyncd·logind·journald·udevd·dbus 포함). K2의 BusyBox 이미지(실행 파일 하나, 프로세스 몇 개)와 비교하면 flash 수십 MB와 RAM 100 MB 이상이 systemd 생태계의 입장료다. Yocto라면 PACKAGECONFIG로 networkd·resolved·hwdb 등을 빼서 줄일 수 있고(K4·K5), 그래도 수십 MB 단위가 남는다는 것이 §0.1 표의 결론이다.

10.5 장비에서의 부팅 시간 최적화 순서#

  1. "부팅 완료" 정의: 제품 서비스의 READY=1(→ 그 서비스 기준 critical-chain imu.service).
  2. 측정 조건 고정: 같은 보드·같은 저장장치 상태·여러 번 측정. TCG·공유 머신이라면 쌍 측정.
  3. critical chain 위의 unit만 본다. blame은 후보 목록일 뿐.
  4. 기다림 제거: network-online, TimeoutStartSec 대기, ExecStartPre=sleep 같은 것.
  5. 불필요한 unit mask, default target 정리, 배포판이 깔아 둔 타이머(apt-daily 등) 정리.
  6. 늦게 해도 되는 것 미루기: socket activation, .timer의 OnBootSec=, After= 끝으로.
  7. udev·커널 쪽: coldplug 대상 줄이기, 모듈 대신 built-in, initcall 분석(C7), 필요하면 initramfs 없애기.
  8. 다시 측정하고 systemd-analyze plot을 남겨 버전 간 비교.

11. 커널 안에서는 무슨 일이 일어나나#

systemd는 유저 공간 프로그램이지만, 하는 일 대부분이 커널 기능 위에 서 있다. 각각이 어떤 커널 구조로 이어지는지, 그리고 드라이버를 쓸 때 어디서 다시 만나는지 정리한다.

그림 9 — systemd 기능과 커널 인터페이스의 대응. 왼쪽 열이 PID 1·journald가 쓰는 API, 오른쪽 열이 커널 안의 구조·함수다.

  • 서비스 추적 = cgroup v2. 서비스마다 /sys/fs/cgroup/system.slice/imu.service/ cgroup을 만들고 그 안에서 fork·exec한다. 데몬이 몇 번 fork하든 자식은 같은 cgroup에 남으므로 "이 서비스의 프로세스 전부"가 정확히 정의된다(커널 struct css_set, cgroup.procs). stop 때는 KillMode=control-group(기본)으로 cgroup 전체에 SIGTERM → TimeoutStopSec= 후 SIGKILL. cgroup이 비면 커널이 cgroup.events의 populated 0을 알리고(inotify), PID 1은 그것으로 "서비스 완전히 끝남"을 안다. 자원 제한(MemoryMax=, CPUQuota=)도 이 cgroup의 컨트롤러 파일에 쓰는 것이다 — L8(컨테이너)에서 같은 메커니즘을 다시 본다.
  • 프로세스 감시 = pidfd + SIGCHLD. PID 1은 자식 종료를 SIGCHLD(signalfd로 이벤트 루프에 연결)와 waitid()로 받고, 최신 버전은 PID 재사용 경쟁을 피하려고 pidfd(pidfd_open, pidfd_send_signal)를 쓴다. PID 1의 특수 규칙(SIGNAL_UNKILLABLE, 고아 입양)은 §7.3과 C7 §1.4.
  • sd_notify = AF_UNIX 데이터그램 + SCM_CREDENTIALS. 커널이 struct ucred(pid/uid/gid)를 채워 주므로 PID 1은 보낸 쪽을 신뢰할 수 있다(SO_PASSCRED). FDSTORE=1은 SCM_RIGHTS로 struct file 참조를 PID 1의 fd 테이블에 복제하는 것이다(A3·A7의 fd 전달과 같은 경로).
  • HW watchdog = /dev/watchdog0 → watchdog core → 드라이버 ops. PID 1의 ioctl(WDIOC_SETTIMEOUT)·WDIOC_KEEPALIVE는 drivers/watchdog/watchdog_dev.c의 watchdog_ioctl() → watchdog_ping() → 드라이버의 struct watchdog_ops.ping(i6300esb는 esb_timer_keepalive)으로 간다. 드라이버를 쓸 때 채우는 것은 .start/.stop/.ping/.set_timeout이고 등록은 devm_watchdog_register_device() — I9 §5.2에서 다뤘다. CONFIG_WATCHDOG_HANDLE_BOOT_ENABLED면 부트로더가 켜 둔 watchdog을 PID 1이 열 때까지 커널 워커가 대신 ping해 준다(watchdog_dev.c의 watchdog_ping_work) — U-Boot에서 WDT를 켠 채 넘기는 장비에서 중요하다.
  • device unit = uevent + udev. 커널 드라이버가 device_add()하면 kobject uevent가 netlink로 나가고, udevd가 규칙을 적용한 뒤 TAG+="systemd"가 붙은 장치를 PID 1에게 알린다(libudev monitor). 그래서 BindsTo=dev-video0.device는 결국 V4L2 드라이버의 video_register_device()가 성공했는가에 묶인다. 장치 이름 규칙은 L2.
  • journald의 입력 = /dev/kmsg + 소켓. 커널 printk 링버퍼를 /dev/kmsg에서 읽고(devkmsg_read), 유저 로그는 /run/systemd/journal/{socket,stdout}과 /dev/log로 받는다. 서비스의 stdout은 PID 1이 미리 만들어 둔 journald 스트림 소켓에 연결된 fd다(ls -l /proc/<pid>/fd/1 → socket:[...]). 드라이버의 dev_err()/dev_info()가 journal에서 _KERNEL_DEVICE=, _KERNEL_SUBSYSTEM= 필드를 갖는 것은 dev_printk가 붙이는 구조화 정보(SUBSYSTEM=, DEVICE=) 덕분이다 — 드라이버 로그를 journalctl _KERNEL_SUBSYSTEM=i2c로 걸러 볼 수 있다.
  • 부팅 시간 기준 = CLOCK_MONOTONIC / CLOCK_BOOTTIME. systemd-analyze의 "kernel" 구간은 커널 시작부터 PID 1 실행까지, "userspace"는 PID 1 시작부터 default target 도달까지다. 부트로더 구간은 펌웨어가 EFI 변수로 알려 줄 때만 나온다(ARM 임베디드 + U-Boot 비EFI 부팅이면 안 나옴 — C7 §4).

14. 면접에서 이렇게 말한다#

Q. "A service crashes in the field — how do you make it self-heal without boot loops?"

A. 세 층으로 답한다. (1) 서비스 수준: Restart=on-failure + 적절한 RestartSec=로 그 서비스만 살린다. 멈춤(hang)은 죽음이 아니라서 Type=notify + WatchdogSec=로 잡는다 — 메인 루프에서 진행이 있을 때만 WATCHDOG=1. (2) 루프 방지: StartLimitIntervalSec/StartLimitBurst로 "N분에 M번"을 넘으면 포기하고 failed에 두고, OnFailure=로 로그 저장·텔레메트리·안전 상태 전환. 재부팅은 정말 필요한 서비스에만 StartLimitAction=reboot, 그리고 재부팅 루프는 U-Boot bootcount + A/B 롤백(L4)이 끊는다. (3) 시스템 수준: PID 1 자체는 RuntimeWatchdogSec=로 HW watchdog이 감시. 그리고 매 실패는 coredump·journal로 남겨 원인을 고친다.

I layer it. First, per service: Restart=on-failure with a sensible RestartSec, and for hangs rather than crashes, Type=notify with WatchdogSec — the main loop sends WATCHDOG=1 only when it has made real progress, so a deadlock gets a SIGABRT, a core dump, and a restart. Second, loop protection: StartLimitIntervalSec and StartLimitBurst sized against RestartSec so the limit actually trips; after that the unit stays failed and an OnFailure= hook saves logs, reports telemetry and puts the hardware in a safe state. I only escalate to a reboot for services the product can't live without, and boot loops are cut by the bootloader's bootcount with A/B rollback. Third, PID 1 itself is covered by RuntimeWatchdogSec feeding the hardware watchdog. And every failure leaves a core dump and journal so we fix the root cause rather than relying on restarts.

꼬리 질문: "재시작으로 상태가 날아가면?" → 상태는 StateDirectory=/파일에 체크포인트, 소켓·장치 fd는 FDSTORE=1로 PID 1에 맡겨 재시작 후 이어받는다.

Q. "What's the difference between Requires= and After=?"

A. Requires=는 "B를 켜면 A도 켜라, A가 명시적으로 멈추면 B도 멈춰라"라는 의존성이고, After=는 "둘 다 켜질 때 A의 start가 끝난 뒤 B를 시작하라"는 순서다. 서로 독립이라 Requires=만 쓰면 동시에 시작된다. 이 노트 실험에서 After= 없이는 B가 A보다 먼저 시작해 A의 파일을 못 찾았고, A가 실패해도 B가 실행됐다. After=를 넣으면 B는 A가 끝날 때까지 기다리고, A 실패 시 "Dependency failed"로 B는 실행되지 않는다. 그리고 "끝났다"는 A의 Type=이 정의한다.

Requires is a dependency: starting B pulls in A, and stopping A explicitly stops B. After is ordering: if both are in the transaction, B's start waits until A's start job has completed. They're orthogonal — Requires alone starts both in parallel. I demonstrated this: without After, B ran before A finished and even ran when A failed; with After, B waited and failed with "dependency failed" when A failed. Also "completed" is defined by A's Type — for Type=simple that's right after fork, so for real readiness you want Type=notify. In practice you almost always pair Wants or Requires with After, and prefer Wants unless you really need the stop propagation; BindsTo is the stronger form that also reacts when A dies on its own.

Q. "How does systemd's watchdog relate to the hardware watchdog?"

A. 두 단이다. 서비스 watchdog(WatchdogSec=)은 순수 소프트웨어 — PID 1이 서비스별 타이머를 들고 있다가 WATCHDOG=1이 안 오면 그 서비스만 죽이고 재시작한다. HW watchdog은 PID 1이 RuntimeWatchdogSec=로 /dev/watchdog0을 열어 주기적으로 ping한다 — PID 1의 이벤트 루프가 돌아야 ping이 가므로 PID 1이나 커널이 멈추면 보드가 리셋된다. 이 노트에서 PID 1을 ptrace로 세웠더니 i6300esb가 timeout 뒤 QEMU 머신을 리셋했다. 추가로 RebootWatchdogSec=가 종료 경로의 멈춤을 잡고, 부팅 직후 bootstatus로 "지난번 리셋이 watchdog 때문이었나"를 텔레메트리에 올린다.

They're two tiers. The service watchdog is purely software: PID 1 keeps a timer per unit and, if WATCHDOG=1 doesn't arrive within WatchdogSec, it kills just that service with SIGABRT and the Restart policy takes over. The hardware watchdog is fed by PID 1 itself when RuntimeWatchdogSec is set — it opens /dev/watchdog0, sets the timeout and pings from its event loop. So if PID 1 or the kernel wedges, nobody pings and the SoC resets. I tested that in QEMU with an i6300esb: I ptrace-stopped PID 1 — you can't SIGSTOP init — and the machine reset after the timeout. RebootWatchdogSec covers a hung shutdown, and on the next boot the driver's bootstatus tells you the reset was a watchdog reset, which you report as a field metric.

Q. "How would you reduce boot time on a systemd-based device?"

A. 먼저 "부팅 완료"를 정의한다(제품 서비스의 READY=1). systemd-analyze로 kernel/userspace를 나누고, critical-chain <target>으로 경로 위의 unit만 본다 — blame은 병렬로 숨는 시간까지 보여서 오해를 준다. 그다음 불필요한 unit mask, default target을 multi-user로, network-online을 기다리는 서비스 줄이기, udev coldplug 비용 확인, 무거운 초기화는 socket/timer/After= 뒤로 미루기. 바꿀 때마다 같은 조건에서 여러 번 재서 비교한다.

Define "booted" first — usually our main service signalling READY=1. Then systemd-analyze to split kernel and userspace, and critical-chain on that target, because blame lists time that's hidden by parallelism. Then: mask units the product doesn't need, set multi-user as default, stop making services wait for network-online unless they must, look at udev coldplug cost, and defer non-critical work with socket activation or timers. Measure every change several times under the same conditions — on my QEMU setup the numbers are only meaningful relative to each other.

Q. "Where do you put your own unit files and how do you change a vendor unit?"

A. 제품 unit은 /etc/systemd/system(이미지에 굽기) 또는 패키지로 /usr/lib/systemd/system. 벤더 unit은 절대 고치지 않고 drop-in(systemctl edit → override.conf)으로 바꾼다. 리스트 항목은 빈 값으로 먼저 지운다. systemctl cat과 systemd-delta로 최종 설정을 확인한다.

Our own units ship in the image under /etc/systemd/system or in a package under /usr/lib/systemd/system. Vendor units are never edited in place — I use drop-ins via systemctl edit, so a package or OTA update doesn't wipe the change, and for list settings like ExecStart I reset with an empty assignment first. systemctl cat shows the merged result and systemd-delta shows everything that's overridden on a box.

Q. "Journald on flash — what do you configure?"

A. Storage=를 명시(volatile+원격, 또는 persistent+상한), SystemMaxUse=/SystemMaxFileSize=로 총량·로테이션, SyncIntervalSec=로 fsync 빈도, rate limit으로 폭주 서비스 차단. 크리티컬 메시지는 즉시 sync된다는 점을 이용하고, 크래시 분석은 pstore로 보완. 가능하면 로그는 데이터 파티션에.

I make Storage explicit — volatile plus remote shipping, or persistent with a hard cap via SystemMaxUse and SystemMaxFileSize — and lengthen SyncIntervalSec to batch writes, knowing CRIT and above are synced immediately. Rate limits stop a runaway service from flooding flash. The journal lives on a data partition so the rootfs can stay read-only, and for crash forensics I add pstore for the last kernel messages.

Q. "What is socket activation and why would you use it on a device?"

A. PID 1이 소켓을 먼저 열어 두고 연결이 오면 서비스를 띄워 fd를 넘긴다. 부팅 순서 의존성이 사라지고(클라이언트는 backlog에서 기다림), 드물게 쓰는 서비스는 메모리를 안 쓰고, 재시작 중에도 연결을 잃지 않는다.

PID 1 creates and listens on the socket early and passes the fd to the service when a connection arrives. That removes ordering dependencies — clients can connect before the server is up and just wait in the backlog — keeps rarely-used diagnostic services out of memory, and lets a service restart without refusing connections.

15. 직접 해보기#

  1. (개념) Wants=A만 있고 After=가 없는 B를 start했는데 A가 실패했다. B는 어떻게 되나? Requires=A면? Requires=A+After=A면? 정답/힌트: Wants → B는 그대로 실행. Requires(After 없음) → 동시 시작이라 B는 실행됨(A의 실패가 B의 start job을 막지 못함). Requires+After → B는 "dependency failed"로 실행 안 됨. §3.3 출력.
  2. (코드) l1_notifyd.c에 EXTEND_TIMEOUT_USEC=를 추가해, 시작 전 10초 캘리브레이션을 하는 서비스가 TimeoutStartSec=5s에도 실패하지 않게 만들어 보라. 정답/힌트: 캘리브레이션 루프 안에서 3초마다 EXTEND_TIMEOUT_USEC=5000000을 보낸다. 안 보내면 start operation timed out으로 실패.
  3. (코드) 메인 루프가 진행했을 때만 ping하도록 "마지막 센서 샘플 시각"을 검사하는 구조로 바꿔라. 별도 스레드가 무조건 ping하는 버전과 비교해, 메인 루프에 pause()를 넣었을 때 어느 쪽이 재시작되는지 확인하라. 정답/힌트: 무조건 ping 버전은 영원히 active로 남는다.
  4. (관찰) 서비스의 stdout이 어디에 연결되어 있는지 ls -l /proc/$(systemctl show -p MainPID --value l1-notifyd)/fd로 보고, ss -xp에서 그 소켓의 반대편을 찾아라. 정답/힌트: fd 1·2가 socket:[N], 반대편은 /run/systemd/journal/stdout의 journald.
  5. (설계) 카메라 서비스가 /dev/video0이 나타날 때 자동으로 뜨고, 사라지면 멈추게 하라. 정답/힌트: BindsTo=dev-video0.device + After=dev-video0.device, udev 규칙 TAG+="systemd", ENV{SYSTEMD_WANTS}+="camera.service" (L2).
  6. (관찰) RuntimeWatchdogSec=10s인 상태에서 strace -p 1 -e trace=ioctl -tt로 PID 1의 WDIOC_KEEPALIVE 주기를 재라. 정답/힌트: 대략 timeout의 절반(5초) 근처. strace를 붙이는 것 자체가 ptrace라 너무 오래 세우지 않게 주의.
  7. (부팅 시간) 이 노트의 trimmed 이미지에서 systemd-analyze critical-chain의 맨 위 항목 하나를 더 없애고(혹은 뒤로 미루고) 3회 측정 평균을 비교하라. 정답/힌트: TCG는 편차가 크다 — 최소 3회, 같은 QEMU 옵션.

17. 요약 & 체크리스트#

systemd는 PID 1 안에서 unit 그래프와 job 큐를 돌리는 서비스 매니저다. 의존성(Wants/Requires/BindsTo/PartOf/Requisite)과 순서(After/Before)는 별개의 축이라 거의 항상 짝으로 쓰고, "시작 완료"는 Type=이 정한다. 필드 장비의 자가 복구는 Restart=on-failure + Type=notify/WatchdogSec=(멈춤 감지) + 계산된 StartLimit* + OnFailure= 훅, 그리고 PID 1 자신을 지키는 RuntimeWatchdogSec=(HW watchdog)의 층으로 만든다. 로그는 journald에 맡기되 flash에 맞게 Storage=·크기·sync 주기를 명시한다. 부팅 시간은 systemd-analyze critical-chain으로 경로 위의 unit만 보고, mask·default target·network-online 정리로 줄이며, TCG 같은 측정 환경의 한계를 알고 상대 비교한다.
