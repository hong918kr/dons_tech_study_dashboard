0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어에서 HardFault를 잡던 순서를 떠올려 보자. ① HardFault_Handler가 예외 스택 프레임(r0–r3, r12, LR, PC, xPSR)과 CFSR·HFSR·BFAR·MMFAR를 RAM/UART에 덤프한다. ② CFSR 비트를 보고 "precise bus fault, BFAR 유효" 같은 원인을 정한다. ③ stacked PC를 .map 파일이나 arm-none-eabi-addr2line에 넣어 소스 줄을 찾는다. ④ stacked LR로 누가 불렀는지 본다. ⑤ BFAR 값 자체(0x00000010? 0xDEADBEEF?)에서 버그 종류를 추정한다.

Linux 커널의 Oops도 정확히 이 다섯 단계다. 차이는 세 가지뿐이다.

  • 커널이 덤프를 알아서, 사람이 읽을 수 있게 찍어 준다 (ESR 필드 해석, 심볼 이름, 콜스택까지).
  • 주소가 KASLR로 매 부팅 무작위라서 System.map과 바로 비교할 수 없고, 모듈은 로드될 때마다 다른 곳에 놓인다.
  • 대부분의 경우 시스템이 죽지 않는다. Oops는 "현재 태스크를 죽이고 계속 간다"가 기본이다. 그래서 "죽었다"가 아니라 "이상해졌다"로 보고되는 버그가 많다.

그림 1 — HardFault 분석과 Oops 분석은 같은 다섯 단계다. Linux는 덤프를 커널이 해석까지 해서 찍어 주고, 기본 동작이 "시스템 정지"가 아니라 "현재 태스크만 죽이고 계속"이라는 점이 다르다.

1. Oops란 무엇인가 — 정의 세 줄#

  • Oops: 커널 모드에서 처리할 수 없는 예외(잘못된 주소 접근, BUG()의 brk 명령, 정의되지 않은 명령 등)가 났을 때 커널이 진단 정보를 찍고 현재 태스크를 죽이는 것. 커널 자체는 계속 돈다. 이름 그대로 "앗, 실수".
  • panic: 커널이 "더 진행하면 안 된다"고 판단하고 모든 CPU를 멈추는 것. Kernel panic - not syncing: <이유>로 시작한다. 인터럽트 문맥에서 Oops가 나거나, panic_on_oops가 켜져 있거나, init이 죽거나, 스택이 넘치면 panic으로 간다.
  • WARN: "이 조건은 버그지만 계속 갈 수는 있다"는 경고. 콜스택을 찍고 taint W를 남기고 그대로 다음 명령으로 진행한다. 아무도 죽지 않는다.

BUG는 이름이 헷갈린다. BUG()/BUG_ON() 매크로는 Oops를 일부러 일으키는 것이고(kernel BUG at file:line!), BUG: scheduling while atomic, BUG: soft lockup 같은 BUG: 접두어 메시지는 커널의 검사기가 문제를 보고하는 것(대개 태스크를 죽이지 않는다)이다. §8에서 하나씩 실제 로그로 비교한다.

3. ESR — "왜 죽었나"를 비트로 읽기#

ESR_EL1(Exception Syndrome Register)은 Cortex-M의 CFSR에 해당한다. 예외 원인을 32비트에 담는다(상위 32비트는 ISS2로 FEAT_LS64 같은 확장용).

  • EC(Exception Class, 비트 31:26): 예외의 큰 분류. 0x25 = 현재 EL의 data abort, 0x24 = 하위 EL(유저)의 data abort, 0x21 = 현재 EL의 instruction abort, 0x3c = BRK 명령, 0x00 = 알 수 없음(UNDEF 명령 등).
  • IL(비트 25): 명령어 길이. 1 = 32비트 명령(A64는 항상 1).
  • ISS(비트 24:0): EC별 세부 정보. data abort라면 아래 필드가 있다.

3.1 예제 — ESR 해독기 (esr.py)#

커널이 이미 풀어서 찍어 주지만, 면접이나 다른 아키텍처 로그(예: 어떤 BSP는 ESR만 숫자로 찍는다)에서 직접 풀 수 있어야 한다. 이번 실험에 나온 EC·FSC만 담은 작은 해독기다.

출력에서 볼 것: translation fault의 레벨이 주소 종류를 알려 준다. 0x10은 유저 영역이라 PGD·PUD는 있고 L2(PMD)에서 비었다(pmd=0). 6b6b…·4141…·dead… 같은 쓰레기 주소는 아예 유효 주소 범위 밖(non-canonical)이라 L0에서 바로 실패한다 — 커널이 address between user and kernel address ranges라고 덧붙인다. 스택 guard page는 매핑 구조는 다 있고 마지막 L3 PTE만 비어 있어서 L3 fault다. 그리고 misalign의 ldxr은 로드라서 WnR=0이다 — atomic 증가지만 첫 명령은 읽기(load-exclusive)다.

4. Call trace — 콜스택은 어떻게 만들어지고, 어디서 거짓말하나#

4.1 직관 — frame record 체인#

arm64 커널은 CONFIG_FRAME_POINTER=y로 빌드된다(이 랩 커널도 그렇다). 함수가 다른 함수를 부르려면 자기 복귀 주소(x30)를 어딘가 보관해야 하므로, 프롤로그에서 x29(frame pointer)와 x30(LR) 한 쌍을 스택에 넣고 x29가 그 쌍을 가리키게 한다. 이 16바이트 쌍을 frame record라고 한다.

unwinder(arch/arm64/kernel/stacktrace.c)는 Oops 순간의 pc를 첫 줄로 찍고((P) 표시), 그다음부터 x29가 가리키는 frame record에서 "복귀 주소"를 읽어 한 줄 찍고, "이전 x29"를 따라 다음 record로 간다. Don이 Cortex-M에서 스택 메모리를 덤프해 손으로 LR 비슷한 값을 찾던 일을, 커널은 x29 체인 덕분에 정확하게 자동으로 한다.

맨 위 (P) 말고 (C)가 붙는 줄도 있다. show_stack+0x30/0x90 (C)처럼 현재 실행 중인 함수에서 직접 unwind를 시작했다는 표시다 — panic이나 dump_stack()이 자기 자리에서 콜스택을 찍을 때 나온다.

4.2 맹점 1 — leaf 함수의 호출자가 사라진다#

null Oops의 Call trace를 다시 보자.

m3_trigger가 Call trace에 없다. lr에만 있다. 이유는 m3_get_irq가 leaf 함수(다른 함수를 안 부름)라서 frame record를 만들지 않았기 때문이다. 실제 기계어가 이를 보여 준다(§6.4의 objdump 출력에서 발췌):

stp x29, x30이 없다. 그래서 Oops 순간 x29는 여전히 호출자 m3_trigger의 frame record를 가리키고 있었다(x29 == sp == ffff8000804fbc50인 것도 그 증거다 — leaf가 sp를 안 건드렸다). unwinder는 첫 줄을 pc로 찍은 뒤 x29의 record를 읽는데, 그 record에 든 것은 m3_trigger의 복귀 주소, 즉 param_attr_store+0x80이다. m3_trigger 자신의 위치(+0x1fc)는 x30 레지스터에만 있었고, unwinder는 x30을 콜스택 줄로 쓰지 않는다.

그림 4 — frame record 체인과 leaf 함수 맹점. 첫 줄은 pc, 둘째 줄부터는 x29 체인에서 온다. leaf 함수에서 죽으면 바로 위 호출자는 lr에만 남는다.

bugon도 같다. m3_check.constprop.0.isra.0이 leaf라서 Call trace는 m3_check... 다음 바로 param_attr_store로 넘어가고, m3_trigger+0x8c는 lr에만 있다. 반대로 uaf의 m3_uaf는 kmalloc·kfree를 부르는 non-leaf라서 Call trace에 m3_trigger+0x174/0x210가 제대로 나온다.

4.3 맹점 2 — lr은 "마지막 bl의 복귀 주소"일 뿐이다#

uaf Oops의 머리 부분이다.

lr이 같은 함수 안, pc 바로 앞을 가리킨다. "자기가 자기를 불렀나?"가 아니다. objdump로 보면(§6.4) m3_uaf+0x40(파일 오프셋 0x168)이 bl kfree이고, 0x44가 그 복귀 지점이다. 즉 lr = "이 함수가 마지막으로 부른 함수(kfree)에서 돌아온 자리"다. 이것만으로 "죽기 직전에 kfree를 불렀다"는 강력한 단서가 된다 — use-after-free다.

warnf에서는 pc와 lr이 똑같이 m3_trigger+0xb8였다. WARN(1, fmt, ...)이 메시지를 먼저 __warn_printk()로 찍고(bl), 그 복귀 지점에 바로 brk 명령이 있기 때문이다. lr은 호출자 정보가 아니라 x30 레지스터의 현재 값이라는 것을 기억한다.

4.4 맹점 3 — 인라인과 .constprop/.isra#

  • m3_get_irq.constprop.0: GCC가 "이 함수는 항상 같은 상수 인자로 불린다"는 걸 알고 그 상수를 박은 복제본을 만들었다. 원래 함수 이름 뒤에 .constprop.N이 붙는다.
  • m3_check.constprop.0.isra.0: 거기에 더해 IPA-SRA(인자를 구조체 포인터 대신 필요한 필드 값만 넘기도록 바꿈)까지 했다.
  • 조회 함수 m3_lookup은 아예 인라인돼서 사라졌다. 기계어에 mov x0, #0x0(조회 결과 NULL을 상수로 박음)만 남았다. Call trace에는 인라인된 함수가 나오지 않는다 — faddr2line의 (inlined by) 체인으로만 보인다(§6.2).
  • bugon의 m3_check는 컴파일러가 "magic은 항상 틀린 값"임을 증명해서 비교를 없애고 무조건 brk #0x800 한 줄로 만들어 버렸다(§6.4 objdump). 그래서 pc가 함수 시작 +0x8이다.

이 접미사들은 "다른 함수"가 아니라 같은 소스 함수의 최적화 버전이다. faddr2line·gdb에는 접미사까지 포함한 이름 그대로 넣는다.

5. Code: 줄 — 죽은 명령어를 직접 보기#

Code:에는 pc 앞 4개 명령과 pc의 명령, 총 5워드(리틀엔디언 32비트 값)가 찍히고 괄호 안이 예외를 낸 명령이다. 커널 트리의 scripts/decodecode가 이를 역어셈블한다(크로스 환경이면 ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-, 이 VM은 네이티브 arm64라 ARCH만).

5.1 예제 — null·dbldel·misalign·list·bugon의 Code: 해독#

출력에서 볼 것:

  • null: mov x0, #0 다음 ldr w0, [x0, #16] — 0 + 16에서 32비트를 읽는다. 소스가 없어도 "NULL 포인터의 오프셋 0x10, 4바이트 멤버"까지 읽힌다. 이 오프셋을 구조체 멤버 이름으로 바꾸는 것은 §6.5의 pahole이다.
  • dbldel: x1 = 0xdead000000000100을 만들고 [x1 + 8]에 쓴다(str). 0xdead000000000100은 LIST_POISON1, x2 = x1 + 0x22 = LIST_POISON2(dead000000000122)다. list_del()이 끝난 노드의 next/prev에 박아 두는 독 값이다 — "이미 지운 노드를 또 지웠다"(§9.3).
  • misalign: 주소에 +1을 더한 뒤 ldxr(load-exclusive) — exclusive 접근은 자연 정렬이 필수다(§9.5).
  • list: ldrb w5, [x2, x4] — 바이트 단위 문자열 읽기. printk의 %s 처리기다(§9.4).
  • bugon: brk #0x800 — BUG()는 일부러 넣은 브레이크포인트 명령이다. ESR의 f2000800과 같은 숫자다.

null과 bugon에 보이는 .inst 0xffffc8db, mov x9, x30, nop은 ftrace의 흔적이다. 커널은 모든 함수 앞에 nop 두 개(patchable function entry)를 넣어 두고, 부팅 때 첫 nop을 mov x9, x30으로 바꿔 ftrace가 언제든 훅을 걸 수 있게 한다. 함수 바로 앞 8바이트에는 ftrace ops 포인터(커널 주소의 상위 32비트 ffffcd3f가 보인다)가 들어간다. 그래서 Code: 바이트는 디스크의 .ko와 다를 수 있다 — 실행 중 패치된 내용이 찍히기 때문이다. .ko의 objdump에는 같은 자리가 nop nop이다(M5 ftrace).

출력에서 볼 것: 커널 쪽 줄은 전부 맞다(vfs_write (fs/read_write.c:593 fs/read_write.c:686)처럼 인라인 체인도 공백으로 이어 붙여 준다). 그런데 pc 줄의 m3_bugs.c:20은 틀렸다. 20번 줄은 m3_get_irq가 아니라 다른 작은 함수 m3_start의 줄이다. 함수 이름은 맞게 찍고 줄 번호만 틀리니 알아채기 어렵다.

6.2 예제 — faddr2line: 크기 불일치 경고와 인라인 체인#

출력에서 볼 것:

  • 크기 불일치: Oops는 m3_get_irq.constprop.0의 크기를 0xa10이라고 찍었지만 ELF 심볼표의 실제 크기는 0x14(20바이트, 명령 5개)다. 커널의 kallsyms는 모듈 심볼의 크기를 따로 저장하지 않고 "다음 심볼까지의 거리"로 계산하는데, 이 함수는 모듈 텍스트 영역의 마지막 심볼이라 "다음 심볼"이 없고, 기본값인 텍스트 영역 끝까지가 크기로 잡혔다(0x...55f0 + 0xa10 = 0x...6000, 4 KiB 페이지 경계와 맞아떨어진다). faddr2line은 크기가 다르면 "다른 빌드일 수 있다"며 거부한다. /size를 떼면 바로 풀린다. 별도 모듈의 lockup 실험에서도 m3_lock_init+0x30/0xfb0처럼 같은 현상이 보였다.
  • 정답은 34번 줄(return d->irq에 해당하는 줄, discriminator 1은 같은 줄 안의 두 번째 기본 블록이라는 DWARF 표시). §6.1의 20번 줄은 틀렸다.
  • inlined by 체인: m3_double_del+0x54의 실제 명령은 include/linux/list.h:210의 __list_del() 안에 있다. 모듈 77번 줄의 list_del() 호출이 세 단계 인라인으로 펼쳐진 것이다. Call trace에는 m3_double_del 하나만 보이지만 faddr2line은 "커널 헤더의 이 줄에서, 내 코드의 이 줄을 거쳐" 죽었다고 알려 준다. misalign은 여섯 단계 — atomic API가 LL/SC 구현까지 인라인된 끝에 ldxr이 있다.
  • m3_trigger+0x1fc(lr) → 90번 줄: m3_get_irq를 부른 줄이다. §4.2에서 Call trace에 빠졌던 호출자를 여기서 찾는다.

6.3 왜 decode_stacktrace.sh가 틀렸나 — .text.unlikely#

출력에서 볼 것: m3_get_irq.constprop.0은 섹션 21번 .text.unlikely의 오프셋 8에 있고, m3_start는 섹션 12번 .text의 같은 오프셋 8에 있다. GCC는 "항상 NULL 역참조로 끝나는 함수 = 거의 실행되지 않을 경로"라고 판단해 .text.unlikely(cold 섹션)로 옮겼다. decode_stacktrace.sh는 모듈 심볼 값(8) + 오프셋(0xc) = 0x14를 계산한 뒤 섹션을 지정하지 않고 addr2line에 넘겼고, addr2line은 .text의 0x14 = m3_start 안의 줄(20)을 돌려줬다. addr2line으로 두 섹션을 직접 비교하면 분명하다.

교훈: 모듈의 줄 번호는 섹션을 알아야 정확하다. 이상한 줄이 나오면 readelf -s로 그 함수가 어느 섹션(Ndx 열)에 있는지부터 본다. 커널 쪽에서도 __init 함수(.init.text), cold 경로(.text.unlikely), noinstr 함수(.noinstr.text)가 같은 함정을 만든다. faddr2line은 심볼표에서 섹션까지 찾아 쓰기 때문에 맞았다.

6.4 예제 — objdump -dr과 gdb로 죽은 명령과 줄을 확인#

uaf의 pc m3_uaf+0x48을 기계어로 확인한다. m3_uaf는 .text 0x128에서 시작하므로 pc는 0x128 + 0x48 = 0x170이다.

출력에서 볼 것: 0x168 bl kfree → 0x16c ldr x0, [x19, #24](해제된 객체의 오프셋 24 = 함수 포인터 테이블 포인터를 읽음, 이 읽기는 성공 — 메모리는 아직 매핑돼 있고 내용이 6b로 칠해져 있다) → 0x170 ldr x1, [x0](그 쓰레기 포인터 6b6b…를 따라감 → fault). lr = m3_uaf+0x44 = 0x16c = kfree의 복귀 지점, x0 = 6b6b6b6b6b6b6b6b가 레지스터 덤프와 정확히 맞는다. paciasp/autiasp는 포인터 인증(PAC, CONFIG_ARM64_PTR_AUTH_KERNEL=y)으로 복귀 주소에 서명하는 명령이다. kmalloc 크기 0x30(48)과 GFP 값 0xcc0(GFP_KERNEL)도 기계어에 그대로 보인다.

.ko를 objdump할 때 반드시 -r을 붙여야 하는 이유는 null의 호출 지점에서 보인다.

.ko는 링크 전 오브젝트라서 bl의 목적지가 아직 채워지지 않았고, objdump는 같은 섹션의 오프셋 8 = m3_start라고 잘못 표시한다. 재배치 항목(R_AARCH64_CALL26 m3_get_irq.constprop.0)이 진짜 목적지다. §6.3과 똑같은 섹션 혼동이다. 그리고 m3_trigger 시작 0x330 + 0x1fc = 0x52c — Oops의 lr이 바로 이 bl 다음 명령이다.

.text.unlikely의 m3_get_irq를 줄 정보와 함께 보면 34번 줄이 다시 확인된다.

gdb는 .ko를 직접 열어 list *(심볼+오프셋)으로 줄과 주변 소스를 보여 준다(소스 10줄 출력은 이 노트에서 생략).

vmlinux 쪽 주소도 같은 방식이다. Call trace의 vfs_write+0x248을 넣으면 인라인된 new_sync_write의 줄이 나온다.

실행 중인 커널 주소 그대로 gdb에 넣고 싶을 때(예: JTAG·kgdb 세션, M4)는 모듈 섹션의 런타임 주소를 add-symbol-file에 다 알려 줘야 한다. 섹션 주소는 /sys/module/<모듈>/sections/에 있다(root 필요).

출력에서 볼 것: 런타임 pc 0xffffd7be87ff55fc(= .text.unlikely 시작 + 0x14)를 넣으니 m3_get_irq.constprop + 12(0xc)가 나왔다 — Oops의 +0xc와 같다. .text.unlikely 주소를 빼먹고 .text만 주면 gdb도 §6.3과 똑같이 틀린다.

6.5 예제 — pahole: 오프셋을 멤버 이름으로#

NULL + 0x10에서 4바이트를 읽었다(ldr w0, [x0, #16]). 무슨 멤버인가?

7. KASLR과 System.map — 주소를 빌드 결과물과 맞추기#

7.1 직관#

Cortex-M의 .map 파일 주소는 플래시에 구운 주소 그대로다. Linux arm64는 CONFIG_RANDOMIZE_BASE=y(KASLR)라서 부팅마다 커널 전체가 무작위 오프셋만큼 옮겨진다. System.map(빌드 때 nm vmlinux로 만든 심볼표)과 vmlinux의 주소는 오프셋 0 기준이다. Oops에 심볼 이름이 찍히면(CONFIG_KALLSYMS=y) 신경 쓸 필요가 없지만, 날 주소만 있는 경우(레지스터 값, 메모리 덤프, kallsyms 없는 빌드, JTAG로 읽은 PC)에는 보정이 필요하다.

7.2 예제 — 런타임 주소 → System.map 주소#

게스트에서 root로 kallsyms를 읽고(kptr_restrict가 0이라 주소가 보인다 — M1·M2), 호스트의 System.map과 비교했다.

출력에서 볼 것:

  • KASLR 오프셋 = 런타임 _text − System.map _text = 0x57be25a00000. 이걸 런타임 vfs_write에서 빼면 System.map 값 ffff8000804ad278과 정확히 같다.
  • 0xffff8000804ad4c0 = vfs_write(…d278) + 0x248, 즉 Call trace의 vfs_write+0x248을 System.map 기준 절대 주소로 만든 것이다. addr2line은 인라인 체인(new_sync_write → vfs_write)까지 준다. 위 decode_stacktrace의 vfs_write (fs/read_write.c:593 fs/read_write.c:686)와 일치한다.
  • 모듈은 커널 이미지와 별도로 무작위 배치된다(2G module region forced by RANDOMIZE_MODULE_REGION_FULL이 부팅 로그에 있다). 모듈 주소는 KASLR 오프셋으로 못 되돌리고, 섹션 시작 주소를 빼서 섹션 오프셋으로 만든다: 0x...55f0 − 0x...55e8 = 0x8(심볼표 값과 같다), pc는 +0xc → 섹션 오프셋 0x14.
  • m3_uaf의 런타임 주소 ...51c8 − .text ...50a0 = 0x128 — 심볼표의 m3_uaf 값과 같다.

panic 메시지에는 커널이 이 오프셋을 직접 찍어 준다. oops=panic 실험의 끝부분이다.

Kernel Offset: X from 0xffff800080000000은 "이 부팅에서 _text = 0xffff800080000000 + X"라는 뜻이다. 그 부팅의 런타임 vfs_write = 0xffff8000804ad278 + 0x3354cd000000 = 0xffffb3554d4ad278(직접 계산한 값). 필드에서 받은 panic 로그에 날 주소가 있다면 이 줄로 System.map 기준 주소를 만든다.

7.3 nokaslr — 디버깅할 때는 끄는 것도 방법#

nokaslr 부팅 인자로 같은 null 버그를 냈더니:

출력에서 볼 것: 모듈 주소가 0xffff80007bfa0000처럼 커널 기본 주소(0xffff800080000000) 바로 아래 고정 영역으로 왔다. 커널 이미지도 System.map 주소 그대로 돈다 — 그래서 JTAG·kgdb 세션(M4)이나 반복 재현 실험에서는 nokaslr이 편하다. Code: 첫 워드가 ffff8000으로 바뀐 것도 보인다(§5의 ftrace ops 포인터 상위 32비트가 주소에 따라 달라짐). 양산 이미지에서는 KASLR을 끄지 않는다. 보안 기능이기 때문이다.

7.4 %p·kptr_restrict와 주소 숨김#

Oops의 레지스터 덤프(x0~x29, sp)는 날 주소를 그대로 찍는다(디버깅용 예외 — pc/lr은 %pS로 심볼+오프셋). 하지만 일반 printk("%p")는 해시값을, /proc/kallsyms는 kptr_restrict가 1 이상이고 CAP_SYSLOG가 없으면 0을 보여 준다(M1 §%p 해싱, M2 /proc/modules). 필드 로그 분석 때 "주소가 다 0이에요"라는 말을 들으면 이것이다. 그래서 Oops를 심볼 이름과 함께 찍는 CONFIG_KALLSYMS가 양산에서도 중요하다 — 끄면 이미지는 조금 작아지지만 필드 Oops가 날 주소뿐이 된다.

8.2 BUG_ON — 그리고 첫 Oops 뒤의 커널은 믿을 수 없다#

출력에서 볼 것:

  • kernel BUG at m3_bugs.c:47! — 파일과 줄이 로그에 바로 있다. BUG()는 brk 명령과 함께 __bug_table 섹션에 "이 brk 주소 = 이 파일:줄"을 기록해 두고, 핸들러(report_bug())가 pc로 표를 찾아 찍는다. 그래서 BUG/WARN은 해독 도구 없이도 줄이 나온다.
  • 숫자 f2000800은 ESR이다. EC 0x3c(BRK), imm 0x800.
  • 그 뒤가 중요하다. 태스크가 IRQ를 끄고 preempt_count 1인 채로 죽었다(note: ... exited with ...). 그 상태가 idle 태스크(swapper/0, PID 0)까지 번져 context tracking 검사기가 WARN을 쳤다. 이 WARN은 m3_bugs와 아무 관계 없는 kernel/context_tracking.c를 가리킨다. 그리고 taint에 D(DIE)가 붙어 있다 — "이미 한 번 죽은 커널"이라는 표시다.
  • 교훈: 로그에 크래시가 여러 개면 항상 첫 번째([#1], 또는 taint에 D/W가 아직 없는 것)부터 본다. 나머지는 후유증일 가능성이 크다. 커뮤니티도 taint D가 있는 보고는 "첫 Oops를 보여 달라"고 돌려보낸다.

8.3 WARN — 계속 달리는 경고, 그리고 _ONCE#

warn 실험은 트리거를 두 번 썼고, 그 뒤 taint 값을 읽었다.

출력에서 볼 것:

  • rc=0 — echo가 성공했다. WARN은 아무도 죽이지 않는다. Internal error, Code: 줄도 없다.
  • 두 번째 트리거(rc2=0)는 아무것도 찍지 않았다. WARN_ON_ONCE는 호출 지점마다 한 번만 찍는다(지점별 static 플래그). 필드 로그에서 WARN이 한 번만 보인다고 한 번만 일어난 것이 아니다.
  • taint 12800 = 0x3200 = 비트 9(W, WARN) + 12(O) + 13(E). 경고 이후 이 커널의 모든 Oops 헤더에 W가 찍힌다(비트 표는 M2).
  • warnf의 WARN(1, "m3: sensor %s timed out (%d)\n", ...)은 메시지 한 줄이 cut here 바로 아래에 먼저 나온다: m3: sensor imu0 timed out (-110). 드라이버에서 WARN을 쓸 거면 메시지 있는 형태가 필드 분석에 훨씬 낫다. (§4.3에서 본 대로 이 경우 pc와 lr이 같다.)

8.4 BUG: scheduling while atomic — 검사기의 보고#

출력에서 볼 것:

  • sh/79/0x00000002 = 명령/PID/preempt_count. 스핀락이 1, __schedule 진입이 1을 더했다.
  • Preemption disabled at: m3_trigger+0x198 — 선점을 끈 위치(= spin_lock)를 따로 알려 준다(CONFIG_DEBUG_PREEMPT). 콜스택은 잠든 곳(msleep)이고 이 줄은 락을 잡은 곳이다. 둘 다 있어야 원인이 보인다.
  • 스케줄러는 보고 뒤 preempt_count를 강제로 맞춰 계속 가므로, 나중의 spin_unlock이 카운트를 0 아래로 내리려 해서 두 번째 WARN이 나왔다. 역시 첫 보고가 원인, 두 번째는 후유증이다. 줄 사이에 ** replaying previous printk message **가 끼어든 것은 콘솔 출력이 겹쳤을 때 printk가 하는 일이다(M1).
  • 이 커널은 DEBUG_ATOMIC_SLEEP이 꺼져 있어 msleep 진입 시점이 아니라 실제로 잠들 때 잡혔다. 켜면 BUG: sleeping function called from invalid context로 더 일찍 잡힌다(E4 §5.4, M8).

8.5 정책 — panic_on_oops, panic_on_warn#

oops=panic(= sysctl kernel.panic_on_oops=1)으로 같은 null 버그를 내면 Oops 끝에 이 줄이 붙고 시스템이 멈춘다(§7.2의 출력).

8.6 lockup — 별도 모듈로 soft lockup 내 보기#

선점을 끈 채 30초 바쁘게 기다리는 별도 모듈(m3_lock.ko)을 watchdog_thresh=5로 부팅한 게스트에서 insmod했다. soft lockup 기준은 2 × watchdog_thresh = 10초다.

출력에서 볼 것:

  • [C1] — 이 보고는 태스크(T77)가 아니라 CPU 1의 hrtimer 인터럽트가 찍었다(PRINTK_CALLER). watchdog은 각 CPU의 타이머 인터럽트에서 "그 CPU의 watchdog 스레드가 최근에 돌았나"를 확인한다. 찍힌 pc·Call trace는 인터럽트 순간 그 CPU가 하던 일이다 — 루프 안 아무 지점이다. 그래서 lockup 보고를 여러 번 비교하면(__delay+0x5c → +0x90) 루프의 범위가 보인다.
  • stuck for 13s — 기준 10초인데 13초, 이후 24s·35s로 반복 보고. TCG에서 타이머가 늦게 돌기 때문에 숫자가 실제 하드웨어보다 거칠다.
  • Modules linked in: m3_lock(OE+) — +는 "로드 중"(init 함수가 아직 안 끝남) 표시다.
  • CPU 1이 묶이자 그 CPU의 workqueue도 멈춰 46초 뒤 BUG: workqueue lockup이 다른 CPU(C0)에서 보고됐다. 하나의 원인이 여러 검사기를 깨운다.
  • 30초 뒤 init이 끝나 rc=0. 시스템은 살았고, taint 28672 = 0x7000 = O·E·L(비트 14, SOFTLOCKUP).
  • 이 밖의 "멈춤" 보고는 이번에 실행하지 않았다(가이드): hard lockup(watchdog: CPU1: Watchdog detected hard LOCKUP on cpu 1 — IRQ까지 꺼진 루프, buddy 검출기는 이웃 CPU가 보고), hung task(INFO: task <이름>:<pid> blocked for more than 120 seconds. — D 상태로 오래 잠든 태스크), RCU stall(rcu: INFO: rcu_preempt detected stalls on CPUs/tasks:).

9.2 사례 — use-after-free (slab_debug=P)#

읽는 순서: FAR이 6b 반복 → 해제된 객체에서 읽은 포인터를 따라갔다. x19 = ffff000006194500은 선형 맵의 slab 객체(= 해제된 그 객체), x0 = 6b6b…는 거기서 읽은 오프셋 24의 값. lr이 kfree 복귀 지점(§4.3). Code:의 97ffff81은 bl(= kfree), f9400e60 = ldr x0, [x19, #24], 괄호 안 ldr x1, [x0]. 소스 없이도 "kfree 직후 그 객체의 +24 포인터를 역참조" 까지 나온다.

slab poisoning이 없었다면? 해제된 메모리에는 예전 값(&m3_ops)이 그대로 남아 있어서 호출이 성공했을 것이다. UAF는 대개 조용히 지나가다 나중에 다른 객체가 그 메모리를 재사용할 때 엉뚱한 곳에서 터진다. 개발 빌드에서 slab_debug=P(또는 slab_debug=FZPU) 부팅 인자로 poisoning을 켜는 이유다. KASAN(M8)은 첫 잘못된 접근에서 alloc·free 콜스택까지 붙여서 바로 잡는다.

9.3 사례 — list_del 두 번 (dead…108)#

list_del(entry)은 entry->next->prev = entry->prev 를 하고 나서 entry->next = LIST_POISON1, entry->prev = LIST_POISON2를 박는다. 두 번째 list_del에서 entry->next가 dead…100이므로 next->prev(= +8)에 쓰기 → dead…108, WnR=1. 레지스터에 x1 = LIST_POISON1, x2 = LIST_POISON2가 그대로 있다. faddr2line은 include/linux/list.h:210의 __list_del 안이라고 알려 줬다(§6.2). CONFIG_DEBUG_LIST(또는 LIST_HARDENED)가 켜져 있으면 fault 전에 list_del corruption. next->prev should be ..., but was dead000000000122 같은 보고로 잡힌다 — 이 랩 커널은 둘 다 꺼져 있다.

9.4 사례 — 크래시 지점 ≠ 버그 지점 (list)#

이 실험은 이 노트에서 가장 중요한 교훈이다. pc가 커널 코어(lib/vsprintf.c)에 있다.

decode_stacktrace.sh는 pc : string (lib/vsprintf.c:653 lib/vsprintf.c:735), m3_list_bug (m3_bugs.c:67 (discriminator 4))라고 풀었다. 추리:

  1. pc는 string() — printk의 %s 처리기. ldrb w5, [x2, x4]로 문자열의 바이트를 읽다가 죽었다. 문자열 주소 x2 = 4141414141414139.
  2. 'A' = 0x41. 그 주소는 "AAAAAAAA"에서 8을 뺀 값이다. §6.5의 pahole: struct m3_ent는 tag[8] 다음 오프셋 8에 node. list_for_each_entry는 node.next에서 8을 빼 엔트리 주소를 만든다(container_of). 즉 어떤 엔트리의 node.next가 'A'로 덮여 있었고, 그 가짜 엔트리의 tag를 출력하려다 죽었다.
  3. 바로 앞에 tag AAAAAAAA가 찍혔다 — 덮어쓰인 엔트리를 정상적으로 출력한 뒤, 그 엔트리의 next를 따라간 것이다.
  4. 그러니 버그는 printk가 아니라 이 엔트리를 덮어쓴 코드다(8바이트 tag에 24바이트를 써서 node의 next·prev까지 침범). 그 코드는 Call trace에 없다 — 이미 끝났기 때문이다.

그림 7 — 크래시 지점 ≠ 버그 지점. 메모리 오염 버그는 오염을 사용하는 코드에서 터진다. pc가 커널 코어 함수(string, memcpy, list_*, kfree)에 있으면 먼저 "누가 나쁜 데이터를 넘겼나"를 Call trace 아래쪽에서 찾는다.

9.5 사례 — 정렬 fault (misalign)#

이번엔 swapper pgtable(커널 주소)이고 PTE까지 전부 유효하다(pte=00e8…ff03). 페이지는 멀쩡히 있다 — 문제는 주소 끝자리 …89(홀수)다. arm64는 일반 메모리에 대한 보통의 ldr/str은 비정렬이어도 하드웨어가 처리하지만, ldxr/stxr(exclusive) 같은 atomic 명령과 Device 메모리(MMIO) 접근은 자연 정렬이 필수다. Cortex-M에서 UNALIGN_TRP나 LDREX 정렬 fault를 본 적이 있다면 같은 이야기다. 실무 원인은 __packed 구조체 안의 atomic_t/spinlock_t, 또는 패킷 버퍼 + 1 같은 포인터 연산이다. 드라이버의 readl()을 비정렬 MMIO 주소로 해도 같은 FSC가 나온다.

9.6 사례 — 스택 overflow (stack)#

FAR …7fc8은 태스크 스택 하한 …8000의 0x38바이트 아래, guard page다. 형식이 일반 Oops와 다르다: Mem abort info 해석 대신 ESR:/FAR: 한 줄씩, 그리고 세 스택의 범위. 예외 진입 코드가 sp를 검사해 CPU별 Overflow stack으로 갈아타고 바로 panic한다(태스크를 정상 종료시킬 스택이 없으니까). pc가 memset인 이유(지역 배열 0 초기화, CONFIG_INIT_STACK_ALL_ZERO)와 16 KiB 스택 이야기는 E4 §4.4에서 같은 형식의 로그로 자세히 다뤘다. 여기서 볼 것은 반복되는 Call trace 줄 = 재귀라는 패턴뿐이다.

9.7 사례 — 0으로 나누기는 트랩이 아니다 (div0)#

Oops가 없다. A64의 sdiv/udiv는 제수가 0이면 결과 0을 돌려줄 뿐 예외를 내지 않는다(아키텍처 정의). x86은 #DE 예외 → divide error: 0000 Oops를 내고, Cortex-M은 CCR.DIV_0_TRP를 켜면 UsageFault를 낸다. 그래서 arm64에서는 0 나누기가 조용히 틀린 값이 된다. "x86에서는 죽던 버그가 ARM 보드에선 안 죽는다"는 이식 함정이고, UBSAN(M8)의 -fsanitize=integer-divide-by-zero로만 잡힌다.

10. 현장 워크플로 — 붙여 넣은 Oops 하나만 받았을 때#

고객이 슬랙에 콘솔 로그를 붙여 넣었다. 할 일을 순서대로 적는다.

  1. 첫 보고를 찾는다. [#1], taint에 D/W가 아직 없는 것. 그 앞 수십 줄(드라이버 에러, 타임아웃, -EIO)도 같이 확보한다 — 원인은 종종 Oops 전에 찍혀 있다.
  2. 종류를 정한다(그림 6). Oops / BUG / WARN / 검사기 / lockup / panic.
  3. 빌드를 고정한다. Linux version·CPU: 줄의 버전 문자열(6.18.55-trace #1)과 Tainted의 모듈 목록으로 정확히 같은 빌드의 vmlinux와 .ko를 구한다. 빌드 서버에 이미지마다 디버그 심볼(vmlinux, .ko 디버그 판, System.map)을 build-id와 함께 보관해 두는 것이 이 단계의 전제다. 다른 빌드로 풀면 줄 번호가 오류 없이 조용히 틀린다.
  4. 원인 필드: ESR → EC·WnR·DFSC, FAR 패턴(§9.1).
  5. 위치: pc를 faddr2line(크기가 안 맞으면 /size 제거), 의심스러우면 readelf -s로 섹션 확인 후 addr2line -j. 인라인 체인까지 본다.
  6. 호출자: lr과 Call trace를 같이 본다. leaf면 lr이 유일한 호출자 정보다(§4.2). lr이 같은 함수 안이면 "마지막으로 부른 함수"다(§4.3).
  7. 데이터: 레지스터 중 FAR과 같은 값, 0, poison 값을 찾고, Code:를 decodecode로 풀어 어느 레지스터가 베이스였는지 본다. 오프셋은 pahole로 멤버 이름이 된다.
  8. 크래시 지점이 버그 지점인가? pc가 커널 코어 함수면 데이터가 어디서 왔는지 거슬러 올라간다(§9.4).
  9. 재현과 탐지기: 같은 조건을 KASAN·DEBUG_LIST·lockdep 켠 빌드에서 재현한다(M8). 날 주소만 있으면 §7의 KASLR 보정.

로그가 아예 없다면? L7(pstore/ramoops로 다음 부팅에 회수, kdump로 메모리 전체), M1(earlycon), M4(JTAG로 멈춘 CPU의 PC·__log_buf 직접 읽기)로 간다.

11. 커널 안에서는 무슨 일이 일어나나#

그림 8 — 커널 안의 경로. MMU abort와 BUG의 brk는 다른 입구로 들어와 같은 die()에서 만난다. WARN은 die()에 가지 않고 pc를 다음 명령으로 넘겨 계속 실행한다.

  • fault 경로 (arch/arm64/mm/fault.c): do_mem_abort()가 ESR의 DFSC로 처리 함수 표를 찾는다(translation fault → do_translation_fault → do_page_fault). 커널 모드이고 유저 주소 처리로 해결이 안 되면 __do_kernel_fault()가 먼저 exception table을 본다. copy_from_user()처럼 "fault가 나도 되는" 명령이면 fixup 주소로 점프해서 -EFAULT를 돌려주고 끝이다(E6, get_user). 표에 없으면 die_kernel_fault()가 Unable to handle kernel ..., mem_abort_decode()(Mem abort info 블록), show_pte()를 찍고 die()를 부른다.
  • BUG/WARN 경로: BUG()/WARN()은 brk #0x800과 __bug_table 항목(주소·파일·줄·플래그)을 만든다. debug 예외 → bug_brk_handler() → report_bug()가 pc로 표를 찾아 kernel BUG at … 또는 WARNING: …을 찍는다. BUG면 die("Oops - BUG", …), WARN이면 arm64_skip_faulting_instruction()으로 pc += 4 하고 돌아간다.
  • die() (arch/arm64/kernel/traps.c): die_lock을 잡고 console_verbose()(콘솔 레벨을 최대로 — quiet여도 Oops가 보이는 이유, M1), __die()가 Internal error: %s: %016lx [#%d] SMP, 모듈 목록, show_regs(), Call trace, Code:를 찍는다. taint D를 더하고, in_interrupt()면 panic("Fatal exception in interrupt"), panic_on_oops면 panic("Fatal exception"), 아니면 make_task_dead(SIGSEGV) — 유저가 본 Segmentation fault/rc=139다.
  • 드라이버를 쓸 때 다시 만나는 지점: BUG_ON은 리뷰에서 거의 거부된다(시스템을 죽이니까). 복구 가능한 상황은 WARN_ON_ONCE + 에러 반환(if (WARN_ON_ONCE(!dev)) return -EINVAL;)이 커널 관례다(E5). 유저 포인터는 반드시 exception table을 쓰는 copy_*_user 계열로 만져야 Oops가 아니라 -EFAULT가 된다(E6, G4).

12. Embedded 실무에서 다시 보기#

센서 키트 IMU 드라이버의 probe NULL. i.MX8 보드에서 IMU 드라이버가 devm_regulator_get_optional()의 반환값을 NULL 검사만 하고 쓰면, 실패 시 돌아온 ERR_PTR(-ENODEV)(= 0xffffffffffffffed)에 멤버 오프셋을 더한 주소가 FAR로 찍힌다(오프셋이 크면 0 근처로 넘어가기도 한다). FAR이 0xffff…fff에 가까운 작은 음수면 ERR_PTR 역참조다(IS_ERR 대신 !ptr 검사). 작은 양수(0x10)는 NULL, 큰 음수 근처는 ERR_PTR — 이 두 패턴만 알아도 bring-up Oops의 절반은 첫 줄에서 끝난다. (이 FAR 패턴은 이번 랩에서 실행하지 않았다 — 가이드.)

전원 꺼진 블록의 레지스터 접근. 런타임 PM으로 클록이 꺼진 IP의 레지스터를 readl()하면 SoC에 따라 동기 external abort(EA = 1, FSC = 0x10)나 비동기 SError Interrupt가 난다. SError는 pc가 원인 명령이 아닐 수 있다(BFSR.IMPRECISERR와 같다). Don의 RF 칩 bring-up 경험 — "버스 에러가 나면 먼저 클록·전원·리셋" — 이 그대로 통한다(N5 런타임 PM, H 모듈). (가이드 — QEMU virt에서는 재현하지 않았다.)

필드 장비의 로그 회수. 양산 드론·카메라에는 UART가 없다. panic_on_oops=1 + panic=5 + ramoops(L7)로 Oops 텍스트를 다음 부팅에 /sys/fs/pstore/dmesg-ramoops-0로 회수하고, 빌드 서버의 build-id 매칭 vmlinux·.ko로 §10 순서를 돌린다. 모듈의 디버그 정보는 이미지에서 strip되므로(INSTALL_MOD_STRIP=1) strip 전 .ko를 따로 보관해야 한다 — 없으면 Call trace의 [모듈] 줄은 함수+오프셋까지만 읽힌다.

벤더 BSP 모듈. 소스 없는 벤더 .ko(GPU, Wi-Fi)에서 Oops가 나면 Tainted: P(proprietary)가 붙고 커뮤니티 지원은 끝이다. 그래도 Code:와 objdump -dr로 죽은 명령과 오프셋까지는 직접 볼 수 있어 벤더에 보낼 버그 리포트의 질이 달라진다.

14. 면접에서 이렇게 말한다#

Q. Here's a kernel oops. Walk me through how you read it.

A. 첫 Oops인지([#1], taint) 확인 → 첫 줄과 ESR로 종류(커널 data abort, 읽기, L2 translation fault)와 FAR(0x10) → Modules linked in·taint로 용의자 → pc를 faddr2line으로 소스 줄과 인라인 체인 → lr과 Call trace로 호출 경로(leaf면 lr만이 호출자) → 레지스터와 Code:로 어느 포인터가 NULL이었는지, pahole로 오프셋을 멤버 이름으로 → 마지막으로 크래시 지점이 진짜 버그 지점인지 판단한다.

First I make sure it's the first oops — the [#1] and no D taint — because later ones are often fallout. The first line plus the ESR tell me what happened: here a kernel-mode data abort, a read, translation fault, at address 0x10. Then Modules linked in and the taint flags give me suspects. I take the pc, symbol plus offset, and run faddr2line against the exact same build's module to get the file, line and inline chain. Then lr and the call trace for the call path — if the faulting function is a leaf, the caller only shows up in lr. The registers and the Code line tell me which register held the bad pointer, and pahole turns the offset into a struct member. Last question: is the crash site the bug site, or did someone corrupt the data earlier?

꼬리 질문: "decode_stacktrace.sh가 틀린 줄을 줄 수 있나?" → 함수가 .text.unlikely 같은 다른 섹션에 있으면 그렇다. 실제로 겪었고 faddr2line/addr2line -j로 교차 확인했다.

Q. The faulting address is 0x10. What does that tell you?

A. 첫 페이지 안의 작은 주소는 NULL 포인터 + 멤버 오프셋이다. 0x10이면 오프셋 16의 멤버다. Code:의 ldr w0, [x0, #16]이 4바이트 읽기임을 확인하고, pahole로 그 구조체의 16번 오프셋 멤버를 찾는다. 그다음은 "왜 그 포인터가 NULL이었나" — 대개 조회·할당 함수의 실패 반환값을 확인하지 않은 것이다.

A small address in the first page means a NULL struct pointer plus a member offset — here offset 16. The Code line shows ldr w0, [x0, #16], so a 32-bit load with x0 equal to zero. pahole on the struct tells me which member sits at offset 16; in my lab it was the irq field. Then the real question is why the pointer was NULL — usually a lookup or allocation whose failure return wasn't checked. If the address were something like 6b6b6b6b, I'd think use-after-free instead, and dead000000000100 or 122 means a list entry that was already deleted.

Q. What's the difference between an oops, a panic, a BUG and a WARN?

A. Oops는 커널 모드 예외로 현재 태스크만 죽이고 계속 간다(taint D). panic은 모든 CPU를 멈춘다. BUG_ON은 일부러 Oops를 내는 것(brk)이고, WARN은 콜스택만 찍고 계속 실행한다(taint W). Oops가 인터럽트 문맥이면 panic이고, panic_on_oops/panic_on_warn으로 정책을 바꾼다.

An oops is an unhandled exception in kernel mode: the kernel prints the report and kills the current task, but keeps running, tainted D. A panic stops all CPUs. BUG_ON deliberately triggers an oops through a brk instruction; WARN prints the same kind of report and then just continues, tainted W. An oops in interrupt context always becomes a panic, and panic_on_oops or panic_on_warn turn the others into panics. On production embedded devices I set panic_on_oops plus a reboot timeout and capture the log with pstore, because a half-dead kernel holding locks is worse than a clean reboot.

Q. Why might the function that called the crashing function be missing from the call trace?

A. arm64 unwinder는 x29 frame record 체인을 따라간다. leaf 함수는 frame record를 안 만들어서 x29가 여전히 호출자의 record를 가리키고, 그 record에는 호출자의 복귀 주소(한 단계 위)만 있다. 호출자 자신의 위치는 x30(lr)에만 있다. 인라인된 함수도 Call trace에 안 나오며 faddr2line의 inlined-by 체인으로만 보인다.

The arm64 unwinder walks the chain of frame records — x29 and x30 pairs pushed in each prologue. A leaf function doesn't push one, so x29 still points at the caller's record, which holds the caller's return address — one level up. The caller's own position is only in lr. I saw exactly that: the pc was in a small getter, and its caller appeared only on the lr line. Inlined functions never appear either; faddr2line's inlined-by chain shows them.

Q. You only have a raw address from a field log. How do you map it to a symbol with KASLR on?

A. 커널 이미지는 panic 로그의 Kernel Offset: X나 런타임 _text와 System.map _text의 차이로 오프셋을 구해 빼면 System.map 주소가 된다. 모듈은 별도 무작위 배치라 /sys/module/<m>/sections/ 시작 주소를 빼서 섹션 오프셋으로 만들고 addr2line -j <섹션> 또는 gdb add-symbol-file에 섹션 주소를 다 준다.

For the kernel image I subtract the KASLR offset — either from the Kernel Offset line in the panic, or runtime _text minus System.map _text — and then addr2line against vmlinux. Modules are randomized separately, so I subtract the section base from /sys/module/name/sections and use addr2line with -j for that section, or give gdb add-symbol-file every section address. For repeatable debugging sessions I'll just boot with nokaslr.

Q. The pc is inside printk's string(). Is this a printk bug?

A. 거의 아니다. 코어 함수에서 죽으면 나쁜 데이터를 넘긴 쪽을 의심한다. 실험에서 FAR이 ASCII 'A' − 8이었다 — 문자열이 리스트 포인터를 덮었고 container_of가 8을 뺐다. 버그는 덮어쓴 코드였고 Call trace에는 없었다. DEBUG_LIST나 KASAN으로 더 일찍 잡는다.

Almost never. When the pc is in a core helper like string, memcpy or list code, I look for who passed bad data. In my lab the address was 0x4141414141414139 — ASCII A's minus 8 — so string data had overwritten a list pointer and container_of subtracted the member offset. The real bug was an earlier buffer overrun that had already returned, so it's not on the stack at all. I'd reproduce with CONFIG_DEBUG_LIST or KASAN to catch it at the write.

Q. How does this map to Cortex-M HardFault debugging you've done?

A. 1:1이다. CFSR ↔ ESR, BFAR/MMFAR ↔ FAR(BFARVALID ↔ FnV 반대 극성), stacked PC/LR/xPSR ↔ pc/lr/pstate, imprecise bus fault ↔ SError, map 파일 ↔ System.map + KASLR 보정. 차이는 Linux는 해석까지 찍어 주고, 기본이 시스템 정지가 아닌 태스크 종료라는 것.

It's almost one to one. CFSR maps to ESR, BFAR and MMFAR to FAR — with FnV as the inverted BFARVALID — and the stacked PC, LR and xPSR to the pc, lr and pstate lines. An imprecise bus fault is an SError on arm64. The map file becomes System.map plus a KASLR correction. The differences are that Linux decodes everything for you, and that by default it kills only the current task instead of halting the system — which is why I'd turn on panic_on_oops on a product.

15. 직접 해보기#

  1. 개념 — ESR 0x92000047을 손으로 풀어라. EC·WnR·DFSC는? 커널 모드인가? 정답/힌트: EC = 0x24(하위 EL = 유저 모드 data abort), WnR = 1, DFSC 0x07 L3 translation. 커널 Oops가 아니라 유저 프로세스의 page fault(대개 정상 처리되거나 SIGSEGV)다.
  2. 개념 — FAR이 fffffffffffffff4였다. 무엇을 의심하나? 정답/힌트: ERR_PTR(-12)(-ENOMEM) 역참조. IS_ERR() 검사 누락.
  3. 해독 과제 — §8.6 lockup 로그의 m3_lock_init+0x30/0xfb0을 faddr2line으로 풀어 보라. 처음에 무슨 메시지가 나오나? 정답/힌트: size mismatch로 거부된다. /0xfb0를 떼면 된다. 0xfb0이 왜 그렇게 큰지 §6.2로 설명해 보라.
  4. 해독 과제 — §9.4 list Oops의 string+0x50/0x140을 vmlinux-trace로 faddr2line하고, 출력의 두 줄(653, 735)이 각각 무슨 함수인지 말하라. 정답/힌트: string_nocheck(vsprintf.c:653)가 string(735)에 인라인됐다. 실제 출력은 §9.4 위 문단.
  5. 관찰 과제 — QEMU 게스트에서 echo 1 > /proc/sys/kernel/panic_on_oops 후 같은 Oops를 내고, panic 줄의 Kernel Offset으로 Call trace의 vfs_write 런타임 주소를 계산해 System.map과 대조하라. 정답/힌트: §7.2. 오프셋을 더하면 런타임, 빼면 System.map.

  7. 관찰 과제 — uaf를 slab_debug=P 없이 돌려 보라. 무슨 일이 일어나나? 왜 그런가? 정답/힌트: 아마 아무 일도 안 일어난다(해제된 메모리에 옛 값이 남음). §9.2. Image-kasan에서 돌리면 KASAN 리포트가 나온다(M8).

17. 요약 & 체크리스트#

Oops는 HardFault 덤프를 커널이 해석까지 해서 찍어 주는 것이다. 첫 Oops를 고르고, 첫 줄·ESR(EC·WnR·DFSC)·FAR로 "무엇이 왜"를, pc→faddr2line으로 "어디서"를, lr·Call trace로 "누가"를, 레지스터·Code:·pahole로 "어떤 데이터"를 읽는다. 도구는 같은 빌드의 심볼이 있어야 맞고, 섹션(.text.unlikely)·kallsyms 크기·재배치 전 objdump 같은 함정 때문에 두 도구로 교차 확인한다. KASLR은 Kernel Offset/_text 차이로, 모듈은 섹션 시작 주소로 보정한다. 주소 패턴(0x10, 6b6b, dead…100/122, ASCII, 홀수 주소, 스택 하한)은 버그 유형을 바로 알려 주고, 메모리 오염 버그는 크래시 지점과 버그 지점이 다르다는 것을 항상 기억한다. Oops·panic·BUG·WARN·lockup은 보고 형식과 "그 뒤"가 다르며, 양산 장비는 panic_on_oops + 리부트 + pstore가 기본 정책이다.
