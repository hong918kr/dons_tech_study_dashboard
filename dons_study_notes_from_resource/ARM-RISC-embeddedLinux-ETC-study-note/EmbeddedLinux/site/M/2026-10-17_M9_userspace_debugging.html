0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어에서 버그를 잡을 때 Don의 도구는 셋이었다: JTAG로 코어를 멈추고 들여다보기, assert 때 SRAM에 남긴 덤프를 나중에 읽기, UART 로그·트레이스 버퍼로 흐름 보기. Embedded Linux의 유저스페이스에도 정확히 같은 세 가지가 있다. 다만 "코어 전체"가 아니라 프로세스 하나가 단위다.

1. 준비 — debug 정보, stripped 바이너리, build-id#

1.1 직관 — "ELF와 .map 파일을 따로 보관한다"#

펌웨어 시절에는 .elf(심볼 있음)를 빌드 서버에 남기고, 칩에는 .bin만 구웠다. 크래시 PC가 오면 그 빌드의 .elf/.map으로 함수를 찾았다. Linux도 똑같다. 보드에는 stripped 바이너리(심볼·DWARF 없음, 작다)를 올리고, PC나 서버에는 debug 정보를 따로 둔다. 둘을 짝짓는 지문이 build-id(링커가 내용 해시로 만들어 .note.gnu.build-id에 넣는 20바이트)다. 기본 원리와 addr2line 사용법은 B3 §9.3에서 했다. 여기서는 디버거가 이 짝을 어떤 순서로 찾는지에 집중한다.

그림 2 — debug 정보 분리. 빌드 결과(파랑)를 보드용(주황)과 서버용(초록)으로 쪼개고, build-id가 둘을 잇는다. 아래 상자는 gdb가 debug 파일을 찾는 경로 순서다.

예제 1 — 게스트에서 빌드하고 쪼개기#

무엇을 확인하나: 같은 빌드에서 나온 세 파일의 크기와 build-id, 그리고 stripped 파일에 무엇이 남는지.

출력에서 볼 것:

  • build-id가 두 파일에서 같다. "이 debug 파일이 저 바이너리의 것"이라는 증거다.
  • sensord.debug를 readelf -n할 때 나온 "Unable to find program interpreter name"은 정상이다. debug 파일은 섹션 헤더만 남고 코드 바이트(.interp 포함)는 비어 있는 NOBITS다.
  • 보드용 파일에 .debug_*가 하나도 없고(원본은 8개), .symtab도 없다. 남은 것은 .gnu_debuglink(이름 + CRC)뿐이다.
  • 67600 vs 76928: 이 예제는 작아서 차이가 작다(arm64 기본 64 KiB 세그먼트 정렬 패딩이 대부분). 실제 앱은 DWARF가 코드보다 3~10배 큰 경우가 흔해서, 보드 플래시에서 큰 차이가 난다.

1.2 무엇을 켜고 빌드하나#

옵션효과보드에 올릴 때
-gDWARF 생성 (코드는 그대로 — -g는 생성 코드를 바꾸지 않는 것이 GCC의 원칙)분리해서 서버에 보관

Yocto는 -dbg 패키지(/usr/lib/debug/.build-id/...)와 IMAGE_GEN_DEBUGFS로 "debug용 rootfs"를 따로 만들고, Buildroot는 BR2_ENABLE_DEBUG + BR2_STRIP_strip로 staging/에는 심볼을, target/에는 stripped를 둔다(K3·K4 참고). 둘 다 그림 2의 구조를 자동화한 것이다.

함정: 같은 소스를 다시 빌드해도 build-id가 같다는 보장은 없다. 컴파일러 버전·경로·__DATE__·링크 순서가 달라지면 해시가 바뀐다. "나중에 다시 빌드하면 되지"는 틀렸다. 출시 빌드의 debug 파일은 빌드할 때 보관해야 한다 (예제 12에서 직접 깨 본다).

2. 원격 디버깅 — gdbserver와 sysroot#

2.1 구조 — "보드에는 작은 stub, PC에는 똑똑한 gdb"#

JTAG 디버깅에서 OpenOCD가 하던 역할(타깃과 gdb 사이의 RSP 서버)을 gdbserver가 한다. 차이는 gdbserver가 보드의 Linux 위에서 도는 평범한 프로세스이고, ptrace()로 디버기 프로세스 하나를 조종한다는 점이다. 보드에는 심볼도 소스도 필요 없다. gdbserver는 레지스터·메모리 읽기/쓰기, breakpoint 삽입, 스레드 목록 정도만 한다. 심볼 해석·DWARF·소스 표시는 전부 PC의 gdb가 한다.

PC의 gdb가 알아야 하는 것은 세 가지다.

  1. 실행 파일의 debug 정보: file sensord.full (또는 stripped + debug-file-directory).
  2. 보드의 공유 라이브러리: 디버기는 보드의 libc.so.6·ld-linux-aarch64.so.1을 쓰므로 gdb도 똑같은 파일을 읽어야 한다. 이것이 set sysroot <보드 rootfs 사본>이다. 기본값 target:은 gdbserver에게 파일을 하나하나 받아 온다(느리지만 항상 맞다).
  3. 소스 경로: DWARF에는 빌드할 때의 경로가 박혀 있다. PC의 경로가 다르면 set substitute-path <빌드 경로> <내 경로>.

크로스 개발(x86 PC → arm 보드)에서는 PC의 gdb가 타깃 아키텍처를 알아야 하므로 gdb-multiarch(Debian/Ubuntu 패키지)나 툴체인의 aarch64-linux-gnu-gdb를 쓴다. 이 랩은 VM 호스트도 aarch64라 그냥 gdb를 썼지만, sysroot 문제는 그대로 재현된다: 호스트의 glibc는 2.43이고 게스트는 2.39이기 때문이다.

그림 3 — 원격 디버깅 토폴로지. 보드(주황)에는 stripped 실행 파일과 gdbserver만, PC(파랑)에는 debug 빌드·보드 rootfs 사본(sysroot)·소스가 있다. 둘은 TCP 위의 gdb Remote Serial Protocol(RSP)로 대화한다.

예제 2 — stripped 바이너리를 PC의 debug 빌드로 디버깅#

무엇을 확인하나: 보드에서는 stripped sensord를 gdbserver로 띄우고, PC에서는 debug 빌드 + sysroot로 breakpoint·스레드·bt를 본다.

먼저 PC 쪽 sysroot를 만든다. 보드 rootfs에서 libc와 로더를 같은 경로 구조로 복사한다(Ubuntu는 /lib → usr/lib usrmerge라 링크도 재현).

(Thread 2·1의 libc 프레임과 info proc mappings의 나머지 줄은 ...로 줄였다.)

출력에서 볼 것:

  • breakpoint는 보드의 stripped 바이너리에 걸렸는데, 함수 이름·줄 번호·스레드 이름이 다 나온다. 심볼은 전부 PC의 sensord.full에서 왔다. 보드에는 심볼이 한 바이트도 없다.
  • 처음 멈춘 곳은 ld-linux 다. gdbserver는 프로그램을 exec 직후, 동적 로더의 첫 명령에서 멈춘 채로 기다린다. main은 아직 안 돌았다.
  • libc 프레임이 ?? ()다. sysroot에는 libc 코드만 복사했고, libc의 debug 정보는 복사하지 않았다(Syms Read의 (*)). 보드에 /usr/lib/debug/.build-id/...가 있으면(이 rootfs는 valgrind 의존성으로 libc6-dbg가 깔려 있다) 그것도 sysroot에 복사하거나 set debug-file-directory로 가리켜야 libc 안까지 이름이 나온다. 예제 4에서 target:을 쓰면 이 파일까지 자동으로 받아 오는 것을 본다.
  • sensord.c: No such file or directory — DWARF에 박힌 빌드 경로 /mnt/m9/src가 PC에는 없다. 예제 4에서 substitute-path로 고친다.
  • info proc mappings의 실행 파일이 0xaaaaaaaa0000, libc가 0xfffff7df0000 — ASLR이 꺼져 있다. gdbserver(와 gdb)는 기본으로 자기가 띄운 프로세스의 ASLR을 끈다(--no-disable-randomization / set disable-randomization off로 켤 수 있다). 디버깅은 편해지지만, "ASLR 때문에만 나는 버그"는 이렇게 띄우면 재현이 안 된다.
  • filter가 apply_filter를 inline했다(#0과 #1이 같은 주소). -O1이라서 raw, prev는 <optimized out>이다. 출시 빌드 디버깅은 늘 이렇다.

예제 3 — sysroot를 틀리면#

무엇을 확인하나: PC 자신의 /(glibc 2.43)를 sysroot로 주면 어떻게 깨지나.

출력에서 볼 것:

  • 첫 줄의 process_envvars_default ... rtld.c:2726은 거짓말이다. PC의 ld.so(2.43) 심볼로 보드의 ld.so(2.39) 주소를 해석해서 엉뚱한 함수 이름이 붙었다. 경고조차 없다.
  • libc에서는 gdb가 .dynamic section ... wrong library or version mismatch?라고 경고하고 심볼을 포기했다(Syms Read No). 그 결과 unwind가 망가져 "corrupt stack?"으로 끝났다. 진짜 스택은 멀쩡하다.
  • 실무에서 "원격 bt가 이상하게 끊긴다", "libc 함수 이름이 이상하다"면 코드보다 sysroot를 먼저 의심한다. 보드 rootfs와 같은 빌드의 sysroot(Yocto SDK의 sysroots/<machine>, Buildroot의 staging/)를 써야 한다.

예제 4 — 이미 돌고 있는 데몬에 붙기: --multi, attach, target: sysroot, 조건부 breakpoint#

무엇을 확인하나: 보드에서 평소처럼 실행 중인 데몬(ASLR 켜짐)에 PC에서 붙는다. sysroot는 기본값 target:으로 두고, 소스 경로를 고치고, 조건부 breakpoint를 건다.

(같은 build-id debug 파일 읽기 줄 반복과 ring의 나머지 원소는 생략했다.)

출력에서 볼 것:

  • target: sysroot는 libc·ld.so를 gdbserver에게서 받아 왔고, 보드의 /usr/lib/debug/.build-id/27/...까지 찾아 받았다. 그래서 이번에는 libc 프레임이 __futex_abstimed_wait_common64 ... futex-internal.c:57처럼 이름이 나온다. 대신 시간이 예제 2(1.5 s)의 2.5배(3.9 s)였다. 이 정도 프로그램에서도 그렇고, 라이브러리 수십 개짜리 앱(Qt, GStreamer, ROS 2)은 몇 분이 걸린다. 그래서 gdb가 직접 "Use set sysroot"라고 권한다.
  • 주소가 0xaaaab869..., 0xffffa66... — 평소처럼 띄운 프로세스라 ASLR이 켜진 주소다. 예제 2와 비교해 보자.
  • break sensord.c:45 if y > 1050: 조건 검사는 gdb(PC)가 한다. 조건이 거짓이어도 breakpoint 때마다 프로세스가 멈추고 → 네트워크로 PC에 알리고 → PC가 조건을 보고 → 다시 진행시킨다. 초당 수천 번 지나는 곳이면 데몬이 눈에 띄게 느려진다(타이밍 버그가 사라지는 원인). ignore N, tbreak, 또는 gdbserver 쪽에서 평가하는 set breakpoint condition-evaluation target(지원되면)을 생각한다.
  • 마지막의 detach로 데몬은 계속 돈다. 운영 중인 장비에서 "붙었다 떨어지기"가 가능하다는 것이 JTAG halt와 다른 점이다(물론 멈춰 있는 동안 watchdog·타이머는 그대로 흐른다 — §9).

3. Linux에서 gdb — MCU와 다른 것들#

MCU의 gdb와 명령은 같지만, OS가 있어서 생기는 것들이 있다: 스레드, 시그널, fork/exec, syscall, 그리고 페이지 단위 메모리.

3.1 스레드#

  • info threads: LWP(커널 스레드 ID)와 스레드 이름(pthread_setname_np/prctl(PR_SET_NAME)으로 붙인 이름 — 데몬은 스레드마다 이름을 붙이자).
  • thread N, thread apply all bt, thread apply all bt full(지역 변수까지).
  • 기본(all-stop) 모드에서는 한 스레드가 멈추면 gdb가 모든 스레드를 멈춘다. set scheduler-locking step이면 step하는 동안 다른 스레드는 안 돈다(레이스 재현이 사라질 수 있다).
  • set non-stop on(attach 전에 설정): 멈춘 스레드만 멈추고 나머지는 계속 돈다. 오디오·제어 루프 스레드가 멈추면 안 되는 장비에서 쓴다. 명령 뒤에 &를 붙여 비동기로 쓴다(continue &, interrupt).

예제 5 — 멈춘 데몬: pstack 방식으로 모든 스레드 스택 뜨기#

무엇을 확인하나: ABBA 데드락에 빠진 프로세스를 커널 쪽(/proc)과 유저 쪽(gdb)에서 동시에 본다.

(gdb 시작 안내문, 반복되는 스택 프레임, __size 바이트열은 생략했다. 게스트 TCG라 gdb 한 번에 10초가 걸렸다.)

출력에서 볼 것:

  • 커널 쪽: 세 스레드 모두 wchan = futex_do_wait, %CPU 0 — 바쁘게 도는 것(livelock, 무한 루프)이 아니라 잠들어서 안 깨어나는 것이다. 커널 스택은 el0t_64_sync(유저의 SVC 예외) → __arm64_sys_futex → futex_wait. 이 정도면 "유저 락 대기"라는 것까지는 루트 권한 셸만으로 안다.
  • 유저 쪽: LWP 689(poll_thread, deadlock.c:15)는 cfg_lock을 기다리고, LWP 690(reload_thread, :28)은 bus_lock을 기다린다.
  • 결정적 증거는 mutex 내부의 __owner: bus_lock의 주인은 689, cfg_lock의 주인은 690. 689 → cfg_lock(주인 690) → bus_lock(주인 689) 로 순환이 닫힌다. glibc의 일반 mutex는 owner TID를 기록하므로 이 방법이 통한다(__owner는 glibc 내부 필드라 버전에 따라 이름이 다를 수 있다).
  • gdb -p ... -batch -ex "thread apply all bt"가 옛날 pstack/gstack 스크립트가 하던 일이다. 현장에서 "멈췄다" 리포트가 오면 죽이기 전에 이것부터 뜬다. gdb가 없는 보드라면 gcore나 kill -ABRT로 core를 남기고 PC에서 분석한다(§4).
  • 고치는 법은 락 순서 규칙(항상 bus → cfg)이다. 커널에서는 lockdep(M8)이 이 순환을 실행 중에 자동으로 잡는다. 유저스페이스의 대응물은 helgrind(--tool=helgrind의 lock order 검사)와 TSan의 lock-order-inversion 보고다.

3.2 시그널 — gdb가 먼저 받는다#

ptrace 중인 프로세스에 시그널이 오면 커널은 디버기를 멈추고 gdb에게 먼저 알린다. gdb는 시그널마다 정책이 있다(info signals).

3.3 fork/exec와 syscall#

  • set follow-fork-mode child: fork() 뒤 자식을 따라간다(기본은 parent). set detach-on-fork off면 둘 다 붙잡고 inferior N으로 오간다. 셸 스크립트로 띄우는 데몬, fork() 후 exec()하는 슈퍼바이저를 디버깅할 때 쓴다.
  • catch exec, catch fork: 그 순간에 멈춘다.
  • catch syscall <이름>: syscall 진입과 복귀에서 멈춘다. strace의 한 줄을 "멈춰서 bt를 볼 수 있는 strace"로 바꾼 것이다.

예제 6 — catch syscall로 "누가 그 파일을 열었나"#

무엇을 확인하나: needcfg가 설정 파일을 여는 openat에서 멈추고, 그 호출의 C 코드 위치와 반환값(-2 = ENOENT)을 본다.

출력에서 볼 것:

  • break main 후에 catch를 건 이유: 처음부터 걸면 동적 로더가 /etc/ld.so.cache, libc.so.6을 여는 openat에서 먼저 멈춘다(직접 해 보면 그렇게 나온다). 관심 구간에서만 catch를 켜는 것이 요령이다.
  • syscall 번호 56(arm64의 openat). arm64에는 open syscall이 없다(A1).
  • "returned from syscall" 시점의 x0 = -2. 커널은 errno를 음수로 돌려주고, glibc가 -1 + errno=ENOENT로 바꾼다. bt가 load_cfg() needcfg.c:11까지 보여 주므로 "어떤 코드가 어떤 경로를 열다 실패했는지"가 한 번에 나온다. strace -k(§5.2)가 이 빌드에서 안 될 때의 대안이다.

3.4 watchpoint — "누가 이 변수를 바꿨나"#

MCU에서 DWT 비교기로 하던 것과 같다. arm64 코어에는 하드웨어 watchpoint 레지스터(DBGWVR/DBGWCR) 가 몇 개 있고, Linux 커널은 ptrace 요청을 받아 그 레지스터를 스레드별로(context switch 때 교체) 프로그래밍한다. 개수를 넘기면 gdb는 소프트웨어 watchpoint(한 명령씩 실행하며 비교 — 수백 배 느림)로 떨어지거나 삽입에 실패한다.

예제 7 — watchpoint로 오염시킨 범인 잡기#

무엇을 확인하나: calib_gain이 언제·누구에 의해 100에서 다른 값으로 바뀌는지.

출력에서 볼 것:

  • 값이 바뀐 바로 그 명령(libc의 memcpy 안)에서 멈췄고, bt가 범인 set_name("imu0-left") ← tick(i=7)을 가리킨다. 116 = 0x74 = 't': 10바이트 문자열 "imu0-left\0"의 9번째 바이트가 name[8]을 넘어 calib_gain의 하위 바이트에 들어갔다(리틀 엔디언).
  • Hardware watchpoint라고 나온다. 데이터 위치가 정해진 전역이라 watch st.calib_gain으로 충분했다. 지역 변수나 힙 주소는 스코프를 벗어나면 gdb가 watchpoint를 지우므로 watch -l *(int *)0x...(location 고정)을 쓴다.
  • -O0 전역 변수라 컴파일러 경고가 없다. 실제로 이런 overflow는 -O2 -D_FORTIFY_SOURCE에서 memcpy 크기 검사에 잡히기도 한다 — 출시 빌드 옵션도 도구다.

4. core dump 분석 — 현장에서 한 번 죽은 것#

4.1 무엇이 남고, 무엇이 필요하나#

core 파일이 생기는 조건(ulimit -c, core_pattern, 파이프 모드에서는 RLIMIT_CORE가 무시되는 것)과 systemd-coredump로 모으는 방법은 A6 §8과 L7 §7에서 했다. 이 rootfs도 core_pattern이 |/usr/lib/systemd/systemd-coredump %P %u %g %s %t ...이다. 이 절은 받은 core를 읽는 쪽이다.

core 파일(ELF ET_CORE)에 들어 있는 것: 스레드별 레지스터(NT_PRSTATUS), siginfo(NT_SIGINFO), 어떤 파일이 어느 주소에 매핑됐었는지(NT_FILE), 그리고 쓰기 가능한 메모리(스택·힙·.data). 각 ELF의 첫 페이지(build-id 노트가 든 헤더)는 /proc/PID/coredump_filter의 비트 4(0x10)가 켜져 있을 때만 들어간다 — 이 보드의 기본값은 00000023이라 꺼져 있었다(예제 12에서 그 결과를 본다). 들어 있지 않은 것: 실행 파일과 .so의 코드 페이지, 그리고 심볼·DWARF. 그래서 같은 빌드의 실행 파일·라이브러리·debug 정보를 따로 구해야 한다. "core만 주세요"는 반쪽짜리 요청이다.

그림 4 — core 분석 흐름. core(빨강)에서 모듈별 build-id를 뽑고, 그 build-id로 symbol store(초록)에서 debug 파일을 찾아 gdb에 준다. 아래 세 결과가 이 절의 예제들이다.

예제 9 — stripped 바이너리가 현장에서 죽었다#

무엇을 확인하나: 보드에 올라간 stripped crash가 SIGSEGV로 죽은 core를 debug 정보 없이 보면 무엇이 보이나.

빌드 서버 역할: debug 정보는 build-id 경로로 "symbol store"(/root/symstore)에 넣고, 보드에는 strip-all 파일만 둔다.

출력에서 볼 것:

  • systemd-coredump가 저널에 남긴 스택은 전부 n/a — 보드에는 심볼이 없으니 당연하다. 주소만 남는다(그래도 이 주소가 중요하다, 예제 11).
  • gdb로 보면 libc 쪽은 이름이 나온다(__strlen_asimd, __libc_start_call_main): 이 보드에는 libc 자체의 debug 파일이 있기 때문이다. 반면 내 코드는 ?? (). strip-all이라 .symtab도 없고, debuglink가 가리키는 crash.debug는 같은 디렉터리에 없다.

예제 10 — symbol store를 가리키면#

출력에서 볼 것:

  • gdb는 core 속 build-id 2b1d43...로 /root/symstore/.build-id/2b/1d43...debug를 찾았다. 실행 파일은 보드의 stripped 그대로인데 함수·줄이 다 나온다.
  • 같은 주소 0xaaaac38e08d0 하나가 checksum ← handle_rx ← main 세 프레임으로 펼쳐졌다. -O1이 두 함수를 main에 inline했고, DWARF의 inline 정보가 그걸 다시 풀어 준 것이다. stripped 바이너리만 보고 "main에서 죽었다"고 하면 틀린다.
  • f=<synthetic pointer>: 구조체 f는 메모리에 안 만들어지고 레지스터로만 존재했다. 출시 빌드 core에서 흔히 보는 표시다.

4.2 PIE와 ASLR — 주소를 오프셋으로 바꾸기#

PIE 실행 파일은 링크할 때 0 기준으로 만들어지고, 실행할 때 커널이 무작위 기준 주소에 올린다(B3 §3). 그래서 현장 로그의 절대 주소는 실행마다 다르다. 소스로 바꾸려면 오프셋 = 주소 − 그 모듈이 올라간 기준 주소를 계산해서 debug 파일에 묻는다. 공유 라이브러리도 똑같다.

그림 5 — PIE 주소 계산. 실행 중 주소(왼쪽)에서 그 모듈의 기준 주소를 빼면 ELF 파일 안의 주소(오른쪽)가 된다. 복귀 주소는 호출 다음 명령을 가리키므로 arm64에서는 4를 뺀다.

예제 11 — gdb 없이 손으로: 기준 주소 찾고 addr2line#

무엇을 확인하나: core의 매핑 표에서 기준 주소를 읽고, 서버의 debug 빌드로 오프셋을 소스 줄로 바꾼다. 크래시 리포터가 "모듈 이름 + 오프셋 + build-id"만 올려 보내는 구조(L7 §9)가 이 계산에 기대고 있다.

출력에서 볼 것:

5. strace — syscall 경계에서 보기#

5.1 어떻게 동작하나, 그리고 왜 느린가#

strace는 ptrace(PTRACE_SEIZE)로 붙은 뒤 PTRACE_SYSCALL로 "다음 syscall 진입/복귀에서 멈춰라"를 반복한다. syscall 한 번마다 디버기 정지 → strace로 context switch → strace가 레지스터·인자 메모리를 읽고 출력 → 디버기 재개, 이 왕복이 두 번(진입, 복귀) 일어난다. Don에게 익숙하게 말하면 "SVC 핸들러 입구와 출구에 JTAG breakpoint를 걸고, 걸릴 때마다 PC 쪽 스크립트가 레지스터를 읽고 다시 run"이다. 그래서 syscall이 잦은 프로그램일수록 느려진다.

-e trace=openat처럼 필터를 줘도 기본 방식에서는 모든 syscall에서 멈춘 뒤 strace가 "이건 안 찍는다"고 판단할 뿐이라 비용이 거의 그대로다. strace 5.3부터 있는 --seccomp-bpf 는 디버기에 seccomp BPF 필터를 설치해서, 관심 있는 syscall만 SECCOMP_RET_TRACE로 strace를 깨우고 나머지는 커널 안에서 그냥 통과시킨다. 필터는 디버기가 시작할 때 설치해야 하므로 이미 도는 프로세스(-p)에는 쓸 수 없고, 필터가 자식에게 상속되므로 -f와 함께 쓴다.

그림 6 — strace의 두 방식. 위: 모든 syscall이 진입·복귀에서 멈추고 strace 프로세스가 매번 깨어난다. 아래: seccomp BPF 필터가 관심 없는 syscall은 커널 안에서 통과시킨다.

6. ltrace — 라이브러리 호출 경계#

6.1 어떻게 동작하나#

ltrace는 실행 파일의 PLT 항목(B3 §6: 공유 라이브러리 함수를 부르는 간접 점프 스텁)에 breakpoint를 심는다. 프로그램이 malloc@plt로 점프할 때마다 멈춰서 인자를 찍고, 복귀 주소에도 breakpoint를 걸어 반환값을 찍는다. 그래서 PLT를 거치지 않는 호출은 보이지 않는다: 정적 링크 바이너리(PLT가 없다), -fno-plt로 빌드한 바이너리(GOT를 직접 읽어 blr), 같은 라이브러리 안의 내부 호출(기본으로는 실행 파일의 PLT만 본다).

-z now(BIND_NOW)는 흔히 "ltrace를 망가뜨린다"고 알려져 있는데, 이 환경에서 직접 해 보면 결과가 다르다.

7. 메모리 버그와 레이스 — valgrind vs sanitizer#

7.1 두 가지 접근#

valgrind는 동적 바이너리 계측(DBI) 도구다. 프로그램을 CPU에서 직접 돌리지 않고, valgrind 코어가 기계어를 블록 단위로 중간 표현(VEX IR)으로 바꾸고, 도구(memcheck, helgrind …)가 검사 코드를 끼워 넣은 뒤 다시 기계어로 JIT해서 돌린다. Don의 말로 하면 ISS 위에서 펌웨어를 돌리면서 모든 load/store를 감시하는 것이다. 재컴파일이 필요 없고(stripped 출시 바이너리에도 쓸 수 있다, 단 줄 번호는 debug 정보가 있어야), 대신 느리고 무겁다. 모든 스레드를 한 번에 하나씩 돌린다(직렬화) — 그래서 멀티코어 타이밍 버그는 재현이 바뀐다.

sanitizer(ASan, TSan, UBSan, LSan)는 컴파일 시점 계측이다. GCC/Clang이 모든 load/store 앞에 "shadow 메모리 확인" 코드를 넣고, 런타임 라이브러리(libasan …)가 malloc/free를 바꿔 끼운다. ASan은 메모리 8바이트마다 shadow 1바이트를 두고, 할당 앞뒤에 "redzone"(접근 금지 띠)을, free된 블록은 "quarantine"(한동안 재사용 금지)에 둔다. MCU의 MPU 영역을 아주 촘촘히 걸어 둔 것과 비슷하다. 다시 빌드해야 하지만 훨씬 빠르고, 실제 멀티스레드로 돈다.

예제 22 — 같은 레이스를 helgrind와 TSan으로#

  • ASan과 TSan은 같이 못 쓴다(둘 다 shadow 메모리를 다른 방식으로 쓴다). CI에서 빌드를 따로 만든다: asan 빌드(+UBSan), tsan 빌드.

예제 24 — 자라는 프로세스를 관찰하고 gcore로 떠 두기#

무엇을 확인하나: grow(엔트리당 4 KB, 10 ms마다 하나)가 도는 동안 4초 간격으로 RSS와 [heap] 경계를 기록하고, 죽이기 전에 core를 떠 둔다.

출력에서 볼 것:

  • RssAnon이 4초에 약 1.8 MB씩 일정하게 늘고, [heap]의 끝 주소(brk)가 같이 밀려난다. 늘어나는 것이 익명·private dirty 힙이라는 것까지 /proc만으로 알았다. 파일 캐시·공유 라이브러리가 아니다.
  • 128 KB 이상의 큰 할당은 glibc가 [heap] 대신 별도 익명 mmap으로 받는다(M_MMAP_THRESHOLD). 그 경우는 [heap]이 아니라 이름 없는 rw-p 매핑 개수가 늘어난다. 스레드별 arena(64 MB 단위 익명 매핑)도 같은 모양이다.

  • 실전 순서: (1) 시간당 증가율을 smaps_rollup으로 며칠 기록(로그로 남기거나 메트릭으로 송신) → (2) 증가가 [heap]/익명인지, 특정 .so의 매핑인지, fd·스레드 수(ls /proc/PID/fd, Threads:)인지 구분 → (3) 재현 환경에서 massif / heaptrack / LSan → (4) 의심 경로에 카운터를 단다. 펌웨어 시절 "free block 수를 주기 로그로 남기던 것"과 같은 생각이다.
  • 누수가 아닐 수도 있다: glibc malloc은 free된 메모리를 OS에 바로 돌려주지 않는다(단편화, arena). RSS가 계단식으로 오르다 멈추면 정상일 수 있다. malloc_trim(0)을 불러 보거나 MALLOC_ARENA_MAX=2로 arena 수를 줄여 보면 구분된다.

  • systemctl kill -s SEGV 직후의 status는 아직 active (running)이었다. 커널이 core를 systemd-coredump에 파이프로 넘기고, systemd-coredump가 압축해서 저장을 마칠 때까지 죽은 프로세스가 회수되지 않는다(L7 §7의 core_pipe_limit). 이 TCG 게스트에서는 그게 약 60초 걸렸다. 그 동안 서비스 재시작도 지연된다 — 큰 프로세스의 core는 장비의 재시작 시간을 늘린다.
  • coredumpctl gdb <match>가 저장된 core를 꺼내 gdb를 바로 띄운다. --debugger-arguments로 배치 명령을 넘기면 스크립트로 쓸 수 있다. --debugger=로 gdb-multiarch 등을 지정할 수도 있다.
  • -p LimitCORE=infinity: 이 rootfs는 파이프 방식이라 RLIMIT_CORE가 무시되지만, 서비스 쪽 한도는 coredump.conf의 크기 제한과 함께 확인하는 습관을 들인다(L7 예제 10).

9.1 systemd 서비스 디버깅 함정 (가이드)#

  • watchdog: WatchdogSec=를 쓰는 서비스는 gdb에서 breakpoint에 멈춰 있는 동안 sd_notify("WATCHDOG=1")를 못 보내서 systemd가 SIGABRT로 죽인다. 디버깅할 때는 systemctl edit로 WatchdogSec=0을 넣거나 systemctl set-property --runtime(지원되는 속성일 때)로 끈다. HW watchdog(I9)를 데몬이 직접 쓰면 보드가 리셋된다 — 펌웨어 시절과 똑같은 함정이다.
  • 처음부터 gdbserver 아래에서 띄우기: drop-in으로 ExecStart= 를 비우고 ExecStart=/usr/bin/gdbserver localhost:2391 /usr/bin/sensord로 바꾸고 TimeoutStartSec=infinity. Type=notify 서비스라면 gdbserver 아래에서도 notify가 오도록 NotifyAccess=all이 필요할 수 있다.
  • 환경 차이 재현: systemd-run --pty -p ProtectSystem=strict -p User=sensor ...로 같은 샌드박스 옵션을 주고 셸에서 실행해 본다. "셸에서는 되는데 서비스로는 안 된다"의 대부분은 권한·경로·환경 변수다. strace -f로 EACCES·EPERM을 찾는다(SystemCallFilter= 위반은 SIGSYS로 죽는다).
  • ptrace 권한: 서비스가 NoNewPrivileges, 다른 사용자로 돌면 Yama ptrace_scope(L6)에 따라 root만 붙을 수 있다. 출시 장비에서 ptrace_scope=2(관리자만)나 3(아예 금지)로 잠그는 것도 정책이다.

10. 커널 안에서는 무슨 일이 일어나나#

이 노트의 거의 모든 도구는 커널의 세 가지 기능 위에 서 있다: ptrace(gdb, gdbserver, strace, ltrace), hw_breakpoint(watchpoint), coredump(core, gcore 제외 — gcore는 gdb가 ptrace로 메모리를 읽어 직접 쓴다). valgrind와 sanitizer는 커널 도움 없이 유저 공간에서 일한다(valgrind는 시그널·syscall을 가로채 흉내 낼 뿐이다).

그림 9 — 유저스페이스 디버깅 도구가 기대는 커널 경로. 왼쪽부터 ptrace(파랑), 디버기의 예외·syscall 정지와 hw watchpoint(주황), core dump(초록).

  • ptrace 연결: ptrace(PTRACE_SEIZE/ATTACH) → ptrace_attach()(kernel/ptrace.c)가 디버기의 task_struct->ptrace에 플래그를 세우고 tracer를 기록한다. 이후 디버기에 오는 시그널은 전달 전에 ptrace_signal()에서 멈추고 tracer에 waitpid()로 통보된다. 레지스터는 PTRACE_GETREGSET(NT_PRSTATUS, FP/SIMD는 NT_PRFPREG)로, 메모리는 PTRACE_PEEKDATA나 /proc/PID/mem·process_vm_readv()로 읽는다.
  • 소프트웨어 breakpoint: gdb가 해당 주소에 arm64 BRK 명령을 써 넣는다. 실행되면 EL0 동기 예외 → el0_brk64()(arch/arm64/kernel/entry-common.c) → SIGTRAP → ptrace 정지. 텍스트 페이지는 private 매핑이라 쓰는 순간 COW로 그 프로세스 사본만 바뀐다.
  • syscall 정지: PTRACE_SYSCALL이면 디버기 스레드에 syscall trace 플래그가 서고, arm64의 syscall_trace_enter()(arch/arm64/kernel/ptrace.c)가 ptrace_report_syscall_entry()로 멈춘다(복귀 때는 exit 쪽 대응 함수). strace의 두 번 정지가 이것이다. seccomp 필터가 있으면 __secure_computing()이 먼저 돌고, SECCOMP_RET_TRACE일 때만 tracer를 깨운다.
  • hw watchpoint: gdb가 NT_ARM_HW_WATCH regset을 쓰면 커널은 register_user_hw_breakpoint()로 perf 이벤트를 만들고, arch/arm64/kernel/hw_breakpoint.c가 DBGWVR/DBGWCR 레지스터를 프로그래밍한다. 스레드 전환마다 hw_breakpoint_thread_switch()가 값을 교체하므로 watchpoint는 스레드 단위다(gdb는 모든 스레드에 같은 값을 넣어 프로세스 단위처럼 보여 준다). 레지스터 수(이 CPU는 4개)를 넘으면 등록이 실패한다(예제 8).
  • core dump: 치명 시그널의 기본 동작이 "core"이면 get_signal()이 vfs_coredump()(fs/coredump.c, 6.18 이름 — 예전에는 do_coredump())를 부르고, ELF 실행 파일이면 binfmt->core_dump = elf_core_dump()(fs/binfmt_elf.c)가 note(레지스터·siginfo·NT_FILE)와 VMA를 쓴다. 어떤 VMA를 쓸지는 mm->flags의 coredump filter 비트가 정한다(예제 12).
  • 드라이버와 다시 만나는 곳: 데몬이 "멈췄다"면 예제 5처럼 /proc/PID/task/*/stack을 본다. 거기에 wait_event_interruptible → 내 드라이버의 .read(G3)가 보이면 유저가 아니라 드라이버가 안 깨우는 것이다(인터럽트 핸들러가 wake_up()을 안 부름, 조건 변수 갱신 누락 — F 모듈). strace -e trace=ioctl,read -T로 어느 ioctl이 몇 ms 막히는지 보는 것도 드라이버 디버깅의 첫 단계다(A3, A10). 커널 쪽 자체를 멈춰서 보는 것은 M4(kgdb·JTAG), 커널 함수 흐름은 M5(ftrace), 커널 메모리 버그 검사기는 M8(KASAN = ASan의 커널판, KCSAN = TSan의 커널판, kmemleak = LSan의 커널판)이다.

11.1 센서 키트 — "보드에서만 죽는다"#

i.MX8 보드의 센서 퓨전 데몬이 하루에 한두 번 SIGSEGV. PC의 x86 빌드에서는 재현이 안 된다. 순서:

  1. 증거부터: coredumpctl list로 core가 있는지, coredumpctl info로 시그널·스레드·저널 스택(주소)을 본다. core가 없으면 coredump.conf·coredump_filter(0x33)·디스크 여유부터 고친다(L7).
  2. 같은 빌드의 debug 파일: CI의 symbol store에서 build-id로 꺼낸다. 없다면 이 장애에서 가장 먼저 고칠 것은 빌드 파이프라인이다.
  3. PC에서 분석: gdb-multiarch -ex "set sysroot <Yocto SDK sysroot>" -ex "set debug-file-directory <store>" sensord core → bt, info threads, p $_siginfo.
  4. 타깃 차이 목록: 아키텍처(정렬 — arm64 유저 공간은 비정렬 접근을 대부분 허용하지만 원자 연산·Device 메모리는 아니다, char의 부호 — ARM은 기본 unsigned), 엔디언 가정, 메모리 순서(arm64는 x86보다 약하다 → 락 없는 링버퍼에서 barrier 누락이 ARM에서만 터진다), 타이밍(느린 CPU에서만 나는 레이스), 라이브러리 버전(sysroot), 커널 기능(ENOSYS), 메모리 부족.
  5. 재현 환경: 타깃용 ASan 빌드를 보드에 올려 돌린다(라이브러리 libasan.so 동봉, quarantine 줄이기). 레이스가 의심되면 TSan 빌드(VA 비트 확인). 재현이 되면 gdbserver + watchpoint로 마무리.

11.2 카메라 장비 — 일주일에 RSS 40 MB 증가#

Verkada 같은 카메라의 스트리밍 데몬. 매시간 smaps_rollup을 메트릭으로 보내 증가율을 본다. [heap]이 아니라 익명 mmap 개수가 늘면 큰 버퍼(프레임)·스레드 arena 쪽이고, fd 수가 같이 늘면 소켓·dmabuf fd 누수다(ls -l /proc/PID/fd에서 anon_inode:dmabuf가 쌓인다 — I 모듈의 V4L2/DRM 버퍼). 랩에서 같은 스트림을 재생해 massif·heaptrack으로 확인한다. ASan/LSan 빌드로 오래 돌리면 프로세스 종료 시 누수 스택이 나온다.

11.3 로봇 제어 루프 — 디버거가 문제를 바꾼다#

1 kHz 모터 제어 스레드(N2의 SCHED_FIFO)에 breakpoint를 걸면 루프가 멈추고, CAN 버스 상대(모터 컨트롤러)는 타임아웃으로 안전 정지한다. 그래서 실시간 경로는 멈추지 않는 도구로 본다: dprintf, non-stop 모드, uprobe·tracepoint(M7, M5), GPIO 토글 + 스코프(M11). strace도 그 스레드에는 붙이지 않는다(§5의 100배 오버헤드). 사후 분석은 core와 링버퍼 로그(펌웨어 시절 trace buffer와 같은 생각)로 한다.

11.4 "설정을 바꿨는데 안 먹는다"#

현장 지원에서 제일 흔한 문의다. strace -f -Z -e trace=%file -p $(pidof app)로 재로드(SIGHUP) 순간 앱이 실제로 여는 경로를 본다 — 대부분 다른 경로(/etc vs /usr/share vs overlay 상위층 J 모듈), 권한(EACCES), 또는 아예 다시 열지 않는다.

13. 면접에서 이렇게 말한다#

Q. "An application crashes only on the target board, never on your PC. How do you debug it?"

A. 먼저 증거를 확보한다: core dump가 남게 설정하고(coredump 정책·filter), 크래시 때의 build-id를 남긴다. 그 build-id로 CI에 보관한 debug 파일을 꺼내 PC에서 sysroot를 맞춰 gdb로 core를 연다. 동시에 타깃과 PC의 차이 — 아키텍처(정렬·char 부호·약한 메모리 순서), 라이브러리 버전, 커널 기능, 타이밍, 메모리 — 를 목록으로 놓고 좁힌다. 재현이 되면 타깃용 ASan/TSan 빌드와 gdbserver + watchpoint로 마무리한다.

First I make sure the target leaves evidence: core dumps enabled with a size policy, and the build-id recorded. With the build-id I pull the exact debug files from our symbol store and open the core on my PC with gdb-multiarch, with the sysroot pointing at the same rootfs build the board runs — otherwise the libc frames are wrong. That usually gives me the faulting thread and line. In parallel I list what differs between the board and the PC: the architecture — alignment, signed versus unsigned char, ARM's weaker memory ordering for lock-free code — library versions, kernel features, timing on a slower CPU, and memory pressure. If I can reproduce it, I run an ASan or TSan build on the board, and for memory corruption I use gdbserver with a hardware watchpoint on the variable that gets corrupted.

꼬리 질문: "core가 없다면?" → systemd-coredump 설정, coredump_filter, 디스크 공간, 그리고 다음 번을 위해 크래시 핸들러(시그널 핸들러에서 backtrace()는 async-signal-safe하지 않으니 별도 프로세스·core 권장)와 크래시 직전 링버퍼 로그.

Q. "Memory usage of a daemon grows slowly over days. How do you approach it?"

A. 누수라고 단정하지 않고 먼저 측정한다. 현장에서는 /proc/PID/smaps_rollup과 status를 주기적으로 기록해서 무엇이 느는지(익명 힙인지, 파일 매핑인지, 특정 매핑인지)와 증가율을 본다. fd·스레드 수도 같이 본다. 그다음 재현 환경에서 massif나 heaptrack으로 어느 호출 경로의 메모리가 살아남는지 보고, LSan/memcheck로 진짜 누수인지 본다. "still reachable"인 캐시 무한 증가, glibc arena 단편화도 후보다.

I don't assume it's a leak; I measure first. On the device I log smaps_rollup and the status fields every hour, so I know whether it's anonymous heap, file-backed mappings or one specific mapping, and the growth rate. I also track the fd count and the thread count. Then in a lab setup I replay the same workload under massif or heaptrack to see which allocation path keeps memory alive, and under LeakSanitizer or memcheck to see whether it's a true leak. Very often it isn't — it's a cache with no eviction, which memcheck reports only as still reachable, or malloc arena fragmentation, which I can test with MALLOC_ARENA_MAX or malloc_trim. And if I need a snapshot from the field, gcore takes a core without killing the process.

Q. "How does remote debugging with gdbserver work, and what is a sysroot for?"

A. 보드에서는 gdbserver가 ptrace로 대상 프로세스를 조종하고 레지스터·메모리·breakpoint만 다룬다. PC의 gdb가 RSP로 붙어서 심볼·DWARF·unwind를 다 한다. 디버기는 보드의 공유 라이브러리를 쓰므로 gdb도 똑같은 파일이 필요한데, 그 보드 rootfs 사본이 sysroot다. 틀리면 라이브러리 심볼이 어긋나 bt가 깨진다.

On the board, gdbserver controls the process through ptrace and only handles registers, memory, breakpoints and threads, so the board doesn't need symbols or sources. The gdb on my PC connects over the remote serial protocol, usually TCP, and does all the symbol, DWARF and unwinding work. The process uses the board's shared libraries, so gdb has to read exactly the same files; the sysroot is a copy of the board's root filesystem — typically the Yocto SDK sysroot or Buildroot's staging directory. If it's wrong, gdb resolves libc addresses with the wrong library and the backtrace breaks; the default target: sysroot fetches files over the connection, which is correct but slow.

Q. "valgrind or AddressSanitizer — which do you use and why?"

A. 재빌드할 수 있으면 ASan이 기본이다: 2배 남짓 느리고 실제 멀티스레드로 돌고 stack·global 넘침도 잡는다. 대신 메모리를 많이 쓴다(quarantine). valgrind는 재빌드가 안 될 때, 초기화 안 된 값 사용을 찾을 때 쓴다. 10배 이상 느리고 스레드를 직렬화한다. 내가 잰 숫자로는 ASan 2.4배, memcheck 13.6배였다.

If I can rebuild, AddressSanitizer is my default: in my measurement it was about 2.4 times slower, against 13.6 times for memcheck, it runs threads truly in parallel, and it also catches stack and global overflows. Its cost is memory — the default quarantine alone is 256 MB, so on a small board I shrink it. I use valgrind when I can't rebuild, for third-party binaries, or when I'm hunting uninitialised reads, which ASan doesn't detect. For races I use ThreadSanitizer in a separate build, since it can't be combined with ASan.

Q. "What's the overhead of strace and how do you limit it?"

A. ptrace 기반이라 syscall마다 진입·복귀 두 번 멈춘다. 내 측정에서 getppid가 160 ns에서 18~74 µs로, 100배 이상 느려졌다. -e로 걸러도 기본 방식은 모든 syscall에서 멈추니 거의 그대로다. --seccomp-bpf를 쓰면 관심 syscall만 멈춰서 오버헤드가 사라진다. 운영 장비에서는 짧게 붙이거나 perf trace, bpftrace 같은 tracepoint 기반 도구를 쓴다.

strace uses ptrace, so the traced thread stops twice per system call, on entry and exit, and the strace process wakes up each time. I measured a getppid loop going from about 160 nanoseconds per call to 18 to 74 microseconds — more than a hundred times slower. Filtering with -e doesn't help much because it still stops on every syscall; with --seccomp-bpf the kernel's seccomp filter only stops the ones I asked for, and the overhead was gone. On a production device I attach only briefly, or I use tracepoint-based tools like perf trace or bpftrace.

Q. "A process is hung. What do you collect before you kill it?"

A. ps -L로 스레드 상태와 wchan, CPU 사용률(도는지 자는지)을 보고, /proc/PID/task/*/stack으로 커널 스택, gdb -p PID -batch -ex "thread apply all bt"로 유저 스택을 뜬다. 가능하면 gcore로 core를 남긴다. 데드락이면 mutex의 owner 필드로 순환을 증명한다.

First whether it's spinning or sleeping: ps with threads shows each thread's state, CPU and wchan. Then the kernel stacks from /proc/PID/task/*/stack, and the user stacks with gdb attached in batch mode running thread apply all bt — that's the classic pstack. If I can afford a pause I take a gcore so I can keep analysing after a restart. For a deadlock, glibc mutexes record the owner TID, so printing the two mutexes shows the cycle directly — thread A holds the bus lock and waits for the config lock, thread B the other way round.

Q. "How do hardware watchpoints work on ARM, and what are the limits?"

A. 코어의 watchpoint 레지스터(주소 + 제어)에 감시 주소를 넣으면 그 주소 접근 시 debug 예외가 난다. Linux에서는 ptrace regset으로 요청하고 커널이 스레드 전환 때 값을 바꿔 끼운다. 개수가 적고(Cortex-A57은 4개), 하나가 정렬된 8바이트까지만 본다. 넘으면 소프트웨어 watchpoint로 떨어져 매우 느려진다.

The core has a few watchpoint register pairs — an address and a control register with a byte mask and read/write bits. When a matching access happens, the CPU raises a debug exception and the kernel turns it into a SIGTRAP for the debugger. On Linux, gdb sets them through a ptrace regset, and the kernel saves and restores them per thread on context switches. The limits are the count — this Cortex-A57 reported four — and the size: one register covers an aligned doubleword at most. Beyond that gdb has to single-step and compare in software, which is orders of magnitude slower.

16. 요약 & 체크리스트#

유저스페이스 디버깅은 "한 프로세스만 멈추는 JTAG"(ptrace 기반 gdb·gdbserver), "죽은 순간의 덤프"(core), "경계 로그"(strace·ltrace), "계측 실행"(valgrind·sanitizer) 네 가지다. 모든 도구의 전제는 같은 빌드의 debug 정보(build-id로 짝지음)와 같은 라이브러리(sysroot)다 — 틀리면 도구가 거짓말을 한다(예제 3, 12). 원격 디버깅은 보드에 gdbserver와 stripped 바이너리만, PC에 debug 빌드·sysroot·소스를 둔다. core는 PIE 기준 주소를 빼서 오프셋으로 다루고, coredump_filter로 build-id가 core에 남게 한다. strace는 syscall마다 두 번 멈춰 100배 이상 느려지므로 --seccomp-bpf나 짧은 부착으로 쓴다. ltrace는 PLT를 지나는 호출만 본다. ASan은 2.4배·큰 메모리, memcheck는 13.6배·초기화 안 된 값까지, TSan/helgrind는 결과가 맞은 실행에서도 레이스를 보고한다. 현장의 메모리 증가는 /proc/PID/smaps_rollup 기록부터, 멈춘 데몬은 죽이기 전에 모든 스레드의 유저·커널 스택부터.
