0. 큰 그림 — 이게 왜 필요한가#

메모리 버그의 가장 나쁜 성질은 원인과 증상이 시간·공간으로 떨어져 있다는 것이다. 드라이버 A가 버퍼 끝을 4바이트 넘겨 썼다(원인, t0). 그 4바이트는 옆 객체 — 예를 들어 네트워크 스택의 sk_buff 포인터 — 위에 있었다. 몇 초 뒤, 혹은 몇 시간 뒤 네트워크 코드가 그 포인터를 따라가다 Unable to handle kernel paging request로 죽는다(증상, t1). M3에서 배운 Oops 해독을 아무리 잘해도 콜스택은 네트워크 코드를 가리킨다. 범인 드라이버는 스택 어디에도 없다.

Don이 SSD 펌웨어에서 겪었던 "어느 날 FTL 테이블 한 엔트리가 깨져 있다"와 같은 종류다. 그때 했던 일 — 버퍼 앞뒤에 canary를 두고, 해제한 메모리를 0xDEADBEEF로 채우고, MPU로 가드 영역을 만들어 쓰는 순간 abort가 나게 하기 — 을 Linux 커널은 체계적인 도구 모음으로 갖고 있다. 이 노트의 주인공들이다.

그림 1 — 메모리 버그는 원인(t0)과 증상(t1)이 떨어져 있다. 탐지기의 가치는 t1을 t0으로 당겨 오는 것이다.

1. 디버그 커널이라는 물건 — Kernel hacking 메뉴와 랩의 Image-kasan#

탐지기는 전부 Kconfig 옵션이다(E2). make menuconfig의 맨 아래 Kernel hacking 메뉴(lib/Kconfig.debug, lib/Kconfig.kasan, lib/Kconfig.kfence, lib/Kconfig.ubsan, lib/Kconfig.kcsan)에 모여 있고, 대부분 CONFIG_DEBUG_KERNEL=y가 있어야 보인다. 실무에서는 같은 소스로 두 벌의 커널을 만든다: 양산용(탐지기 거의 없음)과 디버그용(아래 옵션 다수). 랩도 그렇게 되어 있다.

1.1 예제 1 — 두 커널의 탐지기 옵션 비교#

무엇을 확인하나: 기준 커널(Image-trace)과 디버그 커널(Image-kasan)이 정확히 어떤 탐지기 옵션에서 다른지.

출력에서 볼 것: 기준 커널에는 SLUB_DEBUG=y(코드만 들어 있고 부팅 인자 slab_debug=로 켬, F9 §9)뿐이다. 디버그 커널은 KASAN generic(inline + 스택 + vmalloc), KFENCE(100 ms, 255 객체), kmemleak(자동 스캔), UBSAN 4종, lockdep(+LOCK_STAT), DEBUG_ATOMIC_SLEEP, DEBUG_OBJECTS(+timer), DEBUG_LIST/SG/PAGEALLOC/VM, SLUB_DEBUG_ON(=slab_debug가 기본 켜짐), DMA_API_DEBUG와 KUnit 테스트 모듈(=m)을 갖는다. 랩 문제 하나: 처음 빌드된 Image-kasan에는 KUnit 테스트 모듈이 빠져 있었다(빌드 스크립트의 KASAN_KUNIT_TEST=m 지정 방식 문제). 랩 관리자가 같은 버전으로 다시 빌드해 위처럼 =m이 들어갔고, 이 노트의 모든 실행은 다시 빌드된 커널(#2)로 했다. 실무에서도 흔한 함정이다 — scripts/config로 넣은 값은 olddefconfig가 의존성 때문에 조용히 지울 수 있으니 빌드 후 .config를 꼭 grep으로 확인한다.

1.2 lockdep — 이미 F4에서 돌려 봤다 (요약)#

lockdep(CONFIG_PROVE_LOCKING)은 F4 §13에서 실제로 돌렸다. 핵심만 다시 정리한다. lockdep은 개별 락이 아니라 락 클래스(같은 spin_lock_init 자리에서 초기화된 락 전부)를 단위로, "A를 쥔 채 B를 잡았다"는 순서 간선과 "이 락은 hardirq 안에서도 쓰인다" 같은 사용 상태를 기록한다. 그래서 실제 deadlock이 한 번도 일어나지 않아도 ABBA 사이클(possible circular locking dependency detected)과 IRQ 상태 불일치(inconsistent {IN-HARDIRQ-W} -> {HARDIRQ-ON-W} usage)를 처음 그 경로를 지나는 순간 보고한다. F4 예제 14(f4_abba)는 두 스레드가 겹치지 않게 돌아도 잡히는 것을, 예제 15는 /proc/lockdep에 쌓인 의존 그래프를 보여 줬다. F2 §10은 같은 디버그 커널에서 DEBUG_ATOMIC_SLEEP(E4 §5)이 "BUG: sleeping function called from invalid context"를 찍는 네 가지 문맥 위반을 다뤘다. 이 노트에서 새로 볼 것은 딱 하나다: lockdep은 첫 보고 뒤 스스로 꺼진다(debug_locks=0). 한 부팅에 한 개의 lockdep 버그만 볼 수 있다는 뜻이고, CI가 "lockdep 경고 0개"를 판정할 때 이 값을 본다.

2. KASAN의 원리 — 컴파일러가 모든 load/store 앞에 검사를 심는다#

2.1 직관 — "주소마다 붙은 접근 허가 비트맵"#

Don이 SSD 펌웨어에서 "이 DRAM 영역은 지금 써도 되나"를 검사하려 했다면 아마 비트맵 하나를 두고, 버퍼를 할당할 때 비트를 켜고 해제할 때 끄고, 모든 접근 전에 비트를 확인했을 것이다. 문제는 "모든 접근 전에"다 — 손으로는 불가능하다. KASAN(Kernel Address SANitizer)은 이걸 컴파일러에게 시킨다. -fsanitize=kernel-address로 빌드하면 gcc/clang이 커널의 모든 load/store 앞에 "이 주소의 허가 비트를 보고, 금지면 리포트 함수를 불러라"는 코드를 끼워 넣는다. 그 허가 비트맵이 shadow memory다.

2.2 정의 — shadow memory 1:8 인코딩 (generic KASAN)#

  • 커널 메모리 8바이트(granule)마다 shadow 1바이트. 그래서 shadow는 커널 주소 공간의 1/8을 차지한다.
  • 주소 → shadow 주소: shadow = (addr >> 3) + KASAN_SHADOW_OFFSET. arm64 48비트 VA·generic에서 KASAN_SHADOW_OFFSET = 0xdfff800000000000(arch/arm64/Kconfig).
  • shadow 값의 뜻: 0x00 = 8바이트 전부 접근 가능, 0x01~0x07 = 앞의 N바이트만 가능(객체 끝이 granule 중간에 있을 때), 음수(최상위 비트 1) = 전부 금지이고 값이 이유를 말한다.

2.4 redzone과 quarantine — "옆을 막고, 해제한 건 바로 돌려주지 않는다"#

shadow 비트맵만으로는 부족하다. 두 객체가 딱 붙어 있으면 A를 넘어 쓴 바이트가 B의 정상 영역이라 shadow가 00이다. 그래서 KASAN은 slab 할당자(SLUB)에 끼어들어 두 가지를 더 한다.

  • redzone: 객체 뒤에 금지 구역을 둔다(shadow fc). kmalloc(13)이면 13~15번 바이트는 granule 부분값(05)으로, 그 뒤는 redzone으로 막힌다. 그래서 kmalloc_oob_right처럼 1바이트만 넘겨도 잡힌다.
  • quarantine(generic 전용): kfree()된 객체를 즉시 free list로 돌려보내지 않고 FIFO 격리 구역에 잠시 둔다. shadow는 fb/fa. 그동안 누가 그 주소를 만지면 use-after-free로 잡힌다. 즉시 재사용되면 UAF 접근이 새 주인의 정상 데이터를 건드리는 것이라 못 잡는다. 격리 구역 크기는 전체 RAM의 1/32(QUARANTINE_FRACTION 32, mm/kasan/quarantine.c) 이고 CPU마다 1 MiB 배치로 비운다.
  • 스택 기록: 할당·해제할 때의 콜스택을 stack depot(중복 제거 저장소)에 넣고 객체 메타데이터에 핸들만 적는다. 리포트에 "Allocated by task …", "Freed by task …"가 나오는 이유다. Don의 펌웨어 경험으로 치면 "버퍼 헤더에 할당자 LR을 적어 두기"를 커널이 자동으로 해 주는 셈이다.

3. KASAN 리포트 읽기 — 업스트림 kasan_test KUnit 스위트로#

3.1 KUnit과 kasan_test#

KUnit은 커널 안에서 도는 단위 테스트 프레임워크다(CONFIG_KUNIT). 테스트 함수 하나가 KUNIT_CASE, 묶음이 suite이고, 결과는 KTAP(TAP 형식) 줄로 dmesg에 찍힌다. mm/kasan/kasan_test_c.c는 KASAN 개발자들이 "KASAN이 이런 버그를 잡는가"를 검증하려고 만든 스위트로, 6.18 기준 75개 케이스가 있다(kmalloc_oob_right, kmalloc_uaf, kasan_stack_oob, kasan_global_oob_right, kmalloc_double_kzfree, vmalloc_oob …). 각 케이스는 KUNIT_EXPECT_KASAN_FAIL(test, 식) 매크로로 "이 식을 실행하면 KASAN 리포트가 나와야 한다"를 검사한다. 즉 리포트가 나오면 ok다. 매크로는 console tracepoint에 probe를 걸어 리포트 문자열이 찍혔는지 본다.

버그를 일으키는 코드를 새로 쓰지 않고 이 스위트를 쓰는 이유는 둘이다. (1) 커널 개발자가 이미 검증한, 정확히 한 종류씩만 버그를 내는 코드다. (2) 실무에서 새 보드·새 컴파일러로 KASAN 커널을 만들면 제일 먼저 이 스위트를 돌려 탐지기가 제대로 붙었는지 확인한다.

4. KFENCE — 양산 커널에 넣을 수 있는 샘플링 탐지기#

4.1 직관 — "가끔 한 개만 MPU 가드 페이지 옆에 놓는다"#

KASAN은 정확하지만 비싸서 양산에 못 쓴다. 그런데 필드에서 1주일에 한 번 나는 메모리 버그는 개발 PC에서는 재현이 안 된다. KFENCE(Kernel Electric-Fence)의 답은 샘플링이다. 100 ms에 한 번(기본값, CONFIG_KFENCE_SAMPLE_INTERVAL=100) 다음 slab 할당 하나를 특별한 풀에 놓는다. 그 풀은 "객체 페이지 하나 + 접근 금지 guard 페이지 하나"가 번갈아 놓인 구조라, 그 객체를 넘어 쓰면 MMU가 page fault를 낸다. 검사 코드가 없으니 나머지 99.99% 할당은 비용이 0이다. Don이 MPU 영역 하나를 "버퍼 바로 뒤 접근 금지"로 설정해 두고 범인을 기다리던 것과 똑같다. 차이는 수천 대의 기기가 동시에 기다린다는 것 — 한 대에서는 확률이 낮아도 함대 전체로는 버그가 결국 샘플에 걸린다.

4.2 정의#

  • 풀 크기: CONFIG_KFENCE_NUM_OBJECTS=255개 객체. 객체마다 페이지 하나 + guard 페이지 → (255 + 1) × 2 × 4 KiB = 2 MiB를 부팅 때 예약한다.
  • 객체 배치: 페이지 안에서 오른쪽 끝 또는 왼쪽 끝에 무작위로 붙인다. 오른쪽 끝이면 오른쪽 OOB가 guard 페이지 fault로 즉시 잡힌다. 왼쪽 끝이면 왼쪽 OOB가 즉시 잡힌다. 반대쪽 남는 공간은 canary 바이트로 채워 두고 kfree() 때 검사한다("memory corruption" 리포트).
  • 해제된 KFENCE 객체의 페이지는 접근 금지로 바뀐다 → UAF가 page fault로 잡힌다.
  • 잡는 것: OOB(read/write), UAF, invalid free, double free, 객체 옆 canary 손상. 리포트 제목은 BUG: KFENCE: out-of-bounds read in …, BUG: KFENCE: use-after-free write in …, BUG: KFENCE: memory corruption in …, BUG: KFENCE: invalid free in ….
  • 제어: 부팅 인자 kfence.sample_interval=<ms>(0이면 끔), 런타임 /sys/module/kfence/parameters/sample_interval, 상태 /sys/kernel/debug/kfence/stats·objects.

그림 4 — KFENCE는 할당 일부만 guard 페이지 사이에 놓는다. 검사는 MMU가 하므로 계측 비용이 없다.

  • canary 리포트의 [ 0x2a . . . ]는 손상된 바이트만 값으로, 멀쩡한 canary 바이트는 .로 보여 준다. 객체 끝(…401f) 바로 다음 …4020이 0x2a로 덮였다. 여기서는 해제 스택 = 리포트 스택이다 — 검사가 kfree 안에서 일어났기 때문이다. 즉 범인은 할당과 해제 사이 어딘가이고, KASAN처럼 범인 명령을 짚지는 못한다. KFENCE의 정밀도 한계다.
  • KASAN 리포트와 달리 shadow 덤프가 없고 "kfence-#번호"(풀 슬롯)와 시간 정보(at 19.69s (0.0012s ago), 할당 후 얼마 뒤 깨졌나)가 나온다.
  • 이 실험은 KASAN도 켜진 커널에서 했다. KASAN 훅은 KFENCE 주소를 건너뛰므로(mm/kasan/common.c의 is_kfence_address() 검사) 두 탐지기의 리포트가 겹치지 않았다. 양산에서는 KFENCE만 켠다.

5. kmemleak — 커널용 "참조 없는 객체" 탐지 (GC의 mark 단계만)#

5.1 직관과 정의#

kmemleak은 garbage collector의 mark 단계만 하는 도구다. 모든 kmalloc/vmalloc/alloc_percpu 등 할당을 rbtree에 기록해 두고, 스캔할 때 루트(데이터·bss 섹션, 각 태스크 커널 스택, per-CPU 영역)와 이미 도달한 객체의 메모리를 8바이트씩 훑으며 "이 값이 어떤 할당 객체의 주소 범위 안을 가리키는가"를 본다. 끝까지 아무도 가리키지 않는 객체(5초 이상 된 것, MSECS_MIN_AGE 5000)를 unreferenced object로 보고한다. 즉 "포인터를 잃어버린 메모리"를 찾는다.

  • 자동 스캔: CONFIG_DEBUG_KMEMLEAK_AUTO_SCAN=y면 부팅 60초 뒤(SECS_FIRST_SCAN 60) 첫 스캔, 이후 10분마다(SECS_SCAN_WAIT 600).
  • 수동: echo scan > /sys/kernel/debug/kmemleak 후 cat /sys/kernel/debug/kmemleak. echo clear > …는 지금까지의 의심 목록을 "보고 완료"로 지운다(새 누수만 보려고 쓴다).
  • 한계: 보수적이라 오탐·미탐이 있다. 포인터를 XOR하거나 하위 비트를 태그로 쓰거나, 물리 주소로만 들고 있으면(DMA 디스크립터) 누수로 오탐한다 → kmemleak_not_leak(), kmemleak_ignore()로 알려 준다. 반대로 우연히 그 주소 값을 가진 정수가 있으면 미탐한다. 그래서 "의심 목록"으로 읽는다.

5.2 예제 11 — 업스트림 samples/kmemleak/kmemleak-test.c#

이 샘플 모듈(업스트림 테스트 모듈, samples/kmemleak/kmemleak-test.c)은 랩 커널 빌드에 포함되지 않아서, 소스 파일을 수정 없이 /var/tmp/M8/kmemleak/에 복사하고 한 줄짜리 Kbuild로 linux-build-kasan에 대해 out-of-tree 빌드했다. 모듈이 하는 일은 module_init에서 kmalloc(32)×2, kmalloc(1024/2048/4096)×2씩, vmalloc(64)×5를 받아 포인터를 버리고(주소만 출력), kzalloc한 노드 10개를 모듈 전역 리스트에 걸고, per-CPU 변수에 kmalloc(129)를 넣고, __alloc_percpu(64, 4)를 버리는 것이다. module_exit은 리스트에서 노드를 떼기만 하고 해제하지 않는다.

  • 리스트 노드 10개는 rmmod 전에는 누수가 아니다 — 모듈 전역 test_list(모듈 .data는 스캔 루트)가 가리키고 있으니까. 소스 주석도 "They should only appear as orphan after the module is removed"라고 적는다(이 노트에서는 rmmod 전 스캔은 따로 하지 않았다). 이게 kmemleak의 "도달 가능성" 정의다.

6. UBSAN — C의 미정의 동작을 런타임에 잡기#

6.1 직관과 정의#

C 표준은 signed overflow, 배열 범위 밖 인덱스, 폭 이상 shift, 0 나눗셈, 잘못된 bool/enum 값 읽기, 정렬 위반 등을 미정의 동작(UB) 으로 둔다. 컴파일러는 "UB는 일어나지 않는다"고 가정하고 최적화하므로, 버그가 있으면 엉뚱한 코드가 생성된다(예: 범위 검사가 통째로 지워짐). UBSAN(-fsanitize=bounds,shift,…)은 해당 연산 앞에 검사를 넣고 위반이면 __ubsan_handle_*()를 불러 리포트를 찍는다. KASAN과 달리 메모리 상태를 추적하지 않는다 — 그래서 싸다. 특히 UBSAN_BOUNDS는 배열 크기를 컴파일러가 아는 경우(구조체 안 고정 배열, __counted_by 붙은 flexible array)에만 동작하는 매우 싼 검사라, 일부 배포판·Android 커널은 양산에도 켠다(UBSAN_TRAP으로 리포트 대신 trap 명령을 넣으면 코드도 작아진다).

6.2 예제 12 — 업스트림 lib/test_ubsan.c#

무엇을 확인하나: 이 커널에서 켜진 UBSAN 검사(shift, bounds, bool, enum)가 실제로 무엇을 잡고 무엇을 지나치는지. 업스트림 테스트 모듈 lib/test_ubsan.c(랩 빌드의 kernel/lib/test_ubsan.ko)는 module_init에서 UB 함수 9개를 차례로 부르고, 각 함수 앞에 "해당 Kconfig가 켜졌는지"를 한 줄 찍는다(UBSAN_TEST() 매크로). 0 나누기 테스트는 모듈을 Oops시키므로 업스트림이 일부러 빼 두었다(skip_ubsan_array).

출력에서 볼 것:

  • 리포트 4개: 음수 shift, 배열 int [4]의 인덱스 4와 -1, _Bool에 255 load. 각 리포트 첫 줄이 파일:줄:열까지 준다 — KASAN과 달리 faddr2line이 필요 없다(컴파일러가 위치 정보를 데이터로 넣어 둔다). 리포트 형식은 WARN()과 같은 cut here … end trace 블록이다.
  • INTEGER_WRAP=n 다섯 줄은 검사 자체가 없어서 조용히 지나간다(6.15+의 UBSAN_INTEGER_WRAP은 clang 전용, 이 커널은 gcc 빌드).
  • left overflow(INT_MAX << 4)는 UBSAN_SHIFT=y인데도 리포트가 없다. 커널은 최상위 Makefile에서 -fno-strict-overflow로 빌드되고, gcc에서 이 옵션은 signed overflow를 wrap으로 정의하는 -fwrapv를 포함한다. 그래서 커널 C에서 signed left shift overflow는 UB가 아니게 되어 검사가 빠진 것으로 보인다. 음수 shift 같은 진짜 UB만 남는다.
  • enum도 UBSAN_ENUM=y인데 리포트가 없다. 이 gcc 15 빌드에서는 C 코드의 enum load 검사가 나오지 않았다(원인은 확인하지 않았다 — 컴파일러마다 C enum 검사 지원이 다르다). "켰다 = 잡는다"가 아니라는 좋은 예다. 테스트 모듈이 (CONFIG_X=y)를 찍어 주는 이유가 이것이다: 켜졌는데 리포트가 없으면 컴파일러 쪽 한계다.
  • Not tainted: UBSAN 리포트는 taint를 남기지 않는다(KASAN은 B). 그래서 lockdep도 꺼지지 않는다. 대신 panic_on_warn=1이면 첫 리포트에서 panic한다.

7. KCSAN — 데이터 레이스 탐지기 (가이드)#

7.1 직관 — "watchpoint를 걸고 잠깐 기다린다"#

F4에서 본 int++ 레이스는 lockdep이 못 잡는다(락을 안 썼으니까). KCSAN(Kernel Concurrency SANitizer)은 컴파일러 계측(-fsanitize=thread)으로 모든 메모리 접근 앞에 훅을 넣고, 가끔(기본 약 4000번 접근마다 한 번, CONFIG_KCSAN_SKIP_WATCH=4000) 그 접근 주소에 소프트웨어 watchpoint를 건 뒤 잠깐(태스크 문맥 기본 80 us, KCSAN_UDELAY_TASK) 지연한다. 그 사이 다른 CPU가 같은 주소를 만지면(둘 중 하나가 write이고, 둘 다 marked atomic 접근이 아니면) data race로 보고한다. 지연 전후 값이 바뀌었는지도 본다(watchpoint에 안 걸린 쓰기, "value changed"). Don의 경험으로는 JTAG data watchpoint를 랜덤한 주소에 계속 걸었다 풀었다 하는 것이다.

7.2 리포트 모양 (가이드 — 이 랩에서 실행 안 함)#

KCSAN은 KASAN과 같이 켤 수 없다(lib/Kconfig.kcsan: depends on … !KASAN). 랩 Image-kasan에는 없고, 쓰려면 trace 설정에서 KASAN 계열을 빼고 CONFIG_KCSAN=y, CONFIG_KCSAN_KUNIT_TEST=m으로 별도 커널을 빌드해야 한다(-j2에서 TCG VM 기준 1시간 이상이라 이 노트에서는 하지 않았다). 업스트림 kernel/kcsan/kcsan_test.c KUnit 스위트(test_basic, test_concurrent_races, test_novalue_change, test_write_write_assume_atomic 등)가 KCSAN 자체를 검증한다. 리포트 형식은 Documentation/dev-tools/kcsan.rst 예시와 같다:

  • DMA_API_DEBUG: 매핑 기록용 엔트리 65536개를 미리 잡아 두었고 아직 하나도 안 썼다(num_free_entries = min_free_entries = 65536) — virtio 장치는 DMA API를 쓰지만 이 게스트에서는 블록 장치 없이 initramfs로 부팅해 매핑이 거의 없었다. error_count: 0이 위반 개수다. 헷갈리기 쉬운 것은 num_errors: 1인데, 이건 위반 개수가 아니라 "앞으로 dmesg에 자세히 찍을 남은 횟수"다(show_num_errors, 기본 1, 하나 찍을 때마다 1씩 준다, kernel/dma/debug.c). all_errors에 1을 쓰면 전부 찍는다. (ls 출력의 색 코드는 지웠다.) driver_filter에 드라이버 이름을 쓰면 그 드라이버의 매핑만 검사한다 — 큰 시스템에서 내 드라이버만 보고 싶을 때 쓴다.
  • 부팅 인자로 끄는 법: debug_objects는 no_debug_objects, DMA API 검사는 dma_debug=off, KFENCE는 kfence.sample_interval=0, kmemleak은 kmemleak=off, slab_debug는 slab_debug=-. 같은 디버그 커널로 "어느 탐지기가 비용을 먹나"를 나눠 볼 때 쓴다(§10).

9. 무엇이 무엇을 잡나 — 탐지기 커버리지 지도#

그림 5 — 탐지기 커버리지. KFENCE의 범위 초과·UAF는 "샘플에 걸린 객체만"(◐), slab_debug는 "다음 검사 시점에, 쓰기만", UBSAN은 "크기를 아는 배열만", DEBUG_OBJECTS는 "timer·work가 활성인 채 해제" 같은 수명 위반, DMA_API_DEBUG는 "map/unmap 짝 불일치·unmap 누락"을 잡는다. 한 도구로 다 되지 않으니 조합한다.

읽는 법: 메모리 손상(왼쪽 세 열)은 KASAN이 가장 정확하고, 양산에서는 KFENCE·MTE가 그 자리를 대신한다. 레이스는 KCSAN뿐이고, 락 순서는 lockdep뿐이다. 누수는 kmemleak뿐이다.

11.2 양산 질문에 답하기#

  • KASAN generic을 양산에? 아니다. 메모리 1/8(+quarantine 1/32) 상시 사용, 이미지가 커지고, 커널 경로가 수 배 느리다(§10 실측). 개발·CI 전용.
  • KFENCE를 양산에? 그렇다 — 설계 목표가 그것이다. 2 MiB 풀과 타이머 하나, fast path는 static key 분기뿐이다. 커널 문서(Documentation/dev-tools/kfence.rst)도 "양산 커널에 켜도록 설계됐고 오버헤드가 거의 0"이며, 충분한 총 가동 시간을 얻는 빠른 방법이 "large fleet of machines"에 배포하는 것이라고 적는다. 단, 한 대에서는 확률이 낮으므로 리포트 수집 체계(pstore·로그 업로드)가 짝이다.
  • MTE(KASAN HW_TAGS)를 양산에? 칩이 MTE를 지원하면(ARMv8.5+, 예: Pixel 8 이후 Tensor) async 또는 asymm 모드로 가능하다. 태그 저장용 메모리(태그 3% 정도, HW가 별도 저장)와 태그 설정 비용이 있다. 임베디드 SoC(i.MX8·AM62·Orin의 Cortex-A53/A72/A78AE)는 MTE가 없다 — 그런 보드에서는 KFENCE가 현실적인 선택이다.
  • UBSAN을 양산에? UBSAN_BOUNDS+UBSAN_TRAP 정도는 일부 배포판·Android가 켠다. 전체 UBSAN은 개발용.

12. 커널 안에서는 무슨 일이 일어나나#

KASAN generic 리포트가 나오기까지의 경로를 6.18 소스로 따라가 보자. 예제의 리포트 스택에 나온 함수 이름이 전부 이 경로 위에 있다.

그림 8 — KASAN generic의 생애주기. 할당자 훅이 shadow를 칠하고, 컴파일러가 심은 검사가 읽고, kasan_report()가 리포트를 조립한다.

  • 할당자 훅: mm/slub.c의 할당·해제 경로에서 kasan_slab_alloc()·kasan_kmalloc()·kasan_slab_free()(include/linux/kasan.h 래퍼 → mm/kasan/common.c)가 불린다. 페이지 할당자는 kasan_unpoison_pages()/kasan_poison_pages(), vmalloc은 KASAN_VMALLOC일 때 kasan_populate_vmalloc()로 shadow 자체를 그때그때 매핑한다.
  • 스택 저장: kasan_save_stack() → stack_depot_save()(lib/stackdepot.c). 같은 스택은 한 번만 저장되고 객체에는 4바이트 핸들만 들어간다.
  • 리포트: kasan_report() → print_report()가 print_error_description()(bug 종류) → 접근 스택 → print_address_description()(alloc/free 스택, 객체 위치 "located 0 bytes to the right of allocated 123-byte region") → print_memory_metadata()(shadow 덤프)를 찍는다. 출력이 끝나면 end_report()가 add_taint(TAINT_BAD_PAGE, LOCKDEP_NOW_UNRELIABLE)를 불러 이후 Oops에 taint 문자 B가 붙는다. 두 번째 인자 때문에 KASAN 리포트가 한 번 나면 lockdep도 꺼진다 — 한 부팅에서 KASAN 버그를 먼저 고쳐야 lockdep 결과를 믿을 수 있다.
  • 계측 제외: 부팅 초기 코드·KASAN 자신 등은 Makefile의 KASAN_SANITIZE_foo.o := n으로 빠진다. 드라이버 하나만 계측하고 싶으면 반대로 KASAN_SANITIZE := y를 그 Makefile에 두는 식도 가능하다.
  • 드라이버 작성과 다시 만나는 곳: kmalloc/kfree(F9), dma_map_*(H 모듈, DMA_API_DEBUG), timer_setup/INIT_WORK(F7·F8, DEBUG_OBJECTS), list_head(E5, DEBUG_LIST), 스핀락·뮤텍스(F4, lockdep). 탐지기가 감시하는 API가 곧 드라이버가 매일 쓰는 API다.

13. Embedded 실무에서 다시 보기#

13.1 "필드에서 1주일에 한 번 패닉" — 센서 키트 사례#

예를 들어 센서 키트의 IMU SPI 드라이버가 FIFO를 읽을 때 장치가 보고한 샘플 수를 그대로 믿고 memcpy(buf, rx, n * 12)를 한다고 하자. 평소 n ≤ 32지만 SPI 노이즈로 FIFO count 레지스터가 가끔 0x3FF로 읽히면 384바이트 버퍼 뒤를 덮어쓴다. 증상은 몇 시간 뒤 네트워크 스택 Oops다. 접근 순서:

  1. Oops 콜스택에 범인이 없음 → 메모리 손상 의심(M3).
  2. 같은 소스로 KASAN 커널을 만들어 같은 보드(또는 QEMU + 장치 모델)에서 스트레스 테스트. KASAN은 memcpy 순간 slab-out-of-bounds in imu_read_fifo를 찍는다(kasan_check_range()).
  3. 재현이 안 되면 필드 커널에 KFENCE(이미 켜 두는 게 좋다) + pstore. 수백 대가 돌면 언젠가 그 384바이트 버퍼가 샘플에 걸려 BUG: KFENCE: out-of-bounds write in imu_read_fifo가 수집된다.
  4. 고친 뒤 회귀 방지: FIFO count 범위 검사 + UBSAN_BOUNDS가 볼 수 있게 버퍼를 struct { u8 buf[384]; } 고정 배열로.

13.2 드라이버 remove()에서의 timer·work 정리#

DEBUG_OBJECTS는 "timer가 아직 활성인데 그것을 품은 구조체를 kfree"를 ODEBUG: free active … object type: timer_list로 잡는다. 실기에서는 그 timer가 나중에 해제된 메모리 위에서 발화해 가끔 패닉이 난다. remove()에서 timer_delete_sync()(예전 이름 del_timer_sync()는 6.18에서 이미 없다)·cancel_work_sync()를 빠뜨린 전형적인 버그다(F7·F8, G3).

13.3 DMA 버퍼 짝#

카메라·LiDAR 드라이버(I 모듈)가 에러 경로에서 dma_unmap_single()을 빼먹거나, map은 DMA_FROM_DEVICE로 하고 unmap은 DMA_TO_DEVICE로 하는 버그는 x86 개발 PC(캐시 일관)에서는 증상이 없고 Cortex-A 보드에서만 가끔 데이터가 틀린다. DMA_API_DEBUG는 개발 PC에서도 규칙 위반 자체를 찍어 준다.

13.4 BSP 커널 업그레이드 검증#

벤더 BSP를 새 LTS로 올릴 때 첫 일은 디버그 config로 부팅해 dmesg를 0으로 만드는 것이다. 벤더 드라이버의 lockdep·DEBUG_OBJECTS·KASAN 경고가 수십 개 나오는 일이 흔하다. 이 노트의 kasan_test처럼 KUnit 스위트를 먼저 돌려 "탐지기 자체가 이 SoC·컴파일러에서 정상 동작"하는지 확인한 뒤, 드라이버 경고를 하나씩 없앤다.

15. 면접에서 이렇게 말한다#

Q. "We have intermittent memory corruption in a driver — crashes show up in unrelated code once a week. How do you find it?"

A. 콜스택이 무관한 코드를 가리키면 원인과 증상이 떨어진 메모리 손상이다. 같은 소스로 KASAN generic 커널을 만들어 스트레스·퍼징을 돌리면 손상을 일으키는 바로 그 명령에서 리포트가 나오고, 할당·해제 스택까지 준다. 재현이 안 되면 필드 커널에 KFENCE와 pstore를 켜서 함대에서 샘플로 잡는다. 범위를 좁히는 보조 도구는 slab_debug, DEBUG_OBJECTS(timer/work 수명), DMA_API_DEBUG(DMA 짝)다.

When the crash stack points at unrelated code, it's corruption with cause and symptom separated in time. First I build the same tree with generic KASAN and stress the driver — KASAN reports at the faulting instruction with the allocation and free stacks, so the culprit line is right there. If it won't reproduce in the lab, I rely on KFENCE plus pstore in the field kernel; it's cheap enough to leave on, and across a fleet the bad object eventually gets sampled. Around that I use DEBUG_OBJECTS for timer and work lifetime bugs and DMA_API_DEBUG for map/unmap mismatches, and I gate CI on a clean dmesg.

꼬리 질문: "KASAN이 아무것도 못 찾으면?" → DMA가 쓰는 메모리는 CPU 계측 밖이다(장치가 직접 씀) — DMA_API_DEBUG, IOMMU fault 로그, 버퍼 끝 canary를 보고, 레이스면 KCSAN.

Q. "Can you ship KASAN in production? What about KFENCE and MTE?"

A. generic KASAN은 메모리 1/8 + quarantine, 수 배 느린 커널 경로 때문에 양산 불가다(이 노트의 실측도 그렇다). KFENCE는 양산용으로 설계됐다 — 2 MiB 풀과 샘플링 타이머만 쓰고 fast path 비용이 사실상 0이다. MTE(HW_TAGS)는 ARMv8.5 MTE가 있는 칩에서 async/asymm 모드로 양산 가능한 수준이지만, 대부분의 임베디드 SoC 코어(A53/A72/A78AE)는 MTE가 없다.

Generic KASAN, no — it reserves an eighth of memory for shadow plus a quarantine, and kernel paths run several times slower. KFENCE, yes — that's its design goal: a small guarded pool and a sampling timer, near-zero fast-path cost, and fleet scale makes up for the low per-device probability. MTE-backed KASAN can run in production in async or asymmetric mode, but only on ARMv8.5+ cores with MTE; most embedded SoCs today, like Cortex-A53 or A78AE parts, don't have it, so KFENCE is the realistic choice there.

Q. "How does KASAN know an access is bad?"

A. 컴파일러가 모든 load/store 앞에 shadow 검사를 심는다. 8바이트마다 shadow 1바이트가 있고 0이면 전부 유효, 1~7이면 앞 N바이트만 유효, 음수면 금지이며 값이 이유(redzone, freed 등)다. 할당자가 할당 때 shadow를 풀고, 해제 때 칠하고 객체를 quarantine에 넣어 재사용을 늦춘다.

The compiler instruments every load and store with a shadow check. Each 8-byte granule has one shadow byte: zero means fully addressable, 1 to 7 means only the first N bytes are, and negative values mean poisoned, with the value encoding why — slab redzone, freed object, stack redzone. The allocator unpoisons on allocation, poisons on free and holds freed objects in a quarantine so use-after-free doesn't land on a reused object.

Q. "What's the difference between lockdep and KCSAN?"

A. lockdep은 락을 쓴 코드의 순서·문맥 규칙을 검증한다 — 실제 deadlock 없이도 ABBA 가능성을 증명한다. KCSAN은 락을 안 쓴(또는 잘못 안 쓴) 접근의 데이터 레이스를 watchpoint 샘플링으로 찾는다. 하나는 정적 그래프, 하나는 동적 관찰이다.

Lockdep validates code that does take locks: it builds a graph of lock-class ordering and IRQ usage and reports a possible deadlock the first time an inconsistent path runs, even if it never actually deadlocks. KCSAN looks for the opposite problem — plain concurrent accesses with no proper synchronization — by setting sampled watchpoints and catching a conflicting access from another CPU. Different bug classes, and you can't build KCSAN together with KASAN.

Q. "How do you read a KASAN report?"

A. 위에서부터: 버그 종류와 함수(slab-out-of-bounds in foo+0x..), 접근 크기·주소·태스크, 접근 콜스택(범인), Allocated by / Freed by 스택, "located N bytes to the right of M-byte region"(얼마나 넘었나), 마지막 shadow 덤프(fc·fb 등으로 무엇을 건드렸나). 함수+오프셋은 faddr2line/decode_stacktrace.sh로 줄 번호로 바꾼다(M3).

Top down: the bug type and function, the access size and address, the access stack — that's where the bad code is — then the allocation and free stacks, then the object description that says how many bytes past which region, and finally the shadow dump where values like fc or fb tell me whether I hit a redzone or freed memory. I run the stack through decode_stacktrace or faddr2line to get source lines.

Q. "What would you put in a CI pipeline for kernel drivers?"

A. 같은 소스로 디버그 커널(KASAN+UBSAN+lockdep+DEBUG_OBJECTS+DMA_API_DEBUG+kmemleak)을 빌드하고 QEMU나 실기에서 KUnit·kselftest·드라이버 테스트를 돌린 뒤, 테스트 결과와 별개로 dmesg에 탐지기 패턴이 있으면 실패시킨다. lockdep이 꺼졌는지(debug_locks)도 본다. 별도 잡으로 KCSAN 커널, 가능하면 syzkaller.

A debug-config build of the same tree — KASAN, UBSAN, lockdep, DEBUG_OBJECTS, DMA_API_DEBUG, kmemleak — booted in QEMU or on a board, running KUnit, kselftests and our driver tests. Pass/fail isn't just the test result: I grep dmesg for any detector report and fail on a single hit, check that debug_locks is still 1, and run a kmemleak scan at the end. A separate job runs a KCSAN kernel, and syzkaller if we expose ioctls.

Q. "Why didn't slab_debug catch my overflow but KASAN did?"

A. slab_debug는 redzone을 나중에(해제·검증 시점) 확인하는 사후 검사이고 쓰기만 본다. 읽기 OOB나 UAF 읽기는 못 잡고, 잡아도 "언제"를 모른다. KASAN은 모든 접근에서 즉시 검사한다. 대신 slab_debug는 재컴파일 없이 부팅 인자로 켤 수 있다(F9 §9).

slab_debug checks red zones and poison after the fact, at free or validation time, so it only sees writes and can't tell you when it happened; it also misses out-of-bounds reads. KASAN checks every access as it happens. The upside of slab_debug is that it's a boot parameter on any SLUB_DEBUG kernel, no rebuild needed.

16. 직접 해보기#

  1. (개념) kmalloc(100)을 받은 뒤 p[100]과 p[104]와 p[128]에 쓰면 generic KASAN의 shadow는 각각 무엇이고, 셋 다 잡히나? — 정답/힌트: 100 = 12×8 + 4라 13번째 granule shadow는 04, p[100]·p[104]는 그 granule 밖이거나 부분값 위반으로 잡히고, p[128]은 kmalloc-128 칸 뒤 redzone(fc)이라 잡힌다(kmalloc_oob_right 테스트와 같은 구조).
  2. (관찰) kasan_test를 kasan.fault=panic으로 다시 돌려 첫 리포트에서 패닉하는지 확인하라. — 정답/힌트: 부팅 인자 추가, 첫 BUG: KASAN 직후 Kernel panic - not syncing: kasan.fault=panic set ....
  3. (관찰) kfence.sample_interval=1로 부팅한 뒤 /sys/kernel/debug/kfence/stats의 total allocations가 기본(100 ms)보다 얼마나 빨리 느는지 비교하라. — 정답/힌트: 약 100배 빠르게 풀이 돈다. 풀이 꽉 차면 skipped allocations (capacity)가 는다.
  4. (코드) §11.1 게이트 스크립트를 kmemleak "새 항목만" 판정하도록 고쳐라(부팅 직후 clear, 테스트 후 scan). — 정답/힌트: 테스트 전에 echo clear > /sys/kernel/debug/kmemleak, 후에 echo scan을 두 번(오탐 줄이기) 하고 unreferenced object 개수 판정.
  5. (개념) KFENCE 객체가 페이지 오른쪽 끝에 붙어 있을 때 왼쪽 1바이트 OOB 쓰기는 언제 어떻게 발견되나? — 정답/힌트: guard 페이지가 아니라 canary 위라 즉시 fault는 없고, kfree() 때 canary 검사로 BUG: KFENCE: memory corruption이 난다.
  6. (관찰) Image-kasan에서 /proc/lockdep_stats의 lock-classes를 부팅 직후와 kasan_test 후 비교하라. — 정답/힌트: 새 코드 경로가 돌면 클래스·간선이 는다. 상한(MAX_LOCKDEP_KEYS 8192)에 닿으면 lockdep이 스스로 꺼진다.
  7. (빌드) trace config에서 KASAN 계열을 빼고 CONFIG_KCSAN=y, CONFIG_KCSAN_KUNIT_TEST=m으로 O=/var/tmp/<ID>/kcsan 커널을 빌드해 kcsan_test를 돌려 보라. — 정답/힌트: scripts/config -d KASAN -e KCSAN -e KCSAN_KUNIT_TEST=m 후 olddefconfig, arm64는 EXPERT=y가 필요(HAVE_ARCH_KCSAN if EXPERT).

18. 요약 & 체크리스트#

메모리·동시성 버그는 원인과 증상이 떨어져 있어서 Oops 스택만으로는 범인을 못 찾는다. Linux는 이걸 "원인 시점"으로 당겨 오는 탐지기를 Kconfig로 제공한다. KASAN generic은 컴파일러가 모든 접근 앞에 1:8 shadow 검사를 심고 할당자가 redzone·quarantine·스택 기록을 더해 OOB·UAF를 그 명령에서 잡지만, 메모리·속도 비용이 커서 개발·CI 전용이다. KFENCE는 guard 페이지와 샘플링으로 비용을 거의 0으로 만들어 양산에 켜고, MTE가 있는 칩이면 HW_TAGS KASAN이 그 중간이다. kmemleak은 도달 불가 객체를, UBSAN은 C 미정의 동작을, KCSAN은 data race를(별도 커널), lockdep은 락 순서를(F4), DEBUG_OBJECTS·DEBUG_LIST·DMA_API_DEBUG는 API 사용 규칙을 지킨다. 실무 전략은 "개발 커널은 다 켜고, CI는 dmesg 0개를 게이트로, 양산은 공짜에 가까운 것만 + 리포트 수집"이다.
