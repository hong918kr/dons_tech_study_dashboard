0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어를 할 때 "가끔 커맨드 하나가 늦게 끝난다"를 어떻게 잡았는지 떠올려 보자. 아마 이런 것들을 썼을 것이다.

  • 펌웨어 안의 trace 링버퍼: 이벤트 ID + 타임스탬프(사이클 카운터) + 인자 몇 개를 RAM 링버퍼에 쌓고, 문제가 나면 JTAG으로 덤프한다. 링버퍼라서 오래된 것은 덮어쓴다. printf는 너무 느려서 못 쓴다.
  • ARM CoreSight ETM/ITM: 하드웨어가 명령어 흐름을 뽑아 준다. 코드 수정 없이 "어느 함수를 언제" 볼 수 있다.
  • 로직 분석기 + GPIO 토글: 구간 시작/끝에 핀을 올리고 내려서 실제 시간을 잰다.

ftrace는 이 세 가지를 Linux 커널 안에 소프트웨어로 넣어 둔 것이다.

  • per-CPU ring buffer에 타임스탬프 찍힌 레코드를 lock 없이 쌓는다 (펌웨어 trace 링버퍼와 같은 발상).
  • function tracer: 커널의 거의 모든 함수 입구에 컴파일러가 NOP 자리를 만들어 두었다가, 켤 때만 그 NOP을 BL ftrace_caller로 고쳐 쓴다 (ETM처럼 "코드 수정 없이 함수 흐름 보기"를 소프트웨어로).
  • tracepoint(event): 커널 개발자가 중요한 지점(sched_switch, irq_handler_entry, kmalloc …)에 미리 박아 둔 이벤트. 펌웨어의 "trace ID 찍는 매크로"와 같다.
  • kprobe/uprobe: 실행 중에 아무 함수(커널·유저)에나 이벤트를 붙인다. 디버거의 breakpoint를 "멈추지 않고 기록만" 하는 버전이다.
  • latency tracer(irqsoff, preemptoff, wakeup_rt): "IRQ가 꺼져 있던 가장 긴 구간"처럼 최악값 하나를 자동으로 잡아 그 구간의 함수 흐름을 보관한다. 로직 분석기의 "pulse width > N 트리거"와 같은 역할이다.
  • 이 모든 것을 파일 시스템(tracefs, /sys/kernel/tracing)의 파일에 echo/cat 하는 것으로 제어한다. 별도 도구가 없어도 BusyBox 셸만 있으면 된다. trace-cmd는 그 위의 편한 CLI, KernelShark는 GUI 뷰어다.

그림 1 — ftrace의 구조. 여러 종류의 hook이 같은 per-CPU ring buffer에 기록하고, 사람은 tracefs 파일이나 trace-cmd로 꺼내 본다. hist 트리거는 버퍼에 쓰지 않고 커널 안에서 바로 집계한다.

이름 정리부터 하자. 좁은 뜻의 ftrace는 "function tracer"이지만, 실무에서는 tracefs 아래의 추적 프레임워크 전체(tracer + event + 동적 probe + ring buffer)를 ftrace라고 부른다. perf(M6)와 eBPF(M7)도 같은 tracepoint·kprobe를 쓰지만 데이터를 다른 길로 뽑는다. 이 노트는 tracefs 쪽만 다룬다. osnoise/timerlat/hwlat tracer와 rtla는 N3에서 다룬다.

1. tracefs 한 바퀴 — 파일이 곧 API#

1.1 어디에 있나#

tracefs는 /sys/kernel/tracing에 mount 된다. systemd 시스템은 자동으로 mount 하고, BusyBox initramfs에서는 직접 해야 한다(mount -t tracefs nodev /sys/kernel/tracing). 옛 경로 /sys/kernel/debug/tracing도 debugfs를 mount 하면 자동으로 보이지만, 새 코드는 /sys/kernel/tracing을 쓴다(debugfs 없이 tracefs만 켤 수 있어서 보안상 낫다).

2. 꺼져 있을 때 오버헤드가 거의 0인 이유 — dynamic ftrace#

2.1 직관 — "모든 함수 앞에 빈 칸을 남겨 둔다"#

함수 7만 개 각각에 "추적 코드"를 넣어 두면 느려진다. 그렇다고 빼 두면 필요할 때 커널을 다시 빌드해야 한다. ftrace의 답은 컴파일러에게 모든 함수 입구에 NOP 명령 자리를 만들게 하고, 실행 중에 그 NOP을 call 명령으로 고쳐 쓰는 것이다.

  • 꺼져 있을 때: 함수마다 NOP 몇 개. CPU는 NOP을 거의 공짜로 흘려보낸다(디코드만 하고 실행 유닛을 거의 안 쓴다). 그래서 "near-zero overhead".
  • 켤 때: 고르고 싶은 함수의 NOP만 BL ftrace_caller로 바꾼다. 필터에 없는 함수는 계속 NOP이다.

펌웨어 비유: 플래시에 있는 코드에 "패치 슬롯"을 미리 비워 두고, 필드에서 디버그가 필요하면 그 슬롯에 branch를 써 넣는 ROM patch 기법과 같다. 다른 점은 Linux 커널 텍스트는 RAM에 있어서 커널이 스스로 고칠 수 있다는 것뿐이다.

2.2 역사 — mcount에서 patchable-function-entry로#

  • 옛날(그리고 x86 일부 설정)에는 gcc -pg가 모든 함수 입구에 call mcount(x86-64에서는 __fentry__)를 넣었다. 원래 gprof용이다. 커널은 부팅 때 이 call들을 전부 NOP으로 바꿔 두고(recordmcount/objtool이 위치를 목록으로 모아 둔다), 켤 때 다시 call로 바꾼다.
  • arm64는 -fpatchable-function-entry=N,M 옵션을 쓴다. 컴파일러가 처음부터 NOP N개를 넣고 그중 M개는 함수 시작 주소 앞에 둔다. 위치 목록은 __patchable_function_entries 섹션에 남는다. 6.18.55의 arch/arm64/Makefile:

2.5 커널은 실행 중인 코드를 어떻게 안전하게 고치나#

다른 CPU가 바로 그 명령을 실행하고 있을 수 있다. 어떻게 안전한가?

  • arm64 아키텍처는 B/BL/NOP 사이의 4바이트 교체를 다른 CPU가 동시에 실행해도 안전한 수정으로 허용한다(옛 명령 아니면 새 명령 중 하나가 실행된다). 그래서 6.18의 arm64 ftrace_modify_code()는 aarch64_insn_patch_text_nosync()로 한 워드를 쓰고 I-cache를 flush 할 뿐, 모든 CPU를 세우는 stop_machine()을 쓰지 않는다 (arch_ftrace_update_code()가 FTRACE_MAY_SLEEP을 붙여 ftrace_modify_all_code()를 부른다).
  • 커널 텍스트는 평소에 읽기 전용으로 매핑돼 있으므로, 패치는 임시 쓰기 가능 매핑(fixmap)을 통해 한다.
  • 이 "켜고 끄기"에 걸린 시간은 dyn_ftrace_total_info의 update time으로 보인다.

x86은 call이 5바이트라 한 번에 원자적으로 못 바꿔서, int3 breakpoint를 먼저 써 넣고 나머지를 고친 다음 int3를 지우는 3단계(text_poke_bp)를 쓴다. 면접에서 아키텍처 차이를 말할 수 있으면 좋다.

함정:

  • notrace 표시(__attribute__((no_instrument_function)))된 함수, __init 일부, inline 된 함수, static 함수가 컴파일러에 의해 사라진 경우는 available_filter_functions에 없다. 소스에 있는 이름이 추적 가능한 이름이라는 보장은 없다 — 항상 이 파일을 먼저 grep 한다(F12 §2 함정과 같은 이야기).
  • 컴파일러가 m5_bus_xfer를 m5_bus_xfer.isra.0으로 바꿔 놓을 수 있다(§3.3 출력). 이름에 .isra, .constprop, .part가 붙은 복제본은 원래 이름으로 필터하면 안 걸린다. glob(m5_bus_xfer*)을 쓴다.

4. function_graph — 호출 트리와 소요 시간, 반환값#

4.1 어떻게 함수의 "끝"을 아나#

function tracer는 함수 입구만 안다. 끝(return)을 알려면? 입구에서 리턴 주소를 가로챈다. ftrace_caller가 스택(arm64는 LR)의 진짜 리턴 주소를 태스크별 shadow stack(current->ret_stack)에 저장하고, 리턴 주소를 return_to_handler로 바꿔 둔다. 함수가 ret 하면 return_to_handler로 가서 시간·반환값(x0)을 기록하고 shadow stack에서 진짜 주소를 꺼내 돌아간다.

그림 4 — function_graph가 리턴을 잡는 방법. 함수마다 입구와 출구 두 번 기록하므로 function tracer보다 훨씬 비싸다(§13에서 약 4.5배).

주요 설정:

파일·옵션뜻
set_graph_function이 함수 아래만 트리로 기록 (그 함수가 불렸을 때만 켜짐)
set_graph_notrace이 함수 아래는 빼기
max_graph_depth트리 깊이 제한 (0 = 무제한)
tracing_thresh이 µs 이상 걸린 함수만 기록 (graph에서)

options/funcgraph-argsBTF로 인자 이름·값 표시 (6.16+ 무렵 추가, 이 커널에 있다)
options/funcgraph-proc, -abstime, -irqs, -tail프로세스 이름, 절대 시각, IRQ 안 함수 표시, 닫는 괄호에 함수 이름

DURATION 칸 앞 기호: + > 10 µs, ! > 100 µs, # > 1 ms, * > 10 ms, @ > 100 ms, $ > 1 s.

5. tracepoint(event) — 커널 개발자가 박아 둔 관측 지점#

9. latency tracer — 최악의 구간을 자동으로 잡는다#

9.1 종류#

tracer재는 것시작 → 끝
irqsoffIRQ가 꺼져 있던 가장 긴 구간local_irq_disable/save → enable/restore
preemptoffpreemption이 꺼져 있던 가장 긴 구간preempt_disable → preempt_enable (spinlock 포함)
preemptirqsoff둘 중 하나라도 꺼져 있던 구간 (합집합)가장 실용적인 "스케줄 불가 구간"
wakeup가장 높은 우선순위 태스크의 wakeup → 실행 지연 (모든 태스크)sched_wakeup → sched_switch
wakeup_rt같은데 RT 태스크만
wakeup_dlSCHED_DEADLINE 태스크만

공통 동작: 새 최대값이 나오면 tracing_max_latency(µs)를 갱신하고, 그 구간의 기록을 max 버퍼(snapshot)에 보관한다. trace를 읽으면 그 최악 구간이 나온다. 기본은 최대값 하나만 남긴다. tracing_thresh를 0이 아닌 값으로 쓰면 그 값을 넘는 구간을 전부 남긴다(최대값만이 아니라).

irqsoff/preemptoff는 CONFIG_IRQSOFF_TRACER/CONFIG_PREEMPT_TRACER가 필요하다. 이 tracer들이 trace_hardirqs_off/on hook을 켜 두기 때문에 커널을 이 옵션으로 빌드만 해도 약간 느려진다. 그래서 이 랩의 RT 커널(Image-rt)에는 빠져 있다. 양산 RT 시스템에서는 대신 osnoise/timerlat(N3)을 쓴다.

TCG 잡음 경고 (실측): 같은 스크립트에서 culprit을 실행하기 전 1초 동안의 tracing_max_latency가 이미 17~59 ms였다(커널 자체의 irq-off 구간이 TCG 부하로 늘어진 것). culprit을 1 ms로 돌린 첫 실행에서는 (preemptoff 쪽에서) culprit이 아니라 커널의 16 ms 구간이 1등이 되었다(§9.3). 그래서 60 ms로 키웠다. 그리고 60 ms로 돌린 한 번은 irqsoff의 max가 9 ms로 나와 culprit이 잡히지 않았다(원인 미확인 — 바로 다시 돌린 두 번은 모두 잡혔다). 실제 보드에서는 커널 자체의 irq-off 최대가 보통 수십~수백 µs 수준이라 1 ms 구간이면 바로 1등으로 잡힌다.

10.1 per-CPU ring buffer와 overrun#

ring buffer는 CPU마다 따로 있다. 각 CPU는 자기 버퍼에만 쓰므로 lock이 필요 없고(펌웨어에서 ISR과 메인 루프가 같은 링버퍼를 쓸 때 고민하던 문제를 CPU별 분리로 피한다), 읽을 때 타임스탬프로 합쳐서 보여 준다. 기본 모드는 overwrite: 꽉 차면 가장 오래된 페이지를 덮어쓴다. options/overwrite를 0으로 하면 반대로 새 이벤트를 버린다(dropped).

  • kprobe: 3.3배 — function 1개(1.2배)보다 훨씬 비싸다. arm64에서 kprobe는 BRK 예외 → 핸들러 → 원래 명령 single-step(XOL)으로 예외를 두 번 겪는다(이 커널의 arm64에는 KPROBES_ON_FTRACE가 없다 — arch/arm64/Kconfig에 해당 select가 없음을 확인). 함수 입구라면 fprobe(f:)가 ftrace 자리를 써서 더 싸다 — 이 노트에서는 fprobe를 따로 재지 않았다.

그림 10 — 네 종류의 hook이 같은 기록 경로(reserve → 필터·트리거 → commit)로 모인다.

  • tracefs 파일은 그냥 file_operations다. echo function > current_tracer는 tracing_set_trace_write() → tracing_set_tracer() → tracer의 init → register_ftrace_function() → ftrace_modify_all_code()로 이어져 §2의 패치를 일으킨다. 드라이버의 .write 콜백(G 모듈)과 같은 구조다 — 여러분이 debugfs 파일을 만드는 것과 다르지 않다(m5_lat의 irqoff_us처럼).
  • tracepoint 켜기: events/.../enable에 1을 쓰면 tracepoint_probe_register()가 probe 함수(trace_event_raw_event_<name>)를 등록하고 static key를 켠다 → §5.7에서 본 NOP이 b로 바뀐다. 같은 tracepoint에 perf(perf_trace_<name>)와 BPF(__bpf_trace_<name>)도 붙는다 — m5_tp 모듈의 kallsyms에 이 세 함수가 모두 생긴 것을 확인했다:

  • latency tracer: trace_hardirqs_off/on(irqflags 추적), trace_preempt_off/on hook에서 시각을 재고, 새 최대값이면 update_max_tr()가 버퍼를 max 버퍼와 swap 한다(§10.3의 snapshot과 같은 swap).
  • 드라이버를 쓸 때 다시 만나는 지점: ① 자기 드라이버에 TRACE_EVENT 넣기(§5.7) — 커널 서브시스템들(I2C의 i2c:i2c_write, SPI의 spi:spi_transfer_start, GPIO, regmap의 regmap:regmap_reg_write, videobuf2의 vb2:vb2_buf_queue/vb2:vb2_buf_done)이 이미 이렇게 하고 있어서 버스 트랜잭션을 코드 수정 없이 볼 수 있다(H5 I2C, H 모듈). ② IRQ handler 지연 — irq:irq_handler_entry/exit, irqsoff(F6). ③ probe 실패 원인 — function_graph + retval로 -EPROBE_DEFER/-EINVAL의 출처(G 모듈). ④ 동시성 버그 — sched 이벤트와 lock 관련 이벤트로 순서 재구성(F4).

15.1 센서 키트: IMU 샘플이 가끔 늦다#

로봇의 IMU(SPI, 1 kHz)를 읽는 스레드가 가끔 주기를 놓친다. 순서:

  1. 앱에서 주기 지터를 직접 측정하고 늦은 주기만 trace_marker로 표시(§7.1).
  2. trace-cmd record -e sched:sched_switch -e sched:sched_wakeup -e irq:irq_handler_entry -e spi:spi_transfer_start -e spi:spi_transfer_stop ./imu_app처럼 스케줄링·IRQ와 SPI 트랜잭션 시작/끝을 같이 기록한다. spi:* 이벤트는 SPI core(include/trace/events/spi.h)에 이미 있는 tracepoint라 드라이버 수정이 필요 없다. marker는 따로 켤 필요 없다(§11.2).
  3. 늦은 주기 주변에서: 스레드가 깨워졌는데 못 돌았나(→ wakeup_rt, 우선순위·affinity, N2), 돌았는데 SPI가 늦었나(→ 컨트롤러 IRQ, DMA, irq_handler_entry), SPI 버스를 같은 버스의 다른 장치(예: SPI 플래시)가 쥐고 있었나(→ §8과 같은 mutex 경합 — SPI 컨트롤러의 bus lock).

15.2 카메라 장비: 프레임 드롭#

V4L2(I4) 버퍼 관리 계층 videobuf2의 tracepoint(vb2:vb2_buf_queue, vb2:vb2_buf_done 등)와 irq_handler_entry(CSI 수신 IRQ)를 함께 기록하면 "버퍼가 늦게 queue 되었나(유저 앱이 늦음) vs DMA 완료 IRQ가 늦었나(커널)"가 갈린다. 이벤트 이름은 커널 버전마다 조금씩 다르므로 trace-cmd list -e vb2로 먼저 확인한다.

15.3 양산 장비에서 쓰는 법 — "켜 둔 채로 출하"할 수 있나#

  • 커널 config에 CONFIG_FUNCTION_TRACER/CONFIG_DYNAMIC_FTRACE/CONFIG_FTRACE_SYSCALLS를 켜 두는 것은 많은 배포판·Android 커널이 한다(꺼져 있을 때 NOP — §2, §13). 대신 커널 이미지가 조금 커지고(__mcount_loc/patchable entry 테이블), 함수 앞 NOP이 I-cache를 조금 먹는다.

  • 보안: tracefs는 커널 주소·데이터를 보여 주므로 root 전용이고, Secure Boot + lockdown(L 모듈)에서는 kprobe 등이 제한된다.

15.4 Don의 경험과 연결#

SSD 펌웨어에서 "커맨드 지연 꼬리(tail latency)"를 잡을 때 했던 일 — 이벤트 ID와 타임스탬프를 RAM 링에 남기고, 느린 커맨드가 나오면 링을 얼려 덤프하고, 시간축에 그려 겹치는 GC·리드 리트라이를 찾는 것 — 이 정확히 §8의 흐름이다. 차이는 ① 커널이 이미 수천 개의 이벤트를 제공한다 ② 코드 수정 없이 kprobe/fprobe로 임의 지점을 추가한다 ③ hist/synthetic으로 분포를 커널 안에서 만든다는 점이다. 인터뷰에서 "펌웨어에서 쓰던 trace 링버퍼 + 트리거 방식을 Linux에서는 ftrace로 그대로 한다"고 연결해서 말하면 강하다. 17. 면접에서 이렇게 말한다#

Q. A sensor read on your device usually takes 50 µs but occasionally takes 5 ms. How do you find out why?

A. 먼저 숫자로 재현한다: 앱에서 read 시간을 재고 느린 것만 trace_marker로 표시한다. 그다음 같은 ring buffer에 드라이버 .read 입구·출구(fprobe), 의심 경로(같은 버스를 쓰는 다른 코드), sched_switch/sched_wakeup, IRQ 이벤트를 함께 기록한다. 느린 read 주변을 보면 "다른 스레드가 같은 mutex를 쥐고 있었다", "IRQ가 늦게 왔다", "스레드가 깨워졌는데 못 돌았다" 중 하나가 보인다. 경로가 의심되면 function_graph에 tracing_thresh를 걸어 느린 호출만 트리로 본다. 랩에서 이렇게 해서 5 ms짜리 calibration 스레드가 같은 mutex를 쥐고 있어서 reader가 spin하다가 잠드는 걸 mutex_spin_on_owner와 schedule 이름으로 확인했다.

First I'd quantify it in user space and mark only the slow reads with trace_marker, so the application's view and the kernel's view share one timeline. Then I record, into the same ftrace ring buffer, the driver's read entry and exit with fprobes, sched_switch and sched_wakeup, and IRQ events. Around a slow read you can usually see one of three things: someone else held the lock, the interrupt came late, or the thread was woken but didn't get the CPU. To see which kernel path burned the time, I use function_graph on the read function with tracing_thresh, so only calls slower than a few milliseconds are logged. In my lab, that showed a calibration thread holding the same bus mutex for 5 ms; the reader spun in mutex_spin_on_owner and then slept in schedule. The fix is a design change — shorter critical sections — but ftrace gives the evidence.

꼬리 질문: "그걸 실제 제품에서 켜도 되나?" → 필터를 건 이벤트·fprobe는 오버헤드가 작다(측정: 경로 위 함수 하나 +15%, 경로 밖이면 0). 전 함수 graph는 안 된다.

Q. How can ftrace have near-zero overhead when it's off, if it can trace almost every kernel function?

A. 컴파일러가 모든 함수 입구에 NOP 자리를 만들어 둔다(arm64는 -fpatchable-function-entry, x86은 -pg/mcount를 부팅 때 NOP으로). 꺼져 있을 때는 함수당 NOP 하나(arm64에서는 mov x9, x30 + nop)만 실행된다. 켜면 커널이 필터에 맞는 함수의 NOP만 bl ftrace_caller로 고쳐 쓴다. 랩에서 QEMU gdbstub으로 vfs_read 입구를 덤프해서 NOP이 BL로 바뀌고 끄면 돌아오는 걸 직접 봤다. tracepoint도 같은 원리로 static key(jump label) NOP이다.

Every function is compiled with a few NOP bytes at its entry — on arm64 via -fpatchable-function-entry, on x86 via -pg/mcount call sites that the kernel converts to NOPs at boot. When tracing is off, that's all the CPU executes: on arm64 a mov x9, x30 and a nop. When you enable the function tracer, the kernel rewrites only the selected functions' NOP into a bl to ftrace_caller; arm64 can patch that single 4-byte instruction safely without stop_machine, x86 uses an int3-based sequence. I verified it by dumping vfs_read through the QEMU gdbstub before and after enabling a filter. Tracepoints use the same idea with static keys: the disabled site is one NOP that becomes a branch.

꼬리 질문: "CALL_OPS는?" → 함수 앞 8바이트에 담당 ftrace_ops 포인터를 두어 ftrace_caller가 콜백을 바로 찾는다(리스트 순회 없음).

Q. What's the difference between a tracepoint, a kprobe, and the function tracer?

A. tracepoint는 개발자가 미리 박아 둔 의미 있는 지점이라 필드가 정리돼 있고 비교적 안정적이다. function tracer는 모든 함수 입구에 자동으로 있지만 함수 이름과 호출자만 준다. kprobe는 실행 중 아무 명령에나 붙일 수 있고 레지스터·메모리로 인자를 뽑지만, arm64에서는 BRK 예외라 비싸다(측정 3.3배). 함수 입구라면 fprobe가 ftrace 자리를 쓰므로 더 싸다.

A tracepoint is a static, named hook a kernel developer placed on purpose, with a defined record format — stable and cheap when off. The function tracer instruments every function entry automatically but only tells you which function was called and by whom. A kprobe can be attached at runtime to almost any instruction and can fetch arguments from registers and memory, but on arm64 it works through a BRK exception, so it costs more — about 3x a getpid call in my measurement versus 1.2x for a single traced function. For function entry and exit I prefer fprobes, which reuse the ftrace patch site.

Q. How do you find what's disabling interrupts for too long?

A. irqsoff tracer. IRQ off/on 지점마다 시각을 재서 가장 긴 구간을 자동으로 보관하고 tracing_max_latency, started at/ended at, 콜스택을 준다. 랩에서 모듈이 IRQ를 끈 채 udelay 하는 걸 started at: m5_irqoff_section으로 바로 찾았다. preemption이면 preemptoff, 둘 다면 preemptirqsoff. 단 이 tracer들은 빌드만 해도 hook 비용이 있어 양산 RT 커널에서는 빼고 osnoise/timerlat을 쓴다.

I use the irqsoff latency tracer. It hooks every interrupt disable and enable, keeps the longest window it has seen in tracing_max_latency, and preserves the trace of that window with the start and end functions and a stack trace. In my lab a module busy-waiting with interrupts off showed up immediately as "started at m5_irqoff_section". preemptoff and preemptirqsoff do the same for preemption. Because those hooks cost something even when idle, production RT kernels usually leave them out and rely on osnoise and timerlat instead.

Q. Your trace only shows the last few milliseconds. Why, and what do you do?

A. ring buffer는 CPU별 고정 크기이고 기본이 overwrite라 가장 오래된 것부터 덮어쓴다. 랩에서 32 KB 버퍼 + 전 함수 tracer로 220만 개 중 2530개만 남았다(overrun 105만). 대책: 필터로 양을 줄이고, 버퍼를 키우고, trace-cmd로 계속 디스크에 빼내고, 문제 순간에 traceoff나 snapshot 트리거로 얼린다.

The ring buffer is per-CPU and fixed-size, and by default it overwrites the oldest data. With a 32 KB buffer and the function tracer on everything, I wrote 2.2 million events and kept only 2,530; the per-CPU stats showed over a million overruns. So: reduce volume with filters, enlarge buffer_size_kb, stream continuously with trace-cmd record, and use a traceoff or snapshot trigger to freeze the buffer right when the problem happens.

Q. How would you add tracing to your own driver?

A. TRACE_EVENT로 tracepoint를 정의한다. 헤더 하나에 필드·복사·출력 형식을 쓰고, .c 하나에서 CREATE_TRACE_POINTS로 생성한다. 꺼져 있으면 NOP 하나라 양산 코드에 남겨도 되고, 켜면 필드로 필터·hist가 되고 perf·BPF도 같은 지점을 쓴다. trace_printk는 개발 중에만.

I define tracepoints with TRACE_EVENT in a trace header — fields, the fast-assign copy, and the print format — and instantiate them in one .c file with CREATE_TRACE_POINTS. A disabled tracepoint is a single NOP behind a static key, so it can stay in production code, and when enabled it supports field filters and histograms, and perf and BPF can attach to the same point. trace_printk is fine while debugging, but it prints a debug-kernel warning and shouldn't be merged.

Q. How do you measure wakeup latency of a real-time thread with only ftrace?

A. wakeup_rt tracer가 최고 우선순위 RT 태스크의 최악 wakeup→실행 지연과 그 사이 커널 흐름을 준다. 분포가 필요하면 sched_waking과 sched_switch를 hist 변수로 짝지어 synthetic event를 만들고 거기에 log2 hist를 건다. 전용 도구로는 cyclictest와 rtla timerlat(N3).

The wakeup_rt tracer records the worst wakeup-to-run latency of the highest-priority RT task and the kernel activity in between. For a full distribution, I pair sched_waking and sched_switch with hist trigger variables to create a synthetic wakeup-latency event, then put a log2 histogram on it — all in-kernel, no trace buffer needed. For routine work I'd use cyclictest or rtla timerlat.

20. 요약 & 체크리스트#

ftrace는 커널 안에 내장된 "trace 링버퍼 + 트리거 + 로직 분석기"다. 모든 함수 입구의 NOP 자리(dynamic ftrace), 개발자가 박아 둔 tracepoint, 실행 중에 만드는 kprobe/fprobe/uprobe, 앱이 쓰는 trace_marker가 같은 per-CPU ring buffer에 타임스탬프와 함께 쌓이고, 사람은 /sys/kernel/tracing 파일이나 trace-cmd로 꺼내 본다. 꺼져 있을 때 비용이 NOP 하나라는 점(arm64에서 nop ↔ bl ftrace_caller 한 칸 — gdbstub으로 직접 확인), 필터·hist 트리거·synthetic event로 필요한 것만 커널 안에서 집계할 수 있다는 점, latency tracer가 "가장 긴 IRQ off/preempt off/wakeup 구간"을 범인 함수 이름과 함께 자동으로 잡는다는 점이 핵심이다. 사례 연구에서는 "가끔 느린 센서 read"를 이벤트 타임라인으로 지목하고(같은 mutex를 쥔 calibration 스레드), function_graph + tracing_thresh로 mutex_spin_on_owner/schedule까지 확인했다. 측정은 가벼운 방법으로, 원인 경로는 무거운 방법으로 — 그리고 TCG 숫자는 비율로만 읽는다.
