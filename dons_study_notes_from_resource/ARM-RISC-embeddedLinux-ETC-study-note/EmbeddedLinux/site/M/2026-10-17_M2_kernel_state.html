0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어를 bring-up할 때를 떠올려 보자. 새 컨트롤러 샘플이 왔는데 NAND가 안 읽힌다. 그럴 때 하는 일은 정해져 있다. 먼저 클럭·리셋 레지스터를 읽어 블록이 켜졌는지 보고, 핀먹스 레지스터로 패드가 NAND 기능으로 설정됐는지 보고, 인터럽트 pending/count를 보고, 마지막으로 펌웨어 상태 변수를 JTAG로 덤프한다. 측정 지점이 정해져 있고, 순서가 정해져 있다.

Linux에서도 똑같다. 다만 JTAG로 메모리를 직접 읽는 대신, 커널이 가상 파일로 상태를 보여 준다. 그 창구가 세 개다.

  • /proc — 원래 "프로세스 정보"용 파일시스템이었지만, 역사적으로 커널 전역 통계(interrupts, iomem, meminfo, slabinfo…)도 여기 쌓였다. 형식이 오래 유지된다.
  • /sys (sysfs) — 디바이스 모델(G2) 그 자체. 버스·장치·드라이버·모듈이 디렉터리와 심볼릭 링크로 보인다. "값 하나 = 파일 하나"의 안정 ABI.
  • /sys/kernel/debug (debugfs) — 개발자용. 형식 약속이 없다(ABI 아님). 대신 clk 트리, 레귤레이터, 핀먹스, GPIO, regmap 레지스터처럼 bring-up에 제일 쓸모 있는 정보가 여기 있다. 양산 이미지에서는 꺼 두거나 마운트하지 않는 경우가 많다.

  • QEMU: -machine virt -cpu cortex-a57,pmu=on -smp 2 -m 1G, virtio-blk(PCI) 디스크, virtio-net(PCI). DT는 QEMU가 만들어 준다(같은 인자로 dumpdtb해서 비교에 썼다).
  • 실습 모듈 세 개: m2_defer(없는 GPIO 칩을 기다리며 defer하는 소비자 + GPIO IRQ), m2_regs(RAM 버퍼 위의 regmap-mmio + runtime PM + 실패 주입), m2_slab(전용 slab 캐시·vmalloc·일부러 새는 kmalloc·잠드는 read).
  • 실행 방식: 실험 스크립트를 이미지에 넣고 systemd oneshot 서비스로 부팅 후 자동 실행 → 결과 파일을 debugfs -R cat으로 꺼냈다.

주의: QEMU가 KVM 없이 TCG로 돌고, VM을 17명이 동시에 쓰는 중이라 부팅에 10분 가까이 걸렸다(dmesg 타임스탬프가 600초대인 이유). 이 노트의 타임스탬프·시간 값은 실제 HW 수치가 아니다. 카운트·주소·크기 같은 값만 의미 있게 읽자.

1. 질문 ①~⑤ — "드라이버가 probe 됐나?"#

1.1 직관 — 세 개의 링크만 보면 된다#

1.2 예제 2 — 소비자 드라이버 m2_defer.c#

무엇을 확인하는 코드인가: 센서 드라이버가 리셋 핀과 data-ready(DRDY) 핀을 GPIO 확장기에서 받는 흔한 구조를 흉내 낸다. 확장기(여기서는 gpio-sim 칩 m2_sim)가 아직 없으면 devm_gpiod_get()이 -EPROBE_DEFER를 돌려주고, dev_err_probe()가 그 이유를 기록한다. DT 대신 gpiod_lookup_table(보드 파일식 매핑)을 써서 오버레이 없이 재현했다.

출력에서 볼 것: 코드 자체는 평범한 probe다. 진단에 중요한 줄은 dev_err_probe() 세 개 — 에러가 -EPROBE_DEFER면 로그 대신 이유 문자열을 저장하고, 그 밖의 에러면 dev_err로 찍는다(G3 §9).

1.3 예제 3 — defer 전후를 sysfs·debugfs로 보기#

무엇을 확인하나: 공급자가 없을 때 devices_deferred에 무엇이 보이는지, 공급자(gpio-sim 칩)를 configfs로 만든 뒤 자동 재시도로 bind되는지. dd.c의 dynamic debug를 켜서 driver core의 판단도 같이 본다(M1).

출력에서 볼 것:

  • insmod 직후 devices_deferred에 m2_cons m2_cons: reset gpio not ready가 있다. 형식은 "장치 이름 TAB 이유". 이유 문자열은 우리가 dev_err_probe()에 준 메시지 그대로다 — 드라이버가 dev_err_probe를 안 쓰면 이유 칸이 비어 있다. 그래서 리뷰에서 return -EPROBE_DEFER; 대신 return dev_err_probe(...)를 요구한다.
  • 장치 디렉터리에 driver 링크가 없다. 드라이버 디렉터리에는 bind·unbind·module만 있고 장치 링크가 없다. 장치도 있고 드라이버도 있는데 짝이 안 된 상태 = defer.
  • gpiolib이 cannot find GPIO chip m2_sim, deferring을 dev_warn으로 찍었다. 이건 gpiolib의 lookup 테이블 경로가 남기는 줄이고, driver core 자체는 dyndbg를 켜야만 requests probe deferral·Added to deferred list를 보여 준다. 즉 기본 설정에서는 defer가 거의 조용하다.
  • gpio-sim이 bind되자마자(gpio-sim.0 ... probing) Retrying from deferred list가 나온다. 아무 드라이버나 bind에 성공하면 driver core가 deferred 목록 전체를 다시 시도하기 때문이다(driver_deferred_probe_trigger()).
  • 재시도 후 devices_deferred는 비고, driver -> ../../../bus/platform/drivers/m2_cons 링크가 생겼다.

1.4 deferred_probe_timeout — 영원히 기다리지 않는 장치#

defer가 끝나지 않으면 어떻게 될까. 6.18 drivers/base/dd.c를 보면:

  • 부팅 때 initcall이 다 끝난 뒤 이 타이머(기본 10초, 커널 인자 deferred_probe_timeout=로 변경)가 돈다. 만료되면 아직 대기 중인 장치마다 deferred probe pending: <이유> 경고를 한 번 찍는다. 부팅 로그에서 이 줄을 grep하는 것이 "부팅 후 안 붙은 장치" 목록을 얻는 가장 빠른 방법이다.
  • 만료 후에는 driver_deferred_probe_check_state()를 쓰는 서브시스템(일부 pinctrl·IOMMU·power domain 경로)이 "선택적 공급자"를 포기하고 -ETIMEDOUT으로 진행한다(deferred probe timeout, ignoring dependency).
  • 실습에서는 이 메시지를 재현하지 않았다. 타이머가 부팅 직후 한 번만 돌고, 우리 모듈은 그 뒤에 insmod했기 때문이다. 위 코드는 랩 소스 /var/lab/src/linux-6.18.55/drivers/base/dd.c 255–330행에서 확인한 것이다.

1.5 예제 4 — probe 실패는 에러 코드에 따라 다르게 찍힌다#

무엇을 확인하나: m2_regs의 fail 파라미터로 probe가 -EIO(-5), -ENODEV(-19), -ETIMEDOUT(-110)을 돌려주게 하고, sysfs bind에 쓴 쪽과 dmesg에 무엇이 보이는지.

출력에서 볼 것:

  • bind에 쓴 echo가 probe의 에러 코드를 그대로 errno로 받는다(Input/output error, No such device, Connection timed out). 수동 bind는 probe를 디버깅하는 가장 빠른 루프다 — 모듈을 내렸다 올릴 필요가 없다.
  • -5와 -110은 dev_err로 failed with error가 찍힌다. -19(ENODEV)와 -6(ENXIO)은 "이 장치는 내 것이 아니다"라는 뜻으로 취급돼 dev_dbg(rejects match)로만 찍힌다 — 여기서는 dd.c dyndbg를 켜 뒀기 때문에 보였다. 기본 설정이면 dmesg에 아무것도 없고 장치는 조용히 unbound로 남는다. 칩 ID가 안 맞을 때 -ENODEV를 돌려주는 드라이버가 많으니, "로그 없이 안 붙는다"면 이 경우를 의심한다.
  • fail=0으로 되돌리고 bind하면 정상 bind된다. 설정 파라미터가 0644라서 런타임에 바꿀 수 있었다(§7).

2. 질문 ① — "어떤 DT 노드가 쓰였나?"#

2.1 세 이름은 같은 트리다#

  • /proc/device-tree → /sys/firmware/devicetree/base로 가는 심볼릭 링크다. 커널이 실제로 받아서 해석한 DT(부트로더가 고친 것, 오버레이 적용 후)를 보여 준다. 빌드한 .dts가 아니라 이것이 진실이다(D1, D6).
  • 각 장치의 of_node 링크가 그 트리의 한 노드를 가리킨다. "이 장치는 어느 노드에서 만들어졌나"의 답.
  • 속성 파일은 바이너리다. 문자열 목록은 NUL로 구분되고, 숫자는 big-endian 32비트 셀이다. tr '\0' ' '와 od -An -tx1로 읽는다.

2.2 예제 5 — PL011 UART 장치에서 DT 노드까지#

무엇을 확인하나: amba 버스의 9000000.pl011 장치가 어느 노드에서 왔고 어떤 드라이버가 잡았는지, reg 셀이 /proc/iomem(§4)과 맞는지.

출력에서 볼 것:

  • 루트 compatible이 linux,dummy-virt. of_node는 ../../../firmware/devicetree/base/pl011@9000000을, driver는 amba/drivers/uart-pl011을 가리킨다. 처음에 /sys/bus/platform/devices/9000000.pl011을 찾다가 "No such file"을 봤다 — PL011은 amba 버스 장치라서다. "장치가 없다"고 결론 내리기 전에 ls /sys/bus/의 다른 버스도 본다.
  • reg의 16바이트 = <0x0 0x09000000 0x0 0x1000> (address-cells=2, size-cells=2). §4의 /proc/iomem 줄 09000000-09000fff : 9000000.pl011과 정확히 맞는다.
  • devices_deferred가 비어 있다([end]만). 부팅 후 안 붙은 장치가 없다는 뜻이다.

함정: status = "disabled"인 노드는 /proc/device-tree에는 있지만 장치 객체가 만들어지지 않는다. 노드가 보인다고 장치가 있는 게 아니다 — 그림 1의 ①과 ②는 다른 질문이다. cat .../status가 없으면 기본값 okay다.

3. 질문 ⑦ — "인터럽트가 들어오나?"#

3.1 숫자 세 개가 같은 인터럽트를 가리킨다#

SSD 컨트롤러에서는 인터럽트 번호가 하나였다 — 벡터 테이블의 인덱스. Linux에는 번호가 세 겹이다(H6).

  • hwirq: 인터럽트 컨트롤러 안의 번호. GIC라면 SPI 1 = hwirq 33(32 + 1). gpio-sim이라면 라인 번호.
  • irq_domain: 컨트롤러 하나마다 하나. hwirq → Linux 번호 변환표.
  • virq (Linux IRQ 번호): request_irq()에 넘기는 번호, /proc/interrupts 맨 앞 칸, /proc/irq/N/의 N. 부팅마다 바뀔 수 있다 — 보드 문서에 virq를 적지 말 것.

4. 질문 ⑥의 전제 — "주소 맵이 맞나?" (/proc/iomem, /proc/ioports, memblock)#

4.1 직관#

/proc/iomem은 커널의 struct resource 트리(iomem_resource)를 그대로 출력한다. 들여쓰기가 트리 깊이다. 바깥 줄 = DT/버스가 선언한 영역, 안쪽 줄 = 드라이버가 request_mem_region()(devm_ioremap_resource가 내부에서 호출)으로 실제 점유한 영역. 그래서 안쪽 줄이 없으면 "장치는 있는데 드라이버가 레지스터를 잡지 않았다"는 뜻이다. 두 드라이버가 같은 영역을 잡으려 하면 두 번째가 -EBUSY로 probe에 실패하고, 그 충돌도 여기서 보인다.

4.2 예제 9 — root vs 일반 사용자#

무엇을 확인하나: root로 본 iomem, nobody(uid 65534)로 본 iomem, ioports.

출력에서 볼 것:

  • 09000000-09000fff : pl011@9000000 바깥 줄 아래 9000000.pl011 안쪽 줄 = PL011 드라이버가 4 KiB를 점유했다. 예제 5의 reg와 일치. pl031(RTC), pl061(GPIO)도 같은 모양.
  • 10000000-3efeffff : pcie@10000000, 4010000000-401fffffff : PCI ECAM, 8000000000-ffffffffff(64비트 prefetch 창) — QEMU가 만든 DT의 PCIe ranges·reg와 같다(ranges = <... 0x2000000 0x00 0x10000000 ...>, reg = <0x40 0x10000000 ...>, dumpdtb로 확인). 그 안에 virtio-pci BAR가 virtio-pci-modern으로 잡혀 있다.

5.7 예제 15 — zoneinfo의 watermark#

무엇을 확인하나: 존별 free 페이지와 min/low/high watermark.

출력에서 볼 것:

  • RAM이 전부 0x40000000..0x7fffffff(4 GiB 아래)라서 arm64에서는 전부 DMA 존에 들어간다. managed 241323 페이지 × 4 KiB = 965292 kB = MemTotal과 정확히 같다.
  • min 5632 페이지 × 4 KiB = 22528 kB = vm.min_free_kbytes. free가 low 아래로 내려가면 kswapd가 깨어나고, min 아래면 할당하는 쪽이 직접 회수(direct reclaim)한다 — 인터럽트 문맥의 GFP_ATOMIC 할당이 실패하기 시작하는 지점이다. 네트워크 드라이버가 "page allocation failure: order:2"를 찍는 보드에서는 이 값과 buddyinfo를 같이 본다.

6. 질문 ⑥ — "자원이 살아 있나?" (clk · regulator · pinctrl · GPIO · regmap · devlink · power · DMA)#

bind는 됐는데 장치가 응답하지 않는다. bare-metal이라면 "클럭 게이트 열렸나, 전원 레일 올라왔나, 핀먹스 맞나, 레지스터 값 맞나"를 JTAG로 본다. Linux에서는 각 프레임워크(H2·H3·H4)가 debugfs에 요약표를 내놓는다. 이 표들은 "드라이버가 요청한 상태"를 보여 준다 — 실제 HW 레지스터와 다를 수 있다는 점은 §6.6에서 다시 말한다.

6.1 예제 16 — clk_summary와 regulator_summary#

무엇을 확인하나: QEMU virt의 클럭 트리와 레귤레이터 목록.

출력에서 볼 것:

  • virt에는 클럭이 clk24mhz(DT apb-pclk fixed-clock, 24 MHz) 하나뿐이고, consumer 칸에 pl031·pl061·pl011이 connection id(apb_pclk, no_connection_id)와 함께 나온다. enable count 5 = 소비자 다섯이 clk_prepare_enable()을 했다. hardware enable Y는 클럭 드라이버의 is_enabled 콜백 결과다.
  • 레귤레이터는 regulator-dummy 하나. DT에 공급자가 없는 *-supply를 요청하면 regulator core가 이 dummy를 준다(부팅 로그 supply vdd not found, using dummy regulator).
  • 실제 SoC에서는 (실행 안 함, 구조 설명) 이 표가 수백 줄이다: PLL → divider → gate로 들여쓰기된 트리가 나오고, 각 줄의 rate로 "I2C 컨트롤러 입력 클럭이 정말 66 MHz인가", enable count로 "누가 이 게이트를 잡고 있어서 절전이 안 되나"를 본다. regulator_summary도 PMIC의 buck/LDO 아래 소비자 장치가 들여쓰기되고, use·open·voltage·소비자별 요청 전압(min/max)이 나온다. 센서 레일이 0mV나 use 0이면 전원부터 의심한다.
  • 부팅 로그의 clk: Disabling unused clocks(이 게스트에서도 29.44초에 찍혔다)는 late_initcall에서 아무도 enable 안 한 클럭을 끄는 단계다. 부트로더가 켜 둔 클럭에 기대던 장치가 이 줄 직후 죽으면, 드라이버가 클럭을 요청하지 않은 것이다. 임시 확인용 커널 인자는 clk_ignore_unused, 같은 성격의 레귤레이터 쪽은 regulator_ignore_unused.

무엇을 확인하나: virt 게스트에서 다른 자원 요약 파일이 무엇을 보여 주는지(거의 비어 있다는 사실 자체가 정보다).

(DMA 부분은 ls /sys/kernel/debug 전체 목록을 빼고 결과만 남겼다. dmaengine/ 안에는 summary 파일만 있고 내용은 비어 있다.)

출력에서 볼 것과 실제 SoC와의 차이:

  • pinctrl: pinctrl-devices·pinctrl-handles·pinctrl-maps 세 파일만 있고 컨트롤러 디렉터리가 없다 — virt에는 핀 컨트롤러가 없다. 실제 SoC(실행 안 함)라면 /sys/kernel/debug/pinctrl/<컨트롤러>/ 아래 pins(패드 번호·이름·현재 레지스터 값), pinmux-pins(각 핀을 누가 어떤 function으로 잡았나 — "pin 42 (UART2_TX): device 30890000.serial function uart2 group uart2grp"), pinconf-pins(pull·drive strength)가 있다. 두 드라이버가 한 핀을 다투면 두 번째 probe가 pin X already requested by Y로 실패하고 pinmux-pins에 첫 주인이 보인다(H4).
  • devlink: /sys/class/devlink/에 링크가 0개. gpio-keys는 pl061의 GPIO를 쓰지만 GPIO가 자식 노드(poweroff { gpios = ... })에 있어서인지 장치 링크가 만들어지지 않았다(원인은 확인하지 않았다 — 관찰 사실만 적는다). 실제 SoC에서는 fw_devlink(기본 fw_devlink=on)가 DT의 clocks·*-supply·*-gpios·interrupts·pinctrl-0 참조마다 <공급자>--<소비자> 링크를 만들고, 각 링크의 status(available, consumer probing, active, supplier unbinding…)와 sync_state_only가 보인다. 공급자가 bind되기 전에는 소비자의 probe를 아예 시작하지 않으므로 devices_deferred에도 안 나오는 경우가 있다 — 그때는 /sys/kernel/debug/devices_deferred 대신 이 링크들과 부팅 로그의 fw_devlink 경고를 본다(G3 §9, D3).
  • wakeup_sources: RTC(9010000.pl031)와 alarmtimer만. 시스템이 suspend에 안 들어가면(N 모듈) active_count·prevent_suspend_time이 늘어나는 소스가 범인이다.
  • DMA: virt에는 DMA 엔진 컨트롤러가 없어서 dmaengine/summary가 빈 파일이다. 실제 SoC라면 채널별로 "dma0chan3 (uart2-rx): in-use"처럼 누가 어떤 채널을 잡았는지가 나온다. swiotlb는 DMA 주소 제한이 있는 장치용 바운스 버퍼 풀이다. io_tlb_used가 0이 아니면 어떤 장치가 바운스 복사를 하고 있다는 뜻이라 성능 문제의 원인이 될 수 있다(H9). 이 게스트는 512 슬랩 중 0개 사용.

6.6 함정 — 요약표는 "커널이 믿는 상태"다#

clk_summary의 rate는 클럭 드라이버가 계산한 값이고, regulator_summary의 voltage는 PMIC 드라이버가 설정했다고 믿는 값이다. 클럭 드라이버의 divider 테이블이 틀렸거나 PMIC 레지스터 쓰기가 I2C 오류로 조용히 실패하면 표는 정상인데 HW는 다르다. Don이 잘하는 영역이 여기다 — 표가 정상인데 동작이 이상하면 scope로 클럭 핀·레일을 직접 재고(M11), devmem//dev/mem 또는 regmap 덤프로 실제 레지스터를 읽어 비교한다.

출력에서 볼 것:

  • lsmod는 /proc/modules를 예쁘게 찍는 도구일 뿐이다. /proc/modules에는 상태(Live/Loading/Unloading), 로드 주소, taint 플래그((OE))가 더 있다. nobody에게는 주소가 0이다(kptr_restrict=1 → CAP_SYSLOG 없으면 가림). oops의 PC를 모듈 오프셋으로 바꿀 때(M3) 이 주소가 필요하니 root로 본다.

8. "앱이 멈췄다" — /proc/<pid>/stack, wchan, status, syscall#

8.1 직관#

RTOS에서 태스크가 멈추면 태스크 리스트에서 상태(Blocked)와 "무엇을 기다리나(semaphore X)"를 본다. Linux에서는 /proc/<pid>/ 아래가 그 태스크 리스트다(A2). 특히 커널 스택(stack)은 "이 프로세스가 커널 안 어느 함수에서 자고 있나"를 바로 보여 준다. 센서 앱이 read()에서 안 돌아오면 → 드라이버의 wait_event 줄이 보인다.

8.2 예제 21 — 드라이버 안에서 잠든 태스크 찾기#

무엇을 확인하나: m2_slab의 block 파일을 읽는 cat이 잠든 상태에서 /proc/<pid>/의 여러 파일. 그리고 nobody가 남의 stack을 볼 수 있는지.

출력에서 볼 것:

  • State: S (sleeping) = TASK_INTERRUPTIBLE(시그널로 깨울 수 있다, F3). D (disk sleep)이면 TASK_UNINTERRUPTIBLE — kill도 안 먹고, 120초(hung_task_timeout_secs)가 넘으면 hung task 경고가 뜬다.
  • wchan=blk_read — 잠든 함수 이름 한 단어. ps -o wchan도 같은 파일을 읽는다.
  • stack은 위에서부터 blk_read+0x94/0xe0 [m2_slab] ← full_proxy_read(debugfs의 래퍼) ← vfs_read ← ksys_read ← __arm64_sys_read ← … ← el0t_64_sync(유저 모드에서 SVC 예외 진입, E6). 맨 위 줄의 [모듈명]과 오프셋이 드라이버의 정확한 위치다. +0x94/0xe0은 "함수 시작에서 0x94바이트, 함수 길이 0xe0"이고, scripts/faddr2line m2_slab.ko blk_read+0x94/0xe0으로 소스 줄로 바꿀 수 있다(M3).
  • syscall의 첫 숫자 63은 arm64의 read syscall 번호, 둘째 0x3은 fd 3이다. 그 뒤는 나머지 인자·스택 포인터·PC.
  • nobody는 /proc/1/stack에 Permission denied. stack 파일은 root 전용(0400 + ptrace 권한 검사)이다.
  • voluntary_ctxt_switches: 1 — 스스로 한 번 잠들었다. 이 수가 초당 수천씩 오르는 스레드는 짧게 자고 깨기를 반복하는 것이다(폴링 루프, 지나치게 잦은 IRQ thread).

9.2 timer_list, softirqs, locks, workqueue#

  • /proc/timer_list: CPU별 hrtimer 큐와 tick device. 이 게스트에서는 각 CPU가 arch_sys_timer(set_next_event: arch_timer_set_next_event_virt, event_handler: hrtimer_interrupt)를 쓰고, 별도로 broadcast 장치 bc_hrtimer가 있다. CPU idle에서 로컬 타이머가 멈추는 SoC에서는 broadcast 장치가 진짜 HW 타이머여야 한다 — "idle 들어가면 시스템이 멈춰요"의 단서가 여기 있다(F8, N 모듈).
  • /proc/softirqs: §3.4에서 본 것처럼 softirq 종류별·CPU별 카운트. NET_RX가 한 CPU에만 몰리면 RPS/IRQ affinity를 본다. TIMER·SCHED·RCU는 늘 움직이는 배경 소음이다.
  • /proc/locks: 유저스페이스 파일 잠금(flock/fcntl/OFD) 목록. 이 게스트에서는 그 순간 아무도 잠금을 안 잡고 있어서 비어 있었다. "앱 두 개가 같은 설정 파일에서 서로 기다린다"를 볼 때 쓴다. 커널 내부 lock(mutex·spinlock)은 여기 안 나온다 — 그건 lockdep /proc/lockdep*(M8)과 /proc/<pid>/stack이다.
  • workqueue: /sys/devices/virtual/workqueue/에는 WQ_SYSFS 플래그로 만든 큐만 보인다(이 게스트: blkcg_punt_bio, writeback, 그리고 unbound 큐 기본 cpumask = 3 → CPU 0,1). 바쁜 워크큐 전체 상태는 SysRq t(echo t > /proc/sysrq-trigger, M4)가 태스크 목록과 함께 "Showing busy workqueues and worker pools"로 찍어 주고, 커널 소스의 tools/workqueue/wq_dump.py(drgn)도 있다. workqueue 지연 측정은 ftrace의 workqueue:* tracepoint(M5)로 한다.

10.2 드라이버를 쓸 때 이 지식이 다시 나오는 곳#

  • 이름을 잘 붙여라. /proc/interrupts의 action 이름(devm_request_irq의 devname), slab 캐시 이름, regmap 이름, GPIO con_id, clk con_id가 모두 진단 화면의 "누가"가 된다. "irq" 같은 이름을 주면 현장에서 아무도 못 찾는다. 장치가 여러 개면 dev_name(dev)를 쓰자.
  • dev_err_probe()를 써라. defer 이유가 devices_deferred에 남고, 나머지 에러는 장치 이름과 함께 찍힌다(G3).
  • -ENODEV는 "내 장치 아님"일 때만. 칩 ID 불일치처럼 진짜 HW 문제면 -EIO나 -ENXIO 대신 dev_err를 직접 찍고 반환하자 — 안 그러면 §1.5처럼 아무 로그 없이 사라진다. (커뮤니티 관행은 드라이버마다 다르니 리뷰어 의견을 따른다.)
  • 진단 정보는 debugfs에. 레지스터 덤프·통계는 debugfs_create_regset32()나 regmap debugfs로(G8). /proc에 새 파일을 만드는 건 금지에 가깝다.
  • 잠드는 곳은 interruptible로. 예제 21처럼 S 상태면 앱을 Ctrl-C로 뺄 수 있다. D로 자는 경로는 hung task 경고의 원인이 된다(F3).

13. 면접에서 이렇게 말한다#

Q. "The board boots, but /dev/xxx never appears. Where do you look?"

A. 체인을 순서대로 끊어 본다. DT 노드가 있고 okay인지(/proc/device-tree), 버스 아래 장치 객체가 생겼는지(/sys/bus/*/devices), driver 링크가 있는지. 없으면 devices_deferred에 이유가 있는지, dmesg에 probe ... failed with error가 있는지. bind는 됐는데 노드가 없으면 클래스 등록이나 udev 쪽이고, 동작이 이상하면 clk·regulator·pinmux 요약과 /proc/interrupts를 본다. -ENODEV는 조용히 실패하니 dd.c dynamic debug도 켠다.

I walk the chain in order. Is the DT node present and okay under /proc/device-tree? Did the bus create a device object under /sys/bus/BUS/devices? Is there a driver symlink? If not, I check debugfs devices_deferred for a recorded reason, and dmesg for "probe with driver X failed with error N". If it's bound but there's no device node, it's the class registration or udev. If it's bound but misbehaving, I go to clk_summary, regulator_summary, pinmux-pins, and the interrupt counts. And since -ENODEV from probe is silent by default, I turn on dynamic debug for drivers/base/dd.c.

꼬리 질문: "What does the driver symlink tell you that dmesg doesn't?" → 현재 bind 상태 그 자체(로그는 과거 기록, 링크는 지금 상태).

Q. "What is -EPROBE_DEFER and how do you debug a device stuck in deferred probe?"

A. probe에 필요한 공급자(clk·regulator·GPIO·PHY)가 아직 없다는 뜻이고, driver core가 목록에 넣었다가 다른 드라이버가 bind될 때마다 다시 시도한다. devices_deferred에 dev_err_probe()가 남긴 이유가 나오고, 부팅 후 timeout(기본 10초)이 지나면 deferred probe pending: 경고가 찍힌다. 공급자 드라이버가 빠졌는지, 공급자 자체가 defer 중인지(연쇄)를 따라간다. fw_devlink가 있으면 /sys/class/devlink에서 공급자-소비자 링크 상태도 본다.

It means a supplier the probe needs isn't there yet, so the driver core parks the device and retries every time some other driver binds. debugfs devices_deferred shows the reason recorded by dev_err_probe, and after the deferred probe timeout — ten seconds by default — the kernel prints "deferred probe pending" for whatever is still waiting. Then I follow the chain: is the supplier's driver missing from the build, or is the supplier itself deferred? With fw_devlink I also look at the device links in /sys/class/devlink.

Q. "How do you confirm that an interrupt is actually arriving?"

A. /proc/interrupts에서 그 action 이름의 줄을 찾아, 장치를 한 번 자극하기 전후로 카운트를 비교한다. 0에서 안 움직이면 핀먹스·트리거 타입·컨트롤러 설정, 폭주하면 레벨 인터럽트를 안 지우는 핸들러다. /sys/kernel/irq/N/type으로 실제 트리거를, effective_affinity로 실제 받는 CPU를, spurious로 처리 안 된 수를 본다. 마지막엔 scope로 핀을 직접 본다.

I find the line with the handler's name in /proc/interrupts and compare the counts before and after poking the device. If it stays at zero, it's pinmux, trigger type, or the controller setup; if it explodes, it's usually a level interrupt the handler never clears. /sys/kernel/irq/N/type shows the trigger actually programmed, effective_affinity shows which CPU really receives it, and /proc/irq/N/spurious counts unhandled ones. If the counters disagree with my expectation, I put a scope on the pin.

Q. "Why is MemTotal smaller than the RAM on the board?"

A. MemTotal는 버디 할당자가 관리하는 페이지 합이다. 커널 코드·데이터, memblock 예약, no-map carve-out은 빠진다. 실습에서는 1 GiB 중 83 MB가 빠졌고, zoneinfo의 managed 페이지 × 4 KiB가 MemTotal과 정확히 같았다. 차이는 /proc/iomem의 reserved 줄과 debugfs memblock으로 설명한다.

MemTotal is the number of pages the buddy allocator manages, so the kernel image, memblock reservations and no-map carve-outs are excluded. On my QEMU board, 83 MB of 1 GiB was missing, and zoneinfo's managed pages times four kilobytes matched MemTotal exactly. The reserved entries in /proc/iomem and debugfs memblock account for the difference.

Q. "How would you detect a memory leak in a kernel driver on a deployed device?"

A. 먼저 /proc/meminfo의 SUnreclaim과 /proc/slabinfo를 주기적으로 찍어 diff한다. 늘어나는 캐시 이름이 단서다 — 드라이버 전용 캐시면 바로 범인이고, kmalloc-N이면 디버그 빌드에서 kmemleak나 slub_debug=U의 alloc_calls로 호출 위치를 찾는다. 실습에서 kmalloc-512가 1000개씩 늘고 모듈을 내려도 그대로인 걸 확인했다.

First, periodic snapshots of SUnreclaim in /proc/meminfo and of /proc/slabinfo, then diff them. The growing cache's name is the clue: if it's the driver's own cache, that's the culprit; if it's a generic kmalloc-N cache, I reproduce on a debug build with kmemleak or slub_debug=U and read alloc_calls to get the call site. In my lab, kmalloc-512 grew by exactly a thousand objects per trigger and stayed there after the module was unloaded.

Q. "An application hangs in read() on your device. How do you find where?"

A. /proc/<pid>/status의 State(S냐 D냐), wchan, 그리고 root로 /proc/<pid>/stack을 본다. 맨 위 줄이 [모듈명]이 붙은 드라이버 함수와 오프셋이라 faddr2line으로 소스 줄까지 간다. 그 wait 조건을 깨우는 쪽(IRQ 핸들러가 wake_up을 안 부르는지)을 /proc/interrupts와 ftrace로 확인한다.

I check State in /proc/PID/status — S or D — then wchan, and as root /proc/PID/stack. The top frame is the driver function with the module name and an offset, so faddr2line gets me the source line. Then I check the waker side — does the IRQ handler ever call wake_up? — using /proc/interrupts and ftrace.

꼬리 질문: "S vs D?" → S는 시그널로 깰 수 있고 D는 못 깬다. D가 120초 넘으면 hung task 경고.

Q. "debugfs vs sysfs vs procfs — which do you use for what?"

A. sysfs는 디바이스 모델과 안정 ABI(값 하나 = 파일 하나), procfs는 프로세스와 오래된 전역 통계, debugfs는 개발자용으로 형식 약속이 없다. bring-up 때 가장 유용한 clk·regulator·pinctrl·gpio·regmap 정보는 debugfs에 있어서, 양산 이미지에서도 디버그 빌드로 쉽게 바꿀 수 있게 만들어 둔다.

sysfs is the device model and a stable ABI, one value per file. procfs is per-process info plus legacy global statistics. debugfs is for developers with no format guarantees. The most useful bring-up views — clocks, regulators, pinctrl, GPIO, regmap — live in debugfs, so I make sure we can easily boot a debug build on production hardware.

  1. (개념) /proc/iomem에서 어떤 장치의 바깥 줄은 있는데 안쪽 줄이 없다. 무슨 뜻인가? 정답/힌트: DT·버스가 영역을 선언했지만 드라이버가 request_mem_region()(=devm_ioremap_resource)으로 잡지 않았다 — 드라이버가 bind 안 됐거나 ioremap만 직접 썼다.
  2. (관찰) 예제 3에서 gpio-sim 칩을 만들기 전에 echo m2_cons > /sys/bus/platform/drivers/m2_cons/bind를 하면 어떤 오류 문자열이 나오나? 정답/힌트: 직접 확인할 것(이 노트에서는 실행하지 않았다). -517(EPROBE_DEFER)은 유저 errno 표에 없는 커널 내부 값이라 셸에서 Unknown error 517처럼 보일 수 있다는 점을 생각해 본다.
  3. (코드) m2_defer의 GPIO_ACTIVE_LOW를 GPIO_ACTIVE_HIGH로 바꾸고 다시 빌드해, debugfs gpio의 reset 줄이 output-low로 바뀌는지 확인하라. 정답/힌트: 논리 0 요청 + active-high = 물리 low. debugfs는 물리 레벨을 보여 준다.
  4. (관찰) 예제 7의 IRQF_TRIGGER_RISING을 IRQF_TRIGGER_FALLING | IRQF_TRIGGER_RISING으로 바꾸면 pull-up/pull-down 세 번에 카운트가 몇이 되나? /sys/kernel/irq/N/type은? 정답/힌트: 6, type: edge(양 에지도 edge로 표시).
  5. (코드) m2_slab의 할당을 module_init이 아닌 debugfs 쓰기 핸들러로 옮기고 /proc/vmallocinfo의 호출자 칸이 심볼로 보이는지 확인하라. 정답/힌트: 비-init 함수면 leak_write+0x.../0x... [m2_slab] 형태로 나온다.
  6. (관찰) 같은 게스트를 slab_nomerge 없이, SLAB_NO_MERGE도 빼고 빌드해서 m2_obj가 slabinfo에 나오는지, /sys/kernel/slab/m2_obj가 다른 캐시를 가리키는 링크인지 확인하라. 정답/힌트: 병합되면 /sys/kernel/slab/m2_obj는 :0000192나 :a-0000192 같은 이름의 공용 캐시로 가는 심볼릭 링크가 된다(aliases 파일 값도 확인).
  7. (스크립트) §11.4의 "보드 상태 한 장" 스크립트를 짜서 trace 게스트에서 두 번(모듈 로드 전/후) 찍고 diff하라. 어느 파일이 바뀌었나? 정답/힌트: interrupts(카운트·새 줄), slabinfo, meminfo, debugfs gpio, lsmod, tainted, iomem(변화 없음 — 우리 모듈은 MMIO를 잡지 않음).

16. 요약 & 체크리스트#

bring-up 진단은 "어디를 볼지"를 아는 싸움이다. /sys의 장치·드라이버 링크로 bind 상태를, debugfs devices_deferred와 dmesg의 probe 에러로 실패 이유를, of_node와 /proc/device-tree로 DT 출처를 확인한다. 그다음 debugfs의 clk·regulator·pinctrl·gpio·regmap 요약으로 자원을, /proc/interrupts와 /proc/irq·/sys/kernel/irq로 인터럽트를 본다. 메모리는 meminfo의 SUnreclaim과 slabinfo를 맞춰 보고, buddyinfo·zoneinfo로 단편화와 여유를, vmallocinfo로 큰 버퍼를 본다. 멈춘 앱은 /proc/<pid>/stack이 드라이버의 잠든 줄을 알려 준다. 모든 표는 커널이 믿는 상태라서, 이상하면 HW를 직접 재서 교차 확인한다.
