0. 큰 그림 — 이게 왜 필요한가#

Don의 SSD 펌웨어를 떠올려 보자. main.c, nand_drv.c, nvme.c를 전부 컴파일해서 링커 스크립트로 한 번에 링크하면 firmware.elf가 나온다. 모든 함수 주소가 빌드 때 확정된다. 기능 하나를 고치려면 다시 빌드하고 다시 플래시한다.

Linux 커널도 기본은 똑같다. vmlinux(= Image)는 수천 개의 .o를 한 번에 링크한 거대한 펌웨어다. 그런데 Linux에는 실행 중인 커널에 새 코드를 끼워 넣는 장치가 하나 더 있다. 그게 로더블 커널 모듈(LKM, Loadable Kernel Module) 이고 파일 확장자는 .ko(kernel object)다.

  • .ko는 아직 링크가 덜 끝난 ELF 오브젝트다. 커널 함수(printk, kmalloc …)를 부르는 자리가 "미해결 심볼 + 재배치 항목"으로 남아 있다.
  • insmod가 이 파일을 커널에 넘기면, 커널 안의 모듈 로더(kernel/module/main.c)가 메모리를 잡고, 심볼을 커널 심볼 표에서 찾아 주소를 채우고(재배치), init 함수를 부른다. 링커가 하던 일을 커널이 런타임에 한다.
  • 올라간 모듈은 커널과 같은 주소 공간, 같은 특권(EL1) 에서 돈다. 유저 프로세스처럼 격리된 게 아니다. 모듈의 NULL 역참조는 곧 커널 Oops다.

그림 1 — 왼쪽은 Don이 아는 펌웨어 빌드, 오른쪽은 Linux 모듈. 모듈 로더는 "커널 안에 들어 있는 링커 + 로더"다.

모듈을 쓰는 이유는 실무적이다.

이유장면
개발 속도드라이버 하나 고칠 때마다 커널 전체를 다시 굽고 재부팅하지 않는다. rmmod → 빌드 → insmod로 몇 초 만에 반복한다
이미지 크기·부팅 시간배포판 커널은 수천 개 드라이버를 =m으로 두고 장치가 있을 때만 올린다 (D3 §9의 modalias 자동 로딩)
하드웨어 변형같은 rootfs를 IMU 칩이 다른 보드 리비전 두 개에 쓴다. 맞는 모듈만 로드된다
벤더 코드GPU·Wi-Fi·NPU 벤더는 드라이버를 out-of-tree .ko로 준다. 이걸 우리 커널에 맞춰 빌드하는 게 BSP 엔지니어의 일상이다

이 노트에서는 실제로 모듈 9개(e3_hello, e3_multi, e3_param, e3_fail, e3_hold, e3_lib, e3_user, e3_prop, 실패용 e3_nolic)를 만들어 QEMU 게스트 커널에 넣고 빼면서 모든 규칙을 눈으로 확인한다.

실행 환경: 빌드는 Lima VM elinux(aarch64, 호스트 커널 uname -r = 7.0.0-38-generic)에서 랩의 커널 빌드 트리 /var/lab/out/linux-build(Linux 6.18.55, Module.symvers 있음)를 대상으로 했다. 실행은 전부 QEMU virt(cortex-a57, 512 MB, TCG)로 부팅한 게스트 커널 6.18.55 + BusyBox 1.37 initramfs 안이다. VM 호스트 커널(7.0)에는 모듈을 하나도 넣지 않았다. 커널 소스 인용은 /var/lab/src/linux-6.18.55에서 grep으로 확인했다. 모듈 주소·타임스탬프·umod= 포인터는 실행마다 다르다.

0.1 실습 도구 — 빌드하고 QEMU에 넣는 두 스크립트#

모든 예제는 같은 방식으로 돈다. VM의 /var/tmp/E3/ 아래에서 모듈을 빌드하고, 랩 rootfs를 복사해 .ko와 게스트용 스크립트를 넣고, LAB_CMD=sh~/e3/tN.sh로 부팅하면 스크립트 하나를 실행하고 자동으로 꺼진다.

quiet라서 콘솔에는 pr_warn/pr_err급 메시지만 섞여 나오고, pr_info는 스크립트 안에서 dmesg로 꺼내 본다. 게스트에는 /lib/modules가 비어 있고(랩 README: 랩 커널의 .ko는 initramfs에 설치되지 않음), 우리가 넣은 것만 있다.

1. 모듈의 해부 — hello 모듈 한 개#

1.1 직관#

펌웨어의 드라이버 모듈은 보통 xxx_init()과 (가끔) xxx_deinit()을 가진다. main()이 순서대로 init을 부른다. 커널 모듈도 같다. 차이는 누가 init을 부르느냐다. 모듈은 main()이 없고, "로드될 때 이걸 불러 줘", "빠질 때 이걸 불러 줘" 라고 두 함수를 커널에 등록만 한다.

1.2 예제 1 — e3_hello.c와 out-of-tree Makefile#

무엇을 확인하나: 모듈이 가져야 할 최소 구성 — init/exit 함수, module_init/module_exit 등록, __init/__exit 섹션 표시, 메타데이터 매크로 — 와 커널 트리 밖에서 빌드하는 Makefile.

출력에서 볼 것: 경고 0개. CROSS_COMPILE을 안 줬는데도 되는 것은 VM이 arm64이고 대상 커널도 arm64이기 때문이다(x86 PC에서 보드용으로 빌드하면 ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-가 필요하다, B1). 빌드는 4단계다: 내 .c → .o, modpost(심볼·라이선스 검사, .mod.c 생성), .mod.c → .mod.o, 그리고 셋을 묶어 .ko.

코드 한 줄씩:

요소뜻빠뜨리면
module_init(fn)"로드되면 fn을 불러라". 모듈로 빌드되면 fn의 별칭 init_module을 만든다init이 안 불린다(로드는 됨)
module_exit(fn)"언로드할 때 fn을 불러라". 별칭 cleanup_modulermmod 불가 — [permanent] (§4)

1.3 out-of-tree 빌드는 어떻게 굴러가나#

make -C $(KDIR) M=$(CURDIR) modules는 "커널 빌드 트리로 가서(-C), 외부 디렉터리(M=)의 모듈을 빌드해라"다. 커널의 최상위 Makefile이 우리 디렉터리의 Makefile(또는 Kbuild 파일)을 Kbuild 문법으로 다시 읽어서 obj-m 목록을 얻는다. 그래서 같은 파일 안에 "사람이 치는 make 규칙(all:)"과 "Kbuild가 읽는 obj-m"이 같이 있다. 큰 프로젝트는 둘을 나눠 Kbuild 파일에 obj-m만 두기도 한다.

그림 2 — out-of-tree 빌드. 모듈은 반드시 대상 커널의 빌드 트리(같은 .config, 같은 헤더, 같은 Module.symvers)로 빌드해야 한다. 다른 트리로 빌드한 .ko는 §10의 vermagic 검사에서 튕긴다.

빌드 트리에 무엇이 있어야 하나: 전체 커널 빌드 결과까지는 필요 없고 make modules_prepare(설정 헤더·scripts/mod/modpost 같은 도구 생성)면 빌드는 된다. 다만 Module.symvers가 없으면 modpost가 커널 심볼의 존재·GPL 여부를 검사하지 못해 경고가 쏟아진다. 랩은 make modules까지 돌려서 Module.symvers(20,778줄)가 있다. 데스크톱 배포판에서는 이 역할을 /lib/modules/$(uname -r)/build 심볼릭 링크(→ linux-headers 패키지)가 한다.

2. .ko 안에는 무엇이 들어 있나#

2.1 예제 2 — modinfo와 .mod.c#

무엇을 확인하나: modinfo가 보여 주는 키들이 소스의 어느 매크로에서, 또는 빌드 시스템의 어느 단계에서 왔는지.

출력에서 볼 것: modinfo는 마법이 아니라 .modinfo 섹션의 key=value\0 문자열들을 읽어서 보여 줄 뿐이다(strings로도 그대로 보인다). 각 키의 출처:

키누가 넣나쓰임
license, author, description, version내 소스의 MODULE_* 매크로license는 커널이 GPL 심볼 허용·taint 판단에 쓴다
parmMODULE_PARM_DESC + module_param의 타입사람용 문서 (§5)
aliasMODULE_DEVICE_TABLEmodprobe 자동 로딩 (D3 §9)
name.mod.c의 MODULE_INFO(name, KBUILD_MODNAME)모듈 이름 = 파일 이름에서 -를 _로
dependsmodpost가 "다른 모듈에서 가져다 쓰는 심볼"을 보고 계산depmod가 의존성 색인에 씀 (§11)
srcversionmodpost가 소스 파일들의 해시로 계산 (MODULE_VERSION이 있거나 CONFIG_MODULE_SRCVERSION_ALL일 때)"같은 버전 문자열인데 소스가 다른" 빌드를 구분
vermagicscripts/module-common.c의 MODULE_INFO(vermagic, VERMAGIC_STRING) → .module-common.o로드 때 커널과 비교 (§10)
intree커널 트리 안에서 빌드될 때만 Y없으면 taint O (§9)

.mod.c가 핵심이다. modpost가 만들어 주는 이 C 파일이 struct module __this_module을 .gnu.linkonce.this_module 섹션에 정의하고, 그 .init/.exit 필드에 init_module/cleanup_module(= module_init/module_exit가 만든 별칭)을 꽂는다. 커널 로더는 이 섹션을 찾아 struct module로 쓴다. 즉 THIS_MODULE은 이 __this_module의 주소다.

vermagic의 6.18.55 SMP preempt mod_unload aarch64는 커널 버전 + 핵심 설정(SMP, 선점 모델, 언로드 지원, 아키텍처)이다. 이 값들이 다르면 struct module 배치나 락 구현이 달라져서 모듈이 커널 자료구조를 잘못 읽게 된다.

2.2 예제 3 — __init이 정말 다른 섹션에 들어가나#

무엇을 확인하나: __init/__exit가 붙은 함수가 어느 섹션에 있고, init_module이 정말 같은 함수의 별칭인지.

출력에서 볼 것:

  • e3_hello_init(56바이트)은 섹션 10 = .init.text, e3_hello_exit(44바이트)은 섹션 12 = .exit.text. 일반 .text는 크기 0이다(이 모듈엔 다른 함수가 없다).
  • init_module과 e3_hello_init이 같은 섹션·같은 크기다 — module_init() 매크로가 만든 별칭이다. 6.18 include/linux/module.h(모듈 빌드 쪽 정의)는 이렇다:

__inittest는 "initfn이 int (*)(void) 타입인가"를 컴파일 때 검사하는 장치이고, ___ADDRESSABLE이 위 심볼 표의 __UNIQUE_ID___addressable_init_module413을 만든다. 모듈 빌드에서는 late_initcall(fn)·subsys_initcall(fn)도 전부 module_init(fn)으로 바뀐다(같은 헤더) — 모듈에는 initcall 레벨이 없다.

  • 모든 주소가 0이다. 아직 링크(재배치)가 안 끝난 relocatable ELF라서다. .rela.init.text가 "이 위치에 _printk 주소를 채워 넣어라" 같은 재배치 목록이다. 이 빈칸을 채우는 게 커널 로더의 일이다(§13).
  • .gnu.linkonce.this_module이 0x480 = 1152바이트 = sizeof(struct module)이다.

2.3 .ko 크기 — 파일 38 KB 중 실제 메모리에 올라가는 것은?#

readelf -SW 섹션 크기를 Python으로 분류하고(.debug_*와 그 .rela를 묶음), strip --strip-debug 결과와 게스트의 /sys/module/e3_hello/coresize를 같이 놓았다.

그림 3 — e3_hello.ko의 81%는 디버그 정보다. 실제 코드는 104바이트. 메모리에는 디버그 정보가 안 올라가지만, CONFIG_STRICT_MODULE_RWX=y라서 코드(RX)·읽기 전용(RO)·데이터(RW)를 페이지 단위로 따로 잡아 최소 3페이지 = 12,288바이트가 된다(coresize는 §3 예제 4의 실제 값).

실무 연결: 제품 rootfs에 모듈을 넣을 때는 make INSTALL_MOD_STRIP=1 modules_install로 디버그 정보를 빼서 넣는다(Yocto·Buildroot가 기본으로 한다). 크래시 분석용으로는 strip 안 한 .ko를 따로 보관한다 — 펌웨어에서 .elf는 보관하고 .bin만 굽는 것과 같다.

3. 넣고, 보고, 빼기 — insmod · lsmod · rmmod#

3.1 예제 4 — QEMU 게스트에서 hello 모듈의 한 생애#

무엇을 확인하나: 로드 후 /sys/module/<이름>/에 생기는 것들, /proc/kallsyms에서 __init 함수가 사라지는 것, lsmod = /proc/modules, 언로드 후 흔적.

(ls의 색 코드는 지웠다. 이후 스크립트는 ls --color=never를 쓴다.)

출력에서 볼 것:

  • init 중 state=1, exit 중 state=2. enum module_state는 LIVE=0, COMING=1, GOING=2, UNFORMED=3이다(include/linux/module.h). init이 도는 동안은 아직 LIVE가 아니다.
  • initsize: 0, kallsyms에 e3_hello_init이 없다. do_init_module()이 init 성공 직후 .init.* 영역을 해제하고 kallsyms를 "core 심볼만" 쓰도록 바꾼다. sections/ 디렉터리에는 .init.text 항목이 남아 있지만 그 메모리는 이미 반납됐다. 그래서 __init 함수를 init 이후에 부르면(예: 콜백으로 등록해 두면) 해제된 메모리로 점프한다. 커널은 빌드 때 modpost의 section mismatch 검사로 이것을 잡아 준다.
  • taint: O, tainted: 4096 = 비트 12 = O(out-of-tree). 첫 out-of-tree 모듈이 올라오는 순간 loading out-of-tree module taints kernel.이 한 번 찍힌다. §9에서 해독한다.
  • lsmod의 BusyBox 출력은 /proc/modules를 그대로 보여 준다. 칸의 뜻: 이름, 크기(coresize), refcount, 사용하는 모듈 목록(- = 없음), 상태(Live/Loading/Unloading), 기준 주소, taint 플래그. 데스크톱 kmod lsmod는 같은 파일을 Module Size Used by 3칸으로 예쁘게 보여 줄 뿐이다.
  • rmmod 후 /sys/module/e3_hello가 사라졌다. 그런데 taint는 남는다. 한 번 오염된 커널은 재부팅 전까지 계속 O다.

  • e3_user does not use e3_lib! → Allocating new usage for e3_user.: ref_module()이 "아직 의존 기록이 없으니 새로 만든다"는 뜻이다. 이 순간 e3_lib의 refcount가 1이 되고 holders/e3_user가 생긴다.
  • kallsyms에서 e3_lib_plain만 T(전역)이고 나머지는 t다. 내보내기 여부는 T/t가 아니라 __ksymtab_<이름> 항목의 존재로 판단한다. /proc/kallsyms는 디버깅용 전체 심볼 목록이고, 다른 모듈이 링크할 수 있는 것은 __ksymtab에 있는 것뿐이다.

11. modprobe와 depmod — 의존성을 알아서#

11.1 직관#

insmod는 경로를 받아 그 파일 하나를 넣는다. 의존 모듈은 신경 쓰지 않는다(그래서 §7에서 순서를 틀리자 실패했다). modprobe는 이름을 받아 /lib/modules/$(uname -r)/에서 파일을 찾고, 의존 모듈을 먼저 넣는다. 그러려면 "누가 누구에게 의존하는가" 색인이 필요하다. 그 색인을 만드는 도구가 depmod다. 펌웨어로 치면 링커 맵에서 init 순서를 미리 계산해 표로 만들어 두는 것이다.

11.2 예제 13 — BusyBox depmod/modprobe로 의존 모듈 자동 로드#

무엇을 확인하나: /lib/modules/6.18.55/extra/에 .ko를 두고 depmod → modprobe e3_user 한 번에 e3_lib까지 올라오는지, modprobe -r이 의존 모듈까지 내리는지, 그리고 커널 명령줄의 모듈 옵션을 BusyBox modprobe가 읽는지.

출력에서 볼 것:

  • modprobe e3_user 한 줄에 e3_lib가 먼저 올라왔다. modprobe -r e3_user는 쓰는 모듈이 없어진 e3_lib까지 내렸다(lsmod가 비었다).
  • BusyBox의 색인은 modules.dep.bb 한 파일이다(이 BusyBox는 CONFIG_MODPROBE_SMALL=y). 모듈마다 "파일 경로 [alias/symbol 목록]" 줄 + "의존 모듈 이름" 줄 + 빈 줄. e3_lib 줄의 symbol:e3_lib_add는 "이 심볼이 필요하면 이 모듈을 넣어라"는 색인이다.
  • depmod 전에 이미 modules.dep.bb가 있었다. 이 rootfs에는 우리가 만든 적이 없으니, 부팅 중 커널이 request_module()로 /sbin/modprobe(= /proc/sys/kernel/modprobe)를 부른 적이 있고, modprobe-small이 색인이 없을 때 전체를 스캔하며 만들어 둔 것으로 보인다(BusyBox modprobe-small.c 주석: "This will generate modules.dep.bb as a side effect").
  • 커널 명령줄의 e3_param.count=7은 BusyBox modprobe가 적용하지 않았다(count=1). kmod modprobe는 /proc/cmdline에서 <모듈>.<파라미터>= 항목을 찾아 옵션으로 붙여 준다. 그리고 insmod는 어느 쪽이든 명령줄을 보지 않는다. 장비에서 "명령줄에 넣었는데 안 먹어요"의 흔한 원인이다. 확실한 방법은 /etc/modprobe.d/*.conf의 options e3_param count=7(kmod)이다.

11.3 데스크톱·Yocto의 kmod depmod는 무엇을 만드나#

비교를 위해 같은 .ko들을 VM 호스트의 kmod depmod(kmod 34.2)로 별도 디렉터리에 색인했다. 이건 파일만 읽고 쓰는 작업이라 호스트 커널에 아무것도 넣지 않는다.

출력에서 볼 것:

  • modules.dep의 형식은 모듈: 의존1 의존2. --show-depends가 실제로 할 insmod 순서를 보여 준다 — 의존 모듈이 먼저. (ls 목록의 ...는 modules.builtin.* 세 줄을 생략한 곳이다.)

16. 면접에서 이렇게 말한다#

Q. Write a minimal "hello world" kernel module on the whiteboard and explain each line.

A. 헤더 두 개(linux/module.h, linux/init.h), __init이 붙은 static int init 함수가 pr_info 후 0을 반환, __exit이 붙은 static void exit 함수, module_init/module_exit로 등록, MODULE_LICENSE("GPL")과 MODULE_DESCRIPTION. 그리고 obj-m := hello.o와 make -C <커널 빌드 트리> M=$PWD modules Makefile까지 쓴다. 각 줄의 의미: __init은 로드 후 메모리 해제, 반환값은 0 또는 음수 errno, 라이선스는 GPL 전용 심볼 접근과 taint를 결정한다.

Two headers, an init function marked __init that returns 0 on success or a negative errno, an exit function marked __exit, module_init and module_exit to register them, and MODULE_LICENSE. The Makefile is just obj-m := hello.o, and I build it with make -C pointing at the target kernel's build tree and M equal to the current directory. __init puts the function in .init.text, which the kernel frees right after init succeeds. The license matters: without a GPL-compatible one, modpost refuses GPL-only symbols and the kernel is tainted. On a 6.18 kernel a missing MODULE_LICENSE is actually a build error.

꼬리 질문: "exit을 안 쓰면?" → 로드는 되지만 [permanent]가 되어 rmmod가 -EBUSY로 거절된다.

Q. What is the difference between insmod and modprobe?

A. insmod는 파일 경로 하나를 받아 그 모듈만 넣는다. 의존성을 모른다. modprobe는 이름(또는 alias)을 받아 /lib/modules/$(uname -r)에서 찾고, depmod가 만든 modules.dep을 보고 의존 모듈을 먼저 넣는다. /etc/modprobe.d의 options·blacklist도 적용하고, kmod 버전은 커널 명령줄의 mod.param=도 읽는다. udev 자동 로딩도 modalias로 modprobe를 부른다.

insmod takes a path and loads exactly that file; it knows nothing about dependencies, so if a symbol provider isn't loaded you get "Unknown symbol". modprobe takes a module name or an alias, looks it up under /lib/modules for the running kernel, and uses the modules.dep index built by depmod to load dependencies first. It also applies options and blacklists from /etc/modprobe.d. udev uses modprobe with the device's modalias for automatic loading.

Q. What happens inside the kernel when you insmod a module?

A. finit_module(또는 init_module) → load_module(). 서명 검사, ELF 검증, vermagic 비교, core·init 영역을 따로 할당해 섹션 복사, UNFORMED로 목록 등록, taint 판정, 미해결 심볼을 커널·모듈 심볼 표에서 해석(GPL·네임스페이스 검사, 의존 기록), 재배치 적용, 메모리 권한 설정(text RO+X, data NX), 파라미터 파싱, sysfs 생성, 마지막으로 do_init_module()이 init을 부르고 성공하면 LIVE로 바꾸고 init 영역을 해제한다. 요컨대 커널 안에 있는 런타임 링커 + 로더다.

The syscall goes into load_module. It checks the signature if enabled, validates the ELF, compares vermagic, lays out and allocates separate core and init regions, adds the module to the list as UNFORMED, applies taints, resolves undefined symbols against the kernel and other modules' export tables — checking GPL-only and namespaces and recording the dependency — applies relocations, sets memory permissions, parses parameters, creates the sysfs directory, and finally do_init_module calls the init function. On success the state becomes LIVE and the init sections are freed. It's basically a runtime linker and loader inside the kernel.

Q. EXPORT_SYMBOL vs EXPORT_SYMBOL_GPL — and what are symbol namespaces?

A. 둘 다 심볼을 커널 심볼 표에 올려 다른 모듈이 링크하게 한다. _GPL은 GPL 호환 라이선스 모듈만 쓸 수 있다. 빌드 때 modpost가 에러로 막고, 런타임에도 비GPL 모듈에는 그 심볼이 안 보여 Unknown symbol이 된다 — 직접 확인했다. 네임스페이스는 EXPORT_SYMBOL_NS_GPL(f, "NS")로 내보내고 쓰는 쪽이 MODULE_IMPORT_NS("NS")를 선언해야 하는 장치로, 서브시스템 내부 API가 아무 드라이버에서나 쓰이는 걸 막는다. 6.13부터 인자가 문자열 리터럴이다.

Both put the symbol into the kernel's export table so other modules can link against it. The GPL variant is only usable by modules with a GPL-compatible license — modpost rejects it at build time, and at load time the symbol is simply invisible to a non-GPL module, so you get Unknown symbol. Namespaces add another gate: the exporter uses EXPORT_SYMBOL_NS_GPL with a namespace string, and the user must declare MODULE_IMPORT_NS with the same string, otherwise modpost fails. Since 6.13 the namespace argument is a string literal.

Q. How does the kernel prevent a module from being unloaded while it's in use?

A. 모듈 refcount다. 다른 모듈이 내 심볼을 쓰면 로드 때 ref_module()이 refcount를 올리고 holders에 기록한다. 장치 파일을 열면 VFS가 fops_get()으로 try_module_get(fops->owner)를 한다 — 그래서 .owner = THIS_MODULE이 중요하다. delete_module()은 holders가 있거나 refcount가 0이 아니면 EAGAIN, exit 함수가 없으면 EBUSY로 거절한다. kmod rmmod는 이걸 "Module is in use"로 보여 준다.

With the module reference count. When another module links against my symbols, ref_module takes a reference and records it in holders. When user space opens my device file, the VFS calls try_module_get on fops->owner — which is why .owner = THIS_MODULE matters. delete_module refuses with EAGAIN if there are holders or a non-zero refcount, and with EBUSY if the module has an init but no exit. If I hold a function pointer from another module for later use, I wrap the call in try_module_get and module_put on that module's owner.

꼬리 질문: "try_module_get이 실패하는 경우는?" → 그 모듈이 GOING(언로드 중)일 때. 그래서 try다.

Q. Your module's init fails halfway through. What happens, and how do you write it?

A. init이 음수 errno를 돌려주면 커널은 상태를 GOING으로 바꾸고 바로 free한다. exit은 불리지 않는다. 그래서 init 안에서 이미 획득한 자원을 역순으로 풀어야 하고, 커널 관용구는 goto 라벨 사다리다. 반환한 errno는 insmod 메시지가 된다(-ENODEV → "No such device"). 드라이버 probe에서는 devm 자원으로 사다리를 줄일 수 있다.

The kernel marks it GOING and frees it immediately, and the exit function is not called. So init must undo whatever it already acquired, in reverse order. The idiom is a goto ladder: each failure jumps to the label that releases everything acquired before it. The negative errno propagates to user space, so -ENODEV shows up as "No such device" in insmod. In probe functions I prefer devm-managed resources, which the driver core releases automatically.

Q. What does "tainted kernel" mean? What are O, P and E?

A. 커널이 "지원 범위 밖의 일이 있었다"고 기록하는 비트마스크로, /proc/sys/kernel/tainted와 Oops의 Tainted: 줄에 나온다. O는 트리 밖에서 빌드된 모듈(intree 없음), P는 GPL 호환이 아닌 라이선스(P가 붙으면 lockdep도 꺼진다), E는 서명 검증이 켜진 커널에서 서명 없는 모듈. 고장이라는 뜻이 아니라, 버그 리포트를 볼 때 "재현 가능한 소스만으로 이뤄진 커널인가"를 알려 주는 이력이다.

It's a bitmask recording that something outside the supported envelope happened, shown in /proc/sys/kernel/tainted and in the Tainted line of an oops. O means an out-of-tree module was loaded, P a module with a non-GPL-compatible license — which also disables lock debugging — and E an unsigned module on a kernel with signature checking. It doesn't mean the kernel is broken; it tells whoever reads the bug report that code without available source or outside mainline was involved.

Q. Built-in versus loadable module — how do you decide, and what changes in the code?

A. 코드는 같다. =y면 module_init이 device_initcall이 되어 부팅 중에 불리고, exit 코드는 버려지며, 파라미터는 커널 명령줄 name.param=으로 준다. =m이면 insmod 때 불리고 rmmod로 뺄 수 있다. rootfs 마운트 전에 필요하거나(스토리지, 콘솔, 인터럽트 컨트롤러) 부팅 시간 예산 안에 꼭 떠야 하는 건 built-in, 나머지는 모듈로 둬서 이미지를 작게 하고 개발 중 교체를 쉽게 한다.

The source is the same. Built in, module_init becomes a device_initcall that runs during boot, the exit path is discarded, and parameters come from the kernel command line as module.param. As a module, init runs at insmod and the code can be unloaded and replaced. Anything needed before the root filesystem is mounted — storage, console, the interrupt controller — or anything with a hard boot-time deadline goes built in; the rest stays modular for a smaller image and faster iteration.

19. 요약 & 체크리스트#

모듈은 "실행 중인 커널에 런타임 링크되는 재배치 가능한 ELF"다. 소스는 init/exit 두 함수와 메타데이터 매크로로 이뤄지고, 대상 커널의 빌드 트리로 make -C <KDIR> M=$PWD해서 만든다. 빌드 때 modpost가 심볼 존재·GPL·네임스페이스·라이선스를 미리 검사하고, 로드 때 load_module()이 vermagic·서명을 확인한 뒤 메모리를 잡고 심볼을 해석·재배치하고 init을 부른다. 모듈 사이 함수 호출은 EXPORT_SYMBOL(_GPL/_NS)로만 되며, 의존 관계와 열린 파일은 refcount로 언로드를 막는다. init이 실패하면 exit은 불리지 않으니 goto 사다리로 스스로 정리한다. modprobe는 depmod 색인으로 의존 모듈을 먼저 넣는다. 같은 소스를 =y로 빌드하면 module_init은 initcall이 되고 파라미터는 커널 명령줄로 간다.
