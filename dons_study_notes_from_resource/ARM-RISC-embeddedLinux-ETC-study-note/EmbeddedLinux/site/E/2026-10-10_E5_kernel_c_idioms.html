0. 큰 그림 — 이게 왜 필요한가#

1. container_of — 멤버 포인터에서 바깥 구조체 찾기#

1.1 직관: "필드 주소에서 오프셋을 빼면 구조체 시작 주소"#

Don이 SSD 펌웨어에서 NAND 명령 큐를 만들 때를 떠올려 보자. 명령 디스크립터 struct nand_cmd 안에 큐 링크 필드가 있고, 큐에서 꺼낸 건 링크 필드의 주소다. 이걸 다시 struct nand_cmd *로 바꾸려면? 링크 필드가 구조체 첫 멤버라면 그냥 캐스트하면 되고, 아니라면 "링크 필드 주소 − 링크 필드의 오프셋"을 계산해야 한다. FreeRTOS는 이 문제를 ListItem_t 안에 pvOwner라는 역포인터를 하나 더 둬서 풀었다(포인터 8바이트를 더 쓰는 대신 계산이 없다). 리눅스는 역포인터 없이 컴파일 타임 상수 오프셋 빼기로 푼다. 그게 container_of다.

정의를 한 문장으로: container_of(ptr, type, member)는 "ptr이 type 구조체 안의 member 필드를 가리킨다면, 그 type 구조체의 시작 주소"를 돌려준다.

1.5 커널의 진짜 정의 — 랩 소스에서 보기#

한 줄씩 읽으면:

  • void *__mptr = (void *)(ptr); — ptr을 한 번만 평가한다(매크로 인자에 p++ 같은 부작용이 있어도 안전). 커널은 GNU C라서 void * 산술이 1바이트 단위로 허용되므로 char * 대신 void *에서 바로 뺀다.
  • static_assert(__same_type(...) || __same_type(*(ptr), void), ...) — 예제 1에서 본 타입 검사. void *를 넘기는 것은 예외로 허용한다(콜백의 void *data에서 꺼낼 때). __same_type은 include/linux/compiler_types.h에 __builtin_types_compatible_p(typeof(a), typeof(b))로 정의돼 있다.
  • 주석 "WARNING: any const qualifier of @ptr is lost" — const struct device *를 넣어도 struct imu_priv *(const 아님)가 나온다. 그래서 6.18 소스는 "새 코드에서는 container_of_const()를 써라"라고 적어 두었다. _Generic으로 입력이 const면 const 포인터를 돌려준다. 실제로 6.18의 kobj_to_dev()는 container_of_const(__kobj, struct device, kobj)로 정의돼 있다(§7).

2. list_head — 링크를 객체 안에 넣는 intrusive 리스트#

2.1 직관: "링크 필드를 구조체에 박아 두고, 리스트는 링크끼리만 잇는다"#

교과서 링크드 리스트(그리고 C++ std::list)는 리스트 노드가 데이터를 품거나 가리킨다: struct node { struct node *next; void *data; }. 커널은 반대로 데이터가 링크를 품는다: 데이터 구조체 안에 struct list_head { struct list_head *next, *prev; }를 멤버로 두고, 리스트는 그 list_head끼리만 잇는다. 링크에서 데이터로 돌아갈 때는 §1의 container_of를 쓴다. 이걸 intrusive list(침투형 리스트)라고 한다.

Don의 펌웨어 경험으로 치면, NAND 명령 디스크립터 풀(pool)에서 디스크립터 안에 next 필드를 두고 free list / pending list / done list 사이를 옮기던 방식이 정확히 이것이다. 리스트에 넣는다고 메모리를 새로 할당하지 않는다.

list_for_each_entry_safe(pos, n, head, member)다음 원소를 n에 미리 저장하며 순회순회 중 pos 삭제 가능
list_splice(_init)(list, head)리스트 통째로 붙이기락 안에서 떼어 와 락 밖에서 처리하는 패턴

랩 소스에서 핵심 두 함수와 두 매크로를 보자.

읽을 점:

  • __list_add의 마지막 줄만 WRITE_ONCE다. 새 노드를 완성한 뒤 마지막에 prev->next를 한 번에 써서, 락 없이 앞으로만 읽는 RCU 독자가 반쯤 만든 노드를 보지 않게 한다(§5.6 미리보기). __list_add_valid는 CONFIG_LIST_HARDENED/CONFIG_DEBUG_LIST가 꺼져 있으면 항상 true인 인라인이다(랩 커널은 둘 다 꺼짐).
  • list_del은 뺀 노드의 next/prev를 LIST_POISON1/LIST_POISON2로 덮는다. include/linux/poison.h에서 ((void *) 0x100 + POISON_POINTER_DELTA), 0x122 + ...이고 arm64는 CONFIG_ILLEGAL_POINTER_VALUE=0xdead000000000000이므로 실제 값은 0xdead000000000100과 0xdead000000000122다. 유저 공간도 커널 공간도 아닌 주소라서 접근하면 반드시 fault가 난다. 예제 6에서 이 숫자를 oops에서 다시 만난다.
  • list_for_each_entry는 pos를 바깥 객체 포인터로 두고, 다음 단계에서 pos->member.next를 읽는다. 그러니 몸통에서 pos를 지우면 다음 단계가 poison(또는 해제된 메모리)을 읽는다. _safe는 다음 원소를 n에 미리 빼 둔다.
  • 종료 조건 list_entry_is_head는 "&pos->member == head"다. 머리는 바깥 객체가 아니므로 pos는 마지막에 "머리를 바깥 객체로 착각한 가짜 포인터"가 된다 — 루프가 끝난 뒤 pos를 쓰면 안 되는 이유다.

2.3 예제 4 — userspace로 list_head 다시 만들기 (화이트보드용)#

무엇을 확인하나: 커널 list.h의 핵심(머리 초기화, add, add_tail, del + poison, for_each_entry, _safe)을 60줄 안에 다시 만들고, 센서 샘플 6개를 큐에 넣은 뒤 음수 샘플을 지운다. 같은 객체를 두 번째 리스트(alarm)에도 넣는다. 인자 bug를 주면 non-safe 순회로 지운다.

출력에서 볼 것:

  • queue는 list_add_tail이라 넣은 순서(FIFO), alarms는 list_add라 역순(LIFO: 5가 먼저).
  • _safe 버전은 음수 3개(0, 1, 2)를 지우고 3, 4, 5만 남겼다.
  • bug 모드는 첫 삭제 직후 segfault(종료 코드 139 = 128 + SIGSEGV 11). 어디서 죽었는지 gdb로 보자.

출력에서 볼 것: fault 주소가 우리가 넣은 poison 0x100 근처가 아니다. x0 = 0xb341…8180은 무작위처럼 보이는 값이고, fault 주소 …817c = x0 − 8(node 오프셋) + 4(accel_mg 오프셋)이다. 즉 "다음 원소"를 x0에서 계산했다. 그런데 x0는 어디서 왔나? 버그 코드는 list_del → free(s) → (루프 증가식에서) s->node.next 읽기 순서다. glibc의 free는 해제한 청크의 앞 16바이트에 tcache 메타데이터(다음 free 청크 포인터와 무작위 tcache key)를 쓰는데, node.next가 정확히 오프셋 8 — key 자리 — 라서 poison이 key로 덮였다. 해제 후 사용(use-after-free)은 무엇을 읽을지 할당자에 달려 있다 — 이번엔 즉시 죽었지만 다른 할당자·다른 크기라면 그럴듯한 포인터를 읽고 조용히 계속 갈 수도 있다. 커널에서 같은 일을 하면 어떻게 되는지 예제 6에서 본다(그쪽은 kfree 없이 list_del만 해서 poison이 그대로 보이게 했다).

화이트보드에서 외울 것은 네 줄이다: __list_add의 포인터 4개 대입 순서, list_add = __list_add(new, head, head->next), list_add_tail = __list_add(new, head->prev, head), list_del = prev->next = next; next->prev = prev. 나머지는 이 넷과 container_of의 조합이다.

2.4 예제 5 — 커널 모듈: 센서 샘플 큐 + hlist 해시#

무엇을 확인하나: 커널의 진짜 list.h와 hashtable.h로 같은 일을 한다. 샘플을 kmalloc해 큐(list_head)와 seq 해시(hlist)에 동시에 넣고, 해시로 seq=4를 찾고, _safe로 음수 샘플을 지운 뒤, rmmod 때 전부 해제한다. 모듈 파라미터 bug=1이면 non-safe 순회로 지운다.

게스트 스크립트: insmod /e5_list.ko && rmmod e5_list && dmesg | grep e5_

출력에서 볼 것: struct e5_sample은 seq(4) + accel_mg(4) + node(16) + hnode(16) = 40바이트 — 리스트 두 개에 들어가는 비용이 객체 안 32바이트뿐이고 추가 할당이 없다. hlist_head는 8바이트(포인터 하나)라서 list_head(16)의 절반이다. rmmod 때 _safe로 전부 지워 list_empty가 1.

2.5 예제 6 — 순회 중 삭제 버그를 커널에서 터뜨리고 oops 읽기#

무엇을 확인하나: 같은 모듈을 bug=1로 넣으면 커널이 어떻게 죽는지, 그리고 oops의 주소만 보고 원인을 추론할 수 있는지.

게스트 스크립트: insmod /e5_list.ko bug=1; echo "insmod exit=$?"; dmesg | grep -E "e5_list|Unable|pc :|lr :|Internal error|Call trace|list_" | head -20 (콘솔에 찍힌 oops 전체 중 핵심만 남기고 레지스터 덤프 일부를 생략했다)

이 oops를 Don이 JTAG로 data abort를 분석하듯 읽어 보자.

  1. fault 주소 dead0000000000fc — dead…로 시작하면 거의 항상 poison 값이다. LIST_POISON1 = 0xdead000000000100에서 4가 모자란다.
  2. x0 = dead000000000100 — 레지스터에 LIST_POISON1 그 자체가 있다. 방금 list_del한 노드의 next를 읽어 온 값이다(마지막 dmesg 줄 "node.next now dead000000000100"과 일치).
  3. x19 = dead0000000000f8 — container_of(0xdead…100, struct e5_sample, node) = 0x…100 − 8(node의 오프셋). 즉 다음 pos.
  4. 그 pos의 accel_mg(오프셋 4)를 읽으면 0x…0f8 + 4 = 0x…0fc — fault 주소와 정확히 일치. "삭제한 노드의 next를 따라가서 다음 원소의 필드를 읽다 죽었다."
  5. ESR의 EC = 0x25: DABT (current EL) — 커널 모드(EL1)에서 난 data abort. FSC = 0x04: level 0 translation fault — 페이지 테이블 최상위 단계에서 이미 매핑이 없다. "address between user and kernel address ranges"는 커널이 친절하게 붙인 해설이다.
  6. insmod는 Segmentation fault로 끝났다(CONFIG_PANIC_ON_OOPS가 꺼져 있어 커널은 살아 있지만, 이 모듈은 반쯤 초기화된 상태로 남아 이후 rmmod도 못 한다 — 실제 장비라면 재부팅).

덤: x24 = 0000000061c88647은 include/linux/hash.h의 GOLDEN_RATIO_32(hash_32()가 곱하는 상수)다. 직전의 hash_add/hash_for_each_possible이 레지스터에 남긴 값으로 보인다.

kfree까지 했다면(예제 4처럼) poison 대신 해제된 메모리를 읽어서 가끔만 터지는 더 나쁜 버그가 된다. list_del이 poison을 쓰는 이유가 그 "가끔"을 "항상"으로 바꾸기 위해서다.

2.6 hlist — 해시 버킷용 반쪽 리스트#

해시 테이블은 버킷이 수천 개이고 대부분 비어 있다. 버킷마다 list_head(16바이트)를 두면 낭비라서 커널은 머리가 포인터 하나인 hlist를 쓴다.

  • hlist_head는 first 하나 → 8바이트. 대신 꼬리로 바로 갈 수 없다(add_tail O(1) 불가) — 해시 버킷엔 필요 없다.
  • hlist_node의 pprev는 "이전 노드" 가 아니라 "나를 가리키는 포인터의 주소"(struct hlist_node **)다. 첫 노드면 &head->first, 아니면 &prev->next. 그래서 첫 노드인지 아닌지 분기 없이 *n->pprev = n->next로 삭제된다. "포인터의 포인터로 머리 특수 경우를 없앤다"는 이 기법은 단일 연결 리스트 삭제 면접 문제의 모범 답이기도 하다(§10 드릴 2의 꼬리 질문).
  • DEFINE_HASHTABLE(name, bits)는 struct hlist_head name[1 << bits], hash_add/hash_del/hash_for_each_possible이 그 위의 얇은 래퍼다(예제 5).

2.8 예제 7 — 순회 비용 측정: intrusive vs non-intrusive#

무엇을 확인하나: 원소 2^20개(약 100만)를 순회하며 값을 더하는 시간을 두 방식으로 잰다. non-intrusive의 data는 노드와 다른 시점에 할당해 떨어진 곳에 둔다(실제로 객체가 먼저 있고 나중에 리스트에 넣는 상황). s 인자를 주면 링크 순서를 무작위로 섞어 캐시·프리페치가 못 돕게 한다. 7회 반복 중 최솟값을 출력한다.

같은 명령을 조금 전에 한 번 더 돌렸을 때는 sequential (7.49, 9.11) (5.88, 10.82) (3.77, 4.73), shuffled (335.78, 328.54) (235.42, 187.97) (395.83, 366.20)이 나왔다(괄호 = intrusive, non-intrusive). 두 번의 3회씩, 총 6회를 모아 최솟값과 중앙값을 그렸다.

그림 4 — 원소 하나 순회 비용(ns, 6회 측정의 최솟값과 중앙값). 왼쪽과 오른쪽의 세로축 단위가 30배 이상 다르다.

해석(정직하게):

  • 측정 잡음이 크다. load average 18(6코어 VM에서 다른 노트 작업이 동시에 돌았다)이라 같은 측정이 2~3배 흔들린다. 그래서 최솟값(간섭이 가장 적었던 회)을 같이 봤다.
  • sequential: intrusive가 최솟값 기준 약 1.6배(3.04 vs 4.73 ns), 중앙값 기준 약 1.5배 빠르다. non-intrusive는 원소마다 떨어진 곳의 data를 한 번 더 읽어야 해서 캐시 라인을 두 배로 쓴다.
  • shuffled: 둘 다 원소당 150~480 ns — 캐시 미스와 TLB 미스가 지배하는 포인터 추적(pointer chasing)이다. 최솟값은 거의 같은데(156.64 vs 159.65), 이유는 p->data 읽기와 p->next 읽기가 서로 의존하지 않아 CPU가 두 미스를 겹쳐서 기다릴 수 있기 때문이다(memory-level parallelism). 임계 경로는 next 사슬 하나뿐이다. 중앙값은 non-intrusive가 1.4배 느리다.
  • 결론: intrusive의 결정적인 장점은 속도보다 §2.1의 표 — 추가 할당 없음(실패 불가), 다중 소속, O(1) 삭제 — 이다. 속도 이점은 "있지만 상황에 따라 0~2배" 정도로 말하는 게 정확하다. 그리고 리스트 순회 자체가 캐시에 나쁘다는 사실이 더 크다(배열이 가능하면 배열).

2.9 함정#

  • 리스트는 스레드 안전하지 않다. list_add/list_del/순회 전부 호출자가 락(spinlock/mutex)을 잡아야 한다. 락 없이 읽으려면 RCU 버전(list_add_rcu, list_for_each_entry_rcu, list_del_rcu + synchronize_rcu/kfree_rcu) — M 모듈에서 다룬다.
  • LIST_HEAD 초기화를 빼먹음. kzalloc한 구조체의 list_head는 {NULL, NULL}이라 빈 리스트가 아니다. list_empty가 false를 돌려주고 순회가 NULL을 따라간다 → 반드시 INIT_LIST_HEAD.
  • list_del 후 list_empty(&obj->node)로 "이미 빠졌나" 검사. poison이라 false다. 그런 용도면 list_del_init.
  • 루프가 끝난 뒤 pos 사용. 찾지 못하고 끝났으면 pos는 머리를 바깥 객체로 착각한 가짜 포인터다. 찾았는지는 별도 변수(found = pos; break;)로 기록한다.
  • _safe는 "내가 pos를 지우는 것"만 안전하다. 다른 스레드가 n을 지우는 것은 막지 못한다 — 그건 락의 일이다.

3. ERR_PTR / IS_ERR / PTR_ERR — 포인터 하나에 "결과 또는 이유"를 싣기#

3.1 직관: NULL은 "왜" 실패했는지 말하지 못한다#

포인터를 돌려주는 함수가 실패하면 보통 NULL을 돌려준다. 그런데 드라이버의 probe()는 실패 이유에 따라 다르게 행동해야 한다. 예를 들어 클럭을 가져오다 실패했는데 그게 "클럭 컨트롤러가 아직 probe되지 않음(-EPROBE_DEFER)"이면 나중에 다시 시도해야 하고, "DT에 clocks 속성이 없음(-ENOENT)"이면 에러로 끝내야 한다. 펌웨어라면 int get_clk(struct clk **out)처럼 out-parameter + 에러 코드 반환으로 풀었을 것이다. 커널은 포인터 값 자체에 에러 코드를 심는다.

아이디어: 커널 주소 공간의 맨 꼭대기 4095바이트(0xfffffffffffff001 ~ 0xffffffffffffffff)에는 유효한 객체가 절대 없다. 그러니 -1 ~ -4095를 그대로 unsigned long으로 바꾼 값(2의 보수라서 바로 그 꼭대기 영역)을 "에러 포인터"로 쓰자. errno는 전부 4095 이하이므로(MAX_ERRNO) 다 들어간다.

그림 5 — 64비트 가상 주소 공간(비율 무시). 0번지(NULL)와 꼭대기 4095바이트(ERR 창)는 유효한 객체가 올 수 없는 곳이라 "특수 값"으로 쓴다. list poison(0xdead…)은 그 사이의 non-canonical 구멍을 쓴다. 오른쪽 아래는 ERR 창 안의 실제 값(예제 8, 9에서 출력한 숫자).

3.2 예제 8 — userspace에서 인코딩을 숫자로 보기#

무엇을 확인하나: 커널 err.h와 같은 정의로 errno가 어떤 주소가 되는지, 경계(-4095와 -4096)에서 IS_ERR가 어떻게 바뀌는지, NULL과 에러 포인터를 구분하는 법.

출력에서 볼 것: ERR_PTR은 아무 계산도 하지 않는 캐스트다(-22 → 0x…ffea는 2의 보수 그대로). IS_ERR는 비교 한 번. -4096(0x…f000)부터는 에러가 아니다 — 꼭대기 페이지의 시작 주소는 제외된다. NULL은 IS_ERR로 잡히지 않는다. -517(EPROBE_DEFER)은 커널 내부 전용 errno라 유저 헤더 <errno.h>에는 없다(그래서 숫자로 썼다).

3.3 커널의 정의#

  • __must_check — 반환값을 무시하면 gcc 경고(warn_unused_result). IS_ERR(p);만 쓰고 결과를 안 보면 잡힌다.
  • unlikely(...) — 에러는 드문 경로라고 컴파일러에 알려 정상 경로를 직선 코드로 배치하게 한다(§5.5).
  • __force — sparse에게 "주소 공간 표시(__iomem, __user 등)가 붙은 포인터를 넘겨도 경고하지 마라"(§6). 그래서 IS_ERR()는 void __iomem *에도 쓸 수 있다. 실제로 devm_ioremap_resource()는 IOMEM_ERR_PTR()(= (__force void __iomem *)ERR_PTR(err))로 에러를 돌려준다.

3.4 예제 9 — 커널 모듈: 내 함수와 실제 커널 API의 ERR_PTR#

무엇을 확인하나: "여러 실패 이유"를 가진 lookup 함수를 ERR_PTR로 짜고, %pe printk 포맷으로 에러 이름을 찍고, 실제 커널 API(filp_open)가 돌려주는 에러 포인터도 같은 방식으로 다룬다.

출력에서 볼 것: %pe는 에러 포인터를 받아 -EINVAL, -EPROBE_DEFER 같은 이름을 찍는다(CONFIG_SYMBOLIC_ERRNAME=y일 때. 꺼져 있으면 숫자). 드라이버 로그에 dev_err(dev, "failed to get clock: %pe\n", clk) 패턴이 흔한 이유다. 정수 에러를 찍고 싶으면 %pe에 ERR_PTR(ret)를 넘긴다. filp_open도 실패하면 NULL이 아니라 ERR_PTR(-ENOENT)(0x…fffe)를 돌려줬다. PTR_ERR_OR_ZERO(p)는 "에러면 에러 코드, 아니면 0" — return PTR_ERR_OR_ZERO(p); 한 줄로 끝내는 관용구.

3.5 규칙 — API마다 실패 표현이 다르다#

함수마다 NULL을 돌려주는지 ERR_PTR을 돌려주는지 다르고, 이걸 헷갈리는 게 가장 흔한 버그다. 문서(kernel-doc 주석의 Return: 줄)를 꼭 확인한다.

4. 에러 정리 — goto 사다리, devm_*, cleanup.h#

4.1 직관: 자원은 쌓은 역순으로 내린다#

Don이 SSD 펌웨어 초기화 코드에서 "클럭 켜기 → 전원 켜기 → PHY 초기화 → 인터럽트 등록"을 하다가 세 번째에서 실패하면, 앞의 두 개를 역순으로 끄고 나가야 했다. 리눅스 드라이버 probe()가 정확히 이 구조다. 방법은 세 가지가 있고, 모두 "획득의 역순 해제(LIFO)"라는 같은 원칙을 누가 기억하느냐만 다르다.

그림 6 — 에러 정리 세 방식. 왼쪽은 레이블을 내려가며 떨어지는(fall-through) 사다리, 가운데는 디바이스에 매달린 devres 스택, 오른쪽은 변수 스코프에 매달린 cleanup 함수.

4.2 goto 사다리 규칙#

커널 코딩 스타일 문서(Documentation/process/coding-style.rst 7장 "Centralized exiting of functions")가 권하는 형태다.

(위는 형태를 보여 주는 조각이라 단독 실행하지 않았다. 실행 가능한 같은 구조가 예제 10과 예제 11의 e5_init이다.)

  • 레이블은 무엇을 되돌리는지로 이름 짓는다(err_reg, err_clk, 또는 out_free_buf). err1, err2는 중간에 단계를 끼워 넣을 때 번호가 꼬인다.
  • 레이블은 획득의 역순으로 위에서 아래로 놓고, 아래로 떨어지며(fall-through) 앞 단계들을 차례로 되돌린다.
  • 한 함수에 return 경로가 여러 개면 정리 코드가 복제되고, 복제는 언젠가 어긋난다 — 사다리는 정리 코드를 한 곳에 모은다. Don의 펌웨어에서 do { ... } while (0) + break로 하던 것과 같은 목적이다.
  • 성공 경로는 return 0;으로 사다리 위에서 끝난다(정상 경로가 레이블을 지나가지 않게).

4.3 예제 10 — userspace: goto 사다리 vs cleanup 속성, 실패 주입#

무엇을 확인하나: 4단계 초기화를 goto 사다리로 짜고 fail_at으로 원하는 단계에서 실패시켜 되돌림 순서를 본다. 같은 일을 GCC __attribute__((cleanup(fn))) — 커널 __free()/guard()의 기반 — 으로 짜서 비교한다.

출력에서 볼 것: 사다리는 실패 지점 바로 앞 단계부터 역순으로 되돌린다(fail_at=3 → regulator, clk). cleanup 버전은 goto가 하나도 없는데, 실패든 성공이든 함수를 빠져나갈 때 선언의 역순(buf 먼저, 그다음 held)으로 정리 함수가 불렸다. 성공 경로에서도 buf가 해제된 점에 주의 — 성공 시 버퍼를 호출자에게 넘기려면 커널의 no_free_ptr()/return_ptr()로 "소유권을 빼 간다"고 표시해야 한다.

4.4 devm_* — 디바이스에 수명을 맡기기#

devm_(device-managed) 접두어 API는 자원을 할당하면서 그 해제 함수를 struct device의 devres 리스트에 등록한다. probe()가 실패하거나 드라이버가 unbind(remove() 이후)될 때 드라이버 코어가 그 리스트를 역순으로 실행한다. 그래서 devm만 쓴 probe()에는 정리 코드가 없다.

  • 대표: devm_kzalloc, devm_ioremap_resource/devm_platform_ioremap_resource, devm_clk_get_enabled, devm_regulator_get_enable, devm_request_irq/devm_request_threaded_irq, devm_gpiod_get, devm_mutex_init.
  • devm 버전이 없는 자원은 devm_add_action_or_reset(dev, fn, data)로 직접 등록한다. 등록 자체가 실패하면 fn(data)를 즉시 불러 주므로("or_reset") 누수가 없다.
  • 해제 시점이 remove()가 끝난 뒤라는 것이 핵심 함정이다. 예를 들어 devm_request_irq로 받은 IRQ는 remove()에서 하드웨어를 꺼도 아직 살아 있다 → IRQ 핸들러가 꺼진 하드웨어나 해제된 자원을 만질 수 있다. devm 자원 순서를 "획득 순서 = 역순 해제"에 맞게 짜야 한다.

4.5 cleanup.h — 6.18에 있는가? 있다#

include/linux/cleanup.h는 6.5에 들어왔고(Peter Zijlstra), 6.18 랩 소스에 다음이 있다.

구조가 보인다: DEFINE_FREE(kfree, void *, ...)가 __free_kfree(void *p)라는 정리 함수를 만들고, __free(kfree)는 __cleanup(__free_kfree) = __attribute__((__cleanup__(__free_kfree)))로 펼쳐진다 — 예제 10에서 손으로 쓴 것과 같다. kfree 정리 함수가 IS_ERR_OR_NULL을 검사하므로 NULL이나 에러 포인터인 채로 스코프를 나가도 안전하다. guard(mutex)(&lock)는 생성 시 mutex_lock, 스코프 끝에서 mutex_unlock을 부르는 숨은 변수를 만든다(C++ std::lock_guard와 같은 RAII). scoped_guard(spinlock_irqsave, &lock) { ... }는 블록 하나만 잠근다.

5.1 BIT · GENMASK · FIELD_PREP · FIELD_GET#

Don이 데이터시트의 레지스터 표를 코드로 옮길 때 #define CTRL1_ODR_SHIFT 4, #define CTRL1_ODR_MASK (0xF << 4), reg = (reg & ~MASK) | ((val << SHIFT) & MASK)를 썼을 것이다. 커널은 이걸 마스크 하나만 정의하면 되도록 표준화했다. shift는 마스크에서 컴파일러가 계산한다(__builtin_ctzll).

5.2 ARRAY_SIZE · BUILD_BUG_ON#

  • ARRAY_SIZE(arr) = sizeof(arr) / sizeof((arr)[0]) + __must_be_array(arr). 뒤의 __must_be_array는 arr가 포인터면 컴파일 에러를 내는 0짜리 식이다. 배열이 함수 인자로 넘어오면 포인터로 바뀌므로(decay) 그 자리에서 ARRAY_SIZE를 쓰면 8/2 = 4 같은 엉터리가 나오는데, 이걸 막는다(예제 14의 CASE 2).
  • BUILD_BUG_ON(cond) — cond가 컴파일 타임에 참이면 빌드 실패. 런타임 비용 0인 assert. 펌웨어에서 typedef char check[(cond) ? -1 : 1]; 같은 트릭으로 하던 것. 예: 레지스터 맵 구조체 크기 검사, 표 길이와 비트 폭 일치 검사(예제 13). 메시지를 붙이려면 BUILD_BUG_ON_MSG, 파일 스코프에서는 static_assert(cond, "msg").

5.3 min · max · clamp — 타입 안전#

C 교과서의 #define MIN(a,b) ((a) < (b) ? (a) : (b))에는 두 가지 문제가 있다. (1) 인자를 두 번 평가한다(MIN(i++, j)), (2) signed와 unsigned를 비교하면 C의 일반 산술 변환으로 -1이 0xffffffff가 되어 MIN(10u, -1)이 10이 된다. 커널 min()은 각 인자를 __auto_type 임시 변수에 한 번만 담고, 부호가 섞이면 BUILD_BUG_ON_MSG로 "signedness error"를 낸다(예제 14의 CASE 4). 6.x의 규칙은 include/linux/minmax.h 주석대로 "부호 사용이 호환돼야 한다 — 단, 컴파일 타임에 음수가 아님이 확실한 signed 값은 unsigned와 비교해도 된다"이다.

  • 타입이 정말 다르면 min_t(type, a, b) — 둘 다 type으로 캐스트 후 비교(어떤 타입으로 비교할지 명시하는 것이 핵심).
  • clamp(val, lo, hi) — 범위 제한. DT나 사용자 입력으로 받은 ODR 값을 하드웨어 범위로 자를 때.
  • umin/umax(둘 다 unsigned로 비교)도 있다.

5.4 엔디안 — cpu_to_le32 · le32_to_cpu · __le32#

장치 레지스터, DMA 디스크립터, 네트워크/USB 패킷 필드는 엔디안이 정해져 있다(NVMe는 little-endian, 네트워크·DT는 big-endian). CPU의 엔디안과 무관하게 같은 바이트가 나와야 한다. Don이 NVMe 명령 구조체를 다룰 때 Cortex-R이 LE라서 변환 없이 썼을 텐데, 리눅스 드라이버는 BE CPU(일부 PowerPC, MIPS 설정)에서도 같은 코드가 돌아야 하므로 변환을 항상 쓴다 — LE CPU에서 cpu_to_le32는 아무 일도 안 하는 매크로라 비용은 0이다.

함수방향

le32_to_cpu(x) / be32_to_cpu(x)저장 형식 → CPU 값
le32_to_cpup(p), get_unaligned_le32(p)포인터에서 읽기 (정렬 안 된 버퍼는 get_unaligned_*)

타입 __le32, __be32는 include/uapi/linux/types.h에서 typedef __u32 __bitwise __le32;로 정의된다. gcc에게는 그냥 u32지만, sparse에게는 u32와 섞으면 경고가 나는 별개 타입이다(§6). 구조체 필드를 __le32로 선언해 두는 것이 문서이자 검사다.

참고로 MMIO 접근자 readl()/writel()은 little-endian 장치 레지스터를 가정하고 내부에서 le32_to_cpu를 해 준다. BE 레지스터 장치면 ioread32be().

5.5 likely · unlikely#

likely(x) = __builtin_expect(!!(x), 1). 분기 예측기에 직접 힌트를 주는 게 아니라(arm64엔 그런 명령이 없다), 컴파일러가 코드 배치를 바꾼다: 예상 경로를 fall-through 직선 코드로, 드문 경로를 함수 뒤쪽으로 보내 I-cache와 분기 예측기를 돕는다. 규칙: 측정했거나 명백할 때만 — 에러 경로(if (unlikely(!p))), fast path 검사. 틀리게 쓰면 오히려 느려진다. IS_ERR()가 이미 내부에 unlikely를 품고 있으므로 if (unlikely(IS_ERR(p)))는 중복이다. (CONFIG_PROFILE_ANNOTATED_BRANCHES를 켜면 힌트가 맞았는지 통계를 볼 수 있다.)

5.6 READ_ONCE · WRITE_ONCE — 미리보기#

컴파일러는 "다른 스레드가 이 변수를 바꿀 수 있다"는 것을 모른다. 그래서 루프 안의 while (!flag)를 레지스터에 한 번 읽고 무한 루프로 만들거나, 두 번의 쓰기를 합치거나, 64비트 쓰기를 두 번의 32비트 쓰기로 쪼갤(tearing) 수 있다. READ_ONCE(x)/WRITE_ONCE(x, v)는 정확히 한 번, 쪼개지 않고 접근하라는 표시다(내부적으로 volatile 접근). 펌웨어에서 ISR과 공유하는 변수에 volatile을 붙이던 것과 같은 목적인데, 커널은 변수 선언이 아니라 접근 지점에 붙인다.

중요: READ_ONCE는 메모리 배리어가 아니다. 다른 CPU에서 순서가 보장되지 않는다. 순서가 필요하면 smp_load_acquire/smp_store_release나 락. 락으로 보호된 변수에는 필요 없다. 자세한 건 M 모듈(동시성)에서.

6. sparse — gcc가 못 보는 실수를 잡는 주석들#

6.1 직관: 같은 u32 *라도 "어느 주소 공간의 포인터인가"가 다르다#

Don의 SoC 세계에서 주소는 하나의 공간이 아니다. 같은 0x9010000이라도 CPU의 물리 주소, IOMMU 뒤의 DMA 주소, 커널 가상 주소가 다르다. 리눅스 커널 코드에는 성질이 다른 포인터가 섞여 다닌다:

주석의미직접 역참조올바른 접근
(없음) __kernel커널 가상 주소의 일반 메모리가능*p
__user유저 프로세스 주소. 커널 페이지 테이블에선 의미가 다르거나 매핑이 없을 수 있음, 악의적일 수 있음금지copy_from_user, get_user (E6)
__iomemioremap한 장치 레지스터금지readl/writel, ioread32
__percpuper-CPU 변수의 오프셋금지this_cpu_ptr, per_cpu_ptr
__rcuRCU로 보호된 포인터금지rcu_dereference
__bitwise 타입 (__le32, __be32, gfp_t, __poll_t)정수지만 다른 정수와 섞으면 안 되는 타입산술 금지변환 함수
__force"이 캐스트는 의도한 것" — 위 검사를 끄는 표시최소한으로

gcc에게는 이 주석들이 아무 의미 없다. include/linux/compiler_types.h를 보면 __CHECKER__가 정의된 경우(= sparse가 돌 때)에만 속성이 붙는다.

  • address_space(X) — 포인터에 "주소 공간 꼬리표"를 단다. 꼬리표가 다른 포인터끼리 대입·전달하면 경고.
  • noderef — 이 포인터는 *p, p->x로 직접 역참조하면 경고.
  • __bitwise — 정수 타입에 "제한(restricted)" 꼬리표. 같은 꼬리표끼리 &, |, ==는 되지만 일반 정수와 섞거나 산술하면 경고.
  • 마지막 # define __iomem(66행)은 #else 쪽 — gcc가 볼 때는 빈 매크로다.

왜 __iomem 포인터를 직접 역참조하면 안 되나? (1) 컴파일러가 접근을 합치거나 순서를 바꾸거나 쪼갤 수 있다(레지스터는 읽기 자체가 부수 효과 — read-to-clear). (2) 아키텍처에 따라 MMIO는 특수 명령이나 배리어가 필요하다(readl은 arm64에서 load 뒤에 배리어를 넣어 이후 DMA 버퍼 읽기와 순서를 맞춘다). (3) 일부 아키텍처(x86의 port I/O)는 메모리 명령으로 접근할 수 없다. readl/writel은 이 모든 것을 처리하고 LE 변환까지 한다.

6.2 예제 15 — 일부러 틀린 모듈에 make C=2#

무엇을 확인하나: gcc로는 경고 0개인 코드에서 sparse가 세 종류의 실수를 잡는 것을 본다. make C=1은 다시 컴파일되는 파일만, C=2는 모든 소스 파일을 검사한다. 이 모듈은 로드하지 않는다.

Kbuild: obj-m := e5_sparse.o e5_sparse_ok.o (고친 버전을 같이 넣어 비교)

출력에서 볼 것:

  • CC [M] e5_sparse.o 줄 뒤에 gcc 경고가 없다. 세 실수 모두 gcc에겐 정상 코드다. 그리고 .ko까지 만들어졌다 — sparse 경고는 빌드를 멈추지 않는다.
  • 실수 1(15행, return *r;): "dereference of noderef expression" — __iomem 포인터 직접 역참조.
  • 실수 2(22행): copy_to_user(to, from, n)의 인자 순서를 뒤집었다. 1번 인자 자리는 void __user *인데 char *(커널 스택 버퍼)가 왔고, 2번 자리에는 __user 포인터가 왔다. 이 버그가 런타임에 가면 커널 스택에 유저가 고른 데이터를 쓰는 보안 취약점이다 — 그런데 gcc는 아무 말도 안 한다.
  • 실수 3(28, 29행): __le32를 u32에 바로 대입("different base types"), __le32를 정수 상수와 비교("restricted __le32 degrades to integer"). LE CPU에서는 우연히 맞게 동작하므로 x86/arm64에서 테스트로는 절대 안 잡히고, BE 플랫폼에서야 터진다.
  • [usertype]은 typedef 이름이 있는 타입이라는 sparse의 표시다.

6.3 예제 16 — 고친 버전: sparse 경고 0, QEMU에서 실행#

위 §6.2 빌드 출력에서 CHECK e5_sparse_ok.c 뒤에 경고가 한 줄도 없다. 이 노트의 모든 커널 모듈에도 C=2를 돌렸다.

출력에서 볼 것: 이미 빌드된 상태라 CC 없이 CHECK만 돌았고(C=2는 컴파일 여부와 상관없이 검사), 경고 0개다. 예제 13의 실행 출력에서 e5_sparse_ok: RTCDR=1791664981 payload_len=64(와이어 바이트 40 00 00 00을 LE로 해석한 64)와 raw bits=0x40을 이미 봤다.

고친 방법 정리:

  1. *r → readl(regs). __iomem은 접근자로만.
  2. copy_to_user(ubuf, kbuf, n) — 목적지가 앞. sparse가 순서 실수를 타입으로 잡아 준다.
  3. 값은 le32_to_cpu(h->len)로 꺼내고, 상수 비교는 상수 쪽을 cpu_to_le32(0xE5E5E5E5)로 바꿨다. 상수 변환은 컴파일 타임에 계산되므로 런타임 비용이 0이다(값 쪽을 변환하면 BE CPU에서 매번 바이트 스왑).
  4. 비트 패턴을 의도적으로 재해석할 때(로그 출력용 raw 값 등)는 (__force u32)h->len. __force는 "검토했다"는 서명이다 — 리뷰어는 __force가 보이면 그 줄을 다시 본다.

6.4 sparse를 언제 돌리나#

  • 패치를 메일링 리스트에 보내기 전에 make C=1 (바뀐 파일만) — 새 sparse 경고는 리뷰에서 지적받는다. 0-day 봇(kernel test robot)이 자동으로 돌려 경고를 메일로 보낸다(E7).
  • 기존 코드에도 sparse 경고가 많은 파일이 있다. 내 패치가 새 경고를 추가하지 않는지를 본다(C=2 출력을 패치 전후로 diff).
  • __bitwise는 내 드라이버 타입에도 쓸 수 있다: typedef u32 __bitwise imu_reg_t; 처럼 정의해 두면 "레지스터 값"과 "그냥 숫자"가 섞이는 것을 sparse가 잡는다. 커널의 gfp_t, blk_opf_t, __poll_t가 이렇게 만들어진 타입이다.

7. 커널 안에서는 무슨 일이 일어나나#

이 노트의 관용구들은 커널 자료구조의 뼈대 그 자체다. 가장 좋은 예가 디바이스 모델이다. struct device 하나를 해제하는 경로를 따라가면 container_of가 네 번, kref가 한 번 나온다.

그림 7 — 왼쪽: 객체가 마트료시카처럼 내장(embed)된다. 오른쪽: 마지막 put_device()에서 시작해 안쪽 kref가 0이 되면, 각 층의 release가 container_of로 한 층씩 바깥으로 올라가며 최종적으로 가장 바깥 객체를 kfree한다. "→"는 모두 container_of(또는 그것을 감싼 매크로)다.

랩 소스(6.18.55)에서 한 단계씩 확인한 위치:

단계파일코드
kobject_putlib/kobject.ckref_put(&kobj->kref, kobject_release);
kobject_releaselib/kobject.cstruct kobject *kobj = container_of(kref, struct kobject, kref);
device_releasedrivers/base/core.cstruct device *dev = kobj_to_dev(kobj); → dev->release(dev) 또는 dev->type->release(dev) (없으면 WARN)

container_of의 member에 pdev.dev처럼 중첩 멤버 경로를 쓸 수 있다는 점도 보자(offsetof가 허용한다). platform_object는 platform_device_alloc()이 이름 문자열을 같은 할당 안에 붙이기 위해 만든 래퍼(struct platform_device pdev; char name[];)다 — 예제 3의 pdev를 kfree한 것도 결국 이 경로였다.

같은 패턴이 커널 전체에 반복된다:

  • 버스·드라이버 코어: to_platform_device, to_i2c_client, to_spi_device, to_usb_device, to_pci_dev — 전부 container_of(dev, ..., dev). 버스 콜백은 struct device *를 주고 각 버스가 자기 타입으로 되돌린다. F 모듈(드라이버 모델)과 G 모듈(버스 드라이버)에서 매일 쓴다.
  • file_operations: open(struct inode *inode, struct file *filp)에서 container_of(inode->i_cdev, struct my_dev, cdev)로 내 디바이스 구조체를 찾아 filp->private_data에 저장한다(H 모듈 char 드라이버의 첫 줄). miscdevice면 container_of(filp->private_data, struct my_dev, misc).
  • work와 timer: INIT_WORK(&priv->work, fn)의 fn(struct work_struct *w)는 container_of(w, struct my_priv, work)로, 타이머 콜백은 timer_container_of(priv, t, timer)(예전 커널의 from_timer가 6.16에서 이 이름으로 바뀌었다 — 6.16 이전 커널용 드라이버는 #if LINUX_VERSION_CODE < KERNEL_VERSION(6,16,0)로 #define timer_container_of from_timer를 두기도 한다)로 자기 구조체를 찾는다(I 모듈).
  • 리스트 사용처: 드라이버 코어의 bus->p->klist_devices, 커널 타이머, 워크큐, 프로세스 목록(task_struct.tasks), 블록 I/O 요청 큐 — 전부 intrusive 리스트다. /proc의 많은 파일은 그 리스트를 순회해서 만든다.
  • ERR_PTR: devm_*_get() 계열 전부, clk/regulator/gpiod/phy/reset 프레임워크, kthread_run, debugfs. -EPROBE_DEFER가 ERR_PTR로 전파되는 것이 deferred probe의 근간이다(F 모듈).
  • devm/devres: struct device의 devres_head 리스트(이것도 list_head)에 해제 함수와 데이터를 쌓아 두고, probe 실패나 unbind 때 drivers/base/dd.c의 device_unbind_cleanup() → devres_release_all()이 역순으로 실행한다.
  • sparse 주석: copy_to_user의 인자는 void __user *(E6), devm_ioremap_resource의 반환은 void __iomem *(G·H 모듈의 MMIO), DMA 디스크립터 필드는 __le32/__le64(K 모듈).

8. Embedded 실무에서 다시 보기#

8.1 센서 키트 IMU 드라이버의 probe — 관용구 총출동#

예를 들어 SPI IMU 드라이버라면 probe()의 뼈대는 이렇다(형태를 보여 주는 조각이며 실행하지 않았다).

goto가 하나도 없다. 새 드라이버는 devm으로 probe를 "자원을 선언하는 목록"처럼 쓰고, 함수 안에서만 쓰는 임시 버퍼·락은 __free/guard로 처리한다. 반면 기존 벤더 BSP 드라이버(4.x, 5.x 시절 코드)는 대부분 goto 사다리이므로 둘 다 읽을 줄 알아야 한다. 백포트할 때 cleanup.h 코드를 6.5 이전 커널로 가져가면 컴파일이 안 된다는 점도 기억하자.

8.2 패킷 헤더와 DMA 디스크립터 — __le32로 선언하기#

Q. What does container_of do, and how is it implemented?

A. 구조체 안에 내장된 멤버의 포인터를 받아서 그 멤버를 품은 바깥 구조체의 포인터를 돌려준다. 구현은 멤버 주소에서 offsetof(type, member)를 빼는 것 — 오프셋이 컴파일 타임 상수라서 런타임엔 빼기 한 번(arm64에서 sub 한 줄)이다. 커널판은 statement expression과 static_assert(__same_type(*ptr, ((type *)0)->member))로 포인터 타입이 멤버 타입과 같은지 컴파일 때 검사한다. 새 코드에서는 const를 보존하는 container_of_const를 권장한다.

container_of takes a pointer to a member embedded in a struct and returns a pointer to the enclosing struct. It subtracts offsetof(type, member) from the member's address — the offset is a compile-time constant, so at runtime it's a single subtract. The kernel version wraps it in a statement expression with a static_assert that the pointer type matches the member type, so passing the wrong pointer is a build error. For new code there's container_of_const, which preserves const.

꼬리 질문: "왜 역포인터(back-pointer)를 두지 않나?" → 객체마다 8바이트를 아끼고, 포인터 초기화를 잊는 버그가 없고, 하나의 객체가 여러 부품(device, kref, list_head, work)을 내장해도 각각에서 돌아올 수 있다.

Q. Why does the kernel use intrusive linked lists instead of a generic list that stores pointers?

A. 링크가 객체 안에 있으니 리스트에 넣을 때 할당이 없어서 list_add가 실패할 수 없다 — spinlock을 잡거나 인터럽트 컨텍스트에서도 쓸 수 있다. list_head를 여러 개 두면 한 객체가 여러 리스트에 동시에 있을 수 있고, 객체 포인터만 있으면 O(1)로 뺄 수 있다. 리스트 코드는 list_head만 알아서 타입마다 다시 쓸 필요가 없고, container_of로 바깥 객체로 돌아온다. 캐시에도 대체로 유리한데, 측정해 보면 무작위 순서 순회에선 차이가 작다.

Because the links live inside the object, adding to a list never allocates, so list_add can't fail — that matters under a spinlock or in interrupt context. An object can sit on several lists by embedding several list_heads, and removal is O(1) given the object. The list code only knows about list_head and is reused for every type; container_of gets you back to the object. It's usually a bit more cache-friendly too, although for random-order traversal the difference is small.

Q. How do you delete entries while iterating a kernel list?

A. list_for_each_entry_safe(pos, n, head, member)를 쓴다. 다음 원소를 n에 미리 저장해 두므로 몸통에서 pos를 list_del + kfree해도 된다. 그냥 list_for_each_entry로 지우면 증가식이 지운 노드의 next를 읽는데, list_del이 거기에 LIST_POISON1(0xdead000000000100)을 써 놓았기 때문에 그 근처 주소에서 oops가 난다. _safe는 내가 지우는 것만 안전하고, 동시 수정은 락이나 RCU로 막아야 한다.

I use list_for_each_entry_safe, which caches the next entry in a second cursor, so I can list_del and kfree the current one. With the plain iterator, the increment step reads the deleted node's next pointer, which list_del has poisoned to 0xdead000000000100, so you oops at an address near that. The _safe variant only protects against my own deletion — concurrent modification still needs a lock or RCU.

Q. How does ERR_PTR work?

A. 커널 주소 공간의 맨 위 4095바이트에는 유효한 객체가 없다는 점을 이용한다. ERR_PTR(-ENOENT)은 -2를 그대로 포인터로 캐스트한 것(0xfffffffffffffffe)이고, IS_ERR는 (unsigned long)p >= (unsigned long)-4095 비교 한 번, PTR_ERR는 다시 long으로 캐스트한다. 이걸로 한 반환값에 "객체 또는 실패 이유"를 담는다 — 특히 -EPROBE_DEFER를 구분해야 하는 probe 경로에서 중요하다. NULL은 IS_ERR가 잡지 않으니 API마다 NULL을 주는지 ERR_PTR을 주는지 확인해야 한다.

The top 4095 bytes of the address space never hold a valid object, so a negative errno cast to a pointer — ERR_PTR(-ENOENT) is 0xfffffffffffffffe — can't be confused with a real pointer. IS_ERR is a single unsigned compare against -MAX_ERRNO, and PTR_ERR casts it back to long. That lets one return value carry either the object or the reason it failed, which matters for things like -EPROBE_DEFER. IS_ERR doesn't catch NULL, so you have to know which convention each API uses.

Q. How do you handle errors and cleanup in a probe function?

A. 전통적으로는 goto 사다리 — 자원을 잡을 때마다 실패하면 "직전까지 잡은 것을 되돌리는 레이블"로 점프하고, 레이블은 획득의 역순으로 아래로 떨어지며 해제한다. 지금은 가능한 한 devm_*를 써서 드라이버 코어가 probe 실패나 unbind 때 역순으로 해제하게 하고, devm 버전이 없는 건 devm_add_action_or_reset으로 등록한다. 함수 안에서만 쓰는 버퍼와 락은 6.5부터 있는 __free(kfree), guard(mutex) 같은 scope 기반 정리를 쓴다. 한 함수에서 goto와 cleanup 헬퍼를 섞지 않는다. devm 해제는 remove 이후에 일어나므로 IRQ 같은 자원의 순서에 주의한다.

Classically with a goto ladder: each acquisition jumps on failure to a label that undoes everything acquired before it, with labels in reverse order falling through. In new code I use devm_ helpers so the driver core releases resources in reverse order on probe failure or unbind, and devm_add_action_or_reset for anything without a devm variant. For function-local buffers and locks I use the scope-based helpers from cleanup.h — __free(kfree), guard(mutex) — available since 6.5. I don't mix goto with cleanup helpers in one function, and I keep in mind that devm teardown runs after remove, which matters for IRQs.

Q. What are __iomem and __user, and what checks them?

A. sparse용 주소 공간 주석이다. gcc에게는 빈 매크로라 아무 효과가 없고, make C=1/C=2로 sparse를 돌리면 다른 주소 공간 포인터를 섞거나 직접 역참조할 때 경고한다. __iomem은 ioremap한 장치 레지스터 — 반드시 readl/writel로 접근한다(배리어, 접근 폭, 엔디안). __user는 유저 공간 포인터 — copy_from_user/get_user로만 접근한다(검증, fault 처리). __bitwise는 __le32 같은 타입을 일반 정수와 섞지 못하게 하고, 의도적인 변환은 __force로 표시한다.

They're sparse annotations — address-space tags. To gcc they expand to nothing; running sparse via make C=1 or C=2 warns when pointers from different address spaces are mixed or dereferenced directly. __iomem marks ioremapped registers, which must be accessed with readl/writel so you get the right access width, barriers and endianness. __user marks userspace pointers, which go through copy_from_user or get_user. __bitwise makes types like __le32 incompatible with plain integers, and __force marks an intentional cast.

꼬리 질문: "sparse가 실제로 잡은 버그 예?" → copy_to_user의 인자 순서를 바꾸면 gcc는 조용하지만 sparse는 "different address spaces"로 잡는다 — 그대로 두면 유저가 커널 스택을 덮는 취약점.

Q. How do you define and update a register field in kernel code?

A. 데이터시트의 필드를 GENMASK(h, l)(단일 비트는 BIT(n))로 마스크만 정의하고, 쓰기는 FIELD_PREP(mask, val), 읽기는 FIELD_GET(mask, reg). shift는 마스크에서 계산되고, 상수 값이 필드보다 크면 빌드 에러다. RMW는 reg &= ~mask; reg |= FIELD_PREP(mask, v); — regmap이면 regmap_update_bits가 락과 함께 해 준다. 레지스터 접근은 readl/writel로.

I define each field as a mask with GENMASK(high, low) or BIT(n), then use FIELD_PREP to place a value and FIELD_GET to extract it. The shift is derived from the mask, and a constant that doesn't fit the field fails the build. A read-modify-write is clear the mask, OR in FIELD_PREP — or regmap_update_bits, which also takes the lock. The access itself goes through readl and writel.

Q. Why does the kernel's min() refuse to compare an unsigned int with an int?

A. C의 일반 산술 변환 때문에 -1이 unsigned로 바뀌어 최댓값이 되므로, min(10u, -1)이 10이 되는 버그가 난다. 커널 min()은 각 인자를 한 번만 평가하고(부작용 안전) 부호가 호환되지 않으면 컴파일 에러를 낸다. 의도한 비교 타입이 있으면 min_t(type, a, b)로 명시한다. 컴파일 타임에 음수가 아님이 확실한 signed 상수는 허용된다.

Because of the usual arithmetic conversions, -1 becomes UINT_MAX when compared with an unsigned value, so a naive MIN would return the wrong one. The kernel's min evaluates each argument once and fails the build when the signedness is incompatible; if I really want a particular comparison type I use min_t and name it. Signed values that are provably non-negative at compile time are allowed.

  1. (관찰) 예제 6을 list_del 대신 list_del_init으로 바꾸면 oops가 나는가? 무엇이 출력되는가? 이유를 list_del_init의 정의로 설명하라. 정답/힌트: 지운 노드가 자기 자신을 가리키게 되므로 증가식이 pos를 다시 pos로 만든다 — 같은 원소를 무한히 도는 hang(soft lockup)이 된다. poison이 "크래시로 빨리 드러내기"를 위한 선택임을 확인하라.
  1. (코드) 예제 9의 e5_get_cal()을 쓰는 쪽에서 if (!c)로 검사하도록 일부러 틀리고 id=-1일 때 c->gain을 읽어 보라. oops의 fault 주소는 얼마일 것인가? 예측 후 QEMU에서 확인하라. 정답/힌트: ERR_PTR(-EINVAL) = 0xffffffffffffffea에 gain의 오프셋 0을 더한 주소. 주소의 하위 바이트에서 errno(-22)를 읽어 낼 수 있다.
  1. (코드) 예제 11에 세 번째 devm 액션 C를 e5_parse() 뒤에 추가하고 fail_at=0으로 넣었다 뺐을 때 출력 순서를 예측하라. 이어서 e5_probe()를 devm 없이 goto 사다리로 다시 쓰고 fail_at 1~3에서 출력이 같은지 비교하라. 정답/힌트: remove → C → B → A. goto 버전은 remove에서 A, B, C를 직접 역순으로 해제해야 하므로 코드가 두 곳(에러 경로, remove)에 생긴다 — devm의 가치가 이것.
  1. (관찰) 예제 15의 e5_sparse.c에 void __user *p = (void __force __user *)kbuf; 같은 줄을 넣으면 sparse 경고가 사라지는가? 그게 왜 위험한지 설명하라. 그리고 make C=1과 C=2를 두 번씩 연속 실행해 차이를 보라. 정답/힌트: __force가 검사를 끈다 — 경고만 사라지고 버그는 그대로. C=1은 두 번째 실행에서 재컴파일이 없으니 CHECK도 안 돈다.
  1. (설계) 센서 키트의 GNSS UART 패킷 헤더(sync 0xB562(BE), class, id, length(LE16))를 C 구조체로 정의하라. 필드 타입에 __be16/__le16을 쓰고 static_assert로 크기를 고정하고, 길이를 읽는 함수를 sparse 경고 없이 작성하라. 정답/힌트: struct ubx_hdr { __be16 sync; u8 cls; u8 id; __le16 len; } __packed; static_assert(sizeof(struct ubx_hdr) == 6);, if (h->sync != cpu_to_be16(0xB562)) return -EINVAL; return le16_to_cpu(h->len);.

13. 요약 & 체크리스트#

커널 C 관용구는 새 문법이 아니라 Don이 펌웨어에서 손으로 하던 일을 표준화한 것이다. container_of는 "멤버 주소 − 상수 오프셋"으로 내장된 부품에서 바깥 객체를 찾고, 커널판은 타입까지 검사한다. 디바이스 모델·kref·work·리스트가 모두 이 위에 서 있다. list_head는 링크를 객체 안에 넣어 할당 없는(실패 없는) 삽입, 다중 소속, O(1) 삭제를 얻고, 순회 중 삭제는 반드시 _safe로 한다 — 틀리면 dead… 주소 oops가 난다. ERR_PTR은 주소 공간 꼭대기 4095바이트에 errno를 실어 "객체 또는 이유"를 하나의 포인터로 돌려주며, API마다 NULL/ERR_PTR 관례가 다르다는 것이 가장 큰 함정이다. 에러 정리는 "획득의 역순"이라는 한 원칙을 goto 사다리(사람), devm(드라이버 코어), cleanup.h(컴파일러)가 각각 기억한다. GENMASK/FIELD_PREP/엔디안 헬퍼는 레지스터·패킷 필드를 안전하게 다루고 상당수 실수를 빌드 단계에서 막는다. gcc가 못 보는 주소 공간·엔디안 실수는 __iomem/__user/__bitwise 주석과 make C=2(sparse)가 잡는다.
