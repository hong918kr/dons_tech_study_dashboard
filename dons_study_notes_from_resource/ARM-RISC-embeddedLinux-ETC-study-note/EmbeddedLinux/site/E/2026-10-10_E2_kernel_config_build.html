0. 큰 그림 — 이게 왜 필요한가#

Don의 SSD 펌웨어를 떠올려 보자. 제품마다 config_prodA.h가 있고, 그 안의 #define FEATURE_X 1이 #ifdef로 코드를 켜고 끈다. 빌드는 Makefile이 하고, 결과물은 링커 스크립트가 정한 하나의 .bin이다. 기능 사이의 의존성("X를 켜려면 Y도 켜야 한다")은 사람이 기억하거나 #error로 막는다.

Linux 커널은 이 구조를 그대로 키운 것이다. 다만 규모가 다르다. 이 노트에서 쓰는 6.18.55 소스에는 Kconfig 파일이 1,880개, config 심볼이 21,750개, Makefile/Kbuild가 3,282개 있다. 사람이 #define을 손으로 관리할 수 없으니 세 개의 층을 둔다.

  • Kconfig — "무엇을 켤 수 있고, 무엇에 의존하며, 기본값이 무엇인가"를 적는 설정 언어. 펌웨어의 config.h + 의존성 검사기.
  • .config — 그 언어로 고른 결과 한 파일. 펌웨어의 config_prodA.h에 해당한다. 이 파일이 곧 "이 보드의 커널"이다.
  • Kbuild — .config를 읽어 "어떤 .c를 컴파일해서 어디에 링크할지"를 정하는 Make 프레임워크. 결과물은 vmlinux(ELF), Image(부트로더가 올리는 바이너리), .ko(모듈), .dtb.

그림 1 — 커널 빌드의 세 층. 위층(Kconfig)이 .config를 만들고 그것이 헤더와 make 변수(auto.conf)로 번역된다(점선). 가운데 층(Kbuild)이 디렉터리를 재귀로 돌며 built-in.a와 .ko를 만들고, 아래층 산출물로 링크·변환된다. vmlinux → Image는 objcopy, Image → Image.gz는 gzip이다.

1. Kconfig 언어 — 심볼, 타입, 메뉴#

1.1 직관 — "설정 항목마다 타입·조건·기본값을 가진 변수"#

Kconfig의 config FOO 하나는 전역 변수 하나다. 이름은 FOO, 결과 파일에서는 CONFIG_FOO가 된다. 변수에는 타입(bool/tristate/int/hex/string), 화면에 보일 프롬프트, 기본값, 그리고 언제 존재할 수 있는지(의존성)가 붙는다. make menuconfig의 메뉴 트리는 이 변수들을 소스 순서대로 나열한 것이다.

B4 §7.2에서 키워드 표와 conf 도구로 작은 Kconfig를 처리해 봤다. 여기서는 진짜 커널 트리 안에서, 각 키워드가 실제 값을 어떻게 바꾸는지 실험으로 확인한다.

1.2 진짜 커널의 Kconfig 세 장면#

예제 1 — 무엇을 확인하나: 커널 소스에서 config, choice, "조건부 프롬프트"가 실제로 어떻게 쓰이는지 grep으로 본다.

출력에서 볼 것:

  • QEMU virt의 콘솔 UART 드라이버 SERIAL_AMBA_PL011은 tristate(내장 y / 모듈 m / 끔 n)이고, AMBA 버스(ARM_AMBA)가 있어야 존재할 수 있으며(depends on), 켜는 순간 serial core 계층(SERIAL_CORE)을 끌고 온다(select). 드라이버 Kconfig의 전형적인 3줄이다.
  • choice는 "여러 bool 중 정확히 하나"다. HZ는 100/250/300/1000 중 하나만 고를 수 있다. 랩 커널은 기본값 HZ_250, Ubuntu VM 호스트 커널은 HZ=1000이다(B4에서 본 값).
  • bool "Enable support for printk" if EXPERT — 프롬프트에 조건이 붙어 있다. EXPERT가 꺼져 있으면 이 항목은 메뉴에 안 보이고 기본값 y로 고정된다. 일반 사용자가 실수로 printk를 끄지 못하게 하는 장치다. 이 한 줄이 §4.6의 "allnoconfig인데 printk가 켜져 있다" 수수께끼의 답이다.

2. 의존성 의미론 — depends on · select · imply · visible if#

2.1 직관 — 상한, 강제, 추천#

세 키워드는 모두 "A와 B가 관련 있다"를 말하지만 방향과 힘이 다르다.

  • depends on B (A 쪽에 씀) — A의 상한을 B로 묶는다. B가 n이면 A는 존재하지 않는다. B가 m이면 A는 최대 m. 펌웨어로 말하면 #if !defined(B) #error 대신 "B가 없으면 메뉴에서 A를 아예 지운다".
  • select B (A 쪽에 씀) — A가 켜지면 B의 하한을 A로 올린다. B의 depends on은 보지 않는다. "A를 링크하려면 B 라이브러리가 반드시 있어야 한다"를 강제하는 용도.
  • imply B (A 쪽에 씀) — A가 켜지면 B의 기본값만 올린다. B의 depends는 존중하고, 사용자가 B를 n으로 내릴 수 있다. "있으면 좋은 것"을 추천하는 용도.

그림 2 — 세 키워드의 화살표 방향과 힘. depends on은 아래에서 위를 올려다보는 "상한", select는 위에서 내리꽂는 "강제 하한", imply는 "기본값 추천". 아래 빨간 상자가 면접 단골 함정이다.

2.2 예제 3 — 여섯 가지 조합을 olddefconfig로 판정시키기#

무엇을 확인하나: 같은 시작 .config에서 사용자 값만 바꿔 넣고 Kconfig 엔진(olddefconfig)이 최종 값을 어떻게 정하는지 본다. scripts/config -u는 "줄을 아예 지움(사용자 값 없음)", -d는 "n으로 명시", -e는 "y로 명시"다.

출력에서 볼 것:

  • A — 사용자가 CODEC=y라고 적어도 BUS=n이면 CODEC 줄이 통째로 사라진다. .config에 써 둔 값이 조용히 없어지는 것, 이게 "설정을 넣었는데 안 들어갔다"의 1번 원인이다.
  • B — select는 depends를 무시하고 CODEC=y로 만든다. Kconfig는 경고만 찍고 계속 간다. 실제 드라이버였다면 CODEC 코드가 BUS 함수 없이 컴파일되어 링크 에러(undefined reference)나 런타임 NULL 호출로 터진다.
  • C/D — imply는 BUS가 없으면 아무 일도 하지 않고(C), BUS가 있으면 CODEC 기본값을 y로 올린다(D).
  • E/F — 사용자가 CODEC=n이라고 명시하면 imply는 물러나고(E), select는 무시하고 다시 y로 만든다(F). "사용자가 끌 수 있느냐"가 둘의 결정적 차이다.

2.3 예제 4 — menuconfig 검색 화면은 이 관계를 다 보여 준다#

무엇을 확인하나: 대화형 도구인 menuconfig를 tmux로 띄우고 키 입력을 보내 화면을 캡처한다(노트에 붙이려고 비대화형으로 돌린 것). /(검색)에 심볼 이름을 넣으면 정의 위치, 의존성, 누가 select/imply 하는지가 나온다. F 조합(SEL=y, BUS=y) 상태의 .config에서 찍었다.

출력에서 볼 것 (q, x, l, k는 tmux가 ncurses 선 문자를 ASCII로 찍은 것이다):

  • Depends on: E2_DEMO [=y] && E2_BUS [=y] — 우리는 depends on E2_BUS만 썼는데 E2_DEMO가 붙어 있다. if E2_DEMO … endif 블록이 안의 모든 항목에 depends를 자동으로 AND 한 것이다.
  • Location에서 CODEC이 E2 fake bus core 밑에 들여쓰기되어 있다. Kconfig는 "바로 앞 심볼에 의존하는 항목"을 그 심볼의 자식처럼 보여 준다(메뉴 구조는 depends로 추론된다).
  • Selected by / Implied by — "왜 이 옵션이 켜져 있지?"를 물을 때 가장 빠른 답이다. 실무에서 "끄려고 해도 안 꺼지는 옵션"의 99%는 누군가 select하고 있는 것이다.

2.4 실제 드라이버의 정석 패턴 — "버스는 depends, 라이브러리는 select"#

센서 키트의 IMU로 자주 쓰는 Bosch BMI270의 실제 Kconfig다.

출력에서 볼 것:

  • 사용자가 고르는 것은 BMI270_I2C/BMI270_SPI(프롬프트 있음)뿐이다. 코어 BMI270은 프롬프트가 없는 tristate라 사용자가 직접 켤 수 없고, 버스 드라이버가 select해야만 켜진다. 펌웨어로 말하면 "공통 코어 라이브러리 + 버스별 HAL 래퍼" 구조를 Kconfig로 표현한 것이다.
  • REGMAP_I2C는 drivers/base/regmap/Kconfig에서 tristate + depends on I2C로 정의된 라이브러리다. BMI270_I2C가 자기 자신도 depends on I2C 를 갖고 있기 때문에 select REGMAP_I2C가 안전하다. 이것이 select를 쓰는 규칙이다: select할 대상의 depends를 내가 먼저 다 만족시켜 둔다.
  • select된 심볼은 select한 쪽의 값 이상이 된다. BMI270_I2C=m이면 BMI270과 REGMAP_I2C는 최소 m, 다른 누군가가 y로 select하면 y.

3. .config가 코드와 Makefile에 닿는 길 — auto.conf · autoconf.h · IS_ENABLED()#

3.1 직관 — 한 번 고른 값을 세 가지 언어로 번역한다#

.config는 사람(그리고 menuconfig)이 읽고 쓰는 파일이다. 빌드가 시작되면 make가 syncconfig라는 단계를 먼저 돌려서 이 값을 세 가지 형태로 번역해 둔다.

생성 파일형식누가 읽나
include/config/auto.confCONFIG_FOO=y (make 변수 문법)Kbuild Makefile — obj-$(CONFIG_FOO) 전개
include/generated/autoconf.h#define CONFIG_FOO 1C 소스 — 모든 컴파일에 -include로 강제 포함
include/config/<SYMBOL>빈 파일, 값이 바뀔 때만 타임스탬프 갱신fixdep — 심볼 단위 증분 빌드(§8)

그림 3 — .config 한 줄이 세 갈래로 번역된다. 위는 "어떤 파일을 빌드하나"(Makefile), 가운데는 "코드 안에서 무엇이 켜졌나"(C 전처리기), 아래는 "무엇을 다시 빌드해야 하나"(fixdep). 생성 파일은 전부 O= 출력 디렉터리 안에 생긴다.

3.2 예제 5 — E2 심볼이 autoconf.h와 auto.conf에서 어떻게 보이나#

무엇을 확인하나: E2_HELLO=m, 문자열·정수·choice 값이 각 생성 파일에 어떤 모양으로 들어가는지, 그리고 IS_ENABLED() 계열 매크로가 어떻게 정의되어 있는지 본다.

출력에서 볼 것:

  • E2_HELLO=m은 헤더에서 CONFIG_E2_HELLO가 아니라 CONFIG_E2_HELLO_MODULE로 정의된다. n인 심볼은 헤더에 아예 없다(E2_BUS, E2_STYLE_LOUD가 없다). choice는 고른 쪽만 1.
  • auto.conf에서는 문자열의 따옴표가 빠져 있다(CONFIG_E2_HELLO_GREETING=hi Don). make 변수로 쓰기 위한 형식이다. 헤더 쪽은 C 문자열 리터럴 그대로 "hi Don".
  • IS_BUILTIN()의 트릭: CONFIG_FOO가 1로 정의되어 있으면 __ARG_PLACEHOLDER_##1 → __ARG_PLACEHOLDER_1 → 0,이 되어 인자가 하나 늘고, __take_second_arg가 1을 고른다. 정의되어 있지 않으면 __ARG_PLACEHOLDER_CONFIG_FOO라는 의미 없는 토큰 하나뿐이라 두 번째 인자 0이 고려된다. 결과적으로 #ifdef 없이 C 표현식 안에서 0/1 상수를 얻는다.

왜 #ifdef 대신 IS_ENABLED()를 쓰나? 두 가지 이유다.

  1. 모듈 함정 — #ifdef CONFIG_FOO는 FOO=m일 때 거짓이다. 실습 2(§6.4, §9.3)에서 실제로 #ifdef=0이 찍힌다.
  2. 양쪽 코드가 다 컴파일된다 — if (IS_ENABLED(CONFIG_FOO)) foo();는 꺼져 있어도 foo() 호출이 문법 검사와 타입 검사를 받고 나서 dead code로 제거된다. #ifdef로 가린 코드는 그 설정 조합으로 빌드해 보기 전까지 깨져도 모른다.

IS_REACHABLE(CONFIG_FOO)는 "내 코드에서 FOO의 심볼을 부를 수 있나"다. FOO가 m인데 나는 내장(y)이면 부팅 시 FOO 모듈이 아직 없으므로 거짓이 된다. 이걸 피하는 Kconfig 관용구가 depends on FOO || !FOO(FOO가 m이면 나도 최대 m)다.

4. 설정 워크플로 — .config를 재현 가능하게 다루기#

4.1 직관 — .config는 산출물, defconfig가 소스다#

.config는 1만 줄이 넘고(랩 커널 11,748줄), 툴체인 버전 같은 환경에서 자동 감지한 값(CONFIG_CC_VERSION_TEXT 등)까지 담는다. git에 넣고 리뷰하기에는 너무 크고 시끄럽다. 그래서 실무에서는 기본값과 다른 줄만 모은 최소 파일(defconfig) 을 소스로 관리하고, .config는 그때그때 만든다. 펌웨어로 말하면 defconfig는 config_prodA.h, .config는 전처리기가 펼친 최종 결과다.

4.2 예제 6 — 랩 커널은 "defconfig + 3줄"이다 (savedefconfig + diffconfig)#

무엇을 확인하나: 랩 커널의 11,748줄짜리 .config를 savedefconfig로 최소화하고, 같은 방식으로 최소화한 arm64 기본 defconfig와 비교한다. 랩 README는 "defconfig + IKCONFIG_PROC, OF_OVERLAY, GPIO_SIM, DYNAMIC_DEBUG, …"라고 적고 있다 — 실제로 무엇이 다른지 확인한다.

출력에서 볼 것:

  • 사람이 바꾼 것은 딱 3줄(GPIO_SIM=y, OVERLAY_FS=y, DYNAMIC_DEBUG=y)이다. IKCONFIG_PROC와 OF_OVERLAY는 arm64 defconfig에 이미 켜져 있어서 차이로 안 나온다. 1만 줄 .config를 비교했으면 이 사실을 찾기 어려웠을 것이다.
  • diffconfig(전체 .config 비교)에는 그 3줄의 파생 효과(DYNAMIC_DEBUG_CORE, IRQ_SIM 등 select로 끌려온 것)와 환경 차이가 섞여 나온다. RUSTC_VERSION 109301 -> 0은 랩을 빌드할 때는 VM에 rustc가 없었고, 지금 만든 defc에서는 rustc가 감지됐다는 뜻이다. 같은 defconfig라도 툴체인에 따라 .config가 달라진다 — .config를 툴체인과 함께 버전 관리해야 하는 이유다.
  • E2_DEMO n은 우리가 소스 트리에 Kconfig를 추가했기 때문에 새로 만든 defc에만 있는 심볼이다.

savedefconfig의 결과를 보드 defconfig로 저장하는 게 정석이다: cp $O/defconfig arch/arm64/configs/sensorkit_defconfig → 이후 make sensorkit_defconfig.

4.7 예제 10 — tinyconfig와 allnoconfig, 그리고 localmodconfig#

무엇을 확인하나: "가장 작은 설정" 두 가지가 왜 다르고, 이미 돌아가는 시스템에서 설정을 줄이는 localmodconfig가 무엇을 하는지 본다.

출력에서 볼 것: allnoconfig가 tinyconfig보다 크다(y 489개 vs 427개). allnoconfig는 "보이는 질문에 전부 n"인데, PRINTK·TTY·PROC_FS·FUTEX 같은 핵심 기능은 §1.2에서 본 bool "…" if EXPERT 형태라 EXPERT=n이면 질문 자체가 안 보이고 기본값 y로 남는다. tinyconfig는 tiny-base.config로 EXPERT=y를 먼저 켜서 그 질문들을 드러낸 뒤 전부 n으로 답한다. 그래서 tinyconfig 커널은 printk도 tty도 없어서 부팅해도 아무것도 출력하지 않는다 — 실습 1에서 조각을 얹는 이유다.

출력에서 볼 것: 모듈이 1,272개에서 28개로 줄었다. 그리고 localmodconfig는 내부적으로 oldconfig를 돌려서 새 심볼마다 질문한다((NEW) 줄). 처음에 yes "" 없이 돌렸다가 입력을 기다리며 멈춘 채 2분 타임아웃에 걸렸다 — 스크립트·CI에서 쓸 때는 yes "" |로 기본값을 공급하거나 이후 olddefconfig를 쓴다. 주의: localmodconfig는 "지금 안 꽂혀 있는 장치"의 드라이버도 끄므로, USB 장치를 나중에 꽂으면 드라이버가 없다.

6. Kbuild — 무엇을 어디에 링크할지 선언하는 Makefile#

6.1 직관 — 드라이버 Makefile은 "목록"만 적는다#

일반 Makefile은 규칙(target: deps + 명령)을 적는다. Kbuild의 드라이버 Makefile에는 규칙이 하나도 없다. 변수 목록만 적는다. "어떻게 컴파일하고 링크하는지"는 scripts/Makefile.build가 전부 정한다. 펌웨어로 말하면 "소스 목록 파일 + 공용 빌드 템플릿" 구조다.

변수뜻
obj-y += foo.ofoo.o를 이 디렉터리의 built-in.a에 넣는다 → 결국 vmlinux에 링크
obj-m += foo.ofoo.o로 모듈 foo.ko를 만든다
obj-$(CONFIG_FOO) += foo.o위 둘을 .config가 정하게 한다 (auto.conf에서 y/m/빈값으로 전개)
obj-y += sub/하위 디렉터리로 재귀 — sub/built-in.a를 내 built-in.a에 포함
foo-y := a.o b.o (옛 표기 foo-objs)composite: 여러 .o를 합쳐 foo.o 하나로
foo-$(CONFIG_BAR) += c.ocomposite의 일부를 조건부로
lib-y += x.olib.a에 넣는다 (주로 lib/, arch/*/lib/)
ccflags-y += …이 디렉터리의 모든 C 파일에 컴파일 플래그 추가
CFLAGS_foo.o += …파일 하나에만 플래그 추가
subdir-ccflags-y하위 디렉터리까지 상속되는 플래그

obj-$(CONFIG_FOO) 트릭이 핵심이다. auto.conf가 include되면 CONFIG_FOO=y면 obj-y, =m이면 obj-m, n이면 변수 자체가 없어서 obj-가 되어 아무도 읽지 않는 변수가 된다. 조건문 없이 한 줄로 세 경우를 처리한다.

6.2 예제 14 — E2 드라이버의 Kbuild 파일과 소스#

무엇을 확인하나: composite 모듈(e2_hello.ko = e2_main.o + 조건부 e2_stats.o), 디렉터리 전체 플래그(ccflags-y), 파일 하나 플래그(CFLAGS_e2_stats.o)를 다 쓰는 작은 드라이버를 만든다. 모듈 이름 e2_hello와 같은 이름의 .c가 없어야 composite가 된다는 점에 주의한다(e2_hello.c가 있으면 Kbuild가 단일 파일 모듈로 해석한다).

e2_stats.h의 "꺼지면 빈 static inline" 패턴은 커널 헤더 전체에서 쓰는 관용구다. 호출하는 쪽(e2_main.c)에 #ifdef가 하나도 필요 없다.

6.3 재귀와 링크 순서 — 누가 먼저 링크되나#

그림 5 — Kbuild 재귀와 링크 순서. 최상위 Kbuild 파일의 obj-y 나열 순서(init → usr → arch → kernel/mm/fs … → drivers → sound/net …)가 그대로 vmlinux.a의 오브젝트 순서가 되고, 이것이 같은 initcall 레벨 안에서의 실행 순서를 정한다.

예제 15 — 무엇을 확인하나: 최상위 순서, 각 단계의 아카이브 내용, 그리고 그 순서가 System.map과 initcall에 어떻게 남는지 본다. (E2_HELLO=y로 빌드한 직후 상태.)

출력에서 볼 것:

  • 내장(y)일 때 composite e2_hello.o는 만들어지지 않는다. 구성 파일 e2_main.o, e2_stats.o가 그대로 built-in.a에 들어간다(모듈일 때는 §9에서 LD [M] e2_hello.o가 생긴다).
  • built-in.a와 vmlinux.a는 thin archive다 — .o 내용을 복사하지 않고 경로만 기록한다(ar 옵션 T). 수천 개 오브젝트를 매번 복사하지 않으려는 최적화다.
  • vmlinux.a 안에서 amba-pl011.o(465번째)가 e2_main.o(496번째)보다 앞이다. drivers/Makefile에서 tty/가 misc/보다 먼저 나오기 때문이다. 둘 다 module_init(= device_initcall, 레벨 6)이므로 링크 순서대로 실행된다 — UART 드라이버가 먼저 probe되고 E2가 나중이다. 부팅 로그에서도 PL011 메시지가 e2_hello보다 먼저 찍힌다(§6.4).
  • __initcall__kmod_e2_hello__412_36_e2_hello_init6 — module_init()이 내장 빌드에서 만든 initcall 테이블 항목이다. 끝의 6이 레벨이고, 412_36은 매크로가 붙인 고유 번호와 줄 번호(36번째 줄 module_init)다.
  • e2_hello_init은 소문자 t(로컬 텍스트), .init.text 섹션에 있어서 부팅 후 Freeing unused kernel memory로 해제된다.

lib/는 조금 특별하다. 최상위 Makefile이 libs-y := lib/를 lib/lib.a로 바꿔 KBUILD_VMLINUX_OBJS(= built-in.a lib/lib.a + arch/arm64/lib/lib.a)에 넣고, scripts/Makefile.vmlinux_o가 --whole-archive vmlinux.a로 링크한다. 옛날 커널에서 lib-y는 "필요한 오브젝트만 뽑아 쓰는 진짜 라이브러리"였지만, 6.18에서는 vmlinux.a에 합쳐져 결국 전부 링크된다(ar t vmlinux.a에 lib/ctype.o가 566번째로 들어 있는 것을 확인했다).

7. 빌드 들여다보기 — V=1, V=2, 단일 타깃#

7.1 예제 16 — make V=1로 진짜 gcc 명령 보기#

무엇을 확인하나: 한 파일을 컴파일할 때 Kbuild가 붙이는 플래그 전체를 본다. B4 §7.1에서 out-of-tree 모듈로 일부를 봤으니, 여기서는 트리 안, tinyconfig 기반 설정에서의 전체 명령을 줄 단위로 쪼개 본다(105줄 중 핵심만 남기고 ...로 줄였다).

출력에서 볼 것:

  • -Wp,-MMD,…/.e2_main.o.d — 헤더 의존성 파일(B4 §3). Kbuild는 이걸 그대로 쓰지 않고 fixdep으로 가공한다(§8).
  • -include …/kconfig.h — 모든 파일에 autoconf.h가 강제로 들어가는 지점. 그래서 드라이버는 CONFIG_*를 include 없이 쓴다.
  • -I./include, -I./arch/arm64/include/generated — O= 빌드라서 생성 헤더는 출력 디렉터리(현재 디렉터리 .)에서, 소스 헤더는 /var/tmp/E2/src에서 찾는다. 소스 트리를 깨끗하게 유지하는 원리다. 반대로 소스 트리에 .config나 생성 파일이 남아 있으면 O= 빌드가 "source tree is not clean, please run 'make mrproper'"로 거부한다.
  • -Os — tinyconfig가 CC_OPTIMIZE_FOR_SIZE=y로 바꾼 결과. defconfig는 -O2다. Kconfig 값이 컴파일 플래그까지 바꾼다.
  • -mgeneral-regs-only, -fno-common, -Wframe-larger-than=2048 — FP/SIMD 금지, 커널 스택 프레임 2 KB 경고(E4).
  • 마지막 부분이 Makefile에서 온 것: ccflags-y의 -DE2_BUILD_TAG, 그리고 KBUILD_MODNAME='"e2_hello"' — composite이라 파일 이름(e2_main)이 아니라 모듈 이름이 들어간다. pr_fmt, /sys/module/<이름> 등이 이 값을 쓴다.

CFLAGS_e2_stats.o가 정말 그 파일에만 붙는지는 다른 파일을 컴파일시켜 확인했다.

V=2는 명령 대신 왜 다시 빌드하는지를 알려 준다. "왜 이게 또 컴파일되지?"를 추적할 때 쓴다(이때는 E2_HELLO=m 상태).

8. 실습 3 — 증분 빌드와 fixdep: 무엇을 건드리면 얼마나 다시 빌드되나#

8.1 직관 — 헤더는 비싸고, Kconfig 값은 싸다#

B4 §3에서 -MMD로 헤더 의존성을 추적하는 법을 봤다. 커널에는 문제가 하나 더 있다. 모든 파일이 autoconf.h(수천 개 #define)를 include하므로, 순진하게 하면 .config의 어느 한 줄만 바꿔도 전체가 다시 빌드된다. Kbuild는 이걸 fixdep으로 푼다.

  • 컴파일러가 만든 .e2_main.o.d(헤더 목록)를 scripts/basic/fixdep이 읽는다.
  • 소스와 헤더 본문에서 CONFIG_FOO 문자열을 찾아, 의존성 목록의 autoconf.h를 include/config/FOO 파일들로 바꿔 친다.
  • syncconfig는 값이 바뀐 심볼의 include/config/FOO 파일만 touch한다(conf_touch_deps()).
  • 결과: CONFIG_E2_HELLO_PERIOD_MS를 바꾸면 그 문자열이 들어 있는 파일만 다시 컴파일된다.

8.2 예제 18 — .cmd 파일 안의 심볼 의존성#

무엇을 확인하나: fixdep이 만든 .e2_main.o.cmd에 Kconfig 심볼이 의존성으로 들어 있는지 본다.

출력에서 볼 것:

  • e2_main.c가 쓰는 네 심볼(E2_STYLE_LOUD, E2_HELLO, GREETING, PERIOD_MS)이 각각 의존성이 됐다. E2_STYLE_LOUD는 꺼져 있는데도 들어 있다 — #ifdef CONFIG_E2_STYLE_LOUD가 소스에 있으니 그 값이 바뀌면 다시 빌드해야 하기 때문이다. $(wildcard …)라서 파일이 없어도(심볼이 n) 에러가 아니다.
  • BOOGER, FOO는 커널 헤더 주석에 들어 있는 예시 문자열(CONFIG_BOOGER, CONFIG_FOO)을 fixdep이 그대로 잡은 것이다. fixdep은 C 파서가 아니라 단순 문자열 스캐너다. 해롭지 않다(그런 심볼은 존재하지 않으니 파일도 안 생긴다).
  • .cmd 파일에는 이 의존성 외에 직전 컴파일 명령 전체도 저장된다. 다음 빌드에서 명령이 한 글자라도 다르면(ccflags-y 변경 등) 소스가 그대로여도 다시 컴파일한다(if_changed 규칙).

10. 빌드 산출물 지도 — vmlinux · Image · Image.gz · System.map · dtbs#

10.1 예제 21 — 산출물의 정체와 크기#

무엇을 확인하나: 각 산출물이 어떤 형식이고 크기가 왜 다른지 file, size, xxd로 본다.

출력에서 볼 것:

  • vmlinux — 링크 결과 ELF. 심볼과 섹션 정보가 있어서 gdb, addr2line, objdump, crash 분석에 쓴다. 부트로더는 이걸 직접 올리지 않는다. 랩 vmlinux가 162 MB인 것은 DEBUG_INFO=y(DWARF) 때문이고, size로 본 실제 메모리 이미지(text+data+bss)는 43 MB다. 랩은 pie executable(RELOCATABLE, KASLR용)이고 tuned는 tinyconfig가 RELOCATABLE을 꺼서 일반 executable이다.
  • Image — objcopy -O binary로 ELF 헤더와 디버그 정보를 벗긴 평평한 메모리 이미지. 펌웨어의 .bin과 같다. 파일 크기는 size의 text+data에 섹션 정렬 패딩이 더해진 정도이고(tuned: 3.13 MB → 3.43 MB), bss는 0으로 채울 영역이라 파일에 없다. 앞 64바이트가 arm64 부트 헤더다(Documentation/arch/arm64/booting.rst): 0x00의 1f20 03d5는 nop(EFI 스텁이 켜져 있으면 여기가 MZ), 0x04는 b primary_entry 분기, 0x10의 0x3b0000은 bss를 포함한 메모리상 크기(3.69 MB, 파일 3.43 MB보다 크다), 0x18의 0xa는 플래그(비트0=0 little-endian, 비트1–2=1 4K 페이지, 비트3=1 물리 주소 어디에나 배치 가능 — file이 읽은 정보가 이것), 0x38의 ARMd(ARM\x64)가 매직이다. U-Boot의 booti가 이 헤더를 읽는다(C3).
  • Image.gz — gzip 압축본. arm64 커널은 스스로 압축을 풀지 못한다(32-bit ARM의 zImage와 다르다). 그래서 압축 해제는 부트로더(U-Boot booti는 gzip 이미지를 지원)나 FIT 이미지가 맡는다. 플래시 공간과 적재 시간을 줄이려고 쓴다.
  • System.map — nm vmlinux의 정렬된 결과. Oops의 주소를 함수 이름으로 바꾸거나(KALLSYMS가 꺼진 커널에서 특히), 심볼이 내장인지 확인할 때 쓴다. tuned는 21,327줄, 랩은 224,024줄.

10.2 dtbs — 설정이 정하는 또 하나의 산출물#

출력에서 볼 것: make dtbs는 arch/arm64/boot/dts/<vendor>/Makefile의 dtb-$(CONFIG_ARCH_XXX) += board.dtb를 따른다. tinyconfig에는 SoC 플랫폼(ARCH_*)이 하나도 켜져 있지 않아서 0개, 랩 defconfig는 1,577개 dtb + 169개 overlay(dtbo)를 만들었다. 특정 보드 하나는 설정과 무관하게 make <vendor>/<board>.dtb로 빌드할 수 있다. 보드 DTS를 고치는 루프에서는 이 단일 타깃을 쓴다(D5).

그림 7 — 산출물이 어디로 가나. 주황(커널+DTB)은 부트 파티션이나 FIT로, 초록(모듈)은 rootfs로 간다. 파랑(vmlinux, System.map, .config)은 보드에 안 올리지만 반드시 빌드 번호와 함께 보관한다 — 현장에서 Oops 로그를 받았을 때 그 빌드의 vmlinux가 없으면 주소를 해석할 수 없다.

12. 커널 안에서는 무슨 일이 일어나나#

이 노트의 주제는 대부분 빌드 시간에 일어난다. 하지만 그 결과는 실행 시간의 커널 구조로 이어진다. 빌드 도구의 함수와 커널의 함수를 한 장에 놓는다.

그림 8 — 빌드 도구의 함수(위)와 실행 시간 커널의 함수(아래). 같은 module_init() 한 줄이 내장이면 initcall 테이블 항목이 되고, 모듈이면 struct module의 init 포인터가 된다. modpost가 빌드 시간에 하는 심볼 검사를 load_module()이 실행 시간에 한 번 더 한다.

12.1 Kconfig 엔진 — scripts/kconfig/#

  • parser.y/lexer.l이 1,880개 Kconfig 파일을 source를 따라가며 읽어 struct symbol(심볼)과 struct menu(메뉴 트리) 그래프를 만든다. if 블록과 menu의 의존성은 이때 안의 항목에 AND로 붙는다(예제 4에서 본 E2_DEMO [=y] && …).
  • symbol.c의 sym_calc_value()가 심볼 값을 계산한다. 개념적으로 값 = max(min(사용자값 또는 default, depends 상한), select 하한)이고, imply는 default 쪽에만 더해진다. select 하한이 depends 상한보다 크면 sym_warn_unmet_dep()가 예제 3의 "unmet direct dependencies" 경고를 찍는다.
  • confdata.c의 conf_write()가 .config를, conf_write_autoconf()가 auto.conf·autoconf.h를 쓰고, conf_touch_deps()가 값이 바뀐 심볼의 include/config/<SYM> 파일만 갱신한다.
  • conf(텍스트), mconf(menuconfig), nconf(nconfig), qconf/gconf는 같은 엔진 위의 서로 다른 UI다.

12.2 Kbuild 엔진 — scripts/Makefile.*, fixdep, modpost#

  • 최상위 Makefile이 auto.conf를 include하고, $(MAKE) -f scripts/Makefile.build obj=<dir>로 디렉터리마다 내려간다. Makefile.build가 그 디렉터리의 Makefile/Kbuild를 include해서 obj-y/obj-m/<name>-y를 읽고, built-in.a, composite .o, modules.order를 만든다.
  • scripts/basic/fixdep.c — 주석에도 적혀 있듯 "merely grep" 수준으로 CONFIG_ 문자열을 찾아 .cmd 파일에 include/config/<SYM> 의존성을 쓴다(예제 18의 BOOGER, FOO가 그 증거).
  • scripts/mod/modpost.c — read_symbols()로 각 모듈과 vmlinux의 심볼을 읽고, check_exports()가 미해결·GPL 위반을 잡고(예제 20), .mod.c를 생성하고, write_dump()가 Module.symvers를 쓴다.

12.3 실행 시간 — initcall과 모듈 로더#

  • 내장일 때 module_init(fn)은 include/linux/module.h에서 __initcall(fn) = device_initcall(fn) = __define_initcall(fn, 6)이 되어 .initcall6.init 섹션에 항목을 하나 넣는다(예제 15의 __initcall__kmod_e2_hello__…6). 링커 스크립트가 레벨별로 모은 이 표를 init/main.c의 do_initcalls() → do_initcall_level() → do_one_initcall()이 순서대로 부른다. 같은 레벨 안의 순서 = 링크 순서 = Makefile 순서다. 드라이버 간 probe 순서 문제를 Makefile 순서로 "해결"하는 코드를 가끔 보는데, 올바른 해법은 deferred probe나 device link다(D3 §10, G2).
  • 모듈일 때 insmod/modprobe는 finit_module() syscall로 .ko를 넘기고, kernel/module/main.c의 load_module()이 ELF를 재배치하고, check_modinfo()가 vermagic을 실행 중인 커널과 비교하고, 커널 export 표에서 미해결 심볼을 찾은 뒤, do_init_module()이 init 함수를 부른다. E3에서 이 경로를 직접 따라간다.

12.4 드라이버를 쓸 때 다시 만나는 지점#

15. 면접에서 이렇게 말한다#

Q. What is the difference between depends on and select in Kconfig? Why is select considered dangerous?

A. depends on은 내 심볼의 상한이다. 대상이 n이면 내 심볼은 존재하지 않고, m이면 나도 최대 m이다. select는 반대로 대상의 하한을 내 값으로 끌어올린다. 문제는 select가 대상의 depends를 보지 않는다는 점이다. 대상이 의존하는 서브시스템이 꺼져 있어도 켜져 버리고, Kconfig는 "unmet direct dependencies" 경고만 찍은 채 진행해서 링크 에러나 런타임 오류로 이어진다. 그래서 select는 프롬프트 없는 라이브러리 심볼에만 쓰고, 내가 그 라이브러리의 depends를 먼저 다 가지고 있게 한다. BMI270 I2C 드라이버가 depends on I2C와 select REGMAP_I2C를 같이 쓰는 게 정석 예다. 사용자가 끌 수 있어야 하는 추천이라면 imply를 쓴다.

depends on puts an upper bound on my symbol: if the dependency is n my symbol disappears, and if it's m I can be at most m. select does the opposite — it forces the target up to at least my value — and it ignores the target's own dependencies. So it can turn on something whose subsystem is disabled; Kconfig only prints an "unmet direct dependencies" warning and you get link errors or runtime failures later. The rule is to select only non-visible library symbols, and to make sure I already depend on everything the selected symbol depends on — for example an I2C sensor driver says depends on I2C and select REGMAP_I2C. If it's just a recommendation the user should be able to turn off, I use imply.

꼬리 질문: "imply는요?" → 대상의 기본값만 올리고 대상의 depends는 존중한다. 사용자가 n으로 내리면 그대로 n이다. 직접 olddefconfig로 여섯 조합을 돌려 확인했다.

Q. How do you add a new driver to the kernel source tree so it builds as a module or built-in?

A. 세 군데를 고친다. 드라이버 디렉터리에 tristate로 Kconfig 항목을 만들고 필요한 버스는 depends on으로 건다. 같은 디렉터리 Makefile에 obj-$(CONFIG_FOO) += foo.o를 쓰고, 파일이 여러 개면 foo-y := a.o b.o로 composite를 만든다. 그리고 부모 Kconfig에 source, 부모 Makefile에 obj-$(CONFIG_FOO) += foo/를 추가한다. .config가 y면 built-in.a를 거쳐 vmlinux에, m이면 modpost를 거쳐 foo.ko가 된다. 같은 소스를 두 방식으로 빌드해 부팅 로그에서 IS_BUILTIN/IS_MODULE 값이 바뀌는 것까지 확인해 봤다.

Three places. In the driver's directory I add a tristate Kconfig entry with depends on for the bus it needs, and a Makefile line obj-$(CONFIG_FOO) += foo.o — or a composite foo-y := a.o b.o if there are several files. Then the parent Kconfig sources the new Kconfig and the parent Makefile descends into the directory with obj-$(CONFIG_FOO) += foo/. If the option is y, the objects go into built-in.a and get linked into vmlinux; if it's m, modpost generates the module glue and you get foo.ko. I've built the same driver both ways and watched IS_BUILTIN and IS_MODULE flip in the boot log.

Q. Why does the kernel use IS_ENABLED(CONFIG_FOO) instead of #ifdef CONFIG_FOO?

A. 두 가지 이유다. 첫째, tristate가 m이면 autoconf.h에는 CONFIG_FOO_MODULE만 정의되므로 #ifdef CONFIG_FOO는 모듈 빌드에서 거짓이 된다 — 실제로 같은 코드가 내장일 때 1, 모듈일 때 0을 찍었다. IS_ENABLED는 y와 m 둘 다 참이다. 둘째, if (IS_ENABLED(...))는 일반 C 조건문이라 꺼져 있어도 그 코드가 컴파일러의 문법·타입 검사를 받고 나서 제거된다. #ifdef로 가린 코드는 그 설정으로 빌드하기 전까지 깨져도 모른다.

Two reasons. For a tristate set to m, autoconf.h only defines CONFIG_FOO_MODULE, so #ifdef CONFIG_FOO is false in a modular build — I've seen the same code print 1 built-in and 0 as a module. IS_ENABLED is true for both y and m. Second, IS_ENABLED is a constant expression you can use in a normal if, so the disabled branch is still parsed and type-checked before the compiler drops it, whereas code hidden behind #ifdef can rot unnoticed until someone builds that configuration.

꼬리 질문: "IS_REACHABLE은?" → 내장 코드가 모듈로 빌드된 기능을 부르려 할 때 거짓이 된다. Kconfig에서 depends on FOO || !FOO로 막는 것이 보통이다.

Q. What is a defconfig and how do you manage kernel configuration for a product?

A. .config는 1만 줄이 넘고 툴체인이 감지한 값까지 들어 있어서 소스로 관리하기 나쁘다. 그래서 기본값과 다른 줄만 남긴 defconfig(make savedefconfig)를 git에 넣고 make <board>_defconfig로 .config를 재생성한다. 우리 변경은 보드·기능별 fragment로 나누고 merge_config.sh로 합친다. 커널을 올릴 때는 olddefconfig 후 listnewconfig와 diffconfig로 무엇이 바뀌었는지 리뷰한다. 랩 커널을 savedefconfig로 줄여 보니 arm64 defconfig와 정확히 3줄 차이였다 — 1만 줄 diff로는 못 찾는 정보다.

The full .config is over ten thousand lines and includes values detected from the toolchain, so it's a bad thing to version. Instead I keep a minimal defconfig from make savedefconfig in git and regenerate .config with make board_defconfig. Our own changes live in small fragments per feature, merged with merge_config.sh, and in CI I check that the requested values actually made it into the final .config, because Kconfig silently drops values whose dependencies aren't met. On a kernel upgrade I run olddefconfig, then review listnewconfig and diffconfig output.

Q. What's the difference between vmlinux, Image, and Image.gz on arm64? What is System.map?

A. vmlinux는 링크 결과 ELF로 심볼과 디버그 정보가 있어서 gdb나 Oops 해석에 쓰고, 보드에 올리지 않는다. Image는 objcopy로 ELF를 벗긴 평평한 바이너리에 64바이트 arm64 부트 헤더(매직 ARM\x64, 메모리상 크기, 플래그)가 붙은 것으로, U-Boot booti가 적재한다. Image.gz는 그 gzip본인데, arm64 커널은 32-bit의 zImage처럼 스스로 압축을 풀지 못해서 부트로더가 푼다. System.map은 심볼 주소표다. 랩 커널은 vmlinux 162 MB(디버그 정보), Image 42.7 MB, Image.gz 15.2 MB였다.

vmlinux is the linked ELF with symbols and possibly DWARF — you keep it for gdb and for decoding oopses, but you don't flash it. Image is vmlinux run through objcopy into a flat binary, with the 64-byte arm64 boot header — magic, image size including BSS, flags — that U-Boot's booti reads. Image.gz is just that compressed; unlike 32-bit zImage, arm64 has no self-decompressor, so the bootloader or a FIT image handles decompression. System.map is the sorted symbol table you use to turn addresses into function names.

Q. You changed one Kconfig option and the rebuild was quick, but touching one header rebuilt everything. Why?

A. 모든 파일이 autoconf.h를 include하지만, Kbuild의 fixdep이 의존성을 autoconf.h 대신 include/config/<심볼> 파일 단위로 바꿔 쓴다. syncconfig는 값이 바뀐 심볼의 파일만 touch하므로 그 문자열이 들어 있는 소스만 다시 컴파일된다. 실제로 정수 옵션 하나를 바꾸니 파일 하나만 다시 컴파일됐다. 반면 printk.h를 touch하면 그걸 include하는 563개가 전부 다시 컴파일됐다. 헤더 의존성은 파일 단위이기 때문이다.

Every file includes autoconf.h, but fixdep rewrites the dependency list so that instead of depending on autoconf.h, each object depends on one small file per CONFIG symbol it mentions, under include/config. syncconfig only touches the files for symbols whose value changed, so only the sources that mention that symbol rebuild — I measured one file for an int option. Header dependencies are per file, though, so touching printk.h rebuilt 563 objects in my tiny config.

Q. How do you cross-compile the kernel, and what are the common mistakes?

A. ARCH로 아키텍처 디렉터리와 Kconfig 루트를, CROSS_COMPILE로 툴체인 접두어를 정하고, 설정부터 빌드까지 모든 make 명령에 같은 값을 준다. 흔한 실수는 세 가지다. ARCH 없이 menuconfig를 돌리면 호스트 아키텍처 Kconfig로 설정이 조용히 덮어써진다. 설정할 때와 빌드할 때 컴파일러가 다르면 CC_VERSION_TEXT가 바뀌어 설정이 재계산된다. CROSS_COMPILE을 빼면 호스트 gcc가 -mabi=aapcs-linux 같은 플래그를 몰라 바로 실패한다. 세 경우 모두 실제로 재현해 봤다.

ARCH selects the arch directory and Kconfig root, CROSS_COMPILE is the toolchain prefix, and you pass the same values to every make invocation, configuration included — I export them in the build script. The classic mistakes: running menuconfig or olddefconfig without ARCH silently rewrites the config for the host architecture; configuring with one compiler and building with another makes Kconfig resync because compiler-dependent symbols change; and forgetting CROSS_COMPILE makes the host gcc choke on ARM-specific flags.

18. 요약 & 체크리스트#

커널 빌드는 세 층이다. Kconfig는 2만 개가 넘는 심볼의 타입·기본값·의존성을 정의하고, sym_calc_value()가 depends on(상한)·select(depends를 무시하는 강제 하한)·imply(기본값 추천)를 계산해 .config를 만든다. 빌드 시작 때 syncconfig가 이를 auto.conf(make 변수), autoconf.h(C 매크로, m이면 _MODULE 접미사), include/config/<SYM>(심볼 단위 타임스탬프)로 번역한다. Kbuild는 최상위 Kbuild의 순서대로 디렉터리를 재귀하며 obj-y를 built-in.a로 모아 vmlinux.a → vmlinux → Image(→ Image.gz)를 만들고, 이 링크 순서가 같은 레벨 initcall의 실행 순서가 된다. obj-m은 부분 링크 후 modpost가 심볼 검사·.mod.c·Module.symvers를 만들어 .ko가 되고, modules_install이 lib/modules/<release>/에 depmod 색인과 함께 설치한다. 설정은 savedefconfig로 줄인 defconfig와 fragment로 관리하고, fragment 값이 의존성 때문에 조용히 버려질 수 있으니 검증한다. 실습에서 tinyconfig + 13줄로 3.4 MB짜리 부팅 가능한 커널을 만들었고(defconfig 42.7 MB), Kconfig 정수 하나 변경은 파일 1개, 전역 헤더 하나는 560개 이상을 다시 컴파일시켰다. 크로스 빌드는 모든 명령에 같은 ARCH·CROSS_COMPILE을 준다.
