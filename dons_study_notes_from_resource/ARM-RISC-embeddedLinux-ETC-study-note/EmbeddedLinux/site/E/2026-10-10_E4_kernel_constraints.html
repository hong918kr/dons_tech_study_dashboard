이 노트를 다 읽으면: libc·FPU·큰 스택·sleep·유저 포인터 같은 "앱에서는 당연한 것"이 커널에서 왜 금지되는지 실제 컴파일 에러·Oops 로그로 보여 줄 수 있다 · 커널 스택 16 KiB와 VMAP_STACK guard page, atomic context와 GFP 플래그를 설명할 수 있다 · Oops 로그를 위에서부터 읽고 faddr2line으로 소스 줄을 찾을 수 있다 · checkpatch.pl·sparse·-Wframe-larger-than·slab redzone 같은 도구로 이 제약 위반을 미리 잡을 수 있다 왜 필요한가: "What's different about writing kernel code vs userspace code?"는 드라이버 면접의 단골 첫 질문이고, 실무 첫 버그의 대부분(스핀락 안의 msleep, 스택 위 큰 버퍼, 유저 포인터 직접 접근)이 이 목록에서 나온다 Don 기준 난이도: libc 없음·FPU 제한·작은 스택·ISR 안에서 블로킹 금지는 bare-metal 펌웨어에서 이미 몸에 익었다 / 새로 배울 부분은 "같은 주소 공간을 수천 개 모듈과 나눠 쓴다", "선점·SMP가 기본", "유저 공간이라는 신뢰할 수 없는 이웃", 그리고 이걸 잡아 주는 커널의 디버그 장치들 선행 노트: B1(커널 빌드 플래그), E1(커널 아키텍처), E3(커널 모듈) — E5(커널 C 관용구)·E6(유저↔커널 경계)·F2/F4(동기화)·F9(메모리 할당)·M3(Oops 분석)으로 이어진다

0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어를 쓸 때의 규칙을 떠올려 보자. printf는 UART 링버퍼에 넣는 자체 함수였고, malloc은 없거나 부팅 때 한 번만 쓰는 풀 할당자였고, 스택은 링커 스크립트에 __stack_size = 0x1000처럼 박혀 있었고, ISR 안에서는 절대 기다리지 않았다. 여기까지는 Linux 커널도 똑같다. 커널 코드는 펌웨어처럼 "맨바닥" 위에서 돈다. 밑에서 받쳐 주는 libc도, 잘못된 접근을 잡아서 프로세스만 죽여 주는 운영체제도 없다. 커널이 바로 그 운영체제다.

다른 점은 이웃이 많다는 것이다. 펌웨어는 한 팀이 쓴 코드 수만 줄이 한 칩을 독점한다. 커널 모듈은 수천 명이 쓴 수백만 줄과 같은 주소 공간, 같은 특권 레벨(EL1) 에서 돈다. 내 드라이버가 8바이트를 넘쳐 쓰면 옆 객체(네트워크 스택의 버퍼일 수도, 파일 시스템의 inode일 수도)가 조용히 망가진다. 게다가 CPU가 여러 개고(SMP), 언제든 선점(preemption)되고, 인터럽트가 끼어들고, 위에서는 믿을 수 없는 유저 프로세스가 포인터를 넘긴다.

그림 1 — 세 세계의 바닥. 유저 앱 밑에는 libc와 커널이라는 두 겹의 안전망이 있다. 커널 코드 밑에는 하드웨어뿐이고, 옆에는 벽 없는 이웃(나머지 커널)이 있다.

1. 실습 준비 — 모듈 하나 = QEMU 부팅 하나#

1.1 실행 환경#

이 노트의 모든 커널 코드는 랩 커널(Linux 6.18.55 arm64, QEMU virt)에서 돌렸다. 일부 예제는 위험한 짓을 일부러 해서 게스트를 panic시키므로, VM 호스트 커널(uname -r → 7.0.0-38-generic)이 아니라 일회용 QEMU 게스트에만 넣는다.

출력에서 볼 것: 랩 커널(arm64 defconfig 기반)은 DEBUG_ATOMIC_SLEEP과 SOFTLOCKUP_DETECTOR가 꺼져 있다. 양산 커널도 흔히 그렇다. §5와 §12는 이 차이 자체가 교재다 — 같은 버그가 디버그 옵션이 없으면 어떻게 숨어 버리는지 먼저 보고, 그다음 두 옵션만 켠 커널 복사본(/var/tmp/E4/kbuild, LOCALVERSION=-e4dbg)을 따로 빌드해서 같은 모듈을 다시 돌린다.

2. libc가 없다 — 그럼 무엇을 쓰나#

2.1 직관#

유저 앱의 printf·malloc·strtol은 glibc 함수이고, glibc는 결국 write()·mmap() 같은 syscall을 부른다. 커널은 syscall을 받는 쪽이니 glibc를 쓸 수 없다(자기 자신을 부르는 셈). 펌웨어에서 newlib의 _write stub을 직접 UART로 연결했던 것과 같은 상황인데, 커널은 아예 libc를 링크하지 않고 필요한 함수를 커널 안에 다시 구현해 두었다: lib/string.c(문자열), lib/vsprintf.c(snprintf), lib/kstrtox.c(숫자 파싱), lib/sort.c(정렬), mm/slub.c(kmalloc).

2.2 예제 2 — #include <stdio.h>는 어디서 막히나#

무엇을 확인하나: 커널 모듈에서 libc 헤더를 include하면 무슨 일이 생기는지.

출력에서 볼 것: 링크 단계가 아니라 전처리 단계에서 막힌다. VM에는 /usr/include/stdio.h가 분명히 있는데도 못 찾는다. 이유는 다음 예제의 -nostdinc다.

3. 부동소수점·NEON은 기본 금지#

3.1 직관 — 왜 금지인가#

유저 프로세스가 syscall이나 인터럽트로 커널에 들어올 때 커널은 정수 레지스터(x0~x30)만 저장한다. FP/SIMD 레지스터(v0~v31, 각 128비트 = 512 B, SVE면 더 큼)는 저장하지 않는다. 커널이 그 레지스터를 안 건드린다고 약속했기 때문이고, 그 덕분에 syscall 진입·탈출이 빠르다. 커널 코드가 float를 쓰면 컴파일러가 v0~v31을 쓰는 명령을 내고, 유저 프로세스의 FP 레지스터 값이 몰래 바뀐다 — 유저 앱의 double 계산 결과가 가끔 틀리는 최악의 버그다.

펌웨어 비유: Cortex-M4F에서 ISR이 FPU를 쓰면 lazy stacking으로 S0~S15를 자동 저장한다. 커널은 이 "자동 저장"을 일부러 하지 않는 대신 FPU를 쓰지 않겠다는 계약을 컴파일러 플래그(-mgeneral-regs-only)로 강제한다.

무엇을 확인하나: 센서 raw 값을 m/s² 로 바꾸는 "앱이라면 평범한" 코드가 커널 빌드에서 어떻게 막히는지.

커널식 해법은 고정소수점(fixed-point) 이다. Don이 펌웨어에서 늘 하던 것과 같다: accel_x100 = raw * 981 / 100;. IIO 서브시스템(I2)은 아예 정수 raw 값 + scale(정수부·소수부 두 정수)만 커널이 내보내고 실수 변환은 유저 공간이 하도록 설계돼 있다.

3.3 그래도 FP/SIMD가 꼭 필요하면 — 커널 FPU 구간#

암호(AES·SHA·CRC), RAID6 패리티, XOR 같은 곳은 NEON이 몇 배 빠르므로 커널도 쓴다. 규칙(Documentation/core-api/floating-point.rst):

  1. FP 코드는 별도의 .c 파일에 둔다.
  2. 그 파일만 CFLAGS_<file>.o += $(CC_FLAGS_FPU), CFLAGS_REMOVE_<file>.o += $(CC_FLAGS_NO_FPU)로 컴파일한다.
  3. 호출하는 쪽(일반 파일)에서 kernel_fpu_begin()/kernel_fpu_end()로 감싼다. arm64에서는 asm/fpu.h가 이를 kernel_neon_begin()/kernel_neon_end()로 정의한다.

4. 작고 고정된 커널 스택 — 16 KiB, 넘치면 panic#

4.1 직관#

유저 프로세스의 메인 스레드 스택은 기본 8 MiB(ulimit -s)이고 모자라면 page fault로 자동으로 늘어난다. 커널은 스레드(태스크)마다 스택을 하나씩 따로 갖는데, 수천 개 태스크가 각각 메가바이트 단위 스택을 가지면 메모리가 남아나지 않는다. 그래서 커널 스택은 작고, 고정 크기이며, 늘어나지 않는다. 펌웨어의 링커 스크립트 스택(__stack_size = 0x1000)과 같은 처지다. 다른 점은 태스크 수가 동적이라는 것, 그리고 넘쳤을 때 잡아 주는 장치(guard page)가 있다는 것이다.

4.2 정의 — arm64의 THREAD_SIZE는 어디서 정해지나#

랩 소스 arch/arm64/include/asm/memory.h:

읽는 법:

  • 기본 1 << 14 = 16 KiB. KASAN을 켜면 KASAN_THREAD_SHIFT가 1이 되어 32 KiB(계측 코드가 스택을 더 먹으므로). 64K 페이지 커널이면 PAGE_SHIFT(16)가 더 커서 64 KiB.
  • IRQ_STACK_SIZE도 16 KiB이고 CPU마다 하나씩 따로 있다. 하드웨어 인터럽트와 softirq는 이 IRQ 스택에서 돈다 (태스크 스택을 더 깊게 파먹지 않도록).
  • OVERFLOW_STACK_SIZE 4 KiB — 스택이 넘쳤을 때 panic 메시지를 찍기 위해서만 쓰는 CPU별 비상 스택.
  • 32비트 ARM은 8 KiB(THREAD_SIZE_ORDER 1), x86-64는 16 KiB(KASAN 시 더 큼)다. 면접에서는 "아키텍처마다 다르고 보통 8~16 KiB"라고 답한다.

무엇을 확인하나: 실제 THREAD_SIZE, 스택이 vmalloc 영역에 있는지(VMAP_STACK), module_init이 불렸을 때 이미 쓴 스택, 타이머 콜백(softirq)은 어느 스택에서 도는지 — 그리고 depth 파라미터를 주면 재귀로 스택을 소진한다.

출력에서 볼 것 (주소는 실행마다 다르다):

4.7 재귀는 사실상 금지 — 대신 무엇을 쓰나#

재귀 자체가 문법적으로 금지된 것은 아니다. 커널에도 깊이가 증명된 재귀(예: 디렉터리 트리 depth 제한이 있는 경로)는 있다. 하지만 입력에 따라 깊이가 정해지는 재귀(DT 노드 트리, 유저가 준 중첩 데이터, 링크드 리스트 길이)는 16 KiB 예산에서 언젠가 터진다. 예제 8에서 겨우 560 B 프레임 27개로 죽었다.

대안: (1) 명시적 스택/큐를 힙에 두는 반복문, (2) 깊이 상한을 두고 넘으면 -ELOOP/-E2BIG 반환, (3) 트리 순회는 커널이 제공하는 반복자(for_each_child_of_node, list_for_each_entry, rb_first/rb_next) 사용. MISRA C의 "재귀 금지" 규칙을 지켜 온 Don에게는 익숙한 규칙이다.

5. atomic context에서는 잠들 수 없다#

5.1 직관#

펌웨어 규칙 "ISR 안에서 vTaskDelay()나 세마포어 대기를 하지 마라"의 커널판이다. 다만 커널에는 ISR 말고도 잠들면 안 되는 곳이 더 많다: 스핀락을 잡고 있을 때, 선점을 끈 구간, softirq·tasklet·타이머 콜백. 이런 곳을 통틀어 atomic context라고 부른다. 반대로 syscall 핸들러·probe()·kthread·workqueue는 process context이고 잠들 수 있다.

"잠든다(sleep)"는 정확히 말해 schedule()을 불러 CPU를 다른 태스크에 넘기는 것이다. msleep, mutex_lock(경합 시), wait_event, kmalloc(GFP_KERNEL)(메모리 회수가 필요할 때), copy_from_user(page fault 처리 시), I2C/SPI 동기 전송이 전부 잠들 수 있다.

왜 atomic에서 잠들면 안 되나:

  • 스핀락을 잡은 채 잠들면, 같은 CPU에서 다음에 도는 태스크가 그 락을 잡으려 할 때 영원히 스핀한다 (락 주인은 잠들어 있고, 이 CPU는 선점이 꺼져 있어 주인을 깨워 돌릴 수 없다).
  • 인터럽트 핸들러는 "태스크"가 아니라서 재울 대상(task_struct)이 없다. 끼어든 태스크가 대신 잠들어 버린다.

그림 3 — 커널 실행 문맥 지도. 같은 드라이버 함수라도 spin_lock()을 잡는 순간 오른쪽 세계로 넘어가고(→), 오른쪽에서 잠들어야 하는 일은 workqueue로 왼쪽에 넘긴다(←). 경계 판정은 preempt_count(include/linux/preempt.h) 하나로 한다.

  • mode=2가 이제 잡힌다. 할당은 여전히 성공했지만(p=ok), kmalloc 입구의 might_alloc(GFP_KERNEL) → might_sleep_if() → __might_resched()가 "이 문맥에서 잠들 수도 있는 함수를 불렀다"고 외쳤다. 위치 include/linux/sched/mm.h:321이 바로 might_alloc()의 might_sleep_if(gfpflags_allow_blocking(gfp_mask)) 줄이다.
  • preempt_count: 1, expected: 0 — 스핀락 하나를 잡고 있다는 뜻. irqs_disabled(): 0이므로 spin_lock_irqsave가 아닌 spin_lock이었다는 것까지 알 수 있다.
  • mode=1(msleep)은 디버그 커널에서도 "sleeping function called…"가 아니라 "scheduling while atomic"이었다. msleep() 경로 앞부분에는 might_sleep() 주석이 없고 실제 schedule()에서야 걸린 것이다. 두 메시지의 차이: "scheduling while atomic" = 실제로 잠들었다(사고 발생), "sleeping function called from invalid context" = 잠들 수 있는 함수를 불렀다(사고 예고).
  • 결론: 드라이버 개발·CI 커널에는 CONFIG_DEBUG_ATOMIC_SLEEP=y(+ lockdep CONFIG_PROVE_LOCKING)를 켠다. 양산 커널은 성능 때문에 끄는 경우가 많다.

6. 메모리 할당은 실패할 수 있고, "기다려도 되나"를 알려야 한다#

6.1 직관#

유저 공간의 malloc은 Linux의 overcommit 때문에 거의 실패하지 않는다(대신 나중에 OOM killer가 온다). 커널 할당은 다르다. (1) 커널은 자기 메모리를 스왑할 수 없고, (2) kmalloc은 물리적으로 연속인 메모리를 줘야 하므로 메모리가 조각나면 큰 크기는 실패하며, (3) 호출자가 atomic context에 있으면 메모리 회수를 기다릴 수도 없다. 그래서 커널 할당 API는 크기와 함께 GFP 플래그("Get Free Pages" 플래그)로 "이 할당을 위해 무엇을 해도 되는가"를 받는다.

플래그잠들어도 되나쓰는 곳
GFP_KERNEL예 (reclaim, I/O, FS 콜백 가능)process context 기본값, probe(), ioctl
GFP_ATOMIC아니오. 비상 예비분까지 사용IRQ 핸들러, 스핀락 안, softirq
GFP_NOWAIT아니오. 비상 예비분은 안 씀실패해도 되는 기회성 할당
GFP_NOIO / GFP_NOFS예, 단 블록 I/O / FS 재진입 금지블록 드라이버·FS 내부 (요즘은 memalloc_noio_save() 범위 API 권장)
GFP_DMA / GFP_DMA32플래그 조합주소 제한 있는 오래된 DMA 장치 (보통은 DMA API 사용)
__GFP_ZERO수식자0으로 채움 (kzalloc = kmalloc + 이것)
__GFP_NOWARN수식자실패 경고 출력 안 함

더 깊은 내용(slab 캐시, 페이지 할당자, CMA)은 F9에서 다룬다.

6.2 예제 12 — 실패 경로와 할당자별 비용 (e4_alloc)#

무엇을 확인하나: (1) kmalloc에는 최대 크기가 있고 그보다 크면 무조건 실패하는지, (2) init이 실패를 돌려주면 유저가 무엇을 보는지, (3) kmalloc/kzalloc/vmalloc 비용이 크기에 따라 어떻게 다른지.

출력에서 볼 것:

  • kmalloc(8 MiB)는 메모리가 남아도 실패한다. KMALLOC_MAX_SIZE = 1 << (MAX_PAGE_ORDER + PAGE_SHIFT) = 2^(10+12) = 4 MiB가 상한이다(include/linux/slab.h, CONFIG_ARCH_FORCE_MAX_ORDER=10). __GFP_NOWARN을 빼면 커널이 경고 스택을 찍는다. vmalloc은 물리 페이지를 낱장으로 모아 가상으로만 이어 붙이므로 8 MiB도 된다.
  • fail=1: init이 -ENOMEM을 돌려주자 insmod가 Cannot allocate memory로 실패했다(§9).
  • 비용(그림 5): 작은 크기에서 kmalloc은 수백 ns(slab per-CPU 캐시에서 꺼내기), vmalloc은 수 µs(페이지 할당 + 페이지 테이블 매핑 + 해제 시 TLB 처리)로 10~20배 비싸다. 8 KiB(KMALLOC_SHIFT_HIGH = PAGE_SHIFT + 1)를 넘는 kmalloc은 slab이 아니라 페이지 할당자로 직행해서 µs 단위가 된다. kzalloc의 추가 비용은 순수하게 memset이라 크기에 비례한다 — 128 KiB에서는 vmalloc(이 벤치는 페이지를 0으로 채우지 않음)보다도 비싸다.
  • 이 숫자는 QEMU TCG(명령어 번역 에뮬레이션) 위의 값이라 실제 Cortex-A 하드웨어보다 수 배 느리고, 특히 memset 같은 메모리 집약 코드가 과장된다. 4 KiB kmalloc은 같은 모듈의 이전 실행 두 번에서 294 ns, 303 ns였다 — 974 ns는 TCG 잡음이다. 상대적인 순서(kmalloc < vmalloc, kzalloc ∝ 크기)만 믿는다.

그림 5 — 예제 12에서 직접 잰 할당+해제 비용 (로그 축). 작은 객체는 kmalloc, 크고 물리 연속이 필요 없으면 vmalloc(또는 kvmalloc: 먼저 kmalloc을 시도하고 실패하면 vmalloc), 0 초기화가 꼭 필요할 때만 kzalloc. DMA 버퍼는 셋 다 아니고 DMA API(H8)다.

6.3 할당 규칙 요약#

  • 반환값은 항상 검사한다. kmalloc이 NULL을 돌려줄 수 있다는 전제에서 코드를 쓴다. checkpatch는 kmalloc 실패 후의 pr_err("out of memory" 메시지)를 오히려 지적한다 — 할당자가 이미 경고를 찍기 때문이다.
  • 문맥에 맞는 GFP: process context면 GFP_KERNEL, atomic이면 GFP_ATOMIC. atomic에서 큰 할당이 필요해 보이면 설계를 바꾼다: probe()에서 미리 할당하거나, 메모리 풀(mempool_create)을 쓰거나, 일을 workqueue로 넘긴다.
  • 드라이버는 가능하면 devm_kzalloc(&pdev->dev, ...) — probe() 실패나 remove() 때 자동 해제(G6).
  • vmalloc 메모리는 물리적으로 연속이 아니므로 DMA에 그대로 쓰지 못한다(F9, H8).

7. 유저 포인터는 절대 직접 역참조하지 않는다#

7.1 직관#

write(fd, buf, len)의 buf는 유저 프로세스의 가상 주소다. 커널 입장에서 그 값은 "남이 적어 준 주소 쪽지"일 뿐이다: 매핑이 안 돼 있을 수도(NULL+16), 스왑아웃돼 있을 수도, 아예 커널 주소일 수도 있다(악의적인 유저가 커널 비밀을 읽거나 덮어쓰게 하려고). Don의 SSD 펌웨어가 호스트 NVMe 명령의 PRP 주소를 그대로 DMA에 쓰지 않고 범위·정렬을 먼저 검사했던 것과 같은 원리다.

그래서 유저 메모리는 반드시 copy_from_user/copy_to_user/get_user/put_user로만 접근한다. 이 함수들은 (1) access_ok()로 주소가 유저 영역인지 검사하고, (2) 접근 중 page fault가 나면 exception table(__ex_table)에 등록된 복구 지점으로 점프해 "복사 못 한 바이트 수"를 돌려준다. Oops 대신 -EFAULT가 되는 비결이다. 자세한 경로는 E6.

7.2 예제 13 — misc device로 copy_from_user vs 직접 역참조 (e4_uptr)#

무엇을 확인하나: 같은 write 핸들러에서 copy_from_user를 쓰면 잘못된 포인터가 -EFAULT로 끝나는지, 유저 포인터를 그냥 역참조하면 어떻게 되는지.

유저 쪽 테스트 프로그램 (VM에서 gcc -static으로 빌드해 initramfs에 넣었다):

첫 번째 실행: -cpu cortex-a57 (랩 기본, ARMv8.0)

출력에서 볼 것:

  • copy_from_user 경로: 정상 버퍼는 복사, NULL+16은 -EFAULT(유저에게 "Bad address"). 커널은 멀쩡하다.
  • 커널 주소를 넘긴 경우에는 내 드라이버 로그가 아예 없다. vfs_write()가 드라이버를 부르기 전에 access_ok(buf, count)로 먼저 걸러 -EFAULT를 돌려줬다. 그래도 드라이버는 이 검사에 기대지 말고 늘 copy_from_user를 쓴다 (ioctl 인자 안의 포인터처럼 VFS가 모르는 포인터가 많다).
  • direct=1인데도 "잘 동작"했다. Cortex-A57(ARMv8.0)에는 PAN이 없어서, 커널 모드(EL1)에서 유저 페이지를 그냥 읽을 수 있다. 이 버그는 개발 보드에서는 영원히 숨어 있다가, ARMv8.1 이상 칩이나 x86(SMAP)에서 터진다. 다만 유저가 매핑 안 된 주소를 넘기면 A57에서도 Oops가 난다 — 직접 역참조한 명령에는 exception table 복구 지점이 없기 때문이다(§18 문제 4).

두 번째 실행: -cpu max (PAN 지원) — 같은 커널, 같은 모듈

출력에서 볼 것:

  • PAN (Privileged Access Never, ARMv8.1): pstate의 +PAN. PAN 비트가 켜져 있으면 EL1이 유저 접근 가능(EL0) 페이지를 읽기만 해도 permission fault가 난다. copy_from_user는 복사하는 동안만 PAN을 잠깐 끄거나(uaccess_enable_privileged), 유저 권한으로 접근하는 LDTR/STTR 명령을 쓴다. 그래서 메시지가 "outside uaccess routines"다 — uaccess 함수 밖에서 유저 메모리를 만졌다는 뜻. x86의 같은 기능이 SMAP이다.
  • pte=...가 있으니 페이지는 멀쩡히 매핑돼 있었다. 매핑 문제가 아니라 권한 문제(FSC = 0x0f: level 3 permission fault)다.
  • 유저 쪽은 echo를 실행하던 셸이 Segmentation fault로 죽었다. 커널 Oops가 process context에서 나면 커널은 그 태스크를 죽이고(make_task_dead) 시스템은 계속 돈다 — 하지만 그 태스크가 잡고 있던 락은 영원히 안 풀린다. 이후 시스템 상태는 믿을 수 없다(Tainted에 D가 붙는다).
  • 랩 커널은 CONFIG_ARM64_SW_TTBR0_PAN이 꺼져 있다. 이 옵션은 PAN이 없는 ARMv8.0에서 TTBR0(유저 페이지 테이블)를 커널 실행 중 비워 두는 소프트웨어 PAN 흉내다. 켰다면 A57에서도 직접 역참조가 fault가 났을 것이다.

7.3 예제 14 — sparse는 빌드 때 잡는다 (make C=1)#

무엇을 확인하나: __user 주석이 붙은 포인터를 역참조하는 코드를 정적 분석기 sparse가 잡는지.

출력에서 볼 것: gcc는 아무 말도 안 했지만 sparse는 20번째 줄(kbuf[0] = *ubuf;)을 정확히 짚었다. __user는 gcc에게는 빈 매크로이고, sparse에게만 __attribute__((noderef, address_space(__user)))로 보인다(include/linux/compiler_types.h). 드라이버를 쓰면 make C=1을 습관으로 한다(E5).

8. 커널 안에는 메모리 보호가 없다#

8.1 직관#

유저 공간에서 버퍼 overflow는 내 프로세스만 망친다. 커널에서는 모든 커널 코드가 같은 주소 공간을 쓴다. 내 드라이버의 kmalloc(32) 버퍼 바로 옆 32바이트는 USB 스택의 객체일 수도, 다른 프로세스의 파일 구조체일 수도 있다. 넘쳐 쓰면 fault도 경고도 없이 남의 데이터가 바뀐다. 증상은 한참 뒤 전혀 다른 서브시스템에서 나타난다. 펌웨어에서 전역 배열 overflow가 바로 다음 전역 변수를 덮던 것과 같지만, 이웃이 수천 배 많다.

8.2 예제 15 — 8바이트 overflow가 이웃 객체를 바꾼다 (e4_corrupt)#

무엇을 확인하나: kmalloc-32 캐시에서 메모리상 연속한 두 객체를 찾아, 앞 객체를 8바이트 넘쳐 쓰면 뒤 객체가 어떻게 되는지.

기본 부팅 (slab 디버그 없음)

출력에서 볼 것: r[1]의 id가 'X'(0x58) 8개로 바뀌었다. 커널은 아무것도 몰랐다. 이번에는 r[1]이 내 객체였지만, 실제로는 다른 서브시스템의 객체일 확률이 더 높다. 더 나쁜 경우 해제된 객체 안의 SLUB freelist 포인터를 덮어 나중에 전혀 무관한 kmalloc이 이상한 주소를 돌려주는 형태로 터진다.

커널 인자 slab_debug=FZ,kmalloc-32 추가 (같은 모듈)

출력에서 볼 것:

8.3 Oops 해부 (M3 미리보기)#

§7의 PAN Oops를 위에서부터 읽는 법이다. Oops는 "커널이 자기 코드에서 처리할 수 없는 예외를 만났다"는 보고서이고, 펌웨어의 HardFault 핸들러가 찍던 레지스터 덤프 + 스택 추적의 커널판이다.

그림 4 — Oops 해부도. 위에서 아래로 "무엇이 → 왜(ESR) → 몇 번째 → 누구(모듈·taint) → CPU 상태 → 어디서(pc) → 데이터(레지스터) → 경로(Call trace) → 명령어(Code)" 순서다. 여러 Oops가 이어지면 항상 [#1]부터 본다.

8.4 예제 16 — pc에서 소스 줄까지 (faddr2line, objdump)#

무엇을 확인하나: Oops의 pc : e4_write+0x124/0x144를 소스 파일의 줄 번호와 명령어로 되돌릴 수 있는지.

출력에서 볼 것: 20번째 줄 kbuf[0] = *ubuf; — sparse가 경고한 바로 그 줄이다. 명령어 ldrb w1, [x20]은 Oops의 Code: 괄호 안 39400281과 같고, 주소 레지스터 x20 = 0x1e4d5aa0이 Oops 첫 줄의 fault 주소다. 랩 커널은 CONFIG_DEBUG_INFO=y라서 .ko에 DWARF가 있어 줄 번호까지 나온다. 양산 커널에서 디버그 정보를 빼더라도 같은 빌드의 디버그 심볼(vmlinux, .ko)은 반드시 보관해야 현장 Oops를 해석할 수 있다.

9. 예외는 없다 — 모든 에러를 손으로 처리한다#

9.1 규약#

커널 C에는 C++ 예외도, 전역 errno도, 프로세스 종료로 자원을 회수해 주는 OS도 없다. 규약은 세 가지다.

  1. 실패하면 음수 errno를 돌려준다(return -ENOMEM;). 성공은 0 또는 양수(읽은 바이트 수 등). 유저 공간으로 돌아갈 때 syscall 층이 -ret를 errno에 넣고 -1을 돌려준다.
  2. 포인터를 돌려주는 함수는 실패를 NULL 또는 ERR_PTR(-ENOMEM) 으로 표현한다. 받는 쪽은 IS_ERR()/PTR_ERR()로 검사한다. 어느 쪽인지는 함수마다 다르므로 문서·소스를 확인한다 (kmalloc은 NULL, kthread_create·devm_ioremap_resource는 ERR_PTR).
  3. 여러 자원을 차례로 얻다가 중간에 실패하면 얻은 역순으로 풀어 준다 — goto 레이블 사다리(E5에서 자세히). 요즘 드라이버는 devm_* 관리 자원으로 이 사다리 자체를 줄인다(G6).

10. 동시성은 어디에나 있다#

10.1 직관#

유저 앱은 스레드를 만들지 않으면 동시성이 없다. 커널 코드는 내가 아무것도 안 해도 동시에 실행된다:

  • SMP: 두 프로세스가 동시에 같은 /dev/e4에 write()하면 내 .write 핸들러가 CPU 두 개에서 동시에 돈다.
  • 선점(preemption): CONFIG_PREEMPT=y(랩 커널)면 내 코드가 아무 명령 사이에서나 멈추고 다른 태스크가 같은 코드를 돈다.
  • 인터럽트·softirq: 내 IRQ 핸들러가 내 read() 한가운데 끼어든다.

펌웨어에서 "메인 루프와 ISR이 공유하는 변수는 volatile + 인터럽트 끄고 접근"이 규칙이었다면, 커널에서는 모든 공유 데이터에 대해 "누가 동시에 만질 수 있나"를 먼저 묻는다. volatile은 답이 아니다(F5).

12. 끝없는 busy loop 금지 — soft lockup detector#

12.1 직관#

펌웨어에서 while (!(REG & READY));는 흔하다. 칩이 응답하지 않으면 하드웨어 워치독이 보드를 리셋해 준다. 커널에서 같은 루프를 선점을 끈 채(스핀락 안, preempt_disable() 구간) 돌면 그 CPU는 스케줄러를 영영 못 만난다. 다른 태스크·RCU·워크큐가 그 CPU에서 멈추고, 결국 시스템 전체가 굳는다. 선점이 켜져 있어도 IRQ를 끄고 돌면 더 나쁘다(hard lockup).

커널의 소프트웨어 워치독:

  • soft lockup: CPU가 2 × watchdog_thresh초(기본 10 → 20초) 동안 한 번도 스케줄되지 않음. CPU마다 hrtimer가 주기적으로 돌며 "그 CPU의 stopper 스레드가 최근에 타임스탬프를 갱신했나"를 확인한다(kernel/watchdog.c, 임계값 = get_softlockup_thresh() = watchdog_thresh * 2).
  • hard lockup: IRQ까지 꺼져서 hrtimer조차 못 돎. perf NMI 또는 buddy CPU 방식으로 감지(CONFIG_HARDLOCKUP_DETECTOR).
  • RCU stall: 한 CPU가 RCU grace period를 너무 오래(기본 21초) 막음. 별도 감지기지만 같은 버그에서 같이 뜬다.

12.2 예제 19 — 선점을 끄고 15초 폴링 (e4_lockup)#

무엇을 확인하나: 센서 ready 비트 폴링을 흉내 낸 mdelay(1) 루프를 선점 허용/금지 두 경우로 돌렸을 때 soft lockup detector가 반응하는지. 랩 커널은 SOFTLOCKUP_DETECTOR가 꺼져 있으므로 디버그 커널 복사본에서 돌리고, 빨리 보기 위해 커널 인자 watchdog_thresh=5(임계값 10초)를 준다.

출력에서 볼 것:

  • 선점 허용(nopreempt=0): 15초 동안 똑같이 바쁘게 돌았지만 경고가 없다. CONFIG_PREEMPT=y 커널에서는 타이머 인터럽트에서 돌아올 때 더 높은 우선순위의 stopper 스레드가 끼어들어 타임스탬프를 갱신할 수 있었다. (CPU 시간은 여전히 낭비다 — 다른 일을 못 했다.)
  • 선점 금지: 루프 시작(16.7초) 후 약 13초 시점에 watchdog: BUG: soft lockup - CPU#1 stuck for 13s!. 임계값 10초 + hrtimer 주기(임계값의 1/5 = 2초 간격) 때문에 정확히 10초가 아니라 그다음 검사 시점에 찍힌다. Call trace의 __const_udelay ← e4_lockup_init이 범인을 가리킨다.
  • soft lockup은 경고일 뿐 루프를 멈추지 않는다 — 루프는 끝까지 돌았다(done after 14336 loops). 양산 장비에서 멈춤 대신 재부팅을 원하면 softlockup_panic=1(커널 인자 또는 kernel.softlockup_panic sysctl) + panic=N을 쓴다.
  • mdelay(1) 한 번이 TCG에서 약 1.07 ms(15000 jiffies-ms / 14000 루프)였다. mdelay/udelay는 잠들지 않는 busy-wait다. 수 ms 이상 기다릴 때는 process context에서 usleep_range()/msleep()을 쓴다.

처음에는 기본 임계값(20초)과 25초 루프로 돌렸는데 soft lockup 대신 RCU stall이 먼저(약 21초) 떴고, soft lockup 메시지는 끝내 안 나왔다:

RCU stall 보고 경로가 스택을 덤프하면서 워치독 타임스탬프를 갱신(touch_nmi_watchdog() → touch_softlockup_watchdog())하기 때문에 soft lockup 카운트가 리셋된 것으로 보인다. 현장 로그에서 둘 중 무엇이 찍히든 같은 버그(선점 없이 너무 오래 도는 코드)다. 랩 기본 커널처럼 SOFTLOCKUP_DETECTOR가 꺼져 있어도 RCU stall 감지기는 남아 있어서, 긴 루프는 결국 이런 로그를 남긴다.

13. 커널 코딩 스타일과 checkpatch.pl#

13.1 왜 스타일까지 제약인가#

커널은 수천 명이 같은 코드를 읽고 고친다. 그래서 스타일이 "취향"이 아니라 리뷰를 통과하기 위한 조건이다(Documentation/process/coding-style.rst). 핵심만:

  • 들여쓰기는 탭(8칸 폭), 한 줄 100열 이하(80열 권장). 들여쓰기가 3단계를 넘으면 함수를 나누라는 신호.
  • 함수의 여는 중괄호 {는 다음 줄, if/for/struct의 {는 같은 줄.
  • typedef로 구조체를 숨기지 않는다 (struct e4_priv를 그대로 쓴다). 예외는 불투명 타입·고정 폭 정수.
  • 이름은 snake_case, 전역 심볼에는 드라이버 접두어. CamelCase 금지.
  • printk에는 로그 레벨, 가능하면 pr_*/dev_*.
  • 지역 변수 선언 뒤 빈 줄 하나.

15. Embedded 실무에서 다시 보기#

15.1 장면 1 — IMU IRQ 핸들러에서 I2C로 FIFO를 읽고 싶다#

센서 키트의 IMU가 "FIFO watermark" 인터럽트를 올린다. 펌웨어 습관대로 hardirq 핸들러 안에서 i2c_transfer()로 FIFO를 읽으면 §5의 버그다 — I2C 전송은 컨트롤러 완료 인터럽트를 기다리며 잠든다. 정답은 devm_request_threaded_irq(dev, irq, NULL, e4_imu_thread_fn, IRQF_ONESHOT, ...): 핸들러가 irq thread(process context) 에서 돌므로 I2C·mutex·GFP_KERNEL을 다 쓸 수 있다. IIO 드라이버(I2) 대부분이 이 구조다.

15.2 장면 2 — 카메라 드라이버의 큰 버퍼#

V4L2 드라이버가 센서 레지스터 초기화 테이블(수 KiB)이나 메타데이터 버퍼를 함수 지역 배열로 잡으면 §4.6의 -Wframe-larger-than 경고가 난다. 경고를 무시한 채 다른 큰 프레임 함수에서 부르면 현장에서 가끔 스택 overflow panic이 난다. 정답: 상수 테이블은 static const(.rodata), 작업 버퍼는 probe()에서 devm_kzalloc으로 한 번 잡아 priv 구조체에 둔다. 프레임 버퍼 같은 대용량은 DMA 버퍼(dma_alloc_coherent, videobuf2 — H8, Q1).

15.3 장면 3 — ioctl로 받은 구조체 안의 포인터#

CAN 모터 컨트롤러 설정 ioctl이 struct e4_cfg { __u32 n; __u64 table_ptr; }를 받는다. copy_from_user(&cfg, argp, sizeof(cfg))로 구조체는 안전하게 가져왔어도, table_ptr는 여전히 유저 주소다. 또 한 번 copy_from_user(kbuf, u64_to_user_ptr(cfg.table_ptr), ...)를 해야 하고, n은 상한 검사(if (cfg.n > E4_MAX) return -EINVAL;)를 먼저 해야 한다. 32비트 유저/64비트 커널 조합을 위해 포인터 필드를 __u64로 정의하는 것이 uapi 규칙이다(E6, G4).

15.4 장면 4 — "가끔 부팅 중 멈춘다" → soft lockup 로그#

장비가 가끔 부팅 중 30초씩 멈춘다는 현장 보고. 콘솔 로그에 watchdog: BUG: soft lockup - CPU#1 stuck for 22s!와 함께 Call trace가 남아 있다면 범인은 거의 확실히 선점이나 인터럽트를 끈 채 하드웨어 ready 비트를 무한 폴링하는 드라이버다(§12). 고치는 법은 readl_poll_timeout()(타임아웃 + usleep_range)으로 바꾸고, 타임아웃이면 -ETIMEDOUT을 돌려 probe()를 실패시키는 것. 양산 커널에 SOFTLOCKUP_DETECTOR를 켜 두는 이유가 이 로그 한 줄 때문이다.

17. 면접에서 이렇게 말한다#

Q. What are the main differences between writing kernel code and writing a userspace application?

A. 커널은 libc가 없고, FP를 못 쓰고, 스택이 16 KiB 고정이고, 잠들 수 없는 문맥이 있고, 할당이 실패할 수 있고, 유저 포인터를 믿으면 안 되고, 내부 메모리 보호가 없다. 실수 하나가 프로세스가 아니라 시스템 전체를 죽인다는 게 근본 차이다. 펌웨어 경험으로 보면 bare-metal 규칙에 "수많은 이웃 + 선점 + SMP + 신뢰할 수 없는 유저"가 더해진 환경이다.

Kernel code runs in a single privileged address space with no safety net. There's no libc — the kernel has its own string, printk and allocation APIs. Floating point is off-limits by default because the kernel doesn't save user FP registers on entry. Each task has a small fixed stack, 16 KiB on arm64, so no big locals and no unbounded recursion. Some contexts — interrupt handlers, code holding a spinlock — must never sleep. Allocations can fail and need GFP flags. User pointers must go through copy_from_user. And since there's no memory protection between kernel components, a single bad write can corrupt unrelated subsystems and take down the whole system, not just one process.

꼬리 질문: "Coming from bare-metal firmware, which of these were new to you?" → 선점·SMP가 기본이라는 것과 유저 포인터 검증. 펌웨어에서는 ISR과 메인 루프만 생각하면 됐다.

Q. Why can't you use floating point in the Linux kernel? What if you really need SIMD?

A. 커널 진입 때 FP/SIMD 레지스터를 저장하지 않으므로, 커널이 쓰면 유저 프로세스의 FP 상태가 깨진다. arm64는 -mgeneral-regs-only로 컴파일해서 float를 쓰면 빌드 에러가 난다. 꼭 필요하면 FP 코드를 별도 파일로 분리해 CC_FLAGS_FPU로 컴파일하고, 호출 쪽을 kernel_neon_begin/end(일반 API로는 kernel_fpu_begin/end)로 감싼다. 이 구간에서 유저 FP 상태를 저장·복원한다.

The kernel doesn't save and restore user FP/SIMD state on syscall or interrupt entry, to keep entry cheap, so kernel code touching those registers would silently corrupt user state. On arm64 the kernel is built with -mgeneral-regs-only, so using float is a compile error. When SIMD is really worth it — crypto, checksums, RAID — you put that code in its own translation unit compiled with CC_FLAGS_FPU and bracket the call with kernel_neon_begin and kernel_neon_end, which save the user state first. For sensor math in drivers, use fixed-point and let userspace do the floating-point conversion, like IIO does with raw plus scale.

Q. How big is the kernel stack, and what happens if you overflow it?

A. arm64는 태스크당 16 KiB(THREAD_SIZE, KASAN이면 32 KiB), 인터럽트는 CPU별 IRQ 스택 16 KiB. CONFIG_VMAP_STACK이면 스택이 vmalloc 영역에 있고 아래에 guard page가 있어서, 넘치는 순간 data abort → "Insufficient stack space" → "kernel stack overflow" panic이다. VMAP_STACK이 없으면 옆 메모리를 조용히 덮는다. 예방은 빌드 때 -Wframe-larger-than(CONFIG_FRAME_WARN)과 -fstack-usage로 한다.

On arm64 it's 16 KiB per task, defined by THREAD_SIZE, with a separate per-CPU IRQ stack. With CONFIG_VMAP_STACK the stack lives in vmalloc space with an unmapped guard page below it, so an overflow faults immediately; the entry code detects the bad stack pointer, switches to a small per-CPU overflow stack and panics with "kernel stack overflow". Without VMAP_STACK you'd silently corrupt adjacent memory. I keep locals small, avoid input-dependent recursion, and watch the -Wframe-larger-than warnings; I've reproduced the overflow panic in QEMU with a 560-byte frame recursing 27 deep.

Q. What does "sleeping in atomic context" mean? How would you detect it?

A. atomic context는 스핀락을 잡았거나 선점·IRQ가 꺼졌거나 인터럽트·softirq 안이라서 schedule()을 부르면 안 되는 상태다. 여기서 msleep, mutex_lock, GFP_KERNEL 할당, I2C 전송처럼 잠들 수 있는 함수를 부르면 데드락이나 크래시가 난다. 실제로 잠들면 스케줄러가 "scheduling while atomic"을 찍지만, GFP_KERNEL처럼 가끔만 잠드는 경우는 CONFIG_DEBUG_ATOMIC_SLEEP을 켜야 might_sleep()이 "sleeping function called from invalid context"로 미리 잡는다.

Atomic context means the current code can't call schedule(): holding a spinlock, preemption or interrupts disabled, or running in hardirq or softirq context — it's all tracked in preempt_count. If you call something that may sleep there, like msleep, mutex_lock, a GFP_KERNEL allocation or an I2C transfer, you can deadlock. If it actually schedules, the scheduler prints "scheduling while atomic". But many functions only sleep occasionally, so in development I enable CONFIG_DEBUG_ATOMIC_SLEEP: might_sleep() annotations then flag the call every time, even when it doesn't actually sleep. The fix is usually a threaded IRQ, a mutex instead of a spinlock, GFP_ATOMIC, or deferring to a workqueue.

꼬리 질문: "Can you take a mutex in an interrupt handler?" → 아니다. hardirq는 잠들 수 없다. threaded IRQ 핸들러에서는 된다.

Q. Why can't a driver just dereference a pointer it got from userspace?

A. 그 주소는 매핑이 안 돼 있을 수도, 스왑아웃돼 있을 수도, 커널 주소일 수도 있다. copy_from_user는 access_ok로 유저 영역인지 검사하고 fault를 exception table로 복구해서 -EFAULT를 돌려준다. ARMv8.1 PAN이나 x86 SMAP이 켜진 CPU에서는 직접 역참조가 바로 Oops다. 저는 QEMU에서 같은 모듈이 Cortex-A57(PAN 없음)에서는 조용히 동작하고 -cpu max에서는 Oops 나는 걸 직접 확인했다.

A user pointer is just a number supplied by an untrusted process. It might be unmapped, paged out, or deliberately point into kernel memory. copy_from_user checks it with access_ok, and if the access faults, the exception table turns that into a short copy so the driver returns -EFAULT instead of oopsing. On CPUs with PAN on arm64 or SMAP on x86, a direct dereference faults immediately with "access to user memory outside uaccess routines". On older cores without PAN it may appear to work, which is exactly why it's dangerous — sparse catches it at build time through the __user annotation.

Q. What happens when you write past the end of a kmalloc buffer in the kernel?

A. 커널 안에는 보호 경계가 없어서 fault 없이 옆 객체가 깨진다. 증상은 나중에 전혀 다른 곳에서 나온다. 재현할 때는 slab_debug=FZ로 redzone을 켜서 free 때 잡거나, KASAN으로 접근하는 순간 잡는다.

Nothing stops you — there's no protection between kernel components, so you silently corrupt whatever object is next in the slab, possibly belonging to a different subsystem, and the crash shows up later somewhere unrelated. To catch it I'd boot with slab_debug to add redzones, which reports "Right Redzone overwritten" on free, or use a KASAN build, which catches the bad access as it happens with a precise report.

Q. How do you handle errors in kernel code without exceptions?

A. 음수 errno를 반환하고, 포인터 반환 함수는 NULL 또는 ERR_PTR을 쓴다. 여러 자원을 얻는 함수는 실패 지점에서 얻은 역순으로 해제하는 goto 사다리를 쓰거나, 드라이버라면 devm_*으로 자동 해제한다. 모든 반환값을 검사한다 — kstrto*가 실패하면 출력 변수는 안 바뀐다.

By convention functions return 0 or a negative errno, and pointer-returning functions return NULL or an ERR_PTR that you test with IS_ERR. When a function acquires several resources, failures jump to goto labels that release them in reverse order; in drivers I prefer devm-managed resources so the cleanup is automatic when probe fails. And every return value gets checked — for instance kstrtouint leaves the output untouched on failure, so ignoring the return code means using stale data.

Q. What is a soft lockup?

A. 한 CPU에서 watchdog 스레드가 2 × watchdog_thresh(기본 20초) 동안 스케줄되지 못한 상태다. 보통 선점을 끄고 무한 폴링하는 코드가 원인이다. CONFIG_SOFTLOCKUP_DETECTOR가 hrtimer로 감시해서 "BUG: soft lockup - CPU#N stuck for Xs!"와 스택을 찍는다. 인터럽트까지 꺼져 있으면 hard lockup이고 NMI·perf 기반 detector가 잡는다.

A soft lockup means a CPU has been stuck in kernel mode without scheduling for more than twice watchdog_thresh — 20 seconds by default. The detector uses a per-CPU hrtimer to check whether the per-CPU watchdog task got to run; if not, it prints "BUG: soft lockup - CPU#N stuck for Xs" with a backtrace. The usual cause is busy-polling hardware with preemption disabled. A hard lockup is the same thing with interrupts also off, detected via NMI or a perf counter. The fix is to poll with a timeout and sleep between reads, like readl_poll_timeout.

20. 요약 & 체크리스트#

커널 코드는 펌웨어처럼 맨바닥에서 돌지만, 수많은 이웃과 같은 주소 공간을 쓰고, 선점·SMP·인터럽트가 항상 켜져 있고, 위에서는 믿을 수 없는 유저 공간이 포인터를 던진다. 그래서 libc 대신 커널 라이브러리(lib/, kstrto*, strscpy, kmalloc)를 쓰고, FP는 -mgeneral-regs-only로 막혀 있으며(필요하면 kernel_neon_begin/end 구간), 스택은 16 KiB 고정이라 큰 지역 변수와 재귀를 피하고(VMAP_STACK이 넘침을 panic으로 잡는다), atomic context에서는 절대 잠들지 않고(DEBUG_ATOMIC_SLEEP이 잠복 버그를 드러낸다), 모든 할당·호출의 실패를 음수 errno로 처리하며, 유저 메모리는 copy_from_user로만 만지고(PAN이 직접 접근을 Oops로 만든다), 공유 데이터는 원자 연산·락으로 보호하고, 외부 포맷은 __le32·get_unaligned_*로 다루고, 하드웨어 폴링에는 타임아웃을 둔다. 이 규칙들은 대부분 도구로 확인할 수 있다: 컴파일러 플래그, -Wframe-larger-than, sparse, checkpatch, slab_debug, 디버그 Kconfig.
