0. 큰 그림 — 이게 왜 필요한가#

A1에서는 유저 쪽에서 본 syscall을 다뤘다: libc가 x8에 번호, x0~x5에 인자를 넣고 svc #0, 돌아온 x0가 음수면 -1 + errno. 이 노트는 반대편, 커널 쪽이다. 드라이버 작성자 입장에서 경계는 세 가지 방향으로 넘어온다.

그림 1 — 경계를 넘는 것은 세 가지다. ① 제어(예외로 EL1 진입), ② 데이터(유저가 준 주소를 커널이 특수한 방법으로만 읽고 쓴다), ③ 결과(x0 하나에 성공값 또는 음수 에러 코드).

Don의 펌웨어 경험으로 옮기면:

  • ① 은 RTOS의 SVC 핸들러와 같다. 태스크가 svc를 치면 핸들러가 예외 스택 프레임에서 r0~r3를 꺼내 서비스 번호로 함수 테이블을 찾는다. Linux도 똑같이 레지스터를 struct pt_regs에 저장하고 sys_call_table[x8]을 부른다.
  • ② 가 펌웨어에는 거의 없는 부분이다. MPU로 태스크를 격리한 RTOS라면 "커널이 태스크가 넘긴 포인터를 믿어도 되나?"를 고민했을 것이다. Linux는 이 문제를 세 겹으로 푼다: 주소 범위 검사(access_ok), 유저 권한으로만 접근하는 명령(LDTR/STTR) + PAN, 그리고 접근이 fault 나면 죽지 않고 에러로 바꾸는 예외 테이블.
  • ③ 은 SSD 펌웨어의 NVMe completion status와 같은 약속이다. status code를 아무렇게나 주면 호스트 드라이버가 잘못 재시도하듯, 드라이버가 errno를 틀리게 주면 유저 프로그램이 잘못 반응한다.

1. syscall 진입 — svc #0에서 sys_call_table까지#

1.1 직관 — "예외 벡터 → 레지스터 저장 → 번호로 테이블 점프"#

Cortex-R 펌웨어에서 SVC를 처리하던 순서를 떠올리면 된다.

  1. 하드웨어: 예외 발생, 복귀 주소·상태 저장(ELR_EL1, SPSR_EL1), VBAR_EL1 벡터로 점프.
  2. 소프트웨어 진입부: 범용 레지스터 전부를 스택에 저장 (Linux: struct pt_regs).
  3. 디스패처: 예외 원인(ESR)을 보고 "SVC구나" → 번호로 핸들러 테이블 인덱싱.
  4. 핸들러 실행 → 반환값을 저장된 r0(=pt_regs->regs[0]) 자리에 써 넣음.
  5. 복귀 전 할 일(스케줄, 시그널) 처리 → 레지스터 복원 → eret.

1.2 예제 1 — 함수 이름을 소스와 System.map에서 확인#

무엇을 확인하나: 위 표의 이름이 6.18.55 소스에 실제로 있는지, 그리고 링크된 커널에서 어떤 것이 전역(T)이고 어떤 것이 static(t)인지.

출력에서 볼 것: invoke_syscall과 el0_svc_common은 소스에서 static이라 System.map에 소문자 t로 나오고, 이름 뒤에 .constprop.0이 붙었다. GCC가 "항상 같은 상수 인자(sys_call_table, __NR_syscalls)로 불린다"는 걸 알고 그 인자를 박아 넣은 복제본을 만든 것이다 (constant propagation). 이 빌드에서는 인라인되지 않고 별도 함수로 남았지만, 컴파일러·설정이 바뀌면 인라인되어 스택 트레이스에서 사라질 수도 있다. 트레이스에서 이름이 하나 빠져 보여도 놀라지 말 것.

함정: static 함수는 EXPORT_SYMBOL도 안 되어 있고 모듈에서 부를 수도 없다. "syscall 테이블을 모듈에서 패치한다" 같은 옛날 인터넷 예제는 지금 커널에서 안 된다(sys_call_table은 export되지 않으며 rodata 쪽에 있다).

1.5 예제 4 — invoke_syscall 디스어셈블: 테이블 점프와 반환값 저장#

무엇을 확인하나: C 코드 syscall_table[array_index_nospec(scno, sc_nr)] 호출과 syscall_set_return_value()가 기계어로 어떻게 되는지.

출력에서 볼 것:

2. 드라이버까지 — ksys_read → vfs_read → f_op->read, 그리고 돌아오는 길#

2.1 VFS 구간 — 랩 소스 그대로#

ksys_read()는 fd를 struct file로 바꾸고 파일 위치(f_pos)를 지역 변수로 복사해서 넘긴다.

vfs_read()가 드라이버 앞의 마지막 관문이다.

드라이버 작성자가 알아야 할 점:

  • 드라이버의 .read가 불리기 전에 access_ok(buf, count)가 이미 한 번 검사됐다. 커널 주소를 넘기면 드라이버까지 오지도 않고 -EFAULT다 (예제 9에서 확인). 그래도 드라이버는 copy_to_user를 써야 한다 — access_ok는 "범위가 유저 영역인가"만 보지, "그 주소에 실제로 메모리가 매핑돼 있나"는 모른다.
  • ppos는 file->f_pos가 아니라 지역 변수의 주소다. 드라이버는 *ppos만 갱신하고, ksys_read가 성공했을 때 f_pos에 반영한다. pread()는 같은 경로에서 유저가 준 offset을 ppos로 넘긴다.
  • count는 MAX_RW_COUNT(약 2 GB)로 잘린다. 드라이버는 count가 0일 수도 있다는 점을 처리해야 한다 (§10 실수 표).

2.2 예제 6 — 실습 드라이버 e6_dev (1/3): 전역 상태와 read#

3. 유저 메모리 복사 — copy_to_user / copy_from_user와 친구들#

3.1 왜 *ubuf라고 쓰면 안 되나#

드라이버의 .write가 받은 const char __user *ubuf는 유저 프로세스의 가상 주소다. 이걸 커널이 그냥 memcpy하면 안 되는 이유는 네 가지다.

이유무슨 일이 생기나커널의 해결책
1. 주소가 커널 영역일 수 있다악의적인 앱이 write(fd, 커널주소, n)으로 커널 메모리를 읽거나 덮게 만든다access_ok() — 범위가 TASK_SIZE_MAX 아래인지 검사
2. 매핑이 없거나 권한이 없을 수 있다NULL, 해제된 버퍼, PROT_NONE 페이지 → 커널 모드 data abort → Oops예외 테이블 — fault 나면 에러 경로로 점프 (§4)
3. 매핑은 있지만 아직 물리 페이지가 없을 수 있다처음 접근하는 malloc 버퍼, swap된 페이지정상 page fault 처리(handle_mm_fault) 후 재시도 — 이 때문에 잠들 수 있다
4. 하드웨어가 막는다 (PAN)ARMv8.1+ PAN이 켜져 있으면 EL1의 일반 load/store로 유저 페이지 접근 자체가 permission fault유저 접근은 LDTR/STTR(unprivileged load/store)로만 한다

펌웨어 비유: MPU로 태스크 메모리를 막아 둔 RTOS에서 SVC 핸들러가 태스크 버퍼를 읽으려면 "이 주소가 그 태스크 영역 안인가?"를 확인하고, 읽다가 MemManage fault가 나면 시스템을 죽이지 말고 그 태스크에 에러를 돌려줘야 한다. Linux의 uaccess가 정확히 이것을 일반화한 것이다. Linux에서는 커널과 유저가 같은 주소 공간(TTBR0 = 유저, TTBR1 = 커널)에 동시에 보인다는 점이 다르다 — 그래서 실수로 직접 역참조해도 "돌아가 버리는" 위험이 있다 (예제 12).

4. 예외 테이블과 PAN — 나쁜 포인터가 Oops가 아니라 EFAULT가 되는 원리#

4.1 직관 — "이 명령에서 fault 나면 여기로 가라" 목록#

커널 코드 대부분은 fault가 나면 안 된다. 커널 주소에서 data abort = 커널 버그 = Oops. 그런데 유저 메모리를 만지는 특정 명령 몇 개는 fault가 날 수 있다는 걸 미리 안다. 그래서 링커가 (fault 날 수 있는 명령 주소, 대신 점프할 주소, 처리 방식) 쌍을 __ex_table 섹션에 모아 둔다. 커널 모드 abort가 나면 page fault 핸들러가 먼저 정상 처리(페이지 할당)를 시도하고, 그게 안 되면 PC로 이 테이블을 검색한다. 있으면 레지스터에 -EFAULT를 넣고 PC를 fixup 주소로 바꿔서 예외에서 복귀. 없으면 Oops.

펌웨어로 치면 "abort 핸들러가 faulting PC를 보고, 그 PC가 safe_probe_read() 함수 안이면 에러 코드를 반환시키고 계속 진행" 하는 트릭을, 컴파일러·링커가 자동으로 표를 만들어 주는 형태로 일반화한 것이다.

  • 엔트리 1: 명령 .text+0x8a8 = sttr w0, [x1] → put_user (GET_LEN). 엔트리 2: .text+0x8dc = ldtr w1, [x1] → get_user (SET_THRESH). 둘 다 fixup은 .text+0x740 = mov x3, #-14 = C 코드의 return -EFAULT 경로.
  • 원시 바이트 0200ff03 = type = 0x0002(EX_TYPE_UACCESS_ERR_ZERO), data = 0x03ff. data의 비트 0–4(err 레지스터)와 5–9(zero 레지스터)가 둘 다 31(= xzr)이다. 컴파일러가 asm goto로 "fault 나면 C 레이블로 점프" 형태를 만들었기 때문에, 핸들러가 레지스터에 값을 써 줄 필요 없이 PC만 바꾸면 된다.
  • ldtr/sttr 바로 앞의 and x1, x1, #0xff7fffffffffffff는 uaccess_mask_ptr() — 주소의 bit 55를 지운다. arm64에서 bit 55가 1이면 TTBR1(커널) 영역이므로, 투기 실행으로라도 커널 주소를 유저 접근 명령에 쓰지 못하게 하는 방어다.
  • copy_to_user/copy_from_user는 이 모듈의 테이블에 없다. 실제 복사 명령은 vmlinux의 __arch_copy_*_user 안에 있고, 엔트리도 vmlinux의 __ex_table에 있다 (다음 예제).

5. 에러 코드 규약 — 커널 -errno, libc -1 + errno#

5.1 층마다 같은 숫자가 모양만 바뀐다#

A1 §3.4에서 유저 쪽을 봤다: 커널이 x0 = -2를 주면 libc가 errno = 2, 반환 -1. 커널 안에서는 함수 반환값 자체가 음수 errno다. 드라이버가 return -EFAULT; 하면 그 -14가 VFS를 그대로 통과해 regs->regs[0]에 들어간다. libc는 x0가 -4095~-1 범위(MAX_ERRNO = 4095, include/linux/err.h)면 에러로 본다. 같은 범위 규칙이 커널 포인터에도 쓰인다 — ERR_PTR(-ENOMEM)은 주소 공간 맨 끝 4095바이트를 "에러 포인터"로 예약한 것이다 (E5).

5.3 커널 내부 전용 코드 — 유저에게 새면 안 된다#

include/linux/errno.h(랩 소스)에는 유저 헤더에 없는 코드가 있다:

  • -ERESTARTSYS는 시그널 처리 경로가 반드시 다른 것으로 바꾼다 (§5.4). 시그널이 없는데 드라이버가 -ERESTARTSYS를 돌려주면 유저에게 errno 512가 새어 나간다 — wait_event_interruptible의 반환값이 아닌 곳에서 이 코드를 쓰지 말 것.
  • -ENOIOCTLCMD는 vfs_ioctl()이 -ENOTTY로 바꿔 준다. 서브시스템 안쪽 ioctl 처리(예: 공통 처리 뒤 드라이버 고유 처리)에서 "내 담당 아님"을 뜻한다.
  • -EPROBE_DEFER는 probe 전용 (D3, G3).

5.5 반환값에서 절대 하지 말 것#

  • 양수 에러 코드: return EINVAL; → 유저에게는 "22바이트 읽었다"로 보인다. 컴파일러가 못 잡는다.
  • return -1;: 유저에게는 errno = 1 = EPERM("Operation not permitted")으로 보인다. 엉뚱한 디버깅을 하게 만든다.
  • 다른 함수의 반환값을 확인 없이 전달: return copy_to_user(...)(§3.3), return i2c_smbus_read_byte_data(...)(성공이면 데이터 바이트가 양수로 온다 — 그대로 read의 반환값으로 쓰면 "N바이트 읽음"이 된다).
  • 요청보다 큰 양수: read가 count보다 큰 값을 돌려주면 유저 버퍼 범위를 넘었다고 주장하는 셈이다.
  • 커널 내부 코드(512~517)를 시그널 경로 밖에서 반환.

6. ioctl ABI 설계 — 번호, 구조체, 32/64비트#

6.1 ioctl 번호의 비트 구조#

_IO/_IOR/_IOW/_IOWR(include/uapi/asm-generic/ioctl.h)는 32비트 번호에 네 필드를 넣는다: 방향(2비트), 인자 크기(14비트), type(8비트, 보통 문자 하나), nr(8비트). 방향은 유저 기준이다 — _IOR은 "유저가 읽는다" = 커널이 copy_to_user.

그림 5 — (그림에서 version은 abi_version 필드) 위: ioctl 번호의 네 필드(예제 14의 0x40184502 해부). 아래: 같은 의도의 구조체가 ABI마다 어떻게 놓이는지(예제 15의 pahole 결과). "bad"는 i386에서 크기가 달라져 ioctl 번호까지 달라지고, "ptr"은 32비트 ARM에서 반으로 줄어든다. "good"은 모든 ABI에서 24바이트, 구멍 없음.

7.2 숫자 읽는 법#

  • 고정 비용: 게스트에서 빈 syscall(getppid)이 약 390 명령어, e6_dev 1바이트 pread가 654 명령어. 차이 ~260 명령어가 ksys_pread64 → vfs_read → e6_read(락, copy_to_user 준비) 비용이다. 실측(M2)에서는 빈 syscall 213 ns, 1바이트 파일 pread 309 ns.
  • 바이트당 비용: 게스트 64 KiB에서 (19,087 − 654) / 65,535 ≈ 0.28 명령어/바이트 → 복사 루프가 명령 하나에 약 3.5바이트를 옮긴다(ldtr/sttr 페어 + 루프 제어). 실측에서는 64 KiB에 약 2.4 µs = 약 27 GB/s.
  • 교차점: 실측 기준 1 KiB 이하에서는 syscall 오버헤드가 비용의 대부분이다 — 4바이트씩 읽는 드라이버/앱 설계는 시간 대부분을 경계 넘기에 쓴다. 16 KiB를 넘으면 복사가 지배한다. 이보다 큰 데이터(카메라 프레임, LiDAR 패킷 묶음)는 복사 자체를 없애야 한다 → mmap + DMA 버퍼 공유 (G5, H9, I5의 videobuf2).
  • 파일 쪽 1바이트 pread가 e6_dev보다 게스트에서 2배 가까이 비싼 것은 page cache 조회·iov_iter 경로(read_iter) 때문이다. 드라이버의 단순한 .read가 오히려 짧다.

9.3 데몬의 SIGTERM 처리와 blocking read#

센서 수집 데몬이 read(/dev/imu)에서 잠들어 있을 때 systemd가 SIGTERM을 보내면? 데몬이 SIGTERM 핸들러를 SA_RESTART로 걸었다면 read는 재시작되어 계속 잠들고, 핸들러에서 세운 "종료 플래그"를 메인 루프가 영영 못 본다. 드라이버가 -ERESTARTSYS를 올바르게 줬어도 그렇다. 앱 쪽 해결: 종료용 시그널은 SA_RESTART 없이 걸거나, signalfd + poll로 처리한다 (A6). 드라이버 쪽 책임: wait_event_interruptible의 반환값을 꼭 확인해서 -ERESTARTSYS를 돌려줄 것 — 무시하면 systemctl stop이 90초 타임아웃 후 SIGKILL로 갈 때까지 매달린다.

9.4 "개발 보드에서는 됐는데 양산 SoC에서 Oops"#

Q. Walk me through what happens when a user program calls read() on your device file, on arm64.

A. 유저가 x8에 63, x0~x2에 인자를 넣고 svc #0을 실행하면 EL1의 동기 예외 벡터로 들어간다. el0t_64_sync가 레지스터를 pt_regs에 저장하고, el0t_64_sync_handler가 ESR로 SVC임을 확인해 el0_svc → do_el0_svc → invoke_syscall로 간다. 여기서 sys_call_table[63]인 __arm64_sys_read가 pt_regs에서 인자를 꺼내 ksys_read를 부르고, fd를 struct file로 바꾼 뒤 vfs_read가 권한과 access_ok를 확인하고 file->f_op->read, 즉 내 드라이버 함수를 부른다. 반환값은 regs[0]에 저장되고, 유저로 돌아가기 직전에 재스케줄과 시그널을 처리한 뒤 eret한다.

On arm64 the libc wrapper puts the syscall number in x8 and the arguments in x0 to x2, then executes svc #0. That traps to the EL1 sync vector; el0t_64_sync saves all user registers into a pt_regs frame, the handler checks ESR, sees an SVC, and goes el0_svc, do_el0_svc, invoke_syscall, which indexes sys_call_table and calls __arm64_sys_read. That wrapper pulls the arguments out of pt_regs and calls ksys_read, which resolves the fd to a struct file, and vfs_read does the permission and access_ok checks and calls file->f_op->read, which is my driver. The return value goes into regs[0], and on the way out the kernel handles rescheduling and pending signals before eret.

꼬리 질문: "Why do syscall handlers take a pt_regs pointer instead of normal arguments?" → 커널 C 코드에 유저가 통제하는 다른 레지스터 값이 흘러 들어가지 않게 하고(투기 실행 공격 표면 축소), 래퍼에서 타입별로 잘라(__se_sys_*) 넘기기 위해서다.

Q. Why can't the kernel just dereference a user pointer? What does copy_from_user do differently?

A. 네 가지 이유다. 유저가 커널 주소를 넘길 수 있고, 매핑이 없을 수 있고, 매핑은 있어도 페이지가 아직 없을 수 있고, ARMv8.1 이상에서는 PAN이 커널의 일반 load/store로 유저 메모리 접근을 하드웨어로 막는다. copy_from_user는 access_ok로 범위를 확인하고, 유저 권한으로 접근하는 LDTR 명령으로 복사하며, 그 명령들이 예외 테이블에 등록돼 있어서 fault가 나면 page fault 핸들러가 정상 처리하거나, 불가능하면 fixup 코드로 점프해 못 복사한 바이트 수를 돌려준다. 그래서 나쁜 포인터가 Oops 대신 EFAULT가 된다. 실제로 PAN 없는 Cortex-A57에서는 직접 역참조가 동작해 버리고, PAN 있는 CPU에서는 같은 코드가 Oops 나는 것을 QEMU로 확인했다.

A user pointer may point into kernel space, may be unmapped, may be valid but not yet faulted in, and on ARMv8.1 and later, PAN makes a plain kernel load from user memory fault in hardware. copy_from_user checks the range with access_ok, does the copy with unprivileged LDTR/STTR instructions, and every one of those instructions has an exception table entry. If a fault happens, the page-fault handler either fixes it up normally, or, if the address is really bad, looks up the faulting PC in __ex_table and jumps to fixup code that returns the number of bytes not copied. So a bad pointer becomes -EFAULT instead of an oops. I've seen a direct dereference silently work on a Cortex-A57 without PAN and oops on a CPU with PAN — the bug was there all along.

Q. What does copy_to_user return, and how do you handle a partial copy in read()?

A. 0이면 전부 성공이고, 아니면 복사하지 못한 바이트 수다. 음수 에러가 아니다. read에서는 left == n이면 한 바이트도 못 줬으니 -EFAULT, 아니면 n - left만큼 *ppos를 전진시키고 그 값을 돌려준다. 고정 크기 구조체는 그냥 0이 아니면 -EFAULT. 그리고 그 숫자가 정확히 fault 지점까지라는 보장은 없다 — arm64에서 유효한 100바이트 중 52바이트만 성공으로 센 것을 직접 측정했다. 보장되는 건 앞쪽 n - left 바이트가 복사됐다는 것뿐이다.

It returns the number of bytes that could NOT be copied, so zero means success — not a negative errno. In read I compute left; if nothing was copied I return -EFAULT, otherwise I advance *ppos by n minus left and return that, a short read. For fixed-size structs in ioctl it's all-or-nothing: nonzero means -EFAULT. Also, the count isn't byte-exact at the fault boundary — on arm64 I measured 52 of 100 valid bytes reported as copied — the only guarantee is that the first n minus left bytes made it.

꼬리 질문: "What does copy_from_user do with the uncopied tail?" → 커널 쪽 버퍼의 남은 부분을 0으로 채운다. 정보 누출 방지.

Q. Which errno do you return for an unknown ioctl, and why not EINVAL?

A. -ENOTTY. "이 장치는 그 명령을 모른다"는 표준 의미이고, libc의 isatty()나 라이브러리들이 이 값으로 기능 유무를 판별한다. EINVAL은 "명령은 알지만 인자가 틀렸다"는 뜻이라 섞으면 유저가 잘못 반응한다. 서브시스템 내부에서는 -ENOIOCTLCMD를 쓰고 VFS가 -ENOTTY로 바꿔 준다.

-ENOTTY. It's the established meaning of "this device doesn't implement that command" — isatty() and many libraries probe capabilities that way. EINVAL means "I know the command but your argument is wrong," so mixing them misleads callers. Inside a subsystem you can return -ENOIOCTLCMD and vfs_ioctl converts it to -ENOTTY.

Q. What is ERESTARTSYS and when does the user see EINTR instead?

A. 드라이버가 wait_event_interruptible 같은 대기에서 시그널로 깼을 때 돌려주는 커널 내부 코드(512)다. 유저에게는 절대 그대로 안 간다. syscall 복귀 직전 arch_do_signal_or_restart가 보고, 처리할 시그널 핸들러에 SA_RESTART가 있으면 PC를 svc 명령으로 되돌리고 x0를 orig_x0로 복원해 핸들러 실행 후 syscall을 다시 실행하고, 없으면 -EINTR로 바꾼다. QEMU에서 같은 드라이버로 두 경우를 다 확인했다. 드라이버 규칙은 "잠들기 전엔 상태를 바꾸지 말 것" — 일부 처리했으면 처리한 양을 반환해야 한다.

It's a kernel-internal code the driver returns when an interruptible sleep is broken by a signal; userspace never sees it. On the way back to user mode, arch_do_signal_or_restart checks it: if the handler for the pending signal has SA_RESTART, it rewinds the PC to the svc instruction and restores x0 from orig_x0, so the syscall reruns after the handler; otherwise it rewrites the result to -EINTR. The driver's contract is that returning -ERESTARTSYS means nothing happened yet — if you already consumed data, return the byte count instead.

Q. How do you design an ioctl struct so it works for 32-bit userspace on a 64-bit kernel?

A. 고정 폭 타입(__u32, __u64)만 쓰고, 포인터와 long은 쓰지 않는다 — 포인터는 __u64에 담고 커널에서 u64_to_user_ptr로 꺼낸다. 필드는 큰 것부터 놓거나 명시적 패딩을 넣어 구멍이 없게 하고 pahole로 확인한다. i386은 u64 정렬이 4라 암묵적 패딩이 있으면 크기가 달라진다. 버전 필드와 0이어야 하는 reserved 필드를 넣어 확장을 대비하고, compat_ioctl = compat_ptr_ioctl로 끝낸다. 실제로 포인터가 든 구조체는 armhf에서 12바이트, arm64에서 24바이트라 ioctl 번호부터 달라지는 것을 확인했다.

Use only fixed-width types, never pointers or long; carry pointers as __u64 and convert with u64_to_user_ptr. Order fields or add explicit padding so there are no holes, and check with pahole — on i386 a u64 is only 4-byte aligned, so implicit padding changes the size and therefore the ioctl number, because _IOW encodes sizeof. Add a version field and reserved fields that must be zero so you can extend it later. With that, .compat_ioctl = compat_ptr_ioctl is all you need.

Q. Your driver's read() is called with count == 0, or with a buffer that crosses into an unmapped page. What should happen?

A. count == 0이면 그냥 0을 돌려준다(성공, 아무것도 안 함). 처리 안 하면 "0바이트 못 복사 == 0바이트 요청"이 되어 EFAULT가 나는 버그가 생긴다 — 실제로 측정 코드를 짜다가 내 드라이버에서 발견했다. 매핑이 끊기는 버퍼면 copy_to_user가 일부만 복사하고 나머지 개수를 돌려주므로, 복사된 만큼만 반환하는 짧은 read가 정답이다. 앱은 다음 read에서 EFAULT를 받는다.

Zero count: return 0 — success, nothing done. If you don't special-case it, "left == n" is true for 0 == 0 and you return -EFAULT; I actually hit that bug in my own test driver. For a buffer that runs into an unmapped page, copy_to_user copies a prefix and returns the remainder, so you return a short count and advance *ppos by that much; the application gets -EFAULT on the next call.

14. 요약 & 체크리스트#

arm64에서 syscall은 svc #0 → el0t_64_sync(pt_regs 저장) → el0t_64_sync_handler → el0_svc → do_el0_svc → invoke_syscall(sys_call_table[x8]) → __arm64_sys_*(pt_regs에서 인자 추출) → VFS → f_op->read/write/unlocked_ioctl 순으로 드라이버에 닿고, 반환값은 regs[0]에 저장된 뒤 복귀 직전의 exit_to_user_mode_loop에서 스케줄·시그널(재시작 포함)을 처리하고 eret한다. 드라이버는 유저 포인터를 절대 직접 만지지 않고 copy_*_user/get_user/put_user/strncpy_from_user/memdup_user를 쓴다. 이 함수들은 access_ok, LDTR/STTR, 예외 테이블 덕분에 나쁜 포인터를 Oops 대신 -EFAULT로 바꾸고, copy_*_user는 "못 복사한 바이트 수"를 돌려주므로 read/write는 부분 복사를 짧은 반환값으로 정직하게 알려야 한다. 에러는 항상 음수 errno이며, 모르는 ioctl은 -ENOTTY, 주소 문제만 -EFAULT, 인터럽트 가능한 대기의 시그널은 -ERESTARTSYS다. ioctl 구조체는 고정 폭 타입·명시적 패딩·__u64 포인터·버전·reserved로 설계해서 32/64비트 모두에서 같은 번호와 레이아웃을 갖게 한다.
