166분 읽기1894줄63개 절

이 노트를 다 읽으면: fd → open file description → inode 3단 구조로 dup/fork/O_CLOEXEC 동작을 예측할 수 있다 · short read·EINTR·EAGAIN을 견디는 I/O 루프를 짤 수 있다 · stdio 버퍼, page cache, 디바이스 캐시를 구분하고 fsync를 언제 불러야 하는지 말할 수 있다 · ioctl 번호를 해독하고 /dev/i2c-N, spidev, sysfs로 하드웨어에 접근하는 테스트 툴을 짤 수 있다 왜 필요한가: 드라이버를 만들면 그걸 검증하는 유저 프로그램을 반드시 짜게 되고, 면접에서는 "open() 하면 무슨 일이?", "fsync 안 하면 뭐가 날아가나?", "ioctl 번호는 어떻게 만들어지나?"가 단골이다. Don 기준 난이도: 버퍼·캐시·전원 차단·버스 트랜잭션은 이미 몸으로 안다 / 새로 배울 것은 POSIX 시맨틱(offset 공유, 시그널과 syscall의 상호작용)과 커널이 그걸 어떤 구조체로 구현하는지다. 선행 노트: A1 (everything is a file, syscall), A2 (fork/exec)

0. 큰 그림 — 이게 왜 필요한가#

bare-metal 펌웨어에서 센서를 읽을 때는 I2C 컨트롤러 레지스터를 직접 만졌다. Linux에서 유저 프로그램은 그럴 수 없다. MMU가 레지스터 영역을 매핑해 주지 않고, 매핑해 준다 해도 같은 컨트롤러를 커널 드라이버가 동시에 쓰고 있다. 그래서 Linux는 모든 장치 접근을 "파일 열고 → 읽고/쓰고 → 특수 명령(ioctl) → 닫기"라는 하나의 인터페이스로 통일했다. 커널은 이 호출을 받아 해당 드라이버의 함수로 넘긴다.

그림 1 — 유저 코드는 똑같은 open/read/write/ioctl만 부르고, VFS가 fd를 따라가서 각 드라이버의 함수로 보낸다.

bare-metal 비유로 말하면:

  • fd(file descriptor) = 커널이 들고 있는 핸들 테이블의 인덱스. RTOS에서 xQueueCreate()가 돌려주는 핸들과 같은 역할이다. 유저는 숫자 하나만 들고 있고, 진짜 객체는 커널 메모리에 있다.
  • read/write = 드라이버의 .read/.write 콜백을 부르는 통로. HAL의 HAL_I2C_Master_Receive()를 직접 부르는 대신 커널에 "이 fd로 읽어 줘"라고 부탁한다.
  • ioctl = "데이터 스트림으로 표현하기 어려운 제어 명령"용 만능 통로. 레지스터 맵의 control register에 비유할 수 있다.
  • page cache = SSD 펌웨어의 DRAM write cache와 같은 개념이다. 쓰기는 일단 RAM에 들어가고 나중에 매체로 내려간다. 그래서 fsync가 필요하다.

이 노트의 예제는 모두 Lima Ubuntu VM(aarch64, uname -r = 7.0.0-34-generic, gcc 15.2)에서 -Wall -Wextra 경고 0개로 컴파일하고 실행한 결과다.

1. File descriptor와 3단 구조#

1.1 직관 — 번호표, 대출 기록, 책#

도서관에 비유하면:

  • fd = 내 손에 든 번호표 (프로세스마다 따로 번호를 매긴다. 0, 1, 2, 3 …)
  • open file description(OFD) = 대출 기록 카드. "몇 쪽까지 읽었나(offset)", "어떤 모드로 빌렸나(읽기 전용, append …)"가 적혀 있다. open()을 부를 때마다 새 카드가 생긴다.
  • inode = 책 그 자체. 크기, 권한, 데이터가 디스크 어디 있는지. 파일마다 하나다.

번호표 여러 장이 같은 대출 카드를 가리킬 수 있고, 대출 카드 여러 장이 같은 책을 가리킬 수 있다. 이 "여러 대 하나" 관계 두 단계가 dup, fork, O_APPEND, 파일 잠금의 동작을 전부 설명한다.

그림 2 — 예제 ex1의 상태. fd 3·5·10은 같은 OFD를 공유해서 offset도 공유한다. fd 4는 같은 파일을 따로 open 했으므로 offset이 독립이다.

용어 주의: POSIX 표준은 가운데 층을 open file description이라 부르고, 커널 코드는 struct file이라 부른다. 둘은 같은 것이다. "file descriptor"(fd, 번호)와 "file description"(객체)을 헷갈리지 말 것.

fd 번호 규칙 두 가지:

  1. open()은 비어 있는 가장 작은 번호를 돌려준다. 그래서 close(1) 후 open()하면 stdout이 그 파일로 바뀐다 (셸 리다이렉션의 원리).
  2. 프로세스당 개수 제한은 RLIMIT_NOFILE이다. 이 VM에서 ulimit -n은 soft 1024, hard 524288이었다. 넘으면 EMFILE.

1.3 예제 ex1 — open 두 번 vs dup#

무엇을 확인하나: 같은 파일을 open() 두 번 하면 offset이 따로 놀고, dup()/dup2()로 만든 fd는 offset을 공유하는지 /proc/self/fdinfo로 직접 본다.

출력에서 볼 것:

  • lseek(a, 3)만 했는데 c(dup)의 pos도 3이다. 둘이 같은 OFD를 가리키기 때문이다. b는 0 그대로다.
  • read(c)가 '3'을 읽고 나니 a의 pos가 4로 움직였다. offset은 fd가 아니라 OFD에 있다.
  • flags: 0400002는 8진수다. 끝의 2가 O_RDWR, 0400000은 arm64에서의 O_LARGEFILE이다(64비트 커널은 자동으로 붙인다). 아키텍처마다 이 비트 값이 다르므로 숫자를 외우지 말고 헤더 상수로 비교한다.
  • /proc/<pid>/fdinfo/<fd>는 디버깅에 아주 유용하다. 실행 중인 데몬이 파일을 어디까지 읽었는지 바로 보인다.

2. dup/dup2, fork 상속, O_CLOEXEC#

2.1 dup과 dup2#

  • dup(old): 비어 있는 가장 작은 번호에 old와 같은 OFD를 가리키는 새 fd를 만든다.
  • dup2(old, new): 번호를 new로 지정한다. new가 열려 있으면 먼저 닫는다(원자적으로). 셸의 2>&1이 바로 dup2(1, 2)다.
  • dup3(old, new, O_CLOEXEC): dup2 + close-on-exec 비트를 같이 세팅 (Linux 전용).
  • dup으로 만든 새 fd는 FD_CLOEXEC 비트가 꺼진 상태로 시작한다. 이 비트는 OFD가 아니라 fd 쪽(그림 2의 왼쪽 열)에 있기 때문이다. 그래서 ex1의 c(dup) flags에 O_CLOEXEC가 보이지 않는다.

2.2 fork는 fd table을 복사하고, OFD는 공유한다#

fork()는 부모의 fd table을 통째로 복사한다. 하지만 복사된 항목이 가리키는 OFD는 복사하지 않고 참조 카운트만 올린다. 결과적으로 부모와 자식은 같은 offset을 공유한다. 로그 파일을 부모·자식이 같이 쓰면 서로 덮어쓰지 않고 이어서 써지는 이유가 이것이다.

exec()는 fd table을 유지한다. 다만 close-on-exec 비트가 켜진 fd는 exec 순간에 닫힌다. O_CLOEXEC를 안 붙이면 자식 프로그램(예: system()으로 부른 셸 스크립트)이 부모의 장치 fd·소켓을 몰래 물려받는다. 이것을 fd 누수(fd leak)라고 부른다.

그림 3 — fork 직후 부모·자식 fd table은 같은 OFD들을 가리킨다. 자식이 exec 하면 O_CLOEXEC로 연 fd 4만 끊긴다.

2.3 예제 ex2 — offset 공유와 O_CLOEXEC#

무엇을 확인하나: 자식이 쓴 뒤 부모가 보는 offset, 그리고 exec된 ls가 물려받은 fd 목록.

출력에서 볼 것:

  • 부모는 아무것도 안 썼는데 pos seen by parent=6이다. 자식의 write가 공유 OFD의 offset을 옮겼다. 그래서 log.txt에 "child" 다음 "parent"가 이어서 들어갔다.
  • exec된 ls의 fd 목록에 3(log.txt)과 5(hostname, CLOEXEC 없음)는 있지만, 원래 fd 4(CLOEXEC)는 없다. 그 자리(4번)는 ls가 /proc/self/fd 디렉터리를 열면서 재사용했다(가장 작은 빈 번호 규칙). PID 값은 실행마다 다르다.
  • fd 0이 pipe:인 이유: limactl shell이 tty 없이 실행해서 stdin/stdout이 pipe로 연결되어 있다.

2.4 흔한 함정#

  • 멀티스레드 프로그램에서 open() 후 fcntl(fd, F_SETFD, FD_CLOEXEC)를 따로 부르면, 그 사이에 다른 스레드가 fork()+exec()하는 경쟁이 생긴다. 그래서 처음부터 O_CLOEXEC를 open 플래그로 준다. socket()의 SOCK_CLOEXEC, pipe2(…, O_CLOEXEC), accept4(), dup3()가 같은 이유로 생겼다.
  • O_NONBLOCK은 OFD에 있다. 자식에게 물려준 stdin에 O_NONBLOCK을 켜면 부모 셸의 stdin도 non-blocking이 된다. 프로그램 종료 후 셸이 이상해지는 버그의 원인이다.

무엇을 확인하나: 생성 플래그와 상태 플래그가 실제로 어떻게 동작하고, 상태 플래그를 fcntl로 나중에 바꿀 수 있는지.

출력에서 볼 것:

  • 0666을 요청해도 umask 022 때문에 0644가 된다.
  • O_APPEND로 연 fd는 lseek(0) 후 써도 파일 끝(10 다음)에 붙고 pos가 11이 된다. 여러 프로세스가 같은 로그 파일에 써도 서로 덮어쓰지 않는 이유다. "lseek(END) → write"를 직접 하면 두 동작 사이에 다른 프로세스가 끼어들 수 있지만, O_APPEND는 커널이 inode 락을 잡은 채로 끝 위치를 정하므로 경쟁이 없다.
  • F_SETFL로 바꿀 수 있는 것은 O_APPEND, O_NONBLOCK, O_ASYNC, O_DIRECT, O_NOATIME 정도다. 접근 모드나 O_SYNC는 F_SETFL로 바뀌지 않는다(Linux에서 O_SYNC 변경은 무시된다).

3.3 O_DIRECT 맛보기 — ex17#

O_DIRECT는 page cache를 건너뛰고 유저 버퍼에서 장치로 바로 DMA하게 한다. DB 엔진처럼 자기 캐시를 가진 프로그램이 쓴다. 대가는 정렬 제약이다: 버퍼 주소, 길이, 파일 offset이 장치의 논리 블록 크기(보통 512 B 또는 4 KiB) 배수여야 한다. Don이 SSD 펌웨어에서 봤던 "호스트 DMA 버퍼는 섹터 정렬이어야 한다"는 요구가 유저 API까지 올라온 모습이다.

무엇을 확인하나: 정렬이 어긋나면 EINVAL이 나는 것.

출력에서 볼 것: 주소가 1바이트 어긋나도, 길이가 100바이트여도 EINVAL. posix_memalign으로 4 KiB 정렬한 버퍼로 4096 B를 쓰면 성공한다. (/sys/block/vda/queue/logical_block_size는 512였다. 파일시스템마다 요구치가 다를 수 있으므로 4 KiB 정렬이 무난하고, 정확한 값은 statx()의 STATX_DIOALIGN으로 물어볼 수 있다.) O_DIRECT는 내구성 보장이 아니다. 장치의 쓰기 캐시에는 여전히 머물 수 있으므로 전원 안전을 원하면 fsync/fdatasync가 따로 필요하다.

4. read/write의 진짜 의미 — short count, EINTR, EAGAIN#

4.1 직관#

read(fd, buf, n)은 "n바이트를 읽어라"가 아니라 "최대 n바이트까지, 지금 줄 수 있는 만큼 줘라"다. UART RX FIFO에서 "남은 바이트만큼만 꺼내는" 것과 같다. 반환값 규칙:

반환값의미해야 할 일
n요청한 만큼 다 됨다음으로
0 < r < nshort read/write. 지금 있는 만큼만나머지를 이어서 다시 호출
0 (read)EOF. pipe·소켓은 상대가 닫음루프 종료
-1, errno == EINTR데이터 옮기기 전에 시그널이 끼어듦그냥 다시 호출
-1, errno == EAGAINnon-blocking인데 지금 데이터/공간 없음poll/epoll로 기다렸다가 다시 (A4)
-1, 그 밖의 errno진짜 에러 (EIO, ENODEV, EFAULT …)처리/보고

short count가 나오는 대표 장면: pipe·소켓·tty에서 지금 버퍼에 있는 양이 요청보다 적을 때, 시그널이 일부 전송 후에 끼어들 때, non-blocking pipe에 남은 공간이 요청보다 적을 때, 디스크가 꽉 찼을 때, 그리고 sysfs·드라이버가 원래 한 번에 그만큼만 줄 때. 정규 파일은 보통 다 읽혀서 "short read는 안 일어난다"고 착각하기 쉬운데, 장치·pipe에서는 일상이다.

출력에서 볼 것: 첫 read(3, …, 30)은 10을 돌려줬다. read_full은 내부에서 read(…, 20) = 10, read(…, 10) = 10으로 두 번 불러서 20을 채웠다. 마지막 read = 0은 자식이 끝나 쓰기 쪽이 모두 닫혔다는 EOF 신호다. 이 read_full/write_full 두 함수는 센서 프레임(예: 고정 길이 32바이트 패킷)을 다루는 모든 툴에 그대로 복사해 쓴다.

4.3 예제 ex5 — EAGAIN, non-blocking short write, EINTR#

무엇을 확인하나: O_NONBLOCK이면 기다리는 대신 EAGAIN, 공간이 부족하면 short write, 시그널이 블록 중인 read를 깨우면 EINTR, SA_RESTART가 있으면 자동 재시작.

출력에서 볼 것:

  • 빈 non-blocking pipe를 읽으면 즉시 EAGAIN (EWOULDBLOCK과 같은 값).
  • pipe 용량은 기본 65536(64 KiB, F_SETPIPE_SZ로 /proc/sys/fs/pipe-max-size = 1 MiB까지 늘릴 수 있다). 100000바이트를 요청하면 65536만 쓰고 반환한다. 반환값을 무시하면 34464바이트가 조용히 사라진다.
  • sa_flags = 0으로 등록한 핸들러가 블록 중인 read를 깨우면 EINTR. SA_RESTART를 주면 커널이 read를 다시 걸어 주므로 1초에 시그널이 와도(핸들러 실행 횟수 2: 앞의 것 1번 + 이번 1번) 2초에 들어온 4바이트를 정상으로 받는다.
  • 주의: SA_RESTART가 있어도 재시작되지 않는 syscall이 있다(poll, epoll_wait, nanosleep, 타임아웃이 걸린 소켓 연산 등, man 7 signal 참고). 그러니 EINTR 처리는 항상 넣는다.

4.4 커널 쪽에서 보면#

드라이버의 .read는 보통 이렇게 생겼다 (자세한 것은 F3, G4):

-ERESTARTSYS를 돌려주면 커널의 시그널 처리 코드가 SA_RESTART 여부를 보고 "syscall을 다시 걸지, 유저에게 EINTR을 줄지"를 정한다. 즉 ex5에서 본 두 동작은 드라이버가 이 한 줄로 만들어 내는 것이다.

5. lseek, pread/pwrite, 그리고 hole#

5.1 정의#

  • lseek(fd, off, whence): OFD의 offset만 바꾼다. I/O는 하지 않는다. SEEK_SET(처음 기준), SEEK_CUR(현재 기준), SEEK_END(끝 기준). 현재 위치를 알고 싶으면 lseek(fd, 0, SEEK_CUR).
  • pread(fd, buf, n, off) / pwrite(…): 지정한 offset에서 읽고 쓰되 OFD의 offset을 건드리지 않는다. 원자적인 "seek + read"다. 여러 스레드가 같은 fd를 공유하면서 서로 다른 위치를 읽을 때 필수다 (lseek + read를 따로 하면 사이에 다른 스레드가 offset을 옮긴다).
  • pipe, 소켓, tty는 seek이 안 된다 → lseek은 ESPIPE.
  • 파일 끝 너머로 seek 후 쓰면 그 사이가 hole이 된다. 읽으면 0이 나오지만 디스크 블록은 할당되지 않는다(sparse file).

5.2 예제 ex6 — 가짜 레지스터 맵을 pread/pwrite로#

무엇을 확인하나: pread/pwrite는 offset을 안 움직인다, 끝 너머 쓰기는 hole을 만든다.

출력에서 볼 것:

  • pread로 reg[5]를 읽어도 pos는 64 그대로다.
  • 1 MiB 지점에 1바이트를 쓰면 st_size는 1048577이지만 실제 할당은 8192바이트(첫 블록 + 마지막 블록)뿐이다. ls -ls의 맨 앞 숫자(할당 KiB)도 8이다. SEEK_DATA/SEEK_HOLE로 데이터가 어디 있는지 찾을 수 있다.
  • 실무 연결: 많은 장치 노드가 "offset = 레지스터 주소" 모델을 쓴다. 예를 들어 I2C EEPROM 드라이버(at24)는 sysfs의 eeprom 바이너리 속성 파일을 노출하고, pread(fd, buf, 16, 0x40)이 EEPROM 0x40번지부터 16바이트를 읽는다. NVMEM, /dev/port, /proc/<pid>/mem도 같은 모델이다.

6. Blocking vs non-blocking — 장치와 pipe에서#

6.1 직관#

bare-metal에서 UART 수신을 기다리는 방법은 두 가지였다: 플래그를 polling 하며 busy-wait하거나, 인터럽트가 올 때까지 태스크를 block시키거나(RTOS 세마포어). Linux의 blocking read는 후자다. 데이터가 없으면 커널이 프로세스를 wait queue에 넣고 재운다(CPU 0%). 데이터가 오면 드라이버의 인터럽트 핸들러가 wake_up()으로 깨운다.

non-blocking(O_NONBLOCK)은 "기다릴 상황이면 즉시 EAGAIN으로 돌아와라"다. 혼자서는 쓸모가 적고, poll/epoll과 짝을 이뤄 "여러 fd 중 준비된 것만 처리"하는 이벤트 루프를 만든다(A4).

6.3 흔한 함정#

  • non-blocking fd에 read_full 같은 루프를 그대로 돌리면 EAGAIN에서 에러로 빠지거나, EAGAIN을 continue로 처리하면 busy loop(CPU 100%)가 된다. non-blocking이면 반드시 poll로 기다린다.
  • 장치 드라이버가 O_NONBLOCK을 무시하도록 짜여 있으면 유저가 아무리 플래그를 켜도 블록한다. 테스트 툴을 짤 때 드라이버가 실제로 무엇을 지원하는지 확인한다(G4, G6).

7. 버퍼링 계층과 내구성 — fflush, fsync, fdatasync#

7.1 직관 — 데이터가 머무는 곳은 여섯 군데#

Don이 SSD 펌웨어에서 봤던 "호스트가 보낸 데이터가 DRAM write buffer에 있다가 NAND program으로 내려가는" 구조가 Linux 쪽에는 몇 단계 더 붙어 있다.

그림 4 — fprintf 한 줄이 NAND 셀에 도달하기까지. 각 화살표를 넘기는 함수가 다르다.

  • fclose()나 close()는 fsync를 하지 않는다. close가 성공해도 데이터는 page cache에 있을 수 있다.
  • fsync가 없어도 커널은 결국 내려 쓴다(writeback). 이 VM에서 vm.dirty_expire_centisecs = 3000(30초 지난 dirty page를 내림), dirty_writeback_centisecs = 500(5초마다 flusher 스레드가 깸)이었다. 즉 전원이 나가면 최대 수십 초 분량을 잃을 수 있다.

7.2 예제 ex9 — strace로 계층 경계 보기#

무엇을 확인하나: fprintf는 syscall을 만들지 않고, fflush가 write를, fsync가 fsync를 만든다.

(동적 링커가 라이브러리를 여닫는 앞부분 줄은 생략했다.) 출력에서 볼 것: fprintf를 세 번 했지만 write(3, …)는 fflush 시점에 48바이트 한 번이다. stderr(fd 2)는 버퍼링이 없어서 메시지마다 바로 write가 나간다. stdout은 터미널이면 줄 단위(line buffered), pipe·파일이면 블록 단위(full buffered)라서 "printf가 파이프로 보내면 늦게 나온다"는 현상이 생긴다. 실시간 로그는 setvbuf(stdout, NULL, _IOLBF, 0) 또는 stderr를 쓴다.

7.3 예제 ex7 — 버퍼 크기가 처리량을 결정한다#

무엇을 확인하나: syscall 한 번의 고정 비용 때문에 작은 write를 많이 하면 느리다. stdio가 이걸 어떻게 숨기는지.

그림 5 — 위 측정값(tmpfs, 즉 page cache만 거치는 쓰기). 1바이트 write는 4.3 MB/s, 4 KiB 이상은 7~9 GB/s로 2000배 가까이 차이 난다.

출력에서 볼 것:

  • bs=1에서 838만 번 syscall에 약 2초가 걸렸다. 8 MiB ÷ 4.3 MB/s ≈ 1.95 s ÷ 8388608 ≈ syscall 한 번에 약 230 ns. 이것이 유저↔커널 경계를 넘는 고정비다(A1의 syscall 비용과 같은 이야기).
  • 4 KiB부터는 고정비가 묻히고 memcpy 속도(page cache로의 복사)가 한계가 된다. 그 이상은 이득이 작다.
  • fputc로 1바이트씩 써도 449.5 MB/s다. stdio가 4 KiB 정도 모아서 write 한 번으로 보내기 때문이다. 대신 바이트마다 함수 호출 비용(멀티스레드 프로그램이면 FILE 락 비용까지)이 남아 큰 버퍼 write보다는 느리다.
  • 수치는 이 VM(Apple Silicon 위 aarch64 게스트)의 값이다. 보드에서는 절대값이 다르지만 모양은 같다.

7.4 예제 ex8 — 내구성의 가격#

무엇을 확인하나: 4 KiB 레코드 하나를 "확실히" 쓰는 방식별 비용. tmpfs가 아닌 ext4(/var/tmp) 위에서 측정한다.

그림 6 — 첫 번째 실행 값. write만 하면 0.6 us, 내구성을 요구하면 100배 이상 비싸다.

출력에서 볼 것:

  • write only는 page cache에 복사만 하므로 1 us도 안 걸린다. 그러나 이 상태로 전원이 나가면 데이터가 없다.
  • fdatasync(74~83 us)가 fsync(109~112 us)보다 싸다. 덮어쓰기라 파일 크기는 그대로지만 mtime이 바뀌므로, fsync는 inode 갱신까지 ext4 저널에 커밋해야 하고 fdatasync는 "데이터를 다시 읽는 데 필요 없는 메타데이터"라서 건너뛴다. 로그·저널처럼 자주 sync 하는 파일은 미리 크기를 잡아 두고(fallocate) fdatasync를 쓰는 게 정석이다.
  • O_DSYNC는 두 번 실행에서 80.6 us, 59.5 us로 흔들렸다. 측정값은 실행마다 다르다.
  • 주의: 이 VM의 디스크는 virtio이고 그 뒤에 macOS 호스트 파일이 있다. 호스트가 flush를 어떻게 처리하는지에 따라 숫자가 달라진다. 실제 eMMC/SD 카드에서는 cache flush가 실제 NAND program을 기다려야 해서 보통 이보다 훨씬 느리다(ms 단위도 흔하다). 보드에서는 반드시 직접 재 보라.

7.5 Don의 SSD 경험과 연결 — 장치 쪽 캐시#

Linux가 fsync를 처리할 때 마지막에 하는 일은 장치에 cache flush 명령을 보내는 것이다 (/sys/block/vda/queue/write_cache가 write back이면 커널이 flush를 보낸다). NVMe라면 Flush 명령, SATA는 FLUSH CACHE, eMMC는 EXT_CSD의 FLUSH_CACHE, SCSI/UFS는 SYNCHRONIZE CACHE다. 또 일부 쓰기에는 FUA(Force Unit Access, "이 쓰기는 캐시에 머물지 말고 매체까지") 비트를 단다. ext4 저널 커밋 블록이 대표적이다.

Don이 만든 엔터프라이즈 SSD는 PLP(power loss protection) 커패시터가 있어서 전원이 나가도 DRAM의 데이터를 NAND로 내릴 수 있었다. 그래서 Flush가 싸다. 그러나 임베디드 보드의 eMMC/SD/저가 UFS에는 보통 PLP가 없다. 이런 장치에서는

  1. fsync 없이 쓴 데이터는 page cache에서 날아가고,
  2. fsync를 했어도 장치가 flush를 제대로 구현하지 않으면 장치 DRAM에서 날아가며,
  3. 최악의 경우 FTL 매핑 테이블이 깨져서 방금 쓴 것과 무관한 오래된 데이터까지 손상된다(Don이 FTL에서 매핑 테이블 저널링을 왜 했는지 떠올리면 된다).

그래서 필드 장비 설계에서는 "어떤 데이터를 언제 fsync 할 것인가"를 의식적으로 정하고(설정·캘리브레이션 값은 매번, 대용량 로그는 묶어서), 파일 갱신은 다음 절의 write-temp → fsync → rename → fsync(dir) 패턴을 쓴다. 깊은 이야기는 J5(전원 차단 안전성)에서 다룬다.

8. ioctl — 스트림으로 표현할 수 없는 제어#

8.1 직관과 정의#

read/write는 "바이트 흐름"이다. 그런데 장치에는 흐름이 아닌 명령이 많다: "SPI 모드를 3으로", "이 I2C 주소로 combined transaction", "터미널 창 크기를 알려줘", "블록 장치 용량은?". 이런 걸 위한 탈출구가 ioctl이다.

  • request: 32비트 명령 번호. 드라이버가 정의하고 헤더(<linux/…>)로 공개한다.
  • 셋째 인자: 명령마다 정해진 타입. 보통 포인터이고, 커널은 copy_from_user/copy_to_user로 그 메모리를 읽고 쓴다.
  • 장치가 모르는 명령이면 ENOTTY ("Inappropriate ioctl for device"). 역사적 이유로 이 이름이다. 최근 드라이버는 -ENOIOCTLCMD를 돌려주고 VFS가 ENOTTY로 바꾼다.

8.2 번호 인코딩 — _IO, _IOR, _IOW, _IOWR#

명령 번호를 아무렇게나 정하면 엉뚱한 장치에 보낸 명령이 우연히 다른 의미로 실행될 수 있다. 그래서 번호 안에 방향, 인자 크기, 드라이버 고유 type, 순번을 넣는 규칙을 쓴다.

그림 7 — 32비트 ioctl 번호의 비트 필드 (include/uapi/asm-generic/ioctl.h). PowerPC·MIPS·Alpha 등은 dir 3비트·size 13비트로 다르다.

방향의 R/W는 유저 관점이다. _IOR은 "유저가 읽는다" = 커널이 유저 버퍼에 쓴다. type 값(매직 넘버)은 Documentation/userspace-api/ioctl/ioctl-number.rst에 드라이버별로 등록되어 있다.

8.3 예제 ex10 — 실제 번호 분해#

무엇을 확인하나: 커널 헤더에 정의된 ioctl 번호를 매크로로 분해하면 그림 7처럼 나오는지.

  • BLKGETSIZE64 = 0x80081272: dir=R(2), size=8(size_t), type=0x12(블록 계층), nr=114.
  • SPI_IOC_MESSAGE(n)은 size 필드에 n × sizeof(struct spi_ioc_transfer)(32바이트)를 넣는다. 1개면 32, 2개면 64. 드라이버는 _IOC_SIZE(cmd) / 32로 전송 개수를 알아낸다. 번호에 데이터 길이를 실은 영리한 예다.
  • FS_IOC_GETFLAGS는 _IOR('f', 1, long)으로 정의되어 size=8이지만, 실제로 주고받는 값은 int다(헤더 정의가 역사적으로 잘못된 유명한 예, man ioctl_iflags). 번호의 size는 "정의할 때 쓴 타입"일 뿐 커널이 자동 검증하는 게 아니다.
  • TIOCGWINSZ(0x5413), FIONREAD, I2C_RDWR(0x0707) 등은 인코딩 규칙이 생기기 전의 legacy 번호라 dir·size가 0이다. 이 값들은 아키텍처마다 다를 수 있으니 항상 헤더 상수를 쓴다.

9. 장치 노드 — char/block, major/minor, mknod#

9.1 정의#

/dev의 파일들은 디스크에 데이터가 없는 특수 파일이다. inode에 들어 있는 건 두 가지뿐이다: 종류(문자 c / 블록 b)와 장치 번호(major, minor).

  • major: 어느 드라이버인가 (1 = mem 계열, 4 = tty, 7 = loop, 89 = i2c …)
  • minor: 그 드라이버가 관리하는 몇 번째 장치인가 (i2c-0, i2c-1 …)
  • char 장치: 바이트 스트림 + ioctl. 대부분의 주변장치(UART, I2C, SPI, 센서, GPIO chip, watchdog).
  • block 장치: 고정 크기 블록 단위 랜덤 액세스, page cache와 블록 계층(I/O 스케줄러)을 거친다. eMMC, SD, NVMe, loop.

장치 노드 이름은 관례일 뿐이다. 커널은 이름이 아니라 (type, major, minor)로 드라이버를 찾는다. 지금은 devtmpfs와 udev가 드라이버 등록 시점에 노드를 자동으로 만든다(G9, L2).

10.1 i2c-dev와 I2C_RDWR#

I2C 센서 레지스터 읽기는 보통 "START → 주소+W → 레지스터 번호 → repeated START → 주소+R → 데이터 N바이트 → STOP"이다. Don이 로직 분석기로 매일 보던 그 파형이다. 중간에 STOP이 들어가면 안 되는 센서가 많으므로(레지스터 포인터가 리셋되거나 다른 마스터가 끼어들 수 있음) write() 후 read()를 따로 부르는 대신 I2C_RDWR ioctl 한 번에 메시지 두 개를 넘긴다. 커널은 이것을 하나의 트랜잭션(중간은 repeated START)으로 보낸다.

다른 방법은 SMBus 프로토콜(I2C_SMBUS ioctl)이다. "read byte data" 같은 정해진 형태만 되지만 SMBus만 지원하는 컨트롤러에서도 동작한다. i2c-tools의 i2cget이 이 방식이다.

무엇을 확인하나: 장치가 없으면 open에서 ENOENT, 권한이 없으면 EACCES, 어댑터가 raw I2C를 지원하지 않으면 I2C_RDWR이 EOPNOTSUPP, 주소에 장치가 없으면 에러.

먼저 I2C 장치가 전혀 없을 때(기본 경로 /dev/i2c-1):

이 VM에는 커널의 가짜 I2C 어댑터인 i2c-stub 모듈이 chip_addr=0x68(MPU-6050 계열 IMU 주소)로 올라가 있어서 /dev/i2c-0이 존재한다. 직접 올리려면 sudo modprobe i2c-stub chip_addr=0x68이다.

sudo strace -e trace=ioctl로 보면 (strace가 i2c 번호 이름을 모르면 _IOC(…) 형태로 해독한다. 0x7 0x5 = I2C_FUNCS, 0x7 0x7 = I2C_RDWR, 0x7 0x3 = I2C_SLAVE, 0x7 0x20 = I2C_SMBUS):

출력에서 볼 것:

  • ENOENT: 노드가 없다 = 컨트롤러 드라이버가 안 떴거나 DT에서 버스가 disabled이거나 i2c-dev가 없다. 실제 보드에서 가장 먼저 보는 에러다.
  • EACCES: 노드는 root:i2c 0660이다. 일반 사용자는 i2c 그룹에 넣거나 udev rule로 권한을 준다.
  • I2C_FUNCS로 어댑터 능력을 먼저 물어보는 것이 정석이다. stub은 I2C_FUNC_I2C 비트가 없어서(SMBus 전용) I2C_RDWR이 EOPNOTSUPP로 실패한다. 진짜 SoC I2C 컨트롤러(i.MX, AM62 …)는 보통 둘 다 지원한다.
  • 0x50(장치 없음)에서는 ENODEV, 0x68(stub 칩)에서는 값 0x00을 읽었다. 실제 하드웨어에서 NACK이 나면 드라이버에 따라 ENXIO나 EREMOTEIO가 돌아온다(커널 문서 Documentation/i2c/fault-codes.rst). 로직 분석기에서 NACK을 본 것과 errno를 짝지어 기억해 두면 디버깅이 빨라진다.
  • 주의: 커널 드라이버가 이미 붙은 주소에 I2C_SLAVE를 하면 EBUSY가 난다. 정말 필요하면 I2C_SLAVE_FORCE가 있지만, 드라이버와 동시에 같은 칩을 만지는 것이므로 레지스터 상태가 꼬일 수 있다.

10.2 spidev#

SPI는 전이중이라 "보내는 동안 받는다". spidev의 SPI_IOC_MESSAGE(n)은 struct spi_ioc_transfer 배열을 받아 CS를 잡은 채로 n개의 transfer를 연속 실행한다. 아래는 IMU의 WHO_AM_I 레지스터(예: 0x75)를 읽는 전형적인 코드다. 첫 바이트의 MSB가 "읽기" 비트인 것은 많은 SPI 센서의 관례다(데이터시트 확인 필수).

무엇을 확인하나: 이 VM에는 SPI 컨트롤러가 없으므로 컴파일이 되는지, 그리고 장치가 없을 때의 실패 모습.

출력에서 볼 것: 장치 노드가 없으면 open에서 ENOENT로 끝난다. 실제 보드에서는 DT의 SPI 컨트롤러 아래에 spidev로 바인딩되는 자식 노드가 있어야 /dev/spidev<bus>.<cs>가 생긴다(H7, D 모듈). 번호 해독은 ex10에서 본 대로 SPI_IOC_MESSAGE(1) = 0x40206b00이다.

10.3 /dev/mem — 왜 위험한가#

/dev/mem은 물리 주소 공간 전체를 파일로 보여준다. mmap(fd, offset = 물리주소)로 레지스터를 유저 공간에 매핑하면 bare-metal처럼 volatile uint32_t *로 직접 읽고 쓸 수 있다. 펌웨어 엔지니어에게는 매력적이지만 위험하다:

  1. 커널 드라이버와 경쟁: 드라이버가 같은 레지스터를 read-modify-write 하는 중에 끼어들면 상태가 깨진다. 락도 없다.
  2. 전원·클럭 상태를 모른다: 클럭이 꺼진 블록의 레지스터를 읽으면 SoC에 따라 bus error(SError)로 커널 전체가 죽는다. Don이 bring-up에서 봤던 "클럭 안 켜고 레지스터 읽어서 행" 그대로다.
  3. 보안: 루트가 커널 메모리를 마음대로 읽고 쓸 수 있으면 secure boot·권한 분리가 무의미하다.

그래서 대부분의 커널은 CONFIG_STRICT_DEVMEM=y로 RAM 영역 접근을 막고 I/O 영역만 허용한다(CONFIG_IO_STRICT_DEVMEM=y면 드라이버가 점유한 I/O 영역도 막는다). 이 VM은 STRICT_DEVMEM=y, IO_STRICT_DEVMEM은 꺼져 있다. 안전을 위해 이 예제는 RAM(커널 코드 영역)만 시도한다. MMIO 영역을 VM에서 함부로 읽지 않는다.

무엇을 확인하나: 일반 사용자와 root가 RAM 주소를 읽으려 할 때 어떻게 막히는지.

출력에서 볼 것: /dev/mem은 root:kmem 0640이라 일반 사용자는 EACCES. root여도 STRICT_DEVMEM 때문에 RAM은 read도 mmap도 EPERM이다. 레지스터를 봐야 한다면 정식 경로를 쓴다: 드라이버의 debugfs/regmap 덤프(/sys/kernel/debug/regmap/…, H2), 또는 UIO. devmem2나 busybox devmem은 개발 보드에서 레지스터를 잠깐 들여다볼 때만 쓰는 도구다.

10.4 sysfs 속성 파일 — 한 파일에 값 하나#

sysfs(/sys)는 커널 객체(장치, 드라이버, 버스)를 디렉터리 트리로 보여주고, 각 속성(attribute)을 텍스트 값 하나짜리 파일로 노출한다. 규칙:

  • 한 파일 = 한 값 (ASCII 텍스트, 보통 끝에 개행). 최대 PAGE_SIZE.
  • 읽을 때마다 드라이버의 show() 함수가 불려서 그 순간의 값을 만든다. 쓰면 store()가 불린다.
  • 같은 fd로 다시 읽으려면 lseek(fd, 0, SEEK_SET) 후 read (아니면 EOF가 나온다). 매번 open/close 해도 되지만 고속 폴링에서는 열어 둔 fd를 되감는 게 싸다.

무엇을 확인하나: 되감지 않으면 두 번째부터 EOF이고, 되감으면 새 값이 나오는지. 네트워크 수신 바이트 카운터를 쓰고, 값이 바뀌도록 ping을 동시에 돌린다.

출력에서 볼 것: lseek 없이 다시 읽으면 0바이트(EOF). lseek(0) 후에는 매번 show()가 다시 불려 값이 늘어난다(126853751 → 126853947 → 126854143, 값은 실행마다 다르다). 드라이버가 sysfs_notify()를 지원하는 속성이면 poll()로 POLLPRI를 기다렸다가 "lseek(0) + read"로 새 값을 읽는 패턴도 쓴다(G8, A4).

쓰기도 같다: echo 100 > /sys/bus/iio/devices/iio:device0/sampling_frequency 같은 한 줄이 드라이버 store() 호출이다. C에서 쓸 때는 write(fd, "100", 3)처럼 값 하나만 쓴다. 드라이버가 거부하면 write가 -1 EINVAL을 돌려주므로 반환값을 반드시 확인한다.

11. 커널 안에서는 무슨 일이 일어나나#

그림 8 — fd 3에서 드라이버 함수까지. open() 때 inode의 장치 번호로 cdev를 찾아 struct file의 f_op를 드라이버 것으로 바꿔 둔다. 이후 read/ioctl은 f_op만 따라간다.

11.1 open#

openat() → do_sys_openat2() → do_filp_open() → path_openat()이 경로를 따라가 inode를 찾고, struct file을 할당한 뒤 vfs_open() → do_dentry_open()이 file->f_op = inode->i_fop로 세팅하고 f_op->open을 부른다.

장치 파일이면 init_special_inode()가 미리 i_fop = &def_chr_fops(char) 또는 def_blk_fops(block)로 세팅해 두었다. char면 def_chr_fops.open = chrdev_open()이 i_rdev(major:minor)로 등록된 struct cdev를 찾아서 file->f_op를 드라이버의 file_operations로 교체하고 드라이버의 .open을 부른다. 마지막으로 fd_install()이 빈 fd 번호에 이 struct file을 꽂는다. O_CLOEXEC면 fdtable의 close_on_exec 비트맵에 표시한다.

드라이버를 쓸 때 다시 만나는 곳: cdev_add()/alloc_chrdev_region()으로 major:minor를 등록하는 것, 그리고 .open에서 filp->private_data에 장치 구조체를 걸어 두는 관용구(G4, G7 misc device).

11.2 read / write#

read() → ksys_read() → fdget_pos()(fd → struct file, 공유된 정규 파일이면 f_pos_lock 잡기) → vfs_read() → file->f_op->read 또는 ->read_iter. 드라이버의 .read(filp, ubuf, count, ppos)가 copy_to_user()로 데이터를 넘기고 넘긴 바이트 수를 반환한다. 이 반환값이 그대로 유저의 read() 반환값이다 → short read는 드라이버가 "그만큼만 줬다"는 뜻이다. 정규 파일은 read_iter → filemap_read()가 page cache에서 복사한다. write()는 generic_perform_write()가 page cache 페이지를 dirty로 표시하고 끝난다. 이것이 ex8의 "write only 0.6 us"다.

11.3 ioctl#

ioctl() → do_vfs_ioctl()이 먼저 공통 명령(FIOCLEX, FIONCLEX, FIONBIO, FIOASYNC, 정규 파일의 FIONREAD 등)을 처리하고, 나머지는 vfs_ioctl() → filp->f_op->unlocked_ioctl(filp, cmd, arg)로 보낸다. 32비트 유저 프로그램이 64비트 커널에서 부르면 .compat_ioctl이 불린다(구조체 레이아웃이 다를 수 있어서). i2c-dev의 경우 i2cdev_ioctl() → I2C_RDWR → i2c_transfer() → 어댑터 드라이버의 algo->xfer(옛 이름 master_xfer)이고, 어댑터에 그 함수가 없으면 -EOPNOTSUPP — ex12에서 stub이 돌려준 그 에러다. spidev는 spidev_ioctl() → spi_sync().

11.4 fork, exec, close, fsync#

  • fork() → copy_process() → copy_files() → dup_fd(): fdtable을 복사하고 각 struct file의 참조 카운트를 올린다(f_count, 6.13부터 file_ref_t f_ref). CLONE_FILES(스레드 생성)면 복사 없이 files_struct 자체를 공유한다.
  • exec() → do_close_on_exec(): 비트맵에 표시된 fd만 닫는다.
  • close(): fd 슬롯을 비우고 참조를 하나 내린다. 마지막 참조가 사라질 때만 드라이버의 .release가 불린다. dup된 fd가 남아 있으면 close해도 드라이버는 모른다 — 드라이버 테스트에서 "release가 안 불려요"의 흔한 원인이다. .flush는 close 때마다 불린다.
  • fsync() → vfs_fsync_range() → f_op->fsync(ext4는 ext4_sync_file()): dirty page writeback → 저널 커밋 → 필요하면 blkdev_issue_flush()로 장치에 cache flush.

12.1 설정 파일을 전원 차단에 안전하게 저장 — ex18#

센서 키트라면 IMU 캘리브레이션 값을 파일에 저장한다. 현장에서 배터리가 빠지는 순간 저장 중이었다면? fopen("w")로 덮어쓰다가 끊기면 빈 파일 또는 반쯤 쓴 파일이 남고, 다음 부팅에 캘리브레이션이 사라진다. 정석은 "임시 파일에 다 쓰고 → fsync → rename으로 교체 → 디렉터리 fsync"다. rename()은 같은 파일시스템 안에서 원자적이라서 전원이 언제 끊겨도 옛 파일 아니면 새 파일만 보인다.

  2. termios로 raw 모드, 보율 설정 (H8)
  3. epoll로 readable을 기다리고(A4), 읽은 바이트를 링버퍼에 붙인 뒤 \n 단위로 잘라 파싱

14. 면접에서 이렇게 말한다#

Q. What happens when two processes write to the same file? Explain file descriptors vs open file descriptions.

A. fd는 프로세스별 테이블의 인덱스이고, 그 항목이 커널의 open file description(struct file)을 가리킨다. offset과 상태 플래그는 OFD에 있다. 각자 open 했으면 OFD가 따로라 offset도 따로라서 서로 덮어쓸 수 있다. dup이나 fork로 공유했으면 offset을 공유해서 이어 쓴다. 로그처럼 여러 writer가 있으면 O_APPEND를 쓰면 커널이 매 write마다 원자적으로 끝으로 옮긴다.

There are three levels: the per-process fd table, the open file description which holds the offset and status flags, and the inode. Two independent open() calls create two descriptions with separate offsets, so writers can overwrite each other. dup() or fork() share one description, so they share the offset. For multiple writers to a log file I use O_APPEND, which makes the seek-to-end and write atomic.

꼬리 질문: "Where is the close-on-exec flag stored?" → fd 쪽(fdtable 비트맵). 그래서 dup이 이 비트를 복사하지 않는다.

Q. Why should you always check the return value of read() and write()?

A. 요청보다 적게 처리되는 short count가 정상 동작이기 때문이다. pipe·소켓·tty·장치는 지금 있는 만큼만 준다. 시그널이 오면 EINTR, non-blocking이면 EAGAIN이 온다. 그래서 루프를 돌며 남은 양을 계속 요청하고, EINTR은 재시도, EAGAIN은 poll로 기다린다. 실제로 pipe에 100000바이트를 non-blocking으로 쓰면 65536만 쓰인다.

read and write may transfer fewer bytes than requested; that is normal for pipes, sockets, ttys and device files. They can also fail with EINTR if a signal arrives, or EAGAIN on a non-blocking fd. So I wrap them in read_full/write_full loops that retry on EINTR, advance the buffer on short counts, and stop on EOF. On non-blocking fds I go back to poll or epoll instead of spinning.

Q. What is the difference between fflush, fsync and fdatasync? When does data actually reach the flash?

A. fflush는 stdio 버퍼를 write()로 커널에 넘길 뿐이다. 그때 데이터는 page cache에 있다. fsync는 그 파일의 데이터와 메타데이터를 장치까지 내리고 장치 캐시 flush까지 기다린다. fdatasync는 파일 크기처럼 데이터를 다시 읽는 데 필요한 메타데이터만 같이 내리고 mtime 같은 건 건너뛰어서 더 싸다. 내 VM 측정으로 4 KiB 기준 write만 0.6 us, fdatasync 약 75 us, fsync 약 110 us였다. 임베디드 eMMC는 PLP가 없어서 flush가 실제로 중요하다.

fflush only moves data from the stdio buffer into the kernel with write(); it is still in the page cache. fsync writes the file's dirty data and all its metadata to the device and issues a cache flush, so it survives power loss. fdatasync skips metadata that isn't needed to read the data back, like mtime, so it's cheaper. Close does not imply fsync. On boards with eMMC and no power-loss protection I use write-to-temp, fsync, rename, then fsync the directory for config files.

꼬리 질문: "What's O_DIRECT, does it make writes durable?" → page cache는 건너뛰지만 장치 캐시에 머물 수 있으므로 내구성 보장이 아니다. 여전히 fsync/fdatasync가 필요하다.

Q. How is an ioctl request number constructed?

A. 32비트 안에 방향 2비트, 인자 크기 14비트, 드라이버 고유 type 8비트, 명령 번호 8비트를 넣는다. _IOR/_IOW/_IOWR/_IO 매크로로 만든다. 방향은 유저 관점이라 _IOR은 커널이 유저 버퍼에 쓴다. 예로 BLKGETSIZE64는 _IOR(0x12, 114, size_t) = 0x80081272다. 엉뚱한 장치에 보내면 그 드라이버가 모르는 번호라 ENOTTY가 난다.

It's a 32-bit value built with _IO, _IOR, _IOW or _IOWR: two direction bits, a 14-bit argument size, an 8-bit type or magic number per driver, and an 8-bit command number. Direction is from user space's point of view. For example BLKGETSIZE64 is _IOR(0x12, 114, size_t), which is 0x80081272. In the driver I switch on cmd in unlocked_ioctl, use copy_from_user and copy_to_user with _IOC_SIZE, and return -ENOTTY for unknown commands.

Q. How would you read a register from an I2C sensor from user space?

A. /dev/i2c-N을 열고 I2C_FUNCS로 어댑터 능력을 확인한 뒤, I2C_RDWR ioctl로 "레지스터 번호 쓰기" 메시지와 "N바이트 읽기" 메시지 두 개를 한 번에 보낸다. 그러면 중간에 STOP 없이 repeated START로 나간다. SMBus만 되는 컨트롤러면 I2C_SMBUS ioctl을 쓴다. 이건 bring-up 확인용이고, 제품에서는 IIO 같은 커널 드라이버로 옮긴다.

I open /dev/i2c-N, check I2C_FUNCS, and use the I2C_RDWR ioctl with two i2c_msg entries: a one-byte write of the register address and a read with I2C_M_RD. The kernel sends it as one combined transaction with a repeated start, which many sensors require. If the adapter only supports SMBus I use I2C_SMBUS, like i2cget does. That's fine for bring-up, but for production I'd move to a kernel driver, for example IIO, so I get interrupts, timestamps and power management.

Q. Why is using /dev/mem to poke registers a bad idea?

A. 커널 드라이버와 락 없이 같은 레지스터를 만지게 되고, 클럭·전원이 꺼진 블록을 건드리면 bus error로 시스템이 죽을 수 있고, 보안상 루트에게 물리 메모리 전체를 여는 것이다. 그래서 STRICT_DEVMEM으로 RAM 접근은 막혀 있다. 대신 드라이버, regmap debugfs, UIO를 쓴다.

It bypasses the driver that owns the hardware, so there's no locking and no knowledge of clock or power state; touching a gated block can trigger a bus error and hang the SoC. It's also a security hole, which is why most kernels enable STRICT_DEVMEM and block RAM access. For debugging I use regmap debugfs or the driver's sysfs, and for real user-space drivers UIO or VFIO.

Q. What's the difference between blocking and non-blocking I/O on a device file, and how does the driver implement it?

A. blocking이면 데이터가 없을 때 드라이버가 프로세스를 wait queue에 재우고, 인터럽트 핸들러가 데이터가 오면 깨운다. non-blocking이면 드라이버가 filp->f_flags & O_NONBLOCK을 보고 바로 -EAGAIN을 준다. 시그널로 깨면 -ERESTARTSYS를 반환해서 커널이 EINTR이나 자동 재시작을 결정한다. 정규 파일에는 O_NONBLOCK이 의미 없다.

In blocking mode, the driver's read sleeps on a wait queue with wait_event_interruptible until the interrupt handler calls wake_up. In non-blocking mode it checks O_NONBLOCK in filp->f_flags and returns -EAGAIN immediately, and the application uses poll or epoll, which calls the driver's poll method. If a signal interrupts the sleep the driver returns -ERESTARTSYS and the kernel either restarts the call or returns EINTR depending on SA_RESTART.

Q. After fork(), the child closes a device fd but the driver's release() isn't called. Why?

A. fork 후에는 부모·자식 fd가 같은 struct file을 참조 카운트로 공유한다. release는 마지막 참조가 사라질 때만 불린다. 부모가 아직 열고 있으니 안 불리는 게 정상이다. 매 close마다 뭔가 해야 하면 .flush를 쓴다.

Because fork shares the same struct file between parent and child and only bumps its reference count. The driver's release runs only when the last reference is dropped, so as long as the parent still has it open, release is not called. If the driver needs a hook on every close, that's what the flush method is for.

  1. strace: strace -f -e trace=openat,dup2,dup3,close,execve sh -c 'ls > /tmp/out 2>&1'을 실행해서 셸이 리다이렉션을 어떤 syscall로 구현하는지 찾아라. 정답/힌트: 이 VM의 sh(dash)에서는 openat(/tmp/out, O_WRONLY, O_CREAT, O_TRUNC) = 3 → fcntl(1, F_DUPFD, 10)(원래 stdout을 10번에 백업) → dup3(3, 1, 0) → close(3) → dup3(1, 2, 0) → execve(ls) 순서였다. arm64에는 dup2 syscall이 없어서 glibc가 dup3(…, 0)으로 부른다.
  1. 측정: ex8을 fallocate로 미리 공간을 잡은 파일과, 매번 파일 끝에 덧붙이는(append) 경우로 바꿔 fsync·fdatasync 비용을 다시 재 보라. 덧붙이기에서 fdatasync가 fsync와 비슷해지는 이유는? 정답/힌트: append는 파일 크기(데이터를 읽는 데 필요한 메타데이터)가 매번 바뀌어서 fdatasync도 inode를 커밋해야 한다.
  1. ioctl: <linux/watchdog.h>의 WDIOC_GETTIMEOUT, WDIOC_SETTIMEOUT 번호를 ex10으로 분해하고, /dev/watchdog이 있는 보드라면 현재 타임아웃을 읽는 프로그램을 짜라(주의: watchdog을 열면 타이머가 시작될 수 있다. 닫기 전에 magic close 'V'를 쓴다). 정답/힌트: 둘 다 int 크기(4). GET은 _IOR, SET은 _IOWR(설정 후 실제 적용값을 돌려줌).
  1. sysfs: ex15를 /sys/class/net/eth0/statistics/ 아래 여러 파일(rx_bytes, tx_bytes, rx_packets)을 열어 두고 1초마다 lseek+read로 초당 증가량을 출력하는 미니 ifstat으로 바꿔라. 정답/힌트: fd 3개를 열어 두고 매 주기 pread(fd, buf, n, 0)를 쓰면 lseek이 필요 없다(pread는 offset 0부터 읽는다).

17. 요약 & 체크리스트#

fd는 프로세스별 번호표이고, 진짜 상태(offset, O_APPEND, O_NONBLOCK)는 open 한 번마다 생기는 open file description(struct file)에, 파일 자체 정보는 inode에 있다. dup과 fork는 OFD를 공유하므로 offset을 공유하고, close-on-exec만 fd 쪽 비트다. read/write는 "최대 n바이트"이며 short count, EINTR, EAGAIN을 루프로 다뤄야 한다. 데이터는 stdio 버퍼 → page cache → 장치 캐시 → 매체 순으로 내려가고, fflush·fsync·fdatasync는 각각 다른 경계를 넘긴다. 전원 안전이 필요한 파일은 temp → fsync → rename → fsync(dir). ioctl 번호는 dir·size·type·nr 비트 필드이며, 장치는 major:minor로 드라이버에 연결된다. 유저 공간 하드웨어 접근은 i2c-dev(I2C_RDWR), spidev(SPI_IOC_MESSAGE), sysfs(lseek 0 후 read)가 정식 경로이고 /dev/mem은 최후 수단이다. 이 모든 호출은 커널에서 struct file의 f_op → 드라이버의 file_operations로 이어진다.
