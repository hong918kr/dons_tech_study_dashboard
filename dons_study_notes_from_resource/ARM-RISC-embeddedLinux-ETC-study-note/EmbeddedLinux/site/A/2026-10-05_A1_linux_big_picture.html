이 노트를 다 읽으면: 유저 공간과 커널 공간이 CPU·MMU 수준에서 어떻게 갈리는지 설명할 수 있다 · arm64에서 syscall 한 번이 svc #0부터 eret까지 어떤 길을 가는지 그릴 수 있다 · /dev·/proc·/sys에서 원하는 정보를 찾아 읽을 수 있다 · open("/dev/xyz")가 드라이버의 file_operations까지 가는 경로를 말할 수 있다 왜 필요한가: 면접 첫 질문 "open()을 부르면 무슨 일이 일어나나요?", "user space와 kernel space의 차이는?"의 답이고, 실무에서 장치가 안 보일 때 /dev→/sys→dmesg 순으로 따라가는 감각의 출발점이다 Don 기준 난이도: 예외·특권 모드·MMU·인터럽트는 이미 안다 / Linux가 그것들을 어떻게 "프로세스·파일·syscall"이라는 추상으로 포장하는지가 새로 배울 부분 선행 노트: 없음

0. 큰 그림 — 이게 왜 필요한가#

Don이 만든 SSD 펌웨어를 떠올려 보자. 부팅하면 하나의 이미지가 Cortex-R 위에서 돌고, NVMe 명령 처리 태스크·NAND 스케줄러·에러 처리 코드가 모두 같은 특권 모드, 같은 주소 공간에서 레지스터를 직접 만진다. 어떤 태스크가 포인터를 잘못 쓰면 다른 태스크의 자료구조가 깨지고, 그 디버깅은 JTAG으로 한다.

Linux는 정반대 철학이다. 하드웨어를 직접 만지는 코드(커널)와 일반 프로그램(유저 프로세스)을 CPU 특권 레벨과 MMU로 물리적으로 갈라 놓는다. 유저 프로그램은 레지스터를 만질 수 없고, 다른 프로세스의 메모리를 볼 수도 없다. 무언가 필요하면 syscall(system call, 커널에 일을 부탁하는 정해진 입구)로 커널에 요청한다. 그리고 그 요청의 대부분은 "파일"이라는 하나의 모양으로 통일되어 있다 — 센서도, 시리얼 포트도, 파이프도, 네트워크 소켓도 open/read/write/close로 다룬다. 이것이 "everything is a file"이다.

그림 1 — Linux는 유저 공간(EL0)과 커널 공간(EL1)을 시스템 콜 경계로 가른다. Don의 bare-metal 펌웨어는 모든 코드가 한 특권 모드에서 돈다.

Embedded Linux 엔지니어의 하루는 이 그림의 경계를 오가는 일이다.

  • 센서 키트 bring-up: IMU 드라이버를 올렸는데 /dev/iio:device0이 안 생긴다 → /sys/bus/i2c/devices/에 디바이스가 있는지, 드라이버가 bind 됐는지 본다 (이 노트 §7).
  • 성능 이슈: 카메라 앱이 프레임을 놓친다 → strace -c로 syscall 횟수를 세고, 프레임마다 syscall을 몇 번 하는지 본다 (§4, §5).
  • 드라이버 작성: 내가 쓴 file_operations.read가 유저의 read()와 어떻게 이어지는지 알아야 테스트 코드를 짠다 (§10, G4).

이 노트는 그 전체 지도를 한 번에 그린다. 각 부분의 깊은 설명은 A2~A10, E, F, G 모듈에서 다시 한다.

실행 환경: 모든 출력은 Lima VM elinux(aarch64, uname -r = 7.0.0-34-generic, gcc 15.2, Apple Silicon 위 가상화)에서 실제로 돌린 결과다. PID·주소·inode 번호·시간은 실행마다 다르다.

1. 유저 공간 vs 커널 공간 — CPU 특권과 MMU 격리#

1.1 직관 — "같은 CPU, 다른 권한"#

Linux에서 유저 프로그램과 커널은 같은 CPU 코어에서 번갈아 돈다. 다른 점은 딱 두 가지다.

  1. CPU 특권 레벨: 커널은 EL1(Exception Level 1), 유저는 EL0에서 돈다. EL0에서는 시스템 레지스터 쓰기, 인터럽트 마스킹, 캐시·TLB 관리 같은 명령이 막혀 있다.
  2. MMU 페이지 권한: 페이지 테이블 엔트리마다 "EL0가 접근 가능한가" 비트(AP 비트)가 있다. 커널 메모리는 EL1 전용으로 매핑되어 있어서 유저가 주소를 알아도 못 읽는다.

Don에게 익숙한 말로 바꾸면: 유저 프로세스 = MPU(정확히는 MMU)로 격리된 비특권 태스크 + 자기만의 주소 공간이고, 커널 = 특권 모드에서 도는 RTOS 커널 + 모든 드라이버다.

1.3 코드로 확인 — 유저가 커널 주소를 읽거나 특권 명령을 쓰면?#

무엇을 확인하나: EL0에서 커널 가상 주소를 읽는 것과 msr daifset(bare-metal의 __disable_irq())을 실행하는 것이 각각 어떻게 막히는지 본다.

출력에서 볼 것: 커널 주소 읽기는 MMU permission fault → 커널의 fault 핸들러 → SIGSEGV(11). 특권 명령은 CPU가 EL1로 trap → 커널이 SIGILL(4)로 바꿔 보낸다. bare-metal에서는 HardFault/Data Abort 핸들러에서 시스템 전체가 멈췄을 일이, Linux에서는 그 프로세스 하나만 죽고 끝난다. 이게 격리의 가치다.

함정 메모: 처음 이 코드를 fflush(stdout) 없이 돌렸을 때 "parent: ... signal 11" 줄이 두 번 찍혔다. stdout이 파이프면 full buffering이라, 부모 버퍼에 남은 내용이 fork()로 자식에게 복사되고 자식이 그것을 다시 flush했기 때문이다. A2에서 자세히 본다.

1.4 커널이 유저 메모리를 다룰 때#

반대 방향도 규칙이 있다. 커널(EL1)은 기술적으로 유저 주소를 읽을 수 있지만, 아무 포인터나 믿고 읽으면 안 된다 (유저가 커널 주소를 넘길 수도 있고, 페이지가 아직 없을 수도 있다). 그래서 커널은 반드시 copy_from_user()/copy_to_user()로 유저 버퍼에 접근한다. arm64는 PAN(Privileged Access Never) 기능으로 "EL1이 실수로 유저 메모리를 직접 건드리면 fault"가 나게까지 막는다. 드라이버의 .read/.write에서 이 함수를 쓰는 이유가 이것이다 (E6, G4).

3.2 코드로 확인 — 같은 write를 세 가지 방법으로#

무엇을 확인하나: libc 래퍼 write(), 범용 래퍼 syscall(), 그리고 레지스터를 직접 채우고 svc #0을 쏘는 인라인 어셈블리가 모두 같은 일을 한다는 것.

출력에서 볼 것: 세 방법 모두 쓴 바이트 수(16, 27, 21)를 돌려준다. libc의 write()도 결국 x8=64를 넣고 svc #0을 하는 얇은 래퍼일 뿐이다.

3.4 반환값 규약 — 커널은 -errno, libc는 -1 + errno#

커널 안의 함수들은 실패를 음수 에러 코드로 돌려준다 (return -ENOENT;). 드라이버를 쓸 때도 똑같이 return -EINVAL;처럼 쓴다. 이 값이 그대로 x0에 실려 유저로 온다. libc 래퍼는 x0가 -4095~-1 범위면 "에러"로 보고, errno = -x0로 저장한 뒤 -1을 반환한다.

무엇을 확인하나: 같은 openat을 libc로 부를 때와 직접 svc로 부를 때 반환값이 어떻게 다른지.

출력에서 볼 것: 커널이 실제로 돌려준 값은 -2, -13, -21이다. libc는 그것을 -1과 errno = 2, 13, 21로 바꿨다. 성공한 경우 fd가 3, 4로 늘어나는 것도 보자 — 새 fd는 항상 비어 있는 가장 작은 번호다.

함정: errno는 실패했을 때만 의미가 있다. 성공한 호출은 errno를 0으로 지우지 않는다. "errno != 0이면 에러"라고 판단하면 틀린다. 반환값을 먼저 본다.

3.5 syscall 한 번의 전체 경로#

그림 2 — arm64에서 open() 한 번의 왕복. 왼쪽 두 레인은 EL0, 오른쪽 두 레인은 EL1이다. 함수 이름은 커널 7.0에서 ftrace로 확인한 것(§10).

순서를 말로 쓰면:

  1. 앱이 open(path, flags) 호출 → libc가 x0=AT_FDCWD, x1=path, x2=flags, x3=mode, x8=56을 채운다.
  2. svc #0 → CPU가 동기 예외를 일으키고 EL1으로 올라가 VBAR_EL1 벡터 테이블의 "Lower EL, AArch64, Synchronous" 엔트리로 점프한다. 이때 하드웨어가 복귀 주소를 ELR_EL1, 상태를 SPSR_EL1에 저장한다 (Don이 아는 예외 진입과 같다).
  3. 커널 엔트리 코드(el0t_64_sync)가 유저 레지스터 전부를 커널 스택의 struct pt_regs에 저장한다.
  4. el0t_64_sync_handler → el0_svc → do_el0_svc → invoke_syscall이 sys_call_table[x8]에서 핸들러를 찾아 부른다.
  5. __arm64_sys_openat → VFS → (장치 파일이면) 드라이버의 .open.
  6. 반환값을 pt_regs->regs[0]에 넣고, 레지스터 복원 후 eret. 돌아가기 직전 "다시 스케줄해야 하나?", "보낼 시그널이 있나?"를 확인한다 — 이것이 syscall 복귀가 preemption·시그널 전달 지점이 되는 이유다 (A6, F1).

4. strace — syscall을 눈으로 보는 도구#

strace는 ptrace syscall로 다른 프로세스의 syscall 진입·복귀마다 멈춰서 인자와 반환값을 찍는다. Don에게는 "모든 SVC 진입에 브레이크포인트를 건 JTAG"이라고 생각하면 된다.

무엇을 확인하나: 아주 작은 프로그램 하나가 실제로 몇 개의 syscall을 하는지, 그중 "내 코드"는 어디인지.

5.2 숫자 읽는 법#

  • 함수 호출 0.9 ns vs getpid 125 ns: getpid는 커널이 하는 일이 거의 없다 (current->tgid 읽기). 그런데도 125 ns가 드는 건 경계를 넘는 비용 때문이다: 예외 진입, 레지스터 31개 저장·복원, Spectre/Meltdown 계열 완화 코드, 복귀 전 확인(시그널·재스케줄), eret. 이것이 "syscall 하나의 고정 비용"이다.
  • libc getpid() = syscall(SYS_getpid): glibc 2.25부터 getpid를 캐시하지 않으므로 매번 진짜 syscall이다.
  • vDSO 19 ns: clock_gettime은 커널이 모든 프로세스에 매핑해 주는 작은 공유 라이브러리 vDSO(virtual dynamic shared object) 안에서 처리된다. 커널이 시간 정보를 읽기 전용 페이지(vvar)에 계속 갱신해 두고, 유저는 거기서 값을 읽고 CNTVCT_EL0(ARM generic timer 카운터, EL0에서 읽기 허용)를 직접 읽어 보정한다. 경계를 안 넘으니 빠르다. 같은 일을 syscall()로 강제하면 158 ns.
  • read(/dev/zero, 1B) 167 ns: 고정 비용 + VFS(fdget, 권한 검사, 드라이버 .read_iter 호출, 1바이트 copy_to_user). 1바이트씩 읽는 루프가 왜 나쁜지 보여 준다 — 1 MB를 1바이트씩 읽으면 syscall만 0.17초다.
  • open+close 670 ns: 경로 탐색(/ → dev → null dentry 조회), struct file 할당, 드라이버 .open, 그리고 close의 정리. 열기는 한 번, 읽기는 여러 번이 원칙인 이유.

측정 주의: 이 값은 Apple Silicon 위 가상 머신의 게스트 커널(EL1)에서 잰 값이다. syscall 자체는 하이퍼바이저로 나가지 않으므로 경향은 실제 하드웨어와 같지만, 절대값은 CPU·클럭·커널 설정(완화 옵션)에 따라 크게 다르다. 더 느린 임베디드 코어(예: 저클럭 Cortex-A53)에서는 몇 배 커질 수 있으니, 타깃 보드에서 같은 코드를 돌려 확인하는 습관을 들이자.

5.3 Embedded 관점의 결론#

  • 센서 데이터를 1샘플마다 read() 하지 말고, 드라이버가 FIFO·버퍼를 모아 한 번에 넘기게 한다 (IIO buffer, V4L2 buffer queue, mmap 공유 버퍼 — A5, I).
  • 타임스탬프는 clock_gettime(CLOCK_MONOTONIC)이 vDSO라서 싸다. 마음 놓고 써도 된다.
  • 200 Hz IMU 루프에 syscall 몇 개는 아무 문제 없다 (200 × 1 µs = 0.02% CPU). 문제가 되는 건 수십만 회/초 단위다 — 고속 ADC, 10 GbE 패킷, 1바이트 UART 읽기 루프.

6. VFS와 "everything is a file"#

6.1 직관 — 하나의 리모컨, 여러 기계#

VFS(Virtual File System, 가상 파일 시스템)는 "파일처럼 생긴 모든 것"에 같은 버튼(open/read/write/close/ioctl/mmap/poll)을 달아 주는 커널 계층이다. 버튼을 누르면 실제로 무엇이 일어날지는 그 파일 뒤에 있는 구현(ext4, 파이프, 소켓, 드라이버)이 정한다. C로 말하면 "함수 포인터 테이블로 하는 다형성"이고, 그 테이블이 바로 struct file_operations다. Don이 펌웨어에서 struct nand_ops { int (*read_page)(...); ... } 같은 HAL 테이블을 만들어 본 적이 있다면 정확히 그 패턴이다.

그래서 "everything is a file"의 정확한 의미는 "모든 것이 디스크 위 파일"이 아니라 "모든 것이 fd로 다뤄진다"다. 예외도 있다 — 네트워크 인터페이스(eth0)는 /dev에 노드가 없고 소켓·netlink로 다룬다.

출력에서 볼 것:

  • /dev/vda는 pci0000:00/0000:00:06.0/virtio2/block/vda — PCI 슬롯 6의 virtio 장치에 virtio_blk 드라이버가 붙었다. 실제 보드라면 /sys/devices/platform/soc/30b40000.mmc/... 같은 Device Tree 노드 이름이 보인다 (D 모듈).
  • /dev/rtc0은 platform 버스의 rtc-efi 드라이버가 만든 것이다. 센서 키트의 I2C RTC라면 여기에 rtc-ds1307 같은 이름이 나온다.
  • /dev/ttyS0의 드라이버가 port로 나오는 건 최근 커널의 serial core가 "serial8250 컨트롤러 → 포트" 사이에 serial-base 버스 장치를 하나 더 두기 때문이다. 트리를 한 단계 더 올라가면 serial8250 드라이버가 보인다.
  • uevent 파일은 udev가 받는 이벤트 내용과 같다 (MAJOR, MINOR, DEVNAME). udev는 이것을 보고 /dev 노드의 권한과 심볼릭 링크를 정한다.

드라이버를 쓰면 유저 테스트 코드는 언제나 같은 모양이다. 예를 들어 GNSS UART(/dev/ttyS1)든, 내 IMU char 드라이버든, open → (ioctl로 설정) → read 루프 → close. 그래서 A3의 파일 I/O 코드가 모든 드라이버 검증의 기본 틀이 된다. 반대로 드라이버를 설계할 때도 "유저가 cat으로 읽을 수 있게"(sysfs), "read()가 블로킹되게"(wait queue) 같은 파일 의미론을 지켜야 한다.

카메라 30 fps × 4채널을 처리하는 앱이 프레임마다 open/ioctl/read/close를 반복하면 §5의 비용이 프레임당 수 µs씩 쌓이고, 무엇보다 read()의 메모리 복사가 크다. V4L2는 그래서 mmap된 버퍼 큐 + VIDIOC_QBUF/DQBUF + poll 구조를 쓴다 (A4, A5, I). strace -c -f -p <pid>로 10초 붙여서 syscall 분포를 보는 것이 최적화의 첫 단계다.

Q. "What is the difference between user space and kernel space?"

A. 같은 CPU에서 도는 코드가 특권 레벨과 메모리 권한으로 나뉜 것이다. ARM에선 유저가 EL0, 커널이 EL1이고, MMU 페이지 테이블의 권한 비트로 커널 메모리는 EL0에서 접근이 막힌다. 그래서 유저 프로세스는 다른 프로세스나 커널을 깨뜨릴 수 없고, 하드웨어가 필요하면 syscall로 커널에 부탁한다. 커널 안에는 그런 보호가 없어서 드라이버 버그는 시스템 전체 문제가 된다.

User space and kernel space are separated by CPU privilege and the MMU. On ARM, applications run at EL0 and the kernel at EL1; kernel mappings are marked privileged-only in the page tables, so a user process can't touch kernel memory or hardware registers directly — it has to ask the kernel through a system call. That isolation means a buggy app just gets a SIGSEGV, whereas a bug in kernel code, including drivers, can take down the whole system.

Q. "Walk me through what happens when a program calls open() on a device file."

A. libc가 openat 번호를 x8에 넣고 svc #0을 실행하면 EL1 예외 벡터로 들어가 syscall 테이블에서 sys_openat을 부른다. VFS가 경로를 탐색해 inode를 찾고, 장치 파일이면 inode에 든 major:minor로 등록된 cdev를 찾아 struct file의 f_op를 드라이버의 file_operations로 바꾸고 드라이버의 .open을 호출한다. 마지막으로 fd 테이블의 빈 번호에 struct file을 넣고 그 번호를 돌려준다. 이후 read/write는 fd → struct file → f_op->read로 바로 드라이버에 간다.

The libc wrapper puts the openat syscall number in x8 and executes svc #0, which traps to EL1 and dispatches through the syscall table to do_sys_openat2. The VFS walks the path to the inode; for a character device the inode holds a dev_t, so chrdev_open looks up the registered cdev by major/minor, swaps the file's f_op to the driver's file_operations and calls the driver's open, which usually stashes its device struct in file->private_data. The kernel then installs the struct file in the lowest free slot of the fd table and returns that number. Later reads and writes go fd → struct file → f_op->read/write straight into the driver.

꼬리 질문: "Where would a driver store per-open state?" → file->private_data.

Q. "What does 'everything is a file' mean in Linux? Is it actually true?"

A. 일반 파일뿐 아니라 장치, 파이프, 소켓, 커널 정보(/proc, /sys)까지 fd 하나와 open/read/write/close라는 공통 인터페이스로 다룬다는 뜻이다. VFS가 file_operations 함수 포인터 테이블로 이것을 구현한다. 완전히 참은 아니다 — 네트워크 인터페이스는 /dev 노드가 없고 소켓·netlink로 다루며, 많은 장치 제어는 결국 ioctl이라는 비정형 탈출구를 쓴다.

It means most kernel objects — regular files, device nodes, pipes, sockets, and kernel state under /proc and /sys — are accessed through a file descriptor with the same open/read/write/close/ioctl/poll interface. The VFS implements that with a per-object file_operations table, so the same read() can land in ext4, the pipe code, the socket layer or a driver. It's not literally everything: network interfaces have no device node and are managed through sockets and netlink, and a lot of device control escapes into ioctl.

Q. "What are major and minor numbers?"

A. 장치 파일 inode에 들어 있는 장치 주소다. major는 어느 드라이버인지, minor는 그 드라이버 안에서 몇 번째 장치인지를 뜻한다. 예를 들어 /dev/null과 /dev/zero는 같은 major 1(mem 드라이버)에 minor 3과 5다. 요즘 드라이버는 alloc_chrdev_region으로 major를 동적으로 받고, 노드는 devtmpfs와 udev가 자동으로 만든다.

They're the device address stored in a device node's inode: the major selects the driver, the minor is interpreted by that driver to pick an instance. /dev/null and /dev/zero, for example, are both major 1 — the mem driver — with minors 3 and 5. Modern drivers get a dynamic major with alloc_chrdev_region, and the node itself is created automatically by devtmpfs and adjusted by udev, so you shouldn't hard-code majors.

Q. "What's the difference between /proc, /sys and /dev?"

A. /dev는 I/O를 하는 장치 노드(입구), /sys는 커널 디바이스 모델(bus·device·driver·class)을 그대로 보여 주는 트리로 파일 하나에 값 하나 규칙을 따르고, /proc은 원래 프로세스 정보용이며 /proc/interrupts, /proc/meminfo 같은 오래된 시스템 정보와 sysctl이 남아 있다. 새 드라이버가 설정값을 노출할 때는 sysfs, 디버그 덤프는 debugfs를 쓴다.

/dev holds device nodes — the entry points you open to do I/O. /sys is the kernel's device model exported as a tree of buses, devices, drivers and classes, with the rule of one value per attribute file, and it's what udev and bring-up debugging rely on. /proc started as per-process information and still carries legacy system files like /proc/interrupts and /proc/meminfo plus the sysctl tree. For a new driver, tunables go to sysfs and free-form debug output goes to debugfs, not /proc.

Q. "How expensive is a system call, and how do you avoid the cost?"

A. 커널이 하는 일이 거의 없는 getpid도 함수 호출보다 두 자릿수 이상 비싸다 — 내가 arm64 VM에서 재 보니 함수 호출 1 ns, getpid 약 125 ns, open+close 약 670 ns였다. 비용은 예외 진입·레지스터 저장·완화 코드·복귀 검사에서 온다. 줄이는 방법은 크게 읽고 쓰기(배치), mmap 공유 버퍼, epoll로 대기 묶기, 그리고 vDSO처럼 아예 커널에 안 들어가는 경로(clock_gettime은 약 19 ns)다.

Even a trivial syscall like getpid is two orders of magnitude more than a function call — on an arm64 VM I measured about 1 ns for a call, roughly 125 ns for getpid and about 670 ns for open plus close. The cost is the exception entry, saving and restoring registers, speculation mitigations and the return-path checks. You amortize it by batching I/O, sharing buffers with mmap, waiting on many sources with epoll, and using the vDSO, which handles clock_gettime entirely in user space in about 19 ns.

Q. "Linux is a monolithic kernel — what does that mean, and how do modules fit in?"

A. 스케줄러·메모리·파일시스템·네트워크·드라이버가 모두 커널 주소 공간에서 같은 특권으로 돌고, 서로 함수 호출로 통신한다는 뜻이다. 빠르지만 드라이버 버그가 커널 전체를 죽인다. 모듈은 런타임에 .ko를 커널에 링크하는 장치일 뿐 격리가 아니다 — 들어가면 빌트인과 같은 권한이다. QNX 같은 마이크로커널은 드라이버를 유저 프로세스로 돌려 격리하지만 IPC 비용을 낸다.

Monolithic means the scheduler, memory management, filesystems, networking and drivers all run in one kernel address space at the same privilege and call each other directly. That's fast but a single driver bug can crash everything. Loadable modules don't change that — a .ko is just linked into the running kernel and has full privilege once loaded; it gives flexibility, not isolation. A microkernel like QNX runs drivers as user processes for fault isolation, at the cost of message-passing overhead.

Q. "How would you find out which driver is behind /dev/ttyS0?"

A. stat으로 major:minor를 얻고 /sys/dev/char/<major>:<minor>를 따라가면 /sys/devices/...의 실제 디바이스가 나온다. 그 디렉터리의 device/driver 링크가 바인딩된 드라이버다. /proc/devices로 major의 이름도 확인할 수 있다. 내 VM에서는 /dev/ttyS0(4:64)이 platform 버스의 serial8250 아래 포트로 나왔다.

Stat the node to get major:minor, then follow /sys/dev/char/<major>:<minor>, which links into the real device under /sys/devices. The device's driver symlink names the bound driver, and /proc/devices maps the major to a name. On my test VM /dev/ttyS0, 4:64, resolved to a port under the serial8250 platform device.

14. 직접 해보기#

  1. 개념: arm64에서 read(fd, buf, n) 한 번이 일어날 때 레지스터 x0, x1, x2, x8에는 각각 무엇이 들어가고, 반환 후 x0에는 무엇이 들어오나? 실패하면 어떻게 다른가? 정답/힌트: x0=fd, x1=buf, x2=n, x8=63. 반환 x0=읽은 바이트 수(0이면 EOF), 실패면 -errno이고 libc가 -1과 errno로 바꾼다.
  2. 코드: ex1을 고쳐서 getpid를 인라인 svc #0으로 부르는 raw_getpid()를 만들고 libc getpid()와 값이 같은지, ex6 방식으로 시간도 같은지 확인하라. 정답/힌트: x8 = __NR_getpid(172), 인자 없음, clobber에 "memory". 시간은 libc와 거의 같아야 한다 (래퍼 비용은 무시할 수준).
  3. strace 관찰: strace -f -e trace=%file,%desc sh -c 'echo hi > /tmp/A1/out.txt'를 실행하고, 셸 리다이렉션이 어떤 syscall들(openat, dup3, close)로 구현되는지 설명하라. 정답/힌트: 셸이 파일을 openat(O_WRONLY|O_CREAT|O_TRUNC)으로 열고 dup3(또는 dup2)로 fd 1에 복제한 뒤 원래 fd를 닫는다. "fd 1이 무엇을 가리키나"만 바꾸는 것이다 (A3).
  4. /proc 관찰: 터미널 하나에서 sleep 1000 &를 실행하고 그 PID의 /proc/<pid>/syscall, /proc/<pid>/wchan, /proc/<pid>/status의 State를 읽어라. 무엇에서 잠들어 있나? 정답/힌트: 다른 프로세스의 syscall 파일은 ptrace 권한이 필요해서 일반 유저로는 Operation not permitted가 나고 sudo로 읽어야 한다. 이 VM에서는 첫 숫자 115(clock_nanosleep), State: S (sleeping), wchan = hrtimer_nanosleep이 나왔다.
  5. sysfs 탐색 코드: /sys/class/net/*/statistics/rx_bytes를 1초 간격으로 두 번 읽어 인터페이스별 수신 속도(B/s)를 출력하는 C 프로그램을 짜라. 파일은 매번 다시 열거나 lseek하라. 정답/힌트: opendir("/sys/class/net")로 이름을 얻고, 각 경로를 fopen→fscanf("%llu")→fclose. 같은 fd로 두 번째 read를 하면 EOF가 나는 것도 일부러 확인해 보라.
  6. ftrace 관찰: §10.3의 첫 실험에서 chrdev_open 대신 write_null을 필터로 걸고 func_stack_trace를 켜서, write()가 write_null까지 가는 스택을 직접 얻어라. 정답/힌트: el0t_64_sync … __arm64_sys_write → ksys_write → vfs_write → write_null 순서가 보여야 한다. 끝나면 set_ftrace_filter, set_ftrace_pid를 비우고 current_tracer를 nop으로 되돌린다.
  7. 개념: /dev/ttyUSB0이 꽂을 때마다 ttyUSB1로 바뀌어 GNSS 데몬이 실패한다. 이 노트의 어떤 메커니즘으로 고치나? 정답/힌트: 장치 등록 → uevent → udev 규칙. udevadm info -a /dev/ttyUSB0으로 serial·idVendor 같은 속성을 찾고, SYMLINK+="gnss0" 규칙을 만들어 데몬은 /dev/gnss0을 연다 (G9, L).

16. 요약 & 체크리스트#

Linux는 같은 CPU 위에서 커널(EL1)과 유저 프로세스(EL0)를 특권 레벨과 MMU로 갈라 놓고, 유저는 svc #0 syscall이라는 좁은 문으로만 커널에 일을 부탁한다. syscall은 x8에 번호, x0~x5에 인자, x0에 결과(실패면 -errno)를 싣는 예외이고, 함수 호출보다 두 자릿수 비싸다(VM 실측: 1 ns vs 125 ns). 커널이 제공하는 대부분의 자원은 VFS를 통해 "fd로 다루는 파일"로 통일되며, struct file의 f_op 테이블이 같은 read()를 ext4, 파이프, 소켓, 드라이버로 갈라 보낸다. 장치 파일은 major:minor 주소만 가진 inode이고, open 때 chrdev_open이 그 번호로 드라이버의 file_operations를 찾아 끼운다. /dev는 I/O 입구, /sys는 디바이스 모델 트리, /proc은 프로세스·커널 상태 계기판이고, 장치 등록 → sysfs + devtmpfs 노드 + uevent → udev가 하나의 흐름이다. Linux는 monolithic이라 모듈도 커널 안에서 같은 권한으로 돈다.
