Don 기준 난이도: scope·로직 분석기로 "측정해서 좁히는" 사고방식은 이미 강점 / 그 측정 도구가 Linux에서는 /proc·/sys·dmesg·strace라는 점, 그리고 셸 문법의 함정은 새로 익힌다 선행 노트: A1(everything is a file), A2(프로세스), A3(파일 I/O·ioctl) — 없어도 읽을 수 있다

0. 큰 그림 — 보드 앞에서 던지는 여섯 가지 질문#

bare-metal에서 Don이 보드를 디버그할 때는 JTAG으로 레지스터를 읽고, UART 로그를 보고, scope로 핀을 찍었다. Embedded Linux 보드에서도 하는 일은 같다. 다만 커널이 이미 그 정보를 파일로 내놓고 있어서, 대부분의 "측정"은 셸에서 파일을 읽는 것으로 끝난다. /proc/interrupts는 IRQ 카운터 레지스터 덤프, /sys/bus/i2c/devices/는 버스 스캔 결과, dmesg는 UART 로그 버퍼라고 생각하면 된다.

이 노트는 명령을 알파벳 순으로 외우지 않는다. 대신 보드 앞에서 실제로 던지는 질문 여섯 개를 기준으로 묶는다.

그림 1 — 보드 triage 흐름. 증상이 아니라 "지금 묻는 질문"으로 도구를 고른다. 이 노트의 §4~§10이 각 상자에 대응한다.

실습 환경: Mac 위 Lima VM elinux (aarch64, Ubuntu 26.04.1, uname -r = 7.0.0-34-generic, bash 5.3.9). 이 VM에는 실제 I2C·GPIO·CAN 하드웨어가 없다. 그래서 커널에 들어 있는 가짜 하드웨어 드라이버를 써서 진짜 명령을 진짜로 돌린다.

실제 보드의 것이 노트에서 대신 쓴 것커널 모듈
SoC의 I2C 컨트롤러 + IMU·기압 센서SMBus 가상 어댑터, 0x68·0x76에 가상 칩i2c-stub
SoC GPIO 컨트롤러configfs로 만드는 가상 GPIO 칩gpio-sim
CAN 컨트롤러 (FlexCAN, MCP2518FD 등)bit timing까지 받는 가상 CAN / 루프백 CANdummy_can, vcan
보드 UART 콘솔socat으로 만든 pty 한 쌍없음 (유저 공간)

i2c-stub 위에 커널의 진짜 bmp280·mpu6050 드라이버를 붙여서 probe 성공·실패까지 재현한다. 같은 VM에서 다른 노트의 실습 프로그램(udp_rx, ex5, vcan0 등)이 동시에 돌고 있어서 출력에 그런 이름이 섞여 있다. 출력은 모두 실제 실행 결과이고, 길면 줄을 잘랐다고 적었다. PID·시각·카운터 값은 실행마다 다르다.

1. 셸 기본기 — 파이프, 리다이렉션, exit code#

1.1 세 개의 fd: stdin(0), stdout(1), stderr(2)#

모든 프로세스는 태어날 때 fd 0·1·2를 물려받는다 (A1·A3에서 본 fd 테이블의 0~2번 칸). >는 fd 1을, 2>는 fd 2를 파일로 바꿔 끼운다. 2>&1은 "fd 2를 지금 fd 1이 가리키는 곳으로 복사하라"(내부적으로 dup2(1, 2))는 뜻이다. 그래서 순서가 중요하다 — 셸은 리다이렉션을 왼쪽부터 차례로 적용한다.

무엇을 확인하나: > file 2>&1과 2>&1 > file이 다르게 동작하는 것.

출력에서 볼 것: 첫 줄은 에러까지 파일에 들어갔다(cat으로 둘 다 나옴). 두 번째는 2>&1이 먼저 적용될 때 fd 1이 아직 터미널이라 에러는 화면으로, 정상 출력만 파일로 갔다. 빌드 로그를 통째로 남길 때는 항상 make > build.log 2>&1 순서다. bash 전용 축약형 &> build.log도 같은 뜻이다.

1.2 exit code — 명령의 "리턴값"#

C의 main() 리턴값(0~255)이 셸의 $?다. 0이 성공, 0이 아니면 실패다(C 함수 관례 0 = OK와 같다). grep -q처럼 출력 없이 exit code만으로 답하는 명령이 스크립트의 조건문 재료다.

출력에서 볼 것: 파이프라인의 exit code는 기본적으로 마지막 명령(wc)의 것이라 cat 실패가 묻힌다(rc=0). PIPESTATUS 배열에는 각 단계의 값(1 0)이 남는다. pipefail을 켜면 실패한 단계가 하나라도 있으면 파이프라인 전체가 실패(rc=1)가 된다.

Don이 펌웨어에서 ASSERT()를 켜 두고 개발하듯, 셸 스크립트에는 strict mode를 켠다.

1.4 따옴표 — 단어 분리와 확장#

셸은 따옴표 없는 $var를 공백에서 쪼개고(word splitting), glob 문자가 있으면 파일 이름으로 펼친다. 큰따옴표 "..." 안에서는 변수·$(...)만 확장되고 쪼개지지 않는다. 작은따옴표 '...' 안에서는 아무것도 확장되지 않는다.

출력에서 볼 것: 따옴표 없는 $f는 imu와 log.txt 두 인자로 쪼개졌다. 규칙은 하나다 — 변수는 항상 "$var"로 쓴다. limactl shell ... bash -lc '...'나 ssh board '...'처럼 명령을 문자열로 넘길 때는 "어느 셸이 어느 따옴표를 벗기는가"를 한 번 더 생각해야 한다(바깥 셸이 먼저 한 겹 벗긴다).

1.5 반복문 — /sys를 훑는 기본 패턴#

/sys/class/<클래스>/ 아래 장치마다 같은 속성 파일이 있으므로, for 한 줄이면 "장치 목록 + 상태" 표가 나온다.

출력에서 볼 것: while read -r a b는 한 줄을 공백 기준으로 나눠 변수에 넣는다(_는 나머지를 버리는 관례). < <(cmd)는 process substitution으로, cmd를 파이프로 while에 넘기는 형태와 달리 루프가 서브셸이 아니어서 루프 안에서 바꾼 변수가 루프 밖에서도 살아 있다.

1.6 here-doc — 설정 파일·udev 규칙을 스크립트 안에서 만들기#

<<EOF ... EOF는 여러 줄 문자열을 stdin으로 넣는다. EOF에 따옴표를 붙이면(<<'EOF') 안의 $가 확장되지 않는다 — udev 규칙이나 다른 스크립트를 생성할 때 필수다.

1.7 sudo echo > /sys/...가 안 되는 이유와 tee#

sudo echo X > file에서 >는 sudo가 실행되기 전에 지금의(일반 사용자) 셸이 연다. 그래서 root만 쓸 수 있는 sysfs 파일은 Permission denied가 난다. 해결은 sudo tee(파일을 여는 프로세스 자체가 root) 또는 sudo sh -c "...".

출력에서 볼 것: tee는 받은 내용을 stdout에도 다시 찍는다(pull-down). 출력이 싫으면 > /dev/null을 붙인다. tee -a는 이어 쓰기라서 "화면에도 보고 로그에도 남기기"에 쓴다.

2. 텍스트 도구 — find, grep, xargs, sed, awk, cut·sort·uniq#

Linux는 상태를 텍스트로 내놓는다. 그래서 텍스트를 거르고 세는 작은 도구를 파이프로 잇는 것이 곧 "로직 분석기의 트리거·필터·카운터"다.

그림 2 — sudo dmesg에서 head까지 이어지는 7단 파이프라인의 데이터 흐름. 각 단계는 별개 프로세스이고, stdout만 다음 단계로 흐른다. stderr는 2>&1을 붙이지 않는 한 파이프를 타지 않는다.

출력에서 볼 것: IKCONFIG가 출력에 없다 = 설정되지 않음. 그래서 /proc/config.gz도 없다. 데스크톱 배포판은 /boot/config-*를 주지만, 임베디드 보드는 보통 /proc/config.gz(CONFIG_IKCONFIG_PROC)에 의존하므로 BSP 빌드 때 켜 두는 게 좋다. grep -r "" 파일들은 "파일 이름:내용"을 한 번에 찍는 sysfs 덤프 요령이다. 에러 grep의 -110은 -ETIMEDOUT, -19는 -ENODEV다(이 줄들은 §5·§6 실험이 남긴 것이고, a6sleep은 다른 노트의 실습 모듈이다). 드라이버 로그에는 숫자 errno가 그대로 찍히므로 자주 보는 값(-5 EIO, -6 ENXIO, -16 EBUSY, -22 EINVAL, -110 ETIMEDOUT, -517 EPROBE_DEFER)은 외워 둔다.

2.3 xargs — 표준입력을 인자로 바꾸기#

파이프는 데이터를 stdin으로 넘기는데, modinfo·grep FILE처럼 인자를 받는 명령이 많다. xargs가 그 다리다. 파일 이름에 공백이 있을 수 있으면 find -print0과 xargs -0을 짝지어 쓴다.

출력에서 볼 것: -n1은 인자 하나씩 명령을 여러 번 실행, -I{}는 자리표시자 치환이다.

2.5 awk — 열(column) 단위 계산기#

awk는 줄을 공백으로 쪼개 $1, $2, …, 마지막 열 $NF로 준다. 조건 { 동작 } 형태이고, BEGIN/END 블록이 있다. /proc 파일들은 열 정렬 텍스트라 awk와 궁합이 가장 좋다.

무엇을 확인하나: /proc/interrupts에서 CPU 열을 합산해 "가장 많이 뛴 IRQ"를 뽑고, /proc/meminfo에서 비율을 계산하는 것.

출력에서 볼 것: i=2..5는 이 VM의 CPU가 4개라서다(보드마다 CPU 수가 다르니 숫자 열만 세는 편이 안전하다 — §9의 irqrate.sh가 그렇게 한다). IPI1(rescheduling)·arch_timer가 상위인 것은 정상이다. 실제 보드라면 여기서 "내 센서 IRQ 번호가 목록에 있는가, 카운트가 오르는가"를 본다.

2.6 cut·sort·uniq — 세기#

sort, uniq -c, sort -rn을 차례로 파이프로 잇는 것은 "무엇이 몇 번?"을 뽑는 관용구다. uniq는 인접한 같은 줄만 합치므로 반드시 앞에 sort가 있어야 한다.

출력에서 볼 것: 프로세스 상태 첫 글자 통계(I idle 커널 스레드, S sleep, R running, Z zombie 1개). 두 번째는 그림 2의 파이프라인 그대로이고 "부팅 로그에서 누가 제일 시끄러운가"다. 보드에서 같은 줄 반복으로 로그가 넘치는(예: I2C NACK 폭주) 드라이버를 찾을 때 그대로 쓴다.

2.7 watch, less — 대화형 도구#

4. 질문 ① "어떤 하드웨어·드라이버가 여기 있나?"#

4.1 lspci / lsusb / lsblk — 열거 가능한 버스#

PCIe·USB는 스스로 ID를 알려 주는 열거(enumerable) 버스라서 스캔하면 다 나온다. -k는 "어떤 커널 드라이버가 붙었나"를 함께 보여 준다. 없으면 sudo apt install pciutils usbutils로 설치한다(보드에서는 Yocto/Buildroot 이미지에 넣는다).

출력에서 볼 것 (...은 줄 생략): Kernel driver in use가 없으면 "장치는 보이는데 드라이버가 안 붙었다"는 뜻이다. lsusb -t의 Driver=와 링크 속도(12M, 480M)는 USB 카메라가 USB2로 잘못 붙었는지 볼 때 쓴다. Don의 SSD 경험으로 보면 lspci -vv의 LnkSta(링크 폭·속도)가 NVMe 링크 트레이닝 문제를 볼 때 첫 단서다.

4.2 /proc/iomem, /proc/ioports — 물리 주소 맵#

/proc/iomem은 "어떤 물리 주소 구간을 누가 request_mem_region()으로 잡았나"의 표다. Don에게 익숙한 SoC 메모리 맵 그 자체다. root로 읽어야 주소가 보인다 (일반 사용자는 0으로 가려진다).

출력에서 볼 것: GIC(인터럽트 컨트롤러) 분배기·재분배기, ARMH0061(ARM PL061 GPIO 컨트롤러) MMIO 블록이 0x20060000에 있다. 이 주소는 §7.3에서 devmem으로 직접 읽어 본다. ARM에는 x86식 I/O 포트가 없어서 /proc/ioports는 PCI 구간 하나뿐이다. 드라이버가 devm_ioremap_resource()에 실패해 -EBUSY가 나면 여기서 "누가 먼저 잡았나"를 본다.

4.3 /sys/bus, /sys/class — 장치 모델 트리#

/sys/bus/<버스>/devices/에는 그 버스에 등록된 장치, /sys/bus/<버스>/drivers/에는 등록된 드라이버가 있다. 장치 디렉터리 안의 driver 심볼릭 링크가 "누가 이 장치를 잡았나"다. /sys/class/<기능>/은 같은 장치를 "무슨 기능인가"(net, gpio, input, hwmon…)로 다시 묶은 뷰다.

출력에서 볼 것: eth0 링크를 따라가면 PCI 장치 00:01.0 → virtio0 → net/eth0라는 부모 체인이 그대로 경로에 드러난다. 이 체인이 G 모듈(장치 모델)의 struct device 부모 관계다.

4.4 udevadm info — 장치 속성과 부모 체인 한 번에#

udevadm info는 sysfs 경로 하나에 대해 udev가 아는 속성(E: 환경 변수)을 보여 주고, -a는 부모 장치를 타고 올라가며 모든 sysfs 속성을 udev 규칙 문법(ATTRS{...}==)으로 찍는다. udev 규칙(예: "IMU를 /dev/imu0로 고정 이름 붙이기")을 쓸 때 이 출력을 복사해서 쓴다.

출력에서 볼 것 (...은 줄 생략): 자기 자신은 KERNEL/ATTR, 부모는 KERNELS/ATTRS(복수형)로 매칭한다. 규칙 하나에서는 자신 + 부모 하나의 속성만 섞어 쓸 수 있다는 것이 -a 출력 머리말에도 적혀 있다. 부모의 new_device/delete_device는 §5.3에서 쓴다.

5. 질문 ② "내 드라이버가 load 됐나? probe 됐나?"#

"load"와 "probe"는 다른 사건이다. Don의 펌웨어 비유로 말하면 load = 드라이버 코드가 메모리에 올라옴(모듈 링크), probe = 그 드라이버가 특정 장치 인스턴스를 맡아 초기화 성공(장치별 init() 호출이 OK를 리턴)이다. 모듈이 load 됐는데 probe가 안 되는 경우가 실무에서 가장 흔하다.

5.1 lsmod, modinfo — 무엇이 올라와 있고, 무엇을 받는가#

출력에서 볼 것: Used by 숫자는 참조 카운트다(0이 아니면 rmmod가 거부된다 — §8.4). vermagic이 실행 중인 커널과 다르면 모듈이 로드되지 않는다(out-of-tree 드라이버를 다른 커널 헤더로 빌드했을 때의 단골 에러). alias: rtnl-link-vcan은 ip link add ... type vcan이 이 모듈을 자동 로드하게 해 주는 별명이고, parm:은 modprobe 모듈 이름=값으로 넘길 수 있는 파라미터다.

5.2 modprobe, rmmod — 의존성까지 함께#

insmod는 파일 하나를 그대로 넣고, modprobe는 modules.dep을 보고 의존 모듈(can-dev)까지 순서대로 넣는다. 실무에서는 거의 항상 modprobe다.

출력에서 볼 것: can_dev의 Used by에 vcan이 찍혔다 — 의존성이 함께 올라온 것. -n -v(dry run)는 "실제로 무엇을 insmod할지"만 보여 준다. 보드에서 모듈이 자동 로드되지 않을 때 이 alias 테이블(modules.alias)에 장치의 modalias가 있는지가 첫 확인 포인트다.

5.3 진짜 드라이버 probe 시켜 보기 — i2c-stub + bmp280#

i2c 장치는 열거가 안 되는 버스라서, 보통은 Device Tree가 "이 버스의 0x76에 bmp280이 있다"고 알려 준다(D 모듈). DT 없이 시험할 때는 sysfs의 new_device에 이름 주소를 써서 장치를 즉석에서 만든다. 먼저 가상 I2C 버스에 0x68, 0x76 두 칩을 만들고(§7.1에서 자세히), 0x76의 chip ID 레지스터(0xD0)에 BMP280의 ID 0x58을 미리 써 둔다.

출력에서 볼 것: 장치 0-0076(버스 0, 주소 0x76)이 생기자 커널이 modalias i2c:bmp280으로 모듈을 자동 로드했고, 드라이버가 chip ID를 읽어 0x58을 확인한 뒤 probe에 성공했다. 증거는 세 가지: dmesg의 드라이버 메시지, driver 심볼릭 링크, 그리고 서브시스템(IIO) 장치의 등장이다. supply ... not found, using dummy regulator는 DT에 전원 레귤레이터가 연결 안 됐다는 경고다 — 실제 보드에서 이 줄이 보이면 DT의 vdd-supply 누락을 의심한다. (virtio_net ... promiscuous 줄은 다른 실습의 tcpdump 때문이다.)

출력에서 볼 것: probe가 성공한 드라이버는 서브시스템(I 모듈의 IIO)에 장치를 등록하고, 유저는 in_temp_input을 cat하는 것만으로 센서를 읽는다. 값이 0인 것은 stub 칩의 보정 레지스터가 전부 0이기 때문이다.

5.4 probe 실패를 재현하고 읽기 — mpu6050#

이번에는 0x68에 MPU6050을 붙인다. 이 드라이버는 WHO_AM_I 레지스터(0x75)가 0x68이길 기대하는데, stub 칩의 0x75는 0x00이다. 동시에 udevadm monitor로 커널이 내보내는 uevent도 본다.

출력에서 볼 것: 장치는 생겼지만(add uevent, 0-0068 디렉터리) 드라이버는 붙지 않았다(driver 링크 없음). 드라이버가 남긴 마지막 말이 invalid whoami 0x00 expected 0x68이다. 실제 보드에서 같은 줄이 나오면 원인은 배선·주소(AD0 핀)·전원 시퀀스·다른 칩 변종 중 하나다. 그리고 driver core 자체는 "probe failed"라고 말해 주지 않았다 — probe가 -ENODEV/-ENXIO를 리턴하면 "이 장치는 내 것이 아니다"로 해석해 조용히 넘어가기 때문이다. 그래서 다음 도구가 필요하다.

5.5 bind / unbind — 다시 probe 시키기#

/sys/bus/<버스>/drivers/<드라이버>/bind에 장치 이름을 쓰면 그 드라이버로 probe를 다시 시도하고, unbind는 remove()를 부른다. 재부팅 없이 "고치고 다시 probe"를 반복하는 루프다 (Don의 펌웨어 개발에서 "리셋 없이 init 재실행"에 해당).

출력에서 볼 것: 이번에는 probe가 성공해 driver 링크가 생겼고, MPU6050의 보조 I2C 버스(자력계용)가 i2c-1로 추가됐다. unbind 후 링크가 사라졌다.

5.6 dynamic debug — driver core의 속마음 보기#

pr_debug()/dev_dbg()는 평소 꺼져 있다가 CONFIG_DYNAMIC_DEBUG=y이면 런타임에 켤 수 있다. driver core의 drivers/base/dd.c를 켜면 "probe를 시도했나, 무엇을 리턴했나"가 보인다. WHO_AM_I를 다시 0으로 되돌리고 bind해 본다.

출력에서 볼 것: really_probe: probing driver ...(probe 진입)와 rejects match -19(probe가 -ENODEV 리턴)가 디버그 출력으로 드러났다. bind 쓰기 자체도 errno 19로 실패했다 — 쓰기의 리턴값이 probe 결과를 그대로 돌려준다. ((os error 19) 형식은 Ubuntu 26.04의 tee가 uutils(Rust) 구현이라서 나오는 문구다.) 모듈 전체를 켜려면 module 모듈이름 +p, 부팅 초기에는 커널 커맨드라인 dyndbg="file drivers/base/dd.c +p"를 쓴다.

5.7 deferred probe — -EPROBE_DEFER로 미뤄진 장치#

드라이버가 필요한 자원(클럭, 레귤레이터, GPIO, 다른 장치)이 아직 준비 안 됐으면 probe는 -EPROBE_DEFER(-517)를 리턴하고 나중에 다시 시도된다. 부팅이 끝났는데도 남아 있는 목록이 debugfs의 devices_deferred다.

출력에서 볼 것: 이 VM에서는 비어 있다(미뤄진 장치 없음). 실제 보드 bring-up에서는 여기 장치 이름과 이유(예: 기다리는 공급자)가 남아 있는 경우가 많고, 이것이 "왜 내 카메라가 안 뜨지?"의 단골 답이다(G 모듈). debugfs가 마운트 안 된 보드라면 sudo mount -t debugfs none /sys/kernel/debug.

5.8 udevadm monitor — 핫플러그 이벤트 실시간 보기#

udevadm monitor는 커널의 uevent(KERNEL)와 udev가 규칙 처리 후 내보내는 이벤트(UDEV)를 둘 다 보여 준다. USB 장치 꽂기, 모듈 로드, 네트워크 인터페이스 생성 등이 다 보인다.

출력에서 볼 것: 커널 이벤트 후 약 17 ms 뒤 udev 처리 완료 이벤트가 나왔다. KERNEL은 있는데 UDEV가 없거나 늦으면 udev 규칙이 문제다. --property를 붙이면 각 이벤트의 MODALIAS 등 환경 변수까지 찍힌다.

6. 질문 ⑤ "커널이 뭐라고 했나?" — dmesg와 journalctl#

6.1 로그가 흐르는 길#

드라이버의 dev_err()나 pr_info()는 모두 printk()로 모이고, printk는 메시지를 커널 안의 링버퍼에 넣는다. Don의 펌웨어에서 RAM에 두던 원형 로그 버퍼와 똑같은 구조다. 이 링버퍼를 읽는 소비자가 여럿이다.

그림 4 — printk에서 도구까지의 로그 경로. 링버퍼는 크기가 고정이라 오래된 메시지는 덮어쓰인다. 재부팅 후에도 남는 것은 journald가 디스크에 저장했을 때(persistent journal)와 rsyslog 파일뿐이다.

6.3 printk 레벨과 콘솔#

출력에서 볼 것: 네 값은 순서대로 console_loglevel, 기본 메시지 레벨, 최소 콘솔 레벨, 부팅 시 기본 콘솔 레벨이다. 첫 값 4는 "레벨 숫자가 4보다 작은(0 emerg ~ 3 err) 메시지만 콘솔(UART)에 찍는다"는 뜻이다. 그래서 dev_info()는 dmesg에는 있어도 시리얼 콘솔에는 안 보인다. bring-up 중 콘솔에 다 보고 싶으면 echo 8 | sudo tee /proc/sys/kernel/printk 또는 커널 커맨드라인 loglevel=8. 반대로 UART 출력은 느려서(115200bps에서 한 줄 수 ms) 콘솔 로그가 많으면 타이밍이 바뀐다 — 펌웨어에서 printf 디버깅이 타이밍 버그를 숨기던 것과 같은 함정이다.

6.4 journalctl — 저장된 로그를 질의하기#

systemd 시스템에서는 journald가 /dev/kmsg와 서비스 출력을 모두 받아 색인된 저장소에 둔다. journalctl은 그 질의 도구다.

7.1 i2c-tools — i2cdetect, i2cget, i2cset, i2cdump#

i2c-tools는 /dev/i2c-N(i2c-dev 드라이버)을 열고 ioctl로 SMBus 트랜잭션을 날린다. 이 VM에는 I2C 컨트롤러가 없어서 i2c-stub로 가상 어댑터를 만든다.

출력에서 볼 것: 응답한 주소(0x68)는 숫자로, 응답 없는 주소는 --로 표시된다. -y는 "정말 할 거냐" 확인을 건너뛴다.

출력에서 볼 것: ioctl 번호 0x0705 = I2C_FUNCS, 0x0703 = I2C_SLAVE(대상 주소 설정), 0x0720 = I2C_SMBUS(실제 전송)다. 응답 없는 주소에서 stub 어댑터는 ENODEV를 돌려줬다. 실제 하드웨어 컨트롤러는 주소 NACK를 보통 ENXIO로 돌려준다(커널 문서 i2c/fault-codes). 0x76에 I2C_SLAVE를 하면 EBUSY가 나는데, 드라이버가 잡은 주소라서이고 i2cdetect는 그걸 UU로 표시한다.

위험 — 실제 보드에서 반드시 기억할 것

  • i2cdetect는 "읽기만" 하는 도구가 아니다. 기본 모드는 대부분의 주소에 SMBus quick write를, 0x30~0x37·0x50~0x5F에는 read byte를 보낸다. man 페이지 경고대로 quick write에 반응해 상태가 바뀌는 칩(일부 EEPROM 쓰기 보호 해제 등)이 있고, 어떤 칩은 예상 밖의 트랜잭션에 버스를 잡고(SDA low) 멈춘다. 모르는 버스는 -r(read만)로 범위를 좁혀서 스캔한다.
  • i2cset은 드라이버 몰래 레지스터를 바꾼다. PMIC 버스(전압 레귤레이터)에 잘못 쓰면 코어 전압이 바뀌어 보드가 즉시 죽거나 손상될 수 있다.
  • i2cdump/i2cget도 부작용이 있다: read-to-clear 상태 레지스터, 읽으면 하나씩 빠지는 FIFO 레지스터는 읽는 순간 드라이버가 볼 데이터를 빼앗는다.
  • 드라이버가 바인딩된 주소(UU)에 -f(force)로 접근하면 드라이버와 경쟁한다. 디버그가 끝나면 드라이버를 unbind하고 쓰는 편이 안전하다.

7.2 libgpiod — gpiodetect, gpioinfo, gpioget, gpioset#

gpio-sim으로 8핀짜리 가상 칩을 만들고 3번에 imu_int, 5번에 cam_reset이라는 이름을 붙였다 (configfs: /sys/kernel/config/gpio-sim/sensorkit/bank0/...에 num_lines, line3/name 등을 쓰고 live에 1).

7.3 devmem / devmem2 — 물리 주소 직접 읽기·쓰기#

/dev/mem을 mmap해서 물리 주소의 레지스터를 읽고 쓰는 도구다. JTAG 메모리 창을 셸에서 여는 것과 같다. busybox devmem ADDRESS [WIDTH [VALUE]]와 별도 패키지 devmem2 ADDRESS [b/h/w] [VALUE] 두 가지가 흔하다. §4.2의 /proc/iomem에서 본 PL061 GPIO 블록(0x20060000)의 PrimeCell ID 레지스터(오프셋 0xFE0~0xFEC)를 읽어 본다.

출력에서 볼 것: PeriphID0~3 = 0x61, 0x10, 0x04, 0x00 → 부품 번호 0x061(PL061), 설계사 코드 0x41(ARM). 레지스터 맵에 있는 ID를 읽어 "주소 맵이 맞다"를 확인하는 것은 bring-up의 첫 MMIO 확인 방법이다. 반면 System RAM(0x80000000)은 STRICT_DEVMEM 때문에 거부됐다. IO_STRICT_DEVMEM까지 켜진 커널에서는 드라이버가 잡은 MMIO 구간도 막힌다(이 VM은 꺼져 있어서 PL061 읽기가 됐다).

위험: 쓰기(devmem ADDR 32 VALUE)는 드라이버 몰래 하드웨어 상태를 바꾼다. 클럭이 꺼진(clock-gated) 블록이나 전원이 내려간 도메인을 읽으면 버스 에러로 커널이 즉시 멈출 수 있다(SError/외부 abort). 드라이버가 runtime PM으로 블록을 꺼 두었을 수 있으니, 읽기 전에 그 장치가 켜져 있는지(/sys/.../power/runtime_status) 본다.

9. 질문 ④ "왜 느린가?" — CPU, 메모리, I/O, 인터럽트#

"느리다"는 증상은 네 군데 중 하나다: CPU가 바쁘다, 메모리가 모자라 회수(reclaim)한다, I/O를 기다린다, 인터럽트·softirq가 CPU를 먹는다. 순서대로 좁힌다. 펌웨어에서 "CPU load 측정 → 큐 깊이 확인 → ISR 시간 측정"을 하던 것과 같은 순서다.

9.1 ps — 원하는 열만 골라 보기#

출력에서 볼 것: 같은 PID 아래 LWP(스레드 ID)가 여럿이다 — Linux에서 스레드는 PID를 공유하는 태스크다(A2). STAT의 l은 멀티스레드, WCHAN의 futex_do_wait는 뮤텍스·조건변수에서 잠든 것(A8)이다. 센서 데몬의 한 스레드만 CPU를 먹는다면 top -H -p PID나 pidstat -t -p PID로 스레드 단위로 본다.

9.2 top, htop, pidstat — 누가 CPU를 먹나#

top과 htop은 대화형이다. 스크립트·로그에는 배치 모드(top -b -n 1)를 쓴다. htop은 배치 모드가 없어서(대화형 화면이라 출력 생략) 보드에서 사람이 볼 때만 쓴다(F5 트리, F6 정렬, H 스레드 표시 토글, F2에서 CPU별 막대).

출력에서 볼 것: udp_rx, ex5는 같은 VM의 다른 실습 프로그램이다. top 헤더의 us(유저)/sy(커널)/wa(I/O 대기)/hi·si(하드·소프트 IRQ) 비율이 첫 단서다. yes > /dev/null이 97% system인 것이 흥미롭다 — 하는 일이 거의 write() syscall뿐이라 시간 대부분이 커널 안에 있다. 센서 데몬이 작은 read()를 초당 수만 번 부르면 같은 모양이 나온다(→ 버퍼를 키우거나 poll·mmap으로 바꾼다, A4·A5). pidstat의 %wait는 runqueue에서 CPU를 기다린 비율로, 실시간 스레드의 지연을 볼 때 중요하다.

9.3 free, vmstat — 메모리와 시스템 전체 흐름#

출력에서 볼 것: 메모리 여유는 free가 아니라 available을 본다(page cache는 필요하면 회수되므로). vmstat의 첫 줄은 부팅 후 평균이라 버리고 둘째 줄부터 읽는다. r = 실행 대기 태스크 수(CPU 수보다 계속 크면 CPU 부족), b = uninterruptible sleep(대개 I/O 대기) 수, in = 초당 인터럽트, cs = 초당 context switch.

디스크에 직접 쓰기(oflag=direct)를 걸고 다시 본다. /tmp는 tmpfs(RAM)라서 디스크 부하가 안 생기므로 /var/tmp에 쓴다.

출력에서 볼 것: iostat -x의 w_await(요청 하나가 끝나기까지 평균 ms)가 155 ms, aqu-sz(평균 큐 깊이)가 46~95다 — Don이 SSD 펌웨어에서 보던 바로 그 큐 깊이·지연이다. vmstat의 b가 1~2, wa가 41~50%로 올랐다. 즉 "CPU는 놀고 있는데 다들 디스크를 기다린다". 임베디드 보드에서 eMMC·SD 카드에 로그를 많이 쓰는 서비스가 있으면 정확히 이 모양이 나온다. (iostat은 sysstat 패키지.)

9.4 /proc/interrupts와 IRQ 비율 스크립트#

/proc/interrupts는 IRQ마다 CPU별 누적 카운트다. 두 번 읽어 차이를 내면 초당 인터럽트 수가 된다. 실제 보드에서 "센서 IRQ가 들어오나? 얼마나 자주? 어느 CPU로?"를 이걸로 본다. 첫 열이 IRQ 번호, 그 다음이 CPU별 카운트, 그 다음이 인터럽트 컨트롤러·hwirq·트리거 타입(Level/Edge)·이름이다.

출력에서 볼 것: 타이머(arch_timer, GIC PPI 27)는 CPU마다 고르게 뛰고, 네트워크 수신(virtio0-input.0, MSI-X)은 CPU0에만 몰려 있다. 실제 보드라면 GICv3 123 Level imu-int 같은 줄이 보이고, 그 카운트가 안 오르면 핀·DT의 interrupts 속성·트리거 타입부터 의심한다. 특정 IRQ가 어느 CPU로 가는지는 /proc/irq/N/smp_affinity_list로 바꾼다(N 모듈).

스크립트 1 — IRQ 비율 측정기 (~/.elinux_scratch/A10/irqrate.sh):

awk 루프는 2번째 열부터 숫자인 동안만 더하고 처음 숫자가 아닌 열(컨트롤러 이름)에서 멈춘다. 그래서 CPU 수와 무관하게 동작한다. 측정 중간(2.2초 뒤)에 게이트웨이로 ping flood 2만 개를 쏜다.

그림 5 — irqrate.sh로 잰 네트워크 수신 IRQ 비율. 평소 초당 1회 남짓이던 카운터가 ping flood 동안 초당 1만 5천 회로 뛰었다.

출력에서 볼 것: echo reply 20,000개에 IRQ가 20,001번 — 응답 하나에 IRQ 하나다. ping -f는 응답을 받아야 다음을 보내므로 수신 큐에 패킷이 하나씩만 쌓이고, NAPI(인터럽트 후 폴링으로 전환해 여러 패킷을 한 번에 처리하는 커널 메커니즘)가 묶을 것이 없었다. 반대로 앞 절 xargs 예제에서 eth0는 패킷 9만 개를 받았지만 이 IRQ 카운터는 1만 7천대였다 — 대량 다운로드에서는 NAPI가 IRQ 한 번에 여러 패킷을 처리한다. "IRQ 수 ≠ 이벤트 수"는 센서 드라이버에서도 같다(FIFO watermark 인터럽트 한 번에 샘플 여러 개).

10.1 ip — 링크, 주소, 라우팅#

ifconfig/route(net-tools)는 오래된 도구고, 지금은 ip(iproute2)가 표준이다. 둘 다 결국 커널에 netlink 소켓으로 묻는다.

출력에서 볼 것: 플래그의 UP은 "관리자가 켬", LOWER_UP은 "물리 링크(캐리어) 있음"이다. UP인데 LOWER_UP이 없으면 케이블·PHY 문제다(NO-CARRIER로 표시됨). -s의 errors/dropped/missed가 오르면 드라이버·DMA 링 문제를 의심한다. ip route get은 "이 목적지로 가는 패킷이 실제로 어느 인터페이스·소스 주소를 쓰는가"를 커널에 직접 묻는다 — LiDAR가 연결된 두 번째 NIC로 패킷이 안 갈 때 쓴다.

10.2 ss — 소켓과 포트#

출력에서 볼 것 (...은 줄 생략): -t TCP, -u UDP, -l listen, -p 프로세스, -n 숫자 그대로. "LiDAR 수신 데몬이 2368 포트를 정말 열었나, 어느 주소(0.0.0.0 vs 특정 NIC)에 bind 했나"를 이걸로 확인한다. UDP 수신 버퍼가 넘치는지는 Recv-Q가 계속 차 있는지로 본다. ss는 커널의 sock_diag netlink를 쓰는데, §5.1 lsmod에 있던 tcp_diag·udp_diag 모듈이 바로 그것이다.

10.3 ping, tcpdump — 패킷이 오가나#

tcpdump는 네트워크용 로직 분석기다. 가짜 LiDAR 패킷(UDP)을 루프백으로 보내고 캡처한다. -nn은 이름·포트 해석 안 함, -c N은 N개 후 종료, -X는 hex+ASCII 덤프, -w는 pcap 파일로 저장(나중에 Wireshark로 연다).

출력에서 볼 것: hex 덤프에서 IP 헤더(4500…), UDP 헤더(포트 0x3050 = 12368), 페이로드 LIDAR-PKT-1이 그대로 보인다. received by filter가 캡처 수보다 큰 것은 필터 단계에 도달한 패킷이 더 있었다는 뜻이다(받는 소켓이 없어 생긴 ICMP port unreachable 등 다른 패킷). dropped by kernel이 0이 아니면 캡처가 못 따라간 것이니 필터를 좁히거나 -w로 파일에 쓴다. 보드에서 tcpdump는 -w로 저장하고 PC로 가져와 보는 것이 정석이다. 처음에 LiDAR 표준 포트 2368을 썼다가 같은 VM의 다른 실습과 겹쳐 캡처가 섞였다 — 공용 장비에서는 포트 충돌부터 확인한다.

10.4 CAN — SocketCAN 인터페이스 올리기#

Linux에서 CAN 컨트롤러는 /dev 장치가 아니라 네트워크 인터페이스(can0)다(A9). 그래서 ip로 설정하고, can-utils(candump, cansend, cangen)로 프레임을 주고받는다. 이 VM에는 bit timing 설정을 실제로 받는 가상 컨트롤러 dummy_can이 있어서, 실제 보드와 같은 문법을 그대로 돌려 볼 수 있다.

출력에서 볼 것: ip -details는 컨트롤러가 허용하는 bit timing 범위(tseg1, brp…)와 CAN 클럭(160 MHz)을 보여 준다. bitrate를 정하지 않고 up 하면 Invalid argument — 실제 보드 첫날 가장 흔한 에러다(dmesg에는 can0: bit-timing not yet defined). 순서는 항상 down → type can bitrate ... → up이다.

출력에서 볼 것: 커널이 500 kbit/s, sample point 87.5%를 만족하는 brp=2(tq 12.5 ns, 화면에는 12로 표시), prop-seg 69 + phase-seg1 70 + phase-seg2 20(+ sync 1 = 160 tq)을 자동 계산했다. 160 MHz / 2 / 160 tq = 500 kHz. 실제 컨트롤러에서는 이 값이 트랜시버·버스 길이에 맞는지 scope로 비트 폭(2 µs)을 재서 확인한다. 보낸 프레임이 TX 카운터에 1개로 잡혔다(dummy_can은 수신 측이 없어 RX는 0).

인터페이스가 up인 상태에서 bitrate를 바꾸려 하면(이 노트 작성 중 앞선 실행에서 본 출력):

up 상태에서는 bit timing을 못 바꾼다(EBUSY). 반드시 ip link set can0 down부터 한다.

버스 오프 자동 복구(restart-ms)는 실제 컨트롤러 드라이버(FlexCAN, MCP251xFD 등)는 지원하지만 dummy_can은 지원하지 않는다.

프레임을 주고받는다. candump를 백그라운드로 띄우고 cansend로 표준 ID(11비트), 확장 ID(29비트, J1939 형태), OBD-II 요청을 보낸다. 다른 실습이 vcan0을 쓰고 있어서 이 실험은 별도 vcan 인터페이스 can_a10에서 했다(vcan은 bitrate 개념이 없는 순수 소프트웨어 루프백이다).

출력에서 볼 것: vcan에 bitrate를 주면 Operation not supported다(타이밍이 없는 가상 버스). candump -td는 프레임 간 시간차, -x는 방향(TX/RX) 같은 추가 정보다. ID#DATA 형식에서 ID가 3자리면 표준, 8자리면 확장 프레임이다. candump can_a10,123:7FF는 ID 필터(ID:MASK)로 0x456은 걸러졌다 — 이 필터는 커널의 CAN_RAW_FILTER 소켓 옵션으로 걸린다(A9). -L은 canplayer로 다시 재생할 수 있는 로그 형식이다. 실제 버스에서 프레임이 안 보이면 ip -details -statistics link show can0의 can state(ERROR-ACTIVE → ERROR-WARNING → ERROR-PASSIVE → BUS-OFF)와 bus-errors 카운터를 먼저 본다. 이 dummy_can 출력에서는 이렇게 보였다.

실제 보드 전용 (VM에 하드웨어 없음 — 실제 보드 출력 예시는 생략): 트랜시버가 붙은 진짜 버스에서는 상대 노드가 ACK를 안 주면 can state가 ERROR-PASSIVE로 가고 bus-errors가 오른다. 노드가 하나뿐인 버스에서 "보냈는데 아무 일도 없다"는 대부분 ACK 부재 또는 종단 저항(120 Ω) 누락이다.

17. 면접에서 이렇게 말한다#

Q. "Your driver module loads but the device doesn't work. How do you debug it?"

A. load와 probe를 구분한다. lsmod로 load를 확인하고, /sys/bus/<bus>/devices/<dev>/driver 링크로 바인딩을 확인한다. 없으면 dmesg에서 드라이버의 마지막 메시지와 errno를 보고, -EPROBE_DEFER면 devices_deferred, 메시지가 없으면 dynamic debug로 drivers/base/dd.c를 켜고 bind에 다시 써서 probe를 재시도한다. 바인딩은 됐는데 동작이 없으면 /proc/interrupts 카운터와 버스 도구(i2cdetect, scope)로 하드웨어 쪽을 본다.

I separate "loaded" from "probed". lsmod tells me the module is in; the driver symlink under /sys/bus/.../devices tells me it actually bound. If it didn't bind, I read the last driver message and errno in dmesg; for -EPROBE_DEFER I check devices_deferred in debugfs, and if probe fails silently with -ENODEV I turn on dynamic debug for drivers/base/dd.c and re-trigger with the bind file. If it's bound but dead, I watch /proc/interrupts and go to the bus with i2c-tools or a scope.

꼬리 질문: "Why might probe fail without any error message?" → -ENODEV/-ENXIO는 "내 장치가 아님"으로 해석되어 driver core가 디버그 레벨로만 남긴다.

Q. "rmmod says the module is in use. What do you do?"

A. lsmod의 Used by 카운트를 보고, 그 모듈이 만든 장치 노드를 누가 열었는지 fuser -v나 lsof로 찾는다. 다른 모듈 의존이면 그 모듈부터 내린다. 열린 fd가 자식에게 상속돼 있을 수 있으니 자식 프로세스까지 본다.

lsmod's "Used by" is the refcount. Either another module depends on it, or a process holds a file it backs. I use fuser -v or lsof on the device node to find the holder — remembering that forked children inherit the fd unless O_CLOEXEC was used — stop it, then rmmod.

Q. "What's the difference between dmesg and journalctl?"

A. dmesg는 커널 printk 링버퍼를 /dev/kmsg로 직접 읽는다 — RAM에 있고 크기가 정해져 있어 오래된 것은 덮어쓰인다. journalctl은 journald가 커널 로그와 서비스 로그를 함께 모아 색인한 저장소를 질의한다. 부팅별(-b), 유닛별(-u), 우선순위별(-p) 필터가 되고, persistent로 설정하면 이전 부팅 로그도 남는다.

dmesg reads the kernel's printk ring buffer through /dev/kmsg — volatile and size-limited. journalctl queries journald's indexed store, which contains kernel messages plus service output, filterable by boot, unit and priority, and persistent across reboots if storage is configured that way.

Q. "The system feels slow. What are your first commands?"

A. uptime/top으로 load와 CPU 분해(us·sy·wa·si)를 보고, vmstat 1로 r(CPU 대기), b·wa(I/O 대기), in·cs를 본다. I/O면 iostat -x의 await·큐 깊이, CPU면 pidstat -t로 스레드 단위, 인터럽트가 의심되면 /proc/interrupts를 두 번 읽어 비율을 낸다. 그다음에 perf·ftrace로 내려간다.

I start broad: top for the us/sy/wa/si split, then vmstat 1 — r tells me CPU contention, b and wa tell me I/O waiting, in and cs show interrupt and switch rates. Then I narrow: iostat -x for await and queue depth, pidstat -t per thread, and /proc/interrupts sampled twice for IRQ rates. Only then do I reach for perf or ftrace.

Q. "How do you bring up a CAN interface on Linux?"

A. CAN은 SocketCAN 네트워크 인터페이스다. ip link set can0 type can bitrate 500000(필요하면 sample-point, CAN FD면 dbitrate·fd on)으로 타이밍을 정하고 up 한다. 동작 중에는 타이밍을 못 바꾸므로 먼저 down. 확인은 ip -details -statistics link의 state·에러 카운터와 candump/cansend.

CAN is a SocketCAN netdev, so it's configured with ip: set the bitrate — and sample point or data bitrate for CAN FD — while the link is down, then bring it up. I verify with ip -details -statistics for the bit timing, controller state and error counters, and exercise it with candump and cansend.

Q. "Explain 2>&1 and why order matters. What does set -euo pipefail do?"

A. 2>&1은 fd 2를 지금 fd 1이 가리키는 곳으로 복제(dup2)한다. 셸은 리다이렉션을 왼쪽부터 처리하니 > file 2>&1이어야 둘 다 파일로 간다. strict mode는 실패 시 종료(-e), 미정의 변수 에러(-u), 파이프 중간 실패 전파(pipefail)다. -e가 조건문 안에서는 안 먹는다는 함정도 안다.

2>&1 duplicates fd 2 onto whatever fd 1 points to at that moment; redirections apply left to right, so it has to come after "> file". set -euo pipefail makes the script exit on errors, treat unset variables as errors, and fail a pipeline if any stage fails — with the caveat that -e is suppressed in if conditions and && / || chains.

Q. "How do you check what's on an I2C bus, and what are the risks?"

A. i2cdetect -l로 버스, i2cdetect -y N으로 스캔한다. UU는 드라이버가 잡은 주소다. 하지만 스캔은 quick write나 read를 실제로 보내므로 일부 칩의 상태를 바꾸거나 버스를 멈출 수 있다. 회로도로 주소를 먼저 알고, 필요하면 -r로 범위를 좁힌다. i2cset은 드라이버를 우회하므로 PMIC 같은 버스에서는 특히 위험하다.

i2cdetect -l lists adapters and i2cdetect -y N scans; UU means a kernel driver owns that address. Scanning isn't passive — it issues quick writes or reads that can change some chips' state or hang the bus — so I check the schematic first and limit the range. i2cset and i2cdump bypass the driver entirely; on a PMIC bus a wrong write can take the board down.

Q. "What's the difference between /proc, /sys and debugfs?"

A. /proc는 프로세스 정보와 오래된 커널 상태 파일, /sys는 장치 모델(kobject) 트리로 장치·드라이버·속성을 하나에 하나씩 보여 주는 안정 ABI다. debugfs는 드라이버 개발자가 자유롭게 내놓는 디버그 정보로 ABI 보장이 없어서 제품 코드가 의존하면 안 된다.

/proc holds per-process data and legacy kernel status files. /sys mirrors the device model — buses, devices, drivers, one value per attribute — and is a stable ABI. debugfs is a free-form debugging interface with no ABI guarantees, so production code shouldn't depend on it.

20. 요약 & 체크리스트#

보드 앞에서 셸은 측정 장비다. 정보는 /proc(상태), /sys(장치 모델), /dev(I/O), debugfs(드라이버 내부), 로그(시간 순 기록) 다섯 곳에 있고, lsmod·lspci·dmesg·ss는 그 파일·소켓을 예쁘게 찍는 프로그램일 뿐이다. 문제는 "어떤 HW가 있나 → 드라이버가 load·probe 됐나 → 누가 장치를 쓰나 → 왜 느린가 → 커널이 뭐라 했나 → 네트워크·CAN이 사나"의 질문으로 쪼개서 좁힌다. load와 probe를 구분하고(driver 링크, dynamic debug), i2c-tools·gpioset·devmem은 드라이버를 우회하는 위험한 도구임을 기억한다. 스크립트는 set -euo pipefail·따옴표·2>&1 순서를 지키고, 보드용은 BusyBox sh로 돌아가게 쓴다.
