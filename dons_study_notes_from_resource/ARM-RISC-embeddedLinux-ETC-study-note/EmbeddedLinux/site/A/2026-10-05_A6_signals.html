0. 큰 그림 — 이게 왜 필요한가#

Bare-metal 펌웨어에서 "비동기 이벤트"는 전부 인터럽트였다. UART에 바이트가 오면 IRQ 라인이 올라가고, NVIC의 pending 비트가 켜지고, 마스크가 열려 있으면 벡터 테이블에서 ISR 주소를 찾아 점프한다.

Linux의 유저 프로세스는 하드웨어 IRQ를 직접 받을 수 없다. 대신 커널이 프로세스에게 "이벤트가 생겼다"는 사실을 비동기로 알려 주는 장치가 있는데, 그게 시그널(signal) 이다. 시그널은 번호(1~64)만 가진 아주 작은 메시지이고, 받는 쪽은 미리 등록한 함수(handler)로 반응하거나, 커널이 정한 기본 동작(default action) 을 따른다.

센서 키트 장비에서 시그널이 등장하는 장면은 이런 것들이다.

  • systemd가 systemctl stop sensord를 받으면 데몬에 SIGTERM을 보낸다. 데몬은 IMU 전원을 끄고, 버퍼를 flush하고, 종료해야 한다.
  • 개발자가 터미널에서 Ctrl-C를 누르면 SIGINT.
  • 카메라 버퍼를 mmap 했는데 드라이버가 버퍼를 치워 버렸다면 그 주소를 건드리는 순간 SIGBUS.
  • 데이터 로거가 끊어진 TCP 소켓에 write 하면 SIGPIPE로 조용히 죽는다.
  • NULL 포인터를 밟으면 SIGSEGV → core dump → gdb로 사후 분석.

그림 1 — 하드웨어 인터럽트 경로(왼쪽)와 시그널 경로(오른쪽)는 단계마다 짝이 맞는다. 단, 실행 시점·특권 수준·스택이 다르다.

1. 시그널이란 — 하드웨어 IRQ와 어디까지 같은가#

1.1 정의#

시그널 = 커널이 특정 프로세스(또는 스레드)의 pending 집합에 번호 하나를 기록하고, 그 프로세스가 다음에 커널에서 유저 모드로 돌아갈 때 그 번호에 해당하는 동작을 실행하게 하는 메커니즘이다.

시그널을 만드는 쪽은 세 가지다.

  1. 다른 프로세스: kill(pid, sig), sigqueue(), 셸의 kill 명령, systemd.
  2. 커널 자신 — 동기(synchronous) 시그널: 이 스레드가 방금 실행한 명령이 원인. 잘못된 메모리 접근(SIGSEGV), 매핑은 있지만 뒤에 실체가 없는 페이지(SIGBUS), 0으로 나누기(SIGFPE), 정의되지 않은 명령(SIGILL).
  3. 커널 자신 — 비동기 이벤트: 자식 종료(SIGCHLD), 읽는 쪽 없는 pipe에 쓰기(SIGPIPE), 타이머 만료(SIGALRM), 터미널의 Ctrl-C(SIGINT)·끊김(SIGHUP).

2.3 SIGBUS vs SIGSEGV — Don에게 특히 중요한 구분#

  • SIGSEGV: 그 주소에 매핑 자체가 없거나(SEGV_MAPERR), 권한이 없다(SEGV_ACCERR). MMU 관점에서 "page table에 없음/권한 위반".
  • SIGBUS: 매핑은 있는데 그 페이지를 채울 실체가 없다. 대표적으로 mmap한 파일이 중간에 truncate 되어 파일 끝 너머 페이지를 건드릴 때(BUS_ADRERR), 드라이버의 .fault가 VM_FAULT_SIGBUS를 돌려줄 때, 메모리 하드웨어 오류(BUS_MCEERR_AR). 디바이스 레지스터를 /dev/mem이나 UIO로 mmap 해서 접근하다가 버스 에러(외부 abort)가 나는 경우도 아키텍처에 따라 SIGBUS로 온다.

SSD 펌웨어로 치면 SEGV는 "MPU region 밖 접근", SIGBUS는 "region은 열려 있는데 그 뒤 버스 슬레이브가 에러 응답"에 가깝다. 예제 4에서 직접 만든다.

3.2 signal() 대신 sigaction()을 쓰는 이유#

signal(sig, handler)는 오래된 API라 시스템마다 의미가 다르다. System V 계열은 handler가 한 번 불리면 SIG_DFL로 되돌리고(재진입 중 같은 시그널 오면 죽음), BSD 계열은 유지 + 시스템콜 자동 재시작이다. glibc의 signal()은 BSD 의미지만 이식성 있는 코드는 sigaction()만 쓴다. sigaction은 다음을 명시적으로 정한다.

  • sa_mask: handler 실행 중 추가로 block할 시그널. 처리 중인 시그널 자신은 SA_NODEFER가 없으면 자동으로 막힌다(ISR이 자기 IRQ를 다시 받지 않는 것과 같다).
  • sa_flags: SA_RESTART, SA_SIGINFO, SA_ONSTACK(sigaltstack 사용), SA_NOCLDSTOP, SA_NOCLDWAIT, SA_RESETHAND, SA_NODEFER.

3.3 EINTR와 SA_RESTART — A3의 "robust loop"가 필요한 진짜 이유#

blocking syscall(예: read())로 잠들어 있는 동안 시그널이 오면 커널은 그 잠을 깨우고 handler를 돌려야 한다. 그럼 원래의 read()는?

  • handler에 SA_RESTART가 없으면: read()는 -1, errno=EINTR로 돌아온다.
  • SA_RESTART가 있으면: 커널이 read()를 자동으로 다시 실행한다. 유저 코드는 끊긴 줄도 모른다.

예제 3 — EINTR vs SA_RESTART를 눈으로 보기#

무엇을 확인하나: 2초 뒤에 데이터가 오는 pipe를 read()로 기다리는 동안 1초 시점에 SIGALRM이 온다. 플래그에 따라 결과가 어떻게 달라지는가.

출력에서 볼 것: 두 경우 모두 1초에 handler가 돈다. 그런데 flags=0이면 read()가 1.01초에 EINTR로 실패하고, SA_RESTART면 재시작되어 2.01초에 데이터 4바이트를 정상으로 받는다.

꼭 기억할 함정 세 가지:

  1. SA_RESTART가 있어도 재시작되지 않는 syscall이 있다. poll, select, epoll_wait, nanosleep/clock_nanosleep(남은 시간 반환), 타임아웃을 설정한 소켓 read 등은 handler가 돌면 항상 EINTR다(man 7 signal의 "Interruption of system calls" 절). 그래서 이벤트 루프는 EINTR를 항상 처리해야 한다.
  2. 내가 SA_RESTART를 써도 라이브러리가 설치한 handler가 SA_RESTART 없이 깔릴 수 있다. 결론: A3에서 만든 것처럼 read/write 래퍼는 항상 if (errno == EINTR) continue; 를 넣는다.
  3. 부분 전송: 이미 일부 바이트를 읽거나 쓴 뒤에 시그널이 오면 syscall은 EINTR가 아니라 그때까지의 바이트 수를 돌려준다. 그래서 루프가 필요하다.

그림 2 — 시그널 배달 타임라인. 보내는 쪽은 비트만 세우고 바로 돌아간다. 실제 handler 실행은 대상 스레드가 커널에서 유저로 돌아가는 ⑤ 시점이다. ⑧에서 SA_RESTART 여부가 갈린다.

3.4 SA_SIGINFO — "누가, 왜, 어디서"#

SA_SIGINFO를 켜면 handler 시그니처가 void h(int sig, siginfo_t *si, void *ucontext)가 되고, siginfo_t로 다음을 알 수 있다.

  • si_code: 원인. SI_USER(kill), SI_QUEUE(sigqueue), SI_KERNEL, 폴트면 SEGV_MAPERR/SEGV_ACCERR/BUS_ADRERR 등.
  • si_pid, si_uid: 보낸 프로세스 (kill/sigqueue일 때).
  • si_addr: 폴트 주소 (SIGSEGV/SIGBUS/SIGILL/SIGFPE).
  • si_value: sigqueue로 실려 온 값.
  • si_status: SIGCHLD일 때 자식의 종료 코드.
  • 세 번째 인자 ucontext_t: 끊긴 순간의 레지스터 전체 (10절에서 사용).

4. 마스크, pending, disposition — 시그널 상태 3종 세트#

4.1 세 가지 상태#

  • disposition (프로세스 전체 공유): 시그널마다 SIG_DFL / SIG_IGN / handler 주소. 벡터 테이블.
  • blocked 마스크 (스레드마다): 지금 배달을 미룰 시그널 집합. PRIMASK의 시그널판.
  • pending 집합: 도착했지만 아직 배달 안 된 시그널. 두 종류가 있다.
  • 스레드 전용 pending (pthread_kill, tgkill, 동기 폴트) → /proc/<pid>/status의 SigPnd
  • 프로세스 공유 pending (kill(pid)) → ShdPnd

배달 조건은 간단하다: pending AND NOT blocked 인 시그널이 있으면, 다음 유저 복귀 때 배달된다.

  • 풀자마자 handler가 USR1은 1번, RTMIN은 3번 불렸다. 표준 시그널은 NVIC pending 비트처럼 합쳐지고, RT 시그널은 큐잉된다. 그래서 "시그널로 이벤트 개수를 세면 안 된다"(표준 시그널).

4.2 sigprocmask vs pthread_sigmask#

  • sigprocmask()는 싱글 스레드 프로그램용. 멀티스레드에서는 동작이 정의되지 않았다(POSIX). Linux glibc에서는 호출한 스레드의 마스크만 바꾼다.
  • 멀티스레드에서는 pthread_sigmask()를 쓴다. 마스크는 스레드마다 있고, pthread_create 시 부모 스레드의 마스크를 상속한다(7절의 핵심).
  • fork()의 자식은 마스크와 disposition을 상속, pending은 비운다. exec()는 마스크·무시(SIG_IGN) 설정을 유지하고, handler는 SIG_DFL로 되돌린다(새 프로그램에는 그 handler 코드가 없으니까). 그래서 시그널을 막아 둔 데몬이 자식을 exec 하면 자식도 SIGTERM이 막힌 채로 시작한다 — 흔한 버그(12절).

5. Async-signal-safety — handler 안에서 해도 되는 일#

5.1 왜 제약이 있나#

handler는 프로그램의 아무 명령 사이에서나 끼어든다. 메인 코드가 malloc() 안에서 힙 락을 쥔 순간 시그널이 와서 handler가 또 malloc()을 부르면? 같은 스레드가 자기가 쥔 락을 다시 기다린다 — self-deadlock. printf()는 stdout 버퍼(+락)를, syslog()는 소켓과 락을, exit()는 atexit 핸들러와 stdio flush를 건드린다.

ISR에서 RTOS mutex를 잡지 않는 것과 정확히 같은 이유다. 차이는 ISR은 별도 컨텍스트라 "ISR에서는 mutex API 금지"가 명확한 반면, handler는 같은 스레드 위에 올라타기 때문에 재귀 진입 문제가 생긴다는 것.

POSIX가 handler에서 불러도 된다고 보장하는 함수 목록이 async-signal-safe 목록이다(man 7 signal-safety). 대표적으로 write, read, _exit, kill, sigprocmask, sem_post, clock_gettime, open, close, signal/sigaction 등. 안 되는 것: printf 계열, malloc/free, pthread_mutex_lock, syslog, exit, 대부분의 C++ 라이브러리.

예제 6 — handler에서 "락 잡는 함수"를 부르면 실제로 멈춘다#

무엇을 확인하나: 메인 루프와 handler가 같은 로깅 함수(내부에 비재귀 mutex)를 쓴다. glibc의 malloc·stdio가 내부에서 하는 일과 같은 구조다. 100µs마다 SIGALRM을 건다.

출력에서 볼 것: "main alive"가 첫 줄 이후 더 안 나오고 프로세스는 CPU 0%로 futex에서 잔다. backtrace를 아래에서 위로 읽으면 이야기가 그대로 보인다: main → log_msg(락 쥔 상태로 memcpy 중, #9) → <signal handler called>(#5, 커널이 만든 시그널 프레임) → handler 안의 log_msg → pthread_mutex_lock → 자기 자신이 쥔 락을 영원히 기다림. 한 스레드 안에서 생긴 교착이라 다른 스레드가 풀어 줄 수도 없다.

참고로 같은 실험을 glibc malloc으로 해 보면(handler에서 malloc/free) 이 VM(glibc 2.43)에서는 수십 번 돌려도 거의 재현되지 않았다. 최신 glibc는 스레드별 캐시(tcache)가 락 없이 대부분의 할당을 처리하기 때문이다. 그래서 더 위험하다 — 테스트에선 통과하고, 현장에서 몇 주에 한 번 장비가 멈춘다. "가끔 안 죽는 프로세스"의 backtrace에 <signal handler called> 위로 malloc/printf가 보이면 바로 이 버그다.

5.2 안전한 패턴 1 — volatile sig_atomic_t 플래그#

  • sig_atomic_t: 시그널에 대해 한 번에 읽고 쓰는 것이 보장되는 정수형(찢어진 읽기 없음).
  • volatile: 컴파일러가 루프 안에서 값을 레지스터에 캐시하지 못하게 한다. ISR 플래그에 volatile을 붙이던 것과 같다.
  • C11 이후로는 lock-free atomic_int도 허용된다. 하지만 sig_atomic_t가 가장 이식성 있다.
  • 한계: 메인이 poll()이나 read()에 잠들어 있으면 플래그를 확인할 기회가 없다. SA_RESTART면 read가 다시 잠들어 버린다. 이를 해결하는 게 다음 패턴들이다.

5.3 안전한 패턴 2 — self-pipe trick#

handler는 pipe에 1바이트만 write(async-signal-safe)하고, 메인 루프는 그 pipe의 읽기 끝을 다른 fd들과 함께 poll한다. 시그널이 "읽을 수 있는 fd 이벤트"로 바뀐다. ISR이 RTOS 큐에 메시지 하나 넣고 끝내는 것과 같다.

6. signalfd + epoll — Linux 데몬의 표준 답#

6.1 아이디어#

signalfd는 "pending 시그널을 read()로 꺼내 읽는 fd"다. 시그널을 block 해 두면 커널은 handler를 부르지 않고 pending에 쌓아 두며, signalfd가 readable이 된다. 그 fd를 A4의 epoll에 다른 fd들(timerfd, IMU, UDP 소켓)과 같이 등록하면, 시그널이 그냥 이벤트 루프의 이벤트 하나가 된다. handler 자체가 없으니 async-signal-safety 걱정이 사라진다.

6.2 signalfd 사용 규칙#

  1. 반드시 먼저 block 한다. 안 막으면 기본 동작(SIGTERM이면 즉사)이 signalfd보다 먼저 일어난다.
  2. 멀티스레드면 pthread_create 전에 main에서 block 해야 모든 스레드가 상속한다(7절). 한 스레드라도 안 막으면 커널이 그 스레드에 배달해 버린다.
  3. 표준 시그널은 signalfd에서도 합쳐진다. read는 한 번에 여러 개의 signalfd_siginfo(각 128바이트)를 줄 수 있으니 루프로 다 읽는다.
  4. 자식 exec 전 마스크 복원: 막힌 마스크가 exec 후에도 유지되므로, fork 후 자식에서 sigprocmask(SIG_UNBLOCK, ...) 하거나 posix_spawnattr_setsigmask로 지정한다.
  5. SIGSEGV 같은 동기 폴트는 block 해도 소용없다(막혀 있으면 커널이 강제로 기본 동작 → 사망). signalfd는 비동기 시그널 전용이다.

7. 시그널과 스레드#

7.1 규칙 네 줄#

  1. disposition(handler)은 프로세스 전체 공유. 어느 스레드에서 sigaction해도 전체에 적용.
  2. 마스크는 스레드마다. 새 스레드는 만든 스레드의 마스크를 상속.
  3. process-directed 시그널(kill(pid))은 그 시그널을 막지 않은 스레드 아무나 하나가 받는다. 커널은 먼저 메인 스레드를 시도하고, 막혀 있으면 다른 스레드를 고른다.
  4. thread-directed 시그널(pthread_kill, 그리고 SIGSEGV·SIGBUS·SIGFPE 같은 동기 폴트)은 그 스레드가 받는다. 기본 동작이 Term/Core면 프로세스 전체가 죽는다.

예제 9 — 누가 받나, 그리고 전용 sigwait 스레드#

무엇을 확인하나: [A] 마스크 없이 kill과 pthread_kill이 어느 스레드로 가는지, [B] 모든 스레드가 막고 전용 스레드가 sigwait로 받는 패턴. 그리고 "막기 전에 만든 스레드"가 하나 있으면 어떻게 되는지.

출력에서 볼 것:

  • [A]: kill(pid)는 main 스레드(tid=pid)가, pthread_kill(t)는 지정한 worker가 받았다.
  • 첫 실행 [B]: 프로세스가 SIGHUP으로 죽었다(exit 129 = 128+1). [A]에서 막기 전에 만든 worker가 SIGHUP을 막지 않은 유일한 스레드였고, 커널이 거기로 배달 → 기본 동작 Term → 프로세스 전체 사망. sigwait 스레드는 받아 볼 기회도 없었다.
  • fix 실행: 옛 worker를 정리하자 SIGHUP·SIGTERM이 모두 sig_thread의 sigwait로 들어왔다. 교훈: main 첫 줄에서 block, 그다음에 스레드 생성. 서드파티 라이브러리가 몰래 만든 스레드도 같은 문제를 일으킨다(그래서 라이브러리 초기화보다 먼저 막는다).

sigwait(또는 sigwaitinfo, sigtimedwait)는 signalfd와 같은 원리(막아 두고 동기적으로 꺼내기)를 "스레드 하나를 바쳐서" 구현한 것이다. 스레드 기반 구조면 sigwait 스레드, 이벤트 루프 구조면 signalfd를 쓴다.

8. 코어 덤프 — SIGSEGV/SIGABRT의 사후 분석 (M9 미리보기)#

Core 동작 시그널로 죽을 때 커널은 프로세스 메모리 이미지와 레지스터를 ELF 형식 core 파일로 쓴다. 조건:

  • RLIMIT_CORE(셸 ulimit -c)가 0이 아니어야 한다. 대부분 배포판·systemd 서비스의 기본은 0 또는 제한적.
  • /proc/sys/kernel/core_pattern이 파일 위치·이름을 정한다. %e(실행 파일 이름), %p(pid), %t(시각) 같은 지정자를 쓴다. 맨 앞이 파이프 기호면 커널이 core를 프로그램의 stdin으로 넘긴다(systemd-coredump, Ubuntu의 apport가 이 방식). 이 VM은 단순히 core이고 core_uses_pid=1이라 core.<pid>가 현재 디렉터리에 생긴다.
  • setuid 프로그램 등은 fs.suid_dumpable에 따라 제한된다. 프로세스는 prctl(PR_SET_DUMPABLE)로 끌 수도 있다.

10.3 배달 경로 — "유저로 돌아가는 순간"#

그림 6 — 커널의 배달 경로. 핵심은 "handler 호출 = 커널이 유저 스택에 가짜 호출 프레임을 만들고 PC를 바꿔서 eret 하는 것"이다. 돌아오는 길은 rt_sigreturn syscall이다.

진입 함수 이름은 아키텍처·버전마다 다르다(x86 등 generic entry를 쓰는 아키텍처는 exit_to_user_mode_loop() → arch_do_signal_or_restart(), arm64는 오랫동안 do_notify_resume() → do_signal()이었고 generic entry로 옮겨 가는 중이다). 구조 — "TIF 플래그 보고 → get_signal() → handle_signal() → setup_rt_frame()" — 는 같다. arm64 구현은 arch/arm64/kernel/signal.c에 있고, syscall 재시작 처리는 do_signal()에서 반환값이 -ERESTARTSYS/-ERESTARTNOINTR/-ERESTARTNOHAND/-ERESTART_RESTARTBLOCK인지 보고 x0를 orig_x0로 되돌리고 PC를 4바이트(svc 명령 하나) 뒤로 돌리는 방식이다.

Bare-metal로 번역하면: Cortex-M이 예외 진입 때 하드웨어로 스택에 R0-R3, R12, LR, PC, xPSR을 쌓고 EXC_RETURN으로 돌아오는 것을, 커널이 소프트웨어로 유저 스택에 해 주는 것이다. 그 "EXC_RETURN"에 해당하는 것이 rt_sigreturn이다.

10.4 D 상태 프로세스는 왜 kill -9에 안 죽나 (F3 미리보기)#

13. 면접에서 이렇게 말한다#

Q. What happens when you press Ctrl-C in a terminal running your program?

A. 터미널 드라이버(tty line discipline)가 Ctrl-C 문자를 보고 foreground 프로세스 그룹 전체에 SIGINT를 보낸다. 커널은 각 프로세스의 pending에 SIGINT를 세우고 TIF_SIGPENDING을 켠 뒤 잠들어 있으면 깨운다. 프로세스가 유저로 돌아가는 순간 handler가 있으면 신호 프레임을 쌓아 handler를 실행하고, 없으면 기본 동작인 종료가 일어난다.

The tty line discipline sees the interrupt character and sends SIGINT to the whole foreground process group. The kernel marks it pending, sets TIF_SIGPENDING and wakes the task if it's in an interruptible sleep. On the next return to user space, the kernel either runs the default action, which is terminate, or builds a signal frame on the user stack and jumps to the registered handler, which returns through rt_sigreturn.

꼬리 질문: 백그라운드 작업은 왜 Ctrl-C에 안 죽나? → foreground 프로세스 그룹에만 보내기 때문.

Q. Can you call printf or malloc inside a signal handler? Why not?

A. 안 된다. async-signal-safe가 아니기 때문이다. handler는 메인 코드의 임의 지점에 끼어드는데, 메인이 malloc이나 stdio 안에서 락을 쥔 순간이면 handler가 같은 락을 다시 잡으려다 자기 자신과 교착하거나 내부 자료구조를 깨뜨린다. 그래서 handler에서는 volatile sig_atomic_t 플래그를 세우거나 write()로 self-pipe에 1바이트 쓰는 정도만 하고, 실제 일은 메인 루프에서 한다. Linux에서는 아예 시그널을 막고 signalfd로 이벤트 루프에서 읽는 게 가장 깔끔하다. 실제로 mutex를 쓰는 로깅 함수를 handler에서 불러 gdb로 <signal handler called> 위에서 futex 대기하는 self-deadlock을 재현해 봤다.

No. They're not async-signal-safe. A handler can interrupt the main flow at any instruction, so if the main code is inside malloc holding the arena lock, the handler's malloc tries to take the same non-recursive lock on the same thread and deadlocks, or corrupts internal state. Handlers should only set a volatile sig_atomic_t flag or write a byte to a self-pipe. On Linux my preference is to block the signals and read them from a signalfd in the epoll loop, so there's no handler at all. It's the same discipline as keeping ISRs short and deferring work to the main loop in firmware.

Q. Why can't you catch SIGKILL, and why does kill -9 sometimes not kill a process?

A. SIGKILL과 SIGSTOP은 커널이 프로세스를 확실히 통제하기 위한 수단이라 handler 등록·block·무시가 모두 거부된다. 그런데 SIGKILL도 "pending 비트 + 깨우기"이고, 실제 종료는 그 스레드가 커널을 빠져나오며 get_signal()을 지날 때 일어난다. 드라이버나 파일시스템이 TASK_UNINTERRUPTIBLE로 자고 있으면(ps의 D) 시그널로 깨지 않으니 조건이 만족될 때까지 안 죽는다. 그래서 드라이버는 wait_event_interruptible이나 최소한 wait_event_killable을 써야 한다. 직접 모듈을 만들어 재 보니 uninterruptible은 타임아웃 5초가 끝나서야 죽고, killable은 즉시 죽었다.

SIGKILL and SIGSTOP are reserved so the kernel can always control a process; sigaction refuses to install handlers or block them. But SIGKILL is still just a pending bit plus a wakeup, and the actual exit happens when the task passes through get_signal on its way back to user space. If a driver puts the task in TASK_UNINTERRUPTIBLE, the D state, the signal can't wake it, so it only dies once the wait condition is met. That's why drivers should use wait_event_interruptible, or at least wait_event_killable, and return -ERESTARTSYS.

Q. How are signals delivered in a multithreaded process?

A. handler(disposition)는 프로세스 공유, 마스크는 스레드별이다. kill(pid)처럼 프로세스로 온 시그널은 막지 않은 스레드 중 하나가 받고, pthread_kill이나 SIGSEGV 같은 동기 폴트는 해당 스레드가 받는다. 그래서 패턴은 main 시작 직후 모든 스레드를 만들기 전에 pthread_sigmask로 막아 두고, 전용 스레드에서 sigwait하거나 signalfd로 읽는 것이다. 막기 전에 만든 스레드가 하나라도 있으면 그쪽으로 배달돼 기본 동작으로 프로세스가 죽는 것을 실험으로 확인했다.

Dispositions are process-wide, masks are per thread. A process-directed signal goes to any one thread that doesn't block it; thread-directed signals and synchronous faults go to the specific thread. The robust pattern is to block the signals in main before creating any threads, so every thread inherits the mask, and then have one dedicated thread call sigwait, or read a signalfd in the event loop.

Q. What is EINTR and how does SA_RESTART relate to it?

A. blocking syscall 중에 handler가 실행되면 그 syscall은 중단된다. 드라이버나 커널은 -ERESTARTSYS를 돌려주고, handler에 SA_RESTART가 있으면 커널이 PC를 되돌려 syscall을 다시 실행하고, 없으면 유저에게 -1/EINTR를 준다. 다만 poll, select, epoll_wait, nanosleep 같은 것은 SA_RESTART와 무관하게 EINTR를 준다. 그래서 견고한 코드는 항상 EINTR를 재시도하고 부분 읽기·쓰기도 루프로 처리한다.

If a handler runs while a thread is blocked in a syscall, the kernel side returns -ERESTARTSYS. If the handler was installed with SA_RESTART the kernel rewinds the PC and re-executes the syscall; otherwise user space sees -1 with EINTR. Some calls, like poll, epoll_wait and nanosleep, are never restarted. So robust I/O loops always retry on EINTR and handle short reads and writes.

Q. Standard signals vs real-time signals?

A. 표준 시그널(1~31)은 pending 비트 하나라서 막혀 있는 동안 여러 번 와도 한 번으로 합쳐지고, 값을 실을 수 없다. RT 시그널(SIGRTMIN~SIGRTMAX)은 보낸 만큼 큐잉되고 sigqueue로 정수나 포인터 값을 실을 수 있으며 번호가 낮은 것부터 배달된다. 큐 길이는 RLIMIT_SIGPENDING으로 제한된다.

Standard signals are a single pending bit each, so multiple instances collapse into one and carry no payload. Real-time signals are queued, one entry per send, can carry a value via sigqueue, and are delivered lowest number first. The queue is bounded by RLIMIT_SIGPENDING.

Q. How would you implement graceful shutdown for an embedded Linux daemon under systemd?

A. systemd는 stop 시 SIGTERM을 보내고 TimeoutStopSec(기본 90초) 후 SIGKILL을 보낸다. 데몬은 시작하자마자 SIGTERM/SIGINT/SIGHUP을 막고 signalfd를 epoll 루프에 넣는다. SIGTERM이 오면 루프를 빠져나와 일반 코드에서 하드웨어를 안전 상태로 두고, 버퍼를 flush 하고, 리소스를 정리한 뒤 exit 0 한다. SIGHUP은 설정 reload로 쓴다. 자식을 띄울 때는 막아 둔 마스크를 풀어 준다.

systemd sends SIGTERM, waits TimeoutStopSec, then SIGKILL. I block TERM, INT and HUP at startup, add a signalfd to the epoll loop, and on SIGTERM leave the loop, put the hardware in a safe state — stop streaming, park motors — flush and fsync, remove the pidfile and exit zero. HUP triggers a config reload. And before exec'ing children I restore the signal mask, since it's inherited.

Q. How does the kernel actually invoke a user-space handler?

A. 유저 복귀 직전 TIF_SIGPENDING을 보고 get_signal()로 하나를 꺼낸다. handler가 있으면 setup_rt_frame()이 유저 스택에 siginfo와 ucontext(레지스터 전체, 이전 마스크, FP 상태)를 저장하고, PC를 handler로, 인자 레지스터를 signo/siginfo/ucontext로, 링크 레지스터를 restorer로 바꿔서 eret 한다. handler가 리턴하면 restorer가 rt_sigreturn을 호출하고 커널이 프레임에서 레지스터와 마스크를 복원한다. 하드웨어 예외 진입 때의 스택 프레임과 EXC_RETURN을 소프트웨어로 흉내 내는 것이다.

On the way back to user space the kernel sees TIF_SIGPENDING, dequeues a signal in get_signal, and if there's a handler, setup_rt_frame pushes siginfo and a ucontext — all registers, the old mask and FP state — onto the user stack, then sets PC to the handler, x0 to x2 to the arguments and the link register to the restorer, and erets. When the handler returns, the restorer calls rt_sigreturn and the kernel restores everything from that frame. It's basically a software version of exception stacking and EXC_RETURN.

16. 요약 & 체크리스트#

시그널은 커널이 프로세스의 pending 집합에 번호를 세우고, 그 스레드가 커널에서 유저로 돌아가는 순간 기본 동작이나 handler를 실행하게 하는 "유저 프로세스용 가상 인터럽트"다. NVIC처럼 pending·마스크·벡터 테이블 구조를 갖지만, 배달은 커널 복귀 시점에만 일어나고 handler는 같은 유저 스택에서 돈다. 그래서 handler 안에서는 async-signal-safe 함수만 써야 하고, 실무 데몬은 시그널을 막아 두고 signalfd를 epoll 루프에 넣어 일반 코드에서 처리한다. SA_RESTART·EINTR는 드라이버의 -ERESTARTSYS에서 시작하며, 드라이버가 TASK_UNINTERRUPTIBLE로 자면 SIGKILL조차 처리되지 않는다. 시그널 왕복은 수백 ns로 비싸므로 데이터 알림이 아니라 수명 제어와 치명적 오류 보고에 쓴다.
