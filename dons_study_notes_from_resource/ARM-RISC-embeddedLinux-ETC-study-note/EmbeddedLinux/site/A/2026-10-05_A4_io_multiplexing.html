0. 큰 그림 — 이게 왜 필요한가#

센서 키트 데몬을 하나 떠올려 보자. 이 프로세스는 동시에 여러 가지를 기다린다.

  • IMU 샘플이 IIO 버퍼(/dev/iio:device0)에 들어왔나
  • LiDAR UDP 패킷이 소켓에 도착했나
  • 100 Hz 샘플링 주기가 돌아왔나 (타이머)
  • systemd가 "이제 종료해" (SIGTERM)를 보냈나
  • 워커 스레드가 "캘리브레이션 끝났어"라고 알렸나

read()는 fd 하나에서만 막혀서 기다린다. IMU fd에서 read()하며 잠들어 있으면 LiDAR 패킷이 와도 모른다. 그래서 "여러 fd 중 아무거나 준비되면 깨워 줘"라는 syscall이 필요하다. 이것이 I/O 다중화(I/O multiplexing) 이고, Linux에서는 select → poll → epoll 순서로 발전했다. 여기에 "타이머·스레드 알림·시그널까지 fd로 만들어서 같은 루프에 넣자"는 아이디어가 timerfd, eventfd, signalfd다.

그림 1 — 위: Linux 이벤트 루프. 아래: Don이 펌웨어에서 쓰던 "IRQ가 플래그를 세우고, main loop가 WFI로 자다가 깨서 플래그를 검사"하는 구조. 모양이 같다.

Bare-metal 비유로 한 번 더: SSD 펌웨어에서 NVMe doorbell, NAND 완료, DMA 완료, 타이머 인터럽트를 한 개의 main loop에서 처리했을 것이다. ISR은 짧게 플래그만 세우고(pending |= BIT_DMA_DONE), main loop는 WFI로 자다가 깨어나면 어떤 비트가 섰는지 보고 핸들러를 부른다. FreeRTOS라면 xEventGroupWaitBits()로 여러 비트를 한 번에 기다린다. Linux에서는

  • 인터럽트 소스 → fd (장치 파일, 소켓, 파이프, timerfd …)
  • 플래그 레지스터 → 커널이 fd마다 계산하는 준비 상태 mask (EPOLLIN, EPOLLOUT …)
  • WFI + 비트 검사 → epoll_wait() (잠들었다가, 준비된 fd 목록을 돌려받음)
  • ISR이 플래그를 세움 → 드라이버가 wait queue를 깨움 (wake_up())

실무에서는 섞어 쓴다. 이벤트 루프 하나가 I/O 준비 여부를 보고, 무거운 일(이미지 압축, 파일 쓰기, 긴 계산)은 worker 스레드로 보내고, 끝나면 eventfd로 루프에 알린다. 이 노트의 끝에서 그런 루프를 실제로 만든다(§8).

용어: non-blocking fd = O_NONBLOCK이 켜진 fd. 데이터가 없으면 잠들지 않고 -1 + errno == EAGAIN으로 즉시 돌아온다(A3). 이벤트 루프에서는 "준비됐다는 알림을 받은 뒤 읽는데, 혹시 모를 경우에도 절대 막히지 않게" 하려고 fd를 non-blocking으로 둔다.

2. select — 가장 오래된 방법#

2.1 정의#

  • fd_set은 비트맵이다. fd 번호 = 비트 번호. 크기는 FD_SETSIZE(=1024) 비트로 고정.
  • FD_ZERO, FD_SET(fd, &set), FD_CLR, FD_ISSET은 그 비트를 조작하는 매크로다. 펌웨어의 reg |= (1u << n)과 똑같다.
  • nfds는 "가장 큰 fd 번호 + 1". 커널은 비트 0부터 nfds-1까지 전부 훑는다.
  • in-out 인자: 호출 전에는 "관심 있는 fd", 리턴 후에는 "준비된 fd"만 남는다. 그래서 루프를 돌 때마다 다시 채워야 한다.

2.2 예제 — 두 pipe를 select로 기다리기#

자식 프로세스가 300 ms에 IMU, 600 ms에 GNSS 데이터를 쓴다. 부모는 select 한 번으로 둘을 기다린다.

출력에서 볼 것: 300 ms 근처에서 IMU만, 600 ms 근처에서 GNSS만 깨어났다(§1의 700 ms 지연이 사라졌다). Linux의 select는 timeout을 "남은 시간"으로 덮어쓴다(500 ms 중 약 197 ms 남음). 다른 OS는 안 그럴 수 있어서, 이식성 있는 코드는 루프마다 tv를 다시 설정한다(위 코드처럼).

2.3 strace로 보면 — arm64에는 select syscall이 없다#

출력에서 볼 것: aarch64 커널에는 옛날 select syscall 번호가 없고, glibc가 pselect6로 바꿔 호출한다(poll도 ppoll로, epoll_wait도 epoll_pwait로 — §8에서 확인). 마지막 줄은 자식이 종료하며 보낸 SIGCHLD에 잠깐 끊겼다가 커널이 자동 재시작한 흔적이다(strace에 ERESTARTNOHAND로 보인다; 시그널은 A6). x86_64에서 같은 프로그램을 strace하면 select/poll/epoll_wait가 그대로 보인다. 보드에서 strace 필터를 걸 때 이 이름 차이를 모르면 "아무것도 안 잡힌다"고 헤맨다.

3. poll — 배열 기반, 1024 제한 없음#

3.1 정의#

select와의 차이:

  • 입력(events)과 출력(revents)이 다른 필드라서 재무장이 필요 없다. 같은 배열을 계속 넘기면 된다.
  • fd 번호 제한이 없다(배열 길이 = nfds).
  • 이벤트 종류가 풍부하다.
플래그뜻events에 넣어야 하나
POLLIN읽을 데이터 있음 (또는 EOF)넣는다
POLLOUT지금 쓰면 막히지 않음넣는다
POLLPRI"예외적 조건": TCP urgent data, sysfs 속성 변경 알림(sysfs_notify), cgroup.events 변경 등넣는다
POLLRDHUP스트림 소켓 상대가 쓰기 쪽을 닫음 (Linux 전용, _GNU_SOURCE)넣는다

POLLHUP끊김 (예: pipe writer가 모두 닫힘)넣지 않아도 항상 보고

3.2 예제 — revents가 상황별로 어떻게 켜지나#

pipe 하나로 8가지 상황을 만들고, poll(…, 0)(즉시 확인)으로 revents를 찍어 보는 코드다.

출력에서 볼 것:

  • 5)처럼 writer가 닫혀도 남은 데이터가 있으면 POLLIN | POLLHUP이 같이 온다. HUP을 보자마자 fd를 닫으면 마지막 데이터를 잃는다. "HUP이면 먼저 읽을 수 있는 만큼 읽고, read()==0(EOF)을 보고 닫는다"가 정석이다.
  • 6) 다 읽은 뒤에는 POLLHUP만 남는다. 이걸 무시하고 루프를 돌면 poll이 계속 즉시 리턴해서 CPU 100% 루프가 된다(흔한 버그).
  • 7) 읽는 쪽이 없는 pipe에 쓰기 → POLLERR. 실제로 write()하면 SIGPIPE/EPIPE다(A6).
  • 8) POLLNVAL은 "닫힌 fd를 배열에 남겨 둔" 버그의 신호다.
  • 4) pipe 용량은 기본 64 KiB(16페이지)다. 1바이트가 이미 한 슬롯을 차지해 4 KiB 쓰기 15번에서 멈췄다.

3.3 POLLPRI와 sysfs GPIO — "edge 인터럽트를 유저에서 기다리기"#

sysfs 속성 파일(/sys/...)은 일반 데이터 스트림이 아니다. 그래서 "값이 바뀌었다"는 알림은 POLLIN이 아니라 POLLPRI | POLLERR로 온다. 드라이버가 sysfs_notify()(내부적으로 kernfs_notify())를 부르면, 그 파일을 poll 중인 프로세스가 깨어난다. 대표 예가 레거시 sysfs GPIO의 value 파일이다: edge에 rising/falling/both를 쓰면 GPIO 인터럽트가 걸릴 때마다 sysfs_notify가 불린다.

주의: sysfs GPIO(/sys/class/gpio)는 폐기 예정(deprecated) 인터페이스다. 새 코드는 GPIO character device(/dev/gpiochipN, libgpiod)를 쓴다. 거기서는 line request fd가 POLLIN으로 깨어나고 read()로 struct gpio_v2_line_event를 받는다(H4). 하지만 오래된 BSP·현장 스크립트에 sysfs GPIO가 아직 많고, "sysfs 파일은 POLLPRI"라는 규칙은 다른 sysfs 속성에도 똑같이 적용되므로 여기서 직접 확인한다.

VM에는 실제 GPIO 핀이 없으므로 커널의 gpio-sim(가상 GPIO 칩, configfs로 만든다)을 쓴다. pull 속성을 바꾸면 입력 라인 값이 바뀌고, 진짜 핀처럼 edge 인터럽트가 발생한다.

gpio-sim 칩의 base가 520이므로 라인 3 = 전역 GPIO 523이다(base 값은 환경마다 다르다). sysfs로 export하고 edge를 켠다.

이제 value 파일을 POLLPRI로 기다리는 코드다.

백그라운드로 실행해 두고, 셸에서 0.5초 간격으로 pull을 바꿔 "핀을 흔든다".

출력에서 볼 것: revents=0xa = POLLPRI(0x2) | POLLERR(0x8). 상승·하강 edge마다 한 번씩 깨어났고, 핀을 안 건드린 마지막은 3초 timeout이다. 깨어난 뒤에는 반드시 offset 0부터 다시 읽어야(lseek(fd,0,SEEK_SET)+read 또는 pread(…,0)) 다음 변화를 정상적으로 기다린다 — sysfs GPIO 문서가 요구하는 관례다.

같은 파일을 POLLIN으로 기다리면 어떻게 될까? 파이썬 한 줄로 확인한다.

출력에서 볼 것: 핀을 건드리지 않았는데도 즉시 POLLIN(1)이 나온다. sysfs 파일은 "언제나 읽을 수 있다"고 보고하기 때문이다. sysfs에서 POLLIN으로 기다리면 busy loop가 된다 — 현장에서 자주 보는 실수다.

실습 후 정리:

3.4 poll의 남은 한계#

poll은 select의 1024 제한과 재무장 문제를 없앴지만, 매 호출마다 배열 전체(N개)를 커널로 복사하고, 커널이 N개 fd의 .poll을 전부 호출하고, 리턴 후 유저가 N개 revents를 전부 훑는다. 준비된 fd가 1개여도 비용이 O(N)이다. fd가 10개면 문제가 없고, 수천 개면 문제가 된다(§9에서 측정).

4. epoll — "등록은 한 번, 대기는 준비된 것만"#

4.1 직관#

poll은 "매번 출석부 전체를 들고 교실에 가서 한 명씩 이름을 부르는" 방식이다. epoll은 "학생 명단을 한 번 등록해 두면, 손 든 학생이 스스로 준비 목록(ready list)에 이름을 적는" 방식이다. 선생님(epoll_wait)은 준비 목록만 본다. 펌웨어로 치면 매 루프마다 모든 주변장치의 상태 레지스터를 읽는 polling 대신, ISR이 pending 비트를 세워 두고 main loop는 pending 레지스터 하나만 읽는 구조다.

4.2 API 3개#

함수역할펌웨어 비유
epoll_create1(EPOLL_CLOEXEC)epoll 인스턴스 생성, fd 리턴event group 객체 생성
epoll_ctl(epfd, ADD/MOD/DEL, fd, &ev)관심 목록에 fd 추가·수정·삭제인터럽트 enable/mask 설정
epoll_wait(epfd, events, max, timeout)준비된 fd들을 배열로 받음WFI 후 pending 비트 읽기

struct epoll_event는 events(비트 mask)와 data(union: ptr, fd, u32, u64)로 되어 있다. data는 커널이 해석하지 않고 그대로 돌려주는 사용자 쿠키다. 보통 data.ptr에 "이 fd를 처리할 객체 포인터"를 넣어 두면, 깨어났을 때 테이블 검색 없이 바로 핸들러로 간다. 펌웨어의 인터럽트 벡터 테이블 엔트리 같은 것이다.

  • 3개를 등록했지만 epoll_wait는 준비된 2개만 돌려줬다. 유저가 N개를 훑을 필요가 없다.
  • data.ptr로 바로 struct source를 찾았다.
  • fdinfo의 tfd: 줄이 커널 관심 목록(나중에 볼 epitem)이다. events: 19(16진수) = EPOLLIN(0x1) | EPOLLERR(0x8) | EPOLLHUP(0x10) — 커널이 ERR/HUP을 자동으로 추가한다. data: 값은 우리가 넣은 포인터(주소는 실행마다 다르다).
  • flags: 02000002의 02000000이 O_CLOEXEC다.

4.4 Level-triggered vs Edge-triggered — 가장 중요한 함정#

  • Level-triggered (LT, 기본값): "지금 읽을 데이터가 남아 있으면" 매번 알려 준다. poll/select와 같은 의미다. 펌웨어의 level-sensitive 인터럽트(라인이 high인 동안 계속 pending)와 같다.
  • Edge-triggered (EPOLLET): "준비 상태가 새로 생겼을 때(새 데이터 도착 같은 변화) 한 번" 알려 준다. 펌웨어의 edge-sensitive 인터럽트와 같다. ISR에서 FIFO를 다 비우지 않으면 다음 edge가 올 때까지 남은 데이터가 방치되는 것과 똑같은 버그가 생긴다.

10바이트 센서 패킷이 도착했는데 핸들러가 4바이트씩만 읽는 상황을 세 가지 모드로 비교하는 코드다.

출력에서 볼 것: LT는 데이터가 남아 있는 한 세 번 깨워 줬다. ET + 조금만 읽기는 한 번만 깨우고 끝 — 남은 6바이트는 다음 패킷이 도착해야(새 edge) 비로소 처리된다. 센서라면 "가끔 한 샘플씩 늦게 나오는" 지연 버그, 소켓 서버라면 "가끔 응답이 멈추는" 버그로 나타나서 재현이 어렵다. 정답은 ET를 쓰면 fd를 non-blocking으로 두고 EAGAIN이 나올 때까지 다 읽는 것이다.

그림 3 — 위: LT는 버퍼 수위(level)가 0보다 큰 동안 매번 깨운다. 아래: ET는 "비어 있다가 데이터가 생긴" 순간(edge)에 한 번만 깨운다. 덜 읽으면 남은 데이터가 갇힌다.

언제 ET를 쓰나: 대용량 스트림을 처리하는 고성능 서버(nginx 등)에서 불필요한 재알림을 줄이려고, 또는 여러 스레드가 같은 epoll을 공유할 때(같은 이벤트가 여러 스레드에 중복 전달되는 것을 줄이려고). 센서 데몬 정도면 LT가 기본이고 안전하다. ET를 쓰려면 "non-blocking + EAGAIN까지 drain"을 규칙으로 지킨다.

4.5 EPOLLONESHOT — "한 번 알리고 꺼짐"#

여러 worker 스레드가 같은 epoll fd에서 epoll_wait를 할 때, 한 fd의 이벤트를 스레드 A가 처리하는 도중 같은 fd의 다음 이벤트가 스레드 B로 가면 같은 소켓을 두 스레드가 동시에 읽는 경쟁이 생긴다. EPOLLONESHOT을 주면 한 번 알린 뒤 그 fd는 비활성(disarm)되고, 처리 스레드가 끝난 뒤 EPOLL_CTL_MOD로 다시 켜야(re-arm) 다음 알림이 온다. 펌웨어로 치면 "ISR 진입 시 해당 인터럽트를 mask하고, 처리 끝나면 unmask"다.

출력에서 볼 것: 2)는 LT인데도 데이터가 남아 있는 상태에서 0을 돌려줬고, 3) 새 데이터가 와도 조용하다. 4) EPOLL_CTL_MOD로 재무장하자마자 다시 알린다. 재무장을 잊으면 그 fd는 영원히 조용해진다(흔한 버그).

4.6 EPOLLEXCLUSIVE — 짧게#

여러 스레드가 각자 자기 epoll 인스턴스에 같은 fd(대표적으로 listen 소켓)를 등록하면, 연결 하나가 들어올 때 모든 스레드가 깨어나는 thundering herd(우르르 깨어났다가 한 명만 일하고 나머지는 헛걸음)가 생긴다. EPOLLEXCLUSIVE(Linux 4.5+)를 EPOLL_CTL_ADD 때 주면 커널이 그 중 하나 이상(보통 하나) 만 깨운다. EPOLL_CTL_ADD에서만 쓸 수 있고 EPOLLONESHOT과 함께 쓸 수 없다. 센서 데몬에서는 거의 쓸 일이 없고, 멀티스레드 네트워크 서버 면접 질문에서 이름이 나오는 정도다.

4.7 epoll이 못 하는 것 — 일반 파일#

일반 파일을 epoll에 넣으면 어떻게 되는지 확인한다.

출력에서 볼 것: 일반 파일은 .poll 메서드가 없어서 epoll은 EPERM으로 거절하고, poll은 "항상 읽기·쓰기 가능(0x5 = POLLIN|POLLOUT)"으로 답한다. 디스크 I/O가 느려도 "준비됨"이라는 뜻이다. 디스크 읽기를 진짜 비동기로 하려면 스레드 풀이나 io_uring(§9.3)을 쓴다. 로그 파일 쓰기를 이벤트 루프 안에서 하면 SD 카드가 느린 순간 루프 전체가 멈춘다.

5. eventfd — 스레드·프로세스 사이의 "초인종"#

5.1 정의#

eventfd(initval, flags)는 커널 안의 64비트 카운터 하나를 fd로 감싼 것이다.

  • write(fd, &u64, 8): 카운터에 값을 더한다.
  • read(fd, &u64, 8): 카운터 값을 꺼내고 0으로 리셋. 카운터가 0이면 blocking(또는 EAGAIN).
  • EFD_SEMAPHORE 플래그: read가 1씩만 꺼낸다(세마포어처럼).
  • 카운터가 0보다 크면 POLLIN. 그래서 epoll에 넣을 수 있다.

펌웨어 비유: 다른 코어(또는 ISR)가 공유 변수에 count++ 하고 SEV/doorbell 인터럽트를 쏘는 것. 받는 쪽은 깨어나서 카운트를 원자적으로 가져가고 0으로 만든다.

pipe로도 같은 일(1바이트 쓰고 읽기, "self-pipe trick")을 할 수 있지만, eventfd는 fd 1개(pipe는 2개), 버퍼 대신 카운터 8바이트, 여러 번 써도 합쳐져서 넘칠 일이 없다는 장점이 있다.

5.2 예제 — 카운터 의미와 worker 스레드 알림#

출력에서 볼 것:

  • 일반 모드: 1+2+3이 합쳐져서 한 번의 read로 6이 나오고, 바로 다시 읽으면 0이라 EAGAIN.
  • 세마포어 모드: 1씩 세 번, 네 번째는 EAGAIN.
  • worker가 연달아 3번 알린 것은 메인 루프에서 한 번 깨어나 counter=3으로 받았다. 알림이 합쳐진다(coalescing). 그래서 eventfd는 "몇 번 왔는지"는 셀 수 있지만 "각 알림에 실린 내용"은 전달하지 못한다. 내용은 락으로 보호한 큐(링버퍼)에 넣고, eventfd는 "큐를 봐"라는 초인종으로만 쓴다 — 펌웨어의 "메일박스 데이터 + doorbell 인터럽트" 패턴 그대로다.

드라이버·커널 연결: eventfd는 커널 쪽에서도 신호용으로 쓰인다. KVM의 irqfd/ioeventfd, VFIO의 인터럽트 전달(VFIO_DEVICE_SET_IRQS로 eventfd를 등록하면 장치 인터럽트가 그 eventfd를 올린다)이 대표적이다. 유저스페이스 드라이버(VFIO, UIO 비교는 G 모듈)에서 "인터럽트 = eventfd가 읽을 수 있게 됨"이 된다.

6. timerfd — 타이머를 fd로#

6.1 정의#

  • it_value: 첫 만료까지 시간, it_interval: 이후 주기(0이면 한 번만).
  • 만료되면 fd가 POLLIN이 되고, read()는 8바이트 uint64_t = 마지막 read 이후 만료 횟수를 돌려준다.
  • 그 숫자가 1보다 크면 처리가 늦어서 tick을 놓쳤다(overrun) 는 뜻이다. 펌웨어로 치면 타이머 ISR에서 "missed tick counter"를 세는 것과 같다.
  • TFD_TIMER_ABSTIME을 주면 절대 시각 기준. CLOCK_REALTIME은 NTP·사용자가 시각을 바꾸면 영향을 받으므로 주기 샘플링에는 CLOCK_MONOTONIC을 쓴다(CLOCK_BOOTTIME은 suspend 시간도 센다).

왜 usleep() 루프 대신 timerfd인가: while(1){ work(); usleep(10000); }은 work 시간만큼 주기가 늘어나고(drift), 다른 이벤트와 같이 기다릴 수 없다. timerfd는 커널 hrtimer가 절대 주기로 만료되므로 drift가 없고, epoll에 넣어서 소켓과 같이 기다릴 수 있다.

6.2 예제 — 100 ms 샘플링과 overrun#

출력에서 볼 것:

  • tick 3 이후 350 ms 막혔더니, 다음 read에서 expirations=3(400·500·600 ms 만료가 합쳐짐). 놓친 샘플 수를 정확히 안다. 로그에 "missed N samples"를 남기거나, 센서 FIFO에서 그만큼 더 읽어 오는 데 쓴다.
  • tick 5는 707 ms에 왔다. 주기의 기준은 "처음 설정한 시각"이라서 지연 후에도 700 ms 격자로 다시 맞춰진다(drift 없음).
  • 각 tick이 정확히 100 ms 배수가 아니라 2~10 ms 늦다. 이 VM(Lima, 가상화된 타이머)과 일반 커널의 스케줄링 지연 때문이다. 실제 보드에서도 PREEMPT_RT가 아니면 수백 us~ms 지터가 있다. 정량 측정은 N3(cyclictest)에서 한다.

7. signalfd 미리보기 — 시그널도 fd로#

시그널 핸들러는 아무 때나 끼어들어서 그 안에서 쓸 수 있는 함수가 극히 제한된다(async-signal-safe, A6). 이벤트 루프에서는 시그널을 막아(block) 두고 signalfd로 "읽을 수 있는 이벤트"로 바꾸면, SIGTERM 처리도 평범한 핸들러 함수 안에서 printf·free·로그 쓰기를 마음대로 할 수 있다. systemd가 stop 때 보내는 SIGTERM을 받아 센서를 안전하게 끄는 데 쓴다.

출력에서 볼 것: SIGINT, SIGTERM이 프로세스를 죽이지 않고 읽을 수 있는 레코드(struct signalfd_siginfo, 128바이트)로 왔고, 보낸 프로세스(셸)의 pid까지 들어 있다. PID 값은 실행마다 다르다. sigprocmask를 빼먹으면 signalfd를 만들어도 기본 동작(종료)이 먼저 일어난다. 멀티스레드에서는 모든 스레드가 그 시그널을 block해야 한다(pthread_sigmask, 스레드 생성 전에) — 자세한 내용은 A6.

9. 확장성 측정 — select vs poll vs epoll#

9.1 실험 설계#

N개의 pipe를 만들어 모두 감시하되, 마지막 하나만 계속 활성으로 만든다(데이터 1바이트 쓰기 → 대기 → 1바이트 읽기). "센서·클라이언트는 많은데 대부분 조용하다"는 현실적인 상황이다. 한 번 반복(write + 대기 syscall + read)에 걸린 평균 시간을 잰다. select는 fd 번호가 1024를 넘으면 쓸 수 없으므로 그 구간은 -1로 표시한다.

N=5000이면 pipe 하나에 fd 2개라 fd가 10000개 넘게 필요하다. 기본 ulimit -n은 1024라서 먼저 올린다(하드 리밋 524288 이내).

열은 왼쪽부터 N, select, poll, epoll이고 단위는 us/반복이다. 세 번 반복해도 5% 안쪽으로 일정하다.

그림 5 — run 1 값을 log-log로 그린 것. select와 poll은 N에 비례(기울기 1)해서 N=5000에서 poll 한 번에 222 us, epoll은 N과 상관없이 약 0.56 us다. 빨간 점선은 select가 쓸 수 없어지는 지점(fd 번호 1024).

출력에서 볼 것:

  • N=10에서도 epoll이 약 2배 빠르지만 절대값은 1 us 남짓 차이다. fd 몇 개짜리 센서 데몬이라면 poll로 충분하다. epoll의 진짜 장점은 N이 클 때다.
  • poll은 N이 2배가 되면 시간도 정확히 약 2배(41.6 → 83.3 us). 1 fd당 약 40 ns — 매 호출 N개 .poll 호출 + wait queue 등록·해제 비용이다(§10에서 bpftrace로 센다).
  • select는 poll과 거의 같고, 유저가 매번 FD_SET N번을 하는 비용이 더해져 조금 더 느리다. N=500(가장 큰 read fd 1002)이 이 실험에서 쓸 수 있는 한계였다.
  • 측정 환경은 Apple Silicon Mac 위 Lima VM(aarch64, 4 vCPU)이라 절대값은 실제 보드와 다르다. 비율과 기울기를 기억한다.

9.3 그 다음: io_uring 한 문단#

epoll은 "준비됐다고 알려 주면 내가 read 한다"(readiness 모델)이다. io_uring(Linux 5.1+)은 "read를 미리 맡겨 두면 끝났을 때 결과를 준다"(completion 모델)이다. 유저와 커널이 공유하는 링버퍼 두 개(submission queue, completion queue)로 요청과 완료를 주고받아 syscall 횟수를 크게 줄이고, 일반 파일 I/O도 진짜 비동기로 할 수 있다. Don에게는 NVMe의 SQ/CQ 구조와 같은 모양이라고 보면 바로 이해될 것이다. 다만 보안 이슈로 일부 배포판·컨테이너 환경에서 비활성화되기도 하고, 임베디드 센서 데몬에서는 아직 epoll이 표준이다. 이 노트에서는 이름과 모델만 기억한다.

10. 커널 안에서는 무슨 일이 일어나나#

10.1 공통 기반: 모든 것은 드라이버의 .poll에서 시작한다#

select, poll, epoll 모두 결국 각 fd의 struct file을 찾아 file->f_op->poll(file, poll_table)을 호출한다(vfs_poll()). 이 .poll 메서드는 드라이버(또는 pipe·socket·timerfd 구현)가 제공하는 함수이고, 하는 일은 딱 두 가지다.

  1. poll_wait(filp, &dev->wq, wait): "이 장치의 상태가 바뀌면 깨워 달라"고 자기 wait queue를 poll_table에 알려 준다. 이 함수 자체는 잠들지 않는다. poll_table에 들어 있는 콜백(_qproc)을 불러서 wait queue에 엔트리를 하나 거는 것뿐이다.
  2. 지금 상태를 mask로 계산해 리턴한다(EPOLLIN | EPOLLRDNORM 등).

센서 드라이버라면 이렇게 생겼다(G6 미리보기 — 실행하지 않은 커널 코드 스케치다).

10.2 poll vs epoll 구조#

그림 6 — 왼쪽: poll은 매 호출마다 N개 전부를 등록·검사·해제한다. 오른쪽: epoll은 관심 목록(rb-tree)과 콜백을 미리 걸어 두고, 이벤트가 생긴 fd만 콜백이 ready list에 넣는다.

10.3 깨우기 경로 — IRQ에서 epoll_wait 리턴까지#

그림 7 — 드라이버는 "누가 기다리는지" 모른다. wait queue를 깨우기만 하면, 걸려 있는 엔트리의 콜백(pollwake 또는 ep_poll_callback)이 각자 알아서 처리한다.

조금 더 정확히, 현재 커널(fs/eventpoll.c, 6.x~7.0) 기준의 epoll 경로:

  1. epoll_ctl(ADD) → ep_insert(): struct epitem을 만들어 ep->rbr(rb-tree)에 넣고, ep_item_poll()로 대상 파일의 .poll을 한 번 호출한다. 이때 poll_table의 _qproc가 ep_ptable_queue_proc라서, 드라이버의 poll_wait()가 eppoll_entry(wait 함수 = ep_poll_callback)를 드라이버 wait queue에 건다. 이미 준비 상태면 바로 ready list에 넣는다.
  2. 드라이버가 wake_up(&dev->wq) → wait queue의 각 엔트리 함수 호출 → ep_poll_callback(): 해당 epitem을 ep->rdllist에 추가(이미 있으면 그대로)하고 ep->wq에서 자는 epoll_wait 호출자를 깨운다. 콜백은 wake_up 문맥(인터럽트 문맥일 수도 있다)에서 돌기 때문에 잠들지 않는 짧은 일만 한다(F2).
  3. epoll_wait → do_epoll_wait() → ep_poll(): rdllist가 비어 있으면 잠들고, 깨면 ep_send_events()가 rdllist의 각 epitem에 대해 .poll을 _qproc 없이 다시 불러 현재 mask를 확인하고 유저 배열에 복사한다.
  4. 여기서 LT/ET/ONESHOT 차이가 생긴다: LT면 epitem을 rdllist 뒤에 다시 넣는다(다음 epoll_wait에서 다시 .poll로 확인 → 데이터가 남아 있으면 또 보고). ET면 다시 넣지 않는다(다음 ep_poll_callback, 즉 다음 wake_up이 와야 다시 들어감). ONESHOT이면 이벤트 mask를 지워 콜백이 와도 무시하게 만든다. §4.4~4.5의 실험 결과가 바로 이 코드 몇 줄에서 나온다.

출력에서 볼 것(빈 줄은 지웠다):

  • ep_ptable_queue_proc 1000 = ADD 때 한 번씩 건 eppoll_entry. 두 모드 모두에 보이는 것은 이 프로그램이 셋업에서 모든 pipe를 epoll에도 등록했기 때문이다. 같은 이유로 poll 모드에서도 write가 wake_up을 할 때 ep_poll_callback이 불린다. 횟수(3000)는 write 횟수(2000)보다 조금 많은데, pipe 구현이 epoll 사용자를 위해 추가 wakeup을 하는 등 세부 구현에 따른 것이라 여기서는 "N에 비례하지 않는다"는 점만 본다.
  • bpftrace 프로브를 붙인 상태라 시간(282 us, 1.14 us)은 §9보다 크다. 프로브 오버헤드다.

11.1 센서 키트 메인 데몬#

예를 들어 센서 키트라면 메인 데몬 하나가 이런 fd들을 epoll에 넣는다.

센서의 DRDY 핀이나 E-stop 버튼을 유저스페이스에서 받을 때, 레거시 BSP는 §3.3의 sysfs GPIO + POLLPRI를 쓰고, 최신 코드는 libgpiod(gpiod_line_request_get_fd()로 얻은 fd를 epoll에 넣고 POLLIN → 이벤트 read)를 쓴다. 어느 쪽이든 유저스페이스 경로는 IRQ → 커널 → wake_up → 스케줄링 → 유저 깨어남이라 수십 us~수 ms의 지연과 지터가 있다. 하드 실시간 응답(모터 즉시 정지)은 하드웨어나 MCU(N4)가 맡고 Linux는 기록·상위 판단만 하는 설계가 일반적이다.

11.3 systemd watchdog을 timerfd로#

systemd 서비스에 WatchdogSec=2s를 걸면, 데몬은 그 절반 주기 정도로 sd_notify("WATCHDOG=1")을 보내야 한다(L1). timerfd 1초 주기를 이벤트 루프에 넣고 그 핸들러에서 킥한다. 이렇게 하면 이벤트 루프가 어딘가에서 막혔을 때만 킥이 멈춰서 systemd가 재시작해 준다 — 별도 스레드에서 킥하면 메인 루프가 죽어도 킥이 계속되어 watchdog이 무의미해진다. 펌웨어에서 "watchdog은 main loop에서만 킥한다"는 원칙과 같다.

11.4 overrun 로그로 지연 문제 잡기#

§6의 expirations > 1을 카운터로 남겨 두면, 현장에서 "가끔 IMU 데이터가 튄다"는 리포트가 왔을 때 "그 시각에 루프가 300 ms 막혔다"를 바로 증명할 수 있다. 그 다음 strace -T(syscall 소요 시간)나 perf trace로 어느 핸들러가 막았는지 찾는다(M 모듈). Don이 SSD 펌웨어에서 latency outlier를 타임스탬프 로그로 추적하던 방식과 같다.

13. 면접에서 이렇게 말한다#

Q. What is the difference between select, poll and epoll?

A. 세 가지 모두 여러 fd 중 준비된 것을 기다리는 방법이다. select는 1024비트 고정 비트맵이라 fd 번호 제한이 있고 매번 다시 채워야 한다. poll은 배열이라 제한이 없지만 매 호출마다 N개를 커널에 복사하고 N개 모두 .poll을 부른다. epoll은 관심 목록을 커널에 한 번 등록하고, 이벤트가 생긴 fd만 콜백이 ready list에 넣기 때문에 대기 비용이 준비된 fd 수에만 비례한다. 직접 재 보니 fd 5000개 중 하나만 활성일 때 poll은 한 번에 약 220 us, epoll은 약 0.6 us였다.

select uses a fixed 1024-bit bitmap that you rebuild on every call; poll takes an array, so no fd limit, but it still copies all N entries and calls every file's poll method on each call, so it's O(N). epoll registers the interest set once in the kernel and installs a callback on each file's wait queue; when a file becomes ready, the callback puts it on a ready list, so epoll_wait costs O(ready), not O(N). In my own measurement with 5,000 pipes and one active, poll took about 220 microseconds per wake-up and epoll about 0.6, flat.

꼬리 질문: "그럼 fd가 5개면?" → poll로 충분하다, 차이가 1 us 미만이고 코드가 단순하다.

Q. Explain level-triggered versus edge-triggered epoll. What's the classic bug?

A. LT는 데이터가 남아 있는 동안 매번 알려 주고, ET는 상태가 바뀔 때(새 데이터 도착) 한 번만 알려 준다. 펌웨어의 level/edge 인터럽트와 같다. 고전적인 버그는 ET에서 버퍼를 다 비우지 않는 것이다. 남은 데이터는 다음 패킷이 올 때까지 알림이 없어서 지연이나 멈춤이 생긴다. 그래서 ET는 반드시 non-blocking fd로 EAGAIN까지 읽는다.

Level-triggered reports the fd as long as the condition holds, like a level-sensitive interrupt. Edge-triggered reports only on a transition, like an edge-sensitive interrupt. The classic bug is using edge-triggered mode and only reading part of the data: there's no new edge, so the remaining bytes sit there until the next packet arrives. The rule is: with EPOLLET, make the fd non-blocking and drain until EAGAIN. For a sensor daemon I default to level-triggered.

Q. How would you structure a Linux daemon that handles an IMU, a LiDAR UDP stream, a periodic timer, and clean shutdown?

A. 단일 이벤트 루프로 설계한다. IMU는 IIO 버퍼 fd, LiDAR는 UDP 소켓, 주기는 timerfd, 종료는 SIGTERM을 block하고 signalfd로 받는다. 전부 epoll에 넣고 data.ptr로 핸들러를 찾는다. 핸들러는 짧게 유지하고, 무거운 처리는 worker 스레드로 보낸 뒤 eventfd로 완료를 받는다. timerfd의 만료 카운트로 overrun을 감지해 로그로 남기고, systemd watchdog 킥도 이 루프 안에서 한다.

One epoll-based event loop. The IMU is an IIO buffer fd, the LiDAR is a non-blocking UDP socket, the periodic work is a timerfd on CLOCK_MONOTONIC, and SIGTERM is blocked and read through a signalfd so shutdown is just another event. Each registration carries a pointer to its handler in data.ptr. Handlers never block; heavy work goes to a worker thread that signals completion through an eventfd. I log timerfd overruns, the expiration count above one, and kick the systemd watchdog from inside the loop so a stalled loop actually triggers a restart.

Q. How does a character device driver support poll/select/epoll?

A. file_operations에 .poll을 구현한다. 그 안에서 poll_wait()로 장치의 wait queue를 등록하고, 지금 상태를 mask(EPOLLIN | EPOLLRDNORM 등)로 리턴한다. poll_wait는 잠들지 않는다. 데이터가 생기면 IRQ 경로에서 같은 wait queue에 wake_up_interruptible()을 부른다. 그러면 select/poll은 다시 .poll을 불러 확인하고, epoll은 ep_poll_callback이 해당 항목을 ready list에 넣는다. blocking read도 같은 wait queue를 쓴다.

You implement the poll method in file_operations. It calls poll_wait() with the device's wait queue, which doesn't sleep, it just registers the caller, and then returns the current readiness mask, for example EPOLLIN | EPOLLRDNORM when the FIFO isn't empty. When new data arrives, the interrupt path calls wake_up_interruptible() on that same wait queue. For select and poll that wakes the sleeping task, which re-polls; for epoll the wait-queue entry's callback, ep_poll_callback, moves the item onto the ready list. The blocking read path sleeps on the same queue.

꼬리 질문: "poll이 항상 EPOLLIN을 리턴하면?" → 유저 epoll 루프가 busy loop가 된다. mask는 반드시 실제 상태를 반영해야 한다.

Q. Why use eventfd instead of a pipe to wake up an event loop from another thread?

A. eventfd는 커널의 64비트 카운터 하나라서 fd 하나, 버퍼 할당 없음, 여러 번 써도 합쳐져서 넘치지 않는다. pipe는 fd 두 개에 버퍼가 차면 writer가 막힐 수 있다. eventfd는 알림 횟수만 전달하므로 실제 데이터는 락으로 보호한 큐에 넣고, eventfd는 "큐 확인해"라는 초인종으로 쓴다.

An eventfd is a single 64-bit counter in the kernel: one fd instead of two, no buffer, and multiple writes coalesce, so it can't fill up and block the writer the way a pipe can. It only carries a count, so I put the actual work items in a locked queue and use the eventfd purely as the doorbell, the same mailbox-plus-doorbell pattern I used between cores in firmware.

Q. How do you run a periodic 100 Hz task in user space, and how do you detect if you missed deadlines?

A. usleep 루프는 처리 시간만큼 주기가 밀린다. timerfd를 CLOCK_MONOTONIC, interval 10 ms로 만들고 epoll에 넣는다. read하면 마지막 read 이후 만료 횟수가 오는데, 1보다 크면 그만큼 tick을 놓친 것이다. 이걸 카운터로 남기면 현장에서 지연 문제를 증명할 수 있다. 지터 자체가 문제면 SCHED_FIFO, CPU 격리, PREEMPT_RT를 검토한다.

A sleep loop drifts by the processing time. I use a timerfd on CLOCK_MONOTONIC with a 10 ms interval inside the event loop. Reading it returns the number of expirations since the last read, so anything above one is a missed period, and I count and log it. If the jitter itself is the problem, the next steps are SCHED_FIFO for the thread, CPU isolation, and a PREEMPT_RT kernel, measured with cyclictest.

Q. Can you use epoll on a regular file?

A. 안 된다. 일반 파일은 .poll이 없어서 epoll_ctl이 EPERM을 리턴하고, poll은 항상 준비됨으로 답한다. 디스크 I/O는 "준비" 개념이 없기 때문이다. 이벤트 루프에서 파일 I/O가 필요하면 worker 스레드에 맡기거나 io_uring을 쓴다.

No. Regular files don't implement a poll method, so epoll_ctl returns EPERM, and poll just reports them as always readable and writable. Disk I/O has no readiness concept. If the loop needs file I/O, I hand it to a worker thread, or use io_uring, which is a completion model rather than a readiness model, similar to NVMe submission and completion queues.

Q. What is EPOLLONESHOT for, and what is EPOLLEXCLUSIVE?

A. ONESHOT은 여러 스레드가 한 epoll을 공유할 때 같은 fd가 동시에 두 스레드에 배달되는 것을 막는다. 한 번 알리면 꺼지고, 처리 스레드가 EPOLL_CTL_MOD로 다시 켠다. EXCLUSIVE는 여러 epoll 인스턴스가 같은 fd를 기다릴 때 전부 깨어나는 thundering herd를 줄인다(4.5+).

EPOLLONESHOT disables the fd after one event, so when several threads share one epoll set, the same socket isn't handed to two threads at once; the worker re-arms it with EPOLL_CTL_MOD when it's done. EPOLLEXCLUSIVE, since 4.5, is for the opposite layout, many epoll instances watching the same fd like a listening socket, and it avoids waking all of them for one event.

14. 직접 해보기#

  1. (개념) select가 nfds 인자로 "최대 fd + 1"을 받는 이유는 무엇이고, fd 3 하나만 감시하더라도 fd 1000을 열어 둔 프로세스라면 무엇이 비효율적인가? 정답/힌트: 커널은 0..nfds-1 비트를 다 훑는다. 감시 fd가 큰 번호면 앞쪽 빈 비트까지 스캔한다(실제 감시 fd 수와 무관하게 maxfd에 비례).
  1. (코드) ex5를 고쳐 ET 모드에서 "4바이트씩 읽되 drain하지 않는" 대신, 0.05초 뒤에 1바이트를 더 write하면 어떻게 되는지 확인하라. 깨어났을 때 남은 바이트 수는? 정답/힌트: 새 write가 새 edge를 만들어 다시 깨어난다. 이때 남은 데이터는 6+1=7바이트 — "늦게라도 처리되지만 지연된다"는 ET 버그의 실제 모습이다.
  1. (코드) ex9에 §7의 signalfd를 추가해서 kill -TERM <pid>로 루프를 깔끔하게 끝내도록 만들어라. stdin quit과 같은 종료 경로를 타게 하라. 정답/힌트: pthread_create 전에 sigprocmask(SIG_BLOCK)(스레드가 마스크를 상속), watch(sfd, SRC_SIGNAL), 핸들러에서 struct signalfd_siginfo를 읽고 running = 0.
  1. (관찰) ex9 실행 중에 cat /proc/<pid>/fdinfo/<timerfd>를 여러 번 찍어 it_value가 줄어드는 것과 ticks를 관찰하라. 루프가 timerfd를 읽지 않게(그 case를 주석 처리) 바꾸면 ticks와 CPU 사용률은 어떻게 되나? 정답/힌트: ticks가 계속 증가하고, LT라 epoll_wait가 즉시 리턴해서 CPU 100% busy loop가 된다(top으로 확인).
  1. (관찰) strace -c ./ex11 2000 1과 strace -c ./ex11 2000 2(ulimit -n 올린 뒤)를 비교하라. syscall 횟수는 같은데 왜 시간은 수십 배 차이 나나? 정답/힌트: syscall 횟수는 같고(ppoll vs epoll_pwait 각 1000번) 한 번의 커널 내부 일의 양이 다르다(N개 .poll vs ready 1개). §10.4의 bpftrace 결과가 그 내부다.
  1. (설계) 카메라 30 fps(V4L2), IMU 1 kHz(IIO, 워터마크 32샘플), LiDAR 10 Hz UDP를 한 데몬에서 받는다. 각 fd를 LT/ET 중 무엇으로, 각 핸들러에서 한 번에 얼마나 읽을지 정하고 이유를 써라. 정답/힌트: 기본 LT. IMU는 워터마크 단위로 깨어나므로 FIFO에 있는 만큼 읽기, UDP는 recvmmsg로 여러 패킷 한 번에. 카메라 DQBUF 후 처리는 worker로 넘기고 버퍼 반환(QBUF)은 eventfd로 돌아와서.
  1. (관찰) ex3을 sysfs GPIO 대신 다른 sysfs 속성에도 적용해 보라. 예: gpio-sim의 sim_gpioN/value(출력 라인) 또는 /proc/self/mounts(마운트 변화 시 POLLPRI/POLLERR, proc(5) 참고). 정답/힌트: /proc/self/mounts는 mount/umount가 일어날 때 poll이 POLLERR|POLLPRI로 깨어난다. sudo로 tmpfs를 마운트해 보며 확인한다.

16. 요약 & 체크리스트#

스레드 하나가 여러 이벤트 소스를 기다려야 할 때, Linux는 모든 소스를 fd로 만들고(소켓·장치는 원래 fd, 타이머는 timerfd, 스레드 알림은 eventfd, 시그널은 signalfd) select/poll/epoll로 한 번에 기다린다. select는 1024 제한과 재무장 비용, poll은 매 호출 O(N) 비용이 있고, epoll은 관심 목록을 커널에 한 번 등록한 뒤 드라이버 wait queue에 건 콜백(ep_poll_callback)이 ready list를 채우므로 대기 비용이 준비된 fd 수에만 비례한다 — 직접 측정에서 N=5000일 때 poll 222 us, epoll 0.56 us였다. LT는 안전한 기본값이고, ET는 non-blocking + EAGAIN까지 drain을 지켜야 한다. 이 모든 것은 드라이버의 .poll(= poll_wait + mask)과 IRQ 경로의 wake_up 위에 서 있고, 이것이 G6에서 직접 구현할 부분이다.
