A9. 네트워크 소켓 — LiDAR UDP, 원격 툴 TCP, CAN, netlink가 전부 같은 "socket fd"다

195분 읽기1602줄60개 절

이 노트를 다 읽으면: TCP 서버/클라이언트와 UDP 수신기를 직접 짜고 ss·tcpdump로 상태를 읽을 수 있다 · 스트림 프레이밍과 UDP 손실(SO_RCVBUF, RcvbufErrors)을 측정으로 설명할 수 있다 · SocketCAN·AF_PACKET·netlink(uevent)가 같은 소켓 API라는 것을 코드로 보일 수 있다 · socket()에서 net_device 드라이버까지 커널 경로를 그릴 수 있다 왜 필요한가: "LiDAR 패킷이 가끔 빠진다", "CAN 모터 명령을 어떻게 보내나", "서버 재시작하면 bind가 실패한다"는 Embedded Linux 현장과 면접의 단골 장면이다 Don 기준 난이도: 바이트 순서·링버퍼·DMA·패킷 개념은 이미 안다 / BSD 소켓 API, TCP 상태 머신, 커널 네트워크 스택(sk_buff, NAPI), netlink는 새로 배운다 선행 노트: A1(fd, VFS), A3(blocking vs non-blocking), A4(epoll), A7(UNIX 소켓)

0. 큰 그림 — 이게 왜 필요한가#

센서 키트를 Linux SoC(i.MX8, AM62, Jetson Orin)에 올린다고 하자. 데이터가 들어오고 나가는 길을 세어 보면 이렇다.

  • LiDAR는 이더넷으로 초당 수천~수만 개의 UDP 패킷을 쏜다.
  • 원격 진단 툴, ROS 노드, 웹 설정 페이지는 TCP로 붙는다.
  • 모터 컨트롤러·BMS는 CAN 버스에 있다. Linux에서는 이것도 소켓(SocketCAN)으로 다룬다.
  • ip link set can0 up 같은 설정, 장치 hotplug 알림(udev)은 netlink 소켓으로 커널과 대화한다.
  • 같은 보드 안의 서비스끼리는 UNIX 도메인 소켓(A7)을 쓴다.
  • 배선 문제를 볼 때는 tcpdump가 AF_PACKET 소켓으로 이더넷 프레임을 통째로 받는다.

즉 "소켓"은 TCP/IP 전용 API가 아니라, "커널 안의 어떤 통신 엔드포인트를 fd 하나로 잡는 범용 손잡이"다. 손잡이 모양(socket(), bind(), send(), recv(), epoll)은 같고, 첫 인자 address family(AF_...)만 바꾸면 반대편이 IP 스택이 되기도, CAN 코어가 되기도, 커널 자신이 되기도 한다.

그림 1 — 센서 키트의 여러 통신 경로가 모두 같은 소켓 fd API를 지나 각자의 커널 서브시스템과 드라이버로 내려간다.

bare-metal 비유로 말하면, 펌웨어에서 Ethernet MAC, CAN 컨트롤러, 호스트 메일박스마다 서로 다른 드라이버 API를 불렀던 것을 Linux는 "전부 소켓 하나의 모양으로 통일"해 놓았다. 앱은 write()만 하면 되고, 패킷을 DMA 디스크립터에 올리는 일은 커널 드라이버(I6)가 한다.

이 노트는 VM(Lima, aarch64)에서 직접 돌린 결과로 진행한다. 커널 버전은 다음과 같다.

1. 소켓도 fd다#

1.1 직관#

A1에서 fd는 "커널이 들고 있는 핸들 테이블의 인덱스"라고 했다. 소켓도 똑같다. socket()이 돌려주는 정수는 open()이 돌려주는 정수와 같은 테이블에 들어간다. 그래서 소켓에 read()·write()·close()·epoll이 그대로 된다. 차이는 그 fd 뒤의 struct file이 디스크 inode가 아니라 struct socket을 가리킨다는 것뿐이다.

1.2 정의#

  • domain (address family): AF_INET(IPv4), AF_INET6, AF_UNIX, AF_PACKET, AF_CAN, AF_NETLINK …
  • type: SOCK_STREAM(연결형 바이트 스트림), SOCK_DGRAM(메시지 단위), SOCK_RAW(프로토콜 헤더까지 직접), SOCK_SEQPACKET(연결형 + 메시지 경계)
  • protocol: 보통 0(기본값). raw 계열에서는 의미가 있다(CAN_RAW, NETLINK_ROUTE, htons(ETH_P_ALL)).

AF_와 PF_(protocol family)는 Linux에서 같은 값이다. 둘 다 보게 된다.

1.4 함정#

  • 소켓 fd도 fork()/exec()에서 상속된다. 데몬이 자식 프로세스를 띄울 때 리스닝 소켓이 새어 나가지 않게 SOCK_CLOEXEC를 type에 OR한다.
  • lseek()은 소켓에서 ESPIPE로 실패한다. 파일처럼 보이지만 위치 개념이 없다.

2. TCP — 서버와 클라이언트의 수명주기#

2.1 직관#

TCP는 "양쪽이 합의한 신뢰성 있는 바이트 파이프"다. 순서 보장, 재전송, 흐름 제어를 커널이 다 해 준다. 대신 시작(3-way handshake)과 끝(FIN 교환)이 있고, 그 사이 상태를 커널이 상태 머신으로 관리한다. SSD 펌웨어의 NVMe 큐 쌍처럼 "양쪽이 상태를 공유한 채널"이라고 보면 된다.

UDP는 반대로 "주소를 붙인 메시지를 던지는 것"이다. 연결도, 재전송도, 순서 보장도 없다. 그래서 단순하고 지연이 작다.

그림 2 — TCP는 서버가 socket → bind → listen → accept, 클라이언트가 socket → connect 순서로 연결을 만든다. UDP는 bind한 소켓에 sendto/recvfrom으로 메시지를 바로 주고받는다.

2.5 함정#

  • listen()의 backlog는 "동시 연결 수 제한"이 아니다. handshake가 끝났지만 아직 accept 안 된 연결의 큐 길이다. 실제 상한은 net.core.somaxconn으로 잘린다.
  • connect()는 TCP에서 handshake 완료까지 블록된다. 상대 장비가 꺼져 있으면 SYN 재전송 때문에 기본 설정에서 2분 넘게 걸릴 수 있다. 센서 키트에서는 non-blocking connect + epoll 타임아웃(7절)이나 TCP_USER_TIMEOUT을 쓴다.
  • 상대가 닫은 소켓에 write()하면 SIGPIPE로 프로세스가 죽는다(A6). 서버는 signal(SIGPIPE, SIG_IGN) 또는 send(..., MSG_NOSIGNAL)을 쓴다.

3. 바이트 순서 — htons/htonl은 어디에 쓰나#

Don은 엔디언을 이미 안다. 소켓에서 기억할 규칙만 정리한다.

  • 네트워크 바이트 순서 = big-endian. IP 헤더, TCP/UDP 포트, IP 주소는 big-endian으로 선(wire)에 실린다.
  • struct sockaddr_in의 sin_port와 sin_addr는 이미 네트워크 순서로 담는 필드다. 그래서 htons(5000), htonl(INADDR_ANY)를 넣는다. aarch64·x86은 little-endian이므로 실제로 바이트가 뒤집힌다.
  • h=host, n=network, s=16비트, l=32비트. ntohs/ntohl은 반대 방향이다. 64비트는 htobe64()/be64toh()(<endian.h>)를 쓴다.
  • 내 애플리케이션 프로토콜의 정수 필드(예제 3의 길이 접두, 예제 4의 seq 번호)도 바이트 순서를 정해 두어야 한다. 관례는 big-endian. 센서 벤더 프로토콜은 little-endian인 경우도 많으니(LiDAR 데이터 패킷이 대표적) 데이터시트를 확인한다.

함정 두 개:

  • netlink 메시지는 host 순서다(struct nlmsghdr). 커널과 같은 장비 안에서만 오가기 때문이다. 습관적으로 htonl을 붙이면 깨진다.
  • SocketCAN의 can_id도 host 순서 정수다. CAN 버스 위의 비트 순서는 컨트롤러 하드웨어가 처리한다.

strace가 sin_port=htons(5000)처럼 보여 주는 것도 메모리에 big-endian으로 들어 있다는 표시다.

4. TCP는 스트림 — 메시지 경계가 없다#

4.1 직관#

TCP에서 write() 세 번이 read() 세 번으로 나뉘어 오리라는 보장이 전혀 없다. 커널 입장에서 TCP 소켓은 UART FIFO 같은 바이트 열이다. UART로 패킷을 받을 때 SOF·길이·CRC로 프레임을 직접 잘랐던 것처럼, TCP 위에서도 애플리케이션이 프레이밍을 해야 한다.

그림 4 — TCP는 write 경계를 지우고 바이트 열만 전달하므로 길이 접두 같은 프레이밍이 필요하다. UDP는 sendto 하나가 recvfrom 하나로 온다.

4.4 함정#

  • 길이 필드를 그대로 믿고 malloc(len) 하면 깨진 패킷 하나로 메모리를 다 쓴다. 예제 3처럼 상한(len >= sizeof buf)을 검사한다.
  • write()도 부분 전송될 수 있다(특히 non-blocking 소켓에서 송신 버퍼가 찼을 때). 리턴값이 요청 길이보다 작으면 나머지를 다시 보내야 한다.
  • 구조체를 write(fd, &s, sizeof s)로 통째로 보내면 패딩·엔디언·컴파일러 차이 때문에 다른 보드에서 깨진다. 필드별로 직렬화한다.

5. UDP — 센서·LiDAR 스트림과 패킷 손실#

5.1 직관#

LiDAR는 보통 UDP로 데이터를 쏜다. 예를 들어 Velodyne VLP-16은 1206바이트 데이터 패킷을 초당 약 754개 보낸다(단일 리턴 모드 기준, 장비 매뉴얼 값). 고해상도 LiDAR는 이보다 훨씬 많다. UDP를 쓰는 이유는 명확하다. 늦게 온 포인트 클라우드는 쓸모가 없으니 재전송보다 최신 데이터가 중요하다.

대가는 손실이다. 그리고 손실은 케이블이 아니라 수신 장비 안에서 가장 흔하게 일어난다. 앱이 잠깐 느려지면 소켓 수신 버퍼가 차고, 커널은 새 패킷을 조용히 버린다. 펌웨어에서 DMA 링이 꽉 찼을 때 RX overrun 카운터만 올라가고 프레임이 사라지던 것과 같은 그림이다.

그림 5 — 커널은 softirq에서 UDP 패킷을 소켓 수신 큐에 넣기 전에 큐의 메모리 합(truesize)이 sk_rcvbuf를 넘는지 검사하고, 넘으면 버리고 카운터만 올린다.

5.2 예제 4 — LiDAR 흉내 송신기와 느린 수신기#

무엇을 확인하는가: 수신기의 패킷당 처리 시간과 SO_RCVBUF에 따라 손실이 어떻게 변하는지 측정한다. 패킷 앞 4바이트에 seq 번호를 넣어 빠진 개수를 세고, SO_RXQ_OVFL 옵션으로 커널이 센 drop 수도 함께 받는다.

SO_RCVBUFFORCE는 net.core.rmem_max 상한을 무시하고 버퍼를 키우는 옵션으로 CAP_NET_ADMIN이 필요하다(그래서 버퍼 실험은 sudo로 돌렸다). 일반 SO_RCVBUF는 rmem_max에서 잘린다. VM의 기본값은 이렇다.

5.3 커널 카운터로 손실 보기#

먼저 수신기를 일부러 아주 느리게(패킷당 100 ms) 만들고 50개, 이어서 400개를 쏜 뒤 ss -u -m과 /proc/net/udp를 봤다.

(수신기의 마지막 요약 줄은 송신을 두 번 하면서 seq가 0부터 다시 시작해 의미가 없어 생략했다.)

출력에서 볼 것:

  • skmem:(r…, rb…, d…): r=현재 수신 큐가 쓰는 메모리, rb=수신 버퍼 한도(sk_rcvbuf), d=이 소켓에서 버려진 패킷 수.
  • 두 번째 캡처에서 r211968은 정확히 92 × 2304다. 1206바이트 payload 하나가 커널 안에서는 sk_buff 헤더·정렬 오버헤드를 포함해 truesize 2304바이트를 차지한다. 그래서 기본 버퍼 212992바이트에 1206바이트 패킷은 약 92개만 들어가고, 나머지 358개는 버려졌다(d358). 버퍼 크기 ÷ payload 크기로 계산하면 2배 가까이 과대평가한다. 이 비율(truesize/payload)은 드라이버와 MTU에 따라 다르다.
  • /proc/net/udp의 1770은 포트 6000의 16진수, 0100007F는 127.0.0.1을 little-endian 정수로 찍은 것이다(3절의 바이트 순서가 여기서도 보인다). 맨 끝 drops 열이 같은 358이다.

시스템 전체 카운터는 /proc/net/snmp의 Udp: 줄에 있다. 처리 150 µs 실험 전후로 찍은 것이다.

RcvbufErrors가 6699, 앱이 seq로 센 손실은 6643이다. 차이 56개는 마지막으로 받은 패킷 뒤에서 버려진 꼬리라 seq 비교로는 안 보인다. SO_RXQ_OVFL 값도 "패킷을 받을 때 함께 오는 누적 drop 수"라 꼬리는 못 센다. 현장에서는 이 세 숫자(앱 seq, 소켓 drops, 시스템 RcvbufErrors)를 같이 본다. netstat -su나 nstat으로도 같은 카운터를 볼 수 있다.

5.4 측정 1 — 처리 시간이 패킷 간격을 넘으면#

송신 10,000 pps(100 µs마다 1개, 1206바이트, 2만 개), 기본 버퍼 212992에서 수신기의 패킷당 처리 시간 work_us만 바꿨다.

그림 6 — 위 출력을 손실률(1 − recv/20000)로 그린 것. 처리 시간이 패킷 간격(100 µs)을 넘는 순간부터 손실이 이론선 1 − 100/work를 따라 늘어난다.

출력에서 볼 것: 90 µs까지는 손실 0, 100 µs에서 이미 2.2%다. recvmsg() 자체 비용이 처리 시간에 더해져 실제 처리율이 송신률보다 살짝 낮아졌기 때문이다. 150 µs면 처리율 6,667 pps이므로 이론 손실 33%, 측정 39.7%다. 평균 처리율이 도착률보다 낮으면 버퍼를 아무리 키워도 손실은 결국 생긴다. 버퍼는 시간을 벌어 줄 뿐이다. 해결은 처리 자체를 빠르게 하거나, 수신 스레드는 받기만 하고 처리를 다른 스레드로 넘기거나(링버퍼), recvmmsg()로 syscall 비용을 줄이는 것이다.

5.5 측정 2 — burst 트래픽에는 버퍼 크기가 답#

이번에는 평균 10,000 pps는 같지만 400개를 몰아서 보내고 40 ms 쉬는 burst 패턴, 처리 50 µs(평균 처리 능력 20,000 pps로 충분)에서 SO_RCVBUF만 바꿨다. 실제 LiDAR·카메라도 회전 각도나 프레임 단위로 몰려 오는 경우가 많다.

그림 7 — 같은 평균 속도라도 burst를 통째로 담을 버퍼(400 × 2304 = 921,600바이트 이상)가 있어야 손실이 0이 된다. 실효 512K에서는 burst마다 약 230개만 살아남았다.

출력에서 볼 것:

  • 요청값의 2배가 effective로 돌아온다. 커널이 sk_buff 오버헤드 몫으로 2배를 잡는다고 man 7 socket에 명시되어 있다. ss -m의 rb도 이 2배 값이다.
  • 계산이 맞아떨어진다. burst 400개 × truesize 2304 = 921,600바이트 < 1,048,576(실효 1M)이라 손실 0. 실효 512K(524,288 ÷ 2304 ≈ 227개)에서는 burst 50번 × 약 231개 = 11,568개만 받았다.
  • 현장 규칙: "burst 크기 × truesize"로 버퍼를 잡고, rmem_max도 그만큼 올린다. 일반 사용자 프로세스는 SO_RCVBUF가 rmem_max에서 잘리므로 sysctl -w net.core.rmem_max=...(또는 /etc/sysctl.d/)가 짝으로 따라간다.

5.6 멀티캐스트 짧게#

여러 소비자(인식 노드, 로거, 시각화)가 같은 센서 스트림을 받아야 하면 LiDAR를 멀티캐스트 그룹(예: 239.x.x.x)으로 설정하기도 한다. 수신 측은 IP_ADD_MEMBERSHIP으로 그룹에 가입하고, 커널은 IGMP report를 보내 스위치에 알린다. socat으로 확인했다.

출력에서 볼 것: 가입하자 인터페이스의 멀티캐스트 목록에 239.1.1.1이 생기고, IGMPv3 report가 224.0.0.22로 나간다. 같은 장비가 보낸 멀티캐스트를 자기가 받은 것은 IP_MULTICAST_LOOP 덕분이다. (tcpdump의 [|rx]는 포트 7000을 다른 프로토콜로 추측해 해석하다 잘린 표시라 무시해도 된다.) 실제 망에서는 스위치의 IGMP snooping 설정에 따라 그룹 트래픽이 모든 포트로 퍼질 수 있다는 점이 현장 이슈다.

7. non-blocking 소켓과 epoll#

A4에서 epoll을 "여러 인터럽트 소스를 한 번에 기다리는 이벤트 그룹"이라고 했다. 소켓은 epoll의 가장 대표적인 사용처다. 센서 게이트웨이 데몬 하나가 LiDAR UDP 소켓, CAN 소켓, 진단 TCP 리스너, 여러 TCP 클라이언트를 스레드 하나로 다룰 수 있다.

규칙 세 가지:

  • 소켓을 non-blocking으로 만든다(SOCK_NONBLOCK 또는 fcntl(O_NONBLOCK)). accept4(..., SOCK_NONBLOCK)로 받은 연결도 바로 non-blocking이 된다.
  • 이벤트가 오면 EAGAIN이 나올 때까지 다 비운다(listen 소켓은 쌓인 연결을 다 accept, 데이터 소켓은 다 read). edge-triggered(EPOLLET)라면 필수다.
  • read()가 0이면 상대가 FIN을 보낸 것이다. EPOLLRDHUP로 반쯤 닫힘을 따로 알 수도 있다.

7.1 예제 6 — 스레드 1개로 TCP 클라이언트 3개 처리#

출력에서 볼 것: 세 클라이언트의 데이터가 섞여 처리되지만 각자 자기 응답(대문자 echo)을 받았다. 서버는 스레드 하나, 블록되는 곳은 epoll_wait() 하나뿐이다. 순서는 실행마다 다르다. fd 4는 epoll 인스턴스 자신이다.

함정: non-blocking connect()는 EINPROGRESS를 리턴한다. 그 fd를 EPOLLOUT으로 기다렸다가 getsockopt(SO_ERROR)로 성공 여부를 확인해야 한다. 바로 write하면 안 된다.

8. 자주 쓰는 소켓 옵션#

8.1 예제 7 — 서버 재시작 시 EADDRINUSE와 SO_REUSEADDR#

출력에서 볼 것: 첫 번째 경우는 새 서버가 옵션을 켜도 실패했다. Linux는 TIME_WAIT 소켓 쪽에도 reuse 플래그가 있어야 재사용을 허락한다(TIME_WAIT 소켓은 원래 소켓의 설정을 물려받는다). 그래서 모든 TCP 서버는 bind 전에 무조건 SO_REUSEADDR를 켠다는 관례가 있다. systemd로 데몬을 재시작했는데 1분간 Address already in use가 나는 버그의 정체가 이것이다.

9. AF_PACKET — 이더넷 프레임을 통째로#

9.1 직관#

AF_PACKET은 IP 스택을 건너뛰고 드라이버가 올려 준 이더넷 프레임을 그대로 받거나 보낸다. tcpdump, wireshark(libpcap)가 바닥에서 쓰는 것이 이것이다. 독자 EtherType을 쓰는 산업용 프로토콜(EtherCAT 마스터 구현 등)이나 PHY 루프백 테스트 툴도 이 소켓으로 짠다. 펌웨어에서 MAC RX 디스크립터의 버퍼를 직접 들여다보던 위치와 가장 가깝다.

9.2 예제 8 — ping 프레임 캡처#

출력에서 볼 것: 98바이트 = 이더넷 헤더 14 + IP 헤더 20 + ICMP 8 + ping 데이터 56. loopback은 가짜 이더넷 헤더(MAC 0)를 붙인다. eth0에서는 실제 MAC이 보이고, 나가는 프레임(PACKET_OUTGOING)까지 잡힌다. ETH_P_ALL로 열면 송신 경로의 프레임 복사본도 탭으로 받는다는 뜻이다.

고성능 캡처는 PACKET_MMAP(TPACKET_V3) 링버퍼로 커널과 유저가 메모리를 공유해 복사를 줄인다. A5의 mmap, 펌웨어의 DMA 디스크립터 링과 같은 발상이다.

10. SocketCAN — CAN도 소켓이다#

10.1 직관#

많은 RTOS에서 CAN은 "mailbox에 ID와 데이터를 쓰고 TX 요청 비트를 세우는" 레지스터 API였다. Linux는 CAN 컨트롤러를 네트워크 인터페이스(can0)로 등록하고 CAN 프레임 하나를 패킷 하나로 다룬다. 그래서 ip link로 비트레이트를 설정하고, 소켓으로 송수신하고, ip -s link로 에러 카운터를 본다. 이게 SocketCAN이다(Volkswagen 연구소가 기여해 메인라인에 들어갔다. 아래 modinfo author 줄에서도 보인다).

실물 CAN 컨트롤러가 없으니 vcan(virtual CAN, 보낸 프레임을 그대로 되돌려 주는 루프백 인터페이스)을 만든다.

link/can이 이 인터페이스의 하드웨어 타입이다. 실제 보드라면 ip link set can0 type can bitrate 500000 후 up한다. 이 VM 커널의 vcan은 기본 MTU가 2060(CAN XL 프레임 크기)으로 잡혔다. 커널 버전에 따라 기본 MTU가 16(classic CAN)이나 72(CAN FD)로 보일 수 있다.

10.2 예제 9 — vcan0으로 프레임 보내고 필터로 받기#

출력에서 볼 것:

  • 0x321은 필터 (id & 0x700) == 0x100에 맞지 않아 rx 소켓에 오지 않았다. 필터는 소켓마다 따로 걸린다.
  • 같은 프로세스의 다른 소켓(tx)이 보낸 프레임을 rx가 받은 것은 SocketCAN의 로컬 루프백(CAN_RAW_LOOPBACK, 기본 켜짐) 덕분이다. 실제 버스에서도 같은 장비의 다른 앱이 송신 프레임을 볼 수 있게 해 준다. 보낸 소켓 자신은 기본적으로 자기 프레임을 받지 않는다(CAN_RAW_RECV_OWN_MSGS 기본 꺼짐).
  • 인터페이스 카운터는 3개 송신, 3개 수신(데이터 4바이트 × 3 = 12바이트)이다. 필터는 소켓 단계라 인터페이스 카운터에는 영향이 없다.
  • struct can_frame은 16바이트 고정이다(4바이트 ID + 1바이트 길이 + 패딩·예약 3 + 데이터 8). write 한 번 = 프레임 하나, 부분 쓰기가 없다. CAN FD는 struct canfd_frame(72바이트) + CAN_RAW_FD_FRAMES 옵션을 쓴다.

실물 보드에서는 can-utils 패키지의 candump can0, cansend can0 123#11223344가 같은 소켓 API로 만든 툴이다. ip -details -statistics link show can0에서 berr-counter, bus-off 같은 CAN 에러 상태를 본다.

13. 커널 안에서는 무슨 일이 일어나나#

그림 9 — 소켓 계층 → 프로토콜 → net core → net_device 드라이버의 층 구조. 송신은 위에서 아래로 sk_buff에 헤더를 붙이며 내려가고, 수신은 드라이버의 NAPI poll에서 sk_buff가 만들어져 위로 올라온다.

13.1 socket() — fd와 struct socket#

  • socket() 시스템 콜 → __sys_socket() → sock_create() → family별 net_proto_family.create 함수(inet_create, packet_create, can_create, netlink_create, unix_create)가 호출된다. AF_CAN 소켓을 만들 때 can_raw가 자동 로드된 것은 여기서 request_module("can-proto-1")을 하기 때문이다.
  • 결과물은 두 겹이다. struct socket(VFS 쪽 얼굴: 타입, 상태, proto_ops 포인터)과 struct sock(프로토콜 쪽 몸통: 수신 큐 sk_receive_queue, sk_rcvbuf, sk_drops, 대기 큐). TCP라면 struct sock은 더 큰 struct tcp_sock의 맨 앞에(inet_connection_sock → inet_sock → sock 순으로 겹겹이) 들어 있어서 포인터 캐스팅으로 오간다(C의 구조체 상속 패턴).
  • sock_alloc_file()이 struct file을 만들고 f_op를 socket_file_ops로 채운다. 그래서 read() → sock_read_iter() → sock_recvmsg() → sock->ops->recvmsg()(예: inet_recvmsg → udp_recvmsg)로 이어진다. A1에서 본 "VFS가 file_operations로 분기한다"는 구조가 소켓에도 그대로 적용된다.
  • epoll은 socket_file_ops.poll = sock_poll() → 프로토콜의 poll(tcp_poll, datagram_poll)을 부른다. 드라이버의 .poll + poll_wait()(A4, G4)와 같은 구조다.

13.2 송신 경로#

write() → sock_sendmsg() → inet_sendmsg() → udp_sendmsg()/tcp_sendmsg() → 데이터를 sk_buff(skb)에 담음 → ip_output()이 IP 헤더, 이웃 계층이 이더넷 헤더 → dev_queue_xmit() → qdisc(송신 큐 정책) → 드라이버의 ndo_start_xmit(skb, dev). 드라이버는 skb의 데이터를 DMA 매핑해 TX 디스크립터 링에 올리고 doorbell을 친다. 링이 차면 netif_stop_queue()로 위층을 멈춘다. Don이 SSD에서 하던 submission queue + doorbell과 같은 그림이다.

13.3 수신 경로#

NIC가 프레임을 DMA로 RX 링에 쓰고 인터럽트 → 드라이버 ISR이 인터럽트를 끄고 napi_schedule() → softirq(NET_RX)에서 드라이버의 NAPI poll()이 예산(budget)만큼 디스크립터를 읽어 skb를 만들고 napi_gro_receive()/netif_receive_skb()로 올림 → ip_rcv() → udp_rcv() → 소켓 찾기 → 수신 큐에 넣기 전 sk_rcvbuf 검사(넘치면 drop, sk_drops와 UDP_MIB_RCVBUFERRORS 증가 — 5절의 카운터) → sk_data_ready()가 recvmsg()에서 잠든 태스크나 epoll을 깨움(F3의 wait queue). AF_PACKET 소켓은 netif_receive_skb 단계에서 등록된 탭(packet_rcv)으로 복사본을 받는다. 그래서 tcpdump는 IP 스택이 버리는 패킷도 볼 수 있다.

NAPI는 "인터럽트로 깨운 뒤 폴링으로 몰아서 처리"하는 방식이다. 고속 NIC에서 패킷마다 인터럽트를 받으면 CPU가 인터럽트만 처리하다 끝나는 문제(livelock)를 막는다. 펌웨어에서 인터럽트 coalescing + 폴링 루프로 전환하던 것과 같은 해법이다(F6, F7, I6).

13.4 CAN과 netlink는 어디로#

  • CAN: can_send() → dev_queue_xmit() → CAN 드라이버 ndo_start_xmit()(i.MX8은 flexcan, TI AM62는 m_can, SPI 외장 컨트롤러는 mcp251xfd). 수신은 드라이버가 can_frame을 skb에 담아 올리면 CAN 코어의 can_rcv()가 소켓별 필터를 돌린다. CAN 드라이버도 결국 net_device 드라이버라 I6의 지식이 그대로 쓰인다.
  • netlink: 하드웨어로 내려가지 않는다. netlink_sendmsg() → 프로토콜별 수신 함수(rtnetlink면 rtnetlink_rcv() → rtnl_dump_ifinfo() 같은 핸들러) → 응답 skb를 요청한 소켓의 수신 큐에 넣는다. uevent는 kobject_uevent_env()가 메시지를 만들어 멀티캐스트로 뿌린다.

14. Embedded 실무에서 다시 보기#

14.1 LiDAR 수신 스레드#

예를 들어 센서 키트라면 LiDAR 수신은 이렇게 짠다.

  • LiDAR 전용 NIC(또는 VLAN)에 SO_BINDTODEVICE로 묶어 업링크 트래픽과 섞이지 않게 한다.
  • SO_RCVBUF를 "최대 burst × truesize"로 잡고 rmem_max를 같이 올린다(5.5절).
  • 수신 스레드는 recvmmsg()로 여러 패킷을 한 번에 받아 링버퍼에 넣기만 하고, 포인트 클라우드 변환은 다른 스레드가 한다(5.4절 교훈).
  • SO_TIMESTAMPING으로 도착 시각을 받고, LiDAR 패킷 안의 GPS/PTP 시각과 비교해 지연을 모니터링한다(Q3).
  • 수신 스레드에 RT 우선순위(F1)와 CPU 친화도, NIC IRQ도 같은 클러스터에 고정한다.

14.2 CAN 모터 제어 데몬#

  • 모터 컨트롤러 응답 ID만 받도록 CAN_RAW_FILTER를 건다. 수천 fps 버스에서 관심 없는 프레임으로 유저 공간을 깨우지 않는다.
  • 에러 프레임을 받으려면 CAN_RAW_ERR_FILTER를 켠다. bus-off 같은 상태 변화가 프레임으로 온다.
  • CAN 소켓, 타이머(timerfd), 상위 명령 TCP 소켓을 하나의 epoll 루프로 묶는다(A4, 7절).
  • 개발 PC에서는 vcan0로 상위 로직을 먼저 검증하고, 보드에서는 인터페이스 이름만 can0로 바꾼다. 이것이 "CAN도 소켓"인 실무적 이점이다.

14.3 진단·설정 서버#

  • TCP 서버는 SO_REUSEADDR, SOCK_CLOEXEC, SIGPIPE 무시, 길이 접두 프레이밍을 기본으로 깐다.
  • 장비가 hotplug USB 카메라나 USB-CAN 어댑터를 쓰면 NETLINK uevent(정확히는 libudev monitor)로 연결/해제를 감지해 파이프라인을 재구성한다.
  • 링크 업/다운 감지는 /sys/class/net/eth0/carrier를 폴링하지 말고 rtnetlink RTMGRP_LINK 그룹에 가입해 이벤트로 받는다.

16. 면접에서 이렇게 말한다#

Q. What's the difference between TCP and UDP, and when would you use UDP on an embedded device?

A. TCP는 연결 지향 바이트 스트림으로 순서·재전송·흐름 제어를 보장하지만 지연과 head-of-line blocking이 있다. UDP는 메시지 경계가 보존되는 비연결 데이터그램으로 손실·순서 바뀜이 가능하다. LiDAR나 카메라 스트림처럼 늦은 데이터가 쓸모없는 실시간 센서 데이터에는 UDP를, 설정·펌웨어 업데이트·로그처럼 정확성이 중요한 데에는 TCP를 쓴다.

TCP gives you a reliable, ordered byte stream with retransmission and flow control, at the cost of latency and head-of-line blocking. UDP preserves message boundaries but can lose or reorder datagrams. For real-time sensor streams like LiDAR, a late packet is useless, so UDP with a sequence number in the payload is the right choice. For configuration, firmware updates, or logs, where every byte matters, I'd use TCP.

꼬리 질문: "UDP 손실을 어떻게 감지하나?" → 페이로드 seq 번호 + RcvbufErrors/ss -m의 drops.

Q. Our LiDAR driver occasionally drops packets. How do you debug it?

A. 층별로 카운터를 본다. ethtool -S(NIC RX 링), ip -s link(드라이버), nstat의 UdpRcvbufErrors(소켓 버퍼), ss -u -m의 d(어느 소켓). 소켓 단계라면 burst × truesize 기준으로 SO_RCVBUF와 rmem_max를 올리고, 평균 처리율이 부족하면 수신과 처리를 분리한다. 실측에서 1206바이트 패킷 하나가 커널 메모리 2304바이트를 차지해 기본 버퍼에 92개밖에 안 들어갔다.

I'd walk the stack bottom-up with counters: ethtool -S for NIC ring drops, ip -s link for driver drops, UdpRcvbufErrors for socket buffer overflow, and ss -u -m to see which socket's drop counter is moving. If it's the socket buffer, I size SO_RCVBUF for the worst burst times the skb truesize, which is roughly twice the payload, and raise rmem_max. If the average processing rate is below the arrival rate, a bigger buffer only delays the loss, so I split receiving from processing and use recvmmsg.

Q. Why does TCP need message framing, and how do you implement it?

A. TCP는 write 경계를 보존하지 않는다. 여러 write가 한 read로 붙거나 하나가 여러 read로 쪼개진다. 그래서 4바이트 big-endian 길이 접두를 붙이고, 수신 측은 정확한 바이트 수를 다 읽을 때까지 반복하는 read_full로 헤더와 payload를 읽는다. 길이 상한 검사도 넣는다.

TCP is a byte stream, so message boundaries from write calls are not preserved; I've seen five writes arrive in a single 32-byte read. The usual fix is a length prefix in network byte order, and a read-exactly-n-bytes loop on the receiver, with a sanity limit on the length so a corrupted header can't make you allocate gigabytes.

Q. What is TIME_WAIT and why do servers set SO_REUSEADDR?

A. 먼저 close한 쪽이 지연된 세그먼트가 새 연결에 섞이지 않도록 60초(Linux 고정값) 동안 TIME_WAIT 상태를 유지한다. 서버가 먼저 닫고 재시작하면 그 포트로 bind가 EADDRINUSE로 실패한다. SO_REUSEADDR가 이를 허용하는데, Linux에서는 TIME_WAIT를 남긴 이전 소켓도 옵션을 켰어야 해서 항상 켜는 것이 관례다.

The side that closes first stays in TIME_WAIT for 60 seconds on Linux so that delayed segments from the old connection can't corrupt a new one. If a server restarts while its port has TIME_WAIT entries, bind fails with EADDRINUSE. SO_REUSEADDR allows the bind, and on Linux the old socket must have had it set as well, which is why every server sets it before bind.

Q. How does SocketCAN work, and why is it designed as a socket?

A. CAN 컨트롤러를 net_device(can0)로 등록하고, 프레임 하나를 skb 하나로 다룬다. 앱은 socket(PF_CAN, SOCK_RAW, CAN_RAW), bind로 인터페이스 지정, write/read로 16바이트 can_frame을 주고받는다. 소켓 단위 필터, 여러 앱 동시 접근, epoll 통합, ip로 비트레이트 설정, qdisc, vcan으로 하드웨어 없이 테스트가 모두 네트워크 스택의 기존 기능으로 해결된다.

SocketCAN registers the CAN controller as a network device, so each CAN frame travels as an skb. Applications open a PF_CAN raw socket, bind it to can0, and read or write fixed 16-byte can_frame structs. Reusing the network stack gives you per-socket ID filters, multiple concurrent users, epoll integration, configuration through ip and netlink, and virtual interfaces like vcan for testing without hardware. The driver side is a normal net_device driver using alloc_candev and register_candev.

Q. How do tools like ip or udev talk to the kernel?

A. netlink 소켓이다. ip는 NETLINK_ROUTE에 RTM_GETLINK 같은 요청을 보내고 TLV 속성이 담긴 응답을 받는다. udev는 NETLINK_KOBJECT_UEVENT 멀티캐스트 그룹에 가입해 커널이 kobject_uevent()로 보내는 "add@/devices/..." 메시지를 받아 /dev 노드를 만들고 모듈을 로드한다.

Through netlink sockets. iproute2 sends rtnetlink requests such as RTM_GETLINK with NLM_F_DUMP and parses TLV attributes in the replies, which is extensible and avoids ioctl ABI problems. udev subscribes to the NETLINK_KOBJECT_UEVENT multicast group; the kernel broadcasts messages like add@/devices/... with SUBSYSTEM and MODALIAS keys, and udev uses them to create device nodes and load modules.

Q. Walk me through what happens in the kernel when a UDP packet arrives.

A. NIC가 DMA로 RX 링에 쓰고 인터럽트 → 드라이버가 NAPI를 스케줄 → softirq에서 poll이 skb를 만들어 netif_receive_skb → ip_rcv → udp_rcv → 포트로 소켓을 찾고 sk_rcvbuf 검사 후 수신 큐에 넣음(넘치면 drop + 카운터) → sk_data_ready가 대기 중인 recv나 epoll을 깨움 → 앱이 recvmsg로 skb 데이터를 복사해 감.

The NIC DMAs the frame into an RX ring and raises an interrupt; the driver masks it and schedules NAPI. In the NET_RX softirq, the driver's poll function builds skbs and passes them to netif_receive_skb, then ip_rcv and udp_rcv look up the socket by port. Before queuing, the kernel checks the socket's receive buffer limit; if it's full, the packet is dropped and RcvbufErrors is incremented. Otherwise it's queued and sk_data_ready wakes any thread blocked in recvmsg or epoll_wait.

Q. How would you get accurate arrival timestamps for sensor packets?

A. 앱의 시각은 스케줄링 지연을 포함한다. SO_TIMESTAMPNS로 커널 수신 시각을 cmsg로 받고, 더 정확하게는 SO_TIMESTAMPING으로 NIC 하드웨어 타임스탬프를 받는다. 이를 위해 NIC가 PHC를 지원해야 하고 ptp4l/phc2sys로 시스템 시계와 맞춘다. 실험에서 앱 시각은 최대 64 ms 틀렸다.

Application-side timestamps include scheduling delay; in a quick test, packets that arrived 10 ms apart all looked like they arrived at the same time when read late. I'd enable SO_TIMESTAMPNS for kernel receive timestamps, or SO_TIMESTAMPING for hardware timestamps if the MAC has a PTP hardware clock, and then keep the PHC and system clock aligned with ptp4l and phc2sys.

19. 요약 & 체크리스트#

소켓은 TCP/IP만을 위한 API가 아니라 커널 안의 통신 엔드포인트를 fd로 잡는 범용 손잡이다. 같은 socket/bind/read/write/epoll로 UDP(LiDAR), TCP(원격 툴), AF_PACKET(이더넷 프레임), AF_CAN(모터 버스), AF_NETLINK(커널 설정·hotplug), AF_UNIX(로컬 IPC)를 다룬다. TCP는 신뢰성 있는 바이트 스트림이라 애플리케이션 프레이밍이 필요하고, 상태 머신(LISTEN, ESTABLISHED, TIME_WAIT)을 ss·tcpdump로 읽을 수 있어야 한다. UDP는 메시지 경계를 보존하지만 수신 장비 안에서 소켓 버퍼가 넘치면 조용히 버려진다. 측정해 보면 1206바이트 패킷이 커널 메모리 2304바이트를 차지하고, burst에는 버퍼 크기가, 지속 과부하에는 처리 속도가 답이다. 커널 안에서는 struct file → struct socket → struct sock → 프로토콜 → net core → net_device 드라이버로 sk_buff가 오가고, 이 경로가 I6(네트워크 드라이버), G9(uevent), Q3(타임스탬프)로 이어진다.
