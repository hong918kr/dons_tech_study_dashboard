0. 큰 그림 — 왜 프로세스를 나누고, 그래서 왜 IPC가 필요한가#

bare-metal 펌웨어에서는 모든 태스크가 한 주소 공간에 산다. IMU 태스크가 링버퍼에 샘플을 넣으면 로거 태스크가 같은 전역 변수를 읽는다. 통신 = 그냥 메모리 접근 + 세마포어다. 편하지만, 한 태스크가 포인터를 잘못 쓰면 전체가 죽는다.

Embedded Linux 장비는 보통 일부러 여러 프로세스로 쪼갠다. 예를 들어 센서 키트라면:

  • imu_daemon: IIO 장치(/dev/iio:device0)에서 400 Hz로 샘플을 읽는다. 실시간 우선순위(SCHED_FIFO)로 돈다.
  • camera_daemon: V4L2로 프레임을 받는다. 프레임 버퍼는 커널이 할당한 dmabuf다.
  • logger: 샘플·프레임을 eMMC에 기록한다.
  • uploader: LTE/Wi-Fi로 텔레메트리를 보낸다. 유일하게 네트워크 권한을 가진다.
  • health_mon: 모든 데몬의 상태를 모아 watchdog을 찬다.

나누는 이유는 세 가지다.

  1. 장애 격리(fault isolation): uploader가 TLS 라이브러리 버그로 segfault 나도 imu_daemon은 계속 돈다. 각 프로세스는 MMU로 격리된 자기 주소 공간을 가진다 — Don이 아는 "MPU로 태스크 영역을 막는 것"의 완전판이다.
  2. 권한 분리(privilege separation): 네트워크에 노출된 uploader는 root가 아니고 장치 파일도 못 연다. 뚫려도 피해가 작다.
  3. 독립 재시작·배포: systemd가 죽은 데몬만 다시 띄운다(Restart=on-failure). 로거만 업데이트할 수도 있다. 언어도 섞을 수 있다(C 데몬 + Python 업로더).

대가는 하나다. 데이터가 주소 공간 경계를 넘어가야 한다. 그 경계를 넘는 방법들이 IPC(Inter-Process Communication)다.

그림 1 — 센서 키트를 프로세스로 나눈 모습. 회색은 커널 장치, 파랑은 생산자, 초록은 소비자다. 주황 화살표가 이 노트의 주제다.

1. IPC 메뉴 한 장으로 보기#

그림 2 — Linux IPC 메뉴. 넷째 칸(미들웨어)은 결국 앞의 세 칸(소켓·shm) 위에 만들어진다.

2. pipe와 FIFO — 가장 단순한 바이트 스트림#

2.1 직관#

pipe는 커널 안에 있는 작은 링버퍼 하나 + fd 두 개(읽기 끝, 쓰기 끝)다. 펌웨어로 치면 UART TX FIFO와 RX FIFO를 루프백으로 붙여 놓은 것이다. 한쪽에서 write()로 넣으면 다른 쪽에서 read()로 꺼낸다. 비면 reader가 잠들고, 가득 차면 writer가 잠든다. 깨워 주는 건 커널이다.

  • 익명 pipe(pipe()/pipe2()): 이름이 없다. fd를 물려받은 프로세스끼리만(보통 fork()한 부모-자식) 쓴다. 셸의 cmd1 | cmd2가 바로 이것이다.
  • FIFO(named pipe): 파일시스템에 이름(mkfifo)이 있는 pipe다. 상관없는 두 프로세스가 경로로 만난다. 데이터는 디스크에 안 가고 똑같이 커널 메모리에만 있다.

무엇을 확인하는 코드인가: 기본 pipe 용량이 몇 바이트인지, F_SETPIPE_SZ로 늘릴 수 있는지, 그리고 조금 읽었다고 바로 쓸 공간이 생기지 않는 이유.

2.3 PIPE_BUF — "섞이지 않음"의 보장#

여러 프로세스가 한 pipe에 동시에 write하면(예: 여러 데몬이 로그 FIFO 하나에 쓰는 경우) 메시지가 중간에 섞일 수 있나? POSIX의 답: PIPE_BUF 바이트 이하의 write는 원자적이다. 한 번에 통째로 들어가고 다른 writer의 데이터가 끼어들지 않는다. Linux에서 PIPE_BUF = 4096이다. 그보다 크면 보장이 없다.

예제 2 — 무엇을 확인하는 코드인가: writer 4개가 각자 자기 글자로 채운 레코드를 2000개씩 쓸 때, 레코드 크기에 따라 "찢어진(torn)" 레코드가 나오는지.

같은 프로그램을 세 번 더 돌린 결과(뒤 두 줄만):

출력에서 볼 것: 4096바이트까지는 한 번도 안 섞였고, 딱 1바이트 넘긴 4097바이트에서 수천 개가 찢어졌다. 64 KiB가 0인 것은 레코드 크기가 pipe 용량과 정확히 같아 이번 스케줄링에서 우연히 안 섞인 것이다 — 보장이 아니다. 규칙은 하나: 여러 writer가 공유하는 pipe/FIFO에는 PIPE_BUF 이하 크기로만 쓴다. 넘으면 writer별 pipe를 따로 두거나 소켓(메시지 경계가 있는 SEQPACKET/DGRAM)을 쓴다.

O_NONBLOCK일 때의 규칙도 알아 두자: PIPE_BUF 이하 write는 공간이 모자라면 한 바이트도 안 쓰고 EAGAIN이고, PIPE_BUF 초과 write는 일부만 쓰고 쓴 바이트 수를 돌려줄 수 있다(partial write). 그래서 non-blocking 코드는 항상 반환값을 확인하고 남은 부분을 다시 써야 한다.

2.4 EOF와 SIGPIPE — 한쪽이 죽으면#

pipe의 "크래시 동작"은 깔끔하다.

  • 모든 writer가 닫히면(프로세스가 죽어도 커널이 fd를 닫는다) reader의 read()는 0(EOF) 을 돌려준다.
  • 모든 reader가 닫혔는데 write하면 writer는 SIGPIPE 를 받는다(기본 동작 = 종료). 시그널을 무시하면 write()가 EPIPE로 실패한다. 데몬은 보통 SIGPIPE를 무시하고 EPIPE를 처리한다(A6).
  • 그래서 안 쓰는 끝은 반드시 닫는다. 자식에게 fd를 물려준 뒤 부모가 쓰기 끝을 안 닫으면, 자식이 다 써도 reader는 EOF를 영원히 못 받는다(쓰기 끝을 가진 프로세스가 아직 있으니까). 예제 2에서 부모가 close(p[1])을 하는 이유다.

2.7 pipe의 함정 정리#

  • 바이트 스트림이라 메시지 경계가 없다(3.2절 프레이밍 필요).
  • 단방향이다. 요청-응답이면 pipe 두 개가 필요하다(→ 그럴 바엔 socketpair).
  • reader가 여럿이면 한 바이트는 한 reader만 받는다. 브로드캐스트가 아니다.
  • 64 KiB가 차면 writer가 막힌다. 실시간 생산자(센서 데몬)가 느린 소비자 때문에 막히면 샘플 타이밍이 망가진다 → non-blocking + 드롭 정책이 필요하다.

3. UNIX domain socket — 실무 IPC의 주력#

3.1 직관과 정의#

UNIX domain socket(AF_UNIX)은 같은 머신 안에서만 쓰는 소켓이다. API는 TCP/UDP 소켓(A9)과 똑같고(socket/bind/listen/accept/connect/send/recv), 네트워크 스택(IP, 체크섬, 라우팅)을 안 거치니 훨씬 가볍다. pipe보다 할 수 있는 게 많아서 실무 데몬 간 통신은 대부분 이것이다. systemd, D-Bus, Wayland, Docker, X11이 모두 UNIX socket 위에서 돈다.

pipe에 비해 더 있는 것:

  • 양방향: 한 소켓으로 요청과 응답을 주고받는다.
  • 세 가지 타입: SOCK_STREAM(경계 없는 바이트 스트림, TCP와 비슷), SOCK_DGRAM(경계 보존, 연결 없음, UDP와 비슷하지만 로컬이라 유실·순서 바뀜 없음), SOCK_SEQPACKET(경계 보존 + 연결형 + 순서 보장 — 로컬 메시지 IPC의 숨은 강자).
  • 이름 짓기 세 가지: 파일 경로(/run/sensor.sock, 파일 권한으로 접근 제어), abstract namespace(Linux 전용, 경로 첫 바이트가 '\0', 파일이 안 생겨서 지울 필요가 없음), 이름 없음(socketpair()).
  • 상대 확인: SO_PEERCRED로 상대 프로세스의 pid/uid/gid를 커널이 보증해서 알려 준다.
  • fd 전달: SCM_RIGHTS로 열린 fd 자체를 다른 프로세스에 넘긴다(3.4절). pipe로는 불가능하다.

3.2 예제 5 — 스트림은 경계가 없다#

무엇을 확인하는 코드인가: 같은 메시지 3개를 send() 3번으로 보내고, 소켓 타입별로 recv()가 어떻게 돌려주는지.

출력에서 볼 것: STREAM은 send() 세 번을 한 덩어리 32바이트로 돌려줬다. 반대로 한 번 보낸 것이 여러 번에 나눠 올 수도 있다. SEQPACKET/DGRAM은 보낸 단위 그대로 받는다. 대신 버퍼가 작으면 남은 부분이 잘려 버려진다 — MSG_TRUNC를 주면 원래 크기(10)를 알려 줘서 잘림을 감지할 수 있다.

펌웨어 비유: STREAM은 UART다. 바이트는 순서대로 오지만 "패킷"은 없다. 그래서 UART 프로토콜에 SOF·길이·CRC를 넣듯, 스트림 소켓 위에는 프레이밍을 직접 얹어야 한다. 가장 흔한 방법이 길이 프리픽스: [4바이트 길이][본문]. 받는 쪽은 "정확히 4바이트 읽기 → 정확히 len바이트 읽기"를 반복한다. read()가 요청보다 적게 돌려주는(short read) 경우를 반드시 루프로 처리해야 한다.

무엇을 확인하는 코드인가: 파일을 만들지 않는 abstract 소켓 이름, 커널이 보증하는 상대 자격 증명, 그리고 short read를 견디는 프레이밍.

출력에서 볼 것(pid는 실행마다 다르다): ss -xl에 이름이 @sensor_hub 로 보인다. @는 abstract namespace라는 표시다(실제 첫 바이트는 '\0'). 파일시스템에 소켓 파일이 없으니 데몬이 죽은 뒤 bind: Address already in use로 재시작이 실패하는 고전 문제가 없다. 대신 파일 권한으로 접근을 막을 수 없다(같은 network namespace의 누구나 connect 가능). 그래서 SO_PEERCRED로 uid를 확인하는 코드가 짝으로 따라온다. 출력의 peer pid는 자식(client) pid, uid 501은 VM 사용자 donh다. 이 값은 상대가 위조할 수 없고 connect() 시점의 자격 증명이다.

파일 경로 소켓을 쓴다면: bind() 전에 unlink(path)하고, 디렉터리 권한(예: /run/sensor/ 0750, 그룹 sensor)으로 접근을 제어한다. systemd 소켓 활성화(socket activation)를 쓰면 systemd가 소켓을 만들어 fd로 넘겨준다(L 모듈).

3.4 예제 7 — SCM_RIGHTS로 fd 넘기기 (카메라 버퍼 zero-copy의 핵심)#

직관: 카메라 프레임 1장(1920×1080 NV12 ≈ 3 MB)을 소켓으로 복사해서 넘기면 초당 30장에 90 MB/s를 memcpy한다. 대신 "버퍼를 가리키는 핸들"만 넘기면 복사가 0이다. Linux에서 그 핸들이 fd다. V4L2는 VIDIOC_EXPBUF로 프레임 버퍼를 dmabuf fd로 내보낼 수 있고, 그 fd를 SCM_RIGHTS로 인코더·추론 프로세스에 넘기면 받은 쪽이 같은 버퍼를 mmap하거나 GPU/NPU 드라이버에 그대로 import한다(I5, Q2). 펌웨어에서 DMA 디스크립터에 버퍼 포인터만 넘기는 것과 같은 발상이다.

아래 예제는 dmabuf 대신 memfd_create()(이름 없는 메모리 파일)를 "프레임 버퍼"로 쓴다. fd라는 점에서 다루는 법은 같다.

출력에서 볼 것: producer에서는 fd 6이던 것이 consumer에서는 fd 3이다. fd 번호가 아니라 커널의 struct file 참조가 전달되고, 받는 쪽 fd 테이블의 빈 번호에 새로 설치되기 때문이다. 둘 다 같은 /memfd:cam0_frame42를 가리키고, consumer는 복사 없이 같은 메모리를 읽었다. (deleted)는 memfd가 파일시스템 이름이 없는 파일이라는 뜻이다.

그림 3 — SCM_RIGHTS fd 전달. 소켓에 실려 가는 것은 데이터가 아니라 struct file 참조다. 받는 쪽에는 새 fd 번호가 붙고, 두 fd(점선)는 같은 struct file과 같은 버퍼를 가리킨다.

함정:

  • control 버퍼는 CMSG_SPACE()로 크기를 잡고 정렬을 위해 union { struct cmsghdr; char[] }로 선언한다(위 코드처럼). CMSG_LEN과 CMSG_SPACE를 헷갈리면 플랫폼마다 다르게 깨진다.
  • fd만 보내도 최소 1바이트의 일반 데이터를 같이 보낸다(STREAM에서 0바이트 sendmsg는 의미가 없다). 위 예제는 프레임 이름을 실었다.
  • 받은 fd는 받는 쪽이 close()해야 한다. 안 그러면 fd와 버퍼가 샌다. 카메라 파이프라인에서 프레임마다 fd를 받는데 안 닫으면 몇 분 뒤 EMFILE이나 버퍼 고갈로 멈춘다.
  • 보낸 뒤에도 보낸 쪽 fd는 그대로 열려 있다(복제다). 버퍼 소유권 규칙(누가 언제 돌려주나)은 프로토콜로 정해야 한다.
  • memfd를 남에게 넘길 때 받은 쪽이 크기를 줄여 SIGBUS를 일으키는 공격을 막으려면 MFD_ALLOW_SEALING + fcntl(F_ADD_SEALS, F_SEAL_SHRINK)을 쓴다.

4. POSIX message queue — 커널이 관리하는 우선순위 우편함#

4.1 직관과 정의#

POSIX mq는 RTOS의 메시지 큐(mailbox) 와 거의 같다. 고정 최대 크기(mq_msgsize)의 메시지를 최대 mq_maxmsg개까지 커널이 보관하고, 우선순위가 높은 메시지가 먼저 나온다. 이름은 /sensor_evt처럼 /로 시작하고, Linux에서는 /dev/mqueue 가상 파일시스템에 파일로 보인다.

  • 메시지 경계 보존, 우선순위(0이 가장 낮음, Linux는 0~32767).
  • 커널 지속성(kernel persistence): 모든 프로세스가 닫아도 mq_unlink() 전까지(또는 재부팅 전까지) 큐와 메시지가 남는다. 생산자가 죽어도 이미 넣은 메시지는 소비자가 받는다.
  • mq_notify(): 큐가 비어 있다가 메시지가 들어오는 순간 시그널이나 스레드로 한 번 알려 준다. 또 mqd_t가 Linux에서는 실제 fd라서 epoll에 넣을 수도 있다(A4).
  • 한계: 시스템 기본 상한이 작다(이 VM에서 /proc/sys/fs/mqueue/msg_max = 10, msgsize_max = 8192). 대량 데이터용이 아니라 이벤트·명령·경보용이다.

5. POSIX shared memory — 복사 0번, 대신 동기화는 내 몫#

5.1 직관#

shared memory는 IPC 중 유일하게 커널이 데이터 경로에서 빠진다. 두 프로세스의 페이지 테이블이 같은 물리 페이지를 가리키게 만들어 주는 것까지만 커널이 하고(mmap), 그 다음부터는 그냥 메모리 load/store다. bare-metal에서 두 코어가 공유 SRAM 영역을 쓰는 것과 똑같다. 그래서 가장 빠르지만, 펌웨어에서 그랬듯 동기화·메모리 순서·"데이터가 왔다"는 통지는 전부 직접 해야 한다.

API는 셋이다.

  1. shm_open("/name", O_CREAT|O_RDWR, 0600): /dev/shm/name(tmpfs) 파일을 연다. glibc 구현이 실제로 그 경로를 open한다.
  2. ftruncate(fd, size): 크기를 정한다(새로 만든 객체는 크기 0이다).
  3. mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0): 내 주소 공간에 붙인다(A5). MAP_SHARED여야 상대가 쓴 것이 보인다.

shm_unlink()는 이름만 지운다. 이미 매핑한 프로세스는 계속 쓸 수 있고, 마지막 매핑이 사라지면 메모리가 반환된다(파일의 unlink와 같은 규칙).

5.2 예제 9 — 정말 같은 물리 페이지인가#

무엇을 확인하는 코드인가: 부모와 자식이 서로 다른 가상 주소로 같은 shm을 매핑했을 때 물리 페이지 번호(PFN)가 같은지. /proc/self/pagemap에서 PFN을 읽으려면 root가 필요해서 sudo로 실행한다.

출력에서 볼 것(주소·PFN은 실행마다 다르다): 가상 주소는 ...79000과 ...7a000으로 다르지만 PFN은 둘 다 0x11efa7 이다. 한 물리 페이지가 두 번 매핑된 것이다. /proc/<pid>/maps의 rw-s에서 s가 shared, 장치 번호 00:1c와 inode 18이 둘 다 같은 tmpfs 파일이다. 자식이 쓴 "child overwrote it"이 부모에게 즉시 보인다. root가 아니면 PFN이 0으로 가려진다(커널이 보안상 일반 사용자에게 물리 주소를 숨긴다). 코드에서 pfn_of() 전에 한 번 읽어 page fault로 매핑을 완성하는 점에 주의하자 — 처음 접근 전에는 PTE가 없어서 PFN이 0으로 나온다(A5의 lazy 매핑).

5.3 예제 10 — shm 위의 SPSC 링버퍼 (센서 샘플)#

Don이 펌웨어에서 수없이 짠 single-producer/single-consumer 링버퍼를 그대로 shm에 올린다. 규칙도 같다.

  • head는 producer만, tail은 consumer만 쓴다 → 락이 필요 없다.
  • 인덱스는 계속 증가하는 uint32_t, 슬롯은 idx & (N-1)(N은 2의 거듭제곱). head - tail이 원소 수다(오버플로해도 부호 없는 뺄셈이라 맞다).
  • 메모리 순서: producer는 슬롯을 다 쓴 뒤에 head를 release store로 게시하고, consumer는 head를 acquire load로 읽은 뒤에 슬롯을 읽는다. ARM에서 이 순서가 깨지면 반쯤 쓴 샘플을 읽는다(F5). 펌웨어에서 DMB를 넣던 자리에 C11 memory_order_release/acquire가 들어간다고 보면 된다.
  • head와 tail은 다른 캐시라인에 둔다(false sharing 방지 — 두 코어가 같은 라인을 번갈아 쓰면 라인이 계속 왔다갔다 한다).
  • 가득 차면 producer는 막히지 않고 버린다(drop). 센서 데몬은 실시간 루프라 느린 로거 때문에 멈추면 안 된다. 드롭 수는 카운터로 남긴다.
  • consumer가 비었을 때 바쁘게 돌지 않도록 process-shared 세마포어(sem_init(&sem, 1, 0)의 1)로 잠재운다. 이 세마포어 자체도 shm 안에 있다.

그림 4 — shm 위 SPSC 링의 메모리 레이아웃(위, 바이트 오프셋)과 슬롯 상태(아래). head와 tail은 각자 64바이트 캐시라인을 차지한다.

무엇을 확인하는 코드인가: 100만 개 샘플을 producer 프로세스가 링에 넣고 consumer 프로세스가 꺼낼 때, 받은 수 + 버린 수가 정확히 100만이고 consumer가 seq 번호 구멍으로 센 손실이 producer의 드롭 카운터와 일치하는지.

세 번 실행:

출력에서 볼 것: /dev/shm/imu_ring이 정확히 sizeof(struct ring) = 24744바이트 파일로 보인다. consumer가 5만 개마다 3 ms씩 멈추는 동안 링(1024칸)이 넘쳐 약 1%가 버려졌고, consumer가 seq 구멍으로 센 손실(gaps_seen)과 producer의 드롭 카운터가 정확히 같다. 즉 찢어진 샘플이나 중복 없이 순서대로 전달됐다. 드롭 수는 매번 다르다(스케줄링에 따라 다름).

실제로 만들면서 밟은 함정 하나: 처음엔 "센서 속도 흉내"용 usleep을 루프 끝에 뒀는데, 가득 찼을 때 continue가 그 줄을 건너뛰어 producer가 남은 샘플을 순식간에 전부 버렸다(드롭 85%). 실제 센서는 consumer가 느리다고 빨라지지 않으니 페이싱은 루프 맨 앞에 둬야 한다. 테스트 하네스의 타이밍 모델이 현실과 다르면 숫자가 엉터리가 된다는 교훈이다.

설계 메모:

  • 실제 장비라면 producer는 sem_post 대신 eventfd(A4)에 write하고 consumer는 epoll로 기다리는 경우가 많다. 그러면 consumer가 소켓·타이머와 함께 한 루프에서 기다릴 수 있다. eventfd는 fd라서 SCM_RIGHTS로 넘길 수도 있다.
  • 샘플마다 깨우면 wakeup 비용(8절에서 측정: 수십 µs)이 든다. 실무에서는 "N개 모이면" 또는 "1 ms마다" 깨우는 배치 통지로 비용을 줄인다. 펌웨어의 인터럽트 coalescing과 같다.
  • reader가 여럿이면 SPSC가 깨진다. 방법은 둘: reader마다 링을 따로 두거나, 하나의 링에 reader별 tail을 두고 producer가 가장 느린 tail 기준으로 가득 참을 판단한다(또는 seqlock 방식으로 "덮어쓰기 + reader가 seq로 유효성 검사").

5.4 예제 11 — 락을 쥔 채 죽으면? robust mutex#

shm 안에 pthread_mutex_t를 두고 PTHREAD_PROCESS_SHARED로 초기화하면 프로세스 간 락이 된다. 문제는 락을 쥔 프로세스가 죽을 때다. pipe·소켓은 커널이 fd를 닫아 주니 상대가 EOF를 받지만, shm 안의 락은 그냥 메모리 값이라 아무도 풀어 주지 않는다.

무엇을 확인하는 코드인가: 자식이 락을 쥔 채 SIGKILL로 죽었을 때 일반 mutex와 robust mutex가 어떻게 다른지.

출력에서 볼 것: 일반 mutex는 영원히 잠긴다(1초 timeout = ETIMEDOUT, strerror 문자열이 "Connection timed out"이다). robust mutex는 다음 locker에게 EOWNERDEAD("Owner died") 를 돌려주며 락을 넘겨준다. 받은 쪽은 공유 데이터가 반쯤 갱신됐을 수 있으니(calib_version=7까지만 쓰고 죽었다) 검증하고 pthread_mutex_consistent()를 호출해야 한다. 안 부르고 unlock하면 그 mutex는 영구히 못 쓰게 된다(ENOTRECOVERABLE).

커널 쪽 구현: glibc가 스레드마다 "내가 쥔 robust 락 목록"을 set_robust_list() syscall로 커널에 등록해 두고, 스레드가 죽으면 커널이 그 목록을 따라가며 futex 값에 FUTEX_OWNER_DIED 비트를 세우고 기다리는 쪽을 깨운다(docs.kernel.org "Robust futexes"). 이것이 "shm은 크래시 동작을 직접 설계해야 한다"는 말의 구체적인 모습이다. SPSC 링처럼 락 없는 설계가 이 문제를 아예 피하는 이유이기도 하다.

6. 나머지 메뉴 — System V IPC, D-Bus, 미들웨어#

6.1 System V IPC (legacy)#

shmget/shmat, msgget/msgsnd, semget/semop는 1980년대 System V UNIX에서 온 옛 API다. 객체를 fd가 아니라 정수 키(key_t, 보통 ftok())와 ID로 찾고, 그래서 epoll에 못 넣고, 명시적으로 지우기 전까지 남는다. 새 코드는 POSIX 쪽(shm_open, mq_open, sem_open)을 쓴다. 다만 오래된 산업용 소프트웨어나 일부 벤더 SDK가 아직 쓰므로 보고 알아볼 수는 있어야 한다.

예제 12 — 무엇을 확인하는 명령인가: SysV 객체를 만들고 ipcs로 보고 지우기.

출력에서 볼 것: ipcmk 프로세스는 이미 끝났는데 객체가 남아 있다(nattch 0). 크래시한 프로그램이 SysV shm을 안 지우면 재부팅 전까지 메모리가 새는 이유다. 현장에서 "메모리가 조금씩 줄어든다"는 버그를 볼 때 ipcs -m도 확인 목록에 넣자.

6.2 D-Bus 미리보기 (L3에서 자세히)#

D-Bus는 메시지 버스다. 버스 데몬(dbus-daemon 또는 dbus-broker)이 가운데 있고, 각 서비스가 UNIX socket으로 버스에 붙는다. 메시지 타입은 method call / return / error / signal(브로드캐스트)이고, 객체 경로·인터페이스·프로퍼티라는 객체 모델을 가진다. systemd, NetworkManager, BlueZ, ModemManager 같은 시스템 서비스를 제어하는 표준 통로다.

예제 13 — 무엇을 확인하는 명령인가: 시스템 버스에 붙은 서비스 목록과, D-Bus로 프로퍼티 하나를 읽어 오기.

출력에서 볼 것: 버스 위의 각 연결(:1.x)이 실제 프로세스(systemd-networkd, logind…)다. Properties.Get 호출 하나에 메시지 2개(요청·응답)가 버스 데몬을 거쳐 오간다. 즉 D-Bus는 제어·설정·상태 통지용이다(초당 수십~수백 메시지). 400 Hz IMU 데이터나 카메라 프레임을 D-Bus로 보내면 안 된다. 큰 데이터를 D-Bus로 협상하고 실제 데이터는 fd(D-Bus도 UNIX socket이라 fd 전달을 지원한다)나 shm으로 넘기는 패턴이 흔하다.

6.3 더 높은 층: ROS 2/DDS, ZeroMQ (이름만)#

  • ROS 2: 로보틱스 공통어(Q6). 노드가 토픽에 publish/subscribe한다. 아래는 DDS 미들웨어(UDP 멀티캐스트 기반 발견·전송)이고, 같은 머신 안에서는 구현에 따라 shm 전송(예: Fast DDS의 SHM transport, iceoryx 기반 zero-copy)을 쓴다. 결국 이 노트의 소켓과 shm이다.
  • ZeroMQ: 소켓 위의 메시징 라이브러리. PUB/SUB, REQ/REP, PUSH/PULL 패턴과 자동 재연결·프레이밍을 준다. ipc:// 전송은 UNIX domain socket이다.

면접에서는 "ROS 2를 쓰면 IPC를 신경 안 써도 되나?" 같은 질문이 나온다. 답: 직렬화·복사·발견(discovery) 비용이 붙고, 지연·지터가 중요한 경로(모터 제어 루프)는 같은 프로세스 안이나 shm으로 내린다.

8. 직접 재 보기 — pipe vs UNIX socket vs shm#

8.1 처리량 (예제 14)#

무엇을 확인하는 코드인가: 한 방향으로 64 B 메시지(64 MiB 분량)와 64 KiB 메시지(1 GiB 분량)를 흘려보낼 때의 처리량. pipe는 기본 64 KiB와 1 MiB(pipe1m)로 두 번 잰다. shm은 64칸 링에 memcpy로 넣고 빼며, 기다릴 때는 spin한다(코어가 남는 경우의 상한).

그림 5 — 측정 처리량(로그 스케일). Lima VM(aarch64, 4 vCPU, kernel 7.0)에서 잰 값이다. 세 번 반복해도 순위와 대략적인 크기는 같았다(pipe 64 KiB는 1.6~2.1 GB/s로 가장 많이 흔들렸다).

읽는 법:

  • 64 B: pipe·socket은 메시지당 syscall 1번(writer) + 커널 복사 2번이 고정 비용이다. 초당 2~3백만 메시지에서 막힌다. shm은 syscall이 없어서 약 5~8배 빠르다. 작은 메시지가 많으면 syscall 횟수가 병목이다 — 펌웨어에서 바이트마다 인터럽트를 받던 UART를 DMA로 바꾸던 것과 같은 이야기다. 소켓 쪽 개선책은 배치(여러 샘플을 한 write로) 또는 sendmmsg다.
  • 64 KiB: 기본 pipe(64 KiB)는 메시지 하나가 pipe 전체라서 writer와 reader가 매번 번갈아 잠들고 깬다. pipe를 1 MiB로 키우기만 해도 4배 빨라졌다. 이 VM에서는 UNIX stream socket(송신 버퍼 기본 wmem_default = 212992)이 pipe보다 빨랐는데, 커널 버전·버퍼 크기·CPU에 따라 순위가 바뀔 수 있으니 자기 보드에서 재는 것이 답이다.
  • shm은 64 KiB에서도 가장 빠르지만 0-copy가 아니라 memcpy 2번(넣기·빼기)을 했다. 진짜 0-copy는 consumer가 슬롯을 제자리에서 처리하거나 버퍼 자체(memfd/dmabuf)를 넘기는 것이다.

8.2 지연 (예제 15)#

무엇을 확인하는 코드인가: ping-pong 왕복 시간(RTT). 부모가 메시지를 보내면 자식이 받아서 그대로 돌려보낸다. shm은 두 가지로 잰다: shm_spin(상대를 계속 폴링)과 shm_sem(process-shared 세마포어로 잠들고 깨우기 = futex).

그림 6 — 측정 RTT 중앙값(선형). shm_sem(세마포어로 깨우기)은 pipe·socket과 거의 같고, shm_spin만 극적으로 작다.

이 결과가 이 노트에서 가장 중요한 교훈이다. shm이 빠른 이유는 "복사가 없어서"이지, "상대를 깨우는 게 빨라서"가 아니다. 상대가 잠들어 있으면 어떤 IPC든 커널이 그 스레드를 깨워 다른 CPU에서 스케줄해야 하고, 이 비용이 RTT의 대부분이다. 확인을 위해 두 프로세스를 같은 CPU 하나에 묶어 다시 쟀다.

출력에서 볼 것: 같은 CPU에서는 RTT가 27 µs → 1.8 µs로 15배 줄었다. 즉 앞의 27 µs는 거의 전부 다른 CPU에서 잠든 상대를 깨우는 비용(IPI + idle 상태 탈출 + 스케줄링)이고, 이 VM에서는 vCPU가 하이퍼바이저 위에서 잠들기 때문에 특히 크다. bare-metal 보드에서는 보통 이보다 훨씬 작지만, 구조는 같다. 실무 결론:

  • 저지연이 필요한 경로는 spin(busy-poll) + 전용 코어(isolcpus, N2)로 깨우기 자체를 없앤다. 대가는 코어 하나를 100% 쓰는 것이다.
  • 아니면 깨우는 횟수를 줄인다(배치 통지).
  • p99(꼬리 지연)가 중앙값보다 중요할 때가 많다. RT 튜닝(N2, N3)에서 다시 다룬다.
  • 측정 해상도: arm64의 CLOCK_MONOTONIC은 이 VM에서 약 42 ns 단위(24 MHz 카운터)라 0.12 µs 같은 값은 몇 tick 수준이다.

9. 커널 안에서는 무슨 일이 일어나나#

9.1 pipe = pipe_inode_info 안의 페이지 링#

pipe()는 pipefs라는 가상 파일시스템에 inode 하나를 만들고, 그 inode에 struct pipe_inode_info를 단다(fs/pipe.c, include/linux/pipe_fs_i.h). 핵심 필드:

  • bufs: struct pipe_buffer 배열(기본 16개 = PIPE_DEF_BUFFERS). 각 원소가 page, offset, len, ops를 가진다 — 즉 페이지 하나를 가리키는 슬롯.
  • head, tail: 링 인덱스. 계속 증가하고 & (ring_size - 1)로 슬롯을 고른다. 위 5.3절의 SPSC 링과 같은 규칙이다(커널 5.5부터 이 형태).
  • rd_wait, wr_wait: reader/writer가 잠드는 wait queue(F3).
  • mutex: pipe 하나에 대한 락. 여러 writer가 동시에 와도 이 락 때문에 PIPE_BUF 이하 write가 원자적이다.

그림 7 — pipe의 커널 내부. 슬롯 3~6에 데이터가 든 페이지가 있다. writer는 head 쪽 페이지에 복사해 넣고(마지막 페이지에 공간이 있으면 합쳐 넣음), reader는 tail 쪽 페이지에서 복사해 가고 페이지를 다 비우면 슬롯을 반납한다.

write()의 경로는 이렇다: write() → ksys_write() → vfs_write() → file->f_op->write_iter = pipe_write(). pipe_write()는 마지막 슬롯의 페이지에 자리가 있으면 거기에 이어 붙이고(merge), 아니면 새 페이지를 할당해 head 슬롯에 단다. 슬롯이 다 찼으면 wr_wait에서 잠든다. reader 쪽 pipe_read()는 tail 슬롯에서 copy_page_to_iter()로 복사하고, 그 페이지의 len이 0이 되면 페이지를 놓고 tail을 증가시킨다. 예제 1에서 "100바이트 읽어도 못 쓰고, 4096바이트 다 읽어야 쓸 수 있던" 현상이 정확히 이 동작이다.

pipe 페이지는 실제 struct page라서, splice()/vmsplice()로 복사 없이 페이지를 파일·소켓과 주고받을 수도 있다(고급 주제).

9.2 UNIX socket = socket 계층 + sk_buff 큐#

socket(AF_UNIX, ...)은 sockfs inode와 struct socket + struct sock을 만든다(net/unix/af_unix.c). send() → sock_sendmsg() → unix_stream_sendmsg()(또는 unix_dgram_sendmsg, unix_seqpacket_sendmsg)가 sk_buff를 할당해 데이터를 복사하고 상대 소켓의 sk_receive_queue에 직접 넣은 뒤 상대를 깨운다. TCP와 달리 IP 계층이 없고, 송신 버퍼 계정(sk_sndbuf)만 한다. recv()는 그 큐에서 skb를 꺼내 유저 버퍼로 복사한다. 메시지 경계는 skb 단위로 지켜진다(SEQPACKET/DGRAM은 skb 하나 = 메시지 하나, STREAM은 skb들을 이어 붙여 읽는다).

SCM_RIGHTS는 이 skb에 struct scm_fp_list(struct file 포인터 배열) 를 붙인다(net/core/scm.c). 보낼 때 각 file의 참조 카운트를 올리고, 받을 때 받는 프로세스의 fd 테이블에 새 fd를 설치한다(그림 3). 아무도 안 받은 채 소켓끼리 서로를 가리키는 순환이 생길 수 있어서, 커널에는 in-flight fd를 위한 전용 garbage collector(unix_gc)도 있다. 함수 이름은 커널 버전에 따라 조금씩 바뀌었으니 소스는 elixir에서 자기 버전으로 확인하자.

9.3 shm = 같은 물리 페이지를 두 번 매핑#

그림 8 — 세 방식의 데이터 경로 비교. 위 두 방식은 커널 객체를 거쳐 두 번 복사하고, shm은 MMU 설정만 커널이 한다.

shm_open()은 glibc가 /dev/shm/<name>을 open()하는 것이고, /dev/shm은 tmpfs(mm/shmem.c)다. mmap(MAP_SHARED)는 각 프로세스에 vm_area_struct를 만들고 vm_file이 같은 shmem 파일을 가리키게 한다. 처음 접근 때 page fault → shmem_fault()가 그 파일의 page cache에서 페이지(folio)를 찾거나 만들고 → 각 프로세스의 PTE에 같은 PFN을 써 넣는다. 예제 9에서 PFN이 같았던 이유다. POSIX mq는 ipc/mqueue.c의 mqueue 파일시스템이고 메시지를 커널 메모리에 우선순위별 트리로 보관한다(복사 2번).

process-shared 동기화 객체는 futex(A8)다. sem_post/pthread_mutex_unlock은 경쟁이 없으면 원자 연산만으로 끝나고(syscall 없음), 상대가 기다리고 있을 때만 futex(FUTEX_WAKE) syscall을 부른다. 공유 매핑의 futex는 커널이 (inode/page, offset) 으로 식별하고, 프로세스 전용(FUTEX_PRIVATE_FLAG)은 (mm, 가상 주소) 로 식별한다. 그래서 process-shared가 아닌 mutex를 shm에 두면 다른 프로세스와 서로를 못 깨운다 — pthread_mutexattr_setpshared(PTHREAD_PROCESS_SHARED)가 필수인 이유다.

10. Embedded 실무에서 다시 보기#

장면 1 — 센서 데몬과 로거: shm 링 + eventfd, 드롭은 숫자로#

예를 들어 센서 키트에서 imu_daemon(SCHED_FIFO, 400 Hz~1 kHz)이 로거·퓨전 프로세스에 샘플을 넘긴다. 설계: 소비자마다 SPSC 링(shm), producer는 절대 막히지 않고 가득 차면 드롭 + 카운터, 소비자는 eventfd를 epoll로 기다리고 producer는 10개 또는 10 ms마다 eventfd에 write한다. 샘플에는 seq와 CLOCK_MONOTONIC 타임스탬프(Q3)를 넣어 소비자가 손실·지터를 직접 측정한다(Q7). 예제 10의 gaps_seen == dropped 검사가 바로 그 데이터 품질 도구의 핵심이다.

장면 2 — 카메라: 프레임은 fd로, 메타데이터는 소켓으로#

camera_daemon이 V4L2 버퍼를 VIDIOC_EXPBUF로 dmabuf fd로 만들고, SEQPACKET 소켓으로 {frame_id, timestamp, format} 메시지 + SCM_RIGHTS fd를 인코더와 추론 프로세스에 보낸다. 받은 쪽은 처리 후 "frame_id 반납" 메시지를 돌려보내고 fd를 닫는다. 3 MB 프레임이 한 번도 복사되지 않는다. 버그 패턴: 반납 메시지를 빼먹으면 V4L2 큐에 버퍼가 안 돌아와 몇 프레임 뒤에 캡처가 멈춘다(VIDIOC_DQBUF가 안 깨어남) — 리소스 반납 프로토콜이 IPC 설계의 절반이다.

장면 3 — 제어 채널: UNIX socket + SO_PEERCRED#

진단 툴(sensorctl)이 데몬에게 "샘플레이트 변경" 같은 명령을 보낸다. /run/sensor/ctl.sock(그룹 sensor, 0660) + SEQPACKET + 요청마다 SO_PEERCRED로 uid 확인. root가 아닌 사용자는 읽기 명령만 허용. 데몬이 재시작해도 클라이언트는 EOF/ECONNRESET을 받고 재접속한다.

장면 4 — 시스템 통합: D-Bus는 제어, 데이터는 따로#

LTE 모뎀 상태는 ModemManager에 D-Bus로 묻고, 네트워크 설정은 NetworkManager/systemd-networkd에 D-Bus로 요청한다(L3). 텔레메트리 데이터 자체는 uploader가 소켓으로 직접 보낸다. "D-Bus에 센서 데이터를 싣자"는 제안이 나오면 6.2절의 이유로 반대할 수 있어야 한다.

12. 면접에서 이렇게 말한다#

Q. "What IPC mechanisms does Linux provide, and how do you choose between them?"

A. 바이트 스트림(pipe, FIFO, UNIX stream socket), 메시지(UNIX SEQPACKET/DGRAM, POSIX mq), 공유 메모리(POSIX shm, memfd/dmabuf), 그리고 그 위의 버스(D-Bus)로 나눈다. 고르는 기준은 복사 횟수, 메시지 경계, 깨우기 비용, 다중 수신자, 크래시 시 동작이다. 제어는 UNIX socket, 고속 데이터는 shm 링, 큰 버퍼는 fd 전달, 시스템 서비스는 D-Bus.

I group them into byte streams — pipes, FIFOs, UNIX stream sockets — message-oriented ones like SEQPACKET sockets and POSIX message queues, and shared memory, with D-Bus on top for system services. I choose by copies, message boundaries, wake-up cost, fan-out, and what happens when one side crashes. In practice: UNIX sockets for control, a shared-memory ring for high-rate sensor data, and fd passing for large buffers like camera frames.

꼬리 질문: "Why not just use TCP on localhost?" → 동작은 하지만 IP 스택 비용이 있고, SO_PEERCRED·SCM_RIGHTS·파일 권한 기반 접근 제어가 없다.

Q. "Why is shared memory the fastest IPC, and what's the catch?"

A. 커널이 MMU 설정만 하고 데이터 경로에서 빠지니까 syscall도 복사도 없다. 대가는 동기화·메모리 순서·통지·크래시 처리를 전부 직접 해야 한다는 것. 그리고 측정해 보면 상대를 futex로 깨우는 순간 지연은 pipe와 같아진다 — 빠른 건 복사가 없어서지 wakeup이 빨라서가 아니다.

The kernel only sets up the page tables; after that it's plain loads and stores, so no syscalls and no copies. The catch is you own synchronization, memory ordering, notification and crash recovery. And when I measured it, shared memory with a semaphore wake-up had the same round-trip latency as a pipe — about 27 microseconds on my VM — while busy-polling was 0.1 microseconds. The win is fewer copies, not faster wake-ups.

꼬리 질문: "What if the process holding the lock dies?" → robust mutex(EOWNERDEAD → 검증 → pthread_mutex_consistent) 또는 락 없는 SPSC 설계.

Q. "How would you pass a camera frame to another process without copying?"

A. V4L2 버퍼를 VIDIOC_EXPBUF로 dmabuf fd로 내보내고, UNIX socket의 SCM_RIGHTS로 그 fd를 보낸다. 커널은 struct file 참조를 넘기고 받는 쪽에 새 fd를 설치한다. 받는 쪽은 mmap하거나 GPU/인코더에 import한다. 버퍼 반납 프로토콜과 fd close를 같이 설계한다.

Export the V4L2 buffer as a dma-buf file descriptor with VIDIOC_EXPBUF, then send that fd over a UNIX domain socket using SCM_RIGHTS. The kernel passes a reference to the same struct file and installs a new fd number in the receiver, which can mmap it or import it into the encoder or GPU. The frame is never copied, but you need a clear return protocol so buffers go back to the capture queue.

Q. "What happens when you write to a pipe? What's PIPE_BUF?"

A. pipe는 커널 안 페이지 링(기본 16페이지, 64 KiB)이다. write는 유저 데이터를 그 페이지에 복사하고 reader를 깨운다. 가득 차면 writer가 잠든다. PIPE_BUF(Linux 4096) 이하 write는 원자적이라 여러 writer가 있어도 안 섞인다. 넘으면 섞일 수 있다 — 직접 재 보니 4097바이트에서 바로 찢어졌다. reader가 없으면 SIGPIPE/EPIPE.

A pipe is a ring of page-sized buffers in the kernel, 64 KiB by default. write copies into those pages and wakes the reader; if it's full the writer sleeps. Writes up to PIPE_BUF, 4096 bytes on Linux, are atomic, so concurrent writers don't interleave; above that they can — I saw torn records at 4097 bytes. Writing with no readers gives SIGPIPE or EPIPE.

Q. "How do you frame messages over a stream socket?"

A. 스트림은 경계가 없어서 send 3번이 recv 1번으로 올 수도, 그 반대일 수도 있다. 길이 프리픽스(고정 크기 헤더 + 본문)를 두고, 정확히 n바이트를 다 읽을 때까지 루프 돈다. 로컬이면 SEQPACKET으로 커널이 경계를 지키게 하는 방법도 있다.

A stream has no boundaries — three sends can arrive as one recv or one send as several. I use a length prefix, a fixed header followed by the payload, and a read-exactly-n loop that handles short reads. For local IPC, SOCK_SEQPACKET gives you reliable, ordered messages with boundaries preserved by the kernel.

Q. "Design the IPC for a robot with an IMU daemon, a camera daemon, a logger and an uploader."

A. IMU → 소비자별 SPSC shm 링 + eventfd 배치 통지, 가득 차면 드롭 + 카운터. 카메라 → dmabuf fd를 SEQPACKET + SCM_RIGHTS로, 반납 메시지로 버퍼 순환. 제어·상태 → UNIX socket + SO_PEERCRED. 프로세스 분리로 장애 격리·권한 분리, systemd가 재시작. 모든 메시지에 seq와 모노토닉 타임스탬프를 넣어 손실·지연을 측정한다.

High-rate IMU samples go through a per-consumer single-producer single-consumer ring in shared memory, with eventfd notifications batched, and the producer never blocks — it drops and counts. Camera frames are passed as dma-buf fds over a SEQPACKET socket with SCM_RIGHTS, with an explicit release message. Control and health use UNIX sockets with SO_PEERCRED checks. Each daemon is a separate process for fault isolation and least privilege, restarted by systemd, and every message carries a sequence number and a monotonic timestamp so we can measure loss and latency.

Q. "When would you use D-Bus, and when not?"

A. 시스템 서비스(NetworkManager, systemd, BlueZ)와 대화하거나, 서비스 발견·타입 있는 메서드 호출·브로드캐스트 시그널이 필요할 때. 버스 데몬을 거치고 직렬화가 있어서 초당 수천 메시지 이상의 데이터 경로에는 안 쓴다.

For talking to system services — systemd, NetworkManager, BlueZ — and for low-rate control with discovery, typed method calls and broadcast signals. Every message goes through the bus daemon and gets marshalled, so I don't put sensor or video data on it; at most I negotiate over D-Bus and pass an fd for the bulk data.

15. 요약 & 체크리스트#

Embedded Linux 장비는 장애 격리와 권한 분리를 위해 기능을 프로세스로 쪼개고, 그 경계를 IPC로 넘는다. pipe/FIFO는 커널 페이지 링 위의 단방향 바이트 스트림이고(PIPE_BUF 이하만 원자적, EOF·SIGPIPE로 크래시가 깔끔), UNIX domain socket은 양방향·경계 보존(SEQPACKET)·자격 증명·fd 전달까지 되는 실무 주력이다. POSIX mq는 우선순위 우편함, POSIX shm은 같은 물리 페이지를 두 번 매핑해 복사를 없애지만 동기화·순서·통지·크래시 처리를 직접 설계해야 한다(SPSC 링 + release/acquire + futex/eventfd, robust mutex). D-Bus는 시스템 서비스 제어용이고 ROS 2/ZeroMQ는 이 위에 얹힌다. 직접 재 보면 작은 메시지는 syscall 수가, 큰 메시지는 복사가, 지연은 상대를 깨우는 비용이 지배한다.
