J3. 읽기전용 · 메모리 파일시스템 — SquashFS · EROFS · tmpfs · overlayfs로 견고한 rootfs 만들기

210분 읽기2095줄65개 절

이 노트를 다 읽으면: 같은 rootfs를 SquashFS(gzip·xz·zstd·lz4, 블록 4K~1M)와 EROFS(lz4·lzma·zstd)로 묶고 크기·순차 읽기·첫 접근 지연을 직접 재서 압축기를 고를 수 있다 · tmpfs·ramfs·devtmpfs·zram의 차이(크기 제한, swap, /proc/meminfo 회계)를 실측으로 설명할 수 있다 · overlayfs의 copy-up·whiteout·opaque·redirect를 upper 디렉터리에서 눈으로 확인하고 무엇이 깨지는지(inode 번호, hard link, 디렉터리 rename) 말할 수 있다 · initramfs /init으로 "squashfs 루트 + overlay 상위층 + switch_root"를 만들고, dm-verity를 ioctl로 직접 올려 바이트 하나 변조가 I/O error·SIGBUS·재부팅으로 이어지는 것을 보여 줄 수 있다 왜 필요한가: 필드 장비 rootfs 설계 질문("전원이 아무 때나 끊기는 드론의 rootfs를 어떻게 만들겠나?", "OTA 후 이미지가 공장 이미지와 같다는 걸 어떻게 보장하나?")은 Embedded Linux 면접의 단골이고, 입사 후 Yocto·Buildroot 이미지 레시피에서 IMAGE_FSTYPES = "squashfs-zst", overlayfs-etc 같은 결정을 바로 하게 된다 Don 기준 난이도: 압축 블록·FTL·매핑 테이블·전원 차단 내성·펌웨어 이미지 무결성(CRC/서명)은 SSD 펌웨어에서 이미 안다 / Linux에서 그 개념이 "파일시스템 형식 + page cache + VFS 스택(overlay) + device-mapper"로 나뉘어 있다는 점, 각 층의 함정(이중 캐싱, copy-up 비용, whiteout)이 새로 배울 부분 선행 노트: C7(initramfs·switch_root), J1(저장장치), J2(ext4·파티션) — K1(rootfs 구조)은 있으면 좋지만 C7만으로도 따라올 수 있다

0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어에서 "코드 영역"은 절대 런타임에 덮어쓰지 않았다. 펌웨어 이미지는 통째로 서명·검증되고, 업데이트는 다른 슬롯에 새 이미지를 쓴 뒤 포인터만 바꿨다. 런타임에 바뀌는 것(매핑 테이블, 로그, SMART 카운터)은 따로 관리되는 영역에 저널·체크포인트와 함께 썼다.

Embedded Linux 장비의 rootfs도 똑같이 설계한다. 다만 "펌웨어 이미지" 자리에 파일시스템 이미지가 들어간다.

  • 읽기전용 하층: /usr, /lib, /bin, 기본 /etc가 들어 있는 압축 이미지(SquashFS 또는 EROFS). 빌드 서버에서 만들어 한 번 쓰면 끝. 장비에서는 절대 쓰지 않는다.
  • 쓰기 가능한 상층: overlayfs가 읽기전용 하층 위에 얇은 쓰기층(upper)을 겹쳐서 "보통의 쓰기 가능한 /"처럼 보이게 한다. upper를 RAM(tmpfs)에 두면 재부팅마다 공장 상태로, 데이터 파티션에 두면 설정이 남는다.
  • 무결성: dm-verity가 하층 이미지의 모든 4 KiB 블록을 읽을 때마다 해시 트리로 검증한다. 루트 해시 하나만 믿으면(서명된 커널 cmdline에 넣으면) 이미지 전체를 믿을 수 있다.
  • 메모리 FS: /run, /tmp는 tmpfs, /dev는 devtmpfs. 로그·센서 데이터는 데이터 파티션(ext4·F2FS).

그림 1 — 필드 장비에서 흔한 "RO 루트 + RW 상층" 구조. 이 노트는 가운데 세 층(SquashFS/EROFS, overlayfs, dm-verity 입문)과 메모리 FS를 다룬다. A/B 슬롯 전환과 롤백은 L4, verity·dm-crypt의 보안 깊이(서명, 키, FEC)는 L6에서 다룬다.

이 노트의 실험은 전부 직접 돌렸다.

  • 이미지 생성: Mac(M2) 위 Lima VM elinux(aarch64, Ubuntu 26.04, uname -r = 7.0.0-38-generic)에서 mksquashfs 4.7.5, mkfs.erofs 1.9, veritysetup 2.8.4로 만들었다. VM 쪽 작업 폴더는 /var/tmp/J3/, 소스는 ~/.elinux_scratch/J3/.
  • 읽기 측정과 부팅: 공용 랩의 저장장치용 커널 /var/lab/out/Image-fs (Linux 6.18.55-fs) 를 QEMU virt(-cpu cortex-a57 -m 512M, KVM 없는 TCG 에뮬레이션)로 부팅하고, 이미지를 virtio-blk 디스크로 붙였다.
  • 주의: TCG는 CPU를 소프트웨어로 흉내 내므로 압축 해제가 실제 Cortex-A보다 훨씬 느리다. 그래서 절대값(MB/s, µs)은 실제 보드와 다르고, 압축기 사이의 상대 순서와 경향만 믿어야 한다. 다른 작성자들이 같은 VM을 쓰고 있어 측정값이 10~30% 흔들린다.

1. 왜 필드 장비는 읽기전용 rootfs를 쓰나#

1.1 직관 — "코드 영역은 쓰지 않는다"#

ext4 rootfs를 rw로 마운트해서 쓰는 장비를 생각해 보자. 센서 키트 드론이 비행 중 배터리가 빠진다. 그 순간 패키지 매니저가 /usr/lib/libfoo.so를 교체하고 있었다면? 저널이 메타데이터는 지켜 주지만(J5), "반쯤 바뀐 라이브러리 세트"는 지켜 주지 않는다. 다음 부팅에서 앱이 이상한 심볼 에러로 죽는다. 펌웨어로 치면 코드 영역을 런타임에 부분 덮어쓰기 하다가 전원이 나간 상태다.

읽기전용 rootfs는 이 문제를 구조적으로 없앤다. 쓰지 않는 영역은 깨질 수가 없다.

1.2 이유 다섯 가지#

이유설명SSD 펌웨어에 빗대면
전원 차단 내성루트는 쓰지 않으니 fsck·저널 복구 대상이 아니다. 쓰는 곳(data)만 J5의 규칙으로 지키면 된다코드 영역은 read-only, 메타데이터만 저널링
이미지 동일성장비 1만 대의 /usr가 비트 단위로 같다. "이 장비만 이상해요"를 재현할 수 있다같은 펌웨어 빌드 = 같은 바이너리 해시
무결성 검증이미지가 안 바뀌니 해시 트리(dm-verity)로 블록마다 검증 가능부팅 시 FW 이미지 서명 검증, 그걸 런타임까지 확장
원자적 업데이트파일 단위 패치 대신 이미지 통째로 다른 슬롯에 쓰고 전환(A/B, L4)듀얼 뱅크 펌웨어 슬롯
공장 초기화쓰기층만 지우면 공장 상태사용자 영역 secure erase

추가로 압축이 공짜로 따라온다. 쓸 일이 없으니 "쓰기 가능한 압축 FS"의 복잡함(재압축, 단편화) 없이 고압축을 쓸 수 있다. eMMC 8 GB짜리 보드에서 rootfs 1.2 GB가 450 MB가 되면, A/B 두 슬롯을 넣고도 데이터 파티션이 넉넉해진다.

1.3 대가#

  • 쓰고 싶은 곳이 생긴다: /etc/hostname, 네트워크 설정, SSH 호스트 키, /var/lib 상태 파일. 이것을 처리하는 장치가 overlayfs(§7)와 "/var는 데이터 파티션" 같은 설계 규칙(§8)이다.
  • 압축 해제 CPU 비용: 랜덤 읽기마다 블록을 풀어야 한다. 압축기와 블록 크기 선택이 부팅 시간과 앱 시작 시간을 바꾼다(§5에서 잰다).
  • 개발 편의성 저하: 장비에서 vi /usr/bin/script 한 번으로 고치던 습관이 안 통한다. 개발 빌드는 rw, 양산 빌드는 ro로 나누는 것이 보통이다.

2. 실험 준비 — 같은 트리를 여러 형식으로#

2.1 랩 커널에 무엇이 켜져 있나#

무엇을 확인하나: Image-fs 커널이 이 노트의 FS들을 어떻게(built-in =y / 모듈 =m) 갖고 있는지.

출력에서 볼 것:

  • SquashFS·overlayfs·tmpfs는 built-in이다. 그래서 SquashFS는 root=/dev/vda rootfstype=squashfs로 initramfs 없이도 루트가 될 수 있다(그 위에 overlay를 얹으려면 결국 initramfs나 이른 init 스크립트가 필요하다). EROFS·dm-verity·zram은 모듈이라 initramfs에서 insmod해야 한다. 루트 FS 드라이버를 모듈로 두면 initramfs가 필수라는 C7의 규칙 그대로다.
  • OVERLAY_FS_REDIRECT_DIR, INDEX, XINO_AUTO, METACOPY가 전부 꺼져 있다 = overlayfs의 "보수적인 기본값". 이 기본값에서 무엇이 깨지는지 §7.5에서 본다.
  • SQUASHFS_FILE_CACHE, SQUASHFS_DECOMP_SINGLE은 SquashFS의 성능 관련 선택이다(§3.5).

2.2 공용 rootfs 트리 만들기#

무엇을 확인하나: 모든 이미지에 넣을 "그럴듯한 rootfs" — BusyBox 랩 rootfs + 텍스트 문서(작은 파일 다수) + ELF 바이너리·공유 라이브러리(큰 파일 몇 개).

정규 파일 1,366개, 43,043,123 바이트(41.0 MiB). 그중 gdb(11.1 MiB) 하나를 랜덤 읽기 측정 대상으로 쓴다 — 실행 파일의 page fault가 바로 "큰 파일의 랜덤 4 KiB 읽기"이기 때문이다.

2.3 16가지 이미지 만들기#

무엇을 확인하나: 같은 트리를 압축기·블록 크기만 바꿔 묶었을 때 크기가 어떻게 달라지는지.

출력에서 볼 것: 16개 이미지 전부 22초. mksquashfs -all-root·mkfs.erofs --all-root는 소유자를 root로 바꾼다(빌드 서버의 일반 사용자 UID가 이미지에 박히는 흔한 실수 방지). mksquashfs·mkfs.erofs는 원래 디렉터리를 입력으로 받고, mkfs.ext4도 -d로 디렉터리에서 바로 이미지를 만들어서 마운트 없이(root 권한 없이) 이미지를 만들 수 있다 — Yocto·Buildroot도 이렇게 한다. 숫자의 해석은 §5에서 측정값과 함께 한다.

같은 조건에서 압축기별 생성 시간도 쟀다(VM 6코어 중 2스레드, 다른 작업과 경쟁 중).

xz·lzma는 압축이 느리다(빌드 서버 비용). 41 MiB에선 몇 초지만 1.5 GB rootfs면 Yocto 빌드에서 분 단위가 된다. 장비 쪽에서 중요한 건 압축 해제 비용이고, 그건 §5에서 따로 잰다.

3. SquashFS — 가장 오래된 표준 읽기전용 압축 FS#

3.1 정의#

SquashFS는 2002년부터 쓰인 읽기전용 압축 파일시스템이다(메인라인 2.6.29). 파일 데이터를 고정 크기 입력 블록(block_size, 4 KiB~1 MiB, 기본 128 KiB)으로 잘라 각각 압축하고, 메타데이터(inode, 디렉터리, fragment·id 테이블)도 8 KiB 단위로 압축해서 이미지 끝에 모아 둔다. OpenWrt 라우터, 많은 Yocto·Buildroot 제품 이미지, Ubuntu snap, 라이브 CD가 SquashFS다.

3.2 디스크 위 배치#

무엇을 확인하나: 슈퍼블록(96 바이트)에 들어 있는 테이블 위치를 직접 파싱해서, 이미지의 99% 이상이 데이터이고 메타데이터가 끝에 모여 있음을 본다.

출력에서 볼 것: magic hsqs(리틀엔디언으로 0x73717368), comp_id 4 = xz. 데이터 영역이 0 ~ 13,955,140 바이트(99.75%)이고, 메타데이터 테이블 여섯 개를 다 합쳐도 34,816 바이트다. xattr_table이 0xffff…(없음)인 이유는 트리에 xattr이 없어서다.

그림 2 — SquashFS 배치. 파일 데이터는 고정 크기 입력 블록마다 따로 압축되어 가변 크기로 저장된다. block_size보다 작은 파일(또는 큰 파일의 꼬리, -tailends 옵션일 때)은 fragment 블록에 모아 같이 압축된다. 메타데이터는 이미지 끝의 테이블들에 있다.

3.3 unsquashfs -s — 이미지 속성 보기#

무엇을 확인하나: 장비나 빌드 서버에서 SquashFS 이미지의 압축기·블록 크기·fragment 수를 확인하는 표준 명령.

출력에서 볼 것:

  • Filesystem size 13989956 = 슈퍼블록의 bytes_used와 같다. 파일 크기(13,991,936)가 조금 더 큰 건 mksquashfs가 끝을 4 KiB 배수로 패딩하기 때문이다 — 이 패딩 덕분에 dm-verity(4 KiB 블록) 밑에 바로 놓을 수 있다.
  • Duplicates are removed: 내용이 같은 파일은 한 번만 저장한다(파일 단위 dedupe). §4.4에서 EROFS와 비교한다.
  • Number of fragments 112: 작은 파일 1천여 개가 fragment 블록 112개에 모였다.
  • Tailends are not packed into fragments: mksquashfs 4.7의 기본값. 큰 파일의 꼬리는 자기 블록으로 남는다.

3.4 블록 크기와 fragment — 압축률 vs 랜덤 읽기#

블록이 크면 압축기가 더 긴 문맥을 보므로 압축률이 좋아진다. 대신 4 KiB 한 페이지를 읽으려 해도 그 페이지가 든 블록 전체를 풀어야 한다. 128 KiB 블록이면 4 KiB를 위해 32배를 푼다. 이것이 SquashFS의 "랜덤 읽기 증폭(read amplification)"이다 — SSD의 "4 KiB 호스트 쓰기가 16 KiB NAND 페이지 프로그램이 되는 것"과 같은 모양이다.

SquashFS는 이 낭비를 page cache로 일부 회수한다. 블록을 풀면 그 블록에 속한 모든 페이지를 page cache에 채워 넣는다(squashfs_readahead, squashfs_copy_cache). 그래서 같은 블록의 다른 페이지를 곧 읽으면 공짜다. 결과적으로:

  • 작은 파일을 처음부터 끝까지 읽는 패턴: 큰 블록이 유리(해제 횟수가 적다).
  • 큰 파일을 듬성듬성 한 번씩만 찍는 패턴(실행 파일 page fault, 데이터베이스): 작은 블록이 유리.
  • 메모리 압박으로 page cache가 자주 쫓겨나는 장비: 큰 블록은 같은 블록을 몇 번이고 다시 푼다.

fragment는 작은 파일들을 한 블록에 모아 압축률을 올린다. 대가는 두 가지다. (1) 작은 파일 하나를 읽으려 해도 fragment 블록 전체를 푼다. (2) fragment 블록 하나가 깨지면 그 안의 파일 전부가 깨진다 — §10.4에서 바이트 하나 변조로 파일 11개가 동시에 I/O error가 나는 것을 직접 본다.

  • SQUASHFS_FILE_CACHE vs SQUASHFS_FILE_DIRECT: FILE_CACHE(랩 커널)는 블록을 내부 캐시 버퍼에 먼저 풀고 page cache 페이지로 복사한다. FILE_DIRECT는 page cache 페이지에 바로 푼다(복사 1회 절약). Kconfig 도움말 기준이며, 이 노트에서 두 설정을 비교 측정하지는 않았다.
  • SQUASHFS_DECOMP_SINGLE / _MULTI / _MULTI_PERCPU: SINGLE(랩 커널)은 파일시스템당 해제기 하나를 잠금으로 공유한다 — 여러 스레드가 동시에 읽어도 해제는 한 줄로 선다. 멀티코어 SoC에서 앱 여러 개가 동시에 시작하는 부팅 구간이라면 MULTI_PERCPU가 낫다. 이 실험은 단일 CPU 게스트라 차이가 드러나지 않는다.

4. EROFS — "고정 크기 출력" 압축과 Android#

4.1 정의와 핵심 아이디어#

EROFS(Enhanced Read-Only File System)는 Huawei의 Gao Xiang 등이 Android 스마트폰 시스템 파티션용으로 만든 읽기전용 FS다. 4.19에서 staging으로 들어와 5.4에서 fs/erofs로 정식 편입됐다. AOSP 빌드 시스템이 EROFS 시스템 이미지를 지원하고, 여러 Android 기기의 system/vendor 파티션이 EROFS다. 최근에는 컨테이너 이미지(Nydus, composefs)에서도 쓰인다.

SquashFS와의 결정적 차이는 압축 단위의 방향이다.

  • SquashFS: 입력 고정(128 KiB씩 잘라서 압축) → 출력 크기 가변 → 디스크 위 압축 블록이 4 KiB 경계에 정렬되지 않는다. 블록 하나를 읽으려면 앞뒤 디스크 블록을 함께 읽고, 일부만 쓰고 버린다.
  • EROFS: 출력 고정(압축 결과가 정확히 pcluster 크기, 기본 4 KiB가 되도록 입력을 가변 길이로 자른다) → 디스크 블록 하나 = 압축 단위 하나. 읽기 I/O가 정확히 4 KiB 정렬이고 낭비가 없다.

4.3 in-place decompression과 메모리#

EROFS는 해제할 때 page cache 페이지를 최대한 재활용한다.

  • 압축 데이터를 읽어 올 버퍼로, 어차피 해제 결과가 들어갈 page cache 페이지 자체를 쓸 수 있다(in-place I/O). 압축 데이터가 pcluster 끝에 붙어 있으니(lz4_0padding), 앞에서부터 풀어 나가도 아직 안 읽은 입력을 덮어쓰지 않는다.
  • 그래서 메모리가 빠듯한 폰에서 "압축 데이터용 임시 버퍼 + 해제 결과" 두 벌을 잡지 않아도 된다. 기본 캐시 전략 cache_strategy=readaround(마운트 옵션에서 보인다)는 pcluster 주변만 캐시한다.

§5.4의 page cache 측정에서 이 차이가 숫자로 나온다: 같은 41 MiB를 다 읽은 뒤 EROFS는 page cache가 47 MiB 늘고, SquashFS는 59 MiB 늘었다.

4.4 dedupe와 그 밖의 mkfs 옵션#

무엇을 확인하나: 같은 파일 두 벌을 넣었을 때 SquashFS(기본 dedupe)와 EROFS(-Ededupe 유무)의 크기.

출력에서 볼 것: EROFS는 기본으로는 두 벌을 다 저장하고(13.4 MB), -Ededupe를 주면 압축 데이터 단위로 중복을 지워 한 벌(6.7 MB)이 된다. SquashFS는 아무 옵션 없이 파일 단위 중복 제거를 한다. EROFS의 dedupe는 파일 일부만 같아도(pcluster 단위) 잡을 수 있다는 점이 다르다.

관찰 메모: 이 VM의 erofs-utils 1.9에서 전체 트리(tree/)에 -Ededupe를 주면 오류 메시지 없이 inode 22개짜리 8 KiB 이미지가 나왔다. 원인은 조사하지 않았다. 양산 이미지 레시피에 새 mkfs 옵션을 넣을 때는 fsck.erofs나 마운트 후 파일 수 비교 같은 검증 단계를 반드시 둔다.

그 밖에 자주 보는 mkfs.erofs 옵션: -zlz4hc(압축기 지정, 레벨 문법은 erofs-utils 버전마다 다르니 man mkfs.erofs 확인), -C<bytes>(최대 pcluster 크기), -Eztailpacking(작은 꼬리를 inode 옆에 인라인), -Efragments(SquashFS fragment와 비슷하게 꼬리들을 모음), --all-root, -T<epoch>(재현 가능한 빌드용 고정 타임스탬프).

해석:

  • EROFS를 블록 장치에서 마운트: +47 MiB ≈ 풀린 데이터 41 + 메타데이터. 압축 데이터는 거의 남기지 않는다.
  • SquashFS를 블록 장치에서 마운트: +59 MiB ≈ 41 + 압축 이미지 14.8. 6.18의 SquashFS는 장치 블록 크기가 페이지 크기와 같으면 압축 블록을 자기 전용 page cache(msblk->cache_mapping, fs/squashfs/super.c)에 남긴다. 해제된 데이터와 압축 데이터가 둘 다 메모리에 있다.
  • loop 장치 경유: +74 MiB. loop 장치 아래 백킹 파일의 page cache(ext4 쪽)가 한 벌 더 생긴다. ext4 위의 이미지 파일을 loop으로 마운트하는 구성(개발 보드에서 흔하다)은 압축 데이터를 두 번 캐시한다.
  • EROFS file-backed, 기본: +73 MiB. loop은 없지만 기본으로는 백킹 파일을 buffered I/O로 읽어서 역시 이중 캐싱이다.
  • EROFS file-backed + directio: +48 MiB. 백킹 파일을 direct I/O로 읽어 압축 데이터가 page cache에 남지 않는다. 대신 순차 속도가 71.6 → 48.6 MB/s로 떨어졌다(캐시 없는 작은 I/O).

메모리 256 MB짜리 센서 노드라면 "이미지 크기만큼 RAM을 더 먹는" 차이는 크다. 압축 이미지를 eMMC 파티션에 직접 쓰고 블록 장치로 마운트하는 것이 기본이고, 파일에 두어야 한다면 EROFS의 file-backed + directio를 검토한다.

  • Shmem과 Cached가 함께 16 MiB 늘었다. tmpfs 데이터는 Cached에 포함되지만 drop_caches로 버릴 수 없다. free의 "buff/cache"를 "언제든 회수 가능한 메모리"로 읽으면 틀린다 — 그 안의 Shmem은 회수가 안 된다(swap이 있을 때만 밀려난다).

  • size=는 상한일 뿐 미리 예약하지 않는다. 쓰기 전에는 RAM을 먹지 않는다.

6.3 ramfs — 상한 없이 자란다#

출력에서 볼 것: 200 MB를 썼는데 df는 0이다. 메모리는 Unevictable로 잡혀 drop_caches로도 안 빠지고, Shmem에도 안 잡힌다(모니터링이 Shmem만 보면 놓친다). 512 MB 게스트에서 더 쓰면 OOM killer가 엉뚱한 프로세스를 죽인다. ramfs는 쓰지 않는다 — 크기 제한이 필요 없는 아주 특수한 경우(커널이 쓰는 내부 용도)뿐이다.

6.4 devtmpfs#

devtmpfs는 커널이 장치를 등록할 때(device_add() → devtmpfs_create_node()) 노드를 자동으로 만들어 주는 tmpfs다. 크기 기본값(215,140 KiB)은 게스트 RAM의 절반 정도다. 덕분에 udev 없는 작은 initramfs에서도 /dev/vda, /dev/mapper/control, /dev/dm-0이 저절로 생긴다 — §10의 dm-verity 실습이 udev 없이 되는 이유다. 장치 노드의 권한·심볼릭 링크 규칙은 L2(udev)에서 다룬다.

6.5 zram — 압축 RAM 블록 장치 (간단히)#

zram은 RAM 안에 압축된 블록 장치(/dev/zram0)를 만든다. 주 용도는 압축 swap이다. swap 파티션을 eMMC에 두면 수명을 갉아먹으니, 메모리가 빠듯한 장비(Android, ChromeOS, 작은 게이트웨이)는 zram swap으로 "RAM을 1.5~3배처럼" 쓴다. tmpfs와 조합하면 "tmpfs 페이지가 zram swap으로 압축되어 밀려나는" 구성이 된다.

출력에서 볼 것: 랩 커널은 lzo 계열만 켜져 있다([lzo-rle]가 선택됨). 텍스트(스크립트 + /proc/kallsyms) 10.3 MB가 압축 3.4 MB, 실제 메모리 사용 4.0 MB(zsmalloc 오버헤드 포함)가 됐다. mm_stat 처음 세 칸이 orig_data_size, compr_data_size, mem_used_total이다. 실제 장비에서는 mkswap /dev/zram0 && swapon /dev/zram0(또는 systemd의 zram-generator)로 swap으로 쓴다 — 이 노트에서는 swap 활성화까지는 하지 않았다.

7. overlayfs — 읽기전용 위에 쓰기층 겹치기#

7.1 직관#

투명 필름 두 장을 겹친 것과 같다. 아래 필름(lower)에는 공장에서 인쇄한 그림이 있고, 위 필름(upper)은 처음엔 비어 있다. 위에서 보면 아래 그림이 그대로 보인다. 어떤 칸을 고치고 싶으면 그 칸을 위 필름에 통째로 베껴 그린 다음(copy-up) 고친다. 칸을 지우고 싶으면 위 필름에 "여기 비어 있음" 스티커(whiteout)를 붙인다. 아래 필름은 한 번도 건드리지 않는다.

펌웨어로 치면 ROM 패치 테이블과 같다. ROM 코드는 못 바꾸니, 패치할 함수만 RAM에 복사해서 고치고 패치 테이블로 그쪽을 가리키게 한다.

7.2 정의#

  • lowerdir: 읽기전용 층. 여러 개면 lowerdir=/l2:/l1처럼 콜론으로 잇고, 왼쪽이 위다.
  • upperdir: 쓰기가 가는 디렉터리. 쓰기 가능한 FS(tmpfs, ext4, F2FS …)여야 하고 trusted.* xattr와 d_type을 지원해야 한다.
  • workdir: upper와 같은 FS의 빈 디렉터리. copy-up을 임시 파일로 준비했다가 rename()으로 원자적으로 upper에 넣는 작업 공간이다(전원 차단 중에도 upper에 반쯤 복사된 파일이 보이지 않게).
  • merged: 사용자가 보는 결과.

규칙: 이름이 upper에 있으면 upper가 이긴다. 디렉터리는 양쪽 내용이 합쳐진다(merge). 파일은 합쳐지지 않고 위의 것이 아래 것을 가린다.

7.3 관찰 도구#

무엇을 확인하나: overlay가 만든 upper 쪽 흔적을 보는 세 가지 — lstat(dev·ino·nlink·종류·rdev), xattr 목록, 그리고 mv가 숨기는 rename(2)의 진짜 반환값.

VM 호스트에서 gcc -std=gnu11 -Wall -Wextra -O2 -static으로 경고 없이 빌드된다. lower는 작은 실험용 squashfs다: etc/hostname, etc/app.conf(rate=100), etc/net/{eth0,wlan0}.conf, data/logs/old.log, hard link 쌍 usr/bin/tool_a·tool_b, 1 MiB 랜덤 big/blob.

7.4 실습 — copy-up, whiteout, opaque, redirect#

게스트 스크립트 ovl.sh를 set -x로 돌렸다. squashfs lower를 /lower, tmpfs를 /up에 올리고 overlay를 /merged에 만든다. 출력은 실행 그대로이고, 절별로 끊어서 설명한다.

inode 번호와 st_dev: lower의 app.conf는 squashfs 장치 254:0의 ino 7이다. merged에서 같은 파일은 ino는 7로 같지만 dev가 0:28이다. 디렉터리는 overlay 자신의 dev 0:26. overlayfs는 레이어들이 서로 다른 FS에 있을 때(여기선 squashfs와 tmpfs) 파일의 ino를 레이어 것 그대로 쓰고, 번호가 겹치지 않도록 레이어마다 다른 익명 st_dev를 붙인다(xino 기능이 꺼져 있을 때). 그래서 merged 안에서 (st_dev, st_ino) 쌍은 유일하지만, "같은 FS면 st_dev가 같다"는 가정은 깨진다.

copy-up: 쓰기 위해 여는 순간 app.conf가 upper(tmpfs 0:25)에 생겼고, 부모 디렉터리 etc도 함께 만들어졌다. lower는 그대로 rate=100. merged의 ino·dev는 copy-up 전과 같은 0:28/7로 유지된다 — overlay가 upper 파일에 원본 정보(trusted.overlay.origin)를 기록해 두고 원래 번호를 계속 보여 준다.

copy-up은 파일 통째다: 1 MiB 파일 끝에 2바이트를 붙였을 뿐인데 upper에 1,048,578 바이트 전체가 복사됐다. 300 MB짜리 모델 파일의 메타데이터 하나만 바꿔도(chmod도 copy-up을 일으킨다) 300 MB가 upper로 복사된다. upper가 tmpfs면 그만큼 RAM을 먹는다. metacopy=on(이 커널 기본 꺼짐)은 메타데이터만 바꾸는 경우 데이터 복사를 미루는 기능이다.

whiteout: lower의 파일을 지우면 upper에 장치 번호 0:0인 문자 장치가 같은 이름으로 생긴다. 이것이 whiteout이다. merged에서는 hostname이 사라졌다. nlink=2인 것은 6.x overlayfs가 whiteout마다 inode를 새로 만들지 않고 workdir의 공용 whiteout inode에 hard link로 붙이기 때문이다(inode 절약).

opaque 디렉터리: lower에 있던 디렉터리를 지우고 같은 이름으로 다시 만들면, upper의 새 디렉터리에 trusted.overlay.opaque="y"가 붙는다. "이 디렉터리 아래로는 lower를 보지 마라"는 뜻이다. 그래서 lower의 wlan0.conf는 merged에서 사라지고 새로 쓴 eth0.conf만 보인다. trusted.* xattr은 CAP_SYS_ADMIN이 있어야 보이므로 일반 사용자의 getfattr로는 안 보인다.

hard link가 깨진다: lower에서 tool_a와 tool_b는 같은 inode(14, nlink 2)였다. tool_a에 쓰자 tool_a만 copy-up되어 새 inode(ino 19, nlink 1, dev도 바뀜)가 됐고, tool_b는 여전히 옛 내용(size 20)이다. "같은 파일의 두 이름"이었던 것이 "다른 두 파일"이 됐다. index=on(이 커널 기본 꺼짐)을 켜면 hard link를 유지하며 copy-up한다.

디렉터리 rename은 EXDEV: lower에서 온 디렉터리를 rename(2)하면 EXDEV("다른 FS 사이의 이동")가 나온다. mv는 EXDEV를 받으면 복사 + 삭제로 대신하기 때문에 사용자는 모른다 — 그러나 큰 디렉터리라면 통째 복사가 일어나고, rename()의 원자성을 믿는 프로그램(설정 디렉터리를 rename으로 교체하는 업데이트 스크립트)은 실패한다.

statfs: merged의 df는 upper FS의 숫자(32 MiB tmpfs)를 보여 준다. lower가 수백 MB여도 "남은 공간"은 upper 기준이다. BusyBox stat -f는 overlay의 magic(0x794c7630)을 몰라서 UNKNOWN으로 찍는다.

redirect_dir=on: 같은 upper/work로 다시 마운트하되 redirect_dir=on을 주면 디렉터리 rename이 성공한다. upper의 usr/sbin에 trusted.overlay.redirect="bin"이 붙어 "내 lower 짝은 bin이다"라고 기록한다. origin은 바이너리 file handle(29바이트)이라 문자열로 찍으면 비어 보인다. 주의: redirect가 기록된 upper는 redirect를 이해하지 못하는 옛 커널이나 redirect_dir=off 마운트에서 다르게 보인다 — upper를 장비 여러 세대에 걸쳐 들고 가는 설계라면 옵션을 고정해야 한다.

여러 lower, upper 없음: (첫 실패는 마운트 포인트를 안 만든 스크립트 실수다.) lowerdir=/up/l2:/lower에서 왼쪽 l2의 app.conf가 이겼다. upper 없이 lower만 주면 overlay 전체가 읽기전용이 된다 — "베이스 이미지 + 제품별 차이 이미지"를 쌓기만 하는 구성(컨테이너 이미지 레이어, 제품 변형 레이어)에 쓴다.

그림 7 — 위 실습에서 실제로 upper에 생긴 것들. 위에서부터 copy-up, whiteout(문자 장치 0:0), opaque 디렉터리, redirect(디렉터리 rename).

  • upper에 들어가도 되는 경로를 화이트리스트로 제한한다(설계 C).
  • 이미지 버전을 upper에 기록하고, 버전이 바뀌면 마이그레이션 스크립트를 돌리거나 upper의 해당 경로를 정리한다.
  • "공장 초기화" = upper 디렉터리 삭제. 버튼 하나로 복구할 수 있게 initramfs에 넣어 둔다.

10. dm-verity 맛보기 — 읽기전용 이미지를 "믿을 수 있게"#

이 절은 RO rootfs 설계에 필요한 만큼만 다룬다. 루트 해시 서명(root_hash_sig_key_desc), FEC(오류 정정), 키 관리, dm-crypt와의 조합은 L6, 부트 체인에서 루트 해시를 지키는 방법은 L5에서 다룬다.

10.1 직관 — 해시 트리#

SSD 펌웨어에서 FW 이미지는 부팅 때 한 번 서명 검증한다. 하지만 rootfs는 수백 MB라 부팅 때 전부 해시하면 몇 초가 걸리고, 검증한 뒤에 eMMC가 바뀌면(물리 공격, 플래시 비트 에러) 모른다.

dm-verity는 device-mapper 타깃으로, 블록을 읽을 때마다 그 블록만 검증한다.

  1. 빌드 때: 데이터 4 KiB 블록마다 SHA-256을 구해 해시 블록에 모은다(4 KiB 해시 블록 하나에 32바이트 해시 128개). 해시 블록들을 다시 해시해서 위 층을 만들고, 마지막에 블록 하나가 남으면 그 해시가 루트 해시다.
  2. 런타임: 데이터 블록 N을 읽으면, N의 해시 → 그걸 담은 해시 블록 → … → 루트까지 경로를 검증한다. 해시 블록은 한 번 검증되면 캐시(dm-bufio)되므로 보통은 데이터 블록 해시 1번만 계산하면 된다.
  3. 신뢰의 뿌리: 루트 해시 32바이트 하나만 안전한 곳(서명된 커널 cmdline·FIT·initramfs)에 있으면 이미지 전체를 믿을 수 있다.

RO rootfs + verity가 있으면 OTA는 "슬롯 B에 새 squashfs와 해시 트리를 통째로 쓰고, 새 루트 해시가 든 서명된 커널/FIT를 B 쪽에 두고, 부트로더 변수만 B로 바꾼다"가 된다. 쓰는 도중 전원이 나가도 A는 멀쩡하다. 새 이미지가 verity 오류로 재시작을 반복하면 bootcount가 롤백한다. 이 흐름(RAUC·SWUpdate·Mender, U-Boot bootcount/altbootcmd)은 L4에서 만든다.

11. 커널 안에서는 무슨 일이 일어나나#

그림 9 — 이 노트의 스택에서 읽기·쓰기가 지나가는 커널 함수(6.18.55 소스 fs/overlayfs/, fs/squashfs/, fs/erofs/, drivers/md/dm-verity-target.c에서 이름 확인).

단계별로:

  • overlayfs는 데이터를 들고 있지 않는 "스태킹 FS"다. merged의 struct file은 열 때 lower 또는 upper의 진짜 파일(realfile)을 함께 연다. ovl_read_iter()는 backing_file_read_iter()로 그 진짜 파일에 읽기를 넘긴다. 그래서 page cache는 lower FS(squashfs)의 inode에 쌓인다 — overlay 자체는 페이지를 갖지 않는다.
  • copy-up: ovl_open()이 쓰기 플래그를 보면 ovl_maybe_copy_up() → ovl_copy_up_flags() → ovl_copy_up_one(). workdir에 임시 파일을 만들고 데이터·xattr·속성을 복사한 뒤 rename으로 upper의 제자리에 넣는다. 그래서 copy-up은 원자적이고, 크래시 후 workdir에 쓰레기가 남을 수 있다(다음 마운트 때 정리).
  • whiteout: ovl_do_whiteout() → vfs_whiteout()이 upper FS에 0:0 문자 장치를 만든다. opaque는 ovl_check_setxattr(…, OVL_XATTR_OPAQUE, "y")(fs/overlayfs/dir.c). lookup 때 ovl_lookup()이 upper에서 whiteout을 만나면 "없음", opaque를 만나면 lower 탐색을 멈춘다.
  • SquashFS 읽기: squashfs_read_folio()/squashfs_readahead()가 블록 목록에서 압축 블록 위치를 찾고, squashfs_read_data()가 bio로 읽어 msblk->decompressor로 푼다. fragment·메타데이터는 squashfs_cache_get()의 작은 캐시를 거친다. 6.18에서는 장치 블록 크기 = 페이지 크기이면 압축 블록을 cache_mapping에 남긴다(§5.5의 이중 캐싱).
  • EROFS 읽기: 압축 파일은 z_erofs_read_folio()/z_erofs_readahead() → pcluster 단위로 모아 z_erofs_decompress_pcluster() → z_erofs_lz4_decompress() 등. file-backed 마운트의 비압축 경로는 erofs_fileio_read_folio()(fs/erofs/fileio.c).
  • dm-verity: verity_map()이 bio의 대상 장치를 데이터 장치로 바꿔 내려보내고, 완료 콜백 verity_end_io()가 검증을 workqueue(verity_work)나 BH 문맥(verity_bh_work, 설정 try_verify_in_tasklet)에 넘긴다. verity_verify_io()가 블록마다 verity_hash()로 SHA-256을 구해 해시 트리(해시 블록은 dm-bufio 캐시)와 비교하고, 틀리면 verity_handle_err()가 모드에 따라 EIO/kernel_restart()/panic.
  • tmpfs: mm/shmem.c. 쓰기는 shmem_get_folio()로 페이지를 할당하면서 shmem_inode_acct_blocks()로 size= 한도를 검사한다(넘으면 ENOSPC). ramfs(fs/ramfs/inode.c)는 이 회계가 아예 없다.

드라이버를 쓸 때 다시 만나는 곳:

  • 블록 드라이버(I·J1): dm-verity가 내려보낸 bio를 eMMC/UFS/virtio 드라이버가 받는다. 드라이버가 에러를 BLK_STS_IOERR로 돌려주면 verity의 restart_on_error 쪽이 반응한다 — 저장장치 드라이버의 에러 매핑이 장비 전체의 재시작 정책에 직결된다.
  • device-mapper 타깃 작성: struct target_type의 .ctr/.map/.end_io — §10.3의 테이블 문자열이 .ctr의 argv로 들어간다. dm-flakey·dm-dust(J5 전원 차단 실험에서 사용)도 같은 구조다.
  • page cache·folio(F): FS 드라이버의 .read_folio/.readahead는 address_space_operations다. 압축 FS가 "한 번에 여러 페이지를 채우는" 것은 readahead 경로에서 folio를 추가로 잡는 방식이다.

12. Embedded 실무에서 다시 보기#

12.1 센서 키트 드론: "배터리 탈착이 정상 종료"#

비행 후 배터리를 그냥 뽑는 게 운용 절차인 장비. 설계: squashfs(zstd) 루트 + verity, /etc만 ext4 data 파티션에 overlay, 비행 로그·센서 기록은 data 파티션의 별도 디렉터리에 J5 규칙(fsync, 임시 파일 + rename)으로. /tmp·/run은 tmpfs size=32m. 이렇게 하면 "전원 차단 후 부팅 불가"의 경우의 수가 data 파티션 하나로 줄고, data가 깨져도 initramfs가 "data 마운트 실패 → mkfs 후 기본 설정으로 부팅"하는 복구 경로를 갖는다.

12.2 Jetson·i.MX8급 AI 카메라: 압축기 선택 근거#

모델 파일(수백 MB)과 라이브러리를 rootfs에 넣는 장비. 부팅 후 카메라 파이프라인이 라이브러리 수십 개를 mmap하므로 "첫 접근 지연" 합이 앱 시작 시간을 결정한다. §5의 경향대로 xz를 쓰면 이미지는 작아도 시작이 느리다. 선택지: SquashFS zstd 128K(무난), 시작 시간이 KPI면 EROFS lz4hc. 모델 파일처럼 이미 압축된 데이터는 압축 이득이 없으니 별도 비압축 파티션이나 EROFS 비압축 서브 이미지로 뺀다. 숫자로 말하려면 이 노트의 j3_read와 같은 도구로 대상 보드에서 다시 잰다(TCG 숫자를 그대로 보고하면 안 된다).

12.3 개발 빌드 vs 양산 빌드#

  • 개발: ext4 rw 루트, ssh + scp로 바이너리 교체. 또는 squashfs 루트에 개발자용 overlay(data 파티션 upper)를 켜 두고 rsync로 덮어쓰기.
  • 양산: squashfs/EROFS + verity, overlay는 /etc만, ignore_corruption 같은 디버그 옵션 제거.
  • 흔한 사고: 개발 중 overlay upper에 넣어 둔 패치 파일 때문에 "개발 보드에선 되는데 양산 이미지에선 안 된다". upper가 비어 있는 상태에서 테스트하는 단계를 CI에 둔다.

12.4 "디스크 꽉 참"의 정체 찾기#

필드에서 "No space left on device" 로그가 올라왔는데 data 파티션은 여유가 있다? 확인 순서: df -h /tmp /run /var/volatile(tmpfs size= 한도), df -i(tmpfs nr_inodes 한도 — 작은 파일 수만 개), overlay upper의 FS(merged의 df는 upper 기준), grep -E "Shmem|Unevictable" /proc/meminfo(tmpfs/ramfs가 RAM을 먹고 있나).

14. 면접에서 이렇게 말한다#

Q. "How would you design the root filesystem for a field-deployed device that can lose power at any time?"

A. 루트는 읽기전용 압축 이미지(SquashFS나 EROFS)로 만들어 런타임에 절대 쓰지 않는다. 쓰기가 필요한 /etc는 overlayfs로 data 파티션 위에 얹고, /var와 로그는 data 파티션에 직접, /tmp·/run은 크기를 정한 tmpfs. 그러면 전원 차단 영향은 data 파티션 하나로 줄고 거기에는 fsync·rename 규칙을 적용한다. 무결성은 dm-verity, 업데이트는 A/B 슬롯 통째 교체와 bootcount 롤백.

I'd make the root filesystem a read-only compressed image, SquashFS or EROFS, that is never written at runtime. Only /etc gets an overlayfs upper layer on a separate data partition; /var and logs live directly on that data partition, and /tmp and /run are size-limited tmpfs. That shrinks the power-loss exposure to one partition, where I apply the usual fsync-and-rename rules. I'd put dm-verity under the root image for integrity, and update by writing a whole new image to the inactive A/B slot with bootcount-based rollback.

꼬리 질문: "What breaks when you put an overlay on top?" → copy-up 비용, hard link, 디렉터리 rename EXDEV, OTA 후 upper가 새 lower를 가리는 문제(§7.5, §8.2).

Q. "SquashFS or EROFS — how do you choose, and what's the trade-off with compression algorithms?"

A. 둘 다 읽기전용 압축 FS인데 압축 단위가 반대다. SquashFS는 입력을 128 KiB씩 잘라 압축해서 4 KiB를 읽으려 해도 블록 전체를 풀고, EROFS는 출력을 4 KiB로 고정해서 블록 하나 읽고 그것만 푼다. 그래서 랜덤 읽기·첫 접근 지연은 EROFS가 유리하다. 제가 같은 트리로 잰 것에서 lz4 기준 첫 접근이 EROFS 0.55 ms, SquashFS 1.5 ms였다. 압축기는 xz가 가장 작고 가장 느리고, lz4가 가장 빠르고 크고, zstd가 그 사이에서 xz에 가까운 크기를 낸다. 결국 플래시 크기와 앱 시작 시간 중 무엇이 제약인지로 고르고, 대상 보드에서 잰다.

They're both read-only compressed filesystems but they compress in opposite directions. SquashFS compresses fixed-size input blocks, typically 128 KiB, so reading one 4 KiB page means decompressing the whole block. EROFS produces fixed-size 4 KiB output clusters, so one block read gives you one independent decompression — much better for random reads and page-fault latency. In my own measurement on the same tree, first-touch latency with lz4 was about 0.55 ms on EROFS versus 1.5 ms on SquashFS. For algorithms, xz is the smallest and slowest, lz4 is the fastest and largest, and zstd gets close to xz in size while decompressing several times faster. I'd pick based on whether flash size or startup time is the constraint, and I'd benchmark on the target board.

꼬리 질문: "Why not just use a bigger block size?" → 압축률은 좋아지지만 첫 접근 비용이 커지고, 메모리 압박 시 같은 블록을 반복 해제한다(§3.4, §5.3).

Q. "Explain how overlayfs handles a write to a file that only exists in the lower layer, and a delete."

A. 쓰기용으로 여는 순간 copy-up이 일어난다. workdir에 임시 파일을 만들어 lower 파일의 데이터·속성·xattr를 통째로 복사하고, rename으로 upper의 같은 경로에 넣는다. 이후 쓰기는 upper 파일로 간다. 삭제는 lower를 건드릴 수 없으니 upper에 같은 이름으로 장치 번호 0/0인 문자 장치, 즉 whiteout을 만든다. 디렉터리를 지우고 다시 만들면 upper 디렉터리에 trusted.overlay.opaque=y xattr이 붙어서 lower의 내용을 숨긴다.

On the first open for write, overlayfs copies the file up: it creates a temp file in the workdir, copies the full data, attributes and xattrs from the lower file, then renames it into place in the upper directory, so the copy-up is atomic. All subsequent writes go to the upper file. A delete can't touch the lower layer, so overlayfs creates a whiteout in upper — a character device with device number 0/0 under the same name. If you remove a directory and recreate it, the new upper directory gets the trusted.overlay.opaque xattr so the lower contents stay hidden.

꼬리 질문: "What's the cost of copy-up?" → 파일 전체 복사. 큰 파일 하나의 chmod도 전체 복사(metacopy=on이 완화).

Q. "What's the difference between tmpfs and ramfs, and why does it matter on an embedded device?"

A. 둘 다 page cache에 데이터를 두지만 tmpfs는 size= 한도와 inode 한도가 있고 swap으로 밀려날 수 있으며 Shmem으로 회계된다. ramfs는 한도가 없고 swap도 안 되고 df에 0으로 나온다. 제가 512 MB 게스트에서 해 보니 ramfs에 200 MB를 써도 df는 0이고 메모리는 Unevictable로 잡혀 회수가 안 됐다. 임베디드에서는 로그 폭주 하나가 OOM으로 이어지니, /tmp·/run은 반드시 크기를 정한 tmpfs로 둔다.

Both keep data in the page cache, but tmpfs has size= and inode limits, can be swapped out, and is accounted as Shmem. ramfs has no limit, can't be swapped, and always shows zero in df. When I wrote 200 MB into ramfs on a 512 MB guest, df still said zero and the memory showed up as unevictable. On an embedded device a runaway log could OOM the whole system, so /tmp and /run should always be size-limited tmpfs.

Q. "How does dm-verity work, and what happens when a block is corrupted?"

A. 빌드 때 데이터 4 KiB 블록마다 SHA-256을 구해 해시 트리를 만들고, 루트 해시 하나를 서명된 커널 cmdline 같은 믿을 수 있는 곳에 둔다. 런타임에는 블록을 읽을 때마다 그 블록의 해시를 트리와 비교한다. 해시 블록은 한 번 검증되면 캐시된다. 불일치면 기본은 EIO다. 일반 read는 에러가 나고, 실행 파일 페이지면 SIGBUS로 프로세스가 죽는다. 제가 해 보니 BusyBox 블록을 바꿨을 때 PID 1이 SIGBUS로 죽어 panic이 났다. 양산에서는 restart_on_corruption으로 재시작시키고 bootcount로 다른 슬롯에 롤백한다.

At build time you hash every 4 KiB data block with SHA-256, build a Merkle tree of hash blocks, and keep only the root hash somewhere trusted, like a signed kernel command line. At runtime, every block read is verified against the tree on the fly, and verified hash blocks are cached. On a mismatch the default is to return EIO: a regular read fails, and if it's an executable page the process gets SIGBUS. In my test, corrupting a block inside BusyBox killed PID 1 with SIGBUS and panicked the kernel. In production you'd typically use restart_on_corruption and let the bootloader's bootcount roll back to the other slot.

꼬리 질문: "Does verity protect the overlay upper?" → 아니다. lower만. /etc upper는 보호 밖이라 dm-integrity나 서명된 설정 검증이 필요하다(L6).

Q. "Walk me through what an initramfs does to boot a SquashFS root with an overlay."

A. /proc·/sys·/dev를 마운트하고 cmdline에서 루트 장치와 옵션을 읽는다. 필요하면 dm-verity 모듈을 올리고 루트 해시로 verity 장치를 만든다. 그 장치를 squashfs로 /ro에 마운트하고, upper용으로 tmpfs나 data 파티션을 /rw에 마운트해서 upper와 work 디렉터리를 만든다. overlay를 /newroot에 만들고, /ro·/rw와 가상 FS를 mount --move로 새 루트 안으로 옮긴 다음 exec switch_root /newroot /sbin/init. PID는 1로 유지된다. 실패 경로는 전부 복구 셸로 간다.

It mounts /proc, /sys and /dev, parses the root device and options from the kernel command line, optionally loads dm-verity and creates the verity device from the root hash, mounts that as SquashFS on /ro, mounts a tmpfs or the data partition on /rw and creates the upper and work directories, then mounts the overlay on /newroot. It moves /ro, /rw and the virtual filesystems into the new root with mount --move and finally does exec switch_root /newroot /sbin/init, so PID 1 is preserved. Every failure path drops to a rescue shell instead of exiting, because PID 1 exiting is a panic.

Q. "Why might your memory usage be higher than expected with a compressed read-only filesystem?"

A. 이중 캐싱 때문이다. 풀린 데이터가 page cache에 있는 것은 당연한데, 압축 데이터도 캐시될 수 있다. 제가 잰 바로는 6.18 SquashFS가 블록 장치에서도 압축 블록을 자체 캐시에 남겨 41 MiB를 읽고 59 MiB가 늘었고, 이미지를 ext4 위 파일로 loop 마운트하면 백킹 파일 캐시가 더해져 74 MiB가 됐다. EROFS 블록 장치는 47 MiB였다. 이미지는 파티션에 직접 두고, 파일이어야 하면 EROFS file-backed에 directio를 쓴다.

Double caching. The decompressed pages are obviously in the page cache, but compressed data can be cached too. When I measured it, reading a 41 MiB tree from SquashFS on a block device grew the page cache by about 59 MiB, because the kernel also keeps the compressed blocks around; loop-mounting the same image from a file on ext4 grew it to about 74 MiB because the backing file is cached as well. EROFS on a block device was about 47 MiB. So I'd write the image straight to a partition, and if it has to be a file, use EROFS's file-backed mount with directio.

17. 요약 & 체크리스트#

필드 장비의 rootfs는 "쓰지 않는 영역은 깨지지 않는다"는 원칙으로 설계한다. 루트는 SquashFS나 EROFS 압축 이미지로 만들고, 압축기와 블록 크기는 이미지 크기와 첫 접근 지연 사이의 거래다. 같은 41 MiB 트리에서 xz는 가장 작았고(13.3 MiB) 가장 느렸으며(첫 접근 11 ms), lz4·EROFS는 비압축에 가까운 속도를 냈고, zstd 128K가 무난한 중간이었다. SquashFS는 입력 고정·출력 가변이라 4 KiB 읽기에도 블록 전체를 풀고, EROFS는 출력 고정이라 블록 하나만 푼다. 압축 FS는 page cache 이중 캐싱으로 생각보다 메모리를 더 쓸 수 있다. tmpfs는 한도와 회계가 있는 메모리 FS이고 ramfs는 쓰면 안 된다. overlayfs는 읽기전용 lower 위에 upper를 겹쳐 copy-up·whiteout·opaque로 쓰기를 흉내 내지만, inode 번호·hard link·디렉터리 rename·copy-up 비용이 일반 FS와 다르다. initramfs는 이것들을 조립해 switch_root하고, dm-verity는 lower의 모든 블록을 루트 해시 하나에 묶어 바이트 하나의 변조도 EIO·SIGBUS·재시작으로 드러낸다.
