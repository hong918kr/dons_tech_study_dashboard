0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어 시절을 떠올려 보자. 펌웨어 빌드는 "툴체인(armcc/gcc) 고정 → 소스 모듈 컴파일 → 링커 스크립트로 묶기 → 이미지 헤더·서명 붙이기 → 다운로드용 바이너리" 순서였고, 이 전부를 Makefile 하나와 설정 파일 몇 개가 지휘했다.

Embedded Linux 장비도 똑같은 문제를 푼다. 다만 재료가 훨씬 많다. 크로스 컴파일러, C 라이브러리(glibc/musl), 커널, 부트로더, BusyBox, 수십~수백 개의 오픈소스 패키지(i2c-tools, can-utils, openssl …), 회사 앱, 그리고 이걸 담을 ext4·SD 카드 이미지. Buildroot는 이 전체를 make 한 번으로 재현 가능하게 만드는 도구다. 본체는 거의 전부 GNU Make 규칙과 Kconfig(커널과 같은 menuconfig 설정 언어)다.

그림 1 — Buildroot의 다섯 단계. ①에서 고른 설정으로 ②툴체인을 만들고(또는 받아 오고), ③패키지를 의존 순서대로 빌드해 target/에 설치한 뒤, ④rootfs를 다듬고 ⑤파일시스템·디스크 이미지를 만든다.

0.1 이 노트의 실행 원칙 — 무엇을 실제로 돌렸나#

Don의 요청으로 전체 Buildroot 빌드(툴체인 빌드, 커널·패키지 컴파일, 이미지 생성)는 실행하지 않았다. 시간과 디스크가 많이 들기 때문이다. 대신 다운로드·컴파일이 필요 없는 단계는 전부 실제로 돌렸고, 빌드가 필요한 부분은 "실행하지 않음 — 가이드" 라벨을 붙여 명령과 기대 산출물(문서·소스 기준)만 적었다. 가이드 블록에는 출력 블록을 붙이지 않는다.

2. defconfig 워크플로#

2.1 직관 — 커널과 똑같은 Kconfig#

Buildroot 설정은 커널 설정(E2)과 같은 Kconfig 언어다. make menuconfig로 메뉴를 고르면 .config(수천 줄)가 생기고, 이걸 기본값과 다른 줄만 남긴 것이 defconfig다. 커널과 다른 점은 심볼 접두어가 CONFIG_가 아니라 BR2_라는 것 하나다.

2.2 예제 2 — QEMU aarch64 보드 defconfig 적용#

무엇을 확인하나: 18줄짜리 defconfig가 5307줄짜리 .config로 펼쳐지는 과정. O=로 출력 디렉터리를 소스 트리 밖에 둔다(커널의 O=와 같다).

출력에서 볼 것: ... 자리에는 Kconfig 도구(conf)를 호스트 gcc로 컴파일하는 줄이 있다(생략). 0.7초, 676 KB — 아직 아무것도 다운로드하거나 빌드하지 않았다. O= 디렉터리에는 .config와, 그 디렉터리에서 바로 make를 칠 수 있게 해 주는 래퍼 Makefile만 생겼다. 이후 명령은 전부 /var/tmp/K3/k3_out에서 그냥 make …로 친다.

2.3 예제 3 — 펼쳐진 .config에서 중요한 기본값#

무엇을 확인하나: defconfig에 적지 않은 항목(툴체인 종류, gcc 버전, init, /dev 관리)이 기본값으로 정해졌다는 것.

출력에서 볼 것: 기본은 internal 툴체인(Buildroot가 binutils 2.45.1 + gcc 15.3.0 + glibc를 직접 빌드), init은 BusyBox init(K2), /dev는 devtmpfs만(udev·mdev 없음, K1), root 비밀번호는 빈 문자열(개발용 — 제품에서는 반드시 바꾼다), 다운로드 캐시는 Buildroot 트리 안 dl/이다.

2.4 예제 4 — 설정 바꾸고 savedefconfig로 최소 diff 저장#

무엇을 확인하나: menuconfig 대신 utils/config(커널 scripts/config의 Buildroot판)로 설정을 바꾸고, savedefconfig가 "기본값과 다른 줄"만 남긴다는 것.

출력에서 볼 것: .config는 43줄 늘었지만(새 패키지의 하위 옵션 기본값까지 펼쳐짐) defconfig는 딱 4줄 늘었다. git에 커밋하는 것은 항상 savedefconfig 결과다. .config를 커밋하면 버전 업그레이드 때 새 옵션 기본값을 놓치고, 리뷰 diff가 수백 줄이 된다.

함정: BR2_DEFCONFIG를 주지 않으면 savedefconfig는 defconfig를 불러온 원래 파일(configs/qemu_aarch64_virt_defconfig)을 덮어쓴다. 업스트림 파일을 실수로 고치지 않으려면 경로를 명시하거나, 처음부터 BR2_EXTERNAL의 자기 defconfig를 쓴다. 또 i2c-tools는 depends on BR2_PACKAGE_BUSYBOX_SHOW_OTHERS라서(5.2절 Config.in 참고) 그것 없이 -e BR2_PACKAGE_I2C_TOOLS만 하면 olddefconfig가 조용히 꺼 버린다.

2.5 서브 컴포넌트 설정 — 커널·BusyBox·U-Boot (실행하지 않음 — 가이드)#

Buildroot는 커널·BusyBox·U-Boot의 Kconfig도 같은 방식으로 감싼다. 이 타깃들은 해당 소스를 내려받고 압축을 풀어야 하므로 실행하지 않았다.

실무 규칙: *-menuconfig로 바꾼 내용은 output/build/ 안에만 있으므로 *-update-defconfig(또는 -update-config)를 하지 않으면 make clean 한 번에 사라진다. 작은 변경은 전체 config 파일 대신 config fragment(BR2_LINUX_KERNEL_CONFIG_FRAGMENT_FILES)로 관리하는 편이 업그레이드에 강하다. 6절의 linux.fragment가 그 예다.

3. output/ 디렉터리 — build · host · staging · target · images#

3.1 그림으로 먼저#

그림 2 — 패키지는 build/에서 빌드되고, 라이브러리는 staging(=툴체인 sysroot, 개발용 전체 사본)에, 실행에 필요한 것만 target(제품용)에 설치된다. images/는 target/을 굽는 결과다.

3.2 예제 5 — printvars로 실제 경로 확인#

무엇을 확인하나: 그림 2의 각 디렉터리가 Make 변수로 어떻게 정의되어 있는지. printvars는 아무것도 빌드하지 않고 변수 값만 찍는다.

출력에서 볼 것: STAGING_DIR이 host/<tuple>/sysroot 다. 즉 staging은 별도 개념이 아니라 크로스 컴파일러의 sysroot 그 자체다(B3에서 본 --sysroot). 패키지가 INSTALL_STAGING = YES로 헤더와 라이브러리를 여기 넣으면, 그 뒤에 빌드되는 패키지는 cross gcc가 자동으로 그 헤더를 찾는다. TARGET_CROSS는 모든 패키지에 CC=$(TARGET_CROSS)gcc로 넘어가는 접두어다.

3.3 staging vs target — 왜 둘로 나누나#

staging (sysroot)target
목적빌드할 때 컴파일·링크 대상보드에 실을 rootfs
헤더(/usr/include)있음없음 (target-finalize가 삭제)
정적 라이브러리 .a, .pc있음없음
디버그 심볼있음 (unstripped)BR2_STRIP_strip이면 strip됨
누가 쓰나cross gcc, pkg-config, gdb(심볼)fakeroot → mkfs
SSD 비유링크용 .lib + .h + .map다운로드 이미지

이 구분이 실무에서 중요한 장면은 원격 디버깅이다. 보드 위 gdbserver는 target의 strip된 바이너리를 돌리고, 호스트 gdb는 set sysroot output/staging으로 심볼이 살아 있는 staging 사본을 읽는다(M 모듈에서 다시 나온다).

4. 툴체인 선택 — internal vs external#

4.1 두 가지 길#

internal (BR2_TOOLCHAIN_BUILDROOT)external (BR2_TOOLCHAIN_EXTERNAL)
동작binutils·gcc·C 라이브러리를 소스에서 빌드미리 빌드된 툴체인 tarball을 받아 host/에 풀고 sysroot를 staging으로 복사
C 라이브러리glibc / musl / uClibc-ng 자유 선택툴체인이 정한 것
첫 빌드 시간툴체인 빌드만큼 더 걸림빠름
재현성버전이 defconfig에 고정tarball 버전이 고정 (.hash로 검증)
대표 선택지—Bootlin toolchains, Arm GNU toolchain, 회사·SoC 벤더 SDK(toolchain-external-custom)
언제musl·특수 옵션이 필요할 때, 툴체인도 소스로 감사할 때대부분의 제품 — 툴체인을 팀 전체가 공유

실무 팁: 툴체인 설정을 바꾸면 무조건 전체 재빌드다(10절). 그래서 많은 팀이 "Buildroot로 툴체인만 한 번 만들어 tarball로 굳히고, 제품 빌드는 그걸 external custom으로 쓴다". B4의 crosstool-NG도 같은 목적이다.

4.2 예제 6 — external 툴체인으로 바꿔 보기 (함정 포함)#

무엇을 확인하나: Kconfig 의존성 때문에 "고른 줄 알았던" 툴체인이 조용히 다른 것으로 바뀌는 장면, 그리고 툴체인 종류에 따라 다운로드 목록이 어떻게 달라지는지.

출력에서 볼 것: Bootlin을 켰는데 결과는 Arm 툴체인(aarch64-none-linux-gnu-, toolchain-external-arm-aarch64)이다. 원인은 Bootlin 툴체인의 Kconfig에 있다.

Bootlin 툴체인은 x86_64 호스트용 바이너리만 있다. 이 VM은 aarch64 호스트(M2)라 Bootlin 선택지가 사라지고, olddefconfig가 choice의 다음 후보(Arm AArch64 15.2.rel1, x86_64와 aarch64 호스트 모두 지원)를 골랐다. Kconfig는 불가능한 선택을 에러 없이 조용히 바꾼다 — 그래서 CI에서는 savedefconfig 후 diff가 비어 있는지 확인하는 단계를 둔다. 또 비교해 보면 internal은 busybox의 재귀 의존성에 host-gcc-initial host-gcc-final host-binutils glibc …가 들어가지만(예제 7), external은 toolchain-external-arm-aarch64 하나로 끝나고 다운로드 목록에서 gcc·binutils·glibc 소스가 툴체인 tarball 하나로 바뀐다.

6. BR2_EXTERNAL — 회사 제품 트리#

6.1 직관 — 본체는 건드리지 않는다#

회사에서 Buildroot를 쓸 때 가장 나쁜 패턴은 Buildroot 트리를 fork해서 configs/, board/, package/에 직접 커밋하는 것이다. 업스트림 업그레이드 때마다 merge 지옥이 된다. BR2_EXTERNAL은 "Buildroot 밖의 디렉터리를 Buildroot 트리의 일부처럼 끼워 넣는" 공식 메커니즘이다. 자기 Config.in 메뉴, 패키지, defconfig, 보드 파일을 갖고, 여러 개를 콜론으로 이어 쓸 수도 있다(BR2_EXTERNAL=/a:/b).

그림 4 — 세 덩어리를 분리한다. 업스트림 Buildroot(고정 버전), 회사 BR2_EXTERNAL 트리(제품 정의 전부), 출력 디렉터리(버리는 것).

6.2 필수 파일 세 개#

name:이 SENSORKIT이면 Buildroot가 BR2_EXTERNAL_SENSORKIT_PATH를 정의한다. defconfig와 스크립트 경로는 전부 이 변수로 쓴다 — 그래야 트리를 어디에 clone해도 동작한다.

6.3 제품 defconfig#

QEMU 보드 defconfig를 바탕으로 회사 것을 얹었다. 아래는 6.5절의 savedefconfig 왕복 검증을 통과한 최종본이다.

업스트림 qemu defconfig에 있던 BR2_DOWNLOAD_FORCE_CHECK_HASHES=y는 뺐다. 이 옵션은 모든 패키지에 .hash를 강제하는데, git 사이트의 회사 패키지(k3-imu-mod)에는 아직 해시 파일이 없기 때문이다. 제품 릴리스 브랜치에서는 다시 켜고 회사 패키지에도 해시를 붙이는 것이 정석이다(git 다운로드도 Buildroot가 만든 tarball의 해시로 검증 가능하다). linux.fragment는 다음 다섯 줄이다.

6.4 회사 패키지 세 종류#

(1) generic-package — 손으로 쓴 Makefile (package/k3-tools/k3-tools.mk)

소스 쪽 Makefile은 CC·CFLAGS를 하드코딩하지 않는 것이 핵심이다. Buildroot가 $(TARGET_CONFIGURE_OPTS)로 cross gcc를 넘겨준다.

(2) cmake-package — CMake 프로젝트 (package/k3-sensord/k3-sensord.mk)

빌드 명령이 한 줄도 없다. package/pkg-cmake.mk가 대신 만드는 명령의 핵심 줄은 이렇다.

init 스크립트는 패키지 디렉터리에 두고 _INSTALL_INIT_SYSV로 설치했다(init으로 systemd를 고르면 _INSTALL_INIT_SYSTEMD가 대신 쓰인다). 스크립트는 package/busybox/S01syslogd의 형식(DAEMON, PIDFILE, start()/stop(), 탭 들여쓰기)을 따랐다 — 6.6절의 check-package가 이 형식을 검사한다.

(3) kernel-module — out-of-tree 드라이버 (package/k3-imu-mod/k3-imu-mod.mk)

$(eval $(kernel-module))를 generic-package 앞에 둔다. kernel-module 인프라는 빌드·설치 단계 뒤에 훅을 붙이고, linux를 의존성에 자동으로 추가한다. 드라이버 소스는 E4에서 본 그대로의 Kbuild 한 줄(obj-m := k3_imu.o)이다. git@git.example.com:…은 예시 주소다 — 실제로는 회사 Git 서버이고, 11절의 OVERRIDE_SRCDIR로 로컬 작업 트리를 대신 쓴다. _LINUX_CONFIG_FIXUPS는 "이 패키지를 켜면 커널 config에 이 옵션도 켜라"는 훅으로, 실제 package/dtbocfg/dtbocfg.mk도 같은 방식으로 CONFIG_OF_OVERLAY를 켠다.

8. genimage — SD 카드·eMMC 디스크 이미지#

rootfs.ext4는 파티션 하나의 내용일 뿐이다. 보드는 파티션 테이블 + 부트로더 raw 영역 + boot 파티션 + rootfs 로 된 디스크 이미지가 필요하다(C2, J1). Buildroot는 이것을 genimage(Pengutronix 도구, host-genimage 패키지)와 support/scripts/genimage.sh 래퍼로 만든다. 실제 i.MX8MP 보드(board/polyhex/debix-model-a/genimage.cfg.in)의 설정이 좋은 예다.

읽는 법: i.MX8M BootROM은 SD 카드 32 KiB 오프셋에서 부트 이미지(flash.bin = SPL + DDR 펌웨어 + TF-A + U-Boot)를 찾는다(C2). 그래서 imx-boot는 파티션 테이블에 넣지 않고(in-partition-table = "no") raw로 32K에 쓰고, rootfs 파티션은 8M부터 시작한다. %PARTUUID%는 post-image 스크립트가 sed로 채워 커널 커맨드라인 root=PARTUUID=…와 맞춘다.

K3 센서 키트 보드의 post-image와 genimage 설정은 다음과 같다(실행하지 않음 — genimage가 VM에 없고, host-genimage는 전체 빌드 때 만들어진다).

root-arm64는 Discoverable Partitions 규격의 arm64 루트 파티션 타입 별칭이다(2026.08 트리의 board/ 아래 genimage 설정 3곳에서 쓰인다). 실제 제품에서는 여기에 A/B rootfs 두 개, /data 파티션, U-Boot 환경 영역이 붙는다 — OTA(L 모듈)의 전제다. genimage.sh는 --inputpath와 --outputpath를 둘 다 $(BINARIES_DIR)로 주므로, 입력(rootfs.ext4)과 출력(sdcard.img)이 모두 output/images/에 있다.

11. 드라이버 개발 루프 — <PKG>_OVERRIDE_SRCDIR#

11.1 문제#

드라이버를 고칠 때마다 git에 커밋·태그하고 K3_IMU_MOD_VERSION을 올리고 dirclean할 수는 없다. 매뉴얼(using-buildroot-development.adoc)의 해법은 override 파일 local.mk다. 기본 위치는 .config 옆($(CONFIG_DIR)/local.mk, 즉 O= 디렉터리)이다.

이 줄이 있으면 Buildroot는 그 패키지를 다운로드·압축 해제·패치하지 않고, 지정한 디렉터리를 rsync로 build/<pkg>-custom/에 복사해 빌드한다. make clean도 원본 디렉터리는 건드리지 않는다. 커널도 같은 방식(LINUX_OVERRIDE_SRCDIR = /home/…/linux)으로 회사 커널 작업 트리를 그대로 쓸 수 있다.

12. legal-info — 라이선스 산출물 (K7로 연결)#

make legal-info는 선택된 모든 패키지의 소스 tarball, 패치, 라이선스 파일, 매니페스트(CSV) 를 output/legal-info/에 모은다. GPL 패키지의 "소스 제공 의무"를 지키는 기본 재료다. 모든 소스를 내려받아야 하므로 실행하지 않았다.

회사 패키지에 _LICENSE/_LICENSE_FILES를 빠뜨리면 manifest에 "unknown"으로 찍힌다(6.6절에서 check-package가 LICENCE 철자를 못 잡은 이유와 연결). 독점 패키지는 <PKG>_REDISTRIBUTE = NO로 소스가 legal-info에 복사되지 않게 한다. SBOM 생성(utils/generate-cyclonedx — 2026.08 utils/에 실제로 있다), GPL·LGPL 의무, 고객 배포 절차는 K7에서 다룬다.

14.3 CI 파이프라인 (실행하지 않음 — 가이드)#

실무 체크 포인트:

  • 릴리스 빌드는 clean 빌드로만 한다(10절 — 증분 빌드는 이전 설정의 잔재가 남을 수 있다). 증분은 개발자 PC에서만.
  • BR2_PRIMARY_SITE를 사내 미러로, BR2_BACKUP_SITE를 비워 외부 의존을 끊으면 업스트림 사이트가 사라져도 재현된다.
  • BR2_REPRODUCIBLE(experimental)로 타임스탬프 등을 고정할 수 있다.
  • .config, build.log, legal-info/를 이미지와 함께 보관해야 "필드의 장비가 정확히 무엇으로 빌드됐나"에 답할 수 있다. post-build가 /etc/k3-build-info에 넣은 빌드 ID가 그 연결 고리다.
  • 앱 개발자에게는 make sdk로 만든 relocatable 툴체인 tarball을 준다(실행하지 않음). 앱 팀은 Buildroot 전체를 빌드하지 않고 같은 sysroot로 크로스 컴파일한다.

15. 커널 안에서는 무슨 일이 일어나나#

Buildroot 자체는 빌드 도구라 커널 안으로 들어가지 않는다. 하지만 kernel-module 패키지 하나가 보드에서 /dev 노드가 되기까지는 E·G 모듈의 커널 경로를 그대로 탄다.

그림 6 — 왼쪽은 7.3절에서 손으로 돌린 빌드 머신 쪽 단계, 오른쪽은 7.4절 QEMU 게스트에서 일어난 커널 경로.

  • 빌드 쪽: package/pkg-kernel-module.mk의 KERNEL_MODULES_BUILD 훅은 $(LINUX_MAKE_ENV) make -C $(LINUX_DIR) $(LINUX_MAKE_FLAGS) M=$(@D) modules를 실행한다. E4에서 make -C /var/lab/out/linux-build M=$PWD로 하던 것과 같다. 다른 점은 LINUX_MAKE_FLAGS에 ARCH=arm64 CROSS_COMPILE=$(TARGET_CROSS)가 들어 있다는 것뿐이다. 이 인프라는 커널 config의 CONFIG_TRIM_UNUSED_KSYMS를 끈다(_LINUX_CONFIG_FIXUPS). 켜져 있으면 in-tree에서 쓰지 않는 심볼이 export에서 빠져 외부 모듈이 링크되지 않기 때문이다.
  • 설치 쪽: modules_install은 INSTALL_MOD_PATH=$(TARGET_DIR) 아래 lib/modules/<kernelrelease>/updates/에 .ko를 넣고 depmod를 돌린다. 그래서 보드에서 modprobe k3_imu가 경로 없이 동작한다(7.4절 출력).
  • 보드 쪽: BusyBox modprobe → finit_module(2) syscall(BusyBox 1.37 modutils.c는 finit_module을 먼저 시도하고 실패하면 init_module로 내려간다) → 커널의 load_module()(vermagic·심볼 버전 검사, 재배치) → module_init → misc_register()가 device_create()를 불러 uevent를 내고, devtmpfs가 /dev/k3_imu를 major 10(misc)로 만든다. 노드 권한 0444는 struct miscdevice의 .mode에서 온 것이다(G7). 이후 read()는 VFS → misc 계층 → k3_imu_fops.read로 간다(A3, G4).
  • 드라이버를 쓸 때 다시 만나는 지점: _LINUX_CONFIG_FIXUPS로 드라이버가 필요로 하는 커널 옵션을 패키지와 함께 관리(D·I 모듈의 서브시스템 의존), DT overlay를 함께 설치하려면 같은 패키지의 _INSTALL_TARGET_CMDS나 _INSTALL_IMAGES_CMDS로 .dtbo를 넣는다(D 모듈). 펌웨어 blob(/lib/firmware)은 G10.

장면 1 — 센서 키트 첫 이미지 만들기. 장면 2 — "드라이버 고쳤는데 이미지에 안 들어가요". 원인은 거의 항상 둘 중 하나다. make k3-imu-mod-rebuild만 하고 마지막 make를 안 해서 rootfs 이미지가 예전 것이거나, OVERRIDE_SRCDIR 없이 원본 tarball/git 버전이 그대로라서 수정이 반영되지 않은 것이다. make k3-imu-mod-show-info의 source_dir가 -custom인지, images/rootfs.ext4의 시각이 최신인지 본다.

장면 3 — 필드 장비 문제 분석. 고객 장비의 /etc/k3-build-info에서 빌드 ID를 읽고, CI 아티팩트에서 그 빌드의 .config, staging(심볼 있는 바이너리), legal-info/manifest.csv를 찾는다. 크래시 코어 덤프는 staging의 unstripped 바이너리로 gdb에서 연다(3.3절). 이 연결이 끊기면 "어떤 소스로 빌드됐는지 모르는 장비"가 생긴다.

장면 4 — 보안 패치 대응. CVE가 공지되면 LTS 포인트 릴리스(2025.02.x)의 CHANGES를 확인하고 submodule을 올린다. 해당 패키지만 바뀌었어도 릴리스는 clean 빌드로 다시 만든다. show-info의 cpe-id·ignore_cves(5.6절)와 utils/generate-cyclonedx 결과를 보안 스캐너에 넣는다(K7).

18. 면접에서 이렇게 말한다#

Q. What is Buildroot, and how does it produce an image?

A. Buildroot는 GNU Make와 Kconfig로 된 임베디드 Linux 이미지 생성기다. defconfig로 설정을 정하면 크로스 툴체인을 만들거나 받아 오고, 패키지를 의존 순서대로 download·extract·patch·configure·build·install해서 output/target에 rootfs를 모은다. 그다음 overlay와 post-build 스크립트로 다듬고, fakeroot 안에서 사용자·권한 테이블을 적용해 ext4 같은 파일시스템 이미지를 만들고, post-image에서 genimage로 SD 카드 이미지를 만든다.

Buildroot is a Make- and Kconfig-based image generator. A defconfig selects the architecture, toolchain, kernel, bootloader and packages. Buildroot then builds or imports a cross toolchain, builds each package through download, extract, patch, configure, build and install steps into output/target, applies the rootfs overlay and post-build scripts, generates filesystem images under fakeroot using the users and permission tables, and finally runs post-image scripts, typically genimage, to produce a flashable disk image.

꼬리 질문: "Why fakeroot?" — 빌드는 일반 사용자로 하지만 이미지 안 파일은 root 소유·특수 권한이어야 하므로, chown과 stat을 가로채는 fakeroot 세션 안에서 mkfs를 돌린다.

Q. What is the difference between the staging directory and the target directory?

A. staging은 크로스 툴체인의 sysroot다. 헤더·정적 라이브러리·pkg-config 파일·심볼 있는 라이브러리가 들어가고, 다른 패키지가 컴파일·링크할 때 쓴다. target은 보드에 실릴 rootfs로, 실행 파일과 공유 라이브러리만 strip된 상태로 들어간다. 라이브러리 패키지는 INSTALL_STAGING = YES로 양쪽에 설치한다. 원격 디버깅 때 gdb의 sysroot를 staging으로 두는 이유이기도 하다.

Staging is the toolchain sysroot, host/<tuple>/sysroot. It contains headers, static libraries, pkg-config files and unstripped libraries, and it is what other packages compile and link against. Target is what ends up on the device: binaries and shared libraries only, stripped, no headers. Library packages set INSTALL_STAGING to YES so they land in both. For remote debugging I point gdb's sysroot at staging to get symbols.

Q. How do you add your own application or driver to a Buildroot build?

A. 회사 BR2_EXTERNAL 트리에 패키지 디렉터리를 만든다. Config.in에 메뉴 항목과 의존성, .mk에 VERSION·SITE·LICENSE·LICENSE_FILES를 쓰고 빌드 시스템에 맞는 인프라를 eval한다 — CMake면 cmake-package라 빌드 명령을 안 써도 되고, 손으로 쓴 Makefile이면 generic-package에 BUILD_CMDS와 INSTALL_TARGET_CMDS를 쓴다. 드라이버는 kernel-module 인프라를 generic-package와 함께 eval하면 커널 트리에 대해 Kbuild로 빌드하고 modules_install까지 해 준다. 공개 tarball이면 .hash도 넣고, 마지막에 utils/check-package로 린트한다.

I add a package directory in our BR2_EXTERNAL tree: a Config.in entry with its dependencies, and a .mk that sets VERSION, SITE, LICENSE and LICENSE_FILES and evaluates the right infrastructure. For CMake it is cmake-package and I usually only set CONF_OPTS; for a hand-written Makefile it is generic-package with BUILD_CMDS and INSTALL_TARGET_CMDS. For an out-of-tree driver I evaluate kernel-module together with generic-package, which builds it with Kbuild against the Buildroot kernel and runs modules_install, and adds the linux dependency automatically. Then I run utils/check-package.

Q. Why would you use BR2_EXTERNAL instead of committing to the Buildroot tree?

A. Buildroot 트리를 업스트림 그대로 유지하려고다. 회사 defconfig·보드 파일·패키지·패치를 외부 트리에 두면, Buildroot는 submodule로 LTS 태그에 고정하고 업그레이드는 태그 이동 + savedefconfig diff 리뷰로 끝난다. 경로는 BR2_EXTERNAL_<NAME>_PATH로 쓰므로 어디에 clone해도 동작하고, 여러 외부 트리를 겹칠 수도 있다.

To keep Buildroot itself pristine. Our defconfigs, board files, packages and patches live in an external tree referenced through BR2_EXTERNAL_<NAME>_PATH, while Buildroot is a submodule pinned to an LTS tag. Upgrading becomes moving the tag and reviewing the savedefconfig diff, instead of rebasing a fork.

Q. You changed an option in menuconfig and ran make, but the change is not in the image. Why?

A. Buildroot는 설정 변경을 추적하지 않고 패키지별 stamp 파일만 본다. 이미 빌드된 패키지는 다시 configure되지 않는다. 해당 패키지를 -reconfigure나 -rebuild하고 마지막에 make로 rootfs를 다시 묶어야 한다. 아키텍처·툴체인 변경이나 패키지 제거는 make clean all이 필요하다 — 어떤 패키지가 어떤 파일을 설치했는지 추적하지 않기 때문이다.

Buildroot deliberately does not track configuration changes; it relies on per-package stamp files. A package that was already built is not reconfigured, so I run make <pkg>-reconfigure or -rebuild and then a plain make to regenerate the rootfs. Changing the architecture or toolchain, or removing a package, needs make clean all, because Buildroot does not track which files each package installed.

꼬리 질문: "How do you iterate on a driver quickly?" — local.mk에 <PKG>_OVERRIDE_SRCDIR를 지정하면 다운로드 대신 로컬 작업 트리를 rsync해 빌드하므로 make <pkg>-rebuild && make로 루프를 돈다.

Q. Rootfs overlay, post-build script, post-image script — when do you use which?

A. 정적 설정 파일은 overlay로 얹는다. 빌드 ID 각인, 파일 생성·삭제처럼 로직이 필요하면 post-build(TARGET_DIR를 인자로 받음, fakeroot 전). 소유권·권한은 스크립트에서 chown하지 말고 users·device 테이블로. 디스크 이미지 조립·서명·업데이트 번들은 post-image(BINARIES_DIR를 인자로 받음)에서 genimage로 한다.

Static files go in the overlay. Anything that needs logic, like stamping a build ID or removing a service, goes in post-build, which receives TARGET_DIR and runs before fakeroot. Ownership and permissions go in the users and device tables, not chown in a script. Disk image assembly, signing and update bundles go in post-image, which receives BINARIES_DIR, usually with genimage.

Q. Buildroot or Yocto for a new robotics product?

A. 팀이 작고 제품이 하나이며 이미지를 통째로 OTA하는 구조라면 Buildroot가 빠르고 단순하다. 반대로 SoC 벤더 BSP가 Yocto 레이어로만 제공되거나(NXP·TI가 대표적), 제품 라인이 여러 개거나, 패키지 피드로 부분 업데이트를 하거나, 큰 팀이 sstate 캐시를 공유해야 하면 Yocto다. 실제로는 벤더 BSP 지원이 결정 요인인 경우가 많다.

If it is a small team shipping one product with whole-image A/B updates, Buildroot is faster to set up and easier to reason about. If the SoC vendor ships its BSP as Yocto layers, if there are several product lines, if we need package feeds, or a large team sharing an sstate cache, Yocto wins. In practice vendor BSP support is often the deciding factor.

Q. How do you make Buildroot builds reproducible and CI-friendly?

A. Buildroot는 LTS 태그로 고정, defconfig는 savedefconfig 형식으로 커밋, 외부 트리 하나에 제품 정의 전부. CI는 clean 빌드, BR2_DL_DIR로 공유 다운로드 캐시, BR2_PRIMARY_SITE로 사내 미러, 해시 강제. 산출물로 이미지와 함께 .config, legal-info, 빌드 로그를 보관하고 빌드 ID를 rootfs에 각인한다.

Pin Buildroot to an LTS tag, commit defconfigs in savedefconfig form, keep the whole product in one external tree. CI does clean builds with a shared BR2_DL_DIR, an internal primary mirror, forced hash checks, and a savedefconfig diff to catch Kconfig silently changing choices. We archive the image together with .config, legal-info and the build log, and stamp the build ID into the rootfs.

21. 요약 & 체크리스트#

Buildroot는 Make와 Kconfig로 된 이미지 공장이다. defconfig가 아키텍처·툴체인·커널·패키지를 고르면, 툴체인(internal 빌드 또는 external 수입) → 패키지(stamp 파일로 단계 관리) → target/ 조립 → overlay·post-build → fakeroot 안 users/device 테이블과 mkfs → post-image·genimage 순서로 이미지를 만든다. staging은 툴체인 sysroot(개발용), target은 제품용이다. 회사 제품은 업스트림 트리를 건드리지 않고 BR2_EXTERNAL 트리에 defconfig·보드·패키지를 두며, 패키지는 Config.in + .mk + .hash와 빌드 시스템에 맞는 인프라(generic/cmake/kernel-module …)로 쓴다. Buildroot는 설정 변경을 추적하지 않으므로 -reconfigure/-rebuild/clean all을 사용자가 판단하고, 드라이버 개발은 local.mk의 OVERRIDE_SRCDIR로 루프를 돈다. Yocto와 비교하면 단순·빠름 대 확장성·벤더 BSP·자동 재빌드의 교환이다.
