0. 큰 그림 — Yocto는 "배포판을 만드는 공장"이다#

SSD 펌웨어 시절 빌드를 떠올려 보자. 펌웨어 이미지 하나를 만들려면 컴파일러 버전, 링커 스크립트, 제품별 #define(용량·NAND 종류·고객사), 각 모듈의 빌드 순서, 그리고 "이 바이너리에 어떤 기능이 들어갔나"를 기록하는 장치가 필요했다. 보통 Makefile 몇 개와 제품별 설정 파일로 해결했다.

Embedded Linux 장비의 이미지는 규모가 다르다. 부트로더, 커널, C 라이브러리, BusyBox 또는 coreutils, systemd, OpenSSL, Python, 앱 수십 개 — 수백 개의 오픈소스 프로젝트를 같은 툴체인으로, 같은 정책(보안 플래그·init 시스템·라이선스 규칙)으로, 보드에 맞게 크로스 빌드해서 하나의 rootfs로 묶어야 한다. 그리고 다음 달에도, 3년 뒤에도 같은 결과가 나와야 한다.

Yocto Project는 이 일을 하는 빌드 프레임워크다. 핵심 아이디어는 세 가지다.

  • 모든 것은 메타데이터(텍스트 파일)다. "busybox 1.37.0을 이 URL에서 받아 이 패치를 적용하고 이 설정으로 빌드하라"가 레시피(.bb) 한 장이다. 툴체인도, 커널도, 이미지도 레시피다.
  • 메타데이터는 layer로 쌓는다. 커뮤니티 공통 레시피(OE-Core) 위에 SoC 벤더 BSP layer, 그 위에 우리 제품 layer. 남의 레시피는 고치지 않고 위 layer에서 덧씌운다(.bbappend).
  • BitBake가 메타데이터를 읽어 태스크 그래프를 만들고 병렬로 실행한다. 태스크 결과는 해시로 캐시(sstate)되어, 입력이 같으면 다시 빌드하지 않는다.

그림 1 — 이름 정리. Yocto Project는 우산이고, 실제로 일하는 것은 BitBake(엔진) + OpenEmbedded-Core(공통 메타데이터)다. Poky는 레퍼런스 DISTRO의 이름이다. 아래쪽 layer들은 Yocto Project 밖에서 만들어져 같은 방식으로 쌓인다.

0.3 이 노트의 실습 범위 — 빌드는 하지 않는다#

전체 빌드는 하지 않는다(Don이 나중에 직접 한다). 대신 다음은 전부 실제로 실행했다.

  • 실제 Wrynose 메타데이터 파일 읽기 (grep, sed)
  • 빌드 디렉터리 만들기(oe-init-build-env), bitbake-layers, bitbake-config-build, bitbake-getvar — 설정 파싱 단계까지는 BitBake가 정상 동작했다
  • BitBake 파서(tinfoil API)로 레시피 파일 하나씩 파싱 — 태스크는 실행하지 않고 변수·태스크 목록만 꺼낸다
  • 예제 layer meta-k4-sensorkit의 C 앱을 VM gcc로 컴파일·실행, 라이선스 md5 계산, BusyBox 설정 조각 병합

그리고 빌드를 시작하는 순간 Ubuntu 26.04의 AppArmor user namespace 제한에 막힌다는 것도 실제 에러로 확인했다(10절). 실제 빌드 절차·출력이 필요한 부분은 "실행하지 않음 — 가이드"라고 표시하고, 출력을 지어내지 않았다.

실습 환경: Lima VM elinux, Ubuntu 26.04.1 LTS, 커널 7.0.0-38-generic, aarch64 6코어, RAM 11 GB, /var/tmp 여유 68 GB.

1. 메타데이터 모델 — conf · class · recipe · layer#

1.1 파일 종류는 다섯 가지뿐이다#

BitBake가 읽는 파일은 확장자로 역할이 정해진다.

파일역할예bare-metal 비유
.conf전역 설정. 변수만 정의bitbake.conf, local.conf, machine/qemuarm64.conf, layer.conf전역 config.h, 보드 헤더
.bbclass공통 로직(태스크 함수·변수). inherit로 가져다 씀autotools.bbclass, image.bbclass, module.bbclass공용 Makefile include (rules.mk)
.bb레시피 = 소프트웨어 하나(또는 이미지 하나) 빌드 방법busybox_1.37.0.bb, core-image-minimal.bb모듈별 Makefile
.bbappend다른 layer의 .bb에 덧붙이는 조각busybox_%.bbappend벤더 코드를 안 건드리고 제품 패치를 얹는 오버레이
.increquire/include로 끼워 넣는 공용 조각busybox.inc, qemu.inc#include "common.h"

OE-Core의 meta/를 세어 보면 규모가 감이 온다. 클래스 디렉터리는 세 개로 나뉘어 있다: classes-global/(전역 INHERIT로만 쓰는 것), classes-recipe/(레시피에서 inherit하는 것), classes/(둘 다 가능).

출력에서 볼 것: OE-Core 하나에 레시피 950개, 클래스 230개. 이게 "공통 바닥"이고, 제품에 필요한 나머지(Qt, ROS 2, 벤더 GPU 드라이버 …)는 다른 layer에서 온다.

1.2 layer란 무엇이고, 어떻게 자기를 등록하나#

layer는 conf/layer.conf가 들어 있는 디렉터리다. 관례상 이름이 meta-로 시작한다. layer.conf는 BitBake에게 세 가지를 알려 준다: 내 conf·class를 어디서 찾나(BBPATH), 내 레시피는 어떤 파일인가(BBFILES), 나의 이름과 우선순위는(BBFILE_COLLECTIONS, BBFILE_PRIORITY_<이름>).

실제 OE-Core와 meta-poky의 layer.conf 앞부분이다.

출력에서 볼 것:

  • BBPATH는 콜론으로 이은 검색 경로다. require conf/machine/qemuarm64.conf나 inherit autotools가 나오면 BitBake는 BBPATH의 각 디렉터리 아래 conf/…, classes-recipe/…를 차례로 찾는다. OE-Core는 뒤에 붙이고(.=), meta-poky는 앞에 붙인다(=.) — 앞에 있을수록 먼저 찾아진다.
  • BBFILES는 glob 패턴이다. 그래서 레시피는 반드시 recipes-<분류>/<이름>/<이름>_<버전>.bb 깊이에 있어야 잡힌다. 디렉터리 한 단계를 잘못 만들면 레시피가 "없는 것"이 된다.
  • OE-Core layer.conf는 .bbappend를 BBFILES에 넣지 않는다 — OE-Core는 남의 레시피를 고치지 않는 바닥이기 때문이다.
  • LAYERSERIES_COMPAT은 "이 layer는 어느 릴리스와 호환되나"의 선언이다. 다르면 거부된다(아래 예제).
  • LAYERDEPENDS는 "이 layer가 동작하려면 어떤 layer가 있어야 하나"다.

1.3 layer 쌓기, 우선순위, bbappend 순서#

그림 2 — layer 스택. 빌드 디렉터리의 bblayers.conf가 쓸 layer 목록(BBLAYERS)을 정하고, 각 layer의 layer.conf가 자기 경로를 BBPATH·BBFILES에 등록한다. 같은 레시피가 여러 layer에 있으면 우선순위가 높은 쪽이, bbappend는 낮은 쪽부터 적용되어 높은 쪽이 마지막에 덮는다.

bbappend 적용 순서를 BitBake 소스로 확인했다. lib/bb/cooker.py는 BBFILES를 우선순위 오름차순으로 정렬하고, 그 순서대로 .bbappend 목록을 만든다.

출력에서 볼 것: bbappend 매칭은 파일 이름으로 한다. busybox_%.bbappend의 %는 "이 뒤는 아무거나" 와일드카드라서 busybox_1.37.0.bb에도, 다음 릴리스의 busybox_1.38.0.bb에도 붙는다. busybox_1.37.0.bbappend처럼 버전을 박으면 레시피 버전이 올라가는 순간 "bbappend에 짝이 없다"는 에러로 빌드가 멈춘다. 이건 의도된 안전장치다 — 버전이 바뀌면 덧붙인 패치가 여전히 맞는지 사람이 확인하라는 뜻이다.

1.4 파싱 순서 — 전역 설정 한 번, 레시피마다 한 번#

BitBake의 일은 두 단계다.

  1. 전역 설정 파싱(한 번): conf/bblayers.conf → 각 layer.conf → conf/bitbake.conf. bitbake.conf가 다시 local.conf, MACHINE conf, DISTRO conf 등을 include하고, 마지막에 INHERIT 목록의 전역 클래스를 읽는다. 결과는 전역 datastore(변수 사전) 하나다.
  2. 레시피 파싱(레시피마다): 전역 datastore를 복사한 뒤 .bb를 읽고, inherit한 클래스와 .bbappend를 얹고, override·:append를 확정한다. 결과가 레시피 datastore이고, 이게 그 레시피 태스크들의 입력이다.

bitbake.conf 안의 include 순서는 실제 파일에서 바로 보인다.

출력에서 볼 것:

  • local.conf가 machine/distro conf보다 먼저 읽힌다. 그래서 local.conf에서 MACHINE = "..."라고 정하면 그 값으로 825행의 conf/machine/${MACHINE}.conf가 결정된다. 반대로 machine conf 안에서 ?=로 준 기본값은 local.conf가 이미 정한 값을 못 이긴다.
  • include는 파일이 없어도 조용히 넘어가고, require는 없으면 에러다. MACHINE을 오타 내면 825행이 조용히 넘어가는 대신, 나중에 sanity 검사가 "MACHINE을 찾을 수 없다"고 알려 준다.
  • addfragments(822행)는 Wrynose의 새 기능인 설정 조각(fragment)을 적용한다. 2.3절에서 쓴다.
  • 패키지 형식(PACKAGE_CLASSES)도, sstate·라이선스·SPDX·buildstats도 결국 INHERIT로 들어가는 전역 클래스다(INHERIT_DISTRO).

그림 3 — BitBake의 파싱 순서. ①은 빌드 디렉터리당 한 번, ②는 레시피마다 일어난다. 이 노트에서는 ①과 ②를 실제로 돌렸고, 그 다음 단계인 태스크 실행(빌드)만 하지 않았다.

1.5 레시피 이름에서 PN·PV가 나온다#

레시피 파일 이름 규칙은 <PN>_<PV>.bb다. bitbake.conf가 파일 이름을 잘라 변수로 만든다.

출력에서 볼 것:

  • PN(package name) = 파일 이름의 _ 앞, PV(package version) = _ 뒤. 버전이 없으면 1.0. PR(package revision)은 레시피를 고쳤을 때 올리는 리비전이었지만, 지금은 PR 서버/해시가 관리해서 손으로 올릴 일이 거의 없다. PE(epoch)는 버전 번호가 거꾸로 갈 때만 쓴다.
  • git 소스의 기본 풀림 위치 BB_GIT_DEFAULT_DESTSUFFIX도 ${BP}라서, git으로 받는 레시피는 기본 S가 그대로 맞는다.
  • 6.0의 WORKDIR에는 PR이 들어가지 않는다(.../<PN>/<PV>). 그리고 소스는 WORKDIR 바로 아래가 아니라 ${WORKDIR}/sources(UNPACKDIR)에 풀린다. 옛 튜토리얼의 S = "${WORKDIR}/git"나 S = "${WORKDIR}"는 5.3부터 에러다 — migration-5.3 문서가 S = "${UNPACKDIR}/something"으로 바꾸라고 하고, git 소스는 기본값이 맞으므로 S 줄을 아예 지우라고 한다.

2. 빌드 디렉터리 — oe-init-build-env, local.conf, fragment#

2.1 빌드 디렉터리 만들기#

빌드는 항상 빌드 디렉터리 안에서 한다. oe-init-build-env를 source하면 디렉터리가 없을 때 템플릿으로 conf/를 만들고, PATH에 bitbake와 OE 스크립트를 넣고, 그 디렉터리로 cd한다. 개별 clone 방식에서는 bitbake 위치를 BITBAKEDIR로 알려 준다.

출력에서 볼 것: conf/ 아래 두 파일이 핵심이다 — bblayers.conf(어떤 layer를 쓰나)와 local.conf(이 빌드의 설정). 템플릿은 OE-Core의 meta/conf/templates/default에서 왔다(Wrynose에서는 템플릿이 meta-poky가 아니라 OE-Core에 있다). 이 템플릿의 bblayers.conf는 OE-Core 하나만 담고 있고 DISTRO도 정하지 않는다.

출력에서 볼 것: 아무 것도 안 하면 DISTRO는 nodistro(OE-Core 기본 정책)다. Poky로 빌드하려면 meta-poky layer를 추가하고 DISTRO를 poky로 바꿔야 한다 — bitbake-setup의 poky-wrynose 설정이 정확히 그 일(layer 3개 + distro/poky fragment)을 대신 해 준다.

2.2 첫 실행에서 만나는 것 — HOSTTOOLS 검사#

환경을 잡고 첫 명령을 실행하면 BitBake는 먼저 호스트를 검사한다.

출력에서 볼 것: OE는 빌드가 호스트 환경에 오염되지 않도록, HOSTTOOLS에 나열된 호스트 명령만 tmp/hosttools/에 심볼릭 링크로 모아 두고 PATH를 그 디렉터리로 제한한다. 목록에 있는데 호스트에 없으면 시작조차 하지 않는다. 이 VM에는 chrpath와 diffstat이 없었다(공용 VM이라 apt 설치는 하지 않았다). 정식 해결은 sudo apt install chrpath diffstat(또는 yocto-docs의 Ubuntu 필수 패키지 목록 전체)이다.

이 노트에서는 설정 파싱만 하려고, 아무 일도 하지 않는 가짜 chrpath/diffstat 스크립트를 /var/tmp/K4/k4_fakebin에 두고 PATH 뒤에 붙였다. 실제 빌드에서는 절대 이렇게 하면 안 된다(chrpath는 바이너리의 RPATH를 고치는 도구라 가짜면 패키지가 망가진다). 그 뒤 hosttools 디렉터리가 만들어진 모습이다.

출력에서 볼 것: 호스트 명령 124개만 허용 목록으로 링크되어 있다. 호스트 gcc는 native 도구를 빌드할 때만 쓰이고, 타깃 코드는 Yocto가 직접 만든 크로스 gcc로 빌드한다.

2.3 layer 추가와 MACHINE/DISTRO 선택 — bitbake-layers, bitbake-config-build#

예제 layer(9절)와 meta-poky를 추가한다. bitbake-layers add-layer는 bblayers.conf를 고치고, 추가한 상태로 설정을 다시 파싱해 문제가 있으면 되돌린다.

출력에서 볼 것: 첫 열은 디렉터리 이름이 아니라 BBFILE_COLLECTIONS에 등록한 collection 이름이다(meta-poky의 이름은 "yocto").

호환되지 않는 layer를 넣으면 어떻게 되나. bitbake-layers create-layer로 템플릿 layer를 만들고, LAYERSERIES_COMPAT을 일부러 이전 LTS 이름으로 바꿔 추가해 봤다.

출력에서 볼 것: 거부되고 bblayers.conf는 그대로다(0). 인터넷에서 찾은 layer가 Scarthgap용이면 이렇게 막힌다. LAYERSERIES_COMPAT만 고쳐서 억지로 넣는 것은 "컴파일 경고를 끄는 것"과 같다 — 실제로 호환되는지는 빌드와 테스트로 확인해야 한다.

다음은 MACHINE과 DISTRO 선택이다. 예전에는 local.conf에 MACHINE = "..."를 직접 썼다(지금도 된다). Wrynose에는 fragment 방식이 새로 생겼다. machine/<이름>, distro/<이름>은 내장 fragment라서 아무 MACHINE/DISTRO 이름이나 붙일 수 있다.

출력에서 볼 것: 도구가 고치는 파일(toolcfg.conf)과 사람이 고치는 파일(local.conf)이 분리되었다. k4-sensorkit, k4-distro는 9절에서 만든 예제 layer의 MACHINE/DISTRO다.

2.4 bitbake-getvar — "이 변수의 최종 값과 출처"#

설정 디버깅의 1번 도구다. 예전 bitbake -e | grep을 대신한다. 설정 단계 변수는 레시피를 파싱하지 않아도 바로 나온다.

출력에서 볼 것:

  • MULTIMACH_TARGET_SYS=cortexa57-poky-linux — 이게 작업 디렉터리 경로(tmp/work/cortexa57-poky-linux/...)의 아키텍처 부분이다. 같은 CPU tune을 쓰는 보드끼리는 대부분의 패키지를 공유한다.

3. 변수 문법 — 대입 연산자, override, 인라인 Python#

BitBake 메타데이터는 결국 변수 대입의 연속이다. 그런데 대입 연산자가 열 가지 가까이 되고, "언제 계산되나"와 "어느 것이 이기나" 규칙이 C와 완전히 다르다. 면접에서도 실무에서도 여기서 가장 많이 틀린다.

3.1 연산자 한눈에 보기#

연산자뜻계산 시점대표 용도
A = "v"대입 (덮어씀)읽을 때 확장 (지연)레시피의 대부분
A ?= "v"아직 값이 없을 때만 대입그 줄을 읽을 때 판단machine/distro conf의 기본값
A ??= "v"가장 약한 기본값. 파싱이 다 끝나도 아무도 안 정했을 때만파싱 끝템플릿 local.conf의 MACHINE ??=
A := "v"즉시 확장해서 대입그 줄에서경로를 그 시점 값으로 고정 (${THISDIR})
A += "v"뒤에 공백 + v그 줄에서 붙임목록에 추가
A =+ "v"앞에 v + 공백그 줄에서 붙임목록 앞에 추가
A .= "v"뒤에 공백 없이 붙임그 줄에서 붙임경로·문자열 이어 붙이기 (BBPATH .=)
A =. "v"앞에 공백 없이 붙임그 줄에서 붙임MACHINEOVERRIDES =. "x:"
A:append = "v"뒤에 붙임 (공백 자동 없음)모든 파싱이 끝난 뒤bbappend·local.conf에서 안전하게 추가
A:prepend = "v"앞에 붙임 (공백 자동 없음)모든 파싱이 끝난 뒤FILESEXTRAPATHS:prepend
A:remove = "v"공백으로 나눈 단어 중 v를 제거가장 마지막기본 기능 끄기 (DISTRO_FEATURES:remove)

핵심은 두 줄이다. += .= 같은 연산자는 "그 줄을 읽는 순간" 붙이고, :append :prepend :remove는 "파싱이 다 끝난 뒤" 적용된다. 그리고 :append는 공백을 넣어 주지 않으니 값 앞에 공백을 직접 쓴다.

3.2 실제 BitBake로 확인하기#

규칙을 외우는 대신 BitBake에게 물어보자. 데모 변수를 담은 파일을 만들고, 빌드 디렉터리의 local.conf 끝에 require /Users/donh/.elinux_scratch/K4/k4_demo_vars.conf 한 줄을 넣었다.

무엇을 확인하나: 각 연산자를 섞었을 때 최종 값.

출력에서 볼 것:

  • K4_A: 이미 값이 있으니 ?=는 무시된다.
  • K4_B: ??=(가장 약함)보다 ?=가 이긴다.
  • K4_C: 줄 순서대로 base → base plus → pre base plus → pre base plus-dot → dot-pre base plus-dot.
  • K4_D: +=가 :append보다 뒤 줄에 있는데도 결과는 late app 순서다. :append는 파싱이 끝난 뒤 적용되기 때문이다. 그리고 :remove가 x를 지운 자리에 앞 공백이 남았다. 목록 변수에서는 무해하지만, 문자열 비교를 하는 곳이면 함정이 된다.
  • K4_E와 K4_F: =는 읽을 때 확장하므로 마지막 값 after, :=는 그 줄에서 확장해 before로 고정.
  • K4_F2: :=인데도 defined-later다. 그 줄 시점에 K4_NOT_YET이 정의되지 않아 ${K4_NOT_YET} 문자열이 그대로 저장됐다가 나중에 확장된 것이다. ":=면 무조건 고정"이 아니다.
  • K4_PY: ${@ ... }는 파싱 중에 도는 Python 식이다. d는 datastore 객체다.

3.3 변수 history — "누가 이 값을 바꿨나"#

bitbake-getvar는 값만이 아니라 어느 파일 몇 번째 줄이 어떤 연산을 했는지를 보여 준다. 실무에서 "왜 내 설정이 안 먹지?"의 답은 거의 항상 여기서 나온다.

출력에서 볼 것: append(= +=)와 :append가 다른 연산으로 기록된다. "pre-expansion value"는 :remove 전 값이다.

3.4 override — 조건부 변수#

override는 변수 이름 뒤에 :<조건>을 붙여 "이 조건일 때만 이 값"을 주는 문법이다. 조건 목록은 OVERRIDES 변수 하나에 콜론으로 이어져 있고, 오른쪽에 있을수록 우선순위가 높다. C의 #ifdef BOARD_X를 변수 단위로 하는 셈이다.

출력에서 볼 것:

  • 순서는 OS(linux) → 아키텍처(aarch64) → 레시피 이름(pn-<PN>) → layer → MACHINE 계열 → DISTRO → 클래스(class-target, native 레시피면 class-native) → forcevariable. 그래서 같은 변수에 :aarch64와 :k4-sensorkit이 둘 다 있으면 MACHINE 쪽이 이기고, :k4-distro가 있으면 그게 더 이긴다.
  • 설정 단계에서 물었기 때문에 pn-defaultpkgname, layer-config, ${TCOVERRIDE}처럼 레시피에서 정해질 부분이 기본값으로 나온다. 레시피를 파싱하면 pn-k4-imu-reader 같은 값이 된다.
  • forcevariable은 맨 오른쪽이라 무엇보다 강하다. A:forcevariable = "..."는 디버깅용 "최후의 수단"이다.

그림 4 — override 선택. OVERRIDES에 있는 조건 중 값이 정의된 것들 가운데 가장 오른쪽이 이긴다. 실제 전체 값은 위 출력(linux:aarch64:pn-…:forcevariable)이고, 그림은 일부만 보였다.

history에서도 override 후보가 따로 기록된다.

MACHINE를 바꾸면 같은 메타데이터에서 다른 값이 나온다. fragment로 MACHINE을 qemux86-64로 바꿔 물어보고, 다시 되돌렸다.

출력에서 볼 것: machine/ fragment는 하나만 활성화된다(새로 켜면 이전 것을 대체). x86에서는 :aarch64 계열이 모두 비활성이라 for-x86이 선택되고, :append:qemux86-64만 붙는다. :append:<override>처럼 연산과 조건을 겹쳐 쓸 수 있다 — "이 MACHINE일 때만 뒤에 붙여라"다.

3.5 varflag — 변수에 붙는 속성#

변수에는 값 말고 flag(속성)도 붙는다. 문법은 VAR[flag] = "...". 태스크의 동작 방식을 정하는 데 많이 쓴다.

출력에서 볼 것: do_fetch만 네트워크를 쓸 수 있다(10절에서 이 flag가 AppArmor 문제와 연결된다). do_compile은 ${B}에서 실행되고, do_install은 시작할 때 ${D}를 비운다 — 그래서 do_install은 몇 번을 다시 돌려도 이전 실행의 찌꺼기가 남지 않는다. 그 밖에 [depends](다른 레시피의 태스크에 의존), [vardeps](이 태스크 해시에 포함할 변수), [doc](설명) 등이 있다.

3.6 가장 유명한 함정 — local.conf의 IMAGE_INSTALL +=#

"이미지에 패키지 하나 넣으려고 local.conf에 IMAGE_INSTALL += "foo"를 썼더니 이미지가 부팅을 안 한다"는 Yocto 입문자의 고전이다. 실제로 재현했다. local.conf 끝에 한 줄을 넣고 두 이미지 레시피를 파싱해 IMAGE_INSTALL을 본 뒤, :append로 바꿔 다시 봤다(파싱 도구 $P는 4.4절에서 설명한다).

출력에서 볼 것 — 두 가지 다른 방식으로 망가진다:

  • core-image-base: core-image.bbclass는 IMAGE_INSTALL ?= "${CORE_IMAGE_BASE_INSTALL}"이다. local.conf가 먼저 읽히면서 +=로 이미 값( k4-imu-reader)을 만들어 버렸으니 ?= 기본값이 무시된다. 이미지에 앱 하나만 들어가고 부팅에 필요한 packagegroup-core-boot가 빠진다.
  • core-image-minimal: 레시피가 IMAGE_INSTALL = "packagegroup-core-boot ..."로 덮어쓰기 때문에 local.conf의 추가가 조용히 사라진다.
  • :append는 모든 대입이 끝난 뒤 적용되므로 두 경우 모두 의도대로 된다. 규칙: local.conf와 bbappend에서는 += 대신 :append(앞에 공백 포함)를 쓴다. 이미지에 넣는 정석은 local.conf가 아니라 이미지 레시피나 packagegroup이다(7.4절).

4. 레시피 해부 — 소프트웨어 하나를 빌드하는 방법#

4.1 가장 작은 레시피#

OE-Core의 meta-skeleton에 있는 "hello world" 레시피가 출발점이다.

한 줄씩 보면:

  • LICENSE: 이 소프트웨어의 라이선스(SPDX 식별자). 이미지에 들어갈 수 있는지, 소스 공개 의무가 있는지를 판단하는 데 쓰인다(K7).
  • LIC_FILES_CHKSUM: 라이선스 텍스트 파일의 md5. 업스트림이 라이선스를 바꾸면 md5가 달라져 빌드가 멈춘다 — 사람이 새 라이선스를 검토하라는 장치다.
  • SRC_URI: 소스를 어디서 가져오나. file://은 레시피 옆의 파일 디렉터리(FILESPATH)에서 찾는다.
  • S: 소스가 풀린 디렉터리. 파일 몇 개뿐이면 ${UNPACKDIR} 자체다.
  • do_compile, do_install: 셸 함수로 쓴 태스크. ${CC}는 크로스 컴파일러와 옵션이 다 들어간 변수다.
  • ${D}${bindir}: D는 "가짜 루트"(설치 대상 디렉터리), bindir은 /usr/bin. 절대로 /usr/bin에 직접 설치하지 않는다. make의 DESTDIR과 같은 개념이다.

MIT 라이선스의 md5가 맞는지 직접 계산해 보자.

출력에서 볼 것: 레시피의 md5와 같다. OE-Core는 SPDX 라이선스 텍스트 732개를 COMMON_LICENSE_DIR에 갖고 있다.

4.2 우리 레시피 — k4-imu-reader#

센서 키트의 IMU 값을 IIO sysfs(I2절)에서 읽어 한 줄 찍는 앱을 레시피로 만든다. 먼저 앱 소스다.

Yocto에 넣기 전에 VM에서 네이티브로 먼저 확인한다. IIO 장치 대신 가짜 sysfs 디렉터리를 만들었다.

출력에서 볼 것: 경고 0개로 빌드되고, 기본 설정(iio:device0)은 VM에 IIO 장치가 없어 실패한다(rc=1) — 정상이다. 마지막 줄은 소스 파일 1~2행(SPDX 줄과 Copyright 줄)의 md5다. 라이선스 파일이 따로 없는 작은 앱은 이렇게 헤더 줄 범위로 체크섬을 건다. OE-Core insane.bbclass가 beginline/endline 사이 줄을 바이트 그대로 md5에 넣는 방식과 sed -n 1,2p | md5sum이 같은 계산이다.

이제 레시피다.

skeleton 레시피보다 늘어난 것:

  • CFLAGS를 넘긴다. skeleton처럼 LDFLAGS만 넘기면 DISTRO가 정한 보안 플래그(-fstack-protector-strong, -D_FORTIFY_SOURCE=2 …)와 최적화가 빠진다. 이 정도로는 빌드가 멈추지 않지만, 디버그 경로 매핑(-ffile-prefix-map)이 빠지면 do_package_qa가 "빌드 경로가 바이너리에 남았다"(buildpaths)고 경고할 수 있다.
  • inherit systemd: 서비스를 패키지에 등록하고 systemctl enable을 설치 후 스크립트로 처리하는 클래스.
  • PACKAGES =+, FILES:, CONFFILES:, RDEPENDS:: 6절에서 다룬다.

4.3 레시피 파일을 BitBake 파서로 검증하기#

빌드는 못 하지만, BitBake의 파서는 돌릴 수 있다. BitBake는 Python 라이브러리 API인 tinfoil을 제공한다(bitbake-layers, devtool도 tinfoil로 만들어져 있다). 설정만 파싱한 뒤 레시피 파일 하나를 파싱하면 레시피 datastore를 얻는다. 이건 태스크를 실행하지 않으므로 빌드가 아니다.

빌드 환경을 잡는 셸 조각(k4_env.sh)과 함께 쓴다. 이후 예제의 $P는 이 스크립트, $R은 우리 레시피 경로다.

무엇을 확인하나: 레시피의 PN/PV와 디렉터리 변수(S, B, D, T)가 어디로 잡히는지.

출력에서 볼 것: 약 1초 — 전역 설정 파싱 + 레시피 하나 파싱이다("Reconnecting"은 직전 명령이 띄운 BitBake 서버를 재사용했다는 뜻). 파일 이름 k4-imu-reader_1.0.bb에서 PN과 PV가 나왔다. 파싱이 에러 없이 끝났다는 것은 문법, inherit systemd, 변수 확장이 모두 통과했다는 뜻이다. S와 B가 같다 — 소스 디렉터리에서 그대로 빌드한다. autotools/cmake/meson 클래스는 B를 별도 디렉터리로 바꿔 out-of-tree 빌드를 한다.

do_compile이 실제로 실행할 명령도 볼 수 있다. 함수 본문을 확장하면 크로스 컴파일러와 플래그가 다 드러난다.

출력에서 볼 것 — B 모듈에서 배운 것이 전부 들어 있다:

  • aarch64-poky-linux-gcc: Yocto가 직접 빌드한 크로스 컴파일러(B1). 이름의 poky는 DISTRO의 TARGET_VENDOR다.
  • -mcpu=cortex-a57+crc: MACHINE의 tune(qemuarm64 → cortex-a57)에서 온다.
  • --sysroot=.../recipe-sysroot: 이 레시피 전용 sysroot(B2). DEPENDS로 선언한 레시피의 헤더·라이브러리만 들어 있다. 선언하지 않은 라이브러리는 보이지 않는다 — 이게 Yocto가 "숨은 의존성"을 잡아내는 방법이다.
  • -ffile-prefix-map=...=/usr/src/debug/...: 디버그 정보에서 빌드 경로를 지워 재현 가능한 바이너리를 만든다(K5).
  • -Wl,-z,relro,-z,now, -D_FORTIFY_SOURCE=2, -fstack-protector-strong: DISTRO가 거는 보안 하드닝 플래그.

4.4 SRC_URI와 FILESPATH — 소스는 어디서 오나#

SRC_URI는 공백으로 나눈 URL 목록이다. 형식(fetcher)별로 정리하면 이렇다.

형식예메모
file://file://0001-fix.patch레시피 옆 디렉터리(FILESPATH)에서 찾는다. .patch·.diff는 do_patch가 자동 적용
https://https://busybox.net/downloads/busybox-${PV}.tar.bz2SRC_URI[sha256sum]으로 무결성 검사
git://git://github.com/x/y.git;protocol=https;branch=mainSRCREV에 커밋 해시를 고정
npm://, crate://, gitsm:// 등언어별 패키지·서브모듈생태계별 fetcher

file://이 어디를 뒤지는지는 FILESPATH가 정한다. busybox 레시피를 meta-poky와 우리 layer의 bbappend를 붙여 파싱해 봤다.

출력에서 볼 것: 검색 경로 35개 = (override 6개 + override 없음 1개) × 디렉터리 5개. 바깥 순서는 override가 구체적인 것부터(k4-distro → k4-sensorkit → … → override 없는 기본 디렉터리), 안쪽 순서는 우리 layer → meta-poky → OE-Core다. 그래서 우리 layer의 busybox/defconfig를 두면 OE-Core의 defconfig 대신 그게 잡히고, busybox/k4-sensorkit/defconfig에 두면 이 MACHINE에서만 바뀐다. 우리 layer와 meta-poky 디렉터리가 앞에 온 것은 두 bbappend의 FILESEXTRAPATHS:prepend 때문이다(8절).

4.5 빌드 시스템 클래스 — 직접 do_compile을 쓰지 않는 방법#

현실의 소프트웨어는 대부분 autotools, CMake, Meson, 커널 Kbuild로 빌드된다. 레시피는 해당 클래스를 inherit만 하면 do_configure/do_compile/do_install이 채워진다.

출력에서 볼 것:

  • EXPORT_FUNCTIONS do_compile은 "이 클래스를 inherit하면 do_compile이 autotools_do_compile을 가리킨다"는 뜻이다. 레시피에서 do_compile()을 직접 정의하면 클래스 것을 덮어쓰고, do_compile:append()로 뒤에 덧붙일 수도 있다. 클래스 원본을 부르고 싶으면 autotools_do_compile처럼 이름을 직접 부른다.
  • 아무 클래스도 상속하지 않으면 base_do_compile이 기본이다 — Makefile이 있으면 oe_runmake(크로스 변수를 넘겨 make 실행), 없으면 아무 것도 안 한다. 그래서 단순 Makefile 프로젝트는 레시피에 do_install만 쓰면 되는 경우가 많다.
소스 형태레시피에 쓸 것클래스가 대신 하는 일
./configure && makeinherit autotools크로스 configure 옵션, make install DESTDIR=${D}
CMakeLists.txtinherit cmake툴체인 파일 생성, out-of-tree 빌드, cmake --install

커널 모듈 레시피의 예도 meta-skeleton에 있다. IMU 드라이버를 out-of-tree로 넣을 때 이 형태를 쓴다(커널 레시피와 패치 관리는 K5).

출력에서 볼 것: 레시피에는 빌드 명령이 한 줄도 없다. module.bbclass가 E2 노트에서 손으로 했던 make -C <커널 빌드 트리> M=$PWD를 크로스 환경으로 대신 실행한다.

5.2 stamp, task hash, sstate — 왜 두 번째 빌드는 빠른가#

Make는 파일 시간(mtime)으로 "다시 빌드할까"를 정한다. BitBake는 task hash를 쓴다. 태스크 하나의 해시는 (그 태스크 함수의 본문 + 함수가 참조하는 변수 값들 + 선행 태스크들의 해시)로 계산된다. 그래서 CFLAGS 한 글자만 바꿔도 do_compile부터 아래가 전부 다시 돈다 — Make보다 정확하다.

  • stamp: 태스크가 끝나면 STAMP 경로에 <PV>.do_compile.<hash> 같은 빈 파일을 만든다. 우리 레시피의 STAMP는 아래와 같다. 다음 빌드에서 같은 해시의 stamp가 있으면 그 태스크를 건너뛴다.
  • sstate(shared state) cache: 일부 태스크(그림 5의 회색 상자 목록)의 결과물을 해시 이름의 tarball로 SSTATE_DIR에 저장한다. 빌드 디렉터리를 지워도, 다른 사람의 머신이어도, 해시가 같으면 _setscene 태스크가 결과만 풀고 fetch~install을 통째로 건너뛴다.

출력에서 볼 것: SSTATE_PKGARCH가 cortexa57이다. 같은 cortex-a57 tune을 쓰는 다른 MACHINE은 이 레시피의 sstate를 그대로 재사용할 수 있다. 반대로 PACKAGE_ARCH = "${MACHINE_ARCH}"인 레시피(packagegroup, 이미지, 보드 설정)는 MACHINE마다 따로 빌드된다. sstate를 팀·CI와 공유하는 방법, hash equivalence 서버, 해시가 왜 바뀌었는지 bitbake-diffsigs로 추적하는 법은 K5에서 다룬다.

5.3 DEPENDS vs RDEPENDS, PROVIDES와 virtual/#

그림 6 — DEPENDS는 빌드할 때 레시피 사이의 의존(sysroot를 채운다), RDEPENDS는 기기에서 돌 때 패키지 사이의 의존(rootfs에 같이 설치된다).

우리 레시피를 파싱해 실제 값을 보자.

출력에서 볼 것:

  • 레시피에 DEPENDS를 한 줄도 안 썼는데 4개가 들어 있다. 크로스 gcc, 컴파일러 런타임, libc는 툴체인 클래스(gcc.bbclass)가, systemd-systemctl-native(빌드 중에 서비스를 enable할 호스트 도구)는 systemd.bbclass가 넣었다. 레시피 하나가 실제로는 30개 클래스를 상속하고 있다.
  • virtual/libc, virtual/compilerlibs는 가상 이름이다. "C 라이브러리를 제공하는 무언가"라는 인터페이스이고, 실제 레시피는 PREFERRED_PROVIDER_virtual/libc가 고른다.

가상 이름이 실제 레시피로 어떻게 연결되나.

출력에서 볼 것:

  • 빌드 시점 가상 이름(virtual/…): 레시피가 PROVIDES로 "나는 virtual/kernel을 제공한다"고 선언하고, 설정이 PREFERRED_PROVIDER_virtual/kernel로 하나를 고른다. 벤더 BSP layer는 이걸 linux-imx, linux-ti-staging, linux-tegra 같은 자기 커널 레시피로 바꾼다. 이미지 쪽에서는 "커널"이라고만 말하면 되니 MACHINE만 바꿔도 다른 커널이 들어간다.
  • 실행 시점 가상 이름(VIRTUAL-RUNTIME_…): 같은 아이디어의 RDEPENDS 버전이다. packagegroup-core-boot는 ${VIRTUAL-RUNTIME_init_manager}를 RDEPENDS로 갖고, DISTRO가 그걸 systemd 또는 sysvinit으로 정한다.
  • 커널 버전 6.18.52+git은 Don의 QEMU 랩 커널(6.18.55 LTS)과 같은 6.18 계열이다. PREFERRED_VERSION_linux-yocto = "6.18%"의 %는 와일드카드다.

6. 패키지 — 레시피 하나가 여러 패키지가 된다#

6.1 PACKAGES와 FILES#

Yocto는 레시피를 빌드한 뒤 D(image/)를 통째로 rootfs에 넣지 않는다. 패키지로 쪼갠 다음, 이미지가 필요한 패키지만 설치한다. 데비안에서 libfoo, libfoo-dev, libfoo-dbg가 따로 있는 것과 같다. 쪼개는 규칙이 PACKAGES(패키지 이름 목록)와 FILES:<패키지>(그 패키지가 가져갈 파일 glob)다.

출력에서 볼 것:

  • 기본 PACKAGES는 bitbake.conf에서 온다: 소스(-src), 디버그 심볼(-dbg), 정적 라이브러리(-staticdev), 헤더·.so 링크(-dev), 문서, 로케일, 그리고 본 패키지(${PN}).
  • 우리 -conf 패키지는 =+로 맨 앞에 넣었다. 순서가 중요하다. do_package는 PACKAGES를 왼쪽부터 돌면서 각 패키지의 FILES에 맞는 파일을 가져가고, 한 번 가져간 파일은 다음 패키지가 못 가져간다. 기본 FILES:${PN}에는 ${sysconfdir}가 들어 있어서, -conf를 뒤에 두면 /etc/k4-imu.conf를 본 패키지가 먼저 가져가 버린다.
  • CONFFILES는 "사용자가 고쳤을 수 있는 설정 파일"이라는 표시다. 패키지 업그레이드 때 덮어쓰지 않는다(rpm은 .rpmnew로 따로 둔다).
  • 어떤 패키지도 가져가지 않은 파일이 D에 남으면 do_package가 "installed-vs-shipped" QA 에러로 멈춘다. "설치해 놓고 출하하지 않은 파일"은 실수일 가능성이 높기 때문이다.

6.2 패키지 형식 — rpm, ipk, deb#

PACKAGE_CLASSES가 패키지 파일 형식을 정한다.

형식클래스기기의 패키지 관리자특징
ipkpackage_ipkopkg가장 가볍다. OE 기본값. 작은 장비
rpmpackage_rpmdnfPoky 기본값. 의존성 해석이 엄격, 메타데이터가 크다
debpackage_debapt/dpkg데비안 도구에 익숙한 팀

여러 개를 적으면("package_rpm package_ipk") 모두 만들고, 첫 번째 형식으로 rootfs를 조립한다. 기기에 패키지 관리자를 넣을지는 별개다 — IMAGE_FEATURES += "package-management"가 없으면 rootfs만 조립하고 dnf/opkg는 들어가지 않는다. 대부분의 제품은 넣지 않고, 업데이트는 이미지 단위(A/B, L 모듈의 OTA)로 한다.

7. MACHINE · DISTRO · IMAGE — 세 축을 분리한다#

그림 8 — Yocto 설정의 세 축. "무슨 보드인가"(MACHINE), "어떤 정책의 OS인가"(DISTRO), "무엇을 설치하나"(IMAGE)를 섞지 않는 것이 layer 설계의 기본이다.

이 분리가 왜 중요한가. 센서 키트 회사를 생각해 보자. 보드는 개발용 EVK, 양산 보드 rev A, rev B가 있고(MACHINE 3개), 정책은 개발용(디버그 도구, root 로그인)과 양산용(서명, 읽기 전용 rootfs)이 있고(DISTRO 2개 또는 DISTRO_FEATURES 차이), 이미지는 공장 테스트용과 출하용이 있다(IMAGE 2개). 이걸 한 파일에 섞으면 3×2×2=12개의 조합을 손으로 관리해야 하지만, 축을 나누면 각자 독립적으로 고칠 수 있다.

  • MACHINE conf에 패키지 목록(IMAGE_INSTALL)을 넣지 않는다.
  • 이미지 레시피에 보드 특정 설정(커널 provider, 시리얼 콘솔)을 넣지 않는다.
  • DISTRO conf에 보드 이름을 쓰지 않는다.

7.1 MACHINE — 보드 정의#

실제 qemuarm64.conf의 주석을 뺀 앞부분이다.

출력에서 볼 것: MACHINE conf가 정하는 것은 CPU tune(tune-cortexa57.inc), 커널 이미지 형식, 부트로더 provider와 defconfig, 시리얼 콘솔(K1의 getty가 여기서 정해진다), 그리고 QB_로 시작하는 runqemu 설정이다. -machine virt -cpu cortex-a57은 Don의 QEMU 부팅 랩(C 모듈)과 똑같은 가상 보드다. 실제 보드라면 여기에 KERNEL_DEVICETREE(D 모듈의 dtb 목록), IMAGE_FSTYPES(wic, ubifs …), MACHINE_FEATURES(wifi, can …)가 들어간다.

우리 layer의 MACHINE stub이다.

2.4절에서 본 것처럼 처음에는 MACHINEOVERRIDES =. 줄 없이 만들었고, MACHINEOVERRIDES에 qemuarm64가 없었다. 이게 실제로 어떤 문제를 일으키나? 커널 레시피를 파싱해 보면 바로 드러난다.

출력에서 볼 것:

  • linux-yocto는 COMPATIBLE_MACHINE 정규식으로 "이 커널은 이 보드들에서만 빌드된다"고 선언한다. 정규식은 MACHINE 이름 하나가 아니라 MACHINEOVERRIDES의 각 항목과 비교된다.
  • MACHINEOVERRIDES =. "qemuarm64:"이 없으면 k4-sensorkit은 어느 항목도 맞지 않아 커널 레시피가 통째로 건너뛰어진다(__SKIPPED). 이미지 빌드는 "virtual/kernel을 제공하는 레시피가 없다"는 에러로 멈춘다.
  • 이것이 실무의 표준 패턴이다. 벤더의 레퍼런스 보드 conf를 require해서 자기 보드를 만들 때(예: imx8mp-evk.conf를 기반으로 mycompany-sensorkit.conf), 레퍼런스 보드의 override를 이어받으려면 그 이름을 MACHINEOVERRIDES 앞에 붙인다. NXP·TI BSP의 SoC 계열 이름(mx8mp, k3 같은 것)도 이 방식으로 MACHINEOVERRIDES에 들어가 있어서, :mx8mp 같은 override 하나로 같은 SoC를 쓰는 모든 보드에 적용된다.

7.2 DISTRO — OS 정책#

poky.conf의 앞부분과 정책 줄 몇 개다.

우리 DISTRO는 poky를 상속하고 init 시스템만 systemd로 바꿨다.

출력에서 볼 것: INIT_MANAGER = "systemd" 한 줄이 DISTRO_FEATURES에 systemd와 usrmerge(/bin → /usr/bin 통합, K1)를 넣고, 앞의 VIRTUAL-RUNTIME_init_manager도 systemd로 바꿨다. DISTRO_FEATURES(27개)는 "이 OS가 지원하는 기능" 목록이고, 레시피들이 bb.utils.contains('DISTRO_FEATURES', 'x11', ...)로 보고 빌드 옵션을 켜고 끈다. 센서 키트처럼 화면이 없는 장비라면 실제 제품 DISTRO에서 DISTRO_FEATURES:remove = "x11 wayland opengl vulkan pulseaudio" 같은 정리를 하는 게 보통이다 — 의존성이 줄어 빌드 시간과 이미지 크기가 크게 준다.

정하는 곳예효과
MACHINE_FEATURESwifi bluetooth can하드웨어에 무엇이 있나
DISTRO_FEATURESsystemd ipv6 x11OS가 무엇을 지원하나
둘의 교집합COMBINED_FEATURES예: bluetooth가 둘 다 있어야 bluez가 들어간다
IMAGE_FEATURESssh-server-dropbear read-only-rootfs이 이미지에 무엇을 켜나

7.3 IMAGE — 이미지 레시피와 packagegroup#

이미지도 레시피다. 다만 컴파일하지 않고, 패키지를 골라 rootfs를 조립한다. 가장 작은 공식 이미지를 보자.

출력에서 볼 것:

  • IMAGE_INSTALL: 설치할 패키지 목록. 그 패키지들의 RDEPENDS는 자동으로 따라 들어온다.
  • IMAGE_FEATURES: 이름 붙은 기능 스위치. FEATURE_PACKAGES_<기능>이 "이 기능을 켜면 이 패키지를 넣어라"의 매핑이다. 그 밖에 read-only-rootfs, allow-root-login처럼 패키지가 아니라 rootfs 후처리를 바꾸는 기능도 있다.
  • IMAGE_LINGUAS = " ": 로케일 패키지를 넣지 않는다(공백 하나가 "빈 목록"이라는 뜻).
  • CORE_IMAGE_EXTRA_INSTALL: local.conf에서 이미지들에 공통으로 끼워 넣으라고 열어 둔 변수.

packagegroup은 "패키지 이름만 묶은 빈 패키지"다. 내용 파일은 없고 RDEPENDS만 있다. core-image-minimal이 넣는 유일한 것인 packagegroup-core-boot를 보자.

출력에서 볼 것: K1 노트에서 본 "최소 rootfs의 필수 구성"이 그대로 여기 있다 — base-files(FHS 디렉터리와 /etc 기본 파일), base-passwd(/etc/passwd), 기본 유틸(BusyBox, K2), init, 장치 관리자(udev 또는 mdev), 로그인. 그리고 MACHINE_ESSENTIAL_EXTRA_RDEPENDS로 보드가 부팅에 꼭 필요한 패키지(펌웨어 blob, 커널 모듈)를 MACHINE conf에서 끼워 넣을 수 있게 열어 두었다.

7.4 우리 이미지와 packagegroup#

위가 packagegroup-k4-sensors.bb, 아래가 k4-sensorkit-image.bb다. 파싱해서 최종적으로 무엇이 설치될지 본다.

출력에서 볼 것:

  • PACKAGE_INSTALL = IMAGE_INSTALL + IMAGE_FEATURES가 끌어온 FEATURE_INSTALL + 자동으로 붙는 run-postinsts(첫 부팅 때 남은 설치 후 스크립트를 돌린다). do_rootfs가 실제로 패키지 관리자에게 넘기는 목록이 이것이다.
  • IMAGE_FSTYPES가 ext4 tar.zst라서 do_image_ext4, do_image_tar 태스크가 생겼다. core-image-minimal은 qemu.inc의 기본값(tar.zst ext4.zst)을 그대로 쓴다. 실제 보드에서는 wic(파티션 테이블까지 포함한 디스크 이미지, K5·L 모듈)를 주로 쓴다.
  • 이미지 작업 디렉터리의 아키텍처 부분은 k4_sensorkit-poky-linux다. 이미지와 packagegroup은 PACKAGE_ARCH = "${MACHINE_ARCH}"(MACHINE 이름의 -를 _로 바꾼 것)라서, 같은 tune을 공유하는 앱 패키지(cortexa57)와 달리 MACHINE마다 따로 만들어진다.
  • ALLOW_EMPTY = '1': 파일이 하나도 없는 패키지도 만들어라 — packagegroup 클래스가 켠다. 보통 레시피에서 빈 패키지는 만들어지지 않는다.

8. bbappend — 남의 레시피를 고치는 정석#

8.1 왜 레시피를 직접 고치지 않나#

OE-Core의 busybox 레시피를 열어 한 줄 고치면 당장은 된다. 하지만 OE-Core는 남의 git 저장소다. 다음 보안 업데이트(git pull)에서 충돌하거나, 더 나쁘게는 고친 것이 조용히 사라진다. 그래서 규칙은 이렇다: 남의 layer는 읽기 전용으로 두고, 바꾸고 싶은 것은 우리 layer의 .bbappend로 덧씌운다. Don의 SSD 펌웨어로 치면, 벤더 SDK 소스를 직접 고치지 않고 우리 쪽 패치 디렉터리와 빌드 스크립트로 얹던 것과 같다.

meta-poky 자신도 이렇게 한다.

출력에서 볼 것: 단 한 줄이다. FILESEXTRAPATHS:prepend로 자기 디렉터리를 file:// 검색 경로 맨 앞에 끼우고, busybox/poky-tiny/ 아래에 poky-tiny DISTRO 전용 설정을 둔다. 4.4절의 FILESPATH 규칙(override 디렉터리 우선) 덕분에 DISTRO가 poky-tiny일 때만 그 파일이 쓰인다. 여기서 :=가 중요하다 — ${THISDIR}는 "지금 파싱 중인 파일의 디렉터리"라서, 지연 확장(=)하면 나중에 다른 파일을 파싱하는 시점의 디렉터리가 들어가 버린다.

8.2 우리 bbappend — BusyBox에 I2C 도구 켜기#

센서 키트 현장 디버깅에는 i2cdetect, i2cget과 레지스터를 직접 보는 devmem이 있으면 편하다(H 모듈). BusyBox 설정은 Kconfig라서 설정 조각(config fragment) 파일로 바꾼다.

bbappend 안에서는 SRC_URI += ...를 썼다. bbappend는 원래 레시피 바로 뒤에 이어 붙여 파싱되므로, 레시피가 이미 SRC_URI를 대입한 다음이라 +=가 안전하다(local.conf와 다른 점이다). :append를 써도 된다.

8.3 .cfg가 어떻게 적용되나 — 실제 코드와 실제 병합#

출력에서 볼 것: busybox의 do_configure(149행)는 SRC_URI 중 .cfg로 끝나는 것을 모두 모아 커널의 merge_config.sh로 .config에 병합한다. 그 스크립트를 제공하는 게 DEPENDS의 kern-tools-native다. 커널 레시피(linux-yocto)도 같은 방식으로 .cfg 조각을 쓴다(K5).

우리 bbappend가 SRC_URI에 실제로 붙는지 파서로 확인한다.

출력에서 볼 것: 원래 레시피에 .cfg가 12개 있고(Poky가 기본으로 켜는 기능들), bbappend를 붙이면 우리 조각이 맨 뒤에 추가된다. merge_config.sh는 뒤에 오는 조각이 이긴다 — 그래서 bbappend로 붙인 조각이 OE-Core 조각보다 우선한다.

do_configure가 할 병합을 그대로 손으로 해 보자. OE-Core의 busybox defconfig에 우리 조각을 병합한다(merge_config.sh는 랩 커널 소스의 것을 썼다).

출력에서 볼 것: 4개 항목이 "redefined by fragment"로 바뀌었다. TELNETD는 원래 꺼져 있어서 바뀐 게 없다 — 조각에 넣어 둔 이유는 "누가 defconfig에서 켜도 우리 제품에서는 꺼진다"는 의도의 문서화다. -m(merge only)은 make olddefconfig를 돌리지 않으므로 의존성 정리는 do_configure의 다음 단계(oe_runmake oldconfig, cml1.bbclass)가 한다.

10.2 실제로 막히는 지점#

출력에서 볼 것: bitbake -p는 "모든 레시피를 파싱만 하라"는 옵션인데, 빌드든 파싱이든 레시피 처리를 시작하기 전의 sanity 검사에서 멈춘다. 반면 지금까지 쓴 bitbake-layers, bitbake-config-build, bitbake-getvar(설정 변수), tinfoil parse_recipe_file(레시피 하나)은 이 검사를 거치지 않아서 동작했다.

BitBake는 왜 user namespace가 필요한가. 답은 3.5절의 do_fetch[network] = "1"에 있다. BitBake는 do_fetch 말고는 모든 태스크를 네트워크가 없는 상태에서 실행한다. configure 스크립트가 몰래 인터넷에서 뭔가를 받아 빌드 결과가 날마다 달라지는 것을 막기 위해서다(재현성, K5). 이걸 root 권한 없이 하는 방법이 "새 user namespace + 새 network namespace"를 만드는 것이다. 실제 코드를 보자.

출력에서 볼 것: bitbake-worker는 태스크를 fork한 뒤 [network] flag가 없으면 unshare(CLONE_NEWNET | CLONE_NEWUSER)를 하고, 새 user namespace 안에서 자기 uid를 그대로 매핑하려고 /proc/self/uid_map에 쓴다.

이 함수를 직접 불러 보면 어디서 실패하는지 정확히 보인다(BitBake 서버 없이 라이브러리 함수만 호출).

출력에서 볼 것: unshare() 시스템 콜 자체는 성공하고, 그다음 uid_map 쓰기가 EPERM으로 실패한다. util-linux의 unshare 명령도 같은 지점에서 실패한다. sanity.bbclass의 주석이 정확히 이 상황을 설명한다("unshare succeeds (at which point the uid is nobody) but writing to the uid_map fails").

왜 그런가. Ubuntu 24.04부터 AppArmor가 "프로파일이 없는(unconfined) 비특권 프로세스가 user namespace를 만들면 unprivileged_userns 프로파일로 전환"시킨다. 그 프로파일이 이렇다.

출력에서 볼 것: audit deny capability — namespace 안에서 얻었어야 할 capability(CAP_SETUID 등)를 전부 거부한다. uid_map을 쓰려면 그 capability가 필요하므로 실패한다. 커널 쪽 경로는 13절에서 그림으로 본다.

13. 커널 안에서는 무슨 일이 일어나나#

Yocto는 빌드 시스템이라 런타임 커널 코드와 직접 맞닿는 곳이 적다. 하지만 두 군데에서 커널과 연결된다.

13.1 빌드 호스트 커널 — user namespace와 LSM#

10절의 실패는 순수하게 호스트 커널의 결정이다.

그림 9 — BitBake 태스크가 네트워크를 끊으려다 실패하는 커널 경로. 오른쪽은 통과하는 조건이다.

  • unshare(CLONE_NEWUSER)는 커널의 create_user_ns()로 새 struct user_namespace를 만든다. 리눅스 6.1부터 이 지점에 LSM 훅 userns_create가 있어서 보안 모듈이 허용 여부를 정할 수 있다.
  • Ubuntu의 AppArmor는 sysctl kernel.apparmor_restrict_unprivileged_userns가 1이면 unconfined 비특권 프로세스를 unprivileged_userns 프로파일로 전환한다. 그 프로파일은 capability를 거부한다. uid_map 쓰기를 처리하는 map_write()(kernel/user_namespace.c)는 대상 namespace 안의 CAP_SYS_ADMIN을 file_ns_capable()로 확인하므로, 여기서 EPERM이 난다. 랩 커널 소스(6.18.55)에서 create_user_ns()의 security_create_user_ns() 호출(118행)과 lsm_hook_defs.h의 userns_create 훅을 확인할 수 있다. 이 sysctl 자체는 업스트림 AppArmor에는 없고(랩 소스 security/apparmor/에서 grep되지 않는다) Ubuntu 커널 패치다.
  • 이 메커니즘(struct cred, capability, LSM 훅)은 드라이버를 쓸 때도 다시 만난다. ioctl 핸들러에서 capable(CAP_SYS_ADMIN)으로 권한을 확인하는 코드가 바로 같은 capability 체계를 쓴다(F·G 모듈).

14. Embedded 실무에서 다시 보기#

14.1 벤더 BSP 위에 제품 layer를 쌓는 구조#

i.MX8M Plus 기반 센서 키트라면 bblayers.conf는 대략 이렇게 생긴다. (실행하지 않음 — 가이드: layer 이름은 각 벤더 저장소의 이름이고, 실제 브랜치 호환성은 각 layer의 LAYERSERIES_COMPAT로 확인해야 한다)

회사 layer를 셋으로 나누는 게 흔한 구조다: BSP layer(MACHINE conf, 커널·U-Boot bbappend, dts), DISTRO layer(정책, 보안 플래그, DISTRO_FEATURES 정리), 제품 layer(앱 레시피, packagegroup, 이미지). 다음 보드가 나오면 BSP layer만, 다음 제품이 나오면 제품 layer만 바뀐다. 실제 저장소 구성(repo manifest, kas, bitbake-setup 설정 파일)은 K5와 P 모듈에서 다룬다.

14.2 "필드 장비에서 설정 파일이 업데이트로 초기화됐다"#

현장 로봇의 /etc/k4-imu.conf를 기술자가 보정값에 맞게 고쳤는데, 소프트웨어 업데이트 후 원래대로 돌아갔다. 원인 후보는 두 가지다.

  • 패키지 단위 업데이트라면 CONFFILES를 빠뜨렸을 가능성이 높다. 6.1절처럼 표시하면 패키지 관리자가 사용자 수정본을 보존한다.
  • 이미지 단위(A/B) 업데이트라면 rootfs 전체가 바뀌므로 CONFFILES로는 못 막는다. 보정값은 별도 데이터 파티션(/data)에 두고, 레시피의 기본 conf는 "보정값이 없을 때의 기본값"으로만 쓰는 설계가 필요하다(J5, L 모듈).

14.3 "빌드는 되는데 기기에서 Python 스크립트가 안 돈다"#

센서 로깅 스크립트(#!/usr/bin/env python3)를 레시피로 설치했는데 기기에서 python3: not found. do_package는 ELF 바이너리의 공유 라이브러리 의존성은 자동으로 RDEPENDS에 넣지만, 스크립트의 shebang 인터프리터는 넣지 않는다. RDEPENDS:${PN} += "python3-core python3-json"처럼 직접 적어야 한다. do_package_qa의 file-rdeps 검사가 "/usr/bin/env python3를 요구하는데 RDEPENDS에 없다"고 경고해 주므로, QA 경고를 무시하지 않는 습관이 중요하다.

14.4 i2c 도구 하나 넣으려다 전체가 다시 빌드된다#

BusyBox bbappend로 i2c 도구를 켰더니 BusyBox뿐 아니라 이미지까지 다시 만들어진다 — 이건 정상이다(BusyBox의 task hash가 바뀌었고 이미지는 BusyBox 패키지에 의존). 하지만 local.conf에서 DISTRO_FEATURES를 하나 바꿨더니 수백 개 레시피가 다시 빌드된다면, 그 변수가 거의 모든 레시피의 해시에 들어가기 때문이다. 그래서 DISTRO_FEATURES 같은 전역 정책은 프로젝트 초기에 확정하고 자주 바꾸지 않는다. 어떤 변수 때문에 해시가 바뀌었는지는 bitbake-diffsigs로 추적한다(K5).

Q. "What is the difference between Yocto, OpenEmbedded, Poky and BitBake?"

A. BitBake는 태스크 실행 엔진이고, OpenEmbedded-Core는 그 엔진이 읽는 공통 메타데이터(클래스와 레시피)다. Yocto Project는 이 둘을 포함해 릴리스·문서·테스트를 관리하는 우산 프로젝트이고, Poky는 Yocto가 테스트하는 레퍼런스 DISTRO 이름이다. 제품은 보통 OE-Core 위에 벤더 BSP layer와 자기 layer를 쌓고 DISTRO도 자기 것을 만든다. 참고로 6.0부터는 poky라는 합친 저장소 대신 bitbake, openembedded-core, meta-yocto를 따로 받거나 bitbake-setup을 쓴다.

BitBake is the task execution engine — think of it as make for metadata. OpenEmbedded-Core is the common metadata it executes: the classes and about a thousand base recipes such as the toolchain, glibc and BusyBox. The Yocto Project is the umbrella that releases and tests all of this, and Poky is its reference distribution configuration. In a product you usually stack the vendor's BSP layer and your own layers on top of OE-Core and define your own DISTRO rather than shipping Poky. Since 6.0 the combined poky repository is gone; you clone bitbake, openembedded-core and meta-yocto separately or use bitbake-setup.

꼬리 질문: "현재 LTS는?" → Wrynose 6.0(2030-04까지), 이전 LTS는 Scarthgap 5.0(2028-04까지).

Q. "Would you modify a recipe directly or use a bbappend? Why?"

A. 남의 layer에 있는 레시피는 bbappend로 고친다. 원본 layer를 그대로 두어야 업스트림 보안 업데이트를 충돌 없이 받을 수 있고, 우리가 바꾼 것이 우리 layer에 모여 리뷰·추적이 된다. 패치 추가, 설정 파일 교체(FILESEXTRAPATHS), 빌드 옵션, do_install 덧붙이기가 전형적이다. 반대로 우리 레시피는 직접 고치고, bbappend가 원본을 절반 넘게 뒤집거나 버전 자체를 바꿀 때는 우리 layer에 새 레시피를 둔다. 그리고 범용으로 쓸 수정이면 업스트림에 보내는 게 장기적으로 가장 싸다.

If the recipe lives in someone else's layer, I use a bbappend in our layer. That keeps the upstream layer pristine so we can pull security updates without merge conflicts, and every product-specific change lives in one reviewed place. Typical uses are adding a patch, overriding a config file via FILESEXTRAPATHS, tweaking PACKAGECONFIG or appending to do_install. I scope it with an override like :mymachine so adding the layer alone changes nothing. If the bbappend ends up rewriting most of the recipe, or I need a different version, I write our own recipe instead, and if the fix is generic I send it upstream.

꼬리 질문: "bbappend가 여러 개면 순서는?" → layer 우선순위 낮은 것부터 적용, 높은 것이 마지막(BBFILES 정렬). 파일 이름 % 와일드카드로 버전 무관하게 매칭.

Q. "What's the difference between DEPENDS and RDEPENDS?"

A. DEPENDS는 빌드 시점, 레시피 사이의 의존이다. A가 B를 DEPENDS하면 B의 populate_sysroot 결과(헤더·라이브러리)가 A의 recipe-sysroot에 들어오고, A의 configure는 그 뒤에 돈다. RDEPENDS는 실행 시점, 패키지 사이의 의존이다. 패키지 메타데이터에 기록되고 이미지 조립 때 같이 설치된다. 공유 라이브러리 링크 의존은 do_package가 자동으로 RDEPENDS에 넣지만, 스크립트 인터프리터나 dlopen, 외부 명령 호출은 직접 써야 한다. 이름 공간도 다르다 — DEPENDS는 레시피 이름이나 virtual/ 이름, RDEPENDS는 패키지 이름이다.

DEPENDS is build-time and recipe-to-recipe: it makes the other recipe's sysroot output — headers, libraries, native tools — available in my recipe-sysroot before my configure task runs. RDEPENDS is run-time and package-to-package: it goes into the package metadata and pulls the other package into the image. Shared-library dependencies are added to RDEPENDS automatically by the packaging step, but things like a Python interpreter for a script or a binary I exec must be listed by hand. Forgetting DEPENDS fails loudly at compile time thanks to the per-recipe sysroot; forgetting RDEPENDS fails quietly on the device.

꼬리 질문: "virtual/kernel은?" → 레시피가 PROVIDES로 제공을 선언하고 PREFERRED_PROVIDER_virtual/kernel이 고른다. 런타임 버전은 VIRTUAL-RUNTIME_*.

Q. "How do you add a package to an image?"

A. 제품이라면 이미지 레시피의 IMAGE_INSTALL이나, 여러 이미지가 공유하는 packagegroup의 RDEPENDS에 패키지 이름을 넣는다. ssh 서버나 디버그 도구 같은 정형 기능은 IMAGE_FEATURES로 켠다. 개발 중 잠깐 넣을 때만 local.conf에 IMAGE_INSTALL:append = " foo"를 쓰는데, +=는 local.conf가 먼저 파싱되는 탓에 이미지 기본 목록을 덮거나 사라지므로 쓰면 안 된다. 그리고 넣는 이름은 레시피가 아니라 패키지 이름이어야 한다.

For a product I add the package name to IMAGE_INSTALL in our image recipe, or to a packagegroup's RDEPENDS if several images share it. Well-known features like an SSH server or debug tools go through IMAGE_FEATURES. For a quick local experiment I use IMAGE_INSTALL:append with a leading space in local.conf — never += there, because local.conf is parsed before the image recipe, so += either blocks the image's default ?= list or gets overwritten. And it has to be a package name, not necessarily the recipe name; a recipe can produce several packages.

Q. "Explain the difference between =, ?=, :=, += and :append."

A. =는 대입하되 읽을 때 확장(지연), :=는 그 줄에서 바로 확장, ?=는 아직 값이 없을 때만 대입, ??=는 파싱이 다 끝나도 아무도 안 정했을 때만. +=는 그 줄을 읽는 순간 공백과 함께 붙이고, :append는 모든 파싱이 끝난 뒤 공백 없이 붙인다. 그래서 다른 파일이 나중에 =로 덮을 수 있는 곳(local.conf, bbappend)에서는 :append가 안전하다. 실제 값과 각 연산의 출처는 bitbake-getvar의 history로 확인한다.

= assigns with lazy expansion, := expands immediately, ?= sets a default only if nothing is set yet, and ??= is a weak default resolved at the very end of parsing. += appends with a space at the moment that line is parsed, whereas :append is applied after all parsing and does not add a space. So in local.conf or a bbappend, where a later plain assignment could clobber you, :append is the safe choice. When in doubt I run bitbake-getvar, which shows every operation with file and line.

Q. "What is sstate and why are Yocto rebuilds fast?"

A. 태스크마다 입력(함수 본문, 참조 변수, 선행 태스크 해시)으로 해시를 계산한다. populate_sysroot나 package_write 같은 태스크의 결과물은 그 해시 이름으로 sstate 캐시에 저장되고, 다음 빌드에서 해시가 같으면 setscene 태스크가 결과만 풀고 fetch부터 install까지를 건너뛴다. 빌드 디렉터리를 지워도, 다른 머신이어도 된다. 그래서 팀은 sstate와 DL_DIR을 공유하거나 미러를 두고, CI는 거의 항상 sstate를 재사용한다.

Every task gets a signature hash computed from its function body, the variables it references and the hashes of the tasks it depends on. The outputs of key tasks are stored in the shared-state cache under that hash. On the next build, if the hash matches, BitBake runs the setscene variant that just unpacks the cached output and skips fetch through install. This works across clean build directories and across machines, which is why teams share SSTATE_DIR or run an sstate mirror, and why changing a global variable like DISTRO_FEATURES triggers a large rebuild.

꼬리 질문: "해시가 왜 바뀌었는지 어떻게 아나?" → bitbake-diffsigs(K5).

Q. "Why would BitBake fail on a fresh Ubuntu 24.04 machine even with all packages installed?"

A. BitBake는 do_fetch를 뺀 태스크를 네트워크가 없는 namespace에서 돌리려고 비특권 user namespace를 만든다. Ubuntu 24.04부터 AppArmor가 unconfined 비특권 프로세스의 user namespace에서 capability를 빼앗아 uid_map 쓰기가 EPERM으로 실패하고, sanity 검사가 "User namespaces are not usable"로 멈춘다. bitbake에 userns를 허용하는 AppArmor 프로파일을 주거나, 전용 빌드 서버면 sysctl로 제한을 끄거나, 제한이 없는 호스트를 쓴다. Ubuntu 26.04 VM에서 실제로 재현해 봤다.

BitBake runs every task except do_fetch inside a new user and network namespace so builds cannot silently reach the network, which helps reproducibility. Since 24.04, Ubuntu's AppArmor moves unconfined, unprivileged processes that create a user namespace into a restrictive profile that denies capabilities, so writing the uid_map fails with EPERM and BitBake's sanity check stops with "User namespaces are not usable". The fixes are an AppArmor profile that grants userns to bitbake, disabling the sysctl on a dedicated build server, or building on a host without that restriction. I reproduced it on an Ubuntu 26.04 VM.

19. 요약 & 체크리스트#

Yocto는 BitBake(엔진)가 OpenEmbedded-Core와 여러 layer의 메타데이터(conf · class · recipe)를 읽어 태스크 그래프를 만들고, 레시피마다 fetch → unpack → patch → configure → compile → install → package를 실행해 패키지를 만든 뒤, 이미지 레시피가 그 패키지들로 rootfs를 조립하는 시스템이다. 설정은 MACHINE(보드), DISTRO(정책), IMAGE(설치 목록) 세 축으로 나누고, 남의 레시피는 bbappend로 덧씌운다. 변수 문법에서는 +=와 :append의 적용 시점 차이, 그리고 OVERRIDES의 오른쪽 우선 규칙이 핵심이다. 이 노트에서는 Wrynose 6.0 LTS(BitBake 2.18)로 설정 파싱과 레시피 파싱을 실제로 돌려 모든 규칙을 확인했고, 빌드 자체는 Ubuntu 24.04+의 AppArmor user namespace 제한 때문에 시작 단계에서 멈춘다는 것까지 재현했다.
