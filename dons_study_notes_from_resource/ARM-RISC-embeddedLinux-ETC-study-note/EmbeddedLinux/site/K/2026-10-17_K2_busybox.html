0. 큰 그림 — 실행 파일 하나가 유저 공간 전부가 된다#

SSD 펌웨어 디버그 콘솔을 떠올려 보자. UART로 rd 0x4000_0000, nand_erase 12, log dump를 치면, 펌웨어 안의 명령 테이블({"rd", cmd_rd}, {"log", cmd_log}, ...)에서 이름을 찾아 함수 포인터를 호출한다. 명령이 백 개라도 바이너리는 하나다.

BusyBox는 이 구조를 Linux 유저 공간에 그대로 옮긴 것이다. ls, sh, mount, init, mdev, udhcpc, devmem … 400개 가까운 명령(BusyBox 용어로 applet)이 실행 파일 하나 /bin/busybox 안에 들어 있고, /bin/ls, /sbin/init 같은 파일은 전부 그 하나를 가리키는 링크다. 커널이 /sbin/init을 실행하면 사실 busybox가 실행되고, busybox는 "내가 init이라는 이름으로 불렸구나"를 보고 init_main()을 호출한다.

그림 1 — 랩 rootfs의 실제 모습. 링크 402개가 실행 파일 하나를 가리킨다. 커널이 띄우는 PID 1(/sbin/init)도, 그 init이 띄우는 rcS·데몬·셸도 같은 바이너리다.

왜 이렇게 만들까? 세 가지 이유다.

  • 크기: 명령마다 별도 ELF를 만들면 ELF 헤더, C 런타임 시작 코드, libc 정적 링크분, 공통 유틸(옵션 파싱, 에러 출력)이 400번 반복된다. 하나로 합치면 공통 코드(libbb)가 한 번만 들어간다.
  • 메모리: 모든 프로세스가 같은 파일의 코드 페이지를 쓰므로 page cache에 한 벌만 올라간다(A5의 공유 매핑).
  • 단순함: rootfs에 넣을 파일이 "busybox 하나 + 링크 + 설정 파일 몇 개"로 끝난다. initramfs, 복구 이미지, 생산 테스트 이미지에 딱 맞다.

이 노트는 다음 순서로 간다: 멀티콜 디스패치(1절) → Kconfig 설정(2절) → static/dynamic과 libc(3절) → 크기 엔지니어링(4절) → BusyBox init(5절) → mdev(6절) → ash 함정(7절) → 임베디드용 applet(8절) → 최소 이미지와 사이징(9절) → 라이선스와 대안(10절).

실습 환경: Mac의 Lima VM elinux(aarch64, 커널 7.0.0-38-generic, gcc 15.2)에서 BusyBox 1.37.0을 빌드하고, 랩 커널(/var/lab/out/Image, Image-sub = 6.18.55)로 QEMU virt 보드에서 부팅한다. 랩 소스는 /var/tmp/K2/src로 복사해서 썼다.

1. 멀티콜 바이너리 — argv[0]으로 갈라지는 프로그램#

1.1 직관 — 실행 파일 "이름"이 첫 번째 인자다#

C 프로그램의 main(int argc, char **argv)에서 argv[0]은 "프로그램을 부른 이름"이다. 보통은 무시하지만, 셸이 /bin/ls -l을 실행하면 커널 execve()에 argv = {"/bin/ls", "-l", NULL}이 넘어간다. /bin/ls가 busybox를 가리키는 symlink여도 커널은 링크를 따라가 busybox ELF를 로드할 뿐, argv[0]은 호출자가 준 "/bin/ls" 그대로 둔다. 그러니 busybox의 main()은 argv[0]의 basename(ls)만 보면 무엇을 해야 할지 안다.

1.2 랩 rootfs에서 직접 보기#

랩 rootfs의 링크와, symlink로 실행했을 때 execve에 무엇이 넘어가는지 확인한다.

출력에서 볼 것:

  • execve("inst/ls", ["inst/ls", ...]) — 커널은 symlink를 따라 busybox를 실행했지만 argv[0]은 "inst/ls" 그대로다. busybox는 이걸 보고 ls로 동작했다.
  • exec -a cat(bash 기능: argv[0]만 바꿔 실행)만으로 busybox가 cat이 된다. 링크 파일 자체는 필요 없다. 이름이 전부다.
  • 모르는 이름이면 applet not found + 종료 코드 127(셸의 "command not found"와 같은 값).
  • 로그인 셸은 관례상 argv[0] 앞에 -가 붙는다(-sh). busybox는 이것을 떼고 sh를 찾는다. inittab의 -/bin/sh가 바로 이 관례다(5절).
  • --install -s DIR은 /proc/self/exe로 자기 경로를 알아내 DIR에 symlink 402개를 만든다(403 = 링크 402 + busybox 자신).

1.3 40줄로 만드는 멀티콜 바이너리#

같은 패턴을 C로 재현한다. 정렬된 applet 테이블 + bsearch, busybox <applet> 형태, 로그인 셸의 - 처리, 못 찾으면 127까지 BusyBox와 똑같이 했다.

symlink 두 개(hello, add)와 hardlink 한 개(upper)를 만들어 실행한다.

출력에서 볼 것: symlink(add, hello)는 자기 inode가 따로 있고 내용은 경로 문자열(12바이트)뿐이다. hardlink upper는 k2_multicall과 같은 inode 4500299, 링크 수 2다. 어느 쪽이든 실행되는 코드는 같고 갈림은 오직 이름에서 일어난다. cp로 복사해 이름이 바뀌면(nope) 테이블에 없으니 127이다. 경고 0개로 컴파일됐다.

1.4 BusyBox 진짜 코드 — 빌드가 만드는 applet 테이블#

BusyBox는 각 applet 소스 파일 주석의 //applet: 줄(예: //applet:IF_LS(APPLET_NOEXEC(ls, ls, BB_DIR_BIN, BB_SUID_DROP, ls)))을 빌드 때 모아 include/applet_tables.h를 생성한다. 4절의 최소 빌드(applet 19개)에서 만들어진 파일 앞부분이다.

포인트 세 가지:

  • 이름은 NUL로 이어 붙인 문자열 하나("ash\0cat\0dmesg\0...")에 정렬돼 들어 있다. 포인터 배열보다 작다(64비트에서 포인터 하나가 8바이트). 함수 테이블 applet_main[]은 같은 순서다. 내 C 장난감의 struct 배열을 "이름 블롭 + 함수 배열" 두 개로 쪼갠 모양이다.
  • poweroff(12번)와 reboot(14번)가 halt_main을 공유한다. 함수 하나가 applet_name을 보고 동작을 바꾼다 — 멀티콜 안의 멀티콜이다.
  • 디스패치 코드는 libbb/appletlib.c의 main() → run_applet_and_exit() → find_applet_by_name()(정렬된 이름 탐색) → run_applet_no_and_exit()다. main()에는 if (applet_name[0] == '-') applet_name++;와 bb_basename()이 그대로 있다.

마지막 줄은 "busybox를 setuid root로 만들어야 할 수도 있다"는 경고다. su, passwd, ping(raw socket) 같은 applet이 root 권한을 요구하기 때문인데, 바이너리 하나에 setuid를 걸면 모든 applet이 setuid가 된다. 그래서 BusyBox는 CONFIG_FEATURE_SUID로 applet별 정책(BB_SUID_DROP/BB_SUID_MAYBE/BB_SUID_REQUIRE)을 두고, 필요 없는 applet은 시작하자마자 권한을 버린다. 대부분 임베디드 보드는 전부 root로 돌기 때문에 신경 안 쓰지만, 일반 사용자 계정이 있는 제품이면 보안 리뷰 항목이다.

1.6 함정#

  • cp /bin/busybox /bin/myls처럼 이름을 바꿔 복사하면 myls: applet not found. 디버깅할 때 바이너리 이름을 바꾸지 말 것.
  • ps·top에 프로세스 이름이 busybox가 아니라 applet 이름으로 보인다(argv[0]이므로). 반대로 pkill busybox는 아무것도 못 죽인다.
  • /proc이 없는 chroot에서 busybox --install이나 FEATURE_PREFER_APPLETS(2.3절)는 /proc/self/exe를 못 읽어 실패한다.

2.3 NOFORK / NOEXEC / PREFER_APPLETS — 셸이 applet을 부르는 세 가지 방법#

셸 스크립트에서 basename /a/b/c를 부르면 원래는 fork() → 자식에서 execve("/usr/bin/basename") → busybox 시작 → basename_main()이다. BusyBox는 이 비용을 줄이는 두 단계 최적화가 있다.

  • NOEXEC applet(ls, seq 등, 소스 기준 149개): fork()는 하지만 자식이 execve 없이 바로 applet_main[]을 호출한다. 이미 busybox가 메모리에 있으니까.
  • NOFORK applet(basename, echo, true, test, printf, mkdir, kill 등 40개 — 소스의 //applet: 줄 중 APPLET_NOFORK 개수): fork도 안 한다. 셸 프로세스 안에서 함수처럼 호출하고 돌아온다. 그래서 NOFORK applet은 "메모리·fd를 새지 않고, 전역 상태를 바꾸지 않고, 오래 걸리지 않는" 것만 될 수 있다(소스의 NOFORK_NOEXEC.lst가 그 기준을 설명한다: interactive, leaks, longterm, hardware 등은 탈락).

이 둘은 FEATURE_SH_STANDALONE(셸이 PATH보다 applet을 먼저 찾음) + FEATURE_SH_NOFORK + FEATURE_PREFER_APPLETS(exec할 때 /proc/self/exe로 busybox를 다시 실행)를 켜야 동작한다. defconfig에서는 셋 다 꺼져 있다. 켠 빌드와 비교해 clone/execve 횟수를 strace -c로 센다.

출력에서 볼 것: 기본 빌드는 루프 200회 × 명령 2개 = 400번 fork + 400번 exec(+2는 env와 ash 자신). NOFORK 빌드는 basename(NOFORK)이 fork 0회, seq(NOEXEC)가 fork만 200회, exec는 0회다. 시간은 0.07 s → 0.02 s. M2 위 VM에서도 3배이고, QEMU TCG나 저클럭 Cortex-A7 보드에서는 fork+exec 비용이 훨씬 크므로 부팅 스크립트가 무거운 보드에서 의미 있는 최적화다.

그림 3 — 일반 applet, NOEXEC, NOFORK의 실행 경로와 실측 시스템 콜 수.

함정: NOEXEC로 실행된 프로세스는 /proc/<pid>/cmdline이 부모 셸의 것과 다를 수 있고, PREFER_APPLETS로 재실행된 프로세스는 ps에 exe로 보일 수 있다(BusyBox Config 도움말에 적힌 주의). 그래서 pkill sh 같은 이름 기반 관리가 어긋날 수 있다.

3. static vs dynamic, glibc vs musl#

3.1 static으로 빌드하는 이유#

initramfs나 복구 이미지에는 /lib/libc.so.6과 동적 로더 /lib/ld-linux-aarch64.so.1이 없을 때가 많다. 동적 busybox를 넣으면 커널이 init을 실행하는 순간 로더를 못 찾아 "Kernel panic - not syncing: No working init found" 류로 끝난다(C7). 그래서 CONFIG_STATIC=y가 initramfs의 기본이다. 동적 빌드를 확인한다.

동적 busybox 자체는 1.18 MB로 static(2.24 MB)보다 작지만, 이 네 라이브러리를 합치면 2,781,256바이트가 rootfs에 더 필요하다(VM에서 ls -lL로 합산). 이미 같은 libc를 쓰는 앱(센서 데몬, Qt UI)이 rootfs에 있다면 동적이 이득이고, busybox만 있는 initramfs라면 static이 이득이다.

3.2 glibc static의 경고 — NSS#

glibc를 정적으로 링크하면 링커가 이런 경고를 남긴다. BusyBox는 링크 로그를 busybox_unstripped.out에 따로 저장하므로 거기서 찾는다.

뜻: glibc의 이름 조회 함수(DNS getaddrinfo, 사용자 getpwnam 등)는 NSS(Name Service Switch) 로 구현된다. /etc/nsswitch.conf를 읽고 libnss_dns.so, libnss_files.so 같은 플러그인을 실행 중에 dlopen 한다. 정적 바이너리라도 이 순간엔 공유 라이브러리가 필요하고, 그것도 링크할 때와 같은 glibc 버전이어야 한다. initramfs에 그런 파일이 없으면 wget http://host/의 DNS 조회나 ping hostname이 조용히 실패한다(IP 주소는 된다).

getpwnam 경고가 없는 이유는 BusyBox defconfig가 CONFIG_USE_BB_PWD_GRP=y(자체 /etc/passwd·/etc/group 파서, libpwdgrp/)와 USE_BB_SHADOW, USE_BB_CRYPT를 켜서 glibc NSS를 아예 안 쓰기 때문이다. DNS 쪽은 그런 대체가 없다.

3.3 musl로 빌드하기#

musl은 NSS가 없고(DNS는 libc 안에서 직접 /etc/resolv.conf를 읽는다) 정적 링크를 1급으로 지원하는 작은 libc다(B2). VM에 musl-gcc 래퍼가 있다. 단, musl-gcc는 리눅스 커널 헤더(linux/*.h)를 포함 경로에 넣지 않아서 처음엔 init/init.c:134:11: fatal error: linux/vt.h: No such file or directory로 실패했다. VM의 커널 헤더를 가리키는 디렉터리를 만들어 넘기면 된다.

같은 19개 applet이 glibc static 1,193,592 → musl static 329,496바이트. 3.6배 차이이고, 차이는 전부 libc에서 나온다(4.2절). defconfig도 musl로 문제없이 빌드됐다(1,312,536바이트).

3.4 실제로 당한 함정 — make install이 바이너리를 다시 링크한다#

최소 musl 이미지를 만들려고 make -C b_min_musl install CONFIG_PREFIX=...를 CC=musl-gcc 없이 실행했더니, rootfs의 busybox가 1.19 MB가 됐다.

install 타깃은 all에 의존하고, 컴파일러 플래그가 바뀌었다고 판단해 기본 gcc(glibc)로 다시 빌드한 것이다((GNU/Linux) 표시와 크기로 확인). 빌드 때 준 CC=·EXTRA_CFLAGS=를 install에도 똑같이 줘야 한다. Buildroot·Yocto가 이런 변수를 한 곳에서 관리하는 이유다(K3).

4.3 크기 줄이는 순서 (효과 큰 것부터)#

  1. libc를 고른다 — glibc → musl(또는 uClibc-ng). 최소 빌드에서 3.6배.
  2. applet을 고른다 — allnoconfig에서 시작해 필요한 것만. defconfig 대비 musl에서 4배.
  3. FEATURE_*를 끈다 — 셸 편집, 긴 도움말, 유니코드, 긴 옵션.
  4. -Oz/-Os 유지 + strip — 기본값이므로 망치지만 않으면 된다.
  5. (커널이 지원하면) 압축된 initramfs로 넣는다 — 9절에서 musl 최소 rootfs가 gzip -9로 330 KB → 166 KB.

크기만이 아니라 실행 중 메모리도 따라 준다. 같은 init이 glibc static 빌드에서는 VSZ 3280 KB, musl 최소 빌드에서는 468 KB로 보였다(9절 ps 출력).

5. BusyBox init — inittab 하나로 도는 작은 슈퍼바이저#

C7에서 BusyBox init과 respawn·getty를 처음 봤다. 여기서는 액션 8종 전부와 시그널 처리를 한 번에 돌려 보고, init의 생애를 그림으로 정리한다. PID 1의 일반적 책임(좀비 회수, 절대 exit 금지)은 K1·C7 참고.

5.1 inittab 문법#

한 줄 형식은 <id>::<action>:<process>다. SysV init의 id:runlevels:action:process와 모양은 같지만 runlevel 칸은 완전히 무시된다(BusyBox init 도움말에 그렇게 적혀 있다). id 칸은 BusyBox에서 "그 프로세스의 제어 터미널(tty)"이다. 비어 있으면 init 자신의 콘솔(/dev/console)을 물려준다.

센서 키트 보드를 흉내 낸 inittab이다. 모든 액션을 한 번씩 넣었다.

rcS는 가상 FS를 마운트하고, /dev를 비어 있는 tmpfs로 덮은 뒤 mdev로 채우고(6절), syslogd·klogd를 띄운다(8절).

가짜 센서 데몬(3초마다 syslog에 샘플 기록):

rootfs = 내 defconfig static busybox의 make install + 위 파일들 + /etc/passwd·/etc/group(disk:x:6: 포함) + null_blk.ko·softdog.ko와 modules.dep(랩 modules-sub에서 복사). cpio -H newc로 묶은 k2_init.cpio.gz는 1,850,945바이트. 커널은 모듈과 vermagic이 맞는 Image-sub, 인자는 rdinit=/sbin/init(initramfs의 /init 대신 BusyBox init을 PID 1로).

respawn과 SIGHUP:

데몬을 죽이자 init이 PID 83으로 다시 띄웠다. 처음엔 sleep 1로 확인했다가 아직 안 떠서 빈 결과가 나왔는데, syslog를 보면 이유가 있다: init은 process '/usr/bin/k2_sensord' (pid 72) exited. Scheduling for restart.를 남기고 약 1초 뒤 다시 띄운다(아래 logread 출력의 00:47:29 → 00:47:30). init의 메인 루프가 한 바퀴마다 sleep1()(소스 주석: "Don't consume all CPU time - sleep a bit")을 하기 때문이고, 계속 죽는 프로세스가 CPU를 태우지 않게 하는 효과가 있다. inittab에 줄을 추가하고 kill -HUP 1을 보내자 새 respawn 항목(/bin/sleep 1000, PID 89)이 바로 떴다 — 재부팅 없이 inittab 반영.

ctrlaltdel, restart, poweroff:

출력에서 볼 것:

  • kill -INT 1 = 키보드의 Ctrl-Alt-Del과 같다. 커널은 Ctrl-Alt-Del을 받으면 PID 1에게 SIGINT를 보낸다(11절). init은 ctrlaltdel 액션을 실행하고 원래 루프로 돌아갔다.
  • kill -QUIT 1: shutdown 액션 → 모든 프로세스 SIGTERM/SIGKILL → reboot(2) 대신 restart 액션(/sbin/init)을 exec. PID는 1 그대로이고 새 init이 inittab을 처음부터 다시 실행해 rcS가 또 돌았다(uptime 11.99). "커널 재부팅 없이 유저 공간 전체 재시작"이다. 두 번째 rcS의 "/dev before"에 노드가 잔뜩 보이는 건, 첫 부팅의 tmpfs가 아직 마운트돼 있기 때문이다(rcS가 그 위에 또 tmpfs를 덮었고, 그래서 poweroff 때 umount가 두 번 busy를 말한다).
  • poweroff applet은 init에게 SIGUSR2를 보낼 뿐이고, 실제 순서(shutdown 액션 → SIGTERM → SIGKILL → reboot(LINUX_REBOOT_CMD_POWER_OFF))는 init이 진행한다.

5.4 askfirst, getty, 콘솔#

  • askfirst는 tty에 "Please press Enter to activate this console."을 찍고 Enter를 기다린 뒤 셸을 띄운다. 부팅 로그가 셸 프롬프트와 섞이지 않고, 아무도 시리얼에 안 붙어 있으면 셸 프로세스가 아예 안 생긴다. 개발 보드용이다.
  • 제품에서는 보통 ttyAMA0::respawn:/sbin/getty -L 115200 ttyAMA0 vt100(로그인 프롬프트, C7 실습) 또는 콘솔 셸을 아예 없앤다(보안, L 모듈).
  • tty 칸에 ttyAMA0을 적었으므로 init은 /dev/ttyAMA0을 열어 셸에 준다. 이 노드는 rcS의 mdev가 만들었다. mdev가 실패하면 셸이 안 뜬다 — "커널 로그는 다 나왔는데 프롬프트가 안 나온다"의 단골 원인이다. 반대로 tty 칸을 비우면 init이 부팅 때 받은 /dev/console을 그대로 쓴다.
  • /dev/console 자체는 어디서 왔나? /dev before: console이 보여 준다. 커널에 내장된 기본 initramfs(usr/default_cpio_list)에 /dev/console 노드가 들어 있어서, 내 cpio에 /dev가 비어 있어도 PID 1이 stdin/stdout/stderr를 열 수 있었다(K1의 장치 노드 절 참고).

6.5 그 밖의 mdev 기능 (이번엔 실행하지 않음)#

  • 모듈 자동 로드: $MODALIAS=.* root:root 660 @modprobe "$MODALIAS" 한 줄이면 장치가 나타날 때 드라이버 모듈을 로드한다(udev의 기본 동작, G9의 MODULE_DEVICE_TABLE → modalias). mdev --help에 이 예가 그대로 있다.
  • 펌웨어 로딩: FEATURE_MDEV_LOAD_FIRMWARE. 커널이 SUBSYSTEM=firmware 이벤트에 FIRMWARE=<파일명>을 실어 보내면, mdev가 /lib/firmware/<파일명>을 열어 /sys/$DEVPATH/loading에 1 → data에 내용 → loading에 0을 쓴다(mdev.c의 load_firmware()). 다만 이것은 커널의 sysfs fallback 경로이고, 요즘 커널은 request_firmware()가 먼저 /lib/firmware를 커널 안에서 직접 읽는다. 랩 커널도 CONFIG_FW_LOADER_USER_HELPER=y지만 _FALLBACK은 꺼져 있어, 보통 드라이버에서는 이 경로가 쓰이지 않는다. 자세한 흐름은 G10.
  • 순서 보장: /dev/mdev.seq 파일을 만들어 두면 helper 방식에서 SEQNUM 순서대로 처리한다. mdev -d는 이벤트를 소켓에서 순서대로 읽으므로 이 문제가 덜하다.

7. ash 스크립트 함정 — "내 PC에선 되는데 보드에선 안 돼요"#

보드의 /bin/sh는 BusyBox ash(Almquist shell 계열)다. bash가 아니다. 더 큰 함정은 같은 ash라도 BusyBox 설정에 따라 문법이 달라진다는 것이다. 같은 스니펫을 bash와 defconfig ash에 돌렸다.

이제 같은 스니펫 일부를 defconfig ash(ASH_BASH_COMPAT=y)와 allnoconfig 기반 최소 ash(ASH_BASH_COMPAT·ASH_RANDOM_SUPPORT 꺼짐)에 돌린다.

출력에서 볼 것과 규칙:

  • 배열, 연관 배열(declare -A), 중괄호 확장 {1..3}, 대소문자 변환 ${x^^}은 ash에 없다. 빌드 옵션과 무관하게 안 된다.
  • [[ ]], ${s//a/b}, ${s:1:3}, <(...), function 키워드는 BusyBox 빌드 설정에 달렸다. 개발 보드(defconfig)에서 되던 스크립트가 양산 이미지(최소 설정)에서 syntax error로 죽는다. $RANDOM은 에러도 없이 빈 문자열이 된다 — 더 위험하다.
  • 파이프 안의 while read는 bash와 ash 모두 서브셸이라 n=0이다(bash lastpipe 기본 꺼짐). 흔한 오해.
  • local은 POSIX가 아니지만 ash·dash·bash 모두 지원한다. #!/bin/sh 스크립트의 사실상 표준.

실무 규칙: 보드에서 도는 스크립트는 #!/bin/sh + POSIX 문법으로 쓰고, 개발 PC에서 dash -n이나 shellcheck -s sh로 검사한다. bash가 꼭 필요하면 이미지에 bash를 넣고 #!/bin/bash라고 명시한다.

8.1 syslogd·klogd·logread — RAM 링버퍼 로그#

플래시에 로그 파일을 계속 쓰면 마모되고(J4·J5), 전원이 갑자기 꺼지면 파일이 깨진다. 그래서 BusyBox syslogd는 -C[KiB]: SysV 공유메모리 링버퍼에 로그를 담는 모드가 있다. 넘치면 오래된 것부터 덮어쓴다 — 펌웨어의 RAM 로그 링버퍼와 같은 발상이다. logread는 그 버퍼를 읽기만 한다(-f로 tail처럼 따라가기). klogd는 커널 printk 버퍼를 klogctl()(= syslog(2) 시스템 콜)로 읽어 다시 syslog()로 넣는다. 결과적으로 커널 로그와 앱 로그가 한 버퍼에 시간순으로 모인다.

그림 8 — BusyBox 로그 경로. 앱과 klogd 모두 /dev/log 유닉스 소켓으로 syslogd에 보내고, syslogd는 공유메모리 링버퍼에 쓴다.

BusyBox 1.37.0의 버그 하나를 실제로 밟았다. 처음 rcS에 syslogd -C64만 썼더니 logread에 syslogd started 한 줄만 있고 logger 메시지가 하나도 없었다. VM에서 격리된 mount/IPC/PID 네임스페이스로 재현했다.

원인은 sysklogd/syslogd.c에 있다. syslogd_init()은 "원격 로그(-R)가 없으면 로컬에 기록" 비트를 전역 option_mask32에만 켜고(option_mask32 |= OPT_locallog;), 함수가 돌려주는 지역 변수 opts에는 켜지 않는다. 그런데 메인 루프는 if (!ENABLE_FEATURE_REMOTE_LOG || (opts & OPT_locallog))로 지역 변수를 검사한다. 그래서 FEATURE_REMOTE_LOG=y(defconfig 기본) 빌드에서 -L을 명시하지 않으면 받은 메시지를 전부 버린다. strace로 보면 read(0, "<13>Oct 17 ... k2: hello-pl"..., 255) = 35 직후 아무 write도 없이 다시 read로 돌아간다. 내부 메시지("syslogd started")는 다른 함수(timestamp_and_log_internal, 전역 마스크 검사)를 타서 찍히기 때문에 "syslogd는 잘 떴다"처럼 보이는 게 함정이다. 우회는 -L이다(musl 빌드, 동적 빌드 모두 같은 증상을 확인했다). 상위 버전에서 고쳐졌는지는 확인하지 않았다 — 버전을 올릴 때 이 테스트를 다시 돌려 볼 것.

8.2 udhcpc와 default.script#

udhcpc는 DHCP 프로토콜만 처리하고, IP 설정은 스크립트에 맡긴다. 이벤트(deconfig, bound, renew, leasefail, nak)마다 /usr/share/udhcpc/default.script <이벤트>를 실행하고, 받은 값은 환경 변수(ip, subnet, router, dns, lease, interface …)로 준다. BusyBox 소스의 examples/udhcp/simple.script를 simple.script로 넣고, 앞에 값을 찍는 훅을 두었다.

QEMU에 사용자 모드 네트워크(-netdev user,id=n0 -device virtio-net-device,netdev=n0)를 붙이면 QEMU 내장 DHCP 서버(10.0.2.2)가 응답한다.

출력에서 볼 것: deconfig(인터페이스 올리고 주소 비움) → DISCOVER/SELECT → bound(값이 채워져 옴) 순서. -n(못 받으면 실패로 종료), -q(받으면 종료), -t 5(재시도 5번) 조합은 부팅 스크립트용이다. 상시 운용이라면 -q 없이 데몬으로 두어 renew를 처리하게 한다. SIOCDELRT: No such process는 지울 기본 경로가 없다는 무해한 메시지다. default.script가 없거나 실행 권한이 없으면 udhcpc는 lease를 받고도 아무것도 설정하지 않는다 — "DHCP는 됐다는데 IP가 없다"의 원인.

8.3 devmem — 유저 공간에서 레지스터 peek/poke#

devmem ADDRESS [WIDTH [VALUE]]는 /dev/mem을 mmap해 물리 주소를 읽고 쓴다. Don이 JTAG으로 하던 레지스터 peek을 셸에서 하는 도구다. out/virt.dts에서 주소를 찾는다.

PrimeCell 주변장치는 블록 끝(오프셋 0xFE0~0xFFC)에 PeriphID0~3, PCellID0~3 레지스터가 있다. PL011 UART와 PL061 GPIO(pl061@9030000)의 ID, 그리고 UART Flag Register(UARTFR, 오프셋 0x18)를 읽는다.

출력에서 볼 것: PL011의 PeriphID 하위 바이트 0x11, 0x10, 0x14, 0x00 → part number 0x011, designer 0x41(ARM), PCellID 0x0D, 0xF0, 0x05, 0xB1은 모든 PrimeCell 공통 값이다. PL061은 part 0x061. 커널의 AMBA 버스가 장치를 식별할 때 읽는 바로 그 레지스터다(D3, amba_read_periphid — 랩 README의 패닉 메시지에도 나오는 함수). UARTFR=0x0090은 비트 7(TXFE, 송신 FIFO 빔)과 비트 4(RXFE, 수신 FIFO 빔)가 켜진 상태다.

이게 되는 이유는 랩 커널이 CONFIG_STRICT_DEVMEM=y지만 # CONFIG_IO_STRICT_DEVMEM is not set이기 때문이다. STRICT_DEVMEM은 일반 RAM 접근을 막고, IO_STRICT_DEVMEM까지 켜면 드라이버가 이미 잡은 MMIO 영역(여기선 pl011 드라이버가 잡은 UART)도 막는다. 양산 커널에서는 둘 다 켜는 게 보안상 맞고, 그러면 devmem은 bring-up 전용 커널에서만 쓴다. 쓰기(devmem ADDR 32 VALUE)는 드라이버와 경합하므로 bring-up 초기 확인 용도로만 쓴다(H1).

9.2 그럼 이미지에서 진짜 큰 건 무엇인가#

그림 9 — 부팅 이미지 구성 요소 크기. 랩 커널 Image(42,740,224바이트, gzip -9 해도 15.2 MB)에 비하면 BusyBox initramfs는 막대가 거의 안 보인다.

결론:

  • 랩 커널은 arm64 defconfig 기반(수백 개 SoC 드라이버 내장)이라 크다. 최소 이미지를 만들 때 가장 큰 레버는 BusyBox가 아니라 커널 설정이다(E2: 쓰지 않는 SoC·드라이버를 빼고, 필요한 것만 built-in). 이번 노트에서 tinyconfig 커널은 빌드하지 않았으므로 얼마나 줄어드는지 수치는 적지 않는다.
  • K2 initramfs(1.85 MB)에서는 busybox(2.24 MB, 압축 전)보다 /lib/modules의 메타데이터 파일(modules.alias 등 3.7 MB, 압축 전)이 더 컸다. 모듈 2개를 위해 전체 modules.*를 복사했기 때문이다 — 필요한 모듈만 넣고 depmod로 다시 만들면 된다. "작은 것을 줄이기 전에 큰 것을 재라" 는 펌웨어 코드 크기 최적화와 똑같은 원칙이다.
  • 압축은 기본으로 켠다: busybox 2.24 MB → gzip 1.20 MB, musl 최소 330 KB → 166 KB.

11. 커널 안에서는 무슨 일이 일어나나#

BusyBox의 각 기능이 커널의 어디로 이어지는지 정리한다.

  • 멀티콜 디스패치 — execve() → fs/exec.c가 경로를 해석하며 symlink를 따라가 실제 inode(busybox)를 연다 → binfmt_elf가 ELF를 매핑 → 유저 스택에 argv를 호출자가 준 그대로 복사한다. 커널은 argv[0]을 검사하지 않는다. /proc/self/exe는 커널이 기억한 실행 파일(mm->exe_file)을 가리키므로, --install과 PREFER_APPLETS가 링크 이름과 무관하게 busybox 자신을 찾을 수 있다. comm(ps의 이름)은 execve의 파일 이름 basename에서 정해진다(그래서 ls로 보인다).
  • init과 시그널 — PID 1은 커널이 기본 시그널 처리를 하지 않는 특별한 프로세스다(C7). Ctrl-Alt-Del 키는 키보드 드라이버 → ctrl_alt_del()(kernel/reboot.c) → C_A_D가 1이면 커널이 바로 재부팅, 0이면 kill_cad_pid(SIGINT, 1) → BusyBox init의 ctrlaltdel 액션. BusyBox init은 시작할 때 reboot(RB_DISABLE_CAD)로 이 값을 0으로 만들어 두므로 SIGINT를 받는다. /proc/sys/kernel/ctrl-alt-del이 이 C_A_D 값이다. poweroff는 최종적으로 reboot(LINUX_REBOOT_CMD_POWER_OFF) 시스템 콜 → kernel_power_off() → PSCI SYSTEM_OFF(arm64, C5) → QEMU 종료.
  • mdev — device_add() → kobject_uevent(KOBJ_ADD) → kobject_uevent_env()가 환경 변수 버퍼를 만들고 kobject_uevent_net_broadcast()로 NETLINK_KOBJECT_UEVENT 소켓에 브로드캐스트(+ CONFIG_UEVENT_HELPER가 켜져 있고 uevent_helper[0]이 비어 있지 않으면 call_usermodehelper). mdev -d는 이 netlink 그룹 1에 bind한 소켓이다. 장치 노드의 major/minor는 드라이버가 register_chrdev_region/alloc_chrdev_region(G4) 또는 블록 계층에서 받은 값이 MAJOR=, MINOR=로 실려 온다. 드라이버를 쓸 때 device_create()(char) 한 줄이 바로 이 uevent를 만드는 지점이다 — 이걸 빼먹으면 "모듈은 로드됐는데 /dev에 노드가 없다".
  • syslogd/klogd — /dev/log는 AF_UNIX SOCK_DGRAM 소켓. 커널 로그는 printk 링버퍼(kernel/printk/)에 쌓이고, klogd는 syslog(2)(glibc 이름은 klogctl)의 SYSLOG_ACTION_READ로 읽는다. dmesg는 /dev/kmsg 또는 같은 syscall로 버퍼를 통째로 읽는다(M1).
  • devmem — /dev/mem의 mmap_mem()(drivers/char/mem.c)이 range_is_allowed() → devmem_is_allowed()로 STRICT_DEVMEM 정책을 검사한 뒤 remap_pfn_range()로 물리 페이지를 유저 공간에 매핑한다. 드라이버의 .mmap 구현(G5)과 같은 함수다.
  • watchdog — /dev/watchdog은 drivers/watchdog/watchdog_dev.c의 misc 장치. write() = 킥, 'V' 쓰기 = 다음 close에서 멈춤 허용, release()에서 그게 없으면 watchdog did not stop!. 하드웨어 드라이버는 struct watchdog_ops의 .start/.stop/.ping/.set_timeout만 구현하면 된다(I9).

14. 면접에서 이렇게 말한다#

Q. How can BusyBox provide hundreds of commands in a single binary?

A. 실행 파일 하나 안에 applet마다 xxx_main() 함수가 있고, 정렬된 이름 테이블과 함수 포인터 테이블이 빌드 때 생성된다. /bin/ls 같은 파일은 busybox를 가리키는 링크이고, 커널은 execve에서 argv[0]을 호출자가 준 그대로 넘기므로 main()이 그 basename을 테이블에서 찾아 해당 함수를 호출한다. 공통 코드가 한 번만 들어가서 작고, 코드 페이지를 모든 프로세스가 공유한다.

BusyBox is a multi-call binary: every applet is just a foo_main() function, and the build generates a sorted name table plus a matching function-pointer table. /bin/ls is only a symlink to busybox; the kernel passes argv[0] through unchanged, so busybox's main() takes the basename, looks it up in the table and calls ls_main(). You can also run busybox ls directly. Shared helpers and the C library are linked once, which is why the whole userland fits in about 1–2 MB, and every process shares the same code pages.

꼬리 질문: "symlink와 hardlink 중 뭘 쓰나?" → 기본은 symlink(보이고 FS 무관), hardlink는 inode 하나지만 같은 FS 안에서만. "NOFORK applet이란?" → 셸이 fork 없이 같은 프로세스에서 호출하는 applet, 측정상 fork/exec가 사라진다.

Q. Walk me through what BusyBox init does from boot to shutdown.

A. /etc/inittab을 읽고 액션 종류 순서로 실행한다: sysinit(rcS, 끝까지 대기) → wait → once → respawn·askfirst를 띄우고 감시 루프. 자식이 죽으면 respawn 항목은 1초 정도 뒤 다시 띄운다. SIGHUP이면 inittab을 다시 읽고, SIGINT(Ctrl-Alt-Del)면 ctrlaltdel 액션, SIGUSR1/USR2/TERM이면 shutdown 액션 → 전 프로세스 SIGTERM·SIGKILL → reboot(2), SIGQUIT이면 같은 정리 후 restart 액션을 exec한다. runlevel은 무시한다.

BusyBox init parses /etc/inittab and runs actions by type, not by line order: sysinit entries such as rcS run to completion first, then wait, then once, then it starts respawn and askfirst entries and supervises them, restarting them about a second after they die. Signals drive the rest: SIGHUP rereads inittab, SIGINT from Ctrl-Alt-Del runs ctrlaltdel actions, SIGUSR1, SIGUSR2 and SIGTERM mean halt, poweroff and reboot — shutdown actions run, everything gets SIGTERM then SIGKILL, then it calls reboot(2). SIGQUIT does the same cleanup but execs the restart action instead, so you restart userspace without a kernel reboot. Runlevels are ignored.

꼬리 질문: "daemon이 죽었는데 init이 안 살린다, 왜?" → rcS에서 띄워 데몬화(고아 → PID 1 입양)됐기 때문. respawn은 inittab 항목만 감시한다.

Q. Without udev, how do device nodes appear under /dev?

A. 바닥은 devtmpfs로, 커널이 드라이버 등록 때 직접 노드를 만든다. 규칙(소유자·권한·이름·symlink·스크립트)이 필요하면 BusyBox mdev를 쓴다. 부팅 때 mdev -s로 /sys/dev를 훑어 기존 장치를 만들고, 핫플러그는 커널 uevent를 받아 처리한다. 예전엔 /proc/sys/kernel/hotplug에 mdev를 등록했지만 최근 커널은 CONFIG_UEVENT_HELPER가 꺼진 경우가 많아 netlink를 듣는 mdev -d를 쓴다. 실제로 랩 커널에서 hotplug 파일이 없어서 mdev -d로 null_blk 장치를 /dev/k2/sensor_disk0 + symlink로 만들었다.

The baseline is devtmpfs: the kernel itself creates a node when a driver registers a device. When you need policy — owner, mode, a stable name, a symlink, or a script — BusyBox mdev does it from /etc/mdev.conf regex rules. At boot mdev -s walks /sys/dev for devices that already exist; for hotplug, mdev consumes kernel uevents. The old way was registering it as the uevent helper in /proc/sys/kernel/hotplug, but many current kernels build without CONFIG_UEVENT_HELPER, so you run mdev -d, which listens on the uevent netlink socket. On my QEMU board the hotplug file didn't even exist, and mdev -d created the null_blk disks with a renamed node, a compatibility symlink and a hook script.

Q. Why would you link BusyBox statically, and what are the pitfalls?

A. initramfs나 복구 이미지에 공유 라이브러리를 안 넣어도 되고, 다른 앱과 libc 버전이 엮이지 않는다. 함정은 glibc static이 NSS(DNS·사용자 조회)를 위해 실행 중에 공유 라이브러리를 dlopen한다는 점 — 링커 경고가 그걸 말한다. 크기도 glibc가 대부분이다. 최소 빌드 측정에서 glibc static 1.19 MB 중 libc가 약 87%였고, musl로 바꾸니 329 KB가 됐다.

Static linking means the initramfs or recovery image needs no shared libraries and isn't tied to the libc version of other apps. The catch with glibc is NSS: getaddrinfo and friends still dlopen NSS modules at run time, which is exactly what the "statically linked applications requires at runtime the shared libraries" warnings mean, so DNS can silently fail. Size is the other issue — in my measurement a 19-applet glibc static build was 1.19 MB and about 87 percent of it was libc; the same config with musl was 329 KB.

Q. How do you make a minimal root filesystem as small as possible?

A. 먼저 잰다. 이미지 전체에서는 보통 커널이 가장 크다(랩 defconfig 커널 gzip 15 MB vs BusyBox initramfs 0.17~1.2 MB). 유저 공간에서는 libc 선택 → allnoconfig에서 필요한 applet만 → FEATURE 옵션 정리 → -Os와 strip → 압축 initramfs 순서로 효과가 크다. 링커 map으로 출처를 나눠 보면 어디를 줄일지 보인다.

Measure first. In the whole image the kernel usually dominates — in my lab the defconfig kernel was 15 MB gzipped while the BusyBox initramfs was 0.17 to 1.2 MB — so kernel config is the biggest lever. For userspace the order is: pick the libc (musl gave 3.6x), start from allnoconfig and enable only the applets the scripts actually call, trim FEATURE options like line editing and verbose help, keep -Os and strip, and ship a compressed initramfs. I attribute bytes with the linker map file so I'm not guessing where the size comes from.

Q. Your boot script works on the dev board but fails on the production image with a syntax error. What happened?

A. 보드의 /bin/sh는 BusyBox ash이고, [[ ]], ${var//a/b}, ${var:1:3}, function 같은 bash 확장은 ASH_BASH_COMPAT 설정에 달려 있다. 개발 이미지는 defconfig라 켜져 있고 양산 이미지는 최소 설정이라 꺼졌을 가능성이 크다. 배열·{1..3}은 어느 쪽에서도 안 된다. POSIX sh로 고치고 shellcheck -s sh를 CI에 넣는다.

The board's /bin/sh is BusyBox ash, and bash-isms like [[ ]], ${var//a/b}, substring expansion and the function keyword only work if ASH_BASH_COMPAT was enabled. Dev images often use defconfig, production uses a trimmed config, so the same script breaks — I reproduced exactly that: [[: not found and bad substitution on the minimal build, and $RANDOM silently empty. Arrays and brace ranges never work in ash. The fix is to write POSIX sh and run shellcheck -s sh in CI.

Q. How does a userspace watchdog daemon interact with the kernel watchdog driver?

A. 데몬이 /dev/watchdog을 열면 타이머가 시작되고, write나 WDIOC_KEEPALIVE로 주기적으로 킥한다. 정상 종료할 땐 'V'를 쓰고 닫아(magic close) 타이머를 멈춘다. 데몬이 행이나 SIGKILL로 죽으면 magic close가 없으니 타이머가 만료돼 리셋된다. 실험에서 softdog 5초 설정, SIGTERM은 살아남고 SIGKILL은 약 6초 뒤 리셋됐다. 양산은 NOWAYOUT으로 끌 수 없게 하고, 앱 건강 상태를 확인한 뒤에만 킥한다.

Opening /dev/watchdog arms the timer; the daemon pets it with write() or WDIOC_KEEPALIVE. On a clean exit it writes the magic character 'V' before closing so the driver may stop the timer. If the daemon hangs or gets SIGKILLed there's no magic close and the board resets. I tested it with softdog and a 5 second timeout: SIGTERM left the system up, SIGKILL logged "watchdog did not stop!" and the VM reset about six seconds later. In production you set NOWAYOUT and only pet after checking the application's health, otherwise the watchdog just proves the daemon is alive, not the system.

15. 직접 해보기#

  1. (개념) ln /bin/busybox /tmp/sh2로 hardlink를 만들고 /tmp/sh2 -c 'echo hi'를 실행하면 어떻게 되나? cp로 복사하면? 이유를 argv[0]으로 설명하라. 정답/힌트: hardlink든 복사든 이름이 sh2라 applet not found(127). 이름이 sh면 된다. inode는 무관하다.
  2. (코드) 1.3절 장난감에 --install DIR 옵션을 추가해, /proc/self/exe를 readlink로 읽어 DIR에 applet 이름별 symlink를 만들게 하라. 정답/힌트: readlink("/proc/self/exe", buf, sizeof buf - 1) 후 symlink(buf, path). 이미 있으면 EEXIST 처리.
  3. (빌드) 4절의 allnoconfig 스크립트에 FEATURE_EDITING과 ASH_BASH_COMPAT만 추가로 켜서 musl 빌드 크기가 얼마나 늘어나는지 재라. 결과를 표에 한 줄 추가하라. 정답/힌트: build_min.sh의 for o in 목록에 두 이름 추가, stat -c %s. 늘어난 바이트는 mapsum.py의 busybox:shell과 busybox:libbb에서 보인다.
  4. (init) inittab의 ttyAMA0::askfirst:-/bin/sh를 ttyAMA0::respawn:/sbin/getty -L 115200 ttyAMA0 vt100으로 바꾸고 /etc/passwd의 root 비밀번호 칸을 비운 채 로그인해 보라. 셸에서 exit하면 무엇이 다시 뜨나? 정답/힌트: getty가 respawn되어 다시 login:. C7 2.2절에 같은 실험 출력이 있다.
  5. (mdev) mdev.conf에 $MODALIAS=.* root:root 660 @modprobe "$MODALIAS" 규칙을 넣고, null_blk를 수동 로드하지 않고도 자동 로드되는 장치가 있는지 logread로 관찰하라. 왜 null_blk는 자동 로드되지 않나? 정답/힌트: null_blk는 HW 장치가 없는 가상 드라이버라 MODALIAS를 가진 장치 이벤트가 먼저 오지 않는다. virtio-net 같은 버스 장치가 대상이다(G9).
  6. (관찰) 8.1절 버그를 확인하라: rcS의 syslogd -C64 -L에서 -L을 빼고 부팅해 logread를 보고, strace -f -e trace=read,write로 syslogd가 메시지를 읽고 버리는 것을 VM 네임스페이스에서 확인하라. 정답/힌트: read(0, "<13>...") 다음에 write가 없다. syslogd.c의 syslogd_init() 반환값과 메인 루프의 opts & OPT_locallog를 비교.
  7. (사이징) /lib/modules/6.18.55-sub에서 null_blk.ko·softdog.ko만 남기고 VM의 depmod -b <rootfs> 6.18.55-sub로 modules.dep를 다시 만들어 K2 initramfs 크기를 다시 재라. 정답/힌트: modules.alias 등이 수 KB로 줄어 initramfs가 BusyBox 크기 수준(약 1.2 MB 압축)으로 내려가야 한다.

17. 요약 & 체크리스트#

BusyBox는 argv[0]으로 갈라지는 멀티콜 바이너리 하나로 최소 Linux 유저 공간 전체(init·셸·코어 유틸·mdev·네트워크·로그 도구)를 제공한다. Kconfig로 applet과 기능을 고르고, static/dynamic과 libc 선택이 크기를 좌우한다 — 측정상 최소 빌드에서 glibc가 약 87%를 차지했고 musl로 바꾸면 329 KB가 됐다. BusyBox init은 inittab의 액션 종류 순서(sysinit → wait → once → respawn/askfirst)로 실행하고 시그널(HUP·INT·QUIT·USR1·USR2·TERM)로 재설정·종료한다. mdev는 mdev.conf 규칙으로 /dev를 만들며, CONFIG_UEVENT_HELPER가 꺼진 최근 커널에서는 mdev -d가 정답이다. 보드의 셸은 ash이고 bash 확장은 빌드 설정에 따라 달라진다. syslogd 링버퍼·udhcpc·devmem·watchdog은 임베디드에서 매일 쓰는 도구이고, 1.37.0의 syslogd는 -L 없이는 메시지를 버린다. 이미지 전체에서는 커널이 BusyBox보다 훨씬 크므로, 줄이기 전에 먼저 잰다.
