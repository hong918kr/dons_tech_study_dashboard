0. 큰 그림 — 이게 왜 필요한가#

0.1 이 노트의 실행 원칙 (먼저 읽기)#

Don의 요청으로 이 노트에서는 Yocto 빌드를 한 번도 돌리지 않는다. 이유는 두 가지다.

  1. 시간·디스크 — 이미지 한 번에 수 시간, 수십~백 GB 단위가 든다. 나중에 별도로 한다.
  2. 이 VM(Ubuntu 26.04)은 AppArmor가 비특권 user namespace를 막는다. BitBake는 태스크 격리에 user namespace를 쓰므로 여기서 돌지 않는다. 이 설정은 바꾸지 않는다.

그래서 이 노트의 블록은 두 종류다.

  • 실행한 예제: 실제 Yocto 소스(openembedded-core, bitbake, meta-yocto, meta-freescale, yocto-kernel-cache)를 얕게 clone해서 grep/sed로 읽은 결과, 그리고 BitBake 없이도 검증되는 산출물(DT 패치, config fragment 병합, 모듈 빌드·QEMU insmod, kas checkout/lock, 재현성 실험). 출력은 VM(uname -r = 7.0.0-38-generic, aarch64)에서 나온 그대로다.
  • "실행하지 않음 — 가이드": bitbake, devtool, SDK 설치처럼 BitBake가 필요한 명령. 정확한 명령과 무엇을 확인해야 하는지만 적고 출력은 쓰지 않는다 (지어낸 출력 금지).

poky 저장소와 openembedded-core 저장소의 브랜치·태그를 비교하는 명령이다.

출력에서 볼 것: poky에는 walnascar(5.2)까지만 릴리스 브랜치가 있고 whinlatter(5.3)와 wrynose(6.0) 브랜치가 없다. 반면 openembedded-core에는 yocto-6.0.3 태그가 있다. yoctoproject.org 릴리스 페이지도 Wrynose 6.0 = 현재 LTS(2026년 4월 출시, 최신 6.0.3 = 2026년 8월, 2030년 4월까지 지원), Scarthgap 5.0 = 이전 LTS(5.0.20, 2028년 4월까지)라고 적고 있다. docs.yoctoproject.org의 Quick Start(6.0)는 poky clone 대신 bitbake-setup init 으로 시작한다.

1. 여러 저장소를 묶는 법 — kas, repo, SRCREV 고정#

1.1 문제: "내 PC에선 되는데"#

Yocto 빌드에는 최소 4~6개 git 저장소가 필요하다. 각자 git clone하고 bitbake-layers add-layer를 손으로 하면, 사람마다 다른 커밋·다른 layer 순서·다른 local.conf가 된다. 이를 막는 도구가 셋 있다.

도구누가 쓰나정의 파일커밋 고정
kas (Siemens, 현재 5.x)많은 회사의 새 프로젝트, CIYAML (repos, machine, distro, local_conf_header)commit: 또는 kas lock이 만든 .lock.yml
repo (Google, Android에서 옴)NXP i.MX 릴리스, 오래된 BSPdefault.xml 매니페스트revision="<sha>"
bitbake-setup (Yocto 6.0부터 공식)Yocto 문서·레퍼런스JSON 레지스트리"rev" 필드

kas는 "저장소 받기 + bblayers.conf·local.conf 생성 + bitbake 실행(또는 shell)"을 한 파일로 끝낸다. repo는 저장소만 받는다(설정은 벤더가 주는 setup-environment 같은 스크립트가 만든다). 회사에서 무엇을 쓰든 원리는 같다: 저장소 목록 + 커밋 해시를 git에 넣어 둔다.

1.2 kas 프로젝트 파일 (실제로 만들고 검증함)#

/var/tmp/K5/k5-platform/에 회사 저장소를 흉내 낸 git 저장소를 만들었다. kas 파일은 다음과 같다.

읽는 법: url이 없는 k5-platform은 "이 kas 파일이 들어 있는 저장소 자신"이다. bitbake 저장소는 받기만 하고 layer로는 쓰지 않는다(.: disabled). layers:를 생략한 meta-freescale은 저장소 루트가 곧 layer다. ACCEPT_FSL_EULA는 NXP 바이너리 펌웨어 EULA 동의로, meta-freescale을 쓰면 반드시 마주친다.

kas는 VM 안 전용 venv에 pip install kas로 설치했다 (kas 5.5, configuration format version 23). kas checkout은 저장소를 받고 빌드 디렉터리 설정 파일만 만든다 — bitbake는 실행하지 않는다.

출력에서 볼 것: 브랜치 이름(wrynose)이 그 순간의 커밋으로 풀렸다. openembedded-core의 wrynose 브랜치 끝(636e5d3b)은 이미 6.0.3 태그(ef022bf8)보다 앞서 있다 — 브랜치만 적어 두면 다음 주에는 다른 코드를 받는다는 뜻이다. 생성된 local.conf에는 local_conf_header 블록과 MACHINE ??= "k5-sensorkit", DISTRO ??= "k5os"가 들어갔다.

1.3 kas lock — 브랜치를 커밋으로 박제#

출력에서 볼 것: lock 파일은 원래 YAML 옆에 놓이고, kas는 다음 실행부터 이 파일을 자동으로 겹쳐 읽는다. 이 파일을 커밋하면 "릴리스 v1.4 = 이 해시 다섯 개"가 된다. 벤더 layer를 올리는 일 = lock 파일을 갱신하는 PR이 된다 (리뷰어는 diff에서 바뀐 해시를 본다).

CI는 같은 프로젝트에 캐시 설정만 얹는다. kas는 YAML을 :로 이어 붙이거나 includes로 겹친다.

실행하지 않음 — 가이드: 실제 빌드 명령. 이 VM에서는 BitBake가 돌지 않는다.

1.4 repo 매니페스트와 레시피 안의 SRCREV#

NXP 같은 벤더는 BSP를 repo 매니페스트로 배포한다. 원리는 같다.

layer 커밋을 고정해도 끝이 아니다. 레시피 안에서도 소스 커밋이 고정돼야 한다. vendor 커널 레시피를 보면 그렇게 돼 있다.

출력에서 볼 것: branch=는 "이 커밋이 어느 브랜치에 있는지 확인용"이고, 실제로 받는 것은 SRCREV 해시다. 회사 레시피에서 SRCREV = "${AUTOREV}"(항상 최신)를 쓰면 빌드가 매번 네트워크에 묻고, 재현성과 sstate 재사용이 깨진다. 개발 중 잠깐만 쓰고 릴리스 브랜치에는 금지하는 것이 보통이다.

2. BSP layer 해부 — 가상의 보드 k5-sensorkit 만들기#

2.1 vendor machine conf 읽기#

새 보드는 거의 항상 벤더 평가 보드(EVK)에서 출발한다. 센서 키트 캐리어 보드가 i.MX8M Plus SoM을 쓴다면, meta-freescale의 imx8mp-lpddr4-evk.conf가 출발점이다.

진짜 정보는 require로 끌어오는 include에 있다. 커널·부트로더를 누가 제공하는지(PREFERRED_PROVIDER)는 imx-base.inc가 정한다.

출력에서 볼 것 세 가지.

  1. virtual/kernel은 이름표다. 실제 레시피는 PREFERRED_PROVIDER_virtual/kernel이 고른다. 여기서 IMX_DEFAULT_BSP = "nxp"이면 linux-fslc-imx(NXP 커널 + 커뮤니티 stable 패치), mainline이면 linux-fslc다. 커널 bbappend를 만들기 전에 어느 레시피가 실제로 선택되는지 먼저 확인해야 한다 (6.4절의 bitbake-getvar).
  2. ??=(가장 약한 기본값)로 써 있으므로 회사 machine conf가 =로 덮을 수 있다.
  3. i.MX는 UBOOT_MACHINE을 직접 쓰지 않고 UBOOT_CONFIG 플래그를 쓴다. uboot-config.bbclass가 UBOOT_CONFIG = "sd" → UBOOT_CONFIG[sd]의 defconfig 이름 → 내부 UBOOT_MACHINE으로 바꾼다. 다른 BSP(예: TI, Raspberry Pi)는 UBOOT_MACHINE = "xxx_defconfig" 한 줄로 쓴다.

같은 정보가 다른 벤더에도 있다: meta-ti는 conf/machine/am62xx-evm.conf 계열, meta-tegra는 conf/machine/jetson-orin-*.conf에서 KERNEL_DEVICETREE, PREFERRED_PROVIDER_virtual/kernel(linux-jammy-nvidia-tegra 등 브랜치마다 다름)을 정한다. 이름은 달라도 읽는 순서는 같다: machine conf → require된 inc → PREFERRED_PROVIDER → 그 레시피.

2.2 회사 BSP layer의 파일 구성#

이 노트를 위해 만든 layer다 (/var/tmp/K5/k5-platform/, 사본 ~/.elinux_scratch/K5/k5-platform/).

layer.conf의 핵심은 우선순위와 호환 선언이다.

LAYERDEPENDS의 이름은 상대 layer의 BBFILE_COLLECTIONS 값이다. meta-freescale은 freescale-layer이고, 그쪽도 LAYERSERIES_COMPAT_freescale-layer = "whinlatter wrynose"로 선언돼 있다 (clone한 conf/layer.conf에서 확인).

2.3 machine conf — EVK에서 파생#

설계 판단을 적어 둔다.

  • 파일 이름이 곧 MACHINE 이름이고, MACHINE 이름은 자동으로 override가 된다. 그래서 bbappend에서 SRC_URI:append:k5-sensorkit라고 쓰면 이 보드에서만 적용된다. EVK 빌드에는 영향이 없다.
  • imx8mp-evk.inc가 UBOOT_DTB_NAME = "${KERNEL_DEVICETREE_BASENAME}.dtb"로 정해 두었기 때문에, 커널 DTB 이름을 바꾸면 U-Boot도 그 이름을 찾는다. U-Boot 보드 포팅을 아직 안 했으므로 require 뒤에서 imx8mp-evk.dtb로 되돌렸다. 이런 "include가 만든 연쇄 효과"를 놓치는 것이 BSP 작업의 흔한 실수다.
  • DDR 훈련 펌웨어는 같은 DDR 부품일 때만 그대로 쓸 수 있다. DDR이 다르면 NXP의 DDR tool로 타이밍을 다시 뽑아 U-Boot SPL의 lpddr4_timing.c를 바꿔야 한다 — Don이 SSD에서 DRAM 트레이닝 파라미터를 다룬 것과 같은 일이다.

3. 커널 레시피 실무 — linux-yocto vs vendor 커널, defconfig vs fragment#

3.1 두 종류의 커널 레시피#

중요한 사실 하나: vendor 커널도 대부분 kernel-yocto 클래스를 상속한다. meta-freescale의 linux-imx.inc가 그렇다.

출력에서 볼 것: 그래서 linux-yocto의 fragment 방식(.cfg → merge_config.sh)이 vendor 커널에도 그대로 통한다. NXP는 자기만의 옛 방식(DELTA_KERNEL_DEFCONFIG)을 아예 에러로 막고 "kernel-yocto의 configuration fragment를 써라"라고 안내한다.

linux-yocto 쪽은 이렇게 생겼다.

출력에서 볼 것: SRC_URI에 저장소가 두 개다 — 커널 소스(name=machine)와 yocto-kernel-cache(type=kmeta, 설정 메타데이터). 각각 SRCREV_machine, SRCREV_meta로 고정된다.

3.2 .scc와 .cfg — 설정을 기능 단위로 쪼개기#

KERNEL_FEATURES에 적는 features/netfilter/netfilter.scc가 실제로 무엇인지 kernel-cache에서 본다.

정리하면:

  • .cfg = Kconfig 조각. 그냥 CONFIG_X=y 몇 줄이다.
  • .scc (Series Configuration Control) = "이 기능에는 이 .cfg와 이 패치들이 필요하다"를 묶은 목록. kconf hardware|non-hardware <cfg>, patch <file>, include <다른 scc>.
  • hardware/non-hardware 분류는 나중에 kernel_configcheck가 "부팅에 중요한 설정이 빠졌나"를 판정할 때 쓴다.
  • kernel-cache에는 bsp/nxp-imx9, bsp/nvidia-orin처럼 BSP별 .scc도 있다 — linux-yocto로 그 보드를 돌릴 때 쓰는 것이다.

회사 layer에서는 보통 .scc까지 만들지 않고 .cfg를 SRC_URI에 바로 넣는다. kernel-yocto가 SRC_URI의 .cfg 파일을 찾아 자동으로 설정 큐에 올린다. 기능이 많아지면 .scc로 묶어 KERNEL_FEATURES에 넣는다.

3.3 커널 레시피의 태스크 파이프라인#

3.6 커널 bbappend와 config fragment#

4. devtool — 드라이버 개발의 일상 루프#

4.1 왜 devtool인가#

레시피를 고칠 때마다 패치 파일을 만들고 SRC_URI에 넣고 bitbake를 돌리는 것은 느리다. devtool은 레시피 소스를 내 손 안의 git 트리로 꺼내 주고, 그 트리에서 고친 것을 그대로 빌드하게 해 주고(externalsrc), 끝나면 커밋들을 패치로 바꿔 layer에 넣어 준다. 3.5절에서 손으로 한 "SRCREV 기준 패치 만들기"를 자동으로 해 준다.

devtool 하위 명령 목록을 소스에서 뽑았다 (oe-core scripts/lib/devtool/).

(도움말이 비어 있는 것은 help 문자열이 다음 줄에 있어서 이 grep에 안 잡힌 것이다.) devtool modify가 workspace에 만드는 bbappend의 내용도 소스에 그대로 있다.

출력에서 볼 것: 비밀은 inherit externalsrc + EXTERNALSRC 한 쌍이다. "fetch/unpack/patch를 건너뛰고 이 폴더를 소스로 써라." 커널 레시피라면 소스 트리에 남은 .config를 치워 configme와 충돌하지 않게 한다.

4.2 루프#

그림 3 — devtool 루프. 안쪽 사각형(modify → 편집 → build → deploy → 시험)이 하루에 수십 번 도는 루프이고, 바깥 줄(finish → layer → PR)은 기능 하나가 끝날 때 한 번 돈다.

실행하지 않음 — 가이드: IMU 드라이버를 vendor 커널에서 고치는 하루. 출력은 적지 않는다.

확인 포인트와 함정:

  • deploy-target은 do_install이 설치한 파일을 그대로 보드에 tar로 푼다(deploy.py의 tar cf - . | ssh ...). 커널 Image나 DTB를 부트 파티션에 써 주지는 않는다. 커널 본체를 바꿨다면 deploy/images/<machine>/의 Image/DTB를 직접 복사하거나 tftp/NFS 부팅을 쓴다. 모듈(.ko)만 고칠 때 가장 빠르다.
  • 옵션은 소스에 있다: -n/--dry-run(무엇을 보낼지만 출력), -s(진행 표시), -P 포트, -I 키, -S/--strip. 처음엔 -n으로 보내는 파일 목록부터 본다.
  • finish/update-recipe는 커밋된 것만 패치로 만든다 (도움말: "changes need to have been committed"). 커밋 안 한 수정은 조용히 빠진다. --mode patch|srcrev|auto — 우리 소유의 git 저장소(예: 사내 앱)라면 srcrev 모드로 SRCREV만 갱신한다.
  • finish의 대상 layer를 회사 BSP layer로 지정하면 vendor 레시피 자체가 아니라 우리 layer에 bbappend를 만든다. vendor layer 경로를 주면 남의 저장소를 고치게 된다.
  • 새 소프트웨어(사내 센서 데몬 등)는 devtool add k5-sensord https://git.k5.example/sensord.git로 레시피 초안부터 만든다. 라이선스 체크섬·의존성은 생성된 레시피를 반드시 다시 읽고 고친다.

6.1 실패한 태스크의 로그부터#

BitBake 에러는 항상 ERROR: <recipe>-<ver> do_<task>: ... Logfile of failure stored in: <WORKDIR>/temp/log.do_<task>.<pid>로 끝난다. 그 WORKDIR/temp/ 폴더가 디버깅의 출발점이다.

파일내용
log.do_compile (심볼릭 링크 → 최신 실행)그 태스크의 전체 출력
run.do_compile실제로 실행된 셸 스크립트 — 변수가 다 풀린 상태
log.task_order이 레시피에서 태스크가 돈 순서

run.do_compile이 핵심이다. 이것을 열면 BitBake가 어떤 CC, CFLAGS, make 인자로 돌렸는지 그대로 보인다. Don이 펌웨어 빌드 로그에서 실제 컴파일러 커맨드라인을 뽑아 보던 것과 같다.

6.4 "왜 다시 빌드하지?" — bitbake-diffsigs#

한 줄 고쳤는데 수백 개 태스크가 다시 돌면, 서명(signature) 비교로 원인을 찾는다. bitbake-diffsigs -t recipe task의 의미를 소스에서 확인했다.

전형적인 원인: DATETIME 같은 매번 바뀌는 값을 레시피 변수에 넣음, AUTOREV, layer 안의 파일을 빌드 중에 생성, 호스트 경로가 변수에 섞임. 다음 절(sstate)을 이해하면 이 출력이 읽힌다.

7. sstate cache와 hash equivalence#

7.1 직관 — 입력 해시로 찾는 결과물 캐시#

BitBake는 각 태스크마다 입력의 해시(taskhash) 를 계산한다: 태스크 코드 + 그 태스크가 쓰는 변수 값 + SRC_URI 파일 체크섬 + 의존 태스크들의 해시. 같은 해시의 결과물이 캐시에 있으면 태스크를 돌리지 않고 결과만 풀어 놓는다(setscene). 이 캐시가 sstate(shared state)다. ccache와 비슷하지만 단위가 "컴파일 한 번"이 아니라 "태스크 하나의 출력 전체"다.

sstate 파일 이름 규칙이 클래스에 있다.

출력에서 볼 것: 파일 이름에 들어가는 해시는 BB_UNIHASH다 — taskhash가 아니다. 이것이 hash equivalence의 핵심이다. 압축은 .tar.zst.

7.2 hash equivalence — "입력은 바뀌었지만 출력은 같다"#

문제: 라이브러리 주석 한 줄을 고치면 그 라이브러리의 taskhash가 바뀌고, 그것에 의존하는 모든 레시피의 taskhash가 연쇄로 바뀐다. 출력 바이너리는 똑같은데도 전부 다시 빌드한다.

해결: 태스크를 실제로 돌린 뒤 출력의 해시(outhash) 를 계산해 서버(hashserv)에 보고한다. 이전에 같은 outhash를 낸 taskhash가 있으면 "둘은 동등하다"고 기록하고, 둘 다 같은 unihash를 쓴다. 하위 태스크의 해시는 taskhash가 아니라 unihash로 계산되므로, 연쇄 재빌드가 거기서 끊긴다.

기본값을 확인한다.

출력에서 볼 것: 현재 oe-core는 기본으로 hash equivalence를 켠다(OEEquivHash, BB_HASHSERVE = "auto" = 빌드할 때 로컬 서버를 자동으로 띄움). outhash는 출력 파일의 메타데이터와 내용 전체의 sha256이다. Yocto 프로젝트가 공개 sstate 미러와 hashserv를 운영하며, OE_FRAGMENTS += "core/yocto/sstate-mirror-cdn" 한 줄(6.0의 새 "config fragment" 방식)로 쓸 수 있다 — 단 회사 BSP의 레시피는 거기 없으므로 효과는 공통 부분(툴체인, native 도구)에 한정된다.

동작을 장난감 모델로 확인한다. 실제 BitBake 코드가 아니라 아이디어를 돌려 보는 Python이다.

출력에서 볼 것:

  • build 2: libimu의 taskhash는 바뀌었지만(e298…) outhash가 build 1과 같아서(caca…) unihash가 예전 값(57c8…)으로 매핑됐다. 그래서 imu-app의 taskhash가 변하지 않았고 캐시 HIT — 컴파일 없이 끝났다. 실제 Yocto에서는 "주석 한 줄 고쳤더니 그 레시피만 다시 빌드되고 이미지까지 연쇄가 안 간다"로 나타난다.
  • build 3: libimu가 진짜로 바뀌어 새 unihash. imu-app은 다시 빌드됐지만 출력이 같았으므로 다시 동등 판정을 받았다 — 그 아래 단계(패키징, 이미지)는 재사용된다.
  • 전제 조건: 출력이 재현 가능해야 한다. 빌드할 때마다 타임스탬프가 박히면 outhash가 매번 달라 동등 판정이 절대 나지 않는다. 그래서 8절의 재현성이 sstate 효율과 직결된다.

그림 4 — 태스크 하나가 sstate를 찾고 채우는 흐름. 오른쪽 위→아래가 빠른 길(HIT), 왼쪽 아래가 느린 길(MISS → 실행 → outhash 보고 → 저장)이다. 동등성 정보는 hashserv에, 결과물은 sstate에 따로 있다는 점이 중요하다.

8. 재현 가능한 빌드 — SOURCE_DATE_EPOCH#

8.1 왜 같은 소스가 다른 바이너리가 되나#

같은 커밋을 두 번 빌드해도 파일 mtime, tar/gzip 헤더의 시간, 빌드 경로, 파일 순서, 사용자 이름이 결과에 섞여 해시가 달라진다. 그러면 (1) "이 바이너리가 정말 이 소스에서 나왔나"를 증명할 수 없고(보안·규제), (2) hash equivalence가 동작하지 않는다(7.2).

해법의 중심이 SOURCE_DATE_EPOCH 다 — "현재 시간 대신 이 시각을 써라"라는 표준 환경 변수(reproducible-builds.org 사양). gcc(__DATE__), tar, gzip 계열 도구, 커널 빌드(KBUILD_BUILD_TIMESTAMP와 함께) 등이 존중한다.

8.2 직접 확인#

같은 내용의 "rootfs"를 2초 간격으로 두 번 묶는다. 한 번은 그냥, 한 번은 SOURCE_DATE_EPOCH를 지켜서.

출력에서 볼 것: 그냥 묶은 a/b는 내용이 같은데도 해시가 다르다(mtime·gzip 헤더 시간). SOURCE_DATE_EPOCH(마지막 git 커밋 시각)로 시간을 고정하고 정렬·소유자까지 고정한 c/d는 비트 단위로 같다. a/b의 해시는 실행할 때마다 달라지지만, c/d의 9934ffc0…는 이 스크립트를 몇십 분 간격으로 두 번 돌렸을 때 두 번 다 같았다 — 입력(파일 내용 + 커밋 시각)이 같으면 언제 돌려도 같은 출력이라는 뜻이다. Yocto의 이미지·패키지 클래스가 하는 일이 이 규칙을 모든 레시피에 적용하는 것이다.

8.3 Yocto는 SOURCE_DATE_EPOCH를 어떻게 정하나#

출력에서 볼 것: 레시피마다 자기 소스에서 값을 뽑는다 — git이면 마지막 커밋 시각, tarball이면 가장 새 파일의 mtime(그 전에 NEWS/ChangeLog 같은 "알려진 파일"도 본다), 아무것도 없으면 고정값. reproducible.py 머리 주석에 5단계 규칙이 적혀 있고, 정해진 값은 레시피별 __source_date_epoch.txt(SDE_FILE)에 저장돼 sstate와 함께 다닌다. rootfs 파일 시간은 REPRODUCIBLE_TIMESTAMP_ROOTFS로 고정된다. 예전에 있던 reproducible_build.bbclass는 이제 별도 클래스가 아니다 — 이 동작이 bitbake.conf와 lib/oe/reproducible.py에 기본으로 들어가 있다 (wrynose의 classes*/에 그 파일이 없음을 확인했다).

회사 layer가 재현성을 깨는 흔한 방법:

  • 레시피·스크립트에서 date, $(hostname), ${DATETIME}을 결과물에 박는다 → 빌드 정보가 필요하면 image-buildinfo 클래스(layer 커밋 기록)나 SOURCE_DATE_EPOCH 기반 값을 쓴다.
  • 사내 빌드 스크립트가 절대 경로(/home/jenkins/...)를 바이너리에 넣는다 → -ffile-prefix-map(oe-core가 기본으로 넣는 DEBUG_PREFIX_MAP)을 우회하지 않는다.
  • 검증: Yocto의 oe-selftest -r reproducible가 같은 빌드를 두 경로에서 돌려 패키지를 비교한다 (빌드가 필요하므로 이 노트에서는 실행하지 않음).

8.4 buildhistory와 SBOM — 출하물의 영수증#

  • buildhistory (INHERIT += "buildhistory", 우리 k5os.conf에 넣었다): 이미지마다 패키지 목록·크기·파일 목록·의존성을 git 저장소에 커밋한다. "어제 이미지와 오늘 이미지 차이"가 git diff가 된다 (buildhistory-diff 스크립트).
  • SBOM: oe-core defaultsetup.conf의 INHERIT_DISTRO에 이미 create-spdx가 들어 있고, create-spdx.bbclass는 이제 한 줄 inherit create-spdx-3.0이다 — 즉 기본으로 SPDX 3.0 SBOM을 만든다. 라이선스 의무(GPL 소스 제공, archiver 클래스), SBOM의 내용과 CVE 점검(sbom-cve-check)은 K7에서 다룬다.

10. 커널 안에서는 무슨 일이 일어나나 — 빌드 산출물이 부팅에서 만나는 곳#

Yocto는 빌드 도구지만, 이 노트에서 만든 산출물 셋(DTB, .config, .ko 패키지)은 각각 커널의 특정 경로로 들어간다. 드라이버 엔지니어가 "Yocto에서 넣은 게 왜 안 보이지"를 추적할 때 이 지도가 필요하다.

그림 6 — 이 노트의 세 산출물이 부팅한 커널 안에서 만나는 지점. 셋 중 하나라도 빠지면 IMU가 안 보인다: DTB가 아니면 i2c_client가 안 생기고, .config가 아니면 드라이버가 없고, 모듈 패키지가 아니면 rootfs에 .ko가 없다.

연결되는 커널 구조와 노트:

  • DTB → unflatten_device_tree()가 struct device_node 트리를 만들고, I2C 어댑터 드라이버가 등록될 때 of_i2c_register_devices()가 자식 노드마다 i2c_new_client_device()로 struct i2c_client를 만든다 (D4, H2).
  • 드라이버의 of_device_id 테이블(MODULE_DEVICE_TABLE(of, ...))은 .ko 안의 alias가 되고, rootfs 생성 시 depmod가 modules.alias로 모은다. uevent의 MODALIAS가 이 alias와 맞으면 udev가 modprobe한다 (G3, G4).
  • /proc/config.gz(CONFIG_IKCONFIG_PROC)로 보드에서 실제로 돌고 있는 커널의 설정을 본다 — kernel_configcheck가 빌드 때 본 것과 같아야 한다. 랩 커널에도 CONFIG_IKCONFIG_PROC=y가 켜져 있다 (3.6절에서 본 .config).
  • MACHINE_EXTRA_RRECOMMENDS로 넣은 패키지는 "추천"이라 이미지가 BAD_RECOMMENDATIONS로 뺄 수 있다. 부팅에 반드시 필요한 모듈이면 MACHINE_ESSENTIAL_EXTRA_RDEPENDS를 쓴다.

Don 경험과 연결: SSD 펌웨어에서 "하드웨어 설정 테이블(핀·NAND 파라미터) + 빌드 옵션(define) + 링크되는 모듈 목록"이 맞아야 기능이 살던 것과 정확히 같은 3요소다. Yocto는 이 셋을 각각 DT, Kconfig fragment, 패키지로 분리했을 뿐이다.

11. Embedded 실무에서 다시 보기#

11.1 정적 점검 — BitBake 없이 layer 실수 잡기#

BitBake가 파싱 단계에서 잡는 실수 몇 가지는 스크립트로 미리 잡을 수 있다 (사전 커밋 훅이나 CI 첫 단계로 쓸 만하다). 다음은 kas가 받은 실제 vendor layer를 기준으로 우리 layer를 검사한다.

출력에서 볼 것: 우리 layer의 호환 선언, require 경로, bbappend 대상 레시피, SRC_URI 파일이 실제 vendor checkout과 맞는다. 이 스크립트가 잡는 대표 사고가 "dangling bbappend" — 벤더가 u-boot-imx_2025.04.bb를 _2026.04.bb로 올렸는데 우리 bbappend가 버전을 박아 두었다면(u-boot-imx_2025.04.bbappend) BitBake는 대상 없는 bbappend를 에러로 처리한다. 이것은 정적 점검일 뿐이고, 변수 값·override 해석·태스크 의존성까지는 BitBake 파싱만이 확인한다.

11.2 장면 1 — "벤더가 새 BSP를 냈다"#

NXP가 새 릴리스를 내면 할 일: (1) kas 파일에서 meta-freescale 브랜치/커밋 갱신 → kas lock; (2) 우리 커널 패치가 새 SRCREV에 적용되나 — 3.5절처럼 실패하면 devtool modify → git rebase → devtool finish; (3) kernel_configcheck로 fragment가 아직 유효한지(심볼 이름 변경 감지); (4) bitbake-diffsigs로 예상보다 큰 재빌드 범위 확인; (5) buildhistory diff로 이미지 패키지 변화 리뷰. 이 다섯 줄이 "BSP 업그레이드 PR"의 체크리스트다.

11.3 장면 2 — "CI는 되는데 내 PC에서만 실패"#

거의 항상 셋 중 하나다: 다른 커밋(lock 파일 안 씀), 다른 local.conf(손으로 넣은 줄), 다른 호스트(배포판·Python 버전). 해법도 셋: kas lock 커밋, local_conf_header에만 설정, kas-container. 호스트 차이로 인한 sstate 불일치는 uninative(호스트 glibc 차이를 흡수하는 oe-core 기본 클래스, INHERIT_DISTRO에 들어 있음)가 상당 부분 막아 준다.

13. 면접에서 이렇게 말한다#

Q. How is a typical Yocto project for a product organized?

A. 남의 코드와 우리 코드를 layer로 나눈다. 아래부터 bitbake·openembedded-core, 참조 distro, vendor BSP layer(커밋 고정, 수정 금지), 그 위에 회사 BSP layer(machine conf, DT·커널 패치, bbappend), distro layer(정책), product layer(이미지). 전체를 kas나 repo 매니페스트로 묶고 모든 외부 저장소를 커밋 해시로 고정한다. 그래서 아무 릴리스나 다시 똑같이 빌드할 수 있다.

We split it by ownership. At the bottom we have bitbake and openembedded-core, then the vendor BSP layer like meta-freescale, pinned to a commit and never edited. On top of that we keep our own BSP layer with the machine config, device-tree and kernel patches as bbappends, a distro layer for policy, and a product layer with the image recipes. A kas file with a lock file pins every repository to a hash, so any release can be rebuilt exactly.

꼬리 질문: "Why not just fork the vendor layer?" → 벤더 업데이트를 받을 때마다 머지 지옥이 되고, 무엇을 바꿨는지 리뷰할 수 없다. bbappend는 변경이 작고 명시적이다.

Q. How do you add a device-tree change or a driver patch to the kernel in Yocto?

A. devtool modify virtual/kernel로 레시피가 받는 바로 그 SRCREV를 git 트리로 꺼내고, 고치고 커밋하고 devtool build/deploy-target으로 보드에서 확인한 뒤 devtool finish로 회사 BSP layer에 패치와 bbappend를 만든다. 결과는 FILESEXTRAPATHS:prepend와 SRC_URI:append:<machine>에 0001-….patch가 들어간 bbappend다. 새 보드는 EVK DTS를 고치지 않고 그것을 include하는 새 DTS를 추가한다.

I run devtool modify on the kernel recipe, which gives me a git tree at exactly the recipe's SRCREV. I commit the change, test with devtool build and deploy-target, then devtool finish writes a format-patch file and a bbappend into our BSP layer, scoped with a machine override. Patching against the real SRCREV matters — a patch made on mainline often fails do_patch on a vendor tree.

Q. defconfig or config fragments — how do you manage kernel configuration?

A. vendor의 KBUILD_DEFCONFIG를 기본으로 두고 우리 변경은 작은 .cfg fragment로 둔다. kernel-yocto가 merge_config.sh로 합치고, do_kernel_configcheck가 요청한 값이 실제 .config에 살아남았는지 검사한다. fragment는 menuconfig 후 diffconfig로 뽑는다. 부모 심볼이 m이면 =y가 조용히 m이 되는 것 같은 실수를 KMETA_AUDIT_WERROR로 빌드 실패로 만든다.

Vendor defconfig as the base, our deltas as small fragments. kernel-yocto merges them with merge_config.sh and kernel_configcheck reports any requested value that didn't survive Kconfig — for example a =y under a parent that's =m gets silently demoted. I generate fragments with menuconfig plus diffconfig, and I set KMETA_AUDIT_WERROR so CI fails on mismatches.

Q. What is sstate and what does hash equivalence add?

A. sstate는 태스크 출력의 캐시로, 키는 입력 해시(코드·변수·파일·의존 태스크 해시)다. 같은 해시가 있으면 태스크를 돌리지 않고 결과를 푼다. 문제는 출력이 안 바뀌는 변경(주석)도 하위 전체의 해시를 바꾼다는 것. hash equivalence는 태스크를 돌린 뒤 출력 해시를 서버에 보고해 같은 출력을 낸 입력 해시들을 하나의 unihash로 묶고, 하위 태스크는 unihash를 쓰므로 연쇄 재빌드가 끊긴다. 출력이 재현 가능해야 동작한다.

sstate caches each task's output keyed by a hash of its inputs. Hash equivalence adds an output hash: after a task runs, bitbake reports the output hash to a hash server, and if it matches an earlier build the new input hash is mapped to the same unified hash. Downstream tasks are keyed on that unihash, so a comment-only change stops the rebuild cascade. It only works if outputs are reproducible.

꼬리 질문: "Your build rebuilds everything after a small change — how do you debug it?" → bitbake-diffsigs -t <recipe> <task>로 두 서명의 차이(변수·파일·의존)를 보고, 매번 바뀌는 값(날짜, AUTOREV, 호스트 경로)을 찾는다.

Q. How do you make Yocto builds reproducible?

A. 세 층이다. 소스 — 모든 layer와 레시피를 커밋 해시로 고정(kas lock, SRCREV, AUTOREV 금지), 소스 미러로 네트워크 의존 제거. 빌드 환경 — 컨테이너(kas-container)와 uninative. 출력 — oe-core가 레시피마다 SOURCE_DATE_EPOCH를 소스(git 커밋 시각)에서 정해 모든 도구가 현재 시각 대신 쓰게 하고, 경로 prefix map을 넣는다. 검증은 oe-selftest -r reproducible, 출하물 기록은 buildhistory와 SPDX SBOM.

Pin the inputs — kas lock file, fixed SRCREVs, no AUTOREV, and source mirrors so we don't depend on GitHub. Pin the environment with kas-container. And make outputs deterministic: OE derives SOURCE_DATE_EPOCH per recipe from the source, usually the last git commit time, and tools use it instead of the wall clock. We verify with the reproducible selftest and keep buildhistory and SPDX SBOMs per release.

Q. What's the difference between the standard SDK and the eSDK, and how would an app developer use it?

A. 표준 SDK는 크로스 툴체인 + 타깃 sysroot + environment-setup 스크립트다. 그것을 source하면 CC에 --sysroot와 CPU 튜닝이 들어가므로 $CC나 CMake로 앱을 빌드한다. eSDK는 여기에 devtool과 sstate까지 들어 있어 레시피 추가·수정·보드 배포까지 Yocto 빌드 머신 없이 할 수 있다. 커널 모듈까지 하려면 kernel-devsrc를 SDK에 넣는다.

The standard SDK is a cross toolchain plus target sysroot plus an environment-setup script; after sourcing it, CC already carries --sysroot and the tuning flags, so you just use $CC or CMake. The extensible SDK adds devtool and sstate, so a developer can add or modify recipes and deploy to a board without a full build machine. For out-of-tree modules you add kernel-devsrc to the SDK.

Q. Do you need a PR server?

A. 패키지 피드로 현장 장비를 업데이트한다면 필요하다. 레시피 출력이 바뀌어도 사람이 PR을 안 올리면 버전이 같아 패키지 매니저가 업데이트를 안 한다. PR server가 출력 해시 변화마다 revision을 자동으로 올려 버전을 단조 증가시킨다. 이미지 전체를 A/B로 교체하는 제품이면 우선순위가 낮다. 쓴다면 DB를 export해서 백업한다.

If devices update from a package feed, yes — otherwise a changed package can keep the same version and never get installed. The PR server bumps the revision automatically whenever the output changes, so versions are monotonic across CI builds. With full-image A/B updates it matters less. Either way, back up its database.

16. 요약 & 체크리스트#

회사 Yocto는 소유권별 layer 스택 + 커밋 고정이다. vendor BSP는 건드리지 않고, 회사 BSP layer에서 machine conf(EVK에서 파생), DT·드라이버 패치(레시피 SRCREV 기준, Upstream-Status 포함), Kconfig fragment(kernel_configcheck로 검증)를 bbappend로 얹는다. 일상 개발은 devtool modify → build → deploy-target → finish 루프이고, out-of-tree 드라이버는 inherit module 레시피로 패키지(kernel-module-*)가 된다. U-Boot도 같은 bbappend + .cfg 패턴이다. 빌드 속도는 sstate(입력 해시 캐시)와 hash equivalence(출력 해시로 연쇄 재빌드 차단)에서 나오고, 이를 CI에서 공유하려면 DL_DIR/SSTATE_MIRRORS/BB_HASHSERVE/PRSERV_HOST를 함께 설계한다. hash equivalence와 감사 가능성은 재현성에 기대고, 재현성은 kas lock·SRCREV 고정·SOURCE_DATE_EPOCH로 만든다. 출하물의 영수증은 buildhistory와 SPDX SBOM(K7)이다. 이 노트에서 BitBake는 돌리지 않았지만, 그 아래에서 BitBake가 부르는 도구들(git format-patch, patch, cpp+dtc, merge_config.sh+olddefconfig, make M=, kas)은 모두 실제로 돌려 확인했다.
