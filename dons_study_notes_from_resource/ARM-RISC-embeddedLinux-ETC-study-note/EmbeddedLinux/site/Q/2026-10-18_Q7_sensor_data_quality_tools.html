0. 큰 그림 — 이게 왜 필요한가#

SSD 펌웨어를 양산할 때 Don은 "기능이 동작한다"와 "규격대로 동작한다"를 늘 구분했을 것이다. 읽기 명령이 성공하는 것과, p99.99 latency가 규격 안에 드는 것은 다른 문제다. 그래서 펌웨어 안에 카운터와 히스토그램을 심고, 생산 라인과 CI에서 그 숫자를 판정했다.

로봇·드론·차량의 센서 키트도 똑같다. IMU 드라이버가 /dev/iio:device0에서 값을 내주는 것은 "기능"이다. 그런데 센서 퓨전(EKF)이나 SLAM이 정말 필요로 하는 것은 이런 성질이다.

  • 샘플이 명목 주기대로 온다 (200 Hz라면 5.000 ms마다, 오차 몇백 ppm 이내).
  • 샘플이 빠지지 않는다. 빠지면 빠졌다는 사실을 안다.
  • 타임스탬프가 단조 증가하고, 모든 센서가 같은 시계를 쓴다.
  • 값이 물리적으로 말이 된다 (NaN 없음, 범위 안, 같은 값에 얼어붙지 않음).
  • 이 성질이 필드에서 깨지면 누군가 알아챈다 (헬스 모니터, 경보, 로그).

이걸 사람 눈으로 candump를 보며 확인할 수는 없다. 그래서 데이터 품질 툴을 만든다. 이 노트는 그 툴을 처음부터 짓는다: 정의 → 공식 → 설계 → 세 가지 실제 입력(IIO, V4L2, SocketCAN) → 결함 주입으로 검증 → systemd 헬스 모니터 → CI 게이트.

그림 1 — 센서에서 소비자까지 각 단계에서 생기는 품질 결함. 툴은 단계마다 따로 계측하지 않고, 끝에서 보이는 세 신호(타임스탬프·순번·값)로 거꾸로 추론한다.

bare-metal 비유로 보면, 이 툴은 SSD 펌웨어의 "latency histogram + error counter + assert"를 Linux 유저 공간 데몬으로 옮긴 것이다. 다른 점은 데이터가 커널을 거쳐 온다는 것이다. 커널은 버퍼가 가득 차면 대부분 에러 없이 버린다(IIO kfifo, V4L2 vb2 큐, 소켓 수신 버퍼 모두). 그래서 툴은 "에러가 안 났다"를 믿지 않고 타임스탬프와 순번으로 손실을 증명해야 한다.

2. 지표 정의와 공식#

2.1 직관 — 시간 축 위의 점들#

센서 스트림 하나는 결국 (t_k, seq_k, v_k, a_k)의 나열이다. t_k는 샘플 시각(센서·드라이버가 찍은 것), a_k는 내 프로그램이 받은 시각(arrival), seq_k는 순번, v_k는 값이다. 모든 시간 지표는 이웃한 두 점의 차 dt_k = t_k - t_(k-1)에서 나온다.

2.3 왜 평균이 아니라 percentile인가#

SSD에서 "평균 latency 80 µs"가 아무 의미 없고 "p99.99 latency 2 ms"가 고객 계약인 것과 똑같다. 센서 퓨전은 가장 나쁜 간격에서 깨진다. 예를 들어 200 Hz IMU에서 1초에 한 번 20 ms gap이 생기면 평균 dt는 5.075 ms로 1.5 %만 늘지만, EKF의 예측 단계는 그 순간 4배 긴 적분을 하게 된다. 그래서 리포트에는 p50(전형), p99(꼬리), max(최악)을 같이 싣고, gap은 따로 센다.

2.4 고정 메모리 — 히스토그램으로 percentile 구하기#

모든 dt를 리스트에 쌓고 정렬하면 정확한 percentile이 나오지만, 24시간 1 kHz 스트림이면 8,640만 개다. 장비 위 데몬은 메모리가 샘플 수와 무관해야 한다. 그래서 로그 간격 히스토그램을 쓴다.

  • 경계: 0, 그리고 1 µs ~ 10 s를 decade당 50칸(칸 폭 약 4.7 %). 배열 하나가 353칸(경계 352개 + 넘침 칸) × 8 B = 2,824 B.
  • percentile은 누적 개수가 p × N을 넘는 칸의 상단 경계로 답한다. 오차는 최대 칸 폭(4.7 %)이다.
  • dt 히스토그램은 분포 모양(그림 4, 5)에 쓰고, jitter는 abs(dt - T)를 따로 히스토그램에 넣는다. dt 히스토그램 하나로 jitter p99를 읽으면 10 ms 근처의 칸 폭(0.47 ms)보다 작은 jitter는 안 보이기 때문이다. abs(dt - T)의 히스토그램은 50 µs 근처에서 칸 폭이 2.4 µs다.
  • 평균·분산은 Welford(정확히는 Chan의 chunk 병합 공식)로 누적한다. sum(x^2) - n·mean^2 방식은 큰 값에서 자릿수 손실이 생긴다.

이 선택은 펌웨어의 latency bucket(2의 거듭제곱 버킷)과 같은 생각이다. Prometheus의 histogram, HdrHistogram도 같은 원리다.

2.5 Allan deviation — "rate가 시간에 따라 흔들리는가"를 한 줄로#

rate 오차(ppm)는 "평균적으로 몇 ppm 빠른가"만 말한다. 센서 시계가 온도에 따라 천천히 떠도는지, 아니면 짧은 jitter만 있는지는 구분하지 못한다. 이걸 보는 도구가 Allan deviation(ADEV)이다. 원래 원자시계·크리스털 안정도 지표이고, IMU 노이즈 분석(각속도 random walk, bias instability)에서도 같은 공식을 쓴다.

2.6 예제 1 — 정답을 아는 합성 스트림으로 검출기 자체를 검증#

툴을 실제 장치에 붙이기 전에 검출기가 정확한지 먼저 증명한다. 결함 위치와 개수를 아는 합성 스트림을 만들어 넣고, 툴이 정확히 그 숫자를 내는지 본다. 이 테스트는 CI에서 그대로 단위 테스트가 된다(9절).

무엇을 확인하는 코드인가: 100 Hz, 50 µs 가우시안 jitter인 1만 샘플에 drop 4개(2곳), 300 ms 뒤로 가는 시계 스텝, 중복 1개, stuck 100 샘플, NaN 1개, 범위 밖 1개를 넣고, 256개씩 chunk로 흘려서 집계한다. 마지막에 200만 샘플을 더 넣어도 메모리가 늘지 않는지 본다.

출력에서 볼 것:

  • 넣은 결함이 정확히 나온다: gap 2곳에 손실 4개(시각 기준과 순번 기준이 일치), 중복 1개(dups와 ts_zero_dt 둘 다 1), 시계 스텝 1회(ts_backwards=1), NaN 1, 범위 밖 1.
  • stuck 100 샘플은 "연속 같은 값 비교" 99번(stuck_run_max=99)이고, 그중 기준 50을 넘긴 뒤의 50개가 stuck_samples로 잡힌다. 경보는 "50 샘플째부터" 울린다는 뜻이다.
  • jitter: 타임스탬프에 sd 50 µs 잡음을 넣으면 dt의 sd는 sqrt(2) × 50 = 70.7 µs이고, abs(dt - T)의 중앙값 이론값은 0.674 × 70.7 = 47.7 µs, p99는 2.576 × 70.7 = 182 µs다. 툴은 50.1과 182.0을 냈다(칸 상단 경계로 답하므로 약간 크게 나온다).
  • 200만 샘플을 더 넣어도 maxrss가 그대로다. 상태 배열은 히스토그램 몇 KB뿐이다.

함정: 이 테스트에서 시계 스텝 직후의 dt는 -290 ms다. 음수 dt를 jitter 히스토그램에 넣으면 p99가 망가지고, gap 판정(dt > 1.5T)에서는 빠져서 "아무 일 없음"처럼 보인다. 그래서 dt < 0은 반드시 별도 카운터로 센다.

3. 툴 설계 — sdq (sensor data quality)#

3.1 구조 — 입력은 다르게, 판정은 하나로#

센서마다 툴을 따로 만들면 "IMU 툴은 gap을 1.5T로, 카메라 툴은 2T로" 같은 불일치가 생긴다. 그래서 어댑터(입력별) → 공통 chunk → 하나의 통계 엔진 → 여러 출력으로 자른다. 어댑터는 장치에서 읽어 numpy 배열 묶음 {t, arr, seq, v, kdrop}을 내놓는 일만 한다. 판정 규칙은 엔진 하나에만 있다.

그림 3 — 툴 구조. 회색 어댑터(UDP, ROS 2)는 이 노트에서 돌리지 않고 Q5·Q6에서 만든 수신 코드를 같은 chunk 형식으로 감싸면 된다.

설계 결정과 이유:

결정이유대안과 그 문제
Python + numpy, chunk 단위 벡터 연산샘플마다 Python 루프를 돌면 1 kHz × 여러 센서에서 CPU를 먹는다. chunk(16~256개)를 한 번에 처리하면 Python 오버헤드가 chunk 수에 비례C로 짜면 빠르지만 판정 규칙을 바꾸기 어렵다. 장비 위 상주 데몬이 CPU 예산에 걸리면 엔진만 C로 옮긴다
공통 chunk 형식어댑터 추가가 쉽고, 단위 테스트(합성 스트림)가 실제 장치와 같은 코드 경로를 탄다센서별 툴: 규칙 불일치
히스토그램 + 카운터만 상태로 보관메모리 고정, 24시간 상주 가능원시 dt 보관: 메모리 무한 증가
원시 레코드는 별도 로그(rotation)사후 분석(ADEV, 재현)용. 데몬 메모리와 분리로그 없이: 필드 이슈 재현 불가
도착 시각은 어댑터가 찍는다시계 도메인을 어댑터가 안다(IIO는 고른 시계, V4L2는 MONOTONIC, CAN은 REALTIME)엔진이 찍으면 chunk 처리 지연이 latency에 섞인다

3.2 통계 엔진 sdq_stats.py#

무엇을 하는 코드인가: 스트림 하나의 상태(카운터, 히스토그램 3개, Welford 누적값, 마지막 샘플)를 들고, chunk가 올 때마다 갱신한다. 이전 chunk의 마지막 시각·순번·값을 들고 있어서 chunk 경계에서도 dt·seq 차이·stuck 길이가 끊기지 않는다.

코드에서 볼 것:

  • np.searchsorted(EDGES, x)가 칸 번호를 주고 np.bincount(..., minlength=...)가 그 칸 개수를 센다. 정렬 없이 O(n log 352)다.
  • _welford는 chunk 전체의 평균·편차제곱합을 기존 누적값과 합친다(Chan 등의 병합 공식). 샘플 하나씩 도는 Welford와 결과가 같다.
  • _seq의 wrap 처리: seq_mod = 2^32(V4L2 sequence는 __u32)이면 차이를 (-2^31, 2^31]로 접는다. 그래서 4294967295 → 0은 +1(정상)이고, 큰 음수 점프만 순서 뒤바뀜으로 센다.
  • stuck 검사는 "직전과 같은가"의 bool 배열에서 마지막으로 False였던 위치를 np.maximum.accumulate로 구해 연속 길이를 벡터로 계산한다.
  • latency가 1 s를 넘는 샘플은 히스토그램에 넣지 않고 clk_err로만 센다. 시계가 다르면 latency 숫자 자체가 의미가 없기 때문이다. 음수 latency(도착이 샘플 시각보다 먼저)는 따로 lat_neg로 센다 — 처음 버전은 음수를 0으로 잘라 히스토그램에 넣었다가 V4L2에서 중요한 사실을 숨겼다(6.2절).

3.3 어댑터 sdq_adapt.py#

IIO — scan_elements로 레코드 배치를 계산한다#

IIO 버퍼의 한 레코드(scan) 배치는 I2 노트 4절에서 손으로 계산했다: 켜진 채널을 index 순서로 놓고, 각 원소를 자기 저장 크기의 배수 오프셋에 정렬하고, 레코드 전체를 가장 큰 원소 크기의 배수로 맞춘다. 어댑터는 이 규칙을 그대로 numpy structured dtype으로 만든다.

볼 것: 장치를 연 직후 이미 쌓여 있던 scan을 모두 읽어 버린다(discarded N stale scans). 처음 버전에는 이 줄이 없었는데, 버퍼를 켠 뒤 Python이 numpy를 import하는 수 초 동안 kfifo가 가득 차서 첫 chunk가 오래된 샘플 256개 + 수 초짜리 gap으로 시작했다. 그 결과 "깨끗한" 측정이 gap 44개, 손실 834개, clock_domain_err=256(오래된 샘플의 latency가 1 s 초과)로 나왔다. 측정 시작 조건(warm-up, flush)도 툴 설계의 일부다. 도착 시각은 read() 직후 한 번 찍어 chunk 전체에 쓴다. 그래서 IIO의 latency는 "샘플 시각 → 그 샘플이 들어 있는 read가 끝난 시각"이다. 버퍼 watermark가 크면 latency가 커지는 것이 그대로 보인다.

V4L2 — v4l2_buffer를 struct로 직접 다룬다#

v4l2-ctl 출력을 파싱하는 대신 ioctl을 직접 부른다. 필요한 것은 sequence, timestamp, flags(ERROR 비트) 세 필드뿐이라 픽셀은 mmap하지 않는다(MMAP 버퍼는 매핑하지 않아도 QBUF/DQBUF가 된다). 구조체 크기와 오프셋은 VM에서 C로 확인했다.

볼 것: 64비트에서 struct timeval이 8바이트 정렬이라 field(오프셋 16) 뒤에 4바이트 패딩이 있고 timestamp가 24에서 시작한다. ioctl 번호의 0x58이 크기 88이다(_IOWR('V', 17, struct v4l2_buffer)). 32비트 ARM에서는 이 숫자가 전부 달라진다 — Python에서 struct를 직접 다룰 때의 함정이다.

SocketCAN — 커널 수신 시각과 커널이 센 drop 수를 같이 받는다#

CAN 소켓은 두 가지를 공짜로 준다. SO_TIMESTAMPNS를 켜면 드라이버가 프레임을 받은 시각(skb 타임스탬프, CLOCK_REALTIME 기준)이 cmsg로 오고, SO_RXQ_OVFL을 켜면 이 소켓 수신 큐가 넘쳐서 버린 누적 개수(sk_drops)가 cmsg로 온다. 그래서 CAN에서는 손실을 세 가지 방법(시각 gap, payload 카운터, 커널 drop 카운터)으로 교차 검증할 수 있다.

볼 것: cangen -D i는 payload 8바이트를 리틀엔디언 카운터로 채운다(6.2절 candump 출력에서 확인). 실제 차량·로봇 CAN 메시지에서는 DBC에 정의된 4비트 rolling counter + CRC가 이 역할을 한다(Q4). 그 경우 seq_mod=16으로 두면 같은 엔진이 그대로 동작한다. 단, 4비트 카운터는 16개 이상 연속 손실을 못 본다 — 그래서 시각 gap 검사를 같이 돌린다.

UDP·ROS 2 — 여기서는 감싸기만#

LiDAR UDP 수신(Q5)은 패킷 헤더의 순번·타임스탬프를 꺼내 t, seq로, SO_TIMESTAMPNS로 받은 커널 수신 시각을 arr로 주면 된다. 소켓 drop은 CAN과 같은 SO_RXQ_OVFL이 UDP에서도 동작한다. ROS 2(Q6)는 구독 콜백에서 msg.header.stamp를 t로, 콜백 진입 시각을 arr로, (있으면) 드라이버가 넣은 순번을 seq로 준다. 둘 다 이 노트에서는 실행하지 않았다(가이드).

3.4 로그 — 고정 크기 레코드 + rotation#

헬스 판정에는 히스토그램이면 충분하지만, 필드 이슈를 재현하려면 원시 레코드가 필요하다. 장비 저장장치(eMMC, J 노트)는 작고 수명이 있으므로 크기 상한 + 오래된 파일 삭제가 기본이다. 형식은 고정 크기 binary 레코드(32 B: t, arr, seq, v, flags)다. 텍스트 CSV보다 3~5배 작고, numpy로 그대로 다시 읽힌다.

볼 것: 쓰기는 64 KB 사용자 버퍼를 거치므로 샘플마다 write() syscall이 나가지 않는다. 대신 전원이 갑자기 끊기면 마지막 64 KB는 잃는다. 이 트레이드오프는 J 노트(fsync, 저널링)와 같은 이야기다. 블랙박스처럼 "사고 직전 N초"가 중요하면 RAM 링버퍼에 두다가 이벤트가 나면 그 링버퍼를 덤프하는 방식(펌웨어의 crash log와 같은 설계)을 쓴다.

mcap — 로보틱스에서 쓰는 표준 로그 컨테이너 (가이드, 실행 안 함)#

직접 만든 binary 형식은 툴 하나에는 좋지만, 다른 팀(인지·제어)과 나누려면 표준 형식이 낫다. 로보틱스 쪽 사실상 표준은 MCAP(Foxglove가 만든 공개 형식)이고, ROS 2 Jazzy에서 ros2 bag record의 기본 저장 형식이다(Q6). 구조는 이렇다.

  • 파일 = 헤더 + 여러 chunk(압축 가능, zstd/lz4) + summary(채널·스키마 목록, chunk 인덱스, 통계) + footer.
  • 각 메시지는 channel_id, sequence, log_time, publish_time, data를 가진다. log_time(기록 시각)과 publish_time(발행 시각)을 따로 둔다는 점이 이 노트의 arr와 t에 해당한다.
  • summary의 chunk 인덱스 덕분에 큰 파일에서도 시간 구간을 바로 찾아 읽는다. 끝까지 쓰지 못한 파일(전원 차단)도 chunk 단위로 복구된다.
  • Python은 mcap 패키지(pip install mcap)의 Writer로 쓸 수 있다. 이 노트 랩에는 설치하지 않았다.

3.5 CLI sdq.py — 어댑터와 엔진을 잇는 껍데기#

무엇을 하는 코드인가: 입력 종류를 고르고, chunk를 엔진과 로그에 흘리고, 끝나면 요약(텍스트), ASCII 히스토그램(0이 아닌 칸만), JSON을 낸다. 툴 자신의 최대 메모리(maxrss_kb)도 리포트에 넣는다 — 측정 도구가 장비 자원을 얼마나 먹는지도 품질 정보다.

5. 어댑터 1 — IIO buffered stream (iio_dummy + hrtimer 트리거)#

5.1 설정#

iio_dummy는 configfs mkdir로 만드는 가상 IIO 장치이고, hrtimer 트리거도 configfs로 만든다(I2 노트 2절). 이 장치의 trigger handler는 스레드 안에서 iio_get_time_ns()를 부르고, 값은 상수 표(fakedata[])에서 가져온다(11절). 그래서 이 실습은 (1) 스레드 스케줄 지연이 타임스탬프 jitter로 나타나는 경우, (2) 값이 상수라서 stuck 검사가 반드시 울리는 경우를 함께 보여 준다.

결함 주입 방법을 정리하면 이렇다.

실험주입 방법기대하는 검출
A없음 (100 Hz, 버퍼 256, monotonic)기준선
B게스트 안 stress-ng --cpu 2jitter·latency 증가
C측정 도중 트리거 주파수 100 → 50 Hzrate 오차, dt 분포가 두 봉우리

E타임스탬프 시계 realtime + 측정 도중 date로 5 s 뒤로비단조 1회, 시계 도메인 오류 전부

5.2 A — 기준선과 그 해석#

A는 리포트 전체를 싣고, B 이후는 해석에 필요한 키만 골라 싣는다(줄을 고른 것이지 값은 실제 출력 그대로다).

출력에서 볼 것:

  • discarded 256 stale scans: 3.3절의 flush가 동작했다. 버퍼 길이 256이 꽉 차 있었다는 뜻이다.
  • TCG에서는 "깨끗함"도 깨끗하지 않다. rate가 97.8 Hz(−21,906 ppm), 1.5주기를 넘는 gap 98개, 시각 기준 손실 117개다. 게스트 hrtimer가 호스트 스케줄(19개 QEMU가 6코어를 나눠 씀)에 밀려 늦게 터지고, 그 사이의 주기는 사라진다. 실제 보드라면 hrtimer 트리거 100 Hz의 jitter는 µs 단위이고 gap은 0이어야 한다.
  • lat_p50 = 9.1 ms: 버퍼 watermark가 1이라 샘플이 들어오는 즉시 select()가 깨지지만, TCG에서 Python 루프 한 바퀴가 수 ms다. lat_max 764 ms는 리더가 통째로 밀린 순간이다.
  • stuck_samples 1906, stuck_run_max 1955: iio_dummy의 in_voltage0 값은 상수 7이다. 실제 센서였다면 이것만으로 FAULT다. 툴이 "모든 것"을 정상 처리하지 않고 이상한 값 패턴을 정확히 잡았다.

dt 히스토그램의 가운데 부분(0인 칸은 툴이 이미 생략했고, 양 끝 꼬리는 여기서 잘랐다):

A 실험은 --log로 원시 레코드를 남겼다. 사후 분석 도구는 로그를 읽어 평균 주기를 최소제곱으로 구하고, 2.5절의 공식으로 ADEV를 낸다.

5.3 B — 게스트 부하#

볼 것: 게스트 안 부하를 넣었는데 숫자가 A보다 크게 나쁘지 않다(gap 55 vs 98). TCG에서는 게스트 부하보다 호스트 경쟁이 지배적이라 두 측정의 차이가 잡음 안에 있다. 이런 비교는 한 번 측정으로 결론 내지 않고 반복해 분포로 봐야 한다 — 실제 HW에서는 B가 A보다 명확히 나빠야 정상이다(N3 노트의 cyclictest 비교와 같은 원리).

5.4 C — 트리거 주파수가 바뀌면#

그림 4 — IIO 100 Hz 기준선(A)과 측정 도중 50 Hz로 바뀐 경우(C)의 dt 분포. 실측값(TCG). C는 10 ms와 20 ms 두 봉우리를 갖는다.

볼 것:

5.5 D — 작은 버퍼 + 느린 리더 = 흔적 없는 drop#

볼 것:

  • 20초 동안 373개만 받았다. 100 Hz라면 약 1,960개여야 한다. 리더가 0.2 s마다 읽을 때 kfifo에는 4개만 남아 있고 나머지(약 16개)는 버려진다.
  • kernel_drops 0: IIO는 overflow를 세어 주지 않는다(11절). 손실 1,592개는 오로지 타임스탬프 gap으로 추정한 것이다. 받은 373 + 추정 손실 1,592 = 1,965 ≈ 19.6 s × 100 Hz. 추정이 거의 맞다.
  • lat_p50 = 199.5 ms: 리더 주기만큼 데이터가 늦게 소비된다. 해결은 버퍼 길이를 "리더 최대 지연 × rate"보다 크게(여기서는 최소 20, 여유를 두면 64 이상) 잡는 것이다.

5.6 E — 시계 도메인과 시계 스텝#

볼 것:

  • clock_domain_err 1581 = 모든 샘플. 타임스탬프는 CLOCK_REALTIME(1970 기준), 도착 시각은 CLOCK_MONOTONIC(부팅 기준)이라 차이가 약 −1.79 × 10^9 s(56년)다. 툴은 latency 숫자를 버리고(lat_p50 nan) "시계가 다르다"고만 말한다. 올바른 동작이다.
  • ts_backwards 1: date로 5초 되돌린 순간이다. 그 직후 dt는 −4.99 s 근처였을 것이고, 그래서 span_s가 15.6 s가 아니라 10.6 s로 줄었다.
  • 그 결과 rate_hz 148.9, rate_err +488,524 ppm이라는 틀린 rate가 나온다. 끝점 두 개로 계산하는 rate는 시계 스텝 하나에 완전히 망가진다. 그래서 ts_backwards > 0이면 rate 판정 자체를 무효로 해야 한다.
  • 교훈: IIO의 기본 시계는 realtime이다(I2 노트에서도 확인). 로봇에서는 장치를 열기 전에 current_timestamp_clock을 monotonic(또는 시스템 표준 시계)으로 바꾼다. NTP·timesyncd·GNSS가 시각을 맞추는 순간 realtime은 뛴다.

실패한 첫 측정이 보여 준 것#

4절에서 말한 dash . 함정 때문에 첫 실행은 기본값(버퍼 길이 2, realtime)으로 돌았다. 그 리포트의 일부다.

20초 측정인데 span_s가 36.9 s, dt_max가 16.9 s다. 버퍼 길이 2라서 리더가 조금만 늦어도 버리고(gap 156, 손실 2,044), realtime 시계가 측정 도중 크게 움직였다(게스트 부팅 직후 시각 동기화로 추정, 확인 안 함). 설정이 기대와 다를 때 툴이 즉시 이상하다고 말해 준 사례다. 측정 스크립트는 설정을 다시 읽어 찍는 줄(# iio:device0 ... buflen=2 clock=realtime)을 반드시 남겨야 한다.

6. 어댑터 2 — V4L2 capture (vivid)#

6.1 설정과 결함 주입#

vivid는 커널에 들어 있는 가상 카메라 드라이버다(I5 노트). 쓸모 있는 점은 오류 주입 컨트롤이 있다는 것이다: percentage_of_dropped_buffers(버퍼를 일부러 안 채움), wrap_sequence_number(sequence를 2^32 − 128에서 시작), wrap_timestamp(타임스탬프를 64비트·32비트 경계 근처로 옮김). 실제 카메라에서 재현하기 어려운 결함을 버튼 하나로 만든다.

6.2 A — 기준선, 그리고 음수 latency#

출력에서 볼 것:

  • Frame rate set to 30.000 fps: vivid의 320×180 기본값은 5 fps였다(처음 확인한 --get-parm 결과). 측정 전에 명목값을 설정하고 다시 읽어 확인한다.
  • lost_by_seq 6, lost_by_ts 5: TCG에서 vivid kthread가 늦게 깨서 6프레임을 건너뛰었다. 시각 기준 추정은 5개다 — jitter에 묻힌 손실 하나를 시각 추정이 놓쳤다. 순번이 있으면 순번이 정답이다.
  • lat_negative 587(592개 중), lat_min_us −29037.5: 거의 모든 프레임이 타임스탬프보다 먼저 도착했다. 원인은 vivid 소스에 있다. 기본 타임스탬프 소스가 EOF(end of frame)라서 timestamp = 채운 시각 + 0.9 × 프레임 주기(cap_frame_eof_offset = f_period × 9 / 10)다. 33.3 ms × 0.9 = 30.0 ms만큼 미래 시각이 찍히고, 버퍼는 바로 전달되므로 latency가 약 −29 ms가 된다.
  • 처음 버전의 툴은 음수 latency를 0으로 잘라 히스토그램에 넣어서 lat_p50 0.0(완벽해 보이는 숫자)을 냈다. "완벽해 보이는 숫자"도 의심해야 한다. 고친 툴은 음수를 따로 세고, 그 덕에 "이 드라이버의 타임스탬프는 노출 시작이 아니라 노출 끝(모델링된 시각)"이라는 사실이 드러났다. 실제 센서 드라이버도 SOE/EOF 중 무엇을 찍는지 V4L2_BUF_FLAG_TSTAMP_SRC_SOE/EOF 플래그로 알려 준다. 센서 퓨전에서 이 차이(수십 ms)는 치명적이다(Q3).
  • dt가 33.1 ms 칸에 몰려 있지만 jitter p50이 2 ms다. CONFIG_HZ=250(4 ms jiffy)인 커널에서 vivid kthread는 jiffy 단위로 깨어나서, 33.3 ms 주기가 32 ms·36 ms로 양자화된다(11절, 그림 5의 파란 막대가 두 봉우리인 이유).

6.3 B·C·D — 드롭 세 가지#

그림 5 — vivid 30 fps의 프레임 간격 분포. 실측값(TCG). 파란색은 버퍼 4개 기준선, 빨간색은 버퍼 2개 + 프레임마다 50 ms 처리하는 느린 소비자. 빨간 봉우리가 66 ms(= 2주기)로 옮겨 갔다.

볼 것:

  • B(드라이버가 10 % 드롭): 528개를 받고 순번 손실 65개. 기준선 손실(약 6)을 빼면 59개 ≈ 593 × 10 %. 주입한 비율과 맞는다. lat_negative 526 — 드롭이 있어도 latency 성질은 그대로다.
  • C(소비자가 느림): 프레임 처리에 50 ms가 걸리고 버퍼가 2개뿐이면, 드라이버가 채울 빈 버퍼가 없는 순간이 생긴다. 252개 손실, dt 중앙값 66 ms(그림 5). latency p50이 17 ms로 커지고 음수 latency가 62개로 줄었다 — 버퍼가 큐에서 오래 기다리기 때문이다. 이 결함은 버퍼 수를 늘리면 사라지고, B는 사라지지 않는다. 12.2절의 디버깅 순서가 이 차이를 이용한다.
  • D(부하): 순번 손실 33, dt_max 635 ms, lat_max 685 ms. 부하 순간 kthread와 리더가 모두 밀렸다.

6.4 E·F — wrap#

wrap이 정말 측정 구간 안에서 일어났는지 로그로 확인한다(run_v4l2b.sh: 같은 측정을 --log로 남기고 wrap 지점을 찾는다).

볼 것: sequence가 4294967168(= 2^32 − 128)에서 시작해 128프레임(약 4.3 s) 뒤 4294967295 → 0으로 넘어갔다. 원시 차이는 −4,294,967,295지만 seq_mod=2^32로 접으면 +1이라서 out_of_order 0, 손실은 실제 손실(시각 기준과 같은 3개)만 나온다. wrap 처리 없이 뺐다면 "순서 뒤바뀜 1"로 경보가 울렸을 것이다. 24시간 30 fps 카메라는 4.5년 뒤에 wrap하지만, 장비의 카운터는 더 짧은 경우가 많고(4비트 CAN counter는 16프레임마다), 테스트 없이 wrap을 믿으면 안 된다.

볼 것: wrap_timestamp=2는 타임스탬프를 (2^31 − 16) s 근처로 옮긴다. 간격·순번은 정상(rate·손실 지표는 그대로 계산됨)이지만 도착 시각(CLOCK_MONOTONIC)과의 차가 약 −2.1 × 10^9 s라서 288개 전부 clock_domain_err다. 시간 축 지표(dt)는 같은 시계 안의 차이라서 시계 도메인이 달라도 계산되고, latency만 무의미해진다. 그래서 두 지표군을 따로 판정한다.

7. 어댑터 3 — SocketCAN (vcan + cangen)#

7.1 설정과 결함 주입#

vcan은 가상 CAN 인터페이스이고, cangen -D i는 payload를 증가하는 카운터로 채운다(Q4). CAN에서는 손실을 세 가지 독립된 방법으로 셀 수 있다: 시각 gap 추정, payload 카운터, 커널 소켓 drop 카운터(SO_RXQ_OVFL).

7.2 결과#

먼저 cangen -D i의 payload가 리틀엔디언 카운터(첫 바이트부터 00, 01, 02)라는 것을 candump로 확인했다. 어댑터는 이것을 <Q(리틀엔디언 u64)로 읽는다.

그림 6 — CAN 실험 A~D에서 같은 손실을 세 방법으로 센 결과(실측). D에서 payload 카운터와 커널 drop 카운터가 정확히 1176으로 일치한다. A~C의 시각 기준 "손실"은 실제 손실이 아니다.

볼 것:

  • A(기준선): cangen -g 10인데 실제 rate는 82.7 Hz, dt 중앙값 11.5 ms다. 순번 손실 0, 커널 drop 0 — 프레임은 하나도 안 버려졌다. cangen의 -g는 "보낸 뒤 10 ms 쉬기"(상대 sleep)라서 루프 오버헤드(TCG에서 1~2 ms)가 매 주기 누적된다. 시각 기준 "손실 114"는 느린 송신자를 손실로 오해한 것이다. 순번이 있으면 "rate가 낮다(송신 측 문제)"와 "손실이 있다(전달 경로 문제)"가 구분된다. 그래서 8절의 헬스 모니터용 송신기는 절대 마감 시각으로 보내는 q7_gen.py로 바꿨다.
  • B(부하): 손실은 여전히 0인데 latency p99가 912 ms, max가 1.49 s다. 소켓 수신 버퍼가 충분히 커서 버리지 않고 쌓아 두었다. "drop 0"이 "건강함"은 아니다. 또 latency 1 s 초과 57개가 clock_domain_err로 분류됐다 — 시계 도메인 판정 문턱(1 s)이 실제 지연과 겹친 툴의 오분류다. 시계 도메인은 "차이가 일정한 큰 상수인가"로 보는 편이 맞다(연습 아이디어).
  • C(송신기 1.5 s 정지): dt_max 1540 ms, 시각 기준 손실 160, 순번 손실 0. 송신기가 멈췄다가 카운터를 이어서 보냈으므로 빠진 프레임은 없다. 이것은 "손실"이 아니라 "stall"이다. 헬스 모니터 입장에서는 둘 다 bad 창이지만, 원인 분석에서는 전혀 다르다(센서가 멈춤 vs 경로가 버림).
  • D(작은 수신 버퍼 + 느린 리더): SO_RCVBUF=1024(커널이 두 배로 잡고 최솟값을 적용)이면 몇 프레임만 큐에 들어간다. 리더가 프레임마다 30 ms를 쓰면 나머지는 __sock_queue_rcv_skb()에서 버려진다. payload 카운터 1176 = 커널 drop 1176. 커널이 센 숫자와 데이터에서 추론한 숫자가 정확히 일치하므로, 이 손실은 전부 "내 소켓"에서 생겼다고 증명된다. 시각 추정(1228)은 송신자 느림까지 섞여 과대평가다.
  • E(같은 CAN ID 송신자 둘): 두 번째 cangen이 0부터 카운터를 보내면서 out_of_order 292, lost_by_seq 207663(의미 없는 큰 수), dt_min 1.4 µs(두 프레임이 거의 동시)가 나왔다. 순서가 뒤바뀌기 시작하면 순번 기반 손실 숫자는 무효다. 툴은 이 상황을 "ID 충돌·송신자 중복"으로 분류해야 한다. 실제 차량·로봇에서는 같은 ID를 두 노드가 보내는 설정 실수, 게이트웨이 재전송 루프가 이 패턴을 만든다. ts_backwards 4는 두 CPU에서 각각 보낸 프레임이 소켓 큐에 들어간 순서와 skb 시각 순서가 어긋난 것으로 보인다(추정, 확인 안 함).

8. 헬스 모니터 — 장비 위에서 24시간 지키기#

8.1 벤치 툴과 무엇이 다른가#

sdq.py는 "20초 재고 리포트"다. 장비 위에서는 질문이 바뀐다: "지금 이 순간 센서가 건강한가, 그리고 건강하지 않으면 누가 무엇을 하나." 그래서 헬스 모니터는 세 가지를 더한다.

  • 창(window) 판정: 1초마다 그 1초의 샘플만 보고 good/bad를 낸다. 누적 통계는 "어제 한 번 있었던 일"을 영원히 끌고 다니므로 실시간 판정에 맞지 않다.
  • 히스테리시스: bad 한 번에 바로 FAULT를 내면 부하가 잠깐 튈 때마다 경보가 울린다(alarm flapping). 들어갈 때와 나올 때의 문턱을 다르게 둔다. 펌웨어의 온도 스로틀링(85 °C에서 걸고 80 °C에서 풂)과 같은 생각이다.
  • 바깥 세계와의 연결: systemd watchdog(살아 있음), 상태 문자열(systemctl status에 보임), 메트릭 파일(수집기가 가져감), journal 우선순위(경보 규칙이 걸림).

그림 7 — 헬스 상태 기계. 들어가는 문턱(bad 1회, 3회 연속)과 나오는 문턱(good 3회, 5회 연속)이 다르다. FAULT에서는 일부러 watchdog ping을 멈춰서 systemd가 복구 동작(재시작)을 하게 한다.

8.2 watchdog을 "데이터 건강"에 묶을 것인가#

L1 노트에서 본 WatchdogSec=는 원래 프로세스가 멈췄는지(hang)를 잡는 장치다. 여기서는 한 걸음 더 나가서 "데이터가 건강할 때만 ping" 하는 설계를 쓴다. 장단점이 분명하다.

설계동작장점단점
A. 항상 ping (liveness만)모니터가 살아 있으면 ping, 데이터 결함은 경보만모니터 재시작이 데이터 문제를 못 고칠 때 무의미한 재시작이 없다복구 동작을 따로 짜야 한다
B. 건강할 때만 ping (이 노트)FAULT가 WatchdogSec 넘게 지속되면 systemd가 재시작재시작(= 소켓·장치 다시 열기, 드라이버 재바인드를 ExecStartPre로)이 표준 경로가 된다. 재시작 횟수가 곧 경보 지표센서 자체가 죽었으면 재시작 루프. 그래서 StartLimitBurst로 끊고 OnFailure=로 경보

실무에서는 보통 B를 센서 수집 데몬에, A를 모니터 자신에 쓴다. 이 노트는 둘을 한 프로세스로 합쳐서 B를 보여 준다.

8.3 코드 q7_health.py#

무엇을 하는 코드인가: CAN 어댑터를 그대로 쓰고(0.2 s 수신 타임아웃이라 데이터가 끊겨도 루프가 돈다), 1초마다 판정 → 상태 기계 → sd_notify(READY, STATUS, WATCHDOG) → Prometheus textfile → journal 로그를 한다. sd_notify는 libsystemd 없이 $NOTIFY_SOCKET에 데이터그램을 보내는 프로토콜 그대로다(L1 노트 2절).

볼 것:

  • log(4, ...): stderr에 <4>를 붙이면 journald가 그 줄을 priority 4(warning)로 저장한다(SyslogLevelPrefix=yes가 기본). 경보 규칙은 "q7-health의 warning 이상"으로 걸면 된다.
  • export()는 임시 파일에 쓰고 os.replace로 바꾼다. 수집기(node_exporter textfile collector 같은 것)가 반쯤 쓴 파일을 읽지 않게 하는 원자적 교체다.
  • FAULT에서는 STATUS=는 계속 보내고 WATCHDOG=1만 멈춘다. 그래서 죽기 직전까지 systemctl status에 이유가 보인다.

8.4 가짜 센서와 unit 파일#

7.2절에서 본 것처럼 cangen -g는 상대 sleep이라 TCG에서 명목 rate를 못 낸다. 헬스 모니터 시험에는 평균 rate가 밀리지 않는 송신기가 필요해서, 절대 마감 시각으로 보내는 작은 송신기를 썼다(펌웨어의 "다음 tick = 이전 tick + 주기" 스케줄과 같다).

볼 것: Type=notify라서 systemd는 READY=1이 올 때까지 "activating" 상태로 기다린다. TCG에서 numpy import만 수 초가 걸리는데, 그 시간 동안 이 서비스에 의존하는 unit은 시작하지 않는다. StartLimitIntervalSec=60·StartLimitBurst=3은 60초 안에 세 번 넘게 재시작하면 포기(failed)하라는 뜻이다. 그때 OnFailure=로 경보 unit을 걸면 된다(여기서는 생략).

8.5 실험 — 센서를 얼려서 watchdog을 터뜨린다#

시나리오: 서비스를 시작해 15초 건강하게 돌린 뒤, 송신기를 SIGSTOP으로 10초 얼리고(센서가 조용히 멈춘 상황), 풀어 준 뒤 25초 지켜본다.

journal 타임라인을 읽어 보면(괄호 안은 부팅 후 초):

  1. 631.6 READY → Started. 15초 동안 상태 OK, metrics q7_state 0, 창 샘플 96개(명목 100, 문턱 90 이상).
  2. 647.6 송신기 정지 직후 창의 샘플이 32개 → DEGRADED. 649.7 샘플 0개가 이어지자(bad 3창 연속) → FAULT, 이때부터 ping 중단.
  3. 651.7 마지막 ping 후 3초 → Watchdog timeout (limit 3s)! → SIGABRT. 654.7 code=dumped, status=6/ABRT, Failed with result 'watchdog'.
  4. 655.9 RestartSec=1s 뒤 재시작(restart counter is at 1), 658.2 새 인스턴스 READY. 그 사이 송신기가 풀려서 새 인스턴스는 바로 OK로 돌았고, H3 시점 Status: "OK n=112 ok", NRestarts=1.

볼 것:

  • H2 시점의 ActiveState=activating SubState=start, StatusText=(빈 값): 재시작된 인스턴스가 numpy를 import하는 중이다. 재시작 비용(TCG에서 약 3초)이 곧 감시 공백이다. 실제 장비에서는 모니터를 가볍게(C, 또는 import를 최소화) 만들어 공백을 줄인다.
  • LimitCORE=0을 줬는데도 code=dumped로 나왔다. 이 rootfs의 core_pattern이 파이프 핸들러(systemd-coredump 등)라서 RLIMIT_CORE와 다르게 처리되는 것으로 보인다(추정, 확인 안 함). 처음 실행(LimitCORE 없음)에서는 SIGABRT 후 프로세스가 끝나기까지 9초가 걸렸고, 이번에는 3초였다.
  • 그 처음 실행에서는 송신기를 cangen -g 5(명목 200 Hz)로 뒀는데, 모니터가 시작하자마자 state -> DEGRADED (rate 112/s < 180) → FAULT → watchdog 재시작을 반복했다. 송신기가 TCG에서 200 Hz를 못 낸 것이다. 헬스 모니터는 정확했고, 틀린 것은 시험 장비(가짜 센서)였다. 그래서 8.4절의 절대 마감 송신기로 바꿨다.
  • metrics 파일은 Prometheus textfile 형식이다. 장비에서는 node_exporter의 textfile collector가 이 디렉터리를 읽거나, 자체 수집기가 MQTT 등으로 올린다(가이드).

9. 데이터 품질 회귀를 CI에 넣기#

P6 노트의 테스트 피라미드에 이 툴을 끼우면 두 층이 된다.

  • 단위 테스트(모든 커밋): 2.6절의 test_synth.py처럼 정답을 아는 합성 스트림으로 검출기 자체를 검증한다. 판정 규칙을 고친 커밋이 gap 판정을 망가뜨리면 여기서 걸린다. HW가 필요 없다.
  • HIL 테스트(야간·릴리스): 실제 보드(또는 이 노트처럼 QEMU)에서 고정 시나리오(idle 60 s, 부하 60 s)로 리포트 JSON을 만들고, 스펙 파일과 비교해 위반이 있으면 실패로 끝낸다. 커널·드라이버·BSP 업그레이드(P5)에서 "IMU jitter가 조용히 두 배가 됐다"를 잡는 곳이다.

게이트는 단순하다: 키마다 최대 허용값.

스펙을 지키는 경우를 먼저 확인한다. 깨끗한 100 Hz 합성 스트림(5분, jitter 200 µs, latency 2 ms)의 리포트를 만든다.

출력에서 볼 것:

  • 합성 스트림은 PASS, exit 0. TCG에서 잰 IIO 기준선(5.2절)은 rate·p99·손실 세 항목이 FAIL, exit 1. CI 러너는 exit code만 보면 된다.
  • 같은 스펙을 TCG 결과에 대면 늘 실패한다. 스펙은 타깃 HW 기준이고, VM에서 도는 CI는 "툴이 동작하는가"와 "결함을 넣으면 FAIL이 나는가"만 확인한다. VM용으로 스펙을 느슨하게 만들면 실제 회귀를 놓친다.
  • 실무에서는 스펙을 센서별 YAML로 빼고(예: imu_bmi088.yaml: rate_err_ppm 500, dt_p99_us 1100), 리포트 JSON을 CI 산출물로 보관해 추세 그래프를 그린다. 한 번의 FAIL보다 p99가 릴리스마다 조금씩 커지는 추세가 더 중요한 신호인 경우가 많다.
  • LAVA·Jenkins·GitHub Actions의 self-hosted runner 등 어디에 붙이든 형태는 같다: 보드 부팅 → sdq.py ... --json → sdq_check.py → exit code + JSON 업로드. P6 노트의 HIL 구성과 그대로 이어진다(가이드, 이 노트에서 CI 서버는 구성하지 않았다).

10. 센서 사이의 품질 — 일관성과 sync 오차#

지금까지는 스트림 하나만 봤다. 퓨전에서는 두 센서가 서로 맞는가가 더 자주 문제다. 툴이 자동으로 잡기 어렵고 도메인 지식이 필요한 영역이라, 방법만 정리한다(실행 안 함, 동기화 구현 자체는 Q3).

검사방법판정 예
rate 비율두 스트림의 f_meas 비가 명목 비와 같은가IMU 200 Hz : 카메라 30 Hz = 6.667. 비율이 시간에 따라 변하면 두 센서가 다른 발진기를 쓰고 있고, 그 차이(ppm)만큼 시각이 벌어진다
sync 오차같은 물리 사건이 두 센서에 찍힌 시각의 차카메라 strobe(노출 시작) GPIO를 IIO/PPS로 같이 찍어서 t_cam - t_strobe 분포를 본다(Q3의 HW trigger)
잔차 일관성한 센서로 다른 센서를 예측한 오차휠 오도메트리 속도 vs IMU 가속 적분, GNSS 속도 vs 휠 속도. 잔차의 이동 RMS가 문턱을 넘으면 한쪽이 의심
상호상관 지연두 신호의 상호상관 최대 위치로봇을 흔들어 IMU 각속도와 카메라 광류(optical flow)의 상관 최대 지연 = 카메라 타임스탬프 오프셋. Kalibr 같은 캘리브레이션 도구가 하는 일
시계 도메인 일치모든 스트림이 같은 시계 ID를 쓰는가장치마다 current_timestamp_clock(IIO), V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC(V4L2), 소켓 타임스탬프(REALTIME)를 확인하고 하나로 변환

마지막 줄이 특히 중요하다. 이 노트의 세 어댑터만 해도 기본 시계가 셋 다 다르다. IIO는 기본 CLOCK_REALTIME(설정으로 바꿀 수 있음), V4L2(vivid, 대부분의 드라이버)는 CLOCK_MONOTONIC, 소켓 SO_TIMESTAMPNS는 CLOCK_REALTIME이다. 퓨전 노드에 넘기기 전에 하나의 시계로 변환하는 계층이 반드시 있어야 하고, 품질 툴은 그 계층이 맞게 동작하는지(시계 도메인 오류 = 0)를 확인한다. 장치 사이의 공통 시계(PTP의 PHC, PPS)는 Q3에서 다룬다.

11. 커널 안에서는 무슨 일이 일어나나#

툴이 본 숫자를 해석하려면 커널이 어디서 시각을 찍고, 어디서 데이터를 버리는지 알아야 한다. 세 어댑터의 경로를 6.18 소스로 따라가 본다.

그림 8 — IIO·V4L2·SocketCAN에서 타임스탬프를 찍는 지점(T)과 데이터를 버리는 지점(D). 6.18.55 소스 기준.

경로별로 소스 위치를 짚는다.

  • IIO: drivers/iio/buffer/kfifo_buf.c의 iio_store_to_kfifo()는 kfifo_in()이 1을 못 넣으면 -EBUSY를 돌려준다. 이 값은 iio_push_to_buffer() → iio_push_to_buffers()로 올라가지만 iio_simple_dummy_trigger_h()는 반환값을 보지 않는다. 대부분의 업스트림 드라이버도 그렇다. IIO 버퍼 overflow는 카운터가 없다. 그래서 IIO 스트림의 손실은 타임스탬프 gap으로만 보인다(I2 노트의 i2_imu는 칩 샘플 번호를 채널로 노출해서 이걸 해결했다). 타임스탬프는 iio_get_time_ns()가 current_timestamp_clock에 따라 ktime_get_real_ns()/ktime_get_ns()/... 중 하나를 고른다(industrialio-core.c).
  • V4L2(vivid): vivid-kthread-cap.c에서 cap_seq_count는 "스트림 시작 후 jiffies 경과 ÷ 프레임 주기"로 계산된다. 스레드가 늦게 깨면 dropped_bufs만큼 sequence가 건너뛴다. perc_dropped_buffers나 빈 큐(vid_cap_active 비어 있음)면 goto update_mv로 버퍼를 채우지 않는다. 실제 CSI 수신 드라이버도 "빈 버퍼가 없으면 프레임을 버리고 sequence는 올린다"가 관례라서, V4L2에서는 sequence gap이 곧 드롭이다. 타임스탬프는 vb2_buf.timestamp = ktime_get_ns()이고 큐의 timestamp_flags = V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC(vivid-core.c)이다.
  • SocketCAN: vcan_rx() → netif_rx()에서 net_timestamp_check()가 skb 시각을 찍는다(누군가 타임스탬프를 요청한 경우). can_rcv() → raw_rcv() → sock_queue_rcv_skb_reason()이고, __sock_queue_rcv_skb()가 sk_rmem_alloc >= sk_rcvbuf면 sk_drops_inc() 후 버린다(net/core/sock.c). sock_recv_drops()(net/socket.c)가 SOCK_RXQ_OVFL이 켜져 있고 dropcount가 0이 아닐 때 cmsg를 붙인다.

드라이버를 쓸 때 이 지식이 다시 나오는 곳:

  • IIO 드라이버(I2): 타임스탬프를 hard IRQ 쪽(iio_pollfunc_store_time)에서 찍을지, 스레드에서 찍을지가 jitter를 결정한다. FIFO가 있는 IMU면 샘플 번호나 FIFO 카운트를 채널로 노출하는 것이 품질 툴을 위한 배려다.
  • V4L2 드라이버(I5, Q2): vb2_buffer_done() 전에 sequence를 버린 프레임까지 세어 채워야 한다. 에러 프레임은 VB2_BUF_STATE_ERROR로 돌려서 유저가 V4L2_BUF_FLAG_ERROR를 보게 한다.
  • 네트워크·CAN 드라이버(I6, I10): 수신 시각은 가능하면 HW 타임스탬프(skb_hwtstamps)로, 드롭은 netdev 통계(rx_dropped, rx_over_errors)로 노출한다. ip -s link show can0가 그 숫자다(Q4).

12. Embedded 실무에서 다시 보기#

12.1 장면 1 — 새 IMU 보드 bring-up의 "끝" 판정#

P1 노트의 bring-up 순서에서 드라이버가 probe되고 iio_info에 채널이 보이면 끝난 것처럼 느껴진다. 실제로는 여기서 품질 측정을 한 번 돌려야 "됐다"고 말할 수 있다. 예를 들어 센서 키트의 BMI088을 1 kHz로 설정했다면:

  • sdq.py iio --rate 1000 --secs 600을 idle에서 한 번, stress-ng --cpu N과 카메라 스트리밍을 같이 돌리면서 한 번.
  • 판정: rate 오차가 데이터시트 ODR 허용치 안, lost_by_ts = 0, jitter p99 < 주기의 10 %, ts_backwards = 0.
  • 이 결과 JSON을 bring-up 보고서에 붙인다. 숫자가 없는 "잘 됩니다"는 HW 팀과 인지 팀 둘 다 믿지 않는다.

12.2 장면 2 — 카메라 드롭이 "가끔" 난다는 버그 리포트#

인지 팀이 "SLAM이 가끔 튄다"고 한다. 순서는 이렇다.

  1. 카메라 노드 앞단에 V4L2 어댑터를 붙여 sequence gap을 센다. gap이 있으면 드라이버/버퍼 문제, 없으면 그 뒤(ROS 2 전송, Q6)의 문제다.
  2. gap이 있으면 --nbufs를 바꿔 본다. 버퍼 수를 늘려 사라지면 소비자가 늦는 것(6.3절 C와 같은 상황)이고, 그대로면 드라이버·CSI 수신기 쪽 드롭(Q2: CSI 에러 카운터, media-ctl 링크 상태)이다.
  3. 같은 시간대의 CPU 부하·온도(I4: thermal throttling)와 상관을 본다. 헬스 모니터의 metrics가 시계열로 쌓여 있으면 이 단계가 몇 분 만에 끝난다.

12.3 장면 3 — CAN 모터 컨트롤러의 rolling counter#

로봇 관절 컨트롤러(MCU, O3 노트)가 500 Hz로 상태 프레임을 보낸다. 프로토콜에 4비트 counter + CRC8이 있다. Linux 쪽 수집 데몬은:

  • seq_mod=16으로 손실·중복을 세고, 16개 이상 연속 손실은 시각 gap으로 잡는다.
  • SO_RXQ_OVFL로 Linux 소켓이 버린 것과 counter로 본 버스·MCU 쪽 손실을 구분한다. 소켓 drop이 0인데 counter gap이 있으면 원인은 Linux 바깥(버스 에러, MCU 과부하)이다. ip -s -d link show can0의 bus-error·restart 카운터를 같이 본다(Q4).
  • 헬스 모니터가 FAULT면 제어 루프에 "센서 신뢰 불가"를 알려 안전 정지로 보낸다. 국방·차량 로봇에서는 이 경로가 기능 안전 요구사항이 된다.

12.4 장면 4 — 생산 라인과 필드#

생산 테스트(P6)에서는 장비마다 60초 품질 측정을 돌려 JSON을 남기고 sdq_check의 스펙으로 합격·불합격을 낸다. 필드에서는 헬스 모니터 metrics를 원격 수집해서 장비 집단 통계(어떤 로트의 IMU가 rate 오차가 크다, 어떤 펌웨어 버전 이후 카메라 드롭이 늘었다)를 본다. SSD 양산에서 SMART 로그를 모아 불량 로트를 찾던 것과 같은 일이다.

14. 면접에서 이렇게 말한다#

Q. "How would you verify that an IMU really delivers 1 kHz data without drops?"

A. 버퍼에서 타임스탬프를 오래(수 분~수 시간) 읽어서 세 가지를 본다. 끝점으로 계산한 rate의 ppm 오차, 간격 분포의 p50/p99/max, 그리고 1.5주기를 넘는 gap 개수와 그로 추정한 손실. 센서가 샘플 번호나 FIFO 카운트를 주면 그걸로 손실을 정확히 센다. idle과 부하 상태를 둘 다 측정하고, IIO는 kfifo overflow를 알려 주지 않으니 "에러가 없다"를 증거로 쓰지 않는다.

I'd stream the buffered timestamps for minutes, not seconds, and report three things: rate error in ppm from the endpoints, the period distribution — p50, p99 and max, not just the mean — and the number of gaps over 1.5 periods with the implied lost samples. If the sensor exposes a sample counter, I use it for exact loss counting. I run it idle and under CPU and I/O load, because IIO's kfifo drops silently when full, so "no errors in dmesg" proves nothing.

꼬리 질문: "타임스탬프는 어디서 찍히나?" → hard IRQ에서 iio_pollfunc_store_time으로 찍으면 스레드 스케줄 지연이 빠진다. FIFO 배치면 마지막 샘플 시각에서 ODR로 역산한다(I2).

Q. "What does 'data quality' mean for a sensor platform? Give concrete metrics."

A. 시간 축(rate 오차, jitter, gap·손실, 중복, 순서, 타임스탬프 단조성, 시계 도메인, 지연), 값 축(NaN, 범위, stuck, 포화), 센서 사이(sync 오차, 잔차 일관성)로 나눠 말한다. 각각 검출 공식이 있다고 덧붙인다.

I split it into three groups. Timing: rate accuracy, jitter, gaps and drops, duplicates, ordering, timestamp monotonicity, clock-domain consistency and latency. Values: NaN, out-of-range, stuck or saturated readings. Cross-sensor: synchronization error and physical consistency, like wheel odometry versus integrated IMU. Each one maps to a concrete detector on the timestamp, sequence or value stream.

Q. "How do you compute p99 latency on a device running for weeks without unbounded memory?"

A. 로그 간격 히스토그램을 쓴다. 경계를 고정하고 칸 개수만 세면 메모리가 고정되고, percentile은 누적 개수로 칸을 찾아 상단 경계로 답한다. 칸 폭이 오차 한계다. 평균·분산은 Welford로 누적한다.

A fixed log-spaced histogram — say fifty bins per decade from a microsecond to ten seconds. That's a few kilobytes forever. Percentiles come from the cumulative counts, with the bin width as the error bound, about five percent here. Mean and variance use Welford's online update, which is numerically stable. It's the same idea as HdrHistogram or a Prometheus histogram.

Q. "Your camera pipeline drops frames occasionally. How do you find out where?"

A. V4L2 sequence gap으로 드라이버 단계 드롭인지 먼저 가른다. gap이 있으면 버퍼 수를 늘려 소비자 지연인지 드라이버·수신기 드롭인지 구분하고, 없으면 그 뒤 전송(ROS 2 등)을 본다. 부하·온도와의 상관을 metrics 시계열로 확인한다.

First, split the pipeline at the V4L2 boundary: dequeued buffers carry a sequence number, and the convention is that dropped frames still advance it. If there are sequence gaps, I vary the number of queued buffers — if more buffers make it go away, the consumer is too slow; if not, it's the driver or CSI receiver. If there are no gaps, the loss is downstream, in the middleware. Then I correlate with CPU load and temperature from the health metrics.

Q. "How would you build a health monitor for sensors on a robot, and what happens when it detects a fault?"

A. 1초 창 판정 + 히스테리시스 상태 기계(OK/DEGRADED/FAULT), systemd Type=notify + WatchdogSec, FAULT에서는 ping을 멈춰 재시작 경로를 타게 하고, StartLimitBurst로 재시작 루프를 끊고 경보로 넘긴다. metrics와 journal priority로 바깥에 알린다. 제어 쪽에는 센서 신뢰 상태를 넘겨 안전 정지 판단에 쓰게 한다.

A daemon that judges one-second windows — rate, sequence gaps, max interval — and drives a state machine with hysteresis so it doesn't flap. It runs as a systemd notify service with a watchdog; it only pets the watchdog while data is healthy, so a persistent fault triggers the standard restart path, and a start limit turns a restart loop into a failed unit that raises an alert. It also exports metrics and logs at warning priority, and publishes a sensor-trust flag so the controller can decide on a safe stop.

Q. "Two sensors' timestamps disagree by a few milliseconds that slowly grow. What's going on?"

A. 서로 다른 발진기로 시각을 찍고 있거나, 서로 다른 시계 도메인을 변환 없이 섞은 것이다. 천천히 커지는 차이는 ppm 차이(주파수 오차)이고, 계단식 점프는 시계 스텝(NTP)이다. 공통 시계(PTP PHC, PPS)에 묶거나 변환 계층을 둔다. Allan deviation으로 어떤 시간 척도에서 떠도는지 본다.

A slowly growing offset is a frequency difference — the two timestamp sources run on different oscillators, so it grows at the ppm difference. A sudden jump would instead be a clock step, like NTP adjusting CLOCK_REALTIME. The fix is a common timebase — PTP hardware clock or PPS discipline — or an explicit conversion layer, and I'd check stability over time scales with an Allan deviation plot.

Q. "How do you keep data-quality from regressing release to release?"

A. 품질 리포트를 CI 산출물로 만든다. 합성 스트림 단위 테스트로 검출기 자체를 지키고, HIL 장비에서 고정 시나리오(idle, 부하)로 리포트를 만들어 스펙 파일과 비교해 실패면 빌드를 막는다. 추세는 대시보드에 쌓는다(P6).

Treat the quality report as a CI artifact. Unit tests with synthetic streams where the right answer is known protect the detectors themselves. On hardware-in-the-loop rigs, fixed scenarios — idle and loaded — produce a JSON report that's checked against a spec file; any violation fails the pipeline. Trends go to a dashboard so slow drifts are visible before they cross a limit.

17. 요약 & 체크리스트#

센서 데이터 품질은 "값이 나온다"가 아니라 "값이 약속한 시각에, 빠짐없이, 같은 시계로, 말이 되는 값으로 나온다"를 숫자로 증명하는 일이다. 증명의 재료는 타임스탬프·순번·값·도착 시각 네 가지뿐이고, 커널은 대부분의 경로에서 조용히 데이터를 버리므로 툴은 순번과 시각으로 손실을 추론해야 한다. 재사용 가능한 툴은 입력별 어댑터와 하나의 고정 메모리 통계 엔진으로 나누고, 정답을 아는 합성 스트림으로 엔진부터 검증한다. 그 다음 실제 장치에 결함을 일부러 넣어(부하, rate 변경, 작은 버퍼, 느린 소비자, 시계 스텝, 중복 송신자) 툴이 각 결함을 다른 지표로 잡는지 확인한다. 장비 위에서는 같은 엔진을 1초 창 + 히스테리시스 상태 기계로 돌려 systemd watchdog·metrics·journal로 바깥과 연결하고, CI에서는 같은 리포트를 스펙과 비교하는 게이트로 쓴다.
