0. 큰 그림 — 이게 왜 필요한가#

0.1 1 ms = 2 cm — 시간 오차는 곧 위치 오차다#

센서 퓨전 알고리즘(EKF, VIO, LiDAR-camera 투영)은 모든 측정값에 "이 값은 시각 t의 세상이다" 라는 꼬리표가 붙어 있다고 가정한다. 꼬리표가 틀리면 알고리즘은 틀린 위치의 세상을 본다. 계산은 단순하다.

  • 위치 오차 = 속도 × 시간 오차. 20 m/s(72 km/h) 차량에서 1 ms 오차 → 2 cm.
  • 회전 오차 = 각속도 × 시간 오차. 드론 yaw rate 180 °/s에서 1 ms → 0.18°. 카메라 화각 90°·가로 1920 px면 1 px ≈ 0.047°이니 약 4 px가 밀린다.
  • LiDAR 점을 카메라 영상에 투영할 때 10 ms 어긋나면, 20 m/s에서 20 cm — 보행자 한 명의 폭이 어긋난다.

그래서 시스템 설계 첫 단계에 시간 오차 예산(error budget) 을 잡는다. 예를 들어 센서 키트라면 "카메라-IMU 상대 오차 < 0.5 ms, LiDAR-카메라 < 1 ms, 장비 간 절대 시각 < 10 µs" 같은 식이다.

1.3 함정 — 어떤 시계를 쓸지 섞지 마라#

  • IIO의 기본 타임스탬프 시계는 CLOCK_REALTIME 이다(I2 §10에서 6.18 소스로 확인). evdev도 기본이 REALTIME. bring-up 체크리스트에 echo monotonic > /sys/bus/iio/devices/iio:deviceN/current_timestamp_clock을 넣는다.
  • V4L2는 거의 항상 V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC(I5 §6). 즉 기본값 그대로 두면 IMU는 REALTIME, 카메라는 MONOTONIC — 두 축이 부팅 시각(약 1.79e9 s)만큼 다르다. 정렬 코드가 "IMU 샘플이 하나도 안 맞는다"며 버린다.
  • REALTIME을 퓨전에 쓰면 PTP/NTP가 첫 동기 때 수 초를 step 하는 순간 dt가 음수 또는 수 초가 된다.

2. 1층 — 샘플링 순간을 맞춘다: HW trigger와 frame sync#

2.1 왜 타임스탬프만으로는 부족한가#

카메라 두 대가 각자 30 fps로 free-run 하면, 두 셔터 사이의 위상차는 0~33 ms 사이 아무 값이고 천천히 흘러간다(두 크리스털의 ppm 차이 때문에). 타임스탬프를 완벽하게 찍어도 두 영상은 다른 순간의 세상이다. 스테레오 깊이 계산은 같은 순간의 두 영상이 필요하니, 보간으로 해결이 안 된다(영상은 보간할 수 없다). 그래서 노출 자체를 같은 엣지에 묶는다.

2.3 Linux SoC가 trigger를 직접 만들 때#

  • PWM(I9): /sys/class/pwm/pwmchipN/pwm0/{period,duty_cycle,enable}. 간단하지만 PWM 클럭은 시스템 시각과 묶여 있지 않아 위상이 시각과 무관하고 드리프트한다.
  • PHC perout: NIC의 PTP 하드웨어 시계가 "PTP 시각 정각마다" 펄스를 낸다(PTP_PEROUT_REQUEST2 ioctl, testptp -p, 또는 sysfs /sys/class/ptp/ptpN/period). 펄스가 PTP로 맞춘 시각에 위상 고정되므로, 여러 장비가 같은 순간에 trigger한다. 차량·로봇에서 가장 깔끔한 방법이다. 핀 할당은 /sys/class/ptp/ptpN/pins/ 또는 PTP_PIN_SETFUNC.
  • GPIO 토글을 유저 공간 루프로: 하지 마라. 스케줄링 지터(N3에서 측정한 수십 µs~ms)가 그대로 trigger 지터가 된다. 꼭 SoC가 해야 하면 PREEMPT_RT + hrtimer 커널 모듈, 또는 보조 Cortex-M 코어(O1/O3)에 맡긴다.

확인 범위: perout sysfs·ioctl 이름은 6.18 drivers/ptp/ptp_chardev.c·ptp_sysfs.c·include/uapi/linux/ptp_clock.h에 있다. 이 랩의 mock PHC는 n_per_out=0이라 perout을 실제로 돌려 보지는 못했다(§8 출력).

2.4 함정#

  • trigger 모드 센서에서 trigger 주기가 "노출 + readout"보다 짧으면 프레임이 조용히 건너뛰어진다 → V4L2 sequence 틈(I5 §7)으로 잡는다.
  • SerDes 링크로 전달된 FSYNC에는 링크 고정 지연(수 µs, 기억 기반)이 있다. 모든 카메라가 같은 SerDes 구성이면 상쇄되지만, 카메라마다 케이블·칩이 다르면 측정해서 보정한다.
  • trigger로 노출을 맞춰도 타임스탬프를 소프트웨어로 찍으면 2층에서 다시 흔들린다. 1층과 2층은 별개다.

③ hardirq 진입대부분의 V4L2 드라이버(SOF/EOF IRQ에서 ktime_get_ns()), IIO iio_pollfunc_store_time쉬움, MONOTONICIRQ 지연(µs) + IRQ 끄인 구간만큼 흔들림

V4L2 버퍼의 flags에는 시계 종류와 프레임의 어느 순간인지가 들어 있다(6.18 include/uapi/linux/videodev2.h).

플래그값뜻

V4L2_BUF_FLAG_TIMESTAMP_COPY0x4000m2m: 입력 버퍼 시각을 복사했을 뿐

6.18 소스에서 실제로 TSTAMP_SRC_SOE를 선언하는 드라이버는 uvc_queue.c(V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC | V4L2_BUF_FLAG_TSTAMP_SRC_SOE)와 vivid뿐이었다(grep -rln TSTAMP_SRC_SOE drivers/media). 재미있는 사례: Raspberry Pi 5의 rp1-cfe.c는 cfe_sof_isr()에서 node->ts = ktime_get_ns()로 프레임 시작에 찍지만, 큐의 timestamp_flags는 V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC뿐이라 플래그상으로는 EOF(0)다. 플래그를 믿지 말고 드라이버 코드를 읽어라 — 면접에서 쓸 만한 이야기다.

실무 공식(롤링 셔터, 기억 기반 일반식): 노출 중심 시각 ≈ SOF − 노출 시간 + 노출 시간/2 + 줄 번호 × 라인 시간. SOF가 "첫 줄 readout 시작"이라면 첫 줄 노출은 그보다 노출 시간만큼 먼저 시작했다. 정의는 센서·드라이버마다 다르니 LED 깜빡임 실험(§11.3)으로 실측한다.

vivid로 SOE/EOF 차이를 직접 보는 실험은 I5 §6에 있다(이 노트에서는 반복하지 않는다).

3.3 IIO, 네트워크#

  • IIO: 트리거 핸들러의 top half iio_pollfunc_store_time()이 pf->timestamp = iio_get_time_ns()를 찍는다(I2 §5, §10). FIFO 센서는 watermark IRQ 한 번에 N개 샘플이 오니, 마지막 샘플 시각에서 ODR 주기로 거꾸로 계산하고, 칩 내부 타이머(예: st_lsm6dsx의 HW timestamp)를 쓰는 드라이버도 있다(I2 §11).
  • 네트워크(LiDAR, PTP): SO_TIMESTAMPING으로 SW/HW 타임스탬프를 받는다(A9, I6 §9). HW RX 타임스탬프는 PHC 시간축이고, SW는 REALTIME이다.

5. 3층 — 시계 도메인과 변환#

5.1 한 시스템 안에도 시계가 여럿이다#

센서 키트 하나에 독립된 발진기가 몇 개 있는지 세어 보면: SoC 카운터(→ CLOCK_MONOTONIC), NIC의 PHC(별도 크리스털 또는 같은 PLL), LiDAR 내부 시계, IMU 내부 ODR 발진기, 카메라 센서 픽셀 클럭, GNSS 수신기의 원자시 기반 시계. 각자 수~수십 ppm씩 다르게 흐른다. 20 ppm 차이면 1초에 20 µs, 1분에 1.2 ms 벌어진다 — 몇 분이면 오차 예산을 넘는다.

그림 5 — 시계 도메인: 외부 기준 → PHC → 시스템 시계 → 센서 타임스탬프. 화살표 위가 그 변환을 맡는 프로그램

5.2 변환의 원리 — "같은 순간에 두 시계를 읽는다"#

두 시계 A, B 사이를 변환하려면 같은 순간의 (A값, B값) 쌍이 필요하다. 그런데 두 시계를 동시에 읽을 수는 없으니 샌드위치로 읽는다: B를 읽고(b1) → A를 읽고(a) → B를 다시 읽는다(b2). 그러면 a는 대략 (b1+b2)/2 순간의 값이고, 불확실성은 (b2−b1)/2다. 여러 번 해서 창(window)이 가장 짧은 샘플을 쓴다. phc2sys가 PHC와 시스템 시계 사이에서 하는 일이 정확히 이것이고(§8의 예제 7), PTP가 네트워크 너머 두 시계 사이에서 하는 일도 같은 생각을 패킷으로 한 것이다(§6).

하드웨어가 도와주는 방법도 있다(기억 기반·커널 API는 6.18에서 확인): PTP_SYS_OFFSET_PRECISE(getcrosststamp) — Intel의 ART(Always Running Timer) 같은 공통 카운터로 PHC와 시스템 카운터를 한 번에 래치한다. 창이 0이다.

9. PPS — 1초에 한 번, 정확한 엣지#

9.1 개념#

PPS(Pulse Per Second)는 GNSS 수신기·원자 시계·GM이 내보내는 매 초 정각의 엣지다. 엣지 자체에는 "몇 시 몇 분 몇 초"가 없다 — 그건 NMEA/UBX 문장이나 PTP가 알려 준다. PPS는 위상(초의 경계) 을 ns~수십 ns 정확도로, NMEA는 어느 초인지를 ms~100 ms 지터로 알려 준다. 둘을 합치면 정확한 절대 시각이 된다.

Linux의 PPS 서브시스템(drivers/pps/, RFC 2783 API):

소스 드라이버엣지를 어디서 받나정확도 감각
pps-gpioGPIO IRQ, DT compatible = "pps-gpio"IRQ 지연만큼 흔들림(µs, 기억 기반)
pps-ldisc시리얼 포트 DCD 핀 (line discipline)시리얼 IRQ 지연
PHC extts → PPSNIC 타이머 캡처 입력 (ptp_clock_event PTP_CLOCK_PPS)HW 캡처, ns급
pps-ktimer커널 timer_list (테스트용)jiffies 해상도 — 정확하지 않음

유저 공간: /dev/ppsN의 ioctl(PPS_GETPARAMS, PPS_SETPARAMS, PPS_GETCAP, PPS_FETCH), sysfs /sys/class/pps/ppsN/{assert,clear,mode,name,path}, 도구 ppstest/ppswatch(pps-tools), 소비자 chrony(refclock PPS), gpsd, ts2phc.

  • 타이머 콜백이 실행된 그 순간부터 다시 jiffies + HZ 뒤로 예약한다(상대 재무장). 초 경계에 고정된 게 아니다.
  • timer_list는 timer wheel 위에 있어서 1초(250 tick) 뒤 만료는 레벨 1 버킷(8 tick = 32 ms 단위)으로 반올림돼 늦게 터진다(F8 §6.5). 그래서 주기가 1.016~1.031 s가 되고 위상이 계속 밀린다.
  • 타임스탬프는 pps_get_ts() → ktime_get_snapshot()의 REALTIME 값이다. 실제 pps-gpio도 IRQ 핸들러 맨 앞에서 같은 함수를 부른다 — 차이는 엣지가 정확하냐뿐이다.

즉 pps-ktimer는 API·도구 연습용이지 시간 기준이 아니다. 모듈 설명 자체가 "dummy PPS source by using a kernel timer (just for debug)"다.

9.5 PPS를 PHC에 직접 — ts2phc#

NIC에 extts 입력이 있으면 GNSS PPS를 NIC 핀에 꽂고 ts2phc가 PHC를 PPS에 맞춘다. PPS 엣지가 하드웨어 캡처(ns급)로 찍히고, 그 PHC가 ptp4l GM으로 네트워크에 시각을 뿌린다. 차량·로봇 GM의 정석 구성이다(가이드, 실행 안 함 — mock PHC는 n_ext_ts=0).

확인 범위: 설정 키 이름(ts2phc.nmea_serialport, ts2phc.pulsewidth, ts2phc.extts_polarity, -s nmea 소스)은 rootfs-dom의 linuxptp 4.0 ts2phc 바이너리 문자열로 확인했다(이 rootfs에는 man 페이지가 없다). 같은 바이너리에 UTC-TAI offset not set in system! Trying to revert to leapfile이라는 메시지가 있다 — §1의 tai=0 문제를 ts2phc도 신경 쓴다는 뜻이다. 실행은 하지 않았다.

10. GNSS로 시스템 시계를 맞추기 — chrony + gpsd (Q5 연결)#

PHC가 없는 장비(작은 SoC, USB GNSS)에서는 chrony가 gpsd의 NMEA 시각(대략적인 초)과 커널 PPS(정확한 위상)를 결합한다. gpsd 쪽 설정·UBX 프로토콜·gpsfake는 Q5에서 다룬다. 이 노트는 시간 쪽만 본다(가이드, 실행 안 함 — 이 랩에는 실제 GNSS 엣지가 없고 pps-ktimer는 위상이 흘러가서 chrony가 거부한다).

  • SHM 0: gpsd가 공유 메모리 세그먼트 0에 NMEA 기반 시각을 써 준다. 지터가 크니 noselect로 직접 쓰지 않고,
  • PPS ... lock NMEA: PPS 엣지가 "어느 초"인지를 NMEA에서 빌려 와 결합한다.
  • makestep 1.0 3: 부팅 직후 처음 3번은 1 s 넘게 틀리면 step. 그 뒤로는 slew만 — 센서 녹화 중에 시계가 점프하지 않게 하는 설정이다.
  • PHC가 있으면 chrony가 PHC를 직접 refclock으로 쓸 수도 있다: refclock PHC /dev/ptp0 poll 0 dpoll -2 offset 37(PHC가 TAI일 때 37 s 보정. 기억 기반 설정 예시 — chrony.conf(5)로 확인).
  • 확인 명령: chronyc sources -v, chronyc tracking(System time, Frequency, Skew), gpspipe -r.

11. TSN qdisc 맛보기 — taprio와 etf#

시간 동기가 서면 "언제 보낼지"도 시각으로 정할 수 있다. TSN(Time-Sensitive Networking)의 두 qdisc:

  • taprio(802.1Qbv): 시간 슬롯마다 어떤 트래픽 클래스의 게이트를 열지 정하는 주기 스케줄. 예: 1 ms 주기 중 앞 300 µs는 제어 트래픽만.
  • etf(Earliest TxTime First): 패킷마다 SO_TXTIME으로 "이 시각에 보내라"를 지정. 소켓이 SCM_TXTIME cmsg로 시각을 붙인다.

둘 다 clockid CLOCK_TAI를 쓴다 — §1의 tai=0 함정이 여기서 다시 나온다. 하드웨어 오프로드(offload on, igc·stmmac·enetc 등)가 없으면 소프트웨어로 동작해 정확도가 µs~ms 수준이다.

12.3 시스템 시계 보정의 끝 — adjtimex#

ptp4l(SW 모드), phc2sys(-c CLOCK_REALTIME), chronyd는 결국 모두 clock_adjtime(CLOCK_REALTIME, ...)(= adjtimex)로 커널 timekeeping의 주파수(freq) 를 바꾸거나 오프셋을 한 번에 더한다(ADJ_SETOFFSET). timekeeping 코어(kernel/time/timekeeping.c, ntp.c)는 clocksource의 mult를 조금씩 바꿔 REALTIME과 MONOTONIC의 속도를 함께 바꾼다. 그래서:

  • PTP가 slew하면 MONOTONIC도 같이 빨라지거나 느려진다(예제 1의 MONOTONIC − RAW = 42 s가 증거). 센서 타임스탬프(MONOTONIC)가 PTP 시간축과 같은 속도로 흐르게 된다 — 이게 "MONOTONIC으로 찍고 REALTIME/TAI로 변환"이 가능한 이유다.
  • step(ADJ_SETOFFSET, clock_settime)은 REALTIME만 점프시키고 MONOTONIC은 건드리지 않는다.

Q. How do you time-synchronize a camera, an IMU and a LiDAR on a robot?

A. 세 층으로 나눠 답한다. 먼저 샘플링 순간 — 카메라끼리는 HW trigger/frame sync로 노출을 같은 엣지에 묶고, IMU는 그 펄스를 sync 입력으로 받는다. 둘째, 타임스탬프 — 드라이버가 SOF IRQ나 FIFO IRQ에서 CLOCK_MONOTONIC으로 찍고, 앱이 now()를 찍지 않게 한다. 셋째, 시계 정렬 — LiDAR는 PTP slave로 두고, SoC는 GNSS PPS로 PHC를 맞춰 GM이 되고, phc2sys로 시스템 시계를 PHC에 맞춘다. 그러면 모든 타임스탬프를 하나의 시간축으로 변환할 수 있다.

I split it into three layers. First, make the samples happen at the same instant: the cameras share a hardware trigger or frame-sync line, ideally generated by the NIC's PHC as a periodic output so it's phase-locked to PTP time, and the IMU takes the same pulse on its sync input. Second, timestamp as early as possible: the camera driver stamps at the start-of-frame interrupt and the IMU driver at the FIFO interrupt, both in CLOCK_MONOTONIC, never in the application. Third, align the clocks: the LiDAR is a PTP slave, the SoC disciplines its PHC to GNSS PPS with ts2phc and acts as grandmaster, and phc2sys steers the system clock to the PHC. Then every timestamp can be mapped to one timeline, and I verify the residual offset with an LED or PPS test.

꼬리 질문: "Why not just timestamp in user space when the frame arrives?" → 지연이 일정하지 않아서(스케줄링·버퍼링) 보정이 안 된다. 내 측정에서 SW 스탬프는 평균 0.64 ms인데 최대 오차가 80 cm였다(20 m/s).

Q. Explain how PTP computes the clock offset.

A. master가 Sync를 t1에 보내고 slave가 t2에 받는다. slave가 Delay_Req를 t3에 보내고 master가 t4에 받는다. 오프셋 = ((t2−t1) − (t4−t3))/2, 경로 지연 = ((t2−t1) + (t4−t3))/2. 두 방향 지연이 같다는 가정이 있어서, 비대칭의 절반이 그대로 오프셋 오차가 된다. two-step이면 t1은 Follow_Up으로 온다.

The master sends Sync at t1 and the slave receives it at t2; the slave sends Delay_Req at t3 and the master receives it at t4 and returns t4 in Delay_Resp. With a two-step clock t1 comes in a Follow_Up. Offset is ((t2 minus t1) minus (t4 minus t3)) over two and mean path delay is the sum over two. The key assumption is a symmetric path: half of any asymmetry shows up directly as offset error, and PTP can't detect it, so you remove it with hardware timestamps and transparent or boundary clocks, and calibrate the remaining fixed asymmetry.

Q. What's the difference between hardware and software timestamping, and how do you check what a NIC supports?

A. SW는 커널 네트워크 스택에서 찍어서 IRQ·coalescing·스케줄링 지연이 들어가고, HW는 MAC/PHY가 SFD 순간 PHC를 래치한다. ethtool -T로 hardware-transmit/receive 모드와 PHC 번호를 본다. 내 QEMU 랩에서 SW PTP는 오프셋 중앙값 0.8 ms에 116 ms 스파이크까지 났고, 같은 기계 안 PHC-시스템 동기(phc2sys)는 ±100 ns였다.

Software timestamps are taken in the network stack, so they include interrupt latency, coalescing and scheduling noise; hardware timestamps are latched by the MAC or PHY when the start-of-frame delimiter crosses the wire, in the PHC's timebase. ethtool -T shows the capabilities and the PHC index. In my emulated lab, software PTP between two VMs had a median offset of about 0.8 ms with a 116 ms spike from a host stall, while phc2sys between a PHC and the system clock in the same machine held about plus or minus 100 ns — the timestamp location dominates the accuracy.

Q. Which clock should sensor timestamps use, and why not CLOCK_REALTIME?

A. MONOTONIC. REALTIME은 NTP/PTP의 step이나 date -s로 점프해서 dt가 음수가 될 수 있다. MONOTONIC은 점프하지 않지만 NTP/PTP가 속도를 같이 보정하므로 PTP 시간축과 같은 속도로 흐른다. 절대 시각이 필요하면 MONOTONIC→REALTIME/TAI 오프셋을 같이 기록한다. IIO 기본이 REALTIME이라는 함정도 말한다.

CLOCK_MONOTONIC. REALTIME can step when NTP or PTP first locks or someone sets the date, which gives negative dt to the fusion filter. MONOTONIC never jumps, but the kernel slews its rate together with REALTIME, so it runs at the disciplined rate. If I need absolute time I log the MONOTONIC-to-TAI offset alongside. One gotcha: IIO and evdev default to REALTIME, so the bring-up checklist switches them to monotonic.

Q. What do ptp4l's s0, s1, s2 mean, and what does "clock frequency changed unexpectedly" tell you?

A. s0은 servo unlocked(주파수 추정 중), s1은 step 한 번, s2는 locked(주파수만 slew). clockcheck 경고는 다른 프로세스가 같은 시계를 조정한다는 뜻 — chronyd나 timesyncd, 두 번째 ptp4l. 랩에서 실수로 ptp4l 두 개를 띄웠을 때 정확히 이 메시지가 매초 나왔다.

s0 is unlocked while the servo estimates the frequency, s1 is the one-time step, and s2 is locked, where it only slews frequency. The clockcheck warning means something else is adjusting the same clock — usually chronyd, timesyncd or a second ptp4l or phc2sys instance. I reproduced it by accident with two ptp4l instances on one VM; the rule is one servo per clock.

Q. How would you add a PPS input from a GNSS module to a Linux board?

A. 가능하면 NIC의 extts 핀에 넣어 ts2phc로 PHC를 맞춘다(HW 캡처). 아니면 GPIO에 넣고 DT에 pps-gpio 노드를 쓴 다음 ppstest로 간격 흔들림을 확인하고, chrony에서 gpsd의 NMEA(SHM)와 lock으로 묶는다. 엣지 극성, 레벨 시프터 지연, NO_HZ라 hardpps가 없다는 점도 챙긴다.

Best is to route it to a PHC external-timestamp pin and run ts2phc, so the edge is captured in hardware. Otherwise I put it on a GPIO with a pps-gpio device tree node, check the interval jitter with ppstest, and feed chrony a PPS refclock locked to gpsd's NMEA time through SHM. I check the edge polarity, any level-shifter delay, and that the kernel's hardpps path isn't available on NO_HZ kernels, so chrony does the disciplining in user space.

Q. Two cameras are free-running at 30 fps with perfect timestamps. Is that good enough for stereo?

A. 아니다. 타임스탬프가 정확해도 두 노출은 0~33 ms 다른 순간이고 영상은 보간할 수 없다. 노출 자체를 trigger/frame sync로 묶어야 한다. IMU처럼 연속 신호는 보간이 되지만 영상은 안 된다.

No. Perfect timestamps only tell you how far apart the exposures were; with free-running sensors the phase drifts anywhere within 33 ms, and you can't interpolate an image. For stereo the exposures themselves must be locked with a shared trigger or master-slave frame sync. Interpolation works for continuous signals like IMU data, not for pixels.

Q. What accuracy can you expect from PTP, and what limits it?

A. HW 타임스탬핑 + PTP 인식 스위치면 수십 ns 이하, SW면 µs~수십 µs(실제 HW 기준, 기억 기반). 한계는 타임스탬프 위치, 경로 비대칭, 스위치 큐(TC/BC 없을 때), 발진기 잡음과 servo 대역폭, sync 주기. gPTP는 7홉에서 1 µs 목표.

With hardware timestamping and PTP-aware switches, tens of nanoseconds or better; with software timestamps, microseconds to tens of microseconds on real hardware. The limits are where the timestamp is taken, path asymmetry, queuing in switches that aren't transparent or boundary clocks, oscillator noise versus servo bandwidth, and the sync interval. 802.1AS targets about a microsecond across seven hops.

16. 직접 해보기#

  1. 오차 예산 계산: 드론이 15 m/s, yaw rate 120 °/s로 난다. 카메라(화각 80°, 가로 1280 px)와 IMU 사이 허용 시간 오차는 위치 1 cm, 회전 1 px 기준으로 각각 얼마인가? 정답/힌트: 위치 1 cm / 15 m/s ≈ 0.67 ms. 1 px = 80/1280 = 0.0625°, 0.0625 / 120 ≈ 0.52 ms. 더 빡빡한 쪽(0.52 ms)이 예산이다.
  2. 비대칭: q3_ptpcalc를 고쳐 Sync 경로에만 0~2000 ns 균일 분포 지연(큐잉)을 넣고 1000번 반복해 offset 오차의 평균과 표준편차를 출력하라. 평균은 왜 0이 아닌가? 정답/힌트: 오차 = (d_ms − d_sm)/2이므로 평균 지연 1000 ns의 절반인 +500 ns가 바이어스로 남는다. 최소값 필터(가장 작은 지연 샘플 사용)를 쓰면 줄어든다.
  3. ptp4l 설정 실험: 게스트 두 대 실습에서 slave에 --step_threshold=0.002를 주고 다시 돌려 보라. §7.4의 116 ms 스파이크 같은 상황에서 무엇이 달라지나? 왜 센서 녹화 중에는 위험한가? 정답/힌트: s2에서도 2 ms를 넘으면 step한다. 스파이크(가짜 오프셋)에 반응해 시계를 점프시킬 수 있어서 REALTIME 기반 데이터에 불연속이 생긴다. 녹화 중에는 slew만 하는 편이 안전하다.
  4. phc2sys 방향 바꾸기: netdevsim mock PHC를 기준으로 phc2sys -s /dev/ptp0 -c CLOCK_REALTIME -O 0 -m을 돌리고, 동시에 q3_clocks로 MONOTONIC − MONO_RAW가 변하는지 보라. 정답/힌트: phc2sys가 시스템 시계 주파수를 조정하면 MONOTONIC도 같은 비율로 바뀐다(§12.3). PHC에 phc_ctl freq 100000을 걸면 시스템 시계가 따라가며 MONOTONIC − RAW가 초당 약 100 µs씩 변한다.
  5. IIO 시계 확인: iio_dummy + hrtimer trigger(I2 §5)로 버퍼 캡처를 하면서 current_timestamp_clock을 realtime → monotonic으로 바꾸고, q3_align처럼 MONOTONIC 기준 스트림과 섞어 정렬이 깨지는/고쳐지는 것을 보여라. 정답/힌트: I2 §10의 i2clk 프로그램으로 샘플 ts가 어느 시계와 같은지 먼저 확인한다.
  6. PPS 간격 관찰: pps-ktimer를 올린 상태에서 q3_pps /dev/pps0 30을 돌리면서 다른 터미널에서 stress-ng --cpu 2 --timeout 20을 걸어라. 간격 오차 분포가 어떻게 변하나? timer wheel 반올림(최대 32 ms)과 부하 영향을 구분할 수 있나? 정답/힌트: 기본 분포는 +16~+31 ms(반올림)이고, 부하는 그 위에 꼬리를 더한다. HZ=250에서 1 s 타이머의 granularity는 8 tick = 32 ms다(F8 §6.5).
  7. 관찰 과제: 실제 장비나 노트북에서 ethtool -T <iface>, ls /sys/class/ptp/, cat /sys/class/ptp/ptp*/clock_name을 확인하고 HW 타임스탬핑 지원 여부를 표로 정리하라. 정답/힌트: 유선 Intel/Realtek NIC 다수는 PHC가 있고, Wi-Fi는 보통 SW만 있다. VM의 virtio-net은 PHC가 없다(이 노트 §7.1). KVM 게스트라면 ptp_kvm이 호스트 시계를 PHC로 노출할 수 있다(이 랩은 TCG라 해당 없음).

18. 요약 & 체크리스트#

멀티 센서 동기화는 세 층이다. (1) 샘플링 순간은 HW trigger와 frame sync(FSIN/XVS, SerDes FSYNC 전달, PHC perout)로 묶는다 — 영상은 보간할 수 없기 때문이다. (2) 타임스탬프는 파이프라인의 가능한 한 앞(센서·수신 HW·hardirq)에서 CLOCK_MONOTONIC으로 찍는다 — 늦게 찍은 SW 스탬프는 평균은 괜찮아도 가끔 수십 ms 튀어 cm~m 오차가 된다(예제 3). (3) 시계 정렬은 PPS(위상) + NMEA(초)로 외부 기준을 잡고, PTP(t1~t4, 대칭 가정)로 장비 사이를 맞추고, phc2sys로 PHC와 시스템 시계를 잇는다. 정확도는 프로토콜보다 타임스탬프 위치가 정한다: 이 랩에서 SW PTP는 ms급이었고, 같은 기계 안 PHC-시스템은 ±100 ns였다. 운영에서는 시계 하나에 servo 하나, pmc로 상태 감시, TAI 오프셋 설정을 지킨다.
