0. 큰 그림 — 이게 왜 필요한가#

제품 커널은 "upstream LTS + 벤더 BSP 패치 + 우리 패치"의 3층 케이크다(P2). 업그레이드란 이 케이크의 맨 아래층을 바꾸고 위 두 층을 다시 올리는 일이다. 아래층이 바뀌면 위층 패치 중 일부는 이미 아래층에 들어가 있고(upstreamed), 일부는 대상이 사라졌고(obsolete), 일부는 문맥이나 API가 바뀌어 손으로 고쳐야 하며(needs port), 나머지는 그대로 올라간다(keep). 이 분류를 먼저 하고, 옮기고, 고치고, 회귀를 확인하는 것이 업그레이드 프로젝트 전체다.

그림 1 — 커널 업그레이드 파이프라인. 1~3은 git 작업, 4는 사람이 판단하는 작업, 5~6은 자동화할수록 다음 업그레이드가 싸진다.

bare-metal 비유로 보면 이렇다. SSD 펌웨어에서 새 컨트롤러 세대로 넘어갈 때 "칩 벤더 HAL/SDK v2 → v3 + 우리 FTL 코드"를 옮기던 일과 같다. SDK가 함수 이름과 인자를 바꾸면 컴파일 에러가 할 일 목록이 되고, 우리가 SDK에 넣어 둔 핫픽스 중 일부는 v3에 이미 들어가 있고, 일부 기능은 v3에서 없어졌다. 차이는 두 가지다.

  • 리눅스 커널은 내부 API 안정성을 약속하지 않는다(Documentation/process/stable-api-nonsense.rst). 유저 공간 ABI(syscall, sysfs)는 지키지만, 드라이버가 쓰는 커널 내부 함수는 매 릴리스 바뀐다. 그래서 "in-tree에 들어간 드라이버는 API를 바꾸는 사람이 같이 고쳐 주고, out-of-tree 드라이버는 우리가 고친다".
  • 위층이 git 커밋 단위로 관리되므로 git이 분류의 절반을 자동으로 해 준다(patch-id 비교, 3-way merge). 나머지 절반은 사람이 의미를 판단한다.

  • 커널 모듈은 랩 커널 6.18.55-dom(/var/lab/out/Image-dom, 빌드 트리 linux-build-dom)으로 빌드하고 QEMU virt 게스트(TCG, KVM 없음)에서 insmod 했다. 19명이 VM을 같이 쓰는 중이라 부팅·실행 시간은 실제 하드웨어 값이 아니다.

1. LTS · stable 주기와 수명 — "언제까지 버틸 수 있나"#

E7 §1~§2에서 kernel.org 데이터로 직접 쟀다. 여기서는 업그레이드 판단에 필요한 것만 다시 정리한다.

1.1 트리 안 문서가 말하는 것#

먼저 커널 소스 자체가 stable·LTS를 어떻게 설명하는지 확인한다. 날짜는 바뀌어도 이 규칙은 잘 안 바뀐다.

출력에서 볼 것: (1) 일반 stable은 "한 개발 주기보다 조금 더" 산다(약 3개월, E7 측정 75~100일). (2) LTS 지정은 "maintainer가 필요와 시간이 있을 때"의 결정이라 트리 문서에는 수명이 적혀 있지 않다. 수명은 https://www.kernel.org/category/releases.html을 봐야 한다. (3) stable에 수정을 넣는 방법은 세 가지다(E7 §5.11). 10절에서 "받는 쪽"에서 이 태그를 쓴다.

1.2 LTS 수명 지도#

아래 그림의 시작일은 E7이 kernel.org 디렉터리 목록으로 잰 값(2026-10-03 기준 span에서 역산), EOL은 E7이 2026-10-10에 받은 releases.html의 projected EOL이다. CIP 연장선은 "LTS 시작 + 약 10년"으로 그린 개략치다(CIP가 공개하는 정확한 EOL은 CIP 웹사이트에서 확인 — 기억 기반).

그림 2 — 살아 있는 LTS 6개와 CIP SLTS 연장(5.10, 6.1, 6.12). 회색 막대(5.10·5.15)는 2026-12에 kernel.org 지원이 끝난다. 6.18이 랩 커널이다. CIP 브랜치 목록(4.4, 4.19, 5.10, 6.1, 6.12)은 E7 예제 6에서 git ls-remote로 확인한 값이다.

읽는 법:

  • 5.15 벤더 BSP 제품은 지금(2026-10) 두 달 남았다. contents.md 시나리오 "5.15를 6.x LTS로 올려라"가 바로 지금 해야 하는 일이다. EOL 뒤에도 커널은 동작하지만, CVE 수정이 더 이상 공짜로 오지 않는다.
  • 목표 LTS를 고를 때는 "우리 제품의 남은 수명 ≤ 목표 LTS의 남은 수명"이 되는 것을 고른다. 10년 장비면 CIP가 고른 버전(6.12)이 유리하다. 최신 6.18은 kernel.org 기준으로는 가장 길지만 CIP가 고를지는 아직 모른다(2026-10 기준 CIP 브랜치에 없음).
  • LTS 수명은 연장되기도 줄기도 한다. 처음 2년 예정이던 것이 수요가 있으면 늘어난다(E7 §2.1). 계획은 "projected EOL"로 세우되, 분기마다 releases.html을 다시 본다.

1.3 CIP SLTS 한 줄 정리#

CIP(Civil Infrastructure Platform, Linux Foundation 프로젝트)는 kernel.org LTS 중 일부를 골라 약 10년 유지한다. 브랜치는 linux-6.1.y-cip처럼 -cip 접미어가 붙고, 일정한 주기로 태그(v6.1.x-cipN)를 낸다(태그 형식은 기억 기반 — CIP 저장소로 확인 필요). 철도·전력·공장 장비처럼 "10년 넘게 필드에 있고 커널을 자주 못 올리는" 제품이 대상이다. 국방·차량 장비도 같은 고민을 하므로, 면접에서 "LTS 수명보다 제품 수명이 길면?"에 CIP를 꺼낼 수 있어야 한다. 단, CIP도 보드 지원은 CIP 참조 보드만 테스트한다 — 우리 BSP 패치는 여전히 우리 몫이다.

2. 왜 제품은 옛 커널에 갇히나#

2.1 갇히는 이유#

이유실제 모습업그레이드 때 비용
벤더 BSP가 그 버전에만 있다SoC 벤더가 5.15 BSP만 배포, 6.x BSP는 다음 해벤더가 새 BSP를 낼 때까지 기다리거나 직접 포팅
out-of-tree 드라이버NPU·카메라 ISP·Wi-Fi 바이너리 블롭 + 소스 일부내부 API 변경마다 우리가 고침 (6절)
패치 스택이 크다"핫픽스"가 수백 개 쌓였고 출처가 기록 안 됨분류에 시간이 대부분 든다 (3절)
인증·검증 비용차량·국방·의료는 커널을 바꾸면 재검증테스트 자동화가 없으면 수개월
유저 공간 의존오래된 사용자 도구가 사라진 sysfs·ioctl·debugfs를 씀커널은 ABI를 지키지만 debugfs·벤더 ioctl은 예외
담당자가 없다처음 BSP를 올린 사람이 퇴사왜 그 패치가 있는지 아무도 모름

2.2 머무르는 비용은 시간이 갈수록 커진다#

옛 커널에 머물면 매달 두 가지가 쌓인다. (1) upstream에서 고쳐진 버그가 우리 트리에는 없다 — stable 트리는 EOL 이후 수정을 받지 않는다. (2) upstream과 우리 트리의 거리가 벌어져, 나중에 옮길 때 충돌과 API 변경이 늘어난다. 10절에서 볼 것처럼 6.18.56 stable 한 번에 402개 수정이 들어간다. EOL 이후에는 이것들을 우리가 직접 골라 backport해야 한다.

그래서 실무 원칙은 두 가지다.

  • stable point release는 정기적으로(주~월 단위) 머지한다. 이건 "작은 업그레이드"이고 거의 공짜다(E7 §4).
  • LTS 이동은 1~2년마다 계획된 프로젝트로 한다. 이때 패치 스택을 줄이는 것(upstream에 보내기, P7)이 다음 이동의 비용을 결정한다.

Don 경험과 연결: SSD 펌웨어에서 "이전 세대 코드 브랜치에 핫픽스만 계속 얹다가 신규 세대 이식 때 수백 개 diff를 분류하던" 상황과 같다. 그때 효과가 있던 규칙(커밋 메시지에 출처·이슈 번호, 플랫폼 공통 코드는 공통 브랜치에만)이 커널에서도 그대로 통한다.

3. 업그레이드 계획 — 인벤토리와 분류#

3.1 네 가지 분류#

패치 하나하나를 아래 네 칸 중 하나에 넣는 것이 계획의 핵심이다.

분류판단 기준할 일실습 저장소의 예

3.2 예제 1 — 실습 저장소 만들기#

무엇을 확인하나: 커널 업그레이드의 전형적인 상황을 담은 작은 저장소를 만든다. upstream v1.0 → v2.0(그 사이에 버그 수정, API 인자 변경, 파일 삭제), 벤더 bsp-1.0(v1.0 위 2개)과 bsp-2.0(v2.0 위로 벤더가 직접 옮긴 2개, 내용 일부 변경), 그리고 우리 product 스택 4개.

(처음 만든 긴 버전(heredoc·python 치환)을 노트용으로 printf/sed로 줄인 것이다. 이 짧은 버전을 다시 돌려 아래 출력이 해시까지 똑같이 나오는 것을 확인했다.)

출력에서 볼 것: product는 bsp-1.0 위에 있고, bsp-1.0은 v1.0 위에 있다. 업그레이드 목표는 우리 커밋 4개만 bsp-2.0 위로 옮기는 것이다. 벤더 커밋 2개(574bdba, d62562b)는 벤더가 이미 bsp-2.0으로 옮겨 놓았으니 우리가 옮기면 안 된다. 날짜를 고정했으므로 같은 스크립트를 돌리면 해시도 같다.

3.3 예제 2 — 인벤토리: 범위 고르기, git cherry, 파일 상태#

무엇을 확인하나: (A) 범위를 잘못 잡으면 벤더 커밋까지 "우리 것"으로 섞인다, (B) 바른 범위, (C) git cherry로 "이미 upstream에 있는 것" 찾기, (D) 각 커밋이 건드린 파일이 새 base에서 어떤 상태인지.

출력에서 볼 것:

  • A는 6개, B는 4개다. bsp-2.0..product는 "bsp-2.0에 없는 product 커밋"이라 옛 벤더 커밋까지 포함된다. 벤더 커밋은 bsp-2.0에서 내용이 바뀌어(클럭 24 MHz → 25 MHz) 해시도 patch-id도 다르기 때문이다. 우리 스택의 진짜 범위는 옛 base부터(B)다. 이게 4절 --onto가 필요한 이유다.
  • git cherry <upstream> <head> <limit>은 limit..head의 각 커밋에 대해 "upstream에 같은 patch-id가 있으면 -, 없으면 +"를 찍는다. af12ce4가 - — upstream 0b2c474와 diff가 글자 하나까지 같다. 해시는 다르지만 patch-id가 같다.
  • D의 DELETED는 obsolete 후보, changed는 충돌 후보(needs port 가능), new는 keep 후보다. 진짜 커널에서는 이 스크립트를 수백 개 커밋에 돌려 스프레드시트로 만든다.

진짜 커널에서는 (가이드, 실행 안 함):

함정: patch-id는 diff가 완전히 같을 때만 같다. backport하면서 문맥을 손봤거나 다르게 고쳤으면 +로 나온다. 그래서 git cherry의 -는 "확실히 upstream", +는 "아직 모름"이다. + 중 상당수는 커밋 메시지의 commit <sha> upstream. 줄이나 제목 검색(git log --grep, git log -S)으로 사람이 다시 확인해야 한다.

4. git rebase --onto — 스택만 잘라서 옮기기#

4.1 직관#

git rebase <base>는 "현재 브랜치에서 <base>에 없는 커밋을 전부 <base> 위에 다시 쌓는다". 문제는 "base에 없는 커밋"이 우리 커밋보다 많을 때다(예제 2의 A). --onto는 "어디서부터 잘라서(옛 base) 어디에 붙일지(새 base)"를 따로 지정한다.

그림 4 — --onto의 세 인자. 옛 base(bsp-1.0)는 "여기까지는 내 것이 아니다"라는 경계, 새 base(bsp-2.0)는 "여기 위에 붙인다"는 목적지다. 옮긴 커밋은 내용이 같아도 부모가 달라졌으니 새 해시(P1', P3')를 받는다.

4.2 예제 3 — 그냥 git rebase bsp-2.0을 하면#

무엇을 확인하나: --onto 없이 새 base만 주면 무슨 일이 생기는지.

출력에서 볼 것: git은 patch-id가 같은 두 커밋(벤더의 board init, 우리의 fix channel bound check)은 알아서 건너뛰었다. 하지만 벤더가 내용을 바꿔 옮긴 클럭 드라이버 커밋(574bdba)을 우리 커밋처럼 다시 쌓으려다 add/add 충돌이 났다. 커널 BSP에서는 이런 벤더 커밋이 수천 개라, 이 방식으로는 끝이 안 난다. 벤더 커밋은 벤더가 옮긴 것을 믿고, 우리 범위만 옮긴다.

4.3 예제 4 — --onto + drop 목록 + 충돌 해결 + range-diff#

무엇을 확인하나: 인벤토리 결과(upstreamed·obsolete)를 todo 목록에 자동 반영해 drop하고, 남은 충돌 하나를 zdiff3 표시로 읽어 해결한 뒤, range-diff로 "전 스택 vs 후 스택"을 검토하고 빌드까지 확인한다. git rebase -i의 편집기를 스크립트로 바꿔(GIT_SEQUENCE_EDITOR) 비대화식으로 돌린다.

출력에서 볼 것:

  • todo 목록이 곧 분류표다. pick=keep/needs-port, drop=upstreamed/obsolete. 진짜 업그레이드에서는 이 todo 파일을 리뷰 받고 저장소에 남긴다(왜 drop했는지 한 줄 주석과 함께).
  • 4개 중 2개만 남았고 새 해시(5e990cb, 0aafd5a)를 받았다. 벤더 커밋은 옮기지 않았다(bsp-2.0..product가 2개).
  • range-diff의 기호: = 같은 커밋(내용 동일), < 왼쪽(전)에만 있음 = drop된 것, ! 짝은 있지만 내용이 바뀜. ! 아래는 diff의 diff다: 첫 열은 "전→후"의 변화, 둘째 열은 원래 diff 기호다. - int v = sensor_read(0); / + int v = sensor_read(&imu_sd, 0);는 "우리 패치의 문맥 줄이 새 API로 바뀌었다"는 뜻이고, +imu_count++ 줄 자체(둘째 열 +)는 그대로다 — 즉 우리 의도는 보존되고 문맥만 바뀌었다. 리뷰어는 range-diff만 보고 포팅이 맞는지 판단할 수 있다.
  • --creation-factor=95: range-diff는 "얼마나 바뀌어야 다른 커밋으로 볼지"를 비용으로 정한다(기본 60). 이 예제처럼 작은 커밋에서 문맥이 크게 바뀌면 기본값에서는 짝을 못 찾고 <와 > 두 줄로 나온다 — 실제로 기본값으로 돌렸을 때 3: 7ddb7a8 < -: -------와 -: ------- > 2: ...로 따로 나왔다. 짝이 안 맞으면 이 값을 올린다.
  • 빌드 확인은 범위가 작아도 반드시 한다. 충돌 없이 붙은 커밋도 의미상 깨졌을 수 있다(아래 5.3).

4.4 함정 — --onto에서는 upstream 패치가 자동으로 빠지지 않을 수 있다#

예제 3(plain rebase)에서는 git이 af12ce4를 "skipped previously applied commit"으로 자동으로 건너뛰었다. 그런데 처음 이 실습을 --onto로 돌렸을 때, drop 목록에 af12ce4를 넣지 않았더니 git은 그것을 그대로 pick했고 충돌이 났다(실제 출력 일부):

이유: rebase가 "이미 적용된 커밋"을 거르는 비교 대상은 <upstream> 인자다. --onto bsp-2.0 bsp-1.0에서 <upstream>은 bsp-1.0(옛 base)이고, 거기에는 그 수정이 없다. 그래서 새 base(bsp-2.0)에 같은 수정이 있어도 걸러지지 않는다(이 동작은 이 VM의 git 2.53.0에서 관찰한 것이다). 게다가 upstream이 같은 줄 근처((void)sd; 추가)를 또 바꿨기 때문에 "적용하면 빈 커밋"이 되지도 않고 충돌이 됐다. 그래서 --onto를 쓸 때는 git cherry로 먼저 -를 찾아 직접 drop 한다 — 예제 4가 그렇게 했다.

5. 충돌 해결 전략#

5.1 원칙 — 충돌은 "두 의도의 합"이다#

충돌 표시는 세 칸을 보여 준다(zdiff3): HEAD(새 base 쪽 = upstream이 바꾼 결과), ||||||| 아래 공통 조상(옛 코드), ======= 아래 우리 커밋이 바꾼 결과. 해결은 "둘 중 하나 고르기"가 아니라 upstream의 변경 의도(API에 sd 추가)와 우리 의도(카운터 증가)를 둘 다 살리는 것이다. 공통 조상 칸이 없으면(기본 merge 스타일) 누가 무엇을 바꿨는지 추측해야 해서 실수가 는다. 커널 문서 Documentation/process/backporting.rst도 "Merge styles and diff3" 절에서 git config merge.conflictStyle diff3를 권하고, Git 2.35에 추가된 zdiff3를 소개한다(트리에서 확인).

5.2 충돌 해결 체크리스트#

단계명령·행동왜
1. 조상 칸 보기merge.conflictStyle zdiff3누가 무엇을 바꿨는지 분리
2. upstream 쪽 의도 찾기git log -L:'\<imu_sample\>':drivers/imu.c bsp-1.0..bsp-2.0

5. 메시지에 흔적본문에 [ Don: adapted to sensor_read(sd, ch) API ]다음 사람이 range-diff !를 이해

5.3 충돌이 없는데 깨지는 경우 — 의미 충돌#

git의 3-way merge는 줄 단위 텍스트만 본다. 다음은 충돌 없이 붙지만 깨진다.

  • upstream이 함수의 잠금 규칙을 바꿨다(예: 이제 호출자가 lock을 잡아야 함). 우리 패치는 옛 규칙으로 호출 → 컴파일은 되고 lockdep(M8)에서만 걸린다.
  • upstream이 함수 반환값 의미를 바꿨다(0/1 → 0/-errno). 우리 if (ret == 1)은 조용히 죽은 코드가 된다.
  • upstream이 리소스를 devm으로 바꿨다. 우리 패치의 remove()에 남은 수동 해제가 이중 해제가 된다.
  • 다른 파일에서 같은 기능을 upstream이 이미 추가 → 우리 패치와 두 번 등록.

backporting.rst의 "Gotchas" 절(Function arguments, Error handling, Refactored code)이 바로 이 목록이다. 대응은 7절의 회귀 테스트와 리뷰어가 보는 range-diff다.

6.2 예제 6 — 6.1 시절 스타일 드라이버를 6.18에서 빌드하면#

무엇을 확인하나: 센서 키트 BSP에 있을 법한 out-of-tree 드라이버(platform driver + I2C driver + class + 타이머 + 레거시 GPIO)를 6.1 시절 API로 쓰고, linux-build-dom(6.18.55)으로 빌드해 진짜 에러를 본다. 이 코드는 6.1 트리에서는 빌드됐을 모양이다(6.1 트리로 직접 빌드해 보지는 않았다 — 기억 기반).

출력에서 볼 것 — 에러 메시지 종류가 곧 포팅 유형이다.

  • implicit declaration of function (5개): 함수가 없어졌거나 이름이 바뀌었다. gcc의 "did you mean" 힌트는 반쯤만 맞다: noop_llseek는 맞지만 strncpy(→ 정답은 strscpy), mod_timer(→ 정답 timer_container_of)는 틀린 힌트다. 정답은 upstream에서 그 함수를 지운 커밋 메시지나 Documentation/에 있다.
  • incompatible pointer type (3개): 콜백 시그니처가 바뀌었다. 커널은 이 경고를 에러로 올린다(scripts/Makefile.extrawarn의 -Werror=incompatible-pointer-types — 트리에서 확인). 예전처럼 경고로 넘어갔다면 int 반환을 void로 부르는 미묘한 ABI 버그가 됐을 것이다.
  • too many arguments (1개): 인자 개수가 바뀌었다(class_create에서 owner가 빠짐).
  • expected ‘,’ or ‘;’ (1개): 매크로 문법이 바뀌었다. MODULE_IMPORT_NS가 이제 문자열 리터럴을 받는다 — 에러 메시지만으로는 이유가 안 보이는 유형이라 가장 시간을 잡아먹는다.
  • gpio_is_valid()는 에러가 없다 — 레거시 GPIO 헤더는 아직 있다(6.1절). 빌드가 된다고 끝이 아니다: 레거시 숫자 GPIO는 런타임에 base가 바뀌면 다른 핀을 잡는다.

9. git bisect run — 회귀 커밋을 자동으로 찾기#

9.1 직관#

"5.15에서는 되는데 6.18에서는 안 된다"는 그 사이 수만 커밋 중 하나(또는 몇 개)의 탓이다. 이진 탐색이면 log2(N)번 테스트로 찾는다: 3만 커밋이면 약 15번. 사람이 매번 빌드·부팅·판정하는 대신, 판정 스크립트의 종료 코드로 git이 다음 커밋을 고르게 하는 것이 git bisect run이다.

스크립트 종료 코드의미
0good
1 ~ 127 (125 제외)bad
125이 커밋은 테스트 불가 → skip (빌드 깨짐 등)
128 이상bisect 중단 (스크립트 자체 오류로 취급)

(종료 코드 규칙은 git help bisect의 "bisect run" 절 기준이다.)

9.2 예제 10 — 32커밋 중 회귀 하나 + 빌드 깨진 커밋 하나#

무엇을 확인하나: 링버퍼 "드라이버"에 32개 커밋을 쌓되, rev 20이 wrap 버그(% N → & N)를 넣고, rev 24는 빌드를 깨뜨리고 rev 25가 고친다. 판정 스크립트는 빌드 실패면 125, 테스트 실패면 1을 반환한다.

출력에서 볼 것:

  • 7번 테스트(그중 1번 skip)로 31개 후보 중 범인을 찾았다. rev 24는 빌드가 깨져 125 → # skip:으로 기록됐고, git은 다른 커밋(rev 19, rev 26)을 대신 골랐다. 빌드 깨진 커밋을 bad로 판정하면 엉뚱한 커밋을 범인으로 지목한다 — 125가 그래서 있다.
  • bad=87: 100개 중 87개가 틀림 — (head + 1) & 8은 0 또는 8이라 head가 버퍼 밖(buf[8])을 쓴다. 모듈러를 마스크로 바꿀 때는 & (N - 1)이고 N이 2의 거듭제곱이어야 한다. Don에게 익숙한 펌웨어 링버퍼 버그다.
  • git bisect log는 재현 기록이다. 버그 리포트·upstream 메일에 그대로 붙인다(Documentation/admin-guide/bug-bisect.rst도 log 저장을 권한다).
  • 2.2초(공유 VM, 컴파일 7번 포함) — 진짜 커널 bisect는 단계마다 빌드 + 부팅이라 한 단계 수 분~수십 분이다. 그래서 스크립트를 미리 견고하게 짜는 것이 핵심이다.

그림 5 — 예제 10의 실제 bisect 경로. 위 줄의 숫자는 테스트 순서, 아래 막대는 각 단계 뒤 남은 구간이다. 7단계 뒤 구간이 rev 19(good)와 rev 20(bad) 사이로 좁혀져 rev 20이 범인이다.

랩 커널 소스는 git 저장소가 아니어서 실제 커널 bisect는 돌리지 않았다. 아래는 QEMU 부팅 + 모듈 테스트를 판정으로 쓰는 형태다. 핵심은 빌드 실패 = 125, 부팅 실패(타임아웃) = bad인지 skip인지 미리 정책을 정하는 것이다.

실무 요령:

  • 두 LTS 사이를 bisect할 때 good/bad 지점은 mainline 태그(v5.15, v6.18)로 잡는다. stable 태그(v5.15.180)는 mainline의 조상이 아니라 옆 가지라서 bisect가 "merge base가 good인지" 묻고 헤맨다.

  • 단계가 비싸면 먼저 대략 범위를 좁힌다: mainline 릴리스 태그(6.0, 6.1, …)만 먼저 테스트 → 범인 릴리스를 찾고 → 그 안에서 bisect. git bisect skip이 많으면 git bisect visualize로 남은 후보를 보고 사람이 판단한다.

10. stable backport — 받는 쪽과 보내는 쪽#

10.1 태그 복습 (E7 §5.11과 트리 문서)#

  • Fixes: <12자 sha> ("<제목>") — 이 수정이 고치는 커밋. stable 팀과 AUTOSEL 도구가 "어느 stable에 넣을지"를 이걸로 계산한다.
  • Cc: stable@vger.kernel.org — Option 1. mainline에 머지되면 자동으로 stable 후보가 된다. # 6.1.x 같은 주석으로 버전 범위, # a1f84a3: ...로 선행 패치를 지정할 수 있다(1.1절 grep 출력의 문서 위치 근처, stable-kernel-rules.rst).
  • stable 트리에 들어간 커밋은 본문 첫 줄에 commit <40자 sha> upstream. 또는 [ Upstream commit <sha> ]가 붙는다.
  • Stable-dep-of: — "이 커밋은 그 자체는 수정이 아니지만, 저 수정을 붙이기 위한 선행 패치로 같이 들어왔다".

10.4 보내는 쪽 — 우리가 고친 버그를 stable로 (요약)#

  1. mainline 기준으로 고친다(우리 트리가 6.6이어도).
  2. 커밋에 Fixes:(버그를 넣은 커밋)와 Cc: stable@vger.kernel.org를 단다(Option 1).
  3. 옛 stable에서 그대로 안 붙는다는 메일(FAILED patch)이 오면, 그 트리에 맞게 고친 버전을 commit <sha> upstream. 형식으로 보낸다(Option 3, E7 §5.11).
  4. 우리 제품 트리에는 mainline 커밋을 cherry-pick -x로 미리 넣고, 다음 stable 머지 때 patch-id로 자연히 합쳐지게 한다(예제 3의 "skipped previously applied commit").

11. 커널 안에서는 무슨 일이 일어나나#

업그레이드에서 만나는 에러 두 종류 — "빌드가 안 된다"(6절)와 "빌드는 되는데 로드가 안 된다"(예제 8) — 는 커널 안의 서로 다른 지점에서 생긴다.

그림 6 — 모듈 로드 경로(왼쪽)와 driver core가 우리 콜백을 부르는 경로(오른쪽). 함수 이름은 6.18.55 kernel/module/main.c, drivers/base/platform.c에서 grep으로 확인했다.

  • API 변화의 정체는 "콜백 테이블의 타입"이다. struct platform_driver는 driver core가 부르는 함수 포인터 테이블이다(G3). 6.18.55의 drivers/base/platform.c:

core가 반환값을 안 쓰므로 타입을 void로 바꿨고, 그 순간 모든 드라이버의 .remove = fn 대입이 타입 에러가 된다. bare-metal로 치면 벡터 테이블 엔트리의 함수 타입이 바뀐 것이다. i2c도 같다: drivers/i2c/i2c-core-base.c의 i2c_device_probe()가 driver->probe(client)(593행)를 부른다.

  • 로드 시 검사는 check_modinfo()의 vermagic 비교가 첫 관문이다. 6.18.55 kernel/module/main.c의 check_modinfo()는 모듈의 vermagic 문자열이 커널의 VERMAGIC_STRING과 다르면 "version magic '%s' should be '%s'"를 찍고 -ENOEXEC를 반환한다 — 예제 8의 출력 그대로다. vermagic에는 커널 릴리스 문자열(LOCALVERSION 포함)과 SMP preempt mod_unload 같은 핵심 config 플래그가 들어간다.
  • dom 커널은 CONFIG_MODVERSIONS가 꺼져 있다(# CONFIG_MODVERSIONS is not set, linux-build-dom/.config 950행). MODVERSIONS가 켜져 있으면 심볼마다 CRC(함수 시그니처·구조체 레이아웃의 해시)를 비교해 "disagrees about version of symbol"(kernel/module/version.c)로 거부한다. 꺼져 있으면 vermagic만 맞추면 구조체 레이아웃이 달라도 로드된다 — 그래서 "같은 버전 문자열인데 config가 다른 커널"에 모듈을 억지로 올리면(예: modprobe --force) 메모리 깨짐으로 이어진다. 업그레이드 원칙: out-of-tree 모듈은 정확히 그 커널의 빌드 트리로 다시 빌드한다. Android GKI는 반대로 KMI(커널-모듈 인터페이스)를 CRC로 고정해 이 문제를 제도로 막는다(E7 §2.4, 기억 기반).
  • 서명: dom은 CONFIG_MODULE_SIG=y, MODULE_SIG_FORCE 꺼짐 → 서명 없는 모듈은 로드되고 E taint만 붙는다(예제 8). secure boot 제품(L5)에서는 FORCE를 켜므로, 업그레이드 때 모듈 서명 키와 빌드 파이프라인도 같이 옮겨야 한다.

드라이버 작성 때 다시 만나는 곳: G3(platform 수명주기 — probe/remove 대칭), H3(I2C probe(client)와 id_table/of_match_table), D4·H(gpiod), F(타이머 API), E3(Kbuild·vermagic·modinfo).

12.1 센서 키트 BSP를 5.15 → 6.18로 (작업 계획 예)#

"i.MX8 기반 센서 키트, 벤더 BSP 5.15 + 우리 패치 120개, out-of-tree 드라이버 4개(IMU, 카메라 serializer, CAN 보조 MCU, 전원 관리)"라면:

  1. 1주차 — 결정과 인벤토리. 벤더에 6.18 BSP가 있는지, 없으면 mainline 6.18의 해당 SoC 지원 범위(DT·드라이버)를 확인(E7 예제 7 방식). 우리 120개를 예제 2 스크립트로 스프레드시트화: 제목 접두어, 파일, git cherry 결과, upstream sha trailer.
  2. 2주차 — 분류 회의. upstreamed/obsolete는 근거와 함께 drop 목록으로, needs port는 담당자 배정. keep 중 upstream 가능한 것은 P7 백로그로.
  3. 3~4주차 — 옮기기와 포팅. rebase -i --onto + drop 목록, rerere 켜기. out-of-tree 드라이버 4개는 예제 6처럼 에러 목록 → 대응표 → 포팅. 가능하면 이 기회에 in-tree로 넣는다(다음 업그레이드에서 API 변경을 남이 고쳐 준다).
  4. 5~6주차 — 회귀. 8절 표의 1~7층. 부팅 스냅샷 diff, 센서별 데이터 품질(Q7), CAN 부하, 카메라 프레임 드롭, 전력(N5), RT 지연(N3).
  5. 이후 — 유지. 6.18.y stable을 2~4주 주기로 머지(예제 11·12의 triage를 매번), 회귀가 나오면 bisect run.

12.2 out-of-tree 드라이버를 여러 커널에서 동시에 빌드해야 할 때#

필드에 5.15 장비와 6.18 장비가 섞여 있으면 한 소스가 두 커널을 지원해야 한다. 흔한 방법은 LINUX_VERSION_CODE 분기다.

(위 코드는 문법 예시이고 빌드하지 않았다. 버전 경계 6.11은 기억 기반이라 실제로는 해당 API가 들어온 커밋으로 확인해야 한다.) 분기가 수십 개가 되면 p5_compat.h 한 곳에 모으고(#define timer_delete_sync del_timer_sync 같은 shim), 가능하면 벤더 stable 백포트가 버전 숫자와 API를 어긋나게 만드는 경우(벤더가 새 API를 옛 버전에 backport)를 대비해 버전 대신 기능 검사(Kconfig 심볼, 헤더의 매크로 존재)를 쓴다. 장기적으로는 in-tree로 넣는 것이 가장 싸다.

12.3 "업그레이드 후 IMU가 가끔 0을 읽는다" — bisect 적용#

증상은 새 커널에서만, 재현율 30%. 판정 스크립트는 "부팅 후 IMU를 1000번 읽어 0이 하나라도 있으면 bad"로 만들고, 재현율이 낮으므로 한 단계에서 10회 반복(1회라도 bad면 bad)한다. 범위는 우리 스택을 제외한 mainline 태그 사이로 잡고, 우리 드라이버는 out-of-tree 빌드로 매 단계 붙인다(9.3절 스크립트). 범인이 I2C 컨트롤러 드라이버의 clock stretching 처리 변경 같은 커밋으로 나오면, 그 커밋의 Fixes:가 달린 후속 수정이 이미 stable에 있는지(예제 11 방식)부터 본다. Don의 장점: 버스 장애 root cause 경험이 있으니, bisect로 커밋을 찾은 뒤 로직 분석기로 I2C 파형을 비교(M11)해 왜를 증명할 수 있다.

12.4 벤더가 BSP를 안 올려 줄 때#

벤더가 5.15에서 멈췄다면 선택지는 (1) 벤더 5.15 + 우리가 stable/보안 수정 backport(EOL 후에는 CIP 5.10/6.1 같은 트리를 참고하거나 상용 지원), (2) mainline 6.18로 가고 벤더 드라이버를 우리가 포팅, (3) 다음 하드웨어 리비전에서 SoC 변경. 면접에서는 "비용·위험·제품 수명"을 기준으로 비교하는 것을 보여 주면 된다(E7 §3, P2).

14. 면접에서 이렇게 말한다#

Q. How would you plan a kernel upgrade from a vendor 5.15 BSP to 6.18 LTS?

A. 먼저 목표 LTS의 수명과 SoC의 upstream 지원을 확인해 버전을 정한다. 다음으로 우리 패치 스택을 인벤토리해 upstreamed·obsolete·needs port·keep으로 분류하고, rebase --onto로 우리 범위만 새 base에 옮긴다. out-of-tree 드라이버는 컴파일 에러를 할 일 목록 삼아 포팅하고, 빌드·config diff·부팅·장치 probe·기능·성능 순서로 회귀를 막는다. 끝나면 stable을 정기적으로 머지하는 체계를 만든다.

First I confirm the target: the LTS's projected end of life versus our product lifetime, and how much of our SoC is supported upstream or in the vendor's new BSP. Then I inventory our patch stack and classify every patch as already upstream, obsolete, needs porting, or carried as is — git cherry and the upstream SHAs in our commit messages do half of that automatically. I move only our range with git rebase --onto, port the out-of-tree drivers using the compile errors as a to-do list, and review the result with git range-diff. Validation goes in layers: build with no warnings, a config diff, boot, every device probed, functional tests on the sensors, and performance against the old kernel on the same hardware. After that we merge stable releases on a fixed cadence so the next upgrade is smaller.

꼬리 질문: "패치가 수백 개면?" → 분류를 스크립트로 자동화하고(예제 2), 서브시스템별 담당자에게 나누고, 이 기회에 upstream 가능한 것을 보내 스택을 줄인다.

Q. What does git rebase --onto do and when do you need it?

A. --onto <새 base> <옛 base> <브랜치>는 "옛 base부터 브랜치 끝까지"만 잘라서 새 base 위에 다시 쌓는다. 벤더 BSP 위에 우리 패치가 있을 때, 벤더가 새 BSP를 따로 만들어 줬다면 벤더 커밋은 옮기면 안 되므로 --onto가 필요하다. 주의할 점은 이미 적용된 패치를 거르는 기준이 옛 base라서, upstream에 들어간 우리 패치는 git cherry로 찾아 직접 drop해야 한다는 것이다.

It takes the commits in old-base..branch and replays them on top of a new base. You need it whenever the branch sits on something you don't own — for example our product patches on top of a vendor BSP, when the vendor has already produced their own BSP for the new kernel. A plain rebase onto the new BSP would try to replay the vendor's old commits too. One catch I've seen: with --onto, the automatic skipping of already-applied patches compares against the old base, so I run git cherry against the new base first and drop the patches that are already upstream explicitly.

Q. How do you resolve a rebase conflict safely?

A. zdiff3 스타일로 공통 조상까지 보고, upstream이 그 줄을 왜 바꿨는지 git log -L이나 커밋 메시지로 확인한 뒤, 두 의도를 모두 살려 합친다. 커밋 본문에 어떻게 고쳤는지 한 줄 남기고, range-diff로 "전/후 패치"를 비교해 리뷰받는다. 충돌이 없던 커밋도 의미 충돌이 있을 수 있으니 빌드와 런타임 테스트로 확인한다.

I turn on the zdiff3 conflict style so I can see the common ancestor, then look up why upstream changed those lines — git log -L on the function, or the commit message. The resolution has to keep both intents: upstream's new API and our feature. I note the adaptation in the commit body, and reviewers look at git range-diff, which shows exactly how our patch changed during the port. And I don't trust a clean rebase either; semantic conflicts like changed locking rules only show up in build and runtime tests.

Q. Our driver stopped building on the new kernel with "incompatible pointer type" on .remove. What happened?

A. 6.x에서 platform driver의 .remove가 int 반환에서 void로 바뀌었다. driver core는 원래 반환값을 쓰지 않았기 때문이다. 함수를 void로 바꾸고, 혹시 에러를 반환하며 정리를 건너뛰던 경로가 있었다면 그건 원래부터 누수였으니 끝까지 정리하게 고친다. 비슷하게 i2c probe가 인자 하나로, class_create가 owner 없이 바뀌었다.

The platform bus changed the remove callback to return void, because the driver core never used the return value anyway. So I change the function to void, and I check any early-return error paths — if the old code skipped cleanup on error, that was already a leak and now it has to clean up unconditionally. The same kind of change hit I2C probe, which now takes only the client, and class_create, which lost the owner argument. In 6.18 the kernel turns incompatible-pointer-type into an error, which is good: it catches callback ABI mismatches at build time.

Q. How do you find which commit introduced a regression between two kernels?

A. git bisect run으로 자동화한다. 판정 스크립트는 빌드 실패면 125(skip), 테스트 통과면 0, 실패면 1을 반환한다. 범위는 mainline 태그 사이로 잡고, 단계가 비싸면 릴리스 단위로 먼저 좁힌다. 재현율이 낮으면 한 단계에서 여러 번 돌린다. 찾은 뒤에는 그 커밋의 후속 수정이 stable에 이미 있는지 본다.

I script it with git bisect run: the test script exits 0 for good, 1 for bad, and 125 when the revision can't be tested, like a build failure — otherwise a broken build gets blamed. I bisect between mainline tags, not stable tags, because stable tags aren't ancestors of mainline. If each step is a full build and boot, I first narrow it to a release, then bisect inside it, and for flaky bugs I repeat the test several times per step. Once I have the commit, I check whether a later fix carrying a Fixes: tag for it is already in stable.

Q. What are Fixes: and Cc: stable for?

A. Fixes:는 이 수정이 고치는 원래 커밋을 가리켜, stable 팀과 도구가 어느 버전에 backport할지 계산하게 한다. Cc: stable@vger.kernel.org는 mainline에 들어가면 stable로 자동으로 가져가라는 요청이다. 실제로 6.18.56 stable의 402개 커밋 중 346개가 Fixes:를, 229개가 Cc: stable을 달고 있었다. 받는 쪽에서는 이 태그로 우리 서브시스템 수정을 골라낸다.

Fixes: points at the commit that introduced the bug, so the stable team and their tooling can work out which stable trees need the fix. Cc: stable asks for an automatic backport once the patch lands in mainline. When I counted one real stable release, 6.18.56, 346 of its 402 commits had a Fixes: tag but only 229 had Cc: stable — the rest were picked up via Fixes: tags or automated selection. So I always add Fixes:, and on the receiving side I use these tags to triage which fixes matter for our drivers.

Q. Why can't we just keep the old kernel forever?

A. 커널은 계속 동작하지만, EOL 뒤에는 보안·버그 수정이 더 이상 오지 않는다. stable 하나에 수백 개 수정이 들어오는데 그걸 우리가 직접 골라 붙여야 하고, upstream과 거리가 벌어질수록 다음 업그레이드가 비싸진다. 장수 제품이면 CIP SLTS처럼 10년 유지되는 트리에 맞추거나, 1~2년 주기로 LTS를 옮기는 비용을 계획에 넣는다.

It keeps running, but after end of life the fixes stop arriving. A single stable release carries a few hundred fixes; on an EOL kernel we would have to find and backport the relevant ones ourselves, and every month the distance to upstream grows, so the eventual upgrade gets more expensive. For a long-lived product I'd either align with a CIP super-long-term kernel, which is maintained for about ten years, or budget an LTS move every one to two years and keep the patch stack small so it stays cheap.

17. 요약 & 체크리스트#

커널 업그레이드는 "제품 = LTS + 벤더 BSP + 우리 패치"에서 맨 아래층을 바꾸고 위층을 다시 올리는 프로젝트다. 언제 올릴지는 LTS의 projected EOL(5.10·5.15는 2026-12)과 제품 수명, CIP SLTS 채택 여부로 정한다. 실행은 인벤토리 → 분류(upstreamed·obsolete·needs port·keep) → git rebase -i --onto <새> <옛> <브랜치>(git cherry의 -와 삭제된 파일 대상 커밋은 todo에서 drop) → zdiff3로 두 의도를 합치는 충돌 해결 → range-diff 리뷰 순서다. out-of-tree 드라이버는 컴파일 에러 유형(없어진 함수, 바뀐 콜백 타입, 인자 수, 매크로 문법)이 곧 포팅 목록이며, 6.18.55에서 .remove는 void, i2c .probe는 인자 하나, class_create(name), timer_container_of/timer_delete_sync, strscpy, MODULE_IMPORT_NS("NS")다. 새 커널에는 모듈을 그 빌드 트리로 다시 빌드해야 하고(vermagic), config는 diffconfig로 사라진 심볼을 확인한다. 회귀는 빌드·부팅·probe·기능·성능 층으로 막고, 회귀 커밋은 0/1/125 규칙의 git bisect run으로 찾는다. 업그레이드 뒤에는 stable을 정기 머지하며 Fixes:·Cc: stable·Stable-dep-of: 태그로 우리 서브시스템 수정을 triage한다.
