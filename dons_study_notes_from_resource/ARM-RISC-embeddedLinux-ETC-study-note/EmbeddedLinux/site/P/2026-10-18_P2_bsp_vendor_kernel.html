0. 큰 그림 — 이게 왜 필요한가#

새 보드 프로젝트가 시작되면 SoC 벤더(NXP, TI, NVIDIA, Rockchip …)의 웹사이트에서 BSP(Board Support Package) 를 받는다. BSP는 "이 SoC로 Linux를 띄우는 데 필요한 모든 것"을 벤더가 묶어 준 꾸러미다. 소스 저장소 여러 개, 바이너리 블롭 여러 개, Yocto 레이어, 그리고 수백 쪽짜리 문서가 들어 있다.

Don에게 익숙한 말로 바꾸면 이렇다. SSD 컨트롤러를 새로 받으면 컨트롤러 벤더가 ROM 코드 문서 + 부트로더 + HAL/드라이버 SDK + NAND 벤더 바이너리 라이브러리 + 릴리스 노트 + errata를 준다. 우리는 그 위에 자사 FTL·기능 패치를 얹고, 벤더가 새 SDK를 낼 때마다 우리 패치를 옮긴다. Linux BSP도 구조가 똑같다. 다른 점은 조각 하나하나가 오픈소스 프로젝트의 벤더 포크라는 것이다. 그래서 "벤더 포크를 쓸 것인가, 원본(upstream)을 쓸 것인가"라는 선택지가 생긴다.

그림 1 — 벤더 BSP의 구성. 아래쪽(Boot ROM, 부트 체인)일수록 SoC에 가깝고 손대기 어렵다. 맨 위 빨간 줄(meta-<company>)만 온전히 우리 것이고, 나머지는 "버전을 고정해서 가져다 쓰는 남의 코드"다. 오른쪽 문서들이 실제 디버깅의 절반을 차지한다.

이 노트의 질문은 세 가지다.

  1. 벤더 BSP에는 정확히 무엇이 들어 있고, 각각을 누가 고치나? (1절)
  2. 커널은 벤더 것을 쓸까, mainline LTS를 쓸까? (2절)
  3. 어느 쪽이든 우리가 얹는 패치 스택을 어떻게 관리하나? (3~9절 — 실습의 대부분)

새 LTS로 스택을 옮기는 리베이스 작업 자체는 P5에서 다룬다. 이 노트는 "리베이스하기 쉬운 스택을 처음부터 어떻게 만드나"에 집중한다.

이 노트의 실습 환경#

  • Mac의 Lima VM elinux (aarch64, uname -r = 7.0.0-38-generic, git 2.53.0). 작업 디렉터리는 VM의 /var/tmp/P2/, 스크립트는 Mac의 ~/.elinux_scratch/P2/.
  • 커널 소스는 랩의 /var/lab/src/linux-6.18.55 (읽기 전용). 그 일부(drivers/iio, include/linux/iio, arch/arm64/boot/dts/freescale, arch/arm64/configs, 최상위 Makefile)만 복사해 작은 git 저장소를 만들고 v6.18.55 태그를 붙여 "벤더 패치 스택의 기준점"으로 쓴다. 전체 트리 복사는 디스크가 아깝고, 패치 관리 실습에는 이 정도면 충분하다.
  • quilt는 VM 호스트에 설치돼 있지 않다(공용 상태를 바꾸지 않기 위해 apt 설치 금지). 대신 GNU Savannah의 공식 tarball quilt-0.69.tar.gz(550 KB)를 받아 /var/tmp/P2/quilt에 --prefix로 설치해 썼다. (랩의 rootfs-dom 게스트에는 quilt가 들어 있다.)
  • 드라이버 동작 확인은 랩 커널 out/Image(6.18.55) + BusyBox initramfs를 QEMU virt(TCG, KVM 없음)로 부팅해서 했다. 19명이 같은 VM을 쓰는 중이라 부팅 시간 같은 숫자는 실제 하드웨어 값이 아니다.
  • 이 노트의 보드 "P2 SensorKit", 회사 레이어 meta-p2-sensorkit, 그리고 "upstream 커밋"으로 등장하는 sim/mainline-next 브랜치는 실습용으로 만든 가상의 것이다. 실제 커널 커밋이 아니다.

표의 i.MX 저장소·파일 이름은 기억 기반이다. 실제 이름과 버전은 받은 BSP의 릴리스 노트에서 확인해야 한다. 이 노트 안에서 실제로 확인한 것은 1.4절(커널 트리의 펌웨어 참조)과 1.5절(NXP 커널 저장소의 디렉터리)뿐이다.

1.2 부트 체인은 "포크 네 개"다#

부트 체인은 C1~C5에서 다뤘다. BSP 관점에서 기억할 점은 하나다. TF-A, OP-TEE, U-Boot, 커널이 모두 upstream 프로젝트의 벤더 포크이고, 서로 버전이 맞물려 있다. 예를 들어 벤더 U-Boot의 특정 커밋은 특정 TF-A 버전의 BL31 주소·SMC 인터페이스를 가정하고, 커널의 전원 도메인 드라이버는 그 TF-A가 제공하는 SiP 서비스를 부른다. 그래서 부트 체인의 한 조각만 upstream으로 바꾸면 다른 조각이 깨질 수 있다. 실무에서는 부트 체인은 벤더 릴리스 세트를 통째로 고정하고, 커널만 독립적으로 판단하는 경우가 많다.

1.3 벤더 커널 트리와 DT#

벤더 커널은 "LTS 태그 + 벤더 커밋 N개"다 (E7 4절). N은 수백에서 수천이다. 그 안에는 세 종류가 섞여 있다.

  • 이미 upstream에 있는 것의 backport — 새 LTS로 가면 저절로 사라진다.
  • upstream에 보낼 예정이거나 보내는 중인 것 — 시간이 지나면 사라진다.
  • upstream에 갈 계획이 없는 것 — 벤더 전용 드라이버(GPU 커널 모듈, 벤더 V4L2 드라이버), EVK용 DT 변형, 디버그 기능. 이것이 벤더 커널을 "벤더 커널"로 만든다.

DT도 마찬가지다. 벤더 트리의 EVK dts는 mainline의 같은 파일보다 길다. 2.3절 예제에서 실제로 잰다.

1.4 예제 1 — 커널 트리에서 펌웨어 블롭 찾기#

무엇을 확인하나: i.MX8M Plus 보드가 어떤 펌웨어 파일을 /lib/firmware에 가져야 하는지, mainline 6.18.55 트리만 읽고 알아낸다. 드라이버의 MODULE_FIRMWARE()와 DT의 firmware-name 속성이 단서다. 그리고 GPU/NPU용 오픈 드라이버가 트리에 있는지도 본다 (1.5절과 연결).

출력에서 볼 것:

  • SDMA(Smart DMA) 엔진의 RAM 스크립트 imx/sdma/sdma-imx7d.bin은 i.MX8MP DT 세 곳이 가리킨다. 이 파일이 없으면 SDMA는 ROM 스크립트만으로 동작하고, 일부 주변장치(오디오 등)의 DMA가 안 된다. 커널은 오픈소스지만 그 커널이 요구하는 파일은 블롭이다. BSP의 firmware-imx 같은 패키지가 이것을 채운다.
  • firmware-name은 DT가 "이 보드에서는 이 파일을 써라"라고 지정하는 표준 속성이다. 보드 DT(P4)를 쓸 때 이 이름이 rootfs의 실제 파일과 맞는지 확인해야 한다. 안 맞으면 부팅 로그에 Direct firmware load for ... failed with error -2가 찍힌다 (G10).
  • drivers/gpu/drm/etnaviv(Vivante GPU의 오픈 드라이버)와 drivers/accel/rocket(Rockchip NPU), drivers/accel/ivpu(Intel NPU)가 mainline에 있다. 즉 일부 SoC는 벤더 블롭 없이도 GPU/NPU를 쓸 길이 있다. 다만 오픈 스택이 벤더 스택과 같은 성능·기능(예: 특정 NN 연산자)을 내는지는 별개 문제다 (O4).

1.5 GPU/NPU 유저스페이스 블롭과 "ABI 락인"#

벤더 GPU/NPU 스택은 보통 두 조각이다. 커널 모듈(소스 공개, GPL)과 유저스페이스 라이브러리(바이너리만 제공). 둘 사이의 인터페이스는 벤더 전용 ioctl이고, 버전이 정확히 짝이 맞아야 한다. i.MX의 Vivante GPU라면 커널 쪽이 galcore 모듈, 유저 쪽이 GPU 라이브러리 패키지다 (이름은 기억 기반).

무엇을 확인하나: NXP가 GitHub에 공개한 벤더 커널(nxp-imx/linux-imx)의 lf-6.12.y 브랜치가 어떤 LTS 위에 있고, mainline에는 없는 벤더 전용 디렉터리 drivers/mxc에 무엇이 있는지 본다. (GitHub API로 디렉터리 목록만 읽는다. 전체 클론은 하지 않는다.)

출력에서 볼 것:

  • 2026-10-18에 조회한 lf-6.12.y의 머리는 6.12.49 위에 있고, 마지막 커밋은 2025-11-21이다. 6.12.y stable은 그 뒤로도 거의 매주 나온다(E7). 지금 몇 point release 차이인지는 kernel.org releases.json으로 확인한다 (이 노트에서는 세지 않았다). 즉 벤더 브랜치가 stable을 얼마나 자주 따라가는지가 보안 수정의 실제 속도를 정한다.
  • drivers/mxc/gpu-viv가 Vivante GPU의 벤더 커널 드라이버(galcore)다. mainline에는 이 디렉터리가 없다. hantro*, vpu도 벤더판 비디오 코덱 드라이버다 (mainline에는 별도의 V4L2 기반 hantro 드라이버가 drivers/media/platform/verisilicon에 있다).
  • 이 GPU 유저 라이브러리를 쓰려면 gpu-viv와 같은 릴리스의 커널 모듈이 필요하다. 커널을 mainline LTS로 바꾸려면 (a) 이 모듈을 새 커널로 포팅하거나 (b) 오픈 스택(etnaviv + Mesa)으로 갈아타야 한다. 이것이 블롭 ABI 락인이다. 2절 결정의 가장 큰 변수다.

함정: "커널 모듈 소스가 공개돼 있으니 아무 커널에나 빌드하면 된다"가 아니다. 모듈이 쓰는 커널 내부 API(dma-buf, DRM, 메모리 관리)는 버전마다 바뀌고 (E4 "커널 내부 API는 안정적이지 않다"), 유저 라이브러리가 기대하는 ioctl 버전도 고정이다. 포팅은 가능하지만 공짜가 아니다.

1.7 문서 — 릴리스 노트와 errata를 읽는 법#

BSP 문서는 길지만 bring-up에서 실제로 펼치는 곳은 정해져 있다.

  1. 릴리스 노트의 "구성품 버전표" — 커널 태그, U-Boot·TF-A·OP-TEE 커밋, 펌웨어 패키지 버전, Yocto 릴리스. 우리 meta-<company>의 고정값(SRCREV, kas lock)이 이 표와 일치해야 한다.
  2. Known issues / Limitations — "이 BSP에서 PCIe Gen3 링크가 X 조건에서 안 올라간다" 같은 항목. bring-up 중 이상 현상을 보면 디버깅 전에 여기부터 검색한다. Don이 SSD에서 컨트롤러 errata 시트를 먼저 보던 것과 같다.
  3. SoC errata (Chip Errata 문서) — 실리콘 버그와 SW 우회법. 커널에는 ERRATUM_ 같은 Kconfig나 드라이버 quirk로 들어 있는 경우가 많다 (예: 6.18.55 arch/arm64/Kconfig에는 Arm 코어 errata 우회용 config ARM64_ERRATUM_... 항목이 39개 있다).
  4. Porting Guide — EVK에서 커스텀 보드로 옮길 때 바꿔야 하는 목록 (DDR 설정, 부트 매체, PMIC, DT). P1 bring-up 순서와 거의 같은 목차다.

2. 벤더 커널 vs mainline — 결정 매트릭스#

2.1 직관#

E7 3절에서 "벤더 6.6 BSP냐 6.18 LTS냐"를 네 축(upstream 지원, backport 부담, 보안 수정, 수명)으로 봤다. 여기서는 BSP를 실제로 받아 본 사람의 시선으로 축을 두 개 더한다. 블롭 ABI 락인(1.5절)과 부트 체인 결합(1.2절)이다. 이 둘은 "기술적으로 mainline이 더 좋다"는 판단을 뒤집는 경우가 많다.

그림 2 — 커널 선택 흐름. 첫 질문은 "필요한 블록이 mainline에 있나"이고, 없다면 다음 질문은 "그 블록의 유저 블롭이 벤더 커널 모듈과 묶여 있나"다. 묶여 있으면 벤더 커널이 사실상 강제된다.

2.2 결정 매트릭스#

판단 축벤더 커널 쪽이 유리한 경우mainline LTS 쪽이 유리한 경우확인 방법

2.3 예제 2 — 벤더 DT와 mainline DT를 같은 기준 버전에서 비교#

무엇을 확인하나: 1.5절의 NXP lf-6.12.y(6.12.49 기반)와 같은 기준 버전인 mainline stable v6.12.49에서 imx8mp-evk.dts 한 파일을 받아 비교한다. 서로 다른 기준 버전끼리 비교하면 "벤더가 추가한 것"과 "upstream이 그사이 바꾼 것"이 섞인다. 벤더 커밋은 sha로 고정한다 (재현성, 9절).

출력에서 볼 것:

  • 같은 6.12.49 기준인데도 EVK DT 한 파일이 1145줄 → 1461줄, +478/−162줄 다르다. 벤더 EVK DT에는 카메라(ovti,ov5640), USB-C(nxp,ptn5110 Type-C 컨트롤러, usb-c-connector), 블루투스, LVDS 브리지(ite,it6263)가 켜져 있다. mainline EVK DT는 그 일부만 기술한다.
  • 벤더에만 있는 compatible 8개 중 7개는 6.18.55 mainline에 바인딩이 이미 있다. 즉 "벤더 DT의 대부분은 upstream에서도 표현 가능하다". 이것은 "우리 보드 DT를 mainline 스타일로 써 두면 나중에 갈아탈 수 있다"는 근거다.
  • nxp,cbtl04gp(USB-C 신호 mux로 보인다)는 6.18.55 바인딩 문서에서 찾지 못했다. 이런 노드가 바로 mainline으로 옮길 때 드라이버·바인딩을 직접 챙겨야 하는 항목이다. (이 검사는 바인딩 문서에 문자열이 있는지만 본 것이라, 드라이버가 다른 compatible로 같은 칩을 지원할 가능성은 따로 확인해야 한다.)
  • 커뮤니티 레이어가 쓰는 linux-fslc-imx가 이 NXP 트리와 또 다르다는 것은 K5 3.5절에서 봤다 (패치가 hunk 실패). 비교의 기준은 항상 실제로 빌드할 SRCREV다.

2.4 실제 벤더 커널 전체를 mainline과 비교하는 법 (가이드 — 실행 안 함)#

수 GB의 클론이 필요하므로 이 VM에서는 하지 않았다. 순서와 명령만 정리한다. 명령은 모두 실제 존재하는 git 기능이다.

해석 요령:

  • 2)의 --dirstat에서 drivers/mxc, drivers/gpu, drivers/media, arch/arm64/boot/dts가 크게 나오면 "블롭 의존 드라이버 + 멀티미디어 + EVK DT"가 벤더 차이의 본체다.
  • 3)의 git cherry는 patch-id(diff 내용의 해시)로 비교한다 (E7 4.3). 벤더가 upstream 커밋을 수정해서 backport했다면 patch-id가 달라서 +로 나온다. 즉 이 숫자는 "upstream에 있는 것"의 하한이다.
  • 우리 회사가 실제로 쓰는 것은 그중 일부다. 우리 보드 DT가 참조하는 compatible과 우리 .config의 CONFIG_ 심볼을 기준으로 "우리가 의존하는 벤더 전용 코드"를 좁히는 것이 실무적이다. 이 목록이 P5(리베이스)의 작업 범위가 된다.

3. 패치 스택 — 개념과 규칙#

3.1 직관#

벤더 커널을 쓰든 mainline을 쓰든, 우리 커널은 "기준 태그 + 우리 패치 N개" 다. 이 N개를 패치 스택(patch stack, 또는 patch queue)이라 부른다. 스택의 품질은 하나의 질문으로 판가름 난다: "새 기준 태그로 옮길 때 얼마나 아픈가?" (P5)

그림 3 — 이 노트의 실습에서 만드는 6개짜리 스택. upstream으로 갈 것(파랑)은 아래, 보드 전용(초록)은 위, HACK(빨강)은 맨 위에 둔다. 리베이스할 때 아래쪽 패치는 upstream에 흡수되어 하나씩 사라진다.

3.2 규칙 다섯 개#

  1. 한 패치 = 한 논리적 변경. "DT 추가 + 드라이버 수정 + 설정"을 한 커밋에 넣지 않는다. 나중에 드라이버 수정만 upstream에 보내거나 버려야 할 때 쪼갤 수 없다. 커널 커뮤니티 규칙(E7 5절)과 같다.
  2. 순서는 "upstream으로 갈 가능성" 순. backport → 보낼 수정 → 보드 전용 → 설정 → HACK. 리베이스에서 아래쪽이 사라져도 위쪽이 의존하지 않아야 한다.
  3. 모든 패치에 출처·상태 표시. 제목 접두어(UPSTREAM:, BACKPORT:, FROMLIST:, HACK: — E7 4.4) 또는 Yocto의 Upstream-Status: 태그(3.3절). 이 노트는 Yocto로 내보낼 것이므로 Upstream-Status를 커밋 메시지 본문에 넣는다.
  4. backport는 원본 sha를 남긴다. git cherry-pick -x가 (cherry picked from commit <sha>)를 붙인다. 리베이스 때 그 sha가 새 기준에 있으면 버린다.
  5. HACK은 스택 맨 위, 릴리스에서 빠지는 경로에. 디버그 printk, 타이밍 우회, 임시 비활성화는 따로 모아 빌드 설정 하나로 넣고 뺄 수 있게 한다 (5.3절).

3.3 Upstream-Status 태그#

OpenEmbedded는 레이어에 들어가는 모든 패치의 헤더에 Upstream-Status: 줄을 요구한다. 없으면 QA 검사(patch-status)가 경고 또는 에러를 낸다 (K5 3.4). 값의 형식은 다음과 같다 (OE 문서 기준, 기억 기반 — 사용하는 Yocto 릴리스의 문서로 확인).

값뜻이 노트의 예
Pending아직 upstream에 안 보냄 (보낼 예정)0002, 0003 드라이버 수정
Submitted [where]보냈다. 메일링 리스트 링크(lore) 등0002를 보내면 이 값으로 바꾼다
Backport [version or commit]upstream에 이미 있는 것을 가져옴0001
Denied [reason]upstream이 거절했다—
Inactive-Upstream [lastcommit/lastrelease]upstream 프로젝트가 죽었다—
Inappropriate [reason]upstream에 보낼 성격이 아님0004 보드 DT, 0005 설정, 0006 HACK

이 태그는 "이 패치는 언젠가 사라지나, 영원히 들고 가나" 를 한 줄로 기록한다. 8절에서 이 태그와 git cherry로 스택을 감사(audit)한다.

3.4 번호와 이름#

git format-patch는 0001-<제목을-하이픈으로>.patch 형식으로 파일을 만든다. 번호는 스택 안의 자리일 뿐 ID가 아니다. 중간에 패치를 하나 끼우면 뒤의 번호가 전부 바뀐다 (7절에서 실제로 일어난다). 그래서 실무에서는 다음 중 하나를 쓴다.

  • 레시피의 SRC_URI에 파일 이름 전체를 쓰고, 번호가 바뀌면 같이 고친다 (작은 스택).
  • 번호를 띄워 둔다: 범주별로 0100-(backport), 0200-(fix), 0500-(board), 0900-(debug). git format-patch --start-number로 시작 번호를 정할 수 있다.
  • 범주별 하위 디렉터리를 쓴다 (files/backport/, files/board/, files/debug/). 이 노트는 debug/ 하나만 분리한다.

4. 실습 A — git으로 벤더 패치 스택 만들기#

시나리오: 우리 회사 제품 "P2 SensorKit"은 i.MX8M Plus SoM + 캐리어 보드이고, I2C3에 ADXL345 가속도계가 달려 있다. 가속도계 전원(3.3 V)은 GPIO로 켜는 고정 레귤레이터에서 온다. 우리는 커널 6.18.55 위에 패치를 얹는다.

4.1 예제 3 — 기준 저장소 만들기#

무엇을 확인하나: 랩 소스에서 필요한 부분만 복사해 git 저장소를 만들고 v6.18.55 태그를 붙인다. 날짜·작성자를 고정해서 누가 언제 돌려도 같은 커밋 해시가 나오게 한다 (9절 재현성의 출발점).

출력에서 볼 것: 파일 1366개, 작업 트리 18 MB, 압축된 git 객체 3.36 MiB. 해시 bb21fc9는 날짜·작성자·내용이 같으면 몇 번을 돌려도 같다 (이 노트의 모든 실행에서 같았다). 실제 회사에서는 이 자리에 벤더 커널 저장소(또는 linux-stable)의 태그가 온다.

4.2 예제 4 — 변경 종류별 토픽 브랜치#

무엇을 확인하나: 변경을 종류별 브랜치로 나눠 만든다. 각 브랜치는 v6.18.55에서 따로 시작한다. 이렇게 하면 "드라이버 수정만 upstream에 보내기", "HACK만 빼고 빌드하기"가 브랜치 선택으로 끝난다. linux-next가 maintainer 트리들을 모으는 방식과 같은 생각이다.

만드는 것:

  • sim/mainline-next — 가상의 upstream. 무관한 정리 커밋 X 하나가 있다 (실습용, 실제 커밋 아님).
  • topic/backports — X를 cherry-pick -x로 가져온다 → Upstream-Status: Backport [sha].
  • topic/iio-fixes — ADXL345 드라이버가 vs/vdd-io 전원을 켜도록 수정 → Pending. 6.18.55의 adxl345_core.c에는 레귤레이터 코드가 없고, 바인딩 문서(adi,adxl345.yaml)에도 supply 속성이 없다 (grep regulator로 확인). 그래서 upstream에 보내려면 바인딩 패치가 따로 필요하다는 메모를 태그에 남긴다.
  • topic/board — 보드 DT + Makefile 한 줄, 그리고 config fragment → Inappropriate.
  • topic/debug — 버퍼 enable마다 로그를 찍는 HACK → Inappropriate [debug hack].

먼저 보드 DT 파일이다 (스크립트가 복사해 넣는다). DT 문법은 D2~D5, 회로도에서 이 노드를 끌어내는 과정은 P4에서 다룬다. 핀 설정은 I2C3·UART2만 넣고 GPIO 핀 설정은 생략한 단순화 버전이다.

(지면 때문에 실제 파일보다 줄을 합쳐 보였다. 실제 파일은 68줄이고 내용은 같다. 핀 값 0x400001c2, 0x140은 6.18.55의 imx8mp-evk.dts에서 그대로 가져왔다.)

이제 토픽 브랜치를 만드는 스크립트다. 커밋은 -s(Signed-off-by)를 붙인다. OE 레이어 패치와 커널 패치 모두 Signed-off-by를 요구한다.

출력에서 볼 것: 토픽 브랜치 4개와 가상 upstream 1개. 소스 편집을 sed/python 치환으로 한 것은 스크립트로 재현하기 위해서다. 실무에서는 에디터로 고치고 git commit한다. 드라이버 수정의 실제 diff는 이렇다 (git diff v6.18.55 topic/iio-fixes, 컨텍스트 일부 생략).

devm_regulator_bulk_get_enable()은 레귤레이터 여러 개를 얻고 켜고, 드라이버가 떨어질 때 자동으로 끄는 devm 헬퍼다 (H3). DT에 supply가 없으면 regulator core가 dummy regulator를 돌려줘서 기존 보드도 깨지지 않는다 (7절 QEMU 출력에서 확인).

4.3 예제 5 — 선형 통합 브랜치#

무엇을 확인하나: 토픽 브랜치들을 정해진 순서로 cherry-pick해 하나의 선형 브랜치 p2/bsp를 만들고 릴리스 후보 태그를 붙인다. Yocto나 quilt로 내보낼 스택은 선형이어야 한다 (merge 커밋은 패치 파일로 표현이 안 된다).

6. 실습 C — quilt로 같은 스택 다루기#

6.1 quilt가 무엇인가#

quilt는 git이 없던 시절부터 쓰인 "패치 큐 관리 도구"다. 원본 트리 위에 패치 파일들을 스택처럼 쌓고(push) 내리며(pop), 맨 위 패치를 편집한 뒤 다시 패치 파일로 저장(refresh)한다. 상태는 세 군데에 있다.

  • patches/series — 패치 순서 목록 (텍스트 파일 한 개 = 스택 정의)
  • patches/*.patch — 패치 파일들
  • .pc/ — 적용된 각 패치가 건드리기 전의 원본 파일 사본 (pop할 때 되돌리는 데 쓴다)

왜 아직 배우나: Yocto의 devshell, Debian 패키지(debian/patches/), 벤더가 tarball + 패치 디렉터리로 주는 BSP 등에서 여전히 만난다. 그리고 "series 파일 = 스택" 이라는 모델이 Yocto SRC_URI의 패치 목록과 정확히 같다. Don에게 익숙한 말로는 "ROM 패치 테이블": 순서가 정해진 패치 목록을 부팅 때 위에서부터 차례로 적용하는 것이다.

기본 출력 형식은 git 스타일이 아니라서(Index: 줄, quilt-tree.orig/ 경로), 이 노트는 git과 같은 a/ b/ 형식이 나오도록 설정 파일을 하나 썼다.

함정 하나를 먼저 밝힌다. 처음에는 이 값들을 환경 변수(export QUILT_REFRESH_ARGS=...)로 줬는데 효과가 없었다. 설치된 전역 quilt.quiltrc가 같은 변수(QUILT_REFRESH_ARGS="--no-timestamps --backup")를 설정하고 있어서 환경 변수를 덮어썼기 때문이다. --quiltrc로 파일을 명시하니 해결됐다.

6.2 예제 10 — 원본 트리에 시리즈 올리기 (그리고 quilt import의 함정)#

무엇을 확인하나: git이 없는 원본 트리(git archive로 풀어 낸 것)에 5절의 패치 파일을 quilt 시리즈로 올린다. 먼저 순진하게 quilt import를 반복해서 써 본다.

출력에서 볼 것: 순진한 quilt import 반복은 순서를 뒤집었다. quilt import는 새 패치를 "현재 맨 위에 적용된 패치 바로 다음"에 끼우는데, 아무것도 적용되지 않은 상태에서는 매번 맨 앞에 들어가기 때문이다. 이대로 push -a하면 HACK부터 적용된다. 해결은 단순하다. series 파일을 직접 쓴다. 고친 뒤 push -a로 다섯 개가 다 올라갔고 맨 위(top)는 HACK이다.

6.3 예제 11 — quilt의 일상 루프: 중간 패치 고치기, 새 패치 얹기#

무엇을 확인하나: (1) 스택 중간의 DT 패치(0003)에서 레귤레이터 기동 지연을 2 ms → 5 ms로 바꾼다: 그 패치까지 pop → 파일 수정 → refresh → 다시 push. (2) 맨 위에 새 패치 0006을 만든다: new → add → 수정 → refresh → header.

출력에서 볼 것:

  • pop은 위에서부터 하나씩 내리며 .pc/의 원본으로 파일을 되돌린다 (Restoring, 새로 만든 파일은 Removing).
  • 0003을 고칠 때는 add가 필요 없었다. 그 DTS 파일은 이미 0003이 추적하는 파일이다 (quilt files). 아직 추적하지 않는 파일을 고칠 때는 반드시 quilt add를 먼저 해야 한다. 그래야 quilt가 수정 전 사본을 .pc/에 떠 둔다. 순서를 바꾸면 수정 내용이 패치에 안 들어간다. 이것이 quilt의 가장 흔한 실수다.
  • quilt header -r은 패치 헤더(설명)를 표준 입력으로 바꾼다. 여기에 Upstream-Status를 넣었다.
  • 함정: 0003을 refresh하면 quilt가 diff 본문만 다시 쓰고 헤더는 그대로 둔다. git이 만들었던 헤더의 diffstat(2 files changed, 69 insertions(+) 같은 줄)은 이제 실제 내용과 맞지 않을 수 있다. quilt refresh --diffstat는 diffstat 프로그램이 필요한데 이 VM에는 없다 (실행해 보니 sh: 1: diffstat: not found). git으로 되돌려 다시 내보내면 깔끔해진다 (다음 예제).

6.4 예제 12 — quilt → git 되돌리기와 range-diff#

무엇을 확인하나: quilt로 고친 스택을 git으로 되돌려 넣고(git quiltimport), 원래 git 스택과 무엇이 달라졌는지 git range-diff로 짝지어 본다. 진실의 원천(source of truth)을 하나로 유지하는 연습이다.

출력에서 볼 것:

  • range-diff가 두 스택의 커밋을 짝지었다. =는 내용이 같음, !는 바뀜(0003의 5 ms 수정), >는 새로 생김(0006). 해시는 다르지만(커밋 시각·작성 경로가 다름) 내용이 같다는 것을 정확히 알아낸다. 벤더 BSP 새 버전을 받았을 때 "이전 BSP 대비 무엇이 바뀌었나"를 볼 때도 같은 도구를 쓴다 (P5).
  • 0006의 커밋 제목이 파일 이름(0006-arm64-dts-...)이 됐다. 0006의 헤더에는 From:/Subject: 줄이 없어서, git quiltimport가 제목을 찾지 못하고 패치 이름을 썼다. 교훈: quilt로 새 패치를 만들 때도 메일 형식 헤더(From:, Subject:, 빈 줄, 본문, Upstream-Status, Signed-off-by)를 쓰면 git과 오가는 데 문제가 없다. 또는 처음부터 git에서 만들고 quilt는 "읽기·적용용"으로만 쓴다.

7.1 예제 13 — QEMU에서 우리 드라이버 올려 보기 (수정 전)#

무엇을 확인하나: 실제 보드가 아직 없다고 치고, 랩 커널(6.18.55)을 QEMU로 부팅해 우리 패치가 들어간 ADXL345 드라이버를 올려 본다. 칩은 i2c-stub으로 흉내 낸다. i2c-stub은 "레지스터 256개짜리 가짜 I2C 칩"을 만드는 커널 모듈로, 실제 드라이버가 probe할 수 있다 (H5). 랩 기본 커널에는 i2c-stub이 없어서 소스(drivers/i2c/i2c-stub.c)를 out-of-tree 모듈로 빌드했다. DEVID 레지스터(0x00)에 ADXL345의 ID 0xE5를 미리 써 두고, sysfs new_device로 장치를 만든다. 같은 스크립트를 수정 전(스택이 0002까지인 커밋 62eb9a7)과 수정 후(7.2절 이후의 p2/bsp)에 돌린다.

수정 전 결과만 먼저 본다 (전체 출력은 7.3절).

출력에서 볼 것:

  • 우리 0002 패치는 잘 동작한다. DT가 없으니 supply가 없고, regulator core가 dummy regulator로 대신했다. "supply가 없는 기존 보드도 안 깨진다"를 확인한 셈이다.
  • 그런데 IIO 장치가 안 생겼다. 에러 메시지도 없다. probe가 조용히 실패했다.

7.2 원인 찾기와 수정 (예제 14)#

드라이버를 읽으면 이유가 보인다. 6.18.55의 adxl345_core_probe()는 칩 정보를 이렇게 얻는다.

device_get_match_data()는 펌웨어 노드(DT/ACPI) 의 매치 테이블만 본다. sysfs new_device나 보드 코드로 만든 장치에는 펌웨어 노드가 없으므로 NULL이 나오고, -ENODEV로 끝난다. 그리고 driver core는 probe가 -ENODEV/-ENXIO를 돌려주면 "이 드라이버의 장치가 아니다"로 보고 에러를 찍지 않는다 (G3). 그래서 조용했다. I2C 쪽에는 이미 답이 있다: i2c_get_match_data()는 펌웨어 노드를 먼저 보고, 없으면 I2C id 테이블({ "adxl345", ... })의 driver_data로 돌아간다. SPI에는 spi_get_device_match_data()가 있다.

이것은 6.18.55 트리에서 우리가 관찰한 동작이다. 이후 mainline에서 같은 문제가 이미 고쳐졌는지는 확인하지 않았다 — 실무라면 upstream에 보내기 전에 maintainer 트리와 lore에서 먼저 검색한다 (8절, P7). 그래서 수정은 topic/iio-fixes에 Pending으로 얹는다.

I2C 쪽 변경은 한 줄이다.

설계 포인트: 수정은 토픽 브랜치에 한다. 통합 브랜치(p2/bsp)에 직접 커밋하면 다음 통합 때 사라지거나, upstream으로 보낼 패치를 고를 때 섞인다. 또 이 수정은 core 함수의 시그니처를 바꾸므로 I2C·SPI 글루를 같은 커밋에서 함께 고쳐야 한다 (중간 커밋에서 빌드가 깨지면 git bisect가 망가진다 — 커널 커뮤니티의 "각 패치는 빌드돼야 한다" 규칙).

8. 어떤 패치가 upstream에 갔나 — 스택 추적#

그림 5 — 패치 하나의 일생. Upstream-Status는 이 그림에서 지금 어느 칸에 있는지를 기록한다. 스택 관리의 목표는 파란 칸(Pending/Submitted)에 머무는 패치를 줄이는 것이다.

8.1 예제 15 — git cherry로 "이미 upstream에 있는 것" 찾기#

무엇을 확인하나: 시간이 흘러 maintainer가 우리 드라이버 수정 두 개(0002, 0003)를 그대로 받아들였다고 가정한다. 가상 upstream sim/mainline-next에 그 두 커밋을 넣고, 우리 스택과 비교한다. git cherry는 patch-id(내용 해시)로 비교하므로 커밋 해시·작성 날짜가 달라도 같은 변경을 알아본다.

출력에서 볼 것: 아래 세 개(backport 1 + 수정 2)가 -, 즉 새 기준 위로 옮길 때 버릴 패치다. 위 세 개(DT, 설정, HACK)가 +, 계속 들고 갈 패치다. 이것이 그림 3의 "아래부터 사라진다"를 숫자로 본 것이다. 실제 리베이스(P5)에서 git rebase도 같은 patch-id 비교로 이런 커밋을 자동으로 건너뛴다 (E7 4.3의 dropping ... patch contents already upstream).

주의: maintainer가 패치를 고쳐서(공백, 변수 이름, 커밋 메시지 말고 코드) 받으면 patch-id가 달라져 +로 남는다. 그때는 git range-diff나 사람의 눈으로 "같은 의미"인지 판단하고, 우리 패치를 버린 뒤 upstream 커밋을 Backport로 다시 가져온다.

9. 고객 보드 레이어와 재현성#

9.1 meta-<company> — 벤더 위에 얹는 우리 레이어#

K5 1~2절이 레이어 스택과 kas lock을 다뤘다. BSP 관점의 규칙만 정리한다.

  1. 벤더 레이어는 수정하지 않는다. 바꿀 것은 전부 우리 레이어의 bbappend·machine conf·패치로. 벤더 레이어를 포크해서 고치면 다음 BSP 릴리스 때 머지 지옥이 된다.
  2. 보드 하나 = MACHINE 하나. p2-sensorkit.conf가 SoC include를 require하고 KERNEL_DEVICETREE, U-Boot 설정, 시리얼 콘솔을 정한다. EVK와 우리 보드가 같은 레이어 스택으로 빌드되게 해 두면 "EVK에서는 되는데 우리 보드에서는 안 된다"를 바로 비교할 수 있다 (P1 bring-up의 기본 전술).
  3. BSP 레이어와 제품 레이어를 나눈다. meta-p2-bsp(보드: 커널·U-Boot·펌웨어)와 meta-p2-product(앱·이미지·배포 설정). 보드가 같은 다른 제품이 BSP 레이어를 재사용한다.
  4. 벤더 블롭 버전도 고정 대상이다. 펌웨어·GPU 라이브러리 패키지의 버전은 벤더 레이어의 레시피 버전이 정한다. 레이어 커밋을 고정하면 함께 고정된다. 블롭을 갈아 끼울 일이 있으면 그것도 우리 레이어의 bbappend로.

9.2 예제 16 — 패치 내보내기를 바이트 단위로 재현 가능하게#

무엇을 확인하나: 통합 브랜치를 "내일 다시 만들면"(cherry-pick 시각이 달라 해시가 바뀜) 레이어의 패치 파일이 바뀌는가? 기본 format-patch와 --zero-commit --no-signature를 비교한다.

출력에서 볼 것:

  • 기본 출력은 내용이 같아도 해시가 다르다. 차이는 첫 줄 From <커밋 sha> 하나다. 또 파일 끝에 git 버전(2.53.0) 서명이 붙는다 — 동료의 git 버전이 다르면 그것만으로 diff가 생긴다.
  • --zero-commit --no-signature로 내보내면 두 번의 sha256이 같다. 레이어 저장소의 리뷰 diff에 "의미 없는 변경"이 섞이지 않고, Yocto의 패치 파일 체크섬·sstate도 불필요하게 깨지지 않는다.
  • 작성 날짜(Date:)는 커밋의 author date라 cherry-pick으로 바뀌지 않는다. 사람 손으로 amend하면 바뀐다 — 그것은 의미 있는 변경이니 괜찮다.

9.3 재현성 체크리스트 (BSP 관점)#

10. 커널 안에서는 무슨 일이 일어나나#

이 노트의 실습에서 커널 안을 지나간 경로 세 개를 정리한다.

  1. devm_regulator_bulk_get_enable() (0002 패치): 이름 배열("vs", "vdd-io")마다 regulator core가 DT의 <name>-supply 속성을 찾는다 (of_get_regulator 계열). 찾으면 그 레귤레이터의 consumer가 되고 regulator_enable()이 고정 레귤레이터 드라이버의 GPIO를 올린다. 이때 DT의 startup-delay-us만큼 기다린다 (6.3절에서 5 ms로 고친 값). 못 찾으면 supply ... not found, using dummy regulator를 찍고 더미를 돌려준다 (7.1절 출력). devm이라 드라이버 unbind 때 역순으로 disable된다 (G3, H3).
  2. match data 경로 (0003 패치): I2C 장치가 생기면 I2C core가 드라이버를 매칭하는 순서는 OF 테이블 → ACPI 테이블 → I2C id 테이블이다. probe 안에서 "어떤 칩인가"를 묻는 함수도 이 순서를 따라야 한다. device_get_match_data()는 앞의 둘(펌웨어 노드)만 보고, i2c_get_match_data()는 세 번째까지 본다. 그래서 DT로 만든 장치에서는 둘 다 동작하고, id 테이블로 만든 장치에서는 앞의 것만 실패했다 (D3, G2).
  3. 펌웨어 블롭 (1.4절): SDMA 드라이버가 probe 중 request_firmware_nowait() 계열로 imx/sdma/sdma-imx7d.bin을 요청하면 firmware loader가 /lib/firmware/에서 파일을 찾는다. 없으면 Direct firmware load for ... failed with error -2(ENOENT) 로그가 난다 (6.18.55 drivers/base/firmware_loader/main.c에 이 문자열이 있다). BSP의 펌웨어 패키지 버전과 드라이버가 기대하는 파일 형식이 맞아야 한다 (G10).

그리고 블롭 ABI 락인(1.5절)은 커널 안에서 이렇게 보인다. 벤더 GPU 모듈은 out-of-tree 모듈이라 커널의 vermagic(버전 + 주요 설정)이 맞아야 로드되고 (E3), 커널 내부 API(DRM, dma-buf, mm)가 바뀌면 소스 수정 없이는 빌드조차 안 된다 (E4). 유저 라이브러리는 그 모듈의 ioctl 번호·구조체 레이아웃에 맞춰 컴파일돼 있다 (G5). 세 개의 "버전 짝"이 동시에 맞아야 하는 것이다.

11.1 센서 키트 첫 주 — "EVK BSP를 그대로 띄우고, 차이를 패치로"#

11.2 Jetson — 벤더 커널이 사실상 고정인 경우#

NVIDIA Jetson은 GPU·카메라(ISP)·NVENC 스택이 L4T의 커널 모듈과 유저 라이브러리에 묶여 있어서, 실제 제품은 L4T 커널을 쓰는 것이 일반적이다 (E7 3.2, 기억 기반). 이 경우 우리 일은 "커널 선택"이 아니라 L4T 버전 업그레이드 때 우리 패치 스택을 옮기는 비용을 줄이는 것이다. 그래서 커널 패치는 최소로 (DT·out-of-tree 모듈 위주로) 하고, 우리 드라이버는 out-of-tree 모듈로 유지하는 팀이 많다. meta-tegra를 쓰면 L4T 블롭 버전도 Yocto 레시피로 고정된다.

11.3 고객의 보안 감사 — "CVE-XXXX가 이 제품에 해당되나?"#

벤더 커널 기반 제품이라면 답하는 순서: (1) 벤더 브랜치의 기준 stable 버전(1.5절처럼 SUBLEVEL)과 마지막 머지 날짜 확인. (2) 그 CVE의 수정 커밋이 기준 버전 이후 stable에 들어갔는지 확인. (3) 들어갔지만 벤더가 아직 머지 안 했다면 우리 스택에 Backport [sha]로 얹는다 (cherry-pick -x). (4) 8.2절 장부에 "벤더가 따라오면 drop" 표시. 벤더가 stable을 늦게 따라올수록 이 backport가 쌓인다 — 2.2절 매트릭스의 "보안 수정" 행이 현실이 되는 장면이다.

11.4 NPU를 쓰는 로보틱스 제품#

AI 가속기 진로와 연결되는 장면이다. NPU 유저 런타임이 벤더 블롭이고 커널 모듈과 짝이면(1.5절), 커널을 최신 LTS로 올리고 싶어도 NPU 스택 때문에 못 올린다. 선택지는 (a) 벤더 BSP 일정에 맞춘다, (b) 벤더 모듈을 새 커널로 포팅해 우리 스택에 얹는다 (부채 증가), (c) mainline drivers/accel/의 오픈 드라이버(1.4절 rocket처럼 해당 SoC에 있다면)로 옮긴다. O4에서 DRM accel 구조를 다룬다.

13. 면접에서 이렇게 말한다#

Q. "What does a vendor BSP typically contain, and which parts would you expect to own?"

A. 부트 체인 포크(이미지 패커, DDR 트레이닝 FW, TF-A, OP-TEE, U-Boot), LTS 기반 벤더 커널과 EVK DT, /lib/firmware용 블롭, GPU/NPU 유저 라이브러리, Yocto 레이어, 그리고 릴리스 노트·errata다. 우리가 소유하는 것은 그 위의 회사 레이어: 보드 DT, 커널·U-Boot 패치, 설정 조각, MACHINE 정의다. 나머지는 버전을 고정해서 쓰고, 고칠 일이 있으면 패치로 얹는다.

A BSP is the vendor's bundle: forked boot chain — imaging tool, DDR training firmware, TF-A, OP-TEE, U-Boot — a vendor kernel that's an LTS tag plus thousands of vendor commits, the EVK device trees, firmware blobs for /lib/firmware, userspace GPU or NPU libraries, Yocto layers, and the release notes and errata. What I own is our layer on top: the board DT, our kernel and U-Boot patches, config fragments and the machine definition. Everything below is pinned by commit, and if I need to change it, I carry a patch rather than editing the vendor's tree.

Q. "Vendor kernel or mainline LTS — how would you decide for a new product?"

A. 첫째, 필요한 블록(ISP·NPU·GPU·코덱)이 mainline에 있나. 둘째, 없다면 그 블록의 유저 블롭이 벤더 커널 모듈과 ABI로 묶였나 — 묶였으면 사실상 벤더 커널이다. 셋째, 벤더가 stable을 얼마나 자주 머지하나(보안). 넷째, 제품 수명과 LTS/CIP 수명. 어느 쪽이든 우리 코드는 upstream 스타일로 쓰고 스택을 작게 유지해서 나중에 갈아탈 수 있게 한다.

I go through a few questions. Are the blocks we need — ISP, NPU, GPU, codecs — supported in mainline? If not, is the userspace blob tied to a vendor kernel module ABI? If yes, the vendor kernel is effectively mandatory. Then security: how far behind stable is the vendor branch and how often do they merge it. Then lifetime versus LTS or CIP SLTS. Either way, I write our drivers and DT in upstream style and keep the patch stack small, so switching later is a project, not a rewrite.

꼬리 질문: "How would you check how far the vendor branch is behind stable?" → Makefile의 SUBLEVEL, 마지막 머지 날짜, git merge-base로 기준 태그 확인 (1.5절, 2.4절).

Q. "How do you manage your kernel patches on top of the vendor BSP?"

A. 변경 종류별 토픽 브랜치(backport, 드라이버 수정, 보드, 디버그)를 기준 태그에서 따로 만들고, 스크립트로 정해진 순서의 선형 통합 브랜치를 만든다. 순서는 upstream으로 갈 것부터, HACK은 맨 위. 모든 패치에 Upstream-Status와 Signed-off-by. 통합 브랜치에서 format-patch --zero-commit으로 Yocto 레이어에 내보내고, 패치 디렉터리를 원본에 적용한 결과가 git과 같은지 CI에서 확인한다.

I keep one topic branch per kind of change — backports, driver fixes, board support, debug hacks — each based on the same tag, and a script builds a linear integration branch in a fixed order: upstream-bound patches first, board-specific next, hacks on top and excluded from release builds. Every patch has a Signed-off-by and an Upstream-Status line. I export with format-patch, zero-commit, into our Yocto layer, and CI checks that applying the patch directory to the pristine source gives exactly the git tree.

Q. "When a new BSP arrives, how do you know which of your patches you can drop?"

A. git cherry로 새 기준 대비 patch-id가 같은 커밋을 찾는다 — -는 이미 upstream에 있다. 고쳐서 머지된 것은 patch-id가 달라서 안 잡히니 range-diff와 Upstream-Status의 lore 링크로 사람이 확인한다. 그리고 Backport [sha] 패치는 그 sha가 새 기준의 조상인지 merge-base --is-ancestor로 본다. 실제 리베이스 절차는 P5.

First git cherry against the new base — anything marked minus has an identical patch upstream and gets dropped. Patches that were modified during review won't match by patch-id, so for those I follow the Submitted link and compare with range-diff. Backports carry the upstream sha from cherry-pick -x, so I just check whether that commit is an ancestor of the new base.

Q. "What does 'blob ABI lock-in' mean and why does it matter?"

A. GPU·NPU 유저 라이브러리가 바이너리이고, 특정 버전의 벤더 커널 모듈 ioctl에 맞춰져 있다는 뜻이다. 커널을 올리려면 그 모듈을 새 커널로 포팅해야 하는데 커널 내부 API는 안정적이지 않아서 비용이 크고, 벤더 지원도 끊긴다. 그래서 커널 업그레이드 일정이 벤더 BSP 일정에 묶인다. 오픈 드라이버(etnaviv, DRM accel)가 있으면 탈출구가 된다.

The userspace driver is a binary built against one specific version of the vendor's kernel module interface. To move the kernel, you have to port that module to a new kernel whose internal APIs have changed, and you lose vendor support while doing it. So your kernel schedule becomes the vendor's BSP schedule. An open driver in mainline, like etnaviv or a DRM accel driver, is the way out, if its feature set is good enough.

Q. "How do you make a BSP build reproducible five years from now?"

A. 레이어·레시피를 sha로 고정하고(kas lock, SRCREV), 벤더 저장소와 소스 tarball을 우리 미러에 보관하고, 패치는 결정적으로 내보내고, 커널 저장소와 레이어 저장소에 같은 릴리스 태그를 단다. CI에서 같은 입력으로 두 번 빌드해 해시를 비교한다.

Pin everything by hash — layers through a kas lock file, sources through SRCREV — mirror the vendor repositories and source tarballs on our own servers because vendors do move or rewrite branches, export patches deterministically, and tag the kernel repo and the layer repo together for each release. Then CI rebuilds from the same inputs and compares image hashes.

Q. "Tell me about working with a vendor SDK where you had to carry local changes."

A. (Don의 SSD 경험을 그대로) 컨트롤러 벤더 SDK 위에 자사 FTL·에러 처리 패치를 얹어 양산했다. 패치마다 "벤더 반영 요청 여부"를 장부로 관리했고, 새 SDK가 오면 반영된 것은 버리고 남은 것만 옮겼다. Linux BSP에서는 같은 일을 Upstream-Status, git cherry, Yocto 패치 디렉터리로 한다는 것을 이 노트의 실습으로 해 봤다.

On enterprise SSD firmware we built on a controller vendor's SDK and carried our own patches for error handling and performance. We kept a ledger of every local change and whether we'd asked the vendor to take it, and when a new SDK drop arrived we dropped what they'd absorbed and ported the rest. In Linux the same discipline maps to Upstream-Status tags, git cherry against the new base, and a patch directory in our Yocto layer — I've practiced exactly that flow on a 6.18 tree.

16. 요약 & 체크리스트#

벤더 BSP는 부트 체인 포크, LTS 기반 벤더 커널과 DT, 펌웨어·유저스페이스 블롭, Yocto 레이어, 문서로 이루어진다. 커널 선택은 "mainline이 더 좋다"가 아니라 필요한 블록의 upstream 상태, 블롭 ABI 락인, 벤더의 stable 추종, 제품 수명으로 정한다. 어느 쪽이든 우리 커널은 "기준 태그 + 패치 스택"이고, 스택은 토픽 브랜치 → 순서가 정해진 선형 통합 브랜치 → 결정적 format-patch → Yocto 패치 디렉터리로 관리한다. 모든 패치에 Upstream-Status를 달고, git cherry로 upstream에 간 것을 찾아 버리며, 장부로 "언제 사라질지"를 관리한다. quilt는 같은 모델(series 파일)의 다른 도구이고, git과 오갈 때는 진실의 원천을 하나로 둔다. 스택이 작고 깨끗할수록 다음 LTS로의 이동(P5)이 쉬워진다.
