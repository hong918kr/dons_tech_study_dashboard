이 노트를 다 읽으면: struct dev_pm_ops의 23개 콜백이 시스템 suspend·hibernate·runtime PM의 어느 순간에 불리는지 실제 로그로 설명할 수 있다 · supplier/consumer 두 드라이버의 suspend 순서를 dpm_list와 device link로 맞출 수 있다 · runtime PM(autosuspend, usage count)과 regmap regcache로 "전원이 꺼져도 설정이 돌아오는" 드라이버를 짤 수 있다 · wakeup source와 wake IRQ로 장치가 시스템을 깨우게(또는 suspend를 막게) 만들 수 있다 왜 필요한가: "resume 뒤에 I2C 센서가 죽는다", "배터리가 하룻밤에 다 닳는다", "버튼을 눌러도 안 깬다" — 양산 직전에 터지는 버그 대부분이 드라이버 PM 코드에서 나오고, 면접관은 이걸로 드라이버 완성도를 가늠한다 Don 기준 난이도: SSD 펌웨어의 power state 진입·복귀(컨텍스트 저장, 클럭 게이팅, wake 이벤트)는 이미 안다 / 새로 배울 것은 "수백 개 드라이버의 순서를 커널이 정하는 규칙"과 runtime PM의 참조 카운트 모델 선행 노트: G2(device model, device link), G3 §12(DEFINE_SIMPLE_DEV_PM_OPS 한 쌍), H2 §9(regcache로 suspend/resume), H3(clk/regulator), H4(pinctrl sleep state, gpio-sim), H6(IRQ 컨트롤러), N5(전원 관리 시스템 관점)

0. 큰 그림 — 이게 왜 필요한가#

0.1 펌웨어에서는 이렇게 했다#

SSD 펌웨어에서 NVMe의 낮은 power state(PS3/PS4)로 들어갈 때를 떠올려 보자. 호스트가 들어가라고 하거나(Set Features), 일정 시간 일이 없으면 스스로 들어간다(APST — Autonomous Power State Transition). 진입 순서는 펌웨어가 직접 짠다: 진행 중인 명령을 마무리 → NAND 채널을 멈춤 → 컨트롤러 레지스터 컨텍스트를 always-on SRAM에 저장 → 클럭 게이팅 → PLL off. 깨어날 때는 정확히 거꾸로. 그리고 어떤 이벤트(PCIe 링크 활동, 타이머)가 칩을 깨울지 미리 설정해 둔다.

Linux에서도 하는 일은 똑같다. 다른 점은 그 순서를 한 사람이 짜지 않는다는 것이다. 장치마다 드라이버가 따로 있고, 각 드라이버는 "내 장치를 재우고 깨우는 법"만 콜백으로 커널에 준다. 순서는 PM core(drivers/base/power/)가 장치 트리 관계와 device link를 보고 정한다. 그래서 드라이버 작성자가 알아야 할 것은 세 가지다.

  1. 언제 불리나 — 어떤 콜백이 어느 단계(phase)에서, IRQ가 켜진 상태인지 꺼진 상태인지.
  2. 누구 다음에 불리나 — 내가 쓰는 버스·클럭·레귤레이터가 나보다 먼저 잠들면 안 된다.
  3. 무엇을 잃나 — 전원이 꺼지면 레지스터가 날아간다. 무엇을 저장하고 무엇을 다시 쓸지.

0.2 두 개의 세계: 시스템 sleep과 runtime PM#

그림 1 — Linux 드라이버 PM의 두 축. 시스템 sleep은 전체가 함께 자는 것(APST가 아니라 호스트가 시키는 PS 전환에 가깝다), runtime PM은 장치마다 놀면 혼자 자는 것(APST에 가깝다). 둘은 별개의 상태 기계지만 같은 하드웨어를 다루므로 pm_runtime_force_suspend/resume으로 잇는다.

  • 시스템 sleep (system suspend / hibernation): 유저가 /sys/power/state에 freeze(s2idle), mem(suspend-to-RAM), disk(hibernate)를 쓰면 시작한다. 유저 프로세스를 얼리고(freeze), 모든 장치의 콜백을 정해진 순서로 부르고, CPU를 idle에 두거나 끈다. 전원·열 관점의 시스템 그림은 N5가 다룬다.
  • runtime PM: 시스템은 살아 있고, 장치 하나가 일이 없으면 그 장치만 끈다. 드라이버가 pm_runtime_get/put으로 "지금 쓴다/다 썼다"를 알리면 PM core가 usage count가 0이 될 때 runtime_suspend를 부른다.

1. 실습 판 깔기#

1.1 공급자 — 가짜 버스 컨트롤러와 그 뒤의 칩#

공급자 쪽 API. 소비자는 이 세 함수만 쓴다.

"칩"은 공급자 모듈 안의 배열 8바이트다. n6_bus_xfer()는 실제 I2C 코어의 __i2c_check_suspended()(6.18 drivers/i2c/i2c-core.h)를 흉내 내서, 컨트롤러가 시스템 suspend 중이거나 runtime-suspended면 거부한다. 칩 전원을 끄면 레지스터를 0xEE로 오염(poison) 시키고, 켜면 POR(power-on reset) 값으로 되돌린다. raw 속성은 버스를 거치지 않고 배열을 그대로 보여 준다 — 로직 분석기로 칩을 직접 보는 것에 해당하는 뒷문이다.

공급자 드라이버. 모든 phase의 콜백을 로그만 찍게 채웠다. 매크로 묶음(SYSTEM_SLEEP_PM_OPS 등)은 §2에서 푼다.

출력에서 볼 것은 아직 없다. 두 가지만 기억하자: bus_suspend()에서 n6_bus_sys_suspended = true가 되는 순간부터 소비자의 전송은 실패한다. probe에서 pm_runtime_set_suspended() + devm_pm_runtime_enable()로 "평소에는 꺼져 있고, 누가 쓰면 켜지는" 장치로 시작한다.

1.2 보드 파일 — 등록 순서를 고를 수 있게#

dpm_list(PM core가 suspend 순서를 정하는 목록)는 장치를 등록한 순서로 만들어진다(§3.3). 그래서 등록 순서를 모듈 파라미터 imu_first로 바꿀 수 있게 했다. wake GPIO는 gpiod_lookup_table로 gpio-sim 뱅크(라벨 n6_sim) 0번 라인에 연결한다.

1.3 소비자 — regmap, device link, probe#

regmap은 버스 백엔드 대신 reg_read/reg_write 콜백으로 n6_bus_xfer()를 부른다(H2 §2의 "버스 없는 regmap"). reg_defaults는 칩의 POR 값과 정확히 같아야 한다 — §5에서 왜 그런지 본다. 모듈 파라미터 link=0이면 device link 없이 "공급자를 손으로 깨워 붙잡아 두는" 옛날 방식, link=1이면 device_link_add()다.

DL_FLAG_STATELESS는 "링크의 생명주기를 내가 관리한다"(probe/unbind에 따른 자동 관리 없음 — 그래서 device_link_del()을 devm 액션으로 걸었다), DL_FLAG_PM_RUNTIME은 "소비자가 runtime resume되면 공급자도 먼저 resume", DL_FLAG_RPM_ACTIVE는 "링크를 만드는 지금 공급자를 깨워 둔다"(probe 안에서 바로 레지스터를 써야 하니까)이다. 링크 플래그 전체는 G2 §8과 docs.kernel.org의 Device links 문서에 있다.

probe의 runtime PM 순서가 정석이다: 하드웨어를 켜고 설정한 다음 pm_runtime_set_active()(PM core에게 "지금 켜져 있다"고 알림) → autosuspend 설정 → devm_pm_runtime_enable(). probe가 끝나면 driver core가 pm_request_idle()을 부르고(6.18 drivers/base/dd.c), usage count가 0이므로 500 ms 뒤 autosuspend된다. devm_pm_runtime_enable()은 remove 때 pm_runtime_disable()과 pm_runtime_dont_use_autosuspend()까지 해 준다.

1.4 빌드와 부팅 스크립트#

게스트에서 모든 테스트가 쓰는 공통 스크립트. gpio-sim 칩을 configfs로 만들고(H4 §7.3), 모듈을 순서대로 올리는 up, 상태를 한 줄로 찍는 rt, wake 라인에 엣지를 만드는 pulse를 정의한다.

2.2 매크로 — 6.x의 관용구#

예전 드라이버는 이렇게 썼다.

#ifdef는 설정 조합에 따라 컴파일 에러·경고가 숨고, __maybe_unused는 함수가 링크에 남는다. 지금은 항상 컴파일하고, 설정이 꺼져 있으면 포인터를 NULL로 만들어 컴파일러가 죽은 코드로 지우게 한다. 6.18 소스에서 직접 확인한 정의다(발췌).

2.3 소비자의 dev_pm_ops#

이번 실습에서는 단계마다 로그를 찍어야 하므로 매크로 조각으로 직접 채웠다. 실제 드라이버라면 suspend_late/noirq처럼 할 일이 없는 콜백은 비워 둔다.

imu_suspend()가 핵심이다. 시스템 suspend 전에 칩에 마지막으로 써야 할 것(여기서는 칩 인터럽트 끄기)이 있으면, 장치가 runtime-suspended 상태일 수도 있으므로 먼저 깨운다(pm_runtime_resume_and_get). 그다음 wake를 설정하고, pm_runtime_force_suspend()로 runtime 콜백을 재사용해 전원을 끈다. resume에서는 pm_runtime_force_resume() 뒤에 끈 인터럽트를 다시 켠다 — 장치가 아직 runtime-suspended면 그 쓰기는 캐시에만 들어가고 다음 runtime resume의 regcache_sync가 칩에 쓴다.

2.4 콜백은 누가 부르나 — 버스 래퍼#

PM core는 드라이버 콜백을 바로 부르지 않을 수도 있다. 우선순위는 dev->pm_domain → dev->type->pm → dev->class->pm → dev->bus->pm → dev->driver->pm이다(6.18 drivers/base/power/main.c의 device_suspend() 등). platform 버스는 .suspend/.resume/.freeze... 6개에 platform_pm_suspend 같은 래퍼를 두고(USE_PLATFORM_PM_SLEEP_OPS), late/noirq는 두지 않는다. 그래서 다음 절 로그에서 suspend는 calling platform_pm_suspend로, late는 calling imu_suspend_late [n6_imu]로 찍힌다. SoC의 PM domain(genpd)이 붙은 장치는 domain 콜백이 먼저 불리고 그 안에서 드라이버 콜백을 부른다 — 전원 도메인 끄기는 domain이 한다(N5).

3. 시스템 suspend의 순서#

3.1 예제 2 — 모든 단계의 실제 순서 (링크 있음)#

무엇을 확인하나: 소비자(n6_imu)를 먼저 등록했지만 device link가 있을 때, s2idle 한 번 동안 두 드라이버의 콜백이 어떤 순서로 불리는지. pm_print_times(CONFIG_PM_SLEEP_DEBUG)는 콜백마다 "calling ... / returned ... after N usecs"를 찍어 준다.

출력에서 볼 것:

  • prepare는 정방향(bus → imu), suspend·late·noirq는 역방향(imu → bus), resume 계열은 정방향(bus → imu), complete는 역방향. PM core는 dpm_prepare()에서 dpm_list를 앞에서부터 돌며 준비된 장치를 dpm_prepared_list로 옮기고, dpm_suspend()는 그 목록을 뒤에서부터, resume은 앞에서부터 돈다.
  • 소비자 imu_suspend가 8.0 ms로 가장 길다: 장치가 runtime-suspended였으므로 깨우고(공급자도 링크 때문에 먼저 bus clock ON), regcache_sync, INT_EN 끄기, 다시 runtime_suspend까지 한 번에 했다. 공급자는 그 뒤에 잠든다 — 링크 덕분에 공급자가 아직 깨어 있을 때 소비자가 버스를 쓸 수 있었다.
  • enable_irq_wake(22) = -6(-ENXIO): gpio-sim의 irqchip(irq_sim)에는 irq_set_wake가 없어서 wake 설정이 실패한다. §8에서 다룬다.
  • resume 쪽에서 imu_resume은 장치를 깨우지 않았다. suspend 직전에 runtime-suspended였고 아무도 쓰지 않으니 pm_runtime_force_resume()이 "필요 없음"으로 판단한 것이다. 시스템 resume 직후 쓸데없이 모든 장치를 켜지 않는 것이 배터리 장비에서 중요하다.
  • 마지막 줄 근처 T32(kworker)의 bus clock OFF: complete 뒤 runtime PM이 다시 켜지고 공급자의 usage가 0이므로 비동기 idle → suspend가 일어났다.
  • s2idle 동안(52.86 → 55.32 s)은 로그가 없다. 2초 알람인데 2.46초인 것은 TCG + 부하 때문이다.

3.2 dpm_list — 순서는 어디서 오나#

  • 장치는 device_add() → device_pm_add()에서 dpm_list 꼬리에 붙는다. 그래서 기본 순서 = 등록 순서다. 부모는 자식보다 먼저 등록되므로(부모 없이 자식을 만들 수 없다) "자식이 부모보다 먼저 suspend, 부모가 자식보다 먼저 resume"이 자동으로 지켜진다.
  • 문제는 트리 밖의 의존성이다. IMU의 부모는 platform이지 I2C 컨트롤러가 아니다(이번 실습처럼 platform 장치끼리일 때). 실제 I2C 클라이언트는 어댑터의 자식이라 트리로 해결되지만, 클럭·레귤레이터·GPIO·PHY·IOMMU 공급자는 전부 트리 밖이다.
  • 해결책이 device link다. device_link_add()는 device_reorder_to_tail(consumer)로 소비자(와 그 자식·소비자들)를 dpm_list 꼬리로 옮긴다(6.18 drivers/base/core.c). 그리고 비동기 suspend에서는 dpm_wait_for_consumers()/dpm_wait_for_suppliers()가 링크를 따라 기다린다.
  • DT 시스템에서는 fw_devlink가 clocks, *-supply, *-gpios, interrupts 같은 phandle을 보고 링크를 자동으로 만든다(G2 §8, G3 §13). 그래서 DT를 제대로 쓰면 드라이버가 직접 device_link_add()를 부를 일이 드물다. 직접 부르는 경우는 이번처럼 DT에 표현되지 않는 관계(커스텀 API로 다른 드라이버를 쓰는 경우, 소프트웨어로 찾는 동반 장치 등)다.
  • deferred probe가 재시도될 때도 device_pm_move_to_tail()로 장치를 꼬리로 옮긴다(6.18 drivers/base/dd.c, 주석: "the PM code assumes that the order we add things to the list is a good order for suspend but deferred probe makes that very unsafe"). 공급자가 없어서 defer된 장치는 공급자보다 뒤로 가게 된다.

그림 4 — dpm_list와 device link. A: 소비자를 먼저 등록하고 링크가 없으면 공급자가 먼저 suspend되어 소비자의 마지막 전송이 실패한다(§6에서 실측). B: 링크가 소비자를 꼬리로 옮겨 순서가 맞는다.

3.4 예제 4 — pm_test로 단계까지만 돌리기, 그리고 hibernation 콜백#

무엇을 확인하나: /sys/power/pm_test(CONFIG_PM_DEBUG)는 suspend를 지정한 단계까지만 진행하고 5초 기다린 뒤 되돌린다. 깨울 장치(RTC 등)가 없어도 드라이버 콜백을 시험할 수 있다. 같은 방법으로 hibernation(disk)의 freeze/thaw 경로도 스왑 없이 돌린다.

출력에서 볼 것:

  • devices 수준에서는 prepare + suspend까지만 돌고 late/noirq는 불리지 않는다. 단계를 하나씩 넓히며(devices → platform → processors → core) 어느 단계에서 깨지는지 찾는 이분법 도구다.
  • "Waiting for 5 second(s)"인데 실제로는 약 29초 걸렸다 — TCG에서 mdelay 바쁜 대기가 부하에 따라 늘어진 것이다. 실제 HW에서는 5초다.
  • hibernation에서도 같은 함수(imu_suspend, imu_resume)가 불렸다. 이것은 .freeze/.thaw에 꽂힌 것이다 — SYSTEM_SLEEP_PM_OPS가 suspend 함수를 freeze·poweroff에, resume 함수를 thaw·restore에 똑같이 넣기 때문이다. 대부분의 드라이버는 이것으로 충분하다. 하지만 freeze는 "이미지를 찍는 동안 DMA만 멈추면 되는" 단계라서, 전원까지 끄는 무거운 드라이버(GPU, 모뎀)는 freeze/thaw를 따로 가볍게 만든다. 그리고 restore는 부팅 커널이 장치를 어떤 상태로 넘겼는지 모르는 상태에서 불리므로, resume보다 방어적이어야 한다(칩을 리셋하고 처음부터 설정).

4. runtime PM — 참조 카운트로 장치를 끈다#

4.1 모델#

runtime PM은 각 struct device 안의 struct dev_pm_info power에 상태 기계를 둔다. 핵심 값 세 개:

  • usage_count — "지금 이 장치를 쓰는 중"인 참조 수. pm_runtime_get*가 올리고 pm_runtime_put*이 내린다. 0이 되면 idle 검사 → suspend.
  • child_count — runtime-active인 자식 수. 자식이 깨어 있으면 부모는 못 잔다(ignore_children으로 끌 수 있다).
  • runtime_status — RPM_ACTIVE, RPM_SUSPENDING, RPM_SUSPENDED, RPM_RESUMING.

autosuspend를 켜면(pm_runtime_use_autosuspend) usage가 0이 되어도 바로 끄지 않고 last_busy + autosuspend_delay 시각까지 기다린다. 센서처럼 "짧게 자주" 쓰이는 장치에서 켰다 끄는 비용(전원 램프업, regcache_sync)을 아낀다 — NVMe APST의 idle 시간 임계값과 같은 생각이다.

그림 5 — runtime PM 상태 기계와 usage count. get이 usage를 올리고(필요하면 resume — 공급자 먼저), put_autosuspend가 usage를 내리며 last_busy를 갱신한다. usage가 0이고 지연이 지나면 runtime_suspend. put을 빼먹으면 usage가 0이 되지 않아 장치가 영원히 켜진다(§7).

4.4 시스템 sleep과 runtime PM을 같이 쓰기#

시스템 suspend가 시작되면 PM core는 장치마다 다음을 한다(6.18 drivers/base/power/main.c):

  • device_prepare(): pm_runtime_get_noresume()(시스템 전환 중에 runtime suspend가 끼어들지 않게) → .prepare.
  • device_suspend(): pm_runtime_barrier()로 진행 중인 runtime 작업을 끝낸다. 이 단계에서는 runtime resume이 아직 된다 — 그래서 imu_suspend()가 pm_runtime_resume_and_get()을 쓸 수 있었다.
  • device_suspend_late(): __pm_runtime_disable(). 이후로는 runtime PM이 꺼진다. late/noirq 콜백에서 pm_runtime_get_sync()는 장치가 이미 active면 1(아무것도 안 함), suspended면 -EACCES로 실패한다 — 깨울 수 없다.
  • device_complete(): .complete → pm_runtime_put()(prepare의 get을 돌려줌). 예제 2의 마지막 bus clock OFF가 이 put의 결과다.

그래서 흔한 두 함정:

  • 이중 suspend: .suspend에서 직접 클럭을 끄는데, 장치가 이미 runtime-suspended라서 클럭이 이미 꺼져 있으면 clk_disable_unprepare()가 한 번 더 불려 enable count가 음수가 되고 경고가 뜬다. 해결은 pm_runtime_force_suspend()처럼 "이미 suspended면 아무것도 안 한다"는 판단을 넣거나, 한 경로(runtime 콜백)만 실제 하드웨어를 끄게 하는 것이다.
  • direct_complete: .prepare가 양수를 돌려주고 장치가 runtime-suspended면 PM core는 그 장치의 suspend/resume 콜백을 아예 건너뛴다. 빠르지만, 자식이나 소비자가 wakeup 경로에 있으면 꺼진다(6.18 dpm_clear_superiors_direct_complete()). 그 플래그는 DPM_FLAG_SMART_PREPARE, DPM_FLAG_SMART_SUSPEND, DPM_FLAG_MAY_SKIP_RESUME(dev_pm_set_driver_flags())와 함께 docs.kernel.org의 "Device Power Management Basics"에 정리되어 있다. 예제 7의 dyndbg 출력의 driver flags: 0이 이 플래그 값이다.

무엇을 확인하나: runtime suspend가 칩 레지스터를 0xEE로 오염시킨 뒤, 다음 읽기가 runtime resume을 일으켜 POR 값 위에 regcache_sync가 설정을 다시 쓰는지. 칩 내용(raw), regmap debugfs(cache_only, cache_dirty, registers), regmap tracepoint를 함께 본다. 부하 때문에 확인 도중 autosuspend가 끼어들지 않도록 지연을 sysfs로 3초로 늘렸다.

6. 버그 1 — 공급자가 먼저 잠든다#

6.1 예제 7 — "transfer while suspended"를 일부러 만든다#

무엇을 확인하나: 소비자를 먼저 등록(imu_first=1)하고 링크 없이(link=0) 시스템 suspend를 하면 무슨 일이 생기나. 실제 I2C에서 i2c 코어의 Transfer while suspended WARN과 함께 resume 뒤 센서가 죽는 바로 그 패턴이다.

출력에서 볼 것:

  • prepare가 imu → bus 순서다 = dpm_list가 [..., n6_imu, n6_bus]. 그래서 suspend는 거꾸로 bus가 먼저(79.735) 잠들고, 그다음 imu_suspend가 칩을 깨워 regcache_sync를 하려다 transfer while suspended. 첫 쓰기(reg 0x02)에서 -108(-ESHUTDOWN)이 났고 그 에러가 그대로 시스템 suspend를 실패시켰다.
  • PM core는 실패한 장치 앞에서 멈추고, 이미 suspend된 장치들만 resume한다(bus_resume은 있고 imu_resume은 없다 — imu는 suspend에 실패했으니까). complete는 둘 다 받는다. 유저에게는 rtcwake: write error(ESHUTDOWN의 문자열 "Cannot send after transport endpoint shutdown")로 보인다.

  • 실패가 이렇게 시끄러우면 차라리 다행이다. 소비자가 에러를 무시하고 0을 돌려주는 드라이버라면 suspend는 성공하고, resume 뒤 칩은 설정이 반쯤 빠진 채로 남는다 — 인터뷰 질문 "resume 뒤 I2C 센서가 이상하다"의 대표 원인이다.

6.2 고치기#

예제 2가 이미 고친 버전이다: 같은 imu_first=1이지만 link=1에서 device_link_add(imu, bus, DL_FLAG_STATELESS | DL_FLAG_PM_RUNTIME | DL_FLAG_RPM_ACTIVE)가 imu를 dpm_list 꼬리로 옮겨 prepare가 bus → imu, suspend가 imu → bus가 됐다. 덤으로 공급자를 손으로 붙잡을 필요가 없어져서 평소에 공급자가 꺼진다(예제 5).

고치는 법의 우선순위:

  1. DT에 관계를 표현한다 — 공급자가 클럭·레귤레이터·GPIO·인터럽트 컨트롤러면 phandle만 바르게 쓰면 fw_devlink가 링크를 만든다. I2C/SPI 클라이언트는 어댑터의 자식이므로 트리로 해결된다.

  3. 버스 컨트롤러 드라이버라면 늦게 잠들고 일찍 깨기: 많은 I2C 컨트롤러 드라이버가 실제 끄기를 suspend_noirq에서 하고 resume_noirq에서 켠다. 그래야 다른 드라이버의 suspend/suspend_late에서 아직 버스를 쓸 수 있다(PMIC를 noirq 단계 직전에 설정하는 경우 등). i2c 코어는 어댑터가 i2c_mark_adapter_suspended()된 뒤의 전송을 -ESHUTDOWN + WARN으로 거부한다.

8. IRQ와 wakeup#

8.1 suspend 동안 IRQ는 어떻게 되나#

dpm_suspend_noirq()의 첫 일이 suspend_device_irqs()다(6.18 drivers/base/power/main.c). 이때부터 대부분의 장치 IRQ는 비활성(lazy disable) 되고, 그 사이 들어온 IRQ는 pending으로 기록되었다가 resume_device_irqs()에서 다시 실행된다. 그래서 드라이버는 suspend에서 자기 IRQ를 굳이 끌 필요가 없다 — 단, .suspend(IRQ가 아직 켜진 단계)에서 하드웨어를 끈 뒤 IRQ가 오면 핸들러가 꺼진 하드웨어를 건드린다. 그런 경우는 disable_irq()로 직접 끄거나 칩의 인터럽트를 먼저 끈다(imu_suspend의 INT_EN=0).

8.2 wakeup source — "지금 자면 안 된다"를 알리는 객체#

wake IRQ가 "잠든 시스템을 깨우는" 것이라면, wakeup source는 "깨어 있는 동안 이벤트를 처리 중이니 지금 suspend하지 마"를 커널에 알리는 객체다. Android의 wakelock이 커널로 들어온 형태다.

  • device_init_wakeup(dev, true) (또는 devm_device_init_wakeup(dev)) — power.can_wakeup = 1, power/wakeup = enabled, 그리고 장치 이름의 struct wakeup_source를 만든다.
  • device_may_wakeup(dev) — 할 수 있고(can_wakeup) 유저가 허락했나(power/wakeup). 드라이버는 suspend에서 이것을 보고 wake를 arm한다.
  • pm_stay_awake(dev) / pm_relax(dev) — 이벤트 처리 시작·끝(짝을 맞춘다).
  • pm_wakeup_event(dev, ms) — "이벤트가 있었고, ms 동안 처리 중으로 쳐라"(타이머로 자동 relax). pm_wakeup_hard_event(dev)는 추가로 pm_system_wakeup()을 불러 진행 중인 suspend를 중단시킨다.
  • 관찰: /sys/kernel/debug/wakeup_sources(전체 표), /sys/devices/.../power/wakeup*(장치별), /sys/power/wakeup_count(전역 카운트), /sys/power/pm_wakeup_irq(마지막으로 깨운 IRQ, CONFIG_PM_SLEEP_DEBUG).

중요한 사실 하나: soft 이벤트(pm_wakeup_event)만으로는 echo freeze > /sys/power/state가 막히지 않는다. 6.18 drivers/base/power/wakeup.c의 wakeup_source_report_event()를 보면 hard일 때만 pm_system_wakeup()을 부르고, pm_wakeup_pending()은 events_check_enabled가 켜졌을 때만 이벤트 카운트를 비교한다. events_check_enabled는 유저가 /sys/power/wakeup_count에 값을 써서 켠다 — 그게 race-free suspend 프로토콜이다(아래 예제 9-b).

  • disabled: 유저가 power/wakeup에 disabled를 쓰면 device_may_wakeup()이 false라 PM core가 arm하지 않는다. 버튼(호스트 기준 약 8초 뒤)에 깨지 않았고, 25초 RTC 알람(IRQ 19 = rtc-pl031, 예제 11의 /proc/interrupts로 확인)에 깨어났다. 그리고 잠든 동안 온 IRQ 21이 resume 뒤에 재실행됐다(34.04 s의 wake key IRQ 21) — 그림 8의 "일반 IRQ: pending 기록 → resume 때 재실행" 그대로다.
  • disabled에서는 장치의 wakeup source 객체도 사라진다(wakeup_count= 빈 값, debugfs 표에 행 없음). power/wakeup에 쓰는 것이 device_wakeup_enable/disable()을 부르기 때문이다.
  • 이 정책 손잡이(power/wakeup)가 유저 공간에 있다는 것이 중요하다: 드라이버는 "깨울 수 있다"만 선언하고, "깨우게 할지"는 제품(systemd/udev 규칙, 앱)이 정한다.

11.1 센서 키트의 IMU가 motion으로 시스템을 깨운다#

배터리로 도는 로봇 센서 키트가 대기 중일 때 IMU의 motion-detect 인터럽트로 깨어나야 한다. 드라이버가 할 일:

  1. DT에 interrupts와 wakeup-source. probe에서 device_init_wakeup(dev, device_property_read_bool(dev, "wakeup-source")).
  2. .suspend: device_may_wakeup(dev)이면 칩을 저전력 motion-detect 모드로 설정하고(그래서 버스가 아직 살아 있어야 한다 — §6) enable_irq_wake(). 아니면 칩 전원 off.

wakeup-source가 있는데 SoC GPIO 컨트롤러가 always-on 도메인이 아니면 deep suspend에서 깨지 않는다. 그런 SoC는 별도 wake 컨트롤러(i.MX의 GPC/SNVS, TI의 wkup 도메인 GPIO) 경로를 DT로 지정한다 — 그때 dev_pm_set_dedicated_wake_irq()를 쓴다.

13. 면접에서 이렇게 말한다#

Q. "Your I2C sensor driver works at boot but fails after resume. Why, and how would you debug it?"

A. 원인은 세 부류다. (1) 순서: 센서가 쓰는 공급자(레귤레이터, 클럭, 다른 I2C 장치를 통한 경로)가 먼저 잠들었거나 늦게 깨어났다 — pm_print_times로 콜백 순서를 보고 device link/fw_devlink로 고친다. (2) 상태 소실: 전원이 꺼져 레지스터가 POR로 돌아갔는데 복원을 안 했거나, regmap reg_defaults가 틀려서 sync가 일부를 건너뛰었다 — debugfs regmap과 칩 실제 값을 비교한다. (3) 타이밍: 레귤레이터 enable 뒤 turn-on 시간을 안 지켜 첫 전송이 NACK — scope로 VDD 램프와 SCL을 같이 본다.

There are usually three causes. Ordering: a supplier — a regulator, a clock, or the bus itself — suspended before the sensor or resumed after it; I check the callback order with pm_print_times and fix it with a device link or a proper DT phandle so fw_devlink orders it. State loss: the rail went off, the chip came back with power-on defaults, and the driver didn't restore it — or regmap's reg_defaults don't match the real POR values, so regcache_sync silently skipped registers; I compare the regmap debugfs view with what the chip actually returns. Timing: the first transfer happens before the chip's turn-on time after regulator_enable, so it NACKs; I'd put a scope on VDD and SCL together.

꼬리 질문: "What does 'Transfer while suspended' mean?" — 어댑터가 i2c_mark_adapter_suspended()된 뒤 전송이 왔다는 WARN이고 -ESHUTDOWN을 돌려준다. 클라이언트가 어댑터보다 늦게 suspend되는 순서 문제거나, 클라이언트의 IRQ 스레드가 noirq 이후에 돌았다는 뜻이다.

Q. "How do you make a device wake the system from suspend?"

A. 세 층이다. 하드웨어: 그 IRQ가 suspend 중에도 살아 있는 컨트롤러로 라우팅돼야 하고, irqchip이 irq_set_wake를 지원해야 한다. 드라이버: probe에서 device_init_wakeup()(DT wakeup-source를 보고), 그리고 dev_pm_set_wake_irq()로 등록하거나 suspend에서 device_may_wakeup()이면 enable_irq_wake(). 정책: 유저가 power/wakeup으로 켜고 끈다. 확인은 /sys/power/pm_wakeup_irq와 wakeup_sources. 실습에서 gpio-sim은 irq_set_wake가 없어 -ENXIO였고, PL061 라인은 실제로 s2idle을 깨웠다.

Three layers. Hardware: the interrupt must be routed through a controller that stays powered in the target sleep state, and its irqchip must implement irq_set_wake. Driver: call device_init_wakeup in probe — usually gated on the wakeup-source DT property — and either register the line with dev_pm_set_wake_irq so the PM core arms it, or call enable_irq_wake in suspend when device_may_wakeup is true, and check the return value. Policy: user space decides through the power/wakeup attribute. To verify, I read /sys/power/pm_wakeup_irq after resume and the wakeup_sources table in debugfs.

Q. "What's the difference between system suspend callbacks and runtime PM callbacks? How do you avoid duplicating code?"

A. 시스템 콜백은 전체 전환 때 PM core가 모든 장치에 정해진 순서로 부르고, runtime 콜백은 장치 하나의 usage count가 0이 될 때 부른다. 보통 하드웨어를 끄고 켜는 코드는 runtime 콜백에만 두고, 시스템 쪽은 pm_runtime_force_suspend/resume으로 재사용한다(DEFINE_RUNTIME_DEV_PM_OPS). force 함수는 이미 runtime-suspended면 아무것도 안 해서 이중 suspend를 막고, resume 때도 필요할 때만 깨운다.

System sleep callbacks are invoked for every device in dependency order during a system-wide transition; runtime PM callbacks run for one device when its usage count drops to zero. I put the real power-off and power-on code in the runtime callbacks and reuse them for system sleep through pm_runtime_force_suspend and force_resume — that's what DEFINE_RUNTIME_DEV_PM_OPS does. The force helpers skip devices that are already runtime-suspended, which avoids double-disabling clocks, and on resume they only power the device up if it's needed.

Q. "pm_runtime_get_sync vs pm_runtime_resume_and_get?"

A. get_sync는 resume이 실패해도 usage를 올려서, 에러 경로에서 put_noidle을 안 하면 누수가 된다. resume_and_get은 성공했을 때만 올린다. 누수는 장치를 영원히 켜 두고, 링크로 묶인 공급자까지 켜 둔다. 실습에서 실패 몇 번에 runtime_usage가 5가 되고 드라이버를 다시 올려도 남았다 — usage는 struct device에 있기 때문이다.

get_sync increments the usage count even when the resume fails, so an early return without put_noidle leaks a reference; resume_and_get only increments on success. A leak keeps the device — and any supplier linked with DL_FLAG_PM_RUNTIME — powered forever. In my lab a few failed reads left runtime_usage at five, and reloading the driver didn't clear it, because the count lives in struct device, not in the driver.

Q. "In which suspend phase would you put the code that turns off an I2C controller, and why?"

A. 가능한 늦게 — suspend_noirq(또는 late). 다른 드라이버들이 자기 suspend/suspend_late에서 마지막 설정(PMIC, 센서 wake 모드)을 버스로 써야 하기 때문이다. 대신 noirq에서는 IRQ가 꺼져 있으므로 그 단계의 전송은 polling 모드여야 한다. resume은 반대로 resume_noirq에서 일찍 켠다.

As late as possible — usually suspend_noirq — because other drivers still need the bus in their own suspend and suspend_late callbacks, for example to put a PMIC or a sensor into its wake mode. The trade-off is that interrupts are off by then, so any transfer in the noirq phase must work in polling mode. On the way back I'd bring it up early, in resume_noirq.

Q. "What is a wakeup source, and why can't a driver just block suspend by itself?"

A. wakeup source는 "이벤트를 처리 중이니 자지 마"를 표시하는 커널 객체다(pm_stay_awake/pm_relax, pm_wakeup_event). 그런데 처리 중 표시만으로는 echo mem > state를 막지 못한다 — 유저 공간이 /sys/power/wakeup_count를 읽고 다시 쓰는 프로토콜을 써야 그 뒤의 이벤트가 suspend를 중단시킨다. 커널 스스로 중단시키려면 pm_wakeup_hard_event()인데, 그것도 suspend가 진행 중일 때 와야 한다. 실습에서 세 경우를 모두 확인했다.

A wakeup source is a kernel object that says "an event is being processed, don't sleep yet" — pm_stay_awake and pm_relax, or pm_wakeup_event with a timeout. By itself it doesn't stop a plain write to /sys/power/state; the race-free scheme is the wakeup_count handshake, where the suspend daemon reads the count, writes it back, and the kernel aborts if any event happened in between. A driver can force an abort with pm_wakeup_hard_event, but only events that arrive while the transition is in progress count — anything before the freeze phase is cleared.

Q. "How do you test a driver's PM code before you have the final hardware?"

A. pm_test로 단계까지만 돌리고, rtcwake 스트레스 루프로 수천 번 반복하며 suspend_stats를 본다. pm_print_times로 느린 콜백을, runtime_usage로 누수를, power/control=on으로 "PM 탓인가"를 가른다. 그리고 s2idle만이 아니라 대상 SoC의 deep suspend에서 반드시 돌린다 — 전원 도메인이 진짜로 꺼지는 건 deep뿐이다.

pm_test to stop at a given phase and roll back, an rtcwake loop running thousands of cycles while I watch suspend_stats, pm_print_times for slow callbacks, runtime_usage for reference leaks, and power/control set to "on" to rule PM in or out. And I always run it in the target SoC's deep state, not just suspend-to-idle, because only deep sleep actually cuts the power domains.

16. 요약 & 체크리스트#

드라이버의 PM은 "언제·누구 다음에·무엇을 잃나"의 문제다. struct dev_pm_ops는 전환 종류 × 단계의 표이고, 6.x에서는 SYSTEM_SLEEP_PM_OPS/RUNTIME_PM_OPS 조각과 pm_ptr/pm_sleep_ptr로 #ifdef 없이 쓴다. 순서는 dpm_list(등록 순서)에서 오고, 트리 밖 의존성은 device link(DT면 fw_devlink)로 고친다 — 링크가 없으면 공급자가 먼저 잠들어 transfer while suspended가 난다(예제 7). 하드웨어를 끄고 켜는 코드는 runtime 콜백에 한 번만 두고 pm_runtime_force_*로 시스템 sleep에 재사용하며, 레지스터는 regmap의 cache_only/mark_dirty/sync로 복원한다(reg_defaults = POR). runtime PM은 참조 카운트라 pm_runtime_resume_and_get과 빠짐없는 put이 생명이다(예제 8). 장치가 시스템을 깨우려면 wake 가능한 irqchip + device_init_wakeup + dev_pm_set_wake_irq(또는 enable_irq_wake)가 필요하고, "지금 자지 마"는 wakeup source와 유저의 wakeup_count 프로토콜로 표현한다(예제 9, 10).
