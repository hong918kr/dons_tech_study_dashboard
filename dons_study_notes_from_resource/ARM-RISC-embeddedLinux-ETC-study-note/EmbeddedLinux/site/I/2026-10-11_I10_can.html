이 노트를 다 읽으면: CAN 컨트롤러가 Linux에서 can0 네트워크 인터페이스가 되는 전 경로(소켓 → af_can → can_dev → 드라이버 → 컨트롤러)를 그릴 수 있다 · ip -details가 보여 주는 tq/prop-seg/phase-seg/sjw를 손으로 다시 계산할 수 있다 · TEC/REC와 error-active → warning → passive → bus-off → restart 흐름을 에러 프레임으로 읽고 디버그할 수 있다 · alloc_candev, can_put_echo_skb, NAPI, can_change_state, can_bus_off를 쓰는 CAN 드라이버 뼈대를 직접 쓸 수 있다 왜 필요한가: 로봇·모터 컨트롤러·차량 회사의 Embedded Linux 면접에서 "CAN 버스가 계속 bus-off 된다, 어떻게 디버그하나?", "SocketCAN 구조를 설명해 봐라", "M_CAN/FlexCAN 드라이버 bring-up 해 봤나?"는 거의 반드시 나온다 Don 기준 난이도: 비트 타이밍·에러 카운터·인터럽트·메일박스는 이미 아는 HW 지식 / 새로 배울 것은 "CAN이 Linux에서는 net_device"라는 틀, can_dev 헬퍼, echo skb, NAPI, netlink 설정, 에러 프레임 API 선행 노트: A9(소켓, vcan 기초), A10(ip link ... type can, candump/cansend), F7(deferred work), H1(MMIO), H6(IRQ), H7(SPI). 0. 큰 그림 — 이게 왜 필요한가#

로봇 팔이나 AMR(자율주행 이동 로봇)을 떠올리자. 관절마다 모터 컨트롤러(MCU + FOC 펌웨어)가 있고, 배터리 관리 장치(BMS), IMU 보드가 있다. 이들을 한 쌍의 꼬인 선(CAN_H, CAN_L)으로 묶고, 메인 컴퓨터(i.MX8, AM62, Jetson Orin 같은 Linux SoC)가 1 ms~10 ms 주기로 속도·토크 명령을 보내고 상태를 받는다. 차량(ECU), 드론(ESC, 짐벌), 농기계(J1939)도 똑같다.

그림 1 — 로봇의 CAN 버스. Linux SoC 쪽은 앱 → 커널 → 드라이버 → 컨트롤러 IP → 트랜시버, 버스 반대편에는 MCU 노드들이 있다. 양 끝 120 Ω 종단이 필수다.

Don이 bare-metal MCU에서 CAN을 썼다면 구조는 이랬을 것이다: 컨트롤러 레지스터에 비트 타이밍(BRP, TSEG1, TSEG2, SJW)을 쓰고, TX 메일박스에 ID·DLC·데이터를 쓰고 "전송 요청" 비트를 세우고, TX-complete/RX/에러 인터럽트 ISR에서 메일박스를 비우고, 에러 카운터 레지스터(TEC/REC)를 읽어 bus-off면 재초기화. Linux에서도 HW에서 일어나는 일은 완전히 같다. 다른 점은 "누가 무엇을 맡느냐"다.

1. CAN 프로토콜 — 드라이버를 읽는 데 필요한 만큼만#

Don은 타이밍 분석과 버스 디버그를 잘 안다. 그래서 여기서는 "Linux API의 어느 필드가 프로토콜의 어느 부분에 대응하는가"에 초점을 둔다.

1.1 버스와 비트: dominant가 이긴다#

CAN은 차동 2선 버스다. 논리 0 = dominant(트랜시버가 CAN_H/CAN_L을 벌림), 논리 1 = recessive(아무도 안 몰면 이 상태). 여러 노드가 동시에 비트를 내면 버스는 wired-AND: 한 노드라도 0을 내면 버스는 0이다. 오픈 드레인 I2C SDA와 똑같은 물리다. 모든 노드는 송신하면서 동시에 버스를 읽는다(자기 비트 모니터링).

1.2 프레임 구조와 중재(arbitration)#

그림 2 — Classic CAN 데이터 프레임과 중재. 두 노드가 동시에 SOF를 내고 ID를 MSB부터 보낸다. 0x12F를 보내던 노드 B는 b3에서 1(recessive)을 냈는데 버스에서 0을 읽어 중재에 졌다는 것을 알고 즉시 수신자로 바뀐다. 이긴 노드 A의 프레임은 한 비트도 손상되지 않는다(non-destructive arbitration).

  • ID가 곧 우선순위다. 낮은 ID가 이긴다. 모터 토크 명령에 낮은 ID, 로그·진단에 높은 ID를 주는 이유다.
  • 진 노드는 버스가 비면 자동 재전송한다. 컨트롤러 HW가 하는 일이라 드라이버는 몰라도 된다(진 횟수는 arbitration_lost 통계와 CAN_ERR_LOSTARB 에러 프레임으로 보고할 수 있다).
  • RTR 비트: 원격 요청 프레임. SocketCAN에서는 CAN_RTR_FLAG(can_id의 비트 30).
  • IDE 비트: 1이면 29비트 확장 ID(EFF). SocketCAN에서는 CAN_EFF_FLAG(비트 31).
  • DLC 4비트: 데이터 길이 0..8. (DLC 9..15도 전송 가능하지만 classic에서는 8바이트로 취급. 리눅스는 이 원래 DLC를 len8_dlc 필드에 담을 수 있다.)
  • CRC 15비트 + delimiter, ACK 슬롯: 송신자는 recessive를 내고, 프레임을 정상 수신한 아무 노드라도 그 비트를 dominant로 덮어쓴다. 아무도 안 덮으면 송신자는 ACK 에러. 버스에 노드가 혼자면 ACK가 절대 안 온다 — 6절의 핵심 실험이다.
  • bit stuffing: SOF~CRC 구간에서 같은 값이 5비트 연속되면 송신자가 반대 비트를 하나 끼운다. 수신자는 6비트 연속을 보면 stuff error. 이 덕분에 엣지가 자주 생겨 재동기화가 된다.

프레임 길이 감 잡기(scope로 볼 때 유용): 11비트 ID, 8바이트 데이터 classic 프레임은 stuffing 없이 SOF부터 EOF까지 108비트, 프레임 간 간격(IFS) 3비트를 더하면 111비트다. 500 kbit/s에서 약 222 µs, 최악의 stuffing이면 130비트 이상. 1 Mbit/s 버스 하나에 8바이트 프레임을 초당 최대 약 8000개밖에 못 싣는다. 모터 8개에 1 kHz 명령 + 1 kHz 상태면 이미 16000 프레임/s라 한 버스로는 안 된다 — 로봇에서 CAN FD나 버스 분리가 나오는 이유다.

에러를 본 노드는 즉시 에러 플래그(error-active 노드는 dominant 6비트 — 일부러 stuff 규칙을 깨서 모두가 알게 함, error-passive 노드는 recessive 6비트)를 내고, 프레임은 버려지고 송신자가 재전송한다. 그리고 에러 카운터가 움직인다:

  • 송신 중 에러: TEC += 8. 수신 중 에러: REC += 1(일부 경우 +8).
  • 성공적 송신: TEC −= 1, 성공적 수신: REC −= 1.
  • TEC 또는 REC ≥ 96 → error-warning(규격 상태는 아니고 컨트롤러가 주는 경고), ≥ 128 → error-passive, TEC ≥ 256 → bus-off(버스에서 완전히 손을 뗌).
  • 중요 예외(ISO 11898-1): error-passive 송신자가 ACK 에러를 검출하고 passive 에러 플래그 동안 dominant를 보지 못하면 TEC를 올리지 않는다. 그래서 "케이블이 빠져 혼자 남은 노드"는 bus-off까지 가지 않고 error-passive에 머물며 계속 재전송한다. 반대로 "트랜시버 고장·CAN_H 단락"처럼 bit error가 나면 passive에서도 +8이 계속되어 bus-off로 간다. 6절에서 둘 다 재현한다.

1.4 CAN FD 한눈에#

FD 데이터 구간이 짧은 비트(예: 5 Mbit/s = 200 ns)라서, 송신자가 자기 비트를 다시 읽을 때 트랜시버 루프 지연(100 ns 이상)이 비트 시간의 큰 부분이 된다. 그래서 FD 컨트롤러에는 TDC(Transmitter Delay Compensation)가 있고, Linux에서는 tdcv/tdco/tdcf로 설정한다(ip link ... tdc-mode auto 등). 최근에는 CAN XL(2048 바이트, CANXL_MTU)도 커널에 들어왔지만 이 노트에서는 다루지 않는다.

1.5 흔한 함정#

  • "CAN은 신뢰성 있으니 프레임이 사라지지 않는다" — 버스 위에서는 재전송되지만, Linux 안에서는 qdisc 큐(qlen 10)가 차면 ENOBUFS, 수신 소켓 버퍼가 차면 drop, 컨트롤러 RX FIFO가 넘치면 CAN_ERR_CRTL_RX_OVERFLOW로 잃는다.
  • ACK는 "목적지가 받았다"가 아니라 "누군가 제대로 받았다"는 뜻이다. 목적 노드의 애플리케이션 수신 확인은 상위 프로토콜(CANopen, J1939, ISO-TP)의 몫이다.

2. SocketCAN 구조 — CAN을 소켓으로 다루기#

그림 3 — SocketCAN 계층. 프로토콜 모듈(can_raw, can_bcm, can_isotp, can_j1939, can_gw)이 af_can 코어 위에 올라가고, af_can은 일반 net_device로 프레임을 내려보낸다. 컨트롤러 드라이버는 can_dev 헬퍼(비트 타이밍, netlink, 상태, restart)를 쓴다.

2.2 프레임 구조체 — can_frame과 canfd_frame#

  • 앞 8바이트 레이아웃이 같아서, 커널은 skb->len(16 vs 72)으로 classic/FD를 구분한다. 유저도 read() 반환 크기로 구분한다.
  • can_id는 호스트 바이트 순서 정수다. 버스의 비트 순서는 컨트롤러가 처리한다.
  • CAN_ERR_FLAG가 선 프레임은 버스에서 온 데이터가 아니라 드라이버가 만든 에러 보고다(6절).

2.3 로컬 루프백 — echo의 의미#

같은 보드의 앱 A가 보낸 프레임을 앱 B(candump 등)도 봐야 한다. 실제 버스에서 송신자는 자기 프레임을 RX로 받지 않으므로(컨트롤러가 걸러 냄) 누군가 루프백해 줘야 한다. SocketCAN 규칙:

  • 소켓 옵션 CAN_RAW_LOOPBACK(기본 켜짐): 내 프레임을 같은 장치의 다른 소켓에 보여 준다.
  • CAN_RAW_RECV_OWN_MSGS(기본 꺼짐): 보낸 소켓 자신도 받는다.
  • 장치에 IFF_ECHO 플래그가 있으면 드라이버가 루프백한다: 송신 skb를 보관했다가 TX 완료 인터럽트가 온 뒤에야 위로 올린다(can_put_echo_skb/can_get_echo_skb). 그래서 candump에 보이는 내 송신 프레임의 순서·시각이 "실제로 버스에 나간 순서"와 같다.
  • IFF_ECHO가 없으면 af_can이 can_send() 안에서 즉시 복제해 루프백한다(vcan 기본 동작). 버스에 나갔는지와 무관하다.

7절에서 직접 쓴 드라이버가 IFF_ECHO를 빼먹어 큐가 영원히 멈춘 실제 버그를 다룬다.

3. 실습 랩 — QEMU에 진짜 CAN 컨트롤러 붙이기#

vcan(A9, A10)은 비트 타이밍도 에러 카운터도 없는 순수 SW 루프백이다. 드라이버 쪽을 보려면 "레지스터가 있는 컨트롤러"가 필요하다. QEMU는 CAN 버스 객체와 몇 가지 PCI CAN 카드를 에뮬레이션한다.

  • -object can-bus,id=busA: 가상 버스 하나. 여기에 붙은 컨트롤러끼리 프레임이 오간다.
  • -device kvaser_pci,canbus=busA: SJA1000 칩 1개짜리 Kvaser PCIcan 카드. SJA1000은 1990년대 NXP(Philips) 독립형 CAN 컨트롤러로, 레지스터 구조가 단순해 교과서 같은 드라이버(drivers/net/can/sja1000/)를 갖고 있다.
  • -device ctucan_pci,canbus0=busA,canbus1=busB: CTU CAN FD IP 코어 2채널. CAN FD 지원.
  • -object can-host-socketcan,id=h0,if=i10vc0,canbus=busA: QEMU 버스를 VM 호스트의 SocketCAN 인터페이스(여기서는 vcan)에 연결한다. 게스트의 프레임이 호스트 candump에 보이고, 호스트 cansend가 게스트 컨트롤러에 도착한다.

(작업 중 can-bus,id=canbus0처럼 id를 canbus0으로 주면 ctucan_pci의 속성 이름 canbus0과 겹쳐 "Path 'canbus0' does not uniquely identify an object" 에러가 났다. 버스 id는 속성 이름과 다르게 짓는다. 또 ctucan_pci는 두 채널 모두 버스에 연결해야 했다 — canbus1을 빼면 ctucan_connect_to_bus failed.)

3.1 드라이버를 out-of-tree로 빌드하기#

랩 커널 설정을 보면 SJA1000과 CTU CAN FD 드라이버는 꺼져 있고, FlexCAN·M_CAN·MCP251xFD는 모듈로 켜져 있다(실제 SoC용이라 QEMU에는 장치가 없다).

CONFIG_CAN_CALC_BITTIMING=y가 중요하다. 이게 있어야 ip link ... bitrate 500000만 줘도 커널이 tq·세그먼트를 계산한다(4절).

커널 트리의 드라이버 파일을 /var/tmp/I10/drv/로 복사하고 Kbuild 한 줄로 빌드한다. 소스는 그대로다.

(크기·경로만 남겼다.) 드라이버가 두 층인 것에 주목하자: sja1000.ko는 칩 코어(레지스터 프로그래밍, IRQ 처리, can_dev 연결), kvaser_pci.ko는 버스 글루(PCI BAR 매핑, IRQ 번호, 그리고 priv->read_reg/write_reg 콜백 제공). 같은 SJA1000 코어를 ISA·플랫폼(DT)·PCMCIA 글루가 공유한다. M_CAN도 m_can.ko(코어) + m_can_platform.ko(MMIO) / tcan4x5x(SPI) 구조다. G 모듈(드라이버 모델)에서 본 "코어 + 버스별 글루" 패턴의 전형이다.

4. 비트 타이밍 — 커널이 tq와 세그먼트를 고르는 법#

4.1 한 비트 안의 구조#

그림 4 — 한 비트를 tq(time quantum) 단위로 쪼갠 것. 예: 80 MHz 클럭, brp 1 → tq 12.5 ns, 160 tq = 2 µs = 500 kbit/s. 샘플 포인트는 Phase_Seg1 끝(87.5%).

  • tq = brp / f_clk. 컨트롤러 클럭을 프리스케일러(brp)로 나눈 최소 시간 단위.
  • Sync_Seg = 항상 1 tq. 엣지가 여기 오기를 기대한다.
  • Prop_Seg: 신호가 버스를 왕복하는 지연(트랜시버 루프 + 케이블 전파 × 2)을 흡수한다.
  • Phase_Seg1, Phase_Seg2: 재동기화 때 늘이고 줄이는 버퍼. 샘플 포인트는 Phase_Seg1과 Phase_Seg2 사이.
  • SJW(Synchronization Jump Width): 한 번의 재동기화에서 조정할 수 있는 최대 tq 수. 노드 간 클럭 오차를 흡수한다.
  • 대부분의 컨트롤러 레지스터에는 TSEG1(= Prop_Seg + Phase_Seg1)과 TSEG2(= Phase_Seg2)만 있다. 커널은 TSEG1을 반으로 나눠 prop-seg·phase-seg1로 표시할 뿐이다.

공식: bitrate = f_clk / (brp × (1 + TSEG1 + TSEG2)), sample point = (1 + TSEG1) / (1 + TSEG1 + TSEG2).

Don이 아는 언어로: 이건 UART 16× 오버샘플링의 일반화다. 다만 CAN은 모든 노드가 같은 비트에 동시에 참여하므로(중재·ACK) 샘플 포인트를 늦게(75~87.5%) 잡아 전파 지연을 흡수한다. 버스가 길수록 Prop_Seg가 커야 하므로 1 Mbit/s는 약 40 m가 한계로 흔히 인용된다.

4.2 커널의 계산 알고리즘 (can_calc_bittiming)#

ip link set can0 type can bitrate 500000을 하면 netlink → can_changelink() → can_get_bittiming() → can_calc_bittiming()(drivers/net/can/dev/calc_bittiming.c)가 돈다. 요약하면:

  1. 샘플 포인트 목표: 유저가 sample-point를 안 주면 CiA 권장값 — bitrate > 800 k면 75.0%, > 500 k면 80.0%, 그 외 87.5%.
  2. 가능한 TSEG 총합(tseg1 + tseg2)을 큰 값부터 내려가며, 각각에 대해 brp = clock / ((1 + tseg) × bitrate)를 구하고 brp_min..brp_max에 드는지 본다. → 같은 오차면 tq가 짧은(해상도 높은) 쪽이 먼저 뽑힌다.
  3. 비트레이트 오차가 가장 작고, 그 다음 샘플 포인트 오차가 가장 작은 조합을 고른다. 샘플 포인트는 목표 이하 중에서 고른다.
  4. 비트레이트 오차가 0.5%(CAN_CALC_MAX_ERROR = 50, 0.1% 단위)를 넘으면 EINVAL. 0이 아니면 경고만.
  5. TSEG1을 prop_seg = tseg1 / 2, phase_seg1 = 나머지로 나눈다.
  6. SJW를 안 주면 max(1, min(phase_seg1, phase_seg2 / 2)) (6.x 커널 기본값. 옛 커널·can-calc-bit-timing 일부 버전은 SJW 1).

결과는 드라이버의 do_set_bittiming()(또는 ndo_open 안의 chip start)이 레지스터에 쓴다. 드라이버 작성자가 할 일은 정확한 can_bittiming_const와 clock.freq를 주는 것뿐이다.

4.3 예제 3 — 두 컨트롤러에서 커널이 고른 값#

무엇을 확인하나: 같은 bitrate인데 컨트롤러(클럭·레지스터 폭)에 따라 brp·세그먼트가 어떻게 달라지는지, 그리고 CiA 기본 샘플 포인트가 bitrate에 따라 바뀌는지.

출력에서 볼 것 — 손 계산으로 검산:

  • can0(SJA1000, 8 MHz) 500 k: tq = 1/8 MHz = 125 ns. 1 + 6 + 7 + 2 = 16 tq → 16 × 125 ns = 2 µs = 500 kbit/s. 샘플 포인트 (1+13)/16 = 0.875. TSEG1 최대가 16이라 16 tq가 한계다.
  • can0 1 M: 8 tq/비트밖에 안 된다. 샘플 포인트 (1+5)/8 = 0.75. SJW 1 = phase_seg2 2의 절반.
  • can1(CTU CAN FD, 100 MHz) 500 k: tq 10 ns, 1 + 111 + 63 + 25 = 200 tq → 2 µs. prop-seg 111 / phase-seg1 63으로 "반반"이 아닌 이유: 커널 계산은 tseg1 174를 87/87로 나눴지만, CTU CAN FD는 PROP과 PH1 레지스터 필드가 따로 있고 PH1 최대가 63이라 드라이버의 ctucan_set_btr()가 넘치는 만큼을 prop_seg로 옮기고 bt에 다시 써 넣는다(ctucanfd_base.c). 그래서 ip에 보정된 값이 보인다. SJW 12 = 25/2.
  • 800 k → 80%, 1 M → 75%로 CiA 권장 샘플 포인트가 자동 적용됐다. 버스의 모든 노드가 같은 샘플 포인트를 쓰는 것이 좋다 — MCU 노드 펌웨어의 설정과 맞춰야 한다.

SJA1000 드라이버의 dmesg에는 이 값이 실제 레지스터로 들어간 모습이 찍힌다:

BTR0 = SJW-1(비트 7:6) + BRP-1(비트 5:0) = 0x00 → SJW 1, BRP 1. BTR1 = SAM(비트 7) + TSEG2-1(비트 6:4) + TSEG1-1(비트 3:0) = 0x1c → TSEG2 = 1+1 = 2, TSEG1 = 0xc+1 = 13 = 6 + 7. 데이터시트의 레지스터 정의와 ip -details 출력이 정확히 맞아떨어진다 — bring-up 때 이 대조가 첫 번째 확인이다.

두 번째 방식(tq + 세그먼트 직접 지정)은 다른 벤더 도구나 MCU 설정표에서 받은 값을 그대로 맞출 때 쓴다.

4.4 예제 4 — 클럭이 다르면? (i10_can으로 40/80/24 MHz)#

무엇을 확인하나: 7절에서 만든 i10_can(M_CAN v3.1과 같은 bittiming_const)을 모듈 파라미터 clock_hz로 클럭만 바꿔 로드하면서, 실제 SoC에서 흔한 CAN 클럭(80 MHz: M_CAN에서 흔한 값, 40 MHz: MCP2518FD 오실레이터·i.MX8MP FlexCAN DT 기본, 24 MHz: 일부 보드의 FlexCAN)이 결과에 주는 영향을 본다.

(전체 21줄 중 대표 행만 남겼다.) 출력에서 볼 것:

  • tq 12는 12.5 ns를 정수 ns로 잘라 표시한 것이고, 24 MHz의 tq 41은 41.67 ns다. 표시값으로 거꾸로 계산하면 틀린다 — brp / clock으로 계산하자.
  • 80 MHz에서 8 Mbit/s 데이터 구간은 10 tq/비트, 40 MHz는 5 tq/비트(샘플 포인트 60%로 밀림), 24 MHz는 3 tq에 dprop-seg 0. 24 MHz로 5 Mbit/s는 4.8 Mbit/s(오차 4%)밖에 못 만든다 — 커널은 FD 데이터 비트레이트에서는 경고만 내고 받아들였다. 이런 버스는 동작이 불안하다. CAN FD 보드 설계에서 CAN 클럭을 40 MHz나 80 MHz로 잡으라고 하는 이유(CiA 601-3 권장)가 숫자로 보인다.
  • 같은 SoC라도 CAN 클럭은 DT의 assigned-clock-rates로 바뀐다(8절 i.MX8MP 예). ip -details의 clock 값을 먼저 보자.

컨트롤러가 정확히 못 만드는 nominal 비트레이트도 보자.

  • 470 k를 달라고 했더니 470588(오차 0.1%)과 샘플 포인트 86.2%를 받았다. 0.5% 이내라 경고만.
  • 3 Mbit/s classic이 rc=0으로 통과했다! CAN 규격상 classic은 1 Mbit/s가 최대지만, 커널은 드라이버가 priv->bitrate_max를 설정했을 때만 막는다. 내 드라이버는 안 했다. 실제 드라이버는 DT의 can-transceiver { max-bitrate = <...>; } 자식 노드를 of_can_transceiver()로 읽어 이 값을 채운다(flexcan, m_can 등). 리뷰 포인트다.

4.5 예제 5 — 커널 알고리즘을 Python으로 다시 짜서 검산#

무엇을 확인하나: 4.2절 알고리즘을 그대로 옮긴 30줄짜리 Python이 커널의 ip -details 출력과 같은 답을 내는지. 면접에서 "500 kbit/s, 40 MHz면 BRP·TSEG를 어떻게 잡나?"를 받았을 때 이 순서로 말하면 된다.

출력에서 볼 것: 9개 모두 예제 3·4의 커널 출력(s7의 40 MHz 125 k 행 tq 50 ... brp 2도 포함)과 같다. 40 MHz 125 k가 재미있다. brp 1이면 320 tq로 비트레이트 오차는 0이지만, TSEG1 최대 256 때문에 TSEG2가 63 이상이 되어 샘플 포인트가 80.3%밖에 안 된다(목표 87.5%보다 7.2%p 낮음). 알고리즘은 "비트레이트 오차 → 샘플 포인트 오차" 순으로 더 나은 해를 계속 찾다가 brp 2·160 tq에서 둘 다 0인 해를 만나고 멈춘다. 즉 커널은 무조건 tq가 가장 짧은 해를 고르는 게 아니라, 샘플 포인트까지 맞는 해를 tq가 짧은 쪽부터 찾는다.

5.1 예제 6 — RAW 필터: 정확 일치, 범위, EFF, 그리고 함정#

무엇을 확인하나: 한 소켓에 필터 여러 개(OR 결합)를 걸었을 때 어떤 ID가 통과하는지. 필터 규칙은 (received_id & mask) == (filter_id & mask)이고, can_id의 플래그 비트(EFF, RTR)도 마스크 대상이다.

출력에서 볼 것:

  • 0x123(데이터)은 통과, 0x124와 0x123 RTR은 막혔다. 첫 필터의 마스크에 CAN_EFF_FLAG | CAN_RTR_FLAG를 넣었기 때문에 "SFF이고 RTR이 아닌 0x123"만 맞는다.
  • {0x200, 0x700} 필터는 0x2AB를 통과시켰지만 EFF 0x200(data 5)도 통과시켰다. 마스크에 CAN_EFF_FLAG가 없으면 29비트 ID의 하위 11비트만 보고 판단한다. 표준 ID만 원하면 마스크에 CAN_EFF_FLAG를 꼭 넣자. 실무에서 J1939 장비와 CANopen 장비가 한 버스에 있을 때 이 실수로 엉뚱한 프레임이 섞인다.
  • 0x18FF50E5(J1939: 우선순위 6, PGN 0xFF50, 소스 주소 0xE5)는 통과, 소스 주소만 다른 0x18FF50E6은 차단.
  • 이 필터는 소켓별 SW 필터다. 컨트롤러 HW 필터(메일박스 acceptance mask)는 SocketCAN에서 보통 "모두 받기"로 열어 두고, 커널이 소켓마다 거른다. 그래서 버스 부하가 높으면 필터와 무관하게 CPU가 모든 프레임의 IRQ·skb 비용을 낸다(8절).
  • 필터 개수 제한, CAN_RAW_JOIN_FILTERS(AND 결합), CAN_INV_FILTER(반전)도 있다. candump 문법으로는 can0,123:7FF(일치), can0,123~7FF(반전), can0,#FFFFFFFF(에러 마스크).

5.2 커널은 필터를 어디에 저장하나 — /proc/net/can/rcvlist_*#

af_can은 수신 필터를 장치별 리스트에 넣고, 프레임마다 이 리스트를 훑어 raw_rcv() 같은 콜백을 부른다(9절). 리스트 종류: rx_all(마스크 0), rx_fil(일반 마스크), rx_inv(반전), rx_eff(EFF 정확 일치), rx_sff(SFF 정확 일치, ID로 해시된 배열), rx_err(에러 프레임).

출력에서 볼 것: 123:7FF은 "정확히 0x123"인데도 해시 리스트 rx_sff가 아니라 일반 리스트 rx_fil에 들어갔다. 마스크에 CAN_EFF_FLAG | CAN_RTR_FLAG까지 포함해야(CAN_SFF_MASK | CAN_EFF_FLAG | CAN_RTR_FLAG) 빠른 SFF 해시 리스트로 간다. 필터가 수백 개인 게이트웨이에서는 이 차이가 CPU 사용량 차이로 나타난다. 필터 없는 candump는 rx_all(마스크 0)에 들어간다. function 주소는 raw_rcv(포인터 값은 해시된 값이라 실행마다 다르다).

5.3 예제 7 — CAN FD 프레임: CAN_RAW_FD_FRAMES, BRS, 크기로 구분#

무엇을 확인하나: FD 소켓 옵션을 켜면 한 소켓으로 classic(16 B)과 FD(72 B)를 모두 쓰고 읽을 수 있고, read()가 돌려주는 크기로 종류를 안다는 것. 그리고 FD에서 허용되지 않는 길이(13)를 보내면 어떻게 되는지.

출력에서 볼 것:

  • FD 프레임의 flags가 0x5 = CANFD_BRS(0x01) + CANFD_FDF(0x04). FDF는 CAN XL 도입 이후 커널이 모든 FD 프레임에 세워 주는 "이건 FD다" 표시다.
  • len 13 FD 프레임이 그대로 13으로 도착했다. 실제 버스에는 DLC 코드(0..15)만 있으므로 13바이트는 존재할 수 없다. 실제 드라이버는 can_fd_len2dlc(13) = DLC 10(16바이트)으로 올림해서 보내고, 수신 측은 can_fd_dlc2len()으로 16바이트를 받는다(남은 3바이트는 패딩). 내 i10_can은 레지스터가 없어서 skb를 그대로 복사하므로 이 변환이 빠졌다 — 가상 드라이버가 실제 HW와 다르게 동작하는 지점이다. 앱은 FD 길이를 0..8, 12, 16, 20, 24, 32, 48, 64 중에서 쓰자.
  • FD를 지원하지 않는 소켓(옵션 off)에 FD 프레임이 오면 그 소켓은 받지 않는다. FD가 꺼진 인터페이스에 72바이트를 쓰면 EINVAL.

같은 일을 실제 FD 컨트롤러(CTU CAN FD 두 채널, 같은 QEMU 버스)에서도 했다. cansend의 ##<flags> 문법이 FD 프레임이다(##1 = BRS).

출력에서 볼 것: mtu 72(FD 모드). candump는 FD 프레임 길이를 [64], [02]처럼 두 자리로 찍어 classic([2])과 구분한다. 데이터 샘플 포인트 0.75를 요청했는데 0.740(= (1+18+18)/50)을 받았다 — 50 tq에서 정확히 75%를 만들 수 없어 "목표 이하에서 가장 가까운 값"을 고른 것이다. 그리고 state STOPPED — 인터페이스가 UP인데 상태가 STOPPED다. 6.1절에서 이유를 본다(에뮬레이터 한계).

5.4 예제 8 — ISO-TP: 40바이트를 8바이트 프레임으로 쪼개기#

무엇을 확인하나: CAN_ISOTP 소켓이 커널 안에서 First Frame / Flow Control / Consecutive Frame을 처리하는 모습. UDS 진단(예: 모터 컨트롤러 펌웨어 업데이트)의 전송 계층이다.

출력에서 볼 것: 10 28 = First Frame, 총 길이 0x28 = 40. 수신 측 커널이 30 00 00 = Flow Control(Continue To Send, block size 0 = 끝까지, STmin 0)을 0x7E8로 돌려줬고, 송신 측은 21, 22 … 순번(SN)을 단 Consecutive Frame 5개로 나머지 34바이트를 보냈다. 유저 공간은 write(40바이트)와 read() 한 번씩만 했다. candump -x의 TX/RX 표시는 프레임이 이 장치에서 나간 것(echo)인지 들어온 것인지다.

5.6 예제 10 — BCM 주기 송신과 지터 측정 (10 ms heartbeat)#

모터 컨트롤러는 보통 "명령이 N ms 동안 안 오면 정지(watchdog)"하도록 짠다. 그래서 메인 컴퓨터는 명령을 정확한 주기로 보내야 한다. 방법 세 가지를 비교했다.

  2. 유저 루프 write() + usleep(10000): 가장 흔한 초보 코드.

측정은 두 경로로 했다. (가) VM 호스트에서 vcan에 직접 송신(기준선), (나) QEMU 게스트의 SJA1000(can0) → QEMU 버스 → can-host-socketcan → 호스트 vcan. 각 400 간격.

(위 통계는 수집한 간격 파일을 Python으로 요약한 것. guest_A = BCM, guest_B = usleep 루프, guest_C = ABSTIME 루프. 단위 ms.)

출력에서 볼 것:

  • BCM의 평균이 10 ms보다 길다(호스트 +0.11 ms, 게스트 +0.79 ms). 소스를 보면 이유가 있다. bcm_tx_set_expiry()가 다음 만료를 ktime_get() + ival, 즉 "지금(핸들러가 실제로 돈 시각) + 10 ms"로 잡는다(net/can/bcm.c). 핸들러 지연이 매 주기 누적되어 주기가 늘어난다. 400 프레임 합계 4044 ms vs 4000 ms — 1%의 주기 드리프트다.
  • usleep 루프는 같은 누적에 write()·스케줄링 지연까지 더해져 평균이 더 길고(게스트 11.7 ms), 꼬리(최대 52 ms)가 길다. watchdog 타임아웃 50 ms짜리 모터 컨트롤러라면 한 번 멈출 수 있는 수준이다.
  • ABSTIME 루프는 평균이 정확히 10.000 ms(합계 4000.1 ms). 늦게 깨어난 다음 주기는 짧아져서(min 3.9 ms) 따라잡는다. 장기 주기는 정확하지만 개별 간격의 지터는 남는다. 모터 제어에는 보통 "평균 주기 정확 + 지터 작게"가 필요하므로, 실무에서는 ABSTIME 루프를 SCHED_FIFO 스레드로 돌리거나(L 모듈), 지터가 큰 일은 MCU 쪽 watchdog 여유로 흡수한다.
  • 공용 VM이라 측정 중에 다른 노트의 QEMU 여러 개가 CPU를 쓰고 있었다(load average 약 2.5). 절대값보다 세 방식의 차이를 보자. 실제 보드(i.MX8, PREEMPT_RT)에서는 지터가 수십 µs 수준으로 줄어든다(이 노트에서는 측정하지 않음).

6. 에러 처리 — 에러 상태, 에러 프레임, bus-off, restart#

6.1 상태 머신과 Linux의 enum can_state#

그림 6 — CAN 에러 상태 머신. 문턱값은 TEC·REC 중 큰 쪽 기준(bus-off는 TEC만). Linux의 enum can_state가 그대로 대응한다: CAN_STATE_ERROR_ACTIVE, ERROR_WARNING, ERROR_PASSIVE, BUS_OFF, 그리고 STOPPED(인터페이스 down), SLEEPING.

커널은 문턱값 판정 헬퍼도 제공한다. can_state_get_by_berr_counter()가 TEC·REC를 받아 tx_state·rx_state를 계산하고(내부 can_state_err_to_state(): < 96 active, < 128 warning, < 256 passive, 그 외 bus-off), can_change_state()가 상태를 바꾸면서 통계(error_warning, error_passive, bus_off 카운터)를 올리고 에러 프레임에 CAN_ERR_CRTL 정보를 채운다.

bus-off 이후: 규격상 노드는 recessive 11비트를 128번 관찰하면 다시 error-active로 돌아갈 수 있다. 하지만 Linux는 정책을 유저에게 맡긴다.

  • restart-ms 0(기본): 자동 복구 안 함. ip link set can0 type can restart로 수동 재시작하거나 down/up.
  • restart-ms 100: 드라이버가 can_bus_off()를 부르면 can_dev가 100 ms 뒤 can_restart()를 예약한다. can_restart()는 남은 echo skb를 버리고(tx_dropped), CAN_ERR_RESTARTED 에러 프레임을 올리고, 드라이버의 do_set_mode(dev, CAN_MODE_START)를 부른다.
  • 컨트롤러마다 bus-off 뒤 HW 동작이 다르다. 예를 들어 SJA1000은 bus-off가 되면 HW가 스스로 reset mode로 들어가 멈추고, 드라이버의 do_set_mode(CAN_MODE_START)가 sja1000_start()로 다시 초기화한다. 드라이버는 이런 HW 동작을 can_dev의 restart 정책에 맞춰 준다 — 새 컨트롤러를 쓸 때는 데이터시트의 bus-off recovery 절과 드라이버의 do_set_mode를 함께 읽자.

무엇을 확인하나: 실제 버스에서 노드 혼자 송신하면 ACK가 없어 TEC가 오르고 error-passive가 된다. QEMU의 SJA1000·CTU CAN FD 에뮬레이션이 이것을 재현하는지.

(link/can, bitrate 줄은 생략했다.) 출력에서 볼 것:

  • 혼자인데도 TX 3개 모두 성공, TEC 0, 에러 프레임 0개. QEMU의 CAN 버스 모델은 ACK·비트 레벨을 에뮬레이션하지 않는다 — 프레임 단위로 다른 클라이언트에 전달하고 송신은 항상 완료로 처리한다. 그래서 QEMU로는 ACK 에러·error-passive·bus-off를 볼 수 없다. 이 노트에서 에러 상태를 직접 쓴 드라이버로 재현하는 이유다.
  • CTU CAN FD의 상태가 UP인데 STOPPED다. 드라이버 소스를 보면 ctucan_chip_start()가 priv->can.state = CAN_STATE_STOPPED로 두고 "컨트롤러가 켜지면 FCSI(fault confinement state change) 인터럽트가 와서 ERROR_ACTIVE가 된다"고 기대한다. 에뮬레이터가 그 인터럽트를 안 낸다. 드라이버의 상태 표시는 HW 인터럽트에 의존한다 — 실물에서 상태가 이상하면 IRQ 배선·마스크부터 의심하는 근거가 된다.
  • bus-off가 아닌데 restart를 요청하면 EINVAL. can_dev는 bus-off 상태에서만 수동 restart를 받는다.

6.4 예제 12 — 혼자 남은 노드: ACK 에러 → error-passive에서 멈춤#

무엇을 확인하나: 내 드라이버 i10_can에 fault=1(아무도 ACK 안 함 = 케이블 빠짐, 상대 노드 전원 꺼짐)을 걸고 한 프레임을 보내면, 자동 재전송마다 TEC +8 → 96에서 warning → 128에서 passive → 거기서 멈추는지(1.3절의 예외 규칙). 그리고 고장을 풀면 TEC가 1씩 내려가며 active로 돌아오는지. 드라이버는 재전송 간격을 관찰하기 쉽게 2 ms로 늦췄다(retry_us=2000, 실제 HW는 에러 프레임 + 인터미션 약 20~30비트 후 즉시 재전송).

(errdump 출력 중 cangen이 보낸 DATA id=200 32줄은 생략했다. 시각은 errdump 시작 기준 ms.) 출력에서 볼 것:

  • 15 ms 만에 이미 ERROR-PASSIVE (tx 128). 2 ms마다 재전송 × 16번 = 약 32 ms면 128에 도달한다(TCG 게스트라 타이머가 약간 느슨하다). 그 뒤 0.4 s 동안 계속 재전송했지만 TEC는 128에서 멈췄다. bus-off가 아니다.
  • berr-reporting을 껐으므로 에러 프레임은 상태가 바뀔 때만 왔다: id=20000204 = CAN_ERR_FLAG(0x20000000) + CAN_ERR_CNT(0x200) + CAN_ERR_CRTL(0x4), data[1]이 WARNING → PASSIVE.
  • 고장을 풀자(fault=0) 대기하던 0x123이 바로 나가고(DATA id=123), 성공 1회로 TEC 127 → ERROR-WARNING. 이후 성공 송신 32번째에 TEC 95 → back-to-ACTIVE(CAN_ERR_CRTL_ACTIVE). 40개를 다 보낸 뒤 TEC 87.
  • 실무 의미: 로봇에서 "CAN 케이블이 빠졌다"는 증상은 bus-off가 아니라 error-passive + TX가 안 끝남(echo 안 옴) + 큐가 참으로 나타난다. 앱 쪽에서는 write()가 블록되거나 ENOBUFS가 난다.

6.5 예제 13 — 물리 고장: bit error → bus-off → restart-ms 반복#

무엇을 확인하나: fault=2(송신 비트가 깨짐 — CAN_H가 GND에 단락, 트랜시버 고장, 비트레이트 불일치 노드 등)에서 TEC가 passive에서도 계속 올라 bus-off가 되고, restart-ms 100이 복구시키지만 고장이 남아 있으면 다시 bus-off가 반복되는지. berr-reporting을 켜서 개별 버스 에러도 본다.

(마지막 줄의 긴 gso 필드는 ...로 줄였다. errdump 198줄 중 앞 40줄만 보였다. 이어지는 6, 6은 BUS-OFF, RESTARTED 줄 수.)

그림 7 — 위 실행의 에러 프레임에서 뽑은 TEC 궤적(실측). 2 ms마다 bit error로 +8, 32번째에 256 = bus-off. restart-ms 100 뒤 TEC 0으로 복귀했지만 고장이 그대로라 다음 프레임에서 같은 계단이 반복된다.

출력에서 볼 것:

  • id=20000288 = FLAG + CNT(0x200) + BUSERROR(0x80) + PROT(0x8), data[2] = CAN_ERR_PROT_BIT. 96·128을 지날 때는 + CRTL(0x4) = 2000028C. 마지막은 200002C8 = + BUSOFF(0x40). TEC 256은 u8 data[6]에 255로 잘려 들어갔다(드라이버의 min_t(u16, tec, 255)).
  • error-passive에서도 bit error는 TEC를 올린다(ACK 에러 예외와 대비). 그래서 물리 고장은 bus-off로 끝난다.
  • bus-off 순간 ip link가 NO-CARRIER ... state DOWN을 보인다. can_dev의 can_bus_off()가 netif_carrier_off()를 부르기 때문이다. 인터페이스는 여전히 UP(관리 상태)이고 링크만 down이다. ip monitor link나 systemd-networkd가 이것을 이벤트로 받을 수 있다.
  • 약 100 ms 뒤(375.64 → 479.75 ms) RESTARTED, TEC 0. dmesg에 bus-off, scheduling restart in 100 ms가 6번 — 고장이 있는 동안 bus-off ↔ restart가 계속 반복됐다. 통계 줄: re-started 6, bus-errors 537, error-warn 7, error-pass 7, bus-off 6(warn/pass가 7인 것은 6.4절 phase A의 1번 포함).
  • cangen이 write: No buffer space available(ENOBUFS)로 죽었다. bus-off 동안 드라이버 큐가 멈춰 있고 qdisc(qlen 10)가 가득 찼기 때문이다. CAN 앱은 ENOBUFS를 "잠시 후 재시도" 또는 "버스 이상 신호"로 처리해야 한다 — 무시하고 죽는 앱이 흔하다. TX dropped 6 = restart 때 can_flush_echo_skb()가 버린, bus-off 순간 송신 중이던 프레임 6개.
  • 이 패턴("restart-ms로 계속 살아났다 죽었다")이 면접 단골 질문 "CAN 버스가 계속 bus-off 된다"의 현장 모습이다. restart-ms는 증상을 가릴 뿐 원인을 고치지 않는다. 디버그 순서는 12절 Q1.

6.6 예제 14 — one-shot 모드: 재전송 안 함#

무엇을 확인하나: one-shot on(CAN_CTRLMODE_ONE_SHOT)이면 ACK가 없을 때 컨트롤러가 재전송하지 않고 프레임을 버리는지. 시간 결정성이 중요한 TTCAN류 설계나, "오래된 명령을 늦게 보내느니 버리는 게 낫다"는 제어 루프에서 쓴다.

출력에서 볼 것: ACK 에러 1번(TEC 8, errors 1) 후 프레임을 버렸다(dropped 1). 재전송이 없으니 TEC가 8에서 멈췄다. 앱은 프레임이 사라진 것을 알 방법이 echo가 안 오는 것뿐이므로, one-shot을 쓰면 상위 프로토콜에서 응답 확인이 필요하다.

7.3 코드 (2/6) — RX: "IRQ"가 큐에 넣고 NAPI가 위로 올린다#

  • NAPI(I6에서 자세히): IRQ 핸들러는 RX 인터럽트를 끄고 napi_schedule()만 한다. softirq에서 poll(budget)이 FIFO를 최대 budget개 비우며 netif_receive_skb()로 스택에 올리고, 다 비우면 napi_complete_done() 후 IRQ를 다시 켠다. 고부하에서 IRQ 폭주를 막는 구조다 — bare-metal에서 "RX ISR은 플래그만 세우고 메인 루프에서 FIFO를 비우는 것"과 같다.
  • CAN에서 NAPI의 함정: 수신 순서. 메일박스가 여러 개인 컨트롤러(FlexCAN)는 HW 메일박스 순서와 도착 순서가 다를 수 있다. 그래서 커널에는 IRQ에서 메일박스를 타임스탬프 순으로 정렬해 큐에 넣고 NAPI로 올려 주는 헬퍼 can_rx_offload가 있다(8절, flexcan·m_can 주변 장치·mcp251xfd가 사용).
  • 에러 프레임은 rx_packets에 안 센다. 6.x 커널 드라이버들의 관례다.
  • alloc_can_skb()/alloc_canfd_skb()는 CAN용 skb를 만들고 skb->protocol, ifindex, can_skb_priv 같은 헤더를 채워 준다. CAN 드라이버는 일반 netdev_alloc_skb()를 쓰지 않는다.

7.4 코드 (3/6) — fault confinement: TEC/REC → 상태 → 에러 프레임#

  • 실제 HW는 TEC/REC를 레지스터로 제공한다. 드라이버는 에러 IRQ에서 그 값을 읽어 can_state_get_by_berr_counter() → can_change_state() → (bus-off면) can_bus_off() 순서로 부른다. 이 함수의 흐름이 sja1000_err(), m_can_handle_state_change(), flexcan_irq_state()와 같다.
  • alloc_can_err_skb()가 NULL이어도(메모리 부족) 상태 갱신은 해야 한다. can_change_state(dev, NULL, ...)가 허용되는 이유다.
  • can_change_state()가 같은 상태로 불리면 커널이 oops, state did not change 경고를 찍는다. 그래서 new != p->can.state일 때만 부른다.
  • 이 함수는 hrtimer softirq 컨텍스트에서 돌므로 spin_lock()(BH 비활성 불필요), i10_set_mode()는 프로세스 컨텍스트(workqueue)라 spin_lock_bh(). 같은 데이터를 다른 컨텍스트에서 만질 때 락 종류를 맞추는 것은 F 모듈의 핵심이다.

7.5 코드 (4/6) — TX: echo skb와 "TX 완료 인터럽트"#

  • ndo_start_xmit 계약: skb를 받으면 반드시 소유권을 가져간다(보내거나, 보관하거나, 버리거나). NETDEV_TX_OK를 돌려주고, HW 큐가 꽉 차면 netif_stop_queue(). TX 완료에서 netif_wake_queue(). 메일박스가 하나면 매번 stop/wake다. FlexCAN·M_CAN처럼 TX FIFO가 깊으면 echo_skb_max를 FIFO 깊이로 잡고 인덱스로 관리하며 FIFO가 찰 때만 stop한다.
  • echo skb 수명: can_put_echo_skb(skb, dev, idx, frame_len) → (TX 완료) can_get_echo_skb(dev, idx, NULL)이 skb를 netif_rx()로 올리고 데이터 길이를 돌려준다 → tx_bytes. 실패·중단이면 can_free_echo_skb(). bus-off 재시작 때는 can_dev가 can_flush_echo_skb()로 정리한다.
  • can_dev_dropped_skb(): listen-only 모드면 버리고, 잘못된 길이·MTU의 skb를 걸러 낸다. 모든 CAN 드라이버의 ndo_start_xmit 첫 줄이다.
  • ndo_open의 open_candev()는 비트 타이밍이 설정됐는지 검사하고(bit-timing not yet defined → EINVAL), carrier를 켠다. 실제 드라이버는 그 다음 클럭 enable → 컨트롤러 리셋 → 비트 타이밍·모드 레지스터 → IRQ 요청 → napi_enable → 컨트롤러 start → netif_start_queue 순서다.

7.6 코드 (5/6, 6/6) — stop, ops, 등록과 해제#

  • dev->flags |= IFF_ECHO — 처음 버전에서 이 줄을 빼먹었다. 증상: 프레임 하나를 보내면 그 뒤로 인터페이스가 영원히 멈춤(TX 통계 0, ISO-TP가 First Frame만 보내고 멈춤). 원인: can_put_echo_skb()는 IFF_ECHO가 없으면 skb를 그냥 해제하고 0을 반환한다. 그러면 TX 완료 타이머가 echo_skb[0] == NULL을 보고 바로 return하는데, 그 경로에서 netif_wake_queue()가 안 불려 큐가 멈춘 것이다. 동시에 af_can은 IFF_ECHO가 없으니 스스로 루프백을 해서, 같은 장치의 다른 소켓에는 프레임이 "보인다". 그래서 처음에는 필터 테스트가 성공한 것처럼 보였다. ip link의 플래그가 <NOARP>였고(정상은 <NOARP,ECHO>) 거기서 원인을 찾았다. 교훈: ip -details link의 플래그와 TX 통계부터 보자.
  • 해제 순서: 두 장치를 모두 unregister_candev()(내부에서 close → i10_stop → hrtimer_cancel)한 다음에 free한다. 하나를 먼저 free하면 다른 쪽 타이머가 이미 해제된 peer를 만질 수 있다. 실제 드라이버의 remove()도 "unregister → HW 끄기 → 자원 해제" 역순이다.
  • 실제 드라이버는 module_init 대신 platform_driver/pci_driver/spi_driver의 probe()에서 이 일을 하고, SET_NETDEV_DEV(dev, &pdev->dev)로 부모 장치를 연결한다(그래야 ip -details에 parentbus/parentdev가 보이고 sysfs에 장치 계층이 생긴다). i10_can은 부모가 없어 /sys/devices/virtual/net/i10can0에 생긴다.

8. 실제 SoC의 CAN 컨트롤러 — M_CAN, FlexCAN, MCP251xFD#

8.1 Bosch M_CAN — TI AM62, STM32MP1, NXP i.MX93 등#

Bosch가 IP로 파는 CAN FD 코어. 메시지 RAM(TX buffer, RX FIFO 0/1, TX event FIFO, 필터)이 레지스터 영역과 따로 있다. AM62의 노드(arch/arm64/boot/dts/ti/k3-am62-main.dtsi):

  • reg-names: 레지스터(m_can)와 메시지 RAM(message_ram) 두 영역. 드라이버는 devm_platform_ioremap_resource_byname()으로 각각 매핑한다(H1).
  • clock-names = "hclk", "cclk": 버스 클럭과 CAN 코어 클럭(cclk). ip -details의 clock이 cclk 주파수다. 비트 타이밍 문제의 절반은 이 클럭이 기대와 다른 데서 온다(H3).
  • bosch,mram-cfg = <offset sidf xidf rxf0 rxf1 rxb txe txb>: 메시지 RAM 분할(11비트 필터 128개, 29비트 필터 64개, RX FIFO0 64개 …). 보드마다 튜닝 대상.
  • 보드 dts에서 status = "okay"와 pinctrl(H4), 그리고 트랜시버(phys = <&transceiver1> 또는 can-transceiver 자식 노드)를 붙인다.
  • m_can_platform.c는 DT에 interrupts가 없으면 IRQ 없이 1 ms hrtimer로 폴링한다(HRTIMER_POLL_INTERVAL_MS 1). SoC에 따라 일부 M_CAN 인스턴스의 인터럽트가 메인 CPU로 라우팅되지 않는 경우를 위한 것이다. 폴링이면 RX 지연이 최대 1 ms 늘어나므로 제어 루프 설계에 반영해야 한다.
  • RX는 MMIO M_CAN이면 NAPI(m_can_poll), SPI로 붙는 TCAN4x5x(M_CAN 코어를 SPI 칩에 넣은 것)면 is_peripheral 경로로 rx-offload를 쓴다.

8.2 NXP FlexCAN — i.MX6/8, Layerscape#

메일박스(MB) 기반 컨트롤러. i.MX8MP 노드(imx8mp.dtsi):

  • assigned-clock-rates = <40000000>: CAN 클럭을 SYS_PLL1의 40 MHz 출력으로 고정한다. 4.4절에서 본 대로 CAN FD에 좋은 값이다. 보드에서 이 값을 바꾸면 모든 비트 타이밍 결과가 바뀐다.
  • fsl,clk-source: FlexCAN 내부 클럭 소스 선택(0 = 오실레이터, 1 = 주변장치 클럭 — SoC마다 의미가 다르니 바인딩 문서 fsl,flexcan.yaml 확인).
  • fsl,stop-mode: 저전력 stop 모드에서 CAN 프레임으로 깨어나기(wakeup) 위한 GPR 레지스터 위치.
  • RX는 can_rx_offload: IRQ 핸들러가 메일박스(또는 RX FIFO)를 비워 HW 타임스탬프(FlexCAN 16비트 free-running 타이머) 순으로 정렬한 skb 큐에 넣고(can_rx_offload_irq_offload_timestamp()), NAPI가 순서대로 올린다. 메일박스 여러 개에서 생기는 재정렬(reordering) 문제를 해결하는 장치다.

8.3 Microchip MCP2517FD/MCP2518FD (mcp251xfd) — SPI CAN FD#

SoC에 CAN이 없거나 모자랄 때 SPI로 붙이는 독립 컨트롤러. Raspberry Pi CAN FD HAT, Jetson 캐리어 보드에서 흔하다. 바인딩 예(microchip,mcp251xfd.yaml):

SPI CAN의 지연 문제가 면접에서 자주 나온다. 구조적 이유:

  • 인터럽트 핀은 GPIO(레벨 low)다. SPI 전송은 잠들 수 있으므로 핸들러는 hardirq에서 못 돌고 threaded IRQ로 돈다(request_threaded_irq(..., NULL, mcp251xfd_irq, IRQF_SHARED | IRQF_ONESHOT, ...), F7·H6). 즉 IRQ → 스레드 깨우기 → 스케줄링 지연이 붙는다.
  • 프레임 하나를 꺼내는 데 SPI 트랜잭션이 여러 번(인터럽트 상태 읽기, FIFO 헤드 읽기, 데이터 읽기, FIFO 포인터 갱신) 필요하다. 20 MHz SPI에서도 트랜잭션당 수십 µs, 컨트롤러 드라이버와 DMA 설정에 따라 더 길다(H7). 1 Mbit/s 버스에 프레임이 몰리면 RX FIFO가 넘쳐 CAN_ERR_CRTL_RX_OVERFLOW가 난다.
  • 그래서 드라이버는 SPI 왕복을 줄이는 기법을 쓴다: 여러 레지스터를 한 번에 읽는 bulk read, microchip,rx-int-gpios(RX 전용 인터럽트 핀 — 이 GPIO를 읽어 "RX가 있는지"를 SPI 없이 확인), IRQ coalescing(ethtool -C), 링 크기 조절(ethtool -G).
  • 실무 대책: SPI 컨트롤러 드라이버의 DMA/폴링 임계값 확인, IRQ 스레드를 SCHED_FIFO 높은 우선순위로(chrt), PREEMPT_RT, SPI 클럭 최대치, 그리고 가능한 한 SoC 내장 CAN 사용.

8.4 타임스탬프 — 언제 받았나#

제어·센서 퓨전에서는 "프레임이 언제 버스에 있었나"가 중요하다.

  • SW 타임스탬프: 소켓 옵션 SO_TIMESTAMPNS(5.6절 i10_jit에서 사용) 또는 SO_TIMESTAMPING의 SW RX. skb가 스택에 들어올 때(NAPI 안) 찍힌다. IRQ 지연·NAPI 지연·SPI 지연이 모두 포함된다.
  • HW 타임스탬프: mcp251xfd·m_can·flexcan 일부는 컨트롤러의 타임베이스로 수신 시각을 찍고, 드라이버가 이를 skb_hwtstamps(skb)에 넣는다. 유저는 SO_TIMESTAMPING + SOF_TIMESTAMPING_RAW_HARDWARE로 받는다. 지원 여부는 ethtool -T can0(드라이버의 get_ts_info, mcp251xfd는 can_ethtool_op_get_ts_info_hwts)으로 확인한다. 이 노트의 가상 장치에서는 실행하지 않았다.
  • rx-offload 경로는 HW 타임스탬프로 정렬까지 한다(8.2절).

8.5 종단 저항(termination)#

CAN 버스는 양 끝에 120 Ω이 있어야 한다(측정: 전원 끈 상태에서 CAN_H–CAN_L 사이 약 60 Ω). 일부 보드는 GPIO로 종단을 켜고 끈다 — DT의 termination-gpios, termination-ohms(can-controller.yaml), 유저는 ip link set can0 type can termination 120. 종단이 없거나 3개 이상이면 반사·레벨 문제로 bit/form error가 나고 bus-off까지 간다.

10.1 로봇 보드 CAN bring-up 체크리스트#

새 보드에서 can0가 안 될 때, 아래 순서로 바깥(HW)에서 안(앱)으로 좁힌다. 각 단계의 명령은 이 노트에서 한 번씩 돌려 본 것들이다.

  1. 장치가 있나: ip -details link show can0 — 없으면 DT status, 드라이버 모듈, dmesg | grep -i can(probe 에러, 클럭 못 얻음 -EPROBE_DEFER).
  2. 클럭이 맞나: ip -details의 clock 값이 데이터시트·DT assigned-clock-rates와 같은가.
  3. 비트 타이밍: ip link set can0 type can bitrate 500000 sample-point 0.875 후 ip -details의 tq·세그먼트를 손으로 검산(4절). MCU 노드들의 설정(샘플 포인트·SJW)과 비교.
  4. 버스 물리: 전원 끈 상태 CAN_H–CAN_L 60 Ω, 트랜시버 STB/EN 핀(GPIO)이 normal 모드인가, 트랜시버 전원(xceiver-supply).
  5. 링크 테스트: 상대 노드 없이 ip link set can0 type can loopback on(컨트롤러 내부 루프백, CAN_CTRLMODE_LOOPBACK 지원 시)으로 드라이버·IRQ부터 확인 → 그 다음 실제 버스.
  6. 에러 관찰: candump -e any,0:0,#FFFFFFFF + ip -details -statistics link show can0(berr-counter, error-warn/pass, bus-off, re-started).
  7. scope로 비트 폭 측정(500 k = 2 µs), 디코더로 ACK 슬롯·에러 플래그 확인.

10.4 모터 컨트롤러 예: CANopen/CiA 402와 SocketCAN#

많은 산업용 모터 드라이버는 CANopen(CiA 301/402)을 쓴다. Linux에서는 SocketCAN RAW 위에 유저 공간 스택(예: CANopenNode, Lely)을 올린다. 커널은 프레임 전달·필터·에러 보고까지만 하고, NMT·SDO·PDO·heartbeat는 유저 공간 몫이다. 반면 J1939(트럭·농기계)와 ISO-TP(진단)는 커널 소켓이 있다(2.1절). 면접에서 "커널에 넣을 것 vs 유저 공간에 둘 것"을 물으면: 주소 클레임·세그멘테이션처럼 타이밍이 촘촘하고 여러 앱이 공유하는 상태는 커널, 장치 프로파일 로직은 유저 공간이라고 답하면 된다.

12. 면접에서 이렇게 말한다#

Q. "A CAN bus on our robot keeps going bus-off. How do you debug it?"

A. 먼저 사실 수집: 어느 노드가 bus-off 되는지, 얼마나 자주, 부하·모터 구동과 상관있는지. Linux 쪽에서는 ip -details -statistics link show can0로 bus-off·re-started·error-warn/pass 카운터와 TEC/REC를 보고, candump -e로 에러 프레임 종류(bit/stuff/form/ACK, 위치)를 본다. TEC만 오르면 이 노드의 송신이 문제(트랜시버, 비트 타이밍, 이 노드만의 배선), REC가 오르면 남이 보낸 프레임을 못 읽는 것이다. 그다음 물리: 60 Ω 종단, 접지·차동 전압, scope로 비트 폭과 에러 플래그 위치. 타이밍: 모든 노드의 bitrate·샘플 포인트·클럭 정확도 일치 여부. 모터 구동 때만 나면 EMI(접지, 케이블 차폐, 트랜시버 공통 모드 범위). restart-ms는 증상을 가리므로 원인을 찾는 동안은 끄거나 카운터를 기록한다.

First I gather facts: which node goes bus-off, how often, and whether it correlates with motor load. On Linux I read ip -details -statistics link show can0 for the bus-off and restart counters and the TEC/REC values, and I capture error frames with candump -e to see whether they are bit, stuff, form or ACK errors and where in the frame they occur. If only TEC climbs, the problem is this node's transmit path — transceiver, bit timing, its stub wiring; if REC climbs, it can't read other nodes' frames. Then the physical layer: 60 ohms between CAN_H and CAN_L, ground and differential levels, and a scope to measure bit time and see the error flags. Then timing: same bitrate and sample point and clock accuracy on every node. If it only happens with the motors running, it's usually EMI — grounding, shielding, common-mode range. I don't rely on restart-ms during debugging because it hides the symptom.

꼬리 질문: "케이블을 뽑으면 bus-off가 되나?" → 아니다. 혼자 남은 송신자는 ACK 에러만 받고, error-passive에서 ACK 에러는 TEC를 올리지 않으므로 passive에 머문다(이 노트 6.4절 실측).

Q. "Explain the SocketCAN architecture."

A. CAN 컨트롤러를 네트워크 인터페이스로 만든 것이다. 유저는 PF_CAN 소켓(RAW, BCM, ISO-TP, J1939)을 쓰고, af_can 코어가 장치별 수신 필터 리스트로 프레임을 소켓에 나눠 준다. 송신은 일반 dev_queue_xmit과 qdisc를 거쳐 드라이버의 ndo_start_xmit으로 간다. 드라이버는 can_dev 라이브러리로 비트 타이밍 계산, netlink 설정, 에러 상태·bus-off·restart, echo skb 루프백을 공유한다. 장점은 여러 앱이 동시에 한 버스를 쓰고, 네트워크 도구·필터·타임스탬프를 그대로 쓴다는 것.

SocketCAN models a CAN controller as a network device. Applications open PF_CAN sockets — raw, broadcast manager, ISO-TP or J1939 — and the af_can core dispatches received frames through per-device filter lists to the sockets. Transmit goes through the normal dev_queue_xmit and qdisc path into the driver's ndo_start_xmit. Drivers share the can_dev library for bit-timing calculation, netlink configuration, error states, bus-off and restart handling, and echo-skb based local loopback. The benefit is multiple applications on one bus, standard networking tools, per-socket filters and timestamps.

Q. "What does the echo skb do in a CAN driver, and why not just loop back in software?"

A. 같은 장치의 다른 소켓이 내 송신 프레임을 보려면 루프백이 필요한데, 드라이버가 IFF_ECHO를 세우면 송신 skb를 can_put_echo_skb로 보관했다가 HW가 실제로 전송을 끝낸 TX-complete 인터럽트에서 can_get_echo_skb로 올린다. 그래서 로컬 앱이 보는 순서와 시각이 버스의 실제 순서와 같고, 중재에 지거나 에러로 못 나간 프레임은 보이지 않는다. SW 즉시 루프백은 "보냈다고 착각"하게 만든다.

When IFF_ECHO is set, the driver keeps the transmitted skb with can_put_echo_skb and only loops it back with can_get_echo_skb in the TX-complete interrupt, after the frame really left the controller. Local listeners therefore see frames in actual bus order and timing, and a frame that never made it onto the bus is never echoed. An immediate software loopback would show frames that were never transmitted.

Q. "How does Linux compute CAN bit timing from a bitrate?"

A. 드라이버가 컨트롤러 클럭과 can_bittiming_const(tseg1/tseg2/sjw/brp 범위)를 등록한다. ip ... bitrate가 오면 can_calc_bittiming()이 CiA 권장 샘플 포인트(≤ 500 k는 87.5%, ≤ 800 k는 80%, 그 이상 75%)를 목표로, 총 tq 수를 큰 값부터 내려가며 brp를 구해 비트레이트 오차, 그다음 샘플 포인트 오차가 최소인 조합을 고른다. 오차가 0.5%를 넘으면 거부한다. 예: 40 MHz, 500 k → brp 1, tq 25 ns, 1+34+35+10 = 80 tq, 샘플 포인트 87.5%.

The driver registers the controller clock and a can_bittiming_const with the tseg1, tseg2, sjw and brp ranges. can_calc_bittiming targets the CiA recommended sample point — 87.5 percent up to 500 kbit/s, 80 up to 800, 75 above — walks the total number of time quanta from large to small, derives the prescaler, and keeps the combination with the smallest bitrate error and then the smallest sample-point error, rejecting anything over 0.5 percent error. For a 40 MHz clock at 500 kbit/s that's brp 1, 25 ns quanta, 80 quanta per bit with the sample point at 87.5 percent.

Q. "Walk me through what a CAN driver does on an error interrupt."

A. TEC/REC와 상태 레지스터를 읽고, alloc_can_err_skb()로 에러 프레임을 만든 뒤 버스 에러 종류(bit/stuff/form/ACK, berr-reporting이 켜졌을 때)를 채운다. can_state_get_by_berr_counter()로 tx/rx 상태를 구해 바뀌었으면 can_change_state(), bus-off면 can_bus_off()(carrier off, restart-ms 예약)와 컨트롤러 정지. 마지막으로 에러 프레임을 NAPI나 netif_rx로 올리고 통계를 갱신한다. 재시작은 can_dev가 do_set_mode(CAN_MODE_START)로 부른다.

It reads TEC, REC and the status register, allocates an error frame with alloc_can_err_skb and, if bus-error reporting is enabled, fills in the protocol error type and location. It derives the TX and RX states with can_state_get_by_berr_counter, calls can_change_state when the state changed, and on bus-off calls can_bus_off, which turns the carrier off and schedules the restart, and stops the controller. Then it pushes the error frame up and updates statistics. Recovery comes later through do_set_mode with CAN_MODE_START.

Q. "Why is an SPI CAN controller like the MCP2518FD harder to get low latency with than an on-chip FlexCAN?"

A. SPI 트랜잭션은 잠들 수 있어서 IRQ를 threaded handler에서 처리해야 하고, 프레임 하나에 SPI 왕복이 여러 번 든다. 그래서 IRQ → 스레드 스케줄링 → SPI 전송 지연이 쌓이고 고부하에서 RX FIFO overflow가 난다. 드라이버는 bulk read, RX 전용 인터럽트 GPIO, IRQ coalescing으로 줄이고, 시스템 쪽에서는 IRQ 스레드 우선순위, SPI DMA, PREEMPT_RT로 대응한다.

SPI transfers can sleep, so the interrupt is handled in a threaded handler, and each frame costs several SPI round trips. Interrupt latency, thread scheduling and SPI transfer time add up, and under heavy load the RX FIFO can overflow. The driver mitigates with bulk reads, a dedicated RX-interrupt GPIO and interrupt coalescing; on the system side you raise the IRQ thread priority, make sure SPI uses DMA, and consider PREEMPT_RT.

Q. "How would you send a CAN message every 10 ms from Linux reliably?"

A. 커널 BCM TX_SETUP이면 프로세스 스케줄링과 무관하게 hrtimer가 보낸다. 다만 6.18 BCM은 다음 만료를 "지금 + 간격"으로 잡아 지연이 누적된다(내 측정: VM에서 평균 10.11 ms). 장기 주기가 정확해야 하면 clock_nanosleep(TIMER_ABSTIME) 루프를 SCHED_FIFO로 돌린다(평균 10.000 ms, 지터는 남음). usleep 루프는 누적 + 긴 꼬리로 최악이다. 받는 쪽 watchdog은 측정한 최악 지연 기준으로 잡는다.

The broadcast manager's TX_SETUP lets a kernel hrtimer send the frame independent of process scheduling, but in current kernels the next expiry is computed as now plus the interval, so latency accumulates — I measured a 10.11 ms mean on a VM. If the long-term period must be exact, I use a clock_nanosleep TIMER_ABSTIME loop in a SCHED_FIFO thread, which averages exactly 10 ms with some per-cycle jitter. A plain usleep loop is the worst: drift plus long tails. The receiver's watchdog timeout is set from the measured worst case.

  2. (계산) CAN 클럭 80 MHz, bitrate 250 k, 샘플 포인트 80%를 SJA1000 같은 작은 bittiming_const(tseg1 1..16, tseg2 1..8, brp 1..64)로 만들 수 있나? 4.5절 Python으로 확인하고 손으로 brp와 세그먼트를 써 보자. 정답/힌트: 비트당 tq는 최대 25(1+16+8), 80 MHz/250 k = 320 = brp × ntq → brp 16 × 20 tq 같은 조합. 샘플 포인트 80%면 1+15 / 20 → TSEG1 15, TSEG2 4.

15. 요약 & 체크리스트#

Linux에서 CAN 컨트롤러는 net_device다. 유저는 PF_CAN 소켓(RAW·BCM·ISO-TP·J1939)을 쓰고, af_can이 필터로 프레임을 나눠 주며, 설정은 ip link ... type can(rtnetlink → can_dev)으로 한다. 드라이버는 alloc_candev + struct can_priv(bittiming_const, clock, ctrlmode_supported, do_set_mode, do_get_berr_counter)를 채우고, TX는 can_put_echo_skb/can_get_echo_skb로 HW 완료 기준 루프백, RX는 NAPI(또는 rx-offload), 에러는 can_change_state/can_bus_off로 보고한다. 비트 타이밍은 커널이 클럭과 상수로 계산하므로 ip -details를 손으로 검산할 수 있어야 하고, 에러 상태는 TEC/REC 문턱값(96/128/256)과 "passive + ACK 에러는 TEC 불변" 예외로 설명할 수 있어야 한다. QEMU의 SJA1000·CTU CAN FD 에뮬레이션은 레지스터 수준 드라이버와 FD 프레임은 보여 주지만 ACK·에러 상태는 재현하지 않는다 — 그래서 직접 쓴 i10_can으로 error-passive 정체, bus-off ↔ restart 반복, ENOBUFS, one-shot을 재현했다.
