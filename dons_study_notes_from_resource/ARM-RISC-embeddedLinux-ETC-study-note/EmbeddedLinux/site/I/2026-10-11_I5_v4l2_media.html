이 노트를 다 읽으면: SoC 카메라 파이프라인(센서 → CSI-2 수신기 → ISP → 스케일러/DMA → DRAM)을 Linux 객체(v4l2_subdev, video_device, media_entity/pad/link)로 그리고 /dev/videoN·/dev/v4l-subdevN·/dev/mediaN이 각각 무엇인지 말할 수 있다 · v4l2-ctl/media-ctl 없이 V4L2·MC uAPI를 직접 C로 불러 포맷 협상, 링크 설정, MMAP 스트리밍, DMABUF zero-copy를 할 수 있고 -EPIPE(link validation 실패)를 dmesg로 원인 추적할 수 있다 · videobuf2의 버퍼 상태 기계와 소유권, 타임스탬프·sequence로 드롭 프레임을 잡는 법을 측정으로 설명할 수 있다 · DT의 port/endpoint/remote-endpoint·data-lanes·link-frequencies가 v4l2-async를 거쳐 그래프가 되는 과정을 실제 드라이버(imx219, i.MX8MP CSI-2) 코드로 따라가고, 최소 V4L2 캡처 드라이버를 직접 쓸 수 있다 왜 필요한가: 로봇 카메라 bring-up은 "센서는 I2C에 보이는데 /dev/video0에서 프레임이 안 나온다", "STREAMON이 Broken pipe", "가끔 프레임이 빠진다", "인코더로 넘길 때 CPU가 30% 먹는다"의 연속이고, 면접은 "새 MIPI 센서를 Linux에 올리는 순서를 말해 보라"를 묻는다 — 전부 이 노트의 내용이다 Don 기준 난이도: DMA 링, 디스크립터 소유권, 프레임 카운터, IRQ 타이밍, 레인/클럭 같은 PHY 개념은 SSD·RF bring-up에서 매일 하던 일이다 / 새로 배울 것은 V4L2가 그것을 모델링하는 객체 그래프(subdev·pad·link), 두 종류의 포맷(media bus code vs fourcc), videobuf2라는 버퍼 큐 프레임워크, 그리고 DT 그래프 + async 등록이라는 Linux식 "보드 배선 설명" 선행 노트: G4·G5(char device, ioctl·mmap), G6(poll), H5(I2C), H9(DMA API, dma-buf), F10(CMA, 카메라 버퍼), D2~D4(DT 문법·phandle), F8(hrtimer), I1(프레임워크 원칙) — Q1(MIPI CSI-2 HW), Q2(Linux 카메라 파이프라인 실무), Q3(멀티 카메라 동기화)로 이어진다

0. 큰 그림 — 이게 왜 필요한가#

예를 들어 센서 키트에 카메라가 4대 붙어 있다고 하자. 각 카메라 모듈은 이미지 센서(예: Sony IMX219) 하나다. 센서는 두 가닥의 선으로 SoC와 연결된다. 제어는 I2C(카메라 업계는 CCI — Camera Control Interface라고 부른다)로 레지스터를 쓰고, 픽셀 데이터는 MIPI CSI-2라는 고속 직렬 링크(데이터 lane 1~4개 + 클럭 lane, 물리층은 D-PHY)로 흘러간다. SoC 안에서는 CSI-2 수신기가 패킷을 풀고, ISP가 Bayer 원본을 debayer·화이트밸런스·노이즈 제거해서 YUV로 바꾸고, 스케일러가 크기를 줄이고, DMA writer가 DRAM 버퍼에 쓴다.

Don이 SSD 컨트롤러에서 본 구조와 똑같다. "호스트 인터페이스 → 데이터 경로 블록 여러 개 → DMA → 버퍼"다. 차이는 블록이 SoC 벤더마다 다르고, 블록 사이 연결을 소프트웨어가 바꿀 수 있다는 점이다. 그래서 Linux는 카메라 파이프라인을 "장치 하나"가 아니라 그래프로 모델링한다.

그림 1 — 위는 SoC 카메라 하드웨어, 아래는 그것을 Linux가 모델링한 media controller 그래프. 블록 하나가 커널 객체 하나(대개 v4l2_subdev)가 되고, 블록 사이의 배선은 pad와 link가 된다. 마지막 DMA 블록만 메모리 버퍼를 다루는 video_device(/dev/video0)다. entity 이름 옆의 CAM_SENSOR 등은 MEDIA_ENT_F_* function 값이다(가운데 두 개는 대표적인 예 — 실제 값은 드라이버마다 다르다).

이 노트에서 다룰 V4L2(Video4Linux2) 세계의 구성원을 먼저 표 하나로 정리한다.

  • i5_cam — §12에서 직접 쓰는 최소 캡처 드라이버.

1. 실습 환경 — Image-sub 커널과 BusyBox 게스트#

1.1 왜 QEMU 게스트인가#

Lima VM(elinux)의 호스트 커널은 7.0이고 vivid가 로드되어 있지 않다. 공용 VM에 커널 모듈을 넣는 것은 금지라서, 모든 실습은 공용 랩의 Image-sub 커널(6.18.55 LTS + 테스트 드라이버들을 모듈로 빌드한 것)을 QEMU로 부팅해서 한다. 게스트 rootfs는 BusyBox라 v4l2-ctl·media-ctl(v4l-utils 패키지)이 없다. 그래서 이 노트의 유저 공간 코드는 전부 V4L2·MC uAPI ioctl을 직접 부르는 정적 C 프로그램이다. 덕분에 도구가 숨기는 순서를 전부 손으로 보게 된다.

VM 호스트에 v4l-utils가 있는지 먼저 확인했다(설치는 하지 않는다).

출력에서 볼 것: which가 아무것도 찍지 않았다. 라이브러리(libv4l)만 있고 명령행 도구는 없다. 실무 보드에서는 보통 v4l-utils를 rootfs에 넣는다(Buildroot BR2_PACKAGE_LIBV4L_UTILS, Yocto v4l-utils 레시피). 이 노트의 C 프로그램이 하는 일을 v4l2-ctl/media-ctl로 하면 어떤 명령인지는 각 절에 "(기억 기반, 실행 안 함)"이라고 표시해서 적는다.

1.2 부팅 스크립트#

Lima VM 안에서 실행하는 스크립트다. 랩 rootfs를 한 번 복사해 media 관련 모듈(drivers/media/{test-drivers,v4l2-core,common,mc,cec/core})과 modules.dep을 /lib/modules/6.18.55-sub에 넣어 두면, 게스트에서 BusyBox modprobe vivid가 의존 모듈(videodev, mc, videobuf2-*, v4l2-tpg…)을 알아서 올린다.

유저 프로그램은 VM에서 gcc -static으로 빌드해 /var/tmp/I5/bin에 두고, 부팅 때 initramfs 루트(/)에 복사된다.

모든 예제의 공용 헤더다. xioctl()은 시그널로 끊긴 ioctl을 다시 부르는 V4L2 예제의 관례이고, fcc()는 32비트 fourcc를 YUYV 같은 네 글자로 바꾼다.

헤더는 VM 호스트(커널 7.0)의 /usr/include/linux/videodev2.h를 쓴다. uAPI는 하위 호환이 보장되므로 6.18 게스트에서 그대로 동작한다.

2. 객체 모델 — 누가 누구를 소유하나#

2.1 직관 — "SoC 블록마다 작은 드라이버, 그걸 묶는 브리지"#

bare-metal 펌웨어라면 카메라 경로 전체를 하나의 모듈이 초기화한다. Linux는 그렇게 못 한다. 센서는 I2C 버스에 붙은 별개의 장치(i2c_client)이고 센서 드라이버는 SoC와 무관하게 재사용되어야 한다(IMX219 드라이버는 Raspberry Pi, i.MX8MP, TI AM62, Renesas에서 똑같이 쓴다). CSI-2 수신기, ISP, DMA는 SoC 벤더의 플랫폼 장치다. 그래서 V4L2는 블록마다 subdev 드라이버를 따로 쓰고, "브리지" 드라이버가 그것들을 하나의 v4l2_device·media_device 아래로 모은다.

그림 2 — V4L2 객체 모델. 브리지 드라이버가 v4l2_device와 media_device를 하나씩 갖고, 센서·수신기 subdev와 video_device를 등록한다. 각 객체 안에는 media_entity가 박혀 있고 pad끼리 media_link로 이어진다. 유저 공간 노드는 entity에 interface link로 붙는다.

2.4 흔한 함정#

  • /dev/video0을 열면 카메라가 나온다고 가정한다 — MC 드라이버에서는 subdev 포맷과 링크를 먼저 맞추지 않으면 STREAMON이 -EPIPE다(§9).
  • subdev 노드가 안 생겨서 "드라이버가 안 붙었다"고 판단한다 — subdev 노드는 브리지가 v4l2_device_register_subdev_nodes()를 불러야 생긴다. 센서의 V4L2_SUBDEV_FL_HAS_DEVNODE 플래그도 필요하다.
  • capabilities와 device_caps를 혼동한다 — capabilities는 장치(드라이버) 전체의 합집합, device_caps는 지금 연 노드의 능력이다. 판단은 device_caps로 한다.

3. 첫 장치 열기 — QUERYCAP, ENUM_FMT, G_FMT, 그리고 두 종류의 포맷#

3.1 직관#

V4L2 장치를 처음 열면 하는 일은 SSD 펌웨어가 NVMe Identify를 처리하는 것과 비슷하다. "너는 누구고(QUERYCAP), 무슨 포맷을 지원하고(ENUM_FMT), 지금 설정은 무엇이냐(G_FMT)". 모든 V4L2 앱(GStreamer v4l2src, OpenCV, libcamera)의 첫 3개 ioctl이다.

무엇을 확인하는 코드인지: 노드 하나의 드라이버 이름, device_caps, 지원 pixel format 목록, 현재 포맷, 프레임 간격(G_PARM)을 출력한다.

(포맷 목록 83개 중 일부만 남기고 ...로 줄였다.) 출력에서 볼 것:

  • device_caps=0x05230001 — VIDEO_CAPTURE(0x1) + READWRITE(0x1000000) + STREAMING(0x4000000) 외에 EXT_PIX_FORMAT(0x200000) 등 내가 출력하지 않은 비트도 있다. vivid는 read()로도 프레임을 줄 수 있다(READWRITE). 실제 SoC 캡처 드라이버는 대개 STREAMING만 지원한다.
  • vivid 캡처가 지원하는 pixel format(fourcc)이 83개다. YUYV(4:2:2 packed), NV12(4:2:0 semi-planar — 카메라·코덱의 표준), RGB3(RGB24), RGGB(8비트 Bayer), RG10(10비트 Bayer, 16비트 컨테이너) 등. 실제 SoC는 DMA writer가 지원하는 몇 개뿐이다.
  • fmt[27] Y16 설명이 16-bit Greyscale BE — fourcc 최상위 비트(V4L2_PIX_FMT_BE, bit 31)가 빅엔디언 표시다. 그래서 fcc()에서 & 0x7f로 걸렀다.
  • 현재 포맷 320x240 YUYV bytesperline=640 sizeimage=153600 — bytesperline(stride)은 한 줄의 바이트 수다. 320 픽셀 × 2바이트 = 640. 하드웨어 DMA가 줄 끝을 64·128바이트로 정렬하면 bytesperline이 폭 × bpp보다 커진다. 앱은 반드시 이 값으로 줄을 넘겨야 한다.
  • timeperframe=1/5 — vivid의 웹캠 입력은 해상도별 프레임 간격 목록을 갖고 있고 지금 값은 5 fps다. §6에서 S_PARM으로 바꾼다.
  • 출력 장치(video1)는 VIDEO_OUTPUT이고, 이 vivid 출력 노드는 G_PARM에 -EINVAL을 돌려준다(출력 프레임 간격은 지원 안 함). 720x576 field=4는 PAL 인터레이스(V4L2_FIELD_INTERLACED)다.

3.3 fourcc vs media bus code — 이 노트에서 가장 중요한 구분#

pixel format (fourcc)media bus format (mbus code)
어디에 쓰나메모리 버퍼의 레이아웃 (video node)두 HW 블록 사이 배선 위의 데이터 (subdev pad)
구조체struct v4l2_pix_format (width, height, pixelformat, bytesperline, sizeimage)struct v4l2_mbus_framefmt (width, height, code, field, colorspace)
예V4L2_PIX_FMT_SRGGB10 = 'RG10': 10비트 Bayer를 16비트에 담아 메모리에MEDIA_BUS_FMT_SRGGB10_1X10 = 0x300f: 10비트 Bayer가 버스 한 클럭에 10비트씩
stride·padding있음없음 (버스엔 메모리가 없다)
설정 ioctlVIDIOC_S_FMT on /dev/videoNVIDIOC_SUBDEV_S_FMT on /dev/v4l-subdevN

같은 센서 데이터가 링크 위에서는 mbus code, 메모리에 내려앉으면 fourcc다. 그 사이 변환(예: 10비트 Bayer를 16비트로 펼치기, RAW10 packed로 저장하기, YUV 4:2:2를 NV12로 바꾸기)은 수신기·ISP·DMA writer가 한다. 그래서 MC 파이프라인의 끝 video node는 "어떤 mbus code에서 어떤 fourcc를 만들 수 있나"의 표를 갖고 있고, link_validate가 그 표로 짝을 검사한다(§9). Don에게 익숙한 비유로 하면 mbus code는 "PHY/링크 계층 프레이밍", fourcc는 "호스트 메모리 데이터 구조"다.

3.4 흔한 함정#

  • S_FMT의 반환값을 안 읽는다 — 드라이버는 지원 안 하는 값을 조용히 고쳐서 돌려준다(§12.4에서 i5_cam이 640x480 YUYV 요청을 320x240 GREY로 바꾼다). 에러가 아니다. 반드시 돌려받은 width·height·pixelformat·bytesperline으로 버퍼를 해석한다.
  • sizeimage를 width × height × bpp로 직접 계산한다 — stride 정렬, 평면 사이 패딩, 압축 포맷 때문에 다르다. 드라이버가 준 sizeimage를 쓴다.
  • 멀티플레인 포맷(NV12M처럼 Y와 UV가 다른 버퍼)을 쓰는 드라이버는 V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE과 struct v4l2_pix_format_mplane을 쓴다. vivid도 multiplanar=2 모듈 인자로 그 모드가 된다. 이 노트의 예제는 single-planar만 다룬다.

4. 컨트롤 프레임워크 — 노출, 게인, 테스트 패턴, 링크 주파수#

4.1 직관#

센서 레지스터 중 "앱이 런타임에 바꾸고 싶은 것"(노출 시간, 아날로그 게인, 플립, 테스트 패턴)은 V4L2 컨트롤로 노출된다. 펌웨어로 치면 "레지스터 맵 중 공개 API로 올린 필드"다. 드라이버는 v4l2_ctrl_handler에 컨트롤을 등록하고 s_ctrl 콜백 하나에서 레지스터를 쓴다. 범위 검사, 기본값, 메뉴 문자열, 이벤트 통지, 잠금, 여러 노드에서 상속은 프레임워크가 한다.

4.2 예제 2 — i5_ctrls: 컨트롤 열거와 설정#

무엇을 확인하는 코드인지: VIDIOC_QUERY_EXT_CTRL + V4L2_CTRL_FLAG_NEXT_CTRL로 모든 컨트롤을 차례로 열거하고, 이름에 "Pattern"이 든 메뉴는 VIDIOC_QUERYMENU로 항목을 출력한다. 인자로 0xID=값을 주면 S_CTRL로 설정한다.

(실행은 §3.2의 g_vivid1.sh 마지막 줄.)

(vivid 컨트롤 100여 개 중 일부만 남겼다.) 출력에서 볼 것:

  • 컨트롤은 클래스로 묶인다: [User Controls](V4L2_CID_USER_BASE 0x980900~), [Image Processing Controls](0x9f0900~, 여기에 TEST_PATTERN·LINK_FREQ·PIXEL_RATE가 있다), 드라이버 전용 범위(vivid는 0xf0f000~). §12의 i5_cam은 표준 V4L2_CID_TEST_PATTERN(0x009f0903)을 쓴다.
  • Gain의 기본값은 100인데 현재 값은 12다. 바로 위 Gain, Automatic=1이 켜져 있어서 vivid가 게인을 스스로 바꾸는 volatile 컨트롤이기 때문이다. 자동 노출/게인이 켜진 센서에서 G_CTRL이 매번 다른 값을 돌려주는 것과 같다.
  • Timestamp Source(vivid 전용) — 타임스탬프를 프레임 시작(SOE)으로 찍을지 끝(EOF)으로 찍을지. §6에서 이것 때문에 이상한 값을 보게 된다.
  • Percentage of Dropped Buffers, Inject ... Error 버튼 — vivid는 에러 주입 장치다. 앱의 에러 경로 테스트에 쓰인다.

4.4 흔한 함정#

  • 스트리밍 중에는 바꿀 수 없는 컨트롤이 있다 — imx219는 스트림을 켜면서 __v4l2_ctrl_grab(imx219->hflip, true)(vflip도)로 플립을 잠근다. 플립이 Bayer 순서, 즉 mbus code를 바꾸는데 스트리밍 중에는 파이프라인 포맷을 바꿀 수 없기 때문이다. 잠긴 컨트롤에 S_CTRL을 하면 -EBUSY다.
  • s_ctrl이 전원이 꺼진 센서에 I2C를 쓴다 — 실제 드라이버는 pm_runtime_get_if_in_use()로 전원이 켜져 있을 때만 쓰고, 꺼져 있으면 값만 저장했다가 스트림 시작 때 __v4l2_ctrl_handler_setup()으로 한꺼번에 쓴다(imx219의 enable_streams 코드가 그렇다, §11.3).
  • 컨트롤 ID를 하드코딩한다 — 드라이버 전용 ID는 커널 버전마다 바뀔 수 있다. 이름이나 표준 CID로 찾는다.

5. 스트리밍 — videobuf2와 MMAP 캡처#

5.1 직관 — SSD의 디스크립터 링과 똑같다#

Don이 NVMe에서 본 SQ/CQ를 떠올리자. 호스트가 "이 버퍼에 써 줘"를 SQ에 넣고(doorbell), 컨트롤러가 다 쓰면 CQ에 완료를 올린다. V4L2 스트리밍이 정확히 그 구조다.

  • VIDIOC_REQBUFS — 버퍼 N개를 커널이 할당한다 (링 크기 결정).
  • VIDIOC_QBUF — "이 빈 버퍼에 다음 프레임을 써 줘" (SQ에 넣기).
  • VIDIOC_STREAMON — 엔진 시작 (doorbell + enable).
  • 프레임 끝 인터럽트 → 드라이버가 vb2_buffer_done() (CQ에 완료 기록).
  • VIDIOC_DQBUF — 다 찬 버퍼 하나를 받는다 (CQ 소비). poll()로 기다릴 수 있다.
  • 처리 후 다시 QBUF — 버퍼 재활용.

이 링을 모든 드라이버가 따로 짜면 버그가 나니까, 커널은 videobuf2(vb2)라는 공용 큐 구현을 둔다. 드라이버는 vb2_ops 콜백 5개 정도만 채우고, ioctl 처리·mmap·dma-buf·poll·상태 관리는 vb2가 한다.

5.2 예제 3 — i5_cap: MMAP 스트리밍 캡처 (이 노트의 주력 프로그램)#

무엇을 확인하는 코드인지: 포맷 설정 → REQBUFS(MMAP) → QUERYBUF + mmap → QBUF 전부 → STREAMON → N번 DQBUF/QBUF → STREAMOFF. 매 프레임의 sequence와 timestamp로 프레임 간격, 손실(sequence 틈), fps를 계산하고, 첫 프레임을 파일로 저장할 수 있다. 느린 소비자를 흉내 내는 sleep 옵션이 있다(§7).

이 프로그램이 지키는 규칙 세 가지가 V4L2 앱의 기본이다.

  1. mmap은 QUERYBUF가 준 m.offset으로 한다. 이 값은 진짜 파일 오프셋이 아니라 "버퍼 번호를 인코딩한 쿠키"다(§5.4 출력에서 버퍼 1의 offset이 0x8000인 것을 보라). 드라이버의 .mmap(= vb2_fop_mmap)이 이 쿠키로 버퍼를 찾는다. G5에서 직접 짠 .mmap의 vb2판이다.
  2. DQBUF로 받은 버퍼만 읽고, QBUF한 버퍼는 건드리지 않는다. QBUF 이후 그 메모리는 DMA가 쓰고 있다.
  3. sequence를 믿고 timestamp로 간격을 잰다. 앱이 DQBUF한 시각(now_s())이 아니라 드라이버가 기록한 timestamp가 프레임의 시각이다.

5.3 예제 4 — vivid 컬러바를 캡처해서 바이트로 검증#

무엇을 확인하는 코드인지: 테스트 패턴을 "100% Colorbar"로, OSD 글자를 끄고, 640x480 RGB24로 30장 캡처한 뒤 첫 프레임의 240번째 줄에서 8개 막대의 가운데 픽셀 값을 od로 읽는다. bring-up 때 센서 테스트 패턴으로 "레인 순서·Bayer 순서·바이트 순서가 맞나"를 확인하는 것과 같은 절차다.

출력에서 볼 것:

  • 8개 막대가 흰 · 노 · 청록 · 초 · 자홍 · 빨 · 파 · 검 순서이고 값이 정확히 255/0이다. SMPTE 컬러바 순서 그대로다. 만약 R과 B가 바뀌어 나오면(0 255 255가 노랑 자리에) 포맷을 RGB3가 아니라 BGR3로 해석하고 있는 것이다. Bayer 센서라면 SRGGB와 SBGGR를 혼동하면 같은 증상이 난다.
  • flags=0x2001 — V4L2_BUF_FLAG_MAPPED(0x1) + V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC(0x2000). 타임스탬프가 CLOCK_MONOTONIC 기준이라는 표시다(§6).
  • 이 해상도에서 vivid 기본 프레임 간격이 1/5초라 30장에 6초가 걸렸다. dt_ms min=197 max=204 — QEMU TCG 위라 ±3 ms 흔들린다.
  • 파일 크기 921600 = 640 × 480 × 3. stride 1920에 패딩이 없다.

v4l2-ctl로는 대략 이렇게 한다(기억 기반, 이 VM에서 실행 안 함): v4l2-ctl -d /dev/video0 --set-ctrl test_pattern=1 --set-fmt-video=width=640,height=480,pixelformat=RGB3 --stream-mmap --stream-count=30 --stream-to=f.rgb.

5.4 예제 5 — vb2 디버그 로그로 버퍼 상태 기계 보기#

vb2는 모듈 인자 debug로 상태 전이를 로그로 남긴다. video 노드의 dev_debug sysfs 파일은 ioctl 이름을 찍는다. §12에서 만드는 i5_cam 드라이버(10 fps)로 버퍼 2개, 3프레임만 돌린다.

출력에서 볼 것 (그림 3과 한 줄씩 맞춰 보라):

  • REQBUFS 안에서 __vb2_queue_alloc: allocated 2 buffers와 버퍼별 mmap offset 쿠키(0, 0x8000)가 정해진다.
  • STREAMON 전의 QBUF는 vb2 큐에만 들어간다(QUEUED). vb2_core_streamon: successful 순간 vb2가 쌓인 버퍼를 드라이버의 buf_queue로 넘기고 start_streaming을 부른다.
  • DQBUF가 먼저 와서 will sleep waiting for buffers — 앱이 잠든다. 100 ms 뒤 드라이버(타이머 = 가짜 프레임 끝 IRQ)가 vb2_buffer_done ... state: done을 부르면 깨어나서 dqbuf of buffer 0, state: dequeued.
  • STREAMOFF 때 드라이버에 남아 있던 버퍼 두 개가 state: error로 돌려받아진다. stop_streaming은 갖고 있던 모든 버퍼를 반드시 돌려줘야 한다 — 안 돌려주면 vb2가 WARN을 찍는다.

그림 3 — vb2 버퍼 상태 기계와 소유권. 초록(DEQUEUED)일 때만 앱이 버퍼 내용을 읽을 수 있고, 파랑(ACTIVE)일 때는 DMA가 쓰는 중이다. Don의 SSD 펌웨어로 치면 "호스트 소유 / 큐 대기 / 컨트롤러 소유 / 완료 대기" 네 상태의 디스크립터와 같다.

5.6 흔한 함정#

  • QBUF한 버퍼를 앱이 계속 읽는다 — 다음 프레임이 반쯤 덮인 "찢어진 프레임"이 나온다. 처리 중인 버퍼는 QBUF하지 말고 처리가 끝난 뒤 돌려준다.
  • 버퍼를 2개만 요청한다 — 드라이버가 하나에 쓰는 동안 앱이 하나를 들고 있으면 드라이버는 다음 프레임에 쓸 곳이 없다. 실무 기본은 4~8개(§7 측정).
  • REQBUFS의 count 반환값을 안 본다 — 드라이버가 최소 개수(min_reqbufs_allocation)로 올리거나 메모리 부족으로 줄일 수 있다.
  • STREAMOFF 후 mmap을 풀지 않고 REQBUFS count=0을 부른다 — 매핑이 남아 있으면 -EBUSY다. munmap 먼저.

6.1 정의#

struct v4l2_buffer가 DQBUF로 돌아올 때 채워지는 시간 정보:

필드의미

  • timestamp를 TIMESTAMP_COPY 큐(m2m 장치)에서 해석한다 — m2m은 OUTPUT 버퍼의 타임스탬프를 CAPTURE로 복사할 뿐 실제 시각이 아니다.

7. 드롭 프레임 — sequence 틈으로 잡는다#

7.1 직관#

카메라는 기다려 주지 않는다. 센서는 33.3 ms마다 프레임을 밀어내고, 그 순간 드라이버에게 빈 버퍼(QUEUED → ACTIVE로 갈 버퍼)가 없으면 그 프레임은 버려진다. 드라이버가 할 일은 하나뿐이다: sequence를 그래도 증가시켜서 앱이 알게 하는 것. 앱이 할 일은 b.sequence - prev - 1을 세는 것이다. Don이 SSD에서 CQ가 꽉 차서 완료를 못 올리는 상황을 phase bit로 감지했던 것과 같은 성격의 장치다.

8. DMABUF — 카메라 버퍼를 인코더·GPU에 복사 없이 넘기기#

8.1 직관#

로봇의 카메라 프레임은 보통 한 곳에서 끝나지 않는다. H.264 인코더(원격 영상), GPU/NPU(인식), 디스플레이(디버그 화면)로 동시에 간다. 프레임마다 CPU가 memcpy하면 1080p NV12 3 MiB × 30 fps × 4대 = 약 360 MiB/s를 CPU가 읽고 쓴다. 임베디드 SoC의 메모리 대역폭과 전력에 치명적이다. 해결은 H9 §11에서 본 dma-buf다. 버퍼를 "fd로 표현되는 공유 객체"로 만들어 다른 장치 드라이버가 같은 물리 페이지를 DMA로 읽게 한다.

그림 7 — (가) MMAP으로 받아 CPU가 복사하는 경로, (나) VIDIOC_EXPBUF로 dma-buf fd를 만들어 다른 장치의 큐에 V4L2_MEMORY_DMABUF로 넣는 zero-copy 경로. 앱은 픽셀을 만지지 않고 fd(정수)만 옮긴다.

그림 8 — 위 출력을 그린 vimc 그래프(§9.2에서 고친 뒤의 포맷 표시). 굵은 선은 켜진 링크, 점선은 꺼진 링크다. Scaler의 sink pad 하나에 세 소스가 연결되어 있지만 동시에 하나만 켤 수 있다 — 실제 SoC에서 "CSI-2 수신기 0번과 1번 중 어느 것을 ISP에 물릴지"를 고르는 mux와 같다.

9.2 예제 13 — subdev 포맷 맞추기, 링크 바꾸기, 그리고 -EPIPE#

subdev 포맷 도구와 링크 도구:

무엇을 확인하는 스크립트인지: (1) 기본 상태에서 최종 캡처 노드를 스트리밍 → 실패 원인 추적, (2)(3) 포맷을 하나씩 고쳐서 성공, (4) 스케일러 출력을 바꿔 다시 불일치 만들기, (5) 링크 조작, (6) 스트리밍 중 포맷 변경. 커널 쪽 이유를 보려고 v4l2-subdev.c와 mc-entity.c의 dev_dbg를 dynamic debug로 켰다.

출력에서 볼 것 — 단계별로:

  1. 기본 상태: Sensor A는 RGB888_1X24(0x100a)를 내보내는데 Debayer A의 sink는 SRGGB8_1X8(0x3014, Bayer)을 기대한다. STREAMON이 -EPIPE(errno 32, Broken pipe)이고 dmesg가 정확히 어느 링크의 무엇이 다른지 말해 준다: media bus code does not match (source 0x0000100a, sink 0x00003014). 이 dev_dbg 두 줄이 실무에서 가장 값진 디버그 정보다.
  2. 센서를 Bayer로 맞췄는데 또 -EPIPE. 이번에는 'Sensor A':0 -> 'Raw Capture 0':0 링크다. 우리는 RGB/YUV Capture만 스트리밍하려 했지만 video_device_pipeline_start()는 켜진 링크로 연결된 모든 pad를 파이프라인에 넣는다(media pipeline populated, found pads 로그로 확인했다). Raw Capture 0은 IMMUTABLE 링크로 Sensor A에 붙어 있으니 파이프라인에 들어오고, 그 video 노드의 포맷(기본 RGB3)이 센서의 Bayer와 안 맞는다. "쓰지도 않는 노드 때문에 실패"는 실제 SoC(센서 하나에 raw 출력과 ISP 출력이 같이 달린 구조)에서도 자주 만나는 함정이다.
  3. Raw Capture 0을 RGGB로 맞추자 성공. 첫 바이트 bf = 191 = 75% 흰색(vimc 센서 기본 패턴이 75% 컬러바). 이 체인은 vimc가 CPU로 debayer·스케일을 계산하므로 TCG 위에서 7 fps 정도밖에 안 나온다(실제 HW에서는 ISP가 한다).
  4. Scaler source pad만 1280x720으로 바꾸자 Scaler → 캡처 링크 검증이 실패했다. 이번에는 vimc 캡처의 자체 link_validate(vimc_vdev_link_validate)가 찍은 로그에 양쪽 크기가 나온다. 캡처 노드도 1280x720으로 S_FMT하자 성공(2764800 = 1280×720×3). 스케일러는 sink와 source 크기가 다를 수 있는 유일한 블록이고, 그 비율이 곧 스케일 배율이다.
  5. Sensor A → Debayer A는 IMMUTABLE이라 SETUP_LINK가 -EINVAL. Debayer A → Scaler를 끄고 Debayer B → Scaler를 켜는 것은 된다 — mux 전환.
  6. 스트리밍 중에 Scaler 포맷을 바꾸려 하자 -EBUSY. vimc 스케일러의 set_fmt가 which == ACTIVE이고 스트리밍 중이면 거절한다(vimc-scaler.c). TRY 포맷(V4L2_SUBDEV_FORMAT_TRY)은 언제든 시험할 수 있다.

media-ctl로는 대략 이렇게 한다(기억 기반, 실행 안 함):

9.3 link validation은 누가 하나#

video_device_pipeline_start() → __media_pipeline_start()가 그래프를 걷으며 파이프라인의 각 sink pad에 대해, 그 pad를 가진 entity의 media_entity_operations.link_validate를 부른다.

  • sink가 subdev면 보통 v4l2_subdev_link_validate() → 드라이버의 pad op link_validate가 있으면 그것, 없으면 v4l2_subdev_link_validate_default(): width, height, mbus code가 같아야 하고 field는 같거나 sink가 NONE이어야 한다(위 소스 확인).

10. 포맷 협상 — 파이프라인 전체에서 포맷을 맞추는 순서#

10.1 규칙#

  1. 센서 쪽(상류)부터 하류로 설정한다. 각 subdev는 sink pad 포맷을 받으면 자기 source pad 포맷을 전파(propagate)해서 기본값으로 채운다. vimc 스케일러 코드에서 sink를 설정하면 crop과 source가 같이 바뀌는 것을 봤다(vimc_scaler_set_fmt, §9의 4단계 전에 확인한 소스). 그래서 하류부터 맞추면 상류를 바꾸는 순간 하류가 덮인다.
  2. 각 링크의 source pad 포맷을 읽어 그대로 다음 sink pad에 설정한다. 크기를 바꿀 수 있는 곳은 crop(VIDIOC_SUBDEV_S_SELECTION)과 scaler뿐이다.
  3. 마지막 subdev의 source mbus code에 맞는 fourcc를 video node에 S_FMT한다. VIDIOC_ENUM_FMT에 mbus_code 필드를 넣으면(V4L2_CAP_IO_MC 드라이버) "이 mbus code에서 만들 수 있는 fourcc"만 열거된다.
  4. 드라이버가 고쳐서 돌려준 값을 다음 단계 입력으로 쓴다. 센서가 지원하지 않는 크기를 요청하면 가장 가까운 모드로 바꿔 돌려준다.
  5. 파이프라인이 다 맞으면 STREAMON. 스트리밍 중에는 ACTIVE 포맷을 못 바꾼다(-EBUSY).

10.2 TRY와 ACTIVE#

subdev 포맷에는 두 벌이 있다. which = V4L2_SUBDEV_FORMAT_ACTIVE는 하드웨어에 실제로 적용될 값(드라이버의 active state), V4L2_SUBDEV_FORMAT_TRY는 파일 핸들마다 따로 있는 연습용 state다. libcamera 같은 상위 계층이 "이 조합이 되나"를 하드웨어를 건드리지 않고 시험할 때 쓴다. 6.x state API에서는 둘 다 struct v4l2_subdev_state이고, 드라이버의 set_fmt는 받은 state가 어느 것이든 같은 코드로 처리한다(그래서 imx219의 init_state가 which = TRY인 포맷 구조체로 imx219_set_pad_format을 부른다).

10.3 실제 예 — IMX219 → i.MX8MP CSI-2 → ISI (기억 기반, 실행 안 함)#

entity 이름(imx219 3-0010 = "드라이버명 I2C버스-주소", csis-<장치명>, crossbar, mxc_isi.N은 랩 소스의 이름 규칙으로 확인)과 pad 번호는 보드·커널 버전에 따라 다르다. 반드시 media-ctl -p로 확인한 이름을 쓴다. ISI는 Bayer를 처리하지 못하므로 raw로 받고 debayer는 GPU/소프트웨어가 하거나, i.MX8MP의 ISP(RKISP1 계열 드라이버)를 거친다.

10.4 흔한 함정#

  • 센서 포맷만 바꾸고 수신기 sink는 그대로 둔다 — STREAMON -EPIPE. MC 파이프라인은 자동 전파가 subdev 안에서만(sink → source) 일어나고 링크를 건너서는 일어나지 않는다.
  • Bayer 순서를 무시하고 크기만 맞춘다 — SRGGB10과 SGRBG10은 다른 mbus code다. 센서의 플립이나 crop 시작 위치(홀수 픽셀)를 바꾸면 Bayer 순서가 바뀐다.
  • colorspace를 신경 안 쓴다 — 대부분 DEFAULT면 통과하지만, vimc처럼 colorimetry까지 비교하는 드라이버가 있다(§9.2 2단계에서 센서 colorspace가 0으로 바뀐 것을 보라 — 센서 set_fmt가 요청의 colorspace 0을 그대로 받았다).

11. Device Tree와 async 등록 — 보드 배선이 그래프가 되기까지#

11.1 직관 — "누가 누구에게 몇 lane으로 붙었나"를 적는 곳#

센서 드라이버는 I2C 버스 드라이버가 probe하고, CSI-2 수신기 드라이버는 플랫폼 버스가 probe한다. 둘의 probe 순서는 정해져 있지 않다(센서는 regulator·clock이 준비 안 돼서 -EPROBE_DEFER로 몇 번 미뤄질 수도 있다). 그런데 수신기는 "내 0번 포트에 IMX219가 2 lane, 456 MHz로 붙어 있다"를 알아야 D-PHY를 설정한다. 이 배선 정보가 DT의 OF graph(port/endpoint/remote-endpoint)이고, 서로 늦게 오는 드라이버를 짝지어 주는 것이 v4l2-async다. Don이 보드 bring-up에서 회로도의 "CAM0_D0_P/N → SoC MIPI_CSI1_D0"를 읽던 일을 DT가 대신 기록한다.

11.2 실제 DT — Gateworks GW74xx 보드의 IMX219 overlay (랩 소스)#

랩 트리 arch/arm64/boot/dts/freescale/imx8mp-venice-gw74xx-imx219.dtso의 핵심 부분이다(레귤레이터·핀 설정 생략).

mipi_csi_0(CSI-2 수신기)과 isi_0(Image Sensing Interface — 스케일러·색변환·DMA writer)의 SoC 노드는 imx8mp.dtsi에 status = "disabled"로 이미 있고, 그 안에 mipi_csi_0_out ↔ isi_in_0 연결도 이미 적혀 있다. 보드 overlay는 센서를 붙이고 port@0의 endpoint만 채운 뒤 켠다.

그림 9 — 위 DT의 그래프. 노드마다 port(물리 단자)가 있고 그 안의 endpoint가 상대 endpoint를 remote-endpoint로 서로 가리킨다. 레인 수와 링크 주파수는 endpoint 속성이다.

11.3 커널 코드 — 센서 쪽 (imx219.c, 랩 소스 발췌)#

probe에서 endpoint를 파싱하고 lane 수와 링크 주파수를 검사한다.

probe의 뒷부분은 V4L2 subdev 등록의 교과서 순서다(발췌).

subdev ops 표는 6.x 스타일이다. 스트림 시작은 enable_streams가 하고 옛 s_stream은 공용 헬퍼로 연결한다.

imx219_enable_streams()는 pm_runtime_resume_and_get()(전원 켜기) → 공통 레지스터 표 쓰기(cci_multi_reg_write) → lane 설정 → 포맷·crop 적용 → __v4l2_ctrl_handler_setup()(저장해 둔 컨트롤 값 일괄 쓰기) → MODE_SELECT=streaming 순서다. Don의 bring-up 감각으로 말하면 "전원 시퀀스 → 레지스터 초기화 표 → 모드 표 → 사용자 설정 → 스트림 enable"이다.

11.4 커널 코드 — 수신기 쪽 (imx-mipi-csis.c, 랩 소스 발췌)#

.bound 콜백(mipi_csis_notify_bound)은 v4l2_create_fwnode_links_to_pad(sd, sink, 0)로 센서 pad → 수신기 sink pad 링크를 만든다. 수신기 자신도 subdev라서 마지막 줄에서 자기를 async로 등록한다 — 그러면 ISI(브리지) 드라이버의 notifier가 수신기를 기다렸다가 bound한다. 이렇게 notifier가 사슬처럼 이어지고, 맨 위(ISI)의 notifier가 .complete를 받을 때 v4l2_device_register_subdev_nodes()가 불려 /dev/v4l-subdevN이 한꺼번에 생긴다.

그림 10 — v4l2-async 등록 순서. 수신기가 먼저 와서 기다리든, 센서가 먼저 와서 기다리든 결과는 같다. 하나라도 안 오면(센서 I2C 응답 없음, regulator 누락, DT status 꺼짐) complete가 안 불리고 subdev 노드도 video 노드 사용도 불가능하다. 디버그 출발점은 /sys/kernel/debug/v4l2-async/pending_async_subdevices(랩 소스 v4l2-async.c에서 이름 확인 — 실제 보드가 없어 내용은 보지 못했다)와 dmesg | grep -i defer다.

11.5 예제 14 — dtc로 그래프 검증하기#

무엇을 확인하는 코드인지: 위 구조를 독립 DTS로 옮겨(include 없이) VM 호스트의 dtc로 컴파일하고, fdtget으로 endpoint 속성을 읽는다. 그리고 remote-endpoint 하나를 일부러 엉뚱한 곳으로 바꿔 dtc의 graph 검사가 잡는지 본다.

나쁜 버전은 csi_in의 remote-endpoint만 <&isi_in>으로 바꾼 것이다.

출력에서 볼 것:

  • link-frequencies는 /bits/ 64라서 셀 두 개(0, 0x1b2e0200)로 저장된다. 0x1b2e0200 = 456,000,000. 커널은 v4l2_fwnode_endpoint_alloc_parse()가 이것을 u64 배열로 읽는다.

  • 나쁜 DT는 경고일 뿐 컴파일은 성공(exit=0)한다. 부팅하면 async가 짝을 못 찾아 카메라가 조용히 안 나온다. 그래서 DT 리뷰 때 dtc·make dtbs_check 경고를 0으로 유지하는 것이 중요하다.

11.6 흔한 함정#

  • data-lanes를 센서와 수신기에 다르게 적는다 — 어떤 수신기는 자기 쪽 값을, 어떤 센서는 자기 쪽 값을 쓴다. 양쪽을 같게 맞춘다.
  • link-frequencies를 회로도의 "MIPI 클럭"으로 적는다 — DDR이라 비트레이트의 절반이 링크 주파수다. IMX219 456 MHz = lane당 912 Mbps.
  • 센서 노드의 status나 overlay 적용을 잊는다 — 수신기는 probe되고 영원히 기다린다. 에러 메시지가 없는 것이 증상이다.
  • 센서 전원 순서(VANA/VDIG/VDDL, XCLR 리셋 타이밍)를 데이터시트대로 안 지킨다 — 칩 ID 읽기(imx219_identify_module)에서 I2C NACK. H3(clk·regulator)·H4(GPIO) 노트의 영역이다.

14. 커널 안에서는 무슨 일이 일어나나#

유저의 ioctl 하나가 드라이버 콜백까지 가는 길을 한 장으로 정리한다(함수 이름은 랩 소스 6.18.55에서 확인).

그림 11 — V4L2 ioctl에서 드라이버 콜백까지. video_ioctl2()가 G5의 unlocked_ioctl이고, v4l2_ioctls[] 표가 ioctl 번호별로 인자 크기 검사·복사(copy_from_user/copy_to_user)와 잠금을 한 뒤 v4l2_ioctl_ops의 해당 함수를 부른다.

드라이버를 쓸 때 다시 만나는 지점을 모듈 ID로 연결하면:

  • video_ioctl2 → G5의 ioctl 설계(방향 비트, _IOWR, -ENOTTY). V4L2는 그것을 표 하나로 일반화한 것이다.
  • vb2_fop_mmap → G5의 .mmap. vb2_vmalloc은 remap_vmalloc_range(), vb2_dma_contig는 dma_mmap_attrs()로 PTE를 채운다(H9).
  • vb2_fop_poll → G6의 .poll + poll_wait(&q->done_wq). DQBUF가 잠드는 __vb2_wait_for_done_vb도 같은 wait queue(F3).
  • vb2_buffer_done() → 인터럽트 컨텍스트에서 불러도 된다(스핀락만 쓴다). F6의 top half에서 곧바로 부르는 이유.
  • vb2_dma_contig 할당 → dma_alloc_attrs() → CMA(F10 §8.2). REQBUFS가 곧 "CMA에서 N × sizeimage 할당"이다.
  • EXPBUF/DMABUF import → H9 §11의 dma_buf_export()/dma_buf_attach()/dma_buf_map_attachment().
  • 센서 subdev → H5의 i2c_driver + (최신 센서 드라이버는) v4l2-cci(cci_write(), regmap 기반, H2).
  • async notifier → G3의 probe 순서·-EPROBE_DEFER, D4의 phandle 그래프.
  • subdev state 잠금(sd->state_lock, v4l2_subdev_lock_and_get_active_state()) → F4의 뮤텍스. 컨트롤 핸들러 잠금과 같은 뮤텍스를 쓰게 하는 관례(imx219의 state_lock = ctrl_handler.lock)가 있다.

15.1 "새 MIPI 센서를 보드에 올린다" — 순서#

  1. HW 확인: 회로도에서 lane 수·lane 매핑·클럭 소스(24 MHz XCLK)·전원 레일·리셋/파워다운 GPIO·I2C 버스와 주소. 커넥터·FPC 방향.
  2. I2C로 칩 ID: 전원 시퀀스를 맞춘 뒤 i2ctransfer -y 3 w2@0x10 0x00 0x00 r2(IMX219 칩 ID 레지스터 0x0000, 기억 기반) 같은 명령으로 응답 확인. 여기서 NACK면 전원·리셋·클럭 문제다.
  3. 드라이버 선택: 메인라인에 있으면(drivers/media/i2c/) 그것, 없으면 벤더 드라이버를 6.x API(state, enable_streams, v4l2-cci)로 포팅.
  4. DT: 센서 노드(compatible, reg, clocks, supplies, GPIO) + endpoint(data-lanes, link-frequencies) + 수신기 port@0 endpoint, 양방향 remote-endpoint. dtbs_check 경고 0.
  5. 부팅 확인: dmesg에 probe 메시지, media-ctl -p에 센서 entity와 링크, /dev/v4l-subdevN 등장. 안 보이면 async pending과 -EPROBE_DEFER.
  6. 포맷 맞추고 스트리밍: media-ctl -V로 파이프라인 전체, v4l2-ctl --stream-mmap. -EPIPE면 §9.3 방식으로 링크별 비교.
  7. 테스트 패턴 먼저: 센서 V4L2_CID_TEST_PATTERN으로 컬러바를 받아 바이트 검증(§5.3). 패턴이 깨지면 lane·링크 주파수·Bayer 순서·수신기 D-PHY 설정(HS settle) 문제, 패턴은 되는데 실영상만 이상하면 노출·ISP 튜닝 문제로 나뉜다.
  8. 수신기 에러 카운터: CSI-2 ECC·CRC 에러, FIFO overflow 인터럽트 수를 본다(드라이버의 log_status나 debugfs). 링크 마진은 여기서 드러난다.
  9. 성능: fps·타임스탬프 간격·sequence 틈을 장시간 측정(§6·§7 프로그램을 그대로). 4대 동시일 때 메모리 대역폭과 CMA 크기.
  10. 상위 스택 연결: libcamera pipeline handler·IPA 튜닝, 또는 GStreamer/ROS 2 노드.

15.2 4대 카메라에서 프레임이 가끔 빠진다#

  • 먼저 어디서 빠지는지 나눈다. 앱이 본 sequence 틈(소비자가 늦음) vs 드라이버 에러 카운터(수신기 overflow, CSI CRC) vs 센서 자체(프레임 카운터가 임베디드 데이터에 있으면 그것).
  • 소비자 문제면 §7처럼 버퍼 수·소비 스레드 우선순위(SCHED_FIFO, N1)·복사 제거(DMABUF, §8)로 해결.
  • 수신기 overflow면 메모리 대역폭(다른 DMA 마스터와 경합 — QoS·interconnect 설정), CPU 개입 없는 ping-pong 버퍼 설계를 본다.

15.3 센서 퓨전 타임스탬프#

IMU(IIO, I2)는 샘플 시각을 CLOCK_MONOTONIC(또는 boottime)으로, 카메라는 V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC으로 준다. 같은 시간축이니 바로 정렬할 수 있다. 다만 카메라 타임스탬프는 어느 시점인지(SOE/EOF, 노출 중심이 아니다)를 알아야 한다. 롤링 셔터 센서에서 "노출 중심 시각 = SOE − (노출 시간 / 2) + (줄 번호 × 라인 시간)" 같은 보정을 하려면 드라이버의 타임스탬프 정의가 정확해야 한다. 멀티 카메라 HW 트리거·PTP는 Q3에서 다룬다.

17. 면접에서 이렇게 말한다#

Q. You need to bring up a new MIPI CSI-2 camera sensor on an embedded Linux board. Walk me through the steps.

A. 하드웨어부터 아래에서 위로 간다. 회로도로 레인·클럭·전원·리셋·I2C 주소를 확인하고, 전원 시퀀스를 맞춰 I2C로 칩 ID를 읽는다. 드라이버는 메인라인 subdev 드라이버를 쓰거나 6.x API로 포팅하고, DT에 센서 노드와 endpoint(data-lanes, link-frequencies, 양방향 remote-endpoint)를 쓴다. 부팅 후 media-ctl -p로 그래프에 센서가 붙었는지 보고, 파이프라인 포맷을 맞춘 뒤 센서 테스트 패턴으로 바이트 단위 검증을 한다. 그다음 실영상, 수신기 에러 카운터, fps·타임스탬프·드롭 장시간 측정, 마지막으로 libcamera나 GStreamer 연동이다.

I go bottom-up. First the hardware: lanes, lane mapping, the 24 MHz clock, power rails and their sequence, reset GPIO, and the I2C address, then I read the chip ID over I2C to prove power and clocks. Then the driver: a mainline V4L2 subdev driver if one exists, otherwise I port the vendor one to the current subdev state and enable_streams APIs. In the device tree I add the sensor node and the endpoint with data-lanes and link-frequencies, and a bidirectional remote-endpoint to the CSI-2 receiver port, and keep dtbs_check clean. After boot I check media-ctl -p for the sensor entity and links; if it's missing I look at v4l2-async pending subdevices and probe deferral. Then I configure formats along the pipeline from the sensor downstream, stream the sensor's test pattern and verify the bytes, which isolates lane and Bayer-order problems from image-quality problems. Finally I run long captures measuring frame intervals, sequence gaps and receiver error counters, and hand it to libcamera or GStreamer.

꼬리 질문: "테스트 패턴은 정상인데 실영상만 녹색 기운이 돈다면?" → Bayer 순서나 플립 후 mbus code, 또는 ISP 화이트밸런스·튜닝 문제. 링크는 정상이다.

Q. What is the difference between a video node and a subdev node, and why does a modern SoC camera have both?

A. video node(/dev/videoN)는 메모리 버퍼를 다루는 DMA 끝단이고 vb2 큐와 pixel format(fourcc)을 가진다. subdev node(/dev/v4l-subdevN)는 센서·수신기·ISP 같은 처리 블록이고 pad별 media bus 포맷과 컨트롤을 가진다. SoC 파이프라인은 조합이 많아서 드라이버가 혼자 결정할 수 없으니, media controller로 그래프를 노출하고 유저가 블록마다 포맷을 정하게 한다.

A video node is the DMA endpoint: it owns a videobuf2 queue and a memory pixel format with stride. A subdev node represents a processing block, a sensor, CSI-2 receiver, ISP or scaler, with per-pad media bus formats and its own controls. On a complex SoC the routing and per-block formats have too many valid combinations for the driver to pick, so the media controller exposes the graph and user space, or libcamera, configures each block and enables links. Link validation at stream-on checks that both ends of every enabled link agree.

Q. STREAMON returns EPIPE. How do you debug it?

A. EPIPE는 link validation 실패다. 켜진 링크의 양끝 포맷(크기, mbus code, field)이 다른 곳을 찾는다. media-ctl -p로 pad 포맷을 나란히 비교하고, dynamic debug로 v4l2-subdev.c와 mc-entity.c를 켜면 어느 링크가 어떤 값으로 실패했는지 그대로 나온다. 내가 vimc로 재현했을 때 두 번째 원인은 내가 스트리밍하지 않는 raw 캡처 노드였다 — 같은 센서에 켜진 링크로 붙어 있어서 파이프라인에 포함됐다.

EPIPE from STREAMON means link validation failed somewhere in the pipeline. I compare pad formats with media-ctl -p and enable dynamic debug for v4l2-subdev.c and mc-entity.c, which logs the exact link and the mismatching width, height or media bus code. One gotcha I reproduced on vimc: after fixing the sensor-to-debayer link it still failed, because a raw capture node I wasn't using was attached to the same sensor pad through an enabled immutable link, so it was part of the pipeline and its pixel format didn't match the sensor's Bayer code.

Q. Explain the videobuf2 buffer lifecycle and who owns the buffer in each state.

A. REQBUFS로 할당된 버퍼는 DEQUEUED(유저 소유)다. QBUF하면 QUEUED(vb2 소유), 스트리밍 중이면 드라이버의 buf_queue로 넘어가 ACTIVE(드라이버·DMA 소유), 프레임 끝 IRQ에서 vb2_buffer_done으로 DONE, DQBUF로 다시 유저에게 온다. STREAMOFF 때 드라이버는 갖고 있던 버퍼를 ERROR로 전부 돌려줘야 한다. SSD의 디스크립터 링 소유권과 같은 개념이다.

After REQBUFS a buffer is dequeued and belongs to user space. QBUF moves it to queued, owned by vb2; once streaming, vb2 hands it to the driver's buf_queue and it becomes active, owned by the driver and the DMA engine. The frame-end interrupt calls vb2_buffer_done, which puts it on the done list with timestamp and sequence filled in, and DQBUF returns it to user space. On stop_streaming the driver must return every buffer it holds in the error state. User space may only touch the memory between DQBUF and the next QBUF. It's the same ownership model as an NVMe submission and completion ring.

Q. How do you detect dropped frames, and how many buffers do you allocate?

A. sequence 필드의 틈을 센다. 드라이버는 빈 버퍼가 없어 프레임을 버려도 sequence를 올려야 한다. 버퍼 수는 평균 속도가 아니라 소비자의 최악 멈춤으로 정한다. 내 측정에서 30 fps에 250 ms 멈추는 소비자는 버퍼 8개부터 손실 0이었고, 평균적으로 느린 소비자는 버퍼를 늘려도 정확히 속도 차만큼 잃었다.

I count gaps in the sequence field; a correct driver increments sequence even when it has no buffer and drops the frame. Buffer count comes from the worst-case consumer stall, not the average rate: in my measurement at 30 fps with a consumer that stalls 250 ms every ten frames, losses went 30, 20, 10, then zero at eight buffers. If the consumer is slower on average, no buffer count helps; you lose exactly the rate difference, so you fix the consumer or drop to the latest frame deliberately. More buffers also mean more CMA and more latency.

Q. How would you pass camera frames to a hardware encoder without copying?

A. VIDIOC_EXPBUF로 캡처 버퍼를 dma-buf fd로 내보내고 인코더의 OUTPUT 큐를 V4L2_MEMORY_DMABUF로 열어 fd를 QBUF한다. 인코더가 다 읽고 DQBUF된 뒤에 카메라 큐에 돌려준다. 조건은 버퍼가 importer의 DMA 제약을 만족하는 것이다. vimc/vivid로 해 보니 vmalloc 버퍼를 연속 메모리가 필요한 장치에 넣으면 contiguous chunk is too small로 실패했다. 그래서 CMA나 dma-heap에서, 가장 제약이 큰 장치 기준으로 할당한다.

Export the capture buffers with VIDIOC_EXPBUF to get dma-buf file descriptors, open the encoder's output queue with V4L2_MEMORY_DMABUF, and queue the fd. The importer attaches and maps the buffer for its own device, so no CPU copy happens. Only requeue the buffer to the camera after the encoder has dequeued it. The buffer must satisfy the importer's DMA constraints: I reproduced a vmalloc-backed buffer being rejected by a dma-contig importer with "contiguous chunk is too small", so in practice you allocate from CMA or a dma-heap sized for the most constrained device, and use DMA_BUF_IOCTL_SYNC if the CPU also touches it.

Q. What do data-lanes and link-frequencies in the device tree do, and how does the receiver find the sensor?

A. endpoint 속성이다. data-lanes는 쓰는 레인과 순서, link-frequencies는 허용되는 CSI-2 링크 주파수(DDR이라 레인당 비트레이트의 절반)다. 센서 드라이버는 v4l2_fwnode_endpoint_alloc_parse()로 읽어 자기 모드 표와 맞는지 검사하고, 수신기는 자기 endpoint의 remote를 v4l2_async_nf_add_fwnode_remote()로 notifier에 등록해 센서 subdev가 등록되기를 기다린다. 짝이 맞으면 .bound에서 링크를 만들고, 전부 모이면 .complete에서 subdev 노드를 만든다.

They're endpoint properties in the OF graph. data-lanes lists which lanes are used and their order; link-frequencies lists the allowed CSI-2 link frequencies, which is half the per-lane bit rate because it's DDR. The sensor driver parses them with v4l2_fwnode_endpoint_alloc_parse and rejects unsupported values in probe. The receiver adds its endpoint's remote to a v4l2-async notifier, so whichever driver probes first, the async core matches the sensor subdev by fwnode, calls bound, where the receiver creates the media link, and when everything is present calls complete, which registers the subdev device nodes.

Q. Why is libcamera needed if V4L2 already exists?

A. V4L2는 하드웨어 블록을 노출할 뿐 "좋은 영상"을 만들지 않는다. ISP가 있는 SoC는 매 프레임 통계를 읽고 노출·게인·화이트밸런스와 ISP 파라미터를 바꾸는 3A 루프와, SoC마다 다른 그래프 설정이 필요하다. 그것을 커널에 넣지 않고 유저 공간의 pipeline handler와 IPA로 표준화한 것이 libcamera다.

V4L2 exposes the hardware blocks but doesn't produce a good image by itself. With an ISP you need a per-frame 3A loop that reads statistics buffers and programs sensor exposure and gain plus ISP parameter buffers, and every SoC has a different media graph to configure. The kernel community keeps that policy in user space; libcamera standardizes it with per-SoC pipeline handlers and image processing algorithm modules, and gives apps one API plus GStreamer and V4L2-compatibility layers.

20. 요약 & 체크리스트#

SoC 카메라는 센서(I2C 제어 + MIPI CSI-2 데이터) → CSI-2 수신기 → ISP → 스케일러/DMA → DRAM의 파이프라인이고, Linux는 이것을 media controller 그래프로 모델링한다. 블록은 v4l2_subdev(/dev/v4l-subdevN, pad별 media bus 포맷), 메모리 끝단은 video_device(/dev/videoN, fourcc + videobuf2 큐), 전체는 media_device(/dev/mediaN)다. MC 드라이버에서는 유저가 센서부터 하류로 subdev 포맷을 맞추고 링크를 켜야 하며, STREAMON 때 켜진 링크 전부(쓰지 않는 노드까지)가 검증되어 하나라도 다르면 -EPIPE다(vimc로 재현, dyndbg로 원인 확인). videobuf2는 DEQUEUED → QUEUED → ACTIVE → DONE의 소유권 링이고, 드라이버는 프레임마다 CLOCK_MONOTONIC 타임스탬프와 sequence를 기록해야 한다. 측정으로 보면 평균적으로 느린 소비자는 버퍼 수와 무관하게 속도 차만큼 프레임을 잃고(100 ms 소비자: 60장 받는 동안 111~112장 손실), 순간 멈춤은 버퍼로 흡수된다(250 ms 멈춤 → 8개부터 손실 0). VIDIOC_EXPBUF + V4L2_MEMORY_DMABUF로 복사 없이 다른 장치에 넘길 수 있지만, importer의 DMA 제약(연속성)을 만족해야 한다(vmalloc → dma-contig 실패 재현). 보드 배선은 DT OF graph(data-lanes, link-frequencies, 양방향 remote-endpoint)로 적고, v4l2-async가 probe 순서와 무관하게 센서와 수신기를 짝짓는다. 최소 캡처 드라이버는 vb2_ops 다섯 개, 포맷 ioctl 몇 개, 컨트롤 핸들러, 등록 순서만 지키면 300줄로 된다.
