0. 큰 그림 — 이게 왜 필요한가#

0.1 펌웨어에서는 이렇게 했다#

SSD 컨트롤러 펌웨어에서 이 네 가지는 보통 이렇게 생겼다.

코드는 몇 줄이지만 제품 수준이 되면 질문이 쏟아진다. LED를 누가 언제 깜빡이나(부팅 중? 에러 코드?), PWM duty를 바꾸는 동안 파형이 튀지 않나, RTC 시간과 펌웨어가 쓰는 시간이 어긋나면 누가 맞추나, kick을 메인 루프 어디에 두어야 "진짜로 살아 있을 때만" kick하게 되나.

Linux는 이 네 장치마다 작은 서브시스템(framework) 을 둔다. 드라이버는 하드웨어를 만지는 콜백 몇 개만 채운 ops 구조체를 등록하고, 나머지(유저 인터페이스, 트리거, 알람 큐, keepalive 워커, 권한, 동시성)는 core가 맡는다. I1에서 말한 "char device를 직접 만들지 말고 서브시스템에 등록하라"의 가장 작은 예제들이다.

0.3 센서 키트 장비에서는#

로봇용 센서 키트(i.MX8/AM62/Jetson급 SoC + IMU·카메라·LiDAR·CAN 모터)를 예로 들면:

  • LED: 전원(초록 상시), 상태(부팅 중 heartbeat → 정상 상시 → 에러 코드 패턴), 네트워크 링크(netdev 트리거), 저장장치 활동(disk 트리거). 현장 기술자는 이것만 보고 "어디가 죽었는지" 판단한다.
  • PWM: 냉각 팬(pwm-fan + thermal), 디스플레이 백라이트(pwm_bl), 부저(pwm-beeper), 조명·IR 투광기, 서보(50 Hz). 실시간 모터 전류 제어는 보통 MCU 몫이다.
  • RTC: 로그·사진 타임스탬프의 기준. GNSS/NTP가 잡히기 전 부팅 직후 시간. 정해진 시각에 장비를 깨우는 알람(저전력 감시 모드).
  • watchdog: 커널 hang, 제어 데몬 데드락, 유저 공간 전체 멈춤을 잡아 사람 없이 장비를 되살리는 마지막 안전망.

1.2 예제 1 — DT 조각: sim LED 3개, pwm-gpio 2개, 가짜 PWM 칩과 소비자#

무엇을 확인하나: 이 노트의 LED·PWM 실험을 한 DT에 담는다. virt.dts 사본 끝에 #include해서 C 전처리 → dtc로 dtb를 만든다(D4와 같은 방식). leds/common.h의 LED_FUNCTION_*·LED_COLOR_ID_* 매크로를 쓴다.

요점:

  • function + color가 있으면 LED core가 이름을 <color>:<function>으로 자동 생성한다(led_compose_name()). 옛 DT의 label = "board:green:status"는 deprecated다. 같은 function이 여러 개면 function-enumerator로 green:status-1처럼 번호를 붙인다.
  • default-state는 "on", "off", "keep"(부트로더가 켜 둔 상태 유지) 셋 중 하나다. 부트로더가 이미 전원 LED를 켰다면 "keep"이어야 커널 부팅 중 꺼졌다 켜지는 깜빡임이 없다.
  • panic-indicator는 커널 panic 때 이 LED를 깜빡이게 한다(panic 트리거로 자동 전환).
  • pwms = <&phandle 채널 period_ns 플래그> — #pwm-cells = <3>이면 세 칸이다. 플래그 PWM_POLARITY_INVERTED(값 1)는 극성 반전. 소비자 드라이버는 이 period·polarity를 pwm_init_state()로 받아 쓴다(§3.6).
  • pl061@9030000 노드에는 레이블이 없어서, 빌드 스크립트가 sed로 gpio: 레이블을 붙인다(H4와 같은 수법).

1.4 예제 2 — 네 클래스가 생기는 순간#

무엇을 확인하나: 모듈을 올리기 전과 후에 /sys/class/{leds,pwm,rtc,watchdog}과 /dev 노드가 어떻게 바뀌는가.

출력에서 볼 것:

  • rtc0은 처음부터 있다. PL031 드라이버가 built-in(=y)이라 부팅 중에 probe됐다.
  • LED 이름이 DT의 color·function에서 자동으로 blue:heartbeat, green:status, red:fault가 됐다.
  • pwm-gpio 노드 두 개 중 gpio-sim 위의 것은 probe 실패, PL061 위의 것만 pwmchip0이 됐다. 이유는 §3.5.
  • watchdog은 노드가 두 개다. /dev/watchdog(misc, major 10 minor 130)은 옛 단일 장치 API 호환용으로 첫 번째 watchdog에만 붙고, /dev/watchdog0(동적 major)은 장치별 노드다. 새 코드는 /dev/watchdogN을 쓴다.
  • /dev/pwmchip*는 없다. 6.18에는 PWM 문자 장치(PWM_IOCTL_*)가 있지만, pwmchip_add()가 waveform 콜백(write_waveform)을 구현한 드라이버에만 devt를 준다(랩 소스 drivers/pwm/core.c에서 확인). pwm-gpio는 아직 .apply 방식이다.

2. LED class — "밝기 하나"를 표준화하고 깜빡임은 트리거에 맡긴다#

2.1 직관: LED 드라이버는 "밝기 쓰기" 함수 하나다#

MCU에서 LED를 깜빡이려면 타이머 ISR이나 RTOS 태스크를 하나 만들어야 했다. Linux LED class는 이것을 둘로 쪼갠다.

  1. LED 드라이버(provider): "이 LED의 밝기를 n으로 만들어라"만 할 줄 안다. GPIO 하나든, I2C LED 드라이버 IC의 채널이든, PWM이든.
  2. 트리거(trigger): "언제 켜고 끌지"를 정하는 정책. timer(주기 깜빡임), heartbeat(심장 박동), disk-activity, netdev(링크/트래픽), panic, default-on, pattern(임의 패턴).

둘이 분리돼 있으니 GPIO LED든 I2C LED든 같은 netdev 트리거를 붙일 수 있고, 트리거 코드는 LED 하드웨어를 전혀 모른다. bare-metal 비유로는 "LED HAL 함수 하나 + 이벤트 소스별 정책 모듈"이다.

2.2 정의: struct led_classdev#

드라이버가 채우는 필드 중 중요한 것만 (include/linux/leds.h, 6.18 기준):

콜백어디서 불리나잠들어도 되나대표 하드웨어
brightness_set트리거의 타이머·softirq, 호출자 문맥 그대로안 됨MMIO GPIO, SoC PWM
brightness_set_blockingcore의 ordered workqueue leds(kworker)됨I2C/SPI LED 드라이버 IC, gpio-sim·I2C GPIO 확장기 위의 LED
blink_settimer 트리거 활성화 때 한 번구현에 따라자체 깜빡임 레지스터가 있는 LED IC
pattern_setpattern 트리거 hw_pattern구현에 따라패턴 엔진이 있는 LED IC (예: 일부 PMIC LED)

brightness는 0..max_brightness 정수다. GPIO LED는 max_brightness = 1이고, I2C LED IC나 PWM LED는 보통 255다.

2.3 예제 3 — sysfs로 보는 LED, 그리고 active-low#

무엇을 확인하나: DT의 default-state와 GPIO_ACTIVE_LOW가 실제 핀(gpio-sim 라인의 value)에 어떻게 반영되는가. SIMD는 /sys/devices/platform/i9-gpio-sim/gpiochip* 디렉터리다.

출력에서 볼 것:

  • red:fault는 논리 밝기 0(꺼짐)인데 핀은 1이다. GPIO_ACTIVE_LOW라서 gpiolib이 뒤집는다(H4 §5). 켜자(echo 1) 핀이 0으로 내려갔다. LED 드라이버도 사용자도 극성을 몰라도 된다.
  • blue:heartbeat의 트리거가 아직 none이다. DT에 linux,default-trigger = "heartbeat"라고 썼지만 heartbeat 트리거가 모듈(=m)이라 아직 등록 전이기 때문이다. 트리거가 나중에 등록되면 core가 default_trigger 이름이 같은 LED를 찾아 붙인다(바로 다음 예제에서 확인).
  • trigger 파일은 "읽으면 목록, [ ]가 현재 선택, 쓰면 변경"이다. kbd-*는 키보드 LED 트리거, cpu/cpu0은 CPU 활동, panic은 panic 때 깜빡임이다.

2.4 예제 4 — 트리거 파형을 직접 재 보기 (heartbeat · timer · pattern)#

"정말 그렇게 깜빡이나?"를 눈으로 보려면 오실로스코프가 필요하다. gpio-sim은 출력 라인의 현재 값을 sysfs value로 보여 주므로, 그 파일을 쉬지 않고 읽어 엣지 시각을 기록하는 샘플러를 만든다. PWM 실험(§3)에서도 쓰려고 PL061 레지스터를 /dev/mem으로 직접 읽는 모드도 넣었다.

PL061의 DATA 레지스터는 주소 비트 [9:2]가 마스크다(PrimeCell GPIO 설계). 4번 핀만 보려면 오프셋 (1 << 4) << 2를 읽는다 — uint32_t 배열 인덱스로 gpio[1 << bit]. Don이 STM32의 BSRR이나 bit-band로 하던 "주소에 마스크를 싣는" 트릭과 같은 발상이다.

시나리오(시간 순서대로, 엣지 목록은 처음 몇 줄만):

그림 2 — 세 트리거가 만든 실제 핀 파형. 위 출력의 엣지 목록(전체)을 그대로 그렸다. heartbeat는 "두 번 짧게 + 긴 쉼", timer는 100/300 ms 사각파, pattern은 우리가 적은 "두 번 깜빡 + 700 ms 쉼"이다.

출력에서 볼 것:

  • 트리거가 붙는 순간: heartbeat 모듈을 올리자 [heartbeat]가 선택됐다. DT의 linux,default-trigger가 늦게 등록된 트리거에도 적용된다.
  • heartbeat: 켜짐 약 76 ms, 한 주기(상승 → 다음 쌍의 상승) 약 1223~1248 ms. 소스(ledtrig-heartbeat.c)의 주기는 300 + (6720 << FSHIFT) / (5 * avenrun[0] + (7 << FSHIFT)) ms라 load average 0이면 1260 ms이고, 부하가 오르면 빨라진다. 켜짐 70 ms를 jiffy(HZ=250 → 4 ms) 단위로 올림한 것이 76 ms 근처다. 샘플러의 period=622 ms는 쌍박동의 상승 간격 평균이라 의미가 없다 — 지표는 파형에 맞게 골라야 한다.
  • timer 100/300: 켜짐 104 ms, 주기 약 409 ms인데 한 번은 134 ms(817→951) 켜져 있었다. 소프트웨어 타이머(timer_list) + TCG 에뮬레이션의 지터다. LED 트리거는 소프트웨어 타이머라 정밀하지 않다 — 정밀한 깜빡임이 필요하면 하드웨어 blink_set을 쓴다.
  • pattern: "밝기 시간" 쌍의 나열이다. 1 100 1 0처럼 같은 밝기를 시간 0으로 한 번 더 적으면 계단(즉시 전환), 밝기가 다른 두 항목 사이에 시간이 있으면 그 시간 동안 점진 변화(fade) 한다(Documentation/ABI/testing/sysfs-class-led-trigger-pattern). 한 주기 1000 ms 요청에 실측 1031 ms. repeat 파일로 반복 횟수(-1 = 무한)를 정한다. 에러 코드를 "깜빡임 횟수"로 표시하는 제품 LED에 딱 맞는 트리거다.

2.5 흔한 함정 — brightness에 0을 쓰면 트리거가 사라진다#

brightness_store()(drivers/leds/led-class.c)는 0이 들어오면 led_trigger_remove()부터 부른다. 그래서 "heartbeat 중인 LED를 잠깐 끄려고 echo 0 > brightness" 하면 heartbeat가 영영 꺼진다. 잠깐 끄려면 트리거를 바꾸거나 애플리케이션이 트리거를 다시 설정해야 한다. 같은 이유로 timer 트리거 중 brightness에 0이 아닌 값을 쓰면 깜빡임 밝기(blink_brightness)가 바뀐다(다음 예제에서 200으로 깜빡이는 것을 본다).

2.6 예제 5 — 내 LED 드라이버: brightness_set_blocking은 어디서 불리나#

무엇을 확인하나: I2C LED IC처럼 쓰기가 잠드는 LED를 흉내 내는 드라이버를 만들고, 콜백이 어떤 문맥(task 이름)에서 불리는지, timer 트리거 10/10 ms를 걸었을 때 콜백이 2초에 몇 번 불리는지 센다.

출력에서 볼 것:

  • 이름이 DT 자식 노드의 color = AMBER, function = "indicator"에서 amber:indicator로 만들어졌다. 드라이버는 이름 문자열을 한 글자도 안 썼다(led_init_data.fwnode만 넘김).
  • sysfs에서 echo 200을 한 첫 호출조차 kworker가 불렀다. brightness_set이 없고 _blocking만 있으면 core(led_set_brightness_nopm())가 값을 저장하고 leds workqueue에 일을 넘긴다. 그래서 timer 트리거(softirq 문맥의 timer_list)에서도 안전하게 잠들 수 있다.
  • 깜빡임 밝기가 200이다. 트리거 전 밝기가 blink_brightness가 된다(§2.5).
  • 10/10 ms 깜빡임이면 2초에 200번이어야 하는데 118번. 원인은 jiffy 해상도다: HZ=250이라 10 ms는 msecs_to_jiffies(10) = 3 jiffy = 12 ms로 올림되고, timer_list는 다음 tick 경계에서 돌므로 실제로는 약 16 ms 간격(2000/118 ≈ 17 ms)이 된다. 여기에 1 ms "I2C 쓰기"가 workqueue에서 직렬로 더해진다. LED 트리거로 수십 Hz 이상의 정확한 파형을 기대하지 말 것 — 그런 일은 PWM의 몫이다.

그림 3 — 밝기 쓰기의 두 갈래. 잠들지 않는 brightness_set이 있으면 호출자 문맥에서 바로 부르고, _blocking만 있으면 leds workqueue를 거쳐 kworker가 부른다. 그래서 드라이버는 "내 쓰기가 잠드나"만 정직하게 고르면 된다.

2.7 multicolor LED, PWM LED, 하드웨어 오프로드#

  • multicolor (RGB): struct led_classdev_mc가 led_classdev 하나 + 채널 배열(struct mc_subled)을 갖는다. sysfs에 multi_index(채널 색 순서, 예: red green blue)와 multi_intensity(채널별 강도)가 생기고, 최종 채널 밝기 = brightness × intensity / max_brightness다. 드라이버는 led_mc_calc_color_components()로 계산한다. DT는 color = <LED_COLOR_ID_RGB> 노드 아래 채널 자식 노드를 둔다. 랩 커널에는 led-class-multicolor.ko가 모듈로 있다 (이 노트에서 실행하지 않음).
  • leds-pwm: PWM 채널을 LED class로 감싸는 드라이버(compatible = "pwm-leds"). 밝기 0..255가 duty로 바뀐다. 밝기 조절이 필요한 LED는 GPIO보다 이쪽이다.
  • 하드웨어 오프로드: 이더넷 PHY의 링크/활동 LED는 PHY가 스스로 깜빡인다. 6.x의 netdev 트리거는 hw_control_is_supported/hw_control_set 콜백으로 "이 LED는 하드웨어가 링크·트래픽에 맞춰 직접 깜빡여라"를 PHY 드라이버에 맡길 수 있다. CPU가 패킷마다 LED를 토글하지 않아도 된다.

3. PWM — period · duty · polarity를 "상태 하나"로 원자적으로 바꾼다#

3.1 직관: 펌웨어의 ARR/CCR이 struct pwm_state가 된다#

STM32 타이머로 PWM을 만들 때는 ARR(주기), CCR(비교값 = duty), CCxP(극성), CCxE(출력 enable)를 각각 썼다. 그리고 "ARR을 먼저 줄이면 CCR > ARR인 순간 100% 출력이 한 주기 튄다" 같은 순서 문제를 preload 비트(ARPE/OCxPE)로 피했다.

Linux PWM은 이 네 값을 한 구조체에 담아 한 번에 적용(apply) 한다. 드라이버는 "이 상태를 하드웨어에 반영하라"는 콜백 하나만 구현하고, 순서·글리치 없는 전환은 드라이버가 하드웨어 특성에 맞게 책임진다.

그림 4 — PWM의 네 값과 적용 경로. 시간 단위는 모두 나노초다. inversed 극성은 같은 duty_cycle을 "Low인 시간"으로 해석한다. 소비자는 상태 전체를 만들어 pwm_apply_might_sleep()에 넘기고, core가 검증한 뒤 드라이버의 .apply를 한 번 부른다.

3.2 정의: provider 쪽 — pwm_chip과 pwm_ops#

  • .apply: 상태 전체를 하드웨어에 반영한다. 현재 주기를 끝까지 마치고 바꾸는지(글리치 없음), 즉시 바꾸는지는 하드웨어에 달렸고, 드라이버 주석에 "Limitations"로 적는 것이 관례다.
  • .get_state: 하드웨어에서 현재 상태를 읽는다. 부팅 때 부트로더가 켜 둔 PWM(예: 백라이트)을 커널이 이어받을 때 쓴다.
  • 등록은 devm_pwmchip_alloc(parent, npwm, sizeof_priv) → chip->ops = &ops → devm_pwmchip_add(). 최근 6.x 커널에서 pwm_chip을 core가 할당하는 방식으로 바뀌어(예전 드라이버는 pwm_chip을 자기 구조체에 박아 넣었다) private 데이터는 pwmchip_get_drvdata(chip)로 꺼낸다.
  • chip->atomic = true이면 .apply가 잠들지 않는다는 약속이고, 소비자가 pwm_apply_atomic()(IRQ 문맥 가능)을 쓸 수 있다.
  • waveform API: 6.18 소스의 include/linux/pwm.h에는 struct pwm_waveform { period_length_ns, duty_length_ns, duty_offset_ns }와 pwm_set_waveform_might_sleep(), pwm_round_waveform_might_sleep()이 있다. pwm_state와 달리 상승 엣지의 위상(offset) 을 표현하고, "하드웨어가 실제로 낼 수 있는 값으로 어떻게 반올림되는지"를 적용 전에 물어볼 수 있다. 이 콜백을 구현한 드라이버(pwm-stm32, pwm-axi-pwmgen, pwm-pca9685 등 — 랩 소스에서 write_waveform으로 검색)에만 /dev/pwmchipN 문자 장치가 생긴다(§1.4). 아직은 대부분의 드라이버가 .apply 방식이다.

3.3 예제 6 — sysfs로 소프트웨어 PWM을 돌리고 실제 duty를 재 보기#

무엇을 확인하나: /sys/class/pwm 인터페이스(export → period/duty_cycle/polarity/enable)를 쓰고, PL061 4번 핀을 /dev/mem으로 직접 샘플링해 요청한 duty와 실제 high 비율을 비교한다. 대상은 pwm-gpio(GPIO를 hrtimer로 토글하는 소프트웨어 PWM)다.

첫 번째 실행의 출력:

출력에서 볼 것:

  • 20 ms 주기는 쓸 만하다: 펄스 개수가 정확하고 duty 오차는 대략 ±3%p 이내. LED 밝기, 부저, 느린 서보(50 Hz = 20 ms)에는 충분하다.
  • 1 ms 주기에서는 무너진다: 10%(100 us 펄스)는 1초에 1000개 중 41개만 관측됐다. pwm-gpio의 타이머 콜백(pwm_gpio_timer())은 hrtimer_forward(timer, 이전 만료 시각, 다음 간격)으로 다음 토글을 잡는다. 콜백이 짧은 구간(100 us)보다 늦게 돌면 다음 만료 시각이 이미 지나 있어서 곧바로 다시 토글 → 짧은 구간이 거의 0으로 붕괴한다. 50%처럼 양쪽 구간이 길면 펄스는 다 나오지만 폭이 흔들린다.
  • TCG 주의: 이 가상 머신은 KVM 없이 QEMU가 명령어를 번역해 돌리고(TCG), 호스트도 바쁘다. 실제 Cortex-A의 hrtimer 지연은 보통 수~수십 us라 숫자는 훨씬 좋다. 하지만 경향은 진짜다: 소프트웨어 PWM의 정확도는 "가장 짧은 구간 대비 타이머 지연"이 결정하고, 인터럽트가 막히는 순간(다른 드라이버의 긴 IRQ off 구간) 바로 파형이 깨진다. 모터·전력 제어에 소프트웨어 PWM을 쓰지 않는 이유다.
  • inversed: duty 25%를 inversed로 걸자 high 비율이 71~79% — 즉 Low가 25%다. 극성 변경은 pwm-gpio에서 disable 상태에서만 했다(대부분의 하드웨어도 마찬가지).
  • 샘플러 자체의 정확도: 0.4 us/sample이라 100 us 펄스를 놓칠 만큼 느리지는 않다. 다만 샘플러와 hrtimer가 vCPU 하나를 나눠 쓰므로 vCPU가 호스트에서 잠깐 밀리면 둘 다 멈춘다. "관측" 손실의 일부는 측정 쪽 손실일 수 있다 — 그래서 실제 보드에서는 로직 분석기로 다시 확인해야 한다.

3.4 순서 함정 — period를 먼저 줄이면 EINVAL#

무엇을 확인하나: 펌웨어의 "ARR을 CCR보다 작게 만들면 안 된다"가 Linux에서는 어떻게 나타나나.

출력에서 볼 것: sysfs는 파일 하나를 쓸 때마다 "현재 상태 + 그 값 하나"로 pwm_apply_might_sleep()을 부른다. 켜진(enabled) 상태에서 duty_cycle > period는 pwm_state_valid()가 거부한다. 줄일 때는 duty 먼저, 늘릴 때는 period 먼저. 꺼진 상태에서는 core가 검증을 건너뛰어(꺼진 상태의 나머지 값은 의미 없다고 보므로) 이상한 값이 들어가도 에러가 안 나고, enable 순간에 에러가 난다. 커널 소비자는 struct pwm_state를 통째로 만들어 한 번에 apply하므로 이 문제가 없다 — sysfs가 "원자적 상태"를 잘게 쪼개 버리는 인터페이스라서 생기는 함정이다.

3.5 gpio-sim 위의 pwm-gpio는 왜 거부됐나#

§1.4의 sleeping GPIO not supported는 pwm_gpio_probe()의 이 검사다.

토글은 hrtimer 콜백(hardirq 문맥)에서 gpiod_set_value()로 하므로 잠드는 GPIO 칩(gpio-sim은 can_sleep = true, I2C GPIO 확장기도 마찬가지)은 쓸 수 없다. H4에서 본 "_cansleep 구분"이 여기서 probe 실패로 드러난다. 보드에서 소프트웨어 PWM이 필요하면 SoC 내장 GPIO(MMIO) 핀을 골라야 한다.

3.6 예제 7 — 내 pwm_chip 드라이버 + 소비자 드라이버 + pwm-fan#

무엇을 확인하나: 가짜 PWM 컨트롤러(채널 2개)를 등록하고, ① 직접 만든 소비자가 DT의 pwms에서 period·polarity를 받아 30% duty로 켜는 경로, ② 커널의 pwm-fan(hwmon)이 같은 칩을 쓰는 경로에서 .apply가 어떤 상태로 불리는지 본다. 소스는 길어서 두 부분으로 나눈다.

출력에서 볼 것:

  • 소비자는 숫자를 하드코딩하지 않았다. pwm_init_state()가 DT pwms = <&i9_fpwm 1 50000 PWM_POLARITY_INVERTED>에서 50 us 주기와 inversed 극성을 가져왔고(pol=1), 30% = 15000 ns가 한 번의 .apply로 들어갔다.
  • pwm-fan은 probe 때 최대 속도(pwm1=255 → duty 39999/40000)로 켠다. 팬을 안전 쪽(최대 냉각)으로 시작하는 정책이다. pwm1=128 → duty 20078 ns(128/255 × 40000), pwm1=0 → duty 0이면서 en=0 — pwm-fan은 0일 때 PWM을 아예 끈다.
  • 소비자가 이미 잡은 채널을 sysfs로 export하려 하자 EBUSY. 커널 소비자와 유저 공간이 같은 채널을 동시에 쥘 수 없다.
  • debugfs의 requested와 actual은 각각 core가 마지막으로 apply한 상태와 .get_state로 읽은 하드웨어 상태다. 드라이버가 반올림하면 둘이 달라진다 — bring-up 때 "내가 준 값이 실제로 어떻게 들어갔나"를 보는 곳이다. fan 쪽에 usage_power가 표시된 것은 pwm-fan이 "평균 전력만 맞으면 된다"고 표시해 하드웨어가 위상을 자유롭게 골라도 된다는 뜻이다.

4. RTC — 전원이 꺼져도 흐르는 시계, 그리고 장비를 깨우는 알람#

4.1 직관: Linux에는 시계가 둘 있다#

  1. 시스템 시계 (CLOCK_REALTIME): 커널이 고해상도 타이머(arm64는 generic timer)로 나노초 단위로 유지한다. date, gettimeofday(), 로그 타임스탬프가 이것이다. 전원이 꺼지면 사라진다.
  2. RTC: 코인셀이나 슈퍼커패시터로 버티는 저전력 칩(또는 SoC/PMIC 안의 always-on 블록). 32.768 kHz 크리스털로 초 단위 달력 시간을 센다. 정밀도는 보통 ±20 ppm(하루 약 1.7초) 수준이다.

둘의 관계는 단순하다: 부팅할 때 RTC → 시스템 시계로 한 번 복사(hctosys)하고, 그 뒤로는 시스템 시계가 주인이다. NTP/PTP/GNSS가 시스템 시계를 맞추면, 커널이 주기적으로 시스템 시계 → RTC로 되써서(systohc) 다음 부팅을 대비한다.

그림 7 — 두 시계의 관계. hctosys(CONFIG_RTC_HCTOSYS)는 부팅 중 한 번, systohc(CONFIG_RTC_SYSTOHC)는 커널이 "시계가 외부와 동기화됐다"(adjtimex의 STA_UNSYNC가 꺼짐)고 알 때만 주기적으로 RTC에 되쓴다. 시간 동기화 자체(NTP/PTP 서보, PHC)는 Q3에서 다룬다.

bare-metal 비유: SSD 펌웨어가 호스트의 Set Features(Timestamp)로 받은 시각을 RAM 카운터로 유지하다가 전원 손실 전에 NAND에 저장하던 것과 같은 구조다. 다만 RTC는 "꺼져 있는 동안에도" 센다.

4.2 정의: rtc_class_ops와 등록#

드라이버 probe의 전형적인 모양 (rtc-test.c에서 본 그대로):

  • 드라이버는 struct rtc_time(= struct tm과 같은 필드: 연도는 1900 기준, 월은 0 기준)만 다룬다. BCD 변환, 레지스터 순서, 오실레이터 정지 플래그 검사는 드라이버 몫이다.
  • range_min/max를 주면 core가 범위 밖 시간을 거부하고, 2000~2099만 아는 칩에서 hctosys가 엉뚱한 세기로 해석하는 사고를 막는다.
  • 알람 큐: 유저의 알람, alarmtimer(CLOCK_REALTIME_ALARM/CLOCK_BOOTTIME_ALARM 타이머), uie 에뮬레이션은 모두 core의 timerqueue에 들어가고, 하드웨어 알람 레지스터 하나에는 가장 이른 것만 프로그램된다. 하드웨어 알람이 하나뿐인 칩에서 여러 사용자가 공존하는 방법이다.
  • 알람 기능이 없는 RTC는 core가 RTC_FEATURE_ALARM 비트를 끄고 알람 ioctl을 거부한다(아래 예제에서 rtc-test.0으로 확인).

4.3 예제 8 — 부팅 로그, sysfs, /proc/driver/rtc, hwclock#

무엇을 확인하나: 부팅 중 hctosys가 일어났다는 증거와, RTC를 보는 세 가지 창구.

출력에서 볼 것:

  • setting system clock to ... 한 줄이 hctosys다. 그 시점은 PL031 probe 직후(5.49 s) — RTC 드라이버가 늦게 뜨면(I2C 모듈 등) 그 전까지의 로그는 1970년 시간이다. 그래서 I2C RTC를 쓰는 제품은 RTC 드라이버와 I2C 컨트롤러를 built-in으로 두거나, 유저 공간에서 hwclock -s를 일찍 돌린다.
  • hctosys=1은 "이 RTC가 시스템 시계의 출처였다"는 표시다(CONFIG_RTC_HCTOSYS_DEVICE="rtc0").
  • wakeup=enabled: PL031이 시스템을 깨울 수 있는 장치로 등록됐다(§4.5).
  • alarmtimer.0.auto: alarmtimer가 이 RTC를 "잠든 동안에도 울리는 타이머"의 하드웨어로 잡았다는 흔적이다.
  • RTC는 23:19:12, 시스템 시계는 23:19:11로 1초 차이가 난다. RTC는 초 단위만 알고, 읽는 순간 초 경계와의 위상이 다르니 ±1 s는 정상이다. 정밀한 시각이 필요하면 RTC가 아니라 NTP/PTP로 맞춘 시스템 시계를 믿는다.

4.4 예제 9 — RTC ioctl로 시간 읽기·설정·알람 대기#

무엇을 확인하나: hwclock이 내부에서 하는 일(RTC_RD_TIME/RTC_SET_TIME)과, 알람을 걸고 read()로 IRQ를 기다리는 방법. RTC_WKALM_SET은 "알람 시각 설정 + 알람 IRQ 켜기"를 한 번에 하는 ioctl이다(옛 방식은 RTC_ALM_SET 후 RTC_AIE_ON).

처음 짤 때 struct rtc_time *을 struct tm *로 캐스팅해서 gmtime_r()에 넘겼다가 고쳤다. 앞 9개 필드는 같지만 glibc의 struct tm은 뒤에 tm_gmtoff, tm_zone이 더 있어서 rtc_wkalrm 끝을 넘어 덮어쓴다. 필드를 복사하는 tm2rtc()를 따로 둔 이유다.

출력에서 볼 것:

  • read()가 돌려준 unsigned long의 하위 바이트는 이벤트 종류, 상위는 횟수다. 0xa0 = RTC_IRQF(0x80) | RTC_AF(0x20)(알람), 횟수 1. 드라이버의 rtc_update_irq(rtc, 1, RTC_AF | RTC_IRQF)가 그대로 유저까지 온다. poll()/select()도 된다(A4).
  • rtc-test.0(=rtc1)은 일부러 알람 없는 ops로 등록된 장치라 RTC_WKALM_SET이 EINVAL. 알람 없는 RTC 칩(일부 저가 I2C RTC)에서 rtcwake가 실패하는 모습 그대로다.
  • RTC_SET_TIME으로 rtc-test 시계를 2023-11-14로 돌려도 시스템 시계(2026)는 그대로다. RTC를 바꾼다고 시스템 시계가 바뀌지 않는다(hctosys는 부팅 때 한 번뿐).
  • 알람 대기 시간이 요청과 거의 정확히 같다(0.997~3.223 s). 실제 RTC 칩은 초 경계에서만 알람이 울리므로, 0.37 s 어긋난 시점에 "+1 s"를 걸면 0.63 s 뒤에 울려야 한다. QEMU의 PL031 모델은 알람을 "지금부터 N초 뒤"의 가상 타이머로 구현해서 초 경계 효과가 안 보인다(QEMU 소스 hw/rtc/pl031.c의 알람 계산 — 이 노트에서 직접 확인하지는 않음). rtc-test는 jiffies 타이머라 더 흔들린다. 실제 보드에서는 RTC 알람 오차가 최대 1초라고 가정하고 설계한다.

4.5 예제 10 — 알람으로 s2idle에서 깨어나기 (rtcwake)#

무엇을 확인하나: RTC 알람이 "잠든 시스템을 깨우는 wakeup source"로 동작하는 전체 경로.

그림 8 — RTC 알람이 시스템을 깨우는 흐름. 핵심은 세 가지다: ① 드라이버가 probe에서 device_init_wakeup(dev, true)로 "나는 깨울 수 있다"를 선언, ② suspend 경로에서 알람 IRQ를 wake IRQ로 설정(enable_irq_wake(), 보통 .suspend 콜백이나 dev_pm_set_wake_irq()), ③ IRQ가 오면 wakeup 이벤트로 기록되고 PM core가 resume한다. s2idle은 CPU를 idle에 두는 가장 얕은 잠이라 일반 IRQ로도 깨지만, mem(S3/deep) 같은 깊은 잠에서는 always-on 도메인에 있는 RTC만 남는다.

출력에서 볼 것:

  • sysfs wakealarm은 C 없이 알람을 거는 방법이다. +2는 "지금부터 2초 뒤", 읽으면 epoch 초가 나온다. 0을 쓰면 해제.
  • virt 머신은 freeze mem disk를 광고하지만 mem_sleep은 [s2idle]뿐이다 — 즉 mem도 실제로는 s2idle이다. PSCI SYSTEM_SUSPEND가 없는 플랫폼의 전형이다.
  • rtcwake -m freeze -s 5: 23:19:46에 시작해 23:19:52에 깨어났다(6 s). 알람은 초 단위라 1초 정도의 오차는 예상 범위다. dmesg에 freeze → resume 과정이 그대로 보인다.
  • wakeup_sources의 9010000.pl031 행에 이벤트가 쌓였다. 실제 제품에서 "장비가 왜 깨어났나"를 따질 때 가장 먼저 보는 파일이다(CONFIG_PM_SLEEP_DEBUG를 켜면 /sys/power/pm_wakeup_irq로 마지막으로 깨운 IRQ도 볼 수 있다 — 이 랩 커널은 꺼져 있다).

4.6 실무 메모 — I2C 배터리 백업 RTC#

로봇·카메라 SoC는 내장 RTC가 있어도 SoC 전원 도메인과 함께 꺼지는 경우가 많아, PMIC RTC나 외부 I2C RTC(NXP PCF85063/PCF2127, Micro Crystal RV-3028, Maxim DS3231 등)를 코인셀로 따로 둔다. 랩 커널에는 이들 드라이버가 모듈로 있다(rtc-pcf85063.ko, rtc-rv3028.ko, rtc-ds1307.ko …). DT는 이렇게 생겼다 (예시 — 이 노트에서 실행하지 않음):

  • 오실레이터 정지 플래그: 코인셀이 빠졌다 다시 들어오면 칩은 "시간 무효" 비트(OS/VL/PORF 등)를 세운다. 좋은 드라이버는 .read_time에서 이 비트를 보고 -EINVAL을 돌려 hctosys가 쓰레기 시간을 시스템 시계에 넣지 않게 한다. 이때 부팅 로그에는 "setting system clock" 대신 hctosys 실패가 남고 시계는 1970년이다.
  • 1970년 장비: TLS 인증서 검증 실패(유효 기간 "아직 시작 안 함"), 로그 정렬 붕괴, make의 "clock skew detected". 제품에서는 ① RTC 무효 시 빌드 시각이나 마지막으로 저장한 시각을 하한으로 쓰고(systemd-timesyncd가 /var/lib/systemd/timesync/clock 파일의 mtime으로 이렇게 한다), ② 네트워크·GNSS 동기화 전까지 시간 의존 작업을 미룬다.
  • drift 보정: .set_offset을 구현한 칩은 sysfs offset(ppb)으로 크리스털 오차를 보정할 수 있다. 장기 무선 장비에서 쓴다.

5. watchdog — "살아 있다는 증거"를 못 내면 하드웨어가 리셋한다#

5.1 직관: 펌웨어의 WDT kick과 무엇이 다른가#

MCU 펌웨어에서 watchdog은 단순했다. 하드웨어 다운카운터를 켜고, 메인 루프가 한 바퀴 돌 때마다 kick한다. 루프가 어딘가에서 멈추면 카운터가 0이 되고 칩이 리셋된다. Don이 SSD에서 겪었듯이 어려운 건 "어디서 kick하느냐" 였다 — 타이머 ISR에서 kick하면 메인 루프가 죽어도 ISR은 살아 있어서 watchdog이 무용지물이 된다.

Linux에서도 하드웨어는 같다(SoC WDT, PMIC WDT, 외부 WDT 칩). 달라지는 건 누가 kick하나다.

  • 부팅 중(유저 공간이 아직 없을 때): 커널 watchdog core가 대신 kick할 수 있다(§5.8).
  • 평상시: 유저 공간 프로세스(전용 데몬, 또는 systemd PID 1)가 /dev/watchdog에 주기적으로 쓴다. 이 프로세스가 스케줄되지 못하면(커널 hang, 메모리 고갈, RT 태스크 폭주) kick이 끊겨 리셋된다.
  • 그 프로세스가 "시스템이 건강하다"를 무엇으로 판단하느냐가 watchdog 전략의 전부다(§7.1).

그림 9 — watchdog 타임라인 두 개(둘 다 이 노트의 실측). A: QEMU i6300esb에서 급식을 멈춘 뒤 실제 머신 리셋까지(§5.4). B: 직접 만든 가짜 watchdog에서 pretimeout 경고가 리셋 3초 전에 먼저 오는 모습(§5.7). pretimeout은 "곧 리셋된다 — 지금 진단 정보를 남겨라"라는 마지막 기회다.

  • nowayout=1: 똑같이 'V'를 썼는데 "nowayout prevents watchdog being stopped!" → 약 5초 뒤 리셋(두 번째 부팅 배너). 제품 빌드는 nowayout을 켠다: 데몬이 버그로 'V'를 쓰고 죽거나, 누군가 echo V > /dev/watchdog으로 watchdog을 끄는 일을 막는다. 대신 nowayout에서는 watchdog 데몬을 재시작할 때 timeout 안에 다시 열어야 한다.

5.6 예제 14 — softdog, 그리고 데몬이 죽으면#

무엇을 확인하나: 하드웨어가 없을 때 쓰는 softdog(커널 hrtimer로 흉내)과, 유저 공간 watchdog 데몬(BusyBox watchdog)이 SIGKILL로 죽으면 무슨 일이 일어나는가.

softdog도 시간이 되자 머신을 재부팅했다(emergency_restart()). softdog의 "Initiating system reboot" 메시지는 콘솔에 찍히지 않았다 — 즉시 재시작이라 콘솔 출력이 비워지기 전에 리셋된 것으로 보인다. softdog의 한계: 타이머가 커널 안에 있으므로 커널 자체가 멈추면(IRQ off 상태의 데드락) softdog도 같이 죽는다. 유저 공간 행만 잡는다. 진짜 제품에는 하드웨어 watchdog이 필요하다.

(alive 줄 중간 8줄은 ...로 생략했다. 위의 softdog 출력에서는 커널 명령줄 줄을 뺐다.)

출력에서 볼 것: 데몬이 살아 있는 8초 동안은 아무 일도 없다. SIGKILL로 죽자 커널이 fd를 닫으면서 "did not stop!" — 'V'가 없으니 계속 돈다. 6 × 1.024 ≈ 6.1 s 뒤(13.23 + 6.14 ≈ 19.4) 리셋됐고 마지막 출력은 18.94였다. "watchdog 데몬이 죽으면 장비가 리셋된다"는 의도된 동작이다. 그래서 데몬은 작고 단순해야 하고, 죽을 이유(OOM killer의 표적 등)를 없애야 한다(OOMScoreAdjust=-1000, 메모리 mlockall()).

5.8 예제 16 — 부트로더가 켜 둔 watchdog을 커널이 이어받기#

무엇을 확인하나: 제품에서는 부트로더(U-Boot, 심지어 BootROM)가 watchdog을 켠 채로 커널에 넘긴다. 커널 부팅이나 initramfs에서 멈추면 그것도 잡아야 하기 때문이다. 그런데 유저 공간 데몬이 /dev/watchdog을 열기 전까지는 누가 ping하나? 드라이버가 probe에서 "이미 돌고 있음"(WDOG_HW_RUNNING)을 알리면 core가 대신 ping한다. max_hw_ms=4000은 "하드웨어 최대 주기가 4초"라는 설정이다.

출력에서 볼 것:

  • watchdogd 라는 커널 스레드(core의 kthread_worker, RT 우선순위)가 2초(= 하드웨어 최대 4초의 절반)마다 ping했다. handle_boot_enabled=Y(CONFIG_WATCHDOG_HANDLE_BOOT_ENABLED)가 이 동작을 켠다. 끄면(watchdog.handle_boot_enabled=0) 커널은 손대지 않고, 유저 공간이 하드웨어 주기 안에 열지 못하면 리셋된다.
  • 유저가 열고 timeout을 10 s로 설정한 뒤 left=3이 나왔다. 하드웨어 한계(4 s)보다 긴 timeout을 요청하면 core가 하드웨어 주기 안에서 보충 ping을 해 주며 "10초"를 가상으로 만든다. GETTIMELEFT는 하드웨어 카운터 기준이라 4 s 창 안의 값이 보인다. 제품 문서에 "timeout은 하드웨어 최대값보다 길게 잡아도 되지만 커널이 살아 있어야 보충된다"고 적어 둘 일이다.
  • open_timeout=5: 아무도 열지 않으면 core는 등록 후 5초에 리셋이 나도록 마지막 보충 ping을 계산해서 멈춘다. 등록 4.36 → 마지막 ping 5.37 → 그로부터 하드웨어 4 s 뒤인 9.37에 bite. 5.37 = 9.37 − 4(watchdog_next_keepalive()가 open_deadline − hw_heartbeat로 계산). "rootfs 마운트 실패, systemd가 못 뜸" 같은 부팅 실패를 유한 시간 안에 리셋으로 바꾸는 장치다. 기본값 0은 "영원히 대신 ping" — 부팅이 유저 공간에서 멈춰도 리셋되지 않으므로 제품에서는 위험하다.

7. Embedded 실무에서 다시 보기#

7.1 로봇의 watchdog 전략 — 한 층으로는 부족하다#

Don이 SSD에서 겪은 것: 펌웨어 hang은 "멈췄다"보다 "일부만 멈췄다" 가 훨씬 흔하다. 호스트 명령 처리는 죽었는데 백그라운드 GC 태스크와 타이머 ISR은 살아 있어서 kick이 계속되는 식이다. RF 통합에서도 "칩은 응답하는데 특정 블록이 lock-up" 같은 반쪽 고장을 봤을 것이다. Linux 로봇에서도 똑같다: 커널은 멀쩡한데 제어 데몬이 데드락, 또는 카메라 파이프라인만 멈춤.

그래서 계층으로 설계한다.

그림 12 — 로봇 제품의 watchdog 계층. 위층은 "무엇이 잘못됐는지" 알고 부드럽게 복구하고, 아래층은 위층이 다 죽어도 확실하게 복구한다. 0층(모터 MCU)은 Linux와 독립적이어야 한다 — 로봇에서 "리셋"보다 중요한 것은 "리셋되는 동안 모터가 멈춰 있는 것"이다.

설계 체크리스트:

  1. 하드웨어 watchdog을 부트로더에서 켠다. 커널이 initramfs에서 멈춰도 잡히도록. 커널에서는 handle_boot_enabled=1 + watchdog.open_timeout=(예: 120 s, 정상 부팅 시간의 2~3배)로 "유저 공간이 끝내 안 뜨면 리셋".
  2. nowayout을 켠다(CONFIG_WATCHDOG_NOWAYOUT=y 또는 드라이버 모듈 인자). 업데이트 중에도 watchdog은 돈다 — OTA 스크립트도 watchdog을 고려해야 한다.
  3. kick하는 주체가 "건강"을 증명하게 한다. systemd라면 RuntimeWatchdogSec=로 PID 1을, 각 핵심 서비스는 WatchdogSec=와 sd_notify("WATCHDOG=1")로. 핵심은 제어 루프가 실제로 일을 마친 지점에서만 WATCHDOG=1을 보내는 것 — 별도 스레드에서 무조건 보내면 SSD의 "ISR에서 kick" 실수를 반복하는 것이다.
  4. pretimeout으로 증거를 남긴다. pretimeout governor panic + pstore/ramoops(또는 kdump)로 리셋 직전 스택을 저장. 현장 리셋의 원인 분석이 가능해진다.
  5. 리셋 원인을 센다. 부팅 때 WDIOC_GETBOOTSTATUS(또는 SoC의 reset reason 레지스터)를 읽어 텔레메트리로. 짧은 시간에 여러 번 watchdog 리셋이 나면 리셋 루프 탈출 정책(안전 모드 부팅, A/B 이전 슬롯으로 롤백 — L 모듈의 업데이트와 연결).
  6. 타임아웃 값은 측정으로 정한다. 최악의 정상 지연(대용량 파일 fsync, 카메라 재협상, 부팅 직후 부하)보다 길게, 위험이 커지기 전보다 짧게. 리셋 루프를 만드는 너무 짧은 타임아웃이 가장 흔한 사고다.
  7. 물리 안전은 Linux에 맡기지 않는다. 모터 컨트롤러는 CAN heartbeat가 끊기면 스스로 정지(I10, Q 모듈), E-stop은 하드웨어 회로로.

7.2 상태 LED 설계 — 현장 기술자의 유일한 디버거#

  • 부팅 단계별 패턴: 부트로더(상시 켜짐, default-state = "keep"으로 커널이 끄지 않게) → 커널(heartbeat 트리거 — 커널이 멈추면 heartbeat도 멈춘다는 점이 오히려 진단 정보다) → 앱 정상(상시) → 에러 코드(pattern 트리거로 "깜빡임 N회").
  • panic-indicator를 붙인 빨간 LED는 panic 때 깜빡인다. 원격 로그가 없는 현장에서 "커널 panic인지, 앱 문제인지"를 LED 하나로 가른다.
  • 네트워크 LED는 netdev 트리거(가능하면 PHY 하드웨어 오프로드)로 — CPU 부하 없이 링크/트래픽 표시.
  • 유저 공간에서 LED를 직접 토글하는 루프(while true; echo 1; sleep; echo 0)는 금물. 트리거를 고르고 파라미터만 쓴다.

7.3 팬·백라이트 PWM — thermal과 연결#

pwm-fan은 #cooling-cells로 thermal cooling device가 된다(I4). DT의 thermal zone trips/cooling-maps가 온도에 따라 cooling-levels 인덱스를 고르고, pwm-fan이 그 값을 duty로 바꾼다. 예제 7에서 pwm-fan이 probe 때 최대 duty로 시작한 것은 "thermal이 준비되기 전에는 최대 냉각"이라는 안전 기본값이다. 백라이트는 pwm_bl의 brightness-levels 테이블(사람 눈은 로그 스케일이라 선형 duty가 아닌 테이블을 쓴다)과 default-brightness-level.

PWM 주기 선택 감각: 4선 팬은 25 kHz(40 us — 예제의 pwms = <... 40000 ...>가 이 값), 백라이트는 깜빡임이 안 보이도록 수 kHz 이상, 서보는 50 Hz(20 ms) + 1~2 ms 펄스, 부저는 소리 주파수 그 자체.

9. 면접에서 이렇게 말한다#

Q. How would you design the watchdog strategy for a robot running embedded Linux?

A. 계층으로 설계한다. 맨 아래는 부트로더가 켜는 하드웨어 watchdog(nowayout, open_timeout으로 부팅 실패도 잡음). 그 위에서 systemd RuntimeWatchdogSec가 PID 1을, 핵심 서비스는 WatchdogSec + sd_notify로 감시하는데, ping은 제어 루프가 실제로 deadline 안에 일을 마쳤을 때만 보낸다. pretimeout governor panic + pstore로 리셋 직전 덤프를 남기고, 부팅 때 bootstatus를 텔레메트리로 올려 리셋 횟수를 센다. 반복되면 안전 모드나 A/B 롤백. 그리고 모터 MCU는 CAN heartbeat가 끊기면 Linux와 무관하게 스스로 정지한다.

I'd layer it. At the bottom, a hardware watchdog that the bootloader enables, with nowayout and an open timeout so a hang during boot also resets the board. Above that, systemd's RuntimeWatchdogSec pets the hardware from PID 1, and each critical service has WatchdogSec and only sends WATCHDOG=1 from the point where its control loop actually finished its work on time — not from a side thread. I'd enable a pretimeout with the panic governor plus pstore so every reset leaves a crash record, read the boot status at startup and report watchdog resets as telemetry, and fall back to a safe mode or the previous A/B slot if resets repeat. Independently, the motor controllers run their own watchdog on the CAN heartbeat, so the actuators stop safely even if Linux is gone.

꼬리 질문: "timeout 값은 어떻게 정하나?" → 정상 최악 지연(부팅 직후, 대용량 fsync, 카메라 재협상)을 측정하고 여유를 둔다. 너무 짧으면 리셋 루프.

Q. What is the magic close feature, and what does nowayout change?

A. /dev/watchdog은 열면 시작하고, 닫는다고 멈추지 않는다. 마지막에 'V'를 쓰고 닫아야만 멈춘다 — 데몬이 죽어서 fd가 닫힌 경우와 의도적 종료를 구분하려는 것이다. nowayout이면 'V'도 무시돼서 한 번 시작된 watchdog은 절대 멈추지 않는다. 실습에서 i6300esb로 'V' 없이 닫으면 5초 뒤 실제 리셋, nowayout=1이면 'V'를 써도 리셋되는 것을 확인했다.

Opening the device starts the watchdog, and closing it does not stop it. Only writing the character 'V' right before close stops it, so a daemon that crashes is distinguished from one that shuts down on purpose — the kernel prints "watchdog did not stop" and keeps counting. With nowayout, even the magic close is ignored; once started it can never be stopped, which is what you want in a product.

Q. What's the difference between the RTC and the system clock, and how do they stay in sync?

A. 시스템 시계는 커널이 ns 단위로 유지하고 전원이 꺼지면 사라진다. RTC는 배터리로 초 단위를 유지한다. 부팅 때 hctosys로 RTC → 시스템 시계 한 번, 이후 NTP/PTP가 시스템 시계를 맞추고, 동기화 상태면 커널이 약 11분마다 systohc로 RTC에 되쓴다. RTC 드라이버가 늦게 뜨면 초기 로그가 1970년이 된다.

The system clock is kept by the kernel at nanosecond resolution and is lost at power-off; the RTC is a battery-backed, one-second-resolution clock. At boot the kernel copies RTC to system time once (hctosys). After that NTP or PTP disciplines the system clock, and when it's marked synchronized the kernel writes it back to the RTC about every eleven minutes. If the RTC driver probes late — say it's an I2C module — everything before it is stamped 1970.

Q. How does an RTC alarm wake the system from suspend?

A. 드라이버가 probe에서 device_init_wakeup()으로 wakeup 가능을 선언하고, suspend 때 알람 IRQ를 wake IRQ로 켠다. 유저는 RTC_WKALM_SET이나 sysfs wakealarm, rtcwake로 알람을 건다. IRQ가 오면 rtc_update_irq()가 이벤트를 올리고 PM core가 resume한다. QEMU virt에서 rtcwake -m freeze -s 5로 s2idle에서 깨어나는 것과 wakeup_sources의 카운트를 확인했다.

The driver declares itself wakeup-capable with device_init_wakeup and arms its alarm interrupt as a wake IRQ on suspend. User space sets the alarm with RTC_WKALM_SET, the wakealarm sysfs file, or rtcwake. When it fires, the ISR calls rtc_update_irq, a wakeup event is recorded, and the PM core resumes. I verified it in QEMU with rtcwake into s2idle and checked the pl031 entry in wakeup_sources.

Q. brightness_set vs brightness_set_blocking — when do you use which?

A. 트리거가 타이머·softirq 문맥에서 밝기를 바꾸므로 brightness_set은 절대 잠들면 안 된다 — MMIO GPIO용. I2C/SPI LED IC처럼 쓰기가 잠들면 _blocking을 구현하고, core가 ordered workqueue에서 대신 부른다. 실습에서 sysfs 쓰기조차 kworker 문맥에서 불리는 걸 확인했다.

Triggers change brightness from timer or softirq context, so brightness_set must never sleep — it's for memory-mapped GPIOs. If the write goes over I2C or SPI you implement brightness_set_blocking, and the LED core defers it to its ordered workqueue. In my test even a sysfs write arrived in a kworker.

Q. Why does the PWM API use an atomic pwm_state, and what goes wrong with sysfs?

A. period·duty·polarity·enable을 한 번에 넘겨야 드라이버가 하드웨어 특성에 맞게 글리치 없이 바꿀 수 있다(주기 끝에서 반영 등). sysfs는 파일 하나씩 쓰므로 중간 상태가 생기고, 켜진 상태에서 period를 duty보다 작게 먼저 쓰면 EINVAL이다. 줄일 땐 duty 먼저.

The consumer passes period, duty, polarity and enable as one state, so the driver can apply it without glitches — for example latching it at the end of the current period. Sysfs writes one attribute at a time, so you go through intermediate states; shrinking the period below the current duty while enabled returns EINVAL. Lower the duty first, then the period.

Q. When is a software PWM (pwm-gpio) acceptable?

A. 정확도는 "가장 짧은 구간 대비 타이머 지연"이 결정한다. LED·부저·50 Hz 서보처럼 ms 단위면 괜찮지만, kHz 모터 제어는 안 된다. 잠드는 GPIO에는 아예 못 쓴다. 측정해 보니 20 ms 주기는 ±3%p, 1 ms 주기에서는 10% 펄스가 대부분 사라졌다(에뮬레이터라 절대값보다 경향).

Its accuracy is bounded by timer latency relative to the shortest phase of the waveform. Fine for LEDs, buzzers or a 50 Hz servo; not for kilohertz motor control, and it refuses sleeping GPIOs outright. In my emulated measurement, a 20 ms period stayed within about three points of duty, while at 1 ms most of the 10 % pulses disappeared.

Q. The bootloader enables the watchdog. What happens before user space opens it?

A. 드라이버가 WDOG_HW_RUNNING을 알리면 core의 watchdogd 스레드가 대신 ping한다(handle_boot_enabled). watchdog.open_timeout을 주면 그 시간 안에 유저가 열지 않을 때 리셋이 나도록 ping을 멈춘다. 기본값 0이면 무한정 ping하므로 제품에서는 설정해야 한다.

If the driver reports the hardware as already running, the watchdog core's kernel worker keeps pinging it until user space opens the device. With watchdog.open_timeout set, the core stops pinging so that the board resets if nobody opens it in time — I measured the reset landing exactly at the open deadline. The default of zero pings forever, which hides a boot that hangs in user space.

12. 요약 & 체크리스트#

LED·PWM·RTC·watchdog은 "드라이버는 작은 ops 구조체만, 나머지는 core가"라는 Linux 프레임워크 원칙의 가장 작은 예다. LED class는 밝기 콜백과 트리거를 분리하고, 잠드는 하드웨어는 brightness_set_blocking으로 workqueue에 맡긴다. PWM은 period·duty·polarity·enable을 struct pwm_state 하나로 원자적으로 적용하며, 소프트웨어 PWM의 정확도는 타이머 지연이 결정한다(실측: 20 ms는 양호, 1 ms는 붕괴). RTC는 부팅 때 한 번 시스템 시계의 출처가 되고, 알람은 read()를 깨우거나 suspend에서 시스템을 깨운다. watchdog은 open이 시작, 'V' close만이 정지, nowayout이면 정지 불가이며, core가 부팅 중 보충 ping·open_timeout·pretimeout을 제공한다. 제품의 watchdog은 HW → PID 1 → 서비스 → 앱 헬스, 그리고 Linux와 독립된 모터 MCU까지 계층으로 설계한다.
