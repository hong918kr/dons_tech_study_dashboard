이 노트를 다 읽으면: Linux 서브시스템(프레임워크)의 네 부품 — core, ops 구조체, 등록 API, class/sysfs + 표준 uAPI — 을 그림 한 장으로 설명할 수 있다 · RTC·LED·input·watchdog 네 프레임워크의 "할당 → ops 채우기 → 등록 → core가 콜백" 흐름을 6.18 소스 줄 번호와 함께 비교할 수 있다 · "core가 내 op를 어떤 context에서 부르나"를 알고 brightness_set에서 잠들면 커널이 죽는 이유를 실측으로 보여 줄 수 있다 · 같은 온도계를 misc+ioctl과 hwmon으로 두 번 짜 보고 "왜 char device를 직접 만들면 안 되나"를 숫자로 답할 수 있다 왜 필요한가: 드라이버 설계 면접의 단골 질문이 "Why not just write a char device with an ioctl?"이고, 실무에서 첫 패치를 올렸을 때 메인테이너가 가장 먼저 다는 리뷰 코멘트도 "This should be an IIO/hwmon/LED driver"다 Don 기준 난이도: 함수 포인터 테이블로 HAL을 추상화하는 것(CMSIS-Driver의 ARM_DRIVER_USART, 펌웨어의 NAND/PHY 드라이버 vtable)은 이미 안다 / 새로 배울 부분은 Linux core가 그 vtable 위에 sysfs·uevent·PM·락·표준 툴까지 묶어 준다는 점, 그리고 core가 정한 호출 context 규칙 선행 노트: G1(드라이버 종류와 프레임워크 결정표), G2(디바이스 모델), G3(platform driver), G4(char device), G7(misc device), G8(sysfs) — 이후 I2(IIO), I3(input), I4(hwmon), I9(LED·RTC·watchdog)로 이어진다

0. 큰 그림 — 이게 왜 필요한가#

G1에서 "드라이버 대부분은 char/block/net 위에 올라간 서브시스템 드라이버"라는 결론과, "내 장치는 어느 프레임워크?" 결정표를 이미 봤다. G4에서는 cdev와 file_operations로 char device를 직접 만드는 법을 배웠다. 이 노트는 그 사이의 질문에 답한다.

  • 프레임워크는 어떻게 설계되어 있나 — 모든 프레임워크에 공통인 뼈대는 무엇인가.
  • 드라이버는 프레임워크에 무엇을 넘기고 무엇을 돌려받나.
  • core는 내 콜백을 언제, 어떤 context에서, 어떤 락을 잡고 부르나.
  • 그리고 G4처럼 직접 만든 char device가 왜 대부분의 경우 틀린 답인가.

Don의 펌웨어 경험으로 번역하면 이렇다. SSD 펌웨어에서 NAND 벤더가 바뀌면 nand_ops 같은 함수 포인터 테이블만 새로 채우고, FTL·에러 처리·스케줄러는 그대로 썼을 것이다. ARM의 CMSIS-Driver도 같다. ARM_DRIVER_USART는 Initialize, Send, Receive, Control 같은 함수 포인터를 담은 구조체이고, 미들웨어는 칩이 무엇이든 그 구조체만 부른다. Linux 프레임워크는 이 vtable 패턴에 운영체제 기능을 덧붙인 것이다. 드라이버가 rtc_class_ops 같은 테이블을 채워 등록하면, core는

  1. /dev/rtcN char device와 /sys/class/rtc/rtcN/ sysfs 디렉터리를 만들고,
  2. uevent를 보내 udev/mdev가 노드를 만들게 하고,
  3. 유저가 ioctl(RTC_RD_TIME)을 하면 자기 mutex를 잡은 뒤 내 read_time을 부르고,
  4. suspend/resume 때 알아서 시간 보정을 하고,
  5. hwclock 같은 이미 존재하는 유저 툴이 내 칩에서 바로 돌게 해 준다.

드라이버가 쓰는 코드는 "레지스터를 읽어 struct rtc_time을 채우는 함수" 하나뿐이다.

그림 1 — 프레임워크의 해부. 드라이버는 왼쪽 네 칸만 쓴다. 가운데 core와 오른쪽 uAPI·툴은 커널과 생태계가 이미 갖고 있다.

1. 프레임워크의 해부 — 네 부품#

1.1 직관 — "드라이버는 플러그인, core가 프로그램"#

G4에서 만든 char device는 드라이버가 프로그램이었다. open부터 read·ioctl·락·f_pos·노드 이름·권한까지 드라이버가 전부 정했다. 프레임워크에서는 반대다. core가 프로그램이고 드라이버는 플러그인이다. 유저와 대화하는 쪽(syscall, sysfs, 이벤트 포맷)은 core가 독점하고, 드라이버는 "칩에 실제로 접근하는 함수"만 플러그인으로 꽂는다. 소프트웨어 공학 용어로 제어의 역전(inversion of control)이다.

1.3 드라이버의 생애 — 할당 → 채우기 → 등록 → 콜백#

모든 프레임워크 드라이버의 probe는 거의 같은 모양이다.

(위 코드는 패턴을 보이는 의사 코드다. foo_라는 API는 없다. 실제 API 이름은 §2 표에 있다.)

세 가지 규칙이 따라 나온다.

  1. 등록은 맨 마지막. ③이 끝나는 순간 유저 공간이 /dev/rtcN을 열 수 있고 core가 ④를 부를 수 있다. 그 전에 하드웨어 초기화·IRQ 등록·private data 설정이 끝나 있어야 한다. G4의 "준비 다 하고 마지막에 공개(cdev_add)"와 같은 원칙이다.
  2. ops 구조체는 const이고 정적이다. 장치가 여러 개여도 ops는 하나를 공유하고, 장치별 상태는 dev_get_drvdata()나 container_of()로 찾는다. RTC ops는 struct device *(부모 장치)를 받으므로 dev_get_drvdata(dev)로, LED ops는 struct led_classdev *를 받으므로 container_of(cdev, struct my_led, cdev)로 찾는다.
  3. NULL인 op = 그 기능 없음. core는 op가 NULL이면 그 기능을 끄거나 uAPI에서 숨긴다. 예를 들어 RTC core는 등록 시 set_alarm이 없으면 알람 기능 비트를 지운다(drivers/rtc/class.c:403의 clear_bit(RTC_FEATURE_ALARM, rtc->features)). 그러면 sysfs wakealarm 속성도 나타나지 않는다(§5의 실측).

3. "core는 내 op를 어떤 context에서 부르나"#

3.1 직관 — 콜백의 계약서에는 "언제 불릴지"가 적혀 있다#

펌웨어에서 콜백을 등록할 때(예: DMA 완료 콜백, 타이머 콜백) Don은 "이건 ISR 안에서 불리니까 블로킹 API를 쓰면 안 된다"를 습관처럼 확인했을 것이다. Linux 프레임워크도 똑같다. 단, 누가 부르는지가 core 안에 숨어 있어서 드라이버 코드만 보면 모른다. 그래서 각 ops 구조체의 주석과 core 소스가 "계약서"다. 이 계약을 어기면 테스트에서는 안 터지다가 특정 트리거·특정 타이밍에서만 커널이 죽는다.

그림 4 — "core가 내 op를 어떤 context에서 부르나" 지도 (6.18.55 소스 기준). 한 op가 여러 곳에서 불리면 가장 나쁜 context가 그 op의 규칙이 된다. brightness_set이 sysfs에서는 task context로 불려도, 트리거에서 softirq로 불릴 수 있으므로 "잠들기 금지"다.

3.5 예제 6 — 계약을 어기면: brightness_set에서 msleep()#

무엇을 확인하나: sleepbug=1이면 드라이버가 brightness_set 안에서 msleep(1)을 한다(I2C LED 컨트롤러를 brightness_set으로 잘못 등록한 상황의 재현). sysfs 쓰기(task)에서는 멀쩡하다가 timer 트리거(softirq)에서 무슨 일이 생기는지 본다. 커널이 죽을 수 있으므로 TMO=40, 콘솔 로그를 다 보려고 loglevel=8을 붙였다.

같은 실행의 끝부분(약 40줄 생략):

(quiet만 붙인 첫 실행에서는 같은 BUG 뒤에 Unable to handle kernel paging request at virtual address 0040041ff96962a0라는 다른 Oops가 났고 마지막 panic 문장은 같았다. 잠들면 안 되는 곳에서 잠든 뒤의 증상은 실행마다 다르다. 첫 줄 BUG: scheduling while atomic이 진짜 원인이다.)

출력에서 볼 것:

  • #1(sysfs, task context)에서는 msleep이 아무 문제 없이 지나갔다. 그래서 이런 버그는 "echo로 테스트했는데 잘 되던데요"로 리뷰를 통과한다.
  • 트리거가 켜지자마자 첫 softirq 호출(#2)에서 BUG: scheduling while atomic. 스택을 아래에서 위로 읽으면 Don이 아는 그림 그대로다: idle 루프(default_idle_call) → IRQ 예외 진입(el1h_64_irq) → IRQ 끝에서 softirq 처리(__irq_exit_rcu → handle_softirqs → run_timer_softirq) → LED core의 led_timer_function → 내 i1_set → msleep → schedule. 펌웨어로 치면 타이머 ISR 안에서 RTOS vTaskDelay()를 부른 것이다.
  • 0x00000102는 그 순간의 preempt_count다. 0x100이 "softirq 처리 중"(SOFTIRQ_OFFSET) 비트, 0x2는 선점 비활성 카운트다. 0이 아니므로 "atomic".
  • 결국 idle 태스크(swapper, PID 0)가 잠들려다 Attempted to kill the idle task! panic. 랩 커널은 DEBUG_ATOMIC_SLEEP이 꺼진 일반 커널이라 might_sleep() 경고 없이 바로 이 지경이 됐다. 디버그 커널(Image-dbg, CONFIG_DEBUG_ATOMIC_SLEEP=y)이라면 #1처럼 문제가 없어 보이는 경로에서도 잘못된 context를 더 일찍 잡아 준다(M 모듈).

교훈: op의 context 규칙은 core의 주석과 소스가 정한다. 드라이버 작성자는 "내 테스트에서 어떤 context로 불렸나"가 아니라 "core가 어떤 context에서 부를 수 있나"로 판단해야 한다.

4. 같은 온도계를 두 번 — (a) misc + ioctl vs (b) hwmon#

5.1 내 RTC 드라이버 (공통 뼈대 제외 전부)#

"하드웨어"는 시스템 시계에 대한 오프셋 하나다. 실제 RTC 칩이라면 i1_read_time이 I2C로 BCD 레지스터 7개를 읽어 struct rtc_time을 채우는 자리다(rtc-ds1307.c, rtc-pcf8563.c가 그 모양이다).

코드를 읽는 법: probe는 §1.3의 네 단계 그대로다. range_max는 "이 칩이 표현할 수 있는 최대 시각(초)"이다. core는 이 범위 밖의 set_time을 드라이버에 넘기기 전에 거부한다. 그리고 범위가 0이 아니면 sysfs range 속성을 보여 준다(§1.5). 오프셋을 3600으로 시작한 것은 다른 RTC와 구분하려는 장치일 뿐이다.

비교 대상인 커널의 drivers/rtc/rtc-test.c(201줄)는 같은 구조에 알람 타이머를 더한 것이다. 모듈 init에서 platform 장치 3개를 만들고(:160-167), probe에서 id == 0이면 알람 없는 ops(test_rtc_ops_noalm), 나머지는 알람 있는 ops를 주고 device_init_wakeup()을 부른다(:129-136). 이 차이가 sysfs에 어떻게 드러나는지 보자.

출력에서 볼 것:

  • input: H: Handlers=kbd event0 — 하나의 input_dev에 핸들러 두 개(콘솔 키보드 kbd, 유저용 evdev → event0)가 붙었다(§2.4). B: EV=3은 EV_SYN(비트 0)과 EV_KEY(비트 1), B: KEY=10000000000000 0은 keybit 비트맵에서 비트 116(KEY_POWER) 하나다. 드라이버(gpio-keys)가 선언한 capability가 그대로 공개된다. inhibited 속성은 "이 장치의 이벤트를 잠시 무시하라"는 표준 스위치로, 드라이버가 구현하지 않아도 core가 준다.

  • WDIOC_GETTIMELEFT가 EOPNOTSUPP: softdog은 선택 op get_timeleft를 채우지 않았다. core가 NULL op를 보고 표준 에러를 돌려준다(§1.3 규칙 3). 유저 프로그램은 이것을 보고 기능 없음으로 처리하면 된다.
  • magic close: 'V'를 쓰고 닫았으므로 워치독이 멈췄고 게스트가 리셋되지 않았다. 'V' 없이 닫았다면 softdog이 7초 뒤 리부트를 걸었을 것이다(이 노트에서는 실행하지 않았다).
  • 이 wdt_info 프로그램은 softdog 전용 코드가 한 줄도 없다. i.MX의 imx2_wdt, TI의 rti_wdt, PC의 i6300esb에서도 그대로 돈다. systemd의 RuntimeWatchdogSec=, BusyBox watchdog 데몬도 같은 ioctl을 쓴다.

그럼 char device(misc)는 언제 쓰나#

  • 맞는 프레임워크가 정말 없을 때: FPGA 커스텀 가속기, 특정 보안 칩의 독자 프로토콜, 펌웨어 메일박스처럼 "표준 의미"가 없는 장치. 이때도 설정·상태는 sysfs 속성으로 빼고, ioctl은 Documentation/userspace-api/ioctl/ioctl-number.rst에 번호를 등록하고, Documentation/ABI/에 문서를 쓴다.
  • 프레임워크가 있지만 일부만 맞을 때: 먼저 프레임워크에 넣고, 빠진 기능은 그 프레임워크의 확장 지점(RTC param_get/param_set, hwmon extra_groups, IIO 확장 속성, V4L2 컨트롤)을 쓴다. 정말 새 기능이면 프레임워크 자체를 확장하는 패치를 낸다.
  • UIO/VFIO: 유저 공간 드라이버가 정답인 경우(DPDK류 고속 NIC, 단순 FPGA 레지스터 맵)는 char device를 직접 짜지 않고 UIO/VFIO 프레임워크를 쓴다. 이것도 결국 "프레임워크에 등록"이다.

9.2 구조체 관계 — 프레임워크 객체 안의 struct device#

모든 프레임워크 객체는 안에 struct device를 품고 있다(struct rtc_device의 dev, struct input_dev의 dev, watchdog_core_data의 dev, LED는 led_cdev->dev 포인터). 그래서 G2의 디바이스 모델 기능 — sysfs 디렉터리, uevent, class 링크, 부모-자식 관계, PM 콜백 순서 — 을 프레임워크가 자동으로 상속한다. 예제 7·9의 경로가 이것을 보여 준다.

ops 콜백이 struct device *를 받는 프레임워크(RTC, hwmon)는 부모(platform/I2C 장치)를 넘겨준다. __rtc_read_time()의 rtc->ops->read_time(rtc->dev.parent, tm)가 그 증거다. 그래서 드라이버는 probe에서 dev_set_drvdata(&client->dev, priv) 해 둔 private data를 콜백에서 dev_get_drvdata(dev)로 바로 꺼낸다.

10.3 장면 3 — PMIC 하나가 프레임워크 네 개#

i.MX8·AM62 보드의 PMIC는 레귤레이터 + RTC + 워치독 + 전원 버튼을 한 칩에 갖는다. 드라이버도 한 덩어리 char device가 아니라 MFD 코어 드라이버가 자식 platform 장치들을 만들고, 각 자식이 regulator, rtc_class_ops, watchdog_ops, input_dev로 해당 프레임워크에 등록한다(예: rtc-rk808.ko, rtc-da9063.ko, rtc-tps6594.ko가 modules-sub에 있다). 그러면 hwclock, systemd 워치독, evtest가 PMIC 기능을 각각 표준으로 쓴다. "칩 하나 = 드라이버 하나 = char device 하나"라는 펌웨어식 사고를 버려야 하는 지점이다.

10.4 장면 4 — 하드웨어 워치독과 systemd#

생산 장비는 HW 워치독으로 행(hang)을 잡는다. 드라이버는 watchdog_ops의 start/stop/ping과 max_hw_heartbeat_ms만 준다. 유저 공간은 systemd RuntimeWatchdogSec=30s 한 줄로 /dev/watchdog0을 열고 킥한다. HW 최대 타임아웃이 2초밖에 안 되는 칩이어도 core의 watchdogd FIFO 워커가 그 사이를 메워 준다(§2.5). 예제 3의 옛 드라이버처럼 misc로 짰다면 이 "짧은 HW 타임아웃 보정"을 칩마다 다시 짜야 했다.

12. 면접에서 이렇게 말한다#

Q. "Why shouldn't I just write a char device with an ioctl for my temperature sensor?"

A. char device를 직접 만들면 커널 코드는 비슷하지만 나머지 전부를 새로 만들어야 한다. 전용 ioctl ABI(영원히 유지), 전용 유저 툴, 락, 권한, PM, 문서. hwmon에 등록하면 temp1_input 같은 표준 sysfs, sensors·thermal 연동, core 락을 공짜로 받는다. 실제로 같은 온도계를 둘 다 짜 보니 커널 쪽은 88줄 대 85줄로 같았고, 유저 쪽은 33줄 대 0줄이었다.

A framework gives you the user-space ABI, tooling, locking and power management for free. If I write a misc device with a private ioctl, the kernel code is about the same size — I measured 88 versus 85 lines for the same thermometer — but every consumer needs my header and my CLI, I own a new ABI forever, and the patch would be rejected upstream with "please use hwmon". With hwmon, cat temp1_input and lm-sensors just work.

꼬리 질문: "그럼 char device는 언제 쓰나?" → 맞는 프레임워크가 없을 때(FPGA 커스텀 가속기 등). 그때도 misc + sysfs + Documentation/ABI 문서, ioctl 번호 등록.

Q. "What does a typical subsystem driver look like?"

A. 네 단계다. 프레임워크 객체 할당(devm_rtc_allocate_device), ops 테이블과 능력 채우기, probe 마지막에 등록, 그 뒤로는 core가 내 콜백을 부른다. core는 등록 때 class 장치·sysfs·cdev·uevent를 만들고, 호출 때 락을 잡고 입력을 검증한다.

Allocate the framework object, fill in a const ops table and capability fields, register at the very end of probe, and from then on the core calls you. Registration creates the class device, sysfs attributes, the char device if there is one, and the uevent. On every call the core takes its own lock, validates input and then invokes my op — for RTC that's ops_lock around read_time.

Q. "In which context is an LED brightness_set callback called? What if your LED is on I2C?"

A. brightness_set은 아무 context에서나 불린다. 트리거 타이머에서는 softirq다. I2C 전송은 잠들기 때문에 brightness_set_blocking을 써야 하고, 그러면 core가 호출을 ordered 워크큐의 kworker로 옮긴다. 실제로 brightness_set에서 msleep을 했더니 timer 트리거 첫 호출에서 scheduling while atomic이 나고 panic이 났다.

brightness_set must not sleep because triggers call it from timer softirq — I saw swapper/0 in softirq context in my test. For an I2C LED you implement brightness_set_blocking instead; the LED core then defers the call to its ordered leds workqueue, so it runs in a kworker. Sleeping in the non-blocking op gave me "BUG: scheduling while atomic" with led_timer_function on the stack.

꼬리 질문: "어떻게 확인했나?" → 콜백 안에서 in_serving_softirq()와 current->comm을 찍었다. 디버그 커널이라면 CONFIG_DEBUG_ATOMIC_SLEEP이 might_sleep()으로 미리 잡는다.

Q. "What locking does the framework give you, and what do you still need?"

A. core가 장치 단위로 op 호출을 직렬화하는 경우가 많다. RTC는 ops_lock, watchdog은 wd_data->lock, hwmon(6.18)은 hwdev->lock. 그래서 같은 장치의 op끼리는 겹치지 않는다. 드라이버 락이 필요한 것은 IRQ 핸들러와 공유하는 상태나, 한 칩을 여러 프레임워크가 공유할 때(MFD)다.

Most small frameworks serialize ops per device — RTC holds ops_lock, watchdog holds wd_data->lock, hwmon holds its device mutex. I still need my own lock for state shared with my IRQ handler, or for a register bus shared between MFD children; regmap usually provides that.

Q. "How does user space find and use an RTC you wrote, without any code from you?"

A. core가 /dev/rtcN(major는 rtc class 하나)과 /sys/class/rtc/rtcN을 만들고 uevent를 보낸다. hwclock은 표준 RTC_RD_TIME/RTC_SET_TIME ioctl을 쓰므로 그대로 동작한다. 30줄짜리 드라이버로 확인했다.

The RTC core creates /dev/rtcN and the sysfs directory and emits a uevent; udev or mdev creates the node. hwclock uses the standard RTC_RD_TIME and RTC_SET_TIME ioctls, which the core translates into my read_time and set_time. I verified hwclock -w landing in my set_time with a thirty-line provider.

Q. "What is the watchdog core actually doing for you?"

A. /dev/watchdogN와 호환용 /dev/watchdog를 만들고, open = 시작, write/ioctl = 킥, magic close, WDIOC_* ioctl 전부, nowayout, HW 타임아웃이 짧을 때 hrtimer + FIFO kthread로 대신 킥하기까지 한다. 6.18 소스에서 옛 misc 방식 워치독 47개 중 46개가 WDIOC_GETSUPPORT를 직접 구현했고 core를 쓰는 130개는 0개다.

It owns the whole user ABI — open starts it, writes and WDIOC_KEEPALIVE ping it, magic close, nowayout, timeouts — and if the hardware's max timeout is shorter than what user space asked for, it keeps the hardware alive with an hrtimer and a SCHED_FIFO kthread. In 6.18, 46 of the 47 legacy misc-based watchdog drivers re-implement WDIOC_GETSUPPORT; none of the 130 core-based ones do.

Q. "Why is /dev/input/event0 not created by the input driver?"

A. input은 드라이버와 유저 인터페이스 사이에 핸들러 계층이 있다. 드라이버는 input_dev만 등록하고, evdev 핸들러가 붙으면서 eventN char device를 만든다. 그래서 한 버튼이 콘솔(kbd)과 evdev에 동시에 연결된다.

Input has a handler layer: the driver registers an input_dev, and handlers such as evdev, kbd or joydev attach to it. evdev's connect callback creates the eventN char device, so the same button can feed the console keyboard handler and user space at the same time.

15. 요약 & 체크리스트#

Linux 프레임워크는 펌웨어의 vtable HAL에 운영체제 기능을 얹은 것이다. 드라이버는 프레임워크 객체를 할당하고, const ops 테이블과 능력을 채우고, probe 마지막에 등록한다. 그 순간 core가 class 장치·sysfs 속성·char device·uevent를 만들고, 이후 유저의 표준 uAPI 호출을 자기 락을 잡은 채 내 콜백으로 번역한다. 콜백이 어떤 context에서 불리는지는 core가 정하며, LED brightness_set처럼 softirq에서 불리는 op에서 잠들면 커널이 죽는다(예제 6). 같은 온도계를 misc+ioctl과 hwmon으로 짜 보면 커널 코드는 같지만 유저가 받는 것은 0 대 표준 속성 5개, 유저 코드 33줄 대 0줄이다. watchdog 트리의 옛 드라이버 47개가 같은 ioctl을 46번 다시 구현한 것이 프레임워크가 없을 때의 비용이다. char device를 직접 만드는 것은 맞는 프레임워크가 없을 때의 마지막 수단이다.
