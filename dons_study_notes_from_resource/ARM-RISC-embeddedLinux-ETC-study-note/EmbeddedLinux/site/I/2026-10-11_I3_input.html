0. 큰 그림 — 이게 왜 필요한가#

0.1 펌웨어에서는 이렇게 했다#

MCU에서 버튼 하나와 아날로그 조이스틱 하나를 처리하던 코드는 대략 이렇다.

여기에는 네 가지가 섞여 있다.

  1. 하드웨어 접근: 어느 핀, 어느 ADC 채널, 엣지 IRQ — 보드마다 다르다.
  2. 신호 정리: 디바운스, 데드존(노이즈 무시) — 장치 종류마다 비슷하다.
  3. 이벤트 표현과 큐: EVT_BTN | lvl 같은 사설 인코딩, 링버퍼, 오버플로 처리.
  4. 소비자: UI 태스크, 비상 정지 로직, 디버그 콘솔이 같은 큐를 나눠 읽는다.

Linux input 서브시스템은 3·4를 전 시스템 공통 규격으로 만들었다. 이벤트는 모두 struct input_event {time, type, code, value} 한 가지 모양이고, 큐는 읽는 프로세스마다 하나씩 커널(evdev)이 들고 있으며, 키 상태·자동 반복·노이즈 필터(fuzz)도 input core가 해 준다. 드라이버는 1(하드웨어)과 일부 2(디바운스)만 맡는다. 그래서 같은 앱(evtest, libinput, Qt, 로봇 텔레옵 노드)이 GPIO 버튼, USB 게임패드, I2C 터치, 가상 장치를 구별 없이 읽는다.

0.2 Linux의 3층 구조 — 드라이버, input core, 핸들러#

그림 1 — input 서브시스템의 3층. 아래 드라이버는 하드웨어를 읽고 input_dev에 이벤트를 보고만 한다. 가운데 input core가 상태·필터·배달을 맡고, 위 핸들러가 이벤트를 각자의 유저 인터페이스로 바꾼다. 장치 하나에 핸들러 여러 개가 동시에 붙는다(전원 키 하나가 kbd와 evdev 둘 다로 간다). uinput은 "유저 프로그램이 원천인 드라이버"다.

핵심 단어 세 개:

  • struct input_dev: 입력 장치 하나. "나는 EV_KEY의 KEY_POWER를 낼 수 있다", "ABS_X는 0~1023이다" 같은 capability 비트맵과 현재 상태를 가진다. 드라이버가 만든다.
  • struct input_handler: 이벤트를 받아 어딘가로 내보내는 소비자. evdev, kbd(VT 콘솔 키보드), sysrq, leds, 그리고 레거시 mousedev(/dev/input/mice), joydev(/dev/input/js0).
  • struct input_handle: 장치 하나와 핸들러 하나를 잇는 연결선. 장치가 등록되면 input core가 모든 핸들러의 id_table과 비교해서(match) 맞으면 handle을 만든다(connect).

비유: input core는 RTOS의 메시지 브로커다. 드라이버(publisher)는 정해진 메시지 형식으로 발행만 하고, 핸들러(subscriber)는 장치 capability로 구독할지 정한다. 펌웨어에서 직접 짜던 evq[] 링버퍼는 evdev가 읽는 fd마다 하나씩 따로 들고 있다.

옛날(2.6 시절)에는 노트북의 가속도계(낙하 감지, 화면 회전)를 EV_ABS 축 3개짜리 input 장치로 내보내는 드라이버가 많았다(lis3lv02d 계열이 대표적이다). 지금 새 센서 드라이버는 거의 다 IIO로 간다. 이유는 다음과 같다.

  • input 이벤트는 "변화했을 때만" 나간다. fuzz 필터와 중복 제거가 값을 버린다. 센서 융합(칼만 필터)에는 모든 샘플과 정확한 샘플 시각이 필요하다.
  • input에는 샘플링 주파수 설정, 하드웨어 FIFO·트리거·DMA 버퍼, 단위 변환(scale/offset) 같은 개념이 없다. IIO에는 다 있다.
  • input 장치는 데스크톱 스택(libinput, 게임 라이브러리)이 자동으로 집어 간다. EV_ABS 축 3개짜리 가속도계가 조이스틱으로 오인되는 문제가 있어서, udev가 ID_INPUT_ACCELEROMETER 태그를 따로 붙여 구분해야 했다.

그래서 이 노트의 조이스틱 축도 "사람이 움직이는 스틱"이다. 로봇의 IMU는 I2 노트(IIO)에서 다룬다. 면접에서 이 구분을 한 문장으로 말할 수 있어야 한다(§14).

1.2 예제 1 — DT 조각: gpio-sim 버튼 4개, i3_btn, gpio-keys, gpio-keys-polled#

무엇을 확인하나: 이 노트의 모든 장치를 DT 하나에 담는다. virt.dts 사본 끝에 #include해서 C 전처리 → dtc로 dtb를 만든다(H4와 같은 방식).

요점:

  • linux,code = <KEY_A>의 KEY_A는 include/dt-bindings/input/input.h가 linux-event-codes.h를 가져와서 쓸 수 있는 매크로다. 유저 공간 헤더 <linux/input-event-codes.h>와 같은 번호(KEY_A=30, KEY_ENTER=28, KEY_P=25, KEY_POWER=116, SW_LID=0)다.
  • gpio-sim 라인은 기본 상태가 pull-down(0)이다. 그래서 버튼은 GPIO_ACTIVE_HIGH로 두고 pull-up = "누름"으로 쓴다. 실제 보드의 버튼은 보통 풀업 + 버튼이 GND로 당기는 active-low다(그때는 GPIO_ACTIVE_LOW만 바꾸면 드라이버는 그대로다 — H4의 논리값/물리값).
  • LID는 일부러 GPIO_ACTIVE_LOW로 뒀다. 핀이 0이면 논리 1 = "덮개 닫힘"이다(§7.3에서 확인).
  • 마지막 블록은 QEMU가 만든 기존 노드 /gpio-keys/poweroff에 wakeup-source 속성만 덧붙인다(경로 참조 문법, D4).

빌드 스크립트와 부팅 스크립트:

i3.sh는 게스트 안에서 도는 시나리오 스크립트다(info, btn, bounce, abs, gpiokeys, uinput, grab, flood). 공통 도우미 세 줄만 먼저 본다.

ev "이름"은 장치 이름으로 /dev/input/eventN을 찾는다. event 번호는 등록 순서라 부팅마다 바뀔 수 있다 — 이름(또는 udev가 만드는 /dev/input/by-path/ 링크)으로 찾는 습관을 들인다. pull 0 pull-up은 gpio-sim 0번 라인의 입력을 1로 만든다(엣지 → IRQ). gpio-sim 칩을 configfs로 만들어도 라인을 흔드는 파일은 같은 sim_gpioN/pull이다. 이 노트는 다른 DT 노드가 phandle(<&i3_sim 0 ...>)로 라인을 참조해야 해서 DT로 칩을 만들었다(configfs로 만든 칩은 DT에서 참조할 수 없다).

게스트에는 BusyBox뿐이라 evtest가 없다. 그래서 evdev uAPI를 쓰는 C 프로그램을 VM에서 gcc -static으로 빌드해 넣는다. 네 개 모두 경고 0개로 빌드됐다.

1.3 예제 2 — 기본 virt의 입력 장치 들여다보기#

무엇을 확인하나: DT를 바꾸지 않은 virt 머신에 입력 장치가 무엇이 있는지 /proc·/sys·/dev로 본다 (boot.sh none info).

/proc/bus/input/devices 한 블록을 줄별로 읽는 법:

줄뜻이 출력에서
I:struct input_id — 버스, VID, PID, 버전Bus=0019 = BUS_HOST(SoC 내장)
N: / P: / U:이름, 물리 경로(phys), 고유 ID(uniq)gpio-keys가 정한 고정 문자열
S:sysfs 경로platform 장치 gpio-keys 아래 input0

B: KEY=지원 키 코드 비트맵, 64비트 word를 높은 쪽부터 공백으로 구분두 번째 word가 0, 첫 word 0x10000000000000 = bit 52 → 64+52 = 116 = KEY_POWER

/proc/bus/input/handlers에서 evdev의 Minor=64는 evdev 노드가 major 13, minor 64부터 시작한다는 뜻이고, /dev/input/event0이 13, 64인 것과 맞는다. sysrq (filter)는 이벤트를 가로채서 먹을 수 있는 필터 핸들러다(Alt+SysRq 조합을 잡아 커널 기능을 실행하고 다른 핸들러에는 안 보낸다).

/sys/class/input에는 input0(장치 자체)과 event0(evdev 핸들러가 만든 char device) 두 개가 있다. input 장치 하나 = inputN 하나, 그 위에 핸들러별 노드라는 그림 1의 구조가 그대로 보인다.

2. 이벤트 모델 — struct input_event 하나로 모든 장치를#

2.1 구조체 — 24바이트짜리 메시지#

유저 공간이 read()로 받는 것은 이 구조체의 배열뿐이다 (include/uapi/linux/input.h).

arm64 유저 공간에서의 메모리 배치:

32비트 유저 공간이 64비트 time_t로 빌드되면(__USE_TIME_BITS64) timeval 대신 __kernel_ulong_t __sec, __usec(각 4바이트)를 쓰고 매크로 input_event_sec/input_event_usec로 접근한다. 그래서 이식성 있는 코드는 ev.time.tv_sec 대신 ev.input_event_sec를 쓴다(이 노트의 i3_evtest가 그렇게 한다). 부호 없는 32비트 초라서 2038년 문제 대신 2106년까지 간다.

시간은 기본이 CLOCK_REALTIME이다. EVIOCSCLOCKID로 CLOCK_MONOTONIC(또는 CLOCK_BOOTTIME)으로 바꿀 수 있다. 이 노트의 출력은 전부 MONOTONIC이라 dmesg 시각과 같은 축에 있다. 이벤트 시각은 드라이버가 input_set_timestamp()로 IRQ 시각을 넣어 주지 않으면 input core가 SYN_REPORT를 처리하는 순간에 찍는다.

2.3 SYN_REPORT — 이벤트를 패킷으로 묶는 경계#

터치스크린이 "X=310, Y=122, 눌림"을 보고한다고 하자. 이걸 세 이벤트로 따로 받으면, X만 바뀐 순간의 반쯤 갱신된 좌표를 읽을 수 있다. 그래서 input은 SYN_REPORT가 나올 때까지의 이벤트를 하나의 원자적 패킷으로 정의한다. 드라이버는 값을 다 보고한 뒤 input_sync()(= SYN_REPORT)를 부른다. 소비자는 SYN_REPORT를 볼 때까지 모았다가 한꺼번에 적용한다.

그림 2 — SYN_REPORT로 나뉜 이벤트 스트림. 패킷 안의 순서에는 의미가 없고, 패킷 경계가 "여기까지가 한 순간의 상태"라는 약속이다. 실제 출력은 §10.1에 있다(같은 패킷의 EV_ABS 900과 EV_KEY 25가 같은 timestamp 2.769650을 가진다).

input core는 이 약속을 커널 안에서도 지킨다. input_event()로 들어온 값은 dev->vals[] 배열에 쌓이기만 하고, SYN_REPORT가 올 때 패킷 통째로 핸들러에 넘어간다(§11). 그리고 내용이 없는 빈 SYN_REPORT는 evdev가 버린다 — 값이 모두 필터링된 패킷은 아예 안 보인다(§6.2).

2.4 EV_ABS와 absinfo — min, max, fuzz, flat, resolution#

절대 축은 값 하나만으로는 의미가 없다. "0~1023 중 512"인지 "0~4095 중 512"인지 알아야 화면 좌표로 바꿀 수 있다. 그래서 축마다 struct input_absinfo가 있다.

2.5 흔한 함정#

  • input_sync()를 빠뜨림: 이벤트가 dev->vals[]에 쌓이기만 하고 유저 공간에 안 나온다. 버퍼가 차면 core가 강제로 넘기지만 패킷 경계가 깨진다. "evtest에 아무것도 안 나온다"의 1순위 원인이다.
  • capability를 선언하지 않은 코드를 보고: input_set_capability()로 등록하지 않은 code는 input_get_disposition()이 조용히 버린다. 에러 메시지도 없다.
  • EV_KEY를 "엣지"로 생각함: value는 엣지가 아니라 상태다. 같은 상태를 두 번 보고하면 두 번째는 사라진다. 반대로 "눌림" 없이 "뗌"만 보고하면 core 입장에서 상태 변화가 없어 사라진다.
  • IMU를 EV_ABS로 내보냄: §0.3. fuzz·중복 제거가 샘플을 버리고, 데스크톱이 조이스틱으로 집어 간다.

5.1 원리 — "마지막 엣지 뒤 N ms 동안 조용하면 그때 읽는다"#

기계식 접점은 닫히는 순간 수 ms 동안 붙었다 떨어졌다를 반복한다(채터링, bounce). 엣지 IRQ를 그대로 보고하면 "한 번 눌렀는데 세 번 눌림"이 된다.

그림 3 — 디바운스 타임라인. 엣지(빨강)마다 타이머를 처음부터 다시 걸고(회색 점선 = 중간에 재시작됨), 마지막 엣지 뒤 타이머가 끝까지 가야(주황) work가 핀을 읽어 한 번 보고한다. 대가는 지연이다: 누름이 보고되는 시각은 "마지막 바운스 + debounce" 이후다.

무엇을 확인하나: 엣지 간격과 개수를 정확히 조절한 "채터링 누름"을 만들어, debounce_ms 0 / 5 / 20에서 raw 엣지·work 실행·키 이벤트 수를 센다. 바운스 생성기는 sim_gpio0/pull 파일에 pwrite()로 pull-up/pull-down을 번갈아 쓰는 정적 C 프로그램이다.

bounces를 홀수로 주면 마지막 루프 값이 이미 목표 레벨이라 전이 하나당 엣지가 정확히 bounces개다. 측정 루프(i3.sh bounce):

그림 4 — 위 표를 막대로 그린 것(실측). 회색 = 핀에서 난 엣지 수, 나머지 = 유저 공간이 받은 EV_KEY 이벤트 수. 이상적인 값은 항상 2(누름 1 + 뗌 1)다. debounce 0은 엣지를 전부 키로 내보내고, 5 ms는 엣지 간격이 12 ms로 벌어지자 무너지고(8개), 20 ms는 모든 패턴에서 2개를 지켰다.

출력에서 볼 것:

  • debounce 0: works가 raw 엣지와 같다. 엣지 사이 실제 간격(약 1 ms, usleep(500)이 TCG에서 더 길어진다)이 work 실행 시간보다 길어서 work가 엣지마다 한 번씩 돌았고, 바운스 중간값이 그대로 키 이벤트가 됐다.
  • debounce 5, 5×12 ms: 바운스 간격(12 ms)이 디바운스 시간보다 길면 각 바운스가 "안정된 누름"으로 보인다. 상세 출력의 이벤트 간격이 정확히 약 12 ms다.
  • debounce 20: 모든 패턴에서 2개. 대가는 지연이다 — 마지막 바운스 후 20 ms(실제로는 아래 jiffies 반올림 때문에 그 이상)가 지나야 누름이 보고된다.

5.3 해석 — jiffies 반올림과 input core의 중복 제거#

왜 5 ms가 6 ms 간격까지 버텼나? 랩 커널은 CONFIG_HZ=250, jiffy 하나가 4 ms다. msecs_to_jiffies(5)는 올림으로 2 jiffies이고, delayed_work는 "지금 tick부터 2번째 tick"에 돌므로 실제 지연은 4~8 ms 사이 어딘가다. 6 ms 간격이 이번 실행에서 걸러진 것은 그 범위 안의 운이고, 경계 근처라 실행마다 달라질 수 있다. 반대로 debounce_ms=1은 1 jiffy = 0~4 ms라 사실상 "다음 tick"이다. 정확한 ms 디바운스가 필요하면 hrtimer를 쓴다 — gpio-keys가 잠들지 않는 GPIO에서 그렇게 한다(§7.4).

왜 works=9인데 key_events=8인가? (debounce 5, 5×12 ms 행) work가 9번 돌았지만 그중 한 번은 직전과 같은 값을 읽었다. input_report_key()는 호출됐지만 input core의 input_get_disposition()이 "key[] 비트가 이미 그 값"이라고 보고 이벤트를 버렸다(§2.2). 드라이버가 상태 비교를 안 해도 중복이 유저에게 새지 않는 이유가 이것이다. 단, 반대 방향 오류(누름을 놓침)는 core가 못 막는다 — 그건 디바운스 시간과 샘플 시점의 문제다.

현장 기준값: 택트 스위치 5~20 ms, 큰 기계식 스위치·릴레이 접점 20~50 ms. 비상 정지처럼 안전 기능은 input 디바운스에 맡기지 않는다 — 하드웨어 인터록이 먼저고, 소프트웨어 이벤트는 보고용이다(§12).

6. 폴링 장치와 EV_ABS 조이스틱 축#

6.1 예제 9 — poller는 "열려 있을 때만" 돈다, 그리고 inhibited#

무엇을 확인하나: input_setup_polling()의 poller가 언제 도는지, 그리고 kbd 핸들러가 장치를 열어 두는 문제를 확인한다. sysfs inhibited 속성(5.11부터)은 장치를 강제로 "닫힌" 상태로 만든다 — 드라이버의 close()가 불리고, poller가 멈추고, 이벤트가 버려진다(boot.sh i3 abs).

출력에서 볼 것:

  • evdev를 아무도 안 열었는데도 1초에 약 42번 폴링한다(47 → 89). kbd 핸들러가 EV_KEY를 가진 모든 장치를 열어 두기 때문이다. 20 ms 주기면 50번이어야 하는데 42번인 것은 TCG 에뮬레이션의 타이머 지연이다(실측: 이벤트 간격이 약 24 ms).
  • inhibited=1 동안 polls가 89에서 멈췄다. 저전력 장비에서 "화면이 꺼지면 터치 컨트롤러 폴링을 멈춘다"를 이 속성 하나로 할 수 있다(덮개를 닫거나 태블릿 모드로 접을 때 키보드·터치패드를 끄려는 용도로 5.11에 들어왔다).
  • 교훈: 조이스틱·센서처럼 폴링하는 장치가 EV_KEY도 가지면 VT 키보드 핸들러 때문에 항상 폴링한다. 콘솔이 필요 없는 임베디드 제품이면 CONFIG_VT를 끄거나, 버튼과 축을 다른 input_dev로 나누는 것이 정석이다.

6.2 예제 10 — fuzz가 실제로 거른 것#

같은 4초 동안 poller는 298 − 133 = 165번 값을 보고했고, evtest가 받은 EV_ABS는 100개다. 65개가 사라졌다. 어디서 사라졌는지 시계열로 본다.

그림 5 — evtest가 받은 ABS_X 이벤트(실측, 시각은 첫 이벤트 기준). 삼각파가 오르내리는 구간은 poll마다 64씩 바뀌어 모든 샘플이 이벤트가 됐고, 960 근처에 머무는 두 구간(약 1.1~1.2초씩, 각 50 poll)은 점이 듬성듬성하다.

머무는 구간(값 ≥ 955)만 세는 짧은 Python 스크립트를 VM에서 같은 출력 파일에 돌렸다.

50 poll 중 17~23개만 나갔다. 노이즈는 ±3, fuzz는 4다. §2.4의 규칙대로 변화가 2 미만(fuzz/2)이면 버려지고, 2~3이면 평균을 내서 값이 바뀌면 통과한다. 그래서 절반 넘게 걸러졌지만 다 걸러지지는 않았다. 그리고 값이 버려진 poll은 SYN_REPORT도 안 보인다. input core는 값 없이 SYN_REPORT만 있는 패킷을 핸들러에 넘기지 않는다. 출력의 SYN_REPORT: 101은 grep -c가 evtest 마지막 요약 줄(... N SYN_REPORT, 0 SYN_DROPPED)까지 센 것이라, 실제 패킷 수는 100 = EV_ABS 수와 같다. 165번 보고 → 100개 패킷이다.

실무 판단: 노이즈를 확실히 죽이려면 fuzz를 노이즈 진폭의 2배 이상으로 잡는다. 그러나 fuzz는 해상도를 깎는다(작은 움직임도 버린다). 정밀 조작이 필요한 조이스틱은 fuzz를 작게 두고 데드존(flat)을 소비자가 적용하게 한다.

7.3 gpio-keys 안의 분기 — 하드웨어 디바운스, hrtimer, work#

6.18의 gpio_keys_setup_key() 핵심을 요약하면 이렇다(소스에서 옮긴 것, 일부 생략).

  1. 먼저 GPIO 컨트롤러에 하드웨어 디바운스를 부탁한다(gpiod_set_debounce → 칩 드라이버의 set_config(PIN_CONFIG_INPUT_DEBOUNCE)). i.MX·TI·Rockchip 등 많은 SoC GPIO 블록에 디바운스 필터가 있다. 성공하면 소프트웨어 타이머가 필요 없다.
  2. 실패하면(gpio-sim은 set_config가 풀업/풀다운만 처리한다) 소프트웨어 디바운스.
  3. 칩이 잠들지 않으면 hrtimer(정밀, 콜백은 원자 문맥에서 gpiod_get_value), 잠들 수 있으면 delayed work(jiffies 해상도, _cansleep). 우리 랩은 gpio-sim이라 work 경로다 — i3_btn과 같은 선택이다.

그리고 ISR 첫머리에서 wakeup 키면 pm_stay_awake()를 부르고, suspend 중에 IRQ가 왔으면 누름을 바로 보고한다("깨운 키를 이미 뗐을 수도 있으니 누름을 흉내 낸다"는 주석이 있다). §9에서 이 경로를 실제로 밟는다.

9. 웨이크업 — 버튼으로 suspend에서 깨우기#

9.1 무엇이 필요한가#

키로 깨우려면 세 층이 다 맞아야 한다.

  1. DT: 키 노드에 wakeup-source. gpio-keys가 device_init_wakeup(dev, true)로 장치를 "깨울 수 있음"으로 표시한다(power/wakeup = enabled).
  2. 드라이버 suspend 콜백: gpio-keys의 gpio_keys_suspend()가 키 IRQ에 enable_irq_wake()를 건다.
  3. IRQ 칩: 그 IRQ를 실제로 깨움 신호로 만들 수 있어야 한다(irq_chip.irq_set_wake, 또는 IRQCHIP_SKIP_SET_WAKE). SoC라면 GPIO 블록 → 웨이크업 컨트롤러(i.MX의 GPC, TI의 wakeup gen) → PMIC 경로까지 이어져야 한다.

9.2 예제 12 — gpio-sim 키에 wakeup-source를 달면 suspend가 실패한다#

무엇을 확인하나: §1.2 DT 그대로(i3-keys/key-enter에 wakeup-source) s2idle(echo freeze > /sys/power/state)에 들어가 본다. 같은 expect 세션에서 전원 키도 눌렀다.

출력에서 볼 것:

  • echo freeze가 즉시 ENXIO(-6, "No such device or address")로 실패했다(두 date가 같은 초). 유저 공간은 다 얼었다가 바로 풀렸다.
  • 원인: gpio-sim의 IRQ(내부적으로 irq_sim)는 wake를 설정할 수 없어서 enable_irq_wake()가 -ENXIO를 돌려주고, gpio-keys의 suspend 콜백이 그 에러를 그대로 올려서 시스템 전체 suspend를 거부했다. 이 노트의 다른 실험들에서 전원을 끌 때마다 보인 gpio-keys i3-keys: failed to configure IRQ 22 as wakeup source: -6 / failed to shutdown도 같은 원인이다(gpio-keys의 shutdown 콜백이 suspend 경로를 재사용한다).
  • 실무 교훈: 보드 DT에 wakeup-source를 습관적으로 붙이면, wake를 지원하지 않는 IRQ(일부 I2C GPIO 확장기 등)에 달린 키 하나 때문에 제품 전체가 suspend를 못 한다. "suspend가 바로 풀린다"는 증상이면 dmesg의 failed to suspend 줄에서 장치 이름부터 찾는다.
  • 이 실행에서 30초 타이머로 띄운 evtest가 받은 KEY_POWER(11.099)는 suspend와 상관없이 그 뒤에 보낸 system_powerdown이다.

9.3 예제 13 — 전원 키로 s2idle에서 깨어나기#

무엇을 확인하나: gpio-sim 키의 wakeup-source를 뺀 DT(mkdtb.sh i3nw -DI3_NO_SIM_WAKE)로 다시 부팅해서, s2idle에 들어간 뒤 5초쯤 지나 VM에서 system_powerdown을 보낸다. 전원 키(PL061) 노드에는 §1.2에서 wakeup-source를 붙여 두었다.

출력에서 볼 것:

  • date가 633 → 638로 5초 차이 난다. echo freeze가 그동안 돌아오지 않았다 = 시스템이 s2idle에 있었다. suspend entry (s2idle) 6.07 → suspend exit 11.04.
  • 깨운 것은 PL061 IRQ 21(전원 키)이고, evtest가 그 키를 KEY_POWER 1/0으로 받았다. 이벤트 시각(10.98)이 suspend exit(11.04)보다 앞선다 — resume 도중 IRQ가 처리되며 보고됐다.

10. uinput — 유저 공간에서 입력 장치 만들기 (그리고 테스트하기)#

10.1 예제 14 — 가상 키보드 + 축 장치를 만들고 이벤트 주입#

uinput은 /dev/uinput(misc 장치, 10:223)에 ioctl로 capability를 설정하고 UI_DEV_CREATE하면 진짜 input_dev가 커널에 등록되는 드라이버다. 그다음 write()한 struct input_event가 그 장치의 이벤트로 input core에 들어간다. 쓰임새:

  • 테스트: 하드웨어 없이 앱(HMI, 텔레옵 노드, 키 데몬)의 입력 처리를 자동 시험한다. CI에서 "전원 키 3초 → 종료 시퀀스"를 검증할 수 있다.
  • 브리지: 네트워크 리모컨, 블루투스 게임패드 유저 공간 스택, 원격 데스크톱이 받은 입력을 로컬 입력 장치로 만든다.
  • 변환기: 키 리매핑 데몬, 조이스틱 → 키보드 매핑.

무엇을 확인하나: 키(QWERTY 윗줄 + H)와 ABS_X를 가진 장치를 만들고 "h, i, 축 100, 축 100(같은 값), 축 900 + P 누름, P 뗌"을 주입해서 i3_evtest로 읽는다.

게스트 시나리오(boot.sh i3 uinput):

출력에서 볼 것:

  • uinput 장치는 /sys/devices/virtual/input/input2(부모 하드웨어가 없는 "virtual" 장치)에 생기고, bus=0x6(BUS_VIRTUAL), 우리가 준 VID/PID를 가진다. 진짜 장치와 구별 가능하다 — 보안상 중요한 앱(잠금 화면)은 가상 장치 입력을 따로 취급할 수 있다.
  • 유저가 넣은 이벤트 16개(+ SYN) 중 두 번째 ABS_X 100과 그 SYN_REPORT가 사라졌다(15 events, 7 패킷). uinput 장치도 input core를 지나므로 같은 값 제거와 빈 패킷 제거가 똑같이 적용된다.

  • /dev/uinput이 crw------- root인 이유: 아무나 가상 키보드를 만들면 다른 사용자의 세션에 키를 입력할 수 있다. 권한을 열 때는 신중해야 한다.

10.2 예제 15 — EVIOCGRAB: 한 프로세스가 장치를 독점#

무엇을 확인하나: 같은 장치를 리더 A(일반)와 리더 B(grab)가 열고, 세 번째 프로그램이 또 grab을 시도한다 (boot.sh i3 grab).

출력에서 볼 것:

  • 리더 B가 15개를 다 받는 동안 리더 A는 0개다. 두 번째 grab 시도는 EBUSY.
  • evdev의 grab은 evdev 클라이언트끼리의 독점만이 아니다. evdev_grab()이 input_grab_device()로 장치 수준 grab을 걸어서 같은 장치의 다른 핸들러(kbd)도 이벤트를 못 받는다(§11의 input_pass_values()가 dev->grab부터 본다). X 서버나 Wayland compositor가 키보드를 grab하는 이유가 이것이다 — 그래야 그래픽 세션에서 친 키가 뒤의 VT 콘솔에 함께 입력되지 않는다.

10.3 예제 16 — SYN_DROPPED: 느린 리더의 버퍼가 넘칠 때#

evdev는 클라이언트(fd)마다 링버퍼를 하나씩 가진다. 크기는 장치가 등록될 때 정해진다(6.18 evdev.c).

출력에서 볼 것(값은 실행마다 다르다):

10.4 libevdev — 실제 앱은 이걸 쓴다#

위의 재동기화, 비트맵 조회, 이벤트 이름 출력(KEY_A 같은 문자열)을 매번 직접 짜지 않도록 freedesktop.org의 libevdev가 있다. libevdev_new_from_fd() → libevdev_next_event()가 SYN_DROPPED를 받으면 LIBEVDEV_READ_STATUS_SYNC를 돌려주고 동기화용 가짜 이벤트들을 만들어 준다. 같은 라이브러리의 libevdev_uinput_create_from_device()는 기존 장치를 복제한 uinput 장치를 만든다(테스트에 유용). 데스크톱의 libinput과 evemu(이벤트 녹화·재생 도구)가 libevdev 위에 있다. 장비에서 이벤트를 녹화해 두고 CI에서 uinput으로 재생하는 테스트가 이 조합으로 가능하다. 이 노트는 원리를 보이려고 raw ioctl을 썼지만, 제품 코드에서는 libevdev(MIT 라이선스)를 권한다. 게스트에 libevdev가 없어서 이 노트에서는 실행하지 않았다.

11. 커널 안에서는 무슨 일이 일어나나#

드라이버의 input_report_key() 한 줄이 유저의 read()까지 가는 길(6.18 함수 이름 그대로):

그림 8 — 이벤트 한 개의 경로. 왼쪽 기둥(input core)은 dev->event_lock을 잡은 채 IRQ를 끄고 돈다 — 그래서 input_report_*는 hard IRQ에서도 부를 수 있지만, 핸들러 쪽 처리도 원자 문맥이라 evdev는 버퍼에 복사하고 깨우기만 한다. 오른쪽 기둥(evdev)이 유저 공간과 만나는 곳은 poll/read의 file_operations다.

드라이버 작성과 연결되는 지점:

  • file_operations를 직접 안 쓴다. char device(A3, G6)를 만들면 read/poll/버퍼/권한/핫플러그를 다 짜야 하지만, input 드라이버는 input_dev만 등록하면 evdev가 그것을 전부 제공한다. I1 노트의 "서브시스템에 등록하라"의 가장 깔끔한 예다.
  • dev->open/dev->close 콜백: 첫 사용자가 열 때 하드웨어를 켜고(터치 IC 전원, IRQ enable) 마지막 사용자가 닫을 때 끈다. poller는 이 콜백을 자동으로 쓴다. 단, kbd 핸들러가 EV_KEY 장치를 늘 열어 둔다는 것(§6.1)을 기억한다.
  • 문맥: input_event()는 원자 문맥 OK. 값을 얻는 쪽(I2C 읽기)이 잠들면 threaded IRQ(F6) — 터치·키패드 컨트롤러 드라이버의 표준 모양이다.
  • dev->event 콜백(INPUT_PASS_TO_DEVICE): 반대 방향(유저 → 장치) 이벤트. 유저가 EV_LED(Caps Lock LED)나 EV_FF(진동)를 write하면 드라이버의 event가 불린다.
  • PM: wakeup-source → device_init_wakeup() → suspend 콜백에서 enable_irq_wake()(§9). runtime PM과는 inhibited/open·close로 연결된다.
  • USB HID: H12의 usbhid가 받은 report를 hid-input이 HID usage → input 코드로 바꿔 input_event()를 부른다. 그래서 USB 키보드도 똑같이 /dev/input/eventN이다.

12. Embedded 실무에서 다시 보기#

12.1 로봇 컨트롤 박스의 버튼 패널#

예를 들어 센서 키트를 단 이동 로봇의 컨트롤 박스에 "전원", "모드", "정지 요청" 버튼과 덮개 스위치가 있다고 하자. 보드 DT는 이렇게 된다.

유저 공간은 "전원 키 3초 누름 → 안전 종료", "덮개 열림 → 서비스 모드 경고"를 하는 작은 데몬이다. 그 데몬은 poll()로 이벤트를 기다리고, 시작할 때 EVIOCGSW로 덮개 상태를 한 번 읽고, SYN_DROPPED를 처리하고, 장치가 사라지면(ENODEV) 다시 찾는다. 데몬의 테스트는 uinput으로 같은 이름의 장치를 만들어서 한다.

12.2 비상 정지는 input이 아니다#

"E-stop 버튼도 gpio-keys로 받으면 되나?" — 보고용으로는 된다. 안전 기능으로는 안 된다. E-stop은 모터 드라이버 전원이나 STO(Safe Torque Off) 입력을 하드웨어로 끊어야 한다. 리눅스 쪽 이벤트는 "정지됐다"를 UI와 로그에 알리는 용도다. 이유: 디바운스·스케줄링·유저 공간 데몬·SYN_DROPPED·grab 등 지연과 유실 경로가 너무 많다(이 노트에서 다 재현했다). 면접에서 이 구분을 말하면 시스템 감각이 있다는 신호가 된다.

12.3 조종용 조이스틱 — USB 게임패드 vs 직접 붙인 ADC#

텔레옵에는 보통 USB 게임패드를 쓴다. hid-input(또는 xpad 같은 전용 드라이버)이 EV_ABS/EV_KEY로 바꿔 주므로 ROS의 joy 노드 같은 앱이 /dev/input/eventN을 읽으면 된다. 컨트롤 박스에 아날로그 스틱을 SoC ADC에 직접 붙였다면 커널에 이미 adc-joystick 드라이버가 있다 — IIO ADC 채널을 consumer로 받아 input 축으로 내보낸다(I2의 IIO consumer API). 이 노트의 i3_btn 가짜 ADC 폴링이 그 구조의 축소판이다. 이때 fuzz·flat 튜닝과 "버튼과 축을 다른 input_dev로" 원칙(§6.1)이 그대로 적용된다.

12.4 현장 디버그 순서#

  1. cat /proc/bus/input/devices — 장치가 등록됐나? H:에 eventN이 있나? B: KEY=에 기대한 코드가 있나?
  2. evtest /dev/input/eventN(또는 이 노트의 i3_evtest) — 이벤트가 오나? 값과 극성이 맞나?

14. 면접에서 이렇게 말한다#

Q. "Walk me through how a button press gets from a GPIO pin to an application on Linux."

A. 핀 엣지가 GPIO 컨트롤러 IRQ가 되고, gpio-keys 같은 드라이버가 디바운스한 뒤 input_report_key + input_sync를 부른다. input core가 capability·상태를 확인하고 SYN_REPORT에서 패킷을 핸들러에 넘기면, evdev가 열린 fd마다 링버퍼에 넣고 깨운다. 앱은 /dev/input/eventN을 poll하고 struct input_event를 read한다. QEMU에서 전원 키로 이 경로를 직접 추적했다.

The pin edge becomes an interrupt from the GPIO controller; on most boards that pin is described in the device tree under gpio-keys, so no custom driver is needed. The driver debounces — a delayed work or hrtimer re-armed on every edge — then calls input_report_key and input_sync. The input core checks the device's capability bitmaps, drops duplicate key states, and on SYN_REPORT passes the whole packet to every attached handler. evdev copies it into a per-file-descriptor ring buffer and wakes the reader, so the application just polls /dev/input/eventN and reads struct input_event records with a timestamp, type, code and value.

꼬리 질문: "What does the kbd handler do with the same event?" → VT 콘솔용 키맵 변환. 그래서 EV_KEY 장치는 kbd가 늘 열어 둔다.

Q. "Write the skeleton of an input driver for a single button."

A. probe에서 devm_input_allocate_device, 이름·bustype 설정, input_set_capability(EV_KEY, code), input_register_device. GPIO는 devm_gpiod_get, IRQ는 gpiod_to_irq + 양쪽 엣지. ISR은 디바운스 타이머만 재시작하고, 타이머/워크에서 값을 읽어 input_report_key + input_sync. devm이라 remove가 필요 없지만, work 취소를 IRQ 해제와 input 해제 사이에 오도록 순서를 맞춘다.

In probe: devm_input_allocate_device, set name, phys and bustype, input_set_capability for EV_KEY and the key code, then input_register_device. Get the GPIO with devm_gpiod_get, map it with gpiod_to_irq and request both edges. The handler only re-arms a debounce delayed work; the work reads the line with gpiod_get_value_cansleep and reports the key followed by input_sync. Everything is devm-managed, so there's no remove callback, but I register a devm action to cancel the work before requesting the IRQ so teardown runs IRQ free, cancel work, then unregister. In practice I'd use gpio-keys in the device tree — I'd only write this for something gpio-keys can't express.

Q. "What are fuzz and flat in input_absinfo?"

A. fuzz는 커널이 적용하는 노이즈 필터 폭이다. 변화가 fuzz/2 미만이면 버리고, fuzz·2fuzz 미만이면 평균을 낸다. flat은 중앙 데드존으로 커널이 아니라 소비자가 적용한다. 실험에서 ±3 노이즈에 fuzz 4를 줬더니 정지 구간 50 샘플 중 17~23개만 통과했다 — fuzz를 노이즈 진폭의 두 배 이상으로 잡아야 확실히 조용해진다.

fuzz is a filter the input core applies: changes smaller than half the fuzz are dropped, and changes within one or two times fuzz are averaged with the previous value. flat is a center dead zone that the kernel only reports; consumers like joystick libraries apply it. When I fed plus-or-minus three counts of noise with fuzz four, roughly a third to a half of the stationary samples still got through, so fuzz needs to be about twice the noise amplitude — at the cost of resolution.

Q. "Why are IMUs and ADCs IIO devices rather than input devices?"

A. input은 사람의 사건을 "변화가 있을 때만" 전달하는 모델이라 중복·fuzz 필터가 샘플을 버리고, 샘플링 주파수·하드웨어 FIFO·트리거·스케일 같은 개념이 없다. 센서 융합에는 모든 샘플과 정확한 타임스탬프가 필요하므로 IIO의 buffered capture가 맞다. 또 input 장치는 데스크톱 스택이 자동으로 집어 가서 가속도계가 조이스틱으로 오인되는 문제도 있었다.

The input subsystem is designed for human events: it only forwards changes, drops duplicates and can filter with fuzz, and it has no notion of sampling frequency, hardware FIFOs, triggers or scale and offset. Sensor fusion needs every sample with an accurate timestamp, which is exactly what IIO buffered capture gives you. Input devices also get picked up automatically by desktop stacks, and accelerometers exposed as three-axis ABS devices used to be mistaken for joysticks. So new sensor drivers go to IIO; input is for buttons, touch, keys and sticks.

Q. "What is SYN_DROPPED and how should a client handle it?"

A. evdev 클라이언트 버퍼가 넘치면 읽지 않은 이벤트를 다 버리고 SYN_DROPPED와 최신 이벤트 하나만 남긴다. 클라이언트는 다음 SYN_REPORT까지 버리고 EVIOCGKEY/EVIOCGABS/EVIOCGMTSLOTS로 현재 상태를 읽어 재동기화해야 한다. libevdev가 이를 자동으로 한다. 실험에서 2 ms 지연 리더에 1200 이벤트를 쏘자 48개만 받고 5번 drop이 났다.

Each evdev file descriptor has its own ring buffer sized from the device's events-per-packet estimate. If the reader falls behind and the buffer wraps, evdev throws away everything unread and queues SYN_DROPPED plus the newest event. The client must discard events up to the next SYN_REPORT, then query the current state with EVIOCGKEY, EVIOCGABS, EVIOCGMTSLOTS and so on, and diff it against its own state. libevdev does this for you. The real fix is to drain input quickly in its own thread or event loop and read many events per syscall.

Q. "How would you test an input-handling application without hardware?"

A. uinput으로 같은 capability의 가상 장치를 만들고 이벤트를 write한다. 가상 장치도 input core를 지나므로 중복 제거·패킷 규칙이 똑같이 적용된다. evemu로 실제 장비의 이벤트를 녹화해 재생하면 회귀 테스트가 된다. 앱이 이름으로 장치를 찾게 만들어 두면 테스트 장치로 갈아끼우기 쉽다.

I create a virtual device with uinput that has the same capabilities, then write input_event records followed by SYN_REPORT. It goes through the real input core, so duplicate filtering, packet framing and even hot-unplug with ENODEV behave like hardware. For regression tests I'd record real sessions with evemu and replay them in CI. The application should look devices up by name or capability rather than by event number, which also makes swapping in the virtual device trivial.

꼬리 질문: "Can a uinput device be distinguished from a real one?" → BUS_VIRTUAL, /sys/devices/virtual/input/ 경로, VID/PID.

Q. "A board fails to suspend right after adding a wakeup button. How do you debug it?"

A. dmesg에서 failed to suspend 줄의 장치를 찾는다. 그 키의 IRQ 칩이 wake를 지원하지 않으면 gpio-keys suspend 콜백이 enable_irq_wake 실패를 올려 전체 suspend가 취소된다. 랩에서 gpio-sim 키에 wakeup-source를 달아 -ENXIO로 재현했고, 빼자 전원 키(PL061)로 s2idle에서 정상적으로 깨어났다. 실제 SoC에서는 그 패드가 웨이크업 컨트롤러로 라우팅되는지도 확인한다.

I'd look at the PM lines in dmesg — the device whose suspend callback failed is named there. A common cause is wakeup-source on a key whose interrupt controller can't be a wake source: gpio-keys calls enable_irq_wake during suspend, gets ENXIO, returns the error, and the whole system suspend is aborted. I reproduced that in QEMU with a key on a simulated GPIO chip; removing the property fixed it and the power key then woke the system from s2idle. On real silicon I'd also confirm in the reference manual that the pad routes to the wakeup controller and stays powered in the target sleep state.

15. 직접 해보기#

  1. 개념: B: KEY=10000000000000 0에서 KEY_POWER(116)를 손으로 해독해 보라. B: EV=23은 어떤 타입들인가? 정답/힌트: word는 높은 쪽부터, 두 번째 word = bit 64~127, 0x10000000000000 = bit 52 → 116. 0x23 = bit 0, 1, 5 = SYN, KEY, SW.
  2. 코드: i3_btn의 디바운스를 hrtimer로 바꾸고(SoC GPIO 가정), debounce_ms=5에서 5×6 ms 패턴과 5×12 ms 패턴 결과가 delayed work 버전과 어떻게 달라지는지 예측한 뒤 측정하라. 정답/힌트: hrtimer는 jiffies 반올림이 없어 5 ms가 거의 5 ms다. 6 ms 간격은 이제 못 걸러야 정상이다. gpio-sim은 can_sleep이므로 hrtimer 콜백에서 값을 직접 읽지 말고 거기서 work를 깨우는 구조로 해야 한다.
  3. 코드: i3_btn을 버튼용 input_dev와 축용 input_dev 두 개로 나누고, §6.1처럼 polls 카운터로 "아무도 안 열면 폴링이 멈추는지" 확인하라. 정답/힌트: 축 장치는 EV_KEY가 없으니 kbd가 붙지 않는다. /proc/bus/input/devices의 H:에 event만 있어야 한다.
  4. 관찰: uinput 장치를 만든 뒤 /sys/class/input/inputN/capabilities/의 ev, key, abs 파일을 읽고 /proc/bus/input/devices의 B: 줄과 비교하라. 정답/힌트: 같은 비트맵이 파일별로 나뉘어 있다. udev가 ID_INPUT_KEYBOARD 같은 속성을 이 파일로 판단한다.
  5. 코드: i3_evtest를 고쳐서 SYN_DROPPED 후 다음 SYN_REPORT까지 이벤트를 버리게 하고, 재동기화 뒤 "앱이 기억하는 눌린 키 집합"이 EVIOCGKEY와 일치하는지 검사하라. 정답/힌트: 앱 상태(비트맵)와 EVIOCGKEY 결과를 비교해 차이를 합성 이벤트로 만든다 — libevdev가 하는 일이다.
  6. 관찰: 같은 장치를 리더 둘이 열고 하나가 EVIOCGRAB한 상태에서 /proc/bus/input/devices, kbd로 가는 키(콘솔 입력)가 어떻게 되는지 보라. 정답/힌트: grab은 장치 수준이라 콘솔에도 키가 안 간다. fd를 닫으면 즉시 풀린다.
  7. 설계: 로봇 컨트롤 박스에 버튼 6개가 있는데 GPIO가 2개뿐이다. 선택지(매트릭스, I2C 키패드 컨트롤러, I2C GPIO 확장기 + gpio-keys)를 지연·wake·코드량으로 비교하라. 정답/힌트: 확장기의 INT를 쓰면 gpio-keys가 그대로 되지만 can_sleep이라 work 경로이고 wake는 확장기 INT 핀이 SoC wake 패드에 붙어야 한다. TCA8418 같은 키패드 IC는 스캔·디바운스를 칩이 한다.

17. 요약 & 체크리스트#

input 서브시스템은 펌웨어에서 매번 직접 짜던 "버튼 ISR + 디바운스 + 이벤트 큐 + 여러 소비자"를 표준화한 것이다. 드라이버는 input_dev를 capability와 함께 등록하고 input_report_* + input_sync만 부른다. input core는 상태 비트맵으로 중복을 지우고 fuzz로 노이즈를 거르고 SYN_REPORT 단위로 핸들러에 넘긴다. evdev는 fd마다 링버퍼를 두고, 넘치면 SYN_DROPPED로 재동기화를 요구한다. 버튼은 gpio-keys DT 노드로 코드 없이 붙이고, 테스트는 uinput으로 한다. 센서(IMU·ADC)는 input이 아니라 IIO다. 이 노트에서 QEMU 전원 키 IRQ, gpio-sim 위의 직접 만든 드라이버와 gpio-keys, 디바운스 측정, fuzz 효과, EVIOCGRAB, SYN_DROPPED, s2idle 웨이크업과 그 실패까지 전부 실제로 돌려 확인했다.
