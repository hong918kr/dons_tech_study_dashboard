## 0. 큰 그림 — 이게 왜 필요한가

G9에서 핫플러그 사슬의 **커널 쪽**(`device_add()` → `kobject_uevent()` → netlink)과 BusyBox mdev, 그리고 호스트에서 `udevadm` 맛보기를 했다. 이 노트는 그 뒤, **제품 rootfs에 들어가는 systemd-udevd 정책을 설계하는 쪽**이다.

SSD 펌웨어로 비유하면 이렇다. NAND 채널 0~7에 다이가 붙는데, 부팅 때 스캔 순서나 불량 다이 때문에 "논리 번호 3번 다이"가 매번 다른 물리 다이일 수 있다. 그래서 펌웨어는 **논리 번호가 아니라 (채널, CE, LUN) 물리 주소나 다이 고유 ID**로 매핑 테이블을 만든다. Linux의 `/dev/ttyUSB0`, `/dev/video0`, `/dev/vdb`는 바로 그 "스캔 순서 논리 번호"다. udev는 그 위에 **물리 주소(by-path)·고유 ID(by-id)·역할 이름(`/dev/cam_front`)** 매핑을 얹는 계층이다.

udev가 장비에서 하는 일은 네 가지다.

- **이름**: 커널 번호는 그대로 두고 심볼릭 링크로 안정된 이름을 준다 (`/dev/serial/by-id/...`, `/dev/gnss`). 네트워크 인터페이스만은 진짜 이름을 바꾼다 (`enp0s1`, `lan0`).
- **권한**: 노드의 소유자·그룹·모드 (`GROUP="video"`, `MODE="0660"`) — 앱을 root로 안 돌리기 위한 전제.
- **속성 수집**: builtin(`usb_id`, `path_id`, `hwdb` 등)으로 `ID_SERIAL`, `ID_PATH` 같은 속성을 만들어 udev db에 저장하고 다른 프로그램(systemd, libudev 앱)에 알린다.
- **행동 연결**: 모듈 로드(G9 §4), 그리고 systemd에게 "이 장치가 생기면 이 서비스를 시작해라"(`SYSTEMD_WANTS`).

### 0.2 실험 도구 — 시리얼 소켓으로 게스트 셸 한 줄 실행

게스트는 `-serial unix:/var/tmp/L2/ser.sock`, `-monitor unix:/var/tmp/L2/mon.sock`로 띄우고, VM 쪽에서 작은 Python 스크립트로 "명령 보내고 끝 표시까지 읽기"를 한다. 이 노트의 `g <타임아웃> "<명령>"`이 그것이고, `l2_mon.sh "<HMP 명령>"`은 QEMU monitor에 한 줄을 보낸다.

```sh
# l2_boot.sh 핵심 (VM에서 실행, 이미지 사본은 /var/tmp/L2/l2_root.ext4)
qemu-system-aarch64 -machine virt -cpu cortex-a57 -smp 2 -m 1G -display none \
  -kernel /var/lab/out/Image-sec \
  -drive file=/var/tmp/L2/l2_root.ext4,if=virtio,format=raw \
  -netdev user,id=n0 -device virtio-net-pci,netdev=n0,mac=52:54:00:12:34:56 \
  -device qemu-xhci,id=xhci \
  -serial unix:/var/tmp/L2/ser.sock,server=on,wait=off \
  -monitor unix:/var/tmp/L2/mon.sock,server=on,wait=off \
  -append "console=ttyAMA0 root=/dev/vda rw rootwait $L2_APPEND" "$@"
```

```python
# l2_sh.py <serial.sock> <timeout_s> <cmd...> : run one shell command in the guest via serial socket
import socket, sys, time, re, random
sock, tmo, cmd = sys.argv[1], float(sys.argv[2]), " ".join(sys.argv[3:])
s = socket.socket(socket.AF_UNIX); s.connect(sock); s.settimeout(0.5)
tag = "L2END%04d" % random.randint(0, 9999)
def drain(t=0.3):
    buf = b""; end = time.time() + t
    while time.time() < end:
        try:
            d = s.recv(65536)
            if not d: break
            buf += d
        except socket.timeout: pass
    return buf
drain()
s.sendall(b"stty -echo 2>/dev/null; export SYSTEMD_PAGER=cat PAGER=cat SYSTEMD_COLORS=0 TERM=dumb; "
          + cmd.encode() + b"; echo " + tag[:3].encode() + b"''" + tag[3:].encode() + b"=$?\n")
buf = b""; end = time.time() + tmo
while time.time() < end:
    try:
        d = s.recv(65536)
        if d: buf += d
    except socket.timeout: pass
    if re.search((tag + r"=\d+").encode(), buf): break
out = re.sub(r"\x1b\[[0-9;?]*[A-Za-z]", "", buf.decode(errors="replace").replace("\r", ""))
m = re.search(tag + r"=(\d+)", out)
out = out[:m.start()] if m else out + "\n[TIMEOUT]"
print(out.rstrip("\n"))
sys.exit(int(m.group(1)) if m else 124)
```

- 끝 표시를 `L2E''ND1234`처럼 쪼개서 보내는 이유: 에코된 명령 줄 자체에서 표시가 매칭되지 않게 하려고.
- `SYSTEMD_PAGER=cat`이 없으면 `udevadm info -a`가 `less`를 띄워서 직렬 콘솔이 멈춘다(실제로 한 번 멈췄다). 스크립트로 systemd 도구를 부를 때는 항상 `--no-pager`나 이 환경 변수를 쓴다.
- 작은 파일(rule, 서비스 유닛)은 `put <파일> <게스트 경로>` 스크립트가 base64로 바꿔 `echo ... | base64 -d > 경로`로 넣는다.

## 1. systemd-udevd 구조 — 데몬, 워커, db, 두 개의 이벤트

### 1.1 직관

udevd는 "디스패처 + 워커 풀"이다. 메인 프로세스가 커널 netlink 소켓(`NETLINK_KOBJECT_UEVENT`, 멀티캐스트 group 1)에서 이벤트를 받아 **큐**에 넣고, 같은 장치(그리고 부모·자식 관계인 장치)의 이벤트는 순서대로, 서로 무관한 장치는 **여러 워커가 병렬로** 처리한다. 워커는 rule을 처음부터 끝까지 평가하고, 노드 권한과 링크를 적용하고, `RUN` 목록을 실행한 다음, 결과를 `/run/udev/data/`에 쓰고 **group 2**로 다시 방송한다.

- **KERNEL 이벤트**: 커널이 보낸 원본. `ACTION`, `DEVPATH`, `SUBSYSTEM`, `DEVNAME`, `MAJOR`/`MINOR`, `MODALIAS`, `SEQNUM` 정도.
- **UDEV 이벤트**: udevd가 처리한 뒤 보낸 것. 원본 + udev가 붙인 속성(`ID_*`, `DEVLINKS`, `TAGS`). systemd PID 1과 libudev 앱(`udev_monitor`)은 이쪽을 듣는다. 그래서 앱이 이벤트를 받는 시점에는 **링크와 권한이 이미 준비돼 있다.**

### 1.2 예제 1 — `udevadm monitor --kernel --udev --property` + QEMU monitor 핫플러그

무엇을 확인하나: USB 시리얼 하나를 `device_add`로 꽂고 `device_del`로 뽑으면서, KERNEL과 UDEV 이벤트가 어떤 순서로 몇 개 나오는지, 그리고 UDEV 쪽에 무엇이 더 붙는지.

```sh
# VM에서
g 10 "(udevadm monitor --kernel --udev --property > /run/l2mon.log 2>&1 &) ; sleep 1"
l2_mon.sh "chardev-add null,id=c1"
l2_mon.sh "device_add usb-serial,chardev=c1,serial=GNSS-A1,id=us1,always-plugged=on"
sleep 8
g 10 "ls -l /dev/ttyUSB* /dev/serial/by-id/ /dev/serial/by-path/; lsmod | grep -E 'ftdi|usbserial'"
l2_mon.sh "device_del us1"; sleep 4
g 10 "pkill -f 'udevadm monitor'; grep -n '^KERNEL\|^UDEV' /run/l2mon.log"
```

`always-plugged=on`을 빼면 QEMU `usb-serial`은 chardev가 "열릴" 때만 USB에 붙는다. `null` chardev는 열리지 않으므로 아무 장치도 안 보인다 — 처음에 이것 때문에 `1-1`이 안 생겼다.

## 2. rule 파일 — 어디에, 어떤 순서로

### 2.1 세 디렉터리와 우선순위

G9 §8.3에서 문법표를 봤다. 여기서는 **제품 이미지 관점**에서 파일 배치를 본다.

| 디렉터리 | 누구 것 | 제품에서의 의미 |
|---|---|---|
| `/usr/lib/udev/rules.d/` | 배포판·패키지 (systemd, v4l-utils 등) | OS 이미지의 일부. OTA로 통째 교체된다. **직접 고치지 않는다** |
| `/run/udev/rules.d/` | 런타임 생성 (tmpfs) | 부팅 초기에 스크립트가 만드는 현장별 rule (예: 설정 파티션 값을 읽어 생성) |
| `/etc/udev/rules.d/` | 관리자·제품 | 우리 rule. 같은 이름이면 위 둘을 덮는다 |

세 곳의 파일을 **파일 이름 기준**으로 합친 다음 사전순으로 처리한다. 같은 이름이 둘 이상 있으면 `/etc` > `/run` > `/usr/lib` 순으로 하나만 쓴다. 그래서:

- **덮어쓰기**: `/usr/lib/udev/rules.d/60-serial.rules`를 고치고 싶으면 같은 이름으로 `/etc/udev/rules.d/60-serial.rules`를 만든다.
- **끄기(마스킹)**: `/etc/udev/rules.d/60-serial.rules → /dev/null` 심볼릭 링크.
- **순서**: 번호가 작을수록 먼저. 우리 rule이 `ID_SERIAL` 같은 builtin 속성을 쓰려면 그 속성을 만드는 rule(`60-*`)보다 **뒤 번호**여야 한다. 그래서 관례적으로 제품 rule은 `70-`~`99-`.

### 2.2 예제 2 — vendor rule을 `/dev/null`로 마스킹하면 내 rule까지 죽는다

무엇을 확인하나: `/etc`의 같은 이름 링크가 `/usr/lib` 파일을 정말 대체하는지, 그리고 **rule 사이의 숨은 의존성**. (이 시점에 §4에서 만든 `70-l2-serial.rules`가 `ENV{ID_USB_INTERFACE_NUM}=="00"`을 쓰며 `/dev/gnss`를 만들고 있다.)

```sh
g 120 "ln -s /dev/null /etc/udev/rules.d/60-serial.rules
udevadm control --reload; udevadm trigger --action=change --settle -s tty
ls /dev/serial; ls -l /dev/gnss
rm /etc/udev/rules.d/60-serial.rules
udevadm control --reload; udevadm trigger --action=change --settle -s tty
ls /dev/serial/by-id"
```

```text
ls: cannot access '/dev/serial': No such file or directory
ls: cannot access '/dev/gnss': No such file or directory
usb-QEMU_QEMU_USB_SERIAL_GNSS-A1-if00-port0
usb-QEMU_QEMU_USB_SERIAL_MODEM-B2-if00-port0
```

출력에서 볼 것: `/dev/serial/by-*`가 사라진 건 예상대로다. 그런데 **우리 `/dev/gnss`도 사라졌다.** `ID_USB_INTERFACE_NUM`은 `60-serial.rules` 6번째 줄의 `IMPORT{builtin}="usb_id"`가 만들어 주던 속성이기 때문이다(예제 4의 `udevadm test` 출력에 그 줄이 보인다). 마스킹을 지우고 reload + trigger하면 복구된다. 교훈: **내 rule이 의존하는 속성이 어느 rule에서 오는지 알아야 한다.** 의존을 없애고 싶으면 내 rule 안에서 직접 `IMPORT{builtin}="usb_id"`를 부르면 된다.

### 2.3 rule 수정 → 적용 사이클

udevd는 rule을 메모리에 캐시한다. 그리고 rule은 **이벤트가 올 때만** 평가된다. 그래서 파일을 고친 뒤에는:

```sh
udevadm control --reload                                   # rule 다시 읽기 (systemd 255는 파일 변경을 감지해 자동으로도 다시 읽는다)
udevadm trigger --action=change --settle -s tty             # 이미 있는 장치에 change 이벤트를 다시 보냄
udevadm trigger --action=change --settle /dev/ttyUSB0       # 장치 하나만
```

- `--action=change`를 쓰는 이유: `add`를 다시 보내면 `ACTION=="add"` 조건의 `RUN`(모듈 로드, 서비스 시작)까지 다시 돈다. 권한·링크만 바꾸려면 `change`가 안전하다. 단 `ACTION=="add"`로 묶인 rule을 테스트할 때는 `add`가 필요하다.
- `--settle`: 그 이벤트들이 끝날 때까지 기다린다.

### 2.4 hwdb — rule이 아닌 "표"로 속성 붙이기

`ID_VENDOR_FROM_DATABASE=Future Technology Devices International, Ltd`는 rule이 아니라 **hwdb**에서 왔다. hwdb는 `modalias` 같은 키 패턴 → 속성 목록 표다. 소스는 `/usr/lib/udev/hwdb.d/*.hwdb`(텍스트), 실제 조회는 `systemd-hwdb update`가 컴파일한 trie `hwdb.bin`.

```sh
g 60 "systemd-hwdb query usb:v0403p6001; ls -la /usr/lib/udev/hwdb.bin; du -sh /usr/lib/udev/hwdb.d"
```

```text

ID_MODEL_FROM_DATABASE=FT232 Serial (UART) IC
-r--r--r-- 1 root root 12291952 Oct 18 04:26 /usr/lib/udev/hwdb.bin
8.2M	/usr/lib/udev/hwdb.d
```

- 장비에서 hwdb가 쓰이는 곳: 키보드 스캔코드 재매핑(`evdev:`), 센서 마운트 행렬(`sensor:` → `ACCEL_MOUNT_MATRIX`, `60-sensor.rules`), USB 장치 이름. 우리 장비 전용 키 매핑이나 IMU 축 회전을 hwdb 파일로 넣을 수 있다.
- **용량 함정**: `hwdb.bin` 하나가 12 MB다(그림 7). 작은 장비의 Yocto 이미지에서는 hwdb를 빼거나(`udev-hwdb` 패키지 제외) 필요한 `.hwdb`만 넣는다. 또 읽기 전용 rootfs라면 `hwdb.bin`을 **빌드 때** 만들어 넣어야 한다(`systemd-hwdb update --root=` 또는 Yocto `udev-hwdb` 후처리). 부팅 때 `systemd-hwdb-update.service`가 쓰려다 실패하는 게 흔한 증상이다.

## 3. 매칭 — 단수 키, 복수 키, 그리고 "부모 하나" 규칙

### 3.1 직관

rule 한 줄은 "이 이벤트 장치가 조건을 모두 만족하면 대입을 실행"이다. 조건에는 두 종류가 있다.

- **단수 키** `KERNEL`, `SUBSYSTEM`, `DRIVER`, `ATTR{}`, `DEVPATH`: **이벤트가 난 장치 자신**만 본다.
- **복수 키** `KERNELS`, `SUBSYSTEMS`, `DRIVERS`, `ATTRS{}`, `TAGS`: 자신부터 sysfs 부모를 하나씩 올라가며 찾는다. 단, **한 줄 안의 복수 키들은 모두 같은 장치 하나에서 맞아야 한다.**

두 번째 규칙이 핵심이다. udevd 구현으로 보면, 복수 키를 만나면 "현재 후보 부모"를 정하고 그 부모에서 나머지 복수 키를 확인한다. 하나라도 안 맞으면 **다음 부모로 올라가서 처음부터 다시** 확인한다. 즉 "부모 A에서 키 1, 부모 B에서 키 2"는 성립할 수 없다.

### 3.2 예제 3 — `udevadm info -a`로 부모 체인 보기

### 3.3 예제 4 — 두 부모를 섞은 rule이 조용히 실패하고, 고친 rule이 성공하기

```sh
rm /etc/udev/rules.d/70-l2-gnss-bad.rules; put files/70-l2-serial.rules /etc/udev/rules.d/70-l2-serial.rules
```

### 3.4 연산자와 치환 — 자주 틀리는 것만

G9 §8.3의 표에 더해, 실무에서 실제로 걸리는 것만 모았다.

| 항목 | 함정 |
|---|---|
| `=` vs `+=` | `SYMLINK="x"`는 앞 rule들이 붙인 링크(`by-id`)를 **지운다**. 항상 `SYMLINK+=` |
| `:=` | 값을 잠근다. `GROUP:="video"` 뒤에 오는 rule은 GROUP을 못 바꾼다. 패키지 rule이 우리 권한을 덮어쓸 때 쓴다 |
| `ATTR{x}=="..."` 값 | sysfs 값 끝의 개행은 udev가 떼어 준다. 하지만 앞쪽 공백(`" 2.00"`, `" 0"`)은 그대로다 — `info -a`에서 복사해 쓴다 |
| `$` 문자 | `$attr{}`, `$env{}`, `$kernel` 등 치환 접두어. 셸의 `$!`를 쓰려면 `$$!`. 아니면 verify가 실패한다(예제 13) |
| `%k`, `%n` | 커널 이름(`ttyUSB0`), 커널 번호(`0`). **`%n`으로 안정 이름을 만들면 안 된다** — 그것이 바로 바뀌는 번호다 |
| `NAME=` | 네트워크 인터페이스 전용. 장치 노드 이름은 커널이 정한다(G9 §6) |
| `GOTO`/`LABEL` | 같은 파일 안에서만. 패키지 rule들이 "해당 없으면 끝으로 점프" 패턴을 많이 쓴다 (예제 9의 `60-persistent-v4l.rules`) |

## 4. 순서 문제 — `ttyUSB0`/`ttyUSB1`이 뒤바뀌는 것을 재현하고 고치기

### 4.1 왜 바뀌나

`ttyUSB<N>`의 N은 `usb-serial` 코어가 포트를 등록할 때 `idr_alloc(&serial_minors, ...)`으로 **비어 있는 가장 작은 minor**를 받는 것이다(`drivers/usb/serial/usb-serial.c`의 `allocate_minors()`). `/dev/videoN`도 같다 — `__video_register_device()`가 `devnode_find()`로 빈 번호를 찾는다(`drivers/media/v4l2-core/v4l2-dev.c`). 즉 번호는 **"누가 먼저 probe를 끝냈나"**의 함수다. 그리고 그 순서는

- USB 허브의 포트 스캔 순서, 장치마다 다른 enumeration 지연(전원 켜지는 시간, 펌웨어 부팅),
- 모듈 로드 순서(드라이버 A가 B보다 먼저 올라오면 A의 장치가 앞 번호),
- 비동기 probe(`PROBE_PREFER_ASYNCHRONOUS`)와 다중 코어 스케줄링,
- 현장에서 케이블을 다른 포트에 꽂는 정비사

로 바뀐다. 펌웨어 비유로는 "다이 스캔 순서로 논리 번호를 줬더니 한 다이가 늦게 응답하면 전부 밀린다"이다.

### 4.2 예제 5 — 핫플러그 순서만 바꿔서 번호 뒤집기

무엇을 확인하나: 같은 두 장치(GNSS-A1, MODEM-B2)를 꽂는 순서만 바꿔서 커널 번호가 뒤집히고, serial 기반 링크는 그대로인지.

```sh
l2_mon.sh "chardev-add null,id=c2"; l2_mon.sh "chardev-add null,id=c3"
l2_mon.sh "device_add usb-serial,chardev=c2,serial=GNSS-A1,id=gnss,always-plugged=on"; sleep 4
l2_mon.sh "device_add usb-serial,chardev=c3,serial=MODEM-B2,id=modem,always-plugged=on"; sleep 6
g 20 'echo "== order 1: GNSS then MODEM"
for t in /dev/ttyUSB*; do echo $t $(udevadm info -q property -n $t | grep ID_SERIAL_SHORT); done
ls -l /dev/gnss /dev/modem'
l2_mon.sh "device_del gnss"; l2_mon.sh "device_del modem"; sleep 4
l2_mon.sh "device_add usb-serial,chardev=c3,serial=MODEM-B2,id=modem,always-plugged=on"; sleep 4
l2_mon.sh "device_add usb-serial,chardev=c2,serial=GNSS-A1,id=gnss,always-plugged=on"; sleep 6
g 20 'echo "== order 2: MODEM then GNSS"
for t in /dev/ttyUSB*; do echo $t $(udevadm info -q property -n $t | grep ID_SERIAL_SHORT); done
ls -l /dev/gnss /dev/modem; ls -l /dev/serial/by-id/'
```


### 4.3 예제 6 — 재부팅마다 포트가 바뀌는 경우 (coldplug)

무엇을 확인하나: 핫플러그가 아니라 **부팅 때 이미 꽂혀 있는** 두 장치가, 물리 포트만 바뀐 채 재부팅됐을 때. 현장에서는 "정비 후 케이블을 반대로 꽂았다" 또는 "허브 포트 스캔 순서"에 해당한다. QEMU의 `port=` 속성으로 물리 포트를 지정했다.

```sh

  -device usb-serial,chardev=c2,serial=GNSS-A1,port=1,always-plugged=on \

  -device usb-serial,chardev=c3,serial=MODEM-B2,port=1,always-plugged=on \
  -device usb-serial,chardev=c2,serial=GNSS-A1,port=2,always-plugged=on
```

## 5. 권한 — 비root 앱이 장치를 열게 하기

### 5.1 직관

장치 노드도 파일이므로 권한 검사는 똑같이 `uid`·`gid`·보조 그룹 대 노드의 owner·group·mode다. udev가 할 일은 노드의 **group과 mode**를 정하는 것이고, 앱 쪽이 할 일은 그 **그룹에 들어가는 것**이다. 둘 중 하나만 하면 안 열린다.

배포판 기본(`50-udev-default.rules`)이 이미 주는 그룹: `tty`·`ttyUSB*`·`ttyACM*` → `dialout`, `video*` → `video`, `snd/*` → `audio`, `i2c-*` → `i2c`(일부 배포판), 디스크 → `disk`. 데스크톱에서는 `TAG+="uaccess"`가 로그인 사용자에게 ACL을 주지만(예제 9에서 vivid 노드에 붙어 있다) **헤드리스 장비에는 로그인 seat가 없으니 의존하면 안 된다.**

### 5.2 예제 7 — 전용 그룹 `sensors`로 GNSS만 열어 주기

무엇을 확인하나: rule로 그룹을 바꾸기 전/후, 사용자를 그룹에 넣기 전/후에 일반 사용자 `app`(uid 1000)이 `/dev/gnss`를 열 수 있는지. 여는 쪽은 짧은 Python이다.

```python
# /usr/local/bin/l2_open.py <path> : try to open a device node and report
import os, sys
p = sys.argv[1]
try:
    fd = os.open(p, os.O_RDWR | os.O_NONBLOCK | os.O_NOCTTY)
    print("uid", os.getuid(), "groups", os.getgroups(), "open", p, "-> OK fd", fd)
except OSError as e:
    print("uid", os.getuid(), "groups", os.getgroups(), "open", p, "->", e.strerror)
```

`O_NONBLOCK`은 tty `open()`이 carrier(DCD)를 기다리며 멈추지 않게, `O_NOCTTY`는 열린 tty가 제어 터미널이 되지 않게 한다. rule은 GNSS 줄만 `GROUP="sensors"`로 바꾼다.

```text
SUBSYSTEM=="tty", ATTRS{serial}=="GNSS-A1", ENV{ID_USB_INTERFACE_NUM}=="00", SYMLINK+="gnss", GROUP="sensors", MODE="0660"
SUBSYSTEM=="tty", ATTRS{serial}=="MODEM-B2", ENV{ID_USB_INTERFACE_NUM}=="00", SYMLINK+="modem"
```

```sh
g 20 "echo == before; ls -l /dev/ttyUSB1; runuser -u app -- python3 /usr/local/bin/l2_open.py /dev/gnss"
put files/70-l2-serial.rules /etc/udev/rules.d/70-l2-serial.rules
g 30 "groupadd -r sensors; udevadm control --reload; udevadm trigger --action=change --settle /dev/gnss
echo == after rule; ls -l /dev/ttyUSB1; runuser -u app -- python3 /usr/local/bin/l2_open.py /dev/gnss
usermod -aG sensors app
echo == after usermod; runuser -u app -- python3 /usr/local/bin/l2_open.py /dev/gnss
runuser -u app -- python3 /usr/local/bin/l2_open.py /dev/modem"
```

```text
== before
crw-rw---- 1 root dialout 188, 1 Oct 18 04:33 /dev/ttyUSB1
uid 1000 groups [1000] open /dev/gnss -> Permission denied
== after rule
crw-rw---- 1 root sensors 188, 1 Oct 18 04:34 /dev/ttyUSB1
uid 1000 groups [1000] open /dev/gnss -> Permission denied
== after usermod
uid 1000 groups [987, 1000] open /dev/gnss -> OK fd 3
uid 1000 groups [987, 1000] open /dev/modem -> Permission denied
```

출력에서 볼 것:

- rule만 바꿔도 `app`은 여전히 못 연다 — 그룹에 없으니까. `usermod` 뒤에는 열린다(GID 987 = `sensors`, `groupadd -r`이 시스템 범위 GID를 줬다).
- 모뎀은 여전히 `dialout`이라 `app`은 못 연다. **장치별 최소 권한**이 된다. `app`을 `dialout`에 넣으면 시리얼 전부가 열린다.
- `groupadd`를 rule 로드보다 **먼저** 했다. 그룹이 없는 상태에서 rule을 읽으면 udevd가 경고를 남기고 그 GROUP을 무시한다(이 동작은 udev(7) 기준 설명이고, 이 랩에서 재현하지는 않았다). 이미지 빌드에서는 그룹을 `sysusers.d`(systemd-sysusers)나 Yocto `GROUPADD_PARAM`으로 만들어야 udevd보다 먼저 존재한다.
- 이미 돌고 있는 셸·프로세스의 보조 그룹은 `usermod`로 바뀌지 않는다(`runuser`가 새로 로그인하듯 그룹을 다시 읽어서 된 것). 서비스라면 유닛에 `SupplementaryGroups=sensors`를 쓰는 편이 깔끔하다(예제 11).

- "카메라" 하나가 `/dev/video`를 **네 개**(vid-cap, vid-out, meta-cap, meta-out) 만든다. 실제 UVC 카메라도 캡처 노드 + 메타데이터 노드 두 개를 만든다(커널 4.16+). 그래서 두 번째 카메라의 캡처는 `video1`이 아니라 `video2`(UVC)나 `video4`(여기)다. "카메라 N번 = `/dev/video<N>`" 가정은 처음부터 틀렸다.
- `index`는 **장치 하나 안에서** 노드의 순번이다(`video_device.index`, `get_index()`). 캡처 노드는 보통 `index=0`. 링크 이름의 `-video-index0`이 그것이다.
- 두 인스턴스가 모두 **같은 플랫폼 부모 `vivid.0`** 밑에 있다(이 6.18 vivid는 플랫폼 장치 하나에 인스턴스 여러 개를 올린다). 그래서 `ID_PATH`가 둘 다 `platform-vivid.0`이고, by-path 링크 이름이 **충돌**한다. `platform-vivid.0-video-index0`은 나중에 처리된 `video4`가 가져갔다.
- `/dev/v4l/by-id`는 아예 없다. `60-persistent-v4l.rules`가 by-id를 `ENV{ID_SERIAL}=="?*"`일 때만 만들고, `ID_SERIAL`은 `SUBSYSTEMS=="usb"`일 때 `usb_id`가 만든다. vivid는 USB가 아니라서 **실제 USB 카메라의 시리얼 동작은 이 랩에서 보여 줄 수 없다** — 그 부분은 §4의 usb-serial 실험(같은 `usb_id` builtin)으로 대신한다.

같은 rule 파일의 실제 내용(주석·빈 줄 제외):

```text
ACTION=="remove", GOTO="persistent_v4l_end"
SUBSYSTEM!="video4linux", GOTO="persistent_v4l_end"
ENV{MAJOR}=="", GOTO="persistent_v4l_end"
IMPORT{program}="v4l_id $devnode"
SUBSYSTEMS=="usb", IMPORT{builtin}="usb_id"
KERNEL=="video*", ENV{ID_SERIAL}=="?*", SYMLINK+="v4l/by-id/$env{ID_BUS}-$env{ID_SERIAL}-video-index$attr{index}"
TEST!="index", GOTO="persistent_v4l_end"
ATTR{index}!="?*", GOTO="persistent_v4l_end"
IMPORT{builtin}="path_id"
KERNEL=="video*|vbi*", ENV{ID_PATH}=="?*",                   SYMLINK+="v4l/by-path/$env{ID_PATH}-video-index$attr{index}"
KERNEL=="video*|vbi*", ENV{ID_PATH_WITH_USB_REVISION}=="?*", SYMLINK+="v4l/by-path/$env{ID_PATH_WITH_USB_REVISION}-video-index$attr{index}"
KERNEL=="audio*",      ENV{ID_PATH}=="?*",                   SYMLINK+="v4l/by-path/$env{ID_PATH}-audio-index$attr{index}"
KERNEL=="audio*",      ENV{ID_PATH_WITH_USB_REVISION}=="?*", SYMLINK+="v4l/by-path/$env{ID_PATH_WITH_USB_REVISION}-audio-index$attr{index}"
LABEL="persistent_v4l_end"
```

`GOTO` 탈출 패턴, `IMPORT{program}`(외부 도구 `v4l_id`가 `ID_V4L_*`를 출력), `$env{}`·`$attr{}` 치환이 다 들어 있는 교과서 같은 파일이다. 실제 USB 카메라 두 대라면 by-id는 `usb-<벤더>_<모델>_<시리얼>-video-index0`, by-path는 `platform-xhci-hcd.1.auto-usb-0:1:1.0-video-index0` 같은 모양이 된다(이 형식은 rule에서 읽은 것, 이 랩에서 실행한 출력은 아니다).

### 6.3 MIPI CSI 카메라라면

센서 키트의 카메라가 USB가 아니라 SoC의 CSI-2 수신기 + ISP로 들어오면 `/dev/video*`는 ISP 드라이버가 만들고, 하나의 카메라 파이프라인이 media controller 그래프(I5)의 여러 노드로 나뉜다. 번호는 여전히 probe 순서지만 부모 경로는 DT가 고정하므로 `KERNELS=="32e40000.csi"` 같은 플랫폼 장치 이름이나 `ATTR{name}`(드라이버가 정한 entity 이름)으로 매칭한다. libcamera 같은 프레임워크는 아예 media 그래프를 직접 열거해서 노드를 찾는다(I5 §9의 `i5_topo`와 같은 방식). 이 경우 udev rule은 주로 **권한**만 담당한다.

## 7. 장치가 생기면 서비스 시작 — `RUN+=`가 아니라 `SYSTEMD_WANTS`

### 7.1 직관

`RUN+=`은 rule 평가가 끝난 뒤 **그 이벤트를 처리하던 워커 안에서, 동기로** 실행된다. 펌웨어로 치면 "인터럽트 핸들러의 bottom half에서 긴 작업을 돌리는 것"이다. 그 동안 그 장치(와 의존 장치)의 이벤트는 멈추고, 끝나면 워커가 다음 이벤트로 넘어가며 남은 자식 프로세스를 정리한다. 또 udevd 자체가 샌드박스 안에 있다. 게스트의 `systemd-udevd.service`(주석·빈 줄 제외, 일부):

```text
[Service]
CapabilityBoundingSet=~CAP_SYS_TIME CAP_WAKE_ALARM
Delegate=pids
DelegateSubgroup=udev
Type=notify-reload
...
KillMode=mixed
PrivateMounts=yes
ProtectHostname=yes
MemoryDenyWriteExecute=yes
RestrictAddressFamilies=AF_UNIX AF_NETLINK AF_INET AF_INET6
...
SystemCallFilter=@system-service @module @raw-io bpf
SystemCallFilter=~@clock
SystemCallErrorNumber=EPERM
...
IPAddressDeny=any
WatchdogSec=3min
```

`IPAddressDeny=any`(cgroup BPF로 모든 IP 패킷 차단), `PrivateMounts=yes`(RUN이 한 `mount`는 udevd의 마운트 네임스페이스에만 생겨 다른 프로세스에 안 보임). 그래서 udev(7) 문서는 RUN에 대해 "네트워크 접근·마운트 금지, 데몬 시작 금지 — 짧은 작업만"이라고 못 박는다.

대안은 **systemd에게 일을 넘기는 것**이다. rule은 `TAG+="systemd"`로 장치를 systemd에 보이게 하고 `ENV{SYSTEMD_WANTS}+="foo@%k.service"`로 "이 `.device` 유닛이 활성화되면 이 서비스도 원한다"를 적는다. 그러면 서비스는 PID 1이 자기 cgroup에서, 재시작 정책·로그·사용자·권한 설정과 함께 띄운다(유닛 문법은 L1).

### 7.2 예제 11 — GNSS가 꽂히면 `l2-gnss@ttyUSBn.service` 시작, 뽑으면 정지

무엇을 확인하나: 템플릿 서비스를 rule에서 원하게(Wants) 하고, `BindsTo=`로 장치와 수명을 묶는다.

```text
# /etc/systemd/system/l2-gnss@.service
[Unit]
Description=L2 GNSS reader on /dev/%I
BindsTo=dev-%i.device
After=dev-%i.device

[Service]
User=app
SupplementaryGroups=sensors
ExecStart=/bin/sh -c 'python3 /usr/local/bin/l2_open.py /dev/%I; exec sleep infinity'
```

```text
# /etc/udev/rules.d/71-l2-systemd.rules
# L2: let systemd start a reader service when the GNSS adapter appears
SUBSYSTEM=="tty", ENV{ID_SERIAL_SHORT}=="GNSS-A1", TAG+="systemd", ENV{SYSTEMD_WANTS}+="l2-gnss@%k.service"
```

- `%k`는 udev 치환(커널 이름 `ttyUSB0`), `%i`/`%I`는 systemd 치환(인스턴스 이름). `dev-%i.device`는 `/dev/ttyUSB0`의 장치 유닛 이름 `dev-ttyUSB0.device`가 된다.
- `ENV{ID_SERIAL_SHORT}`로 매칭했다 — 60번대 rule이 만든 속성이므로 파일 번호는 71.
- tty는 `99-systemd.rules`가 이미 `systemd` 태그를 붙이지만, 모든 subsystem이 그런 건 아니다(예: 많은 `misc`, `iio`). 그래서 항상 명시한다.

```sh
put files/l2-gnss@.service /etc/systemd/system/l2-gnss@.service
put files/71-l2-systemd.rules /etc/udev/rules.d/71-l2-systemd.rules
g 30 "systemctl daemon-reload; udevadm control --reload"
l2_mon.sh "device_add usb-serial,chardev=c2,serial=GNSS-A1,id=gnss,always-plugged=on"; sleep 40
g 20 'systemctl list-units --no-legend "l2-gnss@*"; systemctl status --no-pager -n 3 "l2-gnss@*"'
```

### 7.4 예제 13 — RUN이 띄운 "데몬"은 이벤트가 끝나면 사라지고, 네트워크는 막혀 있다

무엇을 확인하나: `$$`로 고치고 45초 작업은 뺀 버전. 백그라운드 프로세스가 언제까지 사는지 1초 간격으로 보고, 같은 네트워크 스크립트를 셸(샌드박스 밖)과 RUN(안)에서 비교한다.

```text
# /etc/udev/rules.d/72-l2-run.rules (fixed: $$ = literal $)
ACTION=="add", SUBSYSTEM=="tty", ENV{ID_SERIAL_SHORT}=="MODEM-B2", RUN+="/bin/sh -c 'setsid sleep 300 >/dev/null 2>&1 & echo $$! > /run/l2_bg.pid'"
ACTION=="add", SUBSYSTEM=="tty", ENV{ID_SERIAL_SHORT}=="MODEM-B2", RUN+="/usr/bin/python3 /usr/local/bin/l2_net.py"
```

```sh

rm -f /run/l2_bg.pid /run/l2_net.log; echo shell-side:; python3 /usr/local/bin/l2_net.py; cat /run/l2_net.log; rm /run/l2_net.log"
l2_mon.sh "device_del modem"; sleep 3
l2_mon.sh "device_add usb-serial,chardev=c3,serial=MODEM-B2,id=modem,always-plugged=on"; sleep 1
for i in 1 2 3 4 5 6; do
  g 10 'echo t=$(cut -d" " -f1 /proc/uptime) pidfile=$(cat /run/l2_bg.pid 2>/dev/null) alive=$(pgrep -x sleep -a | grep 300)'
  sleep 1
done
g 10 "cat /run/l2_net.log"
```

출력에서 볼 것:

- `setsid ... &`로 세션까지 떼어 낸 `sleep 300`(PID 680)이 이벤트 처리 중(네트워크 스크립트가 3초 타임아웃으로 기다리는 동안)에는 살아 있다가, 이벤트가 끝난 뒤(371.6~374.2 s 사이) **사라졌다.** udevd는 워커가 띄운 프로세스를 이벤트가 끝나면 정리한다(udev(7): "the forked processes, detached or not, will be unconditionally killed after the event handling has finished"). 데몬을 RUN으로 띄우면 "가끔 동작하다 사라지는" 버그가 된다.
- 같은 `l2_net.py`가 셸에서는 `connected`, RUN에서는 `timed out`. `IPAddressDeny=any`는 cgroup BPF가 패킷을 **버리기** 때문에 EPERM이 아니라 타임아웃으로 보인다. "RUN에서 MQTT로 장치 연결을 알리는" 코드가 현장에서 조용히 안 되는 이유다.

### 7.5 그럼 RUN은 언제 쓰나

| 쓰는 곳 | 예 |
|---|---|
| 짧고 동기여야 하는 설정 | sysfs 속성 쓰기(`ATTR{queue/scheduler}="mq-deadline"`는 RUN 없이 대입으로), `ethtool`·`hdparm` 한 번, 펌웨어 파라미터 |
| builtin 호출 | `RUN{builtin}+="kmod load $env{MODALIAS}"`(80-drivers.rules), `net_setup_link` |
| systemd에 이벤트 전달 | `systemd-run --no-block`으로 일회성 유닛 띄우기 (RUN 자체는 즉시 끝남) |

긴 일·데몬·네트워크·마운트 → `SYSTEMD_WANTS` + 서비스 유닛. 마운트는 `.mount` 유닛이나 `systemd-mount`.

## 8. coldplug와 부팅 — `udevadm trigger`, `settle`, 그리고 장치 대기

### 8.1 coldplug 대상 보기

G9 §5에서 개념을 봤다. 커널은 udevd보다 먼저 대부분 장치를 만들었으므로, `systemd-udev-trigger.service`가 `/sys`의 모든 장치 `uevent` 파일에 `add`를 써서 이벤트를 다시 받는다. 몇 개나 되나:

### 8.3 `udevadm settle`은 왜 피하나

`settle`은 "**지금** udev 큐가 비었다"만 보장한다. 늦게 열거되는 USB 장치(예제 6에서 200초 뒤에 붙은 FTDI)는 큐에 아직 없으니 기다려 주지 않는다. 동시에 큐가 빌 때까지 부팅 전체를 막는다. `systemd-udev-settle.service`는 그래서 deprecated이고, 서비스는 **필요한 장치의 `.device` 유닛**에 의존한다:

```text
[Unit]
BindsTo=dev-cam_front.device
After=dev-cam_front.device
```

`dev-cam_front.device`는 udev가 `/dev/cam_front` 링크를 만든 순간 활성화된다. "부팅 후 카메라 앱이 가끔 카메라를 못 찾는다"의 정석 해결이다.

## 9. 네트워크 인터페이스 이름 — predictable names와 `.link` 파일

### 9.1 이름이 정해지는 곳

네트워크 인터페이스는 `/dev` 노드가 없고, udev가 **진짜 이름을 바꾸는** 유일한 대상이다. 커널은 `eth0`으로 등록하고, udev의 `80-net-setup-link.rules`가 `net_setup_link` builtin을 불러 `.link` 파일 정책대로 이름을 바꾼다. 기본 정책 파일:

```text
# /usr/lib/systemd/network/99-default.link (주석 제외)
[Match]
OriginalName=*
[Link]
NamePolicy=keep kernel database onboard slot path
AlternativeNamesPolicy=database onboard slot path
MACAddressPolicy=persistent
```

`NamePolicy`는 앞에서부터 시도할 이름 출처다. `onboard`(펌웨어가 알려 준 내장 번호, `eno1`), `slot`(PCIe 핫플러그 슬롯, `ens1`), `path`(버스 위치, `enp0s1`), `mac`(`enx525400123456`). 게스트에서 실제로 계산된 후보들:

```sh
g 60 "ip -br link; udevadm info -q property /sys/class/net/enp0s1 | grep -E 'ID_NET_NAME|ID_PATH=|ID_NET_LINK_FILE|ID_NET_DRIVER'"
```

```text
lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP> 
enp0s1           UP             52:54:00:12:34:56 <BROADCAST,MULTICAST,UP,LOWER_UP> 
ID_NET_DRIVER=virtio_net
ID_NET_NAME_MAC=enx525400123456
ID_NET_NAME_PATH=enp0s1
ID_PATH=platform-4010000000.pcie-pci-0000:00:01.0
ID_NET_LINK_FILE=/usr/lib/systemd/network/99-default.link
ID_NET_NAME=enp0s1
```

ARM SoC 내장 이더넷(DT의 플랫폼 장치)은 PCI 경로가 없어서 정책이 이름을 못 만들고 `eth0`으로 남는 경우가 많다(systemd 버전·naming scheme에 따라 다르다 — `systemd.net-naming-scheme(7)`). 즉 **ARM 보드에서는 "예측 가능한 이름"이 저절로 생기지 않을 수 있다.** 그래서 제품은 `.link`로 직접 정한다.

### 9.3 무엇으로 매칭하나

| `[Match]` 키 | 장점 | 함정 |
|---|---|---|
| `MACAddress=` | 장치 고유 | MAC이 OTP·EEPROM에 없고 부팅마다 랜덤인 보드(일부 SoC 기본)면 못 쓴다 |
| `Path=` (예: `platform-30be0000.ethernet`) | 보드 배선 = 역할, 교체에 강함 | DT 노드 주소가 바뀌면 같이 |
| `Driver=`, `Type=` | 간단 | 같은 드라이버 NIC 두 개면 구분 불가 |
| `OriginalName=eth0` | 가장 쉬움 | `eth0` 번호 자체가 probe 순서 — 피할 것 |

`net.ifnames=0`을 커널 cmdline에 주면 `99-default.link`의 정책이 꺼져 `eth0`으로 돌아간다(우리 `.link`의 `Name=`은 여전히 적용된다). initramfs에서 네트워크(NFS root 등)를 쓰는 장비라면 같은 `.link`를 initramfs에도 넣어야 이름이 일치한다.

## 11. 커널 안에서는 무슨 일이 일어나나

예제 1의 USB 시리얼 하나를 커널 함수로 따라간다(6.18 소스 기준 위치).

1. xHCI가 포트 상태 변화를 알리면 hub 스레드가 장치를 열거하고 `usb_new_device()` → `device_add()`로 `1-1`(usb_device)을 등록한다. 설정이 선택되면 인터페이스 `1-1:1.0`도 `device_add()`된다.
2. `device_add()`(`drivers/base/core.c`)는 노드가 있는 장치면 먼저 `devtmpfs_create_node(dev)`(3731행)로 `/dev`에 노드를 만들고, 그 다음 `kobject_uevent(&dev->kobj, KOBJ_ADD)`(3738행)를 부른다. 그래서 KERNEL 이벤트가 도착했을 때 노드는 이미 있다.
3. `kobject_uevent_env()`(`lib/kobject_uevent.c` 473행)가 `ACTION`/`DEVPATH`/`SUBSYSTEM`/`SEQNUM`을 넣고 bus·class·type의 uevent 콜백(G9 §2.1)을 불러 변수를 채운다 — USB 버스의 콜백이 `PRODUCT`, `INTERFACE`, `MODALIAS`를 넣는다. 버퍼는 `UEVENT_BUFFER_SIZE` 2048바이트(`include/linux/kobject.h`). 그리고 `netlink_broadcast()`로 group 1에 보낸다(`uevent_net_broadcast_untagged()`).
4. udevd가 받아 `MODALIAS`로 `ftdi_sio`를 로드한다(`80-drivers.rules`, G9 §4). 드라이버 probe에서 usb-serial 코어가 `allocate_minors()`(`drivers/usb/serial/usb-serial.c` 84행)로 **`idr_alloc()`의 가장 작은 빈 minor**를 받는다 — `ttyUSB<N>` 순서 문제의 근원. `usb_serial_device_probe()`가 `tty_port_register_device()`(`drivers/usb/serial/bus.c` 53행)로 tty class 장치를 만들고, 다시 1~3이 반복된다.
5. V4L2도 같다. `__video_register_device()`(`drivers/media/v4l2-core/v4l2-dev.c` 910행)가 `devnode_find()`로 빈 번호를 찾아 `videoN`을 정하고(1009행), `get_index()`로 같은 `v4l2_device` 안의 순번 `index`를 매긴다(1042행). udev rule의 `$attr{index}`가 이 값이다.
6. 유저 공간: udevd 워커가 rule을 돌리고 링크·권한·db를 적용한 뒤 udev 고유 헤더(libudev monitor 형식)를 붙여 netlink **group 2**로 재방송한다. systemd PID 1은 sd-device monitor로 group 2를 듣고, `systemd` 태그가 있으면 `.device` 유닛을 "plugged"로 만들어 `SYSTEMD_WANTS`를 실행한다.

- **G9 §2**: 드라이버가 `add_uevent_var()`로 역할 정보(예: DT `label`)를 uevent에 넣으면 rule이 `ENV{}`로 바로 매칭한다 — 부모 탐색이 필요 없다.
- **G8**: rule의 `ATTR{}`은 sysfs 속성이다. 드라이버가 `name`, `serial`, `label` 같은 **읽기 전용·고유** 속성을 노출하면 udev 친화적인 드라이버가 된다. 반대로 `ATTR{x}="값"` 대입은 sysfs `store`를 부른다.
- **I5**: `video_register_device()` 전에 모든 준비를 끝내야 하는 이유 — udev가 즉시 노드를 열 수 있다(권한 적용 전에 열 수 있는 쪽은 root뿐이지만).

## 12. Embedded 실무에서 다시 보기

### 12.1 센서 키트 rule 한 장

예를 들어 Jetson Orin 기반 센서 키트(USB 카메라 2대, USB GNSS, LTE 모뎀, CAN-USB, I2C IMU)라면 제품 rule은 한 파일로 모은다. (아래 값은 예시 — 이 노트에서 실행하지 않음. 실제 값은 `udevadm info -a`로 채운다.)

```text
# /etc/udev/rules.d/70-sensorkit.rules  (example, not executed here)
# cameras: identical models without serial -> key on physical port, capture node only
SUBSYSTEM=="video4linux", ENV{ID_PATH}=="platform-3610000.usb-usb-0:1.1:1.0", ATTR{index}=="0", SYMLINK+="sensorkit/cam_front", GROUP="video", MODE="0660", TAG+="systemd"
SUBSYSTEM=="video4linux", ENV{ID_PATH}=="platform-3610000.usb-usb-0:1.2:1.0", ATTR{index}=="0", SYMLINK+="sensorkit/cam_rear", GROUP="video", MODE="0660", TAG+="systemd"
# GNSS: has a unique FTDI serial
SUBSYSTEM=="tty", ENV{ID_VENDOR_ID}=="0403", ENV{ID_SERIAL_SHORT}=="FT9ABC12", SYMLINK+="sensorkit/gnss", GROUP="sensors", MODE="0660", TAG+="systemd", ENV{SYSTEMD_WANTS}+="gnssd.service"
# LTE modem: several ttys per device, pick the AT port by interface number
SUBSYSTEM=="tty", ENV{ID_VENDOR_ID}=="2c7c", ENV{ID_USB_INTERFACE_NUM}=="02", SYMLINK+="sensorkit/modem_at"
# I2C IMU on bus 1 addr 0x68 (fixed by DT)
SUBSYSTEM=="iio", KERNELS=="1-0068", SYMLINK+="sensorkit/imu", GROUP="sensors", MODE="0660"
```

- 링크를 `sensorkit/` 하위 디렉터리에 모으면 앱 설정이 단순해지고 다른 패키지 rule과 이름이 안 부딪힌다.
- 이 파일은 Yocto 레시피(`SRC_URI += "file://70-sensorkit.rules"`, `do_install`에서 `${sysconfdir}/udev/rules.d`)로 이미지에 넣는다. 읽기 전용 rootfs + A/B OTA(L4)에서는 rule 변경도 OTA로만 배포된다.
- `sensors` 그룹은 `sysusers.d`로 만든다(§5 함정).

### 12.2 현장 진단 순서 — "앱이 카메라를 못 연다"

```sh
ls -l /dev/sensorkit/                 # link exists? which node?
udevadm info -q all -n /dev/video2    # properties, DEVLINKS, TAGS
udevadm info -a -n /dev/video2 | less # keys to match
udevadm test /sys/class/video4linux/video2 2>&1 | grep -n 70-sensorkit   # did my lines fire?
journalctl -b -u systemd-udevd        # invalid rules, worker timeouts
systemctl status dev-sensorkit-cam_front.device
id appuser; systemctl show -p SupplementaryGroups camera-app.service
```

링크가 없다 → rule 매칭(§3, 부모 하나·속성 출처·파일 번호). 링크는 있는데 `EACCES` → 그룹 가입·`SupplementaryGroups`(§5). 서비스가 장치보다 먼저 떴다 → `.device` 의존(§8.3). 가끔 이름이 바뀐다 → 키가 순서 의존(`%n`, `KERNEL=="video0"`)인지 확인(§4).

### 12.3 같은 모델 카메라 교체 (현장 RMA)

serial 기반이면 교체한 카메라는 새 시리얼이라 링크가 사라진다. 운영 선택지: (1) by-path(포트 고정) + 케이블 라벨, (2) serial 기반이되 매핑을 쓰기 가능한 설정 파티션에 두고, 부팅 초기 스크립트가 `/run/udev/rules.d/70-site.rules`를 생성(§2.1의 `/run` 디렉터리 용도), (3) 현장 프로비저닝 도구가 "앞 카메라를 가려 주세요" 같은 절차로 매핑을 다시 기록. 국방·로보틱스 장비는 정비 절차를 단순하게 하려고 (1)을 많이 고른다.

## 14. 면접에서 이렇게 말한다

**Q.** Two cameras swap /dev/video0 and /dev/video1 after a reboot. How do you fix it?

**A.** 먼저 원인을 말한다 — `videoN` 번호는 드라이버가 `video_register_device()`를 부른 순서라 USB 열거·probe 타이밍이 바뀌면 바뀐다. 고정 이름은 udev가 준다. 카메라에 고유 시리얼이 있으면 `/dev/v4l/by-id`(USB `iSerial` 기반), 시리얼이 없거나 같은 모델 두 개면 물리 포트 기반 `/dev/v4l/by-path`를 쓴다. 제품에서는 역할 이름이 필요하니 `udevadm info -a`로 키를 골라 `SUBSYSTEM=="video4linux", ENV{ID_PATH}=="...", ATTR{index}=="0", SYMLINK+="cam_front"` 같은 rule을 쓰고, `udevadm test`로 검증한 뒤 앱은 `/dev/cam_front`만 연다. 그리고 `index`를 꼭 넣는다 — UVC 카메라 하나가 video 노드를 두 개(캡처 + 메타데이터) 만들기 때문이다.

> The numbers come from registration order, so any change in USB enumeration or probe timing can swap them; the kernel never promised stability. The fix is to never open videoN directly. If the cameras have unique serial numbers I use /dev/v4l/by-id, which is built from the USB serial; if they're identical units without serials I key on the physical port with /dev/v4l/by-path. For a product I write a small udev rule that matches the port path or serial plus ATTR{index}=="0" — because a UVC camera exposes a capture node and a metadata node — and creates a role name like /dev/cam_front. I verify it with udevadm test and make the application and its systemd unit depend on that name.

**꼬리 질문**: "What if the cameras are on an internal MIPI CSI bus?" → 노드 번호는 여전히 probe 순서지만 DT가 노드를 고정하므로 `KERNELS`의 플랫폼 장치 이름(또는 media 그래프의 entity 이름, I5)으로 매칭한다.

**Q.** Why shouldn't you start a daemon from RUN+=?

**A.** RUN은 udev 워커가 이벤트 하나를 처리하는 도중에 동기로 실행된다. 그래서 오래 걸리면 그 장치의(그리고 의존 이벤트의) 처리가 막히고, 이벤트 타임아웃(기본 180초)이 지나면 워커와 함께 죽는다. 또 이벤트가 끝나면 워커가 띄운 남은 프로세스는 백그라운드로 떼어 놓아도 정리된다 — 이 노트 예제 13에서 `setsid ... &`로 띄운 sleep이 사라졌다. 게다가 `systemd-udevd.service`는 네트워크 차단·별도 마운트 네임스페이스 샌드박스라 데몬이 할 일을 못 한다. 정답은 `TAG+="systemd", ENV{SYSTEMD_WANTS}+="foo@%k.service"`로 systemd에게 서비스 시작을 맡기는 것이다. 그러면 재시작 정책·로그·cgroup·장치가 빠질 때 함께 멈추기(`BindsTo=`)까지 생긴다.

> RUN programs execute synchronously inside the udev worker that is processing that event. A long-running one blocks event processing for that device, it gets killed when the event timeout expires, and udev cleans up any processes left over when the event finishes, even if they daemonize. The udevd service is also sandboxed — no network, private mount namespace — so a daemon wouldn't work properly anyway. The right pattern is to tag the device for systemd and set SYSTEMD_WANTS to a service, usually a template instance with the kernel name. systemd then starts it in its own cgroup with restart policy and logging, and with BindsTo on the device unit it stops automatically when the device is unplugged.

**Q.** Explain the difference between ATTR and ATTRS in a udev rule.

**A.** `ATTR{}`, `KERNEL`, `SUBSYSTEM`, `DRIVER`는 이벤트가 난 장치 자신만 본다. `ATTRS{}`, `KERNELS`, `SUBSYSTEMS`, `DRIVERS`는 장치 자신부터 sysfs 부모를 하나씩 올라가며 찾는데, 한 줄 안의 이 키들은 **같은 장치 하나**에서 모두 맞아야 한다. 그래서 USB 인터페이스의 `bInterfaceNumber`와 USB 장치의 `serial`을 한 줄에 쓰면 조용히 안 맞는다. 해결은 한 부모의 속성만 쓰거나 builtin이 만든 `ENV{ID_SERIAL_SHORT}`, `ENV{ID_USB_INTERFACE_NUM}` 같은 속성을 쓰는 것이다.

> ATTR, KERNEL, SUBSYSTEM and DRIVER match only the device that generated the event. The plural forms walk up the sysfs parent chain, but within one rule all the plural keys must match on the same single parent. So a rule that combines the interface number from the USB interface with the serial from the USB device silently never matches. I either match attributes of one parent only, or use the properties the usb_id builtin already exports, like ID_SERIAL_SHORT and ID_USB_INTERFACE_NUM, which are flattened onto the device.

**Q.** Where do udev rules live and how do you override a vendor rule?

**A.** `/usr/lib/udev/rules.d`(패키지·OS 이미지), `/etc/udev/rules.d`(관리자), `/run/udev/rules.d`(런타임). 세 곳을 파일 **이름**으로 합쳐 사전순으로 처리하고, 같은 이름이면 `/etc`가 `/run`보다, `/run`이 `/usr/lib`보다 우선이다. 벤더 rule을 고치려면 같은 이름으로 `/etc`에 복사해 고치고, 끄려면 `/etc/udev/rules.d/<같은이름> → /dev/null` 링크를 만든다. 읽기 전용 rootfs + OTA 장비라면 이 rule을 이미지 빌드(Yocto 레시피)에 넣는다.

> There are three directories: /usr/lib/udev/rules.d for the OS image, /etc/udev/rules.d for local admin, and /run/udev/rules.d for runtime-generated rules. udev merges them by file name and processes them in lexical order; for the same file name, /etc wins over /run, which wins over /usr/lib. To override a vendor rule you copy it under the same name into /etc, and to disable it you symlink that name to /dev/null. On a read-only, OTA-updated rootfs I'd bake the rule into the image build rather than editing on the device.

**Q.** How do you get a stable network interface name on an embedded board?

**A.** systemd-udevd의 `net_setup_link` builtin이 `.link` 파일을 보고 이름을 정한다. 기본(`99-default.link`)은 `NamePolicy=`에 따라 `enp0s1`처럼 버스 위치 기반 예측 가능한 이름이다. 제품에서 역할 이름이 필요하면 `/etc/systemd/network/10-lan.link`에 `[Match] MACAddress=` 또는 `Path=`, `[Link] Name=lan0`을 쓴다. `NAME=`을 쓰는 udev rule도 되지만 `.link`가 표준이다. 커널 cmdline `net.ifnames=0`은 이 정책을 꺼서 `eth0`로 돌아간다. 이름 변경은 인터페이스가 up 되기 전에만 되므로 initramfs에서 네트워크를 쓰면 initramfs에도 같은 `.link`를 넣는다.

> Interface naming is done by udev's net_setup_link builtin using .link files. The default policy gives predictable names based on the bus location, like enp0s1. For a product I add a .link file with a lower number than 99-default, match on the MAC address or the device path, and set Name to something like lan0. net.ifnames=0 on the kernel command line disables the policy and gives back eth0. Renaming only works before the interface is brought up, so if the initramfs configures networking, the same .link file has to be in the initramfs too.

**Q.** On a small embedded device, would you use udev, mdev or a static /dev?

**A.** 기능 장비(고정 하드웨어, 핫플러그 없음, 부팅 시간·용량이 중요)면 devtmpfs만 또는 devtmpfs + mdev로 충분하다. USB 카메라·시리얼·저장장치처럼 핫플러그가 있고, `by-id`·`by-path` 같은 안정 이름, 권한 정책, systemd 장치 유닛 의존성이 필요하면 systemd 기반 이미지의 udev가 낫다. 정적 `/dev`(`mknod`)는 devtmpfs 시대에는 initramfs의 `/dev/console` 정도만 남는다. 결정 기준은 핫플러그 여부, rootfs 크기, 부팅 시간, 그리고 이미 systemd를 쓰는지다.

> It depends on the hardware and the init system. For a fixed-function box with no hotplug where boot time and size matter, devtmpfs alone or with BusyBox mdev is enough. If there are hotplug USB cameras, serial adapters or storage, and I want by-id and by-path names, permission policy and systemd device dependencies, I'd use udev — it comes with systemd anyway. A static /dev made with mknod is basically gone since devtmpfs; maybe a console node in the initramfs.

**Q.** What does `udevadm trigger` do at boot, and what's `udevadm settle`?

**A.** coldplug(G9 §5)다. 커널은 udevd보다 먼저 대부분 장치를 만들었으므로 `systemd-udev-trigger.service`가 `/sys`의 모든 장치 `uevent` 파일에 `add`를 써서 이벤트를 다시 보내게 한다. `settle`은 udev 이벤트 큐가 빌 때까지 기다리는 것이고 `systemd-udev-settle.service`가 그것을 서비스로 만든 것인데, 늦게 나타나는 장치는 보장하지 못하고 부팅을 늦추기 때문에 deprecated다. 특정 장치를 기다려야 하면 그 장치의 `.device` 유닛에 의존한다.

> At boot most devices already exist before udevd starts, so systemd-udev-trigger writes "add" to every device's uevent file to replay the events — that's coldplug. udevadm settle just waits until the udev event queue is empty. It's deprecated as a boot dependency because an empty queue doesn't mean a slow USB device has enumerated yet, and it delays boot. If a service needs a specific device, it should depend on that device's .device unit, which udev creates via TAG+="systemd".

## 15. 직접 해보기

1. (개념) `udevadm info -a`의 출력에서 "looking at device"와 "looking at parent device" 블록은 각각 어떤 rule 키와 대응하나? 한 줄에 `KERNELS=="1-1"`과 `ATTRS{bInterfaceNumber}=="00"`을 같이 쓰면 왜 안 맞나? 정답/힌트: 첫 블록은 단수 키(`KERNEL`, `ATTR`), 모든 블록은 복수 키 대상. `bInterfaceNumber`는 인터페이스 `1-1:1.0`에 있고 `1-1`에는 없다 — 한 줄의 복수 키는 한 부모에서 모두 맞아야 한다.
2. (실습) §4의 두 USB 시리얼 랩에서 `serial=` 대신 같은 serial 두 개를 주고(`serial=SAME`) `/dev/serial/by-id`가 어떻게 되는지 확인하라. 그다음 by-path로 바꿔 rule을 다시 써라. 정답/힌트: 같은 by-id 링크 이름을 두 장치가 다투므로 나중 장치가 링크를 가져간다(우선순위 `link_priority`가 같을 때). 포트 기반 `ENV{ID_PATH}`로 구분한다.
3. (실습) vivid를 `n_devs=3`으로 올리고 `/dev/cam_*` rule이 세 번째 인스턴스에 무엇을 하는지 예측한 뒤 확인하라. 정답/힌트: 예제 10의 rule은 `vivid-000-vid-cap`, `vivid-001-vid-cap` 이름만 매칭하므로 세 번째(`vivid-002-vid-cap`)는 역할 링크가 없고, by-path 충돌은 세 개로 늘어난다. 예측과 다르면 `udevadm test`로 줄 단위 매칭을 본다.
4. (실습) `/etc/udev/rules.d/60-persistent-v4l.rules → /dev/null` 마스킹 후 `udevadm trigger -s video4linux`를 하면 `/dev/v4l/`이 어떻게 되나? 원복하라. 정답/힌트: 예제 2의 `60-serial.rules`와 같은 패턴이므로 by-path 링크가 사라질 것으로 예상된다(직접 확인할 것). 링크를 지우고 reload + trigger로 원복.
5. (실습) `TAG+="systemd"` 없이 `ENV{SYSTEMD_WANTS}`만 주면 서비스가 시작되나? `systemctl list-units --type=device`로 확인하라. 정답/힌트: 아니다. systemd는 `systemd` 태그가 붙은 장치만 `.device` 유닛으로 만들고, `SYSTEMD_WANTS`는 그 유닛의 Wants= 로 해석된다. 단 tty·block·net 같은 일부 subsystem은 `99-systemd.rules`가 이미 태그를 붙인다.
6. (관찰) `udevadm monitor --kernel --udev --property`를 켠 채 USB 장치를 `device_del` 해서 remove 이벤트에서 `DEVLINKS`가 어떻게 나오는지, 링크가 언제 사라지는지 본다. 정답/힌트: KERNEL remove → UDEV remove 순서, UDEV 이벤트의 `DEVLINKS`에 지워질 링크가 들어 있다.
7. (설계) 읽기 전용 rootfs + A/B OTA(L4) 장비에서 현장마다 다른 카메라 매핑(`front`가 어느 포트인지)을 어떻게 저장하고 적용할지 설계하라. 정답/힌트: rule은 이미지에, 매핑 값은 쓰기 가능한 `/data`(또는 `/etc` overlay)의 설정에 두고 `IMPORT{file}=` 또는 부팅 초기 생성하는 `/run/udev/rules.d/` rule로 적용한다.

## 16. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| uevent | kernel object event | `kobject_uevent()`가 netlink로 보내는 `ACTION=` 등 KEY=VALUE 묶음 (G9) |
| systemd-udevd | udev 데몬 | 커널 uevent를 받아 rule·builtin을 실행하고 결과를 udev db와 group 2로 재방송 |
| udev db | `/run/udev/data/` | 장치별 udev 속성(`E:`), 링크(`S:`), 태그 저장소. libudev·systemd가 읽는다 |
| rule | `.rules` 파일의 한 줄 | 매칭 키 + 대입 키. 모두 맞으면 대입 실행 |
| builtin | udevd 내장 기능 | `path_id`, `usb_id`, `input_id`, `hwdb`, `net_id`, `net_setup_link`, `kmod`, `blkid` |
| hwdb | hardware database | modalias 패턴 → 속성 표, `systemd-hwdb update`로 `hwdb.bin` 컴파일 |
| DEVLINKS | 링크 목록 속성 | 그 장치가 가진 `/dev` 심볼릭 링크들 (`S:` 항목) |
| ID_PATH | 물리 경로 속성 | `path_id`가 만든 버스 위치 문자열, `by-path` 링크의 재료 |
| ID_SERIAL | 시리얼 속성 | `usb_id` 등이 만든 "벤더_모델_시리얼", `by-id` 링크의 재료 |
| coldplug | 부팅 재생 | `udevadm trigger`로 이미 있는 장치의 add 이벤트를 다시 보냄 |
| `.link` 파일 | systemd.link | NIC 이름·MAC·오프로드 정책. `net_setup_link` builtin이 적용 |
| predictable interface names | 예측 가능한 이름 | `enp0s1`, `wlp2s0`처럼 버스 위치 기반 NIC 이름 |
| `SYSTEMD_WANTS` | udev 속성 | 장치의 `.device` 유닛이 활성화될 때 함께 시작할 유닛 |
| `uaccess` | 태그 | 로그인한 seat 사용자에게 ACL로 장치 접근 허용 (데스크톱용) |
| vivid | Virtual Video Test Driver | 실제 하드웨어 없는 V4L2 테스트 드라이버, `n_devs`로 인스턴스 수 지정 |

## 17. 요약 & 체크리스트

커널은 장치가 생기면 devtmpfs로 노드를 만들고 uevent를 방송할 뿐이다. 이름·권한·안정 링크·서비스 시작은 systemd-udevd가 rule로 정한다. rule은 세 디렉터리를 파일 이름순으로 합친 목록이고 `/etc`가 이긴다. 단수 키는 장치 자신, 복수 키는 부모 하나를 본다 — 두 부모를 섞으면 조용히 실패한다. 커널 번호(`ttyUSB0`, `vdb`, `video1`)는 순서에 따라 바뀌므로 serial 기반 `by-id`, 포트 기반 `by-path`, 또는 직접 쓴 역할 이름 SYMLINK를 쓴다. 비root 앱은 GROUP/MODE + 보조 그룹으로 연다. 긴 작업은 RUN이 아니라 `TAG+="systemd"` + `SYSTEMD_WANTS`로 systemd에 맡긴다. NIC 이름은 `.link` 파일로 고정한다. 작은 장비는 mdev나 devtmpfs만으로도 충분할 수 있다.

- [ ] uevent가 udevd를 거쳐 udev db, 링크, systemd `.device` 유닛까지 가는 길을 그릴 수 있다
- [ ] rule 디렉터리 세 곳의 우선순위와 덮어쓰기·`/dev/null` 마스킹을 설명할 수 있다
- [ ] `==`, `!=`, `=`, `+=`, `:=`의 차이와 단수/복수 키의 "부모 하나" 규칙을 설명할 수 있다
- [ ] `udevadm info -a`로 매칭 키를 골라 rule을 쓰고 `udevadm test`로 미리 검증할 수 있다
- [ ] `udevadm monitor --kernel --udev --property`로 KERNEL/UDEV 이벤트 차이를 읽을 수 있다
- [ ] 장치 순서가 바뀌는 문제를 재현하고 serial/by-path/역할 이름으로 고칠 수 있다
- [ ] UVC·vivid 카메라에 `/dev/cam_front` 같은 이름을 줄 수 있고 `index` 함정을 안다
- [ ] GROUP/MODE와 보조 그룹으로 비root 앱이 장치를 열게 할 수 있다
- [ ] RUN+=의 제약(동기·타임아웃·자식 정리·샌드박스)과 SYSTEMD_WANTS 대안을 설명할 수 있다
- [ ] `.link` 파일로 NIC 이름을 고정하고 `net.ifnames=0`의 의미를 안다
- [ ] udev, mdev, 정적 `/dev`를 장비 조건에 따라 고를 수 있다
