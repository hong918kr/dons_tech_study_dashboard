# L1. systemd — unit/service/target, 의존성, watchdog 연동, journald, systemd-analyze

> **이 노트를 다 읽으면**: unit 파일을 직접 써서 서비스를 "죽으면 살리고, 멈추면 죽여서 살리고, 계속 죽으면 포기하고 알리게" 만들 수 있다 · `Requires=`와 `After=`의 차이를 실험 로그로 설명할 수 있다 · PID 1이 HW watchdog을 먹이는 구조와 PID 1이 멈췄을 때 보드가 리셋되는 과정을 안다 · journald를 flash 수명에 맞게 설정하고 `systemd-analyze`로 부팅 시간을 깎을 수 있다
> **왜 필요한가**: Ubuntu/Debian 기반 장비(Jetson L4T 등)와 대부분의 Yocto 이미지가 systemd를 쓴다. "필드에서 서비스가 죽으면 어떻게 자가 복구하나", "Requires와 After 차이", "systemd watchdog과 HW watchdog의 관계"는 Embedded Linux 면접 단골이다.
> **Don 기준 난이도**: watchdog·재시작 정책·로그 링버퍼는 펌웨어에서 이미 설계해 본 개념 / unit 문법, 의존성 vs 순서, sd_notify 프로토콜, journald 저장 정책은 새로 배울 부분
> **선행 노트**: C7(PID 1, BusyBox init vs systemd 첫 소개, `systemd-analyze` 기본), K1(PID 1 규칙, rootfs), K2(BusyBox init/inittab), K6(Ubuntu Base + systemd 부팅, machine-id), I9(watchdog 프레임워크, i6300esb)

## 0. 큰 그림 — 장비의 "태스크 매니저 + 이벤트 로그 + 워치독 관리자"

펌웨어에서 Don이 만들던 것을 떠올려 보자. SSD 펌웨어의 메인에는 보통 이런 것들이 있다.

- 태스크 테이블: 어떤 태스크를 어떤 순서로 만들지 (NAND 초기화가 끝나야 FTL 태스크 시작).
- 태스크 감시: 태스크가 죽거나(assert) 멈추면(heartbeat 없음) 그 태스크만 재시작하거나, 안 되면 전체 리셋.
- 이벤트 로그: 링버퍼에 남기고, 중요한 것만 NAND의 로그 영역에 flush (쓰기 수명 때문에).
- HW watchdog kick: 메인 루프가 살아 있을 때만 kick.

Linux 장비에서 이 네 가지를 한 번에 해 주는 것이 **systemd**다. 정확히는 PID 1로 도는 **systemd manager**와, 그 옆에서 도는 작은 데몬 묶음(journald, udevd, networkd, logind …)이다.

### 0.1 왜 장비에 systemd를 쓰나 — BusyBox init / sysvinit과 비교

C7과 K2에서 BusyBox init(`/etc/inittab`을 위에서부터 실행)을 봤다. 같은 장비를 두 방식으로 만든다고 해 보자.

| 항목 | BusyBox init + 셸 스크립트 | systemd |
|---|---|---|
| 시작 순서 | inittab·`rcS` 안의 줄 순서 (직렬) | unit 사이 의존성 그래프 (병렬) |
| "준비 완료" 판단 | 스크립트가 `sleep`·폴링으로 추측 | `Type=notify`로 서비스가 직접 `READY=1` |
| 죽은 서비스 재시작 | `respawn` (무조건, 횟수 제한 없음) | `Restart=` + `StartLimitBurst=` + `OnFailure=` |
| 멈춘 서비스 감지 | 없음 (직접 만들어야 함) | `WatchdogSec=` → SIGABRT → 재시작 |
| 자식 프로세스 정리 | PID만 추적 → 데몬이 fork한 손자는 놓침 | cgroup 단위로 추적·kill |
| 로그 | syslogd + 파일 + logrotate | journald (구조화, 크기 상한, rate limit) |
| HW watchdog | 별도 `watchdog` 데몬 | PID 1이 직접 (`RuntimeWatchdogSec=`) |
| 크기 | BusyBox 하나 (수백 KB) | 수십 MB (§10.4에서 실측) |
| 부팅 시간 | 단순하면 매우 빠름 | 병렬화로 빠를 수도, unit 수가 많으면 느림 |

결론은 이렇다. **수 MB 플래시, 서비스 2~3개, 부팅 1초 미만**이 요구사항이면 BusyBox init(또는 직접 쓴 `/init`)이 맞다. **서비스가 10개 이상, 서로 의존하고, 필드에서 스스로 복구해야 하고, 로그를 원격으로 올려야 하는** 장비(로봇·드론 컴패니언 컴퓨터, 카메라, Jetson)라면 systemd가 이미 만들어 둔 것을 쓰는 편이 싸다. 셸 스크립트로 재시작 제한·watchdog·cgroup 정리를 다시 만들면 결국 버그 많은 작은 systemd가 된다.

sysvinit(`/etc/init.d/` 스크립트 + 런레벨)은 BusyBox init보다 조금 더 구조가 있지만 "직렬 스크립트 실행 + PID 파일로 추적"이라는 본질은 같다. 신규 제품에서 고를 이유는 거의 없다.

### 0.2 이 노트의 실습 환경

- VM 호스트: Lima `elinux` (Ubuntu 26.04, 커널 `7.0.0-38-generic`, systemd 259) — C 프로그램 static 빌드만 한다. 호스트의 systemd 상태는 바꾸지 않는다.
- 게스트: QEMU `virt` (TCG, Cortex-A57 2코어, 1 GiB) + 랩 커널 `Image-sec`(6.18.55-sec) + 랩 rootfs `rootfs-sysd.ext4`(Ubuntu Base 24.04.5 + **systemd 255**). 내 복사본 `/var/tmp/L1/l1_root.ext4`에 unit 파일과 테스트 스크립트를 넣고 부팅한다.
- 자동화 방식: 이미지에 `l1-runner.service`를 넣었다. 커널 인자 `l1step=N`을 읽어 `/usr/local/bin/l1_step_N.sh`를 실행하고 결과를 `/root/l1out/N.txt`에 쓴 뒤 poweroff한다. 끝나면 VM에서 이미지를 loop 마운트해서 결과를 읽는다. 아래 출력은 전부 이 결과 파일에서 그대로 옮겼다.
- **TCG는 실제 하드웨어가 아니다.** CPU 명령을 소프트웨어로 번역하므로 모든 시간이 실제 Cortex-A78AE(Orin)나 i.MX8보다 수 배~수십 배 느리다. 시간 숫자는 "같은 환경에서 전후 비교"로만 읽는다.

러너 unit과 러너 스크립트는 이렇다 (이 자체가 systemd 사용 예제다).

```text
# /etc/systemd/system/l1-runner.service
[Unit]
Description=L1 lab runner (reads l1step= from kernel cmdline)
After=multi-user.target

[Service]
Type=simple
ExecStart=/usr/local/bin/l1_run.sh
StandardOutput=journal+console

[Install]
WantedBy=multi-user.target
```

```sh
#!/bin/sh
# /usr/local/bin/l1_run.sh: l1step=N on kernel cmdline -> l1_step_N.sh > /root/l1out/N.txt
step=$(tr ' ' '\n' < /proc/cmdline | sed -n 's/^l1step=//p')
[ -n "$step" ] || exit 0
mkdir -p /root/l1out
systemctl is-system-running --wait > /root/l1out/state_$step.txt 2>&1
echo "L1RUN step=$step state=$(cat /root/l1out/state_$step.txt)"
/usr/local/bin/l1_step_$step.sh > /root/l1out/$step.txt 2>&1
sync
echo "L1RUN step=$step done"
[ -e /root/l1out/nopoweroff ] || systemctl poweroff
```

두 가지 작은 설계 포인트가 있다. 첫째, `Type=simple`이다. `Type=oneshot`으로 하면 스크립트가 끝날 때까지 이 unit의 start job이 끝나지 않고, systemd는 **job이 하나라도 남아 있으면 "Startup finished"를 찍지 않는다** — 부팅 시간 측정이 러너 때문에 망가진다. 둘째, 스크립트가 `systemctl is-system-running --wait`로 부팅 완료를 기다린 뒤에야 측정한다. "부팅 끝"을 sleep으로 추측하지 않는 것, 이것이 systemd 방식의 핵심이다.

## 1. unit, job, transaction — PID 1 안의 엔진

### 1.1 직관 — "상태를 가진 객체 + 그래프 + 작업 큐"

systemd가 관리하는 모든 것은 **unit**이다. unit은 이름(`imu.service`), 설정(unit 파일), 그리고 현재 상태(`active`, `failed` …)를 가진 객체다. 서비스만 unit이 아니다 — 마운트 지점, 장치, 소켓, 타이머, 그리고 "여기까지 왔다"는 동기화 지점(target)도 unit이다.

누군가(부팅 시의 PID 1 자신, 또는 `systemctl start`) "이 unit을 start해 줘"라고 요청하면 systemd는 바로 실행하지 않는다. 먼저 **transaction**(트랜잭션)을 만든다.

1. 요청한 unit에 **job**(start/stop/restart 같은 작업 하나)을 만든다.
2. 그 unit의 `Wants=`/`Requires=`를 따라가며 끌려오는 unit들에도 start job을 붙인다. `Conflicts=`가 있으면 상대에 stop job을 붙인다.
3. 모인 job들을 `After=`/`Before=`로 정렬한다. 순서 고리(cycle)가 있으면 `Wants=`로만 끌려온 job 하나를 버려서 고리를 끊고 경고를 찍는다.
4. 모순이 없으면 transaction 전체를 **job queue**에 넣는다. 이후 이벤트 루프가 "앞 순서 job이 끝난 것"부터 실행한다.

Don이 아는 말로 하면: unit = 태스크 제어 블록(TCB), job = 태스크에 보내는 명령 메시지, transaction = "이 명령을 실행하려면 같이 필요한 명령 전부"를 미리 계산해서 한 번에 큐에 넣는 것, 이벤트 루프 = epoll 기반 단일 스레드 스케줄러다. PID 1은 멀티스레드가 아니다 — 모든 것이 `sd-event`(epoll 래퍼) 하나의 루프에서 돈다. 그래서 PID 1 안의 블로킹 호출 하나가 시스템 전체를 멈출 수 있고, 그래서 HW watchdog을 PID 1이 먹이는 것이 의미가 있다(§7).

### 1.2 unit 타입

| 타입 | 무엇을 나타내나 | 센서 키트 예 |
|---|---|---|
| `.service` | 프로세스 (데몬, 1회성 명령) | `imu.service`, `camera.service` |
| `.socket` | 리스닝 소켓·FIFO. 연결이 오면 짝 서비스를 띄움 | `telemetry.socket` (TCP 7777) |
| `.target` | 동기화 지점·그룹 (실행 내용 없음) | `multi-user.target`, `sensors.target` |
| `.mount` / `.automount` | 마운트 지점 (`/etc/fstab`에서도 생성) | `data.mount` (`/data` 파티션) |
| `.device` | udev가 `TAG+="systemd"`로 알린 장치 | `dev-video0.device` |
| `.timer` | 시간 기반 활성화 (cron 대체) | `logupload.timer` |
| `.path` | 파일·디렉터리 변화 감시(inotify)로 활성화 | `/data/new` 에 파일 생기면 업로드 |

| `.swap` | 스왑 장치·파일 | (장비에서는 보통 zram) |

### 1.3 unit의 상태

unit의 상태는 두 층이다. **LoadState**(파일을 읽었나: `loaded`, `not-found`, `masked`, `error`)와 **ActiveState**(지금 돌고 있나: `inactive`, `activating`, `active`, `deactivating`, `failed`, `reloading`, 그리고 드물게 `maintenance`·`refreshing`). 서비스에는 더 세밀한 **SubState**(`running`, `exited`, `auto-restart`, `start-pre` …)가 있다. `systemctl status`의 `Active: active (running)`이 ActiveState(SubState)다.

## 2. unit 파일 — 어디에 두고, 어떻게 덮어쓰나

### 2.1 위치와 우선순위

같은 이름의 unit 파일이 여러 곳에 있으면 **앞에 있는 것 하나만** 쓴다. 실제 검색 경로는 `systemd-analyze unit-paths`가 보여 준다.

```sh
systemd-analyze unit-paths
```

```text
/etc/systemd/system.control
/run/systemd/system.control
/run/systemd/transient
/run/systemd/generator.early
/etc/systemd/system
/etc/systemd/system.attached
/run/systemd/system
/run/systemd/system.attached
/run/systemd/generator
/usr/local/lib/systemd/system
/usr/lib/systemd/system
/run/systemd/generator.late
```

정리하면 우선순위가 높은 순서로:

| 경로 | 누가 쓰나 | 장비에서의 의미 |
|---|---|---|
| `/etc/systemd/system.control`, `/run/systemd/system.control` | `systemctl set-property` | 런타임 자원 조정 |
| `/run/systemd/transient` | `systemd-run`이 만든 임시 unit | 재부팅하면 사라짐 |
| `/etc/systemd/system` | **관리자·제품 이미지** | 제품 고유 unit, 덮어쓰기, enable 링크 |
| `/run/systemd/system` | 런타임 생성 | 재부팅하면 사라짐 |
| `/run/systemd/generator` (+ `.early`, `.late`) | **generator** (§2.5) | fstab·getty·커맨드라인에서 자동 생성 |
| `/usr/local/lib/systemd/system` | 로컬 설치 | 거의 안 씀 |
| `/usr/lib/systemd/system` | **배포판 패키지** | 건드리지 않는다 (업데이트가 덮어씀) |

규칙은 단순하다: **패키지가 준 파일(`/usr/lib`)은 고치지 않고, `/etc`에서 덮어쓴다.** 그래야 OTA로 패키지를 올려도 내 변경이 살아남는다. read-only rootfs + 쓰기 가능한 `/etc` 오버레이(L4, K6)라면 이 구분이 그대로 "이미지에 굽는 것 vs 장비별 설정"이 된다.

### 2.2 drop-in — 통째로 복사하지 말고 몇 줄만 덮기

`/etc/systemd/system/<unit>.d/*.conf` 파일은 원래 unit 위에 **덧붙여진다**(drop-in). 파일 전체를 `/etc`에 복사하면 패키지 업데이트로 원본이 바뀌어도 반영되지 않는 문제가 생기는데, drop-in은 바꾼 줄만 들고 있으니 그 문제가 없다. 리스트형 설정(`ExecStart=`, `After=` 등)은 drop-in에서 **추가**된다 — 지우려면 먼저 빈 값(`ExecStart=`)을 한 줄 쓰고 새 값을 쓴다.

`systemctl edit <unit>`은 `/etc/systemd/system/<unit>.d/override.conf`를 편집기로 열고, 저장하면 `daemon-reload`까지 해 준다. 대화형 명령이라 자동화 스크립트 안에서는 tty가 없어 거부된다 — 그래서 이미지 빌드·테스트 스크립트에서는 **같은 파일을 직접 만들고 `daemon-reload`** 한다. 아래는 §6의 데모 서비스에 "3번 ping한 뒤 멈춰라"를 drop-in으로 넣는 장면이다 (게스트, 러너 스크립트 안).

```sh
systemctl edit l1-notifyd < /dev/null          # 스크립트 안에서는 거부된다
mkdir -p /etc/systemd/system/l1-notifyd.service.d
printf '[Service]\nEnvironment=HANG=3\n' > /etc/systemd/system/l1-notifyd.service.d/override.conf
systemctl daemon-reload
systemctl cat l1-notifyd --no-pager
systemd-delta --type=extended --no-pager | grep l1
```

```text
StatusText=ping 9

Cannot edit units if not on a tty.

# /etc/systemd/system/l1-notifyd.service
[Unit]
Description=L1 sensor daemon (sd_notify + watchdog demo)
StartLimitIntervalSec=120
StartLimitBurst=3
OnFailure=l1-onfailure@%n.service

[Service]
Type=notify
Environment=HANG=0
ExecStart=/usr/local/bin/l1_notifyd $HANG
WatchdogSec=2s
Restart=on-failure
RestartSec=1s

# /etc/systemd/system/l1-notifyd.service.d/override.conf
[Service]
Environment=HANG=3
```

출력에서 볼 것: `systemctl cat`은 **원본 + drop-in을 파일 경로 주석과 함께 순서대로** 보여 준다. "이 서비스는 실제로 어떤 설정으로 도나"를 확인하는 첫 명령이다. `systemd-delta`는 시스템 전체에서 덮어쓰기·확장·마스킹된 unit을 나열한다 — 남의 장비를 디버깅할 때 "누가 무엇을 바꿨나"를 한 번에 본다.

### 2.3 enable, preset, mask

- **enable**: `[Install]`의 `WantedBy=multi-user.target`을 읽어 `/etc/systemd/system/multi-user.target.wants/<unit>` 심볼릭 링크를 만든다. 그게 전부다. 부팅 때 `multi-user.target`이 `.wants/` 디렉터리 안의 링크를 `Wants=`처럼 취급해 끌고 온다. 이미지 빌드에서는 `systemctl --root=<rootfs> enable foo` 또는 링크를 직접 만든다(Yocto의 `SYSTEMD_AUTO_ENABLE`, Buildroot의 패키지 `.mk`가 하는 일).
- **preset**: `/usr/lib/systemd/system-preset/*.preset`의 `enable foo.service` / `disable *` 규칙. `systemctl preset-all`이 이 정책대로 enable 상태를 일괄 맞춘다. "첫 부팅"(`ConditionFirstBoot=yes`가 참인 부팅)에 systemd가 자동으로 preset을 적용한다 — 이미지 정책을 "어떤 패키지를 깔았나"가 아니라 preset 파일 하나로 관리할 수 있다. 주의: machine-id(5)에 따르면 첫 부팅으로 치는 것은 `/etc/machine-id`가 **없거나 `uninitialized`라는 글자를 담고 있을 때**다. 이 노트의 이미지처럼 **빈 파일**이면 ID는 새로 만들지만 첫 부팅으로 치지 않는다 — §10.1의 첫 부팅 로그에서 `systemd-firstboot.service ... skipped because of an unmet condition check (ConditionFirstBoot=yes)`로 실제로 확인된다. 공장 이미지에서 첫 부팅 동작(preset, 키 생성)을 원하면 `uninitialized`를 써 둔다(K6의 machine-id 이야기와 연결).
- **mask**: `/etc/systemd/system/<unit>` → `/dev/null` 링크. 수동 start도, 다른 unit의 `Requires=`도 막는다. disable은 "부팅 때 자동으로 안 띄움"일 뿐 다른 unit이 끌어오면 뜬다. **확실히 죽이려면 mask**다. §10에서 부팅 시간 줄이기에 쓴다.

### 2.4 unit 파일 문법 한 장

unit 파일은 INI 형식이다. 이 노트의 데모 서비스 하나에 자주 쓰는 섹션이 다 들어 있다.

```text
# /etc/systemd/system/l1-notifyd.service
[Unit]
Description=L1 sensor daemon (sd_notify + watchdog demo)
StartLimitIntervalSec=120
StartLimitBurst=3
OnFailure=l1-onfailure@%n.service

[Service]
Type=notify
Environment=HANG=0
ExecStart=/usr/local/bin/l1_notifyd $HANG
WatchdogSec=2s
Restart=on-failure
RestartSec=1s
```

- `[Unit]`: 모든 unit 공통 — 설명, 의존성(§3), 시작 제한, 실패 훅. `StartLimit*`가 `[Service]`가 아니라 `[Unit]`에 있는 것에 주의한다(옛 문서의 `StartLimitInterval=`은 `[Service]`였다 — 지금은 `[Unit]`의 `StartLimitIntervalSec=`).
- `[Service]`: 서비스 전용 — 실행 방법, 재시작, watchdog.
- `[Install]`: enable 때만 쓰인다. 이 데모는 수동으로 start하므로 없다.
- `%n`은 **specifier**다: unit 전체 이름(`l1-notifyd.service`)으로 치환된다. `%i`는 템플릿 인스턴스 이름(`foo@bar.service`의 `bar`). `l1-onfailure@.service`는 템플릿이고, `OnFailure=l1-onfailure@%n.service`는 "실패한 unit 이름을 인스턴스로 넘겨라"라는 뜻이다.
- `$HANG`은 `Environment=`의 값으로 치환된다. `ExecStart=`는 **셸이 아니다** — 파이프·리다이렉션·`$(...)`가 안 된다. 필요하면 `/bin/sh -c '...'`로 감싸거나 스크립트 파일로 뺀다(이 노트는 스크립트로 뺐다).

### 2.5 generator — 부팅 때 unit을 "생성"하는 작은 프로그램

PID 1은 unit 파일을 읽기 전에 `/usr/lib/systemd/system-generators/`의 실행 파일들을 돌린다. generator는 `/etc/fstab`, 커널 커맨드라인, GPT 파티션 타입 같은 것을 읽어 `/run/systemd/generator*/`에 unit 파일을 만든다. 그래서 `/etc/fstab` 한 줄이 `.mount` unit이 되고, `console=ttyAMA0`이 `serial-getty@ttyAMA0.service`가 된다.

## 3. 의존성(끌어오기)과 순서(기다리기)는 다른 축이다

### 3.1 직관

systemd에서 가장 많이 틀리는 지점이다. 두 질문을 분리해야 한다.

- **"B를 켤 때 A도 켜야 하나?"** → 의존성 (`Wants=`, `Requires=`, `BindsTo=`, `Requisite=`, `PartOf=`). A의 job을 transaction에 **넣을지**를 정한다.
- **"A가 다 켜질 때까지 B는 기다려야 하나?"** → 순서 (`After=`, `Before=`). 둘 다 transaction에 있을 때 **어느 job을 먼저 끝낼지**를 정한다.

둘은 서로 독립이다. `Requires=A`만 쓰고 `After=A`를 안 쓰면, systemd는 A와 B를 **동시에** 시작한다. RTOS로 말하면 "태스크 A도 만들어라"와 "A의 이벤트 플래그를 기다려라"는 다른 API인 것과 같다.

### 3.2 지시어 정리

| 지시어 | 끌어오나 | 상대가 실패/정지하면 나는 | 상대가 이미 없으면 | 대표 용도 |
|---|---|---|---|---|
| `Wants=A` | 예 | 상관없음 | A를 시작해 봄 | 대부분의 경우 (권장 기본값) |
| `Requires=A` | 예 | A가 **명시적으로 stop**되면 나도 stop. A의 start job이 실패하면 나도 실패 (**After=도 있을 때**) | A를 시작해 봄 | 강한 의존 |
| `Requisite=A` | 아니오 | Requires와 같음 | **즉시 실패** (A를 시작하지 않음) | "이미 떠 있어야만" |
| `BindsTo=A` | 예 | A가 **어떤 이유로든** inactive가 되면 나도 stop (A 프로세스가 혼자 죽어도) | A를 시작해 봄 | 장치에 묶인 서비스 (`BindsTo=dev-video0.device`) |
| `PartOf=A` | 아니오 | A가 **systemctl로 stop/restart**될 때만 같이 stop/restart | 영향 없음 | 그룹 재시작 (`PartOf=sensors.target`) |
| `Conflicts=A` | A를 stop | — | — | 둘 중 하나만 (`rescue` vs `multi-user`) |
| `After=A` | 아니오 | — | — | A의 start가 끝난 뒤에 내 start |
| `Before=A` | 아니오 | — | — | 내 start가 끝난 뒤에 A의 start |
| `OnFailure=X` | 실패 시 X를 start | — | — | 알림·복구 훅 (§5.4) |

`After=`의 "끝난 뒤"는 **상대 unit의 start job이 완료된 뒤**다. 서비스라면 `Type=`이 정한 "시작 완료" 시점(§5.1)이다 — `Type=simple`이면 fork 직후, `Type=notify`면 `READY=1` 후, `Type=oneshot`이면 프로세스 종료 후. 그래서 `After=`는 `Type=`과 같이 봐야 의미가 있다. stop 때는 순서가 거꾸로 적용된다(B가 먼저 멈추고 A가 멈춘다).

### 3.3 실험 — `Requires=`만 쓰면 생기는 경주(race)

무엇을 확인하나: B가 `Requires=A`일 때 `After=A`가 있고 없음에 따라 (1) B가 A보다 먼저 시작하는지, (2) A가 실패하면 B가 실행되는지. A는 3초 걸리는 oneshot이고, 성공하면 `/run/l1_a_done`을 만든다. B는 그 파일이 있는지 `ls`로 확인한다 — "A가 만든 장치 노드·설정 파일을 B가 쓰는" 실제 상황의 축소판이다.

```text
# /etc/systemd/system/l1-a.service
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/bin/l1_a.sh        # rm done; echo start; sleep 3; touch done; exit $(cat /run/l1_a_rc)

# /etc/systemd/system/l1-b-noafter.service           # /etc/systemd/system/l1-b-after.service
[Unit]                                               [Unit]
Requires=l1-a.service                                Requires=l1-a.service
                                                     After=l1-a.service
[Service]                                            [Service]
Type=oneshot                                         Type=oneshot
ExecStart=/bin/echo B-noafter: started ...           ExecStart=/bin/echo B-after: started
ExecStart=/bin/ls /run/l1_a_done                     ExecStart=/bin/ls /run/l1_a_done
```

실험 스크립트(게스트, `l1_step_3.sh`의 앞부분):

```sh
for b in l1-b-noafter l1-b-after; do
  for rc in 0 1; do
    echo $rc > /run/l1_a_rc; systemctl stop l1-a; systemctl reset-failed l1-a $b 2>/dev/null
```

`systemctl show -p Requires -p After`의 결과에서 내가 쓰지 않은 `sysinit.target`, `basic.target`, `system.slice`, `systemd-journald.socket`이 보인다 — §3.5의 기본 의존성이 자동으로 들어간 것이다.

### 3.4 BindsTo / PartOf / Requisite — 정지가 어떻게 번지나

무엇을 확인하나: 부모 서비스(`l1-parent`, 카메라 파이프라인이라고 하자)를 (1) `systemctl stop`, (2) `systemctl restart`, (3) 프로세스가 **혼자 죽게**(`kill -9`) 했을 때, `PartOf=`와 `BindsTo=` 자식이 어떻게 반응하나. 세 서비스 모두 `ExecStart=/bin/sleep infinity`이고 자식은 `After=l1-parent.service`를 같이 가진다.

```text
### systemctl start l1-parent l1-partof l1-bindsto; systemctl is-active l1-parent l1-partof l1-bindsto | paste -sd" "
active active active

### systemctl stop l1-parent; sleep 1; systemctl is-active l1-parent l1-partof l1-bindsto | paste -sd" "
inactive inactive inactive

### systemctl start l1-parent l1-partof l1-bindsto; p1=$(systemctl show -p MainPID --value l1-partof); systemctl restart l1-parent; sleep 1; p2=$(systemctl show -p MainPID --value l1-partof); echo "partof MainPID $p1 -> $p2"; systemctl is-active l1-parent l1-partof l1-bindsto | paste -sd" "
partof MainPID 569 -> 579
active active active

### systemctl start l1-bindsto; kill -9 $(systemctl show -p MainPID --value l1-parent); sleep 1; systemctl is-active l1-parent l1-partof l1-bindsto | paste -sd" "
failed active inactive

### systemctl stop l1-partof l1-bindsto; systemctl reset-failed; systemctl start l1-requisite; echo rc=$?; systemctl start l1-parent; systemctl start l1-requisite; echo rc=$?; systemctl is-active l1-requisite
A dependency job for l1-requisite.service failed. See 'journalctl -xe' for details.
rc=1
rc=0
active
```

정리하면:

| 상황 | `PartOf=` 자식 | `BindsTo=` 자식 |
|---|---|---|
| `systemctl stop l1-parent` | 같이 정지 | 같이 정지 |
| `systemctl restart l1-parent` | 같이 재시작 (MainPID 569 → 579) | active 유지 (출력상 active) |
| 부모 프로세스가 혼자 죽음 (`kill -9`) | **영향 없음** (active) | **정지** (inactive) |

- `PartOf=`는 **systemctl 명령(job)만** 전파한다. 부모가 스스로 죽는 것은 job이 아니라서 전파되지 않는다. 그래서 "sensors.target을 restart하면 묶음 전체가 재시작"에 맞다.
- `BindsTo=`는 부모의 **상태**를 본다. 부모가 어떤 이유로든 inactive/failed가 되면 자식을 멈춘다. 장치에 묶는 데 맞다 — USB 카메라가 뽑혀 `dev-video0.device`가 사라지면 카메라 서비스도 멈춘다.
- restart 때 BindsTo 자식이 active로 보이는 것은 부모 restart가 stop→start를 한 job으로 처리하는 동안 BindsTo 자식이 정지 대상이 되지 않았기 때문으로 보인다(이 실험에서 BindsTo 자식의 PID 변화는 기록하지 않았다).
- `Requisite=`는 끌어오지 않는다. 부모가 inactive일 때는 "A dependency job ... failed"로 즉시 실패, 부모를 먼저 띄우면 성공한다. "이미 떠 있어야만 의미가 있는" 진단 도구 등에 쓴다.

### 3.5 기본 의존성과 Condition

모든 service unit에는 `DefaultDependencies=yes`가 기본으로 붙어 다음이 **자동으로** 들어간다: `Requires=sysinit.target`, `After=sysinit.target basic.target`, `Conflicts=shutdown.target`, `Before=shutdown.target`. 그래서 평범한 서비스는 `/proc`·`/sys`·로컬 파일시스템·udev 준비가 끝난 뒤에 뜨고, 종료 때는 먼저 멈춘다. **부팅 아주 초기에 돌아야 하는 서비스**(예: 루트 마운트 전에 eMMC 파티션을 고치는 도구)는 `DefaultDependencies=no`를 쓰고 필요한 순서를 직접 적는다. 이걸 모르고 `Before=sysinit.target`만 쓰면 순서 고리(ordering cycle)가 생겨 systemd가 job 하나를 버린다.

`Condition*=` / `Assert*=`는 의존성이 아니라 **"시작할 조건"**이다. 조건이 거짓이면 unit은 실패가 아니라 "건너뜀(skipped)"이 된다 (K6 부팅 로그의 `ConditionPathExists=/proc/sys/fs/binfmt_misc` 줄이 그 예). 장비에서 유용한 것들:

| 지시어 | 예 | 용도 |
|---|---|---|
| `ConditionPathExists=` | `/dev/ttyUSB0`, `!/etc/l1/disabled` | 옵션 하드웨어, 기능 끄기 플래그 |
| `ConditionFirstBoot=yes` | — | 공장 출하 후 첫 부팅에만 (키 생성, 파티션 확장) |
| `ConditionKernelCommandLine=` | `factory_test` | 공장 테스트 모드 |
| `ConditionVirtualization=no` | — | QEMU에서는 HW 서비스를 끔 |
| `AssertPathExists=` | `/data/calib.json` | 없으면 **실패**로 남김 (조건과 달리) |

## 4. target — 부팅의 이정표와 "모드"

### 4.1 target은 runlevel의 후계자다

target은 실행 내용이 없는 unit이다. 다른 unit들을 `Wants=`로 묶고, 다른 unit들이 `After=`로 기다리는 **동기화 지점** 역할만 한다. 부팅은 "`default.target`을 start하는 transaction 하나"다. `default.target`은 보통 `multi-user.target`(헤드리스) 또는 `graphical.target`(화면 있음)을 가리키는 심볼릭 링크다.

| target | 의미 | sysvinit 대응 |
|---|---|---|
| `sysinit.target` | 로컬 파일시스템, udev, tmpfiles, journald 준비 | rcS |
| `basic.target` | 소켓·타이머·경로 unit 준비, 일반 서비스가 뜰 수 있는 시점 | — |
| `multi-user.target` | 헤드리스 장비의 "부팅 완료" | runlevel 3 |
| `graphical.target` | multi-user + 디스플레이 매니저 | runlevel 5 |
| `rescue.target` | 로컬 FS 마운트 + root 셸, 서비스는 거의 없음 | runlevel 1 |
| `emergency.target` | 루트를 읽기 전용으로만 마운트하고 셸 (fstab이 깨졌을 때) | `init=/bin/sh`에 가까움 |
| `network-online.target` | "네트워크가 실제로 쓸 수 있음" (`*-wait-online.service`가 판정) | — |
| `shutdown.target`, `reboot.target`, `poweroff.target` | 종료 경로 | runlevel 0/6 |

- 커널 커맨드라인에서 바꾸기: `systemd.unit=rescue.target`, 또는 줄여서 `rescue` / `emergency`(`1`, `s`, `single`도 rescue로 해석된다). U-Boot 환경변수 `bootargs`에 넣으면 필드 장비의 "복구 모드 부팅"이 된다(L4의 bootcount 실패 처리와 연결).
- 런타임에 바꾸기: `systemctl isolate rescue.target` — target에 속하지 않은 unit을 전부 멈춘다(`AllowIsolate=yes`인 target만 가능).
- 헤드리스 장비 이미지의 첫 정리 작업: `systemctl set-default multi-user.target` (K6에서 Ubuntu 기본이 `graphical.target`이었다).

### 4.2 `network-online.target` 함정

`After=network.target`은 "네트워크 관리자가 **시작됐다**"는 뜻이지 "IP를 받았다"가 아니다. 서버에 접속해야 하는 서비스는 `Wants=network-online.target` + `After=network-online.target`을 쓴다. 대신 이 target은 `systemd-networkd-wait-online.service`가 모든 링크가 설정될 때까지(기본 최대 2분) 기다리기 때문에, **케이블이 빠진 장비는 부팅이 2분 늦어진다.** §10에서 이 이미지의 critical chain에 실제로 나타나는지 본다. 해결은 (1) 정말 필요한 서비스만 network-online을 기다리게 하고, (2) `systemd-networkd-wait-online --any` 또는 `--interface=eth0`으로 범위를 좁히고, (3) 가능하면 서비스가 스스로 재접속하게 만드는 것이다.

## 5. 서비스의 일생 — Type=, Restart=, 시작 제한, OnFailure

### 5.1 `Type=` — "시작 완료"를 언제로 볼 것인가

`After=`가 기다리는 "시작 완료" 시점을 정하는 설정이다. 잘못 고르면 §3.3의 경주가 `After=`를 써도 다시 생긴다.

| Type | 시작 완료 시점 | 맞는 프로그램 | 주의 |
|---|---|---|---|
| `simple` (기본) | `fork()` 직후 (exec 전) | foreground로 도는 데몬 | exec 실패(바이너리 없음)도 "시작 성공" 후 바로 실패로 보인다 |
| `exec` | `execve()` 성공 직후 | simple과 같음, 더 정확 | 신규 unit은 simple보다 exec 권장 |
| `forking` | 부모 프로세스가 exit한 뒤 | 옛날식 이중 fork 데몬 | `PIDFile=` 필요할 수 있음. 신규 코드에선 쓰지 말 것 |
| `notify` | 서비스가 `READY=1`을 보낸 뒤 | **센서·통신 데몬** — 장치 열기·캘리브레이션이 끝나야 준비 | `NotifyAccess=` 기본 main(메인 PID만 보낼 수 있음) |
| `notify-reload` (v253+) | notify + `SIGHUP`으로 reload | 설정 다시 읽는 데몬 | `RELOADING=1` → `READY=1` 순서 |
| `oneshot` | 프로세스가 **종료**한 뒤 | 초기화 스크립트 (모듈 로드, GPIO 설정) | `RemainAfterExit=yes`가 없으면 끝나자마자 inactive |
| `dbus` | 지정한 D-Bus 이름을 얻은 뒤 | D-Bus 서비스 (L3) | `BusName=` 필요 |
| `idle` | simple과 같되 다른 job이 끝날 때까지 실행을 미룸 | 콘솔 출력 섞임 방지 | 순서 도구로 쓰지 말 것 |

`oneshot` + `RemainAfterExit=yes`가 중요한 조합이다. "GPIO 방향 설정", "CAN 비트레이트 설정" 같은 1회성 작업을 unit으로 만들면, 프로세스는 끝났지만 unit은 `active (exited)`로 남는다. 그래야 다른 unit이 `Requires=`/`After=`로 기대고, `systemctl stop`할 때 `ExecStop=`(되돌리기)이 돈다. §3.3의 `l1-a.service`가 이 조합이다.

### 5.2 `Restart=` — 언제 다시 살리나

| 값 | 깨끗한 종료(exit 0, SIGHUP/INT/TERM/PIPE) | exit ≠ 0 | 시그널로 죽음 | watchdog timeout | 시작 timeout |
|---|---|---|---|---|---|
| `no` (기본) | — | — | — | — | — |
| `on-success` | 재시작 | — | — | — | — |
| `on-failure` | — | 재시작 | 재시작 | 재시작 | 재시작 |
| `on-abnormal` | — | — | 재시작 | 재시작 | 재시작 |
| `on-watchdog` | — | — | — | 재시작 | — |
| `on-abort` | — | — | 잡히지 않은 시그널만 | — | — |
| `always` | 재시작 | 재시작 | 재시작 | 재시작 | 재시작 |

장비 데몬의 기본 선택은 **`Restart=on-failure`**다. `always`는 관리자가 일부러 끝낸(exit 0) 경우까지 살려서 디버깅을 방해한다. `systemctl stop`은 어떤 값이든 재시작을 일으키지 않는다. 특정 exit code는 "재시작해도 소용없다"(설정 파일 문법 오류 등)는 뜻으로 `RestartPreventExitStatus=78`처럼 막을 수 있다.

- `RestartSec=` (기본 100ms): 재시작 전 대기. 센서 버스가 회복할 시간을 준다.
- `RestartSteps=` / `RestartMaxDelaySec=` (v254+): 재시작할 때마다 대기를 늘려 가는 지수 백오프. 원격 서버 접속 데몬에 좋다.

### 5.3 시작 제한 — boot loop 대신 "포기하고 알리기"

무한 재시작은 펌웨어의 "assert → 리셋 → assert → 리셋" 루프와 같다. CPU·flash(로그)·배터리를 태우고, 원인 로그는 덮어써진다. systemd는 **unit별 시작 횟수 제한**을 둔다.

- `StartLimitIntervalSec=` (기본 `DefaultStartLimitIntervalSec=10s`) 안에 `StartLimitBurst=` (기본 5)번보다 많이 start하면, unit은 `failed`(Result `start-limit-hit`)에 머물고 더 이상 자동 재시작하지 않는다.
- 주의: 기본값 10초/5회는 `RestartSec=100ms`일 때를 위한 것이다. `RestartSec=1s`, burst 5면 5초에 5번이라 10초 창 안에서 거의 안 걸린다. **`RestartSec × Burst < IntervalSec`가 되게** 같이 설계해야 제한이 실제로 걸린다. 이 노트의 데모는 120초/3회로 했다.
- `StartLimitAction=` (기본 none): 제한에 걸렸을 때 `reboot`, `reboot-force`, `poweroff` 등을 할 수 있다. "이 서비스 없이는 장비가 의미 없다" + "재부팅하면 고쳐질 수 있다"일 때만 쓴다. 재부팅 루프 위험은 bootcount(L4)로 막는다.
- `FailureAction=` / `SuccessAction=`: unit이 실패/성공하면 시스템 동작(reboot 등). 공장 테스트 이미지에서 "테스트 서비스가 끝나면 poweroff"에 쓴다.

### 5.4 `OnFailure=` — 실패했을 때 할 일

`OnFailure=X`는 unit이 `failed` 결과로 끝날 때 X를 start한다. 여기서 주의할 점을 §6.3 실험에서 확인했다: **systemd 255에서는 `Restart=`로 자동 재시작될 실패에도 매번 `OnFailure=`가 불린다**(journal에 "Triggering OnFailure= dependencies"가 실패마다 찍히고, 훅이 본 `ActiveState`는 첫 번째엔 `activating`, 시작 제한에 걸린 마지막엔 `failed`였다). 그래서 훅 안에서 `systemctl show -p ActiveState`를 보고 "재시작 중인 일시 실패"와 "최종 포기"를 구분해야 한다 — 최종 포기일 때만 fault LED를 켜는 식이다. 템플릿과 `%n`을 쓰면 실패 훅 하나를 모든 서비스가 공유할 수 있다.

```text
# /etc/systemd/system/l1-onfailure@.service
[Unit]
Description=L1 OnFailure hook for %i

[Service]
Type=oneshot
ExecStart=/usr/local/bin/l1_onfailure.sh %i
```

```sh
#!/bin/sh
# /usr/local/bin/l1_onfailure.sh — in a product: save logs, bump a counter, set a fault LED
echo "ONFAILURE: unit $1 entered failed state"
systemctl show -p Result -p NRestarts -p ActiveState "$1"
```

제품에서는 이 자리에 "journal 마지막 200줄을 `/data/crash/`에 저장", "텔레메트리에 실패 이벤트 전송", "fault LED 켜기", "안전 상태로 전환(모터 정지)"이 들어간다. 모든 서비스에 일일이 쓰기 싫으면 `/etc/systemd/system/service.d/onfailure.conf` 같은 **최상위 타입 drop-in**(모든 `.service`에 적용)으로 넣을 수 있다 — 단 훅 서비스 자신에게도 적용되어 무한 호출이 되지 않게 훅 쪽에서 `OnFailure=`를 비운다.

## 6. sd_notify와 서비스 watchdog — 프로토콜을 C로 직접 구현

### 6.1 프로토콜은 "UNIX 데이터그램 한 개"다

`Type=notify` 서비스를 시작할 때 PID 1은 환경 변수 `NOTIFY_SOCKET`에 소켓 주소를 넣어 준다(systemd 255에서는 `/run/systemd/notify`). 서비스는 그 주소로 **`AF_UNIX` + `SOCK_DGRAM` 데이터그램**을 보낸다. 내용은 줄바꿈으로 구분한 `KEY=VALUE` 텍스트다. 그게 전부다. `libsystemd`의 `sd_notify()`는 이 일을 하는 편의 함수일 뿐이고, 의존성을 늘리기 싫은 작은 장비 데몬(또는 Rust·Go·Python 서비스)은 직접 보내도 된다.

| 메시지 | 뜻 |
|---|---|
| `READY=1` | 시작 완료 — `activating` → `active`, `After=`로 기다리던 unit 출발 |
| `STATUS=...` | 사람이 읽는 상태 문자열 (`systemctl status`의 `Status:` 줄) |
| `WATCHDOG=1` | 살아 있음 (watchdog 타이머 리셋) |
| `WATCHDOG=trigger` | 스스로 watchdog 동작을 즉시 일으킴 ("나는 고장났다") |
| `WATCHDOG_USEC=...` | 런타임에 watchdog 주기 변경 |
| `RELOADING=1` / `STOPPING=1` | reload 중 / 종료 중 |
| `EXTEND_TIMEOUT_USEC=...` | 시작·종료 timeout 연장 (긴 캘리브레이션) |
| `ERRNO=...` | 실패 원인 errno 보고 |
| `MAINPID=...` | 메인 PID 변경 알림 |
| `FDSTORE=1` (+ 소켓 fd를 `SCM_RIGHTS`로) | fd를 PID 1에 맡겨 두기 (재시작해도 연결 유지) |

`WatchdogSec=`를 설정하면 PID 1은 서비스 환경에 `WATCHDOG_USEC`(마이크로초)와 `WATCHDOG_PID`도 넣는다. 서비스는 **그 절반 주기로** `WATCHDOG=1`을 보내는 것이 관례다. 주기 안에 한 번도 안 오면 PID 1은 `Watchdog timeout`을 찍고 `WatchdogSignal=`(기본 **SIGABRT**)을 보낸다. SIGABRT라서 coredump가 남고(L7), `Restart=on-failure`면 다시 시작된다.

수신 측 보안: PID 1은 데이터그램과 함께 `SCM_CREDENTIALS`(보낸 프로세스의 PID·UID — 커널이 채워 줌, 위조 불가)를 받아서, `NotifyAccess=main`(기본)이면 서비스의 메인 PID가 보낸 메시지만 받아들인다. 메인 프로세스가 아닌 워커 스레드는 같은 PID라서 괜찮지만, fork한 자식이 보내려면 `NotifyAccess=all`이 필요하다.

### 6.2 코드 — libsystemd 없이 `NOTIFY_SOCKET`에 직접 보내기

무엇을 확인하는 코드인가: 환경 변수에서 소켓 주소와 watchdog 주기를 읽고, 준비가 끝나면 `READY=1`, 이후 주기의 절반마다 `WATCHDOG=1`을 보낸다. 인자 N을 주면 N번 ping한 뒤 "메인 루프가 멈춘 것처럼" ping을 끊는다.

```c
/* l1_notifyd: Type=notify service speaking the NOTIFY_SOCKET protocol directly.
 * usage: l1_notifyd [hang_after_pings]   (0 = never hang)                    */
#define _GNU_SOURCE
#include <stddef.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/socket.h>
#include <sys/un.h>

static int notify(const char *msg)
{
    const char *path = getenv("NOTIFY_SOCKET");
    if (!path) return 0;                         /* not under systemd: no-op */
    struct sockaddr_un sa = { .sun_family = AF_UNIX };
    size_t n = strlen(path);
    if (n >= sizeof(sa.sun_path)) return -1;
    memcpy(sa.sun_path, path, n);
    if (sa.sun_path[0] == '@') sa.sun_path[0] = '\0';   /* abstract socket */
    int fd = socket(AF_UNIX, SOCK_DGRAM | SOCK_CLOEXEC, 0);
    if (fd < 0) { perror("socket"); return -1; }
    ssize_t r = sendto(fd, msg, strlen(msg), MSG_NOSIGNAL, (struct sockaddr *)&sa,
                       offsetof(struct sockaddr_un, sun_path) + n);
    if (r < 0) perror("sendto");
    close(fd);
    return r < 0 ? -1 : 0;
}

int main(int argc, char **argv)
{
    long hang_after = argc > 1 ? atol(argv[1]) : 0;
    const char *w = getenv("WATCHDOG_USEC");
    long wd_usec = w ? atol(w) : 0;
    long period = wd_usec ? wd_usec / 2 : 1000000;     /* ping at half the timeout */
    printf("l1_notifyd: pid=%d NOTIFY_SOCKET=%s WATCHDOG_USEC=%ld\n",
           getpid(), getenv("NOTIFY_SOCKET"), wd_usec);
    fflush(stdout);
    usleep(500000);                                    /* pretend: open sensors */
    notify("READY=1\nSTATUS=sensors open, streaming");
    for (long i = 1;; i++) {
        usleep(period);
        if (hang_after && i > hang_after) {
            if (i == hang_after + 1) { printf("simulating hang (no more pings)\n"); fflush(stdout); }
            continue;                                  /* main loop "stuck" */
        }
        char buf[64];
        snprintf(buf, sizeof buf, "WATCHDOG=1\nSTATUS=ping %ld", i);
        notify(buf);
    }
}
```

포인트:

- 주소가 `@`로 시작하면 Linux **추상(abstract) 소켓**이다 — 파일시스템에 노드가 없고 `sun_path[0] = '\0'`로 표현한다. systemd는 파일 경로를 주지만 컨테이너 런타임 등은 추상 주소를 쓰기도 해서 두 경우를 다 처리한다. 주소 길이는 `offsetof(sun_path) + n`으로 정확히 준다(추상 소켓은 뒤쪽 NUL까지 이름에 포함되기 때문).
- `NOTIFY_SOCKET`이 없으면 아무것도 안 한다. 같은 바이너리를 systemd 없이(BusyBox init, 개발 PC 터미널) 돌려도 동작한다.
- `MSG_NOSIGNAL`: 받는 쪽이 없을 때 SIGPIPE로 죽지 않게.
- 매번 소켓을 열고 닫는다(libsystemd의 `sd_notify`도 그렇게 한다). 1초 주기면 비용은 무시할 만하다.
- **ping은 "진짜 일이 진행됐을 때"만 보내야 한다.** 별도 스레드에서 무조건 ping하면 메인 루프가 데드락에 걸려도 watchdog이 못 잡는다. 펌웨어에서 "타이머 ISR에서 WDT를 kick하면 안 된다"는 규칙과 똑같다.

## 7. RuntimeWatchdogSec — PID 1이 HW watchdog을 먹인다

### 7.1 누가 PID 1을 감시하나

§6의 서비스 watchdog은 PID 1이 서비스를 감시한다. 그럼 PID 1이 멈추면? 커널 데드락, 메모리 고갈로 PID 1이 스케줄되지 못함, PID 1 자체의 버그. 이때는 아무도 서비스를 재시작해 주지 못한다. 그래서 **PID 1 자신은 하드웨어 watchdog이 감시하게** 한다. I9에서 본 `/dev/watchdog` API를 PID 1이 직접 쓰는 것이다.

`/etc/systemd/system.conf`(또는 `system.conf.d/*.conf`)의 `[Manager]` 설정:

| 설정 | 기본 (systemd 255) | 의미 |
|---|---|---|
| `RuntimeWatchdogSec=` | `off` | 평상시 HW watchdog timeout. 설정하면 PID 1이 `/dev/watchdog0`을 열고 `WDIOC_SETTIMEOUT`, 이후 대략 절반 주기로 ping |
| `RuntimeWatchdogPreSec=` | `off` | pretimeout (I9 §5.7) — 리셋 전에 경고 인터럽트 (드라이버가 지원할 때) |
| `RebootWatchdogSec=` | `10min` | reboot/poweroff 경로에서 PID 1이 HW watchdog을 이 값으로 바꿔 두고 넘김 — 종료가 멈추면 이 시간 뒤 강제 리셋 |
| `KExecWatchdogSec=` | `off` | kexec(L7의 kdump) 때 새 커널로 watchdog을 켠 채 넘김 — 새 커널이 시간 안에 급식을 이어받아야 함 |
| `WatchdogDevice=` | `/dev/watchdog0` | 장치 지정. 커널 커맨드라인 `systemd.watchdog_device=`로도 |

장비에서는 보통 `RuntimeWatchdogSec=` 를 10~30초 정도로 켠다. 너무 짧으면 부하가 큰 순간(대량 flash 쓰기, 메모리 압박)에 오탐 리셋이 나고, 너무 길면 멈춘 장비가 오래 멈춰 있는다. 별도 `watchdog` 데몬(watchdog 패키지)과 **같이 쓰면 안 된다** — `/dev/watchdog0`은 한 번에 한 프로세스만 열 수 있어서 늦게 연 쪽이 `EBUSY`를 받는다.

- `State: S (sleeping)`, `TracerPid: 0` — 정상 상태의 PID 1. 이벤트 루프의 `epoll_wait()`에서 자고 있다.

### 7.3 PID 1을 어떻게 멈추나 — `kill -STOP 1`은 안 된다

가장 먼저 떠오르는 방법은 `kill -STOP 1`이다. 하지만 커널은 PID 1에게 가는 SIGSTOP·SIGKILL을 **버린다**. `kernel/signal.c`(6.18.55):

```c
static bool sig_task_ignored(struct task_struct *t, int sig, bool force)
{
	void __user *handler;

	handler = sig_handler(t, sig);

	/* SIGKILL and SIGSTOP may not be sent to the global init */
	if (unlikely(is_global_init(t) && sig_kernel_only(sig)))
		return true;

	if (unlikely(t->signal->flags & SIGNAL_UNKILLABLE) &&
	    handler == SIG_DFL && !(force && sig_kernel_only(sig)))
		return true;
	...
```

`kill()`은 0을 반환하지만(권한 검사는 통과) 시그널은 큐에 들어가기 전에 무시된다. K1·C7에서 본 "PID 1에게는 기본 시그널 동작이 없다"의 커널 쪽 코드다.

멈추는 정당한 방법은 **ptrace**다. 디버거가 프로세스를 세우는 경로는 시그널 무시 규칙과 별개라, root(`CAP_SYS_PTRACE`)는 PID 1에 `PTRACE_SEIZE` + `PTRACE_INTERRUPT`를 걸어 tracing-stop 상태로 만들 수 있다. `gdb -p 1`이 PID 1을 세울 수 있는 것과 같은 원리다. 이 상태에서는 PID 1의 이벤트 루프가 돌지 않으니 HW watchdog ping도 끊긴다 — "PID 1이 데드락에 걸린 상황"의 충실한 재현이다. (다른 방법인 SysRq는 PID 1만 골라 세우는 기능이 없다. `echo c > /proc/sysrq-trigger`로 커널을 panic시키면 `panic=0`일 때 커널이 멈춰 있으니 역시 HW watchdog이 리셋하지만, 그건 "커널 hang" 시나리오다.)

무엇을 확인하는 코드인가: `kill(1, SIGSTOP)`이 성공을 반환해도 효과가 없음을 보이고, ptrace로 PID 1을 세운 뒤 `/proc/1/stat`의 상태를 1초마다 찍는다. 보드가 리셋되면 출력이 거기서 끊긴다.

```c
/* l1_freeze1: stop PID 1 with ptrace (signals to init are ignored, ptrace is not).
 * usage: l1_freeze1 <seconds>   -- holds PID 1 in ptrace-stop, then detaches     */
#include <errno.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <sys/ptrace.h>
#include <sys/wait.h>

int main(int argc, char **argv)
{
    int secs = argc > 1 ? atoi(argv[1]) : 60;
    if (kill(1, SIGSTOP) == 0) printf("kill(1, SIGSTOP) returned 0 (but init ignores it)\n");
    if (ptrace(PTRACE_SEIZE, 1, 0, 0) < 0) { perror("PTRACE_SEIZE"); return 1; }
    if (ptrace(PTRACE_INTERRUPT, 1, 0, 0) < 0) { perror("PTRACE_INTERRUPT"); return 1; }
    int st;
    if (waitpid(1, &st, __WALL) < 0) { perror("waitpid"); return 1; }
    printf("PID 1 is ptrace-stopped (status 0x%x); holding for %d s\n", st, secs);
    fflush(stdout);
    for (int i = 0; i < secs; i++) {
        FILE *f = fopen("/proc/1/stat", "r");
        char line[256] = "";
        if (f) { if (!fgets(line, sizeof line, f)) line[0] = 0; fclose(f); }
        char *p = strrchr(line, ')');
        printf("t=%2d  /proc/1/stat state=%c\n", i, p ? p[2] : '?');
        fflush(stdout);
        sleep(1);
    }
    ptrace(PTRACE_DETACH, 1, 0, 0);
    printf("detached\n");
    return 0;
}
```

출력에서 볼 것 (QEMU 콘솔 로그, `boot_5C.log`에서 해당 줄):

- `kill(1, SIGSTOP) returned 0 (but init ignores it)` — 시스템 호출은 0을 돌려줬지만 커널이 시그널을 큐에 넣기 전에 버렸다(§7.3의 `sig_task_ignored`).
- `waitpid` 상태 `0x80057f` = `(PTRACE_EVENT_STOP(128) << 16) | (SIGTRAP << 8) | 0x7f` — `PTRACE_INTERRUPT`로 생긴 ptrace event stop이다.
- `/proc/1/stat` 상태 `t` = tracing stop. PID 1의 이벤트 루프가 완전히 멈췄다.
- `t= 9`까지 찍힌 직후 **`Booting Linux on physical CPU 0x0`** — 10초 timeout이 지나 i6300esb가 QEMU 머신을 리셋했다. 마지막 ping은 freeze 직전 5초 안쪽(PID 1이 timeout의 절반쯤 주기로 ping한다)이었으므로, 리셋은 "마지막 ping 후 약 10초"와 맞다. 아무도 `reboot`을 부르지 않았고, 커널은 panic하지 않았다 — 하드웨어가 리셋했다.

PID 1만 멈췄을 뿐 커널과 다른 프로세스(journald, 내 freeze 프로그램)는 계속 돌고 있었다는 점이 중요하다. 이런 "부분 hang"은 커널 soft-lockup 감지기로도 안 잡힌다. **PID 1 데드락은 HW watchdog만 잡는다.**

freeze 직전에는 journald가 마지막 순간의 로그를 디스크에 남기는지 보려고 이렇게 했다:

```sh
journalctl -b -t l1 -o short-monotonic --no-pager
```

- `bootstatus`는 sysfs가 꺼져 있어 읽지 못했다. I9 §5.4에서는 같은 i6300esb에서 `WDIOC_GETBOOTSTATUS`가 리셋 후 `0x20`(`WDIOF_CARDRESET`)을 돌려줬다. systemd가 장치를 열기 전에(예: initramfs에서) 읽거나 `CONFIG_WATCHDOG_SYSFS=y`로 sysfs에서 읽어 "지난 리셋 원인"을 텔레메트리로 올리는 것이 제품의 정석이다.

### 8.2 저장 정책 — flash 장비에서 가장 중요한 설정

| 설정 (`journald.conf` `[Journal]`) | 기본 (255) | 장비에서의 의미 |
|---|---|---|
| `Storage=` | `auto` | §그림 6 아래 설명. 장비라면 `volatile` 또는 `persistent`를 **명시**한다 |
| `SystemMaxUse=` | 파일시스템의 10% (최대 4 GiB) | `/var/log/journal` 총량 상한. 작은 eMMC 파티션이면 꼭 명시 (예: 64M) |
| `SystemKeepFree=` | 15% | 파일시스템에 최소 이만큼은 남김 |
| `SystemMaxFileSize=` | SystemMaxUse의 1/8 | 파일 하나 크기 — 로테이션 단위, 지울 때도 파일 단위 |
| `RuntimeMaxUse=` | `/run` 크기의 10% | volatile일 때 RAM 상한 |
| `SyncIntervalSec=` | `5m` | 이 주기마다 `fsync`. **CRIT/ALERT/EMERG 메시지는 즉시 sync** |
| `RateLimitIntervalSec=` / `RateLimitBurst=` | `30s` / `10000` | 서비스(정확히는 cgroup)별 — 구간 안에 burst 넘으면 버리고 "Suppressed N messages" |
| `ForwardToSyslog=` | `no` | rsyslog 등으로 넘김 |
| `MaxRetentionSec=` | 0 (끔) | 오래된 항목 시간 기준 삭제 |
| `Compress=` | `yes` | 큰 항목 압축 (zstd/lz4/xz) |

flash 수명 관점의 선택지:

1. **`Storage=volatile`** + 원격 전송(`systemd-journal-upload`, 또는 텔레메트리 에이전트): flash 쓰기 0. 대신 리셋하면 직전 로그가 사라진다 — 크래시 분석에는 L7의 pstore(`/sys/fs/pstore`, RAM에 남는 마지막 커널 로그)로 보완한다.
2. **`Storage=persistent`** + 작은 `SystemMaxUse=` + 긴 `SyncIntervalSec=`: 쓰기는 배치로 몰리고 총량은 상한. 디버깅이 쉽다(`journalctl -b -1`로 직전 부팅). 저널 파일은 append + 인덱스 갱신이라 쓰기 증폭이 있다는 점을 알고 쓴다.
3. **혼합**: journald는 volatile, 중요한 이벤트만 앱이 별도 작은 파일(또는 전용 파티션)에 남김.

SSD 펌웨어 관점으로 말하면, journald의 `fsync` 빈도가 곧 FTL에 들어오는 작은 랜덤 쓰기 빈도다. eMMC 쓰기 수명(TBW)과 저널의 하루 쓰기량을 곱해 보는 습관이 필요하다 — 이것을 재는 법은 J 모듈(J2)과 연결된다.

### 8.4 journalctl 자주 쓰는 질의

| 명령 | 뜻 |
|---|---|
| `journalctl -b` / `-b -1` / `--list-boots` | 이번 부팅 / 직전 부팅 / 부팅 목록 (persistent일 때만 과거가 있음) |
| `journalctl -u imu.service -f` | 한 unit, 실시간 따라가기 |
| `journalctl -p warning -b` | 심각도 warning(4) 이상 |
| `journalctl -k` | 커널 메시지만 (dmesg와 같지만 부팅 간 보존) |
| `journalctl -o short-monotonic` | 부팅 후 경과 시간 — 부팅 분석·실험 타이밍에 |
| `journalctl -o json` / `-o export` | 기계가 읽는 형식 — 원격 수집기로 보낼 때 |
| `journalctl _PID=123` / `_SYSTEMD_UNIT=x` / `SYSLOG_IDENTIFIER=y` | 필드 매치 (같은 필드는 OR, 다른 필드는 AND) |
| `journalctl --since "-10min"` | 시간 범위 |
| `journalctl --disk-usage` / `--vacuum-size=` / `--vacuum-time=` | 용량 확인·정리 |
| `journalctl --sync` / `--flush` / `--rotate` | 즉시 디스크 반영 / `/run`→`/var` 이동 / 새 파일로 |

함정 하나: `-u`와 `-t`를 같이 쓰면 다른 필드라서 **AND**가 된다. "이 unit **또는** 이 태그"를 원하면 `+`로 묶는다(`journalctl _SYSTEMD_UNIT=a.service + SYSLOG_IDENTIFIER=b`). 이 노트의 실험 스크립트를 처음 쓸 때 실제로 이 실수를 했다.

## 9. timer · socket activation · tmpfiles.d — 작은 도구들

### 9.1 timer — cron 대체

cron 대신 `.timer` unit을 쓰면 (1) 실행 결과·출력이 journal에 unit 이름으로 남고, (2) 실행이 겹치지 않으며(같은 서비스가 아직 돌고 있으면 새로 띄우지 않음), (3) 자원 제한·샌드박스 같은 서비스 설정을 그대로 쓰고, (4) 장비가 꺼져 있던 동안 놓친 실행을 `Persistent=true`로 따라잡을 수 있다. 별도 crond 데몬이 필요 없다.

| 지시어 | 기준 | 예 |
|---|---|---|
| `OnBootSec=` | 부팅 후 | `OnBootSec=20s` — 부팅 직후 혼잡을 피해서 |
| `OnUnitActiveSec=` | 마지막으로 서비스가 활성화된 후 | `OnUnitActiveSec=15min` — 주기 실행 |
| `OnCalendar=` | 벽시계 시간 | `Mon..Fri 02:00`, `*:0/15` |
| `Persistent=true` | (OnCalendar 전용) 꺼져 있던 동안 놓친 것 실행 | 일일 로그 업로드 |
| `AccuracySec=` | 실행 시각 오차 허용 (기본 1min) | 전력 절약을 위해 여러 타이머를 묶어 깨움 |
| `RandomizedDelaySec=` | 무작위 지연 | 1,000대가 동시에 서버를 두드리지 않게 |

장비에서 주의할 점: RTC가 없는(또는 배터리 없는) 장비는 부팅 직후 시계가 1970년이거나 빌드 시각이다. `OnCalendar=` 타이머는 `systemd-timesyncd`가 시간을 맞추기 전에 엉뚱하게 동작할 수 있다 — 단조 타이머(`OnBootSec`/`OnUnitActiveSec`)를 쓰거나 `After=time-sync.target`을 고려한다(I9의 RTC 절과 연결).

무엇을 확인하나: `OnCalendar` 표현식 해석, 타이머 등록, 실제 실행 간격.

```text
# /etc/systemd/system/l1-report.timer              # /etc/systemd/system/l1-report.service
[Timer]                                            [Service]
OnBootSec=20s                                      Type=oneshot
OnUnitActiveSec=15s                                ExecStart=/usr/local/bin/l1_report.sh
AccuracySec=1s
[Install]
WantedBy=timers.target
```

- 타이머를 start한 시점(부팅 후 약 285초)에는 `OnBootSec=20s`가 이미 지났으므로 **즉시 한 번** 실행됐다(`LAST ... 2s ago`, `NEXT -`는 서비스가 막 돌고 있어서 다음 시각이 아직 계산 전). 이후 약 15.5초 간격으로 실행됐다. 15초가 아니라 15.5초인 것은 `OnUnitActiveSec=`가 **서비스가 활성화된 시각 기준**이고, oneshot 서비스가 시작·종료되는 데 TCG에서 시간이 걸리기 때문이다. 정확한 벽시계 주기가 필요하면 `OnCalendar=`를 쓴다.
- 이미지에 원래 있던 `apt-daily*.timer`, `fstrim.timer`, `e2scrub_all.timer`가 보인다. 장비에서 `apt-daily-upgrade`는 **필드에서 몰래 패키지를 올리는 위험한 타이머**다 — OTA(L4)로 업데이트를 관리한다면 이미지에서 mask한다. `fstrim.timer`는 eMMC/SSD에 유익하니 남긴다(J2).

### 9.2 socket activation — 연결이 올 때만 띄운다

PID 1이 소켓을 **미리 만들어 listen**하고 있다가, 연결이 오면 서비스를 띄우며 그 소켓 fd를 넘겨준다(fd 3부터, 환경 변수 `LISTEN_FDS`/`LISTEN_PID`). 효과는 세 가지다.

1. **부팅 병렬화**: 소켓은 부팅 초기에 다 만들어지므로, 클라이언트는 서버가 아직 안 떠도 `connect()`할 수 있다(커널 backlog에 쌓임). `After=` 없이도 순서 문제가 사라진다 — journald의 `/dev/log`가 이 방식이라 모든 서비스가 journald보다 먼저 떠도 로그가 안 사라진다.
2. **온디맨드**: 거의 안 쓰는 진단 서비스(공장 테스트 포트, 디버그 셸)는 연결이 올 때만 메모리를 쓴다.
3. **무중단 재시작**: 서비스가 재시작하는 동안에도 소켓은 PID 1이 들고 있어서 연결이 거부되지 않는다.

`Accept=yes`면 연결마다 서비스 인스턴스를 하나씩 띄운다(inetd 방식, stdin/stdout이 그 연결). `Accept=no`(기본)면 리스닝 소켓 자체를 넘기고 서비스가 `accept()`한다(성능상 이쪽이 일반적).

```text
# /etc/systemd/system/l1-echo.socket               # /etc/systemd/system/l1-echo@.service
[Socket]                                           [Service]
ListenStream=127.0.0.1:7777                        ExecStart=/usr/bin/tr a-z A-Z
Accept=yes                                         StandardInput=socket
```

```sh
systemctl start l1-echo.socket; systemctl list-sockets --no-pager | grep -E "LISTEN|7777"
for m in hello sensor; do
  python3 -c "import socket,sys;s=socket.create_connection(('127.0.0.1',7777));s.sendall(sys.argv[1].encode()+b'\n');s.shutdown(1);print(s.recv(100))" $m
done
journalctl -b -u "l1-echo@*" --no-pager -o cat | tail -4
```

### 9.3 tmpfiles.d와 path unit

- **`tmpfiles.d`**: 부팅 때(`systemd-tmpfiles-setup.service`) `/run`, `/var` 아래 디렉터리·파일·심볼릭 링크를 만들고 권한을 맞추고, 오래된 파일을 정리한다. 한 줄 형식 `타입 경로 모드 사용자 그룹 나이 인자`. read-only rootfs 장비에서 "쓰기 가능한 `/var/lib/imu`를 매 부팅 만들기"에 쓴다. 서비스 하나에만 필요한 디렉터리는 unit의 `RuntimeDirectory=imu`(→ `/run/imu`, 서비스 종료 시 삭제)나 `StateDirectory=imu`(→ `/var/lib/imu`)가 더 간단하다.

```text
# /etc/tmpfiles.d/sensorkit.conf
d /run/sensorkit        0755 sensor sensor -
d /var/log/sensorkit    0750 sensor sensor 7d
L /etc/sensorkit/active.json - - - - /data/calib/active.json
```

- **`.path` unit**: inotify로 경로를 감시하다가 조건(`PathExists=`, `PathChanged=`, `DirectoryNotEmpty=`)이 맞으면 짝 서비스를 띄운다. 예: `/data/upload/`에 파일이 생기면 `upload.service` 실행. 폴링 루프 데몬을 없앤다.

- `podman-restart.service`가 graphical.target 바로 앞에 있다. 컨테이너 런타임 패키지가 "부팅 때 restart-policy 컨테이너 재기동"을 `network-online.target` 뒤에 걸어 둔 것이다. 컨테이너를 안 쓰는 장비라면 순수 비용이다(L8).
- `dev-vda.device` 1분 49초, `systemd-udev-trigger.service` 1분 16초: udev coldplug(부팅 시 모든 장치에 uevent를 다시 보내 규칙을 적용)가 무겁다. K6에서도 1위였다.

- `plot`은 260,080바이트 SVG를 만들었다(가로 19,912 px — 초당 100 px로 그리는 간트 차트). 브라우저로 열어 unit별 막대를 본다. 두 번째 부팅(기준 측정)의 plot은 가로 21,384 px, activating/active 막대 301개였다.

### 10.3 깎아 보기 — mask, default target

무엇을 확인하나: 이 장비(헤드리스, 컨테이너 안 씀, 인터넷 연결이 부팅 완료 조건이 아님)에 필요 없는 것을 이미지 빌드 단계에서 끄면 얼마나 줄어드나. 부팅하지 않고 **VM 호스트에서 이미지 루트에 대해** `systemctl --root=`로 작업했다 — Yocto·Buildroot·K6의 이미지 생성 스크립트가 하는 방식과 같다.

```sh
#!/bin/bash
# trim.sh: image-build-time trimming of the A image with systemctl --root (no boot needed)
M=/var/tmp/L1/mnt; mkdir -p $M
sudo mount -o loop /var/tmp/L1/l1_root.ext4 $M || exit 1
sudo systemctl --root=$M set-default multi-user.target
sudo systemctl --root=$M mask systemd-networkd-wait-online.service podman-restart.service \
  podman-auto-update.service podman-clean-transient.service e2scrub_reap.service swupdate.service
sudo ls -l $M/etc/systemd/system/default.target
sudo umount $M
```

출력에서 볼 것:

- 정리 전 critical chain은 두 번 다 `network-online.target` ← `systemd-networkd-wait-online.service`(+1분 16초, +55초)였다. 이번에는 DHCP가 결국 성공해서 wait-online이 실패하지 않았다 — 즉 **성공하는 경우에도** 이 서비스가 부팅의 가장 긴 막대다.
- 정리 후 critical chain은 `multi-user.target` ← `getty.target` ← `serial-getty@ttyAMA0` ← `dev-ttyAMA0.device`로 바뀌었다. 이제 남은 병목은 **udev coldplug가 콘솔 장치를 알려 주는 시점**이다. 다음 단계는 udev 규칙·hwdb 정리, 불필요한 `modprobe@*.service` 줄이기(커널에 built-in으로), 그리고 실제 장비라면 커널 쪽(C7 §4의 `initcall_debug`)이다.
- `blame` 상위가 `dev-vda.device`·`systemd-udev-trigger`·`apparmor`·`modprobe@*`로 바뀌었다. `modprobe@drm`, `@fuse`, `@loop`, `@dm_mod`, `@configfs`, `@efi_pstore`가 각 4~6초(TCG)씩 — systemd가 "모듈일 수 있으니" 미리 modprobe해 두는 unit이다. 이 커널(`Image-sec` config 확인)에서 loop·dm·fuse·configfs·efi_pstore는 **built-in(`=y`)이라 할 일이 없고**, drm만 `=m`이다. 할 일 없는 unit도 TCG에서는 프로세스 생성 비용으로 각 수 초를 쓴다.
- 활성 unit 120 → 112개, 프로세스 88 → 87개, 사용 메모리는 거의 같다(130 MB 안팎). **부팅 시간은 크게 줄었지만 상주 메모리는 거의 그대로**다 — 줄인 것들이 대부분 "부팅 때만 도는" oneshot이거나 기다림이었기 때문이다.

### 10.5 장비에서의 부팅 시간 최적화 순서

1. **"부팅 완료" 정의**: 제품 서비스의 `READY=1`(→ 그 서비스 기준 `critical-chain imu.service`).
2. **측정 조건 고정**: 같은 보드·같은 저장장치 상태·여러 번 측정. TCG·공유 머신이라면 쌍 측정.
3. **critical chain 위의 unit만** 본다. blame은 후보 목록일 뿐.
4. **기다림 제거**: network-online, `TimeoutStartSec` 대기, `ExecStartPre=sleep` 같은 것.
5. **불필요한 unit mask**, default target 정리, 배포판이 깔아 둔 타이머(apt-daily 등) 정리.
6. **늦게 해도 되는 것 미루기**: socket activation, `.timer`의 `OnBootSec=`, `After=` 끝으로.
7. **udev·커널 쪽**: coldplug 대상 줄이기, 모듈 대신 built-in, initcall 분석(C7), 필요하면 initramfs 없애기.
8. 다시 측정하고 `systemd-analyze plot`을 남겨 버전 간 비교.

그림 9 — systemd 기능과 커널 인터페이스의 대응. 왼쪽 열이 PID 1·journald가 쓰는 API, 오른쪽 열이 커널 안의 구조·함수다.

- **서비스 추적 = cgroup v2.** 서비스마다 `/sys/fs/cgroup/system.slice/imu.service/` cgroup을 만들고 그 안에서 fork·exec한다. 데몬이 몇 번 fork하든 자식은 같은 cgroup에 남으므로 "이 서비스의 프로세스 전부"가 정확히 정의된다(커널 `struct css_set`, `cgroup.procs`). stop 때는 `KillMode=control-group`(기본)으로 cgroup 전체에 SIGTERM → `TimeoutStopSec=` 후 SIGKILL. cgroup이 비면 커널이 `cgroup.events`의 `populated 0`을 알리고(inotify), PID 1은 그것으로 "서비스 완전히 끝남"을 안다. 자원 제한(`MemoryMax=`, `CPUQuota=`)도 이 cgroup의 컨트롤러 파일에 쓰는 것이다 — L8(컨테이너)에서 같은 메커니즘을 다시 본다.
- **프로세스 감시 = pidfd + SIGCHLD.** PID 1은 자식 종료를 `SIGCHLD`(signalfd로 이벤트 루프에 연결)와 `waitid()`로 받고, 최신 버전은 PID 재사용 경쟁을 피하려고 pidfd(`pidfd_open`, `pidfd_send_signal`)를 쓴다. PID 1의 특수 규칙(`SIGNAL_UNKILLABLE`, 고아 입양)은 §7.3과 C7 §1.4.
- **sd_notify = AF_UNIX 데이터그램 + `SCM_CREDENTIALS`.** 커널이 `struct ucred`(pid/uid/gid)를 채워 주므로 PID 1은 보낸 쪽을 신뢰할 수 있다(`SO_PASSCRED`). `FDSTORE=1`은 `SCM_RIGHTS`로 `struct file` 참조를 PID 1의 fd 테이블에 복제하는 것이다(A3·A7의 fd 전달과 같은 경로).
- **HW watchdog = `/dev/watchdog0` → watchdog core → 드라이버 ops.** PID 1의 `ioctl(WDIOC_SETTIMEOUT)`·`WDIOC_KEEPALIVE`는 `drivers/watchdog/watchdog_dev.c`의 `watchdog_ioctl()` → `watchdog_ping()` → 드라이버의 `struct watchdog_ops.ping`(i6300esb는 `esb_timer_keepalive`)으로 간다. 드라이버를 쓸 때 채우는 것은 `.start`/`.stop`/`.ping`/`.set_timeout`이고 등록은 `devm_watchdog_register_device()` — I9 §5.2에서 다뤘다. `CONFIG_WATCHDOG_HANDLE_BOOT_ENABLED`면 부트로더가 켜 둔 watchdog을 PID 1이 열 때까지 **커널 워커가 대신 ping**해 준다(`watchdog_dev.c`의 `watchdog_ping_work`) — U-Boot에서 WDT를 켠 채 넘기는 장비에서 중요하다.
- **device unit = uevent + udev.** 커널 드라이버가 `device_add()`하면 kobject uevent가 netlink로 나가고, udevd가 규칙을 적용한 뒤 `TAG+="systemd"`가 붙은 장치를 PID 1에게 알린다(libudev monitor). 그래서 `BindsTo=dev-video0.device`는 결국 **V4L2 드라이버의 `video_register_device()`가 성공했는가**에 묶인다. 장치 이름 규칙은 L2.
- **journald의 입력 = `/dev/kmsg` + 소켓.** 커널 `printk` 링버퍼를 `/dev/kmsg`에서 읽고(`devkmsg_read`), 유저 로그는 `/run/systemd/journal/{socket,stdout}`과 `/dev/log`로 받는다. 서비스의 stdout은 PID 1이 미리 만들어 둔 journald 스트림 소켓에 연결된 fd다(`ls -l /proc/<pid>/fd/1` → `socket:[...]`). 드라이버의 `dev_err()`/`dev_info()`가 journal에서 `_KERNEL_DEVICE=`, `_KERNEL_SUBSYSTEM=` 필드를 갖는 것은 `dev_printk`가 붙이는 구조화 정보(`SUBSYSTEM=`, `DEVICE=`) 덕분이다 — 드라이버 로그를 `journalctl _KERNEL_SUBSYSTEM=i2c`로 걸러 볼 수 있다.
- **부팅 시간 기준 = `CLOCK_MONOTONIC` / `CLOCK_BOOTTIME`.** `systemd-analyze`의 "kernel" 구간은 커널 시작부터 PID 1 실행까지, "userspace"는 PID 1 시작부터 default target 도달까지다. 부트로더 구간은 펌웨어가 EFI 변수로 알려 줄 때만 나온다(ARM 임베디드 + U-Boot 비EFI 부팅이면 안 나옴 — C7 §4).

## 12. Embedded 실무에서 다시 보기

### 12.1 센서 키트 서비스 묶음 설계

IMU·GNSS·카메라·업로더를 가진 장비라면 이런 형태가 된다.

```text
# /etc/systemd/system/sensors.target
[Unit]
Description=Sensor kit services
Wants=imu.service gnss.service camera.service
After=imu.service gnss.service camera.service

# /etc/systemd/system/imu.service
[Unit]
Description=IMU reader (SPI)
After=dev-spidev1.0.device
BindsTo=dev-spidev1.0.device
PartOf=sensors.target
StartLimitIntervalSec=300
StartLimitBurst=5
OnFailure=fault-report@%n.service

[Service]
Type=notify
ExecStart=/usr/bin/imud --dev /dev/spidev1.0
WatchdogSec=3s
Restart=on-failure
RestartSec=2s
RestartPreventExitStatus=78
User=sensor
RuntimeDirectory=imu
```

- `BindsTo=` 장치: 센서 케이블이 빠져 장치가 사라지면 서비스도 멈추고, 다시 꽂히면(`.device`가 다시 생기면) — 이건 자동으로 다시 start되지 않는다. 다시 띄우려면 udev 규칙에 `ENV{SYSTEMD_WANTS}+="imu.service"`를 넣는다(L2).
- `PartOf=sensors.target`: `systemctl restart sensors.target` 한 번으로 묶음 재시작.
- `WatchdogSec=3s`: 메인 루프가 SPI 읽기에서 멈추면(드라이버가 응답 없는 버스에서 무한 대기) 3초 뒤 SIGABRT → coredump(L7) → 재시작.
- 300초에 5회 넘게 재시작하면 포기하고 `fault-report@`가 텔레메트리에 보고. 장비 전체는 계속 돈다(GNSS·카메라는 영향 없음).

### 12.2 "부팅 완료"를 서비스가 정의하게

공장·필드에서 "장비가 준비됐다"는 LED를 켜는 시점은 커널 부팅이 아니라 **센서 데몬들이 `READY=1`을 보낸 시점**이어야 한다. `ready-led.service`를 `After=sensors.target`, `Type=oneshot`으로 두면 그 순서가 그래프로 보장된다. 부팅 시간 KPI도 `systemd-analyze critical-chain sensors.target`처럼 이 target 기준으로 잰다.

### 12.3 Yocto·Buildroot에서 systemd 켜기 (가이드, 실행 안 함)

- Yocto: `DISTRO_FEATURES:append = " systemd usrmerge"`, `VIRTUAL-RUNTIME_init_manager = "systemd"`, 레시피에서 `inherit systemd` + `SYSTEMD_SERVICE:${PN} = "imu.service"` + `SYSTEMD_AUTO_ENABLE = "enable"`. 필요 없는 systemd 구성요소는 `PACKAGECONFIG:remove:pn-systemd = "networkd resolved ..."`로 뺀다 (K4·K5).
- Buildroot: `BR2_INIT_SYSTEMD=y` (glibc 툴체인 필요 — systemd는 musl을 공식 지원하지 않는다), 패키지 `.mk`의 `<PKG>_INSTALL_INIT_SYSTEMD` 훅 (K3).
- 어느 쪽이든 커널 config가 systemd 요구사항(`CGROUPS`, `INOTIFY_USER`, `SIGNALFD`, `TIMERFD`, `EPOLL`, `FHANDLE`, `DEVTMPFS`, `AUTOFS_FS` 권장 …)을 만족해야 한다 — K6 §6.1의 검사 스크립트.

### 12.4 필드 장비의 로그 정책 예

```text
# /etc/systemd/journald.conf.d/10-device.conf
[Journal]
Storage=persistent
SystemMaxUse=48M
SystemMaxFileSize=4M
SyncIntervalSec=10min
RateLimitIntervalSec=30s
RateLimitBurst=2000
MaxLevelStore=info
```

`/var/log/journal`을 rootfs가 아니라 **별도 데이터 파티션**(예: F2FS, J 모듈)에 두면 rootfs를 read-only/dm-verity(L6)로 유지하면서 로그를 남길 수 있다. 크래시 직전 로그를 꼭 남겨야 하는 메시지는 `LOG_CRIT` 이상으로 찍으면 즉시 sync된다(§7.3 실험에서 확인).

## 14. 면접에서 이렇게 말한다

**Q.** "A service crashes in the field — how do you make it self-heal without boot loops?"

**A.** 세 층으로 답한다. (1) 서비스 수준: `Restart=on-failure` + 적절한 `RestartSec=`로 그 서비스만 살린다. 멈춤(hang)은 죽음이 아니라서 `Type=notify` + `WatchdogSec=`로 잡는다 — 메인 루프에서 진행이 있을 때만 `WATCHDOG=1`. (2) 루프 방지: `StartLimitIntervalSec`/`StartLimitBurst`로 "N분에 M번"을 넘으면 포기하고 `failed`에 두고, `OnFailure=`로 로그 저장·텔레메트리·안전 상태 전환. 재부팅은 정말 필요한 서비스에만 `StartLimitAction=reboot`, 그리고 재부팅 루프는 U-Boot bootcount + A/B 롤백(L4)이 끊는다. (3) 시스템 수준: PID 1 자체는 `RuntimeWatchdogSec=`로 HW watchdog이 감시. 그리고 매 실패는 coredump·journal로 남겨 원인을 고친다.

> I layer it. First, per service: Restart=on-failure with a sensible RestartSec, and for hangs rather than crashes, Type=notify with WatchdogSec — the main loop sends WATCHDOG=1 only when it has made real progress, so a deadlock gets a SIGABRT, a core dump, and a restart. Second, loop protection: StartLimitIntervalSec and StartLimitBurst sized against RestartSec so the limit actually trips; after that the unit stays failed and an OnFailure= hook saves logs, reports telemetry and puts the hardware in a safe state. I only escalate to a reboot for services the product can't live without, and boot loops are cut by the bootloader's bootcount with A/B rollback. Third, PID 1 itself is covered by RuntimeWatchdogSec feeding the hardware watchdog. And every failure leaves a core dump and journal so we fix the root cause rather than relying on restarts.

**꼬리 질문**: "재시작으로 상태가 날아가면?" → 상태는 `StateDirectory=`/파일에 체크포인트, 소켓·장치 fd는 `FDSTORE=1`로 PID 1에 맡겨 재시작 후 이어받는다.

**Q.** "What's the difference between Requires= and After=?"

**A.** `Requires=`는 "B를 켜면 A도 켜라, A가 명시적으로 멈추면 B도 멈춰라"라는 **의존성**이고, `After=`는 "둘 다 켜질 때 A의 start가 끝난 뒤 B를 시작하라"는 **순서**다. 서로 독립이라 `Requires=`만 쓰면 동시에 시작된다. 이 노트 실험에서 `After=` 없이는 B가 A보다 먼저 시작해 A의 파일을 못 찾았고, A가 실패해도 B가 실행됐다. `After=`를 넣으면 B는 A가 끝날 때까지 기다리고, A 실패 시 "Dependency failed"로 B는 실행되지 않는다. 그리고 "끝났다"는 A의 `Type=`이 정의한다.

> Requires is a dependency: starting B pulls in A, and stopping A explicitly stops B. After is ordering: if both are in the transaction, B's start waits until A's start job has completed. They're orthogonal — Requires alone starts both in parallel. I demonstrated this: without After, B ran before A finished and even ran when A failed; with After, B waited and failed with "dependency failed" when A failed. Also "completed" is defined by A's Type — for Type=simple that's right after fork, so for real readiness you want Type=notify. In practice you almost always pair Wants or Requires with After, and prefer Wants unless you really need the stop propagation; BindsTo is the stronger form that also reacts when A dies on its own.

**Q.** "How does systemd's watchdog relate to the hardware watchdog?"

**A.** 두 단이다. 서비스 watchdog(`WatchdogSec=`)은 순수 소프트웨어 — PID 1이 서비스별 타이머를 들고 있다가 `WATCHDOG=1`이 안 오면 그 서비스만 죽이고 재시작한다. HW watchdog은 PID 1이 `RuntimeWatchdogSec=`로 `/dev/watchdog0`을 열어 주기적으로 ping한다 — PID 1의 이벤트 루프가 돌아야 ping이 가므로 PID 1이나 커널이 멈추면 보드가 리셋된다. 이 노트에서 PID 1을 ptrace로 세웠더니 i6300esb가 timeout 뒤 QEMU 머신을 리셋했다. 추가로 `RebootWatchdogSec=`가 종료 경로의 멈춤을 잡고, 부팅 직후 bootstatus로 "지난번 리셋이 watchdog 때문이었나"를 텔레메트리에 올린다.

> They're two tiers. The service watchdog is purely software: PID 1 keeps a timer per unit and, if WATCHDOG=1 doesn't arrive within WatchdogSec, it kills just that service with SIGABRT and the Restart policy takes over. The hardware watchdog is fed by PID 1 itself when RuntimeWatchdogSec is set — it opens /dev/watchdog0, sets the timeout and pings from its event loop. So if PID 1 or the kernel wedges, nobody pings and the SoC resets. I tested that in QEMU with an i6300esb: I ptrace-stopped PID 1 — you can't SIGSTOP init — and the machine reset after the timeout. RebootWatchdogSec covers a hung shutdown, and on the next boot the driver's bootstatus tells you the reset was a watchdog reset, which you report as a field metric.

**Q.** "How would you reduce boot time on a systemd-based device?"

**A.** 먼저 "부팅 완료"를 정의한다(제품 서비스의 `READY=1`). `systemd-analyze`로 kernel/userspace를 나누고, `critical-chain <target>`으로 **경로 위의** unit만 본다 — `blame`은 병렬로 숨는 시간까지 보여서 오해를 준다. 그다음 불필요한 unit mask, default target을 multi-user로, network-online을 기다리는 서비스 줄이기, udev coldplug 비용 확인, 무거운 초기화는 socket/timer/`After=` 뒤로 미루기. 바꿀 때마다 같은 조건에서 여러 번 재서 비교한다.

> Define "booted" first — usually our main service signalling READY=1. Then systemd-analyze to split kernel and userspace, and critical-chain on that target, because blame lists time that's hidden by parallelism. Then: mask units the product doesn't need, set multi-user as default, stop making services wait for network-online unless they must, look at udev coldplug cost, and defer non-critical work with socket activation or timers. Measure every change several times under the same conditions — on my QEMU setup the numbers are only meaningful relative to each other.

**Q.** "Where do you put your own unit files and how do you change a vendor unit?"

**A.** 제품 unit은 `/etc/systemd/system`(이미지에 굽기) 또는 패키지로 `/usr/lib/systemd/system`. 벤더 unit은 절대 고치지 않고 drop-in(`systemctl edit` → `override.conf`)으로 바꾼다. 리스트 항목은 빈 값으로 먼저 지운다. `systemctl cat`과 `systemd-delta`로 최종 설정을 확인한다.

> Our own units ship in the image under /etc/systemd/system or in a package under /usr/lib/systemd/system. Vendor units are never edited in place — I use drop-ins via systemctl edit, so a package or OTA update doesn't wipe the change, and for list settings like ExecStart I reset with an empty assignment first. systemctl cat shows the merged result and systemd-delta shows everything that's overridden on a box.

**Q.** "Journald on flash — what do you configure?"

**A.** `Storage=`를 명시(volatile+원격, 또는 persistent+상한), `SystemMaxUse=`/`SystemMaxFileSize=`로 총량·로테이션, `SyncIntervalSec=`로 fsync 빈도, rate limit으로 폭주 서비스 차단. 크리티컬 메시지는 즉시 sync된다는 점을 이용하고, 크래시 분석은 pstore로 보완. 가능하면 로그는 데이터 파티션에.

> I make Storage explicit — volatile plus remote shipping, or persistent with a hard cap via SystemMaxUse and SystemMaxFileSize — and lengthen SyncIntervalSec to batch writes, knowing CRIT and above are synced immediately. Rate limits stop a runaway service from flooding flash. The journal lives on a data partition so the rootfs can stay read-only, and for crash forensics I add pstore for the last kernel messages.

**Q.** "What is socket activation and why would you use it on a device?"

**A.** PID 1이 소켓을 먼저 열어 두고 연결이 오면 서비스를 띄워 fd를 넘긴다. 부팅 순서 의존성이 사라지고(클라이언트는 backlog에서 기다림), 드물게 쓰는 서비스는 메모리를 안 쓰고, 재시작 중에도 연결을 잃지 않는다.

> PID 1 creates and listens on the socket early and passes the fd to the service when a connection arrives. That removes ordering dependencies — clients can connect before the server is up and just wait in the backlog — keeps rarely-used diagnostic services out of memory, and lets a service restart without refusing connections.

## 15. 직접 해보기

1. (개념) `Wants=A`만 있고 `After=`가 없는 B를 start했는데 A가 실패했다. B는 어떻게 되나? `Requires=A`면? `Requires=A`+`After=A`면?
   정답/힌트: Wants → B는 그대로 실행. Requires(After 없음) → 동시 시작이라 B는 실행됨(A의 실패가 B의 start job을 막지 못함). Requires+After → B는 "dependency failed"로 실행 안 됨. §3.3 출력.
2. (코드) `l1_notifyd.c`에 `EXTEND_TIMEOUT_USEC=`를 추가해, 시작 전 10초 캘리브레이션을 하는 서비스가 `TimeoutStartSec=5s`에도 실패하지 않게 만들어 보라.
   정답/힌트: 캘리브레이션 루프 안에서 3초마다 `EXTEND_TIMEOUT_USEC=5000000`을 보낸다. 안 보내면 `start operation timed out`으로 실패.
3. (코드) 메인 루프가 진행했을 때만 ping하도록 "마지막 센서 샘플 시각"을 검사하는 구조로 바꿔라. 별도 스레드가 무조건 ping하는 버전과 비교해, 메인 루프에 `pause()`를 넣었을 때 어느 쪽이 재시작되는지 확인하라.
   정답/힌트: 무조건 ping 버전은 영원히 `active`로 남는다.
4. (관찰) 서비스의 stdout이 어디에 연결되어 있는지 `ls -l /proc/$(systemctl show -p MainPID --value l1-notifyd)/fd`로 보고, `ss -xp`에서 그 소켓의 반대편을 찾아라.
   정답/힌트: fd 1·2가 `socket:[N]`, 반대편은 `/run/systemd/journal/stdout`의 journald.
5. (설계) 카메라 서비스가 `/dev/video0`이 나타날 때 자동으로 뜨고, 사라지면 멈추게 하라.
   정답/힌트: `BindsTo=dev-video0.device` + `After=dev-video0.device`, udev 규칙 `TAG+="systemd", ENV{SYSTEMD_WANTS}+="camera.service"` (L2).
6. (관찰) `RuntimeWatchdogSec=10s`인 상태에서 `strace -p 1 -e trace=ioctl -tt`로 PID 1의 `WDIOC_KEEPALIVE` 주기를 재라.
   정답/힌트: 대략 timeout의 절반(5초) 근처. strace를 붙이는 것 자체가 ptrace라 너무 오래 세우지 않게 주의.
7. (부팅 시간) 이 노트의 trimmed 이미지에서 `systemd-analyze critical-chain`의 맨 위 항목 하나를 더 없애고(혹은 뒤로 미루고) 3회 측정 평균을 비교하라.
   정답/힌트: TCG는 편차가 크다 — 최소 3회, 같은 QEMU 옵션.

## 16. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| unit | 관리 단위 | 서비스·소켓·마운트·장치·타깃 등 systemd가 상태를 가진 객체로 다루는 것 |
| job | 작업 | unit에 대한 start/stop/restart/reload 요청 하나 |
| transaction | 작업 묶음 | 요청 하나에 필요한 job 전부를 의존성·순서 검사 후 한 번에 큐에 넣는 것 |
| target | 동기화 지점 | 실행 내용 없이 다른 unit을 묶는 unit (runlevel 대체) |
| drop-in | 덧붙임 설정 | `<unit>.d/*.conf` — 원본을 고치지 않고 일부만 덮어씀 |
| generator | 생성기 | 부팅 때 fstab·커맨드라인 등으로 unit 파일을 만드는 프로그램 |
| mask | 봉인 | unit을 `/dev/null` 링크로 덮어 어떤 방법으로도 시작 못 하게 함 |
| preset | 기본 enable 정책 | `*.preset` 파일의 enable/disable 규칙, 첫 부팅 때 적용 |
| sd_notify | 상태 통지 | 서비스 → PID 1 `NOTIFY_SOCKET` 데이터그램 (`READY=1` 등) |
| WatchdogSec | 서비스 watchdog | 주기 안에 `WATCHDOG=1`이 없으면 서비스를 죽이고 재시작 |
| RuntimeWatchdogSec | HW watchdog 급식 | PID 1이 `/dev/watchdog0`을 열고 주기적으로 ping |
| StartLimitBurst | 시작 제한 | 구간 안 시작 횟수 상한 — 넘으면 `start-limit-hit`로 실패 |
| OnFailure | 실패 훅 | unit이 failed로 들어갈 때 시작할 unit |
| socket activation | 소켓 활성화 | PID 1이 listen하다 연결 오면 서비스를 띄우고 fd 전달 |
| journald | 로그 데몬 | 구조화·인덱스 바이너리 로그, 메타데이터 부착, rate limit |
| critical chain | 임계 경로 | target 도달까지 시간상 가장 긴 의존 경로 |
| cgroup | 컨트롤 그룹 | 서비스 프로세스 전체를 묶어 추적·자원 제한하는 커널 기능 |

## 17. 요약 & 체크리스트

systemd는 PID 1 안에서 unit 그래프와 job 큐를 돌리는 서비스 매니저다. 의존성(`Wants`/`Requires`/`BindsTo`/`PartOf`/`Requisite`)과 순서(`After`/`Before`)는 별개의 축이라 거의 항상 짝으로 쓰고, "시작 완료"는 `Type=`이 정한다. 필드 장비의 자가 복구는 `Restart=on-failure` + `Type=notify`/`WatchdogSec=`(멈춤 감지) + 계산된 `StartLimit*` + `OnFailure=` 훅, 그리고 PID 1 자신을 지키는 `RuntimeWatchdogSec=`(HW watchdog)의 층으로 만든다. 로그는 journald에 맡기되 flash에 맞게 `Storage=`·크기·sync 주기를 명시한다. 부팅 시간은 `systemd-analyze critical-chain`으로 경로 위의 unit만 보고, mask·default target·network-online 정리로 줄이며, TCG 같은 측정 환경의 한계를 알고 상대 비교한다.

- [ ] BusyBox init 대비 systemd를 고를 근거와 비용(크기·부팅 시간)을 말할 수 있다
- [ ] unit 파일 검색 경로와 우선순위, drop-in·`systemctl edit`·`systemctl cat`·`systemd-delta`를 쓸 수 있다
- [ ] `Requires=`와 `After=`의 차이를 경주 실험으로 설명할 수 있다
- [ ] `BindsTo=`, `PartOf=`, `Requisite=`의 정지 전파 차이를 말할 수 있다
- [ ] `Type=simple/exec/forking/notify/oneshot`의 "시작 완료" 시점을 구분할 수 있다
- [ ] `Restart=`, `RestartSec=`, `StartLimitIntervalSec=`/`Burst=`를 boot loop 없이 설계할 수 있다
- [ ] `NOTIFY_SOCKET` 프로토콜을 libsystemd 없이 C로 구현할 수 있다
- [ ] 서비스 watchdog과 `RuntimeWatchdogSec=` HW watchdog의 관계와, PID 1이 멈출 때 일어나는 일을 설명할 수 있다
- [ ] journald의 `Storage=`·`SystemMaxUse=`·rate limit을 flash 수명에 맞게 설정할 수 있다
- [ ] `journalctl -b -1 -u -p -o json`으로 필요한 로그를 뽑을 수 있다
- [ ] timer로 cron을, socket activation으로 상시 데몬을 대체할 수 있다
- [ ] `systemd-analyze time/blame/critical-chain/plot`으로 부팅 시간을 분석하고 줄일 수 있다
