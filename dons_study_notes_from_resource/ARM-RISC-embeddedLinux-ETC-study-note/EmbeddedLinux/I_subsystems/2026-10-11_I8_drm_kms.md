# I8. DRM/KMS — CRTC · encoder · connector · plane, framebuffer, atomic modesetting, GPU와의 관계

> **이 노트를 다 읽으면**: DRM이 KMS(화면 파이프라인 제어)·render/GEM(GPU 메모리와 명령 제출)·accel(NPU)의 세 갈래라는 것을 노드(`card0`/`renderD128`/`accel0`)로 구분해 말할 수 있다 · framebuffer → plane → CRTC → encoder(→ bridge) → connector 파이프라인을 libdrm 없이 ioctl로 나열하고, dumb buffer를 그려서 legacy `SETCRTC`와 atomic commit(TEST_ONLY, ALLOW_MODESET, NONBLOCK, out-fence, flip 이벤트)으로 화면에 걸 수 있다 · vkms의 writeback connector와 CRC로 **모니터 없이** 합성 결과를 픽셀 단위로 검증하고, PRIME(dma-buf)으로 GPU 버퍼를 디스플레이에 복사 없이 넘길 수 있다 · 디스플레이 드라이버 뼈대(`drm_driver`, `drm_mode_config_funcs`, atomic helper, bridge/panel, DT ports/endpoints)를 읽을 수 있다
> **왜 필요한가**: 카메라·HMI 화면이 붙는 로봇/차량 장비는 거의 다 DRM/KMS로 화면을 내고(Weston, Qt eglfs, GStreamer `kmssink`), GPU·NPU 드라이버도 같은 DRM 틀(GEM, dma-buf, fence, `drm/accel`) 위에 있다 — "카메라 프레임을 복사 없이 화면과 NPU로 보내라"는 요구가 면접과 실무에서 이 노트의 내용으로 이어진다
> **Don 기준 난이도**: 프레임 버퍼·DMA·더블 버퍼링·인터럽트(vblank)·레지스터 shadow/commit은 펌웨어에서 익숙한 개념이다 / 새로 배울 것은 Linux가 이것을 **객체(plane/CRTC/connector)와 속성(property)으로 모델링하고, "상태 전체를 검사한 뒤 한 번에 적용"하는 atomic 계약**으로 묶는 방식, 그리고 GEM·PRIME·render node·accel 같은 버퍼/권한 모델
> **선행 노트**: G5(`mmap` 드라이버 쪽), F10(CMA — 연속 버퍼 스캔아웃), H9(DMA·dma-buf exporter/importer), I5(V4L2 — 카메라 버퍼를 dma-buf로 내보내기), D 모듈(DT ports/endpoints)

## 0. 큰 그림 — DRM은 세 갈래다

Don이 SSD 컨트롤러에서 DMA 엔진과 호스트 인터페이스를 따로 다뤘듯이, Linux의 그래픽 스택도 **화면을 내보내는 하드웨어**와 **계산하는 하드웨어**를 구분한다. 둘 다 `drivers/gpu/drm/` 아래 **DRM(Direct Rendering Manager)** 이라는 한 서브시스템이 맡는다.

- **KMS (Kernel Mode Setting)**: 디스플레이 컨트롤러. "이 메모리 버퍼를 이 해상도·이 타이밍으로 이 출력 포트에 내보내라." SoC의 LCDIF, DSS, DPU 같은 블록이다. 계산은 안 한다. 메모리를 읽어 픽셀 스트림으로 바꿀 뿐이다(scanout).
- **render / GEM**: GPU. "이 버퍼들에 이 명령 스트림을 실행하라." 메모리 관리(GEM)와 명령 제출(submit), 완료 신호(fence)가 핵심이다. 화면과는 무관하다.
- **accel**: NPU 같은 연산 가속기. 6.2부터 `drivers/accel/`에 생긴 DRM의 갈래로, GPU와 같은 GEM/submit 모델을 쓰되 `/dev/accel/accelN`이라는 별도 노드를 쓴다.

SoC에서는 이 셋이 **보통 서로 다른 IP 블록이고 서로 다른 드라이버**다. 예를 들어 i.MX8M Plus에서 화면은 `imx-lcdif`(KMS), GPU는 `etnaviv`(render), NPU도 etnaviv 계열 또는 벤더 드라이버가 맡는다. 셋을 잇는 것은 **dma-buf** — 한 장치가 만든 버퍼를 fd로 다른 장치에 넘기는 커널 공용 객체(H9 §11)다.

| 펌웨어에서 하던 일 | DRM에서 | 이 노트 |
|---|---|---|

## 1. 실습 준비 — libdrm 없이 ioctl만으로

### 1.1 왜 libdrm 없이 하나

실제 제품에서는 `libdrm`(`drmModeGetResources()` 같은 C 래퍼)과 `modetest`·`kmscube`를 쓴다. 이 노트는 일부러 그 아래 ioctl을 직접 부른다. 이유는 두 가지다. 게스트 initramfs에 libdrm이 없고, 무엇보다 **커널 uAPI 구조체를 직접 채워 봐야** 커널 쪽 코드(`drm_mode_getresources()` 등)와 1:1로 연결된다. libdrm 함수는 거의 다 "ioctl 한 번 + 메모리 할당"의 얇은 래퍼다.

DRM ioctl에는 반복되는 관용구가 하나 있다. **배열을 돌려주는 ioctl은 두 번 부른다**: 처음엔 `count_*`를 0으로 해서 개수를 받고, 배열 포인터(`__u64`로 캐스팅)와 개수를 채워 다시 부른다. 커널은 사용자가 준 개수까지만 채우고 실제 개수를 다시 써 준다. 포인터가 `__u64`인 이유는 32비트 유저가 64비트 커널을 부를 때 구조체 레이아웃이 같아야 하기 때문이다(compat ioctl 변환이 필요 없다).

### 1.3 공용 헤더 `i8_drm.h`

모든 예제가 쓰는 작은 헬퍼다. 세 부분으로 나눠 싣는다. 첫 부분은 ioctl 래퍼, 속성 이름 → id 조회, dumb buffer 생성이다.

```c
/* i8_drm.h (1/3) — libdrm 없이 DRM uAPI ioctl만으로 쓰는 작은 헬퍼 */
#include <drm/drm.h>
#include <drm/drm_mode.h>
#include <drm/drm_fourcc.h>
#include <errno.h>
#include <fcntl.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <unistd.h>

#define P(x) ((uint64_t)(uintptr_t)(x))
static inline void die(const char *m) { perror(m); exit(1); }
static inline int xioctl(int fd, unsigned long req, void *arg)
{
	int r;
	do r = ioctl(fd, req, arg); while (r == -1 && (errno == EINTR || errno == EAGAIN));
	return r;
}
static inline int dopen(const char *path)
{
	int fd = open(path, O_RDWR | O_CLOEXEC);
	if (fd < 0) die(path);
	return fd;
}
/* 객체(obj_id, type)의 속성 이름 → 속성 id. value가 있으면 현재 값도 돌려준다 */
static inline uint32_t prop_id(int fd, uint32_t obj, uint32_t type, const char *name, uint64_t *value)
{
	uint32_t ids[64]; uint64_t vals[64];
	struct drm_mode_obj_get_properties op = { .obj_id = obj, .obj_type = type };
	if (xioctl(fd, DRM_IOCTL_MODE_OBJ_GETPROPERTIES, &op)) die("OBJ_GETPROPERTIES");
	if (op.count_props > 64) op.count_props = 64;
	op.props_ptr = P(ids); op.prop_values_ptr = P(vals);
	if (xioctl(fd, DRM_IOCTL_MODE_OBJ_GETPROPERTIES, &op)) die("OBJ_GETPROPERTIES");
	for (uint32_t i = 0; i < op.count_props; i++) {
		struct drm_mode_get_property gp = { .prop_id = ids[i] };
		if (xioctl(fd, DRM_IOCTL_MODE_GETPROPERTY, &gp)) die("GETPROPERTY");
		if (!strcmp(gp.name, name)) { if (value) *value = vals[i]; return ids[i]; }
	}
	fprintf(stderr, "no prop %s on obj %u\n", name, obj); exit(1);
}
/* dumb buffer + mmap + framebuffer */
struct dumb { uint32_t w, h, fmt, handle, pitch, fb; uint64_t size; uint32_t *px; };
static inline void dumb_create(int fd, struct dumb *d, uint32_t w, uint32_t h, uint32_t fmt)
{
	struct drm_mode_create_dumb c = { .width = w, .height = h, .bpp = 32 };
	if (xioctl(fd, DRM_IOCTL_MODE_CREATE_DUMB, &c)) die("CREATE_DUMB");
	struct drm_mode_map_dumb m = { .handle = c.handle };
	if (xioctl(fd, DRM_IOCTL_MODE_MAP_DUMB, &m)) die("MAP_DUMB");
	d->px = mmap(NULL, c.size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, m.offset);
	if (d->px == MAP_FAILED) die("mmap");
	d->w = w; d->h = h; d->fmt = fmt; d->handle = c.handle; d->pitch = c.pitch; d->size = c.size;
	struct drm_mode_fb_cmd2 f = { .width = w, .height = h, .pixel_format = fmt,
		.handles = { c.handle }, .pitches = { c.pitch } };
	if (xioctl(fd, DRM_IOCTL_MODE_ADDFB2, &f)) die("ADDFB2");
	d->fb = f.fb_id;
}
```

두 번째 부분은 "연결된 첫 connector와 그 preferred 모드 찾기"와 atomic 요청 빌더다. `DRM_IOCTL_MODE_ATOMIC`은 속성을 **객체별로 묶은** 세 배열(객체 id, 객체마다 속성 개수, 속성 id/값의 평탄한 배열)을 받는다. `acommit()`이 그 묶기를 한다.

```c
/* i8_drm.h (2/3) — 출력 찾기, atomic 요청 빌더 */
static inline void first_output(int fd, uint32_t *conn, uint32_t *crtc, struct drm_mode_modeinfo *mode)
{
	uint32_t conns[8], crtcs[8], encs[8];
	struct drm_mode_card_res r = { 0 };
	if (xioctl(fd, DRM_IOCTL_MODE_GETRESOURCES, &r)) die("GETRESOURCES");
	r.connector_id_ptr = P(conns); r.crtc_id_ptr = P(crtcs); r.encoder_id_ptr = P(encs);
	r.count_fbs = 0; r.count_connectors = 8; r.count_crtcs = 8; r.count_encoders = 8;
	if (xioctl(fd, DRM_IOCTL_MODE_GETRESOURCES, &r)) die("GETRESOURCES");
	for (uint32_t i = 0; i < r.count_connectors; i++) {
		struct drm_mode_modeinfo modes[64];
		struct drm_mode_get_connector c = { .connector_id = conns[i] };
		if (xioctl(fd, DRM_IOCTL_MODE_GETCONNECTOR, &c)) die("GETCONNECTOR");
		if (c.connection != 1 || c.count_modes == 0
		    || c.connector_type == DRM_MODE_CONNECTOR_WRITEBACK) continue;
		if (c.count_modes > 64) c.count_modes = 64;
		c.modes_ptr = P(modes); c.count_props = 0; c.count_encoders = 0;
		if (xioctl(fd, DRM_IOCTL_MODE_GETCONNECTOR, &c)) die("GETCONNECTOR");
		*conn = conns[i]; *crtc = crtcs[0]; *mode = modes[0];
		for (uint32_t k = 0; k < c.count_modes; k++)
			if (modes[k].type & DRM_MODE_TYPE_PREFERRED) { *mode = modes[k]; break; }
		return;
	}
	fprintf(stderr, "no connected connector\n"); exit(1);
}
/* atomic 요청 빌더: (obj, prop, value) 를 객체별로 묶어서 DRM_IOCTL_MODE_ATOMIC 한 번에 */
struct areq { int n; uint32_t obj[64], prop[64]; uint64_t val[64]; };
static inline void aadd(struct areq *a, uint32_t obj, uint32_t prop, uint64_t val)
{ a->obj[a->n] = obj; a->prop[a->n] = prop; a->val[a->n] = val; a->n++; }
static inline int acommit(int fd, struct areq *a, uint32_t flags, void *user)
{
	uint32_t objs[64], cnt[64], props[64]; uint64_t vals[64]; int no = 0, np = 0;
	for (int i = 0; i < a->n; i++) {
		int seen = 0;
		for (int k = 0; k < no; k++) if (objs[k] == a->obj[i]) seen = 1;
		if (seen) continue;
		objs[no] = a->obj[i]; cnt[no] = 0;
		for (int j = i; j < a->n; j++) if (a->obj[j] == a->obj[i]) {
			props[np] = a->prop[j]; vals[np++] = a->val[j]; cnt[no]++; }
		no++;
	}
	struct drm_mode_atomic at = { .flags = flags, .count_objs = no, .objs_ptr = P(objs),
		.count_props_ptr = P(cnt), .props_ptr = P(props), .prop_values_ptr = P(vals),
		.user_data = P(user) };
	return ioctl(fd, DRM_IOCTL_MODE_ATOMIC, &at);
}
static inline uint32_t mode_blob(int fd, struct drm_mode_modeinfo *m)
{
	struct drm_mode_create_blob b = { .data = P(m), .length = sizeof(*m) };
	if (xioctl(fd, DRM_IOCTL_MODE_CREATEPROPBLOB, &b)) die("CREATEPROPBLOB");
	return b.blob_id;
}
static inline void cap(int fd, uint64_t c, uint64_t v)
{
	struct drm_set_client_cap s = { .capability = c, .value = v };
	if (xioctl(fd, DRM_IOCTL_SET_CLIENT_CAP, &s)) die("SET_CLIENT_CAP");
}
```

세 번째 부분은 plane 찾기, plane 하나를 배치하는 속성 10개, writeback connector 찾기다.

```c
/* i8_drm.h (3/3) — plane/writeback 헬퍼 */
/* type 속성이 want(0 overlay, 1 primary, 2 cursor)인 n번째 plane */
static inline uint32_t find_plane(int fd, uint64_t want, int nth)
{
	uint32_t ids[16];
	struct drm_mode_get_plane_res pr = { .plane_id_ptr = P(ids), .count_planes = 16 };
	if (xioctl(fd, DRM_IOCTL_MODE_GETPLANERESOURCES, &pr)) die("GETPLANERESOURCES");
	for (uint32_t i = 0; i < pr.count_planes; i++) {
		uint64_t t; prop_id(fd, ids[i], DRM_MODE_OBJECT_PLANE, "type", &t);
		if (t == want && nth-- == 0) return ids[i];
	}
	fprintf(stderr, "no plane of type %llu\n", (unsigned long long)want); exit(1);
}
/* plane 하나를 fb 전체 → CRTC의 (x,y,w,h)에 놓는 속성 10개 */
static inline void aplane(int fd, struct areq *a, uint32_t pl, uint32_t crtc, struct dumb *d,
			  int x, int y)
{
	uint32_t o = DRM_MODE_OBJECT_PLANE;
	aadd(a, pl, prop_id(fd, pl, o, "FB_ID", NULL), d ? d->fb : 0);
	aadd(a, pl, prop_id(fd, pl, o, "CRTC_ID", NULL), d ? crtc : 0);
	aadd(a, pl, prop_id(fd, pl, o, "SRC_X", NULL), 0);
	aadd(a, pl, prop_id(fd, pl, o, "SRC_Y", NULL), 0);
	aadd(a, pl, prop_id(fd, pl, o, "SRC_W", NULL), d ? (uint64_t)d->w << 16 : 0);	/* 16.16 고정소수점 */
	aadd(a, pl, prop_id(fd, pl, o, "SRC_H", NULL), d ? (uint64_t)d->h << 16 : 0);
	aadd(a, pl, prop_id(fd, pl, o, "CRTC_X", NULL), x);
	aadd(a, pl, prop_id(fd, pl, o, "CRTC_Y", NULL), y);
	aadd(a, pl, prop_id(fd, pl, o, "CRTC_W", NULL), d ? d->w : 0);
	aadd(a, pl, prop_id(fd, pl, o, "CRTC_H", NULL), d ? d->h : 0);
}
/* connector_type == WRITEBACK 인 connector (CLIENT_CAP_WRITEBACK_CONNECTORS 필요) */
static inline uint32_t find_wb(int fd)
{
	uint32_t ids[8]; struct drm_mode_card_res r = { .connector_id_ptr = P(ids), .count_connectors = 8 };
	if (xioctl(fd, DRM_IOCTL_MODE_GETRESOURCES, &r)) die("GETRESOURCES");
	for (uint32_t i = 0; i < r.count_connectors; i++) {
		struct drm_mode_get_connector c = { .connector_id = ids[i] };
		if (xioctl(fd, DRM_IOCTL_MODE_GETCONNECTOR, &c)) die("GETCONNECTOR");
		if (c.connector_type == DRM_MODE_CONNECTOR_WRITEBACK) return ids[i];
	}
	fprintf(stderr, "no writeback connector\n"); exit(1);
}
```

### 1.4 흔한 함정

- 배열 ioctl을 한 번만 부르고 `count_*`만 믿는 것: 두 번째 호출 사이에 핫플러그로 개수가 바뀔 수 있다. libdrm도 개수가 늘었으면 다시 부르는 루프를 돈다. 위 헬퍼는 상한(8, 64)을 둬서 단순화했다.
- 구조체를 0으로 초기화하지 않는 것: 예약 필드(`reserved`, `pad`)가 0이 아니면 커널이 `EINVAL`을 돌려준다(예: `drm_mode_atomic.reserved`). 지정 초기화자 `{ .x = … }`는 나머지를 0으로 만든다.
- 포인터를 `__u64`에 넣을 때 `(uint64_t)ptr`로 바로 캐스팅하면 32비트 빌드에서 부호 확장 경고가 난다. `(uintptr_t)`를 거친다(`P()` 매크로).

## 2. DRM 장치 들여다보기 — 노드, 드라이버 이름, capability

### 2.1 직관

DRM 장치 하나는 `struct drm_device` 하나이고, 유저에게는 **minor 노드** 최대 두~세 개로 보인다. `/dev/dri/cardN`(primary, major 226 minor 0~)은 KMS와 GEM 전부, `/dev/dri/renderD128`(render, minor 128~)은 GEM과 명령 제출만, accel 장치는 `/dev/accel/accelN`(major 261)이다. 같은 장치를 가리키는 서로 다른 "권한 창구"라고 생각하면 된다 — Don이 SSD에서 같은 컨트롤러를 관리용 admin 큐와 데이터용 I/O 큐로 나눠 열었던 것과 비슷하다.

`DRM_IOCTL_VERSION`은 드라이버 이름을, `DRM_IOCTL_GET_CAP`은 그 드라이버가 지원하는 기능(dumb buffer, PRIME, vblank 이벤트 형식…)을 알려 준다. 유저 공간 라이브러리는 이 값으로 경로를 고른다.

### 2.2 예제 1 — 드라이버 이름과 capability, 그리고 KMS ioctl 시도

무엇을 확인하나: vkms(card0)에서 `VERSION`·`GET_CAP`이 무엇을 말하는지, KMS ioctl(`GETRESOURCES`)과 dumb buffer 생성이 card 노드에서 되는지.

```c
/* i8_info.c <node> — 드라이버 이름(DRM_IOCTL_VERSION)과 GET_CAP 몇 개 */
#include "i8_drm.h"
int main(int argc, char **argv)
{
	int fd = dopen(argc > 1 ? argv[1] : "/dev/dri/card0");
	char name[32] = "", date[32] = "", desc[64] = "";
	struct drm_version v = { .name_len = sizeof(name) - 1, .name = name,
		.date_len = sizeof(date) - 1, .date = date, .desc_len = sizeof(desc) - 1, .desc = desc };
	if (xioctl(fd, DRM_IOCTL_VERSION, &v)) die("VERSION");
	printf("driver=%s %d.%d.%d desc=\"%s\"\n", name, v.version_major,
	       v.version_minor, v.version_patchlevel, desc);
	static const struct { uint64_t c; const char *n; } caps[] = {
		{ DRM_CAP_DUMB_BUFFER, "DUMB_BUFFER" }, { DRM_CAP_PRIME, "PRIME(1=import 2=export)" },
		{ DRM_CAP_VBLANK_HIGH_CRTC, "VBLANK_HIGH_CRTC" },
		{ DRM_CAP_TIMESTAMP_MONOTONIC, "TIMESTAMP_MONOTONIC" },
		{ DRM_CAP_CRTC_IN_VBLANK_EVENT, "CRTC_IN_VBLANK_EVENT" },
		{ DRM_CAP_SYNCOBJ, "SYNCOBJ" }, { DRM_CAP_ASYNC_PAGE_FLIP, "ASYNC_PAGE_FLIP" },
		{ DRM_CAP_CURSOR_WIDTH, "CURSOR_WIDTH" },
	};
	for (unsigned i = 0; i < sizeof(caps) / sizeof(caps[0]); i++) {
		struct drm_get_cap g = { .capability = caps[i].c };
		if (xioctl(fd, DRM_IOCTL_GET_CAP, &g)) printf("  %-26s err=%s\n", caps[i].n, strerror(errno));
		else printf("  %-26s %llu\n", caps[i].n, (unsigned long long)g.value);
	}
	/* KMS ioctl 하나 시도 — render node에서는 거절된다 */
	struct drm_mode_card_res r = { 0 };
	if (ioctl(fd, DRM_IOCTL_MODE_GETRESOURCES, &r)) printf("  GETRESOURCES -> %s\n", strerror(errno));
	else printf("  GETRESOURCES -> ok (crtcs=%u connectors=%u)\n", r.count_crtcs, r.count_connectors);
	struct drm_mode_create_dumb c = { .width = 64, .height = 64, .bpp = 32 };
	if (ioctl(fd, DRM_IOCTL_MODE_CREATE_DUMB, &c)) printf("  CREATE_DUMB  -> %s\n", strerror(errno));
	else printf("  CREATE_DUMB  -> handle=%u pitch=%u size=%llu\n", c.handle, c.pitch,
		    (unsigned long long)c.size);
	return 0;
}
```

출력에서 볼 것:

- **vkms**(Virtual Kernel Mode Setting)는 하드웨어 없는 순수 소프트웨어 KMS 드라이버다. CRTC의 vblank는 hrtimer로 흉내 내고, plane 합성은 CPU로 한다. 그래서 테스트(IGT)와 CI에서 쓰이고, 이 노트에서는 "화면 없는 보드"처럼 쓴다.
- `PRIME = 3`은 import(1)와 export(2) 둘 다 된다는 비트마스크다. `SYNCOBJ = 0`은 vkms가 GPU가 아니라서 syncobj(명령 제출용 동기화 객체)가 없다는 뜻이다(§9의 virtio-gpu는 1).
- `GETRESOURCES`가 connector 1개라고 하는데 vkms에는 writeback connector가 하나 더 있다. 클라이언트가 `DRM_CLIENT_CAP_WRITEBACK_CONNECTORS`를 켜야 보인다(§3.3에서 확인). 모르는 클라이언트(옛 X 서버)가 writeback을 진짜 모니터로 착각하지 않게 숨기는 것이다.
- 64×64 dumb buffer의 `pitch`는 256바이트(64 × 4)이고 `size`는 16 KiB다. pitch(stride)는 드라이버가 정렬 요구에 맞춰 늘릴 수 있으므로 **항상 커널이 돌려준 값**을 써야 한다.

### 2.3 커널 쪽 — `DRIVER_*` 기능 플래그

노드가 무엇이 생기는지는 드라이버의 `drm_driver.driver_features`가 정한다. 랩 소스(6.18.55)에서 직접 확인한 값이다.

| 드라이버 | `driver_features` | 생기는 노드 |
|---|---|---|
| vkms (`vkms_drv.c`) | `DRIVER_MODESET` `DRIVER_ATOMIC` `DRIVER_GEM` | `card` (render 없음) |
| virtio-gpu (`virtgpu_drv.c`) | `DRIVER_MODESET` `DRIVER_GEM` `DRIVER_RENDER` `DRIVER_ATOMIC` … | `card` + `renderD` |
| panthor (Mali CSF GPU) | `DRIVER_RENDER` `DRIVER_GEM` `DRIVER_SYNCOBJ` … | `card` + `renderD` (KMS 없음) |
| etnaviv (Vivante GPU/NPU) | `DRIVER_GEM` `DRIVER_RENDER` | `card` + `renderD` (KMS 없음) |
| rocket (Rockchip NPU) | `DRIVER_COMPUTE_ACCEL` `DRIVER_GEM` | `accel` 하나만 |

`DRIVER_MODESET`이 없으면 KMS ioctl은 `EOPNOTSUPP`를 돌려주고, `DRIVER_RENDER`가 없으면 render 노드가 안 생긴다. `DRIVER_COMPUTE_ACCEL`이면 `card`/`renderD` 대신 accel 노드 하나가 생긴다(§11).

그림 2 — KMS 객체 파이프라인. framebuffer(메모리 + 포맷)는 plane에 붙고, CRTC가 자기 plane들을 합성해 모드 타이밍대로 내보낸다. encoder가 그 픽셀 스트림을 링크 신호로 바꾸고, bridge 체인을 거쳐 connector(물리 출력)와 패널에 닿는다.

### 3.2 정의 — 객체 다섯(+둘)

| 객체 | 무엇을 모델링하나 | 펌웨어 비유 | 핵심 속성 |
|---|---|---|---|
| framebuffer (`drm_framebuffer`) | GEM 버퍼 1~4개 + 픽셀 포맷 + pitch + modifier | "이 주소부터 이 stride로 XRGB8888" | `ADDFB2`로 만들고 id로 참조 |
| plane (`drm_plane`) | 스캔아웃 레이어 하나: fb의 소스 사각형을 화면의 목적 사각형으로 | LCDC의 layer/window 레지스터 묶음 | `FB_ID` `CRTC_ID` `SRC_*` `CRTC_*` `zpos` `alpha` `rotation` |
| CRTC (`drm_crtc`) | plane 합성 + 타이밍 생성기(스캔아웃 엔진) | 타이밍 컨트롤러 + 블렌더 | `ACTIVE` `MODE_ID` `GAMMA_LUT` `OUT_FENCE_PTR` |
| encoder (`drm_encoder`) | 픽셀 스트림을 링크 신호로 (TMDS, DSI, LVDS) | 출력 PHY/serializer 블록 | 유저에게는 거의 숨겨짐 |
| connector (`drm_connector`) | 물리 출력 포트 + 연결 상태 + 모드 목록 | HPD 핀, DDC(EDID) | `CRTC_ID` `DPMS` `EDID` `link-status` |
| bridge (`drm_bridge`) | encoder 뒤 외부 칩·블록 (DSI→HDMI 등) | 보드의 변환 칩 드라이버 | 커널 내부만, 유저 객체 아님 |
| panel (`drm_panel`) | 고정 패널: 전원 시퀀스, 모드 1개, 백라이트 | 패널 init 시퀀스 코드 | 커널 내부만 |

- "CRTC"라는 이름은 CRT Controller에서 왔다. 브라운관은 없어졌지만 "스캔아웃 타이밍을 만드는 블록"이라는 뜻은 그대로다.
- 관계는 **비트마스크**로 표현한다. plane의 `possible_crtcs`, encoder의 `possible_crtcs`는 "몇 번째 CRTC에 붙을 수 있나"의 비트마스크다(CRTC id가 아니라 **인덱스**다).
- 한 CRTC는 여러 connector를 동시에 구동할 수 있다(clone 모드). 한 connector는 한 순간에 한 CRTC에만 붙는다.
- bridge·panel은 유저 공간 객체가 아니다. 유저는 connector까지만 보고, 커널 안에서 encoder 뒤에 bridge 체인이 붙는다. 임베디드 보드에서 화면 bring-up 문제의 대부분이 이 체인(DSI 레인 수, 패널 전원 시퀀스, 클럭)에서 나온다(§12.3).

### 3.3 예제 2 — mini-modetest: CRTC · encoder · connector · mode 나열

무엇을 확인하나: `GETRESOURCES` → `GETCRTC`/`GETENCODER`/`GETCONNECTOR`로 객체 그래프를 그대로 따라가 본다. atomic·writeback cap을 켜서 숨은 writeback connector도 본다.

```c
/* i8_enum.c [node] [nmodes] — mini-modetest: CRTC · encoder · connector · mode 나열 */
#include "i8_drm.h"
static const char *ctype(uint32_t t)
{
	switch (t) { case DRM_MODE_CONNECTOR_VIRTUAL: return "Virtual";
	case DRM_MODE_CONNECTOR_WRITEBACK: return "Writeback"; case DRM_MODE_CONNECTOR_HDMIA: return "HDMI-A";
	case DRM_MODE_CONNECTOR_DSI: return "DSI"; case DRM_MODE_CONNECTOR_eDP: return "eDP"; }
	return "other";
}
int main(int argc, char **argv)
{
	int fd = dopen(argc > 1 ? argv[1] : "/dev/dri/card0"), nm = argc > 2 ? atoi(argv[2]) : 4;
	uint32_t conns[8], crtcs[8], encs[8];
	cap(fd, DRM_CLIENT_CAP_ATOMIC, 1);			/* writeback connector를 보려면 */
	cap(fd, DRM_CLIENT_CAP_WRITEBACK_CONNECTORS, 1);
	struct drm_mode_card_res r = { .connector_id_ptr = P(conns), .crtc_id_ptr = P(crtcs),
		.encoder_id_ptr = P(encs), .count_connectors = 8, .count_crtcs = 8, .count_encoders = 8 };
	if (xioctl(fd, DRM_IOCTL_MODE_GETRESOURCES, &r)) die("GETRESOURCES");
	printf("fb size range %ux%u .. %ux%u\n", r.min_width, r.min_height, r.max_width, r.max_height);
	for (uint32_t i = 0; i < r.count_crtcs; i++) {
		struct drm_mode_crtc c = { .crtc_id = crtcs[i] };
		if (xioctl(fd, DRM_IOCTL_MODE_GETCRTC, &c)) die("GETCRTC");
		printf("CRTC %u: fb=%u mode_valid=%u %s gamma_size=%u\n", c.crtc_id, c.fb_id,
		       c.mode_valid, c.mode_valid ? c.mode.name : "-", c.gamma_size);
	}
	for (uint32_t i = 0; i < r.count_encoders; i++) {
		struct drm_mode_get_encoder e = { .encoder_id = encs[i] };
		if (xioctl(fd, DRM_IOCTL_MODE_GETENCODER, &e)) die("GETENCODER");
		printf("encoder %u: type=%u crtc=%u possible_crtcs=0x%x\n", e.encoder_id,
		       e.encoder_type, e.crtc_id, e.possible_crtcs);
	}
	for (uint32_t i = 0; i < r.count_connectors; i++) {
		struct drm_mode_modeinfo m[64]; uint32_t ce[4];
		struct drm_mode_get_connector c = { .connector_id = conns[i] };
		if (xioctl(fd, DRM_IOCTL_MODE_GETCONNECTOR, &c)) die("GETCONNECTOR");
		if (c.count_modes > 64) c.count_modes = 64;
		if (c.count_encoders > 4) c.count_encoders = 4;
		c.modes_ptr = P(m); c.encoders_ptr = P(ce); c.count_props = 0;
		if (xioctl(fd, DRM_IOCTL_MODE_GETCONNECTOR, &c)) die("GETCONNECTOR");
		printf("connector %u: %s-%u %s encoders=%u(first %u) modes=%u\n", c.connector_id,
		       ctype(c.connector_type), c.connector_type_id,
		       c.connection == 1 ? "connected" : "disconnected", c.count_encoders,
		       c.count_encoders ? ce[0] : 0, c.count_modes);
		for (uint32_t k = 0; k < c.count_modes && (int)k < nm; k++)
			printf("  [%2u] %-10s %2uHz clk=%6ukHz h %u %u %u %u  v %u %u %u %u%s\n", k, m[k].name,
			       m[k].vrefresh, m[k].clock, m[k].hdisplay, m[k].hsync_start, m[k].hsync_end,
			       m[k].htotal, m[k].vdisplay, m[k].vsync_start, m[k].vsync_end, m[k].vtotal,
			       m[k].type & DRM_MODE_TYPE_PREFERRED ? " preferred" : "");
	}
	return 0;
}
```

### 3.4 예제 3 — plane: 종류, 포맷, possible_crtcs

무엇을 확인하나: `DRM_CLIENT_CAP_UNIVERSAL_PLANES`를 켜면 primary·cursor도 plane으로 보이고, 각 plane이 받는 픽셀 포맷과 붙을 수 있는 CRTC를 알 수 있다. vkms는 `enable_overlay=1` 모듈 인자로 overlay plane을 만든다.

```c
/* i8_planes.c — universal planes: 종류(type), 포맷, possible_crtcs, zpos */
#include "i8_drm.h"
static const char *fourcc(uint32_t f, char *s)
{ for (int i = 0; i < 4; i++) s[i] = (f >> (8 * i)) & 0xff; s[4] = 0; return s; }
static int has_prop(int fd, uint32_t obj, const char *name, uint64_t *v)
{
	uint32_t ids[64]; uint64_t vals[64];
	struct drm_mode_obj_get_properties op = { .obj_id = obj, .obj_type = DRM_MODE_OBJECT_PLANE,
		.count_props = 64, .props_ptr = P(ids), .prop_values_ptr = P(vals) };
	if (xioctl(fd, DRM_IOCTL_MODE_OBJ_GETPROPERTIES, &op)) die("OBJ_GETPROPERTIES");
	for (uint32_t i = 0; i < op.count_props && i < 64; i++) {
		struct drm_mode_get_property gp = { .prop_id = ids[i] };
		if (xioctl(fd, DRM_IOCTL_MODE_GETPROPERTY, &gp)) die("GETPROPERTY");
		if (!strcmp(gp.name, name)) { *v = vals[i]; return 1; }
	}
	return 0;
}
int main(int argc, char **argv)
{
	static const char *tn[] = { "overlay", "primary", "cursor" };
	int fd = dopen(argc > 1 ? argv[1] : "/dev/dri/card0");
	uint32_t ids[16], fmts[64]; char s[5];
	cap(fd, DRM_CLIENT_CAP_UNIVERSAL_PLANES, 1);	/* primary/cursor도 plane으로 보이게 */
	struct drm_mode_get_plane_res pr = { .plane_id_ptr = P(ids), .count_planes = 16 };
	if (xioctl(fd, DRM_IOCTL_MODE_GETPLANERESOURCES, &pr)) die("GETPLANERESOURCES");
	printf("%u planes\n", pr.count_planes);
	for (uint32_t i = 0; i < pr.count_planes; i++) {
		struct drm_mode_get_plane p = { .plane_id = ids[i], .format_type_ptr = P(fmts),
			.count_format_types = 64 };
		uint64_t type = 9, zpos = 0;
		if (xioctl(fd, DRM_IOCTL_MODE_GETPLANE, &p)) die("GETPLANE");
		has_prop(fd, ids[i], "type", &type);
		int hz = has_prop(fd, ids[i], "zpos", &zpos);
		printf("plane %u: %-7s possible_crtcs=0x%x fb=%u formats=%u [", ids[i],
		       type < 3 ? tn[type] : "?", p.possible_crtcs, p.fb_id, p.count_format_types);
		for (uint32_t k = 0; k < p.count_format_types && k < 64; k++)
			if (k < 6 || k == p.count_format_types - 1)
				printf("%s%s", k ? " " : "", fourcc(fmts[k], s));
			else if (k == 6) printf(" ...");
		printf("]");
		if (hz) printf(" zpos=%llu", (unsigned long long)zpos);
		printf("\n");
	}
	return 0;
}
```

```text
plane 38: overlay possible_crtcs=0x1 fb=0 formats=33 [AR24 AB24 BA24 RA24 XR24 XB24 ... R8  ]

```

출력에서 볼 것:

- primary 1개, overlay 8개(`NUM_OVERLAY_PLANES`), cursor 1개. primary만 fb 92(fbcon 화면)를 물고 있다.
- 포맷은 fourcc 코드다. `XR24` = `DRM_FORMAT_XRGB8888`(32비트, 상위 8비트 무시), `AR24` = ARGB8888(알파 있음). vkms 소스의 `vkms_formats[]`에는 RGB565, NV12·YUV420 같은 YUV 포맷도 있어서 총 33개다. 실제 SoC에서는 **plane마다 포맷이 다르다**(예: overlay만 NV12 지원 → 카메라 프레임을 GPU 변환 없이 바로 overlay로). 그래서 포맷 목록 확인은 파이프라인 설계의 첫 단계다.
- 마지막 포맷 `R8`은 fourcc가 `'R','8',' ',' '`라 공백 두 칸이 찍혔다.
- vkms 6.18 plane에는 `zpos` 속성이 없어 출력되지 않았다. zpos가 없으면 순서는 고정(primary < overlay < cursor)이다. 하드웨어 overlay가 있는 드라이버는 보통 `zpos`(범위 또는 immutable)를 노출한다.

### 3.5 흔한 함정

- `possible_crtcs`를 CRTC **id**로 해석하는 것: 비트 n은 `GETRESOURCES`가 돌려준 CRTC 배열의 n번째다.
- UNIVERSAL_PLANES cap 없이 `GETPLANERESOURCES`를 부르면 overlay만 보인다. atomic cap을 켜면 universal planes도 자동으로 켜진다.
- "plane이 8개니 8레이어를 다 쓸 수 있다"고 가정하는 것: 실제 하드웨어는 대역폭·스케일러 수·라인 버퍼 때문에 조합 제약이 있다. 그래서 atomic의 **TEST_ONLY**로 "이 조합 되나?"를 물어본다(§7).

## 4. 모드와 타이밍 — modeline 읽기

### 4.1 직관 — 한 줄은 보이는 픽셀보다 길다

디스플레이 링크는 한 줄의 보이는 픽셀(active)을 보낸 뒤 **front porch → sync 펄스 → back porch**의 빈 구간을 보내고 다음 줄로 간다. 세로 방향도 같다. 이 빈 구간이 원래는 브라운관 전자빔이 되돌아갈 시간이었고, 지금은 수신 칩이 동기를 잡고 패널이 준비하는 시간이다. **세로 빈 구간이 vblank**이고, 이 동안 프레임 버퍼 주소를 바꾸면 찢어짐(tearing) 없이 다음 프레임이 바뀐다.

### 4.2 정의 — `struct drm_mode_modeinfo`

| 필드 | 뜻 | 640x480@60 |
|---|---|---|
| `clock` | 픽셀 클럭 (kHz) | 25175 |
| `hdisplay` `hsync_start` `hsync_end` `htotal` | 가로: 보이는 끝, sync 시작, sync 끝, 줄 전체 | 640 656 752 800 |
| `vdisplay` `vsync_start` `vsync_end` `vtotal` | 세로: 같은 의미, 단위는 줄 | 480 490 492 525 |
| `vrefresh` | 표시용 정수 Hz (계산값을 반올림) | 60 |
| `flags` | sync 극성(`PHSYNC`/`NHSYNC`…), interlace 등 | |
| `type` | `PREFERRED`, `DRIVER`, `USERDEF` 비트 | |

front porch = `hsync_start - hdisplay`, sync 폭 = `hsync_end - hsync_start`, back porch = `htotal - hsync_end`. 패널 데이터시트는 보통 이 세 값을 직접 주므로 변환해서 넣는다(DT의 `panel-timing` 노드도 front/back porch·sync 길이로 적는다).

### 4.3 예제 4 — sysfs의 connector와 EDID

무엇을 확인하나: `/sys/class/drm/cardN-<connector>/`에서 연결 상태·모드·EDID를 읽는다. virtio-gpu(card0)는 QEMU가 만든 EDID를 주고, vkms(card1)는 EDID가 없다. 스크립트(게스트, `DEV="-device virtio-gpu-pci"`):

```sh
#!/bin/sh
modprobe virtio-gpu; modprobe vkms
cd /sys/class/drm
for c in card0-Virtual-1 card1-Virtual-2 card1-Writeback-1; do
  echo "== $c: status=$(cat $c/status) enabled=$(cat $c/enabled) dpms=$(cat $c/dpms) edid=$(wc -c < $c/edid)B"
  head -3 $c/modes
done
echo "== EDID of virtio-gpu (first 32 bytes)"; hexdump -C card0-Virtual-1/edid | head -2
```

출력에서 볼 것:

- EDID는 모니터가 DDC(I2C 버스, 주소 0x50)로 내보내는 128바이트 블록(+확장 블록)이다. 첫 8바이트 `00 ff ff ff ff ff ff 00`이 고정 헤더, `49 14`가 제조사 ID(5비트씩 세 글자: `RHT` = Red Hat, QEMU가 만든 값), `34 12`가 제품 코드 0x1234, `01 04`가 EDID 버전 1.4다. 256바이트 = 기본 블록 + 확장 블록 1개.
- virtio-gpu는 EDID의 preferred 모드(1280x800)를 첫 모드로 보고한다. 실제 HDMI 모니터도 같다: 커널이 DDC로 EDID를 읽어(`drm_get_edid()`/`drm_edid_read()`) 모드 목록을 만든다. **임베디드 고정 패널은 EDID가 없어서** 모드가 DT(`panel-timing`)나 패널 드라이버 코드(panel-simple의 표)에서 온다.
- card1(vkms)의 Virtual-2는 `enabled=disabled`다. fbcon은 첫 번째 fb(card0의 virtio-gpu)에만 붙었고, vkms의 CRTC는 꺼져 있다. 이 사실이 §10에서 중요해진다.
- `status`에 `detect`를 쓰면 다시 감지하고, `on`/`off`로 강제할 수도 있다(디버깅용, 실행하지 않음). 실제 HDMI에서는 HPD 인터럽트 → `drm_helper_hpd_irq_event()` → uevent(`HOTPLUG=1`)로 유저 공간(컴포지터)이 다시 모드를 읽는다.

### 4.4 흔한 함정

- 데이터시트의 "front porch/back porch"를 `hsync_start`/`hsync_end`에 그대로 넣는 것: 이 필드들은 **누적 위치**다. 증상은 화면이 옆으로 밀리거나 패널이 동기를 못 잡는 것.
- `vrefresh`를 바꾸면 refresh가 바뀐다고 생각하는 것: 실제 주기는 `clock`·`htotal`·`vtotal`로 정해진다. §6에서 픽셀 클럭만 바꿔 refresh를 바꾼다.
- 패널이 요구하는 픽셀 클럭을 SoC의 PLL이 정확히 못 만드는 것: 클럭 드라이버가 가장 가까운 값을 주면 refresh가 조금 어긋나고, 일부 패널은 범위를 벗어나면 깜빡인다. `clk_summary`(H3)로 실제 클럭을 확인한다.

## 5. dumb buffer와 legacy modeset — 화면에 첫 픽셀 올리기

### 5.1 직관 — "CPU가 그리는 버퍼"

GPU 없이 CPU가 직접 그린 버퍼를 화면에 거는 가장 단순한 길이 **dumb buffer**다. 드라이버 종류와 무관한 공통 ioctl 세 개로 끝난다.

1. `DRM_IOCTL_MODE_CREATE_DUMB` — 너비·높이·bpp를 주면 커널이 스캔아웃 가능한 버퍼를 할당하고 **GEM handle**, `pitch`, `size`를 돌려준다.
2. `DRM_IOCTL_MODE_MAP_DUMB` — 그 handle을 mmap할 수 있는 "가짜 오프셋"을 받는다. 이 오프셋으로 DRM fd를 `mmap()`한다(G5에서 본 `vm_pgoff`로 객체를 고르는 패턴).
3. `DRM_IOCTL_MODE_ADDFB2` — handle + 포맷 + pitch로 **framebuffer 객체**를 만든다. KMS는 GEM handle이 아니라 fb id를 받는다.

dumb buffer는 이름 그대로 "멍청한" 버퍼다. **GPU 가속에 쓰면 안 되고**(드라이버가 렌더링 가능한 메모리로 잡는다는 보장이 없다), 스플래시 화면, 부트 로고, 최소 UI, 테스트에 쓴다. Don이 펌웨어에서 프레임 버퍼에 직접 픽셀을 쓰던 것과 같다.

그다음 legacy API `DRM_IOCTL_MODE_SETCRTC` 한 번이 "이 CRTC에 이 fb를 이 모드로, 이 connector들로 내보내라"를 한다. KMS 초창기(2008년 무렵)부터 있던 API다.

### 5.2 예제 5 — 색 막대를 그려 SETCRTC로 걸고, 커널의 상태를 덤프

무엇을 확인하나: dumb → mmap → 그리기 → ADDFB2 → SETCRTC 순서, 그리고 debugfs `state`가 보여 주는 커널 쪽 atomic 상태(누가 fb를 할당했나, 어떤 GEM 객체인가).

```c
/* i8_modeset.c — legacy KMS: dumb buffer에 색 막대를 그리고 SETCRTC로 화면에 건다 */
#include "i8_drm.h"
int main(void)
{
	int fd = dopen("/dev/dri/card0");
	uint32_t conn, crtc; struct drm_mode_modeinfo mode; struct dumb d;
	first_output(fd, &conn, &crtc, &mode);
	printf("connector %u -> crtc %u, mode %s %uHz\n", conn, crtc, mode.name, mode.vrefresh);
	dumb_create(fd, &d, mode.hdisplay, mode.vdisplay, DRM_FORMAT_XRGB8888);
	printf("dumb: handle=%u pitch=%u size=%llu -> fb %u, mapped at %p\n", d.handle, d.pitch,
	       (unsigned long long)d.size, d.fb, (void *)d.px);
	static const uint32_t bars[] = { 0xffffff, 0xffff00, 0x00ffff, 0x00ff00,
					 0xff00ff, 0xff0000, 0x0000ff, 0x000000 };
	for (uint32_t y = 0; y < d.h; y++)		/* pitch는 바이트 단위 — /4 해서 픽셀 */
		for (uint32_t x = 0; x < d.w; x++)
			d.px[y * (d.pitch / 4) + x] = bars[x * 8 / d.w];
	struct drm_mode_crtc sc = { .crtc_id = crtc, .fb_id = d.fb, .set_connectors_ptr = P(&conn),
		.count_connectors = 1, .mode = mode, .mode_valid = 1 };
	if (xioctl(fd, DRM_IOCTL_MODE_SETCRTC, &sc)) die("SETCRTC");
	struct drm_mode_crtc gc = { .crtc_id = crtc };
	if (xioctl(fd, DRM_IOCTL_MODE_GETCRTC, &gc)) die("GETCRTC");
	printf("after SETCRTC: crtc %u fb=%u mode=%s\n", gc.crtc_id, gc.fb_id, gc.mode.name);
	fflush(stdout);
	if (system("cat /sys/kernel/debug/dri/0/state")) {}	/* 커널이 보는 atomic state */
	return 0;	/* close 시 이 파일이 만든 fb가 지워지고 fbdev가 다시 화면을 가져간다 */
}
```

게스트 스크립트는 `modprobe vkms` → `cat /sys/kernel/debug/dri/0/state`(before) → `/i8_modeset` 순서다. 출력이 길어서 overlay plane 부분과 connector의 반복 줄을 `...`로 줄였다.

### 5.3 debugfs와 sysfs — 디스플레이 디버깅의 첫 화면

| 경로 | 무엇 |
|---|---|
| `/sys/kernel/debug/dri/N/state` | 현재 atomic 상태 전체: plane별 fb·좌표·포맷, CRTC 모드·활성, connector 연결 |
| `/sys/kernel/debug/dri/N/framebuffer` | 살아 있는 fb 목록과 할당한 프로세스 |
| `/sys/kernel/debug/dri/N/clients` | 이 장치를 연 프로세스, master 여부, uid |
| `/sys/kernel/debug/dri/N/crtc-0/crc/` | CRTC 출력 CRC (§8.3) |
| `/sys/class/drm/cardN-<conn>/{status,modes,edid,enabled,dpms}` | connector 상태 (§4.3) |
| `/sys/module/drm/parameters/debug` | `drm.debug` 비트마스크 (0x04 KMS, 0x10 ATOMIC, …) — §7.3에서 사용 |

이 목록은 이 랩에서 실제로 `ls /sys/kernel/debug/dri/1`로 확인한 파일들이다(vkms의 경우 `Virtual-2`, `Writeback-1`, `clients`, `crtc-0`, `encoder-0`, `encoder-1`, `framebuffer`, `gem_names`, `internal_clients`, `name`, `state`, `vkms_config`).

### 5.4 fbdev 에뮬레이션 — `/dev/fb0`는 DRM의 클라이언트다

옛 Linux 그래픽은 **fbdev**(`/dev/fb0`, `struct fb_info`)였다. 지금은 DRM 드라이버가 fbdev 드라이버를 따로 두지 않고, DRM core의 **in-kernel client**(`drm_fbdev_*` 헬퍼, `CONFIG_DRM_FBDEV_EMULATION=y`)가 dumb buffer 하나를 잡아 `/dev/fb0`처럼 보이게 한다. 콘솔(fbcon)이 그 위에서 글자를 그린다. 위 덤프의 `allocated by = [fbcon]`이 그것이다.

- 유저 공간 KMS 클라이언트(Weston, 이 노트의 프로그램)가 **DRM master**가 되어 화면을 가져가면 fbdev는 물러난다.
- master가 fd를 닫으면 DRM core가 fbdev에 화면을 돌려준다(`drm_client_dev_restore()` — §7.3의 로그 끝에 `fbdev: ret=0`으로 찍힌다). 그래서 위 예제 주석처럼 프로그램이 끝나면 콘솔 화면이 다시 보인다.
- `cat /proc/fb`로 어떤 DRM 드라이버의 fbdev인지 볼 수 있다(§9.1 출력의 `0 virtio_gpudrmfb`, `1 vkmsdrmfb`).
- 임베디드 제품에서는 부팅 로고를 위해 fbdev를 켜 두거나, 반대로 부팅 시간을 줄이려 `CONFIG_DRM_FBDEV_EMULATION`을 끄고 첫 화면을 앱이 바로 그리기도 한다.

### 5.5 흔한 함정

- `pitch`를 `width × 4`로 가정: 정렬 요구가 있는 하드웨어(예: 64바이트 정렬)에서는 커널이 더 큰 pitch를 준다. 증상은 화면이 대각선으로 기울어 찢어지는 모양.
- DRM master 문제: 다른 프로세스(Weston 등)가 master이면 `SETCRTC`가 `EACCES`(권한 거부)를 돌려준다. 콘솔에서 테스트하려면 컴포지터를 멈추거나 그 안에서 클라이언트로 그린다.
- dumb buffer를 GPU 렌더 타깃으로 쓰는 것: 드라이버에 따라 캐시 속성·타일링이 맞지 않아 느리거나 깨진다. GPU 렌더링은 GBM(`gbm_bo_create`)으로 드라이버 전용 버퍼를 잡는다.

## 6. page flip과 vblank — 측정

### 6.1 직관 — 더블 버퍼링과 vblank 이벤트

화면에 걸린 버퍼(front)에 그리면 스캔아웃 중인 줄과 그리는 줄이 섞여 찢어진다. 그래서 버퍼 두 개를 두고 뒤(back)에 그린 뒤 **vblank 동안** 주소를 바꾼다. 이것이 page flip이다. 펌웨어에서 VSYNC ISR 안에서 레이어 주소 레지스터를 바꾸던 것과 같다.

- `DRM_IOCTL_MODE_PAGE_FLIP`에 `DRM_MODE_PAGE_FLIP_EVENT`를 주면 ioctl은 **바로 반환**하고, 실제로 바뀐 vblank에 DRM fd로 `DRM_EVENT_FLIP_COMPLETE` 이벤트가 온다. fd를 `poll()`하고 `read()`로 `struct drm_event_vblank`(타임스탬프, vblank 시퀀스 번호, CRTC id, user_data)를 읽는다. 이벤트 큐 + fd = epoll로 기다릴 수 있는 "인터럽트"다(A 모듈의 fd 모델과 같은 사고방식).
- 앞선 flip이 아직 안 끝났는데 또 flip하면 `EBUSY`다. 그래서 정상 루프는 "flip → 이벤트 기다림 → 다음 프레임 그리기 → flip"이다.
- vkms의 vblank는 진짜 하드웨어 대신 **hrtimer**가 프레임 주기마다 `drm_crtc_handle_vblank()`를 불러 만든다(6.18에서는 `drm_vblank_helper`의 vblank timer를 쓴다 — 랩 소스 `vkms_crtc.c`). 주기는 모드의 `htotal × vtotal / clock`이다.

### 6.2 예제 6 — flip 루프로 vblank 간격과 fps 측정

무엇을 확인하나: 이벤트 타임스탬프 간격이 모드 타이밍 계산과 맞는지, 그리고 **픽셀 클럭만 바꾼 사용자 모드**(같은 640x480 타이밍)로 refresh가 바뀌는지. 세 번째 인자를 주면 `clock = htotal × vtotal × Hz / 1000`으로 바꾼다.

```c
/* i8_flip.c <mode_idx> <frames> [Hz] — PAGE_FLIP + 이벤트로 vblank 간격(fps) 측정 */
#include "i8_drm.h"
#include <poll.h>
int main(int argc, char **argv)
{
	int fd = dopen("/dev/dri/card0"), idx = argc > 1 ? atoi(argv[1]) : -1;
	int n = argc > 2 ? atoi(argv[2]) : 120, cur = 0;
	uint32_t conn, crtc; struct drm_mode_modeinfo mode, m[64]; struct dumb d[2];
	first_output(fd, &conn, &crtc, &mode);
	struct drm_mode_get_connector c = { .connector_id = conn, .count_modes = 64, .modes_ptr = P(m) };
	if (xioctl(fd, DRM_IOCTL_MODE_GETCONNECTOR, &c)) die("GETCONNECTOR");
	if (idx >= 0 && idx < (int)c.count_modes) mode = m[idx];
	if (argc > 3) {		/* 같은 타이밍, pixel clock만 바꿔 refresh를 바꾼 사용자 모드 */
		mode.vrefresh = atoi(argv[3]);
		mode.clock = (uint32_t)((uint64_t)mode.htotal * mode.vtotal * mode.vrefresh / 1000);
		mode.type = DRM_MODE_TYPE_USERDEF;
	}
	for (int i = 0; i < 2; i++) {
		dumb_create(fd, &d[i], mode.hdisplay, mode.vdisplay, DRM_FORMAT_XRGB8888);
		memset(d[i].px, i ? 0x40 : 0xc0, d[i].size);
	}
	struct drm_mode_crtc sc = { .crtc_id = crtc, .fb_id = d[0].fb, .set_connectors_ptr = P(&conn),
		.count_connectors = 1, .mode = mode, .mode_valid = 1 };
	if (xioctl(fd, DRM_IOCTL_MODE_SETCRTC, &sc)) die("SETCRTC");
	double prev = 0, sum = 0, mn = 1e9, mx = 0; unsigned pseq = 0, miss = 0;
	for (int f = 0; f <= n; f++) {
		cur ^= 1;
		struct drm_mode_crtc_page_flip pf = { .crtc_id = crtc, .fb_id = d[cur].fb,
			.flags = DRM_MODE_PAGE_FLIP_EVENT, .user_data = (uint64_t)f };
		if (xioctl(fd, DRM_IOCTL_MODE_PAGE_FLIP, &pf)) die("PAGE_FLIP");
		struct pollfd p = { .fd = fd, .events = POLLIN };
		if (poll(&p, 1, 1000) != 1) { fprintf(stderr, "timeout\n"); return 1; }
		char buf[256]; ssize_t len = read(fd, buf, sizeof(buf));	/* struct drm_event 스트림 */
		struct drm_event_vblank *ev = (void *)buf;
		if (len < (ssize_t)sizeof(*ev) || ev->base.type != DRM_EVENT_FLIP_COMPLETE) die("event");
		double t = ev->tv_sec * 1e3 + ev->tv_usec / 1e3;
		if (f > 0) {
			double dt = t - prev; sum += dt; mn = dt < mn ? dt : mn; mx = dt > mx ? dt : mx;
			miss += ev->sequence - pseq - 1;
		}
		if (f < 3) printf("event: user_data=%llu seq=%u crtc=%u t=%.3f ms\n",
				  (unsigned long long)ev->user_data, ev->sequence, ev->crtc_id, t);
		prev = t; pseq = ev->sequence;
	}
	printf("mode %s@%u (clock %u kHz, htotal %u, vtotal %u) ideal %.3f ms\n", mode.name,
	       mode.vrefresh, mode.clock, mode.htotal, mode.vtotal,
	       1e3 * mode.htotal * mode.vtotal / (mode.clock * 1e3));
	printf("%d flips: mean %.3f ms (%.2f fps) min %.3f max %.3f skipped_vblanks %u\n",
	       n, sum / n, 1e3 / (sum / n), mn, mx, miss);
	return 0;
}
```

그림 4 — vkms page flip 측정. 회색은 모드가 약속한 refresh(Hz), 파랑은 240번 flip의 평균 이벤트 간격으로 계산한 fps, 아래 `skip`은 이벤트 시퀀스 번호가 2 이상 뛴(=한 vblank를 놓친) 횟수다. 30·75·120 Hz는 정확히 맞았고, 60·144·240 Hz에서 1~4번 놓친 프레임이 평균을 조금 끌어내렸다.

출력에서 볼 것:

- 첫 세 이벤트의 간격은 정확히 16.683 ms(= 800 × 525 / 25.175 MHz)이고 시퀀스가 8, 9, 10으로 1씩 오른다. **이벤트 타임스탬프는 "flip이 실제로 일어난 vblank의 시각"** 이지, 프로세스가 깨어난 시각이 아니다. 그래서 최솟값이 이론값과 마이크로초 단위까지 같다.
- `max`가 33.3 ms(= 2프레임)인 줄은 그 회차에 프로그램이 다음 flip을 vblank 전에 못 넣어서 한 프레임을 놓친 것이다. TCG 에뮬레이션에서 프로세스 스케줄이 늦어진 탓이다. `skipped_vblanks`가 정확히 그 횟수를 센다 — 실제 제품에서 "가끔 끊긴다"를 숫자로 잡는 방법이 이것이다.
- 144 Hz(프레임 6.9 ms)에서 가장 많이 놓쳤다(4번). 프레임 예산이 짧을수록 유저 공간 지연에 민감해진다. 실제 장비에서는 이 여유를 늘리려고 flip을 미리 큐잉하거나(atomic NONBLOCK, §7.4), 렌더 스레드에 RT 우선순위를 준다.
- refresh를 바꾼 방법은 **픽셀 클럭만 바꾸는 것**이었다. 실제 하드웨어에서는 그 클럭을 PLL이 만들 수 있어야 하고, 패널·링크가 그 속도를 받아야 한다. vkms는 hrtimer라 아무 값이나 된다.

### 6.3 흔한 함정

- 이벤트를 `read()`하지 않고 다음 flip을 내는 것: 앞 flip이 끝났어도 이벤트가 큐에 쌓이고, 끝나기 전이면 `EBUSY`다. 이벤트 버퍼에는 여러 이벤트가 이어 붙어 올 수 있으므로 `base.length`만큼씩 넘기며 파싱해야 한다(위 예제는 한 번에 하나만 기다리므로 단순화).
- `gettimeofday()`로 flip 시각을 재는 것: 깨어난 시각은 스케줄 지연이 섞인다. 이벤트의 `tv_sec/tv_usec`(CLOCK_MONOTONIC, `DRM_CAP_TIMESTAMP_MONOTONIC=1`)을 쓴다.
- vblank 카운터가 꺼져 있는데 기다리는 것: 드라이버는 전력 절약을 위해 아무도 기다리지 않으면 vblank 인터럽트를 끈다(`drm_vblank_get/put` 참조 카운트). 드라이버를 쓸 때 vblank 인터럽트 enable/disable 콜백이 틀리면 이벤트가 영영 안 오고 컴포지터가 멈춘다(`flip_done timed out` 경고).

## 7. atomic modesetting — "전부 검사한 뒤 한 번에"

### 7.1 직관 — 왜 legacy로는 부족했나

legacy API는 객체마다 ioctl이 따로였다: `SETCRTC`(모드+primary), `SETPLANE`(overlay 하나), `PAGE_FLIP`(primary만), `CURSOR`, 그리고 connector 속성은 `SETPROPERTY` 하나씩. 문제는 세 가지였다.

1. **중간 상태가 화면에 나온다**: overlay 위치와 primary 버퍼를 같은 프레임에 바꾸고 싶어도 ioctl 두 번 사이에 vblank가 끼면 한 프레임은 반만 바뀐 화면이 나온다.
2. **실패를 미리 알 수 없다**: "overlay 3개 + 스케일링 + NV12"가 하드웨어 대역폭 안에 드는지, 일단 해 보고 실패하면 이미 일부가 바뀐 뒤다.
3. **모든 것이 blocking**이거나 primary만 비동기였다.

atomic은 Don이 펌웨어에서 자주 쓰던 패턴 그대로다: **shadow 레지스터에 전부 써 두고, 검증한 뒤, "GO" 비트 하나로 다음 vblank에 한꺼번에 적용**. 유저는 (객체, 속성, 값) 목록 하나를 `DRM_IOCTL_MODE_ATOMIC`으로 보낸다. 커널은 현재 상태를 복제한 **새 상태**에 그 값들을 적용하고, 드라이버의 `atomic_check`로 새 상태 전체를 검증한 뒤, 통과하면 `atomic_commit`으로 하드웨어에 반영한다. 실패하면 아무것도 바뀌지 않는다.

### 7.2 속성(property) — atomic의 어휘

atomic에서는 **모든 것이 속성**이다. plane의 fb와 위치, CRTC의 모드와 on/off, connector가 붙을 CRTC까지. 속성은 id로 참조하고 이름은 이름으로 찾는다(이름은 ABI다).

예제 7 — 무엇을 확인하나: vkms의 primary plane, CRTC, connector, writeback connector에 실제로 어떤 속성이 있는지, 그 종류(range/enum/blob/object)와 현재 값.

```c
/* i8_props.c — 객체별 atomic 속성 이름·종류·현재 값 */
#include "i8_drm.h"
static void dump(int fd, uint32_t obj, uint32_t type, const char *what)
{
	uint32_t ids[64]; uint64_t vals[64];
	struct drm_mode_obj_get_properties op = { .obj_id = obj, .obj_type = type, .count_props = 64,
		.props_ptr = P(ids), .prop_values_ptr = P(vals) };
	if (xioctl(fd, DRM_IOCTL_MODE_OBJ_GETPROPERTIES, &op)) die("OBJ_GETPROPERTIES");
	printf("%s %u:", what, obj);
	for (uint32_t i = 0; i < op.count_props && i < 64; i++) {
		struct drm_mode_get_property gp = { .prop_id = ids[i] };
		if (xioctl(fd, DRM_IOCTL_MODE_GETPROPERTY, &gp)) die("GETPROPERTY");
		uint32_t t = gp.flags & (DRM_MODE_PROP_LEGACY_TYPE | DRM_MODE_PROP_EXTENDED_TYPE);
		const char *k = t == DRM_MODE_PROP_RANGE ? "range" : t == DRM_MODE_PROP_ENUM ? "enum" :
			t == DRM_MODE_PROP_BLOB ? "blob" : t == DRM_MODE_PROP_BITMASK ? "bitmask" :
			t == DRM_MODE_PROP_OBJECT ? "object" : t == DRM_MODE_PROP_SIGNED_RANGE ? "srange" : "?";
		printf("%s %s(%s%s)=%lld", i % 3 ? "" : "\n ", gp.name, k,
		       gp.flags & DRM_MODE_PROP_IMMUTABLE ? ",ro" : "", (long long)vals[i]);
	}
	printf("\n");
}
int main(void)
{
	int fd = dopen("/dev/dri/card0"); uint32_t conn, crtc; struct drm_mode_modeinfo m;
	cap(fd, DRM_CLIENT_CAP_ATOMIC, 1); cap(fd, DRM_CLIENT_CAP_WRITEBACK_CONNECTORS, 1);
	first_output(fd, &conn, &crtc, &m);
	dump(fd, find_plane(fd, 1, 0), DRM_MODE_OBJECT_PLANE, "PLANE(primary)");
	dump(fd, crtc, DRM_MODE_OBJECT_CRTC, "CRTC");
	dump(fd, conn, DRM_MODE_OBJECT_CONNECTOR, "CONNECTOR");
	dump(fd, find_wb(fd), DRM_MODE_OBJECT_CONNECTOR, "CONNECTOR(writeback)");
	return 0;
}
```

```text
  TILE(blob,ro)=0 CRTC_ID(object)=0 WRITEBACK_OUT_FENCE_PTR(range)=0
  WRITEBACK_FB_ID(object)=0 WRITEBACK_PIXEL_FORMATS(blob,ro)=49
```

출력에서 볼 것:

- `SRC_W=67108864`는 1024 << 16이다. **SRC 좌표는 16.16 고정소수점**(서브픽셀 소스 영역, 스케일링용)이고 `CRTC_*`는 정수 픽셀이다. `CRTC_X/Y`는 음수가 될 수 있어서(화면 왼쪽 밖으로 나간 plane) signed range다.
- `MODE_ID`는 **blob** 속성이다. 모드(`drm_mode_modeinfo` 68바이트)를 `CREATEPROPBLOB`로 커널에 올리고 그 blob id를 값으로 준다. `IN_FORMATS`(포맷 + modifier 목록), `GAMMA_LUT`도 blob이다.
- `FB_ID`, `CRTC_ID`는 **object** 속성(값 = 객체 id)이다. connector의 `CRTC_ID`로 "이 connector를 어느 CRTC에 붙이나"를, plane의 `CRTC_ID`로 "이 plane을 어느 CRTC에 올리나"를 정한다. 라우팅도 속성이다.
- `IN_FENCE_FD`(plane, -1 = 없음)와 `OUT_FENCE_PTR`(CRTC)은 **명시적 동기화(explicit fencing)** 용이다. GPU가 렌더링을 끝냈다는 fence를 in-fence로 주면 디스플레이가 그걸 기다렸다가 스캔아웃하고, out-fence는 "이 commit이 화면에 반영되었다"를 알려 준다(§7.4).
- `type`, `IN_FORMATS`, `GAMMA_LUT_SIZE`처럼 `ro`(immutable)인 속성은 정보 제공용이다.

### 7.3 예제 8 — TEST_ONLY, ALLOW_MODESET, 그리고 거절 이유 읽기

무엇을 확인하나: 1024x768로 켜져 있는 화면을 640x480으로 바꾸는 atomic 요청을 만들어 (1) 플래그 없이 TEST_ONLY, (2) ALLOW_MODESET과 TEST_ONLY, (3) 잘못된 SRC, (4) FB만 있고 CRTC 없는 plane을 검사해 본 뒤 (5) 진짜로 커밋한다. `drm.debug=0x10`(ATOMIC)으로 커널이 거절한 이유도 본다.

```c
/* i8_atomic.c — atomic modeset: TEST_ONLY, ALLOW_MODESET, 잘못된 상태 거절 */
#include "i8_drm.h"
static void report(const char *what, int r)
{ printf("%-44s -> %s\n", what, r ? strerror(errno) : "OK"); }
static void show(int fd, uint32_t crtc)
{
	struct drm_mode_crtc g = { .crtc_id = crtc };
	if (xioctl(fd, DRM_IOCTL_MODE_GETCRTC, &g)) die("GETCRTC");
	printf("   current CRTC %u: fb=%u mode=%s\n", crtc, g.fb_id, g.mode_valid ? g.mode.name : "-");
}
int main(void)
{
	int fd = dopen("/dev/dri/card0");
	uint32_t conn, crtc, C = DRM_MODE_OBJECT_CRTC; struct drm_mode_modeinfo mode, m[64];
	struct dumb d;
	cap(fd, DRM_CLIENT_CAP_ATOMIC, 1);
	first_output(fd, &conn, &crtc, &mode);
	struct drm_mode_get_connector gc = { .connector_id = conn, .count_modes = 64, .modes_ptr = P(m) };
	if (xioctl(fd, DRM_IOCTL_MODE_GETCONNECTOR, &gc)) die("GETCONNECTOR");
	mode = m[gc.count_modes - 1];				/* 640x480 — 지금(1024x768)과 다른 모드 */
	uint32_t pl = find_plane(fd, 1, 0);
	printf("connector %u, crtc %u, primary plane %u, target %s\n", conn, crtc, pl, mode.name);
	dumb_create(fd, &d, mode.hdisplay, mode.vdisplay, DRM_FORMAT_XRGB8888);
	memset(d.px, 0x80, d.size);
	struct areq a = { 0 };
	aadd(&a, conn, prop_id(fd, conn, DRM_MODE_OBJECT_CONNECTOR, "CRTC_ID", NULL), crtc);
	aadd(&a, crtc, prop_id(fd, crtc, C, "MODE_ID", NULL), mode_blob(fd, &mode));
	aadd(&a, crtc, prop_id(fd, crtc, C, "ACTIVE", NULL), 1);
	aplane(fd, &a, pl, crtc, &d, 0, 0);
	show(fd, crtc);
	report("TEST_ONLY (mode change, no ALLOW_MODESET)", acommit(fd, &a, DRM_MODE_ATOMIC_TEST_ONLY, NULL));
	report("TEST_ONLY | ALLOW_MODESET", acommit(fd, &a,
	       DRM_MODE_ATOMIC_TEST_ONLY | DRM_MODE_ATOMIC_ALLOW_MODESET, NULL));
	show(fd, crtc);						/* TEST_ONLY는 아무것도 바꾸지 않는다 */
	struct areq bad = a;					/* SRC가 fb보다 크면? */
	bad.val[7] = (uint64_t)(d.w + 1) << 16;			/* index 7 = SRC_W */
	report("TEST_ONLY, SRC_W > fb width", acommit(fd, &bad,
	       DRM_MODE_ATOMIC_TEST_ONLY | DRM_MODE_ATOMIC_ALLOW_MODESET, NULL));
	struct areq nocrtc = a;					/* FB는 있는데 CRTC_ID=0 */
	nocrtc.val[4] = 0;					/* index 4 = plane CRTC_ID */
	report("TEST_ONLY, plane FB set but CRTC_ID=0", acommit(fd, &nocrtc,
	       DRM_MODE_ATOMIC_TEST_ONLY | DRM_MODE_ATOMIC_ALLOW_MODESET, NULL));
	report("commit ALLOW_MODESET (blocking)", acommit(fd, &a, DRM_MODE_ATOMIC_ALLOW_MODESET, NULL));
	show(fd, crtc);
	return 0;
}
```

### 7.4 예제 9 — NONBLOCK commit, out-fence, flip 이벤트, EBUSY

무엇을 확인하나: atomic page flip(plane의 `FB_ID`만 바꾸는 요청)을 `NONBLOCK | PAGE_FLIP_EVENT`로 보내고 CRTC `OUT_FENCE_PTR`로 sync_file fd를 받아, ioctl 반환·fence signal·이벤트 도착 시각을 비교한다. 이전 commit이 끝나기 전에 또 보내면 어떻게 되는지도 본다.

```c
/* i8_nonblock.c — NONBLOCK commit: ioctl 반환 · out-fence signal · flip 이벤트 시각 비교, EBUSY */
#include "i8_drm.h"
#include <poll.h>
#include <time.h>
static double now(void)
{ struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t); return t.tv_sec * 1e3 + t.tv_nsec / 1e6; }
int main(void)
{
	int fd = dopen("/dev/dri/card0");
	uint32_t conn, crtc; struct drm_mode_modeinfo mode; struct dumb d[2];
	cap(fd, DRM_CLIENT_CAP_ATOMIC, 1);
	first_output(fd, &conn, &crtc, &mode);
	uint32_t pl = find_plane(fd, 1, 0);
	uint32_t fbp = prop_id(fd, pl, DRM_MODE_OBJECT_PLANE, "FB_ID", NULL);
	uint32_t ofp = prop_id(fd, crtc, DRM_MODE_OBJECT_CRTC, "OUT_FENCE_PTR", NULL);
	for (int i = 0; i < 2; i++) dumb_create(fd, &d[i], mode.hdisplay, mode.vdisplay, DRM_FORMAT_XRGB8888);
	struct areq a = { 0 };					/* 처음 한 번: plane을 d[0]으로 */
	aplane(fd, &a, pl, crtc, &d[0], 0, 0);
	if (acommit(fd, &a, DRM_MODE_ATOMIC_ALLOW_MODESET, NULL)) die("first commit");
	for (int f = 1; f <= 3; f++) {
		int32_t fence = -1; struct areq b = { 0 };
		aadd(&b, pl, fbp, d[f & 1].fb);				/* 바뀐 속성만 보낸다 */
		aadd(&b, crtc, ofp, P(&fence));				/* 커널이 sync_file fd를 써 준다 */
		double t0 = now();
		if (acommit(fd, &b, DRM_MODE_ATOMIC_NONBLOCK | DRM_MODE_PAGE_FLIP_EVENT, &b)) die("commit");
		double t1 = now();
		int32_t fence2 = -1; struct areq c = { 0 };		/* 이전 flip이 끝나기 전에 또? */
		aadd(&c, pl, fbp, d[f & 1].fb); aadd(&c, crtc, ofp, P(&fence2));
		int r2 = acommit(fd, &c, DRM_MODE_ATOMIC_NONBLOCK | DRM_MODE_PAGE_FLIP_EVENT, &c);
		int e2 = errno;
		struct pollfd pf = { .fd = fence, .events = POLLIN };
		if (poll(&pf, 1, 1000) != 1) die("fence poll");
		double t2 = now();
		struct pollfd pe = { .fd = fd, .events = POLLIN };
		if (poll(&pe, 1, 1000) != 1) die("event poll");
		struct drm_event_vblank ev;
		if (read(fd, &ev, sizeof(ev)) != sizeof(ev)) die("read event");
		double t3 = now(), tv = ev.tv_sec * 1e3 + ev.tv_usec / 1e3;
		printf("flip %d: ioctl %.3f ms | fence fd=%d signaled +%.3f | event +%.3f "
		       "(vblank ts +%.3f, seq %u) | 2nd commit: %s\n", f, t1 - t0, fence, t2 - t0,
		       t3 - t0, tv - t0, ev.sequence, r2 ? strerror(e2) : "OK");
		close(fence);
	}
	return 0;
}
```


출력에서 볼 것:

- ioctl은 **0.4~1.2 ms 만에 반환**했고, fence signal과 이벤트는 다음 vblank 뒤(8~18 ms)에 왔다. 나머지 시간 동안 유저 스레드는 다음 프레임을 준비할 수 있다. 펌웨어로 치면 "GO 비트를 쓰고 바로 ISR 밖으로 나가는 것"이다.
- 이벤트 안의 vblank 타임스탬프(+15.6 ms 등)가 fence signal 시각보다 조금 앞선다. 타임스탬프는 vblank 순간이고, signal·이벤트 전달은 그 뒤 처리(vkms는 hrtimer 콜백 → 커널 스레드)에서 일어나기 때문이다. 프레임 간격 측정에는 항상 이벤트 타임스탬프를 쓴다(§6).
- **두 번째 NONBLOCK commit은 `EBUSY`**: 같은 CRTC에 아직 끝나지 않은 commit이 있으면 커널은 큐잉하지 않고 거절한다(`drm_atomic_helper_setup_commit()`의 `stall_checks`). 컴포지터는 이벤트(또는 fence)를 받은 뒤에 다음 commit을 낸다. 한 프레임에 한 번.
- 실험 중 하나 배운 것: 실패한 두 번째 commit에도 `OUT_FENCE_PTR` 변수가 있으면 커널이 먼저 `-1`을 써 넣는다. 처음 버전은 같은 변수를 재사용해서 첫 fence fd가 `-1`로 덮였고 `poll()`이 실패했다. out-fence 변수는 commit마다 따로 둔다.
- out-fence는 **sync_file**(fd)이다. `poll()`로 기다리거나, 다른 장치(예: GPU 렌더러, V4L2 인코더)에 in-fence로 넘겨 "화면 반영이 끝나면 이 버퍼를 다시 써라"를 장치 간에 표현한다. 이 fence 객체가 커널의 `dma_fence`이고, dma-buf의 `dma_resv`에 붙는 그 fence다(H9 §11).

### 7.5 legacy vs atomic 정리

| | legacy (`SETCRTC`, `SETPLANE`, `PAGE_FLIP`) | atomic (`DRM_IOCTL_MODE_ATOMIC`) |
|---|---|---|
| 단위 | 객체 하나 | 객체 여러 개의 속성 묶음 |
| 원자성 | 없음 (ioctl마다 따로 반영) | 전부 아니면 전무, 같은 vblank에 반영 |
| 미리 검사 | 불가 | `TEST_ONLY` |
| 모드 변경 허락 | 암묵적 | `ALLOW_MODESET` 명시 |
| 비동기 | primary flip만 | `NONBLOCK` (모든 속성) |
| 동기화 | 이벤트 | 이벤트 + `IN_FENCE_FD` + `OUT_FENCE_PTR` |
| 커널 내부 | atomic helper로 변환됨 (`drm_atomic_helper_set_config`, `drm_atomic_helper_page_flip`) | `drm_mode_atomic_ioctl` |
| 쓰는 곳 | 간단한 툴, 오래된 앱 | Weston, wlroots, Android HWC(drm_hwcomposer), Chrome OS |

### 7.6 흔한 함정

- `DRM_CLIENT_CAP_ATOMIC`을 안 켜고 atomic ioctl: `EINVAL`, 로그 `commit failed: atomic cap not enabled`(랩 소스 `drm_atomic_uapi.c`).
- `TEST_ONLY`와 `PAGE_FLIP_EVENT`를 같이 주는 것: `EINVAL`(`page-flip event requested with test-only commit`). 검사만 하는데 이벤트를 줄 수는 없다.
- 첫 commit에서 connector `CRTC_ID`·CRTC `MODE_ID`/`ACTIVE`를 빼먹는 것: CRTC가 꺼져 있으면 plane만 올려서는 아무것도 안 나온다. §10에서 실제로 `has framebuffer, but [CRTC:43] is off`로 거절당했다.
- blob 누수: `CREATEPROPBLOB`으로 만든 모드 blob은 `DESTROYPROPBLOB`으로 지우거나 fd를 닫을 때 정리된다. 매 프레임 새 blob을 만들면 쌓인다.

## 8. writeback connector와 CRC — 화면 없이 파이프라인 검증하기

### 8.1 직관 — "출력 단자에 로직 분석기를 물린다"

Don이 RF 칩 bring-up에서 scope로 실제 신호를 캡처해 기대값과 비교하듯이, 디스플레이 파이프라인도 **합성된 최종 결과**를 캡처할 수 있으면 화면 없이 검증된다. 두 가지 수단이 있다.

- **writeback connector**: CRTC의 합성 결과를 화면 대신(또는 동시에) **메모리 버퍼로 써 주는** 가상의 출력. 일부 SoC 디스플레이 엔진(Arm Mali-DP/Komeda, R-Car DU, MSM DPU 등)이 하드웨어로 지원하고, vkms는 CPU로 흉내 낸다. 용도: 화면 녹화, 원격 디스플레이, 그리고 **테스트**.
- **CRC**: CRTC가 매 프레임 출력 픽셀의 CRC를 계산해 debugfs로 내보낸다. IGT(커널 그래픽 테스트 모음)가 "기대 화면과 같은가"를 CRC 비교로 판정한다.

### 8.2 예제 10 — primary + overlay 합성 결과를 writeback으로 받아 픽셀 검증

무엇을 확인하나: overlay plane의 ARGB 알파 블렌딩이 기대한 수식대로 합성되는지, 그 결과가 writeback 버퍼에 정확히 써지는지. overlay는 화면 가운데 경계(x=512)에 걸치게 (384,100)에 놓는다.

```c
/* i8_wb.c — primary + overlay(ARGB) 합성 결과를 writeback connector로 받아 픽셀 검증 */
#include "i8_drm.h"
#include <poll.h>
int main(void)
{
	int fd = dopen("/dev/dri/card0"); uint32_t conn, crtc, K = DRM_MODE_OBJECT_CONNECTOR;
	struct drm_mode_modeinfo mode; struct dumb pri, ovl, wb; int32_t wfence = -1;
	cap(fd, DRM_CLIENT_CAP_ATOMIC, 1); cap(fd, DRM_CLIENT_CAP_WRITEBACK_CONNECTORS, 1);
	first_output(fd, &conn, &crtc, &mode);
	uint32_t wbc = find_wb(fd), ppl = find_plane(fd, 1, 0), opl = find_plane(fd, 0, 0);
	printf("mode %s, primary plane %u, overlay plane %u, writeback connector %u\n",
	       mode.name, ppl, opl, wbc);
	dumb_create(fd, &pri, mode.hdisplay, mode.vdisplay, DRM_FORMAT_XRGB8888);
	dumb_create(fd, &ovl, 256, 128, DRM_FORMAT_ARGB8888);
	dumb_create(fd, &wb, mode.hdisplay, mode.vdisplay, DRM_FORMAT_XRGB8888);
	for (uint32_t y = 0; y < pri.h; y++)			/* 왼쪽 절반 빨강, 오른쪽 절반 초록 */
		for (uint32_t x = 0; x < pri.w; x++)
			pri.px[y * pri.pitch / 4 + x] = x < pri.w / 2 ? 0x00ff0000 : 0x0000ff00;
	for (uint32_t i = 0; i < ovl.size / 4; i++)
		ovl.px[i] = 0x80404040;				/* premultiplied: alpha 0x80, RGB 0x40 */
	memset(wb.px, 0xee, wb.size);				/* 쓰기 전 표시 값 */
	struct areq a = { 0 };
	aplane(fd, &a, ppl, crtc, &pri, 0, 0);
	aplane(fd, &a, opl, crtc, &ovl, pri.w / 2 - 128, 100);	/* 경계에 걸치게 */
	aadd(&a, wbc, prop_id(fd, wbc, K, "CRTC_ID", NULL), crtc);
	aadd(&a, wbc, prop_id(fd, wbc, K, "WRITEBACK_FB_ID", NULL), wb.fb);
	aadd(&a, wbc, prop_id(fd, wbc, K, "WRITEBACK_OUT_FENCE_PTR", NULL), P(&wfence));
	if (acommit(fd, &a, DRM_MODE_ATOMIC_ALLOW_MODESET, NULL)) die("atomic commit");
	struct pollfd p = { .fd = wfence, .events = POLLIN };
	printf("writeback fence fd=%d, poll=%d\n", wfence, poll(&p, 1, 2000));
	static const int pts[][2] = { { 10, 10 }, { 1000, 10 }, { 400, 150 }, { 600, 150 }, { 383, 99 }, { 384, 100 } };
	for (unsigned i = 0; i < 6; i++) {
		int x = pts[i][0], y = pts[i][1];
		printf("(%4d,%3d) primary=%08x overlay=%s -> writeback=%08x\n", x, y,
		       pri.px[y * pri.pitch / 4 + x],
		       (x >= 384 && x < 640 && y >= 100 && y < 228) ? "80404040" : "--------",
		       wb.px[y * wb.pitch / 4 + x]);
	}
	return 0;
}
```

게스트 스크립트는 `modprobe vkms enable_overlay=1` 후 `/i8_wb`.


출력에서 볼 것:

- overlay 밖 픽셀은 primary 그대로(빨강 `ff0000`, 초록 `00ff00`), 상위 바이트는 writeback이 알파를 `ff`로 채웠다.
- overlay 안: **premultiplied alpha** 수식 `out = src + dst × (1 - α)`, α = 0x80/0xff ≈ 0.502. 빨강 채널 = 0x40 + 0xff × 0.498 = 64 + 127 = 191 = **0xbf**, 초록·파랑 = 0x40 + 0 = **0x40** → `bf4040`. 초록 배경 위는 `40bf40`. 계산과 정확히 일치한다. (vkms 6.18 plane에는 `pixel blend mode` 속성이 없고 premultiplied만 지원한다 — 위 예제 7의 속성 목록에 없음.)
- 경계 픽셀 (383,99)는 overlay 바로 밖, (384,100)은 바로 안 — **좌표가 한 픽셀도 어긋나지 않았다**. 실제 하드웨어 bring-up에서 "overlay가 1픽셀 밀린다", "알파가 straight/premultiplied로 잘못 해석된다" 같은 버그를 이렇게 숫자로 잡는다.
- writeback fence가 signal(`poll=1`)된 뒤에 읽었기 때문에 버퍼는 완성된 프레임이다. fence 없이 읽으면 `0xee` 초기값이 보일 수 있다.

### 8.3 예제 11 — CRTC CRC: 화면이 바뀌면 CRC가 바뀐다

무엇을 확인하나: debugfs `crtc-0/crc`로 프레임별 CRC를 읽고, fbcon이 화면에 글자를 쓰면 CRC가 바뀌는지.

```sh
#!/bin/sh
modprobe vkms
D=/sys/kernel/debug/dri/0/crtc-0/crc
ls /sys/kernel/debug/dri/0/crtc-0/crc | cat
echo auto > $D/control
head -n 3 $D/data                 # 화면이 그대로면 CRC도 그대로
echo "frame changed" > /dev/tty1  # fbcon이 framebuffer에 글자를 그린다
sleep 0.2
echo auto > $D/control
head -n 3 $D/data
```

```text

 0x00000005 0x5d2f9aa5
 0x00000006 0x5d2f9aa5
0x00000017 0x9465de47

```

출력에서 볼 것:

- 한 줄 = (vblank 번호, CRC). 화면이 그대로인 프레임 4~6은 CRC가 같다. 글자를 쓴 뒤에는 다른 값이 된다.
- 두 번째 묶음에서 18 → 19 사이에 CRC가 또 바뀐 것은 fbcon의 **커서 깜빡임** 때문이다(두 값 사이를 오간다). 테스트에서는 커서를 끄거나(`echo 0 > /sys/class/graphics/fbcon/cursor_blink`) 화면을 KMS 클라이언트가 소유한 상태에서 잰다.
- CRC는 픽셀 데이터를 몰라도 "같은가/다른가"를 프레임 단위로 싸게 판정한다. 실제 SoC 디스플레이 엔진 상당수가 하드웨어 CRC 블록을 갖고 있고, 드라이버가 `crtc->funcs->set_crc_source`를 구현하면 같은 debugfs 인터페이스가 생긴다.

### 8.4 흔한 함정

- writeback fb 크기가 모드와 다름: vkms의 `vkms_wb_atomic_check()`가 `Invalid framebuffer size`로 `EINVAL`을 낸다. 포맷은 `WRITEBACK_PIXEL_FORMATS` 안에 있어야 하고, 이것은 공용 헬퍼 `drm_atomic_helper_check_wb_connector_state()`가 검사한다(vkms: ARGB8888, XRGB8888, ABGR8888, XRGB16161616, ARGB16161616 — 랩 소스 `vkms_writeback.c`).
- writeback은 **one-shot**이다. commit마다 `WRITEBACK_FB_ID`를 다시 줘야 그 프레임이 캡처된다. 연속 캡처는 매 프레임 commit.
- writeback connector를 CRTC에 붙이는 것도 라우팅 변경이므로 처음에는 `ALLOW_MODESET`이 필요하다.

### 9.2 왜 render 노드가 따로 있나 — 권한 모델

- **card 노드 + DRM master**: KMS는 시스템에 하나뿐인 화면을 바꾸므로, 한 순간에 한 프로세스(master — 보통 컴포지터)만 모드를 바꿀 수 있다. 다른 프로세스는 GEM을 쓸 수 있어도 KMS는 못 한다. 옛날에는 GPU를 쓰려는 앱도 card 노드를 열고 master에게 "인증(`DRM_IOCTL_AUTH_MAGIC`)"을 받아야 했다.
- **render 노드**: GPU 계산만 하는 앱(브라우저 렌더러, OpenCL, 비디오 디코더, ML 추론)이 master 없이 GPU를 쓰게 하려고 3.12 무렵 생겼다. 화면을 못 건드리므로 권한 검사가 단순하다(보통 `render` 그룹). 한 프로세스의 GEM handle은 다른 프로세스에서 보이지 않는다 — 공유는 dma-buf fd로만.
- 결론: **화면을 내는 프로세스만 card 노드**, 나머지 GPU 사용자는 render 노드.

### 9.3 예제 13 — render 노드로 GPU 버퍼 할당, 매핑, 명령 제출 시도, PRIME export

무엇을 확인하나: render 노드에서 허용되는 드라이버 전용 ioctl(virtio-gpu의 `RESOURCE_CREATE`, `MAP`, `EXECBUFFER`)과 공통 PRIME export, 그리고 거절되는 KMS·master ioctl.

```c
/* i8_render.c — render node(renderD128): KMS는 못 쓰지만 GPU 버퍼 할당·submit·PRIME은 된다 */
#include "i8_drm.h"
#include <drm/virtgpu_drm.h>
static void param(int fd, uint64_t p, const char *n)
{
	int v = -1; struct drm_virtgpu_getparam g = { .param = p, .value = P(&v) };
	if (ioctl(fd, DRM_IOCTL_VIRTGPU_GETPARAM, &g)) printf("  GETPARAM %-13s -> %s\n", n, strerror(errno));
	else printf("  GETPARAM %-13s = %d\n", n, v);
}
int main(void)
{
	int fd = dopen("/dev/dri/renderD128");
	param(fd, VIRTGPU_PARAM_3D_FEATURES, "3D_FEATURES");
	param(fd, VIRTGPU_PARAM_RESOURCE_BLOB, "RESOURCE_BLOB");
	param(fd, VIRTGPU_PARAM_CONTEXT_INIT, "CONTEXT_INIT");
	struct drm_virtgpu_resource_create rc = { .target = 2 /* 2D texture */, .format = 2 /* B8G8R8X8 */,
		.bind = 2, .width = 256, .height = 256, .depth = 1, .array_size = 1,
		.size = 256 * 256 * 4, .stride = 256 * 4 };	/* size는 입력값 (0이면 PAGE_SIZE) */
	if (xioctl(fd, DRM_IOCTL_VIRTGPU_RESOURCE_CREATE, &rc)) die("RESOURCE_CREATE");
	printf("RESOURCE_CREATE: GEM handle %u, host resource id %u, size %u\n",
	       rc.bo_handle, rc.res_handle, rc.size);
	struct drm_virtgpu_map mp = { .handle = rc.bo_handle };
	if (xioctl(fd, DRM_IOCTL_VIRTGPU_MAP, &mp)) die("VIRTGPU_MAP");
	uint32_t *px = mmap(NULL, rc.size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, mp.offset);
	if (px == MAP_FAILED) die("mmap");
	px[0] = 0x00ff00ff;
	printf("VIRTGPU_MAP: fake offset 0x%llx, CPU wrote px[0]=%08x\n", (unsigned long long)mp.offset, px[0]);
	uint32_t cmd[4] = { 0 };				/* 진짜 GPU라면 여기 명령 스트림 */
	struct drm_virtgpu_execbuffer eb = { .size = sizeof(cmd), .command = P(cmd),
		.bo_handles = P(&rc.bo_handle), .num_bo_handles = 1, .fence_fd = -1 };
	if (ioctl(fd, DRM_IOCTL_VIRTGPU_EXECBUFFER, &eb)) printf("EXECBUFFER -> %s (no virgl 3D)\n", strerror(errno));
	else printf("EXECBUFFER -> OK\n");
	struct drm_prime_handle ex = { .handle = rc.bo_handle, .flags = DRM_CLOEXEC | DRM_RDWR };
	if (xioctl(fd, DRM_IOCTL_PRIME_HANDLE_TO_FD, &ex)) die("PRIME export");
	printf("PRIME export from render node -> dma-buf fd %d\n", ex.fd);
	struct drm_mode_card_res r = { 0 };
	if (ioctl(fd, DRM_IOCTL_MODE_GETRESOURCES, &r)) printf("MODE_GETRESOURCES -> %s\n", strerror(errno));
	struct drm_set_client_cap c = { .capability = DRM_CLIENT_CAP_ATOMIC, .value = 1 };
	if (ioctl(fd, DRM_IOCTL_SET_CLIENT_CAP, &c)) printf("SET_CLIENT_CAP(ATOMIC) -> %s\n", strerror(errno));
	if (ioctl(fd, DRM_IOCTL_SET_MASTER, 0)) printf("SET_MASTER -> %s\n", strerror(errno));
	return 0;
}
```

출력에서 볼 것:

- 드라이버 전용 ioctl(`DRM_IOCTL_VIRTGPU_*`)은 `DRM_COMMAND_BASE`(0x40) 위의 번호를 쓴다. 공통 ioctl(`PRIME_HANDLE_TO_FD` 등)은 그 아래다. 모든 GPU 드라이버가 이 구조다: **공통 = GEM handle 관리·PRIME·syncobj, 드라이버 전용 = 버퍼 생성 옵션·명령 제출**.
- 첫 시도에서 `size`를 안 줬더니 `size 0`이 돌아오고 mmap이 `EINVAL`로 실패했다. virtio-gpu의 `RESOURCE_CREATE`에서 `size`는 **입력**이고 0이면 `PAGE_SIZE`로 잡힌다(랩 소스 `virtgpu_ioctl.c`). uAPI 헤더 주석만 믿지 말고 커널 소스를 보는 습관이 필요한 장면이다.
- `3D_FEATURES = 0`: 이 QEMU 장치는 virgl(호스트 OpenGL로 3D 명령을 실행) 없는 2D 장치라 `EXECBUFFER`(명령 제출)가 `ENOSYS`다. 진짜 GPU 드라이버라면 여기서 명령 버퍼와 BO 목록을 넘기고, 커널이 GPU 링에 올린 뒤 완료 fence를 돌려준다. **이 노트에서 실제 GPU 명령 실행은 하지 못했다**(호스트 GL이 없는 headless VM).
- `SET_CLIENT_CAP`과 `SET_MASTER`도 render 노드에서는 `EACCES`다. render 노드에는 master 개념이 없다.

### 9.4 GEM — DRM의 버퍼 객체

**GEM(Graphics Execution Manager)** 은 DRM의 버퍼 객체(`struct drm_gem_object`) 관리자다. 개념은 단순하다.

- 버퍼마다 커널 객체가 있고, 유저는 **파일(드라이버 fd)마다 따로 매겨진 정수 handle**로 부른다. fd 테이블처럼 handle은 그 fd 안에서만 의미가 있다(예제 13에서 handle 1, §10에서 두 장치 모두 handle 1이지만 다른 객체 테이블).
- mmap은 handle → "가짜 오프셋" → `mmap(fd, offset)` 순서(`drm_vma_offset_manager`).
- 다른 프로세스·장치와 공유는 **PRIME(dma-buf fd)**. 옛날 방식인 전역 이름(`GEM_FLINK`, 32비트 숫자를 아무나 열 수 있음)은 보안 문제로 쓰지 않는다.

드라이버는 메모리 성격에 맞는 GEM 헬퍼를 고른다.

| 헬퍼 | 메모리 | 쓰는 드라이버 | 언제 |
|---|---|---|---|
| `drm_gem_dma_helper` (옛 이름 CMA helper) | `dma_alloc_*`로 잡은 **물리 연속** 버퍼 | 많은 SoC 디스플레이 컨트롤러 (mxsfb, imx-lcdif, tidss 등) | 디스플레이 엔진에 IOMMU가 없어 연속 메모리가 필요할 때 (F10 CMA) |
| `drm_gem_shmem_helper` | shmem 페이지(흩어짐) + sg_table | vkms, virtio-gpu, panfrost, panthor, v3d | IOMMU/MMU가 있거나 CPU로 합성할 때 |
| TTM | VRAM과 시스템 메모리 사이 이동·축출 | amdgpu, nouveau, radeon | 전용 VRAM이 있는 dGPU |
| `drm_gem_vram_helper` | 작은 VRAM | bochs, hibmc | 단순한 VRAM 디스플레이 |

임베디드 SoC는 대부분 dGPU처럼 VRAM이 없는 **UMA(통합 메모리)** 이므로 앞의 두 헬퍼를 주로 만난다. "디스플레이는 CMA, GPU는 shmem + GPU MMU"가 흔한 조합이고, 그 둘을 이어 주는 것이 다음 절의 PRIME이다.

### 9.5 흔한 함정

- 컨테이너나 서비스 계정이 `/dev/dri/renderD*` 권한(그룹 `render`)이 없어 GPU 가속이 조용히 꺼지고 소프트웨어 렌더링(llvmpipe)으로 떨어짐. 증상은 CPU 100%.
- GEM handle을 다른 프로세스에 정수로 넘김: 그쪽 fd 테이블에서는 다른 객체거나 없는 handle이다. fd(dma-buf)를 `SCM_RIGHTS`로 넘긴다(A 모듈의 Unix socket fd 전달).
- `DRM_IOCTL_GEM_CLOSE`를 빼먹어 버퍼 누수: handle은 fd를 닫을 때 정리되지만, 오래 사는 컴포지터에서는 쌓인다. debugfs `gem_names`, `framebuffer`, 그리고 `/proc/<pid>/fdinfo/<drm fd>`의 `drm-memory-*` 항목(지원 드라이버)으로 추적한다.

## 10. PRIME / dma-buf — 장치 사이 zero-copy

### 10.1 직관

카메라(ISP)가 쓴 프레임을 GPU가 후처리하고, NPU가 추론하고, 디스플레이가 띄운다. 장치마다 자기 버퍼에 복사하면 1080p NV12 한 장(약 3 MB)을 프레임마다 몇 번씩 memcpy하게 되고, 임베디드 SoC의 메모리 대역폭이 금방 바닥난다. **PRIME**은 DRM에서 dma-buf를 쓰는 이름이다.

- `DRM_IOCTL_PRIME_HANDLE_TO_FD`: GEM handle → dma-buf fd (export). exporter 드라이버의 `dma_buf_ops`가 붙은 `struct dma_buf`가 생긴다.
- `DRM_IOCTL_PRIME_FD_TO_HANDLE`: dma-buf fd → 이 장치의 GEM handle (import). importer 드라이버가 `dma_buf_attach()` + `dma_buf_map_attachment()`로 자기 장치용 sg_table(=DMA 주소)을 받는다.
- 같은 장치에 다시 import하면 새 객체가 아니라 **원래 handle**이 돌아온다(self-import 인식).

### 10.2 예제 14 — GPU 버퍼를 디스플레이가 복사 없이 스캔아웃

무엇을 확인하나: virtio-gpu(card0)에서 dumb buffer를 만들어 패턴을 그리고, PRIME으로 vkms(card1)에 넘겨 framebuffer로 걸고, vkms writeback으로 결과를 받아 **virtio-gpu 쪽 매핑의 픽셀과 같은지** 비교한다. 중간에 dma-buf fd를 직접 mmap해서 한 픽셀을 고친다(CPU 접근 구간은 `DMA_BUF_IOCTL_SYNC`로 감싼다).

```c
/* i8_prime.c — virtio-gpu에서 만든 버퍼를 dma-buf fd로 내보내 vkms가 복사 없이 스캔아웃 */
#include "i8_drm.h"
#include <poll.h>
#include <linux/dma-buf.h>
int main(void)
{
	int g = dopen("/dev/dri/card0"), k = dopen("/dev/dri/card1");	/* virtio_gpu, vkms */
	uint32_t conn, crtc, K = DRM_MODE_OBJECT_CONNECTOR; struct drm_mode_modeinfo mode;
	struct dumb src, wb; int32_t wfence = -1;
	cap(k, DRM_CLIENT_CAP_ATOMIC, 1); cap(k, DRM_CLIENT_CAP_WRITEBACK_CONNECTORS, 1);
	first_output(k, &conn, &crtc, &mode);
	dumb_create(g, &src, mode.hdisplay, mode.vdisplay, DRM_FORMAT_XRGB8888);	/* GPU 쪽 */
	for (uint32_t i = 0; i < src.size / 4; i++) src.px[i] = 0x00123456 + (i % src.w);
	struct drm_prime_handle ex = { .handle = src.handle, .flags = DRM_CLOEXEC | DRM_RDWR };
	if (xioctl(g, DRM_IOCTL_PRIME_HANDLE_TO_FD, &ex)) die("PRIME_HANDLE_TO_FD");
	printf("virtio_gpu handle %u -> dma-buf fd %d\n", src.handle, ex.fd);
	char cmd[96]; snprintf(cmd, sizeof cmd, "grep -E 'size|exp_name' /proc/%d/fdinfo/%d", getpid(), ex.fd);
	fflush(stdout); if (system(cmd)) {}
	struct drm_prime_handle self = { .fd = ex.fd };		/* 같은 장치로 다시 import */
	if (xioctl(g, DRM_IOCTL_PRIME_FD_TO_HANDLE, &self)) die("self import");
	struct drm_prime_handle im = { .fd = ex.fd };		/* 다른 장치(vkms)로 import */
	if (xioctl(k, DRM_IOCTL_PRIME_FD_TO_HANDLE, &im)) die("vkms import");
	printf("self-import on virtio_gpu -> handle %u, import on vkms -> handle %u\n", self.handle, im.handle);
	uint32_t *m = mmap(NULL, src.size, PROT_READ | PROT_WRITE, MAP_SHARED, ex.fd, 0);	/* dma-buf 직접 mmap */
	if (m == MAP_FAILED) die("mmap dmabuf");
	struct dma_buf_sync s = { .flags = DMA_BUF_SYNC_START | DMA_BUF_SYNC_RW };
	if (xioctl(ex.fd, DMA_BUF_IOCTL_SYNC, &s)) die("SYNC start");
	m[0] = 0x00abcdef;					/* dma-buf mmap으로 한 픽셀 고침 */
	s.flags = DMA_BUF_SYNC_END | DMA_BUF_SYNC_RW;
	if (xioctl(ex.fd, DMA_BUF_IOCTL_SYNC, &s)) die("SYNC end");
	struct drm_mode_fb_cmd2 f = { .width = src.w, .height = src.h, .pixel_format = DRM_FORMAT_XRGB8888,
		.handles = { im.handle }, .pitches = { src.pitch } };
	if (xioctl(k, DRM_IOCTL_MODE_ADDFB2, &f)) die("ADDFB2 on vkms");
	struct dumb shown = src; shown.fb = f.fb_id;
	dumb_create(k, &wb, mode.hdisplay, mode.vdisplay, DRM_FORMAT_XRGB8888);
	uint32_t wbc = find_wb(k);
	struct areq a = { 0 };
	aplane(k, &a, find_plane(k, 1, 0), crtc, &shown, 0, 0);
	aadd(&a, conn, prop_id(k, conn, K, "CRTC_ID", NULL), crtc);	/* 이 vkms CRTC는 꺼져 있다 */
	aadd(&a, crtc, prop_id(k, crtc, DRM_MODE_OBJECT_CRTC, "MODE_ID", NULL), mode_blob(k, &mode));
	aadd(&a, crtc, prop_id(k, crtc, DRM_MODE_OBJECT_CRTC, "ACTIVE", NULL), 1);
	aadd(&a, wbc, prop_id(k, wbc, K, "CRTC_ID", NULL), crtc);
	aadd(&a, wbc, prop_id(k, wbc, K, "WRITEBACK_FB_ID", NULL), wb.fb);
	aadd(&a, wbc, prop_id(k, wbc, K, "WRITEBACK_OUT_FENCE_PTR", NULL), P(&wfence));
	if (acommit(k, &a, DRM_MODE_ATOMIC_ALLOW_MODESET, NULL)) die("commit");
	struct pollfd p = { .fd = wfence, .events = POLLIN };
	if (poll(&p, 1, 2000) != 1) die("wb fence");
	printf("pixel  virtio_gpu map -> vkms writeback\n");
	for (int i = 0; i < 3; i++)
		printf("[%4d] %08x       -> %08x\n", i * 500, src.px[i * 500], wb.px[i * 500]);
	if (system("cat /sys/kernel/debug/dma_buf/bufinfo | grep -vE '^$'")) {}
	return 0;
}
```

- `/proc/<pid>/fdinfo/<fd>`에 `exp_name: virtio_gpu` — 이 fd가 어느 드라이버가 내보낸 dma-buf인지 보인다. 시스템 전체는 `/sys/kernel/debug/dma_buf/bufinfo`: 3 MiB 버퍼 하나, exporter virtio_gpu, **attach된 장치 vkms**.
- self-import는 원래 handle 1을 돌려줬다. vkms import도 handle 1이지만 vkms의 handle 테이블의 1번이다.
- vkms writeback이 읽은 픽셀이 virtio-gpu 쪽 CPU 매핑의 값과 같다(상위 바이트는 writeback이 채운 알파). 특히 `[0]`의 `abcdef`는 **dma-buf fd의 mmap으로 고친 값**인데, virtio-gpu의 GEM 매핑에서도, vkms의 스캔아웃에서도 보인다. 세 경로가 같은 페이지라는 증거다. 복사는 한 번도 없었다.
- 처음 시도는 `commit: Invalid argument`로 실패했다. `drm.debug=0x1f`로 본 이유는 `[CONNECTOR:45:Writeback-1] has framebuffer, but [CRTC:43] is off`였다. fbcon이 card0(virtio-gpu)에만 붙어서 vkms의 CRTC는 꺼진 상태였기 때문이다(§4.3의 `enabled=disabled`). 그래서 connector `CRTC_ID`, CRTC `MODE_ID`/`ACTIVE`를 추가했다. 첫 commit은 전체 파이프라인을 다 적어야 한다.
- vkms는 import한 버퍼를 `drm_gem_shmem_prime_import_*` 경로로 받는다(디버그 로그에 `drm_gem_shmem_prime_import_no_map ... size = 3145728`이 찍혔다). 실제 디스플레이 컨트롤러가 importer라면 여기서 **자기 장치 기준의 DMA 주소**를 받아야 하고, IOMMU가 없는 컨트롤러는 그 버퍼가 물리 연속이어야 한다 — 그래서 카메라 → 디스플레이 zero-copy가 "exporter가 CMA로 할당했나"에 달려 있는 경우가 많다(F10, H9 §11).

### 10.3 카메라 → 디스플레이 / NPU zero-copy (I5와 연결)

센서 키트에서 흔한 파이프라인은 이렇다(코드는 I5와 이 노트 예제의 조합 — 여기서는 실행하지 않음).

1. V4L2 캡처 장치에 `VIDIOC_REQBUFS`(MMAP) → `VIDIOC_EXPBUF`로 각 버퍼의 dma-buf fd를 얻는다(I5).
2. 그 fd들을 DRM에 `PRIME_FD_TO_HANDLE` → `ADDFB2`(NV12면 handle 2개, pitch 2개 또는 같은 handle에 offset)로 framebuffer를 미리 만든다.
3. `VIDIOC_DQBUF`로 프레임이 오면 그 버퍼의 fb를 overlay plane의 `FB_ID`로 atomic NONBLOCK commit, 다음 flip 이벤트가 오면 이전 버퍼를 `VIDIOC_QBUF`로 돌려준다.
4. 같은 fd를 NPU 런타임(accel 노드의 import)이나 GPU(EGL `EGL_EXT_image_dma_buf_import`)에도 넘긴다.

GStreamer라면 `v4l2src io-mode=dmabuf ! kmssink`가 이 일을 한다. 핵심 함정은 **포맷·정렬·연속성**이다: 디스플레이 plane이 NV12를 받는지(§3.4), pitch 정렬이 맞는지, importer가 IOMMU 없이 연속 메모리를 요구하는지.

### 10.4 동기화 — implicit vs explicit fence

GPU가 아직 그리는 중인 버퍼를 디스플레이가 스캔아웃하면 반쯤 그린 프레임이 보인다. 두 가지 해법이 있다.

- **implicit sync**: dma-buf마다 붙은 `dma_resv` 객체에 "이 버퍼에 쓰는 중"인 fence가 기록된다. importer(디스플레이)가 그 fence를 자동으로 기다린다. 유저는 아무것도 안 해도 된다. 대신 언제 기다리는지 불투명하다.
- **explicit sync**: 유저가 fence를 sync_file fd로 들고 다니며 넘긴다. GPU submit의 out-fence → plane의 `IN_FENCE_FD`, CRTC의 `OUT_FENCE_PTR` → 다음 렌더링의 in-fence. Android와 Vulkan이 이 모델이다. §7.4에서 out-fence를 직접 받아 봤다.

`DMA_BUF_IOCTL_SYNC`는 이와 별개로 **CPU 캐시 관리**용이다(H9의 `dma_sync_*_for_cpu/for_device`의 유저 공간 버전). 비코히어런트 SoC에서 CPU가 dma-buf mmap으로 쓰고 장치가 읽는다면 반드시 START/END로 감싼다.

## 11. drm/accel — NPU를 위한 자리

### 11.1 왜 GPU 서브시스템을 빌려 쓰나

NPU 드라이버가 필요한 것은 GPU 드라이버와 거의 같다: 장치 메모리(BO) 할당과 매핑, 장치 MMU의 주소 공간 관리, 명령(작업) 제출, 작업 간 의존성 스케줄링, 완료 fence, 다른 장치와 버퍼 공유. 화면만 없다. 그래서 커널은 NPU용 서브시스템을 새로 만들지 않고 **DRM의 갈래로 `drivers/accel/`을 만들었다**(6.2). accel 드라이버는 `DRIVER_COMPUTE_ACCEL` 플래그를 켜고 `drm_device`를 그대로 쓰며, `/dev/accel/accelN`(major 261)만 생긴다. GEM, PRIME, `gpu-sched`(작업 스케줄러), `drm_gpuvm`(장치 가상 주소 관리) 같은 DRM 공용 부품을 그대로 쓴다.

### 11.2 예제 15 — 랩 커널 트리의 accel 드라이버와 uAPI

### 11.3 accel uAPI의 모양 — rocket을 예로

rocket의 ioctl 네 개(랩 소스 `include/uapi/drm/rocket_accel.h`)가 accel 드라이버의 전형을 보여 준다.

| ioctl | 하는 일 | GPU/DMA에서 대응 |
|---|---|---|
| `ROCKET_CREATE_BO` | 크기를 주면 GEM handle, **NPU 주소 공간의 DMA 주소**, mmap 오프셋을 돌려줌 | GEM 생성 + IOMMU 매핑 (H9 IOVA) |
| `ROCKET_PREP_BO` | CPU가 BO를 쓰기 전: NPU 작업 완료를 기다리고 캐시 동기화 | `dma_sync_*_for_cpu` |
| `ROCKET_FINI_BO` | CPU가 다 쓴 뒤: NPU가 보도록 캐시 동기화 | `dma_sync_*_for_device` |
| `ROCKET_SUBMIT` | job 배열 제출. job = task(레지스터 명령 버퍼 주소 + 개수) 목록 + 읽는 BO/쓰는 BO handle 목록 | GPU execbuffer + 의존성 |

- 입력 BO와 출력 BO를 나눠 적는 이유는 커널 스케줄러(`gpu-sched`)가 **BO 단위로 의존성을 계산**하기 때문이다. 앞 job이 쓰는 BO를 다음 job이 읽으면 자동으로 순서가 잡힌다(implicit fence).
- 유저 공간에서는 Mesa의 **Teflon**(TensorFlow Lite delegate)이 rocket·etnaviv(i.MX8M Plus의 Vivante NPU) 같은 오픈 NPU 드라이버 위에서 모델을 레지스터 명령 버퍼로 컴파일해 제출한다(기억에 의존한 설명, 이 랩에서 확인하지 않음).
- 반대로 NVIDIA Jetson이나 많은 벤더 SoC의 NPU는 아직 out-of-tree 드라이버와 자체 uAPI(misc device + ioctl)를 쓴다. Don이 그런 NPU를 bring-up하게 되면 "왜 upstream은 accel로 가는가"(공용 GEM/dma-buf/스케줄러/fdinfo 메트릭)를 설명할 수 있어야 한다.

### 11.4 GPU vs NPU vs 디스플레이 — 한눈에

| | 디스플레이 (KMS) | GPU (render) | NPU (accel) |
|---|---|---|---|
| 노드 | `/dev/dri/cardN` | `/dev/dri/renderD12x` | `/dev/accel/accelN` |
| 드라이버 플래그 | `DRIVER_MODESET` `DRIVER_ATOMIC` | `DRIVER_RENDER` | `DRIVER_COMPUTE_ACCEL` |
| 하는 일 | 버퍼를 타이밍에 맞춰 스캔아웃 | 셰이더 명령 실행 | 텐서 연산 명령 실행 |
| 메모리 | 대개 연속(CMA) 또는 IOMMU | GPU MMU + shmem | NPU MMU/IOMMU + BO |
| 핵심 객체 | plane, CRTC, connector | BO, context, job | BO, job |
| 완료 신호 | vblank 이벤트, out-fence | fence, syncobj | fence |
| 유저 스택 | Weston, Qt eglfs, kmssink | Mesa (GL/Vulkan) | TFLite delegate, 벤더 SDK |
| 버퍼 공유 | dma-buf | dma-buf | dma-buf |

## 12. 드라이버 구조 — 디스플레이 드라이버를 읽는 법

### 12.1 뼈대 — `drm_driver`, `drm_mode_config_funcs`, helper vtable

KMS 드라이버는 "객체를 만들고, 각 객체에 helper 콜백을 달고, atomic helper가 순서대로 부르게 하는" 구조다. vkms가 가장 읽기 쉬운 실제 예다. 아래는 랩 소스(6.18.55)에서 그대로 옮긴 발췌다.

```c
/* drivers/gpu/drm/vkms/vkms_drv.c (발췌) */
static const struct drm_driver vkms_driver = {
	.driver_features	= DRIVER_MODESET | DRIVER_ATOMIC | DRIVER_GEM,
	.fops			= &vkms_driver_fops,
	DRM_GEM_SHMEM_DRIVER_OPS,
	DRM_FBDEV_SHMEM_DRIVER_OPS,

	.name			= DRIVER_NAME,
	.desc			= DRIVER_DESC,
	.major			= DRIVER_MAJOR,
	.minor			= DRIVER_MINOR,
};

static const struct drm_mode_config_funcs vkms_mode_funcs = {
	.fb_create = drm_gem_fb_create,
	.atomic_check = vkms_atomic_check,
	.atomic_commit = drm_atomic_helper_commit,
};

static const struct drm_mode_config_helper_funcs vkms_mode_config_helpers = {
	.atomic_commit_tail = vkms_atomic_commit_tail,
};
/* vkms_atomic_commit_tail(): commit_modeset_disables → commit_planes → commit_modeset_enables
 * → fake_vblank → commit_hw_done → wait_for_flip_done → cleanup_planes */

/* drivers/gpu/drm/vkms/vkms_crtc.c (발췌) */
static const struct drm_crtc_helper_funcs vkms_crtc_helper_funcs = {
	.atomic_check	= vkms_crtc_atomic_check,
	.atomic_begin	= vkms_crtc_atomic_begin,
	.atomic_flush	= vkms_crtc_atomic_flush,
	.atomic_enable	= drm_crtc_vblank_atomic_enable,
	.atomic_disable	= drm_crtc_vblank_atomic_disable,
	.handle_vblank_timeout = vkms_crtc_handle_vblank_timeout,
};

/* drivers/gpu/drm/vkms/vkms_plane.c (발췌) */
static const struct drm_plane_helper_funcs vkms_plane_helper_funcs = {
	.atomic_update		= vkms_plane_atomic_update,
	.atomic_check		= vkms_plane_atomic_check,
	.prepare_fb		= vkms_prepare_fb,
	.cleanup_fb		= vkms_cleanup_fb,
};

/* drivers/gpu/drm/vkms/vkms_connector.c (발췌) */
static const struct drm_connector_helper_funcs vkms_conn_helper_funcs = {
	.get_modes    = vkms_conn_get_modes,
	.best_encoder = vkms_conn_best_encoder,
};
```

읽는 법:

| 콜백 | 언제 불리나 | 실제 하드웨어 드라이버에서 하는 일 |
|---|---|---|
| `mode_config.funcs->fb_create` | `ADDFB2` | GEM handle → `drm_framebuffer` (대개 `drm_gem_fb_create` 그대로) |
| `mode_config.funcs->atomic_check` | 모든 atomic 요청 (TEST_ONLY 포함) | `drm_atomic_helper_check()` + 하드웨어 전역 제약(대역폭, 공유 스케일러) |
| plane `atomic_check` | 그 plane이 바뀔 때 | 포맷·스케일 비율·위치 제약 검사 (`drm_atomic_helper_check_plane_state()`) |
| plane `atomic_update` | commit_tail 안에서 | 레이어 레지스터에 fb의 DMA 주소·pitch·좌표 쓰기 |
| CRTC `atomic_enable`/`disable` | full modeset 때 | 픽셀 클럭 설정, 타이밍 레지스터, vblank IRQ on/off |
| CRTC `atomic_flush` | plane 갱신 뒤 | shadow 레지스터 "GO" 비트, 이벤트 무장(`drm_crtc_arm_vblank_event`) |
| connector `get_modes` | 모드 probe (`GETCONNECTOR`) | EDID 읽기 또는 패널 고정 모드 |
| vblank IRQ 핸들러 | 매 프레임 | `drm_crtc_handle_vblank()` → 대기 중인 flip 이벤트 전송 |

**atomic_check에서는 하드웨어를 건드리지 않는다**(TEST_ONLY가 부작용 없이 끝나야 하므로). 하드웨어 쓰기는 전부 commit_tail 안에서 한다. 그리고 **atomic_check는 실패할 수 있지만 commit은 실패하면 안 된다** — 검사를 통과한 상태는 반드시 적용 가능해야 한다. 메모리 할당·클럭 계산처럼 실패할 수 있는 일은 check 단계(또는 `prepare_fb`)에서 끝낸다.

### 12.2 작은 패널용 helper — simple display pipe와 그 이후

plane 1개 + CRTC 1개 + encoder 1개로 끝나는 단순한 컨트롤러(SPI 소형 LCD, 단순 LCDC)를 위해 `drm_simple_display_pipe_init()`이 있다. plane/CRTC/encoder를 한 덩어리로 만들고 `enable`/`disable`/`update` 세 콜백만 받는다. 랩 트리(6.18.55)에서 이것을 쓰는 곳을 세어 보면 `drm_mipi_dbi.c`(SPI MIPI-DBI 패널 공용 코드), `pl111`, `tve200`, `mcde`, `aspeed`, `imx-lcdc`, `xen`, `tiny/` 일부(gm12u320, arcpgu, repaper) 정도이고, 같은 `tiny/`의 `bochs.c`는 `drm_universal_plane_init()`·`drm_crtc_init_with_planes()`로 객체를 직접 만든다. 새 드라이버는 대체로 일반 atomic helper로 객체를 직접 만드는 쪽으로 가는 흐름이다(기억에 의존한 경향 설명 — 공식 deprecated 표시는 6.18 문서에서 확인하지 못했다).

### 12.3 bridge와 panel — 임베디드 화면 bring-up의 본체

랩 트리의 실제 DT(발췌, 클럭·전원 등 줄임):

```dts

	compatible = "fsl,imx8mm-lcdif", "fsl,imx6sx-lcdif";
	/* ... clocks: pix, axi, disp_axi; interrupts; power-domains ... */
	port {
		lcdif_to_dsim: endpoint {
			remote-endpoint = <&dsim_from_lcdif>;
		};
	};
};
mipi_dsi: dsi@32e10000 {
	compatible = "fsl,imx8mm-mipi-dsim";
	ports {
		port@0 { reg = <0>; dsim_from_lcdif: endpoint { remote-endpoint = <&lcdif_to_dsim>; }; };
		port@1 { reg = <1>; mipi_dsi_out: endpoint { }; };
	};
};

/* imx8mm-evk.dtsi */
&mipi_dsi {
	samsung,esc-clock-frequency = <10000000>;
	status = "okay";
	ports {
		port@1 {
			reg = <1>;
			dsi_out: endpoint {
				remote-endpoint = <&adv7535_in>;
				data-lanes = <1 2 3 4>;
			};
		};
	};
};
hdmi@3d {				/* I2C 버스 아래 */
	compatible = "adi,adv7535";
	reg = <0x3d>;
	interrupt-parent = <&gpio1>;
	interrupts = <9 IRQ_TYPE_EDGE_FALLING>;
	adi,dsi-lanes = <4>;
	ports {
		port@0 { reg = <0>; adv7535_in: endpoint { remote-endpoint = <&dsi_out>; }; };
		port@1 { reg = <1>; adv7535_out: endpoint { remote-endpoint = <&hdmi_connector_in>; }; };
	};
};
hdmi-connector {
	compatible = "hdmi-connector";
	label = "hdmi";
	type = "a";
	port { hdmi_connector_in: endpoint { remote-endpoint = <&adv7535_out>; }; };
};
```

(원본은 여러 줄로 펼쳐져 있다. 위는 endpoint 부분을 한 줄로 접은 것이다. 이 DT는 i.MX8MM 보드용이라 QEMU에서 부팅해 보지는 않았다.)

드라이버 쪽에서 이 그래프는 이렇게 쓰인다:

1. 디스플레이 컨트롤러(또는 DSI 호스트)가 `devm_drm_of_get_bridge(dev, np, port, endpoint)`로 다음 단계의 bridge(또는 패널을 감싼 panel-bridge)를 찾는다. 아직 그 드라이버가 probe되지 않았으면 `-EPROBE_DEFER`(G 모듈)로 나중에 다시 시도한다.
2. `drm_bridge_attach(encoder, bridge, …, DRM_BRIDGE_ATTACH_NO_CONNECTOR)`로 체인을 잇고, 마지막에 `drm_bridge_connector_init()`이 체인 끝의 정보(HPD, EDID, 모드)로 connector를 만든다.
3. 화면을 켤 때 atomic helper가 체인을 따라 `pre_enable` → `enable`을 부르고, 패널의 `prepare`(전원·리셋·초기화 명령) → `enable`(백라이트)이 이어진다. 끌 때는 역순이다.

### 12.4 패널 드라이버 뼈대 — 빌드 확인

무엇을 확인하나: 가상의 720x1280 MIPI-DSI 패널 드라이버가 6.18 API(`devm_drm_panel_alloc`, `mipi_dsi_*_multi`, `drm_connector_helper_get_modes_fixed`)로 어떻게 생기는지. 장치가 없어서 **로드·probe는 하지 않았고, `make -C /var/lab/out/linux-build-sub M=$PWD`로 빌드만 확인**했다.

```c
// i8_panel.c (1/2) — 가상의 720x1280 MIPI-DSI 패널 드라이버 뼈대 (빌드만 확인, 장치 없음)
#include <linux/module.h>
#include <linux/delay.h>
#include <linux/gpio/consumer.h>
#include <linux/regulator/consumer.h>
#include <drm/drm_mipi_dsi.h>
#include <drm/drm_modes.h>
#include <drm/drm_panel.h>
#include <drm/drm_connector.h>
#include <drm/drm_probe_helper.h>
#include <linux/mod_devicetable.h>

struct i8p { struct drm_panel panel; struct mipi_dsi_device *dsi;
	     struct regulator *vdd; struct gpio_desc *reset; };
static const struct drm_display_mode i8p_mode = {
	.clock = 62000, .hdisplay = 720, .hsync_start = 720 + 40, .hsync_end = 720 + 40 + 10,
	.htotal = 720 + 40 + 10 + 40, .vdisplay = 1280, .vsync_start = 1280 + 16,
	.vsync_end = 1280 + 16 + 4, .vtotal = 1280 + 16 + 4 + 16, .width_mm = 62, .height_mm = 110,
};
static int i8p_prepare(struct drm_panel *p)	/* 전원 → 리셋 → 초기화 명령 → sleep out */
{
	struct i8p *ctx = container_of(p, struct i8p, panel);
	struct mipi_dsi_multi_context dsi = { .dsi = ctx->dsi };
	int ret = regulator_enable(ctx->vdd);
	if (ret) return ret;
	gpiod_set_value_cansleep(ctx->reset, 1); usleep_range(1000, 2000);
	gpiod_set_value_cansleep(ctx->reset, 0); msleep(20);
	mipi_dsi_dcs_exit_sleep_mode_multi(&dsi);
	mipi_dsi_msleep(&dsi, 120);
	mipi_dsi_dcs_set_display_on_multi(&dsi);
	return dsi.accum_err;
}
static int i8p_unprepare(struct drm_panel *p)
{
	struct i8p *ctx = container_of(p, struct i8p, panel);
	struct mipi_dsi_multi_context dsi = { .dsi = ctx->dsi };
	mipi_dsi_dcs_set_display_off_multi(&dsi);
	mipi_dsi_dcs_enter_sleep_mode_multi(&dsi);
	gpiod_set_value_cansleep(ctx->reset, 1);
	regulator_disable(ctx->vdd);
	return 0;
}
static int i8p_get_modes(struct drm_panel *p, struct drm_connector *c)
{
	return drm_connector_helper_get_modes_fixed(c, &i8p_mode);	/* EDID 대신 고정 모드 1개 */
}
```

```c
// i8_panel.c (2/2) — panel funcs, probe/remove, DSI 드라이버 등록
static const struct drm_panel_funcs i8p_funcs = {
	.prepare = i8p_prepare, .unprepare = i8p_unprepare, .get_modes = i8p_get_modes,
};
static int i8p_probe(struct mipi_dsi_device *dsi)
{
	struct i8p *ctx = devm_drm_panel_alloc(&dsi->dev, struct i8p, panel, &i8p_funcs,
					       DRM_MODE_CONNECTOR_DSI);
	if (IS_ERR(ctx)) return PTR_ERR(ctx);
	ctx->dsi = dsi;
	ctx->vdd = devm_regulator_get(&dsi->dev, "vdd");
	if (IS_ERR(ctx->vdd)) return PTR_ERR(ctx->vdd);
	ctx->reset = devm_gpiod_get(&dsi->dev, "reset", GPIOD_OUT_HIGH);
	if (IS_ERR(ctx->reset)) return PTR_ERR(ctx->reset);
	dsi->lanes = 4; dsi->format = MIPI_DSI_FMT_RGB888;
	dsi->mode_flags = MIPI_DSI_MODE_VIDEO | MIPI_DSI_MODE_VIDEO_BURST;
	mipi_dsi_set_drvdata(dsi, ctx);
	drm_panel_add(&ctx->panel);
	return mipi_dsi_attach(dsi);	/* DSI 호스트(encoder/bridge)에 붙는다 */
}
static void i8p_remove(struct mipi_dsi_device *dsi)
{
	struct i8p *ctx = mipi_dsi_get_drvdata(dsi);
	mipi_dsi_detach(dsi);
	drm_panel_remove(&ctx->panel);
}
static const struct of_device_id i8p_of[] = { { .compatible = "i8,demo-720p-dsi" }, { } };
MODULE_DEVICE_TABLE(of, i8p_of);
static struct mipi_dsi_driver i8p_driver = {
	.probe = i8p_probe, .remove = i8p_remove,
	.driver = { .name = "i8_panel", .of_match_table = i8p_of },
};
module_mipi_dsi_driver(i8p_driver);
MODULE_LICENSE("GPL");
```

- 경고 없이 빌드되었다. 첫 시도는 `drm_connector_helper_get_modes_fixed()`(헤더 `drm_probe_helper.h`)와 `struct of_device_id`(`mod_devicetable.h`) 선언이 없어서 실패했다 — 헤더를 추가해서 고쳤다.
- `prepare`/`unprepare`는 **전원 시퀀스**다: regulator → reset 펄스 → DCS 명령(`exit_sleep_mode` 후 120 ms 대기 → `display_on`). 실제 패널은 여기에 데이터시트의 초기화 레지스터 테이블(벤더 DCS 명령 수십 개)이 들어간다. Don이 펌웨어에서 RF 칩 전원·리셋 시퀀스를 짜던 일과 같다(H3 regulator, H4 GPIO).
- `_multi` 계열 DSI 함수는 6.x에서 들어온 패턴으로, 명령마다 에러를 검사하는 대신 컨텍스트에 첫 에러를 모아 두고(`accum_err`) 이후 명령은 건너뛴다.
- 모드는 EDID가 아니라 코드의 `drm_display_mode` 하나다(§4의 modeline과 같은 필드). panel-simple 드라이버는 이런 표를 수백 개 패널에 대해 갖고 있다.
- `module_mipi_dsi_driver()`: 이 드라이버는 platform이 아니라 **MIPI DSI 버스**의 장치 드라이버다. DT에서 DSI 호스트 노드의 자식으로 `compatible = "i8,demo-720p-dsi"` 노드를 두면 DSI 호스트 드라이버가 그 자식을 `mipi_dsi_device`로 만들어 이 probe를 부른다(G 모듈의 버스/드라이버 매칭).

```
    drm_mode_atomic_ioctl()                     drivers/gpu/drm/drm_atomic_uapi.c

        drm_atomic_set_property()  -> plane/crtc/connector state duplicated into drm_atomic_state
```

핵심 자료구조:

| 구조체 | 무엇 | 어디서 다시 만나나 |
|---|---|---|
| `struct drm_device` | DRM 장치 하나 (`card`/`renderD`/`accel` 노드의 주인) | 모든 DRM/accel 드라이버의 probe |
| `struct drm_file` | 열린 fd 하나: GEM handle 테이블(idr), 이벤트 큐, master 여부, client cap | `drm_open`, ioctl 권한 |
| `struct drm_gem_object` | 버퍼 객체, `dma_buf` 연결, `dma_resv`(fence) | GEM 헬퍼, PRIME (H9 §11) |
| `struct drm_framebuffer` | GEM 객체 + 포맷 + pitch/offset | `ADDFB2`, plane state |
| `struct drm_plane_state` / `drm_crtc_state` / `drm_connector_state` | 객체별 atomic 상태 (속성 값의 커널 쪽 사본) | 드라이버의 `atomic_check`/`atomic_update` |
| `struct drm_atomic_state` | 한 요청에 엮인 모든 새 상태 묶음 | commit_tail |
| `struct drm_pending_vblank_event` | 이벤트 하나 (user_data 포함) | `drm_crtc_send_vblank_event()` |
| `struct dma_fence` / `sync_file` | 완료 신호 / 그 fd 표현 | GPU·NPU submit, IN/OUT fence |

드라이버를 쓸 때 다시 만나는 곳:

- **G 모듈**: DRM 드라이버도 platform/PCI/DSI 버스 드라이버다. 여러 블록(LCDIF, DSI, bridge)을 하나의 `drm_device`로 묶을 때는 **component framework**(`component_master_add_with_match`)를 쓴다 — 모든 부품이 probe된 뒤 bind.
- **F 모듈**: vblank IRQ는 hard IRQ 컨텍스트에서 `drm_crtc_handle_vblank()`를 부르고, commit_tail은 워크큐(F7)에서 돈다. `atomic_update`에서 잠들면 안 되는 드라이버(레지스터 shadow가 vblank 안에 써져야 하는 하드웨어)는 이 경계를 지킨다.
- **F10 / H9**: 스캔아웃 버퍼 할당 = `drm_gem_dma_helper`(→ `dma_alloc_coherent` → CMA), import = `dma_buf_map_attachment`.
- **I5**: 카메라 버퍼의 `VIDIOC_EXPBUF` → 이 노트의 `PRIME_FD_TO_HANDLE`.

## 14. Embedded 실무에서 다시 보기

### 14.1 센서 키트의 HMI 화면 bring-up 순서

예를 들어 센서 키트에 7인치 MIPI-DSI 패널을 붙인다면, 화면이 안 나올 때 이 순서로 좁힌다.

1. **드라이버가 다 probe되었나**: `ls /sys/class/drm`에 `card0-DSI-1`이 있나. 없으면 `cat /sys/kernel/debug/devices_deferred`로 `-EPROBE_DEFER`에 걸린 블록(패널 regulator, bridge I2C, DSI PHY 클럭)을 찾는다(G 모듈).
2. **connector가 connected이고 모드가 있나**: `cat /sys/class/drm/card0-DSI-1/{status,modes}`. 패널 드라이버의 `get_modes`가 모드를 주는지.
3. **모드가 걸렸나**: `cat /sys/kernel/debug/dri/0/state`에서 CRTC `active=1`, plane에 fb가 있나(§5.2).
4. **타이밍·클럭**: `/sys/kernel/debug/clk/clk_summary`로 실제 픽셀 클럭이 모드의 `clock`과 맞는지(§4.4).
5. **링크**: DSI 레인 수(`data-lanes`, `dsi->lanes`), 비디오 모드 플래그(burst/sync pulse), 패널 초기화 시퀀스. 이 단계부터는 scope로 DSI 클럭 레인을 보는 Don의 영역이다.
6. **픽셀 경로**: 화면은 나오는데 색이 이상하면 포맷(XRGB vs XBGR, RGB565)과 `drm.debug=0x14`로 plane 설정을 확인한다. writeback/CRC를 지원하는 SoC면 §8처럼 숫자로 검증한다.

### 14.2 카메라 프리뷰 + NPU 추론을 복사 없이

카메라(V4L2) 버퍼를 dma-buf로 내보내 (a) 디스플레이 overlay plane에 NV12 그대로 올리고 (b) 같은 fd를 NPU 런타임에 넘긴다(§10.3). 체크할 것: overlay plane의 포맷 목록(§3.4), pitch 정렬, importer가 IOMMU 없이 연속 메모리를 요구하는지(그러면 V4L2 쪽 `vb2_dma_contig` + CMA), 그리고 프레임 수명 — 디스플레이가 flip 이벤트를 주기 전에 그 버퍼를 `VIDIOC_QBUF`로 돌려주면 화면에 다음 프레임이 섞여 들어간다.

### 14.3 부팅 로고와 첫 화면 시간

부팅 로고는 U-Boot가 그린 프레임 버퍼를 커널이 이어받거나(simplefb/simpledrm), 커널 fbdev 에뮬레이션이 그린다(§5.4). 제품 요구가 "전원 인가 후 2초 안에 후방 카메라 화면"이라면, 디스플레이 드라이버를 built-in으로 만들고(모듈 로딩 지연 제거), fbdev 콘솔을 끄고, 앱이 atomic commit 한 번으로 첫 화면을 건다. 화면 깜빡임 없이 이어받으려면 같은 모드를 다시 거는 commit이 `mode_changed=0`이 되도록 하는 것이 핵심이다(§7.3의 "requires full modeset"을 피한다).

### 14.4 헤드리스 CI에서 디스플레이 회귀 테스트

모니터 없는 CI 랙에서 컴포지터·UI 앱의 회귀를 잡으려면 vkms를 올리고, 앱을 실행한 뒤 writeback으로 프레임을 받아 기준 이미지와 비교하거나 CRC만 비교한다(§8). 커널 쪽은 IGT(`kms_*` 테스트)가 같은 방법을 쓴다.

## 16. 면접에서 이렇게 말한다

**Q.** Explain the KMS object model: planes, CRTCs, encoders, connectors.

**A.** framebuffer는 GEM 버퍼에 포맷과 pitch를 붙인 것이고, plane은 그 fb의 소스 영역을 화면의 어디에 놓을지 정하는 스캔아웃 레이어다. CRTC는 자기 plane들을 합성하고 모드 타이밍대로 픽셀을 내보내는 타이밍 생성기, encoder는 그 스트림을 TMDS·DSI·LVDS 같은 링크 신호로 바꾸고, connector는 물리 출력 포트로 연결 상태·EDID·모드 목록을 갖는다. 임베디드에서는 encoder 뒤에 bridge 체인과 panel이 커널 안에만 있는 객체로 붙는다.

> A framebuffer is a GEM buffer plus format and pitch. A plane is a scanout layer that takes a source rectangle from a framebuffer and places it on the screen. A CRTC blends its planes and generates the timing for a mode — it's the scanout engine, and it raises vblank. An encoder converts the pixel stream into a link signal like TMDS, DSI or LVDS, and a connector is the physical output with its connection status, EDID and mode list. On SoCs there's usually a chain of bridges and a panel behind the encoder, which are kernel-internal objects — userspace only sees up to the connector.

**꼬리 질문**: "possible_crtcs는?" — plane·encoder가 붙을 수 있는 CRTC의 **인덱스** 비트마스크다. id가 아니다.

**Q.** What problem does atomic modesetting solve? What do TEST_ONLY and ALLOW_MODESET do?

**A.** legacy API는 객체마다 따로 바꿔서 중간 상태가 화면에 나오고, 조합이 되는지 미리 알 수 없었다. atomic은 여러 객체의 속성을 한 요청으로 보내고, 커널이 새 상태 전체를 atomic_check로 검증한 뒤 같은 vblank에 한꺼번에 적용한다 — 전부 아니면 전무. TEST_ONLY는 검증만 하고 아무것도 바꾸지 않아서 컴포지터가 "이 창을 overlay에 올릴 수 있나"를 물어볼 때 쓴다. ALLOW_MODESET은 화면이 깜빡일 수 있는 모드·라우팅 변경을 명시적으로 허락하는 플래그다.

> Legacy modesetting changed one object per ioctl, so intermediate states could reach the screen and you couldn't know in advance whether a combination of planes would work. Atomic sends properties for many objects in one request; the kernel builds a complete new state, validates it in atomic_check, and applies it all at the next vblank or not at all. TEST_ONLY runs the check without touching hardware — compositors use it every frame to decide which surfaces can go on hardware planes. ALLOW_MODESET explicitly permits changes that may blank the screen, like a new mode or routing; without it the kernel returns EINVAL with "requires full modeset". In my lab I saw exactly that, and drm.debug 0x10 gave the reason for each rejection.

**꼬리 질문**: "atomic_check에서 하드웨어를 써도 되나?" — 안 된다. TEST_ONLY가 부작용 없어야 하고, check를 통과한 상태는 commit에서 실패하면 안 된다.

**Q.** How do page flips and vblank events work? How would you detect dropped frames?

**A.** 버퍼 두 개를 두고 뒤 버퍼에 그린 뒤 flip을 요청하면 드라이버가 vblank에 스캔아웃 주소를 바꾸고, DRM fd로 타임스탬프와 vblank 시퀀스가 담긴 이벤트를 보낸다. 앞 flip이 끝나기 전에 또 요청하면 EBUSY. 놓친 프레임은 이벤트 시퀀스 번호가 2 이상 뛰는 것으로 센다. 실제로 vkms에서 640x480을 30~240 Hz로 바꿔 가며 쟀더니 평균 간격이 모드 계산값과 일치했고, 144 Hz에서 240프레임 중 4번 놓쳤다.

> You render into a back buffer and request a flip with an event. The driver latches the new address at vblank and sends a flip-complete event on the DRM fd with the vblank timestamp and sequence number. A second flip before the first completes returns EBUSY. To detect dropped frames I compare consecutive sequence numbers — a jump of more than one is a missed vblank — and I use the event timestamps, not wakeup times. On vkms I measured flip intervals at 30 to 240 Hz; they matched htotal times vtotal over pixel clock to the microsecond, and at 144 Hz four of 240 frames were missed under emulation.

**Q.** What is the difference between /dev/dri/card0, renderD128 and /dev/accel/accel0?

**A.** card는 primary 노드로 KMS와 GEM 전부, 화면 변경은 DRM master 한 명만 가능하다. render 노드는 GEM과 명령 제출만 되고 KMS·master ioctl은 EACCES라서 GPU 계산만 하는 앱이 권한 문제 없이 쓴다. accel은 6.2에 생긴 NPU용 DRM 갈래로, DRIVER_COMPUTE_ACCEL 드라이버가 같은 GEM·스케줄러·dma-buf 인프라를 쓰되 /dev/accel 노드 하나만 노출한다. 6.18에는 ivpu, habanalabs, qaic, amdxdna, 그리고 Rockchip NPU용 rocket이 있다.

> card is the primary node: full KMS plus GEM, and only the DRM master — usually the compositor — can change the display. renderD nodes expose only buffer management and command submission; KMS and master ioctls return EACCES, so compute and rendering clients don't need display privileges. accel is the DRM branch for NPUs added in 6.2: drivers set DRIVER_COMPUTE_ACCEL and get a /dev/accel/accelN node, reusing GEM, dma-buf, fences and the GPU scheduler without any display concepts. In 6.18 there are ivpu, habanalabs, qaic, amdxdna and rocket for Rockchip NPUs.

**꼬리 질문**: "왜 NPU를 misc device로 안 만드나?" — 메모리 관리·스케줄러·fence·dma-buf 공유·fdinfo 사용량 통계를 처음부터 다시 만들 이유가 없고, 리뷰어가 같은 패턴을 기대한다.

**Q.** How would you get camera frames onto the display with zero copies?

**A.** V4L2에서 VIDIOC_EXPBUF로 각 버퍼의 dma-buf fd를 받고, DRM에서 PRIME_FD_TO_HANDLE과 ADDFB2로 framebuffer를 미리 만든다. 프레임이 오면 그 fb를 overlay plane의 FB_ID로 nonblocking atomic commit하고, flip 이벤트가 오면 이전 버퍼를 카메라 큐에 돌려준다. 조건은 plane이 그 포맷(NV12 등)과 pitch를 받는지, 그리고 디스플레이가 IOMMU가 없다면 버퍼가 물리 연속인지다. 랩에서는 virtio-gpu 버퍼를 vkms에 import해서 writeback으로 같은 픽셀이 나오는 것을 확인했다.

> Export each V4L2 buffer with VIDIOC_EXPBUF, import the fds into DRM with PRIME_FD_TO_HANDLE, and create framebuffers up front with ADDFB2. When a frame is dequeued, do a nonblocking atomic commit setting the overlay plane's FB_ID, and requeue the previous buffer only after the flip event. Constraints: the plane must support the format and pitch, and if the display engine has no IOMMU the buffer must be physically contiguous, which pushes the camera side to dma-contig and CMA. In my lab I exported a virtio-gpu buffer, imported it into vkms, scanned it out and verified through writeback that the pixels matched, including one I modified through the dma-buf mmap.

**꼬리 질문**: "GPU가 아직 쓰는 중이면?" — implicit sync(dma_resv fence를 importer가 기다림) 또는 explicit sync(GPU out-fence를 plane `IN_FENCE_FD`로).

**Q.** You bring up a new MIPI-DSI panel and the screen stays black. How do you debug it?

**A.** 위에서부터 내려간다. 모든 블록이 probe되었는지(devices_deferred), connector가 connected이고 모드가 있는지, debugfs state에서 CRTC가 active이고 plane에 fb가 있는지, 실제 픽셀 클럭이 맞는지(clk_summary), 그다음 링크 — 레인 수, 비디오 모드 플래그, 패널 전원·리셋·초기화 시퀀스 타이밍. 마지막은 scope로 DSI 클럭 레인과 LP/HS 전환을 본다. writeback이나 CRC가 있는 SoC면 컨트롤러까지는 맞는지 숫자로 먼저 확인해 문제를 링크 쪽으로 좁힌다.

> I go top-down. Are all components probed — check devices_deferred for a panel regulator or bridge stuck in probe defer. Is the connector connected with modes? Does debugfs state show the CRTC active with a framebuffer on the plane? Does clk_summary show the pixel clock the mode asks for? Then the link: lane count in DT versus the driver, video mode flags, and the panel's power, reset and init-sequence timing against the datasheet. Finally a scope on the DSI clock lane for LP-to-HS transitions. If the SoC has writeback or CRC, I first prove the controller output is right, which isolates the problem to the link or panel.

## 17. 직접 해보기

1. (개념) 1920x1080@60 모드(`clock 148500`, `htotal 2200`, `vtotal 1125`)의 프레임 시간과 vblank 구간 길이(ms)를 계산하라.
   정답/힌트: 2200 × 1125 / 148.5 MHz = 16.667 ms. vblank = (1125 - 1080) × 2200 / 148.5 MHz ≈ 0.667 ms.
2. (코드) `i8_flip`에 "그리기 시간" 인자를 추가해 각 프레임마다 `usleep()`으로 N ms 지연을 넣고, 60 Hz에서 N = 10, 17, 25일 때 fps와 `skipped_vblanks`를 측정하라.
   정답/힌트: 17 ms를 넘기면 매 프레임 한 vblank를 놓쳐 약 30 fps가 되는 것이 예상된다(직접 확인할 것).
3. (코드) `i8_wb`의 overlay에 `CRTC_W/H`를 원래 크기의 2배로 줘서 스케일링을 시도하라. vkms가 받아들이나? 거절한다면 로그는?
   정답/힌트: `drm.debug=0x10`으로 plane check 로그를 본다. vkms plane check의 스케일 허용 범위를 `vkms_plane.c`에서 확인.
4. (관찰) vkms를 `enable_cursor=0 enable_writeback=0`으로 올렸을 때 예제 3과 예제 2의 출력이 어떻게 바뀌는지 예측하고 확인하라.
   정답/힌트: cursor plane과 Writeback-1 connector, 그 encoder가 사라진다.
5. (코드) `i8_atomic`에 CRTC `ACTIVE=0`만 보내는 commit을 추가해 화면을 끄고, debugfs state의 `active`, `enable` 값을 비교하라. `ALLOW_MODESET`이 필요한가?
   정답/힌트: active 변경은 full modeset이므로 필요하다. `enable=1 active=0`(DPMS off에 해당)이 된다.
6. (PRIME) `i8_prime`에서 import 방향을 바꿔 vkms dumb buffer를 virtio-gpu로 import해 보라. 되는가? virtio-gpu의 import 경로(`virtgpu_prime.c`)를 읽고 이유를 설명하라.
   정답/힌트: 직접 확인할 것. virtio-gpu의 외부 dma-buf import 지원 범위는 커널 버전과 기능 비트(blob 등)에 따라 다르다.
7. (accel) `rocket_accel.h`의 `drm_rocket_job`에서 `in_bo_handles`와 `out_bo_handles`를 나눈 이유를 `gpu-sched`의 의존성 관점에서 설명하라.
   정답/힌트: §11.3. 쓰기 BO에는 `DMA_RESV_USAGE_WRITE`, 읽기 BO에는 `DMA_RESV_USAGE_READ` 용도의 fence가 붙어(기억 기반 — rocket 소스에서 확인할 것) 다음 job의 순서가 자동으로 정해진다.

## 18. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| DRM | Direct Rendering Manager | GPU·디스플레이·NPU를 다루는 커널 서브시스템 |
| KMS | Kernel Mode Setting | 커널이 화면 모드·스캔아웃을 제어하는 DRM의 디스플레이 부분 |
| framebuffer | 프레임 버퍼 객체 | GEM 버퍼 + 포맷 + pitch, `ADDFB2`로 생성 |
| plane | 스캔아웃 레이어 | primary / overlay / cursor, fb의 영역을 화면에 배치 |
| CRTC | 스캔아웃 엔진 | plane 합성 + 타이밍 생성 + vblank |
| encoder | 링크 변환기 | 픽셀 스트림 → TMDS/DSI/LVDS |
| connector | 출력 포트 | 연결 상태, EDID, 모드 목록 |
| bridge | 외부 변환 블록 | encoder 뒤 체인, 커널 내부 객체 |
| panel | 고정 패널 | 전원 시퀀스 + 고정 모드 (`drm_panel`) |
| mode / modeline | 디스플레이 타이밍 | hdisplay·porch·sync·total·픽셀 클럭 |
| EDID | 모니터 정보 블록 | DDC(I2C 0x50)로 읽는 128바이트 단위 데이터 |
| vblank | 수직 귀선 구간 | 프레임 사이 빈 줄, flip이 반영되는 순간 |
| page flip | 버퍼 교체 | vblank에 스캔아웃 버퍼를 바꿈 |
| atomic commit | 원자적 적용 | 속성 묶음을 검사 후 한 번에 반영 |
| TEST_ONLY | 검사 전용 플래그 | 상태를 바꾸지 않고 가능 여부만 확인 |
| ALLOW_MODESET | 모드 변경 허락 플래그 | 화면이 깜빡일 수 있는 변경을 허용 |
| property | 속성 | 객체의 설정 값 (range/enum/blob/object) |
| dumb buffer | CPU용 스캔아웃 버퍼 | 드라이버 무관 공통 ioctl, GPU 가속용 아님 |
| GEM | 버퍼 객체 관리자 | fd별 handle, mmap 오프셋, PRIME |
| PRIME | DRM의 dma-buf 공유 | handle ↔ dma-buf fd 변환 |
| render node | `renderD12x` | GEM + submit만, KMS 없음 |
| DRM master | 화면 소유자 | KMS를 바꿀 수 있는 유일한 fd |
| fbdev emulation | `/dev/fb0` 호환 | DRM 내장 클라이언트가 만든 레거시 인터페이스 |
| writeback connector | 메모리 출력 | 합성 결과를 버퍼로 캡처 |
| CRC | 프레임 체크섬 | debugfs로 보는 프레임별 출력 CRC |
| sync_file / dma_fence | 완료 신호 | fd로 표현된 fence, IN/OUT fence |
| drm/accel | NPU용 DRM 갈래 | `/dev/accel/accelN`, `DRIVER_COMPUTE_ACCEL` |
| vkms | 가상 KMS 드라이버 | 하드웨어 없는 테스트용 디스플레이 |

## 19. 요약 & 체크리스트

DRM은 화면을 내는 KMS, GPU 계산용 render/GEM, NPU용 accel의 세 갈래이고, 그 사이 버퍼 공유는 dma-buf(PRIME)가 맡는다. KMS는 디스플레이 하드웨어를 framebuffer → plane → CRTC → encoder(→ bridge → panel) → connector 객체로 모델링하고, 모든 설정을 속성으로 표현한다. legacy API는 객체마다 따로 바꾸지만 atomic은 속성 묶음을 검사(`atomic_check`, `TEST_ONLY`)한 뒤 한 vblank에 전부 적용하며, 모드 변경은 `ALLOW_MODESET`으로 허락하고, 비동기 commit의 완료는 flip 이벤트와 out-fence로 받는다. dumb buffer로 CPU가 그린 화면을 걸 수 있고, vkms의 writeback·CRC로 모니터 없이 합성 결과를 픽셀 단위로 검증할 수 있다. 드라이버는 helper vtable(plane/CRTC/connector `atomic_*`)을 채우고, 임베디드에서는 DT의 ports/endpoints로 bridge·panel 체인을 잇는다.

- [ ] DRM의 세 갈래(KMS, render, accel)와 각 노드(`card`, `renderD`, `accel`)의 권한 차이를 설명할 수 있다
- [ ] framebuffer, plane, CRTC, encoder, bridge, panel, connector의 역할과 관계(`possible_crtcs` 비트마스크)를 그릴 수 있다
- [ ] modeline을 읽고 프레임 시간을 `htotal × vtotal / clock`으로 계산할 수 있다
- [ ] libdrm 없이 ioctl로 리소스를 나열하고 dumb buffer를 만들어 `SETCRTC`로 화면에 걸 수 있다
- [ ] page flip + vblank 이벤트 루프를 짜고 이벤트 시퀀스로 놓친 프레임을 셀 수 있다
- [ ] atomic 요청을 만들어 `TEST_ONLY`, `ALLOW_MODESET`, `NONBLOCK`, out-fence를 쓸 수 있고, `drm.debug`로 거절 이유를 읽을 수 있다
- [ ] debugfs `state`·`crc`와 sysfs connector 파일로 디스플레이 상태를 진단할 수 있다
- [ ] writeback connector로 합성 결과를 캡처해 알파 블렌딩까지 검증할 수 있다
- [ ] GEM handle과 dma-buf fd의 차이, PRIME export/import, implicit/explicit sync를 설명할 수 있다
- [ ] 카메라 → 디스플레이/NPU zero-copy 파이프라인의 단계와 제약(포맷, pitch, 연속 메모리)을 말할 수 있다
- [ ] KMS 드라이버의 helper 콜백과 "check에서는 HW를 건드리지 않는다" 규칙을 설명하고, DSI 패널 드라이버 뼈대를 쓸 수 있다
- [ ] drm/accel의 존재 이유와 6.18의 accel 드라이버, rocket uAPI의 BO/submit 모델을 설명할 수 있다
