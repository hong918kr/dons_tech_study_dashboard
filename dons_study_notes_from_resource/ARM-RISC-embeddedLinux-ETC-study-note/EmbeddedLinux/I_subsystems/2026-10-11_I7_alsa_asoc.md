# I7. ALSA / ASoC — PCM, period/buffer, codec·platform·machine, DAPM

> **이 노트를 다 읽으면**: ALSA의 card·device·substream과 `/dev/snd/pcmC0D0p` 같은 노드를 읽고, alsa-lib 없이 PCM ioctl(`HW_PARAMS`·`SW_PARAMS`·`PREPARE`·`WRITEI_FRAMES`·`STATUS`)만으로 소리를 내고 받을 수 있다 · 링버퍼의 `hw_ptr`/`appl_ptr`/`avail`, period 인터럽트, underrun/overrun(XRUN)과 복구를 측정값으로 설명할 수 있다 · `snd_pcm_ops`(open/hw_params/prepare/trigger/pointer)와 mixer control을 가진 PCM 드라이버를 직접 짜서 돌릴 수 있다 · ASoC의 codec / CPU DAI·platform / machine 분리, simple-audio-card DT, I2S의 BCLK·LRCLK·MCLK 계산, DAPM 전원 관리를 실제 카드로 보여 줄 수 있다
> **왜 필요한가**: 음성 웨어러블·로봇의 마이크 어레이와 스피커는 거의 전부 "SoC의 I2S/TDM/PDM 컨트롤러 + DMA + I2C로 제어하는 codec"이고, 리눅스에서는 그것이 ASoC 카드 하나로 보인다. "소리가 안 나요", "가끔 틱 소리가 나요(xrun)", "마이크 레이턴시가 길어요"를 디버깅하려면 이 노트의 모델이 그대로 필요하다
> **Don 기준 난이도**: I2S/DMA 핑퐁 버퍼, 링버퍼 head/tail, DMA 완료 인터럽트, I2C 레지스터 설정은 이미 아는 것이다 / 새로 배울 것은 그것을 **ALSA가 부르는 이름**(period, `hw_ptr`, `appl_ptr`, `snd_pcm_period_elapsed`), 유저와 커널 사이의 **파라미터 협상**(hw_params refine), ASoC가 한 보드를 **세 드라이버로 쪼개는 이유**와 DAPM
> **선행 노트**: F(인터럽트 컨텍스트, hrtimer, spinlock), G2·G3(platform driver, probe), G5(ioctl·mmap), H3(clk·regulator), H5(I2C — codec 제어), H9(DMA, dmaengine cyclic) — I1(프레임워크 원칙)의 "ops 구조체에 등록" 패턴이 여기서 그대로 나온다

## 0. 큰 그림 — 이게 왜 필요한가

Don이 bare-metal에서 오디오를 다뤘다면 아마 이런 코드였을 것이다. I2S 컨트롤러를 48 kHz, 16비트 스테레오로 설정하고, DMA를 **순환(circular) 모드**로 걸어서 메모리의 버퍼 두 개(핑퐁)를 번갈아 I2S TX FIFO로 밀어 넣는다. 반쪽이 끝날 때마다 "half-transfer" 인터럽트가 오면, 그동안 다 쓴 반쪽에 다음 오디오를 채운다. 늦게 채우면 스피커에서 "틱" 소리가 난다. codec(DAC 칩)은 I2C로 레지스터를 써서 전원을 켜고 볼륨을 맞춘다.

ALSA(Advanced Linux Sound Architecture)는 정확히 이 구조에 이름을 붙이고, 여러 앱이 같은 장치를 표준 방식으로 쓰게 만든 것이다.

- 핑퐁의 "반쪽" → **period**. 버퍼는 period 여러 개로 된 **링버퍼**다.
- half-transfer 인터럽트 → **period interrupt**, 드라이버는 거기서 `snd_pcm_period_elapsed()`를 부른다.
- "DMA가 지금 어디를 읽고 있나" → **`hw_ptr`** (드라이버의 `.pointer` 콜백이 알려 준다).
- "앱이 어디까지 채웠나" → **`appl_ptr`**.
- 늦게 채워서 나는 틱 소리 → **underrun (XRUN)**. 캡처에서는 앱이 늦게 읽어서 덮어쓰이는 **overrun**.
- I2S 컨트롤러 + DMA 드라이버, I2C codec 드라이버, 둘을 묶는 보드 설정 → **ASoC**의 CPU DAI·platform / codec / machine.

## 1. ALSA 장치 모델 — card · device · substream

### 1.1 직관 — "사운드 카드 = 장치 묶음"

ALSA의 단위는 **card**다. 한 card는 물리적으로 한 오디오 하드웨어(USB 헤드셋 하나, SoC의 오디오 서브시스템 하나)이고, 그 안에 여러 **device**가 있다. PCM device는 재생(playback)과 캡처(capture) 두 **stream**을 가질 수 있고, 각 stream에는 동시에 열 수 있는 **substream**(하드웨어 채널)이 하나 이상 있다. 그리고 card마다 **control** 장치 하나가 mixer 설정(볼륨, 스위치, 경로 선택)을 전부 맡는다.

| 노드 | 뜻 | 주 번호 | 드라이버 쪽 구조체 |
|---|---|---|---|
| `/dev/snd/controlC0` | card 0의 control (mixer, 카드 정보) | 116 | `struct snd_card`, `struct snd_kcontrol` |
| `/dev/snd/pcmC0D0p` | card 0, device 0, **p**layback | 116 | `struct snd_pcm`, `snd_pcm_substream` |
| `/dev/snd/pcmC0D0c` | card 0, device 0, **c**apture | 116 | 위와 같음 |
| `/dev/snd/timer` | ALSA 타이머 (전역) | 116 | `snd_timer` |

모든 노드가 주 번호 116을 공유하고, 부 번호로 구분된다(`CONFIG_SND_DYNAMIC_MINORS=y`라 부 번호는 등록 순서대로 붙는다). 유저 공간 이름 `hw:0,0`은 "card 0, device 0"을 뜻하는 alsa-lib의 이름이다.

### 1.3 `/proc/asound` 지도

| 경로 | 내용 | 언제 보나 |
|---|---|---|
| `/proc/asound/cards` | 등록된 card 목록과 id | "카드가 아예 안 뜬다" (probe 실패, DT 문제) |
| `/proc/asound/pcm` | 모든 PCM device와 substream 수 | 장치 번호 확인 |
| `/proc/asound/cardN/pcmXp/info` | 이름, substream 수, 사용 중 수 | 누가 장치를 잡고 있나 |
| `/proc/asound/cardN/pcmXp/subY/hw_params` | 지금 협상된 포맷·rate·period·buffer | "왜 44.1k로 열렸지?" |
| `/proc/asound/cardN/pcmXp/subY/sw_params` | start/stop threshold, avail_min | xrun 원인 분석 |
| `/proc/asound/cardN/pcmXp/subY/status` | state, `hw_ptr`, `appl_ptr`, avail, delay | 지금 스트림이 도는지, 포인터가 움직이는지 |

이 표의 마지막 세 파일이 오디오 버그의 1차 증거다. 소리가 안 날 때 `status`의 `hw_ptr`가 움직이면 "DMA는 돈다 → 문제는 codec·경로·전원(DAPM)", 안 움직이면 "DMA/인터럽트/클럭 문제"로 반을 가를 수 있다.

## 2. hw_params — 포맷 · rate · 채널 · period · buffer

### 2.1 정의

PCM 스트림을 쓰기 전에 앱과 드라이버는 다음을 합의해야 한다. 이것이 **hw_params**다.

| 파라미터 | 뜻 | 예 |
|---|---|---|
| access | 데이터 전달 방식: `RW_INTERLEAVED`(write/read 복사) 또는 `MMAP_INTERLEAVED`(링버퍼를 mmap) | `RW_INTERLEAVED` |
| format | 샘플 형식 | `S16_LE` = 부호 있는 16비트 little-endian |
| channels | 채널 수 | 2 (스테레오), 마이크 어레이면 4·6·8 |
| rate | 초당 frame 수 | 48000, 음성 인식은 16000 |
| period_size | 인터럽트 한 번당 frame 수 | 1024 |
| periods | 버퍼 안 period 개수 | 4 |
| buffer_size | period_size × periods (frame) | 4096 |

용어 하나: **frame** = 한 시점의 모든 채널 샘플 묶음. `S16_LE` 스테레오면 1 frame = 2 채널 × 2바이트 = 4바이트. ALSA의 크기 단위는 대부분 frame이다.

계산 몇 개를 바로 해 두자. 48 kHz, S16_LE, 2ch에서

- 데이터율 = 48000 × 4 B = 192 kB/s
- period 1024 frame = 4096 B = 21.3 ms → 초당 인터럽트 약 47번
- buffer 4096 frame = 16 KiB = **85.3 ms** — 재생에서 앱이 최대 85 ms 늦어도 버틴다. 동시에 "지금 쓴 샘플이 스피커에 나오기까지" 최대 85 ms 걸린다(**latency = buffer_size / rate**)

### 2.2 refine — 파라미터는 "범위"로 협상한다

hw_params 구조체(`struct snd_pcm_hw_params`)에는 값이 아니라 **범위**가 들어 있다. format·access처럼 이산적인 것은 비트 마스크(`struct snd_mask`), rate·period_size처럼 수치인 것은 구간(`struct snd_interval`, `[min, max]`와 열림/닫힘 플래그)이다. 앱이 "다 괜찮다"로 채워 `SNDRV_PCM_IOCTL_HW_REFINE`을 부르면, 커널은 드라이버의 `snd_pcm_hardware` 범위와 **규칙(rule)들**(예: `period_bytes = period_size × frame_bytes`, `buffer_size = period_size × periods`)을 반복 적용해서 범위를 좁혀 돌려준다. alsa-lib의 `snd_pcm_hw_params_set_rate_near()` 같은 함수들은 이 refine을 여러 번 부르면서 하나씩 고정해 가는 것이다. 마지막에 `HW_PARAMS`가 모든 값이 한 점으로 고정된 구조체를 받아 드라이버의 `.hw_params`를 부른다.

alsa-lib가 없으니 이 노트의 프로그램들은 아래 작은 헤더를 공유한다. `hw_any()`가 "모든 것 허용", `hw_mask()`/`hw_int()`가 "이 값 하나로 고정"이다.

```c
/* i7alsa.h — minimal ALSA PCM uAPI helpers (no alsa-lib) — 앞부분 */
#include <fcntl.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <sound/asound.h>

#define DIE(m) do { perror(m); exit(1); } while (0)
#define MASK(p, v) (&(p)->masks[(v) - SNDRV_PCM_HW_PARAM_FIRST_MASK])
#define IVAL(p, v) (&(p)->intervals[(v) - SNDRV_PCM_HW_PARAM_FIRST_INTERVAL])

static inline void hw_any(struct snd_pcm_hw_params *p)      /* "everything allowed" */
{
	memset(p, 0, sizeof(*p));
	for (int v = SNDRV_PCM_HW_PARAM_FIRST_MASK; v <= SNDRV_PCM_HW_PARAM_LAST_MASK; v++)
		memset(MASK(p, v)->bits, 0xff, sizeof(MASK(p, v)->bits));
	for (int v = SNDRV_PCM_HW_PARAM_FIRST_INTERVAL; v <= SNDRV_PCM_HW_PARAM_LAST_INTERVAL; v++)
		IVAL(p, v)->max = UINT_MAX;
	p->rmask = ~0U;
	p->info = ~0U;
}
static inline void hw_mask(struct snd_pcm_hw_params *p, int v, unsigned bit)  /* pick one */
{
	struct snd_mask *m = MASK(p, v);
	memset(m->bits, 0, sizeof(m->bits));
	m->bits[bit >> 5] = 1U << (bit & 31);
}
static inline void hw_int(struct snd_pcm_hw_params *p, int v, unsigned val)   /* min=max */
{
	struct snd_interval *i = IVAL(p, v);
	i->min = i->max = val;
	i->integer = 1;
	i->openmin = i->openmax = 0;
}
static inline unsigned hw_get(struct snd_pcm_hw_params *p, int v) { return IVAL(p, v)->min; }
static inline double now_ms(void)
{
	struct timespec t;
	clock_gettime(CLOCK_MONOTONIC, &t);
	return t.tv_sec * 1e3 + t.tv_nsec / 1e6;
}
```

`rmask`는 "다시 계산해 달라는 파라미터 비트", 커널이 돌려줄 때 `cmask`는 "바뀐 파라미터 비트"다. `info`에는 드라이버가 가진 능력 플래그(`SNDRV_PCM_INFO_*`)가 돌아온다.

```c
static const char *names[] = { "ACCESS", "FORMAT", "SUBFORMAT" };

	"PERIOD_TIME", "PERIOD_SIZE", "PERIOD_BYTES", "PERIODS",

int main(int argc, char **argv)
{
	const char *dev = argc > 1 ? argv[1] : "/dev/snd/pcmC0D0p";

	if (fd < 0) DIE("open");

	       ver >> 16, (ver >> 8) & 0xff, ver & 0xff, info.card, info.device,
	       info.subdevice, info.id, info.stream ? "CAPTURE" : "PLAYBACK");

	hw_any(&hp);

	for (int v = SNDRV_PCM_HW_PARAM_FIRST_MASK; v <= SNDRV_PCM_HW_PARAM_LAST_MASK; v++) {
		printf("%-12s bits:", names[v]);
		for (int b = 0; b < 64; b++)

				printf(" %d", b);
		printf("\n");
	}
	for (int v = SNDRV_PCM_HW_PARAM_FIRST_INTERVAL; v <= SNDRV_PCM_HW_PARAM_LAST_INTERVAL; v++) {
		struct snd_interval *i = IVAL(&hp, v);
		printf("%-12s %c%u, %u%c\n", inames[v - SNDRV_PCM_HW_PARAM_FIRST_INTERVAL],
		       i->openmin ? '(' : '[', i->min, i->max, i->openmax ? ')' : ']');
	}
	printf("info flags 0x%x  fifo_size %lu\n", hp.info, (unsigned long)hp.fifo_size);
```

### 3.2 정의

| 이름 | 누가 움직이나 | 뜻 |
|---|---|---|
| `hw_ptr` | 커널 (드라이버 `.pointer`로 계산) | 하드웨어가 소비(재생) 또는 생산(캡처)한 누적 frame 수 |
| `appl_ptr` | 앱 (`write`/`read` 또는 mmap 후 commit) | 앱이 쓴(재생) 또는 읽은(캡처) 누적 frame 수 |
| `avail` | 계산 값 | 앱이 지금 막힘 없이 쓸/읽을 수 있는 frame 수 |
| `delay` | 계산 값 (+ 드라이버의 FIFO 지연) | 지금 쓴 frame이 실제로 소리가 되기까지 남은 frame 수 |
| `boundary` | sw_params | 포인터가 0으로 돌아가는 큰 값. 64비트에서는 buffer_size의 2의 거듭제곱 배 중 `LONG_MAX` 이하 최대값 |

포인터가 "링 안의 위치"가 아니라 **누적값**이라는 점이 중요하다. 링 안 위치는 `ptr % buffer_size`다. 누적값이라서 "앱이 한 바퀴 이상 뒤처졌다(xrun)"를 판정할 수 있다. Don이 SSD 펌웨어에서 head/tail을 `2 × 큐 크기`까지 세서 full/empty를 구분했던 것과 같은 생각이다.

### 3.3 sw_params — "언제 시작하고, 언제 깨우고, 언제 멈추나"

hw_params가 하드웨어 설정이라면 **sw_params**는 커널 쪽 정책이다.

| 필드 | 뜻 | 이 노트의 값 |
|---|---|---|
| `start_threshold` | 재생: 버퍼에 이만큼 차면 자동으로 START | buffer_size (가득 차면 시작) |
| `stop_threshold` | avail이 이만큼 되면 XRUN으로 멈춤 | buffer_size (완전히 비면 xrun) |
| `avail_min` | `poll()`/블로킹 write가 깨어나는 최소 avail | period_size |
| `silence_threshold`/`silence_size` | underrun 대비 무음 자동 채우기 | 0 (끔) |
| `boundary` | 포인터 wrap 지점 | 2^62 (buffer 4096일 때) |

앱이 쓰는 순서는 alsa-lib가 하는 일 그대로다: `open` → `HW_PARAMS` → `SW_PARAMS` → `PREPARE` → `WRITEI_FRAMES` 반복 → (start_threshold 도달 시 커널이 자동 START) → `DRAIN` → `close`. 공용 헤더의 뒷부분이 이것이다.

```c
/* i7alsa.h — 뒷부분: open + S16_LE interleaved + rate/ch/period/periods; returns fd */
static inline int pcm_open(const char *dev, int capture, unsigned rate, unsigned ch,
		    unsigned period, unsigned periods)
{
	int fd = open(dev, (capture ? O_RDONLY : O_WRONLY));
	if (fd < 0) DIE("open pcm");
	struct snd_pcm_hw_params hp;
	hw_any(&hp);
	hw_mask(&hp, SNDRV_PCM_HW_PARAM_ACCESS, SNDRV_PCM_ACCESS_RW_INTERLEAVED);
	hw_mask(&hp, SNDRV_PCM_HW_PARAM_FORMAT, SNDRV_PCM_FORMAT_S16_LE);
	hw_int(&hp, SNDRV_PCM_HW_PARAM_CHANNELS, ch);
	hw_int(&hp, SNDRV_PCM_HW_PARAM_RATE, rate);
	hw_int(&hp, SNDRV_PCM_HW_PARAM_PERIOD_SIZE, period);
	hw_int(&hp, SNDRV_PCM_HW_PARAM_PERIODS, periods);
	if (ioctl(fd, SNDRV_PCM_IOCTL_HW_PARAMS, &hp) < 0) DIE("HW_PARAMS");
	struct snd_pcm_sw_params sp = {0};
	sp.tstamp_mode = SNDRV_PCM_TSTAMP_ENABLE;
	sp.period_step = 1;
	sp.avail_min = period;
	sp.start_threshold = capture ? 1 : period * periods;  /* start when buffer full */
	sp.stop_threshold = period * periods;                 /* xrun when empty/full */
	sp.boundary = period * periods;
	while (sp.boundary * 2 <= (snd_pcm_uframes_t)LONG_MAX - period * periods) sp.boundary *= 2;
	if (ioctl(fd, SNDRV_PCM_IOCTL_SW_PARAMS, &sp) < 0) DIE("SW_PARAMS");
	if (ioctl(fd, SNDRV_PCM_IOCTL_PREPARE) < 0) DIE("PREPARE");
	return fd;
}
```

### 3.4 예제 3 — 사인파를 재생하며 포인터가 움직이는 것 보기 (게스트 실행)

무엇을 확인하나: 앱이 쓰는 속도가 실제 시간(48000 frame/s)에 묶이는 것, 그리고 `STATUS` ioctl과 `/proc/.../status`가 같은 `hw_ptr`/`appl_ptr`를 보여 주는 것. 아래 프로그램은 §4의 underrun 실험(마지막 인자)과 §6의 루프백(`FREQ`, `TAIL` 환경 변수)에도 그대로 쓴다.

```c
/* i7_play.c — S16_LE stereo sine via WRITEI_FRAMES; print hw_ptr/appl_ptr */
#include "i7alsa.h"
#include <math.h>
#include <errno.h>

static const char *st[] = { "OPEN", "SETUP", "PREPARED", "RUNNING", "XRUN",
			    "DRAINING", "PAUSED", "SUSPENDED", "DISCONNECTED" };

static void show(int fd, double t0, const char *tag)
{
	struct snd_pcm_status s = {0};
	if (ioctl(fd, SNDRV_PCM_IOCTL_STATUS, &s) < 0) DIE("STATUS");
	printf("%7.1f ms %-8s state=%-8s hw_ptr=%6lu appl_ptr=%6lu avail=%5lu delay=%5ld\n",
	       now_ms() - t0, tag, st[s.state], s.hw_ptr, s.appl_ptr, s.avail, s.delay);
}

int main(int argc, char **argv)
{
	if (argc < 6) { fprintf(stderr, "usage: %s dev rate period periods ms [sleep_ms_at_1s]\n", argv[0]); return 1; }
	unsigned rate = atoi(argv[2]), period = atoi(argv[3]), periods = atoi(argv[4]);
	int total_ms = atoi(argv[5]), stall_ms = argc > 6 ? atoi(argv[6]) : 0;
	int fd = pcm_open(argv[1], 0, rate, 2, period, periods);
	short *buf = malloc(period * 4);
	double t0 = now_ms(), ph = 0, f = getenv("FREQ") ? atof(getenv("FREQ")) : 440;
	unsigned long frames = 0, target = (unsigned long)rate * total_ms / 1000;
	int stalled = 0, xruns = 0;
	show(fd, t0, "prepared");
	while (frames < target) {
		for (unsigned i = 0; i < period; i++, ph += 2 * M_PI * f / rate)
			buf[2 * i] = buf[2 * i + 1] = (short)(8000 * sin(ph));
		if (stall_ms && !stalled && frames >= rate) {   /* app "hangs" at 1 s */
			show(fd, t0, "stall");
			usleep(stall_ms * 1000);
			show(fd, t0, "woke");
			stalled = 1;
		}
		struct snd_xferi x = { .buf = buf, .frames = period };
		if (ioctl(fd, SNDRV_PCM_IOCTL_WRITEI_FRAMES, &x) < 0) {
			if (errno != EPIPE) DIE("WRITEI");
			xruns++;
			printf("%7.1f ms WRITEI -> EPIPE (underrun #%d)\n", now_ms() - t0, xruns);
			show(fd, t0, "xrun");
			if (ioctl(fd, SNDRV_PCM_IOCTL_PREPARE) < 0) DIE("PREPARE");
			show(fd, t0, "recover");
			continue;   /* rewrite same period; stream restarts at start_threshold */
		}
		frames += x.result;
		if (frames % (rate / 4) < period) show(fd, t0, "write");
	}
	if (getenv("TAIL")) {                       /* pad with silence instead of DRAIN */
		memset(buf, 0, period * 4);
		for (int i = 0; i < 8; i++) { struct snd_xferi x = { .buf = buf, .frames = period }; ioctl(fd, SNDRV_PCM_IOCTL_WRITEI_FRAMES, &x); }
	}
	if (ioctl(fd, SNDRV_PCM_IOCTL_DRAIN) < 0) DIE("DRAIN");
	show(fd, t0, "drained");
	printf("wrote %lu frames in %.1f ms, xruns=%d\n", frames, now_ms() - t0, xruns);
	return 0;
}
```

### 3.5 PCM 상태 기계

| 상태 | 들어가는 계기 | 나오는 계기 |
|---|---|---|
| `OPEN` | `open()` | `HW_PARAMS` → `SETUP` |
| `SETUP` | hw_params 설정됨 | `PREPARE` → `PREPARED` |
| `PREPARED` | 버퍼·포인터 초기화 | `START` 또는 start_threshold 도달 → `RUNNING` |
| `RUNNING` | 트리거됨, DMA 동작 | `DROP` → `SETUP`, `DRAIN` → `DRAINING`, xrun → `XRUN`, `PAUSE` |
| `XRUN` | avail ≥ stop_threshold | `PREPARE` → `PREPARED` (복구) |
| `DRAINING` | 남은 데이터 재생 중 | 버퍼 비면 → `SETUP` |
| `SUSPENDED` | 시스템 suspend | `RESUME`(드라이버가 `SNDRV_PCM_INFO_RESUME` 지원 시) 또는 `PREPARE` |

## 4. XRUN — underrun · overrun · 복구

### 4.1 정의

- **underrun** (재생): 하드웨어가 읽을 데이터가 떨어졌다. 앱이 늦게 썼다. 스피커에서 끊김·틱 소리.
- **overrun** (캡처): 하드웨어가 쓸 공간이 떨어졌다. 앱이 늦게 읽었다. 마이크 데이터가 **빠진다**(음성 인식에서 단어가 잘린다).
- 둘을 합쳐 **XRUN**이라 부른다. 커널은 period 인터럽트 때마다(그리고 앱이 포인터를 물을 때마다) `snd_pcm_update_state()`에서 판정한다. 소스는 `sound/core/pcm_lib.c:209`:

```c
/* sound/core/pcm_lib.c:209 (6.18.55) — 발췌 */
int snd_pcm_update_state(struct snd_pcm_substream *substream,
			 struct snd_pcm_runtime *runtime)
{
	snd_pcm_uframes_t avail;

	avail = snd_pcm_avail(substream);
	if (avail > runtime->avail_max)
		runtime->avail_max = avail;
	if (runtime->state == SNDRV_PCM_STATE_DRAINING) {
		if (avail >= runtime->buffer_size) {
			snd_pcm_drain_done(substream);
			return -EPIPE;
		}
	} else {
		if (avail >= runtime->stop_threshold) {
			__snd_pcm_xrun(substream);
			return -EPIPE;
		}
	}
	if (runtime->twake) {
		if (avail >= runtime->twake)
			wake_up(&runtime->tsleep);
	} else if (avail >= runtime->control->avail_min)
		wake_up(&runtime->sleep);
	return 0;
}
```

판정은 단순하다. **avail이 stop_threshold 이상이면 XRUN**, 아니면 avail_min 이상일 때 잠든 앱을 깨운다. `__snd_pcm_xrun()`(같은 파일 168행)은 스트림을 멈추고 state를 `XRUN`으로 바꾼다. 그 뒤 앱의 다음 `write`/`read`는 `-EPIPE`를 받는다. 복구는 `PREPARE`(포인터를 0으로 되돌리고 `PREPARED`로) → 다시 써서 start_threshold를 채우는 것이다. alsa-lib의 `snd_pcm_recover()`가 하는 일이 바로 이것이다.

### 4.3 캡처의 overrun은 더 조용하다

재생 underrun은 귀에 들리지만, 캡처 overrun은 **아무 소리 없이 데이터가 빠진다**. 웨이크워드 엔진이 가끔 단어를 놓치는 버그의 흔한 원인이다. 캡처 앱은 다음을 반드시 한다.

- `READI_FRAMES`가 `-EPIPE`를 돌려주면 로그를 남기고 카운트한다(조용히 PREPARE만 하면 버그가 숨는다).
- `STATUS`의 `avail_max`(마지막 STATUS 이후 최대 avail)를 주기적으로 보고, buffer_size에 가까워지면 경고한다. 예제 3의 `/proc`에 보인 `avail_max : 1082`가 그 값이다.
- 처리 스레드를 캡처 스레드와 분리하고(링버퍼 하나 더), 캡처 스레드는 `SCHED_FIFO`로 올린다(N 모듈).

## 5. period 크기 · latency · 타이밍 지터

### 5.1 period와 buffer를 고르는 법

두 숫자가 서로 다른 것을 정한다.

| 숫자 | 정하는 것 | 크게 하면 | 작게 하면 |
|---|---|---|---|
| `buffer_size` | 최대 latency, xrun 여유 | 안전하지만 지연 큼 | 지연 작지만 xrun 위험 |
| `period_size` | 인터럽트·깨움 주기 | CPU 부하 작음, 반응 느림 | 반응 빠름, 인터럽트·문맥 전환 많음 |

경험적인 출발점은 이렇다(정답은 측정으로 정한다).

- 음악 재생: 버퍼 100~500 ms. 지연이 상관없다.
- 음성 인식 캡처(웨이크워드): 10~20 ms period, 3~4 period. 엔진이 10 ms 단위로 프레임을 먹는 경우가 많다.
- 양방향 통화·에코 제거(AEC): 재생과 캡처 모두 10 ms period, 총 지연을 예측 가능하게. AEC는 "스피커로 나간 신호가 마이크로 돌아오기까지"의 지연이 일정해야 한다. 그래서 xrun보다 **지연 변동**이 더 큰 적이다.
- 로봇의 경고음·음성 피드백: 수십 ms 지연은 괜찮고, 끊김이 없는 게 중요하다.

### 5.2 예제 5 — period마다 깨어나는 간격의 지터 재기 (게스트 실행, 차트)

무엇을 확인하나: `avail_min = period`로 `poll()`하면 앱이 period마다 깨어나는지, 그 간격이 얼마나 흔들리는지. 그리고 snd-dummy의 타이밍 소스를 hrtimer(기본)와 jiffies(`hrtimer=0`, HZ=250 → 4 ms 단위)로 바꿨을 때 차이.

```c
/* i7_jitter.c — how regularly does "one period free" wake us up? */
#include "i7alsa.h"
#include <math.h>
#include <poll.h>

static int cmp(const void *a, const void *b)
{
	double x = *(const double *)a, y = *(const double *)b;
	return (x > y) - (x < y);
}

int main(int argc, char **argv)
{
	if (argc < 4) { fprintf(stderr, "usage: %s dev rate period [wakes]\n", argv[0]); return 1; }
	unsigned rate = atoi(argv[2]), period = atoi(argv[3]);
	int n = argc > 4 ? atoi(argv[4]) : 200;
	int fd = pcm_open(argv[1], 0, rate, 2, period, 4);   /* buffer = 4 periods */
	short *buf = calloc(period, 4);
	double *t = malloc(sizeof(double) * (n + 1)), *dev = malloc(sizeof(double) * n);
	double ideal = 1000.0 * period / rate;
	struct snd_xferi x = { .buf = buf, .frames = period };
	for (int i = 0; i < 4; i++)                       /* prefill -> auto start */
		if (ioctl(fd, SNDRV_PCM_IOCTL_WRITEI_FRAMES, &x) < 0) DIE("prefill");
	for (int i = 0; i <= n; i++) {
		struct pollfd p = { .fd = fd, .events = POLLOUT };
		if (poll(&p, 1, 2000) != 1) DIE("poll");
		t[i] = now_ms();
		if (ioctl(fd, SNDRV_PCM_IOCTL_WRITEI_FRAMES, &x) < 0) {
			printf("period %5u (%7.3f ms): XRUN after %d wakes (buffer %.1f ms)\n",
			       period, ideal, i, 4 * ideal);
			return 0;
		}
	}
	double sum = 0;
	for (int i = 1; i <= n; i++) {
		sum += t[i] - t[i - 1];
		dev[i - 1] = fabs(t[i] - t[i - 1] - ideal);
	}
	qsort(dev, n, sizeof(double), cmp);
	printf("period %5u (%7.3f ms): n=%d mean %7.3f  |dev| p50 %6.3f p99 %6.3f max %6.3f ms\n",
	       period, ideal, n, sum / n, dev[n / 2], dev[n * 99 / 100], dev[n - 1]);
	return 0;
}
```

그림 4 — 예제 5의 측정값. 막대 = "깨어난 간격 − 이상적인 period 시간"의 절댓값 중앙값(p50). 파랑은 hrtimer 구동, 주황은 jiffies(4 ms 틱) 구동. XRUN 표시는 그 조건에서 300번을 채우기 전에 underrun이 난 경우다.

출력에서 볼 것:

- **평균**은 어느 경우든 period 시간과 거의 같다(0.996, 2.000, 5.006 …). 오디오 클럭(여기선 타이머)이 장기적으로 속도를 정하기 때문이다. 문제는 **분포**다.
- hrtimer 구동은 p50 지터가 0.1~0.2 ms로 period와 상관없이 작다. jiffies 구동은 5 ms period에서 p50이 4.9 ms다. 4 ms 틱으로만 진행하니 깨어나는 간격이 0·4·8 ms처럼 양자화된다. 1 ms·2 ms period(버퍼 4·8 ms)에서는 틱 하나만 밀려도 버퍼가 바닥나 **바로 XRUN**이다. 실제 하드웨어에서 "DMA 완료 인터럽트가 아니라 느린 타이머로 위치를 갱신하는 드라이버"가 작은 period를 못 버티는 이유와 같다.
- hrtimer 구동인데도 10 ms period(버퍼 40 ms)에서 XRUN이 났고, p99·max가 10 ms 넘게 튄 경우가 있다. 이것은 snd-dummy 탓이 아니라 **환경** 탓이다. KVM 없는 TCG 에뮬레이션에 다른 작업자들의 QEMU가 같은 호스트에서 돌았다(측정 직전 VM load average 2.5). 게스트 전체가 수십 ms씩 멈추면 버퍼가 아무리 커도 그보다 작으면 xrun이다. 실제 장비에서도 똑같은 일이 생긴다. 다른 고우선순위 작업이나 긴 인터럽트 비활성 구간이 오디오 스레드를 막으면 생긴다(M·N 모듈의 latency 측정 도구로 찾는다).
- 반복 측정은 매번 조금씩 다르다(같은 조건의 앞선 실행에서는 hrtimer 1 ms가 XRUN, 10 ms는 정상이었다). 그래서 이 표는 "jiffies 양자화 대 hrtimer"라는 **질적 차이**만 믿어야 한다.

### 5.3 latency 계산 정리

| 구간 | 계산 | 48 kHz, period 480, periods 4일 때 |
|---|---|---|
| 재생 버퍼 지연 (최대) | buffer_size / rate | 1920 / 48000 = 40 ms |
| 캡처 → 앱 (최소) | period_size / rate | 480 / 48000 = 10 ms |
| codec·FIFO 지연 | 드라이버가 `runtime->delay`로 보고 | 하드웨어마다 (수십 µs ~ 수 ms) |
| 사운드 서버 버퍼 | PipeWire quantum / rate | 기본 quantum 1024면 21.3 ms (설정값, 이 노트에서 측정 안 함) |

마이크에서 앱까지의 최소 지연은 "period 하나가 다 찰 때까지"다. 웨이크워드처럼 반응이 중요한 앱이 period를 작게 잡는 이유다. 대신 period가 작으면 인터럽트가 늘고, 위 측정처럼 스케줄링 지터에 약해진다.

## 6. snd-aloop — 재생한 것이 캡처로 나오는지 끝까지 확인하기

### 6.1 직관

`snd-aloop`은 재생 device 0에 쓴 것을 같은 card의 캡처 device 1에서 읽게 해 주는 가상 케이블이다. 실제 장비에서는 "스피커 출력을 루프백으로 다시 받아 에코 제거 기준 신호로 쓰기", 테스트 자동화에서는 "하드웨어 없이 오디오 파이프라인 끝단까지 검증하기"에 쓴다.

### 6.2 예제 6 — 1 kHz 사인을 넣고, 다른 프로세스에서 샘플 단위로 맞는지 확인 (게스트 실행)

무엇을 확인하나: PCM 데이터 경로가 비트 단위로 손실 없이 이어지는지. 캡처 쪽은 재생 쪽과 **같은 수식**으로 사인을 다시 만들어 첫 신호 샘플부터 한 샘플씩 비교하고, 영점 교차로 주파수도 잰다.

```c
/* i7_cap.c — capture S16_LE stereo, check it is the exact sine i7_play wrote */
#include "i7alsa.h"
#include <math.h>

int main(int argc, char **argv)
{
	if (argc < 5) { fprintf(stderr, "usage: %s dev rate ms freq\n", argv[0]); return 1; }
	unsigned rate = atoi(argv[2]), period = 1024;
	unsigned long n = (unsigned long)rate * atoi(argv[3]) / 1000;
	double f = atof(argv[4]);
	int fd = pcm_open(argv[1], 1, rate, 2, period, 4);
	short *s = malloc(n * 4);
	if (ioctl(fd, SNDRV_PCM_IOCTL_START) < 0) DIE("START");
	for (unsigned long got = 0; got < n; ) {
		struct snd_xferi x = { .buf = s + 2 * got, .frames = period };
		if (n - got < period) x.frames = n - got;
		if (ioctl(fd, SNDRV_PCM_IOCTL_READI_FRAMES, &x) < 0) DIE("READI");
		got += x.result;
	}
	unsigned long first = 0, last = 0;               /* signal region */
	while (first < n && s[2 * first] == 0) first++;
	for (unsigned long i = first; i < n; i++) if (s[2 * i]) last = i;
	if (first == n) { printf("all silence\n"); return 1; }
	unsigned long off = first - 1, ok = 0, bad = 0, near = 0, zc = 0;  /* sin(0)=0 first */
	double ph = 0;
	for (unsigned long i = off; i <= last; i++, ph += 2 * M_PI * f / rate) {
		short want = (short)(8000 * sin(ph));
		if (s[2 * i] == want && s[2 * i + 1] == want) ok++;
		else if (abs(s[2 * i] - want) <= 1 && abs(s[2 * i + 1] - want) <= 1) near++;
		else bad++;
		if (i > off && (s[2 * i - 2] < 0) != (s[2 * i] < 0)) zc++;
	}
	double secs = (double)(last - off + 1) / rate;
	printf("captured %lu frames: silence %lu frames (%.1f ms) then signal %.3f s\n",
	       n, off, 1000.0 * off / rate, secs);
	printf("exact %lu, off-by-1LSB %lu, bad %lu; zero-crossing freq = %.2f Hz\n",
	       ok, near, bad, zc / 2.0 / secs);
	return 0;
}
```

## 7. ALSA PCM 드라이버 직접 쓰기 — `i7_pcm`

### 7.1 드라이버가 채우는 것

ALSA PCM 드라이버의 일은 세 가지뿐이다. (1) 하드웨어 능력을 `struct snd_pcm_hardware`로 알린다. (2) `struct snd_pcm_ops`의 콜백을 구현한다. (3) DMA가 period 하나를 끝낼 때마다 `snd_pcm_period_elapsed()`를 부른다. 링버퍼 관리, xrun 판정, 앱 깨우기, `read`/`write`/`mmap`/`poll`은 전부 core가 한다. I1의 "프레임워크에 ops를 등록하라"가 가장 깔끔하게 드러나는 서브시스템이다.

| 콜백 | 언제 불리나 | 컨텍스트 | 하는 일 |
|---|---|---|---|
| `.open` | `open()` | 프로세스, sleep 가능 | `runtime->hw` 설정, 제약 규칙 추가 |
| `.close` | 마지막 `close()` | sleep 가능 | open의 반대 |
| `.hw_params` | `HW_PARAMS` | sleep 가능 | 클럭·포맷 설정. managed buffer면 버퍼는 core가 이미 할당 |
| `.hw_free` | `HW_FREE`/close | sleep 가능 | hw_params의 반대 |
| `.prepare` | `PREPARE` (시작 전, xrun 복구 시) | sleep 가능 (nonatomic 아닐 때도 이 콜백은 락 밖) | 포인터·하드웨어 FIFO 초기화 |
| `.trigger` | START/STOP/PAUSE/SUSPEND | **atomic** — 스트림 spinlock + IRQ off | DMA 시작/정지만. sleep·mutex·I2C 금지 |
| `.sync_stop` | STOP 뒤, prepare·hw_free 전 | sleep 가능 | 남은 IRQ/타이머가 끝나길 기다림 (5.6부터) |
| `.pointer` | period IRQ, `STATUS`, write/read 안 | **atomic** | 현재 DMA 위치를 frame으로 반환 |

`.trigger`가 atomic인 이유: 여러 substream을 묶어 동시에 시작하는 `snd_pcm_link`, 그리고 인터럽트 핸들러 안에서 부르는 `snd_pcm_stop()`(xrun) 같은 경로가 모두 스트림 spinlock을 잡은 채 trigger를 부르기 때문이다(`sound/core/pcm_native.c`의 `snd_pcm_action_lock_irq()`, 1406행). 그래서 trigger에서 I2C로 codec을 건드리면 "scheduling while atomic"이 난다. codec 설정은 `hw_params`/`prepare`에서 하거나, ASoC에서는 DAPM이 맡는다. 정말 trigger에서 sleep해야 하는 드라이버(예: 펌웨어 IPC로 DSP를 제어)는 `pcm->nonatomic = true`로 스트림 락을 mutex로 바꾼다.

### 7.2 `i7_pcm.c` — hrtimer가 DMA 엔진 노릇을 한다

하드웨어가 없으니 hrtimer가 "period 하나 분량을 소비하고 인터럽트를 거는 DMA"를 흉내 낸다. 타이머 콜백은 hardirq 컨텍스트에서 돌고(로그에서 확인), 버퍼의 실제 샘플을 읽어 peak를 잰다. 진짜 "DAC가 데이터를 읽는다"를 흉내 내기 위해서다. 전체 215줄을 네 조각으로 나눠 싣는다.

조각 1 — 상태 구조체, 하드웨어 능력, "DMA 완료 인터럽트"

```c
// SPDX-License-Identifier: GPL-2.0
/* i7_pcm.c — minimal ALSA playback driver: hrtimer = fake DMA engine */
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/hrtimer.h>
#include <sound/core.h>
#include <sound/pcm.h>
#include <sound/pcm_params.h>
#include <sound/control.h>

struct i7 {
	struct snd_card *card;
	struct snd_pcm_substream *ss;
	struct hrtimer timer;
	ktime_t period_kt;
	unsigned int pos;          /* "DMA" position in frames, 0..buffer_size-1 */
	unsigned int nperiods;     /* periods completed (for logging) */
	int peak;                  /* peak sample of last period */
	int volume;                /* mixer control value 0..100 */
};

static const struct snd_pcm_hardware i7_hw = {
	.info = SNDRV_PCM_INFO_INTERLEAVED | SNDRV_PCM_INFO_MMAP |
		SNDRV_PCM_INFO_MMAP_VALID | SNDRV_PCM_INFO_BLOCK_TRANSFER,
	.formats = SNDRV_PCM_FMTBIT_S16_LE,
	.rates = SNDRV_PCM_RATE_48000, .rate_min = 48000, .rate_max = 48000,
	.channels_min = 1, .channels_max = 2,
	.buffer_bytes_max = 64 * 1024,
	.period_bytes_min = 256, .period_bytes_max = 16 * 1024,
	.periods_min = 2, .periods_max = 64,
};

/* "DMA complete" interrupt: consume one period, report it */
static enum hrtimer_restart i7_tick(struct hrtimer *t)
{
	struct i7 *c = container_of(t, struct i7, timer);
	struct snd_pcm_runtime *rt = c->ss->runtime;
	s16 *p = (s16 *)(rt->dma_area + frames_to_bytes(rt, c->pos));
	int i, n = rt->period_size * rt->channels, pk = 0;

	for (i = 0; i < n; i++)                 /* the "DAC" reads the samples */
		pk = max(pk, abs((int)p[i]));
	c->peak = pk * c->volume / 100;
	c->pos = (c->pos + rt->period_size) % rt->buffer_size;
	if (++c->nperiods % 25 == 0)
		pr_info("i7_pcm: tick pos=%u hw_ptr=%lu appl_ptr=%lu peak=%d hardirq=%d\n",
			c->pos, rt->status->hw_ptr, rt->control->appl_ptr, c->peak,
			!!in_hardirq());
	snd_pcm_period_elapsed(c->ss);          /* core: update hw_ptr, wake writer, xrun check */
	hrtimer_forward_now(t, c->period_kt);
	return HRTIMER_RESTART;
}
```

핵심 포인트 몇 개.

- `snd_devm_card_new()` — devres 버전이라 remove에서 `snd_card_free()`를 따로 부르지 않는다.
- `snd_pcm_set_managed_buffer_all(..., SNDRV_DMA_TYPE_VMALLOC, NULL, 0, 0)` — "버퍼는 core가 hw_params 때 vmalloc으로 할당해라". 진짜 DMA 하드웨어면 `SNDRV_DMA_TYPE_DEV`와 `&pdev->dev`를 넘겨 `dma_alloc_coherent()` 계열(H9)로 할당받고, `runtime->dma_addr`를 DMA 엔진에 준다.
- 타이머 콜백이 `pos`를 먼저 옮기고 `snd_pcm_period_elapsed()`를 부른다. core는 그 안에서 `.pointer`를 불러 새 `hw_ptr`를 계산한다. 순서가 반대면 core가 옛 위치를 읽어 "period가 안 지났다"고 판단한다.
- trigger STOP에서는 `hrtimer_try_to_cancel()`만 한다. `hrtimer_cancel()`은 콜백이 끝나길 **기다리는데**, 콜백이 `snd_pcm_period_elapsed()` 안에서 같은 스트림 락을 잡으려 하면 교착이다. 기다리는 일은 sleep 가능한 `.sync_stop`에서 한다. 이 패턴은 `sound/drivers/dummy.c`와 같다(dummy는 `HRTIMER_MODE_REL_SOFT`, 457행이라 콜백이 softirq에서 돈다).
- mixer control의 `.put`은 값이 바뀌면 1, 안 바뀌면 0을 돌려준다. 1이면 core가 control 장치를 듣는 다른 앱(사운드 서버 등)에 변경 이벤트를 보낸다.

### 7.3 mixer control을 ioctl로 읽고 쓰는 도구

`amixer`가 없으니 control 장치 ioctl(`SNDRV_CTL_IOCTL_ELEM_LIST`/`ELEM_INFO`/`ELEM_READ`/`ELEM_WRITE`)로 직접 만든다.

```c
/* i7_ctl.c — list mixer controls via /dev/snd/controlC0, optionally set one int */
#include "i7alsa.h"

int main(int argc, char **argv)
{
	const char *dev = argc > 1 ? argv[1] : "/dev/snd/controlC0";
	int fd = open(dev, O_RDWR);
	if (fd < 0) DIE("open ctl");
	struct snd_ctl_card_info ci = {0};
	if (ioctl(fd, SNDRV_CTL_IOCTL_CARD_INFO, &ci) < 0) DIE("CARD_INFO");
	printf("card %d id=%s driver=%s name='%s'\n", ci.card, ci.id, ci.driver, ci.name);

	struct snd_ctl_elem_list l = {0};
	if (ioctl(fd, SNDRV_CTL_IOCTL_ELEM_LIST, &l) < 0) DIE("ELEM_LIST count");
	struct snd_ctl_elem_id ids[64];
	l.space = l.count < 64 ? l.count : 64;
	l.pids = ids;
	if (ioctl(fd, SNDRV_CTL_IOCTL_ELEM_LIST, &l) < 0) DIE("ELEM_LIST");
	for (unsigned i = 0; i < l.used; i++) {
		struct snd_ctl_elem_info inf = { .id = ids[i] };
		if (ioctl(fd, SNDRV_CTL_IOCTL_ELEM_INFO, &inf) < 0) DIE("ELEM_INFO");
		struct snd_ctl_elem_value v = { .id = ids[i] };
		if (argc > 3 && !strcmp((char *)ids[i].name, argv[2])) {   /* write */
			v.value.integer.value[0] = atol(argv[3]);
			int r = ioctl(fd, SNDRV_CTL_IOCTL_ELEM_WRITE, &v);
			if (r < 0) DIE("ELEM_WRITE");
		}
		if (ioctl(fd, SNDRV_CTL_IOCTL_ELEM_READ, &v) < 0) DIE("ELEM_READ");
		printf("numid=%u iface=%u '%s' type=%d count=%u",
		       ids[i].numid, ids[i].iface, ids[i].name, inf.type, inf.count);
		if (inf.type == SNDRV_CTL_ELEM_TYPE_INTEGER)
			printf(" range=[%ld,%ld] value=%ld", inf.value.integer.min,
			       inf.value.integer.max, v.value.integer.value[0]);
		else if (inf.type == SNDRV_CTL_ELEM_TYPE_BOOLEAN)
			printf(" value=%ld", v.value.integer.value[0]);
		else if (inf.type == SNDRV_CTL_ELEM_TYPE_ENUMERATED)
			printf(" items=%u value=%u", inf.value.enumerated.items,
			       v.value.enumerated.item[0]);
		printf("\n");
	}
	return 0;
}
```

## 8. ASoC — SoC 오디오를 세 드라이버로 쪼개는 이유

### 8.1 직관 — "같은 codec, 다른 SoC, 다른 보드"

i7_pcm 같은 일반 ALSA 드라이버는 한 드라이버가 카드 전체를 안다. PC의 HDA나 USB 오디오는 그래도 된다. 장치 하나가 카드 하나이기 때문이다. SoC 세계는 다르다. WM8960 codec 하나가 NXP i.MX8, TI AM62, Rockchip 보드 수십 종에 붙고, i.MX8의 SAI(I2S) 컨트롤러 하나에 보드마다 다른 codec이 붙는다. 한 드라이버에 다 넣으면 (SoC 수 × codec 수 × 보드 수)만큼 드라이버가 생긴다.

**ASoC (ALSA System on Chip)** 는 이것을 세 종류의 드라이버로 쪼갠다.

| 역할 | 무엇을 아나 | 재사용 단위 | 예 (이 노트 / i.MX8MP EVK) |
|---|---|---|---|
| **codec** (component) | codec 칩의 레지스터, DAC/ADC/앰프, DAPM 위젯, DAI 포맷 | 칩 하나 → 모든 보드 | `es7134`·`dmic-codec` / `wm8960` (I2C) |
| **CPU DAI + platform** (component) | SoC의 I2S/TDM/PDM 컨트롤러 레지스터, DMA로 링버퍼 옮기기 | SoC 하나 → 모든 보드 | `i7_asoc` / `fsl_sai` + generic dmaengine PCM |
| **machine** (card) | "이 보드에서는 SAI3에 I2C3의 WM8960이 붙어 있고, MCLK는 SoC가 준다" | 보드 하나 | `simple-audio-card` DT / `fsl-asoc-card` |

**DAI (Digital Audio Interface)** 는 디지털 오디오 포트 한 쪽 끝이다. CPU 쪽 DAI(SoC의 I2S 포트)와 codec 쪽 DAI(칩의 I2S 핀)를 **dai-link**가 잇는다. 하나의 dai-link가 ALSA PCM device 하나가 된다.

그림 6 — I2S 타이밍(축약). LRCLK(= frame sync, word select)가 0이면 왼쪽, 1이면 오른쪽 채널 슬롯이다. 데이터(SD)는 MSB부터 나가고, I2S 형식에서는 LRCLK가 바뀐 뒤 **한 BCLK 늦게** MSB가 시작한다. 그래서 LRCLK가 바뀐 첫 BCLK에는 이전 채널의 LSB(`L0`)가 나간다. Left-justified 형식은 이 지연이 없고, DSP_A/DSP_B는 짧은 프레임 펄스를 쓴다.

| 형식 | 선 | 한 프레임에 | BCLK 계산 | 쓰는 곳 |
|---|---|---|---|---|
| I2S | BCLK, LRCLK, SD (+MCLK) | 2 슬롯 (L/R) | rate × 2 × 슬롯 비트 | 스테레오 DAC/ADC, 앰프 |
| TDM | BCLK, FSYNC, SD (+MCLK) | N 슬롯 (4·8·16) | rate × N × 슬롯 비트 | 마이크 어레이 ADC, 멀티채널 앰프 |
| PDM | CLK, DATA | 1비트 스트림 (L/R은 클럭 엣지로 구분) | 보통 rate × 64 (데시메이션 비) | MEMS 디지털 마이크 |

계산을 손에 익혀 두자. 예제 9(§9)의 커널 로그와 같은 숫자다.

- 48 kHz, 16비트, I2S 2슬롯: BCLK = 48000 × 2 × 16 = **1.536 MHz**. LRCLK = 48 kHz.
- 슬롯을 32비트로 두면(24비트 데이터를 32비트 슬롯에 실음, 흔하다): 48000 × 2 × 32 = 3.072 MHz.
- 8채널 마이크 어레이 TDM, 16 kHz, 32비트 슬롯: 16000 × 8 × 32 = 4.096 MHz.
- MCLK(codec 내부 오버샘플링·PLL 기준): 보통 256 × fs = 12.288 MHz(48k 계열) 또는 11.2896 MHz(44.1k 계열). 그래서 SoC에 **오디오 PLL이 두 개**(8k 배수용, 11.025k 배수용) 있는 경우가 많다. i.MX8MP의 micfil 클럭 이름 `pll8k`, `pll11k`(§11)가 그것이다.
- PDM 마이크: 클럭 3.072 MHz면 64배 데시메이션으로 48 kHz PCM. 음성 인식용 16 kHz면 1.024 MHz 근처. PDM→PCM 변환(CIC/FIR 데시메이션 필터)은 SoC의 PDM 컨트롤러 하드웨어가 하거나, 없으면 DSP·소프트웨어가 한다.

위 PDM 수치는 일반적인 구성 예시다(데이터시트별로 다르다, 이 노트에서 측정한 것이 아니다).

### 8.3 platform = DMA — generic dmaengine PCM

SoC의 CPU DAI 드라이버는 대개 PCM ops를 직접 쓰지 않는다. SoC의 범용 DMA 컨트롤러(i.MX의 SDMA, TI의 UDMA, Arm PL330 …)가 dmaengine 드라이버(H9 §10)로 있으니, ASoC가 제공하는 **generic dmaengine PCM**을 등록 한 줄로 쓴다. i.MX SAI 드라이버가 그렇게 한다.

```c
/* sound/soc/fsl/fsl_sai.c:1627~1642 (6.18.55) — 발췌, 소스 읽기 */
		ret = imx_pcm_dma_init(pdev);              /* 1627: i.MX SDMA 경로 */
		...
		ret = devm_snd_dmaengine_pcm_register(dev, NULL, 0);   /* 1635 */
	...
	ret = devm_snd_soc_register_component(dev, &fsl_component,   /* 1642: CPU DAI */
```

generic dmaengine PCM이 내부에서 하는 일은 i7_pcm의 hrtimer 자리에 **순환(cyclic) DMA**를 넣은 것이다.

```c
/* sound/core/pcm_dmaengine.c:136-175 (6.18.55) — 발췌 */
static void dmaengine_pcm_dma_complete(void *arg)
{
	unsigned int new_pos;
	struct snd_pcm_substream *substream = arg;
	struct dmaengine_pcm_runtime_data *prtd = substream_to_prtd(substream);

	new_pos = prtd->pos + snd_pcm_lib_period_bytes(substream);
	if (new_pos >= snd_pcm_lib_buffer_bytes(substream))
		new_pos = 0;
	prtd->pos = new_pos;

	snd_pcm_period_elapsed(substream);
}

static int dmaengine_pcm_prepare_and_submit(struct snd_pcm_substream *substream)
{
	struct dmaengine_pcm_runtime_data *prtd = substream_to_prtd(substream);
	struct dma_chan *chan = prtd->dma_chan;
	struct dma_async_tx_descriptor *desc;
	enum dma_transfer_direction direction;
	unsigned long flags = DMA_CTRL_ACK;

	direction = snd_pcm_substream_to_dma_direction(substream);

	if (!substream->runtime->no_period_wakeup)
		flags |= DMA_PREP_INTERRUPT;

	prtd->pos = 0;
	desc = dmaengine_prep_dma_cyclic(chan,
		substream->runtime->dma_addr,
		snd_pcm_lib_buffer_bytes(substream),
		snd_pcm_lib_period_bytes(substream), direction, flags);

	if (!desc)
		return -ENOMEM;

	desc->callback = dmaengine_pcm_dma_complete;
	desc->callback_param = substream;
	prtd->cookie = dmaengine_submit(desc);

```

- `dmaengine_prep_dma_cyclic(chan, dma_addr, buffer_bytes, period_bytes, ...)` — 링버퍼 전체를 period 단위로 끝없이 도는 DMA 디스크립터를 만든다. Don이 bare-metal에서 걸던 circular DMA와 같다.
- period 하나가 끝날 때마다 DMA 드라이버가 `dmaengine_pcm_dma_complete()` 콜백을 부르고, 그것이 `snd_pcm_period_elapsed()`를 부른다. i7_pcm의 `i7_tick()`과 같은 자리다.
- `.pointer`는 `snd_dmaengine_pcm_pointer()`(같은 파일 251행)로, dmaengine의 `tx_status` **residue**(남은 바이트 수)에서 현재 위치를 계산한다. DMA 컨트롤러가 residue를 보고하지 못하면 `_no_residue` 버전(235행)이 period 단위 위치만 준다. i7_pcm처럼.

이 절은 **소스 읽기**다. 이 QEMU `virt` 랩에는 DMA로 오디오를 나르는 하드웨어가 없어서 실행하지 못했다.

## 9. ASoC 실습 — 가짜 I2S 컨트롤러 + 진짜 codec 드라이버 + simple-audio-card

### 9.1 무엇을 만들었나

QEMU `virt`에는 오디오 하드웨어가 없다(랩 커널에 `snd-hda-intel`·USB audio 드라이버도 없다). 하지만 ASoC는 "부품 드라이버들이 DT로 이어져 카드가 되는 과정"이 핵심이라, 레지스터가 필요 없는 부품을 모으면 **진짜 ASoC 카드를 조립할 수 있다**.

| 부품 | 드라이버 | 역할 |
|---|---|---|
| CPU DAI + platform | 직접 쓴 `i7_asoc.ko` (compatible `i7,fake-i2s`) | DAI 2개(`i7-i2s-tx` 재생, `i7-pdm-rx` 캡처), hrtimer 가짜 DMA. 캡처는 1 kHz 사인을 "마이크 데이터"로 채운다 |
| codec 1 | 커널의 `snd-soc-es7134` (`everest,es7134`) | 제어 인터페이스가 없는 I2S DAC. DAPM 위젯 `DAC`·`AOUTL/R`·`VDD`가 있다 |
| codec 2 | 커널의 `snd-soc-dmic` (`dmic-codec`) | 범용 PDM 디지털 마이크 codec. 위젯 `DMic`·`DMIC AIF` |
| machine | 커널의 `snd-soc-simple-card` (`simple-audio-card`) | DT의 dai-link 2개로 카드 조립 |

### 9.2 DT — QEMU `virt.dts`에 덧붙인 노드

랩의 `out/virt.dts`를 `/var/tmp/I7/`로 복사해 루트 노드 끝에 아래를 넣고 `dtc`로 컴파일, `-dtb`로 부팅했다(`-m 512M -cpu cortex-a57 -smp 1`, virt.dts를 뽑은 조건과 같게).

```dts
/* i7_sound.dtsi — virt.dts 루트 노드 끝(1-43행 전체)에 덧붙임 */
	i7_i2s: i7-i2s {
		compatible = "i7,fake-i2s";
		#sound-dai-cells = <1>;
	};

	i7_dac: i7-dac {
		compatible = "everest,es7134";
		#sound-dai-cells = <0>;
	};

	i7_dmic: i7-dmic {
		compatible = "dmic-codec";
		#sound-dai-cells = <0>;
		num-channels = <2>;
		wakeup-delay-ms = <50>;
	};

	i7-sound {
		compatible = "simple-audio-card";
		simple-audio-card,name = "i7-asoc";
		simple-audio-card,widgets = "Speaker", "Board Speaker",
					    "Microphone", "Board Mic";
		simple-audio-card,routing = "Board Speaker", "AOUTL",
					    "Board Speaker", "AOUTR",
					    "DMic", "Board Mic";
		#address-cells = <1>;
		#size-cells = <0>;

		simple-audio-card,dai-link@0 {
			reg = <0>;
			format = "i2s";
			mclk-fs = <256>;
			cpu { sound-dai = <&i7_i2s 0>; };
			codec { sound-dai = <&i7_dac>; };
		};

		simple-audio-card,dai-link@1 {
			reg = <1>;
			format = "i2s";
			cpu { sound-dai = <&i7_i2s 1>; };
			codec { sound-dai = <&i7_dmic>; };
		};
	};
```

읽는 법:

- `#sound-dai-cells = <1>` — CPU 노드는 DAI가 둘이라 `<&i7_i2s 0>`·`<&i7_i2s 1>`처럼 번호로 고른다. codec은 DAI가 하나라 0셀.
- `format = "i2s"` — dai-link의 DAI 포맷. 양쪽 DAI의 `.set_fmt`로 전달된다.
- `mclk-fs = <256>` — hw_params 때 simple-card가 MCLK = rate × 256을 계산해 양쪽 DAI의 `.set_sysclk`를 부른다.
- `bitclock-master`/`frame-master`를 안 적으면 codec이 clock consumer, 즉 **CPU(SoC)가 BCLK·LRCLK를 낸다**.
- `widgets`는 보드에 있는 물리 부품(스피커, 마이크)을 DAPM 위젯으로 만들고, `routing`은 "싱크, 소스" 쌍으로 그 위젯과 codec 핀을 잇는다. `"Board Speaker", "AOUTL"`은 "AOUTL이 Board Speaker로 간다"는 뜻이다.

### 9.3 `i7_asoc.c` — CPU DAI와 platform(PCM) component

i7_pcm과 비교하면 같은 일을 하는 코드가 **두 군데로 나뉜다**. DMA·링버퍼 쪽은 `snd_soc_component_driver`의 PCM 콜백(첫 인자가 `component`), I2S 컨트롤러 쪽은 `snd_soc_dai_ops`(포맷·클럭·hw_params)다. 실제 SoC에서는 앞쪽을 generic dmaengine PCM이 대신하고, 드라이버 작성자는 뒤쪽만 쓴다.

조각 1 — 상태와 가짜 DMA (재생은 읽고, 캡처는 사인을 쓴다)

```c
// SPDX-License-Identifier: GPL-2.0
/* i7_asoc.c — ASoC CPU DAI + platform(PCM) component for a fake I2S/PDM controller */
#include <linux/module.h>
#include <linux/of.h>
#include <linux/platform_device.h>
#include <linux/hrtimer.h>
#include <sound/soc.h>
#include <sound/pcm_params.h>

struct i7s {                       /* one per direction: a fake DMA channel */
	struct hrtimer timer;
	struct snd_pcm_substream *ss;
	ktime_t period_kt;
	unsigned int pos, n, phase;
	int peak;
};
struct i7a { struct i7s st[2]; struct device *dev; };

static const s16 sine1k[48] = { /* 1 kHz at 48 kHz, amplitude 8000 */
	0, 1044, 2070, 3061, 3999, 4870, 5656, 6346, 6928, 7391, 7727, 7931,
	8000, 7931, 7727, 7391, 6928, 6346, 5656, 4870, 3999, 3061, 2070, 1044,
	0, -1044, -2070, -3061, -3999, -4870, -5656, -6346, -6928, -7391, -7727, -7931,
	-8000, -7931, -7727, -7391, -6928, -6346, -5656, -4870, -4000, -3061, -2070, -1044 };

static enum hrtimer_restart i7a_tick(struct hrtimer *t)
{
	struct i7s *s = container_of(t, struct i7s, timer);
	struct snd_pcm_runtime *rt = s->ss->runtime;
	s16 *p = (s16 *)(rt->dma_area + frames_to_bytes(rt, s->pos));
	unsigned int i, ch, pk = 0;

	for (i = 0; i < rt->period_size; i++)
		for (ch = 0; ch < rt->channels; ch++, p++) {
			if (s->ss->stream == SNDRV_PCM_STREAM_CAPTURE)
				*p = sine1k[s->phase];          /* "mic" writes RAM */
			else
				pk = max(pk, (unsigned int)abs(*p)); /* "DAC" reads RAM */
			if (ch == rt->channels - 1)
				s->phase = (s->phase + 1) % 48;
		}
	s->peak = pk;
	s->pos = (s->pos + rt->period_size) % rt->buffer_size;
	s->n++;
	snd_pcm_period_elapsed(s->ss);
	hrtimer_forward_now(t, s->period_kt);
	return HRTIMER_RESTART;
}

static const struct snd_pcm_hardware i7a_hw = {
	.info = SNDRV_PCM_INFO_INTERLEAVED | SNDRV_PCM_INFO_MMAP | SNDRV_PCM_INFO_MMAP_VALID,
	.buffer_bytes_max = 64 * 1024, .period_bytes_min = 256,
	.period_bytes_max = 16 * 1024, .periods_min = 2, .periods_max = 64,
};

```

조각 2 — platform(PCM) component 콜백

```c
/* ---- platform / PCM component ops (the "DMA" side) ---- */
static int i7a_open(struct snd_soc_component *c, struct snd_pcm_substream *ss)
{
	struct i7a *a = snd_soc_component_get_drvdata(c);

	a->st[ss->stream].ss = ss;
	return snd_soc_set_runtime_hwparams(ss, &i7a_hw);
}
static int i7a_prepare(struct snd_soc_component *c, struct snd_pcm_substream *ss)
{
	struct i7s *s = &((struct i7a *)snd_soc_component_get_drvdata(c))->st[ss->stream];

	s->pos = s->n = s->phase = 0;
	s->period_kt = ns_to_ktime(div_u64((u64)ss->runtime->period_size * NSEC_PER_SEC,
					   ss->runtime->rate));
	return 0;
}
static int i7a_trigger(struct snd_soc_component *c, struct snd_pcm_substream *ss, int cmd)
{
	struct i7s *s = &((struct i7a *)snd_soc_component_get_drvdata(c))->st[ss->stream];

	dev_info(c->dev, "%s trigger cmd=%d in_atomic=%d\n",
		 ss->stream ? "capture" : "playback", cmd, in_atomic());
	if (cmd == SNDRV_PCM_TRIGGER_START)
		hrtimer_start(&s->timer, s->period_kt, HRTIMER_MODE_REL);
	else if (cmd == SNDRV_PCM_TRIGGER_STOP)
		hrtimer_try_to_cancel(&s->timer);
	return 0;
}
static int i7a_sync_stop(struct snd_soc_component *c, struct snd_pcm_substream *ss)
{
	struct i7a *a = snd_soc_component_get_drvdata(c);

	hrtimer_cancel(&a->st[ss->stream].timer);
	dev_info(c->dev, "%s stopped after %u periods, last peak %d\n",
		 ss->stream ? "capture" : "playback", a->st[ss->stream].n,
		 a->st[ss->stream].peak);
	return 0;
}
static snd_pcm_uframes_t i7a_pointer(struct snd_soc_component *c, struct snd_pcm_substream *ss)
{
	return ((struct i7a *)snd_soc_component_get_drvdata(c))->st[ss->stream].pos;
}
static int i7a_construct(struct snd_soc_component *c, struct snd_soc_pcm_runtime *rtd)
{
	snd_pcm_set_managed_buffer_all(rtd->pcm, SNDRV_DMA_TYPE_VMALLOC, NULL, 0, 0);
	return 0;
}
static const struct snd_soc_component_driver i7a_component = {
	.name = "i7-fake-i2s",
	.open = i7a_open, .prepare = i7a_prepare, .trigger = i7a_trigger,
	.sync_stop = i7a_sync_stop, .pointer = i7a_pointer, .pcm_construct = i7a_construct,
	.legacy_dai_naming = 1,
};

```

조각 3 — CPU DAI ops, DAI 두 개, probe

```c
/* ---- CPU DAI ops (the "I2S controller" side) ---- */
static int i7a_set_fmt(struct snd_soc_dai *dai, unsigned int fmt)
{
	dev_info(dai->dev, "%s set_fmt format=%u (1=I2S) clock=0x%x inv=0x%x\n", dai->name,
		 fmt & SND_SOC_DAIFMT_FORMAT_MASK, fmt & SND_SOC_DAIFMT_CLOCK_PROVIDER_MASK,
		 fmt & SND_SOC_DAIFMT_INV_MASK);
	return 0;
}
static int i7a_set_sysclk(struct snd_soc_dai *dai, int id, unsigned int freq, int dir)
{
	dev_info(dai->dev, "%s set_sysclk MCLK=%u Hz dir=%s\n", dai->name, freq,
		 dir == SND_SOC_CLOCK_OUT ? "out" : "in");
	return 0;
}
static int i7a_hw_params(struct snd_pcm_substream *ss, struct snd_pcm_hw_params *p,
			 struct snd_soc_dai *dai)
{
	unsigned int slots = 2, w = params_physical_width(p);   /* I2S: always 2 slots */

	dev_info(dai->dev, "%s hw_params rate=%u ch=%u width=%u -> LRCLK=%u BCLK=%u\n",
		 dai->name, params_rate(p), params_channels(p), w, params_rate(p),
		 params_rate(p) * slots * w);
	return 0;
}
static const struct snd_soc_dai_ops i7a_dai_ops = {
	.set_fmt = i7a_set_fmt, .set_sysclk = i7a_set_sysclk, .hw_params = i7a_hw_params,
};
static struct snd_soc_dai_driver i7a_dais[] = {
	{ .name = "i7-i2s-tx", .ops = &i7a_dai_ops,
	  .playback = { .stream_name = "I7 TX", .channels_min = 2, .channels_max = 2,
			.rates = SNDRV_PCM_RATE_48000, .formats = SNDRV_PCM_FMTBIT_S16_LE } },
	{ .name = "i7-pdm-rx", .ops = &i7a_dai_ops,
	  .capture = { .stream_name = "I7 RX", .channels_min = 2, .channels_max = 2,
		       .rates = SNDRV_PCM_RATE_48000, .formats = SNDRV_PCM_FMTBIT_S16_LE } },
};

static int i7a_probe(struct platform_device *pdev)
{
	struct i7a *a = devm_kzalloc(&pdev->dev, sizeof(*a), GFP_KERNEL);
	int i;

	if (!a)
		return -ENOMEM;
	for (i = 0; i < 2; i++)
		hrtimer_setup(&a->st[i].timer, i7a_tick, CLOCK_MONOTONIC, HRTIMER_MODE_REL);
	a->dev = &pdev->dev;
	platform_set_drvdata(pdev, a);
	return devm_snd_soc_register_component(&pdev->dev, &i7a_component, i7a_dais,
					       ARRAY_SIZE(i7a_dais));
}
static const struct of_device_id i7a_of[] = { { .compatible = "i7,fake-i2s" }, { } };
MODULE_DEVICE_TABLE(of, i7a_of);
static struct platform_driver i7a_drv = {
	.probe = i7a_probe,
	.driver = { .name = "i7-fake-i2s", .of_match_table = i7a_of },
};
module_platform_driver(i7a_drv);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("I7 fake I2S/PDM CPU DAI + PCM component");
```

ASoC는 dai-link의 포맷을 **codec 관점**으로 저장하고, CPU DAI에 넘길 때 provider 비트를 뒤집는다(`sound/soc/soc-core.c:1455` `snd_soc_runtime_set_dai_fmt()`, 1495행 `snd_soc_daifmt_clock_provider_flipped()`). 그래서 CPU 드라이버가 받는 0x1000은 "**너(CPU)가 provider**"라는 뜻이다. 실제 SAI 드라이버도 이 값을 보고 BCLK·LRCLK 출력 방향 레지스터를 설정한다.
- `set_sysclk MCLK=12288000` = 48000 × 256. DT의 `mclk-fs`. 캡처 링크에는 `mclk-fs`를 안 적어서 set_sysclk가 불리지 않았다. 스트림이 끝나면 simple-card가 MCLK=0으로 다시 부른다(클럭 해제 신호).
- BCLK = 48000 × 2 × 16 = 1 536 000. §8.2 계산과 같다.
- `supply VDD not found, using dummy regulator` — es7134의 `VDD` supply 위젯이 DT에 `vdd-supply`가 없어서 regulator core가 더미를 붙였다. 실제 보드라면 여기에 codec 전원 레귤레이터를 연결하고, DAPM이 그 레귤레이터를 켜고 끈다(H3).
- 캡처는 1초에 47 period(1024 frame). peak 0은 캡처 방향에서는 peak를 재지 않기 때문이다. 재생은 480 frame period로 1초에 100번, 마지막 peak 8000 = 앱이 쓴 사인 진폭.

## 10. DAPM — 오디오 경로의 전원을 그래프로 관리한다

### 10.1 직관 — "소리가 지나갈 길만 불을 켠다"

배터리로 도는 음성 웨어러블에서 codec의 ADC·PGA·마이크 바이어스·스피커 앰프를 늘 켜 두면 수 mA가 샌다. bare-metal에서는 "녹음 시작하면 ADC 켜고, 끝나면 끄고"를 손으로 짰다. 경로가 많아지면(헤드폰 꽂힘, 스피커, 블루투스, 루프백) 그 조합이 폭발한다.

**DAPM (Dynamic Audio Power Management)** 은 codec 내부와 보드를 **그래프**로 적어 두고, "지금 활성인 스트림에서 실제 입출력 끝점까지 완전히 이어진 경로"에 있는 위젯만 전원을 켠다. 드라이버 작성자는 위젯과 연결(route)만 선언한다. 켜고 끄는 순서와 시점은 ASoC core가 계산한다.

| 개념 | 뜻 | 예 (이 노트의 카드) |
|---|---|---|
| widget | 전원을 켜고 끌 수 있는 블록, 또는 끝점 | `DAC`, `DMic`, `DMIC AIF`, `Board Speaker` |
| endpoint | 경로의 끝: 마이크·스피커·입출력 핀, 그리고 활성 스트림 | `Board Mic`(mic), `AOUTL`(output), `Capture`(stream) |
| route | `{싱크, 컨트롤, 소스}` 연결. 컨트롤이 있으면 mixer 스위치·mux로 끊고 이을 수 있다 | `{"DMIC AIF", NULL, "DMic"}`, `{"DAC", NULL, "VDD"}` |
| supply widget | 경로 위에 있진 않지만, 의존하는 위젯이 켜지면 같이 켜지는 전원 | `VDD` (regulator supply) |
| bias level | codec 전체 상태: `OFF` → `STANDBY` → `PREPARE` → `ON` | idle일 때 es7134·dmic는 Standby |
| pmdown_time | 재생 스트림이 닫힌 뒤 전원을 끄기 전 기다리는 시간(기본 5000 ms) | 연속 재생 사이에 팝 노이즈·재시작 지연 방지 |

위젯은 codec 드라이버의 `snd_soc_dapm_widget` 배열로 선언한다(§9의 es7134 소스: `SND_SOC_DAPM_DAC("DAC", "Playback", SND_SOC_NOPM, 0, 0)` — 레지스터가 없어 `SND_SOC_NOPM`). 진짜 codec이면 위젯마다 "이 레지스터의 이 비트가 전원"을 적는다. 예를 들어 `sound/soc/codecs/wm8960.c:382`의 `SND_SOC_DAPM_ADC("Left ADC", "Capture", WM8960_POWER1, 3, 0)`는 "Left ADC 전원 = POWER1 레지스터 비트 3"이다. 그러면 DAPM이 그 비트를 regmap(H2)으로 직접 쓴다.

### 10.2 예제 10 — 캡처를 열면 마이크 경로만 켜진다 (게스트 실행)

무엇을 확인하나: 같은 부팅(예제 9)에서 idle → 캡처 중 → 재생 중 → 정지 직후 → 6초 뒤의 위젯 전원 상태. 그리고 마이크 데이터(가짜 DMA가 쓴 1 kHz)가 앱까지 오는지.

```sh
# 게스트 (예제 9에 이어서)
```

출력에서 볼 것:

- 각 줄의 `in N out M`은 그 위젯에서 "입력 끝점까지 이어진 경로 수 / 출력 끝점까지 이어진 경로 수"다. 위젯은 **양쪽이 모두 0이 아닐 때** 켜진다. idle에서 `DMic`는 `in 1 out 0` — 마이크(입력 끝점)와는 이어져 있지만 활성 캡처 스트림(출력 끝점)이 없다. 캡처를 열자 `in 1 out 1`이 되며 On.
- 재생 쪽(`DAC`, `AOUTL`, `VDD`)은 캡처 중에도 Off. **경로 단위로** 전원이 관리된다. 진짜 codec이었다면 이 순간 스피커 앰프 전류가 0이다.
- `Board Mic`의 상세: 위젯 타입 `mic`, 나가는 경로 하나 `"static" "DMic" "i7-dmic"`. `static`은 mixer 스위치 없이 늘 이어진 route라는 뜻이다. DT의 `routing = "DMic", "Board Mic"`가 이것을 만들었다.
- bias level: idle일 때 codec component는 `Standby`, 카드와 CPU는 `Off`. 스트림이 열리면 전부 `On`.
- 캡처 데이터: 1초, 1 kHz(영점 교차 999.50 Hz). `off-by-1LSB 2688`은 커널의 사인 테이블을 `(int)` 절삭으로 만들어 유저 쪽 수식과 1 LSB씩 다른 칸이 있기 때문이다. `bad 0`이니 데이터 경로는 깨끗하다.

### 10.3 예제 11 — 재생 경로와 pmdown_time (게스트 실행)

```sh

./i7_play /dev/snd/pcmC0D0p 48000 480 4 1000 > /tmp/p.log &
sleep 0.5; echo "== playing"; for w in DAC VDD AOUTL; do head -1 $D/$w; done; head -1 "$A/i7-asoc/dapm/Board Speaker"
wait; tail -1 /tmp/p.log
echo "== just stopped"; head -1 $D/DAC; cat /sys/devices/platform/i7-sound/*/pmdown_time 2>/dev/null || find /sys -name pmdown_time
sleep 6; echo "== 6 s later"; head -1 $D/DAC; head -1 $D/VDD
```

```text

DAC: On  in 1 out 2
VDD: On  in 0 out 0
AOUTL: On  in 1 out 1
Board Speaker: On  in 2 out 1
wrote 48000 frames in 1005.0 ms, xruns=0
== just stopped
DAC: On  in 1 out 2
5000
5000
== 6 s later

VDD: Off  in 0 out 0
```

출력에서 볼 것:

- 재생 중 `DAC`·`AOUTL`·`Board Speaker`가 On이고, 경로에 없는 supply 위젯 `VDD`도 On이다(`in 0 out 0`인데도). supply는 의존하는 위젯이 켜지면 따라 켜진다. 실제 보드라면 여기서 codec 레귤레이터가 켜진다.
- 재생이 끝난 **직후에도 `DAC`가 On**이다. dai-link(PCM 런타임)마다 있는 `pmdown_time`(5000 ms, 두 링크라 두 줄)만큼 기다렸다 끈다. es7134 드라이버가 `.use_pmdown_time = 1`을 켰기 때문이다. 짧은 효과음이 연달아 나올 때마다 앰프를 껐다 켜면 "퍽" 하는 팝 노이즈와 수십 ms 시작 지연이 생기는데, 그것을 막는 장치다. 6초 뒤에는 Off.
- 캡처 쪽에는 이런 지연이 없다(캡처 스트림은 닫히면 바로 끈다).

## 11. 실제 보드 DT 읽기 — NXP i.MX8M Plus EVK

### 11.1 왜 이 보드인가

i.MX8MP는 로봇·카메라·음성 장비에 흔한 SoC이고, EVK의 오디오 구성(SAI + I2C codec, PDM 마이크 컨트롤러, 블루투스 SCO, HDMI)은 실무에서 마주칠 패턴을 다 담고 있다. 아래는 랩 소스 트리(6.18.55)의 `arch/arm64/boot/dts/freescale/imx8mp-evk.dts`를 줄 번호와 함께 읽은 것이다(**소스 읽기 — 이 보드에서 실행한 것이 아니다**).

```sh
# VM: 오디오 관련 노드 위치 찾기
cd /var/lab/src/linux-6.18.55/arch/arm64/boot/dts/freescale
grep -n "sound\|wm8960\|codec\|sai3\|audio\|micfil\|dmic" imx8mp-evk.dts | head -60
```

출력 중 핵심 줄만 남기면 이렇다(전체 출력은 regulator·pinctrl 줄이 더 있다).

```text

```

### 11.2 machine 노드 — `sound-wm8960` (211~229행)

```dts
// arch/arm64/boot/dts/freescale/imx8mp-evk.dts:211-229 (6.18.55)
	sound-wm8960 {
		compatible = "fsl,imx-audio-wm8960";
		audio-asrc = <&easrc>;
		audio-codec = <&wm8960>;
		audio-cpu = <&sai3>;
		audio-routing = "Headphone Jack", "HP_L",
			"Headphone Jack", "HP_R",
			"Ext Spk", "SPK_LP",
			"Ext Spk", "SPK_LN",
			"Ext Spk", "SPK_RP",
			"Ext Spk", "SPK_RN",
			"LINPUT1", "Mic Jack",
			"LINPUT3", "Mic Jack",
			"Mic Jack", "MICB";
		hp-det-gpio = <&gpio4 28 GPIO_ACTIVE_HIGH>;
		model = "wm8960-audio";
		pinctrl-0 = <&pinctrl_hpdet>;
		pinctrl-names = "default";
	};
```

- `compatible = "fsl,imx-audio-wm8960"` — simple-audio-card가 아니라 NXP 전용 machine 드라이버 `sound/soc/fsl/fsl-asoc-card.c`(787행에서 이 compatible을 처리)가 받는다. 하는 일은 simple-card와 같다. CPU DAI(`audio-cpu = <&sai3>`)와 codec(`audio-codec = <&wm8960>`)을 dai-link로 잇고, 보드별 포맷·클럭을 정한다.
- `audio-routing`은 simple-card의 `routing`과 같은 "싱크, 소스" 쌍이다. `"Headphone Jack", "HP_L"`은 codec 핀 HP_L이 헤드폰 잭으로 간다는 뜻. `"LINPUT1", "Mic Jack"`과 `"Mic Jack", "MICB"`는 "마이크 잭 → codec 입력 LINPUT1", "마이크 바이어스 MICB → 마이크 잭"이다. **마이크 바이어스도 DAPM 위젯**이라 녹음할 때만 켜진다.
- `hp-det-gpio` — 헤드폰 잭 감지 GPIO(H4). jack 이벤트로 스피커/헤드폰 경로를 바꾼다.
- `audio-asrc = <&easrc>` — 하드웨어 샘플레이트 변환기를 경로에 끼울 수 있게 한다.

### 11.3 codec 노드 — I2C3 버스의 `wm8960@1a` (602~616행)

```dts
// arch/arm64/boot/dts/freescale/imx8mp-evk.dts:602-616 (6.18.55)
	wm8960: codec@1a {
		compatible = "wlf,wm8960";
		reg = <0x1a>;
		#sound-dai-cells = <0>;
		clocks = <&audio_blk_ctrl IMX8MP_CLK_AUDIOMIX_SAI3_MCLK1>;
		clock-names = "mclk";
		wlf,shared-lrclk;
		wlf,hp-cfg = <3 2 3>;
		wlf,gpio-cfg = <1 3>;
		AVDD-supply = <&reg_audio_3v3>;
		DBVDD-supply = <&reg_audio_1v8>;
		DCVDD-supply = <&reg_audio_1v8>;
		SPKVDD1-supply = <&reg_audio_pwr>;
		SPKVDD2-supply = <&reg_audio_pwr>;
	};
```

- `reg = <0x1a>` — I2C 주소 0x1a. codec 드라이버(`sound/soc/codecs/wm8960.c`)는 `module_i2c_driver`(1585행)로 등록되는 **I2C 드라이버**이고, 레지스터는 regmap(1396행 `wm8960_regmap`)으로 쓴다(H2, H5). DAPM 위젯이 레지스터 전원 비트를 이 regmap으로 토글한다.
- `clocks = <... IMX8MP_CLK_AUDIOMIX_SAI3_MCLK1>` — codec의 MCLK이 SoC의 SAI3 MCLK 출력에서 온다(H3의 clk). 그림 5의 MCLK 선이다.
- `AVDD-supply` 등 5개 — codec의 전원 레일. 아날로그 3.3 V, 디지털 1.8 V, 스피커 앰프 전원이 따로다. 어느 하나라도 regulator 노드가 잘못되면 codec probe가 `-EPROBE_DEFER`로 멈춘다(G3).

### 11.4 CPU DAI — `&sai3` (751~759행)와 SoC dtsi

```dts
// arch/arm64/boot/dts/freescale/imx8mp-evk.dts:751-759 (6.18.55)
&sai3 {
	pinctrl-names = "default";
	pinctrl-0 = <&pinctrl_sai3>;
	assigned-clocks = <&clk IMX8MP_CLK_SAI3>;
	assigned-clock-parents = <&clk IMX8MP_AUDIO_PLL1_OUT>;
	assigned-clock-rates = <12288000>;
	fsl,sai-mclk-direction-output;
	status = "okay";
};
```

- `assigned-clock-rates = <12288000>` — SAI3 루트 클럭을 오디오 PLL1에서 12.288 MHz로. 48 kHz × 256이다(§8.2).
- `fsl,sai-mclk-direction-output` — SAI가 MCLK 핀을 **출력**한다. 그래서 codec의 `clocks`가 SAI3 MCLK을 가리킨다.
- SoC 공통 `imx8mp.dtsi`(1445행 `sai3: sai@30c30000`)에는 `dmas = <&sdma2 4 2 0>, <&sdma2 5 2 0>; dma-names = "rx", "tx";`가 있다. generic dmaengine PCM이 이 이름으로 DMA 채널을 얻는다(§8.3). 보드 파일은 핀(`pinctrl_sai3`: TX_SYNC=LRCLK, TX_BCLK, RX_DATA00, TX_DATA00, MCLK)과 클럭만 정한다.

### 11.5 PDM 마이크 — `sound-micfil`(197~209행)과 `&micfil`(671~679행)

```dts
// arch/arm64/boot/dts/freescale/imx8mp-evk.dts:197-209 (6.18.55)
	sound-micfil {
		compatible = "fsl,imx-audio-card";
		model = "micfil-audio";

				sound-dai = <&micfil>;

	};
```

```dts
// arch/arm64/boot/dts/freescale/imx8mp-evk.dts:671-679 (6.18.55)
&micfil {
	#sound-dai-cells = <0>;
	pinctrl-names = "default";
	pinctrl-0 = <&pinctrl_pdm>;
	assigned-clocks = <&clk IMX8MP_CLK_PDM>;
	assigned-clock-parents = <&clk IMX8MP_AUDIO_PLL1_OUT>;
	assigned-clock-rates = <196608000>;
	status = "okay";

```

- micfil은 i.MX8MP의 **PDM 마이크 인터페이스 + 데시메이션 필터** 블록이다. dai-link에 codec이 없다(`cpu`만 있음). PDM 마이크는 제어 레지스터가 없으니 codec 드라이버가 필요 없다. 이 노트의 실습에서 `dmic-codec`을 붙인 자리를 machine 드라이버 `imx-card`가 ASoC 더미 codec으로 채운다(`sound/soc/fsl/imx-card.c:670`, `link->codecs = &snd_soc_dummy_dlc`).
- `assigned-clock-rates = <196608000>` — PDM 블록 클럭 196.608 MHz = 12.288 MHz × 16. 여기서 PDM 클럭(수 MHz)을 나눠 만든다. dtsi의 클럭 이름 `pll8k`·`pll11k`(1529행 이하)는 48k 계열과 44.1k 계열 PLL이다.
- 음성 웨어러블·로봇에서 가장 흔한 마이크 연결이 이것이다. MEMS 마이크 2~8개를 PDM으로 SoC에 바로 꽂는다.

### 11.6 simple-audio-card 실전 예 — `sound-bt-sco` (171~188행)

```dts
// arch/arm64/boot/dts/freescale/imx8mp-evk.dts:171-188 (6.18.55)
	sound-bt-sco {
		compatible = "simple-audio-card";
		simple-audio-card,name = "bt-sco-audio";
		simple-audio-card,format = "dsp_a";
		simple-audio-card,bitclock-inversion;
		simple-audio-card,frame-master = <&btcpu>;
		simple-audio-card,bitclock-master = <&btcpu>;

		btcpu: simple-audio-card,cpu {
			sound-dai = <&sai2>;
			dai-tdm-slot-num = <2>;
			dai-tdm-slot-width = <16>;
		};

		simple-audio-card,codec {
			sound-dai = <&audio_codec_bt_sco 1>;
		};
	};
```

- 블루투스 모듈의 PCM(SCO, 음성 통화) 포트를 SAI2에 잇는 **simple-audio-card**다. 이 노트 §9.2와 같은 문법이다.
- `format = "dsp_a"` + `bitclock-inversion` — I2S가 아니라 DSP_A(짧은 프레임 펄스) 형식에 BCLK 극성 반전.
- `frame-master`/`bitclock-master = <&btcpu>` — CPU(SAI2)가 클럭 provider. 이 노트에서 생략했던 속성을 명시한 예다.
- `dai-tdm-slot-num = <2>`, `dai-tdm-slot-width = <16>` — 2슬롯 × 16비트. 이 값으로 simple-card가 CPU DAI의 `.set_tdm_slot`을 부르고, BCLK = rate × 2 × 16이 된다(SCO 광대역이면 16 kHz × 32 = 512 kHz).

## 13. Embedded 실무에서 다시 보기

### 13.1 음성 웨어러블 — PDM 마이크 2개, 웨이크워드, 배터리

- 하드웨어: MEMS PDM 마이크 2개 → SoC의 PDM 컨트롤러(i.MX의 micfil 같은 블록) → DMA. codec 없음. 스피커는 I2S 디지털 앰프(제어 없는 클래스 D 앰프면 es7134처럼 "control 없는 codec"으로 표현된다).
- 캡처 설정: 16 kHz, S16_LE(또는 S32_LE), 2ch, period 10 ms(160 frame), periods 4. 웨이크워드 엔진이 10 ms 프레임을 먹는다.
- 전력: 대기 중에는 마이크 하나만 켜 두고 저전력 웨이크워드를 돌리는 구성이 흔하다(SoC의 저전력 DSP가 하기도 한다). DAPM 경로를 나눠 두면 "1채널 경로만 켜기"가 DT·mixer 설정으로 된다.
- 버그 사례: "가끔 단어 첫 음절이 잘린다" → 캡처 overrun 카운터부터 본다(§4.3). 처리 스레드가 USB·Wi-Fi 인터럽트 폭주에 밀리는 경우가 많다.

### 13.2 로봇 — 마이크 어레이 + 스피커 + 다른 서브시스템과 시간 맞추기

- 마이크 어레이(4~8ch)는 보통 TDM ADC(예: 8채널 TDM) 하나로 받는다. BCLK = 16 kHz × 8 × 32 = 4.096 MHz. 빔포밍·음원 방향 추정(DOA)을 하려면 **채널 간 샘플 정렬**이 절대적이다. 한 TDM 프레임 안의 채널은 같은 순간의 샘플이니, 마이크를 여러 I2S 포트에 나눠 꽂는 것보다 TDM 하나가 낫다.
- 다른 센서(카메라, IMU)와 오디오 시각을 맞추려면 `STATUS`의 `tstamp`(시스템 시각)와 `hw_ptr`(오디오 시각) 쌍, 또는 `audio_tstamp`를 쓴다. "이 `hw_ptr` 값이 이 `CLOCK_MONOTONIC` 시각"이라는 쌍을 주기적으로 기록하면 오디오 클럭과 시스템 클럭의 드리프트를 추정할 수 있다.
- 스피커 출력은 경고음·TTS라 latency보다 끊김 없는 것이 중요하다. 버퍼를 넉넉히(100 ms 이상).

### 13.3 "소리가 안 나요" — bring-up 순서

Don의 버스 디버깅 방식 그대로 아래에서 위로 간다.

1. `cat /proc/asound/cards` — 카드가 없으면 probe 문제. `dmesg`에서 codec I2C probe 실패, `-EPROBE_DEFER`(regulator·clk 미준비), DAI 이름 불일치(`ASoC: CPU DAI ... not registered`)를 찾는다.
2. 재생하면서 `/proc/asound/cardN/pcmXp/sub0/status`의 `hw_ptr` 확인 — 안 움직이면 DMA·IRQ·클럭 문제. SAI가 클럭을 못 받아 FIFO가 안 비는 경우가 흔하다.
3. 스코프·로직 분석기로 BCLK·LRCLK·SD·MCLK 측정 — 주파수가 §8.2 계산과 맞는지, provider/consumer 방향이 맞는지(두 쪽 다 클럭을 내거나 아무도 안 내는 경우), 포맷(I2S vs left-justified, 1비트 지연)이 맞는지. 포맷이 한 비트 어긋나면 소리는 나지만 크게 찌그러지거나 6 dB 작게 들린다.
4. `/sys/kernel/debug/asoc/<card>/.../dapm/` — 경로 위젯이 On인지. Off면 mixer 스위치(`amixer`의 `Switch` 항목)나 DT `routing`이 경로를 끊고 있다.
5. codec 레지스터 덤프 — regmap debugfs(`/sys/kernel/debug/regmap/<dev>/registers`)로 전원·뮤트 비트 확인.

### 13.4 PipeWire / PulseAudio는 어디에 있나

데스크톱형 리눅스(그리고 요즘 일부 임베디드 이미지)에서는 앱이 ALSA 장치를 직접 열지 않고 사운드 서버가 연다. 사운드 서버는 ALSA 장치를 하나 열어 큰 버퍼로 돌리고, 여러 앱의 스트림을 섞고(mixing), rate를 맞추고(resampling), 장치 전환을 처리한다. 결과적으로 사운드 서버의 버퍼만큼 지연이 더해진다. 음성 인식처럼 지연·정확한 타이밍이 중요한 임베디드 앱은 사운드 서버를 빼고 `hw:` 장치를 직접 열거나, PipeWire의 quantum(period에 해당)을 작게 설정한다. 이 노트의 랩에는 사운드 서버가 없어서 이 부분은 실행하지 않았다.

## 15. 면접에서 이렇게 말한다

**Q.** Explain the ALSA PCM ring buffer. What are hw_ptr and appl_ptr, and what is a period?

**A.** PCM 버퍼는 period 여러 개로 된 링이다. `hw_ptr`는 하드웨어(DMA)가 소비·생산한 위치, `appl_ptr`는 앱이 쓴·읽은 위치이고 둘 다 누적값이라 차이로 avail과 delay를 계산한다. period는 인터럽트 단위다. DMA가 period 하나를 끝낼 때마다 드라이버가 `snd_pcm_period_elapsed()`를 부르면 core가 `.pointer`로 `hw_ptr`를 갱신하고 xrun 판정이나 앱 깨우기를 한다.

> The buffer is a ring made of N periods. hw_ptr is where the DMA engine is, appl_ptr is where the application is, both are monotonically increasing counters so their difference gives available space and delay. A period is the interrupt granularity: each time DMA completes a period the driver calls snd_pcm_period_elapsed, the core reads the pointer callback, updates hw_ptr, and either wakes the writer or declares an xrun.

**꼬리 질문**: How do you choose period and buffer size? → buffer는 최대 지연과 xrun 여유, period는 깨움 주기·CPU 부하. 측정한 스케줄링 지연의 최악값보다 버퍼가 커야 한다.

**Q.** What is an xrun and how does an application recover?

**A.** 재생에서 데이터가 떨어지면 underrun, 캡처에서 앱이 늦게 읽어 덮이면 overrun. core는 avail이 stop_threshold 이상이면 스트림을 멈추고 XRUN 상태로 바꾼다. 앱의 다음 read/write가 `-EPIPE`를 받고, `PREPARE`로 포인터를 리셋한 뒤 다시 채워 시작한다. 실제로 200 ms 멈춰서 85 ms 버퍼가 xrun 나는 걸 측정했다. 캡처 overrun은 조용히 데이터가 빠지니 반드시 카운트해서 로그로 남긴다.

> Underrun on playback, overrun on capture. The core checks avail against stop_threshold on every pointer update and stops the stream in the XRUN state. The next read or write returns EPIPE; the app calls prepare, refills, and restarts. Capture overruns are silent data loss, so I always count and log them rather than just recovering.

**Q.** Which PCM callbacks run in atomic context, and why does it matter?

**A.** `trigger`와 `pointer`다. trigger는 스트림 spinlock을 잡고 IRQ를 끈 채 불린다. linked stream 동시 시작, 인터럽트 핸들러에서의 xrun 정지 같은 경로 때문이다. 그래서 trigger에서는 DMA 시작·정지 레지스터만 쓰고, I2C로 codec을 만지거나 sleep하면 안 된다. 직접 쓴 드라이버에서 `in_atomic=1 irqs_disabled=1`을 찍어 확인했다. 정지 후 기다리는 일은 `.sync_stop`에서 한다.

> Trigger and pointer. Trigger is called with the stream spinlock held and interrupts disabled, because streams can be linked and the core may stop a stream from interrupt context on xrun. So trigger only pokes DMA start and stop registers; codec I2C writes belong in hw_params, prepare or DAPM. Anything that must wait for an in-flight interrupt goes into sync_stop. If a driver truly needs to sleep there, it sets pcm->nonatomic.

**Q.** Describe the ASoC driver split. Why codec, platform/CPU DAI, and machine?

**A.** 재사용 때문이다. codec 드라이버는 칩(레지스터, DAPM 위젯, DAI 능력)만 알아서 모든 보드에 재사용되고, CPU DAI·platform 드라이버는 SoC의 I2S/TDM/PDM 컨트롤러와 DMA만 알아서 모든 보드에 재사용된다. 보드마다 다른 것(어느 SAI에 어느 codec, 포맷, 클럭 방향, MCLK 비율, 잭·스피커 연결)은 machine이 정하고, 요즘은 대부분 simple-audio-card나 audio-graph-card로 DT에 적는다. platform의 DMA는 보통 generic dmaengine PCM이 cyclic DMA로 처리한다.

> It's about reuse. The codec driver knows only the chip — registers, DAPM widgets, DAI capabilities — and works on any board. The CPU DAI and platform drivers know only the SoC's I2S or TDM controller and its DMA, usually through the generic dmaengine PCM with cyclic descriptors. Everything board-specific — which controller connects to which codec, format, who provides the clocks, MCLK ratio, routing to jacks and speakers — lives in the machine driver, today usually simple-audio-card or audio-graph-card in device tree.

**Q.** How do you compute BCLK for I2S and TDM, and what is MCLK for?

**A.** BCLK = 샘플레이트 × 슬롯 수 × 슬롯 비트 폭. I2S 48 kHz 16비트 2슬롯이면 1.536 MHz, 8슬롯 32비트 TDM 16 kHz면 4.096 MHz. LRCLK(frame sync)는 샘플레이트와 같다. MCLK은 codec의 내부 오버샘플링·PLL 기준 클럭으로 보통 256 fs(12.288 MHz)이고, DT의 `mclk-fs`로 machine이 계산해 `set_sysclk`로 넘긴다. 44.1k 계열은 11.2896 MHz라 SoC에 오디오 PLL이 두 개 있는 경우가 많다.

> BCLK is sample rate times slots times slot width: 48 kHz stereo 16-bit I2S is 1.536 MHz, eight 32-bit TDM slots at 16 kHz is 4.096 MHz. LRCLK equals the sample rate. MCLK is the codec's master clock for its oversampling and PLL, typically 256 fs, so 12.288 MHz for the 48 k family and 11.2896 for 44.1 k, which is why SoCs often have two audio PLLs.

**Q.** What is DAPM and how would you debug "no sound" on a new board?

**A.** DAPM은 codec과 보드를 위젯·라우트 그래프로 적어 두고, 활성 스트림에서 실제 끝점(스피커·마이크)까지 완전히 이어진 경로의 위젯만 전원을 켜는 프레임워크다. 재생 정지 후에는 팝 노이즈를 막으려고 pmdown_time(기본 5초) 뒤에 끈다. 무음 디버깅은 아래에서 위로: 카드 등록 여부, `/proc/.../status`의 `hw_ptr` 진행(=DMA·클럭), 스코프로 BCLK/LRCLK/데이터, 그다음 debugfs의 DAPM 위젯이 On인지, 마지막으로 codec 레지스터.

> DAPM models the codec and board as a graph of widgets and routes and powers only widgets on a complete path between an active stream and a real endpoint like a speaker or mic; playback paths power down after pmdown_time to avoid pops. For no sound I go bottom-up: is the card registered, is hw_ptr advancing in proc status, what do BCLK, LRCLK and data look like on the scope, are the path widgets On in the DAPM debugfs, and finally the codec registers through regmap debugfs.

**꼬리 질문**: The widgets are all On but still silence? → 뮤트·볼륨 kcontrol, DAI 포맷 불일치(데이터가 한 비트 밀림), codec이 MCLK을 못 받아 PLL 미동작.

**Q.** How would you capture from a microphone array with low and predictable latency?

**A.** 가능하면 TDM 하나로 모든 채널을 받아 샘플 정렬을 보장한다. `hw:`로 하드웨어 rate 그대로 열고(리샘플링 금지), period 10 ms·periods 3~4, 캡처 스레드는 SCHED_FIFO로 두고 처리는 별도 스레드로 넘긴다. overrun은 카운트하고, `hw_ptr`와 시스템 시각 쌍을 기록해 다른 센서와 시간을 맞춘다.

> One TDM link for all channels so samples are aligned, open the hw device at the native rate with no resampling, about 10 ms periods with three or four of them, a SCHED_FIFO capture thread that only copies into a ring for a processing thread, overrun counters, and timestamp pairs of hw_ptr and monotonic time to align with other sensors.

## 17. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| card | 사운드 카드 | 오디오 하드웨어 하나. `/proc/asound/cards` |
| PCM device / substream | 오디오 스트림 장치 / 동시에 열 수 있는 채널 | `pcmC0D0p` = card 0, device 0, playback |
| frame | 한 시점의 모든 채널 샘플 | S16_LE 스테레오 = 4바이트 |
| period | 인터럽트 단위 | DMA가 period 하나 끝낼 때 IRQ |
| buffer_size | 링버퍼 전체 크기 (frame) | period_size × periods |
| hw_ptr / appl_ptr | 하드웨어 위치 / 앱 위치 | 누적 카운터, 차이 = 대기 데이터 |
| avail / delay | 앱이 쓸·읽을 수 있는 양 / 출력까지 남은 양 | sw_params 판정의 기준 |
| hw_params / sw_params | 하드웨어 설정 / 커널 정책 설정 | 포맷·rate·period / threshold |
| refine | 파라미터 범위 좁히기 | 마스크·구간에 규칙 반복 적용 |
| XRUN | underrun(재생) 또는 overrun(캡처) | `-EPIPE`, `PREPARE`로 복구 |
| kcontrol | mixer 항목 | 볼륨·스위치·mux, `controlC0` |
| ASoC | ALSA System on Chip | codec / CPU DAI·platform / machine 분리 |
| DAI | Digital Audio Interface | I2S·TDM·PDM 포트의 한쪽 끝 |
| dai-link | CPU DAI와 codec DAI의 연결 | 하나가 PCM device 하나 |
| codec | 오디오 변환 칩 | DAC/ADC/앰프, 보통 I2C 제어 |
| machine | 보드 연결 설명 | simple-audio-card, fsl-asoc-card |
| generic dmaengine PCM | ASoC 공용 DMA PCM 구현 | cyclic DMA + residue pointer |
| DAPM | Dynamic Audio Power Management | 경로 기반 전원 관리 그래프 |
| widget / route | DAPM 노드 / 간선 | DAC, Mic / `{sink, control, source}` |
| pmdown_time | 재생 정지 후 전원 끄기 지연 | 기본 5000 ms, 팝 노이즈 방지 |
| BCLK / LRCLK / MCLK | 비트 클럭 / 프레임(좌우) 클럭 / codec 마스터 클럭 | rate×slots×bits / rate / 256 fs |
| TDM | 한 프레임에 N 슬롯 | 마이크 어레이·멀티채널 |
| PDM | 1비트 고속 스트림 | MEMS 디지털 마이크, 데시메이션 필요 |
| clock provider / consumer | 클럭을 내는 쪽 / 받는 쪽 | 옛 이름 master / slave |

## 18. 요약 & 체크리스트

ALSA는 오디오를 card·PCM device·substream과 control로 보이고, PCM은 period 여러 개로 된 링버퍼를 `hw_ptr`(하드웨어)와 `appl_ptr`(앱) 두 누적 포인터로 관리한다. 앱은 hw_params(포맷·rate·채널·period·buffer)와 sw_params(시작·정지 threshold, avail_min)를 정한 뒤 write/read하고, 드라이버는 DMA period 완료마다 `snd_pcm_period_elapsed()`를 불러 core가 `.pointer`로 위치를 갱신하고 xrun을 판정하게 한다. latency는 buffer/rate, 인터럽트 주기는 period/rate이고, 버퍼는 실측한 최악 스케줄링 지연보다 커야 한다. SoC에서는 ASoC가 이 드라이버를 codec(칩), CPU DAI·platform(SoC I2S/TDM/PDM 컨트롤러와 generic dmaengine PCM), machine(보드, 주로 simple-audio-card DT)으로 나누고, DAPM이 활성 스트림과 끝점 사이 경로의 위젯만 전원을 켠다. 이 노트에서는 snd-dummy·snd-aloop·직접 쓴 `i7_pcm`과 `i7_asoc` + es7134·dmic-codec·simple-audio-card로 이것들을 전부 실제로 돌려 확인했다.

- [ ] `/dev/snd/pcmC0D0p`, `controlC0`의 의미와 `/proc/asound`의 `status`로 스트림 상태를 읽을 수 있다
- [ ] hw_params의 각 항목과 frame·period·buffer 계산(바이트, 시간, 인터럽트 빈도)을 할 수 있다
- [ ] alsa-lib 없이 ioctl만으로 PCM을 열고 쓰고 읽는 C 코드를 짤 수 있다
- [ ] `hw_ptr`/`appl_ptr`/avail/delay를 그림으로 설명할 수 있다
- [ ] XRUN이 어디서 판정되고(`snd_pcm_update_state`) 앱이 어떻게 복구하는지 말할 수 있다
- [ ] period·buffer 크기를 latency·지터 측정에 근거해 고를 수 있다
- [ ] `snd_pcm_ops` 각 콜백의 역할과 컨텍스트(trigger·pointer = atomic)를 설명할 수 있다
- [ ] hrtimer·DMA 완료 콜백에서 위치 갱신 → `snd_pcm_period_elapsed()` 순서를 지키는 드라이버를 짤 수 있다
- [ ] mixer control(`snd_kcontrol_new`의 info/get/put)을 만들고 ioctl로 읽고 쓸 수 있다
- [ ] ASoC의 codec / CPU DAI·platform / machine 분리 이유와 각 드라이버가 아는 것을 설명할 수 있다
- [ ] simple-audio-card DT(dai-link, format, mclk-fs, widgets, routing)를 읽고 쓸 수 있고, BCLK·LRCLK·MCLK를 계산할 수 있다
- [ ] DAPM 위젯·라우트·pmdown_time을 debugfs로 관찰하고 "소리가 안 남"을 아래에서 위로 디버깅할 수 있다
