# I3. input 서브시스템 — input_dev, 이벤트 모델, evdev, gpio-keys, uinput

> **이 노트를 다 읽으면**: 버튼·조이스틱·터치가 "드라이버 → input core → 핸들러(evdev) → `/dev/input/eventN`"으로 흘러가는 길을 그림으로 설명할 수 있다 · `struct input_event`와 `SYN_REPORT` 패킷, `EV_KEY`/`EV_ABS`(absinfo의 fuzz·flat)/`EV_SW`/`SYN_DROPPED`의 뜻을 실제 출력으로 읽을 수 있다 · `devm_input_allocate_device` → capability 설정 → `input_register_device` → `input_report_*` + `input_sync`로 디바운스 버튼과 폴링 축을 가진 드라이버를 짤 수 있다 · gpio-keys DT 바인딩만으로 버튼을 붙이고, uinput으로 가짜 입력 장치를 만들어 테스트하고, `EVIOCGRAB`·`SYN_DROPPED`·wakeup을 직접 재현할 수 있다
> **왜 필요한가**: 로봇·드론의 비상 정지 버튼, 전원 키, 조그 다이얼, 조종용 조이스틱, HMI 터치스크린은 전부 input 장치다. bring-up 때 "버튼이 한 번 눌렀는데 세 번 들어온다", "터치 좌표가 반대다", "전원 키로 suspend에서 안 깨어난다"를 만나고, 면접에서는 "input 드라이버 뼈대를 써 보라", "IMU는 왜 input이 아니라 IIO인가", "`SYN_DROPPED`를 받으면 어떻게 하나"로 나온다
> **Don 기준 난이도**: 버튼 ISR + 디바운스 타이머 + 이벤트 큐는 펌웨어에서 늘 짜던 것 / 새로 배울 것은 "그 큐와 디바운스와 상태 관리를 커널 input core가 표준화해 두고, 드라이버는 `input_report_key()` 한 줄만 부른다"는 구조, evdev의 패킷·버퍼·grab 규칙, gpio-keys와 uinput 같은 "코드 없이 붙이는" 도구
> **선행 노트**: G2–G3(platform 드라이버·probe·devm), H4(gpiod, GPIO→IRQ, gpio-sim), F6(threaded IRQ·workqueue), A4(poll), D4(DT 문법)

## 0. 큰 그림 — 이게 왜 필요한가

### 0.1 펌웨어에서는 이렇게 했다

MCU에서 버튼 하나와 아날로그 조이스틱 하나를 처리하던 코드는 대략 이렇다.

```c
/* bare-metal 시절: 버튼 EXTI + 디바운스 타이머 + 이벤트 큐 */
static volatile uint32_t evq[32]; static volatile uint8_t evq_head, evq_tail;

void EXTI3_IRQHandler(void)            /* 버튼 핀 양쪽 엣지 */
{
	EXTI->PR = 1u << 3;
	TIM6->CNT = 0; TIM6->CR1 |= TIM_CR1_CEN;   /* 엣지마다 10 ms 타이머 재시작 */
}
void TIM6_IRQHandler(void)             /* 10 ms 동안 조용했다 = 안정 */
{
	TIM6->SR = 0; TIM6->CR1 &= ~TIM_CR1_CEN;
	uint32_t lvl = (GPIOA->IDR >> 3) & 1;
	if (lvl != last) { last = lvl; evq[evq_head++ & 31] = EVT_BTN | lvl; }
}
void adc_poll_20ms(void)               /* 조이스틱: 주기 샘플 + 데드존 */
{
	int v = ADC1->DR;
	if (abs(v - last_x) > 4) { last_x = v; evq[evq_head++ & 31] = EVT_JOY_X | v; }
}
```

여기에는 네 가지가 섞여 있다.

1. **하드웨어 접근**: 어느 핀, 어느 ADC 채널, 엣지 IRQ — 보드마다 다르다.
2. **신호 정리**: 디바운스, 데드존(노이즈 무시) — 장치 종류마다 비슷하다.
3. **이벤트 표현과 큐**: `EVT_BTN | lvl` 같은 사설 인코딩, 링버퍼, 오버플로 처리.
4. **소비자**: UI 태스크, 비상 정지 로직, 디버그 콘솔이 같은 큐를 나눠 읽는다.

Linux input 서브시스템은 3·4를 **전 시스템 공통 규격**으로 만들었다. 이벤트는 모두 `struct input_event {time, type, code, value}` 한 가지 모양이고, 큐는 읽는 프로세스마다 하나씩 커널(evdev)이 들고 있으며, 키 상태·자동 반복·노이즈 필터(fuzz)도 input core가 해 준다. 드라이버는 1(하드웨어)과 일부 2(디바운스)만 맡는다. 그래서 같은 앱(`evtest`, libinput, Qt, 로봇 텔레옵 노드)이 GPIO 버튼, USB 게임패드, I2C 터치, 가상 장치를 **구별 없이** 읽는다.

그림 1 — input 서브시스템의 3층. 아래 **드라이버**는 하드웨어를 읽고 `input_dev`에 이벤트를 보고만 한다. 가운데 **input core**가 상태·필터·배달을 맡고, 위 **핸들러**가 이벤트를 각자의 유저 인터페이스로 바꾼다. 장치 하나에 핸들러 여러 개가 동시에 붙는다(전원 키 하나가 `kbd`와 `evdev` 둘 다로 간다). uinput은 "유저 프로그램이 원천인 드라이버"다.

핵심 단어 세 개:

- **`struct input_dev`**: 입력 장치 하나. "나는 `EV_KEY`의 `KEY_POWER`를 낼 수 있다", "`ABS_X`는 0~1023이다" 같은 **capability 비트맵**과 현재 상태를 가진다. 드라이버가 만든다.
- **`struct input_handler`**: 이벤트를 받아 어딘가로 내보내는 소비자. `evdev`, `kbd`(VT 콘솔 키보드), `sysrq`, `leds`, 그리고 레거시 `mousedev`(`/dev/input/mice`), `joydev`(`/dev/input/js0`).
- **`struct input_handle`**: 장치 하나와 핸들러 하나를 잇는 연결선. 장치가 등록되면 input core가 모든 핸들러의 `id_table`과 비교해서(`match`) 맞으면 handle을 만든다(`connect`).

비유: input core는 **RTOS의 메시지 브로커**다. 드라이버(publisher)는 정해진 메시지 형식으로 발행만 하고, 핸들러(subscriber)는 장치 capability로 구독할지 정한다. 펌웨어에서 직접 짜던 `evq[]` 링버퍼는 evdev가 **읽는 fd마다 하나씩** 따로 들고 있다.

### 0.3 무엇이 input이고 무엇이 아닌가

| 장치 | 서브시스템 | 이유 |
|---|---|---|
| 버튼, 전원 키, 키패드, 조그 다이얼 | **input** (`EV_KEY`, `EV_REL`) | 사람이 만든 사건, 상태 변화만 의미 있음 |
| 덮개·도킹·헤드폰 잭 스위치 | **input** (`EV_SW`) | 켜짐/꺼짐 "상태"를 알림 |
| 조이스틱, 터치패드, 터치스크린 | **input** (`EV_ABS`, multitouch) | 사람의 조작을 좌표로 |
| IMU(가속도·자이로), ADC, 압력·온도 센서 | **IIO** (I2) | 연속 샘플링, 정확한 타임스탬프, 버퍼·트리거, 단위(scale) |
| 배터리 잔량, 칩 온도 | power_supply, hwmon/thermal (I4) | 시스템 상태 감시 |
| 카메라 | V4L2 (I5) | 프레임 스트림 |

옛날(2.6 시절)에는 노트북의 가속도계(낙하 감지, 화면 회전)를 `EV_ABS` 축 3개짜리 input 장치로 내보내는 드라이버가 많았다(`lis3lv02d` 계열이 대표적이다). 지금 새 센서 드라이버는 거의 다 **IIO**로 간다. 이유는 다음과 같다.

- input 이벤트는 "**변화했을 때만**" 나간다. fuzz 필터와 중복 제거가 값을 버린다. 센서 융합(칼만 필터)에는 **모든 샘플**과 **정확한 샘플 시각**이 필요하다.
- input에는 샘플링 주파수 설정, 하드웨어 FIFO·트리거·DMA 버퍼, 단위 변환(`scale`/`offset`) 같은 개념이 없다. IIO에는 다 있다.
- input 장치는 데스크톱 스택(libinput, 게임 라이브러리)이 자동으로 집어 간다. `EV_ABS` 축 3개짜리 가속도계가 조이스틱으로 오인되는 문제가 있어서, udev가 `ID_INPUT_ACCELEROMETER` 태그를 따로 붙여 구분해야 했다.

그래서 이 노트의 조이스틱 축도 "사람이 움직이는 스틱"이다. **로봇의 IMU는 I2 노트(IIO)에서** 다룬다. 면접에서 이 구분을 한 문장으로 말할 수 있어야 한다(§14).

## 1. 실습 판 — QEMU virt의 전원 키와 gpio-sim

이 노트의 실습은 공용 랩의 **서브시스템 커널** `out/Image-sub`(Linux `6.18.55-sub`)을 QEMU `virt` 머신으로 부팅해서 게스트 안에서 돌린다. 빌드 호스트는 Lima VM `elinux`(`uname -r` = `7.0.0-38-generic`)다. `Image-sub`를 쓰는 이유는 `uinput`이 모듈로 들어 있기 때문이다(기본 `Image`에는 `CONFIG_INPUT_UINPUT`이 꺼져 있다).

### 1.1 virt에 있는 것과 없는 것

| 필요한 것 | virt 머신에 | 이 노트의 해결 |
|---|---|---|

| 마음대로 흔들 수 있는 버튼 핀 | 없음 | **gpio-sim** 칩(H4) 4라인을 DT로 만들고, `sim_gpioN/pull`에 써서 엣지를 만든다 |
| 조이스틱 ADC | 없음 | 우리 드라이버 `i3_btn` 안의 가짜 ADC(삼각파 + 노이즈) |
| 가상 입력 장치 | — | `uinput.ko` (`out/modules-sub`에서 복사) |

### 1.2 예제 1 — DT 조각: gpio-sim 버튼 4개, `i3_btn`, gpio-keys, gpio-keys-polled

무엇을 확인하나: 이 노트의 모든 장치를 DT 하나에 담는다. `virt.dts` 사본 끝에 `#include`해서 C 전처리 → dtc로 dtb를 만든다(H4와 같은 방식).

```dts
/* i3_nodes.dtsi — gpio-sim bank + i3_btn + in-tree gpio-keys / gpio-keys-polled */
#include <dt-bindings/gpio/gpio.h>
#include <dt-bindings/input/input.h>

/ {
	i3-gpio-sim {
		compatible = "gpio-simulator";
		i3_sim: bank0 {
			gpio-controller;
			#gpio-cells = <2>;
			ngpios = <4>;
			gpio-sim,label = "i3_sim";
			gpio-line-names = "BTN_A", "BTN_B", "LID", "BTN_P";
		};
	};

	i3-btn {				/* our driver (section 4) */
		compatible = "dons,i3-btn";
		btn-gpios = <&i3_sim 0 GPIO_ACTIVE_HIGH>;
		linux,code = <KEY_A>;
		debounce-interval = <5>;
	};

	i3-keys {				/* in-tree gpio-keys, zero lines of C */
		compatible = "gpio-keys";
		label = "i3 gpio-keys";
		key-enter {
			label = "BTN_B";
			gpios = <&i3_sim 1 GPIO_ACTIVE_HIGH>;
			linux,code = <KEY_ENTER>;
			debounce-interval = <20>;
#ifndef I3_NO_SIM_WAKE
			wakeup-source;		/* gpio-sim irq can't wake: see section 9 */
#endif
		};
		lid {
			label = "LID";
			gpios = <&i3_sim 2 GPIO_ACTIVE_LOW>;
			linux,input-type = <EV_SW>;
			linux,code = <SW_LID>;
		};
	};

	i3-keys-polled {			/* no IRQ: sampled every poll-interval */
		compatible = "gpio-keys-polled";
		label = "i3 polled";
		poll-interval = <50>;
		key-p {
			label = "BTN_P";
			gpios = <&i3_sim 3 GPIO_ACTIVE_HIGH>;
			linux,code = <KEY_P>;
		};
	};
};

&{/gpio-keys/poweroff} {			/* QEMU's power key may wake us from s2idle */
	wakeup-source;
};
```

요점:

- `linux,code = <KEY_A>`의 `KEY_A`는 `include/dt-bindings/input/input.h`가 `linux-event-codes.h`를 가져와서 쓸 수 있는 매크로다. 유저 공간 헤더 `<linux/input-event-codes.h>`와 **같은 번호**(KEY_A=30, KEY_ENTER=28, KEY_P=25, KEY_POWER=116, SW_LID=0)다.
- gpio-sim 라인은 기본 상태가 `pull-down`(0)이다. 그래서 버튼은 `GPIO_ACTIVE_HIGH`로 두고 `pull-up` = "누름"으로 쓴다. 실제 보드의 버튼은 보통 풀업 + 버튼이 GND로 당기는 **active-low**다(그때는 `GPIO_ACTIVE_LOW`만 바꾸면 드라이버는 그대로다 — H4의 논리값/물리값).
- `LID`는 일부러 `GPIO_ACTIVE_LOW`로 뒀다. 핀이 0이면 논리 1 = "덮개 닫힘"이다(§7.3에서 확인).
- 마지막 블록은 QEMU가 만든 기존 노드 `/gpio-keys/poweroff`에 `wakeup-source` 속성만 덧붙인다(경로 참조 문법, D4).

빌드 스크립트와 부팅 스크립트:



`/proc/bus/input/devices` 한 블록을 줄별로 읽는 법:

| 줄 | 뜻 | 이 출력에서 |
|---|---|---|
| `I:` | `struct input_id` — 버스, VID, PID, 버전 | `Bus=0019` = `BUS_HOST`(SoC 내장) |
| `N:` / `P:` / `U:` | 이름, 물리 경로(phys), 고유 ID(uniq) | gpio-keys가 정한 고정 문자열 |
| `S:` | sysfs 경로 | platform 장치 `gpio-keys` 아래 `input0` |
| `H:` | 붙은 핸들러 | `kbd`와 `event0`(evdev) 두 개 |
| `B: EV=` | 지원 이벤트 타입 비트맵(16진) | `3` = bit0 `EV_SYN` + bit1 `EV_KEY` |
| `B: KEY=` | 지원 키 코드 비트맵, 64비트 word를 **높은 쪽부터** 공백으로 구분 | 두 번째 word가 0, 첫 word `0x10000000000000` = bit 52 → 64+52 = **116 = `KEY_POWER`** |

`/proc/bus/input/handlers`에서 evdev의 `Minor=64`는 evdev 노드가 major 13, minor 64부터 시작한다는 뜻이고, `/dev/input/event0`이 `13, 64`인 것과 맞는다. `sysrq (filter)`는 이벤트를 **가로채서 먹을 수 있는** 필터 핸들러다(Alt+SysRq 조합을 잡아 커널 기능을 실행하고 다른 핸들러에는 안 보낸다).

`/sys/class/input`에는 `input0`(장치 자체)과 `event0`(evdev 핸들러가 만든 char device) 두 개가 있다. **input 장치 하나 = inputN 하나, 그 위에 핸들러별 노드**라는 그림 1의 구조가 그대로 보인다.

## 2. 이벤트 모델 — `struct input_event` 하나로 모든 장치를

### 2.1 구조체 — 24바이트짜리 메시지

유저 공간이 `read()`로 받는 것은 이 구조체의 배열뿐이다 (`include/uapi/linux/input.h`).

```c
struct input_event {
	struct timeval time;   /* 64비트 유저: tv_sec, tv_usec (각 8바이트) */
	__u16 type;            /* EV_KEY, EV_ABS, ... */
	__u16 code;            /* KEY_A, ABS_X, SYN_REPORT, ... */
	__s32 value;           /* 1/0/2, 좌표, 상대 이동량 ... */
};
```

arm64 유저 공간에서의 메모리 배치:

```
offset  size  field
0x00    8     time.tv_sec    (input_event_sec)
0x08    8     time.tv_usec   (input_event_usec)
0x10    2     type
0x12    2     code
0x14    4     value
        ----
        24 bytes = sizeof(struct input_event) on arm64 / x86_64
```

32비트 유저 공간이 64비트 `time_t`로 빌드되면(`__USE_TIME_BITS64`) `timeval` 대신 `__kernel_ulong_t __sec, __usec`(각 4바이트)를 쓰고 매크로 `input_event_sec`/`input_event_usec`로 접근한다. 그래서 **이식성 있는 코드는 `ev.time.tv_sec` 대신 `ev.input_event_sec`를 쓴다**(이 노트의 `i3_evtest`가 그렇게 한다). 부호 없는 32비트 초라서 2038년 문제 대신 2106년까지 간다.

시간은 기본이 `CLOCK_REALTIME`이다. `EVIOCSCLOCKID`로 `CLOCK_MONOTONIC`(또는 `CLOCK_BOOTTIME`)으로 바꿀 수 있다. 이 노트의 출력은 전부 MONOTONIC이라 **dmesg 시각과 같은 축**에 있다. 이벤트 시각은 드라이버가 `input_set_timestamp()`로 IRQ 시각을 넣어 주지 않으면 input core가 `SYN_REPORT`를 처리하는 순간에 찍는다.

### 2.2 type · code · value

| type (값) | 무엇 | 대표 code | value의 뜻 |
|---|---|---|---|
| `EV_SYN` (0) | 구분자 | `SYN_REPORT`(0), `SYN_MT_REPORT`(2), `SYN_DROPPED`(3) | 보통 0 |
| `EV_KEY` (1) | 키·버튼 | `KEY_A`(30), `KEY_ENTER`(28), `KEY_POWER`(116), `BTN_LEFT`(0x110), `BTN_TOUCH`(0x14a) | 1 누름, 0 뗌, 2 자동 반복 |
| `EV_REL` (2) | 상대 이동 | `REL_X`, `REL_WHEEL` | 이번 보고 이후 이동량(±) |
| `EV_ABS` (3) | 절대 좌표 | `ABS_X`, `ABS_Y`, `ABS_PRESSURE`, `ABS_MT_POSITION_X` | 현재 위치 (absinfo 범위 안) |
| `EV_MSC` (4) | 기타 | `MSC_SCAN`(스캔 코드), `MSC_TIMESTAMP` | 장치 의존 |
| `EV_SW` (5) | 2상태 스위치 | `SW_LID`(0), `SW_TABLET_MODE`, `SW_HEADPHONE_INSERT` | 1 켜짐, 0 꺼짐 |
| `EV_LED` (0x11) | 장치 쪽 LED (유저 → 장치) | `LED_CAPSL`, `LED_NUML` | 1/0 |
| `EV_REP` (0x14) | 자동 반복 설정 | `REP_DELAY`, `REP_PERIOD` | ms |
| `EV_FF` (0x15) | 힘 피드백(진동) | 효과 id | 재생 횟수 |

`EV_KEY`와 `EV_SW`는 **상태**를 가진 타입이다. input core가 장치마다 `key[]`, `sw[]` 비트맵을 들고 있다가 **값이 바뀔 때만** 이벤트를 통과시킨다. 같은 키를 "눌림"으로 두 번 보고해도 두 번째는 버려진다(§5.3에서 실제로 본다). `EV_REL`은 상태가 없어서 0이 아닌 값은 매번 나간다.

### 2.4 `EV_ABS`와 absinfo — min, max, fuzz, flat, resolution

절대 축은 값 하나만으로는 의미가 없다. "0~1023 중 512"인지 "0~4095 중 512"인지 알아야 화면 좌표로 바꿀 수 있다. 그래서 축마다 `struct input_absinfo`가 있다.

| 필드 | 뜻 | 누가 쓰나 |
|---|---|---|
| `value` | 현재 값 (마지막으로 보고된 값) | `EVIOCGABS`로 언제든 조회 |
| `minimum` / `maximum` | 범위 | 소비자가 정규화 |
| `fuzz` | 노이즈 폭. input core가 이 범위 안의 흔들림을 걸러낸다 | **커널**(`input_defuzz_abs_event`) |
| `flat` | 중앙 데드존. 조이스틱이 이 범위 안이면 "중립" | **소비자**(joydev, 게임 라이브러리). 커널은 값을 바꾸지 않는다 |
| `resolution` | 단위당 개수. 터치는 units/mm, 회전축은 units/radian | 소비자(libinput이 mm로 환산) |

fuzz 필터는 단순한 저역 통과 필터다. 6.18 소스 그대로:

```c
static int input_defuzz_abs_event(int value, int old_val, int fuzz)
{
	if (fuzz) {
		if (value > old_val - fuzz / 2 && value < old_val + fuzz / 2)
			return old_val;

		if (value > old_val - fuzz && value < old_val + fuzz)
			return (old_val * 3 + value) / 4;

		if (value > old_val - fuzz * 2 && value < old_val + fuzz * 2)
			return (old_val + value) / 2;
	}

	return value;
}
```

변화가 `fuzz/2` 미만이면 **이전 값 그대로**(그러면 값이 안 바뀌었으니 이벤트가 사라진다), `fuzz` 미만이면 3:1 가중 평균, `2·fuzz` 미만이면 1:1 평균, 그 이상이면 그대로 통과. 펌웨어에서 짜던 "`abs(v - last) > 4`면 보낸다"보다 부드럽지만, **노이즈가 fuzz/2보다 크면 대부분 통과한다**는 점에 주의한다(§6.2에서 수치로 본다). 그리고 fuzz는 유저 공간이 `EVIOCSABS`로 바꿀 수 있다 — 보드마다 노이즈가 다르면 udev 규칙이나 앱에서 튜닝한다.

### 2.5 흔한 함정

- **`input_sync()`를 빠뜨림**: 이벤트가 `dev->vals[]`에 쌓이기만 하고 유저 공간에 안 나온다. 버퍼가 차면 core가 강제로 넘기지만 패킷 경계가 깨진다. "evtest에 아무것도 안 나온다"의 1순위 원인이다.
- **capability를 선언하지 않은 코드를 보고**: `input_set_capability()`로 등록하지 않은 `code`는 `input_get_disposition()`이 조용히 버린다. 에러 메시지도 없다.
- **`EV_KEY`를 "엣지"로 생각함**: value는 엣지가 아니라 **상태**다. 같은 상태를 두 번 보고하면 두 번째는 사라진다. 반대로 "눌림" 없이 "뗌"만 보고하면 core 입장에서 상태 변화가 없어 사라진다.
- **IMU를 `EV_ABS`로 내보냄**: §0.3. fuzz·중복 제거가 샘플을 버리고, 데스크톱이 조이스틱으로 집어 간다.

## 3. evdev — 유저 공간이 보는 `/dev/input/eventN`

### 3.1 예제 3 — `EVIOCG*` ioctl로 장치 신원 조회 (`i3_evinfo`)

무엇을 확인하나: 이벤트를 읽기 전에, 장치가 **무엇을 낼 수 있는지** evdev ioctl로 물어본다. `evtest`가 시작할 때 하는 일이다.

```c
/* i3_evinfo: what does an evdev node say about itself? (EVIOCG* ioctls) */
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <linux/input.h>

#define NB(x) (((x) + 8 * sizeof(long) - 1) / (8 * sizeof(long)))
#define TEST(b, n) ((b[(n) / (8 * sizeof(long))] >> ((n) % (8 * sizeof(long)))) & 1)
static const char *tn[EV_CNT] = { [EV_SYN] = "SYN", [EV_KEY] = "KEY", [EV_REL] = "REL",
	[EV_ABS] = "ABS", [EV_MSC] = "MSC", [EV_SW] = "SW", [EV_LED] = "LED", [EV_REP] = "REP" };
static const int max[EV_CNT] = { [EV_KEY] = KEY_MAX, [EV_REL] = REL_MAX, [EV_ABS] = ABS_MAX,
	[EV_MSC] = MSC_MAX, [EV_SW] = SW_MAX, [EV_LED] = LED_MAX, [EV_REP] = REP_MAX };

int main(int argc, char **argv)
{
	unsigned long ev[NB(EV_CNT)] = { 0 }, bits[NB(KEY_CNT)];
	char name[128] = "?", phys[128] = "";
	struct input_id id;
	int fd, ver;

	if (argc < 2 || (fd = open(argv[1], O_RDONLY)) < 0) { perror("open"); exit(1); }
	if (ioctl(fd, EVIOCGVERSION, &ver) < 0 || ioctl(fd, EVIOCGID, &id) < 0) {
		perror("ioctl"); exit(1);
	}
	ioctl(fd, EVIOCGNAME(sizeof(name)), name);
	ioctl(fd, EVIOCGPHYS(sizeof(phys)), phys);	/* may fail: phys is optional */
	printf("%s: \"%s\" phys=%s evdev=%#x bus=%#x vendor=%#x product=%#x\n", argv[1],
	       name, phys, ver, id.bustype, id.vendor, id.product);
	ioctl(fd, EVIOCGBIT(0, sizeof(ev)), ev);
	for (int t = 1; t < EV_CNT; t++) {
		if (!TEST(ev, t))
			continue;
		printf("  EV_%-3s codes:", tn[t] ? tn[t] : "?");
		ioctl(fd, EVIOCGBIT(t, sizeof(bits)), bits);
		for (int c = 0, n = 0; c <= max[t]; c++)
			if (TEST(bits, c) && n++ < 12)
				printf(" %d", c);
		printf("\n");
		for (int c = 0; t == EV_ABS && c <= ABS_MAX; c++) {
			struct input_absinfo a;
			if (TEST(bits, c) && ioctl(fd, EVIOCGABS(c), &a) == 0)
				printf("    abs %d: value=%d min=%d max=%d fuzz=%d flat=%d res=%d\n",
				       c, a.value, a.minimum, a.maximum, a.fuzz, a.flat, a.resolution);
		}
	}
	close(fd);
	return 0;
}
```

게스트에서 세 장치에 돌린 결과(전원 키, DT의 gpio-keys, §4의 `i3_btn` — 서로 다른 부팅의 출력을 모았다):

```text
/dev/input/event0: "gpio-keys" phys=gpio-keys/input0 evdev=0x10001 bus=0x19 vendor=0x1 product=0x1
  EV_KEY codes: 116
/dev/input/event1: "i3 gpio-keys" phys=gpio-keys/input0 evdev=0x10001 bus=0x19 vendor=0x1 product=0x1
  EV_KEY codes: 28
  EV_SW  codes: 0
/dev/input/event2: "i3_btn joystick" phys=i3_btn/input0 evdev=0x10001 bus=0x19 vendor=0 product=0
  EV_KEY codes: 30
  EV_ABS codes: 0
    abs 0: value=961 min=0 max=1023 fuzz=4 flat=8 res=0
```

출력에서 볼 것:

- `EVIOCGBIT(0, ...)`은 **타입** 비트맵, `EVIOCGBIT(EV_KEY, ...)`는 그 타입의 **코드** 비트맵이다. `/proc/bus/input/devices`의 `B:` 줄과 같은 정보를 ioctl로 받은 것이다.
- `evdev=0x10001`은 evdev 프로토콜 버전 `EV_VERSION`이다.
- gpio-keys 두 개가 **같은 phys `gpio-keys/input0`**을 가진다. gpio-keys 드라이버가 phys를 고정 문자열로 넣기 때문이다. phys로 장치를 구분하는 코드는 여기서 깨진다 — 이름이나 sysfs 경로를 써야 한다.
- `abs 0`(`ABS_X`)의 `value=961`은 마지막으로 보고된 값이다. 이벤트를 하나도 안 읽어도 `EVIOCGABS`로 **현재 상태**를 알 수 있다. 키도 마찬가지로 `EVIOCGKEY`, 스위치는 `EVIOCGSW`로 조회한다. 앱 시작 시 "지금 덮개가 닫혀 있나?"를 이걸로 안다.

### 3.2 예제 4 — 이벤트 읽기 프로그램 `i3_evtest`

무엇을 확인하나: `read()`로 `struct input_event`를 받아 출력하는 최소 evtest. 시간 축을 MONOTONIC으로 바꾸고, 옵션으로 `EVIOCGRAB`(독점)과 "느린 소비자"(이벤트 하나마다 `slow_ms` 잠듦) 모드를 넣었다. `SYN_DROPPED`를 받으면 `EVIOCGKEY`로 현재 키 상태를 다시 읽는다(§10.3).

```c
/* i3_evtest <dev> [secs] [g=grab] [slow_ms]: print input_event stream, monotonic stamps */
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <time.h>
#include <fcntl.h>
#include <poll.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <linux/input.h>

static const char *tname(int t)
{
	static const char *n[] = { "EV_SYN", "EV_KEY", "EV_REL", "EV_ABS", "EV_MSC", "EV_SW" };
	return t < 6 ? n[t] : "EV_?";
}

int main(int argc, char **argv)
{
	int secs = argc > 2 ? atoi(argv[2]) : 5, slow = argc > 4 ? atoi(argv[4]) : 0;
	int clk = CLOCK_MONOTONIC, fd, n = 0, pk = 0, drops = 0;
	struct input_event ev;
	struct timespec t0, t;

	if (argc < 2 || (fd = open(argv[1], O_RDONLY)) < 0) { perror("open"); exit(1); }
	if (ioctl(fd, EVIOCSCLOCKID, &clk) < 0) { perror("EVIOCSCLOCKID"); exit(1); }
	if (argc > 3 && argv[3][0] == 'g') {
		if (ioctl(fd, EVIOCGRAB, 1) < 0) { perror("EVIOCGRAB"); exit(1); }
		printf("%s: grabbed\n", argv[1]);
	}
	fflush(stdout);
	clock_gettime(CLOCK_MONOTONIC, &t0);
	for (;;) {
		clock_gettime(CLOCK_MONOTONIC, &t);
		int left = secs * 1000 - (int)((t.tv_sec - t0.tv_sec) * 1000 +
					      (t.tv_nsec - t0.tv_nsec) / 1000000);
		struct pollfd p = { .fd = fd, .events = POLLIN };
		if (left <= 0 || poll(&p, 1, left) <= 0)
			break;
		if (slow)
			usleep(slow * 1000);	/* a slow consumer: one event per slow ms */
		if (read(fd, &ev, sizeof(ev)) != sizeof(ev)) {
			if (errno != ENODEV) { perror("read"); exit(1); }
			printf("%s: read -> ENODEV (device unregistered)\n", argv[1]);
			break;
		}
		n++;
		if (ev.type == EV_SYN && ev.code == SYN_REPORT)
			pk++;
		if (!slow || ev.type != EV_SYN || ev.code == SYN_DROPPED)
			printf("[%5ld.%06ld] %-6s code=%-3d value=%d%s\n",
			       (long)ev.input_event_sec, (long)ev.input_event_usec, tname(ev.type),
			       ev.code, ev.value, ev.type == EV_SYN ? (ev.code ?
			       "   <-- SYN_DROPPED" : "   ---- SYN_REPORT") : "");
		if (ev.type == EV_SYN && ev.code == SYN_DROPPED) {	/* resync from state */
			unsigned char k[KEY_MAX / 8 + 1] = { 0 };
			int down = 0;
			drops++;
			ioctl(fd, EVIOCGKEY(sizeof(k)), k);
			for (unsigned i = 0; i < sizeof(k); i++)
				down += __builtin_popcount(k[i]);
			printf("  resync: EVIOCGKEY says %d key(s) down now\n", down);
		}
		fflush(stdout);
	}
	printf("%s: %d events, %d SYN_REPORT, %d SYN_DROPPED\n", argv[1], n, pk, drops);
	return 0;
}
```

설명을 위해 이벤트를 하나씩 `read()`했지만, 실제 앱은 `struct input_event buf[64]`로 **한 번에 여러 개** 읽는다. evdev의 `read`는 버퍼가 이벤트 하나보다 작으면 `-EINVAL`을 돌려주고, 들어가는 만큼의 **완성된 이벤트만** 복사한다. 그리고 `SYN_REPORT`로 닫힌 패킷까지만 내준다 — 드라이버가 아직 `input_sync()`를 안 부른 반쪽 패킷은 `read`에 안 보인다(`client->packet_head`). `O_NONBLOCK`으로 열면 큐가 비었을 때 `-EAGAIN`, 장치가 사라지면 `-ENODEV`이고 `poll()`은 `POLLHUP | POLLERR`을 낸다.

### 3.3 예제 5 — QEMU 모니터로 전원 키 누르기

무엇을 확인하나: 진짜 IRQ 경로(PL061 GPIO 3번 → gpio-keys → evdev)로 들어오는 이벤트를 본다. QEMU `virt`는 모니터 명령 `system_powerdown`을 받으면 이 DT 부팅 구성에서는 PL061 GPIO 3번 라인을 올렸다 내린다(아래 출력으로 확인). 이 핀이 DT의 `gpio-keys/poweroff`(`linux,code = <0x74>` = 116)다.

QEMU를 모니터 유닉스 소켓과 함께 띄우고, `expect`가 게스트 콘솔을 조종하면서 중간에 VM에서 `socat`으로 모니터 명령을 보낸다(H12와 같은 방식).

```sh
# run_pwr.exp 의 핵심 부분
spawn qemu-system-aarch64 -machine virt -cpu cortex-a57 -m 512M -nographic \
  -kernel /var/lab/out/Image-sub -initrd $W/i.gz -dtb $W/i3nw.dtb \
  -monitor unix:$W/i3_mon.sock,server=on,wait=off -append "console=ttyAMA0 quiet"
# 게스트: /i3_evtest /dev/input/event0 4 > /tmp/p.txt & sleep 1
# VM:    (echo 'system_powerdown'; sleep 0.5) | socat - UNIX-CONNECT:$W/i3_mon.sock
```

게스트 콘솔(expect 기록, 터미널 줄바꿈만 합침):

```text
~ # dmesg -n 1; grep -E 'pl061|gpio-keys|GPIO Key' /proc/interrupts; cat /sys/devices/platform/gpio-keys/power/wakeup
 21:          0 9030000.pl061   3 Edge      GPIO Key Poweroff
enabled
~ # /i3_evtest /dev/input/event0 4 > /tmp/p.txt & sleep 1
~ # wait; cat /tmp/p.txt; grep -E 'GPIO Key' /proc/interrupts
[    1.950513] EV_KEY code=116 value=1
[    1.950513] EV_SYN code=0   value=0   ---- SYN_REPORT
[    2.049659] EV_KEY code=116 value=0
[    2.049659] EV_SYN code=0   value=0   ---- SYN_REPORT
/dev/input/event0: 4 events, 2 SYN_REPORT, 0 SYN_DROPPED
 21:          2 9030000.pl061   3 Edge      GPIO Key Poweroff
```

출력에서 볼 것:

- `/proc/interrupts`: IRQ 21은 GIC가 아니라 **PL061의 3번 핀**(`9030000.pl061 3 Edge`)이고, 이름 `GPIO Key Poweroff`는 DT의 `label`이다. gpio-keys가 `gpiod_to_irq()` → `request_any_context_irq()`로 양쪽 엣지를 걸었다. 키 한 번에 카운트가 0 → 2(누름 엣지 + 뗌 엣지).
- 누름과 뗌 사이가 약 **100 ms**(1.950513 → 2.049659)다. QEMU가 라인을 올린 뒤 약 100 ms 뒤에 내린다는 뜻이다(QEMU 소스를 확인하지는 않았고, 측정값이다).
- 이 부팅의 DT는 `i3nw`(§9에서 설명하는 "gpio-sim 키에 wakeup-source를 뺀" 버전)다. 전원 키 쪽은 기본 virt와 같다.
- 게스트에 `acpid`나 systemd-logind 같은 "KEY_POWER를 받으면 끄는" 데몬이 없어서 아무 일도 안 일어난다. **전원 키를 누르면 꺼지는 것은 커널이 아니라 유저 공간 정책**이다. 임베디드 장비에서 "전원 버튼 3초 = 종료"를 구현하려면 이 이벤트를 읽는 데몬이 필요하다.

### 3.4 evdev ioctl 한눈에

| ioctl | 방향 | 하는 일 |
|---|---|---|
| `EVIOCGVERSION` | 읽기 | evdev 프로토콜 버전 |
| `EVIOCGID` | 읽기 | `struct input_id` (bus, vendor, product, version) |
| `EVIOCGNAME(len)` / `EVIOCGPHYS` / `EVIOCGUNIQ` | 읽기 | 이름, 물리 경로, 고유 ID 문자열 |
| `EVIOCGPROP(len)` | 읽기 | 장치 속성(`INPUT_PROP_DIRECT` = 터치스크린, `INPUT_PROP_POINTER` = 터치패드) |
| `EVIOCGBIT(type, len)` | 읽기 | type 0이면 지원 타입, 아니면 그 타입의 지원 코드 비트맵 |
| `EVIOCGKEY` / `EVIOCGSW` / `EVIOCGLED` | 읽기 | 현재 눌린 키, 스위치, LED 상태 비트맵 |
| `EVIOCGABS(axis)` / `EVIOCSABS(axis)` | 읽기/쓰기 | absinfo 조회 / fuzz 등 변경 |
| `EVIOCGRAB` (1/0) | 쓰기 | 이 fd가 장치를 **독점**. 다른 evdev 클라이언트와 kbd 핸들러에 이벤트가 안 간다 |
| `EVIOCREVOKE` | 쓰기 | 이 fd를 영구 무효화 (세션 전환 시 compositor가 사용) |
| `EVIOCSCLOCKID` | 쓰기 | timestamp 시계 선택 (REALTIME/MONOTONIC/BOOTTIME) |
| `EVIOCSMASK` | 쓰기 | 이 fd가 받을 이벤트 종류를 필터링 |
| `EVIOCGREP` / `EVIOCSREP` | 읽기/쓰기 | 자동 반복 지연·주기 |

권한: `/dev/input/event0`은 `crw------- root`였다(§1.3). 데스크톱 배포판은 udev 규칙으로 `input` 그룹에 읽기 권한을 준다. 임베디드 장비에서 일반 사용자 서비스가 버튼을 읽게 하려면 udev 규칙이나 그룹 설정이 필요하다 — **키 입력은 비밀번호 입력이기도 하므로 world-readable로 만들면 안 된다**.

## 4. 드라이버 쪽 — `input_dev`를 만들고 등록하고 보고하기

### 4.1 다섯 단계

| 단계 | API | 펌웨어 비유 |
|---|---|---|
| 1. 할당 | `devm_input_allocate_device(dev)` | 이벤트 디스크립터 구조체 하나 |
| 2. 신원 | `input->name`, `phys`, `id.bustype` | 장치 이름표 |
| 3. capability | `input_set_capability(input, EV_KEY, KEY_A)`, `input_set_abs_params(input, ABS_X, min, max, fuzz, flat)` (직접 비트를 켜는 옛 방식: `__set_bit(EV_KEY, input->evbit); __set_bit(KEY_A, input->keybit);`) | "이 장치는 이런 메시지만 낸다" 선언 |
| 4. 등록 | `input_register_device(input)` | 브로커에 publisher 등록. 이 순간 핸들러가 붙고 `/dev/input/eventN`이 생긴다 |
| 5. 보고 | `input_report_key/abs/rel/switch(...)` 후 `input_sync(input)` | 큐에 메시지 넣고 "패킷 끝" |

`devm_input_allocate_device()`로 만든 장치는 **등록도 자동 관리**된다. 드라이버가 unbind되면 devm이 `input_unregister_device()`를 불러 준다. 그래서 `remove` 콜백이 필요 없다. 등록한 뒤에는 `input_free_device()`를 부르면 안 된다(이중 해제) — devm을 쓰면 이 실수를 아예 할 수 없다.

보고 함수는 전부 `input_event(dev, type, code, value)`의 얇은 래퍼다. `input_report_key(dev, code, v)`는 `v`를 `!!v`로 0/1로 바꾼다. 이 함수들은 **어느 문맥에서나**(hard IRQ 포함) 부를 수 있다. 내부에서 `dev->event_lock`을 `spin_lock_irqsave`로 잡기 때문이다. 그러나 값을 얻으려고 I2C를 읽는 일은 잠들 수 있으므로 threaded IRQ나 work에서 한다(F6).

### 4.2 예제 6 — `i3_btn`: 디바운스 버튼 + 폴링 조이스틱 축 (세 조각을 합쳐 한 파일)

무엇을 확인하나: gpio-keys가 하는 일을 직접 짜 본다. GPIO 엣지 IRQ → 디바운스용 `delayed_work` → 안정된 값을 `EV_KEY`로 보고. 같은 `input_dev`에 가짜 ADC로 만든 `EV_ABS` 조이스틱 축을 붙이고, 그 축은 input core의 **poller**(`input_setup_polling`)가 20 ms마다 읽는다. 실험용으로 sysfs `stats`(카운터)와 `debounce_ms`(쓰기)를 둔다.

조각 1 — IRQ와 디바운스 work:

```c
// SPDX-License-Identifier: GPL-2.0
/* i3_btn: gpio-keys-like button (IRQ + debounce work) + polled fake-ADC joystick axis */
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/gpio/consumer.h>
#include <linux/interrupt.h>
#include <linux/input.h>
#include <linux/workqueue.h>
#include <linux/random.h>
#include <linux/property.h>

struct i3_btn {
	struct input_dev *input;
	struct gpio_desc *gpiod;
	struct delayed_work work;
	unsigned int code, debounce_ms;
	atomic_t raw_edges;
	unsigned int works, polls, adc;
	int dir, hold;
};

/* hard-IRQ side: only count and (re)arm the debounce timer */
static irqreturn_t i3_btn_isr(int irq, void *data)
{
	struct i3_btn *b = data;

	atomic_inc(&b->raw_edges);
	mod_delayed_work(system_wq, &b->work, msecs_to_jiffies(b->debounce_ms));
	return IRQ_HANDLED;
}

/* process context: line has been quiet for debounce_ms -> sample and report */
static void i3_btn_work(struct work_struct *w)
{
	struct i3_btn *b = container_of(to_delayed_work(w), struct i3_btn, work);
	int v = gpiod_get_value_cansleep(b->gpiod);	/* gpio-sim can sleep */

	if (v < 0)
		return;
	b->works++;
	input_report_key(b->input, b->code, v);
	input_sync(b->input);
}
```

조각 2 — 폴링 콜백(가짜 ADC)과 sysfs:

```c
/* input-poller callback: a fake 10-bit ADC = triangle wave + noise, held at the top */
static void i3_btn_poll(struct input_dev *input)
{
	struct i3_btn *b = input_get_drvdata(input);
	int noise = (int)(get_random_u32() % 7) - 3;	/* -3..+3 LSB */

	b->polls++;
	if (b->hold) {				/* holding: only noise moves */
		if (--b->hold == 0)
			b->dir = -1;
	} else {
		b->adc += b->dir * 64;
		if (b->adc >= 960)
			b->hold = 50;		/* hold at 960 for 50 polls */
		if (b->adc <= 64)
			b->dir = 1;
	}
	input_report_abs(input, ABS_X, clamp_t(int, b->adc + noise, 0, 1023));
	input_sync(input);
}

static ssize_t stats_show(struct device *dev, struct device_attribute *a, char *buf)
{
	struct i3_btn *b = dev_get_drvdata(dev);

	return sysfs_emit(buf, "raw_edges=%d works=%u polls=%u debounce_ms=%u\n",
			  atomic_read(&b->raw_edges), b->works, b->polls, b->debounce_ms);
}
static DEVICE_ATTR_RO(stats);

static ssize_t debounce_ms_store(struct device *dev, struct device_attribute *a,
				 const char *buf, size_t n)
{
	struct i3_btn *b = dev_get_drvdata(dev);
	int ret = kstrtouint(buf, 0, &b->debounce_ms);

	atomic_set(&b->raw_edges, 0);		/* new experiment: reset counters */
	b->works = 0;
	return ret ? ret : n;
}
static DEVICE_ATTR_WO(debounce_ms);

static struct attribute *i3_btn_attrs[] = {
	&dev_attr_stats.attr, &dev_attr_debounce_ms.attr, NULL };
ATTRIBUTE_GROUPS(i3_btn);

static void i3_btn_cancel(void *data)
{
	cancel_delayed_work_sync(data);
}
```

```c
static int i3_btn_probe(struct platform_device *pdev)
{
	struct device *dev = &pdev->dev;
	struct i3_btn *b;
	int irq, err;

	b = devm_kzalloc(dev, sizeof(*b), GFP_KERNEL);
	if (!b)
		return -ENOMEM;
	b->adc = 512;
	b->dir = 1;
	if (device_property_read_u32(dev, "linux,code", &b->code))
		return dev_err_probe(dev, -EINVAL, "linux,code missing\n");
	if (device_property_read_u32(dev, "debounce-interval", &b->debounce_ms))
		b->debounce_ms = 5;			/* same default as gpio-keys */
	b->gpiod = devm_gpiod_get(dev, "btn", GPIOD_IN);
	if (IS_ERR(b->gpiod))
		return dev_err_probe(dev, PTR_ERR(b->gpiod), "btn-gpios\n");
	INIT_DELAYED_WORK(&b->work, i3_btn_work);

	b->input = devm_input_allocate_device(dev);
	if (!b->input)
		return -ENOMEM;
	b->input->name = "i3_btn joystick";
	b->input->phys = "i3_btn/input0";
	b->input->id.bustype = BUS_HOST;
	input_set_capability(b->input, EV_KEY, b->code);
	input_set_abs_params(b->input, ABS_X, 0, 1023, 4, 8);	/* fuzz 4, flat 8 */
	input_set_drvdata(b->input, b);

	err = input_setup_polling(b->input, i3_btn_poll);
	if (err)
		return err;
	input_set_poll_interval(b->input, 20);			/* 50 Hz "ADC" */

	err = input_register_device(b->input);
	if (err)
		return err;
	platform_set_drvdata(pdev, b);

	irq = gpiod_to_irq(b->gpiod);
	if (irq < 0)
		return irq;
	err = devm_add_action_or_reset(dev, i3_btn_cancel, &b->work);
	if (err)
		return err;
	err = devm_request_irq(dev, irq, i3_btn_isr,
			       IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING, "i3_btn", b);
	if (err)
		return err;
	dev_info(dev, "code=%u debounce=%ums irq=%d -> %s\n", b->code, b->debounce_ms,
		 irq, dev_name(&b->input->dev));
	return 0;
}

static const struct of_device_id i3_btn_of[] = {
	{ .compatible = "dons,i3-btn" }, { }
};
MODULE_DEVICE_TABLE(of, i3_btn_of);
```

- **IRQ 핸들러는 세기만 한다.** gpio-sim은 `can_sleep = true`인 칩이라(값을 읽을 때 mutex를 잡는다) hard IRQ에서 `gpiod_get_value()`를 부르면 gpiolib이 WARN을 낸다(H4 §5.5). 그래서 읽기는 work에서 `_cansleep`으로 한다. SoC 내장 GPIO라면 hrtimer로 더 짧은 지연을 낼 수 있다 — 실제 gpio-keys가 정확히 이 분기를 한다(§7.4).
- **`mod_delayed_work()`가 디바운스의 전부다.** 엣지가 올 때마다 타이머를 처음부터 다시 건다. 마지막 엣지 뒤 `debounce_ms` 동안 조용해야 work가 돈다. 펌웨어의 "엣지마다 TIM6 카운터 0으로" 그대로다.
- **work는 "값"을 보고하지 "엣지"를 보고하지 않는다.** 바운스 중간에 잘못 읽어도 상태가 같으면 input core가 버린다(§5.3).
- 정리 순서: devm은 등록의 **역순**으로 푼다. `devm_request_irq`(마지막 등록) → `i3_btn_cancel`(work 취소) → input 장치 해제 순이다. IRQ가 먼저 사라지므로 취소된 work가 다시 걸릴 수 없고, work가 끝난 뒤 input 장치가 사라진다. 이 순서를 맞추려고 `devm_add_action_or_reset()`을 IRQ 요청 **직전**에 넣었다.
- `input_setup_polling()`을 쓰면 드라이버가 타이머를 직접 만들 필요가 없다. 옛날 `input_polled_dev` 구조체는 5.x에서 사라졌고, 지금은 일반 `input_dev`에 poller를 붙인다.

### 5.2 예제 8 — 바운스 패턴 × 디바운스 시간 측정

무엇을 확인하나: 엣지 간격과 개수를 정확히 조절한 "채터링 누름"을 만들어, `debounce_ms` 0 / 5 / 20에서 raw 엣지·work 실행·키 이벤트 수를 센다. 바운스 생성기는 `sim_gpio0/pull` 파일에 `pwrite()`로 `pull-up`/`pull-down`을 번갈아 쓰는 정적 C 프로그램이다.

```c
/* i3_bounce <pull-file> <bounces> <gap_us> <hold_ms>: one press + one release, each
 * preceded by <bounces> chatter edges <gap_us> apart (a bouncing mechanical contact) */
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>

static int fd;
static void set(int up)
{
	const char *s = up ? "pull-up" : "pull-down";
	if (pwrite(fd, s, up ? 7 : 9, 0) < 0) { perror("pwrite"); exit(1); }
}
static void edge(int level, int bounces, int gap_us)
{
	for (int i = 0; i < bounces; i++) {	/* level, !level, level, ... */
		set(i % 2 == 0 ? level : !level);
		usleep(gap_us);
	}
	set(level);				/* final settled level */
}

	return 0;
}
```

- **debounce 5, 5×12 ms**: 바운스 간격(12 ms)이 디바운스 시간보다 길면 각 바운스가 "안정된 누름"으로 보인다. 상세 출력의 이벤트 간격이 정확히 약 12 ms다.
- **debounce 20**: 모든 패턴에서 2개. 대가는 지연이다 — 마지막 바운스 후 20 ms(실제로는 아래 jiffies 반올림 때문에 그 이상)가 지나야 누름이 보고된다.

### 5.3 해석 — jiffies 반올림과 input core의 중복 제거

**왜 5 ms가 6 ms 간격까지 버텼나?** 랩 커널은 `CONFIG_HZ=250`, jiffy 하나가 4 ms다. `msecs_to_jiffies(5)`는 올림으로 2 jiffies이고, `delayed_work`는 "지금 tick부터 2번째 tick"에 돌므로 실제 지연은 **4~8 ms** 사이 어딘가다. 6 ms 간격이 이번 실행에서 걸러진 것은 그 범위 안의 운이고, 경계 근처라 실행마다 달라질 수 있다. 반대로 `debounce_ms=1`은 1 jiffy = 0~4 ms라 사실상 "다음 tick"이다. 정확한 ms 디바운스가 필요하면 **hrtimer**를 쓴다 — gpio-keys가 잠들지 않는 GPIO에서 그렇게 한다(§7.4).

**왜 `works=9`인데 `key_events=8`인가?** (debounce 5, 5×12 ms 행) work가 9번 돌았지만 그중 한 번은 직전과 같은 값을 읽었다. `input_report_key()`는 호출됐지만 input core의 `input_get_disposition()`이 "`key[]` 비트가 이미 그 값"이라고 보고 이벤트를 버렸다(§2.2). 드라이버가 상태 비교를 안 해도 중복이 유저에게 새지 않는 이유가 이것이다. 단, **반대 방향 오류(누름을 놓침)는 core가 못 막는다** — 그건 디바운스 시간과 샘플 시점의 문제다.

현장 기준값: 택트 스위치 5~20 ms, 큰 기계식 스위치·릴레이 접점 20~50 ms. 비상 정지처럼 **안전 기능은 input 디바운스에 맡기지 않는다** — 하드웨어 인터록이 먼저고, 소프트웨어 이벤트는 보고용이다(§12).

### 6.1 예제 9 — poller는 "열려 있을 때만" 돈다, 그리고 `inhibited`

무엇을 확인하나: `input_setup_polling()`의 poller가 언제 도는지, 그리고 `kbd` 핸들러가 장치를 열어 두는 문제를 확인한다. sysfs `inhibited` 속성(5.11부터)은 장치를 강제로 "닫힌" 상태로 만든다 — 드라이버의 `close()`가 불리고, poller가 멈추고, 이벤트가 버려진다(`boot.sh i3 abs`).

```sh
I=$(readlink -f /sys/class/input/${E##*/}/device)      # .../i3-btn/input/input2
grep -A5 'i3_btn joystick' /proc/bus/input/devices | grep H:
```

머무는 구간(값 ≥ 955)만 세는 짧은 Python 스크립트를 VM에서 같은 출력 파일에 돌렸다.

```python
import sys
s = open(sys.argv[1]).read().split('ABS_SERIES_BEGIN')[1].split('ABS_SERIES_END')[0].split()
t = list(map(float, s[0::2])); v = list(map(int, s[1::2]))
runs, cur = [], []
for a, b in zip(t, v):
    if b >= 955: cur.append((a, b))
    elif cur: runs.append(cur); cur = []
if cur: runs.append(cur)
print("all ABS events:", len(v))
for i, r in enumerate(runs, 1):
    print(f"hold {i}: {len(r)} events  t={r[0][0]:.6f}..{r[-1][0]:.6f}  values {sorted(set(x[1] for x in r))}")
```

50 poll 중 17~23개만 나갔다. 노이즈는 ±3, fuzz는 4다. §2.4의 규칙대로 변화가 2 미만(`fuzz/2`)이면 버려지고, 2~3이면 평균을 내서 **값이 바뀌면 통과**한다. 그래서 절반 넘게 걸러졌지만 다 걸러지지는 않았다. 그리고 값이 버려진 poll은 `SYN_REPORT`도 안 보인다. input core는 값 없이 `SYN_REPORT`만 있는 패킷을 핸들러에 넘기지 않는다. 출력의 `SYN_REPORT: 101`은 `grep -c`가 evtest 마지막 요약 줄(`... N SYN_REPORT, 0 SYN_DROPPED`)까지 센 것이라, 실제 패킷 수는 100 = `EV_ABS` 수와 같다. 165번 보고 → 100개 패킷이다.

실무 판단: 노이즈를 확실히 죽이려면 fuzz를 노이즈 진폭의 2배 이상으로 잡는다. 그러나 fuzz는 **해상도를 깎는다**(작은 움직임도 버린다). 정밀 조작이 필요한 조이스틱은 fuzz를 작게 두고 데드존(`flat`)을 소비자가 적용하게 한다.

## 7. gpio-keys — 버튼에는 보통 코드를 쓰지 않는다

### 7.1 DT 바인딩

§4의 `i3_btn`이 한 일(엣지 IRQ, 디바운스, 보고)은 커널에 이미 `drivers/input/keyboard/gpio_keys.c`로 있다. 보드에 버튼이 있으면 **DT 노드만 쓰는 것이 정답**이고, 직접 드라이버를 쓰면 리뷰에서 거절된다. 바인딩은 `Documentation/devicetree/bindings/input/gpio-keys.yaml`.

| 속성 | 위치 | 뜻 |
|---|---|---|
| `compatible = "gpio-keys"` | 부모 | 인터럽트 방식. 폴링은 `"gpio-keys-polled"` + `poll-interval`(ms) |
| `label` | 부모 | input 장치 이름 (`N: Name=`) |
| `autorepeat` | 부모 | `EV_REP` 켜기 (누르고 있으면 value=2 반복) |
| `gpios` | 자식(키 하나) | 버튼 핀과 극성 플래그 |
| `interrupts` | 자식 | GPIO 대신(또는 함께) 쓸 IRQ. GPIO 없이 IRQ만 있으면 "뗌" 엣지를 못 보므로 `debounce-interval` 뒤 자동 뗌 |
| `linux,code` | 자식 | 보낼 코드 (`KEY_POWER`, `SW_LID` …) |
| `linux,input-type` | 자식 | 기본 `EV_KEY`(1). 스위치면 `EV_SW`(5), 축이면 `EV_ABS`(3) + `linux,input-value` |

| `wakeup-source` | 자식 | 이 키로 suspend에서 깨운다 (§9) |
| `wakeup-event-action` | 자식 | 누름에만/뗌에만/둘 다 깨울지 (`EV_ACT_ASSERTED` 등) |
| `linux,can-disable` | 자식 | sysfs `disabled_keys`로 런타임에 끌 수 있게 |

### 7.2 예제 11 — gpio-sim 위의 gpio-keys: 코드 0줄로 같은 결과

무엇을 확인하나: §1.2 DT의 `i3-keys` 노드(ENTER 키 + LID 스위치)가 커널 내장 gpio-keys로 바인딩되는지, 채터링 누름이 디바운스되는지, `EV_SW`가 어떻게 보이는지 본다. 이어서 `gpio-keys-polled` 모듈을 올려 폴링 방식의 약점을 본다 (`boot.sh i3 gpiokeys`).

```sh

echo "keys=$(cat $K/keys) switches=$(cat $K/switches) wakeup=$(cat $K/power/wakeup)"
grep -E "i3_sim|BTN|LID" /sys/kernel/debug/gpio
./i3_evtest $E 4 > /tmp/k.txt &
sleep 0.5; ./i3_bounce $SIM/sim_gpio1/pull 9 2000 300      # 채터링 ENTER (9 x 2 ms)
sleep 0.3; pull 2 pull-up; sleep 0.3; pull 2 pull-down     # LID: active-low
wait; cat /tmp/k.txt
insmod /gpio_keys_polled.ko; sleep 0.5; P=$(ev "i3 polled"); echo "polled: $P"
./i3_evtest $P 2 > /tmp/p.txt &
sleep 0.5; pull 3 pull-up; sleep 0.02; pull 3 pull-down; sleep 0.3; pull 3 pull-up; sleep 0.3; pull 3 pull-down
wait; grep -v SYN /tmp/p.txt
```

출력에서 볼 것:

- **디바운스**: 채터링 9엣지 × 2회(누름·뗌)가 `KEY_ENTER` 1/0 **두 이벤트**로 줄었다. `debounce-interval = <20>`이 일했다.
- **`EV_SW`와 극성**: `LID`는 `GPIO_ACTIVE_LOW`다. 부팅 때 핀이 0(`pull-down`)이므로 논리값 1 = 덮개 닫힘 상태로 시작했다. `pull-up`(핀 1) → `SW_LID 0`(열림), `pull-down`(핀 0) → `SW_LID 1`(닫힘). 앱이 "지금" 상태를 알고 싶으면 이벤트를 기다리지 말고 `EVIOCGSW`로 묻는다.
- **sysfs `keys`/`switches`**: gpio-keys가 제공하는 속성으로, 이 장치가 내는 코드 목록(28 = ENTER, 0 = SW_LID)이다. `disabled_keys`/`disabled_switches`에 쓰면 런타임에 끌 수 있다(`linux,can-disable`이 있는 키만).
- **`/sys/kernel/debug/gpio`**: gpio-keys가 라인 1·2를 입력으로 요청했다. `can sleep` 칩이다. 라인 이름 `BTN_B`, `LID`는 DT의 `gpio-line-names`다(라인 0·3은 아직 요청되지 않아 목록에 없다).
- **gpio-keys-polled의 약점**: 세 번의 `pull-up` 중 첫 번째(20 ms만 유지)는 **놓쳤다**. `poll-interval = <50>`이라 50 ms마다 한 번 읽는데, 그 사이에 올라갔다 내려간 펄스는 보이지 않는다. 300 ms 유지한 두 번째 누름만 잡혔다(6.27 → 6.55, 약 0.28초). IRQ를 못 거는 핀(일부 I2C 확장기, IRQ 라인이 없는 보드)에서만 쓰고, 폴링 주기 < 가장 짧은 누름 시간의 절반으로 잡는다.

### 7.3 gpio-keys 안의 분기 — 하드웨어 디바운스, hrtimer, work

6.18의 `gpio_keys_setup_key()` 핵심을 요약하면 이렇다(소스에서 옮긴 것, 일부 생략).

```c
if (button->debounce_interval) {
	error = gpiod_set_debounce(bdata->gpiod, button->debounce_interval * 1000);
	/* use timer if gpiolib doesn't provide debounce */
	if (error < 0)
		bdata->software_debounce = button->debounce_interval;
	/* reading won't sleep -> hrtimer instead of a standard timer */
	bdata->debounce_use_hrtimer = !gpiod_cansleep(bdata->gpiod);
}
...
isr = gpio_keys_gpio_isr;
irqflags = IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING;
```

1. 먼저 **GPIO 컨트롤러에 하드웨어 디바운스**를 부탁한다(`gpiod_set_debounce` → 칩 드라이버의 `set_config(PIN_CONFIG_INPUT_DEBOUNCE)`). i.MX·TI·Rockchip 등 많은 SoC GPIO 블록에 디바운스 필터가 있다. 성공하면 소프트웨어 타이머가 필요 없다.
2. 실패하면(gpio-sim은 `set_config`가 풀업/풀다운만 처리한다) 소프트웨어 디바운스.
3. 칩이 잠들지 않으면 **hrtimer**(정밀, 콜백은 원자 문맥에서 `gpiod_get_value`), 잠들 수 있으면 **delayed work**(jiffies 해상도, `_cansleep`). 우리 랩은 gpio-sim이라 work 경로다 — `i3_btn`과 같은 선택이다.

그리고 ISR 첫머리에서 `wakeup` 키면 `pm_stay_awake()`를 부르고, suspend 중에 IRQ가 왔으면 **누름을 바로 보고한다**("깨운 키를 이미 뗐을 수도 있으니 누름을 흉내 낸다"는 주석이 있다). §9에서 이 경로를 실제로 밟는다.

## 8. 다른 입력 장치들 — 매트릭스 키패드, 로터리 인코더, 터치스크린

이 절의 DT는 **실행하지 않았다**(랩 커널에 해당 드라이버가 꺼져 있고, virt에 하드웨어가 없다). 바인딩 이름과 속성은 6.18 소스의 `Documentation/devicetree/bindings/input/`에서 확인했다.

### 8.1 매트릭스 키패드 — 핀 8개로 키 16개

4×4 키패드는 행 4 + 열 4 = GPIO 8개로 16키를 읽는다. 드라이버가 열을 하나씩 구동하고 행을 읽는 **스캔**을 한다(펌웨어에서 짜던 그 루프다). `gpio-matrix-keypad.yaml`:

```dts
keypad {
	compatible = "gpio-matrix-keypad";
	row-gpios = <&gpio2 0 GPIO_ACTIVE_LOW>, <&gpio2 1 GPIO_ACTIVE_LOW>,
		    <&gpio2 2 GPIO_ACTIVE_LOW>, <&gpio2 3 GPIO_ACTIVE_LOW>;
	col-gpios = <&gpio2 4 GPIO_ACTIVE_LOW>, <&gpio2 5 GPIO_ACTIVE_LOW>,
		    <&gpio2 6 GPIO_ACTIVE_LOW>, <&gpio2 7 GPIO_ACTIVE_LOW>;
	linux,keymap = <MATRIX_KEY(0, 0, KEY_1) MATRIX_KEY(0, 1, KEY_2)
			MATRIX_KEY(0, 2, KEY_3) MATRIX_KEY(0, 3, KEY_A)
			/* ... 16 entries: (row, col, code) ... */>;
	debounce-delay-ms = <20>;
	col-scan-delay-us = <20>;
	wakeup-source;
};
```

`linux,keymap`의 각 항목은 `MATRIX_KEY(row, col, code)` 매크로가 32비트 하나로 접는다(`include/dt-bindings/input/input.h`). 공통 파서는 `matrix-keymap.c`(`CONFIG_INPUT_MATRIXKMAP=y`가 랩에도 켜져 있다). 키를 여러 개 동시에 누르면 생기는 **고스트 키**는 다이오드 없는 매트릭스의 하드웨어 한계다. I2C 키패드 컨트롤러(TCA8418 등)는 스캔을 칩이 하고 IRQ로 알린다.

### 8.2 로터리 인코더 — 조그 다이얼

A/B 두 상(quadrature) 신호의 엣지 순서로 방향을 안다. `rotary-encoder.yaml`:

```dts
rotary {
	compatible = "rotary-encoder";
	gpios = <&gpio3 10 GPIO_ACTIVE_LOW>, <&gpio3 11 GPIO_ACTIVE_LOW>;
	linux,axis = <REL_WHEEL>;		/* 0x08 */
	rotary-encoder,relative-axis;		/* EV_REL: +1/-1 per detent */
	rotary-encoder,steps-per-period = <4>;
	wakeup-source;
};
```

`relative-axis`가 있으면 `EV_REL`(바퀴처럼 "몇 칸 돌았나"), 없으면 `EV_ABS`(`rotary-encoder,steps` 범위의 절대 위치, `rollover`로 감김). 디텐트(딸깍) 하나가 몇 엣지인지가 `steps-per-period`다. 로봇 HMI의 "메뉴 다이얼"은 보통 REL로 하고, "속도 노브"는 ABS로 한다. 고속 회전(모터 엔코더)은 이 드라이버가 아니라 **counter 서브시스템**이나 eQEP 같은 하드웨어 카운터로 간다 — 엣지마다 IRQ를 받는 구조라 수 kHz를 못 따라간다.

### 8.3 I2C 터치스크린과 멀티터치

정전식 터치 컨트롤러(FocalTech FT5x06, Goodix GT911 등)는 I2C 장치 + 인터럽트 핀 + 리셋 핀이다. `edt-ft5x06.yaml`의 예제(바인딩 문서에서 옮김):

```dts
touchscreen@38 {
	compatible = "edt,edt-ft5406";
	reg = <0x38>;
	interrupt-parent = <&gpio2>;
	interrupts = <5 IRQ_TYPE_EDGE_FALLING>;
	reset-gpios = <&gpio2 6 GPIO_ACTIVE_LOW>;
	wake-gpios = <&gpio4 9 GPIO_ACTIVE_HIGH>;
	/* common properties (touchscreen.yaml): */
	touchscreen-size-x = <800>;
	touchscreen-size-y = <480>;
	touchscreen-inverted-x;
	touchscreen-swapped-x-y;
};
```

`touchscreen-*` 공통 속성은 드라이버가 `touchscreen_parse_properties()`로 읽고, 보고할 때 `touchscreen_report_pos()`가 뒤집기·축 교환을 적용한다. **"터치 좌표가 반대다"는 거의 항상 이 속성 문제**이고 드라이버 수정이 필요 없다. 드라이버 구조는 I2C 드라이버(H5) + threaded IRQ(F6)에서 I2C로 터치 레지스터를 읽고 보고하는 형태다 — IRQ 문맥에서 잠드는 I2C를 못 하니 반드시 threaded IRQ다.

**멀티터치(MT) 프로토콜 B — slot**: 손가락 여러 개를 보고하려고 `ABS_MT_*` 축과 **slot**을 쓴다. slot은 "손가락 자리 번호", `ABS_MT_TRACKING_ID`는 "그 자리에 있는 손가락의 신원"(-1이면 손가락이 떨어짐)이다. 바뀐 slot만 보내므로 대역폭이 작다. 드라이버 쪽 코드 모양(실행하지 않음, `input-mt.h` API):

```c
/* probe */
input_set_abs_params(in, ABS_MT_POSITION_X, 0, 799, 0, 0);
input_set_abs_params(in, ABS_MT_POSITION_Y, 0, 479, 0, 0);
input_mt_init_slots(in, 5, INPUT_MT_DIRECT | INPUT_MT_DROP_UNUSED);
/* threaded IRQ: for each finger read over I2C */
input_mt_slot(in, id);
input_mt_report_slot_state(in, MT_TOOL_FINGER, down);
if (down) {
	touchscreen_report_pos(in, &prop, x, y, true);   /* applies invert/swap */
}
input_mt_sync_frame(in);   /* emulates BTN_TOUCH/ABS_X for single-touch readers */
input_sync(in);
```

스트림은 `ABS_MT_SLOT 0, ABS_MT_TRACKING_ID 45, ABS_MT_POSITION_X …, SYN_REPORT`처럼 보인다. 그래서 `input_estimate_events_per_packet()`가 slot 수만큼 패킷이 크다고 추정하고 evdev 버퍼를 키운다(§10.3). `INPUT_MT_DIRECT`는 `INPUT_PROP_DIRECT`(화면 위 직접 터치 = 터치스크린)를 켠다.

## 9. 웨이크업 — 버튼으로 suspend에서 깨우기

### 9.1 무엇이 필요한가

키로 깨우려면 세 층이 다 맞아야 한다.

1. **DT**: 키 노드에 `wakeup-source`. gpio-keys가 `device_init_wakeup(dev, true)`로 장치를 "깨울 수 있음"으로 표시한다(`power/wakeup = enabled`).
2. **드라이버 suspend 콜백**: gpio-keys의 `gpio_keys_suspend()`가 키 IRQ에 `enable_irq_wake()`를 건다.
3. **IRQ 칩**: 그 IRQ를 실제로 깨움 신호로 만들 수 있어야 한다(`irq_chip.irq_set_wake`, 또는 `IRQCHIP_SKIP_SET_WAKE`). SoC라면 GPIO 블록 → 웨이크업 컨트롤러(i.MX의 GPC, TI의 wakeup gen) → PMIC 경로까지 이어져야 한다.

### 9.2 예제 12 — gpio-sim 키에 `wakeup-source`를 달면 suspend가 실패한다

무엇을 확인하나: §1.2 DT 그대로(`i3-keys/key-enter`에 `wakeup-source`) s2idle(`echo freeze > /sys/power/state`)에 들어가 본다. 같은 expect 세션에서 전원 키도 눌렀다.

- 이 실행에서 30초 타이머로 띄운 evtest가 받은 `KEY_POWER`(11.099)는 suspend와 상관없이 그 뒤에 보낸 `system_powerdown`이다.

### 9.3 예제 13 — 전원 키로 s2idle에서 깨어나기

무엇을 확인하나: gpio-sim 키의 `wakeup-source`를 뺀 DT(`mkdtb.sh i3nw -DI3_NO_SIM_WAKE`)로 다시 부팅해서, s2idle에 들어간 뒤 5초쯤 지나 VM에서 `system_powerdown`을 보낸다. 전원 키(PL061) 노드에는 §1.2에서 `wakeup-source`를 붙여 두었다.

```sh
# run_pwr.exp (발췌): 게스트에 freeze 명령을 보내고, 6초 뒤 모니터로 전원 키
send "cat /sys/power/state; /i3_evtest /dev/input/event0 30 > /tmp/s.txt & sleep 1; date +%s; echo freeze > /sys/power/state; date +%s\r"
sleep 6
hmp "system_powerdown"
```

## 10. uinput — 유저 공간에서 입력 장치 만들기 (그리고 테스트하기)

### 10.1 예제 14 — 가상 키보드 + 축 장치를 만들고 이벤트 주입

uinput은 `/dev/uinput`(misc 장치, 10:223)에 ioctl로 capability를 설정하고 `UI_DEV_CREATE`하면 **진짜 `input_dev`가 커널에 등록**되는 드라이버다. 그다음 `write()`한 `struct input_event`가 그 장치의 이벤트로 input core에 들어간다. 쓰임새:

- **테스트**: 하드웨어 없이 앱(HMI, 텔레옵 노드, 키 데몬)의 입력 처리를 자동 시험한다. CI에서 "전원 키 3초 → 종료 시퀀스"를 검증할 수 있다.
- **브리지**: 네트워크 리모컨, 블루투스 게임패드 유저 공간 스택, 원격 데스크톱이 받은 입력을 로컬 입력 장치로 만든다.
- **변환기**: 키 리매핑 데몬, 조이스틱 → 키보드 매핑.

무엇을 확인하나: 키(QWERTY 윗줄 + H)와 `ABS_X`를 가진 장치를 만들고 "h, i, 축 100, 축 100(같은 값), 축 900 + P 누름, P 뗌"을 주입해서 `i3_evtest`로 읽는다.

```c
/* i3_uinput <wait_s> demo|flood<N>: create a virtual key+abs device, inject events */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <linux/uinput.h>

static int fd;
static void emit(int type, int code, int val)
{
	struct input_event ie = { .type = type, .code = code, .value = val };
	if (write(fd, &ie, sizeof(ie)) != sizeof(ie)) { perror("write"); exit(1); }
}
static void key(int code)		/* press + release = 2 packets */
{
	emit(EV_KEY, code, 1); emit(EV_SYN, SYN_REPORT, 0);
	emit(EV_KEY, code, 0); emit(EV_SYN, SYN_REPORT, 0);
}

int main(int argc, char **argv)
{
	struct uinput_setup us = { .id = { BUS_VIRTUAL, 0x1234, 0x5678, 1 } };
	struct uinput_abs_setup as = { .code = ABS_X,
		.absinfo = { .minimum = 0, .maximum = 1023, .fuzz = 0, .resolution = 0 } };
	char sys[64];

	if (argc < 3) { fprintf(stderr, "usage: %s wait_s demo|floodN\n", argv[0]); exit(1); }
	if ((fd = open("/dev/uinput", O_WRONLY)) < 0) { perror("/dev/uinput"); exit(1); }
	ioctl(fd, UI_SET_EVBIT, EV_KEY);
	for (int k = KEY_Q; k <= KEY_P; k++)		/* top letter row */
		ioctl(fd, UI_SET_KEYBIT, k);
	ioctl(fd, UI_SET_KEYBIT, KEY_H);
	ioctl(fd, UI_SET_EVBIT, EV_ABS);
	ioctl(fd, UI_SET_ABSBIT, ABS_X);
	strcpy(us.name, "i3 virtual pad");
	if (ioctl(fd, UI_DEV_SETUP, &us) < 0 || ioctl(fd, UI_ABS_SETUP, &as) < 0 ||
	    ioctl(fd, UI_DEV_CREATE) < 0) { perror("UI_DEV_*"); exit(1); }
	ioctl(fd, UI_GET_SYSNAME(sizeof(sys)), sys);
	printf("uinput: created /sys/devices/virtual/input/%s\n", sys);
	fflush(stdout);
	sleep(atoi(argv[1]));			/* give readers time to open eventN */

	if (!strcmp(argv[2], "demo")) {
		key(KEY_H); key(KEY_I);
		emit(EV_ABS, ABS_X, 100); emit(EV_SYN, SYN_REPORT, 0);
		emit(EV_ABS, ABS_X, 100); emit(EV_SYN, SYN_REPORT, 0);	/* same value */
		emit(EV_ABS, ABS_X, 900); emit(EV_KEY, KEY_P, 1); emit(EV_SYN, SYN_REPORT, 0);
		emit(EV_KEY, KEY_P, 0); emit(EV_SYN, SYN_REPORT, 0);
	} else if (!strncmp(argv[2], "flood", 5)) {
		int n = atoi(argv[2] + 5);
		for (int i = 0; i < n; i++)
			key(KEY_Q + i % 10);
		printf("uinput: flooded %d key press/release pairs (%d events)\n", n, n * 4);
	}
	sleep(1);
	ioctl(fd, UI_DEV_DESTROY);
	close(fd);
	return 0;
}
```

### 10.2 예제 15 — `EVIOCGRAB`: 한 프로세스가 장치를 독점

무엇을 확인하나: 같은 장치를 리더 A(일반)와 리더 B(grab)가 열고, 세 번째 프로그램이 또 grab을 시도한다 (`boot.sh i3 grab`).

```sh

./i3_evtest $E 3 > /tmp/g1.txt &
./i3_evtest $E 3 g > /tmp/g2.txt & sleep 0.5

wait; echo "--- reader A (no grab)"; cat /tmp/g1.txt; echo "--- reader B (grab)"; tail -3 /tmp/g2.txt
```

출력에서 볼 것:

- 리더 B가 15개를 다 받는 동안 리더 A는 **0개**다. 두 번째 grab 시도는 `EBUSY`.
- evdev의 grab은 evdev 클라이언트끼리의 독점만이 아니다. `evdev_grab()`이 `input_grab_device()`로 **장치 수준 grab**을 걸어서 같은 장치의 **다른 핸들러(`kbd`)도 이벤트를 못 받는다**(§11의 `input_pass_values()`가 `dev->grab`부터 본다). X 서버나 Wayland compositor가 키보드를 grab하는 이유가 이것이다 — 그래야 그래픽 세션에서 친 키가 뒤의 VT 콘솔에 함께 입력되지 않는다.
- grab은 fd가 닫히면 자동으로 풀린다. 그러나 grab한 프로세스가 멈춰(hang) 있으면 **그 장치는 시스템 전체에서 먹통**이 된다. 현장에서 "키보드가 갑자기 안 먹는다"의 원인 중 하나다. `EVIOCGRAB`은 꼭 필요할 때만(키오스크 앱, 리매퍼) 쓴다.

### 10.3 예제 16 — `SYN_DROPPED`: 느린 리더의 버퍼가 넘칠 때

evdev는 **클라이언트(fd)마다 링버퍼**를 하나씩 가진다. 크기는 장치가 등록될 때 정해진다(6.18 `evdev.c`).

```c
#define EVDEV_MIN_BUFFER_SIZE	64U
#define EVDEV_BUF_PACKETS	8

static unsigned int evdev_compute_buffer_size(struct input_dev *dev)
{
	unsigned int n_events =
		max(dev->hint_events_per_packet * EVDEV_BUF_PACKETS,
		    EVDEV_MIN_BUFFER_SIZE);

	return roundup_pow_of_two(n_events);
}
```

`hint_events_per_packet`은 `input_estimate_events_per_packet()`가 정한다: MT slot 수 + 1, 축마다 +1(MT 축은 slot 수만큼), REL 축마다 +1, 그리고 키·MSC 몫으로 +7. 우리 가상 장치는 MT 없음 → 1 + `ABS_X` 1 + 7 = 9 → 9 × 8 = 72 → 2의 거듭제곱으로 올려 **128 이벤트**다(소스에서 계산한 값이고 직접 측정하지는 않았다). 축이 없는 gpio-keys는 64다. 멀티터치 10 slot 터치스크린은 이보다 훨씬 크다.

### 10.4 libevdev — 실제 앱은 이걸 쓴다

위의 재동기화, 비트맵 조회, 이벤트 이름 출력(`KEY_A` 같은 문자열)을 매번 직접 짜지 않도록 freedesktop.org의 **libevdev**가 있다. `libevdev_new_from_fd()` → `libevdev_next_event()`가 `SYN_DROPPED`를 받으면 `LIBEVDEV_READ_STATUS_SYNC`를 돌려주고 **동기화용 가짜 이벤트들을 만들어 준다**. 같은 라이브러리의 `libevdev_uinput_create_from_device()`는 기존 장치를 복제한 uinput 장치를 만든다(테스트에 유용). 데스크톱의 libinput과 `evemu`(이벤트 녹화·재생 도구)가 libevdev 위에 있다. 장비에서 이벤트를 녹화해 두고 CI에서 uinput으로 재생하는 테스트가 이 조합으로 가능하다. 이 노트는 원리를 보이려고 raw ioctl을 썼지만, 제품 코드에서는 libevdev(MIT 라이선스)를 권한다. 게스트에 libevdev가 없어서 이 노트에서는 실행하지 않았다.

드라이버 작성과 연결되는 지점:

- **`file_operations`를 직접 안 쓴다.** char device(A3, G6)를 만들면 `read`/`poll`/버퍼/권한/핫플러그를 다 짜야 하지만, input 드라이버는 `input_dev`만 등록하면 evdev가 그것을 전부 제공한다. I1 노트의 "서브시스템에 등록하라"의 가장 깔끔한 예다.
- **`dev->open`/`dev->close` 콜백**: 첫 사용자가 열 때 하드웨어를 켜고(터치 IC 전원, IRQ enable) 마지막 사용자가 닫을 때 끈다. poller는 이 콜백을 자동으로 쓴다. 단, `kbd` 핸들러가 `EV_KEY` 장치를 늘 열어 둔다는 것(§6.1)을 기억한다.
- **문맥**: `input_event()`는 원자 문맥 OK. 값을 얻는 쪽(I2C 읽기)이 잠들면 threaded IRQ(F6) — 터치·키패드 컨트롤러 드라이버의 표준 모양이다.
- **`dev->event` 콜백(`INPUT_PASS_TO_DEVICE`)**: 반대 방향(유저 → 장치) 이벤트. 유저가 `EV_LED`(Caps Lock LED)나 `EV_FF`(진동)를 `write`하면 드라이버의 `event`가 불린다.
- **PM**: `wakeup-source` → `device_init_wakeup()` → suspend 콜백에서 `enable_irq_wake()`(§9). runtime PM과는 `inhibited`/`open`·`close`로 연결된다.
- **USB HID**: H12의 `usbhid`가 받은 report를 `hid-input`이 HID usage → input 코드로 바꿔 `input_event()`를 부른다. 그래서 USB 키보드도 똑같이 `/dev/input/eventN`이다.

## 12. Embedded 실무에서 다시 보기

### 12.1 로봇 컨트롤 박스의 버튼 패널

예를 들어 센서 키트를 단 이동 로봇의 컨트롤 박스에 "전원", "모드", "정지 요청" 버튼과 덮개 스위치가 있다고 하자. 보드 DT는 이렇게 된다.

```dts
/* 실행하지 않음 — 실제 보드 DT의 모양 */
gpio-keys {
	compatible = "gpio-keys";
	pinctrl-names = "default";
	pinctrl-0 = <&pinctrl_keys>;		/* 패드 풀업·슈미트 (H4) */
	key-power {
		label = "PWR";
		gpios = <&gpio1 4 GPIO_ACTIVE_LOW>;
		linux,code = <KEY_POWER>;
		debounce-interval = <20>;
		wakeup-source;			/* 이 패드가 wake 가능한지 회로도 확인 */
	};
	key-mode {
		label = "MODE";
		gpios = <&gpio1 5 GPIO_ACTIVE_LOW>;
		linux,code = <KEY_PROG1>;
	};
	lid {
		label = "LID";
		gpios = <&gpio1 6 GPIO_ACTIVE_LOW>;
		linux,input-type = <EV_SW>;
		linux,code = <SW_LID>;
	};
};
```

유저 공간은 "전원 키 3초 누름 → 안전 종료", "덮개 열림 → 서비스 모드 경고"를 하는 작은 데몬이다. 그 데몬은 `poll()`로 이벤트를 기다리고, 시작할 때 `EVIOCGSW`로 덮개 상태를 한 번 읽고, `SYN_DROPPED`를 처리하고, 장치가 사라지면(`ENODEV`) 다시 찾는다. 데몬의 테스트는 uinput으로 같은 이름의 장치를 만들어서 한다.

### 12.2 비상 정지는 input이 아니다

"E-stop 버튼도 gpio-keys로 받으면 되나?" — **보고용으로는 된다. 안전 기능으로는 안 된다.** E-stop은 모터 드라이버 전원이나 STO(Safe Torque Off) 입력을 **하드웨어로** 끊어야 한다. 리눅스 쪽 이벤트는 "정지됐다"를 UI와 로그에 알리는 용도다. 이유: 디바운스·스케줄링·유저 공간 데몬·`SYN_DROPPED`·grab 등 지연과 유실 경로가 너무 많다(이 노트에서 다 재현했다). 면접에서 이 구분을 말하면 시스템 감각이 있다는 신호가 된다.

### 12.3 조종용 조이스틱 — USB 게임패드 vs 직접 붙인 ADC

텔레옵에는 보통 USB 게임패드를 쓴다. `hid-input`(또는 `xpad` 같은 전용 드라이버)이 `EV_ABS`/`EV_KEY`로 바꿔 주므로 ROS의 joy 노드 같은 앱이 `/dev/input/eventN`을 읽으면 된다. 컨트롤 박스에 아날로그 스틱을 **SoC ADC에 직접** 붙였다면 커널에 이미 `adc-joystick` 드라이버가 있다 — IIO ADC 채널을 consumer로 받아 input 축으로 내보낸다(I2의 IIO consumer API). 이 노트의 `i3_btn` 가짜 ADC 폴링이 그 구조의 축소판이다. 이때 fuzz·flat 튜닝과 "버튼과 축을 다른 `input_dev`로" 원칙(§6.1)이 그대로 적용된다.

### 12.4 현장 디버그 순서

1. `cat /proc/bus/input/devices` — 장치가 등록됐나? `H:`에 `eventN`이 있나? `B: KEY=`에 기대한 코드가 있나?
2. `evtest /dev/input/eventN`(또는 이 노트의 `i3_evtest`) — 이벤트가 오나? 값과 극성이 맞나?
3. 안 오면 `grep <label> /proc/interrupts` — IRQ 카운트가 느나? 안 늘면 핀·pinctrl·IRQ 트리거 문제(H4, H6).
4. 카운트는 느는데 이벤트가 없으면 디바운스(너무 긺)·capability 누락·`input_sync` 누락·`inhibited`·다른 프로세스의 `EVIOCGRAB`.
5. suspend 관련이면 `power/wakeup`, `/sys/kernel/debug/wakeup_sources`, dmesg의 `failed to suspend`.

## 14. 면접에서 이렇게 말한다

**Q.** "Walk me through how a button press gets from a GPIO pin to an application on Linux."

**A.** 핀 엣지가 GPIO 컨트롤러 IRQ가 되고, gpio-keys 같은 드라이버가 디바운스한 뒤 `input_report_key` + `input_sync`를 부른다. input core가 capability·상태를 확인하고 `SYN_REPORT`에서 패킷을 핸들러에 넘기면, evdev가 열린 fd마다 링버퍼에 넣고 깨운다. 앱은 `/dev/input/eventN`을 `poll`하고 `struct input_event`를 `read`한다. QEMU에서 전원 키로 이 경로를 직접 추적했다.

> The pin edge becomes an interrupt from the GPIO controller; on most boards that pin is described in the device tree under gpio-keys, so no custom driver is needed. The driver debounces — a delayed work or hrtimer re-armed on every edge — then calls input_report_key and input_sync. The input core checks the device's capability bitmaps, drops duplicate key states, and on SYN_REPORT passes the whole packet to every attached handler. evdev copies it into a per-file-descriptor ring buffer and wakes the reader, so the application just polls /dev/input/eventN and reads struct input_event records with a timestamp, type, code and value.

**꼬리 질문**: "What does the kbd handler do with the same event?" → VT 콘솔용 키맵 변환. 그래서 `EV_KEY` 장치는 kbd가 늘 열어 둔다.

**Q.** "Write the skeleton of an input driver for a single button."

**A.** probe에서 `devm_input_allocate_device`, 이름·bustype 설정, `input_set_capability(EV_KEY, code)`, `input_register_device`. GPIO는 `devm_gpiod_get`, IRQ는 `gpiod_to_irq` + 양쪽 엣지. ISR은 디바운스 타이머만 재시작하고, 타이머/워크에서 값을 읽어 `input_report_key` + `input_sync`. devm이라 remove가 필요 없지만, work 취소를 IRQ 해제와 input 해제 사이에 오도록 순서를 맞춘다.

> In probe: devm_input_allocate_device, set name, phys and bustype, input_set_capability for EV_KEY and the key code, then input_register_device. Get the GPIO with devm_gpiod_get, map it with gpiod_to_irq and request both edges. The handler only re-arms a debounce delayed work; the work reads the line with gpiod_get_value_cansleep and reports the key followed by input_sync. Everything is devm-managed, so there's no remove callback, but I register a devm action to cancel the work before requesting the IRQ so teardown runs IRQ free, cancel work, then unregister. In practice I'd use gpio-keys in the device tree — I'd only write this for something gpio-keys can't express.

**Q.** "What are fuzz and flat in input_absinfo?"

**A.** fuzz는 커널이 적용하는 노이즈 필터 폭이다. 변화가 fuzz/2 미만이면 버리고, fuzz·2fuzz 미만이면 평균을 낸다. flat은 중앙 데드존으로 커널이 아니라 소비자가 적용한다. 실험에서 ±3 노이즈에 fuzz 4를 줬더니 정지 구간 50 샘플 중 17~23개만 통과했다 — fuzz를 노이즈 진폭의 두 배 이상으로 잡아야 확실히 조용해진다.

> fuzz is a filter the input core applies: changes smaller than half the fuzz are dropped, and changes within one or two times fuzz are averaged with the previous value. flat is a center dead zone that the kernel only reports; consumers like joystick libraries apply it. When I fed plus-or-minus three counts of noise with fuzz four, roughly a third to a half of the stationary samples still got through, so fuzz needs to be about twice the noise amplitude — at the cost of resolution.

**Q.** "Why are IMUs and ADCs IIO devices rather than input devices?"

**A.** input은 사람의 사건을 "변화가 있을 때만" 전달하는 모델이라 중복·fuzz 필터가 샘플을 버리고, 샘플링 주파수·하드웨어 FIFO·트리거·스케일 같은 개념이 없다. 센서 융합에는 모든 샘플과 정확한 타임스탬프가 필요하므로 IIO의 buffered capture가 맞다. 또 input 장치는 데스크톱 스택이 자동으로 집어 가서 가속도계가 조이스틱으로 오인되는 문제도 있었다.

> The input subsystem is designed for human events: it only forwards changes, drops duplicates and can filter with fuzz, and it has no notion of sampling frequency, hardware FIFOs, triggers or scale and offset. Sensor fusion needs every sample with an accurate timestamp, which is exactly what IIO buffered capture gives you. Input devices also get picked up automatically by desktop stacks, and accelerometers exposed as three-axis ABS devices used to be mistaken for joysticks. So new sensor drivers go to IIO; input is for buttons, touch, keys and sticks.

**Q.** "What is SYN_DROPPED and how should a client handle it?"

**A.** evdev 클라이언트 버퍼가 넘치면 읽지 않은 이벤트를 다 버리고 `SYN_DROPPED`와 최신 이벤트 하나만 남긴다. 클라이언트는 다음 `SYN_REPORT`까지 버리고 `EVIOCGKEY`/`EVIOCGABS`/`EVIOCGMTSLOTS`로 현재 상태를 읽어 재동기화해야 한다. libevdev가 이를 자동으로 한다. 실험에서 2 ms 지연 리더에 1200 이벤트를 쏘자 48개만 받고 5번 drop이 났다.

> Each evdev file descriptor has its own ring buffer sized from the device's events-per-packet estimate. If the reader falls behind and the buffer wraps, evdev throws away everything unread and queues SYN_DROPPED plus the newest event. The client must discard events up to the next SYN_REPORT, then query the current state with EVIOCGKEY, EVIOCGABS, EVIOCGMTSLOTS and so on, and diff it against its own state. libevdev does this for you. The real fix is to drain input quickly in its own thread or event loop and read many events per syscall.

**Q.** "How would you test an input-handling application without hardware?"

**A.** uinput으로 같은 capability의 가상 장치를 만들고 이벤트를 `write`한다. 가상 장치도 input core를 지나므로 중복 제거·패킷 규칙이 똑같이 적용된다. evemu로 실제 장비의 이벤트를 녹화해 재생하면 회귀 테스트가 된다. 앱이 이름으로 장치를 찾게 만들어 두면 테스트 장치로 갈아끼우기 쉽다.

> I create a virtual device with uinput that has the same capabilities, then write input_event records followed by SYN_REPORT. It goes through the real input core, so duplicate filtering, packet framing and even hot-unplug with ENODEV behave like hardware. For regression tests I'd record real sessions with evemu and replay them in CI. The application should look devices up by name or capability rather than by event number, which also makes swapping in the virtual device trivial.

**꼬리 질문**: "Can a uinput device be distinguished from a real one?" → `BUS_VIRTUAL`, `/sys/devices/virtual/input/` 경로, VID/PID.

**Q.** "A board fails to suspend right after adding a wakeup button. How do you debug it?"

**A.** dmesg에서 `failed to suspend` 줄의 장치를 찾는다. 그 키의 IRQ 칩이 wake를 지원하지 않으면 gpio-keys suspend 콜백이 `enable_irq_wake` 실패를 올려 전체 suspend가 취소된다. 랩에서 gpio-sim 키에 `wakeup-source`를 달아 `-ENXIO`로 재현했고, 빼자 전원 키(PL061)로 s2idle에서 정상적으로 깨어났다. 실제 SoC에서는 그 패드가 웨이크업 컨트롤러로 라우팅되는지도 확인한다.

> I'd look at the PM lines in dmesg — the device whose suspend callback failed is named there. A common cause is wakeup-source on a key whose interrupt controller can't be a wake source: gpio-keys calls enable_irq_wake during suspend, gets ENXIO, returns the error, and the whole system suspend is aborted. I reproduced that in QEMU with a key on a simulated GPIO chip; removing the property fixed it and the power key then woke the system from s2idle. On real silicon I'd also confirm in the reference manual that the pad routes to the wakeup controller and stays powered in the target sleep state.

## 15. 직접 해보기

1. **개념**: `B: KEY=10000000000000 0`에서 `KEY_POWER`(116)를 손으로 해독해 보라. `B: EV=23`은 어떤 타입들인가?
   정답/힌트: word는 높은 쪽부터, 두 번째 word = bit 64~127, `0x10000000000000` = bit 52 → 116. `0x23` = bit 0, 1, 5 = SYN, KEY, SW.
2. **코드**: `i3_btn`의 디바운스를 hrtimer로 바꾸고(SoC GPIO 가정), `debounce_ms=5`에서 5×6 ms 패턴과 5×12 ms 패턴 결과가 delayed work 버전과 어떻게 달라지는지 예측한 뒤 측정하라.
   정답/힌트: hrtimer는 jiffies 반올림이 없어 5 ms가 거의 5 ms다. 6 ms 간격은 이제 **못 걸러야** 정상이다. gpio-sim은 can_sleep이므로 hrtimer 콜백에서 값을 직접 읽지 말고 거기서 work를 깨우는 구조로 해야 한다.
3. **코드**: `i3_btn`을 버튼용 `input_dev`와 축용 `input_dev` 두 개로 나누고, §6.1처럼 `polls` 카운터로 "아무도 안 열면 폴링이 멈추는지" 확인하라.
   정답/힌트: 축 장치는 `EV_KEY`가 없으니 `kbd`가 붙지 않는다. `/proc/bus/input/devices`의 `H:`에 `event`만 있어야 한다.
4. **관찰**: uinput 장치를 만든 뒤 `/sys/class/input/inputN/capabilities/`의 `ev`, `key`, `abs` 파일을 읽고 `/proc/bus/input/devices`의 `B:` 줄과 비교하라.
   정답/힌트: 같은 비트맵이 파일별로 나뉘어 있다. udev가 `ID_INPUT_KEYBOARD` 같은 속성을 이 파일로 판단한다.
5. **코드**: `i3_evtest`를 고쳐서 `SYN_DROPPED` 후 다음 `SYN_REPORT`까지 이벤트를 버리게 하고, 재동기화 뒤 "앱이 기억하는 눌린 키 집합"이 `EVIOCGKEY`와 일치하는지 검사하라.
   정답/힌트: 앱 상태(비트맵)와 `EVIOCGKEY` 결과를 비교해 차이를 합성 이벤트로 만든다 — libevdev가 하는 일이다.
6. **관찰**: 같은 장치를 리더 둘이 열고 하나가 `EVIOCGRAB`한 상태에서 `/proc/bus/input/devices`, `kbd`로 가는 키(콘솔 입력)가 어떻게 되는지 보라.
   정답/힌트: grab은 장치 수준이라 콘솔에도 키가 안 간다. fd를 닫으면 즉시 풀린다.
7. **설계**: 로봇 컨트롤 박스에 버튼 6개가 있는데 GPIO가 2개뿐이다. 선택지(매트릭스, I2C 키패드 컨트롤러, I2C GPIO 확장기 + gpio-keys)를 지연·wake·코드량으로 비교하라.
   정답/힌트: 확장기의 INT를 쓰면 gpio-keys가 그대로 되지만 can_sleep이라 work 경로이고 wake는 확장기 INT 핀이 SoC wake 패드에 붙어야 한다. TCA8418 같은 키패드 IC는 스캔·디바운스를 칩이 한다.

## 16. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| input core | 입력 서브시스템 중심부 | `drivers/input/input.c`. 장치·핸들러 등록, 필터, 배달 |
| `input_dev` | 입력 장치 | capability 비트맵 + 현재 상태 + 콜백. 드라이버가 만든다 |
| `input_handler` | 핸들러 | evdev, kbd, sysrq, leds, mousedev, joydev |
| `input_handle` | 연결 | 장치 하나 ↔ 핸들러 하나 |
| evdev | 범용 이벤트 핸들러 | `/dev/input/eventN`. 오늘날 유저 공간 입력의 표준 |
| `struct input_event` | 이벤트 레코드 | time, type, code, value. arm64에서 24바이트 |
| `SYN_REPORT` | 패킷 경계 | 여기까지가 한 순간의 상태. `input_sync()` |
| `SYN_DROPPED` | 버퍼 넘침 알림 | 이후 재동기화 필요 |
| capability | 지원 목록 | evbit/keybit/absbit … 비트맵 |
| absinfo | 축 정보 | value, min, max, fuzz, flat, resolution |
| fuzz | 노이즈 필터 폭 | 커널이 적용 |
| flat | 데드존 | 소비자가 적용 |
| 디바운스 | 채터링 제거 | 마지막 엣지 뒤 일정 시간 조용하면 읽기 |
| poller | 폴링 도우미 | `input_setup_polling()`. 열려 있을 때만 주기 호출 |
| `inhibited` | 강제 비활성 | sysfs 속성. close + 이벤트 무시 |
| gpio-keys | GPIO 버튼 드라이버 | DT만으로 키·스위치 등록 |
| `linux,code` | 보낼 코드 | DT 속성, `input-event-codes.h`와 같은 번호 |
| `wakeup-source` | 깨움 가능 | DT 속성 → `device_init_wakeup` → `enable_irq_wake` |
| 멀티터치 slot | 손가락 자리 | 프로토콜 B. `ABS_MT_SLOT` + `ABS_MT_TRACKING_ID` |
| uinput | 유저 공간 입력 장치 | `/dev/uinput`으로 진짜 `input_dev`를 만든다 |
| `EVIOCGRAB` | 독점 | 장치 수준 grab. 다른 클라이언트·핸들러 차단 |
| libevdev | evdev 래퍼 라이브러리 | 재동기화, 이름 변환, uinput 복제 |
| IIO | Industrial I/O | 센서·ADC용 서브시스템 (I2) |

## 17. 요약 & 체크리스트

input 서브시스템은 펌웨어에서 매번 직접 짜던 "버튼 ISR + 디바운스 + 이벤트 큐 + 여러 소비자"를 표준화한 것이다. 드라이버는 `input_dev`를 capability와 함께 등록하고 `input_report_*` + `input_sync`만 부른다. input core는 상태 비트맵으로 중복을 지우고 fuzz로 노이즈를 거르고 `SYN_REPORT` 단위로 핸들러에 넘긴다. evdev는 fd마다 링버퍼를 두고, 넘치면 `SYN_DROPPED`로 재동기화를 요구한다. 버튼은 gpio-keys DT 노드로 코드 없이 붙이고, 테스트는 uinput으로 한다. 센서(IMU·ADC)는 input이 아니라 IIO다. 이 노트에서 QEMU 전원 키 IRQ, gpio-sim 위의 직접 만든 드라이버와 gpio-keys, 디바운스 측정, fuzz 효과, `EVIOCGRAB`, `SYN_DROPPED`, s2idle 웨이크업과 그 실패까지 전부 실제로 돌려 확인했다.

- [ ] 드라이버 → input core → 핸들러(evdev, kbd, mousedev, joydev) 구조를 그림으로 설명할 수 있다
- [ ] `struct input_event`의 필드와 `EV_KEY`/`EV_REL`/`EV_ABS`/`EV_SW`/`EV_SYN`의 value 의미를 말할 수 있다
- [ ] `SYN_REPORT`가 왜 필요한지, 빈 패킷과 중복 값이 어디서 사라지는지 설명할 수 있다
- [ ] absinfo의 fuzz와 flat의 차이, `input_defuzz_abs_event` 규칙을 설명할 수 있다
- [ ] `devm_input_allocate_device` → capability → `input_register_device` → report + sync로 버튼 드라이버를 코드로 짤 수 있다
- [ ] delayed work/hrtimer 디바운스를 짜고, HZ 반올림이 디바운스 시간에 주는 영향을 설명할 수 있다
- [ ] `input_setup_polling`과 `kbd` 핸들러가 장치를 열어 두는 문제, `inhibited`를 설명할 수 있다
- [ ] gpio-keys / gpio-keys-polled DT 바인딩(`linux,code`, `linux,input-type`, `debounce-interval`, `wakeup-source`)을 쓸 수 있다
- [ ] evdev ioctl(`EVIOCGNAME`, `EVIOCGBIT`, `EVIOCGABS`, `EVIOCGKEY`, `EVIOCGRAB`, `EVIOCSCLOCKID`)로 장치를 조회하는 C 코드를 짤 수 있다
- [ ] uinput으로 가상 장치를 만들어 앱을 테스트할 수 있다
- [ ] `SYN_DROPPED`의 원인(클라이언트 버퍼 크기 계산 포함)과 재동기화 절차를 설명할 수 있다
- [ ] wakeup 키가 suspend를 깨우는 세 층(DT, 드라이버, IRQ 칩)과 실패 증상을 설명할 수 있다
