# I5. V4L2와 media controller — v4l2_device/subdev, video node, media graph, videobuf2, 포맷 협상

> **이 노트를 다 읽으면**: SoC 카메라 파이프라인(센서 → CSI-2 수신기 → ISP → 스케일러/DMA → DRAM)을 Linux 객체(`v4l2_subdev`, `video_device`, `media_entity`/pad/link)로 그리고 `/dev/videoN`·`/dev/v4l-subdevN`·`/dev/mediaN`이 각각 무엇인지 말할 수 있다 · `v4l2-ctl`/`media-ctl` 없이 V4L2·MC uAPI를 직접 C로 불러 포맷 협상, 링크 설정, MMAP 스트리밍, DMABUF zero-copy를 할 수 있고 `-EPIPE`(link validation 실패)를 dmesg로 원인 추적할 수 있다 · videobuf2의 버퍼 상태 기계와 소유권, 타임스탬프·sequence로 드롭 프레임을 잡는 법을 측정으로 설명할 수 있다 · DT의 `port`/`endpoint`/`remote-endpoint`·`data-lanes`·`link-frequencies`가 v4l2-async를 거쳐 그래프가 되는 과정을 실제 드라이버(imx219, i.MX8MP CSI-2) 코드로 따라가고, 최소 V4L2 캡처 드라이버를 직접 쓸 수 있다
> **왜 필요한가**: 로봇 카메라 bring-up은 "센서는 I2C에 보이는데 `/dev/video0`에서 프레임이 안 나온다", "STREAMON이 `Broken pipe`", "가끔 프레임이 빠진다", "인코더로 넘길 때 CPU가 30% 먹는다"의 연속이고, 면접은 "새 MIPI 센서를 Linux에 올리는 순서를 말해 보라"를 묻는다 — 전부 이 노트의 내용이다
> **Don 기준 난이도**: DMA 링, 디스크립터 소유권, 프레임 카운터, IRQ 타이밍, 레인/클럭 같은 PHY 개념은 SSD·RF bring-up에서 매일 하던 일이다 / 새로 배울 것은 V4L2가 그것을 모델링하는 **객체 그래프**(subdev·pad·link), **두 종류의 포맷**(media bus code vs fourcc), **videobuf2**라는 버퍼 큐 프레임워크, 그리고 DT 그래프 + async 등록이라는 Linux식 "보드 배선 설명"
> **선행 노트**: G4·G5(char device, ioctl·mmap), G6(poll), H5(I2C), H9(DMA API, dma-buf), F10(CMA, 카메라 버퍼), D2~D4(DT 문법·phandle), F8(hrtimer), I1(프레임워크 원칙) — Q1(MIPI CSI-2 HW), Q2(Linux 카메라 파이프라인 실무), Q3(멀티 카메라 동기화)로 이어진다

## 0. 큰 그림 — 이게 왜 필요한가

예를 들어 센서 키트에 카메라가 4대 붙어 있다고 하자. 각 카메라 모듈은 이미지 센서(예: Sony IMX219) 하나다. 센서는 두 가닥의 선으로 SoC와 연결된다. **제어**는 I2C(카메라 업계는 CCI — Camera Control Interface라고 부른다)로 레지스터를 쓰고, **픽셀 데이터**는 MIPI CSI-2라는 고속 직렬 링크(데이터 lane 1~4개 + 클럭 lane, 물리층은 D-PHY)로 흘러간다. SoC 안에서는 CSI-2 수신기가 패킷을 풀고, ISP가 Bayer 원본을 debayer·화이트밸런스·노이즈 제거해서 YUV로 바꾸고, 스케일러가 크기를 줄이고, DMA writer가 DRAM 버퍼에 쓴다.

Don이 SSD 컨트롤러에서 본 구조와 똑같다. "호스트 인터페이스 → 데이터 경로 블록 여러 개 → DMA → 버퍼"다. 차이는 **블록이 SoC 벤더마다 다르고, 블록 사이 연결을 소프트웨어가 바꿀 수 있다**는 점이다. 그래서 Linux는 카메라 파이프라인을 "장치 하나"가 아니라 **그래프**로 모델링한다.

그림 1 — 위는 SoC 카메라 하드웨어, 아래는 그것을 Linux가 모델링한 media controller 그래프. 블록 하나가 커널 객체 하나(대개 `v4l2_subdev`)가 되고, 블록 사이의 배선은 pad와 link가 된다. 마지막 DMA 블록만 메모리 버퍼를 다루는 `video_device`(`/dev/video0`)다. entity 이름 옆의 `CAM_SENSOR` 등은 `MEDIA_ENT_F_*` function 값이다(가운데 두 개는 대표적인 예 — 실제 값은 드라이버마다 다르다).

이 노트에서 다룰 V4L2(Video4Linux2) 세계의 구성원을 먼저 표 하나로 정리한다.

| HW 블록 | Linux 객체 | 유저가 보는 것 | 이 노트 절 |
|---|---|---|---|
| 카메라 파이프라인 전체 | `struct media_device` | `/dev/mediaN` (`MEDIA_IOC_*`) | §2, §9 |
| 브리지 드라이버(수신기/ISP의 주인) | `struct v4l2_device` | 없음 (내부 컨테이너) | §2 |
| 센서, CSI-2 수신기, ISP, 스케일러 | `struct v4l2_subdev` + `media_entity` | `/dev/v4l-subdevN` (`VIDIOC_SUBDEV_*`) | §2, §9, §10 |
| 블록 사이 배선 | `media_pad` + `media_link` | 링크 켜기/끄기 (`MEDIA_IOC_SETUP_LINK`) | §9 |
| DMA writer(메모리로 쓰는 끝단) | `struct video_device` + `vb2_queue` | `/dev/videoN` (`VIDIOC_*`) | §3~§8 |
| 노출·게인·테스트 패턴 레지스터 | `v4l2_ctrl_handler` / `v4l2_ctrl` | `VIDIOC_QUERY_EXT_CTRL`, `S_CTRL` | §4 |
| DRAM 프레임 버퍼 링 | videobuf2 (`vb2_buffer`) | `REQBUFS`/`QBUF`/`DQBUF`, mmap, dma-buf fd | §5, §8 |
| 보드 배선(어느 센서가 어느 수신기 몇 lane에) | DT `port`/`endpoint` → v4l2-async | 없음 (부팅 때 결정) | §11 |

이 노트의 실습은 전부 진짜 카메라 없이 커널에 들어 있는 **가상(테스트) 드라이버**로 한다.

- **vivid** — "Virtual Video Test Driver". 웹캠·HDMI 입력 등을 흉내 내는 단순한(video-centric) 캡처/출력 장치. 컨트롤이 아주 많고 테스트 패턴을 만든다.
- **vimc** — "Virtual Media Controller". 센서 → debayer → 스케일러 → 캡처의 **media controller 파이프라인**을 흉내 낸다. 실제 SoC 카메라(i.MX8, RK3399, Jetson 등)와 같은 사용 방식이다.
- **vim2m** — 메모리 → 메모리(m2m) 변환 장치. 인코더·스케일러 역할로 DMABUF import 대상으로 쓴다.
- **i5_cam** — §12에서 직접 쓰는 최소 캡처 드라이버.

## 1. 실습 환경 — Image-sub 커널과 BusyBox 게스트

### 1.1 왜 QEMU 게스트인가

Lima VM(`elinux`)의 호스트 커널은 7.0이고 vivid가 로드되어 있지 않다. 공용 VM에 커널 모듈을 넣는 것은 금지라서, 모든 실습은 공용 랩의 **Image-sub** 커널(6.18.55 LTS + 테스트 드라이버들을 모듈로 빌드한 것)을 QEMU로 부팅해서 한다. 게스트 rootfs는 BusyBox라 `v4l2-ctl`·`media-ctl`(v4l-utils 패키지)이 없다. 그래서 이 노트의 유저 공간 코드는 전부 **V4L2·MC uAPI ioctl을 직접 부르는 정적 C 프로그램**이다. 덕분에 도구가 숨기는 순서를 전부 손으로 보게 된다.

VM 호스트에 v4l-utils가 있는지 먼저 확인했다(설치는 하지 않는다).

```sh
limactl shell elinux -- bash -lc 'uname -r; which v4l2-ctl media-ctl; dpkg -l | grep -i v4l'
```

출력에서 볼 것: `which`가 아무것도 찍지 않았다. 라이브러리(`libv4l`)만 있고 명령행 도구는 없다. 실무 보드에서는 보통 `v4l-utils`를 rootfs에 넣는다(Buildroot `BR2_PACKAGE_LIBV4L_UTILS`, Yocto `v4l-utils` 레시피). 이 노트의 C 프로그램이 하는 일을 v4l2-ctl/media-ctl로 하면 어떤 명령인지는 각 절에 "(기억 기반, 실행 안 함)"이라고 표시해서 적는다.

### 1.2 부팅 스크립트

Lima VM 안에서 실행하는 스크립트다. 랩 rootfs를 한 번 복사해 media 관련 모듈(`drivers/media/{test-drivers,v4l2-core,common,mc,cec/core}`)과 `modules.dep`을 `/lib/modules/6.18.55-sub`에 넣어 두면, 게스트에서 BusyBox `modprobe vivid`가 의존 모듈(`videodev`, `mc`, `videobuf2-*`, `v4l2-tpg`…)을 알아서 올린다.

```sh
#!/bin/sh
# boot.sh <guest-script> — boots Image-sub with media modules + /var/tmp/I5/bin/* + scratch *.sh
set -e
W=/var/tmp/I5; S=/Users/donh/.elinux_scratch/I5
M=/var/lab/out/modules-sub/lib/modules/6.18.55-sub
MEM=${MEM:-1024}; SMP=${SMP:-2}; APP=${APP:-}
if [ ! -d $W/base ]; then
  mkdir -p $W/base && cp -a /var/lab/build/rootfs/. $W/base/
  D=$W/base/lib/modules/6.18.55-sub; mkdir -p $D
  cp $M/modules.* $D/
  for p in test-drivers v4l2-core common mc cec/core; do mkdir -p $D/kernel/drivers/media/$p; cp -a $M/kernel/drivers/media/$p/. $D/kernel/drivers/media/$p/; done
fi
rm -rf $W/r && cp -a $W/base $W/r
cp $S/*.sh $W/r/ 2>/dev/null || true
cp $W/bin/* $W/r/ 2>/dev/null || true
cp $W/mod/*.ko $W/r/ 2>/dev/null || true
(cd $W/r && find . | cpio -o -H newc --quiet | gzip -1) > $W/i.gz
timeout ${TMO:-300} qemu-system-aarch64 -machine virt -cpu cortex-a57 -m $MEM -smp $SMP -nographic \
  -kernel /var/lab/out/Image-sub -initrd $W/i.gz \
  -append "console=ttyAMA0 quiet $APP LAB_CMD=sh~/$1"
```

유저 프로그램은 VM에서 `gcc -static`으로 빌드해 `/var/tmp/I5/bin`에 두고, 부팅 때 initramfs 루트(`/`)에 복사된다.

```sh
#!/bin/sh
# build.sh — 정적 바이너리를 /var/tmp/I5/bin 에
set -e
S=/Users/donh/.elinux_scratch/I5; mkdir -p /var/tmp/I5/bin
for p in "$@"; do gcc -std=gnu11 -Wall -Wextra -O2 -static -I$S $S/$p.c -o /var/tmp/I5/bin/$p; echo "built $p"; done
```

모든 예제의 공용 헤더다. `xioctl()`은 시그널로 끊긴 ioctl을 다시 부르는 V4L2 예제의 관례이고, `fcc()`는 32비트 fourcc를 `YUYV` 같은 네 글자로 바꾼다.

```c
/* i5.h — 예제 공용: 에러 처리, EINTR 재시도 ioctl, fourcc 문자열 */
#pragma once
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <time.h>
#include <unistd.h>
#include <linux/videodev2.h>
#include <linux/media.h>
#include <linux/v4l2-subdev.h>

#define die(m) do { perror(m); exit(1); } while (0)

static inline int xioctl(int fd, unsigned long req, void *arg)
{
	int r;
	do r = ioctl(fd, req, arg); while (r < 0 && errno == EINTR);
	return r;
}

static inline const char *fcc(unsigned v)   /* 'YUYV' 같은 4글자 */
{
	static char s[4][5]; static int i;
	char *p = s[i++ & 3];
	for (int k = 0; k < 4; k++) p[k] = (v >> (8 * k)) & 0x7f; /* bit31 = BE 플래그 */
	p[4] = 0;
	return p;
}

static inline double now_s(void)
{
	struct timespec t;
	clock_gettime(CLOCK_MONOTONIC, &t);
	return t.tv_sec + t.tv_nsec / 1e9;
}
```

헤더는 VM 호스트(커널 7.0)의 `/usr/include/linux/videodev2.h`를 쓴다. uAPI는 하위 호환이 보장되므로 6.18 게스트에서 그대로 동작한다.

## 2. 객체 모델 — 누가 누구를 소유하나

### 2.1 직관 — "SoC 블록마다 작은 드라이버, 그걸 묶는 브리지"

bare-metal 펌웨어라면 카메라 경로 전체를 하나의 모듈이 초기화한다. Linux는 그렇게 못 한다. 센서는 I2C 버스에 붙은 별개의 장치(`i2c_client`)이고 센서 드라이버는 SoC와 무관하게 재사용되어야 한다(IMX219 드라이버는 Raspberry Pi, i.MX8MP, TI AM62, Renesas에서 똑같이 쓴다). ### 2.2 정의

| 구조체 | 헤더 | 한 줄 정의 | 만드는 함수 |
|---|---|---|---|
| `struct v4l2_device` | `media/v4l2-device.h` | 한 카메라 시스템의 최상위 컨테이너. subdev 목록, 공용 ctrl handler, `mdev` 포인터 | `v4l2_device_register()` |
| `struct video_device` | `media/v4l2-dev.h` | `/dev/videoN` 하나. fops, ioctl_ops, `vb2_queue`, `device_caps` | `video_register_device()` |
| `struct v4l2_subdev` | `media/v4l2-subdev.h` | HW 블록 하나. `ops`(core/video/pad/sensor), ctrl handler, 활성 상태(state) | `v4l2_i2c_subdev_init()` 등 → `v4l2_device_register_subdev()` 또는 async |
| `struct media_device` | `media/media-device.h` | `/dev/mediaN`. 그래프 전체(entity·pad·link·interface)와 topology 버전 | `media_device_init()` + `media_device_register()` |
| `struct media_entity` | `media/media-entity.h` | 그래프의 노드. `function`(`MEDIA_ENT_F_CAM_SENSOR` 등), pad 배열 | subdev·video_device 안에 내장 |
| `struct media_pad` | 같음 | entity의 입출력 단자. `MEDIA_PAD_FL_SINK` 또는 `_SOURCE` | `media_entity_pads_init()` |
| `struct media_link` | 같음 | source pad → sink pad 연결. `ENABLED`, `IMMUTABLE` 플래그 | `media_create_pad_link()`, `v4l2_create_fwnode_links_to_pad()` |

subdev의 ops는 세 묶음이 핵심이다.

| ops 묶음 | 대표 콜백 | 무엇을 하나 |
|---|---|---|
| `v4l2_subdev_core_ops` | `log_status`, `subscribe_event` | 공통 관리 |
| `v4l2_subdev_video_ops` | `s_stream` | 스트림 켜기/끄기 (6.x 새 드라이버는 아래 `enable_streams` + `v4l2_subdev_s_stream_helper`) |
| `v4l2_subdev_pad_ops` | `enum_mbus_code`, `get_fmt`/`set_fmt`, `get_selection`/`set_selection`, `enum_frame_size`, `link_validate`, `enable_streams`/`disable_streams` | pad별 포맷·크롭과 스트림 |
| `v4l2_subdev_internal_ops` | `init_state` | 새 state(TRY/ACTIVE)의 기본 포맷 채우기 (6.8 전에는 pad op `init_cfg`) |

6.x의 큰 변화는 **subdev state API**다. 예전에는 드라이버가 자기 구조체에 "현재 포맷"을 직접 들고 있었는데, 지금은 코어가 `struct v4l2_subdev_state`(pad별 포맷·crop·compose, 스트림 라우팅)를 관리하고 드라이버는 `v4l2_subdev_init_finalize()`로 그것을 만든 뒤 `v4l2_subdev_state_get_format(state, pad)`로 읽는다. 포맷 조회는 `.get_fmt = v4l2_subdev_get_fmt`라는 공용 헬퍼로 끝난다. §11의 imx219 코드에서 이 패턴이 그대로 보인다.

### 2.3 video-centric vs MC-centric 드라이버

| | video-centric | MC-centric |
|---|---|---|
| 예 | UVC 웹캠, vivid, 단순한 SoC 캡처 브리지 | vimc, i.MX8MP ISI, Rockchip RKISP1, TI J721E CSI2RX, Qualcomm CAMSS, Renesas R-Car VIN |
| 누가 파이프라인을 설정하나 | **video 노드 드라이버**가 `S_FMT`를 받아서 subdev들에 포맷을 전파 | **유저 공간**이 subdev마다 포맷을 설정하고 링크를 켠다 |
| `/dev/v4l-subdevN` | 없거나 쓸 일 없음 | 필수 |
| `device_caps`의 `V4L2_CAP_IO_MC` | 없음 | 있음 ("이 노드의 입력은 media controller로 정한다") |
| `S_FMT` 의미 | "이 해상도로 찍어 줘" | "메모리에 이 포맷으로 써 줘" (센서 해상도는 바꾸지 않음) |
| 유저 도구 | v4l2-ctl 하나로 끝 | media-ctl + v4l2-ctl, 또는 libcamera |

복잡한 SoC 카메라는 거의 다 MC-centric이다. ISP가 여러 출력(메인·프리뷰·통계)을 내고, CSI-2 수신기 하나에 가상 채널(VC)로 여러 센서가 들어오고, 같은 센서 해상도에서 스케일러만 바꾸는 등 조합이 너무 많아서 드라이버가 "알아서" 정할 수 없기 때문이다. 이 결정권이 유저 공간으로 넘어가면서 생긴 것이 libcamera(§13)다.

### 2.4 흔한 함정

- `/dev/video0`을 열면 카메라가 나온다고 가정한다 — MC 드라이버에서는 subdev 포맷과 링크를 먼저 맞추지 않으면 STREAMON이 `-EPIPE`다(§9).
- subdev 노드가 안 생겨서 "드라이버가 안 붙었다"고 판단한다 — subdev 노드는 브리지가 `v4l2_device_register_subdev_nodes()`를 불러야 생긴다. 센서의 `V4L2_SUBDEV_FL_HAS_DEVNODE` 플래그도 필요하다.
- `capabilities`와 `device_caps`를 혼동한다 — `capabilities`는 장치(드라이버) 전체의 합집합, `device_caps`는 지금 연 노드의 능력이다. 판단은 `device_caps`로 한다.

## 3. 첫 장치 열기 — QUERYCAP, ENUM_FMT, G_FMT, 그리고 두 종류의 포맷

### 3.1 직관

V4L2 장치를 처음 열면 하는 일은 SSD 펌웨어가 NVMe Identify를 처리하는 것과 비슷하다. "너는 누구고(QUERYCAP), 무슨 포맷을 지원하고(ENUM_FMT), 지금 설정은 무엇이냐(G_FMT)". 모든 V4L2 앱(GStreamer `v4l2src`, OpenCV, libcamera)의 첫 3개 ioctl이다.

### 3.2 예제 1 — `i5_info`: 장치가 뭘 할 수 있나

무엇을 확인하는 코드인지: 노드 하나의 드라이버 이름, `device_caps`, 지원 pixel format 목록, 현재 포맷, 프레임 간격(`G_PARM`)을 출력한다.

```c
/* i5_info.c <dev> — QUERYCAP, ENUM_FMT, G_FMT, G_PARM: 장치가 뭘 할 수 있나 */
#include "i5.h"

int main(int argc, char **argv)
{
	int fd = open(argc > 1 ? argv[1] : "/dev/video0", O_RDWR);
	if (fd < 0) die("open");

	struct v4l2_capability cap = {0};
	if (xioctl(fd, VIDIOC_QUERYCAP, &cap)) die("QUERYCAP");
	printf("driver=%s card=%s bus=%s version=%u.%u.%u\n", cap.driver, cap.card,
	       cap.bus_info, cap.version >> 16, (cap.version >> 8) & 0xff, cap.version & 0xff);
	unsigned c = cap.device_caps;          /* 이 노드의 능력 (capabilities는 장치 전체) */
	printf("device_caps=0x%08x%s%s%s%s%s%s\n", c,
	       c & V4L2_CAP_VIDEO_CAPTURE ? " VIDEO_CAPTURE" : "",
	       c & V4L2_CAP_VIDEO_OUTPUT ? " VIDEO_OUTPUT" : "",
	       c & V4L2_CAP_VIDEO_M2M ? " M2M" : "",
	       c & V4L2_CAP_STREAMING ? " STREAMING" : "",
	       c & V4L2_CAP_READWRITE ? " READWRITE" : "",
	       c & V4L2_CAP_IO_MC ? " IO_MC" : "");

	enum v4l2_buf_type t = (c & V4L2_CAP_VIDEO_CAPTURE) || (c & V4L2_CAP_VIDEO_M2M) ?
		V4L2_BUF_TYPE_VIDEO_CAPTURE : V4L2_BUF_TYPE_VIDEO_OUTPUT;
	struct v4l2_fmtdesc fd_ = { .type = t };
	for (fd_.index = 0; xioctl(fd, VIDIOC_ENUM_FMT, &fd_) == 0; fd_.index++)
		printf("  fmt[%2u] %s  %s\n", fd_.index, fcc(fd_.pixelformat), fd_.description);

	struct v4l2_format f = { .type = t };
	if (xioctl(fd, VIDIOC_G_FMT, &f)) die("G_FMT");
	printf("current: %ux%u %s bytesperline=%u sizeimage=%u field=%u colorspace=%u\n",
	       f.fmt.pix.width, f.fmt.pix.height, fcc(f.fmt.pix.pixelformat),
	       f.fmt.pix.bytesperline, f.fmt.pix.sizeimage, f.fmt.pix.field, f.fmt.pix.colorspace);

	struct v4l2_streamparm p = { .type = t };
	if (xioctl(fd, VIDIOC_G_PARM, &p) == 0 && t == V4L2_BUF_TYPE_VIDEO_CAPTURE)
		printf("timeperframe=%u/%u\n", p.parm.capture.timeperframe.numerator,
		       p.parm.capture.timeperframe.denominator);
	else
		printf("G_PARM: %s\n", strerror(errno));
	close(fd);
	return 0;
}
```

(포맷 목록 83개 중 일부만 남기고 `...`로 줄였다.) 출력에서 볼 것:

- `device_caps=0x05230001` — `VIDEO_CAPTURE`(0x1) + `READWRITE`(0x1000000) + `STREAMING`(0x4000000) 외에 `EXT_PIX_FORMAT`(0x200000) 등 내가 출력하지 않은 비트도 있다. vivid는 `read()`로도 프레임을 줄 수 있다(READWRITE). 실제 SoC 캡처 드라이버는 대개 STREAMING만 지원한다.
- vivid 캡처가 지원하는 **pixel format(fourcc)이 83개**다. `YUYV`(4:2:2 packed), `NV12`(4:2:0 semi-planar — 카메라·코덱의 표준), `RGB3`(RGB24), `RGGB`(8비트 Bayer), `RG10`(10비트 Bayer, 16비트 컨테이너) 등. 실제 SoC는 DMA writer가 지원하는 몇 개뿐이다.
- `fmt[27] Y16 ` 설명이 `16-bit Greyscale BE` — fourcc 최상위 비트(`V4L2_PIX_FMT_BE`, bit 31)가 빅엔디언 표시다. 그래서 `fcc()`에서 `& 0x7f`로 걸렀다.
- 현재 포맷 `320x240 YUYV bytesperline=640 sizeimage=153600` — **bytesperline(stride)**은 한 줄의 바이트 수다. 320 픽셀 × 2바이트 = 640. 하드웨어 DMA가 줄 끝을 64·128바이트로 정렬하면 bytesperline이 폭 × bpp보다 커진다. 앱은 반드시 이 값으로 줄을 넘겨야 한다.
- `timeperframe=1/5` — vivid의 웹캠 입력은 해상도별 프레임 간격 목록을 갖고 있고 지금 값은 5 fps다. §6에서 `S_PARM`으로 바꾼다.
- 출력 장치(`video1`)는 `VIDEO_OUTPUT`이고, 이 vivid 출력 노드는 `G_PARM`에 `-EINVAL`을 돌려준다(출력 프레임 간격은 지원 안 함). `720x576 field=4`는 PAL 인터레이스(`V4L2_FIELD_INTERLACED`)다.

### 3.3 fourcc vs media bus code — 이 노트에서 가장 중요한 구분

| | pixel format (fourcc) | media bus format (mbus code) |
|---|---|---|
| 어디에 쓰나 | **메모리 버퍼**의 레이아웃 (video node) | **두 HW 블록 사이 배선** 위의 데이터 (subdev pad) |
| 구조체 | `struct v4l2_pix_format` (`width`, `height`, `pixelformat`, `bytesperline`, `sizeimage`) | `struct v4l2_mbus_framefmt` (`width`, `height`, `code`, `field`, colorspace) |
| 예 | `V4L2_PIX_FMT_SRGGB10` = `'RG10'`: 10비트 Bayer를 16비트에 담아 메모리에 | `MEDIA_BUS_FMT_SRGGB10_1X10` = `0x300f`: 10비트 Bayer가 버스 한 클럭에 10비트씩 |
| stride·padding | 있음 | 없음 (버스엔 메모리가 없다) |
| 설정 ioctl | `VIDIOC_S_FMT` on `/dev/videoN` | `VIDIOC_SUBDEV_S_FMT` on `/dev/v4l-subdevN` |

같은 센서 데이터가 **링크 위에서는 mbus code, 메모리에 내려앉으면 fourcc**다. 그 사이 변환(예: 10비트 Bayer를 16비트로 펼치기, RAW10 packed로 저장하기, YUV 4:2:2를 NV12로 바꾸기)은 수신기·ISP·DMA writer가 한다. 그래서 MC 파이프라인의 끝 video node는 "어떤 mbus code에서 어떤 fourcc를 만들 수 있나"의 표를 갖고 있고, `link_validate`가 그 표로 짝을 검사한다(§9). Don에게 익숙한 비유로 하면 mbus code는 "PHY/링크 계층 프레이밍", fourcc는 "호스트 메모리 데이터 구조"다.

### 3.4 흔한 함정

- `S_FMT`의 반환값을 안 읽는다 — 드라이버는 지원 안 하는 값을 **조용히 고쳐서** 돌려준다(§12.4에서 i5_cam이 640x480 YUYV 요청을 320x240 GREY로 바꾼다). 에러가 아니다. 반드시 돌려받은 `width`·`height`·`pixelformat`·`bytesperline`으로 버퍼를 해석한다.
- `sizeimage`를 `width × height × bpp`로 직접 계산한다 — stride 정렬, 평면 사이 패딩, 압축 포맷 때문에 다르다. 드라이버가 준 `sizeimage`를 쓴다.
- 멀티플레인 포맷(`NV12M`처럼 Y와 UV가 다른 버퍼)을 쓰는 드라이버는 `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE`과 `struct v4l2_pix_format_mplane`을 쓴다. vivid도 `multiplanar=2` 모듈 인자로 그 모드가 된다. 이 노트의 예제는 single-planar만 다룬다.

## 4. 컨트롤 프레임워크 — 노출, 게인, 테스트 패턴, 링크 주파수

### 4.1 직관

센서 레지스터 중 "앱이 런타임에 바꾸고 싶은 것"(노출 시간, 아날로그 게인, 플립, 테스트 패턴)은 V4L2 **컨트롤**로 노출된다. 펌웨어로 치면 "레지스터 맵 중 공개 API로 올린 필드"다. 드라이버는 `v4l2_ctrl_handler`에 컨트롤을 등록하고 `s_ctrl` 콜백 하나에서 레지스터를 쓴다. 범위 검사, 기본값, 메뉴 문자열, 이벤트 통지, 잠금, 여러 노드에서 상속은 프레임워크가 한다.

### 4.2 예제 2 — `i5_ctrls`: 컨트롤 열거와 설정

무엇을 확인하는 코드인지: `VIDIOC_QUERY_EXT_CTRL` + `V4L2_CTRL_FLAG_NEXT_CTRL`로 모든 컨트롤을 차례로 열거하고, 이름에 "Pattern"이 든 메뉴는 `VIDIOC_QUERYMENU`로 항목을 출력한다. 인자로 `0xID=값`을 주면 `S_CTRL`로 설정한다.

```c
/* i5_ctrls.c <dev> [0xID=val ...] — 컨트롤 열거(QUERY_EXT_CTRL), 메뉴 항목, 값 설정 */
#include "i5.h"

static const char *tname(unsigned t)
{
	switch (t) {
	case V4L2_CTRL_TYPE_INTEGER: return "int";   case V4L2_CTRL_TYPE_BOOLEAN: return "bool";
	case V4L2_CTRL_TYPE_MENU: return "menu";     case V4L2_CTRL_TYPE_INTEGER_MENU: return "intmenu";
	case V4L2_CTRL_TYPE_BUTTON: return "button"; case V4L2_CTRL_TYPE_CTRL_CLASS: return "class";
	case V4L2_CTRL_TYPE_INTEGER64: return "int64"; default: return "other";
	}
}

int main(int argc, char **argv)
{
	int fd = open(argv[1], O_RDWR);
	if (fd < 0) die("open");
	for (int i = 2; i < argc; i++) {              /* 설정: 0xID=val */
		struct v4l2_control c = { .id = strtoul(argv[i], NULL, 0) };
		c.value = atoi(strchr(argv[i], '=') + 1);
		if (xioctl(fd, VIDIOC_S_CTRL, &c)) die("S_CTRL");
		xioctl(fd, VIDIOC_G_CTRL, &c);
		printf("set 0x%08x -> %d\n", c.id, c.value);
	}
	if (argc > 2) return 0;
	struct v4l2_query_ext_ctrl q = { .id = V4L2_CTRL_FLAG_NEXT_CTRL | V4L2_CTRL_FLAG_NEXT_COMPOUND };
	while (xioctl(fd, VIDIOC_QUERY_EXT_CTRL, &q) == 0) {
		if (q.type == V4L2_CTRL_TYPE_CTRL_CLASS) {
			printf("[%s]\n", q.name);
		} else if (!(q.flags & V4L2_CTRL_FLAG_DISABLED)) {
			struct v4l2_control c = { .id = q.id };
			int ok = q.type < V4L2_CTRL_COMPOUND_TYPES && xioctl(fd, VIDIOC_G_CTRL, &c) == 0;
			printf("  0x%08x %-26.26s %-7s min=%lld max=%lld def=%lld", q.id, q.name,
			       tname(q.type), q.minimum, q.maximum, q.default_value);
			if (ok) printf(" val=%d", c.value);
			printf("%s\n", q.flags & V4L2_CTRL_FLAG_READ_ONLY ? " (ro)" : "");
			if (q.type == V4L2_CTRL_TYPE_MENU && strstr(q.name, "Pattern")) {
				struct v4l2_querymenu m = { .id = q.id };
				for (m.index = q.minimum; m.index <= q.maximum; m.index++)
					if (xioctl(fd, VIDIOC_QUERYMENU, &m) == 0)
						printf("      %u: %s\n", m.index, m.name);
			}
		}
		q.id |= V4L2_CTRL_FLAG_NEXT_CTRL | V4L2_CTRL_FLAG_NEXT_COMPOUND;
	}
	close(fd);
	return 0;
}
```

### 4.3 실제 센서의 컨트롤 — imx219

랩 트리 `drivers/media/i2c/imx219.c`의 `imx219_init_controls()`가 등록하는 컨트롤(소스에서 직접 확인):

| 컨트롤 | 의미 | 왜 중요한가 |
|---|---|---|
| `V4L2_CID_PIXEL_RATE` (ro) | 초당 픽셀 수 | 수신기·ISP가 클럭과 대역폭을 계산할 때 읽는다 |
| `V4L2_CID_LINK_FREQ` (int menu) | CSI-2 링크 주파수 | DT의 `link-frequencies`와 일치해야 probe 성공. 수신기는 이것으로 D-PHY 설정(HS settle 등)을 계산 |
| `V4L2_CID_VBLANK`, `V4L2_CID_HBLANK` | 블랭킹 길이 | **프레임 레이트는 VBLANK로 조절**한다 (frame time = (height + vblank) × line_length / pixel_rate) |
| `V4L2_CID_EXPOSURE` | 노출(라인 단위) | 최대값이 VBLANK에 따라 바뀐다 (`s_ctrl`에서 범위 갱신) |
| `V4L2_CID_ANALOGUE_GAIN`, `V4L2_CID_DIGITAL_GAIN` | 게인 | 3A(자동 노출) 루프가 매 프레임 쓴다 |
| `V4L2_CID_HFLIP`, `V4L2_CID_VFLIP` | 뒤집기 | Bayer 순서(`SRGGB` → `SGRBG` 등)가 바뀌므로 mbus code도 바뀐다 |
| `V4L2_CID_TEST_PATTERN` + `TEST_PATTERN_RED/GREENR/BLUE/GREENB` | 센서 내장 패턴 | bring-up 첫날 **레인·포맷 검증**의 핵심 도구 |

센서 드라이버에는 `S_PARM`(프레임 간격)이 없다는 점이 MC 세계의 관례다. fps는 VBLANK·HBLANK·PIXEL_RATE 컨트롤로 표현하고, libcamera가 그것을 계산한다. MC 파이프라인에서 센서 컨트롤은 **센서 subdev 노드**(`/dev/v4l-subdevN`)에서 설정한다. video-centric 드라이버는 subdev의 컨트롤을 video 노드로 상속시킨다(`v4l2_ctrl_add_handler()`).

### 4.4 흔한 함정

- 스트리밍 중에는 바꿀 수 없는 컨트롤이 있다 — imx219는 스트림을 켜면서 `__v4l2_ctrl_grab(imx219->hflip, true)`(vflip도)로 플립을 잠근다. 플립이 Bayer 순서, 즉 mbus code를 바꾸는데 스트리밍 중에는 파이프라인 포맷을 바꿀 수 없기 때문이다. 잠긴 컨트롤에 `S_CTRL`을 하면 `-EBUSY`다.
- `s_ctrl`이 전원이 꺼진 센서에 I2C를 쓴다 — 실제 드라이버는 `pm_runtime_get_if_in_use()`로 전원이 켜져 있을 때만 쓰고, 꺼져 있으면 값만 저장했다가 스트림 시작 때 `__v4l2_ctrl_handler_setup()`으로 한꺼번에 쓴다(imx219의 `enable_streams` 코드가 그렇다, §11.3).
- 컨트롤 ID를 하드코딩한다 — 드라이버 전용 ID는 커널 버전마다 바뀔 수 있다. 이름이나 표준 CID로 찾는다.

## 5. 스트리밍 — videobuf2와 MMAP 캡처

### 5.1 직관 — SSD의 디스크립터 링과 똑같다

Don이 NVMe에서 본 SQ/CQ를 떠올리자. 호스트가 "이 버퍼에 써 줘"를 SQ에 넣고(doorbell), 컨트롤러가 다 쓰면 CQ에 완료를 올린다. V4L2 스트리밍이 정확히 그 구조다.

- `VIDIOC_REQBUFS` — 버퍼 N개를 커널이 할당한다 (링 크기 결정).
- `VIDIOC_QBUF` — "이 빈 버퍼에 다음 프레임을 써 줘" (SQ에 넣기).
- `VIDIOC_STREAMON` — 엔진 시작 (doorbell + enable).
- 프레임 끝 인터럽트 → 드라이버가 `vb2_buffer_done()` (CQ에 완료 기록).
- `VIDIOC_DQBUF` — 다 찬 버퍼 하나를 받는다 (CQ 소비). `poll()`로 기다릴 수 있다.
- 처리 후 다시 `QBUF` — 버퍼 재활용.

이 링을 모든 드라이버가 따로 짜면 버그가 나니까, 커널은 **videobuf2**(vb2)라는 공용 큐 구현을 둔다. 드라이버는 `vb2_ops` 콜백 5개 정도만 채우고, ioctl 처리·mmap·dma-buf·poll·상태 관리는 vb2가 한다.

### 5.2 예제 3 — `i5_cap`: MMAP 스트리밍 캡처 (이 노트의 주력 프로그램)

무엇을 확인하는 코드인지: 포맷 설정 → REQBUFS(MMAP) → QUERYBUF + mmap → QBUF 전부 → STREAMON → N번 DQBUF/QBUF → STREAMOFF. 매 프레임의 `sequence`와 `timestamp`로 프레임 간격, 손실(sequence 틈), fps를 계산하고, 첫 프레임을 파일로 저장할 수 있다. 느린 소비자를 흉내 내는 sleep 옵션이 있다(§7).

```c
/* i5_cap.c <dev> <W> <H> <FOURCC> <N> [nbufs] [sleep_ms(<0: 10프레임마다)] [save] — MMAP 스트리밍 캡처
 * env: V=1 프레임별 출력, FPS=n 이면 S_PARM 1/n.  W=0이면 S_FMT 생략 */
#include "i5.h"
#define T V4L2_BUF_TYPE_VIDEO_CAPTURE

int main(int argc, char **argv)
{
	if (argc < 6) { fprintf(stderr, "usage\n"); return 2; }
	int fd = open(argv[1], O_RDWR), n = atoi(argv[5]), nb = argc > 6 ? atoi(argv[6]) : 4;
	int slp = argc > 7 ? atoi(argv[7]) : 0, verbose = getenv("V") != NULL;
	if (fd < 0) die("open");
	struct v4l2_format f = { .type = T };
	if (xioctl(fd, VIDIOC_G_FMT, &f)) die("G_FMT");
	if (atoi(argv[2])) { f.fmt.pix.width = atoi(argv[2]); f.fmt.pix.height = atoi(argv[3]);
		f.fmt.pix.pixelformat = v4l2_fourcc(argv[4][0], argv[4][1], argv[4][2], argv[4][3]);
		f.fmt.pix.field = V4L2_FIELD_NONE;
		if (xioctl(fd, VIDIOC_S_FMT, &f)) die("S_FMT"); }  /* 드라이버가 값을 고쳐서 돌려준다 */
	struct v4l2_streamparm sp_ = { .type = T };
	if (getenv("FPS")) { sp_.parm.capture.timeperframe = (struct v4l2_fract){ 1, atoi(getenv("FPS")) };
		if (xioctl(fd, VIDIOC_S_PARM, &sp_)) die("S_PARM"); }
	printf("fmt %ux%u %s stride=%u size=%u\n", f.fmt.pix.width, f.fmt.pix.height,
	       fcc(f.fmt.pix.pixelformat), f.fmt.pix.bytesperline, f.fmt.pix.sizeimage);
	if (n == 0) return close(fd);                      /* N=0: 포맷만 설정하고 끝 */
	struct v4l2_requestbuffers rb = { .count = nb, .type = T, .memory = V4L2_MEMORY_MMAP };
	if (xioctl(fd, VIDIOC_REQBUFS, &rb)) die("REQBUFS");
	unsigned char *mem[32]; size_t len[32];
	for (unsigned i = 0; i < rb.count; i++) {
		struct v4l2_buffer b = { .index = i, .type = T, .memory = V4L2_MEMORY_MMAP };
		if (xioctl(fd, VIDIOC_QUERYBUF, &b)) die("QUERYBUF");
		mem[i] = mmap(NULL, len[i] = b.length, PROT_READ, MAP_SHARED, fd, b.m.offset);
		if (mem[i] == MAP_FAILED) die("mmap");
		if (xioctl(fd, VIDIOC_QBUF, &b)) die("QBUF");
	}
	enum v4l2_buf_type t = T;
	if (xioctl(fd, VIDIOC_STREAMON, &t)) die("STREAMON");
	double ts0 = 0, tp = 0, dmin = 1e9, dmax = 0; unsigned seq0 = 0, sp = 0, lost = 0;
	for (int k = 0; k < n; k++) {
		struct v4l2_buffer b = { .type = T, .memory = V4L2_MEMORY_MMAP };
		if (xioctl(fd, VIDIOC_DQBUF, &b)) die("DQBUF");   /* 블로킹: 다 찬 버퍼를 받는다 */
		double ts = b.timestamp.tv_sec + b.timestamp.tv_usec / 1e6, d = ts - tp;
		unsigned char *m = mem[b.index];
		if (k == 0) { ts0 = ts; seq0 = b.sequence;
			printf("REQBUFS %d->%u flags=0x%x monotonic=%d first bytes %02x %02x %02x %02x\n",
			       nb, rb.count, b.flags, (b.flags & V4L2_BUF_FLAG_TIMESTAMP_MASK) ==
			       V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC, m[0], m[1], m[2], m[3]);
			FILE *o = argc > 8 ? fopen(argv[8], "w") : NULL;
			if (o) { fwrite(m, 1, b.bytesused, o); fclose(o); }
		} else { dmin = d < dmin ? d : dmin; dmax = d > dmax ? d : dmax; lost += b.sequence - sp - 1; }
		if (verbose) printf("k=%d idx=%u seq=%u dt_ms=%.3f bytes=%u lag_ms=%.1f w0=%08x\n", k,
			b.index, b.sequence, k ? d * 1e3 : 0, b.bytesused, (now_s() - ts) * 1e3, *(unsigned *)m);
		tp = ts; sp = b.sequence;
		if (slp > 0 || (slp < 0 && k % 10 == 9)) usleep(abs(slp) * 1000); /* 느린/가끔 멈추는 소비자 */
		if (xioctl(fd, VIDIOC_QBUF, &b)) die("QBUF");      /* 버퍼를 드라이버에게 돌려준다 */
	}
	if (xioctl(fd, VIDIOC_STREAMOFF, &t)) die("STREAMOFF");
	printf("frames=%d seq %u..%u lost=%u fps=%.2f dt_ms min=%.2f max=%.2f\n", n, seq0, sp,
	       lost, (n - 1) / (tp - ts0), dmin * 1e3, dmax * 1e3);
	for (unsigned i = 0; i < rb.count; i++) munmap(mem[i], len[i]);
	return close(fd);
}
```

이 프로그램이 지키는 규칙 세 가지가 V4L2 앱의 기본이다.

1. **mmap은 QUERYBUF가 준 `m.offset`으로** 한다. 이 값은 진짜 파일 오프셋이 아니라 "버퍼 번호를 인코딩한 쿠키"다(§5.4 출력에서 버퍼 1의 offset이 `0x8000`인 것을 보라). 드라이버의 `.mmap`(= `vb2_fop_mmap`)이 이 쿠키로 버퍼를 찾는다. G5에서 직접 짠 `.mmap`의 vb2판이다.
2. **DQBUF로 받은 버퍼만 읽고, QBUF한 버퍼는 건드리지 않는다.** QBUF 이후 그 메모리는 DMA가 쓰고 있다.
3. **sequence를 믿고 timestamp로 간격을 잰다.** 앱이 DQBUF한 시각(`now_s()`)이 아니라 드라이버가 기록한 `timestamp`가 프레임의 시각이다.

### 5.3 예제 4 — vivid 컬러바를 캡처해서 바이트로 검증

### 5.5 메모리 타입 — 누가 버퍼를 할당하나

`v4l2_requestbuffers.memory`와 드라이버의 `vb2_queue.mem_ops` 두 축이 있다.

| 유저 쪽 `memory` | 누가 할당 | 앱이 받는 것 | 쓰는 경우 |
|---|---|---|---|
| `V4L2_MEMORY_MMAP` | 드라이버(vb2 mem_ops) | `m.offset` → mmap | 기본. 가장 흔함 |
| `V4L2_MEMORY_USERPTR` | 앱 (`malloc`) | 앱 포인터를 `m.userptr`로 넘김 | 레거시. DMA 장치는 페이지 고정·연속성 문제로 비추천 |
| `V4L2_MEMORY_DMABUF` | **다른 장치나 dma-heap** | dma-buf fd를 `m.fd`로 넘김 | zero-copy 공유 (§8) |

| 드라이버 `mem_ops` | 메모리 | 쓰는 장치 |
|---|---|---|
| `vb2_vmalloc_memops` | `vmalloc` — 가상으로만 연속 | CPU가 픽셀을 만드는 장치(vivid, vimc, UVC 웹캠: USB로 받은 데이터를 CPU가 복사) |
| `vb2_dma_contig_memops` | DMA API로 **물리(또는 IOVA) 연속** — CMA(F10) | 단순 DMA 엔진의 SoC 수신기(i.MX8 ISI, RZ/G2L CRU 등) |
| `vb2_dma_sg_memops` | 흩어진 페이지 + scatterlist | SG를 지원하는 DMA (PCIe 캡처 카드 등) |

`VIDIOC_EXPBUF`는 MMAP 버퍼를 **dma-buf fd로 내보내는** ioctl이다. 세 mem_ops 모두 exporter가 될 수 있다.

### 5.6 흔한 함정

- QBUF한 버퍼를 앱이 계속 읽는다 — 다음 프레임이 반쯤 덮인 "찢어진 프레임"이 나온다. 처리 중인 버퍼는 QBUF하지 말고 처리가 끝난 뒤 돌려준다.
- 버퍼를 2개만 요청한다 — 드라이버가 하나에 쓰는 동안 앱이 하나를 들고 있으면 드라이버는 다음 프레임에 쓸 곳이 없다. 실무 기본은 4~8개(§7 측정).
- `REQBUFS`의 count 반환값을 안 본다 — 드라이버가 최소 개수(`min_reqbufs_allocation`)로 올리거나 메모리 부족으로 줄일 수 있다.
- STREAMOFF 후 mmap을 풀지 않고 `REQBUFS count=0`을 부른다 — 매핑이 남아 있으면 `-EBUSY`다. munmap 먼저.

## 6. 타임스탬프 · sequence · 프레임 레이트

### 6.1 정의

`struct v4l2_buffer`가 DQBUF로 돌아올 때 채워지는 시간 정보:

| 필드 | 의미 |
|---|---|
| `timestamp` (`struct timeval`) | 드라이버가 기록한 프레임 시각. `flags & V4L2_BUF_FLAG_TIMESTAMP_MASK`가 `MONOTONIC`이면 `CLOCK_MONOTONIC` 기준 |
| `flags & V4L2_BUF_FLAG_TSTAMP_SRC_MASK` | 그 시각이 프레임 **끝**(`TSTAMP_SRC_EOF`, 0)인지 **시작**(`TSTAMP_SRC_SOE`)인지 |
| `sequence` | 드라이버의 프레임 카운터. **버퍼가 없어 버린 프레임에도 증가해야 한다** |

`CLOCK_MONOTONIC`이라는 것이 핵심이다. 앱은 `clock_gettime(CLOCK_MONOTONIC)`과 같은 시간축에서 카메라 프레임을 IMU 샘플(IIO 타임스탬프, I2)이나 LiDAR 패킷과 맞출 수 있다. 멀티 카메라 동기화(Q3)는 결국 "각 카메라의 SOE 타임스탬프가 몇 µs 안에 모이나"의 문제다.

출력에서 볼 것:

- **vivid의 `lag_ms`가 -29.7 ms로 음수다.** DQBUF한 시각보다 타임스탬프가 30 ms "미래"라는 뜻이다. 소스(`vivid-kthread-cap.c`)를 보면 vivid는 프레임을 그린 시각에 `cap_frame_eof_offset`(프레임 주기의 9/10)을 더해서 "프레임 끝(EOF) 시각"을 흉내 낸다. 실제 하드웨어에서는 불가능한 값이지만, 교훈은 분명하다. **타임스탬프의 의미(SOE/EOF, 어느 클럭, 어느 지점에서 찍었나)는 드라이버가 정한다.** 센서 퓨전 코드는 그 의미를 문서나 소스로 확인해야 한다.
- i5_cam은 hrtimer 콜백(가짜 IRQ)에서 `ktime_get_ns()`로 찍으므로 lag가 0.3~1.1 ms다. 진짜 드라이버도 **ISR에서, 가능한 한 빨리** 타임스탬프를 찍는다. bottom half(workqueue)에서 찍으면 스케줄링 지연만큼 흔들린다.
- 간격의 흔들림(jitter)은 타임스탬프를 찍는 지점의 흔들림이다. 실제 센서의 프레임 주기는 수정 발진기로 정해지므로 수 µs 이내로 일정하다. 그러므로 실 장비에서 타임스탬프 간격이 ms 단위로 흔들린다면 **IRQ 지연**(긴 irq-off 구간, threaded IRQ 우선순위) 문제다(N1·M 모듈).

### 6.4 흔한 함정

- `gettimeofday()`(CLOCK_REALTIME)와 버퍼 타임스탬프를 비교한다 — 기준 시계가 다르다. NTP가 시간을 조정하면 수 초가 틀어진다. 항상 `CLOCK_MONOTONIC`.
- 앱이 DQBUF한 시각을 프레임 시각으로 쓴다 — 앱 스케줄링 지연(예제 8에서 lag 17~42 ms)이 그대로 센서 퓨전 오차가 된다.
- `timestamp`를 `TIMESTAMP_COPY` 큐(m2m 장치)에서 해석한다 — m2m은 OUTPUT 버퍼의 타임스탬프를 CAPTURE로 복사할 뿐 실제 시각이 아니다.

## 7. 드롭 프레임 — sequence 틈으로 잡는다

### 7.1 직관

카메라는 기다려 주지 않는다. 센서는 33.3 ms마다 프레임을 밀어내고, 그 순간 드라이버에게 빈 버퍼(QUEUED → ACTIVE로 갈 버퍼)가 없으면 그 프레임은 **버려진다**. 드라이버가 할 일은 하나뿐이다: sequence를 그래도 증가시켜서 앱이 알게 하는 것. 앱이 할 일은 `b.sequence - prev - 1`을 세는 것이다. Don이 SSD에서 CQ가 꽉 차서 완료를 못 올리는 상황을 phase bit로 감지했던 것과 같은 성격의 장치다.

### 7.4 흔한 함정

- 손실을 앱 쪽 fps(초당 DQBUF 수)로 판단한다 — 소비자가 일정하게 느리면 fps는 안정적으로 보이지만 프레임은 꾸준히 버려진다. sequence 틈을 센다.
- 드라이버가 빈 버퍼가 없을 때 sequence를 증가시키지 않는다 — 앱이 손실을 영원히 모른다. 리뷰에서 반드시 보는 지점이다(i5_cam의 `else` 분기).
- 버퍼를 무작정 늘린다 — 1080p NV12 3 MiB × 카메라 4대 × 12개 = 144 MiB의 CMA(F10)다. 지연(latency)도 늘어난다: 앱은 최대 N 프레임 전 영상을 보게 된다. 로봇 제어 루프에서는 오래된 프레임을 버리고 최신 것만 쓰는 정책이 더 낫다.

### 8.2 예제 10 — vivid 캡처 → EXPBUF → vim2m OUTPUT(DMABUF import)

무엇을 확인하는 코드인지: vivid 캡처 버퍼 4개를 MMAP으로 할당하고 `VIDIOC_EXPBUF`로 dma-buf fd 4개를 만든다. vim2m(메모리 → 메모리 변환기, 여기서는 "인코더" 역할)의 OUTPUT 큐를 `V4L2_MEMORY_DMABUF`로 열고, vivid가 채운 버퍼의 **fd만** QBUF한다. vim2m은 RGB24를 BGR24로 바꿔 자기 CAPTURE 버퍼에 쓴다. 두 번째 프레임에서 debugfs의 dma-buf 목록을 출력한다.

```c
/* i5_dmabuf.c <cam> <m2m> <N> — vivid 캡처 버퍼를 EXPBUF로 dma-buf fd로 내보내고,
 * vim2m OUTPUT 큐에 V4L2_MEMORY_DMABUF로 import (복사 없음). vim2m은 RGB24→BGR24 변환 */
#include "i5.h"
#define CAP V4L2_BUF_TYPE_VIDEO_CAPTURE
#define OUT V4L2_BUF_TYPE_VIDEO_OUTPUT

static void setup(int fd, int type, unsigned fourcc, int mem, int n)
{
	struct v4l2_format f = { .type = type };
	f.fmt.pix = (struct v4l2_pix_format){ .width = 640, .height = 480, .pixelformat = fourcc,
					      .field = V4L2_FIELD_NONE };
	if (xioctl(fd, VIDIOC_S_FMT, &f)) die("S_FMT");
	struct v4l2_requestbuffers rb = { .count = n, .type = type, .memory = mem };
	if (xioctl(fd, VIDIOC_REQBUFS, &rb)) die("REQBUFS");
	for (int i = 0; i < n && type == CAP; i++) {
		struct v4l2_buffer b = { .index = i, .type = type, .memory = mem };
		if (xioctl(fd, VIDIOC_QBUF, &b)) die("QBUF");
	}
	if (xioctl(fd, VIDIOC_STREAMON, &type)) die("STREAMON");
}

int main(int argc, char **argv)
{
	int cam = open(argv[1], O_RDWR), m2m = open(argv[2], O_RDWR), n = atoi(argv[3]), xfd[4];
	if (argc < 4 || cam < 0 || m2m < 0) die("open");
	setup(cam, CAP, V4L2_PIX_FMT_RGB24, V4L2_MEMORY_MMAP, 4);
	for (int i = 0; i < 4; i++) {                 /* vb2 버퍼 → dma-buf fd */
		struct v4l2_exportbuffer e = { .type = CAP, .index = i, .flags = O_RDONLY | O_CLOEXEC };
		if (xioctl(cam, VIDIOC_EXPBUF, &e)) die("EXPBUF");
		xfd[i] = e.fd;
	}
	printf("exported fds: %d %d %d %d\n", xfd[0], xfd[1], xfd[2], xfd[3]);
	setup(m2m, OUT, V4L2_PIX_FMT_RGB24, V4L2_MEMORY_DMABUF, 4);
	setup(m2m, CAP, V4L2_PIX_FMT_BGR24, V4L2_MEMORY_MMAP, 2);
	struct v4l2_buffer q = { .index = 0, .type = CAP, .memory = V4L2_MEMORY_MMAP };
	if (xioctl(m2m, VIDIOC_QUERYBUF, &q)) die("QUERYBUF");
	unsigned char *o0 = mmap(NULL, q.length, PROT_READ, MAP_SHARED, m2m, q.m.offset);
	q.index = 1; if (xioctl(m2m, VIDIOC_QUERYBUF, &q)) die("QUERYBUF");
	unsigned char *o1 = mmap(NULL, q.length, PROT_READ, MAP_SHARED, m2m, q.m.offset);
	if (o0 == MAP_FAILED || o1 == MAP_FAILED) die("mmap");
	for (int k = 0; k < n; k++) {
		struct v4l2_buffer c = { .type = CAP, .memory = V4L2_MEMORY_MMAP };
		if (xioctl(cam, VIDIOC_DQBUF, &c)) die("cam DQBUF");
		struct v4l2_buffer in = { .type = OUT, .memory = V4L2_MEMORY_DMABUF, .index = c.index,
					  .bytesused = c.bytesused, .m.fd = xfd[c.index] };
		if (xioctl(m2m, VIDIOC_QBUF, &in)) die("m2m QBUF(DMABUF)");   /* fd만 넘긴다 */
		if (k == 1 && (fflush(stdout), system("grep -E '^0|exp_name' /sys/kernel/debug/dma_buf/bufinfo")))
			perror("system");
		if (xioctl(m2m, VIDIOC_DQBUF, &in)) die("m2m DQBUF out");
		struct v4l2_buffer ob = { .type = CAP, .memory = V4L2_MEMORY_MMAP };
		if (xioctl(m2m, VIDIOC_DQBUF, &ob)) die("m2m DQBUF cap");
		unsigned char *p = (ob.index ? o1 : o0) + 240 * 1920 + 120 * 3;   /* 노랑 막대 */
		printf("k=%d cam idx=%u seq=%u -> m2m out idx=%u seq=%u px(120,240)=%u,%u,%u\n", k,
		       c.index, c.sequence, ob.index, ob.sequence, p[0], p[1], p[2]);
		if (xioctl(m2m, VIDIOC_QBUF, &ob)) die("m2m QBUF cap");
		if (xioctl(cam, VIDIOC_QBUF, &c)) die("cam QBUF");
	}
	return 0;
}
```

### 8.3 예제 11 — DMA 제약이 다른 장치끼리 공유하면

무엇을 확인하는 코드인지: vivid를 두 인스턴스로 올리고 `allocators` 모듈 인자로 메모리 종류를 다르게 한다(0 = vmalloc, 1 = dma-contig). 캡처 인스턴스의 버퍼 하나를 EXPBUF해서 출력 인스턴스(`node_types=0x100`, video 출력만)의 큐에 DMABUF로 넣는다.

```c
/* i5_attach.c <cam> <out> — vmalloc 캡처 버퍼(exporter)를 dma-contig 출력 장치(importer)에
 * DMABUF로 넘겨 dma_buf_attach()가 일어나는지 debugfs로 본다 */
#include "i5.h"
#define CAP V4L2_BUF_TYPE_VIDEO_CAPTURE
#define OUT V4L2_BUF_TYPE_VIDEO_OUTPUT

static void fmt_reqbufs(int fd, int type, int mem)
{
	struct v4l2_format f = { .type = type };
	f.fmt.pix = (struct v4l2_pix_format){ .width = 640, .height = 480,
		.pixelformat = V4L2_PIX_FMT_RGB24, .field = V4L2_FIELD_NONE };
	if (xioctl(fd, VIDIOC_S_FMT, &f)) die("S_FMT");
	struct v4l2_requestbuffers rb = { .count = 2, .type = type, .memory = mem };
	if (xioctl(fd, VIDIOC_REQBUFS, &rb)) die("REQBUFS");
}

int main(int argc, char **argv)
{
	if (argc < 3) return 2;
	int cam = open(argv[1], O_RDWR), out = open(argv[2], O_RDWR);
	if (cam < 0 || out < 0) die("open");
	fmt_reqbufs(cam, CAP, V4L2_MEMORY_MMAP);
	fmt_reqbufs(out, OUT, V4L2_MEMORY_DMABUF);
	struct v4l2_exportbuffer e = { .type = CAP, .index = 0, .flags = O_RDWR };
	if (xioctl(cam, VIDIOC_EXPBUF, &e)) die("EXPBUF");
	struct v4l2_buffer b = { .type = OUT, .memory = V4L2_MEMORY_DMABUF, .index = 0,
				 .bytesused = 640 * 480 * 3, .m.fd = e.fd };
	if (xioctl(out, VIDIOC_QBUF, &b)) die("QBUF(DMABUF)");   /* 여기서 attach + map */
	fflush(stdout);
	if (system("cat /sys/kernel/debug/dma_buf/bufinfo")) perror("system");
	return 0;
}
```

출력에서 볼 것:

- 첫 실험에서 QBUF가 `-EFAULT`(Bad address)로 실패하고 커널이 `contiguous chunk is too small 4096/921600`을 남겼다. `videobuf2-dma-contig`의 import 경로가 `dma_buf_map_attachment()`로 받은 sg_table이 **한 덩어리로 연속인지** 검사했는데, vmalloc 버퍼는 4 KiB 페이지가 흩어져 있었다. IOMMU가 있었다면 IOVA로 이어 붙여 성공했을 것이다(H9 §7). 실무 규칙: **공유 버퍼는 가장 제약이 큰 장치 기준으로 할당한다.** 보통 dma-contig(CMA) 쪽이 exporter가 되거나, `/dev/dma_heap/linux,cma`(F10 §8.1)에서 받아 양쪽에 import한다.
- 둘째 실험은 성공했고 `Attached Devices: vivid.0`이 보인다. importer가 `dma_buf_attach()`를 불렀다는 뜻이다. 두 인스턴스(vivid-000, vivid-001)가 같은 플랫폼 장치 `vivid.0` 하나를 공유하기 때문에(`vivid-core.c`의 `vivid_pdev`는 하나다) 장치 이름이 같다. `exp_name`이 `videobuf2_dma_contig`, `count`(파일 참조 수)는 3 — 앱의 EXPBUF fd 외에 importer 쪽이 잡은 참조들이다(정확한 내역은 추적하지 않았다).

### 8.4 흔한 함정

- dma-buf fd를 넘긴 뒤 원래 큐에 QBUF한다 — 카메라가 다음 프레임을 같은 버퍼에 쓰는 동안 인코더가 읽는다. 소비자 쪽 DQBUF로 "다 읽었다"를 확인한 다음에 카메라 큐에 돌려준다(예제 10의 루프 순서).
- 캐시 일관성을 잊는다 — CPU도 그 버퍼를 만진다면 `DMA_BUF_IOCTL_SYNC`(`DMA_BUF_SYNC_START`/`END`)로 감싼다. 장치끼리만 쓰면 exporter·importer의 map/unmap이 처리한다.
- fd 누수 — EXPBUF fd는 앱이 `close()`해야 한다. 안 닫으면 `REQBUFS count=0`을 해도 메모리가 해제되지 않는다(`bufinfo`에 계속 남는다).

## 9. media controller 실습 — vimc 그래프를 직접 읽고 설정하기

### 9.1 예제 12 — `i5_topo`: `MEDIA_IOC_G_TOPOLOGY`로 그래프 출력

무엇을 확인하는 코드인지: `media-ctl -p`의 축소판이다. `MEDIA_IOC_G_TOPOLOGY`는 **두 번** 부른다 — 첫 호출은 배열 포인터 없이 개수만 받고, 두 번째에 그 크기의 배열을 넘겨 내용을 받는다. 그 뒤 entity마다 데이터 링크(pad → pad), 보조 링크(ancillary, 센서 → 렌즈), 인터페이스 링크(devnode → entity)를 출력한다. devnode의 major:minor는 `/sys/dev/char/M:m` 심볼릭 링크로 `/dev` 이름으로 바꾼다.

```c
/* i5_topo.c <media> — MEDIA_IOC_DEVICE_INFO + MEDIA_IOC_G_TOPOLOGY 로 그래프 출력 (media-ctl -p 축소판) */
#include "i5.h"
#include <stdint.h>
#define P(x) ((uintptr_t)(x))
static struct media_v2_topology t;
static struct media_v2_entity *E; static struct media_v2_interface *I;
static struct media_v2_pad *Pd; static struct media_v2_link *L;

static const char *ename(unsigned id)        /* entity id 또는 pad id → entity 이름 */
{
	for (unsigned i = 0; i < t.num_pads; i++) if (Pd[i].id == id) id = Pd[i].entity_id;
	for (unsigned i = 0; i < t.num_entities; i++) if (E[i].id == id) return E[i].name;
	return "?";
}
static int pidx(unsigned id)
{
	for (unsigned i = 0; i < t.num_pads; i++) if (Pd[i].id == id) return Pd[i].index;
	return -1;
}

int main(int argc, char **argv)
{
	int fd = open(argc > 1 ? argv[1] : "/dev/media0", O_RDWR);
	if (fd < 0) die("open");
	struct media_device_info di = {0};
	if (xioctl(fd, MEDIA_IOC_DEVICE_INFO, &di)) die("DEVICE_INFO");
	printf("driver=%s model=%s bus=%s\n", di.driver, di.model, di.bus_info);
	if (xioctl(fd, MEDIA_IOC_G_TOPOLOGY, &t)) die("G_TOPOLOGY");      /* 1차: 개수만 */
	E = calloc(t.num_entities, sizeof *E); I = calloc(t.num_interfaces, sizeof *I);
	Pd = calloc(t.num_pads, sizeof *Pd); L = calloc(t.num_links, sizeof *L);
	t.ptr_entities = P(E); t.ptr_interfaces = P(I); t.ptr_pads = P(Pd); t.ptr_links = P(L);
	if (xioctl(fd, MEDIA_IOC_G_TOPOLOGY, &t)) die("G_TOPOLOGY");      /* 2차: 내용 */
	printf("topology_version=%llu entities=%u interfaces=%u pads=%u links=%u\n",
	       (unsigned long long)t.topology_version, t.num_entities, t.num_interfaces, t.num_pads, t.num_links);
	for (unsigned e = 0; e < t.num_entities; e++) {
		printf("- entity %u '%s' function=0x%05x\n", E[e].id, E[e].name, E[e].function);
		for (unsigned l = 0; l < t.num_links; l++) {
			struct media_v2_link *k = &L[l];
			unsigned ty = k->flags & MEDIA_LNK_FL_LINK_TYPE;
			if (ty == MEDIA_LNK_FL_INTERFACE_LINK && k->sink_id == E[e].id)
				for (unsigned i = 0; i < t.num_interfaces; i++) {
					if (I[i].id != k->source_id) continue;
					char p[64], d[64] = "?"; ssize_t r;
					snprintf(p, sizeof p, "/sys/dev/char/%u:%u", I[i].devnode.major, I[i].devnode.minor);
					if ((r = readlink(p, d, sizeof d - 1)) > 0) d[r] = 0;
					printf("    devnode /dev/%s (intf type 0x%x)\n", strrchr(d, '/') ? strrchr(d, '/') + 1 : d, I[i].intf_type);
				}
			if (ty == MEDIA_LNK_FL_DATA_LINK && strcmp(ename(k->source_id), E[e].name) == 0)
				printf("    pad%d -> '%s':%d [%s%s]\n", pidx(k->source_id), ename(k->sink_id), pidx(k->sink_id),
				       k->flags & MEDIA_LNK_FL_ENABLED ? "ENABLED" : "disabled",
				       k->flags & MEDIA_LNK_FL_IMMUTABLE ? ",IMMUTABLE" : "");
			if (ty == MEDIA_LNK_FL_ANCILLARY_LINK && k->source_id == E[e].id)
				printf("    ancillary -> '%s'\n", ename(k->sink_id));
		}
	}
	return close(fd);
}
```

그림 8 — 위 출력을 그린 vimc 그래프(§9.2에서 고친 뒤의 포맷 표시). 굵은 선은 켜진 링크, 점선은 꺼진 링크다. Scaler의 sink pad 하나에 세 소스가 연결되어 있지만 동시에 하나만 켤 수 있다 — 실제 SoC에서 "CSI-2 수신기 0번과 1번 중 어느 것을 ISP에 물릴지"를 고르는 mux와 같다.

출력에서 볼 것:

- function 코드: `0x20001` = `MEDIA_ENT_F_CAM_SENSOR`, `0x04003` = `MEDIA_ENT_F_PROC_VIDEO_PIXEL_ENC_CONV`(debayer), `0x04005` = `MEDIA_ENT_F_PROC_VIDEO_SCALER`, `0x10001` = `MEDIA_ENT_F_IO_V4L`(video node), `0x20003` = `MEDIA_ENT_F_LENS`. interface 타입 `0x200` = `MEDIA_INTF_T_V4L_VIDEO`, `0x203` = `MEDIA_INTF_T_V4L_SUBDEV`.
- `topology_version=16` — 그래프가 바뀔 때마다(entity 추가 등) 증가한다. 앱은 두 번의 G_TOPOLOGY 사이에 그래프가 바뀌었는지 이 값으로 안다.
- entity id(1, 3, 5, 8, 11 …)는 연속이 아니다. pad·link·interface도 같은 id 공간을 쓰기 때문이다(graph object id).
- **Raw Capture 0도 Sensor A에 붙어 있다.** 이 사실이 §9.2의 두 번째 실패 원인이다.

```c
/* i5_subfmt.c <subdev> <pad> [W H CODE] — VIDIOC_SUBDEV_G_FMT / S_FMT (ACTIVE), ENUM_MBUS_CODE */
#include "i5.h"

int main(int argc, char **argv)
{
	if (argc < 3) return 2;
	int fd = open(argv[1], O_RDWR), pad = atoi(argv[2]);
	if (fd < 0) die("open");
	struct v4l2_subdev_mbus_code_enum ce = { .pad = pad, .which = V4L2_SUBDEV_FORMAT_ACTIVE };
	printf("%s pad%d codes:", argv[1], pad);
	for (ce.index = 0; xioctl(fd, VIDIOC_SUBDEV_ENUM_MBUS_CODE, &ce) == 0 && ce.index < 8; ce.index++)
		printf(" 0x%04x", ce.code);
	printf("%s\n", ce.index == 8 ? " ..." : "");
	struct v4l2_subdev_format f = { .pad = pad, .which = V4L2_SUBDEV_FORMAT_ACTIVE };
	if (argc > 5) {
		f.format.width = atoi(argv[3]); f.format.height = atoi(argv[4]);
		f.format.code = strtoul(argv[5], NULL, 0); f.format.field = V4L2_FIELD_NONE;
		printf("  S_FMT req %ux%u 0x%04x\n", f.format.width, f.format.height, f.format.code);
		if (xioctl(fd, VIDIOC_SUBDEV_S_FMT, &f)) die("  S_FMT");
		printf("  -> got %ux%u 0x%04x\n", f.format.width, f.format.height, f.format.code);
	}
	if (xioctl(fd, VIDIOC_SUBDEV_G_FMT, &f)) die("G_FMT");
	printf("  active: %ux%u code=0x%04x field=%u colorspace=%u\n", f.format.width,
	       f.format.height, f.format.code, f.format.field, f.format.colorspace);
	return close(fd);
}
```

```c
/* i5_link.c <media> <src-entity> <src-pad> <sink-entity> <sink-pad> <0|1> — MEDIA_IOC_SETUP_LINK */
#include "i5.h"

static unsigned find(int fd, const char *name)       /* 이름 → entity id (ENUM_ENTITIES) */
{
	struct media_entity_desc d = { .id = MEDIA_ENT_ID_FLAG_NEXT };
	while (xioctl(fd, MEDIA_IOC_ENUM_ENTITIES, &d) == 0) {
		if (strcmp(d.name, name) == 0) return d.id;
		d.id |= MEDIA_ENT_ID_FLAG_NEXT;
	}
	fprintf(stderr, "no entity '%s'\n", name); exit(1);
}

int main(int argc, char **argv)
{
	if (argc < 7) return 2;
	int fd = open(argv[1], O_RDWR);
	if (fd < 0) die("open");
	struct media_link_desc l = {0};
	l.source.entity = find(fd, argv[2]); l.source.index = atoi(argv[3]);
	l.sink.entity = find(fd, argv[4]);   l.sink.index = atoi(argv[5]);
	l.flags = atoi(argv[6]) ? MEDIA_LNK_FL_ENABLED : 0;
	if (xioctl(fd, MEDIA_IOC_SETUP_LINK, &l)) die("SETUP_LINK");
	printf("link '%s':%s -> '%s':%s %s\n", argv[2], argv[3], argv[4], argv[5],
	       l.flags ? "ENABLED" : "disabled");
	return close(fd);
}
```

### 9.3 link validation은 누가 하나

`video_device_pipeline_start()` → `__media_pipeline_start()`가 그래프를 걷으며 파이프라인의 각 sink pad에 대해, 그 pad를 가진 entity의 `media_entity_operations.link_validate`를 부른다.

- sink가 **subdev**면 보통 `v4l2_subdev_link_validate()` → 드라이버의 pad op `link_validate`가 있으면 그것, 없으면 `v4l2_subdev_link_validate_default()`: **width, height, mbus code가 같아야** 하고 field는 같거나 sink가 `NONE`이어야 한다(위 소스 확인).
- sink가 **video node**면 드라이버가 직접 구현한다. vimc는 크기·pixelformat·field·colorimetry를 비교한다. 실제 SoC 드라이버는 "이 mbus code에서 이 fourcc를 만들 수 있나" 표를 본다.

에러 코드는 관례상 `-EPIPE`다. 그래서 MC 카메라에서 `STREAMON: Broken pipe`를 보면 첫 번째 질문은 "어느 링크의 양끝 포맷이 다른가"이고, 답은 `dyndbg`로 `v4l2-subdev.c`·`mc-entity.c`를 켜거나 `media-ctl -p`로 각 pad 포맷을 나란히 놓고 비교해서 얻는다.

## 10. 포맷 협상 — 파이프라인 전체에서 포맷을 맞추는 순서

### 10.1 규칙

1. **센서 쪽(상류)부터 하류로** 설정한다. 각 subdev는 sink pad 포맷을 받으면 자기 source pad 포맷을 **전파**(propagate)해서 기본값으로 채운다. vimc 스케일러 코드에서 sink를 설정하면 crop과 source가 같이 바뀌는 것을 봤다(`vimc_scaler_set_fmt`, §9의 4단계 전에 확인한 소스). 그래서 하류부터 맞추면 상류를 바꾸는 순간 하류가 덮인다.
2. 각 링크의 **source pad 포맷을 읽어 그대로 다음 sink pad에 설정**한다. 크기를 바꿀 수 있는 곳은 crop(`VIDIOC_SUBDEV_S_SELECTION`)과 scaler뿐이다.
3. 마지막 subdev의 source mbus code에 맞는 fourcc를 video node에 `S_FMT`한다. `VIDIOC_ENUM_FMT`에 `mbus_code` 필드를 넣으면(`V4L2_CAP_IO_MC` 드라이버) "이 mbus code에서 만들 수 있는 fourcc"만 열거된다.
4. 드라이버가 **고쳐서 돌려준 값**을 다음 단계 입력으로 쓴다. 센서가 지원하지 않는 크기를 요청하면 가장 가까운 모드로 바꿔 돌려준다.
5. 파이프라인이 다 맞으면 STREAMON. 스트리밍 중에는 ACTIVE 포맷을 못 바꾼다(`-EBUSY`).

### 10.2 TRY와 ACTIVE

subdev 포맷에는 두 벌이 있다. `which = V4L2_SUBDEV_FORMAT_ACTIVE`는 하드웨어에 실제로 적용될 값(드라이버의 active state), `V4L2_SUBDEV_FORMAT_TRY`는 **파일 핸들마다 따로 있는 연습용 state**다. libcamera 같은 상위 계층이 "이 조합이 되나"를 하드웨어를 건드리지 않고 시험할 때 쓴다. 6.x state API에서는 둘 다 `struct v4l2_subdev_state`이고, 드라이버의 `set_fmt`는 받은 state가 어느 것이든 같은 코드로 처리한다(그래서 imx219의 `init_state`가 `which = TRY`인 포맷 구조체로 `imx219_set_pad_format`을 부른다).

### 10.3 실제 예 — IMX219 → i.MX8MP CSI-2 → ISI (기억 기반, 실행 안 함)

```sh
media-ctl -V '"imx219 3-0010":0[fmt:SRGGB10_1X10/1920x1080]'
media-ctl -V '"csis-32e40000.csi":0[fmt:SRGGB10_1X10/1920x1080]'
media-ctl -V '"crossbar":0[fmt:SRGGB10_1X10/1920x1080]'
media-ctl -V '"mxc_isi.0":0[fmt:SRGGB10_1X10/1920x1080]'
v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10
```

entity 이름(`imx219 3-0010` = "드라이버명 I2C버스-주소", `csis-<장치명>`, `crossbar`, `mxc_isi.N`은 랩 소스의 이름 규칙으로 확인)과 pad 번호는 보드·커널 버전에 따라 다르다. 반드시 `media-ctl -p`로 확인한 이름을 쓴다. ISI는 Bayer를 처리하지 못하므로 raw로 받고 debayer는 GPU/소프트웨어가 하거나, i.MX8MP의 ISP(RKISP1 계열 드라이버)를 거친다.

### 10.4 흔한 함정

- 센서 포맷만 바꾸고 수신기 sink는 그대로 둔다 — STREAMON `-EPIPE`. MC 파이프라인은 자동 전파가 **subdev 안에서만**(sink → source) 일어나고 **링크를 건너서는** 일어나지 않는다.
- Bayer 순서를 무시하고 크기만 맞춘다 — `SRGGB10`과 `SGRBG10`은 다른 mbus code다. 센서의 플립이나 crop 시작 위치(홀수 픽셀)를 바꾸면 Bayer 순서가 바뀐다.
- `colorspace`를 신경 안 쓴다 — 대부분 `DEFAULT`면 통과하지만, vimc처럼 colorimetry까지 비교하는 드라이버가 있다(§9.2 2단계에서 센서 colorspace가 0으로 바뀐 것을 보라 — 센서 `set_fmt`가 요청의 colorspace 0을 그대로 받았다).

## 11. Device Tree와 async 등록 — 보드 배선이 그래프가 되기까지

### 11.1 직관 — "누가 누구에게 몇 lane으로 붙었나"를 적는 곳

센서 드라이버는 I2C 버스 드라이버가 probe하고, CSI-2 수신기 드라이버는 플랫폼 버스가 probe한다. 둘의 probe 순서는 정해져 있지 않다(센서는 regulator·clock이 준비 안 돼서 `-EPROBE_DEFER`로 몇 번 미뤄질 수도 있다). 그런데 수신기는 "내 0번 포트에 IMX219가 2 lane, 456 MHz로 붙어 있다"를 알아야 D-PHY를 설정한다. 이 배선 정보가 DT의 **OF graph**(`port`/`endpoint`/`remote-endpoint`)이고, 서로 늦게 오는 드라이버를 짝지어 주는 것이 **v4l2-async**다. Don이 보드 bring-up에서 회로도의 "CAM0_D0_P/N → SoC MIPI_CSI1_D0"를 읽던 일을 DT가 대신 기록한다.

### 11.2 실제 DT — Gateworks GW74xx 보드의 IMX219 overlay (랩 소스)

그림 9 — 위 DT의 그래프. 노드마다 `port`(물리 단자)가 있고 그 안의 `endpoint`가 상대 endpoint를 `remote-endpoint`로 **서로** 가리킨다. 레인 수와 링크 주파수는 endpoint 속성이다.

| 속성 | 위치 | 의미 | 틀리면 |
|---|---|---|---|
| `remote-endpoint` | 양쪽 endpoint | 상대 endpoint의 phandle | async 짝짓기가 안 되어 `/dev/video`가 안 생김 |
| `data-lanes = <1 2>` | 양쪽 | 사용하는 데이터 lane과 논리 순서 | 프레임이 안 오거나 줄무늬·색 깨짐. lane 수 불일치면 수신기 probe 실패 가능 |
| `clock-lanes = <0>` | 센서 쪽 | 클럭 lane 위치 | 대부분 0 고정 |
| `link-frequencies` | 센서 쪽 | 허용된 CSI-2 링크 주파수 목록(64비트) | imx219는 자기 표에 없으면 probe에서 `Link frequency not supported` |
| `clock-noncontinuous` | 센서 쪽 | 클럭 lane을 프레임 사이에 LP로 내리나 | 수신기가 continuous만 지원하면 동기 실패 |
| `port@N`의 `reg` | 수신기 | 포트 번호 = media pad 번호로 매핑되는 경우가 많음 | 링크가 엉뚱한 pad에 생김 |

출력에서 볼 것:

- `link-frequencies`는 `/bits/ 64`라서 셀 두 개(`0`, `0x1b2e0200`)로 저장된다. `0x1b2e0200` = 456,000,000. 커널은 `v4l2_fwnode_endpoint_alloc_parse()`가 이것을 `u64` 배열로 읽는다.
- 센서 endpoint의 `remote-endpoint`는 phandle 2이고, 그것이 정확히 CSI port@0 endpoint의 `phandle`이다. 이것이 "그래프 간선"의 실체다.
- 나쁜 DT는 **경고일 뿐 컴파일은 성공(exit=0)**한다. 부팅하면 async가 짝을 못 찾아 카메라가 조용히 안 나온다. 그래서 DT 리뷰 때 `dtc`·`make dtbs_check` 경고를 0으로 유지하는 것이 중요하다.

### 11.6 흔한 함정

- `data-lanes`를 센서와 수신기에 다르게 적는다 — 어떤 수신기는 자기 쪽 값을, 어떤 센서는 자기 쪽 값을 쓴다. 양쪽을 같게 맞춘다.
- `link-frequencies`를 회로도의 "MIPI 클럭"으로 적는다 — DDR이라 비트레이트의 절반이 링크 주파수다. IMX219 456 MHz = lane당 912 Mbps.
- 센서 노드의 `status`나 overlay 적용을 잊는다 — 수신기는 probe되고 영원히 기다린다. 에러 메시지가 없는 것이 증상이다.
- 센서 전원 순서(VANA/VDIG/VDDL, XCLR 리셋 타이밍)를 데이터시트대로 안 지킨다 — 칩 ID 읽기(`imx219_identify_module`)에서 I2C NACK. H3(clk·regulator)·H4(GPIO) 노트의 영역이다.

## 12. 직접 쓰는 최소 V4L2 캡처 드라이버 — `i5_cam`

### 12.1 설계

| 요구 | 구현 |
|---|---|
| 프레임 생성 | hrtimer(`HRTIMER_MODE_REL_SOFT`, softirq 컨텍스트)를 "프레임 끝 인터럽트"로 쓴다. 콜백이 다음 빈 버퍼를 꺼내 320x240 GREY 그라디언트를 그리고 `vb2_buffer_done()` |
| 버퍼 | `vb2_vmalloc_memops` — CPU가 픽셀을 쓰니까 연속 메모리가 필요 없다 |
| 프레임 카운터 | 매 프레임 `sequence` 증가, 빈 버퍼가 없으면 `dropped++`(sequence는 그래도 증가). 이미지 첫 4바이트에도 카운터 |
| 타임스탬프 | 콜백 진입 직후 `ktime_get_ns()` (`TIMESTAMP_MONOTONIC`) |
| 컨트롤 | `V4L2_CID_BRIGHTNESS`, `V4L2_CID_TEST_PATTERN`(움직임/정지) |
| 포맷 | GREY 320x240 하나. S_FMT/TRY_FMT는 요청을 그것으로 고쳐서 돌려준다 |
| 장치 | 모듈이 스스로 `platform_device`를 하나 만들고 `platform_driver`가 probe (실제 SoC에서는 DT가 만든다) |

잠금 구조: ioctl은 `vdev.lock`(= `q.lock`) 뮤텍스로 직렬화되고, 버퍼 리스트는 타이머(softirq)와 `buf_queue`(프로세스 컨텍스트)가 같이 만지므로 스핀락 + `irqsave`다(F4). 실제 드라이버에서 타이머 자리는 하드웨어 IRQ 핸들러, 그라디언트 그리기 자리는 "다음 버퍼의 DMA 주소를 레지스터에 쓰기"다.

### 12.2 코드 (1/4) — 구조체와 프레임 끝 처리

```c
// SPDX-License-Identifier: GPL-2.0
/* i5_cam — 최소 V4L2 캡처 드라이버: vb2_vmalloc, hrtimer = "frame-end IRQ", 컨트롤 2개 */
#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/hrtimer.h>
#include <media/v4l2-device.h>
#include <media/v4l2-ioctl.h>
#include <media/v4l2-ctrls.h>
#include <media/v4l2-event.h>
#include <media/videobuf2-v4l2.h>
#include <media/videobuf2-vmalloc.h>

#define W 320
#define H 240
static unsigned int fps = 30;
module_param(fps, uint, 0444);

struct i5_buf { struct vb2_v4l2_buffer vb; struct list_head list; };
struct i5_cam {
	struct v4l2_device v4l2;
	struct video_device vdev;
	struct vb2_queue q;
	struct v4l2_ctrl_handler hdl;
	int pat, bright;                /* s_ctrl가 갱신, 타이머가 읽음 */
	struct mutex lock;              /* ioctl 직렬화 (vdev.lock, q.lock) */
	spinlock_t slock;               /* buf 리스트: 타이머(softirq) ↔ buf_queue */
	struct list_head bufs;
	struct hrtimer timer;
	u32 seq, dropped;
};
```

타이머 콜백 = 이 드라이버의 "IRQ 핸들러":

```c
/* ---- "프레임 끝 인터럽트": 다음 버퍼를 채우고 done 처리 ---- */
static enum hrtimer_restart i5_tick(struct hrtimer *t)
{
	struct i5_cam *c = container_of(t, struct i5_cam, timer);
	struct i5_buf *b = NULL;
	unsigned long flags;
	u64 ov, ts = ktime_get_ns();    /* CLOCK_MONOTONIC: 프레임 끝 시각 */

	spin_lock_irqsave(&c->slock, flags);
	if (!list_empty(&c->bufs)) {
		b = list_first_entry(&c->bufs, struct i5_buf, list);
		list_del(&b->list);
	}
	spin_unlock_irqrestore(&c->slock, flags);

	if (b) {
		u8 *p = vb2_plane_vaddr(&b->vb.vb2_buf, 0);
		int x, y, mv = READ_ONCE(c->pat) == 0 ? c->seq * 4 : 0;
		int br = READ_ONCE(c->bright) - 128;

		for (y = 0; y < H; y++)
			for (x = 0; x < W; x++)
				p[y * W + x] = clamp(((x + mv) & 0xff) + br, 0, 255);
		memcpy(p, &c->seq, sizeof(c->seq));   /* 첫 4바이트 = 프레임 카운터 */
		b->vb.vb2_buf.timestamp = ts;
		b->vb.sequence = c->seq;
		b->vb.field = V4L2_FIELD_NONE;
		vb2_set_plane_payload(&b->vb.vb2_buf, 0, W * H);
		vb2_buffer_done(&b->vb.vb2_buf, VB2_BUF_STATE_DONE);
	} else {
		c->dropped++;           /* 빈 버퍼 없음 → 프레임 버림, seq는 그래도 증가 */
	}
	ov = hrtimer_forward_now(t, ns_to_ktime(NSEC_PER_SEC / fps));
	c->dropped += ov - 1;           /* 콜백이 늦어 건너뛴 주기 = 놓친 프레임 */
	c->seq += ov;                   /* 보통 ov == 1 */
	return HRTIMER_RESTART;
}
```

`hrtimer_forward_now()`의 반환값은 "타이머를 몇 주기 앞으로 밀었나"다. 콜백이 늦게 불려서 주기를 건너뛰었으면 2 이상이 되고, 그만큼을 sequence와 dropped에 더한다. 하드웨어 프레임 카운터가 있는 SoC라면 그 레지스터를 읽어 sequence로 쓰는 것이 더 정확하다.

### 12.3 코드 (2/4) — videobuf2 ops

```c
/* ---- videobuf2 ops ---- */
static int i5_queue_setup(struct vb2_queue *q, unsigned int *nbuf, unsigned int *nplanes,
			  unsigned int sizes[], struct device *alloc_devs[])
{
	if (*nplanes)                   /* CREATE_BUFS: 요청 크기 검사 */
		return sizes[0] < W * H ? -EINVAL : 0;
	*nplanes = 1;
	sizes[0] = W * H;
	return 0;
}

static int i5_buf_prepare(struct vb2_buffer *vb)
{
	if (vb2_plane_size(vb, 0) < W * H)
		return -EINVAL;
	return 0;
}

static void i5_buf_queue(struct vb2_buffer *vb)   /* QBUF(스트리밍 중) → 드라이버 소유 */
{
	struct i5_cam *c = vb2_get_drv_priv(vb->vb2_queue);
	struct i5_buf *b = container_of(to_vb2_v4l2_buffer(vb), struct i5_buf, vb);
	unsigned long flags;

	spin_lock_irqsave(&c->slock, flags);
	list_add_tail(&b->list, &c->bufs);
	spin_unlock_irqrestore(&c->slock, flags);
}

static void i5_return_all(struct i5_cam *c, enum vb2_buffer_state st)
{
	struct i5_buf *b, *n;
	unsigned long flags;

	spin_lock_irqsave(&c->slock, flags);
	list_for_each_entry_safe(b, n, &c->bufs, list) {
		list_del(&b->list);
		vb2_buffer_done(&b->vb.vb2_buf, st);
	}
	spin_unlock_irqrestore(&c->slock, flags);
}
```

스트림 시작·정지와 ops 표:

```c
static int i5_start_streaming(struct vb2_queue *q, unsigned int count)
{
	struct i5_cam *c = vb2_get_drv_priv(q);

	c->seq = 0;
	c->dropped = 0;
	hrtimer_start(&c->timer, ns_to_ktime(NSEC_PER_SEC / fps), HRTIMER_MODE_REL_SOFT);
	return 0;
}

static void i5_stop_streaming(struct vb2_queue *q)
{
	struct i5_cam *c = vb2_get_drv_priv(q);

	hrtimer_cancel(&c->timer);      /* 콜백이 끝날 때까지 기다린다 */
	i5_return_all(c, VB2_BUF_STATE_ERROR);
	dev_info(c->v4l2.dev, "stop: frames=%u dropped=%u\n", c->seq, c->dropped);
}

static const struct vb2_ops i5_qops = {
	.queue_setup = i5_queue_setup, .buf_prepare = i5_buf_prepare,
	.buf_queue = i5_buf_queue, .start_streaming = i5_start_streaming,
	.stop_streaming = i5_stop_streaming,
};
```

`start_streaming`에서 `count`는 이미 큐에 있는 버퍼 수다. `min_queued_buffers = 1`로 했으므로 vb2는 버퍼가 최소 1개 들어온 뒤에 이것을 부른다. 실제 DMA 드라이버는 하드웨어의 "섀도 레지스터" 개수(예: 다음 프레임 주소 레지스터 2개)만큼을 `min_queued_buffers`로 둔다. `start_streaming`이 실패하면 받은 버퍼를 `VB2_BUF_STATE_QUEUED`로 돌려줘야 한다는 규칙도 있다(여기서는 실패 경로가 없다).

컨트롤 — `s_ctrl` 하나가 모든 컨트롤 변경을 받는다:

```c
static const char * const i5_patterns[] = { "Moving Gradient", "Static Gradient", NULL };

static int i5_s_ctrl(struct v4l2_ctrl *ctrl)      /* 레지스터 쓰기 자리 */
{
	struct i5_cam *c = container_of(ctrl->handler, struct i5_cam, hdl);

	if (ctrl->id == V4L2_CID_BRIGHTNESS)
		WRITE_ONCE(c->bright, ctrl->val);
	else if (ctrl->id == V4L2_CID_TEST_PATTERN)
		WRITE_ONCE(c->pat, ctrl->val);
	else
		return -EINVAL;
	return 0;
}

static const struct v4l2_ctrl_ops i5_ctrl_ops = { .s_ctrl = i5_s_ctrl };
```

ioctl 표의 절반이 `vb2_ioctl_*` 헬퍼다. 드라이버가 직접 쓰는 것은 "장치가 누구이고 무슨 포맷을 내나"뿐이다. 이것이 I1에서 말한 "직접 char device를 만들지 말고 서브시스템에 등록하라"의 실제 모습이다. G4·G5에서 손으로 짠 `file_operations`·`.mmap`·`.poll`을 `vb2_fop_*`가 대신한다.

### 12.5 코드 (4/4) — probe, remove, 모듈 init

```c
/* ---- probe: v4l2_device → ctrl handler → vb2_queue → video_device 순서 ---- */
static int i5_probe(struct platform_device *pdev)
{
	struct i5_cam *c = devm_kzalloc(&pdev->dev, sizeof(*c), GFP_KERNEL);
	struct vb2_queue *q;
	int ret;

	if (!c)
		return -ENOMEM;
	mutex_init(&c->lock);
	spin_lock_init(&c->slock);
	INIT_LIST_HEAD(&c->bufs);
	hrtimer_setup(&c->timer, i5_tick, CLOCK_MONOTONIC, HRTIMER_MODE_REL_SOFT);

	ret = v4l2_device_register(&pdev->dev, &c->v4l2);
	if (ret)
		return ret;
	v4l2_ctrl_handler_init(&c->hdl, 2);
	v4l2_ctrl_new_std(&c->hdl, &i5_ctrl_ops, V4L2_CID_BRIGHTNESS, 0, 255, 1, 128);
	v4l2_ctrl_new_std_menu_items(&c->hdl, &i5_ctrl_ops, V4L2_CID_TEST_PATTERN,
				     1, 0, 0, i5_patterns);
	if (c->hdl.error) {
		ret = c->hdl.error;
		goto err_hdl;
	}
	v4l2_ctrl_handler_setup(&c->hdl);      /* 기본값을 s_ctrl로 한 번 밀어 넣기 */
	c->v4l2.ctrl_handler = &c->hdl;
```

(probe 이어서) vb2 큐와 video_device 등록:

```c
	q = &c->q;
	q->type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
```

remove와 모듈 init/exit:

```c
static void i5_remove(struct platform_device *pdev)
{
	struct i5_cam *c = platform_get_drvdata(pdev);

	vb2_video_unregister_device(&c->vdev);   /* 스트리밍 중이면 멈추고 해제 */
	v4l2_ctrl_handler_free(&c->hdl);
	v4l2_device_unregister(&c->v4l2);
}

static struct platform_driver i5_drv = {
	.probe = i5_probe, .remove = i5_remove, .driver.name = "i5_cam",
};
static struct platform_device *i5_pdev;

static int __init i5_init(void)
{
	int ret = platform_driver_register(&i5_drv);

	if (ret)
		return ret;
	i5_pdev = platform_device_register_simple("i5_cam", -1, NULL, 0);
	if (IS_ERR(i5_pdev)) {
		platform_driver_unregister(&i5_drv);
		return PTR_ERR(i5_pdev);
	}
	return 0;
}

static void __exit i5_exit(void)
{
	platform_device_unregister(i5_pdev);
	platform_driver_unregister(&i5_drv);
}
module_init(i5_init);
module_exit(i5_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("I5 minimal V4L2 capture driver");
```

등록 순서(v4l2_device → 컨트롤 → vb2 큐 → video_device)는 순서가 의미가 있다. `video_register_device()`가 성공하는 순간 udev가 `/dev/video0`을 만들고 유저가 열 수 있으므로 **그 전에 모든 것이 준비되어 있어야 한다.** 해제는 역순이고, `vb2_video_unregister_device()`는 스트리밍 중인 큐를 멈추고 버퍼를 정리한 뒤 노드를 내린다.

## 13. libcamera — 복잡한 카메라의 현대적 유저 공간 (실행 안 함, 개념)

MC 파이프라인을 앱마다 media-ctl 스크립트로 설정하는 것은 유지보수가 안 된다. 더 근본적으로, ISP가 있는 SoC에서 좋은 영상을 얻으려면 매 프레임 **3A**(자동 노출·화이트밸런스·포커스) 루프가 ISP 통계(별도 video 노드로 나오는 metadata 버퍼)를 읽고 센서 노출·게인 컨트롤과 ISP 파라미터 버퍼를 갱신해야 한다. 이것을 커널에 넣지 않는 것이 Linux의 결정이고, 그 일을 하는 유저 공간 라이브러리가 **libcamera**다. 이 VM과 게스트에는 libcamera가 없어 실행하지 않았다.

| 구성 요소 | 역할 |
|---|---|
| pipeline handler | SoC별 C++ 코드. media 그래프를 찾고 링크·subdev 포맷을 설정하고 video 노드들의 버퍼를 돌린다 (예: rkisp1, imx8-isi, rpi/vc4, simple) |
| IPA 모듈 | 3A 알고리즘. 통계를 받아 컨트롤 값을 계산 (샌드박스로 분리 가능) |
| 센서 데이터베이스 · 튜닝 파일 | 센서별 블랭킹·크롭 특성, 색 보정 행렬 등 |
| 앱 API | `CameraManager` → `Camera` → `configure()` → `Request`(버퍼 + 컨트롤 묶음)를 큐에 넣고 완료 받기 |
| 도구 · 연동 | `cam`(CLI), `qcam`, GStreamer `libcamerasrc`, V4L2 호환 레이어 |

V4L2 개념과의 대응: libcamera의 `Request`는 "버퍼 + 그 프레임에 적용할 컨트롤"의 묶음인데, 이것이 커널 쪽 **Request API**(`MEDIA_IOC_REQUEST_ALLOC`, 버퍼와 컨트롤을 원자적으로 묶는 기능 — 주로 stateless 코덱이 쓴다)와 같은 발상이다. 실무에서 Jetson은 NVIDIA의 자체 스택(Argus)을, i.MX8MP·Rockchip·Raspberry Pi는 libcamera를 쓰는 경우가 많다. 로봇 회사에서는 "ROS 2 노드가 libcamera 또는 V4L2 MMAP/DMABUF로 프레임을 받는다"가 흔한 구성이다(Q6).

명령 예(기억 기반, 실행 안 함): `cam -l`(카메라 목록), `cam -c 1 --capture=10 --file=frame-#.bin`, `gst-launch-1.0 libcamerasrc ! video/x-raw,width=1280,height=720 ! fakesink`.

- `vb2_buffer_done()` → 인터럽트 컨텍스트에서 불러도 된다(스핀락만 쓴다). F6의 top half에서 곧바로 부르는 이유.
- `vb2_dma_contig` 할당 → `dma_alloc_attrs()` → CMA(F10 §8.2). `REQBUFS`가 곧 "CMA에서 N × sizeimage 할당"이다.
- `EXPBUF`/DMABUF import → H9 §11의 `dma_buf_export()`/`dma_buf_attach()`/`dma_buf_map_attachment()`.
- 센서 subdev → H5의 `i2c_driver` + (최신 센서 드라이버는) `v4l2-cci`(`cci_write()`, regmap 기반, H2).
- async notifier → G3의 probe 순서·`-EPROBE_DEFER`, D4의 phandle 그래프.
- subdev state 잠금(`sd->state_lock`, `v4l2_subdev_lock_and_get_active_state()`) → F4의 뮤텍스. 컨트롤 핸들러 잠금과 같은 뮤텍스를 쓰게 하는 관례(imx219의 `state_lock = ctrl_handler.lock`)가 있다.

## 15. Embedded 실무에서 다시 보기

### 15.1 "새 MIPI 센서를 보드에 올린다" — 순서

1. **HW 확인**: 회로도에서 lane 수·lane 매핑·클럭 소스(24 MHz XCLK)·전원 레일·리셋/파워다운 GPIO·I2C 버스와 주소. 커넥터·FPC 방향.
2. **I2C로 칩 ID**: 전원 시퀀스를 맞춘 뒤 `i2ctransfer -y 3 w2@0x10 0x00 0x00 r2`(IMX219 칩 ID 레지스터 0x0000, 기억 기반) 같은 명령으로 응답 확인. 여기서 NACK면 전원·리셋·클럭 문제다.
3. **드라이버 선택**: 메인라인에 있으면(`drivers/media/i2c/`) 그것, 없으면 벤더 드라이버를 6.x API(state, `enable_streams`, `v4l2-cci`)로 포팅.
4. **DT**: 센서 노드(`compatible`, `reg`, `clocks`, supplies, GPIO) + endpoint(`data-lanes`, `link-frequencies`) + 수신기 port@0 endpoint, 양방향 `remote-endpoint`. `dtbs_check` 경고 0.
5. **부팅 확인**: dmesg에 probe 메시지, `media-ctl -p`에 센서 entity와 링크, `/dev/v4l-subdevN` 등장. 안 보이면 async pending과 `-EPROBE_DEFER`.
6. **포맷 맞추고 스트리밍**: `media-ctl -V`로 파이프라인 전체, `v4l2-ctl --stream-mmap`. `-EPIPE`면 §9.3 방식으로 링크별 비교.
7. **테스트 패턴 먼저**: 센서 `V4L2_CID_TEST_PATTERN`으로 컬러바를 받아 바이트 검증(§5.3). 패턴이 깨지면 lane·링크 주파수·Bayer 순서·수신기 D-PHY 설정(HS settle) 문제, 패턴은 되는데 실영상만 이상하면 노출·ISP 튜닝 문제로 나뉜다.
8. **수신기 에러 카운터**: CSI-2 ECC·CRC 에러, FIFO overflow 인터럽트 수를 본다(드라이버의 `log_status`나 debugfs). 링크 마진은 여기서 드러난다.
9. **성능**: fps·타임스탬프 간격·sequence 틈을 장시간 측정(§6·§7 프로그램을 그대로). 4대 동시일 때 메모리 대역폭과 CMA 크기.
10. **상위 스택 연결**: libcamera pipeline handler·IPA 튜닝, 또는 GStreamer/ROS 2 노드.

### 15.2 4대 카메라에서 프레임이 가끔 빠진다

- 먼저 **어디서** 빠지는지 나눈다. 앱이 본 sequence 틈(소비자가 늦음) vs 드라이버 에러 카운터(수신기 overflow, CSI CRC) vs 센서 자체(프레임 카운터가 임베디드 데이터에 있으면 그것).
- 소비자 문제면 §7처럼 버퍼 수·소비 스레드 우선순위(SCHED_FIFO, N1)·복사 제거(DMABUF, §8)로 해결.
- 수신기 overflow면 메모리 대역폭(다른 DMA 마스터와 경합 — QoS·interconnect 설정), CPU 개입 없는 ping-pong 버퍼 설계를 본다.

### 15.3 센서 퓨전 타임스탬프

IMU(IIO, I2)는 샘플 시각을 `CLOCK_MONOTONIC`(또는 boottime)으로, 카메라는 `V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC`으로 준다. 같은 시간축이니 바로 정렬할 수 있다. 다만 카메라 타임스탬프는 **어느 시점**인지(SOE/EOF, 노출 중심이 아니다)를 알아야 한다. 롤링 셔터 센서에서 "노출 중심 시각 = SOE − (노출 시간 / 2) + (줄 번호 × 라인 시간)" 같은 보정을 하려면 드라이버의 타임스탬프 정의가 정확해야 한다. 멀티 카메라 HW 트리거·PTP는 Q3에서 다룬다.

### 15.4 GStreamer·OpenCV 앱 쪽에서 본 같은 개념 (기억 기반, 실행 안 함)

```sh
gst-launch-1.0 v4l2src device=/dev/video0 io-mode=dmabuf ! video/x-raw,format=NV12,width=1920,height=1080,framerate=30/1 ! v4l2h264enc ! fakesink
```

`io-mode=dmabuf`가 §8의 EXPBUF 경로이고, 인코더 쪽(`v4l2h264enc`)이 `output-io-mode=dmabuf-import`이면 zero-copy가 된다. OpenCV `VideoCapture`(V4L2 백엔드)는 MMAP + 복사다.

| 쓰지 않는 video 노드가 같은 센서에 붙어 있음 | 포맷을 다 맞췄는데도 `-EPIPE` | 켜진 링크로 연결된 모든 entity가 파이프라인에 들어간다 | 그 노드 포맷도 맞추거나 링크를 끈다 (§9.2 2단계) |
| `S_FMT` 반환값 무시 | 이미지가 비스듬히 밀리거나 색이 깨짐 | 드라이버가 크기·stride·포맷을 고쳐서 돌려줌 | 돌려받은 `bytesperline`·`pixelformat` 사용 |
| QBUF한 버퍼를 계속 읽음 | 찢어진 프레임 | DMA가 덮어쓰는 중 | DQBUF ~ QBUF 사이에서만 접근 |
| 버퍼 2~3개 | 주기적 프레임 손실 | 소비자 순간 멈춤을 흡수 못 함 | 최악 멈춤 / 프레임 주기 + 2개 이상 (§7.3) |
| 드라이버가 드롭 시 sequence를 안 올림 | 앱이 손실을 모름 | 빈 버퍼 없을 때 카운터 정지 | 프레임마다 무조건 sequence++ |
| bottom half에서 타임스탬프 | 프레임 간격 jitter 수 ms | 스케줄링 지연 | ISR에서 `ktime_get_ns()` |
| `stop_streaming`에서 버퍼를 안 돌려줌 | STREAMOFF 때 vb2 WARN, 다음 스트리밍 hang | ACTIVE 버퍼가 드라이버에 남음 | 모든 버퍼 `vb2_buffer_done(..., ERROR)` |
| vmalloc 버퍼를 dma-contig 장치에 import | QBUF `-EFAULT`, `contiguous chunk is too small` | importer가 연속 메모리 필요 | 제약 큰 쪽(CMA, dma-heap)에서 할당 (§8.3) |
| DT `remote-endpoint` 단방향/오타 | 에러 없이 카메라가 안 보임 | async 짝짓기 실패 | `dtc` graph 경고 0, `v4l2-async/pending_async_subdevices` 확인 |
| `link-frequencies`를 비트레이트로 적음 | 센서 probe 실패 또는 수신기 동기 실패 | DDR: 링크 주파수 = 비트레이트/2 | 데이터시트의 PLL 설정과 맞춘 값 |

## 17. 면접에서 이렇게 말한다

**Q.** You need to bring up a new MIPI CSI-2 camera sensor on an embedded Linux board. Walk me through the steps.

**A.** 하드웨어부터 아래에서 위로 간다. 회로도로 레인·클럭·전원·리셋·I2C 주소를 확인하고, 전원 시퀀스를 맞춰 I2C로 칩 ID를 읽는다. 드라이버는 메인라인 subdev 드라이버를 쓰거나 6.x API로 포팅하고, DT에 센서 노드와 endpoint(`data-lanes`, `link-frequencies`, 양방향 `remote-endpoint`)를 쓴다. 부팅 후 `media-ctl -p`로 그래프에 센서가 붙었는지 보고, 파이프라인 포맷을 맞춘 뒤 센서 테스트 패턴으로 바이트 단위 검증을 한다. 그다음 실영상, 수신기 에러 카운터, fps·타임스탬프·드롭 장시간 측정, 마지막으로 libcamera나 GStreamer 연동이다.

> I go bottom-up. First the hardware: lanes, lane mapping, the 24 MHz clock, power rails and their sequence, reset GPIO, and the I2C address, then I read the chip ID over I2C to prove power and clocks. Then the driver: a mainline V4L2 subdev driver if one exists, otherwise I port the vendor one to the current subdev state and enable_streams APIs. In the device tree I add the sensor node and the endpoint with data-lanes and link-frequencies, and a bidirectional remote-endpoint to the CSI-2 receiver port, and keep dtbs_check clean. After boot I check media-ctl -p for the sensor entity and links; if it's missing I look at v4l2-async pending subdevices and probe deferral. Then I configure formats along the pipeline from the sensor downstream, stream the sensor's test pattern and verify the bytes, which isolates lane and Bayer-order problems from image-quality problems. Finally I run long captures measuring frame intervals, sequence gaps and receiver error counters, and hand it to libcamera or GStreamer.

**꼬리 질문**: "테스트 패턴은 정상인데 실영상만 녹색 기운이 돈다면?" → Bayer 순서나 플립 후 mbus code, 또는 ISP 화이트밸런스·튜닝 문제. 링크는 정상이다.

**Q.** What is the difference between a video node and a subdev node, and why does a modern SoC camera have both?

**A.** video node(`/dev/videoN`)는 메모리 버퍼를 다루는 DMA 끝단이고 vb2 큐와 pixel format(fourcc)을 가진다. subdev node(`/dev/v4l-subdevN`)는 센서·수신기·ISP 같은 처리 블록이고 pad별 media bus 포맷과 컨트롤을 가진다. SoC 파이프라인은 조합이 많아서 드라이버가 혼자 결정할 수 없으니, media controller로 그래프를 노출하고 유저가 블록마다 포맷을 정하게 한다.

> A video node is the DMA endpoint: it owns a videobuf2 queue and a memory pixel format with stride. A subdev node represents a processing block, a sensor, CSI-2 receiver, ISP or scaler, with per-pad media bus formats and its own controls. On a complex SoC the routing and per-block formats have too many valid combinations for the driver to pick, so the media controller exposes the graph and user space, or libcamera, configures each block and enables links. Link validation at stream-on checks that both ends of every enabled link agree.

**Q.** STREAMON returns EPIPE. How do you debug it?

**A.** EPIPE는 link validation 실패다. 켜진 링크의 양끝 포맷(크기, mbus code, field)이 다른 곳을 찾는다. `media-ctl -p`로 pad 포맷을 나란히 비교하고, dynamic debug로 `v4l2-subdev.c`와 `mc-entity.c`를 켜면 어느 링크가 어떤 값으로 실패했는지 그대로 나온다. 내가 vimc로 재현했을 때 두 번째 원인은 내가 스트리밍하지 않는 raw 캡처 노드였다 — 같은 센서에 켜진 링크로 붙어 있어서 파이프라인에 포함됐다.

> EPIPE from STREAMON means link validation failed somewhere in the pipeline. I compare pad formats with media-ctl -p and enable dynamic debug for v4l2-subdev.c and mc-entity.c, which logs the exact link and the mismatching width, height or media bus code. One gotcha I reproduced on vimc: after fixing the sensor-to-debayer link it still failed, because a raw capture node I wasn't using was attached to the same sensor pad through an enabled immutable link, so it was part of the pipeline and its pixel format didn't match the sensor's Bayer code.

**Q.** Explain the videobuf2 buffer lifecycle and who owns the buffer in each state.

**A.** REQBUFS로 할당된 버퍼는 DEQUEUED(유저 소유)다. QBUF하면 QUEUED(vb2 소유), 스트리밍 중이면 드라이버의 `buf_queue`로 넘어가 ACTIVE(드라이버·DMA 소유), 프레임 끝 IRQ에서 `vb2_buffer_done`으로 DONE, DQBUF로 다시 유저에게 온다. STREAMOFF 때 드라이버는 갖고 있던 버퍼를 ERROR로 전부 돌려줘야 한다. SSD의 디스크립터 링 소유권과 같은 개념이다.

> After REQBUFS a buffer is dequeued and belongs to user space. QBUF moves it to queued, owned by vb2; once streaming, vb2 hands it to the driver's buf_queue and it becomes active, owned by the driver and the DMA engine. The frame-end interrupt calls vb2_buffer_done, which puts it on the done list with timestamp and sequence filled in, and DQBUF returns it to user space. On stop_streaming the driver must return every buffer it holds in the error state. User space may only touch the memory between DQBUF and the next QBUF. It's the same ownership model as an NVMe submission and completion ring.

**Q.** How do you detect dropped frames, and how many buffers do you allocate?

**A.** sequence 필드의 틈을 센다. 드라이버는 빈 버퍼가 없어 프레임을 버려도 sequence를 올려야 한다. 버퍼 수는 평균 속도가 아니라 소비자의 최악 멈춤으로 정한다. 내 측정에서 30 fps에 250 ms 멈추는 소비자는 버퍼 8개부터 손실 0이었고, 평균적으로 느린 소비자는 버퍼를 늘려도 정확히 속도 차만큼 잃었다.

> I count gaps in the sequence field; a correct driver increments sequence even when it has no buffer and drops the frame. Buffer count comes from the worst-case consumer stall, not the average rate: in my measurement at 30 fps with a consumer that stalls 250 ms every ten frames, losses went 30, 20, 10, then zero at eight buffers. If the consumer is slower on average, no buffer count helps; you lose exactly the rate difference, so you fix the consumer or drop to the latest frame deliberately. More buffers also mean more CMA and more latency.

**Q.** How would you pass camera frames to a hardware encoder without copying?

**A.** VIDIOC_EXPBUF로 캡처 버퍼를 dma-buf fd로 내보내고 인코더의 OUTPUT 큐를 `V4L2_MEMORY_DMABUF`로 열어 fd를 QBUF한다. 인코더가 다 읽고 DQBUF된 뒤에 카메라 큐에 돌려준다. 조건은 버퍼가 importer의 DMA 제약을 만족하는 것이다. vimc/vivid로 해 보니 vmalloc 버퍼를 연속 메모리가 필요한 장치에 넣으면 `contiguous chunk is too small`로 실패했다. 그래서 CMA나 dma-heap에서, 가장 제약이 큰 장치 기준으로 할당한다.

> Export the capture buffers with VIDIOC_EXPBUF to get dma-buf file descriptors, open the encoder's output queue with V4L2_MEMORY_DMABUF, and queue the fd. The importer attaches and maps the buffer for its own device, so no CPU copy happens. Only requeue the buffer to the camera after the encoder has dequeued it. The buffer must satisfy the importer's DMA constraints: I reproduced a vmalloc-backed buffer being rejected by a dma-contig importer with "contiguous chunk is too small", so in practice you allocate from CMA or a dma-heap sized for the most constrained device, and use DMA_BUF_IOCTL_SYNC if the CPU also touches it.

**Q.** What do data-lanes and link-frequencies in the device tree do, and how does the receiver find the sensor?

**A.** endpoint 속성이다. `data-lanes`는 쓰는 레인과 순서, `link-frequencies`는 허용되는 CSI-2 링크 주파수(DDR이라 레인당 비트레이트의 절반)다. 센서 드라이버는 `v4l2_fwnode_endpoint_alloc_parse()`로 읽어 자기 모드 표와 맞는지 검사하고, 수신기는 자기 endpoint의 remote를 `v4l2_async_nf_add_fwnode_remote()`로 notifier에 등록해 센서 subdev가 등록되기를 기다린다. 짝이 맞으면 `.bound`에서 링크를 만들고, 전부 모이면 `.complete`에서 subdev 노드를 만든다.

> They're endpoint properties in the OF graph. data-lanes lists which lanes are used and their order; link-frequencies lists the allowed CSI-2 link frequencies, which is half the per-lane bit rate because it's DDR. The sensor driver parses them with v4l2_fwnode_endpoint_alloc_parse and rejects unsupported values in probe. The receiver adds its endpoint's remote to a v4l2-async notifier, so whichever driver probes first, the async core matches the sensor subdev by fwnode, calls bound, where the receiver creates the media link, and when everything is present calls complete, which registers the subdev device nodes.

**Q.** Why is libcamera needed if V4L2 already exists?

**A.** V4L2는 하드웨어 블록을 노출할 뿐 "좋은 영상"을 만들지 않는다. ISP가 있는 SoC는 매 프레임 통계를 읽고 노출·게인·화이트밸런스와 ISP 파라미터를 바꾸는 3A 루프와, SoC마다 다른 그래프 설정이 필요하다. 그것을 커널에 넣지 않고 유저 공간의 pipeline handler와 IPA로 표준화한 것이 libcamera다.

> V4L2 exposes the hardware blocks but doesn't produce a good image by itself. With an ISP you need a per-frame 3A loop that reads statistics buffers and programs sensor exposure and gain plus ISP parameter buffers, and every SoC has a different media graph to configure. The kernel community keeps that policy in user space; libcamera standardizes it with per-SoC pipeline handlers and image processing algorithm modules, and gives apps one API plus GStreamer and V4L2-compatibility layers.

## 20. 요약 & 체크리스트

SoC 카메라는 센서(I2C 제어 + MIPI CSI-2 데이터) → CSI-2 수신기 → ISP → 스케일러/DMA → DRAM의 파이프라인이고, Linux는 이것을 media controller 그래프로 모델링한다. 블록은 `v4l2_subdev`(`/dev/v4l-subdevN`, pad별 media bus 포맷), 메모리 끝단은 `video_device`(`/dev/videoN`, fourcc + videobuf2 큐), 전체는 `media_device`(`/dev/mediaN`)다. MC 드라이버에서는 유저가 센서부터 하류로 subdev 포맷을 맞추고 링크를 켜야 하며, STREAMON 때 켜진 링크 전부(쓰지 않는 노드까지)가 검증되어 하나라도 다르면 `-EPIPE`다(vimc로 재현, dyndbg로 원인 확인). videobuf2는 DEQUEUED → QUEUED → ACTIVE → DONE의 소유권 링이고, 드라이버는 프레임마다 `CLOCK_MONOTONIC` 타임스탬프와 sequence를 기록해야 한다. 측정으로 보면 평균적으로 느린 소비자는 버퍼 수와 무관하게 속도 차만큼 프레임을 잃고(100 ms 소비자: 60장 받는 동안 111~112장 손실), 순간 멈춤은 버퍼로 흡수된다(250 ms 멈춤 → 8개부터 손실 0). `VIDIOC_EXPBUF` + `V4L2_MEMORY_DMABUF`로 복사 없이 다른 장치에 넘길 수 있지만, importer의 DMA 제약(연속성)을 만족해야 한다(vmalloc → dma-contig 실패 재현). 보드 배선은 DT OF graph(`data-lanes`, `link-frequencies`, 양방향 `remote-endpoint`)로 적고, v4l2-async가 probe 순서와 무관하게 센서와 수신기를 짝짓는다. 최소 캡처 드라이버는 `vb2_ops` 다섯 개, 포맷 ioctl 몇 개, 컨트롤 핸들러, 등록 순서만 지키면 300줄로 된다.

- [ ] SoC 카메라 HW 블록과 Linux 객체(`v4l2_device`, `video_device`, `v4l2_subdev`, `media_device`, entity/pad/link)를 짝지어 그릴 수 있다
- [ ] video-centric과 MC-centric 드라이버의 차이와 `V4L2_CAP_IO_MC`의 의미를 설명할 수 있다
- [ ] fourcc와 media bus code의 차이를 예로 설명할 수 있다
- [ ] QUERYCAP → S_FMT → REQBUFS → mmap → QBUF → STREAMON → DQBUF 루프를 C로 짤 수 있다
- [ ] vb2 버퍼 상태와 각 상태의 소유자를 말하고, `stop_streaming`이 해야 할 일을 안다
- [ ] sequence 틈으로 드롭을 세고, 필요한 버퍼 수를 최악 멈춤 시간으로 계산할 수 있다
- [ ] 타임스탬프의 클럭과 SOE/EOF 의미를 확인해야 하는 이유를 말할 수 있다
- [ ] `MEDIA_IOC_G_TOPOLOGY`로 그래프를 읽고 `SETUP_LINK`·`VIDIOC_SUBDEV_S_FMT`로 파이프라인을 설정할 수 있다
- [ ] STREAMON `-EPIPE`를 dyndbg와 pad 포맷 비교로 원인 추적할 수 있다
- [ ] EXPBUF/DMABUF zero-copy 흐름과 importer 제약을 설명할 수 있다
- [ ] DT endpoint 속성과 v4l2-async(bound/complete) 흐름을 imx219·imx-mipi-csis 코드로 설명할 수 있다
- [ ] 새 MIPI 센서 bring-up 순서를 하드웨어부터 libcamera까지 말할 수 있다
