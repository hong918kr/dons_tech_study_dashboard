# I10. CAN 서브시스템 — SocketCAN, can_dev, 비트레이트·에러 상태·bus-off, CAN FD, 컨트롤러 드라이버

> **이 노트를 다 읽으면**: CAN 컨트롤러가 Linux에서 `can0` 네트워크 인터페이스가 되는 전 경로(소켓 → af_can → can_dev → 드라이버 → 컨트롤러)를 그릴 수 있다 · `ip -details`가 보여 주는 tq/prop-seg/phase-seg/sjw를 손으로 다시 계산할 수 있다 · TEC/REC와 error-active → warning → passive → bus-off → restart 흐름을 에러 프레임으로 읽고 디버그할 수 있다 · `alloc_candev`, `can_put_echo_skb`, NAPI, `can_change_state`, `can_bus_off`를 쓰는 CAN 드라이버 뼈대를 직접 쓸 수 있다
> **왜 필요한가**: 로봇·모터 컨트롤러·차량 회사의 Embedded Linux 면접에서 "CAN 버스가 계속 bus-off 된다, 어떻게 디버그하나?", "SocketCAN 구조를 설명해 봐라", "M_CAN/FlexCAN 드라이버 bring-up 해 봤나?"는 거의 반드시 나온다
> **Don 기준 난이도**: 비트 타이밍·에러 카운터·인터럽트·메일박스는 이미 아는 HW 지식 / 새로 배울 것은 "CAN이 Linux에서는 net_device"라는 틀, can_dev 헬퍼, echo skb, NAPI, netlink 설정, 에러 프레임 API
> **선행 노트**: A9(소켓, vcan 기초), A10(`ip link ... type can`, candump/cansend), F7(deferred work), H1(MMIO), H6(IRQ), H7(SPI). I6(네트워크 드라이버 — NAPI)과 함께 읽으면 좋다

그림 1 — 로봇의 CAN 버스. Linux SoC 쪽은 앱 → 커널 → 드라이버 → 컨트롤러 IP → 트랜시버, 버스 반대편에는 MCU 노드들이 있다. 양 끝 120 Ω 종단이 필수다.

Don이 bare-metal MCU에서 CAN을 썼다면 구조는 이랬을 것이다: 컨트롤러 레지스터에 비트 타이밍(BRP, TSEG1, TSEG2, SJW)을 쓰고, TX 메일박스에 ID·DLC·데이터를 쓰고 "전송 요청" 비트를 세우고, TX-complete/RX/에러 인터럽트 ISR에서 메일박스를 비우고, 에러 카운터 레지스터(TEC/REC)를 읽어 bus-off면 재초기화. Linux에서도 HW에서 일어나는 일은 **완전히 같다**. 다른 점은 "누가 무엇을 맡느냐"다.

| bare-metal에서 내가 하던 일 | Linux에서 맡는 곳 | 이 노트 절 |
|---|---|---|
| BRP/TSEG 계산해서 레지스터에 쓰기 | `ip link ... bitrate` → can_dev가 계산 → 드라이버 `do_set_bittiming` | 4 |
| TX 메일박스 채우고 전송 요청 | 소켓 `write()` → af_can → qdisc → 드라이버 `ndo_start_xmit` | 2, 7 |
| TX 완료 ISR | 드라이버 IRQ → `can_get_echo_skb` (로컬 루프백까지) | 7 |
| RX ISR에서 메일박스 복사 | 드라이버 IRQ → NAPI poll → `netif_receive_skb` | 7 |
| ID 필터(acceptance filter) | 주로 소켓별 SW 필터 (`CAN_RAW_FILTER`) | 5 |
| TEC/REC 읽고 bus-off 처리 | 드라이버 → `can_change_state`/`can_bus_off` → 에러 프레임, `restart-ms` | 6 |
| 주기 송신 타이머 | `CAN_BCM` (커널 hrtimer) | 5 |

핵심 한 문장: **Linux에서 CAN 컨트롤러는 `/dev` 문자 장치가 아니라 네트워크 인터페이스(`net_device`)다.** 그래서 설정은 `ip`(rtnetlink), 데이터는 소켓(`PF_CAN`), 드라이버는 네트워크 드라이버(`ndo_start_xmit`, NAPI) 모양을 한다. 이 틀을 **SocketCAN**이라고 부른다.

### 0.1 이 노트의 실습 환경

- VM 호스트: Lima `elinux`, `uname -r` = `7.0.0-38-generic` (aarch64). can-utils(candump, cansend, cangen, isotpsend, can-calc-bit-timing …) 설치됨.
- QEMU 게스트: 공용 랩의 `Image-sub` (Linux `6.18.55-sub`, CAN 코어·vcan·vxcan·can-raw/bcm/gw/isotp/j1939가 모듈로 빌드됨). QEMU 10.2.1.
- 실제 컨트롤러 에뮬레이션: QEMU가 **SJA1000 기반 Kvaser PCIcan(`kvaser_pci`)**과 **CTU CAN FD(`ctucan_pci`)**를 흉내 낸다. 랩 커널에는 이 두 드라이버가 꺼져 있어서(`# CONFIG_CAN_SJA1000 is not set`, `# CONFIG_CAN_CTUCANFD_PCI is not set`), 커널 소스의 해당 디렉터리를 **out-of-tree 모듈로 빌드**해서 게스트에 넣었다(3.1절).
- 게스트 initramfs는 BusyBox라 `ip`가 CAN 설정을 모른다. 그래서 VM 호스트의 iproute2 `ip`(6.19)와 can-utils 바이너리를, 필요한 공유 라이브러리(`ldd`로 확인)와 함께 initramfs에 복사했다. 둘 다 aarch64라 그대로 돈다. 노트에 나오는 C 예제는 `gcc -static -Wall -Wextra`로 빌드했고 경고 0개다.
- 마지막으로 **직접 쓴 드라이버 `i10_can`**(7절): 가상 컨트롤러 2개(`i10can0` ↔ `i10can1`)를 서로 연결하고, can_priv 비트 타이밍·echo skb·NAPI RX·TEC/REC 상태 머신·bus-off·restart를 구현했다. QEMU 에뮬레이터가 못 보여 주는 에러 상태를 이것으로 재현한다.

게스트 부팅은 이런 스크립트로 자동화했다. initramfs `/init`이 `LAB_CMD=` 인자의 명령 하나를 실행하고 전원을 끈다.

```sh
# run.sh <guest-script> [qemu args...]
timeout ${TMO:-90} qemu-system-aarch64 -machine virt -cpu cortex-a57 -m 512M -smp 1 -nographic \
  -kernel /var/lab/out/Image-sub -initrd /var/tmp/I10/i.gz "$@" \
  -append "console=ttyAMA0 quiet LAB_CMD=sh~/i10/$S"
```

출력은 모두 실제 실행 결과다. 타임스탬프·카운터 값은 실행마다 조금씩 다르다. 실습 셸 스크립트 안의 `ip`는 색 출력을 끄려고 `ip -c=never`로 감쌌다.

## 1. CAN 프로토콜 — 드라이버를 읽는 데 필요한 만큼만

Don은 타이밍 분석과 버스 디버그를 잘 안다. 그래서 여기서는 "Linux API의 어느 필드가 프로토콜의 어느 부분에 대응하는가"에 초점을 둔다.

### 1.1 버스와 비트: dominant가 이긴다

CAN은 차동 2선 버스다. 논리 0 = **dominant**(트랜시버가 CAN_H/CAN_L을 벌림), 논리 1 = **recessive**(아무도 안 몰면 이 상태). 여러 노드가 동시에 비트를 내면 버스는 **wired-AND**: 한 노드라도 0을 내면 버스는 0이다. 오픈 드레인 I2C SDA와 똑같은 물리다. 모든 노드는 송신하면서 동시에 버스를 읽는다(자기 비트 모니터링).

그림 2 — Classic CAN 데이터 프레임과 중재. 두 노드가 동시에 SOF를 내고 ID를 MSB부터 보낸다. 0x12F를 보내던 노드 B는 b3에서 1(recessive)을 냈는데 버스에서 0을 읽어 중재에 졌다는 것을 알고 즉시 수신자로 바뀐다. 이긴 노드 A의 프레임은 한 비트도 손상되지 않는다(non-destructive arbitration).

- **ID가 곧 우선순위**다. 낮은 ID가 이긴다. 모터 토크 명령에 낮은 ID, 로그·진단에 높은 ID를 주는 이유다.
- 진 노드는 버스가 비면 **자동 재전송**한다. 컨트롤러 HW가 하는 일이라 드라이버는 몰라도 된다(진 횟수는 `arbitration_lost` 통계와 `CAN_ERR_LOSTARB` 에러 프레임으로 보고할 수 있다).
- **RTR** 비트: 원격 요청 프레임. SocketCAN에서는 `CAN_RTR_FLAG`(can_id의 비트 30).
- **IDE** 비트: 1이면 29비트 확장 ID(EFF). SocketCAN에서는 `CAN_EFF_FLAG`(비트 31).
- **DLC** 4비트: 데이터 길이 0..8. (DLC 9..15도 전송 가능하지만 classic에서는 8바이트로 취급. 리눅스는 이 원래 DLC를 `len8_dlc` 필드에 담을 수 있다.)
- **CRC** 15비트 + delimiter, **ACK 슬롯**: 송신자는 recessive를 내고, 프레임을 정상 수신한 **아무 노드라도** 그 비트를 dominant로 덮어쓴다. 아무도 안 덮으면 송신자는 **ACK 에러**. 버스에 노드가 혼자면 ACK가 절대 안 온다 — 6절의 핵심 실험이다.
- **bit stuffing**: SOF~CRC 구간에서 같은 값이 5비트 연속되면 송신자가 반대 비트를 하나 끼운다. 수신자는 6비트 연속을 보면 **stuff error**. 이 덕분에 엣지가 자주 생겨 재동기화가 된다.

프레임 길이 감 잡기(scope로 볼 때 유용): 11비트 ID, 8바이트 데이터 classic 프레임은 stuffing 없이 SOF부터 EOF까지 108비트, 프레임 간 간격(IFS) 3비트를 더하면 111비트다. 500 kbit/s에서 약 222 µs, 최악의 stuffing이면 130비트 이상. **1 Mbit/s 버스 하나에 8바이트 프레임을 초당 최대 약 8000개**밖에 못 싣는다. 모터 8개에 1 kHz 명령 + 1 kHz 상태면 이미 16000 프레임/s라 한 버스로는 안 된다 — 로봇에서 CAN FD나 버스 분리가 나오는 이유다.

### 1.3 에러 검출 5종과 에러 프레임

| 에러 | 누가 검출 | 언제 |
|---|---|---|
| bit error | 송신자 | 내가 낸 비트와 읽은 비트가 다름 (중재 구간·ACK 슬롯 제외) |
| stuff error | 수신자 | 같은 값 6비트 연속 |
| CRC error | 수신자 | 계산한 CRC 불일치 |
| form error | 수신자 | 고정 형식 비트(delimiter, EOF)가 틀림 |
| ACK error | 송신자 | ACK 슬롯이 recessive 그대로 |

에러를 본 노드는 즉시 **에러 플래그**(error-active 노드는 dominant 6비트 — 일부러 stuff 규칙을 깨서 모두가 알게 함, error-passive 노드는 recessive 6비트)를 내고, 프레임은 버려지고 송신자가 재전송한다. 그리고 **에러 카운터**가 움직인다:

- 송신 중 에러: **TEC += 8**. 수신 중 에러: **REC += 1**(일부 경우 +8).
- 성공적 송신: TEC −= 1, 성공적 수신: REC −= 1.
- TEC 또는 REC ≥ 96 → **error-warning**(규격 상태는 아니고 컨트롤러가 주는 경고), ≥ 128 → **error-passive**, TEC ≥ 256 → **bus-off**(버스에서 완전히 손을 뗌).
- 중요 예외(ISO 11898-1): **error-passive 송신자가 ACK 에러를 검출하고 passive 에러 플래그 동안 dominant를 보지 못하면 TEC를 올리지 않는다**. 그래서 "케이블이 빠져 혼자 남은 노드"는 bus-off까지 가지 않고 **error-passive에 머물며 계속 재전송**한다. 반대로 "트랜시버 고장·CAN_H 단락"처럼 bit error가 나면 passive에서도 +8이 계속되어 bus-off로 간다. 6절에서 둘 다 재현한다.

### 1.4 CAN FD 한눈에

CAN FD(Flexible Data-rate)는 같은 버스·같은 중재를 쓰되 두 가지를 바꿨다.

| 항목 | Classic CAN | CAN FD |
|---|---|---|
| 데이터 길이 | 0..8 바이트 | 0..8, 12, 16, 20, 24, 32, 48, 64 바이트 |
| 비트레이트 | 하나 (≤ 1 Mbit/s) | 중재 구간 = nominal (보통 500 k~1 M), 데이터 구간 = data (2~8 Mbit/s) |
| 전환 플래그 | 없음 | **BRS**(Bit Rate Switch) 비트가 1이면 데이터 구간에서 빨라짐 |
| 에러 상태 표시 | 없음 | **ESI**(Error State Indicator): 송신자가 error-passive면 1 |
| CRC | 15비트 | 17/21비트 + stuff count |
| Linux 구조체 | `struct can_frame` (16 B) | `struct canfd_frame` (72 B) |
| MTU | `CAN_MTU` = 16 | `CANFD_MTU` = 72 |

FD 데이터 구간이 짧은 비트(예: 5 Mbit/s = 200 ns)라서, 송신자가 자기 비트를 다시 읽을 때 **트랜시버 루프 지연**(100 ns 이상)이 비트 시간의 큰 부분이 된다. 그래서 FD 컨트롤러에는 **TDC**(Transmitter Delay Compensation)가 있고, Linux에서는 `tdcv`/`tdco`/`tdcf`로 설정한다(`ip link ... tdc-mode auto` 등). 최근에는 CAN XL(2048 바이트, `CANXL_MTU`)도 커널에 들어왔지만 이 노트에서는 다루지 않는다.

### 1.5 흔한 함정

- "CAN은 신뢰성 있으니 프레임이 사라지지 않는다" — 버스 위에서는 재전송되지만, **Linux 안에서는** qdisc 큐(`qlen 10`)가 차면 `ENOBUFS`, 수신 소켓 버퍼가 차면 drop, 컨트롤러 RX FIFO가 넘치면 `CAN_ERR_CRTL_RX_OVERFLOW`로 잃는다.
- ACK는 "목적지가 받았다"가 아니라 "**누군가** 제대로 받았다"는 뜻이다. 목적 노드의 애플리케이션 수신 확인은 상위 프로토콜(CANopen, J1939, ISO-TP)의 몫이다.

| 소켓 | 모듈 | 용도 | 언제 쓰나 |
|---|---|---|---|
| `socket(PF_CAN, SOCK_RAW, CAN_RAW)` | `can_raw` | 프레임 한 개 = `write()` 한 번 | 모터 명령·상태 수신, 대부분의 앱 |
| `socket(PF_CAN, SOCK_DGRAM, CAN_BCM)` | `can_bcm` | 커널이 주기 송신·수신 감시(타임아웃, 내용 변경 감지) | 10 ms heartbeat, 주기 명령 |
| `socket(PF_CAN, SOCK_DGRAM, CAN_ISOTP)` | `can_isotp` | ISO 15765-2: 4095 바이트(FD는 더 큼)까지 분할·재조립, flow control | UDS 진단, 펌웨어 업데이트 |
| `socket(PF_CAN, SOCK_DGRAM, CAN_J1939)` | `can_j1939` | SAE J1939: PGN 주소, 주소 클레임, 전송 프로토콜 | 트럭·농기계·선박 |

A9 노트에서 봤듯 `AF_CAN` 소켓을 처음 열면 커널이 `can-proto-1` 별명으로 `can_raw`를 자동 로드한다.

### 2.2 프레임 구조체 — `can_frame`과 `canfd_frame`

```
struct can_frame (16 bytes)               struct canfd_frame (72 bytes)
off  0: canid_t can_id  (32 bit)           off  0: canid_t can_id
off  4: __u8    len     (0..8)             off  4: __u8    len    (0..64)
off  5: __u8    __pad                      off  5: __u8    flags  (BRS 0x01 ESI 0x02 FDF 0x04)
off  6: __u8    __res0                     off  6: __u8    __res0
off  7: __u8    len8_dlc (9..15 opt.)      off  7: __u8    __res1
off  8: __u8    data[8]  (8-aligned)       off  8: __u8    data[64]

can_id bits:  31 = CAN_EFF_FLAG   30 = CAN_RTR_FLAG   29 = CAN_ERR_FLAG
              28..0 = 29-bit ID (EFF)  or  10..0 = 11-bit ID (SFF)
```

- 앞 8바이트 레이아웃이 같아서, 커널은 `skb->len`(16 vs 72)으로 classic/FD를 구분한다. 유저도 `read()` 반환 크기로 구분한다.
- `can_id`는 **호스트 바이트 순서** 정수다. 버스의 비트 순서는 컨트롤러가 처리한다.
- `CAN_ERR_FLAG`가 선 프레임은 버스에서 온 데이터가 아니라 **드라이버가 만든 에러 보고**다(6절).

### 2.3 로컬 루프백 — echo의 의미

같은 보드의 앱 A가 보낸 프레임을 앱 B(candump 등)도 봐야 한다. 실제 버스에서 송신자는 자기 프레임을 RX로 받지 않으므로(컨트롤러가 걸러 냄) 누군가 루프백해 줘야 한다. SocketCAN 규칙:

- 소켓 옵션 `CAN_RAW_LOOPBACK`(기본 켜짐): 내 프레임을 같은 장치의 다른 소켓에 보여 준다.
- `CAN_RAW_RECV_OWN_MSGS`(기본 꺼짐): 보낸 소켓 자신도 받는다.
- 장치에 `IFF_ECHO` 플래그가 있으면 **드라이버가** 루프백한다: 송신 skb를 보관했다가 **TX 완료 인터럽트가 온 뒤에야** 위로 올린다(`can_put_echo_skb`/`can_get_echo_skb`). 그래서 candump에 보이는 내 송신 프레임의 순서·시각이 "실제로 버스에 나간 순서"와 같다.
- `IFF_ECHO`가 없으면 af_can이 `can_send()` 안에서 즉시 복제해 루프백한다(vcan 기본 동작). 버스에 나갔는지와 무관하다.

7절에서 직접 쓴 드라이버가 `IFF_ECHO`를 빼먹어 큐가 영원히 멈춘 실제 버그를 다룬다.

## 3. 실습 랩 — QEMU에 진짜 CAN 컨트롤러 붙이기

vcan(A9, A10)은 비트 타이밍도 에러 카운터도 없는 순수 SW 루프백이다. 드라이버 쪽을 보려면 "레지스터가 있는 컨트롤러"가 필요하다. QEMU는 CAN 버스 객체와 몇 가지 PCI CAN 카드를 에뮬레이션한다.

```sh
qemu-system-aarch64 -device help 2>/dev/null | grep -i can
qemu-system-aarch64 -object help | grep -i can
```

```text
name "ctucan_pci", bus PCI, desc "CTU CAN PCI"
name "kvaser_pci", bus PCI, desc "Kvaser PCICANx"
name "mioe3680_pci", bus PCI, desc "Mioe3680 PCICANx"
name "pcm3680_pci", bus PCI, desc "Pcm3680i PCICANx"
  can-bus
  can-host-socketcan
```

- `-object can-bus,id=busA`: 가상 버스 하나. 여기에 붙은 컨트롤러끼리 프레임이 오간다.
- `-device kvaser_pci,canbus=busA`: SJA1000 칩 1개짜리 Kvaser PCIcan 카드. SJA1000은 1990년대 NXP(Philips) 독립형 CAN 컨트롤러로, 레지스터 구조가 단순해 교과서 같은 드라이버(`drivers/net/can/sja1000/`)를 갖고 있다.
- `-device ctucan_pci,canbus0=busA,canbus1=busB`: CTU CAN FD IP 코어 2채널. **CAN FD 지원**.
- `-object can-host-socketcan,id=h0,if=i10vc0,canbus=busA`: QEMU 버스를 **VM 호스트의 SocketCAN 인터페이스**(여기서는 vcan)에 연결한다. 게스트의 프레임이 호스트 candump에 보이고, 호스트 cansend가 게스트 컨트롤러에 도착한다.

(작업 중 `can-bus,id=canbus0`처럼 id를 `canbus0`으로 주면 `ctucan_pci`의 속성 이름 `canbus0`과 겹쳐 "Path 'canbus0' does not uniquely identify an object" 에러가 났다. 버스 id는 속성 이름과 다르게 짓는다. 또 `ctucan_pci`는 두 채널 모두 버스에 연결해야 했다 — `canbus1`을 빼면 `ctucan_connect_to_bus failed`.)

그림 4 — 한 비트를 tq(time quantum) 단위로 쪼갠 것. 예: 80 MHz 클럭, brp 1 → tq 12.5 ns, 160 tq = 2 µs = 500 kbit/s. 샘플 포인트는 Phase_Seg1 끝(87.5%).

- **tq** = brp / f_clk. 컨트롤러 클럭을 프리스케일러(brp)로 나눈 최소 시간 단위.
- **Sync_Seg** = 항상 1 tq. 엣지가 여기 오기를 기대한다.
- **Prop_Seg**: 신호가 버스를 왕복하는 지연(트랜시버 루프 + 케이블 전파 × 2)을 흡수한다.
- **Phase_Seg1, Phase_Seg2**: 재동기화 때 늘이고 줄이는 버퍼. 샘플 포인트는 Phase_Seg1과 Phase_Seg2 사이.
- **SJW**(Synchronization Jump Width): 한 번의 재동기화에서 조정할 수 있는 최대 tq 수. 노드 간 클럭 오차를 흡수한다.
- 대부분의 컨트롤러 레지스터에는 TSEG1(= Prop_Seg + Phase_Seg1)과 TSEG2(= Phase_Seg2)만 있다. 커널은 TSEG1을 반으로 나눠 `prop-seg`·`phase-seg1`로 표시할 뿐이다.

공식: **bitrate = f_clk / (brp × (1 + TSEG1 + TSEG2))**, **sample point = (1 + TSEG1) / (1 + TSEG1 + TSEG2)**.

Don이 아는 언어로: 이건 UART 16× 오버샘플링의 일반화다. 다만 CAN은 모든 노드가 같은 비트에 동시에 참여하므로(중재·ACK) 샘플 포인트를 늦게(75~87.5%) 잡아 전파 지연을 흡수한다. 버스가 길수록 Prop_Seg가 커야 하므로 1 Mbit/s는 약 40 m가 한계로 흔히 인용된다.

### 4.2 커널의 계산 알고리즘 (`can_calc_bittiming`)

`ip link set can0 type can bitrate 500000`을 하면 netlink → `can_changelink()` → `can_get_bittiming()` → `can_calc_bittiming()`(`drivers/net/can/dev/calc_bittiming.c`)가 돈다. 요약하면:

1. 샘플 포인트 목표: 유저가 `sample-point`를 안 주면 **CiA 권장값** — bitrate > 800 k면 75.0%, > 500 k면 80.0%, 그 외 87.5%.
2. 가능한 TSEG 총합(`tseg1 + tseg2`)을 **큰 값부터** 내려가며, 각각에 대해 brp = clock / ((1 + tseg) × bitrate)를 구하고 `brp_min..brp_max`에 드는지 본다. → 같은 오차면 **tq가 짧은(해상도 높은) 쪽**이 먼저 뽑힌다.
3. 비트레이트 오차가 가장 작고, 그 다음 샘플 포인트 오차가 가장 작은 조합을 고른다. 샘플 포인트는 목표 **이하** 중에서 고른다.
4. 비트레이트 오차가 0.5%(`CAN_CALC_MAX_ERROR` = 50, 0.1% 단위)를 넘으면 `EINVAL`. 0이 아니면 경고만.
5. TSEG1을 `prop_seg = tseg1 / 2`, `phase_seg1 = 나머지`로 나눈다.
6. SJW를 안 주면 **`max(1, min(phase_seg1, phase_seg2 / 2))`** (6.x 커널 기본값. 옛 커널·can-calc-bit-timing 일부 버전은 SJW 1).

결과는 드라이버의 `do_set_bittiming()`(또는 `ndo_open` 안의 chip start)이 레지스터에 쓴다. 드라이버 작성자가 할 일은 **정확한 `can_bittiming_const`와 `clock.freq`를 주는 것**뿐이다.

### 4.5 예제 5 — 커널 알고리즘을 Python으로 다시 짜서 검산

무엇을 확인하나: 4.2절 알고리즘을 그대로 옮긴 30줄짜리 Python이 커널의 `ip -details` 출력과 같은 답을 내는지. 면접에서 "500 kbit/s, 40 MHz면 BRP·TSEG를 어떻게 잡나?"를 받았을 때 이 순서로 말하면 된다.

```python
# bt_calc.py — the kernel's can_calc_bittiming() in 30 lines of Python, to check "ip -details"
def sp_update(c, spn, tseg):
    best = None
    for i in (0, 1):
        t2 = max(c['t2min'], min(c['t2max'], tseg + 1 - spn * (tseg + 1) // 1000 - i))
        t1 = tseg - t2
        if t1 > c['t1max']:
            t1, t2 = c['t1max'], tseg - c['t1max']
        sp = 1000 * (tseg + 1 - t2) // (tseg + 1)
        if sp <= spn and (best is None or abs(spn - sp) < best[0]):
            best = (abs(spn - sp), sp, t1, t2)
    return best

def calc(c, clk, br):
    spn = 750 if br > 800000 else 800 if br > 500000 else 875     # CiA recommendation
    best = None
    for tseg in range((c['t1max'] + c['t2max']) * 2 + 1, (c['t1min'] + c['t2min']) * 2 - 1, -1):
        tsegall = 1 + tseg // 2
        brp = clk // (tsegall * br) + tseg % 2
        if not c['bmin'] <= brp <= c['bmax']:
            continue
        err = abs(br - clk // (brp * tsegall))
        r = sp_update(c, spn, tseg // 2)
        if r is None: continue
        key = (err, r[0])
        if best is None or key < best[0]:
            best = (key, brp, tseg // 2)
        if key == (0, 0): break
    (_, _), brp, tseg = best
    _, sp, t1, t2 = sp_update(c, spn, tseg)
    prop = t1 // 2
    return dict(brp=brp, tq_ns=brp * 1e9 / clk, prop=prop, ps1=t1 - prop, ps2=t2,
                sjw=max(1, min(t1 - prop, t2 // 2)), sp=sp / 1000, nbt=1 + t1 + t2)

SJA = dict(t1min=1, t1max=16, t2min=1, t2max=8, bmin=1, bmax=64)
MCAN = dict(t1min=2, t1max=256, t2min=2, t2max=128, bmin=1, bmax=512)
for name, c, clk in (("sja1000", SJA, 8000000), ("i10/M_CAN", MCAN, 40000000), ("i10/M_CAN", MCAN, 24000000)):
    for br in (125000, 500000, 1000000):
        r = calc(c, clk, br)
        print(f"{name:9s} clk={clk/1e6:4.0f}MHz br={br:7d}: brp={r['brp']} tq={r['tq_ns']:.2f}ns "
              f"1+{r['prop']}+{r['ps1']}+{r['ps2']}={r['nbt']}tq sjw={r['sjw']} sp={r['sp']:.3f} "
              f"-> {clk/(r['brp']*r['nbt']):.0f} bit/s")
```


### 5.1 예제 6 — RAW 필터: 정확 일치, 범위, EFF, 그리고 함정

무엇을 확인하나: 한 소켓에 필터 여러 개(OR 결합)를 걸었을 때 어떤 ID가 통과하는지. 필터 규칙은 `(received_id & mask) == (filter_id & mask)`이고, `can_id`의 플래그 비트(EFF, RTR)도 마스크 대상이다.

```c
// i10_filt: several CAN_RAW_FILTER entries on one socket, incl. inverted and EFF filters
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <net/if.h>
#include <poll.h>
#include <sys/socket.h>
#include <linux/can.h>
#include <linux/can/raw.h>
#define DIE(m) do { perror(m); exit(1); } while (0)

static int open_can(const char *ifn) {
    int s = socket(PF_CAN, SOCK_RAW, CAN_RAW);
    if (s < 0) DIE("socket");
    struct sockaddr_can a = { .can_family = AF_CAN, .can_ifindex = if_nametoindex(ifn) };
    if (!a.can_ifindex || bind(s, (struct sockaddr *)&a, sizeof a) < 0) DIE("bind");
    return s;
}

int main(int argc, char **argv) {
    const char *ifn = argc > 1 ? argv[1] : "can0";
    int tx = open_can(ifn), rx = open_can(ifn);
    struct can_filter flt[] = {
        { 0x123, CAN_SFF_MASK | CAN_EFF_FLAG | CAN_RTR_FLAG },  /* exactly SFF 0x123, data */
        { 0x200, 0x700 },                                       /* 0x200..0x2FF (SFF or EFF!) */
        { 0x18FF50E5 | CAN_EFF_FLAG, CAN_EFF_MASK | CAN_EFF_FLAG }, /* one J1939 PGN/SA */
    };
    if (setsockopt(rx, SOL_CAN_RAW, CAN_RAW_FILTER, flt, sizeof flt) < 0) DIE("FILTER");
    canid_t ids[] = { 0x123, 0x124, 0x123 | CAN_RTR_FLAG, 0x2AB, 0x7FF, 0x200 | CAN_EFF_FLAG,
                      0x18FF50E5 | CAN_EFF_FLAG, 0x18FF50E6 | CAN_EFF_FLAG };
    for (unsigned i = 0; i < sizeof ids / sizeof ids[0]; i++) {
        struct can_frame f = { .can_id = ids[i], .len = 1, .data = { (unsigned char)i } };
        if (write(tx, &f, sizeof f) != sizeof f) DIE("write");
    }
    struct pollfd p = { .fd = rx, .events = POLLIN };
    while (poll(&p, 1, 300) > 0) {
        struct can_frame f;
        if (read(rx, &f, sizeof f) != sizeof f) DIE("read");
        printf("passed: %s id=%X%s data[0]=%d\n", f.can_id & CAN_EFF_FLAG ? "EFF" : "SFF",
               f.can_id & CAN_EFF_MASK, f.can_id & CAN_RTR_FLAG ? " RTR" : "", f.data[0]);
    }
    return 0;
}
```

```sh
/i10/i10_filt i10can0      # in guest
```

```text

passed: SFF id=2AB data[0]=3
passed: EFF id=200 data[0]=5
passed: EFF id=18FF50E5 data[0]=6
```

출력에서 볼 것:

- 0x123(데이터)은 통과, 0x124와 0x123 RTR은 막혔다. 첫 필터의 마스크에 `CAN_EFF_FLAG | CAN_RTR_FLAG`를 넣었기 때문에 "SFF이고 RTR이 아닌 0x123"만 맞는다.
- `{0x200, 0x700}` 필터는 0x2AB를 통과시켰지만 **EFF 0x200(data 5)도 통과시켰다.** 마스크에 `CAN_EFF_FLAG`가 없으면 29비트 ID의 하위 11비트만 보고 판단한다. 표준 ID만 원하면 마스크에 `CAN_EFF_FLAG`를 꼭 넣자. 실무에서 J1939 장비와 CANopen 장비가 한 버스에 있을 때 이 실수로 엉뚱한 프레임이 섞인다.
- 0x18FF50E5(J1939: 우선순위 6, PGN 0xFF50, 소스 주소 0xE5)는 통과, 소스 주소만 다른 0x18FF50E6은 차단.
- 이 필터는 **소켓별 SW 필터**다. 컨트롤러 HW 필터(메일박스 acceptance mask)는 SocketCAN에서 보통 "모두 받기"로 열어 두고, 커널이 소켓마다 거른다. 그래서 버스 부하가 높으면 필터와 무관하게 CPU가 모든 프레임의 IRQ·skb 비용을 낸다(8절).
- 필터 개수 제한, `CAN_RAW_JOIN_FILTERS`(AND 결합), `CAN_INV_FILTER`(반전)도 있다. `candump` 문법으로는 `can0,123:7FF`(일치), `can0,123~7FF`(반전), `can0,#FFFFFFFF`(에러 마스크).

### 5.3 예제 7 — CAN FD 프레임: `CAN_RAW_FD_FRAMES`, BRS, 크기로 구분

무엇을 확인하나: FD 소켓 옵션을 켜면 한 소켓으로 classic(16 B)과 FD(72 B)를 모두 쓰고 읽을 수 있고, `read()`가 돌려주는 크기로 종류를 안다는 것. 그리고 FD에서 허용되지 않는 길이(13)를 보내면 어떻게 되는지.

```c
// i10_fd: classic vs FD frames on one socket (CAN_RAW_FD_FRAMES), BRS flag, read size = MTU
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <net/if.h>
#include <poll.h>
#include <sys/socket.h>
#include <linux/can.h>
#include <linux/can/raw.h>
#define DIE(m) do { perror(m); exit(1); } while (0)

static int open_fd(const char *ifn) {
    int s = socket(PF_CAN, SOCK_RAW, CAN_RAW), on = 1;
    if (s < 0) DIE("socket");
    if (setsockopt(s, SOL_CAN_RAW, CAN_RAW_FD_FRAMES, &on, sizeof on) < 0) DIE("FD_FRAMES");
    struct sockaddr_can a = { .can_family = AF_CAN, .can_ifindex = if_nametoindex(ifn) };
    if (!a.can_ifindex || bind(s, (struct sockaddr *)&a, sizeof a) < 0) DIE("bind");
    return s;
}

int main(int argc, char **argv) {
    if (argc < 3) { fprintf(stderr, "usage: %s tx_if rx_if\n", argv[0]); return 2; }
    int tx = open_fd(argv[1]), rx = open_fd(argv[2]);
    struct can_frame c = { .can_id = 0x100, .len = 8, .data = "classic" };
    struct canfd_frame f = { .can_id = 0x101, .len = 64, .flags = CANFD_BRS };
    for (int i = 0; i < 64; i++) f.data[i] = (unsigned char)i;
    printf("sizeof can_frame=%zu canfd_frame=%zu (CAN_MTU=%d CANFD_MTU=%d)\n",
           sizeof c, sizeof f, (int)CAN_MTU, (int)CANFD_MTU);
    if (write(tx, &c, CAN_MTU) != CAN_MTU) DIE("write classic");
    if (write(tx, &f, CANFD_MTU) != CANFD_MTU) DIE("write fd");
    f.len = 13;                                        /* invalid FD length -> padded? */
    if (write(tx, &f, CANFD_MTU) != CANFD_MTU) perror("write fd len 13");
    struct pollfd p = { .fd = rx, .events = POLLIN };
    while (poll(&p, 1, 300) > 0) {
        struct canfd_frame r;
        ssize_t nb = read(rx, &r, sizeof r);
        if (nb < 0) DIE("read");
        printf("read %zd bytes -> %s id=%03X len=%d flags=0x%x%s last=%02x\n", nb,
               nb == CANFD_MTU ? "FD" : "classic", r.can_id, r.len, r.flags,
               r.flags & CANFD_BRS ? " (BRS)" : "", r.data[r.len - 1]);
    }
    return 0;
}
```

```text
read 72 bytes -> FD id=101 len=64 flags=0x5 (BRS) last=3f
read 72 bytes -> FD id=101 len=13 flags=0x5 (BRS) last=0c
```

출력에서 볼 것:

- FD 프레임의 flags가 0x5 = `CANFD_BRS`(0x01) + `CANFD_FDF`(0x04). FDF는 CAN XL 도입 이후 커널이 모든 FD 프레임에 세워 주는 "이건 FD다" 표시다.
- len 13 FD 프레임이 **그대로 13으로 도착했다.** 실제 버스에는 DLC 코드(0..15)만 있으므로 13바이트는 존재할 수 없다. 실제 드라이버는 `can_fd_len2dlc(13)` = DLC 10(16바이트)으로 올림해서 보내고, 수신 측은 `can_fd_dlc2len()`으로 16바이트를 받는다(남은 3바이트는 패딩). 내 `i10_can`은 레지스터가 없어서 skb를 그대로 복사하므로 이 변환이 빠졌다 — **가상 드라이버가 실제 HW와 다르게 동작하는 지점**이다. 앱은 FD 길이를 0..8, 12, 16, 20, 24, 32, 48, 64 중에서 쓰자.
- FD를 지원하지 않는 소켓(옵션 off)에 FD 프레임이 오면 그 소켓은 받지 않는다. FD가 꺼진 인터페이스에 72바이트를 쓰면 `EINVAL`.

같은 일을 실제 FD 컨트롤러(CTU CAN FD 두 채널, 같은 QEMU 버스)에서도 했다. cansend의 `##<flags>` 문법이 FD 프레임이다(`##1` = BRS).

### 5.6 예제 10 — BCM 주기 송신과 지터 측정 (10 ms heartbeat)

모터 컨트롤러는 보통 "명령이 N ms 동안 안 오면 정지(watchdog)"하도록 짠다. 그래서 메인 컴퓨터는 명령을 **정확한 주기로** 보내야 한다. 방법 세 가지를 비교했다.

1. **BCM** `TX_SETUP`: 커널 hrtimer가 주기 송신. 프로세스는 잠들어도 된다.
2. 유저 루프 `write()` + `usleep(10000)`: 가장 흔한 초보 코드.
3. 유저 루프 `clock_nanosleep(TIMER_ABSTIME)`: 절대 시각 격자(t0 + i × 10 ms)에 맞춰 깨어남.

```c
// i10_bcm: let the kernel (CAN_BCM, hrtimer) send id 0x0A0 every 10 ms for N seconds
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <net/if.h>
#include <sys/socket.h>
#include <linux/can.h>
#include <linux/can/bcm.h>
#define DIE(m) do { perror(m); exit(1); } while (0)

int main(int argc, char **argv) {
    if (argc < 3) { fprintf(stderr, "usage: %s ifname seconds\n", argv[0]); return 2; }
    int s = socket(PF_CAN, SOCK_DGRAM, CAN_BCM);   /* BCM = SOCK_DGRAM + connect() */
    if (s < 0) DIE("socket");
    struct sockaddr_can a = { .can_family = AF_CAN, .can_ifindex = if_nametoindex(argv[1]) };
    if (!a.can_ifindex || connect(s, (struct sockaddr *)&a, sizeof a) < 0) DIE("connect");
    struct { struct bcm_msg_head h; struct can_frame f[1]; } m;
    memset(&m, 0, sizeof m);
    m.h.opcode = TX_SETUP;
    m.h.flags = SETTIMER | STARTTIMER;
    m.h.can_id = 0x0A0;
    m.h.nframes = 1;
    m.h.count = 0;                                 /* no initial burst: ival2 forever */
    m.h.ival2.tv_usec = 10000;                     /* 10 ms period */
    m.f[0].can_id = 0x0A0;
    m.f[0].len = 8;
    memcpy(m.f[0].data, "\x11\x22\x33\x44\x55\x66\x77\x88", 8);
    if (write(s, &m, sizeof m) != sizeof m) DIE("write TX_SETUP");
    printf("BCM TX_SETUP done: 0x0A0 every 10 ms, process now sleeps\n");
    fflush(stdout);
    sleep(atoi(argv[2]));                          /* zero user-space work while sending */
    m.h.opcode = TX_DELETE;
    if (write(s, &m.h, sizeof m.h) != sizeof m.h) DIE("write TX_DELETE");
    return 0;
}
```

```c
// i10_absloop: phase-locked 10 ms sender — clock_nanosleep(TIMER_ABSTIME) on a fixed grid
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <unistd.h>
#include <net/if.h>
#include <sys/socket.h>
#include <linux/can.h>
#include <linux/can/raw.h>
#define DIE(m) do { perror(m); exit(1); } while (0)

int main(int argc, char **argv) {
    if (argc < 3) { fprintf(stderr, "usage: %s ifname count\n", argv[0]); return 2; }
    int s = socket(PF_CAN, SOCK_RAW, CAN_RAW), n = atoi(argv[2]);
    if (s < 0) DIE("socket");
    struct sockaddr_can a = { .can_family = AF_CAN, .can_ifindex = if_nametoindex(argv[1]) };
    if (!a.can_ifindex || bind(s, (struct sockaddr *)&a, sizeof a) < 0) DIE("bind");
    struct can_frame f = { .can_id = 0x0C0, .len = 8 };
    struct timespec next;
    clock_gettime(CLOCK_MONOTONIC, &next);
    for (int i = 0; i < n; i++) {
        next.tv_nsec += 10000000;                     /* grid: t0 + i * 10 ms */
        if (next.tv_nsec >= 1000000000) { next.tv_nsec -= 1000000000; next.tv_sec++; }
        int e = clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);
        if (e) { fprintf(stderr, "clock_nanosleep: %d\n", e); return 1; }
        f.data[0] = (unsigned char)i;
        if (write(s, &f, sizeof f) != sizeof f) DIE("write");
    }
    return 0;
}
```

```c
// i10_jit: receive N frames of one id, use kernel RX timestamps, print interval stats
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <net/if.h>
#include <sys/socket.h>
#include <linux/can.h>
#include <linux/can/raw.h>
#define DIE(m) do { perror(m); exit(1); } while (0)

int main(int argc, char **argv) {
    if (argc < 4) { fprintf(stderr, "usage: %s ifname id count\n", argv[0]); return 2; }
    int s = socket(PF_CAN, SOCK_RAW, CAN_RAW), n = atoi(argv[3]), on = 1;
    if (s < 0) DIE("socket");
    struct can_filter flt = { strtoul(argv[2], 0, 16), CAN_SFF_MASK | CAN_EFF_FLAG };
    if (setsockopt(s, SOL_CAN_RAW, CAN_RAW_FILTER, &flt, sizeof flt) < 0) DIE("filter");
    if (setsockopt(s, SOL_SOCKET, SO_TIMESTAMPNS, &on, sizeof on) < 0) DIE("TSNS");
    struct sockaddr_can a = { .can_family = AF_CAN, .can_ifindex = if_nametoindex(argv[1]) };
    if (!a.can_ifindex || bind(s, (struct sockaddr *)&a, sizeof a) < 0) DIE("bind");
    double prev = 0;
    for (int i = 0; i < n; i++) {
        struct can_frame f;
        char cbuf[CMSG_SPACE(sizeof(struct timespec))];
        struct iovec iov = { &f, sizeof f };
        struct msghdr mh = { .msg_iov = &iov, .msg_iovlen = 1,
                             .msg_control = cbuf, .msg_controllen = sizeof cbuf };
        if (recvmsg(s, &mh, 0) < 0) DIE("recvmsg");
        struct cmsghdr *c = CMSG_FIRSTHDR(&mh);
        if (!c || c->cmsg_type != SCM_TIMESTAMPNS) { fprintf(stderr, "no ts\n"); return 1; }
        struct timespec ts;
        memcpy(&ts, CMSG_DATA(c), sizeof ts);
        double t = ts.tv_sec * 1e3 + ts.tv_nsec / 1e6;  /* ms */
        if (i) printf("%.3f\n", t - prev);              /* one interval per line */
        prev = t;
    }
    return 0;
}
```

출력에서 볼 것:

- **BCM의 평균이 10 ms보다 길다**(호스트 +0.11 ms, 게스트 +0.79 ms). 소스를 보면 이유가 있다. `bcm_tx_set_expiry()`가 다음 만료를 `ktime_get() + ival`, 즉 **"지금(핸들러가 실제로 돈 시각) + 10 ms"**로 잡는다(`net/can/bcm.c`). 핸들러 지연이 매 주기 누적되어 주기가 늘어난다. 400 프레임 합계 4044 ms vs 4000 ms — 1%의 주기 드리프트다.
- usleep 루프는 같은 누적에 `write()`·스케줄링 지연까지 더해져 평균이 더 길고(게스트 11.7 ms), 꼬리(최대 52 ms)가 길다. watchdog 타임아웃 50 ms짜리 모터 컨트롤러라면 **한 번 멈출 수 있는 수준**이다.
- ABSTIME 루프는 평균이 **정확히 10.000 ms**(합계 4000.1 ms). 늦게 깨어난 다음 주기는 짧아져서(min 3.9 ms) 따라잡는다. 장기 주기는 정확하지만 개별 간격의 지터는 남는다. 모터 제어에는 보통 "평균 주기 정확 + 지터 작게"가 필요하므로, 실무에서는 ABSTIME 루프를 SCHED_FIFO 스레드로 돌리거나(L 모듈), 지터가 큰 일은 MCU 쪽 watchdog 여유로 흡수한다.
- 공용 VM이라 측정 중에 다른 노트의 QEMU 여러 개가 CPU를 쓰고 있었다(load average 약 2.5). 절대값보다 **세 방식의 차이**를 보자. 실제 보드(i.MX8, PREEMPT_RT)에서는 지터가 수십 µs 수준으로 줄어든다(이 노트에서는 측정하지 않음).

그림 6 — CAN 에러 상태 머신. 문턱값은 TEC·REC 중 큰 쪽 기준(bus-off는 TEC만). Linux의 `enum can_state`가 그대로 대응한다: `CAN_STATE_ERROR_ACTIVE`, `ERROR_WARNING`, `ERROR_PASSIVE`, `BUS_OFF`, 그리고 `STOPPED`(인터페이스 down), `SLEEPING`.

커널은 문턱값 판정 헬퍼도 제공한다. `can_state_get_by_berr_counter()`가 TEC·REC를 받아 tx_state·rx_state를 계산하고(내부 `can_state_err_to_state()`: < 96 active, < 128 warning, < 256 passive, 그 외 bus-off), `can_change_state()`가 상태를 바꾸면서 통계(`error_warning`, `error_passive`, `bus_off` 카운터)를 올리고 에러 프레임에 `CAN_ERR_CRTL` 정보를 채운다.

**bus-off 이후**: 규격상 노드는 recessive 11비트를 128번 관찰하면 다시 error-active로 돌아갈 수 있다. 하지만 Linux는 정책을 유저에게 맡긴다.

- `restart-ms 0`(기본): 자동 복구 안 함. `ip link set can0 type can restart`로 수동 재시작하거나 `down`/`up`.
- `restart-ms 100`: 드라이버가 `can_bus_off()`를 부르면 can_dev가 100 ms 뒤 `can_restart()`를 예약한다. `can_restart()`는 남은 echo skb를 버리고(`tx_dropped`), `CAN_ERR_RESTARTED` 에러 프레임을 올리고, 드라이버의 `do_set_mode(dev, CAN_MODE_START)`를 부른다.
- 컨트롤러마다 bus-off 뒤 HW 동작이 다르다. 예를 들어 SJA1000은 bus-off가 되면 HW가 스스로 reset mode로 들어가 멈추고, 드라이버의 `do_set_mode(CAN_MODE_START)`가 `sja1000_start()`로 다시 초기화한다. 드라이버는 이런 HW 동작을 can_dev의 restart 정책에 맞춰 준다 — 새 컨트롤러를 쓸 때는 데이터시트의 bus-off recovery 절과 드라이버의 `do_set_mode`를 함께 읽자.

### 6.2 에러 프레임 형식

드라이버는 에러를 `CAN_ERR_FLAG`가 선 가짜 프레임(`alloc_can_err_skb()`)으로 위에 올린다. 소켓이 받으려면 `CAN_RAW_ERR_FILTER`로 관심 클래스를 켜야 한다(기본 0 = 안 받음).

| `can_id` 비트 | 이름 | 의미 · 데이터 |
|---|---|---|
| 0x001 | `CAN_ERR_TX_TIMEOUT` | 드라이버 TX 타임아웃 |
| 0x002 | `CAN_ERR_LOSTARB` | 중재 패배, `data[0]` = 비트 위치 |
| 0x004 | `CAN_ERR_CRTL` | 컨트롤러 상태, `data[1]` (RX/TX_WARNING 0x04/0x08, RX/TX_PASSIVE 0x10/0x20, ACTIVE 0x40, RX/TX_OVERFLOW 0x01/0x02) |
| 0x008 | `CAN_ERR_PROT` | 프로토콜 위반, `data[2]` 종류(BIT 0x01, FORM 0x02, STUFF 0x04 …), `data[3]` 위치 |
| 0x010 | `CAN_ERR_TRX` | 트랜시버 상태, `data[4]` |
| 0x020 | `CAN_ERR_ACK` | ACK 못 받음 |
| 0x040 | `CAN_ERR_BUSOFF` | bus-off 진입 |
| 0x080 | `CAN_ERR_BUSERROR` | 버스 에러 (berr-reporting 켰을 때, 폭주 가능) |
| 0x100 | `CAN_ERR_RESTARTED` | restart 완료 |
| 0x200 | `CAN_ERR_CNT` | `data[6]` = TEC, `data[7]` = REC 포함 |

`ip link set can0 type can berr-reporting on`을 켜야 개별 버스 에러(BUSERROR)가 올라온다. 기본은 꺼짐이고, 상태가 바뀔 때만 보고한다. 끊어진 버스에서 berr-reporting을 켜면 초당 수천 개 IRQ·에러 프레임이 생길 수 있어서다(필요할 때만 켜는 디버그 옵션).

에러 프레임을 받아 해석하는 프로그램:

```c
// i10_errdump: receive data + error frames on one CAN interface and decode them
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
#include <unistd.h>
#include <net/if.h>
#include <sys/socket.h>
#include <linux/can.h>
#include <linux/can/raw.h>
#include <linux/can/error.h>
#define DIE(m) do { perror(m); exit(1); } while (0)

static const char *ctrl(unsigned char d1) {     /* data[1] = controller status */
    if (d1 & (CAN_ERR_CRTL_TX_PASSIVE | CAN_ERR_CRTL_RX_PASSIVE)) return "PASSIVE";
    if (d1 & (CAN_ERR_CRTL_TX_WARNING | CAN_ERR_CRTL_RX_WARNING)) return "WARNING";
    if (d1 & CAN_ERR_CRTL_ACTIVE) return "back-to-ACTIVE";
    return d1 ? "other" : "-";
}

int main(int argc, char **argv) {
    if (argc < 3) { fprintf(stderr, "usage: %s ifname count\n", argv[0]); return 2; }
    int s = socket(PF_CAN, SOCK_RAW, CAN_RAW), n = atoi(argv[2]);
    if (s < 0) DIE("socket");
    can_err_mask_t em = CAN_ERR_MASK;             /* all error classes */
    if (setsockopt(s, SOL_CAN_RAW, CAN_RAW_ERR_FILTER, &em, sizeof em) < 0) DIE("ERR_FILTER");
    struct sockaddr_can a = { .can_family = AF_CAN, .can_ifindex = if_nametoindex(argv[1]) };
    if (!a.can_ifindex) DIE("if_nametoindex");
    if (bind(s, (struct sockaddr *)&a, sizeof a) < 0) DIE("bind");
    struct timespec t0, t;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    for (int i = 0; i < n; i++) {
        struct can_frame f;
        if (read(s, &f, sizeof f) != sizeof f) DIE("read");
        clock_gettime(CLOCK_MONOTONIC, &t);
        double ms = (t.tv_sec - t0.tv_sec) * 1e3 + (t.tv_nsec - t0.tv_nsec) / 1e6;
        if (!(f.can_id & CAN_ERR_FLAG)) {
            printf("%8.2f ms DATA id=%03X len=%d\n", ms, f.can_id & CAN_EFF_MASK, f.len);
            continue;
        }
        canid_t c = f.can_id;
        printf("%8.2f ms ERR  id=%08X%s%s%s%s%s%s%s ctrl=%s tec=%d rec=%d\n", ms, c,
               c & CAN_ERR_BUSERROR ? " BUSERROR" : "", c & CAN_ERR_ACK ? " NO-ACK" : "",
               c & CAN_ERR_PROT ? (f.data[2] & CAN_ERR_PROT_BIT ? " PROT(bit)" : " PROT") : "",
               c & CAN_ERR_CRTL ? " CRTL" : "", c & CAN_ERR_BUSOFF ? " BUS-OFF" : "",
               c & CAN_ERR_RESTARTED ? " RESTARTED" : "", c & CAN_ERR_CNT ? " CNT" : "",
               ctrl(f.data[1]), f.data[6], f.data[7]);
        fflush(stdout);
    }
    return 0;
}
```

- bus-off가 아닌데 `restart`를 요청하면 `EINVAL`. can_dev는 bus-off 상태에서만 수동 restart를 받는다.

### 6.4 예제 12 — 혼자 남은 노드: ACK 에러 → error-passive에서 멈춤

무엇을 확인하나: 내 드라이버 `i10_can`에 `fault=1`(아무도 ACK 안 함 = 케이블 빠짐, 상대 노드 전원 꺼짐)을 걸고 한 프레임을 보내면, 자동 재전송마다 TEC +8 → 96에서 warning → 128에서 passive → **거기서 멈추는지**(1.3절의 예외 규칙). 그리고 고장을 풀면 TEC가 1씩 내려가며 active로 돌아오는지. 드라이버는 재전송 간격을 관찰하기 쉽게 2 ms로 늦췄다(`retry_us=2000`, 실제 HW는 에러 프레임 + 인터미션 약 20~30비트 후 즉시 재전송).

```sh
# guest: s5.sh 앞부분
insmod /i10/i10_can.ko retry_us=2000
P=/sys/module/i10_can/parameters
for d in i10can0 i10can1; do ip link set $d type can bitrate 500000 restart-ms 100; ip link set $d up; done
st() { ip -details link show i10can0 | grep -o "state.*restart-ms [0-9]*"; }
/i10/i10_errdump i10can0 400 > /tmp/eA.txt & E=$!; sleep 0.3
echo 1 > $P/fault; cansend i10can0 123#01
for i in 1 2 3 4 5 6; do usleep 15000; echo "t+$((i*15))ms: $(st)"; done
sleep 0.3; echo "after 0.4 s: $(st)"
echo 0 > $P/fault; usleep 50000; echo "fault=0 -> $(st)"
cangen i10can0 -g 1 -n 40 -I 200 -L 1; sleep 0.3; echo "after 40 more frames: $(st)"
kill $E; cat /tmp/eA.txt
```

그림 7 — 위 실행의 에러 프레임에서 뽑은 TEC 궤적(실측). 2 ms마다 bit error로 +8, 32번째에 256 = bus-off. restart-ms 100 뒤 TEC 0으로 복귀했지만 고장이 그대로라 다음 프레임에서 같은 계단이 반복된다.

출력에서 볼 것:

- `id=20000288` = FLAG + CNT(0x200) + BUSERROR(0x80) + PROT(0x8), `data[2]` = `CAN_ERR_PROT_BIT`. 96·128을 지날 때는 `+ CRTL(0x4)` = `2000028C`. 마지막은 `200002C8` = `+ BUSOFF(0x40)`. TEC 256은 u8 `data[6]`에 255로 잘려 들어갔다(드라이버의 `min_t(u16, tec, 255)`).
- **error-passive에서도 bit error는 TEC를 올린다**(ACK 에러 예외와 대비). 그래서 물리 고장은 bus-off로 끝난다.
- bus-off 순간 `ip link`가 `NO-CARRIER ... state DOWN`을 보인다. can_dev의 `can_bus_off()`가 `netif_carrier_off()`를 부르기 때문이다. 인터페이스는 여전히 UP(관리 상태)이고 링크만 down이다. `ip monitor link`나 systemd-networkd가 이것을 이벤트로 받을 수 있다.
- 약 100 ms 뒤(`375.64 → 479.75 ms`) `RESTARTED`, TEC 0. dmesg에 `bus-off, scheduling restart in 100 ms`가 6번 — 고장이 있는 동안 **bus-off ↔ restart가 계속 반복**됐다. 통계 줄: `re-started 6, bus-errors 537, error-warn 7, error-pass 7, bus-off 6`(warn/pass가 7인 것은 6.4절 phase A의 1번 포함).
- cangen이 `write: No buffer space available`(ENOBUFS)로 죽었다. bus-off 동안 드라이버 큐가 멈춰 있고 qdisc(`qlen 10`)가 가득 찼기 때문이다. **CAN 앱은 ENOBUFS를 "잠시 후 재시도" 또는 "버스 이상 신호"로 처리해야 한다** — 무시하고 죽는 앱이 흔하다. `TX dropped 6` = restart 때 `can_flush_echo_skb()`가 버린, bus-off 순간 송신 중이던 프레임 6개.
- 이 패턴("restart-ms로 계속 살아났다 죽었다")이 면접 단골 질문 "CAN 버스가 계속 bus-off 된다"의 현장 모습이다. restart-ms는 증상을 가릴 뿐 원인을 고치지 않는다. 디버그 순서는 12절 Q1.

### 6.6 예제 14 — one-shot 모드: 재전송 안 함

무엇을 확인하나: `one-shot on`(`CAN_CTRLMODE_ONE_SHOT`)이면 ACK가 없을 때 컨트롤러가 재전송하지 않고 프레임을 버리는지. 시간 결정성이 중요한 TTCAN류 설계나, "오래된 명령을 늦게 보내느니 버리는 게 낫다"는 제어 루프에서 쓴다.

```sh
insmod /i10/i10_can.ko clock_hz=24000000
ip link set i10can0 type can bitrate 500000 one-shot on; ip link set i10can0 up
echo 1 > /sys/module/i10_can/parameters/fault
cansend i10can0 123#01; sleep 0.2
ip -details link show i10can0 | grep -o "can <.*restart-ms [0-9]*"; ip -s link show i10can0 | tail -2
```

```text
can <ONE-SHOT> state ERROR-ACTIVE (berr-counter tx 8 rx 0) restart-ms 0
    TX:  bytes packets errors dropped carrier collsns           
             0       0      1       1       0       0 
```

출력에서 볼 것: ACK 에러 1번(TEC 8, `errors 1`) 후 프레임을 버렸다(`dropped 1`). 재전송이 없으니 TEC가 8에서 멈췄다. 앱은 프레임이 사라진 것을 알 방법이 echo가 안 오는 것뿐이므로, one-shot을 쓰면 상위 프로토콜에서 응답 확인이 필요하다.

## 7. 드라이버 쓰기 — `i10_can`: can_dev 위의 최소 CAN 컨트롤러 드라이버

이제 드라이버 쪽이다. 실제 HW가 없으니 "버스로 연결된 컨트롤러 두 개"를 소프트웨어로 만든다. vxcan(커널의 가상 CAN 터널 쌍)과 비슷하지만, vxcan과 달리 **can_dev를 제대로 쓴다**: 비트 타이밍 제약·클럭 등록, echo skb로 TX 완료 루프백, NAPI RX, TEC/REC 상태 머신, bus-off와 restart. 실물 드라이버(sja1000.c, m_can.c, flexcan-core.c)를 읽을 때 같은 함수들이 같은 자리에 나온다.

| 실제 드라이버 | `i10_can`의 흉내 |
|---|---|
| `probe()`: MMIO 매핑, 클럭, IRQ 요청, `alloc_candev`, `register_candev` | `module_init`에서 `alloc_candev` × 2, `register_candev` |
| TX 메일박스에 쓰고 "전송 요청" | `hrtimer_start(프레임 길이만큼의 시간)` |
| TX-done IRQ | hrtimer 콜백 `i10_txdone()` (softirq 컨텍스트) |
| RX IRQ → NAPI | 상대 장치의 `rxq`에 skb 넣고 `napi_schedule` |
| 에러 IRQ (TEC/REC 레지스터 읽기) | 모듈 파라미터 `fault`로 고장 주입, 소프트웨어 TEC/REC |

### 7.1 핵심 구조체 — `struct can_priv`를 맨 앞에

`alloc_candev(sizeof(struct my_priv), echo_skb_max)`는 `net_device`와 private 영역을 한 번에 할당한다. can_dev 헬퍼들은 `netdev_priv(dev)`를 `struct can_priv *`로 캐스팅해서 쓰므로 **드라이버 private 구조체의 첫 멤버가 반드시 `struct can_priv`**여야 한다. C 상속 패턴이다(G 모듈의 `container_of` 패턴과 같은 생각).

`struct can_priv`(6.18, `include/linux/can/dev.h`)에서 드라이버가 채우는 필드:

| 필드 | 뜻 | 누가 쓰나 |
|---|---|---|
| `bittiming_const` | 레지스터 비트 폭이 정하는 tseg1/tseg2/sjw/brp 범위 | `can_calc_bittiming()` |
| `fd.data_bittiming_const` | FD 데이터 구간 범위 (6.18에서 `struct data_bittiming_params fd` 안으로 이동) | 같은 함수, `dbitrate` |
| `clock.freq` | CAN 코어 클럭 Hz | 비트 타이밍 계산의 기준 |
| `ctrlmode_supported` | 유저가 켤 수 있는 모드 (`CAN_CTRLMODE_FD`, `ONE_SHOT`, `BERR_REPORTING`, `LOOPBACK`, `LISTENONLY`, `3_SAMPLES`, `CC_LEN8_DLC` …) | netlink `ip ... fd on` 등 |
| `do_set_bittiming` | 계산된 `priv->bittiming`을 레지스터에 쓰기 (없으면 `ndo_open`에서 써도 됨) | netlink 설정 시 |
| `do_set_mode` | `CAN_MODE_START`: bus-off 후 재시작 | `can_restart()` |
| `do_get_berr_counter` | TEC/REC 읽기 | `ip -details`, 에러 처리 |
| `do_get_state` | HW 상태를 직접 읽어 보고 (선택) | `ip -details` |
| `bitrate_max`, `termination_const` | 트랜시버 한계, 종단 저항 스위치 | netlink 검증 |
| `state`, `restart_ms`, `echo_skb` | can_dev가 관리 (드라이버는 `state`를 갱신) | — |

### 7.2 코드 (1/6) — private 구조체, 비트 타이밍 상수, 모드·카운터 콜백

```c
// i10_can.c (1/6) — virtual CAN controller pair: i10can0 <-> i10can1
#include <linux/module.h>
#include <linux/netdevice.h>
#include <linux/hrtimer.h>
#include <linux/can/dev.h>
#include <linux/can/skb.h>
#include <linux/can/error.h>

static unsigned int clock_hz = 80000000;            /* CAN core clock, like M_CAN on AM62 */
module_param(clock_hz, uint, 0444);
static int fault;      /* 0 = ok, 1 = nobody ACKs (single node), 2 = bit errors (CAN_H short) */
module_param(fault, int, 0644);
static unsigned int retry_us = 1000;                /* HW retransmits after ~25 bits; slowed down */
module_param(retry_us, uint, 0644);

struct i10_priv {
	struct can_priv can;            /* MUST be first: netdev_priv() is also a can_priv */
	struct net_device *dev, *peer;
	struct napi_struct napi;
	struct sk_buff_head rxq;        /* "RX FIFO" of the fake controller */
	struct hrtimer txt;             /* fires when the frame would have left the wire */
	spinlock_t lock;                /* protects tec/rec/state */
	u16 tec, rec;
};
static struct net_device *i10dev[2];

static const struct can_bittiming_const i10_btc = {   /* copied from M_CAN v3.1 nominal */
	.name = "i10_can", .tseg1_min = 2, .tseg1_max = 256, .tseg2_min = 2,
	.tseg2_max = 128, .sjw_max = 128, .brp_min = 1, .brp_max = 512, .brp_inc = 1,
};
static const struct can_bittiming_const i10_dbtc = {  /* M_CAN v3.1 data phase */
	.name = "i10_can", .tseg1_min = 1, .tseg1_max = 32, .tseg2_min = 1,
	.tseg2_max = 16, .sjw_max = 16, .brp_min = 1, .brp_max = 32, .brp_inc = 1,
};

static int i10_get_berr(const struct net_device *dev, struct can_berr_counter *bec)
{
	struct i10_priv *p = netdev_priv(dev);

	bec->txerr = p->tec;
	bec->rxerr = p->rec;
	return 0;
}

static int i10_set_mode(struct net_device *dev, enum can_mode mode)
{
	struct i10_priv *p = netdev_priv(dev);

	if (mode != CAN_MODE_START)      /* called by restart-ms worker or "ip ... restart" */
		return -EOPNOTSUPP;
	spin_lock_bh(&p->lock);
	p->tec = p->rec = 0;             /* bus-off recovery = controller re-init */
	p->can.state = CAN_STATE_ERROR_ACTIVE;
	spin_unlock_bh(&p->lock);
	netif_wake_queue(dev);
	return 0;
}
```

- `i10_btc`/`i10_dbtc`는 `m_can.c`의 `m_can_bittiming_const_31X`/`m_can_data_bittiming_const_31X` 값을 그대로 가져왔다. 실제 드라이버라면 데이터시트의 NBTP/DBTP 레지스터 필드 폭에서 나온다(예: NTSEG1 8비트 → 1..256, 레지스터에는 값−1을 씀).
- `i10_set_mode()`는 `can_restart()`가 부른다. 실제 드라이버에서는 "컨트롤러를 init 모드로 넣고 → 비트 타이밍 다시 쓰고 → normal 모드로" 같은 시퀀스다(sja1000은 `sja1000_start()`).

### 7.3 코드 (2/6) — RX: "IRQ"가 큐에 넣고 NAPI가 위로 올린다

```c
/* (2/6) RX side: the "IRQ" queues frames, NAPI poll pushes them up the stack */
static void i10_rx_queue(struct i10_priv *p, struct sk_buff *skb)
{
	skb_queue_tail(&p->rxq, skb);
	napi_schedule(&p->napi);         /* like an RX IRQ handler: mask + schedule poll */
}

static int i10_poll(struct napi_struct *napi, int budget)
{
	struct i10_priv *p = container_of(napi, struct i10_priv, napi);
	struct net_device_stats *st = &p->dev->stats;
	struct sk_buff *skb;
	int n = 0;

	while (n < budget && (skb = skb_dequeue(&p->rxq))) {
		struct can_frame *cf = (struct can_frame *)skb->data;

		if (!(cf->can_id & CAN_ERR_FLAG)) {   /* error frames are not traffic */
			st->rx_packets++;
			st->rx_bytes += can_skb_get_data_len(skb);
		}
		netif_receive_skb(skb);
		n++;
	}
	if (n < budget)
		napi_complete_done(napi, n);  /* "re-enable RX IRQ" */
	return n;
}

/* copy the frame that is on the wire into the peer's RX FIFO */
static void i10_deliver(struct i10_priv *p, const struct sk_buff *e)
{
	struct i10_priv *pp = netdev_priv(p->peer);
	struct sk_buff *skb;

	if (can_is_canfd_skb(e)) {
		struct canfd_frame *cfd;

		if (!(pp->can.ctrlmode & CAN_CTRLMODE_FD)) {  /* classic node sees FD: form error */
			p->peer->stats.rx_errors++;
			return;
		}
		skb = alloc_canfd_skb(p->peer, &cfd);
		if (skb)
			memcpy(cfd, e->data, sizeof(*cfd));
	} else {
		struct can_frame *cf;

		skb = alloc_can_skb(p->peer, &cf);
		if (skb)
			memcpy(cf, e->data, sizeof(*cf));
	}
	if (!skb) {
		p->peer->stats.rx_dropped++;
		return;
	}
	i10_rx_queue(pp, skb);
}
```

- NAPI(I6에서 자세히): IRQ 핸들러는 RX 인터럽트를 끄고 `napi_schedule()`만 한다. softirq에서 `poll(budget)`이 FIFO를 최대 budget개 비우며 `netif_receive_skb()`로 스택에 올리고, 다 비우면 `napi_complete_done()` 후 IRQ를 다시 켠다. 고부하에서 IRQ 폭주를 막는 구조다 — bare-metal에서 "RX ISR은 플래그만 세우고 메인 루프에서 FIFO를 비우는 것"과 같다.
- CAN에서 NAPI의 함정: **수신 순서**. 메일박스가 여러 개인 컨트롤러(FlexCAN)는 HW 메일박스 순서와 도착 순서가 다를 수 있다. 그래서 커널에는 IRQ에서 메일박스를 타임스탬프 순으로 정렬해 큐에 넣고 NAPI로 올려 주는 헬퍼 **`can_rx_offload`**가 있다(8절, flexcan·m_can 주변 장치·mcp251xfd가 사용).
- 에러 프레임은 `rx_packets`에 안 센다. 6.x 커널 드라이버들의 관례다.
- `alloc_can_skb()`/`alloc_canfd_skb()`는 CAN용 skb를 만들고 `skb->protocol`, `ifindex`, `can_skb_priv` 같은 헤더를 채워 준다. CAN 드라이버는 일반 `netdev_alloc_skb()`를 쓰지 않는다.

### 7.4 코드 (3/6) — fault confinement: TEC/REC → 상태 → 에러 프레임

```c
/* (3/6) fault confinement: TEC/REC -> state, error frame up to user space */
enum { I10_TX_OK, I10_ACK_ERR, I10_BIT_ERR };

static void i10_err_update(struct i10_priv *p, int ev)
{
	struct net_device *dev = p->dev;
	bool berr = p->can.ctrlmode & CAN_CTRLMODE_BERR_REPORTING;
	struct can_berr_counter bec;
	enum can_state tx, rx, new;
	struct can_frame *cf = NULL;
	struct sk_buff *skb = NULL;

	spin_lock(&p->lock);
	if (ev == I10_TX_OK)
		p->tec = p->tec ? p->tec - 1 : 0;   /* successful TX: TEC - 1 */
	/* ISO 11898-1: transmitter +8; exception: error-passive + ACK error -> no change */
	else if (!(ev == I10_ACK_ERR && p->can.state == CAN_STATE_ERROR_PASSIVE))
		p->tec = min(p->tec + 8, 256);
	bec.txerr = p->tec;
	bec.rxerr = p->rec;
	spin_unlock(&p->lock);

	if (ev != I10_TX_OK) {
		p->can.can_stats.bus_error++;
		dev->stats.tx_errors++;
	}
	can_state_get_by_berr_counter(dev, &bec, &tx, &rx);
	new = max(tx, rx);
	if (new != p->can.state || (ev != I10_TX_OK && berr))
		skb = alloc_can_err_skb(dev, &cf);  /* may be NULL; still update state */
	if (skb && ev != I10_TX_OK && berr) {
		cf->can_id |= CAN_ERR_BUSERROR | (ev == I10_ACK_ERR ? CAN_ERR_ACK : CAN_ERR_PROT);
		if (ev == I10_ACK_ERR)
			cf->data[3] = CAN_ERR_PROT_LOC_ACK;
		else
			cf->data[2] = CAN_ERR_PROT_BIT;
	}
	if (skb) {
		cf->can_id |= CAN_ERR_CNT;
		cf->data[6] = min_t(u16, bec.txerr, 255);
		cf->data[7] = bec.rxerr;
	}
	if (new != p->can.state) {
		can_change_state(dev, cf, tx, rx);  /* sets CAN_ERR_CRTL/BUSOFF + stats */
		if (new == CAN_STATE_BUS_OFF)
			can_bus_off(dev);           /* carrier off, arm restart-ms */
	}
	if (skb)
		i10_rx_queue(p, skb);
}
```

- 실제 HW는 TEC/REC를 레지스터로 제공한다. 드라이버는 에러 IRQ에서 그 값을 읽어 `can_state_get_by_berr_counter()` → `can_change_state()` → (bus-off면) `can_bus_off()` 순서로 부른다. 이 함수의 흐름이 `sja1000_err()`, `m_can_handle_state_change()`, `flexcan_irq_state()`와 같다.
- `alloc_can_err_skb()`가 NULL이어도(메모리 부족) **상태 갱신은 해야 한다**. `can_change_state(dev, NULL, ...)`가 허용되는 이유다.
- `can_change_state()`가 같은 상태로 불리면 커널이 `oops, state did not change` 경고를 찍는다. 그래서 `new != p->can.state`일 때만 부른다.
- 이 함수는 hrtimer softirq 컨텍스트에서 돌므로 `spin_lock()`(BH 비활성 불필요), `i10_set_mode()`는 프로세스 컨텍스트(workqueue)라 `spin_lock_bh()`. **같은 데이터를 다른 컨텍스트에서 만질 때 락 종류를 맞추는 것**은 F 모듈의 핵심이다.

### 7.5 코드 (4/6) — TX: echo skb와 "TX 완료 인터럽트"

```c
/* (4/6) TX: echo skb + "TX-done IRQ" (hrtimer) + netdev glue */
static enum hrtimer_restart i10_txdone(struct hrtimer *t)
{
	struct i10_priv *p = container_of(t, struct i10_priv, txt);
	struct sk_buff *e = p->can.echo_skb[0];
	bool acked = fault == 0 && netif_running(p->peer);

	if (!e || p->can.state == CAN_STATE_BUS_OFF)
		return HRTIMER_NORESTART;
	if (fault == 2 || !acked) {
		i10_err_update(p, fault == 2 ? I10_BIT_ERR : I10_ACK_ERR);
		if (p->can.state == CAN_STATE_BUS_OFF)
			return HRTIMER_NORESTART;   /* frame stays in echo[0]; restart flushes */
		if (!(p->can.ctrlmode & CAN_CTRLMODE_ONE_SHOT)) {
			hrtimer_forward_now(t, us_to_ktime(retry_us)); /* automatic retransmission */
			return HRTIMER_RESTART;
		}
		can_free_echo_skb(p->dev, 0, NULL);  /* one-shot: give up */
		p->dev->stats.tx_dropped++;
	} else {
		i10_deliver(p, e);
		p->dev->stats.tx_bytes += can_get_echo_skb(p->dev, 0, NULL); /* local loopback */
		p->dev->stats.tx_packets++;
		i10_err_update(p, I10_TX_OK);       /* TEC - 1, maybe back to error-active */
	}
	netif_wake_queue(p->dev);
	return HRTIMER_NORESTART;
}

static netdev_tx_t i10_xmit(struct sk_buff *skb, struct net_device *dev)
{
	struct i10_priv *p = netdev_priv(dev);
	u32 br = p->can.bittiming.bitrate, len = can_skb_get_data_len(skb);

	if (can_dev_dropped_skb(dev, skb))
		return NETDEV_TX_OK;
	netif_stop_queue(dev);              /* one TX mailbox, like SJA1000 */
	can_put_echo_skb(skb, dev, 0, 0);   /* keep it until TX-complete */
	hrtimer_start(&p->txt, ns_to_ktime(div_u64((64ULL + 8 * len) * NSEC_PER_SEC, br)),
		      HRTIMER_MODE_REL_SOFT);
	return NETDEV_TX_OK;
}

static int i10_open(struct net_device *dev)
{
	struct i10_priv *p = netdev_priv(dev);
	int err = open_candev(dev);         /* fails with EINVAL if no bitrate set */

	if (err)
		return err;
	p->tec = p->rec = 0;
	p->can.state = CAN_STATE_ERROR_ACTIVE;
	napi_enable(&p->napi);
	netif_start_queue(dev);
	return 0;
}
```

- **`ndo_start_xmit` 계약**: skb를 받으면 반드시 소유권을 가져간다(보내거나, 보관하거나, 버리거나). `NETDEV_TX_OK`를 돌려주고, HW 큐가 꽉 차면 `netif_stop_queue()`. TX 완료에서 `netif_wake_queue()`. 메일박스가 하나면 매번 stop/wake다. FlexCAN·M_CAN처럼 TX FIFO가 깊으면 `echo_skb_max`를 FIFO 깊이로 잡고 인덱스로 관리하며 FIFO가 찰 때만 stop한다.
- **echo skb 수명**: `can_put_echo_skb(skb, dev, idx, frame_len)` → (TX 완료) `can_get_echo_skb(dev, idx, NULL)`이 skb를 `netif_rx()`로 올리고 데이터 길이를 돌려준다 → `tx_bytes`. 실패·중단이면 `can_free_echo_skb()`. bus-off 재시작 때는 can_dev가 `can_flush_echo_skb()`로 정리한다.
- `can_dev_dropped_skb()`: listen-only 모드면 버리고, 잘못된 길이·MTU의 skb를 걸러 낸다. 모든 CAN 드라이버의 `ndo_start_xmit` 첫 줄이다.
- `ndo_open`의 `open_candev()`는 비트 타이밍이 설정됐는지 검사하고(`bit-timing not yet defined` → `EINVAL`), carrier를 켠다. 실제 드라이버는 그 다음 클럭 enable → 컨트롤러 리셋 → 비트 타이밍·모드 레지스터 → IRQ 요청 → `napi_enable` → 컨트롤러 start → `netif_start_queue` 순서다.

### 7.6 코드 (5/6, 6/6) — stop, ops, 등록과 해제

```c
/* (5/6) stop, ops, module init = what probe() does in a real driver */
static int i10_stop(struct net_device *dev)
{
	struct i10_priv *p = netdev_priv(dev);

	netif_stop_queue(dev);
	hrtimer_cancel(&p->txt);
	napi_disable(&p->napi);
	skb_queue_purge(&p->rxq);
	can_free_echo_skb(dev, 0, NULL);
	p->can.state = CAN_STATE_STOPPED;
	close_candev(dev);                  /* also cancels the restart-ms work */
	return 0;
}

static const struct net_device_ops i10_ops = {
	.ndo_open = i10_open, .ndo_stop = i10_stop,
	.ndo_start_xmit = i10_xmit, .ndo_change_mtu = can_change_mtu,
};

static int __init i10_init(void)
{
	int i, err;

	for (i = 0; i < 2; i++) {
		struct net_device *dev = alloc_candev(sizeof(struct i10_priv), 1);
		struct i10_priv *p;

		if (!dev)
			return -ENOMEM;             /* (leaks dev[0] on failure: demo) */
		p = netdev_priv(dev);
		strscpy(dev->name, "i10can%d", IFNAMSIZ);
		dev->netdev_ops = &i10_ops;
		dev->flags |= IFF_ECHO;          /* we do local loopback via echo skb */
		p->dev = dev;
		p->can.clock.freq = clock_hz;
		p->can.bittiming_const = &i10_btc;
		p->can.fd.data_bittiming_const = &i10_dbtc;
		p->can.do_set_mode = i10_set_mode;
		p->can.do_get_berr_counter = i10_get_berr;
		p->can.ctrlmode_supported = CAN_CTRLMODE_FD | CAN_CTRLMODE_ONE_SHOT |
					    CAN_CTRLMODE_BERR_REPORTING;
		spin_lock_init(&p->lock);
		skb_queue_head_init(&p->rxq);
		hrtimer_setup(&p->txt, i10_txdone, CLOCK_MONOTONIC, HRTIMER_MODE_REL_SOFT);
		netif_napi_add(dev, &p->napi, i10_poll);
		i10dev[i] = dev;
	}
	((struct i10_priv *)netdev_priv(i10dev[0]))->peer = i10dev[1];
	((struct i10_priv *)netdev_priv(i10dev[1]))->peer = i10dev[0];
	for (i = 0; i < 2; i++) {
		err = register_candev(i10dev[i]);
		if (err)
			return err;
	}
	pr_info("i10_can: 2 controllers, clock %u Hz\n", clock_hz);
	return 0;
}
```

```c
/* (6/6) exit */
static void __exit i10_exit(void)
{
	int i;

	for (i = 0; i < 2; i++)
		unregister_candev(i10dev[i]);   /* both closed before anything is freed */
	for (i = 0; i < 2; i++) {
		netif_napi_del(&((struct i10_priv *)netdev_priv(i10dev[i]))->napi);
		free_candev(i10dev[i]);
	}
}
module_init(i10_init);
module_exit(i10_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("I10 demo: virtual CAN controller pair with error states");
```

- `dev->flags |= IFF_ECHO` — **처음 버전에서 이 줄을 빼먹었다.** 증상: 프레임 하나를 보내면 그 뒤로 인터페이스가 영원히 멈춤(TX 통계 0, ISO-TP가 First Frame만 보내고 멈춤). 원인: `can_put_echo_skb()`는 `IFF_ECHO`가 없으면 skb를 그냥 해제하고 0을 반환한다. 그러면 TX 완료 타이머가 `echo_skb[0] == NULL`을 보고 바로 return하는데, 그 경로에서 `netif_wake_queue()`가 안 불려 큐가 멈춘 것이다. 동시에 af_can은 `IFF_ECHO`가 없으니 스스로 루프백을 해서, 같은 장치의 다른 소켓에는 프레임이 "보인다". 그래서 처음에는 필터 테스트가 성공한 것처럼 보였다. `ip link`의 플래그가 `<NOARP>`였고(정상은 `<NOARP,ECHO>`) 거기서 원인을 찾았다. 교훈: **`ip -details link`의 플래그와 TX 통계부터 보자.**
- 해제 순서: 두 장치를 모두 `unregister_candev()`(내부에서 close → `i10_stop` → `hrtimer_cancel`)한 다음에 free한다. 하나를 먼저 free하면 다른 쪽 타이머가 이미 해제된 peer를 만질 수 있다. 실제 드라이버의 `remove()`도 "unregister → HW 끄기 → 자원 해제" 역순이다.
- 실제 드라이버는 `module_init` 대신 `platform_driver`/`pci_driver`/`spi_driver`의 `probe()`에서 이 일을 하고, `SET_NETDEV_DEV(dev, &pdev->dev)`로 부모 장치를 연결한다(그래야 `ip -details`에 `parentbus`/`parentdev`가 보이고 sysfs에 장치 계층이 생긴다). i10_can은 부모가 없어 `/sys/devices/virtual/net/i10can0`에 생긴다.

```dts
};
```

- `reg-names`: 레지스터(`m_can`)와 메시지 RAM(`message_ram`) 두 영역. 드라이버는 `devm_platform_ioremap_resource_byname()`으로 각각 매핑한다(H1).
- `clock-names = "hclk", "cclk"`: 버스 클럭과 **CAN 코어 클럭(cclk)**. `ip -details`의 `clock`이 cclk 주파수다. 비트 타이밍 문제의 절반은 이 클럭이 기대와 다른 데서 온다(H3).
- `bosch,mram-cfg = <offset sidf xidf rxf0 rxf1 rxb txe txb>`: 메시지 RAM 분할(11비트 필터 128개, 29비트 필터 64개, RX FIFO0 64개 …). 보드마다 튜닝 대상.
- 보드 dts에서 `status = "okay"`와 pinctrl(H4), 그리고 트랜시버(`phys = <&transceiver1>` 또는 `can-transceiver` 자식 노드)를 붙인다.
- `m_can_platform.c`는 DT에 `interrupts`가 **없으면** IRQ 없이 1 ms hrtimer로 폴링한다(`HRTIMER_POLL_INTERVAL_MS 1`). SoC에 따라 일부 M_CAN 인스턴스의 인터럽트가 메인 CPU로 라우팅되지 않는 경우를 위한 것이다. 폴링이면 RX 지연이 최대 1 ms 늘어나므로 제어 루프 설계에 반영해야 한다.
- RX는 MMIO M_CAN이면 NAPI(`m_can_poll`), SPI로 붙는 TCAN4x5x(M_CAN 코어를 SPI 칩에 넣은 것)면 `is_peripheral` 경로로 rx-offload를 쓴다.

### 8.2 NXP FlexCAN — i.MX6/8, Layerscape

메일박스(MB) 기반 컨트롤러. i.MX8MP 노드(`imx8mp.dtsi`):

```dts
flexcan1: can@308c0000 {
	compatible = "fsl,imx8mp-flexcan";
	reg = <0x308c0000 0x10000>;
	interrupts = <GIC_SPI 142 IRQ_TYPE_LEVEL_HIGH>;
	clocks = <&clk IMX8MP_CLK_IPG_ROOT>,
		 <&clk IMX8MP_CLK_CAN1_ROOT>;
	clock-names = "ipg", "per";
	assigned-clocks = <&clk IMX8MP_CLK_CAN1>;
	assigned-clock-parents = <&clk IMX8MP_SYS_PLL1_40M>;
	assigned-clock-rates = <40000000>;
	fsl,clk-source = /bits/ 8 <0>;
	fsl,stop-mode = <&gpr 0x10 4>;
	status = "disabled";
};
```

- `assigned-clock-rates = <40000000>`: CAN 클럭을 SYS_PLL1의 40 MHz 출력으로 고정한다. 4.4절에서 본 대로 CAN FD에 좋은 값이다. 보드에서 이 값을 바꾸면 모든 비트 타이밍 결과가 바뀐다.
- `fsl,clk-source`: FlexCAN 내부 클럭 소스 선택(0 = 오실레이터, 1 = 주변장치 클럭 — SoC마다 의미가 다르니 바인딩 문서 `fsl,flexcan.yaml` 확인).
- `fsl,stop-mode`: 저전력 stop 모드에서 CAN 프레임으로 깨어나기(wakeup) 위한 GPR 레지스터 위치.
- RX는 **`can_rx_offload`**: IRQ 핸들러가 메일박스(또는 RX FIFO)를 비워 HW 타임스탬프(FlexCAN 16비트 free-running 타이머) 순으로 정렬한 skb 큐에 넣고(`can_rx_offload_irq_offload_timestamp()`), NAPI가 순서대로 올린다. 메일박스 여러 개에서 생기는 **재정렬(reordering) 문제**를 해결하는 장치다.

### 8.3 Microchip MCP2517FD/MCP2518FD (`mcp251xfd`) — SPI CAN FD

SoC에 CAN이 없거나 모자랄 때 SPI로 붙이는 독립 컨트롤러. Raspberry Pi CAN FD HAT, Jetson 캐리어 보드에서 흔하다. 바인딩 예(`microchip,mcp251xfd.yaml`):

```dts
can@0 {
    compatible = "microchip,mcp251xfd";
    reg = <0>;
    clocks = <&can0_osc>;
    pinctrl-names = "default";
    pinctrl-0 = <&can0_pins>;
    spi-max-frequency = <20000000>;
    interrupts-extended = <&gpio 13 IRQ_TYPE_LEVEL_LOW>;
    microchip,rx-int-gpios = <&gpio 27 GPIO_ACTIVE_LOW>;
    vdd-supply = <&reg5v0>;
    xceiver-supply = <&reg5v0>;
};
```

SPI CAN의 **지연 문제**가 면접에서 자주 나온다. 구조적 이유:

- 인터럽트 핀은 GPIO(레벨 low)다. SPI 전송은 잠들 수 있으므로 핸들러는 hardirq에서 못 돌고 **threaded IRQ**로 돈다(`request_threaded_irq(..., NULL, mcp251xfd_irq, IRQF_SHARED | IRQF_ONESHOT, ...)`, F7·H6). 즉 IRQ → 스레드 깨우기 → 스케줄링 지연이 붙는다.
- 프레임 하나를 꺼내는 데 SPI 트랜잭션이 여러 번(인터럽트 상태 읽기, FIFO 헤드 읽기, 데이터 읽기, FIFO 포인터 갱신) 필요하다. 20 MHz SPI에서도 트랜잭션당 수십 µs, 컨트롤러 드라이버와 DMA 설정에 따라 더 길다(H7). 1 Mbit/s 버스에 프레임이 몰리면 RX FIFO가 넘쳐 `CAN_ERR_CRTL_RX_OVERFLOW`가 난다.
- 그래서 드라이버는 SPI 왕복을 줄이는 기법을 쓴다: 여러 레지스터를 한 번에 읽는 bulk read, **`microchip,rx-int-gpios`**(RX 전용 인터럽트 핀 — 이 GPIO를 읽어 "RX가 있는지"를 SPI 없이 확인), IRQ coalescing(`ethtool -C`), 링 크기 조절(`ethtool -G`).
- 실무 대책: SPI 컨트롤러 드라이버의 DMA/폴링 임계값 확인, IRQ 스레드를 SCHED_FIFO 높은 우선순위로(`chrt`), PREEMPT_RT, SPI 클럭 최대치, 그리고 가능한 한 SoC 내장 CAN 사용.

### 8.4 타임스탬프 — 언제 받았나

제어·센서 퓨전에서는 "프레임이 언제 버스에 있었나"가 중요하다.

- SW 타임스탬프: 소켓 옵션 `SO_TIMESTAMPNS`(5.6절 `i10_jit`에서 사용) 또는 `SO_TIMESTAMPING`의 SW RX. skb가 스택에 들어올 때(NAPI 안) 찍힌다. IRQ 지연·NAPI 지연·SPI 지연이 모두 포함된다.
- HW 타임스탬프: mcp251xfd·m_can·flexcan 일부는 컨트롤러의 타임베이스로 수신 시각을 찍고, 드라이버가 이를 `skb_hwtstamps(skb)`에 넣는다. 유저는 `SO_TIMESTAMPING` + `SOF_TIMESTAMPING_RAW_HARDWARE`로 받는다. 지원 여부는 `ethtool -T can0`(드라이버의 `get_ts_info`, mcp251xfd는 `can_ethtool_op_get_ts_info_hwts`)으로 확인한다. 이 노트의 가상 장치에서는 실행하지 않았다.
- rx-offload 경로는 HW 타임스탬프로 **정렬**까지 한다(8.2절).

### 8.5 종단 저항(termination)

CAN 버스는 양 끝에 120 Ω이 있어야 한다(측정: 전원 끈 상태에서 CAN_H–CAN_L 사이 약 60 Ω). 일부 보드는 GPIO로 종단을 켜고 끈다 — DT의 `termination-gpios`, `termination-ohms`(`can-controller.yaml`), 유저는 `ip link set can0 type can termination 120`. 종단이 없거나 3개 이상이면 반사·레벨 문제로 bit/form error가 나고 bus-off까지 간다.

## 9. 커널 안에서는 무슨 일이 일어나나

유저의 `write(s, &frame, 16)`부터 상대 노드의 `read()`까지:

```
TX (process context)
 raw_sendmsg()                      net/can/raw.c     : skb alloc, copy can_frame
  can_send(skb, loop)               net/can/af_can.c  : checks, loopback policy (IFF_ECHO?)
   dev_queue_xmit(skb)              net/core          : qdisc pfifo_fast (qlen 10) -> ENOBUFS if full
    dev_hard_start_xmit()
     ndo_start_xmit(skb, dev)       driver            : can_dev_dropped_skb, can_put_echo_skb, HW mailbox
TX done (hardirq / threaded irq / softirq)
 driver irq handler
  can_get_echo_skb(dev, idx)        drivers/net/can/dev/skb.c : netif_rx(echo) -> local sockets
  netif_wake_queue(dev)
RX
 driver irq -> napi_schedule() / can_rx_offload
  poll(): alloc_can_skb + netif_receive_skb()
   can_rcv() / canfd_rcv()          net/can/af_can.c  : ETH_P_CAN / ETH_P_CANFD packet_type
    can_receive()
     can_rcv_filter()               rx_all, rx_fil, rx_inv, rx_eff, rx_sff[id], rx_err
      deliver() -> raw_rcv()        net/can/raw.c     : per-socket checks -> sock_queue_rcv_skb
Config
 ip link set can0 type can bitrate ...  -> rtnetlink -> can_changelink()  drivers/net/can/dev/netlink.c
   can_get_bittiming() -> can_calc_bittiming() -> priv->do_set_bittiming()
 bus-off: driver can_bus_off() -> netif_carrier_off + schedule restart_work (restart-ms)
   can_restart_work() -> can_restart() -> can_flush_echo_skb, CAN_ERR_RESTARTED, do_set_mode(START)
```

(영문만 들어간 경로 그림이라 ASCII로 그렸다.) 드라이버 작성 때 다시 만나는 지점:

- `ndo_start_xmit`과 NAPI는 **I6(네트워크 드라이버)**의 일반 규칙을 따른다. CAN만의 추가 규칙은 echo skb와 `can_dev_dropped_skb()`다.
- IRQ 핸들러의 컨텍스트(hardirq / threaded / softirq)와 락 선택은 **F7, F3/F4**. SPI 컨트롤러(mcp251xfd)는 threaded IRQ(H6, H7).
- 레지스터 접근은 **H1(MMIO)**, H2(regmap — mcp251xfd가 SPI regmap을 쓴다), 클럭은 H3, 핀은 H4.
- DT 노드와 `of_match_table`, `probe()`는 **D, G**. `SET_NETDEV_DEV()`로 부모 장치를 연결해야 sysfs 계층과 `parentdev`가 생긴다.
- restart-ms는 delayed work(F7), bus-off 시 `netif_carrier_off()`는 링크 이벤트로 netlink에 퍼진다(`ip monitor`).

## 10. Embedded 실무에서 다시 보기

### 10.1 로봇 보드 CAN bring-up 체크리스트

새 보드에서 `can0`가 안 될 때, 아래 순서로 바깥(HW)에서 안(앱)으로 좁힌다. 각 단계의 명령은 이 노트에서 한 번씩 돌려 본 것들이다.

1. 장치가 있나: `ip -details link show can0` — 없으면 DT `status`, 드라이버 모듈, `dmesg | grep -i can`(probe 에러, 클럭 못 얻음 `-EPROBE_DEFER`).
2. 클럭이 맞나: `ip -details`의 `clock` 값이 데이터시트·DT `assigned-clock-rates`와 같은가.
3. 비트 타이밍: `ip link set can0 type can bitrate 500000 sample-point 0.875` 후 `ip -details`의 tq·세그먼트를 손으로 검산(4절). MCU 노드들의 설정(샘플 포인트·SJW)과 비교.
4. 버스 물리: 전원 끈 상태 CAN_H–CAN_L 60 Ω, 트랜시버 STB/EN 핀(GPIO)이 normal 모드인가, 트랜시버 전원(`xceiver-supply`).
5. 링크 테스트: 상대 노드 없이 `ip link set can0 type can loopback on`(컨트롤러 내부 루프백, `CAN_CTRLMODE_LOOPBACK` 지원 시)으로 드라이버·IRQ부터 확인 → 그 다음 실제 버스.
6. 에러 관찰: `candump -e any,0:0,#FFFFFFFF` + `ip -details -statistics link show can0`(berr-counter, error-warn/pass, bus-off, re-started).
7. scope로 비트 폭 측정(500 k = 2 µs), 디코더로 ACK 슬롯·에러 플래그 확인.

### 10.2 부팅 때 자동 설정 — systemd-networkd (실행하지 않음)

보드에서는 `ip` 명령을 스크립트로 치지 않고 systemd-networkd로 설정하는 경우가 많다. 아래는 `systemd.network(5)`의 `[CAN]` 섹션 문법이다. 이 노트의 랩(BusyBox initramfs)에는 systemd가 없어 **실행하지 않았다** — 키 이름은 사용하는 systemd 버전의 man 페이지로 확인하자.

```text
# /etc/systemd/network/80-can0.network
[Match]
Name=can0

[CAN]
BitRate=500000
SamplePoint=87.5%
DataBitRate=2000000
DataSamplePoint=75%
FDMode=yes
RestartSec=100ms
```

### 10.3 앱 쪽 방어 코드

6절 실험이 알려 주는 앱 설계 규칙:

- `write()`의 `ENOBUFS`를 처리한다(재시도 + 카운트 + 일정 횟수 넘으면 "버스 이상" 상태로).
- 에러 프레임을 받는 별도 소켓(또는 같은 소켓에 `CAN_RAW_ERR_FILTER`)으로 `CAN_ERR_BUSOFF`, `CAN_ERR_CRTL`(passive), `CAN_ERR_RESTARTED`를 감시해 상위(로봇 상태 머신)에 알린다. 모터를 안전 정지시키는 근거가 된다.
- 주기 명령은 BCM 또는 ABSTIME 루프 + 실시간 스케줄링. watchdog 타임아웃은 측정한 최악 지연(5.6절 p99·max)보다 넉넉하게.
- 버스 부하는 `canbusload can0@500000`으로 본다. 50%를 넘으면 낮은 우선순위 ID의 지연이 급격히 늘어난다.
- 기록: `candump -l -t A can0`으로 로그 파일, `canplayer`로 재생 — 현장 문제 재현의 기본.

### 10.4 모터 컨트롤러 예: CANopen/CiA 402와 SocketCAN

많은 산업용 모터 드라이버는 CANopen(CiA 301/402)을 쓴다. Linux에서는 SocketCAN RAW 위에 유저 공간 스택(예: CANopenNode, Lely)을 올린다. 커널은 프레임 전달·필터·에러 보고까지만 하고, NMT·SDO·PDO·heartbeat는 유저 공간 몫이다. 반면 J1939(트럭·농기계)와 ISO-TP(진단)는 커널 소켓이 있다(2.1절). 면접에서 "커널에 넣을 것 vs 유저 공간에 둘 것"을 물으면: 주소 클레임·세그멘테이션처럼 **타이밍이 촘촘하고 여러 앱이 공유하는 상태**는 커널, 장치 프로파일 로직은 유저 공간이라고 답하면 된다.

## 11. 흔한 실수와 증상

| 실수 | 증상 | 원인 | 고치는 법 |
|---|---|---|---|
| bitrate 없이 `ip link set can0 up` | `RTNETLINK answers: Invalid argument`, dmesg `bit-timing not yet defined` | `open_candev()`가 비트 타이밍 미설정을 거부 | `down` → `type can bitrate ...` → `up` 순서 |
| up 상태에서 bitrate 변경 | `Device or resource busy` | 동작 중 비트 타이밍 변경 금지 | 먼저 `ip link set can0 down` |
| 노드 하나만 연결해 놓고 테스트 | TX가 안 끝나고 큐가 참, `ERROR-PASSIVE (tx 128)`에서 멈춤 | 아무도 ACK 안 함. passive + ACK 에러는 TEC 불변 | 상대 노드 연결, 또는 컨트롤러 `loopback on`으로 먼저 검증 |
| 노드마다 샘플 포인트·클럭이 다름 | 부하 높을 때만 간헐 bit/stuff error, 한 노드가 반복 bus-off | 비트 경계 오차가 SJW로 못 흡수됨 | 모든 노드 bitrate·sample point 통일, `ip -details`로 검산 |
| 종단 저항 0개 또는 3개 이상 | 짧은 버스에선 되다가 길어지면 에러 폭증 | 반사, 차동 전압 레벨 이상 | CAN_H–CAN_L 60 Ω 확인 |
| 필터 마스크에 `CAN_EFF_FLAG` 누락 | 표준 ID 필터에 29비트 프레임이 섞여 들어옴 | 플래그 비트도 마스크 대상 | `CAN_SFF_MASK` + `CAN_EFF_FLAG` (+ `CAN_RTR_FLAG`) |
| 앱이 `ENOBUFS`를 치명 에러로 처리 | bus-off 한 번에 앱이 죽음 | bus-off 동안 qdisc(qlen 10)가 참 | 재시도·백오프, 에러 프레임으로 버스 상태 감시 |
| restart-ms만 켜고 원인 방치 | 로그에 `bus-off, scheduling restart`가 주기적으로 반복 | 물리·타이밍 고장이 그대로 | 12절 Q1 순서로 원인 추적 |
| 드라이버가 `IFF_ECHO`를 안 세우고 echo skb 사용 | 첫 프레임 후 TX 영구 정지, `ip link` 플래그에 ECHO 없음 | `can_put_echo_skb()`가 skb를 버리고 0 반환 → TX 완료 경로가 wake를 못 함 | alloc 직후 `dev->flags`에 `IFF_ECHO` 비트를 OR (이 노트 7.6절에서 실제로 겪음) |
| 드라이버 `bittiming_const`·`clock.freq`가 데이터시트와 다름 | `ip`는 500 k라는데 scope로 재면 비트 폭이 다름 | can_dev 계산의 입력이 틀림 | 레지스터 필드 폭·실제 CAN 클럭으로 상수 수정 |

## 12. 면접에서 이렇게 말한다

**Q.** "A CAN bus on our robot keeps going bus-off. How do you debug it?"

**A.** 먼저 사실 수집: 어느 노드가 bus-off 되는지, 얼마나 자주, 부하·모터 구동과 상관있는지. Linux 쪽에서는 `ip -details -statistics link show can0`로 bus-off·re-started·error-warn/pass 카운터와 TEC/REC를 보고, `candump -e`로 에러 프레임 종류(bit/stuff/form/ACK, 위치)를 본다. **TEC만 오르면 이 노드의 송신이 문제**(트랜시버, 비트 타이밍, 이 노드만의 배선), **REC가 오르면 남이 보낸 프레임을 못 읽는 것**이다. 그다음 물리: 60 Ω 종단, 접지·차동 전압, scope로 비트 폭과 에러 플래그 위치. 타이밍: 모든 노드의 bitrate·샘플 포인트·클럭 정확도 일치 여부. 모터 구동 때만 나면 EMI(접지, 케이블 차폐, 트랜시버 공통 모드 범위). restart-ms는 증상을 가리므로 원인을 찾는 동안은 끄거나 카운터를 기록한다.

> First I gather facts: which node goes bus-off, how often, and whether it correlates with motor load. On Linux I read `ip -details -statistics link show can0` for the bus-off and restart counters and the TEC/REC values, and I capture error frames with `candump -e` to see whether they are bit, stuff, form or ACK errors and where in the frame they occur. If only TEC climbs, the problem is this node's transmit path — transceiver, bit timing, its stub wiring; if REC climbs, it can't read other nodes' frames. Then the physical layer: 60 ohms between CAN_H and CAN_L, ground and differential levels, and a scope to measure bit time and see the error flags. Then timing: same bitrate and sample point and clock accuracy on every node. If it only happens with the motors running, it's usually EMI — grounding, shielding, common-mode range. I don't rely on restart-ms during debugging because it hides the symptom.

**꼬리 질문**: "케이블을 뽑으면 bus-off가 되나?" → 아니다. 혼자 남은 송신자는 ACK 에러만 받고, error-passive에서 ACK 에러는 TEC를 올리지 않으므로 passive에 머문다(이 노트 6.4절 실측).

**Q.** "Explain the SocketCAN architecture."

**A.** CAN 컨트롤러를 네트워크 인터페이스로 만든 것이다. 유저는 `PF_CAN` 소켓(RAW, BCM, ISO-TP, J1939)을 쓰고, af_can 코어가 장치별 수신 필터 리스트로 프레임을 소켓에 나눠 준다. 송신은 일반 `dev_queue_xmit`과 qdisc를 거쳐 드라이버의 `ndo_start_xmit`으로 간다. 드라이버는 can_dev 라이브러리로 비트 타이밍 계산, netlink 설정, 에러 상태·bus-off·restart, echo skb 루프백을 공유한다. 장점은 여러 앱이 동시에 한 버스를 쓰고, 네트워크 도구·필터·타임스탬프를 그대로 쓴다는 것.

> SocketCAN models a CAN controller as a network device. Applications open PF_CAN sockets — raw, broadcast manager, ISO-TP or J1939 — and the af_can core dispatches received frames through per-device filter lists to the sockets. Transmit goes through the normal dev_queue_xmit and qdisc path into the driver's ndo_start_xmit. Drivers share the can_dev library for bit-timing calculation, netlink configuration, error states, bus-off and restart handling, and echo-skb based local loopback. The benefit is multiple applications on one bus, standard networking tools, per-socket filters and timestamps.

**Q.** "What does the echo skb do in a CAN driver, and why not just loop back in software?"

**A.** 같은 장치의 다른 소켓이 내 송신 프레임을 보려면 루프백이 필요한데, 드라이버가 `IFF_ECHO`를 세우면 송신 skb를 `can_put_echo_skb`로 보관했다가 **HW가 실제로 전송을 끝낸 TX-complete 인터럽트에서** `can_get_echo_skb`로 올린다. 그래서 로컬 앱이 보는 순서와 시각이 버스의 실제 순서와 같고, 중재에 지거나 에러로 못 나간 프레임은 보이지 않는다. SW 즉시 루프백은 "보냈다고 착각"하게 만든다.

> When IFF_ECHO is set, the driver keeps the transmitted skb with can_put_echo_skb and only loops it back with can_get_echo_skb in the TX-complete interrupt, after the frame really left the controller. Local listeners therefore see frames in actual bus order and timing, and a frame that never made it onto the bus is never echoed. An immediate software loopback would show frames that were never transmitted.

**Q.** "How does Linux compute CAN bit timing from a bitrate?"

**A.** 드라이버가 컨트롤러 클럭과 `can_bittiming_const`(tseg1/tseg2/sjw/brp 범위)를 등록한다. `ip ... bitrate`가 오면 `can_calc_bittiming()`이 CiA 권장 샘플 포인트(≤ 500 k는 87.5%, ≤ 800 k는 80%, 그 이상 75%)를 목표로, 총 tq 수를 큰 값부터 내려가며 brp를 구해 비트레이트 오차, 그다음 샘플 포인트 오차가 최소인 조합을 고른다. 오차가 0.5%를 넘으면 거부한다. 예: 40 MHz, 500 k → brp 1, tq 25 ns, 1+34+35+10 = 80 tq, 샘플 포인트 87.5%.

> The driver registers the controller clock and a can_bittiming_const with the tseg1, tseg2, sjw and brp ranges. can_calc_bittiming targets the CiA recommended sample point — 87.5 percent up to 500 kbit/s, 80 up to 800, 75 above — walks the total number of time quanta from large to small, derives the prescaler, and keeps the combination with the smallest bitrate error and then the smallest sample-point error, rejecting anything over 0.5 percent error. For a 40 MHz clock at 500 kbit/s that's brp 1, 25 ns quanta, 80 quanta per bit with the sample point at 87.5 percent.

**Q.** "Walk me through what a CAN driver does on an error interrupt."

**A.** TEC/REC와 상태 레지스터를 읽고, `alloc_can_err_skb()`로 에러 프레임을 만든 뒤 버스 에러 종류(bit/stuff/form/ACK, berr-reporting이 켜졌을 때)를 채운다. `can_state_get_by_berr_counter()`로 tx/rx 상태를 구해 바뀌었으면 `can_change_state()`, bus-off면 `can_bus_off()`(carrier off, restart-ms 예약)와 컨트롤러 정지. 마지막으로 에러 프레임을 NAPI나 `netif_rx`로 올리고 통계를 갱신한다. 재시작은 can_dev가 `do_set_mode(CAN_MODE_START)`로 부른다.

> It reads TEC, REC and the status register, allocates an error frame with alloc_can_err_skb and, if bus-error reporting is enabled, fills in the protocol error type and location. It derives the TX and RX states with can_state_get_by_berr_counter, calls can_change_state when the state changed, and on bus-off calls can_bus_off, which turns the carrier off and schedules the restart, and stops the controller. Then it pushes the error frame up and updates statistics. Recovery comes later through do_set_mode with CAN_MODE_START.

**Q.** "Why is an SPI CAN controller like the MCP2518FD harder to get low latency with than an on-chip FlexCAN?"

**A.** SPI 트랜잭션은 잠들 수 있어서 IRQ를 threaded handler에서 처리해야 하고, 프레임 하나에 SPI 왕복이 여러 번 든다. 그래서 IRQ → 스레드 스케줄링 → SPI 전송 지연이 쌓이고 고부하에서 RX FIFO overflow가 난다. 드라이버는 bulk read, RX 전용 인터럽트 GPIO, IRQ coalescing으로 줄이고, 시스템 쪽에서는 IRQ 스레드 우선순위, SPI DMA, PREEMPT_RT로 대응한다.

> SPI transfers can sleep, so the interrupt is handled in a threaded handler, and each frame costs several SPI round trips. Interrupt latency, thread scheduling and SPI transfer time add up, and under heavy load the RX FIFO can overflow. The driver mitigates with bulk reads, a dedicated RX-interrupt GPIO and interrupt coalescing; on the system side you raise the IRQ thread priority, make sure SPI uses DMA, and consider PREEMPT_RT.

**Q.** "How would you send a CAN message every 10 ms from Linux reliably?"

**A.** 커널 BCM `TX_SETUP`이면 프로세스 스케줄링과 무관하게 hrtimer가 보낸다. 다만 6.18 BCM은 다음 만료를 "지금 + 간격"으로 잡아 지연이 누적된다(내 측정: VM에서 평균 10.11 ms). 장기 주기가 정확해야 하면 `clock_nanosleep(TIMER_ABSTIME)` 루프를 SCHED_FIFO로 돌린다(평균 10.000 ms, 지터는 남음). usleep 루프는 누적 + 긴 꼬리로 최악이다. 받는 쪽 watchdog은 측정한 최악 지연 기준으로 잡는다.

> The broadcast manager's TX_SETUP lets a kernel hrtimer send the frame independent of process scheduling, but in current kernels the next expiry is computed as now plus the interval, so latency accumulates — I measured a 10.11 ms mean on a VM. If the long-term period must be exact, I use a clock_nanosleep TIMER_ABSTIME loop in a SCHED_FIFO thread, which averages exactly 10 ms with some per-cycle jitter. A plain usleep loop is the worst: drift plus long tails. The receiver's watchdog timeout is set from the measured worst case.

## 13. 직접 해보기

1. (개념) 노드 A, B만 있는 버스에서 B의 전원을 끄면 A의 TEC는 어디까지 오르고 어떤 상태가 되나? B의 트랜시버만 CAN_H를 GND에 단락시키면? 정답/힌트: 전자는 128(error-passive)에서 멈춤(ACK 에러 예외), 후자는 bit error로 계속 +8 → bus-off.
2. (계산) CAN 클럭 80 MHz, bitrate 250 k, 샘플 포인트 80%를 SJA1000 같은 작은 bittiming_const(tseg1 1..16, tseg2 1..8, brp 1..64)로 만들 수 있나? 4.5절 Python으로 확인하고 손으로 brp와 세그먼트를 써 보자. 정답/힌트: 비트당 tq는 최대 25(1+16+8), 80 MHz/250 k = 320 = brp × ntq → brp 16 × 20 tq 같은 조합. 샘플 포인트 80%면 1+15 / 20 → TSEG1 15, TSEG2 4.
3. (코드) `i10_errdump`를 고쳐 `CAN_ERR_LOSTARB`, `CAN_ERR_CRTL_RX_OVERFLOW`도 해석하고, `poll()`로 데이터 소켓과 에러 소켓을 함께 기다리게 하라. 정답/힌트: 에러 마스크에 해당 비트, `data[0]`(비트 위치), `data[1]`의 0x01.
4. (드라이버) `i10_can`에 `CAN_CTRLMODE_LOOPBACK`을 추가해, 켜져 있으면 peer 대신 자기 RX 큐로 프레임을 넣고 ACK가 항상 성공하게 하라. `ip link set i10can0 type can loopback on`으로 확인. 정답/힌트: `ctrlmode_supported`에 플래그 추가, `i10_txdone()`에서 `p->can.ctrlmode & CAN_CTRLMODE_LOOPBACK` 분기.
5. (드라이버) `i10_can`에 `priv->bitrate_max = 1000000`(classic)을 넣고 `bitrate 3000000`이 거부되는지 확인하라. FD 데이터 비트레이트 상한은 어떻게 걸까? 정답/힌트: netlink가 `bitrate_max`와 비교해 `EINVAL`. FD 데이터는 같은 `bitrate_max` 검사를 받는다(커널 버전별로 `can_changelink` 확인).
6. (관찰) `/proc/net/can/rcvlist_sff`에 항목이 생기게 candump 필터를 만들어 보라(`123:C00007FF` 형태로 EFF·RTR 플래그를 마스크에 포함). 그리고 `/proc/net/can/stats`의 matched frames가 변하는지 보라. 정답/힌트: `CAN_EFF_FLAG | CAN_RTR_FLAG | CAN_SFF_MASK` = `0xC00007FF`.
7. (측정) 5.6절 실험을 게스트 안에서 `SCHED_FIFO`(`chrt -f 50`)로 다시 돌려 ABSTIME 루프의 p99가 줄어드는지 보라. 정답/힌트: TCG 게스트는 호스트 스케줄링의 영향이 커서 개선 폭이 작을 수 있다 — 결과를 그대로 기록하는 게 핵심.

| arbitration | 중재 | ID 비트를 동시에 내며 낮은 ID가 이김, 비파괴 |
| ACK slot | 확인 비트 | 누군가 정상 수신하면 dominant로 덮음 |

| bus-off | 버스 이탈 | TEC ≥ 256, 송수신 중단, restart 필요 |

| tq | time quantum | brp / CAN 클럭, 비트 타이밍의 최소 단위 |

| BRS / ESI / FDF | FD 플래그 | 데이터 구간 고속 / 송신자 passive / FD 프레임 표시 |
| TDC | 송신 지연 보상 | 고속 FD 데이터 구간에서 트랜시버 루프 지연 보정 |

| rx-offload | CAN RX 헬퍼 | IRQ에서 메일박스를 타임스탬프 순으로 큐잉, NAPI로 전달 |
| BCM | Broadcast Manager | 커널 주기 송신·수신 감시 소켓 |
| ISO-TP | ISO 15765-2 | 긴 메시지 분할(FF/CF)과 흐름 제어(FC) |

## 15. 요약 & 체크리스트

Linux에서 CAN 컨트롤러는 net_device다. 유저는 PF_CAN 소켓(RAW·BCM·ISO-TP·J1939)을 쓰고, af_can이 필터로 프레임을 나눠 주며, 설정은 `ip link ... type can`(rtnetlink → can_dev)으로 한다. 드라이버는 `alloc_candev` + `struct can_priv`(bittiming_const, clock, ctrlmode_supported, do_set_mode, do_get_berr_counter)를 채우고, TX는 `can_put_echo_skb`/`can_get_echo_skb`로 HW 완료 기준 루프백, RX는 NAPI(또는 rx-offload), 에러는 `can_change_state`/`can_bus_off`로 보고한다. 비트 타이밍은 커널이 클럭과 상수로 계산하므로 `ip -details`를 손으로 검산할 수 있어야 하고, 에러 상태는 TEC/REC 문턱값(96/128/256)과 "passive + ACK 에러는 TEC 불변" 예외로 설명할 수 있어야 한다. QEMU의 SJA1000·CTU CAN FD 에뮬레이션은 레지스터 수준 드라이버와 FD 프레임은 보여 주지만 ACK·에러 상태는 재현하지 않는다 — 그래서 직접 쓴 `i10_can`으로 error-passive 정체, bus-off ↔ restart 반복, ENOBUFS, one-shot을 재현했다.

- [ ] CAN 컨트롤러가 왜 `/dev`가 아니라 네트워크 인터페이스인지, SocketCAN 계층을 그림으로 설명할 수 있다
- [ ] `can_frame`/`canfd_frame` 레이아웃, `can_id` 플래그 비트, `CAN_MTU`/`CANFD_MTU`를 설명할 수 있다
- [ ] 필터 `(id & mask) == (fid & mask)`와 `CAN_EFF_FLAG` 함정, 에러 마스크를 코드로 쓸 수 있다
- [ ] `ip -details`의 tq·prop-seg·phase-seg·sjw·brp를 클럭과 bitrate로 손 계산할 수 있다
- [ ] CiA 권장 샘플 포인트와 커널 `can_calc_bittiming` 탐색 순서를 설명할 수 있다
- [ ] TEC/REC 규칙, 96/128/256 문턱값, error-passive ACK 예외를 설명할 수 있다
- [ ] 에러 프레임(`CAN_ERR_*` 클래스, `data[1]`, `data[6..7]`)을 받아 해석하는 C 코드를 짤 수 있다
- [ ] restart-ms와 수동 restart, bus-off 시 carrier off·ENOBUFS를 설명할 수 있다
- [ ] `alloc_candev`, `can_priv` 콜백, `open_candev`/`close_candev`, echo skb, NAPI RX를 갖춘 드라이버 뼈대를 쓸 수 있다
- [ ] `IFF_ECHO` 누락 같은 드라이버 버그를 `ip link` 플래그와 통계로 찾을 수 있다
- [ ] M_CAN·FlexCAN·MCP251xFD의 DT 노드와 SPI CAN 지연 원인을 설명할 수 있다
- [ ] "CAN이 계속 bus-off 된다" 디버그 순서를 영어로 2분 안에 말할 수 있다
