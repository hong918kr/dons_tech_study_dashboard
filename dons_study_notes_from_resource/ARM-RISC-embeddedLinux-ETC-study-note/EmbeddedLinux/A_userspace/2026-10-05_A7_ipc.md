# A7. IPC (프로세스 간 통신) — pipe, UNIX socket, message queue, shared memory를 언제 무엇으로 쓰나

> **이 노트를 다 읽으면**: IPC 메뉴(pipe·FIFO·UNIX socket·POSIX mq·POSIX shm·D-Bus)를 특성으로 비교할 수 있다 · 스트림 소켓 위에 메시지 프레이밍을 짜고 SCM_RIGHTS로 fd(카메라 dmabuf)를 넘길 수 있다 · shm 위에 SPSC 링버퍼와 process-shared 동기화를 직접 만든다 · pipe/socket/shm의 처리량·지연을 직접 재서 숫자로 말할 수 있다
> **왜 필요한가**: "센서 데몬과 로거를 어떻게 연결할 건가?", "카메라 프레임을 복사 없이 다른 프로세스로 넘기려면?" — 로봇·카메라 장비의 서비스 설계 면접과 실무에서 그대로 나온다
> **Don 기준 난이도**: 링버퍼·DMA 버퍼 공유·메모리 순서는 이미 안다 / 리눅스가 제공하는 IPC 객체들의 의미(누가 복사하고, 누가 깨우고, 죽으면 무엇이 남는지)는 새로 배운다
> **선행 노트**: A1(fd와 "everything is a file"), A2(fork), A4(epoll), A5(mmap) — A8(동기화)과 같이 읽으면 좋다

## 0. 큰 그림 — 왜 프로세스를 나누고, 그래서 왜 IPC가 필요한가

bare-metal 펌웨어에서는 모든 태스크가 **한 주소 공간**에 산다. IMU 태스크가 링버퍼에 샘플을 넣으면 로거 태스크가 같은 전역 변수를 읽는다. 통신 = 그냥 메모리 접근 + 세마포어다. 편하지만, 한 태스크가 포인터를 잘못 쓰면 전체가 죽는다.

Embedded Linux 장비는 보통 일부러 **여러 프로세스로 쪼갠다**. 예를 들어 센서 키트라면:

- `imu_daemon`: IIO 장치(`/dev/iio:device0`)에서 400 Hz로 샘플을 읽는다. 실시간 우선순위(SCHED_FIFO)로 돈다.
- `camera_daemon`: V4L2로 프레임을 받는다. 프레임 버퍼는 커널이 할당한 dmabuf다.
- `logger`: 샘플·프레임을 eMMC에 기록한다.
- `uploader`: LTE/Wi-Fi로 텔레메트리를 보낸다. **유일하게 네트워크 권한**을 가진다.
- `health_mon`: 모든 데몬의 상태를 모아 watchdog을 찬다.

나누는 이유는 세 가지다.

1. **장애 격리(fault isolation)**: uploader가 TLS 라이브러리 버그로 segfault 나도 imu_daemon은 계속 돈다. 각 프로세스는 MMU로 격리된 자기 주소 공간을 가진다 — Don이 아는 "MPU로 태스크 영역을 막는 것"의 완전판이다.
2. **권한 분리(privilege separation)**: 네트워크에 노출된 uploader는 root가 아니고 장치 파일도 못 연다. 뚫려도 피해가 작다.
3. **독립 재시작·배포**: systemd가 죽은 데몬만 다시 띄운다(`Restart=on-failure`). 로거만 업데이트할 수도 있다. 언어도 섞을 수 있다(C 데몬 + Python 업로더).

대가는 하나다. **데이터가 주소 공간 경계를 넘어가야 한다.** 그 경계를 넘는 방법들이 IPC(Inter-Process Communication)다.

### IPC를 고를 때 묻는 질문 6개

IPC 방식은 많지만 고르는 기준은 몇 개 안 된다. 이 노트 내내 이 질문으로 각 방식을 평가한다.

| 질문 | 왜 중요한가 | 펌웨어 비유 |
|---|---|---|
| 데이터가 몇 번 복사되나 | 64 KB 프레임을 초당 수백 장 옮기면 복사가 CPU를 먹는다 | memcpy vs DMA 버퍼 포인터 넘기기 |

## 2. pipe와 FIFO — 가장 단순한 바이트 스트림

### 2.1 직관

pipe는 **커널 안에 있는 작은 링버퍼 하나 + fd 두 개**(읽기 끝, 쓰기 끝)다. 펌웨어로 치면 UART TX FIFO와 RX FIFO를 루프백으로 붙여 놓은 것이다. 한쪽에서 `write()`로 넣으면 다른 쪽에서 `read()`로 꺼낸다. 비면 reader가 잠들고, 가득 차면 writer가 잠든다. 깨워 주는 건 커널이다.

- **익명 pipe**(`pipe()`/`pipe2()`): 이름이 없다. fd를 물려받은 프로세스끼리만(보통 `fork()`한 부모-자식) 쓴다. 셸의 `cmd1 | cmd2`가 바로 이것이다.
- **FIFO(named pipe)**: 파일시스템에 이름(`mkfifo`)이 있는 pipe다. 상관없는 두 프로세스가 경로로 만난다. 데이터는 디스크에 안 가고 똑같이 커널 메모리에만 있다.

### 2.2 예제 1 — pipe 용량과 "페이지 단위" 링

무엇을 확인하는 코드인가: 기본 pipe 용량이 몇 바이트인지, `F_SETPIPE_SZ`로 늘릴 수 있는지, 그리고 조금 읽었다고 바로 쓸 공간이 생기지 않는 이유.

```c
/* 예제 1: pipe 기본 + 용량(F_GETPIPE_SZ) 측정 + 크기 변경 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

static void die(const char *m) { perror(m); exit(1); }

static long fill(int wfd) {          /* EAGAIN 날 때까지 1바이트씩 쓴다 */
    long n = 0;
    char c = 'x';
    for (;;) {
        ssize_t r = write(wfd, &c, 1);
        if (r == 1) { n++; continue; }
        if (errno == EAGAIN) return n;
        die("write");
    }
}

int main(void) {
    int p[2];
    if (pipe2(p, O_NONBLOCK) < 0) die("pipe2");
    printf("fds: read=%d write=%d\n", p[0], p[1]);
    printf("PIPE_BUF        = %d\n", PIPE_BUF);
    printf("F_GETPIPE_SZ    = %d\n", fcntl(p[1], F_GETPIPE_SZ));
    printf("filled bytes    = %ld\n", fill(p[1]));

    char buf[100];
    ssize_t r = read(p[0], buf, sizeof buf);       /* 100바이트 비우기 */
    printf("read %zd -> 1-byte write now: %zd\n", r, write(p[1], "y", 1));
    char page[4096];
    r = read(p[0], page, sizeof page - 100);       /* 첫 페이지를 다 비우기 */
    printf("read %zd more -> 1-byte write now: %zd\n", r, write(p[1], "y", 1));

    int q[2];
    if (pipe2(q, O_NONBLOCK) < 0) die("pipe2");
    int sz = fcntl(q[1], F_SETPIPE_SZ, 1 << 20);   /* 1 MiB로 키우기 */
    if (sz < 0) die("F_SETPIPE_SZ");
    printf("after SETPIPE_SZ= %d, filled = %ld\n", sz, fill(q[1]));
    return 0;
}
```

```text
fds: read=3 write=4
PIPE_BUF        = 4096
F_GETPIPE_SZ    = 65536
filled bytes    = 65536
read 100 -> 1-byte write now: -1
read 3996 more -> 1-byte write now: 1
after SETPIPE_SZ= 1048576, filled = 1048576
```

출력에서 볼 것: 기본 용량은 64 KiB(= 16 페이지)다. 가득 찬 뒤 100바이트를 읽어도 1바이트 write가 실패(-1, `EAGAIN`)하고, **첫 페이지를 다 비워야**(총 4096바이트) 성공한다. pipe는 바이트 링이 아니라 **페이지 슬롯 16개짜리 링**이기 때문이다(9.1절 그림 7). 빈 슬롯이 하나 생겨야 새 페이지를 붙일 수 있다. 크기는 `F_SETPIPE_SZ`로 키울 수 있고, 일반 사용자의 상한은 `/proc/sys/fs/pipe-max-size`(이 VM에서 1048576)다.

### 2.3 PIPE_BUF — "섞이지 않음"의 보장

여러 프로세스가 **한 pipe에 동시에 write**하면(예: 여러 데몬이 로그 FIFO 하나에 쓰는 경우) 메시지가 중간에 섞일 수 있나? POSIX의 답: **`PIPE_BUF` 바이트 이하의 write는 원자적**이다. 한 번에 통째로 들어가고 다른 writer의 데이터가 끼어들지 않는다. Linux에서 `PIPE_BUF` = 4096이다. 그보다 크면 보장이 없다.

예제 2 — 무엇을 확인하는 코드인가: writer 4개가 각자 자기 글자로 채운 레코드를 2000개씩 쓸 때, 레코드 크기에 따라 "찢어진(torn)" 레코드가 나오는지.

```c
/* 예제 2: 여러 writer가 한 pipe에 쓸 때 PIPE_BUF 이하/초과 레코드가 섞이는가 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

#define NW 4          /* writer 프로세스 수 */
#define NREC 2000     /* writer당 레코드 수 */

static void die(const char *m) { perror(m); exit(1); }

static int run(size_t rec) {
    int p[2];
    if (pipe(p) < 0) die("pipe");
    for (int w = 0; w < NW; w++) {
        if (fork() == 0) {                      /* writer: 'A'+w 로 채운 레코드 */
            close(p[0]);
            char *b = malloc(rec);
            memset(b, 'A' + w, rec);
            for (int i = 0; i < NREC; i++)
                if (write(p[1], b, rec) != (ssize_t)rec) die("write");
            _exit(0);
        }
    }
    close(p[1]);
    char *b = malloc(rec);
    int torn = 0, total = 0;
    for (;;) {                                  /* 정확히 rec 바이트씩 모아 검사 */
        size_t got = 0;
        while (got < rec) {
            ssize_t r = read(p[0], b + got, rec - got);
            if (r < 0) die("read");
            if (r == 0) break;
            got += r;
        }
        if (got < rec) break;
        total++;
        for (size_t i = 1; i < rec; i++)
            if (b[i] != b[0]) { torn++; break; }
    }
    while (wait(NULL) > 0) {}
    close(p[0]); free(b);
    printf("record=%6zu B  records=%5d  torn=%d\n", rec, total, torn);
    return torn;
}

int main(void) {
    run(512);
    run(4096);      /* == PIPE_BUF: 원자적 보장 */
    run(4097);      /* PIPE_BUF 초과: 보장 없음 */
    run(65536);
    return 0;
}
```

```text
record=   512 B  records= 8000  torn=0
record=  4096 B  records= 8000  torn=0
record=  4097 B  records= 8000  torn=2812
record= 65536 B  records= 8000  torn=0
```

같은 프로그램을 세 번 더 돌린 결과(뒤 두 줄만):

```text
record=  4097 B  records= 8000  torn=3723
record= 65536 B  records= 8000  torn=0
record=  4097 B  records= 8000  torn=3935
record= 65536 B  records= 8000  torn=0
record=  4097 B  records= 8000  torn=3861
record= 65536 B  records= 8000  torn=0
```

출력에서 볼 것: 4096바이트까지는 한 번도 안 섞였고, **딱 1바이트 넘긴 4097바이트에서 수천 개가 찢어졌다.** 64 KiB가 0인 것은 레코드 크기가 pipe 용량과 정확히 같아 이번 스케줄링에서 우연히 안 섞인 것이다 — 보장이 아니다. 규칙은 하나: **여러 writer가 공유하는 pipe/FIFO에는 PIPE_BUF 이하 크기로만 쓴다.** 넘으면 writer별 pipe를 따로 두거나 소켓(메시지 경계가 있는 SEQPACKET/DGRAM)을 쓴다.

`O_NONBLOCK`일 때의 규칙도 알아 두자: PIPE_BUF 이하 write는 공간이 모자라면 **한 바이트도 안 쓰고** `EAGAIN`이고, PIPE_BUF 초과 write는 **일부만 쓰고** 쓴 바이트 수를 돌려줄 수 있다(partial write). 그래서 non-blocking 코드는 항상 반환값을 확인하고 남은 부분을 다시 써야 한다.

### 2.4 EOF와 SIGPIPE — 한쪽이 죽으면

pipe의 "크래시 동작"은 깔끔하다.

- 모든 writer가 닫히면(프로세스가 죽어도 커널이 fd를 닫는다) reader의 `read()`는 **0(EOF)** 을 돌려준다.
- 모든 reader가 닫혔는데 write하면 writer는 **`SIGPIPE`** 를 받는다(기본 동작 = 종료). 시그널을 무시하면 `write()`가 `EPIPE`로 실패한다. 데몬은 보통 `SIGPIPE`를 무시하고 `EPIPE`를 처리한다(A6).
- 그래서 **안 쓰는 끝은 반드시 닫는다.** 자식에게 fd를 물려준 뒤 부모가 쓰기 끝을 안 닫으면, 자식이 다 써도 reader는 EOF를 영원히 못 받는다(쓰기 끝을 가진 프로세스가 아직 있으니까). 예제 2에서 부모가 `close(p[1])`을 하는 이유다.

### 2.5 셸의 `|`를 strace로 보기 (예제 3)

### 2.6 FIFO 예제 4 — 이름으로 만나는 pipe

무엇을 확인하는 코드인가: FIFO 파일의 정체, 그리고 **상대가 열 때까지 `open()` 자체가 막힌다**는 FIFO 고유의 동작.

```sh
cat imu.fifo > out.txt &

wait; cat out.txt; ls -l imu.fifo
```

```text
writer exit code=124 (124 = open()에서 막혀 timeout)

imu seq=2 ax=0.02
```

출력에서 볼 것: 파일 타입 글자가 `p`이고 크기는 항상 0이다(데이터는 커널 메모리에만 있다). reader가 없을 때 writer는 `echo`도 못 하고 **`open()`에서 1초 동안 막혀** timeout(124)으로 끝났다. 막힌 writer가 커널의 어디에 있는지 보자.


`fifo_open()` → `wait_for_partner()`에서 잠들어 있다. VFS의 `open()`이 파일 타입별 `file_operations.open`(여기서는 `pipefifo_fops`의 `fifo_open`)으로 내려간다는 A1의 그림이 그대로 보인다. 드라이버의 `.open`도 이렇게 불린다(G4). 데몬에서 FIFO를 쓸 때는 reader가 `O_RDWR`로 열거나(자기 자신이 writer 역할도 해서 EOF가 안 온다) `O_NONBLOCK`으로 열어 막힘을 피하는 패턴을 많이 쓴다.

### 2.7 pipe의 함정 정리

- 바이트 스트림이라 **메시지 경계가 없다**(3.2절 프레이밍 필요).
- 단방향이다. 요청-응답이면 pipe 두 개가 필요하다(→ 그럴 바엔 socketpair).
- reader가 여럿이면 **한 바이트는 한 reader만** 받는다. 브로드캐스트가 아니다.
- 64 KiB가 차면 writer가 막힌다. 실시간 생산자(센서 데몬)가 느린 소비자 때문에 막히면 샘플 타이밍이 망가진다 → non-blocking + 드롭 정책이 필요하다.

## 3. UNIX domain socket — 실무 IPC의 주력

### 3.1 직관과 정의

UNIX domain socket(`AF_UNIX`)은 **같은 머신 안에서만 쓰는 소켓**이다. API는 TCP/UDP 소켓(A9)과 똑같고(`socket`/`bind`/`listen`/`accept`/`connect`/`send`/`recv`), 네트워크 스택(IP, 체크섬, 라우팅)을 안 거치니 훨씬 가볍다. pipe보다 할 수 있는 게 많아서 실무 데몬 간 통신은 대부분 이것이다. systemd, D-Bus, Wayland, Docker, X11이 모두 UNIX socket 위에서 돈다.

pipe에 비해 더 있는 것:

- **양방향**: 한 소켓으로 요청과 응답을 주고받는다.
- **세 가지 타입**: `SOCK_STREAM`(경계 없는 바이트 스트림, TCP와 비슷), `SOCK_DGRAM`(경계 보존, 연결 없음, UDP와 비슷하지만 **로컬이라 유실·순서 바뀜 없음**), `SOCK_SEQPACKET`(경계 보존 + 연결형 + 순서 보장 — 로컬 메시지 IPC의 숨은 강자).
- **이름 짓기 세 가지**: 파일 경로(`/run/sensor.sock`, 파일 권한으로 접근 제어), **abstract namespace**(Linux 전용, 경로 첫 바이트가 `'\0'`, 파일이 안 생겨서 지울 필요가 없음), 이름 없음(`socketpair()`).
- **상대 확인**: `SO_PEERCRED`로 상대 프로세스의 pid/uid/gid를 커널이 보증해서 알려 준다.
- **fd 전달**: `SCM_RIGHTS`로 열린 fd 자체를 다른 프로세스에 넘긴다(3.4절). pipe로는 불가능하다.

### 3.2 예제 5 — 스트림은 경계가 없다

무엇을 확인하는 코드인가: 같은 메시지 3개를 `send()` 3번으로 보내고, 소켓 타입별로 `recv()`가 어떻게 돌려주는지.

```c
/* 예제 5: SOCK_STREAM은 경계가 없고 SOCK_SEQPACKET/DGRAM은 경계를 지킨다 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <unistd.h>

static void die(const char *m) { perror(m); exit(1); }

static void demo(int type, const char *name) {
    int sv[2];
    if (socketpair(AF_UNIX, type, 0, sv) < 0) die("socketpair");
    const char *msg[] = { "IMU,1,0.01", "IMU,2,0.02", "GNSS,3,37.42" };
    for (int i = 0; i < 3; i++)                 /* 메시지 3개를 따로 send */
        if (send(sv[0], msg[i], strlen(msg[i]), 0) < 0) die("send");
    close(sv[0]);
    printf("[%s]\n", name);
    char buf[256];
    ssize_t n;
    while ((n = recv(sv[1], buf, sizeof buf, MSG_DONTWAIT)) > 0)
        printf("  recv %2zd bytes: \"%.*s\"\n", n, (int)n, buf);
    close(sv[1]);
}

int main(void) {
    demo(SOCK_STREAM, "SOCK_STREAM");
    demo(SOCK_SEQPACKET, "SOCK_SEQPACKET");
    demo(SOCK_DGRAM, "SOCK_DGRAM");

    int sv[2];                                  /* 작은 버퍼로 받으면? */
    if (socketpair(AF_UNIX, SOCK_SEQPACKET, 0, sv) < 0) die("socketpair");
    send(sv[0], "0123456789", 10, 0);
    char small[4];
    ssize_t n = recv(sv[1], small, sizeof small, MSG_TRUNC);
    printf("[SEQPACKET, 4B buffer + MSG_TRUNC] recv returned %zd (real size), got \"%.4s\"\n",
           n, small);
    return 0;
}
```

```text
[SOCK_STREAM]
  recv 32 bytes: "IMU,1,0.01IMU,2,0.02GNSS,3,37.42"
[SOCK_SEQPACKET]
  recv 10 bytes: "IMU,1,0.01"
  recv 10 bytes: "IMU,2,0.02"
  recv 12 bytes: "GNSS,3,37.42"
[SOCK_DGRAM]
  recv 10 bytes: "IMU,1,0.01"
  recv 10 bytes: "IMU,2,0.02"
  recv 12 bytes: "GNSS,3,37.42"
[SEQPACKET, 4B buffer + MSG_TRUNC] recv returned 10 (real size), got "0123"
```

출력에서 볼 것: STREAM은 `send()` 세 번을 **한 덩어리 32바이트**로 돌려줬다. 반대로 한 번 보낸 것이 여러 번에 나눠 올 수도 있다. SEQPACKET/DGRAM은 보낸 단위 그대로 받는다. 대신 버퍼가 작으면 **남은 부분이 잘려 버려진다** — `MSG_TRUNC`를 주면 원래 크기(10)를 알려 줘서 잘림을 감지할 수 있다.

펌웨어 비유: STREAM은 UART다. 바이트는 순서대로 오지만 "패킷"은 없다. 그래서 UART 프로토콜에 SOF·길이·CRC를 넣듯, 스트림 소켓 위에는 **프레이밍**을 직접 얹어야 한다. 가장 흔한 방법이 **길이 프리픽스**: `[4바이트 길이][본문]`. 받는 쪽은 "정확히 4바이트 읽기 → 정확히 len바이트 읽기"를 반복한다. `read()`가 요청보다 적게 돌려주는(short read) 경우를 반드시 루프로 처리해야 한다.

### 3.3 예제 6 — abstract namespace + SO_PEERCRED + 길이 프리픽스

무엇을 확인하는 코드인가: 파일을 만들지 않는 abstract 소켓 이름, 커널이 보증하는 상대 자격 증명, 그리고 short read를 견디는 프레이밍.

```c
/* 예제 6: abstract namespace UNIX socket + SO_PEERCRED + 길이 프리픽스 프레이밍 */
#define _GNU_SOURCE
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/un.h>
#include <sys/wait.h>
#include <unistd.h>

static void die(const char *m) { perror(m); exit(1); }

static int io_all(int fd, void *b, size_t n, int wr) {  /* 짧은 read/write 처리 */
    char *p = b;
    while (n) {
        ssize_t r = wr ? write(fd, p, n) : read(fd, p, n);
        if (r <= 0) return -1;
        p += r; n -= r;
    }
    return 0;
}

int main(void) {
    struct sockaddr_un a = { .sun_family = AF_UNIX };
    const char name[] = "sensor_hub";              /* sun_path[0] = '\0' → abstract */
    memcpy(a.sun_path + 1, name, sizeof name - 1);
    socklen_t alen = offsetof(struct sockaddr_un, sun_path) + 1 + sizeof name - 1;

    int ls = socket(AF_UNIX, SOCK_STREAM, 0);
    if (ls < 0 || bind(ls, (void *)&a, alen) < 0 || listen(ls, 4) < 0) die("server");
    if (system("ss -xl | grep sensor_hub | tr -s ' '") < 0) perror("system");

    if (fork() == 0) {                             /* client: 프레임 2개 전송 */
        int c = socket(AF_UNIX, SOCK_STREAM, 0);
        if (connect(c, (void *)&a, alen) < 0) die("connect");
        const char *m[] = { "temp=41.5C", "imu_rate=400Hz,dropped=0" };
        for (int i = 0; i < 2; i++) {
            uint32_t len = strlen(m[i]);           /* [4B 길이][본문] */
            if (io_all(c, &len, 4, 1) || io_all(c, (void *)m[i], len, 1)) die("send");
        }
        _exit(0);
    }
    int s = accept(ls, NULL, NULL);
    if (s < 0) die("accept");
    struct ucred cr;
    socklen_t cl = sizeof cr;
    if (getsockopt(s, SOL_SOCKET, SO_PEERCRED, &cr, &cl) < 0) die("SO_PEERCRED");
    printf("peer pid=%d uid=%d gid=%d (my pid=%d)\n", cr.pid, cr.uid, cr.gid, getpid());

    uint32_t len;
    char buf[256];
    while (io_all(s, &len, 4, 0) == 0) {
        if (len >= sizeof buf || io_all(s, buf, len, 0)) die("frame");
        printf("frame len=%u: %.*s\n", len, (int)len, buf);
    }
    wait(NULL);
    return 0;
}
```

```text
u_str LISTEN 0 4 @sensor_hub 124634 * 0 
peer pid=187221 uid=501 gid=1000 (my pid=187216)
frame len=10: temp=41.5C
frame len=24: imu_rate=400Hz,dropped=0
```

출력에서 볼 것(pid는 실행마다 다르다): `ss -xl`에 이름이 **`@sensor_hub`** 로 보인다. `@`는 abstract namespace라는 표시다(실제 첫 바이트는 `'\0'`). 파일시스템에 소켓 파일이 없으니 데몬이 죽은 뒤 `bind: Address already in use`로 재시작이 실패하는 고전 문제가 없다. 대신 **파일 권한으로 접근을 막을 수 없다**(같은 network namespace의 누구나 connect 가능). 그래서 `SO_PEERCRED`로 uid를 확인하는 코드가 짝으로 따라온다. 출력의 peer pid는 자식(client) pid, uid 501은 VM 사용자 `donh`다. 이 값은 상대가 위조할 수 없고 **connect() 시점**의 자격 증명이다.

파일 경로 소켓을 쓴다면: `bind()` 전에 `unlink(path)`하고, 디렉터리 권한(예: `/run/sensor/` 0750, 그룹 `sensor`)으로 접근을 제어한다. systemd 소켓 활성화(socket activation)를 쓰면 systemd가 소켓을 만들어 fd로 넘겨준다(L 모듈).

### 3.4 예제 7 — SCM_RIGHTS로 fd 넘기기 (카메라 버퍼 zero-copy의 핵심)

직관: 카메라 프레임 1장(1920×1080 NV12 ≈ 3 MB)을 소켓으로 **복사**해서 넘기면 초당 30장에 90 MB/s를 memcpy한다. 대신 **"버퍼를 가리키는 핸들"만** 넘기면 복사가 0이다. Linux에서 그 핸들이 fd다. V4L2는 `VIDIOC_EXPBUF`로 프레임 버퍼를 **dmabuf fd**로 내보낼 수 있고, 그 fd를 `SCM_RIGHTS`로 인코더·추론 프로세스에 넘기면 받은 쪽이 같은 버퍼를 `mmap`하거나 GPU/NPU 드라이버에 그대로 import한다(I5, Q2). 펌웨어에서 DMA 디스크립터에 버퍼 **포인터**만 넘기는 것과 같은 발상이다.

아래 예제는 dmabuf 대신 `memfd_create()`(이름 없는 메모리 파일)를 "프레임 버퍼"로 쓴다. fd라는 점에서 다루는 법은 같다.

```c
/* 예제 7: SCM_RIGHTS로 fd 전달 — memfd를 "카메라 프레임 버퍼"로 보고 consumer에 넘긴다 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <unistd.h>

static void die(const char *m) { perror(m); exit(1); }

static void show(const char *who, int fd) {
    char path[64], tgt[128];
    snprintf(path, sizeof path, "/proc/self/fd/%d", fd);
    ssize_t n = readlink(path, tgt, sizeof tgt - 1); tgt[n < 0 ? 0 : n] = 0;
    printf("%-9s pid=%d fd=%d -> %s\n", who, getpid(), fd, tgt);
}

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);               /* _exit 전에 출력이 사라지지 않게 */
    int sv[2];
    if (socketpair(AF_UNIX, SOCK_SEQPACKET, 0, sv) < 0) die("socketpair");
    if (fork() == 0) {                              /* consumer (예: 인코더) */
        close(sv[0]);
        char tag[16];
        union { struct cmsghdr h; char b[CMSG_SPACE(sizeof(int))]; } u;
        struct iovec iov = { tag, sizeof tag };
        struct msghdr m = { .msg_iov = &iov, .msg_iovlen = 1,
                            .msg_control = u.b, .msg_controllen = sizeof u.b };
        if (recvmsg(sv[1], &m, 0) < 0) die("recvmsg");
        struct cmsghdr *c = CMSG_FIRSTHDR(&m);
        if (!c || c->cmsg_type != SCM_RIGHTS) { fprintf(stderr, "no fd\n"); _exit(1); }
        int fd; memcpy(&fd, CMSG_DATA(c), sizeof fd);
        show("consumer", fd);
        char *p = mmap(NULL, 4096, PROT_READ, MAP_SHARED, fd, 0);
        if (p == MAP_FAILED) die("mmap");
        printf("consumer  msg=\"%s\" frame says: %s\n", tag, p);
        _exit(0);
    }
    close(sv[1]);                                   /* producer (카메라 데몬) */
    if (dup(0) < 0 || dup(0) < 0) die("dup");       /* 일부러 fd 번호를 어긋나게 */
    int fd = memfd_create("cam0_frame42", 0);
    if (fd < 0 || ftruncate(fd, 4096) < 0) die("memfd");
    char *p = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) die("mmap");
    strcpy(p, "1920x1080 NV12 ts=123456789");       /* 프레임 내용 대신 */
    show("producer", fd);

    union { struct cmsghdr h; char b[CMSG_SPACE(sizeof(int))]; } u = { 0 };
    struct iovec iov = { "frame42", 8 };
    struct msghdr m = { .msg_iov = &iov, .msg_iovlen = 1,
                        .msg_control = u.b, .msg_controllen = sizeof u.b };
    struct cmsghdr *c = CMSG_FIRSTHDR(&m);
    c->cmsg_level = SOL_SOCKET; c->cmsg_type = SCM_RIGHTS; c->cmsg_len = CMSG_LEN(sizeof(int));
    memcpy(CMSG_DATA(c), &fd, sizeof fd);
    if (sendmsg(sv[0], &m, 0) < 0) die("sendmsg");
    wait(NULL);
    return 0;
}
```

```text
producer  pid=188034 fd=6 -> /memfd:cam0_frame42 (deleted)
consumer  pid=188063 fd=3 -> /memfd:cam0_frame42 (deleted)
consumer  msg="frame42" frame says: 1920x1080 NV12 ts=123456789
```

출력에서 볼 것: producer에서는 fd **6**이던 것이 consumer에서는 fd **3**이다. **fd 번호가 아니라 커널의 `struct file` 참조가 전달**되고, 받는 쪽 fd 테이블의 빈 번호에 새로 설치되기 때문이다. 둘 다 같은 `/memfd:cam0_frame42`를 가리키고, consumer는 복사 없이 같은 메모리를 읽었다. `(deleted)`는 memfd가 파일시스템 이름이 없는 파일이라는 뜻이다.

그림 3 — SCM_RIGHTS fd 전달. 소켓에 실려 가는 것은 데이터가 아니라 `struct file` 참조다. 받는 쪽에는 새 fd 번호가 붙고, 두 fd(점선)는 같은 `struct file`과 같은 버퍼를 가리킨다.

함정:

- control 버퍼는 `CMSG_SPACE()`로 크기를 잡고 정렬을 위해 `union { struct cmsghdr; char[] }`로 선언한다(위 코드처럼). `CMSG_LEN`과 `CMSG_SPACE`를 헷갈리면 플랫폼마다 다르게 깨진다.
- fd만 보내도 **최소 1바이트의 일반 데이터**를 같이 보낸다(STREAM에서 0바이트 sendmsg는 의미가 없다). 위 예제는 프레임 이름을 실었다.
- 받은 fd는 받는 쪽이 `close()`해야 한다. 안 그러면 fd와 버퍼가 샌다. 카메라 파이프라인에서 프레임마다 fd를 받는데 안 닫으면 몇 분 뒤 `EMFILE`이나 버퍼 고갈로 멈춘다.
- 보낸 뒤에도 보낸 쪽 fd는 그대로 열려 있다(복제다). 버퍼 소유권 규칙(누가 언제 돌려주나)은 프로토콜로 정해야 한다.
- memfd를 남에게 넘길 때 받은 쪽이 크기를 줄여 SIGBUS를 일으키는 공격을 막으려면 `MFD_ALLOW_SEALING` + `fcntl(F_ADD_SEALS, F_SEAL_SHRINK)`을 쓴다.

## 4. POSIX message queue — 커널이 관리하는 우선순위 우편함

### 4.1 직관과 정의

POSIX mq는 RTOS의 **메시지 큐(mailbox)** 와 거의 같다. 고정 최대 크기(`mq_msgsize`)의 메시지를 최대 `mq_maxmsg`개까지 커널이 보관하고, **우선순위가 높은 메시지가 먼저** 나온다. 이름은 `/sensor_evt`처럼 `/`로 시작하고, Linux에서는 `/dev/mqueue` 가상 파일시스템에 파일로 보인다.

- 메시지 경계 보존, 우선순위(0이 가장 낮음, Linux는 0~32767).
- **커널 지속성(kernel persistence)**: 모든 프로세스가 닫아도 `mq_unlink()` 전까지(또는 재부팅 전까지) 큐와 메시지가 남는다. 생산자가 죽어도 이미 넣은 메시지는 소비자가 받는다.
- `mq_notify()`: 큐가 **비어 있다가 메시지가 들어오는 순간** 시그널이나 스레드로 한 번 알려 준다. 또 `mqd_t`가 Linux에서는 실제 fd라서 epoll에 넣을 수도 있다(A4).
- 한계: 시스템 기본 상한이 작다(이 VM에서 `/proc/sys/fs/mqueue/msg_max` = 10, `msgsize_max` = 8192). 대량 데이터용이 아니라 **이벤트·명령·경보용**이다.

### 4.2 예제 8 — 우선순위와 mq_notify

무엇을 확인하는 코드인가: 낮은 우선순위 텔레메트리 사이에 끼어든 높은 우선순위 고장 경보가 먼저 나오는지, `/dev/mqueue`에서 큐 상태가 어떻게 보이는지, `mq_notify`가 언제 불리는지.

```c
/* 예제 8: POSIX message queue — 우선순위, mq_getattr, /dev/mqueue, mq_notify */
#include <fcntl.h>
#include <mqueue.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>

#define QN "/sensor_evt"
static void die(const char *m) { perror(m); exit(1); }
static mqd_t q;
static volatile int notified;

static void on_msg(union sigval sv) {             /* 빈 큐 → 비지 않음 전이에 1회 호출 */
    (void)sv;
    printf("  [notify thread] queue became non-empty\n");
    notified = 1;
}

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);
    struct mq_attr at = { .mq_maxmsg = 8, .mq_msgsize = 64 };
    mq_unlink(QN);
    q = mq_open(QN, O_CREAT | O_RDWR, 0600, &at);
    if (q == (mqd_t)-1) die("mq_open");

    struct sigevent se = { .sigev_notify = SIGEV_THREAD,
                           .sigev_notify_function = on_msg };
    if (mq_notify(q, &se) < 0) die("mq_notify");

    struct { const char *s; unsigned prio; } m[] = {
        { "telemetry temp=41C", 0 }, { "telemetry imu ok", 0 },
        { "FAULT motor overcurrent", 9 }, { "warn gnss no fix", 5 } };
    for (int i = 0; i < 4; i++)
        if (mq_send(q, m[i].s, strlen(m[i].s) + 1, m[i].prio) < 0) die("mq_send");
    while (!notified) usleep(1000);

    mq_getattr(q, &at);
    printf("maxmsg=%ld msgsize=%ld curmsgs=%ld\n", at.mq_maxmsg, at.mq_msgsize, at.mq_curmsgs);
    if (system("cat /dev/mqueue/sensor_evt") < 0) perror("system");

    char buf[64];
    unsigned prio;
    while (mq_getattr(q, &at) == 0 && at.mq_curmsgs > 0) {
        if (mq_receive(q, buf, sizeof buf, &prio) < 0) die("mq_receive");
        printf("recv prio=%u: %s\n", prio, buf);
    }
    if (mq_receive(q, buf, 10, &prio) < 0) perror("mq_receive with 10B buffer");
    mq_close(q);
    mq_unlink(QN);
    return 0;
}
```

```text
  [notify thread] queue became non-empty
maxmsg=8 msgsize=64 curmsgs=4
QSIZE:77         NOTIFY:0     SIGNO:0     NOTIFY_PID:0     
recv prio=9: FAULT motor overcurrent
recv prio=5: warn gnss no fix
recv prio=0: telemetry temp=41C
recv prio=0: telemetry imu ok
mq_receive with 10B buffer: Message too long
```

출력에서 볼 것: 보낸 순서는 telemetry, telemetry, FAULT, warn이었지만 받은 순서는 **우선순위 9 → 5 → 0 → 0**이고, 같은 우선순위끼리는 보낸 순서(FIFO)다. `/dev/mqueue/sensor_evt`의 `QSIZE:77`은 큐에 든 메시지 바이트 합(19+17+24+17)이다. `NOTIFY_PID:0`인 이유: `mq_notify` 등록은 **한 번 발화하면 해제**되기 때문이다(계속 받으려면 콜백 안에서 다시 등록). 또 수신 버퍼가 `mq_msgsize`(64)보다 작으면 메시지가 있든 없든 바로 `EMSGSIZE`다 — `mq_getattr`로 크기를 확인하고 버퍼를 잡는다.

`mq_notify`의 함정: 큐에 등록할 수 있는 프로세스는 하나뿐이고, `mq_receive`로 **이미 블록된 reader가 있으면 알림이 안 온다**. 실무에서는 `mqd_t`를 epoll에 넣는 쪽이 단순하다.

## 5. POSIX shared memory — 복사 0번, 대신 동기화는 내 몫

### 5.1 직관

shared memory는 IPC 중 유일하게 **커널이 데이터 경로에서 빠진다.** 두 프로세스의 페이지 테이블이 **같은 물리 페이지**를 가리키게 만들어 주는 것까지만 커널이 하고(mmap), 그 다음부터는 그냥 메모리 load/store다. bare-metal에서 두 코어가 공유 SRAM 영역을 쓰는 것과 똑같다. 그래서 가장 빠르지만, 펌웨어에서 그랬듯 **동기화·메모리 순서·"데이터가 왔다"는 통지**는 전부 직접 해야 한다.

API는 셋이다.

1. `shm_open("/name", O_CREAT|O_RDWR, 0600)`: `/dev/shm/name`(tmpfs) 파일을 연다. glibc 구현이 실제로 그 경로를 open한다.
2. `ftruncate(fd, size)`: 크기를 정한다(새로 만든 객체는 크기 0이다).
3. `mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0)`: 내 주소 공간에 붙인다(A5). **`MAP_SHARED`여야** 상대가 쓴 것이 보인다.

`shm_unlink()`는 이름만 지운다. 이미 매핑한 프로세스는 계속 쓸 수 있고, 마지막 매핑이 사라지면 메모리가 반환된다(파일의 unlink와 같은 규칙).

### 5.2 예제 9 — 정말 같은 물리 페이지인가

무엇을 확인하는 코드인가: 부모와 자식이 **서로 다른 가상 주소**로 같은 shm을 매핑했을 때 물리 페이지 번호(PFN)가 같은지. `/proc/self/pagemap`에서 PFN을 읽으려면 root가 필요해서 `sudo`로 실행한다.

```c
/* 예제 9: shm = 같은 물리 페이지를 두 프로세스가 각자 다른 가상주소로 매핑 (root로 실행) */
#include <fcntl.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>

static void die(const char *m) { perror(m); exit(1); }

static uint64_t pfn_of(void *va) {                  /* /proc/self/pagemap: 페이지당 8바이트 */
    int fd = open("/proc/self/pagemap", O_RDONLY);
    uint64_t e;
    if (fd < 0 || pread(fd, &e, 8, (uintptr_t)va / 4096 * 8) != 8) die("pagemap");
    close(fd);
    return e & ((1ULL << 55) - 1);                  /* bit 0-54 = PFN */
}

static void report(const char *who, char *p) {
    char cmd[128];
    volatile char touch = p[0]; (void)touch;        /* 먼저 접근해서 page fault로 매핑 완성 */
    printf("%-6s pid=%d va=%p pfn=0x%llx data=\"%s\"\n", who, getpid(), (void *)p,
           (unsigned long long)pfn_of(p), p);
    snprintf(cmd, sizeof cmd, "grep frame_buf /proc/%d/maps", getpid());
    if (system(cmd) < 0) perror("system");
}

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);
    int fd = shm_open("/frame_buf", O_CREAT | O_RDWR, 0600);
    if (fd < 0 || ftruncate(fd, 4096) < 0) die("shm");
    char *p = mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (p == MAP_FAILED) die("mmap");
    strcpy(p, "written by parent");
    if (fork() == 0) {
        munmap(p, 4096);                            /* 일부러 다른 주소에 다시 매핑 */
        char *q = mmap(NULL, 3 * 4096, PROT_NONE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
        char *c = mmap(q + 4096, 4096, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_FIXED, fd, 0);
        if (q == MAP_FAILED || c == MAP_FAILED) die("mmap child");
        report("child", c);
        strcpy(c, "child overwrote it");
        _exit(0);
    }
    wait(NULL);
    report("parent", p);
    shm_unlink("/frame_buf");
    return 0;
}
```

### 5.3 예제 10 — shm 위의 SPSC 링버퍼 (센서 샘플)

Don이 펌웨어에서 수없이 짠 **single-producer/single-consumer 링버퍼**를 그대로 shm에 올린다. 규칙도 같다.

- `head`는 producer만, `tail`은 consumer만 쓴다 → 락이 필요 없다.
- 인덱스는 계속 증가하는 `uint32_t`, 슬롯은 `idx & (N-1)`(N은 2의 거듭제곱). `head - tail`이 원소 수다(오버플로해도 부호 없는 뺄셈이라 맞다).
- **메모리 순서**: producer는 슬롯을 다 쓴 **뒤에** head를 release store로 게시하고, consumer는 head를 acquire load로 읽은 **뒤에** 슬롯을 읽는다. ARM에서 이 순서가 깨지면 반쯤 쓴 샘플을 읽는다(F5). 펌웨어에서 DMB를 넣던 자리에 C11 `memory_order_release`/`acquire`가 들어간다고 보면 된다.
- `head`와 `tail`은 **다른 캐시라인**에 둔다(false sharing 방지 — 두 코어가 같은 라인을 번갈아 쓰면 라인이 계속 왔다갔다 한다).
- 가득 차면 **producer는 막히지 않고 버린다(drop)**. 센서 데몬은 실시간 루프라 느린 로거 때문에 멈추면 안 된다. 드롭 수는 카운터로 남긴다.
- consumer가 비었을 때 바쁘게 돌지 않도록 **process-shared 세마포어**(`sem_init(&sem, 1, 0)`의 1)로 잠재운다. 이 세마포어 자체도 shm 안에 있다.

```c
/* 예제 10: shm_open + mmap 위의 SPSC 링버퍼 (센서 샘플) + process-shared 세마포어 */
#include <fcntl.h>
#include <semaphore.h>
#include <stdatomic.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>

#define N 1024                       /* 2의 거듭제곱 → 인덱스 마스킹 */
#define TOTAL 1000000
struct sample { uint32_t seq; int16_t ax, ay, az; uint64_t ts; };
struct ring {
    _Atomic uint32_t head; char pad1[60];   /* producer만 씀, 캐시라인 분리 */
    _Atomic uint32_t tail; char pad2[60];   /* consumer만 씀 */
    sem_t items;                     /* consumer 잠재우기용 (pshared=1) */
    _Atomic uint32_t dropped, done;
    struct sample s[N];
};
static void die(const char *m) { perror(m); exit(1); }

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);
    int fd = shm_open("/imu_ring", O_CREAT | O_RDWR, 0600);
    if (fd < 0 || ftruncate(fd, sizeof(struct ring)) < 0) die("shm");
    struct ring *r = mmap(NULL, sizeof *r, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
    if (r == MAP_FAILED) die("mmap");
    if (sem_init(&r->items, 1, 0) < 0) die("sem_init");   /* 1 = 프로세스 간 공유 */
    if (system("ls -l /dev/shm/imu_ring") < 0) perror("system");

    if (fork() == 0) {                                     /* producer: IMU 드라이버 읽는 데몬 */
        for (uint32_t i = 0; i < TOTAL; i++) {
            if (i % 64 == 0) usleep(50);                   /* 센서 속도 흉내 */
            uint32_t h = atomic_load_explicit(&r->head, memory_order_relaxed);
            uint32_t t = atomic_load_explicit(&r->tail, memory_order_acquire);
            if (h - t == N) { atomic_fetch_add(&r->dropped, 1); continue; }  /* 가득: 버림 */
            r->s[h & (N - 1)] = (struct sample){ i, 1, 2, 3, i * 2500ULL };
            atomic_store_explicit(&r->head, h + 1, memory_order_release);   /* 게시 */
            sem_post(&r->items);
        }
        atomic_store(&r->done, 1); sem_post(&r->items); _exit(0);
    }
    uint32_t got = 0, gaps = 0, last = UINT32_MAX;         /* consumer: logger */
    for (;;) {
        sem_wait(&r->items);
        uint32_t t = atomic_load_explicit(&r->tail, memory_order_relaxed);
        if (t == atomic_load_explicit(&r->head, memory_order_acquire)) {
            if (atomic_load(&r->done)) break; else continue;
        }
        struct sample s = r->s[t & (N - 1)];
        atomic_store_explicit(&r->tail, t + 1, memory_order_release);    /* 슬롯 반납 */
        gaps += s.seq - last - 1; last = s.seq; got++;
        if (got % 50000 == 0) usleep(3000);                /* 가끔 느린 consumer */
    }
    wait(NULL); gaps += TOTAL - 1 - last;                              /* 끝부분 손실 */
    printf("received=%u dropped=%u gaps_seen=%u sum=%u\n", got, r->dropped, gaps, got + r->dropped);
    shm_unlink("/imu_ring"); return 0;
}
```

출력에서 볼 것: `/dev/shm/imu_ring`이 정확히 `sizeof(struct ring)` = 24744바이트 파일로 보인다. consumer가 5만 개마다 3 ms씩 멈추는 동안 링(1024칸)이 넘쳐 약 1%가 버려졌고, **consumer가 seq 구멍으로 센 손실(gaps_seen)과 producer의 드롭 카운터가 정확히 같다.** 즉 찢어진 샘플이나 중복 없이 순서대로 전달됐다. 드롭 수는 매번 다르다(스케줄링에 따라 다름).

실제로 만들면서 밟은 함정 하나: 처음엔 "센서 속도 흉내"용 `usleep`을 루프 **끝**에 뒀는데, 가득 찼을 때 `continue`가 그 줄을 건너뛰어 producer가 남은 샘플을 순식간에 전부 버렸다(드롭 85%). 실제 센서는 consumer가 느리다고 빨라지지 않으니 페이싱은 루프 맨 앞에 둬야 한다. 테스트 하네스의 타이밍 모델이 현실과 다르면 숫자가 엉터리가 된다는 교훈이다.

설계 메모:

- 실제 장비라면 producer는 `sem_post` 대신 **eventfd**(A4)에 write하고 consumer는 epoll로 기다리는 경우가 많다. 그러면 consumer가 소켓·타이머와 함께 한 루프에서 기다릴 수 있다. eventfd는 fd라서 SCM_RIGHTS로 넘길 수도 있다.
- 샘플마다 깨우면 wakeup 비용(8절에서 측정: 수십 µs)이 든다. 실무에서는 "N개 모이면" 또는 "1 ms마다" 깨우는 **배치 통지**로 비용을 줄인다. 펌웨어의 인터럽트 coalescing과 같다.
- **reader가 여럿**이면 SPSC가 깨진다. 방법은 둘: reader마다 링을 따로 두거나, 하나의 링에 reader별 tail을 두고 producer가 가장 느린 tail 기준으로 가득 참을 판단한다(또는 seqlock 방식으로 "덮어쓰기 + reader가 seq로 유효성 검사").

### 5.4 예제 11 — 락을 쥔 채 죽으면? robust mutex

shm 안에 `pthread_mutex_t`를 두고 `PTHREAD_PROCESS_SHARED`로 초기화하면 프로세스 간 락이 된다. 문제는 **락을 쥔 프로세스가 죽을 때**다. pipe·소켓은 커널이 fd를 닫아 주니 상대가 EOF를 받지만, shm 안의 락은 그냥 메모리 값이라 아무도 풀어 주지 않는다.

무엇을 확인하는 코드인가: 자식이 락을 쥔 채 SIGKILL로 죽었을 때 일반 mutex와 robust mutex가 어떻게 다른지.

```c
/* 예제 11: process-shared robust mutex — 락을 쥔 프로세스가 죽으면? */
#include <errno.h>
#include <pthread.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <unistd.h>

struct shared { pthread_mutex_t m; int calib_version; };
static void die(const char *m, int e) { fprintf(stderr, "%s: %s\n", m, strerror(e)); exit(1); }

static struct shared *make(int robust) {
    struct shared *s = mmap(NULL, sizeof *s, PROT_READ | PROT_WRITE,
                            MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (s == MAP_FAILED) { perror("mmap"); exit(1); }
    pthread_mutexattr_t a;
    pthread_mutexattr_init(&a);
    pthread_mutexattr_setpshared(&a, PTHREAD_PROCESS_SHARED);
    if (robust) pthread_mutexattr_setrobust(&a, PTHREAD_MUTEX_ROBUST);
    int e = pthread_mutex_init(&s->m, &a);
    if (e) die("mutex_init", e);
    return s;
}

static void trial(int robust) {
    struct shared *s = make(robust);
    pid_t c = fork();
    if (c == 0) {                       /* 업데이트 도중 크래시하는 프로세스 */
        pthread_mutex_lock(&s->m);
        s->calib_version = 7;
        raise(SIGKILL);
    }
    waitpid(c, NULL, 0);
    printf("[%s] child killed while holding lock\n", robust ? "ROBUST " : "DEFAULT");
    struct timespec ts;
    clock_gettime(CLOCK_REALTIME, &ts);
    ts.tv_sec += 1;
    int e = pthread_mutex_timedlock(&s->m, &ts);
    printf("  timedlock -> %s\n", e ? strerror(e) : "0 (locked)");
    if (e == EOWNERDEAD) {              /* 데이터 검증 후 consistent 선언 */
        printf("  calib_version=%d, validating... mark consistent\n", s->calib_version);
        pthread_mutex_consistent(&s->m);
        pthread_mutex_unlock(&s->m);
        e = pthread_mutex_lock(&s->m);
        printf("  lock again -> %s\n", e ? strerror(e) : "0 (locked)");
    }
}

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);
    trial(0);
    trial(1);
    return 0;
}
```

```text
[DEFAULT] child killed while holding lock
  timedlock -> Connection timed out
[ROBUST ] child killed while holding lock
  timedlock -> Owner died
  calib_version=7, validating... mark consistent
  lock again -> 0 (locked)
```

출력에서 볼 것: 일반 mutex는 **영원히 잠긴다**(1초 timeout = `ETIMEDOUT`, strerror 문자열이 "Connection timed out"이다). robust mutex는 다음 locker에게 **`EOWNERDEAD`("Owner died")** 를 돌려주며 락을 넘겨준다. 받은 쪽은 공유 데이터가 반쯤 갱신됐을 수 있으니(`calib_version=7`까지만 쓰고 죽었다) 검증하고 `pthread_mutex_consistent()`를 호출해야 한다. 안 부르고 unlock하면 그 mutex는 영구히 못 쓰게 된다(`ENOTRECOVERABLE`).

커널 쪽 구현: glibc가 스레드마다 "내가 쥔 robust 락 목록"을 `set_robust_list()` syscall로 커널에 등록해 두고, 스레드가 죽으면 커널이 그 목록을 따라가며 futex 값에 `FUTEX_OWNER_DIED` 비트를 세우고 기다리는 쪽을 깨운다(docs.kernel.org "Robust futexes"). 이것이 "shm은 크래시 동작을 직접 설계해야 한다"는 말의 구체적인 모습이다. SPSC 링처럼 **락 없는 설계**가 이 문제를 아예 피하는 이유이기도 하다.

### 6.1 System V IPC (legacy)

`shmget`/`shmat`, `msgget`/`msgsnd`, `semget`/`semop`는 1980년대 System V UNIX에서 온 옛 API다. 객체를 fd가 아니라 정수 키(`key_t`, 보통 `ftok()`)와 ID로 찾고, 그래서 **epoll에 못 넣고**, 명시적으로 지우기 전까지 남는다. 새 코드는 POSIX 쪽(`shm_open`, `mq_open`, `sem_open`)을 쓴다. 다만 오래된 산업용 소프트웨어나 일부 벤더 SDK가 아직 쓰므로 **보고 알아볼 수는 있어야** 한다.

예제 12 — 무엇을 확인하는 명령인가: SysV 객체를 만들고 `ipcs`로 보고 지우기.

### 6.2 D-Bus 미리보기 (L3에서 자세히)

D-Bus는 **메시지 버스**다. 버스 데몬(dbus-daemon 또는 dbus-broker)이 가운데 있고, 각 서비스가 UNIX socket으로 버스에 붙는다. 메시지 타입은 method call / return / error / signal(브로드캐스트)이고, 객체 경로·인터페이스·프로퍼티라는 객체 모델을 가진다. systemd, NetworkManager, BlueZ, ModemManager 같은 **시스템 서비스를 제어하는 표준 통로**다.

### 6.3 더 높은 층: ROS 2/DDS, ZeroMQ (이름만)

- **ROS 2**: 로보틱스 공통어(Q6). 노드가 토픽에 publish/subscribe한다. 아래는 DDS 미들웨어(UDP 멀티캐스트 기반 발견·전송)이고, 같은 머신 안에서는 구현에 따라 shm 전송(예: Fast DDS의 SHM transport, iceoryx 기반 zero-copy)을 쓴다. 결국 이 노트의 소켓과 shm이다.
- **ZeroMQ**: 소켓 위의 메시징 라이브러리. PUB/SUB, REQ/REP, PUSH/PULL 패턴과 자동 재연결·프레이밍을 준다. `ipc://` 전송은 UNIX domain socket이다.

면접에서는 "ROS 2를 쓰면 IPC를 신경 안 써도 되나?" 같은 질문이 나온다. 답: 직렬화·복사·발견(discovery) 비용이 붙고, 지연·지터가 중요한 경로(모터 제어 루프)는 같은 프로세스 안이나 shm으로 내린다.

1. **제어·명령·상태**: UNIX socket(SEQPACKET이면 프레이밍도 공짜). 시스템 서비스와 대화할 때는 D-Bus.

## 8. 직접 재 보기 — pipe vs UNIX socket vs shm

### 8.1 처리량 (예제 14)

무엇을 확인하는 코드인가: 한 방향으로 64 B 메시지(64 MiB 분량)와 64 KiB 메시지(1 GiB 분량)를 흘려보낼 때의 처리량. pipe는 기본 64 KiB와 1 MiB(`pipe1m`)로 두 번 잰다. shm은 64칸 링에 memcpy로 넣고 빼며, 기다릴 때는 spin한다(코어가 남는 경우의 상한).

```c
/* 예제 14: 처리량 — pipe vs UNIX stream socket vs shm 링(spin) / 사용법: ./tp <mech> <msg_bytes> */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdatomic.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

#define SLOTS 64
struct ring { _Atomic uint64_t head; char p1[56]; _Atomic uint64_t tail; char p2[56]; char d[]; };
static void die(const char *m) { perror(m); exit(1); }
static double now(void) {
    struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t); return t.tv_sec + t.tv_nsec / 1e9;
}

int main(int argc, char **argv) {
    if (argc != 3) return 2;
    const char *mech = argv[1];  static char buf[65536];
    size_t sz = atol(argv[2]), total = (size_t)(sz < 1024 ? 64 : 1024) << 20;  long n = total / sz;
    int fd[2] = { -1, -1 };  struct ring *r = NULL;
    if (!strncmp(mech, "pipe", 4)) {                     /* "pipe1m" = 1 MiB 파이프 */
        if (pipe(fd) < 0 || (mech[4] && fcntl(fd[1], F_SETPIPE_SZ, 1 << 20) < 0)) die("pipe");
    }
    else if (!strcmp(mech, "sock")) { if (socketpair(AF_UNIX, SOCK_STREAM, 0, fd) < 0) die("sp"); }
    else if ((r = mmap(NULL, sizeof *r + SLOTS * sz, PROT_READ | PROT_WRITE,
                       MAP_SHARED | MAP_ANONYMOUS, -1, 0)) == MAP_FAILED) die("mmap");
    double t0 = now();
    if (fork() == 0) {                                   /* producer */
        memset(buf, 0x5a, sizeof buf);
        for (long i = 0; i < n; i++) {
            if (!r) { if (write(fd[1], buf, sz) != (ssize_t)sz) die("write"); continue; }
            uint64_t h = atomic_load_explicit(&r->head, memory_order_relaxed);
            while (h - atomic_load_explicit(&r->tail, memory_order_acquire) == SLOTS) {}
            memcpy(r->d + (h % SLOTS) * sz, buf, sz);
            atomic_store_explicit(&r->head, h + 1, memory_order_release);
        }
        _exit(0);
    }
    if (r) {                                             /* consumer */
        for (long i = 0; i < n; i++) {
            while (atomic_load_explicit(&r->head, memory_order_acquire) == (uint64_t)i) {}
            memcpy(buf, r->d + (i % SLOTS) * sz, sz);
            atomic_store_explicit(&r->tail, i + 1, memory_order_release);
        }
    } else {
        close(fd[1]);
        ssize_t k;                                       /* 있는 만큼 한 번에 읽는다 */
        for (size_t got = 0; got < total; got += k)
            if ((k = read(fd[0], buf, sizeof buf)) <= 0) die("read");
    }
    wait(NULL);  double dt = now() - t0;
    printf("%-6s %6zu B  %8.0f MB/s  %7.3f Mmsg/s\n", mech, sz, total / dt / 1e6, n / dt / 1e6);
    return 0;
}
```

그림 5 — 측정 처리량(로그 스케일). Lima VM(aarch64, 4 vCPU, kernel 7.0)에서 잰 값이다. 세 번 반복해도 순위와 대략적인 크기는 같았다(pipe 64 KiB는 1.6~2.1 GB/s로 가장 많이 흔들렸다).

읽는 법:

- **64 B**: pipe·socket은 메시지당 syscall 1번(writer) + 커널 복사 2번이 고정 비용이다. 초당 2~3백만 메시지에서 막힌다. shm은 syscall이 없어서 약 5~8배 빠르다. 작은 메시지가 많으면 **syscall 횟수가 병목**이다 — 펌웨어에서 바이트마다 인터럽트를 받던 UART를 DMA로 바꾸던 것과 같은 이야기다. 소켓 쪽 개선책은 배치(여러 샘플을 한 write로) 또는 `sendmmsg`다.
- **64 KiB**: 기본 pipe(64 KiB)는 **메시지 하나가 pipe 전체**라서 writer와 reader가 매번 번갈아 잠들고 깬다. pipe를 1 MiB로 키우기만 해도 4배 빨라졌다. 이 VM에서는 UNIX stream socket(송신 버퍼 기본 `wmem_default` = 212992)이 pipe보다 빨랐는데, 커널 버전·버퍼 크기·CPU에 따라 순위가 바뀔 수 있으니 **자기 보드에서 재는 것**이 답이다.
- **shm**은 64 KiB에서도 가장 빠르지만 0-copy가 아니라 memcpy 2번(넣기·빼기)을 했다. 진짜 0-copy는 consumer가 슬롯을 **제자리에서** 처리하거나 버퍼 자체(memfd/dmabuf)를 넘기는 것이다.

### 8.2 지연 (예제 15)

무엇을 확인하는 코드인가: ping-pong 왕복 시간(RTT). 부모가 메시지를 보내면 자식이 받아서 그대로 돌려보낸다. shm은 두 가지로 잰다: `shm_spin`(상대를 계속 폴링)과 `shm_sem`(process-shared 세마포어로 잠들고 깨우기 = futex).

```c
/* 예제 15: 왕복 지연(ping-pong) — pipe / sock / shm+spin / shm+sem. ./lat <mech> <bytes> */
#include <semaphore.h>
#include <stdatomic.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/socket.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

#define N 20000
struct box { _Atomic int seq; sem_t sem; char d[65536]; };   /* 방향별 우편함 */
static void die(const char *m) { perror(m); exit(1); }
static double now(void) {
    struct timespec t; clock_gettime(CLOCK_MONOTONIC, &t); return t.tv_sec * 1e6 + t.tv_nsec / 1e3;
}
static const char *mech; static size_t sz; static int use_sem; static int rd[2], wr[2]; static struct box *bx;
static char buf[65536];

static void tx(int side, int seq) {                 /* side 0: parent→child, 1: child→parent */
    if (bx) {
        struct box *b = &bx[side];
        memcpy(b->d, buf, sz);
        atomic_store_explicit(&b->seq, seq, memory_order_release);
        if (use_sem) sem_post(&b->sem);             /* futex로 상대 깨우기 */
    } else if (write(wr[side], buf, sz) != (ssize_t)sz) die("write");
}
static void rx(int side, int seq) {
    if (bx) {
        struct box *b = &bx[side];
        if (use_sem) sem_wait(&b->sem);             /* 아니면 계속 spin */
        while (atomic_load_explicit(&b->seq, memory_order_acquire) != seq) {}
        memcpy(buf, b->d, sz);
    } else for (size_t got = 0; got < sz;) {        /* 스트림: sz 바이트 다 모을 때까지 */
        ssize_t k = read(rd[side], buf + got, sz - got);
        if (k <= 0) die("read"); else got += k;
    }
}
static int cmp(const void *a, const void *b) { double x = *(double *)a, y = *(double *)b; return (x > y) - (x < y); }

int main(int argc, char **argv) {
    if (argc != 3) return 2;
    mech = argv[1]; sz = atol(argv[2]); use_sem = !strcmp(mech, "shm_sem");
    int a[2], b[2];
    if (!strcmp(mech, "pipe")) { if (pipe(a) || pipe(b)) die("pipe"); rd[0] = a[0]; wr[0] = a[1]; rd[1] = b[0]; wr[1] = b[1]; }
    else if (!strcmp(mech, "sock")) { if (socketpair(AF_UNIX, SOCK_STREAM, 0, a)) die("sp"); wr[0] = rd[1] = a[0]; wr[1] = rd[0] = a[1]; }
    else {
        bx = mmap(NULL, 2 * sizeof *bx, PROT_READ | PROT_WRITE, MAP_SHARED | MAP_ANONYMOUS, -1, 0);
        if (bx == MAP_FAILED || sem_init(&bx[0].sem, 1, 0) || sem_init(&bx[1].sem, 1, 0)) die("shm");
    }
    if (fork() == 0) { for (int i = 1; i <= N; i++) { rx(0, i); tx(1, i); } _exit(0); }
    static double lat[N];
    for (int i = 1; i <= N; i++) { double t = now(); tx(0, i); rx(1, i); lat[i - 1] = now() - t; }
    wait(NULL);
    qsort(lat, N, sizeof lat[0], cmp);
    printf("%-8s %6zu B  RTT median %7.2f us  p99 %7.2f us\n", mech, sz, lat[N / 2], lat[N * 99 / 100]);
    return 0;
}
```

출력에서 볼 것: 같은 CPU에서는 RTT가 27 µs → 1.8 µs로 15배 줄었다. 즉 앞의 27 µs는 거의 전부 **다른 CPU에서 잠든 상대를 깨우는 비용**(IPI + idle 상태 탈출 + 스케줄링)이고, 이 VM에서는 vCPU가 하이퍼바이저 위에서 잠들기 때문에 특히 크다. bare-metal 보드에서는 보통 이보다 훨씬 작지만, 구조는 같다. 실무 결론:

- 저지연이 필요한 경로는 **spin(busy-poll) + 전용 코어**(`isolcpus`, N2)로 깨우기 자체를 없앤다. 대가는 코어 하나를 100% 쓰는 것이다.
- 아니면 깨우는 **횟수**를 줄인다(배치 통지).
- p99(꼬리 지연)가 중앙값보다 중요할 때가 많다. RT 튜닝(N2, N3)에서 다시 다룬다.
- 측정 해상도: arm64의 `CLOCK_MONOTONIC`은 이 VM에서 약 42 ns 단위(24 MHz 카운터)라 0.12 µs 같은 값은 몇 tick 수준이다.

## 9. 커널 안에서는 무슨 일이 일어나나

### 9.1 pipe = `pipe_inode_info` 안의 페이지 링

`pipe()`는 pipefs라는 가상 파일시스템에 inode 하나를 만들고, 그 inode에 `struct pipe_inode_info`를 단다(`fs/pipe.c`, `include/linux/pipe_fs_i.h`). 핵심 필드:

- `bufs`: `struct pipe_buffer` 배열(기본 16개 = `PIPE_DEF_BUFFERS`). 각 원소가 `page`, `offset`, `len`, `ops`를 가진다 — 즉 **페이지 하나를 가리키는 슬롯**.
- `head`, `tail`: 링 인덱스. 계속 증가하고 `& (ring_size - 1)`로 슬롯을 고른다. 위 5.3절의 SPSC 링과 같은 규칙이다(커널 5.5부터 이 형태).
- `rd_wait`, `wr_wait`: reader/writer가 잠드는 wait queue(F3).
- `mutex`: pipe 하나에 대한 락. 여러 writer가 동시에 와도 이 락 때문에 PIPE_BUF 이하 write가 원자적이다.

`write()`의 경로는 이렇다: `write()` → `ksys_write()` → `vfs_write()` → `file->f_op->write_iter` = `pipe_write()`. `pipe_write()`는 마지막 슬롯의 페이지에 자리가 있으면 거기에 이어 붙이고(merge), 아니면 새 페이지를 할당해 head 슬롯에 단다. 슬롯이 다 찼으면 `wr_wait`에서 잠든다. reader 쪽 `pipe_read()`는 tail 슬롯에서 `copy_page_to_iter()`로 복사하고, 그 페이지의 `len`이 0이 되면 페이지를 놓고 tail을 증가시킨다. 예제 1에서 "100바이트 읽어도 못 쓰고, 4096바이트 다 읽어야 쓸 수 있던" 현상이 정확히 이 동작이다.

pipe 페이지는 실제 `struct page`라서, `splice()`/`vmsplice()`로 복사 없이 페이지를 파일·소켓과 주고받을 수도 있다(고급 주제).

### 9.2 UNIX socket = socket 계층 + sk_buff 큐

`socket(AF_UNIX, ...)`은 sockfs inode와 `struct socket` + `struct sock`을 만든다(`net/unix/af_unix.c`). `send()` → `sock_sendmsg()` → `unix_stream_sendmsg()`(또는 `unix_dgram_sendmsg`, `unix_seqpacket_sendmsg`)가 **`sk_buff`를 할당해 데이터를 복사하고 상대 소켓의 `sk_receive_queue`에 직접 넣은 뒤** 상대를 깨운다. TCP와 달리 IP 계층이 없고, 송신 버퍼 계정(`sk_sndbuf`)만 한다. `recv()`는 그 큐에서 skb를 꺼내 유저 버퍼로 복사한다. 메시지 경계는 skb 단위로 지켜진다(SEQPACKET/DGRAM은 skb 하나 = 메시지 하나, STREAM은 skb들을 이어 붙여 읽는다).

SCM_RIGHTS는 이 skb에 **`struct scm_fp_list`(struct file 포인터 배열)** 를 붙인다(`net/core/scm.c`). 보낼 때 각 file의 참조 카운트를 올리고, 받을 때 받는 프로세스의 fd 테이블에 새 fd를 설치한다(그림 3). 아무도 안 받은 채 소켓끼리 서로를 가리키는 순환이 생길 수 있어서, 커널에는 in-flight fd를 위한 전용 garbage collector(`unix_gc`)도 있다. 함수 이름은 커널 버전에 따라 조금씩 바뀌었으니 소스는 elixir에서 자기 버전으로 확인하자.

그림 8 — 세 방식의 데이터 경로 비교. 위 두 방식은 커널 객체를 거쳐 두 번 복사하고, shm은 MMU 설정만 커널이 한다.

`shm_open()`은 glibc가 `/dev/shm/<name>`을 `open()`하는 것이고, `/dev/shm`은 tmpfs(`mm/shmem.c`)다. `mmap(MAP_SHARED)`는 각 프로세스에 `vm_area_struct`를 만들고 `vm_file`이 같은 shmem 파일을 가리키게 한다. 처음 접근 때 page fault → `shmem_fault()`가 그 파일의 page cache에서 페이지(folio)를 찾거나 만들고 → 각 프로세스의 PTE에 같은 PFN을 써 넣는다. 예제 9에서 PFN이 같았던 이유다. POSIX mq는 `ipc/mqueue.c`의 mqueue 파일시스템이고 메시지를 커널 메모리에 우선순위별 트리로 보관한다(복사 2번).

process-shared 동기화 객체는 **futex**(A8)다. `sem_post`/`pthread_mutex_unlock`은 경쟁이 없으면 원자 연산만으로 끝나고(syscall 없음), 상대가 기다리고 있을 때만 `futex(FUTEX_WAKE)` syscall을 부른다. 공유 매핑의 futex는 커널이 **(inode/page, offset)** 으로 식별하고, 프로세스 전용(`FUTEX_PRIVATE_FLAG`)은 **(mm, 가상 주소)** 로 식별한다. 그래서 process-shared가 아닌 mutex를 shm에 두면 다른 프로세스와 서로를 못 깨운다 — `pthread_mutexattr_setpshared(PTHREAD_PROCESS_SHARED)`가 필수인 이유다.

### 9.4 드라이버를 쓸 때 다시 만나는 곳

| 유저 IPC에서 본 것 | 드라이버/커널에서 다시 만나는 곳 | 모듈 |
|---|---|---|
| pipe의 `rd_wait`/`wr_wait`에서 잠들고 깨우기 | 드라이버의 blocking `read()`: `wait_event_interruptible()` + ISR의 `wake_up()` | F3, G4 |
| pipe 링의 head/tail | `kfifo`, IIO buffered capture의 링 | I2 |
| 페이지 단위 링, `copy_to_user` | 드라이버 `.read`에서 `copy_to_user()` | G4 |
| fd가 epoll에서 깨어나는 것 | 드라이버 `.poll` + `poll_wait()` | G6, A4 |
| shm = 같은 페이지 두 번 매핑 | 드라이버 `.mmap` + `remap_pfn_range()`로 장치 메모리를 유저에 노출 | G5 |
| SCM_RIGHTS로 넘기는 dmabuf fd | `dma_buf_export()`/`dma_buf_get()`, V4L2 `VIDIOC_EXPBUF`, videobuf2 | I5, Q2 |
| head/tail release·acquire | `smp_store_release()`/`smp_load_acquire()`, DMA 디스크립터 링 | F5 |
| robust futex | 커널 `futex` 서브시스템 | A8, F4 |

## 10. Embedded 실무에서 다시 보기

### 장면 1 — 센서 데몬과 로거: shm 링 + eventfd, 드롭은 숫자로

예를 들어 센서 키트에서 imu_daemon(SCHED_FIFO, 400 Hz~1 kHz)이 로거·퓨전 프로세스에 샘플을 넘긴다. 설계: 소비자마다 SPSC 링(shm), producer는 절대 막히지 않고 가득 차면 드롭 + 카운터, 소비자는 eventfd를 epoll로 기다리고 producer는 10개 또는 10 ms마다 eventfd에 write한다. 샘플에는 seq와 `CLOCK_MONOTONIC` 타임스탬프(Q3)를 넣어 소비자가 손실·지터를 직접 측정한다(Q7). 예제 10의 `gaps_seen == dropped` 검사가 바로 그 데이터 품질 도구의 핵심이다.

### 장면 2 — 카메라: 프레임은 fd로, 메타데이터는 소켓으로

camera_daemon이 V4L2 버퍼를 `VIDIOC_EXPBUF`로 dmabuf fd로 만들고, SEQPACKET 소켓으로 `{frame_id, timestamp, format}` 메시지 + SCM_RIGHTS fd를 인코더와 추론 프로세스에 보낸다. 받은 쪽은 처리 후 "frame_id 반납" 메시지를 돌려보내고 fd를 닫는다. 3 MB 프레임이 한 번도 복사되지 않는다. 버그 패턴: 반납 메시지를 빼먹으면 V4L2 큐에 버퍼가 안 돌아와 몇 프레임 뒤에 캡처가 멈춘다(`VIDIOC_DQBUF`가 안 깨어남) — 리소스 반납 프로토콜이 IPC 설계의 절반이다.

### 장면 3 — 제어 채널: UNIX socket + SO_PEERCRED

진단 툴(`sensorctl`)이 데몬에게 "샘플레이트 변경" 같은 명령을 보낸다. `/run/sensor/ctl.sock`(그룹 `sensor`, 0660) + SEQPACKET + 요청마다 `SO_PEERCRED`로 uid 확인. root가 아닌 사용자는 읽기 명령만 허용. 데몬이 재시작해도 클라이언트는 EOF/ECONNRESET을 받고 재접속한다.

### 장면 4 — 시스템 통합: D-Bus는 제어, 데이터는 따로

LTE 모뎀 상태는 ModemManager에 D-Bus로 묻고, 네트워크 설정은 NetworkManager/systemd-networkd에 D-Bus로 요청한다(L3). 텔레메트리 데이터 자체는 uploader가 소켓으로 직접 보낸다. "D-Bus에 센서 데이터를 싣자"는 제안이 나오면 6.2절의 이유로 반대할 수 있어야 한다.

## 12. 면접에서 이렇게 말한다

**Q.** "What IPC mechanisms does Linux provide, and how do you choose between them?"

**A.** 바이트 스트림(pipe, FIFO, UNIX stream socket), 메시지(UNIX SEQPACKET/DGRAM, POSIX mq), 공유 메모리(POSIX shm, memfd/dmabuf), 그리고 그 위의 버스(D-Bus)로 나눈다. 고르는 기준은 복사 횟수, 메시지 경계, 깨우기 비용, 다중 수신자, 크래시 시 동작이다. 제어는 UNIX socket, 고속 데이터는 shm 링, 큰 버퍼는 fd 전달, 시스템 서비스는 D-Bus.

> I group them into byte streams — pipes, FIFOs, UNIX stream sockets — message-oriented ones like SEQPACKET sockets and POSIX message queues, and shared memory, with D-Bus on top for system services. I choose by copies, message boundaries, wake-up cost, fan-out, and what happens when one side crashes. In practice: UNIX sockets for control, a shared-memory ring for high-rate sensor data, and fd passing for large buffers like camera frames.

**꼬리 질문**: "Why not just use TCP on localhost?" → 동작은 하지만 IP 스택 비용이 있고, SO_PEERCRED·SCM_RIGHTS·파일 권한 기반 접근 제어가 없다.

**Q.** "Why is shared memory the fastest IPC, and what's the catch?"

**A.** 커널이 MMU 설정만 하고 데이터 경로에서 빠지니까 syscall도 복사도 없다. 대가는 동기화·메모리 순서·통지·크래시 처리를 전부 직접 해야 한다는 것. 그리고 측정해 보면 상대를 futex로 깨우는 순간 지연은 pipe와 같아진다 — 빠른 건 복사가 없어서지 wakeup이 빨라서가 아니다.

> The kernel only sets up the page tables; after that it's plain loads and stores, so no syscalls and no copies. The catch is you own synchronization, memory ordering, notification and crash recovery. And when I measured it, shared memory with a semaphore wake-up had the same round-trip latency as a pipe — about 27 microseconds on my VM — while busy-polling was 0.1 microseconds. The win is fewer copies, not faster wake-ups.

**꼬리 질문**: "What if the process holding the lock dies?" → robust mutex(`EOWNERDEAD` → 검증 → `pthread_mutex_consistent`) 또는 락 없는 SPSC 설계.

**Q.** "How would you pass a camera frame to another process without copying?"

**A.** V4L2 버퍼를 `VIDIOC_EXPBUF`로 dmabuf fd로 내보내고, UNIX socket의 SCM_RIGHTS로 그 fd를 보낸다. 커널은 struct file 참조를 넘기고 받는 쪽에 새 fd를 설치한다. 받는 쪽은 mmap하거나 GPU/인코더에 import한다. 버퍼 반납 프로토콜과 fd close를 같이 설계한다.

> Export the V4L2 buffer as a dma-buf file descriptor with VIDIOC_EXPBUF, then send that fd over a UNIX domain socket using SCM_RIGHTS. The kernel passes a reference to the same struct file and installs a new fd number in the receiver, which can mmap it or import it into the encoder or GPU. The frame is never copied, but you need a clear return protocol so buffers go back to the capture queue.

**Q.** "What happens when you write to a pipe? What's PIPE_BUF?"

**A.** pipe는 커널 안 페이지 링(기본 16페이지, 64 KiB)이다. write는 유저 데이터를 그 페이지에 복사하고 reader를 깨운다. 가득 차면 writer가 잠든다. PIPE_BUF(Linux 4096) 이하 write는 원자적이라 여러 writer가 있어도 안 섞인다. 넘으면 섞일 수 있다 — 직접 재 보니 4097바이트에서 바로 찢어졌다. reader가 없으면 SIGPIPE/EPIPE.

> A pipe is a ring of page-sized buffers in the kernel, 64 KiB by default. write copies into those pages and wakes the reader; if it's full the writer sleeps. Writes up to PIPE_BUF, 4096 bytes on Linux, are atomic, so concurrent writers don't interleave; above that they can — I saw torn records at 4097 bytes. Writing with no readers gives SIGPIPE or EPIPE.

**Q.** "How do you frame messages over a stream socket?"

**A.** 스트림은 경계가 없어서 send 3번이 recv 1번으로 올 수도, 그 반대일 수도 있다. 길이 프리픽스(고정 크기 헤더 + 본문)를 두고, 정확히 n바이트를 다 읽을 때까지 루프 돈다. 로컬이면 SEQPACKET으로 커널이 경계를 지키게 하는 방법도 있다.

> A stream has no boundaries — three sends can arrive as one recv or one send as several. I use a length prefix, a fixed header followed by the payload, and a read-exactly-n loop that handles short reads. For local IPC, SOCK_SEQPACKET gives you reliable, ordered messages with boundaries preserved by the kernel.

**Q.** "Design the IPC for a robot with an IMU daemon, a camera daemon, a logger and an uploader."

**A.** IMU → 소비자별 SPSC shm 링 + eventfd 배치 통지, 가득 차면 드롭 + 카운터. 카메라 → dmabuf fd를 SEQPACKET + SCM_RIGHTS로, 반납 메시지로 버퍼 순환. 제어·상태 → UNIX socket + SO_PEERCRED. 프로세스 분리로 장애 격리·권한 분리, systemd가 재시작. 모든 메시지에 seq와 모노토닉 타임스탬프를 넣어 손실·지연을 측정한다.

> High-rate IMU samples go through a per-consumer single-producer single-consumer ring in shared memory, with eventfd notifications batched, and the producer never blocks — it drops and counts. Camera frames are passed as dma-buf fds over a SEQPACKET socket with SCM_RIGHTS, with an explicit release message. Control and health use UNIX sockets with SO_PEERCRED checks. Each daemon is a separate process for fault isolation and least privilege, restarted by systemd, and every message carries a sequence number and a monotonic timestamp so we can measure loss and latency.

**Q.** "When would you use D-Bus, and when not?"

**A.** 시스템 서비스(NetworkManager, systemd, BlueZ)와 대화하거나, 서비스 발견·타입 있는 메서드 호출·브로드캐스트 시그널이 필요할 때. 버스 데몬을 거치고 직렬화가 있어서 초당 수천 메시지 이상의 데이터 경로에는 안 쓴다.

> For talking to system services — systemd, NetworkManager, BlueZ — and for low-rate control with discovery, typed method calls and broadcast signals. Every message goes through the bus daemon and gets marshalled, so I don't put sensor or video data on it; at most I negotiate over D-Bus and pass an fd for the bulk data.

## 14. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| IPC | Inter-Process Communication | 주소 공간이 다른 프로세스끼리 데이터·이벤트를 주고받는 방법 |
| pipe | 익명 단방향 바이트 스트림 | 커널 페이지 링 + fd 두 개, fork로 물려받아 씀 |
| FIFO | named pipe | 파일시스템 이름이 있는 pipe, 상대가 열 때까지 open이 막힘 |
| PIPE_BUF | 원자적 write 상한 | Linux 4096바이트, 이하 크기 write는 섞이지 않음 |
| F_GETPIPE_SZ / F_SETPIPE_SZ | pipe 용량 조회·변경 | 기본 64 KiB, 상한은 `/proc/sys/fs/pipe-max-size` |
| UNIX domain socket | `AF_UNIX` 소켓 | 같은 호스트 전용 소켓, STREAM·DGRAM·SEQPACKET |
| SOCK_SEQPACKET | 순서·경계 보존 연결형 소켓 | 로컬 메시지 IPC에 프레이밍이 필요 없음 |
| abstract namespace | `sun_path[0] == '\0'`인 소켓 이름 | 파일이 안 생기는 Linux 전용 이름, `ss`에 `@`로 보임 |
| SO_PEERCRED | 상대 자격 증명 | connect 시점 상대의 pid/uid/gid를 커널이 보증 |
| SCM_RIGHTS | fd 전달 제어 메시지 | struct file 참조를 넘기고 받는 쪽에 새 fd 설치 |
| memfd | `memfd_create()` 메모리 파일 | 이름 없는 tmpfs 파일, fd로 공유·봉인(seal) 가능 |
| dmabuf | DMA 버퍼 공유 프레임워크 | 장치 버퍼를 fd로 내보내 다른 드라이버·프로세스가 import |
| POSIX mq | `mq_open` 메시지 큐 | 우선순위, 커널 지속성, `/dev/mqueue` |
| mq_notify | 큐 도착 통지 | 빈 큐에 메시지가 들어올 때 한 번 알림, 다시 등록 필요 |
| POSIX shm | `shm_open` + `mmap` | `/dev/shm` tmpfs 파일을 MAP_SHARED로 매핑 |
| SPSC ring | single-producer single-consumer 링버퍼 | head는 producer만, tail은 consumer만 써서 락 불필요 |
| process-shared | 프로세스 간 공유 속성 | shm 안 mutex/sem이 다른 프로세스와 동작하게 하는 속성 |
| robust mutex | 소유자 사망 감지 mutex | 소유자가 죽으면 다음 locker가 `EOWNERDEAD` 받음 |
| futex | fast userspace mutex | 경쟁 없으면 원자 연산, 기다릴 때만 syscall |
| System V IPC | `shmget`/`msgget`/`semget` | key·ID 기반 옛 API, 재부팅까지 남음, `ipcs`/`ipcrm` |
| D-Bus | 메시지 버스 | 시스템 서비스 제어용 IPC, 버스 데몬 경유 |
| framing | 메시지 경계 표시 | 스트림 위에 길이 헤더 등으로 메시지를 구분 |
| `pipe_inode_info` | 커널의 pipe 객체 | `bufs` 페이지 링, head/tail, rd_wait/wr_wait |
| `sk_buff` | 소켓 버퍼 | 소켓 데이터 한 덩어리, 수신 큐에 매달림 |

## 15. 요약 & 체크리스트

Embedded Linux 장비는 장애 격리와 권한 분리를 위해 기능을 프로세스로 쪼개고, 그 경계를 IPC로 넘는다. pipe/FIFO는 커널 페이지 링 위의 단방향 바이트 스트림이고(PIPE_BUF 이하만 원자적, EOF·SIGPIPE로 크래시가 깔끔), UNIX domain socket은 양방향·경계 보존(SEQPACKET)·자격 증명·**fd 전달**까지 되는 실무 주력이다. POSIX mq는 우선순위 우편함, POSIX shm은 같은 물리 페이지를 두 번 매핑해 복사를 없애지만 동기화·순서·통지·크래시 처리를 직접 설계해야 한다(SPSC 링 + release/acquire + futex/eventfd, robust mutex). D-Bus는 시스템 서비스 제어용이고 ROS 2/ZeroMQ는 이 위에 얹힌다. 직접 재 보면 작은 메시지는 syscall 수가, 큰 메시지는 복사가, 지연은 **상대를 깨우는 비용**이 지배한다.

- [ ] 프로세스를 나누는 이유 세 가지와 그 대가를 설명할 수 있다
- [ ] pipe가 커널 안에서 페이지 링(`pipe_inode_info`)이라는 것과 PIPE_BUF의 의미를 설명할 수 있다
- [ ] pipe/소켓에서 한쪽이 죽으면 무엇이 오는지(EOF, SIGPIPE/EPIPE) 말할 수 있다
- [ ] STREAM·SEQPACKET·DGRAM 소켓의 경계 차이를 말하고 길이 프리픽스 프레이밍을 코드로 짤 수 있다
- [ ] abstract namespace 소켓과 SO_PEERCRED를 쓸 수 있다
- [ ] SCM_RIGHTS로 fd를 넘기는 코드를 짜고, 카메라 dmabuf 공유에 어떻게 쓰이는지 설명할 수 있다
- [ ] POSIX mq의 우선순위·커널 지속성·mq_notify의 한계를 말할 수 있다
- [ ] shm_open + mmap 위에 SPSC 링버퍼를 release/acquire 순서로 짤 수 있다
- [ ] process-shared 속성과 robust mutex가 왜 필요한지 설명할 수 있다
- [ ] 선택 가이드 표의 기준(복사, 경계, 깨우기, 다중 reader, 크래시)으로 설계를 정당화할 수 있다
- [ ] "shm이 빠른 건 복사가 없어서지 wakeup이 빨라서가 아니다"를 측정값으로 말할 수 있다
- [ ] 각 IPC가 드라이버의 wait queue, `.poll`, `.mmap`, dmabuf와 어디서 연결되는지 말할 수 있다
