# C1. 부트 전체 지도 — 전원 ON부터 셸 프롬프트까지

> **이 노트를 다 읽으면**: BootROM → SPL → TF-A(BL1/BL2/BL31, BL32) → U-Boot(BL33) → kernel → initramfs → PID 1까지 각 단계가 "무엇을 초기화하고 무엇을 다음에게 넘기는지"를 EL·메모리 주소와 함께 그릴 수 있다 · QEMU 랩에서 TF-A+U-Boot 경로로 직접 부팅해 시리얼 로그를 단계별로 읽고 시간을 잴 수 있다 · DTB·cmdline이 넘어갔다는 증거를 게스트 안에서 `/proc/cmdline`, `/sys/firmware/devicetree`로 보여 줄 수 있다 · "walk me through the Linux boot process"에 30초·2분·딥다이브 세 길이로 답할 수 있다
> **왜 필요한가**: Embedded Linux 면접 1순위 질문이 "Linux 보드 부팅 과정을 설명해 보라"이고, 입사 첫 주에 만나는 버그가 "Starting kernel ... 이후 아무것도 안 나와요"다. 어느 단계가 무엇을 맡는지 모르면 어디서 멈췄는지조차 말할 수 없다
> **Don 기준 난이도**: 리셋 벡터, ROM 부트로더, SRAM에서 DRAM 초기화 후 메인 FW 로드, 서명 검증은 SSD 컨트롤러에서 이미 해 본 일이다 / 그 위에 얹히는 EL3·Secure world(TF-A), U-Boot, DTB 핸드오버, 커널의 initramfs와 PID 1이 새로 배울 부분
> **선행 노트**: A1(프로세스·syscall), B1(크로스 툴체인), B3(ELF와 링킹) — 이 노트는 모듈 C의 지도이고, 각 단계의 깊은 내용은 C2~C8로 넘긴다

## 0. 큰 그림 — 이게 왜 필요한가

Don이 SSD 컨트롤러에서 본 부팅은 이랬을 것이다. 전원이 들어오면 Cortex-R이 마스크 ROM의 리셋 벡터에서 출발하고, ROM 코드가 NAND(또는 SPI NOR)에서 부트로더를 읽어 내부 SRAM에 올린다. 부트로더가 DRAM 컨트롤러를 초기화하고, 메인 펌웨어 이미지를 DRAM으로 읽어 서명을 확인한 뒤 점프한다. **"작은 것이 조금 더 큰 것을 올리고, 그것이 더 큰 것을 올린다"** — 이 사슬 구조는 Linux 보드에서도 그대로다.

달라지는 점은 세 가지다.

- **단계가 더 많다.** 메인 펌웨어 자리에 Linux 커널이 오고, 그 앞에 범용 부트로더(U-Boot)가, 그 앞에 보안·전원 관리를 맡는 펌웨어(TF-A)가 끼어 있다. 커널 뒤에도 initramfs와 init(PID 1)이 있다.
- **특권 레벨이 내려간다.** ARMv8-A에는 Exception Level(EL)이 있다: EL3(가장 높음, Secure Monitor) → EL2(하이퍼바이저) → EL1(OS 커널) → EL0(유저 앱). 부팅은 EL3에서 시작해 단계마다 아래로 내려간다. 한 번 내려가면 위로는 예외(SMC·HVC)로만 다시 들어갈 수 있다. Cortex-R의 특권/유저 모드를 4층으로 늘린 것이라고 보면 된다.
- **"보드 설명서"를 같이 넘긴다.** SSD FW는 자기가 어느 보드에서 도는지 컴파일 타임에 알았다. Linux 커널 이미지 하나는 수백 가지 보드에서 돈다. 그래서 부트로더가 **Device Tree Blob(DTB)** — 이 보드에 어떤 메모리·UART·I2C가 어디 있는지 적은 이진 데이터 — 와 **커널 커맨드라인(cmdline)** 을 커널에 넘긴다. 이것이 "핸드오버"다.

그림 1 — 이 노트의 QEMU 랩에서 실제로 일어나는 부트 체인. 세로축은 Exception Level, 상자 안 주소는 각 단계가 실행되는 물리 주소(TF-A 빌드의 ELF와 U-Boot `bdinfo`에서 확인, §3). 실제 SoC에서는 BL1 자리를 칩의 BootROM이 차지하고, BL2 앞에 DDR을 초기화하는 SPL이 끼는 경우가 많다(§8).

한 문장으로 줄이면 이렇다: **"ROM이 SRAM에 들어갈 만큼 작은 로더를 올리고, 그 로더가 DRAM을 살린 뒤 보안 펌웨어와 U-Boot를 올리고, U-Boot가 커널·DTB·initramfs를 RAM에 놓고 점프하고, 커널이 하드웨어를 초기화한 뒤 첫 유저 프로세스 PID 1을 띄운다."**

Embedded Linux 엔지니어가 이 지도를 쓰는 장면은 이렇다.

- **bring-up 디버깅**: 새 보드에서 콘솔에 아무것도 안 나온다 → BootROM이 부트 미디어를 못 찾았나(C2), SPL이 DDR 초기화에서 죽었나(C4), U-Boot까지는 왔나(C3), 커널이 `Starting kernel ...` 뒤에 조용한가(C6)? 로그의 마지막 줄이 어느 단계 것인지 알아야 다음 수를 둔다.
- **부팅 시간 과제**: "카메라 장비가 전원 ON 후 3초 안에 영상을 내야 한다" — 단계별 시간을 재고(§7) 가장 큰 덩어리부터 줄인다(C7).
- **보안 질문**: "secure boot를 어떻게 구성하나?" — 체인의 각 단계가 다음 단계의 서명을 확인하는 chain of trust(C5).
- **전원 관리**: Linux가 CPU를 끄고 켤 때(`cpu_on`, suspend) 실제 일은 EL3의 BL31이 한다(PSCI). 부트 체인을 알아야 "왜 커널이 SMC를 부르나"가 이해된다.

## 1. 단계별로 — 누가 무엇을 초기화하고 무엇을 넘기나

### 1.1 한 장짜리 표

먼저 전체를 표 하나로 본다. 이 표가 이 노트의 뼈대다. "랩" 열은 이 노트의 QEMU 랩에 그 단계가 있는지다.

| 단계 | 어디서 실행되나 | EL | 초기화하는 것 | 다음에게 넘기는 것 | 코드·설정이 사는 곳 | 랩 |
|---|---|---|---|---|---|---|
| BootROM | SoC 마스크 ROM, 내부 SRAM | EL3 | 최소 클럭(기본 PLL), 부트 미디어 컨트롤러, 서명 검증 엔진 | 부트 미디어에서 읽은 첫 이미지(SPL 등)를 SRAM에 | 칩 안(수정 불가). 동작은 eFuse·boot pin으로 선택 | BL1이 대신 |
| TPL / SPL | 내부 SRAM (수십~수백 KB) | EL3 (SoC마다 다름) | **DDR 컨트롤러·PHY(트레이닝)**, PMIC 전압, 클럭 트리, UART pinmux | DRAM에 TF-A BL31·U-Boot(·OP-TEE)를 올림 | U-Boot 소스 `common/spl/`, `board/<vendor>/`, `<board>_defconfig`의 `CONFIG_SPL_*` | 없음 |
| TF-A BL1 | ROM(또는 flash) | EL3 | 예외 벡터, 보안 상태 기본값, 부트 미디어 접근 | BL2를 Secure SRAM에 로드 | TF-A `bl1/`, `plat/<soc>/` | 있음 |
| TF-A BL2 | Secure SRAM | S-EL1 (또는 EL3) | FIP 파싱, 인증서 체인 검증(TBBR), 일부 SoC는 DDR 초기화 | BL31·BL32·BL33을 정해진 주소로 | TF-A `bl2/`, `plat/<soc>/..._bl2_setup.c`, FIP(`fiptool`) | 있음 |
| TF-A BL31 | Secure SRAM/DRAM, **상주** | EL3 | GIC 보안 설정, PSCI·SMCCC 서비스, Secure Monitor | BL33으로 ERET(Non-secure로 전환) | TF-A `bl31/`, `services/std_svc/psci/`, `plat/<soc>/..._bl31_setup.c` | 있음 |
| BL32 (OP-TEE) | Secure DRAM, **상주** | S-EL1 | TEE OS, Trusted Application 실행 환경 | (BL31을 통해) 리눅스와 SMC로 대화 | OP-TEE `optee_os`, TF-A `SPD=opteed` | 없음 |
| U-Boot (BL33) | DRAM (자기 자신을 RAM 끝으로 재배치) | NS-EL2 (없으면 EL1) | driver model, 콘솔, 스토리지·네트워크, 환경변수 | 커널 Image·initramfs·DTB를 RAM에 놓고 `x0 = DTB`로 점프 | U-Boot `board/`, `configs/*_defconfig`, `arch/arm/dts/`, 환경(`bootcmd`, `bootargs`) | 있음 |
| Linux kernel | DRAM | EL1 (또는 EL2, VHE) | MMU·페이지 테이블, 메모리 관리, 인터럽트, 타이머, 드라이버 probe | rootfs를 마운트하고 `/init` 실행 | `arch/arm64/kernel/head.S`, `init/main.c`, `.config`, DTB | 있음 |
| initramfs | RAM 위 tmpfs (rootfs) | — | 커널이 cpio를 풀어 만든 첫 파일시스템 | 진짜 rootfs 마운트(`switch_root`) 또는 그대로 사용 | `init/initramfs.c`, Buildroot·Yocto가 만든 cpio | 있음 |
| init (PID 1) | 유저 공간 | EL0 | `/proc`·`/sys`·`/dev` 마운트, 서비스 시작 | 셸·로그인·애플리케이션 | BusyBox init, systemd, 이 랩은 셸 스크립트 `/init` | 있음 |

표를 세로로 읽으면 패턴이 보인다. **위로 갈수록 작고 고정되어 있고(ROM), 아래로 갈수록 크고 바꾸기 쉽다(rootfs).** 그리고 **"DRAM이 살아나는 시점"이 경계**다. DRAM이 살기 전 단계(BootROM, SPL)는 SRAM 크기 안에 들어가야 해서 기능이 최소다. Don이 SSD에서 "ROM 부트로더 → DRAM 초기화 → 메인 FW"로 나눈 이유와 같다.

### 1.2 BootROM — 칩이 태어날 때부터 가진 코드

- **정의**: SoC 안 마스크 ROM에 구워진 첫 코드. 리셋 후 CPU(대개 부트 전용 코어)가 여기서 시작한다.
- **하는 일**: boot mode pin과 eFuse를 읽어 부트 미디어(eMMC boot partition, SD, SPI NOR, NAND, USB 복구 모드)를 고르고, 정해진 위치에서 첫 이미지를 **내부 SRAM**으로 읽는다. secure boot가 켜져 있으면 eFuse에 박힌 공개키 해시로 이미지 서명을 검증한다.
- **하지 않는 일**: DDR 초기화는 보통 하지 않는다. DDR 종류·타이밍·보드 배선은 보드마다 다르기 때문에 ROM이 알 수 없다. 그래서 다음 단계(SPL)가 필요하다.
- **Don 연결**: SSD 컨트롤러 ROM이 NAND의 여러 사본 중 ECC가 통과하는 부트로더 사본을 찾는 것과 같은 역할이다. 고칠 수 없으므로 ROM의 "복구 경로"(USB SDP·DFU 같은 다운로드 모드)가 벽돌 복구의 마지막 보루다(C2).

### 1.3 SPL/TPL — DRAM을 살리는 작은 로더

- **SPL(Secondary Program Loader)**: U-Boot 소스에서 함께 빌드되는 축소판 U-Boot. SRAM에 들어가도록 필요한 드라이버만 넣는다. 핵심 임무는 **DDR 초기화**(컨트롤러 레지스터 설정 + PHY 트레이닝), PMIC로 코어·DDR 전압 설정, 클럭 트리, 콘솔 UART다. 그 다음 DRAM에 TF-A BL31과 U-Boot proper(+OP-TEE)를 올린다. 이 묶음은 흔히 FIT 이미지 하나로 들어 있다.
- **TPL(Tertiary Program Loader)**: SRAM이 너무 작아 SPL조차 안 들어가는 SoC에서 SPL 앞에 끼는 더 작은 단계. 어떤 SoC에서는 TPL이 DDR만 초기화하고 BootROM으로 돌아가 SPL을 다시 읽게 한다(SoC마다 다르다).
- **TF-A BL2와의 관계**: Arm의 참조 설계에서는 TF-A BL2가 이 "로더" 역할을 한다. 실제 SoC 벤더는 **U-Boot SPL이 BL2 역할을 대신**하는 경우(NXP i.MX8M, TI AM62의 A53 SPL)와 **TF-A BL2를 쓰는 경우**(일부 Renesas, STM32MP1의 TF-A BL2 등)로 갈린다. 이 랩은 SPL이 없고 TF-A BL1/BL2가 그 자리를 맡는다.

### 1.4 TF-A — EL3의 보안·전원 펌웨어

TF-A(Trusted Firmware-A)는 Arm이 주도하는 ARMv8-A용 참조 Secure-world 펌웨어다. 이름에 BL(Boot Loader stage)이 붙는다.

- **BL1 (AP Trusted ROM)**: 참조 설계에서 ROM에 들어가는 단계. 이 랩에서는 QEMU의 secure flash 0번지가 리셋 벡터이고 거기에 BL1이 있다.
- **BL2 (Trusted Boot Firmware)**: FIP(Firmware Image Package — 여러 펌웨어를 목차와 함께 묶은 컨테이너)를 열어 BL31, BL32, BL33을 각자 주소로 로드한다. Trusted Board Boot(TBBR)를 켜면 각 이미지의 인증서 체인을 검증한다.
- **BL31 (EL3 Runtime Firmware)**: 부팅이 끝나도 **사라지지 않는다**. Linux가 `smc` 명령을 실행하면 EL3로 트랩되어 BL31이 처리한다. 대표 서비스가 **PSCI**(Power State Coordination Interface: CPU 켜기/끄기, 시스템 리셋·전원 끄기)다. Secure world(BL32)와 Normal world 사이 문맥 전환(Secure Monitor)도 여기서 한다.
- **BL32**: Secure-EL1에서 도는 TEE OS. 보통 OP-TEE다. 키 저장, DRM, 보안 업데이트 검증 같은 Trusted Application을 돌린다. 이 랩의 FIP에는 없다(§3.2에서 확인).
- **BL33 (Non-trusted Firmware)**: Normal world의 첫 코드. U-Boot나 UEFI(EDK2)가 온다.

Don 관점에서 BL31은 "**전원이 꺼질 때까지 상주하는 특권 서비스 루틴**"이다. RTOS에서 SVC 핸들러가 커널 서비스를 제공하듯, BL31은 SMC 핸들러로 OS에 플랫폼 서비스를 제공한다. 깊은 내용은 C5.

### 1.5 U-Boot — 범용 부트로더

U-Boot proper는 "작은 OS"에 가깝다. 자기 driver model(DM)과 Device Tree로 하드웨어를 찾고, 셸(`=>` 프롬프트), 환경변수, FAT/ext4 파일시스템, TFTP·DHCP, USB, MMC 드라이버를 갖는다.

- **초기화**: 콘솔, DRAM 크기 확인(이미 SPL/BL2가 살려 놓음), 자기 자신을 RAM 끝으로 **재배치(relocation)** — 커널을 놓을 낮은 주소를 비워 두기 위해서다. 그 뒤 스토리지·네트워크 드라이버를 probe.
- **로드**: `bootcmd` 환경변수가 자동 부팅 스크립트다. 커널 Image, initramfs, DTB를 RAM 주소(`kernel_addr_r`, `ramdisk_addr_r`, `fdt_addr_r`)로 읽는다.
- **DT fixup**: DTB의 `/chosen` 노드에 `bootargs`(커널 cmdline), `linux,initrd-start/end`를 써 넣고, `/memory` 노드를 실제 크기로 고치고, MAC 주소·`kaslr-seed` 등을 채운다.
- **점프**: arm64는 `booti`. 캐시·MMU를 끄고 `x0 = DTB 물리 주소`, `x1 = x2 = x3 = 0`으로 커널 Image 첫 바이트로 점프한다. 이 레지스터 약속이 커널 문서 `Documentation/arch/arm64/booting.rst`에 정의된 **arm64 부트 프로토콜**이다(§4).

U-Boot 사용법은 C3, 포팅은 C4.

### 1.6 커널 — head.S부터 PID 1까지

- `arch/arm64/kernel/head.S`의 `primary_entry`: 부트 인자(x0~x3)를 저장하고, EL2로 들어왔으면 EL2 설정을 하고, 초기 페이지 테이블을 만들어 **MMU를 켠다**. 그 다음 C 코드 `start_kernel()`(`init/main.c`)로 간다.
- `start_kernel()`: `setup_arch()`에서 DTB를 읽어 메모리 범위·예약 영역을 잡고(`memblock`), cmdline의 early 파라미터(`earlycon` 등)를 처리하고, DT를 커널 자료구조로 펼친다(`unflatten_device_tree`). 이후 인터럽트, 타이머, 스케줄러, 콘솔을 초기화한다.
- `rest_init()` → `kernel_init` 스레드: initcall들을 레벨 순서대로 실행한다. **드라이버 probe가 여기서 일어난다**(DT 노드 → platform device → driver 매칭, 모듈 G). `rootfs_initcall` 레벨에서 initramfs cpio를 rootfs(tmpfs)에 푼다.
- 마지막으로 `run_init_process("/init")` — 커널 스레드가 `execve`로 유저 프로그램이 되며 **PID 1**이 된다. initramfs에 `/init`이 없으면 `root=`로 지정한 블록 장치를 마운트하고 `/sbin/init` 등을 찾는다.

커널 시작 과정의 세부(initcall 레벨, earlycon, `root=`/`init=`)는 C6, init과 부팅 완료·시간 단축은 C7.

### 1.7 initramfs와 init — 첫 유저 공간

- **initramfs**: gzip 등으로 압축된 cpio 아카이브. 부트로더가 RAM에 올려 두고 위치를 DT `/chosen/linux,initrd-start`로 알려 주면, 커널이 tmpfs 기반 rootfs에 푼다. 용도는 둘이다: (1) 작은 시스템이면 그 자체가 rootfs(이 랩), (2) 큰 시스템이면 진짜 rootfs(eMMC의 ext4, dm-verity, 암호화 볼륨)를 준비해 마운트하고 `switch_root`로 넘어가는 디딤돌.
- **init(PID 1)**: 모든 유저 프로세스의 조상. `/proc`·`/sys`·`/dev`를 마운트하고 서비스를 시작하고, 고아 프로세스를 거두고(reap), 절대 종료하면 안 된다 — PID 1이 죽으면 커널이 `Kernel panic - not syncing: Attempted to kill init!`을 낸다. BusyBox init, systemd가 대표다.

출력에서 볼 것: 부트 경로가 두 가지다. `-bios flash.bin`(TF-A → U-Boot, `secure=on` 필요)과 `-bios u-boot.bin`(TF-A 없이 U-Boot만). 그리고 `-kernel Image`로 펌웨어 없이 커널을 바로 올리는 세 번째 방법이 있다. 이 노트는 셋을 모두 쓴다. (README 중간 줄 일부는 `...`로 생략했다.)

### 3.2 TF-A 이미지는 어디에 놓이나 — ELF·FIP·소스로 확인

무엇을 확인하나: 그림 1·2의 주소가 지어낸 값이 아니라 빌드 산출물과 소스에서 나온다는 것을 본다. ELF의 LOAD 세그먼트 주소 = 그 단계가 실행되는 물리 주소다(MMU가 꺼져 있거나 1:1 매핑이라서).

```sh
cd /var/lab && R=build/tfa/qemu/release
for b in bl1 bl2 bl31; do
  readelf -lW $R/$b/$b.elf | awk -v b=$b '/LOAD/{printf "%-5s vaddr=%s memsz=%s %s%s\n", b, $3, $6, $7, $8}'
done
```

```text
bl1   vaddr=0x0000000000000000 memsz=0x005830 RE
bl1   vaddr=0x000000000e0ee000 memsz=0x001100 RW0x1000
bl1   vaddr=0x000000000e0ef100 memsz=0x0009a0 RW0x1000
bl1   vaddr=0x000000000e0f0000 memsz=0x006000 RW0x1000
bl2   vaddr=0x000000000e05b000 memsz=0x006000 RE
bl2   vaddr=0x000000000e061000 memsz=0x008000 RW0x1000
bl31  vaddr=0x000000000e090000 memsz=0x00c000 RE
bl31  vaddr=0x000000000e09c000 memsz=0x02f000 RW0x1000
```

출력에서 볼 것: BL1의 코드(`RE` = 읽기+실행)는 주소 0 — flash에서 바로 실행(XIP)되고, 쓰기 가능한 데이터(`RW`, 뒤의 `0x1000`은 정렬값이 붙어 찍힌 것)만 Secure SRAM(0x0e0xxxxx)에 있다. BL2와 BL31은 코드까지 Secure SRAM에 올라간다. SSD 컨트롤러 ROM 코드가 ROM에서 돌고 스택·변수만 SRAM에 두는 것과 똑같은 배치다.

이제 FIP 안에 무엇이 들었는지, 그리고 flash.bin의 어디에 FIP가 있는지 본다. FIP 목차(ToC) 헤더는 매직 넘버 `0xAA640001`로 시작한다.

```sh
src/tfa/tools/fiptool/fiptool info out/fip.bin
python3 -c "import struct;d=open('out/flash.bin','rb').read();print(len(d), hex(d.find(struct.pack('<I',0xAA640001))))"
grep -E "define (SEC_SRAM_BASE|SEC_SRAM_SIZE|NS_DRAM0_BASE|NS_IMAGE_OFFSET|PLAT_QEMU_DT_BASE)\b" src/tfa/plat/qemu/qemu/include/platform_def.h
ls -l out/u-boot.bin | awk '{print $5, $9}'; printf "%d\n" 0x16F3D0
```

```text
Trusted Boot Firmware BL2: offset=0xB0, size=0x61F0, cmdline="--tb-fw"
EL3 Runtime Firmware BL31: offset=0x62A0, size=0xC067, cmdline="--soc-fw"
Non-Trusted Firmware BL33: offset=0x12307, size=0x16F3D0, cmdline="--nt-fw"
67108864 0x40000
#define NS_DRAM0_BASE			ULL(0x40000000)
#define SEC_SRAM_BASE			0x0e000000
#define SEC_SRAM_SIZE			0x00100000
#define NS_IMAGE_OFFSET			(NS_DRAM0_BASE + 0x20000000)
#define PLAT_QEMU_DT_BASE		NS_DRAM0_BASE
1504208 out/u-boot.bin
1504208
```

출력에서 볼 것:

- FIP에는 BL2, BL31, BL33 세 개뿐이다. **BL32(OP-TEE)는 없다** — 이 랩은 Secure OS 없이 부팅한다. OP-TEE를 넣으면 `--tos-fw` 항목이 생긴다(이 노트에서는 실행하지 않음).
- flash.bin(64 MiB)의 0x40000 오프셋에 FIP가 있다. BL1은 0번지, FIP는 256 KiB 지점 — 이 배치가 BL1 소스의 "FIP는 flash의 어디"라는 플랫폼 정의와 맞물린다.
- BL33의 크기 0x16F3D0 = 1504208 바이트 = `out/u-boot.bin`과 같은 크기다. **FIP의 BL33이 바로 U-Boot 바이너리**다.
- `NS_IMAGE_OFFSET = 0x40000000 + 0x20000000 = 0x60000000` — BL2가 U-Boot를 여기에 올린다. DRAM 시작에서 512 MiB 지점이라 `-m 512`면 RAM 밖이다. README가 "512 MB면 BL2 뒤에 조용히 멈춘다"고 경고한 이유다.
- `PLAT_QEMU_DT_BASE = 0x40000000` — QEMU가 만든 DTB를 TF-A가 DRAM 시작에서 찾는다(§4.3에서 QEMU 쪽 증거를 본다).

### 3.4 시리얼을 시간 도장 찍으며 운전하는 스크립트

부팅을 재고(단계별 시간), U-Boot에 명령을 자동으로 쳐 넣으려면 expect 같은 도구가 필요하다. 여기서는 짧은 Python 스크립트를 쓴다. QEMU를 자식 프로세스로 띄우고, 시리얼 출력의 **줄마다 호스트 단조 시계(monotonic) 기준 경과 시간**을 붙이고, 지정한 문자열이 보이면 정해진 입력을 보낸다.

무엇을 확인하나: 이 노트의 모든 시간 측정과 대화형 부팅이 이 도구 하나로 이뤄진다. `t = 0`은 QEMU 프로세스를 띄운 순간이다.

```python
#!/usr/bin/env python3
"""c1_drive.py: run QEMU, timestamp every serial line (host monotonic clock,
t=0 at process spawn), optionally answer prompts like expect.
usage: c1_drive.py LOG SCRIPT.json -- qemu-system-aarch64 ...
SCRIPT.json = [["pattern", "text to send"], ...]  (fired once, in order)"""
import json, os, re, select, subprocess, sys, time

log_path, script_path = sys.argv[1], sys.argv[2]
cmd = sys.argv[sys.argv.index("--") + 1:]
rules = json.load(open(script_path)) if script_path != "-" else []
t0 = time.monotonic()
p = subprocess.Popen(cmd, stdin=subprocess.PIPE, stdout=subprocess.PIPE,
                     stderr=subprocess.STDOUT)
buf, out, ri, since = b"", [], 0, b""
deadline = t0 + 120
while time.monotonic() < deadline:
    r, _, _ = select.select([p.stdout], [], [], 0.2)
    if r:
        chunk = os.read(p.stdout.fileno(), 4096)
        if not chunk:
            break
        buf += chunk
        since += chunk
        while b"\n" in buf:
            line, buf = buf.split(b"\n", 1)
            out.append((time.monotonic() - t0, line))
    # prompt matching: only on bytes received since the last send
    if ri < len(rules) and rules[ri][0].encode() in since:
        time.sleep(0.05)
        p.stdin.write(rules[ri][1].encode()); p.stdin.flush()
        out.append((time.monotonic() - t0, b"<<SENT " + rules[ri][1].encode().strip() + b">>"))
        ri += 1
        since = b""
    if p.poll() is not None and not r:
        break
if buf:
    out.append((time.monotonic() - t0, buf))
p.kill()
with open(log_path, "w") as f:
    for t, l in out:
        s = l.decode("utf-8", "replace").replace("\r", "")
        s = re.sub(r"\x1b\[[0-9;?]*[A-Za-z]|\x1b[78]", "", s)
        s = "".join(ch for ch in s if ch == "\t" or ch >= " ")
        f.write("[%8.3f] %s\n" % (t, s))
print("exit", p.returncode, "lines", len(out), "total %.3f s" % (time.monotonic() - t0))
```

로그의 `<<SENT ...>>` 줄은 스크립트가 보낸 입력을 표시한 것이고, 시간 도장은 "그 줄의 줄바꿈이 호스트에 도착한 시각"이다. 한계도 알고 쓰자: 시리얼은 QEMU 안에서 버퍼링되어 여러 줄이 한 덩어리로 오면 같은 시각이 찍힌다. 그리고 커널은 콘솔 드라이버가 등록되기 전에 찍은 로그를 **나중에 몰아서** 내보내므로, 그 줄들의 호스트 시각은 실제 발생 시각이 아니다(§3.6에서 다룬다).

이 도구로 U-Boot 프롬프트를 잡고 환경과 보드 정보를 본다.

- **`poweroff` → `ERROR: QEMU System Power off: with GPIO.`** — 이 줄은 U-Boot가 아니라 **BL31(TF-A)** 이 찍은 것이다. U-Boot의 poweroff가 PSCI `SYSTEM_OFF`를 SMC로 부르고, EL3의 BL31이 QEMU의 GPIO 전원 키로 실제 전원을 끈다. 부팅 후에도 BL31이 살아 있다는 첫 증거다(ERROR 레벨로 찍히는 것은 TF-A QEMU 플랫폼 코드의 선택일 뿐 실패가 아니다).

### 3.6 U-Boot로 커널 부팅 — 전체 시리얼 로그를 단계별로 읽기

무엇을 확인하나: 리셋부터 셸까지 한 번의 부팅을 처음부터 끝까지 캡처하고 단계마다 시간을 읽는다. U-Boot에는 아래 명령을 차례로 친다(스크립트가 자동 입력).

```text

fatload virtio 0 ${ramdisk_addr_r} initrd.gz
```

## 4. 핸드오버 — 커널은 무엇을 받아서 시작하나

### 4.1 arm64 부트 프로토콜

커널 문서 `Documentation/arch/arm64/booting.rst`가 부트로더의 의무를 정한다. 핵심만 추리면 이렇다.

- RAM을 초기화하고, **DTB를 RAM에 놓고**(8바이트 정렬, 2 MB 경계를 넘지 않게), 커널 Image를 Image 헤더가 요구하는 정렬로 놓는다.
- 점프 직전 레지스터: **`x0 = DTB의 물리 주소`, `x1 = x2 = x3 = 0`**.
- CPU 상태: 모든 인터럽트 마스크, **MMU off, D-cache off**(대상 영역은 clean 상태로), EL2(가능하면) 또는 Non-secure EL1.
- 커널 Image의 첫 바이트로 점프한다.

Don의 SSD FW라면 "부트로더가 FW에 넘기는 부트 파라미터 구조체 포인터를 r0에 넣고 점프"에 해당한다. Linux는 그 구조체가 **Device Tree라는 표준 형식**이라는 점만 다르다.

### 4.2 커널 Image 헤더 — 부트로더가 읽는 64바이트

무엇을 확인하나: `booti`가 커널을 어디에 어떻게 놓을지는 Image 앞 64바이트의 헤더를 보고 정한다.

```sh
xxd -l 64 /var/lab/out/Image
```

```text
00000000: 4d5a 40fa 3ba8 7f14 0000 0000 0000 0000  MZ@.;...........
00000010: 0000 9802 0000 0000 0a00 0000 0000 0000  ................
00000020: 0000 0000 0000 0000 0000 0000 0000 0000  ................
00000030: 0000 0000 0000 0000 4152 4d64 4000 0000  ........ARMd@...
```

출력에서 볼 것 (필드 배치는 `booting.rst`의 헤더 정의, 리틀 엔디언):

- 0x00 `code0` = `4d5a 40fa` — `MZ`로 시작한다. 같은 파일이 UEFI PE/COFF 실행 파일로도 읽히게 하는 트릭(EFI stub)이다. 이 명령어 자리는 무해한 명령으로 해석된다.
- 0x08 `text_offset` = 0, 0x10 `image_size` = `0x02980000`(약 43.5 MB, BSS 포함 메모리상 크기 — 파일 크기 42.7 MB보다 크다).
- 0x18 `flags` = `0x0a` = 이진수 1010: bit0 = 0(리틀 엔디언 커널), bit1~2 = 01(4 KB 페이지), bit3 = 1(물리 메모리 **어디든** 2 MB 정렬이면 놓아도 된다).
- 0x38 `magic` = `ARMd`(0x644d5241). `booti`는 이 매직을 확인하고 arm64 Image로 인정한다.

`kernel_addr_r = 0x40400000`은 2 MB 정렬이라 U-Boot는 Image를 옮기지 않고 그 자리에서 실행했다(로그에 커널 이동 메시지가 없다).

### 4.3 QEMU가 대신 해 주는 부트로더 — 40바이트

`-kernel`로 바로 부팅하면 펌웨어가 없는데 누가 x0에 DTB 주소를 넣을까? QEMU가 RAM에 아주 작은 스텁을 써 넣는다. QEMU 모니터로 확인한다.

무엇을 확인하나: 펌웨어 경로와 `-kernel` 경로에서 QEMU가 RAM에 미리 놓는 것(ROM blob)이 어떻게 다른지, 그리고 그 스텁이 정확히 무슨 명령인지 본다.

```sh
printf "info roms\nquit\n" | qemu-system-aarch64 -machine virt -cpu cortex-a57 -m 1057 -display none \
  -serial null -S -monitor stdio -kernel /var/lab/out/Image -initrd /var/lab/out/initramfs.cpio.gz \
  -append "console=ttyAMA0" 2>&1 | grep -v "^(qemu)" | tr -d "\r" | head
echo ----
printf "info roms\nquit\n" | qemu-system-aarch64 -machine virt,secure=on -cpu cortex-a57 -m 1057 -display none \
  -serial null -S -monitor stdio -bios /var/lab/out/flash.bin 2>&1 | tr -d "\r" | grep -v "^(qemu)" | head
```

출력에서 볼 것:

- **`-kernel` 경로**: QEMU가 RAM에 네 가지를 놓는다 — 0x40000000에 0x28(40) 바이트짜리 `bootloader`, 0x40200000에 Image, 0x48000000에 initrd, 0x48200000에 1 MiB DTB. QEMU가 U-Boot의 일(이미지 배치)을 대신 한 것이다.
- **`-bios flash.bin` 경로**: flash에 펌웨어, RAM에는 0x40000000의 DTB 하나뿐이다. TF-A 소스의 `PLAT_QEMU_DT_BASE = NS_DRAM0_BASE`(§3.2)와 정확히 맞는다. 나머지는 펌웨어가 알아서 하라는 뜻이다.

이제 40바이트 스텁을 꺼내 역어셈블한다. 모니터의 `xp`로 10워드를 읽어 바이너리로 되돌린 뒤 `objdump`에 넣는다.

```sh
printf "xp /10wx 0x40000000\nquit\n" | qemu-system-aarch64 -machine virt -cpu cortex-a57 -m 1057 \
  -display none -serial null -S -monitor stdio -kernel /var/lab/out/Image \
  -initrd /var/lab/out/initramfs.cpio.gz -append "console=ttyAMA0" 2>&1 | tr -d "\r" \
  | grep -aoE "^0000000040[0-9a-f]+:.*" | tee c1_stub.txt
python3 -c "
import re,struct
w=[int(x,16) for x in re.findall(r\"0x([0-9a-f]{8})\", open(\"c1_stub.txt\").read())]
open(\"c1_stub.bin\",\"wb\").write(struct.pack(\"<%dI\"%len(w),*w))"
objdump -D -b binary -m aarch64 c1_stub.bin | tail -n +8
```

U-Boot의 `booti`도 결국 같은 일을 한다 — U-Boot 소스 `arch/arm/lib/bootm.c`의 `boot_jump_linux()`가 `kernel_entry(fdt_addr, 0, 0, 0)` 모양으로 부르거나, EL2로 내려가야 하면 `armv8_switch_to_el2(ft_addr, 0, 0, 0, ...)`를 부른다.

두 출력을 나란히 놓으면 핸드오버의 모든 증거가 나온다.

| 확인 항목 | TF-A + U-Boot | `-kernel` (QEMU) | 무엇을 증명하나 |
|---|---|---|---|
| `/proc/cmdline` | `c1_from=uboot` | `c1_from=qemu` | cmdline은 DT `/chosen/bootargs`로 넘어오고, 쓴 주체가 다르다 |

| `linux,initrd-start` | 0x7f404000 | 0x48000000 | U-Boot는 initrd를 RAM 위쪽으로 옮겼다(`Loading Ramdisk to 7f404000`) |

| `/psci/method` | `smc` | `hvc` | PSCI를 EL3 펌웨어(BL31)가 처리 vs QEMU가 에뮬레이션 |
| SMCCC 버전 | v1.5 | v1.0 | 응답하는 펌웨어가 실제로 다르다(TF-A vs QEMU 내장 PSCI) |

| `started at EL` | EL1 | EL1 | 둘 다 EL2가 없는 머신(`virtualization=off`) — §5.2에서 EL2로 바꿔 본다 |
| PID 1 | `/bin/sh` (busybox) | `/bin/sh` (busybox) | initramfs의 `/init` 스크립트가 `exec /bin/sh`로 PID 1을 넘겼다 |

## 5. `-kernel` 부팅은 무엇을 건너뛰나

### 5.1 비교표

QEMU의 `-kernel`은 개발할 때 아주 편하다(이 랩의 다른 노트들도 대부분 이걸 쓴다). 하지만 실제 보드의 부팅과 무엇이 다른지 알고 써야 한다.

| 항목 | 실제 보드 / TF-A+U-Boot 경로 | QEMU `-kernel` | 건너뛰어서 생기는 차이 |
|---|---|---|---|
| 리셋 벡터 코드 | BootROM·BL1 | 없음 (QEMU 스텁 40 B) | ROM·부트 미디어·boot pin 문제를 재현할 수 없다 |
| DDR 초기화 | SPL 또는 BL2 | 없음 (RAM이 처음부터 살아 있음) | DDR 트레이닝 실패 같은 bring-up 1순위 문제가 안 보인다 |
| Secure world | BL31 상주, BL32 선택 | 없음 | PSCI가 `hvc`로 QEMU 내장 구현 → 실제 펌웨어 버그·SMC 경로가 안 보인다 |
| 서명 검증 | ROM → BL2 → U-Boot(FIT) 체인 | 없음 | secure boot 흐름을 시험할 수 없다 |
| 이미지 로드 | U-Boot가 eMMC·TFTP에서 | QEMU가 호스트 파일을 RAM에 직접 | 스토리지 드라이버·파일시스템·`bootcmd` 문제가 안 보인다 |
| DT | 보드 DTB를 U-Boot가 읽고 fixup | QEMU 생성 DTB에 QEMU가 `/chosen`만 추가 | MAC 주소·메모리 크기·`/reserved-memory` fixup 차이 |
| 진입 EL | 보통 EL2 (U-Boot가 EL2로) | EL1 (`virtualization=off`일 때) | KVM·pKVM·VHE 관련 동작이 다르다 |
| 부팅 시간 | 펌웨어 단계 시간 포함 | 커널부터 | 부팅 시간 예산을 잡을 때 앞단을 빼먹기 쉽다 |

요약하면 **`-kernel`은 "커널부터 위"만 시험한다.** 드라이버·커널 기능을 배우는 데는 충분하지만, 부트로더·보안·전원 관리를 이야기할 때는 `-bios flash.bin` 경로로 확인해야 한다.

### 5.2 EL2로 들어가기 — `virtualization=on`

무엇을 확인하나: 머신에 EL2를 켜면 TF-A가 U-Boot를 EL2로 내려 보내고, 커널도 EL2에서 시작해 KVM 하이퍼바이저 모드를 쓸 수 있게 되는지 본다. U-Boot 환경은 자동 부팅(`bootdelay=0`, `bootcmd`에 §3.6의 명령, `bootargs=console=ttyAMA0 LAB_CMD=true`)으로 저장해 둔 flash 이미지 `c1_env.img`를 쓴다(만드는 법은 §7.1). `LAB_CMD=true`는 랩 initramfs가 명령 하나를 실행하고 전원을 끄게 하는 인자다.

```sh
python3 c1_drive.py c1_el2.log - -- qemu-system-aarch64 -machine virt,secure=on,virtualization=on \
  -cpu cortex-a57 -m 1057 -nographic -bios /var/lab/out/flash.bin \
  -drive if=pflash,unit=1,file=c1_env.img,format=raw \
  -drive if=none,file=c1_boot.img,format=raw,id=c1d -device virtio-blk-device,drive=c1d
grep -E "started at EL|kvm \[|psci: (SMC|PSCI)|Starting kernel" c1_el2.log
grep -E "started at EL|kvm \[" c1_t_tfa_1.log      # 같은 경로, virtualization=off
```

### 5.3 반대 방향: 펌웨어는 그대로, 이미지만 QEMU가 — fw_cfg bootmeth

무엇을 확인하나: `-bios flash.bin`과 `-kernel`을 **같이** 주면 어떻게 되나. §3.3의 `bootflow scan`이 뒤지던 `fw-cfg` 부트 장치가 QEMU가 준 커널을 찾아 U-Boot가 부팅한다.

```sh
  -initrd /var/lab/out/initramfs.cpio.gz -append "console=ttyAMA0 quiet LAB_CMD=cat~/proc/cmdline"
```

## 6. 네트워크로 커널 받기 — TFTP

실제 bring-up과 커널 개발에서는 커널을 매번 SD 카드에 굽지 않고 **U-Boot가 개발 PC에서 TFTP로 받아** 부팅한다(rootfs는 NFS). QEMU의 user-mode 네트워크는 TFTP 서버를 내장하고 있어서(`tftp=` 옵션) 이 흐름을 그대로 해 볼 수 있다.

무엇을 확인하나: U-Boot의 `dhcp` → `tftpboot` → `booti` 흐름과 전송 속도.

```sh
mkdir -p c1_tftp && cp /var/lab/out/Image c1_tftp/ && cp /var/lab/out/initramfs.cpio.gz c1_tftp/initrd.gz
cat > c1_tftp.json <<'EOF'
[["Hit any key", " "],
 ["=> ", "setenv autoload no; dhcp\n"],
 ["=> ", "tftpboot ${kernel_addr_r} Image\n"],
 ["=> ", "tftpboot ${ramdisk_addr_r} initrd.gz\n"],
 ["=> ", "setenv bootargs \"console=ttyAMA0 quiet LAB_CMD=cat~/proc/cmdline\"\n"],
 ["=> ", "booti ${kernel_addr_r} ${ramdisk_addr_r}:${filesize} ${fdtcontroladdr}\n"]]
EOF
python3 c1_drive.py c1_tftp.log c1_tftp.json -- qemu-system-aarch64 -machine virt,secure=on \
  -cpu cortex-a57 -m 1057 -nographic -bios /var/lab/out/flash.bin \
  -nic user,model=virtio-net-pci,tftp=/var/tmp/C1/c1_tftp
```

출력에서 볼 것:

- **TFTP가 압도적으로 느리다**: 42.7 MB에 11.5 s(3.5 MiB/s). 같은 파일을 virtio 디스크 FAT에서 읽을 때는 63~357 ms였다. TFTP는 블록마다 ACK를 기다리는 stop-and-wait 프로토콜이라 지연에 민감하다(여기서는 QEMU slirp 에뮬레이션 비용까지 겹쳤다). 실제 보드에서도 TFTP는 디스크보다 훨씬 느린 편이라, 개발 중에는 커널을 작게(필요한 드라이버만, 또는 압축 Image) 유지하는 것이 이득이다. U-Boot의 `tftpblocksize`·`tftpwindowsize` 환경변수로 더 큰 블록과 윈도우를 쓰면 빨라질 수 있다(이 노트에서는 시험하지 않음).
- `quiet`를 주니 커널 로그가 사라지고 `/init` 출력만 남았다. 이 차이는 §7.3에서 잰다.
- 그 외 흐름(`Loading Ramdisk to 7f404000`, `Starting kernel`)은 디스크 부팅과 똑같다. **U-Boot 이후 단계는 이미지를 어디서 가져왔는지 모른다.**

### 7.1 사람 입력 없는 자동 부팅 만들기 — U-Boot 환경 저장

시간을 재려면 사람(스크립트)의 타이핑 간격과 2초 카운트다운을 없애야 한다. 실제 제품처럼 U-Boot 환경에 `bootcmd`를 저장하고 `bootdelay=0`으로 만든다. 환경은 두 번째 flash(`-drive if=pflash,unit=1`)에 저장되므로 빈 64 MiB 파일을 하나 붙인다.

무엇을 확인하나: `saveenv`가 flash에 환경을 쓰고, 다음 부팅부터 `bootcmd`가 자동 실행되는지 본다. `bootcmd`는 작은따옴표로 감싸야 `${...}`가 저장 시점이 아니라 실행 시점에 펼쳐진다.

### 7.2 세 가지 경로를 여러 번 재기

무엇을 확인하나: (a) TF-A+U-Boot, (b) U-Boot만(`-bios u-boot.bin`, Non-secure), (c) `-kernel` 직접 — 세 경로를 같은 커널·initramfs·cmdline으로 번갈아 8회씩 부팅해 단계별 시간을 모은다. 번갈아 돌리는 이유는 VM 부하의 시간 변화가 한 경로에만 몰리지 않게 하려는 것이다.

```sh
#!/bin/bash
# c1_timing.sh N : boot 3 configurations N times each, keep timestamped logs
cd /var/tmp/C1 || exit 1

  python3 $D c1_t_tfa_$i.log - -- qemu-system-aarch64 -machine virt,secure=on $COMMON \
    -bios $L/flash.bin -drive if=pflash,unit=1,file=c1_env.img,format=raw $DISK >/dev/null

```

로그에서 표지(marker) 줄의 호스트 시각을 뽑아 단계 길이를 계산하는 파서:

```python
#!/usr/bin/env python3
"""c1_parse.py: per-stage boot times from c1_t_<cfg>_<n>.log (host timestamps)."""
import glob, re, statistics, sys

MARK = [("bl1", r"Booting Trusted Firmware"), ("bl31", r"BL31: v"),
        ("ub", r"^U-Boot 20"), ("net", r"^Net:"), ("sk", r"Starting kernel"),
        ("init", r"Run /init as init"), ("lab", r"lab initramfs")]

def marks(path):
    m = {}
    for line in open(path):
        t, _, text = line.partition("] ")
        t = float(t.strip("[ "))
        for k, pat in MARK:
            if k not in m and re.search(pat, text):
                m[k] = t
                if k == "lab":
                    m["uptime"] = float(re.search(r"up ([0-9.]+)s", text).group(1))
                if k == "init":
                    m["kinit"] = float(re.search(r"\[\s*([0-9.]+)\]", text).group(1))
    return m

def stages(cfg, m):
    kzero = m["lab"] - m["uptime"]          # host time when kernel clock was 0
    if cfg == "tfa":
        s = [("QEMU->BL1", m["bl1"]), ("BL1+BL2", m["bl31"] - m["bl1"]),
             ("BL31->U-Boot", m["ub"] - m["bl31"]), ("U-Boot init", m["net"] - m["ub"]),
             ("U-Boot load+booti", m["sk"] - m["net"]), ("kernel->/init", m["init"] - m["sk"])]
    elif cfg == "ub":
        s = [("QEMU->U-Boot", m["ub"]), ("U-Boot init", m["net"] - m["ub"]),
             ("U-Boot load+booti", m["sk"] - m["net"]), ("kernel->/init", m["init"] - m["sk"])]
    else:
        s = [("QEMU->kernel", kzero), ("kernel->/init", m["init"] - kzero)]
    s.append(("/init->shell", m["lab"] - m["init"]))
    s.append(("TOTAL", m["lab"]))
    return s, m

for cfg in ("tfa", "ub", "direct"):
    rows = {}
    for f in sorted(glob.glob(f"/var/tmp/C1/c1_t_{cfg}_*.log")):
        s, m = stages(cfg, marks(f))
        for k, v in s:
            rows.setdefault(k, []).append(v)
        rows.setdefault("kernel dmesg Run /init", []).append(m["kinit"])
    print(f"== {cfg} (n={len(rows['TOTAL'])})")
    for k, v in rows.items():
        print(f"  {k:24s} median {statistics.median(v):6.3f}  min {min(v):6.3f}  max {max(v):6.3f}  "
              + " ".join(f"{x:.3f}" for x in v))
```

같은 측정을 두 번 했다. 첫 번째는 다른 노트 작업이 동시에 돌아 VM이 바쁠 때(load average 12~13), 두 번째는 VM이 한가할 때(load average 1 근처)다. 한가할 때의 값을 기준으로 삼고, 바쁠 때의 값은 "측정이 얼마나 흔들릴 수 있나"의 예로 본다.

숫자에서 읽을 것:

- **펌웨어 단계(BL1+BL2+BL31)는 약 30 ms**(BL1+BL2 0.020 s, BL31→U-Boot 0.008 s). QEMU에서는 DDR 초기화·서명 검증이 없어서 작다. 실제 보드에서는 DDR 트레이닝과 서명 검증 때문에 이 구간이 훨씬 길어지는 경우가 많다(보드마다 다르고 이 노트에서 측정하지 않음).
- **U-Boot는 약 0.17 s**(초기화 0.126 s + 로드·booti 0.041 s). 초기화 안에서는 flash·USB·네트워크 probe가 대부분이다(§3.6에서 flash probe만 88 ms). 부팅 시간 최적화에서 U-Boot는 "필요 없는 드라이버를 빼고 bootdelay를 0으로" 하는 첫 대상이다(C7).
- **커널→/init이 전체의 약 70%**(1.10 s 중 0.78 s). 이 랩 커널은 arm64 defconfig라 수백 개 드라이버가 built-in이고 initcall마다 probe를 시도한다. 실제 제품 커널은 필요한 드라이버만 남겨 이 구간을 크게 줄인다.
- **경로 간 차이**: TF-A+U-Boot(1.10 s)와 U-Boot만(1.05 s)의 차이 약 0.05 s가 TF-A의 몫이고, `-kernel`(0.85 s)과의 차이 약 0.26 s가 "펌웨어+부트로더 전체"의 몫이다. **TF-A 자체는 비싸지 않다.** 실제 보드에서도 시간을 먹는 것은 TF-A 코드보다 DDR·서명 검증·스토리지 읽기다.
- **측정 방법의 교훈**: VM이 바쁠 때는 같은 측정이 2~5배 느렸고(TF-A 경로 TOTAL 중앙값 5.12 s, 최소~최대 2.14~9.17 s), 그 상태에서는 세 경로의 차이가 잡음에 묻혀 보이지 않았다. 한가할 때는 8회 중 첫 회만 튀고(1회차 2.71 s, 원인은 확인하지 못했다) 나머지는 ±5% 안이다. **한 번 잰 값으로 결론을 내지 않고, 측정 환경의 부하를 같이 기록한다.** Don이 SSD에서 latency를 percentile로 보던 것과 같다.

### 7.3 콘솔 출력의 비용 — default · quiet · earlycon

무엇을 확인하나: 커널 로그를 시리얼로 찍는 것 자체가 부팅 시간을 잡아먹는지 본다. `-kernel` 경로에서 cmdline만 바꿔 5회씩 부팅하고, `/init`이 찍은 uptime과 `/init` 이전에 시리얼로 나간 바이트 수를 센다.

```sh
#!/bin/bash
# c1_console.sh N : direct -kernel boot with 3 console settings, N runs each
cd /var/tmp/C1 || exit 1
D=/Users/donh/.elinux_scratch/C1/c1_drive.py
L=/var/lab/out
for i in $(seq 1 $1); do
  for v in default quiet earlycon; do
    case $v in default) A="";; quiet) A="quiet";; earlycon) A="earlycon";; esac
    python3 $D c1_con_${v}_$i.log - -- qemu-system-aarch64 -machine virt -cpu cortex-a57 -m 1057 -nographic \
      -kernel $L/Image -initrd $L/initramfs.cpio.gz -append "console=ttyAMA0 $A LAB_CMD=true" >/dev/null
  done
done
for v in default quiet earlycon; do
  printf "%-9s uptime@init:" $v; grep -ho "up [0-9.]*s" c1_con_${v}_*.log | tr -d "ups" | tr "\n" " "
  printf "  host@shell:"; grep -h "lab initramfs" c1_con_${v}_*.log | cut -c2-9 | tr "\n" " "
  printf "  lines:"; for f in c1_con_${v}_*.log; do printf "%s " $(wc -l < $f); done; echo
done
printf "earlycon first kernel line (host s): "; for f in c1_con_earlycon_*.log; do grep -m1 "Booting Linux" $f | cut -c2-9 | tr "\n" " "; done; echo
```

## 8. 실제 보드에서는 — 네 가지 SoC 비교

QEMU 랩의 체인은 "교과서형"이다. 실제 SoC는 벤더마다 단계 이름과 담당이 다르다. 아래 표는 **이 노트에서 실행하거나 확인하지 않은, 기억에 기반한 정리**다. 큰 구조는 널리 알려진 내용이지만 파일 이름·오프셋·코어 배치 같은 세부는 SoC 세대와 BSP 버전마다 다르므로 실제 작업 전에는 벤더 문서(NXP i.MX Linux User's Guide, TI Processor SDK 문서, Raspberry Pi 문서, NVIDIA Jetson Linux Developer Guide)로 반드시 확인한다.

| 단계 | QEMU 랩 (실행함) | NXP i.MX8M Mini/Plus (기억) | TI AM62x (기억) | Raspberry Pi 4 (기억) | NVIDIA Jetson Orin (기억) |
|---|---|---|---|---|---|
| 첫 코드 | BL1 @ flash 0x0 | Cortex-A53의 BootROM | Cortex-R5 쪽 ROM (+ 보안 서브시스템) | VideoCore GPU의 ROM | BootROM (CPU 복합체가 아닌 보조 프로세서에서) |
| 첫 이미지 | FIP 속 BL2 | `imx-boot`(`imx-mkimage`로 만든 묶음) 속 U-Boot SPL | `tiboot3.bin` (R5 SPL + TIFS 펌웨어 + 보드 설정) | SPI EEPROM의 부트로더 | MB1 (BCT와 함께) |
| DRAM 초기화 | 없음 (QEMU) | SPL이 DDR PHY 트레이닝 펌웨어로 | R5 SPL | GPU 펌웨어 | MB1 단계 (MEM BCT 기반) |
| 다음 묶음 | BL31 + U-Boot | BL31 + U-Boot proper (+OP-TEE) | `tispl.bin` (BL31 + OP-TEE + A53 SPL + DM 펌웨어) → `u-boot.img` | `start4.elf`가 `config.txt` 읽고 커널·DTB 로드 | MB2가 BPMP 펌웨어·TOS(TF-A + OP-TEE)·UEFI 로드 |
| OS 로더 | U-Boot `booti` | U-Boot | U-Boot (A53) | GPU 펌웨어가 직접 (U-Boot는 선택) | UEFI(EDK2 기반) → extlinux.conf |
| DTB 출처 | QEMU 생성 → U-Boot fixup | eMMC FAT의 `*.dtb` 또는 FIT | `/boot/dtb/...` 또는 FIT | `bcm2711-rpi-4-b.dtb` + overlay를 GPU 펌웨어가 병합 | UEFI가 DTB 전달 |
| cmdline 출처 | `bootargs` | `bootargs` (U-Boot env) | `bootargs` | `cmdline.txt` | `extlinux.conf`의 `APPEND` |
| secure boot | (TBBR 미사용) | HAB (CST로 서명) | x509 인증서 체인, TIFS | 제한적 (모델에 따라 서명 부트 지원) | PKC/SBK 퓨즈 기반 |
| 복구 모드 | 해당 없음 | USB SDP (`uuu`) | USB DFU / UART 부트 | EEPROM 복구 이미지 | USB Recovery Mode (`flash.sh`, `l4t_initrd_flash.sh`) |

표에서 가져갈 일반 원칙:

- **"DRAM을 누가 살리나"가 SoC마다 다르다.** i.MX8M·AM62는 U-Boot SPL, Pi는 GPU 펌웨어, Jetson은 MB1. bring-up에서 "DDR이 안 잡힌다"고 하면 이 단계의 설정(DDR 타이밍 표, 트레이닝 펌웨어)을 본다(C4).
- **TI AM62처럼 이종 코어 SoC는 부트가 R5에서 시작**한다. 그래서 SPL이 두 벌(R5용, A53용)이고 R5는 부팅 후에도 Device Manager 펌웨어로 남는다(모듈 O).
- **Raspberry Pi는 예외적**이다. ARM 코어가 GPU 펌웨어의 "손님"이고, 펌웨어가 U-Boot 없이 바로 커널을 띄울 수 있다. 면접에서 "Pi로 해 봤다"고 하면 이 차이를 알고 있다는 것을 보여 주면 좋다.
- **Jetson(JetPack 5 이후)은 U-Boot가 아니라 UEFI**다. 그래서 "U-Boot만 안다"면 NVIDIA 면접에서 C8(UEFI 비교)도 준비해야 한다.

### 9.2 PID 1이 죽으면 — 직접 확인

무엇을 확인하나: "PID 1은 절대 종료하면 안 된다"를 눈으로 본다. `rdinit=/bin/true`로 initramfs의 첫 프로그램을 "바로 끝나는 프로그램"으로 바꾼다. `panic=1`과 QEMU `-no-reboot`로 panic 뒤 QEMU가 끝나게 한다.

### 9.3 드라이버를 쓸 때 다시 만나는 지점

- **DT 노드 → `probe()`**: `unflatten_device_tree()`가 만든 `device_node`가 `of_platform_default_populate_init()`에서 platform device가 되고, 드라이버의 `of_match_table`(`compatible` 문자열)과 매칭되면 `probe()`가 불린다. 부트로더가 넘긴 DTB가 곧 "어떤 드라이버의 probe가 불릴지"를 정한다(D, G 모듈).
- **initcall 레벨**: `module_init()`은 built-in 드라이버에서 `device_initcall`(레벨 6)이 된다. 다른 드라이버보다 먼저 떠야 하는 것(예: 클럭·핀 컨트롤러·PMIC)은 더 이른 레벨을 쓰거나 deferred probe(`-EPROBE_DEFER`)로 순서를 해결한다(G 모듈).
- **cmdline 파라미터**: 드라이버의 `module_param()`은 built-in이면 cmdline에서 `<모듈이름>.<파라미터>=값`으로 줄 수 있다. 커널이 모르는 인자(`c1_from=uboot`)는 `/init`에 환경변수·인자로 넘어간다(§3.6의 `Unknown kernel command line parameters ... will be passed to user space`).
- **PSCI**: CPU hotplug(`echo 0 > /sys/devices/system/cpu/cpu1/online`)와 시스템 suspend는 결국 `drivers/firmware/psci/`의 SMC 호출로 BL31에 간다(N 모듈 전원 관리).
- **`/sys/firmware/devicetree`**: 드라이버 디버깅 때 "커널이 실제로 받은 DT"를 보는 첫 장소다. 소스 `.dts`가 아니라 부트로더 fixup까지 반영된 결과다(D 모듈).

## 10. Embedded 실무에서 다시 보기

### 10.1 "Starting kernel ..." 뒤에 아무것도 안 나온다

센서 키트 보드 bring-up 첫 주에 가장 흔한 장면이다. 지도로 보면 원인은 "U-Boot와 커널 콘솔 드라이버 등록(랩에서 0.22 s) 사이"에 있다. 순서대로 확인한다.

1. cmdline에 `earlycon`을 넣는다(DT `/chosen/stdout-path`가 맞으면 인자 없이도 된다). 이제 커널 첫 줄이 보이면 커널은 살아 있고, 문제는 콘솔 드라이버·`console=` 이름(예: `ttyS0` vs `ttyAMA0` vs `ttymxc0`)이다.
2. earlycon으로도 안 나오면: DTB 주소가 틀렸거나(`booti`의 세 번째 인자), Image와 DTB·initrd가 메모리에서 겹쳤거나(로드 주소 간격 < 커널 `image_size`), 커널이 그 SoC를 지원하지 않는 설정이다.
3. U-Boot에서 `fdt addr ${fdt_addr_r}; fdt print /chosen`으로 넘길 DT를 확인하고, `md`로 커널 Image 헤더의 `ARMd` 매직이 그 주소에 있는지 본다(§4.2).
4. 그래도 모르면 JTAG으로 PC를 본다. PC가 커널 가상 주소(0xffff...)에 있으면 MMU는 켜졌고, 물리 주소 근처면 head.S에서 멈춘 것이다. Don이 JTAG으로 하던 "어디서 멈췄나"와 같은 방법이다.

### 10.2 부팅 시간 예산

예를 들어 "전원 ON 후 2초 안에 IMU 데이터를 ROS 노드가 받아야 한다"는 요구가 있으면, §7처럼 단계별로 재서 예산표를 만든다.

| 단계 | 랩 측정 (VM 한가할 때 중앙값) | 줄이는 수단 (C7에서 자세히) |
|---|---|---|
| ROM~펌웨어 | 약 0.03 s (BL1+BL2+BL31) | DDR 트레이닝 결과 캐시, 서명 검증 하드웨어 가속 |
| U-Boot | 약 0.17 s (초기화 0.13 + 로드 0.04) | `bootdelay=0`, 불필요한 드라이버 제거, Falcon mode(SPL이 커널 직접 부팅) |
| 커널 → /init | 약 0.78 s (전체의 70%) | 드라이버 정리, `quiet`, initcall_debug로 느린 probe 찾기, 모듈로 미루기 |
| init → 앱 | 약 0.065 s (셸까지) | systemd 의존성 정리, 앱을 먼저 띄우기 |

### 10.3 secure boot 체인

국방 로보틱스(예: Scout AI)나 카메라(예: Verkada) 제품은 "서명 안 된 펌웨어는 돌지 않는다"가 요구사항이다. 체인은 지도의 각 화살표에 검증을 붙이는 것이다: ROM이 eFuse 키 해시로 SPL/BL2를 검증 → BL2가 BL31·BL32·BL33 인증서를 검증(TBBR) → U-Boot가 서명된 FIT 이미지(커널+DTB+initramfs)를 검증 → 커널이 dm-verity로 rootfs를 검증. 한 고리라도 빠지면 그 뒤는 모두 무의미하다. 이 랩은 TBBR을 켜지 않았으므로 이 체인은 실행하지 않았다(C5, L 모듈에서 다룬다).

### 10.4 A/B 업데이트와 부트 카운터

현장 장비는 업데이트 중 전원이 나가도 살아나야 한다. U-Boot 환경에 "지금 슬롯 A/B", "부팅 시도 횟수(bootcount)"를 두고, 새 슬롯으로 N번 연속 부팅 실패하면 이전 슬롯으로 돌아간다(RAUC, SWUpdate, Mender 같은 도구가 이 구조를 쓴다, L 모듈). 부트로더가 "어느 커널·rootfs를 고르는지"의 결정권을 가진다는 점에서 이것도 부트 지도의 일부다.

Don이 면접에서 이 연결을 말하는 방법:

- "SSD 컨트롤러에서 ROM → 부트로더 → 메인 FW 체인을 다뤘고, 부트로더가 DRAM을 초기화한 뒤 FW 이미지를 검증해 올리는 구조였다. Linux 보드도 같은 3단 구조에 TF-A(EL3 서비스)와 U-Boot(범용 로더)가 끼고, 끝에 커널이 DTB로 하드웨어를 배운다는 점이 다르다."
- "부팅 실패 디버깅도 같다. 마지막으로 찍힌 로그로 어느 단계인지 가르고, 로그가 없으면 JTAG으로 PC를 본다. SSD의 FW 슬롯·Activate는 Linux의 A/B 슬롯과 bootcount에 해당한다."
- 차이를 정확히 아는 것도 보여 준다: SSD FW는 보드를 컴파일 타임에 알지만, Linux 커널 한 바이너리는 DTB 덕분에 여러 보드에서 돈다. 그리고 Linux에서는 부팅이 끝나도 EL3 펌웨어가 남아 PSCI 같은 서비스를 계속 제공한다.

## 13. 면접에서 이렇게 말한다

**Q.** "Walk me through the Linux boot process on an ARM embedded board." — 30초 · 2분 · 딥다이브

**A. (30초)** 전원이 들어오면 SoC의 BootROM이 boot pin·fuse로 부트 미디어를 고르고 첫 로더(SPL)를 내부 SRAM에 올린다. SPL이 DDR을 초기화하고 TF-A BL31과 U-Boot를 DRAM에 올린다. BL31은 EL3에 상주해 PSCI 같은 서비스를 맡고, U-Boot가 커널 Image·DTB·initramfs를 RAM에 놓고 x0에 DTB 주소를 담아 점프한다. 커널은 DTB로 하드웨어를 알고, 드라이버를 probe하고, initramfs나 rootfs를 마운트한 뒤 PID 1 init을 실행한다.

> On power-up the SoC's boot ROM reads the boot pins and fuses, picks a boot device and loads a small first-stage loader — usually U-Boot SPL — into on-chip SRAM. SPL brings up DDR and loads Trusted Firmware-A's BL31 and U-Boot proper into DRAM. BL31 stays resident at EL3 to provide PSCI and other secure services. U-Boot loads the kernel image, the device tree blob and an initramfs, fixes up the DT's chosen node with the command line, and jumps to the kernel with x0 pointing at the DTB. The kernel sets up the MMU, parses the device tree, probes drivers through the initcalls, unpacks the initramfs or mounts the root filesystem, and finally execs /init as PID 1.

**A. (2분)** 위에 "각 단계가 왜 있는가"를 붙인다. ROM은 수정 불가라 최소 기능만 갖고, DDR은 보드마다 달라서 SRAM에 들어가는 SPL이 초기화한다. TF-A는 Secure world와 Normal world를 나누는 EL3 펌웨어로 BL1/BL2/BL31(+BL32 OP-TEE)로 나뉘고, 부팅 후에도 BL31이 남아 CPU on/off·suspend·reset을 SMC로 처리한다. U-Boot는 driver model로 eMMC·네트워크를 다루고, `bootcmd`로 이미지를 읽어 DT `/chosen`에 `bootargs`와 initrd 위치를 쓰고, MMU·캐시를 끈 채 EL2로 커널에 넘긴다. 커널은 `head.S`에서 MMU를 켜고 `start_kernel` → `setup_arch`에서 DT로 메모리와 cmdline을 잡고, initcall 레벨 순으로 드라이버를 probe하고, `rootfs_initcall`에서 initramfs를 풀고, `/init`을 실행한다. initramfs는 작은 시스템이면 그대로 rootfs가 되고 큰 시스템이면 진짜 rootfs를 준비해 `switch_root`한다. 각 단계는 다음 단계를 서명 검증해 chain of trust를 만든다.

> I'd add why each stage exists. The boot ROM is immutable, so it does the minimum. DDR configuration is board-specific, so a small SPL that fits in SRAM trains DDR. TF-A is the EL3 firmware that separates the secure and normal worlds: BL1 and BL2 load and authenticate images from a FIP, BL31 stays resident as the secure monitor and implements PSCI, so later Linux turns CPUs on and off or resets the system with SMC calls, and BL32 is an optional trusted OS like OP-TEE. U-Boot is the general-purpose loader: it has drivers for eMMC, USB and Ethernet, runs bootcmd, writes bootargs and the initrd location into the DT, and enters the kernel at EL2 with the MMU and D-cache off, per the arm64 booting protocol. The kernel's head.S enables the MMU, start_kernel and setup_arch parse the DT for memory and the command line, the initcalls probe drivers by level, populate_rootfs unpacks the initramfs, and kernel_init execs /init. Each stage can verify the next one's signature, which gives you the chain of trust.

**A. (딥다이브 — 꼬리 질문을 기다리며 꺼낼 디테일)** QEMU에서 직접 해 봤다: TF-A 로그에서 `BL1: Booting BL2` 다음에 `BL1: Booting BL31`이 나오는데, BL2가 S-EL1이라 EL3로 직접 못 가서 SMC로 BL1에게 부탁하기 때문이다. U-Boot의 `booti`는 Image 헤더의 `ARMd` 매직과 flags를 보고, 커널은 `head.S`에서 x0를 x21에 보관해 `setup_machine_fdt`로 넘긴다. 펌웨어가 있으면 DT `/psci/method`가 `smc`, QEMU `-kernel`이면 `hvc`이고 SMCCC 버전도 다르게 보고되는 것을 게스트의 `/sys/firmware/devicetree`로 확인했다. 단계별로 8번씩 재 보니 TF-A는 약 30 ms, U-Boot는 약 0.17 s, 커널→/init이 전체 1.1 s의 약 70%였다.

> If they want depth: I traced it on QEMU with TF-A 2.15, U-Boot and a 6.18 kernel. The TF-A log shows "BL1: Booting BL31" right after BL2, because BL2 runs at secure EL1 and has to SMC back into BL1 to start the EL3 runtime. U-Boot's booti checks the ARMd magic and flags in the Image header; head.S saves x0 in x21 and setup_arch hands it to setup_machine_fdt. From inside the guest I could prove the handover: /proc/cmdline matched U-Boot's bootargs, the chosen node had u-boot,version and U-Boot's relocated initrd address, and psci method was "smc" with SMCCC 1.5, versus "hvc" and SMCCC 1.0 when QEMU loads the kernel directly. Timing eight boots per path, TF-A took about 30 milliseconds, U-Boot about 170, and kernel-to-init was roughly 70 percent of a 1.1-second boot.

**꼬리 질문**: "Where does the device tree come from on a real board?" → eMMC 부트 파티션의 `*.dtb`나 서명된 FIT 이미지에서 U-Boot가 읽고, 필요하면 overlay를 적용하고 `/chosen`·`/memory`·MAC 주소를 fixup해서 넘긴다. Raspberry Pi는 GPU 펌웨어가, Jetson은 UEFI가 그 역할을 한다.

**Q.** "What is SPL and why can't the boot ROM load U-Boot directly?"

**A.** ROM이 이미지를 올릴 수 있는 곳은 내부 SRAM뿐이다. DDR은 아직 초기화되지 않았고, DDR 종류·타이밍·배선은 보드마다 달라서 ROM이 알 수 없다. U-Boot proper는 수백 KB~MB라 SRAM에 안 들어간다. 그래서 U-Boot 소스에서 필요한 것만 넣은 SPL을 SRAM에 올려 DDR·PMIC·클럭을 초기화한 뒤, DRAM에 U-Boot proper와 TF-A를 올린다. SRAM이 더 작으면 TPL을 앞에 하나 더 둔다.

> The boot ROM can only load into on-chip SRAM, because DDR isn't up yet and the ROM can't know the board's DDR type, timings or layout. Full U-Boot is too big for SRAM. So we build a stripped-down U-Boot, the SPL, that fits in SRAM, initializes the PMIC rails, clocks and DDR — including PHY training — and then loads TF-A and U-Boot proper into DRAM, often from a FIT image. If SRAM is even smaller, a TPL runs before SPL just to do DDR. On i.MX8M, for example, SPL loads DDR training firmware as part of that step.

**꼬리 질문**: "What is Falcon mode?" → SPL이 U-Boot proper를 건너뛰고 커널을 바로 부팅해 부팅 시간을 줄이는 U-Boot 기능.

**Q.** "What does TF-A's BL31 do after Linux has booted?"

**A.** 사라지지 않고 EL3에 상주한다. Linux가 `smc` 명령을 실행하면 EL3로 트랩되어 BL31이 처리한다. 대표가 PSCI — 2차 CPU 켜기(`CPU_ON`), CPU hotplug, suspend, `SYSTEM_RESET`·`SYSTEM_OFF`. OP-TEE가 있으면 Normal↔Secure world 전환(Secure Monitor)도 한다. QEMU 랩에서 U-Boot의 `poweroff`나 Linux의 `poweroff -f` 뒤 마지막 줄을 BL31이 찍는 것을 봤다.

> BL31 is the EL3 runtime firmware and stays resident for the life of the system. When Linux executes an SMC instruction, it traps to EL3 and BL31 dispatches it. The main service is PSCI: bringing up secondary cores with CPU_ON, hotplug, idle and system suspend, system reset and power-off. It also hosts the SMC Calling Convention services and, if there's a trusted OS like OP-TEE, it's the secure monitor that switches between the normal and secure worlds. In my QEMU lab, the final "System Power off" message after Linux's poweroff is printed by BL31, not by the kernel.

**Q.** "How does the kernel receive its command line and device tree on arm64?"

**A.** arm64 부트 프로토콜(`Documentation/arch/arm64/booting.rst`): 부트로더가 DTB를 RAM에 놓고 x0에 그 물리 주소, x1~x3에 0을 넣고 MMU·D-cache를 끈 상태로 Image 시작에 점프한다. cmdline은 DTB의 `/chosen/bootargs`에, initrd 위치는 `/chosen/linux,initrd-start/end`에 들어 있다. 게스트에서 `/proc/cmdline`과 `/sys/firmware/devicetree/base/chosen`으로 확인할 수 있다. QEMU의 `-kernel`도 40바이트 스텁으로 똑같이 x0를 채운다.

> Through the arm64 booting protocol. The bootloader places the DTB in memory, sets x0 to its physical address and x1 to x3 to zero, and branches to the start of the Image with the MMU and data cache off, ideally at EL2. Everything else is inside the DTB: the command line is /chosen/bootargs, the initrd range is linux,initrd-start and initrd-end, memory comes from the memory node. You can verify it from userspace with /proc/cmdline and /sys/firmware/devicetree. Even QEMU's -kernel path does exactly this — I disassembled its 40-byte stub: load x0 with the DTB address, zero x1 to x3, branch to the kernel.

**Q.** "What's an initramfs for? When would you use one on an embedded product?"

**A.** 커널이 부팅 중 tmpfs에 푸는 cpio 아카이브로, 블록 장치 드라이버 없이도 쓸 수 있는 첫 rootfs다. 작은 장비는 이것 자체가 rootfs다. 큰 장비는 initramfs에서 rootfs를 준비한다 — dm-verity 검증, LUKS 복호화, A/B 슬롯 선택, 네트워크 rootfs — 그리고 `switch_root`로 넘어간다. 복구 모드 이미지로도 쓴다. 단점은 크기만큼 로드·압축 해제 시간이 든다는 것.

> An initramfs is a compressed cpio archive the kernel unpacks into a tmpfs root very early, so userspace can run before any block or network driver is ready. On small devices it can be the whole root filesystem. On bigger ones it's a staging step: set up dm-verity or decrypt the rootfs, pick the A or B slot, load firmware or modules needed to reach storage, then switch_root into the real root. It's also handy as a recovery environment. The cost is boot time — it has to be loaded and decompressed — so you keep it minimal.

**Q.** "The board prints 'Starting kernel ...' and then nothing. How do you debug it?"

**A.** 범위는 "U-Boot의 점프 ~ 커널 콘솔 등록" 사이다. 먼저 `earlycon`을 켠다 — 커널 첫 줄이 나오면 `console=` 이름이나 UART 드라이버 문제다. 안 나오면 U-Boot에서 넘기는 DTB 주소·내용(`fdt print /chosen`), Image·initrd·DTB 주소 겹침(헤더의 `image_size`), 커널 설정에 그 SoC 지원이 있는지 본다. 그래도 모르면 JTAG으로 PC를 보거나 `__log_buf`를 메모리에서 덤프한다.

> The problem is somewhere between U-Boot's jump and the kernel registering its console. First add earlycon — if early messages appear, it's a console= name or UART driver issue, like ttyS0 versus ttyAMA0. If nothing appears, check the handover: the DTB address passed to booti, its chosen node, and whether the kernel, initrd and DTB overlap given the image_size in the Image header; also confirm the kernel config supports the SoC and the earlycon UART. If it's still silent, attach JTAG: if the PC is in kernel virtual addresses the MMU came up and you can dump the printk buffer from memory; if it's near the load address it died in head.S.

**Q.** "How would you reduce boot time on an embedded Linux device?"

**A.** 먼저 단계별로 잰다(시리얼 타임스탬프, `initcall_debug`, systemd-analyze). 그 다음 큰 덩어리부터: U-Boot는 `bootdelay=0`·불필요 드라이버 제거·Falcon mode, 커널은 필요한 드라이버만 built-in·`quiet`·느린 probe를 모듈로·비동기 probe, rootfs는 initramfs 최소화·압축 방식 선택, userspace는 서비스 의존성 정리와 핵심 앱 먼저. 실제로 랩에서 115200 baud라면 커널 로그 16 KB만으로 1.4 s가 든다는 것을 계산해 봤다.

> Measure first, per stage: serial timestamps for firmware and U-Boot, initcall_debug or bootgraph for the kernel, systemd-analyze for userspace. Then attack the biggest piece. In U-Boot, bootdelay zero, strip unused drivers, or Falcon mode to skip U-Boot proper. In the kernel, build in only what the product needs, add quiet — sixteen kilobytes of boot log at 115200 baud is about 1.4 seconds of serial output — defer non-critical drivers to modules or async probe. Keep the initramfs small and pick a fast decompressor. In userspace, trim the systemd dependency graph and start the critical application early. And always measure several runs, because the variance can be bigger than the improvement.

**Q.** "What's different when you boot QEMU with -kernel versus with real firmware?"

**A.** `-kernel`이면 QEMU가 커널·initrd·DTB를 RAM에 직접 놓고 40바이트 스텁으로 점프한다. ROM·DDR 초기화·TF-A·U-Boot·서명 검증이 모두 빠진다. 그래서 PSCI는 QEMU가 `hvc`로 에뮬레이션하고, DT fixup도 없다. 커널·드라이버 개발에는 좋지만 부트 체인·전원 관리·보안은 펌웨어 경로로 확인해야 한다.

> With -kernel, QEMU itself plays bootloader: it copies the kernel, initrd and a generated DTB into RAM and runs a tiny stub that sets x0 and jumps. You skip the boot ROM, DDR init, TF-A, U-Boot, image authentication and DT fixups. PSCI is emulated by QEMU over HVC instead of handled by EL3 firmware over SMC, and you usually enter at EL1. It's great for kernel and driver work, but for anything involving the boot chain, power management or secure boot you want the firmware path — QEMU's virt machine with secure=on can run TF-A and U-Boot for that.

## 14. 직접 해보기

1. **개념**: BootROM이 DDR을 초기화하지 않는 이유를 두 가지 대고, 그 일을 맡는 단계를 i.MX8M·Raspberry Pi 4·Jetson에서 각각 말하라.
   정답/힌트: DDR 종류·타이밍·배선이 보드마다 다르고 ROM은 수정 불가 · 크기 제약. i.MX8M = U-Boot SPL, Pi 4 = GPU 펌웨어, Jetson = MB1 단계(§8, 기억 기반).
2. **로그 읽기**: §3.3 로그에서 `BL1: Booting BL31`이 `BL2:` 줄 뒤에 나오는 이유를 EL로 설명하라. TF-A를 `RESET_TO_BL2`(BL2가 EL3에서 리셋 벡터로 시작)로 빌드하면 이 줄이 어떻게 달라질지 예상하라.
   정답/힌트: S-EL1의 BL2는 SMC로 BL1(EL3)에게 BL31 실행을 부탁한다. BL2가 EL3라면 BL1 없이 BL2가 직접 BL31로 넘어가므로 BL1 줄이 없어질 것이다(예상 — 이 노트에서 빌드해 보지 않음).
3. **핸드오버 실험**: U-Boot에서 `booti` 전에 `fdt addr ${fdtcontroladdr}; fdt resize; fdt set /chosen c1-note "hello"`를 하고 부팅해서 게스트의 `/sys/firmware/devicetree/base/chosen/c1-note`에 보이는지 확인하라.
   정답/힌트: `booti`는 `fdtcontroladdr`의 DT를 복사·fixup하므로 미리 추가한 속성도 따라간다. 문자열 속성은 `cat`으로 읽힌다. 작성 중 `LAB_CMD=cat~/sys/firmware/devicetree/base/chosen/c1-note`로 확인했을 때 게스트가 `hello`를 출력했고, U-Boot의 `Loading Device Tree ... end` 주소가 속성만큼 늘었다(0x7f403087 → 0x7f40331f).
4. **주소 계산**: `kernel_addr_r = 0x40400000`이고 Image 헤더의 `image_size = 0x02980000`이다. `ramdisk_addr_r = 0x44000000`이 안전한지 계산하라. 커널을 2배로 키우면?
   정답/힌트: 0x40400000 + 0x02980000 = 0x42D80000 < 0x44000000이라 안전(여유 약 18.5 MB). 두 배(0x05300000)면 0x45700000으로 initrd 주소를 침범 — 커널이 BSS를 0으로 지우면서 initrd를 덮는다. 이 랩에서는 U-Boot가 initrd를 0x7f404000으로 옮겨서 피해 가지만, 옮기지 않는 설정(`initrd_high=0xffffffffffffffff`)이면 문제가 된다.
5. **측정 과제**: `c1_timing.sh`의 QEMU 옵션에 `-smp 4`를 추가해 8회 다시 재고 그림 4를 다시 그려라. 어느 단계가 길어지나? 2차 CPU는 누가 켜나?
   정답/힌트: 커널 단계에서 `smp: Bringing up secondary CPUs`가 PSCI `CPU_ON`(TF-A 경로는 SMC로 BL31, `-kernel`은 HVC로 QEMU)을 부른다. TCG는 vCPU를 호스트 스레드로 돌리므로 결과가 VM 부하에 더 민감해진다(이 노트에서는 실행하지 않음).
6. **PID 1 관찰**: `rdinit=/bin/sh`로 부팅하면 무엇이 달라지는가? `/proc/1/cmdline`과 마운트 상태(`cat /proc/mounts`)를 랩 기본 `/init` 경로와 비교하라.
   정답/힌트: `/init` 스크립트를 건너뛰므로 `/proc`가 마운트되지 않아 `/proc/1/cmdline`부터 읽을 수 없다 — 먼저 `mount -t proc proc /proc`. init의 첫 임무가 무엇인지 체감하는 과제.
7. **비교 정리**: TF-A+U-Boot 경로와 `-kernel` 경로에서 `dmesg | grep -i psci` 결과를 다시 뽑고, 다른 줄마다 "누가 그 PSCI 호출에 답했는가"를 적어라.
   정답/힌트: §4.4 표. `smc` + SMCCC v1.5 + `MIGRATE_INFO_TYPE not supported`는 TF-A BL31, `hvc` + v1.0 + `Trusted OS migration not required`는 QEMU 내장 PSCI.

| PSCI | Power State Coordination Interface | CPU on/off·suspend·reset·poweroff를 펌웨어에 부탁하는 표준 SMC/HVC 인터페이스 |

| U-Boot | Das U-Boot | 임베디드 표준 부트로더. 셸·환경변수·드라이버·이미지 로드 |

| XIP | eXecute In Place | flash에서 RAM 복사 없이 바로 실행 |

## 16. 요약 & 체크리스트

Linux 보드의 부팅은 "작은 것이 큰 것을 올리는" 사슬이다. 수정 불가능한 BootROM이 SRAM에 들어갈 만큼 작은 SPL(또는 TF-A BL2)을 올리고, 그것이 DDR을 살린 뒤 EL3에 상주할 TF-A BL31(+OP-TEE)과 U-Boot를 DRAM에 올린다. U-Boot는 커널 Image·DTB·initramfs를 RAM에 놓고, DTB `/chosen`에 cmdline과 initrd 위치를 써 넣고, x0에 DTB 주소를 담아 점프한다. 커널은 `head.S`에서 MMU를 켜고 `setup_arch`에서 DT를 읽고, initcall에서 드라이버를 probe하고 initramfs를 풀고, `/init`을 PID 1로 실행한다. QEMU 랩에서 이 체인을 실제로 부팅해 보니 펌웨어 단계(BL1+BL2+BL31)는 약 30 ms, U-Boot는 약 0.17 s, 커널→/init이 전체 1.1 s의 약 70%였고, 게스트의 `/proc/cmdline`·`/sys/firmware/devicetree`(`u-boot,version`, `psci method = smc`)가 핸드오버를 증명했다. `-kernel` 부팅은 QEMU가 40바이트 스텁으로 부트로더 역할을 대신하는 것이라 펌웨어 관련 문제는 보이지 않는다.

- [ ] BootROM → SPL → TF-A(BL1/BL2/BL31/BL32) → U-Boot → kernel → initramfs → PID 1을 순서대로 그리고 각 단계의 EL을 적을 수 있다
- [ ] 각 단계가 무엇을 초기화하는지(클럭, DDR, 보안, 스토리지, DT 핸드오버) 한 줄씩 말할 수 있다
- [ ] SPL이 왜 필요한지, BL31이 왜 부팅 후에도 남는지 설명할 수 있다
- [ ] arm64 부트 프로토콜(x0 = DTB, MMU off)과 Image 헤더의 `ARMd`·`image_size`를 설명할 수 있다
- [ ] U-Boot에서 `fatload`/`tftpboot`로 커널·initrd를 읽고 `booti`로 부팅할 수 있다
- [ ] `bootcmd`·`bootargs`를 저장하고, 작은따옴표가 왜 필요한지 설명할 수 있다
- [ ] 게스트에서 `/proc/cmdline`, `/sys/firmware/devicetree/base/chosen`, `psci/method`로 핸드오버를 증명할 수 있다
- [ ] QEMU `-kernel` 부팅이 건너뛰는 것 다섯 가지를 말할 수 있다
- [ ] 시리얼 로그에 시간을 찍어 단계별 부팅 시간을 여러 번 재고 중앙값으로 정리할 수 있다
- [ ] "Starting kernel ... 이후 무응답"을 earlycon → DT·주소 확인 → JTAG 순서로 디버깅할 수 있다
- [ ] i.MX8M·AM62·Raspberry Pi·Jetson의 부트 체인 차이를 큰 틀에서 비교할 수 있다
- [ ] "walk me through the Linux boot process"에 30초·2분·딥다이브 세 길이로 영어로 답할 수 있다
