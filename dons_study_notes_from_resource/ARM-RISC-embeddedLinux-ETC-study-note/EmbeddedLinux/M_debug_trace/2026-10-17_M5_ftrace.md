# M5. ftrace — function/function_graph tracer, tracepoints, trace-cmd, KernelShark, irqsoff/wakeup tracer

> **이 노트를 다 읽으면**: `/sys/kernel/tracing`의 파일만으로 함수 호출·이벤트·지연을 기록하고 읽을 수 있다 · "꺼져 있을 때 오버헤드가 거의 0"인 이유를 arm64 명령어 수준(NOP 두 개 → `BL ftrace_caller` 패치)으로 설명할 수 있다 · tracepoint 필터·hist 트리거·synthetic event, kprobe/fprobe/uprobe 동적 이벤트로 "가끔 느린 read"의 원인을 직접 찾을 수 있다 · irqsoff/preemptoff/wakeup_rt tracer와 trace-cmd로 지연의 범인을 이름까지 짚을 수 있다
> **왜 필요한가**: "센서 read가 가끔 5 ms 걸린다", "모터 제어 루프가 가끔 한 주기를 놓친다" 같은 **지연·순서 문제**는 printk로는 못 잡는다(printk 자체가 수십 µs ~ ms를 먹는다). 면접에서도 "How would you debug an occasional latency spike?"는 Embedded Linux·로보틱스 포지션의 단골이다
> **Don 기준 난이도**: 링버퍼·타임스탬프 로그·로직 분석기로 "누가 언제 무엇을"을 맞추는 사고방식은 이미 있다 / tracefs 인터페이스, dynamic ftrace의 코드 패치, tracepoint·kprobe 문법, 트리거, latency tracer 해석은 새로 배운다
> **선행 노트**: E3(커널 모듈), E6(유저↔커널 경계, syscall 경로), F1(스케줄러 — §9에서 sched 이벤트·wakeup_rt 맛보기), F6(인터럽트 — §10 irqsoff tracer 맛보기), F12(VFS — function_graph로 open 경로), M3(Oops 해독)

## 0. 큰 그림 — 이게 왜 필요한가

SSD 펌웨어를 할 때 "가끔 커맨드 하나가 늦게 끝난다"를 어떻게 잡았는지 떠올려 보자. 아마 이런 것들을 썼을 것이다.

- 펌웨어 안의 **trace 링버퍼**: 이벤트 ID + 타임스탬프(사이클 카운터) + 인자 몇 개를 RAM 링버퍼에 쌓고, 문제가 나면 JTAG으로 덤프한다. 링버퍼라서 오래된 것은 덮어쓴다. printf는 너무 느려서 못 쓴다.
- **ARM CoreSight ETM/ITM**: 하드웨어가 명령어 흐름을 뽑아 준다. 코드 수정 없이 "어느 함수를 언제" 볼 수 있다.
- **로직 분석기 + GPIO 토글**: 구간 시작/끝에 핀을 올리고 내려서 실제 시간을 잰다.

**ftrace는 이 세 가지를 Linux 커널 안에 소프트웨어로 넣어 둔 것**이다.

- per-CPU **ring buffer**에 타임스탬프 찍힌 레코드를 lock 없이 쌓는다 (펌웨어 trace 링버퍼와 같은 발상).
- **function tracer**: 커널의 거의 모든 함수 입구에 컴파일러가 NOP 자리를 만들어 두었다가, 켤 때만 그 NOP을 `BL ftrace_caller`로 고쳐 쓴다 (ETM처럼 "코드 수정 없이 함수 흐름 보기"를 소프트웨어로).
- **tracepoint(event)**: 커널 개발자가 중요한 지점(`sched_switch`, `irq_handler_entry`, `kmalloc` …)에 미리 박아 둔 이벤트. 펌웨어의 "trace ID 찍는 매크로"와 같다.
- **kprobe/uprobe**: 실행 중에 아무 함수(커널·유저)에나 이벤트를 붙인다. 디버거의 breakpoint를 "멈추지 않고 기록만" 하는 버전이다.
- **latency tracer**(irqsoff, preemptoff, wakeup_rt): "IRQ가 꺼져 있던 가장 긴 구간"처럼 **최악값 하나를 자동으로 잡아** 그 구간의 함수 흐름을 보관한다. 로직 분석기의 "pulse width > N 트리거"와 같은 역할이다.
- 이 모든 것을 **파일 시스템(tracefs, `/sys/kernel/tracing`)의 파일에 `echo`/`cat`** 하는 것으로 제어한다. 별도 도구가 없어도 BusyBox 셸만 있으면 된다. `trace-cmd`는 그 위의 편한 CLI, KernelShark는 GUI 뷰어다.

그림 1 — ftrace의 구조. 여러 종류의 hook이 같은 per-CPU ring buffer에 기록하고, 사람은 tracefs 파일이나 trace-cmd로 꺼내 본다. hist 트리거는 버퍼에 쓰지 않고 커널 안에서 바로 집계한다.

이름 정리부터 하자. 좁은 뜻의 **ftrace**는 "function tracer"이지만, 실무에서는 tracefs 아래의 **추적 프레임워크 전체**(tracer + event + 동적 probe + ring buffer)를 ftrace라고 부른다. perf(M6)와 eBPF(M7)도 같은 tracepoint·kprobe를 쓰지만 데이터를 다른 길로 뽑는다. 이 노트는 tracefs 쪽만 다룬다. osnoise/timerlat/hwlat tracer와 `rtla`는 N3에서 다룬다.

### 0.1 이 노트의 랩 환경

모든 실습은 공용 랩의 **trace 커널** `out/Image-trace`(Linux 6.18.55-trace: function/function_graph+retval, dynamic ftrace, irqsoff/preemptoff/wakeup, hist 트리거, kprobe/uprobe/fprobe 이벤트, BTF)와 **`rootfs-trace.ext4`**(Ubuntu 24.04 + systemd, gcc, trace-cmd 3.2.0, rt-tests)를 QEMU `virt`(`-cpu cortex-a57,pmu=on -smp 2 -m 1G`, TCG)로 부팅해서 돌렸다. 이미지는 `/var/tmp/M5/`로 복사해서 썼다. 부팅 스크립트의 핵심:

```sh
qemu-system-aarch64 -machine virt -cpu cortex-a57,pmu=on -smp 2 -m 1G -display none \
  -kernel /var/lab/out/Image-trace \
  -drive file=/var/tmp/M5/m5_root.ext4,if=virtio,format=raw \
  -netdev user,id=n0 -device virtio-net-pci,netdev=n0 \
  -virtfs local,path=/var/tmp/M5/share,mount_tag=m5share,security_model=none,id=m5fs \
  -gdb unix:/var/tmp/M5/m5_gdb.sock,server=on,wait=off \
  -chardev socket,id=s0,path=/var/tmp/M5/m5_ser.sock,server=on,wait=off,logfile=/var/tmp/M5/serial.log \
  -serial chardev:s0 -monitor none \
  -append "console=ttyAMA0 root=/dev/vda rw rootwait nokaslr systemd.default_device_timeout_sec=900"
```

- `-virtfs`: VM 쪽 디렉터리를 게스트에 9p로 공유한다(`mount -t 9p -o trans=virtio,version=9p2000.L m5share /mnt/m5`). 스크립트·소스·`.ko`를 이 길로 넣었다.
- `-gdb unix:...`: QEMU gdbstub. 이 노트에서는 **JTAG 대용**으로, 커널이 자기 코드를 고쳐 쓰는 순간을 밖에서 메모리 덤프로 확인하는 데 쓴다(§2). `nokaslr`은 gdb 심볼 주소와 실제 주소를 맞추려고 넣었다.
- 게스트 셸은 직렬 소켓에 붙는 작은 Python 스크립트로 명령을 보내고 출력을 받았다.

> **TCG 주의 (숫자 읽는 법)**: QEMU가 KVM 없이 소프트웨어 에뮬레이션(TCG)으로 돌고, 같은 VM에서 다른 작성자 16명이 동시에 빌드·부팅을 돌려 VM load average가 10~26이었다. 그래서 이 노트의 **절대 시간(µs, ms)은 실제 보드 숫자가 아니다**. 예를 들어 `getpid()` 한 번이 게스트에서 약 15 µs인데 같은 VM 호스트 커널(`uname -r` → `7.0.0-38-generic`)에서는 476 ns였다. 또 게스트의 vCPU 스레드가 호스트에서 밀려나면 "아무 함수도 안 찍힌 10 ms 공백"이 생긴다(§9.4). **비율과 구조(무엇이 무엇보다 몇 배, 어떤 함수가 범인)는 그대로 유효하다.**

실습에 쓴 프로그램은 다섯 개다. 전부 이 노트 본문에 있다.

| 이름 | 종류 | 역할 |
|---|---|---|
| `m5_lat.ko` | 커널 모듈 | `/dev/m5_sensor`(read 한 번에 `udelay(50)` = "50 µs 센서 읽기"), 200 ms마다 같은 mutex를 5 ms 잡는 `m5_calib` 스레드, debugfs `irqoff_us`/`preemptoff_us`(쓰면 그만큼 IRQ/preempt를 끄고 busy-wait) |
| `m5_tp.ko` | 커널 모듈 | 자기 `TRACE_EVENT(m5_sample)`을 가진 "드라이버" (§5.6) |
| `m5_app` | 유저 C | `/dev/m5_sensor`를 1 kHz로 읽고, 느린 read와 phase를 `trace_marker`에 남긴다 |
| `m5_uprobe` | 유저 C | uprobe를 걸 함수 `m5_process()` |
| `m5_bench` | 유저 C | `getpid()` 루프로 tracing 오버헤드 측정 |

모듈 소스 (두 조각을 합쳐 한 파일 `m5_lat.c`, 빌드는 `make -C /var/lab/out/linux-build-trace M=$PWD`, 경고 0개):

```c
/* m5_lat.c (1/2): IRQ/preempt-off culprit + debugfs knobs */
#include <linux/module.h>
#include <linux/debugfs.h>
#include <linux/delay.h>
#include <linux/miscdevice.h>
#include <linux/fs.h>
#include <linux/mutex.h>
#include <linux/kthread.h>
#include <linux/uaccess.h>

static struct dentry *m5_dir;
static DEFINE_MUTEX(m5_bus_lock);          /* the shared "I2C bus" */
static struct task_struct *m5_calib_task;
static u32 m5_seq;

static noinline void m5_irqoff_section(u64 us)
{
	unsigned long flags;
	local_irq_save(flags);
	udelay(us);                             /* BAD: busy-wait with IRQs off */
	local_irq_restore(flags);
}
static noinline void m5_preemptoff_section(u64 us)
{
	preempt_disable();
	udelay(us);
	preempt_enable();
}
static int irqoff_set(void *d, u64 us) { m5_irqoff_section(us); return 0; }
static int preemptoff_set(void *d, u64 us) { m5_preemptoff_section(us); return 0; }
DEFINE_DEBUGFS_ATTRIBUTE(irqoff_fops, NULL, irqoff_set, "%llu\n");
DEFINE_DEBUGFS_ATTRIBUTE(preemptoff_fops, NULL, preemptoff_set, "%llu\n");

static noinline int m5_bus_xfer(void) { udelay(50); return 0; }  /* 50 us read */
static noinline void m5_calibrate(void)                          /* 5 ms hog */
{
	trace_printk("calib start seq=%u\n", m5_seq);
	mdelay(5);
}
```

```c
/* m5_lat.c (2/2): /dev/m5_sensor + calibration thread */
static ssize_t m5_sensor_read(struct file *f, char __user *buf, size_t n, loff_t *pos)
{
	u32 v;
	if (n < sizeof(v))
		return -EINVAL;
	mutex_lock(&m5_bus_lock);
	m5_bus_xfer();
	v = ++m5_seq;
	mutex_unlock(&m5_bus_lock);
	return copy_to_user(buf, &v, sizeof(v)) ? -EFAULT : sizeof(v);
}
static const struct file_operations m5_sensor_fops = {
	.owner = THIS_MODULE, .read = m5_sensor_read,
};
static struct miscdevice m5_misc = {
	.minor = MISC_DYNAMIC_MINOR, .name = "m5_sensor", .fops = &m5_sensor_fops,
};
static int m5_calib_fn(void *arg)          /* every 200 ms: hold the bus 5 ms */
{
	while (!kthread_should_stop()) {
		msleep_interruptible(200);
		mutex_lock(&m5_bus_lock);
		m5_calibrate();
		mutex_unlock(&m5_bus_lock);
	}
	return 0;
}
static int __init m5_init(void)
{
	int ret = misc_register(&m5_misc);
	if (ret)
		return ret;
	m5_dir = debugfs_create_dir("m5", NULL);
	debugfs_create_file_unsafe("irqoff_us", 0200, m5_dir, NULL, &irqoff_fops);
	debugfs_create_file_unsafe("preemptoff_us", 0200, m5_dir, NULL, &preemptoff_fops);
	m5_calib_task = kthread_run(m5_calib_fn, NULL, "m5_calib");
	if (IS_ERR(m5_calib_task)) {
		debugfs_remove_recursive(m5_dir);
		misc_deregister(&m5_misc);
		return PTR_ERR(m5_calib_task);
	}
	pr_info("m5_lat: loaded\n");
	return 0;
}
static void __exit m5_exit(void)
{
	kthread_stop(m5_calib_task);
	debugfs_remove_recursive(m5_dir);
	misc_deregister(&m5_misc);
}
module_init(m5_init);
module_exit(m5_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("M5 ftrace demo");
```

이 모듈에는 **일부러 심어 둔 버그가 세 개** 있다. (1) IRQ를 끈 채 busy-wait, (2) preempt를 끈 채 busy-wait, (3) 센서 read와 같은 mutex를 5 ms씩 잡는 calibration 스레드. 노트 전체가 "ftrace로 이 셋을 이름까지 찾아내기"다.

## 1. tracefs 한 바퀴 — 파일이 곧 API

### 1.1 어디에 있나

tracefs는 `/sys/kernel/tracing`에 mount 된다. systemd 시스템은 자동으로 mount 하고, BusyBox initramfs에서는 직접 해야 한다(`mount -t tracefs nodev /sys/kernel/tracing`). 옛 경로 `/sys/kernel/debug/tracing`도 debugfs를 mount 하면 자동으로 보이지만, 새 코드는 `/sys/kernel/tracing`을 쓴다(debugfs 없이 tracefs만 켤 수 있어서 보안상 낫다).

### 1.2 예제 1 — 무엇이 있는지 둘러보기

무엇을 확인하나: tracefs 최상위 파일, 쓸 수 있는 tracer, 버퍼 크기, 추적 가능한 함수·이벤트 수.

```sh
# lib.sh: reset tracefs to a clean state before each experiment
T=/sys/kernel/tracing
treset() {
  echo 0 > $T/tracing_on
  echo nop > $T/current_tracer
  echo > $T/set_ftrace_filter; echo > $T/set_ftrace_notrace
  echo > $T/set_graph_function; echo > $T/set_ftrace_pid; echo > $T/set_event_pid
  echo 0 > $T/events/enable
  echo 0 > $T/tracing_thresh; echo 0 > $T/max_graph_depth
  echo 0 > $T/options/trace_printk; echo > $T/trace
}
```

(마지막 줄 `options/trace_printk` 끄기는 §3.2·§5.5 실습 뒤에 추가했다. 그 전 출력에는 `trace_printk` 줄이 섞여 있다.) `trace-cmd reset`도 같은 일을 한다(§11).

## 2. 꺼져 있을 때 오버헤드가 거의 0인 이유 — dynamic ftrace

### 2.1 직관 — "모든 함수 앞에 빈 칸을 남겨 둔다"

함수 7만 개 각각에 "추적 코드"를 넣어 두면 느려진다. 그렇다고 빼 두면 필요할 때 커널을 다시 빌드해야 한다. ftrace의 답은 **컴파일러에게 모든 함수 입구에 NOP 명령 자리를 만들게 하고, 실행 중에 그 NOP을 call 명령으로 고쳐 쓰는 것**이다.

- 꺼져 있을 때: 함수마다 NOP 몇 개. CPU는 NOP을 거의 공짜로 흘려보낸다(디코드만 하고 실행 유닛을 거의 안 쓴다). 그래서 "near-zero overhead".
- 켤 때: 고르고 싶은 함수의 NOP만 `BL ftrace_caller`로 바꾼다. 필터에 없는 함수는 계속 NOP이다.

펌웨어 비유: 플래시에 있는 코드에 "패치 슬롯"을 미리 비워 두고, 필드에서 디버그가 필요하면 그 슬롯에 branch를 써 넣는 ROM patch 기법과 같다. 다른 점은 Linux 커널 텍스트는 RAM에 있어서 커널이 스스로 고칠 수 있다는 것뿐이다.

### 2.2 역사 — `mcount`에서 `patchable-function-entry`로

- 옛날(그리고 x86 일부 설정)에는 gcc `-pg`가 모든 함수 입구에 `call mcount`(x86-64에서는 `__fentry__`)를 넣었다. 원래 gprof용이다. 커널은 부팅 때 이 call들을 전부 NOP으로 바꿔 두고(`recordmcount`/`objtool`이 위치를 목록으로 모아 둔다), 켤 때 다시 call로 바꾼다.
- arm64는 `-fpatchable-function-entry=N,M` 옵션을 쓴다. 컴파일러가 처음부터 **NOP N개**를 넣고 그중 M개는 함수 시작 주소 **앞**에 둔다. 위치 목록은 `__patchable_function_entries` 섹션에 남는다. 6.18.55의 `arch/arm64/Makefile`:

```make
  CC_FLAGS_FTRACE := -fpatchable-function-entry=4,2   # DYNAMIC_FTRACE_WITH_CALL_OPS
  CC_FLAGS_FTRACE := -fpatchable-function-entry=2     # otherwise
```

이 랩 커널은 `CONFIG_DYNAMIC_FTRACE_WITH_CALL_OPS=y`라서 **함수 앞 2개 + 입구 2개 = NOP 4개**다. 앞의 2개(8바이트)는 명령이 아니라 **"이 함수를 담당하는 `ftrace_ops` 포인터"를 저장하는 데이터 칸**으로 쓰인다. `ftrace_caller`는 이 칸을 읽어 콜백을 바로 부른다(모든 콜백 리스트를 도는 것보다 빠르다).

### 2.3 예제 2 — 빌드된 `vmlinux`의 `vfs_read` 입구 (컴파일 직후 상태)

무엇을 확인하나: 컴파일러가 넣은 NOP이 실제로 함수 앞뒤에 있는지.

```sh

objdump -d --start-address=0x$(printf %x $((0x$A-8))) --stop-address=0x$(printf %x $((0x$A+20))) /var/lab/out/vmlinux-trace | tail -8
```

### 2.4 예제 3 — 실행 중인 커널을 gdbstub(JTAG 대용)으로 들여다보기

무엇을 확인하나: 부팅 후, function tracer를 켜기 전·후·끈 뒤에 `vfs_read` 입구의 명령이 실제로 바뀌는지. 게스트를 잠깐 세우고 메모리를 읽는 것은 JTAG으로 RAM을 덤프하는 것과 같다.

```sh

cd /var/tmp/M5
gdb -q -batch -nx /var/lab/out/vmlinux-trace \
  -ex 'target remote m5_gdb.sock' \
  -ex 'x/5i vfs_read-8' -ex 'x/5i __arm64_sys_getpid-8' \
```

### 2.5 커널은 실행 중인 코드를 어떻게 안전하게 고치나

다른 CPU가 바로 그 명령을 실행하고 있을 수 있다. 어떻게 안전한가?

- arm64 아키텍처는 **`B`/`BL`/`NOP` 사이의 4바이트 교체를 다른 CPU가 동시에 실행해도 안전한 수정**으로 허용한다(옛 명령 아니면 새 명령 중 하나가 실행된다). 그래서 6.18의 arm64 `ftrace_modify_code()`는 `aarch64_insn_patch_text_nosync()`로 한 워드를 쓰고 I-cache를 flush 할 뿐, 모든 CPU를 세우는 `stop_machine()`을 쓰지 않는다 (`arch_ftrace_update_code()`가 `FTRACE_MAY_SLEEP`을 붙여 `ftrace_modify_all_code()`를 부른다).
- 커널 텍스트는 평소에 읽기 전용으로 매핑돼 있으므로, 패치는 임시 쓰기 가능 매핑(fixmap)을 통해 한다.
- 이 "켜고 끄기"에 걸린 시간은 `dyn_ftrace_total_info`의 `update time`으로 보인다.

x86은 `call`이 5바이트라 한 번에 원자적으로 못 바꿔서, int3 breakpoint를 먼저 써 넣고 나머지를 고친 다음 int3를 지우는 3단계(`text_poke_bp`)를 쓴다. 면접에서 아키텍처 차이를 말할 수 있으면 좋다.

함정:
- `notrace` 표시(`__attribute__((no_instrument_function))`)된 함수, `__init` 일부, inline 된 함수, `static` 함수가 컴파일러에 의해 사라진 경우는 `available_filter_functions`에 없다. 소스에 있는 이름이 추적 가능한 이름이라는 보장은 없다 — 항상 이 파일을 먼저 grep 한다(F12 §2 함정과 같은 이야기).
- 컴파일러가 `m5_bus_xfer`를 `m5_bus_xfer.isra.0`으로 바꿔 놓을 수 있다(§3.3 출력). 이름에 `.isra`, `.constprop`, `.part`가 붙은 복제본은 원래 이름으로 필터하면 안 걸린다. glob(`m5_bus_xfer*`)을 쓴다.

## 3. function tracer — "어떤 함수가 불렸나"

### 3.1 기본 흐름

1. `set_ftrace_filter`에 볼 함수를 쓴다 (glob 가능: `vfs_*`, `*spi*`). 비워 두면 **전부**다 — 7만 개 함수 전부는 무겁다(§13).
2. 필요하면 `set_ftrace_pid`로 프로세스를 좁힌다.
3. `echo function > current_tracer`, `tracing_on` 1 → 작업 → 0.
4. `trace`를 읽는다.

한 프로세스만 정확히 잡는 요령: 셸이 **자기 PID를 `set_ftrace_pid`에 쓰고 나서 `exec`로 대상 프로그램이 된다**. `exec`는 PID를 유지하므로 대상 프로그램의 처음부터 끝까지가 잡힌다.

### 3.2 예제 4 — `vfs_*` 함수만, `cat` 한 번만

```text
 1)    cat-1001    |   7.040 us    |      } /* _raw_spin_unlock ret=0x100000000 */
 1)    cat-1001    | + 22.864 us   |    } /* put_unused_fd ret=0x100000000 */
 1)    cat-1001    |               |    putname() {
 1)    cat-1001    |   2.784 us    |      kmem_cache_free(); /* ret=0xffff000005352300 */
 1)    cat-1001    |   7.792 us    |    } /* putname ret=0xffff000005352300 */
 1)    cat-1001    | ! 329.680 us  |  } /* do_sys_openat2 ret=-2 */
```

출력에서 볼 것:
- 흐름: 이름 복사(`getname_flags`) → fd 번호 예약(`alloc_fd` ret=3) → 경로 탐색 `path_openat` → **`link_path_walk()`가 `-2`(= `-ENOENT`)** → 위로 전파 → 예약한 fd 반납(`put_unused_fd`) → `ret=-2`. **`-ENOENT`가 처음 나타난 함수**를 바로 짚을 수 있다. 드라이버 `probe`가 `-EINVAL`을 내는데 어디서인지 모를 때 똑같이 쓴다(예: `set_graph_function`에 `really_probe`).
- `ret=` 값은 그냥 x0 레지스터다. `void` 함수(`_raw_spin_unlock`)나 포인터 반환 함수도 x0 값이 찍힌다. **의미 있는 값인지는 함수 시그니처를 보고 판단**한다. `funcgraph-retval-hex`를 끄면 작은 음수는 10진 에러 코드로 보인다.
- 시간(µs)은 **추적 비용이 섞인 값**이다(그리고 TCG). function_graph의 duration은 "어디가 상대적으로 무거운가"를 보는 용도지 절대 지연 측정용이 아니다.

함정: 첫 시도에서 트리 맨 앞에 `mutex_unlock()` 아래 `unwind_find_stack`, `gic_handle_irq`(IRQ가 끼어든 것) 같은 줄이 섞였다. `sh`가 `set_ftrace_pid`에 쓰는 바로 그 순간부터 기록되기 때문이다. 그래서 출력을 `grep -B`로 원하는 블록만 잘랐다. IRQ 안 함수는 `options/funcgraph-irqs`를 0으로 하면 뺄 수 있다.

## 5. tracepoint(event) — 커널 개발자가 박아 둔 관측 지점

### 5.1 정의

**tracepoint**는 소스에 고정으로 들어간 `trace_<이름>(인자…)` 호출이다. `TRACE_EVENT()` 매크로 하나로 ① 레코드 구조체 ② 인자를 레코드에 복사하는 코드 ③ 사람이 읽는 출력 형식 ④ tracefs 파일(`enable`/`filter`/`format`…)이 전부 생성된다. 꺼져 있을 때 호출 지점은 **static key(jump label) NOP 하나**다 — function tracer의 NOP과 같은 발상인데, 이건 함수 입구가 아니라 소스의 원하는 위치에 있다(§5.6에서 직접 확인).

function tracer와 비교:

| | function tracer | tracepoint |
|---|---|---|
| 위치 | 모든 함수 입구 (자동) | 개발자가 고른 지점 |
| 데이터 | 함수 이름 + 호출자 | **의미 있는 필드** (`prev_comm`, `bytes_req`, `irq` …) |
| 안정성 | 함수 이름은 버전마다 바뀜 | 비교적 안정 (도구들이 의존) |
| 필터 | 함수 이름 | 필드 값 (`bytes_req > 4096`) |
| 비용 | 켜면 함수마다 | 켠 이벤트만 |

### 5.2 사용법

```sh
cd /sys/kernel/tracing
cat available_events | grep sched_             # subsys:event 목록
echo 1 > events/sched/sched_switch/enable       # 하나 켜기
echo 1 > events/irq/enable                      # 서브시스템 통째로
echo 'sched:sched_wakeup' >> set_event          # 같은 일, 다른 인터페이스
cat events/sched/sched_switch/format            # 필드 정의
echo 'prev_comm ~ "m5_*"' > events/sched/sched_switch/filter   # 필드 필터
```

필터 문법: `==`, `!=`, `<`, `>`, `<=`, `>=`, `&`(비트), 문자열 `==`/`!=`/`~`(glob), `&&`, `||`, 괄호. 잘못 쓰면 `error_log`가 위치를 짚어 준다:

```text
[ 2457.614543] event filter parse error: error: Invalid value (did you forget quotes)?
  Command: bytes_req >> 3
                       ^
```

### 5.3 예제 8 — sched 이벤트로 "누가 언제 CPU를 잡았나"

무엇을 확인하나: `sched_switch`/`sched_wakeup`에 이름 필터를 걸고, 센서 앱(`m5_app`)과 `m5_calib` 스레드만 기록한다. `m5_app`은 느린 read를 `trace_marker`로 표시한다(§7). 앱 소스:

```c
/* m5_app: read /dev/m5_sensor N times, mark phases + slow reads in trace_marker */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <fcntl.h>
#include <unistd.h>
#include <time.h>
#include <stdint.h>

static int mfd = -1;
static void mark(const char *s)
{
	if (mfd >= 0 && write(mfd, s, strlen(s)) < 0)
		perror("trace_marker");
}
static uint64_t now_ns(void)
{
	struct timespec ts;
	clock_gettime(CLOCK_MONOTONIC, &ts);
	return (uint64_t)ts.tv_sec * 1000000000ull + ts.tv_nsec;
}
int main(int argc, char **argv)
{
	int n = argc > 1 ? atoi(argv[1]) : 500;
	uint64_t thr_us = argc > 2 ? strtoull(argv[2], NULL, 0) : 1000;
	int fd = open("/dev/m5_sensor", O_RDONLY);
	if (fd < 0) { perror("open /dev/m5_sensor"); exit(1); }
	mfd = open("/sys/kernel/tracing/trace_marker", O_WRONLY);
	uint64_t max = 0, sum = 0; int slow = 0;
	char msg[96];
	mark("phase=read_loop begin");
	for (int i = 0; i < n; i++) {
		uint32_t v;
		uint64_t t0 = now_ns();
		if (read(fd, &v, sizeof(v)) != sizeof(v)) { perror("read"); exit(1); }
		uint64_t d = now_ns() - t0;
		sum += d; if (d > max) max = d;
		if (d > thr_us * 1000) {      /* slow: tag it in the kernel trace */
			slow++;
			snprintf(msg, sizeof(msg), "SLOW read i=%d took %llu us", i,
				 (unsigned long long)(d / 1000));
			mark(msg);
		}
		usleep(1000);                 /* 1 kHz sensor loop */
	}
	mark("phase=read_loop end");
	printf("reads=%d avg=%llu us max=%llu us slow(>%llu us)=%d\n", n,
	       (unsigned long long)(sum / n / 1000), (unsigned long long)(max / 1000),
	       (unsigned long long)thr_us, slow);
	return 0;
}
```

게스트에서 `gcc -std=gnu11 -Wall -Wextra -O2`로 빌드(경고 0개). 추적 스크립트:

### 5.4 트리거 — 이벤트가 일어나면 "무언가를 한다"

`events/<subsys>/<event>/trigger`에 쓴다. 필터(`if ...`)와 횟수(`:N`)를 붙일 수 있다.

| 트리거 | 하는 일 |
|---|---|
| `traceon` / `traceoff` | 기록 켜기/끄기 (문제 순간에 버퍼 얼리기) |
| `snapshot` | 지금 버퍼를 snapshot 버퍼로 바꿔치기 (§10.3) |
| `stacktrace` | 이 이벤트의 커널 콜스택 기록 |
| `enable_event:<sys>:<ev>` / `disable_event:` | 다른 이벤트를 켜고 끄기 |
| `hist:keys=...:vals=...` | **커널 안에서 히스토그램 집계** (버퍼에 안 씀) |

### 5.7 예제 11 — 내 드라이버에 tracepoint 넣기 (`TRACE_EVENT`)

드라이버를 쓰는 사람에게 가장 실용적인 부분이다. printk 대신 tracepoint를 넣으면 ① 꺼져 있을 때 비용이 NOP 하나 ② 켜면 µs 단위 타임스탬프와 함께 다른 커널 이벤트와 같은 타임라인에 섞인다 ③ 필드로 필터·hist가 된다. 무엇을 확인하나: 모듈 하나에 `m5:m5_sample` 이벤트를 정의하고, 플래그 필드로 필터한다.

```c

#define TRACE_SYSTEM m5

#define _M5_TRACE_H
#include <linux/tracepoint.h>

	TP_PROTO(u32 seq, s32 mdeg, u32 status),
	TP_ARGS(seq, mdeg, status),
	TP_STRUCT__entry(
		__field(u32, seq)
		__field(s32, mdeg)
		__field(u32, status)
	),

		__entry->seq = seq;
		__entry->mdeg = mdeg;
		__entry->status = status;
	),

				{ 1, "VALID" }, { 2, "OVERHEAT" }, { 4, "CRC_ERR" }))
);
#endif /* _M5_TRACE_H */

#define TRACE_INCLUDE_PATH .
#define TRACE_INCLUDE_FILE m5_trace

```

```c
// m5_tp: a driver-style module with its own TRACE_EVENT
#include <linux/module.h>
#include <linux/kthread.h>
#include <linux/delay.h>
#define CREATE_TRACE_POINTS
#include "m5_trace.h"

static struct task_struct *m5_tp_task;

static int m5_tp_fn(void *arg)
{
	u32 seq = 0;
	while (!kthread_should_stop()) {
		s32 mdeg = 40000 + (seq % 7) * 6500;      /* fake temperature */
		u32 st = 1 | (mdeg > 75000 ? 2 : 0) | (seq % 11 == 10 ? 4 : 0);
		trace_m5_sample(seq++, mdeg, st);           /* ~1 NOP when disabled */
		msleep(50);
	}

}

{

}
static void __exit m5_tp_exit(void) { kthread_stop(m5_tp_task); }
module_init(m5_tp_init);
module_exit(m5_tp_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("M5 ftrace demo");
```

## 6. 동적 이벤트 — kprobe, kretprobe, fprobe, uprobe

### 6.1 무엇이 다른가

tracepoint는 미리 박아 둔 곳에만 있다. 원하는 곳에 없으면? **실행 중에 만든다.**

| 종류 | 정의 파일 | 문법 첫 글자 | 붙는 곳 | 구현 (arm64) |
|---|---|---|---|---|
| kprobe | `kprobe_events` | `p:` | 커널 함수 (+오프셋) | 그 자리 명령을 `BRK`로 바꿔 예외로 진입 |
| kretprobe | `kprobe_events` | `r:` | 커널 함수 리턴 | 리턴 주소 가로채기 |
| fprobe | `dynamic_events` | `f:` | 커널 함수 입구/리턴(`%return`) | **ftrace 패치 자리** 재사용 (BRK 없음) |
| uprobe / uretprobe | `uprobe_events` | `p:` / `r:` | 유저 바이너리 오프셋 | 유저 코드 페이지에 `BRK` |
| eprobe | `dynamic_events` | `e:` | 기존 이벤트의 필드를 가공 | 이벤트 위에 얹기 |

인자 가져오기: `$arg1..N`(함수 인자, arm64 x0~x7), `%x0`(레지스터), `+off(주소)`(메모리 역참조), `$retval`, `$comm`, 타입 `:s32`/`:u64`/`:x64`/`:string`/`:ustring`(유저 공간 문자열). BTF가 있는 커널(`CONFIG_PROBE_EVENTS_BTF_ARGS`)은 **인자 이름**(`filename`, `how->flags`)을 그대로 쓸 수 있다.

### 6.2 예제 12 — `do_sys_openat2`에 kprobe + kretprobe + BTF fprobe

무엇을 확인하나: 세 방식으로 같은 함수의 인자·반환값을 뽑고, 정의가 어떻게 정규화되는지 본다.

```sh
. /mnt/m5/lib.sh; treset; cd $T
echo 'p:m5/open do_sys_openat2 dfd=$arg1:s32 path=+0($arg2):ustring' > kprobe_events
echo 'r:m5/open_ret do_sys_openat2 ret=$retval:s64' >> kprobe_events   # s64: see the pitfall below
echo 'f:m5/open_btf do_sys_openat2 dfd filename:ustring how->flags:x64' >> dynamic_events
cat dynamic_events
echo 1 > events/m5/enable
sh -c "echo \$\$ > $T/set_event_pid; echo 1 > $T/tracing_on; exec cat /etc/hostname /nope > /dev/null 2>&1"
echo 0 > tracing_on
grep -v '^#' trace | grep -v 'so\.\|ld.so' | cut -c1-150 | tail -8
echo 0 > events/m5/enable; echo > dynamic_events; echo > set_event_pid
```

이 첫 실행은 kretprobe를 `ret=$retval:s64`로 정의했다. `:s32`로 고쳐 다시 돌린 실행의 마지막 줄:

```text
             cat-1323    [001] d..1.  1392.296087: open_ret: (__arm64_sys_openat+0x70/0xc8 <- do_sys_openat2) ret=-2
```

출력에서 볼 것:
- `dfd=-100`은 `AT_FDCWD`, 경로 문자열이 유저 메모리에서 그대로 읽혔다(`:ustring`). `/nope`의 반환값은 `-2`(ENOENT)인데, 첫 실행에서는 `4294967294`(= 0xfffffffe)로 찍혔다 — 아래 함정.
- **kprobe는 `+0x0`, fprobe는 `+0x4`**: fprobe는 ftrace의 `bl ftrace_caller` 자리(함수+4)를 쓴다. kprobe는 함수 첫 명령에 BRK를 쓴다. kprobe 줄의 플래그 `d....`(IRQ off) — BRK 예외 핸들러 안에서 기록되기 때문이다.
- `r10:` — kretprobe가 동시에 추적할 수 있는 인스턴스 수(maxactive)를 커널이 기본값 10으로 채워 넣었다.
- BTF 이름 방식은 오프셋 계산이 필요 없다. F12 §8에서는 BTF가 없는 debug 커널이라 `+0x..(...)` 오프셋을 손으로 계산해야 했다 — BTF가 있으면 `how->flags`처럼 C 문법으로 쓴다. `flags=0x20000`은 arm64의 `O_LARGEFILE`(cat이 넣는 플래그)다.

함정 (실제로 겪음):
- `ret=$retval:s64`로 썼더니 `-2`가 `4294967294`로 나왔다. x0의 하위 32비트만 `0xfffffffe`이고 상위 32비트가 0이었다는 뜻이다(32비트 값으로 다뤄진 결과). **타입을 실제 반환값 폭에 맞춰라** — `:s32`로 바꾸자 `-2`.
- 첫 실행 뒤 `set_event_pid`를 비우지 않아 다음 uprobe 실습에서 **아무것도 안 찍혔다**. 이벤트 PID 필터가 이전 `cat`의 PID로 남아 있었기 때문이다.

### 6.3 예제 13 — uprobe/uretprobe: 유저 함수의 인자와 반환값

무엇을 확인하나: 다시 빌드하지 않고, 실행 중인 유저 프로그램의 함수 인자를 커널 trace에 함께 기록한다.

```c
/* m5_uprobe: a user function to attach a uprobe (and uretprobe) to */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

__attribute__((noinline)) int m5_process(int id, int raw)
{
	int v = raw * 3 - 7 + id;     /* pretend calibration */
	__asm__ volatile("" ::: "memory");
	return v;
}
int main(int argc, char **argv)
{
	int n = argc > 1 ? atoi(argv[1]) : 5, acc = 0;
	for (int i = 0; i < n; i++) {
		acc += m5_process(i, 100 + i * 10);
		usleep(10000);
	}
	printf("acc=%d\n", acc);
	return 0;
}
```

- 이 방식으로 **앱의 함수(예: `process_frame()`)와 커널 이벤트를 같은 타임라인에** 놓을 수 있다. 앱을 다시 빌드할 수 없을 때 유용하다(소스를 고칠 수 있으면 §7의 trace_marker가 더 싸다).

## 7. 유저 공간과 드라이버가 직접 쓰는 줄 — `trace_marker`, `trace_printk`

### 7.1 `trace_marker` — 앱의 "phase"를 커널 타임라인에 박기

유저 프로그램이 `/sys/kernel/tracing/trace_marker`에 `write()` 하면 그 문자열이 **ring buffer에 `tracing_mark_write:` 이벤트로** 들어간다. 커널 이벤트와 같은 시계, 같은 버퍼다. 로직 분석기에서 "앱이 GPIO 하나 토글"하는 것과 같은 역할을, 핀 없이 한다.

- §5.3의 `m5_app`이 쓰는 방식 그대로: 시작할 때 한 번 `open()`해 두고, 필요할 때 `write()`만 한다. 매번 open 하면 그 비용이 더 크다.
- 바이너리 형식이 필요하면 `trace_marker_raw`(앞 4바이트가 ID).
- 권한: `--w--w----`(0220, root:root) — 이 랩에서 `ls -l`로 확인. 제품에서는 앱 계정에 쓰기 권한을 줄지 정해야 한다.
- 비용: write syscall 한 번(TCG에서 수십 µs, 실제 Cortex-A53/A72에서는 대략 µs 단위). 1 kHz 루프에서 매 주기 쓰는 건 괜찮지만, **느린 경우에만** 쓰는 게 좋다 — `m5_app`처럼 "SLOW일 때만 marker"가 실무 패턴이다.

출력에서는 이렇게 보인다(§5.3, §8):

```text
 m5_app-1037 [000] ...1. 1217.766642: tracing_mark_write: phase=read_loop begin
 m5_app-1037 [000] ...1. 1217.805235: tracing_mark_write: SLOW read i=3 took 1418 us
```

### 7.2 `trace_printk()` — 커널 개발 중 임시 printf

`printk`는 콘솔(UART!)로 나가서 느리고, 로그 레벨·ratelimit 등을 거친다(M1). `trace_printk()`는 **ring buffer에만** 쓴다. 수 µs 이하 구간을 디버깅할 때 printk를 넣으면 타이밍이 바뀌어 버그가 사라지는(heisenbug) 일이 많은데, `trace_printk`는 그 방해가 훨씬 작다. `m5_calibrate()`에 넣은 것이 그 예다:

```text
        m5_calib-677     [001] .....   895.436366: m5_calibrate: calib start seq=0
```

그런데 모듈을 넣는 순간 `dmesg`에 이런 경고가 뜬다(실제 출력, 앞 4줄):

```text
[  844.363432] ** trace_printk() being used. Allocating extra memory.  **
[  844.363451] **                                                      **
[  844.363471] ** This means that this is a DEBUG kernel and it is     **
[  844.363491] ** unsafe for production use.                           **
```

**양산 코드에 `trace_printk`를 남기지 말라는 뜻**이다(추가 버퍼를 잡고, 커뮤니티 패치에서 거절된다). 남겨야 하는 관측점은 tracepoint(§5.7)로 만든다. 그리고 §3.2에서 본 것처럼 `trace_printk` 줄은 `set_ftrace_pid`·`set_event_pid` 필터를 무시하고 섞여 들어온다. `echo 0 > options/trace_printk`로 숨길 수 있다.

## 8. 사례 연구 — "센서 read가 가끔 5 ms 걸린다"

### 8.1 증상

`m5_app`이 1 kHz로 `/dev/m5_sensor`를 읽는다. 평소 read는 50 µs(`udelay(50)`)여야 하는데, 가끔 수 ms가 나온다. 면접 질문 그대로다. 접근 순서:

1. **숫자로 확인**: 앱이 직접 잰 지연 분포(평균, 최대, 임계값 초과 횟수). 이미 `m5_app`이 출력한다.
2. **언제**: 느린 read를 `trace_marker`로 표시해 커널 타임라인과 맞춘다.
3. **커널 안 어디서**: 드라이버 `.read` 입구/출구(fprobe), 의심 가는 다른 경로(calibration), 스케줄링(`sched_switch`)을 같은 버퍼에.
4. **무엇이 시간을 먹었나**: function_graph + `tracing_thresh`로 느린 호출만 트리로.

### 8.2 예제 14 (a) — 이벤트 타임라인으로 범인 지목

## 9. latency tracer — 최악의 구간을 자동으로 잡는다

### 9.1 종류

| tracer | 재는 것 | 시작 → 끝 |
|---|---|---|
| `irqsoff` | IRQ가 꺼져 있던 가장 긴 구간 | `local_irq_disable/save` → `enable/restore` |
| `preemptoff` | preemption이 꺼져 있던 가장 긴 구간 | `preempt_disable` → `preempt_enable` (spinlock 포함) |
| `preemptirqsoff` | 둘 중 하나라도 꺼져 있던 구간 (합집합) | 가장 실용적인 "스케줄 불가 구간" |
| `wakeup` | 가장 높은 우선순위 태스크의 wakeup → 실행 지연 (모든 태스크) | `sched_wakeup` → `sched_switch` |
| `wakeup_rt` | 같은데 RT 태스크만 | |
| `wakeup_dl` | SCHED_DEADLINE 태스크만 | |

공통 동작: 새 최대값이 나오면 `tracing_max_latency`(µs)를 갱신하고, **그 구간의 기록을 max 버퍼(snapshot)에 보관**한다. `trace`를 읽으면 그 최악 구간이 나온다. 기본은 최대값 하나만 남긴다. `tracing_thresh`를 0이 아닌 값으로 쓰면 **그 값을 넘는 구간을 전부** 남긴다(최대값만이 아니라).

`irqsoff`/`preemptoff`는 `CONFIG_IRQSOFF_TRACER`/`CONFIG_PREEMPT_TRACER`가 필요하다. 이 tracer들이 `trace_hardirqs_off/on` hook을 켜 두기 때문에 **커널을 이 옵션으로 빌드만 해도 약간 느려진다**. 그래서 이 랩의 RT 커널(`Image-rt`)에는 빠져 있다. 양산 RT 시스템에서는 대신 osnoise/timerlat(N3)을 쓴다.

### 10.1 per-CPU ring buffer와 overrun

ring buffer는 **CPU마다 따로** 있다. 각 CPU는 자기 버퍼에만 쓰므로 lock이 필요 없고(펌웨어에서 ISR과 메인 루프가 같은 링버퍼를 쓸 때 고민하던 문제를 CPU별 분리로 피한다), 읽을 때 타임스탬프로 합쳐서 보여 준다. 기본 모드는 **overwrite**: 꽉 차면 가장 오래된 페이지를 덮어쓴다. `options/overwrite`를 0으로 하면 반대로 새 이벤트를 버린다(`dropped`).

- stack tracer: 지금까지 본 가장 깊은 커널 스택 4328바이트. 프레임별 크기가 나와서 **큰 지역 변수를 가진 함수**(`mas_topiary_replace` 1184 B, `vms_gather_munmap_vmas` 800 B)를 찾을 수 있다. arm64 커널 스택은 16 KB(`THREAD_SIZE`)다. 드라이버에서 `char buf[2048]`을 스택에 잡으면 여기서 바로 드러난다(E4 "커널 스택은 작다").

### 10.3 snapshot과 instances

예제 20 — 무엇을 확인하나: `snapshot`은 "지금 버퍼를 따로 빼 두기"(실제로는 버퍼 swap), `instances/`는 완전히 독립된 두 번째 버퍼.

```sh
echo 1 > events/sched/sched_process_exec/enable; echo 1 > tracing_on
ls > /dev/null; echo 1 > snapshot; uname > /dev/null; echo 0 > tracing_on
echo "[main buffer]"; grep -v '^#' trace | cut -c1-110
echo "[snapshot]"; grep -v '^#' snapshot | cut -c1-110
echo 0 > snapshot; echo 0 > events/enable
mkdir instances/m5
echo 1 > instances/m5/events/sched/sched_process_exec/enable
echo 1 > instances/m5/tracing_on; date > /dev/null
echo "[instance m5]"; grep -v '^#' instances/m5/trace | cut -c1-110
echo "[top-level (events off)] lines: $(grep -vc '^#' trace)"
echo 0 > instances/m5/tracing_on; rmdir instances/m5; ls instances
```

- 인스턴스 `m5`에만 이벤트를 켰더니, 그 버퍼에만 `date`(그리고 출력을 거르는 `grep`, `cut`)가 들어갔다. 최상위 버퍼의 1줄은 앞 snapshot 실습에서 남은 `uname` 줄이다. **두 도구(또는 두 사람)가 서로의 설정을 망치지 않고** 동시에 추적할 수 있다. trace-cmd의 `-B 이름`, rtla(N3), perf 일부가 instance를 쓴다. 단, function tracer는 인스턴스에서도 쓸 수 있지만 `set_ftrace_filter`는 인스턴스별로 따로다.

## 11. trace-cmd와 KernelShark

### 11.1 trace-cmd — tracefs의 편한 앞단

지금까지 한 `echo`들을 한 줄 명령으로 묶고, 결과를 **파일(`trace.dat`)로 저장**해 다른 PC에서 분석할 수 있게 해 주는 도구다. 내부적으로는 CPU마다 스레드를 띄워 `per_cpu/cpuN/trace_pipe_raw`(바이너리)를 계속 읽어 파일에 쓴다. 그래서 ring buffer보다 긴 시간을 기록할 수 있다.

| 명령 | 뜻 | tracefs로 치면 |
|---|---|---|
| `trace-cmd list -t` / `-e PAT` / `-f PAT` / `-o` | tracer / 이벤트 / 함수 / 옵션 목록 | `available_*` |
| `trace-cmd record -e sched:sched_switch CMD` | 이벤트 켜고 CMD 실행 동안 기록 → `trace.dat` | `events/.../enable` + `trace_pipe_raw` |
| `-p function` / `-p function_graph` | tracer 고르기 | `current_tracer` |
| `-l FUNC` / `-n FUNC` / `-g FUNC` | filter / notrace / graph 시작 함수 | `set_ftrace_filter` 등 |
| `-F` / `-P PID` / `--max-graph-depth N` | CMD만 추적 / PID 추적 / 깊이 | `set_ftrace_pid` / `max_graph_depth` |
| `-b KB` / `-B NAME` / `-o FILE` | 버퍼 크기 / instance 사용 / 출력 파일 | `buffer_size_kb` / `instances/` |
| `trace-cmd report [-i FILE]` | 파일을 글로 | `trace` |
| `trace-cmd start ...` / `stop` / `show` / `extract` | 파일 없이 커널 버퍼만 켜기·끄기·보기·빼내기 | `echo` 들 |
| `trace-cmd stat` | 지금 tracefs 설정 요약 | 여러 파일 `cat` |
| `trace-cmd reset` | 전부 초기화 | `treset` |

### 11.2 예제 21 — record → report, function_graph, stat

### 11.3 KernelShark (가이드 — 이 랩에서는 실행 안 함)

KernelShark는 `trace.dat`를 여는 **GUI 타임라인 뷰어**다(Qt 기반, trace-cmd와 같은 프로젝트). 랩 VM과 게스트에는 GUI도 `kernelshark` 바이너리도 없어서 실행하지 않았다. 쓰는 법과 화면 구성만 정리한다.

- 실행: 호스트 PC(Ubuntu `apt install kernelshark`)에서 `kernelshark t1.dat`.
- 화면 위쪽: **CPU별 가로 막대**(그림 6과 같은 모양). 색 = 그 시각에 돌던 태스크. 확대/축소, 두 마커(A/B) 사이 시간 차 표시.
- 화면 아래쪽: `trace-cmd report`와 같은 이벤트 목록. 막대를 클릭하면 해당 줄로 간다.
- **태스크 플롯 추가**: 특정 PID(예: `m5_app`)를 골라 "그 태스크가 언제 돌았고 언제 잠들었나"를 별도 줄로 본다. "왜 깨어났는데 늦게 돌았나"가 눈으로 보인다.
- 필터: 이벤트·태스크·CPU로 거른다. 대용량 trace에서 원하는 부분만 본다.
- 실무 사용 장면: 그림 6을 손으로 그리는 대신 KernelShark로 보고, 중요한 구간의 스크린숏을 버그 리포트에 붙인다. 이 노트의 그림 6은 그 화면을 trace 타임스탬프로 직접 그린 대용품이다.

대안: Perfetto UI(웹)도 ftrace 텍스트 출력을 열 수 있다는 것이 알려져 있지만, 이 노트에서는 확인하지 않았다.

### 12.1 커널 커맨드라인으로 부팅부터 추적

| 파라미터 | 뜻 |
|---|---|
| `trace_event=sched:sched_process_exec,irq:*` | 부팅 초기부터 이벤트 켜기 |
| `ftrace=function_graph` / `ftrace=function` | 부팅 초기부터 tracer 켜기 |
| `ftrace_filter=`, `ftrace_notrace=`, `ftrace_graph_filter=` | 그 tracer의 필터 |
| `trace_buf_size=4M` | 부팅 때 버퍼 크기 |
| `trace_options=...` | 옵션 |
| `tp_printk` | 이벤트를 printk로도 내보내기(콘솔이 살아 있을 때만, 매우 느림) |
| `ftrace_dump_on_oops` | oops 때 버퍼를 콘솔로 덤프 |
| `traceoff_on_warning` | `WARN()` 순간 기록 멈춤 |

`CONFIG_BOOT_CONFIG` + `CONFIG_BOOTTIME_TRACING`이 있으면 **bootconfig**(initrd 끝에 붙이는 트리 형식 설정 파일)로 instance·트리거·kprobe까지 부팅 때 정의할 수 있다. 이 랩 커널은 둘 다 꺼져 있어서 커맨드라인 방식만 확인했다. 부팅 시간 분석 전체(`initcall_debug`, `systemd-analyze`)는 M10에서 다룬다.

### 12.2 `ftrace_dump_on_oops` — 커널이 죽는 순간의 블랙박스

커널이 oops/panic으로 죽으면 ring buffer는 RAM과 함께 사라진다. `ftrace_dump_on_oops`(sysctl `kernel.ftrace_dump_on_oops` 또는 부트 파라미터)를 켜 두면 **죽기 직전에 버퍼 전체를 콘솔로 쏟아낸다**. 시리얼 콘솔 로그만 남는 보드에서 "죽기 직전 무슨 일이 있었나"를 알 수 있다. 덤프가 길면 콘솔 출력이 수 초~수 분 걸리므로, 버퍼를 작게·이벤트를 적게 해 둔다(`=orig_cpu`로 죽은 CPU 것만 덤프하는 옵션도 있다).

예제 23 — 무엇을 확인하나: 이벤트 하나 + marker 하나를 남기고 `sysrq c`로 일부러 panic 시킨다. (이 게스트는 이걸로 죽었고, 위 §12.1을 위해 다시 부팅했다.)

```sh
cd /sys/kernel/tracing; echo > trace
echo 1 > events/sched/sched_process_exec/enable; echo 1 > tracing_on
ls > /dev/null; echo "m5: about to crash" > trace_marker
sysctl -w kernel.ftrace_dump_on_oops=1; sync; echo c > /proc/sysrq-trigger
```

출력에서 볼 것: panic 메시지 → 다른 CPU 정지 → **`Dumping ftrace buffer:`** 아래에 두 CPU의 버퍼가 시간순으로. 시각은 덤프용 latency 형식(첫 이벤트 기준 µs)이다. marker 줄로 "죽기 전 앱이 어디까지 진행했나"를 남길 수 있다는 게 실무 포인트다. (`Tainted: OE` = 서명 안 된 out-of-tree 모듈 `m5_lat`이 들어가 있음 — M3.)

재부팅해도 버퍼를 남기고 싶다면 **pstore ftrace**(`CONFIG_PSTORE_FTRACE`, 이 랩 커널에 있다): 함수 호출 기록을 재부팅에도 살아남는 RAM 영역(ramoops)에 쓴다. 사용법은 L7(크래시 수집)과 pstore 문서를 참고 — 이 노트에서는 실행하지 않았다.

### 13.1 예제 24 — `getpid()` 한 번의 비용, tracing 모드별

무엇을 확인하나: 커널 안에서 거의 아무것도 안 하는 syscall(`getpid`)을 2만 번 부르고 평균을 낸다. 모드마다 3회, 중앙값을 쓴다.

```c
/* m5_bench: cost of one getpid() syscall, averaged over N calls */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <time.h>
#include <sys/syscall.h>

int main(int argc, char **argv)
{
	long n = argc > 1 ? atol(argv[1]) : 200000;
	const char *tag = argc > 2 ? argv[2] : "run";
	struct timespec a, b;
	clock_gettime(CLOCK_MONOTONIC, &a);
	for (long i = 0; i < n; i++)
		syscall(SYS_getpid);   /* glibc getpid() is not cached, but be explicit */
	clock_gettime(CLOCK_MONOTONIC, &b);
	double ns = ((b.tv_sec - a.tv_sec) * 1e9 + (b.tv_nsec - a.tv_nsec)) / n;
	printf("%-22s %8.0f ns/getpid (n=%ld)\n", tag, ns, n);
	return 0;
}
```

- kprobe: 3.3배 — function 1개(1.2배)보다 훨씬 비싸다. arm64에서 kprobe는 `BRK` 예외 → 핸들러 → 원래 명령 single-step(XOL)으로 **예외를 두 번** 겪는다(이 커널의 arm64에는 `KPROBES_ON_FTRACE`가 없다 — `arch/arm64/Kconfig`에 해당 select가 없음을 확인). 함수 입구라면 **fprobe(`f:`)가 ftrace 자리를 써서 더 싸다** — 이 노트에서는 fprobe를 따로 재지 않았다.
- 측정 잡음: 같은 모드 3회가 ±40%까지 흔들렸다(VM 부하 10~26). 그래서 중앙값을 썼고, 1.2배 이하 차이는 이 환경에서 의미 있게 말하기 어렵다. 실제 보드에서 다시 재는 것이 맞다(§18 연습 6).

| 끝나면 `trace-cmd reset` | 전역 상태가 다음 사람을 망친다 |

- **ring buffer** (`kernel/trace/ring_buffer.c`): CPU별 페이지 리스트. 쓰는 쪽은 자기 CPU 버퍼에 `local_t` 원자 연산으로 자리를 예약(reserve)하고 채운 뒤 commit 한다. ## 15. Embedded 실무에서 다시 보기

### 15.1 센서 키트: IMU 샘플이 가끔 늦다

로봇의 IMU(SPI, 1 kHz)를 읽는 스레드가 가끔 주기를 놓친다. 순서:

1. 앱에서 주기 지터를 직접 측정하고 늦은 주기만 `trace_marker`로 표시(§7.1).
2. `trace-cmd record -e sched:sched_switch -e sched:sched_wakeup -e irq:irq_handler_entry -e spi:spi_transfer_start -e spi:spi_transfer_stop ./imu_app`처럼 스케줄링·IRQ와 **SPI 트랜잭션 시작/끝**을 같이 기록한다. `spi:*` 이벤트는 SPI core(`include/trace/events/spi.h`)에 이미 있는 tracepoint라 드라이버 수정이 필요 없다. marker는 따로 켤 필요 없다(§11.2).
3. 늦은 주기 주변에서: 스레드가 깨워졌는데 못 돌았나(→ `wakeup_rt`, 우선순위·affinity, N2), 돌았는데 SPI가 늦었나(→ 컨트롤러 IRQ, DMA, `irq_handler_entry`), SPI 버스를 같은 버스의 다른 장치(예: SPI 플래시)가 쥐고 있었나(→ §8과 같은 mutex 경합 — SPI 컨트롤러의 bus lock).
4. 결론을 숫자와 trace 조각으로 리포트한다.

### 15.2 카메라 장비: 프레임 드롭

V4L2(I4) 버퍼 관리 계층 videobuf2의 tracepoint(`vb2:vb2_buf_queue`, `vb2:vb2_buf_done` 등)와 `irq_handler_entry`(CSI 수신 IRQ)를 함께 기록하면 "버퍼가 늦게 queue 되었나(유저 앱이 늦음) vs DMA 완료 IRQ가 늦었나(커널)"가 갈린다. 이벤트 이름은 커널 버전마다 조금씩 다르므로 `trace-cmd list -e vb2`로 먼저 확인한다.

### 15.3 양산 장비에서 쓰는 법 — "켜 둔 채로 출하"할 수 있나

- 커널 config에 `CONFIG_FUNCTION_TRACER`/`CONFIG_DYNAMIC_FTRACE`/`CONFIG_FTRACE_SYSCALLS`를 켜 두는 것은 많은 배포판·Android 커널이 한다(꺼져 있을 때 NOP — §2, §13). 대신 커널 이미지가 조금 커지고(`__mcount_loc`/patchable entry 테이블), 함수 앞 NOP이 I-cache를 조금 먹는다.
- `CONFIG_IRQSOFF_TRACER`/`CONFIG_PREEMPT_TRACER`는 켜 두기만 해도 hook 비용이 있어 양산 RT 커널에서는 보통 끈다(이 랩의 `Image-rt`처럼). 대신 osnoise/timerlat(N3).
- 보안: tracefs는 커널 주소·데이터를 보여 주므로 root 전용이고, Secure Boot + lockdown(L 모듈)에서는 kprobe 등이 제한된다.
- 현장 장비에서는 **"버퍼를 작게 켜 두고, 문제가 생기면 traceoff 트리거로 얼린 뒤 수집"** 방식(flight recorder)이 실용적이다. 예: 앱이 이상을 감지하면 `echo 0 > tracing_on` 후 `cat trace > /data/crash_trace.txt`.

### 15.4 Don의 경험과 연결

SSD 펌웨어에서 "커맨드 지연 꼬리(tail latency)"를 잡을 때 했던 일 — 이벤트 ID와 타임스탬프를 RAM 링에 남기고, 느린 커맨드가 나오면 링을 얼려 덤프하고, 시간축에 그려 겹치는 GC·리드 리트라이를 찾는 것 — 이 정확히 §8의 흐름이다. 차이는 ① 커널이 이미 수천 개의 이벤트를 제공한다 ② 코드 수정 없이 kprobe/fprobe로 임의 지점을 추가한다 ③ hist/synthetic으로 분포를 커널 안에서 만든다는 점이다. 인터뷰에서 "펌웨어에서 쓰던 trace 링버퍼 + 트리거 방식을 Linux에서는 ftrace로 그대로 한다"고 연결해서 말하면 강하다. M11(GPIO 토글 + 스코프)과 합치면 커널 이벤트와 실제 핀 신호를 같은 축에 놓을 수 있다.

## 17. 면접에서 이렇게 말한다

**Q.** A sensor read on your device usually takes 50 µs but occasionally takes 5 ms. How do you find out why?

**A.** 먼저 숫자로 재현한다: 앱에서 read 시간을 재고 느린 것만 `trace_marker`로 표시한다. 그다음 같은 ring buffer에 드라이버 `.read` 입구·출구(fprobe), 의심 경로(같은 버스를 쓰는 다른 코드), `sched_switch`/`sched_wakeup`, IRQ 이벤트를 함께 기록한다. 느린 read 주변을 보면 "다른 스레드가 같은 mutex를 쥐고 있었다", "IRQ가 늦게 왔다", "스레드가 깨워졌는데 못 돌았다" 중 하나가 보인다. 경로가 의심되면 function_graph에 `tracing_thresh`를 걸어 느린 호출만 트리로 본다. 랩에서 이렇게 해서 5 ms짜리 calibration 스레드가 같은 mutex를 쥐고 있어서 reader가 spin하다가 잠드는 걸 `mutex_spin_on_owner`와 `schedule` 이름으로 확인했다.

> First I'd quantify it in user space and mark only the slow reads with trace_marker, so the application's view and the kernel's view share one timeline. Then I record, into the same ftrace ring buffer, the driver's read entry and exit with fprobes, sched_switch and sched_wakeup, and IRQ events. Around a slow read you can usually see one of three things: someone else held the lock, the interrupt came late, or the thread was woken but didn't get the CPU. To see which kernel path burned the time, I use function_graph on the read function with tracing_thresh, so only calls slower than a few milliseconds are logged. In my lab, that showed a calibration thread holding the same bus mutex for 5 ms; the reader spun in mutex_spin_on_owner and then slept in schedule. The fix is a design change — shorter critical sections — but ftrace gives the evidence.

**꼬리 질문**: "그걸 실제 제품에서 켜도 되나?" → 필터를 건 이벤트·fprobe는 오버헤드가 작다(측정: 경로 위 함수 하나 +15%, 경로 밖이면 0). 전 함수 graph는 안 된다.

**Q.** How can ftrace have near-zero overhead when it's off, if it can trace almost every kernel function?

**A.** 컴파일러가 모든 함수 입구에 NOP 자리를 만들어 둔다(arm64는 `-fpatchable-function-entry`, x86은 `-pg`/`mcount`를 부팅 때 NOP으로). 꺼져 있을 때는 함수당 NOP 하나(arm64에서는 `mov x9, x30` + `nop`)만 실행된다. 켜면 커널이 필터에 맞는 함수의 NOP만 `bl ftrace_caller`로 고쳐 쓴다. 랩에서 QEMU gdbstub으로 `vfs_read` 입구를 덤프해서 NOP이 BL로 바뀌고 끄면 돌아오는 걸 직접 봤다. tracepoint도 같은 원리로 static key(jump label) NOP이다.

> Every function is compiled with a few NOP bytes at its entry — on arm64 via -fpatchable-function-entry, on x86 via -pg/mcount call sites that the kernel converts to NOPs at boot. When tracing is off, that's all the CPU executes: on arm64 a mov x9, x30 and a nop. When you enable the function tracer, the kernel rewrites only the selected functions' NOP into a bl to ftrace_caller; arm64 can patch that single 4-byte instruction safely without stop_machine, x86 uses an int3-based sequence. I verified it by dumping vfs_read through the QEMU gdbstub before and after enabling a filter. Tracepoints use the same idea with static keys: the disabled site is one NOP that becomes a branch.

**꼬리 질문**: "CALL_OPS는?" → 함수 앞 8바이트에 담당 `ftrace_ops` 포인터를 두어 `ftrace_caller`가 콜백을 바로 찾는다(리스트 순회 없음).

**Q.** What's the difference between a tracepoint, a kprobe, and the function tracer?

**A.** tracepoint는 개발자가 미리 박아 둔 의미 있는 지점이라 필드가 정리돼 있고 비교적 안정적이다. function tracer는 모든 함수 입구에 자동으로 있지만 함수 이름과 호출자만 준다. kprobe는 실행 중 아무 명령에나 붙일 수 있고 레지스터·메모리로 인자를 뽑지만, arm64에서는 BRK 예외라 비싸다(측정 3.3배). 함수 입구라면 fprobe가 ftrace 자리를 쓰므로 더 싸다.

> A tracepoint is a static, named hook a kernel developer placed on purpose, with a defined record format — stable and cheap when off. The function tracer instruments every function entry automatically but only tells you which function was called and by whom. A kprobe can be attached at runtime to almost any instruction and can fetch arguments from registers and memory, but on arm64 it works through a BRK exception, so it costs more — about 3x a getpid call in my measurement versus 1.2x for a single traced function. For function entry and exit I prefer fprobes, which reuse the ftrace patch site.

**Q.** How do you find what's disabling interrupts for too long?

**A.** `irqsoff` tracer. IRQ off/on 지점마다 시각을 재서 가장 긴 구간을 자동으로 보관하고 `tracing_max_latency`, `started at`/`ended at`, 콜스택을 준다. 랩에서 모듈이 IRQ를 끈 채 `udelay` 하는 걸 `started at: m5_irqoff_section`으로 바로 찾았다. preemption이면 `preemptoff`, 둘 다면 `preemptirqsoff`. 단 이 tracer들은 빌드만 해도 hook 비용이 있어 양산 RT 커널에서는 빼고 osnoise/timerlat을 쓴다.

> I use the irqsoff latency tracer. It hooks every interrupt disable and enable, keeps the longest window it has seen in tracing_max_latency, and preserves the trace of that window with the start and end functions and a stack trace. In my lab a module busy-waiting with interrupts off showed up immediately as "started at m5_irqoff_section". preemptoff and preemptirqsoff do the same for preemption. Because those hooks cost something even when idle, production RT kernels usually leave them out and rely on osnoise and timerlat instead.

**Q.** Your trace only shows the last few milliseconds. Why, and what do you do?

**A.** ring buffer는 CPU별 고정 크기이고 기본이 overwrite라 가장 오래된 것부터 덮어쓴다. 랩에서 32 KB 버퍼 + 전 함수 tracer로 220만 개 중 2530개만 남았다(`overrun` 105만). 대책: 필터로 양을 줄이고, 버퍼를 키우고, trace-cmd로 계속 디스크에 빼내고, 문제 순간에 `traceoff`나 `snapshot` 트리거로 얼린다.

> The ring buffer is per-CPU and fixed-size, and by default it overwrites the oldest data. With a 32 KB buffer and the function tracer on everything, I wrote 2.2 million events and kept only 2,530; the per-CPU stats showed over a million overruns. So: reduce volume with filters, enlarge buffer_size_kb, stream continuously with trace-cmd record, and use a traceoff or snapshot trigger to freeze the buffer right when the problem happens.

**Q.** How would you add tracing to your own driver?

**A.** `TRACE_EVENT`로 tracepoint를 정의한다. 헤더 하나에 필드·복사·출력 형식을 쓰고, `.c` 하나에서 `CREATE_TRACE_POINTS`로 생성한다. 꺼져 있으면 NOP 하나라 양산 코드에 남겨도 되고, 켜면 필드로 필터·hist가 되고 perf·BPF도 같은 지점을 쓴다. `trace_printk`는 개발 중에만.

> I define tracepoints with TRACE_EVENT in a trace header — fields, the fast-assign copy, and the print format — and instantiate them in one .c file with CREATE_TRACE_POINTS. A disabled tracepoint is a single NOP behind a static key, so it can stay in production code, and when enabled it supports field filters and histograms, and perf and BPF can attach to the same point. trace_printk is fine while debugging, but it prints a debug-kernel warning and shouldn't be merged.

**Q.** How do you measure wakeup latency of a real-time thread with only ftrace?

**A.** `wakeup_rt` tracer가 최고 우선순위 RT 태스크의 최악 wakeup→실행 지연과 그 사이 커널 흐름을 준다. 분포가 필요하면 `sched_waking`과 `sched_switch`를 hist 변수로 짝지어 synthetic event를 만들고 거기에 log2 hist를 건다. 전용 도구로는 cyclictest와 rtla timerlat(N3).

> The wakeup_rt tracer records the worst wakeup-to-run latency of the highest-priority RT task and the kernel activity in between. For a full distribution, I pair sched_waking and sched_switch with hist trigger variables to create a synthetic wakeup-latency event, then put a log2 histogram on it — all in-kernel, no trace buffer needed. For routine work I'd use cyclictest or rtla timerlat.

## 18. 직접 해보기

1. **개념**: `available_filter_functions`에 있는데 `set_ftrace_filter`에 넣어도 한 번도 안 찍히는 함수는 어떤 경우인가? 두 가지 이상 말해 보라.
   정답/힌트: 그 경로가 실행되지 않음, 다른 PID에서만 실행(`set_ftrace_pid`), `tracing_on=0`, `.isra` 복제본만 실제로 불림.
2. **gdbstub 관찰**: §2.4의 `gdbpeek.sh`로 `m5_sensor_read` 입구를 덤프하라. `echo '*:mod:m5_lat' > set_ftrace_filter` + function 켠 뒤 다시 덤프하면 모듈 함수 앞 ops 칸에 무엇이 들어가는가?
   정답/힌트: 모듈도 `-fpatchable-function-entry`로 빌드되므로 같은 패턴. `info symbol`로 ops 포인터를 확인.
3. **hist 과제**: `raw_syscalls:sys_enter`에 `hist:keys=common_pid.execname,id.syscall:sort=hitcount.descending`을 걸고 systemd가 부팅 직후 가장 많이 부르는 syscall을 찾아라.
   정답/힌트: `.execname`, `.syscall` 수식어. 끝나면 `!hist...`로 제거.
4. **synthetic 응용**: `m5_app`의 read 지연(`m5_sensor_read` 입구 → 리턴)을 fprobe 두 개 + synthetic event로 히스토그램 내 보라. 앱이 직접 잰 분포와 비교하라.
   정답/힌트: `f:m5/rd` / `f:m5/rd_ret`에 `hist:keys=common_pid:ts0=common_timestamp.usecs`, 리턴 쪽에 `onmatch(m5.rd).trace(...)`.
5. **tracing_thresh 모드**: `irqsoff`에 `echo 30000 > tracing_thresh`를 걸고 `irqoff_us`에 40000을 두 번 써라. `trace`에 몇 개가 남는가? 최대값 모드와 무엇이 다른가?
   정답/힌트: thresh 모드는 넘는 구간마다 기록(덮어쓰지 않음). 커널 자체 구간(TCG 잡음)도 섞일 수 있다.
6. **실제 하드웨어 오버헤드**: Raspberry Pi나 i.MX 보드에서 §13의 `m5_bench`를 같은 모드로 돌려 표를 다시 만들어라. TCG 결과와 비율이 같은가?
   정답/힌트: 절대값은 수백 ns 단위로 작아지고, kprobe/graph 비율이 달라질 수 있다.
7. **드라이버 tracepoint**: §5.7의 `m5_tp`에 `TRACE_EVENT_CONDITION` 또는 `__string()` 필드(장치 이름)를 추가하고, `filter`로 특정 장치만 기록하라.
   정답/힌트: `__string(name, dev_name(dev))` + `__assign_str(name)`(6.10+는 인자 1개), 출력은 `__get_str(name)`.

| snapshot | 버퍼 스왑 | 현재 버퍼를 보존용 버퍼와 교체 |
| instance | 독립 버퍼 | `instances/NAME`, 설정·버퍼가 따로 |
| overrun | 덮어쓰기로 잃은 수 | `per_cpu/cpuN/stats` |
| trace-cmd | CLI 프런트엔드 | record/report/list/stat/reset |
| trace.dat | trace-cmd 파일 | 다른 PC에서 report/KernelShark로 분석 |
| KernelShark | GUI 뷰어 | CPU·태스크 타임라인 |
| BTF | BPF Type Format | 커널 타입 정보 → probe 인자를 이름으로 |

## 20. 요약 & 체크리스트

ftrace는 커널 안에 내장된 "trace 링버퍼 + 트리거 + 로직 분석기"다. 모든 함수 입구의 NOP 자리(dynamic ftrace), 개발자가 박아 둔 tracepoint, 실행 중에 만드는 kprobe/fprobe/uprobe, 앱이 쓰는 trace_marker가 같은 per-CPU ring buffer에 타임스탬프와 함께 쌓이고, 사람은 `/sys/kernel/tracing` 파일이나 trace-cmd로 꺼내 본다. 꺼져 있을 때 비용이 NOP 하나라는 점(arm64에서 `nop` ↔ `bl ftrace_caller` 한 칸 — gdbstub으로 직접 확인), 필터·hist 트리거·synthetic event로 필요한 것만 커널 안에서 집계할 수 있다는 점, latency tracer가 "가장 긴 IRQ off/preempt off/wakeup 구간"을 범인 함수 이름과 함께 자동으로 잡는다는 점이 핵심이다. 사례 연구에서는 "가끔 느린 센서 read"를 이벤트 타임라인으로 지목하고(같은 mutex를 쥔 calibration 스레드), function_graph + `tracing_thresh`로 `mutex_spin_on_owner`/`schedule`까지 확인했다. 측정은 가벼운 방법으로, 원인 경로는 무거운 방법으로 — 그리고 TCG 숫자는 비율로만 읽는다.

- [ ] tracefs의 주요 파일(current_tracer, tracing_on, trace/trace_pipe, set_ftrace_filter, events/, buffer_size_kb)을 역할별로 설명할 수 있다
- [ ] "꺼져 있을 때 오버헤드가 거의 0"인 이유를 arm64 명령어(`mov x9, x30` + `nop` → `bl ftrace_caller`)로 설명할 수 있다
- [ ] function tracer에 glob·`:mod:`·PID 필터와 `func_stack_trace`, `traceoff` 명령을 걸 수 있다
- [ ] function_graph + `funcgraph-retval`로 에러 코드(-ENOENT 등)가 처음 생긴 함수를 찾을 수 있다
- [ ] 이벤트 `format`을 읽고 필터를 쓰고, `stacktrace`/`snapshot`/`traceoff` 트리거를 걸 수 있다
- [ ] hist 트리거로 call_site별 합계를, synthetic event로 두 이벤트 사이 지연 분포를 만들 수 있다
- [ ] kprobe/kretprobe/fprobe/uprobe를 인자·반환값과 함께 정의하고, 타입·오프셋 함정을 피할 수 있다
- [ ] `trace_marker`로 앱 phase를 커널 타임라인에 맞출 수 있고, `trace_printk`를 양산에 남기면 안 되는 이유를 말할 수 있다
- [ ] irqsoff/preemptoff/wakeup_rt 출력의 `latency`, `started at`/`ended at`, 플래그 칸을 해석할 수 있다
- [ ] overrun이 왜 생기는지, snapshot·instance·trace-cmd로 어떻게 피하는지 말할 수 있다
- [ ] 드라이버에 `TRACE_EVENT`를 추가하고 빌드·필터까지 할 수 있다
- [ ] "센서 read가 가끔 5 ms"를 ftrace로 조사하는 절차를 30초 안에 영어로 말할 수 있다
