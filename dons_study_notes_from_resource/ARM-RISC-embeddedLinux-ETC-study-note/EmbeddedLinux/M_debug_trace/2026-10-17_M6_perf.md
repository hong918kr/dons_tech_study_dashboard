# M6. perf — perf stat/record/report/top, 하드웨어 카운터, flame graph — "추측하지 말고 세어 보고, 찍어 본다"

> **이 노트를 다 읽으면**: perf_events가 PMU·소프트웨어·tracepoint 이벤트를 어떻게 한 인터페이스로 묶는지 설명할 수 있다 · `perf stat`로 IPC·캐시·분기 지표를 읽고 multiplexing 스케일링을 해석할 수 있다 · `perf record -g`(fp/dwarf)로 콜스택을 찍고 flame graph를 직접 만들 수 있다 · 타깃에서 기록하고 호스트에서 `--symfs`·build-id로 분석하는 크로스 워크플로를 돌릴 수 있다
> **왜 필요한가**: "추론 루프가 커널 업데이트 후 30% 느려졌다", "센서 파이프라인이 CPU를 90% 먹는다" 같은 질문에 **숫자와 콜스택으로** 답하는 표준 도구가 perf다. 성능 면접의 단골이고, AI 가속기·로보틱스 칩 팀은 IPC·cache-miss·memory-bound 판단을 기본기로 본다.
> **Don 기준 난이도**: 사이클 카운터로 구간 시간을 재는 것, 캐시 라인·DMA·메모리 대역폭 감각은 이미 있다(SSD FW 성능 튜닝) / 새로 배울 것은 Linux가 PMU를 추상화하는 방식(perf_event), 샘플링 기반 프로파일링, 콜스택 언와인딩, 심볼 해석 체인
> **선행 노트**: E1(커널 구조), E6(유저/커널 경계), F1(스케줄러), F6(인터럽트), A5(가상 메모리·page fault), B3(ELF·심볼·debuginfo), M5(ftrace — tracepoint의 다른 소비자). 다음 노트: M7(eBPF)

## 0. 큰 그림 — 이게 왜 필요한가

bare-metal에서 성능을 잴 때 Don은 아마 이렇게 했다: Cortex-M의 `DWT->CYCCNT`나 Cortex-R의 PMU cycle counter를 구간 앞뒤로 읽고, 빼서, UART로 찍는다. 더 깊게 가면 GPIO를 토글해 scope로 보거나, ETM/trace 포트로 명령어 흐름을 잡았다.

Linux에서 같은 일을 하려면 문제가 세 가지 생긴다.

1. **CPU 레지스터를 유저가 직접 못 만진다.** PMU 레지스터(PMCR_EL0, PMEVCNTRn_EL0 …)는 기본적으로 EL1(커널)만 접근 가능하다. 누군가 대신 설정하고 읽어 줘야 한다.
2. **CPU가 여러 프로세스를 번갈아 돈다.** 카운터를 그냥 켜 두면 "내 프로그램"의 사이클이 아니라 그 CPU에서 돈 모든 것의 사이클이 섞인다. context switch마다 카운터를 저장·복원해야 한다(태스크별 가상화).
3. **"어디서" 시간이 쓰였는지가 궁금하다.** 전체 사이클 수만으로는 부족하고, 함수·콜스택별 분포가 필요하다. 이건 카운터 overflow 인터럽트로 PC와 스택을 **샘플링**해서 얻는다.

Linux의 답이 **perf_events** 서브시스템(커널 `kernel/events/`)과 그 유저 도구 **perf**(커널 소스 `tools/perf/`)다. 커널이 PMU를 소유하고, 유저는 `perf_event_open(2)`이라는 syscall 하나로 "이 이벤트를, 이 태스크(또는 CPU)에 대해, 세거나(counting) 샘플링해(sampling) 달라"고 요청한다.

## 1. perf_events 구조 — 이벤트 4종, counting vs sampling

### 1.1 이벤트의 네 종류

| 종류 | `perf_event_attr.type` | 예 | 누가 세나 | 비고 |
|---|---|---|---|---|
| hardware | `PERF_TYPE_HARDWARE` (일반화 이름) / `PERF_TYPE_RAW` (CPU 고유 번호) | `cycles`, `instructions`, `r08`, `armv8_pmuv3/l1d_cache_refill/` | CPU PMU 카운터 | 개수 제한(A57: 6 + cycle 1) → multiplexing |
| software | `PERF_TYPE_SOFTWARE` | `task-clock`, `cpu-clock`, `page-faults`, `context-switches`, `cpu-migrations` | 커널 코드가 직접 증가 | PMU 없이도 동작 (VM 호스트에서도 OK) |
| tracepoint | `PERF_TYPE_TRACEPOINT` | `sched:sched_switch`, `syscalls:sys_enter_read` | 커널 정적 tracepoint (M5와 같은 것) | ftrace 인프라 필요 |
| dynamic | kprobe/uprobe PMU 타입 | `perf probe`로 만든 `probe:foo` | 런타임에 심은 breakpoint | M7(eBPF)에서 자세히 |

`perf list`가 이 목록을 보여 준다. 일반화 이름(`cycles`, `cache-misses`)은 커널의 PMU 드라이버가 CPU 고유 이벤트 번호로 **매핑**해 준다. 매핑이 없으면 `<not supported>`가 뜬다. 게스트에서 `perf list tracepoint`는 2198개(6.18.55-trace) tracepoint를 보여 줬다.

그림 2 — counting은 오버헤드가 거의 없고 합계만 준다. sampling은 overflow 인터럽트마다 "그 순간 무엇을 하고 있었나"를 기록해 통계적인 분포를 만든다.

- **counting**: 카운터를 켜고, 끝나면 `read()`로 합계를 읽는다. 인터럽트가 없으니 오버헤드가 거의 0이다. `perf stat`.
- **sampling**: 카운터를 `-period`로 미리 채워 두면 period 개 이벤트 뒤에 overflow → PMU 인터럽트. 핸들러가 그 순간의 PC, 레지스터, (요청하면) 콜스택을 링버퍼에 쓰고 카운터를 다시 채운다. `perf record`. 샘플 수 × period ≈ 전체 이벤트 수이므로, **샘플이 몰린 함수 = 이벤트가 많이 발생한 함수**다.
- `-F 999`처럼 주파수로 주면 커널이 period를 자동 조정한다(`perf_event_attr.freq = 1`). 999처럼 홀수로 하는 이유는 100Hz/1000Hz 같은 타이머 주기와 박자가 맞아 떨어져(lockstep) 특정 코드만 계속 찍히는 것을 피하려는 관습이다.

Don의 SSD 경험으로 말하면: counting은 "구간 시작/끝에 CYCCNT 읽기", sampling은 "타이머 인터럽트에서 스택에 저장된 PC를 히스토그램에 넣는 statistical profiler"를 커널이 표준화한 것이다.

### 1.3 예제 1 — `perf_event_open(2)`을 직접 불러 보기

perf 도구가 없어도 C 코드에서 카운터를 쓸 수 있다. 펌웨어에서 "특정 루프만 사이클 측정"하던 습관 그대로 쓸 수 있는 방법이다. 아래는 cycles를 리더로, instructions와 raw 이벤트 0x03(L1D_CACHE_REFILL)을 같은 **그룹**으로 묶어(그룹 = 항상 같이 스케줄되는 카운터 묶음) 루프 하나를 잰다.

```c
/* perfev.c — perf_event_open(2)을 직접 불러 cycles/instructions를 그룹으로 센다 */
#define _GNU_SOURCE
#include <linux/perf_event.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/syscall.h>
#include <unistd.h>

static int open_ev(uint32_t type, uint64_t config, int group_fd)
{
    struct perf_event_attr a;
    memset(&a, 0, sizeof a);
    a.size = sizeof a;
    a.type = type;                 /* HARDWARE / SOFTWARE / RAW / TRACEPOINT */
    a.config = config;             /* 이벤트 번호 */
    a.disabled = (group_fd == -1); /* 리더만 꺼진 채로 만들고 나중에 켠다 */
    a.exclude_kernel = 1;          /* 유저 모드만 (paranoid 2에서도 허용) */
    a.exclude_hv = 1;
    a.read_format = PERF_FORMAT_GROUP;
    return (int)syscall(SYS_perf_event_open, &a, 0 /*this pid*/, -1 /*any cpu*/, group_fd, 0);
}

int main(void)
{
    int lead = open_ev(PERF_TYPE_HARDWARE, PERF_COUNT_HW_CPU_CYCLES, -1);
    if (lead < 0) { perror("perf_event_open(cycles)"); exit(1); }
    int ins = open_ev(PERF_TYPE_HARDWARE, PERF_COUNT_HW_INSTRUCTIONS, lead);
    if (ins < 0) perror("perf_event_open(instructions)");      /* TCG면 실패 가능 */
    int raw = open_ev(PERF_TYPE_RAW, 0x03 /* L1D_CACHE_REFILL */, lead);
    if (raw < 0) perror("perf_event_open(raw 0x03)");

    ioctl(lead, PERF_EVENT_IOC_RESET, PERF_IOC_FLAG_GROUP);
    ioctl(lead, PERF_EVENT_IOC_ENABLE, PERF_IOC_FLAG_GROUP);
    volatile unsigned long x = 0;
    for (unsigned long i = 0; i < 10000000UL; i++)           /* 측정 대상 */
        x += i;
    ioctl(lead, PERF_EVENT_IOC_DISABLE, PERF_IOC_FLAG_GROUP);

    uint64_t buf[8];                                          /* {nr, v0, v1, ...} */
    ssize_t n = read(lead, buf, sizeof buf);
    if (n < 0) { perror("read"); exit(1); }
    printf("events in group: %llu\n", (unsigned long long)buf[0]);
    printf("cycles        : %llu\n", (unsigned long long)buf[1]);
    if (ins >= 0) printf("instructions  : %llu\n", (unsigned long long)buf[2]);
    if (raw >= 0) printf("raw 0x03      : %llu\n", (unsigned long long)buf[ins >= 0 ? 3 : 2]);
    return 0;
}
```

같은 바이너리를 세 곳에서 돌렸다. 먼저 QEMU 게스트(`-cpu cortex-a57,pmu=on`, root):

```text
perf_event_open(instructions): No such file or directory
events in group: 2
cycles        : 77594359
raw 0x03      : 0
```

VM 호스트에서 일반 사용자로, 그리고 `sudo`로:

```text
$ ./perfev
perf_event_open(cycles): Permission denied
$ sudo ./perfev
perf_event_open(cycles): No such file or directory
```

출력에서 볼 것: 에러 코드가 **원인을 정확히 구분해 준다.**
- `EACCES`(Permission denied) = 권한 문제. VM 호스트의 `perf_event_paranoid`가 4(Ubuntu 기본값)라서 CAP_PERFMON 없는 사용자는 아무 이벤트도 못 연다.
- `ENOENT`(No such file or directory) = 그 이벤트를 이 PMU가 모른다. 호스트는 PMU 자체가 없고, TCG 게스트는 instructions를 지원하지 않는다고 광고한다(2절).
- raw 0x03은 **열리기는 했지만 0**을 돌려준다. 이게 제일 위험한 경우다. 에러 없이 0이 나오면 "캐시 미스가 없는 완벽한 코드"로 오해하기 쉽다. 값은 실행마다 다르다.

### 1.4 권한: `perf_event_paranoid`와 `kptr_restrict`

| 값 | `kernel.perf_event_paranoid` 의미 (일반 사용자 기준) |
|---|---|
| -1 | 거의 모든 이벤트 허용 (raw tracepoint 포함), mlock 한도 무시 |
| 0 | CPU 전체(`-a`) 측정 허용, raw/ftrace function tracepoint 금지 |
| 1 | CPU 전체 측정 금지, 자기 프로세스의 user+kernel 측정 허용 |
| 2 | 자기 프로세스의 **유저 모드만** (커널 프로파일링 금지) — 메인라인 기본값 |
| 3, 4 | 메인라인에 없는 배포판 패치. Ubuntu는 4 = CAP_PERFMON/CAP_SYS_ADMIN 없으면 perf_event_open 자체 금지 (위 호스트 에러 메시지가 그대로 이 표를 출력했다) |

게스트(lab 커널, 메인라인)에서 확인한 값:

```text
kernel.perf_event_paranoid = 2
kernel.kptr_restrict = 0
kernel.perf_event_max_sample_rate = 100000
kernel.perf_event_mlock_kb = 516
```

- **root(또는 `CAP_PERFMON`, 커널 5.8+)는 paranoid와 무관하게 허용**된다. 그래서 공유 VM의 전역 sysctl을 바꾸지 않고 `sudo perf`로 호스트 측정을 했다.
- `kernel.kptr_restrict`는 `/proc/kallsyms`의 커널 주소를 가린다. 1이면 CAP_SYSLOG 없는 사용자에게, 2면 모두에게 주소가 0으로 보인다. 주소가 0이면 perf가 커널 샘플을 심볼로 바꾸지 못해 `[k] 0xffff...` 또는 `[unknown]`만 나온다. root로 기록할 때도 2면 kallsyms가 쓸모없으니, 이때는 `vmlinux`를 `-k`로 직접 주면 된다(7절).
- `perf_event_max_sample_rate`(기본 100000)를 넘는 `-F`는 잘린다. 커널이 샘플 처리 시간이 너무 길다고 판단하면 이 값을 스스로 낮추고 dmesg에 "perf: interrupt took too long ... lowering kernel.perf_event_max_sample_rate"를 찍는다. 느린 임베디드 코어에서 자주 본다.
- `perf_event_mlock_kb`: 사용자당 ring buffer로 고정(mlock)할 수 있는 메모리 상한. `-m`으로 버퍼를 키우다 막히면 이것 때문이다.

임베디드 제품에서는 보통 **양산 이미지에서 paranoid를 2 이상으로, kptr_restrict를 1 이상으로** 두고, 디버그 빌드에서만 풀어 준다(L6 런타임 보안과 같은 이유 — 커널 주소 유출은 KASLR 우회 재료다).

## 2. ARM PMUv3 — 레지스터와 이벤트 번호, 그리고 QEMU TCG의 진실

### 2.1 PMUv3 하드웨어

ARMv8-A의 PMU(Performance Monitors Extension, PMUv3)는 코어마다 들어 있는 카운터 블록이다. Cortex-R/M에서 써 본 PMU와 개념이 같고, 레지스터 이름에 `_EL0`가 붙어 있다(EL0 접근은 PMUSERENR_EL0로 허용해야 가능 — Linux는 기본적으로 막는다).

| 레지스터 | 역할 |
|---|---|
| `PMCR_EL0` | 전체 enable(E), 카운터 리셋(P, C), 카운터 개수(N 필드, 읽기 전용), 64비트 cycle 모드(LC) |
| `PMCCNTR_EL0` | 전용 cycle counter (64비트). perf에서는 인덱스 31 |
| `PMEVCNTR<n>_EL0` | 범용 이벤트 카운터 n (A57/A72는 n=0..5, 6개) |
| `PMEVTYPER<n>_EL0` | 카운터 n이 셀 이벤트 번호 + EL 필터(유저/커널 제외 비트) |
| `PMCNTENSET/CLR_EL0` | 카운터별 enable 비트마스크 |
| `PMINTENSET/CLR_EL1` | 카운터별 overflow 인터럽트 enable |
| `PMOVSCLR_EL0` | overflow 상태 (인터럽트 핸들러가 읽고 지움) |
| `PMCEID0/1_EL0` | "이 코어가 지원하는 공통 이벤트" 비트맵 — 커널이 읽어서 perf list에 반영 |

일반화 이름 → 번호 매핑은 `drivers/perf/arm_pmuv3.c`의 `armv8_pmuv3_perf_map[]`(6.18.55 소스에서 확인)과 캐시 맵(`armv8_a57_perf_cache_map` 등)에 있다. 주요 공통 이벤트 번호(ARM ARM에 정의된 architectural/common event, 코어마다 지원 여부는 PMCEID로 확인):

| 번호 | 이름 | perf 일반화 이름 |
|---|---|---|
| 0x00 | SW_INCR | — |
| 0x01 | L1I_CACHE_REFILL | `L1-icache-load-misses` |
| 0x03 | L1D_CACHE_REFILL | `cache-misses`, `L1-dcache-load-misses` |
| 0x04 | L1D_CACHE | `cache-references`, `L1-dcache-loads` |
| 0x05 | L1D_TLB_REFILL | `dTLB-load-misses` |
| 0x08 | INST_RETIRED | `instructions` |
| 0x10 | BR_MIS_PRED | `branch-misses` |
| 0x11 | CPU_CYCLES | `cycles` |
| 0x19 | BUS_CYCLES | `bus-cycles` |
| 0x12 | BR_PRED | — (6.18 generic 맵에서 `branches`는 미지원) |
| 0x16 / 0x17 | L2D_CACHE / L2D_CACHE_REFILL | — |
| 0x1B | INST_SPEC | — |
| 0x23 / 0x24 | STALL_FRONTEND / STALL_BACKEND | `stalled-cycles-frontend/backend` |

### 2.2 커널이 PMU를 발견하는 과정

DT의 `pmu` 노드(QEMU virt: `compatible = "arm,armv8-pmuv3"`, `interrupts = <0x01 0x07 0x104>` = PPI 7, level-high)를 `drivers/perf/arm_pmuv3.c`가 매칭하고(D3 driver matching), PMCR_EL0.N과 PMCEID를 읽어 카운터 수·지원 이벤트를 등록한다. 게스트 dmesg:

```text
[    0.567453] CPU features: detected: PMUv3
[    7.638258] hw perfevents: enabled with armv8_pmuv3 PMU driver, 7 (0,8000003f) counters available
```

출력에서 볼 것: "7 counters" = 범용 6개 + cycle counter 1개. QEMU DT가 범용 `arm,armv8-pmuv3`로 선언했기 때문에 PMU 이름이 `armv8_cortex_a57`가 아니라 `armv8_pmuv3`다(실제 SoC DT는 보통 `arm,cortex-a57-pmu`처럼 코어별 compatible을 써서 코어 전용 이벤트 맵을 쓴다). `8000003f`는 사용 가능한 카운터 비트마스크다 — 비트 0..5(범용 6개)와 비트 31(PMCCNTR). 실제 Cortex-A57/A72 실리콘과 같은 구성이다. PMU 인터럽트도 확인된다(`/proc/interrupts`, `-icount` 부팅에서 찍은 값):

```text
 24:         63          0 GIC-0  23 Level     arm-pmu
```

GIC INTID 23 = PPI 7(PPI는 INTID 16부터 시작), DT의 `<0x01 0x07 0x104>`와 일치한다. 이 카운트가 `perf record` 중에 늘어나지 않으면 샘플링이 안 되는 것이다(12절 장면 4). sysfs에는 `/sys/bus/event_source/devices/armv8_pmuv3/`가 생기고 `events/`에 이름 붙은 이벤트가 나열된다.

### 2.3 예제 2 — TCG PMU가 실제로 세는 이벤트 전수 조사

"PMU가 있다"와 "카운터가 의미 있는 값을 낸다"는 다르다. 게스트에서 raw 이벤트 0x00~0x24를 하나씩 `dd`에 대해 세어 봤다.

```sh
# 게스트 안 (perf_event_paranoid=2, root)
perf list hw
ls /sys/bus/event_source/devices/armv8_pmuv3/events/
for e in r00 r01 r02 r03 r04 r05 r08 r09 r0a r0b r0c r0d r0e r10 r11 r12 r13 r14 r15 \
         r16 r17 r18 r19 r1a r1b r1c r1d r1e r20 r21 r22 r23 r24; do
  perf stat -x, -e $e -- dd if=/dev/zero of=/dev/null bs=4k count=200 2>&1 | grep -v records | tail -1
done
```

`-x,`는 CSV 출력(값, 단위, 이벤트, 실행 시간 ns, 실행 비율 %)이다. 결과 중 일부(전체 33개 중 대표):

```text
0,,r00,61105200,100.00,,
0,,r03,41401984,100.00,,
0,,r04,27742800,100.00,,
0,,r08,46967808,100.00,,
0,,r10,130698400,100.00,,
253261988,,r11,253524832,100.00,,
0,,r12,217132432,100.00,,
0,,r1b,2316559424,100.00,,
0,,r23,108520768,100.00,,
0,,r24,40044848,100.00,,
```

그리고 `perf list hw`는 `cpu-cycles OR cycles` **한 줄만** 보여 줬고, `events/` 디렉터리에도 `cpu_cycles`만 있었다. 일반화 이름으로 열면:

```text
          22247473      cycles
   <not supported>      instructions
   <not supported>      branches
   <not supported>      branch-misses
   <not supported>      cache-references
   <not supported>      cache-misses
```

CPU 모델과 옵션을 바꿔 가며 같은 실험을 한 결과(QEMU 10.2.1, 모두 실측):

| QEMU 옵션 | PMCEID가 광고한 이벤트 (`events/`) | 0이 아닌 값을 낸 이벤트 | 비고 |
|---|---|---|---|
| `-cpu cortex-a57,pmu=on` | `cpu_cycles` | **0x11 CPU_CYCLES만** | 나머지 raw 번호는 열리지만 항상 0. 0x1E(CHAIN)는 출력 없음 |
| `-cpu max,pmu=on` | `cpu_cycles`, `stall`, `stall_backend`, `stall_frontend` | 0x11 | `cpu part 0x051`(QEMU max). r08 = 0 |
| `-cpu cortex-a57,pmu=on -icount shift=0` | `cpu_cycles`, `inst_retired` | **0x11 + 0x08** | `instructions`가 `[Hardware event]`로 나타남 |

정리하면 **TCG의 PMU에는 캐시도, 분기 예측기도, 파이프라인 스톨도 없다.** TCG는 게스트 명령어를 호스트 코드로 번역해 실행하는 에뮬레이터라 캐시·분기 예측기를 모델링하지 않는다. 그래서 L1D refill, branch miss 같은 이벤트는 셀 대상 자체가 없다.

### 2.4 TCG의 "cycles"는 무엇을 세나

```text
 Performance counter stats for './matwalk row 4' (3 runs):

         845215770      task-clock                       #    0.906 CPUs utilized               ( +-  2.23% )
         844500919      cycles                           #    0.999 GHz                         ( +-  2.24% )
               568      page-faults                      #  672.018 /sec                        ( +-  0.06% )
```

출력에서 볼 것: `cycles`가 `task-clock`(나노초)과 거의 같고, perf가 계산한 주파수가 **정확히 1 GHz**다. QEMU TCG는 cycle counter를 가상 시계(virtual clock)의 나노초에 1 GHz를 곱해 만든다. 즉 TCG의 cycles = **호스트에서 에뮬레이션에 걸린 시간**이지 Cortex-A57의 사이클이 아니다. 에뮬레이션 비용(특히 메모리 접근마다 소프트웨어 TLB 조회)이 그대로 섞인다.

또 하나: `perf stat -a -- sleep 1`로 시스템 전체를 재면 아무것도 안 하는 CPU에서도 1초에 10억 cycles가 나왔다.

```text
S0-D0-C0              1         1231780091      cycles                           #    1.000 GHz
S0-D0-C0              1         1231787216      task-clock                       #    0.997 CPUs utilized
S0-D0-C1              1         1236022360      cycles                           #    1.000 GHz
S0-D0-C1              1         1236067696      task-clock                       #    1.001 CPUs utilized
```

실리콘의 cycle counter는 코어가 WFI로 클럭 게이팅되면 보통 멈추지만(구현에 따라 다름), TCG의 것은 벽시계처럼 계속 간다. 실제 보드에서 idle CPU의 cycles는 이보다 훨씬 작게 나온다.

### 2.5 예제 3 — `-icount`로 결정적인 명령어 수 얻기

`-icount shift=0`은 QEMU가 "명령어 1개 = 가상 시간 2^0 ns"로 시간을 진행시키는 모드다. 그러면 INST_RETIRED가 지원되고, **명령어 수는 실행할 때마다 똑같이** 나온다(공유 VM 부하와 무관). 대신 cycles도 같은 가상 시계를 쓰므로 IPC는 언제나 정확히 1.00이 된다.

```sh
# VM 호스트: 같은 게스트를 -icount shift=0 을 붙여 다시 부팅
qemu-system-aarch64 -machine virt -cpu cortex-a57,pmu=on -icount shift=0 -smp 2 -m 1G ... (나머지 동일)
# 게스트 안
perf stat -e instructions,cycles -- ./matwalk row 4
perf stat -e instructions,cycles -- ./matwalk col 4
perf stat -e instructions:u,instructions:k -- ./branch branchy
perf stat -e instructions:u,instructions:k -- ./branch branchless
./perfev
```

```text
 Performance counter stats for './matwalk row 4':

          34978901      instructions                     #    1.00  insn per cycle
          34978901      cycles

       0.037590720 seconds time elapsed

 Performance counter stats for './matwalk col 4':

          56165559      instructions                     #    1.00  insn per cycle
          56165559      cycles

       0.058233552 seconds time elapsed

 Performance counter stats for './branch branchy':

         217551790      instructions:u
           4305564      instructions:k

 Performance counter stats for './branch branchless':

         228500179      instructions:u
           4168373      instructions:k

events in group: 3
cycles        : 60417707
instructions  : 60417707
raw 0x03      : 0
```

(출력 사이의 빈 줄과 user/sys 시간 줄 일부를 생략했다.)

출력에서 볼 것:
- `instructions`와 `cycles`가 **한 자리까지 같다**. `insn per cycle`은 TCG가 만들어 낸 값(언제나 1.00)이라 의미가 없다. `perfev`도 이번엔 instructions 카운터를 열었다(그룹 3개) — 같은 바이너리가 QEMU 옵션 하나로 다르게 동작한다.
- 경과 시간까지 명령어 수에 비례한다(row 0.0376 s, col 0.0582 s ≈ 35.0M : 56.2M). icount 모드에서는 가상 시간 = 명령어 수이므로 **메모리 접근 패턴이 시간에 전혀 반영되지 않는다.** 일반 TCG 모드에서 row/col이 15배 차이 났던 것(3.2절)과 비교하면, 그 15배 중 명령어 수 차이는 1.6배뿐이고 나머지는 에뮬레이터의 메모리 처리 비용이었다는 것을 알 수 있다.
- branchless가 branchy보다 명령어를 **5% 더** 실행한다(228.5M vs 217.6M). 그런데 실제 M2 코어에서는 branchless가 4배 빨랐다(3.3절). 같은 일을 하는 데 명령어가 더 많아도 IPC가 훨씬 높으면 이긴다 — "명령어 수를 줄이는 최적화"만으로는 부족하고 IPC(분기 미스·캐시 미스)를 같이 봐야 하는 이유다.
- `instructions:k` 약 420만 = 프로그램 시작·page fault·exit 등 커널이 대신 한 일. `:u`/`:k` 수식어로 나눠 셀 수 있다.

결정적인 명령어 수는 "알고리즘을 바꿨더니 명령어가 몇 % 줄었나"를 노이즈 없이 비교할 때 쓸모가 있다. 실리콘이 아니라 ISA 수준의 측정이라는 것만 기억한다.

> 실무 교훈: 새 보드·새 커널·가상화 환경에서 perf를 쓰기 전에 **`perf list hw`와 `ls /sys/bus/event_source/devices/*/events`로 무엇이 광고되는지, 그리고 알려진 워크로드로 값이 0이 아닌지** 먼저 확인한다. KVM 게스트도 하이퍼바이저가 PMU를 가상화해 줘야 카운터가 보인다(arm64 KVM은 `-cpu host,pmu=on` 계열로 PMUv3를 노출, Apple Virtualization.framework는 노출하지 않음 — 이 VM 호스트에서 `sudo perf stat -e cycles`가 "The cycles event is not supported"로 실패했다).

## 3. perf stat — 세기 (counting)

### 3.1 기본 사용법

| 옵션 | 뜻 |
|---|---|
| `perf stat ./prog` | 기본 이벤트 세트(task-clock, context-switches, cpu-migrations, page-faults, cycles, instructions, branches, branch-misses) |
| `-e ev1,ev2` | 이벤트 지정. `:u`/`:k` 접미사로 유저/커널만 (`instructions:u`) |
| `-e '{ev1,ev2}'` | 중괄호 = 그룹. 항상 같은 순간에 같이 카운터에 올라간다 (비율 계산이 정확해짐) |
| `-r N` | N번 반복, 평균과 `+- x%` 표준편차 출력 |
| `-a` | 시스템 전체(모든 CPU). 보통 `-- sleep 5`와 함께 |
| `-C 1,3` | 특정 CPU만 (`-a` 함의) |
| `-A` / `--per-core` / `--per-socket` | CPU별 / 코어별 / 소켓별로 나눠 출력 |
| `-p PID`, `-t TID` | 이미 도는 프로세스/스레드에 붙기 |
| `-I 1000` | 1초마다 중간값 출력 (장시간 관찰) |
| `-x,` | CSV 출력 (스크립트 처리용) |

**IPC**(instructions per cycle)는 perf stat이 instructions와 cycles가 둘 다 있으면 자동으로 `# 1.85 insn per cycle`처럼 계산해 준다. 한 줄 요약: "코어가 매 사이클 몇 개의 명령어를 끝냈나". 최신 out-of-order 코어(A76 이상)는 이론상 4 이상도 가능하고, **IPC가 0.5 이하이면 대개 메모리를 기다리고 있다(memory-bound)**, 2 이상이면 계산이 코어를 잘 채우고 있다(compute-bound 쪽). 이 해석은 9절 roofline과 이어진다.

### 3.2 예제 4 — 같은 합, 다른 순회 순서 (cache-friendly vs hostile)

16 MiB 행렬(L2보다 큼)을 행 우선(row-major, 연속 주소)과 열 우선(column-major, 8 KiB stride)으로 합산한다. C의 2차원 배열은 행 우선 저장이므로 `m[i][j]`에서 j를 안쪽 루프로 돌리면 캐시 라인 하나(64 B)로 원소 16개를 쓰고, i를 안쪽으로 돌리면 원소마다 새 캐시 라인(그리고 2개 원소마다 새 4 KiB 페이지)을 건드린다.

```c
/* matwalk.c — 같은 행렬을 row-major / column-major 로 합산: 캐시 친화도 비교 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define N 2048                       /* 2048 x 2048 x 4B = 16 MiB > L2 */

static int m[N][N];

static long sum_row(void)            /* 연속 주소: 64B 라인 하나로 16개 원소 */
{
    long s = 0;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            s += m[i][j];
    return s;
}

static long sum_col(void)            /* stride 8 KiB: 원소마다 새 캐시 라인 */
{
    long s = 0;
    for (int j = 0; j < N; j++)
        for (int i = 0; i < N; i++)
            s += m[i][j];
    return s;
}

int main(int argc, char **argv)
{
    if (argc < 2) { fprintf(stderr, "usage: %s row|col [reps]\n", argv[0]); exit(1); }
    int reps = argc > 2 ? atoi(argv[2]) : 4;
    for (int i = 0; i < N; i++)
        for (int j = 0; j < N; j++)
            m[i][j] = i ^ j;
    long s = 0;
    for (int r = 0; r < reps; r++)
        s += strcmp(argv[1], "row") == 0 ? sum_row() : sum_col();
    printf("%s sum=%ld\n", argv[1], s);
    return 0;
}
```

**(a) VM 호스트 — 진짜 Apple M2 코어, 하지만 PMU 없음.** 하드웨어 이벤트는 못 쓰고 software 이벤트(task-clock)만 쓴다. `sudo`는 paranoid=4를 우회하기 위해서다(전역 sysctl은 건드리지 않음).

```sh

sudo perf stat -e cycles,instructions ./matwalk row
```

### 3.3 예제 5 — 예측 불가능한 분기 vs branchless

```c
/* branch.c — 예측 불가능한 분기 vs branchless: branch-misses 비교 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define LEN (1 << 20)
static unsigned char data[LEN];

__attribute__((noinline)) static long branchy(void)
{
    long s = 0;
    for (int i = 0; i < LEN; i++)
        if (data[i] >= 128)          /* 랜덤 데이터 → 50% 확률 분기 */
            s += data[i];
    return s;
}

__attribute__((noinline)) static long branchless(void)
{
    long s = 0;
    for (int i = 0; i < LEN; i++) {
        long mask = -(long)(data[i] >= 128);   /* 0 또는 -1 */
        s += mask & data[i];
    }
    return s;
}

static int cmp(const void *a, const void *b)
{
    return *(const unsigned char *)a - *(const unsigned char *)b;
}

int main(int argc, char **argv)
{
    if (argc < 2) { fprintf(stderr, "usage: %s branchy|branchless|sorted\n", argv[0]); exit(1); }
    srand(1);
    for (int i = 0; i < LEN; i++)
        data[i] = rand() & 0xff;
    if (strcmp(argv[1], "sorted") == 0)
        qsort(data, LEN, 1, cmp);
    long s = 0;
    for (int r = 0; r < 20; r++)
        s += strcmp(argv[1], "branchless") == 0 ? branchless() : branchy();
    printf("%s s=%ld\n", argv[1], s);
    return 0;
}
```

함정 하나부터. 그냥 `-O2`로 컴파일하면 gcc 15가 **branchy를 스스로 NEON 벡터 코드로 바꿔 버린다**(`cmlt`로 마스크를 만들고 `and`·`add` — 분기가 사라짐). 측정하려는 현상이 컴파일러에 의해 지워진 것이다. 그래서 if-conversion과 벡터화를 끄고 컴파일한 뒤 `objdump`로 확인했다.

```sh
gcc -std=gnu11 -Wall -Wextra -O2 -fno-tree-vectorize -fno-if-conversion -fno-if-conversion2 -g branch.c -o branch
objdump -d --no-show-raw-insn branch | awk '/<branchy>:/,/^$/'
```

### 3.4 multiplexing과 `(xx.xx%)` 스케일링

카운터는 6개(+cycle 1개)뿐인데 이벤트를 그보다 많이 요청하면? perf는 이벤트 그룹들을 **시간 분할(time-slicing)**로 돌린다. 커널의 hrtimer(`perf_mux_hrtimer_handler` → `perf_rotate_context`, 주기는 `/sys/bus/event_source/devices/<pmu>/perf_event_mux_interval_ms`, 기본값은 커널의 `PERF_CPU_HRTIMER` = 1000/HZ ms — 게스트에서 `cat`하면 `4`, HZ=250이므로 4 ms)가 주기적으로 카운터에 올라가는 이벤트를 회전시킨다. 각 이벤트는 자기가 실제로 카운터에 올라가 있던 시간(time_running)과 활성화되어 있던 시간(time_enabled)을 기록하고, perf stat은 다음처럼 **추정치로 보정**한다.

`보고값 = 원시값 × time_enabled / time_running`, 그리고 괄호 안 퍼센트 = `time_running / time_enabled`

## 4. perf record · report · annotate — 샘플링 프로파일링

### 4.1 테스트 프로그램 — 깊은 호출 체인

"추론 파이프라인" 모양을 흉내 낸 프로그램이다: `preprocess`, `inference`, `postprocess`가 `stage1 → stage2 → stage3 → leaf_*`를 부르고, 실제 일은 잎(leaf) 함수 두 개(부동소수 연산 `leaf_math`, 메모리 긁기 `leaf_mem`)가 한다. `noinline`으로 인라인을 막았다.

```c
/* deepcall.c — 깊은 호출 체인: fp vs dwarf 언와인딩 비교용 */
#include <stdio.h>
#include <stdlib.h>

#define NOINL __attribute__((noinline))
static volatile double sink;

NOINL static double leaf_math(int n)          /* 실제 일을 하는 잎 함수 */
{
    double x = 0;
    for (int i = 1; i < n; i++)
        x += 1.0 / ((double)i * i);
    return x;
}
NOINL static double leaf_mem(int n)           /* 메모리를 긁는 잎 함수 */
{
    static int buf[1 << 18];
    long s = 0;
    for (int r = 0; r < n / 1024; r++)
        for (int i = 0; i < (1 << 18); i += 16)
            s += buf[i]++;
    return (double)s;
}
NOINL static double stage3(int n, int k) { return k ? leaf_math(n) : leaf_mem(n); }
NOINL static double stage2(int n, int k) { return stage3(n, k) + 1; }
NOINL static double stage1(int n, int k) { return stage2(n, k) + 1; }
NOINL static double preprocess(int n)  { return stage1(n, 0); }
NOINL static double inference(int n)   { return stage1(n * 3, 1); }
NOINL static double postprocess(int n) { return leaf_math(n); }

int main(int argc, char **argv)
{
    int iters = argc > 1 ? atoi(argv[1]) : 200;
    for (int it = 0; it < iters; it++) {
        sink = preprocess(20000);
        sink = inference(20000);
        sink = postprocess(20000);
    }
    printf("done %f\n", sink);
    return 0;
}
```

게스트 안에서 두 가지로 컴파일했다: `deep_fp`(`-O2 -g -fno-omit-frame-pointer`)와 `deep_omit`(`-O2 -g -fomit-frame-pointer`).

> 재미있는 사실: 처음엔 옵션 없이 `-O2`로 "frame pointer 없는 버전"을 만들려 했는데, `objdump`해 보니 프롤로그에 `stp x29, x30, [sp, #-16]!` / `mov x29, sp`가 그대로 있었다. **Ubuntu 24.04부터 배포판 gcc가 기본으로 frame pointer를 켠다**(배포판 전체 프로파일링을 쉽게 하려는 정책). 그래서 frame pointer를 빼려면 `-fomit-frame-pointer`를 명시해야 했다. Yocto/Buildroot 툴체인은 이런 기본값이 없으니 직접 확인해야 한다.

- `cycles:P` — `:P`는 perf가 가능한 최대 정밀도(precise_ip)를 요청했다는 뜻. x86 PEBS처럼 skid(인터럽트가 실제 이벤트보다 몇 명령 늦게 걸리는 현상) 없는 샘플링을 하드웨어가 지원하면 쓰고, ARM PMUv3 기본 샘플링은 skid가 있다(ARM에서 정확한 주소가 필요하면 SPE, 9절).
- 콜스택은 **caller 방향으로** 읽는다(`leaf_mem` ← `stage2` ← `stage1` ← `main`).

출력에서 볼 것 세 가지:
1. **`preprocess`, `inference`, `stage3`가 없다.** `objdump`를 보면 `stage3`는 `cbz w1, ...; b leaf_math; b leaf_mem` — 꼬리 호출(tail call)이라 `bl`이 아니라 `b`로 점프한다. 자기 프레임을 만들지 않고 잎 함수로 넘어가 버리므로 스택에 흔적이 없다. `preprocess`/`inference`는 gcc가 상수 인자를 전파한 복제본 `preprocess.constprop.0`/`inference.constprop.0`이 되었고, 둘 다 `mov w0, #...; b stage1`로 꼬리 점프한다. `postprocess.constprop.0`도 `b leaf_math`라서 `leaf_math`의 5.15%는 `main` 바로 아래에 붙었다. **프로파일러가 거짓말하는 게 아니라 컴파일러가 프레임을 지운 것**이다. 정확한 경로가 필요하면 `-fno-optimize-sibling-calls`로 다시 빌드한다.
2. **잎 함수 바로 위의 `stage2`가 보인다.** AArch64 잎 함수는 프레임 레코드를 만들지 않아서(`leaf_mem` 프롤로그에 `stp x29, x30`이 없다), 순수 frame pointer 걷기는 잎 함수의 caller를 건너뛴다. perf 도구는 arm64에서 `--call-graph fp`일 때 **LR 레지스터를 같이 기록**(`arch__add_leaf_frame_record_opts`, tools/perf/arch/arm64/util/machine.c)하고, 리포트 시 잎 함수의 DWARF CFI로 "지금 LR이 진짜 리턴 주소인가"를 판단해 빠진 프레임을 끼워 넣는다(tools/perf/util/arm64-frame-pointer-unwind-support.c).
3. **커널 프레임 `el0_da` → `do_page_fault` → `do_wp_page`가 20% 가까이 된다.** `leaf_mem`이 `static int buf[1 << 18]`(1 MiB, .bss)에 처음 쓰는 순간마다 page fault가 난다(A5에서 본 demand paging; `do_wp_page`는 zero page를 쓰기 가능 페이지로 바꾸는 write-protect fault). 30회만 돌린 짧은 실행이라 초기 fault 비중이 크다. `el0_da` = "EL0에서 온 Data Abort" — MMU abort를 커널이 정상 경로로 처리하는 것이다.

비교를 위해 같은 소스를 VM 호스트(gcc 15, 진짜 M2 코어)에서 200회 돌리며 software 이벤트 `cpu-clock`으로 샘플링했다(PMU가 없으니 하드웨어 cycles 대신 타이머 기반 샘플링):

```sh
sudo perf record -e cpu-clock -F 999 -g -o host_fp.data ./deep_fp 200
sudo perf report -i host_fp.data --stdio --no-children --percent-limit 3 -g none
```

```text

    78.95%  deep_fp  deep_fp            [.] leaf_mem
    16.37%  deep_fp  deep_fp            [.] leaf_math
```

출력에서 볼 것: 실행이 길어 초기 page fault 비중이 사라졌고, `leaf_mem`:`leaf_math` 비율도 게스트(35.8 : 16.5)와 다르다. **에뮬레이터·실행 길이·컴파일러가 바뀌면 프로파일 모양이 바뀐다** — 프로파일은 항상 목표 하드웨어에서, 정상 상태(steady state) 구간을 떠야 한다. PMU가 없는 환경에서도 `cpu-clock`/`task-clock` 샘플링으로 "어디서 시간을 쓰나"는 볼 수 있다는 것도 기억해 두자.

| 방법 | 기록 시점 비용 | 파일 크기 | 필요 조건 | 함정 |
|---|---|---|---|---|
| `-g` / `--call-graph fp` | 낮음 (커널이 프레임 레코드 순회) | 작음 | 모든 유저 코드가 frame pointer로 빌드 | 라이브러리 하나라도 fp 없으면 그 아래가 끊김. 꼬리 호출은 원래 안 보임 |
| `--call-graph dwarf[,size]` | 높음 (샘플마다 스택 복사) | 매우 큼 | `.eh_frame`/`.debug_frame` + perf가 libdw/libunwind로 빌드됨 | 스택 복사 크기(기본 8192)보다 깊으면 잘림. 버퍼 넘침 → "lost chunks". JIT 코드 불가 |

## 6. flame graph — 콜스택 수천 개를 한 장으로

### 6.1 무엇을 그리는가

Brendan Gregg가 만든 시각화다. 규칙은 단 세 개다.
- **y축 = 스택 깊이.** 맨 아래가 루트(`_start`, 스레드 시작), 위로 갈수록 callee.
- **x축 = 샘플 비율.** 상자 폭 = 그 함수가 스택에 있었던 샘플 수. **시간 순서가 아니다** — 같은 부모 아래 형제는 이름순으로 정렬된다(그래서 "왼쪽이 먼저 실행됐다"고 읽으면 틀린다).
- **꼭대기(위가 비어 있는 부분) = self 시간.** 넓은 고원(plateau)이 최적화 대상이다.

만드는 파이프라인은 세 단계다: `perf script`(샘플마다 콜스택을 텍스트로 출력) → **stackcollapse**(같은 스택을 한 줄 `a;b;c 개수`로 접기 = "folded" 형식) → **flamegraph.pl**(folded를 SVG로). 원조 스크립트는 github.com/brendangregg/FlameGraph의 `stackcollapse-perf.pl`과 `flamegraph.pl`이다. 이 랩에는 인터넷 없이 쓸 FlameGraph 저장소가 없어서(VM 호스트·게스트 모두 확인), 같은 일을 하는 짧은 Python 두 개를 직접 썼다. 최신 perf에는 `perf script report flamegraph`도 있지만 Python 스크립팅 지원과 d3-flame-graph 템플릿(HTML)이 필요하다.

### 6.2 예제 11 — stackcollapse 직접 구현

`perf script` 출력은 이런 모양이다(게스트 실제 출력, 샘플 1개):

```text
perf-exec     162   649.795445:          1 cycles:P:
	ffffa94b9c9817c0 perf_event_exec+0x388 ([kernel.kallsyms])
	ffffa94b9cab901c begin_new_exec+0x594 ([kernel.kallsyms])
	ffffa94b9cb40af0 load_elf_binary+0x378 ([kernel.kallsyms])
	ffffa94b9cab6e58 bprm_execve+0x290 ([kernel.kallsyms])
...
```

헤더 줄(comm pid time: period event) 다음에 탭으로 들여쓴 프레임이 잎→루트 순으로 나오고, 빈 줄로 샘플이 끝난다.

```python
#!/usr/bin/env python3
"""collapse.py — `perf script` 출력 → folded stacks (stackcollapse-perf.pl 최소 구현)"""
import sys, collections, re

counts = collections.Counter()
comm, stack = None, []

def flush():
    if comm is not None and stack:
        counts[";".join([comm] + stack[::-1])] += 1   # root → leaf 순서

for line in sys.stdin:
    line = line.rstrip("\n")
    if not line.strip():                 # 빈 줄 = 샘플 하나 끝
        flush(); comm, stack = None, []
        continue
    if not line.startswith((" ", "\t")):  # 헤더: "comm pid [cpu] time: period event:"
        comm = line.split()[0]
        continue
    parts = line.split(None, 1)          # "  addr sym+off (dso)"
    if len(parts) < 2:
        continue
    sym = re.sub(r"\+0x[0-9a-f]+", "", parts[1])
    sym = re.sub(r"\s*\(.*\)$", "", sym).strip() or "[unknown]"
    stack.append(sym)
flush()
for k, v in sorted(counts.items()):
    print(k, v)
```

```sh
# VM 호스트: 게스트에서 만든 perf script 텍스트를 접는다
python3 collapse.py < fp.script > fp.folded
grep '^deep_fp;' fp.folded > fpu.folded          # perf-exec 등 다른 comm 제외
sort -t' ' -k2 -n fpu.folded | tail -4
```

### 6.3 예제 12 — folded → SVG

```python
#!/usr/bin/env python3
"""flamesvg.py — folded stacks → note-spec SVG flame graph (no text fill, viewBox only)"""
import sys, html

W, ROW, X0, TOP = 660, 20, 10, 30
folded = [l.rsplit(" ", 1) for l in open(sys.argv[1]) if l.strip()]
title = sys.argv[2] if len(sys.argv) > 2 else "flame graph"
MAXD = int(sys.argv[3]) if len(sys.argv) > 3 else 99
total = sum(int(c) for _, c in folded)
tree = {}
for stk, c in folded:                       # trie: name -> [count, children]
    node = tree
    for f in stk.split(";")[:MAXD]:
        ent = node.setdefault(f, [0, {}])
        ent[0] += int(c)
        node = ent[1]

def depth(n):
    return 1 + max((depth(ch) for c, ch in n.values() if W * c / total >= 1.5), default=0) if n else 0
D = depth(tree)
H = TOP + D * ROW + 30
pal = ["#e08a3c", "#d0564a", "#4a7bd0", "#3f9a6b"]
out = [f'<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 {W + 2*X0} {H}">',
       f'<text x="{X0}" y="18" font-size="13">{title} — {total} samples</text>']

def draw(node, x, d):
    for name, (c, ch) in sorted(node.items()):
        w = (W) * c / total
        if w < 1.5:
            x += w
            continue
        y = TOP + (D - 1 - d) * ROW                 # root at bottom
        col = pal[d % len(pal)]
        out.append(f'<rect x="{x:.1f}" y="{y}" width="{max(w - 1, 0.5):.1f}" height="{ROW - 2}" '
                   f'fill="{col}" fill-opacity="0.25" stroke="{col}" stroke-width="0.6"/>')
        label = name + f" {100*c/total:.1f}%"
        maxch = int((w - 6) / 7.2)                  # 12px font ~7.2px per char
        if maxch >= 4:
            if len(label) > maxch:
                label = label[:maxch - 2] + ".."
            out.append(f'<text x="{x+3:.1f}" y="{y + ROW - 7}" font-size="12">{html.escape(label)}</text>')
        draw(ch, x, d + 1)
        x += w
draw(tree, X0, 0)
out.append(f'<text x="{X0}" y="{H - 8}" font-size="12">x = sample share (sorted by name, not time), y = stack depth (root at bottom)</text>')
out.append("</svg>")
print("\n".join(out))
```

### 6.4 off-CPU 분석이라는 반쪽

on-CPU flame graph(cycles 샘플링)는 **CPU 위에서 돈 시간**만 보인다. 센서 스레드가 I/O·락·`read()`에서 **잠들어 있던 시간**은 샘플이 안 찍힌다. 지연 문제의 절반은 여기 있다. off-CPU 분석은 `sched:sched_switch`에서 "잠드는 순간의 스택"과 "깨어난 시각 − 잠든 시각"을 모아 그 시간으로 가중한 flame graph를 만든다. perf만으로는 `perf record -e sched:sched_switch -g` + 후처리로 근사하고(잠드는 횟수만 셈, 시간 가중은 스크립트로), 시간 가중까지 정확히 하는 표준 도구는 bcc의 `offcputime`(eBPF, M7)이다. 8.3절에서 sched_switch 스택 기록을 실제로 해 본다.

출력에서 볼 것:
- 유저 → 커널 경계를 넘는 **한 줄짜리 전체 경로**: libc `read` → `el0t_64_sync`(EL0 동기 예외 벡터) → `el0_svc`(SVC 처리, E6) → `invoke_syscall` → `__arm64_sys_read` → `vfs_read`(F12) → `/dev/zero`의 read가 유저 버퍼를 0으로 채우는 `__arch_clear_user`. Don이 bare-metal에서 SVC 핸들러를 따라가던 그 경로가 실측 스택으로 보인다.
- `0xaaaad8ed2d58` 같은 **이름 없는 주소**: Ubuntu의 `/usr/bin/dd`는 strip되어 있고 디버그 심볼 패키지(`coreutils-dbgsym`)가 없다. 그래서 dd 내부 함수는 이름이 없다. 심볼 해석 체인은 10절.
- `el0_svc` self가 24%로 이상하게 크다. 해석(추정): arm64에서 PMU overflow는 일반 IRQ라서, 커널이 IRQ를 막고 있는 구간(syscall 진입·종료 처리 일부)에서는 샘플이 찍히지 못하고 **IRQ가 다시 풀리는 지점에 몰린다**. 실리콘에서도 같은 현상이 있어서 arm64는 GICv3 pseudo-NMI(`CONFIG_ARM64_PSEUDO_NMI` + 부트 인자 `irqchip.gicv3_pseudo_nmi=1`)로 PMU 인터럽트를 NMI처럼 받게 할 수 있다. x86의 PMU NMI와 같은 목적이다.

### 7.2 커널 심볼: `/proc/kallsyms` vs `vmlinux`

| 소스 | 언제 쓰나 | 얻는 것 |
|---|---|---|
| `/proc/kallsyms` (기록 시 perf가 읽어 둠) | 기본값. 타깃에서 바로 report | 함수 이름 + 오프셋 (`CONFIG_KALLSYMS_ALL`이면 데이터 심볼까지). 소스 줄 번호 없음 |
| `vmlinux` (`-k /path/vmlinux` 또는 `--vmlinux`) | 호스트에서 분석, `perf annotate`로 커널 함수 소스 보기 | DWARF가 있으면 소스·인라인 정보, 커널 함수 annotate |
| 모듈 `.ko` | `--symfs`에 `/lib/modules/<ver>/...` 트리 | 모듈 함수 이름 |

lab의 `vmlinux-trace`는 full DWARF5라서 호스트에서 `perf annotate -k vmlinux-trace __arch_clear_user`처럼 커널 함수 내부까지 볼 수 있다(10.3절에서 실행). `kptr_restrict=2`인 양산 커널에서는 kallsyms가 0 주소를 주므로 vmlinux가 유일한 길이다. KASLR 때문에 런타임 주소는 부팅마다 다르지만 perf는 기록 시점의 커널 맵(`_stext` 위치)을 perf.data에 저장해 vmlinux의 링크 주소와 맞춘다.

## 8. 스케줄링 보기 — `perf sched`, 그리고 off-CPU

### 8.1 테스트 프로그램 — 한 CPU를 다투는 두 스레드

```c
/* compete.c — 같은 CPU에 묶인 두 스레드가 CPU를 다툰다: perf sched 관찰용 */
#define _GNU_SOURCE
#include <pthread.h>
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <unistd.h>

static void *worker(void *arg)
{
    const char *name = arg;
    cpu_set_t set;
    CPU_ZERO(&set);
    CPU_SET(0, &set);                         /* 둘 다 CPU0 에 고정 */
    if (pthread_setaffinity_np(pthread_self(), sizeof(set), &set) != 0) {
        perror("affinity");
        exit(1);
    }
    pthread_setname_np(pthread_self(), name);
    struct timespec t0, t;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    volatile unsigned long x = 0;
    do {                                      /* 1초 동안 바쁜 루프 */
        for (int i = 0; i < 100000; i++)
            x++;
        clock_gettime(CLOCK_MONOTONIC, &t);
    } while ((t.tv_sec - t0.tv_sec) * 1000000000L + (t.tv_nsec - t0.tv_nsec) < 1000000000L);
    return NULL;
}

int main(void)
{
    pthread_t a, b;
    if (pthread_create(&a, NULL, worker, "m6_hogA") ||
        pthread_create(&b, NULL, worker, "m6_hogB")) {
        perror("pthread_create");
        exit(1);
    }
    pthread_join(a, NULL);
    pthread_join(b, NULL);
    puts("compete done");
    return 0;
}
```

읽는 법:

- `perf sched latency`의 max delay 206 ms는 스레드 생성 직후 한 스레드가 오래 못 받은 구간이다. 공유 VM에서 QEMU vCPU 스레드 자체가 호스트에서 밀렸을 가능성도 있어 이 값 하나로 결론 내지 않는다. 대신 **"max가 avg의 수십 배"라는 패턴**이 실제 보드에서도 지터 조사의 출발점이다.
- Idle stats: CPU0은 0.43%만 idle(두 hog가 다 먹음), CPU1은 93% idle — affinity로 묶어 놓아서 옆 CPU가 놀고 있다는 게 숫자로 보인다. "CPU 사용률은 50%인데 왜 느리지?"의 전형적 답이다.

## 9. `perf trace` vs `strace`, 그리고 `perf mem`/`c2c`·roofline

### 9.1 예제 16 — syscall 추적 오버헤드

```c
/* sysloop.c — 짧은 syscall을 많이: perf trace vs strace 오버헤드 비교 */
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <unistd.h>

int main(int argc, char **argv)
{
    int n = argc > 1 ? atoi(argv[1]) : 100000;
    int fd = open("/dev/zero", O_RDONLY);
    if (fd < 0) { perror("open"); exit(1); }
    char buf[64];
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    for (int i = 0; i < n; i++) {
        if (read(fd, buf, sizeof buf) != sizeof buf) { perror("read"); exit(1); }
        getppid();
    }
    clock_gettime(CLOCK_MONOTONIC, &t1);
    double ms = (t1.tv_sec - t0.tv_sec) * 1e3 + (t1.tv_nsec - t0.tv_nsec) / 1e6;
    printf("%d iters (%d syscalls) in %.1f ms\n", n, 2 * n, ms);
    close(fd);
    return 0;
}
```

| 도구 | 방식 | 오버헤드의 원천 |
|---|---|---|
| `strace` | `ptrace(2)` — syscall마다 대상 프로세스를 **멈추고** tracer 프로세스로 context switch, 레지스터·메모리를 읽고 재개 | syscall 하나에 context switch 최소 2번 |
| `perf trace` | `raw_syscalls:sys_enter/exit` tracepoint를 ring buffer로 받음(대상은 멈추지 않음). 빌드에 따라 BPF로 인자(문자열 등)를 보강 | 이벤트 기록 + perf 프로세스가 버퍼를 비우는 CPU 비용. 비우는 속도가 못 따라가면 **LOST events** |
| `perf stat -e 'syscalls:sys_enter_*'` | 횟수만 셈 | 거의 0 |

### 9.2 `perf mem`과 `perf c2c` — 메모리 접근 자체를 샘플링

`perf stat`의 cache-miss 숫자는 "얼마나"만 알려 준다. "**어느 주소·어느 명령이** 미스를 내나"를 알려면 메모리 접근을 샘플링하는 하드웨어가 필요하다: x86은 PEBS load latency, arm64는 **SPE**(Statistical Profiling Extension, Armv8.2 선택 기능, Neoverse N1/V1, Cortex-A76 이후 일부) — 커널 드라이버 `drivers/perf/arm_spe_pmu.c`.
- `perf mem record/report`: 샘플마다 데이터 주소, 어느 레벨(L1/L2/DRAM)에서 hit했는지, 지연 사이클.
- `perf c2c`(cache-to-cache): 여러 코어가 같은 캐시 라인을 두고 핑퐁하는 **false sharing**을 찾는다. 링버퍼의 head/tail 인덱스를 같은 64 B 라인에 두는 실수 — Don이 SSD FW에서 멀티코어 큐를 만들 때 패딩을 넣던 그 문제다.

게스트에서 시도한 결과:

```sh
perf mem record -o mem.data -- ./matwalk row 1
perf c2c record -o c2c.data -- ./matwalk row 1
```

```text
failed: no PMU supports the memory events
failed: no PMU supports the memory events
```

출력에서 볼 것: Cortex-A57(그리고 TCG)에는 SPE가 없으니 당연한 실패다. SPE가 있는 코어(예: Neoverse 서버, 일부 Cortex-A76+ SoC)에서는 `/sys/bus/event_source/devices/arm_spe_0`이 보이고 같은 명령이 동작한다. 면접에서는 "perf mem/c2c는 x86 PEBS나 Arm SPE 같은 정밀 샘플링 하드웨어가 필요하다"까지 말할 수 있으면 충분하다.

### 9.3 IPC · cache-miss · roofline — AI 추론 루프를 볼 때의 틀

AI 가속기·로보틱스 SoC 면접에서 "이 커널이 왜 느린가"의 첫 질문은 **compute-bound인가 memory-bound인가**다. roofline 모델은 이것을 한 장으로 정리한다.

- **연산 강도(arithmetic intensity)** I = FLOP ÷ (DRAM에서 옮긴 바이트).
- 달성 가능 성능 = min(피크 FLOP/s, I × 메모리 대역폭). 그래프에서 기울어진 지붕(대역폭 한계)과 평평한 지붕(연산 한계)이 만나는 점이 **ridge point**.
- 예(계산): 행렬-벡터 곱(GEMV, fp32)은 원소 하나(4 B)를 읽어 곱셈·덧셈 2 FLOP — I ≈ 0.5 FLOP/B. DRAM 대역폭을 25.6 GB/s로 가정하면(예: 64비트 LPDDR4-3200 = 3200 MT/s × 8 B; 실제 값은 SoC 데이터시트에서 가져온다) 상한은 0.5 × 25.6 = 약 12.8 GFLOP/s로, 코어가 몇 개든 그 이상은 안 나온다. 큰 행렬 곱(GEMM)은 타일링으로 데이터를 재사용해 I를 수십까지 올릴 수 있어 연산 지붕에 닿는다.

perf로 이 판단을 하는 순서:
1. `perf stat -e cycles,instructions,L1-dcache-load-misses,LLC-load-misses`(또는 raw 이벤트 `r03` L1D_CACHE_REFILL, `r17` L2D_CACHE_REFILL, `r24` STALL_BACKEND — A53/A72급에서는 L2가 사실상 LLC) → IPC가 낮고(≈0.3~0.6) LLC miss/1000 instructions(MPKI)가 높으면 memory-bound 의심.
2. `stalled-cycles-backend`(STALL_BACKEND 0x24) 비율이 크면 백엔드(메모리·실행 유닛) 대기.
3. 예제 4처럼 순회 순서·타일 크기를 바꿔 보고 miss와 시간이 같이 움직이는지 확인.

이 노트의 TCG·VM 환경에서는 1~2를 실측할 수 없었다(2절). 그래서 예제 4의 cachegrind로 miss 패턴을, M2 task-clock으로 시간을 대신 보였다. 실제 보드(Jetson Orin = Cortex-A78AE, i.MX8M Plus = Cortex-A53, AM62 = Cortex-A53)에서는 같은 명령이 바로 동작한다.

## 10. 크로스 타깃 워크플로 — 타깃에서 기록, 호스트에서 분석

### 10.1 왜 나눠야 하나

임베디드 타깃은 보통 (1) rootfs가 작아서 바이너리가 strip되어 있고 디버그 정보가 없으며, (2) CPU가 느려 `perf report`(특히 dwarf 언와인딩, `annotate`)가 오래 걸리고, (3) 저장 공간이 적다. 그래서 **타깃은 기록만**, 해석은 디버그 정보가 다 있는 빌드 호스트에서 한다. 이때 연결 고리가 **build-id**다.

- **build-id**: 링커가 ELF의 `.note.gnu.build-id` 섹션에 넣는 해시(보통 SHA-1 160비트). 같은 소스·같은 옵션이면 같은 값, 한 바이트라도 다르면 다른 값. `file`, `readelf -n`으로 본다(B3).
- `perf record`는 샘플에 등장한 모든 DSO(실행 파일, 공유 라이브러리, 커널, vdso)의 경로와 build-id를 perf.data 헤더에 적는다 → `perf buildid-list`.
- `perf report`는 심볼을 찾을 때 **build-id가 맞는 파일만** 쓴다. 경로가 같아도 build-id가 다르면 버린다(엉뚱한 심볼보다 없는 게 낫다는 설계).

### 10.4 타깃용 perf 빌드하기 (가이드, 이 노트에서는 실행 안 함)

```sh

     EXTRA_CFLAGS="--sysroot=$SYSROOT" LDFLAGS="--sysroot=$SYSROOT" NO_LIBPYTHON=1 NO_GTK2=1
# 빌드 끝에 "Auto-detecting system features" 표가 나온다: libdw(dwarf 언와인딩), libelf, libunwind, libtraceevent ... ON/OFF 확인
```

- Buildroot: `BR2_PACKAGE_LINUX_TOOLS_PERF=y`(커널 패키지의 tools에서 빌드, K3). Yocto: `IMAGE_FEATURES += "tools-profile"` 또는 `perf` 레시피(K4·K5).
- 기능 표의 `libdw`/`libunwind`가 OFF면 `--call-graph dwarf`가 동작하지 않는다. `libtraceevent`가 OFF면 tracepoint 필드 해석이 안 된다. "perf가 있는데 dwarf가 안 돼요"의 대부분이 이것이다.
- 정 안 되면 static 빌드(`LDFLAGS=-static`)로 한 파일만 복사하는 방법도 쓴다.

## 12. Embedded 실무에서 다시 보기

**장면 1 — 센서 키트의 융합 스레드가 CPU 85%.** 로봇의 IMU(1 kHz, SPI) + 카메라(30 fps, V4L2) + LiDAR(UDP) 융합 프로세스가 Cortex-A53 한 코어를 거의 다 먹는다. 순서: `perf top -p $(pidof fusion)`으로 즉석 핫스팟 → `perf record -F 999 -g -p PID -- sleep 20`(이미 돌고 있는 프로세스에 20초만 붙기) → 보드에서 `perf.data`를 가져와 호스트에서 `--symfs=<Yocto의 rootfs + dbg 패키지>`로 flame graph. 흔한 결론: 카메라 프레임마다 `memcpy`(V4L2 MMAP 버퍼 → 앱 버퍼, I5)와 포맷 변환이 고원을 만든다 → DMABUF로 zero-copy, 변환은 ISP/GPU로.

**장면 2 — "커널 업데이트 후 느려졌다".** 같은 워크로드로 `perf stat -r 10 -e task-clock,context-switches,cpu-migrations,page-faults,cycles,instructions`를 커널 두 개에서 비교한다. instructions는 같은데 cycles만 늘었다 → IPC 하락(캐시·주파수·메모리 문제). context-switches나 page-faults가 늘었다 → 스케줄링·메모리 정책 변화. 그다음 `perf record -a -g`로 두 커널의 flame graph를 나란히 보거나 `perf diff old.data new.data`로 함수별 차이를 뽑는다. 주파수 거버너(cpufreq, N5)가 바뀌었는지(`cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor`)는 항상 먼저 본다.

**장면 3 — 커스텀 NPU/DSP 드라이버의 ioctl 지연.** 유저가 `ioctl(SUBMIT)` 후 완료까지 걸리는 시간이 들쭉날쭉하다. CPU 프로파일로는 안 보인다(대부분 기다리는 시간). `perf trace -e ioctl --duration 1`(1 ms 넘는 syscall만)로 느린 호출을 골라내고, `perf sched timehist -w`로 그 스레드가 언제 깨어났는지(wakeup) 본다. 드라이버의 완료 IRQ → `complete()` → 스레드 wakeup까지의 지연이 길면 IRQ 스레드 우선순위·CPU 친화도 문제다(N2). 더 정밀하게는 M5 ftrace의 `irq:*`·`sched:*` 이벤트, 그리고 HW 연계(M11: 드라이버에서 GPIO 토글 + scope).

**장면 4 — 보드 bring-up 때 perf가 이상하다.** `perf stat`이 `<not supported>`만 뱉거나 cycles가 0이다. 체크리스트: (1) `dmesg | grep "hw perfevents"` — PMU 드라이버가 probe됐나, DT에 `pmu` 노드와 올바른 `interrupts`(PPI, 코어별)가 있나(D4). (2) `CONFIG_HW_PERF_EVENTS`, `CONFIG_ARM_PMUV3`. (3) 하이퍼바이저/TrustZone 펌웨어가 PMU를 막고 있나(`MDCR_EL2`/`MDCR_EL3` 설정 — TF-A, C5). (4) 샘플링만 안 되고 counting은 되면 PMU IRQ 배선/트리거 타입 문제(`grep -i pmu /proc/interrupts`의 카운트가 늘어나는지). 이 마지막 항목은 Don이 RF 칩 bring-up에서 하던 "IRQ 라인 확인"과 완전히 같은 작업이다.

## 14. 면접에서 이렇게 말한다

**Q.** "Our inference loop got 30% slower after a kernel update. How do you investigate?"

**A.** 먼저 재현 가능한 벤치마크와 환경 고정(같은 입력, CPU 주파수 고정 또는 거버너 확인, 같은 바이너리)을 만든다. 두 커널에서 `perf stat -r 10`으로 task-clock, cycles, instructions, IPC, context-switches, cpu-migrations, page-faults를 비교해 문제를 분류한다: instructions가 같고 cycles만 늘었으면 마이크로아키텍처/메모리(캐시·TLB·주파수), 스위치·마이그레이션이 늘었으면 스케줄러, page-fault가 늘었으면 메모리 관리. 그다음 `perf record -g`로 양쪽 프로파일을 떠서 `perf diff`와 flame graph로 새로 커진 함수를 찾고, 커널 쪽 함수라면 `git log`/bisect로 해당 커밋을 좁힌다. 숫자 하나하나에 반복 편차를 같이 보고한다.

> I'd first make it reproducible and pin the environment — same binary, same input, fixed CPU frequency or at least the same governor. Then `perf stat -r 10` on both kernels to classify the regression: if instructions are flat but cycles went up, IPC dropped, so it's cache, TLB, frequency or memory bandwidth; if context switches or migrations went up it's a scheduling change; if page faults went up it's memory management. Next I'd record call graphs on both, compare with `perf diff` and side-by-side flame graphs to find what grew, and if it's a kernel function, bisect between the two kernels. I always report the run-to-run variance with each number.

**꼬리 질문**: "cpufreq 거버너가 같은데도 주파수가 다를 수 있나?" → 열 제한(thermal throttling, I4), 새 커널의 schedutil 동작 차이. `perf stat`의 `cycles`÷`task-clock`(= 실효 GHz)로 바로 확인된다.

**Q.** "perf shows 40% of the time in memcpy. What are your next steps?"

**A.** memcpy 자체를 빠르게 하려 하기 전에 **누가 왜 복사하는지**를 본다. `--children`이나 caller 기준 콜그래프(`perf report -G`)로 memcpy를 부르는 경로를 찾고, 복사 크기 분포를 확인한다(uprobe/bpftrace로 size 인자 히스토그램, M7). 큰 버퍼를 반복 복사하는 거라면 zero-copy(V4L2 DMABUF, mmap 공유, 포인터 전달)로 복사를 없애는 게 정답이고, 작은 복사가 수백만 번이라면 구조체·배치 설계를 바꾼다. 남는 복사는 memory-bound이므로 IPC·cache-miss로 대역폭 한계인지 확인하고, 정렬·NEON 구현(glibc가 CPU에 맞는 memcpy를 고르는지)을 본다.

> I'd first ask who is copying and why, rather than trying to make memcpy itself faster. I'd look at the callers with a caller-based call graph, and get the size distribution — a uprobe on memcpy with bpftrace gives a histogram of the length argument. If it's large frame buffers being copied, the fix is zero-copy: DMABUF between V4L2 and the consumer, shared mappings, or passing ownership instead of data. If it's millions of tiny copies, it's a data-structure or batching problem. Whatever copying remains is memory-bound, so I'd check IPC and cache misses against the platform's bandwidth, and make sure the libc picked the optimized memcpy variant for that core.

**Q.** "What's the difference between counting and sampling mode in perf?"

**A.** counting은 PMU 카운터를 켜 두고 끝에 합계만 읽는다 — 인터럽트가 없어 오버헤드가 거의 없고 `perf stat`이 쓴다. sampling은 카운터를 −period로 채워 overflow 인터럽트를 받아 그때의 PC·콜스택을 기록하는 통계적 프로파일링이고 `perf record`가 쓴다. 샘플 수 × period ≈ 전체 이벤트 수라서 샘플 분포가 이벤트 분포를 근사한다. `-F`면 커널이 period를 자동 조정한다.

> Counting just enables the counter and reads the total at the end — no interrupts, near-zero overhead; that's perf stat. Sampling preloads the counter so it overflows every N events, and the overflow interrupt records the PC, thread and optionally the call chain into a ring buffer; that's perf record. The distribution of samples approximates where the events happened. With -F the kernel adjusts the period dynamically to hit a target sample rate.

**Q.** "perf stat prints numbers with percentages in parentheses. What does that mean?"

**A.** multiplexing이다. 요청한 이벤트가 하드웨어 카운터보다 많아서(예: Cortex-A72는 범용 6개) 커널이 시간 분할로 돌렸고, 괄호 안은 그 이벤트가 실제로 카운터에 올라가 있던 시간 비율이다. 출력값은 `raw × enabled/running`으로 외삽한 추정치라 위상이 바뀌는 워크로드에서는 틀릴 수 있다. 비율을 낼 이벤트는 그룹으로 묶거나 실행을 나눈다.

> That's multiplexing. I asked for more events than the PMU has counters — an A72 has six general-purpose counters plus the cycle counter — so the kernel time-slices them, and the percentage is how long each event was actually on a counter. The printed value is scaled by enabled over running time, so it's an estimate that can be wrong if the workload has phases. For ratios like IPC I put the events in one group so they're always scheduled together.

**Q.** "Why are call stacks broken in perf, and how do you fix it?"

**A.** 기본 `-g`는 frame pointer 체인을 따라간다. `-fomit-frame-pointer`로 빌드된 코드가 끼면 체인이 끊겨 프레임이 사라진다. 해결은 세 가지: 프레임 포인터로 재빌드(가장 싸고 확실), `--call-graph dwarf`(스택을 복사해 CFI로 오프라인 언와인드 — 데이터가 수십 배 커짐), 하드웨어 분기 기록(x86 LBR, Armv9.2 BRBE). 꼬리 호출로 없어진 프레임은 원래 스택에 없으니 어떤 방법으로도 안 나온다. 직접 실험에서 fp 없는 빌드는 `stage2` 다음에 바로 `__libc_start_main`으로 건너뛰었고 dwarf로 복구됐다.

> Default -g walks frame pointers, so any code built with omit-frame-pointer breaks the chain and frames disappear. The fixes are: rebuild with frame pointers, which is the cheapest and why distros like Ubuntu and Fedora turned them on by default; use --call-graph dwarf, which copies a chunk of user stack per sample and unwinds offline with CFI, at a big cost in data size; or use hardware branch records like LBR on Intel or BRBE on newer Arm cores. Frames removed by tail-call optimization aren't on the stack at all, so no unwinder will show them.

**Q.** "How do you profile on an embedded target that has no debug symbols?"

**A.** 타깃에서는 기록만 한다(`perf record -g`, 필요하면 `perf archive`). perf.data에는 DSO마다 build-id가 들어 있으니, 호스트에서 같은 빌드의 unstripped 산출물(Yocto의 `-dbg` 패키지, Buildroot의 staging)을 `--symfs`로 주거나 build-id 캐시에 넣고 `-k vmlinux`로 커널 심볼을 준다. build-id가 맞아야 채택되므로 릴리스마다 디버그 산출물을 보관하는 것이 핵심이다. 실제로 게스트에서 찍은 데이터를 다른 버전 perf가 있는 호스트에서 이렇게 복원해 봤다.

> Record on the target, analyze on the host. perf.data stores the build-id of every binary that appears in samples, so on the build machine I point --symfs at the unstripped sysroot or add the debug binaries to the build-id cache, and pass -k with the matching vmlinux. perf only accepts files whose build-id matches, so the real process requirement is archiving debug artifacts for every release. It also means I can use a newer perf on the host than the one on the target.

**Q.** "Is the workload compute-bound or memory-bound — how would you tell with perf?"

**A.** IPC와 캐시 미스(MPKI), 백엔드 스톨을 본다. IPC가 낮고(0.5 근처) LLC miss가 많고 STALL_BACKEND 비율이 높으면 memory-bound다. 확인 실험으로 데이터 크기·순회 순서·타일 크기를 바꿔 miss와 시간이 같이 움직이는지 본다. 그리고 roofline으로 연산 강도 대비 달성 성능을 놓고, 대역폭은 SoC의 DDR uncore PMU로 실측한다. memory-bound면 더 빠른 연산 유닛이 아니라 데이터 재사용·양자화·zero-copy가 해법이다.

> I look at IPC, cache misses per thousand instructions, and backend stall cycles. Low IPC with high last-level misses and lots of backend stalls means memory-bound. Then I confirm it by changing the working-set size or traversal order and checking that misses and time move together. Putting it on a roofline — arithmetic intensity versus achieved throughput, with bandwidth measured from the SoC's DDR PMU — tells me whether to work on data reuse and bytes moved, or on compute.

1. (개념) `perf_event_paranoid`가 2인 보드에서 일반 사용자가 `perf record -a`를 하면 어떻게 되나? root는? `kptr_restrict=2`라면 root의 커널 프로파일은 어떻게 보이나?
   정답/힌트: 일반 사용자는 `-a` 거부(paranoid ≥ 1), 커널 샘플도 제외(2). root·CAP_PERFMON은 허용. kptr_restrict=2면 kallsyms 주소가 0이라 커널 심볼이 안 풀리므로 `-k vmlinux`가 필요하다.

   정답/힌트: 소프트웨어 이벤트는 VM 호스트(PMU 없음)에서도 `sudo`로 동작한다. 첫 패스는 약 256개(4 KiB 페이지 기준, THP면 훨씬 적음), 두 번째는 0에 가깝다.
3. (측정) 예제 4의 `N`을 256(256 KiB, L2 안에 들어감)으로 줄여 row/col을 cachegrind로 다시 재 보라. miss rate 차이가 어떻게 변하나?
   정답/힌트: 작업 집합이 캐시에 들어가면 첫 반복 이후 열 우선도 미스가 거의 사라진다 — "캐시 친화도"는 데이터 크기와 함께 말해야 한다.
4. (관찰) 게스트에서 `perf record -F 999 -g -- ./deep_fp 30`과 `--call-graph dwarf,4096`을 비교하라. 4096바이트 스택 복사로도 `_start`까지 보이는가? perf.data 크기는?
   정답/힌트: 이 프로그램은 스택이 얕아서 보일 가능성이 높다. 깊은 재귀 함수를 추가해 잘림을 재현해 보라.
5. (flame graph) 6절의 `collapse.py`를 고쳐 커널 프레임(심볼 뒤 dso가 `[kernel.kallsyms]`)에 `_[k]` 접미사를 붙이고, `flamesvg.py`에서 접미사가 있으면 다른 색을 쓰게 하라.
   정답/힌트: 원조 `stackcollapse-perf.pl --kernel`이 같은 일을 한다. 정규식으로 `(\[kernel.kallsyms\])`를 먼저 검사하면 된다.
6. (sched) `compete.c`에서 한 스레드만 `nice(10)`을 호출하게 바꾸고 `perf sched timehist`로 run time 비율을 재라.
   정답/힌트: nice 10은 가중치가 약 1/9.3이라 CPU 몫이 약 10:90 근처로 기운다(F1의 가중치 표). 교대 주기는 여전히 tick 경계를 따른다.
7. (크로스) 게스트에서 `perf archive fp.data`로 만든 tar를 호스트에서 `~/.debug`가 아닌 별도 디렉터리에 풀고 `perf --buildid-dir <dir> report`로 열어 보라.
   정답/힌트: `perf archive`는 build-id 캐시의 해당 파일들을 묶는다(커널은 kallsyms 사본). 주의: 이 lab의 6.18.55 perf 빌드에서는 `perf archive`가 "Did you mean this? archive"로 실패했다 — `archive`는 C 명령이 아니라 `perf-archive` 셸 스크립트이고, 그 스크립트가 perf의 libexec 디렉터리(`perf-core`)에 설치되지 않았기 때문이다. 직접 해 보려면 `tools/perf/perf-archive.sh`를 복사해 실행하거나, `perf buildid-list`로 목록을 뽑아 해당 파일을 tar로 묶는다.

## 16. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| PMU | Performance Monitoring Unit | CPU 안의 이벤트 카운터 블록 (ARM: PMUv3) |
| perf_events | 커널 성능 이벤트 서브시스템 | `perf_event_open(2)` 하나로 HW/SW/tracepoint 이벤트를 다룸 |
| counting / sampling | 세기 / 표본 추출 | 합계만 vs overflow마다 PC·스택 기록 |
| period / frequency | `-c` / `-F` | 몇 이벤트마다 샘플 vs 초당 몇 샘플 |
| multiplexing | 카운터 시간 분할 | 이벤트 > 카운터일 때 회전, `(xx%)`로 스케일링 |
| IPC | instructions per cycle | 코어 효율의 1차 지표 |
| skid | 샘플 PC 밀림 | overflow와 인터럽트 사이에 실행된 명령만큼 PC가 늦게 찍힘 |
| frame pointer (x29) | 프레임 체인 레지스터 | AArch64 프레임 레코드 {이전 x29, x30(LR)} 연결 리스트 |
| DWARF CFI | Call Frame Information | `.eh_frame`에 든 "이 PC에서 리턴 주소는 어디" 표 |
| LBR / BRBE | 분기 기록 하드웨어 | Intel Last Branch Record / Arm Branch Record Buffer Extension |
| SPE | Statistical Profiling Extension | arm64의 정밀 샘플링(데이터 주소·지연), `perf mem`의 기반 |
| build-id | ELF 해시 노트 | 기록 파일과 심볼 파일을 정확히 짝짓는 열쇠 |
| `--symfs` | 심볼 루트 디렉터리 | 타깃 rootfs 구조의 디버그 산출물을 가리킴 |
| flame graph | 스택 시각화 | x=샘플 비율(시간 순서 아님), y=스택 깊이 |
| folded stack | 접힌 스택 형식 | `a;b;c 개수` 한 줄 — 도구 간 공용 형식 |
| off-CPU | CPU 밖 시간 | 잠들어 기다린 시간의 분석 (sched_switch 기반) |
| uncore PMU | 코어 밖 카운터 | DDR 컨트롤러·인터커넥트·NPU의 성능 카운터 |
| roofline | 성능 상한 모델 | min(피크 연산, 연산 강도 × 대역폭) |
| TCG | Tiny Code Generator | QEMU의 동적 번역 에뮬레이터 — 캐시·분기 예측기 없음 |

## 17. 요약 & 체크리스트

perf는 커널의 perf_events 서브시스템을 쓰는 도구다. 하드웨어 PMU·소프트웨어·tracepoint·동적 probe 이벤트를 `perf_event_open` 하나로 열어, `perf stat`은 세고(counting) `perf record`는 overflow 인터럽트로 표본을 뜬다(sampling). 숫자를 믿기 전에 카운터가 진짜인지(이 노트의 TCG는 cycles만, VM 호스트는 PMU 없음), multiplexing으로 외삽된 값인지, 샘플 수가 충분한지 확인한다. 콜스택은 frame pointer가 가장 싸고, 없으면 dwarf로 보완하며, 꼬리 호출은 원래 보이지 않는다. flame graph는 `perf script → folded → SVG`의 단순한 파이프라인이고, on-CPU만 보인다는 한계가 있어 off-CPU·스케줄링(`perf sched`)과 짝지어 본다. 임베디드에서는 타깃에서 기록하고 build-id로 호스트의 디버그 산출물과 연결해 분석한다. 그리고 AI 추론 같은 루프는 IPC·cache-miss·roofline으로 compute-bound/memory-bound를 먼저 가른다.

- [ ] perf_events의 이벤트 4종과 `perf_event_open`의 인자(attr, pid, cpu, group_fd)를 설명할 수 있다
- [ ] counting과 sampling의 차이, `-F`와 `-c`의 차이를 설명할 수 있다
- [ ] `perf_event_paranoid` 값별 의미와 `kptr_restrict`가 커널 심볼에 주는 영향을 말할 수 있다
- [ ] ARM PMUv3의 cycle counter + 범용 카운터 구조와 대표 이벤트 번호(0x03, 0x08, 0x10, 0x11)를 말할 수 있다
- [ ] 새 플랫폼에서 하드웨어 카운터가 진짜로 동작하는지 검증할 수 있다
- [ ] multiplexing 스케일링 `(xx%)`의 의미와 그룹으로 피하는 법을 설명할 수 있다
- [ ] `perf record -g`와 `--call-graph dwarf`의 비용·한계를 비교하고, 깨진 스택의 원인을 진단할 수 있다
- [ ] `perf report --children/--no-children`, `perf annotate`를 읽고 skid를 감안해 해석할 수 있다
- [ ] `perf script` 출력에서 flame graph를 직접 만들 수 있다
- [ ] `perf sched timehist/latency`로 scheduling delay를 읽을 수 있다
- [ ] 타깃에서 기록하고 호스트에서 `--symfs`, `-k vmlinux`, build-id 캐시로 분석할 수 있다
- [ ] IPC·cache-miss·roofline으로 memory-bound 여부를 판단하는 절차를 말할 수 있다
