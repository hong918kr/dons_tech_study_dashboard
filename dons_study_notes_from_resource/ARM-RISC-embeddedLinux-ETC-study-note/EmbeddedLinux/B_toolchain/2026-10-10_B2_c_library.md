## 0. 큰 그림 — libc는 앱과 커널 사이의 "번역층"

Don이 SSD 펌웨어에서 `printf`를 쓸 때를 떠올려 보자. 대개 **newlib**(또는 newlib-nano)이 링크되고, `printf`는 결국 `_write()`라는 **stub 함수**를 부른다. 그 stub은 Don(또는 BSP)이 직접 써서 UART 레지스터에 바이트를 밀어 넣는다. `malloc`은 `_sbrk()` stub을 불러 링커 스크립트가 정한 heap 영역을 잘라 준다. 즉 **newlib의 아래쪽 끝은 "Don이 채우는 함수 몇 개"**다.

Linux에서는 그 아래쪽 끝이 **커널**이다. C 라이브러리(**libc**)는 `printf`의 포맷팅·버퍼링을 한 뒤 `write` **syscall**로 커널에 넘기고, `malloc`은 `brk`/`mmap` syscall로 커널에게 페이지를 받는다. 그리고 Linux libc는 newlib에는 없는 일을 잔뜩 한다: 스레드(**NPTL**), 동적 라이브러리 로딩(**ld.so**), 사용자·호스트 이름 조회(**NSS**, DNS resolver), 로케일·문자 변환(**locale**, **iconv**), 그리고 프로그램 시작·종료 처리(**crt1.o**, `__libc_start_main`, `atexit`).

Embedded Linux 엔지니어가 libc를 신경 써야 하는 장면은 이렇다.

- **이미지 크기**: 32 MB SPI-NOR에 rootfs를 넣어야 하는 게이트웨이라면 glibc(공유 라이브러리만 약 2 MB, 로케일·gconv까지 넣으면 훨씬 큼) 대신 musl(약 0.8 MB 파일 하나)로 가는 결정이 바로 나온다 (§3, §9).
- **호환성**: Jetson이나 i.MX8의 GPU/NPU 드라이버 유저 공간 라이브러리는 대부분 **glibc용 바이너리**로만 온다. musl rootfs에서는 붙지 않는다 (§9).
- **배포 사고**: 개발 PC(Ubuntu 최신)에서 빌드한 진단 툴을 보드에 `scp`했더니 `version 'GLIBC_2.38' not found`. 원인은 **심볼 버전** (§7).
- **성능·안정성**: musl로 옮겼더니 멀티스레드 로깅 데몬이 느려졌다(malloc), 또는 스레드 안의 깊은 재귀가 segfault 났다(기본 스레드 스택 128 KiB) (§4).

## 1. libc가 실제로 하는 일

"C 라이브러리"라고 하면 `strlen`, `printf` 같은 함수 모음을 떠올리기 쉽다. 그건 일부일 뿐이고, Linux에서 libc는 **POSIX API를 커널 syscall 위에 구현한 런타임**이다. 하나씩 본다.

### 1.1 syscall 래퍼와 errno

**직관**: 커널은 C 함수가 아니다. 커널에 일을 시키려면 레지스터에 번호와 인자를 넣고 `svc #0` 예외를 일으켜야 한다(A1). libc의 `close()`, `read()` 같은 함수는 이 일을 대신해 주는 **얇은 래퍼**다.

**정의**: arm64에서 커널은 결과를 `x0`에 돌려주는데, 실패하면 **음수 에러 번호**(`-EBADF` = -9 같은)를 준다. POSIX는 "실패하면 -1을 반환하고 원인은 `errno`에"라는 규약이다. 이 둘을 맞춰 주는 게 libc 래퍼다: 반환값이 -4095~-1 범위면 `errno = -반환값`, 반환은 -1로 바꾼다. 그리고 `errno`는 전역 변수가 아니라 **스레드마다 따로 있는 변수**(TLS, thread-local storage)다. glibc 헤더는 `errno`를 `(*__errno_location ())`로 정의한다.

무엇을 확인하나: 인라인 `svc #0`으로 커널을 직접 부른 결과(-9)와, libc `close()`·`syscall()`의 결과(-1 + errno 9)를 비교하고, `errno` 주소가 스레드마다 다른지 본다.

```c
/* wrap: libc syscall 래퍼가 하는 일 — 커널의 -errno를 (-1, errno)로 바꾸고, errno는 스레드마다 따로 */
#define _GNU_SOURCE
#include <errno.h>
#include <pthread.h>
#include <stdio.h>
#include <string.h>
#include <sys/syscall.h>
#include <unistd.h>

static long raw_close(long fd)              /* libc 없이 커널에 직접: x8=번호, x0=인자 */
{
    register long x8 __asm__("x8") = __NR_close;
    register long x0 __asm__("x0") = fd;
    __asm__ volatile("svc #0" : "+r"(x0) : "r"(x8) : "memory");
    return x0;
}

static void *peek(void *arg)
{
    (void)arg;
    printf("thread: &errno = %p\n", (void *)&errno);
    return NULL;
}

int main(void)
{
    long r = raw_close(-1);
    printf("raw svc     : return %ld  (커널 원본 = -EBADF, EBADF=%d)\n", r, EBADF);
    errno = 0;
    int r2 = close(-1);
    printf("libc close(): return %d, errno=%d (%s)\n", r2, errno, strerror(errno));
    errno = 0;
    long r3 = syscall(SYS_close, -1);
    printf("syscall()   : return %ld, errno=%d\n", r3, errno);
    printf("__NR_close = %d (asm-generic/unistd.h)\n", __NR_close);

    printf("main  : &errno = %p\n", (void *)&errno);
    pthread_t t;
    if (pthread_create(&t, NULL, peek, NULL) != 0) { perror("pthread_create"); return 1; }
    pthread_join(t, NULL);
    return 0;
}
```

```sh
musl-gcc -O2 -Wall -Wextra wrap.c -o wrap_musl && ./wrap_musl
```

Don 경험과 연결: newlib에서 `errno`는 `struct _reent` 안에 있고, RTOS 태스크마다 `_impure_ptr`를 바꿔 주는 방식으로 "태스크별 errno"를 흉내 냈다. Linux libc는 같은 목적을 CPU의 스레드 포인터 레지스터(arm64 `TPIDR_EL0`)가 가리키는 TLS 블록으로 해결한다.

함정: 성공한 호출은 `errno`를 지우지 않는다. "반환값이 -1일 때만 `errno`를 본다"가 규칙이다 (A1 §12).

### 1.2 stdio 버퍼링 — `printf` 한 번 ≠ `write` 한 번

**직관**: newlib에서 UART로 `printf`하면 바로 나가는 경우가 많았다. Linux libc의 `stdout`은 **버퍼**를 가진다. 출력 대상이 터미널이면 **줄 단위(line buffered)**, 파일·파이프면 **블록 단위(fully buffered)**로 모았다가 `write` syscall을 한 번에 한다. 블록 크기는 libc마다 다르다.

무엇을 확인하나: 같은 `printf` 1000줄(47,000바이트)이 glibc와 musl에서, 파일과 터미널(pty)로 보낼 때 각각 `write` syscall 몇 번이 되는지 센다.

```c
/* stdiobuf: 같은 printf 1000줄이 write() 몇 번이 되는지 — 출력 대상과 libc에 따라 다르다 */
#include <stdio.h>

int main(void)
{
    for (int i = 0; i < 1000; i++)
        printf("imu sample %4d: ax=%6d ay=%6d az=%6d\n", i, i * 3, -i, 16384);
    return 0;
}
```

```sh
gcc -O2 -Wall -Wextra stdiobuf.c -o sb_glibc && musl-gcc -O2 -Wall -Wextra stdiobuf.c -o sb_musl
for b in sb_glibc sb_musl; do
  strace -e trace=write,writev -o w.txt ./$b > out.txt; grep -cE "^(write|writev)" w.txt     # 파일로
  script -qc "strace -e trace=write,writev -o w2.txt ./$b" /dev/null > /dev/null
  grep -cE "^(write|writev)" w2.txt                                                      # pty로
done
```


출력에서 볼 것: 파일로 보낼 때 glibc는 4096바이트(파일의 `st_blksize`) 단위로 12번, musl은 1024바이트 버퍼 + 새 데이터를 `writev`로 묶어 47번 쓴다. 터미널이면 둘 다 줄마다 1000번이다. musl은 첫 출력 때 `ioctl(TIOCGWINSZ)`로 "터미널인가"를 확인하고 그때까지는 줄 단위로 동작해서 첫 줄은 따로 나갔다.

함정: 센서 로그를 파이프(`./daemon | logger`)로 넘기면 블록 버퍼링 때문에 로그가 몇 KB씩 늦게 나온다. `setvbuf(stdout, NULL, _IOLBF, 0)` 또는 `fflush`, 아니면 `stderr`(기본 unbuffered)를 쓴다. 그리고 `fork()` 전에 `fflush`하지 않으면 버퍼 내용이 두 번 출력된다(A2).

### 1.3 malloc — 커널에서 페이지를 받아 잘게 나눠 주는 할당기

newlib의 `malloc`은 `_sbrk`로 고정 heap을 늘려 가는 단순한 할당기였다. Linux libc의 `malloc`도 원리는 같지만 커널에서 메모리를 받는 방법이 두 가지다: 작은 할당은 `brk`(데이터 세그먼트 끝을 올림)로 늘린 heap에서, 큰 할당(glibc 기본 128 KiB 이상)은 `mmap`으로 따로 받는다(A5).

- **glibc malloc (ptmalloc2)**: 스레드별 **arena**와 **tcache**(스레드별 작은 캐시)를 둬서 스레드끼리 잠금 경쟁이 적다. 빠르지만 메모리를 넉넉히 쓰고 단편화가 생길 수 있다. `mallopt`, `GLIBC_TUNABLES`로 조정한다.
- **musl malloc (mallocng, 1.2.1부터)**: 메모리 효율·보안(메타데이터 분리, 해제 검증)을 우선한 설계라 단일 스레드에서도 느리고, 잠금이 사실상 전역이라 스레드가 늘면 더 느려진다. 그래서 musl 기반 이미지에서 할당이 많은 서비스는 mimalloc·jemalloc 같은 할당기를 따로 링크하기도 한다.

§4.1에서 직접 잰다.

### 1.4 pthread와 NPTL

**NPTL**(Native POSIX Thread Library)은 glibc의 pthread 구현이다. 스레드 하나 = 커널 태스크 하나(1:1 모델)이고, `pthread_create`는 스택을 `mmap`으로 만들고 `clone()` syscall을 부른다. 뮤텍스는 경쟁이 없으면 유저 공간 원자 연산만으로 끝나고, 경쟁이 생길 때만 `futex` syscall로 커널에서 잠든다(A8). glibc 2.34부터는 `libpthread`가 `libc.so.6` 안으로 합쳐졌다. musl도 같은 1:1 모델이고 처음부터 libc 하나에 다 들어 있다. 차이는 **기본 스레드 스택 크기**(§4.2)와 세부 기능(예: 일부 `_np` 확장 함수 지원 여부)이다.

### 1.5 locale·iconv, NSS·DNS resolver — glibc가 커지는 이유

- **locale**: 숫자·날짜 포맷, 문자 분류(`isalpha`), 멀티바이트 변환을 언어별로 바꾸는 기능. glibc는 로케일 데이터를 `/usr/lib/locale/locale-archive`(이 VM에서 3 MB)에 두고, 문자셋 변환(`iconv`)은 `gconv` 모듈(이 VM의 `/usr/lib/aarch64-linux-gnu/gconv`에 256개 파일, 약 20 MB)을 **dlopen**으로 불러 쓴다. musl은 사실상 C와 UTF-8만 지원하고 iconv 변환표를 libc 안에 넣었다.
- **NSS**(Name Service Switch): `getpwnam("root")`, `getaddrinfo("imu-gw")` 같은 "이름 → 정보" 조회를 `/etc/nsswitch.conf`가 정한 순서(files, dns, systemd, ldap …)대로 **플러그인 `.so`를 dlopen**해서 처리하는 glibc 구조다. 유연하지만 정적 링크와 궁합이 나쁘다(§8). musl은 NSS가 없고 `/etc/passwd`, `/etc/hosts`, DNS만 직접 읽는다.
- **DNS resolver**: `getaddrinfo` 안의 DNS 클라이언트. musl은 여러 네임서버에 **동시에** 질의하는 등 동작이 다르고, TCP fallback은 1.2.4에서야 들어왔다. 이 차이로 "glibc에선 되는데 Alpine 컨테이너에선 이름이 안 풀린다" 같은 이슈가 생긴다.

### 1.6 시작 코드와 `atexit`

newlib 프로젝트에서 `crt0.s`(또는 `startup_stm32xxx.s`)가 `.data` 복사, `.bss` 0 채우기, `__libc_init_array()` 호출, 그리고 `main` 호출을 했다. Linux에서는 `.data`/`.bss` 준비를 **커널의 ELF 로더**(와 동적 로더)가 해 주고, libc의 시작 코드는 `crt1.o`(PIE면 `Scrt1.o`)의 `_start` → `__libc_start_main`이다. 이 함수가 TLS·스택 가드·`init_array`(C++ 전역 생성자, `__attribute__((constructor))`)를 처리하고 `main`을 부르며, `main`이 돌아오면 `exit()`이 `atexit` 핸들러 → `fini_array` → stdio flush → `exit_group` syscall 순서로 정리한다. §5에서 gdb로 따라간다.

### 1.7 newlib과 한눈에 비교

| 항목 | newlib (bare-metal) | glibc / musl (Linux) |
|---|---|---|
| 아래쪽 끝 | Don이 쓴 stub (`_write`, `_sbrk`, `_read`) | 커널 syscall (`write`, `brk`, `mmap`) |
| errno | `struct _reent` (태스크별 reent 포인터) | TLS 변수, `__errno_location()` |
| 메모리 | 링커 스크립트가 정한 고정 heap | `brk` heap + `mmap`, 가상 메모리 |
| 스레드 | 없음 (RTOS가 제공) | pthread = 커널 태스크 1:1, futex |
| 시작 코드 | crt0: `.data` 복사·`.bss` 클리어 직접 | 커널이 ELF 매핑, crt1.o `_start` → `__libc_start_main` |
| 동적 로딩 | 없음 (이미지 1개) | `ld-linux` / `ld-musl`이 `.so`를 붙임 |
| 이름 조회·로케일 | 없음 | NSS·resolver·locale·iconv |
| 라이선스 | BSD 계열 여러 개 | glibc LGPL-2.1+, musl MIT |

### 2.2 지금 어떤 libc인가 확인하기

무엇을 확인하나: 컴파일 시점(`__GLIBC__` 매크로)과 실행 시점(`gnu_get_libc_version()`)에 libc 종류·버전을 알아내는 방법.

```c
/* which: 지금 이 바이너리가 어떤 libc로 빌드·실행되는지 확인하는 방법 */
#include <stdio.h>
#ifdef __GLIBC__
#include <gnu/libc-version.h>
#endif

int main(void)
{
#ifdef __GLIBC__
    printf("compile-time: __GLIBC__=%d __GLIBC_MINOR__=%d\n", __GLIBC__, __GLIBC_MINOR__);
    printf("run-time    : gnu_get_libc_version() = %s\n", gnu_get_libc_version());
#else
    printf("compile-time: __GLIBC__ not defined (musl은 일부러 버전 매크로를 두지 않는다)\n");
#endif
    return 0;
}
```

```sh
gcc -O2 -Wall -Wextra which.c -o which_glibc && musl-gcc -O2 -Wall -Wextra which.c -o which_musl
./which_glibc; ./which_musl
getconf GNU_LIBC_VERSION; getconf GNU_LIBPTHREAD_VERSION; ldd --version | head -1
/lib/aarch64-linux-gnu/libc.so.6 | head -3       # glibc의 libc.so.6은 실행하면 버전을 말한다
/lib/ld-musl-aarch64.so.1 2>&1 | head -4          # musl 로더도 마찬가지
```

### 2.3 musl-gcc는 무엇인가

Ubuntu의 `musl-tools`가 주는 `musl-gcc`는 별도 컴파일러가 아니라 **시스템 gcc에 specs 파일을 끼워 헤더·crt·libc 경로만 musl 쪽으로 바꾸는 래퍼 스크립트**다.

```sh
cat /usr/bin/musl-gcc
ls /usr/lib/aarch64-linux-musl
```

```text
#!/bin/sh
exec "${REALGCC:-aarch64-linux-gnu-gcc}" "$@" -specs "/usr/lib/aarch64-linux-musl/musl-gcc.specs"

crt1.o
crti.o
crtn.o
libc.a
libc.so
libdl.a
libm.a
libpthread.a
libresolv.a
```

`libm.a`, `libpthread.a` 등이 있지만 musl에서는 전부 빈 껍데기이고 실제 코드는 `libc.a`/`libc.so` 하나에 들어 있다. C++이나 다른 라이브러리(OpenSSL 등)까지 musl로 빌드하려면 이 래퍼로는 부족하고, musl 기반 크로스 툴체인(Buildroot·Yocto가 만든 것, musl.cc 계열, `aarch64-linux-musl-gcc`)을 쓴다 (B1, B5).

줄별로 읽는 법:

1. `faccessat("/etc/ld.so.preload")` ~ `close(3)`: **동적 로더**가 일하는 구간. preload 목록 확인, `/etc/ld.so.cache`(라이브러리 이름 → 경로 색인)를 mmap해서 `libc.so.6` 위치를 찾고, libc를 열어 ELF 헤더 832바이트를 읽은 뒤 세그먼트별로 `mmap`한다. 마지막 `PROT_EXEC|0x10`의 `0x10`은 arm64의 `PROT_BTI`(Branch Target Identification 보호)다.
2. `set_tid_address`, `set_robust_list`, `rseq`: **NPTL 초기화**. 스레드 종료 시 futex를 깨울 주소, 뮤텍스 소유자가 죽었을 때를 위한 robust list, restartable sequences 등록.
3. `mprotect(..., PROT_READ)`: **RELRO** — 재배치가 끝난 GOT 등을 읽기 전용으로 잠근다(B3).
4. `prlimit64(RLIMIT_STACK)`: glibc가 **기본 스레드 스택 크기**를 정하려고 스택 rlimit을 읽는다 (§4.2의 8 MiB가 여기서 온다).
5. `getrandom(8 bytes)`: malloc 내부 보호용 난수 키 초기화(glibc `malloc.c`의 tcache key로 알고 있다).
6. `fstat(1)`, `ioctl(1, TCGETS2)`: stdio가 stdout이 터미널인지 확인해 버퍼링 방식을 고른다 (§1.2).
7. `brk`: `printf`가 stdout 버퍼를 `malloc`하면서 heap이 처음 생긴다.

musl 정적 hello는 `execve` → `set_tid_address` → `ioctl(TIOCGWINSZ)` → `writev` → `exit_group`이 전부다. 로더 단계도 없고, robust list·rseq도 필요해질 때까지 미룬다.

### 3.3 시작~종료 시간

무엇을 확인하나: 프로그램을 2000번 `posix_spawn` → `waitpid`해서 1회 평균 시간(fork·exec·로딩·종료 포함)을 잰다. 셸 스크립트에서 작은 툴을 수천 번 부르거나, 이벤트마다 helper를 실행하는 장비에서 체감되는 숫자다.

```c
/* spawnbench: 프로그램을 N번 posix_spawn → waitpid 해서 1회 평균 시작~종료 시간을 잰다 */
#include <spawn.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <time.h>
#include <fcntl.h>
#include <unistd.h>

extern char **environ;

static double now_us(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec * 1e6 + ts.tv_nsec / 1e3;
}

int main(int argc, char **argv)
{
    if (argc < 3) { fprintf(stderr, "usage: %s N prog\n", argv[0]); exit(1); }
    int n = atoi(argv[1]);
    posix_spawn_file_actions_t fa;
    posix_spawn_file_actions_init(&fa);
    posix_spawn_file_actions_addopen(&fa, 1, "/dev/null", O_WRONLY, 0);
    char *args[] = { argv[2], NULL };
    double t0 = now_us();
    for (int i = 0; i < n; i++) {
        pid_t pid;
        int st;
        if (posix_spawn(&pid, argv[2], &fa, NULL, args, environ) != 0) {
            perror("posix_spawn"); exit(1);
        }
        if (waitpid(pid, &st, 0) < 0) { perror("waitpid"); exit(1); }
    }
    double t1 = now_us();
    printf("%-22s %8.1f us/run\n", argv[2], (t1 - t0) / n);
    return 0;
}
```

## 4. 측정 2 — 런타임 성격: malloc, 스레드 스택, vDSO

### 4.1 malloc 마이크로벤치

무엇을 확인하나: 16~255바이트 블록을 무작위로 할당·해제하는 루프(스레드당 200만 회)를 1개, 4개 스레드에서 돌려 glibc와 musl의 할당기 비용을 비교한다.

```c
/* mallocbench: 작은 블록 malloc/free를 T개 스레드에서 반복 — libc별 할당기 비용 비교 */
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define ITERS 2000000
#define SLOTS 256

static void *worker(void *arg)
{
    unsigned seed = (unsigned)(unsigned long)arg;
    void *slot[SLOTS] = { 0 };
    for (long i = 0; i < ITERS; i++) {
        seed = seed * 1103515245u + 12345u;
        int k = (seed >> 8) % SLOTS;
        free(slot[k]);                       /* free(NULL)은 아무 일도 안 한다 */
        slot[k] = malloc(16 + (seed >> 20) % 240);   /* 16~255 바이트 */
        if (!slot[k]) { perror("malloc"); exit(1); }
        *(char *)slot[k] = (char)i;
    }
    for (int k = 0; k < SLOTS; k++) free(slot[k]);
    return NULL;
}

int main(int argc, char **argv)
{
    int t = argc > 1 ? atoi(argv[1]) : 1;
    pthread_t th[16];
    struct timespec a, b;
    if (t < 1 || t > 16) { fprintf(stderr, "threads 1..16\n"); exit(1); }
    clock_gettime(CLOCK_MONOTONIC, &a);
    for (int i = 0; i < t; i++)
        if (pthread_create(&th[i], NULL, worker, (void *)(long)(i + 1)) != 0) {
            fprintf(stderr, "pthread_create failed\n"); exit(1);
        }
    for (int i = 0; i < t; i++) pthread_join(th[i], NULL);
    clock_gettime(CLOCK_MONOTONIC, &b);
    double ns = ((b.tv_sec - a.tv_sec) * 1e9 + (b.tv_nsec - a.tv_nsec)) / ((double)ITERS * t);
    printf("threads=%d  total ops=%ld  %.1f ns/op (wall)\n", t, (long)ITERS * t, ns);
    return 0;
}
```

### 4.2 기본 스레드 스택 크기 — 8 MiB vs 128 KiB

**직관**: RTOS에서 태스크를 만들 때 스택 크기를 반드시 지정했다. pthread는 지정하지 않으면 libc 기본값을 쓰는데, 그 기본값이 glibc와 musl에서 **60배 이상** 다르다. glibc는 `ulimit -s`(RLIMIT_STACK, 보통 8 MiB) 값을 쓰고, musl은 128 KiB 고정이다.

무엇을 확인하나: 스레드 안에서 프레임당 약 1 KiB를 쓰는 재귀를 N단계 하고, 기본 스택 크기를 출력한다. 두 번째 인자를 주면 스택 크기를 명시한다.

```c
/* stack: 기본 스레드 스택 크기를 출력하고, 스레드 안에서 깊은 재귀를 해 본다 */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static int depth_target;

static int recurse(int n)
{
    volatile char pad[1024];                 /* 프레임당 약 1 KiB 스택 사용 */
    memset((char *)pad, n & 0xff, sizeof pad);
    if (n >= depth_target) return pad[0];
    return recurse(n + 1) + pad[1];
}

static void *worker(void *arg)
{
    (void)arg;
    pthread_attr_t a;
    size_t sz;
    if (pthread_getattr_np(pthread_self(), &a) != 0) { fprintf(stderr, "getattr\n"); exit(1); }
    pthread_attr_getstacksize(&a, &sz);
    pthread_attr_destroy(&a);
    printf("thread stack = %zu KiB, recursing %d frames (~%d KiB)\n",
           sz / 1024, depth_target, depth_target);
    fflush(stdout);
    printf("done: %d\n", recurse(0) & 1);
    return NULL;
}

int main(int argc, char **argv)
{
    depth_target = argc > 1 ? atoi(argv[1]) : 200;
    pthread_t t;
    pthread_attr_t attr;
    pthread_attr_init(&attr);
    if (argc > 2)                            /* 두 번째 인자: 스택 크기를 KiB로 명시 */
        pthread_attr_setstacksize(&attr, (size_t)atoi(argv[2]) * 1024);
    if (pthread_create(&t, &attr, worker, NULL) != 0) { fprintf(stderr, "create\n"); exit(1); }
    pthread_join(t, NULL);
    return 0;
}
```

### 4.3 vDSO와 `clock_gettime` — 이 VM에서 발견한 차이

**vDSO**(virtual dynamic shared object)는 커널이 모든 프로세스에 자동으로 매핑해 주는 작은 공유 라이브러리다. `clock_gettime`, `gettimeofday` 같은 "읽기만 하는" 호출을 **커널 진입 없이** 유저 공간에서 처리한다(A1). libc는 시작할 때 auxv의 `AT_SYSINFO_EHDR`로 vDSO 위치를 받아 심볼을 찾아 둔다.

무엇을 확인하나: vDSO가 어디 매핑되는지, 그리고 `clock_gettime` 10만 번이 실제 syscall이 되는지를 glibc와 musl에서 본다.

```c
/* vdso: 커널이 모든 프로세스에 넣어 주는 vDSO 위치와, clock_gettime이 syscall 없이 끝나는지 확인 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/auxv.h>
#include <time.h>

int main(void)
{
    printf("AT_SYSINFO_EHDR = %#lx\n", getauxval(AT_SYSINFO_EHDR));
    FILE *f = fopen("/proc/self/maps", "r");
    if (!f) { perror("fopen"); exit(1); }
    char line[256];
    while (fgets(line, sizeof line, f))
        if (strstr(line, "[vdso]") || strstr(line, "[vvar")) fputs(line, stdout);
    fclose(f);

    struct timespec ts;
    long long sum = 0;
    for (int i = 0; i < 100000; i++) {      /* 10만 번 호출 */
        clock_gettime(CLOCK_MONOTONIC, &ts);
        sum += ts.tv_nsec & 1;
    }
    printf("done (%lld)\n", sum >= 0 ? 100000LL : 0LL);
    return 0;
}
```

```c
/* cgt: clock_gettime 1회 비용을 잰다 — vDSO 경로면 수십 ns, 진짜 syscall이면 수백 ns */
#include <stdio.h>
#include <time.h>

int main(void)
{
    struct timespec a, b, t;
    const int n = 1000000;
    clock_gettime(CLOCK_MONOTONIC, &a);
    for (int i = 0; i < n; i++)
        clock_gettime(CLOCK_MONOTONIC, &t);
    clock_gettime(CLOCK_MONOTONIC, &b);
    double ns = ((b.tv_sec - a.tv_sec) * 1e9 + (b.tv_nsec - a.tv_nsec)) / n;
    printf("clock_gettime: %.1f ns/call\n", ns);
    return 0;
}
```

### 5.2 코드로 확인 — constructor, atexit, destructor 순서

무엇을 확인하나: `main` 전후에 libc가 실행하는 사용자 코드의 순서.

```c
/* startup: main 전후에 libc가 무엇을 실행하는지 — constructor, atexit, destructor 순서 */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

static void __attribute__((constructor)) early(void)
{
    printf("[1] constructor: main 전에 실행 (init_array)\n");
}

static void __attribute__((destructor)) late(void)
{
    printf("[5] destructor: atexit 핸들러 다음 (fini_array)\n");
}

static void bye(void)
{
    printf("[4] atexit handler\n");
}

int main(void)
{
    printf("[2] main 진입, pid=%d\n", getpid());
    if (atexit(bye) != 0) { perror("atexit"); exit(1); }
    printf("[3] main 끝 → return 0 → exit(0)\n");
    return 0;
}
```

출력에서 볼 것: `starti`(첫 명령에서 멈춤)의 위치는 **프로그램이 아니라 `/lib/ld-linux-aarch64.so.1`의 `_start`**다. 커널이 먼저 로더를 실행한다는 증거다. `_start`라는 이름이 로더와 프로그램 두 곳에 있어서 "2 locations"가 나왔다. `bt`는 `_start` → `__libc_start_main_impl` → `__libc_start_call_main` → `main` 체인을 보여 준다. `[PAC]`는 arm64 Pointer Authentication으로 서명된 반환 주소라는 표시다. 같은 걸 musl로 하면 `#1 0x... in ?? () from /lib/ld-musl-aarch64.so.1`처럼 디버그 심볼 없는 한 단계로 끝난다(musl의 `__libc_start_main`이 libc.so 안에 있다).

## 6. 동적 로더 `ld-linux-aarch64.so.1`

### 6.1 PT_INTERP와 DT_NEEDED — 누가 로더를 고르고, 로더는 무엇을 붙이나

**정의**: 동적 링크된 ELF에는 두 가지 표시가 있다.

- **`PT_INTERP`** 프로그램 헤더: "이 프로그램은 이 로더로 실행하라"는 **절대 경로**. 커널의 ELF 로더(`fs/binfmt_elf.c`)가 이걸 보고 로더도 함께 매핑한 뒤 **로더의 진입점으로** 점프한다.

### 6.3 `ldd`는 왜 위험할 수 있나 — 그리고 대안

`ldd`는 ELF 분석기가 아니라 **셸 스크립트**다. 로더에 `LD_TRACE_LOADED_OBJECTS=1`을 주고 대상 프로그램을 **로딩**시켜서, 로더가 찍는 목록을 보여 준다.

```sh
file $(which ldd)
grep -nE "RTLDLIST=|LD_TRACE_LOADED_OBJECTS" $(which ldd) | head -3
```

```text
/usr/bin/ldd: Bourne-Again shell script, ASCII text executable
23:# variable LD_TRACE_LOADED_OBJECTS to a non-empty value.
29:RTLDLIST=/lib/ld-linux-aarch64.so.1
104:add_env="LD_TRACE_LOADED_OBJECTS=1 LD_WARN=$warn LD_BIND_NOW=$bind_now"
```

`ldd(1)` man 페이지는 "일부 버전의 ldd는 프로그램이 지정한 ELF 인터프리터를 직접 실행해 정보를 얻으려 할 수 있으니, 신뢰할 수 없는 실행 파일에 ldd를 쓰지 말라"고 경고한다. `PT_INTERP`가 공격자가 만든 파일을 가리키면 `ldd`만 했는데 그 코드가 실행된다는 뜻이다. 이 VM에서 직접 실험해 본다.

무엇을 확인하나: `PT_INTERP`를 가짜 로더로 바꾼 "트로이 목마" 바이너리를 만들고, 직접 실행할 때와 `ldd`할 때 각각 무슨 일이 생기는지 본다.

```c
/* evil_ld: 가짜 "동적 로더" — libc 없이 write/exit만 하는 _start (PT_INTERP로 지정할 대상) */
static const char msg[] = "!!! evil_ld executed instead of the real loader !!!\n";

static long sys3(long nr, long a, long b, long c)
{
    register long x8 __asm__("x8") = nr;
    register long x0 __asm__("x0") = a;
    register long x1 __asm__("x1") = b;
    register long x2 __asm__("x2") = c;
    __asm__ volatile("svc #0" : "+r"(x0) : "r"(x8), "r"(x1), "r"(x2) : "memory");
    return x0;
}

void _start(void)
{
    sys3(64, 1, (long)msg, sizeof msg - 1);   /* __NR_write = 64 */
    sys3(93, 0, 0, 0);                        /* __NR_exit  = 93 */
    for (;;) ;
}
```

## 7. 심볼 버저닝과 "version `GLIBC_2.38' not found"

### 7.1 직관 — 함수 이름에 "생년"이 붙어 있다

glibc는 하위 호환을 위해 **같은 이름의 함수를 여러 버전으로** 들고 다닌다. 예를 들어 어떤 함수의 동작을 바꿔야 하면 옛 버전(`foo@GLIBC_2.17`)은 그대로 두고 새 버전(`foo@@GLIBC_2.38`)을 추가한다. 새로 링크하는 프로그램은 새 버전에 묶이고, 옛 프로그램은 옛 버전을 계속 쓴다. 덕분에 **옛날에 빌드한 바이너리는 새 glibc에서 돈다**(하위 호환). 반대 방향은 보장되지 않는다: **새 glibc로 빌드한 바이너리는, 그 버전 태그가 없는 옛 glibc에서 실행 전에 거부된다.**

### 7.2 코드로 확인 — 평범한 코드가 요구하는 태그

무엇을 확인하나: 센서 주기를 파싱하는 평범한 코드가 어떤 `GLIBC_2.xx` 태그를 요구하는지 `objdump -T`로 본다.

```c
/* ver: 평범해 보이는 코드가 어떤 GLIBC_2.xx 버전 태그를 요구하게 되는지 본다 */
#include <stdio.h>

int main(int argc, char **argv)

    strlcpy(name, "imu0", sizeof name);                        /* glibc 2.38에서 추가 */
```

## 8. 정적 링크 — glibc에서의 함정

"정적 링크하면 libc 의존성이 사라지니 아무 보드에서나 돈다"는 musl에선 대체로 맞고, glibc에선 **반만 맞다**. glibc의 일부 기능은 정적 바이너리 안에서도 **실행 중에 공유 라이브러리를 dlopen**하기 때문이다: NSS(`getpwnam`, `getaddrinfo`의 일부 경로), `iconv`(gconv 모듈), `dlopen` 자체.

무엇을 확인하나: 사용자·호스트 이름 조회를 정적 링크할 때 링커 경고, 그리고 실제 실행 중에 무엇을 여는지.

```c
/* nss: 사용자 이름·호스트 이름 조회 — glibc에서는 NSS(동적 로딩)를 거치는 함수들 */
#include <netdb.h>
#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <arpa/inet.h>

int main(void)
{
    struct passwd *pw = getpwnam("root");
    if (!pw) { perror("getpwnam"); exit(1); }
    printf("root uid=%d home=%s\n", (int)pw->pw_uid, pw->pw_dir);

    struct addrinfo hints, *res;
    memset(&hints, 0, sizeof hints);
    hints.ai_family = AF_INET;
    int rc = getaddrinfo("localhost", NULL, &hints, &res);
    if (rc != 0) { fprintf(stderr, "getaddrinfo: %s\n", gai_strerror(rc)); exit(1); }
    char ip[INET_ADDRSTRLEN];
    inet_ntop(AF_INET, &((struct sockaddr_in *)res->ai_addr)->sin_addr, ip, sizeof ip);
    printf("localhost -> %s\n", ip);
    freeaddrinfo(res);
    return 0;
}
```

```text
openat(AT_FDCWD, "/usr/lib/aarch64-linux-gnu/libc.so.6", O_RDONLY|O_CLOEXEC) = 3
openat(AT_FDCWD, "/usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1", O_RDONLY|O_CLOEXEC) = 3
...
```

(이후 systemd userdb 조회용 `openat` 수십 줄은 생략했다. 마지막 줄은 `no_such_user: not found`.)

출력에서 볼 것: **"정적" 바이너리가 실행 중에 `libnss_systemd.so.2`를 열고, 그것이 의존하는 공유 `libc.so.6`과 로더까지 끌어왔다.** 한 프로세스 안에 정적으로 박힌 glibc 2.43과 공유 glibc가 함께 있는 셈이고, 두 버전이 다르면(다른 rootfs로 복사하면) 내부 자료구조가 안 맞아 크래시하거나 조회가 조용히 실패한다. musl 정적 바이너리는 NSS가 없어서 이 문제가 없는 대신, LDAP·systemd 사용자 같은 NSS 확장도 쓸 수 없다.

glibc 정적 링크의 다른 주의점:

- **LGPL**: glibc를 정적 링크한 바이너리를 배포하면, 사용자가 다른 glibc로 다시 링크할 수 있도록 오브젝트 파일 등을 제공해야 하는 의무가 생긴다(LGPL-2.1 6절). 상용 제품에서 법무 검토가 필요하다. musl(MIT)은 이 부담이 없다.
- **보안 업데이트**: libc 취약점이 고쳐져도 정적 바이너리는 다시 빌드해야 반영된다.
- **`dlopen`**: 정적 glibc 바이너리에서 `dlopen`은 같은 경고가 나오고, 같은 버전의 공유 glibc가 rootfs에 있어야 한다.

언제 정적 링크가 좋은가: initramfs 안의 복구 툴, 공장 테스트 툴처럼 "어떤 rootfs에서도 돌아야 하는" 작은 프로그램 — 이때는 **musl 정적**이 정답에 가깝다. BusyBox도 흔히 이렇게 빌드한다.

## 9. 제품에 쓸 libc 고르기

| 기준 | glibc | musl | uClibc-ng |
|---|---|---|---|
| rootfs의 libc 크기 | 약 2 MB(.so + 로더) + 로케일·gconv·NSS 모듈 선택 | 약 0.8 MB 파일 하나 | 설정에 따라 수백 KB 수준까지 |
| Yocto | 기본값 (`TCLIBC = "glibc"`) | `TCLIBC = "musl"`로 지원 | 공식 지원 아님 |
| Buildroot | 선택 가능 | 선택 가능 | 선택 가능 (noMMU 타깃이면 사실상 이것) |
| 대표 배포판 | Debian/Ubuntu, Jetson L4T, Raspberry Pi OS | Alpine, OpenWrt | 작은 라우터·레거시 장비 |
| 벤더 바이너리 (GPU·NPU·ISP·Wi-Fi 펌웨어 툴) | 대부분 glibc용으로만 배포 → 그대로 동작 | 대부분 실행 불가 (soname·심볼 버전·ABI 차이) | 거의 불가 |
| 멀티스레드 할당 성능 | 좋음 (§4.1) | 약함, 대체 할당기 고려 | 설정에 따라 |
| 정적 링크 | 함정 많음 (§8) | 깔끔 | 가능 |
| 라이선스 | LGPL-2.1+ | MIT | LGPL-2.1 |

결정 흐름:

1. **벤더 바이너리 블롭이 있는가?** Jetson의 CUDA/TensorRT, i.MX8의 GPU(Vivante)·NPU 런타임, TI의 TIDL 같은 것은 거의 항상 glibc 대상 바이너리다. 하나라도 있으면 **glibc**. 그리고 벤더 BSP가 쓰는 glibc 버전 이상이어야 한다(§7).
2. **플래시가 매우 작거나 대부분이 정적 툴인가?** SPI-NOR 수십 MB, 게이트웨이·센서 허브 → **musl**이 유리하다.
3. **MMU가 없는 코어에서 Linux를 돌리는가?** (Cortex-M7 같은 noMMU Linux) → **uClibc-ng**(또는 FDPIC 지원 툴체인).
4. 섞어 쓰기: rootfs는 glibc로 두고, 어떤 rootfs에서도 돌아야 하는 진단 툴만 **musl 정적**으로 빌드해 같이 배포하는 조합이 실무에서 자주 쓰인다.

musl 위에서 glibc 바이너리를 억지로 돌리는 호환층(`gcompat` 등)도 있지만 GPU·NPU 드라이버처럼 복잡한 라이브러리에는 기대하지 않는 게 좋다.

## 10. 커널 안에서는 무슨 일이 일어나나

### 10.1 libc가 경계다

libc와 커널 사이의 계약은 **세 가지 숫자 체계**뿐이다: syscall 번호, 인자·반환 레지스터 규약, 그리고 구조체 레이아웃(예: `struct stat`, `struct i2c_msg`). 이 계약은 커널 소스의 `include/uapi/`와 `arch/arm64/include/uapi/`에 정의되고, `make headers_install`로 뽑혀 배포판의 **`linux-libc-dev`** 패키지(`/usr/include/linux`, `/usr/include/asm-generic`, `/usr/include/asm`)가 된다. §1.1에서 `__NR_close 57`, `EBADF 9`, `linux/i2c-dev.h`가 모두 이 패키지에서 왔다.

그림 8 — libc는 유저 공간 쪽 경계다. 번호·에러 코드·구조체는 커널의 UAPI 헤더에서 오고, 커널 자신은 libc 없이 자체 `lib/` 함수로 산다. 드라이버가 돌려준 음수 에러 코드가 그대로 유저의 `errno`가 된다.

### 10.2 단계별로

1. 유저의 `close(fd)` → libc 래퍼가 `x8 = __NR_close`(57), `x0 = fd`를 넣고 `svc #0`.
2. EL1 예외 벡터 → `el0t_64_sync` → `el0_svc`(`arch/arm64/kernel/entry-common.c`) → `invoke_syscall`(`arch/arm64/kernel/syscall.c`)이 `sys_call_table[57]`을 호출 → `__arm64_sys_close` → `close_fd`.
3. 실패하면 커널 함수가 `-EBADF`를 반환하고, 그 값이 `x0`에 실린 채 `eret`으로 유저에 돌아온다.
4. libc가 `-4095 ≤ x0 ≤ -1`을 보고 TLS의 `errno`에 9를 쓰고 -1을 반환한다.

### 10.3 커널은 libc를 쓰지 않는다

커널은 glibc도 musl도 링크하지 않는다. Kbuild는 `-nostdinc`(시스템 헤더 금지)와 freestanding 모드로 컴파일하고, 필요한 함수는 직접 들고 있다: `lib/string.c`(`memcpy`, `strlen`, `strscpy`), `lib/vsprintf.c`(`snprintf`, `printk`의 포맷팅), `mm/slab`(`kmalloc` — `malloc`이 아니다). arm64는 `arch/arm64/lib/`에 최적화된 `memcpy` 등을 따로 둔다. 커널 코드에서 `printf`나 `errno`를 찾으면 없다 — 에러는 **음수 반환값**으로만 전달한다. 이 관례가 그대로 syscall 반환값이 되고, libc가 그걸 `errno`로 옮겨 담는 것이다. Don의 bare-metal 펌웨어가 newlib 없이 자체 `memcpy`·`uart_printf`를 들고 다니던 것과 같은 처지다.

### 10.4 드라이버를 쓸 때 다시 만나는 지점

- **에러 코드 규약**: 드라이버의 `.read`/`.write`/`.unlocked_ioctl`이 `-EINVAL`, `-EAGAIN`, `-ENOTTY`를 돌려주면 유저 앱은 `errno`로 그 값을 본다. "유저가 무엇을 보게 될지"를 생각하고 에러 코드를 고른다 (G4, G5).
- **UAPI 헤더 설계**: 드라이버가 새 `ioctl`이나 구조체를 유저에게 노출하면 `include/uapi/linux/xxx.h`에 넣어야 하고, 그 레이아웃은 **영원히 바뀌면 안 되는 ABI**가 된다. 32/64비트 겸용을 위해 `__u32`, `__u64` 고정 폭 타입과 명시적 패딩을 쓴다 (G5).
- **커널 lib/ 함수**: 드라이버 안에서 `strcpy` 대신 `strscpy`, `sprintf` 대신 `scnprintf`/`sysfs_emit`을 쓴다 — 커널판 "libc"의 관례다 (E4, G 모듈).
- **vDSO**: 커널이 유저 공간에 코드를 넣어 주는 유일한 일반 경로다. 시간 관련 드라이버(PTP 하드웨어 클록 등)를 볼 때 "어떤 시계는 vDSO로 읽히고 어떤 건 syscall이 필요한가"가 다시 나온다 (E 모듈).

커널 내부의 libc 대체물과 빌드 방식은 **E4**(커널 소스 구조·빌드)에서 더 본다.

## 11. Embedded 실무에서 다시 보기

### 11.1 "보드에서 툴이 안 돌아요" 트리아지 순서

예를 들어 센서 키트의 진단 툴 `imu_diag`를 개발 PC에서 크로스 빌드해 보드에 복사했는데 실행이 안 된다. 증상별로 이 순서로 본다.

```sh
# 1) 셸이 "not found"라고 하는데 파일은 있다 → 로더(PT_INTERP)가 보드에 없다
readelf -l imu_diag | grep interpreter          # 예: /lib/ld-linux-aarch64.so.1 인데 보드는 musl
# 2) 어떤 라이브러리를 요구하나 (ldd 대신 정적으로)
readelf -d imu_diag | grep NEEDED
# 3) 어떤 glibc 버전을 요구하나
objdump -T imu_diag | grep -o "GLIBC_2\.[0-9]*" | sort -t. -k2 -n -u | tail -1
# 4) 보드의 glibc는 몇인가 (보드에서)
/lib/aarch64-linux-gnu/libc.so.6 | head -1     # 또는 /lib/libc.so.6
```

1번의 "No such file or directory"는 Linux에서 가장 헷갈리는 메시지 중 하나다. 실행 파일은 있는데 **`PT_INTERP`의 로더가 없어서** `execve`가 `ENOENT`를 돌려준 것이다. musl 보드에 glibc 바이너리를 올렸거나, 32비트 ARM 로더(`/lib/ld-linux-armhf.so.3`)만 있는 보드에 64비트 바이너리를 올렸을 때 나온다.

### 11.2 벤더 SDK와 rootfs 버전 맞추기

Jetson L4T나 NXP Yocto BSP는 특정 glibc 버전으로 고정돼 있다. 팀 개발 환경은 **그 SDK의 sysroot로 빌드**하거나(B5), BSP와 같은 배포판 버전 컨테이너에서 빌드한다. CI에 "산출물의 최고 `GLIBC_2.xx` 태그가 타깃 버전 이하인지" 검사하는 스크립트를 넣으면 §7의 사고를 출고 전에 잡는다.

### 11.3 musl로 옮길 때 체크리스트

- 스레드를 만드는 모든 곳에 `pthread_attr_setstacksize` 명시 (§4.2), 또는 `-Wl,-z,stack-size=`.
- 할당이 많은 멀티스레드 서비스(로깅, 메시지 브로커)는 벤치마크 후 필요하면 대체 할당기 (§4.1).
- 고빈도 타임스탬프 경로가 vDSO를 타는지 `strace -c`로 확인 (§4.3).
- DNS·사용자 조회 동작 차이(NSS 없음, resolver 동작 차이) 확인.
- 벤더 블롭이 하나라도 있으면 포기하고 glibc.

### 11.4 initramfs 복구 툴은 musl 정적으로

eMMC의 rootfs가 깨졌을 때 initramfs에서 도는 업데이트·복구 툴은 rootfs의 libc에 의존하면 안 된다. musl 정적 빌드면 툴 하나가 수십~수백 KB이고(§3.1), 로더·`.so`가 필요 없으니 initramfs를 작게 유지할 수 있다.

## 13. 면접에서 이렇게 말한다

**Q.** "What does the C library actually do on Linux? Where does it sit?"

**A.** libc는 앱과 커널 사이의 유저 공간 런타임이다. 커널 syscall 위에 POSIX API를 구현하고(래퍼가 `-errno`를 -1과 TLS `errno`로 바꾼다), stdio 버퍼링, `brk`/`mmap` 위의 malloc, NPTL 스레드와 futex 기반 동기화, 로케일·iconv, NSS와 DNS resolver, 그리고 `_start`부터 `main`과 `exit`까지의 시작·종료 코드를 제공한다. 동적 링크면 로더 `ld-linux`도 libc 프로젝트의 일부다. bare-metal의 newlib과 달리 아래쪽 끝이 stub 함수가 아니라 커널이다.

> It's the user-space runtime between applications and the kernel. It implements POSIX on top of raw system calls — the wrappers turn the kernel's negative error return into -1 plus a thread-local errno — and adds stdio buffering, malloc on top of brk and mmap, NPTL threads with futex-based locks, locale and iconv, name resolution through NSS and the DNS resolver, and the startup and shutdown path from _start through main to exit. With dynamic linking, the loader ld-linux comes from the same project. Compared with newlib on bare metal, the bottom edge is the kernel's syscall ABI instead of stub functions you write yourself.

**꼬리 질문**: "Is errno a global variable?" → 스레드별 TLS, glibc는 `(*__errno_location())` 매크로.

**Q.** "glibc vs musl — how do you choose for an embedded product?"

**A.** 먼저 벤더 바이너리를 본다. GPU·NPU·카메라 ISP 라이브러리는 거의 항상 glibc 전용이라 하나라도 있으면 glibc다. 없고 플래시가 작거나 정적 툴이 많으면 musl이 좋다 — 내가 재 보니 정적 hello가 550 KiB 대 33 KiB, 시작 시간 126 대 75 µs였다. 대신 musl은 malloc이 멀티스레드에서 느리고(4스레드에서 3 대 94 ns/op), 기본 스레드 스택이 128 KiB라서 스택 크기를 명시해야 한다. 라이선스도 LGPL 대 MIT라 정적 배포 때 차이가 난다.

> First I check for vendor binaries: GPU, NPU and ISP user-space stacks are almost always built against glibc, so if there's even one, it's glibc. Otherwise, if flash is tight or we ship many static tools, musl is attractive — in my measurements a static hello was 550 KiB with glibc versus 33 KiB with musl, and start-up was about 126 versus 75 microseconds. The trade-offs are musl's slower allocator under threads — roughly 3 versus 94 ns per malloc/free with four threads — and its 128 KiB default thread stack, so you set stack sizes explicitly. Licensing matters too: glibc is LGPL, musl is MIT, which simplifies static distribution.

**Q.** "What happens before main() is called?"

**A.** `execve`에서 커널이 ELF를 매핑하고 `PT_INTERP`가 있으면 로더도 매핑해 로더 진입점으로 간다. 스택에는 argc, argv, envp, auxv가 쌓인다. 로더는 자기 재배치 후 `DT_NEEDED` 라이브러리를 찾아 매핑하고, 심볼 버전 확인, 재배치, RELRO, 라이브러리 init을 한 뒤 프로그램의 `_start`(crt1.o)로 점프한다. `_start`는 argc/argv를 꺼내 `__libc_start_main`을 부르고, 이 함수가 TLS·스택 가드·`init_array`(생성자)를 처리하고 `main`을 부른다. `main`이 리턴하면 `exit`가 atexit 핸들러, 소멸자, stdio flush, `exit_group` 순으로 정리한다.

> On execve the kernel maps the ELF and, if there's a PT_INTERP, maps the dynamic loader too and starts executing at the loader's entry, with argc, argv, envp and the auxiliary vector on the stack. The loader relocates itself, finds and maps every DT_NEEDED library, checks symbol versions, applies relocations, write-protects the RELRO region and runs library initializers, then jumps to the program's _start from crt1.o. _start pulls argc and argv off the stack and calls __libc_start_main, which sets up TLS and the stack protector, runs the init_array constructors and calls main. When main returns, exit runs atexit handlers, destructors, flushes stdio and finally calls exit_group.

**꼬리 질문**: "Where does the very first user-space instruction execute?" → 동적 바이너리면 로더의 `_start`(gdb `starti`로 확인 가능).

**Q.** "A binary fails on the target with 'version GLIBC_2.38 not found'. Explain and fix."

**A.** glibc는 심볼마다 버전 태그를 붙여 하위 호환을 유지한다. 새 glibc로 링크하면 바이너리가 새 태그(예: C23 모드의 `__isoc23_strtol@GLIBC_2.38`)를 요구하게 되고, 타깃의 옛 glibc에는 그 정의가 없으니 로더가 버전 확인 단계에서 실행을 거부한다. `objdump -T`로 요구 태그를 확인하고, 근본적으로는 타깃과 같은 glibc의 sysroot·SDK로 빌드한다. 임시로는 새 API와 C23 기본값을 피하거나, musl 정적 링크로 libc 의존을 없앤다.

> glibc versions its symbols so old binaries keep working on newer libraries, but not the other way round. Linking on a newer host binds to newer versions — gcc 15 defaults to C23, so even strtol becomes __isoc23_strtol at GLIBC_2.38 — and the target's older libc.so.6 doesn't define that version, so the dynamic loader refuses to start the program during version checking. I'd confirm with objdump -T to see the highest GLIBC tag required, and fix it properly by building against the target's sysroot or SDK so the linker can only bind to versions the target has. Short-term options are avoiding the new APIs, compiling with -std=gnu17, or linking statically against musl.

**Q.** "Why is static linking with glibc discouraged?"

**A.** NSS, iconv, dlopen 같은 기능은 정적 바이너리에서도 실행 중 공유 라이브러리를 불러오고, 그 라이브러리는 공유 glibc를 끌고 온다. 실제로 `getpwnam`으로 없는 사용자를 조회하는 정적 바이너리가 `libnss_systemd.so.2`와 `libc.so.6`, 로더까지 여는 걸 strace로 봤다. 링크한 버전과 rootfs 버전이 다르면 깨진다. 거기에 바이너리가 크고, 보안 패치가 재빌드 없이 반영되지 않고, LGPL 재링크 의무가 생긴다. 정적이 필요하면 musl을 쓴다.

> Because parts of glibc still load shared objects at run time even in a static binary — NSS, iconv and dlopen. I traced a static binary looking up an unknown user and it opened libnss_systemd.so.2, which pulled in the shared libc.so.6 and the loader; if those don't match the glibc you linked against, lookups fail or crash. On top of that the binaries are large, security fixes need a rebuild, and LGPL adds relinking obligations for static distribution. If I need a truly self-contained binary, I use musl.

**Q.** "How does the dynamic loader find libraries, and how do you debug 'cannot open shared object file'?"

**A.** 로더는 `DT_NEEDED`의 이름을 RUNPATH가 없을 때의 `DT_RPATH`, `LD_LIBRARY_PATH`, `DT_RUNPATH`, `/etc/ld.so.cache`, 기본 경로(`/lib`, `/usr/lib`) 순으로 찾는다. 디버그는 `readelf -d`로 NEEDED·RUNPATH를 보고, glibc면 `LD_DEBUG=libs`로 실제로 어디를 뒤졌는지 본다. 새 라이브러리를 넣었으면 `ldconfig`로 캐시를 갱신한다.

> The loader resolves each DT_NEEDED name by checking DT_RPATH when there's no RUNPATH, then LD_LIBRARY_PATH, then DT_RUNPATH, then the /etc/ld.so.cache index, then the default directories. To debug, I read NEEDED and RUNPATH with readelf -d, and on glibc I run with LD_DEBUG=libs to see exactly which paths it tried. If a library was just installed, running ldconfig to refresh the cache is often the fix.

**Q.** "Why can ldd be dangerous?"

**A.** `ldd`는 분석기가 아니라 로더를 `LD_TRACE_LOADED_OBJECTS=1`로 돌리는 스크립트다. man 페이지는 일부 구현이 프로그램의 `PT_INTERP`를 직접 실행할 수 있다고 경고한다 — 그러면 가짜 인터프리터를 넣은 바이너리에 `ldd`만 해도 코드가 실행된다. 내가 실험해 보니 최신 glibc의 ldd는 시스템 로더를 써서 실행은 안 했지만 가짜 로더를 진짜 로더로 표시했고, musl·크로스 바이너리에도 틀린 답을 냈다. 그래서 `readelf -d`나 `objdump -p`로 본다.

> ldd isn't a parser — it's a script that runs the loader with LD_TRACE_LOADED_OBJECTS set, so it actually loads the program. The man page warns that some implementations may execute the program's own ELF interpreter, so a crafted binary could run code just by being inspected. When I tested a binary with a fake PT_INTERP, modern glibc's ldd used the system loader and didn't execute it, but it misreported the interpreter, and it also gives wrong answers for musl or cross-compiled binaries. For untrusted or foreign binaries I use readelf -d or objdump -p instead.

**Q.** "What is the vDSO?"

**A.** 커널이 모든 프로세스에 매핑하는 작은 공유 라이브러리로, `clock_gettime` 같은 읽기 전용 호출을 syscall 없이 처리한다. libc가 auxv의 `AT_SYSINFO_EHDR`로 위치를 받아 심볼을 찾는다. 내 측정에서 glibc의 `clock_gettime`은 20 ns였고, vDSO를 못 쓰는 경우(이 커널 조합의 musl)는 실제 syscall이 돼서 170 ns였다.

> It's a small shared object the kernel maps into every process so that read-mostly calls like clock_gettime can run without entering the kernel. The C library finds it through AT_SYSINFO_EHDR in the auxiliary vector and resolves its symbols like any other library. I measured clock_gettime at about 20 ns through glibc's vDSO path versus about 170 ns when it fell back to a real system call, which is what happened with musl on that kernel.

## 14. 직접 해보기

1. **개념**: 동적 링크된 바이너리에서 사용자 공간의 첫 명령어는 어느 파일의 어느 함수에서 실행되나? 정적 바이너리면?
   정답/힌트: 동적이면 `PT_INTERP`의 로더(`ld-linux-aarch64.so.1`)의 `_start`, 정적이면 프로그램 자신의 `_start`. `gdb`의 `starti`로 확인한다.
2. **코드**: §4.2의 `stack.c`를 musl로 빌드해서, 재귀 깊이를 이분 탐색으로 늘려 가며 segfault가 나는 최소 깊이를 찾아라. 그 값이 128 KiB와 어떻게 맞는지 설명하라.
   정답/힌트: 이 VM에서는 125단계는 통과, 130단계에서 SIGSEGV였다. 프레임당 1 KiB 배열 + 프레임 오버헤드에, TLS·스레드 구조체가 같은 매핑을 나눠 쓰기 때문에 128보다 약간 작은 곳에서 죽는다.
3. **strace 관찰**: `strace -f ./mb_glibc 4 2>&1 | grep -E "clone|mmap"`과 musl판을 비교해, 스레드 스택이 어떤 크기로 `mmap`되는지 확인하라.
   정답/힌트: 이 VM에서 glibc는 `mmap(NULL, 8454144, ..., MAP_STACK)`(8 MiB + 64 KiB guard), musl은 `mmap(NULL, 143360, PROT_NONE, ...)` 뒤 `mprotect`로 사용 부분을 여는 방식이었다(스택 + guard + TLS). musl은 `clone`, glibc는 `clone3`를 쓴다.
4. **심볼 버전**: `ver.c`를 `-std=gnu17`로만 빌드하면(strlcpy는 그대로) 요구 태그 목록이 어떻게 바뀌나? `objdump -T`로 확인하라.
   정답/힌트: `__isoc23_strtol`이 `strtol@GLIBC_2.17`로 돌아가지만 `strlcpy@GLIBC_2.38` 때문에 최고 태그는 여전히 2.38이다.
5. **LD_DEBUG**: `LD_DEBUG=libs LD_LIBRARY_PATH=/tmp/B2/oldroot ./hello_glibc_dyn`을 실행해 로더가 어떤 순서로 경로를 시도하는지 보고, §7.3의 가짜 libc가 왜 먼저 잡히는지 설명하라.
   정답/힌트: `search path=/tmp/B2/oldroot` 줄이 cache보다 먼저 나온다. `LD_LIBRARY_PATH`는 `ld.so.cache`보다 우선한다. 이 hello는 가짜 libc에 `__printf_chk`가 없어 "symbol lookup error"로 끝난다.
6. **크기**: `nss.c`를 musl 정적으로 빌드한 뒤 `nm --size-sort`로 가장 큰 심볼 10개를 뽑고, glibc 정적판과 비교해 어떤 기능이 크기를 차지하는지 찾아라.
   정답/힌트: glibc 쪽은 NSS·로케일·`vfprintf` 관련 심볼과 ifunc로 고르는 여러 CPU용 `memcpy` 변종이 크다.
7. **실무 스크립트**: 디렉터리 안의 모든 ELF에 대해 최고 `GLIBC_2.xx` 요구 태그를 출력하고, 지정한 타깃 버전보다 높으면 실패하는 CI 스크립트를 셸로 짜라.
   정답/힌트: `file`로 ELF를 거르고 `objdump -T`의 태그를 `sort -t. -k2 -n`으로 정렬한다. 버전 비교는 마이너 번호만 정수로 비교하면 된다(`GLIBC_2.x` 체계).

| glibc | GNU C Library | 데스크톱·서버·Yocto 기본 libc, LGPL, 심볼 버전 사용 |
| musl | musl libc | 작고 단순한 MIT 라이선스 libc, Alpine·OpenWrt |
| uClibc-ng | micro C library | 작은 임베디드·noMMU Linux용 설정형 libc |
| bionic | Android libc | Android 전용 BSD 라이선스 libc |
| newlib | 임베디드 C 라이브러리 | bare-metal·RTOS용, 아래쪽을 stub 함수로 채운다 |
| NPTL | Native POSIX Thread Library | glibc의 1:1 pthread 구현 (스레드 = 커널 태스크) |
| NSS | Name Service Switch | `nsswitch.conf` 순서대로 `libnss_*.so`를 불러 이름을 조회하는 glibc 구조 |
| locale / iconv | 지역화 / 문자셋 변환 | glibc는 locale-archive와 gconv 모듈을 쓴다 |
| crt1.o / Scrt1.o | C runtime 시작 오브젝트 | `_start`를 담는다, PIE는 `Scrt1.o` |
| crti.o / crtn.o | init/fini 프롤로그·에필로그 | `.init`/`.fini` 섹션 앞뒤 조각 |
| `__libc_start_main` | libc 시작 함수 | TLS·init_array 처리 후 `main` 호출, 리턴하면 `exit` |
| init_array / fini_array | 생성자·소멸자 표 | `constructor`/`destructor` 함수 포인터 배열 |
| dynamic loader (ld.so) | 동적 로더 | `ld-linux-aarch64.so.1`, 공유 라이브러리를 찾아 붙인다 |
| PT_INTERP | 인터프리터 프로그램 헤더 | 커널이 실행할 로더의 절대 경로 |
| DT_NEEDED | 필요 라이브러리 항목 | 로더가 찾아 붙일 soname 목록 |
| soname | 공유 라이브러리 이름 | `libc.so.6`처럼 ABI 호환 단위를 나타내는 이름 |
| `/etc/ld.so.cache` | 라이브러리 색인 | `ldconfig`가 만드는 이름 → 경로 캐시 |
| symbol versioning | 심볼 버전 | `strtol@GLIBC_2.17`처럼 심볼마다 붙은 ABI 버전 태그 |
| BIND_NOW | 즉시 결합 | 시작 시 모든 심볼을 결합, lazy binding 없음 |
| RELRO | Relocation Read-Only | 재배치 후 GOT 등을 읽기 전용으로 잠그는 보호 |
| vDSO | virtual dynamic shared object | 커널이 매핑하는 라이브러리, `clock_gettime`을 syscall 없이 처리 |
| auxv | auxiliary vector | 커널이 스택에 넣어 주는 정보 (`AT_PHDR`, `AT_SYSINFO_EHDR` …) |
| TLS | thread-local storage | 스레드별 변수 영역, arm64는 `TPIDR_EL0`가 가리킨다 |
| UAPI | user-space API 헤더 | 커널이 유저에게 공개하는 번호·구조체 정의, `linux-libc-dev` |
| LGPL | GNU Lesser GPL | glibc 라이선스, 정적 링크 배포 시 재링크 가능성 제공 의무 |

## 16. 요약 & 체크리스트

Linux의 C 라이브러리는 newlib의 "stub 함수" 자리에 커널 syscall을 두고, 그 위에 syscall 래퍼와 TLS `errno`, stdio 버퍼링, `brk`/`mmap` 기반 malloc, NPTL 스레드, locale·iconv, NSS·resolver, 그리고 `_start` → `__libc_start_main` → `main` → `exit`의 시작·종료 코드를 제공한다. 동적 바이너리는 `PT_INTERP`의 로더가 먼저 실행되어 `DT_NEEDED` 라이브러리를 찾고, **심볼 버전**을 확인하고, 재배치한 뒤 프로그램으로 넘긴다. 그래서 새 glibc로 빌드한 바이너리는 옛 rootfs에서 "version `GLIBC_2.xx' not found"로 거부된다. 이 VM 실측으로 musl은 정적 크기(33 KiB 대 550 KiB)·시작 비용(75 대 126 µs)·syscall 수(4 대 15)에서 이기고, 멀티스레드 malloc(94 대 3 ns/op)·기본 스레드 스택(128 KiB 대 8 MiB)·vDSO 사용(이 커널에서 170 대 20 ns)에서 불리했다. 제품 선택은 벤더 바이너리(대개 glibc 전용)가 먼저 결정하고, 그다음이 플래시 크기다. 커널 자신은 libc를 쓰지 않고, 번호·에러 코드·구조체를 UAPI 헤더로 libc와 공유하며, 드라이버가 돌려준 음수 에러 코드가 그대로 유저의 `errno`가 된다.

- [ ] libc가 하는 일 7가지를 newlib과 비교해 설명할 수 있다
- [ ] 커널의 `-errno`가 libc 래퍼에서 `-1` + TLS `errno`로 바뀌는 과정을 코드로 보일 수 있다
- [ ] glibc·musl·uClibc-ng·bionic의 크기·라이선스·호환성·용도를 표로 말할 수 있다
- [ ] 보드에서 libc 종류와 버전을 확인하는 방법 3가지를 안다 (`libc.so.6` 실행, `getconf`, `ldd --version`)
- [ ] `strace`로 프로그램 시작 시 로더·libc가 하는 syscall을 읽고 해석할 수 있다
- [ ] `execve` → 로더 `_start` → 프로그램 `_start` → `__libc_start_main` → `main` → `exit` 흐름을 그리고 gdb로 확인할 수 있다
- [ ] `PT_INTERP`와 `DT_NEEDED`를 `readelf`로 읽고, 로더를 직접 실행해 프로그램을 띄울 수 있다
- [ ] `LD_DEBUG=libs,bindings,versions,statistics`로 로더 동작을 관찰할 수 있다
