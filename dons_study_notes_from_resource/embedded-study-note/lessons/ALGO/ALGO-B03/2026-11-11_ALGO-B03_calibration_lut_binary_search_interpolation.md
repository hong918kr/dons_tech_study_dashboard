# ALGO-B03 보정 테이블 조회: 이진 탐색 + 선형 보간

## 학습 목표

- 비균등 보정 테이블(calibration table)에서 **upper_bound − 1** 로 구간을 찾는다 (ALGO-B02 의 경계 탐색 재사용). 키가 오름차순이든 내림차순이든 같은 함수로 처리한다.
- 정수만으로 선형 보간(linear interpolation)을 하면서 **중간 곱의 크기를 증명**하고 int32 / int64 를 의도적으로 고른다.
- C 의 `/` 가 0 쪽으로 자른다는 것(C11 6.5.5p6)을 알고, 음수까지 맞는 **반올림 나눗셈**(동점은 0에서 먼 쪽)을 쓴다. 왜 "가중 평균 꼴"이 "y0 + 증분 꼴"보다 반올림이 깔끔한지 설명한다.
- 표 끝 밖은 **포화(saturation) + 상태 코드**, 단락/단선은 고장으로 나누고, double 모델과 비교해 **ADC 코드 0..4095 전부**의 최대 오차를 잰다.
- 비균등 표 · 균등 표(시프트 색인) · 코드당 1칸 표 · float 계산을 **메모리 · 속도 · 정확도**로 비교하고, FPU 없는 Cortex-M0 / 단정도 FPU Cortex-M4F 에서 무엇이 달라지는지 말한다.

## 1. 문제

센서 값 변환은 펌웨어에서 가장 흔한 "알고리즘"이고, 면접에서는 "이진 탐색 + 정수 산술 + 경계 처리"를 한 문제로 묶어 보는 단골 소재다 — 오프 바이 원, 오버플로, 음수 반올림이 한꺼번에 드러난다.

상황: 보드에 NTC 서미스터(온도가 오르면 저항이 내려가는 소자)가 분압 회로로 붙어 있고, 12-bit ADC 코드(0..4095)를 온도로 바꿔야 한다. MCU 는 Cortex-M0 급이라 FPU 가 없고, 변환은 1 kHz 제어 루프에서 채널 8개마다 돈다.

**이 레슨이 정한 모델** (실제 부품 데이터시트 표 대신, 재현 가능하게 식으로 만든다):

- NTC: R0 = 10 kΩ @ 25 °C, Beta 식 `1/T = 1/T0 + ln(R/R0)/B`, B = 3950 K (10k NTC 에서 흔한 값), T 는 켈빈.
- 분압: 고정 저항 10 kΩ 를 Vref 쪽, NTC 를 GND 쪽. 비율측정(ratiometric) ADC 라 Vref 가 약분된다.
- ADC: 코드 c 의 중심 = (c + 0.5)/4096 · Vref → `R = 10k · x/(1−x)`, x = (c+0.5)/4096.
- 출력: **centi-°C, int32** (25.00 °C = 2500). 0.01 °C 단위면 −40..125 °C 가 int16 에도 들어간다.
- 표: `demo_gen_table.c` 가 −40..125 °C 를 **5 °C 간격**으로 코드로 바꿔 반올림하고, 그 코드에서 온도를 다시 계산해 centi 로 반올림한다 → 34점, 각 점은 모델과 ±0.5 centi 이내. 5 °C 간격은 코드 축에서는 **비균등**하다: 곡선이 많이 휘는 양 끝에서 코드 간격이 19~41, 거의 직선인 가운데서 230 안팎.

### Part A — 구간 찾기 · 반올림 나눗셈 · 보간

```c
typedef struct { const int32_t *x; const int32_t *y; int n; } lut_t;
int     seg_find(const int32_t *x, int n, int32_t q);   /* 0..n-2, 오름/내림 자동 */
int64_t div_round(int64_t num, int64_t den);            /* den > 0, 동점은 0에서 먼 쪽 */
int32_t lut_eval(const lut_t *t, int32_t q);            /* 양 끝 포화 + 정수 보간 */
```

- `seg_find`: 오름차순이면 `x[i] <= q < x[i+1]`, 내림차순이면 `x[i] >= q > x[i+1]`, q 가 마지막 점이면 n−2. 이진 탐색, O(log n).
- `div_round`: `|num| <= 2^62`. 7/2 → 4, −7/2 → −4, −5/3 → −2.
- `lut_eval`: 결과 = **정확한 보간값 v 를 반올림한 것** (동점은 0에서 먼 쪽). 값은 int32 전 범위, 키 폭은 INT32_MAX 이하에서 넘침 없이.

### Part B — 표 검사와 까다로운 변형

- `lut_validate(t)`: 크기(n ≥ 2, NULL 아님) → 순단조(한 방향, **같은 키 금지** — 0 나눗셈) → 키 폭 ≤ INT32_MAX. 반환 `LUT_OK / LUT_ERR_SIZE / LUT_ERR_ORDER / LUT_ERR_SPAN`.
- 하네스가 확인하는 변형: 내림차순 키(역조회: 온도 → 코드, 경보 임계값 설정용), int32 로 곱하면 넘치는 µV 표(3,300,000 × 2048), 값이 INT32_MIN..INT32_MAX 인 표(차이 자체가 int32 를 넘음), 부호 반전 대칭(`-y` 표 → `-결과`), 표를 거꾸로 저장해도 같은 결과, 단조성.

### Part C — NTC 채널 드라이버와 균등 LUT 비교

- `ntc_read(code, &centi)`: 코드 ≤ 15 → `NTC_FAULT_SHORT`, ≥ 4080 → `NTC_FAULT_OPEN` (출력은 건드리지 않음), 표 밖 → 끝 값 + `NTC_HOT_CLAMP / NTC_COLD_CLAMP`, 안 → `NTC_OK`. 보간은 **int32 만** 쓴다 (근거는 하네스가 확인).
- `ulut_eval(code)`: 코드 128 부터 64 코드 간격 62점 균등 표. 탐색 없이 `j = off >> 6`, `f = off & 63`, 반올림도 시프트.
- 검증: 0..4095 전부 상태 분류, int32 경로 == int64 경로, double 모델 대비 최대 |오차| ≤ 20 centi (비균등) / ≤ 100 centi (균등).

## 2. Problem (English)

> **Sensor calibration lookup.** A 12-bit ADC reads an NTC thermistor. You are given a calibration table of `n` points `(x[i], y[i])` where `x` is strictly monotonic (increasing or decreasing) and `y` is the value in fixed point (centi-degrees Celsius, `int32_t`). Implement:
>
> ```c
> int     seg_find(const int32_t *x, int n, int32_t q);   // segment index 0..n-2 (binary search)
> int64_t div_round(int64_t num, int64_t den);            // den > 0, round half away from zero
> int32_t lut_eval(const lut_t *t, int32_t q);            // clamp outside, integer linear interpolation inside
> int     lut_validate(const lut_t *t);                   // size, strict monotonicity, key span <= INT32_MAX
> ntc_status_t ntc_read(uint16_t code, int32_t *centi);  // faults, clamping, int32-only fast path
> int32_t ulut_eval(uint16_t code);                       // uniform 64-code-step table, shift indexing
> ```
>
> Constraints: no floating point in the lookup path; no undefined behavior for any `int32_t` input; `y` may use the full `int32_t` range; result must equal `round_half_away(v)` where `v` is the exact interpolated value; O(log n) per lookup; no heap.
>
> Examples (table `x = {0, 10}`, `y = {0, 100}`): `lut_eval(5) = 50`, `lut_eval(-3) = 0`, `lut_eval(12) = 100`.
> Table `x = {0, 1000}`, `y = {INT32_MIN, INT32_MAX}`: `lut_eval(500) = -1` (exact value −0.5).
> NTC table: `ntc_read(2048) → OK, 2499`; `ntc_read(140) → HOT_CLAMP, 12511`; `ntc_read(4095) → FAULT_OPEN`.
>
> Follow-ups: How large can the intermediate product get? What does `/` do with negatives in C? How would you pick the table points? Binary search or a uniform table — which one in an ISR on a Cortex-M0?

## 4. 힌트

<details>
<summary>힌트 1 — 구간 = "q 보다 큰 첫 키" 의 바로 앞</summary>

ALGO-B02 의 `upper_bound`(첫 `x[i] > q`)를 구하면 그 앞 칸이 구간 시작이다. q 가 마지막 점과 같으면 upper_bound = n 이라 i = n−1 이 되는데, 구간은 n−2 까지뿐이니 한 번 잘라 준다. 내림차순은 비교 방향만 뒤집는다: "q 이전" = `x[mid] >= q`.

</details>

<details>
<summary>힌트 2 — 음수 반올림은 부호를 떼고</summary>

`(num + den/2) / den` 은 num ≥ 0 일 때만 맞다. num < 0 이면 `-((-num + den/2) / den)`. 이러면 `f(-a) = -f(a)` 가 저절로 성립한다.

</details>

<details>
<summary>힌트 3 — 보간식을 가중 평균으로</summary>

`d = |x1 − x0|`, `s = |q − x0|` (0 ≤ s ≤ d) 로 두면 `v = (y0·(d−s) + y1·s) / d`. 두 곱 모두 계수가 0 이상이라 `|분자| ≤ max(|y0|,|y1|)·d < 2^31 · 2^31 = 2^62` — int64 에 넉넉히 들어간다. `y1 − y0` 를 계산할 필요도 없다.

</details>

<details>
<summary>힌트 4 — 포화를 먼저, 고장은 그보다 먼저</summary>

`seg_find` 의 전제는 "q 가 표 범위 안" 이다. 그러니 `lut_eval` 은 양 끝 포화를 탐색 **앞에서** 처리한다. `ntc_read` 는 단락/단선 → 포화 → 보간 순서. 고장일 때 출력 포인터에 쓰지 않는 것도 계약이다.

</details>

<details>
<summary>힌트 5 — 균등 표는 나눗셈이 시프트</summary>

간격이 64 = 2^6 이면 `j = off >> 6`, `f = off & 63`, 반올림은 `(num + 32) >> 6`. 단, num 이 음수일 때 `>>` 는 **구현 정의**(C11 6.5.7p5)이고 대부분 바닥(floor) 쪽으로 간다 — 힌트 2 처럼 부호를 떼라.

</details>

### Part A — 반올림 나눗셈: C 의 `/` 는 0 쪽으로 자른다

C99 부터 정수 나눗셈은 **0 쪽으로 자르기**(truncation)로 정해져 있다(C11 6.5.5p6, `a == (a/b)*b + a%b`). 그래서 반올림 공식이 부호에 따라 달라진다.

| 정확한 값 v | 자르기 `num/den` | 흔한 실수 `(num + den/2)/den` | `floor(v + 0.5)` | **0에서 먼 쪽 (이 레슨)** |
|---|---|---|---|---|
| 2.5 | 2 | 3 | 3 | **3** |
| −2.5 | −2 | −2 | −2 | **−3** |
| −1017.63 (q=3500) | −1017 | −1017 (틀림) | −1018 | **−1018** |
| −0.5 (int32 전 범위 표) | 0 | 0 | 0 | **−1** |

`(num + den/2)/den` 은 num < 0 에서 "더한 다음 0 쪽으로 자르기"라 반올림이 아니다 — −1017.63 이 −1017 이 된다. 고친 식은 부호를 떼고 처리한다:

```c
if (num >= 0) return (num + den / 2) / den;
return -((-num + den / 2) / den);
```

den 이 홀수면 정확한 .5 가 없으므로 `den/2 = (den−1)/2` 로도 맞고, 짝수면 나머지가 정확히 den/2 일 때 올림(= 0에서 먼 쪽)이 된다. `|num| ≤ 2^62`, `den < 2^31` 이라 `num + den/2` 도 넘치지 않는다.

**어떤 동점 규칙을 고를까 — 수학적으로 둘 중 하나만 얻는다.** `floor(v + ½)` 는 정수 이동에 불변(`r(v + k) = r(v) + k`)이지만 부호 대칭이 아니다(2.5 → 3, −2.5 → −2). 0에서 먼 쪽은 부호 대칭(`r(−v) = −r(v)`)이지만 정수 이동 불변이 아니다. 이 레슨은 `lround` 와 같고 온도 0 °C 근처에서 대칭인 0에서 먼 쪽을 골랐다. 그 대가로 **무엇을 반올림하느냐**가 중요해진다 ↓.

### Part A — 보간식: 왜 가중 평균 꼴인가

흔한 꼴은 `y0 + round(dy·s/d)` (증분 꼴)이다. 0에서 먼 쪽 반올림은 정수 이동 불변이 아니므로, 증분 꼴은 **v 가 아니라 증분을 반올림**해서 동점에서 결과가 기준점(y0 냐 y1 이냐)에 따라 달라진다. 예: v = 11374.5 (코드 187) — 가중 평균 꼴은 11375, 증분 꼴은 y0 = 11497 에서 −122.5 → −123 이라 11374.

그래서 정답은 v 자체를 한 분수로 만든다:

```c
int64_t num = (int64_t)y[i] * (d - s) + (int64_t)y[i + 1] * s;   /* v = num / d */
return (int32_t)div_round(num, d);
```

- **상한 증명**: 0 ≤ s ≤ d, 두 계수 모두 0 이상 → `|num| ≤ max(|y0|,|y1|)·((d−s)+s) ≤ 2^31·d`. 키 폭을 `INT32_MAX` 이하로 제한했으니 d < 2^31 → `|num| < 2^62`. int64 안.
- **결과도 int32 안**: v 는 y0 과 y1 사이, 둘 다 정수라 반올림해도 그 사이 → 캐스트가 안전하다.
- **차이 `y1 − y0` 를 계산하지 않는다**: y = {INT32_MIN, INT32_MAX} 면 차이가 2^32−1 이라 int32 로는 UB 다. 가중 평균 꼴은 이 함정을 아예 피한다.
- 실측: NTC 표의 표 범위 3856개 코드 중 정확한 .5 동점이 **22개**, 증분 꼴은 그중 21개에서 다른 답을 냈고, 표를 거꾸로 저장했을 때 결과가 바뀐 코드가 22개였다(7. 실수 2).

### Part B — 표 검사, 내림차순 키, int32 넘침

- `lut_validate` 의 세 검사는 각각 `lut_eval` 의 전제다: n ≥ 2 (구간이 하나는 있어야), 순단조 (같은 키 → d = 0 → 0 나눗셈, 방향이 바뀌면 이진 탐색 불변식이 깨짐), 키 폭 ≤ INT32_MAX (분자 상한 2^62 의 근거). 키 폭은 `(int64_t)x[n-1] - x[0]` 으로 계산한다 — int32 끼리 빼면 {INT32_MIN, 0} 에서 이미 넘친다.
- **내림차순 키**: 역조회 `{x = NTC_CENTI, y = NTC_CODE}` 가 그렇다. `seg_find` 는 `x[0] < x[n-1]` 로 방향을 보고, `lut_eval` 은 d < 0 이면 d, s 의 부호를 함께 뒤집어 0 ≤ s ≤ d 로 맞춘다. 85.00 °C → 코드 401 (표의 점), 25.00 °C → 2048.
- **int32 넘침**: 12-bit → µV 표 `{0,4095} → {0,3300000}` 에 흔한 한 줄 `y0 + (y1-y0)*(q-x0)/(x1-x0)` 를 int32 로 쓰면 (작업용 프로그램, 실제 출력):

```text
naive = -447261 (want 1650403)
ovf.c:4:27: runtime error: signed integer overflow: 3300000 * 2048 cannot be represented in type 'int32_t' (aka 'int')
```

  -O2 에서는 조용히 음수가 나오고(부호 있는 오버플로는 UB, C11 6.5p5), UBSan 이 정확히 그 곱을 짚는다. 정답의 int64 경로는 1650403 (= round(6758400000/4095)).

### Part C — int32 빠른 경로를 고른 근거와 상태 코드

Cortex-M 에서 int64 나눗셈은 라이브러리 호출이다(아래 asm). 그래서 NTC 채널은 int32 로 계산하되 **근거를 숫자로** 남긴다: 하네스의 `lut_i32_bound` 가 모든 구간에서 `max(|y0|,|y1|)·d` 를 계산 → **최대 800822** (< 2^31 = 2147483648, 약 2680배 여유). 같은 0..4095 입력에서 int32 경로와 int64 `lut_eval` 의 결과가 전부 같은 것도 확인한다(`int32!=int64 path=0`). 표를 바꾸면 이 검사가 먼저 깨지게 해 두는 것이 요점이다 — C11 에는 배열 원소에 대한 `_Static_assert` 가 안 되니(const 배열 원소는 정수 상수식이 아니다) 단위 테스트나 표 생성기에서 확인한다.

상태는 넷 + OK 하나. 순서가 중요하다: 단락(≤ 15)과 단선(≥ 4080)을 **포화보다 먼저** 봐야 "NTC 가 빠졌는데 −40 °C 로 포화되어 히터가 최대로 켜지는" 사고를 막는다. 고장일 때 `*centi` 를 건드리지 않는 계약은 하네스가 0..4095 전부에서 확인한다(`fault-output-touched=0`).

읽을 것:

- **이 맥에서는 double `log` 가 이진 탐색보다 빠르다.** 무작위 입력에서 이진 탐색의 분기 5~6개는 예측이 거의 안 맞아(분기 예측 실패, branch misprediction) 비싸고, M6 의 FPU + libm 은 빠르다. 입력이 천천히 변하면(walk) 분기가 예측되어 이진 탐색이 1.5~2배 빨라진다. 즉 **데스크톱 숫자로 MCU 를 판단하면 안 된다** — 아래 Cortex-M 절.
- 균등 표는 탐색도 나눗셈도 없어 이진 탐색보다 4~5배 빠르지만, 같은 메모리에서 오차가 5배 크다. 같은 오차(≈ 7 centi)를 내려면 243점(486 B as int16)이 필요하다.
- 코드당 1칸 표는 가장 빠르고 정확하지만 8 KB. flash 가 32 KB 인 M0 에서는 부담, 512 KB 인 M4 에서는 합리적 선택일 수 있다.

### Cortex-M 에서는: 나눗셈과 FPU

같은 보간식을 `clang --target=thumbv6m-none-eabi -mcpu=cortex-m0 -O2 -S` 와 `--target=thumbv7em-none-eabi -mcpu=cortex-m4` 로 컴파일한 결과 (작업용 파일, 핵심 줄만 실제 출력에서 발췌):

| 함수 | Cortex-M0 | Cortex-M4 |
|---|---|---|
| int32 가중 평균 + 나눗셈 | `muls` ×2, `bl __aeabi_idiv` | `muls`, `mla`, **`sdiv`** (명령 1개) |
| int64 가중 평균 + 나눗셈 | `bl __aeabi_lmul` ×2, `bl __aeabi_ldivmod` | `smull`, `smlal`, **`bl __aeabi_ldivmod`** |
| 64 간격 시프트 반올림 | `muls` ×2, `lsrs #6` — 호출 없음 | `muls`, `mla`, `lsrs #6` — 호출 없음 |

- M0(ARMv6-M)는 나눗셈 명령이 없어 32비트 나눗셈도 런타임 라이브러리 루틴이다. 곱셈 `MULS` 는 칩 설계에 따라 1 cycle 또는 32 cycle(작은 곱셈기 옵션)이다.
- M4 는 `SDIV` 가 있지만(ARM 문서상 2~12 cycle, 피연산자에 따라 일찍 끝남) **64비트 나눗셈은 M4 에서도 라이브러리 호출**이다. int32 경로를 증명해서 쓰는 이유가 이것이다.
- M4F 의 FPU 는 **단정도만**(FPv4-SP)이다. `double` 의 `log` 는 M4F 에서도 소프트웨어로 돈다. `logf` 도 libm 구현이라 수십~수백 cycle 대를 예상해야 하고, ISR 에서 FPU 를 쓰면 예외 진입 때 FPU 레지스터 저장(lazy stacking)도 따라온다. M0 의 soft-float `log` 는 그보다 훨씬 비싸다(이 레슨에서 측정하지 않음 — 실제 보드에서 DWT 사이클 카운터로 잴 것).
- **ISR 예산 어림**: 64 MHz M0+, 1 kHz 루프 × 8채널. 조회 1번을 대략 100~300 cycle(비교 6번 + 곱 2 + `__aeabi_idiv`)로 잡으면 1 ms 당 800~2400 cycle = 1.3~3.8 % CPU. 그래도 더 좋은 설계는 ISR(또는 DMA)이 **원시 코드만** 저장하고 변환은 태스크에서, 과열 경보는 미리 코드로 바꾼 임계값과 정수 비교만 하는 것이다(9. 연습 4).

### 복잡도

| | 시간 | 추가 메모리 | 스택 |
|---|---|---|---|
| `seg_find` | O(log n): 비교 ⌊log2 n⌋+1 이하 (n = 34 → 6) | O(1) | 상수, 재귀 없음 |

## 7. 자주 하는 실수

각 변형을 정답에 한 줄씩 넣어 실제로 돌린 결과다.

**1. 음수에서 `(num + den/2) / den`.** 0 쪽으로 자르는 `/` 와 섞여 음수 결과가 반올림되지 않는다. 실제: 27/37, 무작위 20만 쌍 중 97889개 불일치, NTC 표에서 영하 코드 840개 중 **833개**가 int32 경로와 1 centi 다름(−1017.63 → −1017).

```c
return num >= 0 ? (num + den / 2) / den : -((-num + den / 2) / den);   /* 고침 */
```

**2. 증분 꼴 `y0 + div_round(dy*s, d)`.** 평소엔 맞지만 .5 동점에서 기준점에 따라 결과가 갈린다(5. 풀이). 실제: 33/37 — 무작위 표 303개 불일치, 표를 거꾸로 저장하면 22개 코드가 바뀜, 값이 int32 전 범위인 표에서 `dy` 계산이 int64 로는 되지만 결과가 −1 대신 0. → 가중 평균 꼴로 v 를 한 분수로 만든다.

**3. 32비트로 곱한다.** `(y1-y0)*(q-x0)` 가 3300000 × 2048 에서 넘친다. -O2 는 조용히 −447261, UBSan 은 `signed integer overflow` (5. 풀이 Part B). → 상한을 증명하고 int64, 또는 int32 를 쓰려면 그 표에 대해 상한(800822)을 테스트로 고정.

**4. 포화를 빼먹고 `seg_find` 를 바로 부른다.** 전제(q 가 범위 안)가 깨져 첫/마지막 구간으로 **외삽**된다. 실제: 33/37, 무작위 20601개 불일치. NTC 코드 0(단락)이 163.55 °C 로 나온다 — 고장도 포화도 아닌 그럴듯한 숫자가 제일 위험하다.

**5. `lower_bound` − 1 로 구간을 찾는다.** 값은 맞는다(점에 맞으면 앞 구간의 s = d → y[k]) — 실제로 `lut_eval` 무작위 비교는 0 불일치. 하지만 `seg_find` 의 계약(q = x[0] → 0, 점에 맞으면 그 점에서 시작)이 깨진다: 34/37. q = x[0] 에서 −1 이 되므로 다른 코드가 이 인덱스를 배열 색인에 쓰면 범위 밖 접근이다.

**6. 마지막 점에서 n−2 로 자르기를 잊는다.** q == x[n−1] 이면 i = n−1, `x[i+1]` 은 배열 밖. 이 레슨의 `lut_eval` 은 포화가 먼저라 그 경로에 안 닿아서 `seg_find` 검사만 실패(33/37) — 숨어 있다가 포화 순서를 바꾸는 날 터지는 버그.

**7. 균등 표에서 음수를 `(num + 32) >> 6`.** 음수 오른쪽 시프트는 구현 정의(C11 6.5.7p5)이고 이 맥에선 바닥 쪽이라 −20.5 → −20. 실제: 49개 코드 불일치(예: 코드 3164 에서 −20, 기준 −21), 36/37. → 부호를 떼고 시프트.

**8. `mid = (lo + hi) / 2`.** 이 레슨(n = 34)에선 37/37 그대로다. 넘침은 lo + hi 가 `INT_MAX` 를 넘는 큰 배열에서만 생긴다. 습관으로 `lo + (hi - lo) / 2` (ALGO-B02).

**9. 표 검사를 안 한다.** 생성 스크립트 버그로 같은 키가 두 번 들어가면 d = 0 → 0 나눗셈(정수는 UB, Cortex-M3/M4 는 `DIV_0_TRP` 를 켰을 때만 UsageFault, 기본은 결과 0). Cortex-M0 는 나눗셈이 라이브러리라 `__aeabi_idiv0` 처리에 따른다. 부팅 때 `lut_validate` 한 번, 또는 표 생성기에서 검사.

<summary>Q1. 그냥 float 로 Beta 식을 계산하면 안 되나요? 왜 정수 표인가요?</summary>

FPU 가 없는 Cortex-M0/M0+ 에서는 `log` 가 소프트웨어 부동소수점이라 수천 cycle 대가 될 수 있고(구현마다 다름), 코드 크기도 커진다. M4F 는 단정도 FPU 만 있어 `double` 은 여전히 소프트웨어다. ISR 에서 FPU 를 쓰면 예외 진입 때 FPU 레지스터 저장(lazy stacking)이 붙는다. 정수 표는 실행 시간이 입력과 무관하게 일정하고, 결과가 비트 단위로 재현돼서 PC 에서 같은 코드로 전수 테스트할 수 있다(이 레슨의 0..4095 검사). 또 실제 서미스터는 Beta 식보다 데이터시트 R-T 표가 더 정확해서, **표가 원본 데이터**인 경우가 많다. 꼬리: "M7 이면?" → 배정도 FPU(FPv5-D16)가 있는 칩도 있다. 그래도 데스크톱 측정처럼 FPU 계산이 표보다 빠를 수 있으니 **보드에서 DWT 사이클 카운터로 재고** 고른다.

<details>
<summary>Q2. 중간 곱이 넘치지 않는다는 걸 어떻게 보장하나요? int32 와 int64 중 무엇을?</summary>

가중 평균 꼴 `y0·(d−s) + y1·s` 에서 계수가 0 이상이고 합이 d 이므로 `|분자| ≤ max|y|·d`. 일반 함수(값 int32 전 범위, 키 폭 < 2^31)에서는 < 2^62 → int64. 특정 표에서는 상한을 계산해(NTC: 800822) int32 로 충분함을 증명하고, 그 숫자를 테스트로 고정한다. 이유: M0/M4 모두 64비트 나눗셈은 `__aeabi_ldivmod` 라이브러리 호출이다(asm 확인). 꼬리: "키 폭 제한을 풀면?" → `|dy| < 2^32`, `s < 2^32` → 곱 < 2^64 라 int64 로도 부족하다. 128비트 또는 키를 먼저 줄이는 정규화가 필요하다.

</details>

<details>
<summary>Q3. 음수 결과의 반올림은 어떻게 하나요? C 의 / 와 % 는 음수에서 어떻게 동작하죠?</summary>

C99 부터 `/` 는 0 쪽으로 자르고 `%` 는 피제수의 부호를 따른다(`a == (a/b)*b + a%b`). C89 에서는 음수 나눗셈 방향이 구현 정의였다. 반올림은 부호를 떼서: `n >= 0 ? (n + d/2)/d : -((-n + d/2)/d)`. 동점 규칙은 `floor(v+½)`(정수 이동 불변, 부호 비대칭) 과 0에서 먼 쪽(부호 대칭, 이동 불변 아님) 중 하나를 고르고 문서에 적는다. 후자를 고르면 증분이 아니라 v 를 반올림해야 표 방향과 무관해진다. 꼬리: "동점이 실제로 얼마나 나오나?" → 이 표에서 3856개 중 22개. 드물어서 테스트가 놓치기 쉽다 — 그래서 대칭·역순 불변 같은 **성질 테스트**로 잡았다.

</details>

<details>
<summary>Q4. 표의 점은 몇 개를, 어디에 두나요?</summary>

직선 보간 오차는 `h²/8 · max|f''|`. 곡률이 큰 곳에 점을 촘촘히, 직선에 가까운 곳은 듬성하게. 등온도 간격(5 °C)은 NTC 코드 축에서 자연히 양 끝이 촘촘하다. 더 나아가 허용 오차 E 를 주고 "갈 수 있는 데까지 늘리는" greedy 배치를 하면 같은 최대 오차를 34점 대신 23점으로 낸다(연습 3). 점 수는 결국 메모리 · 오차 · 조회 시간의 타협이다. 꼬리: "센서 자체 오차는?" → 10k NTC 의 B 값 허용차가 보통 ±1~3 %, 저항 허용차도 있어서 표 보간 오차 0.19 °C 보다 센서 오차가 클 수 있다 — 표는 센서 오차의 몇 분의 1 이면 충분하다. 보정(SENS-B06, BMS-B05)이 더 중요하다.

</details>

<details>
<summary>Q5. 이진 탐색, 균등 표, 코드당 1칸 표 중 무엇을 쓰겠어요?</summary>

flash 가 넉넉하면(수백 KB) 코드당 1칸 int16 표(8 KB): 조회 = 메모리 읽기 1번, 오차 = 반올림뿐. flash 가 빠듯하고 ISR 에서 쓰면 균등 2^k 간격: 나눗셈 없음, 실행 시간 상수 — 단 같은 정확도를 내려면 비균등보다 점이 많다(243점 ≈ 7 centi vs 34점 18.6 centi). 메모리 최소 + 정확도면 비균등 + 이진 탐색. 하이브리드도 흔하다: 균등 거친 색인 표로 구간 후보를 O(1) 에 고른 뒤 좁은 범위만 탐색, 또는 직전 구간 기억(연습 1 — 천천히 변하는 입력에서 20만 번 중 이진 탐색 1번). 꼬리: "이 맥에서 double `log` 가 더 빨랐는데?" → 분기 예측 실패와 빠른 FPU 때문. MCU 는 분기 예측기가 단순하거나 없고 FPU 가 없거나 단정도뿐이라 결론이 뒤집힌다 — 타깃에서 잰다.

</details>

<details>
<summary>Q6. 표 밖 값은 어떻게 처리하나요? 외삽하면 안 되나요?</summary>

표 밖은 끝 값으로 **포화 + 상태 코드**. 외삽은 마지막 구간의 기울기를 끝없이 늘리는 것이라 물리적으로 틀린 값이 그럴듯하게 나온다(실수 4: 단락 코드가 163.55 °C). 고장(단락 ≤ 15, 단선 ≥ 4080)은 포화와 구분해 따로 알린다 — 단선을 −40 °C 포화로 처리하면 히터 제어가 폭주한다. 출력 포인터를 고장 시 건드리지 않는 것도 계약이다(호출자가 마지막 정상값을 유지). 꼬리: "고장 판정 임계값은?" → 회로에서 정한다. 풀업 쪽 단선이면 ADC 가 Vref 로 붙고, 실제론 노이즈·오프셋 때문에 4095 가 안 나올 수 있어 여유를 둔다. 디바운스(연속 N 번)와 변화율 검사(plausibility)도 붙인다.

</details>

<details>
<summary>Q7. 이걸 ADC 인터럽트에서 돌려도 되나요? 실행 시간 예산은?</summary>

어림: 64 MHz M0+, 1 kHz × 8채널, 조회당 100~300 cycle 이면 CPU 1~4 %. 가능은 하지만 보통은 ISR/DMA 가 원시 코드만 링 버퍼에 넣고 변환은 태스크에서 한다. 빠른 보호(과열 차단)가 ISR 에 필요하면 **임계값을 부팅 때 코드로 바꿔 두고**(연습 4: 단조 함수 위 이진 탐색으로 정확한 경계 코드) ISR 은 `code <= THR_CODE` 비교 하나만 한다 — 온도 역방향(뜨거우면 코드가 작다)을 주의. 꼬리: "실행 시간은 어떻게 재나?" → Cortex-M3/M4 는 DWT->CYCCNT, M0 는 DWT 사이클 카운터가 없어 GPIO 토글 + 오실로스코프나 SysTick 으로 잰다.

</details>

<details>
<summary>Q8. 조회 때 나눗셈을 아예 없앨 수 있나요?</summary>

구간 기울기를 미리 Q16 고정소수점으로 계산해 두면(`slope = round(dy·65536/d)`) 조회는 곱 1 + 시프트 1 이다(연습 2). 비용: 표가 n−1 워드 늘고, 기울기 양자화 때문에 정확한 나눗셈 결과와 최대 1 centi 차이(이 표에서 14개 코드). 곱의 상한도 다시 증명해야 한다(`|dy|·65536 ≤ 518·65536 < 2^31`). 균등 2^k 간격이면 나눗셈이 원래 시프트다. 상수 나눗셈을 곱셈+시프트로 바꾸는 일반 기법은 ALGO-M15, Q 형식은 C-A09 / DSP-B01.

</details>

<details>
<summary>Q9. 이진 탐색에서 흔히 틀리는 곳은? (꼬리: int 와 size_t)</summary>

`mid = (lo + hi)/2` 의 넘침(큰 배열), 닫힌/반열린 구간 혼용으로 무한 루프, `lower_bound` 와 `upper_bound` 혼동(점에 정확히 맞을 때 구간이 바뀜), 결과를 n−2 로 자르지 않아 `x[i+1]` 범위 밖 읽기. 인덱스 타입: `size_t` 를 쓰면 `lo - 1` 이 0 에서 거대한 수로 감싸지므로(부호 없는 연산, UB 는 아님) `i = lo - 1` 전에 lo > 0 을 확인해야 한다. 이 레슨은 n 이 작아 `int` 로 두고 클램프했다. 이 구간 찾기는 LeetCode 35 Search Insert Position 과 같은 모양(삽입 위치 − 1)이다.

</details>

## 9. 추가 연습

### 연습 1 — 직전 구간 기억 (hint)

온도는 천천히 변한다. `ntc_read_hint(code, &hint, &centi)` 를 만들어 직전 구간 → 이웃 구간 → 그래도 아니면 이진 탐색 순서로 찾아라. 결과는 `ntc_read` 와 항상 같아야 하고, 천천히 변하는 입력에서 이진 탐색으로 떨어지는 비율을 재라.

<details>
<summary>답 보기</summary>

hint 구간이 q 를 담는지(`x[i] <= q < x[i+1]`, 마지막 구간은 오른쪽 끝 포함) 보고, 아니면 i+1, i−1 을 본 뒤 `seg_find`. 표 밖·고장은 본문 함수에 맡긴다. 실제 출력:

```text
[1] hint: mismatches=0, binary searches: walk(codes 1115..2225) 1 / 200000, random 164622 / 200000
```

한 걸음 ±3 코드의 입력(코드 1115..2225, 구간 7개를 오감)에서 이진 탐색은 처음 1번뿐 — 평균 O(1). 무작위 입력에서는 82 %가 탐색으로 떨어져 오히려 비교가 늘어난다. 최악 시간은 그대로 O(log n) 이라 결정성은 유지된다. hint 는 채널마다 따로 둬야 한다(채널 8개가 한 hint 를 공유하면 매번 빗나간다). 디스크 FTL 의 "마지막 매핑 캐시"와 같은 발상이다.

</details>

### 연습 2 — Q16 기울기로 나눗셈 없애기

부팅 때 `SLOPE_Q16[i] = round(dy·65536/d)` 를 계산해 두고, 조회는 `y0 + round(slope·s / 65536)` (시프트) 로 하라. 정확한 나눗셈 결과와 몇 개 코드가, 얼마나 다른지 재라.

<details>
<summary>답 보기</summary>

곱의 상한: `|slope·s| ≤ (|dy|·65536/d + ½)·d ≈ |dy|·65536 ≤ 518·65536 ≈ 3.4e7 < 2^31` → int32. 음수 시프트는 부호를 떼서 반올림. 실제 출력:

```text
[2] q16 slope: codes differing from exact division=14, max diff=1 centi, max |err| vs model=18.58
```

3856개 중 14개가 1 centi 다르고(기울기 양자화 오차 ≤ ½/65536 × s ≤ 0.002 centi 가 .5 경계 근처에서만 반올림을 바꿈) 모델 대비 최대 오차는 그대로 18.58. 대가는 표 33워드 추가. M0 에서 `__aeabi_idiv` 호출이 사라진다.

</details>

### 연습 3 — 허용 오차를 지키는 최소 점 배치

모델 f(코드)와 허용 오차 E 가 주어질 때, 코드 141 에서 시작해 "오차 ≤ E 를 지키며 갈 수 있는 데까지" 구간을 늘리는 욕심쟁이(greedy) 배치를 구현하라. E = 18.22 centi (5 °C 표의 순수 보간 최대 오차)와 E = 5 centi 에서 점 수를 비교하라.

<details>
<summary>답 보기</summary>

현재 점 a 에서 b 를 하나씩 늘리며 `[a, b]` 의 최대 보간 오차를 확인, 넘기 직전의 b 를 다음 점으로. 실제 출력:

```text
[3] greedy knots: tol 18.22 centi -> 23 points (5 C table: 34), tol 5.00 -> 44 points
    tol 18.22 knots: 141 167 199 238 286 345 417 507 618 757 932 1156 1448 1857 2932 3268 3498 3663 3783 3871 3935 3981 3996
```

같은 최대 오차를 34점 대신 23점(−32 %)으로. 가운데(1857..2932)는 한 구간이 1075 코드 — 변곡점 근처라 거의 직선이다. 이 greedy 는 "구간 [a,b] 가 되면 그 안의 부분 구간도 된다"는 성질이 있을 때 점 수가 최소다. 볼록/오목한 부분에서는 이 성질이 성립하고(부분 구간의 현이 원래 현과 곡선 사이에 있다), 변곡점을 끼면 일반적으론 보장되지 않는다 — 여기서는 검증만 했다. 표 생성기(PC)에서 돌리는 오프라인 작업이라 O(N·h²) 비용은 상관없다.

</details>

### 연습 4 — 경보 임계값을 ADC 코드로 (ISR 에서는 비교만)

"85.00 °C 이상이면 경보" 를 ISR 에서 `code <= THR` 비교 하나로 하고 싶다. `alarm_code(thr_centi)` 를 만들어라: `ntc_read` 값이 thr 이상인 **가장 큰 코드**. 모든 임계값(−39.99..125.11 °C, 0.01 °C 단위)과 모든 코드에서 코드 비교와 온도 비교가 같은 결정을 내는지 확인하고, 역보간 `lut_eval({NTC_CENTI, NTC_CODE}, thr)` 추정치와 비교하라.

<details>
<summary>답 보기</summary>

`ntc_read` 값은 코드에 대해 단조 감소이므로(5. 풀이: 반올림은 단조 함수라 단조성을 보존) "value(c) ≥ thr" 는 앞쪽이 참, 뒤쪽이 거짓인 술어다 → 첫 거짓을 이진 탐색(ALGO-B02 의 first-true 모양, ALGO-B04 의 "답을 이분 탐색")하고 1을 뺀다. 실제 출력:

```text
[4] alarm_code: 16511 thresholds, wrong decisions=0; inverse-LUT estimate differs in 6330 (max 1 code)
    85.00 C -> code <= 401, 87.50 C -> code <= 375 (inverse estimate 375)
```

정의상 정확하고(결정 불일치 0), 역보간 추정은 38 %의 임계값에서 1 코드 어긋난다 — 정방향 결과가 반올림된 계단 함수라 역함수 보간과 경계가 미세하게 다르기 때문. 1 코드는 0.02~0.3 °C 라 실무에선 보통 무시해도 되지만, "온도로 보면 85.00 인데 경보가 안 울렸다" 같은 경계 버그 리포트를 없애려면 정확한 쪽을 부팅 때 한 번(이진 탐색 12번 × `ntc_read`) 계산해 둔다. 해제 임계값(예: 80.00 °C)도 같은 방법으로 코드화하면 히스테리시스까지 ISR 에서 정수 비교 둘로 끝난다.

</details>

## 10. 핵심 정리

- 구간 찾기 = **upper_bound(q) − 1**, n−2 로 자르기. 불변식 "[0,lo) ≤ q, [hi,n) > q". 키 방향은 `x[0] < x[n-1]` 로 판단. O(log n), 비교 ⌊log2 n⌋+1 이하.
- **포화가 먼저**(탐색의 전제), 고장(단락/단선)은 포화보다 먼저. 외삽 금지, 상태 코드로 알린다.
- 보간은 가중 평균 꼴 `(y0·(d−s) + y1·s)/d`: `|분자| ≤ max|y|·d < 2^62`, `y1 − y0` 넘침 없음, v 자체를 반올림하므로 표 방향·부호에 무관.
- C 의 `/` 는 0 쪽 자르기(C11 6.5.5p6), 음수 `>>` 는 구현 정의(6.5.7p5) → 반올림은 부호를 떼서 `(|n| + d/2)/d`.
- int32 를 쓰려면 그 표의 상한을 숫자로 증명하고 테스트로 고정(NTC: 800822). 64비트 나눗셈은 M0·M4 모두 라이브러리 호출, M4 의 `SDIV` 는 32비트만.
- 검증 = double 모델 대비 **입력 전 범위**(0..4095) + 성질 테스트(대칭·역순·단조) + 독립 기준 구현. 비균등 34점 18.6 centi, 균등 62점 98 centi, 1칸 표 0.5 centi(8 KB).
- 오차 상한 h²/8·max|f''| → 곡률 큰 곳에 점을 촘촘히. 오차 기준 greedy 배치로 23점.
- ISR 에는 원시 코드 저장 + 코드 도메인 임계 비교만. 변환은 태스크에서. 데스크톱 벤치로 MCU 를 판단하지 않는다.

- Arm, *Cortex-M4 Technical Reference Manual* — 명령 타이밍(SDIV/UDIV 2~12 cycle), FPv4-SP 단정도 FPU: <https://developer.arm.com/documentation/100166/latest/>
- Arm, *Cortex-M0 Technical Reference Manual* / *ARMv6-M Architecture Reference Manual* — 나눗셈 명령 없음, MULS 1/32 cycle 구현 옵션.
- Arm, *Run-time ABI for the Arm Architecture* (RTABI) — `__aeabi_idiv`, `__aeabi_ldivmod`, `__aeabi_lmul`: <https://github.com/ARM-software/abi-aa>

- AlgoMonster 노트 M02 §2 First True · §4 First Element Not Smaller Than Target (Don 정리본) — 경계 이진 탐색 템플릿. 보간 자체는 소스에 없는 임베디드 응용.
- LeetCode 35 Search Insert Position — 구간 찾기와 같은 모양.
- 관련 레슨: ALGO-B02 (lower/upper_bound), ALGO-B04 (답을 이분 탐색 — 연습 4), ALGO-M15 (상수 나눗셈·정수 산술), C-A09 (Q15 고정소수점·포화), DSP-B01 (Q 형식), ARM-B07 (SDIV/UMULH), CPP-M13 (constexpr 로 표를 .rodata 에 생성), SENS-B01 (ADC 코드 → 공학 단위), SENS-B06 (다항식 보정·서미스터 선형화), BMS-B05 (NTC 변환과 센서 고장 검출), BM-M07 (ADC 드라이버 보정).
