웹 서비스화 계획표: 임베디드 스터디 노트 + 브라우저 에디터 (2026-11-08)

아이디어: 지금 맥/Lima/QEMU로 하는 실습 환경을 서버에 올리고, 스터디 노트를 인터넷에서 서비스한다. 문제를 읽다가 브라우저 에디터에서 바로 코드를 쓰고 실행한다.

결론부터: 가능하다. 다만 "읽기 사이트"와 "코드 실행 서비스"는 난이도와 비용이 완전히 다르므로, 단계를 쪼개서 가야 한다. 코드 실행은 남의 코드를 내 서버에서 돌리는 일이라 보안·남용 방지가 비용의 대부분이다.

쓰는 법

  • 단계(Phase)는 앞 단계만으로도 가치가 있게 나눴다. 중간에 멈춰도 손해가 없다.
  • 맨 아래 결정이 필요한 것 4가지에 답하면 Phase 0~1을 바로 시작할 수 있다.
  • 가격은 2026-11 기준 대략값이다. 결제 전에 각 업체 페이지에서 확인한다.

2. 시스템 그림#

그림은 4장이다. 위에서 아래로 "전체 구조 → 실행 한 번의 흐름 → 단계별 성장 → 콘텐츠가 사이트가 되는 길" 순서다.

2-1. 전체 구조 (최종 형태, Phase 3 이후)#

점선 박스가 한 덩어리의 책임이다. ①에서 시작해 ②를 거쳐 ④까지 간다. 읽기만 하는 사용자는 ②의 Pages에서 끝나고 서버 비용이 들지 않는다.

읽는 법: 초록색은 비용이 거의 안 드는 부분, 노란색은 보안·남용 방어, 파란색은 사용자가 만지는 부분이다. 서버(④)는 "실행"만 담당하고, 계정·진행도(③)와 분리돼 있어 서버가 뚫려도 DB 비밀이 없다.

2-2. ▶ 실행 버튼을 눌렀을 때 (서버 경로 B)#

핵심은 ③에서 봇·한도 검사를 통과한 요청만 서버에 닿고, ⑦에서 실행마다 새 컨테이너를 쓴다는 점이다. 이전 사용자의 파일이나 프로세스가 남지 않는다. 경로 A(WASM)는 ②에서 끝나고 서버를 거치지 않는다.

2-3. 단계별 성장#

2-4. 콘텐츠가 사이트가 되는 길 (기존 파이프라인 위에 올라탐)#

이미 있는 curriculum → lessons → build_site.py 흐름이 그대로 서비스의 뼈대다. 레슨 폴더의 starter.*와 solution.*에 테스트 하네스가 들어 있어서, 실행 서버는 새로 만들 것 없이 이 파일을 그대로 실행하면 된다. 즉 서비스화의 진짜 병목은 서버가 아니라 레슨이 아직 92개뿐이라는 점이다.

4. 보안: 서버 실행에서 반드시 막을 것#

남의 코드를 컴파일하고 실행한다는 건 원격 코드 실행을 일부러 열어두는 것이다.

위협대책
서버 탈취·호스트 탈출gVisor 또는 microVM으로 격리, 컨테이너 root 금지, 읽기 전용 파일시스템 + tmpfs 작업 디렉터리
무한 루프·메모리 폭탄CPU 시간 5~10초, 메모리 256MB, 프로세스 수·파일 크기 제한 (isolate/cgroup)
암호화폐 채굴·스팸네트워크 완전 차단 (egress 없음), 실행 시간 제한, 로그인 필수
포크 폭탄pids 제한
비용 폭탄사용자당 일일 실행 횟수 제한, 전체 동시 실행 상한, 큐
내 서버의 다른 비밀실행 서버를 다른 서비스와 분리, 비밀키 없는 전용 VPS

QEMU 항목은 "게스트 안에서 돌린다"는 이중 격리라 상대적으로 안전하지만, 컨테이너 격리는 그대로 해야 한다.

5-1. 병행 트랙 C: 문제(레슨) 생성 — 서비스의 진짜 본체#

서버는 몇 주면 만들지만, 콘텐츠는 지금 2191개 중 92개(4%)뿐이다. 서비스를 열어도 대부분이 "준비중"이면 가치가 없으므로, 이 트랙이 Phase 0~5와 동시에 계속 도는 상시 액션 아이템이다.

트랙작성됨 / 전체비고
C41 / 41✅ 완료
DS28 / 39Basic · Mid 완료, Advanced 남음
CPP14 / 38Basic 완료

액션 아이템

  1. 서비스 호환 규약 확정 (먼저, 반나절): 새 레슨의 starter.*가 서비스에서 그대로 실행되게 규칙을 정한다.
    • 단일 파일, 외부 입력 없이 main에서 시작해 stdout으로 PASS / FAIL: <이유>를 출력하고 종료 코드로 판정
    • 파일·네트워크·시간 의존 금지 (결과가 항상 같아야 함)
    • 레슨 front matter에 runner: wasm | server | local 필드 추가 (wasm=브라우저 가능, server=qemu/verilator 필요, local=맥 전용)
  2. 작성 순서 (우선순위): 면접·목표 직무 직결 → 서비스에서 실행 가능한 것 순서.
    • 1순위: SIV · MEM · TEST · RTOS · ARCH · BM (실리콘 검증·펌웨어, mac/qemu)
    • 2순위: PCIE · PLAT · SEC · ARM · RISCV · RTLDV
    • 3순위: 나머지 (AI 가속기·로보틱스·퀀트·시스템 설계 등)
    • 마지막: linux env 133개 (서비스 범위 밖이면 "로컬 가이드형"으로 작성)
  3. 배치 단위로 병렬 작성: 트랙 하나(30~40개)를 NOTES_SPEC과 트랙별 WRITER_BRIEF로 에이전트에 나눠 맡기고, verify_lessons.py가 통과해야 머지한다 (지금까지의 C · DS · CPP 방식 그대로).
  4. 공개 전 저작권 점검: 레슨마다 외부 문장 인용이 없는지 훑는다. 유료 강의(AlgoMonster, 퀀트 코스)에서 온 문제는 문제 본문을 새로 작성한다.
  5. 진행도 지표: 사이트 허브의 "학습가능" 숫자를 공개 기준으로 삼는다. 제안: 전체의 30%(약 650개)가 되면 Phase 0 공개, 100%까지는 점진적으로.

공개 시점 제안: 콘텐츠가 0이어도 Phase 0~1은 시작할 수 있다 (도메인과 환경 검증은 콘텐츠와 무관). 단 불특정 공개는 학습가능 30% 이후를 권장한다.

최소 가치 순서: Phase 0만으로도 "어디서든 읽는 사이트", Phase 1만으로도 "어디서든 실습하는 내 환경", Phase 2까지면 "문제 옆에서 바로 실행"이다. Phase 3 이후는 사용자를 받을 때만 의미가 크다.
