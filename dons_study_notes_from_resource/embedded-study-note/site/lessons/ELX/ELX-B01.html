부트 플로우 지도: ROM→SPL→U-Boot→Kernel→init

Basic⏱ 70분env: mac#boot#spl#u-boot#initupdated 2026-11-15
목표 SoC 전원 인가부터 사용자공간 init까지 각 단계의 책임·로드 위치·전달 인자를 설명할 수 있다.
과제 제공된(또는 QEMU에서 캡처한) UART 부트 로그를 단계별(BootROM/SPL/U-Boot/kernel/init)로 분할하고 각 단계 소요시간·로드 주소·bootargs를 추출하는 Python 파서를 작성해 타임라인 표로 출력한다.
내 상태

학습 목표#

  • 전원 ON부터 PID 1까지 각 단계가 어디서 실행되고, 다음 단계를 어디에 올리고, 무엇을 넘기는지 표 하나로 말할 수 있다 (arm64: x0 = DTB 물리 주소, bootargs는 /chosen).
  • UART 로그 한 덩어리를 단계별로 잘라 시작·끝 시각, 줄 수, 로드 주소, bootargs, 커널 버전을 뽑는 파서를 Python으로 쓴다.
  • 실제 로그의 함정 — CR 덮어쓰기, ESC 제어열, 깨진 바이트, 콘솔이 켜질 때 몰아서 나오는 커널 줄, printk 시각 리셋 — 을 테스트로 다룬다.
  • 부트 루프 로그를 부팅별로 나누고 "어느 단계에서 왜 죽었나"를 기계적으로 뽑는다 (bring-up 첫날 하는 일).

1. 문제#

보드 bring-up 첫날 손에 쥐는 것은 UART 로그 하나다. "어디까지 갔고 어디서 멈췄나, 시간은 어디서 새나"를 그 로그로 답하는 능력이 임베디드 리눅스 면접의 단골 첫 질문("전원 켜면 무슨 일이 일어나나요?")과 실무 디버깅을 동시에 덮는다.

환경: 로그 파서(starter/solution/practice)는 맥의 Python 3.9 표준 라이브러리만 쓴다. 입력 로그 중 2개는 이 랩에서 실제로 캡처했다 — Lima VM elinux(aarch64, TCG 에뮬레이션) 위 qemu-system-aarch64 -machine virt,secure=on -cpu cortex-a57 -smp 1 -m 1057, TF-A v2.15.0 → U-Boot 2026.10 → Linux 6.18.55 → BusyBox /init. 나머지 2개는 i.MX8M Plus 스타일로 손으로 쓴 합성(synthetic) 로그다 (QEMU에는 SPL·DDR training이 없어서). TCG 시각은 실제 하드웨어 시간이 아니다 — 순서와 비율만 본다.

부팅은 릴레이 경주다. 각 주자는 자기가 아는 최소한만 초기화하고, 다음 주자를 더 큰 메모리에 올려 놓고 바통(인자)을 넘긴다. 아래 그림의 주소는 이번 레슨에서 캡처한 QEMU 로그와 TF-A/U-Boot 소스에서 확인한 값이다.

  • BootROM: 칩에 구워진 코드. 부트 핀(boot mode)을 읽어 eMMC/SD/SPI NOR/USB 중 하나에서 작은 다음 단계를 칩 내부 SRAM(OCRAM)에 읽는다. 보통 UART에 아무것도 안 찍는다 → 로그에서는 "전원 ON부터 첫 줄까지의 침묵"으로만 보인다.
  • SPL(Secondary Program Loader): SRAM(수백 KB)에 들어갈 만큼 작은 U-Boot. 핵심 일은 DDR 초기화(training) 와 다음 이미지 로드. arm64 SoC에서는 그다음에 TF-A BL31(EL3 보안 모니터)과 U-Boot 본체를 올린다. QEMU virt에는 SPL이 없고, TF-A의 BL1+BL2가 그 역할을 한다 (TF-A 문서 용어로 BL1 = "AP Trusted ROM").
  • U-Boot: 장치 초기화, 환경 변수, 저장 매체에서 Image/DTB/initrd 로드, booti로 점프. U-Boot 환경·FIT은 ELX-M12에서 다룬다.
  • kernel: head.S가 x0의 DTB 주소를 보관하고 MMU를 켠 뒤 start_kernel. DTB의 /chosen/bootargs가 커널 command line이 된다. 마지막에 /init(initramfs) 또는 /sbin/init(디스크 rootfs)을 실행한다.
  • init: 첫 사용자 공간 프로세스(PID 1). BusyBox init이든 systemd든 여기서부터 사용자 공간이다 (ELX-B04 initramfs, ELX-B13 systemd).

Part A — 한 줄 정리 + 단계 상태 기계 + 타임라인#

capture_boot.py(이 레슨 폴더)는 QEMU 시리얼의 각 줄 앞에 grabserial 스타일 호스트 시각 [ abs_s delta_s] 를 붙인다 (abs = QEMU를 띄운 순간 = "전원 ON"부터 경과 초, delta = 직전 줄과의 차이). U-Boot·TF-A 줄에는 자체 시각이 없기 때문이다. 커널 줄은 그 뒤에 다시 printk 시각 [ 0.000000]을 갖는다.

  1. clean_text(s) — 터미널에 실제로 보이는 글자만 남긴다: ESC 제어열 제거, 줄 끝 CR/LF 제거, 줄 중간 CR = 0열로 돌아가 덮어쓰기, 깨진 바이트 제거.
  2. parse_line(raw) → Line(no, host, ktime, text) — 호스트 시각과 printk 시각을 떼어 낸다.
  3. step(state, line) — 단계 상태 기계: 표지(marker) 줄로 단계를 앞으로만 옮기고, 핸드오프 줄("Starting kernel ...", "Run /init as init process")을 경계로 쓴다.
  4. parse_boot_log(text) → 단계 6개의 시작/끝/길이/줄 수. 출력은 format_timeline()이 표로 그린다.

Part B — 정보 추출과 가장자리 경우#

  • extract_info(text) — TF-A/U-Boot/커널 버전, Kernel command line:(= 커널이 실제로 받은 bootargs), init 경로, U-Boot 환경의 주소(kernel_addr_r=0x40400000, fdtcontroladdr=8054cce0 — 0x가 없어도 16진수), booti가 찍는 주소(Loading Ramdisk to, Loading Device Tree to, Moving Image from), => booti ${kernel_addr_r} ...의 ${var} 풀기, 커널 printk 시계 0의 호스트 시각 추정.
  • 가장자리: 펌웨어 단계가 없는 로그(QEMU -kernel 직접 부팅), 호스트 시각이 없는 로그, 캡처가 커널 중간부터 시작된 로그, CRLF/LF, 전원 ON 순간의 쓰레기 바이트, printk 시각 리셋.

Part C — 부트 루프 로그 진단#

합성 로그 imx8mp_bootloop_synthetic.log에는 부팅이 3번 들어 있다: ① rootwait가 빠진 bootargs로 커널 패닉 → 워치독 리셋 ② SPL이 eMMC를 못 읽고 멈춤 → 전원 재투입 ③ 정상 부팅. split_boots()로 나누고 diagnose()로 부팅마다 "마지막 단계, init 도달 여부, 첫 치명 줄, bootargs"를 뽑는다.

2. Problem (English)#

Boot-log timeline parser.

You are given a UART capture of an embedded Linux board. Each line may carry a host timestamp prefix [abs delta] added by the capture tool, and kernel lines additionally carry a printk timestamp [ s.uuuuuu]. Raw bytes may include CRLF, mid-line carriage returns (progress counters), ANSI escape sequences and garbage bytes.

  1. Implement clean_text, parse_line and a stage state machine step that assigns every non-empty line to one of BootROM, SPL, BL31, U-Boot, kernel, init. Stages only move forward within a boot; a firmware banner seen again, a stage marker earlier than the current stage, or a printk timestamp that jumps backwards starts a new boot. Handoff lines (BL1: Booting BL31, Starting kernel ..., Run <path> as init process) belong to the outgoing stage, and their timestamp is the start of the next stage.
  2. parse_boot_log(text, boot=0) returns one row per stage: present, start, end, dur, lines, first_no, first_text, note. BootROM prints nothing: infer it as [0, first stage start) for the first boot when host timestamps exist. If there is no Starting kernel ... handoff, the kernel starts at min(first arrival, min(host - printk)).
  3. extract_info returns versions, bootargs (from Kernel command line:), init path, U-Boot env addresses and booti load addresses as ints.
  4. split_boots / diagnose handle a capture that contains a boot loop: for each boot report the last stage reached, whether init was reached, the first fatal line, and the bootargs.

Example: for the captured QEMU log the timeline is BootROM 0.000–0.176 (inferred), SPL 0.176–0.196, BL31 0.196–0.212, U-Boot 0.212–0.562, kernel 0.562–1.714, init 1.714–1.858, and bootargs == "console=ttyAMA0 b01_from=uboot LAB_CMD=cat~/proc/cmdline".

capture_boot.py가 하는 일 (expect 대신 파이썬으로 같은 일을 한다 — 시각 도장까지 한 번에 붙이려고):

  • -device loader,file=/var/lab/out/Image,addr=0x40400000, -device loader,file=initramfs.cpio.gz,addr=0x44000000 — 리셋 전에 RAM에 바이트만 복사한다(PC는 안 바꾼다). 실제 보드의 fatload mmc ...를 대신한다.
  • Hit any key가 보이면 스페이스 → => 마다 printenv kernel_addr_r ramdisk_addr_r fdtcontroladdr, setenv bootargs "console=ttyAMA0 b01_from=uboot LAB_CMD=cat~/proc/cmdline", booti ${kernel_addr_r} ${ramdisk_addr_r}:0x1277e2 ${fdtcontroladdr} (0x1277e2 = initramfs 1210338바이트).
  • LAB_CMD=는 랩 initramfs의 /init이 실행하고 poweroff -f 하는 명령이다 → 여기서는 cat /proc/cmdline으로 bootargs가 사용자 공간까지 왔는지 찍고 끝난다. 그래서 ROM 자리부터 init까지 한 번에 끝까지 간다.
  • 줄 내용은 손대지 않는다: CR, ESC가 그대로 남는다 (file 결과: ASCII text, with CRLF, CR line terminators, with escape sequences).

4. 힌트#

힌트 1 — 호스트 접두어는 정리하기 전에 뗀다

U-Boot 카운트다운 줄의 실물은 [ 0.394029 0.052090] ESC[2K CR Hit any key to stop autoboot: 2 ESC[2K CR Hit any key to stop autoboot: 0 CR이다. CR 덮어쓰기를 먼저 하면 줄 맨 앞의 [ 0.394029 ...]가 지워진다. 접두어는 캡처 도구가 붙인 ASCII이므로 원문에서 먼저 떼고, 나머지만 clean_text.

힌트 2 — CR 은 "0열로 돌아가 덮어쓰기"

screen = ""; for seg in s.split("\r"): screen = seg + screen[len(seg):] — 뒤 조각이 짧으면 앞 조각의 꼬리가 남는다("abcdef\rXY" → "XYcdef"). 줄 끝의 \r\n은 먼저 떼야 빈 조각이 화면을 지우지 않는다.

힌트 3 — 표지 없는 printk 줄의 단계

[ 1.163490] reboot: Power down처럼 init 이후에도 커널 줄이 나온다. "printk 시각이 있으면 kernel"은 현재 단계가 kernel보다 앞일 때만 적용한다. 단계는 앞으로만 간다.

힌트 4 — 새 부팅을 알아보는 세 신호

① 지금 단계보다 앞 단계의 표지(커널 다음에 U-Boot SPL ...) ② 이 부팅에서 이미 본 배너가 또 나옴(SPL에서 멈췄다가 다시 U-Boot SPL ... — 단계 번호는 같아서 ①로는 못 잡는다) ③ printk 시각이 0.1 s 넘게 뒤로 감(펌웨어 출력 없이 커널만 다시 시작: kexec, 잘린 캡처).

힌트 5 — 커널 시작 시각은 첫 커널 줄의 도착 시각이 아니다

Starting kernel ...은 0.562 s인데 [0.000000] Booting Linux 줄은 0.918 s에 도착한다. 콘솔 드라이버가 등록되기 전의 printk는 버퍼에 쌓였다가 몰아서 나오기 때문이다. 핸드오프 줄이 있으면 그 시각을 쓰고, 없으면 min(host − printk)로 printk 0의 호스트 시각을 추정한다.

Part A — 단계 상태 기계#

표지는 줄 맨 앞에 고정(^) 한다. U-Boot \d{4}\.\d{2}는 U-Boot SPL 2024.04와 겹치지 않고, 줄 중간에 "U-Boot"가 들어간 사용자 공간 출력에도 걸리지 않는다.

NOTICE: BL1: Booting BL31은 재미있는 줄이다. BL2(S-EL1)는 BL31을 직접 부를 수 없어서 SMC로 BL1(EL3)에 돌아가고, BL1이 다시 찍은 뒤 BL31로 간다 (bl1/bl1_main.c의 NOTICE("BL1: Booting BL31\n")). 그래서 BL2 줄 다음에 BL1 줄이 또 나온다 — SPL 안에서 일어나는 일이므로 SPL에 남기고, 그 시각(0.196010)을 BL31 시작으로 쓴다.

커널 t0 추정이 왜 min인가. 커널 줄 하나의 host − printk는 "printk 시계 0의 호스트 시각 + 그 줄이 늦게 도착한 만큼"이다. 콘솔 등록 전에 쌓였다가 몰아서 나온 줄은 늦게 도착한 만큼 값이 크고, 실시간으로 나온 줄은 작다. 그래서 최솟값이 가장 좋은 추정이다 (그래도 줄 전송 시간만큼은 늦다). 실측: 0.693177 (157행 ACPI: Interpreter disabled. 0.977495 − 0.284318). 검산: 0.693177 + 1.016896(Run /init의 printk) = 1.710073 ≈ 실제 도착 1.713714. 합성 로그는 참값을 알고 있다 — 생성기 기준 printk 0 = 2.540215, 추정 2.545337 → 5.1 ms 늦게 추정된다(115200 baud에서 줄 하나 보내는 시간 정도).

"Starting kernel ..."(0.562)과 printk 0(0.693) 사이 131 ms는 커널이 printk 시계가 돌기 전에 한 일이다 — head.S(부트 인자 보관, 페이지 테이블, MMU on), setup_arch의 앞부분. 이 구간의 printk는 모두 [ 0.000000]으로 찍힌다(아래 로그의 sched_clock 줄부터 시각이 움직인다). TCG 에뮬레이션 시간이라 실제 칩에서는 훨씬 짧다.

(실측 로그 발췌, 107·148행 부근. 42~148행의 107줄 — printk 0.000000~0.222258 — 이 호스트 0.918~0.959 s, 약 41 ms 동안 한꺼번에 나왔다. 콘솔 등록 뒤의 줄부터 host − printk ≈ 0.69로 일정해진다.)

U-Boot booti는 initrd와 DTB를 RAM 위쪽(U-Boot 자신 0x8158_f000 바로 아래)으로 옮기고, DTB의 /chosen에 bootargs(boot/fdt_support.c fdt_chosen)와 linux,initrd-start/end(fdt_initrd)를 써 넣은 뒤, arm64에서는 arch/arm/lib/bootm.c:280의 armv8_switch_to_el2((u64)images->ft_addr, 0, 0, 0, ...)로 점프한다 → x0 = DTB 주소, x1~x3 = 0. 커널 쪽에서는 arch/arm64/kernel/head.S의 preserve_boot_args가 mov x21, x0 // x21=FDT로 받아 __fdt_pointer에 저장하고, setup.c:372는 x1~x3이 0이 아니면 WARNING: x1-x3 nonzero in violation of boot protocol을 찍는다. drivers/of/fdt.c:1116의 early_init_dt_scan_chosen이 /chosen/bootargs를 읽어 command line이 된다.

booti가 Image를 옮기는 규칙은 U-Boot arch/arm/lib/image.c의 booti_setup()에 있다: Image 헤더 flags의 bit 3("2 MB 정렬만 맞으면 물리 메모리 어디든")이 켜져 있으면 ALIGN(load − text_offset, 2 MiB) + text_offset, 꺼져 있으면 DRAM 시작. 랩 Image 헤더는 text_offset=0, image_size=0x2980000, flags=0xa(bit 3 켜짐)라서 0x4040_0000은 그대로, 0x4048_0000은 0x4060_0000으로 옮겨진다 (추가 연습 2).

8. 면접 Q&A#

Q1. arm64 보드에서 전원을 켜면 셸이 뜰 때까지 무슨 일이 일어나나요? 왜 SPL이 따로 있나요?

BootROM이 부트 핀을 보고 매체에서 SPL을 칩 내부 SRAM에 읽어 실행 → SPL이 클럭·PMIC·DDR training을 하고 BL31(TF-A, EL3)과 U-Boot를 DRAM에 로드 → BL31이 보안 설정 후 U-Boot를 Non-secure EL2/EL1로 → U-Boot가 Image·DTB·initrd를 로드하고 booti → 커널이 드라이버를 올리고 rootfs를 마운트한 뒤 /init 또는 /sbin/init 실행. SPL이 따로 있는 이유: 리셋 직후엔 DRAM이 안 살아 있고 SRAM은 수백 KB라 U-Boot 본체(MB 단위)가 안 들어간다. 꼬리질문 "QEMU virt에서는?" → ROM·DDR training이 없다. CPU가 secure flash 0번지의 TF-A BL1에서 리셋되고, BL2가 BL31을 secure SRAM(0x0e00_0000대)에, U-Boot를 DRAM 0x6000_0000에 올린다(이 레슨 실측 로그와 plat/qemu/qemu/include/platform_def.h).

Q2. 부트로더가 arm64 커널에 넘기는 것은 정확히 무엇인가요?

Documentation/arch/arm64/booting.rst의 약속: x0 = DTB 물리 주소, x1 = x2 = x3 = 0, MMU off, D-cache off(이미지 영역은 clean), 인터럽트 마스크, EL2(권장) 또는 non-secure EL1, Image는 2 MB 정렬 + text_offset. U-Boot는 armv8_switch_to_el2(ft_addr, 0, 0, 0, ...), 커널은 head.S에서 mov x21, x0로 받는다. 꼬리질문 "x1이 0이 아니면?" → setup.c가 WARNING: x1-x3 nonzero in violation of boot protocol을 찍는다(부팅은 계속). "32비트 ARM은?" → r0=0, r1=machine type, r2=ATAGS 또는 DTB 주소. bootargs·initrd 위치는 레지스터가 아니라 DTB의 /chosen(bootargs, linux,initrd-start/end)으로 간다.

Q3. U-Boot의 bootargs는 어떤 경로로 커널과 사용자 공간까지 가나요?

U-Boot 환경 bootargs → fdt_chosen()이 DTB /chosen/bootargs에 기록 → 커널 early_init_dt_scan_chosen()이 읽어 boot_command_line → Kernel command line: 출력 → 커널 파라미터로 처리되고, 커널이 모르는 a=b 꼴은 init의 환경 변수(envp_init)로, = 없는 것은 argv(argv_init)로 넘어간다 (init/main.c unknown_bootoption)(Unknown kernel command line parameters "...", will be passed to user space.). 실측: b01_from=uboot LAB_CMD=...가 그렇게 넘어가 /proc/cmdline에도 그대로 보였다. 꼬리질문 "setenv bootargs를 했는데 반영이 안 된다" → bootcmd가 run mmcargs 같은 스크립트로 bootargs를 덮어쓰는 경우가 흔하다. 커널 쪽 CONFIG_CMDLINE_FORCE도 DT 값을 무시한다. 로그의 Kernel command line:이 진실이다 (추가 연습 5).

Q4. "Starting kernel ..." 다음에 아무것도 안 나옵니다. 어떻게 좁히나요?

커널 콘솔이 켜지기 전에 죽었을 가능성이 크다(이 레슨 실측에서도 그 구간이 356 ms 침묵이었다). 순서: ① earlycon(예: earlycon=pl011,0x9000000, i.MX earlycon=ec_imx6q,0x30890000)을 bootargs에 넣어 초기 printk를 바로 보이게 ② console= 이름 오타(ttyAMA0/ttymxc1/ttyS0) ③ DTB가 이 보드 것인지, UART 노드·/memory가 맞는지 ④ 로드 영역 겹침 — Image의 image_size가 커져 DTB/initrd를 덮는지(추가 연습 3) ⑤ 커널 config에 그 UART 드라이버가 built-in인지 ⑥ JTAG로 PC가 어디서 도는지, 또는 리셋 후 U-Boot에서 __log_buf(System.map 주소)를 md로 덤프. 꼬리질문 "printk는 버퍼에 있는데 왜 안 보이나" → 콘솔 드라이버 등록 전 printk는 링 버퍼에만 쌓인다.

Q5. 부팅 시간을 재려고 dmesg 시각을 그대로 쓰면 무엇이 빠지나요?

① 커널 이전 전부(ROM, SPL DDR training, U-Boot, 이미지 로드) ② 커널 진입부터 sched_clock 등록까지(모두 0.000000) ③ UART 출력 비용. 그래서 외부 기준 시계(grabserial 같은 캡처 도구, 또는 GPIO 토글 + 로직 분석기)로 재고, 커널 내부는 printk/initcall_debug로 쪼갠다(ELX-A08). 꼬리질문 "115200 baud가 부팅을 늦추나?" → 초당 약 11.5 KB라 80자 줄 하나에 약 7 ms. 콘솔 출력이 동기식이면 그대로 부팅 시간이 된다 → 양산 이미지는 quiet/loglevel을 쓴다. 이 레슨 합성 로그도 그 모델로 만들었다.

Q6. TF-A의 BL1/BL2/BL31/BL32/BL33은 각각 무엇이고, BL31은 왜 부팅 후에도 남아 있나요?

BL1 = AP Trusted ROM(EL3, 리셋 벡터), BL2 = Trusted Boot Firmware(다음 이미지 로드·검증, 보통 S-EL1 또는 EL3), BL31 = EL3 Runtime Firmware(보안 모니터), BL32 = Secure-EL1 Payload(OP-TEE 같은 TEE, 선택), BL33 = Non-trusted Firmware(U-Boot/UEFI). 실제 SoC는 BL1 대신 자체 ROM을, BL2 대신 U-Boot SPL을 쓰는 경우가 많다(i.MX8M: ROM → SPL → BL31 → U-Boot). BL31이 남는 이유: PSCI(CPU on/off, suspend, SYSTEM_OFF/RESET)를 SMC로 서비스해야 한다. 이 레슨 실측 로그의 마지막 줄 ERROR: QEMU System Power off: with GPIO.가 그 증거 — 리눅스가 poweroff로 PSCI SYSTEM_OFF를 부르자 BL31이 찍었다.

Q7. initramfs의 /init과 디스크 rootfs의 /sbin/init은 어떻게 고르나요? "No working init found"는 언제 나오나요?

initramfs가 있으면 커널은 rdinit=(기본 /init)을 실행한다(init/main.c의 ramdisk_execute_command). 없거나 실패하면 root=의 rootfs를 마운트하고 init= 또는 /sbin/init, /etc/init, /bin/init, /bin/sh 순으로 시도, 모두 실패하면 panic("No working init found. ..."). 꼬리질문 "rootwait은 왜?" → eMMC/USB처럼 늦게 probe되는 장치는 루트 마운트 시점에 아직 없을 수 있다. rootwait이 없으면 Part C 부팅 1처럼 VFS: Unable to mount root fs로 패닉한다. init이 종료하면 Attempted to kill init! 패닉(ELX-B04에서 실제로 본다).

Q8. 고객사에서 "가끔 재부팅 루프"라며 2 MB짜리 UART 로그를 보냈습니다. 어떻게 분석하나요?

① 배너(TPL/SPL/TF-A/U-Boot/Linux)와 printk 리셋으로 부팅 단위로 자른다 ② 부팅마다 마지막 도달 단계와 첫 치명 줄(panic, abort, failed to boot, Please RESET)을 표로 ③ 성공 부팅과 실패 부팅의 차이(bootargs, Reset cause:, 온도·전압 줄, DDR training 결과, 커널 버전/슬롯)를 비교 ④ 리셋 원인 분류: 워치독(실패 뒤 일정 간격으로 재시작), 브라운아웃(로그 중간이 끊기고 바로 ROM 배너), 소프트웨어 reboot(reboot: 줄). 이 레슨의 diagnose()가 ①②를 자동화한다. 꼬리질문 "A/B 슬롯이면?" → U-Boot bootcount/bootlimit과 altbootcmd로 다른 슬롯으로 넘어간다(ELX-M12).

답 보기

연습 3 — 로드 영역 겹침#

{이름: (시작, 크기)}에서 겹치는 쌍을 찾아라. QEMU: kernel 0x40400000 + image_size, initrd 0x44000000 + 0x1277e2, QEMU DTB 0x40000000 + 1 MiB. ramdisk_addr_r=0x42000000으로 바꾸면? 합성 i.MX에서 Image가 36 MiB → 43 MiB로 커지면?

답 보기

반열린 구간 [s, s+z) 두 개는 sa < sb+zb and sb < sa+za일 때 겹친다. QEMU 기본값은 겹침 없음(커널 끝 0x42D8_0000 < 0x4400_0000). ramdisk_addr_r=0x42000000이면 커널과 겹친다 — U-Boot가 initrd를 먼저 읽고 booti가 커널을 옮기면 조용히 깨진다. i.MX는 커널 0x4060_0000 + 0x2b00000 = 0x4310_0000 > DTB 0x4300_0000 → 커널이 DTB를 밟는다. 커널 config에 드라이버를 잔뜩 built-in으로 넣은 날 "Starting kernel ..." 뒤에 멈추는 전형적인 원인이다. (i.MX8MP 주소 0x40480000/0x43000000은 NXP EVK 기본 환경의 기억값이며 이 랩에서 확인하지 않았다.)

10. 핵심 정리#

  • ROM → SPL(SRAM, DDR training) → BL31(EL3 상주, PSCI) → U-Boot(DRAM) → Linux → /init(PID 1). 각 단계는 다음 단계를 더 큰 메모리에 올리고 바통을 넘긴다.
  • arm64 핸드오프: x0 = DTB 물리 주소, x1~x3 = 0, MMU off, Image 2 MB 정렬. bootargs와 initrd 위치는 DTB /chosen으로 간다.
  • 실측 QEMU: kernel_addr_r=0x40400000, initrd → 0x7f40_4000, DTB → 0x7f3f_e000, U-Boot 재배치 0x8158_f000, BL31 secure SRAM.
  • 단계 경계는 핸드오프 줄(BL1: Booting BL31, Starting kernel ..., Run /init as init process)로 자른다. 첫 커널 줄의 도착 시각은 356 ms 늦었다(콘솔 등록 때 몰아서 출력).
  • printk 0 ≠ 커널 진입. 호스트 기준 시계 + min(host − printk)로 정렬한다.
  • 로그 정리: 접두어 먼저 떼고, CR은 덮어쓰기, ESC·깨진 바이트 제거, 표지는 ^로 고정, 단계는 앞으로만.
  • 부트 루프: 배너 반복·앞 단계 표지·printk 역행으로 자르고, 부팅마다 마지막 단계·첫 치명 줄·bootargs를 비교한다.
