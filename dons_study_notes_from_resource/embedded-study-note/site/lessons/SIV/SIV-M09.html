동시성 스트레스 테스트 설계

Mid⏱ 95분env: mac#stress#concurrency#pthreadupdated 2026-11-08
목표 CPU·DMA·메모리 트래픽을 동시에 걸어 단독 테스트에서 안 보이는 버그를 노출한다
과제 pthread로 CPU 메모리 체커, DMA 모델, 인터럽트 소스를 동시에 돌리는 host 스트레스 하네스를 만들고 각 트래픽에 독립적인 checker(시그니처/CRC)를 붙여 장시간 실행; 공유 자원 경합 버그(일부러 넣은 race)를 몇 분 안에 잡아내는지 확인한다.
내 상태

학습 목표#

  • CPU memtest · DMA · 인터럽트 소스를 동시에 돌리는 스트레스 하네스를 pthread로 만들고, 트래픽마다 독립 checker(소유자 시그니처 / 태그 순서 + CRC32 / 시퀀스 ack)를 붙인다.
  • 공유 자원 경쟁(완료 큐 티켓, W1C 상태 레지스터의 read-modify-write)이 단독 테스트에서는 안 보이고 동시 실행에서만 드러나는 이유를 인터리빙 전수 탐색으로 설명한다.
  • 간헐적인 race를 시드 고정 토큰 스케줄러로 결정적으로 재현·리플레이하고, 단일 스레드 hook으로 정확한 인터리빙을 강제해 단위 테스트로 고정한다.
  • "n번 돌려서 안 나왔다"의 통계적 의미(검출 확률, 95% 신뢰에 필요한 실행 수, 0 실패의 상한)를 계산하고, 이벤트 속도·race window 넓히기가 검출 시간을 얼마나 줄이는지 실측한다.
  • TSan이 잡는 것(data race)과 못 잡는 것(원자적 접근으로 만든 atomicity violation)을 구분하고, 실패 한 줄에 "어디를 보라"까지 담는 리포트를 만든다.

1. 문제#

first silicon 랩에서 가장 비싼 버그는 "블록마다 단독 테스트는 다 통과하는데 시스템을 다 켜면 몇 시간에 한 번 죽는" 버그다 — NVIDIA·Apple·Rivian 실리콘 검증 면접의 "concurrency stress test를 설계해 보라"는 질문이 정확히 이것을 묻는다.

단독 테스트(SIV-B03~B11)는 한 번에 한 마스터만 버스를 쓴다. 실제 칩에서는 CPU 코어, DMA 엔진, 인터럽트가 같은 메모리·같은 상태 레지스터·같은 큐를 동시에 쓴다. 그래서 검증 엔지니어는 ① 트래픽을 동시에 최대한 세게 걸고 ② 트래픽마다 서로 독립인 checker를 붙여 "누가 누구를 망가뜨렸는지"를 알아내고 ③ 실패를 재현 가능하게 만든다. 이 레슨은 그 하네스를 host에서 pthread로 만든다.

가상 SoC KES1 (SIV-B02의 mock을 축약해 넣었다; 버스 접근은 워드 단위 원자적이라고 보고 _Atomic uint32_t + relaxed로 모델링):

Part A — 트래픽 checker와 공유 자원 프로토콜#

  • cpu_agent_pass(me, iter): 자기 영역 32워드에 sig_word(me, iter, i)를 쓰고 다시 읽어 비교. 틀린 워드의 최상위 바이트가 다른 agent면 FOREIGN_WRITE("written by DMA1"), 아니면 CORRUPT.
  • cq_push(claim 이후 부분) / cq_peek / cq_release: 슬롯별 seq로 소유권을 넘기는 MPSC 큐. 빈 슬롯은 seq == 티켓, 찬 슬롯은 seq == 티켓+1. publish는 release, 소비는 acquire. 기다림이 예산을 넘으면 HANG.
  • irq_take(): INT_STS를 읽고, 읽은 비트만 W1C로 지운다.
  • dma_check_entry(e): 태그 → (채널, seq). 순서가 앞서면 MISSING, 뒤면 DUP, 엔진 CRC가 생성기 기대값과 다르면 CRC_ENGINE, dst 메모리 CRC가 다르면 첫 번째 틀린 워드 주소로 CRC_DST.
  • 끝에 det 모드로 6스레드 전체를 돌려 정상 모델이 깨끗하게 통과하는지 확인.

Part B — 경쟁을 결정적으로: 전수 탐색 · hook 재현 · 통계#

  • explore_rec: k개 agent가 공유 워드에 자기 비트를 세우는 프로그램(원자적 1단계 / RMW 2단계)의 모든 인터리빙을 펼쳐 갱신 유실 스케줄 수를 센다.
  • 단일 스레드 hook으로 cq_claim·irq_rmw의 race window에 다른 agent를 정확히 끼워 넣어, 유실·HANG·spurious를 결정적으로 재현 (정상 모델은 같은 끼어들기에 멀쩡).
  • p_detect(p, n), runs_needed(p, cl): 실행 1회 검출 확률 p일 때 n회 안에 검출할 확률, 신뢰도 cl에 필요한 실행 수.
  • det 리플레이: 처음 검출된 시드를 다시 돌리면 같은 실패가 같은 step에서 나와야 한다.

Part C — 야간 회귀: 결함 × 트래픽 조합 캠페인과 리포트#

  • isr_final(): 생산자가 다 끝난 뒤 마지막 판정 — CQ에 엔트리가 남았는데 DONE 비트가 없었다면 LOST_IRQ, 채널별 생산 수 ≠ 검사 수면 MISSING.
  • fail_format(): FAIL @step=… checker=… kind=… addr=… exp=… act=… diff=… | detail | suspect: … 한 줄.
  • 캠페인: 결함 4종(none 포함) × 트래픽 조합 6개(CPU / DMA1 / TMR / DMA0+1 / DMA+TMR / ALL) × 시드 8개. 단독 조합은 0, ALL은 셋 다 검출, 검출되면 기대한 checker·종류여야 한다.
  • free 모드로 정상 모델 실제 동시 실행 (DMA 3000+3000, TMR 300) → 통과, TSan 깨끗.

2. Problem (English)#

Design a host-side concurrency stress harness for an SoC validation lab (C11 + pthreads).

Agents run as threads: two CPU memtest agents (own regions), two DMA channels that copy 8-word blocks, compute an engine-side CRC-32 and post completions into a shared 4-entry completion queue, a timer that bumps TMR_SEQ and raises a status bit, and an ISR that takes INT_STS (write-1-to-clear) and drains the queue.

  1. Give every traffic type an independent checker: CPU data carries an owner signature in bits [31:24] so a corrupted word names its writer; DMA completions are checked for per-channel order (missing / duplicate), engine CRC and destination-memory CRC (report the first bad word address); timer events must be acknowledged exactly once (lost / spurious).
  2. Implement the queue (cq_push after the ticket claim, cq_peek, cq_release) with per-slot sequence numbers and release/acquire publication; a producer that waits past its budget reports HANG. Implement irq_take() with correct W1C semantics.
  3. Three planted defects — non-atomic ticket claim, read-modify-write of INT_STS, and a DMA write-tail overrun — must stay invisible when each traffic runs alone and be detected, with the right checker and failure kind, when traffic runs concurrently.
  4. Make it reproducible: a seeded token scheduler (det mode) must replay the same failure at the same step for the same seed. Enumerate all interleavings of k racing RMW agents and count lost updates. Compute p_detect(p, n) = 1-(1-p)^n and the minimum runs for confidence cl.
  5. Report one actionable line per failure, e.g. FAIL @step=459 checker=CPU0 kind=FOREIGN_WRITE addr=0x80000400 exp=0xC0F5EC4E act=0xD10FD56D … | iter=1 word=0 written by DMA1 | suspect: …

Checked tests must be deterministic and finish in seconds; long free-running stress is a CLI mode. The good harness must be ThreadSanitizer-clean.

4. 힌트#

힌트 1 — checker는 "기대값을 메모리가 아니라 정의에서" 만든다

CPU checker는 sig_word(me, iter, i), DMA checker는 crc_expected(ch, seq)(생성기 정의로 계산)와 비교한다. dst 메모리에서 CRC를 계산해 엔진 CRC와만 비교하면, 소스 준비가 틀렸을 때 둘 다 같은 틀린 값이라 통과해 버린다. 기대값의 출처가 검사 대상과 독립이어야 "독립 checker"다.

힌트 2 — 슬롯 seq 하나로 "누구 차례인지"를 표현한다

슬롯 i의 seq 초깃값은 i. 티켓 w를 받은 생산자는 seq == w가 될 때까지 기다리고(acquire), 엔트리를 쓰고, seq = w+1(release). 소비자는 seq == rd+1이면 읽고, 검사가 끝나면 seq = rd + CQ_SIZE(release) — 다음 바퀴 티켓의 "빈 슬롯" 표시다. 순서가 바뀌면(seq를 먼저 publish) 소비자가 덜 쓴 엔트리를 읽는다.

힌트 3 — W1C는 "읽은 비트만" 지운다

s = load(STS); fetch_and(STS, ~s). store(STS, 0)으로 지우면 load와 store 사이에 선 새 비트가 같이 사라진다. 실제 하드웨어 W1C 레지스터에 s를 쓰는 것과 같은 의미다.

힌트 4 — 인터리빙 탐색은 "아직 안 끝난 agent 중 하나를 골라 한 단계" 재귀

상태 = (공유값 x, 각 agent의 pc와 레지스터). 매 단계 pc < len인 agent마다 한 단계 실행해 재귀하고 되돌린다(backtracking). 아무도 못 움직이면 스케줄 하나 끝 — 이때 x가 모든 비트를 가졌는지 본다.

힌트 5 — 확률은 log1p로

n회 모두 못 잡을 확률 (1-p)^n = exp(n·ln(1-p)). p가 1e-6이면 log(1-p)는 1-p를 double로 반올림하면서 정밀도를 잃는다 → log1p(-p). 필요한 n = ⌈ln(1-cl) / ln(1-p)⌉.

5. 풀이#

Part A — 독립 checker 세 가지와 공유 자원 프로토콜#

왜 "독립"이어야 하나. 스트레스에서 실패는 대개 다른 트래픽이 일으킨다. checker가 자기 트래픽의 결과만 보면 "CPU0 memtest 실패"까지만 알고, 범인은 모른다. 그래서 데이터 자체에 출처를 새긴다.

checker기대값 출처잡는 것보고
CPU 시그니처sig_word(agent, iter, idx) = owner<<24 | hash24다른 마스터의 쓰기(FOREIGN), 자기 데이터 비트 뒤집힘(CORRUPT)주소, 기대/실제, 쓴 agent 이름
DMA 태그 순서채널별 다음 seq (g_next[ch])완료 유실(MISSING), 중복·stale(DUP)기대 태그 vs 받은 태그
DMA CRCcrc_expected(ch, seq) (정의에서 계산)엔진 읽기 경로·찢어진 엔트리(CRC_ENGINE), 쓰기 경로·덮어쓰기(CRC_DST)첫 번째 틀린 워드 주소
IRQ ackTMR이 seq n을 올리고 ack를 기다림상태 비트 유실(LOST), 지운 비트 부활(SPURIOUS)seq, 당시 INT_STS

실제 랩에서는 memtest 패턴에 코어 ID·반복 번호를 넣고, DMA는 하드웨어 CRC 유닛이나 descriptor의 체크섬 필드, 인터럽트는 per-source 카운터나 타임스탬프 레지스터로 같은 일을 한다. 핵심은 실패한 워드 하나만 보고도 "누가 언제 썼는지"를 알 수 있게 데이터 형식을 설계하는 것이다.

완료 큐 프로토콜. 슬롯 seq가 소유권 토큰이다.

슬롯 seq의미누가 다음에 움직이나
w비어 있음, 티켓 w의 생산자 차례생산자: 엔트리 쓰고 seq = w+1 (release)
w+1찼음소비자(rd = w): 읽고 검사 → seq = w + CQ_SIZE (release)
w + CQ_SIZE다음 바퀴 티켓의 빈 슬롯티켓 w+4의 생산자

release/acquire가 하는 일: 생산자의 엔트리 쓰기(평범한 sl->e = …)와 dst 메모리 쓰기(relaxed)가 seq release store보다 먼저 보이도록 보장하고, 소비자가 seq를 acquire로 읽으면 그 앞의 쓰기가 전부 보인다. 그래서 엔트리 필드는 _Atomic이 아니어도 data race가 아니다(TSan도 그렇게 판단한다 — 아래 TSan 결과).

슬롯은 검사가 끝난 뒤에 돌려준다. 채널은 블록 8개를 seq % 8로 재사용한다. 소비자가 dst 블록 CRC를 다 읽기 전에 슬롯을 돌려주면, 생산자가 다음 디스크립터를 들고 와 같은 블록을 덮어쓸 수 있다 → 정상 모델에서 가짜 CRC_DST. 검사 후 release이면: 채널이 seq s를 복사하기 시작할 때 s-1이 이미 push됐고, 그러려면 티켓 w(s-1) - 4 이하가 소비·검사 완료여야 한다. 같은 채널 티켓은 증가하므로 w(s-8) ≤ w(s-1) - 7 < w(s-1) - 4 → seq s-8(같은 블록)의 검사는 끝났다. 그래서 CQ_SIZE ≤ NBLK - 1이 조건이다. 실제 DMA 드라이버의 "완료 처리 전에 버퍼를 재사용하지 마라"와 같은 규칙이다.

W1C. irq_take는 s = load; fetch_and(~s). ISR이 store(0)으로 지우면 그 사이 DMA가 세운 DONE이 사라진다 — 이것도 lost interrupt지만 정상 모델에서 생기는 하네스 버그라 checker가 결함 모델과 구분할 수 없게 된다. 하네스 자신이 깨끗해야 결함을 결함이라고 말할 수 있다.

읽는 법:

  • 단독 조합(CPU / DMA1 / TMR)은 결함 셋 모두 0/8. cq_claim은 생산자가 둘이어야, irq_rmw는 set하는 쪽이 둘 이상이거나 ISR과 겹쳐야 한다(TMR 혼자면 ack를 기다리므로 자기 RMW 동안 STS가 비어 있다). dma_overrun은 DMA1 혼자서도 매번 일어나지만 아무도 CPU0[0]을 보지 않는다 — 버그는 있는데 checker가 없다.

  • dma_overrun × DMA+TMR = 0/8, ALL = 7/8. CPU checker가 있어야 보이고, 그것도 덮어쓴 순간이 CPU0가 word 0을 쓴 뒤·읽기 전이어야 한다. 안쪽 블록의 overrun은 다음 블록 word 0에 떨어지는데, 그 블록은 이미 검사가 끝났고 곧 자기 데이터로 덮이므로 영원히 안 보인다 — 경계(영역 끝)에서만 새는 버그.
  • 최소 재현 조합: cq_claim → DMA0+1, irq_rmw → DMA+TMR, dma_overrun → ALL (연습 5). 디버그 엔지니어에게 넘길 때는 이 최소 조합과 시드를 같이 준다.

8. 면접 Q&A#

Q1. 동시성 스트레스 테스트를 어떻게 설계하나요?

① 공유 자원 목록부터: 메모리 영역·버스·캐시 라인, 큐/링 인덱스, 상태·doorbell 레지스터, 클럭/파워 도메인. ② 그 자원을 쓰는 트래픽 생성기(CPU memtest, DMA, 인터럽트, 가능하면 GPU/NPU·PCIe 트래픽)를 동시에 최대 부하로. ③ 트래픽마다 독립 checker: 데이터에 출처(소유자·반복 번호)를 새기고, 기대값은 정의에서 계산. ④ 결함 주입으로 "이 하네스가 실제로 잡는가"를 검증. ⑤ 재현성: 시드, 시작 순서, 실패 시 즉시 정지 + 상태 스냅숏. ⑥ 통계: 몇 시간/몇 번 돌려야 하는지. 꼬리질문 "부하를 어떻게 키우나?" → 이벤트 속도 올리기(인터럽트 rate, 작은 DMA), race window 넓히기(지연 주입, 클럭 비율 변경), 같은 캐시 라인/뱅크로 주소를 몰기, 전압·온도 코너(SIV-M07/M08).

Q2. 단독 테스트가 다 통과했는데 왜 동시 테스트가 필요하죠?

결함이 상호작용에 있기 때문이다. 이 레슨의 매트릭스: 공유 큐 인덱스 경쟁은 생산자 둘, 상태 RMW는 set 주체 둘 이상, DMA 꼬리 overrun은 옆 영역을 쓰는 다른 마스터가 있어야 보인다. 단독 조합은 셋 다 0/8이었다. 실제 칩에서는 버스 arbitration, 캐시 coherency, 공유 FIFO, 전력 노이즈(동시 스위칭으로 인한 IR drop)도 같은 부류다. 꼬리질문 "그럼 처음부터 전부 켜고 돌리면?" → 실패했을 때 원인 공간이 너무 넓다. 단독 → 둘씩 → 전부 순으로 올리고, 실패하면 거꾸로 줄여 최소 재현 조합을 만든다.

Q3. 간헐적인 race를 어떻게 재현하나요?

(1) 시드 고정: 트래픽 패턴·순서를 시드에서 만들고 로그에 시드를 남긴다. (2) 스케줄 제어: 이 레슨의 det 토큰 스케줄러처럼 인터리빙 자체를 시드로 고정(소프트웨어), 시뮬레이션/에뮬레이터에서 재실행(RTL). (3) window 넓히기: 의심 구간에 지연을 넣어 확률을 올린다 — 실측에서 1 kHz 이벤트 기준 검출 시간이 수 초~수십 초에서 sub-second로 줄었다. (4) 원인이 좁혀지면 hook으로 정확한 인터리빙을 강제하는 단위 테스트로 고정해 회귀 방지. 꼬리질문 "로그를 더 찍었더니 재현이 안 된다?" → 관측이 타이밍을 바꾼 것(heisenbug). 링버퍼에 타임스탬프만 기록하고 실패 후 덤프한다.

Q4. 72시간 스트레스에서 실패가 없었습니다. 버그가 없다고 할 수 있나요?

아니다. 실패가 지수분포를 따른다고 보면 0 실패에서 95% 신뢰로 말할 수 있는 건 "평균 실패 간격 > 72/3 = 24시간" 정도다. 실행 횟수로는 n번 깨끗 → p < 1-(0.05)^(1/n) ≈ 3/n. 그래서 출하 기준은 "어떤 조건에서 몇 시간"을 명시하고, 부하·코너·결함 주입으로 하네스가 잡을 수 있음을 따로 보인다. 꼬리질문 "BER 측정과 같은 식인가?" → 같다. 0 오류에서 BER < 1e-12 @95%를 주장하려면 약 3e12 비트 (SIV-M06).

Q5. TSan이 깨끗하면 race가 없는 건가요?

TSan은 happens-before 관계가 없는 동시 비원자 접근(data race)을 찾는다. 이 레슨에서 irq_rmw는 atomic load + atomic store라 TSan이 조용했지만 checker는 잡았다(atomicity violation). cq_claim도 실측 8회 모두 TSan 경고 0 — 경쟁의 결과가 data race가 아니라 HANG으로 나타났기 때문이다. 또 TSan은 실제로 실행된 경로만 보고, 칩의 RTL이나 DMA 같은 HW 마스터는 못 본다. 그래서 TSan은 하네스 자신의 위생 검사로 쓰고, 칩의 경쟁은 데이터 checker로 잡는다. 꼬리질문 "그럼 load와 store를 _Atomic으로 바꾸면 '고친' 건가?" → 경고만 사라진 것. 연산 단위(RMW 전체)가 원자적이어야 한다: fetch_or, CAS 루프, lock, HW SET/CLR 레지스터.

Q6. W1C 상태 레지스터를 드라이버에서 다룰 때 흔한 버그는?

① STS = STS & ~handled (RMW로 쓰기): W1C 레지스터에 읽은 값을 그대로 다시 쓰면 1인 비트를 전부 지운다 → 아직 처리 안 한 이벤트 유실. ② 읽은 값과 상관없이 0xFFFFFFFF 기록: 같은 문제. ③ 처리 전에 지우지 않고 처리 후 지움: 처리 중에 다시 온 이벤트가 같이 지워질 수 있다 (edge 이벤트 유실). 올바른 순서: 읽기 → 읽은 비트만 W1C → 처리 → 다시 읽어 남은 비트가 있으면 반복. (SIV-B11, C-M02 참고) 꼬리질문 "level 인터럽트면?" → 원인(소스 쪽 조건)을 먼저 없애고 상태를 지워야 한다. 순서가 바뀌면 즉시 다시 선다.

Q7. 실패 리포트에 무엇을 남기나요? 첫 실패에서 멈추나요?

검출한 checker, 종류, 시각(step/µs), 주소, 기대/실제/diff, 시드·설정, 그리고 "suspect" 힌트. 시그니처 덕분에 실제값에서 누가 썼는지를 바로 말할 수 있다(act=0xD1… → DMA1). 멈추는 게 기본이다: 첫 실패 이후는 2차 피해라 원인을 흐리고, 멈춰야 메모리·레지스터 상태를 JTAG로 덤프할 수 있다. 대신 "계속 모드"는 실패율 통계를 낼 때만 쓴다. 꼬리질문 "실패 시 무엇을 덤프?" → 공유 자원 전부(STS, 큐 인덱스, 슬롯 seq, 각 agent의 진행 카운터) — 연습 4의 heartbeat가 HANG의 주인을 가린다.

Q8. 메모리 순서(memory ordering)는 이 하네스 어디에서 중요했나요?

완료 큐의 publish. 엔트리 필드를 쓴 다음 seq를 release로 쓰고, 소비자는 acquire로 읽는다. 이 맥(arm64)은 약한 메모리 모델이라 순서를 안 지키면 실제로 덜 쓴 엔트리가 보일 수 있다. 하드웨어에서도 같은 문제가 있다: DMA 디스크립터를 메모리에 쓰고 doorbell MMIO를 치기 전에 dmb/wmb가 필요하고, 완료 상태를 읽은 뒤 데이터를 읽기 전에 rmb가 필요하다(Linux dma_wmb/dma_rmb).

9. 추가 연습#

연습 1 — guard 워드: CPU checker 없이 overrun 잡기#

DMA 영역 바로 뒤에 guard 워드 4개(0xA5A5A5A5 ^ i)를 두고 guard_scan()으로 첫 번째 깨진 guard를 찾아라. DMA 단독 실행에서 dma_overrun이 잡히는지 확인하라.

답 보기

정상 복사 후 guard_scan == -1, overrun 모드로 8블록 복사 후 0번 guard가 깨지고 그 값이 0xD1000007(DMA1의 마지막 데이터 — 범인 서명). 안쪽 블록 하나만 overrun하면 guard는 무사하다(다음 블록 word 0에 떨어지므로). 본문 매트릭스에서 7/8이던 검출이 단독 실행에서 결정적으로 1/1이 된다 — 검출을 왼쪽(shift-left)으로 옮긴 것. 실제로는 메모리 할당기 redzone(ASan과 같은 발상), MPU/IOMMU 보호 영역으로 같은 일을 하고, IOMMU는 위반 주소와 마스터 ID까지 보고한다. guard 값을 워드마다 다르게 하는 이유: "마지막 값 반복" 같은 결함이 우연히 guard와 같은 값을 쓸 확률을 낮춘다.

연습 2 — 0 실패가 말해 주는 것#

p_upper_zero(n, cl) = 1 - (1-cl)^(1/n) 과 soak_seconds(mttd, cl) = -ln(1-cl)·mttd 를 구현하라. n = 300, 3000에서 rule of three(3/n)와 비교하고, 본문 실측 MTTD로 필요한 soak 시간을 구하라.

답 보기

n=300 → 0.009936 (3/n = 0.01), n=3000 → 3/n과 소수 둘째 자리까지 같다. MTTD 15.6 s(1 kHz·window 0 탐색 실행 한 번에서 잰 값)면 95%에 46.7 s, 99%에 71.8 s. 다만 표의 실측(시드 5개)은 2.8~48 s로 넓게 퍼지고 평균은 27 s다 — 그래서 MTTD는 여러 번 재서 추정하고, 계획에는 그 몇 배를 잡는다.

연습 3 — W1C와 RMW의 경쟁: spurious는 몇 가지?#

시작 상태 STS = TMR(대기 중). DMA는 RMW로 DONE을 세우고(2단계), ISR은 s = load; STS &= ~s(2단계). 모든 인터리빙 중 ISR이 TMR을 가져갔는데 끝에 TMR이 다시 서 있는 스케줄을 세라. DMA가 원자적 set이면?

답 보기

RMW: 6개 중 2개 (rD rI cI wD, rI rD cI wD — DMA가 TMR이 든 옛 값을 읽은 뒤, ISR이 지운 다음에 쓰는 경우). 원자적 set: 3개 중 0개. 본문 hook 테스트 3번(SPURIOUS)이 이 2개 중 하나를 강제한 것이다. 실행 출력: [ex3] W1C vs RMW setter: spurious 2/6, atomic setter 0/3.

연습 4 — HANG의 주인 찾기 (heartbeat)#

agent별 진행 카운터 스냅숏 두 개와 끝난 agent 마스크를 받아, 진행이 없는 agent 마스크를 돌려주는 stalled_agents()를 작성하라.

답 보기

!(done & bit) && cur == prev. 예: DMA0(40→40)와 TMR(9→9)이 멈췄지만 TMR은 끝났으면 DMA0만. free 모드 HANG에서 "누가" 멈췄는지(그리고 무엇을 기다렸는지)를 리포트에 넣는 장치다. 칩에서는 각 코어/엔진이 공유 SRAM의 heartbeat 워드를 증가시키고, 감시 코어나 JTAG 스크립트가 주기적으로 읽는다. 하드웨어 watchdog은 "죽었다"까지만, heartbeat 표는 "누가"까지 말한다.

연습 5 — 최소 재현 조합#

검출 매트릭스(조합별 agent 마스크와 검출 시드 수)에서, 검출된 조합 중 agent 수가 가장 적은 것(같으면 검출률이 높은 것)을 고르는 minimal_repro()를 작성하라.

답 보기

본문 매트릭스로 cq_claim → DMA0+1(2개), irq_rmw → DMA+TMR(3개), dma_overrun → ALL(5개), none → -1. 디버그 팀에게는 "ALL에서 실패"가 아니라 "DMA0+DMA1만 켜고 시드 1이면 step 2146에서 HANG"을 넘겨야 한다 — 원인 공간이 작을수록 빨리 고친다. 실제로는 delta debugging(ddmin)처럼 조합을 반씩 줄여 가며 자동화한다.

10. 핵심 정리#

  • 스트레스 하네스 = 공유 자원 목록 + 동시 트래픽 + 트래픽마다 독립 checker. 데이터에 출처(소유자·반복·seq)를 새기면 깨진 워드 하나가 범인을 말한다.
  • 기대값은 메모리가 아니라 정의에서 계산한다 (sig_word, crc_expected).
  • 원자적 load + 원자적 store ≠ 원자적 RMW. 구간이 겹치면 거의 항상 유실(k=2 4/6, k=3 84/90). 고치려면 fetch_or/CAS/lock, HW는 SET/CLR·W1C·W1S.
  • W1C는 읽은 비트만 지운다. 인터럽트 검사는 횟수가 아니라 이벤트별 seq + ack (coalescing이 유실을 가린다).
  • 큐 publish는 "필드 → seq(release)", 소비는 "seq(acquire) → 필드", 슬롯 반환은 검사 뒤.
  • race 재현: 시드 고정 스케줄러로 리플레이, hook으로 인터리빙 강제, window·이벤트 속도를 올려 MTTD 단축.
  • 0 실패 n번 = p < 3/n (95%). 필요한 실행 수 n ≥ ln(1-cl)/ln(1-p).
  • TSan은 data race만, atomicity violation과 HW 경쟁은 못 본다 → 데이터 checker가 1차 방어선. 실패하면 즉시 멈추고, 최소 재현 조합 + 시드로 넘긴다.
