캐시 친화 레이아웃: AoS vs SoA와 정렬

Advanced⏱ 100분env: mac#cache-friendly#soa#layout#see:ARCHupdated 2026-11-08
목표 자료구조 메모리 레이아웃이 실제 성능에 주는 영향을 측정한다
과제 파티클/센서 레코드 배열을 AoS·SoA·AoSoA로 구현해 일부 필드만 읽는 루프와 전체 갱신 루프의 처리량을 M2에서 측정하고, 연결 리스트 vs 배열 순회 비용까지 비교해 설계 지침을 정리한다.
내 상태

학습 목표#

  • 같은 논리 레코드(64바이트)를 AoS(Array of Structs), SoA(Struct of Arrays), AoSoA(블록 단위 혼합)로 구현하고, 세 레이아웃이 값·합·체크섬까지 똑같다는 것을 레퍼런스 모델로 보인다.
  • sizeof/offsetof/스트라이드(stride)/패딩을 _Static_assert로 못박고, C의 배치 규칙을 layout_size()로 직접 재현한다.
  • "SoA가 빠르다"를 원인별로 쪼갠다. SIMD를 끈 빌드와 켠 빌드, -Rpass=loop-vectorize 실제 출력, 작업 집합(working set) 크기별 측정으로 캐시 효과와 SIMD 효과와 정렬 효과를 따로 본다.
  • 건드리는 캐시 라인 수를 세는 플랫폼 독립 모델(line_switches)로 측정을 뒷받침한다. 연결 리스트의 비용을 할당 순서 vs 뒤섞인 순서로 비교한다.
  • 측정에서 나온 것만으로 설계 지침을 쓰고, D-캐시가 없는 Cortex-M에서 무엇이 달라지는지 설명한다.

1. 문제#

"센서 레코드 수만 개를 매 주기 처리합니다. 구조체 배열로 둘 건가요, 필드별 배열로 둘 건가요? 왜요?" 펌웨어와 시스템 면접에서 데이터 레이아웃은 답이 하나가 아니어서 자주 나온다. 근거를 숫자로 대는 사람과 "SoA가 캐시에 좋대요"라고 외운 사람이 바로 갈린다. 파티클 시뮬레이션, 레이더 포인트 클라우드, FTL의 블록 메타데이터 테이블이 전부 같은 질문이다.

이 레슨의 레코드는 64바이트다. 위치와 속도(x,y,z,vx,vy,vz), 타임스탬프, 시퀀스, 온도, 플래그, 그리고 거의 안 보는 교정 계수 cal[6]이 들어 있다.

Part A — AoS 기준점과 SoA#

  • Rec은 64바이트이고 패딩이 없다. 필드는 큰 정렬부터 놓았다. Aos는 그냥 Rec r[CAP]이다(주어짐).
  • Soa를 구현한다: soa_get/set/push, 부분 필드 읽기 soa_sum_x, soa_sum_masked(flags bit0이 켜진 레코드의 x만 합산), 절반 갱신 soa_update_pos, 전체 갱신 soa_update_all, soa_swap_remove.
  • 전체 갱신의 계약은 rec_update_all과 레코드별로 똑같아야 한다. 위치는 옛 속도로 적분한 뒤 속도를 줄인다. 필드별 for 루프로 쪼개면 이 순서를 지키는 것이 일이 된다.

Part B — AoSoA, 패딩, 라인 모델#

  • Block은 W=8 레인 묶음이다. 인덱스 i는 (blk_of(i), lane_of(i))로 바뀐다. n이 W의 배수가 아니면 마지막 블록은 일부 레인만 유효하다. 유효 레인 밖은 읽지도 쓰지도 않는다. 하네스가 빈 슬롯을 포이즌(0xA5)으로 채워 놓고 합에 섞이거나 값이 변하면 잡는다.
  • aosoa_swap_remove는 다른 블록의 레코드를 옮겨 온다.
  • layout_size(fields, n): 멤버 offset을 정렬 배수로 올리고, 끝을 최대 정렬 배수로 올리는 규칙을 그대로 구현해서 실제 sizeof와 일치시킨다.
  • line_switches(c, addr_fn, n, elem, line): 원소를 순서대로 건드릴 때 다른 라인으로 넘어가는 횟수를 센다. 128B/32B 라인에서 레이아웃별 정답을 체크한다.

Part C — 펌웨어 현실: DMA 바이트열, 윈도, 리스트#

  • wire_decode: DMA 버퍼에는 19바이트짜리 프레임이 정렬 없이 놓인다. (const uint32_t *)로 캐스트하지 않고 바이트로 조립해서 SoA에 붙인다. 남는 조각은 무시하고, CAP에 차면 멈춘다.
  • soa_window_stats: x[first..first+count)의 min/max/sum. first + count 덧셈이 감기지 않게 범위를 검사한다.
  • 노드 풀 연결 리스트: order[] 순서대로 next를 잇고 합을 구한다. 뒤섞인 순서에서도 합은 같고, 라인 전환 수만 커지는 것을 체크한다.

2. Problem (English)#

Implement a fixed-capacity container of 64-byte records in three layouts and compare them.

Constraints: no heap in the containers; the AoSoA block width is 8; a kernel must never read or write a slot at index ≥ n. All layouts must produce bit-identical records, sums and checksums for the same operation sequence. Then measure throughput (ns/record) of partial-field and full-update kernels across working sets crossing L1, L2 and the system cache, with and without auto-vectorization, and say which effect explains each result.

4. 힌트#

힌트 1 — SoA의 전체 갱신을 필드별 루프로 쪼갤 때

rec_update_all에서 필드 사이의 의존은 x += vx → vx -= vx >> 4 하나뿐이다. 필드별 루프로 나누어도 위치 루프를 속도 루프보다 먼저 돌리면 결과가 같다. 다른 필드는 서로 독립이라 순서가 상관없다.

힌트 2 — AoSoA의 꼬리

블록 포인터 b와 남은 개수 rem을 들고 돈다. 이 블록에서 처리할 레인 수는 m = min(W, rem)이다. 블록 전체(l < W)를 돌리는 코드는 합에 포이즌을 섞거나, 갱신 커널이 n 밖의 값을 바꾼다.

힌트 3 — layout_size의 끝 패딩

배열로 썼을 때 다음 원소가 정렬되어야 한다. 그래서 {uint16_t; uint8_t;}의 크기는 3이 아니라 4다. 끝에 최대 정렬 배수로 올리는 단계를 빼먹기 쉽다.

힌트 4 — line_switches

원소 하나가 라인 경계를 걸칠 수 있다. 원소의 첫 바이트 라인 ~ 끝 바이트 라인을 차례로 보고, 직전 라인과 다를 때만 +1 한다. "지금까지 본 라인 집합"은 필요 없다. 주소가 단조 증가하면 전환 횟수가 곧 라인 수다.

힌트 5 — wire_decode

get_le32는 주어져 있다. t_us는 32비트 두 번을 조합한다. len >= WIRE_SIZE && s->n < CAP이 루프 조건이다. (const uint32_t *)buf로 읽으면 이 맥에서는 값이 맞게 나와도 UBSan이 잡고, Cortex-M0에서는 HardFault가 난다.

힌트 6 — window_stats의 범위 검사

first + count > n은 count가 크면 감겨서 통과할 수 있다. first >= n || count > n - first처럼 뺄셈으로 쓴다.

5. 풀이#

불변식#

세 컨테이너와 레퍼런스(Rec g_ref[CAP])에 대해 invariants_ok()가 다음을 확인한다.

  1. 개수 n이 같다.
  2. i < n인 모든 슬롯이 레퍼런스와 바이트까지 같다(Rec은 패딩이 없으니 memcmp가 값 비교와 같다).
  3. 합과 마스크 합이 같고, FNV-1a 체크섬이 같다.
  4. i ≥ n인 슬롯은 전부 포이즌 그대로다. 커널이 n 밖을 건드리지 않았다는 증거다.

작은 n(≤40, 4000 연산)은 매 연산마다 전수 검사, n ≈ 1024(30만 연산)는 K = 1024 연산마다 + 끝에서 전수 검사한다. 이 스케일은 ASan/UBSan에서도 그대로 돌아서 1.5초쯤 걸린다.

Part A — 레이아웃을 바꿔도 값은 안 바뀐다#

SoA의 핵심은 간단하다. 접근자가 필드 배열에서 모아 주고(soa_get), 흩어 넣는다(soa_set). 전체 갱신은 필드별 루프로 쪼갠다. 문제는 의존 순서다.

감쇠 루프를 먼저 돌리면 x가 이미 줄어든 속도로 적분된다. 하네스의 고정값 체크(x == 17, vx == 15)와 레퍼런스 비교가 이 버그를 잡는다. 실제로 damp_before_integrate 변형을 넣어 보면 7개 체크가 FAIL한다.

정렬은 어떻게 했나? 컨테이너의 시작을 alignas(128)로 잡았다. 이 맥의 라인이 128바이트이고, 시작이 라인 경계여야 line_switches의 답이 결정적이기 때문이다. SoA의 각 필드 배열도 alignas(128)이고, CAP = 1024라 필드 배열 크기가 128의 배수여서 중간 패딩은 없다(offsetof(y) - offsetof(x) == 4096을 _Static_assert로 확인).

Part B — AoSoA와 꼬리#

AoSoA의 인덱스 계산은 비트 연산이다. W가 2의 거듭제곱이어야 i >> 3과 i & 7로 끝난다.

꼬리를 놓치는 버그 두 가지는 실제로 잡힌다. 합 루프를 l < W로 돌리면(변형 tail_full_block) 7개 FAIL이 나고, 갱신의 한 루프만 l < W로 돌려도(변형 update_tail_full) 4개 FAIL이 난다(포이즌이 변했다는 불변식 4).

패딩. 같은 멤버를 어떤 순서로 놓느냐에 따라 16바이트 차이가 난다.

측정 환경과 방법#

  • CPU: Apple M6. sysctl 실제 값: 세 등급의 코어가 있다. Super 2코어(L1d 128 KB, L2 20 MB/2코어), Performance 4코어(L1d 64 KB, L2 20 MB/4코어), Efficiency 6코어(L1d 96 KB, L2 8 MB/6코어). hw.cachelinesize = 128, 페이지 16 KB. SLC(시스템 레벨 캐시) 크기는 sysctl에 나오지 않는다.
  • demo_bench.c: 작업 집합 S 를 16 KB ~ 256 MB로 늘리며, n = S/64 레코드에 커널을 돌린다. 한 칸 = 5회 반복의 중앙값. 시간은 CLOCK_UPTIME_RAW. 첫 패스는 데우기로 빼고, 메모리는 미리 건드려(memset) 페이지 폴트를 뺐다. QOS_CLASS_USER_INTERACTIVE로 P 코어를 권유할 뿐, 코어 고정은 안 된다. Super와 Performance 중 어디서 돌았는지는 모른다.
  • 빌드 3종: 기본(-O2, AoSoA W=8), -DAW=32, 그리고 SIMD를 끈 -O2 -fno-vectorize -fno-slp-vectorize.
  • 이 측정은 시끄럽다. 같은 시간에 다른 작업이 돌아서 부하 평균이 10~52였다. 전체를 6회 돌렸고(3회 × 2묶음), 표의 각 칸은 중앙값 (최솟값)이다. 실행 간 spread(최대-최소/중앙값)는 칸마다 대체로 30~60%, 최악 178%다. 그래서 2배 미만의 차이는 신호로 해석하지 않는다. 최솟값이 중앙값과 같은 방향이면 믿는다.

정리하면 SoA가 AoS보다 빠른 배수의 대부분은 SIMD에서 나오고, 캐시 효과는 2~3배다. 그리고 그 캐시 효과는 L1을 넘어선 뒤에야 나타난다. AoS에서 SIMD의 이득은 L1 안에서 1.8배(0.286 → 0.162)이고, L2 이상에서는 없다(4 MB에서 0.536 → 0.548). 위 asm처럼 레인마다 ld1.s로 끼워 넣어야 하니 로드 수가 줄지 않는다. 절약되는 것은 덧셈뿐이다.

놀라운 점 하나: 순차 AoS는 DRAM까지 가도 별로 안 느려진다. 4 MB 0.548 → 256 MB 0.740이다. 일정한 스트라이드를 하드웨어 프리페처가 따라가는 것으로 보인다(PMU로 확인하지는 않았다). 뒤의 뒤섞인 리스트 측정과 정반대다.

AoSoA는 그 중간이다. L1에서는 SoA에 가깝고(0.049 vs 0.036), DRAM으로 가면 W=8이 AoS 쪽으로 간다(0.665 vs AoS 0.740). W=32(0.205)가 낫다. 라인 모델의 예측과 방향이 같다: W=8의 x[8]은 32바이트라 라인당 x가 8개뿐이다. W=32면 x[32]가 128바이트로 라인 하나를 가득 채운다.

Part C — 비정렬 바이트와 경계 검사#

wire_decode는 프레임이 홀수 주소에서 시작해도 동작한다. 바이트로 조립하기 때문이다. 포인터 캐스트로 바꾸면(변형 wire_cast) 이 맥에서는 체크가 통과한다. 그러나 UBSan이 다음을 보고한다.

Cortex-M0/M0+(ARMv6-M)는 비정렬 접근이 HardFault다. Cortex-M3/M4(ARMv7-M)는 LDR/LDRH/STR/STRH 비정렬을 허용하지만(UNALIGN_TRP가 꺼져 있을 때), LDM/STM/LDRD/STRD는 정렬이 필요하다. 그래서 바이트로 조립하거나 memcpy를 쓰는 것이 휴대 가능한 답이다.

soa_window_stats의 범위 검사는 first + count > s->n처럼 쓰면 감김 버그가 있다(변형 window_overflow: count = UINT32_MAX가 통과해 FAIL 1개). 뺄셈으로 쓴다.

측정에서 뽑은 설계 지침#

아래 지침은 이 맥에서 측정한 것만 근거로 한다.

  1. 일부 필드만 읽는 스캔은 SoA. SIMD가 켜지면 AoS 대비 4.5~15배(sum_x). SIMD를 끄면 L1 안에서는 차이가 없고 L2/DRAM에서 2~3배뿐이다. "캐시 때문에 빠르다"라고만 말하면 틀린다.
  2. 거의 모든 필드를 건드리는 갱신에서는 AoS가 나쁘지 않다. SIMD 빌드에서 SoA가 1.5~2배 빠른 것이 전부고, SIMD가 없으면 AoS가 약 2배 빠르다.
  3. AoSoA는 공짜가 아니다. W=8은 update_pos의 DRAM 영역에서 AoS보다 느렸다(2.3 vs 1.3 ns). W=32는 라인 크기(128B)에 맞아 나았다. W는 측정으로 정한다.
  4. 조건 연산이 있으면 레이아웃보다 분기 제거가 먼저다. 난수 플래그에서 분기 있는 버전은 16 MB 이상에서 2.3~3.1 ns(레이아웃 무관), 분기 없는 SoA는 0.09 ns다.
  5. 자동 벡터화를 믿지 말고 재라. 분기 없는 AoS 커널은 벡터화 후 빨라지지 않았다(중앙값 약 2배, 최솟값 1.1~1.4배 느림). -Rpass의 "vectorized"는 빠르다는 뜻이 아니다.
  6. 연결 리스트는 노드의 메모리 순서가 문제다. 할당 순서로 놓으면 1 ns대, 뒤섞이면 DRAM 크기에서 약 100 ns다. 이 측정에서 끌어낸 추론 하나: 할당/해제를 오래 반복해 순서가 섞인 풀은 후자에 가까워진다.
  7. 시작 주소 정렬(라인 맞춤)은 이 CPU에서는 성능 차이를 못 찾았다. 정렬 강제는 기능 이유(DMA, 원자성, SIMD 명령 제약)로 넣는다.

D-캐시가 없는 Cortex-M에서는#

Cortex-M4 같은 칩은 D-캐시가 없다(보통 SRAM에 직접 접근). 그러면 캐시 라인 논리가 사라진다. 레이아웃의 비용은 명령어 수로 돌아간다. demo_asm.c를 clang --target=thumbv7em-none-eabi -mcpu=cortex-m4 -mthumb -O2 -S로 본 실제 출력이다.

(가운데 add/subs는 줄였다.) 두 레이아웃 모두 원소당 ldr 하나다. SRAM이 균일 지연이면 AoS와 SoA의 sum_x는 같은 일을 한다. 차이는 레지스터 사용이다. AoS의 update_pos는 base 하나 + 즉값 오프셋으로 끝난다. SoA는 필드 포인터 6개와 n이 인자로 온다(AAPCS는 앞 4개만 레지스터, 나머지는 스택). 실제 Cortex-M4 출력에서도 차이가 보인다. SoA update_pos는 push.w {r4, r5, r6, r7, r8, r9, r10, r11, lr}에 @ 4-byte Spill이 붙은 스택 저장이 나왔고, AoS는 push {r4, r5, r6, lr}로 끝났다. 레지스터가 더 적은 Cortex-M0+에서는 더 불리할 것이다(추정). 이 레슨은 이 칩의 사이클을 재지 않았으니, 실제 판단은 DWT->CYCCNT로 한다.

MVE가 있는 Cortex-M55(--target=thumbv8.1m.main-none-eabi -mcpu=cortex-m55)에서는 다시 SIMD 이야기가 된다.

MVE에는 진짜 gather 명령이 있어서 AoS도 벡터화되지만, 주소 벡터를 만드는 추가 명령이 든다(vshl, vadd). D-캐시를 넣은 Cortex-M7 구현(라인 32바이트)에는 이 레슨의 라인 모델 32B 열이 적용된다. 위의 M4 asm은 이 레슨의 컴파일 결과이고, 플래시 대기 상태나 버스 경합은 이 측정에 없다.

실행 환경은 Apple M6, -O2, 부하 평균 10~52(같이 돌던 작업 때문)다. 절대 ns보다 비율을 보고, 2배 미만의 차이는 해석하지 않는다.

7. 자주 하는 실수#

1. 필드별 루프로 쪼개면서 의존 순서를 바꾼다. vx 감쇠를 위치 적분보다 먼저 돌리면 값이 조금씩 달라진다. 컴파일도 되고 눈으로 봐서는 안 보인다. 레퍼런스 비교가 필요한 이유다.

2. AoSoA 꼬리 블록을 통째로 돈다. l < W로 돌리면 n 밖 레인을 읽거나 쓴다. 블록이 다 차 있다고 가정하지 말고 m = min(W, rem)을 쓴다.

3. W를 2의 거듭제곱이 아니게 잡는다. i & (W-1)이 깨진다. _Static_assert로 막거나 나눗셈으로 쓴다(비용은 측정).

4. -Rpass의 "vectorized"를 "빨라졌다"로 읽는다. 이 레슨의 AoS sum_x(L2 이상에서 이득 없음)와 sum_mask_bl이 반례다. asm을 보고, SIMD를 끈 빌드와 비교해야 한다.

5. SoA 포인터 사이의 앨리어싱을 잊는다. 필드 포인터를 그냥 넘기면 컴파일러가 런타임 겹침 검사를 넣거나 벡터화를 포기한다. restrict를 쓰거나, 정적 배열(필드가 겹치지 않는 게 자명)로 둔다.

6. 타이밍을 CHECK에 넣는다. 측정값이 부하에 따라 칸마다 수십 % 흔들렸다(최악 178%). 시간 측정은 demo에만 둔다. 체크에는 라인 수처럼 결정적인 숫자만 넣는다.

7. 패킷을 구조체로 캐스트한다. (const Frame *)buf는 비정렬에서 UB이고 패딩 때문에 필드 위치도 다르다. 바이트로 조립하거나 memcpy를 쓴다.

8. 범위 검사를 덧셈으로 쓴다. first + count > n은 uint32_t 감김으로 통과한다. count > n - first로 쓴다.

9. "캐시 라인에 정렬하면 빠르다"고 단정한다. 측정해 보면 이 M6에서는 차이가 없었다. 정렬이 진짜 필요한 곳은 DMA 버퍼, 원자 변수 경계, SIMD 정렬 명령을 쓰는 코드다.

8. 면접 Q&A#

Q1. AoS와 SoA 중 언제 무엇을 고르나요?

접근 패턴을 먼저 본다. 일부 필드만 많이 스캔하면 SoA다. 이 레슨에서 x 합산은 SoA가 4.5~15배 빨랐다. 레코드 대부분을 함께 읽고 쓰거나, 인덱스로 레코드를 하나씩 다루는 코드는 AoS가 낫다. 전체 갱신은 SIMD 없이 AoS가 약 2배 빨랐고, 레코드 복사와 교환은 AoS가 한 번이다. SoA는 필드 수만큼 필요하다. 중간 지점이 Hot/Cold 분리다(연습 2). 답하기 전에 "측정 환경에서 SIMD가 돌아가나"를 먼저 말하면 좋다.

Q2. "SoA가 빠른 건 캐시 때문이죠?" — 어떻게 검증하죠?

두 원인을 분리해야 한다. 나는 SIMD를 끈 빌드(-fno-vectorize -fno-slp-vectorize)와 켠 빌드를, 캐시 안과 밖 작업 집합에서 비교했다. 16 KB에서는 SIMD를 끄면 AoS와 SoA가 0.286 ns로 똑같았다. 즉 L1 안의 차이는 전부 SIMD다. 4 MB에서는 SIMD를 꺼도 1.9배 차이가 나는데, 이것이 순수한 캐시 효과다. 256 MB에서는 3배다. 꼬리질문으로 "왜 SIMD를 켜도 L2 이상에서 AoS는 안 빨라지나요?"가 나오면, 64바이트 스트라이드의 원소 네 개를 레인마다 따로 로드하는 실제 -S를 보여 준다.

Q3. AoSoA의 W는 어떻게 정하죠?

두 가지 축이다. SIMD 폭의 배수이고(NEON u32 4레인이면 W=4/8/16), 필드 하나의 W개가 캐시 라인과 맞아야 한다. 라인 모델에서 W×4 = 라인 크기일 때 SoA와 같은 라인 수가 나온다(32B 라인이면 W=8, 128B 라인이면 W=32). 측정도 같은 방향이었다. x만 읽을 때 W=32가 W=8보다 DRAM에서 3배 빨랐다. 다만 필드 여러 개를 쓰는 커널에서는 블록 안에서 띄엄띄엄 쓰게 되어, update_pos의 W=8은 DRAM에서 AoS보다 느렸다. 정답은 측정이다.

Q4. D-캐시 없는 Cortex-M에서는 이 얘기가 어떻게 바뀌나요?

SRAM이 균일 지연이면 "라인을 몇 개 건드리나"가 의미가 없다. 명령어 수와 레지스터 수의 문제가 된다. 실제 Cortex-M4 출력에서 AoS와 SoA의 sum_x는 둘 다 원소당 ldr 하나다. AoS는 base 하나에 즉값 오프셋으로 끝나서 레지스터가 적은 코어에서 유리할 수 있다(추정, DWT로 측정해야 함). SoA는 필드 포인터가 많아 스필이 생길 수 있다. Cortex-M7은 D-캐시가 있어 라인 32B 이야기로 돌아오고, DTCM에 두면 캐시를 우회한다. MVE가 있는 M55에서는 SoA가 vldrw + vaddva로 벡터화된다.

Q5. 캐시 라인 정렬(alignas(64))은 언제 필요하죠?

이 맥의 측정에서는 시작 주소를 +0/+4/+1로 바꿔도 차이를 못 찾았다. 그러니 "빨라진다"가 이유는 아니다. 필요한 곳은 셋이다. ① DMA 버퍼: 캐시 무효화는 라인 단위라서, 버퍼가 라인을 공유하면 옆 변수의 변경이 날아간다(연습 4). ② 스레드 사이의 false sharing: 서로 다른 코어가 쓰는 변수를 같은 라인에 두지 않는다. 이 맥의 라인은 128B라 64B로 맞추면 부족할 수 있다(이 레슨에서 측정하지는 않았다). ③ 정렬 요구 명령: Cortex-M0 비정렬 금지, LDRD/LDM 정렬 요구.

Q6. 연결 리스트는 왜 느린가요? 그래도 쓰는 이유는요?

포인터 추적 자체는 1 ns 근처였다. 이 레슨의 측정에서 할당 순서로 놓인 리스트는 256 MB에서도 1.3 ns였다. 느린 것은 순서가 뒤섞인 경우로 256 MB에서 102 ns였다. 다음 주소를 알 수 없어 프리페치가 안 되고, 체인이 직렬 의존이다. 그래도 쓰는 이유는 침입형 리스트의 O(1) 제거(DS-M01), 고정 풀과 맞음, ISR에서 메모리 이동 없이 쓰는 것이다. 순회가 잦다면 배열이나 풀 순서 유지를 먼저 생각한다.

Q7. update_pos에서 AoSoA-8이 AoS보다 느린 이유를 뭐라고 설명하죠?

측정이 보여 주는 것은 "DRAM 영역에서 2.28 vs 1.33 ns"뿐이다. 내 가설은 하드웨어 프리페처다. AoS는 모든 라인을 순서대로 건드려 스트림 프리페처에 이상적이고, AoSoA-8은 라인 2개 쓰고 2개 건너뛰는 패턴이 된다. PMU 없이 돌렸으니 이것은 검증되지 않은 설명이다. 확인하려면 메모리에 W=8 패턴을 흉내 낸 합성 트레이스로 프리페처 영향을 분리하거나, 코어 PMU가 있는 환경에서 프리페치 카운터를 본다.

Q8. 패딩을 없앤다고 __packed를 써도 되나요?

쓰면 크기는 줄지만 멤버가 비정렬이 된다. Cortex-M0는 그 멤버 접근이 폴트고, 컴파일러는 packed 멤버를 바이트/하프워드로 쪼개 읽어 코드가 커지며, 그 필드의 포인터를 함수에 넘기면 UB 위험이 있다. 먼저 멤버를 정렬 내림차순으로 놓는다. 이 레슨의 BadOrder는 재배치만으로 32 → 16바이트가 되었다. packed는 와이어 포맷처럼 레이아웃이 외부에서 정해질 때만 쓰고, 그때도 저장소로는 바이트 배열로 다룬다.

9. 추가 연습#

연습 1 — 정렬 내림차순이 최소 크기인가#

필드 3~7개를 무작위로 뽑아, 정렬 내림차순으로 놓은 크기가 모든 순열의 최솟값과 같은지 300번 확인한다. (필드 크기는 자기 정렬의 배수로 한정)

답

layout_size로 전수 탐색(재귀 순열)과 sort_by_align_desc 결과를 비교한다. 정렬이 2의 거듭제곱이고 크기가 정렬의 배수이면, 큰 정렬부터 놓을 때 중간 패딩이 생기지 않고 꼬리 패딩만 남는다. 전체 크기는 "멤버 합을 최대 정렬로 올린 값"보다 작을 수 없으니 이것이 최솟값이다. 300회 모두 통과한다.

연습 2 — Hot/Cold 분리#

레코드를 Hot 28바이트(x,y,z,vx,vy,vz,temp,flags,health)와 Cold 40바이트로 나누고, x 합산이 AoS와 같은지와 건드리는 라인 수를 비교한다.

답

실제 출력은 x 스캔 라인 수 (128B): AoS 512, Hot/Cold 224, SoA 32다. 스트라이드가 64에서 28로 줄어 라인 수가 2.3배 줄었다. 필드를 더 잘게 쪼갤수록 SoA에 가까워진다. 구조체 접근 코드를 거의 안 바꾸고도 얻는 이득이라 기존 펌웨어를 고칠 때 제일 먼저 해 볼 만하다. FTL 블록 메타데이터에서 valid count와 상태를 hot으로, 소거 횟수와 이력을 cold로 나누는 것이 같은 발상이다.

연습 3 — SoA의 flags를 비트맵으로#

flags를 1024바이트에서 128바이트 비트맵으로 줄이고, 비트가 켜진 x만 합산한다.

답

bits &= bits - 1과 __builtin_ctz로 켜진 비트만 건너뛴다. 마지막 워드는 n 밖 비트를 마스킹한다(bits &= (1u << (n & 31)) - 1). n & 31 == 0이면 마지막 워드가 통째로 유효하니 마스킹하지 않는다((1u << 0) - 1 == 0이라 전부 지워진다). 플래그 메모리는 8배 준다. Cortex-M3/M4 이상은 CLZ가 있지만 CTZ는 RBIT+CLZ 조합이고, Cortex-M0는 둘 다 없다.

연습 4 — DMA 수신 버퍼와 라인#

Cortex-M7(라인 32B)의 수신 버퍼 [addr, addr+len)에서 무효화해도 안전한 안쪽 구간을 계산한다. rx_buffer_ok는 시작과 길이가 라인 배수인지 본다.

답

start는 올림, end는 내림이다. 예: 0x20000010 + 64 → 안전 구간 [0x20000020, 0x20000040). 양 끝의 부분 라인에는 옆 변수가 같이 있어서, 무효화하면 그 변수의 변경이 사라진다. 그래서 alignas(32)로 시작을 맞추고 크기를 32의 배수로 잡는다. CMSIS의 SCB_InvalidateDCache_by_Addr는 주소/길이를 받지만, 라인에 맞추는 책임은 호출자에게 있다. 이 레슨의 측정이 성능에서 찾지 못한 정렬의 필요가 여기에 있다.

10. 핵심 정리#

  • 레이아웃은 접근 패턴과 SIMD로 고른다. 일부 필드를 많이 스캔하면 SoA, 레코드 전체를 함께 다루면 AoS, 중간은 Hot/Cold 분리.
  • 이 M6에서 sum_x의 SoA 이득은 L1에서 4.5배(SIMD 끄면 1.0배), L2에서 14배(SIMD 끄면 1.9배), DRAM에서 15배(SIMD 끄면 3배). 큰 부분은 SIMD다.
  • 전체 갱신은 SIMD 없으면 AoS가 약 2배 빠르고, SIMD가 있으면 SoA가 1.5~2배 빠르다.
  • AoSoA는 W×필드 크기 = 라인일 때 부분 스캔이 좋다. W가 라인과 안 맞으면(W=8, 128B 라인) DRAM 갱신에서 AoS보다 느릴 수 있다.
  • 분기 있는 마스크 합산은 16 MB 이상에서 레이아웃과 무관하게 2.3~3.1 ns, 분기 없는 SoA는 0.09 ns. 분기가 먼저다.
  • -Rpass의 "vectorized"는 빠르다는 뜻이 아니다. 분기 없는 AoS 커널은 벡터화로 빨라지지 않았다. -S와 no-SIMD 빌드로 확인한다.
  • 리스트는 순서가 문제다. 할당 순서면 1 ns대, 뒤섞이면 DRAM에서 약 100 ns.
  • 시작 주소 정렬은 이 CPU에서 측정 가능한 이득이 없었다. DMA, false sharing, 비정렬 금지 코어 때문에 쓴다. Cortex-M4는 D-캐시가 없어서 라인 논리 자체가 없고, 명령어와 레지스터 수 문제로 돌아온다.
