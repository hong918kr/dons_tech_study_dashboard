침입형 레드블랙 트리 (Linux rbtree 스타일)

Advanced⏱ 120분env: mac#rbtree#intrusive#balanced-treeupdated 2026-11-08
목표 삽입/삭제 재색칠·회전 케이스를 구현하고 불변식을 검증한다
과제 rb_node 내장형 레드블랙 트리의 insert/erase/next를 구현하고, 루트 검정·빨강 연속 금지·검정 높이 동일 불변식 검사기와 랜덤 연산 100만 회 테스트로 검증한다.
내 상태

학습 목표#

  • struct rb_node를 객체 안에 박아 넣고(intrusive), 색을 부모 포인터의 비트 0에 숨기는 인코딩을 구현한다. 어떤 정렬 가정 위에 서 있는지 _Static_assert로 적고, packed가 왜 이 가정을 깨는지 설명한다.
  • 삽입 복구 3 케이스와 삭제 복구 4 케이스를 그림 없이 재현하고, "삽입 회전 ≤ 2, 삭제 회전 ≤ 3"이 왜 성립하는지 케이스 흐름으로 증명한다.
  • 삭제에서 키를 복사하지 않고 후계자 노드를 재연결해야 하는 이유(객체 포인터의 안정성)를 말하고 구현한다.
  • 불변식 검사기(루트 검정, 빨강 연속 금지, 검정 높이, 전역 BST 순서, 부모 링크, 개수)가 각 위반을 실제로 잡는지 음성 테스트로 확인하고, 키 6개 전수 순열 + 랜덤 100만 회로 검증한다.
  • RB와 AVL을 측정값으로 비교하고, 펌웨어 타임아웃 큐를 rb_root_cached로 만든다. 언제 정렬 리스트가 더 나은지 수치로 판단한다.

1. 문제#

"균형 트리를 하나 짜 보세요. AVL 말고 레드블랙으로요. 삭제까지요." 시니어 펌웨어 면접에서 레드블랙은 구현력과 설계 판단을 동시에 본다. 리눅스의 타이머(hrtimer), 스케줄러 런큐(see:OS-A04), I/O 스케줄러가 모두 이 구조 위에 있고, 펌웨어에서는 malloc 없이 객체 안에 노드를 박아 쓰는 형태로 그대로 가져올 수 있다.

레드블랙 트리는 다섯 규칙을 지키는 이진 탐색 트리다. 노드는 빨강이나 검정이고, 루트는 검정, NIL은 검정, 빨강의 자식은 검정(빨강 연속 금지), 어떤 노드에서든 아래 NIL까지 가는 모든 경로의 검정 수가 같다(검정 높이 동일). 뒤의 두 규칙에서 높이 상한이 나온다.

  • 검정 높이 b인 서브트리에는 내부 노드가 최소 2^b − 1개 있다(귀납법, 빨강을 무시하면 완전 이진 트리다).
  • 빨강 연속 금지 때문에 경로의 절반 이상이 검정이다. 즉 b ≥ h/2.
  • 합치면 n ≥ 2^(h/2) − 1, 곧 h ≤ 2·log₂(n+1) (Guibas & Sedgewick 1978, CLRS 13장).

이 레슨의 "침입형(intrusive)"은 DS-M01의 list_head와 같은 뜻이다. 트리는 키도 모르고 메모리도 할당하지 않는다. 노드는 사용자 객체의 필드이고, container_of로 객체를 되찾는다.

Part A — 인코딩, 회전, 삽입, 순회, 검사기#

  • parent_color 한 워드에 부모 주소와 색을 함께 넣는다. rb_parent, rb_color, rb_set_parent, rb_set_parent_color를 구현한다.
  • rb_rotate_left/right: 부모 링크까지 고치고 색은 건드리지 않는다.
  • rb_insert_color: 호출자가 rb_link_node로 빨강 노드를 연결한 뒤 부른다. 3 케이스 + 거울상.
  • item_insert: 사용자 쪽 코드다. 키를 비교하며 struct rb_node **link로 내려간다.
  • rb_first/last/next/prev: 스택 없이 부모 포인터로 걷는다.
  • rb_validate: 위반 종류를 enum으로 돌려준다. 사이클에도 끝나야 한다.

Part B — 삭제와 대규모 검증#

  • rb_erase: 자식 0~1개면 노드 자체가 빠지고, 자식 2개면 후계자 노드가 빠져서 삭제 노드 자리로 옮겨 간다.
  • rb_erase_color: 이중 검정 복구 4 케이스 + 거울상.
  • 검증: 케이스별 고정 트리 17개, 키 6개의 삽입 순열 720 × 삭제 순열 720 전수, 랜덤 20만 회(n ≤ 32, 매 연산 전체 검사), 랜덤 100만 회(n ≤ 8192, 1000회마다 전체 검사 + 끝에 전부 삭제).
  • 모든 케이스가 양 방향으로 실제 실행됐는지, 연산당 회전이 삽입 ≤ 2, 삭제 ≤ 3인지 체크한다.

Part C — 타임아웃 큐 (cached leftmost)#

  • rb_insert_color_cached, rb_erase_cached로 가장 이른 노드를 O(1)에 읽는다.
  • tq_add, tq_cancel, tq_next_deadline, tq_tick을 만든다. 32비트 틱 랩어라운드, 같은 시각은 FIFO, 이미 등록된 타이머는 거절, 취소는 여러 번 불러도 안전, 주기 타이머 재등록, 콜백이 다른 타이머를 취소해도 안전, 한 번에 발화하는 수 제한(budget).

2. Problem (English)#

Intrusive red-black tree (Linux rbtree style).

struct rb_node { uintptr_t parent_color; struct rb_node *rb_right, *rb_left; }; is embedded in user objects. Bit 0 of parent_color is the colour (0 = red, 1 = black); the rest is the parent pointer. State the alignment assumption with _Static_assert.

Implement, without malloc and without recursion in the tree code:

  1. rb_insert_color(node, root), called after rb_link_node() attached node as a red leaf; rb_first/last/next/prev.
  2. rb_erase(node, root). A node with two children is replaced by relinking its successor (object addresses must stay valid; do not copy keys).
  3. rb_validate(root, n, key_fn, ctx, allow_dup) returning which invariant failed: root black, no red-red, equal black height, global BST order, parent links, node count.
  4. A timeout queue on struct rb_root_cached: tq_add, tq_cancel, tq_next_deadline (O(1)), tq_tick(q, now, budget, fire, arg). Ticks are 32-bit and wrap; equal deadlines fire in FIFO order.

Test with exhaustive permutations of a small key set and 1,000,000 random operations against a reference model.

Follow-ups: why are at most 2 / 3 rotations enough? Is "O(1) rotations" the same as O(1) worst-case work? RB or AVL for a lookup-heavy table? When is a sorted list better? What breaks with __packed? Can an ISR touch this tree?

4. 힌트#

힌트 1 — 왜 빨강이 0인가

새 노드는 항상 빨강으로 들어간다(검정으로 넣으면 검정 높이가 깨진다. 빨강이면 깨질 수 있는 건 "빨강 연속" 하나뿐이다). RB_RED == 0이면 rb_link_node가 node->parent_color = (uintptr_t)parent; 한 줄로 끝난다.

힌트 2 — 삽입 복구는 "삼촌"만 본다

node와 부모가 둘 다 빨강이면 조부모는 반드시 검정이고 존재한다(부모가 빨강이니 루트가 아니다). 결정은 삼촌의 색으로 한다. 빨강이면 색만 뒤집고 두 칸 위로, 검정이면 회전으로 끝낸다. 꺾인 모양이면 먼저 부모에서 회전해 일직선을 만든다.

힌트 3 — rb_next는 두 갈래

오른쪽 자식이 있으면 그 서브트리의 왼쪽 끝이다. 없으면 "내가 왼쪽 자식인 첫 조상"까지 올라간다. 오른쪽 자식이었던 동안은 계속 올라간다는 뜻이다.

힌트 4 — 삭제에서 "빠지는 색"을 먼저 정한다

복구가 필요한지는 "트리에서 실제로 사라지는 위치의 색"으로 정해진다. 자식 2개면 그 위치는 후계자의 원래 자리다. 빠지는 색이 검정이고 그 자리를 잇는 자식이 있으면 그 자식은 빨강이므로(자식이 하나뿐인 노드는 검정 높이 때문에 빨강 잎만 가질 수 있다) 검정으로 칠하면 끝이다. 자식이 없을 때만 복구 루프에 들어간다.

힌트 5 — 이중 검정은 NULL에서 시작한다

첫 반복에서는 node가 NULL이다. 그러면 "왼쪽 자식인가?"를 어떻게 판단할까? parent->rb_right != node로 본다. 오른쪽이 NULL이고 node도 NULL이면 node는 오른쪽 자식이다. 왼쪽과 오른쪽이 둘 다 NULL일 수는 없다(검정 하나가 빠졌으니 형제 쪽에 노드가 있어야 검정 높이가 맞았다).

힌트 6 — Case 1의 다음은 항상 끝난다

Case 1을 지나면 부모는 빨강이고 형제는 검정이다. 이 상태에서 Case 2는 "부모가 빨강"이라 바로 끝나고, Case 3/4도 그 반복에서 끝난다. 그래서 Case 1은 삭제 한 번에 최대 한 번이다.

힌트 7 — 캐시를 고치는 순서

rb_erase_cached에서 캐시를 옮길 때 rb_next(node)는 rb_erase 전에 부른다. 지운 뒤에 부르는 코드는 지운 노드의 남은 필드에 기대게 되고, 이는 구현이 필드를 지우지 않는다는 우연에 기대는 것이다(7장에서 실제로 실험한다).

5. 풀이#

Part A — 색 비트 인코딩: 무엇을 가정하는가#

가정깨지는 경우우리 방어
노드 주소의 비트 0이 항상 0정렬 1인 타입, __packed 컨테이너_Static_assert(_Alignof(struct rb_node) >= 2), 컨테이너별 RB_CONTAINER_OK (연습 6)
포인터 ↔ 정수 변환 뒤 비트를 조작해도 의미가 유지됨void * ↔ uintptr_t 왕복만 표준이 보장한다(C11 7.20.1.4). 변환 결과의 비트 의미는 구현 정의다(6.3.2.3)주소를 그대로 정수로 쓰는 gcc/clang + ARM/x86에서 동작. 표준만으로 보장되는 코드는 아니다
포인터 하위 비트를 지워도 같은 객체포인터 인증이나 캐퍼빌리티를 쓰는 아키텍처이 레슨의 범위 밖. 해당 플랫폼이면 색을 별도 필드로

리눅스는 struct rb_node에 __attribute__((aligned(sizeof(long))))를 달고, include/linux/rbtree_augmented.h의 __rb_parent에서 ~3으로 하위 2비트를 지운다. 정렬이 4 이상임을 가정하는 셈이다(소스 주석에 "allegedly CRIS needs it"이라고 적혀 있다). 우리는 필요한 만큼만 지우려고 ~1을 쓰고, 정렬 ≥ 2만 가정한다. Cortex-M4 타깃에서 sizeof(struct rb_node) = 12, _Alignof = 4다(_Static_assert로 thumbv7em 컴파일 확인).

부모 포인터를 읽는 비용은 명령 하나(bic)가 더 붙는 것이 전부다. 색 읽기는 컴파일러가 ldrb로 줄였다. 리틀엔디언이라 워드의 비트 0이 첫 바이트에 있기 때문이다. 대신 rb_set_parent는 읽기-수정-쓰기(read-modify-write)다. 인터럽트 코드와 같은 노드를 만지면 이 세 명령 사이에서 깨진다(8장 Q6).

Part A — 회전과 삽입 복구#

회전 자체는 DS-M07과 같다. inorder를 보존하고 높이를 옮긴다. 다른 점은 부모 링크를 함께 고쳐야 한다는 것이다.

링크 쓰기 6개 중 하나라도 빠지면 모양은 맞아 보이는데 나중에 rb_next나 다음 복구가 틀린다. 검사기의 부모 링크 확인이 이걸 잡는다.

세 케이스의 흐름. 진입 시 유일한 위반은 "node와 부모가 둘 다 빨강"이다.

케이스조건처리회전다음
1삼촌 빨강부모·삼촌 검정, 조부모 빨강0node = 조부모, 반복
2삼촌 검정, 꺾임부모에서 회전1Case 3
3삼촌 검정, 일직선부모 검정, 조부모 빨강, 조부모에서 회전1끝

회전이 2번을 넘지 않는 이유. 회전이 일어나는 경로는 Case 2 → Case 3 또는 Case 3뿐이고 Case 3 뒤에는 break다. Case 1은 회전이 없다. 그래서 회전 ≤ 2. 그러나 Case 1은 O(log n)번 반복될 수 있다. 뒤의 측정표에서 삽입 한 번에 색 변경이 55번까지 나온다.

왜 Case 3 뒤에 끝나는가. 회전 후 서브트리의 루트가 검정이고, 이 서브트리의 검정 높이는 삽입 전과 같다. 위로 전달되는 변화가 없다.

리눅스 lib/rbtree.c의 __rb_insert 주석도 같은 번호를 쓴다("Case 1 - node's uncle is red (color flips)", "Case 2 - right rotate at parent", "Case 3 - left rotate at gparent"). 리눅스는 포인터 쓰기를 케이스 안에 직접 적고 __rb_rotate_set_parents만 헬퍼로 쓴다. 우리는 읽기 쉽게 회전 전체를 함수로 뺐다.

Part B — 삭제: 위치와 색을 분리해서 본다#

삭제는 두 단계다.

1단계: 실제로 사라지는 위치를 정한다. 자식이 0~1개면 node의 자리다. 자식이 2개면 후계자(succ)의 원래 자리다. succ는 왼쪽 자식이 없으니 자식이 최대 하나다. 그리고 succ의 색은 빠지는 자리에서 사라지고, succ 노드 자체는 node의 parent_color를 물려받아 node의 색이 된다. 이 두 줄이 핵심이다.

왜 키를 복사하지 않나. 교과서식 "후계자의 키를 node에 복사하고 후계자를 지운다"는 침입형에서 쓸 수 없다. 객체 자체가 item_t이고 노드는 그 안의 필드다. 키만 옮기면 다른 코드(DS-M01처럼 리스트에 같이 걸려 있거나 타이머 핸들을 쥔 코드)가 들고 있는 item_t *가 엉뚱한 키를 가리키게 된다. DS-M07에서 "복사가 아닌 재연결"이라고 한 것과 같은 이유다.

2단계: 검정이 빠졌을 때만 복구한다.

RB vs AVL: 측정#

demo_rb_vs_avl.c 실제 출력이다. AVL은 DS-M07의 재귀 알고리즘이다(부모 포인터 없음, 노드에 height 저장). meta는 실제로 값이 바뀐 메타데이터 수다. RB는 색 변경, AVL은 height 변경이고, 조기 종료하는 반복 구현이 쓰게 될 양과 같다.

읽는 법(10k, 100k 행도 같은 추세라 생략했다):

  • 높이: 랜덤에서는 RB와 AVL이 같다(24 vs 24). 정렬 입력에서 차이가 난다. RB 37 vs AVL 20이고, RB는 상한 39.9에 가깝다. 타임스탬프처럼 단조 증가하는 키는 펌웨어에서 흔하다.
  • 평균 깊이는 정렬 입력에서도 거의 같다(19.33 vs 18.95). 높이를 만드는 긴 척추가 소수 경로이기 때문이다. 즉 최악의 검색은 RB가 1.85배 깊지만 평균 검색은 거의 같다.
  • 회전 상한: RB 삭제는 항상 ≤ 3이다. AVL 삭제는 관측 최대가 n과 함께 커진다(1000: 4, 1만: 6, 10만: 7, 100만: 8회). 이것이 RB의 진짜 장점이고, 리눅스 문서가 "faster real-time bounded worst case performance for insertion and deletion"이라고 쓴 이유다.
  • 그러나 색 변경은 RB도 O(log n)이다. 삽입 한 번의 색 변경 최대는 RB 55(정렬), AVL height 변경 최대는 21이다. "회전 O(1)"은 "작업량 O(1)"이 아니다.

벌크 시간(같은 프로그램, -O2, Apple M6, 5회 중앙값 [최소, 최대], 키마다 재지 않음. 타이머 눈금이 41.7 ns라서다):

  • 검색은 구별되지 않는다. 범위가 겹친다. 평균 깊이가 같으니 그럴 만하다.
  • RB erase(ptr) 27.7 ns를 AVL 138 ns와 비교하면 안 된다. RB 쪽은 검색이 없다. 공정한 비교는 RB find + erase다(121 vs 138 ns, 100k에서는 범위가 겹치고 100만에서는 안 겹친다). 27.7 ns는 침입형의 이득이다. 객체 포인터를 이미 쥐고 있으면 검색 비용이 사라진다.
  • 삽입이 AVL보다 빠른 이유는 이 구현 차이가 섞여 있다. AVL 쪽은 재귀로 경로 전체의 height를 다시 계산한다. 이 표는 "RB가 AVL보다 빠르다"가 아니라 "이 두 구현에서는 이렇다"로 읽어야 한다. 알고리즘 비교는 위의 작업량 표가 더 믿을 만하다.
  • 측정 중 다른 프로세스가 돌고 있었고 macOS에서는 스레드를 코어에 고정할 수 없다. 첫 실행에서는 100만 행의 범위가 2배 넘게 벌어지기도 했다. 표의 수치는 비율만 참고하자.

Part C — 타임아웃 큐#

타이머는 항상 "가장 이른 것"을 물어보는 구조다. rb_first는 O(log n)이니 캐시를 둔다. 리눅스의 struct rb_root_cached가 정확히 이것이다(rb_root에 rb_leftmost 포인터 하나를 추가했다). 리눅스의 범용 타이머 큐 lib/timerqueue.c도 rb_add_cached와 rb_erase_cached로 만들어져 있고, 노드를 넣기 전에 RB_EMPTY_NODE로 이중 등록을 검사한다.

leftmost 판단은 삽입 경로에서 공짜로 얻는다. 내려가며 한 번이라도 오른쪽으로 갔으면 leftmost가 아니다. 추가 비교가 없다.

동률 FIFO. 같은 시각이면 오른쪽으로 내려간다. 그러면 in-order 순서가 등록 순서가 되고, 회전은 in-order를 보존하므로 항상 유지된다. 리스트 기반 RTOS에서 쓰는 동작과 같다(FreeRTOS vListInsert도 같은 값이면 뒤에 넣는다). 동률을 금지하는 구현도 있다. Zephyr rbtree 문서는 lessthan_fn에 "equal"을 허용하지 않는다고 적고 있으니, 거기서 타이머를 쓰려면 키에 일련번호를 붙여야 한다.

랩어라운드. (int32_t)(a - b) < 0은 a와 b의 거리가 2³¹ 미만일 때만 뜻이 있다. 거리가 그보다 크면 전순서(순서를 매기는 관계)가 아니게 되고, 트리 전체가 깨진다. 그래서 tq_add는 now 기준 ±2³⁰ 안의 만료 시각만 받는다. 활성 타이머 어느 쌍을 골라도 거리가 2³¹ 미만이다. 만료된 뒤 처리가 늦어지는 경우(backlog)를 위한 창도 여기 포함된다. 범위를 벗어난 값의 (int32_t) 변환은 C 표준상 구현 정의다(C11 6.3.1.3). gcc 문서는 2^N 모듈러 축소로 명시하고, 이 맥의 clang에서도 랩어라운드 체크가 통과한다.

콜백 안전성. tq_tick은 매 반복에서 rb_leftmost를 다시 읽는다. 콜백이 다른 타이머를 취소하거나 새 타이머를 넣어도 다음 반복의 전제가 깨지지 않는다. 주기 타이머는 콜백 전에 재등록한다. 그래야 콜백이 자기 자신을 cancel할 수 있다.

budget. 한 tick에서 발화할 수를 제한한다. 주기 타이머가 now보다 뒤처졌을 때 tick 하나가 끝없이 돌며 ISR이나 스케줄러를 붙잡는 것을 막는다. 남은 건 다음 tick이 처리한다(체크: tq_tick(q, 95, 3, ...) → 3회, 다음 호출 → 6회).

펌웨어 관점에서 정렬 리스트와 비교. 작은 RTOS의 지연 목록은 정렬 연결 리스트로 충분한 경우가 많다. FreeRTOS vListInsert는 정렬 삽입을 위해 리스트 앞에서부터 차례로 걷는다. 그러면 언제 트리가 이득일까? demo_timerq_vs_list.c 실제 출력(정상 상태 n개, "맨 앞 꺼내기 + 재등록" 1쌍, 만료 시각 균등 분포):

  • 비교 수만 보면 n=8에서 이미 트리가 적지만(3.2 vs 5.3), 시간은 n=32까지 리스트가 빠르다. 트리는 비교 외에 재균형 비용을 낸다. n=64에서 범위가 겹치고, 128 이상에서 트리가 뚜렷이 앞선다.
  • 이 교차점은 이 맥의 값이다. 교차점은 캐시, 분기 예측, 코어에 따라 움직인다. D-cache가 없는 Cortex-M0/M3 계열에서는 포인터 추적 비용이 다르니 타깃에서 재야 한다.
  • 비교 수의 최악은 플랫폼과 무관한 숫자다. 리스트는 n−1번(인터럽트를 막은 임계 구역이면 그대로 지연이다), 트리는 높이 이하다.
  • 입력 분포가 다르면 결론도 달라진다. 대부분 가까운 시각에 만료되는 타이머라면 리스트는 앞쪽에서 삽입 위치를 찾으니 측정값보다 유리하다.

6. 정답 코드#

7. 자주 하는 실수#

  1. rb_set_parent가 색을 지운다. n->parent_color = (uintptr_t)p; — 회전에서 쓰면 형제의 색이 빨강으로 바뀐다(빨강 = 0). 고친 코드는 (uintptr_t)p | (n->parent_color & RB_COLOR_MASK). 실제로 넣어 보면 고정 트리 시험과 ASan이 함께 잡는다.
  2. Case 4에서 부모 색을 물려받지 않는다. 형제는 rb_color(parent)를 받아야 한다. 무조건 검정으로 칠하면 p가 빨강이었던 경우 검정 높이가 깨진다. 고정 트리 (((10B)20r(30B(40r)))50B(70B))가 이 경우를 잡는다.
  3. Case 2 뒤에 n과 p를 안 바꾼다. 회전으로 n이 위로 갔는데 그대로 Case 3을 부르면 p와 n의 색·회전 대상이 어긋난다.
  4. 후계자 키를 복사한다. 트리 모양은 맞는데 객체 동일성이 깨진다. t_erase의 동일성 검사가 잡는다. 실제 코드에서는 타이머 핸들이 다른 객체를 가리키게 되는 버그다.
  5. fix_parent를 잘못 잡는다. 후계자가 node의 오른쪽 자식이면 복구가 시작될 위치의 부모는 node가 아니라 후계자 자신이다. node를 그대로 쓰면 이미 트리에서 빠진 노드를 따라 복구한다.
  6. 순서 검사를 부모-자식 비교로 끝낸다. ((10B(25r))20B(30B))는 지나간다. in-order로 직전 키와 비교해야 한다.
  7. 시각을 a < b로 비교한다. 랩어라운드 시각에서 만료 순서가 뒤집힌다.
  8. 캐시 갱신을 rb_erase 뒤에 한다. 이 실수는 흥미롭다. 뮤턴트를 넣어 보니 테스트를 통과했다. rb_erase가 지워진 노드의 rb_right와 부모 필드를 건드리지 않아서 rb_next가 우연히 맞게 동작한다. 그런데 지운 뒤 RB_CLEAR_NODE를 먼저 부르면 NULL이 나오고 잡힌다. 지운 노드의 필드에 기대는 코드는 디버그 빌드에서 노드를 포이즈닝하는 순간 깨진다. "테스트가 통과했다"가 "맞다"는 아니다.
  9. 컨테이너를 __packed로 만든다. 노드 주소의 비트 0이 1일 수 있고, 그러면 rb_parent가 틀린 주소를 돌려준다. RB_CONTAINER_OK로 컴파일 시점에 거절한다(연습 6). 프로토콜 헤더와 같은 구조체에 트리 노드를 넣지 않는 것이 습관으로 더 낫다.
  10. RB_EMPTY_NODE 없이 취소를 짠다. 한 번 더 취소하면 지워진 노드를 다시 지운다. RB_CLEAR_NODE로 표시하고 검사하면 여러 번 불러도 안전하다.

8. 면접 Q&A#

Q1. 색을 포인터 비트에 넣는 대신 별도 필드를 두면 뭐가 나쁜가요?

필드 하나가 Cortex-M에서 패딩 포함 4바이트, 64비트에서 8바이트를 쓴다. 노드 12 B가 16 B로 33% 커진다. 트리가 큰 임베디드에서는 의미 있다. 대가는 ① 정렬 가정, ② 모든 부모 접근에 마스크, ③ 부모 쓰기가 read-modify-write가 된다는 것이다. ②는 실측한 대로 bic 한 명령이다. ③은 ISR과 공유하면 문제가 되지만, 트리는 어차피 임계 구역 안에서만 만져야 하므로 별도의 비용은 없다. 꼬리질문 "더 줄일 수 있나?": Zephyr rbtree 문서에 따르면 노드는 포인터 두 개뿐이고 부모 포인터가 없다. 내려가면서 스택에 경로를 쌓아 올라갈 길을 얻는다. 노드 RAM을 스택 사용(로그 크기)과 맞바꾼 설계다.

Q2. "삽입은 회전 2번, 삭제는 3번이니 O(1)"이라고 말해도 되나요?

회전 수에 한해서만 맞다. 위치를 찾는 데 O(log n), Case 1과 Case 2 반복이 O(log n)이다. 측정에서 삽입 한 번의 색 변경은 최대 55회였다(100만 개, 정렬 입력). 임계 구역 길이를 재는 사람에게 O(1)이라고 답하면 틀린다. 정확한 답은 "구조 변경은 O(1)이고 작업량은 O(log n)이며, 높이로 상한이 잡힌다"이다.

Q3. RB와 AVL 중 어떻게 고르나요?

측정 기준으로 답한다. 랜덤 입력의 높이와 평균 깊이는 같았고 검색 시간도 구별되지 않았다. 차이는 두 군데다. ① 정렬 입력에서 RB 높이가 AVL보다 1.85배 커서(37 vs 20) 최악의 검색 경로가 길다. ② RB 삭제 회전은 ≤ 3으로 묶이지만 AVL은 O(log n)이고 이번 측정에서 최대 8회였다. 회전은 메모리 쓰기가 몰리는 작업이니, 쓰기가 많거나 동시 접근 비용이 크면 RB, 최악 검색 깊이가 중요한 읽기 위주 테이블이면 AVL이다. 그리고 노드 크기는 구현 선택이다. 우리 AVL은 부모 포인터가 없어서 더 작았다(24 vs 32 B). 알고리즘이 아닌 구현 차이다.

Q4. 왜 삭제에서 키를 복사하면 안 되나요?

침입형에서는 노드가 객체의 일부이기 때문이다. 복사는 "어느 객체가 어느 키를 가지는가"를 바꾼다. 다른 곳이 쥐고 있는 포인터(타이머 핸들, 리스트 연결, DMA 디스크립터의 back pointer)가 조용히 다른 데이터를 가리키게 된다. 재연결은 객체 주소를 그대로 둔다. 비용은 상수개 포인터 쓰기다.

Q5. 왜 취소가 "검색 없이" O(log n)인가요? 리스트 취소는 O(1)인데요?

객체 안에 노드가 있으니 rb_erase에 노드 포인터를 바로 넘긴다. 탐색 단계가 없다. 그래도 O(log n)인 이유는 복구가 위로 올라갈 수 있어서다(Case 2 반복). 이중 연결 리스트의 O(1) 제거보다 느리지만, 리스트는 정렬 삽입이 O(n)이다. 측정에서 RB erase(ptr)는 find+erase보다 4배 이상 빨랐다(27.7 vs 121 ns, n=10만).

Q6. ISR에서 이 타이머를 쓸 수 있나요?

그대로는 안 된다. 회전 한 번이 여러 필드를 고치고, 그 사이의 트리는 불변식이 깨져 있다. 태스크가 회전 중일 때 ISR이 들어와 같은 트리를 만지면 끝이다. 방법은 ① 트리 조작 전체를 인터럽트 금지 또는 스케줄러 잠금으로 감싼다(임계 구역 길이 = 높이에 비례. 그래서 n과 높이를 재어 둔다), ② ISR은 lock-free 링으로 요청만 넘기고(DS-A01, DS-A02) 태스크가 트리를 처리한다. 리눅스 lib/rbtree.c 주석에도 "tree rotations are not atomic so a lookup might"로 시작하는 경고가 있고, 락 없는 조회를 쓰려면 seqcount 같은 추가 장치가 필요하다. 리눅스 문서는 "Locking is also left up to the user"라고 명시한다.

Q7. 왜 리눅스는 "비교 콜백"이 아니라 사용자가 직접 삽입 루프를 쓰게 하나요?

문서에 따르면 "users are expected to write their own tree search and insert functions which call the provided rbtree functions"이다. 비교 콜백을 없애면 비교가 인라인되고 키 타입이 자유롭다. 우리 item_insert와 tq_add처럼 사용자 코드가 struct rb_node **link로 내려가고, 트리 코어(rb_insert_color)는 키를 아예 모른다. 그래서 라이브러리는 키 타입별로 복제되지 않는다. 대가는 호출마다 짧은 루프를 쓴다는 것이고, Zephyr는 반대로 lessthan_fn 콜백을 받는다. 어느 쪽이든 트레이드오프다.

Q8. 이 코드는 어떻게 믿나요? 테스트 전략을 설명해 보세요.

네 겹이다. ① 고정 트리 + 정확한 결과 문자열로 케이스별 동작 검증 ② 검사기 음성 테스트(위반을 넣어 enum 값까지 확인) ③ 전수 순열로 작은 n의 모든 경로 ④ 참조 모델 대조 랜덤 100만 회, 카운터로 "실제로 모든 케이스가 양 방향으로 실행됐는가"까지 체크. 마지막으로 뮤턴트로 테스트 자체를 시험했다. 19개 중 18개를 잡았고, 살아남은 하나(7장 8번)는 구현에 기댄 코드라는 걸 알려 주었다.

Q9. 펌웨어에서 이 구조를 안 쓰는 게 나은 경우는요?

n이 수십 이하이고 삽입 빈도가 낮으면 정렬 리스트가 더 빠르고 단순하다(이 맥 측정에서 n=32까지 리스트 승). 키 범위가 작고 고정이면 타이머 휠(DS-M06, 지연 리스트 비교는 RTOS-M07)이나 우선순위 비트맵(RTOS-B04)이 O(1)로 이긴다. 플래시 인덱스처럼 한 번에 페이지를 읽어야 한다면 B+ 트리(DS-A08)가 맞다. 그리고 RAM이 빠듯하면 포인터 3개/노드는 크다. Zephyr처럼 2포인터 구조나 인덱스 기반 풀로 줄인다.

9. 추가 연습#

연습 1 — 가장 키 큰 RB 트리#

검정 높이 bh에서 높이 2·bh를 만드는 최소 트리를 직접 구성하라. 노드 수는 얼마인가?

답

왼쪽 척추를 검정·빨강 교대로 두고, 나머지 자리에 최소 노드(완전 검정 트리)를 둔다. T(b) = T(b−1) + 2^b, T(0) = 0이므로 n = 2^(b+1) − 2, 높이 2b다. 즉 h = 2·log₂(n+2) − 2로 상한 2·log₂(n+1)에 거의 닿는다. 실제 출력: bh=10 n=2046 height=20. 검사기가 유효한 트리로 인정한다. 다만 삽입·삭제 순서로 이 트리에 도달할 수 있는지는 별개 문제이고, 여기서는 트리를 직접 구성했다.

연습 2 — rb_replace_node#

같은 키의 새 객체로 노드를 교체하라. 재균형 없이 O(1)이어야 한다.

답

노드 3워드를 그대로 복사하고(*nw = *victim), 양쪽 자식의 부모와 부모의 자식 링크만 고친다. 트리 모양과 색이 그대로라 불변식은 건드릴 일이 없다. 키가 같아야 한다는 전제를 지키지 않으면 순서가 깨진다. 객체 교체 없이 업데이트하는 패턴에 쓴다.

연습 3 — 후위 순회로 전체 해제#

rb_first_postorder / rb_next_postorder를 구현하고, 방문 중 노드를 망가뜨려도(해제 흉내) 순회가 안전함을 보여라.

답

후위 순회는 자식을 먼저 방문하므로 재균형 없이 전부 해제할 수 있고, rb_erase를 n번 부르는 것보다 낫다. 현재 노드를 지우기 전에 다음 노드를 구해야 한다. 다음을 구할 때 읽는 것은 현재 노드의 부모 필드와 아직 안 지운 부모의 링크뿐이다. 리눅스에도 rb_first_postorder와 rb_next_postorder가 있다.

연습 4 — 한 객체, 두 트리#

연결 객체 하나를 id 트리와 만료 시각 트리에 동시에 넣어라.

답

노드를 두 개(by_id, by_deadline) 넣고 container_of에서 멤버 이름만 다르게 쓴다. 침입형의 장점이 그대로 드러나는 예다. 두 트리는 서로의 링크를 건드리지 않는다. 만료 키에 동률이 있으면 id를 섞어 전순서를 만들어야 검사기가 통과한다.

연습 5 — lower_bound와 구간 순회#

key 이상의 첫 노드를 찾고 rb_next로 구간을 걸어라. 전체 순회의 포인터 이동 수도 세어 보라.

답

내려가며 "key 이상인 후보"를 기억한다. 전체 in-order는 간선을 많아야 두 번 지나므로 이동 수 ≤ 2(n−1), 즉 rb_next는 상각 O(1)이다(최악 한 번은 O(log n)). 실제 출력: n=1805 full in-order walk: 3597 pointer hops, 2(n-1)=3608.

연습 6 — packed 컨테이너 컴파일 시점 거절#

노드의 정렬 가정이 깨지는 컨테이너를 컴파일 시점에 거절하는 매크로를 만들어라.

답

RB_CONTAINER_OK(T, m) = _Alignof(T) >= _Alignof(struct rb_node) && offsetof(T, m) % _Alignof(struct rb_node) == 0. 구조체의 정렬과 멤버의 오프셋 둘 다 확인해야 한다. struct __attribute__((packed)) { char tag; struct rb_node node; }은 오프셋 1, 정렬 1이라 거절된다. 런타임에 실제로 터뜨리는 것은 UB라서 일부러 시험하지 않았다.

10. 핵심 정리#

  • 색은 부모 포인터 비트 0에 넣는다. 노드 정렬 ≥ 2가 전제이고 _Static_assert로 적어 둔다. packed 컨테이너는 이 가정을 깬다. 빨강 = 0이라 rb_link_node가 한 줄이다.
  • 삽입: 삼촌 빨강 → 색 뒤집고 위로, 삼촌 검정 → 회전으로 끝(꺾임은 먼저 펴기). 회전 ≤ 2.
  • 삭제: "사라지는 색"이 검정이고 잇는 자식이 없을 때만 복구한다. 형제 빨강 → 회전, 조카 둘 다 검정 → 위로, 먼 조카 검정 → 형제 회전, 먼 조카 빨강 → 부모 회전 후 끝. 회전 ≤ 3.
  • 자식 2개 삭제는 키 복사 금지. 후계자 노드를 재연결한다.
  • 회전 O(1)은 작업량 O(1)이 아니다. 색 변경과 경로 탐색은 O(log n)이고, 측정 최대 색 변경은 55회였다.
  • 측정: 랜덤에서 RB·AVL 높이와 검색은 같다. 정렬 입력에서 RB 높이 37 vs AVL 20. RB 삭제 회전 ≤ 3, AVL은 최대 8회 관측.
  • 타이머: 캐시로 다음 만료 O(1), 같은 시각은 오른쪽으로 FIFO, 시각 비교는 (int32_t)(a - b) < 0이고 창은 ±2³⁰. 이 맥에서 n ≤ 32는 정렬 리스트가 더 빠르다.
  • 검증은 고정 트리 + 음성 테스트 + 전수 + 모델 대조 + 뮤턴트까지 해야 "케이스를 다 지났다"고 말할 수 있다.
