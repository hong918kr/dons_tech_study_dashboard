> Stanford · 2025-11-21 · 01:49:54 · [영상 링크](https://www.youtube.com/watch?v=k1njvbBmfsw) · 강사: Kian Katanforoosh (Andrew Ng 공동 진행)

## 📌 한 줄 요약

기본(base) 대규모 언어 모델(LLM, large language model)을 실제 제품 수준으로 끌어올리는 "수직축 최적화" 기법을 총정리한다. 프롬프트 엔지니어링(prompt engineering) → 파인튜닝(fine-tuning) → 검색 증강 생성(RAG, retrieval augmented generation) → 에이전트형 워크플로우(agentic workflow) → 평가(eval) → 멀티 에이전트(multi-agent) 순으로, 각 기법을 언제·왜·어떻게 쓰는지 실무 관점에서 설명한다. 깊이보다 **폭(breadth)**을 갖춰 필요할 때 빠르게 깊게 파고들 수 있게 하는 것이 강의의 목표다.

## 🎯 핵심 메시지

> LLM 성능을 높이는 길은 두 축이다. **수평축**은 더 좋은 기반 모델로 갈아타는 것(GPT-3.5 → GPT-4 → GPT-5), **수직축**은 같은 모델을 프롬프트·체이닝·RAG·에이전트·멀티에이전트로 감싸 성능을 끌어내는 것이다. 이 강의는 수직축을 다룬다.

**보조 메시지**
- 바닐라(vanilla) 사전학습 모델은 도메인 지식 부족, 최신성 결여, 제어 어려움, 환각(hallucination), 출처 부재, 제한된 컨텍스트 윈도우(context window) 등의 한계를 가진다.
- **파인튜닝은 가능한 한 피하라.** 라벨 데이터·시간·비용이 많이 들고, 다 만들 때쯤 다음 모델이 나와 당신의 파인튜닝 모델을 이긴다.
- **체이닝(chaining)이 프롬프트 기법 중 가장 강력**하다 — 성능뿐 아니라 단계별 디버깅과 제어가 가능해지기 때문이다.
- 좋은 엔지니어는 **결정론적(deterministic) 사고와 퍼지(fuzzy) 사고를 오갈 줄 안다.** 결정론으로 끝낼 수 있는 건 끝내고, 퍼지가 필요한 곳엔 가드레일(guardrail)을 친다.
- 에이전트형 시스템은 "관리자처럼" 역할을 나눠 설계하라. 그리고 **eval 없이는 개선할 수 없다.**

## ⚠️ 바닐라 LLM의 한계 (왜 증강이 필요한가)

| 한계 | 설명 / 예시 |
|---|---|
| 도메인 지식 부족 | 작물 질병 판별처럼 세상에 없는 데이터셋 → 사전학습 모델은 모름 |
| 분포 차이 | 학습 데이터(고품질)와 실제 데이터(저품질) 분포가 다름 (GAN에서 본 문제와 유사) |
| 최신성 결여 | 컷오프(cutoff) 이후 트렌드·신조어 모름 (트럼프의 "covfefe" 트윗 일화) |
| 제어 어려움 | MS의 인종차별 봇(2016, 16시간 만에 내림), Grok·OpenAI도 통제 실패 |
| 좁은 과제 약점 | 폭넓은 지식은 있어도 정밀·저지연이 필요한 좁은 과제엔 부족 |
| 무겁고 느림 | 능력의 2%만 쓰는데 거대 모델 → 가지치기(prune)·양자화(quantize) 필요 |
| 출처 부재 | 의료·법률·연구·교육은 출처 필수, 그런데 모델은 가짜 논문을 지어냄 |
| 스타일·포맷 불일치 | 법률 문서처럼 단어 하나가 중요한 영역에서 정밀도 부족 |
| 과제별 이해 부족 | 산업마다 "부정 리뷰"의 기준(NPS)이 다름 → 정렬(alignment) 필요 |
| 제한된 컨텍스트 | 최신 모델도 수십만 토큰 수준(20만 토큰 ≈ 책 2권). 청킹·임베딩 필요 |
| 어텐션 한계 | 큰 컨텍스트에서 특정 사실 집중이 약함 → **needle in a haystack** 벤치마크 |

> **RAG는 미래에도 유효할까?** 무한 컴퓨트가 있으면 전체 코퍼스를 매번 읽으면 되므로 RAG가 불필요하다는 논쟁이 있다. 그러나 지연(latency)과 출처(sourcing)라는 이점 때문에, 검색 엔진이 여전히 링크를 랭킹해 보여주듯 RAG류 접근은 오래 유효할 가능성이 크다.

## ✏️ 프롬프트 엔지니어링 (1차 최적화 라인)

> **동기 (BCG 연구):** 컨설턴트를 ① AI 없음 ② AI 사용 ③ AI + 프롬프트 교육 세 그룹으로 나눠 비교. **재그드 프론티어(jagged frontier)** — AI가 도움 되는 영역과 오히려 해가 되는 영역이 들쭉날쭉하다. 프론티어 밖 과제를 AI에 맡기고 검토를 소홀히 하면 "운전 중 졸기(falling asleep at the wheel)"처럼 결과가 더 나빠진다. **교육받은 그룹이 가장 우수** → 이 강의가 중요한 이유.
>
> **센타우르(centaur) vs 사이보그(cyborg):** 센타우르는 큰 과제를 통째로 위임(분업), 사이보그는 모델과 빠르게 주고받음(혼합). 학생은 사이보그형, 업무 자동화는 센타우르형 경향. "프롬프트 엔지니어"는 직업이 아니라 누구나 가질 스킬이다.

**기본 설계 원칙 — 나쁜 → 좋은 프롬프트**

```
나쁨:  Summarize this document.
좋음:  Summarize this 10-page scientific paper on renewable energy in
       5 bullet points, focusing on key findings and implications for
       policy makers.
```
→ 청중, 길이/형식, 초점을 명시할수록 좋아진다.

**주요 기법 요약**

| 기법 | 내용 |
|---|---|
| 예시 제공 | "여기 좋은 요약 예시가 있다" 식으로 모범 답안을 보여줌 |
| 역할 부여(act as) | "act as a renewable energy expert..." — GitHub의 *awesome prompt* 같은 프롬프트 저장소 참고 |
| 반성(reflection) | "critique your own output" — 출력 후 스스로 비평하고 다시 개선 (보통 가장 효과적) |
| 사고 사슬(chain of thought) | "think step by step, do not skip any step" + 단계 명시 (2023 논문이 대중화) |
| 프롬프트 템플릿(prompt template) | 코드에 넣어 사용자별로 확장. (예: Workera의 Cara가 HR 메타데이터로 Jane/Joe별 개인화) |

> **시스템 프롬프트:** ChatGPT 뒤에는 공개되지 않은 시스템 프롬프트(예: "act like a helpful assistant" + 사용자 메모리)가 있을 가능성. 그래도 내가 별도 템플릿을 추가할 수 있다.

**제로샷 vs 퓨샷(zero-shot vs few-shot)**

```
제로샷:  Classify the tone as positive/negative/neutral.
        "The product is fine but I was expecting more."   → 사람마다 답이 갈림(주관적)

퓨샷:    (위 프롬프트 + 예시들)
        "This exceeded my expectation completely." → Positive
        "It's okay but I wish it had more features." → Negative
        "The service was adequate." → Neutral
        Now classify: "The product is fine but I was expecting more." → Negative
```
→ 예시로 모델을 **우리 과제 기준에 정렬**. 별도 데이터셋·파인튜닝 없이 프롬프트만 갱신하면 되어 빠른 실험에 유리. 단, 컨텍스트 윈도우 한계는 존재.

**체이닝 (가장 강력)**

`chain of thought`와는 다르다. 복잡한 프롬프트를 여러 개로 **쪼개** 출력을 다음 프롬프트 입력으로 넘긴다.

```
[Prompt 1] 리뷰에서 핵심 이슈 추출  ──▶  이슈
[Prompt 2] 이슈로 전문적 응답 개요(outline) 작성  ──▶  개요
[Prompt 3] 개요로 최종 이메일 작성  ──▶  최종 출력
```
- 핵심 이점: **단계별로 독립 테스트·디버깅 가능.** 개요는 좋은데 이메일이 나쁘면 3번 프롬프트가 문제임을 특정 가능 → 가장 큰 개선 지점을 찾는다.
- 주의: 단계가 길어지면 **지연(latency)** 증가 → 일부 앱에선 긴 체인을 피한다.

**프롬프트 테스트와 LLM 심판(LLM judge)**
- 시작은 사람이 직접 출력을 평가(수작업)하며 직관을 얻는 것이 좋다.
- 규모 확장 시 자동화: `Promptfoo` 같은 도구로 같은 프롬프트를 여러 LLM에 돌려 표로 비교하거나, **LLM judge** 활용.
- LLM judge 종류: ① 쌍대 비교(pair-wise), ② 단일 점수(1~5), ③ 루브릭(rubric) 기반(기준 명시), ④ 퓨샷을 결합해 점수별 예시까지 제공.

## 🔧 파인튜닝 (왜 피하는가)

**단점**: ① 상당한 라벨 데이터 필요 ② 특정 데이터에 과적합(overfit)되어 범용성 상실 ③ 시간·비용이 큼 — **가장 큰 문제**.

> 파인튜닝이 끝날 때쯤 다음 모델이 나와 당신의 파인튜닝 버전을 이긴다. 프롬프트 기법은 다음 최고 모델을 코드에 꽂으면 즉시 전체가 갱신되지만, 파인튜닝은 그렇지 않다.

**그래도 쓸 만한 경우**: 반복적 고정밀 출력이 필요하고(법률·과학), 범용 LLM이 도메인 언어에 약할 때.

**실패 일화 (Slack 파인튜닝, Ross Lazerovitz, 2023):** Slack 메시지로 파인튜닝했더니 "500단어 블로그 써줘"에 모델이 *"I shall work on that in the morning"*, *"It's 6:30 a.m. here..."* 라며 **사람처럼 굴고 지시를 안 따름** → 과적합으로 도구가 아니라 직원처럼 행동.

## 🔎 검색 증강 생성 (RAG)

> 인터뷰 단골 질문: "RAG를 5살에게 설명하라." RAG는 외부 지식(DB·문서·API)을 임베딩해 저장해 두고, 질의에 관련 문서를 **검색해 프롬프트에 붙여** 답하게 하는 기법. 모델을 건드리지 않고 위에 얹는다.

**해결하는 문제**: 작은 컨텍스트, 대용량 내 세부사항 망각, 지식 공백/컷오프, 환각, 출처 부재. **이점**: 정확·최신·근거 기반(grounded) 답변, 재학습 없는 개발자 제어.

**바닐라 RAG 파이프라인 (예: "약물 X의 부작용은?")**

```
[지식 베이스 문서들] ──임베딩(embedding)──▶ 저차원 벡터 ──저장──▶ [벡터 DB(vector database)]
                                                                      │
[사용자 질의] ──같은 임베딩──▶ 질의 벡터 ──검색(거리 기준)──────────────┘
                                                  │
                            관련 문서 추출 ──▶ 프롬프트 템플릿에 삽입
                                                  │
        "다음 문서들에 근거해 질의에 답하라. 문서에 없으면 '모른다'고 하라.
         관련된 정확한 페이지/챕터/줄을 명시하고 링크하라."
                                                  │
                                              근거 있는 답변 + 출처
```
- 임베딩 차원 트레이드오프: 너무 작으면 정보 손실, 너무 크면 지연 증가.

**RAG 개선 기법**

| 기법 | 내용 |
|---|---|
| 청킹(chunking) | 전체 문서 임베딩 + 챕터 단위 벡터도 저장 → 정밀한 출처 표시 (대용량 문서에 유리) |
| HyDE (hypothetical document embeddings) | 질의가 문서와 형태가 달라 매칭이 약한 문제 해결. 질의로 **가짜 문서(예: 5페이지 답변)를 생성**해 임베딩 → 실제 문서 벡터와 더 가까워짐 |

> 2020~2025 사이 RAG 연구가 폭발적으로 분화했다(서베이 논문은 슬라이드 참조). 모든 기법을 외우기보다 존재를 알고 필요할 때 파고드는 것이 목표.

## 🤖 에이전트형 AI 워크플로우

> Andrew Ng가 **agentic workflow**라는 용어를 만든 이유: 회사마다 "agent"가 천차만별(프롬프트 하나도, 복잡한 멀티에이전트도 "agent"라 부름). 실제로는 **프롬프트 + 도구(tool) + 자원(resource) + API 호출을 다단계로 엮은 워크플로우**다. 또 RL의 "agent"(환경·상태·보상·관측)와 혼동을 피하려는 의도.

**한 단계 → 다단계 (환불 예시)**

```
바닐라(RAG): "환불 정책?" → "구매 후 30일 내 환불 가능" (+정책 문서 링크)

에이전트형: "환불 받을 수 있나요?"
  → RAG로 정책 검색
  → 사용자에게 주문번호 요청
  → API로 주문 상세 조회
  → "환불 대상입니다. 3~5영업일 내 처리됩니다"
```

**패러다임 전환: 전통 SW vs 에이전트형 SW**

| 축 | 전통 소프트웨어 | 에이전트형 소프트웨어 |
|---|---|---|
| 데이터 | 구조화(JSON, DB, 폼) | 자유 텍스트·이미지, 동적 해석 |
| 동작 | 결정론적(deterministic) | 퍼지(fuzzy) — 통제·공격·파손 위험 큼 |
| 구조화 사고 | 모놀리스/마이크로서비스(데이터/UI/비즈니스 로직 박스) | **관리자처럼 역할 분담**(디자이너→마케터→데이터과학자...) |
| 코드 태도 | 견고하게 짓고 오래 유지 | 실험 비용↓ → 코드를 더 쉽게 버림 (속도↑, 품질 위험↑) |

> **퍼지 엔지니어링은 진짜 어렵다.** 사용자가 무엇이든 묻게 두면 파손·공격·DB 손상 위험이 크다. 결정론으로 끝낼 건 끝내고, 퍼지에는 **가드레일 + 휴먼인더루프(human-in-the-loop)**를 둔다. (예: Workera의 객관식=결정론적, 음성/코딩 채점=퍼지 → 종료 시 *appeal* 기능으로 사람이 교정.)

**기업 워크플로우 재설계 (McKinsey, 신용 리스크 메모 사례)**
- 기존: 관계 매니저가 15+ 출처 수집 → 분석가와 협업 → 20시간+ 메모 작성 → 피드백 루프 → 1~4주 소요.
- GenAI 적용: 관계 매니저가 에이전트 시스템에 자료 제공 → 에이전트가 과제를 전문 에이전트들에 분배·분석·초안 작성 → 사람이 함께 검토·피드백 → **시간 20~60% 단축.**
- 가장 어려운 부분은 기술이 아니라 **사람·조직 변화**. 10만 명 규모 기업에서 실제 정착엔 10~20년 걸릴 수 있다.

**에이전트의 핵심 구성요소 (여행 예약 에이전트 예)**

| 구성요소 | 설명 |
|---|---|
| 프롬프트(prompts) | 앞서 본 기법으로 최적화 |
| 컨텍스트/메모리 관리 | **작업 메모리(working/core memory)**: 자주 쓰는 정보(이름) 빠른 접근. **아카이벌 메모리(archival memory)**: 가끔 쓰는 정보(생일) 느린 장기 저장. 매번 전체 메모리를 읽으면 비용·지연이 크므로 분리 |
| 도구(tools) | 항공/호텔/렌터카/날씨/결제 API 등. LLM은 API 문서(JSON, GET 요청 형식)를 잘 읽고 호출함 |
| 자원(resources) | 어딘가에 있는 데이터(예: CRM). 룩업(lookup) 도구로 접근 (Anthropic이 강조) |

**자율성(autonomy) 수준**

```
낮음:   단계를 하드코딩 (intent 파악 → DB 조회 → ... 순서 고정)
중간:   도구는 하드코딩, 단계는 에이전트가 결정 ("넌 여행 에이전트, 이 도구들을 써")
높음:   에이전트가 단계 결정 + 도구 생성(코드 에디터 접근, 웹 검색, 계산 코드 작성)
```

**API vs MCP (Model Context Protocol, Anthropic 제안)**
- **API**: LLM에게 각 API 호출법을 일일이 가르쳐야 함 → 잘 확장되지 않음.
- **MCP**: 중간에 표준 계층(MCP 서버/클라이언트)을 둠. 에이전트가 "뭐가 필요해?"라고 묻고 MCP가 "출발지·목적지·예산 알려줘"라고 답하는 **에이전트 간 통신** → 확장성↑, 모든 걸 하드코딩할 필요 없음.
- **본질**: MCP는 더 많은 데이터 접근이 아니라 **효율성**에 관한 것. 노출 데이터는 여전히 내가 통제. 단, MCP 서버는 다른 LLM의 임의 입력을 받으므로 **견고함·인증(authentication)**이 필요.
- 한계: API가 바뀌면 MCP도 갱신 필요(완전 자율 아님). 이상적으론 문서를 읽고 코드를 자동 갱신하는 LLM 워크플로우로 보완.

**여행 에이전트 단계별 흐름**

```
1. 사용자 과제: "12/15~20 파리 여행, 에펠탑 근처 호텔 + 항공 + 필수 방문지"
2. 계획 수립: 항공 검색 → 호텔 검색 → 추천 생성 → 선호/예산 검증 → 결제
3. 실행: 도구 사용·결과 결합
4. 능동적 상호작용: 1차 제안 → 사용자 검증/반려 → 계획·실행 반복
5. 메모리 갱신: "이 사용자는 직항만, 3성급 OK" 등 학습 저장
```

## 📊 Eval 케이스 스터디 (고객지원 에이전트)

> PM이 "주소 변경 같은 고객지원 AI 에이전트를 만들라"고 함. **어디서 시작하나?** → 모델 벤치마크 조사도 좋지만, **고객지원 상담원과 1~2일 함께 앉아 과제를 분해(task decomposition)**하는 것이 핵심. 어디서 막히고 얼마나 걸리는지 관찰.

**과제 분해 → 에이전트 설계 매핑**

| 단계 | 적합한 기법 |
|---|---|
| 정보 추출(extract info) | 바닐라 LLM (한 번 호출로 충분) |
| 고객 기록 조회 + 주소 갱신 | 도구(tool) / MCP — DB 연결, 커스텀 툴 |
| 정책 확인(주소 변경 허용?) | 룩업/RAG |
| 응답 이메일 초안 | LLM (확인 결과를 붙여 작성) |
| 이메일 발송 | 도구(전송 API) |

> **LLM 트레이스(trace)는 필수.** AI 스타트업 면접 때 "LLM 트레이스가 있나요?"를 물어보라. 없으면 복잡한 프롬프트 체인에서 버그 위치를 추적할 수 없어 디버깅이 매우 어렵다.

**Eval 설계 4가지 축**

| 축 | 한쪽 | 다른 쪽 |
|---|---|---|
| 범위 | **컴포넌트 기반(component-based)** — 도구·단계별 에러 분석, 디버깅 쉬움 | **엔드투엔드(end-to-end)** — 최종 사용자 만족도(1~5) |
| 성격 | **객관(objective)** — 잘못된 주문 ID 추출 등, Python으로 자동 검사 | **주관(subjective)** — 톤·예의 등, 사람 평가 또는 LLM judge |
| 형태 | **정량(quantitative)** — 주소 갱신 성공률, 컴포넌트별 지연 | **정성(qualitative)** — 환각·톤 불일치·사용자 혼란, 화이트글러브 에러 분석 |

**예시 적용**
- *객관*: "더 비싼 항공편을 고른다" → 자동 추적해 "가격 인식이 약하다" 발견.
- *주관(직항 vs 경유, 톤)*: 의도된 선호가 담긴 평가용 데이터셋(예: "나는 시간 때문에 직항 선호" 10개)을 만들어 좋은 출력 기준과 비교.
- *톤 개선 절차*: ① **에러 분석(error analysis)** — 20개 대화 직접 읽고 "무뚝뚝하다" 발견 → ② **LLM judge + 루브릭**으로 예의 점수화 → ③ 모델 교체(GPT-4 / Grok / Llama 병렬 비교) 또는 프롬프트 변경("act like a **helpful** travel agent")의 효과 측정.

## 👥 멀티 에이전트 워크플로우

**왜 필요한가?** (이미 다단계·다중 도구인데?)
- **병렬성(parallelism)** — 독립적으로 동시에 돌릴 작업이 있을 때. (멀티에이전트의 주된 이점)
- **재사용(reuse)** — 한 디자인 에이전트를 마케팅·제품 팀이 공유.
- 추가 이점: **전문화된 에이전트는 디버깅이 쉽고**, 병렬화로 시간 절약.

**스마트홈 예시 (학생 브레인스토밍)**: 위치 추적, 온도 제어, 에너지 효율, 보안(입장 권한·신원별 권한), 날씨 API 연동 제어, 냉장고/식료품 자동 주문(카메라 + e-커머스 API), 조명, 엔터테인먼트, 알림, 그리고 **오케스트레이터(orchestrator)**.

**상호작용 패턴**
- **계층형(hierarchical)**: 사용자는 오케스트레이터하고만 대화, 오케스트레이터가 하위 에이전트로 지시 전달 (UX 측면에서 선호).
- **플랫(flat / all-to-all)**: 모든 에이전트가 서로 통신 (예: 기후 제어 ↔ 에너지 연결).

> **에이전트끼리 대화시키는 것 = 기본적으로 MCP 프로토콜.** 에이전트를 도구처럼 취급한다 — "이렇게 상호작용하고, 이런 정보를 주고, 이런 게 필요하다."

## 🔮 다음은 무엇인가 (AI 트렌드)

- **정체(plateau)?** (Ilya Sutskever의 질문) 최신 GPT가 기대만큼 도약하진 않았으나 사용성은 향상. 스케일링 법칙(scaling laws)상 컴퓨트·에너지를 늘리면 개선되지만 결국 정체 → 다음 도약은 **아키텍처 탐색(architecture search)**에서. 인간 뇌는 더 적은 데이터로 더 효율적 → "다음 트랜스포머"가 컴퓨트·에너지를 10배 줄일 수 있다. (Asimov *Foundation* 비유: 한 연구 그룹의 발견이 방향을 바꿀 수 있다.)
- **멀티모달리티(multimodality)**: 텍스트 + 이미지 + 오디오 + 비디오가 서로를 강화한다. 고양이 이미지를 잘 이해하면 고양이 텍스트도 잘 쓴다. 정점은 **로보틱스** — 모든 모달리티가 합쳐짐.
- **여러 방법의 조화**: 지도/비지도/자기지도/강화학습 + 프롬프트 엔지니어링 + RAG가 함께 작동. 아기의 학습이 그 혼합(DNA=사전학습, 부모 지도=지도학습, 넘어짐=보상 신호, 관찰=비지도)과 같다.
- **인간 중심 vs 비인간 중심 연구**: 뇌를 모방한 접근(인간은 역전파(backpropagation)가 아닌 순전파(forward propagation)만 쓸 수 있다는 연구)과, 인체 한계를 넘어서는 접근 둘 다 가치 있음.
- **속도(velocity)**: 기법의 반감기가 짧다. 그래서 CS230은 **폭**을 주고, 필요할 때 빠르게 깊이 파고들게 한다.

## 🔑 핵심 용어

| 용어 | 뜻 |
|---|---|
| 재그드 프론티어(jagged frontier) | AI가 도움 되는 영역과 해가 되는 영역의 들쭉날쭉한 경계 |
| 센타우르 / 사이보그 | AI 협업 방식: 통째 위임(분업) vs 빠른 주고받기(혼합) |
| 사고 사슬(chain of thought) | "단계별로 생각하라"로 추론을 유도하는 단일 프롬프트 기법 |
| 체이닝(chaining) | 복잡한 작업을 여러 프롬프트로 쪼개 출력을 연결 — 디버깅·제어 용이 |
| 제로샷 / 퓨샷(zero-shot / few-shot) | 예시 없이 / 예시를 주어 과제에 정렬하는 프롬프트 |
| 프롬프트 템플릿(prompt template) | 변수를 끼워 사용자별로 확장 가능한 프롬프트 |
| LLM 심판(LLM judge) | LLM으로 출력을 채점(쌍대 비교·루브릭 등) |
| 검색 증강 생성(RAG) | 외부 지식을 임베딩·검색해 프롬프트에 붙여 근거 있는 답변 생성 |
| 벡터 DB(vector database) | 임베딩 벡터를 거리 기준 빠른 검색용으로 저장 |
| 청킹(chunking) | 문서를 챕터 단위로도 임베딩해 정밀 출처 표시 |
| HyDE | 질의로 가짜 문서를 생성·임베딩해 검색 정확도를 높이는 기법 |
| 에이전트형 워크플로우(agentic workflow) | 프롬프트+도구+자원+API를 다단계로 엮은 시스템 (Andrew Ng 용어) |
| 결정론적 / 퍼지(deterministic / fuzzy) | 정답이 고정 / 모델이 실수할 수 있는 처리 |
| 가드레일 / 휴먼인더루프 | 퍼지 시스템의 안전장치 / 사람이 개입해 교정 |
| 작업·아카이벌 메모리 | 빠른 접근 단기 메모리 / 느린 접근 장기 메모리 |
| MCP(Model Context Protocol) | 에이전트-도구/에이전트 간 표준 통신 계층 (Anthropic) |
| LLM 트레이스(trace) | 프롬프트 체인 호출 기록 — 디버깅 필수 |
| 에러 분석(error analysis) | 실제 상호작용을 직접 읽어 문제를 찾는 정성 평가 |
| 오케스트레이터(orchestrator) | 멀티에이전트에서 사용자와 소통하며 하위 에이전트를 조율 |
| 니들 인 헤이스택(needle in a haystack) | 거대 컨텍스트에서 특정 사실을 찾는 어텐션 벤치마크 |

## ✍️ 학습 메모

- **최적화 순서 직관**: 프롬프트 → 체이닝 → (필요 시) RAG → 에이전트 → 멀티에이전트. **파인튜닝은 최후의 수단.** 가능한 한 모델 가중치는 건드리지 말 것 — 다음 모델로 즉시 갈아탈 수 있는 유연성을 잃는다.
- **체이닝의 진짜 가치는 성능이 아니라 디버깅 가능성**이다. "개요는 좋은데 이메일이 나쁘다"처럼 약한 단계를 특정할 수 있어야 개선 지점을 찾는다. 단, 단계가 길어지면 지연을 의식하라.
- **Eval은 4축으로 교차**해 보라: 컴포넌트/엔드투엔드 × 객관/주관 × 정량/정성. 객관은 코드로 자동, 주관은 LLM judge + 루브릭.
- **실무 출발점은 항상 사람**: 과제 분해는 실제 상담원과 1~2일 앉아서, 톤 문제는 20개 대화를 직접 읽는 에러 분석부터. 자동화는 그 다음.
- **MCP의 본질은 효율·확장성**(데이터 접근권이 아님). 에이전트 간 통신 = 에이전트를 도구로 취급하는 MCP.
- **결정론 우선, 퍼지에는 가드레일**: 끝낼 수 있는 건 결정론으로 끝내고, 퍼지가 주는 상호작용성에는 반드시 안전장치와 휴먼인더루프를 둔다.
- **인터뷰 팁**: "RAG를 5살에게 설명하라"와 "LLM 트레이스가 있는가"는 실전 단골.
