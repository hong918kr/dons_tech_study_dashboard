# Stanford CS230 | Autumn 2025 | Lecture 3: Full Cycle of a DL project

> Stanford · 2025-10-15 · 01:07:04 · 강사: Andrew Ng · [영상 링크](https://www.youtube.com/watch?v=MGqQuQEUXhk)

## 📌 한 줄 요약

딥러닝 프로젝트는 모델 학습만이 전부가 아니라 **문제 정의 → 데이터 수집 → 모델 설계 → 학습 → 배포 → 모니터링/유지보수**로 이어지는 전체 사이클(full cycle)이다. 코드는 통제할 수 있어도 데이터는 통제할 수 없기 때문에, 머신러닝 개발은 본질적으로 반복적·실험적(empirical) 과정이며, 그래서 **속도(speed)** — 빠르게 만들어 보고, 어디서 실패하는지 발견하고, 고치는 루프를 빠르게 도는 것 — 이 가장 중요하다. Andrew Ng가 얼굴 인식(face recognition) 도어락 시스템을 예시로 각 단계를 대화형으로 풀어나간다.

## 🎯 핵심 메시지

> "데이터 속에 무엇이 있는지 미리 알 수 없으므로, 일단 빠르게 무언가를 만들어 어디서 잘되고 어디서 안 되는지 발견하고 고치는 것 — 이 반복 루프의 속도가 프로젝트 성공의 가장 강력한 예측 변수다."

**보조 메시지**
- AI 프로젝트는 전통적 소프트웨어 공학과 다르다: 코드는 통제하지만 데이터(과거·미래)는 통제할 수 없다.
- 학계는 "모델링"이라는 작은 상자에 집중하지만, 실제 시스템 구축에는 그 바깥의 일(데이터, 배포, 유지보수)이 훨씬 많다.
- 데이터는 단일체(monolithic)가 아니다. 무작정 더 많이 모으는 것이 아니라, **에러 분석(error analysis)** 으로 어느 하위 범주(subcategory)에 투자할지 정해야 한다.
- 모델은 한 번 배포하면 끝이 아니다. 세상이 변하면서 발생하는 **data drift / concept drift** 를 모니터링하고 유지보수해야 한다.
- "내 일은 테스트셋에서 잘하는 것"이 아니라 "실제로 작동하는 것을 만드는 것"이 ML 엔지니어의 일이다.

## 🔄 딥러닝 프로젝트의 전체 사이클

전통적 소프트웨어와 달리, AI 프로젝트는 코드 + 데이터로 구성되며 데이터에 무엇이 들어있는지 미리 알 수 없다. 얼굴 인식의 경우 조명, 긴 머리/짧은 머리, 표정, 안경, (겨울철) 스카프 등 예측 불가능한 변수가 가득하다. LLM도 마찬가지로, 인간이 다 볼 수 없는 수십 조 토큰으로 학습되었기에 그 동작을 미리 알 수 없어 매우 실험적(empirical)이다.

전체 사이클 단계:

| 단계 | 내용 |
|------|------|
| 1. 문제 정의 (Specify the problem) | 무엇을 만들지 정한다 (예: 문을 언제 열지 결정하는 얼굴 인식 보안 시스템) |
| 2. 데이터 수집 (Get data) | 학습에 쓸 데이터를 모은다 |
| 3. 모델 설계 (Design model) | 신경망 아키텍처를 설계한다 |
| 4. 모델 학습 (Train model) | gradient descent로 학습한다 |
| (반복 루프) | **설계 → 학습 → 결과 분석 → 모델/데이터 수정** 을 만족할 때까지 여러 번 반복 |
| 5. 배포 (Deploy) | 클라우드/로컬 서버에 올려 추론(inference) 수행 |
| 6. 모니터링·유지보수 (Monitor & Maintain) | 배포 후 변화하는 세상에 맞춰 시스템을 갱신 |

> 핵심 루프: **Design model → Train → Analyze results → (update model or data) → 반복.** 빠르게 움직이는 팀은 작은 모델의 경우 이 루프를 하루에 한 번 돌기도 한다.

## 🧑‍💻 예시: 얼굴 인식 도어락 시스템

- **목적**: 회사 건물·집 같은 제한 구역에서 누가 입장 권한이 있는지 얼굴로 판별해 문을 열지 결정.
- **실사용 사례**: 키카드(key card) 도난 대응. 카드를 스와이프할 때 사진을 함께 찍어(곧 폐기), 카드 소유자와 실제 사용자가 같은 사람인지 확인 → 도난 카드로의 무단 출입 차단.
- **아키텍처 — Siamese network(샴 네트워크)**: 두 장의 사진을 입력받아 "같은 사람인가 / 다른 사람인가"를 판별하는 신경망.
  - 매 가정·매 건물마다 재학습하지 않아도 됨. 등록 사진(registration picture)만 몇 장 넣어두면, 새로 온 사람이 등록된 사람 중 하나인지 빠르게 대조 가능.

## 📦 데이터 수집: "속도"라는 가이드 원칙

질문: "변호사가 인터넷 데이터 다운로드를 금지했다. 팔로알토의 3인 스타트업 CTO라면 어떻게 데이터를 모으겠는가? 학습 전 며칠을 쓰겠는가?"

수강생 아이디어: 화상회의(Zoom) 같은 스트리밍 서비스 활용, 카메라를 설치하고 직원들이 **opt-in**, 친구·지인의 LinkedIn 사진 수집, 학생증 사진, 스탠퍼드 전체 메일 발송 등.

**Andrew Ng의 프레임워크 — 속도(speed)**

> "데이터의 가치는 미리 알기 매우 어렵다. 그래서 나는 열등하고 작고 낮은 품질의 데이터셋이 나오더라도, 1~2일 안에 데이터셋을 빠르게 확보하는 전술을 선호한다."

- 빠르게 = 보통 **하루나 이틀(48시간)**. 팀에게 "이만큼 데이터를 모으려면 얼마나 걸릴까?"라고 묻는 대신, **"이틀 안에 가장 창의적이고 책임감 있게 모을 수 있는 방법은?"** 이라고 묻는다. 후자가 실행 속도를 높인다.
- 빨리 데이터를 얻을수록 → 빨리 모델 학습 → 빨리 무엇이 잘못됐는지 발견 → 빨리 수정.
- 실제 사례: 한 CEO가 데이터를 얻으려고 수천만~1억 달러 이상을 들여 회사를 인수했지만, 정작 그 데이터를 어떻게 수익화할지 몰랐다. → 비싼 데이터에 미리 큰돈을 쓰는 것의 위험.
- 스탠퍼드 캠퍼스의 고밀도 구역(카페테리아 등)에서 정중하게 동의를 구하며 사진·음성 샘플을 수집한 경험.

**시간 배분 원칙 (commensurate time)**

| 모델 학습 시간 | 권장 데이터 수집 시간 |
|----------------|----------------------|
| 몇 시간 ~ 하룻밤 (예: 얼굴 인식) | 며칠 (몇 달을 쓰면 데이터가 병목이 됨) |
| 수 주 ~ 수 개월 (대규모 foundation model) | 몇 달 들여 데이터를 제대로 갖추는 것이 합리적 |

**예외**: 이미 여러 번 해본 프로젝트라면, 사전 경험·논문 근거로 "최소 5만 장이 필요하다"는 것을 알 수 있어 처음부터 더 투자해도 된다. 하지만 **처음 하는 응용**이라면 속도 위주로 가라.

**LLM 응용에도 동일**: 프롬프트가 어떻게 동작할지 미리 알 수 없으므로, 오래 이론화하지 말고 일단 시도해 문제를 발견하고 고쳐라. 책임 있는 AI(responsible AI)도 마찬가지 — 먼저 만들어 **샌드박스(sandbox)** 안에서 충분히 탐침(probe)·검증한 뒤 세상에 내보내라.

## 🔍 데이터 관련 핵심 원칙

**(1) 무엇이 잘못됐는지로 다음 단계 결정 → Error Analysis**
- 모델이 어디서 실패하는지(예: 모자 쓴 사람을 못 알아봄) 보고 → 그 하위 범주의 데이터만 더 모은다.
- **Data-centric AI**: 성공적 AI 시스템을 위해 데이터를 체계적으로 엔지니어링하는 분야.
- 무작정 "모든 종류의 데이터를 더(willy-nilly)" 모으는 것은 느리고 비싸며 비효율적. 프론티어 모델 학습조차 "아무 데이터나 더"가 아니라 가치 있는 하위 범주를 식별해 고품질 데이터를 확보하는 게임이다.
- LLM의 두 가치 버킷: (a) 일반 질의응답, (b) **코딩 보조(coding assistance)** — 코딩을 잘하려면 저품질 인터넷 잡담이 아니라 **고품질 코딩 데이터**가 필요.

**(2) 데이터 품질(quality)**
- 처음엔 속도 우선이지만, 분석을 거치면 품질이 매우 중요해진다.
- LLM: 고품질의 잘 편집된 책·기사 > 저품질 인터넷 잡담.
- 얼굴 인식: 선명한(in-focus) 이미지 > 흐릿한(blurry) 이미지.

**(3) 학습 데이터가 테스트 분포와 얼마나 같아야 하나?**

> "생각만큼 중요하지 않다." — 충분히 큰 신경망은 약간 무관한(slightly relevant) 데이터를 넣어도 손해보지 않고 오히려 도움이 될 수 있다.

- 과거(10~15년 전, 모델이 작던 시절)에는 학습 분포 = 테스트 분포여야 한다는 강박이 있었다. 파라미터가 적어 무관한 데이터에 "산만해지면" 핵심 작업 성능이 떨어졌기 때문.
- 지금은 큰 신경망을 쉽게 학습할 수 있어, **무관(irrelevant)** 데이터를 넣는 것은 손해가 거의 없다 (인간 뇌가 피아노도 배우고 AI도 배우는 것처럼). 단, **틀린(incorrect)** 데이터는 여전히 문제.
- (셜록 홈즈의 "다락방 이론" — 뇌 용량이 한정되어 새 걸 배우려면 잊어야 한다 — 은 큰 신경망에는 해당되지 않는다.)

## 🚀 배포(Deployment): VAD를 통한 최적화

배포 시 신경망을 클라우드/로컬 서버에 올려 추론하는 소프트웨어 작업이 필요하다. 그러나 24/7 영상을 30fps로 클라우드에 스트리밍해 매 프레임을 분류하는 것은 **너무 비싸고 느리다**.

**해결책 — VAD (Visual Activity Detection, 시각 활동 감지)**: 저비용·저전력의 가벼운 사전 필터. "사람 얼굴이 있는가?"를 빠르게 판단해, 있을 때만 무거운 얼굴 인식 신경망(클라우드)으로 넘긴다. (집 현관 앞은 대부분 아무 일도 없으므로 모든 영상을 보내는 것은 낭비.)

VAD 구현 두 가지 옵션:

| | 옵션 1: 비-ML (픽셀 변화) | 옵션 2: 작은 신경망 |
|---|------------------------|---------------------|
| 방법 | 변한 픽셀 수 > 임계값 ε 인지 확인 (RGB가 1초 전 대비 일정 비율 이상 변했는가) | "사람이 있는가"만 판단하는 매우 가볍고 저전력인 작은 신경망 학습 |
| 구현 시간 | 파이썬 ~5줄, 20분 이내 | 최소 수 시간 이상 |
| 장점 | 매우 빠름, 단순함 | 더 정확 (나무 흔들림, 차, 고양이 등 오탐 줄임) |
| 단점 | 배경의 흔들리는 나무·지나가는 차·이웃 고양이가 오탐을 유발 | 구현·데이터 비용 큼 |

**Ng의 접근 — 속도 우선**: 옵션 1을 먼저 (20분이면 됨) → 배포해보고 실제로 어디서 실패하는지 발견 → 그 학습으로 옵션 2로 이동. (실제로 옵션 1은 충분히 잘 작동하지 않아 결국 옵션 2로 가지만, 옵션 1을 만든 경험이 통찰을 준다.)

> 발견한 통찰 예시: 사람이 카메라로 걸어올 때 어떤 프레임은 선명하고 어떤 프레임은 흐릿하다. **고해상도·초점 맞은 프레임을 (1장이 아니라 5장 정도) 선별**해 얼굴 인식에 넘기면 정확도가 크게 향상된다. → 이런 통찰은 시스템을 실제로 구현해봐야만 얻을 수 있다.

수강생 아이디어: 옵션을 캐스케이드(옵션1 통과 → 옵션2), 프레임 샘플링, 엣지(edge, 기기 상)에서 두 옵션 모두 실행 등. Ng: 두 옵션 다 **엣지(기기)** 에서 돌리는 것을 선호. 분당 몇 장 정도를 클라우드로 보내는 건 문제없지만 24/7 스트리밍은 불가.

**참조 성능(human-level performance)**: 좋은 분류 정확도가 무엇인지 알려면 달성 가능 목표가 필요하며, 흔히 **인간 전문가 수준**을 기준으로 삼는다. 이는 나중에 다룰 **bias/variance** 진단을 쉽게 한다. (얼굴 인식은 통제된 환경에서 이미 인간을 능가하며, 인간을 넘어선 뒤에는 기준 설정이 더 어려워진다.)

## 📊 모니터링 & 유지보수: Data Drift / Concept Drift

배포 후 "세상이 변하면서" 시스템이 더 이상 작동하지 않는 일이 생긴다.

| 용어 | 의미 |
|------|------|
| **Data drift** | 세상이 주는 입력 데이터의 **분포**가 학습셋과 달라짐 (예: 겨울이 되어 스카프·우비, 여름이 되어 선글라스) |
| **Concept drift** | 입력→출력 매핑(X→Y) 자체가 변함 |

실제 drift 사례:
- 얼굴 인식: 계절·국가에 따라 복장·외모 분포 변화.
- 웹 검색: 새 정치인 당선, 신곡 발매(테일러 스위프트 새 앨범) 등으로 검색어가 급변.
- 공장 검사: 새 기계가 새로운 종류의 스크래치를 만들어냄.
- 자율주행: 캘리포니아에서 학습한 모델을 텍사스로 가져가니 **신호등 모양이 다름** (강풍 대비로 다르게 설치) → 작동 안 함 → 데이터 갱신 필요.

> "테스트셋에서 잘했으니 내 일은 끝"이라는 사고를 버려라. ML 엔지니어의 일은 **테스트셋이 아니라 실제로 작동하는 것**을 만드는 것이다. 제품 담당자가 "안 된다"고 하면, "왜 테스트셋 성능이 실제로 이어지지 않는가"를 고민하라 (흔한 원인이 바로 분포 변화).

**모니터링 베스트 프랙티스**
- 사용자 동의 하에(프라이버시 존중·투명성) 일부 데이터를 클라우드로 받아 대시보드를 그린다.
- 고위험(high-stakes) 응용에서는 팀을 모아 **잘못될 수 있는 모든 것을 브레인스토밍**한다. (Ng의 경험상, 브레인스토밍한 목록에 없던 문제가 실제로 터진 적이 거의 없다.)
- 브레인스토밍한 위험을 감시할 **대시보드/메트릭**을 설계: 재인증(reauthentication) 빈도(사용자 좌절 신호), accept vs reject 비율, latency(지연), 0/1 판정 수 등을 시간에 따라 플롯.
- 어떤 대시보드가 유용할지 미리 알기 어려우므로 → **일단 많이(30~100개) 그려보고**, 지루한 것(예: 클라우드 배포라 항상 일정한 latency)은 가지치기(prune) → 핵심 지표만 장기 추적.
- 정상 범위를 파악한 뒤 **상·하한 경보(alarm)** 를 설정해 범위를 벗어나면 담당자를 호출(page).

**단순 모델의 강점 — drift 견고성**: 옵션 1(ε 파라미터 1개)은 매우 단순해 분포 변화에 **robust**하다 (선글라스를 써도 변한 픽셀 비율은 크게 안 변함). 반면 수천~수만 파라미터의 신경망(옵션 2)은 "선글라스 없는 사람"에 overfit하기 쉬워, 선글라스가 유행하면 모델을 갱신해야 할 가능성이 높다.

| Empirical / iterative process | 미리 알 수 없으므로 만들고-보고-고치는 실험적·반복적 개발 과정 |

| Registration picture (등록 사진) | 권한 있는 사람의 기준 사진. 새 입력과 대조에 사용 |
| Speed (속도) | 반복 루프를 빠르게 도는 것 — 성공의 가장 강력한 예측 변수 |
| Error analysis (에러 분석) | 어디서 실패하는지 분석해 어떤 데이터/수정에 투자할지 결정 |
| Data-centric AI | 데이터를 체계적으로 엔지니어링해 성능을 올리는 접근 |

| Edge (엣지) | 클라우드가 아닌 기기 자체에서 추론을 실행 |
| Human-level performance | 달성 가능 목표·참조 성능으로 삼는 인간 전문가 수준 |
| Data drift | 입력 데이터 분포가 학습셋과 달라지는 현상 |
| Concept drift | 입력→출력 매핑 자체가 변하는 현상 |
| Reauthentication (재인증) | 사용자가 두 번 인증해야 하는 빈도 — 좌절·오류의 신호 |

## ✍️ 학습 메모

- **모델링은 빙산의 일각.** 강의·논문은 모델 학습에 집중하지만, 실전에서는 데이터·배포·유지보수가 일의 대부분이다. "모델 상자" 바깥을 보라.
- **"얼마나 걸릴까?" 대신 "이틀 안에 어떻게 할까?"** 로 질문을 뒤집어 실행 속도를 끌어올려라. 첫 응용이라면 작고 낮은 품질의 데이터라도 빠르게 확보하는 게 정답.
- **데이터 수집 시간은 모델 학습 시간에 비례**시켜라 (얼굴 인식은 몇 시간이면 학습되니, 데이터에 몇 달 쓰지 말 것). 단, 사전 경험·논문 근거가 있으면 예외.
- **무작정 더 모으지 말고, error analysis로 실패하는 하위 범주의 데이터를 표적 수집**하라. 데이터는 단일체가 아니다.
- 큰 신경망에는 약간 무관한 데이터를 섞어도 손해가 적다. 단 **틀린 데이터는 금물**.
- **배포는 비용 최적화 문제**다. VAD 같은 저비용 사전 필터로 무거운 모델 호출을 줄여라. 가능하면 엣지에서 실행.
- **단순한 비-ML 솔루션을 먼저 시도**하라 (구현 빠름 + drift에 견고). 실패하더라도 그 과정에서 핵심 통찰(예: 선명한 프레임 선별)을 얻는다.
- **배포는 끝이 아니다.** data/concept drift를 가정하고, 잘못될 일을 브레인스토밍 → 풍부한 대시보드(많이 그리고 가지치기) → 경보 설정으로 모니터링·유지보수 체계를 갖춰라.
- **"테스트셋에서 잘함" ≠ "작동함".** 실제로 작동하는 것을 만드는 것이 ML 엔지니어의 책임이다.
- 책임 있는 AI: 먼저 만들어 **샌드박스에서 탐침·검증**한 뒤 세상에 내보내라.
