## 📌 한 줄 요약

AI 시스템을 실제로 구축할 때 매일매일 어떤 결정을 내려야 하는지를, 두 가지 구체적 예제(음성 깨우기 단어 감지, AI 딥 리서처)로 따라가며 보여주는 강의다. 알고리즘 이해를 넘어 **빠른 반복(iteration), 창의적 데이터 수집, 그리고 오차 분석(error analysis)을 통한 우선순위 결정**이 팀 생산성에서 10배 이상의 차이를 만든다는 것이 핵심이다. 음성 예제는 단일 신경망(end-to-end), 딥 리서처 예제는 파이프라인(pipeline)을 대표하며, 후자에서는 "어느 구성요소를 고칠 것인가"를 정하는 오차 분석이 결정적이다.

## 🎯 핵심 메시지

> 알고리즘을 아는 것보다, 무언가가 처음에 작동하지 않을 때 "다음에 무엇을 할 것인가"를 잘 결정하는 효율적 개발 프로세스가 생산성에서 말 그대로 10배(혹은 그 이상)의 차이를 만든다.

**보조 메시지**
- **속도(speed)가 제품 성공의 가장 강력한 예측 변수**다. 아이디어의 우열보다, 오늘/일주일 안에 무언가를 만들어 빠르게 궤도 수정하는 능력이 우선한다.
- 머신러닝 작업은 개발(development)보다 **디버깅(debugging)에 가깝다.** 다음에 무엇이 잘못될지 미리 알 수 없으므로, "만들고 → 어디가 안 되는지 찾고 → 고치는" 반복 사이클의 리듬을 만드는 팀이 빠르다.
- 새 문제는 **문헌 조사(literature search)와 오픈소스 시도**로 시작하라. 논문을 하나씩 100% 끝내지 말고 여러 개를 넓게 훑어라(skim). 막히면 전문가에게 정중히 이메일을 보내라(고ROI).
- 데이터가 없으면 **창의적으로 직접 수집**하라(동의를 받고 녹음, 배경 소음 합성 등). 합성 데이터(synthetic data)는 유용하지만 보통 나중에 쓴다.
- 파이프라인에서는 **오차 분석으로 어느 구성요소에 노력을 집중할지** 정하는 것이 몇 주의 헛수고를 아낀다.

## 🗣️ 예제 1 — 음성 깨우기 단어 감지 ("Robert, turn on")

### 문제 설정
- 시나리오: 스타트업 CTO가 되어, **Wi-Fi/클라우드 설정 없이** 이름을 부르면 켜지는 음성 제어 램프(예: "Robert"라는 이름의 램프)를 만든다. 작은 IC 회로(edge device)에서 돌아가야 한다.
- 단순화: 한 가지 문구 **"Robert, turn on"** 을 감지하는 신경망 하나만 다룬다. (turn off나 다른 이름은 같은 방식으로 반복 적용.)
- 이런 깨우기 단어는 **wake word / trigger word**라 부른다("Hey Siri", "Alexa" 등).

### 시작하는 법 — 학생 아이디어와 강사의 코멘트
| 학생 제안 | 강사 코멘트 |
|---|---|
| 오픈소스 speech-to-text 모델을 받아서 돌려보기 | 좋은 출발점 |
| Robert 감지 + 나머지 문장 이해용 여러 모델 | 가능한 접근 |
| 두 오디오가 같은 단어인지 판별하는 Siamese network | 이 수업 뒤에서 다룸. 새 단어로 일반화하기 좋아 흥미로움 |
| 기기를 Siri에 연결 | 휴대폰 연결이 필요하면 이건 다른 제품이 됨 |

> 핵심 관찰: **일반용 음성 인식은 아직 무겁고(edge에서 비싸다).** 반면 한 문구만 감지하는 wake word는 **작은 신경망**으로 충분하다. 단, 단어를 바꾸려면 다른 신경망으로 교체해야 한다. 그리고 wake word 검출에 대해 십수 년이 지난 지금도 **모두가 동의하는 단일 표준 아키텍처는 없다** — 그래서 문헌 조사의 가치가 크다.

### 처음 시작할 때의 작업 순서 (강사 조언)
1. **문헌 조사 + 오픈소스 시도** — 구현보다 먼저, 속도를 가장 크게 높이는 가속기.
2. **넓게 훑기(skim).** 논문 1→2→3을 각각 100%까지 읽지 말고, 여러 개를 0%→대충 훑기로 빠르게 본 뒤, 핵심적인 한두 편(seminal)에만 시간을 깊게 쏟는다.
3. **전문가에게 연락.** 자기 일을 먼저 한 뒤, 막히면 논문 저자/교수에게 정중한 이메일. (예: 음성 문제로 Dan Jurafsky에게 전화 → 10~30분 대화가 큰 진전을 만듦. 응답률은 50% 정도라도 ROI가 높다.)

### 데이터 수집 — "Robert, turn on" 데이터는 인터넷에 없다
인터넷에는 사람들이 "Robert, turn on"이라고 말한 대규모 데이터셋이 **존재하지 않는다.** 직접 모아야 한다.

| 방법 | 평가 |
|---|---|
| 캠퍼스/샌프란시스코를 돌며 사람들에게 **동의를 받고** 목소리 녹음 | 추천. 하루에 수십~수백 샘플 확보 가능 |
| Text-to-Speech(TTS) 합성 데이터 | 작동은 하지만 **보통 첫 선택이 아님** |

> **프라이버시/동의(consent)가 중요하다.** 몰래 하거나 이상하게 하지 말고, 무엇을 하는지 명확히 알리고 자유롭게 주어진 동의만 받는다. 거절하면 존중한다. 의외로 많은 사람이 친절하게 동의해준다.

**합성 데이터를 첫 선택으로 쓰지 않는 이유**
- 진짜 자연 데이터와 얼마나 비슷한지 알기 어렵다.
- TTS 제공자의 **목소리 다양성(voice diversity)** 이 제한적일 수 있어, 충분한 다양성 확보가 번거롭다.
- 너무 많은 하이퍼파라미터·손잡이(knob)가 있고, "내가 모르는 이상한 점이 합성 데이터에 있는 건 아닐까"라는 걱정이 머릿속에 남는다. 진짜 데이터를 쓰면 걱정거리가 하나 준다.
- 비유(자율주행): 비디오 게임에서 차 이미지를 뽑으려는 아이디어 → 게임에는 차종이 20개뿐일 수 있어 **현실의 풍부함을 못 담는다.** 진짜 사진을 쓰면 걱정거리가 하나 줄어든다.
- 결론: 합성 데이터는 **매우 유용하지만 보통 프로세스 후반에** 도입한다.

### 실제 시스템을 만든 과정 — "지저분한 실전 해킹"

**train/dev/test 구성 (실전형)**
```
훈련(train) 오디오 클립: 100개
개발(dev) 셋:           25개  ← 파라미터 튜닝 대상
테스트(test) 셋:         0개  ← 없음
```
> 논문을 낼 거라면 편향 없는 깨끗한 test 셋이 필요하다. 하지만 **"그냥 작동하는 시스템을 만들어 출시"가 목표라면**, test 셋 없이 dev 셋에만 거리낌 없이(unapologetically) 튜닝하기도 한다.

**100개 클립 → 3,000개 이진(binary) 예제로 만들기**
- 오디오 파형(waveform): X축 시간, 마이크가 공기 압력의 빠른 변화를 기록한 wiggly 시계열.
- 10초 오디오에서 **3초 윈도우**를 슬라이딩하며 잘라낸다.
- 라벨: 그 3초 윈도우의 **끝이 방금 "Robert turn on"을 다 말한 순간**이면 **1**, 그 외에는 **0**.
- 한 클립에서 30개 윈도우 → 100 클립 × 30 = **약 3,000개의 0/1 라벨 예제.**

### 문제 1 — 97% 정확도인데 전부 0만 출력
- dev 셋에서 이진 분류 **97% 정확도**를 얻었지만, 사실 **항상 0을 출력**해서(탐지 0건) 얻은 것. 거대한 신경망이 `print(0)` 한 줄과 똑같은 결과를 낸 셈.
- 원인: **불균형 데이터(unbalanced data).** 양성:음성 ≈ **1:30**.

**해결책(학생들 + 강사)**
- 양성 예제 **복제(duplicate)** 하거나, 손실 함수에서 양성에 **가중치(weight)** 부여.
- **거짓 음성(false negative) 패널티** 강화 (비용 함수 변경).
- **음성 예제 수 줄이기** — 단, 음성의 다양성이 줄면 학습 정보가 약간 줄어드는 단점(작은 차이).
- **노이즈 추가** 등 합성 데이터 변형.

> **불균형 데이터 경험칙(rule of thumb):** 신경망은 대략 **1:10 비율까지는 잘 견딘다.** 1:2 정도면 보통 신경 안 쓴다. 1:10을 넘어가면(이 예제는 1:30) 균형을 맞출 조치를 고려한다. (결과는 경우마다 다름.)

**팀이 실제로 쓴 변형 (자랑이 아니라 실전 예시)**
- 양성 라벨을 "방금 100ms 안에 끝남" → **"지난 0.5초~1초 안에 끝나면 1"** 로 윈도우를 약간 늘림.
- 효과: 단순 복제보다 **양성 예제의 다양성(diversity)** 이 조금 더 생긴다(여러 위치의 빨간 사각형이 모두 양성). 성능 차이는 작지만 약간 더 낫다.

### 문제 2 — 훈련 95%, dev 30% (과적합)
- 한 문제를 고치니 다음 문제 등장: 훈련 95%, **dev 30%(부족)** → **과적합(overfitting).**
- (참고로 train과 dev를 무작위로 섞었다면 두 분포는 같다.)

**train/test 분포에 대한 통찰**
> 학계 머신러닝은 train과 test가 **같은 분포(same distribution)** 라고 가정한다(정리 증명·보장이 쉬워서). 하지만 **실무에서는 train 분포가 test 분포와 다른 경우가 흔하다.** 특히 합성 데이터로 거대한 train 셋을 만들면, 사용자는 합성 데이터처럼 말하지 않으므로 **test 셋에는 진짜 데이터(true data)** 를 넣어야 제품 체감 성능을 정확히 반영한다.

**해결책**
1. **정규화(regularization)** 를 먼저 시도.
2. **데이터 더 모으기** — 음성 문제에서 과적합엔 데이터가 좋다.

### 효과적인 합성 데이터 기법 — 배경 소음 합성 (결국 채택)
- **소리는 더해진다(superposition property of sound).** 두 오디오 파형을 합치면, 두 소리가 동시에 나는 것처럼 들린다.
- 절차:
  1. **깨끗한 "Robert turn on"** 녹음 소수 + **다양한 배경 소음**(에어컨, 도로, 카페 소음 등; YouTube 등에 공개 라이선스 클립 많음 — **라이선스 확인 필수**) 다수 확보.
  2. `배경소음 + 깨끗한 음성`을 더해 → 다양한 배경에서 말한 것 같은 **양성 예제 수천 개** 합성.
- **함정:** 위만 하면 "Robert turn on" 감지기가 아니라 **음성 활동 감지기(voice activity detector)** 가 된다 (말소리만 나면 무조건 양성이 됨, 그게 더 쉬우니까).
  - **수정:** 배경 소음 위에 "Robert turn on"뿐 아니라 **다른 단어들**(예: "cardinal" 등 사전에서 뽑은 단어)도 합성해 넣어, "그 외 단어"의 음성 예제도 풍부하게 만든다.
- 음악 환경 대응: 사용자가 음악을 많이 듣는다면 **배경에 음악을 합성.** 어떤 장르일지 모르면 **classical·rock·EDM 등 다양하게 모두 포함**하는 것이 좁게 골라 틀리는 것보다 낫다.

> **데이터 다양성 경험칙:** 신경망 용량이 충분하다면, **더 많고 더 다양한 데이터가 보통 더 좋다.** 단, 네트워크가 너무 작으면(edge용 초소형) 다 외울 용량이 부족할 수 있다.

## 🔁 머신러닝 = 디버깅, 그리고 반복 속도

> 머신러닝의 워크플로는 개발보다 **디버깅**에 가깝다. 시스템을 만들고, 어디가 안 되는지 반복적으로 찾아 고친다. 사람이 할 수 있는 일을 시킬 때, 성능의 빈틈은 보통 "사람은 명확히 하는데 AI는 못 하는" 부분이다.

**규율 있는 일일 디버깅 사이클 (4시간 훈련 모델 예시)**
| 시간대 | 작업 |
|---|---|
| 밤(night) | 훈련 작업(job) 실행 (예: 4시간 소요) → 밤새 돌림 |
| 아침(morning) | 결과 확인, **오차 분석**으로 무엇이 잘못됐는지 파악 |
| 오후(afternoon) | 어제 발견한 문제를 고치는 코드 작성 |
| 저녁(evening) | 퇴근 전 훈련 작업 실행 (필요시 잘 도는지만 확인) |

- **하루에 한 문제씩 고쳐도 꽤 좋다.** 규율 있는 팀은 계속 전진하지만, "다음에 뭐 하지? 회의는 내일... 인프라 다운..." 하는 팀은 훨씬 느리다.

**훈련 시간이 반복 속도(pacing)를 좌우한다**
| 훈련 시간 | 작업 리듬 |
|---|---|
| 10분 | 이상적. 돌리고 결과 보고, 커피 한 잔. 병목은 "얼마나 빨리 데이터 분석·확보하느냐" |
| 4시간 | 기다리기엔 길지만 밤새 돌리면 OK |
| 3주 | 작업을 비동기로 여러 개 병렬 실행; 이전 작업 분석하며 새 작업 시작. 체크포인트(checkpoint)로 중간 점검 |

- 흔한 함정: 성능이 오르면서 더 큰 모델·더 많은 데이터로 가다 보면, **10분 반복이 4시간 → 3주 → 한 달 반으로** 늘어난다. 어쩔 수 없이 감수해야 할 때도 있다.
- **체크포인트 활용:** 3주짜리 작업이 며칠/일주일 후 기대 수준과 크게 어긋나면, 2주를 더 태우기 전에 "학습률(learning rate)이 명백히 틀렸나? 새 데이터셋이 틀렸나?"를 점검. 가끔(아주 드물게) 작업을 중단(yank)하기도 한다.
- **전이 학습(transfer learning):** 큰 데이터로 사전학습 후 작은 데이터로 **파인튜닝(fine-tuning)** 하면(예: 30분), 훨씬 빠른 반복이 가능하다.

**왜 속도에 집착하는가 — 시장 경쟁**
> 경쟁사가 같은 성능에 도달하는 데 **2배 시간**이 걸린다면, 같은 시점에 **당신의 시스템이 훨씬 더 나아** 보인다. "이틀 vs 하루"의 문제가 아니라 "**2배 느림**"의 문제이며, 그 차이가 시장 성능의 거대한 격차로 누적된다.

## 🔬 예제 2 — AI 딥 리서처 (파이프라인/캐스케이드)

### 단일 신경망 vs 파이프라인
- 예제 1(wake word)은 입력 오디오 → 신경망 하나 → 출력의 **end-to-end** 시스템.
- 많은 실제 응용은 **파이프라인(pipeline, 또는 cascade)** — 여러 구성요소를 연결. (지난 시간 얼굴 인식 문 잠금: 영상 → 활동 감지 → 인식 신경망 → 0/1.)

### 기본 딥 리서처 아키텍처 (선형 파이프라인)
```
쿼리 (예: "show me the latest research on black holes")
   │
   ├─► [LLM] 검색어(search terms) 생성
   │
   ├─► [웹 검색 엔진] 호출 (Google / Bing / DuckDuckGo / AI용 검색엔진 등)
   │
   ├─► [LLM] 스니펫 보고 상위 URL 선택 → 상위 페이지 fetch
   │       (10개 다 받지 않고 관련성 높은 것만)
   │
   └─► [LLM] 종합하여 최종 보고서(writing) 작성
```
> 이것은 **초기/전통적** 딥 리서처 구조(선형). **현대적·에이전트형(agentic)** 구조는 시스템이 **언제 더 검색할지, 더 fetch할지를 스스로 결정**하고 몇 번 반복한다.

### 핵심: 어느 구성요소를 고칠 것인가
파이프라인에서 잘못될 수 있는 곳이 많다:
- 검색어 생성이 부적절한가?
- 웹 검색 엔진이 충분히 포괄적인가? (특히 **신선한 뉴스(fresh news)** 는 엔진별 성능 차이가 큼)
- **권위 있는 페이지**(예: nasa.gov)를 잘 골라 fetch하는가, 아니면 `bobsbackyardastronomyblog.com`이나 랜덤 TikTok을 가져오는가?
- 주어진 출처로 사려 깊은 글을 쓰는가?

> 경험 있는 AI 전문가들은 "다음에 뭘 할지"에 대해 **의견의 분산(variance)이 의외로 작다.** 항상 옳아서가 아니라, **체계적인 오차 분석 방법론**이 있기 때문이다. 경험 적은 엔지니어들 사이에서는 분산이 훨씬 크다.

## 🧪 오차 분석(error analysis) — 방법론

> 머신러닝은 마구잡이로 시도하는 게 아니라, **무엇을 작업할지 결정하는 사려 깊고 규율 있는 과정**이다. 그 핵심이 오차 분석이다.

**원칙**
- 각 **중간 단계(intermediate step)의 출력**을 직접 들여다본다. "좋은 생각"이라며 동의는 해도 막상 실제로 하는 사람의 비율은 100%보다 훨씬 낮다.
- 오차/갭 분석은 대개 **수작업(manual)** 이다. **사람이 AI보다 잘하는 지점**을 찾아 그 지식을 AI에 주입하는 과정이므로, 사람의 시간이 필요하다. (자동화 시도는 있으나 아직은 사람의 통찰이 필요.)
- **성능이 부족한(subpar) 쿼리에 집중**한다(그래서 "error" 분석). 잘 되는 건 덜 본다. 보통 **10~100개** 쿼리를 본다(100개 넘게 보기도).

**스프레드시트 예시** — 행=쿼리, 열=파이프라인 단계, 각 칸에 "이 단계 만족스러운가?"와 메모

| 쿼리 | 검색어(search terms) | 웹 검색(web search) | 페이지 fetch | 글쓰기(writing) |
|---|---|---|---|---|
| black hole science | OK | OK | ✗ (Bob 대신 NASA를 놓침 → 메모: "Bob instead of NASA") | OK |
| rent vs buy (SF) | OK | ✗ (좋은 블로거를 놓침; 검색엔진 문제?) | ... | ... |
| weekend in Santa Cruz | OK | ... | ✗ (지역 명소 대신 과대광고 관광지) | ... |

**불만족 비율 집계 예시 (한 칸이 여러 문제일 수 있어 합이 100%일 필요 없음)**
```
전체 불만족          : 70%
페이지 fetch 실패    : (큰 비중)   ← 여기 집중!
검색어 오류          : ~20%
글쓰기 부족          : ~20%
웹 검색 부족         : ~5%
```
→ 불만족의 큰 부분이 **"웹 검색 결과에서 좋은 페이지를 못 고름"** 이면, **거기에 노력을 집중**한다.

**왜 중요한가**
- 이 분석 없이는 어느 구성요소에 집중할지 알 수 없다. 몇 시간(3~4시간)의 오차 분석이 **잘못된 방향으로 가는 몇 주를 절약**한다.
- 반례: 진짜 문제는 "좋은 페이지를 못 고르는 것"인데, 어떤 영업사원이 새 웹 검색 서비스를 팔러 와서 팀이 **6개월간 검색 엔진만 바꿔보다** 결국 전체 성능엔 영향을 못 주는 경우. — 오차 분석을 했다면 피할 수 있었다.

## 🔑 핵심 용어

| 용어 | 뜻 |
|---|---|
| wake word / trigger word (깨우기 단어) | 기기를 활성화시키는 짧은 문구. 예: "Hey Siri", "Alexa", "Robert turn on" |
| end-to-end 시스템 | 입력→출력을 단일 신경망 하나로 처리하는 구조 |
| pipeline / cascade (파이프라인) | 여러 구성요소를 순차 연결한 시스템 |
| train/dev/test split | 훈련/개발(튜닝)/테스트 데이터 분할. 실전에선 test 없이 dev만 쓰기도 함 |
| unbalanced data (불균형 데이터) | 클래스 비율이 치우친 데이터. 경험칙상 ~1:10까지는 견딤 |
| overfitting (과적합) | 훈련엔 잘 맞지만 dev/test 성능이 나쁜 상태. 정규화·데이터 증가로 대응 |
| regularization (정규화) | 과적합을 줄이는 기법 |
| synthetic data (합성 데이터) | TTS·오디오 합성 등으로 생성한 데이터. 유용하나 보통 후반에 도입 |
| superposition property of sound | 두 오디오 파형을 더하면 두 소리가 동시에 나는 것처럼 들리는 성질 (배경 소음 합성에 이용) |
| voice activity detection | 단어 식별이 아니라 "말소리가 있는가"만 감지 — 데이터 구성이 부실하면 빠지는 함정 |
| error analysis (오차 분석) | 성능 부족 사례를 수작업으로 분석해 어느 구성요소를 고칠지 정하는 과정 |
| transfer learning / fine-tuning | 큰 데이터로 사전학습 후 작은 데이터로 미세조정 — 반복 속도 향상 |
| iteration speed (반복 속도) | 만들고-분석하고-고치는 한 사이클의 속도. 훈련 시간이 이를 좌우 |
| agentic pipeline | 다음 행동(추가 검색·fetch)을 스스로 결정하는 자율형 파이프라인 |

## ✍️ 학습 메모

- **첫 행동 = 문헌 조사 + 오픈소스.** 구현부터 달려들지 말 것. 논문은 하나씩 끝내지 말고 넓게 훑고, 막히면 저자/전문가에게 정중한 이메일(ROI 높음).
- **데이터가 없으면 직접, 창의적으로 모은다.** 동의·프라이버시는 필수. 합성 데이터는 강력하지만 손잡이가 많아 보통 나중에.
- 작은 데이터(100 클립)도 **슬라이딩 윈도우**로 수천 개 이진 예제로 확장 가능. 단 **불균형**을 조심(전부 0 출력하는 함정).
- **한 문제 고치면 다음 문제가 나온다**가 정상. ML은 디버깅 루프다. "밤 훈련 / 아침 분석 / 오후 코딩 / 저녁 실행"의 규율 있는 cadence가 속도를 만든다.
- **train과 test 분포는 달라도 된다.** test에는 사용자가 실제로 신경 쓰는 **진짜 데이터**를 넣어 체감 성능을 반영하라.
- **배경 소음 합성**은 실전에서 잘 통한 기법. 단 "그 외 단어"도 섞어야 voice activity detector로 전락하지 않는다.
- **속도는 곧 경쟁력.** 2배 느림은 시장에서 치명적 격차로 누적된다.
- 파이프라인에서는 **오차 분석으로 병목 구성요소를 특정**하는 것이 핵심. 스프레드시트로 10~100개 subpar 쿼리를 단계별로 점검하고, 불만족 비율을 집계해 **가장 큰 칸에 집중**하라. 몇 시간의 분석이 몇 주~몇 달의 헛수고를 막는다.
