# VI. 추가 면접 질문 목록 (Advanced Interview Questions)


## A. 고급 아키텍처 및 메모리 질문 (DTCM/Cache Focus)

---

**1. TCM vs. Cache: 결정론적 성능 보장 방법**  
- **TCM(Tightly Coupled Memory)**는 CPU와 직접 연결된 고속 메모리로, 접근 시간이 항상 일정합니다(결정론적).  
- **Cache**는 CPU와 메모리 사이에 위치한 임시 저장소로, 캐시 미스가 발생하면 접근 시간이 불확실해집니다(비결정론적).  
- **RTOS 스택을 DTCM에 배치하는 이유:**  
  - RTOS의 태스크 스택은 인터럽트, 컨텍스트 스위칭 등 실시간 동작에 사용되므로  
    항상 일정한 접근 시간이 필요합니다.  
  - DTCM에 스택을 두면 캐시 미스에 의한 예측 불가능한 지연 없이  
    하드 실시간 요구사항을 만족할 수 있습니다.

---

**2. DMA와 Write-Back 캐시 동기화 절차**  
- **문제:** CPU가 Write-Back 캐시를 사용하는 영역을 DMA로 외부 장치와 공유할 때,  
  캐시와 실제 메모리의 데이터가 불일치할 수 있습니다.
- **동기화 방법:**  
  - DMA 전송 전에:  
    - **Cache Clean(Write-Back)** 연산을 수행하여 캐시에 있는 변경 데이터를 메모리에 반영합니다.
  - DMA 전송 후:  
    - **Cache Invalidate** 연산을 수행하여 캐시를 무효화하고,  
      DMA가 변경한 최신 데이터를 메모리에서 읽도록 합니다.
- **순서:**  
  1. DMA 시작 전: Clean (Write-Back)  
  2. DMA 완료 후: Invalidate

---

**3. Cortex-M의 자동 스택킹 이점**  
- Cortex-M 코어는 예외(인터럽트) 진입 시 **자동으로 R0~R3, R12, LR, PC, xPSR** 레지스터를 스택에 저장합니다.
- **이점:**  
  - RTOS에서 컨텍스트 스위칭 시, 소프트웨어가 모든 레지스터를 직접 저장/복원할 필요가 없습니다.
  - 하드웨어가 자동으로 주요 레지스터를 스택에 저장하므로  
    컨텍스트 스위칭 오버헤드가 줄고, 레이턴시가 낮아집니다.

---

**4. Cortex-R의 파이프라인과 결정론**  
- Cortex-R은 Cortex-M보다 더 깊은 파이프라인(더 많은 단계)을 가지고 있습니다.
- **깊은 파이프라인의 영향:**  
  - 분기 예측(branch prediction)이 더 중요해집니다.  
  - 분기 예측 실패(misprediction)가 발생하면, 파이프라인을 flush하고 다시 채워야 하므로  
    실행 시간이 크게 변동(비결정론적)이 생깁니다.
- **결정론적 성능 저하:**  
  - 실시간 시스템에서는 예측 실패로 인한 지연이  
    응답 시간의 worst-case를 늘려, 결정론적 성능을 저해할 수 있습니다.

## B. RTOS 및 동기화 난제 질문

---

**5. RTOS 스케줄러 트리거 메커니즘**  
- OS Tick 인터럽트는 주기적으로 발생하여 RTOS의 시간 관리 및 태스크 스케줄링을 트리거합니다.
- Tick 인터럽트가 발생하면, RTOS는 현재 실행 중인 태스크의 실행 시간을 갱신하고, 필요 시 스케줄러를 호출하여 태스크 전환(Context Switch)을 수행합니다.
- **Context Switch가 인터럽트 컨텍스트에서 발생:**  
  - 인터럽트 핸들러 내부에서 바로 태스크 전환이 이루어집니다.
  - 인터럽트 종료 후 바로 새로운 태스크가 실행됩니다.
- **Context Switch가 태스크 컨텍스트에서 발생:**  
  - 태스크가 스스로 yield하거나, 이벤트(예: 세마포어 획득 실패)로 인해 스케줄러가 호출됩니다.
  - 태스크 코드 흐름 내에서 전환이 이루어집니다.
- 차이점: 인터럽트 컨텍스트에서는 즉시 전환, 태스크 컨텍스트에서는 태스크 코드 흐름에 따라 전환.

---

**6. 무계 우선순위 역전 시나리오와 해결책**  
- **무계 우선순위 역전(Unbounded Priority Inversion):**  
  - 저(L) 우선순위 태스크가 자원을 점유하고 있을 때, 중(M) 우선순위 태스크가 계속 실행되어 고(H) 우선순위 태스크가 자원을 획득하지 못하는 상황.
  - 중(M) 태스크가 계속 실행되면, 고(H) 태스크의 대기 시간이 예측 불가능하게 길어질 수 있음.
- **우선순위 상속(Priority Inheritance) 프로토콜:**  
  - 저(L) 태스크가 자원을 점유하고 있고, 고(H) 태스크가 자원을 기다리면, 저(L) 태스크의 우선순위를 고(H)로 임시 상승시킴.
  - 저(L) 태스크가 자원을 해제할 때까지 중(M) 태스크가 실행되지 않으므로, 고(H) 태스크가 빠르게 자원을 획득할 수 있음.

---

**7. 세마포어 vs. 뮤텍스**  
- **소유권(Ownership) 차이:**  
  - 뮤텍스는 락을 획득한 태스크만 해제할 수 있어 소유권이 명확함.
  - 세마포어는 누구나 값을 증가/감소할 수 있어 소유권이 없음.
- **Priority Inversion 해결:**  
  - 뮤텍스는 소유권이 있기 때문에 우선순위 상속 등 Priority Inversion 해결 기법을 적용할 수 있음.
  - 세마포어는 소유권이 없으므로, 우선순위 상속이 불가능하거나 효과가 제한적임.

---

**8. 단일 코어에서의 스핀락 사용처**  
- **단일 코어에서 스핀락이 권장되지 않는 이유:**  
  - 스핀락은 락이 해제될 때까지 CPU를 계속 바쁘게 대기시키므로, 단일 코어에서는 다른 태스크가 실행될 기회가 없어 비효율적임.
- **임계 영역 예시:**  
  - 인터럽트 비활성화(disable)를 통해 임계구역을 보호하는 경우:  
    - 예: ISR과 메인 루프가 공유하는 변수 접근, 하드웨어 레지스터 설정 등  
    - 아주 짧은 시간 동안만 보호가 필요할 때 사용.

## C. Embedded C 및 디버깅 질문

---

**9. Inline 함수와 컴파일러 최적화**  
- `inline` 키워드는 컴파일러에게 함수 호출 대신 함수 본문을 직접 삽입하도록 요청합니다.
- 컴파일러가 인라인을 거부할 수 있는 상황:  
  - 함수가 너무 크거나, 재귀적이거나, 주소가 필요한 경우 등
- 인라인이 거부되면 일반 함수 호출이 발생하여, 성능(함수 호출 오버헤드)이 저하될 수 있음.

---

**10. T32 디버깅과 인라인 함수**  
- 인라인 함수는 여러 위치에 삽입되므로, 디버거에서 브레이크포인트 설정이 어려울 수 있음.
- TRACE32 등 디버거는 인라인된 코드의 각 인스턴스를 별도로 식별해야 하며,  
  소스 코드와 실제 실행 위치가 다를 수 있어 디버깅이 복잡해짐.

---

**11. volatile 키워드의 필요성**  
- ISR과 메인 루프가 공유하는 변수에 `volatile`을 사용하면,  
  컴파일러가 해당 변수의 값을 항상 메모리에서 읽고, 최적화로 제거하지 않게 보장함.
- `volatile`을 생략하면, 컴파일러가 변수 값을 레지스터에 캐싱하여  
  ISR에서 변경된 값을 메인 루프에서 인식하지 못하는 버그가 발생할 수 있음.

---

**12. Context Switching을 위한 C 함수 포인터**  
- RTOS는 새로운 태스크 생성 시, 태스크 함수의 시작 주소와 초기 파라미터,  
  그리고 예외 복귀(EXC_RETURN) 값을 포함한 Stack Frame을 미리 구성함.
- Cortex-M에서는 예외 복귀 시 EXC_RETURN 값을 통해  
  자동으로 태스크 함수로 점프할 수 있도록 스택을 세팅함.
- 이를 통해 태스크가 처음 실행될 때, 함수 포인터로 진입하게 됨.
