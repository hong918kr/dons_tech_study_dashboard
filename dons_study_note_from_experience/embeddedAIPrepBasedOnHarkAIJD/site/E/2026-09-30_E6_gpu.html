0. 큰 그림 — 이게 왜 필요한가#

Don이 실리콘 평가를 하게 되면 데이터시트 표에 거의 항상 이런 줄이 있다: "CPU: 8코어, GPU: Adreno xxx, NPU: Hexagon, 45 TOPS". 그리고 PM이나 ML 팀이 묻는다. "GPU가 있는데 NPU가 왜 필요하냐?", "우리 모델은 GPU에서 돌리면 되지 않냐?", "LLM은 GPU로 돌리는 게 빠르다던데?"

이 질문에 답하려면 GPU가 무엇을 잘하도록 설계된 기계인지를 알아야 한다. 한 문장으로 요약하면 이렇다.

  • CPU는 latency machine이다. thread 하나를 가능한 한 빨리 끝내려고 큰 캐시, 분기 예측, out-of-order 실행에 면적을 쓴다.
  • GPU는 throughput machine이다. thread 하나는 느려도 괜찮고, 수천~수만 개를 동시에 걸어 두고 그중 준비된 것을 번갈아 돌려서 전체 처리량을 최대화한다. 면적은 ALU와 레지스터에 쓴다.

그림 1 — CPU와 GPU가 실리콘 면적을 쓰는 방식(개념도, 비율은 실제가 아님). CPU 코어는 제어·캐시가 크고 ALU가 상대적으로 작다. GPU는 SM(streaming multiprocessor) 안에 작은 ALU lane이 빽빽하고, 그것을 warp scheduler가 묶어서 돌린다.

Don의 경험에 비유하면: SSD 컨트롤러 펌웨어에서 NAND 읽기 지연(수십 µs)을 숨기려고 여러 die에 명령을 동시에 걸어 두고(queue depth), 먼저 끝난 것부터 처리했던 것을 떠올리면 된다. GPU는 그 아이디어를 하드웨어 스케줄러로 만든 것이다. 명령 하나의 지연은 줄이지 않는다. 동시에 걸린 일의 수로 지연을 덮는다.

이 설계 철학에서 이 노트의 결론이 바로 나온다.

  • 일이 많고 규칙적이면(큰 행렬곱, 고해상도 이미지, batch, LLM prefill) GPU는 강하다.
  • 일이 작고 한 번에 하나씩이면(batch=1, 10 ms마다 작은 오디오 모델) GPU는 걸어 둘 일이 부족해서 대부분 놀고, launch·동기화 고정비와 켜 두는 전력만 낸다.

1. GPU 실행 모델 — SM, SIMT, warp#

1.1 계층 구조 — thread, warp, block, grid#

GPU 프로그래밍 모델은 같은 함수(kernel)를 아주 많은 thread가 각자 다른 인덱스로 실행하는 구조다. 펌웨어 식으로 말하면 for (i = 0; i < N; i++) body(i);에서 루프를 없애고 body(i)를 N개의 thread에 뿌리는 것이다.

소프트웨어 쪽 계층과 하드웨어 쪽 계층이 짝을 이룬다.

  • SM (streaming multiprocessor): NVIDIA 용어. GPU의 "코어"에 해당하는 단위다. 안에 ALU lane 수십~백여 개, 큰 레지스터 파일, shared memory, warp scheduler가 있다. AMD는 CU (compute unit), Apple은 그냥 "GPU core", Arm Mali는 "shader core"라고 부른다.
  • warp: 한 명령을 동시에 실행하는 thread 묶음. NVIDIA는 32다. 한 warp의 32 thread는 같은 명령어를 같은 시점에 실행한다.
  • block(CUDA) / threadgroup(Metal) / work-group(OpenCL) / workgroup(Vulkan): 서로 협력할 수 있는(shared memory 공유, barrier 동기화) thread 묶음. 반드시 한 SM 안에서 돈다.

회사마다 이름이 달라서 처음엔 헷갈린다. 표로 정리한다.

1.2 SIMT vs SIMD — Don이 아는 NEON/HVX와 무엇이 다른가#

SIMD(single instruction, multiple data)는 Don이 아는 것이다. NEON 명령 하나가 128-bit 레지스터 안의 float 4개를 한 번에 더한다. 프로그래머(또는 컴파일러)가 "4개씩 묶어서" 코드를 쓴다.

SIMT(single instruction, multiple threads)는 NVIDIA가 붙인 이름이다. 하드웨어는 사실상 32-wide SIMD인데, 프로그래머에게는 thread 하나의 스칼라 코드를 쓰게 한다. 하드웨어가 32개 thread를 모아 한 명령으로 실행하고, 분기가 갈리면 mask로 일부 lane을 끈다.

1.3 Divergence — 분기가 갈리면 두 길을 모두 간다#

한 warp의 32 lane은 같은 명령을 실행해야 한다. 그런데 if (x[i] > 0) A(); else B();에서 lane마다 조건이 다르면? 하드웨어는 A를 실행하는 동안 B쪽 lane을 끄고, 그다음 B를 실행하는 동안 A쪽 lane을 끈다. 이것이 divergence(분기 발산)다.

그림 2 — divergence. 8-lane으로 줄여 그렸다. 조건이 섞이면 A 단계와 B 단계를 순서대로 모두 거치고, 각 단계에서 절반 정도의 lane은 자리만 차지한다.

손계산: A와 B가 각각 10 사이클이라고 하자.

  • warp 안의 모든 lane이 같은 쪽 → 10 사이클.
  • 섞여 있음 → 10 + 10 = 20 사이클. 효율은 절반.
  • 32 lane 중 딱 1개만 B → 그래도 20 사이클. 가장 드문 lane 하나가 warp 전체의 비용을 정한다.

중요한 점: divergence는 warp 안에서만 문제다. warp 0은 모두 A, warp 1은 모두 B로 갈리면 각 warp는 한 경로만 실행하므로 손해가 없다.

예제 1 — 무엇을 확인하나: 1024 thread(32 warp)가 다섯 가지 조건으로 분기할 때 총 사이클을 시뮬레이션한다. 하드웨어 모델은 위의 단순 규칙(원하는 lane이 하나라도 있으면 그 경로를 실행)이다.

출력에서 볼 것:

  • tid % 2처럼 lane 단위로 번갈아 갈리면 두 배가 된다. 같은 50 % 분할이라도 (tid // 32) % 2처럼 warp 경계에 맞춰 갈리면 손해가 0이다.
  • 데이터 의존 분기(x > 0)는 정규분포 데이터에서 거의 모든 warp가 섞이므로 두 배다.
  • 드문 예외(x > 2.5, 약 0.6 %)는 32개 warp 중 3개만 B 경로를 추가로 탔다(350 = 320 + 3 × 10). 예외 처리 분기는 싸다.

Don의 경험과 연결: DSP에서 샘플마다 if를 쓰면 VLIW 슬롯이 깨지니까 select/predication으로 바꿨던 것과 같은 문제다. GPU에서는 하드웨어가 자동으로 predication을 해 주지만, 비용은 똑같이 두 경로의 합이다.

참고: NVIDIA Volta 이후 GPU는 thread마다 별도의 program counter를 두는 "independent thread scheduling"을 도입했다. 이것은 warp 안에서의 동기화·데드락 문제를 풀어 주지만, 갈라진 경로가 동시에 실행된다는 뜻은 아니다. 성능 관점의 결론(두 경로의 합)은 그대로다.

ML과 연결: 행렬곱·conv·elementwise는 분기가 거의 없어서 divergence 걱정이 없다. 문제가 되는 곳은 NMS(non-maximum suppression), beam search, top-k, 동적 shape 처리, tokenizer처럼 데이터 의존 제어 흐름이 있는 부분이다. 이런 연산은 GPU delegate가 CPU로 되돌려 보내는(fallback) 경우가 많다.

1.4 Latency hiding — 기다리는 warp 대신 준비된 warp#

GPU의 global memory 접근은 수백 사이클이 걸린다. CPU는 이 지연을 큰 캐시와 out-of-order로 줄이려 한다. GPU는 다른 방법을 쓴다: SM 안에 warp를 여러 개 상주(resident)시켜 두고, 어떤 warp가 load 결과를 기다리면 다음 사이클에 준비된 다른 warp의 명령을 issue한다. 레지스터 파일이 warp마다 따로 있으므로 이 전환은 비용이 0이다(CPU의 context switch처럼 레지스터를 저장·복원하지 않는다).

그림 3 — latency hiding. warp 하나가 "계산 2칸, 메모리 대기 10칸"을 반복한다. (a) warp 1개면 ALU는 26칸 중 6칸만 일한다. (b) warp 4개를 엇갈려 놓으면 32칸 중 24칸이 일한다. warp가 6개(= 1 + 10/2)면 빈칸이 거의 사라진다.

손계산: 필요한 warp 수 추정.

말로 하면: 메모리가 느릴수록, 그리고 warp 하나가 load 사이에 하는 계산이 적을수록 더 많은 warp가 동시에 떠 있어야 한다.

대역폭 관점에서 다시 보면 이것은 Don이 PCIe·NVMe에서 본 Little's law다. 메모리 대역폭 100 GB/s, 지연 500 ns라면 "비행 중인 바이트" = 100e9 × 500e-9 = 50 KB가 항상 걸려 있어야 대역폭을 다 쓴다. warp 하나의 load가 128 B라면 약 400개의 load가 동시에 떠 있어야 한다. NVMe에서 queue depth 1로는 SSD 대역폭을 못 뽑는 것과 정확히 같은 이야기다.

1.5 Occupancy — 상주 warp 수를 무엇이 제한하나#

occupancy(점유율) = SM에 실제로 상주하는 warp 수 ÷ SM이 받을 수 있는 최대 warp 수.

상주 warp 수는 SM의 자원 중 가장 먼저 바닥나는 것이 정한다.

  • 레지스터: SM 레지스터 파일(예: 32-bit 레지스터 65,536개)을 thread들이 나눠 쓴다. thread당 레지스터를 많이 쓰는 커널은 동시에 올라갈 수 있는 thread가 줄어든다.
  • shared memory: block마다 요청한 shared memory의 합이 SM 용량을 넘을 수 없다.
  • warp 슬롯 / block 슬롯: SM이 추적할 수 있는 warp·block 수의 하드웨어 상한.

손계산 (예시 SM: 레지스터 65,536개, 최대 64 warp):

예제 2 — 무엇을 확인하나: 위 계산을 여러 설정으로 돌린다. SM 한도는 설명용으로 NVIDIA A100의 공개 수치(SM당 레지스터 64K개, 최대 64 warp, 최대 32 block, shared memory 최대 164 KB)와 비슷하게 잡았다. 실제 하드웨어는 레지스터를 할당 단위로 반올림하는 등 세부 규칙이 더 있다(NVIDIA의 occupancy calculator가 그것까지 계산한다).

그림 4 — 예제 2의 결과. 같은 256-thread block이라도 thread당 레지스터가 32 → 64 → 128개로 늘면 상주 warp가 64 → 32 → 16으로 줄어든다. shared memory를 block당 48 KB 쓰면 block 3개만 올라가 37.5 %가 된다.

출력에서 볼 것:

  • thread당 레지스터가 두 배가 되면 occupancy가 반이 된다. 레지스터가 가장 흔한 제한 요인이다.
  • 128 thread × 255 레지스터(레지스터를 최대로 쓰는 커널)는 12.5 %.

흔한 오해: occupancy가 높을수록 항상 빠르다 — 아니다. occupancy는 "지연을 숨길 여유"일 뿐이다. 잘 튜닝된 GEMM 커널은 thread당 레지스터를 많이 써서 레지스터에 타일을 올리고(재사용 ↑), 일부러 occupancy를 낮춘다. warp 하나가 load 사이에 계산을 많이 하면(1.4절의 c가 크면) 적은 warp로도 지연이 숨겨진다. 판단 기준은 occupancy가 아니라 실측 처리량과 roofline(D3) 대비 위치다.

2.2 Coalescing — warp의 주소를 한 덩어리로#

warp 32 lane이 동시에 load를 하면, 하드웨어는 32개 주소를 모아 몇 개의 메모리 transaction으로 합칠지 계산한다. NVIDIA GPU는 L2/DRAM과 32 B sector 단위로, L1은 128 B 라인 단위로 데이터를 옮긴다. lane들의 주소가 연속된 128 B 안에 모여 있으면 sector 4개로 끝난다. 이것이 coalesced access(합쳐진 접근)다.

예시 — 컴파일하지 않음 (CUDA C, 이 Mac에는 CUDA가 없다):

(c)는 CPU라면 좋은 코드다(thread 하나가 연속 메모리를 훑는다). 그런데 GPU에서는 같은 순간에 warp의 32 lane이 읽는 주소들이 중요하다. 그 순간 lane들은 서로 다른 행의 같은 열 j를 읽으므로 주소가 cols × 4 바이트씩 떨어져 있다. 이것이 CPU 직관이 GPU에서 틀리는 대표 사례다.

그림 6 — coalescing. (a) 연속 주소는 32 B sector 하나(8 lane 기준)에 들어간다. (b) stride 8(= 32 B 간격)이면 lane마다 다른 sector를 건드려 8배의 데이터를 옮기고 그중 1/8만 쓴다.

예제 3 — 무엇을 확인하나: 여섯 가지 접근 패턴에서 warp 하나(32 lane × float)가 건드리는 32 B sector 수와 효율을 센다.

  • 한 칸만 어긋나도(tid + 1, 정렬 안 됨) sector가 하나 더 붙어 80 %가 된다. 그래서 텐서 할당은 보통 큰 정렬(수백 B 이상)로 한다.
  • stride 32 이상(열 읽기 포함)은 lane마다 sector 하나씩 32개 — 8배의 트래픽, 효율 12.5 %.
  • 모두 같은 주소(broadcast)는 sector 1개로 끝난다. 효율 숫자는 낮게 나오지만 transaction 하나라 싸다.

Don의 경험과 연결: DMA burst와 똑같다. AXI에서 4 B씩 흩어진 주소로 single transfer를 날리면 bus 효율이 바닥이고, 정렬된 연속 burst로 묶어야 대역폭이 나온다. GPU는 이 "묶기"를 warp 단위로 하드웨어가 자동으로 해 주지만, 묶일 수 있는 주소 패턴을 만드는 것은 프로그래머 몫이다.

2.3 Shared memory bank conflict (짧게)#

shared memory는 보통 32개 bank로 나뉘어 있고, 연속된 4 B 워드가 bank 0, 1, 2 … 31, 0, 1 … 순서로 배치된다. warp의 32 lane이 서로 다른 bank를 건드리면 한 사이클, 같은 bank의 서로 다른 주소를 건드리면 직렬화된다. 예: float tile[32][32]에서 열 방향으로 읽으면 모든 lane이 같은 bank → 32-way conflict. 흔한 해결책은 tile[32][33]처럼 한 칸 padding을 넣어 bank를 어긋나게 하는 것이다. Don이 SRAM bank interleaving으로 동시 접근을 늘렸던 것과 같은 원리다.

2.4 Tensor core / matrix unit — GPU 안의 작은 NPU#

2017년 NVIDIA Volta부터 SM 안에 tensor core가 들어갔다. 일반 ALU lane이 스칼라 FMA(곱셈-누산) 하나를 하는 동안, tensor core는 작은 행렬곱 한 덩어리(예: 4×4×4, 세대에 따라 더 큼)를 한 번에 처리한다. 프로그래머는 warp 단위 명령(CUDA의 WMMA API는 16×16×16 fragment, PTX의 mma 명령)으로 이를 쓴다.

  • 지원 정밀도는 세대마다 늘었다: FP16(Volta) → INT8·INT4(Turing) → BF16·TF32(Ampere) → FP8(Hopper) → FP4(Blackwell) 등. 입력은 저정밀, 누산은 FP32/INT32.
  • 데이터시트의 거대한 TOPS 숫자는 대부분 tensor core + INT8(또는 그 이하) + sparsity 조건에서 나온다(M4에서 "숨은 조건"으로 다룸).
  • Apple GPU에도 SIMD-group 단위 행렬 명령(Metal의 simdgroup_matrix, 8×8)이 있다. Qualcomm·Arm 모바일 GPU도 dot-product·행렬 확장을 넣는 추세로 알려져 있지만 세대별 세부는 벤더 문서로 확인해야 한다.

개념적으로 tensor core는 GPU 안에 들어간 작은 systolic/MAC array다. 즉 GPU도 ML용으로 점점 NPU 쪽 요소를 흡수하고 있다. 차이는 GPU가 여전히 범용 SIMT 파이프라인·큰 레지스터 파일·그래픽 기능을 끌고 다닌다는 것이다(→ 면적·전력, 8절).

3.1 Vector add — "루프를 thread로 바꾼다"#

예시 — 컴파일하지 않음 (CUDA):

읽는 법:

  • __global__: CPU가 launch하고 GPU에서 도는 함수(커널).
  • blockIdx.x, blockDim.x, threadIdx.x: 하드웨어가 thread마다 넣어 주는 내장 변수. i = blockIdx.x × blockDim.x + threadIdx.x는 2차원 배열의 row-major 주소 계산(row × width + col)과 같은 식이다.

3.2 Tiled GEMM — shared memory로 재사용을 만든다#

순진한 GEMM 커널은 C의 원소 하나당 thread 하나를 두고, 각 thread가 A의 행 K개와 B의 열 K개를 global memory에서 읽는다. C 원소 M·N개가 각각 2K번 읽으므로 global 읽기는 2·M·N·K. 같은 A 원소를 N개 thread가 따로따로 DRAM에서 가져온다 — arithmetic intensity(D3)가 바닥이다.

tiled GEMM은 block 하나가 C의 T×T 타일을 맡고, K 방향으로 A·B의 T×T 타일을 shared memory에 한 번 올려 block 안의 T² thread가 함께 재사용한다.

그림 7 — tiled GEMM. block(bx, by)는 C의 초록 타일을 맡는다. K 방향으로 A의 파란 띠와 B의 주황 띠를 T×T 조각(As, Bs)씩 shared memory에 올리고, 각 조각을 T번 재사용한다.

예시 — 컴파일하지 않음 (CUDA):

읽는 법:

  • __shared__: block 안의 모든 thread가 보는 on-chip 메모리.
  • __syncthreads(): block 안의 barrier. 두 번 쓰는 이유 — 첫 번째는 "모두 다 올렸나", 두 번째는 "모두 다 썼나(다음 load가 덮어써도 되나)". 두 번째를 빼먹는 것이 대표적인 race condition 버그다. Don이 ping-pong 버퍼에서 "DMA가 덮어쓰기 전에 CPU가 다 읽었나"를 확인하던 것과 같다.
  • 실전 커널(cuBLAS, CUTLASS)은 여기에 더해 thread 하나가 C의 여러 원소(예: 8×8)를 레지스터에 들고(register tiling), 다음 타일을 비동기로 미리 load하고(double buffering — ping-pong!), tensor core를 쓴다.

4. 이 Mac에서 재 보기 — MPS vs CPU#

이론은 충분하다. 이제 Apple M2(GPU 10코어, CPU P-core 4 + E-core 4, 24 GB unified LPDDR5)에서 직접 잰다.

측정 규칙 (D6의 규칙을 따른다):

  • 이 머신에서는 다른 작업이 동시에 돌고 있었다(load average 2.5~3.4). 모든 측정은 반복해서 median을 쓰고, 같은 스크립트를 두 번 이상 돌려 경향이 같은지 확인했다. 표의 숫자는 첫 실행 값이며, 두 번째 실행과 다른 곳은 본문에 적는다. 소수점이 아니라 자릿수와 비율을 읽자.
  • GPU는 비동기다. y = x + 1은 명령을 큐에 넣고 바로 리턴한다. 시간을 재려면 반드시 torch.mps.synchronize()로 GPU가 끝날 때까지 기다리거나, 결과를 .cpu()/.item()으로 읽어서 암묵적으로 기다려야 한다. 이것을 빼먹으면 "GPU가 1000배 빠르다"는 가짜 숫자가 나온다.
  • 첫 호출은 Metal 셰이더 컴파일·캐시 때문에 느리다. warm-up을 버린다.

CUDA 쪽 dGPU에서도 kernel launch 비용은 수 µs, 동기화 왕복은 그보다 크다고 알려져 있다. 그래서 NVIDIA는 여러 커널을 미리 녹화해 한 번에 제출하는 CUDA Graphs를 제공하고, 컴파일러들은 여러 op를 한 커널로 합치는 fusion(C6)을 한다. 둘 다 "launch 횟수를 줄이는" 처방이다.

  • 64K 원소(768 KB)에서 두 쪽이 비슷해지고(약 9 µs), 1M 원소(12 MB)에서는 CPU가 오히려 이긴다 — 12 MB는 CPU L2(16 MiB, D3 5.1절)에 들어가서 캐시 대역폭(약 100 GB/s)을 쓰기 때문이다.
  • 4M 이상(48 MB 이상, DRAM 구간)에서 MPS가 약 80~89 GB/s로 CPU 1 thread(약 70 GB/s)를 앞선다. 그런데 차이는 1.3배 정도다. elementwise는 memory-bound라서 GPU의 연산력이 쓸모없다. 같은 LPDDR을 공유하는 unified memory 시스템에서는 대역폭 천장이 같으므로 GPU가 elementwise로 크게 이길 수 없다.

4.4 (b) 행렬곱 처리량 vs 크기#

예제 10 — 무엇을 확인하나: 정사각 행렬곱 N×N @ N×N을 N = 32 ~ 4096으로 키우며 GFLOP/s를 잰다. CPU는 PyTorch가 Apple Accelerate로 보내는 기본 경로(기본 스레드 수), MPS는 fp32와 fp16.

그림 9 — 행렬곱 처리량 vs N(로그-로그, 실측 median). 교차점은 N ≈ 1024. 빨간 점선은 Apple이 M2 GPU에 대해 밝힌 약 3.6 TFLOPS.

출력에서 볼 것:

  • 작은 N에서 MPS가 13배 느리다(N=32: 4 vs 54 GFLOP/s). N=32 행렬곱 한 번은 2 × 32³ = 65,536 FLOP. 4.1 GFLOP/s면 한 번에 약 16 µs — 계산이 아니라 명령 발행 고정비다. N=128(4.2 MFLOP)도 약 18 µs로 거의 같다. 즉 N ≤ 128에서 MPS 시간은 크기와 무관한 바닥에 붙어 있다.
  • N ≥ 1024에서 MPS가 이긴다: 약 2.9 TFLOPS. 3.6 TFLOPS 대비 약 80 %다. (M2 GPU 10코어 × 코어당 128 FP32 ALU × 2 FLOP(FMA) × 약 1.4 GHz ≈ 3.6 TFLOPS라는 계산이 널리 인용되지만, ALU 수·클럭은 Apple이 공식 공개한 세부가 아니므로 추정으로 둔다.)
  • CPU가 1 TFLOPS 근처에서 평평하다. NEON만으로 P-core 4개가 이 숫자를 내기는 어렵다. Accelerate가 Apple CPU 클러스터의 비공개 행렬 가속기(흔히 "AMX"로 불린다)를 쓰는 것으로 널리 알려져 있고, 그 덕분으로 보인다(Apple 비공개, 확인 불가). 요점: 이 Mac에서 "CPU 대 GPU" 비교는 사실상 "CPU 옆 행렬 유닛 대 GPU"다. 실리콘 평가에서도 CPU라고 다 같은 CPU가 아니다 — SME/i8mm/행렬 확장 유무를 확인해야 한다(E2).
  • fp16이 fp32보다 겨우 5~10 % 빠르다. 이 GPU에서는 fp16 연산률이 fp32의 2배가 아닌 것으로 보인다. 데이터시트의 "fp16 TFLOPS"가 fp32의 2배라고 가정하지 말고 재야 한다.
  • 두 번째 실행에서 N=1024 MPS fp32가 1166 GFLOP/s로 나왔다(첫 실행 1817). 교차점 부근은 노이즈에 민감하다 — 그래서 median과 반복이 필요하다.

roofline(D3)으로 보면: GPU의 ridge point ≈ 3.6 TFLOP/s ÷ 100 GB/s ≈ 36 FLOP/B. N×N 행렬곱의 intensity ≈ 2N³ / (3 × 4N²) = N/6 FLOP/B이므로 N ≈ 216부터 이론상 compute-bound다. 그런데 실측은 N=1024까지 천장에 못 미친다. roofline이 모르는 세 번째 천장 — launch/동기화 고정비와 SM을 다 채우지 못하는 작은 grid — 가 작은 크기를 지배하기 때문이다. 작은 N에서는 thread block 수가 GPU의 코어 수보다 적어서 일부 코어는 아예 논다(5.1절).

4.5 (c) batch=1 작은 모델 — 작은 MLP#

예제 11 — 무엇을 확인하나: 키워드 스포팅(KWS)급 크기의 MLP(입력 490 = 49 프레임 × 10 MFCC, 은닉 256 × 2, 출력 12 클래스, 파라미터 약 19.5만)를 "입력은 CPU 메모리에서 오고 결과는 CPU가 쓴다"는 현실적인 조건으로 호출당 잰다.

출력에서 볼 것:

  • batch=1: CPU 30 µs vs MPS 508 µs — GPU가 17배 느리다. MAC은 약 19.5만 개(= 파라미터 수와 거의 같음)라서 CPU로 30 µs면 약 6.5 GMAC/s. GPU는 계산 전에 H2D 복사(4.8절), Linear·ReLU 5개 커널 발행, D2H 복사 + 동기화 왕복을 내야 한다. 4.2절의 왕복 150 µs가 여러 번 쌓인 모양이다.
  • batch를 키우면 GPU의 샘플당 비용이 빠르게 줄지만(508 → 0.89 µs), 이 MLP에서는 batch 4096에서도 CPU를 못 이겼다. 레이어가 작아서(256 폭) GEMM 하나하나가 GPU를 채우지 못하고, CPU 쪽 행렬 유닛이 이 크기에서 매우 효율적이기 때문이다.
  • 두 번째 실행도 같은 결론(batch 1: 30.3 vs 517.7 µs, batch 4096: 2848 vs 3057 µs).

Hark 같은 웨어러블의 always-on 오디오 모델이 정확히 이 크기대다. 이 측정 하나로 "왜 wake word를 GPU에서 돌리지 않나"에 대한 답의 절반(latency)이 나온다. 나머지 절반(전력)은 5절.

4.6 (c′) MobileNetV2 batch=1 — 해상도에 따른 교차점#

예제 12 — 무엇을 확인하나: MobileNetV2(weights=None, 무작위 가중치 — 속도에는 영향 없다)를 batch=1로, 입력 해상도 32 ~ 320 px에서 CPU 1 thread, CPU 4 threads, MPS로 잰다. MMAC 열은 논문의 224 px 약 300 MMAC를 해상도²로 비례시킨 근사다.

그림 10 — MobileNetV2 batch=1 latency vs 해상도(실측 median). MPS는 해상도와 무관하게 약 6~7 ms에 평평하다. CPU 1 thread는 MAC에 비례해 늘어나고 96~128 px 사이에서 MPS와 교차한다.

출력에서 볼 것:

  • MPS 곡선이 평평하다(6.1 ~ 7.3 ms). 계산량이 100배(6 → 612 MMAC) 늘어도 시간이 거의 그대로다. 즉 이 모델의 GPU 시간은 계산이 아니라 op 개수 × op당 고정비다. MobileNetV2는 eager 모드에서 conv·BN·ReLU6·add 등 op가 150개 안팎이다. 6.5 ms ÷ 150 ≈ 40 µs/op 정도의 고정비로 해석된다(op 수는 대략치, 확인하지 않음).
  • 320 px에서 MPS의 실효 처리량은 612 MMAC × 2 ÷ 6.63 ms ≈ 185 GFLOP/s — 약 3.6 TFLOPS peak의 5 %다. 5 %만 써도 CPU를 이긴다는 것이 GPU의 힘이자, 95 %를 놀린다는 것이 batch=1의 한계다.
  • CPU 1 thread가 작은 해상도에서 이긴다(32 px 3.5 ms vs 6.1 ms). 교차점은 96 ~ 128 px.
  • CPU 4 threads가 1 thread보다 훨씬 느리다(32 px에서 18.8 vs 3.5 ms). PyTorch profiler로 보면 이 CPU 경로에서 depthwise conv가 그룹별로 쪼개진 _slow_conv2d_forward 호출 1000여 개로 실행되었다. 작은 조각마다 스레드를 깨우고 동기화하는 비용이, 다른 작업이 돌고 있는 기계에서 크게 부풀었다. 스레드를 늘리면 빨라진다는 가정도 재 봐야 한다(D6의 교훈과 같다). 공정한 CPU 기준선은 이 경우 1 thread다.
  • PyTorch eager CPU는 모바일 런타임(XNNPACK, TFLite, ONNX Runtime)보다 depthwise에 느린 경로를 탄다. 그러므로 이 숫자는 "M2 CPU의 한계"가 아니라 "이 소프트웨어 스택에서의 교차점"이다. 실리콘 평가에서는 타깃 런타임으로 재야 한다(M2 벤치 방법론).

4.7 (c″) batch를 키우면 — 교차점과 포화#

예제 13 — 무엇을 확인하나: 저해상도(96 px, 웨어러블 카메라의 저전력 감지 모드 정도)에서 batch를 1 ~ 64로 키우며 CPU(1 thread)와 MPS의 latency·처리량을 잰다.

그림 11 — MobileNetV2 @96 px 처리량 vs batch(로그-로그, 실측). MPS는 batch 8까지 latency가 거의 그대로라 처리량이 batch에 비례해 늘고, 16 이후 포화된다. CPU는 batch 16에서 절벽을 만난다.

출력에서 볼 것:

  • batch 1: CPU 승(5.4 vs 6.2 ms). batch 2부터 MPS 승. 교차점이 batch 1~2다.
  • MPS는 batch 1 → 8에서 latency가 6.2 → 6.6 ms로 거의 안 변한다. 고정비 구간이라 batch를 8배 늘려도 공짜다. 처리량이 160 → 1209 img/s로 7.6배. batch 16 이후 latency가 batch에 비례하기 시작하면 GPU가 비로소 "일로 꽉 찬" 상태다(약 2,200 img/s에서 포화).
  • CPU batch 16에서 25.5 → 396 ms로 15배 절벽이 두 번의 실행 모두에서 재현되었다. PyTorch CPU conv가 크기에 따라 다른 구현 경로를 고르는 것으로 보이며, 원인은 확인하지 않았다. 교훈은 같다: 런타임의 구현 경로 전환이 하드웨어 차이보다 클 수 있다.

말로 하면: GPU는 batch가 있어야 고정비를 나눠 낸다. 서버는 여러 사용자의 요청을 모아 batch를 만들 수 있다. 웨어러블의 always-on 센서는 한 사용자의 한 스트림이다 — 모을 요청이 없다. 여러 프레임을 모으면 batch가 생기지만 그만큼 지연이 늘어난다(D6 9절 batching).

4.8 (d) 데이터 전송과 동기화 — unified memory인데도?#

예제 14 — 무엇을 확인하나: CPU 텐서를 MPS로(H2D), MPS 텐서를 CPU로(D2H) 복사하는 시간을 4 B ~ 256 MiB에서 잰다. 비교용으로 GPU 안에서의 복사(D2D)도 잰다. 모두 동기화 포함.

그림 12 — CPU↔MPS 복사 시간 vs 크기(로그-로그, 실측). 1 MiB까지는 약 160~210 µs 바닥에 붙어 있고, 그 이후 크기에 비례한다.

출력에서 볼 것:

  • 4 B든 64 KiB든 약 160 µs. 작은 복사의 비용은 전부 동기화 왕복이다(4.2절의 146 µs와 같은 자릿수).
  • 큰 복사는 약 30 GB/s — GPU 안의 복사(약 87 GB/s)보다 3배 느리다. unified memory인데도 복사가 느린 것은, PyTorch MPS가 CPU 텐서와 GPU 텐서를 별도의 버퍼로 관리하고 .to()마다 실제로 복사하기 때문이다(내부 경로의 세부는 확인하지 않았다). 물리 메모리는 같아도 소프트웨어 스택이 복사를 만든다.
  • 그래도 dGPU보다는 낫다: PCIe 너머 dGPU에서는 전송 대역폭이 PCIe 링크로 제한되고, 작은 전송의 왕복 지연도 붙는다. Apple silicon, Qualcomm, Arm 모바일 SoC 같은 unified memory 시스템에서는 드라이버가 zero-copy(CPU와 GPU가 같은 버퍼를 매핑)를 지원하는 경우가 많다. 런타임이 그것을 쓰도록 버퍼를 할당하면(예: 카메라 버퍼를 GPU가 바로 읽는 경로) 복사는 사라진다. 하지만 동기화(누가 언제 다 썼나)는 사라지지 않는다. 캐시 일관성(cache coherence)과 fence 비용은 E7에서 다룬다.

Don의 경험과 연결: DMA 전송 비용 = "설정 + 완료 인터럽트 왕복" 고정비 + 바이트 ÷ 대역폭. 작은 전송은 고정비가 지배해서 CPU memcpy가 이기고, 큰 전송만 DMA가 이긴다. GPU offload도 정확히 같은 곡선이다.

5. 왜 GPU는 batch=1 always-on 추론에 불리한가#

4절의 측정과 이론을 한 곳에 모은다.

5.1 네 가지 이유#

  1. Launch·동기화 고정비. 스트리밍 추론은 프레임마다 "넣고 → 기다리고 → 결과를 CPU가 읽는다". 매 프레임 동기화 왕복(이 Mac에서 약 150 µs)과 op당 발행 비용이 붙는다. 모델이 작을수록 이 고정비가 전체를 지배한다(4.5절: 계산 수 µs, 총 508 µs).
  2. 낮은 활용률. GPU는 수천 개 thread가 떠 있어야 지연을 숨긴다(1.4절). KWS 모델의 레이어 하나는 출력이 수십~수백 원소라 block 몇 개로 끝나고, SM 대부분이 논다. 4.6절에서 큰 입력조차 peak의 5 %였다.
  3. 전력. GPU는 큰 레지스터 파일, 스케줄러, 캐시, 넓은 버스를 켜야 일을 시작한다. 활용률이 낮으면 켜 둔 비용(정적 전력 + 클럭 트리) ÷ 적은 일 = 연산당 에너지가 나쁘다. D7의 "race-to-idle" 관점에서 GPU가 빨리 끝내고 꺼지면 좋겠지만, 10 ms마다 깨우는 스트리밍에서는 꺼질 틈이 짧다.
  4. Idle 전력과 wake 지연. 모바일 GPU는 쓰지 않을 때 power gating으로 레일을 끈다. 다시 켜려면 전원 레일 안정화, 클럭 켜기, 드라이버·펌웨어 상태 복구가 필요하고, 이 지연과 에너지는 SoC마다 다르며 공개되지 않는 경우가 많다(벤더에게 물어야 할 항목). always-on 워크로드를 GPU에 두면 "계속 켜 두기"와 "매번 깨우기" 사이에서 둘 다 비싸다.

5.2 손계산 — always-on KWS를 어디에 둘까 (가정 숫자)#

아래 숫자는 설명용 가정이다. 실제 값은 SoC별로 측정해야 한다(D7 8절, K3).

말로 하면: 가정이 다소 틀려도 자릿수가 두세 개 차이 난다. 게다가 GPU를 쓰려면 AP(애플리케이션 프로세서)와 DRAM도 깨어 있어야 하므로 실제 시스템 전력 차이는 더 크다. 웨어러블 배터리가 수백 mWh라면 72 mW 상시 부하는 몇 시간 만에 배터리를 비운다(D7 6절의 배터리 수학). 그래서 always-on은 MCU/DSP/소형 NPU의 몫이다(E4, E5, E8).

6.2 Jetson Orin — 로보틱스 edge의 기준점#

Jetson Orin 계열은 "edge에서 CUDA를 그대로 쓸 수 있는" 레퍼런스다. 널리 공개된 사실만 적는다(모델별 수치는 NVIDIA 데이터시트로 확인).

  • GPU: NVIDIA Ampere 아키텍처 — CUDA core + tensor core. 상위 AGX Orin 64GB는 CUDA core 2048개, tensor core 64개.
  • DLA(Deep Learning Accelerator): 고정 기능 CNN 가속기. AGX Orin·Orin NX에 들어 있고 Orin Nano에는 없다. TensorRT로 레이어를 GPU와 DLA에 나눠 배치한다 — 한 칩 안에서 GPU와 NPU를 같이 쓰는 구조의 교과서적 예다.
  • 메모리: CPU·GPU·DLA가 LPDDR5를 공유(unified). AGX Orin 64GB는 204.8 GB/s.
  • 성능·전력: AGX Orin 최대 275 TOPS(INT8, sparsity 포함 조건), 전력 모드 15~60 W. Orin Nano는 7~15 W급(이후 소프트웨어 업데이트로 더 높은 전력 모드가 추가됨).
  • 소프트웨어: JetPack(Linux + CUDA + cuDNN + TensorRT). 서버에서 쓰던 CUDA 코드·PyTorch가 그대로 돈다는 것이 가장 큰 장점이다.

웨어러블에서 보면 Orin은 전력이 두세 자릿수 크다(W 단위). Hark 같은 기기의 on-body 부분에는 맞지 않지만, 로봇·드론·스마트 카메라, 또는 웨어러블과 짝을 이루는 edge 허브·개발용 기준점으로는 자주 등장한다.

6.3 모바일 GPU를 ML에 쓸 때 현실적인 제약#

  • 정밀도: 모바일 GPU ML 경로는 fp16이 기본이다. INT8 가속은 세대·드라이버에 따라 다르고, INT4 가중치는 보통 fp16으로 풀어서(dequant) 곱한다. NPU의 INT8/INT4 네이티브 경로보다 에너지 효율이 떨어지는 이유 중 하나다.
  • 드라이버 품질·파편화: 같은 OpenCL 커널이 기기·드라이버 버전에 따라 성능·정확도가 달라진다. Don에게 익숙한 "벤더 BSP 버전마다 다른 버그"의 GPU판이다.
  • 열·지속 성능: 휴대폰 GPU는 게임에서도 수 분 뒤 throttling된다(K4, E9). 짧은 burst(prefill 1초)는 괜찮아도 지속 부하는 벤치마크 숫자보다 느리다.
  • 자원 공유: UI 렌더링과 GPU를 나눠 쓴다. ML이 GPU를 오래 점유하면 화면이 끊긴다. 웨어러블의 디스플레이가 작아도 compositor는 GPU를 쓴다.

10. 면접에서 이렇게 말한다#

Q. "What is a warp, and what is divergence?"

A. warp는 GPU가 한 명령으로 동시에 실행하는 thread 묶음이다 — NVIDIA는 32개. 같은 warp의 thread들이 분기에서 다른 쪽으로 가면 하드웨어가 두 경로를 순서대로 실행하면서 해당하지 않는 lane을 mask로 끈다. 그래서 비용은 두 경로의 합이다. warp 경계에 맞춰 갈리면 손해가 없고, 드문 예외 분기는 싸다. ML에서는 GEMM·conv는 분기가 없어 괜찮고 NMS·top-k 같은 데이터 의존 연산이 문제다.

A warp is the group of threads the GPU issues together with a single instruction — 32 on NVIDIA, and other vendors have similar concepts like AMD wavefronts or Apple SIMD-groups. If threads in the same warp take different sides of a branch, the hardware runs both paths one after the other and masks off the inactive lanes, so you pay for the sum of both paths. Divergence only matters within a warp; if the branch splits along warp boundaries, there's no penalty. For ML, GEMMs and convolutions are branch-free, so divergence mostly shows up in data-dependent ops like NMS, top-k or beam search.

Q. "Why is a GPU slow for batch-1 tiny models?"

A. GPU는 수천 개 thread로 지연을 숨기는 throughput 기계라서, 작은 모델은 GPU를 채우지 못하고 고정비만 낸다. 내가 M2에서 재 보니 결과를 기다리는 동기화 왕복만 약 150 µs였고, 20만 MAC짜리 MLP는 CPU 30 µs, GPU 500 µs였다. 거기에 GPU를 켜 두는 전력까지 생각하면 always-on 경로는 MCU나 DSP, 소형 NPU가 맞다. GPU는 batch가 있거나 입력이 클 때 이긴다 — MobileNetV2는 96~128 px에서 교차했다.

Because a GPU is a throughput machine — it hides latency by having thousands of threads in flight — and a batch-one tiny model can't fill it, so you mostly pay fixed costs. On an M2 I measured about 150 microseconds just for the submit-and-wait round trip, and a 200-thousand-MAC MLP took 30 microseconds on the CPU versus about 500 on the GPU. Add the power of keeping the GPU awake and it's clearly the wrong place for an always-on model; that belongs on an MCU, DSP or small NPU. The GPU wins once there's batch or the input is large — for MobileNetV2 the crossover was around 96 to 128 pixels at batch one.

Q. "What is occupancy, and is higher always better?"

A. occupancy는 SM에 상주하는 warp 수를 최대치로 나눈 값이다. 레지스터, shared memory, warp·block 슬롯 중 가장 먼저 바닥나는 자원이 정한다 — 예를 들어 256 thread block에서 thread당 레지스터를 64개 쓰면 50 %다. 상주 warp가 많을수록 메모리 지연을 숨길 여유가 크지만, 항상 좋은 것은 아니다. 잘 만든 GEMM은 레지스터 타일링으로 재사용을 늘리려고 일부러 occupancy를 낮춘다. 판단은 실측 처리량과 roofline으로 한다.

Occupancy is the number of warps resident on an SM divided by the maximum it supports. It's set by whichever resource runs out first — registers per thread, shared memory per block, or the warp and block slots. For example, 256-thread blocks using 64 registers per thread give 50 percent on an SM with 64K registers. More resident warps means more ability to hide memory latency, but it's not a goal in itself; good GEMM kernels deliberately use lots of registers for register tiling and accept lower occupancy. I judge by achieved throughput against the roofline, not by occupancy.

Q. "What does coalesced memory access mean?"

A. warp의 32 lane이 동시에 load할 때 주소들이 연속된 한 덩어리면 하드웨어가 소수의 transaction(32 B sector 4개 = 128 B)으로 합친다. 주소가 흩어지면 lane마다 sector 하나씩, 8배의 트래픽이 된다. CPU에서 좋은 "thread 하나가 행 하나를 훑는" 코드가 GPU에서는 열 방향 stride라 나쁘다. 인접 thread가 인접 주소를 읽게 인덱싱하거나 shared memory를 거쳐 전치한다. 이 Mac에서 같은 64 MiB 복사가 연속이면 80 GB/s, stride면 20 GB/s였다.

It means the addresses the 32 lanes of a warp access at the same time fall into one contiguous, aligned chunk, so the hardware merges them into a few transactions — four 32-byte sectors for 32 floats. If each lane hits a different sector, you move eight times more data than you use. The classic trap is CPU-style code where each thread walks its own row; at any instant the warp is reading a column, which is strided. The fix is to index so adjacent threads touch adjacent addresses, or stage through shared memory. It's the same idea as aligning DMA bursts on a bus. On my M2 the same copy ran at 80 GB/s contiguous and 20 GB/s strided.

Q. "When would you run an SLM on the phone GPU versus the NPU?"

A. 기본은 NPU다 — INT8/INT4 네이티브 경로가 있고 같은 일에 전력 효율이 좋다. GPU를 고르는 경우는 NPU 컴파일러가 모델 구조나 동적 shape, 긴 context를 지원하지 못할 때, fp16 정확도가 필요할 때, 오픈 스택(llama.cpp Vulkan/OpenCL, MLC)으로 빨리 돌려야 할 때, NPU가 다른 기능에 점유되어 있을 때다. 그리고 decode는 memory-bound라서 GPU로 옮겨도 대역폭 천장은 같다 — 차이는 prefill(TTFT)과 전력·발열에서 난다. 결국 대표 프롬프트로 TTFT, tokens/s, 줄당 에너지, 지속 성능을 둘 다 재서 정한다.

I'd start with the NPU: it has native INT8 or INT4 paths and better energy per token for the same work. I'd pick the GPU when the NPU toolchain can't handle the model — a new attention variant, dynamic shapes, long context — when I need fp16 accuracy, when I need to move fast with open stacks like llama.cpp's Vulkan or OpenCL backends, or when the NPU is busy with camera or audio. Also, decode is memory-bound, so moving it to the GPU doesn't raise the bandwidth ceiling; the differences show up in prefill time and in power and thermals. In the end I'd measure time-to-first-token, tokens per second, energy per response and sustained performance on both with representative prompts.

Q. "How is a GPU's execution model different from a CPU's?"

A. CPU는 latency machine이다 — 큰 캐시, 분기 예측, out-of-order로 thread 하나를 빨리 끝낸다. GPU는 throughput machine이다 — 레지스터 파일을 크게 두고 warp 수십 개를 상주시킨 다음, 하나가 메모리를 기다리면 비용 없이 다른 warp를 실행한다. SSD 펌웨어에서 queue depth를 높여 NAND 지연을 숨기던 것과 같은 원리다. 그래서 GPU는 일이 많고 규칙적일 때 강하고, 작고 순차적인 일에는 약하다.

A CPU is a latency machine: big caches, branch prediction and out-of-order execution to finish one thread fast. A GPU is a throughput machine: it keeps dozens of warps resident with their registers in a huge register file, and when one warp stalls on memory it issues from another at zero switch cost. It's the same principle as keeping a high queue depth to hide NAND latency in SSD firmware. So GPUs shine on large, regular, parallel work and struggle with small or sequential work.

11. 직접 해보기#

  1. SM에 레지스터 65,536개, 최대 64 warp가 있다. block 128 thread, thread당 레지스터 96개면 occupancy는? 정답: block 레지스터 128 × 96 = 12,288 → 65,536 / 12,288 = 5 block → 5 × 4 = 20 warp → 31.25 %.
  2. warp 32 lane이 double(8 B)을 a[tid]로 읽는다. 32 B sector 몇 개? a[tid × 2]라면? 정답: 256 B 연속 → 8 sector. stride 2면 512 B 범위에 흩어져 16 sector(효율 50 %).
  3. 1.4절 식으로, 메모리 지연 600 사이클이고 warp가 load 사이에 30 사이클 계산한다. 지연을 숨기려면 warp 몇 개가 필요한가? 정답: 1 + 600/30 = 21개.
  4. tiled GEMM에서 M = N = K = 1024, T = 32일 때 naive와 tiled의 global 읽기(원소 수)는? 정답: naive 2 × 1024³ ≈ 2.15e9, tiled = 2 × 1024² × (1024/32) ≈ 6.7e7 → 정확히 32배 감소.
  5. 코드 과제: 예제 11의 MLP 은닉 폭을 256 → 1024, 2048로 키워서 batch=1과 batch=64에서 CPU vs MPS를 다시 재라. 교차점이 어디로 움직이나? 힌트: 레이어가 커질수록 GPU의 고정비 비중이 줄어 교차 batch가 작아질 것으로 예상된다 — 예상과 실측을 비교하라.
  6. 코드 과제: 예제 12에서 입력을 미리 MPS에 올려 두고(x.to("mps")를 루프 밖으로) .cpu() 대신 torch.mps.synchronize()만 하도록 바꿔 재라. 6 ms 바닥 중 복사·읽기 비중은 얼마인가? 힌트: 4.8절의 H2D·D2H가 각각 약 160 µs이므로 0.3 ms 안팎이 빠질 것으로 예상된다.

13. 요약 & 체크리스트#

GPU는 작은 ALU lane을 SM으로 묶고, thread를 warp로 묶어 한 명령으로 실행하며(SIMT), 메모리 지연을 캐시가 아니라 상주 warp 수로 숨기는 throughput machine이다. 분기가 warp 안에서 갈리면 두 경로를 모두 지나고(divergence), 상주 warp 수는 레지스터·shared memory가 정하며(occupancy), 메모리 효율은 warp 주소가 한 덩어리인지(coalescing)가 정한다. tiled GEMM은 shared memory로 재사용을 만들어 global 트래픽을 1/T로 줄인다. 이 Mac에서 재 보면 GPU는 동기화 왕복 약 150 µs, 작은 op 발행 수 µs의 고정비를 가져서, KWS급 MLP는 CPU보다 17배 느렸고 MobileNetV2는 해상도 96~128 px, batch 1~2에서 교차했다. 큰 행렬곱에서는 약 2.9 TFLOPS로 CPU의 3배였다. 그래서 always-on batch=1 워크로드는 MCU·DSP·소형 NPU에, GPU는 고해상도 비전·batch·prefill·범용성이 필요한 burst 작업에 둔다. LLM decode는 대역폭이 천장이라 GPU로 옮겨도 빨라지지 않는다.
