0. 큰 그림 — 이게 왜 필요한가#

Hark 같은 웨어러블(추정)의 always-on 도메인에는 작은 MCU가 하나 산다. study_prep_list의 기기 그림에는 그 자리에 "Cortex-M / RISC-V"라고 적혀 있다. 지금 그 자리의 주류는 Arm Cortex-M이지만, 점점 더 많은 MCU·센서 허브·NPU 내부 제어 코어가 RISC-V로 채워지고 있다. 예를 들어 Espressif의 최근 MCU 라인(ESP32-C 시리즈, P4)은 RISC-V 코어를 쓰고, 많은 NPU·가속기 IP가 내부 시퀀서나 제어 코어로 RISC-V를 넣는다.

edge ML 엔지니어가 RISC-V를 만나는 장면은 크게 세 가지다.

  1. always-on MCU가 RISC-V인 경우 — VAD, 착용 감지, IMU 제스처 같은 작은 모델을 TFLite Micro로 돌린다. 스칼라 코어면 int8 커널이 느리고, 벡터(RVV)나 벤더 확장이 있으면 커널을 그 명령에 맞춰야 한다.
  2. 가속기 안에 RISC-V가 숨어 있는 경우 — NPU 벤더 SDK를 bring-up하다 보면 "펌웨어는 내부 RISC-V 코어에서 돈다"는 문서를 만난다. 디버그·로그·부트 순서를 이해해야 한다.
  3. 실리콘 선정 회의 — "이번 세대 MCU를 Cortex-M55로 갈까, RISC-V + 벡터로 갈까"라는 질문에 라이선스·생태계·툴체인·벡터 모델을 근거로 답해야 한다.

그림 1 — RISC-V는 "칩"이 아니라 "명령어 계약서"다. 계약서(ISA)는 하나, 그걸 지키는 회로(코어)는 여러 회사가 각자 만든다. 이 한 문장이 RISC-V의 장점(자유, 커스텀)과 단점(파편화, 코어마다 다른 성능)을 모두 설명한다.

Don에게 가장 가까운 비유는 SSD다. NVMe 스펙은 공개되어 있고, 컨트롤러는 회사마다 다르다. 호스트 드라이버는 스펙만 믿고 짜지만, 성능 튜닝은 컨트롤러마다 다시 해야 한다. RISC-V도 똑같다. 그리고 Don이 써 본 Xtensa는 "코어를 고객이 설정하고 TIE로 명령을 추가하는" ISA였는데, RISC-V의 확장·커스텀 명령 철학과 매우 닮았다. 차이는 Xtensa는 Cadence 한 회사의 것이고 RISC-V는 공개 표준이라는 점이다.

이 노트의 순서: ISA vs 마이크로아키텍처와 오픈 ISA(1절) → base ISA와 표준 확장, 이름 읽기(2절) → 명령 형식과 인코더/디코더(3절) → 특권 모드·CSR·인터럽트(4절) → RVV 벡터 확장과 strip-mining(5절) → 커스텀 명령(6절) → 엣지 AI 칩 지형(7절) → 툴체인·소프트웨어(8절) → ARM vs RISC-V 비교(9절) → 펌웨어 엔지니어 관점(10절) → 실수·면접·연습.

1. ISA vs 마이크로아키텍처, 그리고 "오픈" ISA#

1.1 직관 — 계약서와 공장#

ISA(Instruction Set Architecture)는 소프트웨어와 하드웨어 사이의 계약서다. "0x00500093이라는 32비트를 만나면 x1 레지스터에 0+5를 써라" 같은 약속의 모음이다. 레지스터가 몇 개인지, 메모리를 어떻게 읽는지, 예외가 나면 PC가 어디로 가는지도 ISA가 정한다.

마이크로아키텍처(microarchitecture)는 그 계약을 지키는 실제 회로 설계다. 파이프라인이 3단인지 12단인지, 분기 예측기가 있는지, out-of-order로 도는지, 캐시가 몇 KB인지 — 이건 계약서에 없다. 같은 바이너리가 돌아가기만 하면 된다.

Don이 아는 ARM으로 말하면: Armv7-M / Armv8-M이 ISA(아키텍처)이고, Cortex-M4, Cortex-M33, Cortex-M55가 마이크로아키텍처(코어 구현)다. Cortex-M33과 M55는 둘 다 Armv8-M을 구현하지만 M55만 Helium(MVE)을 가진다.

1.3 오픈·royalty-free라는 것의 의미#

RISC-V는 2010년 무렵 UC Berkeley(Don의 모교)의 Par Lab에서 연구·교육용 ISA로 시작됐다 (Krste Asanović, David Patterson 등). 지금은 비영리 단체 RISC-V International(스위스 소재)이 스펙을 관리한다.

  • ISA 스펙은 무료 공개다. RISC-V 호환 코어를 만들어 팔아도 ISA 사용료(로열티)를 누구에게도 내지 않는다.
  • 그렇다고 코어가 무료라는 뜻은 아니다. SiFive·Andes 같은 회사는 자기가 설계한 코어 IP를 유료로 라이선스한다. 오픈소스 코어(PULP 계열, lowRISC Ibex 등)도 있지만, 검증·품질 책임은 가져다 쓰는 쪽에 있다.
  • 비교: Arm은 ISA와 코어 설계를 함께 라이선스한다. Cortex-M을 쓰면 코어 라이선스 + 칩당 로열티 구조가 일반적이다 (구체 조건은 계약마다 다르다).

말로 하면: RISC-V의 "오픈"은 계약서가 공짜라는 뜻이지, 공장(코어)까지 공짜라는 뜻이 아니다.

1.4 ratified vs draft — 스펙 상태를 항상 확인하라#

RISC-V 확장은 제안 → draft → freeze → ratified(비준) 단계를 거친다. 비준된 확장은 인코딩이 고정되어 툴체인이 믿고 지원한다. draft 확장은 인코딩이 바뀔 수 있다.

실제로 사고가 난 예가 있다. 벡터 확장은 draft 0.7.1 시절에 일부 상용 코어(T-Head의 C906/C910 계열로 알려져 있다)가 먼저 구현했는데, 나중에 비준된 RVV 1.0과 인코딩·의미가 호환되지 않는다. 그래서 "RVV 지원"이라고 적힌 보드를 사도 upstream GCC/LLVM의 RVV 1.0 코드가 안 돈다. 데이터시트에서 버전 번호를 확인하는 습관이 필요하다.

1.5 Don 경험과 연결#

SSD 펌웨어 시절 NVMe 스펙의 "optional feature"를 컨트롤러가 지원하는지 Identify로 확인하고 코드 경로를 나눴을 것이다. RISC-V도 같다. 코어가 어떤 확장을 갖는지는 misa CSR(일부 비트), 디바이스 트리의 riscv,isa 문자열, 또는 벤더 데이터시트로 확인하고, 빌드 시에는 -march로 고정한다.

1.6 함정#

  • "RISC-V는 오픈이니까 칩이 싸다" — ISA 로열티가 없을 뿐, 코어 IP·검증·툴체인·인력 비용은 그대로다.
  • "RISC-V 코어 = 느리다/빠르다" — ISA에는 속도가 없다. 같은 RV32IMC라도 2단 파이프라인 초저전력 코어부터 GHz급 코어까지 있다.
  • draft 확장(P, 0.7.1 벡터)을 비준된 것처럼 믿고 코드를 쌓는 것.

2. Base ISA와 표준 확장 — 이름을 읽는 법#

2.1 Base ISA#

RISC-V는 아주 작은 정수 base 하나 위에 확장을 쌓는다. base만으로도 C 컴파일러가 모든 프로그램을 만들 수 있을 만큼은 된다(곱셈은 소프트웨어 루틴으로).

baseXLEN정수 레지스터쓰임
RV32I32x0–x31 (32개)MCU, 가속기 제어 코어
RV32E32x0–x15 (16개)극소형 코어 (면적 절약)
RV64I64x0–x31 (32개)Linux급 앱 프로세서

RV32I의 정수 명령은 40개 남짓이다. 교과서 한 장에 전부 들어가는 크기다.

Don이 ARM에서 오면 놀랄 점 네 가지:

  1. x0는 항상 0이다. 써도 버려진다. 그래서 mv a0, a1은 사실 addi a0, a1, 0이고, nop은 addi x0, x0, 0(0x00000013)이다.
  2. 조건 플래그(NZCV)가 없다. beq x1, x2, label처럼 분기 명령이 두 레지스터를 직접 비교한다. cmp + bne 두 개가 한 개가 된다. 오버플로 검사는 명시적으로 sltu 등으로 한다.
  3. load/store 주소 모드가 하나: base + 12비트 부호 있는 즉값. ARM의 post-increment, 레지스터 offset shift 같은 모드가 없다 (벡터나 벤더 확장에는 있을 수 있다).
  4. push/pop multiple이 없다(기본 ISA 기준). 함수 prologue가 sw를 여러 개 나열한다. 그래서 C(압축) 확장과 코드 크기 최적화가 중요하다.

2.3 이름 문자열 풀어 읽기 — 손계산#

RV32IMAC → XLEN 32, I(base) + M + A + C. ESP32-C6 같은 MCU 코어가 이런 이름이다.

RV64GCV → XLEN 64, G(=I, M, A, F, D, Zicsr, Zifencei) + C + V.

rv32imac_zicsr_zifencei → 소문자·밑줄 형식. GCC/LLVM의 -march에 넣는 형식이 이것이다. 한 글자 확장은 정해진 순서(IMAFDQC…)로 이어 쓰고, Z 확장은 _로 구분한다.

말로 하면: 이름은 "XLEN + base + 확장 목록"이고, G는 7개 항목의 약칭일 뿐이다. RV32IMAC에는 F가 없다 — float 연산은 소프트웨어 에뮬레이션이라는 뜻이고, MCU 선정표에서 "F 없음"은 float 전처리(MFCC 등)가 수십 배 느려질 수 있다는 신호다.

2.4 Profile — "이 조합이면 리눅스 배포판이 돈다"#

확장이 많아지면 소프트웨어 배포가 어려워진다. 그래서 RISC-V International은 profile을 정한다. 앱 프로세서용 RVA20 → RVA22 → RVA23으로 이어지는 계열이 대표적이고, RVA23은 2024년에 비준되었고 V(벡터)를 필수로 포함한 것으로 알려져 있다. 즉 "RVA23 호환 앱 프로세서"면 RVV 1.0 코드가 돈다고 기대할 수 있다.

MCU 쪽은 profile보다 벤더별 조합(rv32imc, rv32imac_zba_zbb, rv32imc_zve32x 등)이 현실이다. 그래서 MCU 펌웨어는 "이 칩의 정확한 -march"를 BSP에서 가져오는 것이 첫 작업이다.

2.5 함정#

  • GCC 12 무렵부터 기본 ISA 스펙 버전이 바뀌면서 csrr, fence.i가 I에서 분리되었다. 예전 프로젝트를 새 툴체인으로 빌드하면 "unrecognized opcode csrr"가 뜬다. -march=rv32imac_zicsr_zifencei처럼 명시하면 해결된다.
  • -march에 칩에 없는 확장(예: c가 없는 코어에 c)을 넣으면 컴파일·링크는 되고 실행 시 illegal instruction trap이 난다. mcause=2로 보인다(4절).
  • F가 있는 코어라도 부트 코드가 mstatus.FS를 켜지 않으면 첫 float 명령에서 illegal instruction이 난다(10절). Cortex-M4F에서 CPACR로 FPU를 켜는 것과 같은 이야기다.

3. 명령 형식과 인코딩 — 32비트를 손으로 읽기#

3.1 여섯 가지 형식#

RISC-V의 32비트 명령은 형식이 6개뿐이다. 모든 명령의 하위 7비트가 opcode이고, 레지스터 필드(rs1, rs2, rd)는 어느 형식에서든 같은 비트 위치에 있다.

그림 2 — RV32I 명령 형식. 파랑은 소스 레지스터, 초록은 목적 레지스터, 주황은 즉값 조각이다. S/B형은 즉값이 두 조각으로 갈라지고, B/J형은 비트 순서까지 뒤섞여 있다. 이상해 보이지만 하드웨어를 위한 설계다: rs1·rs2·rd 위치가 고정이라 디코더가 형식을 판별하기 전에 레지스터 파일을 읽기 시작할 수 있고, 즉값의 부호 비트가 항상 bit 31이라 부호 확장도 바로 시작할 수 있다.

3.2 손계산 — addi x1, x0, 5#

I형이다. 필드를 왼쪽(bit 31)부터 채운다.

이어 붙이면 0000 0000 0101 0000 0000 0000 1001 0011 = 0x00500093. 말로 하면: "즉값 5, 소스 x0, 연산 종류 ADDI, 목적 x1, 분류 OP-IMM"을 정해진 칸에 넣은 것뿐이다.

음수 즉값은 12비트 2의 보수로 들어간다. addi sp, sp, -16은 imm = 0xFF0, rs1 = rd = 2 → 0xFF010113. 거의 모든 RISC-V 함수의 첫 명령이라 디스어셈블리에서 매일 보게 되는 숫자다.

B형 beq x1, x2, +8: 분기 offset은 항상 2의 배수라서 imm[0]을 저장하지 않는다. 8 = 0b0_0000_0000_1000 → imm[12]=0, imm[10:5]=000000, imm[4:1]=0100, imm[11]=0. rd 자리(bit 11:7)에 imm[4:1] 다음에 imm[11]이 오므로 01000 → 0x00208463.

3.3 코드로 확인 — 인코더#

스펙의 비트 배치를 그대로 옮긴 인코더가, 손으로 계산한(그리고 디스어셈블리에서 흔히 보는) 기계어와 일치하는지 확인한다.

출력에서 볼 것: 10개가 모두 OK. mul은 add와 opcode·funct3가 같고 funct7=0000001만 다르다 — M 확장이 R형의 빈 funct7 공간에 들어간 것이다.

3.4 코드로 확인 — 디코더#

반대 방향이다. 32비트 워드에서 필드를 뽑아 부호 확장하고 어셈블리로 되돌린다. B/J형의 뒤섞인 즉값을 재조립하는 부분이 핵심이다.

출력에서 볼 것: 0xFE209EE3이 bne x1, x2, pc-4(뒤로 가는 루프 분기)로 풀리는 것 — 음수 offset의 부호가 bit 31에서 온다. 마지막 0x4501은 하위 2비트가 11이 아니므로 16비트 압축 명령이다(실제로는 c.li a0, 0). 디코더는 하위 2비트만 보고 명령 길이를 안다.

3.5 C 확장(16비트)과 opcode 공간#

  • 하위 2비트가 00, 01, 10이면 16비트 명령, 11이면 32비트 명령이다. 그래서 C 확장이 있으면 16/32비트 명령이 섞여 흐르고, 명령 정렬은 2바이트가 된다.
  • ARM의 Thumb-2와 같은 발상이다. 다만 Thumb은 모드가 있고, RISC-V C는 모드 없이 항상 섞인다.
  • 32비트 opcode 공간 중 custom-0(0001011), custom-1(0101011) 등은 표준이 절대 쓰지 않겠다고 약속한 벤더 전용 칸이다. 6절의 커스텀 명령이 여기에 들어간다. 벡터 명령은 OP-V(1010111)를 쓴다.

3.6 Don 경험과 연결#

펌웨어 크래시 덤프에서 mepc가 가리키는 워드를 직접 디코드해야 하는 순간이 온다 (예: "illegal instruction인데 그 워드가 뭐지?"). Xtensa에서 FLIX 번들을 디코드하던 것에 비하면 RISC-V는 규칙이 단순하다. 위 디코더를 50줄쯤 확장하면 로그 파서에 붙일 수 있다.

3.7 함정#

  • B/J형 즉값은 2바이트 단위다. offset을 4로 나누는 ARM(Thumb 제외) 습관으로 계산하면 두 배 틀린다.
  • lui는 상위 20비트를 채우고, 하위 12비트는 다음 addi가 부호 있는 값으로 더한다. 그래서 0x12345800 같은 상수는 lui에 0x12346을 넣고 addi에 -0x800을 넣는다(어셈블러의 %hi/%lo가 처리). 손으로 패치할 때 자주 틀린다.
  • x0에 쓰는 명령은 버려진다. 디스어셈블리의 jal x0, …는 그냥 j(점프, 링크 안 함)다.

인터럽트나 예외가 나면 하드웨어가 하는 일은 딱 이만큼이다.

5. RVV 1.0 벡터 확장 — 길이를 모르는 벡터#

5.1 직관 — "몇 개씩 할래?"를 하드웨어가 대답한다#

NEON이나 Helium은 폭이 고정된 SIMD다. 레지스터가 128비트로 정해져 있으니 int8이면 16개씩 처리하고, 남은 꼬리는 따로 처리한다(NEON은 스칼라 루프, Helium은 tail predication — E2 참고).

RVV는 1970년대 Cray 벡터 머신 전통을 잇는 vector-length agnostic(VLA) 모델이다. 프로그램이 "나 n개 남았어"라고 말하면, 하드웨어가 "이번엔 vl개 해 줄게"라고 답한다. 같은 바이너리가 벡터 레지스터 128비트 칩에서도, 1024비트 칩에서도 수정 없이 돈다. ARM의 SVE/SVE2가 같은 철학이고(predicate + whilelt), NEON·Helium은 고정 폭이다.

펌웨어 비유: DMA 엔진에 "남은 바이트 수"를 주면, 엔진이 "이번 burst는 최대 N바이트"로 잘라 처리하고 실제 전송량을 돌려주는 구조다. 드라이버는 burst 크기를 몰라도 된다.

그림 5 — n=100을 여러 설정으로 strip-mining한 결과(위 코드의 실제 출력). 주황 칸이 VLMAX보다 짧은 반복이다. NEON 스타일 코드에서는 이 부분이 별도의 스칼라 tail 루프(또는 padding)였다. RVV에서는 같은 루프 본체가 그대로 처리한다.

5.6 마스크와 tail/mask 정책#

  • 마스크: 비교 명령(vmslt.vx 등)이 v0에 lane별 1비트를 쓴다. 마스크가 붙은 명령(, v0.t)은 v0 비트가 1인 lane만 계산한다. if (x[i] < 0)를 분기 없이 처리하는 방법이다.
  • tail: vl 이후의 원소(i ≥ vl). tail undisturbed(tu)면 이전 값을 유지, tail agnostic(ta)면 하드웨어가 이전 값을 유지하거나 전부 1로 채울 수 있다(어느 쪽인지 소프트웨어가 기대하면 안 된다).
  • mask 정책: 꺼진 lane에 대해 같은 규칙(mu / ma).

ta/ma를 쓰는 이유: 하드웨어가 이전 값을 읽어 합칠 필요가 없어 빨라질 수 있다. 결과를 tail까지 쓸 일이 없다면 기본적으로 ta, ma를 쓴다.

아래는 VLEN=128, e8(16 lane) 레지스터 하나를 흉내 내어 vl=10일 때 tu/ta, 그리고 마스크의 효과를 보여 준다. ta의 "전부 1"(int8로 -1)은 스펙이 허용하는 여러 선택 중 하나를 골라 보인 것이다.

출력에서 볼 것: tu는 lane 10–15에 이전 값 7이 남고, ta 예시는 -1(all-1s)로 덮였다. 마스크 버전은 음수 lane(0–4)만 +100이 되고 나머지는 이전 값 7을 유지한다(mu). 마지막 줄은 마스크 + vmerge로 ReLU를 분기 없이 만드는 모양이다(실제 RVV에서는 vmax.vx v, v, zero 한 명령으로도 된다).

5.7 Widening과 reduction — int8 내적#

C1에서 본 것처럼 int8 커널의 기본은 int8 × int8 → int32 누산이다. RVV에는 이를 위한 두 종류의 명령이 있다.

명령의미폭 변화
vwmul.vv vd, vs2, vs1lane별 부호 있는 곱SEW → 2·SEW (목적지 LMUL 두 배)
vwmacc.vv vd, vs1, vs2vd += vs1 × vs2 (lane별)SEW → 2·SEW 누산
vredsum.vs vd, vs2, vs1vd[0] = vs1[0] + Σ vs2[i]같은 폭
vwredsum.vs vd, vs2, vs1vd[0] = vs1[0] + Σ vs2[i] (넓혀서)SEW → 2·SEW

int8 곱은 최대 (-128)×(-128) = 16384라 int16에 들어가지만, int16에 두 번만 더해도 32768로 넘친다. 그래서 int8 입력을 vwmacc로 int16 누산기에 계속 쌓는 건 위험하다. 안전한 기본형은 vwmul(int8→int16) 후 vwredsum(int16→int32)으로 strip마다 int32 스칼라에 더하는 것이다. 더 빠른 버전은 strip마다 reduction하지 않고 vwadd.wv 등으로 int32 벡터 누산기에 lane별로 모았다가 마지막에 한 번만 reduction한다.

아래는 그 알고리즘의 RVV 어셈블리다.

컴파일하지 않음 (예시) — 이 Mac에는 RISC-V 툴체인이 없다. RVV 1.0 문법 기준으로 작성했다.

같은 것을 C intrinsics로 쓰면 이렇다 (<riscv_vector.h>, __riscv_ 접두사가 붙은 RVV 1.0 intrinsics API).

컴파일하지 않음 (예시) — -march=rv64gcv 같은 V 지원 타깃에서 빌드해야 한다.

이 코드는 여기서 돌릴 수 없으니, 의미를 numpy로 흉내 내어 검증한다. 각 strip에서 vl만큼 읽고, int16으로 곱하고, int32로 모은다.

출력에서 볼 것: VLEN이 128/256/1024로 바뀌어도 결과가 np.dot과 같고 반복 수만 7/4/1로 바뀐다. 마지막 두 줄은 int16 누산기 함정이다 — (-128)² 두 개를 더했더니 -32768로 뒤집혔다.

마지막으로 같은 루프 구조를 이식 가능한 C로 쓴다. 펌웨어에서 RVV 커널을 짤 때 "레퍼런스 C 구현"을 이렇게 같은 strip 구조로 먼저 만들어 두면, 벡터 버전과 strip 단위로 중간값을 비교하기 쉽다.

출력에서 볼 것: vsetvl_e8m1만 바꿔 VLEN을 흉내 냈을 뿐 루프 본체는 그대로인데 결과가 모두 같다. 이게 VLA의 핵심 — 알고리즘은 vl에 대해 정확해야 하고, VLMAX는 몰라도 된다.

5.8 MCU용 벡터: Zve 부분집합#

풀 V 확장은 VLEN ≥ 128과 64비트 원소(ELEN=64), float64까지 요구한다. MCU에는 무겁다. 그래서 Zve32x(정수, 원소 최대 32비트), Zve32f(+float32), Zve64x/f/d 같은 임베디드 부분집합이 정의되어 있고, VLEN도 더 작게(최소 32) 허용된다. int8 추론에는 Zve32x만으로 충분한 경우가 많다. MCU 데이터시트에서 "RVV 지원"을 보면 V인지 Zve 무엇인지, VLEN이 얼마인지를 확인해야 한다. VLEN과 벡터 유닛의 실제 datapath 폭(한 사이클에 처리하는 비트)은 또 다를 수 있다 — 예를 들어 VLEN=256이지만 datapath가 128비트면 한 명령이 2사이클 이상 걸린다.

5.9 함정#

  • vl = VLMAX를 가정하고 포인터를 VLMAX씩 증가 → 균등 정책 구현에서 원소를 건너뛴다.
  • int16 누산기 오버플로 (위 출력). int8 커널은 최소 int32 누산.
  • LMUL을 크게 올리면 반복은 줄지만 레지스터 그룹이 줄어 spill이 생긴다. LMUL=8이면 논리 레지스터가 4개뿐이다.
  • mstatus.VS가 Off인 상태에서 벡터 명령 → illegal instruction. 부트 코드에서 켜야 한다.
  • RVV 0.7.1 칩(1.4절)에 1.0 바이너리 → illegal instruction 또는 이상 동작.
  • reduction을 strip마다 하면 느리다. 핫 루프에서는 lane별 누산 후 마지막에 한 번.

6. 커스텀 명령과 확장 — 칩 벤더가 ISA를 늘리는 이유#

6.1 왜 넣나#

ML 커널의 핫 루프는 몇 가지 연산의 반복이다: int8 dot product, requantization(곱하고 시프트하고 포화), 활성화(clamp, LUT), 비트 unpacking(int4 weight). 범용 명령으로는 4~10개가 필요한 걸 명령 1개로 만들면, 코드 크기·사이클·에너지가 모두 준다. 명령 fetch·decode·레지스터 파일 접근이 연산 자체보다 에너지를 더 먹는 작은 코어에서는 효과가 더 크다(D7의 에너지 모델 참고).

RISC-V는 이걸 공식적으로 허락한다. opcode 공간에 custom 칸을 남겨 두었고, 비표준 확장은 X 접두사 이름(Xvendorname)으로 부르는 관례가 있다. Arm도 최근 일부 코어(Cortex-M33/M55 등)에 Arm Custom Instructions를 허용했지만, 범위가 정해진 틀 안에서다. Xtensa의 TIE는 반대로 커스텀이 설계 철학의 중심이었다 — Don에게 가장 익숙한 비교 대상이다.

6.2 손계산 — 가상의 dot4.i8#

32비트 레지스터 하나에 int8 4개를 packing하고, 명령 하나로 4개 곱의 합을 낸다고 하자.

Arm의 SMLAD(16비트 2개 dual MAC)나 SDOT(E2) 계열과 같은 발상이다. 하드웨어에서는 8비트 곱셈기 4개와 덧셈 트리 하나다.

C에서 이런 명령을 쓰는 가장 흔한 방법은 GNU 어셈블러의 .insn 지시어로 인코딩을 직접 넣는 것이다. 컴파일러를 고치지 않고도 새 명령을 실험할 수 있다.

컴파일하지 않음 (예시) — 가상의 명령이고, custom-0 opcode(0x0B)에 R형으로 인코딩한 예시다. 실제 칩에서는 벤더가 정한 인코딩과 intrinsic을 쓴다.

새 명령을 만들 때 가장 먼저 만드는 것은 RTL이 아니라 골든 모델이다. 명령의 의미를 C로 정확히 써 두고, ISS(명령어 시뮬레이터)·RTL·컴파일러 테스트가 모두 이 모델과 비교한다. Don이 pre-silicon bring-up에서 FPGA 결과를 reference model과 비교하던 흐름 그대로다.

출력에서 볼 것: packing한 레지스터 값(0xFC03FE01 = 바이트 -4, 3, -2, 1)과 첫 명령 결과 -60이 손계산과 같다. 두 번째 묶음의 127·127 + (-128)·(-128) = 32513이 int16을 넘는데도 int32로 정확하다. 명령 수가 32 → 8로 줄어드는 것이 커스텀 명령의 이득이다(실제 사이클은 파이프라인에 따라 다름).

6.3 표준·준표준 쪽의 움직임 (상태는 확인 필요)#

  • P 확장(packed SIMD): 32/64비트 정수 레지스터 안에서 8·16비트 SIMD를 하는 DSP용 확장이다. 오랫동안 draft 상태였고, Andes 등 일부 벤더가 draft 기반 구현을 제품에 넣은 것으로 알려져 있다. 작성 시점에 비준 여부·최종 인코딩은 확인하지 못했으므로, 쓰려면 벤더 툴체인 문서를 따라야 한다.
  • 벡터 쪽 int8 dot 확장: RVV 1.0에는 int8 4개를 int32로 바로 모으는 quad-widening dot 명령이 없다. 그래서 벤더별 확장(예: SiFive가 공개한 벡터 확장들)과 표준화 제안들이 나오고 있다. 이름과 상태는 빠르게 바뀌므로 여기서는 개념만 기억한다: "RVV 1.0 표준만으로 int8 dot은 widening 두 단계가 필요하다."
  • matrix 확장: 여러 벤더가 벡터 레지스터나 별도 타일 레지스터를 쓰는 행렬곱 확장을 제안·구현하고 있다(Arm의 SME와 비슷한 방향). 표준화 전 단계로 보는 게 안전하다.

6.4 가속기를 CPU에 붙이는 거리#

그림 6 — 가속 기능을 붙이는 세 가지 거리. ①은 파이프라인 안의 ALU 확장, ②는 코어 옆에 붙은 코프로세서(명령으로 기동, 레지스터나 벡터 레지스터를 공유할 수 있음), ③은 버스에 달린 메모리맵 NPU(E5, F8). 오른쪽으로 갈수록 한 번 부르는 비용이 커지지만, 한 번에 처리하는 일도 커진다.

선택 기준을 숫자로: 호출 비용이 2 µs인 NPU에 1000 MAC짜리 작은 op를 보내면, CPU가 1 MAC/cycle·100 MHz로 해도 10 µs다 — NPU가 이기려면 op가 충분히 커야 한다. 반대로 활성화 함수 하나를 NPU에 보내는 건 거의 항상 손해다. 그래서 실제 칩은 셋을 섞는다: 큰 층은 NPU, 작은 후처리는 벡터/커스텀 명령.

6.5 커스텀의 대가#

  • 툴체인 파편화: 표준 GCC/LLVM이 모르는 명령은 벤더 포크 컴파일러나 inline asm으로만 쓸 수 있다. upstream 버전을 따라가기 어려워진다.
  • 이식성: 커스텀 명령을 쓴 커널은 그 칩에서만 돈다. 모델 배포 파이프라인이 칩별 커널 라이브러리를 관리해야 한다.
  • 검증 부담: 새 명령마다 골든 모델, ISS, RTL 검증, 컴파일러 테스트가 필요하다.
  • 그래서 좋은 전략은 "표준(RVV)으로 대부분, 커스텀은 프로파일에서 증명된 핫스팟 몇 개만"이다.

  • ML 전용 저전력 칩(GAP 계열)은 여러 코어를 cluster로 묶고 DSP·SIMD 확장을 얹는다 — 커스텀의 자유가 핵심 가치다.
  • 벡터 IP(SiFive, Andes)는 RVV로 NEON/Helium 자리를 노린다. 그리고 NPU 칩 내부의 제어·시퀀서 코어로 RISC-V가 매우 흔하다(사용 여부를 공개하지 않는 경우도 많다).

Hark 같은 기기(추정)에 대입하면: 메인 SoC(Qualcomm)의 DSP·NPU는 벤더 고유 아키텍처지만, 센서 허브나 무선 칩·전원 관리 칩 안의 작은 코어는 RISC-V일 수 있다. 인터뷰에서는 "RISC-V MCU라면 먼저 확인할 것 3가지: -march 조합, 벡터(V/Zve·VLEN) 여부, 커널 라이브러리 지원"처럼 말하는 게 좋다.

8. 툴체인과 소프트웨어 생태계#

8.1 컴파일러 — -march와 -mabi#

GCC와 LLVM/Clang 모두 RISC-V를 upstream에서 지원한다. RVV 1.0 intrinsics와 자동 벡터화도 최근 버전(대략 GCC 13~14, LLVM 16 이후)에서 쓸 만해졌다 — 버전별 품질 차이가 크니 실제 생성 코드를 확인할 것.

옵션뜻예
-march=어떤 확장의 명령을 생성해도 되나rv32imc_zicsr_zifencei, rv32imac_zba_zbb, rv64gcv
-mabi=호출 규약: 정수 폭과 float 인자를 어느 레지스터로 넘기나ilp32(float도 정수 레지스터), ilp32f, ilp32e, lp64d
-mcmodel=코드·데이터 주소 범위 모델medlow(0 근처 절대 주소 ±2 GiB), medany(PC 기준 ±2 GiB)

말로 하면: -march는 "무슨 명령을 써도 되나", -mabi는 "함수끼리 어떻게 인자를 주고받나"다. 둘이 맞지 않는 라이브러리를 링크하면 링커가 ABI 불일치로 거부하거나(좋은 경우), float 인자가 엉뚱한 레지스터로 가는 버그가 난다. Cortex-M의 -mfloat-abi=soft/softfp/hard와 같은 문제다.

8.2 RTOS와 추론 런타임#

  • Zephyr: RISC-V 보드를 많이 지원한다(ESP32-C 계열, SiFive HiFive 보드, QEMU qemu_riscv32 등).
  • FreeRTOS: RISC-V 포트가 공식으로 있다. ESP-IDF의 RTOS도 FreeRTOS 기반이다.
  • TensorFlow Lite Micro(TFLM): 이식 가능한 C++ reference 커널이라 RISC-V에서 그대로 돈다. 성능은 최적화 커널 라이브러리에 달려 있다.
  • 최적화 커널 라이브러리: Arm의 CMSIS-NN에 해당하는 것들이 벤더·학계별로 있다. Espressif의 ESP-NN·ESP-DL, 그리고 TUM에서 공개한 것으로 알려진 muRISCV-NN(CMSIS-NN과 비슷한 API로 RVV·P 확장을 겨냥) 등이다. 성숙도는 CMSIS-NN보다 낮다고 보는 게 안전하다.
  • 컴파일러 기반 스택: TVM, IREE 같은 ML 컴파일러가 RISC-V(RVV) 타깃을 다룬다 (F 모듈에서 다룬다).

8.3 시뮬레이터 — 하드웨어 없이 해 보기#

실행하지 않음 (독자가 해 볼 명령) — 이 Mac에는 RISC-V 툴체인·에뮬레이터가 설치되어 있지 않다. Linux(또는 Docker)에서 배포판 패키지로 설치하는 것이 가장 쉽다. 옵션 이름은 버전에 따라 조금씩 다를 수 있다.

  • QEMU: 빠르고 편하다. user-mode(리눅스 바이너리)와 system-mode(qemu-system-riscv32 -machine virt 등 bare-metal·Zephyr) 모두 된다. 사이클 정확도는 없다.
  • Spike: RISC-V International 쪽 레퍼런스 ISA 시뮬레이터. 스펙 해석이 궁금할 때 기준.
  • Renode: 보드·주변장치까지 모델링하는 시스템 시뮬레이터. MCU 펌웨어 CI에 쓰기 좋다.
  • Verilator + 오픈 코어: 사이클 수준 측정이 필요할 때.

10. 임베디드 관점 — 펌웨어 엔지니어가 RISC-V로 옮길 때 바뀌는 것#

10.1 부트·startup 코드#

Cortex-M은 리셋 시 하드웨어가 벡터 테이블의 첫 워드를 SP로, 두 번째 워드를 PC로 로드한다. C 함수 하나(Reset_Handler)로 시작할 수 있다. RISC-V는 리셋 벡터 주소(구현 정의)에서 명령을 바로 실행하므로, SP·GP 설정부터 어셈블리로 해야 한다.

컴파일하지 않음 (예시) — 전형적인 RV32 bare-metal _start. 심볼 이름은 링커 스크립트에 따라 다르다.

체크 포인트:

  • gp(global pointer): 링커가 gp 기준 ±2 KiB 안의 전역 변수 접근을 lui+addi 두 명령에서 한 명령으로 줄이는 relaxation을 한다. gp를 설정하는 그 명령 자체가 relax되면 안 되므로 norelax로 감싼다.
  • .data 복사(flash → RAM)는 위에서 생략했다. Cortex-M과 동일하게 필요하다.
  • FS/VS: F/D, V 확장 레지스터는 mstatus의 해당 필드가 Off(0)면 쓸 수 없다. Cortex-M4F의 CPACR 설정과 같은 역할이다.
  • 멀티 hart 칩이면 mhartid를 읽어 hart 0만 초기화를 하고 나머지는 대기시키는 코드가 앞에 붙는다.

10.2 인터럽트 핸들러 작성#

  • GCC/Clang에는 __attribute__((interrupt("machine"))) 같은 함수 속성이 있어서, 컴파일러가 쓰는 레지스터를 저장·복원하고 mret으로 끝나는 prologue/epilogue를 만든다. 편하지만 PLIC dispatch 같은 공용 진입점은 보통 어셈블리 trap_entry로 두고 C 함수를 부른다.
  • CSR 접근은 inline asm이다. 예: __asm__ volatile("csrr %0, mcause" : "=r"(cause)); — 대부분의 SDK가 read_csr(mcause) 같은 매크로로 감싸 준다.
  • 크리티컬 섹션: csrrci t0, mstatus, 8(MIE 끄고 이전 값 저장) → … → csrs mstatus, t0(복원). Cortex-M의 __disable_irq()/PRIMASK 저장·복원과 같다.

10.3 성능 측정#

  • mcycle(또는 user-mode에서 rdcycle)과 minstret로 사이클·명령 수를 잰다. IPC = minstret 증가량 ÷ mcycle 증가량. Cortex-M의 DWT CYCCNT 대응이다.
  • mhpmcounter3…은 구현 정의 하드웨어 이벤트 카운터(캐시 미스 등)다. 어떤 이벤트가 있는지는 코어 매뉴얼에만 있다.
  • user-mode 카운터 접근은 mcounteren으로 허용해야 한다. 안 하면 rdcycle이 illegal instruction.

12. 면접에서 이렇게 말한다#

Q. "What is RVV's LMUL and vl?"

A. vl은 이번 벡터 명령이 실제로 처리할 원소 수로, vsetvli가 남은 원소 수(AVL)와 하드웨어 최대치(VLMAX)를 보고 정해 돌려준다. LMUL은 벡터 레지스터 몇 개를 묶어 하나의 논리 벡터로 쓸지 정하는 값으로, VLMAX = LMUL × VLEN ÷ SEW다. LMUL을 키우면 반복 수가 줄지만 쓸 수 있는 레지스터 그룹이 줄어든다. widening 연산은 목적지 LMUL이 두 배가 된다.

vl is the number of elements the next vector instructions will actually process; vsetvli computes it from the remaining application length and VLMAX. LMUL groups 1 to 8 vector registers into one logical register, so VLMAX = LMUL × VLEN / SEW. A larger LMUL means fewer loop iterations but fewer usable register groups, and widening ops write a destination with twice the LMUL.

Q. "What does vector-length agnostic mean?"

A. 코드가 하드웨어의 벡터 레지스터 폭을 모른 채로 작성되고, 실행 시 하드웨어가 알려 주는 vl로 루프를 도는 방식이다. 같은 바이너리가 VLEN 128 칩에서도 512 칩에서도 수정 없이 돌고, 꼬리 처리를 위한 스칼라 루프가 필요 없다. ARM SVE가 같은 모델이고, NEON과 Helium은 128비트 고정 폭이다.

It means the code never hard-codes the vector register width. Each strip-mined iteration asks the hardware how many elements it can process with vsetvli, so the same binary runs on a 128-bit or a 512-bit implementation and the tail is handled by the same loop body. SVE follows the same model; NEON and Helium are fixed 128-bit.

Q. "RISC-V vs ARM for an edge AI MCU — how would you choose?"

A. 기준을 나눠 본다. Arm Cortex-M55/M85 + Helium + Ethos-U는 CMSIS-NN, Vela, 디버그 도구까지 검증된 조합이라 일정 위험이 낮다. RISC-V는 ISA 로열티가 없고 커스텀 명령으로 핫 커널을 가속할 수 있으며 공급망 독립성이 있지만, 확장 조합과 커널 라이브러리 성숙도가 칩마다 달라 파편화 위험이 있다. 그래서 필요한 모델의 op 커버리지, 벤더 SDK·커널 라이브러리 품질, 벡터/NPU 유무, 전력·면적, 팀의 툴체인 경험을 표로 놓고 벤치마크로 결정한다.

I'd separate the criteria. Cortex-M55 or M85 with Helium and Ethos-U is a proven stack — CMSIS-NN, Vela and mature debug tools — so the schedule risk is low. RISC-V gives royalty-free ISA, the freedom to add custom instructions for hot kernels and less vendor lock-in at the ISA level, but extension sets and kernel-library maturity vary a lot between chips. So I'd compare op coverage, the vendor SDK and kernel libraries, vector or NPU availability, power and area, and then decide with a benchmark of our actual model.

Q. "Why would a chip vendor add custom instructions?"

A. ML 핫 루프는 int8 dot product, requantization, 활성화, int4 unpacking 같은 소수 패턴의 반복이다. 범용 명령 여러 개를 하나로 합치면 사이클과 명령 fetch 에너지가 크게 준다. RISC-V는 custom opcode 공간을 예약해 두어서 표준을 깨지 않고 이걸 할 수 있다. 대가는 컴파일러 지원, 이식성, 검증 부담이므로 프로파일로 증명된 핫스팟에만 쓰고, 골든 모델로 검증한다.

Because ML inner loops are dominated by a few patterns — int8 dot products, requantization, activations, unpacking low-bit weights. Fusing several generic instructions into one saves cycles and the fetch and decode energy that dominates on small cores. RISC-V reserves custom opcode space, so vendors can do this without breaking compatibility. The cost is toolchain support, portability and verification, so you only do it for hotspots proven by profiling, with a C golden model as the reference.

Q. "How does interrupt handling on RISC-V differ from Cortex-M?"

A. Cortex-M는 NVIC가 표준이고 예외 진입 시 하드웨어가 레지스터 8개를 자동으로 스택에 쌓아서 ISR을 일반 C 함수로 쓸 수 있다. RISC-V 기본 모델은 하드웨어가 mepc, mcause, mstatus만 갱신하고 mtvec로 점프하며, 범용 레지스터 저장은 소프트웨어 몫이다. 인터럽트 컨트롤러도 CLINT(타이머), PLIC(외부, claim/complete), MCU용 CLIC 등 플랫폼마다 다르다. 복귀는 mret이다.

On Cortex-M the NVIC is standard and the hardware stacks eight registers, so an ISR is a plain C function. On RISC-V the hardware only updates mepc, mcause and mstatus and jumps to mtvec; saving general registers is software's job, often via the compiler's interrupt attribute. The interrupt controller is platform-specific — CLINT for timer and software interrupts, PLIC with claim and complete for external ones, or CLIC on MCU-class cores — and you return with mret.

15. 요약 & 체크리스트#

RISC-V는 칩이 아니라 공개된 ISA 계약서다. 작은 정수 base(RV32I/RV64I/RV32E) 위에 M·A·F·D·C·Zicsr·B(Zba/Zbb/Zbs)·Zfh·V 같은 확장을 골라 얹고, 그 조합이 rv32imac_zicsr 같은 이름이 된다. 명령은 여섯 형식에 레지스터 필드 위치가 고정이라 손으로 인코딩·디코딩할 수 있다. 특권 구조는 M/S/U, trap은 mtvec·mepc·mcause 몇 개로 돌고, Cortex-M과 달리 레지스터 저장은 소프트웨어 몫이며 인터럽트 컨트롤러(CLINT/PLIC/CLIC)는 플랫폼마다 다르다. ML 관점의 핵심은 RVV다: vsetvli가 매 반복 vl을 돌려주는 VLA 모델이라 같은 바이너리가 VLEN과 무관하게 돌고 꼬리 루프가 필요 없다. int8 내적은 widening(vwmul)과 widening reduction(vwredsum)으로 int32까지 넓혀야 안전하다. 칩 벤더는 custom opcode로 ML 핫스팟 명령을 넣고, 이것이 RISC-V의 최대 장점이자 파편화의 원인이다. ARM(Helium+Ethos)과의 선택은 생태계 성숙도 vs 자유도·비용의 trade-off로 설명한다.
