0. 큰 그림 — 이게 왜 필요한가#

D5에서 확인한 한 줄부터 다시 쓴다: decode에서 token 하나를 만들 때마다 가중치 전체를 메모리에서 한 번 읽는다. 연산기는 놀고 메모리 버스가 병목이다(memory-bound). 그래서 decode를 빠르게 하는 방법은 결국 네 갈래 중 하나다.

그림 1 — decode 가속의 네 갈래. ①은 C3(양자화)·L1(작은 모델), ③은 B9(early exit, MoE), ④는 D5 5.6절·L2(prefix/KV 재사용)에서 다뤘다. 이 노트는 ②, 즉 가중치를 한 번 읽어서 token을 여러 개 얻는 방법을 이 Mac에서 실제로 잰다.

펌웨어 비유로 말하면 ②는 "버스 트랜잭션 한 번에 여러 워드를 실어 보내기"다. NAND에서 page 하나를 읽는 비용은 고정이고, 그 page에서 몇 바이트를 쓰느냐에 따라 효율이 달라진다. decode는 매번 page 전체(가중치 전체)를 읽고 1바이트(token 1개)만 쓰는 낭비 상태다. ②의 방법들은 같은 읽기로 token을 여러 개 뽑으려 한다.

  • speculative decoding: 작은 draft 모델이 다음 γ개 token을 추측하고, target 모델이 γ+1개 위치를 한 번의 forward로 검증한다.
  • prompt lookup (n-gram drafting): draft 모델 없이, 프롬프트·지금까지의 출력에서 같은 n-gram을 찾아 그 뒤 token들을 추측으로 쓴다. 요약·편집·RAG처럼 입력을 베끼는 과제에서 강하다.
  • Medusa, EAGLE, lookahead, MTP, LayerSkip: draft를 다른 곳(추가 head, target의 hidden state, Jacobi 반복, 학습 때 넣은 다중 token head, target의 얕은 층)에서 얻는 변형들이다.
  • batching: 서로 다른 사용자의 요청 여러 개를 한 forward에 묶는다. 서버에서는 핵심이지만 개인 기기는 사용자가 한 명이라 거의 못 쓴다.

이 노트에서 실제로 재는 것 (Apple M2, 8코어, 24 GB, Metal GPU와 CPU 4 threads 둘 다):

1. speculative decoding — 5줄 복습과 정확성#

1.1 다섯 줄 요약 (유도는 D5 6.2절)#

  1. draft 모델이 γ개 token d₁…d_γ를 하나씩(자기회귀로) 뽑는다. draft가 작으니 한 step이 싸다.
  2. target 모델에 "마지막 확정 token + d₁…d_γ"를 넣고 한 번 forward 한다. 출력은 γ+1개 위치의 다음-token 분포다. prefill과 같은 모양이다.
  3. 앞에서부터 비교해서 처음 틀린 위치까지 받아들인다. 틀린 자리에는 target의 token을 쓴다. 다 맞으면 target이 하나 더 준다(보너스).
  4. 그래서 한 사이클에 1 ~ γ+1개 token이 나오고, target 가중치는 한 번만 읽힌다.
  5. 기대 이득 = (사이클당 얻은 token 수) ÷ (draft γ step 시간 + 검증 1회 시간, target 1 step 단위). D5의 E = (1 − α^(γ+1)) / (1 − α)와 속도 ≈ E ÷ (γ·c + 1)가 이것이다.

1.2 왜 품질 손해가 없나 — rejection sampling#

greedy(temperature 0)라면 간단하다. target의 argmax와 draft token이 같으면 받아들이고, 다르면 target의 argmax를 쓴다. 출력은 target 혼자 greedy로 돌린 것과 token 단위로 똑같다.

sampling(temperature > 0)이면 Leviathan et al.(2023)의 규칙을 쓴다. draft가 확률 q(x)로 뽑은 token x를

말로 하면: target이 draft보다 그 token을 더 좋아하면 무조건 받고, 덜 좋아하면 그 비율만큼만 받는다. 거절됐을 때는 "target이 원했는데 draft가 덜 준 몫"에서 뽑는다. 이렇게 하면 최종 출력 분포가 정확히 p(target 분포)가 된다. D5의 Monte Carlo가 이 부분은 다루지 않았으니, 핵심만 기억하자: speculative decoding은 근사가 아니라 정확한 샘플러다.

llama.cpp는 어떻게 하나? 이 빌드의 common/sampling.cpp의 common_sampler_sample_and_accept_n()을 보면, target이 각 위치에서 자기 sampler로 직접 token을 뽑고, 그것이 draft token과 같을 때만 다음으로 넘어간다. draft는 top-k 10에서 가장 높은 token을 내는 greedy draft다(common/speculative.cpp, top_k = 10). 이것도 출력 분포는 target 단독과 같다(매 위치의 token을 target이 자기 분포로 뽑으니까). 대신 sampling일 때 수락률은 rejection sampling보다 낮다: 같은 분포에서 뽑아도 "우연히 같은 token"이어야 수락되기 때문이다. 4.4절에서 temperature 0.8의 수락률이 실제로 떨어지는 것을 본다.

정리: greedy는 "같으면 수락", sampled는 "rejection sampling(논문)" 또는 "target이 뽑고 같으면 수락(llama.cpp server)". 둘 다 출력 분포는 target과 같다. 수락률만 다르다.

1.3 C로 보는 greedy 검증 루프#

무엇을 확인하나: target이 한 번의 forward로 낸 argmax 배열 하나로 "몇 개를 받고 무엇을 내보내는지"가 결정되는 과정. 펌웨어의 "CRC 맞는 데까지 받고, 틀린 프레임부터 재전송"과 같은 구조다.

출력에서 볼 것: 최악(case 2)에도 1 token은 나온다. 즉 speculative decoding은 품질은 절대 안 잃고, 속도만 잃을 수 있다. case 1에서 3번째 draft 이후(42, 9)는 맞든 틀리든 버려진다. 뒤쪽 draft의 가치가 기하급수로 줄어드는 이유다.

2. 실험 준비 — 모델 짝, 도구, 측정 방법#

2.1 draft–target 짝: tokenizer가 같아야 한다#

draft token ID를 target에 그대로 넣으니, 두 모델의 vocab이 ID 단위로 같아야 한다. llama.cpp는 common/speculative.cpp의 common_speculative_are_compatible()에서 vocab 종류, BOS/EOS, vocab 크기 차이, 그리고 일정 ID 이후의 token 문자열을 하나씩 비교한다. 다르면 "the target and draft vocabs are not compatible"로 거부한다.

무엇을 확인하나: 이 Mac에 있는 GGUF들의 vocab이 실제로 같은지, llama.cpp에 들어 있는 gguf-py 파서로 직접 읽어서 비교한다 (pip 설치 없이 경로만 추가).

출력에서 볼 것: SmolLM2 135M과 360M은 token 49,152개의 문자열 목록 전체의 해시(020bbde8)까지 같다. 같은 tokenizer로 학습된 한 가족이라 짝이 된다. Qwen2.5-0.5B는 vocab이 151,936개로 완전히 다르고, 이 Mac에는 Qwen2.5보다 작은 Qwen 모델이 없어서 Qwen 쪽 짝은 만들 수 없다(새 다운로드 금지 조건). 실무에서는 같은 가족의 작은 모델(예: Llama-3.2-1B → 3B, Qwen2.5-0.5B → 1.5B/3B)을 쓴다.

짝의 크기를 보자. 파라미터 비는 135M ÷ 362M ≈ 0.37, Q8_0 파일 크기 비는 145 MB ÷ 386 MB ≈ 0.38이다. memory-bound 이론대로라면 draft 1 step은 target의 약 38% 시간이어야 한다. D5 예제의 1B → 3B 짝(c = 0.38)과 거의 같은 비율이고, D5는 이 정도 c면 α가 아주 높아야 겨우 이득이라고 계산했다. 실제는 그보다 더 나쁘다는 것을 3절에서 본다.

2.3 측정 방법 — 부하가 있는 기계에서 공정하게 재기#

이 Mac은 측정 중에 다른 작업(다른 llama-server 여러 개)이 같이 돌았다. 1분 load average가 처음엔 70을 넘었고, 그때 360M 모델이 0.6 tok/s까지 떨어졌다. 그래서 다음 규칙으로 쟀다.

  1. 게이트: 1분 load average가 6 아래로 내려갈 때까지 기다렸다가 시작했다(최대 30분).
  2. 동시 기동 + 교차(interleave): 비교할 설정의 서버를 전부 미리 띄워 두고, 같은 프롬프트를 설정 A, B, C… 순서로 번갈아 보냈다. 부하가 시간에 따라 변해도 모든 설정에 비슷하게 걸린다. 펌웨어 A/B 테스트에서 "같은 보드, 같은 온도, 교대로 측정"하는 것과 같다.
  3. 과제 5종 × 3회 반복, median. 요청마다 load average를 같이 기록했다.
  4. greedy(temperature 0), cache_prompt: false, 출력 최대 128 token. 프롬프트는 SmolLM2의 ChatML 형식으로 직접 감쌌다.
  5. 정답 확인: greedy에서 speculative 출력이 target 단독 출력과 글자 단위로 같은지 비교했다.

3. 재료 측정 — draft 비용 c와 검증 비용 T(k)#

speculative decoding의 이득은 세 숫자로 정해진다: τ(얻은 token), c(draft 상대 비용), T_t(γ+1)/T_t(1)(검증 비용). τ는 과제가 정하고, 나머지 둘은 하드웨어와 런타임이 정한다. 먼저 하드웨어 쪽 두 숫자를 잰다.

3.1 llama-bench로 k-token forward 시간 재기#

llama-bench -p k는 빈 context에서 k개 token을 한 번에 넣는 forward(prefill)의 시간을 잰다. 이게 곧 "γ = k − 1개 draft를 검증하는 데 드는 시간"이다. -r 10으로 10번 재고 jsonl의 samples_ns에서 median을 뽑았다(측정 시 1분 load average 약 5).

무엇을 확인하나: 모델·백엔드별로 k개 위치 forward 1회의 시간(ms)과 decode 1 token 시간.

출력에서 볼 것은 세 가지다.

(1) c는 0.38이 아니라 0.50~0.63이다.

말로 하면: 작은 모델은 바이트에 비례해서 빨라지지 않는다. 360M Q8_0은 386 MB ÷ 6.57 ms ≈ 59 GB/s로 대역폭을 잘 쓰지만, 135M Q8_0은 145 MB ÷ 3.28 ms ≈ 44 GB/s다. 층 수가 30개로 360M(32개)과 거의 같아서 층마다 붙는 고정 비용(커널 실행, 스레드 동기화, norm·attention 같은 작은 연산)이 줄지 않는다. Metal은 커널 launch 오버헤드가 더 커서 c가 0.63까지 간다. 펌웨어로 치면 "전송 크기가 줄어도 DMA descriptor 설정·인터럽트 비용은 그대로"인 상황이다.

(2) Q4_K_M draft가 Q8_0 draft보다 빠르지 않다. Metal에서 3.97 vs 4.02 ms로 같고, CPU에서는 4.08 vs 3.28 ms로 오히려 느리다. 이 크기에서는 바이트가 아니라 고정 비용·역양자화 비용이 지배하기 때문이다. "draft를 더 세게 양자화하면 c가 준다"는 직관은 큰 모델에서만 맞다.

(3) 검증 비용이 k에 따라 늘어난다. 이건 다음 절에서 그림으로 본다.

3.2 검증 비용 T(k) — "검증은 공짜"라는 가정이 깨지는 곳#

그림 2 — 360M Q8_0 target의 forward 1회 시간 vs 한 번에 넣는 token 수 k (실측, median of 10). 회색 점선은 "memory-bound라 k와 무관"이라는 이상적 가정. CPU(파랑)는 k = 5까지 거의 평평(×1.3)하다가 k = 9부터 연산이 보이기 시작한다. Metal(주황)은 k = 2~5에서 오히려 가파르게 오르다가, k = 9에서 떨어진다.

Metal의 이상한 모양은 커널 선택 때문이다. 이 빌드의 ggml/src/ggml-metal/ggml-metal-common.cpp에 행렬곱을 GEMM 커널(mul_mm, simdgroup 행렬 연산)로 보낼지 정하는 조건이 있다:

ne11이 한 번에 곱하는 token(행) 수다. 8개 이하면 GEMM이 아니라 행렬-벡터 계열 커널을 쓰고, 9개부터 GEMM을 쓴다. ggml-metal-ops.cpp에는 "small-batch mat-mv kernels, should be efficient for BS [2, ~8]"라는 주석과 함께 소배치 전용 경로가 있는데, 조건에 ne00 % 128 == 0(입력 차원이 128의 배수)이 들어 있다. SmolLM2-360M의 hidden 크기는 960이라 128의 배수가 아니다. 그래서 이 모델의 상당수 행렬곱은 소배치 경로도 못 타고 일반 mat-vec 경로로 가는 것으로 보인다(추정 — 층별 커널 선택을 trace하지는 않았다). 측정에서 T(5) = 20.0 ms > T(9) = 16.1 ms인 것이 정확히 8/9 경계와 맞는다.

D5 6.1절의 PyTorch 실측(M = 1은 53 GB/s, M ≥ 2는 22 GB/s)과 같은 교훈이다: "검증 k개 = 1 token 비용"은 커널이 작은 M을 잘 처리할 때만 성립한다. 그리고 speculative decoding은 정확히 그 작은 M(2~17)에서 산다.

3.3 k개 검증은 arithmetic intensity를 얼마나 올리나 (D3, E5 연결)#

decode 1 token은 GEMV다: 가중치 행렬 W(d_out × d_in)에 벡터 하나를 곱한다. 가중치 1바이트로 곱셈-덧셈을 한 번(Q8_0이면 약 1 MAC/B) 한다. k개 위치를 한 번에 검증하면 같은 가중치로 k번 곱하는 작은 GEMM이 된다.

손계산: 1B int4, k = 8이면 3.6 × 8 ≈ 28 FLOP/B. 웨어러블 NPU 가정(2 TFLOP/s, 17 GB/s)의 ridge는 2e12 / 17e9 ≈ 118 FLOP/B라서 여전히 memory-bound다. 즉 이론상 k = 8까지는 검증 시간이 1 token과 같다.

무엇을 확인하나: 모델 두 개 × k에 대해 intensity와 웨어러블 가정의 메모리 시간 vs 연산 시간.

출력에서 볼 것: intensity는 k에 정확히 비례한다(1.9 → 7.5 → 15.1, 즉 1.9k). k = 1, 4, 8에서 1B int4는 3.6, 14.2, 28.4 FLOP/B로 ridge 118의 3~24%다. 연산은 메모리 시간의 3~24%를 차지할 뿐이니 이상적인 NPU에서는 검증이 거의 공짜다. 그런데 3.2절의 Metal처럼 커널이 작은 M을 못 다루면 이 이론적 여유가 사라진다. NPU를 평가할 때(M1) "batch 1 GEMV"와 "M = 2~16 작은 GEMM" 둘 다 측정해야 하는 이유다.

E5의 systolic array로 보면 더 분명하다. 128×128 배열에 벡터 하나(M = 1)를 넣으면 한 열만 일하고 나머지는 논다. M = 8이면 8배의 일을 같은 가중치 로드로 한다. 하지만 배열이 M = 128을 전제로 tiling을 짜 놨다면, M = 8도 padding으로 128짜리 타일을 돌릴 수 있다 — 이 경우 검증 시간이 k와 무관하게 비싸다(타일 하나 비용). 어느 쪽인지는 NPU 툴체인이 작은 M을 어떻게 lowering하는지에 달렸고, 문서보다 측정이 확실하다.

4.3 왜 안 빨라지나 — D5 식에 측정값 넣기#

D5의 식을 수락률 α 대신 측정한 τ로 쓰면 가정이 하나 줄어든다.

말로 하면: "draft γ번 + 검증 1번"으로 τ개를 얻는 시간과, target이 τ번 decode하는 시간을 비교한다. τ는 서버 응답에서 n_out ÷ (n_out − accepted)로 계산했다(사이클마다 수락 수 + 1개가 나오므로 사이클 수 = n_out − accepted).

무엇을 확인하나: code 과제의 τ와 3.1절의 T 값으로 예측한 배수가 4.2절의 실측과 맞는지.

(실측 열의 CPU 값은 첫 CPU 측정 세트, load median 6.2에서 나온 값이다. 4.2절 표의 CPU 세트는 그 뒤 다시 잰 것이라 약간 다르다: γ = 2/4/8에서 0.75/0.96/0.99.)

출력에서 볼 것:

  • Metal은 식이 맞는다. γ = 8, 16에서 예측 0.90/0.77 vs 실측 0.88/0.72. 실패 원인이 그대로 보인다: γ = 16이면 사이클 82 ms 중 64 ms가 draft다. τ = 9.85로 검증 한 번에 거의 10 token을 건져도, draft에 쓴 시간이 target이 직접 10번 decode하는 시간(64 ms)과 같다. c = 0.63이면 draft 하나가 target 하나의 2/3 값이다. 이 상태에서는 수락률 100%라도 최대 1 ÷ 0.63 ≈ ×1.6 미만이다.
  • CPU는 예측(×1.16~1.31)이 실측(×0.70~0.99)보다 높다. 식에 없는 사이클당 고정 비용이 있다는 뜻이다. 후보: 모델 두 개의 context가 번갈아 실행되며 생기는 스레드풀 전환, draft의 logits 복사와 top-k 샘플링(49,152개 vocab), 서버의 사이클당 처리. 이 중 하나는 확인했다: --poll 0(스레드가 일을 기다리며 spin하지 않게)을 주면 같은 γ = 4가 ×0.96 → ×1.02, γ = 8이 ×0.99 → ×1.08로 올라갔다(4.2절 표). draft와 target이 각자 4개 스레드로 spin-wait하면서 8코어(성능 코어 4 + 효율 코어 4)를 서로 뺏는 것으로 보인다(추정 — 스레드 스케줄을 직접 trace하지는 않았다).
  • D5의 손계산이 경고했던 것: c = 0.38에서도 α가 0.65는 넘어야 이득이었다. 실제 c는 0.50~0.63이고, 검증도 공짜가 아니다. 그래서 "수락률 80%대 + 이득 없음"이라는 결과가 나온다. 수락률만 보고 speculative decoding을 판단하면 안 된다.

4.5 "출력이 똑같다"를 확인하기 — 그리고 부동소수점의 함정#

greedy에서는 speculative 출력이 target 단독 출력과 글자 단위로 같아야 한다. 모든 측정의 rep 0 출력을 비교했다.

(Metal, 순서는 code, summary, extract, chat, korean.) draft 방식은 전부 같았다. 그런데 prompt lookup(ng3)의 chat 하나가 달랐다. 출력의 앞 39단어는 같고, "He was a robot who" 다음에 기준 출력은 "had been designed to paint", prompt lookup 쪽은 "loved to paint"로 갈라졌다. draft가 틀려서가 아니다 — draft는 수락 여부만 정하지 token을 정하지 않는다. 원인은 target 쪽 계산 경로다: 검증 forward는 k개 위치를 한꺼번에 계산하는데, k에 따라 다른 커널(3.2절)과 다른 누산 순서를 쓴다. 부동소수점 덧셈은 결합법칙이 성립하지 않으니 logit이 아주 조금 달라지고, 1등과 2등이 거의 동점인 위치에서 argmax가 뒤집힌다. CPU 측정에서는 모두 같았다.

펌웨어 경험으로 말하면 "DMA burst 크기를 바꿨더니 결과 CRC가 달라졌다"와 같은 종류의 문제다. 수학적으로는 lossless지만 수치적으로는 batch 모양에 따라 결과가 흔들린다. 회귀 테스트에서 "spec on/off 출력 비교"를 할 때는 완전 일치가 아니라 "divergence 위치에서 top-2 logit 차이가 아주 작은지"로 판정해야 한다.

4.6 언제 이길까 — target을 무겁게, draft를 가볍게#

c를 줄이는 가장 직접적인 방법은 target을 더 크게(무겁게) 만드는 것이다. 같은 135M draft에 target을 f16 360M(725 MB)으로 바꾸면 target 단독은 Metal 95~106 tok/s로 느려지지만, γ = 4 speculative는 chat을 빼면 76~81 tok/s로 Q8_0 target 때와 거의 같아서, 배수가 ×0.49~0.63에서 ×0.76~0.85로 오른다(Metal, 같은 f16 단독 대비, chat 제외. chat은 ×0.33 → ×0.52). 방향은 맞지만 이 짝으로는 여전히 이득이 안 난다.

5. prompt lookup — draft 모델 없이 프롬프트에서 베끼기#

5.1 아이디어#

요약, 문서 편집, RAG 답변, 코드 수정 같은 과제에서는 출력의 상당 부분이 입력에 이미 있다. "The Aria wrist-worn device has a 120 mAh battery"를 쓰는 중이라면, 다음 token들은 원문 "… a wrist-worn device with a 120 mAh battery. In always-on mode …"에서 그대로 올 가능성이 높다. 그러니 draft 모델 대신 지금까지의 마지막 n개 token과 같은 n-gram을 프롬프트(+지금까지 출력)에서 찾아, 그 뒤 m개를 draft로 쓴다. Saxena(2023)가 "prompt lookup decoding"으로 공개한 방법이고, llama.cpp의 ngram-simple이 같은 방식이다.

장점은 펌웨어 엔지니어가 좋아할 만한 것들이다: 추가 가중치 0바이트, 추가 KV 0바이트, draft 연산 0 FLOP(문자열 검색 비용만), 학습 불필요. 단점은 과제 의존성이 크다는 것 — 입력을 베끼지 않는 자유 대화에서는 draft가 거의 안 나오거나 틀린다.

5.2 오프라인 시뮬레이션 — 실제 출력에 n-gram 매칭을 돌려 보기#

먼저 llama.cpp 없이 원리를 확인한다. target의 실제 greedy 출력 token열을 서버에서 받아 두고(return_tokens: true), 그 위에서 "prompt lookup이 있었다면 검증 한 번에 몇 token을 얻었을지"를 계산한다. greedy에서는 수락 여부가 "draft token == 실제 출력 token"으로 결정되니, 출력만 있으면 정확히 시뮬레이션할 수 있다.

무엇을 확인하나: 360M Q8_0 서버에서 과제 5종의 프롬프트 token과 greedy 출력 token(최대 256개)을 받아 저장한다.

출력에서 볼 것: summary 출력의 끝("… wake word false accepts from 20 per hour to 4 per hour.")이 원문 문장 거의 그대로다. 한국어 프롬프트는 약 40글자인데 106 token이다 — SmolLM2 tokenizer에서 한글 한 글자가 2~3 token으로 쪼개진다(B8의 tokenizer 효율 이야기). korean 출력은 프롬프트를 되풀이하고 있다.

무엇을 확인하나: 저장한 token열 위에서 prompt lookup(n-gram n = 3, draft 최대 k = 8)을 흉내 내고, 검증 1회당 얻는 token 수(tok/step)와 수락률을 센다. 그다음 n과 k를 바꿔 본다.

출력에서 볼 것:

  • summary는 검증 한 번에 평균 2.84 token을 얻는다. 145 token을 51번의 target forward로 만든다. chat은 1.07로 거의 이득이 없다(240번 중 대부분 draft가 없거나 첫 token에서 틀림).
  • code(1.23)는 draft 모델 방식(τ = 4.27)보다 훨씬 낮다. 코드의 반복 구조("assert is_palindrome(")는 잡지만, 새 내용은 못 맞힌다. draft 모델은 "언어를 아는" 추측, prompt lookup은 "베끼기" 추측이다.
  • n이 작을수록 매치는 자주 되지만 틀린 매치도 늘어난다. summary에서는 n = 2가 가장 좋고(k = 16에서 3.92), n = 4는 너무 엄격하다. k를 늘리면 tok/step은 계속 오르지만, 실제로는 검증 비용 T(k+1)도 오른다(3.2절).
  • korean의 6.40은 프롬프트를 그대로 되풀이하는 퇴화 출력이라 생긴 숫자다. 5.4절.

draft 모델과 prompt lookup 사이에는 여러 변형이 있다. 모두 "검증은 target이 한 번에"라는 뼈대는 같고, draft를 얻는 곳이 다르다.

한 줄씩 풀면:

  • Medusa (Cai et al., 2024): target의 마지막 hidden state 위에 작은 head(대개 1층 MLP) 여러 개를 붙여, head i가 i칸 뒤 token을 예측한다. 후보들의 조합을 tree로 만들어 한 번에 검증한다(tree attention: 각 후보 경로가 자기 조상만 보도록 attention mask를 준다). 추가 메모리가 작고 target forward 한 번으로 draft까지 나온다.
  • EAGLE (Li et al., 2024): "token을 맞히는 것보다 다음 feature(hidden state)를 맞히는 게 쉽다"는 관찰로, target의 feature와 한 칸 앞 token을 입력으로 받는 1-layer draft를 학습한다. EAGLE-2는 draft tree를 신뢰도에 따라 동적으로 키우고, EAGLE-3는 여러 층의 feature를 섞는다. 이 llama.cpp 빌드는 --spec-type draft-eagle3를 지원한다(전용 draft GGUF 필요).
  • lookahead decoding (Fu et al., 2024): Jacobi 반복으로 미래 여러 위치를 병렬로 추측·갱신하며 n-gram 후보 풀을 만들고 검증한다. draft 모델이 필요 없지만 한 step의 연산이 크다(창 크기 × n-gram 길이만큼의 위치를 매 step 계산). GPU처럼 연산이 남는 곳에 맞고, 연산 예산이 빠듯한 웨어러블 NPU에는 불리하다(추정). llama.cpp에는 examples/lookahead가 있지만 이 빌드에서는 빌드하지 않았다.
  • MTP (Gloeckle et al., 2024; DeepSeek-V3에서 대규모로 사용): 사전학습 때 "다음 1개"뿐 아니라 "다음 n개"를 예측하는 head를 같이 학습한다. 추론 때 이 head가 draft가 된다. 모델을 처음부터 이렇게 만들어야 해서 우리가 고를 수 있는 선택지는 "MTP head가 있는 모델을 고르기"다. 이 빌드의 draft-mtp가 그것이다.
  • self-speculative / LayerSkip (Elhoushi et al., 2024): 학습 때 layer dropout과 early-exit loss를 넣어 얕은 층의 출력도 쓸 만하게 만들고, 추론 때 앞쪽 L층만으로 draft를 만든 뒤 나머지 층으로 검증한다. 가중치를 공유하니 추가 메모리가 거의 없고, 앞 L층의 KV도 재사용한다. B9 4절의 early exit와 같은 뿌리다. (학습 없이 층을 건너뛰는 Draft & Verify, Zhang et al. 2023도 있다.)

NPU에서 따질 것 (E5, F4와 연결):

  1. 정적 shape: NPU 컴파일러는 대개 고정 shape 그래프를 좋아한다. 검증 그래프를 k = 4 또는 8 같은 고정 크기로 컴파일하고, draft가 적으면 padding하는 것이 현실적이다. prompt lookup처럼 draft 길이가 들쭉날쭉한 방법도 고정 k 그래프 하나 + mask로 처리한다.
  2. KV 되감기: 거절된 위치의 KV를 무효화해야 한다. 런타임이 KV를 그래프 내부 상태로 숨기면 어렵고, 입력·출력 버퍼로 노출하면 "길이 포인터만 되돌리기"로 끝난다(9.2절 C 코드).
  3. 작은 M 커널: 3.2절의 Metal처럼 M = 2~8 경로가 느리면 검증이 비싸진다. 벤더 툴체인에서 이 구간을 반드시 측정한다.
  4. draft를 어디서 돌리나: 독립 draft 모델을 NPU에서 target과 번갈아 돌리면 그래프 전환 비용이 사이클마다 든다. draft를 CPU에, target 검증을 NPU에 두는 분업도 가능하지만, 두 장치 사이 동기화 지연이 사이클당 들어간다(E8의 이종 SoC 문제). Medusa·MTP·self-speculative는 그래프 하나라 이 문제가 없다는 점이 웨어러블에서 큰 장점이다(추정 — 실제 NPU 지원 여부는 툴체인마다 다르다).

7. batching — 폰과 서버는 왜 다른가#

7.1 continuous batching이란#

D5 6.1절에서 본 대로, 서로 다른 sequence N개를 한 forward에 묶으면 가중치를 한 번 읽어 N개 token을 만든다. speculative decoding이 "한 사용자의 미래 token"을 묶는다면, batching은 "여러 사용자의 현재 token"을 묶는다. 서버는 요청이 제각각 들어오고 끝나니, step마다 끝난 sequence를 빼고 새 요청을 넣는다. 이것이 continuous batching(iteration-level scheduling, Orca, Yu et al. OSDI 2022)이고, vLLM의 PagedAttention(Kwon et al. SOSP 2023)이 그 KV 관리를 맡는다. llama-server에서는 --parallel N(slot N개)이 동시에 처리하는 sequence 수, --cont-batching(기본 켜짐)이 그 스케줄링이다.

7.2 실측 — N개 동시 요청#

같은 chat 프롬프트를 temperature 0.8, seed만 다르게, ignore_eos로 정확히 128 token씩 N개 동시에 보냈다. 서버는 -np N -c 512×N, target 360M Q8_0. N마다 3회, median. (측정 시 load average 4.3~5.5)

무엇을 확인하나: N에 따른 총 처리량(모든 요청 token ÷ 벽시계 시간)과 요청 하나가 체감하는 속도.

그림 8 — 동시 요청 수 N에 따른 총 처리량(실선)과 요청당 속도(점선). CPU(파랑)는 N = 4까지 총 처리량이 거의 N배로 오르다가(×3.1) 연산 한계에 닿아 평평해진다. Metal(주황)은 N = 8까지 거의 안 오르다가 N = 16에서 ×5로 뛴다 — 3.2절과 같은 커널 경계(ne11 > 8)다.

출력에서 볼 것:

  • CPU N = 4: 총 처리량 392 tok/s(×3.1)인데 요청 하나는 107 tok/s(×0.82). 서버 운영자에게는 "같은 하드웨어로 3배 손님", 사용자 한 명에게는 "18% 느려짐"이다. memory-bound decode에 batch가 공짜에 가깝다는 D5의 이론이 그대로 보인다.
  • CPU N = 8~16: 총 처리량이 446 → 473으로 포화. 4 threads의 연산 한계에 닿았다(compute-bound로 넘어감). 요청당 속도는 35 tok/s까지 떨어진다.
  • Metal N = 2~8: 총 처리량이 154 → 203으로 거의 그대로이고 요청당 속도만 1/N로 준다. 3.2절의 mat-vec 경로가 행마다 비용을 다시 내기 때문으로 보인다. N = 16에서 GEMM 경로로 넘어가자 775 tok/s. 같은 하드웨어에서 batch 8과 16의 효율이 4배 차이 나는 것은 커널 경계 하나 때문이다.

7.3 폰·웨어러블이 서버 같은 처리량을 못 얻는 이유#

  • 사용자가 한 명이다. 묶을 다른 요청이 없다. 위 표의 N = 1 줄이 기기의 현실이다.
  • 묶을 수 있는 것은 "한 사용자의 미래 token"(speculative, prompt lookup)이나 "한 사용자의 여러 후보"(parallel sampling, beam search) 정도다. 후자는 처리량이 아니라 품질을 위한 것이라 지연은 오히려 늘어난다.
  • 그래서 서버 업계의 "tokens/s per GPU" 숫자(batch 수십~수백)를 기기 성능과 비교하면 안 된다. 기기에서 볼 숫자는 batch 1 TPOT다(D5).
  • 거꾸로 hybrid 설계(L3)에서는 이 비대칭이 경제성을 만든다: 클라우드는 수많은 사용자를 batch로 묶어 token당 비용이 싸고, 기기는 batch 1이라 token당 에너지·시간이 비싸다. "어떤 요청을 기기에서, 어떤 요청을 클라우드에서"의 판단 근거 중 하나다.

8. 에너지 — 더 계산하고 덜 읽기#

speculative decoding은 연산을 더 하고(draft 연산, 거절된 token의 검증 연산), 가중치 읽기를 줄인다(target 가중치를 τ token마다 한 번만 읽음). memory-bound 기기에서 에너지는 대부분 DRAM 읽기와 static 전력이니(D7 3.4절: token당 DRAM 22.5 mJ vs MAC 0.3 mJ), 이 교환이 에너지에도 이득일 가능성이 높다. 바이트만 세면 조건이 간단하다.

말로 하면: 한 사이클에 읽는 바이트(draft γ번 + target 1번)를 얻은 token 수로 나눈 값이 W_t보다 작으면 이득이다. 손계산 — γ = 4, W_d / W_t = 0.135(135M int4 / 1B int4)면 τ > 1.54. 4.2절의 code(τ = 4.27)는 넉넉히 넘고, 자유 대화도 τ = 2.5 정도면 넘는다. prompt lookup은 W_d = 0이라 τ > 1이면 무조건 이득이다.

무엇을 확인하나: D7의 가정 숫자(DRAM 40 pJ/B, int8 MAC 0.3 pJ, static 300 mW)와 웨어러블 가정(17 GB/s, 2 TMAC/s)으로 token당 시간과 에너지를 계산한다. τ는 이 노트에서 측정한 값을 빌려 쓴다(모델 짝이 다르니 예시일 뿐이다).

그림 9 — 웨어러블 가정 모델의 token당 에너지 (target 1B int4 단독 = 1.0). 초록은 절약, 빨강은 손해, 회색은 비김. 가정 모델이므로 절대값이 아니라 방향만 본다.

출력에서 볼 것과 해석:

  • 이 이상적 모델에서는 c = 76 MB ÷ 562 MB = 0.135이고 검증도 공짜(memory-bound)라서, 같은 τ로 속도 ×2.8, 에너지 ×0.37이 나온다. 이 Mac의 실측(×1.0 언저리)과의 차이는 전부 3절의 두 가지 — 실측 c가 0.5~0.63이고, 검증이 공짜가 아님 — 에서 온다. 기기 NPU가 작은 모델에서도 대역폭에 비례하는 속도를 내는지(고정 오버헤드가 작은지)가 판단의 열쇠다.
  • 에너지와 속도가 거의 같은 비율로 움직인다. 이 모델에서 token당 에너지 = DRAM 바이트 비용 + static × 시간이고, 둘 다 "읽은 바이트"에 비례하기 때문이다(D7 3.4절과 같은 결론). race-to-idle 관점으로 말하면 빨리 끝내는 것이 곧 아끼는 것이다.
  • τ가 낮으면(최악 τ = 1.2) 에너지가 ×1.31로 손해다. draft 연산과 draft 가중치 읽기가 버려지기 때문이다. 과제에 따라 speculative를 켜고 끄는 정책(예: 최근 수락률이 낮으면 끄기 — llama.cpp ngram-map-k가 n-gram별 수락 기록을 쓰는 것과 같은 발상)이 에너지에도 필요하다.
  • 빠진 것: KV 읽기(짧은 context라 무시), draft를 SRAM에 상주시키는 경우(가중치가 작으면 DRAM 40 pJ/B가 아니라 SRAM 수 pJ/B — draft가 2~4 MB 수준인 Medusa head나 n-gram 테이블이라면 가능), DVFS. 실제 판단은 K3의 전력 측정으로 한다.

9.2 C로 보는 KV 되감기 — "지우지 말고 포인터만 되돌린다"#

검증 forward는 draft token들의 KV까지 일단 캐시에 쓴다. 일부가 거절되면 그 위치들을 무효화해야 한다. 링버퍼의 write pointer를 되돌리는 것과 같다. 데이터를 지울 필요가 없다 — 다음 쓰기가 덮어쓴다.

무엇을 확인하나: prompt 3개, draft 4개 검증, 2개만 수락, 교정 token 1개를 넣은 뒤 KV 길이와 내용.

출력에서 볼 것: 위치 5에는 원래 draft 42의 KV가 있었지만, 되감은 뒤 교정 token 77이 덮어썼다. 위치 6(draft 9)의 KV는 메모리에 남아 있지만 n_past 밖이라 attention이 보지 않는다. 실제 런타임에서는 (1) attention이 n_past까지만 보도록 mask나 길이 인자를 주고, (2) 교정 token의 KV는 다음 사이클의 검증 forward 첫 위치에서 계산된다(여기서는 단순화해서 바로 넣었다). llama.cpp에서는 sequence의 KV 범위를 지우는 메모리 API로 같은 일을 한다. paged KV(D5 5.3)라면 블록 단위 할당이라, 거절이 블록 경계를 넘을 때만 블록을 반납하면 된다.

펌웨어 경험과 연결하면: NVMe의 completion queue에서 "head pointer만 옮기고 엔트리는 안 지운다"와 같은 패턴이다. 실수하기 쉬운 곳도 같다 — 포인터를 되돌리는 것을 잊으면 거절된 token의 KV가 context에 남아 이후 출력이 미묘하게 틀어진다. 증상은 crash가 아니라 "가끔 문맥이 이상한 답"이라 찾기 어렵다. 4.5절처럼 spec on/off greedy 출력 비교 테스트를 회귀 스위트에 넣어 두는 것이 가장 싼 보험이다.

9.3 bring-up 체크리스트 — "speculative 켰더니 빨라졌다/느려졌다"를 받았을 때#

  1. c를 먼저 잰다. draft 1 token 시간 ÷ target 1 token 시간. 0.3을 넘으면 기대를 낮춘다. 바이트 비가 아니라 실측으로.

  3. τ와 수락률을 과제별로 잰다. 벤치마크 프롬프트가 아니라 제품 프롬프트로. temperature도 제품 설정으로.
  4. 출력 동일성(greedy)을 확인한다. 다르면 KV 되감기 버그 또는 수치 경로 차이(4.5절) 중 무엇인지 가른다.

11. 면접에서 이렇게 말한다#

Q. "Explain speculative decoding and when it helps."

A. decode는 token마다 가중치 전체를 읽는 memory-bound 작업이다. 작은 draft 모델이 γ개를 추측하고 target이 γ+1개 위치를 한 번의 forward로 검증하면, target 가중치를 한 번 읽고 여러 token을 얻는다. 수락 규칙(greedy 일치 또는 rejection sampling) 덕분에 출력 분포는 target과 정확히 같다. 이득은 τ × T_t(1) ÷ (γ·T_d + T_t(γ+1))이라서, draft가 target보다 10배 이상 싸고, 과제가 예측 가능하고, 검증 batch가 거의 공짜일 때 이긴다.

Decode is memory-bound: every token re-reads all the weights. A cheap draft model proposes γ tokens and the target verifies γ+1 positions in one forward pass, so one weight read yields several tokens, and the acceptance rule keeps the output distribution identical to the target's. It pays off when the draft is roughly ten times cheaper than the target, the text is predictable, and the hardware can verify a small batch at close to single-token cost.

Q. "Why might speculative decoding not help on our device?"

A. 세 가지다. 첫째, 기기에 들어가는 target이 작아서 draft와의 크기 차이가 작다 — 내가 135M → 360M으로 재 보니 draft가 target 시간의 50~63%를 먹었고(바이트 비는 38%), 수락률 80%대에서도 ×0.5~1.1이었다. 둘째, 검증 비용이 공짜가 아니다 — Metal에서 5-token forward가 1-token의 3.1배였다(커널 경로 때문). 셋째, draft 가중치와 KV가 메모리를 더 먹고, 두 모델을 번갈아 돌리는 전환 비용이 있다. 그래서 먼저 c와 T(k)를 재고, 안 되면 prompt lookup이나 MTP/Medusa 같은 단일 그래프 방식을 본다.

On a wearable the target itself is small, so the draft is not much cheaper: when I measured SmolLM2 135M drafting for 360M, the draft cost 50 to 63 percent of a target step and, even with 80-plus percent acceptance, I got 0.5 to 1.1x. Verification also isn't free if the NPU or GPU kernels handle batch sizes of 2 to 8 poorly, and the draft adds weights, KV and switching overhead. So I measure the draft cost ratio and the k-token forward cost first, and then I look at zero-memory options like prompt lookup or single-graph ones like MTP heads.

Q. "What is prompt lookup decoding and which tasks benefit?"

A. draft 모델 대신 마지막 n개 token과 같은 n-gram을 프롬프트·출력에서 찾아 그 뒤 token들을 draft로 쓰는 방법이다. 추가 메모리와 학습이 0이고, 매치가 없으면 일반 decode라 손해도 작다. 요약·편집·RAG·코드 수정처럼 입력을 베끼는 과제에서 이득이 크다. 내가 잰 것으로는 요약에서 ×1.55~1.77, 자유 대화에서 ×0.93~1.00이었다. 단, 반복·퇴화 출력도 엄청 빨라 보이니 품질과 같이 봐야 한다.

Prompt lookup drafts by matching the last few tokens against an n-gram in the prompt or earlier output and proposing whatever followed it. It needs no extra weights or training, and when nothing matches it falls back to normal decode, so the downside is small. It shines on copy-heavy tasks like summarization, editing, RAG and code edits: I measured 1.55 to 1.77x on summarization and roughly 1.0x on open chat. One caveat is that degenerate repetitive output also looks very fast, so I always report quality next to speed.

Q. "How does verifying k tokens change arithmetic intensity?"

A. 1 token decode는 GEMV라서 가중치 1바이트당 MAC 1번 정도다(int8 기준 약 2 FLOP/B, int4면 약 3.6). k개를 한 번에 검증하면 같은 가중치로 k번 곱하는 작은 GEMM이 되어 intensity가 k배가 된다. 1B int4에서 k = 1, 4, 8이면 3.6, 14, 28 FLOP/B로, 웨어러블 ridge(가정 약 118)보다 한참 아래라 이론상 시간은 거의 그대로다. 실제로는 커널이 작은 M을 잘 처리하는지가 관건이라 k = 1~17을 직접 잰다.

Single-token decode is a GEMV, about 2 FLOP per byte for int8 weights and about 3.6 for int4. Verifying k positions reuses each weight k times, so it becomes a skinny GEMM with k times the intensity: 3.6, 14 and 28 FLOP per byte for k = 1, 4 and 8 on a 1B int4 model. All of those are still far below a wearable ridge point of around 118, so in theory verification costs about the same as one token. In practice it depends on whether the kernels handle small M efficiently, so I measure k from 1 to 17 directly.

Q. "Batching on a phone versus a server?"

A. 서버는 여러 사용자의 요청을 continuous batching으로 한 forward에 묶어 가중치 재사용을 N배로 만든다. 내가 CPU에서 재 보니 동시 4개에서 총 처리량 ×3.1, 요청 하나는 ×0.82였다. 폰·웨어러블은 사용자가 한 명이라 batch가 1이고, 남는 수단은 한 사용자의 미래 token을 묶는 speculative·prompt lookup이다. 그래서 서버의 "tokens/s per GPU"와 기기의 batch-1 TPOT는 비교하면 안 된다.

A server packs many users' sequences into each forward pass with continuous batching, so it reuses each weight read N times. On this CPU, four concurrent requests gave 3.1x aggregate throughput while each request ran at 0.82x. A phone serves one user at batch size 1, so the only way to get the same reuse is to batch one user's future tokens through speculative decoding or prompt lookup. That's why server tokens-per-second numbers can't be compared with on-device batch-1 TPOT.

Q. "Does speculative decoding save energy?"

A. memory-bound 기기에서는 대체로 그렇다. token당 읽는 바이트가 (γ·W_d + W_t)/τ로 줄고, 빨리 끝나니 static 에너지도 준다. 조건은 τ > 1 + γ·W_d/W_t다. 하지만 τ가 낮으면 draft 연산과 읽기가 버려져서 손해(가정 모델에서 τ = 1.2일 때 ×1.3)라, 수락률이 낮을 때 자동으로 끄는 정책이 필요하다.

Usually yes on a memory-bound device: bytes read per output token drop to (γ·W_draft + W_target)/τ, and finishing sooner also cuts static energy. The break-even condition is τ > 1 + γ·W_draft/W_target. When acceptance is poor the draft work is wasted and energy goes up, about 1.3x in my model at τ = 1.2, so I'd add a policy that turns drafting off when recent acceptance drops.

14. 요약 & 체크리스트#

speculative decoding은 "가중치 한 번 읽고 token 여러 개"를 노리는 정확한(lossless) 가속이다. 이득은 τ × T_t(1) ÷ (γ·T_d + T_t(γ+1))로 정해지고, 이 Mac의 SmolLM2 135M → 360M 실측에서는 draft 비용 c가 0.50~0.63(바이트 비 0.38보다 큼), 검증 비용이 Metal에서 5 token에 ×3.1이라 수락률 80~93%에도 대부분 ×1 미만이었다(최선은 CPU ×1.08 — 퇴화한 korean 출력 제외 — , Metal ×0.88). draft 비용이 0인 prompt lookup은 요약 과제에서 ×1.55~1.77, 맞지 않는 과제에서도 ×0.9~1.0으로 손해가 작았다. batching은 서버에서 총 처리량을 ×3~5로 올리지만 기기는 batch 1이다. 웨어러블에서는 양자화·작은 모델·prompt lookup·prefix 재사용이 먼저이고, 독립 draft 모델은 c와 T(k)를 측정한 뒤에만 고려한다.
