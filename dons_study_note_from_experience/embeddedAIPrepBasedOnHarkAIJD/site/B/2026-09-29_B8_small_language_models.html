0. 큰 그림 — 이게 왜 필요한가#

B4에서 attention 한 층이 어떻게 계산되는지 봤다. 이 노트는 한 발 뒤로 물러나서 LLM을 하나의 시스템으로 본다. 펌웨어 엔지니어 눈으로 보면 LLM 추론은 이런 물건이다.

  • 입력: 텍스트 → tokenizer가 정수 배열(token id)로 바꾼다. UART로 들어온 바이트 스트림을 프로토콜 파서가 명령어 ID로 바꾸는 것과 비슷하다.
  • 본체: 같은 모양의 decoder block을 N번 쌓은 거대한 함수. 파라미터(가중치)는 수억~수십억 개이고 DRAM에 산다.
  • 출력: 매 step마다 "다음 token 후보 전체(vocab 크기)에 대한 점수(logits)" 하나를 낸다. sampler가 그중 하나를 고른다.
  • 루프: 고른 token을 입력 끝에 붙여서 다시 돌린다. 문장이 끝날 때까지 반복한다. 이것을 autoregressive 생성이라 부른다.

그림 1 — 추론 때의 LLM 전체 구조. token id가 embedding 표에서 벡터로 바뀌고, decoder block N개를 지나, LM head가 vocab 크기의 logits를 낸다. sampler가 고른 token은 다시 입력으로 들어간다(주황 점선). KV-cache는 과거 token의 계산 결과를 저장해 두는 버퍼다(B4).

Edge ML 엔지니어가 이 구조에서 알아야 하는 질문은 대부분 숫자 질문이다.

  1. 이 모델은 몇 바이트인가? (가중치 크기, 3절)
  2. context 4K에서 KV-cache는 몇 바이트인가? (4절)
  3. 기기의 메모리 대역폭으로 초당 몇 token이 나오는가? (4절, D5)
  4. 한국어 문장 하나는 몇 token인가? 그래서 context가 얼마나 빨리 차는가? (5절)
  5. 첫 글자가 나올 때까지 몇 ms인가(TTFT)? 그다음 글자마다 몇 ms인가(TPOT)? (7절)

이 노트는 이 다섯 질문에 직접 계산하고 실제로 측정해서 답한다. 실습에는 Hugging Face의 SmolLM2-135M-Instruct(1억 3,450만 파라미터, Apache-2.0)를 이 Mac에 내려받아 썼다. 다운로드한 가중치가 필요한 예제는 제목 옆에 [모델 필요], config·tokenizer 파일만 받는 예제는 [config/tokenizer], 순수 numpy/C 예제는 [독립]으로 표시한다.

실습 환경: Apple M2 (8코어 CPU, 24 GB unified memory), Python 3.9, PyTorch 2.8, transformers 4.57. 모델은 ~/.cache/huggingface에 약 260 MB로 저장됐다.

1. 추론 때의 LLM — decoder-only transformer 한 벌#

1.1 직관: 거대한 "다음 글자 예측기"#

휴대폰 키보드의 단어 추천을 생각하면 된다. "내일 아침" 까지 치면 "에"를 추천한다. LLM은 이것을 극단적으로 잘하는 함수다. 입력 token 열 x₁ … x_t를 받아 다음 token x_{t+1}의 확률분포를 낸다.

말로 하면: token들을 벡터로 바꾸고(Embed), 같은 구조의 블록을 N번 통과시키고(Decoder^N), 마지막 위치의 벡터를 vocab 크기의 점수로 바꾼 뒤(LMHead), softmax로 확률로 만든다(A2 6절).

1.3 코드로 확인: 모델을 열어 본다 [모델 필요]#

실제 모델을 불러와 파라미터 수, 블록 수, embedding 공유 여부를 보고, "The capital of France is" 다음 token 분포의 상위 5개를 뽑는 코드다.

출력에서 볼 것:

  • 입력 문장 5단어가 token 5개가 됐다. 영어 흔한 단어는 대개 단어 하나 = token 하나다(앞 공백 포함, 5절).
  • logits 모양이 [1, 5, 49152]다. 모든 위치에 대해 다음 token 점수가 나오지만 생성에 쓰는 것은 마지막 위치 하나뿐이다. 나머지 4개는 학습 때(모든 위치에서 동시에 loss를 계산할 때) 쓴다.
  • lm_head tied: True — LM head와 embedding 표가 같은 메모리를 가리킨다. 1억 3,450만 중 2,831만(21%)이 이 표다(3절).
  • 135M짜리 작은 모델도 " Paris"에 0.469를 준다. 하지만 " the"(0.266)도 꽤 높다. "The capital of France is the city of Paris"도 말이 되기 때문이다. 이 분포에서 무엇을 고를지가 6절(sampling)의 주제다.

1.4 next-token 루프#

생성은 이 함수를 반복 호출하는 루프다. C로 쓰면 이렇다(의사 코드).

그림 2 — autoregressive 루프를 펼친 모습. step 1(prefill)은 프롬프트 5개를 한꺼번에 계산한다. step 2부터(decode)는 새 token 1개만 모델에 넣고, 앞의 token들은 KV-cache에 저장된 K, V를 재사용한다(점선). stop token이 나오면 루프를 끝낸다. (그림은 개념도다. 실제 chat 모델은 앞뒤에 template token이 더 붙는다, 6.6절.)

1.5 핵심 관찰 — 매 token마다 가중치 전부를 읽는다#

decode step 하나를 보자. 입력은 벡터 하나([1, d])다. 이것이 30개 블록을 지나는 동안 모든 Linear 가중치 행렬과 한 번씩 곱해진다. 즉 token 하나를 만들 때마다 모델 가중치 거의 전부(embedding 표 조회만 예외 — 한 행만 읽는다)를 DRAM에서 읽어야 한다.

말로 하면: 가중치 1바이트(INT8)를 읽어서 곱셈-덧셈 1번(2 FLOP)만 하고 버린다. arithmetic intensity(연산/바이트, D3)가 약 2 FLOP/byte다. NPU의 ridge point는 보통 수십~수백 FLOP/byte이므로 decode는 연산기가 놀고 메모리 버스만 바쁜 상태, 즉 memory-bound다.

펌웨어로 비유하면 이렇다. 매 명령마다 flash 전체를 한 번 훑어야 하는 상태 머신이 있다면, CPU 클럭을 올려도 빨라지지 않는다. flash 읽기 속도가 상한이다. decode의 tokens/s가 딱 그렇다. 4절에서 이 상한을 숫자로 계산하고, 7절에서 prefill은 왜 다른지 본다. 더 깊은 성능 모델은 D5에서 다룬다.

2. SLM 지형 — 2024~2025년의 작은 모델들#

2.1 SLM이란#

정해진 정의는 없지만 업계에서 대략 0.1B~4B 파라미터의 모델을 Small Language Model(SLM)이라고 부른다. "폰·노트북·웨어러블에서 돌릴 수 있는 크기"라는 뜻이다. 대표 계열은 다섯 개다.

2.2 config로 확인하기 [config/tokenizer]#

모든 Hugging Face 모델에는 config.json이 있고, 여기에 구조 숫자가 전부 들어 있다. 가중치(수백 MB~수 GB)를 받지 않고 config(수 KB)만 받아서 표를 만드는 코드다. Meta와 Google 원본 저장소는 약관 동의가 필요한 gated repo라서, 같은 파일을 공개로 올려 둔 unsloth/ 미러를 썼다.

열의 뜻: L = decoder block 수, d = hidden size, ffn = MLP 중간 크기, H = query head 수, KV = key/value head 수(GQA, B4), hd = head 하나의 차원, vocab = 어휘 크기, ctx = config의 max_position_embeddings, tied = embedding과 LM head 공유 여부.

표를 읽는 법:

  • 파라미터 수는 모두 3절의 방법(가중치 없이 모델 뼈대만 만들어 numel() 합산)으로 센 값이다.

2.4 흔한 함정#

  • "1B 모델 = 1 GB"라고 외우면 틀린다. 1B 파라미터 × 2바이트(FP16) = 2 GB다. INT4면 약 0.5~0.6 GB다. 단위를 반드시 적는다.
  • Phi-3.5-mini처럼 tied = False인 모델은 embedding과 LM head가 따로 있어서 vocab × d 행렬이 두 개다.

3. 파라미터 수 — config에서 손으로 세기#

3.1 공식#

B1·B4에서 본 부품별 가중치 모양을 그대로 더하면 된다. bias는 대부분의 최신 LLM에서 없다(Qwen2.5의 q·k·v bias는 예외).

말로 하면: "vocab 표 한 장 + 블록 L개 × (attention 행렬 4장 + MLP 행렬 3장 + norm 벡터 2개) + 출력 쪽"이다. 주의할 점 하나: attention 행렬 크기는 d가 아니라 H·hd로 쓴다. 대부분 H·hd = d지만 Qwen3-0.6B는 d = 1024인데 H·hd = 16 × 128 = 2048이다.

3.2 손으로 계산: SmolLM2-135M#

config: V = 49152, d = 576, L = 30, H = 9, KV = 3, hd = 64, ffn = 1536, tied.

1.3절에서 실제 가중치로 센 134,515,008과 정확히 같다. 블록 하나에서 MLP가 2.65M, attention이 0.88M으로 MLP가 attention의 3배다. GQA 덕분에 W_k, W_v가 W_q의 1/3 크기인 것도 보인다.

3.3 코드로 확인: 공식 vs 실제 모델 9종 [config/tokenizer]#

공식을 함수로 만들고, 가중치 없이 모델 뼈대만 만드는 torch.device("meta")로 실제 구현의 파라미터 수와 비교한다. meta device는 텐서의 shape만 있고 메모리를 할당하지 않는다 — 링커 map 파일로 섹션 크기만 보는 것과 같다.

출력에서 볼 것: 9개 모델 모두 공식과 실제가 한 자리까지 일치한다. 모델별 차이(Qwen2.5의 bias, Qwen3·Gemma3의 q_norm·k_norm, Gemma3의 norm 4개)는 함수 안 if 세 줄로 충분했다. Phi-4-mini는 q·k·v를 한 행렬(qkv_proj)로, gate·up을 한 행렬(gate_up_proj)로 합쳐 두었지만 원소 수는 같다.

3.4 embedding 표가 차지하는 비율#

그림 3 — 전체 파라미터 중 embedding 표(주황)의 비율. 작은 모델에 큰 vocab을 붙이면 비율이 급격히 커진다. Gemma-3-270M은 vocab 262,144 × d 640 = 1억 6,777만으로 모델의 62.6%가 단어표다.

이 그림이 말하는 것:

  • 작은 모델일수록 vocab이 비싸다. 블록 쪽 파라미터는 d²에 비례해 줄지만 embedding은 V × d로 d에만 비례한다. d가 작아져도 V는 그대로라서 비율이 커진다.
  • embedding 표는 decode 때 "읽는 양"이 특이하다. 입력 쪽 조회는 token 하나당 한 행(d개)만 읽는다. 하지만 tied 모델에서는 같은 행렬이 LM head로도 쓰이고, LM head는 [d] × [d, V] GEMV라서 표 전체를 매 token 읽는다. 그래서 tied든 untied든 decode의 메모리 트래픽에는 V × d가 한 번 들어간다.
  • 양자화 때 따로 취급한다. 많은 런타임이 embedding·LM head를 다른 블록보다 높은 정밀도(예: INT8 또는 FP16)로 둔다. 큰 vocab 모델에서는 이 결정이 전체 크기에 크게 영향을 준다(C3, F3).

4.3 활성값(activation) scratch#

decode 때 한 번에 살아 있는 중간 텐서는 작다. 입력이 [1, d] 하나이기 때문이다.

prefill은 다르다. 프롬프트 S개를 한꺼번에 처리하므로 S × ffn 크기 텐서가 생긴다. S = 512면 512 × 8192 × 2(gate, up) × 2 B = 16 MiB 정도이고, attention 점수를 통째로 만들면 H × S × S로 커진다. 그래서 런타임은 prefill을 chunk 단위(예: 128~512 token)로 나눠 scratch 상한을 고정한다. 펌웨어의 DMA 버퍼를 최대 전송 크기로 잘라서 쓰는 것과 같은 발상이다(D2).

4.6 이 Mac에서 재 보기 — 상한과 실측의 차이 [모델 필요]#

SmolLM2-135M을 FP32로 CPU에서 돌리면 token당 가중치 읽기는 134.5M × 4 B = 538 MB다. Apple M2의 메모리 대역폭 사양 100 GB/s로 나누면 상한 약 186 tok/s다. 실제는 어떤가? 먼저 "가중치 GEMV만" 따로 떼어 잰다. 모델의 모든 Linear 가중치(lm_head 포함)에 벡터 하나를 곱하는 시간이다.

출력에서 볼 것:

  • Linear 211개 = 30블록 × 7 + lm_head 1. 이것만으로 token당 약 14 ms이고 실효 대역폭은 약 38 GB/s다. PyTorch CPU 백엔드가 4개 스레드로 GEMV를 돌릴 때 사양 대역폭(100 GB/s)의 약 40%만 쓰고 있다.
  • 7절의 전체 생성 루프에서는 TPOT이 약 18 ms(57 tok/s)로 측정된다. GEMV 14 ms + attention·RMSNorm·RoPE·Python 호출 오버헤드 약 4 ms로 설명된다.
  • 즉 순서가 맞다: 대역폭 상한(186) > GEMV만(71) > 전체 루프(57). 실측이 상한을 넘으면 계산을 의심해야 한다.
  • 측정 당시 이 Mac에서 다른 작업이 같이 돌고 있어(load average 5~8) 실행마다 값이 ±30% 정도 흔들렸다. 벤치마크는 여러 번 재고 중앙값을 쓴다(M2).

실무 연결: 기기 bring-up 때 "llama.cpp에서 몇 tok/s 나왔다"는 숫자를 받으면 먼저 대역폭 ÷ 모델 바이트로 상한을 계산해서 비교한다. 상한의 60~80%면 정상, 20%면 어딘가 CPU fallback이나 잘못된 스레드 설정이 있다(F3, F8). 이 계산이 PJ3 프로젝트의 핵심 산출물이다.

5.2 BPE — 가장 자주 붙어 다니는 쌍을 합친다#

BPE(Byte Pair Encoding)의 학습 절차:

  1. 모든 단어를 문자 단위로 쪼갠다. 단어 끝에 표시(_)를 붙인다.
  2. 말뭉치 전체에서 인접한 두 기호 쌍의 빈도를 센다.
  3. 가장 많은 쌍 하나를 새 기호로 합친다(merge). 이 merge 규칙을 순서대로 기록한다.
  4. 원하는 vocab 크기가 될 때까지 2–3을 반복한다.

인코딩(학습 후 새 단어 쪼개기)은 학습된 merge를 학습된 순서대로 적용한다.

말뭉치: low×5, lower×2, newest×6, widest×3.

5.8 토크나이저 함정#

  • 토크나이저와 모델은 한 쌍이다. 다른 모델의 토크나이저로 id를 만들면 오류 없이 헛소리가 나온다. 펌웨어로 치면 레지스터 맵 버전이 다른 헤더로 빌드한 것과 같다.
  • token을 하나씩 decode하면 한글이 깨진다. 6.7절에서 본다.
  • 앞 공백이 token의 일부다. " Paris"와 "Paris"는 다른 id다. 프롬프트 끝에 공백을 붙이면 모델이 이상한 분포를 낸다.

6. 생성 — logits에서 token 하나 고르기#

6.1 sampler의 위치#

모델은 매 step마다 logits 벡터(길이 V)를 낸다. sampler는 이것을 받아 정수 하나를 돌려주는 작은 C 함수다. 모델보다 훨씬 작지만 출력 품질(반복, 헛소리, 다양성)을 크게 좌우한다. 처리 순서는 보통 이렇다.

6.2 greedy — 항상 1등#

argmax(logits). 결정적이고 가장 단순하다. 단점: 같은 구절을 반복하는 루프에 잘 빠진다("I think that I think that …"). 사실 확인·분류·짧은 명령 파싱처럼 정답이 하나인 작업에는 greedy가 맞다.

6.3 temperature — 분포의 뾰족함 (A2 10절 복습)#

p = softmax(z / T). T < 1이면 1등에 확률이 몰리고, T > 1이면 평평해진다. T → 0이면 greedy와 같다. argmax는 바뀌지 않는다.

6.4 top-k와 top-p (nucleus)#

  • top-k: 확률 상위 k개만 남기고 나머지를 0으로 만든 뒤 다시 정규화한다. k가 고정이라 분포 모양을 무시한다. 확신이 큰 상황(1등이 0.99)에서도 k개를 억지로 남기고, 애매한 상황(비슷한 후보 50개)에서도 k개만 남긴다.
  • top-p: 확률을 큰 순서로 누적해서 누적합이 p 이상이 되는 최소 집합만 남긴다. 확신이 크면 1~2개만, 애매하면 많이 남긴다. 분포에 적응한다.

6.5 repetition penalty#

이미 나온 token의 logit을 깎아서 반복을 줄인다. Hugging Face 방식(CTRL 논문에서 온 것): 이미 나온 token의 logit이 양수면 ÷ penalty, 음수면 × penalty. 1.1~1.3 정도를 쓴다. 너무 크면 "the", "." 같은 필수 token까지 피해서 문장이 망가진다. 비슷한 것으로 frequency/presence penalty(나온 횟수만큼 빼기)가 있다.

7. prefill vs decode — TTFT와 TPOT#

7.1 정의#

  • prefill: 프롬프트 S개 token을 한꺼번에 모델에 넣어 KV-cache를 채우고 첫 logits를 얻는 단계. 행렬 × 행렬(GEMM, [S, d] × [d, d'])이다. 가중치를 한 번 읽어서 S번 재사용하므로 arithmetic intensity가 S배 높다 → compute-bound.
  • decode: 이후 token을 하나씩 만드는 단계. 행렬 × 벡터(GEMV)다 → memory-bound (1.5절).
  • TTFT (Time To First Token): 요청부터 첫 token이 나올 때까지. ≈ tokenize + prefill + 첫 sampling. 사용자가 느끼는 "반응 속도"다.
  • TPOT (Time Per Output Token): 두 번째 token부터 token 하나당 평균 시간. 1 / TPOT = decode tokens/s. 사용자가 느끼는 "말하는 속도"다.

그림 6 — prefill과 decode의 시간표(SmolLM2-135M, 프롬프트 512 token, 아래 예제의 실측값으로 축척). prefill은 긴 블록 하나로 가중치를 한 번 읽어 512번 재사용한다. decode는 짧은 호출을 반복하고, 매번 가중치 전체와 KV-cache를 다시 읽는다. 위 줄은 연산 유닛이 얼마나 바쁜지, 아래 줄은 DRAM이 얼마나 바쁜지를 개념적으로 나타낸다.

7.2 코드로 확인: KV-cache를 쓰는 수동 생성 루프 [모델 필요]#

model.generate() 대신 루프를 직접 써서 prefill과 decode를 따로 잰다. past_key_values가 KV-cache 객체다. 프롬프트 길이를 128 / 512 / 2048로 바꿔 TTFT와 TPOT이 어떻게 변하는지 본다. 앞의 두 줄은 stop token을 확인하지 않은 루프와 확인한 루프의 출력 비교다.

출력에서 볼 것:

  • stop token: 확인하지 않은 루프는 <|im_end|> 뒤에도 계속 가짜 대화(<|im_start|>system …)를 만들어 낸다. 확인한 루프는 정확히 거기서 멈춘다. 이 버그는 제품에서 "기기가 혼자 계속 떠든다"로 나타난다.
  • 프롬프트가 37 token인 이유: SmolLM2의 chat template은 system 메시지를 주지 않으면 기본 system prompt("You are a helpful AI assistant named SmolLM, trained by Hugging Face")를 자동으로 넣는다.
  • TTFT는 프롬프트 길이에 거의 비례한다: 128 → 512 → 2048 token에서 79 → 302 → 2609 ms. 2048에서 비례 이상으로 늘어난 것은 attention의 S² 항 때문이다(prefill 처리량이 1,695 → 785 tok/s로 떨어짐).
  • TPOT은 context가 길어질수록 천천히 는다: 19 → 23 → 41 ms. 가중치 읽기(고정)에 KV-cache 읽기(context에 비례)가 더해지기 때문이다. 4.5절 식의 "+ KV 바이트" 항이 실측으로 보인다.
  • prefill 처리량(최대 약 1,700 tok/s)이 decode 처리량(약 57 tok/s)보다 30배 높다. 같은 하드웨어, 같은 가중치인데 이만큼 차이 나는 이유가 바로 GEMM vs GEMV(재사용 여부)다.
  • CPU 측정값은 실행마다 ±30% 정도 흔들렸다(4.6절). 절대값보다 추세를 본다.

7.3 임베디드 연결 — 음성 비서의 지연 예산#

"예를 들어 Hark 같은 웨어러블 음성 비서라면" 사용자가 말을 끝낸 뒤 첫 음성이 나오기까지의 예산은 대략 수백 ms~1초다(L4에서 자세히). 그 안에 ASR 마무리, LLM TTFT, TTS 첫 청크가 들어가야 한다. 그래서:

  • TTFT를 줄이는 손잡이: 프롬프트를 짧게(system prompt 축소), system prompt KV-cache 재사용(prompt caching), prefill을 NPU(연산이 강한 곳)에서, 한국어 효율이 좋은 토크나이저.
  • TPOT을 줄이는 손잡이: 가중치 비트 수 줄이기(INT4), KV-cache 양자화, 메모리 대역폭이 큰 경로, speculative decoding(L6).

prefill은 연산, decode는 대역폭 — 두 단계의 병목이 다르다는 것이 D5 전체의 출발점이다.

8. SLM은 어떻게 만들어지나#

모델을 직접 학습시킬 일은 드물지만, 모델팀과 대화하고 "이 모델에 무엇을 기대할 수 있는지" 판단하려면 단계를 알아야 한다.

8.1 학습 단계#

단계데이터목적비유
Pretraining웹·책·코드 수조 token (예: SmolLM2-1.7B는 약 11T token이라고 보고)다음 token 예측으로 언어·지식 습득ROM에 기본 지식 굽기

선호 학습 (RLHF / DPO)같은 질문에 대한 (좋은 답, 나쁜 답) 쌍사람이 선호하는 답으로 기울이기QA 피드백 반영

  • Base vs Instruct: SmolLM2-135M은 pretraining만 한 base 모델, SmolLM2-135M-Instruct는 SFT와 선호 학습을 거친 모델이다. base 모델에 chat template을 넣으면 대화가 잘 안 된다. 기기에 넣는 것은 거의 항상 instruct 버전이다.
  • RLHF: 선호 데이터로 reward model을 따로 학습하고, 그 점수를 높이도록 강화학습(PPO 등)으로 LLM을 조정한다. 구성 요소가 많고 불안정하다.
  • DPO (Direct Preference Optimization): reward model 없이, 선호 쌍에서 "좋은 답의 log-likelihood는 올리고 나쁜 답은 내리는" loss를 직접 최소화한다. 훨씬 단순해서 작은 모델에 많이 쓴다.
  • Distillation (C5): 작은 모델을 처음부터 혼자 학습시키는 대신, 큰 모델이 낸 확률분포(soft label)를 따라 하도록 학습한다. Meta는 Llama 3.2 1B/3B를 만들 때 더 큰 Llama 3.1 모델에서 pruning한 뒤 그 큰 모델들의 출력(logits)으로 distillation했다고 발표했다. Gemma 2의 작은 모델들도 distillation으로 학습했다고 보고됐다. 서버의 큰 모델 → 기기의 작은 모델이라는 경로는 Hark 같은 회사에도 자연스러운 선택이다(추정).

8.2 LoRA — 작은 추가 행렬로 fine-tuning#

제품에 맞게 모델을 조금 바꾸고 싶을 때(예: 기기 명령 형식, 회사 말투) 모든 가중치를 다시 학습하면 비싸고, 모델 파일도 통째로 새로 배포해야 한다. LoRA (Low-Rank Adaptation)는 원래 가중치 W를 얼리고, 옆에 작은 두 행렬을 붙여 그것만 학습한다.

말로 하면: 변화량 ΔW를 "rank r짜리 행렬"로 제한한다. A1에서 본 SVD의 관점으로, 학습으로 생기는 가중치 변화는 대개 소수의 방향(큰 특이값 몇 개)에 몰려 있으므로 rank r로 근사해도 충분하다는 가정이다.

손으로 계산: d_in = d_out = 576, r = 8 → 원래 576 × 576 = 331,776, LoRA 8 × (576 + 576) = 9,216 (2.8%).

9. 멀티모달 입력 — 음성과 이미지를 token으로#

9.1 구조: encoder → projector → "가짜 token"#

LLM은 embedding 벡터 열만 받는다. 텍스트가 아닌 입력을 넣으려면 그것을 LLM의 embedding 공간(d차원) 벡터 열로 바꾸면 된다.

  • encoder: 음성·이미지를 특징 벡터 열로 바꾸는 별도 신경망. 보통 사전학습된 것을 가져다 쓴다.
  • projector: encoder 출력 차원을 LLM의 d로 맞추는 작은 MLP(또는 Linear). 학습은 주로 이 부분과 LLM 쪽에서 한다.
  • LLM 입장에서는 이 벡터들이 그냥 "특이한 token들"이다. attention·KV-cache·prefill 비용도 텍스트 token과 똑같이 든다.

9.2 token 예산 계산#

  • 이미지: 패치 크기 14인 ViT에 336 × 336 이미지를 넣으면 (336 / 14)² = 24² = 576 패치다. LLaVA-1.5가 이 구성이라 이미지 한 장이 576 token이다. Llama-3.2-1B급 KV로 치면 576 × 32 KiB = 18 MiB이고, 4.6절 CPU 측정의 prefill 속도(1,700 tok/s, 135M 기준)로도 0.3초가 넘는다. 그래서 edge VLM은 이미지 token을 pooling으로 줄이는 설계를 많이 쓴다.
  • 음성: Whisper encoder는 30초 입력을 1,500 프레임(초당 50 프레임)으로 만든다. 그대로 넣으면 10초 발화가 500 token이다. projector에서 4배 pooling하면 125 token이 된다(가정한 설계 예시).
  • 비교: 같은 10초를 ASR로 먼저 텍스트로 바꾸면 영어 기준 약 25단어(분당 150단어 가정) ≈ 30~35 token이다. ASR → 텍스트 → LLM cascade가 token 수로는 훨씬 싸다. 대신 억양·감정·화자 정보가 사라진다. 이 trade-off가 L4의 설계 질문이다.

9.3 임베디드 연결#

  • encoder는 LLM과 별도로 돌기 때문에 다른 가속기에 올릴 수 있다. 예: 오디오 encoder는 DSP/NPU에서 스트리밍으로, LLM decode는 대역폭이 큰 경로에서.
  • 멀티모달 token은 prefill 길이를 늘리므로 TTFT에 직접 더해진다. 카메라 한 장 = 텍스트 수백 단어짜리 프롬프트와 같다.

11. 임베디드 관점에서 다시 보기#

  • 메모리 레이아웃: 가중치는 읽기 전용이라 파일을 mmap해서 페이지 캐시로 공유하는 것이 표준이다(llama.cpp GGUF, F3). KV-cache는 쓰기 버퍼라서 context 상한만큼 미리 잡아 두는(정적 할당) 방식과 페이지 단위로 늘리는 방식(paged KV, D5)이 있다. 펌웨어의 정적 arena vs 동적 풀 선택과 같다.
  • 대역폭이 1순위 사양이다: decode tokens/s는 TOPS가 아니라 GB/s로 결정된다. NPU TOPS 경쟁표보다 LPDDR 버스 폭·속도·실효 효율을 먼저 본다(E7, M1).
  • 전력: DRAM 접근 에너지가 연산 에너지보다 훨씬 크다(D7). decode는 token마다 수백 MB를 읽으므로, 생성 token 수를 줄이는 것(짧은 답 지시, 조기 종료)이 곧 배터리 절약이다.
  • 정밀도: 가중치 INT4, 활성값 FP16(W4A16)이 기기 SLM의 기본 조합이다. embedding·LM head·KV-cache의 정밀도는 따로 결정한다(C3).
  • sampler와 detokenizer는 C 코드다: 6.7절처럼 수십 줄이지만 UTF-8 버퍼링, stop token, 최대 길이 제한(watchdog), 반복 감지 같은 안전장치가 여기에 들어간다. 모델이 끝없이 생성하는 상황을 펌웨어가 끊어야 한다.
  • KV-cache가 꽉 차면: context 상한에 도달했을 때의 동작(오래된 대화 버리기, sliding window, 요약 후 재시작)을 정해 두지 않으면 긴 대화에서 크래시나 OOM이 난다(L2).

13. 면접에서 이렇게 말한다#

Q. "How much memory does a 1B model need at int4 with a 4K context?"

A. 가중치: 1.24B × 4.5 bit(group scale 포함) ≈ 0.66 GiB. KV-cache: Llama-3.2-1B 기준 2 × 16층 × 8 KV head × 64 × 2 B = 32 KiB/token, 4K면 128 MiB. 여기에 scratch·런타임 수십 MB를 더해 약 0.8~0.9 GiB. GQA가 없었다면 KV만 512 MiB였을 것이다.

Weights are about 1.24 billion parameters at roughly 4.5 bits including group scales, so around 0.66 GiB. The KV cache for Llama 3.2 1B is two times 16 layers times 8 KV heads times 64 dims times 2 bytes, which is 32 KiB per token, or 128 MiB at 4K context. Add some tens of megabytes for activations and runtime buffers, and you land around 0.8 to 0.9 GiB. Without GQA the KV cache alone would have been four times larger.

Q. "Why is LLM decode memory-bound?"

A. decode는 token 하나를 만들 때 입력이 벡터 하나라서 모든 Linear가 GEMV다. 가중치 1바이트를 읽어 곱셈-덧셈 한두 번만 하고 버리므로 arithmetic intensity가 약 2 FLOP/byte로, 어느 가속기의 ridge point보다 훨씬 낮다. 그래서 tokens/s 상한 ≈ 대역폭 ÷ (가중치 + KV 바이트). 제가 SmolLM2-135M으로 재 보니 prefill은 1,700 tok/s, decode는 57 tok/s로 30배 차이가 났다. prefill은 가중치를 S번 재사용하는 GEMM이라 compute-bound다.

In decode each step processes a single token, so every linear layer is a matrix-vector product. You read each weight once and do about two flops with it, which gives an arithmetic intensity around two flops per byte, far below any accelerator's ridge point. So the ceiling is memory bandwidth divided by the bytes of weights plus KV cache per token. When I measured a 135M model on CPU, prefill ran about thirty times faster per token than decode, because prefill is a GEMM that reuses each weight across the whole prompt.

Q. "Top-p vs top-k?"

A. top-k는 항상 상위 k개를 남기고, top-p는 누적확률이 p를 넘는 최소 집합을 남긴다. top-p는 분포 모양에 적응한다 — 모델이 확신하면 후보 1~2개, 애매하면 많이. 실무에서는 temperature + top-p(0.9 전후)가 흔하고, top-k는 큰 vocab에서 계산량을 제한하는 상한으로 함께 쓴다. 정답이 하나인 작업(명령 파싱)은 greedy가 맞다.

Top-k always keeps a fixed number of candidates, while top-p keeps the smallest set whose cumulative probability reaches p, so it adapts to how confident the model is. When the distribution is peaked it keeps one or two tokens, when it's flat it keeps many. In practice I'd use temperature with top-p around 0.9, possibly with a top-k cap to bound the sorting cost on a large vocabulary, and plain greedy for tasks with a single right answer like command parsing.

Q. "Why does Korean use more tokens than English?"

A. 토크나이저의 merge 규칙은 학습 말뭉치 빈도로 만들어지는데, 대부분 영어 중심이라 한글 조각이 vocab에 적다. vocab에 없는 글자는 UTF-8 바이트(한 글자 3바이트)로 쪼개진다. 실제로 같은 뜻의 문장이 영어 16 token일 때 한국어는 SmolLM2 77, Llama 3.2 25, Gemma 3 22 token이었다. 그래서 한국어 제품은 token/s가 아니라 글자/s로 비교하고, vocab이 큰 다국어 모델을 고려한다.

Tokenizer merges are learned from corpus frequency, and most corpora are English-heavy, so Korean syllables are underrepresented in the vocabulary. Anything missing falls back to UTF-8 bytes, three per Hangul syllable. On the same sentence I measured 16 English tokens versus 77 Korean tokens on SmolLM2, 25 on Llama 3.2, and 22 on Gemma 3. That directly scales prefill time, KV cache size and characters per second, so for a Korean product I'd compare models in characters per second, not tokens per second.

Q. "How would you pick an SLM for a wearable?"

A. 숫자에서 역산한다. (1) LLM에 줄 수 있는 DRAM에서 KV-cache(목표 context)와 scratch를 빼서 가중치 상한, (2) 목표 응답 속도와 메모리 대역폭에서 token당 바이트 상한, (3) 제품 언어의 token 효율, (4) 그 SoC의 NPU 런타임 지원, (5) license. 그 안에 드는 후보(보통 0.5~1B INT4)를 실제 제품 프롬프트로 평가한다. 어려운 요청은 클라우드로 보내는 hybrid 라우팅을 전제로 기기 모델의 역할 범위를 좁힌다.

I'd work backwards from the budgets. Take the DRAM available to the model, subtract the KV cache for the target context and the activation scratch, and that caps the weight size. Take the target response speed and the memory bandwidth, and that caps bytes per token. Then check token efficiency in the product's language, whether the SoC's NPU runtime supports the architecture, and the license. Among the candidates that fit, usually half a billion to one billion parameters at int4, I'd evaluate on real product prompts, and I'd scope the on-device model narrowly with hybrid routing to the cloud for hard requests.

Q. "What determines TTFT versus TPOT?"

A. TTFT는 프롬프트 길이 × prefill 속도(연산 성능)에 좌우되고, 긴 프롬프트에서는 attention의 S² 항이 더해진다. TPOT은 token당 읽는 바이트(가중치 + 현재 KV) ÷ 대역폭에 좌우된다. 측정해 보니 프롬프트 128 → 2048에서 TTFT는 79 → 2,609 ms, TPOT은 19 → 41 ms였다. 줄이는 방법도 다르다 — TTFT는 짧은 프롬프트·prompt caching·NPU prefill, TPOT은 양자화·KV 압축·speculative decoding.

Time to first token is driven by prompt length times prefill throughput, which is compute bound, with a quadratic attention term for long prompts. Time per output token is driven by bytes read per step, weights plus the current KV cache, divided by memory bandwidth. In my measurement, going from a 128 to a 2048 token prompt raised TTFT from about 80 milliseconds to 2.6 seconds, while TPOT only went from 19 to 41 milliseconds. The fixes differ too: shorter prompts, prompt caching and NPU prefill for TTFT; quantization, KV compression and speculative decoding for TPOT.

16. 요약 & 체크리스트#

LLM 추론은 tokenizer → embedding 표 → decoder block N개 → LM head → sampler로 이어지는 루프다. 매 decode step마다 가중치 거의 전부를 DRAM에서 읽으므로 decode는 memory-bound이고, tokens/s 상한은 대역폭 ÷ (가중치 바이트 + KV 바이트)다. 파라미터 수는 config에서 V·d + L·(attention 4행렬 + SwiGLU 3행렬 + norm) + (untied면 V·d)로 정확히 셀 수 있고, 작은 모델에서는 embedding 표가 20~60%를 차지한다. KV-cache는 2·L·KV·hd·바이트·context이며 INT4 가중치에서는 가중치에 맞먹을 만큼 커진다. 토크나이저(BPE)는 말뭉치 빈도로 만들어지기 때문에 한국어는 영어보다 1.4~4.8배 많은 token을 쓴다. sampler는 temperature·top-k·top-p·repetition penalty로 분포를 다듬어 하나를 고르고, stop token·chat template·UTF-8 스트리밍 처리가 제품 품질을 좌우한다. prefill(TTFT)은 연산, decode(TPOT)는 대역폭이 병목이다. 웨어러블급 기기에서는 0.5~1B INT4가 현실적이고, 나머지는 클라우드와 나누는 hybrid 구조가 된다.
