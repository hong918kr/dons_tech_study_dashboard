0. 큰 그림 — 이게 왜 필요한가#

edge 기기에서 실제로 도는 모델을 모아 보면 CNN이 가장 많다. 이유는 단순하다. 센서 데이터는 "가까운 것끼리 관련 있다" — 시간적으로 붙어 있는 IMU 샘플, 주파수·시간으로 붙어 있는 스펙트로그램 칸, 공간적으로 붙어 있는 픽셀. conv는 이 성질을 구조로 박아 넣은 레이어라서 적은 파라미터로 잘 배운다. 그리고 연산이 규칙적인 MAC 루프라서 DSP·NPU가 좋아한다.

예를 들어 Hark 같은 웨어러블이라면(추정), 다음 세 경로가 모두 CNN 계열일 가능성이 높다.

1. 합성곱의 직관 — 2D로 확장한 FIR 필터#

1.1 dense layer로는 왜 안 되나 — locality와 weight sharing#

B1의 dense(fully-connected) layer는 입력 원소 전부와 출력 원소 전부를 연결한다. 56×56 크기, 채널 32개인 feature map(= 100,352개 숫자)을 같은 크기, 채널 64개(= 200,704개)로 바꾸는 dense layer를 생각해 보자.

말로 하면: conv는 두 가지 가정을 해서 파라미터를 백만 배 넘게 줄인다.

  • locality(국소성): 출력 한 칸은 입력의 가까운 영역(3×3) 만 본다. 멀리 있는 픽셀과의 연결은 버린다.
  • weight sharing(가중치 공유): 그 3×3 필터를 모든 위치에서 똑같이 쓴다. 왼쪽 위의 edge 검출기와 오른쪽 아래의 edge 검출기가 같은 계수다.

FIR 필터가 정확히 이 두 성질을 가진다. 탭 수가 유한하고(locality), 계수가 시간에 따라 바뀌지 않는다(시불변 = weight sharing). 그래서 conv는 "학습되는 FIR 필터 뱅크"라고 기억하면 된다. 이 가정 덕분에 생기는 성질이 translation equivariance다 — 입력을 한 칸 밀면 출력도 한 칸 밀린다. 제스처가 창의 앞에서 일어나든 뒤에서 일어나든 같은 필터가 반응한다.

1.4 함정#

  • conv 가중치를 외부 도구와 주고받을 때 뒤집힘(flip) 여부를 확인하지 않으면, 대칭 필터에서는 멀쩡하다가 비대칭 필터에서만 결과가 틀린다. 테스트 벡터에 비대칭 kernel을 꼭 넣는다.
  • "conv = 이미지 전용"이 아니다. 1D(시간), 2D(시간×주파수 스펙트로그램), 3D(비디오)까지 같은 연산이다.
  • weight sharing은 "위치가 중요하지 않다"는 가정이다. 위치 자체가 정보인 문제(예: 센서가 창의 어느 시점에 튀었는지가 중요)라면 뒤에서 풀링 방식이나 구조를 바꿔야 한다 (9절에서 실제로 부딪힌다).

2. 출력 크기 — stride, padding, dilation#

2.1 세 가지 손잡이#

  • stride s: 창을 한 번에 몇 칸 옮기나. s = 2면 출력이 대략 절반. DSP의 decimation과 같다.
  • padding p: 입력 가장자리에 0을 몇 칸 두르나. 가장자리 정보 손실을 막고 출력 크기를 맞춘다.
  • dilation d: kernel 탭 사이를 몇 칸씩 벌리나. d = 2인 3탭 필터는 x[t], x[t+2], x[t+4]를 본다. 탭 수(MAC 수)는 그대로인데 보는 범위가 넓어진다. 희소 탭 FIR과 같다.

2.2 공식 유도#

한 축(H 또는 W)만 보자. 입력 길이 n, kernel k, stride s, padding p, dilation d.

말로 하면: "패딩한 길이에서 유효 kernel 폭을 빼고, 남는 여유를 stride로 나눈 몫 + 1"이다. 나머지는 버린다(floor). 그래서 stride 2에 홀수 입력이면 마지막 줄이 계산에 안 쓰일 수 있다.

2.4 임베디드 연결과 함정#

  • TensorFlow/TFLite의 SAME 패딩은 비대칭일 수 있다. stride 2에서 필요한 패딩 총량이 홀수면 TF는 오른쪽·아래에 한 칸 더 넣는다. PyTorch의 padding=1은 항상 대칭이다. 그래서 PyTorch → TFLite 변환에서 stride 2 conv 출력이 한 픽셀씩 밀려 정확도가 조금 떨어지는 사고가 난다. 레이어별 diff에서 stride 2 레이어부터 어긋나면 이걸 의심한다.
  • 출력 크기를 잘못 계산하면 펌웨어에서 버퍼 오버런이다. 정적 arena를 쓰는 MCU 런타임은 컴파일 시점에 shape을 확정하므로, 입력 해상도를 바꾸면 반드시 전체 shape을 다시 계산해야 한다.
  • floor 때문에 stride 2를 여러 번 거치면 크기가 입력의 정확히 1/2ⁿ이 아닐 수 있다 (예: 7 → 4 → 2 → 1). skip connection으로 두 텐서를 더할 때 크기 불일치 에러의 흔한 원인이다.

3. 채널 — 가중치 shape, 파라미터 수, MAC 수#

3.1 필터 뱅크로서의 conv#

실제 conv 레이어는 입력 채널이 여러 개다 (RGB 3, IMU 6, 중간 feature map 32…). 출력 채널 하나를 만드는 필터 하나는 모든 입력 채널을 동시에 본다. 즉 필터 하나의 모양은 [C_in, kH, kW]이고, 출력 한 칸은 이 C_in·kH·kW개 숫자와 입력 창의 내적이다 (A1의 dot product). 이런 필터가 C_out개 있으면 출력 채널이 C_out개다.

말로 하면: 출력 채널 o의 (i, j) 칸 = 편향 + (모든 입력 채널 × 3×3 창)과 필터 o의 내적. 펌웨어 관점에서는 "C_out개 탭 세트를 가진 다채널 FIR 필터 뱅크"다.

그림 3 — 3×3 conv, 32 → 64 채널, 56×56. 필터 하나는 입력의 3×3×32 기둥을 보고 출력의 한 칸을 만든다. 필터 64개가 출력 채널 64개를 만든다.

3.2 파라미터와 MAC 공식#

말로 하면: 파라미터는 해상도와 무관하고, MAC은 출력 해상도에 비례한다. 그래서 CNN은 "파라미터는 작은데 연산은 많은" 모델이다 (B1의 dense layer는 파라미터 하나가 샘플당 MAC 한 번에만 쓰인다. conv는 파라미터 하나가 H_out·W_out번 재사용된다).

MAC과 FLOP은 2배 차이가 난다. 자료마다 섞어 쓰므로 숫자를 볼 때 어느 쪽인지 반드시 확인한다 (D1에서 다시 다룬다).

3.4 임베디드 연결과 함정#

  • bias는 흔히 없다. conv 뒤에 BatchNorm이 오면 bias가 BN의 β와 중복이라 bias=False로 만든다. 배포 때는 B1의 BN folding으로 BN을 conv 가중치·bias에 합쳐서, 기기에서는 bias 있는 conv 하나만 돈다.
  • 가중치 레이아웃이 런타임마다 다르다. PyTorch는 [C_out, C_in, kH, kW](OIHW), TFLite Conv2D는 [C_out, kH, kW, C_in](OHWI)다. 헤더를 직접 생성할 때 순서를 틀리면 에러 없이 틀린 답이 나온다 (A6의 endianness 사고와 같은 종류).
  • 파라미터가 작다고 빠른 게 아니다. 3×3 conv 18 K 파라미터가 57.8 M MAC을 만든다. MCU에서 "모델 크기(flash)"와 "지연시간(MAC)"은 서로 다른 예산이다.

4. Receptive field와 pooling#

4.1 receptive field란#

receptive field(RF, 수용 영역) 는 출력 한 칸이 "볼 수 있는" 입력 영역의 크기다. 3×3 conv 하나의 출력은 입력 3×3을 본다. 그 위에 3×3 conv를 하나 더 쌓으면, 두 번째 층의 한 칸은 첫 층의 3×3을 보고, 그 각각이 입력 3×3을 보므로 합쳐서 입력 5×5를 본다.

그림 4 — 1D로 그린 receptive field. k = 3 conv를 세 층 쌓으면 맨 위 한 칸이 입력 7칸에 의존한다. 층마다 (k − 1) = 2씩 넓어진다.

왜 중요한가: 모델이 "손목을 한 바퀴 돌리는 1초짜리 동작"을 알아보려면 출력 한 칸의 RF가 적어도 그 1초(50 Hz면 50샘플)를 덮어야 한다. RF가 10샘플이면 모델은 구조적으로 그 동작 전체를 볼 수 없다. 오디오 wake word도 단어 길이(수백 ms)를 덮는 RF가 필요하다.

4.2 공식 — stride가 있으면 jump가 곱해진다#

층을 아래에서 위로 쌓으며 두 값을 갱신한다. r = 지금까지의 RF, j = jump(현재 층의 인접 두 출력이 입력에서 몇 칸 떨어져 있나).

말로 하면: 새 층은 아래층 칸 k개를 보는데, 아래층 칸 사이 간격이 입력 기준 j칸이므로 RF가 (k − 1)·j만큼 늘어난다. stride(와 pooling)는 이후 모든 층의 성장 속도를 곱으로 키운다. 그래서 CNN은 앞쪽에서 stride 2를 반복해 해상도를 줄이면서 RF를 빠르게 키운다.

손계산: conv3 → conv3 → avgpool2(s2) → conv3 → conv3(s2) → conv3.

4.3 코드로 확인 — gradient로 RF를 "측정"#

A3에서 gradient는 "이 입력을 살짝 건드리면 출력이 변하나"였다. 그러므로 출력 한 칸에서 backward 했을 때 gradient가 0이 아닌 입력 영역 = RF다. 가중치를 모두 1로 두어 양수끼리 상쇄되지 않게 한다 (max pooling은 gradient가 최댓값 한 곳으로만 가므로 avg pooling을 썼다).

출력에서 볼 것: 공식의 22와 gradient로 잰 22(입력 행 8~29)가 같다. 출력 shape 64 → 62 → 60 → 30 → 28 → 13 → 11도 2절 공식 그대로다.

두 가지 보충. 첫째, 이론 RF 안에서도 가장자리 픽셀은 경로 수가 적어 영향이 약하다 — 실제로 영향이 큰 영역(effective receptive field)은 이론 RF보다 좁고 가운데가 두꺼운 종 모양이다. 둘째, 3×3 두 층(RF 5, 파라미터 2·9·C²)이 5×5 한 층(RF 5, 25·C²)보다 파라미터가 적고 비선형성이 하나 더 들어간다. VGG 이후 3×3을 쌓는 설계가 표준이 된 이유다.

4.4 pooling — 파라미터 없는 다운샘플#

pooling은 창 안의 값을 하나로 요약한다. 학습 파라미터가 없다.

  • max pooling: 창의 최댓값. "이 영역 어딘가에 특징이 있었나"를 남긴다.
  • average pooling: 창의 평균. 부드러운 다운샘플 (DSP의 boxcar 평균 + decimation).
  • global average pooling(GAP): 창 = feature map 전체. [N, C, H, W] → [N, C, 1, 1]. 채널마다 숫자 하나. 분류 head 앞에서 공간 차원을 없애서, 입력 해상도가 바뀌어도 FC 크기가 그대로다.

손계산 (4×4 입력 [[1,3,2,0],[4,6,1,1],[0,2,5,7],[1,1,3,2]], 2×2 창, stride 2): 왼쪽 위 창 [1, 3; 4, 6]의 max = 6, avg = 14/4 = 3.5, 오른쪽 아래 창 [5, 7; 3, 2]의 max = 7, avg = 17/4 = 4.25. GAP는 nn.AdaptiveAvgPool2d(1)(1D는 AdaptiveAvgPool1d(1))이고 파라미터는 0개다. 최신 모바일 CNN은 중간 다운샘플을 pooling 대신 stride 2 conv로 하고, 마지막에만 GAP를 쓰는 경우가 많다. 9절에서 GAP와 global max의 차이를 실제 학습으로 본다.

5. C로 직접 — naive conv2d (NCHW)#

5.1 루프 구조#

conv는 결국 6중(배치 포함 7중) MAC 루프다. A1에서 GEMM이 삼중 루프였던 것과 같은 모양이다. 레이아웃은 PyTorch와 같은 NCHW(배치 1이라 x[c][h][w])로 하고, 패딩은 메모리에 0을 실제로 두르지 않고 경계 검사로 건너뛰는 방식으로 처리한다 (MCU에서 패딩 버퍼를 따로 잡지 않기 위해 흔히 쓰는 방식).

5.2 PyTorch golden과 비교#

같은 결정적 초기화(flat index 기반)를 PyTorch에서 만들어 F.conv2d로 계산한다. A5에서 말한 대로 PyTorch 출력이 golden reference다.

출력에서 볼 것: 출력 채널 1의 25개 값과 전체 checksum(두 채널 합)이 C와 같다. C의 flat 배열 순서 [o][c][kh][kw]가 PyTorch 가중치 [C_out, C_in, kH, kW]의 contiguous 순서와 같기 때문에 view만으로 맞출 수 있었다. 이 값들은 0.125 배수라 float로 정확히 표현돼 오차 0이지만, 일반 값에서는 합산 순서 차이로 1e-6 수준 차이가 정상이다 (A5 8.4절).

5.3 이 루프를 빠르게 만드는 방법들 (미리 보기)#

  • im2col + GEMM (A1 미리보기): 입력 창을 열로 펼쳐 [C_out, C_in·k²] × [C_in·k², H_out·W_out] 행렬곱 하나로 만든다. 최적화된 GEMM을 재사용할 수 있지만 펼친 행렬이 입력의 약 k²배 메모리를 먹는다 (10절에서 숫자로 본다).
  • direct conv + 루프 순서/타일링: 메모리를 더 쓰지 않고, 가장 안쪽 루프를 연속 메모리(NHWC면 채널)로 두어 SIMD로 돌린다. CMSIS-NN, XNNPACK 같은 라이브러리의 핵심 작업이다 (K2, J3).
  • Winograd: 3×3 conv의 곱셈 수를 줄이는 변환. 정수 양자화와 궁합이 나빠 MCU보다는 모바일 CPU/GPU float 경로에서 쓰인다.

6. Depthwise, pointwise, depthwise separable#

6.1 standard conv가 비싼 이유#

3.2절 공식 MACs = H·W·C_out·C_in·k²를 보면 공간(k²)과 채널(C_in·C_out)이 곱해져 있다. 필터 하나가 "공간 패턴 찾기"와 "채널 섞기"를 동시에 하기 때문이다. 이 둘을 분리하면 곱이 합으로 바뀐다. 이것이 depthwise separable conv의 아이디어 전부다.

6.2 세 가지 conv 정의#

  • depthwise conv: 채널마다 자기 전용 k×k 필터 하나. 채널끼리 섞지 않는다. groups = C_in, 가중치 [C_in, 1, k, k]. 공간 필터링만 한다. Don 언어로는 "채널별 독립 FIR"이다.
  • pointwise conv (1×1 conv): kernel 1×1. 한 픽셀 위치에서 C_in개 값을 C_out개로 섞는다. 공간은 안 본다. 모든 픽셀에 같은 dense layer를 적용하는 것과 같고, W[C_out, C_in] × X[C_in, H·W] GEMM이다 (A1 표).
  • depthwise separable conv (DS conv): depthwise k×k → pointwise 1×1. 보통 사이에 BN + ReLU.

groups는 일반화된 손잡이다: 입력·출력 채널을 groups개 묶음으로 나누고 묶음 안에서만 섞는다. groups = 1은 standard, groups = C_in = C_out은 depthwise.

그림 5 — standard conv(a)는 필터 하나가 k×k×C_in을 한꺼번에 본다. depthwise separable(b)은 채널별 k×k 필터로 공간을 먼저 걸러 내고, 1×1 필터로 채널을 섞는다.

6.3 감소율 유도#

말로 하면: 3×3 kernel이면 1/k² = 1/9이 지배적이고 1/C_out은 작은 보정이다. 그래서 3×3 DS conv는 standard 대비 대략 8~9배 적은 MAC을 쓴다. 파라미터도 같은 비율이다 (C_in·k² + C_in·C_out vs C_in·C_out·k², bias 제외).

손계산: C_in = 64, C_out = 128, k = 3, 56×56, stride 1.

눈여겨볼 점: DS 블록 MAC의 93%가 pointwise(25.7 M / 27.5 M)다. depthwise는 싸다. 그래서 MobileNet 계열의 연산량은 사실상 1×1 conv가 결정한다.

6.4 코드로 확인#

출력에서 볼 것: depthwise 가중치 shape이 [64, 1, 3, 3] — 필터 하나가 입력 채널 1개만 본다. 모든 숫자가 손계산과 같고, 감소율 0.1189가 공식과 일치한다.

6.5 공짜가 아니다 — 표현력과 arithmetic intensity#

DS conv는 두 가지 대가를 치른다.

(1) 표현력: 공간과 채널을 동시에 섞는 필터를 "공간 따로, 채널 따로"로 근사한다. 같은 채널 수라면 standard보다 약하다. 그래서 MobileNet은 채널을 넓히거나(v2의 expansion) 층을 더 쌓아 보완한다.

(2) arithmetic intensity(연산 밀도): 옮긴 바이트당 MAC 수다 (D3의 roofline에서 핵심 축). 입력·출력·가중치를 각각 한 번만 옮긴다고 가정하고 int8(1 B/원소)로 계산해 보자.

출력에서 볼 것: depthwise는 standard와 거의 같은 양의 데이터(402 KB) 를 옮기면서 MAC은 64분의 1이다. 연산 밀도 4.5 MAC/B는 거의 모든 가속기에서 memory-bound(대역폭이 병목)다. MAC을 64배 줄였다고 시간이 64배 줄지 않는다.

NPU에서 더 불리한 이유가 하나 더 있다. NPU의 MAC 배열(E5의 systolic array 등)은 보통 "긴 내적(C_in·k² 방향 reduction)"을 여러 출력 채널에 동시에 뿌리도록 설계된다. depthwise는 출력 하나당 내적 길이가 k² = 9뿐이고 채널끼리 가중치를 공유하지 않아서, 배열의 많은 lane이 놀게 된다. 그래서 MobileNet이 "MAC은 ResNet의 1/6인데 NPU에서 기대만큼 빠르지 않다"는 일이 생기고, 일부 최신 설계는 초기 고해상도 층에서 depthwise 대신 standard(또는 fused) conv를 다시 쓴다 (D4, E5에서 자세히).

7. 아키텍처 계보 — ResNet, MobileNet v1–v4, EfficientNet#

7.1 ResNet — skip connection#

ResNet(He et al., 2015)의 블록은 y = F(x) + x다. F는 conv-BN-ReLU-conv-BN 두세 층이고, 입력 x를 그대로 더하는 경로가 skip(residual) connection이다.

왜 도움이 되나 (A3의 chain rule로):

말로 하면: gradient가 ∂F/∂x를 거치는 경로 말고도 항등 행렬 I를 통해 그대로 흘러내려가는 고속도로가 생긴다. 층이 50개, 100개여도 앞쪽 층까지 gradient가 사라지지 않는다(vanishing gradient 완화). 또 F가 "고칠 부분(residual)"만 배우면 되므로, 필요 없는 블록은 F ≈ 0으로 두면 된다. 그 결과 ResNet은 수십~수백 층을 안정적으로 학습시킨 첫 구조가 됐다.

  • Bottleneck 블록(ResNet-50 이상): 1×1(채널 축소) → 3×3 → 1×1(채널 복원). 비싼 3×3을 좁은 채널에서만 한다.
  • stride 2 블록: x와 F(x)의 shape이 달라지므로 skip 쪽에 1×1 stride 2 conv(projection)를 둔다.
  • 임베디드 비용: skip 경로 때문에 x를 블록이 끝날 때까지 메모리에 살려 둬야 한다. 순수 체인 모델보다 activation peak가 커진다 (10절, D2).

7.2 MobileNet v1 — DS conv로 전부 바꾸기#

MobileNet v1(Howard et al., 2017)은 첫 층(3×3 standard conv, stride 2)을 빼고 모든 conv를 DS conv로 쌓은 13블록 구조다. 두 개의 전역 손잡이를 둔다.

  • width multiplier α: 모든 층의 채널 수에 α를 곱한다. MAC·파라미터가 대략 α²배.
  • resolution multiplier ρ: 입력 해상도 배율. MAC이 대략 ρ²배 (파라미터는 불변).

MCU용으로 α = 0.25, 입력 96×96 같은 작은 설정이 자주 쓰인다 (TFLite Micro의 person detection 예제가 이 계열로 알려져 있다).

7.3 MobileNet v2 — inverted residual + linear bottleneck#

MobileNet v2(Sandler et al., 2018) 블록은 ResNet bottleneck을 뒤집었다.

  • inverted residual: ResNet은 "넓음 → 좁음 → 넓음"이고 skip이 넓은 쪽을 잇는다. v2는 "좁음 → 넓음 → 좁음"이고 skip이 좁은 쪽을 잇는다. 블록 사이를 흐르는(그래서 메모리에 오래 살아 있는) 텐서가 좁아서 activation 메모리에 유리하다.
  • linear bottleneck: 마지막 1×1 projection 뒤에 ReLU를 두지 않는다. 좁은 채널에서 ReLU를 걸면 음수 쪽 정보가 잘려 복구가 안 된다는 논리다.
  • ReLU6 = min(max(x, 0), 6): 출력 범위가 [0, 6]으로 고정돼 저정밀(고정소수점·int8) 표현에 유리하다. 범위가 정해져 있으면 scale을 정하기 쉽다.

torchvision 구현에서 실제 블록 구조를 확인한다.

출력에서 볼 것: 16 → 96(×6 expand) → depthwise(groups=96, stride 2) → 96 → 24. conv가 3개인데 ReLU6는 2개 — projection 뒤에는 활성화가 없다(linear bottleneck). stride 2인 features[2]는 residual이 없고, 입출력 shape이 같은 features[3](24 → 144 → 24)은 residual이 있다. 아래 줄은 v3-small에 Hardswish, Hardsigmoid, SE 모듈이 들어 있음을 보여 준다 (ReLU 개수에는 SE 내부의 ReLU도 포함).

7.4 MobileNet v3 — SE, hard-swish, NAS#

MobileNet v3(Howard et al., 2019)는 v2 블록 위에 세 가지를 얹었다.

  • SE(Squeeze-and-Excitation): 블록 안에서 GAP로 채널별 평균을 구하고(squeeze), 작은 FC 두 층 + hard-sigmoid로 채널별 가중치(0~1)를 만들어 feature map에 곱한다(excitation). "이번 입력에서는 어느 채널이 중요한가"를 동적으로 조절한다. 파라미터·MAC은 적게 늘지만 GAP → FC → 원소별 곱이라는, feature map 전체를 한 번 다 읽어야 다음으로 갈 수 있는 동기화 지점이 생긴다.
  • hard-swish: h-swish(x) = x · ReLU6(x + 3) / 6. swish(= SiLU, x·σ(x))의 근사로, exp가 필요한 sigmoid 대신 조각 선형 함수를 써서 정수 하드웨어에서 싸다.
  • NAS(Neural Architecture Search): 블록 구성(kernel 크기, expansion, SE 여부)을 사람 대신 탐색 알고리즘이 모바일 CPU 지연시간을 목표로 골랐다 (platform-aware NAS + NetAdapt). 마지막 단의 비싼 층도 손으로 다시 설계했다. Large/Small 두 버전이 있다.

7.5 MobileNet v4 — Universal Inverted Bottleneck (확실한 것만)#

MobileNet v4(Qin et al., 2024)의 핵심은 UIB(Universal Inverted Bottleneck) 블록이다. v2의 inverted bottleneck에 선택적인 depthwise conv 두 개(expansion 앞 하나, expansion 뒤 하나)를 두어, 두 스위치의 조합으로 네 가지 블록을 하나의 틀로 표현한다: 기존 inverted bottleneck(IB), ConvNext 스타일, ExtraDW(둘 다 켬), FFN(둘 다 끔 = 1×1 두 개). NAS가 층마다 어느 형태를 쓸지 고른다. 논문은 roofline 모델로 CPU·DSP·GPU·EdgeTPU·Apple Neural Engine 등 여러 하드웨어에서 동시에 Pareto 최적에 가깝게 되도록 설계했다고 주장하며, 하이브리드 버전에는 모바일용 attention 블록(Mobile MQA)을 넣었다. torchvision 0.23에는 없고 서드파티 구현(timm 등)을 쓴다. 세부 채널 구성과 수치는 원 논문을 직접 확인할 것.

7.6 EfficientNet — compound scaling#

EfficientNet(Tan & Le, 2019)의 질문: "모델을 키울 때 깊이(depth), 폭(width, 채널), 입력 해상도(resolution) 중 무엇을 얼마나 키워야 하나?" 답은 셋을 정해진 비율로 함께 키우는 compound scaling이다.

말로 하면: conv의 MAC은 깊이에 1제곱, 채널 폭에 2제곱(C_in·C_out), 해상도에 2제곱(H·W)으로 비례하므로, φ를 1 올릴 때마다 연산량이 약 2배가 되도록 세 비율을 묶었다. 기준 모델 B0는 NAS로 찾은 MBConv(= v2 inverted residual + SE) 블록과 swish 활성화를 쓴다. B1~B7은 φ를 키운 버전이다. edge용으로는 SE를 빼고 swish를 ReLU6로 바꾼 EfficientNet-Lite가 따로 나왔다 — 양자화와 가속기 호환성을 위해서다.

8. 1D conv — 시계열, causal, dilated, TCN, 스트리밍#

8.1 1D conv의 텐서 모양#

IMU·오디오 같은 시계열은 Conv1d에 [N, C, L](배치, 채널, 길이)로 들어간다 (A5 2.4절). IMU 6축 1초 @ 50 Hz면 [N, 6, 50]이다. 필터 하나는 [C_in, k] — 6축 × k샘플을 한 번에 보고 시간축으로 미끄러진다. 공식은 2절·3절에서 W 축만 없앤 것이다.

오디오는 두 방식이 있다. (1) MFCC/log-mel 스펙트로그램을 이미지처럼 [N, 1, 시간, 주파수]로 보고 Conv2d (KWS의 DS-CNN, B5), (2) 주파수 bin을 채널로 보고 [N, n_mels, 시간]에 Conv1d. 원시 파형에 바로 Conv1d를 거는 모델도 있지만 edge에서는 특징 추출(G4) 뒤에 거는 경우가 많다.

8.2 causal conv — 미래를 보지 않는다#

오프라인 분류(창 하나를 통째로 받고 판정)라면 대칭 패딩도 괜찮다. 하지만 샘플이 올 때마다 출력을 내야 하는 스트리밍이라면 출력 t가 입력 t 이후를 보면 안 된다. causal conv는 패딩을 왼쪽(과거)에만 (k − 1)·d칸 넣어서 이를 보장한다.

펌웨어 관점: 이게 바로 실시간 FIR 필터다. 대칭 패딩 모델을 실시간으로 돌리려면 (k − 1)/2샘플 지연(latency) 을 받아들여야 하고, 층이 쌓이면 지연도 쌓인다.

8.3 dilated conv와 TCN#

causal conv만 쌓으면 RF가 층당 (k − 1)씩밖에 안 는다. 50 Hz에서 2초(100샘플)를 보려면 k = 3으로 50층이 필요하다. dilation을 층마다 1, 2, 4, 8…로 두 배씩 키우면 RF가 지수적으로 는다.

말로 하면: 층 수에 대해 RF가 2^L로 커진다. WaveNet(van den Oord et al., 2016)이 원시 오디오에 쓴 구조이고, 이를 일반 시계열용으로 정리한 것이 TCN(Temporal Convolutional Network, Bai et al., 2018) 이다. TCN의 실제 블록은 같은 dilation의 causal conv 두 개 + residual이라 RF는 1 + 2·(k − 1)·Σd다.

그림 6 — k = 2, dilation 1·2·4·8인 causal TCN. 맨 위 출력 t(주황)는 입력 t−15~t 16개에 의존하고, 미래(오른쪽)는 전혀 보지 않는다. 층마다 연결 간격이 두 배가 된다.

코드로 확인: k = 3, dilation 1·2·4·8의 causal conv 4층을 만들고 gradient로 RF와 causality를 잰다.

출력에서 볼 것: 출력 t = 50은 입력 20~50(31개)에만 의존하고 51 이후는 보지 않는다. 입출력 길이가 64로 같다 — causal 패딩이 길이를 보존한다.

8.4 스트리밍 추론 — 층마다 링버퍼#

MCU에서 1D CNN을 돌리는 가장 단순한 방법은 "창(예: 1초)이 찰 때마다 전체 모델 실행"이다. 창을 0.1초마다 밀면(hop) 매번 90%를 중복 계산한다. causal conv 모델은 더 잘할 수 있다: 각 층이 자기 입력의 과거 (k − 1)·d프레임만 링버퍼에 기억하면, 새 샘플 하나가 들어올 때마다 각 층에서 출력 한 열만 계산하면 된다. 결과는 전체 시퀀스를 오프라인으로 돌린 것과 비트 단위로 같다.

그림 7 — k = 3, d = 2 층의 링버퍼. 길이 SPAN = (k − 1)·d + 1 = 5. head가 방금 쓴 칸이고, tap j는 (k − 1 − j)·d칸 전을 읽는다. 버퍼를 0으로 초기화하면 오프라인의 왼쪽 zero padding과 같아진다.

Don에게는 익숙한 구조다: DMA가 채우는 오디오 링버퍼, FIR의 delay line과 같다. 차이는 층마다 링이 하나씩 있고, 다음 층의 링에 들어가는 것은 이전 층의 출력(ReLU 후) 이라는 점뿐이다.

아래 C 코드는 2층(2 → 3채널 k=3 d=1 + ReLU, 3 → 1채널 k=3 d=2) causal 1D CNN을 (1) 샘플 단위 스트리밍으로, (2) 전체 시퀀스 오프라인으로 계산해 비교한다.

출력에서 볼 것: 스트리밍과 오프라인이 정확히 0 차이다 (같은 순서로 같은 곱을 더하므로). 상태 메모리는 층별 SPAN × C의 합 = 21 float = 84 B뿐이다. 코드는 간단히 하려고 두 링을 같은 크기 구조체로 잡았지만, 실제로 쓰는 칸은 층별 SPAN만큼이다.

8.5 스트리밍 설계에서 챙길 것#

  • stride가 있는 층: stride 2 층은 입력 2개가 들어올 때마다 출력 1개를 낸다. 층마다 "몇 번째 샘플에서 실행하나" 카운터가 필요하다 (멀티레이트 DSP의 decimator와 같다).
  • 대칭 패딩으로 학습한 모델은 그대로 스트리밍하면 결과가 달라진다. 학습 때부터 causal로 만들거나, 층별 지연을 계산해 출력 타이밍을 맞춘다.
  • BatchNorm은 추론 때 고정 affine이라 스트리밍에 문제없다 (B1 folding). GAP처럼 "전체 시간 평균"을 쓰는 head는 스트리밍에서 이동 평균/누적 평균으로 바꿔야 한다.
  • 상태 메모리는 작지만 리셋 정책이 필요하다: 기기 슬립 후 깨어났을 때 링을 0으로 비울지, 이전 상태를 retention SRAM에 유지할지.
  • 오프라인(창 단위) 대비 연산 절감률은 창과 hop 길이의 비율에 달려 있다. 연산이 줄어드는 대신 매 샘플 호출이 되므로 호출 오버헤드와 wake-up 전력(E9)을 같이 본다. 실무에선 샘플 몇 개를 묶어(block) 처리하는 절충을 많이 쓴다.

9. 작은 end-to-end — 합성 IMU로 DS-CNN 1D 학습#

지금까지 배운 것(1D conv, depthwise separable, GAP, MAC 세기)을 한 번에 돌린다. 예를 들어 Hark 같은 손목 기기라면(추정) 제스처 몇 개를 구분하는 always-on 모델을 생각할 수 있다. 합성 데이터 4 class: 가만히(still), 흔들기(shake, 3~6 Hz), 원 그리기(circle, 1~2.5 Hz, ax·ay 90° 위상차), 톡 치기(tap, 임의 시점 3샘플 충격). 창은 6축 × 64샘플 @ 50 Hz.

모델: Conv1d(6 → 16, k5, stride 2) → DS 블록 두 개(depthwise k5 + pointwise) → global pooling → Linear(32 → 4). global pooling을 avg와 max로 바꿔 가며 비교한다. 아래를 ex13.py로 저장하고 인자로 풀링 종류를 준다.

10. 임베디드 관점에서 다시 보기#

10.1 activation 메모리 — peak는 "가장 큰 입력 + 출력 쌍"#

MCU에서 가중치는 flash에 두고 읽기만 하면 되지만, activation(중간 feature map)은 SRAM에 있어야 한다. 분기가 없는 체인 모델에서 레이어 하나를 실행하는 순간 살아 있어야 하는 것은 그 레이어의 입력과 출력이다 (그 앞 텐서는 이미 버려도 된다). 그래서 런타임의 memory planner(D2, F2)는 버퍼 두 개를 번갈아 쓰는 ping-pong 방식에 가깝게 arena를 배치하고, peak activation ≈ max over layers (입력 크기 + 출력 크기) 가 된다. residual이 있으면 skip 텐서가 블록 끝까지 살아 있어서 이보다 커진다.

7절의 MobileNet v1을 96×96 입력, 2 class로 만들고 α = 1.0과 0.25를 비교한다 (int8 가정).

출력에서 볼 것:

  • peak는 앞쪽 고해상도 층(48×48에서 32 → 64 pointwise: 73,728 + 147,456 B = 216 KB)에서 나온다. 뒤쪽은 채널이 많아도 해상도가 작아 activation이 작다. 반대로 가중치는 뒤쪽 층에 몰린다. "activation은 앞, weight는 뒤" — MCU 모델 설계에서 가장 먼저 떠올릴 그림이다.
  • α = 0.25로 채널을 1/4로 줄이면 activation peak가 1/4(54 KB), 파라미터가 약 1/15(213.6 K, int8 flash 약 209 KB), MAC이 약 1/14(7.5 M)로 줄어 수백 KB SRAM MCU에 들어간다. 파라미터·MAC이 정확히 1/16이 아닌 것은 첫 conv(입력 3채널 고정)와 FC 등 α에 제곱으로 비례하지 않는 부분 때문이다.
  • 해상도를 줄이는 것(ρ)은 activation을 제곱으로 줄이므로 SRAM이 부족할 때 가장 강한 손잡이다. MCUNetV2(Lin et al., 2021)는 초기 층을 patch 단위로 나눠 실행해 이 peak 자체를 낮춘다 (C8, MIT 6.5940).

10.2 im2col vs direct conv — 메모리 트레이드오프#

위 출력의 마지막 줄: 3×3 conv 32 → 64, 56×56에서 입력은 98 KB인데 전체 im2col 행렬은 882 KB(9배) 다. 서버·모바일 CPU는 이 메모리를 감수하고 빠른 GEMM을 쓰지만, SRAM 수백 KB짜리 MCU에서는 불가능하다. 그래서:

  • CMSIS-NN 같은 MCU 커널은 전체 im2col 대신 출력 몇 픽셀분만 펼치는 작은 scratch buffer를 쓰고 (필요한 크기는 arm_convolve_s8_get_buffer_size 같은 함수로 조회해 arena에 잡는다), 1×1 conv는 im2col 없이 바로 GEMM으로 처리한다.
  • depthwise conv는 im2col이 거의 이득이 없다 (내적 길이 9짜리 GEMM이라). 전용 direct 커널을 쓴다.
  • NPU는 컴파일러가 텐서를 tile로 쪼개 on-chip SRAM에 DMA로 올리고 내린다 (E5). 이때 conv의 halo(창이 타일 경계를 넘는 k − 1줄)를 중복 로드한다.

10.3 레이아웃 — NHWC가 edge 표준인 이유#

A1·A5에서 본 대로 PyTorch는 NCHW, TFLite·CMSIS-NN·대부분의 모바일 NPU는 NHWC다. conv 관점의 이유:

  • 1×1 conv와 standard conv의 가장 안쪽 루프는 C_in 방향 내적이다. NHWC면 한 픽셀의 채널들이 연속이라 SIMD(예: Cortex-M의 SMLAD, Helium, NEON SDOT)로 바로 로드된다.
  • depthwise는 채널끼리 독립이라 NHWC에서 "여러 채널을 SIMD lane에 나란히 놓고 같은 탭을 동시에 계산"하기 좋다.
  • TFLite 가중치: Conv2D [C_out, kH, kW, C_in], DepthwiseConv2D [1, kH, kW, C_out]. PyTorch [C_out, C_in, kH, kW]와 다르므로 변환기가 transpose한다. 5절 C 코드를 NHWC로 바꾸는 것이 직접 해보기 6번이다.

10.4 양자화 친화성#

  • BN folding 후 conv + bias + ReLU(6)가 하나의 int8 커널로 합쳐진다 (B1, C6 op fusion).
  • ReLU6·hard-swish는 범위가 제한되거나 조각 선형이라 int8 lookup/근사가 쉽다. swish·GELU처럼 exp가 들어가는 활성화는 LUT가 필요하다.
  • depthwise 가중치는 채널별 범위 차이가 크다. 채널 하나가 필터 하나라 BN folding 후 채널마다 스케일이 크게 다를 수 있고, 텐서 전체에 scale 하나(per-tensor)를 쓰면 작은 채널이 0으로 뭉개진다. 그래서 TFLite int8 규격은 conv/depthwise 가중치에 per-channel scale을 쓴다. MobileNet v1을 per-tensor로 양자화했을 때 정확도가 크게 떨어지는 사례가 잘 알려져 있다 (C2에서 자세히).
  • SE 블록은 GAP → FC → sigmoid → 곱으로 동기화 지점과 원소별 연산을 추가해 NPU 파이프라인을 끊을 수 있다. EfficientNet-Lite가 SE를 뺀 이유 중 하나다.

12. 면접에서 이렇게 말한다#

Q. Compute the parameters and MACs of a 3×3 convolution from 32 to 64 channels on a 56×56 input, stride 1, same padding.

A. 출력은 56×56×64. 필터 하나가 3·3·32 = 288개 가중치라서 파라미터는 64·288 = 18,432, bias 포함 18,496. MAC은 출력 원소 수 × 288 = 3,136·64·288 ≈ 57.8 M, FLOP으로는 약 116 M. 파라미터는 해상도와 무관하고 MAC은 출력 해상도에 비례한다는 점을 같이 말한다.

"The output is 56 by 56 by 64. Each filter has 3 times 3 times 32, so 288 weights, which gives 18,432 parameters, or 18,496 with bias. Every output element is a 288-long dot product, so MACs are 56 times 56 times 64 times 288, about 57.8 million, or roughly 116 MFLOPs. Parameters don't depend on resolution, but compute scales with the output area, which is why CNNs are small in flash but heavy in compute."

Q. Why depthwise separable convolutions?

A. standard conv는 공간 필터링과 채널 섞기를 한 번에 해서 비용이 k²·C_in·C_out에 비례한다. 이를 채널별 k×k depthwise와 1×1 pointwise로 나누면 k²·C_in + C_in·C_out이 되어 비율이 1/C_out + 1/k², 3×3이면 대략 8~9배 절감이다. 대가는 표현력 감소와, depthwise의 낮은 arithmetic intensity라서 가속기에서 MAC 감소만큼 빨라지지 않는다는 점이다.

"A standard conv mixes space and channels in one step, costing k-squared times C-in times C-out per pixel. Splitting it into a per-channel k-by-k depthwise conv and a 1-by-1 pointwise conv costs k-squared C-in plus C-in C-out, so the ratio is one over C-out plus one over k-squared — roughly eight to nine times fewer MACs for 3-by-3. The catch is that the depthwise part has very low arithmetic intensity and short reductions, so on NPUs it's often memory-bound and underutilizes the MAC array; the speedup is smaller than the MAC count suggests."

Q. What is the receptive field, and how do you make it larger?

A. 출력 한 칸이 의존하는 입력 영역의 크기다. 층마다 r ← r + (k − 1)·d·j, j ← j·s로 계산한다. 키우는 방법은 층을 더 쌓기, stride나 pooling으로 다운샘플해 이후 층의 jump 키우기, dilation 쓰기. 시계열에서는 dilation을 1, 2, 4, 8로 두 배씩 키우는 TCN이 층 수에 대해 지수적으로 RF를 늘린다. 이론 RF보다 실효 RF가 좁다는 점도 덧붙인다.

"It's the span of input that one output value can depend on. Each layer adds (k minus 1) times dilation times the current jump, and strides multiply the jump. You grow it by adding layers, downsampling early with strides or pooling, or using dilation — a TCN with dilations 1, 2, 4, 8 grows it exponentially with depth. I also check it against the physical scale of the signal: if a gesture lasts a second at 50 Hz, the receptive field has to cover about 50 samples. And the effective receptive field is narrower than the theoretical one."

Q. How do you run a 1D CNN in streaming mode on an MCU?

A. 모델을 causal conv로 학습해서 출력이 과거와 현재 샘플만 보게 한다. 기기에서는 층마다 입력의 과거 (k − 1)·d 프레임을 링버퍼로 들고 있다가, 새 샘플이 오면 각 층에서 출력 한 열만 계산해 다음 층의 링에 넣는다. 결과는 오프라인 전체 시퀀스 계산과 정확히 같고, 창 단위 재계산의 중복을 없앤다. stride 층은 카운터로 실행 주기를 나누고, 상태 리셋 정책과 GAP 대신 누적 풀링을 챙긴다. PyTorch golden과 비트 단위로 비교해서 검증한다.

"I train it with causal padding so each output only depends on current and past samples. On the device each layer keeps a ring buffer of its last (k minus 1) times dilation input frames. When a new sample arrives, each layer computes just one new output column and pushes it into the next layer's ring. That's mathematically identical to running the full sequence offline, but without recomputing overlapping windows. Strided layers run every s-th step, global pooling becomes a running statistic, and I define what happens to the state across sleep. I validate it by comparing the streamed output against the PyTorch model on the same sequence."

Q. MobileNetV2 has one-sixth the MACs of ResNet-18 but isn't six times faster on our NPU. Why?

A. MAC 수는 연산 상한만 말해 준다. depthwise conv는 MAC의 몇 %지만 입출력 데이터를 standard conv와 비슷하게 옮기므로 arithmetic intensity가 4~5 MAC/B 수준으로 memory-bound다. 게다가 내적 길이가 9뿐이라 NPU MAC 배열이 놀고, expand 1×1이 만든 넓은 activation을 여러 번 오간다. 층별 프로파일로 memory-bound 층을 찾고, fused/standard conv로 바꾸거나 NPU 친화 변종을 쓰는 걸 고려한다.

"MACs only bound the compute. Depthwise layers are a small fraction of MACs but move about as much data as a full conv, so their arithmetic intensity is a few MACs per byte — firmly memory-bound. Their reductions are only nine long, so a MAC array built for long dot products sits mostly idle, and the expanded activations in inverted residuals add traffic. I'd profile per layer, place each on a roofline, and consider fusing or replacing early depthwise layers with regular convs, which newer NPU-oriented designs do."

Q. Why do skip connections help?

A. y = F(x) + x에서 ∂y/∂x = ∂F/∂x + I라서 gradient가 항등 경로로 앞 층까지 직접 흐른다. 깊은 망에서도 vanishing gradient가 완화되고, 블록은 필요한 수정분만 배우면 된다. 배포 관점에서는 skip 텐서가 블록 끝까지 살아 있어야 해서 activation peak가 늘어난다는 비용도 말한다.

"With y equals F of x plus x, the Jacobian is dF/dx plus the identity, so gradients have a direct path back to early layers and don't vanish as depth grows; each block only has to learn a correction. On-device, the cost is that the skip tensor must stay alive until the add, which raises peak activation memory — something the memory planner has to account for."

15. 요약 & 체크리스트#

conv는 학습되는 다채널 FIR 필터 뱅크다. locality와 weight sharing으로 dense layer보다 파라미터를 백만 배 넘게 줄이고, 파라미터 하나를 출력 해상도만큼 재사용하므로 "작은 가중치, 많은 MAC"이 된다. 출력 크기는 ⌊(n + 2p − d(k − 1) − 1)/s⌋ + 1, 파라미터는 C_out·C_in·k², MAC은 출력 원소 수 × C_in·k²이고, 이 셋으로 모델 전체를 종이 위에서 추적할 수 있다. receptive field는 층마다 (k − 1)·d·jump씩 자라고, stride와 dilation이 성장을 가속한다. depthwise separable conv는 공간과 채널 섞기를 분리해 비용을 1/C_out + 1/k²배로 줄이며 MobileNet v1–v4와 EfficientNet의 기반이지만, depthwise는 arithmetic intensity가 낮아 가속기에서 MAC 감소만큼 빨라지지 않는다. ResNet의 skip은 gradient 고속도로이자 activation 메모리 비용이다. 시계열에서는 causal·dilated conv(TCN)가 RF를 지수적으로 키우고, 층별 링버퍼로 샘플 단위 스트리밍을 오프라인과 정확히 같은 결과로 실행할 수 있다. MCU 배포에서는 앞단 고해상도 층의 activation peak, im2col 메모리, NHWC 레이아웃, per-channel 양자화를 먼저 본다.
