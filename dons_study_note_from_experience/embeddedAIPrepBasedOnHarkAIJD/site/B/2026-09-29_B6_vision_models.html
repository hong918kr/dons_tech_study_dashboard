1. 카메라에서 텐서까지 — 전처리#

1.1 직관: 이미지는 uint8 3차원 배열이다#

카메라 센서는 Bayer 패턴(픽셀마다 R/G/B 중 한 색만)의 RAW 값을 낸다. ISP(Image Signal Processor)가 demosaic(빠진 색 보간), 화이트 밸런스, 노출·감마 보정을 해서 우리가 아는 RGB 또는 YUV 영상을 만든다. 이 부분은 G6에서 따로 다룬다. 여기서는 ISP 출력부터 시작한다.

ISP 출력 RGB 한 장은 [H, W, 3] 모양의 uint8 배열이다. 320×240 RGB라면 320·240·3 = 230,400 바이트. 메모리에는 픽셀 단위로 R,G,B,R,G,B… 순서로 놓인다. 이것이 HWC(채널이 가장 안쪽) 레이아웃이다.

모델은 이것을 그대로 먹지 않는다. 보통 다음 네 단계를 거친다.

  1. Resize: 모델이 학습된 해상도(예: 224×224)로 크기를 맞춘다. 비율이 다르면 짧은 변 기준으로 줄인 뒤
  2. Center crop: 가운데를 정사각형으로 자른다.
  3. 정규화(normalization): 0~255를 0~1로 나누고, 학습 데이터(ImageNet)의 채널별 평균·표준편차로 z-score를 한다(A2 4절과 같은 개념). ImageNet 값은 mean = (0.485, 0.456, 0.406), std = (0.229, 0.224, 0.225)다.
  4. 레이아웃 변환: PyTorch는 [N, C, H, W](NCHW), TFLite와 많은 NPU는 [N, H, W, C](NHWC)를 원한다(A1에서 본 stride 차이).

1.4 임베디드 연결 — 기기에서는 정규화를 "없앤다"#

기기에서 fp32 정규화를 픽셀마다 하는 것은 낭비다. int8 모델에서는 보통 이렇게 처리한다.

  • 입력 양자화 파라미터에 흡수: int8 입력 텐서는 real = scale × (q − zero_point)로 해석된다(C 모듈에서 자세히). 변환기가 첫 레이어 앞의 (x/255 − mean)/std를 scale·zero_point와 첫 conv 가중치에 접어 넣으면, 펌웨어는 uint8 픽셀을 거의 그대로(예: 128을 빼서 int8로) 넘기면 된다. B1의 BN folding과 같은 발상이다.
  • resize는 ISP나 카메라 센서에서: 많은 저전력 센서는 binning/windowing으로 저해상도를 직접 출력한다. CPU에서 bilinear resize를 하면 메모리 대역폭을 두 번 쓴다.
  • 흑백으로 충분하면 흑백: 사람 존재 감지 같은 작업은 Y(밝기) 평면 하나로도 되는 경우가 많다. 입력 바이트가 1/3이 된다.

같은 전처리를 펌웨어 스타일 C로 쓰면 이렇다. 320×240 Y 평면에서 가운데 240×240을 잘라 96×96으로 nearest-neighbor 축소하고 int8로 바꾸는 코드이며, numpy로 같은 계산을 해서 결과를 대조한다.

출력에서 볼 것: C와 numpy가 비트 단위로 같다. 이런 golden vector 대조는 Don이 SSD 펌웨어에서 하던 검증과 똑같고, 전처리 버그(가로·세로 뒤바뀜, BGR/RGB 뒤바뀜, crop 오프셋)를 잡는 가장 싼 방법이다. 모델 입력은 9 KB로 원본 프레임(77 KB)의 1/8이다.

1.5 흔한 함정#

  • 학습 때와 다른 전처리: 학습은 bilinear resize + ImageNet 정규화였는데 기기에서는 nearest + 정규화 없음 → 정확도가 조용히 몇 % 떨어진다. 에러는 나지 않는다(A0 8.3절 "조용한 데이터 버그").
  • BGR vs RGB: OpenCV는 BGR 순서로 읽는다. 채널 순서가 바뀌어도 모델은 뭔가를 출력한다.
  • YUV의 stride/padding: ISP 출력 버퍼는 행 끝에 정렬 padding이 있는 경우가 많다. width가 아니라 stride로 행을 넘겨야 한다.
  • 전처리 비용 무시: 640×480 RGB → 224×224 bilinear resize + 정규화를 CPU에서 fp32로 하면, 작은 모델에서는 모델 추론보다 오래 걸리기도 한다.

2. 이미지 분류 — backbone + pooling + head#

2.1 구조#

분류 모델은 거의 항상 이 세 부분으로 나뉜다.

  • Backbone: B2에서 배운 conv 블록 더미. 앞쪽은 가장자리·질감, 뒤쪽은 "눈", "바퀴" 같은 부분을 감지한다고 해석된다.
  • Global average pooling(GAP): C×7×7을 채널별 평균으로 C개 숫자로 만든다. 입력 해상도가 달라도 출력 길이가 C로 같아서, 같은 모델을 96×96에도 224×224에도 넣을 수 있게 해 준다(정확도는 해상도에 따라 다르다).
  • Head: Linear 한두 개. 모델 크기에서 의외로 큰 비중을 차지하기도 한다(2.4절).

2.2 top-1과 top-5#

ImageNet 같은 1000-class 벤치마크는 정확도를 두 가지로 보고한다.

  • top-1: 가장 높은 확률 class가 정답이면 맞음.
  • top-5: 확률 상위 5개 안에 정답이 있으면 맞음.

손으로 계산해 보자. 6-class 모델 [0 mug, 1 dog, 2 cup, 3 teapot, 4 stairs, 5 bowl]이 logits [2.1, 0.3, 1.7, 2.4, −0.5, 1.9]를 냈고 정답은 0(mug)이다. softmax 확률은 [0.245, 0.041, 0.164, 0.331, 0.018, 0.201], 내림차순 순서는 3, 0, 5, 2, 1, 4. top-1 예측은 teapot이라 틀림, top-5 안에는 mug가 있으므로 맞음. 이런 식으로 "비슷한 class끼리 헷갈린" 경우를 top-5가 봐준다.

기기에서는 top-5를 거의 쓰지 않는다. 제품은 보통 top-1과 threshold(A0 8.1절, A4)로 결정한다. top-5는 "backbone이 쓸 만한 특징을 뽑는가"를 보는 연구용 지표로 이해하면 된다.

2.3 Transfer learning — 남이 학습시킨 backbone 재사용#

직관: ImageNet 128만 장으로 학습된 backbone은 "가장자리·질감·모양"을 이미 잘 뽑는다. 우리 제품의 "손 들기 / 사람 / 없음" 3-class 문제는 데이터가 수천 장뿐이어도, backbone은 그대로 두고 head만 새로 학습하면 꽤 잘 된다. 펌웨어로 치면 검증된 HAL/드라이버 레이어는 재사용하고 앱 로직만 새로 쓰는 것과 같다.

정도에 따라 세 가지가 있다.

2.4 임베디드 연결과 함정#

  • head도 메모리다: MCU에서 1000-class head는 int8로도 1 MB다. 제품 class 수에 맞춰 교체하는 것만으로 flash가 크게 준다.
  • BatchNorm 함정: requires_grad=False로 동결해도 모델이 train() 모드면 BN의 running mean/var는 계속 갱신된다. 작은 배치로 fine-tuning하면 이 통계가 망가져 정확도가 떨어진다. 동결 부분은 eval()로 두는 것이 안전하다.
  • 학습 해상도 ≠ 배포 해상도: 224로 학습한 모델을 96으로 돌리면 GAP 덕분에 실행은 되지만 정확도가 크게 떨어진다. 배포 해상도로 fine-tuning해야 한다.

3. Edge용 backbone — 파라미터와 MACs, 그리고 해상도²#

3.1 후보들#

  • ResNet (18/50): skip connection의 원조. 표준 conv라 MACs가 크다. 서버·GPU 기준 모델이자 비교 기준.
  • MobileNetV2: inverted residual(1×1 expand → 3×3 depthwise → 1×1 project, B2). 모바일/MCU 비전의 사실상 기본값.
  • MobileNetV3 (Small/Large): 구조 탐색(NAS)으로 찾은 블록 + SE(squeeze-and-excitation) + h-swish 활성화.
  • EfficientNet: 깊이·폭·해상도를 함께 키우는 compound scaling. B0가 가장 작다. SE와 swish를 쓴다.
  • EfficientNet-Lite: EfficientNet을 모바일 가속기용으로 고친 변형이다. TensorFlow 팀 발표에 따르면 SE를 빼고 swish를 ReLU6로 바꿨다. 양자화와 NPU 지원이 나쁜 연산을 걷어낸 것이 핵심 아이디어이며, torchvision에는 없다.

3.2 MACs를 직접 세기 — forward hook 카운터#

라이브러리를 쓰지 않고 conv와 linear의 MAC을 세는 카운터를 만든다. 원리는 B2의 공식 그대로다.

말로 하면, 출력 한 칸을 만들 때 커널이 덮는 입력 개수만큼 곱셈-누산을 한다. depthwise conv는 groups = C_in이라 채널 방향 합이 없어서 싸다.

출력에서 볼 것:

  • 224×224 기준 값이 논문·torchvision 문서의 공개 수치(MobileNetV2 약 300M, ResNet-50 약 4.1G MACs)와 맞는다. 카운터가 제대로 동작한다는 뜻이다.
  • 파라미터 수는 해상도와 무관하지만 MACs는 해상도 비율의 제곱(0.510, 0.184)을 거의 정확히 따른다. ResNet은 정확히 0.510/0.184이고, MobileNetV3-Small은 조금 더 크다(0.528/0.214). 해상도와 무관한 고정 비용(마지막 Linear, 1×1로 줄어든 SE 블록)의 비중이 큰 작은 모델일수록 제곱 법칙에서 조금 벗어난다.
  • MobileNetV3-Small at 96×96은 12M MACs다. ResNet-50 at 224의 1/340이다.

3.4 왜 해상도가 제곱으로 들어가나#

conv 레이어의 MAC은 (출력 H·W) × C_out × (C_in/groups) × k²다. 해상도를 바꾸면 채널과 커널은 그대로이고 H·W만 바뀐다. 모든 feature map의 H·W는 입력 한 변의 제곱에 비례하므로, conv 전체 MAC이 한 변²에 비례한다. activation 메모리(10절)도 같은 이유로 제곱으로 준다. 반면 가중치는 해상도와 무관하다.

그래서 비전 모델 배포에서 입력 해상도는 가장 먼저 돌려 보는 손잡이다. 폭 배수(width multiplier α)는 채널을 곱으로 줄이므로 MAC이 대략 α²로 준다. 해상도와 폭, 두 손잡이 모두 제곱이지만, 해상도는 가중치 크기를 안 바꾸고 폭은 가중치도 줄인다는 차이가 있다.

4.3 검출기는 무엇을 출력하나 — grid, anchor, 두 가지 설계#

분류기는 "이미지 전체에 대해 한 번" 답하지만, 검출기는 feature map의 칸마다 답한다.

  • backbone이 만든 feature map의 각 칸(예: 320 입력 · stride 32 → 10×10칸)이 "내 근처에 물체가 있는가, 있다면 박스는 어떻게 생겼나"를 예측한다.
  • Anchor(또는 default box): 칸마다 미리 정해 둔 기준 박스 몇 개(가로로 긴 것, 세로로 긴 것 등). 모델은 박스 좌표를 처음부터 맞히지 않고 anchor에서 얼마나 옮기고 늘일지(offset)를 예측한다. 펌웨어로 치면 절대값 대신 기준값 대비 delta를 전송하는 것과 같다.
  • 여러 크기의 물체를 위해 여러 stride의 feature map(예: 8, 16, 32)에서 동시에 예측한다.

4.4 NMS — 중복 박스 지우기#

Non-Maximum Suppression의 greedy 알고리즘:

  1. 점수 threshold 아래 박스를 버린다.
  2. 남은 박스를 점수 내림차순으로 정렬한다.
  3. 가장 점수 높은 박스를 결과에 넣는다.
  4. 그 박스와 IoU가 임계값(예: 0.5)을 넘는 나머지 박스를 모두 지운다.
  5. 남은 박스가 없을 때까지 3~4를 반복한다.

말로 하면, "제일 확신하는 박스를 대표로 뽑고, 그 박스와 많이 겹치는(= 같은 물체로 보이는) 박스는 버린다"를 반복한다. 보통 class별로 따로 돌린다(사람 박스가 옆의 가방 박스를 지우면 안 되므로).

4.5 NMS를 C로 — NPU 뒤의 CPU 코드#

NMS는 데이터에 따라 반복 횟수가 달라지는 분기 많은 코드라 NPU에 잘 안 맞는다. 그래서 보통 NPU가 박스·점수 텐서를 내면 CPU가 NMS를 한다. 펌웨어 스타일(malloc 없음, 고정 크기 배열)로 쓰고, 위 numpy와 결과가 같은지 확인한다.

출력에서 볼 것: cc -std=c11 -Wall -Wextra -O2 nms.c -o nms -lm로 경고 0개로 컴파일되고, numpy와 네 경우 모두 같다.

실제 기기에서 챙길 것:

  • 먼저 score threshold로 거른다. 6300개 후보를 전부 정렬하면 O(N log N) 정렬 + O(N²) IoU다. threshold 0.3 이후 수십 개만 남기면 NMS는 수십 µs 수준이 된다. 반대로 threshold를 너무 낮추면 후처리 시간이 폭발한다.
  • top-k 제한: 정렬 전에 상위 k개(예: 100개)만 남기면 최악 시간을 bound할 수 있다. 펌웨어의 worst-case 실행 시간(WCET) 사고방식 그대로다.
  • 정수 좌표: 박스를 int16 픽셀 좌표로 두면 넓이 곱셈을 int32로 할 수 있고, inter / union > thr는 나눗셈 없이 inter > thr × union(고정소수점)으로 비교할 수 있다.
  • decode도 CPU 몫: anchor offset → 실제 좌표 변환(exp, sigmoid 포함)을 NPU 그래프에 넣을지 CPU에서 할지는 런타임마다 다르다. TFLite는 SSD 계열용 TFLite_Detection_PostProcess 같은 custom op로 decode+NMS를 묶어 제공한다.

4.6 mAP — 검출기는 어떻게 채점하나#

분류의 accuracy에 해당하는 검출 지표가 mAP(mean Average Precision)다. A4의 precision/recall을 그대로 쓴다.

  1. 한 class에 대해 모든 검출을 점수 내림차순으로 정렬한다.
  2. 각 검출을 정답 박스와 매칭한다: IoU ≥ 0.5(기준값)인 아직 안 쓴 정답이 있으면 TP, 없으면 FP.
  3. 위에서부터 하나씩 내려가며 누적 precision, recall을 계산한다 → PR 곡선.
  4. PR 곡선 아래 넓이 = AP. 모든 class의 AP 평균 = mAP.

COCO 벤치마크는 IoU 기준을 0.50, 0.55, …, 0.95 열 개로 바꿔 가며 평균한 값을 주 지표로 쓰고(박스를 정밀하게 맞출수록 점수가 오름), PASCAL VOC는 IoU 0.5 하나로 잰 mAP@0.5를 썼다. 논문 숫자를 비교할 때 어떤 mAP인지 확인해야 한다.

작은 예제로 AP를 계산한다. 정답 사람 4명, 검출 6개의 TP/FP가 이미 매칭돼 있다고 하자.

손으로 확인하면 recall이 0.25씩 네 번 오르고, 그때의 (보간된) precision이 1, 1, 0.75, 0.667이므로 AP = 0.25 × (1 + 1 + 0.75 + 0.667) = 0.854. 출력에서 볼 것: 각 행은 "점수 threshold를 거기에 두면 제품이 얻는 precision/recall"이다. 제품에서는 mAP 하나보다 이 표에서 동작점 하나를 고르는 것이 더 중요하다(A4의 ROC 동작점과 같은 이야기).

5. 분할(Segmentation) — 픽셀마다 답하기#

5.1 semantic vs instance#

  • Semantic segmentation: 픽셀마다 class 하나. 사람이 셋 있어도 "사람 픽셀"로 한 덩어리. 출력 [K, H, W] logits → 픽셀별 argmax → [H, W] mask.
  • Instance segmentation: 개체를 구별한다. 사람 1, 사람 2, 사람 3. 보통 검출기 + 박스마다 작은 mask(예: Mask R-CNN).
  • (참고) panoptic segmentation은 둘을 합친 것이다.

웨어러블 예시(추정): 배경 흐림이나 "손 영역만 잘라서 제스처 모델에 넣기"는 semantic으로 충분하다.

5.2 encoder-decoder와 U-Net#

분류 backbone은 해상도를 1/32로 줄인다. 분할은 원래 해상도의 mask가 필요하므로 다시 키워야 한다.

  • Encoder: 분류 backbone과 같다. 해상도를 줄이며 "무엇인지"를 알아낸다.
  • Decoder: upsampling(transposed conv나 보간)으로 해상도를 되돌린다.
  • Skip connection(U-Net): 줄이기 전의 고해상도 feature를 decoder에 채널로 이어 붙여(concatenate), 경계를 정확히 그리게 한다. 그림으로 그리면 U자 모양이라 U-Net이다.

5.3 코드로 — 출력 크기와 skip 메모리#

작은 U-Net을 만들어 128과 256 입력에서 각 텐서 모양과, decoder가 쓸 때까지 들고 있어야 하는 skip 텐서 메모리를 int8 기준으로 계산하는 코드다.

출력에서 볼 것: 파라미터는 57K(int8로 56 KB)밖에 안 되는데, 128×128에서 skip 텐서만 384 KB를 동시에 들고 있어야 한다. 해상도를 두 배로 하면 4배(1536 KB)가 된다. 분할 모델은 가중치가 아니라 activation이 메모리를 지배한다. 또 출력 자체가 이미지 크기라서 NPU → CPU로 옮기는 대역폭도 무시할 수 없다. 출력 logits 전체 대신 NPU 안에서 argmax까지 끝내고 1바이트 mask만 받으면 4배(class 수만큼) 줄어든다.

5.4 edge에서의 선택#

  • 출력을 입력보다 작게(예: 1/4 해상도 mask) 내고 필요하면 CPU에서 bilinear로 키운다.
  • torchvision에는 모바일용으로 deeplabv3_mobilenet_v3_large, lraspp_mobilenet_v3_large 같은 MobileNetV3 기반 분할 모델이 있다.
  • skip 텐서의 수명(lifetime)이 길다는 것은 메모리 planner 입장에서 "해제할 수 없는 큰 버퍼"다. 10절에서 다시 본다.

6. ViT — 이미지를 토큰으로#

6.1 직관: 이미지를 16×16 조각으로 잘라 "단어"처럼#

B4의 transformer는 토큰 열을 입력으로 받는다. ViT(Vision Transformer)의 아이디어는 단순하다. 이미지를 겹치지 않는 16×16 조각(patch)으로 자르고, 조각 하나를 토큰 하나로 쓴다. 논문 제목부터 "An Image is Worth 16x16 Words"다.

손으로 shape을 따라가 보자(224×224 RGB, patch 16, 폭 D=192).

  • Class token: 이미지 전체를 요약하라고 붙이는 빈 토큰. attention을 통해 모든 patch의 정보를 모은다. CNN의 global average pooling 역할이다(patch 토큰 평균을 쓰는 변형도 있다).
  • Position embedding: attention은 순서를 모른다(B4). "이 patch가 왼쪽 위"라는 정보를 벡터로 더해 준다. 학습된 197개 위치에 묶이므로, 해상도를 바꾸면 position embedding을 보간해야 한다.

그림 4 — ViT의 patchify. 224×224를 16 px 격자로 자르면 14×14 = 196 patch. 주황·파랑·초록 patch가 각각 토큰 p1, p2, p196이 된다. 맨 앞에 CLS 토큰을 붙여 197 토큰.

6.2 코드로 — patchify = stride 16 conv, 그리고 ViT 블록 하나#

reshape로 자른 patch에 Linear를 곱한 결과가, kernel=stride=16인 Conv2d와 정확히 같은 연산임을 확인하고, class token·position embedding·transformer 블록 하나를 통과시키는 코드다.

출력에서 볼 것:

  • patch 196개 × 768 숫자, 그리고 Linear와 Conv2d 결과가 같다(True). 배포 도구는 patch embedding을 보통 stride 16 conv 하나로 표현하므로, NPU 입장에서는 평범한 conv다.
  • 블록 하나 파라미터 444,864 = 12·D² + 13·D (QKV 3D², out proj D², FFN 8D², bias·LayerNorm 13D). D=192, 블록 12개면 약 5.3M으로, ViT-Tiny(DeiT-Ti, 약 5.7M)와 비슷한 크기다.

6.3 비용 — CNN과 무엇이 다른가#

ViT 블록의 MAC은 두 종류다(B4).

말로 하면, 해상도를 두 배로 하면 토큰이 4배, attention 행렬은 16배가 된다. ViT-Tiny 급(D=192, L=12)을 해상도별로 계산하는 코드다. torchvision의 ViT-B/16 파라미터 수도 같이 센다.

출력에서 볼 것:

  • 224에서 ViT-Tiny 급은 약 1.25G MACs다. 파라미터가 비슷한 MobileNetV2(3.5M, 300M MACs)의 4배 연산이다. 같은 파라미터 예산이면 ViT가 MAC을 훨씬 많이 쓴다. 파라미터 하나가 토큰 196개에 모두 재사용되기 때문이다.
  • attention 비중은 224에서 14%지만 448에서는 40%로 커진다. 고해상도 ViT의 비용은 attention이 지배하기 시작한다.
  • ViT-B/16은 86.6M 파라미터로, 모바일 분류 backbone의 25배쯤이다. CLIP이나 VLM의 비전 인코더가 이 급 이상인 경우가 많다.

7. CLIP — 이미지와 텍스트를 같은 공간에#

7.1 직관#

분류기는 "1000개 class 중 하나"만 말할 수 있다. 새 class("내 차 열쇠")를 추가하려면 head를 다시 학습해야 한다. CLIP(Contrastive Language-Image Pre-training)은 다르게 접근한다.

  • 이미지 인코더(ViT나 ResNet)와 텍스트 인코더(transformer) 두 개를 둔다.
  • 각각 D차원 벡터를 내고, L2 정규화해서 같은 공간에 놓는다.
  • 인터넷에서 모은 (이미지, 캡션) 쌍으로 "짝이 맞는 쌍은 코사인 유사도가 높고, 안 맞는 쌍은 낮게" 학습한다. 원 논문은 약 4억 쌍을 썼다.

학습이 끝나면 zero-shot 분류가 된다. class 이름을 "a photo of a {class}" 문장으로 만들어 텍스트 인코더에 넣고, 이미지 벡터와 가장 유사도가 높은 문장을 고르면 된다. 새 class를 추가하는 것은 문장 하나를 추가하는 것뿐이다. 펌웨어로 비유하면, 매번 새 명령마다 디코더 로직을 다시 합성하는 대신 명령을 "해시"해서 테이블과 비교하는 구조로 바꾼 셈이다.

7.4 edge에서의 CLIP#

  • 텍스트 쪽은 미리 계산: zero-shot class 문장이 고정이면 텍스트 임베딩을 오프라인에서 계산해 [K, D] 테이블로 flash에 둔다. 기기에서는 이미지 인코더 + 내적 K번만 돈다. D=512, K=100이면 int8로 50 KB다.
  • 이미지 검색·기억: 사진마다 임베딩 벡터만 저장해 두면 "지난주 본 빨간 우산"을 텍스트 임베딩과의 코사인으로 찾을 수 있다(웨어러블의 "기억" 기능 예시, 추정).
  • 이미지 인코더가 ViT-B 급이면 수십억 MAC이라 MCU가 아니라 SoC NPU 몫이다. MobileCLIP처럼 모바일용으로 줄인 CLIP 계열도 연구되고 있다.

8. VLM — 이미지를 LLM에 넣는 법#

8.1 구조: vision encoder → projector → LLM#

VLM(Vision-Language Model)은 "이미지를 보고 말로 답하는 LLM"이다. 가장 널리 알려진 단순한 구조가 LLaVA 계열이다.

  • Vision encoder: 보통 CLIP 계열로 사전학습된 ViT. 마지막 층(또는 끝에서 두 번째 층)의 patch 토큰 전부를 쓴다. 분류처럼 CLS 하나만 쓰는 게 아니다.
  • Projector: 비전 임베딩 폭을 LLM 폭으로 바꾸는 작은 네트워크. LLaVA 원본은 Linear 하나, LLaVA-1.5는 2층 MLP였다.
  • LLM 입장에서는 이미지 토큰이 그냥 "576개 단어가 먼저 들어온 것"이다.

8.2 비용: 이미지 토큰 수 = LLM의 prefill 길이#

B8·L 모듈에서 볼 것처럼, LLM 추론은 두 단계다. 입력 토큰 전체를 한 번에 처리하는 prefill(연산 위주)과 한 토큰씩 생성하는 decode(대역폭 위주). 이미지 토큰은 prefill 길이를 늘리고, KV cache(토큰마다 층마다 저장하는 K, V 벡터)도 그만큼 키운다.

그래서 VLM들은 이미지 토큰 압축을 한다.

  • Pixel shuffle / token merge: 이웃한 2×2 토큰 4개를 채널 방향으로 이어 붙여 토큰 1개로 만든다. 토큰 수 1/4, 폭 4배. 그 뒤 projector가 폭을 줄인다. InternVL, SmolVLM 등 여러 VLM이 이런 방식을 쓰는 것으로 알려져 있다.
  • Query 기반 resampler: 고정 개수(예: 32개)의 학습 query 토큰이 cross-attention으로 이미지 정보를 뽑아 온다. BLIP-2의 Q-Former, Flamingo의 Perceiver Resampler가 이 계열이다.
  • 해상도 낮추기 / 필요한 영역만 crop: 제일 단순하고 제일 효과가 크다(해상도² 법칙).

2×2 merge를 텐서 모양으로 확인하고, 1B급 LLM에서 이미지 토큰 수가 prefill 연산량과 KV cache를 얼마나 바꾸는지 계산하는 코드다. LLM 설정(16층, KV head 8개, head 폭 64, fp16 KV)은 Llama-3.2-1B와 비슷한 값을 가정한 것이고, 2 TFLOP/s 실효 성능도 가정이다.

출력에서 볼 것:

  • 이미지 한 장이 576 토큰이다. 짧은 질문("이게 뭐야?")은 5~10 토큰이므로, 입력의 대부분이 이미지다.
  • 2×2 merge로 토큰을 144개로 줄이면 prefill 연산과 KV cache가 정확히 1/4이 된다. 가정한 실효 성능에서 첫 토큰까지 시간(TTFT)이 576 ms → 144 ms. 사용자가 "이게 뭐야?"라고 물은 뒤 체감하는 지연이 여기서 결정된다.
  • 이 계산에 비전 인코더 자체 비용(ViT-L 급이면 수십~수백 GMAC)은 들어 있지 않다. 실제로는 인코더 + prefill + decode를 모두 더해야 한다.

8.3 멀티모달 웨어러블에서의 의미 (추정)#

예를 들어 Hark 같은 기기에 카메라가 있다면, 합리적인 구성은 이런 계층일 것이다(모두 추정).

  • 항상: MCU/저전력 NPU에서 저해상도 존재 감지(9절).
  • 사용자 요청 시: SoC NPU에서 이미지 인코더 실행, 토큰 압축.
  • LLM은 기기 SLM 또는 클라우드(L 모듈의 hybrid edge-cloud). 클라우드로 보낼 때 원본 이미지 대신 이미지 임베딩/토큰을 보내면 대역폭과 프라이버시 측면에서 유리할 수 있지만, 서버 쪽 모델과 인코더 버전이 묶이는 문제가 생긴다.

9. Always-on 비전 — 웨어러블에서 사람 감지#

9.1 문제 설정#

"카메라를 항상 켜 두고 VLM을 돌린다"는 전력상 불가능하다(아래 계산). 대신 음성의 wake word(B5)와 같은 cascade를 쓴다.

  • Visual Wake Words(VWW): 이 문제를 벤치마크로 만든 데이터셋이다. COCO 이미지를 "사람 있음 / 없음" 두 class로 다시 라벨링했고, 마이크로컨트롤러용 비전의 대표 과제다. MLPerf Tiny 벤치마크에 Visual Wake Words 과제가 포함되어 있고, 참조 모델은 96×96 입력의 폭을 줄인(0.25배) MobileNetV1이다.
  • 입력은 작게: 96×96이면 3.2절 표에서 MobileNetV3-Small도 12M MACs이고, 폭을 줄이면 수 M MACs까지 내려간다.
  • Event camera(DVS): 픽셀마다 밝기 변화가 있을 때만 비동기 이벤트를 내는 센서다. 정지 장면에서는 데이터가 거의 없어 always-on에 흥미로운 대안이지만, 출력 형식이 프레임이 아니어서 모델과 도구가 다르다. 참고로만 알아 두자.

9.2 전력 계산 — duty cycling#

아래 모든 전력·시간 값은 설명용 가정이다(특정 칩 데이터시트가 아님). 구조는 Don이 RF 칩 전력 margin을 볼 때와 같다: 평균 전력 = sleep 전력 + (이벤트당 에너지 × 이벤트율).

말로 하면, 평균 전력은 "잠자는 바닥 전력 + 1초에 찍는 프레임 수만큼의 프레임 에너지 + 그중 SoC를 깨우는 비율만큼의 큰 비용"이다.

출력에서 볼 것:

  • MCU 단계만 보면 1 fps에서 약 1 mW로, 150 mAh 배터리로 500시간 이상이다(카메라만의 예산, 다른 기능 제외).
  • 그런데 SoC를 깨우는 비율이 5%만 돼도 평균 전력이 16배가 된다. 50%면 4시간. always-on 설계의 핵심은 1단계 모델의 MAC이 아니라 1단계의 false positive율이다. B5 wake word, A2 9절 Bayes 계산과 똑같은 구조다.
  • 그래서 1단계에 "N프레임 연속 감지"(debounce), "IMU로 기기가 움직일 때만 카메라 켜기" 같은 게이팅을 붙인다. 펌웨어 엔지니어가 가장 잘하는 부분이다.

10. 임베디드 관점에서 다시 보기#

10.1 activation 메모리 — 비전 모델의 진짜 병목#

MCU에서 비전 모델이 안 들어가는 이유는 대개 가중치(flash)가 아니라 activation(SRAM)이다. 레이어 하나를 실행하는 순간 적어도 입력 텐서와 출력 텐서가 동시에 메모리에 있어야 한다. MobileNetV2의 conv마다 (입력 + 출력) 크기를 hook으로 재서 최댓값(peak)을 찾는 코드다(int8, 1바이트/원소 가정).

손으로 확인: peak 지점은 두 번째 inverted residual 블록의 depthwise conv(stride 2)다. 입력 96·112·112 = 1,204,224 + 출력 96·56·56 = 301,056 = 1,505,280 바이트 = 1470 KB. expand 1×1 conv가 채널을 16 → 96으로 6배 늘린 고해상도 텐서라 크다.

출력에서 볼 것:

  • peak는 앞쪽(고해상도) 블록에 있다. 뒤쪽 conv는 수십 KB뿐이다. 가중치는 뒤쪽에 몰려 있고(2.3절), activation은 앞쪽에 몰려 있다.
  • peak도 해상도²를 따른다: 1470 → 750 → 270 KB (비율 0.51, 0.18). 96×96이면 270 KB로 SRAM 512 KB급 MCU에 들어갈 여지가 생긴다(여기에 residual 연결로 들고 있는 텐서와 런타임 오버헤드가 더해지므로 실제 arena는 이보다 크다).
  • 해법들: (1) 해상도를 낮춘다, (2) 앞쪽 블록의 폭(expand ratio)을 줄인다, (3) 앞쪽 몇 층을 이미지 조각(patch) 단위로 나눠 실행해 peak를 줄이는 patch-based inference(MCUNetV2의 아이디어), (4) 메모리 planner가 수명이 끝난 버퍼를 재사용하게 한다. 펌웨어의 버퍼 풀 설계, DMA 타일링과 같은 발상이다.

10.3 int8 친화성#

  • 좋음: conv, depthwise conv, ReLU/ReLU6, add, avg pool. MobileNetV2가 오래 표준인 이유 중 하나다.
  • 주의: h-swish/swish(비선형 LUT나 근사 필요), SE 블록(global pooling → 작은 FC → 곱하기, 스칼라 곱의 동적 범위), 첫 conv(입력 정규화 흡수), depthwise conv의 채널별 범위 차이(per-channel 양자화 필요).
  • 어려움: ViT의 softmax·LayerNorm·GELU, attention 행렬의 큰 값(outlier). int8 PTQ에서 정확도가 많이 떨어지면 이 연산들을 fp16으로 남기는 혼합 정밀도를 쓴다(C 모듈).
  • 검출 head: 박스 좌표(회귀값)와 class 점수는 범위가 전혀 달라서, 하나의 텐서로 합쳐 양자화하면 좌표 정밀도가 망가진다. 출력 텐서를 분리해서 각자 scale을 갖게 한다.

10.4 NPU 뒤의 CPU — 파이프라인 관점#

(시간은 예시.) NPU 벤치마크 숫자(backbone만)와 실제 end-to-end 지연이 다른 이유가 이 그림이다. 전처리·decode·NMS·메모리 복사(캐시 flush/invalidate 포함)는 CPU 시간이고, NPU 입력/출력 레이아웃이 모델과 다르면 transpose가 추가된다(A1). 프로파일은 항상 카메라 프레임 도착부터 결과까지로 잰다.

12. 면접에서 이렇게 말한다#

Q. How does non-maximum suppression work, and where does it run on an edge device?

A. 검출기는 칸마다 박스를 내서 한 물체에 겹친 박스가 여러 개 나온다. NMS는 점수 threshold로 거른 뒤 점수순으로 정렬하고, 최고점 박스를 확정한 다음 그 박스와 IoU가 임계값(보통 0.5 안팎)을 넘는 박스를 지우는 것을 반복한다. class별로 따로 돌린다. 분기와 데이터 의존 반복이 많아 NPU에 안 맞으므로 보통 NPU 출력 뒤 CPU에서 돈다. 최악 시간을 bound하려고 top-k 제한을 둔다.

Detectors predict many overlapping candidate boxes per object. NMS filters by a score threshold, sorts the rest by score, keeps the top box, removes every remaining box whose IoU with it exceeds a threshold — typically around 0.5 — and repeats, usually per class. It's branchy, data-dependent code, so on a device it normally runs on the CPU after the NPU produces boxes and scores. I cap the candidates with a score threshold and a top-k so the worst-case latency is bounded.

Q. What is IoU? Compute it for two 40×40 boxes offset by 20 pixels in both x and y.

A. 교집합 넓이를 합집합 넓이로 나눈 값이다. 두 박스가 x, y 모두 20 px씩 어긋나면 교집합은 20×20 = 400, 합집합은 1600 + 1600 − 400 = 2800이라 IoU ≈ 0.14다. 조금만 어긋나도 IoU가 크게 떨어지고, 작은 물체일수록 같은 픽셀 오차에 더 민감하다.

IoU is intersection area over union area. Here the overlap is 20 by 20, so 400, and the union is 1600 plus 1600 minus 400, which is 2800 — an IoU of about 0.14. It's a strict metric, and small objects are hit hardest because the same pixel error is a larger fraction of the box.

Q. Why does input resolution dominate the cost of a vision model?

A. conv의 MAC은 출력 H·W × 채널 × 커널이고, 해상도를 바꾸면 모든 feature map의 H·W가 한 변²에 비례해 바뀐다. 직접 세어 보니 MobileNetV2가 224에서 301M, 96에서 56M MACs로 (96/224)² = 0.18배를 그대로 따랐다. peak activation도 1470 KB에서 270 KB로 같이 줄었다. 가중치는 그대로다. 그래서 MCU에 넣을 때 가장 먼저 해상도를 조정한다.

Conv cost is output height times width times channels times kernel size, and every feature map's area scales with the square of the input side. When I counted it, MobileNetV2 went from about 301 million MACs at 224 to 56 million at 96 — exactly the (96/224)² ratio — and the peak activation memory dropped from about 1.5 MB to 270 KB, while the weights didn't change at all. So resolution is the first knob I turn for an MCU target.

Q. ViT vs CNN on the edge — which would you pick?

A. 기기와 태스크에 따라 다르다. MCU나 always-on에서는 CNN이다: 연산이 conv라 CMSIS-NN 같은 커널이 성숙했고, int8 양자화가 잘 되고, 해상도가 층마다 줄어서 메모리가 작다. ViT는 같은 파라미터로 MAC이 훨씬 많고(ViT-Tiny 급 224에서 약 1.25G vs MobileNetV2 0.3G), softmax·LayerNorm의 int8 처리가 까다롭고, attention이 토큰 수²로 커진다. 반면 transformer를 잘 지원하는 NPU가 있고 CLIP·VLM처럼 사전학습된 ViT 인코더가 필요하면 ViT가 맞다. 이때는 벤더 SDK가 attention과 LayerNorm을 NPU에서 돌리는지, CPU로 fallback하는지부터 확인한다.

It depends on the target. For an MCU or an always-on path I'd pick a CNN: convs have mature int8 kernels, quantization is well-behaved, and the feature maps shrink, so memory is small. A ViT spends far more MACs per parameter — a ViT-Tiny-sized model is about 1.25 GMACs at 224 versus 0.3 for MobileNetV2 — attention grows with the square of the token count, and softmax and LayerNorm are harder in int8. On an NPU with good transformer support, and when I need a pretrained ViT encoder for CLIP or a VLM, a ViT is the right choice — and the first thing I'd check is whether the vendor stack keeps attention and LayerNorm on the NPU or falls back to the CPU.

Q. How would you run person detection always-on on a wearable?

A. cascade로 한다. 1단계는 저해상도 흑백(96×96 안팎) 카메라를 1 fps 정도로 켜고, MCU에서 Visual Wake Words 급 작은 CNN으로 사람 유무만 본다. 프레임당 수 mJ 이하, 평균 mW 이하가 목표다. 여러 프레임 연속 감지나 IMU 움직임으로 게이팅한 뒤에만 SoC를 깨워 고해상도 검출이나 VLM을 돌린다. 전력 계산을 해 보면 1단계의 MAC보다 SoC를 얼마나 자주 깨우는지(false positive율)가 배터리를 결정하므로, 동작점은 FP율 기준으로 잡는다.

I'd build a cascade. The first stage keeps a low-res grayscale sensor — around 96×96 at about one frame per second — and runs a tiny Visual-Wake-Words-style CNN on the MCU that only answers "is a person present". That's around a millijoule per frame and a milliwatt average. Only after debouncing over several frames, or gating with the IMU, do I wake the SoC for high-resolution detection or a VLM. When you do the power math, the false-positive rate of the first stage — how often it wakes the big core — dominates battery life, so I'd pick the operating point on that, not on accuracy alone.

Q. How does CLIP enable zero-shot classification?

A. 이미지 인코더와 텍스트 인코더를 대규모 (이미지, 캡션) 쌍으로 contrastive 학습해서 같은 벡터 공간에 둔다. 배치의 B×B 코사인 유사도 행렬에서 대각선이 정답인 대칭 cross-entropy(InfoNCE)를 쓴다. 추론 때는 class 이름을 "a photo of a …" 문장으로 만들어 텍스트 임베딩을 미리 계산해 두고, 이미지 임베딩과 코사인이 가장 큰 것을 고른다. 기기에서는 텍스트 임베딩 테이블을 flash에 두고 이미지 인코더와 내적만 돌리면 된다.

CLIP trains an image encoder and a text encoder contrastively on image–caption pairs so they share an embedding space; the loss is a symmetric cross-entropy over the batch's cosine-similarity matrix, with the matching pairs on the diagonal. For zero-shot classification you embed prompts like "a photo of a dog" once, then pick the class whose text embedding has the highest cosine similarity with the image embedding. On a device the text embeddings are just a precomputed table, so you only run the image encoder and a few dot products.

Q. What drives the latency of a VLM on device?

A. 비전 인코더 비용 + 이미지 토큰이 늘린 LLM prefill + decode다. 336 px, patch 14면 이미지 한 장이 576 토큰이라 짧은 질문보다 훨씬 길다. 1B급 LLM에서 prefill 연산과 KV cache가 토큰 수에 비례하므로, 2×2 token merge로 144 토큰으로 줄이면 둘 다 1/4이 된다. 그래서 해상도, crop, 토큰 압축이 첫 응답 지연의 주 손잡이다.

It's the vision encoder, plus the LLM prefill that the image tokens add, plus decode. A 336-pixel image with 14-pixel patches is 576 tokens — far longer than the question — and both prefill compute and KV-cache size scale with that count. Merging 2×2 neighboring tokens cuts it to 144 and both costs by 4×. So resolution, cropping and token compression are the main levers on time-to-first-token.

15. 요약 & 체크리스트#

비전 모델은 출력 모양으로 구분한다: 분류는 [K], 검출은 박스 목록, 분할은 [K, H, W], CLIP은 [D] 임베딩, VLM은 텍스트다. 어떤 태스크든 앞단에는 전처리(resize·정규화·레이아웃)가, 뒷단에는 CPU 후처리(NMS·argmax·decode)가 붙고, 둘 다 end-to-end 지연과 전력에 들어간다. 비용의 주 손잡이는 입력 해상도다. MACs, peak activation, 입력 버퍼가 모두 한 변²에 비례하고(MobileNetV2 224 → 96: 301M → 56M MACs, 1470 KB → 270 KB), 가중치는 변하지 않는다. ViT는 이미지를 patch 토큰으로 바꿔 transformer에 넣으며, 파라미터당 MAC이 많고 int8이 까다로워 MCU보다는 transformer 지원이 좋은 NPU에 맞다. CLIP은 두 인코더를 InfoNCE로 같은 공간에 맞춰 zero-shot 분류와 검색을 가능하게 하고, VLM은 그 비전 인코더의 토큰을 LLM에 넣는다. 이때 이미지 토큰 수가 prefill 연산과 KV cache를 결정한다. 웨어러블의 always-on 비전은 저해상도·저fps 1단계와 드물게 깨어나는 2단계의 cascade이며, 배터리는 1단계의 false positive율이 좌우한다.
