0. 큰 그림 — "ML 기능을 테스트했다"는 말은 무슨 뜻인가#

SSD 펌웨어에서 "테스트 끝났다"는 말의 뜻은 분명했다. 명령 하나하나가 스펙대로 응답하고, 데이터가 비트 단위로 같고, 전원 차단 후에도 매핑 테이블이 살아 있고, 성능이 스펙 + margin 안이다. 모든 판정이 결정적(deterministic) 이다. 같은 입력이면 같은 출력이고, 다르면 버그다.

ML 기능이 들어가면 판정의 성격이 바뀐다. "손목 튕기기 제스처 인식"이라는 기능에는 정답 출력이 정해진 입력이 없다. 사람마다 동작이 다르고, 모델은 일부를 틀린다. 그래서 테스트가 두 종류로 갈라진다.

  • 결정적인 부분 — 링버퍼, 특징 추출, requant, 파서, 상태 기계, 프로토콜. 여기는 SSD 펌웨어와 똑같이 비트 단위로 검사한다.
  • 통계적인 부분 — "이 데이터 묶음에서 recall 90% 이상, 시간당 오검출(FA/h) 0.1 이하". 여기는 데이터 묶음이 곧 스펙이고, 판정은 숫자와 신뢰구간이다.

이 노트의 일은 이 둘을 한 제품의 테스트 전략으로 묶는 것이다. 검증 방법론의 세부(golden vector를 만드는 법, bit-exact냐 tolerance냐, 레이어별 diff, bootstrap 신뢰구간)는 C8에 이미 있다. 여기서는 그것들이 어느 층에서, 어떤 빌드로, 얼마나 자주, 어떤 장비로 도는지를 설계한다.

핵심 규칙 세 가지.

  • 결정적인 것은 아래 층에서 끝낸다. requant 반올림 버그를 HIL에서 정확도 0.3%p 하락으로 발견하면 원인을 찾는 데 하루가 걸린다. unit에서는 1초다.
  • 통계적인 것은 replay 층에서 주로 잰다. host에서는 수백 시간 분량의 녹음을 몇 분에 재생할 수 있다. HIL에서는 실시간이라 그만큼 못 돌린다.
  • HIL은 "host에서 원리상 못 보는 것"만 맡긴다. 타이밍, 실제 드라이버 경로, 전력, 실제 컴파일러 산출물. host에서 볼 수 있는 것을 HIL로 보면 느리고 flaky해진다.

0.3 이 노트의 공용 예제 — 손목 제스처 검출기#

예를 들어 Hark 같은 웨어러블이라면 손목을 튕기는 제스처로 무언가를 켤 수 있을 것이다(가정이다). 이 노트의 모든 예제는 아래 장난감 파이프라인 하나를 대상으로 한다. 실제 모델 대신 정수 가중치의 선형 점수를 쓰지만, 테스트 구조는 진짜 모델이어도 똑같다.

소스는 C 파일 하나(mlfw.c)와 헤더 하나다. 이 소스가 제품 펌웨어와 모든 테스트 빌드에 똑같이 들어간다는 것이 이 노트 전체의 전제다.

구현(mlfw.c)은 각 절에서 그 절이 테스트하는 부분만 보여 준다. 일부러 #ifdef BUG_... 스위치를 넣어 두었다. 테스트가 버그를 실제로 잡는지 확인하려면 버그를 넣어 봐야 하기 때문이다(mutation testing의 손작업 판).

1. Unit test — host에서 C를 검사한다#

1.1 왜 host인가, 그리고 host로 안 되는 것#

host(맥북·리눅스 서버)에서 C를 테스트하는 이유는 세 가지다. 빠르다(수천 개 테스트가 1초), 도구가 있다(sanitizer, coverage, 디버거), CI 서버에서 하드웨어 없이 돈다.

대신 host는 타깃과 다르다. 그 차이를 알고 있어야 "host에서 통과했는데 기기에서 깨지는" 일을 줄일 수 있다.

1.2 최소 테스트 프레임워크 — 헤더 하나#

Unity, CppUTest, GoogleTest 같은 프레임워크가 있다. 그런데 핵심은 매크로 몇 개다. 직접 써 보면 프레임워크가 무엇을 해 주는지 정확히 알게 된다. 아래가 이 노트에서 쓰는 전부다.

설계 포인트를 짚어 보자.

  • CHECK_EQ는 실패해도 멈추지 않는다. 한 번 돌릴 때 실패를 전부 보는 편이 빠르다. (Unity의 TEST_ASSERT는 기본적으로 그 테스트 함수를 빠져나간다. 둘 다 장단이 있다.)
  • #act로 실패한 식 자체를 출력하고, __FILE__:__LINE__으로 위치를 찍는다. CI 로그에서 바로 클릭해 갈 수 있다.
  • mt_case는 table-driven test에서 몇 번째 행이 깨졌는지 알려 준다. 이게 없으면 34번째 줄이 깨졌다는 것만 알고 어느 입력인지 모른다.
  • TEST_REPORT()가 실패 시 0이 아닌 값을 돌려주고, 그게 main의 반환값 = 프로세스 exit code가 된다. CI는 exit code만 본다.

1.3 테스트 대상 코드 — ring, feature, requant#

requant는 C8 3.4절의 규격(gemmlowp 방식)을 단순화한 것이다. 여기서 중요한 것은 규격 자체가 아니라 무엇을 테스트해야 하는가다.

  • ring의 head - tail은 uint32_t 뺄셈이라 head가 2³²를 넘어 0으로 돌아가도 개수가 맞다. 이걸 테스트하려고 2³²번 push할 수는 없다 → 내부 상태를 직접 경계 근처로 세팅한다.
  • iabs(-32768)은 int32에서는 32768로 문제없다(int16이었다면 오버플로). L1 크기 최댓값은 3 × 32768 = 98304, 이게 int32에 들어간다는 것을 테스트로 고정한다.
  • requant는 반올림 방향(+0.5가 양수·음수에서 어떻게 되나)과 포화가 버그의 90%다.

1.6 테스트를 테스트한다 — 버그를 넣고 돌려 본다#

무엇을 확인하는 코드인가: 포화를 빼먹은 requant와 int32 누산기 feature 버그를 넣었을 때 테스트가 빨개지는지.

출력에서 볼 것: 포화가 없으면 5000이 int8로 잘려 −120이 된다(5000 mod 256 = 136 → −120). 이게 실제 기기에서는 "큰 소리일 때만 모델이 이상해진다"는 증상으로 나타난다. int32 누산기 버그는 64 × 2,415,919,104 = 2³⁷ + 2³⁴이 정확히 2³²의 배수라서 0이 나왔다. 그리고 주목할 점 — -Wall -Wextra로도 int64 → int32 대입 경고가 안 나왔다. -Wconversion이 없으면 컴파일러는 침묵한다. 경고 플래그는 테스트를 대신하지 못한다.

수정 전 손계산 테스트(test_feat_hand_computed)는 버그가 있어도 통과했다는 점도 보자. 작은 값만 쓰는 테스트는 오버플로를 못 잡는다. 경계값 행이 따로 있어야 한다.

1.7 Coverage — 무엇을 안 돌렸나#

coverage는 "테스트가 실행한 코드의 비율"이다. 높다고 맞는 건 아니지만, 낮은 곳은 확실히 검사 안 된 곳이다. Apple clang에는 LLVM source-based coverage가 들어 있다(-fprofile-instr-generate -fcoverage-mapping). Makefile에 타깃을 하나 추가한다.

(파일 요약 줄은 같은 TOTAL이라 생략했다.)

출력에서 볼 것: ring·feature·requant는 줄 기준 100%지만 branch는 아니다. ring_init의 branch 6개 중 2개(!mem, size < 2)를 안 밟았고, feat_frame도 2개(!xyz, !o)를 안 밟았다. 그리고 EMA·detector·파서는 0%다. 이 표가 다음 할 일을 알려 준다 — 상태 기계와 파서는 2절(성질·fuzz)과 3절(replay)이 맡는다.

coverage를 쓸 때의 주의.

  • 줄 coverage 100% ≠ 맞다. BUG_NO_SAT 빌드도 requant 줄 coverage는 100%다. 포화 줄이 아예 없으니까. coverage는 "없는 코드"를 못 본다.
  • ML 코드는 데이터 경로가 중요하다. conv 커널의 모든 줄을 실행해도 padding 경계, stride > 1, 채널 수가 SIMD 폭의 배수가 아닌 경우를 안 밟았을 수 있다. 이건 coverage가 아니라 입력 공간 설계(경계값, 2절의 성질 테스트, J3의 무작위 shape)로 잡는다.
  • CI에서 coverage를 게이트로 쓰기보다 추세로 본다. "새 코드의 branch coverage가 기존보다 낮으면 경고" 정도가 현실적이다.

gcov 방식(--coverage, gcov, lcov)은 GCC 쪽 도구이고 원리는 같다. 타깃 크로스 컴파일러가 GCC라면 타깃용 coverage는 gcov 계열을 쓰게 되는데, 기기에서 .gcda를 꺼내 오는 과정(semihosting 또는 RAM 덤프)이 필요해서 보통은 host coverage만 본다.

  • printf 출력 비교로 판정한다: 포맷이 바뀌면 다 깨진다. 값으로 비교한다.

2. Property-based test와 fuzz — 입력을 사람이 고르지 않는다#

2.1 직관 — 점 검사 vs 성질 검사#

1절의 테스트는 점(example) 을 검사했다. "이 입력이면 이 출력". 사람이 고른 점이라 사람이 생각 못 한 입력은 영원히 검사되지 않는다. 1.6절에서 손계산 4샘플 테스트가 오버플로를 못 잡은 것이 그 예다.

property-based test(성질 기반 테스트)는 거꾸로 간다. 출력값을 정하지 않고 모든 입력에서 성립해야 하는 성질을 적는다. 그다음 입력을 무작위로 수백~수천 개 만들어 성질을 검사한다. 깨지는 입력이 나오면 그 입력을 가장 작은 형태로 줄여서(shrink) 보여 준다. Python의 Hypothesis, Haskell의 QuickCheck가 대표적 도구다.

Don에게 익숙한 말로 하면, SSD에서 "임의의 LBA·길이·순서로 write를 퍼붓고 read-back이 항상 같아야 한다"는 랜덤 스트레스 테스트가 property test다. 성질은 "read-back == 마지막으로 쓴 값"이다.

BUG_VAR_I32 버전에서 아래 성질 테스트가 찾아낸 최소 반례는 4샘플, 마지막 샘플만 (0, −24513, −32768)인 입력이다. 손으로 확인해 보자.

말로 하면, 샘플 4개만으로도 하나가 크게 튀면 제곱합이 int32를 넘는다. 손목 기기에서 "책상에 탁 내려놓는 순간"이 정확히 이런 입력이다. 사람이 "64샘플 전부 최댓값" 같은 극단만 생각하면 놓치는 반례를, 생성기 + 축소가 4샘플짜리로 줄여서 보여 준다.

2.4 ctypes로 C를 Python에서 부른다#

property tester는 Python으로 쓰는 게 편하다(생성·축소·참조 구현이 쉽다). C 라이브러리를 shared library로 빌드하고 ctypes로 부른다. 같은 mlfw.c다.

ctypes.Structure의 필드 순서·타입은 C 구조체와 정확히 같아야 한다. feat_t는 int32, int64, int32라서 C에서 패딩이 들어가는데(int64 정렬), ctypes도 같은 ABI 규칙으로 패딩을 넣으므로 맞는다. 헤더가 바뀌면 여기도 바꿔야 한다는 것이 이 방식의 유지비다. (규모가 커지면 cffi나 헤더에서 바인딩을 생성하는 도구를 쓴다.)

2.5 50줄짜리 property tester#

무엇을 확인하는 코드인가: 생성 → 검사 → 축소 루프를 직접 만들어 본다.

설계 포인트.

  • 경계값 편향: 30% 확률로 EDGE(0, ±1, 최대·최소)에서 뽑는다. 균등 난수만 쓰면 −32768이 나올 확률은 1/65536이다. 버그는 경계에 몰려 있다.
  • 길이도 무작위: n = 1, 2, 3(SIMD 폭이 아닌 크기), 8, 64, 256. 커널 버그의 상당수는 "길이가 4의 배수가 아닐 때"다.
  • seed 고정: 실패를 재현할 수 있어야 한다. CI에서는 seed를 로그에 찍고, 실패한 seed를 회귀 테스트로 고정한다.
  • shrink: 실패한 입력에서 출발해 "더 작은 후보" 중 여전히 실패하는 것으로 계속 이동한다. 256샘플짜리 반례보다 4샘플짜리 반례가 디버깅하기 백 배 쉽다.

이제 성질을 적는다. 참조 구현은 Python 정수(무한 정밀도)라서 오버플로가 없다.

출력에서 볼 것: 버그판은 첫 시도(trial 0) 에서 깨졌고, 23단계 축소 끝에 2.3절에서 손으로 확인한 4샘플 반례가 나왔다. 참조 비교(matches_ref)뿐 아니라 참조 없이 쓴 불변식(bounds: var ≥ 0)도 같은 버그를 잡았다 — 오버플로가 분산을 음수로 만들었기 때문이다. 참조 구현이 없는 코드(예: 벤더 DSP 라이브러리)에서는 이런 참조 없는 불변식이 유일한 무기다. const_zero_var와 axis_perm은 버그판에서도 통과했다. 성질 하나가 모든 버그를 잡지는 않으므로 여러 개를 건다.

그림 3 — property test 루프. 실패 입력을 그대로 보고하지 않고 축소해서 보고하는 것이 핵심이다. 찾은 반례는 1절의 표(table-driven test)에 한 행으로 추가해 영원히 고정한다.

2.6 상태가 있는 코드의 성질 — EMA와 detector#

무엇을 확인하는 코드인가: 단조성·무 overshoot, reset 멱등성, 그리고 고정소수점 EMA의 수렴 성질.

먼저 EMA 구현을 보자.

출력에서 볼 것: 단조성과 reset 멱등성은 통과. 그런데 수렴 성질이 작은 alpha에서 깨진다. 이것은 코딩 실수가 아니라 고정소수점 EMA의 dead band다. 손으로 보자.

말로 하면, 스무딩을 세게 걸수록(α 작게) 출력이 목표값 근처에서 멈춰 버린다. 제스처 점수에서 327 LSB는 무시해도 되지만, 같은 코드를 배터리 전압이나 온도 보정에 쓰면 문제가 된다. 고치는 법은 y를 더 많은 소수 비트로 들고 있거나(예: Q16 확장 상태), 잘라 내기 대신 반올림하는 것이다(반올림하면 overshoot 성질을 다시 확인해야 한다). property test는 이렇게 스펙이 정하지 않은 동작을 드러내서 결정을 강요한다. "수렴 오차 몇 LSB까지 허용?"을 스펙에 적게 된다.

2.7 Fuzz — 파서를 망가진 바이트로 두드린다#

fuzzing은 property test의 극단적인 형태다. 성질은 단 하나 — "어떤 입력에도 죽지 않는다(메모리 오류·UB·무한 루프 없음)". 대신 입력은 바이트열이고 수백만 개를 넣는다.

coverage-guided fuzzer(libFuzzer, AFL++)는 실행한 코드 경로를 계측해서, 새 경로를 연 입력을 씨앗(corpus)으로 남기고 그걸 변형한다. 그래서 무작위 바이트로는 절대 통과 못 할 CRC 검사 뒤쪽까지 들어간다. 오류 검출은 보통 sanitizer가 한다.

  • AddressSanitizer(ASan): 버퍼 경계 밖 읽기·쓰기, use-after-free를 즉시 잡는다. 메모리 주변에 redzone을 두고 모든 접근을 검사한다.
  • UndefinedBehaviorSanitizer(UBSan): signed 오버플로, 잘못된 shift, 정렬 위반 등 C의 UB를 잡는다.

ML 펌웨어에서 fuzz 대상은 외부에서 바이트가 들어오는 모든 곳이다.

대상왜 위험한가
host ↔ 기기 명령 프로토콜케이블·BLE에서 무엇이든 들어온다
센서 패킷 파서 (IMU FIFO 프레임, 오디오 헤더)센서 글리치, 버스 오류가 쓰레기를 만든다
모델 파일 로더 (FlatBuffer, 자체 헤더)OTA로 받은 모델이 깨졌을 수 있다 (J5). TFLite의 FlatBuffer도 verifier 없이 읽으면 경계 밖 접근

파서 코드와 일부러 넣은 off-by-one을 보자.

프레임은 sync 1 + len 1 + type 1 + payload len + crc 1 = len + 4 바이트다. 버그판은 len + 3바이트만 있어도 진행해서 buf[3 + len] = buf[n], 즉 버퍼 끝 다음 바이트를 읽는다. 실기기에서는 이게 거의 항상 "우연히 동작"한다. 다음 바이트가 메모리에 있긴 하니까.

먼저 libFuzzer를 시도했다. Apple clang 21은 -fsanitize=fuzzer를 옵션으로는 받지만 런타임 라이브러리가 Command Line Tools에 들어 있지 않다.

리눅스 CI(upstream clang)나 Homebrew LLVM에서는 이 플래그가 그대로 동작한다. 그래서 fuzz 대상은 libFuzzer 진입점 LLVMFuzzerTestOneInput 형태로 쓰고, 맥에서는 같은 함수를 부르는 자체 랜덤 드라이버 + ASan/UBSan으로 돌린다. 코드 한 벌이 양쪽에서 쓰인다.

두 가지 요령이 들어 있다. 첫째, 입력 버퍼를 정확히 n바이트로 malloc한다. 큰 정적 버퍼에 넣으면 끝 너머도 "유효한 메모리"라 ASan이 못 잡는다. libFuzzer도 같은 방식으로 입력을 준다. 둘째, 절반은 sync·len을 맞춘 구조를 아는(structure-aware) 입력이다. coverage-guided가 아닌 단순 랜덤 드라이버는 이런 도움 없이는 CRC 검사를 거의 통과하지 못한다.

무엇을 확인하는 코드인가: off-by-one 버그판을 sanitizer 없이, 그리고 ASan+UBSan으로 돌려 본다.

출력에서 볼 것: sanitizer 없이 100만 번 돌린 버그판은 아무 문제 없이 끝났다. 이게 off-by-one이 양산까지 살아남는 이유다. ASan 빌드는 같은 버그를 바로 잡았고, "48바이트 영역의 0바이트 뒤"(정확히 끝 다음 바이트)를 mlfw.c:99 — buf[3 + len]을 읽는 CRC 비교 줄 — 에서 읽었다고 알려 준다. 할당 위치까지 나온다. (ASan 출력 뒤에는 shadow memory 표가 이어지는데 생략했다.)

100만 개 입력에 2초. 커밋마다 10만 개(0.2초)를, 야간에는 libFuzzer로 몇 시간을 돌리는 식으로 나눈다. 실제 기기에는 ASan이 없다(MCU에는 shadow memory를 둘 RAM이 없다). 그래서 host에서 sanitizer로 돌릴 수 있게 파서를 순수 함수로 짜 두는 것(그림 2의 seam)이 곧 보안·안정성 설계다.

2.8 함정#

  • 성질이 구현을 베낀다: 참조 구현을 C 코드에서 옮겨 쓰면 같은 버그를 같이 가진다. 참조는 정의에서 직접, 가능하면 다른 사람이 쓴다.
  • seed를 매번 바꾸고 기록 안 함: 실패가 재현되지 않는다. seed를 로그에 찍고, 찾은 반례는 고정 테스트로 승격한다.
  • sanitizer 빌드를 최적화 없이만 돌림: 일부 UB는 -O2에서만 드러난다. -O1/-O2 + sanitizer 조합도 돌린다.
  • "죽지 않음"만 검사: 파서가 쓰레기를 "정상 프레임"으로 받아들이는 것도 버그다. 왕복 성질(serialize → parse == 원본)을 함께 건다.

3. Replay 테스트 — 녹음된 센서 로그로 전체 파이프라인을 돌린다#

3.1 왜 replay인가 — "사람이 100시간 말하지 않고 wake word를 테스트하는 법"#

unit과 property test는 함수가 명세대로 동작하는지 본다. 그런데 명세 자체(임계값, 스무딩, refractory)가 틀렸으면? "걷는 중에 제스처를 하면 두 번째부터 안 잡힌다" 같은 버그는 함수 단위로는 아무 문제가 없다. 전체 파이프라인을 현실적인 입력으로 돌려 봐야 보인다.

현실적인 입력을 매번 사람이 만들 수는 없다. 그래서 한 번 녹음하고 영원히 재생한다. 센서 로그(타임스탬프 + 원시 샘플)와 라벨(이벤트가 언제 있었나)을 데이터셋으로 관리하고, host 빌드 파이프라인에 넣어 이벤트를 뽑고 라벨과 비교한다.

  • host에서는 실시간보다 수천 배 빠르다. 아래 예제에서 19분 분량 로그 8개를 두 번씩 재생하는 데 0.08초 걸렸다. 100시간 분량의 음성·잡음 코퍼스도 CI 서버 몇 대면 몇 분이다.
  • 같은 로그는 같은 결과를 낸다(결정적). 그래서 회귀 테스트가 된다.
  • 녹음 한 번이 영원한 자산이다. 필드에서 문제가 된 상황(H1의 on-device 로그)을 잡아 오면 그게 새 시나리오가 된다.

Don의 SSD 경험으로는, 고객 사이트에서 뜬 문제를 워크로드 트레이스로 떠 와서 사내 시뮬레이터에서 재생하던 것과 같다.

같은 로그를 넣었는데 결과가 다르면 replay 테스트는 쓸모가 없다. 결정성을 깨는 것들과 대책이다.

3.4 합성 시나리오 만들기#

무엇을 확인하는 코드인가: 라벨이 달린 IMU 로그를 seed 고정으로 만든다. (실제로는 녹음 데이터를 쓰고, 합성은 부족한 경계 상황을 채우는 데 쓴다.)

로그 한 줄은 t_us,x,y,z, 라벨은 별도 JSON이다({"duration_s": 90, "events_s": [10, 25, 40, 55, 70]}). 로그 포맷과 라벨 포맷을 분리해 두면 라벨만 고칠 때(H4의 재라벨링) 로그를 건드리지 않는다.

detector와 모델 부분은 이렇다. v1(첫 버전)은 th_on = 6000, th_off = 2000이었고, 아래 코드는 3.7절에서 고친 v2 기본값이다.

출력에서 볼 것: 같은 로그인데 v1은 제스처 5개 중 첫 번째만 잡았다. 함수 단위로는 아무 버그가 없다. 왜 그런지는 3.7절에서 점수 궤적으로 본다.

3.6 이벤트 단위 채점 — 손계산#

frame 단위 정확도는 제품 품질을 말해 주지 않는다. 사용자가 느끼는 것은 이벤트다 — "튕겼는데 반응했나", "가만히 있는데 혼자 켜졌나", "얼마나 늦게 반응했나". 그래서 채점도 이벤트 단위로 한다.

규칙(이 예제에서 쓰는 것):

  • 라벨 시각 t₀마다 [t₀, t₀ + 1.0 s] 창 안의 첫 번째 아직 안 쓴 검출을 TP로 짝짓는다. 지연 = 검출 시각 − t₀.
  • 짝이 없는 라벨 = FN(놓침). 짝이 안 된 검출 = FP(오검출).
  • FA/h = FP 수 / 녹음 시간(시간).

손으로 해 보자. 라벨 [10, 25, 40] s, 검출 [10.22, 18.0, 25.26, 26.0] s.

말로 하면, 한 제스처에 두 번 반응하는 것(26.0)도 FP다. 사용자에게는 "한 번 튕겼는데 두 번 켜졌다"는 버그이기 때문이다. refractory가 이걸 막는 장치다. 그리고 창 크기(여기서는 1 s)는 제품 요구 지연에서 나온다. 창을 넓히면 recall이 올라가 보이지만, 사용자는 1초 넘게 늦은 반응을 "안 됐다"고 느낀다.

wake word라면 같은 구조에서 이벤트가 "키워드 발화 끝"이고 창은 발화 끝에서 수백 ms다. 지표는 FRR(놓침률)과 FA/h, 그리고 C8 6.5절의 운영점 곡선이다.

3.7 게이트 — v1이 막히고 v2가 통과한다#

무엇을 확인하는 코드인가: 시나리오마다 재생 → 채점 → 판정, 그리고 같은 시나리오를 두 번 돌려 결정성까지 확인하는 게이트.

출력에서 볼 것: v1은 gesture_walk에서 1/5로 막혔다. 정지 상태 시나리오만 있었다면 v1은 통과했을 것이다 — 시나리오 라이브러리의 가치가 이것이다. 원인은 점수 궤적을 그려 보면 바로 보인다.

그림 4 — gesture_walk의 실제 EMA 점수 궤적(DUMP_SCORES=1로 뽑은 140프레임). 걷는 동안 점수는 약 2700에 머문다. v1의 th_off(2000)는 그보다 낮아서, 첫 제스처 뒤 detector가 다시 armed 상태로 돌아가지 못한다. v2는 th_off를 4000으로 올려 걷는 중에도 re-arm된다.

말로 하면, hysteresis의 "내려가야 하는 선"이 정지 상태 기준으로 정해져 있었고, 걷는 동안의 기저 점수를 고려하지 않았다. 정지 시나리오만으로 튜닝한 임계값이 일상 동작에서 깨진 것이다. 펌웨어 엔지니어에게 익숙한 말로는 "bench에서만 튜닝한 threshold" 다.

v2도 완벽하지 않다는 점을 표가 숨기지 않는다.

  • run: FA/h 12로 기준(30) 안이라 PASS. 하지만 FP가 딱 1개인 이유는 달리는 동안 점수가 계속 13000 근처라 한 번 켜진 뒤 다시 armed가 안 되기 때문이다. 달리면서 하는 제스처는 전부 놓칠 것이다. 이 위험을 검사하는 시나리오(gesture_run)가 아직 없다 — 지표가 좋아 보이는 이유가 "시나리오가 없어서"일 수 있다는 것을 기억하자.
  • gesture_weak: 약한 제스처는 못 잡는다(0/5). xfail로 표시해 보고는 하되 막지 않는다. xfail에는 담당자와 티켓이 붙어야 하고, 어느 날 통과하기 시작하면(XPASS) 그것도 알려야 한다(기대를 갱신하라는 신호).

3.8 음성(negative) 데이터는 몇 시간이 필요한가#

"FA 0회"는 녹음 길이가 붙어야 의미가 있다. FA가 Poisson 과정이라고 보면, T시간 동안 k번 관측했을 때 FA율의 95% 상한을 계산할 수 있다. k = 0이면 상한 ≈ 3/T — rule of three다.

무엇을 확인하는 코드인가: k > 0인 경우까지 포함해 Poisson 상한을 이분법으로 구한다.

출력에서 볼 것: 우리 시나리오의 still + walk는 합쳐 6.5분이다. "FP 0"이 말해 주는 것은 거의 없다. "하루에 한 번 이하"를 주장하려면 오검출 0회로 72시간이 필요하고, "100시간에 한 번 이하"면 300시간이다. 이것이 "wake word를 사람이 100시간 말하지 않고 어떻게 테스트하나"에 대한 답의 절반이다 — 수백 시간의 음성 아닌 오디오(TV, 대화, 음악, 거리 소음)를 한 번 모아 두고 host에서 재생한다. 나머지 절반은 positive 쪽: 다양한 화자·거리·잡음 SNR의 키워드 발화를 녹음하고, 잡음을 여러 SNR로 섞어(augmentation) 조건을 늘린다. 둘 다 host replay라서 몇 분이면 돈다. HIL은 그중 일부(음향 경로 포함)를 실시간으로 확인하는 데만 쓴다.

3.9 replay가 못 보는 것#

replay는 강력하지만 로그가 찍힌 지점 이후만 검사한다.

  • 센서 드라이버, FIFO watermark, DMA, ISR 타이밍 → 로그 이전 단계라 안 보인다.
  • 실시간성: host는 기다리지 않는다. 추론이 deadline을 넘는지는 모른다 (J2).
  • 아날로그 프런트엔드: 마이크 개체 차이, 하우징 공진, AGC는 녹음에 이미 섞여 있거나 아예 없다.
  • 기기 컴파일러 산출물: host는 다른 컴파일러다.

이것들이 HIL의 몫이다.

3.10 함정#

  • 라벨 시각 기준이 모호: 제스처 "시작"인지 "피크"인지 정하지 않으면 지연 지표가 흔들린다. 라벨 규약을 문서로 고정한다 (H4).
  • 시나리오 데이터로 튜닝하고 같은 데이터로 게이트: overfitting이다. 튜닝용과 게이트용 시나리오를 분리한다 (A4의 train/test 분리와 같다).
  • xfail이 쌓인다: 담당자·기한 없는 xfail은 무시와 같다.
  • 합성 데이터만 쓴다: 합성은 경계 조건 보충용이다. 게이트의 몸통은 실제 녹음이어야 한다.

4. HIL — 실기기를 루프에 넣는다#

4.1 HIL이 추가로 보는 것#

HIL(hardware-in-the-loop)은 실제 기기에서 실제 펌웨어를 돌리고, 테스트 PC가 입력을 공급하고 출력을 판정하는 구성이다. Don의 factory test station과 모양이 같다. 차이는 목적이다. 공장 station은 "이 유닛이 제대로 조립됐나"(6절)를 보고, 개발용 HIL은 "이 펌웨어 빌드가 이 하드웨어에서 제대로 동작하나"를 본다.

test mode 주입에는 보안 문제가 따라온다. 양산 기기에서 외부 명령으로 센서 데이터를 바꿀 수 있으면 공격 경로가 된다. 그래서 test mode는 개발 빌드 또는 공장 단계에서만 열리고, 양산 출하 시 fuse·서명된 토큰으로 잠근다. 이것도 테스트 항목이다("출하 상태에서 주입 명령이 거부되는가").

4.5 HIL runner — 시나리오 스위트, 재시도 정책, JUnit XML#

C8 7.1절의 HIL은 벡터 하나를 보내고 비교하는 최소 구성이었다. 여기서는 그걸 테스트 스위트로 키운다. 요구 사항은 이렇다.

  • 테스트마다 DUT를 깨끗한 상태로 (리셋 또는 재시작).
  • 실패를 두 종류로 구분: failure(펌웨어가 틀린 답) vs error(링크 끊김·타임아웃 같은 인프라 문제).
  • error만 재시도한다. failure는 재시도하지 않는다 — 틀린 답을 다시 돌려서 맞으면 그건 더 큰 문제(비결정성)다.
  • 재시도로 통과한 테스트는 숨기지 않고 flaky로 기록한다.
  • 결과는 CI가 읽는 JUnit XML로 쓴다. Jenkins, GitLab, GitHub Actions 등 대부분의 CI가 이 포맷을 그대로 표로 보여 준다.

실기기 대신 같은 mlfw.c를 쓰는 "기기 흉내" 프로그램을 파이프로 연결한다. 실기기로 바꿀 때는 Dut 클래스의 Popen을 pyserial 포트로 바꾸고, 리셋을 debug probe 명령으로 바꾸면 된다.

먼저 기기 쪽이다. 명령 4개(버전, 리셋, 주입, self-test)와 응답 3종(ACK, EVENT, NACK)을 처리한다. FLAKY 환경변수는 불안정한 링크를 흉내 낸다(응답을 확률적으로 잃어버림).

눈여겨볼 점: 이벤트에 벽시계 시각이 아니라 샘플 번호(nsamp − 1)를 실어 보낸다. 그래서 host가 주입 속도를 어떻게 하든 판정이 같다. 실기기에서 지연을 재고 싶다면 별도로 DWT 사이클 카운터 같은 타깃 타임스탬프를 같이 보낸다(J2). 그리고 selftest()는 6.5절의 공장 self-test와 같은 함수다. 개발 HIL과 공장이 같은 self-test를 공유하면 공장에서 실패했을 때 개발 쪽에서 즉시 재현할 수 있다.

host 쪽 DUT 드라이버다.

그리고 runner다. 채점 함수 score는 3.7절의 replay gate에서 그대로 가져온다. host replay와 HIL이 같은 채점 규칙을 쓰는 것이 중요하다. 규칙이 다르면 두 층의 숫자를 비교할 수 없다.

4.6 실행 — 정상, 펌웨어 회귀, 불안정한 링크#

무엇을 확인하는 코드인가: v2 펌웨어로 스위트를 돌리고 JUnit XML을 확인한다.

출력에서 볼 것: 파이프 위라서 300초짜리 walk 시나리오가 0.13초에 끝났다. 실기기 UART(예: 921600 baud)라면 15000샘플 × 6바이트 + 프레임 오버헤드 ≈ 100 kB라 전송만 1초 남짓이고, 실시간 주입(센서와 같은 속도로 넣어 타이밍까지 검사)을 하면 300초 그대로 걸린다. 그래서 HIL 스위트는 "빠른 주입(기능 확인)"과 "실시간 주입(타이밍 확인)" 두 모드를 둔다.

다음은 v1 임계값으로 빌드한 펌웨어다. 실제 기기에서 펌웨어 회귀가 들어온 상황이다.

출력에서 볼 것: host replay(3.7절)와 같은 시나리오에서 같은 숫자(1/5) 로 실패했다. 두 층이 일치한다는 것 자체가 검증이다. 만약 host는 5/5인데 HIL이 1/5라면, 그 차이가 곧 버그 위치(타깃 빌드, 드라이버 경로, 메모리)를 가리킨다. 그리고 t_selftest는 통과했다. self-test는 임계값을 쓰지 않고 점수만 해시하기 때문이다 — self-test가 무엇을 덮고 무엇을 안 덮는지 알고 있어야 한다(6.5절).

마지막으로 불안정한 링크다. 응답 유실 확률 0.1%로 돌리면 walk 하나가 "passed on retry 1"로 통과했다. 0.2%로 올려 보자.

출력에서 볼 것: 명령 1개짜리 테스트는 0.2% 유실에 거의 영향을 안 받지만, 명령 1500개짜리 walk 시나리오는 한 번이라도 유실될 확률이 1 − 0.998¹⁵⁰⁰ ≈ 95%다. 긴 HIL 테스트는 flake 증폭기다. 재시도 3번으로도 막을 수 없다. 해법은 테스트 재시도가 아니라 프로토콜 수준 재전송(명령마다 sequence 번호 + 응답 없으면 그 명령만 재전송)이다. 테스트 전체를 다시 돌리는 재시도는 마지막 안전망일 뿐이다. 그리고 XML이 error와 failure를 구분해 두었기 때문에, CI 대시보드에서 "펌웨어가 틀렸다"와 "랙이 아프다"를 다른 색으로 보여 줄 수 있다.

덤으로, 같은 기기 흉내를 ASan+UBSan으로 빌드해 같은 스위트를 돌려도 깨끗했다. 실기기 HIL과 별도로 "sanitizer 빌드 기기 흉내 + HIL 스위트" 를 커밋마다 돌리면, HIL 스위트를 메모리 오류 탐지기로도 쓸 수 있다.

4.8 함정#

  • HIL에서 host로 잡을 수 있는 것을 잡는다: 느리고 flaky해진다. 4.1절 표에서 ❌인 것만 HIL에 맡긴다.
  • 랙에서 펌웨어를 빌드한다: 랙마다 툴체인이 달라 "같은 커밋, 다른 바이너리"가 된다.
  • test mode를 양산에 남긴다: 보안 구멍. 출하 상태 잠금도 테스트한다.
  • 실시간 주입 없이 타이밍을 검증했다고 말한다: 빠른 주입은 기능만 본다.

5. CI 파이프라인 — 무엇을 언제 돌리나#

5.1 원칙 — 피드백 시간과 비용으로 나눈다#

모든 테스트를 커밋마다 돌리면 개발자가 한 시간씩 기다린다. 아무것도 안 돌리면 버그가 릴리스까지 간다. 기준은 두 가지다.

  • 피드백 시간: 커밋마다 도는 단계는 10~15분 안에 끝나야 개발자가 기다린다. 그보다 길면 사람들이 결과를 안 보고 머지한다.
  • 자원 비용: 실기기는 비싸고 수가 적다. host CPU는 싸고 많다.

그래서 host에서 돌릴 수 있는 것은 최대한 커밋 단계로, 실기기가 필요한 것은 야간으로, 사람·장비·시간이 많이 드는 것은 릴리스로 보낸다.

5.3 산출물과 추적성#

CI의 진짜 산출물은 PASS 표시가 아니라 "이 바이너리가 이 데이터로 이렇게 테스트되었다"는 기록이다.

이렇게 묶어 두면 필드에서 "1.4.2를 받은 뒤 오검출이 늘었다"는 보고가 왔을 때, 그 버전이 어떤 데이터로 어떤 기준을 통과했는지 바로 볼 수 있고, 빠진 시나리오를 찾아 추가할 수 있다. 모델이 펌웨어와 따로 업데이트된다면(J5) 모델 해시와 펌웨어 해시의 조합마다 이 기록이 있어야 한다.

5.4 flaky 테스트 관리#

flaky 테스트(같은 코드에서 결과가 바뀌는 테스트)는 CI의 신뢰를 갉아먹는다. 빨간 불이 자주 거짓말을 하면 사람들은 진짜 빨간 불도 무시한다. 숫자로 보면 문제가 얼마나 큰지 알 수 있다.

무엇을 확인하는 코드인가: 테스트 하나의 flake율이 작아도 스위트 전체가 거짓으로 빨개질 확률, 그리고 이력으로 flake율을 추정하는 방법.

출력에서 볼 것: 테스트 200개가 각각 0.5%만 flaky해도 재시도가 없으면 스위트의 63%가 거짓 FAIL이다. 손으로: 1 − 0.995²⁰⁰ = 1 − e^(200 × ln 0.995) = 1 − e^(−1.0025) ≈ 0.633. 재시도 1번이면 0.5%로 떨어진다. 재시도가 강력하다는 뜻이지만, 동시에 재시도가 진짜 간헐 버그도 가린다는 뜻이다. (history 숫자는 예시로 넣은 값이다.)

그래서 정책은 이렇게 짠다.

  • 재시도는 infra error에만 (4.5절). failure는 재시도하지 않는다.
  • 재시도로 통과하면 flaky로 기록하고, 테스트별 flake율을 대시보드에 추세로 보인다.
  • flake율이 기준(예: 1%)을 넘으면 격리(quarantine): 계속 돌리되 머지를 막지 않고, 담당자와 기한이 붙은 티켓을 자동 생성한다. 격리 목록이 길어지는 것 자체를 팀 지표로 본다.
  • 격리된 테스트가 지키던 위험을 다른 테스트가 덮는지 확인한다. 아무도 안 덮으면 그 위험은 지금 무방비다.
  • 원인별 처방: 링크 유실 → 프로토콜 재전송. 타이밍 의존 판정 → 샘플 번호 기반 판정. 전류 측정 흔들림(위의 power_idle_uA) → 측정 창 늘리기, 온도 안정화 대기, A/A로 잡음 바닥 재기(I5 7.2절). 공유 기기 상태 → 테스트마다 전원 재투입.
  • 릴리스 차단 테스트(정확도, 전력)는 flaky이면 안 된다. 통계적 판정이라면 신뢰구간으로 판정해서 "운 나쁜 실행"이 실패로 보이지 않게 한다(C8 6절).

5.5 테스트 데이터 버전 관리#

ML 펌웨어에서는 테스트 데이터를 바꾸는 것이 테스트를 바꾸는 것이다. 시나리오 하나를 추가하면 지표가 바뀌고, 라벨 하나를 고치면 recall이 바뀐다. 그래서 코드처럼 다룬다.

  • 데이터는 git 밖(오브젝트 스토리지)에 두되, manifest(파일 목록 + 해시 + 버전)는 git 안에 둔다. 테스트는 manifest 버전을 명시해서 받아 간다. (DVC, git-lfs 같은 도구가 이 방식이다. 상세는 H5.)
  • 데이터 변경은 코드 변경과 다른 PR로 한다. 그래야 "지표가 바뀐 이유가 코드인지 데이터인지" 분리된다.
  • 데이터 변경 PR은 이전 버전과 새 버전으로 같은 펌웨어를 돌린 비교표를 첨부한다. 기준선(baseline)을 바꾸는 행위라서다.
  • 게이트 기준값(recall 0.8, FA/h 30)도 버전 관리되는 파일에 두고, 바꿀 때 리뷰를 받는다(CODEOWNERS로 ML 리드 승인 필수 같은 규칙).
  • 필드 데이터를 시나리오로 승격할 때는 동의·개인정보 처리(H6)를 거친 것만 쓴다.

5.6 함정#

  • 커밋 단계가 30분: 사람들이 결과를 안 본다. 무거운 것은 야간으로 옮긴다.
  • 야간 결과를 아무도 안 본다: 아침마다 분류(triage) 담당 순번을 정한다. 실패를 티켓으로 자동 연결한다.
  • 기준선이 몰래 움직인다: 데이터·기준값 변경이 코드 PR에 섞여 들어온다.
  • 산출물 대신 소스를 테스트: 릴리스 바이너리가 아니라 CI에서 다시 빌드한 바이너리를 테스트하면, 실제로 나간 것과 테스트한 것이 다를 수 있다.

6. 공장 테스트 — ML 기능을 양산 라인에서 검사한다#

6.1 목적이 다르다 — 설계 검증이 아니라 조립 검증#

개발 테스트(1~5절)는 "이 설계가 맞나"를 묻는다. 공장 테스트는 "이 한 대가 설계대로 만들어졌나"를 묻는다. 모델의 정확도는 공장에서 다시 재지 않는다. 그건 설계 속성이고 모든 유닛이 같다. 공장에서 보는 것은 유닛마다 다를 수 있는 것 — 부품 불량, 조립 불량, 캘리브레이션 값, 플래시에 들어간 이미지가 맞는지.

Don이 Apple에서 test station·limit·yield를 다룬 경험이 이 절의 중심이다. ML 기능이 추가하는 새 항목은 세 가지다.

  • ML 입력이 되는 센서의 기능·특성 검사 (마이크 감도·매칭, IMU 바이어스·노이즈).
  • 모델과 런타임이 이 유닛에서 동작하는지 확인하는 짧은 self-test.
  • 센서 캘리브레이션 값을 기기에 기록하고 모델 입력 경로에 반영하는 것 (G3).

6.2 station 흐름과 시간 예산#

그림 7 — station 한 대의 cycle time 예산(가정한 숫자). 마이크 측정이 가장 크고, ML self-test는 1초 남짓으로 작다. 핸들링·부팅처럼 "테스트가 아닌 시간"이 40%를 넘는다는 점이 공장 테스트 설계의 현실이다.

손계산: 합계 8 + 5 + 9 + 4 + 1 + 3 + 2 = 32 s. station 한 대의 UPH(시간당 처리량) = 3600 / 32 = 112.5대. 라인 목표가 시간당 200대라면 이 station이 2대 필요하다(병목 공정). 그래서 공장 테스트에서는 1초가 돈이다. 마이크 측정을 3톤 순차에서 다중톤 동시 측정으로 바꿔 9 s → 4 s로 줄이면 station 수를 줄일 수 있다. ML self-test를 길게 만들고 싶은 유혹(예: 모델 정확도 측정)이 있지만, 공장에서는 조립 불량을 잡는 데 필요한 최소만 한다.

6.3 마이크 기능 시험 — 자극과 응답#

방법은 Don에게 익숙한 "자극 → 응답 → limit 비교"다. 차폐 박스 안에서 기준 스피커로 94 dB SPL, 1 kHz(1 Pa, 마이크 감도의 표준 기준점) 톤을 틀고, 기기의 마이크 경로로 녹음한 PCM을 test 명령으로 받아 분석한다. 기준 마이크로 박스의 실제 음압을 확인하고 보정한다(박스마다 다르다).

측정 항목:

  • 감도: 1 kHz 톤의 레벨 (dBFS). 사양은 보통 공칭값 ±1 dB 근처.
  • THD: 고조파 왜곡. 마이크·ADC 불량, 포화.
  • 주파수 응답: 여러 톤(예: 200 Hz, 1 kHz, 4 kHz)의 상대 레벨. 개스킷 누설·포트 막힘은 특정 대역을 깎는다.
  • mic 간 매칭: 감도 차이(dB)와 위상 차이. 빔포밍은 수 µs·수 도 단위 위상 차이에 민감하다.
  • 잡음 바닥: 무음 상태 레벨 (차폐 박스 필요).

무엇을 확인하는 코드인가: 캡처 신호에서 감도·THD·mic 간 위상 차이를 단일 bin DFT로 계산한다.

출력에서 볼 것: 심어 둔 값(−26.4 dB, 2% 고조파, 20 µs)이 그대로 측정된다. 위상 손계산: 20 µs × 1000 Hz × 360° = 7.2°. 캡처 길이를 톤 주기의 정수배(250 ms = 250주기)로 잡아서 창 함수 없이도 누설이 없다 — 공장 측정에서 시간을 아끼는 흔한 요령이다. 실기기에서는 같은 계산을 기기 안에서 Goertzel로 하고 결과 숫자만 보내면, 오디오 덤프 전송 시간(수 초)을 아낄 수 있다.

6.4 IMU 검사와 캘리브레이션 기록#

IMU는 공장에서 비싼 6면 텀블링 대신 짧은 검사를 한다.

  • 정지 자세 중력 검사: 치구에 고정된 자세에서 |a| ≈ 1 g (예: 4096 ± 수십 LSB), 방향이 치구 기준과 맞는지 → 실장 기울기·축 뒤바뀜.
  • 잡음: 정지 상태 1초의 표준편차 → 불량 소자.
  • BIST(built-in self-test): 대부분의 MEMS IMU에는 정전기력으로 질량을 밀어 출력 변화를 보는 self-test 모드가 있다. 변화량이 데이터시트 범위 안이면 기계 구조가 살아 있다.
  • 바이어스·스케일 캘리브레이션: 자세를 몇 개 바꿔 가며 측정해 offset·gain을 구한다(G3). 시간이 드는 만큼 생략하고 필드에서 자동 보정하는 제품도 있다.

캘리브레이션 값은 기기의 보호된 flash 영역에 저장한다. 테스트 관점에서 중요한 것은 기록 자체를 검사하는 것이다.

station은 기록 → 재부팅 → 펌웨어가 읽어 적용한 값을 test 명령으로 되읽기 → 기록한 값과 비교한다. 쓰기만 하고 끝내면 "flash에는 있는데 펌웨어가 버전 불일치로 무시하는" 상황을 못 잡는다. 이 레코드 파서는 2.7절의 fuzz 대상이기도 하다.

6.5 모델 self-test — 라인에서 1초 안에#

ML self-test의 목적은 정확도 측정이 아니라 "이 유닛에서 모델 경로가 설계대로 계산하는가" 다. 4.5절의 selftest()가 그 형태다.

  • 고정된 golden 입력(코드에 내장, 또는 flash의 작은 블롭)을 넣는다.
  • 전체 파이프라인(특징 → 모델 → 후처리)을 실제 하드웨어 경로(NPU/DSP 포함)로 돌린다.
  • 출력 점수들의 해시(정수 경로라면 bit-exact) 또는 허용 범위(float 경로라면)를 기대값과 비교한다.
  • 모델 블롭의 해시와 펌웨어가 보고하는 모델 버전도 함께 확인한다.

이것이 잡는 것: 모델 블롭 손상, 잘못된 모델 버전이 플래시됨, NPU·DSP·SRAM의 하드웨어 결함(특정 연산이 틀린 값), 캘리브레이션 적용 경로 오류(입력에 캘리브를 적용하는 버전이라면). 못 잡는 것: 센서 불량(입력이 고정이므로 — 6.3·6.4절이 맡는다), 임계값 설정 오류(4.6절에서 v1 펌웨어가 self-test를 통과한 것을 기억하자 — 그래서 펌웨어·모델·임계값 파일의 해시 검사를 따로 둔다).

시간 손계산: 장난감 모델은 8프레임이라 µs 단위다. 실제 모델이 한 번에 20 ms라면 golden 입력 10개 = 200 ms + 명령 왕복. 1초 예산 안에 충분히 들어간다. 정확도를 재려고 수천 개를 돌리면 분 단위가 되어 라인에서는 불가능하다.

같은 self-test를 부팅 시(축약판)와 필드 진단 명령으로도 노출하면, RMA로 돌아온 기기를 공장과 같은 기준으로 바로 판정할 수 있다.

6.6 limit 설정 — 통계로 정한다#

limit을 어떻게 정하나. 세 가지 출발점이 있다.

  • 설계 사양(spec limit): 데이터시트·시스템 요구에서 온 값. 예: 감도 −26 ± 1 dB.
  • 통계적 limit: 파일럿 빌드 모집단의 분포에서 정한 값. 예: 평균 ± 3σ, 백분위, robust 통계.
  • ML 영향 기반: "감도가 X dB 낮으면 wake word recall이 Y% 떨어진다"를 replay로 재서 정한 값 (3절의 시나리오에 감도 오프셋을 걸어 보면 된다).

무엇을 확인하는 코드인가: 불량이 섞인 모집단에서 limit 계산 방법 네 가지를 비교한다.

그림 8 — 정상 분포(파랑)와 불량(빨강), 그리고 네 방법의 합격 구간(아래 막대). 누설 불량(−27.6 근처)은 정상 분포 바로 왼쪽에 붙어 있어서 구간 왼쪽 끝이 어디냐가 전부다.

출력에서 볼 것:

  • mean ± 3σ: 불량이 섞이면 σ가 0.35 → 0.64로 부풀어 구간이 넓어진다. 막힘은 잡지만 누설 17/20이 통과한다. 모집단으로 limit을 정할 때 그 모집단에 불량이 섞여 있다는 사실을 잊으면 이렇게 된다.
  • percentile 0.5–99.5: 정의상 항상 1%를 버린다(정상 25대 탈락). 그리고 불량이 1%라서 하한이 불량 분포 안쪽(−30.97)에 놓여 막힘 5대까지 통과한다. 백분위 limit은 불량률이 바뀌면 limit도 따라 움직이는 최악의 성질을 가진다.
  • median ± 4·robust-σ: 중앙값과 MAD(중앙 절대 편차, ×1.4826이면 정규분포의 σ 추정)는 불량 몇 %에 거의 흔들리지 않는다. robust-σ 0.358이 실제 정상 σ 0.35와 거의 같다. 정상 탈락 0, 누설 5/20만 통과.
  • datasheet ±1 dB: 불량은 다 잡지만 정상 17대를 버린다(Cpk 0.95의 대가 — 손계산 21대와 같은 규모).

실무 절차는 이렇게 된다. 파일럿 빌드(EVT/DVT)에서 분포를 모으고, robust 통계로 정상 분포를 추정하고, 사양 limit과 비교해 Cpk를 본다. 통계 limit이 사양보다 좁으면 통계 limit으로 "이상한 유닛"을 걸러 원인 분석을 하고(누설 같은 공정 문제 발견), 사양보다 넓으면 사양으로 판정한다. 그리고 측정 시스템 자체의 반복성(같은 유닛을 10번 재서 흔들림 — Gauge R&R)이 limit 폭에 비해 작은지 먼저 확인한다. 측정이 ±0.3 dB 흔들리는데 limit이 ±0.5 dB면 판정이 동전 던지기가 된다. 누설처럼 감도로는 정상과 겹치는 불량은 다른 측정(저주파 응답, 밀폐 상태 비교) 을 추가해야 확실히 잡힌다. limit 하나로 모든 불량을 잡으려 하지 않는다.

6.7 추적성 — 시리얼 ↔ 결과 ↔ 모델 버전#

공장 데이터는 한 대 한 대가 기록이다. station은 유닛마다 이런 레코드를 서버(MES)로 올린다.

(값은 예시다.) 이 기록이 있으면 할 수 있는 일:

  • 필드 문제 → 공장 데이터 역추적: "오검출이 많은 기기들"의 시리얼로 공장 기록을 조회하면, 예를 들어 마이크 감도가 limit 안이지만 하한 근처에 몰려 있다는 것을 발견할 수 있다. 그러면 limit을 조이거나 모델을 그 조건에 강하게 만든다 (H8의 필드 데이터와 연결).
  • 리콜 범위 결정: 특정 fixture나 특정 날짜의 펌웨어로 테스트된 유닛만 골라낼 수 있다.
  • 모델 업데이트 영향 분석: OTA로 모델을 바꿀 때(J5), 공장 캘리브레이션 값 분포 전체에 대해 새 모델이 괜찮은지 replay로 확인할 수 있다.
  • yield 대시보드: station·fixture·시간대별 불량률. 한 fixture만 불량률이 높으면 제품이 아니라 fixture 문제다 (Don이 매일 보던 그 그래프).

6.8 함정#

  • 공장에서 정확도를 잰다: 시간만 들고 설계 속성이라 유닛마다 같다. 조립 불량을 잡는 측정만 한다.
  • 측정 반복성을 확인 안 함: Gauge R&R 없이 limit을 조이면 정상이 랜덤하게 떨어진다.
  • 캘리브레이션을 쓰기만 하고 되읽지 않음: 펌웨어가 실제로 적용하는지 확인해야 한다.
  • test program·limit 파일 버전을 기록 안 함: 나중에 어떤 기준으로 통과했는지 모른다.

9. 면접에서 이렇게 말한다#

Q. How do you test an ML feature in firmware end to end?

A. 층으로 나눠 말한다. 결정적인 부분(커널, DSP, 파서, 링버퍼, 상태 기계)은 host unit test + sanitizer + 성질 테스트로 비트 단위까지. 모델 경로는 golden vector로 component 검증. 기능 전체는 녹음된 센서 로그 + 라벨을 host 빌드 파이프라인에 재생해서 이벤트 단위(recall, FA/h, 지연)로 시나리오별 게이트. 실기기에서만 보이는 것(타이밍, 드라이버, 전력, 실제 컴파일러)은 HIL. 마지막이 dogfood와 텔레메트리. 핵심은 같은 소스가 모든 층에 들어가고, 같은 채점 규칙을 host와 HIL이 공유해서 두 층의 숫자를 비교할 수 있게 하는 것.

"I split it into layers. The deterministic parts — kernels, DSP blocks, parsers, ring buffers, the post-processing state machine — get host unit tests with sanitizers and property-based tests, and integer paths are checked bit-exactly against a reference. The model path gets golden-vector component tests. The feature as a whole is tested by replaying recorded, labeled sensor logs through the host build of the real pipeline and scoring at the event level — recall, false alarms per hour, latency — per scenario, with a gate. HIL covers only what the host can't see: timing, drivers and DMA, the real compiler output, and power. Above that is dogfooding and field telemetry. The two things that make it work are that the same source goes into every layer, and that host replay and HIL share the same scoring code, so a disagreement between them points straight at the hardware-specific layer."

Q. How do you test a wake word without a human talking for 100 hours?

A. 한 번 녹음하고 영원히 재생한다. negative 쪽은 TV·대화·음악·거리 소음 같은 키워드 없는 오디오 수백 시간을 모아 두고 host에서 수천 배 속도로 재생해 FA/h를 잰다. "0회"의 의미는 녹음 시간에 달려 있다 — rule of three로 72시간 0회면 95% 상한이 하루 1회다. positive 쪽은 다양한 화자·거리 녹음에 잡음을 여러 SNR로 섞어 조건을 늘린다. 둘 다 재생은 결정적이어야 하고 데이터는 버전 관리한다. 실제 마이크·하우징 경로는 차폐 박스 스피커로 하는 음향 HIL에서 일부만 반복 측정으로 확인한다.

"You record once and replay forever. For false alarms, I keep a corpus of hundreds of hours of keyword-free audio — TV, conversations, music, street noise — and replay it through the host build of the full pipeline, thousands of times faster than real time. The number of hours matters: zero false alarms in 72 hours only bounds the rate at about one per day at 95% confidence, by the rule of three. For recall, I use many speakers and distances and mix noise at a sweep of SNRs to multiply the conditions. The replay is deterministic and the dataset is versioned, so it works as a regression test. Then a smaller subset goes through an acoustic HIL — a speaker in a shielded box playing into the real device's microphones — repeated several times per clip, to cover the analog and enclosure path that recordings can't."

Q. What would you run per commit versus nightly?

A. 기준은 피드백 시간과 자원이다. 커밋마다(15분 이내, host만): host·타깃 cross 빌드, unit test를 일반·sanitizer 빌드로, 짧은 성질 테스트와 fuzz, 핵심 시나리오 replay 게이트, flash·RAM·MAC 예산 체크. 야간(기기 farm): HIL 스위트, 전체 녹음 코퍼스 replay, 지연·전류 성능 회귀(A/A 잡음 바닥 기준), 8시간 soak, 장시간 libFuzzer. 릴리스: 전체 정확도 회귀(신뢰구간, 클래스·사용자별), 전력 sign-off, 음향 HIL, dogfood, 공장 프로그램 dry-run. 아래로 갈수록 판정이 자동 차단에서 리포트 + 사람 승인으로 바뀐다.

"I sort by feedback time and resource cost. Per commit, under about fifteen minutes and host-only: build for host and every target, unit tests in a normal and a sanitizer build, short property and fuzz runs with fixed seeds, a replay gate on the core scenarios, and a memory and compute budget check. Nightly, on the device farm: the full HIL suite, replay of the whole recorded corpus, latency and current regression measured against an A/A noise floor, an eight-hour soak, and long fuzzing. At release: the full accuracy regression with confidence intervals and per-class breakdowns, power sign-off, acoustic HIL, dogfood, and a dry run of the factory test program. The further down, the more the verdict shifts from an automatic block to a report that a person signs off — just like a margin sign-off in NPI."

Q. Design the factory test for the microphones and the ML self-test.

A. 목적은 조립 불량을 찾는 것이지 정확도를 재는 게 아니다. 마이크: 차폐 박스에서 기준 마이크로 보정한 94 dB SPL 톤(1 kHz + 저·고주파 몇 개)을 틀고, 기기 안에서 Goertzel로 감도·THD·주파수 응답·mic 간 감도·위상 차이를 계산해 숫자만 보낸다. 막힘·누설은 감도와 대역 응답으로 잡는다. limit은 파일럿 빌드 분포를 robust 통계로 보고 사양과 비교해 Cpk 확인, Gauge R&R로 측정 반복성 먼저 확인. 캘리브 값은 기록 후 재부팅해서 펌웨어가 적용한 값을 되읽는다. ML self-test: 고정 golden 입력을 실제 하드웨어 경로로 돌려 출력 해시 비교 + 모델·펌웨어·임계값 해시 확인, 1초 이내. 결과는 시리얼·fixture·test program 버전·모델 해시와 함께 MES에 올려 필드 문제를 역추적할 수 있게 한다.

"The goal is to catch build defects, not to measure model accuracy — that's a design property. For the microphones: in a shielded box, play a 94 dB SPL tone calibrated with a reference mic — 1 kHz plus a low and a high tone — and compute sensitivity, THD, band response, and mic-to-mic gain and phase mismatch on the device with a Goertzel, sending back only the numbers to save cycle time. Blocked ports and gasket leaks show up in sensitivity and band response. Limits come from pilot-build distributions using robust statistics, compared against the spec with a Cpk check, after a gauge R&R confirms the measurement repeats well inside the limit width. Calibration values are written, then read back after a reboot from what the firmware actually applied. The ML self-test runs a fixed golden input through the real hardware path and compares an output hash, plus the firmware, model and threshold hashes — under a second. Everything is logged against the serial number, fixture, test program and model version, so field issues can be traced back to the line data."

Q. How do you keep flaky HIL tests from blocking releases?

A. 먼저 failure와 infra error를 구분한다. 재시도는 infra error(타임아웃, 링크)에만 하고, 틀린 답은 재시도하지 않는다 — 재시도로 맞으면 그건 비결정성 버그다. 재시도로 통과한 것도 flaky로 기록해서 테스트별 flake율을 추세로 본다. 기준을 넘으면 격리하고 담당자·기한 티켓을 자동으로 만들고, 그 테스트가 지키던 위험을 다른 테스트가 덮는지 확인한다. 그리고 원인을 고친다: 긴 테스트는 flake 증폭기이므로 프로토콜에 sequence + 재전송을 넣고, 판정은 벽시계가 아닌 샘플 번호로, 전류 측정은 잡음 바닥을 재서 허용폭을 정하고, 기기 상태는 테스트마다 전원 재투입. 릴리스 차단 테스트는 신뢰구간으로 판정해 운 나쁜 실행이 실패로 보이지 않게 한다.

"First I separate failures from infrastructure errors. Only infra errors — timeouts, a dropped link — get retried; a wrong answer is never retried, because if a retry fixes it, that's a nondeterminism bug. Anything that passes on retry is still recorded as flaky, and each test's flake rate is tracked as a trend. Above a threshold it's quarantined: it keeps running but doesn't block, and it gets an owner and a deadline automatically — and I check what risk it was covering and whether anything else covers it. Then fix the causes. Long HIL tests amplify flakiness — at a 0.2% drop rate a 1500-command scenario fails almost every time — so the protocol needs sequence numbers and per-command retransmit; judgments should use sample indices rather than wall-clock time; power measurements need a measured noise floor; and every test starts from a power cycle. Release-blocking tests use confidence intervals so an unlucky run doesn't read as a regression."

Q. A unit passes the factory ML self-test but the gesture feature doesn't work for that customer. What could it be?

A. self-test가 덮는 범위부터 말한다 — 고정 입력이라 센서 경로와 설정은 안 본다. 후보: IMU 실장 기울기·바이어스(공장 중력 검사 기록 확인), 캘리브 값이 기록됐지만 펌웨어가 버전 불일치로 무시(되읽기 기록 확인), 임계값 파일 버전(해시 확인), 착용 방식·사용자 동작이 시나리오에 없는 분포(필드 로그를 받아 replay 시나리오로 추가). 시리얼로 공장 기록을 조회해서 limit 경계에 있는 값이 있는지 본다.

"I'd start from what the self-test doesn't cover: it uses a fixed input, so it says nothing about the sensor path or the configuration. So I'd look up the unit's serial in the factory records — IMU gravity and bias results, whether calibration was read back as applied or silently ignored because of a version mismatch, and the threshold and model hashes. If the factory data is clean and near the middle of the limits, it's likely a usage pattern our scenarios don't cover, so I'd pull the device logs with consent, replay them on the host to reproduce, and add them as a new scenario before changing anything."

  4. 코드: 3절의 시나리오에 gesture_run(달리기 + 제스처 5회)을 추가하고 v2로 replay gate를 돌려라. 무엇이 나오고, 어떻게 고칠 것인가? 정답: 달리는 동안 점수가 약 13000에 머물러 th_off(4000) 아래로 안 내려가므로 첫 검출 뒤 re-arm이 안 된다. 실제로 돌려 보면(seed 9) 0.3 s에 오검출 1개만 나오고 recall 0/5다. 고정 하한 대신 기저 점수를 추적하는 적응형 하한, 또는 모델이 달리기를 별도 클래스로 학습하게 하는 방향.
  5. 코드: limits.py에서 누설 불량을 감도 하나로는 완전히 못 잡았다. 누설은 저주파(예: 200 Hz)를 정상 대비 3 dB 더 깎는다고 가정하고, 2차원(1 kHz 감도, 200 Hz − 1 kHz 차이) limit으로 탈출 수가 어떻게 바뀌는지 시뮬레이션하라. 힌트: 두 번째 측정이 정상과 누설을 거의 분리하므로 탈출이 0 근처로 떨어질 것이다. 요점은 limit 하나로 모든 불량을 잡으려 하지 말고 불량 메커니즘별 측정을 추가하는 것.
  6. 설계: 마이크 2개와 IMU가 있고 station takt가 30초다. 그림 7의 예산(32 s)을 30초 안으로 줄이는 방법 세 가지를 제시하라. 정답 예: 다중톤 동시 측정으로 마이크 9 → 4 s, IMU 측정을 마이크 측정과 병렬로(서로 다른 센서), test-mode 빠른 부팅, 결과 업로드를 비동기로. 핸들링 시간은 fixture 설계 문제다.

12. 요약 & 체크리스트#

ML 기능이 들어간 펌웨어의 테스트는 결정적인 부분은 비트 단위로, 통계적인 부분은 데이터와 신뢰구간으로 판정한다. 결정적인 부분(커널·DSP·파서·버퍼·상태 기계)은 host에서 table-driven unit test, 성질 테스트, sanitizer fuzz로 아래 층에서 끝낸다. 기능 전체는 녹음된 센서 로그를 같은 소스의 host 빌드로 결정적으로 재생해 시나리오별 이벤트 지표로 게이트를 건다 — 시나리오 라이브러리가 "정지 상태에서만 튜닝한 임계값" 같은 설계 버그를 잡는다. HIL은 host가 원리상 못 보는 타이밍·드라이버·전력·컴파일러 산출물만 맡고, host와 같은 채점 규칙을 써서 두 층의 차이가 버그 위치를 가리키게 한다. CI는 피드백 시간과 자원으로 커밋·야간·릴리스 차선을 나누고, 재시도는 infra error에만, flaky는 기록·격리·원인 수정으로 다룬다. 공장 테스트는 정확도가 아니라 조립 불량을 찾는다 — 센서 자극·응답, 짧은 golden self-test, robust 통계로 정한 limit, 그리고 시리얼과 모델 버전까지 묶은 추적성.
