0. 큰 그림 — 데이터셋은 "릴리스되는 제품"이다#

펌웨어 엔지니어에게 익숙한 장면부터 보자. 양산 펌웨어는 그냥 "최신 빌드"가 아니다. 버전 번호가 있고, 어떤 소스 커밋·어떤 컴파일러·어떤 설정으로 빌드됐는지 기록이 있고, release note가 있고, 한 번 나간 바이너리는 절대 덮어쓰지 않는다. 문제가 생기면 "FW 3.2.1에서 재현된다"고 말할 수 있다.

ML 모델의 동작은 코드보다 데이터가 더 많이 결정한다. 그런데 많은 팀에서 데이터는 "S3 어딘가의 폴더"로 관리된다. 그러면 이런 일이 생긴다.

  • 모델팀: "지난주보다 정확도가 2%p 올랐어요" — 알고 보니 test 폴더에 새 사용자가 섞여 들어가서 test 자체가 바뀌었다.
  • 펌웨어팀: "기기 결과가 PC 결과와 다른데요" — PC 쪽이 어떤 버전의 test vector를 썼는지 아무도 모른다.
  • 6개월 뒤: "v1.3 모델에서 왼손잡이 사용자 불만이 많다. 그때 학습 데이터에 왼손잡이가 몇 명이었지?" — 답할 수 없다.

이 노트의 관점은 한 문장이다: 데이터셋을 펌웨어 릴리스처럼 다룬다. 버전이 있고, 불변(immutable)이고, 내용 해시로 검증되고, 변경 기록이 있고, 사용 설명서(dataset card)가 있다.

A4에서 "데이터를 사용자 단위로 나눠야 한다(leakage)"는 한 번의 실험 관점을 배웠다. H5는 같은 문제를 시간이 흐르는 조직 관점에서 본다: 데이터가 매주 늘어나고, 라벨이 고쳐지고, 기기 리비전이 바뀌고, 여러 팀이 같은 데이터를 쓴다. 이때도 split이 흔들리지 않고 숫자를 비교할 수 있어야 한다.

0.2 좋은 데이터셋의 요구사항#

  • Coverage(포괄성): 제품이 만날 사용자·기기·환경이 골고루 들어 있다. 손목 크기, 왼손/오른손, 실내/실외, 기기 리비전(EVT/DVT/PVT), 펌웨어 버전.
  • 라벨 품질: 라벨 정의서가 있고, 라벨러 간 일치도가 측정돼 있다(H4).
  • 크기: 클래스·그룹별로 통계적으로 의미 있는 양. 전체 1000시간이어도 "실외 낙상"이 0분이면 그 칸은 모른다.
  • 분할 안정성: 데이터가 늘어도 기존 사용자가 train ↔ test를 오가지 않는다.
  • 추적 가능성: 어떤 모델이 어떤 버전으로 학습됐는지, 그 버전에 무엇이 들어 있는지 기록이 있다.

0.3 수명주기#

그림 1 — 데이터셋은 수집 → 정제·라벨 → 분할 → 버전 → 릴리스 → (언젠가) 폐기의 수명주기를 갖는다. 릴리스된 버전을 여러 팀이 쓰고, 그들이 찾은 빈칸(주황 점선)이 다음 수집 목표가 된다. 펌웨어의 "bring-up → 릴리스 → 현장 이슈 → 다음 릴리스" 루프와 같은 모양이다.

폐기(deprecate)도 단계다. 예를 들어 EVT 기기의 IMU가 축 방향 배선이 반대였다는 게 밝혀지면, EVT 데이터를 쓰는 버전은 "deprecated: EVT 축 반전 버그, 2.x 이상 사용"으로 표시한다. 지우지는 않는다 — 그 버전으로 학습된 모델을 재현해야 할 수 있기 때문이다(단, 사용자 삭제 요청은 예외, 6.4절·H6).

0.4 이 노트의 공용 합성 메타데이터#

예를 들어 Hark 같은 웨어러블이라면(추정) 손목 IMU로 idle / tap / swipe / raise / fall 같은 제스처·이벤트를 구분할 수 있다. 아래 생성기는 그런 가상의 데이터셋의 세션 메타데이터를 만든다. 실제 센서 샘플은 없고 "세션 1행 = 녹음 1회"의 표다. 사용자 200명, 기기 리비전 EVT/DVT/PVT, 손목 크기 S/M/L, 왼손/오른손, 실내/실외, 날짜(2026-03 ~ 2026-08), 녹음 길이(분). 낙상(fall)은 매트 위에서 연기하는 스턴트 참여자 약 6%만 녹음했고, EVT 기기는 실외 녹음이 적다 — 현실에서 흔한 치우침을 일부러 넣었다.

출력에서 볼 것: 세션 1170개 중 fall은 42개(3.6%)뿐이고, 그것도 소수의 사용자에게 몰려 있다(사용자 u0000이 스턴트 참여자). 이 "희귀 클래스가 소수 사용자에게 몰린" 구조가 1.5절의 split과 3절의 불균형 문제를 동시에 만든다. 생성기는 사용자 순서대로 난수를 쓰기 때문에 make_meta(300)의 앞 200명은 make_meta(200)과 똑같다 — "데이터가 늘어난 다음 버전"을 흉내 낼 때 쓴다.

1. 분할 정책 — A4 복습, 그리고 "시간이 흐르는" split#

1.1 A4에서 이미 본 것 (복습)#

A4 3절의 결론을 세 줄로 줄이면 이렇다.

  • 윈도우 단위로 섞어서 나누면 겹치는 윈도우와 같은 사용자가 train/test 양쪽에 들어가 점수가 부풀려진다(A4 예제: 94.6% vs 48.9%).
  • 그래서 사용자(또는 기기·세션) 단위로 나누고, 윈도우는 split 후에 자른다.
  • 하이퍼파라미터는 group k-fold로 고르고, test는 봉인해 한 번만 쓴다.

H5에서 새로 다룰 질문은 이것이다: 데이터가 매주 들어오는데, 이 규칙을 어떻게 "정책"으로 만들어 자동으로, 안정적으로 지키나?

1.3 hash 기반 결정적 split — 사용자가 늘어도 흔들리지 않게#

문제. 처음에 200명을 모아서 np.random.permutation으로 섞은 뒤 160/20/20으로 나눴다고 하자. 한 달 뒤 100명이 더 들어와 300명을 다시 섞어 나누면? 기존 200명 중 상당수가 다른 split으로 이동한다. 지난달 test에 있던 사람이 이번엔 train에 들어간다 — 그러면 모델은 그 사람을 학습했고, 이전 test 숫자와 비교할 수 없다.

해결. split을 "전체를 섞는 연산"이 아니라 사용자 ID 하나만 보고 결정되는 함수로 만든다.

말로 하면: 사용자 ID를 암호학적 해시에 넣으면 0~99 중 하나가 거의 균등하게 나온다. 그 숫자로 split을 정한다. 이 함수는 다른 사용자가 몇 명인지 전혀 보지 않으므로, 사용자가 추가돼도 기존 사람의 split은 절대 바뀌지 않는다. salt는 "split 정책의 이름"이다. 정책을 바꾸고 싶으면(예: 70/15/15) salt를 바꾸고 데이터셋 MAJOR 버전을 올린다.

손으로 보면: u0000의 bucket이 46이면 46 < 80이라 train이다. u0007의 bucket이 80이면 val이다. 새 사용자 u0250이 들어와도 u0000의 해시는 그대로 46이다.

출력에서 볼 것: hash 방식은 사용자가 300명으로 늘어도 기존 200명 중 0명이 이동한다. 셔플 방식은 같은 seed를 썼는데도 47명이 이동했고, 그중 7명은 test에 있던 사람이 train으로 들어갔다 — 다음 버전의 모델은 지난 test 사용자를 학습한 상태다. 대가도 보인다: hash 방식은 비율이 정확히 80/10/10이 아니라 163/19/18(81.5/9.5/9)처럼 확률적으로 맞는다. 사용자 수가 적을수록 흔들림이 크다(이항분포: 200명에서 test 비율의 표준편차 ≈ √(0.1·0.9/200) ≈ 2.1%p).

그림 2 — hash split은 각 사용자에게 0~99의 "고정 좌석"을 준다. 좌석 번호는 그 사람의 ID만으로 정해지므로 새 사람이 들어와도 기존 좌석은 그대로다. 아래 막대는 위 코드의 실제 결과다. (이 그림의 golden 구간 95~99는 1.4절의 정책이다. 1.3절 코드에서는 90~99가 모두 test다.)

함정 — Python 내장 hash()를 쓰면 안 된다. 문자열에 대한 hash()는 프로세스마다 무작위 seed가 붙는다(PYTHONHASHSEED). 노트북에서는 같아 보여도 CI 서버에서 돌리면 split이 바뀐다.

같은 문자열 "u0007"이 실행마다 60, 43으로 다른 bucket에 떨어진다. hashlib.sha256(또는 MD5, xxhash, CRC32 같은 결정적 해시)을 쓴다. 펌웨어 비유: "부팅마다 다른 seed로 초기화되는 PRNG로 lot을 배정하는" 실수와 같다.

무엇을 해시할까. 사용자 ID를 해시하면 사용자 단위로 묶인다. 하지만 같은 사람이 기기를 바꿔 새 ID를 받으면 묶임이 깨진다. 그래서 실무에서는 등록 시점에 "사람 ID(person_id)"를 별도로 두고, 기기 교체는 같은 person_id로 연결한다. 해시 키는 누수를 막고 싶은 가장 큰 단위로 정한다 — 가족이 한 기기를 같이 쓰면 household 단위가 될 수도 있다.

1.4 여러 축을 한 정책으로 — 우선순위 규칙#

실제 정책은 축 하나로 끝나지 않는다. golden test, 시간 split, 사용자 hash split을 우선순위가 있는 규칙으로 합친다. 위에서 걸리면 아래 규칙은 보지 않는다.

출력에서 볼 것은 세 가지다.

  • test에 EVT 세션이 0개다. 규칙은 맞게 돌았는데, 우연히 test bucket(90~94)에 EVT 사용자가 없었다. split을 만든 뒤에는 반드시 split × 메타데이터 교차표를 찍어서 이런 빈칸을 찾는다. 해결은 bucket 범위를 바꾸는 게 아니라(그러면 정책이 흔들린다), 다음 수집에서 EVT 사용자를 더 모으거나, "EVT 성능은 golden_test로 본다"고 card에 명시하는 것이다.
  • future_test의 88%는 train에 있던 사람이다. 시간 split은 "같은 사람의 미래"를 재는 것이라 사용자 겹침이 정상이다. 대신 이 숫자를 "처음 보는 사람" 성능이라고 보고하면 안 된다. 두 질문(새 사람? 새 시간?)을 섞지 않는 게 핵심이다.
  • golden 13명의 세션 74개는 날짜와 무관하게 golden이다(규칙 1이 먼저다). 우선순위를 바꾸면 golden이 시간에 따라 줄어든다 — 순서 자체가 정책이고, card에 적어야 한다.

1.5 StratifiedGroupKFold — 그룹은 지키고 클래스 비율도 맞추고#

A4에서 본 GroupKFold는 "같은 사용자가 두 fold에 걸치지 않게"만 보장한다. 클래스 비율은 신경 쓰지 않는다. 희귀 클래스(fall)가 소수의 사용자에게 몰려 있으면 어떤 fold에는 fall이 거의 없어서 그 fold의 fall recall이 의미가 없어진다.

sklearn.model_selection.StratifiedGroupKFold(scikit-learn 1.0부터 있다)는 그룹을 지키면서 각 fold의 클래스 분포를 전체와 비슷하게 맞추려고 한다. 그룹을 통째로 옮겨야 하므로 완벽하게 맞출 수는 없고, 탐욕적(greedy) 휴리스틱이다. 그래서 결과를 반드시 찍어 봐야 한다.

출력에서 볼 것: fall 사용자 14명 × 3세션이므로 이상적인 배분은 [9, 9, 9, 9, 6]이다. GroupKFold는 [12, 9, 12, 3, 6]으로 한 fold에 fall이 3개뿐이다. StratifiedGroupKFold는 이 데이터에서 shuffle=False일 때 [6, 9, 9, 9, 9]로 잘 맞췄지만, shuffle=True와 seed에 따라 [3, 15, 3, 3, 18]처럼 오히려 더 나빠지기도 했다. 이 함수는 모든 클래스의 분포를 함께 맞추려 하므로 3.6%짜리 fall은 우선순위가 낮을 수 있다. 가장 안정적이었던 것은 마지막 줄 — 사용자 단위 표를 만들고 "fall 보유 여부"로 직접 층화한 방법이다.

교훈은 "어떤 함수를 쓰느냐"보다 "fold별 희귀 클래스 개수를 찍어서 확인하느냐"다. 펌웨어로 치면 테스트 매트릭스를 자동 생성했으면, 생성된 매트릭스에 corner case가 실제로 들어갔는지 세어 보는 것이다.

1.6 golden test set — 동결 규칙#

golden test set은 버전이 바뀌어도 변하지 않는 평가 세트다. 펌웨어의 qualification 벡터 세트, 혹은 "reference board"와 같다.

  • 처음 버전(예: 1.0.0)에서 고르고 사용자 ID 목록 파일을 커밋한다. 위 예제처럼 bucket 95~99로 뽑아도 되지만, 결과 목록 자체를 파일로 고정하는 것이 핵심이다(나중에 bucket 규칙이 바뀌어도 목록은 남는다).
  • 절대 학습·튜닝·calibration(C2)에 쓰지 않는다. threshold를 고르는 데도 쓰지 않는다(그건 val의 일).
  • 라벨 오류를 발견하면 고친다. 단 "golden 라벨 수정"은 별도 changelog 항목이고, 이전 숫자와 비교할 때 보정이 필요하다.
  • golden 자체를 바꾸면(사용자 추가·제거) 데이터셋 MAJOR 버전이다. 그 전후 모델 숫자는 직접 비교하지 않는다.
  • golden에는 희귀 클래스와 중요한 그룹이 반드시 들어가야 한다. 해시로만 뽑으면 우연히 빠질 수 있다(8절에서 실제로 fall이 빠진다). 희귀 클래스는 "스턴트 참여자 중 2명" 식으로 명시적으로 넣는다.

1.7 함정 모음#

  • split을 매번 다시 계산하면서 "같은 코드니까 같은 split"이라고 믿는다 → 라이브러리 버전·입력 순서·내장 hash()가 바뀌면 다르다. 계산 결과(사용자 → split 표)를 데이터셋 버전에 저장한다.
  • 세션을 해시한다 → 같은 사람의 세션이 train/test로 흩어진다(A4 누수). 해시 키는 사용자(또는 그보다 큰 단위)다.
  • 나중에 "test가 너무 작다"며 bucket 경계를 옮긴다 → 기존 사용자가 이동한다. 경계를 바꾸는 건 MAJOR 변경이다. 작으면 데이터를 더 모은다.
  • 시간 split의 날짜 경계에서 한 세션이 반으로 잘린다 → 세션 시작 시각 기준으로 통째로 배정한다.

2. Coverage 분석 — 데이터의 빈칸 찾기#

2.1 직관#

전체 데이터가 100시간이어도 그것이 "실내 · DVT · idle"에 몰려 있으면 모델은 실외 낙상에 대해 아무것도 모른다. 펌웨어 검증에서 "온도 × 전압 × 클럭" corner 매트릭스를 만들고 빈칸을 채우는 것과 똑같이, 데이터도 class × 조건 × 기기 매트릭스를 만들고 각 칸의 양(시간·세션·사용자 수)을 센다.

2.2 코드 — 시간(h) 표, 빈칸, 재균형 가중치#

그림 3 — 위 코드의 실제 표를 heatmap으로 그렸다. 빨간 테두리 5칸이 1시간 미만이다. 빈칸이 무작위로 흩어져 있지 않고 한 열(EVT × 실외)과 한 행(fall)에 몰려 있다 — 수집 계획의 구조적 문제(EVT 시절엔 실외 녹음을 거의 안 했다, 낙상은 스턴트로만 모았다)를 드러낸다.

출력에서 볼 것은 마지막 두 줄이다. 가중치는 "각 (label, env) 칸이 전체 학습 신호에서 같은 비중(1/10 = 0.1)을 갖도록" 계산했다. 대부분 칸은 0.105로 맞춰졌지만 ('fall', 'outdoor')는 0.058에 머물렀다. 상한 5를 걸었기 때문이다. 상한이 없으면 1.5시간짜리 칸에 9배 가까운 가중치가 붙어, 소수 세션의 노이즈를 그대로 9번 학습하게 된다.

2.3 손으로 한 칸 계산해 보기#

전체 시간은 약 137.5시간(표의 칸을 모두 더한 값), (label, env) 칸이 10개이므로 칸당 목표는 13.75시간이다. ('fall', 'indoor')는 반올림 전 값으로 3.56시간(표로는 1.0 + 0.7 + 1.8)이므로 가중치는 13.75 / 3.56 ≈ 3.9다(상한 5 이내). ('fall', 'outdoor')는 1.52시간(0.3 + 0.0 + 1.2) → 13.75 / 1.52 ≈ 9.0이지만 상한에 걸려 5.0이다. 그래서 실효 시간은 1.52 × 5 = 7.6시간이고, 나머지 9칸은 각각 13.75시간으로 맞춰지므로 비중은 7.6 / (9 × 13.75 + 7.6) = 7.6 / 131.4 ≈ 0.058 — 출력과 같다. 나머지 칸은 13.75 / 131.4 ≈ 0.105다.

말로 하면: 가중치는 이미 있는 데이터의 목소리를 키울 뿐, 없는 데이터를 만들지 못한다. 0시간 칸(fall × outdoor × EVT)은 어떤 가중치로도 채워지지 않는다. coverage 표의 진짜 용도는 가중치 계산이 아니라 다음 수집 목표를 정하는 것이다.

2.4 coverage 표를 운영하는 법#

  • 표의 단위를 여러 개로 본다: 시간, 세션 수, 사용자 수. 1시간이 한 사람에게서 나왔으면 사실상 1명분이다.
  • 축은 제품 요구에서 정한다: 손목 크기, 손잡이, 연령대, 기기 리비전, 펌웨어 버전, 실내/실외, 활동 강도. 축이 늘면 칸이 곱으로 늘어나므로 2~3축 조합까지만 표로 보고, 나머지는 축별 주변합(marginal)으로 본다.
  • 수집 계획(H8)에 "칸당 최소 사용자 N명, 최소 M시간" 같은 수집 목표를 숫자로 적는다. 펌웨어의 corner 커버리지 목표와 같다.
  • 데이터셋 버전마다 이 표를 자동 생성해 card(5절)에 붙인다.

3.1 직관 — 무엇이 문제인가#

idle 4000 : gesture 400 : fall 40 (100 : 10 : 1)인 데이터로 평범하게 학습하면, 모델은 loss의 대부분이 idle에서 나오므로 idle을 잘 맞히는 데 집중한다. "애매하면 idle"이라고 답하는 것이 평균 loss를 가장 많이 줄이기 때문이다. 결과는 A4 7절의 정확도 역설이다: accuracy는 높은데 fall을 놓친다.

3.2 Resampling — WeightedRandomSampler로 확인#

PyTorch에서 oversampling은 보통 torch.utils.data.WeightedRandomSampler로 한다. 샘플마다 "뽑힐 가중치"를 주고 복원 추출한다. 클래스 균형을 맞추려면 샘플 가중치 = 1 / (자기 클래스 개수)로 둔다.

출력에서 볼 것: 한 epoch에 세 클래스가 약 1/3씩 뽑혔다. 그 대가로 fall 샘플 40개는 각각 평균 37번 반복되고, idle 4000개 중 이번 epoch에 본 것은 1232개뿐이다. 반복이 37번이면 모델은 그 40개를 외우기 쉽다 — oversampling은 augmentation(매번 조금씩 다른 변형)과 같이 쓰는 게 보통이다. undersampling은 데이터의 81%를 버린다. 데이터가 넘치는 음성(idle) 클래스에는 괜찮을 수 있지만, 버린 idle 안에 "fall과 헷갈리는 어려운 음성(hard negative, 예: 손목을 책상에 탁 내려놓기)"이 있었다면 손해다.

3.3 Class weight — 손계산#

scikit-learn의 class_weight="balanced"와 같은 공식이다.

손으로: N = 4440, K = 3.

  • idle: 4440 / (3 × 4000) = 0.37
  • gesture: 4440 / (3 × 400) = 3.7
  • fall: 4440 / (3 × 40) = 37

말로 하면: "클래스별 가중치 × 개수"가 모든 클래스에서 같아지도록(0.37 × 4000 = 3.7 × 400 = 37 × 40 = 1480) 맞춘다. 그러면 loss 합계에서 세 클래스가 같은 목소리를 낸다. PyTorch에서는 F.cross_entropy(logits, y, weight=w)로 준다. 주의: weight를 주면 reduction="mean"은 단순 평균이 아니라 가중 평균(가중치 합으로 나눔)이다.

희귀 클래스가 극단적이면(1 : 10000) 역빈도 가중치가 너무 커져 학습이 불안정해진다. 그때는 √ 역빈도처럼 완화하거나, 상한을 두거나, "effective number of samples" 방식(Cui et al., 2019) 같은 변형을 쓴다.

3.4 Focal loss — 쉬운 샘플의 목소리를 줄인다#

직관. 불균형 데이터의 진짜 문제는 "idle이 많다"보다 "이미 쉽게 맞히는 idle이 많다"인 경우가 많다. 그 쉬운 샘플 하나하나의 loss는 작지만, 수천 개가 모이면 gradient를 지배한다. Focal loss(Lin et al., 2017, 원래 물체 검출의 배경/전경 불균형용)는 잘 맞힌 샘플의 loss를 곱셈으로 깎는다.

말로 하면: (1 − p_t)^γ는 "얼마나 틀렸나"의 γ제곱이다. 거의 맞힌 샘플(p_t = 0.9)은 (0.1)² = 0.01배로 줄고, 틀린 샘플(p_t = 0.1)은 (0.9)² = 0.81배로 거의 그대로 남는다. γ = 0이면 보통 CE다.

3.5 코드 — CE vs weighted CE vs focal, 클래스별 recall#

다음 코드는 2차원 특징 공간에 세 클래스(idle · gesture · fall)의 가우시안 덩어리를 100 : 10 : 1로 만들고, 같은 작은 MLP를 다섯 가지 방법으로 비교한다. test는 클래스별 recall을 보기 위해 균등(2000 / 2000 / 2000)하게 만들었다.

그림 5 — 위 코드의 실제 결과. 보통 CE와 α 없는 focal은 fall recall이 0.28~0.29로 거의 같다. 클래스 비율을 직접 다루는 방법(weighted CE, focal + α, 그리고 재학습 없는 logit 조정)은 fall recall을 0.78~0.80으로 올리는 대신 idle recall을 0.985 → 0.87 정도로 내준다.

출력에서 볼 것은 세 가지다.

  • focal loss만으로는 클래스 비율 문제가 풀리지 않았다. γ는 "쉬운 샘플 대 어려운 샘플"을 다루지, "흔한 클래스 대 드문 클래스"를 직접 다루지 않는다. 이 데이터는 클래스가 서로 겹쳐 있어서(σ = 0.6) 쉬운 샘플이 압도하는 상황이 아니었다. focal이 빛나는 곳은 물체 검출처럼 "아주 쉬운 배경 후보가 수만 개"인 경우다. 실무에서 focal은 α와 함께 쓰는 경우가 많고, 원 논문도 α를 같이 쓴다.
  • 불균형 처리는 공짜가 아니다. fall recall을 0.28 → 0.78로 올리면 idle recall은 0.985 → 0.87로 떨어진다. 결정 경계가 idle 쪽으로 이동했을 뿐이다. 어느 동작점이 맞는지는 제품이 정한다(낙상은 놓치면 위험하고, 오경보는 사용자를 귀찮게 한다).
  • 마지막 줄이 중요하다. 보통 CE로 학습한 모델의 logit에서 log(학습 데이터 클래스 비율)을 빼기만 해도(재학습 없이) weighted CE와 거의 같은 recall이 나왔다. 이것을 logit adjustment라고 하며(Menon et al., 2021), A4 7.4절의 "임계값 고르기"를 다중 클래스로 일반화한 것이다. 말로 하면: CE 모델은 "사전 확률이 100 : 10 : 1인 세상"에 맞춰 답하고, 그 사전 확률을 빼 주면 "균등한 세상"의 답이 된다. 임계값은 펌웨어 상수나 NVM 파라미터라서 OTA로 바꿀 수 있지만, weight는 재학습해야 바뀐다 — 배포 관점에서 큰 차이다.

3.6 균등 test의 precision은 현장 precision이 아니다#

위 출력의 "fall precision 0.831"은 fall이 1/3인 균등 test에서 잰 숫자다. 현장에서 fall은 훨씬 드물다. 대략 계산해 보자(weighted CE): fall 2000개 중 recall 0.783 → TP ≈ 1566. precision 0.831이므로 fall이라고 판정한 수 ≈ 1566 / 0.831 ≈ 1884, 그중 FP ≈ 318개가 비(非)fall 4000개에서 나왔다 → 비fall 오판정률 FPR ≈ 8%.

3.7 낙상 감지 같은 "희귀하고 비싼" 클래스의 레시피#

  1. 지표를 먼저 정한다: 이벤트 단위 recall(낙상 100회 중 몇 회 검출), 하루당 오경보 수(FA/day), 검출 지연. 윈도우 단위 accuracy는 쓰지 않는다.
  2. 데이터를 늘린다: 스턴트 수집(매트 위 연기, 여러 방향·속도), 공개 낙상 데이터셋 참고, 회전·스케일 증강. 음성 쪽은 hard negative(손목을 탁 내려놓기, 소파에 털썩 앉기, 기기 떨어뜨리기)를 의도적으로 모은다.
  3. split을 지킨다: 스턴트 참여자가 적으므로 fall 사용자를 fold마다 고르게(1.5절). test·golden에 fall이 반드시 있게(1.6절).
  4. 학습: class weight 또는 focal + α, 혹은 oversampling + 증강. 한 가지로 시작하고 seed 3~5개로 비교한다.
  5. 판정: val에서 FA/day 예산을 만족하는 임계값을 고른다(A4 9절). 후처리(연속 N프레임, 움직임 없음 확인)로 오경보를 더 줄인다.
  6. 평가: 클래스별·그룹별(6절) 표로 보고, 현장 비율로 precision을 다시 계산한다.

4.2 content-addressed 저장소와 dataset hash#

canonical()이 핵심이다. 같은 내용이면 항목 순서·키 순서·공백이 달라도 같은 바이트열이 나오게 만든 다음 해시한다. 이것을 정규화(canonicalization)라고 한다. 펌웨어로 치면 "구조체를 해시하기 전에 padding 바이트를 0으로 채우고 endianness를 고정하는" 것과 같은 이유다 — 의미가 같으면 비트도 같아야 해시가 쓸모 있다. 센서 샘플을 "<i2"(little-endian int16)로 명시한 것도 같은 이유다.

출력에서 볼 것: (1) 목록 순서를 뒤집어도 dataset hash가 같다 — 정규화 덕분이다. (2) 센서 파일은 그대로인데 라벨 하나만 바꿔도 dataset hash가 완전히 바뀐다. 데이터셋의 정체는 "파일"이 아니라 "파일 + 라벨 + split"이기 때문이다. 파일 해시만 기록하는 팀이 많은데, 그러면 라벨 수정이 버전에 안 잡힌다. (3) 같은 내용을 다시 넣어도 object는 4개 그대로다 — 버전이 100개여도 바뀌지 않은 파일은 한 번만 저장된다(deduplication). (4) 1비트 손상도 잡힌다 — SSD 펌웨어의 end-to-end data protection과 같은 발상이다.

4.5 도구 — DVC, lakeFS, 테이블 포맷#

이 노트에서는 설치하지 않았으므로 개념만 설명한다(아래 명령은 실행하지 않은 예시다).

DVC(Data Version Control) 는 git 옆에서 큰 파일을 버전 관리하는 도구다. 동작 원리는 4.2절과 같다.

  • .dvc 파일 안에는 출력 경로와 내용 해시(기본 MD5), 크기, 파일 수 같은 정보가 들어간다. git은 이 작은 파일만 관리하고, 큰 데이터는 원격 저장소에 해시 이름으로 있다 — "git 커밋 = 코드 + 데이터 포인터"가 된다.
  • dvc.yaml 파이프라인으로 "raw → 전처리 → split → 학습" 단계를 정의하면, 입력 해시가 안 바뀐 단계는 다시 돌리지 않는다(make의 의존성 추적과 같다).

lakeFS 는 object storage(S3) 위에 git 같은 branch/commit/merge를 얹는다. 데이터 레이크 전체를 브랜치로 떠서 실험하고, 검증이 통과하면 merge하는 식이다.

Delta Lake · Apache Iceberg 는 Parquet 파일들 위에 트랜잭션 로그·snapshot을 두는 테이블 포맷이다. 메타데이터 테이블(H3의 세션 표)을 버전 관리하기 좋고, "time travel"(예: 특정 버전·시점의 테이블을 다시 읽기)을 지원한다. 센서 원본 파일은 object storage에 두고, 세션 메타데이터·라벨·split 표를 이런 테이블로 관리하는 조합이 흔하다.

무엇을 쓰든 질문은 같다: (1) 버전이 불변인가, (2) 내용 해시로 검증되나, (3) 모델 학습 기록이 버전·해시를 가리키나, (4) diff를 볼 수 있나.

4.6 학습 run이 정말 그 데이터를 썼는지 검증하기#

모델을 학습할 때마다 run 메타데이터(O3의 ML CI와 연결)를 남긴다. 그리고 "주장된 데이터셋 해시"와 "실제 디스크의 데이터"를 대조한다.

출력에서 볼 것: 검증은 두 층이다. 파일 무결성(각 object를 다시 해시해 이름과 비교 — 검증 2에서 s2 손상을 정확히 짚었다)과 구성 일치(목록·라벨·split의 dataset hash가 run 기록과 같은가 — 검증 3에서 "1.2.0이라고 써 놓고 1.1.0의 해시를 기록한" 실수를 잡았다). 학습 스크립트 첫 줄에서 이 검증을 돌리고 실패하면 학습을 멈추게 하면, "어떤 데이터로 학습했는지 모르는 모델"이 생길 수 없다. 펌웨어 부트로더가 이미지 서명·CRC를 확인하고 부팅을 거부하는 것과 같은 자리다.

5. Dataset card — 데이터셋의 사용 설명서#

5.1 왜 필요한가#

칩에는 datasheet가 있다. 동작 전압, 온도 범위, 알려진 errata, 권장 사용 조건. datasheet 없이 칩을 쓰면 범위 밖에서 쓰다가 사고가 난다. Gebru et al.의 "Datasheets for Datasets"(2018 arXiv, 2021 CACM)는 바로 이 비유로 데이터셋에도 표준 문서를 붙이자고 제안했다. 모델 쪽 짝은 Mitchell et al.의 "Model Cards for Model Reporting"(ACM FAT 2019, 현 FAccT)으로, 모델의 용도·평가 조건·그룹별 성능을 적는다. Hugging Face Hub의 dataset card도 같은 흐름이다.

dataset card는 "누가, 왜, 어떻게 모았고, 무엇이 들어 있고, 무엇이 빠져 있고, 어디에 쓰면 안 되는지"를 적는다. 마지막 두 가지가 가장 중요하다.

이 표에서 "Known biases"와 "Intended use"가 가장 많은 사고를 막는다. 예를 들어 "연기된 낙상"이라는 한 줄이 없으면, 누군가 이 데이터로 학습한 모델을 노인 낙상 감지 기능에 그대로 쓸 수 있다.

5.4 card를 살아 있게 유지하는 법#

  • 숫자 부분(구성, split 교차표, coverage 표)은 레지스트리에서 자동 생성한다. 사람이 손으로 쓰면 버전과 어긋난다.
  • 서술 부분(동기, 알려진 치우침, 비용도)은 사람이 쓰고, 버전마다 리뷰한다. 코드 리뷰처럼 card 변경도 리뷰 대상이다.
  • 모델 card는 학습에 쓴 dataset card를 링크하고, 그룹별 성능(6절)을 적는다.

6.1 어디서 치우침이 생기나#

웨어러블 센서 데이터에서 성능이 그룹에 따라 달라지는 대표적인 원인:

손잡이(왼손/오른손)같은 제스처가 좌우 반전된 축으로 나타난다. 착용 손이 다르면 부호가 바뀐다IMU

PPG(광학 심박)와 피부색에 대해서는 신중하게 말해야 한다. 맥박 산소포화도(pulse oximetry, SpO2)에서는 피부색이 어두운 환자에서 SpO2를 과대 추정하는 경향이 임상 데이터로 보고됐다(Sjoding et al., NEJM 2020). 손목 웨어러블의 광학 심박 정확도에 대해서는 연구 결과가 엇갈린다 — 예를 들어 Bent et al.(npj Digital Medicine, 2020)은 피부색에 따른 유의한 차이는 찾지 못했고, 활동 중 오차가 더 크다고 보고했다. 면접에서는 "알려진 우려가 있고 그래서 측정해야 한다"고 말하는 것이 안전하다. 음성 쪽은 상용 음성 인식에서 화자 그룹에 따른 오류율 차이가 보고됐다(Koenecke et al., PNAS 2020).

6.2 측정 — 그룹별 지표와 신뢰구간#

치우침은 "전체 평균"에서 안 보인다. 그룹별로 쪼개서 보고, 그룹이 작으면 신뢰구간이 넓다는 것도 함께 본다. 신뢰구간은 사용자 단위 bootstrap으로 구한다 — 같은 사람의 제스처 40개는 독립이 아니므로, 제스처 단위로 resampling하면 구간이 실제보다 좁게 나온다.

6.3 완화 — 수집 목표가 먼저다#

  1. 수집 목표를 그룹별로 정한다: "각 그룹(손목 S/M/L, 왼손/오른손, 연령대 3구간)에 최소 30명" 같은 목표를 수집 계획(H8)에 숫자로 적는다. 인구 비율대로 모으면 소수 그룹은 영원히 작다 — 의도적으로 과대 표집(oversample in collection)한다.
  2. 평가 게이트에 그룹별 기준을 넣는다: "모든 그룹의 recall ≥ 0.85, 그룹 간 차이 ≤ 0.05" 같은 조건을 C8의 회귀 테스트에 넣는다. 평균만 보는 게이트는 그룹 회귀를 통과시킨다.
  3. 모델·전처리로 원인을 없앤다: 손잡이 문제는 축 반전 augmentation(좌우 미러링)이나 착용 손 설정값으로 입력을 정규화해서 푼다. 헐거운 착용은 착용 감지·품질 점수로 걸러 낸다.
  4. card에 적는다: 남은 차이는 Known biases에 숫자로 적는다.

7.1 고정해야 할 네 가지#

11. 면접에서 이렇게 말한다#

Q. "You have data from 200 users and more arrives every week. How do you split it, and keep the splits stable as data grows?"

A. 사용자 단위로 나누고, 셔플이 아니라 사용자 ID의 결정적 해시(salt 포함 SHA-256 mod 100)로 split을 정한다. 그러면 새 사용자가 들어와도 기존 사용자의 split은 절대 안 바뀐다. 별도로 golden test 사용자 목록을 동결하고, 희귀 클래스가 각 split에 들어갔는지 교차표로 확인한다. split 정책을 바꾸면 데이터셋 MAJOR 버전을 올린다.

"I'd split by user, and assign each user deterministically by hashing their ID with a salt — something like SHA-256 mod 100, with buckets 0–79 for train, 80–89 for validation, and the rest for test. Because the assignment depends only on the user's own ID, new users never move existing ones, so test users can't leak into training as the dataset grows. On top of that I'd freeze a golden test list, check a split-by-metadata crosstab so rare classes and device revisions show up in every split, and treat any change to the policy as a major dataset version."

Q. "How do you version datasets?"

A. 펌웨어 릴리스처럼 한다. 원본 파일은 내용 해시를 이름으로 object storage에 저장하고, 버전은 세션·파일 해시·라벨·split을 담은 manifest로 표현한다. manifest를 정규화해 해시하면 버전 전체의 지문이 된다. 버전은 불변, semantic versioning(split·스키마 변경 = MAJOR, 데이터·라벨 변경 = MINOR), changelog와 diff를 남긴다. 도구는 DVC나 lakeFS, 메타데이터는 Delta/Iceberg 테이블을 쓸 수 있다.

"Like firmware releases. Raw sensor files go into object storage, content-addressed by their hash, and a dataset version is a manifest listing sessions, file hashes, labels and split assignments. I canonicalize and hash that manifest, so the whole version has one fingerprint — and a label fix changes it, not just a file change. Versions are immutable, I use semantic versioning where split or label-schema changes are major and added data or label fixes are minor, and every release has a changelog and a diff. Tools like DVC or lakeFS implement the same idea."

Q. "Fall detection: falls are extremely rare in your data. What do you do?"

A. 먼저 지표를 바꾼다: 이벤트 단위 recall과 하루당 오경보 수. 데이터 쪽에서는 스턴트 수집과 증강, 그리고 손목 내려놓기 같은 hard negative를 모은다. 학습은 class weight나 focal + α, 판정 임계값은 val에서 FA/day 예산으로 고른다. 균등 test의 precision은 현장 비율로 다시 계산하고, trigger → 분류 → 확인의 다단계 구조로 오경보를 줄인다. split에서는 낙상 사용자가 fold와 golden에 고르게 들어가게 한다.

"First I'd change the metrics — event-level recall and false alarms per day, not window accuracy. On the data side I'd collect staged falls with varied directions and speeds, augment them, and deliberately collect hard negatives like slapping the wrist on a table. For training I'd start with class weights or focal loss with an alpha term, then pick the threshold on validation to meet a false-alarm budget, and recompute precision at the real-world base rate. Architecturally I'd use a cascade: a cheap accelerometer trigger, a classifier on the candidate window, then a confirmation step. And I'd make sure the few users with falls are spread across folds and included in the golden test set."

Q. "What goes into a dataset card?"

A. 동기, 구성(양·클래스·그룹 분포·빈칸), 수집 과정(기기·FW·센서 설정·프로토콜), 전처리, 라벨링 방법과 일치도, split 정책, 알려진 치우침, 동의·프라이버시, 용도와 비용도, 유지보수(담당·버전 규칙·deprecated). 숫자는 레지스트리에서 자동 생성하고, 가장 중요한 건 "무엇이 빠져 있고 어디에 쓰면 안 되는지"다.

"It follows Gebru et al.'s datasheets: motivation, composition — how many hours, users, classes and which cells are thin — the collection process including device revision, firmware and sensor settings, preprocessing, labeling method and agreement, the split policy, known biases, consent and privacy, intended and out-of-scope uses, and maintenance. I generate the numeric parts from the registry so they never drift from the version. The most valuable lines are usually the known gaps and the out-of-scope uses — for example, staged falls aren't the same as real falls in elderly users."

Q. "How would you reproduce a model trained six months ago?"

A. run 메타데이터에서 code commit, 데이터셋 버전과 해시, seed, config, 환경(lock 파일·docker digest)을 찾는다. 레지스트리에서 그 버전을 받아 해시를 검증하고, 결정적 loader로 다시 학습한 뒤 같은 golden으로 평가해 seed 분산 안에서 일치하는지 본다. 이게 안 되면 프로세스가 문제이므로, 학습 시작 시 dataset hash 검증과 메타데이터 기록을 강제한다.

"I'd start from the run metadata: code commit, dataset version and hash, seed, config, and the environment — lock file or container digest. I'd pull that dataset version, verify its hash, rebuild the environment, and retrain with deterministic data loading. Then I'd evaluate on the same golden set and expect the metrics to match within seed variance; bit-exact matches only on identical hardware and library versions. If any of those pieces is missing, the fix is process: the training script should refuse to start unless it can verify and record the dataset hash."

Q. "How would you find out if your model works worse for some users — say, left-handed users?"

A. 메타데이터에 손잡이·손목 크기 같은 그룹 정보가 있어야 한다. 그룹별 지표를 사용자 단위 bootstrap 신뢰구간과 함께 본다. 차이가 실제면 수집 목표를 그룹별로 정하고, 축 반전 증강 같은 모델 쪽 대책을 넣고, 그룹별 기준을 회귀 테스트 게이트에 넣는다.

"I'd make sure handedness and wrist size are captured as metadata at collection time, then report per-group recall with confidence intervals from a user-level bootstrap, since one person's gestures aren't independent. If a group is clearly worse, I'd set explicit collection targets for that group, add mitigations like mirroring augmentation, and add per-group thresholds to the release gate so an average can't hide a regression."

14. 요약 & 체크리스트#

데이터셋은 펌웨어 릴리스처럼 다룬다. split은 셔플이 아니라 사용자 ID의 결정적 해시로 정해 데이터가 늘어도 흔들리지 않게 하고, golden test는 동결하며, 시간·기기·환경 split은 서로 다른 질문이므로 섞지 않는다. 만든 뒤에는 split × 메타데이터 교차표와 fold별 희귀 클래스 개수를 반드시 센다. coverage 표로 빈칸을 찾되, 빈칸은 가중치가 아니라 수집으로 메운다. 불균형은 데이터(resampling·수집), 학습(class weight·focal + α), 판정(임계값·logit 조정), 평가(클래스별·현장 비율 precision) 네 곳에서 다룬다. 버전은 content-addressed 저장소 + 라벨·split까지 포함한 manifest의 해시로 정의하고, 불변·semantic versioning·changelog·diff를 갖춘다. dataset card에는 빠진 것과 쓰면 안 되는 곳을 적고, 그룹별 지표를 사용자 단위 신뢰구간과 함께 본다. 모든 학습 run은 code·data·seed·환경을 기록하고, 시작할 때 dataset hash를 검증한다. golden vector도 같은 규칙으로 데이터셋에서 작게, 버전을 달고 뽑는다.
