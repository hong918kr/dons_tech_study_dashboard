0. 큰 그림 — 이게 왜 필요한가#

0.1 센서 데이터는 "값"이 아니라 "(값, 시각)"이다#

펌웨어에서 센서를 읽으면 숫자가 나온다. 그런데 ML 데이터셋에 들어가는 순간 그 숫자는 반드시 언제 측정됐는지와 짝을 이룬다. 이유는 세 가지다.

  1. 라벨은 시간 구간으로 붙는다. "1.20 s ~ 1.55 s 사이에 손목 탭"처럼 사람이 영상이나 앱 버튼으로 붙인 라벨은 시간 축 위에 있다. 센서 시각이 150 ms 틀리면 라벨이 엉뚱한 샘플에 붙는다.
  2. 모델은 고정 rate를 가정한다. 1D-CNN 입력이 "100 Hz × 2 s = 200샘플"이라면, 실제로는 101.8 Hz였던 데이터를 그대로 넣으면 창 하나가 1.965 s가 된다. 학습 때와 배포 때 rate가 다르면 주파수 특징이 1.8% 밀린다.
  3. 멀티모달은 센서끼리 맞아야 한다. "말하면서 손을 들었다"를 학습하려면 마이크와 IMU가 같은 시간축에 있어야 한다. 두 센서는 보통 다른 칩, 다른 시계로 돈다.

Don에게 익숙한 말로 하면: SSD 펌웨어에서 여러 코어 로그를 합칠 때 timestamp가 어긋나면 "명령 완료가 명령 도착보다 먼저" 찍히는 말도 안 되는 타임라인이 나온다. ML 데이터에서는 그런 모순이 에러로 드러나지 않고 모델 정확도가 조용히 떨어지는 것으로만 나타난다. 그래서 더 위험하다.

0.2 기기 안의 시계들#

웨어러블 하나에도 시계가 여러 개 있다. 각 센서는 자기 발진기로 샘플링하고, MCU와 SoC는 각자의 크리스털로 시간을 센다.

그림 1 — 시계 도메인. 예를 들어 Hark 같은 웨어러블이라면 IMU·마이크·기타 센서가 always-on MCU에 붙고, MCU가 SoC와 메시지로 시간을 맞추고, SoC가 폰·NTP로 wall clock을 얻는 구성을 생각할 수 있다 (구성은 추정). 화살표마다 시간 오차가 끼어든다.

이 노트의 목표는 한 문장이다: 모든 샘플을 하나의 기준 시간축으로 옮기고, 그 정확도를 숫자로 보증한다.

0.3 얼마나 어긋나면 망가지나 — 직접 재 보자#

말로만 하면 감이 안 오니 실험부터 한다. 가짜 IMU 스트림(100 Hz)에 200~400 ms짜리 "제스처"를 300번 심고, 50 ms frame마다 "제스처/정지"를 맞히는 아주 작은 logistic regression을 학습한다. 그리고 학습 데이터의 라벨만 Δt만큼 늦게 찍는다 (테스트 라벨은 정확). 실제 수집에서 "라벨 앱의 시계와 센서 시계가 Δt 어긋난" 상황이다.

예제 1 — 무엇을 확인하나: 라벨 시각 오차 Δt가 커질 때 test accuracy와 제스처 recall이 어떻게 변하는지.

출력에서 볼 것: accuracy만 보면 속는다. Δt = 200 ms에서도 accuracy는 85.4%인데, 이는 모든 frame을 "정지"라고 답한 값(제스처 비율이 약 14.6%)이다. 제스처 recall은 Δt = 50 ms에서 이미 96.7% → 88.6%, 100 ms에서 69.9%, 200 ms에서 0.3%로 무너진다. 라벨 오류율(2·Δt / 2 s)이 10%만 돼도 짧은 이벤트 검출은 크게 망가진다.

그림 2 — 예제 1의 결과. 파란선(accuracy)은 완만하지만 주황선(제스처 recall)은 Δt ≈ 이벤트 길이의 절반을 넘으면 0으로 떨어진다. 점선은 "항상 정지"라고 답하는 쓸모없는 모델의 accuracy다.

말로 하면: 허용 가능한 시간 오차는 "가장 짧은 이벤트 길이"의 몇 분의 1이다. 200 ms짜리 탭을 잡는 모델이라면 라벨·센서 정렬은 20 ms 이내(이벤트의 10%)가 목표로 적당하다. 오디오의 phoneme(수십 ms)이나 오디오–IMU 융합이라면 수 ms가 필요하다. 이 숫자가 이 노트 전체의 "요구 사양"이다.

0.4 이 노트의 지도#

1. 시계 — ppm, 온도, 센서 내부 발진기#

1.1 직관 — 모든 시계는 조금씩 틀린다#

ppm (parts per million)은 "백만 분의 몇만큼 빠르거나 느린가"다. 20 ppm 빠른 시계는 1초(= 1,000,000 µs)를 1,000,020 µs로 센다. 즉 1초마다 20 µs씩 앞서 나간다.

말로 하면: ppm에 경과 초를 곱하면 µs 단위 drift가 나온다. 20 ppm × 3600 s = 72,000 µs = 72 ms.

손으로 하나 더: 100 Hz IMU가 1.8%(= 18,000 ppm) 빠르면 1분에 60 × 0.018 = 1.08 s, 즉 108샘플이 더 나온다. 이걸 "100 Hz"라고 믿고 샘플 번호 × 10 ms로 시각을 매기면 1분 뒤에는 1초 넘게 틀린다.

1.2 시계 모델 — offset, rate, jitter#

두 시계 A, B의 관계는 거의 항상 이 식으로 충분하다.

말로 하면: 시계 차이는 "처음에 얼마나 어긋났나(θ)" + "얼마나 다른 속도로 가나(ε)" + "매번 얼마나 흔들리나(n)"다. 동기화는 θ와 ε을 추정하는 일이고, jitter는 평균이나 하한 포락선으로 걸러 내는 일이다. RF 엔지니어인 Don에게는 "주파수 오프셋 + 위상 오프셋 + 위상 잡음"과 같은 구조다.

1.4 숫자로 감 잡기#

예제 2 — 무엇을 확인하나: ppm 값별로 1초·1분·1시간·하루 drift와, 100 Hz 센서가 1시간에 몇 샘플 어긋나는지. 그리고 32.768 kHz 크리스털의 온도 특성(전형 계수 −0.034 ppm/°C², 25 °C 정점).

출력에서 볼 것: 크리스털급(20~50 ppm)은 1시간에 72~180 ms — 긴 녹음에서는 무시 못 하지만 회귀로 쉽게 잡히는 크기다. 반면 IMU 내부 발진기급(1.8%)은 1시간에 64.8 s, 6480샘플이다. 이건 "시간 오차"라기보다 "rate 자체가 다르다"고 봐야 한다. 온도 쪽은 −10 °C에서 −42 ppm: 겨울 야외에서 차고 다니는 웨어러블의 RTC는 하루 3.6 s 느려진다. 체온(37 °C) 근처에서는 −4.9 ppm으로 작다.

1.5 임베디드 연결과 함정#

  • 32-bit µs 타이머는 2³² µs ≈ 71.6분에 한 번 감싼다(wrap). 1시간 넘는 세션 로그에 32-bit 시각만 남기면 후처리에서 시간이 거꾸로 간다. 펌웨어에서 64-bit로 확장하거나, 로그에 wrap 횟수를 남긴다 (A6에서 uint32 wrap 복원, 예제 4에서 C로 확장).
  • 저전력 모드에서 HF 크리스털을 끄고 RC 발진기로 타이머를 돌리면 그 구간만 timestamp가 1~3% 틀린다. "sleep 다녀온 뒤에만 이상한 데이터"의 흔한 원인이다.
  • Wall clock(CLOCK_REALTIME, NTP)은 동기화 순간 점프한다. 샘플 간격 계산에는 단조 시계(CLOCK_MONOTONIC, MCU 타이머)를 쓰고, wall clock은 세션 시작에 한 번 "앵커"로만 기록한다.
  • ppm은 기기마다 다르다. 한 대에서 잰 ODR 보정값을 펌웨어에 상수로 박으면 다른 기기에서는 틀린다. 기기별·세션별로 추정한다 (2절).

2.5 FIFO 지연과 ISR jitter를 다루는 법#

  • 하드웨어 capture가 최선: IMU INT 핀을 타이머 input capture 채널에 연결하면 엣지 순간의 카운터 값이 래치된다. ISR이 50 µs 늦게 돌아도 시각은 정확하다. 보드 설계 단계에서 요구해야 한다 — BSP·HW 리뷰 때 "센서 INT 핀은 capture 가능한 핀으로" 한 줄을 넣는다.
  • 소프트웨어 timestamp는 ISR 맨 첫 줄에서: FIFO를 SPI로 다 읽은 뒤 시각을 찍으면 읽기 시간(25샘플 × 12 B = 300 B, 8 MHz SPI면 약 0.3 ms)과 그 흔들림이 다 들어간다. 시각을 먼저, 읽기는 나중.
  • "마지막 샘플 = IRQ 시각"이 아닐 수도 있다: watermark IRQ와 FIFO 읽기 사이에 샘플이 더 쌓이면, 읽은 샘플 수 N이 watermark보다 크다. 이때 IRQ 시각에 해당하는 샘플은 마지막이 아니라 watermark번째다. 읽기 시점에 FIFO 카운트 레지스터를 같이 읽어 "IRQ 순간 샘플 번호"를 맞춘다.
  • 지연 하한은 측정한다: 로직 분석기로 INT 엣지와 ISR 진입 GPIO toggle의 차이를 재서 Δ_lat의 바닥과 분포를 얻는다 (Don이 bring-up에서 늘 하던 일).
  • 센서 timestamp가 있으면 둘 다 쓴다: 센서 timestamp는 "센서 시계로 정확"하고 IRQ 시각은 "MCU 시계로 흔들림". 두 시계 사이를 회귀(같은 방법)로 묶으면 정확 + MCU 시간축 둘 다 얻는다.

2.6 흔한 함정#

  • 명목 ODR로 역산 → batch 톱니 + batch 경계 간격 이상. 학습 데이터의 dt 히스토그램에 봉우리가 두 개 생긴다.
  • 기기 한 대에서 잰 ODR을 상수로 사용 → 다른 기기에서 ±수 % 틀림.
  • 회귀를 세션 전체에 한 번만 → 온도가 크게 바뀌는 세션(실내 → 야외)에서 ODR이 변하면 잔차가 휘어진다. 창을 움직이는 회귀(4.5절의 piecewise와 같은 생각)를 쓴다.
  • ODR 설정을 바꾼 직후 FIFO에 이전 rate 샘플이 섞여 있다 → 설정 변경 시 FIFO flush + 세션 세그먼트 분리.

3.2 검출 신호 세 가지#

  1. seq 카운터: 펌웨어가 샘플(또는 batch)마다 1씩 올리는 번호. 가장 확실하다. diff == 1 정상, > 1 누락, == 0 중복, < 0 역순. 16-bit면 wrap을 처리한다 (65535 → 0은 −65535가 아니라 +1).
  2. timestamp 간격: seq가 없는 센서는 dt > 1.5 × T를 gap으로 본다. 단 2절의 톱니가 있으면 오탐이 생기므로 회귀 보정 후에 검사한다.
  3. 센서 상태 플래그: FIFO overflow 비트, FIFO 카운트. "몇 개가 사라졌는지"는 모를 수 있어도 "사라졌다"는 확실히 안다 (G2).

seq를 어디에 붙이냐도 설계 결정이다. 샘플을 처음 손에 넣는 곳(센서 ISR)에서 붙여야 그 뒤 모든 단계의 손실을 잡는다. 전송 직전에 붙이면 FIFO overflow는 안 보인다.

4. 칩 사이 · 센서 사이 동기화#

2절은 "한 센서의 샘플을 MCU 시간축에 올리는 일"이었다. 이제 서로 다른 시계를 가진 두 스트림을 맞춘다. 좋은 것부터 순서대로 본다.

4.1 최선은 시계를 하나로 — 같은 clock domain#

  • 같은 MCU에 붙은 센서들은 모두 MCU 타이머로 timestamp를 찍는다 → 시간축은 이미 하나다. 남는 건 각 센서의 ODR 추정(2절)뿐이다.
  • 마이크는 MCU/SoC가 PDM clock을 공급하므로 오디오 샘플 rate가 호스트 크리스털에 묶인다. 같은 SoC 안의 여러 마이크는 같은 clock을 받으므로 샘플 단위로 맞다 (beamforming의 전제, G4).
  • IMU에 외부 clock 입력이 있으면 호스트 클럭을 넣어 ODR까지 묶을 수 있다 (1.3절).
  • 같은 SoC 안의 코어들은 전역 system counter를 쓰면 끝이다 (E8 7.2절).

4.2 칩이 다르면 — 하드웨어 sync pulse#

두 칩(예: 손목 MCU와 이어버드 SoC, 또는 데이터 수집용 리그의 카메라와 IMU 보드)을 선으로 연결할 수 있다면 GPIO sync pulse가 가장 정확하다.

말로 하면: 같은 사건(펄스 엣지)을 두 시계로 찍은 쌍을 모으면 1.2절의 θ와 ε이 직선 fit으로 나온다. capture를 쓰면 µs 이하로 맞는다. 데이터 수집 리그(카메라 + 센서 보드)에서는 카메라 strobe/trigger 출력을 센서 보드 capture 핀에 넣는 방식을 흔히 쓴다.

4.3 선이 없으면 — 물리 이벤트로 맞추기 (탭·박수)#

웨어러블 데이터 수집에서는 선을 연결할 수 없는 경우가 많다. 그때는 두 센서가 동시에 느끼는 물리 이벤트를 쓴다. 기기를 손가락으로 톡 치면 마이크에는 "딱" 소리가, 가속도계에는 충격 진동이 동시에 기록된다. 두 신호의 envelope를 cross-correlation하면 시간 차이가 나온다.

cross-correlation은 한 신호를 다른 신호에 대해 lag만큼 밀면서 곱해서 더한 값이다. 두 신호가 가장 잘 겹치는 lag에서 최대가 된다.

말로 하면: accel envelope a와 mic envelope m을 ℓ만큼 어긋나게 겹쳐서 곱의 합을 구하고, 그 합이 가장 큰 ℓ이 두 시계의 offset이다. Don이 RF에서 쓰던 preamble correlation(동기 검출)과 같은 연산이다.

설계 포인트 세 가지:

  1. rate가 다른 두 신호를 공통 rate로: mic 16 kHz는 1 ms 블록 평균 envelope(1 kHz), accel 100 Hz는 |차분|을 1 kHz로 선형 보간한다. 정렬 정밀도는 결국 느린 쪽(accel 10 ms)에 묶이지만, 포물선 보간으로 격자보다 세밀하게 peak를 찾는다.
  2. 이벤트를 불규칙 간격으로 여러 번: 탭을 일정 간격(예: 정확히 2초마다)으로 치면 2초 어긋난 lag에서도 peak가 생겨 모호하다. 간격을 들쭉날쭉하게.
  3. 신뢰도 지표: peak 값 ÷ 다른 lag의 최대값. 이 비가 작으면 정렬을 믿지 않는다.

예제 6 — 무엇을 확인하나: mic 시계 기준 2.0, 4.7, 7.9 s에 탭 3번, accel 시계는 mic보다 137.4 ms 늦은 상황. envelope cross-correlation + 포물선 보간으로 offset을 추정한다.

출력에서 볼 것: 추정 offset 138.0 ms, 오차 +0.6 ms — accel 샘플 주기(10 ms)의 1/16이다. peak가 다른 후보보다 2.9배 크다(탭 3개가 모두 같은 lag에서 겹쳤다는 뜻). 남은 0.6 ms 오차는 두 envelope 모양이 다르고(소리는 날카롭고 진동은 감쇠가 느림) accel 차분이 반 샘플 밀리기 때문이다. 이런 고정 편향은 탭 실험을 여러 기기에서 반복해 평균 편향을 재고 빼 준다.

4.4 메시지로 맞추기 — NTP/PTP, BLE#

선도, 공통 이벤트도 없으면 메시지를 주고받는다. 4-타임스탬프 방식의 유도와 코드는 E8 7.2절에 있다. 요약만 다시 쓴다.

  • NTP: 인터넷 위에서 대략 ms~수십 ms. 라벨 앱(폰)의 wall clock이 보통 이 수준이라, 폰 앱으로 찍은 라벨 시각을 그대로 믿으면 수십 ms 오차를 안고 시작한다.
  • PTP (IEEE 1588): 같은 원리지만 하드웨어 timestamp(MAC/PHY에서 패킷이 지나가는 순간 시각을 래치)로 소프트웨어 지연을 없애 LAN에서 sub-µs까지 간다. 핵심 교훈은 "정확도는 프로토콜이 아니라 timestamp를 어디서 찍느냐가 정한다"이다 — 2.5절의 input capture와 같은 이야기다.
  • BLE: connection event는 양쪽이 공유하는 시간 기준(anchor point)에서 일정 간격으로 일어나므로, 이를 이용해 두 기기의 시계를 수십 µs 수준까지 맞추는 구현이 있다고 알려져 있다. 다만 일반 GATT 앱 계층에서는 그 시각이 노출되지 않는 경우가 많고, 스택·칩마다 다르다 (확인 필요). LE Audio의 isochronous channel은 동기 재생을 위한 기준점을 규격에 둔다. 실무에서는 "링크 계층 시각을 얻을 수 있는 칩·스택인가?"를 먼저 확인한다.

4.5 긴 녹음 — offset 한 번으로는 안 된다#

offset을 시작에 한 번 재면 끝이 아니다. 1.2절의 ε 때문에 시간이 지날수록 벌어지고, ε 자체도 온도에 따라 변한다. 그래서 주기적으로 offset을 재고(sync 메시지, 주기적 펄스, 가끔의 탭), 그 시계열에 선을 맞춘다.

예제 7 — 무엇을 확인하나: 2시간 녹음, 1분마다 offset 측정(잡음 0.3 ms). 처음 1시간은 drift 20 ppm, 60~70분 사이 온도 변화로 35 ppm으로 바뀐다. 보정 방법 다섯 가지의 정렬 오차를 비교한다.

출력에서 볼 것:

  • 처음 offset 1회: 최대 193 ms — 2시간에 20~35 ppm이 쌓인 값. 시작에 한 번 맞추는 수집 스크립트가 흔히 이 상태다.
  • 전체 직선 1개: 26.6 ppm 평균 기울기로 최대 14.3 ms. drift가 변하면 직선 하나로는 휜 곡선을 못 따라간다.
  • 측정점 직선 연결: RMS 0.22 ms지만 측정 잡음을 그대로 따라간다.
  • 국소 직선(piecewise): ±3분 창이 최대 0.37 ms로 가장 좋다. ±10분 창은 잡음은 더 줄지만 drift가 바뀌는 구간에서 따라가지 못해(bias) 최대 1.4 ms다. 창 크기는 bias–variance trade-off다 — 측정 잡음이 크면 창을 넓히고, 온도 변화가 빠르면 좁힌다. Don에게는 "loop bandwidth를 정하는 문제"와 같다.

그림 5 — 예제 7의 정렬 오차. 주황(전체 직선 1개)은 drift가 바뀌는 60~70분(회색 띠) 전후로 휘어 ±14 ms까지 간다. 초록(±3분 국소 직선)은 전 구간에서 0 근처다.

4.6 흔한 함정#

  • offset 부호 혼동: "B − A"인지 "A − B"인지 문서와 코드에 명시하지 않아 보정이 두 배로 틀어짐. 변수 이름에 방향을 넣는다 (off_imu_minus_mic).
  • 폰 라벨 앱의 wall clock을 그대로 사용 → NTP 오차(수십 ms) + 앱의 터치 지연. 세션 시작·끝에 sync 이벤트(탭)를 넣어 라벨 시계도 같은 방법으로 맞춘다.
  • 정렬은 했지만 rate는 안 맞춤 → 녹음 앞쪽은 맞고 뒤쪽으로 갈수록 벌어진다. 탭을 시작과 끝 두 번 이상 넣으면 offset과 drift를 둘 다 구할 수 있다.
  • cross-correlation을 raw 신호로 → 소리(kHz)와 진동(수십 Hz)은 파형이 달라 상관이 약하다. envelope로 바꿔서 한다.

5. ML용 resampling — 불규칙 timestamp에서 고정 rate로#

5.1 왜 고정 rate가 필요한가#

모델 입력은 X [N, C, L] — L개 샘플이 정확히 같은 간격이라는 가정 위에 있다 (A6 6절). 그런데 2~4절을 거친 데이터는:

  • 실제 rate가 명목과 다르다 (101.8 Hz)
  • 드물게 구멍이 있다 (3절)
  • 다른 센서와 시간축은 맞췄지만 샘플 시각이 서로 다른 격자 위에 있다 (IMU 101.8 Hz, PPG 24.95 Hz, 오디오 16 kHz)

그래서 마지막 단계로 목표 격자(예: 정확히 100 Hz, t = 0, 10, 20 … ms)를 만들고 각 격자점의 값을 원래 샘플들로부터 추정한다. 이게 resampling이다. 방법에 따라 오차가 크게 다르다.

5.2 방법 다섯 가지 — 직관#

방법격자점 값장점단점
ZOH (zero-order hold)직전 샘플 값을 그대로미래를 안 봄(실시간 가능), 가장 쌈평균 반 샘플 지연 + 계단
nearest가장 가까운 샘플원래 값만 사용반 샘플 이내 시간 이동, 계단
linear앞뒤 두 샘플을 시간 비율로 섞음싸고 대부분 충분고주파 성분을 깎음 (low-pass 효과)
cubic spline주변 여러 점의 3차 곡선부드러운 신호에 매우 정확경계·구멍 근처에서 overshoot
band-limited (sinc / polyphase)이론상 Nyquist 이하 신호를 완벽 복원하는 필터대역 안에서 가장 정확, 오디오 표준비쌈, 입력이 (거의) 균일해야 함, 앞뒤 지연

linear 보간 오차를 손으로: 간격 h로 샘플된 신호 x(t)의 선형 보간 오차는 최대 h²/8 × max|x''|이다. 진폭 1, 주파수 f인 사인파는 max|x''| = (2πf)².

말로 하면: 선형 보간 오차는 (주파수 × 간격)²에 비례한다. 신호가 샘플 rate에 비해 느리면 무시할 만하고, Nyquist에 가까워지면 급격히 커진다. ZOH는 평균 h/2 지연이 있어서 위상 오차가 2πf·h/2, 2 Hz에서 약 6%로 linear보다 훨씬 크다.

5.3 코드로 확인 — 같은 신호, 다섯 방법#

예제 8 — 무엇을 확인하나: 2·10·25·40 Hz 사인파를 101.8 Hz로 샘플링(2절 회귀로 보정된 시각이라고 가정)하고 100 Hz 격자로 옮길 때, ZOH·nearest·linear·cubic·polyphase(resample_poly, 101.8 × 500/509 = 100)의 RMS 오차.

출력에서 볼 것: 2 Hz에서 linear 0.14%(손계산의 최대 0.19%와 맞음), ZOH 7.1%(반 샘플 지연 때문). 10 Hz에서 linear 3.4%(손계산 최대 4.8%), 40 Hz에서는 48.5% — Nyquist(50 Hz) 근처에서 linear는 쓸모가 없다. polyphase는 모든 주파수에서 0.25% 이하다. cubic은 저주파에서 최고지만 40 Hz에서 21.6%로 무너진다.

그림 6 — 예제 8의 RMS 오차 (log 축). 주파수가 올라가면 ZOH·nearest·linear 순으로 무너지고, polyphase(회색)만 바닥에 남는다.

그래서 무엇을 쓰나:

  • IMU 동작 인식처럼 관심 대역이 rate의 1/5 이하(100 Hz에서 < 20 Hz)면 linear로 충분하다. 오차 수 % 이하이고, 구멍 근처에서도 안전하다.
  • 진동·오디오처럼 대역이 Nyquist 가까이까지 차 있으면 polyphase/band-limited. 단 입력이 균일 간격이어야 하므로 "2절 회귀로 균일 시각을 만든 뒤 → 비율 변환" 순서로 한다. 구멍이 있으면 구멍 기준으로 세그먼트를 나눠 각각 처리한다.
  • 실시간 펌웨어(미래 샘플을 기다릴 수 없음)는 ZOH나 짧은 FIR 보간. 지연을 감수할 수 있으면 polyphase.
  • cubic은 깔끔한 저주파 신호 후처리에만, 구멍·경계 근처는 조심.

5.4 줄이는 방향 (downsampling)에는 anti-aliasing이 먼저#

rate를 낮출 때는 보간 방법보다 aliasing이 더 큰 문제다. 새 Nyquist보다 높은 성분이 남아 있으면 낮은 주파수로 접혀 들어와 진짜 신호와 구별할 수 없게 된다 (G5에서 자세히).

예제 9 — 무엇을 확인하나: 1 Hz 동작 + 30 Hz 진동(예: 차량·모터)을 100 Hz → 25 Hz로 줄일 때, 그냥 4개마다 1개 솎아내기 vs scipy.signal.decimate(low-pass FIR 후 솎아내기). 30 Hz는 새 Nyquist 12.5 Hz를 넘으므로 |30 − 25| = 5 Hz로 접힌다.

출력에서 볼 것: 솎아내기만 하면 존재하지 않던 5 Hz 성분이 진폭 0.5로 나타난다 — 모델 입장에서는 "손을 5 Hz로 떠는 동작"처럼 보인다. decimate는 30 Hz를 먼저 걸러서 5 Hz가 0이다. pandas resample().mean()(구간 평균)도 약한 low-pass라 aliasing을 조금 줄이지만 충분하지 않다 (A6 5.3절).

5.5 pandas 함정 (A6 연결)#

A6에서 reindex(method="nearest") + interpolate(limit=…)로 드롭 구간을 메우는 법을 봤다. 여기서는 rate가 명목과 다를 때 생기는 함정을 본다.

예제 10 — 무엇을 확인하나: (1) interpolate() 기본값이 시간 간격을 무시하는 문제, (2) 1.8% 빠른/느린 센서를 resample("10ms")로 칸에 넣을 때 생기는 일, (3) asfreq가 거의 다 NaN이 되는 이유, (4) 올바른 시간 기반 보간.

출력에서 볼 것:

  • interpolate() 기본 method="linear"는 index를 무시하고 행 순서로 보간한다. 10 ms와 50 ms 사이 40 ms의 값을 "가운데 행"으로 보고 2.5를 넣는다. 시간으로 맞으면 1 + 3 × 30/40 = 3.25다. 시간 index가 불규칙하면 반드시 method="time".
  • 101.8 Hz를 10 ms 칸에 넣으면 18칸에 샘플이 2개 → mean()이 두 샘플을 평균해 시간이 흐려진다. 98.2 Hz면 17칸이 비어서 NaN이 생긴다 — 드롭이 없는데도 NaN이 생기므로 3절의 gap 검출과 섞이면 "드롭 17개"로 잘못 보고된다.
  • asfreq("10ms")는 격자 시각과 정확히 같은 timestamp만 가져온다. 실제 timestamp는 격자에 딱 맞을 일이 거의 없어서 1000칸 중 2칸만 값이 있다.
  • 올바른 방법: 원래 시각과 격자 시각을 합친 index에서 interpolate(method="time")를 하고 격자만 남긴다. 1 Hz 신호에서 최대 오차 0.0005.

5.6 라벨 정렬 — 구간 라벨을 샘플 라벨로#

라벨은 보통 (시작, 끝, class) 구간으로 온다 (영상 주석 도구, 앱 버튼). 이걸 샘플 단위 라벨로 바꿀 때 두 가지를 한다.

  1. 시계 변환: 라벨 시계(영상·폰) → 센서 시계. 4절에서 구한 offset(필요하면 drift까지)을 적용.
  2. 경계 tolerance: 정렬 오차와 사람의 주석 오차(수십 ms)가 있으므로 경계 ±tol 안의 샘플은 확신할 수 없다. 이 샘플들을 무시 라벨(-1)로 두고 학습 loss에서 뺀다 (PyTorch CrossEntropyLoss(ignore_index=-1)).

손으로: 50 Hz, tol = 60 ms → 경계 하나당 ±60 ms = 120 ms 폭 → 약 6샘플이 -1. 구간 2개 = 경계 4개 = 24샘플.

예제 11 — 무엇을 확인하나: 영상 시계 기준 라벨 2개를 offset −250 ms로 IMU 시계에 옮기고, 경계 ±60 ms를 -1로 표시.

출력에서 볼 것: -1이 24샘플로 손계산과 같다. 첫 구간 시작(영상 1.00 s → IMU 0.75 s) 주변 0.70~0.80 s가 -1이고, 0.82 s부터 class 1이다. class 1은 원래 55샘플(0.75~1.85 s)에서 경계 6샘플이 빠져 49샘플이다.

pd.merge_asof(…, tolerance=…)(A6)는 "점 이벤트를 가장 가까운 샘플에 붙이기"에 좋고, 구간 라벨은 이 예제처럼 searchsorted로 index 범위를 구하는 게 단순하고 빠르다.

5.7 정리 — 보간할까, 말까#

  • 같은 센서, 짧은 구멍(대역에 비해 짧음), 저주파 신호 → 보간 OK, mask 남김.
  • 긴 구멍, 오디오, 이벤트성 신호(탭 충격) → 보간 금지, 세그먼트 분리 또는 창 버림.
  • rate 변환(101.8 → 100) → 보간이 아니라 resampling. 대역이 낮으면 linear, 높으면 polyphase.
  • 줄이는 방향 → 항상 anti-aliasing 먼저.
  • 어떤 경우든 배포 기기에서 하는 전처리와 똑같이 한다. 학습은 polyphase로 100 Hz를 만들었는데 기기는 IMU 104 Hz를 그대로 넣는다면, 학습/배포 불일치(training–serving skew)가 생긴다.

6. 스트리밍에서의 rate mismatch — 버퍼 drift와 ASRC#

6.1 직관 — 두 수도꼭지#

지금까지는 녹음을 나중에 맞추는 이야기였다. 실시간 시스템에서는 같은 문제가 버퍼로 나타난다. 마이크 ADC(생산자)는 자기 시계로 16 kHz를 만들고, 소비자(예: 다른 칩의 KWS 엔진, BT로 받는 쪽, USB 호스트)는 자기 시계로 "10 ms마다 160샘플"을 가져간다. 두 시계가 100 ppm 다르면 물이 들어오는 속도와 나가는 속도가 아주 조금 달라서 욕조가 서서히 넘치거나 마른다.

말로 하면: 100 ppm 차이는 16 kHz에서 초당 1.6샘플이다. 작아 보이지만 17분이면 100 ms 버퍼 여유를 다 먹는다. 버퍼를 키우면 늦게 넘칠 뿐 언젠가 넘치고, 지연(latency)만 커진다 (D6 5.2절).

6.2 해결 — 버퍼 fill을 보고 비율을 조정하는 제어 루프#

ASRC(asynchronous sample-rate conversion)는 "입력 rate와 출력 rate의 비율이 정확히 알려지지 않고 천천히 변하는" 상황의 rate 변환기다. 5.3절의 polyphase 변환기를 비율 r을 실시간으로 바꿔 가며 돌린다고 보면 된다. 그 r을 무엇으로 정하나? 버퍼 fill이 센서다:

말로 하면: 버퍼가 목표보다 차오르면 소비 쪽이 입력을 조금 더 빨리(비율 r > 0) 먹게 한다. 이건 Don에게 익숙한 PLL과 같은 구조다 — 버퍼 fill = 위상 오차, r = VCO 주파수 조정, EMA = loop filter. 플랜트(버퍼)가 적분기라서 P 제어만으로도 안정하지만, 정상 상태에서 r = 100 ppm을 유지하려면 오차 e = 100 ppm / Kp가 남는다 (Kp = 0.5 ppm/샘플이면 200샘플 = 12.5 ms 치우침). I 항이 그 정상 상태 오차를 없앤다.

현실의 잡음은 DMA 블록 양자화다. 생산 쪽은 64샘플 블록 단위로만 버퍼에 보이므로 fill이 0~64 계단으로 흔들린다. 이걸 EMA로 평활하지 않으면 r이 덜컹거려 소리의 피치가 미세하게 떨린다.

예제 12 — 무엇을 확인하나: 생산자 100 ppm 빠름, 64샘플 DMA, 1시간. 제어 없음 vs PI + EMA. 인자로 파일 이름을 주면 그림용 CSV를 쓴다.

출력에서 볼 것: 제어 없으면 1020 s에 overflow(손계산 1000 s + 시작 시 DMA 블록 여유). PI는 fill을 1568~1632, 즉 목표 ±32(= DMA 블록의 절반)에 붙잡는다. 매 10분 찍은 순간 r은 83~90 ppm으로 보이지만, 마지막 10분 평균 r은 100.00 ppm — 생산자와 소비자의 시계 차이를 정확히 추정한 것이다. 순간 r이 85~106 ppm 사이에서 흔들리는 건 DMA 계단 때문이며, ±10 ppm 피치 변화는 귀로 들을 수 없는 크기다.

그림 7 — 예제 12의 버퍼 fill. 주황(제어 없음)은 초당 1.6샘플씩 올라 17분 무렵 용량(빨간 점선)을 넘는다. 초록(PI 제어 ASRC)은 1600 근처에 평평하게 머문다.

6.3 실제 시스템에서는#

  • USB Audio의 asynchronous 모드는 기기가 "내가 실제로 소비하는 rate"를 피드백 endpoint로 호스트에 알려 주고, 호스트가 보내는 샘플 수를 조정한다 — 같은 제어 루프를 USB 위에 올린 것이다.
  • 블루투스 오디오, 여러 오디오 장치를 합치는 OS 오디오 서버도 ASRC나 비슷한 rate 추적을 쓴다고 알려져 있다 (구현은 제품마다 다르다).
  • 가장 단순한 대안은 "가끔 샘플 하나를 버리거나 복제"하는 것이다. 100 ppm이면 1만 샘플(0.6 s)에 한 번. 음성 품질에는 작은 클릭이 생기지만 KWS 입력처럼 품질 요구가 낮으면 쓸 수 있다. 단 학습 데이터를 녹음하는 경로에서는 피한다 — 미세한 불연속도 특징 분포를 바꾼다.
  • ML 관점의 교훈: 같은 마이크라도 "ADC 직후 녹음"과 "ASRC를 거친 스트림"은 미세하게 다른 신호다. 학습 데이터를 어느 지점에서 떠 왔는지 메타데이터에 남긴다 (H1·H3).

10. 면접에서 이렇게 말한다#

Q. "How do you timestamp FIFO-batched IMU samples accurately?"

A. watermark IRQ 시각을 하드웨어 capture(없으면 ISR 첫 줄)로 찍고, 그 시각을 batch 마지막 샘플에 맞춘 뒤 앞 샘플들은 주기로 거꾸로 계산한다. 핵심은 주기를 명목값이 아니라 IRQ 시각 vs 누적 샘플 번호의 회귀 기울기로 추정하는 것이다. IRQ 지연은 항상 양수라서 아래 포락선에 맞춘다. 시뮬레이션에서 1.8% 빠른 IMU를 명목 주기로 역산하면 batch마다 4 ms 톱니가 생겼고, 회귀로 바꾸면 수십 µs 이내였다.

"I latch the watermark interrupt with a timer input capture, or timestamp at the very top of the ISR if I can't, and anchor that time to the last sample in the batch. Then I back-calculate the earlier samples using the real sample period, not the nominal one — I estimate it by regressing interrupt times against the cumulative sample index over many batches, fitting the lower envelope because interrupt latency is always positive. In a simulation with an IMU running 1.8 percent fast, nominal back-calculation gave a 4-millisecond sawtooth per batch, while the regression got it down to tens of microseconds, and it runs fine on a Cortex-M with a 32-point sliding window."

Q. "Your IMU's ODR is 2% off from nominal. What are the consequences and how do you fix it?"

A. 결과 세 가지: (1) 샘플 번호로 시각을 매기면 1분에 1.2 s씩 밀려 라벨이 어긋난다, (2) 모델 창이 "200샘플 = 2 s"가 아니라 1.96 s가 되어 주파수 특징이 2% 밀린다 — 기기마다 오차가 다르면 기기 간 분포 차이가 된다, (3) 다른 센서와의 정렬이 시간에 따라 벌어진다. 고치는 법: 실제 rate를 회귀로 추정해 정확한 timestamp를 만들고, 학습 전 고정 rate로 resampling, 배포 기기도 같은 전처리. 가능하면 센서의 외부 clock 입력이나 보정 레지스터를 쓴다.

"Three things break. If you assign times by sample count, you drift about 1.2 seconds per minute, so labels slide off the events. The model's fixed-length window now covers a different duration, so frequency features shift by 2 percent, and since every unit is off by a different amount it shows up as device-to-device distribution shift. And alignment with other sensors drifts over the session. The fix is to estimate the true rate per device and session from interrupt timestamps, timestamp samples from that, resample to the nominal rate before training, and do the identical resampling on the device. If the part supports an external clock input or reports its frequency error, I use that too."

Q. "How do you align audio and IMU recorded on different chips?"

A. 같은 시계를 공유할 수 있으면 그게 최선이다. 아니면 GPIO sync pulse + input capture, 그것도 안 되면 두 센서가 같이 느끼는 물리 이벤트(탭)를 envelope cross-correlation으로 맞춘다. 탭은 시작과 끝, 불규칙 간격으로 여러 번 — 그래야 offset과 drift를 둘 다 구하고 lag 모호성이 없다. 긴 녹음은 주기적 offset 측정에 국소 직선을 맞춘다. 시뮬레이션에서 2시간 녹음에 offset 한 번만 쓰면 193 ms 틀렸고, ±3분 국소 fit은 0.4 ms 이내였다.

"Best case, they share a clock or I can wire a sync pulse into a timer capture on both sides. If not, I use a physical event both sensors feel — a tap on the device — and cross-correlate the audio envelope with the accelerometer's high-passed magnitude, with parabolic peak interpolation; in my simulation that recovered a 137-millisecond offset to within about half a millisecond with a 100-hertz accelerometer. I put taps at the start and end at irregular spacing so I can solve for both offset and drift without lag ambiguity, and for long recordings I fit a piecewise or sliding-window line to periodic offset measurements, because the drift itself changes with temperature."

Q. "How do you detect dropped samples?"

A. 센서 ISR에서 붙이는 seq 카운터가 1순위, 센서의 FIFO overflow 플래그가 2순위, timestamp gap이 3순위(seq 없는 경우). seq는 wrap 처리를 하고, 정렬·중복 제거를 먼저 한 뒤 누락을 센다 — 순서 뒤바뀜이 가짜 gap으로 보이기 때문이다. 결과는 세션 리포트에 드롭률·최대 gap·보간 개수로 남기고, 정책(짧으면 보간 + mask, 길면 세그먼트 분리)을 코드로 고정한다.

"A sequence counter attached at the point where samples first enter firmware, ideally the sensor ISR, so every downstream loss is visible. I handle counter wrap, sort and de-duplicate by sequence first — otherwise a reordered packet looks like two gaps — and then count missing runs. The sensor's FIFO overflow flag tells me why, and for streams without a counter I fall back to timestamp gaps after correcting the rate. Short gaps get interpolated and masked, long ones split the recording, and the drop rate, longest gap and number of interpolated samples go into every session's QA report."

Q. "When resampling sensor data, do you interpolate or not?"

A. rate 변환과 구멍 메우기를 구분한다. rate 변환은 신호 대역에 따라 linear(대역이 rate의 1/5 이하) 또는 polyphase. 구멍은 짧고 저주파일 때만 보간하고 mask를 남기며, 오디오나 이벤트성 신호, 긴 구멍은 보간하지 않는다. 줄이는 방향은 항상 anti-aliasing 먼저. 그리고 학습과 기기에서 같은 방법.

"I separate rate conversion from gap filling. For rate conversion, linear interpolation is fine when the signal bandwidth is well below Nyquist — in a quick test it was under half a percent error at 2 hertz on a 100-hertz stream but almost 50 percent at 40 hertz — so for wideband signals I use a polyphase resampler. For gaps, I only interpolate short ones on low-frequency signals and keep a mask; I never interpolate audio or long gaps. Downsampling always gets an anti-aliasing filter first. And whatever I do in the training pipeline has to match what the device does at inference."

Q. "Two devices stream audio to each other and the buffer slowly overflows after about 20 minutes. Why, and what do you do?"

A. 두 기기의 크리스털이 다르기 때문이다. 100 ppm이면 16 kHz에서 초당 1.6샘플, 100 ms 여유는 약 17분에 소진된다. 버퍼를 키우는 건 시간을 미루고 지연만 늘린다. 버퍼 fill을 오차로 하는 PI 루프로 ASRC 비율을 조정하거나, 시계를 공유하거나, USB async처럼 피드백으로 송신 rate를 맞춘다.

"It's clock-rate mismatch: a 100-ppm difference at 16 kilohertz is 1.6 samples per second, which eats a 100-millisecond margin in about 17 minutes. A bigger buffer only delays it and adds latency. I'd run an asynchronous sample-rate converter whose ratio is driven by a PI loop on the filtered buffer fill — essentially a PLL where the buffer level is the phase error — or share a clock or use a feedback scheme like USB asynchronous audio. In simulation the PI loop held the fill within half a DMA block and its average ratio converged to exactly the 100-ppm offset."

13. 요약 & 체크리스트#

센서 데이터는 (값, 시각) 쌍이고, 시각이 틀리면 라벨과 특징이 조용히 틀린다 — 예제 1에서 라벨 100 ms 밀림만으로 제스처 recall이 97% → 70%가 됐다. 시계는 offset·rate(ppm)·jitter로 모델링하고, IMU 내부 발진기는 % 단위로 틀릴 수 있다는 전제로 설계한다. FIFO batch는 IRQ 시각 + 회귀로 추정한 실제 주기로 역산하고(아래 포락선, 64-bit 시각), seq 카운터로 드롭·중복·역순을 정렬 후 검출해 정책을 코드로 고정한다. 칩 사이는 공통 시계 > sync pulse > 물리 이벤트 cross-correlation > 메시지 순으로 맞추고, 긴 녹음은 국소 직선으로 drift 변화를 따라간다. 학습용 고정 rate는 대역에 맞는 resampling(linear 또는 polyphase), 줄일 땐 anti-aliasing, pandas는 method="time", 라벨 경계는 ignore. 실시간 스트림의 rate mismatch는 버퍼 fill PI 제어 + ASRC로 잡는다. 그리고 이 모든 것을 세션마다 time QA report로 숫자로 보증한다.
