0. 큰 그림 — 이게 왜 필요한가#

Don이 SSD 펌웨어에서 하던 회귀 테스트를 떠올려 보자. 커밋이 들어오면 빌드하고, unit test를 돌리고, 밤에 랙에서 NVMe 회귀 스위트와 성능 테스트(IOPS, latency QoS)를 돌린다. 결과는 대부분 결정적이다. 같은 펌웨어, 같은 명령이면 같은 completion이 나온다. 성능 숫자만 흔들리고, 그건 몇 번 재서 평균을 냈다.

ML 모델이 제품에 들어오면 CI가 지켜야 할 것이 늘어난다.

  • 산출물이 코드가 아니다. .tflite, .onnx, QNN context binary, 양자화 encoding 파일. 소스 한 줄 안 바뀌어도 재학습·재양자화로 바이너리가 통째로 바뀐다.
  • 입력에 데이터가 있다. 학습 데이터 버전, calibration 데이터, 테스트 세트 버전이 바뀌면 결과가 바뀐다. 코드 diff에는 안 보인다.
  • 지표가 확률적이다. "정확도 91.8% → 91.5%"는 회귀인가 우연인가? 펌웨어의 PASS/FAIL처럼 딱 떨어지지 않는다.
  • 지연·메모리·전력은 하드웨어에 묶인다. 노트북에서 2 ms인 모델이 NPU에서는 CPU fallback 때문에 20 ms일 수 있다. 실기기가 있어야 진짜 숫자가 나온다.

그래서 ML CI는 "테스트를 돌린다"보다 "모델 후보가 릴리스 자격이 있는지 단계마다 증거를 쌓는다"에 가깝다.

그림 1 — ML CI 파이프라인. 커밋 하나가 unit → golden → 정확도 → 실기기 측정 → 게이트 → 릴리스를 거친다. 왼쪽은 Don의 펌웨어 CI와 거의 같고, 오른쪽으로 갈수록 "통계로 판정"과 "실기기 필요"가 늘어난다. 아래 점선 상자가 ML CI를 펌웨어 CI와 다르게 만드는 부분이다.

0.2 이 노트의 공용 예제 — 작은 제스처 모델#

예를 들어 Hark 같은 웨어러블이라면 손목 IMU로 제스처를 분류하는 작은 모델이 있을 것이다(추정). 여기서는 6개 IMU 특징 → 16 hidden → 4 클래스의 MLP와, 같은 모델의 int8 레퍼런스 구현(numpy)을 공용으로 쓴다. 양자화는 C1의 대칭 int8, per-tensor 또는 per-channel이다.

실험 코드는 모두 스크래치 폴더에서 .venv/bin/python으로 돌렸다. 모델은 학습하지 않은 무작위 초기화다. 숫자 자체보다 테스트가 무엇을 잡고 무엇을 놓치는지를 보는 것이 목적이다.

1. ML CI가 코드 CI와 다른 네 가지#

1.1 직관 — "같은 입력이면 같은 출력"이 깨지는 곳#

펌웨어 CI의 암묵적 전제는 결정성이다. 같은 소스 → 같은 바이너리 → 같은 동작. ML에서는 이 사슬의 고리마다 변수가 붙는다: 학습에는 데이터 버전과 seed, 양자화에는 calibration 데이터와 설정, 컴파일에는 벤더 컴파일러 버전, 실행에는 기기·OS·온도, 평가에는 테스트 세트 버전.

2. pytest로 ML을 테스트한다#

2.1 tolerance의 정의 — assert_allclose는 무엇을 비교하나#

float 출력을 비교할 때 가장 많이 쓰는 함수가 np.testing.assert_allclose(actual, desired, rtol, atol)이다. 원소마다 이 식을 검사한다.

말로 하면, 허용 오차 = 고정 바닥(atol) + 기대값 크기에 비례하는 부분(rtol)이다. rtol만 쓰면 기대값이 0 근처일 때 허용치가 0이 되어 아주 작은 차이에도 실패한다. atol만 쓰면 큰 값에서 너무 엄격하거나 작은 값에서 너무 느슨하다. 그래서 둘을 함께 쓴다.

손계산을 먼저 해 보자. desired = [1.000, 0.010, −2.000, 0.0], actual = [1.001, 0.012, −2.003, 0.000003].

원소차이rtol=1e-3, atol=0 허용치rtol=1e-3, atol=1e-5 허용치판정 (둘째 설정)
1.0000.0010.0010.00101통과
0.0100.0020.000010.00002실패
−2.0000.0030.0020.00201실패
0.00.00000300.00001통과

넷째 원소가 핵심이다. atol이 0이면 기대값 0에 대해 3e-6 차이로도 실패한다.

무엇을 확인하는 코드인가: 위 손계산과 assert_allclose의 실패 메시지, 그리고 int8 비교는 tolerance가 아니라 정확히 같아야 한다는 점.

출력에서 볼 것: 같은 데이터가 tolerance 설정에 따라 0개, 2개, 3개 실패로 바뀐다. tolerance가 곧 테스트의 정의이므로, 코드 안에 숫자를 흩뿌리지 말고 이유와 함께 한 곳(설정 파일이나 상수)에 둔다. int8 쪽은 1 LSB 차이도 실패로 잡는다. C8 3절의 결론 그대로다: 정수 커널은 규격이 같으면 bit-exact가 가능하므로 exact로 검사한다.

tolerance를 정하는 실무 규칙:

  • 같은 런타임, 같은 하드웨어, 같은 스레드 수: 이론상 bit-exact. 그래도 float이면 rtol=1e-6 정도로 시작.
  • torch vs ONNX Runtime (CPU): 합산 순서·커널이 달라서 1e-7~1e-6 수준 차이. rtol=1e-5, atol=1e-6 출발점.
  • float vs int8: allclose가 아니라 C8의 SQNR·top-1 agreement로 본다. allclose로 하면 tolerance가 너무 커서 의미가 없다.
  • NPU fp16: rtol=1e-2 근처. 이것도 대개는 과제 지표로 보는 편이 낫다.

2.2 golden 테스트 — fixture와 parametrize#

golden 파일은 릴리스 시점에 한 번 기준 모델로 만들고, CI는 읽기만 한다. Don에게 익숙한 말로 하면 "검증된 펌웨어로 뽑아 둔 expected 로그"다.

fixture는 테스트가 쓰는 준비물을 만들어 주는 함수다. scope="session"이면 테스트 실행 전체에서 한 번만 만든다. 모델 로드처럼 비싼 일에 쓴다. 테스트 함수의 인자 이름이 fixture 이름과 같으면 pytest가 자동으로 넣어 준다. conftest.py에 두면 같은 폴더의 모든 테스트 파일이 쓸 수 있다.

O3_MODEL 환경 변수로 테스트 대상 모델을 바꿀 수 있게 했다. CI에서는 "후보 모델 경로"를 이렇게 넘긴다.

parametrize는 같은 테스트를 여러 설정으로 돌리는 장치다. 양자화 설정(per-channel, per-tensor), 입력 shape, 런타임 종류처럼 축이 여러 개인 ML 테스트에 딱 맞는다. ids를 주면 결과에 사람이 읽을 수 있는 이름이 붙는다.

무엇을 확인하는 코드인가: float은 tolerance, int8은 bit-exact, 그리고 과제 수준 지표(top-1 agreement)를 세 층으로 검사하는 테스트 파일.

실행: .venv/bin/python -m pytest test_golden.py -v -p no:cacheprovider

(위 출력은 -v 결과 중 테스트 줄과 요약 줄만 남긴 것이다.) agreement 값을 -s로 보면 per-channel 0.9775, per-tensor 0.9765였다.

이제 "재export했더니 가중치가 1e-3 정도 흔들린" 후보 모델(model_v1b.pt, 모든 파라미터에 표준편차 1e-3 잡음)을 넣어 본다.

실행: O3_MODEL=model_v1b.pt .venv/bin/python -m pytest test_golden.py -p no:cacheprovider -q --tb=line -rfE

출력에서 볼 것: golden 두 층은 실패하고(64행 중 49·50행이 다름), 과제 수준인 top-1 agreement는 통과한다. 이게 층을 나눠 두는 이유다. golden 실패는 "무언가 바뀌었다"는 신호이고, agreement 통과는 "그래도 과제에는 영향이 작다"는 신호다. 의도한 변경(재학습)이라면 golden을 리뷰를 거쳐 다시 굽고, 의도하지 않은 변경(리팩터링)이라면 버그다. golden을 자동으로 덮어쓰는 스크립트를 CI에 두면 이 구분이 사라진다.

2.3 op parity — 런타임끼리 같은 답을 내는가#

모델 전체가 틀렸을 때 원인을 찾는 것은 어렵다(C8 4절의 레이어별 diff). 그 전에 op 하나씩 기준 런타임과 배포 런타임을 비교해 두면, 런타임 버전을 올릴 때 어느 op가 바뀌었는지 바로 보인다. Don의 말로 하면 "명령 하나하나의 conformance 테스트"다.

무엇을 확인하는 코드인가: op마다 작은 모듈을 ONNX로 내보내 torch와 onnxruntime 결과를 op별 tolerance로 비교한다.

출력에서 볼 것: 줄 앞의 .은 바로 앞 테스트의 PASS 표시다(-s로 print가 섞여 나옴). 모든 op가 1e-6 아래로 일치한다. conv1d는 이 입력에서 정확히 0이었지만, 그건 우연이지 보장이 아니다. 이 표를 런타임 버전마다 저장해 두면, onnxruntime을 올렸더니 layernorm만 1e-4로 뛰었다 같은 변화가 바로 보인다.

같은 틀을 세 번째 열로 넓히면 C 레퍼런스 커널(8절)이나 벤더 런타임(F4의 QNN)도 같은 표에 들어간다. 원칙은 하나다: 기준 하나(보통 torch float 또는 numpy 레퍼런스)를 정하고, 나머지는 모두 그것과 비교한다. 런타임끼리 서로 비교하면 어느 쪽이 틀렸는지 모른다.

2.4 성질(property) 테스트 — 정답 없이 검사하기#

golden은 "이 입력에서 이 출력"만 지킨다. 성질 테스트는 어떤 입력에서도 성립해야 하는 규칙을 무작위 입력 여러 개로 검사한다(J6 2절은 C 코드 쪽, 여기는 모델 쪽). ML 모델에 쓸 만한 성질:

성질무엇을 잡나
batch invariance: 배치로 돌린 결과 = 한 개씩 돌린 결과배치 전체로 scale을 잡는 dynamic quant, 배치 축이 섞이는 reshape 버그, BatchNorm을 train 모드로 둔 실수
범위: int8 출력은 [−128, 127], softmax 합은 1saturation 누락, dtype 실수
결정성: 같은 입력 두 번 → 같은 바이트초기화 안 된 버퍼, 스레드 순서 의존
대칭·불변성: 시간축 이동이나 채널 순서에 대한 기대 동작전처리 윈도 경계 버그
단조성: 확신이 큰 입력에서 확률이 커짐 (해당될 때만)부호 실수

무엇을 확인하는 코드인가: batch invariance 성질이 "배치 max로 입력 scale을 잡는" 흔한 버그를 20개 seed 모두에서 잡는지.

hypothesis 같은 라이브러리를 쓰면 반례를 자동으로 줄여(shrinking) 주지만, 이 정도 성질은 seed parametrize로 충분하다. seed를 고정해야 실패가 재현된다.

3. 정확도 게이트 — "0.3%p 떨어졌다"를 판정하는 법#

3.1 왜 단순 문턱은 위험한가 — 손계산#

가장 흔한 게이트는 "정확도가 0.5%p 넘게 떨어지면 FAIL"이다. 테스트 세트가 n = 2000개이고 정확도가 92% 근처라면, 정확도 하나의 표준오차는

말로 하면, 같은 모델이라도 테스트 세트를 새로 뽑으면 정확도가 ±0.6%p쯤 흔들린다. 그런데 CI의 테스트 세트는 고정이다. 그러면 흔들림이 없지 않나? 아니다. 두 모델 비교에서 흔들리는 것은 어느 샘플에서 두 모델이 엇갈리느냐다. 재학습이나 재양자화는 일부 샘플의 정답 여부를 바꾼다(churn). 같은 실력의 후보라도 이 엇갈림 때문에 관측 drop이 0 근처에서 흔들린다.

엇갈림을 숫자로 보자. 두 모델의 샘플별 정답 여부를 짝지으면 네 칸이 된다.

후보 맞음후보 틀림
기준 맞음a (둘 다 맞음)b (새로 틀림)
기준 틀림c (새로 맞음)d (둘 다 틀림)

drop = (b − c) / n이다. a와 d는 차이에 대해 아무 정보가 없다. b + c(엇갈린 샘플 수)가 클수록 drop이 잘 흔들린다. churn이 3%(b + c ≈ 60개)이고 진짜 차이가 0이면, b는 대략 Binomial(60, 0.5)이라서 b − c의 표준편차는 √60 ≈ 7.7개 = 0.39%p다. 그러면 "관측 drop > 0.5%p"는 대략 z = 0.5/0.39 ≈ 1.3, 즉 약 10%의 확률로 무고한 후보를 막는다. 하루 PR 10개면 매일 한 번 거짓 경보다.

3.2 McNemar 검정 — 엇갈린 샘플만 본다#

McNemar 검정은 위 표의 b와 c만 쓴다. "차이가 없다"면 엇갈린 샘플 하나가 b쪽일 확률이 1/2이므로, b는 Binomial(b + c, 1/2)을 따라야 한다. 관측된 b가 그보다 지나치게 크면 "후보가 정말 나빠졌다"고 본다(L1 4.2절에서 SLM 비교에 같은 검정을 썼다).

손계산: b = 14, c = 0이면 엇갈린 14개가 전부 한쪽이다. 차이가 없을 때 이럴 확률은 (1/2)¹⁴ = 1/16384 ≈ 0.00006이다. 같은 drop(0.7%p)이라도 b = 73, c = 59라면 132개 중 73개가 한쪽인 정도는 동전 던지기로 흔히 나온다.

무엇을 확인하는 코드인가: McNemar exact p 값과 paired 차이의 신뢰구간, 그리고 같은 drop이라도 churn에 따라 증거의 세기가 달라진다는 점.

출력에서 볼 것: 세 경우 모두 drop은 0.70%p로 같지만 p 값은 0.0001, 0.01, 0.13으로 천 배 넘게 다르다. 정확도 숫자 두 개만 저장하면 이 판정을 할 수 없다. 샘플별 정답 여부(또는 예측)를 저장해야 한다(C8 6.1절과 같은 결론). 신뢰구간 계산은 C8 6.2절의 paired bootstrap으로 해도 되고, 여기처럼 정규근사 식으로 해도 n이 크면 거의 같다.

3.3 게이트 세 가지의 오판률 — 시뮬레이션#

게이트는 결국 두 가지 실수를 한다. Don의 factory test 용어로 하면 과검(false alarm, 좋은 걸 불량 판정)과 미검(miss, 불량을 통과)이다. 세 게이트를 비교한다.

  • G1 단순 문턱: 관측 drop > 0.5%p 이면 FAIL.
  • G2 유의성: McNemar 단측 p < 0.05 이면 FAIL. "나빠졌다는 증거가 있으면 막는다."
  • G3 비열등(non-inferiority): drop의 95% 상한 > 1.0%p 이면 FAIL. "1%p보다 덜 나빠졌다는 증거가 없으면 막는다." 증명 책임이 후보에게 있다.

무엇을 확인하는 코드인가: 진짜 drop(0~2%p)마다 각 게이트가 FAIL을 낼 확률을, n = 2000과 n = 8000에서 2만 번씩 시뮬레이션한다.

그림 2 — 게이트의 동작 곡선(operating characteristic). 실험 ex7의 숫자를 그대로 찍었다. 초록(G3, n=8000)이 계단에 가장 가깝다. 빨강 점선(G2, n=8000)은 1%p 왼쪽에서 일찍 올라가서, 제품상 문제없는 0.5%p drop도 81% 확률로 막는다.

출력에서 볼 것, 세 가지:

  1. G1(단순 문턱)은 n과 상관없이 문턱 근처에서 동전 던지기다. 진짜 drop 0.5%p에서 FAIL 확률이 n=2000·8000 모두 약 0.48이다. 그리고 n=2000이면 무고한 후보를 8.8% 막는다.
  2. G2(유의성)는 n이 커질수록 "의미 없이 작은" 차이까지 막는다. n=8000에서 0.25%p drop을 34% 막는다. 유의성(statistical significance)은 "차이가 있다"이지 "차이가 크다"가 아니다. 테스트 세트를 늘릴수록 게이트가 점점 까다로워지는 이상한 게이트다.
  3. G3(비열등)는 n이 작으면 과검이 크고(17%), n이 충분하면 거의 이상적이다(0.0%와 94.7%). 증명 책임을 후보에게 두면, 증명할 데이터가 충분해야 공정하다.

그래서 실무 규칙은 이렇다.

  • "얼마까지 나빠져도 되는가"(허용 한계, margin)를 제품 기준으로 먼저 정한다. 예: 제스처 top-1은 1%p, wake word FA/h는 기준 대비 +10%. 결과를 보고 정하면 안 된다(C8 6.1절).
  • G3 형태(신뢰구간 상한 vs margin)로 판정하고, n은 G3의 과검이 작아질 만큼 키운다. 위 시뮬레이션처럼 "진짜 차이 0일 때 FAIL 확률"을 목표(예: 1% 이하)로 잡고 n을 역산한다.
  • 데이터를 더 모을 수 없으면 3단 판정: 상한 < margin → PASS, 하한 > margin → FAIL, 그 사이 → "판정 보류, 사람 리뷰". 보류를 정식 결과로 인정하는 것이 거짓 FAIL을 남발하는 것보다 낫다.
  • 여러 지표(전체, 클래스별 4개, 사용자 그룹별)를 동시에 게이트하면 과검이 쌓인다. 지표가 10개고 각각 과검 5%면, 하나라도 FAIL일 확률은 1 − 0.95¹⁰ ≈ 40%다. 주 지표만 엄격하게 게이트하고 나머지는 경고로 두거나, 지표별 유의수준을 나눈다(Bonferroni: 0.05/10).

4. 지연 게이트 — 잡음 낀 측정에서 3% 회귀 찾기#

4.1 지연 측정 잡음의 구조#

K2·M2에서 측정 잡음을 다뤘다. CI 게이트 관점에서 중요한 것은 잡음이 층으로 쌓인다는 점이다.

Don에게 익숙한 비유: SSD의 latency QoS 측정에서 같은 드라이브라도 precondition 상태와 온도가 달라지면 분포 전체가 옮겨 간다. 한 번의 측정 세션 안에서 1000번 잰 숫자는 서로 독립이 아니다. 같은 세션 효과를 공유한다.

robust 통계 두 가지를 기억해 둔다(H7 5절에서 정의).

  • median: outlier 몇 개에 흔들리지 않는 중앙값.
  • MAD(median absolute deviation): median으로부터 거리들의 median. 표준편차 대신 쓴다. 정규분포에서 σ ≈ 1.4826 × MAD.

4.2 게이트 네 가지 — 시뮬레이션#

진짜 지연 20 ms, 세션 효과 1.5%, 반복 잡음 3%, warmup 3회(1.5배), outlier 5%(1.3배)인 기기를 흉내 낸다. 네 게이트:

  • L1: 기준·후보 세션 1번씩, 평균 비교, +3% 넘으면 FAIL.
  • L2: 세션 1번씩, warmup 5회 버리고, 반복 25개를 표본으로 Mann–Whitney U 단측 p < 0.01.
  • L3: 기준·후보 세션 5번씩 교대, 세션별 median의 median 비교, +3% 넘으면 FAIL.
  • L4: L3의 세션 median 5개끼리 Mann–Whitney U 단측 p < 0.05 그리고 median 비 +2% 초과.

Mann–Whitney U 검정은 "한 그룹 값이 다른 그룹 값보다 큰 경향이 있는가"를 순위만으로 검사한다. 정규분포 가정이 없어서 꼬리가 긴 지연 분포에 잘 맞는다.

무엇을 확인하는 코드인가: 진짜 느려짐 0~8%에서 네 게이트의 FAIL 확률.

그림 3 — 지연 게이트 네 가지의 과검(빨강)과 5% 회귀 검출률(파랑). ex8의 숫자 그대로다. 세션을 여러 번 나눠 잰 L3·L4가 과검과 검출 둘 다에서 낫다.

출력에서 볼 것:

  1. L2가 함정이다. p < 0.01이라는 엄격한 기준인데도 진짜 차이 0에서 15.8%가 FAIL이다. 검정은 "반복 25개가 서로 독립"이라고 가정하는데, 실제로는 세션 효과(1.5%)를 공유한다. 그래서 세션 효과 차이를 "진짜 차이"로 착각한다. 반복을 1000번으로 늘리면 더 나빠진다. p 값이 작아질 뿐 세션 효과는 그대로이기 때문이다.
  2. 반복을 늘리는 것보다 세션을 늘리는 것이 효과적이다. L3는 같은 3% 문턱인데 과검이 13% → 0.9%로 떨어졌다. 독립인 단위(세션)를 표본으로 써야 통계가 맞다. Don의 말로 하면 "한 드라이브를 1000번 재지 말고, 다시 붙이고 다시 precondition해서 5번 재라"다.
  3. L4는 "유의하면서 + 크기도 의미 있을 때만" FAIL이라서 과검 1.5%, 5% 검출 97.7%로 가장 균형이 좋다. 3.3절 G2의 함정(작은 차이에 과민)을 크기 조건으로 막은 형태다.

4.3 측정 순서 — 열 drift를 교대로 상쇄한다#

기기는 측정할수록 데워진다(K4). 기준 5세션을 먼저 다 재고 후보 5세션을 나중에 재면, 후보가 더운 상태에서 측정되어 억울하게 느리게 나온다.

무엇을 확인하는 코드인가: 진짜 차이가 0인 A/A 비교에서, 세션마다 6%까지 올라가는 열 drift가 있을 때 측정 순서별 겉보기 차이.

출력에서 볼 것: 같은 모델끼리인데 순차 측정은 평균 +3.3% "회귀"를 만들고, 3% 게이트를 61% 확률로 거짓 FAIL시킨다. 교대(ABAB)는 +0.6%, ABBA 순서는 +0.2%까지 줄인다. ABBA는 A와 B의 평균 위치가 거의 같아서 선형 drift가 상쇄된다. 손으로: ABAB에서 A의 위치는 0,2,4,6,8(평균 4), B는 1,3,5,7,9(평균 5)라서 B가 한 칸만큼(6%/9 ≈ 0.67%) 불리하다. 출력의 +0.63%와 맞는다.

실무 규칙:

  • 기준 모델을 매번 같이 잰다. 지난주에 잰 기준 숫자와 오늘 후보 숫자를 비교하지 않는다. 기기 펌웨어·OS 업데이트·온도가 다르다. 같은 기기, 같은 날, 교대로.
  • 세션 사이에 냉각 대기(예: 기기 온도 센서 값이 시작값 근처로 돌아올 때까지)를 넣거나, 반대로 일정 부하로 열 평형에 도달한 뒤 잰다. 무엇을 택하든 기준과 후보에 같게 한다(K4).
  • A/A 테스트를 정기적으로 돌린다. 같은 모델을 A와 B 양쪽에 넣고 게이트를 돌리면 과검률이 직접 나온다. 과검률이 설계값(예: 1%)보다 크면 측정 프로토콜에 문제가 있다(I5 7.2절의 잡음 바닥 측정과 같은 생각).

5. 예산을 코드로 — budgets YAML, 추세, bisect#

5.1 budgets.yaml — 숫자 계약서#

NPI에서 Don이 margin sign-off를 할 때 기준표가 있었다. ML 모델도 같다. 모델마다 크기·peak RAM·지연·전력 예산을 파일로 적고 git에 넣는다. 바꾸려면 리뷰가 필요하다(J6 5.5절의 CODEOWNERS 규칙). I6에서 본 flash·RAM·MAC 예산표의 모델 저장소 판이다.

전력 예산을 지연에서 끌어내는 손계산부터. 제스처 모델이 100 ms마다 돈다면 하루 실행 횟수는 86,400 s / 0.1 s = 864,000회다. 한 번에 2.05 ms 동안 idle 대비 12 mA를 더 쓴다면

말로 하면, 지연이 1% 늘면 이 모델의 하루 전력도 1% 는다. 웨어러블 배터리가 수백 mAh라면 모델 하나가 몇 %를 쓰는지 바로 보인다(N1·D7). 아래 체커는 보수적으로 p90 지연을 썼다. 평균 전하를 정확히 보려면 mean 지연이 맞고, 더 정확히는 K3의 전류 적분 측정이 맞다.

무엇을 확인하는 코드인가: 측정값을 예산과 기준선 양쪽에 비교해 FAIL / WARN / PASS를 내고, CI가 읽을 종료 코드를 돌려준다. 측정값은 예시로 넣은 숫자다(실제로는 6절 farm 결과 JSON을 읽는다).

(마지막 줄은 셸에서 echo "exit code=$?"로 찍은 것이다.) 출력에서 볼 것: 결과가 PASS/FAIL 한 비트가 아니라 표다. wakeword의 peak RAM이 예산을 2.3% 넘어서 전체 FAIL이고, 기준선 대비 +9.2%라서 이번 변경이 원인임을 바로 알 수 있다. gesture의 크기는 예산 안이지만 기준선 대비 +4.1%라서 WARN이다. 손계산한 5.90 mAh/day가 그대로 나온다.

설계 포인트:

  • 예산 초과(절대)와 변화량(상대)을 따로 본다. 절대 예산만 보면 여유가 많은 동안 아무 경고 없이 조금씩 잠식된다(5.2절).
  • 크기·RAM처럼 결정적인 값은 문턱 하나로 충분하다. 지연·전력처럼 잡음 있는 값은 4절의 게이트를 거친 숫자를 여기에 넣는다.
  • 예산 파일 자체도 manifest(7절)에 해시로 들어가야 한다. 누가 로컬에서 숫자를 고쳐 통과시키는 것을 막는다.

5.2 추세와 creep — 직전 PR 대비 게이트의 맹점#

PR마다 "직전 대비 +3% 이내면 통과"로 게이트하면, 매번 1~2%씩 나빠지는 변경이 모두 통과한다. 이것을 creep(서서히 기어오름)이라고 한다. SSD 펌웨어에서도 "이번 PR은 IOPS 1% 손해, 괜찮다"가 열 번 쌓이면 릴리스 성능 목표를 놓친다.

무엇을 확인하는 코드인가: PR마다 진짜로 1.2%씩 느려질 때, 직전 PR 대비 게이트(3%)와 릴리스 기준선 대비 게이트(8%) 중 무엇이 잡는가.

그림 4 — creep 추세. 파란 선은 ex11의 측정값 16개. 회색 점선이 릴리스 기준선, 빨간 점선이 기준선 +8%. 직전 대비 게이트는 PR15에서야(그것도 잡음 덕분에) 처음 반응했다.

출력에서 볼 것: 직전 PR 대비 게이트는 15개 PR 동안 단 한 번, 그것도 마지막에야 울렸다. 릴리스 기준선 대비 게이트는 PR07(+9.2%)에서 잡았다. 규칙:

  • 비교 기준을 "직전"이 아니라 "마지막 릴리스(또는 고정 기준선)"로 둔다. 기준선은 릴리스 때만, 리뷰를 거쳐 옮긴다. 이것을 ratchet(톱니) 방식이라고 부르기도 한다. 좋아진 숫자는 기준선을 내리고, 나빠진 숫자는 기준선을 못 올린다.
  • 대시보드에는 PR별 숫자를 시계열로 그리고, 기준선과 예산선을 같이 그린다. 그림 4가 그대로 대시보드 한 칸이다. 도구는 무엇이든 된다(JSON 결과를 쌓아 두고 그리는 정적 페이지, 사내 Grafana 등).
  • 같은 그래프에 기기 ID·OS 빌드·툴체인 버전 변경 시점을 세로선으로 표시한다. 계단이 생긴 지점이 모델 변경이 아니라 farm 기기 교체일 때가 많다.

5.3 모델 버전 bisect — git bisect의 ML 판#

git bisect는 good 커밋과 bad 커밋 사이를 이분 탐색해서 첫 bad 커밋을 찾는다. 커밋 N개면 log₂N번 테스트로 끝난다. Don이 bring-up에서 펌웨어 버전을 반씩 잘라 가며 버그 도입 시점을 찾던 그 방법이다.

ML에서 두 가지가 다르다.

  1. 테스트가 잡음 있다. 한 번 잘못 판정하면 이분 탐색이 엉뚱한 반쪽으로 가고, 이후 단계는 전부 헛수고다. 단계가 log₂N개라면 각 단계가 모두 맞아야 한다.
  2. "버전"이 여러 축이다. 코드 커밋만 바뀐 게 아니라 데이터 버전, 양자화 설정, 컴파일러 버전이 함께 바뀌었을 수 있다.

무엇을 확인하는 코드인가: v0(good)~v16(bad) 사이에서 +6%를 만든 v11을 찾을 때, 단계마다 몇 세션을 재야 정답을 찾는가. v5에는 무해한 +1% 변화가 섞여 있다.

출력에서 볼 것: 16개 버전을 4단계로 좁혔다(log₂16 = 4). 하지만 단계마다 한 세션만 재면 정답을 찾을 확률이 39%밖에 안 된다. 9세션씩 재야 90%다. 기준 측정(ref)도 잡음이 있어서 모든 단계에 같은 오차가 실린다는 점도 원인이다. 개선책:

  • 단계마다 기준(v0)을 같이, 교대로 잰다(4.3절). 한 번 잰 ref를 재사용하지 않는다.
  • 결과가 문턱 근처(예: +2~4%)면 "판정 보류"로 측정을 더 한다. 확실한 단계는 빨리 넘긴다.
  • 마지막에 찾은 범인 앞뒤(v10, v11)를 많이 재서 확인한다. 이분 탐색 결과 자체를 검증하는 단계다.
  • 결정적인 지표(모델 크기, peak RAM 계산값, golden 해시)는 잡음이 없으므로 이런 문제가 없다. 결정적 지표로 먼저 bisect할 수 있으면 그렇게 한다.

  • 클라우드 farm의 열 상태·배경 부하는 우리가 통제하지 못한다. 그래서 기준 모델을 같은 job 묶음 안에서 교대로 제출한다(4.3절). 절대 숫자보다 같은 시점의 기준 대비 비율을 믿는다.
  • 외부 서비스는 큐 대기·장애가 있다. 커밋 차선을 여기에 걸면 개발자가 기다린다. 야간 차선에 두고, 서비스 장애는 FAIL이 아니라 ERROR(infra)로 분류한다(J6 4.5절의 failure/error 구분).
  • 모델 파일을 외부로 올리는 것이므로 보안·IP 정책 확인이 먼저다.

무엇을 확인하는 코드인가: 산출물 해시와 환경 버전을 manifest에 적고, CI가 테스트 전에 파일과 대조해서 몰래 바뀐 파일을 잡는지.

출력에서 볼 것: 주석 한 줄만 추가해도 해시가 바뀌어 잡힌다. 해시는 앞 16자리만 보여 주려고 잘랐다(실제로는 전체 64자리를 저장한다). 툴체인 버전이 manifest에 들어간 이유는 5.3절 표의 "컴파일러만 되돌림" 실험을 하려면 그 버전을 알아야 하기 때문이다.

manifest 운영 규칙:

  • CI의 첫 단계에서 manifest 검증을 한다. 불일치면 나머지 테스트를 돌리지 않는다(잘못된 물건을 측정하는 것은 낭비다).
  • 기기에 배포되는 바이너리 안에도 모델 해시를 넣고, 기기가 부팅 로그·텔레메트리로 보고하게 한다(J5·H1). 그래야 필드 문제를 manifest와 연결할 수 있다.
  • "다시 만들 수 있나"는 정기적으로 실제로 다시 만들어 본다. 6개월 전 manifest로 재학습·재양자화해서 golden 해시나 정확도가 재현되는지 본다(H5 7.3절 체크리스트). 학습은 GPU 비결정성 때문에 bit-exact 재현이 어려울 수 있으니, 재현 기준(정확도 ± 얼마)을 정해 둔다. 양자화·컴파일 단계는 같은 입력이면 bit-exact를 기대한다.

8.2 C golden-vector harness — 실패 수를 종료 코드로#

펌웨어 unit test처럼, int8 커널 출력을 기대 배열과 비교하고 실패 수를 종료 코드로 돌려주는 harness다. CI는 종료 코드만 보면 된다. 기대값은 float64 레퍼런스로 따로 계산했다.

손으로 첫 행을 확인하면: acc₀ = 10·12 + (−20)·(−7) + 30·33 + (−40)·5 + 100 = 120 + 140 + 990 − 200 + 100 = 1150. 1150 × 0.0123 = 14.145 → 14. 둘째 출력은 −4920 × 0.0123 = −60.516 → −61. 32679 × 0.0123 = 401.95라서 127로 saturation된다.

C 쪽 requant는 scale 0.0123을 Q31 multiplier + shift로 표현한다. 0.0123 = 0.7872 × 2⁻⁶이고, 0.7872 × 2³¹ ≈ 1,690,499,128이다(C1·J3의 requantization 형식).

(두 빌드 모두 경고 0개.) 출력에서 볼 것:

  • 정상 커널은 float64 레퍼런스와 bit-exact다. Q31 근사가 이 벡터들에서는 반올림 경계를 넘지 않았다. 경계 근처 값(x.5 근처)을 일부러 넣은 벡터를 추가하면 Q31 근사와 float 레퍼런스가 갈릴 수 있으므로, 기대값은 배포 규격과 같은 정수 연산으로 만드는 것이 원칙이다(C8 3.4절).
  • 반올림을 빼먹은 버그는 음수 출력에서만 틀린다. 크기를 버리면 음수는 0 쪽으로 가서 항상 +1 쪽으로 틀린다. 양수 14.145 → 14처럼 우연히 맞는 값도 많다. golden 벡터에 음수와 경계값을 일부러 넣어야 하는 이유다.
  • tol=1로 돌리면 같은 버그가 PASS다. 그런데 4개 오차가 모두 +1이다. 무작위 ±1이 아니라 한쪽으로 치우친 오차는 버그의 지문이다. 1 LSB tolerance를 허용하더라도 오차의 평균(bias)이 0 근처인지를 함께 검사해야 한다. 치우친 1 LSB는 레이어를 거치며 누적된다.

이 harness는 host에서는 CI 커밋 차선에서, 타깃에서는 같은 소스를 cross 빌드해 HIL 차선에서 돈다(J6 0.4절의 "한 소스, 여러 빌드").

10. 면접에서 이렇게 말한다#

Q. "How would you set up CI for an on-device ML model?"

A. 싸고 결정적인 것을 앞에, 비싸고 확률적인 것을 뒤에 둔다. 커밋마다 host에서 전처리 unit test, op parity, golden(float은 tolerance, int8은 bit-exact), 성질 테스트, 크기·RAM 예산을 돈다. 모델이 바뀌면 고정 test set 정확도를 비열등 판정으로, 야간에는 실기기 farm에서 기준 모델과 교대로 지연·메모리를 잰다. 릴리스에는 전력·열과 사람 리뷰. 모든 입력은 manifest 해시로 고정한다.

I split it by cost and determinism. Every PR runs host-side tests: preprocessing unit tests, op-level parity against a reference, golden tests — tolerance for float, bit-exact for int8 — property tests like batch invariance, and size/RAM budgets from the build. Model changes trigger a fixed-test-set accuracy check with a non-inferiority gate. Nightly, we measure latency and memory on real devices, interleaving the baseline and the candidate on the same pinned device. Power, thermal and a human sign-off happen at release. Every artifact is pinned by a hashed manifest.

Q. "Accuracy dropped by 0.4 points on the regression set. Do you block the release?"

A. 숫자만으로는 모른다. 샘플별로 짝지어 엇갈린 샘플 b와 c를 보고 McNemar나 paired CI를 낸다. 판정 기준은 미리 정한 허용 한계(예: 1%p) 대비 신뢰구간 상한이다. 상한이 한계 안이면 통과, 하한이 한계 밖이면 차단, 걸치면 데이터를 늘리거나 리뷰. 클래스·사용자별 breakdown도 본다.

It depends on the evidence, not the point estimate. I'd look at the paired predictions — how many samples flipped each way — and compute a McNemar test or a paired confidence interval. Our gate is defined against a pre-agreed margin, say one point: if the upper bound of the drop is inside the margin we ship, if the lower bound is outside we block, and if the interval straddles it we either add data or escalate for review. I'd also check per-class and per-user breakdowns, because an average can hide one class collapsing.

Q. "Your latency regression tests are flaky. How do you fix them?"

A. 먼저 A/A 테스트로 과검률을 잰다. 흔한 원인은 한 세션 안의 반복을 독립 표본으로 쓰는 것, 열 drift, 기기 간 차이다. 세션을 여러 번 나눠 교대로 재고, 같은 물리 기기에 pinning하고, warmup을 버리고, median과 세션 단위 검정에 최소 효과 크기 조건을 붙인다. 재시도로 통과시키는 것은 미검을 늘리므로 infra error에만 쓴다.

First I measure the false-alarm rate directly with A/A runs. The usual culprits are treating iterations within one session as independent samples, thermal drift, and unit-to-unit variation. So we measure several independent sessions, interleave baseline and candidate on the same pinned device, discard warmup, and gate on session medians with a rank test plus a minimum effect size. Retrying until it passes just trades false alarms for misses, so retries are only for infrastructure errors.

Q. "How would you use something like Qualcomm AI Hub in your pipeline?"

A. 칩이 책상에 없거나 여러 Snapdragon 기종을 비교할 때 야간 차선에 둔다. 후보를 compile하고 profile job을 세션 여러 번으로 나눠 제출해서 지연·peak memory·compute unit(NPU fallback 여부)을 받는다. 기준 모델을 같은 묶음에서 같이 제출하고 비율로 판정한다. 우리 보드의 센서 경로나 전력은 못 재므로 그건 사내 랙에서 한다. 서비스 장애는 FAIL이 아니라 infra error로 분류한다.

I'd put it in the nightly lane, for targets we don't have on our bench or to compare Snapdragon tiers. The job compiles the candidate, submits several profile sessions, and pulls back latency, peak memory and which compute unit each op landed on, so we catch CPU fallbacks. The baseline goes in the same batch and we gate on the ratio, not the absolute number. It can't see our sensor path or measure battery current, so those stay on our in-house rack, and a hosted-service outage is classified as an infra error rather than a test failure.

Q. "Latency crept up 20% over a quarter and nobody noticed. What went wrong and how would you find the cause?"

A. 직전 PR 대비로만 게이트해서 creep를 놓쳤다. 릴리스 기준선 대비 비교와 추세 대시보드로 고친다. 원인 찾기는 버전 bisect인데, 측정이 잡음 있으니 단계마다 기준과 교대로 여러 세션을 재고, 문턱 근처는 판정을 보류해서 더 잰다. 축이 여러 개면 컴파일러·양자화·데이터를 하나씩 되돌리는 실험표를 만든다. 이게 가능하려면 manifest가 있어야 한다.

The gate compared each PR to the previous one, so small regressions accumulated. The fix is to compare against the last release baseline and plot the trend with budget lines. To find the cause I'd bisect across model versions, but with noisy measurements each step needs several interleaved sessions against the baseline, and borderline results get re-measured instead of decided. If multiple axes changed — compiler, quantization config, data — I'd revert one axis at a time, which only works if each build has a manifest pinning those versions.

13. 요약 & 체크리스트#

ML CI는 펌웨어 CI의 뼈대(커밋·야간·릴리스 차선, golden, 랙)를 그대로 쓰되, 네 가지를 더한다. 모델·데이터·툴체인을 해시로 고정하는 manifest, 결정적인 것(int8 커널, 크기·RAM 계산)과 확률적인 것(정확도, 지연, 전력)의 분리, 확률적인 것을 판정하는 통계 게이트(허용 한계 대비 신뢰구간 상한, 세션 단위 교대 측정), 그리고 실기기 farm(클라우드 AI Hub·폰 farm, 사내 랙)과 그 측정 프로토콜이다. 게이트는 과검과 미검을 둘 다 내므로, 시뮬레이션이나 A/A 테스트로 두 오류율을 숫자로 알고 설계해야 한다. 비교 기준은 직전 PR이 아니라 릴리스 기준선이고, 회귀가 나면 축별로 되돌리며 bisect한다.
