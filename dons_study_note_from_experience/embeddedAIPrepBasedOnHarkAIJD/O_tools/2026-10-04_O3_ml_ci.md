## 0. 큰 그림 — 이게 왜 필요한가

Don이 SSD 펌웨어에서 하던 회귀 테스트를 떠올려 보자. 커밋이 들어오면 빌드하고, unit test를 돌리고, 밤에 랙에서 NVMe 회귀 스위트와 성능 테스트(IOPS, latency QoS)를 돌린다. 결과는 대부분 **결정적**이다. 같은 펌웨어, 같은 명령이면 같은 completion이 나온다. 성능 숫자만 흔들리고, 그건 몇 번 재서 평균을 냈다.

ML 모델이 제품에 들어오면 CI가 지켜야 할 것이 늘어난다.

- **산출물이 코드가 아니다.** `.tflite`, `.onnx`, QNN context binary, 양자화 encoding 파일. 소스 한 줄 안 바뀌어도 재학습·재양자화로 바이너리가 통째로 바뀐다.
- **입력에 데이터가 있다.** 학습 데이터 버전, calibration 데이터, 테스트 세트 버전이 바뀌면 결과가 바뀐다. 코드 diff에는 안 보인다.
- **지표가 확률적이다.** "정확도 91.8% → 91.5%"는 회귀인가 우연인가? 펌웨어의 PASS/FAIL처럼 딱 떨어지지 않는다.
- **지연·메모리·전력은 하드웨어에 묶인다.** 노트북에서 2 ms인 모델이 NPU에서는 CPU fallback 때문에 20 ms일 수 있다. 실기기가 있어야 진짜 숫자가 나온다.

그래서 ML CI는 "테스트를 돌린다"보다 **"모델 후보가 릴리스 자격이 있는지 단계마다 증거를 쌓는다"**에 가깝다.

### 0.1 다른 노트와의 경계 — 다시 쓰지 않는 것

이 주제는 여러 노트에 조금씩 걸쳐 있다. 이 노트는 **"CI에 넣을 때의 설계"**만 다룬다.

| 이미 다룬 곳 | 내용 | 이 노트에서는 |
|---|---|---|
| C8 | 비교 지표(SQNR·cosine·top-1 agreement), bit-exact vs tolerance 판단, 레이어별 diff, bootstrap CI | 지표를 **pytest 테스트**로 바꾸는 법, 게이트의 오판률 |
| J6 | 펌웨어 C unit test, property·fuzz, replay, HIL 랙, CI 세 차선, flaky 관리, 공장 테스트 | 모델 쪽 저장소의 CI, 통계 게이트, 클라우드 farm 비교 |
| K2·K3·K4 | 프로파일러, 전력 측정 장비 원리, 열·sustained 성능 | 측정값을 **게이트**로 쓸 때의 잡음 처리 |
| M2 | 칩 간 비교 벤치마크의 공정성과 계층 bootstrap | 같은 칩에서 **버전 간** 비교 |
| H5 | 데이터 버전, content hash, DVC, registry, 재현성 | 모델 릴리스 manifest와 CI 검증만 |
| F4 8절 | Qualcomm AI Hub의 compile·profile·inference API | AI Hub를 CI 단계로 쓰는 법, 다른 farm과 비교 |
| O1 | export → quantize → bench → report 파이프라인 스크립트 | 그 스크립트를 **언제, 어떤 판정으로** 돌리나 |
| O2 | Linux/Android 기기 위 실행, adb | farm에서 기기를 다루는 운영 관점만 |

### 0.2 이 노트의 공용 예제 — 작은 제스처 모델

예를 들어 Hark 같은 웨어러블이라면 손목 IMU로 제스처를 분류하는 작은 모델이 있을 것이다(추정). 여기서는 6개 IMU 특징 → 16 hidden → 4 클래스의 MLP와, 같은 모델의 **int8 레퍼런스 구현**(numpy)을 공용으로 쓴다. 양자화는 C1의 대칭 int8, per-tensor 또는 per-channel이다.

```python
# o3_model.py — 노트 공용: 6개 IMU 특징 → 4개 제스처의 작은 MLP + int8 레퍼런스
import numpy as np, torch
def make_model(seed=0):
    torch.manual_seed(seed)
    return torch.nn.Sequential(torch.nn.Linear(6, 16), torch.nn.ReLU(), torch.nn.Linear(16, 4)).eval()
def make_inputs(n, seed=1):
    return np.random.default_rng(seed).normal(0, 1, (n, 6)).astype(np.float32)
def quant_w(w, per_channel):            # 대칭 int8, per-tensor 또는 출력 채널별 scale
    amax = np.abs(w).max(axis=1, keepdims=True) if per_channel else np.abs(w).max()
    s = np.maximum(amax, 1e-12) / 127.0
    return np.clip(np.round(w / s), -127, 127).astype(np.int8), np.broadcast_to(s, (w.shape[0], 1)).ravel()
def int8_forward(model, x, per_channel=True, s_x=4/127, s_h=3/127, s_y=1.2/127):
    (w1, b1), (w2, b2) = [(m.weight.detach().numpy(), m.bias.detach().numpy()) for m in (model[0], model[2])]
    q1, sw1 = quant_w(w1, per_channel); q2, sw2 = quant_w(w2, per_channel)
    xq = np.clip(np.round(x / s_x), -128, 127).astype(np.int32)
    acc = xq @ q1.T.astype(np.int32) + np.round(b1 / (s_x * sw1)).astype(np.int32)
    hq = np.clip(np.round(np.maximum(acc, 0) * (s_x * sw1) / s_h), -128, 127).astype(np.int32)
    acc2 = hq @ q2.T.astype(np.int32) + np.round(b2 / (s_h * sw2)).astype(np.int32)
    return np.clip(np.round(acc2 * (s_h * sw2) / s_y), -128, 127).astype(np.int8)
```

실험 코드는 모두 스크래치 폴더에서 `.venv/bin/python`으로 돌렸다. 모델은 학습하지 않은 무작위 초기화다. 숫자 자체보다 **테스트가 무엇을 잡고 무엇을 놓치는지**를 보는 것이 목적이다.

## 1. ML CI가 코드 CI와 다른 네 가지

### 1.1 직관 — "같은 입력이면 같은 출력"이 깨지는 곳

펌웨어 CI의 암묵적 전제는 **결정성**이다. 같은 소스 → 같은 바이너리 → 같은 동작. ML에서는 이 사슬의 고리마다 변수가 붙는다: 학습에는 데이터 버전과 seed, 양자화에는 calibration 데이터와 설정, 컴파일에는 벤더 컴파일러 버전, 실행에는 기기·OS·온도, 평가에는 테스트 세트 버전.

### 1.2 네 가지 차이를 표로

| 축 | 코드 CI (Don의 SSD FW) | ML CI | CI 설계에서 바뀌는 점 |
|---|---|---|---|
| 산출물 | 소스에서 결정적으로 빌드된 바이너리 | 학습·양자화·컴파일이 만든 큰 바이너리 (MB 단위) | 산출물을 git 밖에 두고 **해시로 고정** (7절) |
| 입력 버전 | 코드 커밋 하나 | 코드 + 데이터 + calib + 툴체인 + seed | 회귀가 나면 **어느 축**이 바뀌었는지부터 (5.4절) |
| 판정 | PASS/FAIL, 비트 비교 | 정확도는 표본 추정치, 지연은 분포 | 통계 게이트 (3·4절) |
| 측정 환경 | host에서 대부분 재현 | 지연·메모리·전력은 실기기에서만 진짜 | 기기 farm과 측정 프로토콜 (6절) |

### 1.3 어떤 테스트를 어디에 둘까 — 차선 요약

J6 5.2절의 세 차선(커밋 / 야간 / 릴리스)을 그대로 쓰되, 모델 저장소 기준으로는 이렇게 채운다.

| 차선 | 모델 저장소에서 도는 것 | 판정 | 시간 예산 |
|---|---|---|---|
| 커밋 (PR) | 전처리 unit, op parity, golden(float tol, int8 exact), 성질 테스트, 크기 예산 | PASS/FAIL | 10분 안 |
| 모델 변경 시 | 고정 test set 정확도, 클래스·사용자별 breakdown, host 벤치 | 통계 게이트 (3절) | 30분 안팎 |
| 야간 | 실기기 지연·peak RAM (farm), 세션 교대 측정 | 통계 게이트 (4절) + 추세 | 1~2시간 |
| 릴리스 | 전력(mAh/day), 열 sustained, 여러 기기 종류, 사람 리뷰 | 예산 + margin 리뷰 | 하루 |

말로 하면, **싸고 결정적인 것은 앞으로, 비싸고 확률적인 것은 뒤로** 보낸다. 앞 단계가 결정적이어야 뒤 단계의 통계가 의미를 가진다. 전처리 버그가 있는 채로 정확도 신뢰구간을 계산하는 것은 시간 낭비다.

## 2. pytest로 ML을 테스트한다

### 2.1 tolerance의 정의 — `assert_allclose`는 무엇을 비교하나

float 출력을 비교할 때 가장 많이 쓰는 함수가 `np.testing.assert_allclose(actual, desired, rtol, atol)`이다. 원소마다 이 식을 검사한다.

```
|actual − desired| ≤ atol + rtol × |desired|
```

말로 하면, **허용 오차 = 고정 바닥(atol) + 기대값 크기에 비례하는 부분(rtol)**이다. rtol만 쓰면 기대값이 0 근처일 때 허용치가 0이 되어 아주 작은 차이에도 실패한다. atol만 쓰면 큰 값에서 너무 엄격하거나 작은 값에서 너무 느슨하다. 그래서 둘을 함께 쓴다.

손계산을 먼저 해 보자. desired = [1.000, 0.010, −2.000, 0.0], actual = [1.001, 0.012, −2.003, 0.000003].

| 원소 | 차이 | rtol=1e-3, atol=0 허용치 | rtol=1e-3, atol=1e-5 허용치 | 판정 (둘째 설정) |
|---|---|---|---|---|
| 1.000 | 0.001 | 0.001 | 0.00101 | 통과 |
| 0.010 | 0.002 | 0.00001 | 0.00002 | 실패 |
| −2.000 | 0.003 | 0.002 | 0.00201 | 실패 |
| 0.0 | 0.000003 | 0 | 0.00001 | 통과 |

넷째 원소가 핵심이다. atol이 0이면 기대값 0에 대해 3e-6 차이로도 실패한다.

무엇을 확인하는 코드인가: 위 손계산과 `assert_allclose`의 실패 메시지, 그리고 int8 비교는 tolerance가 아니라 정확히 같아야 한다는 점.

```python
# assert_allclose의 판정식: |actual - desired| <= atol + rtol * |desired|  (원소마다)
import numpy as np
desired = np.array([1.000, 0.010, -2.000, 0.0])
actual  = np.array([1.001, 0.012, -2.003, 3e-6])
for rtol, atol in [(1e-3, 0.0), (1e-3, 1e-5), (1e-3, 3e-3)]:
    bound = atol + rtol * np.abs(desired)
    ok = np.abs(actual - desired) <= bound
    print(f"rtol={rtol:g} atol={atol:g}  bound={np.round(bound, 6)}  ok={ok}")
try:
    np.testing.assert_allclose(actual, desired, rtol=1e-3, atol=1e-5)
except AssertionError as e:
    print("\n".join(str(e).strip().splitlines()[:4]))
# int8 출력은 tolerance가 아니라 정확히 같아야 한다
q_ref = np.array([12, -128, 127, 0], dtype=np.int8)
q_dut = np.array([12, -128, 126, 0], dtype=np.int8)
print("int8 mismatches at", np.flatnonzero(q_ref != q_dut), "diff", (q_dut.astype(int) - q_ref)[q_ref != q_dut])
```

출력에서 볼 것: 같은 데이터가 tolerance 설정에 따라 0개, 2개, 3개 실패로 바뀐다. **tolerance가 곧 테스트의 정의**이므로, 코드 안에 숫자를 흩뿌리지 말고 이유와 함께 한 곳(설정 파일이나 상수)에 둔다. int8 쪽은 1 LSB 차이도 실패로 잡는다. C8 3절의 결론 그대로다: 정수 커널은 규격이 같으면 bit-exact가 가능하므로 exact로 검사한다.

tolerance를 정하는 실무 규칙:

- **같은 런타임, 같은 하드웨어, 같은 스레드 수**: 이론상 bit-exact. 그래도 float이면 `rtol=1e-6` 정도로 시작.
- **torch vs ONNX Runtime (CPU)**: 합산 순서·커널이 달라서 1e-7~1e-6 수준 차이. `rtol=1e-5, atol=1e-6` 출발점.
- **float vs int8**: allclose가 아니라 C8의 SQNR·top-1 agreement로 본다. allclose로 하면 tolerance가 너무 커서 의미가 없다.
- **NPU fp16**: `rtol=1e-2` 근처. 이것도 대개는 과제 지표로 보는 편이 낫다.

### 2.2 golden 테스트 — fixture와 parametrize

golden 파일은 **릴리스 시점에 한 번** 기준 모델로 만들고, CI는 읽기만 한다. Don에게 익숙한 말로 하면 "검증된 펌웨어로 뽑아 둔 expected 로그"다.

```python
# 릴리스 시점에 한 번: 기준 모델로 golden 파일을 만든다 (CI는 이것을 읽기만 한다)
import numpy as np, torch
from o3_model import make_model, make_inputs, int8_forward

with torch.no_grad(): y = m(torch.from_numpy(x)).numpy()
np.savez("golden_v1.npz", x=x, y_float=y,
         y_int8_pc=int8_forward(m, x, True), y_int8_pt=int8_forward(m, x, False))
torch.save(m.state_dict(), "model_v1.pt")
print("golden:", {k: v.shape for k, v in np.load("golden_v1.npz").items()})
```


**fixture**는 테스트가 쓰는 준비물을 만들어 주는 함수다. `scope="session"`이면 테스트 실행 전체에서 한 번만 만든다. 모델 로드처럼 비싼 일에 쓴다. 테스트 함수의 인자 이름이 fixture 이름과 같으면 pytest가 자동으로 넣어 준다. `conftest.py`에 두면 같은 폴더의 모든 테스트 파일이 쓸 수 있다.

```python
# conftest.py — 모든 테스트가 공유하는 fixture (session: 한 번만 로드)
import os, numpy as np, pytest, torch
from o3_model import make_model
@pytest.fixture(scope="session")
def golden():
    return dict(np.load("golden_v1.npz"))
@pytest.fixture(scope="session")
def model():
    m = make_model(); m.load_state_dict(torch.load(os.environ.get("O3_MODEL", "model_v1.pt")))
    return m
```

`O3_MODEL` 환경 변수로 테스트 대상 모델을 바꿀 수 있게 했다. CI에서는 "후보 모델 경로"를 이렇게 넘긴다.

**parametrize**는 같은 테스트를 여러 설정으로 돌리는 장치다. 양자화 설정(per-channel, per-tensor), 입력 shape, 런타임 종류처럼 축이 여러 개인 ML 테스트에 딱 맞는다. `ids`를 주면 결과에 사람이 읽을 수 있는 이름이 붙는다.

무엇을 확인하는 코드인가: float은 tolerance, int8은 bit-exact, 그리고 과제 수준 지표(top-1 agreement)를 세 층으로 검사하는 테스트 파일.

```python
# test_golden.py — float은 tolerance, int8은 bit-exact, 설정별 parametrize
import numpy as np, pytest, torch
from o3_model import int8_forward, make_inputs
def test_float_golden(model, golden):
    with torch.no_grad(): y = model(torch.from_numpy(golden["x"])).numpy()
    np.testing.assert_allclose(y, golden["y_float"], rtol=1e-5, atol=1e-6)
@pytest.mark.parametrize("per_channel,key", [(True, "y_int8_pc"), (False, "y_int8_pt")],
                         ids=["per_channel", "per_tensor"])
def test_int8_bit_exact(model, golden, per_channel, key):
    q = int8_forward(model, golden["x"], per_channel)
    bad = np.flatnonzero((q != golden[key]).any(axis=1))
    assert bad.size == 0, f"{bad.size} rows differ, first rows {bad[:5].tolist()}"
@pytest.mark.parametrize("per_channel,min_agree", [(True, 0.97), (False, 0.95)],
                         ids=["per_channel", "per_tensor"])
def test_top1_agreement(model, per_channel, min_agree):
    x = make_inputs(2000, seed=7)
    with torch.no_grad(): ref = model(torch.from_numpy(x)).numpy().argmax(1)
    agree = (int8_forward(model, x, per_channel).argmax(1) == ref).mean()
    print(f"agreement={agree:.4f}")
    assert agree >= min_agree
```

### 2.3 op parity — 런타임끼리 같은 답을 내는가

모델 전체가 틀렸을 때 원인을 찾는 것은 어렵다(C8 4절의 레이어별 diff). 그 전에 **op 하나씩** 기준 런타임과 배포 런타임을 비교해 두면, 런타임 버전을 올릴 때 어느 op가 바뀌었는지 바로 보인다. Don의 말로 하면 "명령 하나하나의 conformance 테스트"다.

무엇을 확인하는 코드인가: op마다 작은 모듈을 ONNX로 내보내 torch와 onnxruntime 결과를 op별 tolerance로 비교한다.

```python
# test_parity.py — op 하나씩 ONNX로 내보내 torch vs onnxruntime 비교 (op별 tolerance)
import io, numpy as np, onnxruntime as ort, pytest, torch
OPS = {  # 이름: (모듈, 입력 shape, rtol, atol)
    "conv1d":    (torch.nn.Conv1d(6, 8, 5, padding=2), (2, 6, 50), 1e-5, 1e-5),
    "layernorm": (torch.nn.LayerNorm(16),              (4, 10, 16), 1e-4, 1e-5),
    "gelu":      (torch.nn.GELU(),                      (3, 64), 1e-5, 1e-6),
    "softmax":   (torch.nn.Softmax(dim=-1),             (3, 32), 1e-5, 1e-7),
    "gru":       (torch.nn.GRU(6, 12, batch_first=True),(2, 20, 6), 1e-4, 1e-5),
}
def run_ort(mod, x):
    buf = io.BytesIO()
    torch.onnx.export(mod, (x,), buf, input_names=["x"], dynamo=False, opset_version=17)
    sess = ort.InferenceSession(buf.getvalue(), providers=["CPUExecutionProvider"])
    return sess.run(None, {"x": x.numpy()})[0]
@pytest.mark.parametrize("name", list(OPS))
def test_op_parity(name):
    torch.manual_seed(0)
    mod, shape, rtol, atol = OPS[name]; mod.eval()
    x = torch.randn(shape)
    with torch.no_grad():
        ref = mod(x); ref = (ref[0] if isinstance(ref, tuple) else ref).numpy()
    out = run_ort(mod, x)
    print(f"{name:9s} max_abs={np.abs(out - ref).max():.2e}")
    np.testing.assert_allclose(out, ref, rtol=rtol, atol=atol)
```

```text

.layernorm max_abs=3.58e-07
.gelu      max_abs=2.38e-07
.softmax   max_abs=1.49e-08
.gru       max_abs=1.34e-07
.
5 passed in 0.21s
```

출력에서 볼 것: 줄 앞의 `.`은 바로 앞 테스트의 PASS 표시다(`-s`로 print가 섞여 나옴). 모든 op가 1e-6 아래로 일치한다. conv1d는 이 입력에서 정확히 0이었지만, 그건 우연이지 보장이 아니다. 이 표를 **런타임 버전마다 저장해 두면**, onnxruntime을 올렸더니 layernorm만 1e-4로 뛰었다 같은 변화가 바로 보인다.

같은 틀을 세 번째 열로 넓히면 C 레퍼런스 커널(8절)이나 벤더 런타임(F4의 QNN)도 같은 표에 들어간다. 원칙은 하나다: **기준 하나(보통 torch float 또는 numpy 레퍼런스)를 정하고, 나머지는 모두 그것과 비교**한다. 런타임끼리 서로 비교하면 어느 쪽이 틀렸는지 모른다.

### 2.4 성질(property) 테스트 — 정답 없이 검사하기

golden은 "이 입력에서 이 출력"만 지킨다. 성질 테스트는 **어떤 입력에서도 성립해야 하는 규칙**을 무작위 입력 여러 개로 검사한다(J6 2절은 C 코드 쪽, 여기는 모델 쪽). ML 모델에 쓸 만한 성질:

| 성질 | 무엇을 잡나 |
|---|---|
| batch invariance: 배치로 돌린 결과 = 한 개씩 돌린 결과 | 배치 전체로 scale을 잡는 dynamic quant, 배치 축이 섞이는 reshape 버그, BatchNorm을 train 모드로 둔 실수 |
| 범위: int8 출력은 [−128, 127], softmax 합은 1 | saturation 누락, dtype 실수 |
| 결정성: 같은 입력 두 번 → 같은 바이트 | 초기화 안 된 버퍼, 스레드 순서 의존 |
| 대칭·불변성: 시간축 이동이나 채널 순서에 대한 기대 동작 | 전처리 윈도 경계 버그 |
| 단조성: 확신이 큰 입력에서 확률이 커짐 (해당될 때만) | 부호 실수 |

무엇을 확인하는 코드인가: batch invariance 성질이 "배치 max로 입력 scale을 잡는" 흔한 버그를 20개 seed 모두에서 잡는지.

```python
# test_props.py — 정답값 없이 "항상 성립해야 하는 성질"을 무작위 입력 여러 개로 검사
import numpy as np, pytest
from o3_model import int8_forward, make_inputs
def dynamic_bug(model, x, per_channel=True):        # 흔한 버그: 입력 scale을 "배치 전체 max"로 잡음
    return int8_forward(model, x, per_channel, s_x=np.abs(x).max() / 127)
@pytest.mark.parametrize("fwd", [int8_forward, dynamic_bug], ids=["static", "dynamic_bug"])
@pytest.mark.parametrize("seed", range(20))
def test_batch_invariance(model, fwd, seed):        # 혼자 돌리든 배치로 돌리든 같은 답
    x = make_inputs(8, seed=100 + seed)
    batch = fwd(model, x)
    single = np.stack([fwd(model, x[i:i + 1])[0] for i in range(8)])
    assert np.array_equal(batch, single)
@pytest.mark.parametrize("seed", range(20))
def test_range_and_determinism(model, seed):
    x = make_inputs(32, seed=200 + seed) * 10        # 일부러 범위를 넘는 입력 (saturation 경로)
    a, b = int8_forward(model, x), int8_forward(model, x)
    assert a.dtype == np.int8 and a.min() >= -128 and a.max() <= 127
    assert a.tobytes() == b.tobytes()
```

(실패 20개는 전부 `dynamic_bug`였다 — `grep -c` 결과 20.) 출력에서 볼 것: parametrize 두 개가 곱해져 2 × 20 = 40개 batch 테스트 + 20개 범위 테스트 = 60개가 0.09초에 돌았다. 버그 버전은 20개 seed **전부**에서 실패했다. 이 버그는 golden 테스트로는 잡기 어렵다. golden 파일을 만들 때의 배치 크기와 CI의 배치 크기가 같으면 golden이 그대로 맞기 때문이다. 기기에서는 배치 1로 돌리므로 결과가 달라진다. 실제로 **"host 평가와 기기 결과가 다르다"의 흔한 원인**이 이것이다.

`hypothesis` 같은 라이브러리를 쓰면 반례를 자동으로 줄여(shrinking) 주지만, 이 정도 성질은 seed parametrize로 충분하다. seed를 고정해야 실패가 재현된다.

### 2.5 host 벤치마크 — pytest-benchmark

`pytest-benchmark`는 `benchmark` fixture를 주는 플러그인이다. 함수를 넘기면 반복 횟수를 스스로 정하고(calibration), 통계(min, median, IQR 등)를 낸다. `--benchmark-autosave`로 결과를 `.benchmarks/`에 JSON으로 저장하고, `--benchmark-compare`로 지난 결과와 비교하며, `--benchmark-compare-fail=median:10%`처럼 쓰면 median이 10% 넘게 나빠질 때 실패한다(설치된 5.2.3의 `--help`로 확인).

무엇을 확인하는 코드인가: 전처리 + int8 추론을 벤치마크로 저장하고, 전처리에 파이썬 루프를 넣는 회귀를 비교 게이트가 잡는지.

```python
# test_bench.py — host에서 전처리+int8 추론 시간을 pytest-benchmark로 기록 (O3_SLOW=1이면 일부러 느린 경로)
import os, numpy as np
from o3_model import int8_forward, make_inputs
def preprocess(x):
    if os.environ.get("O3_SLOW"):                   # 회귀 주입: 행마다 파이썬 루프
        return np.stack([(r - r.mean()) / (r.std() + 1e-6) for r in x])
    return (x - x.mean(1, keepdims=True)) / (x.std(1, keepdims=True) + 1e-6)
def test_bench_pipeline(benchmark, model):
    x = make_inputs(256, seed=5)
    out = benchmark(lambda: int8_forward(model, preprocess(x)))
    assert out.shape == (256, 4)
```

### 2.6 marker로 차선을 나눈다

pytest marker는 테스트에 꼬리표를 붙여 골라 돌리게 한다. 차선(1.3절)을 marker로 표현하면 같은 테스트 코드베이스를 CI 단계마다 다르게 쓸 수 있다.

```python
# 실행하지 않음 — 구조 예시
import pytest
@pytest.mark.device          # 실기기 필요: 커밋 차선에서는 제외
def test_latency_on_device(farm_device): ...
@pytest.mark.slow            # 정확도 전체 평가: 모델 변경 차선
def test_accuracy_full_testset(model, testset_v9): ...
```

차선별로는 `pytest -m "not slow and not device"`(커밋), `pytest -m "slow and not device"`(모델 변경), `pytest -m device --junitxml=device.xml`(야간 farm)처럼 부른다. marker는 `pytest.ini`의 `markers`에 등록해야 경고가 나지 않는다.

`farm_device` 같은 fixture가 기기를 예약하고 반납하게 만들면, 테스트 코드는 기기가 클라우드든 사내 랙이든 모른다. 기기 연결 자체(adb, 파일 push)는 O2에서 다룬다.

## 3. 정확도 게이트 — "0.3%p 떨어졌다"를 판정하는 법

### 3.1 왜 단순 문턱은 위험한가 — 손계산

가장 흔한 게이트는 "정확도가 0.5%p 넘게 떨어지면 FAIL"이다. 테스트 세트가 n = 2000개이고 정확도가 92% 근처라면, **정확도 하나의 표준오차**는

```
SE = √(p(1−p)/n) = √(0.92 × 0.08 / 2000) = √0.0000368 ≈ 0.0061 = 0.61%p
```

말로 하면, 같은 모델이라도 테스트 세트를 새로 뽑으면 정확도가 ±0.6%p쯤 흔들린다. 그런데 CI의 테스트 세트는 **고정**이다. 그러면 흔들림이 없지 않나? 아니다. 두 모델 비교에서 흔들리는 것은 **어느 샘플에서 두 모델이 엇갈리느냐**다. 재학습이나 재양자화는 일부 샘플의 정답 여부를 바꾼다(churn). 같은 실력의 후보라도 이 엇갈림 때문에 관측 drop이 0 근처에서 흔들린다.

엇갈림을 숫자로 보자. 두 모델의 샘플별 정답 여부를 짝지으면 네 칸이 된다.

| | 후보 맞음 | 후보 틀림 |
|---|---|---|
| 기준 맞음 | a (둘 다 맞음) | b (새로 틀림) |
| 기준 틀림 | c (새로 맞음) | d (둘 다 틀림) |

drop = (b − c) / n이다. a와 d는 차이에 대해 아무 정보가 없다. **b + c(엇갈린 샘플 수)가 클수록 drop이 잘 흔들린다.** churn이 3%(b + c ≈ 60개)이고 진짜 차이가 0이면, b는 대략 Binomial(60, 0.5)이라서 b − c의 표준편차는 √60 ≈ 7.7개 = 0.39%p다. 그러면 "관측 drop > 0.5%p"는 대략 z = 0.5/0.39 ≈ 1.3, 즉 **약 10%의 확률로 무고한 후보를 막는다**. 하루 PR 10개면 매일 한 번 거짓 경보다.

### 3.2 McNemar 검정 — 엇갈린 샘플만 본다

McNemar 검정은 위 표의 b와 c만 쓴다. "차이가 없다"면 엇갈린 샘플 하나가 b쪽일 확률이 1/2이므로, b는 Binomial(b + c, 1/2)을 따라야 한다. 관측된 b가 그보다 지나치게 크면 "후보가 정말 나빠졌다"고 본다(L1 4.2절에서 SLM 비교에 같은 검정을 썼다).

손계산: b = 14, c = 0이면 엇갈린 14개가 전부 한쪽이다. 차이가 없을 때 이럴 확률은 (1/2)¹⁴ = 1/16384 ≈ 0.00006이다. 같은 drop(0.7%p)이라도 b = 73, c = 59라면 132개 중 73개가 한쪽인 정도는 동전 던지기로 흔히 나온다.

무엇을 확인하는 코드인가: McNemar exact p 값과 paired 차이의 신뢰구간, 그리고 같은 drop이라도 churn에 따라 증거의 세기가 달라진다는 점.

```python
# 짝지은 예측의 McNemar exact 검정: 한쪽만 맞은 샘플 수 b, c만 본다
import numpy as np
from scipy.stats import binom
n = 2000
b, c = 23, 9            # b: 기준만 맞음(후보가 새로 틀림), c: 후보만 맞음(후보가 새로 맞음)
drop = (b - c) / n
p_one = binom.sf(b - 1, b + c, 0.5)          # P(B >= b | 차이 없음), 단측
p_two = min(1.0, 2 * p_one)
se = np.sqrt(b + c - (b - c) ** 2 / n) / n   # paired 차이의 표준오차
print(f"drop={drop*100:.2f}%p  b+c={b+c}  p_one={p_one:.4f}  p_two={p_two:.4f}")
print(f"95% CI of drop = [{(drop-1.96*se)*100:.2f}, {(drop+1.96*se)*100:.2f}] %p")
# 같은 drop이라도 discordant가 많으면(= 모델이 많이 '흔들리면') 근거가 약해진다
for b, c in [(14, 0), (23, 9), (73, 59)]:
    print(f"b={b:3d} c={c:3d}  drop={(b-c)/n*100:.2f}%p  p_one={binom.sf(b-1, b+c, 0.5):.4f}")
```

```text
drop=0.70%p  b+c=32  p_one=0.0100  p_two=0.0201
95% CI of drop = [0.15, 1.25] %p
b= 14 c=  0  drop=0.70%p  p_one=0.0001
b= 23 c=  9  drop=0.70%p  p_one=0.0100
b= 73 c= 59  drop=0.70%p  p_one=0.1289
```

출력에서 볼 것: 세 경우 모두 drop은 0.70%p로 같지만 p 값은 0.0001, 0.01, 0.13으로 천 배 넘게 다르다. **정확도 숫자 두 개만 저장하면 이 판정을 할 수 없다.** 샘플별 정답 여부(또는 예측)를 저장해야 한다(C8 6.1절과 같은 결론). 신뢰구간 계산은 C8 6.2절의 paired bootstrap으로 해도 되고, 여기처럼 정규근사 식으로 해도 n이 크면 거의 같다.

### 3.3 게이트 세 가지의 오판률 — 시뮬레이션

게이트는 결국 두 가지 실수를 한다. Don의 factory test 용어로 하면 **과검(false alarm, 좋은 걸 불량 판정)**과 **미검(miss, 불량을 통과)**이다. 세 게이트를 비교한다.

- **G1 단순 문턱**: 관측 drop > 0.5%p 이면 FAIL.
- **G2 유의성**: McNemar 단측 p < 0.05 이면 FAIL. "나빠졌다는 증거가 있으면 막는다."
- **G3 비열등(non-inferiority)**: drop의 95% 상한 > 1.0%p 이면 FAIL. "1%p보다 덜 나빠졌다는 증거가 없으면 막는다." 증명 책임이 후보에게 있다.

무엇을 확인하는 코드인가: 진짜 drop(0~2%p)마다 각 게이트가 FAIL을 낼 확률을, n = 2000과 n = 8000에서 2만 번씩 시뮬레이션한다.

```python
# 정확도 게이트 3종의 P(FAIL)을 실제 drop별로 시뮬레이션 (짝지은 churn 3%, 반복 20000번)
import numpy as np
from scipy.stats import binom
rng = np.random.default_rng(0)
T, churn = 20000, 0.03
def p_fail(n, d):
    p_out, p_in = churn / 2 + d / 2, churn / 2 - d / 2    # 새로 틀림 / 새로 맞음 비율
    k = rng.multinomial(n, [p_out, p_in, 1 - p_out - p_in], size=T)
    b, c = k[:, 0], k[:, 1]
    drop = (b - c) / n
    se = np.sqrt(np.maximum(b + c - (b - c) ** 2 / n, 1e-9)) / n
    g1 = drop > 0.005                                     # G1: 관측 drop > 0.5%p → FAIL
    g2 = binom.sf(b - 1, b + c, 0.5) < 0.05               # G2: McNemar 단측 p < 0.05 → FAIL
    g3 = drop + 1.645 * se > 0.010                        # G3: drop 95% 상한 > 1.0%p → FAIL
    return g1.mean(), g2.mean(), g3.mean()
print("true_drop | n=2000: G1    G2    G3 | n=8000: G1    G2    G3")
for d in [0.0, 0.0025, 0.005, 0.0075, 0.010, 0.015, 0.020]:
    a, b = p_fail(2000, d), p_fail(8000, d)
    print(f"{d*100:5.2f}%p  |       " + " ".join(f"{v:5.3f}" for v in a)
          + " |       " + " ".join(f"{v:5.3f}" for v in b))
```

출력에서 볼 것, 세 가지:

1. **G1(단순 문턱)은 n과 상관없이 문턱 근처에서 동전 던지기다.** 진짜 drop 0.5%p에서 FAIL 확률이 n=2000·8000 모두 약 0.48이다. 그리고 n=2000이면 무고한 후보를 8.8% 막는다.
2. **G2(유의성)는 n이 커질수록 "의미 없이 작은" 차이까지 막는다.** n=8000에서 0.25%p drop을 34% 막는다. 유의성(statistical significance)은 "차이가 있다"이지 "차이가 크다"가 아니다. 테스트 세트를 늘릴수록 게이트가 점점 까다로워지는 이상한 게이트다.
3. **G3(비열등)는 n이 작으면 과검이 크고(17%), n이 충분하면 거의 이상적**이다(0.0%와 94.7%). 증명 책임을 후보에게 두면, 증명할 데이터가 충분해야 공정하다.

그래서 실무 규칙은 이렇다.

- **"얼마까지 나빠져도 되는가"(허용 한계, margin)를 제품 기준으로 먼저 정한다.** 예: 제스처 top-1은 1%p, wake word FA/h는 기준 대비 +10%. 결과를 보고 정하면 안 된다(C8 6.1절).
- **G3 형태(신뢰구간 상한 vs margin)로 판정하고, n은 G3의 과검이 작아질 만큼 키운다.** 위 시뮬레이션처럼 "진짜 차이 0일 때 FAIL 확률"을 목표(예: 1% 이하)로 잡고 n을 역산한다.
- 데이터를 더 모을 수 없으면 **3단 판정**: 상한 < margin → PASS, 하한 > margin → FAIL, 그 사이 → "판정 보류, 사람 리뷰". 보류를 정식 결과로 인정하는 것이 거짓 FAIL을 남발하는 것보다 낫다.
- 여러 지표(전체, 클래스별 4개, 사용자 그룹별)를 동시에 게이트하면 과검이 쌓인다. 지표가 10개고 각각 과검 5%면, 하나라도 FAIL일 확률은 1 − 0.95¹⁰ ≈ 40%다. **주 지표만 엄격하게 게이트하고 나머지는 경고**로 두거나, 지표별 유의수준을 나눈다(Bonferroni: 0.05/10).

## 4. 지연 게이트 — 잡음 낀 측정에서 3% 회귀 찾기

### 4.1 지연 측정 잡음의 구조

K2·M2에서 측정 잡음을 다뤘다. CI 게이트 관점에서 중요한 것은 잡음이 **층**으로 쌓인다는 점이다.

```
측정값 = 진짜 지연 × 세션 효과 × 반복 잡음 + warmup + outlier
          │           │            │           │        └ 인터럽트, GC, 다른 앱 (드물고 큼)
          │           │            │           └ 첫 몇 번: 캐시 콜드, 그래프 초기화, DVFS 상승 전
          │           │            └ 같은 세션 안에서 반복마다 (작고 잦음)
          │           └ 기기를 재부팅·재연결할 때마다 바뀌는 상태: 온도, 클럭 정책, 메모리 배치
          └ 우리가 알고 싶은 것
```

Don에게 익숙한 비유: SSD의 latency QoS 측정에서 같은 드라이브라도 **precondition 상태와 온도**가 달라지면 분포 전체가 옮겨 간다. 한 번의 측정 세션 안에서 1000번 잰 숫자는 서로 독립이 아니다. 같은 세션 효과를 공유한다.

robust 통계 두 가지를 기억해 둔다(H7 5절에서 정의).

- **median**: outlier 몇 개에 흔들리지 않는 중앙값.
- **MAD**(median absolute deviation): median으로부터 거리들의 median. 표준편차 대신 쓴다. 정규분포에서 σ ≈ 1.4826 × MAD.

### 4.2 게이트 네 가지 — 시뮬레이션

진짜 지연 20 ms, 세션 효과 1.5%, 반복 잡음 3%, warmup 3회(1.5배), outlier 5%(1.3배)인 기기를 흉내 낸다. 네 게이트:

- **L1**: 기준·후보 세션 1번씩, 평균 비교, +3% 넘으면 FAIL.
- **L2**: 세션 1번씩, warmup 5회 버리고, 반복 25개를 표본으로 Mann–Whitney U 단측 p < 0.01.
- **L3**: 기준·후보 세션 5번씩 교대, 세션별 median의 median 비교, +3% 넘으면 FAIL.
- **L4**: L3의 세션 median 5개끼리 Mann–Whitney U 단측 p < 0.05 **그리고** median 비 +2% 초과.

Mann–Whitney U 검정은 "한 그룹 값이 다른 그룹 값보다 큰 경향이 있는가"를 순위만으로 검사한다. 정규분포 가정이 없어서 꼬리가 긴 지연 분포에 잘 맞는다.

무엇을 확인하는 코드인가: 진짜 느려짐 0~8%에서 네 게이트의 FAIL 확률.

```python
# 지연 회귀 게이트 4종의 P(FAIL): 세션 간 흔들림(열·DVFS) + 반복 내 잡음 + warmup + outlier
import numpy as np
from scipy.stats import mannwhitneyu
rng = np.random.default_rng(1)
def session(slow, iters=30):                     # 기기 세션 1번 = 30회 측정 (ms)
    base = 20.0 * (1 + slow) * np.exp(rng.normal(0, 0.015))          # 세션 수준 오프셋 1.5%
    x = base * np.exp(rng.normal(0, 0.03, iters))                     # 반복 잡음 3%
    x[:3] *= 1.5                                                      # warmup 3회
    x[rng.random(iters) < 0.05] *= 1.3                                # 5% outlier (인터럽트 등)
    return x
def trial(slow):
    A1, B1 = session(0), session(slow)                                # 세션 1번씩
    g1 = B1.mean() / A1.mean() - 1 > 0.03                             # L1: 평균 비교 > 3%
    a, b = A1[5:], B1[5:]
    g2 = mannwhitneyu(b, a, alternative="greater").pvalue < 0.01      # L2: 반복을 표본으로 MWU
    A = [np.median(session(0)[5:]) for _ in range(5)]                 # L3/L4: 세션 5번씩 교대
    B = [np.median(session(slow)[5:]) for _ in range(5)]
    ratio = np.median(B) / np.median(A) - 1
    g3 = ratio > 0.03                                                  # L3: 세션 median의 median > 3%
    g4 = (mannwhitneyu(B, A, alternative="greater").pvalue < 0.05) and ratio > 0.02  # L4
    return g1, g2, g3, g4
print("true_slowdown  L1 mean>3%  L2 MWU(iter)  L3 med5>3%  L4 MWU(sess)&>2%")
for s in [0.0, 0.02, 0.03, 0.05, 0.08]:
    r = np.array([trial(s) for _ in range(2000)]).mean(0)
    print(f"{s*100:8.0f}%      " + "   ".join(f"{v:9.3f}" for v in r))
```

그림 3 — 지연 게이트 네 가지의 과검(빨강)과 5% 회귀 검출률(파랑). ex8의 숫자 그대로다. 세션을 여러 번 나눠 잰 L3·L4가 과검과 검출 둘 다에서 낫다.

출력에서 볼 것:

1. **L2가 함정이다.** p < 0.01이라는 엄격한 기준인데도 진짜 차이 0에서 15.8%가 FAIL이다. 검정은 "반복 25개가 서로 독립"이라고 가정하는데, 실제로는 세션 효과(1.5%)를 공유한다. 그래서 세션 효과 차이를 "진짜 차이"로 착각한다. 반복을 1000번으로 늘리면 더 나빠진다. p 값이 작아질 뿐 세션 효과는 그대로이기 때문이다.
2. **반복을 늘리는 것보다 세션을 늘리는 것이 효과적이다.** L3는 같은 3% 문턱인데 과검이 13% → 0.9%로 떨어졌다. 독립인 단위(세션)를 표본으로 써야 통계가 맞다. Don의 말로 하면 **"한 드라이브를 1000번 재지 말고, 다시 붙이고 다시 precondition해서 5번 재라"**다.
3. L4는 "유의하면서 + 크기도 의미 있을 때만" FAIL이라서 과검 1.5%, 5% 검출 97.7%로 가장 균형이 좋다. 3.3절 G2의 함정(작은 차이에 과민)을 크기 조건으로 막은 형태다.

### 4.3 측정 순서 — 열 drift를 교대로 상쇄한다

기기는 측정할수록 데워진다(K4). 기준 5세션을 먼저 다 재고 후보 5세션을 나중에 재면, 후보가 더운 상태에서 측정되어 억울하게 느리게 나온다.

무엇을 확인하는 코드인가: 진짜 차이가 0인 A/A 비교에서, 세션마다 6%까지 올라가는 열 drift가 있을 때 측정 순서별 겉보기 차이.

```python
# 열 drift가 있을 때 측정 순서가 결과를 바꾼다: 진짜 차이 0인 A/A 비교
import numpy as np
rng = np.random.default_rng(2)
def run(order, trials=4000):
    out = []
    for _ in range(trials):
        drift = np.linspace(0, 0.06, len(order))            # 세션이 지날수록 6%까지 느려짐 (발열)
        lat = 20 * (1 + drift) * np.exp(rng.normal(0, 0.01, len(order)))
        a = np.median(lat[[i for i, o in enumerate(order) if o == "A"]])
        b = np.median(lat[[i for i, o in enumerate(order) if o == "B"]])
        out.append(b / a - 1)
    out = np.array(out)
    return out.mean(), (out > 0.03).mean()
for name, order in [("sequential", "AAAAABBBBB"), ("interleaved", "ABABABABAB"), ("ABBA", "ABBAABBAAB")]:
    m, fa = run(order)
    print(f"{name:11s} {order}  mean(B/A-1)={m*100:+.2f}%  P(>3%)={fa:.3f}")
```

```text
sequential  AAAAABBBBB  mean(B/A-1)=+3.27%  P(>3%)=0.614
interleaved ABABABABAB  mean(B/A-1)=+0.63%  P(>3%)=0.014
ABBA        ABBAABBAAB  mean(B/A-1)=+0.21%  P(>3%)=0.005
```

출력에서 볼 것: 같은 모델끼리인데 순차 측정은 평균 +3.3% "회귀"를 만들고, 3% 게이트를 61% 확률로 거짓 FAIL시킨다. 교대(ABAB)는 +0.6%, ABBA 순서는 +0.2%까지 줄인다. ABBA는 A와 B의 평균 위치가 거의 같아서 선형 drift가 상쇄된다. 손으로: ABAB에서 A의 위치는 0,2,4,6,8(평균 4), B는 1,3,5,7,9(평균 5)라서 B가 한 칸만큼(6%/9 ≈ 0.67%) 불리하다. 출력의 +0.63%와 맞는다.

실무 규칙:

- **기준 모델을 매번 같이 잰다.** 지난주에 잰 기준 숫자와 오늘 후보 숫자를 비교하지 않는다. 기기 펌웨어·OS 업데이트·온도가 다르다. 같은 기기, 같은 날, 교대로.
- 세션 사이에 **냉각 대기**(예: 기기 온도 센서 값이 시작값 근처로 돌아올 때까지)를 넣거나, 반대로 일정 부하로 **열 평형**에 도달한 뒤 잰다. 무엇을 택하든 기준과 후보에 같게 한다(K4).
- **A/A 테스트를 정기적으로 돌린다.** 같은 모델을 A와 B 양쪽에 넣고 게이트를 돌리면 과검률이 직접 나온다. 과검률이 설계값(예: 1%)보다 크면 측정 프로토콜에 문제가 있다(I5 7.2절의 잡음 바닥 측정과 같은 생각).

### 5.1 budgets.yaml — 숫자 계약서

NPI에서 Don이 margin sign-off를 할 때 기준표가 있었다. ML 모델도 같다. **모델마다 크기·peak RAM·지연·전력 예산을 파일로 적고 git에 넣는다.** 바꾸려면 리뷰가 필요하다(J6 5.5절의 CODEOWNERS 규칙). I6에서 본 flash·RAM·MAC 예산표의 모델 저장소 판이다.

전력 예산을 지연에서 끌어내는 손계산부터. 제스처 모델이 100 ms마다 돈다면 하루 실행 횟수는 86,400 s / 0.1 s = 864,000회다. 한 번에 2.05 ms 동안 idle 대비 12 mA를 더 쓴다면

```
하루 추가 전하 = 864,000 × 2.05 ms × 12 mA
              = 1,771.2 s × 12 mA = 0.492 h × 12 mA ≈ 5.90 mAh/day
```

말로 하면, **지연이 1% 늘면 이 모델의 하루 전력도 1% 는다.** 웨어러블 배터리가 수백 mAh라면 모델 하나가 몇 %를 쓰는지 바로 보인다(N1·D7). 아래 체커는 보수적으로 p90 지연을 썼다. 평균 전하를 정확히 보려면 mean 지연이 맞고, 더 정확히는 K3의 전류 적분 측정이 맞다.


무엇을 확인하는 코드인가: 측정값을 예산과 기준선 양쪽에 비교해 FAIL / WARN / PASS를 내고, CI가 읽을 종료 코드를 돌려준다. 측정값은 예시로 넣은 숫자다(실제로는 6절 farm 결과 JSON을 읽는다).

```python
# 측정값(JSON)을 예산(YAML)과 비교: FAIL(초과) / WARN(여유 5% 미만 또는 기준선 대비 +3% 이상) / PASS
import json, sys, yaml
budgets = yaml.safe_load(open("budgets.yaml"))
measured = {"gesture_v2":  {"size_kb": 88.4, "peak_ram_kb": 41.0, "p90_latency_ms": 2.05},
            "wakeword_v5": {"size_kb": 371.0, "peak_ram_kb": 262.0, "p90_latency_ms": 6.1}}
baseline = {"gesture_v2":  {"size_kb": 84.9, "peak_ram_kb": 41.0, "p90_latency_ms": 2.01},
            "wakeword_v5": {"size_kb": 371.0, "peak_ram_kb": 240.0, "p90_latency_ms": 6.0}}
worst = "PASS"
for name, b in budgets.items():
    m, base_m = dict(measured[name]), dict(baseline[name])
    for d in (m, base_m):             # mAh/day = 횟수 × 시간(h) × 전류(mA), 보수적으로 p90 사용
        d["mah_per_day"] = b["invocations_per_day"] * d["p90_latency_ms"] / 3.6e6 * b["active_current_ma"]
    for key in ["size_kb", "peak_ram_kb", "p90_latency_ms", "mah_per_day"]:
        lim, val = b[key]["max"], m[key]
        delta = val / base_m[key] - 1
        st = "FAIL" if val > lim else "WARN" if (val > 0.95 * lim or delta > 0.03) else "PASS"
        worst = max(worst, st, key=["PASS", "WARN", "FAIL"].index)
        print(f"{name:12s} {key:15s} {val:8.2f} / {lim:7.1f}  margin {1 - val/lim:6.1%}  Δbase {delta:+6.1%}  {st}")
print("overall:", worst); sys.exit(worst == "FAIL")
```

설계 포인트:

- **예산 초과(절대)와 변화량(상대)을 따로 본다.** 절대 예산만 보면 여유가 많은 동안 아무 경고 없이 조금씩 잠식된다(5.2절).

### 5.2 추세와 creep — 직전 PR 대비 게이트의 맹점

PR마다 "직전 대비 +3% 이내면 통과"로 게이트하면, 매번 1~2%씩 나빠지는 변경이 모두 통과한다. 이것을 creep(서서히 기어오름)이라고 한다. SSD 펌웨어에서도 "이번 PR은 IOPS 1% 손해, 괜찮다"가 열 번 쌓이면 릴리스 성능 목표를 놓친다.

무엇을 확인하는 코드인가: PR마다 진짜로 1.2%씩 느려질 때, 직전 PR 대비 게이트(3%)와 릴리스 기준선 대비 게이트(8%) 중 무엇이 잡는가.

```python
# 서서히 느려지기(creep): 직전 PR 대비 게이트는 못 잡고, 릴리스 기준선 대비 게이트는 잡는다
import numpy as np
rng = np.random.default_rng(4)
true = 2.00 * 1.012 ** np.arange(16)                     # PR마다 진짜로 1.2%씩 느려짐 (ms)
meas = true * np.exp(rng.normal(0, 0.006, 16))           # 측정 잡음 0.6% (세션 5번 median 수준)
release = meas[0]
for i in range(1, 16):
    vs_prev = meas[i] / meas[i - 1] - 1
    vs_rel = meas[i] / release - 1
    flag = ("prev>3% " if vs_prev > 0.03 else "        ") + ("REL>8% " if vs_rel > 0.08 else "")
    print(f"PR{i:02d}  {meas[i]:.3f} ms  vs_prev {vs_prev:+.1%}  vs_release {vs_rel:+.1%}  {flag}".rstrip())
print("meas:", " ".join(f"{v:.3f}" for v in meas))
```

### 5.3 모델 버전 bisect — git bisect의 ML 판

`git bisect`는 good 커밋과 bad 커밋 사이를 이분 탐색해서 첫 bad 커밋을 찾는다. 커밋 N개면 log₂N번 테스트로 끝난다. Don이 bring-up에서 펌웨어 버전을 반씩 잘라 가며 버그 도입 시점을 찾던 그 방법이다.

ML에서 두 가지가 다르다.

1. **테스트가 잡음 있다.** 한 번 잘못 판정하면 이분 탐색이 엉뚱한 반쪽으로 가고, 이후 단계는 전부 헛수고다. 단계가 log₂N개라면 각 단계가 모두 맞아야 한다.
2. **"버전"이 여러 축이다.** 코드 커밋만 바뀐 게 아니라 데이터 버전, 양자화 설정, 컴파일러 버전이 함께 바뀌었을 수 있다.

무엇을 확인하는 코드인가: v0(good)~v16(bad) 사이에서 +6%를 만든 v11을 찾을 때, 단계마다 몇 세션을 재야 정답을 찾는가. v5에는 무해한 +1% 변화가 섞여 있다.

```python
# 모델 버전 bisect: v0(good) ~ v16(bad) 사이에서 지연 +6%를 만든 첫 버전 찾기 (진짜 범인 = v11)
import numpy as np
rng = np.random.default_rng(5)
true_ms = np.array([2.0] * 5 + [2.02] * 6 + [2.12] * 6)      # v5에 무해한 +1%, v11에 +6%
def measure(v, k):                                            # 세션 k번의 median (세션 잡음 2%)
    return np.median(true_ms[v] * np.exp(rng.normal(0, 0.02, k)))
def bisect(k, thr=0.03, log=False):
    good, bad, steps = 0, 16, 0
    ref = measure(0, k)
    while bad - good > 1:
        mid = (good + bad) // 2; steps += 1
        r = measure(mid, k) / ref - 1
        if log: print(f"  test v{mid:02d}: {r:+.1%} -> {'bad' if r > thr else 'good'}")
        if r > thr: bad = mid
        else: good = mid
    return bad, steps
print("one run with k=5:"); print("  culprit = v%02d after %d steps" % bisect(5, log=True))
for k in [1, 3, 5, 9]:
    hits = np.mean([bisect(k)[0] == 11 for _ in range(4000)])
    print(f"sessions per step k={k}: P(correct culprit) = {hits:.3f}")
```

```text
one run with k=5:
  test v08: +1.7% -> good
  test v12: +7.0% -> bad
  test v10: +0.2% -> good
  test v11: +6.4% -> bad
  culprit = v11 after 4 steps
sessions per step k=1: P(correct culprit) = 0.391
sessions per step k=3: P(correct culprit) = 0.639
sessions per step k=5: P(correct culprit) = 0.772
sessions per step k=9: P(correct culprit) = 0.901
```

출력에서 볼 것: 16개 버전을 4단계로 좁혔다(log₂16 = 4). 하지만 단계마다 한 세션만 재면 **정답을 찾을 확률이 39%**밖에 안 된다. 9세션씩 재야 90%다. 기준 측정(`ref`)도 잡음이 있어서 모든 단계에 같은 오차가 실린다는 점도 원인이다. 개선책:

- 단계마다 **기준(v0)을 같이, 교대로** 잰다(4.3절). 한 번 잰 `ref`를 재사용하지 않는다.
- 결과가 문턱 근처(예: +2~4%)면 "판정 보류"로 측정을 더 한다. 확실한 단계는 빨리 넘긴다.
- 마지막에 찾은 범인 앞뒤(v10, v11)를 **많이** 재서 확인한다. 이분 탐색 결과 자체를 검증하는 단계다.
- 결정적인 지표(모델 크기, peak RAM 계산값, golden 해시)는 잡음이 없으므로 이런 문제가 없다. 결정적 지표로 먼저 bisect할 수 있으면 그렇게 한다.

여러 축이 섞였을 때는 **한 번에 한 축만 되돌리는 표**를 만든다.

AI Hub API 이름은 F4 8.2절에 정리했고, 공식 API 문서에는 `submit_compile_job`, `submit_profile_job`, `submit_inference_job`, `submit_quantize_job`, `get_devices`, `upload_dataset` 등이 있다. profile·inference job에 넘기는 옵션으로 `--max_profiler_iterations <num>`, `--max_profiler_time <seconds>`, `--compute_unit`(npu, gpu, cpu)이 문서에 나온다. 전력계 두 가지(K3에서 원리를 다뤘다): Monsoon High Voltage Power Monitor는 연속 6 A까지, Main·USB·Aux 채널, Linux·macOS·Windows용 Python API를 제공한다(제조사 페이지). Joulescope JS220은 ±3 A 연속(10 A 펄스), ±15 V, 2 Msps 샘플링, 300 kHz 대역폭, 0.5 nA 분해능이다(제조사 페이지). 둘 다 Python으로 측정 시작·정지를 걸 수 있어서 CI에 붙일 수 있다.

### 6.2 AI Hub를 CI 단계로 쓰는 모양 — 실행하지 않음 (계정 필요)

F4의 API 스케치를 CI 관점으로 감싸면 이렇게 된다. 핵심은 **결과를 우리 형식의 JSON으로 바꿔서 5.1절 체커와 4절 게이트에 넣는 것**이다.

```python
# 실행하지 않음 (계정/API token 필요) — 야간 차선 job의 골격
import json, qai_hub as hub
DEVICES = ["Samsung Galaxy S24 (Family)"]            # get_devices() 결과에서 고정 — 이름 문자열은 확인 필요
def nightly(onnx_path, out_json, sessions=5):
    rows = []
    for name in DEVICES:
        dev = hub.Device(name)
        target = hub.submit_compile_job(model=onnx_path, device=dev,
                                        input_specs=dict(x=(1, 6))).get_target_model()
        for s in range(sessions):                     # 세션을 나눠 제출 = 독립 표본 (4.2절)
            prof = hub.submit_profile_job(model=target, device=dev,
                                          options="--max_profiler_iterations 100").download_profile()
            rows.append({"device": name, "session": s, "raw": prof})   # 키는 저장해 두고 나중에 파싱
    json.dump(rows, open(out_json, "w"), default=str)
```

주의할 점:

- **같은 이름의 기기가 매번 같은 물리 기기라는 보장이 없다.** 기기 이름은 "기종"이다. 결과에 기기 식별 정보가 있으면 같이 저장하고, 기종 안 unit 간 차이(M2 5.4절)를 잡음으로 계산에 넣는다.
- 클라우드 farm의 **열 상태·배경 부하는 우리가 통제하지 못한다.** 그래서 기준 모델을 같은 job 묶음 안에서 교대로 제출한다(4.3절). 절대 숫자보다 **같은 시점의 기준 대비 비율**을 믿는다.
- 외부 서비스는 큐 대기·장애가 있다. 커밋 차선을 여기에 걸면 개발자가 기다린다. **야간 차선**에 두고, 서비스 장애는 FAIL이 아니라 ERROR(infra)로 분류한다(J6 4.5절의 failure/error 구분).
- 모델 파일을 외부로 올리는 것이므로 **보안·IP 정책** 확인이 먼저다.

J6 4.7절의 운영 항목(라벨, 건강 검사, 자동 복구, 격리)에 더해, **측정을 게이트로 쓰기 위한** 규칙:

| 통제 항목 | 왜 | 어떻게 |
|---|---|---|
| device pinning | unit 간 차이(같은 기종이라도 수 %)가 회귀로 보인다 | 기준·후보를 **같은 물리 기기**에서, 같은 job 안에서 교대로 |
| 열 상태 | 온도가 클럭 throttling을 결정한다(K4) | 시작 온도 문턱(예: 배터리 온도가 기준값 근처)까지 대기, 또는 고정 예열 후 측정. 시작·끝 온도를 기록 |
| 클럭·전원 정책 | DVFS governor, 절전 모드, 충전 중 여부가 지연을 바꾼다 | 측정 전 상태를 읽어서 기록하고, 기준과 다르면 측정 거부. 충전 전류가 전력 측정을 오염시키면 USB 전원 분리(전력계 경유 공급) |
| 배경 부하 | 다른 앱, 업데이트, 로그 수집 | 비행기 모드·자동 업데이트 끔 같은 고정 프로필을 매 세션 적용 (adb 명령은 O2) |
| warmup | 첫 실행은 그래프 초기화·캐시 콜드 | 버릴 횟수를 고정하고, warmup 구간도 따로 저장(초기화 시간 회귀도 지표다) |
| 기기 건강 | 배터리 노화, 플래시 마모로 기기가 점점 느려진다 | A/A 기준 측정을 매일 돌려 기기별 추세를 본다. 기준 자체가 움직이면 기기 교체 |

flaky 관리(재시도는 infra error에만, 격리, flake율 추세)는 J6 5.4절을 그대로 쓴다. 지연 게이트에서 하나만 덧붙이면: **재시도해서 통과하면 PASS로 치는 정책은 지연 게이트에서 특히 위험하다.** "FAIL이면 다시 재 보고 PASS면 통과"는 게이트를 두 번 굴려 한 번만 통과하면 되는 것이라서, 과검은 줄지만 미검이 크게 는다. 다시 잴 거면 처음부터 세션 수를 늘린 게이트(L3·L4)로 설계한다.

## 7. 모델·데이터 버전과 재현성 — manifest

### 7.1 무엇을 고정하나

H5 4절에서 데이터셋 버전 관리(불변 snapshot, content hash, registry, DVC)를 다뤘다. 여기서는 그 위에 얹는 **모델 릴리스 manifest**만 본다. 질문은 하나다: "CI가 테스트한 것이 정확히 무엇이었나, 그리고 그것을 다시 만들 수 있나?"

| 개념 | 하는 일 | 대표 도구 (개념만) |
|---|---|---|
| 큰 파일 포인터 | git에는 작은 포인터만, 실제 바이트는 별도 저장소 | git-lfs, DVC |
| 데이터·파이프라인 버전 | 데이터 파일과 처리 단계를 해시로 추적, 단계 재실행 | DVC |
| 모델 registry | 모델 이름 → 버전 번호 → 별칭(예: `champion`, `production`) → 산출물·메타데이터 | MLflow Model Registry (`models:/<name>@<alias>` URI) |
| manifest | 한 릴리스의 모든 입력·산출물 해시와 툴체인 버전을 담은 파일 | 직접 만드는 JSON (아래) |

registry의 **별칭(alias)**은 펌웨어 쪽의 "릴리스 브랜치 태그"와 같다. 기기 배포 스크립트는 버전 번호가 아니라 별칭을 보고, 승격은 별칭을 옮기는 것으로 한다. 롤백도 별칭을 되돌리면 된다.

### 7.2 manifest 만들기와 검증

무엇을 확인하는 코드인가: 산출물 해시와 환경 버전을 manifest에 적고, CI가 테스트 전에 파일과 대조해서 몰래 바뀐 파일을 잡는지.

```python
# 모델 릴리스 manifest: 산출물 해시 + 만든 환경 버전. CI는 테스트 전에 manifest와 실제 파일을 대조한다
import hashlib, json, platform, numpy, torch, onnxruntime
def sha(p): return hashlib.sha256(open(p, "rb").read()).hexdigest()[:16]
files = ["model_v1.pt", "golden_v1.npz", "budgets.yaml"]
manifest = {"model": "gesture", "version": "1.3.0", "dataset": "imu-gestures@v17",
            "train_commit": "<git rev-parse HEAD>", "quant": {"weights": "int8 per-channel", "act": "int8 static"},
            "toolchain": {"python": platform.python_version(), "numpy": numpy.__version__,
                          "torch": torch.__version__, "onnxruntime": onnxruntime.__version__},
            "files": {f: sha(f) for f in files}}
json.dump(manifest, open("manifest.json", "w"), indent=1)
print(json.dumps(manifest["files"]), manifest["toolchain"])
def verify(m):
    bad = [f for f, h in m["files"].items() if sha(f) != h]
    return "OK" if not bad else f"MISMATCH {bad}"
print("verify:", verify(manifest))
open("budgets.yaml", "a").write("# someone edited a limit locally\n")
print("verify after edit:", verify(json.load(open("manifest.json"))))
```

```text
{"model_v1.pt": "7ea371e677710ebb", "golden_v1.npz": "5ff8650cc8befb9c", "budgets.yaml": "5e99f1dd8c9d7f75"} {'python': '3.9.6', 'numpy': '2.0.2', 'torch': '2.8.0', 'onnxruntime': '1.19.2'}
verify: OK
verify after edit: MISMATCH ['budgets.yaml']
```

출력에서 볼 것: 주석 한 줄만 추가해도 해시가 바뀌어 잡힌다. 해시는 앞 16자리만 보여 주려고 잘랐다(실제로는 전체 64자리를 저장한다). 툴체인 버전이 manifest에 들어간 이유는 5.3절 표의 "컴파일러만 되돌림" 실험을 하려면 그 버전을 알아야 하기 때문이다.

manifest 운영 규칙:

- CI의 **첫 단계**에서 manifest 검증을 한다. 불일치면 나머지 테스트를 돌리지 않는다(잘못된 물건을 측정하는 것은 낭비다).
- 기기에 배포되는 바이너리 안에도 모델 해시를 넣고, 기기가 부팅 로그·텔레메트리로 보고하게 한다(J5·H1). 그래야 필드 문제를 manifest와 연결할 수 있다.
- "다시 만들 수 있나"는 정기적으로 **실제로 다시 만들어 본다.** 6개월 전 manifest로 재학습·재양자화해서 golden 해시나 정확도가 재현되는지 본다(H5 7.3절 체크리스트). 학습은 GPU 비결정성 때문에 bit-exact 재현이 어려울 수 있으니, 재현 기준(정확도 ± 얼마)을 정해 둔다. 양자화·컴파일 단계는 같은 입력이면 bit-exact를 기대한다.

## 8. 임베디드 관점에서 다시 보기

### 8.1 on-target 테스트 — SSD 펌웨어 검증과 같은 구조

모델 저장소의 CI가 아무리 좋아도 **기기 펌웨어 안의 추론 경로**가 같은 답을 내는지는 따로 확인해야 한다. 펌웨어의 전처리(고정소수점 특징 추출), 메모리 배치(arena), 벤더 커널이 모두 다르기 때문이다. 구조는 Don이 SSD에서 하던 것과 같다.

| SSD 펌웨어 검증 | ML on-target 검증 |
|---|---|
| host 시뮬레이터에서 FTL 알고리즘 unit test | host 빌드에서 int8 커널 golden test (아래 C 예제) |
| FPGA·EVB에서 같은 테스트를 펌웨어로 | 실보드에서 같은 golden 벡터, UART·RTT로 결과 회수 (C8 7.1절, J6 4절 HIL) |
| 랙의 장시간 회귀 + 성능 QoS | farm의 지연·전력 세션 측정 (4·6절) |
| 릴리스 전 margin sign-off 리포트 | 예산 표 + 정확도 비열등 판정 + 사람 리뷰 (3·5절) |

### 8.2 C golden-vector harness — 실패 수를 종료 코드로

펌웨어 unit test처럼, int8 커널 출력을 기대 배열과 비교하고 **실패 수를 종료 코드로** 돌려주는 harness다. CI는 종료 코드만 보면 된다. 기대값은 float64 레퍼런스로 따로 계산했다.

```python
# C harness용 기대값: int8 dense + requant(scale 0.0123, round-half-away) — float64 레퍼런스
import numpy as np
W = np.array([[12, -7, 33, 5], [-128, 64, 0, 9], [127, 127, -3, -90]], np.int32)
B = np.array([100, -2000, 37], np.int32)
X = np.array([[10, -20, 30, -40], [127, 127, -128, 0], [0, 0, 0, 0]], np.int32)
acc = X @ W.T + B
y = np.clip(np.sign(acc) * np.floor(np.abs(acc) * 0.0123 + 0.5), -128, 127).astype(int)
print("acc =", acc.tolist()); print("y   =", y.tolist())
```

```text
acc = [[1150, -4920, 2277], [-3489, -10128, 32679], [100, -2000, 37]]
y   = [[14, -61, 28], [-43, -125, 127], [1, -25, 0]]
```

손으로 첫 행을 확인하면: acc₀ = 10·12 + (−20)·(−7) + 30·33 + (−40)·5 + 100 = 120 + 140 + 990 − 200 + 100 = 1150. 1150 × 0.0123 = 14.145 → 14. 둘째 출력은 −4920 × 0.0123 = −60.516 → −61. 32679 × 0.0123 = 401.95라서 127로 saturation된다.

C 쪽 requant는 scale 0.0123을 **Q31 multiplier + shift**로 표현한다. 0.0123 = 0.7872 × 2⁻⁶이고, 0.7872 × 2³¹ ≈ 1,690,499,128이다(C1·J3의 requantization 형식).

```c
/* golden_harness.c — int8 dense + Q31 requant 커널을 golden 벡터와 비교. 실패 수를 exit code로 (CI용) */
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#define NI 4
#define NO 3
static const int8_t  W[NO][NI] = {{12, -7, 33, 5}, {-128, 64, 0, 9}, {127, 127, -3, -90}};
static const int32_t B[NO] = {100, -2000, 37};
static const int32_t M = 1690499128;   /* 0.7872 in Q31 */
static const int SHIFT = 6;            /* 0.7872 / 2^6 = 0.0123 */
static int8_t requant(int32_t acc) {
    int64_t p = (int64_t)acc * M;
    int64_t mag = p < 0 ? -p : p;
#ifdef BUG_TRUNCATE
    mag >>= 31 + SHIFT;                                    /* 반올림 없이 버림 */
#else
    mag = (mag + ((int64_t)1 << (30 + SHIFT))) >> (31 + SHIFT);  /* half away from zero */
#endif
    int64_t y = p < 0 ? -mag : mag;
    return (int8_t)(y > 127 ? 127 : y < -128 ? -128 : y);
}
static void dense(const int8_t *x, int8_t *y) {
    for (int o = 0; o < NO; o++) {
        int32_t acc = B[o];
        for (int i = 0; i < NI; i++) acc += (int32_t)x[i] * W[o][i];
        y[o] = requant(acc);
    }
}
static const int8_t X[3][NI]   = {{10, -20, 30, -40}, {127, 127, -128, 0}, {0, 0, 0, 0}};
static const int8_t EXP[3][NO] = {{14, -61, 28}, {-43, -125, 127}, {1, -25, 0}};
int main(int argc, char **argv) {
    int tol = argc > 1 ? atoi(argv[1]) : 0, fails = 0;     /* 허용 LSB (기본 0 = bit-exact) */
    for (int v = 0; v < 3; v++) {
        int8_t y[NO]; dense(X[v], y);
        for (int o = 0; o < NO; o++) {
            int d = y[o] - EXP[v][o];
            if (abs(d) > tol) { printf("FAIL vec%d out%d got %d exp %d (diff %+d)\n", v, o, y[o], EXP[v][o], d); fails++; }
        }
    }
    printf("%s: %d mismatches (tol=%d LSB)\n", fails ? "FAIL" : "PASS", fails, tol);
    return fails ? 1 : 0;
}
```

```sh
cc -std=c11 -Wall -Wextra -O2 golden_harness.c -o gh && ./gh; echo "exit=$?"
cc -std=c11 -Wall -Wextra -O2 -DBUG_TRUNCATE golden_harness.c -o gh_bug && ./gh_bug; echo "exit=$?"
./gh_bug 1; echo "exit=$?"
```

```text

exit=0
FAIL vec0 out1 got -60 exp -61 (diff +1)
FAIL vec1 out0 got -42 exp -43 (diff +1)
FAIL vec1 out1 got -124 exp -125 (diff +1)
FAIL vec2 out1 got -24 exp -25 (diff +1)
FAIL: 4 mismatches (tol=0 LSB)
exit=1
PASS: 0 mismatches (tol=1 LSB)
exit=0
```

(두 빌드 모두 경고 0개.) 출력에서 볼 것:

- 정상 커널은 float64 레퍼런스와 bit-exact다. Q31 근사가 이 벡터들에서는 반올림 경계를 넘지 않았다. 경계 근처 값(x.5 근처)을 일부러 넣은 벡터를 추가하면 Q31 근사와 float 레퍼런스가 갈릴 수 있으므로, 기대값은 **배포 규격과 같은 정수 연산**으로 만드는 것이 원칙이다(C8 3.4절).
- 반올림을 빼먹은 버그는 **음수 출력에서만** 틀린다. 크기를 버리면 음수는 0 쪽으로 가서 항상 +1 쪽으로 틀린다. 양수 14.145 → 14처럼 우연히 맞는 값도 많다. golden 벡터에 **음수와 경계값을 일부러 넣어야** 하는 이유다.
- `tol=1`로 돌리면 같은 버그가 PASS다. 그런데 4개 오차가 **모두 +1**이다. 무작위 ±1이 아니라 한쪽으로 치우친 오차는 버그의 지문이다. 1 LSB tolerance를 허용하더라도 **오차의 평균(bias)이 0 근처인지**를 함께 검사해야 한다. 치우친 1 LSB는 레이어를 거치며 누적된다.

이 harness는 host에서는 CI 커밋 차선에서, 타깃에서는 같은 소스를 cross 빌드해 HIL 차선에서 돈다(J6 0.4절의 "한 소스, 여러 빌드").

### 8.3 메모리·크기 예산은 빌드 산출물에서 결정적으로

peak RAM과 모델 크기는 대부분 **측정이 아니라 계산**으로 얻을 수 있다. map 파일의 섹션 크기, 런타임의 arena 크기 요구량(TFLM의 arena 사용량 보고 등, F2), 모델 파일 크기. 결정적이므로 5.1절 체커의 문턱 하나로 충분하고, 커밋 차선에 둔다. 실기기가 필요한 것은 지연·전력·열이다. 이렇게 **결정적인 것과 확률적인 것을 분리**하는 것이 ML CI 설계의 절반이다.

|---|---|---|---|
| golden을 CI가 자동 재생성 | golden 테스트가 한 번도 실패하지 않음 | 기대값이 매번 현재 출력으로 덮어써짐 | golden은 릴리스에서만, 리뷰를 거쳐 갱신. 갱신 PR은 따로 |
| int8 출력을 allclose로 비교 | 1 LSB 버그가 통과, 레이어 거치며 누적 | 정수 결과에 float tolerance | int8은 exact. tolerance가 필요하면 bias 검사 추가 (8.2절) |
| 정확도 숫자 두 개만 저장 | 0.3%p drop이 진짜인지 판정 불가 | 샘플별 결과 없음 | 샘플별 예측 저장, McNemar·paired CI (3.2절) |
| 단순 문턱 게이트 0.5%p | 매일 거짓 FAIL, 사람들이 무시 | churn에 의한 흔들림을 무시 | 허용 한계 + 신뢰구간 상한(비열등), n 역산 (3.3절) |
| 한 세션 1000회 반복에 검정 | p < 0.01인데 과검 15% 이상 | 반복이 세션 효과를 공유해서 독립이 아님 | 세션을 표본 단위로, 5회 이상 교대 (4.2절) |
| 기준을 먼저 다 재고 후보를 나중에 | 같은 모델인데 +3% "회귀" | 열 drift | ABAB 또는 ABBA 교대, 냉각·예열 규칙 (4.3절) |
| 직전 PR 대비만 비교 | 릴리스 직전에 20% 느려진 걸 발견 | creep | 릴리스 기준선 대비 비교 + ratchet (5.2절) |
| 지난주 기준 숫자와 오늘 후보 비교 | 기기 OS 업데이트 후 모든 PR이 FAIL | 환경이 바뀜 | 기준 모델을 매번 같은 기기에서 같이 측정 |
| 지연 게이트 FAIL을 재시도로 통과 | 진짜 회귀가 릴리스까지 감 | 두 번 굴려 한 번 통과 = 미검 증가 | 처음부터 세션 수를 늘린 게이트로 설계, 재시도는 infra error만 |
| manifest 없이 "v1.4" 이름만 | 회귀 bisect 때 무엇이 바뀌었는지 모름 | 데이터·툴체인 버전 미기록 | 해시·버전 manifest, CI 첫 단계에서 검증 (7절) |

## 10. 면접에서 이렇게 말한다

**Q.** "How would you set up CI for an on-device ML model?"

**A.** 싸고 결정적인 것을 앞에, 비싸고 확률적인 것을 뒤에 둔다. 커밋마다 host에서 전처리 unit test, op parity, golden(float은 tolerance, int8은 bit-exact), 성질 테스트, 크기·RAM 예산을 돈다. 모델이 바뀌면 고정 test set 정확도를 비열등 판정으로, 야간에는 실기기 farm에서 기준 모델과 교대로 지연·메모리를 잰다. 릴리스에는 전력·열과 사람 리뷰. 모든 입력은 manifest 해시로 고정한다.

> I split it by cost and determinism. Every PR runs host-side tests: preprocessing unit tests, op-level parity against a reference, golden tests — tolerance for float, bit-exact for int8 — property tests like batch invariance, and size/RAM budgets from the build. Model changes trigger a fixed-test-set accuracy check with a non-inferiority gate. Nightly, we measure latency and memory on real devices, interleaving the baseline and the candidate on the same pinned device. Power, thermal and a human sign-off happen at release. Every artifact is pinned by a hashed manifest.

**Q.** "Accuracy dropped by 0.4 points on the regression set. Do you block the release?"

**A.** 숫자만으로는 모른다. 샘플별로 짝지어 엇갈린 샘플 b와 c를 보고 McNemar나 paired CI를 낸다. 판정 기준은 미리 정한 허용 한계(예: 1%p) 대비 신뢰구간 상한이다. 상한이 한계 안이면 통과, 하한이 한계 밖이면 차단, 걸치면 데이터를 늘리거나 리뷰. 클래스·사용자별 breakdown도 본다.

> It depends on the evidence, not the point estimate. I'd look at the paired predictions — how many samples flipped each way — and compute a McNemar test or a paired confidence interval. Our gate is defined against a pre-agreed margin, say one point: if the upper bound of the drop is inside the margin we ship, if the lower bound is outside we block, and if the interval straddles it we either add data or escalate for review. I'd also check per-class and per-user breakdowns, because an average can hide one class collapsing.

**Q.** "Your latency regression tests are flaky. How do you fix them?"

**A.** 먼저 A/A 테스트로 과검률을 잰다. 흔한 원인은 한 세션 안의 반복을 독립 표본으로 쓰는 것, 열 drift, 기기 간 차이다. 세션을 여러 번 나눠 교대로 재고, 같은 물리 기기에 pinning하고, warmup을 버리고, median과 세션 단위 검정에 최소 효과 크기 조건을 붙인다. 재시도로 통과시키는 것은 미검을 늘리므로 infra error에만 쓴다.

> First I measure the false-alarm rate directly with A/A runs. The usual culprits are treating iterations within one session as independent samples, thermal drift, and unit-to-unit variation. So we measure several independent sessions, interleave baseline and candidate on the same pinned device, discard warmup, and gate on session medians with a rank test plus a minimum effect size. Retrying until it passes just trades false alarms for misses, so retries are only for infrastructure errors.

**Q.** "How would you use something like Qualcomm AI Hub in your pipeline?"

**A.** 칩이 책상에 없거나 여러 Snapdragon 기종을 비교할 때 야간 차선에 둔다. 후보를 compile하고 profile job을 세션 여러 번으로 나눠 제출해서 지연·peak memory·compute unit(NPU fallback 여부)을 받는다. 기준 모델을 같은 묶음에서 같이 제출하고 비율로 판정한다. 우리 보드의 센서 경로나 전력은 못 재므로 그건 사내 랙에서 한다. 서비스 장애는 FAIL이 아니라 infra error로 분류한다.

> I'd put it in the nightly lane, for targets we don't have on our bench or to compare Snapdragon tiers. The job compiles the candidate, submits several profile sessions, and pulls back latency, peak memory and which compute unit each op landed on, so we catch CPU fallbacks. The baseline goes in the same batch and we gate on the ratio, not the absolute number. It can't see our sensor path or measure battery current, so those stay on our in-house rack, and a hosted-service outage is classified as an infra error rather than a test failure.

**Q.** "Latency crept up 20% over a quarter and nobody noticed. What went wrong and how would you find the cause?"

**A.** 직전 PR 대비로만 게이트해서 creep를 놓쳤다. 릴리스 기준선 대비 비교와 추세 대시보드로 고친다. 원인 찾기는 버전 bisect인데, 측정이 잡음 있으니 단계마다 기준과 교대로 여러 세션을 재고, 문턱 근처는 판정을 보류해서 더 잰다. 축이 여러 개면 컴파일러·양자화·데이터를 하나씩 되돌리는 실험표를 만든다. 이게 가능하려면 manifest가 있어야 한다.

> The gate compared each PR to the previous one, so small regressions accumulated. The fix is to compare against the last release baseline and plot the trend with budget lines. To find the cause I'd bisect across model versions, but with noisy measurements each step needs several interleaved sessions against the baseline, and borderline results get re-measured instead of decided. If multiple axes changed — compiler, quantization config, data — I'd revert one axis at a time, which only works if each build has a manifest pinning those versions.

## 11. 직접 해보기

1. (손계산) `rtol=1e-4, atol=1e-6`일 때 desired = 0.5에서 허용되는 최대 차이는? desired = 0에서는? 정답: 0.5에서 1e-6 + 5e-5 = 5.1e-5, 0에서 1e-6.
2. (손계산) n = 5000, 두 모델이 엇갈린 샘플이 b = 30, c = 10이다. drop은 몇 %p이고, McNemar 단측 p 값은 대략 어느 정도인가(정규근사 z = (b − c)/√(b + c))? 정답: drop = 20/5000 = 0.4%p, z = 20/√40 ≈ 3.16, 단측 p ≈ 0.0008.
3. (코드) ex7을 고쳐 G3의 margin을 1.0%p로 두고 "진짜 drop 0일 때 FAIL ≤ 1%"를 만족하는 최소 n을 찾아라(n = 2000, 3000, 4000, … 순서로). 힌트: 과검은 대략 P(Z > (margin − 1.645·SE)/SE)이고 SE ≈ √(churn·n)/n이므로, 1.0%p ≥ (1.645 + 2.33)·√(0.03/n) 근처에서 만족한다. 손으로 풀면 n ≈ 4,700.
4. (코드) ex8의 L2를 반복 25회 대신 200회로 바꿔 과검이 어떻게 변하는지 보고 이유를 한 문장으로 써라. 정답: 과검이 오히려 늘어난다. 반복을 늘리면 p 값만 작아지고 세션 효과 차이는 그대로라 "세션 차이"를 더 확신 있게 회귀로 판정한다.
5. (코드) `golden_harness.c`에 bias 검사를 추가하라: 전체 출력의 (got − exp) 합이 0이 아니고 모든 오차의 부호가 같으면, tol 안이어도 FAIL. `-DBUG_TRUNCATE`와 `tol=1`에서 FAIL이 나와야 한다. 힌트: 오차 합 = +4, 양수 개수 4, 음수 개수 0.
6. (설계) Hark 같은 웨어러블의 wake word 모델에 대해 budgets.yaml 항목을 정해 보라: 무엇을 커밋 차선에서 결정적으로 보고, 무엇을 야간 farm에서 통계로 보고, 무엇을 릴리스에서 사람이 보는가. 힌트: 크기·arena = 커밋, 지연·peak RAM 실측 = 야간, mAh/day·FA/h·열 = 릴리스.

## 12. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| golden test | 기준 출력 비교 테스트 | 릴리스 때 구운 기대 출력과 현재 출력을 비교 |
| rtol / atol | 상대·절대 허용 오차 | abs(a − d) ≤ atol + rtol·abs(d) 의 두 계수 |
| bit-exact | 비트 단위 일치 | 정수 커널·같은 규격이면 기대할 수 있는 수준 |
| property test | 성질 테스트 | 정답 대신 항상 성립할 규칙을 무작위 입력으로 검사 |
| fixture | pytest 준비물 | 테스트 인자 이름으로 주입되는 공유 자원 |
| parametrize | 매개변수화 | 같은 테스트를 설정 조합마다 반복 |
| churn | 예측 엇갈림 | 두 모델의 정답 여부가 다른 샘플 비율 |
| McNemar test | 짝 비교 검정 | 엇갈린 샘플 b, c만으로 두 분류기 차이를 검정 |
| non-inferiority | 비열등 | "허용 한계보다 나쁘지 않다"를 신뢰구간 상한으로 판정 |
| false alarm / miss | 과검 / 미검 | 좋은 후보를 막음 / 나쁜 후보를 통과시킴 |
| Mann–Whitney U | 순위 검정 | 한 그룹이 다른 그룹보다 큰 경향을 순위로 검사 |
| session | 측정 세션 | 기기 상태를 새로 잡고 재는 독립 단위 |
| interleaving / ABBA | 교대 측정 | drift를 상쇄하도록 기준·후보 순서를 섞음 |
| A/A test | 같은 것끼리 비교 | 게이트의 과검률을 직접 재는 방법 |
| creep | 서서히 악화 | 작은 회귀가 PR마다 쌓임 |
| ratchet baseline | 톱니 기준선 | 좋아질 때만 움직이는 고정 기준선 |
| device pinning | 기기 고정 | 비교 대상을 같은 물리 기기에서 측정 |
| manifest | 산출물 명세 | 해시·버전으로 릴리스 입력·출력을 고정한 파일 |

## 13. 요약 & 체크리스트

ML CI는 펌웨어 CI의 뼈대(커밋·야간·릴리스 차선, golden, 랙)를 그대로 쓰되, 네 가지를 더한다. 모델·데이터·툴체인을 해시로 고정하는 manifest, 결정적인 것(int8 커널, 크기·RAM 계산)과 확률적인 것(정확도, 지연, 전력)의 분리, 확률적인 것을 판정하는 통계 게이트(허용 한계 대비 신뢰구간 상한, 세션 단위 교대 측정), 그리고 실기기 farm(클라우드 AI Hub·폰 farm, 사내 랙)과 그 측정 프로토콜이다. 게이트는 과검과 미검을 둘 다 내므로, 시뮬레이션이나 A/A 테스트로 두 오류율을 숫자로 알고 설계해야 한다. 비교 기준은 직전 PR이 아니라 릴리스 기준선이고, 회귀가 나면 축별로 되돌리며 bisect한다.

- [ ] `assert_allclose`의 판정식을 쓰고, rtol만 쓸 때 0 근처에서 생기는 문제를 손으로 보일 수 있다
- [ ] fixture·parametrize·marker로 golden(float tol, int8 exact), op parity, 성질 테스트를 pytest로 짤 수 있다
- [ ] batch invariance 같은 성질 테스트가 golden이 놓치는 버그를 잡는 이유를 설명할 수 있다
- [ ] 2×2 짝 표에서 b, c로 drop과 McNemar p 값을 계산할 수 있다
- [ ] 단순 문턱·유의성·비열등 게이트의 과검·미검 차이를 시뮬레이션 결과로 설명할 수 있다
- [ ] 지연 측정에서 반복이 아니라 세션이 독립 단위인 이유와, ABBA 교대가 drift를 상쇄하는 이유를 말할 수 있다
- [ ] 지연·호출 빈도·전류로 mAh/day를 손계산하고 budgets.yaml 체커를 만들 수 있다
- [ ] creep를 막는 기준선 정책과, 잡음 있는 측정에서의 bisect 전략을 설명할 수 있다
- [ ] AI Hub·Firebase Test Lab·AWS Device Farm·사내 랙의 용도와 한계를 비교할 수 있다
- [ ] 모델 manifest에 넣을 항목을 말하고 CI 첫 단계에서 검증하게 만들 수 있다
