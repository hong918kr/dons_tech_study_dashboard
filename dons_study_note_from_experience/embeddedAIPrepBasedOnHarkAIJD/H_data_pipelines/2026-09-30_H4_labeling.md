## 0. 큰 그림 — 라벨링이 왜 병목인가

### 0.1 "IMU판 ImageNet"은 없다

이미지 분류를 공부하면 ImageNet(사람이 라벨을 붙인 사진 100만 장 이상)이 늘 등장한다. 음성 인식에도 공개 corpus가 여럿 있다. 그런데 **손목 IMU 제스처**, **귀에 건 기기의 착용 감지**, **우리 제품 이름으로 된 wake word** 같은 과제에는 그런 데이터셋이 없다. 이유는 셋이다.

1. **센서가 제품마다 다르다.** IMU 칩, 장착 위치(손목·귀·목걸이), 축 방향, ODR, full-scale range가 다르면 같은 "탭"도 다른 파형이 된다. 남의 데이터셋을 그대로 쓰기 어렵다.
2. **사람이 raw 신호를 보고 정답을 알 수 없다.** 사진은 보면 고양이인지 안다. 그러나 3축 가속도 곡선만 보고 "이게 손목 들기인지 컵 들기인지"를 사람이 맞히기는 거의 불가능하다. 그래서 **라벨은 센서 밖의 증거**(영상, 앱 프롬프트, 기준 기기, 사용자 자기보고)에서 와야 한다.
3. **정답이 시간 구간이다.** "1.20 s ~ 1.45 s에 탭" 같은 라벨은 시계가 맞아야 쓸 수 있다 (G7). 시각이 틀리면 라벨이 엉뚱한 샘플에 붙는다.

말로 하면: 모델 구조는 논문에서 가져올 수 있지만, **우리 기기의 라벨 데이터는 우리가 만들어야 한다.** 그래서 edge ML 팀에서 "데이터 수집 + 라벨링 파이프라인"은 모델 코드만큼, 때로는 그 이상으로 일이 많다.

Don에게 익숙한 말로 하면: SSD 펌웨어 검증에서 "이 로그가 pass인지 fail인지"를 판정하는 **golden reference**가 없으면 아무리 많은 로그를 모아도 쓸모가 없다. 라벨이 ML의 golden reference다. 그리고 ML에서는 그 golden reference 자체가 사람 손으로 만들어져서 **틀릴 수 있다**는 점이 다르다.

### 0.3 이 노트의 데이터에 대해

이 노트의 모든 숫자는 **합성(synthetic) 데이터**로 만든 것이다. 실제 제품 데이터가 아니다. 합성 데이터의 장점은 **진짜 정답을 우리가 안다**는 것이다. 그래서 "라벨이 20% 틀리면 정확도가 얼마나 떨어지나" 같은 질문에 정확히 답할 수 있다. 실전에서는 진짜 정답을 모르므로, 같은 실험을 "깨끗하게 다시 라벨한 작은 세트"로 흉내 낸다. 숫자의 크기는 과제마다 다르고, **경향**을 가져가는 것이 목적이다.

## 1. 라벨의 종류와 스키마 설계

### 1.1 라벨은 다섯 가지 모양이 있다

먼저 용어 하나. **ground truth**는 "모델이 맞혀야 하는 진짜 정답"이다. 라벨은 우리가 ground truth라고 믿고 붙인 값이다. 둘은 같지 않을 수 있다.

| 라벨 종류 | 모양 | 예 (웨어러블이라면) | 누가·무엇으로 붙이나 | 모델 출력 |
|---|---|---|---|---|
| 창 클래스 (per-window class) | 창 i → 클래스 1개 | 2 s 창: still / walk / run | scripted session, 구간 라벨에서 변환 | softmax K개 |
| 이벤트 구간 (onset/offset) | (label, start, end) 목록 | 탭 1.20 ~ 1.45 s | 영상 보고 수동, 앱 버튼 | 프레임별 확률 → 이벤트 |
| 연속값 (continuous target) | 시각마다 실수 | 심박 72 bpm, 걸음 속도 | 기준 기기 (chest strap, 트레드밀) | 회귀 |
| 시퀀스 전사 (transcript) | 오디오 → 문자열 | "hey hark, what time is it" | 사람 받아쓰기, ASR 초벌 + 수정 | CTC/RNN-T 등 (B5) |
| 키워드 timestamp | (단어, start, end) | "hey hark" 0.42 ~ 0.98 s | forced alignment + 확인 | KWS 검출 시점 |

말로 하면: **모델 출력 모양이 라벨 모양을 정한다.** 이벤트 검출기를 만들 거면 창 클래스만 모아서는 부족하고 onset/offset이 필요하다. 반대로 창 분류기를 만들 거면 구간 라벨을 모은 뒤 §3의 규칙으로 창 라벨로 바꾼다. 구간 라벨이 정보가 더 많으므로, **헷갈리면 구간으로 모으고 나중에 줄여라.** 반대 방향(창 라벨 → 정확한 구간)은 정보가 없어서 불가능하다.

### 1.2 스키마 — taxonomy, unknown, null 클래스

**라벨 스키마(label schema)** 는 "어떤 라벨 값이 존재하고 각각 무엇을 뜻하는가"를 적은 명세다. 펌웨어의 레지스터 맵 문서와 같다. 비트 의미를 문서 없이 바꾸면 사고가 나듯, 라벨 의미를 문서 없이 바꾸면 데이터셋이 조용히 망가진다.

설계할 때 결정할 것:

| 결정 | 선택지 | 권장 (예) |
|---|---|---|
| 계층 (taxonomy) | 평평한 목록 vs 계층 (gesture → tap → single/double) | 계층으로 모으고 학습 때 필요한 수준으로 접기 |
| null 클래스 | "아무 이벤트 아님" 클래스를 둘까 | 반드시 둔다. 실제 시간의 대부분은 null이다 |
| unknown / other | "뭔가 했는데 목록에 없음" | 둔다. 억지로 가까운 클래스에 넣으면 noise가 된다 |
| ignore / unsure | 라벨러가 확신 못 함, 센서 오류 구간 | 둔다. 학습·평가에서 제외할 수 있게 |
| 상호배타 여부 | 한 시각에 라벨 1개 vs 여러 개 (걷기 + 말하기) | 다중 라벨이면 축별로 분리된 스키마 |
| 정의 문서 | 경계 정의, 애매한 사례 사진·영상 | "탭 시작 = 손가락이 닿기 직전 가속 시작" 처럼 구체적으로 |
| 버전 | `gesture-v1`, `gesture-v2` | 라벨 파일마다 스키마 버전 기록 (§9) |

**null 클래스**와 **unknown**은 다르다. null은 "확실히 관심 이벤트가 아님"(앉아서 타이핑 중), unknown은 "관심 이벤트 같긴 한데 정의된 클래스 중 무엇인지 모름"이다. wake word로 치면 null은 일반 대화, unknown은 "hey hark인지 hey harp인지 애매함"이다.

함정: unknown이 없으면 라벨러가 애매한 사례를 **가장 비슷한 클래스에 억지로 넣는다.** 이것이 §4에서 다룰 라벨 noise의 가장 흔한 원인이다. 반대로 unknown 비율이 20%를 넘기 시작하면 스키마 정의가 부족하다는 신호다.

### 1.3 손으로 해 보기 — 스키마 하나 써 보기

예를 들어 Hark 같은 웨어러블이라면(추정) 손목 제스처 과제의 스키마를 이렇게 쓸 수 있다.

```text
schema: gesture-v2   (2026-09-30)
labels:
  null          관심 제스처 없음 (일상 동작 전부 포함)
  tap           손가락으로 기기 표면 1회 두드림. 시작 = 충격 직전 가속 상승, 끝 = 진동 감쇠 50 ms 후
  double_tap    tap 2회, 간격 ≤ 400 ms. 400 ms 초과면 tap 2개
  wrist_raise   팔을 들어 화면을 보는 동작. 시작 = pitch 변화 시작, 끝 = 정지
  unknown       제스처로 보이나 위 정의에 안 맞음
  ignore        센서 오류, 영상 가림, 동기화 불확실
changes from v1: v1의 "tap"을 tap / double_tap으로 분리
```

여기서 볼 것: 경계(시작·끝)의 정의가 문장으로 있다. 경계 정의가 없으면 라벨러 A는 "충격 순간"을, B는 "손이 움직이기 시작한 순간"을 시작으로 찍어서 같은 이벤트에 100 ms 이상 차이가 난다. §4의 kappa로 재면 이 차이가 숫자로 드러난다.

## 2. 수집 프로토콜 — 라벨은 "모을 때" 같이 만든다

가장 싼 라벨은 **녹음하는 순간에 자동으로 생기는 라벨**이다. 나중에 사람이 영상을 보며 붙이는 라벨은 데이터 1분당 수 분이 든다(§9). 그래서 프로토콜 설계의 목표는 "사후 수동 라벨을 최소화"다.

### 2.1 Scripted session — 앱이 지시하고, 지시 시각이 라벨이 된다

**scripted session**은 참가자에게 정해진 동작을 정해진 순서로 시키는 수집 방식이다. 폰 앱이 "지금 탭을 10번 하세요"라고 화면에 띄우고, 프롬프트를 띄운 시각과 내린 시각을 로그로 남긴다. 그 시각이 곧 구간 라벨이 된다.

```
시간 →   0s        4s                      14s       18s ...
앱      [ 휴식 ]   [ "탭 10번 하세요" ON ]  OFF       [ "손목 들기" ON ] ...
참가자   가만히     ↑0.6s 늦게 시작 … 탭탭탭 …  ↑끝      ↑반응 지연 …
라벨     rest      ignore | tap ........... | ignore   rest ...
```

주의할 점은 **사람은 프롬프트에 바로 반응하지 않는다**는 것이다. 수백 ms의 반응 지연이 있고, 끝날 때도 프롬프트가 꺼지기 전에 멈추곤 한다. 그래서 구간 앞뒤에 **ignore 여유**를 둔다.

**예제 1.** 이 코드는 앱 프롬프트 로그(가짜)를 (label, start, end) 구간 표로 바꾸고, 앞 0.6 s·뒤 0.3 s를 ignore로 떼어 낸다.

```python
import pandas as pd
# 앱이 남긴 scripted session 로그 (가짜). t = 기기 시간축으로 이미 변환된 시각 [s] (G7)
log = pd.DataFrame({
    "t":     [0.0, 4.0, 14.0, 18.0, 28.0, 32.0, 40.5, 44.0],
    "event": ["start", "on", "off", "on", "off", "on", "off", "end"],
    "label": [None, "tap", None, "wrist_raise", None, "tap", None, None]})
REACT, TAIL = 0.6, 0.3          # 사람 반응 지연, 끝부분 여유 [s]

rows, prev = [], log.t.iloc[0]
for (_, on), (_, off) in zip(log[log.event == "on"].iterrows(),
                             log[log.event == "off"].iterrows()):
    rows += [("rest", prev, on.t),                               # 프롬프트 사이 = 휴식
             ("ignore", on.t, on.t + REACT),                      # 반응 지연 구간
             (on.label, on.t + REACT, off.t - TAIL),
             ("ignore", off.t - TAIL, off.t)]
    prev = off.t
rows.append(("rest", prev, log.t.iloc[-1]))
iv = pd.DataFrame(rows, columns=["label", "start", "end"])
iv["dur"] = iv.end - iv.start
print(iv.to_string(index=False, float_format="%.1f"))
print(iv.groupby("label").dur.sum().round(1).to_dict())
```

```text
      label  start  end  dur
       rest    0.0  4.0  4.0
     ignore    4.0  4.6  0.6
        tap    4.6 13.7  9.1
     ignore   13.7 14.0  0.3
       rest   14.0 18.0  4.0
     ignore   18.0 18.6  0.6
wrist_raise   18.6 27.7  9.1
     ignore   27.7 28.0  0.3
       rest   28.0 32.0  4.0
     ignore   32.0 32.6  0.6
        tap   32.6 40.2  7.6
     ignore   40.2 40.5  0.3
       rest   40.5 44.0  3.5
{'ignore': 2.7, 'rest': 15.5, 'tap': 16.7, 'wrist_raise': 9.1}
```

출력에서 볼 것: 44 s 세션이 rest·tap·wrist_raise·ignore 구간으로 빈틈없이 덮였다. ignore가 2.7 s(약 6%)다. 그리고 "tap" 구간은 9.1 s짜리다. 실제 탭 하나는 0.2 ~ 0.3 s이므로 이 구간 안의 대부분 샘플은 **탭과 탭 사이의 대기**다. 즉 scripted session 라벨은 "이 구간 어딘가에 탭이 10번 있다"는 **거친(coarse) 라벨**이다. 탭 하나하나의 onset이 필요하면 구간 안에서 피크 검출(§5의 labeling function)로 후보를 찾고 사람이 확인하는 2단계가 필요하다.

Scripted session의 장단점:

| 장점 | 단점 |
|---|---|
| 라벨이 거의 공짜 (프롬프트 로그) | 연기한 동작 — 실제 생활의 동작과 분포가 다르다 |
| 클래스 균형을 마음대로 맞춤 | null 클래스가 "가만히 있기"로 편향 (실생활 null은 훨씬 다양) |
| 참가자 수십 명 × 30분이면 시작 가능 | 반응 지연·끝 흐림 → ignore 여유 필요 |
| 프로토콜이 재현 가능 (시험 절차서처럼) | 참가자가 지루해져 후반부 동작이 대충 됨 (drift) |

Don에게 익숙한 말로 하면: scripted session은 **챔버 시험 스크립트**와 같다. 조건을 통제하니 재현성이 좋지만, 필드에서만 나오는 조합은 못 잡는다. 그래서 다음 절의 free-living 데이터가 꼭 같이 필요하다.

### 2.2 펌웨어 쪽 — 라벨 마커를 센서와 같은 시계로 남기기

앱 프롬프트 시각은 **폰 시계**로 찍힌다. 센서 샘플은 **기기 MCU 시계**로 찍힌다. 둘 사이의 offset·drift를 맞추지 않으면 라벨이 통째로 Δt만큼 밀린다 (G7 §0.3에서 Δt가 정확도를 어떻게 깎는지 실험했다). 가장 단순한 해결은 **기기 쪽에서 마커를 남기는 것**이다: 앱이 BLE로 "START label=1"을 보내면 펌웨어가 그 메시지를 받은 시각을 **센서 timestamp와 같은 µs 타이머**로 찍어 로그 스트림에 마커 레코드로 넣는다. 기기의 버튼을 누르게 하는 방법도 같다.

**예제 2.** 이 C 코드는 마커 레코드(START/STOP)를 구간으로 짝짓고, 짝이 안 맞는 경우·너무 긴 구간·32-bit µs 카운터 wrap을 처리한다.

```c
#include <stdint.h>
#include <stdio.h>

typedef struct { uint32_t t_us; uint8_t kind; uint8_t label; } marker_t;  /* kind: 1=START 2=STOP */
enum { START = 1, STOP = 2, MAX_OPEN_US = 10000000u };                    /* 10 s 넘으면 자동 종료 */

/* 펌웨어가 센서 로그와 같은 시계(µs 타이머)로 남긴 마커 → (label, start, end) 구간 */
static int pair_markers(const marker_t *m, int n) {
    int open = -1, out = 0;
    for (int i = 0; i < n; i++) {
        if (m[i].kind == START) {
            if (open >= 0)                        /* STOP 없이 또 START: 앞 구간 버림 */
                printf("warn: START@%u without STOP -> dropped\n", (unsigned)m[open].t_us);
            open = i;
        } else if (m[i].kind == STOP && open >= 0) {
            uint32_t dur = m[i].t_us - m[open].t_us;          /* unsigned 차이: wrap 안전 */
            if (dur > MAX_OPEN_US || m[i].label != m[open].label)
                printf("warn: bad pair label %u dur=%u us -> dropped\n", m[open].label, (unsigned)dur);
            else
                printf("interval label=%u start=%u dur=%u us\n", m[i].label, (unsigned)m[open].t_us, (unsigned)dur);
            out += (dur <= MAX_OPEN_US && m[i].label == m[open].label);
            open = -1;
        }
    }
    return out;
}

int main(void) {
    const marker_t log[] = {
        {4000000u, START, 1}, {13700000u, STOP, 1},           /* 정상: tap 세션 */
        {18000000u, START, 2}, {20000000u, START, 2},         /* 버튼 두 번 눌림 */
        {27700000u, STOP, 2},
        {4294000000u, START, 1}, {3032704u, STOP, 1},         /* 32-bit µs 카운터 wrap */
        {40000000u, START, 3}, {65000000u, STOP, 3},          /* 25 s: 너무 김 */
    };
    printf("valid intervals: %d\n", pair_markers(log, (int)(sizeof log / sizeof log[0])));
    return 0;
}
```

```text
interval label=1 start=4000000 dur=9700000 us
warn: START@18000000 without STOP -> dropped
interval label=2 start=20000000 dur=7700000 us
interval label=1 start=4294000000 dur=4000000 us
warn: bad pair label 3 dur=25000000 us -> dropped
valid intervals: 3
```

출력에서 볼 것: START가 두 번 연달아 오면 앞의 것을 버리고 경고한다(버튼 바운스나 BLE 재전송). `4294000000 → 3032704`처럼 카운터가 wrap된 경우에도 `uint32_t` 뺄셈 덕분에 4,000,000 µs(4 s)로 맞게 나온다 (2³² − 4,294,000,000 + 3,032,704 = 967,296 + 3,032,704 = 4,000,000). 25 s짜리 구간은 상한(10 s)을 넘어서 버렸다. 이것은 "STOP을 누르는 걸 잊은" 사람의 흔한 실수다. 컴파일은 `cc -std=c11 -Wall -Wextra -O2`로 경고 0개다.

함정: 마커 BLE 메시지도 지연이 있다 (connection interval 7.5 ~ 50 ms 이상, H2). 정밀한 onset이 필요하면 마커는 "대략 여기"만 알려 주고, 정확한 경계는 신호에서 찾는다.

### 2.3 Free-living 데이터와 EMA — 실생활은 지시할 수 없다

**free-living** 데이터는 참가자가 평소처럼 생활하는 동안 기기가 계속 기록한 데이터다. 실제 배포 환경과 분포가 같다는 것이 최대 장점이고, **라벨이 거의 없다**는 것이 최대 약점이다.

여기서 쓰는 라벨 출처가 **EMA (ecological momentary assessment)** 다. 연구 분야에서 쓰는 용어로, 하루 중 무작위 또는 이벤트 직후에 폰이 짧은 질문을 띄워 "지금 무엇을 하고 있었나요?"를 묻는 자기보고 방식을 말한다 (용어와 세부 설계는 행동과학·디지털 헬스 쪽 관행이고, 여기서는 개념만 쓴다). 웨어러블 데이터팀 맥락에서는 이런 식이 될 수 있다.

1. 기기가 "탭 같은 이벤트"를 감지하면 폰에 알림: "방금 기기를 두드렸나요? 예 / 아니오 / 모름"
2. 하루 3번 무작위로: "지난 10분간 주로 무엇을 했나요? 걷기 / 앉기 / 운전 / 운동 / 기타"
3. 사용자가 직접 앱에서 "지금부터 달리기" 버튼을 누르는 self-labeling

EMA 라벨의 성질:

| 성질 | 결과 | 대응 |
|---|---|---|
| 시간 해상도가 거칠다 ("지난 10분") | 창 단위로 쓰면 noise 큼 | 세션 수준 라벨로 쓰거나 weak label로 취급 (§5) |
| 응답률이 떨어진다 (피로) | 라벨이 특정 시간대·사람에 편향 | 하루 질문 수 상한, 응답률 모니터링 |
| 기억 오류·사회적 바람직성 | 체계적 편향 | 객관 신호(GPS 속도, 걸음 수)와 교차 확인 |
| "예/아니오" 확인은 싸고 정확한 편 | 모델 감지 이벤트 검증에 좋음 | false positive 수집에 특히 유용 (§8) |

말로 하면: free-living + EMA는 "정확하지 않지만 실제 분포에서 온" 라벨이고, scripted session은 "정확하지만 연기된" 라벨이다. 둘을 섞는 것이 보통이다. 평가 세트는 가능한 한 실제 분포(free-living)에서 정확하게 라벨해야 한다 (§4.3의 noisy test 함정).

### 2.4 동기화된 영상 ground truth

정밀한 이벤트 경계(onset/offset)가 필요하면 **영상**이 가장 많이 쓰이는 증거다. 참가자 옆에 폰 카메라를 세워 두고 녹화한 다음, 라벨러가 영상을 프레임 단위로 보며 이벤트 시작·끝을 찍는다.

핵심 문제는 **영상 시계와 센서 시계를 맞추는 것**이다. 가장 흔한 방법이 녹화 시작과 끝에 **박수(또는 기기를 책상에 탁 치기)** 를 하는 것이다. 박수는 영상에서 손이 맞닿는 프레임, 마이크에서 날카로운 펄스, IMU에서 충격 스파이크로 동시에 보인다. 이 세 시각을 맞추면 offset을 구하고, 시작·끝 두 번의 박수로 drift(rate 차이)까지 구한다. 구체적인 방법(cross-correlation, offset·drift fit)은 G7 §4.3에 있다.

```
영상 프레임 (30 fps → 33 ms 해상도)   |  |  |  |  |  |  |  |  |
                                      ↑ 박수 프레임 k=152 → t_video = 5.067 s
IMU |a| (100 Hz)          ____/\_____ ↑ 충격 피크 t_imu = 12.340 s
offset = t_imu − t_video = 7.273 s   → 모든 영상 라벨 시각에 더한다
끝 박수로 한 번 더 → rate 차이(ppm)까지 보정 (G7 §4.5)
```

정밀도 한계: 30 fps 영상의 프레임 간격은 33 ms다. 사람이 프레임을 고르는 오차까지 더하면 라벨 경계는 보통 ±1 ~ 2 프레임(33 ~ 67 ms) 흔들린다. 100 Hz IMU로 치면 3 ~ 7 샘플이다. 0.3 s 탭 이벤트에서는 무시할 수 없는 크기다. 그래서 §3의 ignore margin이 필요하다. 더 정밀하게 하려면 60/120/240 fps 녹화를 쓴다.

**어노테이션 도구**: 영상·오디오·센서 곡선을 나란히 보며 구간을 찍는 도구로는 Label Studio(웹 기반 범용 라벨링 도구), ELAN(언어학 쪽에서 오래 쓰인 시간축 주석 도구) 같은 것이 알려져 있다. 실제 기능·포맷은 버전마다 다르니 쓰기 전에 문서를 확인해야 한다. 많은 팀이 결국 "영상 + IMU 곡선 + 오디오 파형을 같은 시간축에 띄우는" 사내 도구를 따로 만든다. 도구가 내보내는 포맷이 무엇이든, 파이프라인 안에서는 §9의 `(raw_sha, schema, annotator, intervals[])` 형태로 정규화한다.

프라이버시 주의: 영상에는 얼굴·집 안·다른 사람이 찍힌다. 동의서, 촬영 범위, 라벨러 접근 권한, 보관 기간을 수집 전에 정한다 (H6).

### 2.5 기준 기기 (reference device) — 연속값 라벨

심박 같은 **연속값**은 사람이 라벨할 수 없다. 대신 더 정확한 **기준 기기**를 같이 착용한다. 손목 PPG 심박 모델을 만든다면 가슴 스트랩 ECG 심박계가 흔한 기준이다 (PPG의 원리와 모션 아티팩트는 G6 §3). 걸음 속도라면 트레드밀 설정값, 고도라면 기압계 + GNSS, 수면이라면 수면다원검사(PSG) 같은 식이다.

기준 기기 라벨에서 확인할 것:

| 항목 | 이유 |
|---|---|
| 기준 기기 자체의 오차 | "ground truth"도 오차가 있다. 스펙과 검증 논문을 확인 |
| 시간 정렬 | 기준 기기는 또 다른 시계다 → G7의 offset·drift 보정 |
| 출력 지연·평활 | 많은 심박계는 수 초 평균값을 낸다 → 같은 평활을 라벨에 적용하거나 지연 보정 |
| 결측·접촉 불량 | 스트랩이 떨어진 구간은 ignore |
| 샘플링 rate | 1 Hz 심박을 50 Hz IMU 창에 붙이려면 보간 규칙 (A6 `merge_asof`, G7 resampling) |

Don에게 익숙한 말로 하면: RF 칩 통합에서 DUT 측정값을 **calibrated reference instrument**(spectrum analyzer, power meter)와 비교하는 것과 같다. reference도 calibration 이력이 있어야 믿을 수 있고, 케이블 loss(= 시간 지연·평활)를 보정해야 한다.

### 2.6 프로토콜 비교 — 무엇을 언제 쓰나

| 방법 | 라벨 정밀도 | 실제 분포와의 거리 | 사람 비용 | 주 용도 |
|---|---|---|---|---|
| scripted session | 구간 수준, 반응 지연 | 멀다 (연기) | 낮음 | 첫 모델, 클래스 균형 |
| 마커 버튼 (기기·앱) | 수백 ms | 중간 | 낮음 | self-labeling, 긴 활동 |
| free-living + EMA | 분 단위, 기억 오류 | 가깝다 | 중간 (참가자 부담) | 실제 분포 확보, FP 확인 |
| 동기화 영상 + 수동 | 수십 ms | 중간 (촬영 환경 제약) | 높음 | 정밀 onset, 평가 세트 |
| 기준 기기 | 기기 정확도만큼 | 중간 ~ 가깝다 | 낮음 (착용만) | 연속값 (HR, 속도) |

## 3. 구간 라벨 → 창 라벨 — 경계에서 무슨 일이 일어나나

### 3.1 직관

모델은 보통 **고정 길이 창**(예: 1 s, 50샘플)을 입력으로 받는다 (A6 §6, B7 §2.4). 그런데 라벨은 구간으로 온다. 창이 이벤트 구간에 **일부만 걸치면** 그 창의 라벨은 무엇인가? 이것이 창 라벨 규칙 문제다. A6 §6.3에서 규칙을 표로 봤다. 여기서는 직접 구현해서 **경계에서 숫자가 어떻게 달라지는지**를 본다.

먼저 정의 하나. 창 i의 **양성 비율** fᵢ는 창 안 샘플 중 이벤트 구간에 속한 샘플의 비율이다.

```
fᵢ = (창 i 안에서 라벨이 양성인 샘플 수) / L
center   규칙: 창 가운데 샘플 하나의 라벨          → y[sᵢ + L/2]
majority 규칙: fᵢ > 0.5 이면 양성
any      규칙: fᵢ > 0   이면 양성 (한 샘플이라도 걸치면)
contains 규칙: 이벤트가 창 안에 통째로 들어가면 양성
ignore margin: fᵢ ≥ 0.5 → 양성, fᵢ = 0 → 음성, 그 사이 → 학습에서 제외
```

말로 하면: 다섯 규칙은 "애매한 창(0 < f < 1)을 어떻게 처리할까"에 대한 다섯 가지 답이다. 애매하지 않은 창(f = 0 또는 1)은 어느 규칙이든 같은 라벨을 받는다.

### 3.2 손으로 계산해 보기

그림 2의 숫자를 직접 따라가 보자. 창 길이 L = 1 s, hop = 0.5 s, 창 시작 sᵢ = 0, 0.5, 1.0, …, 5.0.

1. 창 [0.5, 1.5): 탭(1.2 ~ 1.5)이 0.3 s 겹친다 → f = 0.3/1.0 = 0.30. 가운데 시각 1.0 s는 탭 밖 → center = 음성. majority: 0.30 ≤ 0.5 → 음성. any: 양성. contains: 탭이 [0.5, 1.5) 안에 통째로 → 양성.
2. 창 [1.0, 2.0): 탭이 통째로 들어 있음 → f = 0.30. 가운데 1.5 s는 탭의 끝(1.5는 구간 밖, 끝 배타) → center = 음성. 이렇게 **hop(0.5 s)이 이벤트 길이(0.3 s)보다 길면** center 규칙은 이벤트를 하나도 못 잡을 수 있다.
3. 창 [2.5, 3.5): 제스처(3.0 ~ 4.5)와 0.5 s 겹침 → f = 0.50. 가운데 3.0 s → 제스처 시작 샘플이라 center = 양성. majority는 `f > 0.5`라 음성. ignore margin은 `f ≥ 0.5`라 양성. **부등호 하나**가 경계 창의 라벨을 바꾼다.

### 3.3 코드로 확인 — 2분 시퀀스, 이벤트 길이 세 종류

**예제 3.** 이 코드는 가짜 2분 시퀀스(50 Hz)에 0.3 / 0.6 / 1.5 s 이벤트 29개를 심고, 1 s 창·0.2 s hop으로 각 규칙의 양성 창 수, 순도(양성 창의 평균·최소 f), 이벤트 길이별 "양성 창을 하나라도 받은 이벤트 비율"을 잰다.

```python
import numpy as np
FS, L, HOP = 50, 50, 10                       # 50 Hz, 1 s 창, 0.2 s hop
rng = np.random.default_rng(0)
T = 120 * FS                                  # 가짜 2분 시퀀스
y = np.zeros(T, int); ev = []
for s in np.arange(2, 118, 4.0):              # 4 s마다 이벤트 1개
    d = rng.choice([0.3, 0.6, 1.5])           # 짧은 탭 · 중간 · 긴 제스처 [s]
    a = int((s + rng.uniform(0, 1)) * FS); ev.append((a, a + int(d * FS), d))
    y[a:a + int(d * FS)] = 1
st = np.arange(0, T - L + 1, HOP)
frac = np.array([y[s:s + L].mean() for s in st])          # 창 안 양성 비율
inside = np.array([any(a >= s and b <= s + L for a, b, _ in ev) for s in st])
rules = {"center":   y[st + L // 2] == 1,
         "majority": frac > 0.5,
         "any":      frac > 0,
         "contains": inside}
for name, pos in rules.items():
    cov = [np.mean([any(pos[(st < b) & (st + L > a)]) for a, b, dd in ev if dd == d])
           for d in (0.3, 0.6, 1.5)]
    print(f"{name:8s} pos={pos.sum():3d}  mean_purity={frac[pos].mean():.2f}  "
          f"min_purity={frac[pos].min():.2f}  covered(0.3/0.6/1.5s)={cov[0]:.2f}/{cov[1]:.2f}/{cov[2]:.2f}")
mixed = (frac > 0) & (frac < 1)
print(f"windows={len(st)}  pure_neg={np.sum(frac == 0)}  pure_pos={np.sum(frac == 1)}  mixed={mixed.sum()}")
keep = (frac == 0) | (frac >= 0.5)                        # ignore margin: 애매한 창은 버림
print(f"ignore-margin: pos={np.sum(frac >= 0.5)}  neg={np.sum(frac == 0)}  dropped={np.sum(~keep)}")
```

1. **창 596개 중 235개(39%)가 애매한 창**(0 < f < 1)이다. 이벤트가 4 s마다 있고 창이 1 s면 경계 창이 이렇게 많다. 경계 규칙은 사소한 결정이 아니다.
2. **majority는 0.3 s 이벤트를 하나도 못 잡는다** (covered 0.00). 1 s 창에서 0.3 s 이벤트의 f는 최대 0.30이므로 0.5를 넘을 수 없다. 짧은 이벤트에 majority를 쓰면 "탭" 클래스의 학습 데이터가 0개가 된다. 이 버그는 에러가 안 난다.
3. **any는 양성이 261개로 가장 많지만 순도가 0.46, 최소 0.02**다. f = 0.02면 1 s 창 중 20 ms만 이벤트다. 이런 창을 "양성"이라고 가르치면 모델은 "거의 아무것도 없는 창"도 양성이라고 배운다 → false positive 증가.
4. **contains는 짧은 이벤트에 맞춤**이다. 0.3 / 0.6 s 이벤트는 모두 잡고, 창보다 긴 1.5 s 이벤트는 0개다. wake word처럼 "창 안에 단어가 통째로 들어와야 의미가 있는" 과제에 쓴다. 창 길이를 가장 긴 이벤트보다 길게 잡는 것이 전제다.
5. **center는 이 설정에서 모든 이벤트를 잡았다.** hop(0.2 s) < 가장 짧은 이벤트(0.3 s)이기 때문이다. 그림 2처럼 hop이 0.5 s면 탭을 놓친다. 규칙은 hop·창 길이·이벤트 길이와 **같이** 정해야 한다.
6. **ignore margin**은 양성 109 / 음성 335 / 제외 152다. 학습 데이터 26%를 버리는 대신, 남은 라벨은 "확실한 것"만 남는다.

### 3.4 경계의 라벨 noise와 ignore margin

§2.4에서 영상 라벨 경계가 ±33 ~ 67 ms 흔들린다고 했다. 즉 라벨 경계 근처 샘플은 **원래부터 확실하지 않다.** 이 불확실성을 처리하는 방법은 세 가지다.

| 방법 | 하는 일 | 장점 | 단점 |
|---|---|---|---|
| ignore margin (경계 ± m 샘플 제외) | 경계 근처 창·프레임을 loss에서 뺀다 (mask) | 단순, 효과 큼 | 경계 판단을 못 배운다 |
| soft label (f를 그대로 target) | 창 target = f (예: 0.3) | 정보 보존 | 학습 코드·평가 정의가 복잡 |
| 순도 문턱 (purity ≥ 0.75만) | 애매한 창 버림 | 깨끗 | 데이터 손실, 짧은 이벤트 소실 |

손계산: 100 Hz IMU, 경계 오차 ±50 ms면 ±5샘플이다. 1 s 창(100샘플)에서 경계 하나가 f를 ±0.05 흔든다. 그러니 f가 0.45 ~ 0.55인 창은 라벨이 "동전 던지기"와 비슷하다. ignore 폭을 정할 때는 **라벨 경계 오차 × 2 정도**를 출발점으로 잡고, 검증 세트 성능으로 조정한다.

PyTorch에서 ignore는 보통 라벨을 특수값으로 두고 loss에서 빼는 식으로 구현한다. `torch.nn.CrossEntropyLoss`의 `ignore_index`(기본값 −100)가 바로 그 용도다. 즉 ignore 창의 라벨을 −100으로 두면 그 창은 gradient에 기여하지 않는다.

### 3.5 임베디드 연결과 함정

- 학습 때 쓴 **창 길이·hop·라벨 규칙**은 배포 때 후처리(smoothing, refractory, B5 §3.4)와 짝이다. 학습을 center 규칙으로 했다면 모델 출력은 "창 가운데 시각"의 상태를 뜻하므로, 기기에서 이벤트 시각을 보고할 때 L/2만큼 지연이 있다.
- 평가는 창 정확도보다 **이벤트 단위 지표**(이벤트 recall, 시간당 false alarm)로 하는 것이 제품과 가깝다 (A4 §9). 창 정확도는 경계 규칙에 따라 숫자가 크게 바뀐다.
- 함정: 라벨을 창으로 바꾸기 **전에** 라벨 시각을 센서 시계로 옮겨야 한다 (G7). `merge_asof`로 라벨을 붙일 때는 `tolerance`를 둬서 너무 먼 라벨이 붙지 않게 한다 (A6 §5.5, G7).

## 4. 라벨 품질 — 정답도 틀린다

### 4.1 직관 — 라벨러도 "측정기"다

같은 영상을 두 사람에게 라벨하게 하면 결과가 다르다. 라벨러는 **오차가 있는 측정기**다. 그러니 측정기 검증처럼 다룬다: 반복성(같은 사람의 일관성), 재현성(사람 간 일치), 기준 대비 정확도(gold), 시간에 따른 drift.

Don에게 익숙한 말로 하면: 양산 시험에서 측정 시스템 자체의 변동을 평가하는 gage R&R과 같은 사고다. 측정기 변동이 크면 DUT 판정을 믿을 수 없듯, 라벨러 간 불일치가 크면 모델 정확도 숫자를 믿을 수 없다.

### 4.2 Cohen's kappa — 우연히 맞은 것을 빼고 본 일치도

두 라벨러가 같은 항목 N개에 라벨을 붙였다. 가장 단순한 지표는 **일치율** pₒ = (같은 라벨을 붙인 항목 수)/N 이다. 그런데 pₒ는 속기 쉽다. 두 사람이 아무 생각 없이 무작위로 찍어도 클래스 비율이 치우쳐 있으면 많이 맞는다.

**Cohen's kappa** κ는 "우연히 맞을 비율" pₑ를 빼고 다시 잰 일치도다.

```
pₒ = ∑ₖ Cₖₖ / N                      (confusion matrix 대각합 / 전체)
pₑ = ∑ₖ (Aₖ / N) · (Bₖ / N)          (A가 k라고 할 확률 × B가 k라고 할 확률)
κ  = (pₒ − pₑ) / (1 − pₑ)
```

말로 하면: 분자는 "우연보다 얼마나 더 맞았나", 분모는 "우연보다 더 맞을 수 있는 최대치"다. κ = 1이면 완전 일치, κ = 0이면 우연 수준, 음수면 우연보다도 못하다.

**손으로 계산해 보기.** 창 20개를 두 라벨러가 rest(0) / tap(1)로 라벨했다 (가짜).

```
                B = rest   B = tap    합
A = rest           7          3       10
A = tap            2          8       10
합                 9         11       20

pₒ = (7 + 8) / 20 = 0.75
pₑ = (10/20)·(9/20) + (10/20)·(11/20) = 0.225 + 0.275 = 0.50
κ  = (0.75 − 0.50) / (1 − 0.50) = 0.50
```

75% 일치처럼 보이지만, 클래스가 반반이라 우연히도 50%는 맞는다. 우연 이상의 일치는 그 절반인 0.50이다.

**예제 4.** 이 코드는 위 손계산을 직접 구현한 함수와 `sklearn.metrics.cohen_kappa_score`로 확인하고, 클래스가 5% / 95%로 치우친 경우의 함정을 보여 준다.

```python
import numpy as np
from sklearn.metrics import cohen_kappa_score

def kappa(a, b):
    k = max(a.max(), b.max()) + 1
    C = np.zeros((k, k)); np.add.at(C, (a, b), 1)          # 2인 confusion matrix
    n = C.sum()
    po = np.trace(C) / n                                    # 관측 일치율
    pe = (C.sum(1) / n) @ (C.sum(0) / n)                    # 우연 일치율
    return po, pe, (po - pe) / (1 - pe)

# 손계산 예: 창 20개, 0=rest 1=tap.  A\B = [[7,3],[2,8]]  (가짜)
A = np.array([0] * 10 + [1] * 10)
B = np.array([0] * 7 + [1] * 3 + [0] * 2 + [1] * 8)
po, pe, k = kappa(A, B)
print(f"hand  : po={po:.3f} pe={pe:.3f} kappa={k:.3f}  sklearn={cohen_kappa_score(A, B):.3f}")

# 불균형 함정: 양성 5%. 둘 다 거의 항상 0이라고 찍으면?
rng = np.random.default_rng(1)
truth = (rng.random(1000) < 0.05).astype(int)
lazyA = np.where(rng.random(1000) < 0.3, truth, 0)          # 양성의 30%만 표시
lazyB = np.where(rng.random(1000) < 0.3, truth, 0)
po, pe, k = kappa(lazyA, lazyB)
print(f"skewed: po={po:.3f} pe={pe:.3f} kappa={k:.3f}")
```

```text
hand  : po=0.750 pe=0.500 kappa=0.500  sklearn=0.500
skewed: po=0.983 pe=0.981 kappa=0.097
```

출력에서 볼 것: 손계산(0.500)과 sklearn이 같다. 두 번째 줄이 핵심이다. 두 "게으른" 라벨러는 양성의 30%만 표시했는데도 **일치율 98.3%** 다. 하지만 거의 모든 항목이 "둘 다 0"이라서 우연 일치 pₑ도 98.1%이고, **κ = 0.097**, 즉 거의 우연 수준이다. 희귀 이벤트(탭, wake word) 라벨에서 일치율만 보고하면 이런 사고를 놓친다.

κ 해석의 대략적인 기준(Landis & Koch 1977의 구간이 자주 인용된다: 0.61 ~ 0.80 "substantial", 0.81 이상 "almost perfect")이 있지만, 과제마다 달라서 **절대 기준으로 쓰지 말고** 같은 과제 안에서 라벨러·스키마 버전을 비교하는 용도로 쓴다.

**Krippendorff's alpha**: 라벨러가 3명 이상이거나, 라벨러마다 항목 일부만 라벨했거나(결측), 라벨이 순서형·연속값일 때 쓰는 더 일반적인 일치도 지표다. 이 노트에서는 이름과 용도만 기억하고, 필요하면 구현된 패키지를 쓴다. 이벤트 경계처럼 연속값이면 "onset 시각 차이의 분포(중앙값, 95 백분위수 ms)"를 직접 보는 것이 더 직관적이다.

### 4.3 여러 라벨러 — gold 문항, 투표, drift

실무에서 쓰는 품질 관리 도구 세 가지:

1. **gold 문항 (gold questions)**: 정답을 이미 아는 항목을 작업 중간중간 몰래 섞는다 (예: 5%). 라벨러별 정확도를 추정한다.
2. **합의 (consensus)**: 같은 항목을 여러 명이 라벨하고 투표로 합친다. 불일치 항목은 전문가가 판정(adjudication)한다.
3. **drift 감시**: 같은 라벨러의 정확도가 시간이 지나며 떨어지는지(피로, 기준 망각) 배치별로 본다.

**예제 5.** 이 코드는 4클래스 창 2000개(가짜)를 라벨러 4명이 라벨하는 상황을 만든다. ann3은 정확도 0.90에서 시작해 점점 0.65까지 떨어지는 drift가 있고, spammer는 무작위로 찍는다. gold 100개(5%)로 각자의 정확도를 추정하고, 단순 다수결과 **정확도 가중 투표**를 비교한다.

```python
import numpy as np
rng = np.random.default_rng(7)
N, K = 2000, 4                                    # 창 2000개, 4클래스 (가짜)
truth = rng.integers(0, K, N)

def annotate(p, drift=0.0):
    pi = p - drift * np.arange(N) / N             # 시간이 갈수록 정확도 감소(drift)
    wrong = (truth + rng.integers(1, K, N)) % K   # 틀릴 땐 다른 클래스 중 무작위
    return np.where(rng.random(N) < pi, truth, wrong)
lab = {"ann1": annotate(0.92), "ann2": annotate(0.88),
       "ann3": annotate(0.90, drift=0.25),        # 0.90에서 시작해 0.65까지 떨어짐
       "spammer": annotate(0.25)}                 # 4클래스 무작위 = 0.25

gold = rng.choice(N, 100, replace=False)          # 정답을 아는 gold 문항 100개(5%)
g_acc = {}
for n, l in lab.items():
    g_acc[n] = (l[gold] == truth[gold]).mean()
    print(f"{n:8s} gold_acc={g_acc[n]:.2f}  true_acc={(l == truth).mean():.2f}  "
          f"first500={(l[:500] == truth[:500]).mean():.2f}  last500={(l[-500:] == truth[-500:]).mean():.2f}")

def vote(names, weighted=False):
    V = np.zeros((N, K))
    for n in names:
        p = np.clip(g_acc[n], 0.26, 0.99)
        w = np.log((K - 1) * p / (1 - p)) if weighted else 1.0   # 정확도 → log-odds 가중치
        V[np.arange(N), lab[n]] += w
    return V.argmax(1)                            # 동률이면 작은 클래스 번호 (단순화)
for names in (["ann1", "ann2", "ann3"], ["ann1", "ann2", "spammer"]):
    print(f"{'+'.join(names):22s} majority={(vote(names) == truth).mean():.3f}  "
          f"weighted={(vote(names, True) == truth).mean():.3f}")
```

```text
ann1     gold_acc=0.89  true_acc=0.92  first500=0.92  last500=0.92
ann2     gold_acc=0.86  true_acc=0.88  first500=0.88  last500=0.86
ann3     gold_acc=0.76  true_acc=0.76  first500=0.84  last500=0.68
spammer  gold_acc=0.23  true_acc=0.25  first500=0.27  last500=0.21
ann1+ann2+ann3         majority=0.959  weighted=0.965
ann1+ann2+spammer      majority=0.887  weighted=0.922
```

출력에서 볼 것:

1. **gold 100개로 정확도를 꽤 잘 추정한다** (ann1 0.89 vs 진짜 0.92, spammer 0.23 vs 0.25). 표본 100개면 표준오차가 √(0.9 × 0.1 / 100) = 0.03 정도라 이 정도 오차는 정상이다.
2. **ann3의 drift**: 처음 500개 0.84 → 마지막 500개 0.68. 전체 평균(0.76)만 보면 안 보인다. gold를 시간순으로 나눠 봐야 잡힌다.
3. **다수결의 함정**: ann1 + ann2 + spammer 다수결(0.887)은 **ann1 혼자(0.92)보다 나쁘다.** 좋은 라벨러 둘이 엇갈리면 spammer가 캐스팅보트를 쥐기 때문이다.
4. **가중 투표**는 0.922로 회복한다. spammer의 가중치가 거의 0이 되기 때문이다.

가중치 식은 "라벨러가 정확도 p로 맞히고, 틀릴 때는 나머지 K − 1개 클래스 중 무작위"라는 모델에서 나온다.

```
w = log( (K − 1) · p / (1 − p) )
ann1  p = 0.89 → log(3 × 0.89 / 0.11) = log(24.3) ≈ 3.19
ann2  p = 0.86 → log(3 × 0.86 / 0.14) = log(18.4) ≈ 2.91
spammer p = 0.26(하한 clip) → log(3 × 0.26 / 0.74) = log(1.05) ≈ 0.05
```

말로 하면: 각 라벨러의 표는 "이 라벨러가 이 클래스를 말했을 때 그게 정답일 log-odds"만큼의 무게를 가진다. 무작위 수준(p = 1/K)이면 무게가 0이다. 이 생각을 라벨러별 confusion matrix까지 확장해서 EM으로 정답과 라벨러 정확도를 **동시에** 추정하는 고전 방법이 Dawid–Skene(1979) 모델이다. §5의 labeling function 결합도 같은 생각이다.

### 4.4 라벨 noise가 모델에 주는 영향 — 실험

라벨이 틀리면 모델은 얼마나 나빠지나? 합성 데이터라서 직접 잴 수 있다. 이 노트의 §4 ~ §7은 공용 합성 데이터 `h4_data.py`를 쓴다. 손목 IMU 크기 |a|의 2 s 창(50 Hz, 100샘플)을 4클래스(still / walk / run / other)로 만들고, 창마다 특징 4개(표준편차, 주 주파수, 스펙트럼 피크 비율, peak-to-peak)를 뽑는다. 폰 GPS 속도(절반은 결측)도 같이 만든다 (§5에서 씀). 걷기(1.4 ~ 2.4 Hz)와 달리기(2.1 ~ 3.2 Hz)의 주파수가 겹치게 만들어서 완벽히 맞히기는 어렵다.

```python
"""H4 공용 합성 데이터: 손목 IMU 2 s 창 (50 Hz) — 모두 가짜(synthetic) 데이터."""
import numpy as np
FS, L = 50, 100                                  # 50 Hz × 2 s
CLASSES = ["still", "walk", "run", "other"]

def make_windows(n, seed=0):
    rng = np.random.default_rng(seed)
    y = rng.integers(0, 4, n)
    t = np.arange(L) / FS
    f = np.select([y == 1, y == 2], [rng.uniform(1.4, 2.4, n), rng.uniform(2.1, 3.2, n)], 0.0)
    a = np.select([y == 1, y == 2, y == 3], [rng.uniform(0.1, 0.5, n),
                  rng.uniform(0.3, 0.9, n), rng.uniform(0.1, 0.7, n)], 0.01)
    ph = rng.uniform(0, 2 * np.pi, n)
    mag = 1 + a[:, None] * np.sin(2 * np.pi * f[:, None] * t + ph[:, None])
    burst = rng.normal(0, 1, (n, L)) * a[:, None] * (y[:, None] == 3)   # other = 불규칙
    mag = mag + burst + rng.normal(0, 0.03, (n, L))
    speed = np.select([y == 1, y == 2], [rng.normal(1.3, 0.4, n), rng.normal(2.6, 0.6, n)],
                      np.abs(rng.normal(0, 0.4, n)))                   # 폰 GPS 속도 [m/s]
    speed[rng.random(n) < 0.5] = np.nan                                # 절반은 GPS 없음
    return mag, y, speed

def features(mag):
    x = mag - mag.mean(1, keepdims=True)
    spec = np.abs(np.fft.rfft(x, axis=1))[:, 1:]                       # DC 제외
    k = spec.argmax(1) + 1
    dom_f = k * FS / L                                                 # 주파수 해상도 0.5 Hz
    peak_ratio = spec.max(1) / (spec.sum(1) + 1e-9)                    # 주기성 지표
    return np.column_stack([x.std(1), dom_f, peak_ratio, np.ptp(x, 1)])
```

**예제 6.** 이 코드는 train 라벨에 **symmetric noise**(정해진 비율만큼 무작위로 다른 클래스로 바꿈)를 0 ~ 40% 넣고, logistic regression과 random forest를 train 300개 / 3000개로 학습해서 **깨끗한** test 4000개로 잰다 (seed 5개 평균). 마지막 줄은 test 라벨까지 오염된 경우다.

```python
import numpy as np
from h4_data import make_windows, features
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

def flip(y, rate, rng):                         # symmetric noise: rate만큼 다른 클래스로
    m = rng.random(len(y)) < rate
    return np.where(m, (y + rng.integers(1, 4, len(y))) % 4, y)
mt, yt, _ = make_windows(4000, seed=99); Xt = features(mt)    # 깨끗한 test
models = {"logreg": lambda: make_pipeline(StandardScaler(), LogisticRegression(max_iter=2000)),
          "rf":     lambda: RandomForestClassifier(100, random_state=0, n_jobs=-1)}
for n_tr in (300, 3000):
    for name, mk in models.items():
        row = []
        for rate in (0.0, 0.1, 0.2, 0.3, 0.4):
            accs = []
            for s in range(5):
                m, y, _ = make_windows(n_tr, seed=s); rng = np.random.default_rng(100 + s)
                accs.append((mk().fit(features(m), flip(y, rate, rng)).predict(Xt) == yt).mean())
            row.append(np.mean(accs))
        print(f"n={n_tr:4d} {name:6s} " + " ".join(f"{a:.3f}" for a in row))
# 측정 함정: test 라벨도 20% 오염돼 있으면 같은 모델이 몇 점으로 보이나?
m, y, _ = make_windows(3000, seed=0); clf = models["rf"]().fit(features(m), y)
pred = clf.predict(Xt); noisy_yt = flip(yt, 0.2, np.random.default_rng(5))
print(f"same model: clean-test acc={(pred == yt).mean():.3f}  noisy-test acc={(pred == noisy_yt).mean():.3f}")
```

그림 3 — train 라벨 noise 비율 대 clean test 정확도 (예제 6의 실제 출력). 실선은 train 3000개, 점선은 300개. 데이터가 많은 RF는 20% noise까지 거의 버틴다(0.964 → 0.948). 데이터가 적으면 같은 noise에 더 크게 무너진다(RF 300개: 0.962 → 0.912 → 0.778).

출력에서 볼 것:

1. **데이터가 많으면 symmetric noise는 꽤 견딘다.** 무작위로 틀린 라벨은 클래스 사이에 고르게 퍼져서, 다수의 맞는 라벨이 결정 경계를 지켜 준다. 그러나 30 ~ 40%로 가면 무너진다.
2. **데이터가 적으면 noise가 더 아프다.** 300개에 30% noise면 틀린 라벨 90개가 경계를 끌고 다닌다.
3. **모델마다 다르다.** logreg는 10% noise에서 0.937 → 0.894로 먼저 떨어졌지만 이후 완만하다. RF는 깨끗할 때 더 강하지만 40%에서 더 크게 떨어진다. 그러니 "noise에 강한 모델"은 실험으로 확인할 것이지 가정할 것이 아니다.
4. **가장 위험한 줄은 마지막이다.** 같은 모델이 깨끗한 test에서는 0.964인데 **20% 오염된 test로 재면 0.763**으로 보인다. 근사식: 측정 정확도 ≈ a(1 − r) + (1 − a)·r/(K − 1) = 0.964 × 0.8 + 0.036 × 0.2/3 ≈ 0.774 (표본 오차로 0.763). 즉 **test 라벨의 noise는 모델 개선을 가린다.** 모델을 아무리 고쳐도 0.8 근처에 천장이 생긴다.

현실의 noise는 symmetric이 아니다. walk ↔ run처럼 **비슷한 클래스끼리 헷갈리는 noise**(class-conditional noise)와, 경계 근처에 몰리는 noise(§3.4)가 대부분이다. 이런 noise는 결정 경계를 체계적으로 밀어서 symmetric보다 해롭다. 그래서 실험 결과는 "하한선이 아니라 낙관적인 경우"로 읽는다.

## 5. Weak supervision — 사람 대신 규칙이 라벨을 붙인다

### 5.1 직관

dogfood 기기 100대가 한 달 동안 올린 IMU 로그가 수천 시간 있다. 사람이 다 볼 수는 없다. 그런데 펌웨어 엔지니어라면 "대충 이렇게 하면 걷기는 잡힌다"는 **휴리스틱**을 몇 개 금방 쓸 수 있다: 에너지가 거의 없으면 정지, 1.5 ~ 2 Hz 주기가 뚜렷하면 걷기, 폰 GPS 속도가 3 m/s면 달리기…

**weak supervision**은 이런 부정확한 규칙 여러 개(= **labeling function**, LF)를 대량의 무라벨 데이터에 돌리고, 그 출력을 합쳐 "약한 라벨"을 만든 뒤, 그 라벨로 모델을 학습하는 방법이다. 각 LF는:

1. 자기가 확신하는 경우에만 라벨을 내고, 아니면 **기권(abstain)** 한다.
2. 틀릴 수 있다. 서로 충돌할 수 있다.
3. 사람 라벨 대신 **사람의 지식을 코드로** 넣는 것이다. 라벨 1000개 대신 LF 5개를 쓴다.

이 생각을 체계화한 대표적인 도구가 Stanford에서 나온 **Snorkel**(Ratner et al., 2017)이다. Snorkel은 LF들의 정확도와 상관관계를 라벨 없이 추정하는 생성 모델(label model)로 LF 출력을 합친다고 알려져 있다. 여기서는 그 개념만 가져와서, 작은 dev set으로 LF 정확도를 추정하고 §4.3의 가중 투표로 합치는 단순한 버전을 직접 구현한다 (Snorkel의 실제 label model은 이보다 정교하다).

LF로 쓸 수 있는 신호들(웨어러블이라면):

| LF 출처 | 예 | 성질 |
|---|---|---|
| 신호 휴리스틱 | 에너지 문턱, 주 주파수, 피크 수 (step detector) | 빠르고 설명 가능, 경계 사례에 약함 |
| 다른 센서 / context | 폰 GPS 속도, 폰 활동 인식 API, 블루투스 연결(차량) | 다른 시점·해상도 → 정렬 필요 (G7) |
| 기존 모델 | 이전 버전 모델, 서버의 큰 모델 (§6 teacher) | 높은 coverage, 체계적 오류 공유 위험 |
| 메타데이터 | 시간대(새벽 3시 = 수면 가능성), 앱 상태 | 매우 약함, 보조용 |
| 사용자 행동 | 알림 확인, "취소" 버튼 (wake word 오작동 신호) | 암묵적 피드백, 노이즈 많음 |

### 5.2 LF 다섯 개 — 코드

LF를 평가하는 세 숫자:

```
coverage  = LF가 기권하지 않은 비율
accuracy  = 기권하지 않은 것 중 맞은 비율 (평가용 정답이 있을 때만 잴 수 있다)
conflict  = 기권하지 않았는데 다른 LF와 라벨이 다른 비율
```

**예제 7.** 이 코드는 합성 창 3000개에 LF 5개를 돌려 (N, 5) **label matrix**를 만들고, LF별 coverage·conflict·accuracy를 잰다. y는 평가용으로만 쓴다 (실전에는 없다).

```python
import numpy as np
from h4_data import make_windows, features
ABSTAIN = -1
mag, y, speed = make_windows(3000, seed=3)        # y는 평가용으로만 쓴다 (실전엔 없음)
std, dom_f, peak, p2p = features(mag).T

def lf_still(i):     return 0 if std[i] < 0.06 else ABSTAIN               # 에너지 거의 없음
def lf_steps(i):     return 1 if 1.0 <= dom_f[i] <= 2.5 and peak[i] > 0.2 else ABSTAIN
def lf_cadence(i):   return 2 if dom_f[i] >= 2.5 and std[i] > 0.3 else ABSTAIN
def lf_aperiodic(i): return 3 if std[i] > 0.1 and peak[i] < 0.12 else ABSTAIN  # 세지만 주기 없음
def lf_gps(i):                                                             # 폰 context
    s = speed[i]
    if np.isnan(s): return ABSTAIN                                         # GPS 없음
    return 1 if 0.8 <= s <= 1.8 else 2 if s >= 2.3 else ABSTAIN
LFS = [lf_still, lf_steps, lf_cadence, lf_aperiodic, lf_gps]
Lm = np.array([[lf(i) for lf in LFS] for i in range(len(y))])        # (N, 5) label matrix

if __name__ == "__main__":
    print("Lm[:4] =", Lm[:4].tolist(), " y[:4] =", y[:4].tolist())
    for j, lf in enumerate(LFS):
        v = Lm[:, j] != ABSTAIN
        conf = v & np.any((Lm != ABSTAIN) & (Lm != Lm[:, [j]]), axis=1)  # 다른 LF와 충돌
        print(f"{lf.__name__:13s} coverage={v.mean():.2f}  conflict={conf.mean():.2f}  "
              f"accuracy={(Lm[v, j] == y[v]).mean():.2f}")
```

출력에서 볼 것: label matrix의 각 행은 창 하나, 각 열은 LF 하나, −1은 기권이다. 대부분의 창에서 LF 1 ~ 2개만 말한다. `lf_still`과 `lf_aperiodic`은 coverage는 작지만 정확도가 1.00이다 (이 합성 데이터에서는 정지와 불규칙 움직임이 특징으로 깨끗하게 갈린다 — 실데이터에서는 이렇게 좋지 않다). `lf_steps`(0.61)와 `lf_cadence`(0.51)는 많이 틀린다. 걷기·달리기 주파수가 겹치고, 불규칙한 "other" 창도 우연히 주 주파수가 2.5 Hz 이상이면 `lf_cadence`가 달리기라고 말하기 때문이다. conflict도 이 둘이 가장 크다.

### 5.3 LF 결합 — 다수결 vs 가중 투표

**예제 8.** 이 코드는 label matrix를 두 방식으로 합친다. (1) 단순 다수결, (2) 사람 라벨 dev set **100개**로 LF 정확도를 추정해 §4.3의 log-odds 가중치로 투표. 그 약한 라벨로 RF를 학습해 깨끗한 test로 재고, 사람 라벨 100개 / 3000개로 직접 학습한 경우와 비교한다.

```python
import numpy as np
from h4_lfs import Lm, y, ABSTAIN, mag
from h4_data import make_windows, features
from sklearn.ensemble import RandomForestClassifier
K, N = 4, len(y)
dev = np.arange(100)                               # 사람이 라벨한 dev set 100개만 정답 사용

def combine(weights):
    V = np.zeros((N, K))
    for j in range(Lm.shape[1]):
        v = Lm[:, j] != ABSTAIN
        V[np.flatnonzero(v), Lm[v, j]] += weights[j]
    out = V.argmax(1); out[V.max(1) == 0] = ABSTAIN  # 아무 LF도 안 붙으면 abstain
    return out
acc_dev = []
for j in range(Lm.shape[1]):                        # dev set에서 LF 정확도 추정
    v = Lm[dev, j] != ABSTAIN
    acc_dev.append(np.clip((Lm[dev][v, j] == y[dev][v]).mean(), 0.3, 0.98))
w = np.log((K - 1) * np.array(acc_dev) / (1 - np.array(acc_dev)))
print("dev acc:", np.round(acc_dev, 2), " weights:", np.round(w, 2))
mt, yt, _ = make_windows(4000, seed=99); Xt = features(mt); X = features(mag)
for name, lab in (("majority", combine(np.ones(5))), ("weighted", combine(w))):
    c = lab != ABSTAIN
    rf = RandomForestClassifier(100, random_state=0).fit(X[c], lab[c])
    print(f"{name:8s} coverage={c.mean():.2f}  label_acc={(lab[c] == y[c]).mean():.3f}  "
          f"end_model_test_acc={(rf.predict(Xt) == yt).mean():.3f}")
for n in (100, 3000):                               # 비교: 사람 라벨만으로 학습
    rf = RandomForestClassifier(100, random_state=0).fit(X[:n], y[:n])
    print(f"gold n={n:4d}                              end_model_test_acc={(rf.predict(Xt) == yt).mean():.3f}")
```

### 5.4 임베디드 연결과 함정

- LF는 펌웨어 엔지니어가 가장 잘 만드는 것이다. 이미 기기에 있는 step counter, 착용 감지 FSM, VAD(B5 §2)가 그대로 LF가 된다. 반대로 말하면 **이미 기기에 있는 휴리스틱의 실수를 모델이 그대로 배운다.** 모델이 LF보다 나으려면 LF가 서로 다른 방식으로 틀려야 한다 (상관된 LF 여러 개는 하나와 같다).
- 함정 1: LF를 test 세트를 보면서 고치면 test에 overfit된다. LF 개발은 dev set으로, 평가는 따로 둔 test로.
- 함정 2: coverage가 편향된다. LF가 쉬운 사례만 라벨하면 학습 데이터에 어려운 사례가 빠진다 (§6의 high threshold와 같은 문제).
- 함정 3: GPS 같은 context는 **배포 시에는 없을 수 있다.** 학습 라벨에만 쓰고 모델 입력에는 넣지 않으면 괜찮다. 입력에 넣으면 "GPS가 있어야만 동작하는 모델"이 된다.

## 6. Semi-supervised와 pseudo-labeling — 무라벨 로그를 teacher가 라벨한다

### 6.1 직관

**semi-supervised learning**은 라벨이 있는 작은 데이터와 라벨이 없는 큰 데이터를 함께 쓰는 학습이다. 가장 단순한 방법이 **pseudo-labeling**(self-training)이다.

1. 라벨 있는 데이터로 모델(teacher)을 학습한다.
2. teacher로 무라벨 데이터를 예측한다. 예측 클래스를 **pseudo-label**(가짜 라벨)로 쓴다.
3. teacher가 **충분히 확신하는**(max 확률 ≥ threshold) 것만 골라 원래 라벨 데이터에 더한다.
4. 합친 데이터로 모델(student)을 학습한다. 필요하면 반복한다.

C5 §4에서 같은 구조를 distillation 관점으로 봤다 — 서버의 큰 teacher가 무라벨 로그에 soft label을 붙이고 기기용 작은 student가 배운다. 여기서는 **hard pseudo-label + confidence threshold**의 효과를 본다.

### 6.2 threshold의 딜레마

threshold를 높이면 pseudo-label이 더 정확해진다. 그러면 무조건 높이는 게 좋을까? 실험으로 보자.

**예제 9.** 이 코드는 사람 라벨 40개로 큰 teacher(RF)를 학습하고, 무라벨 3000개에 pseudo-label을 붙여 threshold별로 작은 student(logreg, 기기용이라고 생각)를 학습한다. 비교 기준은 student를 라벨 40개만으로 학습한 경우와, 진짜 라벨 3040개로 학습한 경우다 (seed 5개 평균).

```python
import numpy as np
from h4_data import make_windows, features
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
mt, yt, _ = make_windows(4000, seed=99); Xt = features(mt)
student = lambda: make_pipeline(StandardScaler(), LogisticRegression(max_iter=2000))  # 기기용 소형
res, mix = {}, {}
for s in range(5):
    m, y, _ = make_windows(3040, seed=s); X = features(m)
    Xl, yl, Xu, yu = X[:40], y[:40], X[40:], y[40:]          # 라벨 40개 + 무라벨 3000개
    teacher = RandomForestClassifier(200, random_state=0).fit(Xl, yl)  # 서버용 큰 모델
    P = teacher.predict_proba(Xu); conf, pl = P.max(1), teacher.classes_[P.argmax(1)]
    acc = lambda mdl: (mdl.predict(Xt) == yt).mean()
    res.setdefault("teacher(RF)", []).append((acc(teacher), np.nan, np.nan))
    res.setdefault("student 40 only", []).append((acc(student().fit(Xl, yl)), 0, np.nan))
    for th in (0.0, 0.5, 0.7, 0.9):
        k = conf >= th                                        # 확신 높은 pseudo-label만
        st = student().fit(np.vstack([Xl, Xu[k]]), np.concatenate([yl, pl[k]]))
        res.setdefault(f"student th={th:.1f}", []).append((acc(st), k.mean(), (pl[k] == yu[k]).mean()))
        mix.setdefault(th, []).append(np.bincount(yu[k], minlength=4) / k.sum())
    res.setdefault("student 3040 true", []).append((acc(student().fit(X, y)), 1, 1))
for name, r in res.items():
    a, cov, pacc = np.array(r).mean(0)
    print(f"{name:17s} acc={a:.3f}  used_unlab={cov:.2f}  pseudo_acc={pacc:.3f}")
for th in (0.0, 0.9):
    print(f"true class mix of used windows th={th}: {np.round(np.mean(mix[th], 0), 2)}  (still,walk,run,other)")
```

그림 5 — confidence threshold 대 student 정확도와 pseudo-label 정확도 (예제 9의 실제 출력). threshold를 올리면 pseudo-label은 깨끗해지지만(주황, 0.927 → 0.977) student는 오히려 나빠진다(파랑, 0.918 → 0.885). 아래 숫자는 사용된 무라벨 창의 비율.

출력에서 볼 것:

1. **pseudo-label만으로 student가 0.887 → 0.918**로 올랐다. 진짜 라벨 3040개(0.939)와의 격차의 약 60%를 사람 라벨 없이 메웠다. teacher(0.925)의 지식이 무라벨 데이터를 통해 작은 모델로 옮겨 간 것이다.
2. **threshold 0.9는 pseudo-label 정확도 0.977인데 student는 0.885** — 라벨 40개만 쓴 것과 같다. 왜?
3. 마지막 두 줄이 답이다. threshold 0.0에서는 실제 클래스 비율이 25%씩 고르다. threshold 0.9에서는 **still 35% / other 30% / walk 16% / run 18%**. teacher가 확신하는 것은 **쉬운 창**(정지, 불규칙)이고, 정작 student가 배워야 할 **walk ↔ run 경계 근처 창**은 빠진다. 깨끗하지만 쓸모없는 라벨이다.

말로 하면: pseudo-label의 가치는 정확도 × **정보량**이다. 경계에서 먼 쉬운 샘플은 정확하지만 결정 경계를 움직이지 않는다. 이것은 §7 active learning과 정반대 방향의 선택이다 (active learning은 일부러 **불확실한** 샘플을 사람에게 보낸다).

### 6.3 실무 규칙과 함정

| 규칙 | 이유 |
|---|---|
| threshold는 validation 세트로 고른다 (높을수록 좋다고 가정 금지) | 위 실험처럼 정확도와 정보량의 trade-off |
| 클래스별 threshold 또는 클래스별 상한 수 | 쉬운 클래스가 pseudo-label을 독점하는 것 방지 |
| teacher는 student보다 강해야 이득이 크다 | 같은 모델로 자기 자신을 라벨하면 자기 실수를 강화한다 (confirmation bias) |
| soft label(확률) 사용 고려 | 경계 샘플의 불확실성도 정보다 (C5 §1) |
| test 세트는 절대 pseudo-label 금지 | 사람 라벨만 평가 기준 |
| 반복할 때는 매 라운드 사람 표본으로 pseudo-label 정확도 확인 | 오류가 누적되는지 감시 |

임베디드 연결: 이 구조가 C5에서 말한 "서버 teacher + 기기 student"의 데이터 파이프라인이다. 기기는 무라벨 로그를 올리고(H1 ~ H3), 서버의 큰 모델이 라벨을 붙이고, 기기 모델이 그걸로 다시 학습된다. 기기에서 할 일은 **teacher가 쓸 수 있는 품질의 raw 로그**(동기화, 드롭 없음, 메타데이터)를 올리는 것이다.

## 7. Active learning — 사람 라벨을 어디에 쓸 것인가

### 7.1 직관

라벨 예산이 정해져 있다: "라벨러가 이번 주에 창 200개를 볼 수 있다". 무라벨 창은 3000개. 어떤 200개를 보여 줄까?

**active learning**은 현재 모델이 **가장 헷갈려 하는** 샘플을 골라 사람에게 라벨을 받고, 모델을 다시 학습하고, 다시 고르는 반복이다. 이미 잘 맞히는 쉬운 샘플에 사람 시간을 쓰지 않는다.

```
     ┌────────────────────────────────────────────┐
     ▼                                            │
 [라벨 세트] ──학습──▶ [모델] ──예측──▶ [무라벨 pool]  │
                                   │ 불확실도 점수     │
                                   ▼                 │
                          상위 b개 선택 ──▶ 사람 라벨 ─┘
```

Don에게 익숙한 말로 하면: 양산 검증에서 모든 corner를 같은 횟수로 돌리지 않고, **margin이 작은 조건**(온도·전압 끝)에 시험 시간을 몰아주는 것과 같다. margin이 큰 조건은 몇 번만 봐도 결론이 난다.

### 7.2 불확실도 점수 세 가지

모델이 창 하나에 대해 확률 p = (p₁, …, p_K)를 낸다. p₍₁₎ ≥ p₍₂₎는 가장 큰 확률과 두 번째 확률이다.

```
least confidence :  1 − p₍₁₎                    (최고 확률이 낮을수록 불확실)
margin           :  −(p₍₁₎ − p₍₂₎)              (1등과 2등 차이가 작을수록 불확실)
entropy          :  −∑ₖ pₖ · log pₖ              (분포가 퍼질수록 불확실)
```

손계산: 두 창의 확률이 A = (0.50, 0.48, 0.01, 0.01), B = (0.40, 0.20, 0.20, 0.20)이라 하자.

```
least conf : A = 0.50,  B = 0.60            → B가 더 불확실
margin     : A: 0.50 − 0.48 = 0.02,  B: 0.40 − 0.20 = 0.20   → A가 더 불확실
entropy    : A ≈ −(0.5·ln0.5 + 0.48·ln0.48 + 2·0.01·ln0.01) ≈ 0.347 + 0.352 + 0.092 = 0.791
             B ≈ −(0.4·ln0.4 + 3·0.2·ln0.2) ≈ 0.367 + 0.966 = 1.332   → B가 더 불확실
```

말로 하면: A는 "walk냐 run이냐 딱 둘 사이에서 고민"이고, B는 "전반적으로 모르겠음"이다. margin은 **두 클래스 사이 결정 경계**에 있는 샘플을 고르고, entropy는 **모든 클래스가 섞인** 샘플을 고른다. 분류기가 경계를 다듬는 데는 보통 A 같은 샘플이 더 쓸모 있다.

### 7.3 코드로 확인 — 라벨 예산 루프

**예제 10.** 이 코드는 무라벨 pool 3000개에서 무작위 10개로 시작해, 매 라운드 10개씩 골라 "사람"(= 합성 데이터의 정답)에게 라벨을 받아 200개까지 늘린다. random과 세 가지 불확실도를 비교한다 (seed 5개 평균).

```python
import numpy as np
from h4_data import make_windows, features
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
mt, yt, _ = make_windows(4000, seed=99); Xt = features(mt)
mk = lambda: make_pipeline(StandardScaler(), LogisticRegression(max_iter=2000))

def score(P, how):                                  # 클수록 "라벨 받고 싶은" 창
    Ps = np.sort(P, 1)
    if how == "least_conf": return 1 - Ps[:, -1]
    if how == "margin":     return -(Ps[:, -1] - Ps[:, -2])
    if how == "entropy":    return -(P * np.log(P + 1e-12)).sum(1)

def run(how, seed, start=10, batch=10, budget=200):
    m, y, _ = make_windows(3000, seed=seed); X = features(m)    # 무라벨 pool (y = 사람 오라클)
    rng = np.random.default_rng(seed)
    lab = list(rng.choice(len(y), start, replace=False))         # cold start: 무작위 10개
    curve = []
    while True:
        clf = mk().fit(X[lab], y[lab])
        curve.append((len(lab), (clf.predict(Xt) == yt).mean()))
        if len(lab) >= budget: return curve
        pool = np.setdiff1d(np.arange(len(y)), lab)
        if how == "random": pick = rng.choice(pool, batch, replace=False)
        else: pick = pool[np.argsort(-score(clf.predict_proba(X[pool]), how))[:batch]]
        lab += list(pick)                                        # "사람에게 보내 라벨 받기"
for how in ("random", "least_conf", "margin", "entropy"):
    c = np.mean([[a for _, a in run(how, s)] for s in range(5)], axis=0)   # seed 5개 평균
    print(f"{how:10s} " + " ".join(f"{10 * (i + 1)}:{c[i]:.3f}" for i in (0, 1, 3, 5, 9, 14, 19)))
```

출력에서 볼 것:

1. **margin sampling이 가장 좋다.** 40개로 0.906(random 200개 수준), 100개로 0.937(pool 전체 라벨 수준). 이 과제의 어려움은 walk ↔ run 경계 하나에 몰려 있어서, "두 클래스 사이" 샘플을 고르는 margin이 정확히 그곳을 판다.
2. **least confidence는 cold start에서 random보다 나쁘다** (20개: 0.728 vs 0.813). 처음 10개로 학습한 모델은 엉망이라 "불확실하다"는 판단 자체가 틀린다. 엉뚱한 곳을 반복해서 고를 수 있다.
3. **entropy는 이 과제에서 random과 비슷하다** (200개: 0.906 vs 0.905). 4클래스 전체가 섞인 샘플을 고르는데, 이 데이터에서 그런 샘플은 특징 공간 구석의 드문 창이라 경계를 다듬는 데 별 도움이 안 된다.
4. **200개 margin(0.962)이 pool 전체 3000개 라벨(0.937)보다 높다.** 처음 보면 이상하지만, logreg처럼 단순한 모델에서는 경계 근처 샘플만으로 학습하면 경계가 더 정확해지는 일이 있다. 그러나 이것은 이 합성 데이터의 성질이고, 일반적으로 기대할 일은 아니다. 오히려 active learning으로 모은 데이터는 **분포가 편향**되어 있다는 신호로 읽어야 한다(아래 함정).

### 7.4 언제 도움이 되고, 언제 함정인가

| 상황 | active learning이 | 이유 |
|---|---|---|
| 무라벨은 많고 라벨이 비쌈 (영상 onset 라벨) | 도움 | 사람 시간을 경계 사례에 집중 |
| 희귀 클래스 (탭, wake word, 낙상) | 크게 도움 | random으로는 희귀 사례가 거의 안 뽑힘 |
| cold start (라벨 수십 개) | 위험 | 모델의 불확실도가 믿을 수 없음 → 처음엔 random·층화 표본으로 시작 |
| 배치로 한 번에 많이 고를 때 | 위험 | 비슷한 샘플 b개가 같이 뽑힘(중복) → **diversity**(클러스터별·사용자별 분산) 섞기 |
| 고른 데이터로 평가 | 금지 | 편향된 표본 — 평가는 random 표본으로 |
| 라벨 noise가 큰 과제 | 주의 | 불확실한 샘플은 사람에게도 어렵다 → 라벨 noise가 그 샘플에 몰림 |
| 모델을 나중에 바꿈 | 주의 | 모델 A가 고른 데이터가 모델 B에게도 좋다는 보장 없음 |

실무 레시피(흔한 형태): 첫 라운드는 사용자·세션·클래스별로 층화한 random 표본 → 이후 라운드는 margin 상위 + diversity(예: 특징 공간 클러스터별로 몇 개씩) + random 일부(분포 감시용)를 섞는다.

임베디드 연결: active learning의 "pool"은 기기에서 올라온 로그다. 기기가 **모든 로그를 올릴 수 없으면**(전력·BLE 대역폭·프라이버시), 기기에서 모델이 애매해할 때만 창을 캡처해 올리는 **온디바이스 선택**이 active learning의 첫 단계가 된다 (§10에 C 예제).

## 8. Wake word · 오디오 라벨링의 특수성

### 8.1 positive — 다양성이 양보다 중요하다

wake word(KWS) 모델의 positive는 "hey hark"를 말한 오디오 클립이다 (B5 §3). 수집 시 챙길 축:

| 축 | 예 | 왜 |
|---|---|---|
| 화자 | 수백 명 이상, 성별·나이·억양·방언 | 특정 화자군만 FRR이 높으면 제품 결함 |
| 발화 방식 | 빠르게·느리게·속삭임·외침, 문장 중간 | 실제 사용은 또박또박하지 않다 |
| 거리·방향 | 입 가까이, 팔 길이, 방 건너 | 마이크 SNR·잔향이 바뀐다 (G4) |
| 환경 | 조용한 방, 카페, 차 안, 바람 | 배경 잡음 |
| 기기 상태 | 착용 위치, 마이크 가림, 음악 재생 중 | 실제 기기 경로로 녹음해야 함 |
| 증강 | 잡음 합성, 잔향(RIR), 속도·피치 변화 | 녹음 수를 늘리는 대신 (A4 §5.4) |

**split은 화자 단위로** 한다. 같은 사람의 발화가 train과 test에 섞이면 점수가 부풀려진다 (A4 §3, H5).

### 8.2 negative — 수천 시간의 "아닌 것"

negative는 키워드가 **없는** 오디오다. 제품 요구는 보통 "시간당 false accept(FA) x회 이하"이므로(A4 §9), negative는 클립 수가 아니라 **시간**으로 센다. 예를 들어 목표가 "10시간에 1회 이하"라면, 그걸 통계적으로 확인하려면 negative 평가 오디오만 수백 시간이 필요하다 (FA 0회를 관측해도 95% 신뢰 상한은 대략 3/T — "rule of three" — 이므로 T = 30시간 무오작동이면 상한 0.1회/시간).

negative의 출처: 일반 대화 corpus, TV·팟캐스트·음악, 생활 소음, **우리 기기 dogfood 로그**(가장 중요 — 실제 마이크·실제 환경). 라벨은 대부분 공짜다: "키워드를 말하지 않은 구간"이면 된다. 다만 dogfood 로그에는 진짜 키워드 발화가 섞여 있을 수 있어서 확인이 필요하다.

### 8.3 hard negative mining — 현장 오작동에서 배운다

일반 negative는 대부분 **쉬운** negative다. 모델이 정말 헷갈리는 것은 키워드와 비슷한 말("hey mark", "hey, park it")이다. 이런 **hard negative**는 일반 corpus에 드물어서 학습 데이터에 거의 없다. 그래서 배포 후 현장에서 **false accept가 난 오디오**를 모아(사용자 동의 하에) negative로 추가하고 재학습한다. 이것이 **hard negative mining**이다.

**예제 11.** 이 코드는 6차원 가짜 embedding으로 키워드(positive), 일반 negative, 비슷한 말(confusable)을 만든다. v1은 일반 negative만으로 학습한다. 그다음 "현장 로그 48시간"에서 FA가 난 창을 자동 수집해 negative로 추가하고 재학습하기를 두 번 한다. FRR은 매번 5%로 고정하고 FA/시간을 출처별로 잰다.

```python
import numpy as np
from sklearn.linear_model import LogisticRegression
rng = np.random.default_rng(0)
D = 6                                                    # 가짜 "embedding" 6차원
mu_kw = np.array([2.5, 2.5, 2.5, 2.5, 1.5, 1.5])         # "Hey Hark"
mu_cf = np.array([2.5, 2.5, 2.5, 2.5, -1.5, -1.5])       # 비슷한 말 ("hey Mark" 같은) = hard negative
kw  = lambda n: rng.normal(mu_kw, 1.0, (n, D))
gen = lambda n: rng.normal(0.0, 1.0, (n, D))             # 일반 대화·소음 = easy negative
cf  = lambda n: rng.normal(mu_cf, 1.0, (n, D))

def field(h):                  # 현장 로그 h시간: 1 s hop 창, 시간당 confusable 30번 (가정)
    return gen(3570 * h), cf(30 * h)
def evaluate(clf, tag):
    th = np.quantile(clf.predict_proba(kw(2000))[:, 1], 0.05)   # FRR 5%가 되는 임계값
    g, c = (np.sum(clf.predict_proba(F)[:, 1] >= th) / 24 for F in field(24))
    print(f"{tag:22s} th={th:.3f}  FA/hour={g + c:5.2f}  (generic {g:.2f} + confusable {c:.2f})")
    return th
X = np.vstack([kw(1000), gen(20000)]); y = np.r_[np.ones(1000), np.zeros(20000)]
clf = LogisticRegression(max_iter=1000).fit(X, y)
th = evaluate(clf, "v1 generic negatives")
for rnd in (1, 2):                                       # dogfood 로그에서 오작동 수집 → 재학습
    F = np.vstack(field(48))
    fa = F[clf.predict_proba(F)[:, 1] >= th]             # false accept = 자동으로 모인 hard negative
    X = np.vstack([X, fa]); y = np.r_[y, np.zeros(len(fa))]
    clf = LogisticRegression(max_iter=1000).fit(X, y)
    th = evaluate(clf, f"v{rnd + 1} +{len(fa)} mined FAs")
```

```text
v1 generic negatives   th=0.882  FA/hour=18.29  (generic 0.42 + confusable 17.88)
v2 +881 mined FAs      th=0.311  FA/hour= 5.46  (generic 4.50 + confusable 0.96)
v3 +261 mined FAs      th=0.174  FA/hour= 3.92  (generic 2.50 + confusable 1.42)
```

출력에서 볼 것:

2. **mining 한 번에 881개의 hard negative가 자동으로 모였다** (48시간 로그의 FA). 사람이 라벨할 필요가 거의 없다 — "키워드가 아닌데 깨어났다"는 사실 자체가 라벨이다. 실제로는 사용자의 "취소" 행동이나 사람 확인으로 진짜 FA인지 검증한다 (진짜 키워드를 negative로 넣으면 큰일).
3. **총 FA는 18.29 → 5.46 → 3.92로 줄었지만, generic FA는 늘었다.** 선형 모델이 confusable을 밀어내느라 결정 경계를 돌렸고, 그 대가로 일반 negative 일부가 넘어왔다. 교훈: mining 후에는 **전체 negative 세트로 다시 평가**해야 하고, 남은 오류가 모델 용량의 한계라면 더 큰 모델·더 좋은 특징이 필요하다. 데이터만으로는 안 된다.

### 8.4 keyword timestamp와 forced alignment

KWS 학습에서 "창 안에 키워드가 통째로 들어 있나"(§3의 contains 규칙)를 판단하려면 **키워드의 시작·끝 시각**이 필요하다. 사람이 파형을 보고 찍을 수도 있지만 느리다. 흔한 방법은 **forced alignment**다: 오디오와 그 전사(transcript)가 주어졌을 때, 음향 모델로 각 단어·음소가 어디에 있는지 정렬 경로를 찾는 것이다. 개념적으로는 B5 §4의 CTC처럼 "모든 정렬 중 가장 그럴듯한 하나"를 고르는 Viterbi 탐색이다. Montreal Forced Aligner 같은 도구가 알려져 있다 (구체 사용법은 도구 문서 확인). 정렬 결과는 수십 ms 오차가 있으므로 창 라벨에는 §3.4의 margin을 둔다.

ASR 전사 라벨은 보통 **기존 ASR로 초벌 전사 → 사람이 수정**하는 방식으로 비용을 줄인다. 사람이 처음부터 받아쓰는 것보다 빠르지만, 초벌의 실수를 사람이 그대로 넘기는 편향(automation bias)이 생기므로 일부는 처음부터 전사해 비교한다.

## 9. 비용 · 처리량 · 도구 · 프라이버시 · 버전 관리

### 9.1 라벨링 비용을 어림하는 법

라벨링 비용은 "데이터 1분을 라벨하는 데 사람이 몇 분 쓰나"(배수)로 어림한다. 배수는 과제·도구·라벨러 숙련도에 따라 몇 배씩 다르므로 **반드시 파일럿으로 직접 잰다.** 아래 숫자는 이 노트에서 계산 연습을 위해 정한 **가정치**이고, 업계 표준값이 아니다.

**예제 12.** 이 코드는 dogfooder 100명 × 2시간 데이터를 과제 종류별로 라벨할 때의 작업 시간과 비용을 어림한다 (2중 라벨링 + QA 20% 가산, 시급 $25 가정).

```python
# 라벨링 비용 어림 — 배수(annotation minutes per minute of data)는 전부 "가정치"다
tasks = {                       # task: (데이터 1분당 작업 분, 설명)
    "window class check":     (0.5, "스크립트 세션 라벨 확인·수정"),
    "event onset/offset":     (6.0, "영상 보며 탭·제스처 경계 찍기"),
    "speech transcript":      (5.0, "대화 받아쓰기 (깨끗한 음성 가정)"),
    "wake-word clip yes/no":  (1.5, "2초 클립 듣고 예/아니오"),
}
data_min = 100 * 2 * 60          # dogfooder 100명 × 2시간 = 12,000분
rate = 25.0                      # 작업자 시급 $ (가정), 2중 라벨링 + QA 20% 가산
for name, (mult, desc) in tasks.items():
    hours = data_min * mult / 60 * 2 * 1.2
    print(f"{name:22s} x{mult:<4} -> {hours:7,.0f} annotator-h  ${hours * rate:9,.0f}  ({desc})")
```

```text
window class check     x0.5  ->     240 annotator-h  $    6,000  (스크립트 세션 라벨 확인·수정)
event onset/offset     x6.0  ->   2,880 annotator-h  $   72,000  (영상 보며 탭·제스처 경계 찍기)
speech transcript      x5.0  ->   2,400 annotator-h  $   60,000  (대화 받아쓰기 (깨끗한 음성 가정))
wake-word clip yes/no  x1.5  ->     720 annotator-h  $   18,000  (2초 클립 듣고 예/아니오)
```

출력에서 볼 것: 같은 200시간 데이터라도 **과제 모양에 따라 비용이 12배 차이**난다 (창 확인 240시간 vs onset 찍기 2,880시간). 손으로 확인: 12,000분 × 6.0 / 60 = 1,200시간, × 2(2중) × 1.2(QA) = 2,880시간. 그래서 §2의 원칙 — **녹음할 때 라벨이 생기게 설계하고, 사람 시간은 정밀 라벨이 꼭 필요한 평가 세트와 active learning이 고른 샘플에만 쓴다** — 이 돈으로 정당화된다.

처리량(throughput)을 올리는 도구 쪽 요령:

| 요령 | 효과 |
|---|---|
| 모델·LF가 초벌 라벨 → 사람은 수정만 (pre-labeling) | 처음부터 찍는 것보다 빠름. 단 초벌 편향 주의 (§8.4) |
| 예/아니오 확인 과제로 쪼개기 | 구간 찍기보다 훨씬 빠름 |
| 영상·센서 곡선·오디오를 한 화면, 단축키, 재생 속도 조절 | 작업자 피로 감소 |
| 애매하면 unknown/ignore 버튼 (고민 시간 상한) | 시간 절약 + noise 감소 |
| gold 문항 자동 삽입, 라벨러별 대시보드 | 품질 문제를 빨리 발견 (§4.3) |

### 9.2 프라이버시 — 라벨러는 raw 데이터를 본다

라벨링은 **사람이 raw 데이터를 직접 보고 듣는** 단계다. always-listening 기기라면 라벨러가 사용자의 대화를 듣게 된다. 그래서 라벨 파이프라인은 프라이버시 설계의 중심이다 (자세한 내용은 H6).

- 수집 동의서에 "사람이 검토할 수 있음"을 명시한다.
- 라벨러에게 필요한 최소한만 보여 준다: wake word 확인이면 2 s 클립만, 앞뒤 대화는 잘라 낸다. IMU 라벨이면 영상 대신 스틱 피겨·골격만.
- 사용자 ID·위치 같은 메타데이터는 라벨 도구에서 가린다 (가명 ID).
- 라벨러 접근 로그, 다운로드 금지, 보관 기간 후 삭제.
- 가능하면 사람 대신 §5 ~ §6의 자동 라벨을 쓴다 — 프라이버시 측면에서도 이득이다.

### 9.3 라벨은 raw와 따로 버전 관리한다

raw 센서 로그는 크고(GB ~ TB), **한 번 쓰면 바뀌지 않는다**(immutable). 라벨은 작고(KB), **자주 바뀐다** — 재라벨, 스키마 v1 → v2, 판정(adjudication), 경계 수정. 둘을 한 파일에 묶으면 라벨 한 줄을 고칠 때마다 raw 전체의 새 버전이 생긴다. 그래서 라벨은 **raw의 해시를 가리키는 별도 파일**로 둔다 (데이터셋 버전 관리 전반은 H5).

**예제 13.** 이 코드는 가짜 raw 세션의 SHA-256을 라벨 파일에 기록하고, 라벨만 v1 → v2로 고쳤을 때 라벨 해시는 바뀌고 raw 해시는 그대로임을 보인다.

```python
import hashlib, json, numpy as np
raw = np.random.default_rng(0).normal(0, 1, (600, 3)).astype(np.float32).tobytes()  # 가짜 raw 세션
sha = hashlib.sha256(raw).hexdigest()[:16]
labels_v1 = {"raw_sha256": sha, "schema": "gesture-v2", "annotator": "ann1", "tool": "video",
             "intervals": [{"label": "tap", "start_s": 1.20, "end_s": 1.45},
                           {"label": "unknown", "start_s": 3.00, "end_s": 3.80}]}
labels_v2 = dict(labels_v1, annotator="ann1+ann2:adjudicated",
                 intervals=[{"label": "tap", "start_s": 1.22, "end_s": 1.44},
                            {"label": "wrist_raise", "start_s": 3.00, "end_s": 3.80}])
for v in (labels_v1, labels_v2):                 # 라벨 파일은 작고 자주 바뀐다 → 따로 버전
    blob = json.dumps(v, sort_keys=True).encode()
    print(f"label_sha={hashlib.sha256(blob).hexdigest()[:12]}  bytes={len(blob)}  raw_sha={v['raw_sha256']}")
print("raw bytes:", len(raw), " raw unchanged across label versions:", hashlib.sha256(raw).hexdigest()[:16] == sha)
```

```text
label_sha=f680f73058ef  bytes=212  raw_sha=2945e2fc4ee8f98b
label_sha=d5dc72108c39  bytes=234  raw_sha=2945e2fc4ee8f98b
raw bytes: 7200  raw unchanged across label versions: True
```

출력에서 볼 것: 라벨 파일은 200바이트대, raw는 7,200바이트(실제로는 수 MB ~ GB)다. 라벨 v1 → v2에서 `label_sha`는 바뀌고 `raw_sha`는 그대로다. 데이터셋 버전 = (raw 해시 목록, 라벨 해시 목록, 창 규칙·전처리 설정)의 조합으로 정의하면, "모델 v7은 라벨 v2 + center 규칙으로 학습했다"를 정확히 재현할 수 있다. 라벨 파일에는 **누가(annotator), 어떤 도구로, 어떤 스키마 버전으로** 만들었는지도 같이 적는다 — §4의 품질 분석이 이 필드에 의존한다.

Don에게 익숙한 말로 하면: 펌웨어 바이너리와 그 바이너리로 돌린 시험 결과(pass/fail 판정)를 따로 저장하고, 결과 파일이 바이너리의 빌드 해시를 가리키는 것과 같다. 판정 기준이 바뀌면 결과만 다시 만들고 바이너리는 그대로 둔다.

| 마커 레코드 (버튼, BLE 명령) 로그 포맷에 포함 | scripted session 라벨이 공짜 | H1, §2.2 |

| 드롭·saturation 구간 표시 | 자동 ignore 라벨 | H7, G7 §3 |

마지막 두 줄을 C로 보자. **예제 14.** 이 C 코드는 추론마다 top-1과 top-2 확률의 차(margin)를 계산하고, margin이 작은 "애매한 창"만 캡처 후보로 삼되, **token bucket**으로 시간당 캡처 수를 제한한다. 캡처는 flash 쓰기와 업로드를 부르므로 전력·저장 예산이 있다 (H1). Don에게 익숙한 rate limiter 패턴이다.

```c
#include <stdint.h>
#include <stdio.h>

/* 추론마다 호출: top-2 확률 차(margin)가 작으면 "애매한 창" → 로그 캡처 후보.
   예산(budget): 시간당 최대 캡처 수를 token bucket으로 제한 (전력·flash·업로드 보호). */
typedef struct { float tokens, per_sec, cap; uint32_t last_ms; } bucket_t;

static int take(bucket_t *b, uint32_t now_ms) {
    b->tokens += (float)(now_ms - b->last_ms) / 1000.0f * b->per_sec;   /* 시간만큼 충전 */
    if (b->tokens > b->cap) b->tokens = b->cap;
    b->last_ms = now_ms;
    if (b->tokens >= 1.0f) { b->tokens -= 1.0f; return 1; }
    return 0;
}

static float margin(const float *p, int k) {             /* top1 − top2 */
    float a = 0.0f, b = 0.0f;
    for (int i = 0; i < k; i++) {
        if (p[i] > a) { b = a; a = p[i]; } else if (p[i] > b) b = p[i];
    }
    return a - b;
}

int main(void) {
    bucket_t bk = { 2.0f, 6.0f / 3600.0f, 2.0f, 0 };      /* 시간당 6개, 최대 2개 몰아서 */
    uint32_t seed = 12345u; int ambiguous = 0, captured = 0;
    for (uint32_t t_ms = 0; t_ms < 3600u * 1000u; t_ms += 500u) {      /* 1시간, 0.5 s hop */
        float p[4], s = 0.0f;
        for (int i = 0; i < 4; i++) {                    /* 가짜 softmax 출력 (LCG 난수) */
            seed = seed * 1664525u + 1013904223u;
            p[i] = (float)((seed >> 8) & 0xFFFF) / 65536.0f + (i == 0 ? 1.5f : 0.0f);
            s += p[i];
        }
        for (int i = 0; i < 4; i++) p[i] /= s;
        if (margin(p, 4) < 0.15f) { ambiguous++; captured += take(&bk, t_ms); }
    }
    printf("windows=7200 ambiguous=%d captured=%d (budget 6/h + burst 2)\n", ambiguous, captured);
    return 0;
}
```

```text
windows=7200 ambiguous=28 captured=7 (budget 6/h + burst 2)
```

출력에서 볼 것: 1시간 동안 창 7200개 중 28개가 애매했고, 예산(시간당 6개 + 처음 burst 2개, 최대 8개) 때문에 7개만 캡처됐다. 실제 기기에서는 캡처한 창의 앞뒤 raw(예: 링버퍼의 직전 2 s)를 같이 저장해야 사람이 라벨할 수 있다. 가짜 확률은 LCG 난수로 만든 것이라 비율 자체에는 의미가 없다. `-Wall -Wextra` 경고 0개로 컴파일된다.

설계 질문 몇 가지(면접에서도 나올 수 있다):

- margin 문턱과 예산을 **원격 설정**(H8)으로 바꿀 수 있게 하라. 모델이 바뀌면 margin 분포가 바뀐다.
- 캡처는 **사용자 동의 상태**를 확인한 뒤에만 (H6). wake word FA 캡처는 특히 민감하다.
- 캡처 기준 자체가 데이터를 편향시킨다. 일부는 무작위로 캡처해서 "모델이 확신했지만 틀린" 사례도 잡아야 한다 (모델이 확신하는 오류는 margin으로 안 잡힌다).

## 12. 면접에서 이렇게 말한다

**Q.** "How would you get ground-truth labels for gestures from 100 dogfooders?"

**A.** 세 층으로 한다. (1) 첫 주는 앱이 지시하는 scripted session으로 클래스별 데이터를 빠르게 모으고 프롬프트 시각을 기기 시계 마커로 남겨 라벨을 자동으로 얻는다. (2) 일부 참가자는 폰 영상을 같이 찍고 박수로 동기화해 정밀 onset 라벨 평가 세트를 만든다. (3) 나머지 기간은 free-living 로그를 올리고, 모델이 감지한 이벤트에 EMA 예/아니오 확인을 받아 실제 분포의 positive·false positive를 모은다. 스키마에 null·unknown·ignore를 두고, 사용자 단위로 split한다.

> I'd layer it. First, scripted sessions where the app prompts each gesture and the device logs START/STOP markers on the same clock as the IMU, so labels come for free. Second, a subset records phone video with a clap at start and end for sync, and annotators mark precise onsets — that becomes the held-out evaluation set. Third, free-living logging with lightweight in-app confirmations ("did you just tap?") to capture real-world positives and false positives. The schema includes null, unknown and ignore classes, and all splits are by user.

**Q.** "Labels are noisy — how do you measure and handle it?"

**A.** 측정: 무작위 표본을 전문가가 재라벨해서 noise 비율과 혼동 구조를 직접 보고, 라벨러 간 Cohen's kappa와 gold 문항 정확도를 배치별로 추적해 drift를 잡는다. 처리: 가중 투표로 합치고, 의심 항목(out-of-fold 예측과 크게 다른 것)만 재라벨하고, 경계는 ignore margin을 둔다. 가장 중요한 것은 test 세트를 깨끗하게 유지하는 것 — noisy test는 모델 개선을 가린다.

> I measure it directly: an expert relabels a random sample to estimate the noise rate and confusion structure, and I track inter-annotator kappa and gold-question accuracy per batch to catch drift. To handle it, I weight annotators by estimated accuracy instead of plain majority vote, relabel only suspicious items flagged by out-of-fold predictions, and mask boundary regions with an ignore margin. Above all I keep the test set clean with multiple labels plus adjudication, because a noisy test set caps the accuracy you can measure.

**Q.** "Explain active learning and when it helps."

**A.** 현재 모델이 가장 헷갈리는 샘플(margin이 작은 것 등)을 골라 사람에게 라벨을 받고 재학습하는 반복이다. 무라벨은 많고 라벨이 비쌀 때, 희귀 클래스가 있을 때 크게 도움이 된다. 내 합성 실험에서는 margin sampling이 random의 약 1/5 라벨로 같은 정확도를 냈다. 단 cold start에서는 불확실도가 믿을 수 없어서 random으로 시작해야 하고, 배치 선택에는 diversity를 섞고, 평가는 반드시 random 표본으로 한다.

> Active learning is a loop: train, score the unlabeled pool by uncertainty — least confidence, margin or entropy — send the most uncertain items to annotators, retrain. It pays off when unlabeled data is abundant, labels are expensive, or the classes of interest are rare. In a synthetic experiment margin sampling matched random sampling's accuracy with about one fifth of the labels. The caveats are cold start, where the model's uncertainty is unreliable so I seed with a stratified random sample, redundancy within a batch, so I mix in diversity, and bias, so evaluation always uses a random sample.

**Q.** "How do you collect negatives for a wake word?"

**A.** negative는 클립 수가 아니라 시간으로 센다 — 요구가 시간당 FA이기 때문이다. 일반 대화·미디어·소음 수백 ~ 수천 시간에, 가장 중요한 것은 우리 기기 마이크로 녹음한 dogfood 로그다. 그리고 배포 후 현장 false accept를 동의 하에 모아 hard negative로 넣고 재학습한다. 합성 실험에서 confusable 단어가 FA의 대부분이었고 mining으로 크게 줄었지만, 다른 negative의 FA가 늘어서 전체 negative 세트로 재평가가 필수였다.

> I budget negatives in hours, not clips, because the spec is false accepts per hour — hundreds to thousands of hours of conversation, media and noise, and most importantly audio recorded through our own device's mic path from dogfooders. After launch, with consent, I mine false accepts from the field as hard negatives and retrain. Each round must be re-evaluated on the full negative set — in my simulation mining cut confusable-word false accepts sharply but raised generic ones, so you can trade one failure mode for another.

**Q.** "What window labeling rule do you use at event boundaries?"

**A.** 이벤트 길이와 hop에 맞춰 고른다. 창보다 짧은 이벤트(탭, wake word)는 "창 안에 통째로 포함"이면 양성으로, 긴 활동은 center나 majority로 한다. majority를 짧은 이벤트에 쓰면 양성이 하나도 안 생길 수 있다. 경계 근처 애매한 창은 ignore margin으로 loss에서 빼서, 라벨 경계 오차(영상이면 수십 ms)만큼의 noise를 학습하지 않게 한다. 그리고 이벤트 길이별로 "양성 창을 받은 이벤트 비율"을 꼭 확인한다.

> It depends on event length relative to the window and hop. For events shorter than the window — taps, keywords — a window is positive only if it fully contains the event; for long activities I use the center or majority label. Majority on short events can silently produce zero positives. Windows that straddle a boundary get an ignore margin, masked out of the loss, sized to roughly twice the label timing error. I always check, per event length, what fraction of events received at least one positive window.

**Q.** "When would you use weak supervision instead of manual labeling?"

**A.** 무라벨 데이터가 사람 라벨보다 수천 배 많고, 도메인 지식을 규칙으로 쓸 수 있고, 분포가 바뀌어 라벨을 반복해서 다시 만들어야 할 때다. LF 여러 개의 coverage·conflict·정확도를 작은 dev set으로 재고, 정확도 가중으로 합친다. 단순 다수결은 동률·나쁜 LF 때문에 크게 틀릴 수 있다. 평가는 여전히 사람 라벨 test로 한다.

> When unlabeled data dwarfs what humans can label, domain knowledge can be written as heuristics — energy thresholds, step detectors, phone context — and the distribution shifts so labels must be regenerated often. I measure each labeling function's coverage, conflicts and accuracy on a small hand-labeled dev set, then combine them with accuracy-weighted voting or a label model rather than a plain majority vote. The final evaluation still uses a human-labeled test set.

힌트: 바뀌는 창은 거의 전부 0 < f < 1인 경계 창이다. `frac`을 두 번 계산해 비교.

4. 코드: 예제 6을 **class-conditional noise**(walk ↔ run만 서로 30% 확률로 뒤바꿈)로 바꿔 symmetric 10%와 비교하라. 전체 noise 비율은 비슷한데 어느 쪽이 더 해로운가?
힌트: walk·run이 전체의 절반이므로 전체 noise ≈ 15%. 경계를 체계적으로 미는 쪽이 더 아프다 — 직접 확인할 것.

5. 코드: 예제 10에 diversity를 섞어라 — margin 상위 30개 중 특징 공간에서 서로 가장 먼 10개를 고르는 방식(또는 상위 5개 + random 5개). cold start(20 ~ 40개)에서 least confidence의 손해가 줄어드는지 보라.
힌트: `sklearn.cluster.KMeans(n_clusters=10)`로 상위 후보를 묶고 클러스터마다 1개.

6. 설계: wake word FA 목표가 "24시간에 1회 이하"다. 무오작동을 관측해서 이 목표를 95% 신뢰로 주장하려면 negative 평가 오디오가 몇 시간 필요한가?
정답: rule of three — 3/T ≤ 1/24 → T ≥ 72시간 (오작동 0회일 때). 오작동이 1회라도 나오면 더 필요하다.

## 14. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| ground truth | 진짜 정답 | 라벨은 ground truth의 추정치일 뿐이다 |
| label schema | 라벨 명세 | 라벨 값·의미·경계 정의·버전 |
| null class | 관심 없음 클래스 | 실제 시간의 대부분, 반드시 둔다 |
| unknown / ignore | 애매 / 제외 | 억지 분류 방지, loss에서 mask |
| scripted session | 지시 수집 | 앱 프롬프트 시각이 곧 라벨 |
| EMA | 순간 자기보고 | 폰 질문으로 "지금 뭐 했나" (연구 분야 용어) |
| ignore margin | 경계 제외 | 애매한 창을 loss에서 뺌 (`ignore_index`) |
| inter-annotator agreement | 라벨러 간 일치도 | 라벨 품질의 기본 지표 |
| Cohen's kappa | 우연 보정 일치도 | (pₒ − pₑ)/(1 − pₑ), 2인 |
| Krippendorff's alpha | 일반화 일치도 | 다인·결측·순서형 |
| gold question | 정답 아는 문항 | 라벨러 정확도 측정용 |
| annotator drift | 라벨러 변화 | 피로·기준 망각으로 정확도 하락 |
| symmetric noise | 무작위 오라벨 | 다른 클래스로 균등하게 틀림 |
| class-conditional noise | 혼동형 오라벨 | 비슷한 클래스끼리 틀림, 더 해로움 |
| weak supervision | 약한 지도 | 규칙·context로 만든 부정확한 라벨로 학습 |
| labeling function (LF) | 라벨 규칙 | 라벨 또는 기권(abstain)을 내는 함수 |
| label model | 라벨 결합 모델 | LF 정확도를 추정해 합침 (Snorkel 개념) |
| pseudo-label | 가짜 라벨 | teacher 예측을 라벨로 사용 |
| active learning | 능동 학습 | 모델이 고른 샘플만 사람이 라벨 |
| uncertainty sampling | 불확실도 표집 | least confidence / margin / entropy |
| cold start | 초기 부족 | 라벨이 적어 불확실도를 믿을 수 없는 상태 |
| hard negative | 어려운 음성 | 키워드와 비슷한 말 등 모델이 헷갈리는 negative |
| hard negative mining | 어려운 음성 수집 | 현장 FA를 모아 재학습 |
| forced alignment | 강제 정렬 | 오디오 + 전사 → 단어·음소 시각 |

## 15. 요약 & 체크리스트

센서 ML에는 공개 대형 데이터셋이 거의 없어서 라벨은 직접 만들어야 하고, 라벨은 센서 밖의 증거(앱 프롬프트, 영상, 기준 기기, 자기보고)에서 온다. 가장 싼 라벨은 수집 순간에 생기는 라벨이므로 scripted session과 기기 마커로 시작하고, 정밀 라벨은 동기화된 영상으로 평가 세트에만 쓴다. 구간 라벨을 창 라벨로 바꾸는 규칙은 경계 창(이 노트의 예에서 39%)의 운명을 정하며, 짧은 이벤트에 majority를 쓰면 양성이 사라진다. 라벨러는 오차 있는 측정기이므로 kappa·gold·가중 투표·drift 감시로 관리하고, test 세트는 특히 깨끗하게 유지한다. 사람 라벨을 아끼는 세 도구 — weak supervision(LF 가중 투표), pseudo-labeling(threshold는 정확도와 정보량의 trade-off), active learning(margin sampling이 random의 약 1/5 라벨로 같은 정확도) — 은 모두 이득과 함정이 같이 있다. wake word는 다양한 positive, 시간 단위 negative, 현장 hard negative mining이 핵심이다. 라벨은 raw와 따로 버전 관리하고, 라벨러가 raw를 본다는 사실을 프라이버시 설계에 반영한다.

- [ ] 과제의 모델 출력에 맞춰 라벨 종류(창·구간·연속값·전사·timestamp)를 고르고 null/unknown/ignore가 있는 스키마를 쓸 수 있다
- [ ] scripted session 프롬프트 로그를 반응 지연 margin을 둔 구간 라벨로 바꿀 수 있다
- [ ] 영상 라벨을 박수 sync로 센서 시계에 맞추는 절차와 경계 정밀도 한계(프레임 간격)를 말할 수 있다
- [ ] center/majority/any/contains 규칙의 결과를 손으로 계산하고, hop·창 길이·이벤트 길이와의 관계를 설명할 수 있다
- [ ] Cohen's kappa를 2×2 표에서 손으로 계산하고, 일치율이 왜 속는지 설명할 수 있다
- [ ] gold 문항으로 라벨러 정확도를 추정하고 log-odds 가중 투표를 구현할 수 있다
- [ ] 라벨 noise 비율별 정확도 실험을 설계하고, noisy test의 천장 효과를 설명할 수 있다
- [ ] LF의 coverage·conflict·accuracy를 재고 가중 투표로 합칠 수 있다
- [ ] pseudo-label threshold가 높을수록 좋지 않은 이유(쉬운 샘플 편향)를 숫자로 말할 수 있다
- [ ] least confidence / margin / entropy를 손으로 계산하고, active learning의 cold start·diversity·평가 편향 함정을 말할 수 있다
