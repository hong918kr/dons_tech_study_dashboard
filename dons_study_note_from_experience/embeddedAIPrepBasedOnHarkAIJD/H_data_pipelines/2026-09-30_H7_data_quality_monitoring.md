## 0. 큰 그림 — 이게 왜 필요한가

### 0.1 세 가지 사고

센서 데이터 파이프라인은 조용히 망가진다. 에러 메시지도, 크래시도 없다. 숫자가 조금 틀린 채로 계속 흘러간다. 예를 들어 Hark 같은 웨어러블(구성은 추정)을 수만 대 운영한다고 하자. 실제로 생기는 사고는 대개 이 세 가지다.

1. **Garbage-in** — 고장 난 센서, 단위가 틀린 로그, 마이크가 막힌 세션이 학습 데이터에 섞인다. 모델은 이상한 데이터에도 "열심히" 맞춘다. 정확도가 1~2%p 떨어지는데 원인을 아무도 모른다.
2. **조용한 field regression** — FW 업데이트가 특정 HW 리비전에서만 IMU full-scale 설정을 바꿨다. 기기는 정상 동작하는 것처럼 보이지만 제스처 인식률이 그 기기들에서만 떨어진다. 고객 불만이 쌓일 때까지 몇 주가 걸린다.
3. **일부 기기의 센서 고장** — 전체의 0.5%에서 gyro 한 축이 멈추거나, 마이크 포트가 땀·먼지로 막힌다. 평균 지표로는 보이지 않는다.

이 노트의 목표는 이 세 가지를 **사람이 로그를 들여다보기 전에 자동으로** 잡는 시스템이다. 핵심 아이디어는 단순하다. 원시 데이터 → 세션마다 지표(metric) 몇십 개 → 지표를 기기 · FW · HW · 날짜로 집계 → 기준과 비교 → 알림 → 조치. 그리고 조치는 두 방향으로 돌아간다: 학습 데이터에서 나쁜 세션을 빼고(quarantine), 기기 쪽 원인을 고친다(FW 수정, RMA).

## 1. 품질 검사 분류 — 무엇을 검사하나

### 1.1 여섯 범주

검사 항목을 생각나는 대로 나열하면 반드시 빠지는 것이 생긴다. 범주부터 정하고 범주마다 채운다. 펌웨어 검증에서 "기능 · 경계값 · 에러 경로 · 성능"으로 나누는 것과 같다.

| 범주 | 질문 | 구체 검사 (예) | 주로 잡는 원인 |
|---|---|---|---|
| Schema · 포맷 | 읽을 수 있는가? 약속한 형태인가? | parse 에러 수, magic · 버전 필드, 필수 메타데이터(기기 ID, FW, HW, 센서 설정, 단위), 레코드 크기 | 로그 포맷 변경, FW · 파서 버전 불일치 (H1 · H3) |
| 완전성 (completeness) | 빠진 것이 없는가? | 기대 샘플 수 대비 비율, 최대 gap, seq 구멍, 세션 길이, 업로드 누락 | FIFO overflow, BLE 끊김, 전원 (G7 3절) |
| 유효성 (validity) | 값이 가능한 값인가? | NaN · Inf, 물리 범위(‖x‖ > FS면 불가능), 단위(정지 시 ‖a‖ ≈ 1 g), timestamp 단조성 | 변환 버그, 단위 혼동(g vs m/s²), endianness (A6 4.4절) |
| 센서 건강 | 센서가 제대로 일하는가? | 포화(clipping) 비율, stuck-at(동일값 run), noise floor 변화, bias 단차, dead axis(std = 0), mic: clipping · DC offset · 무음 · 레벨 | 센서 고장, FS 설정 실수, 막힌 마이크 포트, 노화 (G1 · G4) |
| 교차 일관성 | 센서끼리 말이 맞는가? | 정지 시 ‖a‖ ≈ 1 g이면서 gyro ≈ 0, 탭 이벤트가 accel과 mic에 같은 시각, 착용 감지와 PPG 신호 존재 | 센서 간 시계 offset(G7 4절), 축 매핑 오류, 한 센서만 고장 |
| 라벨 sanity | 라벨이 데이터와 맞는가? | 클래스 분포, 라벨 구간 길이 분포, "걷기" 라벨인데 accel 분산이 정지 수준, 라벨러 간 일치율, 라벨-센서 시간 정렬 | 라벨 도구 버그, 시계 offset, 라벨러 실수 (H4) |

말로 하면, 앞의 세 범주는 "데이터가 데이터로서 성립하는가", 뒤의 세 범주는 "그 데이터가 현실을 제대로 담았는가"다. 앞의 것은 규칙으로 100% 판정할 수 있고, 뒤의 것은 통계적 판정(임계값, 분포 비교)이 필요하다.

### 1.2 지표 정의를 손으로

각 지표를 숫자 12개짜리 배열로 직접 계산해 보자. 가속도 한 축, full-scale(FS) ±8 g.

```
ax = [0.01, 0.02, 8.0, 8.0, 7.99, 0.03, 0.03, 0.03, 0.03, 0.03, NaN, 0.02]
```

- **NaN 개수** = 1. NaN을 뺀 유효 샘플은 11개.
- **포화 비율** — 정의: `|x| ≥ 0.999 × FS`인 샘플의 비율. 0.999 × 8 = 7.992이므로 8.0 두 개만 해당(7.99는 7.992보다 작다). 2 / 11 = 0.182. 말로 하면 "센서가 낼 수 있는 끝값에 붙어 있는 샘플의 비율"이다. 끝값에 붙었다는 건 실제 값은 더 컸는데 잘렸다는 뜻이다.
- **최장 동일값 run** — 같은 값이 연속된 최대 길이. 0.03이 5번 → 5샘플. 100 Hz라면 0.05 s. 정상 센서도 양자화 때문에 우연히 2~3번 같은 값이 나오므로, stuck 판정은 "수 초 이상"처럼 길게 잡는다.
- **단위 검사** — 정지 상태 한 샘플 (0.02, 0.05, 9.79)의 크기는 √(0.02² + 0.05² + 9.79²) ≈ 9.79. 1 g 근처가 아니라 9.8 근처면 단위가 m/s²다.
- **bias 단차** — gyro 정지 구간 앞 절반의 median 0.5 dps, 뒤 절반 3.5 dps → 단차 3.0 dps. 평균이 아니라 median을 쓰는 이유는 5.1절에서 다룬다.

**예제 1** — 무엇을 확인하나: 위 손계산을 numpy로 그대로 재현한다.

```python
# 손계산용 작은 배열로 센서 건강 지표 5개를 정의대로 계산
import numpy as np
FS = 8.0                                             # accel full-scale ±8 g
ax = np.array([0.01, 0.02, 8.0, 8.0, 7.99, 0.03, 0.03, 0.03, 0.03, 0.03, np.nan, 0.02])
def longest_run(x):                                  # 같은 값이 연속된 최장 길이 (stuck 검사)
    best = cur = 1
    for a, b in zip(x[:-1], x[1:]):
        cur = cur + 1 if a == b else 1
        best = max(best, cur)
    return best
v = ax[~np.isnan(ax)]
print("NaN 개수          :", int(np.isnan(ax).sum()))
print("saturation 비율   :", f"{np.mean(np.abs(v) >= 0.999 * FS):.3f}", "(|x| >= 0.999·FS)")
print("최장 동일값 run   :", longest_run(v), "샘플")
mag = np.sqrt(0.02**2 + 0.05**2 + 9.79**2)           # 정지 상태 한 샘플의 |a|
print(f"|a| = {mag:.2f}  → 1 g 근처가 아니라 9.8 근처면 단위가 m/s² (×9.81)")
g = np.array([0.4, 0.5, 0.6, 0.5, 0.4, 3.4, 3.5, 3.6, 3.5, 3.4])  # gyro rest, 중간에 bias jump
print("bias 전/후 (median):", np.median(g[:5]), np.median(g[5:]), "dps → 단차",
      np.median(g[5:]) - np.median(g[:5]))
```

### 1.3 함정

- **지표 정의의 버전 관리**: "sat_pct"의 정의(임계 0.999 · FS? 끝값 정확히 일치? 축별 최대? 전체 평균?)가 바뀌면 대시보드의 그래프가 그날부터 점프한다. FW 버전처럼 **지표 정의에도 버전**을 붙인다.
- **포화와 범위 밖을 구분**: 값이 FS를 넘는다(‖x‖ > FS)면 센서가 아니라 **변환 코드**가 틀렸다는 뜻이다. 2절 예제의 `units_ms2` 세션이 이 경우다.
- **stuck은 해상도와 함께**: 저잡음 센서를 정지 상태로 두면 LSB 하나 안에서 값이 오래 같을 수 있다. stuck 임계는 "noise σ가 LSB보다 몇 배 큰가"로 정한다.

## 2. 세션 단위 QA — 결함 주입으로 검사기를 검증한다

### 2.1 왜 결함 주입인가

검사기도 코드다. 검사기가 결함을 정말 잡는지는 **결함이 있는 입력을 넣어 봐야** 안다. SSD 펌웨어에서 ECC · 에러 처리 경로를 검증할 때 일부러 비트를 뒤집거나 NAND 에러를 주입하던 것과 같다. 여기서는 정상 세션 하나를 만들고, 실제로 현장에서 보는 결함 9가지를 하나씩 주입한다.

| 주입 결함 | 현실에서의 원인 (예) | 기대 flag |
|---|---|---|
| `stuck_gyro_y` | gyro 한 축 출력 레지스터가 갱신 안 됨, 센서 hang | STUCK |
| `acc_saturation` | FS를 ±2 g로 잘못 설정 + 격한 동작 | SAT |
| `dropout` | 2.5 s 동안 FIFO overflow · 링크 끊김 | DROP |
| `gyro_bias_jump` | 충격 후 bias 이동, 온도 급변 | BIAS |
| `mic_dead` | 마이크 전원 · clock 미공급, 포트 막힘 | MIC_DEAD |
| `mic_clipping` | 아날로그 gain 과다, AGC 버그 | MIC_CLIP |
| `mic_dc_offset` | 고역통과 필터 꺼짐, ADC offset | MIC_DC |
| `units_ms2` | 변환 코드가 m/s²를 내는데 메타데이터는 g | RANGE, GRAVITY |
| `av_offset` | mic와 IMU 시계 offset 150 ms (G7) | AV_SYNC |

### 2.2 합성 세션

세션 = 30초. IMU는 100 Hz 6축(±8 g, ±1000 dps, int16 양자화), mic는 16 kHz int16. 정지 상태에 2초짜리 제스처 하나, 4 · 16 · 28초에 손목 탭(accel 스파이크 + mic 딸깍 소리)이 있다. 탭은 6절의 교차 일관성 검사에 쓴다.

**예제 2** — 무엇을 확인하나: 결함 9종을 주입한 합성 세션 10개를 만든다 (정상 1 + 결함 9).

```python
# 합성 세션 생성기: 30 s IMU(100 Hz, ±8 g / ±1000 dps) + mic(16 kHz) + 탭 3번, 결함 주입
import numpy as np
FS_HZ, AFS, DUR, AFS_G, GFS = 100, 16000, 30, 8.0, 1000.0
TAPS = [4.0, 16.0, 28.0]                                   # 말소리 없는 구간
def make_session(fault="clean", seed=0):
    r = np.random.default_rng(seed)
    t = np.arange(DUR * FS_HZ) / FS_HZ
    acc = np.c_[r.normal(0, .02, t.size), r.normal(0, .02, t.size), 1 + r.normal(0, .02, t.size)]
    gyr = r.normal(0, .3, (t.size, 3)) + [0.2, -0.1, 0.4]            # 작은 고정 bias
    mv = (t > 10) & (t < 12)                                           # 2 s 제스처
    acc[mv, 0] += 1.5 * np.sin(2 * np.pi * 2 * t[mv]); gyr[mv, 2] += 120 * np.sin(2 * np.pi * 2 * t[mv])
    ta = np.arange(DUR * AFS) / AFS
    mic = r.normal(0, 100, ta.size) + 3000 * r.normal(0, 1, ta.size) * ((ta % 6) < 1.5)  # 배경 + 말소리
    for tp in TAPS:
        acc[int(tp * FS_HZ), 2] += 2.5                                 # 탭: accel 스파이크
        k = int(tp * AFS); mic[k:k + 80] += 12000 * np.exp(-np.arange(80) / 15)   # 탭: 딸깍
    if fault == "stuck_gyro_y":  gyr[900:, 1] = gyr[900, 1]
    fs_g = 2.0 if fault == "acc_saturation" else AFS_G                 # FS 설정 실수: ±2 g
    if fault == "acc_saturation": acc[mv, 0] *= 2.5                     # + 격한 동작 → 클리핑
    if fault == "dropout":      keep = (t < 18) | (t >= 20.5); t, acc, gyr = t[keep], acc[keep], gyr[keep]
    if fault == "gyro_bias_jump": gyr[t >= 15, 2] += 3.0
    if fault == "mic_dead":     mic = r.normal(0, 0.4, ta.size)
    if fault == "mic_clipping": mic = mic * 12
    if fault == "mic_dc_offset": mic = mic + 6000
    if fault == "av_offset":    mic = np.roll(mic, int(0.150 * AFS))     # 오디오가 150 ms 늦음
    acc = np.clip(np.round(acc * 4096) / 4096, -fs_g, fs_g - 1 / 4096)  # 양자화 + 포화
    if fault == "units_ms2":    acc = acc * 9.81                        # 변환 버그. 메타는 'g'라고 주장
    gyr = np.clip(np.round(gyr * 32.768) / 32.768, -GFS, GFS)
    mic = np.clip(np.round(mic), -32768, 32767)
    meta = {"fw": "1.4.0", "hw": "B", "acc_unit": "g", "gyr_unit": "dps", "fs_hz": FS_HZ, "acc_fs_g": fs_g}
    return {"t": t, "acc": acc, "gyr": gyr, "mic": mic, "meta": meta}
FAULTS = ["clean", "stuck_gyro_y", "acc_saturation", "dropout", "gyro_bias_jump",
          "mic_dead", "mic_clipping", "mic_dc_offset", "units_ms2", "av_offset"]
sessions = {f: make_session(f, seed=i) for i, f in enumerate(FAULTS)}
s = sessions["clean"]
print({k: (v.shape if hasattr(v, "shape") else v) for k, v in s.items()})
```


출력에서 볼 것: 세션은 timestamp `t`, 센서 배열 3개, 메타데이터 dict로 이루어진다. 메타데이터에 FS 설정(`acc_fs_g`)과 단위가 들어 있다는 것이 중요하다 — QA 함수는 FS를 알아야 포화를 판정할 수 있고, 단위 주장을 알아야 단위 버그를 잡을 수 있다. 메타데이터 없는 raw 로그는 검사도 할 수 없다.

### 2.3 지표 계산

세션 하나에서 12개 지표를 뽑는다. 원칙은 세 가지다.

1. **지표는 원인 하나에 민감하고 다른 원인에는 둔감하게** 만든다. 예: bias 단차는 "회전이 작은 샘플(‖ω‖ < 20 dps)"만 써서 제스처의 영향을 뺀다.
2. **robust 통계(median)**를 쓴다. 탭 · 제스처 같은 정상적인 큰 값이 지표를 흔들지 않게.
3. **교차 일관성**은 두 센서의 공통 이벤트로 잰다. 탭 시각을 accel에서 찾고(robust z > 20인 스파이크), 그 주변 ±0.3 s의 mic에서 최대 진폭 위치를 찾아 시간차를 잰다.

**예제 3** — 무엇을 확인하나: 세션 → 지표 dict 함수. 정상 세션과 단위 버그 세션을 비교한다.

```python
# 세션 하나 → 품질 지표 dict. 완전성·유효성·센서 건강·mic·교차 일관성(탭 정렬)
def run_max(x):                                       # 같은 값이 이어진 최장 길이 (벡터화)
    ch = np.flatnonzero(np.diff(x) != 0)
    edges = np.r_[-1, ch, x.size - 1]
    return int(np.diff(edges).max())
def session_qa(s):
    m, t, acc, gyr, mic = s["meta"], s["t"], s["acc"], s["gyr"], s["mic"]
    fs, FSg = m["fs_hz"], m["acc_fs_g"]
    q = {"complete": t.size / (DUR * fs), "max_gap_ms": 1e3 * np.diff(t).max()}
    q["nan"] = int(np.isnan(acc).sum() + np.isnan(gyr).sum())
    a = np.abs(acc)
    q["oor_pct"] = 100 * np.mean(a > 1.001 * FSg)                      # 물리적으로 불가능한 값
    q["sat_pct"] = 100 * ((a >= 0.999 * FSg) & (a <= FSg)).mean(axis=0).max()   # 최악 축
    q["stuck_s"] = max(run_max(c) for c in np.c_[acc, gyr].T) / fs
    rest = np.linalg.norm(gyr, axis=1) < 20                             # 큰 회전 없는 샘플
    q["amag_g"] = np.median(np.linalg.norm(acc[rest], axis=1))
    h = t.size // 2
    q["bias_step_dps"] = np.abs(np.median(gyr[h:][rest[h:]], 0) - np.median(gyr[:h][rest[:h]], 0)).max()
    q["mic_dbfs"] = 20 * np.log10(np.sqrt(np.mean(mic ** 2)) / 32768 + 1e-12)
    q["mic_clip_pct"] = 100 * np.mean(np.abs(mic) >= 32767)
    q["mic_dc"] = mic.mean() / 32768
    lags = []                                                           # 탭: accel 시각 vs mic 피크
    z = acc[:, 2] - np.median(acc[:, 2]); z = np.abs(z) / (1.4826 * np.median(np.abs(z)) + 1e-9)
    for k in np.flatnonzero(z > 20):                                    # robust z > 20 = 탭 스파이크
        w0 = int((t[k] - 0.3) * AFS); w = np.abs(mic[w0:w0 + int(0.6 * AFS)] - np.median(mic))
        if w.size and w.max() > 20 * np.median(w) + 100: lags.append((w0 + w.argmax()) / AFS - t[k])
    q["av_lag_ms"] = 1e3 * np.median(lags) if lags else np.nan
    return q
for f in ["clean", "units_ms2"]:
    print(f, {k: round(float(v), 3) for k, v in session_qa(sessions[f]).items()})
```

### 2.4 규칙 → flag → 리포트

지표를 판정으로 바꾸는 규칙은 표로 관리한다. 각 규칙은 (flag 이름, 조건, 심각도)다. FAIL은 "학습에 쓰면 안 된다", WARN은 "쓸 수는 있지만 태그를 달고 사람이 본다".

**예제 4** — 무엇을 확인하나: 10개 세션 전부에 QA를 돌려 리포트 표와 판정을 만든다.

```python
# 지표 → 규칙 기반 flag (FAIL/WARN) → 세션별 리포트 표
import pandas as pd
RULES = [  # (flag, 조건, 심각도)
    ("DROP",     lambda q: q["complete"] < 0.99 or q["max_gap_ms"] > 50, "FAIL"),
    ("NAN",      lambda q: q["nan"] > 0,                                 "FAIL"),
    ("RANGE",    lambda q: q["oor_pct"] > 0,                             "FAIL"),
    ("SAT",      lambda q: q["sat_pct"] > 0.5,                           "WARN"),
    ("STUCK",    lambda q: q["stuck_s"] >= 2.0,                          "FAIL"),
    ("GRAVITY",  lambda q: not 0.9 < q["amag_g"] < 1.1,                  "FAIL"),
    ("BIAS",     lambda q: q["bias_step_dps"] > 1.0,                     "WARN"),
    ("MIC_DEAD", lambda q: q["mic_dbfs"] < -70,                          "FAIL"),
    ("MIC_CLIP", lambda q: q["mic_clip_pct"] > 0.1,                      "WARN"),
    ("MIC_DC",   lambda q: abs(q["mic_dc"]) > 0.05,                      "WARN"),
    ("AV_SYNC",  lambda q: not abs(q["av_lag_ms"]) <= 20,                "WARN"),  # NaN도 걸림
]
def judge(q):
    hits = [(f, sev) for f, cond, sev in RULES if cond(q)]
    verdict = "FAIL" if any(s == "FAIL" for _, s in hits) else ("WARN" if hits else "PASS")
    return verdict, ",".join(f for f, _ in hits) or "-"
rows = []
for name, s in sessions.items():
    q = session_qa(s); v, flags = judge(q)
    rows.append({"session": name, "cmpl": q["complete"], "gap_ms": q["max_gap_ms"],
                 "sat%": q["sat_pct"], "stuck_s": q["stuck_s"], "|a|_g": q["amag_g"],
                 "bias": q["bias_step_dps"], "mic_dB": q["mic_dbfs"], "clip%": q["mic_clip_pct"],
                 "dc": q["mic_dc"], "lag_ms": q["av_lag_ms"], "verdict": v, "flags": flags})
report = pd.DataFrame(rows).set_index("session")
pd.set_option("display.width", 140)
print(report.round(2).to_string())
```

### 2.5 임계값은 어떻게 정하나

예제 4의 임계값(완전성 0.99, gap 50 ms, sat 0.5%, stuck 2 s, ‖a‖ 0.9~1.1, bias 1 dps, −70 dBFS, clip 0.1%, DC 0.05, 정렬 20 ms)은 예시다. 실제로는 이렇게 정한다.

1. **요구사항에서 거꾸로**: "탭 라벨 정렬은 20 ms 이내여야 한다"(G7 0.3절의 표) → AV_SYNC 임계 20 ms.
2. **정상 분포에서**: 정상으로 알려진 세션 수천 개에서 지표 분포를 보고 99.9 percentile 바깥을 WARN으로. factory test에서 golden unit 분포로 limit을 잡던 것과 같다.
3. **비용으로 조정**: 오탐(정상 세션을 버림)의 비용은 데이터 조금, 미탐(고장 세션이 학습에 들어감)의 비용은 모델 품질. 학습셋 보호용이면 보수적으로(잘 버리게) 잡아도 된다. 알림(사람을 깨움)용이면 반대로 잡는다. 같은 지표에 **용도별로 임계값이 다를 수 있다**.

## 3. Fleet 모니터링 — FW 릴리스가 일부 기기를 망가뜨렸을 때

### 3.1 집계의 차원

세션 리포트 한 줄 = (session_id, device_id, 시각, 지표 12개). 여기에 **차원(dimension)**을 붙인다: FW 버전, HW 리비전, 센서 vendor · lot, 국가 · 지역, 착용 위치 설정, 앱 버전. 대시보드는 결국 `groupby(차원).agg(지표)`다.

| 집계 수준 | 행 하나 | 쓰는 곳 |
|---|---|---|
| 세션 | 세션 하나의 지표 | quarantine 판정, triage 증거 |
| device-day | 기기 하나의 하루 요약 (지표별 p50 · p95 · max, 세션 수, FAIL 수) | 기기별 trend, CUSUM (5절) |
| group-day | (day, FW, HW, …) 그룹의 분포 요약 (기기 수, median, p95, 이상 기기 비율) | 대시보드, 릴리스 감시, 알림 |

### 3.2 시나리오 — 500대, 30일, 나쁜 릴리스

- HW rev A 60%, rev B 40%. rev B 중 30%는 2nd-source IMU를 쓴다.
- day 15부터 FW 1.5.0이 단계적으로 배포된다(매일 남은 기기의 35%가 업데이트).
- 1.5.0은 2nd-source IMU의 sensitivity 테이블을 잘못 골라 **accel gain을 ×1.10**으로 만든다. 다른 기기는 멀쩡하다.
- 매일 10% 기기는 업로드하지 않는다(현실적인 결측).
- 지표: 기기-일 단위 "정지 구간 ‖a‖의 median"(`amag_g`). 정상은 1 g ± 기기별 calibration 오차(σ 0.008).

먼저 손으로 예상해 보자. 영향받는 기기 = 0.4 × 0.3 = 12% (실제 샘플에서는 63/500 = 12.6%). 배포 첫날(day 15)에는 업데이트된 기기가 35% 정도라서 fleet 전체로는 12.6% × 0.35 ≈ 4.4%만 이상하다. **fleet 전체 median은 꿈쩍도 하지 않는다** — median은 50% 넘게 바뀌어야 움직이기 때문이다.

**예제 5** — 무엇을 확인하나: 500대 × 30일 device-day 테이블을 만든다.

```python
# fleet 시뮬레이션: 500대 × 30일. day 15부터 FW 1.5.0 단계적 배포.
# 1.5.0은 HW rev B 중 2nd-source IMU(30%)에서 accel gain을 ×1.10으로 잘못 설정한다
r = np.random.default_rng(7)
N, D = 500, 30
dev = pd.DataFrame({"device": np.arange(N), "hw": r.choice(["A", "B"], N, p=[0.6, 0.4])})
dev["imu_vendor2"] = (dev.hw == "B") & (r.random(N) < 0.30)
dev["update_day"] = 15 + r.geometric(0.35, N) - 1                   # 15일부터 하루하루 따라온다
dev["cal_err"] = r.normal(0, 0.008, N)                              # 기기별 고정 오차 (정상 산포)
rows = []
for d in range(D):
    up = r.random(N) > 0.10                                          # 매일 10%는 업로드 안 함
    fw = np.where(d >= dev.update_day, "1.5.0", "1.4.0")
    gain = np.where((fw == "1.5.0") & dev.imu_vendor2, 1.10, 1.0)
    amag = gain * (1 + dev.cal_err + r.normal(0, 0.004, N))           # 하루 정지 구간 median |a|
    sat = r.gamma(0.5, 0.02, N) * gain ** 8                           # gain↑ → 포화 비율↑
    rows.append(pd.DataFrame({"day": d, "device": dev.device, "hw": dev.hw, "fw": fw,
                              "amag_g": amag, "sat_pct": sat})[up])
fleet = pd.concat(rows, ignore_index=True)
print(fleet.shape, "행 (device-day)")
print(fleet.groupby("hw").device.nunique().to_dict(), "| vendor2 in B:", int(dev.imu_vendor2.sum()))
print(fleet[fleet.day == 29].fw.value_counts().to_dict(), "(day 29 업로드 기준)")
```

```text
(13535, 6) 행 (device-day)
{'A': 294, 'B': 206} | vendor2 in B: 63
{'1.5.0': 450, '1.4.0': 1} (day 29 업로드 기준)
```

출력에서 볼 것: device-day 행이 13535개(500 × 30 × 0.9 ≈ 13500). day 29에는 업로드한 기기 451대 중 450대가 1.5.0이다. 열은 (day, device, hw, fw, amag_g, sat_pct) — 이 테이블이 metrics store의 모양이다.

### 3.3 대시보드 집계와 알림

알림 규칙: **"(day, HW, FW) 그룹에서 기기가 20대 이상이고, ‖a‖가 1 g ± 5% 밖인 기기 비율이 5%를 넘으면 알림"**. 그룹 크기 하한은 기기 3대짜리 그룹에서 1대만 이상해도 33%가 되는 소음을 막는다.

**예제 6** — 무엇을 확인하나: 그룹별 median · p95 · 이상 기기 비율, fleet 전체 median, 첫 알림 시점, FW 전후 분포 비교(KS), 원인 차원(IMU vendor)으로 drill-down.

```python
# 대시보드 집계: (day, hw, fw)별 median과 "정상 범위 밖 기기 비율". fleet 전체 median과 비교
from scipy import stats
fleet["bad"] = (fleet.amag_g - 1).abs() > 0.05                       # |a| 정지값이 1 g ± 5% 밖
g = fleet.groupby(["day", "hw", "fw"]).agg(n=("device", "size"), med=("amag_g", "median"),
                                           p95=("amag_g", lambda x: x.quantile(0.95)),
                                           bad_pct=("bad", lambda x: 100 * x.mean()))
whole = fleet.groupby("day").amag_g.median()
for d in [15, 18]:
    print(f"day {d}  fleet median {whole[d]:.4f}")
    print(g.loc[d].round(3).to_string(), "\n")
alert = g[(g.n >= 20) & (g.bad_pct > 5)].reset_index()                # 알림 규칙
print("첫 알림:", alert.iloc[0][["day", "hw", "fw", "n", "bad_pct"]].to_dict())
b = fleet[fleet.hw == "B"]                                            # 같은 HW에서 FW 전/후 분포 비교
ks = stats.ks_2samp(b[b.fw == "1.4.0"].amag_g, b[b.fw == "1.5.0"].amag_g)
print(f"rev B: KS D={ks.statistic:.3f}, p={ks.pvalue:.1e}")
a = fleet[fleet.hw == "A"]
ks = stats.ks_2samp(a[a.fw == "1.4.0"].amag_g, a[a.fw == "1.5.0"].amag_g)
print(f"rev A: KS D={ks.statistic:.3f}, p={ks.pvalue:.2f}")
post = fleet[(fleet.hw == "B") & (fleet.fw == "1.5.0")].merge(dev[["device", "imu_vendor2"]])
print(post.groupby("imu_vendor2").agg(devices=("device", "nunique"),
                                      bad_pct=("bad", lambda x: round(100 * x.mean(), 1))).to_string())
```

- **(B, 1.5.0) 그룹의 median**도 1.002~1.005로 거의 안 움직인다. 그룹의 30%만 망가졌으니까. 반면 **p95는 1.104**(같은 날 rev B × 1.4.0은 1.017), **이상 기기 비율은 27%**(1.4.0은 0%)로 뛴다. 꼬리와 비율을 봐야 한다. SSD에서 평균 latency가 아니라 p99.9 latency를 보던 것과 같은 이유다.

### 3.4 희석(dilution) 산수 — 왜 쪼개야 하나

평균류 지표는 영향받는 비율만큼 희석된다. 영향받는 기기 비율을 f, 그 기기들의 지표 변화를 Δ라 하면

```
fleet 평균의 변화 ≈ f × Δ
이상 기기 비율    = f            (Δ가 임계를 넘는다면)
fleet median      : f < 50%면 거의 그대로
fleet p95         : f > 5%면 크게 움직임
```

말로 하면, **"평균을 보면 f × Δ, 비율을 보면 f, median은 f가 반을 넘어야"**다. 이번 예에서 f = 12.6%, Δ = 0.10 g → fleet 평균 변화 0.0126 g. 표본이 많아 통계적으로는 보이는 크기지만, 1% 남짓한 이동은 계절 · 사용 패턴 변동에 쉽게 묻히고, 무엇보다 "모두가 1.3% 틀렸다"인지 "12%가 10% 틀렸다"인지 평균으로는 구분이 안 된다. 그룹을 rev B × 1.5.0으로 좁히면 f = 30%, 다시 vendor로 좁히면 f = 100%가 된다. **차원으로 쪼갤수록 f가 커지고 신호가 선명해진다.** 단, 쪼갤수록 그룹이 작아져 소음도 커지므로 그룹 크기 하한(예제 6의 n ≥ 20)과 다중 비교 보정(6.2절의 Bonferroni)이 따라와야 한다.

### 3.5 릴리스 감시 운영

- **Staged rollout + canary**: 1% → 10% → 50% → 100%. 각 단계 사이에 "업데이트된 기기 vs 아직 안 된 기기"를 **같은 날, 같은 HW**에서 비교한다. 같은 날짜끼리 비교하면 계절 · 요일 효과가 상쇄된다. 이건 사실상 A/B 테스트다.
- **Go/no-go 체크리스트**에 데이터 품질 지표를 넣는다: 각 (HW, 센서 vendor) 그룹에서 FAIL 세션 비율, 이상 기기 비율, 주요 지표의 KS D가 기준 이하일 것.
- **자동 rollout 정지**: 알림이 특정 FW에 묶여 있으면 배포 서버가 다음 단계로 넘어가지 않게 한다. SSD fleet에서 FW 배포를 drive 모델별로 멈추던 것과 같다.

### 3.6 함정

- **업데이트한 기기는 무작위가 아니다**: 자주 충전 · 동기화하는 사용자가 먼저 업데이트된다. 사용 패턴이 다른 집단이라 FW와 무관한 차이가 보일 수 있다. 그래서 "같은 기기의 업데이트 전 vs 후"(paired) 비교를 함께 본다.
- **업로드 편향**: 고장 난 기기는 업로드를 안 할 수도 있다. "업로드한 기기의 지표"만 보면 고장이 숨는다 — 업로드 기기 수 자체도 지표다.
- **같은 기기의 세션을 독립 표본으로 세지 않기**: 한 기기의 세션 1000개가 같은 방향으로 이상하면 세션 기준 p-value는 터무니없이 작아진다. 판정 단위는 기기로.

## 4. 분포 drift 탐지 — PSI, KS, JS

### 4.1 drift의 종류

모델 입장에서 입력을 x, 정답을 y라 하면 학습 데이터는 결합분포 P(x, y)에서 나온 샘플이다. P(x, y) = P(x) · P(y | x)이므로 바뀔 수 있는 것은 두 가지다.

| 종류 | 바뀌는 것 | 웨어러블 예 | 무엇으로 감지 |
|---|---|---|---|
| covariate drift (입력 drift) | P(x) | 새 FW가 mic gain +3 dB, 겨울이라 장갑 낀 제스처, 새 국가 출시 | 입력 특징 분포 비교 (PSI, KS) — 라벨 없이 가능 |
| prior (label) drift | P(y) | 여름에 운동 세션 비율 증가 | 라벨 분포 (라벨 있는 표본에서), 예측 분포 |
| concept drift | P(y ∣ x) | 같은 손동작인데 새 UX에서 의미가 바뀜, 새 사투리의 같은 소리가 다른 단어 | **라벨이 있어야** 감지 — 정확도 모니터링, 라벨링 표본 |

말로 하면, 입력 분포가 바뀌는 건 라벨 없이도 볼 수 있지만, "같은 입력의 정답이 바뀌는" concept drift는 정답 라벨을 다시 모으지 않으면 보이지 않는다. 그래서 운영에서는 (1) 입력 · 출력 분포를 상시 감시하고, (2) 소량의 표본을 계속 라벨링해서(H4) 정확도를 직접 잰다. 센서 고장 · FW 버그는 거의 모두 covariate drift로 나타난다 — 3절의 gain 버그도 ‖a‖ 분포의 covariate drift다.

### 4.2 PSI — Population Stability Index

**직관**: 기준(reference) 분포를 bin으로 나누고, 지금(current) 분포가 각 bin에 얼마나 들어가는지 비교한다. 히스토그램 두 개의 "거리"다.

**정의**: bin i의 기준 비율 eᵢ, 현재 비율 aᵢ에 대해

```
PSI = ∑ᵢ (aᵢ − eᵢ) · ln(aᵢ / eᵢ)
    = KL(a ‖ e) + KL(e ‖ a)       (양방향 KL의 합, "J-divergence")
```

말로 하면, bin마다 "비율 차이 × 비율의 로그 비"를 더한다. 두 인수의 부호가 항상 같아서 각 항은 0 이상이고, 분포가 같으면 0이다. A2에서 본 KL은 방향이 있었는데(KL(a‖e) ≠ KL(e‖a)), PSI는 둘을 더해서 대칭이다.

**손계산** — 4개 bin, 기준은 균등 e = (0.25, 0.25, 0.25, 0.25), 현재 a = (0.10, 0.20, 0.30, 0.40):

```
bin1: (0.10 − 0.25) · ln(0.10/0.25) = (−0.15)(−0.9163) = 0.1374
bin2: (0.20 − 0.25) · ln(0.20/0.25) = (−0.05)(−0.2231) = 0.0112
bin3: (0.30 − 0.25) · ln(0.30/0.25) = (+0.05)(+0.1823) = 0.0091
bin4: (0.40 − 0.25) · ln(0.40/0.25) = (+0.15)(+0.4700) = 0.0705
PSI = 0.2282
```

업계(원래 신용평가 모델 감시)에서 쓰는 경험칙: **PSI < 0.1 안정, 0.1~0.25 주의, > 0.25 큰 변화**. 경험칙일 뿐이며, 4.5절에서 보듯 표본 크기와 bin 수에 따라 "정상일 때의 PSI"가 달라지므로 자기 데이터로 다시 정해야 한다.

**JS (Jensen-Shannon)**: m = (a + e)/2로 두고 JS = ½KL(a‖m) + ½KL(e‖m). 대칭이고, 항상 유한하며(어느 bin이 0이어도 된다), 자연로그 기준으로 최대 ln 2 = 0.693. 대시보드에 0~1 사이 숫자가 필요하면 JS / ln 2를 쓴다.

### 4.3 KS — Kolmogorov–Smirnov

**직관**: bin을 나누지 않는다. 두 표본의 **누적분포함수(CDF)**를 그리고, 세로 방향으로 가장 크게 벌어진 거리를 잰다.

```
D = maxₓ | F_ref(x) − F_cur(x) |
```

**손계산** — ref = (1, 2, 3, 4), cur = (2.5, 3.5, 4.5, 5.5). 모든 점에서 CDF를 계산하면 x = 2에서 F_ref = 0.5, F_cur = 0 → D = 0.5.

장점은 bin 선택이 없다는 것, 단점은 연속 1차원 특징에만 자연스럽고, **표본이 크면 p-value가 사소한 차이에도 0으로 간다**는 것이다(4.5절).

**예제 7** — 무엇을 확인하나: PSI 손계산, PSI = KL 양방향 합, JS, KS의 D를 CDF로 직접 계산해 scipy와 비교.

```python
# PSI · KL · JS 손계산 확인 (4개 bin), 그리고 KS 통계량을 작은 표본으로
e = np.array([0.25, 0.25, 0.25, 0.25])      # 기준(reference) 분포의 bin 비율
a = np.array([0.10, 0.20, 0.30, 0.40])      # 지금(current) 분포
terms = (a - e) * np.log(a / e)
print("PSI 항:", terms.round(4), " PSI =", round(terms.sum(), 4))
kl = lambda p, q: np.sum(p * np.log(p / q))
m = (a + e) / 2
print(f"KL(a‖e)={kl(a, e):.4f}  KL(e‖a)={kl(e, a):.4f}  합={kl(a, e) + kl(e, a):.4f} (=PSI)")
print(f"JS = {0.5 * kl(a, m) + 0.5 * kl(e, m):.4f}  (≤ ln2 = {np.log(2):.4f})")
ref = np.array([1.0, 2.0, 3.0, 4.0]); cur = np.array([2.5, 3.5, 4.5, 5.5])
grid = np.sort(np.r_[ref, cur])
F_ref = np.searchsorted(np.sort(ref), grid, side="right") / ref.size
F_cur = np.searchsorted(np.sort(cur), grid, side="right") / cur.size
print("x     :", grid); print("F_ref :", F_ref); print("F_cur :", F_cur)
ks = stats.ks_2samp(ref, cur)
print("D =", np.abs(F_ref - F_cur).max(), f"| scipy D={ks.statistic:.2f}, p={ks.pvalue:.3f}")
```

```text
PSI 항: [0.1374 0.0112 0.0091 0.0705]  PSI = 0.2282
KL(a‖e)=0.1064  KL(e‖a)=0.1218  합=0.2282 (=PSI)
JS = 0.0279  (≤ ln2 = 0.6931)
x     : [1.  2.  2.5 3.  3.5 4.  4.5 5.5]
F_ref : [0.25 0.5  0.5  0.75 0.75 1.   1.   1.  ]
F_cur : [0.   0.   0.25 0.25 0.5  0.5  0.75 1.  ]
D = 0.5 | scipy D=0.50, p=0.771
```

출력에서 볼 것: PSI 0.2282가 손계산과 같고, KL(a‖e) + KL(e‖a)와 정확히 같다. KS의 D = 0.5는 scipy와 일치하지만, 표본이 4개씩이라 p = 0.771 — "다르다고 말할 근거가 없다". 같은 D라도 표본 수가 p-value를 좌우한다.

### 4.4 정규분포 mean shift ↔ PSI — 머릿속 환산표

두 분포가 표준편차 σ가 같은 정규분포이고 평균만 Δ 차이 나면, KL(p‖q) = Δ² / (2σ²)이므로

```
PSI(연속 극한) = KL + KL = (Δ/σ)²
→ PSI 0.10 ↔ Δ ≈ 0.32σ,   PSI 0.25 ↔ Δ = 0.5σ,   PSI 1.0 ↔ Δ = σ
```

말로 하면, **"PSI 0.25는 평균이 σ의 절반 움직인 것"**이다. bin으로 나누면 정보가 조금 뭉개져서 실제 PSI는 이보다 약간 작다. 반대로 drift가 없어도 표본 잡음 때문에 PSI는 0이 아니다. bin B개, 표본 n(현재)과 m(기준)이면 대략

```
E[PSI | drift 없음] ≈ (B − 1) · (1/n + 1/m)
예: B = 10, n = 2000, m = 20000 → 9 × (0.0005 + 0.00005) ≈ 0.005
```

### 4.5 시나리오 — 갑작스러운 drift vs 서서히 오는 drift

특징: 창(window)별 mic 레벨(dBFS). 기준은 출시 직후 2주의 20000창, 정규분포 평균 −35 dBFS, σ 6 dB. 매일 2000창이 들어온다. 현실감을 위해 **날마다 자연스러운 변동**(평균이 ±0.5 dB 정도 흔들림 — 요일, 날씨, 사용 장소)을 넣었다. day 30부터:

- sudden: FW 업데이트로 mic gain +3 dB (= 0.5σ → PSI 이론값 0.25)
- gradual: 마이크 메쉬에 먼지가 쌓이는 것처럼 하루 0.1 dB씩 (30일 뒤 +3 dB)

**예제 8** — 무엇을 확인하나: 세 시나리오 × 60일의 일별 PSI(10 bin, 기준의 분위수로 bin 경계)와 KS. drift 전 30일 동안 오경보가 얼마나 나는지.

```python
# drift 시나리오 3개 × 60일. 특징 = 창별 mic level(dBFS), 하루 2000창. day 30부터 drift
def psi(ref, cur, nb=10):
    edges = np.quantile(ref, np.linspace(0, 1, nb + 1)); edges[[0, -1]] = -np.inf, np.inf
    e = np.histogram(ref, edges)[0] / ref.size; a = np.histogram(cur, edges)[0] / cur.size
    e, a = np.clip(e, 1e-4, None), np.clip(a, 1e-4, None)               # 빈 bin → log(0) 방지
    return float(np.sum((a - e) * np.log(a / e)))
def day_feature(r, shift, n=2000):
    day_jitter = r.normal(0, 0.5)                                       # 자연스러운 날마다 변동
    return r.normal(-35 + shift + day_jitter, 6, n)
def scenario(kind, r, days=60, onset=30):
    sh = np.zeros(days)
    if kind == "sudden":  sh[onset:] = 3.0                              # 새 FW: mic gain +3 dB
    if kind == "gradual": sh[onset:] = 0.1 * (np.arange(days - onset) + 1)  # 메쉬 막힘 등
    return [day_feature(r, s) for s in sh]
r = np.random.default_rng(11)
ref = r.normal(-35, 6, 20000)                                           # 기준: 출시 직후 2주
res = {}
for kind in ["none", "sudden", "gradual"]:
    days = scenario(kind, r)
    res[kind] = np.array([(psi(ref, x), *stats.ks_2samp(ref, x)[:2]) for x in days])
for kind, v in res.items():
    pre, post = v[:30], v[30:]
    print(f"{kind:8s} PSI pre max {pre[:, 0].max():.3f} | KS D pre max {pre[:, 1].max():.3f}"
          f" | KS p<0.01 인 날(pre) {np.sum(pre[:, 2] < 0.01):2d}/30"
          f" | PSI>0.1 첫날 {np.argmax(v[:, 0] > 0.1) if (v[:, 0] > 0.1).any() else '-'}")
```

```text
none     PSI pre max 0.027 | KS D pre max 0.071 | KS p<0.01 인 날(pre) 17/30 | PSI>0.1 첫날 -
sudden   PSI pre max 0.061 | KS D pre max 0.100 | KS p<0.01 인 날(pre) 17/30 | PSI>0.1 첫날 30
gradual  PSI pre max 0.037 | KS D pre max 0.081 | KS p<0.01 인 날(pre) 14/30 | PSI>0.1 첫날 41
```

출력에서 볼 것:

- **KS p < 0.01이 drift 없는 30일 중 14~17일**이다. KS p-value를 알림에 그대로 쓰면 이틀에 한 번 오경보다. 이유: 표본 2000개면 KS의 1% 임계 D는 약 1.63 × √((n+m)/(nm)) ≈ 0.038인데, 날마다의 자연 변동 0.5 dB(= 0.083σ)만으로도 D ≈ 0.083 × 0.399 ≈ 0.033이 나온다. **p-value는 "차이가 있는가"에 답하지, "차이가 중요한가"에 답하지 않는다.** 대량 데이터에서는 effect size(D, PSI)에 임계를 건다.
- PSI는 drift 전 최대가 0.027~0.061로 0.1 아래다. sudden은 day 30 당일에 0.1을 넘고, gradual은 day 41(11일 뒤, 누적 +1.2 dB ≈ 0.2σ — 이론 PSI 0.04에 날 변동이 더해져서)에야 넘는다.

### 4.6 임계값의 trade-off — 오경보 vs 검출 지연

임계를 낮추면 빨리 잡지만 오경보가 늘고, 높이면 조용하지만 늦다. 이건 감도(sensitivity)와 오경보율의 trade-off로, A4의 wake word 동작점(FA/hour vs FRR) 고르기와 같은 구조다. 시뮬레이션을 100번 반복해서 숫자로 보자. 규칙 두 가지를 비교한다: (1) PSI가 하루라도 임계를 넘으면 알림, (2) **이틀 연속** 넘어야 알림.

**예제 9** — 무엇을 확인하나: 임계값 7개 × 규칙 2개에 대해 "drift 없는 fleet에서 30일당 오경보 수"와 "drift 시작 후 검출까지 평균 일수".

```python
# 임계값 trade-off: 100번 반복해서 "오경보/30일" vs "검출 지연(일)"을 잰다
r = np.random.default_rng(5)
runs = {k: np.array([[psi(ref, x) for x in scenario(k, r)] for _ in range(100)])
        for k in ["none", "sudden", "gradual"]}
def delay(P, th, onset=30):                                  # onset 이후 처음 넘는 날까지 (일)
    hit = P[:, onset:] > th
    return np.where(hit.any(1), hit.argmax(1), np.nan)
def delay2(P, th, onset=30):                                 # 규칙 B: 이틀 연속 넘어야 알림
    hit = (P[:, onset:-1] > th) & (P[:, onset + 1:] > th)
    return np.where(hit.any(1), hit.argmax(1) + 1, np.nan)
print("  th   | 오경보/30일  지연 sudden  지연 gradual | (2일 연속) 오경보/30일  지연 gradual")
for th in [0.02, 0.03, 0.05, 0.08, 0.10, 0.15, 0.25]:
    fa = 30 * (runs["none"] > th).mean()
    fa2 = 30 * ((runs["none"][:, :-1] > th) & (runs["none"][:, 1:] > th)).mean()
    print(f" {th:.2f}  |   {fa:6.2f}      {np.nanmean(delay(runs['sudden'], th)):5.2f}"
          f"       {np.nanmean(delay(runs['gradual'], th)):5.2f}     |"
          f"        {fa2:6.2f}           {np.nanmean(delay2(runs['gradual'], th)):5.2f}")
```

### 4.7 실무 메모

- **기준(reference) 고르기**: 고정 기준(출시 직후, 학습 데이터)은 "학습 때와 다른가"를 묻고, 이동 기준(지난 4주)은 "최근에 바뀌었나"를 묻는다. 둘 다 본다. 이동 기준만 쓰면 gradual drift를 기준이 따라가 버려 영영 못 잡는다(가마솥 개구리).
- **bin 경계는 기준 분포의 분위수로** 고정하고 저장한다. 매번 새로 정하면 PSI끼리 비교할 수 없다. 빈 bin은 작은 값(1e-4)으로 clip해서 log(0)을 막는다(예제 8의 `psi`).
- **특징이 수백 개면** 특징마다 PSI를 매일 계산하고, 상위 몇 개를 보여 주되, 특징 수만큼 오경보가 늘어나는 다중 비교 문제를 잊지 않는다. 모델에 중요한 특징(입력 레벨, 정지 ‖a‖, 세션 길이)부터.
- **다변량 drift**: 각 특징의 분포는 그대로인데 상관이 바뀌는 경우(예: accel과 gyro의 축 매핑이 바뀜)는 1차원 PSI로 안 잡힌다. 교차 일관성 지표(1.1절)를 따로 두는 이유다. 더 일반적으로는 "기준 vs 현재를 구분하는 분류기"를 학습해 AUC가 0.5보다 크면 drift로 보는 방법(classifier two-sample test)이 있다.

## 5. 지표 위의 이상 탐지 — robust z, EWMA, CUSUM

4절은 "분포 전체"를 비교했다. 이 절은 **지표 하나의 숫자 열**(기기별 값 목록, 또는 한 기기의 세션별 값 시계열)에서 이상한 것을 찾는다. Don이 제조 쪽에서 봤을 SPC(statistical process control) 그대로다.

### 5.1 robust z-score — 평균과 표준편차는 이상치에 오염된다

**직관**: 기기 200대의 gyro noise floor 중 이상한 기기를 찾고 싶다. 보통 z = (x − 평균) / 표준편차로 3을 넘으면 이상이라고 한다. 그런데 이상치가 평균과 표준편차 자체를 끌어올리면, 이상치의 z가 작아진다. 이걸 **masking**이라 한다.

**정의**: 평균 대신 median, 표준편차 대신 MAD(median absolute deviation)를 쓴다.

```
MAD = median( |xᵢ − median(x)| )
robust z = 0.6745 · (x − median) / MAD
```

말로 하면, "가운데 값에서 얼마나 떨어졌나를, 전형적인 떨어짐 크기로 나눈 것"이다. 정규분포에서는 MAD ≈ 0.6745σ이므로 0.6745를 곱하면 보통 z와 같은 눈금이 된다. 경험적 임계로 3.5를 많이 쓴다(Iglewicz · Hoaglin).

**손계산** — 기기 7대: (0.30, 0.31, 0.29, 0.30, 0.32, 0.90, 0.28).

```
평균 = 2.70 / 7 = 0.3857,  표준편차(모집단) = 0.2103
z(0.90) = (0.90 − 0.3857) / 0.2103 = 2.45        → 3 미만, 못 잡음
median = 0.30,  |x − 0.30| = (0, 0.01, 0.01, 0, 0.02, 0.60, 0.02) → MAD = 0.01
robust z(0.90) = 0.6745 × 0.60 / 0.01 = 40.5     → 확실히 잡음
```

사실 n = 7이면 보통 z는 **아무리 큰 이상치라도 √(n−1) = √6 ≈ 2.45를 넘을 수 없다** (Samuelson 부등식). 위의 2.45가 바로 그 상한이다. 작은 그룹에서 "z > 3"은 원리적으로 불가능한 규칙이다.

**예제 10** — 무엇을 확인하나: 200대 중 8대가 고장(가벼운 것부터 심한 것까지)일 때 보통 z와 robust z의 검출 비교.

```python
# 기기 간 비교: 평균/표준편차 z-score vs median/MAD robust z-score (masking 효과)
r = np.random.default_rng(3)

for i in bad: print(f"{i:3d}  {noise[i]:.2f}  {z[i]:5.2f}  {rz[i]:8.1f}")
print("z>3 로 잡힌 기기:", np.flatnonzero(z > 3).tolist())
print("robust z>3.5 로 잡힌 기기:", np.flatnonzero(rz > 3.5).tolist())
```

### 5.2 SPC 세 가지 — Shewhart, EWMA, CUSUM

한 기기의 세션별 지표 xₜ가 시간 순으로 들어온다. 정상 상태 평균 μ, 표준편차 σ를 기준 기간에서 추정하고 zₜ = (xₜ − μ)/σ로 표준화한다.

| 방법 | 통계량 | 알림 조건 | 성격 |
|---|---|---|---|
| Shewhart | zₜ 그대로 | ∣zₜ∣ > 3 | 큰 변화를 즉시. 작은 변화엔 둔함. 기억 없음 |
| EWMA | Eₜ = λ·zₜ + (1−λ)·Eₜ₋₁ | ∣Eₜ∣ > L·√(λ/(2−λ)) | 지수 가중 평균. 1차 IIR 저역통과 필터 |
| CUSUM | C⁺ₜ = max(0, C⁺ₜ₋₁ + zₜ − k) (아래쪽도 대칭) | C⁺ₜ > h | 기준보다 위로 벗어난 양을 누적. 작은 지속 변화에 최적 |

말로 하면:

- **EWMA**는 Don에게 익숙한 1차 IIR 필터 `y += λ·(x − y)`다. 잡음을 평균 내서 줄이고, 줄어든 잡음 크기(정상 상태 표준편차 σ·√(λ/(2−λ)))의 L배를 임계로 쓴다.
- **CUSUM**은 "k만큼은 봐준다. k를 넘는 부분만 쌓는다. 쌓인 게 h를 넘으면 알림, 0 아래로는 안 내려간다." 누설(leak)이 있는 적분기 + 0 클램프다. k는 **잡고 싶은 shift 크기의 절반**(σ 단위)으로 잡는 것이 정석이다 — 1σ shift를 잡고 싶으면 k = 0.5.

**CUSUM 손계산** — k = 0.5, h = 3, z = (0.2, 1.4, 1.1, 0.9, 1.6, 1.3):

```
C₀ = max(0, 0   + 0.2 − 0.5) = 0
C₁ = max(0, 0   + 1.4 − 0.5) = 0.9
C₂ = max(0, 0.9 + 1.1 − 0.5) = 1.5
C₃ = max(0, 1.5 + 0.9 − 0.5) = 1.9
C₄ = max(0, 1.9 + 1.6 − 0.5) = 3.0    (h = 3을 "넘지"는 않음)
C₅ = max(0, 3.0 + 1.3 − 0.5) = 3.8    → 알림
```

z 하나하나는 2도 안 되지만(Shewhart라면 조용), 계속 1 근처에 있으니 쌓여서 넘는다.

### 5.3 코드로 확인 — 한 기기의 gyro noise floor가 +1σ 올라갔다

**예제 11** — 무엇을 확인하나: 정상 σ = 0.02 dps, 세션 100부터 noise floor가 0.30 → 0.32(+1σ)로 오를 때 세 방법의 첫 알림 시점.

```python
# 한 기기의 세션별 지표(gyro noise floor) 스트림에서 작은 shift 찾기: Shewhart 3σ vs EWMA vs CUSUM
MU, SIG = 0.30, 0.02                                    # 정상 상태 평균·표준편차 (기준 기간에서 추정)
def detectors(x, k=0.5, h=5.0, lam=0.2, L=3.0):
    z = (x - MU) / SIG
    shew = np.abs(z) > 3
    e = np.zeros_like(z); cp = np.zeros_like(z); cm = np.zeros_like(z)
    ep = sp = sm = 0.0
    for i, zi in enumerate(z):
        ep = lam * zi + (1 - lam) * ep; e[i] = ep            # EWMA
        sp = max(0.0, sp + zi - k); cp[i] = sp               # 위쪽 CUSUM
        sm = max(0.0, sm - zi - k); cm[i] = sm               # 아래쪽 CUSUM
    ewma = np.abs(e) > L * np.sqrt(lam / (2 - lam))
    cusum = (cp > h) | (cm > h)
    first = lambda m: int(np.argmax(m)) if m.any() else None
    return first(shew), first(ewma), first(cusum), cp
r = np.random.default_rng(21)
x = r.normal(MU, SIG, 200); x[100:] += 1.0 * SIG         # session 100부터 +1σ (0.30 → 0.32)
s, e, c, cp = detectors(x)
print(f"변화점 100 | Shewhart 첫 알림 {s} | EWMA {e} | CUSUM {c}")
print("CUSUM C+ (95..115):", np.round(cp[95:116], 1).tolist())
```


### 5.4 ARL — 오경보 간격과 검출 지연을 한 숫자로

SPC에서는 성능을 **ARL(average run length)**로 말한다. 정상일 때 첫 (오)알림까지 평균 몇 표본인지가 ARL₀(클수록 좋음), shift가 있을 때 첫 알림까지가 ARL₁(작을수록 좋음 = 검출 지연). 4.6절의 "오경보/30일 vs 지연"과 같은 trade-off를 다른 단위로 말한 것이다.

**예제 12** — 무엇을 확인하나: 4000번 Monte Carlo로 세 방법의 ARL을 shift 크기별로 잰다 (k = 0.5, h = 5, λ = 0.2, L = 3).

```python
# Monte Carlo: 정상일 때 평균 몇 세션마다 오경보(ARL0)? shift가 생기면 평균 몇 세션 뒤에 잡나(지연)?
def run_length(shift, n_runs=4000, T=3000, k=0.5, h=5.0, lam=0.2, L=3.0, seed=0):
    z = np.random.default_rng(seed).normal(shift, 1, (n_runs, T))   # 이미 표준화된 지표
    out = {}
    out["Shewhart"] = np.abs(z) > 3
    e = np.zeros(n_runs); sp = np.zeros(n_runs); sm = np.zeros(n_runs)
    ew = np.zeros_like(z, bool); cu = np.zeros_like(z, bool)
    lim = L * np.sqrt(lam / (2 - lam))
    for t in range(T):
        e = lam * z[:, t] + (1 - lam) * e; ew[:, t] = np.abs(e) > lim
        sp = np.maximum(0, sp + z[:, t] - k); sm = np.maximum(0, sm - z[:, t] - k)
        cu[:, t] = (sp > h) | (sm > h)
    out["EWMA"], out["CUSUM"] = ew, cu
    return {n: np.where(m.any(1), m.argmax(1) + 1, T).mean() for n, m in out.items()}
print("shift(σ)  Shewhart   EWMA   CUSUM   (평균 run length, 세션)")
for sh in [0.0, 0.5, 1.0, 2.0, 3.0]:
    rl = run_length(sh)
    print(f"  {sh:3.1f}    {rl['Shewhart']:7.1f} {rl['EWMA']:7.1f} {rl['CUSUM']:7.1f}")
```

```text
  0.0      369.4   546.0   468.6
  0.5      154.0    43.1    37.1
  1.0       44.0    10.9    10.5
  2.0        6.4     3.8     4.0

```

출력에서 볼 것:

- shift 0(정상): Shewhart 369 — 이론값 1/0.0027 = 370과 일치한다(양쪽 3σ 밖 확률 0.27%). EWMA 546, CUSUM 469. 세 방법 모두 "대략 400~500세션에 한 번 오경보"로 비슷하게 맞춰져 있다. (T = 3000에서 끊었지만 그때까지 알림이 없을 확률은 무시할 만하다.)
- 0.5σ shift: Shewhart 154세션, CUSUM 37세션. **작은 shift에서 4배 빠르다.**
- 1σ shift: Shewhart 44, EWMA 11, CUSUM 10.5.
- 3σ shift: Shewhart 2.0이 가장 빠르다. 큰 변화는 Shewhart가 즉시 잡는다.

그래서 실무에서는 **둘을 같이** 쓴다: Shewhart(또는 단순 임계)로 큰 사고를 즉시, CUSUM/EWMA로 서서히 나빠지는 것을. 이건 SSD에서 "UECC 1건이면 즉시 알림" + "correctable error 비율의 추세 감시"를 같이 하던 것과 같다.

## 6. Model-in-the-loop 품질 — 모델 출력도 센서다

### 6.1 무엇을 보나

배포된 모델의 출력은 라벨 없이도 볼 수 있는 가장 민감한 지표다. 입력 파이프라인 어디가 고장 나든 결국 출력 분포가 바뀐다.

| 지표 | 단위 | 의미 | 연결 |
|---|---|---|---|
| confidence 히스토그램 | 기기 · FW별, 일 단위 | 모델이 얼마나 확신하나. 입력이 학습 분포에서 멀어지면 보통 아래로 이동 | 4절 PSI로 비교 |
| abstain(보류) 비율 | 회색 지대(예: 0.4~0.6)에 든 비율 | 판단을 못 하는 입력의 비율 | — |
| wake word trigger rate | 기기당 시간당 횟수 | 오작동(FA)의 대리 지표. 사용자 불만과 직결 | A4 9절 FA/hour, B5 |
| 예측 클래스 비율 | 그룹 · 일 단위 | prediction drift | 4.1절 |
| 추론 latency · 실패 수 | p50 · p99 | 런타임 · 전력 문제 | D6, F8 |
| on-device vs server 불일치율 | shadow 세션 | 양자화 · 전처리 차이, 모델 버전 문제 | C8 |

### 6.2 코드로 확인 — trigger 폭주 기기와 confidence 이동

trigger 수는 "사건 수"라서 Poisson 분포로 모델링한다. 기대 횟수 λ에서 k번 이상 볼 확률이 아주 작으면 이상이다. 기기 300대를 동시에 검정하므로 유의수준을 300으로 나눈다(Bonferroni) — 300번 검정하면 우연히 p < 0.01이 3번은 나오기 때문이다.

**예제 13** — 무엇을 확인하나: (1) fleet 기준 rate와 비교하면 무엇이 잘못 잡히는지, 자기 과거와 비교하면 어떻게 되는지. (2) FW 업데이트로 입력 gain이 틀어졌을 때 confidence 분포 · abstain 비율 · PSI.

```python
# model-in-the-loop: 기기별 wake-word trigger 수 (Poisson 꼬리 검정) + confidence 분포 PSI·abstain 비율
r = np.random.default_rng(13)
ND, H = 300, 24                                          # 300대, 하루 24시간 집계
base = r.gamma(4, 0.5 / 4, ND)                           # 기기별 정상 trigger rate (평균 0.5/h, 사용자 차이)
lam = base.copy(); lam[[7, 123]] = [3.0, 1.5]            # 7: mic 잡음 고장, 123: 시끄러운 환경?
counts = r.poisson(lam * H)
lam0 = np.median(counts) / H                             # fleet 기준 rate (robust)
p = stats.poisson.sf(counts - 1, lam0 * H)               # P(X ≥ 관측값 | 정상 rate)
alpha = 0.01 / ND                                        # 300대를 동시에 검정 → Bonferroni
print(f"fleet median rate {lam0:.3f}/h, 하루 기대 {lam0 * H:.1f}회")
for i in np.argsort(p)[:4]:
    print(f"dev {i:3d}: {counts[i]:3d}회/일  p={p[i]:.1e}  {'ALERT' if p[i] < alpha else ''}"
          f"  (실제 정상 rate {base[i]:.2f}/h)")
hist = r.poisson(base * H * 7)                           # 같은 기기의 지난 7일 (고장 전)
p_self = stats.poisson.sf(counts - 1, (hist + 1) / 7)    # 자기 자신의 과거와 비교
print("자기 기준선 대비 ALERT:", np.flatnonzero(p_self < alpha).tolist())
def scores(n, shift):                                    # trigger 직전 창의 model confidence
    return np.clip(r.beta(8, 2, n) - shift, 0, 1)
before, after = scores(20000, 0.0), scores(20000, 0.08)  # 새 FW: 입력 gain 버그로 점수 하락
for name, s in [("before", before), ("after", after)]:
    acc = s >= 0.6; gray = (s >= 0.4) & (s < 0.6)
    print(f"{name}: 수락 {100 * acc.mean():.1f}%  abstain(0.4~0.6) {100 * gray.mean():.1f}%"
          f"  median {np.median(s):.3f}")
print(f"confidence PSI = {psi(before, after):.3f}")
```

```text
dev   7:  77회/일  p=3.6e-41  ALERT  (실제 정상 rate 0.65/h)
dev 123:  41회/일  p=1.8e-13  ALERT  (실제 정상 rate 0.49/h)
```

출력에서 볼 것:

- fleet 기준으로 검정하면 고장 기기 7과 123 외에 **기기 3과 81도 ALERT**다. 그런데 이 둘의 "실제 정상 rate"는 1.05, 1.57/h — 원래 말을 많이 거는 사용자(또는 TV가 켜진 집)다. 사용자마다 기본 rate가 다르기 때문에(과산포, overdispersion) fleet 하나의 λ로 모든 기기를 재면 "원래 바쁜 기기"가 고장으로 보인다.
- **자기 자신의 지난 7일과 비교하면** 7과 123만 남는다. 기기 단위 지표는 기기 자신의 기준선과 비교하는 것이 기본이다 (5.5절 표).
- confidence: 수락 92.8% → 84.1%, abstain 6.8% → 14.5%로 두 배, PSI 1.15. 라벨이 하나도 없어도 "새 FW 이후 모델이 덜 확신한다"를 하루 만에 알 수 있다. abstain이 늘면 사용자 쪽에서는 "말을 못 알아듣는다"로 나타난다.

### 6.3 Shadow evaluation — on-device vs server

라벨이 없을 때 정확도의 대리 지표를 얻는 방법이다.

1. dogfood · opt-in 기기에서 세션 일부의 raw 입력을 업로드한다 (H6 동의 범위 안에서).
2. 서버에서 **큰 모델(teacher) 또는 같은 모델의 float 버전**으로 같은 입력을 다시 추론한다.
3. 기기 결과와 비교해 불일치율을 FW · 모델 버전 · HW별로 집계한다.

불일치가 갑자기 늘면 (a) 기기 쪽 전처리 · 양자화 경로가 바뀌었거나(C8의 회귀 테스트가 놓친 것), (b) 입력 분포가 큰 모델은 버티고 작은 모델은 못 버티는 쪽으로 바뀐 것이다. 불일치 세션은 그대로 **라벨링 우선순위 큐**(H4 active learning)로 보낸다 — 모니터링이 데이터 수집을 이끈다.

## 7. 루프 닫기 — quarantine, triage, RMA

### 7.1 Quarantine — 지우지 말고 태그를 단다

나쁜 세션을 학습셋에서 빼는 방법은 **데이터셋 manifest에 태그를 다는 것**이다. 원본은 지우지 않는다. 이유:

- 판정 규칙이 틀렸을 수 있다 (규칙을 고치면 되살린다).
- 원인이 고쳐지면 보정해서 다시 쓸 수 있다 (gain 버그는 나누기 한 번으로 복원).
- 고장 데이터 자체가 **고장 검출 모델의 학습 데이터**다.

H5의 데이터셋 버전에는 "어떤 QA 규칙 버전으로 어떤 세션을 뺐는지"가 들어가야 재현이 된다.

**예제 14** — 무엇을 확인하나: 세션 QA 판정과 fleet 사고 판정을 manifest의 quarantine 태그로 바꾸고, 원인이 확인된 경우 보정 후 복원 가능성을 확인한다.

```python
# 루프 닫기: QA 결과 + fleet 알림 → dataset manifest의 quarantine 태그 (삭제가 아니라 태그)
man = report[["verdict", "flags"]].reset_index()
man["quarantine"] = np.select(
    [man.verdict == "FAIL", man["flags"].str.contains("AV_SYNC")],
    ["qa_fail", "needs_resync"], default="")                           # WARN 중 일부는 고칠 수 있다
print(man.to_string(index=False))
# fleet 규칙: (fw 1.5.0, imu_vendor2) device-day는 원인 확인 전까지 학습 제외
ff = fleet.merge(dev[["device", "imu_vendor2"]])
rule = (ff.fw == "1.5.0") & ff.imu_vendor2
ff["quarantine"] = np.where(rule, "INC-0042:accel_gain_fw150_vendor2", "")
print(f"\nfleet device-day {len(ff)}개 중 quarantine {rule.sum()}개 ({100 * rule.mean():.1f}%)")
print("학습셋 후보 (quarantine 없음):", int((ff.quarantine == "").sum()))
# 버그가 fw 1.5.1에서 고쳐지고 gain이 정확히 1.10이었다면? → 보정 후 복원(re-admit)도 가능
fix = ff[rule].amag_g / 1.10
print(f"보정 후 |a| median {fix.median():.4f} g, 범위 밖 비율 {100 * ((fix - 1).abs() > 0.05).mean():.1f}%")
```

출력에서 볼 것: FAIL 4개는 `qa_fail`, AV_SYNC만 걸린 세션은 `needs_resync` — 버리지 않고 G7의 재정렬 단계로 보낸다(offset만 틀린 세션은 고칠 수 있다). fleet 사고는 ticket 번호(INC-0042)를 태그에 넣어서, 나중에 "이 세션들은 왜 빠졌나"를 추적할 수 있게 한다. 731개 device-day(5.4%)가 빠졌고, gain이 정확히 1.10이었다면 나눠서 복원하면 이상 비율 0%가 된다. 단, 포화된 샘플은 복원이 안 된다 — 잘린 값은 영원히 잘린 값이다.

pandas 함정 하나: 코드에서 `man.flags`가 아니라 `man["flags"]`를 쓴 이유는 `DataFrame.flags`가 pandas의 내장 속성이라서 열 이름 대신 그것이 나오기 때문이다. 열 이름이 `flags`, `index`, `values`, `shape`처럼 DataFrame 속성과 겹치면 항상 대괄호로 접근한다.

### 7.2 Triage — 증거가 붙은 ticket

알림 → 사람이 판단 → 조치. 사람이 빨리 판단하려면 알림이 **증거를 같이 들고 와야** 한다. F8의 vendor 버그 리포트(재현 조건 · 버전 · 최소 재현 예 · 기대 vs 실제)와 같은 형식이다.

```text
[INC-0042] accel ‖a‖ 정지값 +10% — FW 1.5.0 × HW rev B × IMU vendor2
감지     : day 15 09:00, 규칙 GRP_GRAVITY_OOR (그룹 n ≥ 20, 이상 기기 > 5%)
범위     : rev B × 1.5.0 기기의 27~31%, rev A · 1.4.0에서는 0%
drill-down: imu_vendor2 = True → 100%, False → 0%   (예제 6)
증거     : 그룹별 일별 표, KS D = 0.299 (rev B 1.4.0 vs 1.5.0), 대표 세션 5개 링크
추정 원인: 1.5.0의 2nd-source IMU sensitivity 테이블 (gain ×1.10과 일치)
영향     : 해당 세션 학습 제외 (quarantine 731 device-day), 제스처 인식률 영향 추정 필요
조치     : 1.5.0 rollout 정지 → FW 담당 지정 → 1.5.1 수정 확인 후 보정 · 복원 판단
```

triage 순서는 bring-up 디버깅과 같다: (1) 범위 확정 — 어떤 차원에서 갈리나, (2) 최초 시점 — 무엇이 바뀐 날인가(FW, 앱, 서버 파서, 계절), (3) 대표 표본을 raw로 열어 눈으로 확인, (4) 가설 → 재현(실험실 기기에 같은 FW) → 수정 → 지표로 확인.

**파이프라인 자신도 의심한다**: 지표가 갑자기 바뀌었는데 원인이 기기가 아니라 서버 파서 배포, 지표 정의 변경, 시간대 처리 버그인 경우가 의외로 많다. 백엔드 배포 이력도 같은 대시보드에 표시한다.

### 7.3 RMA 같은 하드웨어 고장 분석

센서 고장 판정(STUCK, MIC_DEAD 등)이 반복되는 기기는 하드웨어 문제일 가능성이 높다. Don이 SSD · 칩 신뢰성에서 하던 분석이 그대로다.

- **코호트**: 고장을 생산 lot, 센서 vendor, date code, 조립 라인, 출하 국가로 나눈다.
- **고장률 단위**: "고장 수 / 기기-월(device-month)". 운영 기간이 다른 기기를 공정하게 비교한다. 예: lot X는 4,000 기기-월에 12건 → 3.0건/1000 기기-월, 나머지는 10,000 기기-월에 2건 → 0.2건/1000 기기-월. 15배.
- **고장 시점 분포**: 초기 고장(infant mortality — 출하 직후 몰림), 우발 고장(일정), 마모 고장(시간이 갈수록 증가)의 bathtub 곡선. 마이크 메쉬 막힘 같은 마모형은 4.5절의 gradual drift로 먼저 보인다.
- **조기 경보 → 예방 조치**: 지표(noise floor 상승, mic 레벨 하락)가 고장보다 먼저 움직이면, 고장 전에 사용자에게 청소 안내를 하거나 교체를 제안할 수 있다. SSD의 predictive failure(SMART 임계 전 경고)와 같다.
- **현장 반납품 분석과 연결**: RMA로 돌아온 기기의 실험실 측정 결과를 그 기기의 fleet 지표 이력과 붙여 놓으면, 어떤 지표가 고장을 가장 일찍 예고했는지 배울 수 있다.

### 8.2 metrics schema

| 필드 | 예 | 메모 |
|---|---|---|
| session_id, device_id(가명) | `s_8f3a…`, `d_19c2…` | device_id는 해시 · 가명 (H6) |
| t_start, duration_s | 2026-09-30T09:00Z, 30 | UTC, 기기 시계 → 서버 시계 보정 여부 플래그 |
| fw, hw_rev, sensor_vendor, sensor_lot, app_ver | 1.5.0, B, vendor2, L2408 | 차원. 나중에 추가하기 어렵다 — 처음부터 넣는다 |
| sensor_config | acc_fs_g = 8, odr = 100 | 판정에 필요 (포화 · 단위) |
| metric_name, value, metric_def_ver | sat_pct, 0.0, v3 | 지표 정의 버전 (1.3절) |
| qa_verdict, qa_flags, qa_rules_ver | FAIL, STUCK, r12 | 재현 가능한 판정 |
| quarantine_tag | INC-0042:… | 학습셋 manifest와 공유 |

long 포맷(지표 하나당 한 행)은 지표 추가가 쉽고, wide 포맷(세션 하나당 한 행, 지표가 열)은 집계가 빠르다. 보통 수집은 long, 분석용 테이블은 wide(Parquet 열 저장)로 만든다.

### 8.3 저장 비용

**예제 15** — 무엇을 확인하나: 100만 대, 기기당 하루 20세션일 때 raw vs 세션 QA 행 vs 기기-일 요약의 저장량.

```python
# 저장 비용 산수: raw 센서 vs 세션 QA 지표 vs 일 단위 기기 요약 (100만 대 가정)
DEV, SESS = 1_000_000, 20                          # 기기 수, 기기당 하루 세션 수 (30 s)
raw_imu = 6 * 2 * 100 * 30                         # 6축 × int16 × 100 Hz × 30 s
raw_mic = 2 * 16000 * 30                           # int16 × 16 kHz × 30 s
qa_row = 40 * 4 + 64                               # 지표 40개 float32 + 키/메타 64 B
day_row = 120 * 4 + 64                             # 기기-일 요약: 지표 40개 × (p50, p95, max)
for name, b in [("raw IMU+mic", raw_imu + raw_mic), ("session QA", qa_row), ("device-day", day_row / SESS)]:
    per_day = b * SESS * DEV
    print(f"{name:12s} {b:>9,.0f} B/세션 → {per_day / 1e12:9.4f} TB/일 → {per_day * 365 / 1e12:9.2f} TB/년")
```

```text
raw IMU+mic    996,000 B/세션 →   19.9200 TB/일 →   7270.80 TB/년
session QA         224 B/세션 →    0.0045 TB/일 →      1.64 TB/년
device-day          27 B/세션 →    0.0005 TB/일 →      0.20 TB/년
```

출력에서 볼 것: raw는 하루 20 TB(년 7 PB) — 전부 올리는 것은 비용으로도, 배터리 · 대역폭(H2)으로도, 프라이버시(H6)로도 불가능하다. 세션 QA 행은 4,400배 작아서 1년에 1.6 TB, **모든 기기의 모든 세션**을 감시할 수 있다. 이것이 "지표는 전수, raw는 표본" 원칙의 산수다. NVMe SMART log가 512 B로 drive 전체 상태를 요약하던 것과 같은 설계다.

### 8.4 프라이버시 — 집계만 (H6)

- 기기에서 나가는 품질 지표는 **센서 신호의 내용이 아니라 상태**만 담는다: 포화 수, 레벨 통계, 드롭 수. 음성 내용은 복원할 수 없다.
- mic 레벨 히스토그램처럼 세밀한 분포도, 기기 하나의 시간별 패턴은 생활 패턴(언제 말하나, 언제 자나)을 드러낼 수 있다. 시간 해상도를 낮추거나(일 단위), 그룹 집계 후에만 보여 주거나, 노이즈를 더한다(differential privacy).
- raw 세션은 명시적 동의(opt-in)와 보관 기간 정책이 있을 때만. quarantine된 raw는 디버깅이 끝나면 보관 기간 규칙에 따라 지운다.

## 9. 임베디드 관점에서 다시 보기 — 기기 쪽 health 카운터

기기 쪽 검사는 **샘플마다 상수 시간, 축당 수십 바이트**여야 한다. ISR · DMA 완료 콜백에서 돌 수 있는 수준이다. 세션이 끝나면 고정 크기 요약 레코드로 로그에 남기고 업로드한다. NVMe SMART / Health log page처럼 "고정 레이아웃의 카운터 묶음"이다.

**예제 16** — 무엇을 확인하나: int16 원시 count에 대해 포화 수, 최장 동일값 run, min · max, 합 · 제곱합을 샘플당 O(1)로 갱신하는 C 구조체. 1초 포화 + 20초 이후 stuck을 주입해 확인한다.

```c
/* 온디바이스 health 카운터: 샘플마다 O(1), 세션 끝에 고정 크기 요약 레코드 (NVMe SMART log page 느낌) */
#include <math.h>
#include <stdint.h>
#include <stdio.h>
#include <string.h>
#define FS_MAX 32767
#define FS_MIN (-32768)
typedef struct {                 /* 축 하나 */
    uint32_t n, sat, run, max_run;
    int16_t prev, min, max;
    int64_t sum, sumsq;          /* 평균·분산용 (정수 누적, 오버플로 주의: 30 s × 100 Hz면 충분) */
} axis_health_t;
static void ah_reset(axis_health_t *h) { memset(h, 0, sizeof *h); h->min = FS_MAX; h->max = FS_MIN; }
static void ah_update(axis_health_t *h, int16_t x) {
    if (x >= FS_MAX - 1 || x <= FS_MIN + 1) h->sat++;            /* 끝값 근처 = 포화 */
    h->run = (h->n && x == h->prev) ? h->run + 1 : 1;            /* 같은 값 연속 길이 */
    if (h->run > h->max_run) h->max_run = h->run;
    if (x < h->min) h->min = x;
    if (x > h->max) h->max = x;
    h->sum += x; h->sumsq += (int64_t)x * x; h->prev = x; h->n++;
}
int main(void) {
    axis_health_t ax, gy;
    ah_reset(&ax); ah_reset(&gy);
    uint32_t lcg = 12345u;
    for (int i = 0; i < 3000; i++) {
        lcg = lcg * 1664525u + 1013904223u;
        int16_t noise = (int16_t)((int32_t)(lcg >> 24) - 128);   /* −128..127 LSB 잡음 */
        int16_t a = (i >= 1000 && i < 1100) ? FS_MAX : noise;    /* 1 s 포화 */
        int16_t g = (i >= 2000) ? 517 : noise;                    /* 20 s 이후 stuck */
        ah_update(&ax, a); ah_update(&gy, g);
    }
    const axis_health_t *hs[2] = { &ax, &gy };
    for (int k = 0; k < 2; k++) {
        const axis_health_t *h = hs[k];
        double mean = (double)h->sum / h->n, var = (double)h->sumsq / h->n - mean * mean;
        printf("%s: n=%u sat=%u (%.2f%%) max_run=%u min=%d max=%d mean=%.1f std=%.1f\n",
               k ? "gyro_y" : "acc_x", h->n, h->sat, 100.0 * h->sat / h->n, h->max_run,
               h->min, h->max, mean, var > 0 ? sqrt(var) : 0.0);
    }
    printf("sizeof(axis_health_t) = %zu B\n", sizeof(axis_health_t));
    return 0;
}
```

```sh
cc -std=c11 -Wall -Wextra -O2 ex16.c -o ex16 -lm && ./ex16
```

```text
acc_x: n=3000 sat=100 (3.33%) max_run=100 min=-128 max=32767 mean=1091.5 std=5882.4
gyro_y: n=3000 sat=0 (0.00%) max_run=1000 min=-128 max=517 mean=171.9 std=251.3
sizeof(axis_health_t) = 40 B
```

출력에서 볼 것: acc_x는 포화 100샘플(3.33%)이 정확히 잡히고 max = 32767. gyro_y는 2000번째 샘플부터 517로 고정해서 최장 run이 1000샘플(10 s)이다. 축당 구조체 40 B — 6축이면 240 B, 세션당 한 번 기록하면 저장 · 전송 부담이 거의 없다.

설계 메모:

- **분산 계산**: 정수 합 · 제곱합으로 세션 끝에 한 번 분산을 낸다. int16 값의 제곱은 최대 2³⁰이므로 int64 누적은 2³³개 샘플까지 오버플로가 없다. 다만 E[x²] − E[x]² 공식은 평균이 크고 분산이 작을 때(예: 중력이 실린 z축) float에서 정밀도를 잃는다 — 여기서는 정수 누적이라 정확하고, float로 바꿀 때만 조심하면 된다. 더 안전하게는 정지 구간 평균을 빼고 누적하거나 Welford 알고리즘을 쓴다.
- **noise floor는 정지 구간에서**: 세션 전체 std(예제의 acc_x std 5882)는 포화 구간 · 동작이 섞여 의미가 없다. 기기에서는 "움직임 없음" 판정(이미 착용 감지 · 활동 인식 FW에 있음)이 켜졌을 때만 별도 누적기를 갱신한다.
- **stuck 임계는 LSB 기준으로**: `x == prev` 비교는 저잡음 센서에서 정상적으로도 길어질 수 있다. 센서 noise가 LSB의 몇 배인지 보고 임계를 정한다(1.3절).
- **FW가 즉시 대응**: stuck이 수 초 이어지면 FW가 센서를 soft reset하고 그 사실을 이벤트 로그에 남긴다. 리셋 횟수 자체가 fleet 지표가 된다 — SSD에서 "controller reset 횟수"를 health 지표로 보던 것과 같다.

## 11. 면접에서 이렇게 말한다

**Q.** "How would you detect a sensor going bad across a fleet?"

**A.** 기기에서 센서 health 카운터(포화, 동일값 run, noise, bias, mic 레벨)를 세션마다 요약해 올린다. 백엔드에서 두 방향으로 비교한다. 같은 시점의 다른 기기들과는 HW · vendor 그룹 안에서 robust z(median · MAD)로, 같은 기기의 과거와는 CUSUM · EWMA로 작은 지속 변화를 잡는다. 반복되는 기기는 lot · vendor 코호트로 묶어 고장률(건/기기-월)을 비교한다. SSD fleet에서 SMART 카운터로 하던 것과 같은 구조다.

> I'd have the firmware keep cheap per-session health counters — saturation counts, longest constant run, noise floor at rest, gyro bias, mic level and DC — and upload them for every session, the same way an SSD exposes a SMART log page. In the backend I compare each device two ways: against its peers in the same hardware and sensor-vendor group using a robust z-score based on the median and MAD, so a few dead units don't mask the slowly degrading ones, and against its own history with a CUSUM or EWMA chart, which catches a one-sigma drift in about ten sessions where a three-sigma limit would take forty. Devices that keep tripping get grouped by lot and vendor, and I look at failures per thousand device-months, which is exactly the RMA cohort analysis I used to do for data-center SSDs.

**Q.** "A FW update broke the IMU scaling on some units — how do you catch it fast?"

**A.** 물리 불변량을 지표로 둔다: 정지 시 ‖a‖ ≈ 1 g. staged rollout 동안 매일 (FW × HW × 센서 vendor) 그룹별로 이 지표의 p95와 "정상 범위 밖 기기 비율"을 보고, 같은 날 업데이트 전 기기와 비교한다. 평균 · median은 희석되므로 안 된다. 시뮬레이션에서 12% 기기만 망가졌을 때 fleet median은 1.000 → 1.001로 안 보였지만 그룹별 이상 비율은 배포 첫날 27%로 바로 알림이 떴고, vendor로 drill-down하니 100% 대 0%로 원인까지 나왔다. 알림은 rollout을 자동 정지한다.

> I'd monitor a physical invariant rather than the raw values: the accelerometer magnitude at rest should be one g. During a staged rollout I slice that metric every day by firmware, hardware revision and IMU vendor, and look at the tail and the fraction of devices out of tolerance, not the mean, because the mean gets diluted by the unaffected units. In a simulation where only about twelve percent of the fleet had a ten percent gain error, the fleet median barely moved, but the affected slice showed twenty-seven percent of devices out of range on the very first day, and drilling down by IMU vendor split it a hundred to zero. That alert should automatically pause the rollout, and the affected sessions get quarantined from training data.

**Q.** "What is PSI / KS and when would you alert?"

**A.** PSI는 기준과 현재 분포를 bin으로 나눠 ∑(a−e)·ln(a/e)를 더한 것으로 양방향 KL의 합이다. 같은 σ의 정규분포라면 PSI ≈ (Δ/σ)², 즉 0.25는 평균이 σ의 절반 움직인 것이다. KS는 두 CDF의 최대 수직 거리 D다. 대량 데이터에서는 KS p-value가 사소한 날 변동에도 1% 아래로 떨어지므로 p가 아니라 D나 PSI 같은 effect size에 임계를 건다. 임계는 오경보 예산에서 정한다: 시뮬레이션에서 PSI 0.1 하루 규칙은 오경보가 거의 없지만 서서히 오는 drift를 14일 늦게 잡았고, 0.03 이틀 연속 규칙은 한 달 0.1회 오경보에 10일이었다.

> PSI bins the reference and current distributions and sums the difference times the log ratio in each bin — it's the symmetric KL divergence. For a mean shift between equal-variance Gaussians it's roughly the shift in sigmas squared, so 0.25 means the mean moved half a sigma. KS is the maximum vertical gap between the two empirical CDFs. With thousands of samples per day the KS p-value goes significant on ordinary day-to-day noise, so I alert on effect size — the D statistic or PSI — not on p-values, and I pick the threshold from an alert budget. In my simulation a single-day PSI threshold of 0.1 almost never false-alarmed but caught a slow drift two weeks late, while requiring two consecutive days above 0.03 gave about one false alarm every eight months per feature and caught it in ten days. Sudden shifts are easy at any threshold; gradual ones are where the trade-off lives.

**Q.** "How do you keep bad data out of training sets?"

**A.** 모든 세션이 ingest에서 schema 검사와 세션 QA(완전성, 범위 · 단위, 포화, stuck, bias, mic 상태, 센서 간 정렬)를 통과해야 하고, 판정은 규칙 버전과 함께 dataset manifest의 태그로 남는다. FAIL은 제외, 고칠 수 있는 것(시계 offset)은 재처리, fleet 사고는 ticket 번호로 일괄 quarantine한다. 삭제하지 않으므로 규칙을 고치거나 원인을 보정하면 되살릴 수 있다. QA 함수 자체는 결함을 주입한 합성 세션으로 회귀 테스트한다.

> Every session goes through an ingest validator — schema and metadata checks, then a session QA that computes completeness, range and unit sanity, saturation, stuck channels, bias steps, mic dead, clipping and DC, and cross-sensor alignment using shared events like taps. The verdict and the rule version are written as a tag in the dataset manifest rather than deleting anything: failures are excluded, fixable issues like a clock offset are sent back for reprocessing, and fleet incidents quarantine whole slices under a ticket ID. Because nothing is deleted, I can re-admit data if a rule was wrong or if the root cause is correctable, like a known gain error. And the QA code itself has a regression suite of synthetic sessions with injected faults, so I know each check actually fires.

**Q.** "Which checks run on device vs in the backend?"

**A.** 기기에서는 샘플당 O(1)이고 모든 세션에 필요한 것: 포화 · 동일값 run · min/max · 합/제곱합 · 드롭 카운터, mic 레벨 · clip. 이건 raw 없이 전수 감시를 가능하게 하고 프라이버시에도 좋다. ingest에서는 raw가 필요한 판정: schema, 단위, 센서 간 정렬, 세밀한 세션 QA. batch에서는 비교 대상이 다른 기기나 과거인 것: 그룹 집계, drift, CUSUM, 모델 출력 분석. 저장량으로 보면 100만 대 기준 raw는 하루 20 TB지만 세션 지표는 1년에 1.6 TB다.

> On the device I only run things that are constant time per sample and useful for every session: saturation and range counts, longest constant run, min, max, sum and sum of squares, dropped-sample and FIFO overflow counters, and mic level and clip counts. That gives full coverage without uploading raw audio, which matters for both bandwidth and privacy. At ingest, where raw data is available for opted-in sessions, I run schema and unit checks, cross-sensor alignment and the detailed session QA. Anything that needs a comparison — against other devices, against the past, or across firmware versions — runs in batch analytics: group aggregates, drift scores, control charts and model-output monitoring. As a sanity check on cost, for a million devices raw data would be about twenty terabytes a day, while per-session metrics are under two terabytes a year.

| data quality check | 데이터 품질 검사 | 데이터가 형식 · 완전성 · 유효성 · 센서 건강 · 일관성 · 라벨 면에서 쓸 만한지 자동 판정 |

| concept drift | 개념 변화 | P(y ∣ x)가 바뀜. 라벨이 있어야 감지 |
| prediction drift | 예측 분포 변화 | 모델 출력 분포가 바뀜 |
| PSI | Population Stability Index | ∑(a−e)·ln(a/e). 양방향 KL. 0.1 / 0.25 경험칙 |
| KS test | Kolmogorov–Smirnov | 두 경험 CDF의 최대 수직 거리 D |
| effect size | 효과 크기 | 차이의 크기 (D, PSI). p-value와 달리 표본 수에 덜 민감 |
| MAD | median absolute deviation | median으로부터 절대편차의 median. 정규분포에서 ≈ 0.6745σ |
| robust z-score | 강건 z | 0.6745 · (x − median) / MAD. 이상치에 오염되지 않음 |
| masking | 가림 | 큰 이상치가 평균 · 표준편차를 부풀려 다른 이상치를 숨김 |
| Shewhart chart | 슈하트 관리도 | ∣z∣ > 3이면 알림. 큰 변화용 |
| EWMA | 지수 가중 이동 평균 | 1차 IIR로 평활한 통계량의 관리도 |
| CUSUM | 누적합 관리도 | k를 넘는 편차를 누적해 h를 넘으면 알림. 작은 지속 변화용 |
| ARL | average run length | 첫 알림까지 평균 표본 수. ARL₀ 클수록, ARL₁ 작을수록 좋음 |
| overdispersion | 과산포 | 사건 수의 분산이 Poisson 가정보다 큼 (사용자별 rate 차이) |
| shadow evaluation | 그림자 평가 | 같은 입력을 서버의 큰 모델로 다시 돌려 기기 결과와 비교 |
| quarantine | 격리 | 데이터를 지우지 않고 태그로 학습에서 제외 |
| triage | 분류 · 우선순위 판단 | 알림 → 범위 · 시점 · 증거 → 원인 가설 → 담당 지정 |
| RMA | Return Merchandise Authorization | 반품 · 교체 절차. 여기서는 고장 기기 코호트 분석 |

## 14. 요약 & 체크리스트

데이터 품질 모니터링은 SSD fleet telemetry와 같은 구조다: 기기가 싸게 세고(카운터), ingest가 세션을 판정하고(QA 규칙 → PASS/WARN/FAIL → manifest 태그), batch가 그룹과 시간으로 비교한다(FW × HW × vendor 집계, PSI · KS drift, robust z, CUSUM), 그리고 결과가 학습 데이터 정화와 기기 수정 두 방향으로 돌아간다. 핵심 숫자 감각: 평균은 영향 비율만큼 희석되므로 그룹으로 쪼개 꼬리와 이상 비율을 본다 · PSI ≈ (Δ/σ)²라서 0.25는 σ의 절반 · 대량 데이터에서는 p-value가 아니라 effect size에 임계를 건다 · 작은 지속 변화는 CUSUM이 Shewhart보다 4배 빠르다 · 기기 단위 지표는 기기 자신의 과거와 비교한다 · 검사기 자체를 결함 주입으로 회귀 테스트한다.

- [ ] 품질 검사 여섯 범주를 말하고 범주마다 검사 두 개씩 예를 들 수 있다
- [ ] 포화 비율, 최장 동일값 run, 정지 ‖a‖, bias 단차를 작은 배열로 손계산할 수 있다
- [ ] 포화와 범위 밖, root flag와 derived flag를 구분해 설명할 수 있다
- [ ] 결함 주입 세션으로 QA 함수를 검증하는 이유와 방법을 설명할 수 있다
- [ ] 희석 산수(f × Δ)로 fleet 평균이 FW 회귀를 숨기는 이유를 숫자로 말할 수 있다
- [ ] PSI를 손으로 계산하고, PSI = 양방향 KL, PSI ≈ (Δ/σ)²를 설명할 수 있다
- [ ] 대량 표본에서 KS p-value로 알림하면 안 되는 이유를 설명할 수 있다
- [ ] median · MAD로 robust z를 손계산하고 masking과 Samuelson 상한을 설명할 수 있다
- [ ] CUSUM 점화식을 손으로 돌리고 k · h를 고르는 기준과 ARL trade-off를 말할 수 있다
- [ ] 기기 · ingest · batch에 어떤 검사를 둘지와 그 이유(비용 · 프라이버시)를 설계할 수 있다
