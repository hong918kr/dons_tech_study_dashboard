## 0. 큰 그림 — 이게 왜 필요한가

Don이 실리콘 평가를 하게 되면 데이터시트 표에 거의 항상 이런 줄이 있다: "CPU: 8코어, GPU: Adreno xxx, NPU: Hexagon, 45 TOPS". 그리고 PM이나 ML 팀이 묻는다. "GPU가 있는데 NPU가 왜 필요하냐?", "우리 모델은 GPU에서 돌리면 되지 않냐?", "LLM은 GPU로 돌리는 게 빠르다던데?"

이 질문에 답하려면 GPU가 **무엇을 잘하도록 설계된 기계인지**를 알아야 한다. 한 문장으로 요약하면 이렇다.

- CPU는 **latency machine**이다. thread 하나를 가능한 한 빨리 끝내려고 큰 캐시, 분기 예측, out-of-order 실행에 면적을 쓴다.
- GPU는 **throughput machine**이다. thread 하나는 느려도 괜찮고, 수천~수만 개를 **동시에 걸어 두고** 그중 준비된 것을 번갈아 돌려서 전체 처리량을 최대화한다. 면적은 ALU와 레지스터에 쓴다.

## 1. GPU 실행 모델 — SM, SIMT, warp

### 1.1 계층 구조 — thread, warp, block, grid

GPU 프로그래밍 모델은 **같은 함수(kernel)를 아주 많은 thread가 각자 다른 인덱스로 실행**하는 구조다. 펌웨어 식으로 말하면 `for (i = 0; i < N; i++) body(i);`에서 루프를 없애고 `body(i)`를 N개의 thread에 뿌리는 것이다.

소프트웨어 쪽 계층과 하드웨어 쪽 계층이 짝을 이룬다.

```
소프트웨어(프로그래머가 보는 것)            하드웨어(실제로 도는 곳)
grid     = 커널 한 번 launch의 전체 thread     GPU 전체 (SM 여러 개)
 └ block = thread 묶음 (예: 256개)             SM 하나에 배정, 끝날 때까지 그 SM에 상주
    └ warp = 연속된 32 thread                   warp scheduler가 명령을 한 번에 issue하는 단위
       └ thread = 커널 본문 1회 실행             ALU lane 하나 (레지스터를 따로 가짐)
```

- **SM (streaming multiprocessor)**: NVIDIA 용어. GPU의 "코어"에 해당하는 단위다. 안에 ALU lane 수십~백여 개, 큰 레지스터 파일, shared memory, warp scheduler가 있다. AMD는 **CU (compute unit)**, Apple은 그냥 "GPU core", Arm Mali는 "shader core"라고 부른다.
- **warp**: 한 명령을 동시에 실행하는 thread 묶음. NVIDIA는 32다. 한 warp의 32 thread는 **같은 명령어**를 같은 시점에 실행한다.
- **block**(CUDA) / **threadgroup**(Metal) / **work-group**(OpenCL) / **workgroup**(Vulkan): 서로 협력할 수 있는(shared memory 공유, barrier 동기화) thread 묶음. 반드시 한 SM 안에서 돈다.

회사마다 이름이 달라서 처음엔 헷갈린다. 표로 정리한다.

| 개념 | NVIDIA CUDA | AMD | Apple Metal | OpenCL | Vulkan |
|---|---|---|---|---|---|
| 커널 1회 실행 단위 | thread | work-item | thread | work-item | invocation |
| 동시 실행 묶음 | warp (32) | wavefront (64, RDNA는 32도) | SIMD-group (보통 32) | sub-group | subgroup |
| 협력 묶음 | block (thread block) | work-group | threadgroup | work-group | workgroup |
| 전체 | grid | NDRange | grid | NDRange | dispatch |
| 묶음 공유 메모리 | shared memory | LDS (local data share) | threadgroup memory | local memory | shared variables |
| 하드웨어 코어 | SM | CU | GPU core | compute unit | (구현 의존) |

Apple GPU의 SIMD-group 폭은 Metal에서 `threadExecutionWidth`로 조회하며, 현재 Apple GPU들에서는 32로 보고된다고 알려져 있다(정확한 내부 구조는 Apple이 공개하지 않는다). 모바일 GPU는 세대마다 폭이 다르다 — 예컨대 Arm Mali Valhall 세대는 16-wide warp, Qualcomm Adreno는 64/128 fiber 크기의 wave를 쓰는 것으로 알려져 있다. 숫자를 외우기보다 "**warp 폭은 벤더·세대마다 다르고, 런타임에서 조회한다**"를 기억하자.

### 1.2 SIMT vs SIMD — Don이 아는 NEON/HVX와 무엇이 다른가

**SIMD**(single instruction, multiple data)는 Don이 아는 것이다. NEON 명령 하나가 128-bit 레지스터 안의 float 4개를 한 번에 더한다. 프로그래머(또는 컴파일러)가 "4개씩 묶어서" 코드를 쓴다.

**SIMT**(single instruction, multiple threads)는 NVIDIA가 붙인 이름이다. 하드웨어는 사실상 32-wide SIMD인데, 프로그래머에게는 **thread 하나의 스칼라 코드**를 쓰게 한다. 하드웨어가 32개 thread를 모아 한 명령으로 실행하고, 분기가 갈리면 **mask**로 일부 lane을 끈다.

| 항목 | SIMD (NEON, HVX) | SIMT (GPU) |
|---|---|---|
| 프로그래머가 쓰는 코드 | 벡터 코드 (intrinsic, 자동 벡터화) | 스칼라 thread 코드 |
| 폭 | 레지스터 폭 고정 (NEON 128-bit, HVX 1024-bit) | warp 폭 (32 등) |
| 분기 | 프로그래머가 select/blend로 처리 | 하드웨어가 mask로 처리 (divergence) |
| 메모리 접근 | 연속 load 명령 (vld1) | lane마다 주소가 다를 수 있음 (gather) — 하드웨어가 합쳐 줌 (coalescing) |
| 지연 숨기기 | 소프트웨어 파이프라이닝, prefetch | 하드웨어가 다른 warp로 전환 |

말로 하면: SIMT는 "SIMD 하드웨어 + 분기·gather를 하드웨어가 대신 처리해 주는 프로그래밍 모델 + 수십 개의 warp를 번갈아 돌리는 스케줄러"다.

그림 2 — divergence. 8-lane으로 줄여 그렸다. 조건이 섞이면 A 단계와 B 단계를 순서대로 모두 거치고, 각 단계에서 절반 정도의 lane은 자리만 차지한다.

손계산: A와 B가 각각 10 사이클이라고 하자.

- warp 안의 모든 lane이 같은 쪽 → 10 사이클.
- 섞여 있음 → 10 + 10 = 20 사이클. 효율은 절반.
- 32 lane 중 딱 1개만 B → 그래도 20 사이클. **가장 드문 lane 하나가 warp 전체의 비용을 정한다.**

중요한 점: divergence는 **warp 안에서만** 문제다. warp 0은 모두 A, warp 1은 모두 B로 갈리면 각 warp는 한 경로만 실행하므로 손해가 없다.

**예제 1** — 무엇을 확인하나: 1024 thread(32 warp)가 다섯 가지 조건으로 분기할 때 총 사이클을 시뮬레이션한다. 하드웨어 모델은 위의 단순 규칙(원하는 lane이 하나라도 있으면 그 경로를 실행)이다.

```python
# SIMT divergence 시뮬레이터: warp 하나(32 lane)가 if/else를 만나면 몇 "사이클" 걸리나
import numpy as np
WARP, COST_A, COST_B = 32, 10, 10          # 경로 A, B 각각 10 사이클짜리 코드라고 가정
def warp_cycles(cond):                      # cond: lane별 bool (True면 A 경로)
    c = 0
    if cond.any():  c += COST_A             # A를 원하는 lane이 하나라도 있으면 A를 실행 (나머지 lane은 mask off)
    if (~cond).any(): c += COST_B           # B를 원하는 lane이 하나라도 있으면 B도 실행
    return c
def kernel_cycles(n_threads, pred):
    tid = np.arange(n_threads)
    warps = tid.reshape(-1, WARP)           # 연속된 32개 thread = 1 warp
    per = [warp_cycles(pred(w)) for w in warps]
    return sum(per), len(per)
rng = np.random.default_rng(0)
data = rng.standard_normal(1024)
cases = {
    "모두 같은 경로 (if True)":        lambda t: np.ones_like(t, bool),
    "짝/홀 lane (tid % 2 == 0)":      lambda t: t % 2 == 0,
    "warp 단위로 갈림 ((tid//32)%2)": lambda t: (t // 32) % 2 == 0,
    "데이터 의존 (x[tid] > 0)":       lambda t: data[t] > 0,
    "드문 예외 (x[tid] > 2.5)":       lambda t: data[t] > 2.5,
}
for name, p in cases.items():
    cyc, nw = kernel_cycles(1024, p)
    print(f"total={cyc:4d} cycles ({cyc/nw:4.1f}/warp, {nw} warps) : {name}")
```

```text
total= 320 cycles (10.0/warp, 32 warps) : 모두 같은 경로 (if True)
total= 640 cycles (20.0/warp, 32 warps) : 짝/홀 lane (tid % 2 == 0)
total= 320 cycles (10.0/warp, 32 warps) : warp 단위로 갈림 ((tid//32)%2)
total= 640 cycles (20.0/warp, 32 warps) : 데이터 의존 (x[tid] > 0)
total= 350 cycles (10.9/warp, 32 warps) : 드문 예외 (x[tid] > 2.5)
```

출력에서 볼 것:

- `tid % 2`처럼 **lane 단위로 번갈아** 갈리면 두 배가 된다. 같은 50 % 분할이라도 `(tid // 32) % 2`처럼 **warp 경계에 맞춰** 갈리면 손해가 0이다.
- 데이터 의존 분기(`x > 0`)는 정규분포 데이터에서 거의 모든 warp가 섞이므로 두 배다.
- 드문 예외(`x > 2.5`, 약 0.6 %)는 32개 warp 중 3개만 B 경로를 추가로 탔다(350 = 320 + 3 × 10). 예외 처리 분기는 싸다.

Don의 경험과 연결: DSP에서 샘플마다 `if`를 쓰면 VLIW 슬롯이 깨지니까 `select`/predication으로 바꿨던 것과 같은 문제다. GPU에서는 하드웨어가 자동으로 predication을 해 주지만, **비용은 똑같이 두 경로의 합**이다.

참고: NVIDIA Volta 이후 GPU는 thread마다 별도의 program counter를 두는 "independent thread scheduling"을 도입했다. 이것은 warp 안에서의 동기화·데드락 문제를 풀어 주지만, 갈라진 경로가 **동시에** 실행된다는 뜻은 아니다. 성능 관점의 결론(두 경로의 합)은 그대로다.

ML과 연결: 행렬곱·conv·elementwise는 분기가 거의 없어서 divergence 걱정이 없다. 문제가 되는 곳은 NMS(non-maximum suppression), beam search, top-k, 동적 shape 처리, tokenizer처럼 **데이터 의존 제어 흐름**이 있는 부분이다. 이런 연산은 GPU delegate가 CPU로 되돌려 보내는(fallback) 경우가 많다.

### 1.4 Latency hiding — 기다리는 warp 대신 준비된 warp

GPU의 global memory 접근은 수백 사이클이 걸린다. CPU는 이 지연을 큰 캐시와 out-of-order로 줄이려 한다. GPU는 다른 방법을 쓴다: **SM 안에 warp를 여러 개 상주(resident)시켜 두고, 어떤 warp가 load 결과를 기다리면 다음 사이클에 준비된 다른 warp의 명령을 issue한다.** 레지스터 파일이 warp마다 따로 있으므로 이 전환은 비용이 0이다(CPU의 context switch처럼 레지스터를 저장·복원하지 않는다).

손계산: 필요한 warp 수 추정.

```
한 warp: 계산 c 사이클 → 메모리 대기 L 사이클 → 반복
ALU를 쉬지 않게 하려면, 한 warp가 기다리는 L 사이클 동안 다른 warp들이 계산을 채워야 한다
필요한 warp 수 ≈ 1 + L / c
예) L = 400 사이클, c = 20 사이클  →  1 + 400/20 = 21 warp
```

말로 하면: 메모리가 느릴수록, 그리고 warp 하나가 load 사이에 하는 계산이 적을수록 **더 많은 warp가 동시에 떠 있어야** 한다.

대역폭 관점에서 다시 보면 이것은 Don이 PCIe·NVMe에서 본 **Little's law**다. 메모리 대역폭 100 GB/s, 지연 500 ns라면 "비행 중인 바이트" = 100e9 × 500e-9 = **50 KB**가 항상 걸려 있어야 대역폭을 다 쓴다. warp 하나의 load가 128 B라면 약 400개의 load가 동시에 떠 있어야 한다. NVMe에서 queue depth 1로는 SSD 대역폭을 못 뽑는 것과 정확히 같은 이야기다.

### 1.5 Occupancy — 상주 warp 수를 무엇이 제한하나

**occupancy**(점유율) = SM에 실제로 상주하는 warp 수 ÷ SM이 받을 수 있는 최대 warp 수.

상주 warp 수는 SM의 **자원 중 가장 먼저 바닥나는 것**이 정한다.

- **레지스터**: SM 레지스터 파일(예: 32-bit 레지스터 65,536개)을 thread들이 나눠 쓴다. thread당 레지스터를 많이 쓰는 커널은 동시에 올라갈 수 있는 thread가 줄어든다.
- **shared memory**: block마다 요청한 shared memory의 합이 SM 용량을 넘을 수 없다.
- **warp 슬롯 / block 슬롯**: SM이 추적할 수 있는 warp·block 수의 하드웨어 상한.

손계산 (예시 SM: 레지스터 65,536개, 최대 64 warp):

```
block = 256 thread = 8 warp, thread당 레지스터 64개
block 하나의 레지스터 = 256 × 64 = 16,384
SM에 올라가는 block 수 = 65,536 / 16,384 = 4
상주 warp = 4 × 8 = 32  →  occupancy = 32 / 64 = 50 %
```

**예제 2** — 무엇을 확인하나: 위 계산을 여러 설정으로 돌린다. SM 한도는 설명용으로 NVIDIA A100의 공개 수치(SM당 레지스터 64K개, 최대 64 warp, 최대 32 block, shared memory 최대 164 KB)와 비슷하게 잡았다. 실제 하드웨어는 레지스터를 할당 단위로 반올림하는 등 세부 규칙이 더 있다(NVIDIA의 occupancy calculator가 그것까지 계산한다).

```python
# Occupancy 계산기: SM 하나에 warp가 몇 개 동시에 "상주"할 수 있나 (자원 한도 중 가장 빡빡한 것이 결정)
# SM 한도는 설명용 예시 값 (NVIDIA Ampere A100 SM 공개 수치와 비슷하게 잡음)
SM = dict(max_warps=64, max_blocks=32, regs=65536, smem=164 * 1024)
def occupancy(threads_per_block, regs_per_thread, smem_per_block):
    wpb = -(-threads_per_block // 32)                        # block당 warp 수 (올림)
    lim = {
        "warps": SM["max_warps"] // wpb,
        "blocks": SM["max_blocks"],
        "regs": SM["regs"] // (regs_per_thread * 32 * wpb),  # 실제 HW는 할당 단위로 반올림 — 여기선 생략
        "smem": SM["smem"] // smem_per_block if smem_per_block else 10**9,
    }
    blocks = min(lim.values())
    who = min(lim, key=lim.get)
    warps = blocks * wpb
    return blocks, warps, warps / SM["max_warps"], who
for tpb, r, s in [(256, 32, 0), (256, 64, 0), (256, 128, 0), (256, 32, 48 * 1024), (128, 255, 0), (64, 32, 0)]:
    b, w, occ, who = occupancy(tpb, r, s)
    print(f"threads/blk={tpb:3d} regs/thr={r:3d} smem/blk={s//1024:3d}KB -> blocks={b:2d} warps={w:2d} occupancy={occ:5.1%} (limited by {who})")
```

```text
threads/blk= 64 regs/thr= 32 smem/blk=  0KB -> blocks=32 warps=64 occupancy=100.0% (limited by warps)
```

### 2.2 Coalescing — warp의 주소를 한 덩어리로

warp 32 lane이 동시에 load를 하면, 하드웨어는 32개 주소를 모아 **몇 개의 메모리 transaction으로 합칠지** 계산한다. NVIDIA GPU는 L2/DRAM과 32 B **sector** 단위로, L1은 128 B 라인 단위로 데이터를 옮긴다. lane들의 주소가 연속된 128 B 안에 모여 있으면 sector 4개로 끝난다. 이것이 **coalesced access**(합쳐진 접근)다.

예시 — 컴파일하지 않음 (CUDA C, 이 Mac에는 CUDA가 없다):

```c
// 예시 — 컴파일하지 않음 (CUDA)
// (a) coalesced: 인접 thread가 인접 주소를 읽는다
__global__ void copy_good(const float *in, float *out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = in[i];                 // lane k → in[base + k]: 128 B 한 덩어리
}
// (b) strided: 인접 thread가 stride만큼 떨어진 주소를 읽는다
__global__ void copy_strided(const float *in, float *out, int n, int stride) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = in[(long)i * stride];  // lane마다 다른 sector → transaction 폭증
}
// (c) row-major 행렬에서 "thread 하나가 행 하나"를 맡으면 열 방향으로 stride = 폭
__global__ void row_sum_bad(const float *A, float *s, int rows, int cols) {
    int r = blockIdx.x * blockDim.x + threadIdx.x;   // 같은 순간 lane들은 A[r][j], A[r+1][j] ... → stride = cols
    if (r < rows) { float acc = 0; for (int j = 0; j < cols; j++) acc += A[r * cols + j]; s[r] = acc; }
}
```

(c)는 CPU라면 좋은 코드다(thread 하나가 연속 메모리를 훑는다). 그런데 GPU에서는 **같은 순간에 warp의 32 lane이 읽는 주소들**이 중요하다. 그 순간 lane들은 서로 다른 행의 같은 열 j를 읽으므로 주소가 `cols × 4` 바이트씩 떨어져 있다. 이것이 CPU 직관이 GPU에서 틀리는 대표 사례다.

**예제 3** — 무엇을 확인하나: 여섯 가지 접근 패턴에서 warp 하나(32 lane × float)가 건드리는 32 B sector 수와 효율을 센다.

```python
# Coalescing 계산: warp 32 lane이 float(4 B)를 하나씩 읽을 때 몇 개의 32 B sector를 건드리나
import numpy as np
lane = np.arange(32)
N = 1024                                              # 행렬 폭 (float 1024개 = 4 KB/행)
patterns = {
    "a[tid]            (연속)":        4 * lane,
    "a[tid + 1]        (1칸 어긋남)":   4 * (lane + 1),
    "a[2*tid]          (stride 2)":    4 * (2 * lane),
    "a[32*tid]         (stride 32)":   4 * (32 * lane),
    "A[tid][0] 열 읽기 (stride N)":    4 * (lane * N),
    "a[0]              (모두 같은 주소)": np.zeros(32, int),
}
for name, addr in patterns.items():
    sectors = len(np.unique(addr // 32))              # 32 B sector 단위로 DRAM/L2에서 가져온다고 보자
    lines = len(np.unique(addr // 128))
    useful = 4 * len(np.unique(addr))                 # 실제로 필요한 서로 다른 바이트
    print(f"sectors={sectors:2d} lines={lines:2d} moved={sectors*32:5d} B useful={useful:3d} B eff={useful/(sectors*32):6.1%} : {name}")
```

```text
sectors= 4 lines= 1 moved=  128 B useful=128 B eff=100.0% : a[tid]            (연속)
sectors= 5 lines= 2 moved=  160 B useful=128 B eff= 80.0% : a[tid + 1]        (1칸 어긋남)
sectors= 8 lines= 2 moved=  256 B useful=128 B eff= 50.0% : a[2*tid]          (stride 2)
sectors=32 lines=32 moved= 1024 B useful=128 B eff= 12.5% : a[32*tid]         (stride 32)
sectors=32 lines=32 moved= 1024 B useful=128 B eff= 12.5% : A[tid][0] 열 읽기 (stride N)
sectors= 1 lines= 1 moved=   32 B useful=  4 B eff= 12.5% : a[0]              (모두 같은 주소)
```

출력에서 볼 것:

- 연속 접근은 128 B를 읽으려고 정확히 128 B를 옮긴다(100 %).
- 한 칸만 어긋나도(`tid + 1`, 정렬 안 됨) sector가 하나 더 붙어 80 %가 된다. 그래서 텐서 할당은 보통 큰 정렬(수백 B 이상)로 한다.
- stride 32 이상(열 읽기 포함)은 lane마다 sector 하나씩 32개 — **8배의 트래픽**, 효율 12.5 %.
- 모두 같은 주소(broadcast)는 sector 1개로 끝난다. 효율 숫자는 낮게 나오지만 transaction 하나라 싸다.

Don의 경험과 연결: DMA burst와 똑같다. AXI에서 4 B씩 흩어진 주소로 single transfer를 날리면 bus 효율이 바닥이고, 정렬된 연속 burst로 묶어야 대역폭이 나온다. GPU는 이 "묶기"를 warp 단위로 하드웨어가 자동으로 해 주지만, **묶일 수 있는 주소 패턴을 만드는 것은 프로그래머 몫**이다.

**예제 4** — 무엇을 확인하나: 이 Mac의 GPU에서 같은 64 MiB 결과를 만드는 세 가지 복사를 비교한다. `x.t()`는 전치된 view(stride가 바뀐 텐서)라서 복사 커널이 한쪽(읽기 또는 쓰기)을 strided로 접근해야 한다. `big[:, ::8]`은 32 B 간격으로 float 하나씩 읽는다.

```python
# GPU에서 접근 패턴 비용: 같은 64 MiB를 (a) 연속 복사 (b) 전치 복사 (c) stride 읽기로 — MPS
import torch, time, statistics as st
def ms(fn, reps=21):
    fn(); torch.mps.synchronize()
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); fn(); torch.mps.synchronize(); ts.append((time.perf_counter() - t0) * 1e3)
    return st.median(ts)
n = 4096
x = torch.randn(n, n, device="mps")                     # 64 MiB, row-major
big = torch.randn(n, n * 8, device="mps")                # stride 실험용 512 MiB
out = torch.empty(n, n, device="mps")
cases = {
    "contiguous copy   out.copy_(x)":         lambda: out.copy_(x),
    "transpose copy    out.copy_(x.t())":     lambda: out.copy_(x.t()),
    "stride-8 gather   out.copy_(big[:, ::8])": lambda: out.copy_(big[:, ::8]),
}
for name, f in cases.items():
    t = ms(f)
    print(f"{t:6.2f} ms  {2 * n * n * 4 / t / 1e6:6.1f} GB/s(useful)  {name}")
```

```text
  1.69 ms    79.5 GB/s(useful)  contiguous copy   out.copy_(x)
  3.12 ms    43.1 GB/s(useful)  transpose copy    out.copy_(x.t())
  6.72 ms    20.0 GB/s(useful)  stride-8 gather   out.copy_(big[:, ::8])
```

출력에서 볼 것:

- 연속 복사 약 80 GB/s — M2의 메모리 이론 대역폭 약 100 GB/s(D3 5.1절)에 가깝다.
- 전치 복사는 약 절반. 커널이 타일링으로 어느 정도 완화했을 것으로 보이지만(내부 구현은 확인하지 않았다) 여전히 2배 느리다.
- stride-8 gather는 4배 느리다. 이론상 8배 낭비인데 4배로 끝난 것은 캐시가 인접 행 접근에서 일부를 재사용했기 때문으로 추정한다(확인하지 않음). 요점은 "**레이아웃이 GPU 대역폭을 2~4배 좌우한다**"는 것이다. 모델 변환 시 NCHW/NHWC 선택, 불필요한 transpose/permute 제거가 GPU 성능에 중요한 이유다(C6 그래프 최적화).

### 2.3 Shared memory bank conflict (짧게)

shared memory는 보통 32개 **bank**로 나뉘어 있고, 연속된 4 B 워드가 bank 0, 1, 2 … 31, 0, 1 … 순서로 배치된다. warp의 32 lane이 서로 다른 bank를 건드리면 한 사이클, 같은 bank의 서로 다른 주소를 건드리면 **직렬화**된다. 예: `float tile[32][32]`에서 열 방향으로 읽으면 모든 lane이 같은 bank → 32-way conflict. 흔한 해결책은 `tile[32][33]`처럼 한 칸 padding을 넣어 bank를 어긋나게 하는 것이다. Don이 SRAM bank interleaving으로 동시 접근을 늘렸던 것과 같은 원리다.

### 2.4 Tensor core / matrix unit — GPU 안의 작은 NPU

2017년 NVIDIA Volta부터 SM 안에 **tensor core**가 들어갔다. 일반 ALU lane이 스칼라 FMA(곱셈-누산) 하나를 하는 동안, tensor core는 **작은 행렬곱 한 덩어리**(예: 4×4×4, 세대에 따라 더 큼)를 한 번에 처리한다. 프로그래머는 warp 단위 명령(CUDA의 WMMA API는 16×16×16 fragment, PTX의 `mma` 명령)으로 이를 쓴다.

- 지원 정밀도는 세대마다 늘었다: FP16(Volta) → INT8·INT4(Turing) → BF16·TF32(Ampere) → FP8(Hopper) → FP4(Blackwell) 등. 입력은 저정밀, 누산은 FP32/INT32.
- 데이터시트의 거대한 TOPS 숫자는 대부분 tensor core + INT8(또는 그 이하) + sparsity 조건에서 나온다(M4에서 "숨은 조건"으로 다룸).
- Apple GPU에도 SIMD-group 단위 행렬 명령(Metal의 `simdgroup_matrix`, 8×8)이 있다. Qualcomm·Arm 모바일 GPU도 dot-product·행렬 확장을 넣는 추세로 알려져 있지만 세대별 세부는 벤더 문서로 확인해야 한다.

개념적으로 tensor core는 **GPU 안에 들어간 작은 systolic/MAC array**다. 즉 GPU도 ML용으로 점점 NPU 쪽 요소를 흡수하고 있다. 차이는 GPU가 여전히 범용 SIMT 파이프라인·큰 레지스터 파일·그래픽 기능을 끌고 다닌다는 것이다(→ 면적·전력, 8절).

## 3. 프로그래밍 모델 — CUDA 커널 두 개와 Metal 대응

### 3.1 Vector add — "루프를 thread로 바꾼다"

예시 — 컴파일하지 않음 (CUDA):

```c
// 예시 — 컴파일하지 않음 (CUDA)
__global__ void vec_add(const float *a, const float *b, float *c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // 이 thread의 전역 인덱스
    if (i < n) c[i] = a[i] + b[i];                   // 마지막 block의 남는 thread는 아무것도 안 함
}

void host(const float *h_a, const float *h_b, float *h_c, int n) {
    float *a, *b, *c; size_t bytes = n * sizeof(float);
    cudaMalloc(&a, bytes); cudaMalloc(&b, bytes); cudaMalloc(&c, bytes);
    cudaMemcpy(a, h_a, bytes, cudaMemcpyHostToDevice);    // dGPU: PCIe로 복사
    cudaMemcpy(b, h_b, bytes, cudaMemcpyHostToDevice);
    int block = 256;
    int grid = (n + block - 1) / block;                    // ceil(n / 256)
    vec_add<<<grid, block>>>(a, b, c, n);                  // launch — 비동기! 즉시 리턴
    cudaMemcpy(h_c, c, bytes, cudaMemcpyDeviceToHost);    // 여기서 커널 완료를 기다림 (암묵적 동기화)
    cudaFree(a); cudaFree(b); cudaFree(c);
}
```

읽는 법:

- `__global__`: CPU가 launch하고 GPU에서 도는 함수(커널).
- `blockIdx.x`, `blockDim.x`, `threadIdx.x`: 하드웨어가 thread마다 넣어 주는 내장 변수. `i = blockIdx.x × blockDim.x + threadIdx.x`는 2차원 배열의 row-major 주소 계산(`row × width + col`)과 같은 식이다.
- `<<<grid, block>>>`: launch 설정. n = 1,000,000이면 grid = ceil(1e6/256) = 3907 block, 총 1,000,192 thread. 남는 192개는 `if (i < n)`에서 걸러진다.
- launch는 **비동기**다. CPU는 명령을 큐에 넣고 바로 다음 줄로 간다. 결과를 CPU가 읽는 순간(`cudaMemcpy` D2H) 기다린다. 이 비동기성이 4절 측정의 핵심이다.

**예제 5** — 무엇을 확인하나: 위 커널을 C로 "흉내" 낸다. GPU 하드웨어가 해 주는 일(grid × block 이중 루프)을 명시적으로 쓰면, 커널 본문이 글자 그대로 같다는 것이 보인다. `cc -std=c11 -Wall -Wextra -O2`, 경고 0개.

```c
/* CUDA vecAdd 커널을 C로 "흉내": grid × block 이중 루프가 GPU 하드웨어가 대신 해 주는 일 */
#include <stdio.h>
typedef struct { int x; } dim1;
static void vec_add_kernel(dim1 blockIdx, dim1 blockDim, dim1 threadIdx,
                           const float *a, const float *b, float *c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   /* CUDA 커널 본문과 글자 그대로 같다 */
    if (i < n) c[i] = a[i] + b[i];                   /* 경계 검사: 마지막 block의 남는 thread */
}
int main(void) {
    enum { N = 10 };
    float a[N], b[N], c[N];
    for (int i = 0; i < N; i++) { a[i] = (float)i; b[i] = 100.0f * (float)i; c[i] = -1.0f; }
    dim1 blockDim = { 4 };
    dim1 gridDim = { (N + blockDim.x - 1) / blockDim.x };      /* ceil(10/4) = 3 blocks = 12 threads */
    int launched = 0;
    for (int bx = 0; bx < gridDim.x; bx++)                     /* GPU: block들이 SM에 흩어져 병렬 실행 */
        for (int tx = 0; tx < blockDim.x; tx++, launched++)    /* GPU: 한 block의 thread들이 warp로 묶여 동시 실행 */
            vec_add_kernel((dim1){ bx }, blockDim, (dim1){ tx }, a, b, c, N);
    printf("gridDim=%d blockDim=%d launched=%d threads for N=%d\n", gridDim.x, blockDim.x, launched, N);
    for (int i = 0; i < N; i++) printf("%g%s", c[i], i + 1 < N ? " " : "\n");
    return 0;
}
```

```text
gridDim=3 blockDim=4 launched=12 threads for N=10
0 101 202 303 404 505 606 707 808 909
```

출력에서 볼 것: 10개 원소에 block 4개짜리 thread 3 block = 12 thread를 띄웠고, 넘치는 2개는 경계 검사로 아무 일도 안 했다. GPU에서는 이 이중 루프의 모든 반복이 (자원이 허락하는 만큼) **동시에** 돈다.

### 3.2 Tiled GEMM — shared memory로 재사용을 만든다

순진한 GEMM 커널은 C의 원소 하나당 thread 하나를 두고, 각 thread가 A의 행 K개와 B의 열 K개를 global memory에서 읽는다. C 원소 M·N개가 각각 2K번 읽으므로 global 읽기는 2·M·N·K. 같은 A 원소를 N개 thread가 따로따로 DRAM에서 가져온다 — arithmetic intensity(D3)가 바닥이다.

tiled GEMM은 **block 하나가 C의 T×T 타일을 맡고, K 방향으로 A·B의 T×T 타일을 shared memory에 한 번 올려 block 안의 T² thread가 함께 재사용**한다.

예시 — 컴파일하지 않음 (CUDA):

```c
// 예시 — 컴파일하지 않음 (CUDA). C[M×N] = A[M×K] · B[K×N], row-major, TILE × TILE block
#define TILE 16
__global__ void gemm_tiled(const float *A, const float *B, float *C, int M, int N, int K) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];
    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;              // 이 thread가 맡은 C의 행
    int col = blockIdx.x * TILE + tx;              // 이 thread가 맡은 C의 열
    float acc = 0.0f;                              // 레지스터 누산기
    for (int t0 = 0; t0 < K; t0 += TILE) {
        // 1) 협력 load: thread마다 A 한 원소, B 한 원소 → shared (인접 tx가 인접 열 → coalesced)
        As[ty][tx] = (row < M && t0 + tx < K) ? A[row * K + t0 + tx] : 0.0f;
        Bs[ty][tx] = (t0 + ty < K && col < N) ? B[(t0 + ty) * N + col] : 0.0f;
        __syncthreads();                           // 타일이 다 올라올 때까지 block 전체 대기
        // 2) shared에서 TILE번 MAC — global 접근 없음
        for (int k = 0; k < TILE; k++) acc += As[ty][k] * Bs[k][tx];
        __syncthreads();                           // 다음 타일로 덮어쓰기 전에 모두 다 썼는지 대기
    }
    if (row < M && col < N) C[row * N + col] = acc;
}
// launch: dim3 block(TILE, TILE); dim3 grid((N + TILE - 1) / TILE, (M + TILE - 1) / TILE);
```

읽는 법:

- `__shared__`: block 안의 모든 thread가 보는 on-chip 메모리.
- `__syncthreads()`: block 안의 barrier. 두 번 쓰는 이유 — 첫 번째는 "모두 다 올렸나", 두 번째는 "모두 다 썼나(다음 load가 덮어써도 되나)". 두 번째를 빼먹는 것이 대표적인 race condition 버그다. Don이 ping-pong 버퍼에서 "DMA가 덮어쓰기 전에 CPU가 다 읽었나"를 확인하던 것과 같다.
- 실전 커널(cuBLAS, CUTLASS)은 여기에 더해 thread 하나가 C의 여러 원소(예: 8×8)를 레지스터에 들고(register tiling), 다음 타일을 비동기로 미리 load하고(double buffering — ping-pong!), tensor core를 쓴다.

**예제 6** — 무엇을 확인하나: 위 CUDA 커널의 인덱스 논리를 Python으로 그대로 흉내 내서(블록·thread 루프를 명시), 결과가 `A @ B`와 같은지, global 읽기가 얼마나 줄었는지 센다. 일부러 T로 나누어떨어지지 않는 크기를 써서 경계 처리까지 확인한다.

```python
# CUDA tiled GEMM의 인덱스 논리를 Python으로 "흉내" 내서 정답과 비교 + global 메모리 읽기 횟수 세기
import numpy as np
M, N, K, T = 6, 5, 7, 2                          # 일부러 T로 나누어떨어지지 않는 크기 (경계 처리 확인)
rng = np.random.default_rng(0)
A = rng.integers(-3, 4, (M, K)).astype(np.float32); B = rng.integers(-3, 4, (K, N)).astype(np.float32)
C = np.zeros((M, N), np.float32); gloads = 0
grid = ((N + T - 1) // T, (M + T - 1) // T)      # gridDim.x (열 방향), gridDim.y (행 방향)
for by in range(grid[1]):
    for bx in range(grid[0]):                    # block 하나 = C의 T×T 타일 하나
        acc = np.zeros((T, T), np.float32)       # 각 thread의 레지스터 누산기
        for t0 in range(0, K, T):                # K 방향으로 타일을 하나씩
            As = np.zeros((T, T), np.float32); Bs = np.zeros((T, T), np.float32)   # __shared__
            for ty in range(T):
                for tx in range(T):              # 각 thread가 A 한 원소, B 한 원소를 shared로 복사
                    r, c = by * T + ty, t0 + tx
                    if r < M and c < K: As[ty, tx] = A[r, c]; gloads += 1
                    r, c = t0 + ty, bx * T + tx
                    if r < K and c < N: Bs[ty, tx] = B[r, c]; gloads += 1
            # __syncthreads(); 이후 shared에서 T번 MAC
            for ty in range(T):
                for tx in range(T):
                    acc[ty, tx] += As[ty, :] @ Bs[:, tx]
        for ty in range(T):
            for tx in range(T):
                r, c = by * T + ty, bx * T + tx
                if r < M and c < N: C[r, c] = acc[ty, tx]
print("grid =", grid, " max |C - A@B| =", np.abs(C - A @ B).max())
naive = 2 * M * N * K                            # 타일링 없이: C 원소마다 A 행 K개 + B 열 K개
print(f"global loads: naive={naive}  tiled(T={T})={gloads}  ratio={naive/gloads:.2f}x")
```

```text
grid = (3, 3)  max |C - A@B| = 0.0
global loads: naive=420  tiled(T=2)=231  ratio=1.82x
```

출력에서 볼 것:

- 결과 오차 0 — 경계 처리(`if r < M and c < K`)를 포함한 인덱스 논리가 맞다.
- global 읽기 손계산: tiled = A 원소 M·K개가 N 방향 block 수 ceil(N/T)번 + B 원소 K·N개가 ceil(M/T)번 = 42 × 3 + 35 × 3 = 231. naive = 2 × 6 × 5 × 7 = 420. 크기가 T로 나누어떨어지고 충분히 크면 비율은 정확히 **T배**가 된다. T = 16이면 global 트래픽이 1/16, 즉 arithmetic intensity가 16배 오른다(D3에서 점이 오른쪽으로 이동).

### 3.3 같은 것을 Metal·OpenCL·Vulkan으로 부르면

Apple GPU용 Metal Shading Language(MSL)로 같은 vector add를 쓰면 이런 모양이다(예시 — 컴파일하지 않음).

```c
// 예시 — 컴파일하지 않음 (Metal Shading Language, C++ 기반)
kernel void vec_add(device const float *a [[buffer(0)]],
                    device const float *b [[buffer(1)]],
                    device float *c       [[buffer(2)]],
                    constant uint &n      [[buffer(3)]],
                    uint i [[thread_position_in_grid]]) {   // CUDA의 blockIdx*blockDim+threadIdx
    if (i < n) c[i] = a[i] + b[i];
}
// tiled 버전: threadgroup float As[16][16];  threadgroup_barrier(mem_flags::mem_threadgroup);
```

| CUDA | Metal | OpenCL | Vulkan GLSL compute |
|---|---|---|---|
| `__global__` 함수 | `kernel` 함수 | `__kernel` 함수 | `main()` in compute shader |
| `blockIdx·blockDim + threadIdx` | `thread_position_in_grid` | `get_global_id(0)` | `gl_GlobalInvocationID` |
| `threadIdx` | `thread_position_in_threadgroup` | `get_local_id(0)` | `gl_LocalInvocationID` |
| `__shared__` | `threadgroup` | `__local` | `shared` |
| `__syncthreads()` | `threadgroup_barrier(...)` | `barrier(CLK_LOCAL_MEM_FENCE)` | `barrier()` |
| warp shuffle | `simd_shuffle` 계열 | sub-group 함수 (확장) | subgroup 연산 (확장) |

PyTorch의 `mps` device는 이 Metal 위에서 Apple의 **MPS**(Metal Performance Shaders)·**MPSGraph** 라이브러리와 자체 Metal 커널로 연산을 구현한다. 우리가 `x.to("mps")`라고 쓰면 그 아래에서 Metal command buffer가 만들어지고 GPU 큐에 들어간다.

## 4. 이 Mac에서 재 보기 — MPS vs CPU

이론은 충분하다. 이제 Apple M2(GPU 10코어, CPU P-core 4 + E-core 4, 24 GB unified LPDDR5)에서 직접 잰다.

측정 규칙 (D6의 규칙을 따른다):

- 이 머신에서는 **다른 작업이 동시에 돌고 있었다**(load average 2.5~3.4). 모든 측정은 반복해서 **median**을 쓰고, 같은 스크립트를 두 번 이상 돌려 경향이 같은지 확인했다. 표의 숫자는 첫 실행 값이며, 두 번째 실행과 다른 곳은 본문에 적는다. 소수점이 아니라 **자릿수와 비율**을 읽자.
- GPU는 **비동기**다. `y = x + 1`은 명령을 큐에 넣고 바로 리턴한다. 시간을 재려면 반드시 `torch.mps.synchronize()`로 GPU가 끝날 때까지 기다리거나, 결과를 `.cpu()`/`.item()`으로 읽어서 암묵적으로 기다려야 한다. 이것을 빼먹으면 "GPU가 1000배 빠르다"는 가짜 숫자가 나온다.
- 첫 호출은 Metal 셰이더 컴파일·캐시 때문에 느리다. warm-up을 버린다.

### 4.2 (a) Launch 오버헤드 — 원소 1개 더하기

**예제 8** — 무엇을 확인하나: 계산량이 사실상 0인 연산(원소 1개 + 1)을 CPU와 MPS에서 2000번씩 실행하고, 동기화 방식에 따라 연산당 시간이 어떻게 변하는지 본다.

```python
# 커널 launch 오버헤드: 원소 1개짜리 add를 CPU와 MPS에서. 동기화 방식에 따라 무엇이 보이나
import torch, time, statistics as st
torch.set_num_threads(1)
def us_per_op(fn, n=2000, reps=7):
    fn(n // 10)                                              # warm-up (MPS 커널 컴파일·캐시)
    res = []
    for _ in range(reps):
        t0 = time.perf_counter(); fn(n); res.append((time.perf_counter() - t0) / n * 1e6)
    return st.median(res)
xc = torch.ones(1); xm = xc.to("mps")
def cpu(n):
    for _ in range(n): y = xc + 1.0
def mps_async(n):                                            # 명령만 큐에 넣고, 끝에서 한 번만 기다림
    for _ in range(n): y = xm + 1.0
    torch.mps.synchronize()
def mps_sync_each(n):                                        # 매번 GPU가 끝날 때까지 기다림
    for _ in range(n): y = xm + 1.0; torch.mps.synchronize()
def mps_item(n):                                             # 매번 결과를 CPU로 읽어 옴 (.item() = 동기화 + 복사)
    for _ in range(n): v = (xm + 1.0).item()
for name, f in [("cpu", cpu), ("mps async (sync at end)", mps_async),
                ("mps sync every op", mps_sync_each), ("mps .item() every op", mps_item)]:
    print(f"{name:26s} {us_per_op(f):8.1f} us/op")
```

```text
cpu                             1.5 us/op
mps async (sync at end)         4.8 us/op
mps sync every op             146.3 us/op
mps .item() every op          178.8 us/op
```

출력에서 볼 것 (두 번째 실행: 1.4 / 4.9 / 152.8 / 161.6 µs로 같은 경향):

- **CPU 1.5 µs**: PyTorch의 Python → C++ dispatcher 오버헤드가 거의 전부다. 계산은 나노초.
- **MPS 비동기 4.8 µs**: CPU 쪽에서 GPU 명령을 만들어 큐에 넣는 비용. GPU가 명령을 연달아 처리하므로 "한 번에 몰아서 기다리면" 이 정도로 보인다. 이것이 GPU의 **처리량 관점** 비용이다.
- **MPS 매번 동기화 146 µs**: 명령을 GPU에 제출(commit)하고, GPU가 실행하고, 완료 신호가 CPU로 돌아올 때까지의 **왕복 시간**이다. 이것이 GPU의 **latency 관점** 바닥이다. CPU 대비 약 100배.
- `.item()`은 동기화 + 결과 복사라 조금 더 든다.

말로 하면: GPU는 "명령 하나를 빨리 끝내는" 기계가 아니다. 결과를 바로 기다려야 하는 작은 일은 **최소 수십~수백 µs의 왕복 비용**이 붙는다. batch=1 스트리밍 추론이 정확히 이 모양이다 — 프레임마다 입력을 넣고 결과를 기다린다.

CUDA 쪽 dGPU에서도 kernel launch 비용은 수 µs, 동기화 왕복은 그보다 크다고 알려져 있다. 그래서 NVIDIA는 여러 커널을 미리 녹화해 한 번에 제출하는 **CUDA Graphs**를 제공하고, 컴파일러들은 여러 op를 한 커널로 합치는 **fusion**(C6)을 한다. 둘 다 "launch 횟수를 줄이는" 처방이다.

### 4.3 (a′) 크기를 키우면 — 고정비 구간과 대역폭 구간

**예제 9** — 무엇을 확인하나: elementwise add를 원소 1개부터 16M개까지 키우면서, 연산당 시간이 언제 "고정비"에서 "대역폭 한계"로 바뀌는지 본다. 여기서는 연속 발행 후 한 번 동기화(처리량 관점)로 잰다.

```python
# elementwise add 크기 sweep: 작은 크기는 "고정비"가, 큰 크기는 대역폭이 시간을 정한다 (CPU 1 thread vs MPS)
import torch, time, statistics as st
torch.set_num_threads(1)
def us_per_op(dev, n, reps=7):
    a = torch.randn(n, device=dev); b = torch.randn(n, device=dev); c = torch.empty_like(a)
    iters = max(5, min(2000, int(2e8 / (12 * n))))
    def run():
        for _ in range(iters): torch.add(a, b, out=c)
        if dev == "mps": torch.mps.synchronize()
    run(); ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); run(); ts.append((time.perf_counter() - t0) / iters * 1e6)
    return st.median(ts)
print(f"{'n':>9} {'cpu us':>9} {'mps us':>9} {'cpu GB/s':>9} {'mps GB/s':>9}")
for n in [1, 256, 4096, 65536, 1 << 20, 1 << 22, 1 << 24]:
    c, m = us_per_op("cpu", n), us_per_op("mps", n)
    B = 12 * n                                   # a, b 읽기 + c 쓰기 (float32)
    print(f"{n:9d} {c:9.2f} {m:9.2f} {B/c/1e3:9.2f} {B/m/1e3:9.2f}")
```

### 4.4 (b) 행렬곱 처리량 vs 크기

**예제 10** — 무엇을 확인하나: 정사각 행렬곱 N×N @ N×N을 N = 32 ~ 4096으로 키우며 GFLOP/s를 잰다. CPU는 PyTorch가 Apple Accelerate로 보내는 기본 경로(기본 스레드 수), MPS는 fp32와 fp16.

```python
# 정사각 행렬곱 N×N @ N×N 처리량(GFLOP/s): CPU(Accelerate, 기본 스레드) vs MPS fp32 vs MPS fp16
import torch, time, statistics as st
def gflops(dev, dtype, n, reps=5):
    a = torch.randn(n, n, device=dev, dtype=dtype); b = torch.randn(n, n, device=dev, dtype=dtype)
    iters = max(3, min(2000, int(2e9 / (2 * n**3))))       # 한 측정이 대략 비슷한 연산량이 되게
    def run():
        for _ in range(iters): c = a @ b
        if dev == "mps": torch.mps.synchronize()           # GPU가 실제로 끝날 때까지 기다려야 정확
    run()                                                   # warm-up
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); run(); ts.append(time.perf_counter() - t0)
    return 2 * n**3 * iters / st.median(ts) / 1e9
print(f"{'N':>5} {'cpu fp32':>9} {'mps fp32':>9} {'mps fp16':>9}  (GFLOP/s, median)")
for n in [32, 64, 128, 256, 512, 1024, 2048, 4096]:
    c = gflops("cpu", torch.float32, n)
    m = gflops("mps", torch.float32, n); h = gflops("mps", torch.float16, n)
    print(f"{n:5d} {c:9.1f} {m:9.1f} {h:9.1f}")
```

- 두 번째 실행에서 N=1024 MPS fp32가 1166 GFLOP/s로 나왔다(첫 실행 1817). 교차점 부근은 노이즈에 민감하다 — 그래서 median과 반복이 필요하다.

roofline(D3)으로 보면: GPU의 ridge point ≈ 3.6 TFLOP/s ÷ 100 GB/s ≈ 36 FLOP/B. N×N 행렬곱의 intensity ≈ 2N³ / (3 × 4N²) = N/6 FLOP/B이므로 N ≈ 216부터 이론상 compute-bound다. 그런데 실측은 N=1024까지 천장에 못 미친다. **roofline이 모르는 세 번째 천장 — launch/동기화 고정비와 SM을 다 채우지 못하는 작은 grid —** 가 작은 크기를 지배하기 때문이다. 작은 N에서는 thread block 수가 GPU의 코어 수보다 적어서 일부 코어는 아예 논다(5.1절).

### 4.5 (c) batch=1 작은 모델 — 작은 MLP

**예제 11** — 무엇을 확인하나: 키워드 스포팅(KWS)급 크기의 MLP(입력 490 = 49 프레임 × 10 MFCC, 은닉 256 × 2, 출력 12 클래스, 파라미터 약 19.5만)를 "입력은 CPU 메모리에서 오고 결과는 CPU가 쓴다"는 현실적인 조건으로 호출당 잰다.

```python
# 작은 MLP(KWS 크기급) 추론: 입력 CPU → (MPS면 복사) → forward → 결과를 CPU로. 호출당 latency, batch별
import torch, time, copy, statistics as st
torch.manual_seed(0)
net = torch.nn.Sequential(torch.nn.Linear(490, 256), torch.nn.ReLU(),
                          torch.nn.Linear(256, 256), torch.nn.ReLU(), torch.nn.Linear(256, 12)).eval()
print("params:", sum(p.numel() for p in net.parameters()), "| cpu threads:", torch.get_num_threads())
nets = {"cpu": net, "mps": copy.deepcopy(net).to("mps")}   # 같은 가중치의 MPS 사본
def lat_us(dev, bs, n=300, reps=5):
    x = torch.randn(bs, 490)                                  # 센서/feature 버퍼는 CPU 메모리에서 온다
    def once():
        with torch.inference_mode():
            return nets[dev](x.to(dev)).cpu()                 # 결과를 CPU가 써야 끝 (→ MPS는 동기화 포함)
    for _ in range(30): once()
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter()
        for _ in range(n): once()
        ts.append((time.perf_counter() - t0) / n * 1e6)
    return st.median(ts)
print(f"{'batch':>5} {'cpu us/call':>12} {'mps us/call':>12} {'cpu us/sample':>14} {'mps us/sample':>14}")
for bs in [1, 8, 64, 512, 4096]:
    c, m = lat_us("cpu", bs), lat_us("mps", bs)
    print(f"{bs:5d} {c:12.1f} {m:12.1f} {c/bs:14.2f} {m/bs:14.2f}")
```

### 4.6 (c′) MobileNetV2 batch=1 — 해상도에 따른 교차점

**예제 12** — 무엇을 확인하나: MobileNetV2(`weights=None`, 무작위 가중치 — 속도에는 영향 없다)를 batch=1로, 입력 해상도 32 ~ 320 px에서 CPU 1 thread, CPU 4 threads, MPS로 잰다. MMAC 열은 논문의 224 px 약 300 MMAC를 해상도²로 비례시킨 근사다.

```python
# MobileNetV2 batch=1: 입력 해상도별 latency — CPU 1 thread, CPU 4 threads, MPS. 교차점은 어디인가
import torch, torchvision, time, copy, statistics as st
torch.manual_seed(0)
cpu_net = torchvision.models.mobilenet_v2(weights=None).eval()
mps_net = copy.deepcopy(cpu_net).to("mps")
def ms(dev, res, threads=1, reps=15):
    torch.set_num_threads(threads)
    net = cpu_net if dev == "cpu" else mps_net
    x = torch.randn(1, 3, res, res)
    def once():
        with torch.inference_mode():
            return net(x.to(dev)).cpu()
    for _ in range(5): once()
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); once(); ts.append((time.perf_counter() - t0) * 1e3)
    return st.median(ts)
print(f"{'res':>4} {'MMAC':>5} {'cpu1 ms':>8} {'cpu4 ms':>8} {'mps ms':>7}  best")
for res in [32, 64, 96, 128, 160, 224, 320]:
    mmac = 300 * (res / 224) ** 2          # MobileNetV2 1.0 @224 ≈ 300 MMAC(논문 값), 해상도² 비례 근사
    c1, c4, m = ms("cpu", res, 1), ms("cpu", res, 4), ms("mps", res)
    best = min([("cpu1", c1), ("cpu4", c4), ("mps", m)], key=lambda t: t[1])[0]
    print(f"{res:4d} {mmac:5.0f} {c1:8.2f} {c4:8.2f} {m:7.2f}  {best}")
```

출력에서 볼 것:

- **MPS 곡선이 평평하다(6.1 ~ 7.3 ms).** 계산량이 100배(6 → 612 MMAC) 늘어도 시간이 거의 그대로다. 즉 이 모델의 GPU 시간은 **계산이 아니라 op 개수 × op당 고정비**다. MobileNetV2는 eager 모드에서 conv·BN·ReLU6·add 등 op가 150개 안팎이다. 6.5 ms ÷ 150 ≈ 40 µs/op 정도의 고정비로 해석된다(op 수는 대략치, 확인하지 않음).
- 320 px에서 MPS의 실효 처리량은 612 MMAC × 2 ÷ 6.63 ms ≈ 185 GFLOP/s — 약 3.6 TFLOPS peak의 **5 %**다. 5 %만 써도 CPU를 이긴다는 것이 GPU의 힘이자, 95 %를 놀린다는 것이 batch=1의 한계다.
- **CPU 1 thread가 작은 해상도에서 이긴다**(32 px 3.5 ms vs 6.1 ms). 교차점은 96 ~ 128 px.
- **CPU 4 threads가 1 thread보다 훨씬 느리다**(32 px에서 18.8 vs 3.5 ms). PyTorch profiler로 보면 이 CPU 경로에서 depthwise conv가 그룹별로 쪼개진 `_slow_conv2d_forward` 호출 1000여 개로 실행되었다. 작은 조각마다 스레드를 깨우고 동기화하는 비용이, 다른 작업이 돌고 있는 기계에서 크게 부풀었다. **스레드를 늘리면 빨라진다는 가정도 재 봐야 한다**(D6의 교훈과 같다). 공정한 CPU 기준선은 이 경우 1 thread다.
- PyTorch eager CPU는 모바일 런타임(XNNPACK, TFLite, ONNX Runtime)보다 depthwise에 느린 경로를 탄다. 그러므로 이 숫자는 "M2 CPU의 한계"가 아니라 "이 소프트웨어 스택에서의 교차점"이다. 실리콘 평가에서는 **타깃 런타임으로** 재야 한다(M2 벤치 방법론).

그림 11 — MobileNetV2 @96 px 처리량 vs batch(로그-로그, 실측). MPS는 batch 8까지 latency가 거의 그대로라 처리량이 batch에 비례해 늘고, 16 이후 포화된다. CPU는 batch 16에서 절벽을 만난다.

출력에서 볼 것:

- **batch 1: CPU 승(5.4 vs 6.2 ms). batch 2부터 MPS 승.** 교차점이 batch 1~2다.
- MPS는 batch 1 → 8에서 latency가 6.2 → 6.6 ms로 거의 안 변한다. 고정비 구간이라 **batch를 8배 늘려도 공짜**다. 처리량이 160 → 1209 img/s로 7.6배. batch 16 이후 latency가 batch에 비례하기 시작하면 GPU가 비로소 "일로 꽉 찬" 상태다(약 2,200 img/s에서 포화).
- CPU batch 16에서 25.5 → 396 ms로 **15배 절벽**이 두 번의 실행 모두에서 재현되었다. PyTorch CPU conv가 크기에 따라 다른 구현 경로를 고르는 것으로 보이며, 원인은 확인하지 않았다. 교훈은 같다: 런타임의 구현 경로 전환이 하드웨어 차이보다 클 수 있다.

말로 하면: GPU는 **batch가 있어야** 고정비를 나눠 낸다. 서버는 여러 사용자의 요청을 모아 batch를 만들 수 있다. 웨어러블의 always-on 센서는 한 사용자의 한 스트림이다 — 모을 요청이 없다. 여러 프레임을 모으면 batch가 생기지만 그만큼 **지연이 늘어난다**(D6 9절 batching).

### 4.8 (d) 데이터 전송과 동기화 — unified memory인데도?

**예제 14** — 무엇을 확인하나: CPU 텐서를 MPS로(H2D), MPS 텐서를 CPU로(D2H) 복사하는 시간을 4 B ~ 256 MiB에서 잰다. 비교용으로 GPU 안에서의 복사(D2D)도 잰다. 모두 동기화 포함.

```python
# CPU↔MPS 복사 비용: 크기별 시간과 실효 대역폭 (unified memory여도 복사는 복사다)
import torch, time, statistics as st
def med_us(fn, reps=21):
    fn(); fn()
    ts = []
    for _ in range(reps):
        t0 = time.perf_counter(); fn(); ts.append((time.perf_counter() - t0) * 1e6)
    return st.median(ts)
print(f"{'size':>8} {'H2D us':>9} {'D2H us':>9} {'H2D GB/s':>9} {'D2H GB/s':>9} {'on-GPU copy GB/s':>17}")
for nbytes in [4, 4 << 10, 64 << 10, 1 << 20, 16 << 20, 256 << 20]:
    n = max(1, nbytes // 4)
    h = torch.randn(n); d = h.to("mps"); d2 = torch.empty_like(d)
    def h2d(): h.to("mps"); torch.mps.synchronize()           # 동기화를 포함해야 "정말 도착한" 시간
    def d2h(): d.cpu()                                         # .cpu()는 스스로 기다린다
    def d2d(): d2.copy_(d); torch.mps.synchronize()            # GPU 안에서 복사 (읽기+쓰기)
    a, b, c = med_us(h2d), med_us(d2h), med_us(d2d)
    label = f"{nbytes/2**20:.0f} MiB" if nbytes >= 1 << 20 else (f"{nbytes>>10} KiB" if nbytes >= 1024 else f"{nbytes} B")
    print(f"{label:>8} {a:9.1f} {b:9.1f} {nbytes/a/1e3:9.2f} {nbytes/b/1e3:9.2f} {2*nbytes/c/1e3:17.2f}")
```

- 그래도 dGPU보다는 낫다: PCIe 너머 dGPU에서는 전송 대역폭이 PCIe 링크로 제한되고, 작은 전송의 왕복 지연도 붙는다. Apple silicon, Qualcomm, Arm 모바일 SoC 같은 unified memory 시스템에서는 드라이버가 **zero-copy**(CPU와 GPU가 같은 버퍼를 매핑)를 지원하는 경우가 많다. 런타임이 그것을 쓰도록 버퍼를 할당하면(예: 카메라 버퍼를 GPU가 바로 읽는 경로) 복사는 사라진다. 하지만 **동기화(누가 언제 다 썼나)는 사라지지 않는다.** 캐시 일관성(cache coherence)과 fence 비용은 E7에서 다룬다.

Don의 경험과 연결: DMA 전송 비용 = "설정 + 완료 인터럽트 왕복" 고정비 + 바이트 ÷ 대역폭. 작은 전송은 고정비가 지배해서 CPU `memcpy`가 이기고, 큰 전송만 DMA가 이긴다. GPU offload도 정확히 같은 곡선이다.

## 5. 왜 GPU는 batch=1 always-on 추론에 불리한가

4절의 측정과 이론을 한 곳에 모은다.

### 5.1 네 가지 이유

1. **Launch·동기화 고정비.** 스트리밍 추론은 프레임마다 "넣고 → 기다리고 → 결과를 CPU가 읽는다". 매 프레임 동기화 왕복(이 Mac에서 약 150 µs)과 op당 발행 비용이 붙는다. 모델이 작을수록 이 고정비가 전체를 지배한다(4.5절: 계산 수 µs, 총 508 µs).
2. **낮은 활용률.** GPU는 수천 개 thread가 떠 있어야 지연을 숨긴다(1.4절). KWS 모델의 레이어 하나는 출력이 수십~수백 원소라 block 몇 개로 끝나고, SM 대부분이 논다. 4.6절에서 큰 입력조차 peak의 5 %였다.
3. **전력.** GPU는 큰 레지스터 파일, 스케줄러, 캐시, 넓은 버스를 켜야 일을 시작한다. 활용률이 낮으면 **켜 둔 비용(정적 전력 + 클럭 트리) ÷ 적은 일 = 연산당 에너지가 나쁘다.** D7의 "race-to-idle" 관점에서 GPU가 빨리 끝내고 꺼지면 좋겠지만, 10 ms마다 깨우는 스트리밍에서는 꺼질 틈이 짧다.
4. **Idle 전력과 wake 지연.** 모바일 GPU는 쓰지 않을 때 power gating으로 레일을 끈다. 다시 켜려면 전원 레일 안정화, 클럭 켜기, 드라이버·펌웨어 상태 복구가 필요하고, 이 지연과 에너지는 SoC마다 다르며 공개되지 않는 경우가 많다(벤더에게 물어야 할 항목). always-on 워크로드를 GPU에 두면 "계속 켜 두기"와 "매번 깨우기" 사이에서 둘 다 비싸다.

### 5.2 손계산 — always-on KWS를 어디에 둘까 (가정 숫자)

아래 숫자는 **설명용 가정**이다. 실제 값은 SoC별로 측정해야 한다(D7 8절, K3).

```
워크로드: 10 ms hop마다 KWS 추론 1회, 모델 0.2 MMAC

(1) MCU + 소형 NPU (Ethos-U급) 가정: 추론 0.3 ms, 활성 5 mW
    에너지/추론 = 5 mW × 0.3 ms = 1.5 µJ
    평균 전력  = 1.5 µJ / 10 ms = 0.15 mW (+ 대기 전력)

(2) 모바일 GPU 가정: 추론(발행+동기화 포함) 0.5 ms, 활성 500 mW,
    hop 사이에 GPU를 끌 수 없어 idle 50 mW 유지
    에너지/추론 = 500 mW × 0.5 ms = 250 µJ
    평균 전력  = 250 µJ / 10 ms + 50 mW × (9.5/10) ≈ 25 + 47.5 ≈ 72 mW
```

말로 하면: 가정이 다소 틀려도 **자릿수가 두세 개 차이** 난다. 게다가 GPU를 쓰려면 AP(애플리케이션 프로세서)와 DRAM도 깨어 있어야 하므로 실제 시스템 전력 차이는 더 크다. 웨어러블 배터리가 수백 mWh라면 72 mW 상시 부하는 몇 시간 만에 배터리를 비운다(D7 6절의 배터리 수학). 그래서 always-on은 MCU/DSP/소형 NPU의 몫이다(E4, E5, E8).

### 5.3 그럼 GPU는 어디서 빛나나

| 워크로드 | 왜 GPU에 맞나 | 주의 |
|---|---|---|
| 고해상도 비전 (224 px 이상, 세그멘테이션, 깊이 추정) | op당 일이 커서 고정비가 묻힌다 (4.6절 320 px에서 4배) | NPU가 지원하면 NPU가 전력 효율 우위일 가능성 큼 |
| batch 처리 (사진 갤러리 인덱싱, 오프라인 처리) | batch로 고정비를 나눈다 (4.7절) | 지연 허용 가능한 작업만 |
| LLM prefill | 프롬프트 토큰 수백 개 = 큰 GEMM, compute-bound (D5) | NPU도 강함, 정밀도·op 지원이 관건 |
| LLM decode | 가중치를 매 토큰 읽는 GEMV, memory-bound (D5) | GPU·NPU·CPU 모두 **같은 LPDDR 대역폭 천장** — GPU라서 빨라지지 않는다 |
| 이미지 생성 (diffusion) | 큰 conv/attention을 수십 step 반복 | 발열·지속 성능(K4) |
| 새 연산·동적 shape·연구 모델 | 커널을 직접 쓸 수 있는 범용성 | NPU는 op 미지원 시 CPU fallback |
| 그래픽과 함께 (AR 오버레이, 카메라 효과) | 데이터가 이미 GPU에 있음 — 복사 없음 | 렌더링과 자원 경쟁 |

LLM decode에 대한 한 줄: 토큰 하나를 만들 때 모든 가중치를 한 번 읽어야 하므로 tokens/s 상한 ≈ 대역폭 ÷ 모델 바이트(D5). 1 GB 모델, LPDDR5X 60 GB/s라면 상한 약 60 tok/s — CPU로 읽든 GPU로 읽든 NPU로 읽든 같은 DRAM이다. 가속기의 차이는 이 상한에 **얼마나 가까이** 가느냐와 **그때의 전력**에서 난다.

## 6. 모바일 GPU와 edge GPU 지형

아래는 널리 알려진 사실 위주로 정리했다. 세대별 세부 사양은 바뀌므로 실제 선정 시 벤더 문서로 확인한다.

### 6.1 벤더와 API

| GPU | 들어 있는 곳 | 주요 compute API | ML에서 쓰는 경로 (예) |
|---|---|---|---|
| Qualcomm **Adreno** | Snapdragon 모바일·XR·일부 웨어러블 SoC | OpenCL, Vulkan, OpenGL ES | TFLite(LiteRT) GPU delegate, Qualcomm AI Engine Direct(QNN)의 GPU backend, llama.cpp OpenCL backend(Adreno 최적화 경로가 추가된 것으로 알려짐) |
| Arm **Mali** / **Immortalis** | MediaTek Dimensity, Samsung Exynos 일부, Google Tensor(G1~G4) 등 | OpenCL, Vulkan, OpenGL ES | TFLite GPU delegate, Arm Compute Library, llama.cpp Vulkan |
| **Apple GPU** | iPhone·iPad(A 시리즈), Mac(M 시리즈) | Metal | Core ML(GPU/ANE/CPU 자동 배분), MPS·MPSGraph, PyTorch `mps`, llama.cpp Metal, MLX |
| **Imagination** (PowerVR, IMG) | 일부 MediaTek·Unisoc 등 SoC | OpenCL, Vulkan, OpenGL ES | TFLite GPU delegate 등 |
| NVIDIA **Jetson** (Orin 등) | 로보틱스·edge 모듈 | CUDA (+ Vulkan, OpenGL) | TensorRT, cuDNN, PyTorch CUDA |

- Immortalis는 Arm이 하드웨어 ray tracing을 넣은 상위 Mali 라인에 붙인 이름이다(예: Immortalis-G715, G720).
- **OpenCL**은 Android에서 공식 API가 아니지만(구글이 Android 필수 API로 지정하지 않음) Qualcomm·Arm 등 주요 벤더 드라이버가 제공한다. **Vulkan**은 Android 공식 API이며 compute shader를 지원한다. **OpenGL ES 3.1 compute shader**는 구형 경로다.
- **TFLite GPU delegate**(현재 Google은 TFLite를 LiteRT로 이름을 바꿨다)는 Android에서 OpenCL을 우선 쓰고 안 되면 OpenGL ES로, iOS에서는 Metal로 동작한다. fp16 연산을 주로 쓰고, 지원하지 않는 op는 CPU로 넘긴다.
- **llama.cpp**(ggml)는 CPU 외에 Metal, CUDA, Vulkan, OpenCL, SYCL 등 여러 backend를 가진다. 모바일에서는 CPU(NEON·i8mm·dotprod 커널)가 여전히 기본이고, GPU backend는 기기·모델에 따라 빠를 수도 느릴 수도 있다 — 직접 재야 한다(F 모듈).
- **ExecuTorch**(PyTorch의 온디바이스 런타임)는 XNNPACK(CPU), Vulkan(GPU), Core ML·MPS(Apple), Qualcomm QNN, Arm Ethos-U, MediaTek 등 여러 backend(delegate)를 제공한다. backend별 성숙도는 차이가 크다.
- 이 밖에 MLC LLM(Apache TVM 기반, Vulkan/OpenCL/Metal), Google MediaPipe LLM Inference API(Android GPU) 등도 모바일 GPU로 LLM을 돌린다.

### 6.2 Jetson Orin — 로보틱스 edge의 기준점

Jetson Orin 계열은 "edge에서 CUDA를 그대로 쓸 수 있는" 레퍼런스다. 널리 공개된 사실만 적는다(모델별 수치는 NVIDIA 데이터시트로 확인).

- **GPU**: NVIDIA Ampere 아키텍처 — CUDA core + **tensor core**. 상위 AGX Orin 64GB는 CUDA core 2048개, tensor core 64개.
- **DLA**(Deep Learning Accelerator): 고정 기능 CNN 가속기. AGX Orin·Orin NX에 들어 있고 Orin Nano에는 없다. TensorRT로 레이어를 GPU와 DLA에 나눠 배치한다 — **한 칩 안에서 GPU와 NPU를 같이 쓰는 구조**의 교과서적 예다.
- **메모리**: CPU·GPU·DLA가 LPDDR5를 공유(unified). AGX Orin 64GB는 204.8 GB/s.
- **성능·전력**: AGX Orin 최대 275 TOPS(INT8, sparsity 포함 조건), 전력 모드 15~60 W. Orin Nano는 7~15 W급(이후 소프트웨어 업데이트로 더 높은 전력 모드가 추가됨).
- **소프트웨어**: JetPack(Linux + CUDA + cuDNN + TensorRT). 서버에서 쓰던 CUDA 코드·PyTorch가 그대로 돈다는 것이 가장 큰 장점이다.

웨어러블에서 보면 Orin은 **전력이 두세 자릿수 크다**(W 단위). Hark 같은 기기의 on-body 부분에는 맞지 않지만, 로봇·드론·스마트 카메라, 또는 웨어러블과 짝을 이루는 edge 허브·개발용 기준점으로는 자주 등장한다.

### 6.3 모바일 GPU를 ML에 쓸 때 현실적인 제약

- **정밀도**: 모바일 GPU ML 경로는 fp16이 기본이다. INT8 가속은 세대·드라이버에 따라 다르고, INT4 가중치는 보통 fp16으로 풀어서(dequant) 곱한다. NPU의 INT8/INT4 네이티브 경로보다 에너지 효율이 떨어지는 이유 중 하나다.
- **드라이버 품질·파편화**: 같은 OpenCL 커널이 기기·드라이버 버전에 따라 성능·정확도가 달라진다. Don에게 익숙한 "벤더 BSP 버전마다 다른 버그"의 GPU판이다.
- **열·지속 성능**: 휴대폰 GPU는 게임에서도 수 분 뒤 throttling된다(K4, E9). 짧은 burst(prefill 1초)는 괜찮아도 지속 부하는 벤치마크 숫자보다 느리다.
- **자원 공유**: UI 렌더링과 GPU를 나눠 쓴다. ML이 GPU를 오래 점유하면 화면이 끊긴다. 웨어러블의 디스플레이가 작아도 compositor는 GPU를 쓴다.

## 7. GPU vs NPU vs DSP — Hark 같은 워크로드에서 무엇을 고르나

아래 표는 일반적인 경향에 기반한 **추정 판단**이다. 실제 선택은 타깃 SoC에서 대표 모델을 재서(M2) 결정한다. "Hark 같은 웨어러블이라면"을 가정한다(Qualcomm SoC + always-on MCU 추정).

| 워크로드 | 성격 | 1순위 (추정) | GPU가 맞는 경우 | 근거 |
|---|---|---|---|---|
| always-on wake word / VAD | 10~20 ms hop, 수십만 MAC, 상시 | MCU(+ 소형 NPU) 또는 저전력 DSP 섬 | 거의 없음 | 4.5절 17배 느림 + 5.2절 전력 자릿수 차이 |
| 스트리밍 ASR 인코더 | 프레임 연속, 중간 크기, 사용자 발화 중에만 | DSP(HVX) 또는 NPU | NPU가 op를 지원 못 할 때 임시 경로 | 지연 예산 + 전력 (D6) |
| IMU 제스처 / 착용 감지 | 아주 작은 모델, 상시 | MCU / sensor hub | 없음 | 모델이 작아 고정비가 전부 |
| 카메라 저전력 감지 (저해상도) | 96 px 급, 간헐 | NPU 또는 ISP 옆 전용 블록 | batch가 생기는 오프라인 처리 | 4.6·4.7절 교차점 아래 |
| 카메라 고해상도 비전 | 224 px 이상, 사용자 요청 시 | NPU | NPU 미지원 op, 그래픽 파이프라인과 결합 | 4.6절 GPU도 유효, 전력은 NPU 유리 추정 |
| SLM prefill | 수백 토큰, compute-bound, 짧은 burst | NPU (INT8/INT4 경로가 있으면) | NPU SDK가 모델·길이를 지원 못 할 때, fp16 필요 시 | D5, 5.3절 |
| SLM decode | 토큰당 가중치 전체 읽기, memory-bound | 대역폭·전력 효율이 좋은 쪽 (NPU 또는 CPU) | 런타임 성숙도가 GPU 쪽이 좋을 때 | 모두 같은 LPDDR 천장 (D5) |
| 이미지 생성·오프라인 대형 작업 | 큰 연산, 지연 허용 | GPU 또는 NPU | 기본 후보 | 범용성·fp16 |

"When would you run an SLM on the phone GPU vs NPU?"에 대한 요지:

- **NPU를 먼저 본다.** 같은 일에 전력 효율이 좋고, INT8/INT4 네이티브 경로가 있다. Qualcomm은 Hexagon NPU용 도구(QNN/AI Engine Direct, Genie 등)로 LLM 실행을 지원한다고 밝히고 있다.
- **GPU를 고르는 조건**: NPU 컴파일러가 모델 구조(새 attention 변형, 동적 shape, 긴 context)를 지원하지 못할 때, fp16 정확도가 필요할 때, 개발 속도가 중요할 때(llama.cpp·MLC 같은 오픈 스택이 GPU backend로 바로 돈다), 또는 NPU가 다른 기능(카메라·오디오)에 점유되어 있을 때.
- **decode 속도는 GPU로 옮긴다고 오르지 않는다** — 대역폭이 같다. 차이는 prefill 속도(TTFT)와 전력·발열에서 난다.

## 8. 임베디드 관점에서 다시 보기

Don의 펌웨어 경험으로 GPU 개념을 다시 번역한다.

| GPU 개념 | 펌웨어·SoC에서 대응하는 것 |
|---|---|
| warp 전환으로 지연 숨기기 | NVMe queue depth / 여러 NAND die에 명령 걸어 두기 |
| occupancy (자원이 상주 수를 제한) | 명령 슬롯·태그 수가 outstanding 요청 수를 제한 |
| coalescing | AXI burst, 캐시 라인 정렬, DMA descriptor 병합 |
| shared memory + `__syncthreads` | TCM + DMA ping-pong + 완료 플래그/barrier |
| bank conflict | SRAM bank interleaving, 같은 bank 동시 접근 stall |
| kernel launch + 동기화 왕복 | 코프로세서에 mailbox로 명령 보내고 완료 인터럽트 기다리기 (IPC 왕복) |
| CUDA Graphs / fusion | descriptor chain 한 번에 제출, 인터럽트 coalescing |
| divergence | DSP에서 분기 대신 predication/select |
| power gating + wake 지연 | 도메인 power-up 시퀀스, retention, 레일 안정화 시간 |

그리고 실리콘 평가에서 GPU에 대해 벤더에게 물을 질문 (M1, M4):

- 우리 대표 모델(batch=1, 해당 해상도·길이)에서 GPU·NPU·CPU **각각의 latency와 전력**. 피크 TFLOPS가 아니라.
- GPU를 idle에서 깨우는 데 걸리는 시간과 에너지, 그리고 idle 시 GPU 레일 전력.
- 지원하는 ML 런타임과 버전: TFLite GPU delegate, Vulkan/OpenCL 드라이버 버전, llama.cpp·ExecuTorch backend 상태. 드라이버 업데이트 정책.
- fp16/INT8 연산률(데이터시트가 fp32의 2배라고 쓰는지, 실측과 맞는지 — 4.4절에서 fp16이 1.1배였다).
- 메모리 대역폭을 GPU·NPU·CPU·ISP·디스플레이가 동시에 쓸 때 QoS와 실효 대역폭(E7).
- zero-copy 경로(카메라 → GPU/NPU)와 캐시 일관성 처리 방식.

MCU 쪽에서 보면 결론은 간단하다. **always-on 경로에는 GPU가 없다.** GPU는 AP가 깨어 있을 때만 쓰는 "burst 가속기"다. 시스템 설계는 E8(이기종 SoC)에서 MCU ↔ DSP ↔ NPU ↔ AP(+GPU) 역할 분담으로 다룬다.

## 10. 면접에서 이렇게 말한다

**Q.** "What is a warp, and what is divergence?"

**A.** warp는 GPU가 한 명령으로 동시에 실행하는 thread 묶음이다 — NVIDIA는 32개. 같은 warp의 thread들이 분기에서 다른 쪽으로 가면 하드웨어가 두 경로를 순서대로 실행하면서 해당하지 않는 lane을 mask로 끈다. 그래서 비용은 두 경로의 합이다. warp 경계에 맞춰 갈리면 손해가 없고, 드문 예외 분기는 싸다. ML에서는 GEMM·conv는 분기가 없어 괜찮고 NMS·top-k 같은 데이터 의존 연산이 문제다.

> A warp is the group of threads the GPU issues together with a single instruction — 32 on NVIDIA, and other vendors have similar concepts like AMD wavefronts or Apple SIMD-groups. If threads in the same warp take different sides of a branch, the hardware runs both paths one after the other and masks off the inactive lanes, so you pay for the sum of both paths. Divergence only matters within a warp; if the branch splits along warp boundaries, there's no penalty. For ML, GEMMs and convolutions are branch-free, so divergence mostly shows up in data-dependent ops like NMS, top-k or beam search.

**Q.** "Why is a GPU slow for batch-1 tiny models?"

**A.** GPU는 수천 개 thread로 지연을 숨기는 throughput 기계라서, 작은 모델은 GPU를 채우지 못하고 고정비만 낸다. 내가 M2에서 재 보니 결과를 기다리는 동기화 왕복만 약 150 µs였고, 20만 MAC짜리 MLP는 CPU 30 µs, GPU 500 µs였다. 거기에 GPU를 켜 두는 전력까지 생각하면 always-on 경로는 MCU나 DSP, 소형 NPU가 맞다. GPU는 batch가 있거나 입력이 클 때 이긴다 — MobileNetV2는 96~128 px에서 교차했다.

> Because a GPU is a throughput machine — it hides latency by having thousands of threads in flight — and a batch-one tiny model can't fill it, so you mostly pay fixed costs. On an M2 I measured about 150 microseconds just for the submit-and-wait round trip, and a 200-thousand-MAC MLP took 30 microseconds on the CPU versus about 500 on the GPU. Add the power of keeping the GPU awake and it's clearly the wrong place for an always-on model; that belongs on an MCU, DSP or small NPU. The GPU wins once there's batch or the input is large — for MobileNetV2 the crossover was around 96 to 128 pixels at batch one.

**Q.** "What is occupancy, and is higher always better?"

**A.** occupancy는 SM에 상주하는 warp 수를 최대치로 나눈 값이다. 레지스터, shared memory, warp·block 슬롯 중 가장 먼저 바닥나는 자원이 정한다 — 예를 들어 256 thread block에서 thread당 레지스터를 64개 쓰면 50 %다. 상주 warp가 많을수록 메모리 지연을 숨길 여유가 크지만, 항상 좋은 것은 아니다. 잘 만든 GEMM은 레지스터 타일링으로 재사용을 늘리려고 일부러 occupancy를 낮춘다. 판단은 실측 처리량과 roofline으로 한다.

> Occupancy is the number of warps resident on an SM divided by the maximum it supports. It's set by whichever resource runs out first — registers per thread, shared memory per block, or the warp and block slots. For example, 256-thread blocks using 64 registers per thread give 50 percent on an SM with 64K registers. More resident warps means more ability to hide memory latency, but it's not a goal in itself; good GEMM kernels deliberately use lots of registers for register tiling and accept lower occupancy. I judge by achieved throughput against the roofline, not by occupancy.

**Q.** "What does coalesced memory access mean?"

**A.** warp의 32 lane이 동시에 load할 때 주소들이 연속된 한 덩어리면 하드웨어가 소수의 transaction(32 B sector 4개 = 128 B)으로 합친다. 주소가 흩어지면 lane마다 sector 하나씩, 8배의 트래픽이 된다. CPU에서 좋은 "thread 하나가 행 하나를 훑는" 코드가 GPU에서는 열 방향 stride라 나쁘다. 인접 thread가 인접 주소를 읽게 인덱싱하거나 shared memory를 거쳐 전치한다. 이 Mac에서 같은 64 MiB 복사가 연속이면 80 GB/s, stride면 20 GB/s였다.

> It means the addresses the 32 lanes of a warp access at the same time fall into one contiguous, aligned chunk, so the hardware merges them into a few transactions — four 32-byte sectors for 32 floats. If each lane hits a different sector, you move eight times more data than you use. The classic trap is CPU-style code where each thread walks its own row; at any instant the warp is reading a column, which is strided. The fix is to index so adjacent threads touch adjacent addresses, or stage through shared memory. It's the same idea as aligning DMA bursts on a bus. On my M2 the same copy ran at 80 GB/s contiguous and 20 GB/s strided.

**Q.** "When would you run an SLM on the phone GPU versus the NPU?"

**A.** 기본은 NPU다 — INT8/INT4 네이티브 경로가 있고 같은 일에 전력 효율이 좋다. GPU를 고르는 경우는 NPU 컴파일러가 모델 구조나 동적 shape, 긴 context를 지원하지 못할 때, fp16 정확도가 필요할 때, 오픈 스택(llama.cpp Vulkan/OpenCL, MLC)으로 빨리 돌려야 할 때, NPU가 다른 기능에 점유되어 있을 때다. 그리고 decode는 memory-bound라서 GPU로 옮겨도 대역폭 천장은 같다 — 차이는 prefill(TTFT)과 전력·발열에서 난다. 결국 대표 프롬프트로 TTFT, tokens/s, 줄당 에너지, 지속 성능을 둘 다 재서 정한다.

> I'd start with the NPU: it has native INT8 or INT4 paths and better energy per token for the same work. I'd pick the GPU when the NPU toolchain can't handle the model — a new attention variant, dynamic shapes, long context — when I need fp16 accuracy, when I need to move fast with open stacks like llama.cpp's Vulkan or OpenCL backends, or when the NPU is busy with camera or audio. Also, decode is memory-bound, so moving it to the GPU doesn't raise the bandwidth ceiling; the differences show up in prefill time and in power and thermals. In the end I'd measure time-to-first-token, tokens per second, energy per response and sustained performance on both with representative prompts.

**Q.** "How is a GPU's execution model different from a CPU's?"

**A.** CPU는 latency machine이다 — 큰 캐시, 분기 예측, out-of-order로 thread 하나를 빨리 끝낸다. GPU는 throughput machine이다 — 레지스터 파일을 크게 두고 warp 수십 개를 상주시킨 다음, 하나가 메모리를 기다리면 비용 없이 다른 warp를 실행한다. SSD 펌웨어에서 queue depth를 높여 NAND 지연을 숨기던 것과 같은 원리다. 그래서 GPU는 일이 많고 규칙적일 때 강하고, 작고 순차적인 일에는 약하다.

> A CPU is a latency machine: big caches, branch prediction and out-of-order execution to finish one thread fast. A GPU is a throughput machine: it keeps dozens of warps resident with their registers in a huge register file, and when one warp stalls on memory it issues from another at zero switch cost. It's the same principle as keeping a high queue depth to hide NAND latency in SSD firmware. So GPUs shine on large, regular, parallel work and struggle with small or sequential work.

## 11. 직접 해보기

1. SM에 레지스터 65,536개, 최대 64 warp가 있다. block 128 thread, thread당 레지스터 96개면 occupancy는? 정답: block 레지스터 128 × 96 = 12,288 → 65,536 / 12,288 = 5 block → 5 × 4 = 20 warp → 31.25 %.
2. warp 32 lane이 `double`(8 B)을 `a[tid]`로 읽는다. 32 B sector 몇 개? `a[tid × 2]`라면? 정답: 256 B 연속 → 8 sector. stride 2면 512 B 범위에 흩어져 16 sector(효율 50 %).
3. 1.4절 식으로, 메모리 지연 600 사이클이고 warp가 load 사이에 30 사이클 계산한다. 지연을 숨기려면 warp 몇 개가 필요한가? 정답: 1 + 600/30 = 21개.
4. tiled GEMM에서 M = N = K = 1024, T = 32일 때 naive와 tiled의 global 읽기(원소 수)는? 정답: naive 2 × 1024³ ≈ 2.15e9, tiled = 2 × 1024² × (1024/32) ≈ 6.7e7 → 정확히 32배 감소.
5. 코드 과제: 예제 11의 MLP 은닉 폭을 256 → 1024, 2048로 키워서 batch=1과 batch=64에서 CPU vs MPS를 다시 재라. 교차점이 어디로 움직이나? 힌트: 레이어가 커질수록 GPU의 고정비 비중이 줄어 교차 batch가 작아질 것으로 예상된다 — 예상과 실측을 비교하라.
6. 코드 과제: 예제 12에서 입력을 미리 MPS에 올려 두고(`x.to("mps")`를 루프 밖으로) `.cpu()` 대신 `torch.mps.synchronize()`만 하도록 바꿔 재라. 6 ms 바닥 중 복사·읽기 비중은 얼마인가? 힌트: 4.8절의 H2D·D2H가 각각 약 160 µs이므로 0.3 ms 안팎이 빠질 것으로 예상된다.

## 12. 용어 사전

| 용어 | 뜻 | 한 줄 설명 |
|---|---|---|
| SIMT | single instruction, multiple threads | 스칼라 thread 코드를 warp 단위 SIMD 하드웨어로 실행하는 모델 |
| warp | NVIDIA의 동시 실행 thread 묶음 (32) | 한 명령을 함께 issue하는 단위 |
| wavefront | AMD의 warp (64, RDNA는 32도) | 같은 개념, 다른 이름과 폭 |
| SIMD-group | Apple Metal의 warp | `threadExecutionWidth`로 폭 조회 |
| SM / CU | streaming multiprocessor / compute unit | GPU의 "코어" — 레지스터·shared memory·스케줄러 포함 |
| block / threadgroup | 협력하는 thread 묶음 | 한 SM에 상주, shared memory와 barrier 공유 |
| grid | 커널 launch 하나의 전체 thread | block들의 배열 |
| divergence | warp 안에서 분기가 갈림 | 두 경로를 순서대로 실행, 비용 = 합 |
| latency hiding | 기다리는 warp 대신 다른 warp 실행 | 캐시 대신 병렬성으로 지연을 덮기 |
| occupancy | 상주 warp ÷ 최대 warp | 레지스터·shared memory·슬롯이 제한 |
| shared memory | block이 공유하는 on-chip SRAM | 소프트웨어가 관리하는 캐시(TCM과 비슷) |
| coalescing | warp의 주소를 적은 transaction으로 합침 | 인접 thread → 인접 주소 |
| bank conflict | shared memory 같은 bank 동시 접근 | 직렬화 — padding으로 회피 |
| tensor core | GPU 안의 행렬곱 유닛 | warp 단위 MMA, 저정밀 입력·고정밀 누산 |
| kernel launch | GPU에 커널 실행 명령 제출 | 비동기, 수 µs 발행 비용 |
| synchronize | GPU 완료를 CPU가 기다림 | 왕복 비용(이 Mac에서 약 150 µs) |
| unified memory | CPU와 GPU가 같은 물리 DRAM 공유 | 모바일·Apple — 복사는 줄지만 대역폭 공유 |
| zero-copy | 같은 버퍼를 CPU·GPU가 매핑 | 복사 없음, 동기화는 필요 |
| MPS | Metal Performance Shaders | Apple GPU 연산 라이브러리, PyTorch `mps` device의 기반 |
| GPU delegate | TFLite(LiteRT)의 GPU 실행 backend | OpenCL/OpenGL ES/Metal, 미지원 op는 CPU로 |
| DLA | NVIDIA Deep Learning Accelerator | Jetson의 고정 기능 CNN 가속기 |
| CUDA Graphs | 커널 시퀀스를 녹화해 한 번에 제출 | launch 오버헤드 감소 |

## 13. 요약 & 체크리스트

GPU는 작은 ALU lane을 SM으로 묶고, thread를 warp로 묶어 한 명령으로 실행하며(SIMT), 메모리 지연을 캐시가 아니라 **상주 warp 수**로 숨기는 throughput machine이다. 분기가 warp 안에서 갈리면 두 경로를 모두 지나고(divergence), 상주 warp 수는 레지스터·shared memory가 정하며(occupancy), 메모리 효율은 warp 주소가 한 덩어리인지(coalescing)가 정한다. tiled GEMM은 shared memory로 재사용을 만들어 global 트래픽을 1/T로 줄인다. 이 Mac에서 재 보면 GPU는 동기화 왕복 약 150 µs, 작은 op 발행 수 µs의 고정비를 가져서, KWS급 MLP는 CPU보다 17배 느렸고 MobileNetV2는 해상도 96~128 px, batch 1~2에서 교차했다. 큰 행렬곱에서는 약 2.9 TFLOPS로 CPU의 3배였다. 그래서 always-on batch=1 워크로드는 MCU·DSP·소형 NPU에, GPU는 고해상도 비전·batch·prefill·범용성이 필요한 burst 작업에 둔다. LLM decode는 대역폭이 천장이라 GPU로 옮겨도 빨라지지 않는다.

- [ ] CPU(latency machine)와 GPU(throughput machine)의 차이를 SSD queue depth 비유로 설명할 수 있다
- [ ] thread / warp / block / grid와 SM의 관계를 그리고, CUDA·Metal·OpenCL·Vulkan 용어를 대응시킬 수 있다
- [ ] 주어진 분기 패턴에서 divergence 비용을 손으로 계산할 수 있다
- [ ] 지연 L, 계산 c로 필요한 warp 수를 추정하고, Little's law로 비행 중 바이트를 계산할 수 있다
- [ ] 레지스터·shared memory·슬롯 한도로 occupancy를 손으로 계산하고, 높은 occupancy가 항상 좋지 않은 이유를 말할 수 있다
- [ ] 접근 패턴별로 warp가 건드리는 32 B sector 수를 세고 coalesced 여부를 판정할 수 있다
- [ ] CUDA vector add와 tiled GEMM 커널을 읽고 인덱스·`__syncthreads()` 두 번의 이유·global 트래픽 감소율을 설명할 수 있다
- [ ] GPU 시간을 잴 때 동기화·warm-up·median을 지키는 벤치마크를 짤 수 있다
- [ ] batch=1 작은 모델에서 GPU가 느린 이유 네 가지(고정비·활용률·전력·wake)를 숫자로 말할 수 있다
- [ ] Hark 같은 기기의 워크로드별로 GPU/NPU/DSP/MCU 중 무엇을 고를지 근거와 함께 말하고, 벤더에게 물을 질문을 나열할 수 있다
