1. Floating-Point Representation#

핵심: 트레이딩 시스템 최다 수치 버그의 뿌리 = double은 0.1을 저장할 수 없다.

왜 0.1을 못 담나#

  • 값 = fraction × 2^exponent → double은 이진 분수(1/2, 1/4, 1/8 … 의 합)로 저장.
  • 격자에 딱 맞는 수: 1/2 = 0.1₂, 1/4 = 0.01₂, 190.5 = 10111110.1₂ → 유한, 정확.
  • 10진 0.1 = 0.000110011001100…₂ (0011 무한 반복) — 10진에서 1/3 = 0.333…과 같은 상황. 53비트만 있으니 가장 가까운 값으로 반올림 → 돌아오는 건 0.1이 아니라 0.1 + 최하위 비트의 작은 오차.
  • 고전 증상: 0.1 + 0.2 != 0.3. 트레이딩 엔지니어가 걱정할 줄: 달러 가격과 센트 합이 둘 다 틀리게 나오는 것.

트레이딩 시스템에 드는 비용#

  • 누적: hot path는 반복한다. 0.01을 100번 더하면 1.0이 아님이 보일 만큼 복리. 하루 1억 번 × 모든 포지션 → 거래소 정수 회계와 대사(reconcile)되지 않는 실제 돈.
  • 비교 (더 날카로운 함정): 0.1 + 0.2 != 0.3 → if (price == target)이 같아야 할 때 false → 그 가격에 발동해야 할 limit 주문이 조용히 안 나감. 부동소수점은 10진 산술이 줄 답을 기대하며 exact equality로 비교 불가.

무엇이 정확하고 무엇이 아닌가#

정확 ✅부정확 ❌
2의 거듭제곱의 합: 0.5, 0.25, 128.5, 1024.0사람이 돈으로 적는 거의 모든 10진 소수: 0.1, 0.01, 190.10, 19.99
2⁵³ (~9.0×10¹⁵)까지의 모든 정수
  • 처방이 여기서 바로 나옴: 가격·수량은 10진이고 유한 → 정수(센트)로 저장 → 모든 값·합이 정확. = Module 1 MarketUpdate의 price가 처음부터 std::int64_t였던 이유.
  • ✅ 체크포인트: AAPL 가격을 double 달러로, if (last_price == 190.10) fire_order();가 실제 190.10인데도 가끔 안 발동 → 190.10은 이진 double로 정확 표현 불가 → 저장값과 리터럴이 최하위 비트에서 달라 불일치. 근본 원인 = 10진 가격에 부동소수점을 쓴 것 자체. (race condition이나 컴파일러 플래그 문제 아님)
  • 🎤 "부동소수점이 괜찮을 때는?" → 본질적으로 근사적인 양: 비율, 변동성, 통계. 센트 단위로 대사해야 하는 돈은 아님.

2. Integer Ticks & Price Representation#

핵심: 업계 표준 처방은 더 영리한 float가 아니라 분수를 아예 그만 쓰고 정수 단위로 세기.

가격 = tick의 정수 개수#

  • 가격은 연속적으로 변하지 않는다. 종목마다 tick size(가격이 움직일 수 있는 최소 단위) → 모든 유효 가격 = tick의 정수 배. 1달러 이상 미국 주식 대부분 tick = 1센트 → AAPL은 190.10/190.11은 되지만 190.104는 불가. 수량은 원래 정수(주).
  • Fixed-point: 가격 × 고정 scale factor(10^k) → std::int64_t. 센트면 scale 100 → 190.10 → 19010, 정확히. 소수점은 합의된 고정 위치에, 기계는 정수만 봄.
  • int64 최대 ~9.2×10¹⁸ → 센트로 세면 9경 달러까지. 가격 범위 걱정 없음 + 경로 위 모든 값이 정확 (double과 달리).

정수가 이기는 이유#

  • 정확: 가격 합이 정확, 100센트를 하나씩 더하면 정확히 100 (double은 1.00000000000000067).
  • 비교 정확: price == 19010이 문자 그대로 의미 → 가격 트리거 주문이 발동해야 할 때 발동.
  • 빠르고 완전히 결정적: 부동소수점 rounding mode 없음 → 같은 입력 = 모든 머신에서 같은 결과 → 거래소 정수 회계와 센트 단위 대사 가능.

폭(width)을 조심하라 — 곱셈#

  • 정수는 정확하지만 무한하지 않다. 물리는 곳 = 곱셈.
  • 가격 하나는 int32에 여유 있게 들어가지만 notional = price × quantity는 아님: AAPL 100만 주 ≈ 190억 센트, int32 최대 ~21억 → 곱이 조용히 wrap해서 틀린(흔히 음수) 값, 피연산자는 멀쩡해 보였는데.
  • 규칙: 결과 타입을 입력이 아니라 곱에 맞춰라. 가격·수량을 int64로 보관, notional을 int64로 계산 (곱하기 전에 cast), int64도 넘을 수 있는 드문 곱엔 __int128 또는 rescale.
  • 10진 변환은 표시 관심사 → 로그 줄·화면·리포트 같은 사람 쪽 가장자리에서만, scale로 나누고 나머지를 포맷. 가격이 산술용 double이 되는 순간 레슨 1의 오차 복귀.
  • 정수를 진짜로 떠나는 유일한 연산 = 나눗셈 (예: VWAP, 거래량 가중 평균가) → 분자·분모를 유지하거나, 부동소수점으로 신중하게 넘어감 (다음 레슨).
  • ✅ 체크포인트: 가격은 int64 센트(정답)인데 notional을 int32 shares * int32 price_cents로 → 500만 주 × 19010센트 ≈ 950억 센트 → 두 피연산자는 32비트에 들어가도 32비트 결과가 오버플로 → 틀린/음수 notional. 수정: 곱하기 전에 cast해 int64로 계산, int64도 넘을 수 있으면 __int128/rescale. (double이었다거나 숏 포지션 표시라는 답 ❌)
  • 🎤 "평균가는?" → 나눗셈은 정수를 떠남. 분자·분모를 유지하거나, 의도적으로 부동소수점으로 가서 정밀도를 관리.

3. Numerical Stability Intro#

핵심: 진짜 분수인 양 (VWAP, 수익률, 변동성, 두 합의 비율)은 부동소수점에 살 수밖에 없다. 반올림이 누적돼 틀린 답이 되지 않게 쓰는 법. 지킬 성질 = numerical stability: 안정적 계산은 반올림 오차를 작게 유지, 불안정한 계산은 결과를 지배할 때까지 키움.

작은 수는 큰 합 속으로 사라진다 → Kahan summation#

  • double은 53비트 정밀도 = 자기 크기 대비 상대적으로 값을 보관. 누적 합이 크고 다음 addend가 작으면, addend를 합에 맞춰 shift하다 하위 비트가 끝으로 떨어짐. 한 번은 안 보이지만 천만 번이면 눈에 보이게 틀린 합.
  • Compensated (Kahan) summation: 두 번째 변수(correction)가 지난 덧셈이 떨어뜨린 것을 기억 → 다음 스텝에 되더함. 원소당 연산 몇 개 추가로 잃은 정밀도 거의 전부 회복.
  • 데모: 0.1을 천만 번 더하면 정확히 100만이어야 함 → naive는 소수점 넷째 자리에서 이탈, Kahan은 착지.
  • (주의: -ffast-math는 이 보정식을 대수적으로 소거해버릴 수 있음 → Kahan 쓰는 곳에선 끄기)

거의 같은 수의 뺄셈 → Catastrophic cancellation#

  • 거의 같은 두 부동소수점을 빼면 앞자리들이 상쇄되고 이미 반올림된 하위 비트만 남음 → 결과가 거의 전부 오차.
  • 교과서 분산 공식 "제곱의 평균 − 평균의 제곱"이 정면으로 걸림: AAPL ~190.10이면 두 항 다 ~36,000이고 여러 자리까지 일치 → 차이에 실제 정밀도 거의 없음 → 음수 분산(수학적으로 불가능)까지 나옴.
  • 프로덕션 답 = Welford 알고리즘: 상쇄 없이 한 패스로 running mean·variance 갱신.
  • 일반화: 크고 비슷한 두 수를 빼는 공식이면, 그러지 않는 동치 공식을 찾아라.

절대 exact equality로 비교하지 마라 → tolerance#

  • 모든 float 연산이 반올림 → 같아야 할 두 계산이 몇 비트 차이 → a == b는 틀린 테스트.
  • 절대 + 상대 tolerance 둘 다 → 아주 작은 값과 아주 큰 값 모두에서 작동:
  • 상대 항: 큰 값은 자기 반올림 스텝이 어떤 고정 절대 tolerance보다 큼 → 상대 항이 처리.
  • 절대 항: 0 근처에선 상대 테스트가 붕괴 → 절대 항이 처리.
  • 뒷면: 정수로 보관한 가격은 그냥 == (정확하니까). Tolerance는 부동소수점을 쓴 대가로 내는 세금 → 꼭 필요한 곳에서만.
  • ✅ 체크포인트: 하루 AAPL 체결가(~190.10)의 분산을 sum_of_squares/n - mean*mean으로 → 가끔 작은 음수 분산 → 두 항이 ~36,000으로 거의 같아 catastrophic cancellation, 정밀도 거의 없음 + 약간 음수 가능. 수정: 평균 편차 제곱으로 계산하거나 Welford → 큰 비슷한 항끼리 빼지 않게. (가격 하락으로 진짜 음수 ❌, int64 오버플로 ❌)
  • 🎤 "부동소수점이 옳은 선택일 때?" → 평균·수익률·변동성처럼 본질적으로 분수인 양. 돈은 정수로, float은 값이 진짜 정수가 아닌 곳에만, 그리고 누적과 비교를 보호.

4. Time, Timestamps, Clocks#

핵심: 코스의 모든 타이밍 러너는 std::chrono::steady_clock을 썼고 이유는 설명 안 했다 → 여기서 닫는다. 트레이딩 시스템은 이벤트 스탬프와 tick-to-trade 계산을 위해 끊임없이 시간을 재고, 재는 시계는 틀리기 쉽다.

두 시계, 두 일#

steady_clocksystem_clock
성질단조(monotonic): 앞으로만, 일정 속도, 0점은 임의벽시계: UTC 기준 달력 시간, 조정 가능
답하는 질문"두 지점 사이에 얼마나 흘렀나" = duration"언제 일어났나" = timestamp
점프?정의상 뒤로 안 감NTP 드리프트 보정, 운영자 리셋, 윤초 → 앞으로도 뒤로도 점프
  • 레이턴시를 벽시계로 재지 마라: 두 벽시계 읽기 사이 NTP 보정 → 음수 duration 또는 ms 단위 오차 → ns 경주에선 헛소리.
  • "언제" = system_clock, "얼마나" = steady_clock. 코스의 모든 러너는 duration을 쟀으니 전부 steady_clock.

시계 읽기는 공짜가 아니다 (M8 경고의 청산)#

  • fast path에선 커널이 아니라 CPU 카운터로 가는 함수 호출이지만 여전히 수십 ns 규모. tick-to-trade 예산이 수백 ns 초반이면 모든 단계를 스탬프하는 건 공짜가 아님 → 타이머는 의도적으로 배치, 아무 데나 ❌.
  • Resolution: 시계가 구분할 수 있는 최소 간격, 플랫폼 의존 → 가정하지 말고 출력해 확인.
  • x86에서 steady_clock 밑은 보통 TSC (rdtsc 명령): CPU와 함께 tick하는 코어별 레지스터. 가장 빠르고 가장 세밀하지만 invariant-rate CPU여야 steady하고, tick → ns 변환에 calibration 필요 → 먼저 std::chrono, 프로파일링이 시계 읽기 자체가 크리티컬 경로라고 말할 때만 raw 카운터.
  • 데모에서 읽을 셋: 각 시계의 resolution, 읽기 1회 비용, steady_clock이 뒤로 간 횟수(표준이 0을 보장).

타임스탬프도 정수다#

  • 이 모듈 첫 교훈이 돈만큼 시간에도: 타임스탬프는 숫자 → 정수로.
  • 관례: std::int64_t epoch 이후 나노초 (고정 0점, 예: 1970-01-01 00:00 UTC). int64 ns ≈ 292년 범위 → 범위 걱정 없음, 모든 타임스탬프 정확.
  • tick-to-trade가 레슨 2의 정수 산술에서 그대로 나옴: 거래소가 AAPL 호가를 스탬프, 피드 핸들러가 도착을 스탬프, 게이트웨이가 send를 스탬프 → 각 레이턴시 = int64 뺄셈 1번, 정확하고 쌈.
  • 시간을 double 초로 저장하면 레슨 3으로 복귀: 크고 거의 같은 두 타임스탬프의 차이가 상쇄로 하위 자릿수를 잃음. 돈도 정수, 시간도 정수.

머신 간 타임스탬프 일치#

  • 내 머신 스탬프와 거래소 스탬프는 두 시계가 일치할 때만 비교 가능, 시계는 저절로 벌어짐 → 동기화 프로토콜.
    프로토콜정밀도용도
    NTP네트워크로 ~1ms로깅, 대략적 순서
    PTP (IEEE 1588), 특히 NIC HW 타임스탬핑sub-µs트레이딩 회사가 교차 머신 레이턴시 숫자를 믿으려면
    NIC 하드웨어에서 패킷 타임스탬프소프트웨어가 돌기 전가장 까다로운 셋업
  • 규제이기도 함: MiFID II 시계 동기화 규정 (RTS 25) → HFT 회사는 시계를 UTC ±100µs 이내, 이벤트를 µs 단위로 스탬프, 그 추적 가능성을 입증해야. 정확한 시간 = 레이턴시 예산만이 아니라 컴플라이언스 표면.
  • ✅ 체크포인트: 레이턴시 모니터가 두 system_clock 읽기를 빼서 처리 시간 계산 → 대부분 맞는데 하루 몇 번 큰 음수 → system_clock은 벽시계라 NTP/운영자가 step → 두 읽기 사이 보정이 차이를 음수로. 수정: duration은 steady_clock(단조), system_clock은 "언제 일어났나" 벽시각 타임스탬프에만. (투기적 실행으로 음수 레이턴시 ❌, int64 오버플로라 double로 ❌)
  • 🎤 "머신들이 시간을 어떻게 맞추나?" → NTP ~1ms, PTP + NIC HW 타임스탬핑 sub-µs. 교차 머신 레이턴시는 동기화돼야 의미 있고, MiFID II는 HFT 시계를 UTC 100µs 이내로 요구.

코스 전체의 결론 (한 문단)#

10개 모듈 전엔 두 O(n) 루프가 왜 10배 차이 나는지 말 못 했다. 이제: hot path를 실제 비용으로 읽고, 수명·소유권을 안전하게 관리하는 C++을 쓰고, 교과서가 아니라 기계를 위한 자료구조를 고르고, 자신을 속이지 않고 스레드를 다루고, 캐시·OS·네트워크에서 측정 가능한 레이턴시와 그 시스템이 봉사하는 트레이딩 도메인까지 추론한다. 이 마지막 모듈은 그 모든 것이 표기되는 숫자와 시간이라는 바닥을 깔았다.

관통하는 습관 하나: 추측하지 마라 — 데이터가 어디 사는지 알고, 각 연산의 비용을 알고, 평균이 아니라 꼬리를 재고, 한 번에 하나만 바꾸고, 돈과 시간은 정확한 정수로. 퀀트 시스템 면접이 실제로 시험하는 것이 이것이다.
