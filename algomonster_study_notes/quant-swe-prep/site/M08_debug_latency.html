1. Latency Measurement & Percentiles#

핵심: Module 1부터 "숫자를 믿지 마라"고 했다. 이제 측정 자체가 주제. 만든 모든 것의 가치 = 그게 작동함을 증명하는 능력.

Percentile = 순위(rank)지 평균이 아님#

  • 모든 샘플을 빠른→느린 순 정렬 → 주어진 비율이 그 값 이하인 지점 = pN. p50 = 중앙값, p99 = 100개 중 99개가 이 값 이하, p99.9 = 1000개 중 999개.
  • 모든 percentile은 실제 어떤 업데이트가 겪은 레이턴시. 평균은 빠른 경우와 느린 경우의 산술 혼합 → 긴 꼬리 시스템에선 어느 쪽도 설명 못 함.
  • 비유: 통근 평균 30분은 비행기 시간 정하는 데 쓸모없다 — 20번 중 한 번 1시간 걸리는 날 기준으로 출발. 트레이딩도 시장이 움직일 때 도착하는 업데이트로 돈을 받고, 그건 정확히 꼬리에 있다.

느린 샘플 몇 개는 평균을 안 움직인다#

  • 10만 건 중 대부분 빠르고 일부 느리고 극소수 끔찍 → 평균·중앙값·심지어 p99까지 ~1µs로 "건강". p99.9에서야 그림이 바뀌고, 최악은 평균의 100배+.
  • 하루 수백만 업데이트에서 "천 분의 일"은 반올림 오차가 아니라 수천 건, 그리고 바쁜 순간에 몰려 있다.

Percentile엔 분포가 필요 (running total로는 불가)#

  • 평균 = 합 + 개수. 순위는 분포 모양을 알아야 함.
  • 모든 샘플 보관: 정확하지만 저장 무한 증가 + 끝에 수백만 개 정렬.
  • Histogram: 레이턴시 구간별 카운터 배열. 기록 = 구간 찾아 +1. 메모리 고정, hot path 할당 0, 정렬 없이 카운트에서 바로 percentile.
  • 구간 = "bucket" (Module 3 해시 bucket과 무관한 같은 단어).
  • 프로덕션: HDR(high dynamic range) histogram — 고정 메모리로 µs~s의 넓은 범위를 작은 쪽 해상도 손실 없이.

Coordinated omission — 찾는 꼬리를 숨기는 측정 버그#

  • 하네스: 1µs마다 업데이트 1개 전송, "보내고 → 응답 기다리고 → 경과 기록". 시스템이 10ms stall → 하네스도 기다리느라 그동안 보내야 할 1만 건을 안 보냄 → 느린 샘플 1개만 기록 (실제 피드였다면 1만 개).
  • = 측정 루프가 시스템이 느릴 때 같이 조용해지는 협력. 안 찍힌 샘플이 꼬리를 희석 → p99.9가 자릿수 단위로 틀림.
  • 해결: 하네스 기준이 아니라 스케줄 기준으로 — 각 업데이트가 *보내졌어야 할 시각*을 기록하고 거기서부터 레이턴시 계산. stall 동안 나갔어야 할 모든 업데이트에 정확히 청구. 거래소는 네 핸들러가 바쁘다고 피드를 멈추지 않는다 → 측정도 멈추면 안 된다.

어떤 percentile로 평가받나#

  • 불운할 기회가 몇 번인가에 달림. 페이지당 요청 1번인 웹 → p99. 하루 수백만 업데이트 + 변동성 시기에 느린 게 몰리는 트레이딩 → p99.9 / p99.99 + 장중 최대값.
  • Tail amplification: 업데이트 하나가 여러 컴포넌트를 순차로 거치면, 어느 하나라도 느리면 느림 → 홉마다 누군가의 꼬리를 밟을 확률이 복리로. "각자 p99에선 괜찮은" 컴포넌트로 만든 시스템이 end-to-end로 자주 느린 이유. 꼬리는 합성을 견디는 숫자, 평균은 아님.
  • 코스 전체가 할당·블록·커널 횡단·서프라이즈 제거로 이끈 이유: 평균 최적화가 아니라 꼬리를 중앙값처럼 보이게 하려는 시도.
  • ✅ 체크포인트: 평균 1.2µs, p99 1.2µs → "건강" 결론의 가장 강한 반론 → 둘 다 깨끗해도 더 깊은 percentile은 훨씬 나쁠 수 있음 (p99 순위는 가장 느린 1%에 대해 아무 말도 안 함). p99.9와 max + 정직하게 계산할 histogram 필요.
  • 🎤 "hot path에서 p99.9를 실제로 어떻게 계산?" → 분포가 필요하니 running sum 대신 레이턴시 구간별 카운터 histogram. 샘플당 명령 몇 개, 할당 0. HDR로 넓은 범위를 고정 메모리에.

2. Profiling the Hot Path#

상황: p99.9가 중앙값의 10배. 본능 = 추측 ("allocator일 거야", "map 탓"). 추측은 가장 비싼 습관 — 그럴듯한 이론은 하루, 측정은 10분.

방법: 측정 → 하나만 변경 → 재측정#

  1. Baseline 기록 (이길 숫자, 도움됐는지 판단할 기준)
  2. 틀릴 수 있을 만큼 구체적인 가설 ("대부분 시간이 메시지 파싱에" ✅ / "파싱이 느린 느낌" ❌)
  3. 가설을 반박할 수 있는 측정
  4. 정확히 한 가지 변경 후 baseline 대비 재측정
  • 두 변경이 같이 들어가 4% 빨라지면 → 어느 걸 유지할지 아무도 모름 (Module 1 벤치마크 규율과 동일).

프로파일 읽기#

  • (book = 오더북, 심볼별 대기 매수·매도 기록. Module 9에서 제대로)
  • 퍼센트 = 자기 + 호출한 모든 것.
  • Flame graph: 같은 데이터를 스택 깊이별 행으로. 폭 = 샘플 비율(유일한 크기 인코딩), 위의 박스 = 호출한 것. 색은 임의, 좌→우 순서는 보통 알파벳순 — 가장 흔한 오독. 수직 위치는 의미 있음(호출자 바로 위).
  • 이 프로파일은 이미 코스 이야기를 하고 있음: 이국적인 걸 찾는 게 아니라 이미 아는 비용 중 실제로 지불되고 있는 게 뭔지 찾는 것.

Sampling은 평균을 찾지 꼬리를 찾지 않는다#

  • 샘플링 = "이 프로그램이 주로 뭘 하나" → 분포의 두꺼운 부분에 대한 질문. 문제는 천 번에 한 번의 stall.
  • 초당 수천 번 샘플, µs짜리 병적 이벤트가 가끔 발생 → 샘플 0개가 걸릴 수 있음. 문제 아닌 정상 작업만 충실히 보고.
  • 더 나쁨: 대기로 인한 stall(major page fault, 락, 블록된 recv — Module 4–7 전부)은 스레드가 안 돌고 있어 CPU 샘플에 아예 안 나타날 수 있음. (예외: minor fault는 커널 모드로 코어에 남아 샘플됨)
  • 꼬리엔 다른 도구: 이벤트마다 타임스탬프 + 파이프라인 단계별 histogram(어느 단계 분포가 긴 꼬리인지). 더 좋게는 트리거: 업데이트가 임계치를 넘으면 그때 상황(단계 타이밍, 큐 깊이, 카운터)을 덤프 → 데이터는 적고 전부 관심 케이스.
  • Sampling = 어떤 코드를 빠르게 할지 / per-event capture = 어떤 코드가 가끔 멈추는지.

그다음: 더 빠른 일이 아니라 없앤 일#

  • 함수를 지목하면 마이크로 최적화부터 하지 말 것. 가장 싼 변경 = 일을 삭제: memcpy → zero-copy parse, map lookup → 밀집 정수 키면 직접 인덱싱, push_back → 시작 시 reserve. = 주소가 붙어 도착한 Module 1 체크리스트. 프로파일링은 새 해법을 가르쳐준 게 아니라 이미 아는 해법 중 할 가치 있는 걸 알려줌.
  • ✅ 체크포인트: 샘플링 프로파일이 평범한 작업에 고르게 분포, 의심 없음, 그런데 p99.9는 중앙값의 10배 → 샘플링은 집계 동작을 보고하므로 드문/비-CPU stall은 샘플 사이에 빠지거나 스레드가 블록 중이라 안 나타남 → per-event 타임스탬프나 느린 이벤트 트리거 캡처 필요.

3. Performance Counters Intro#

핵심: 프로파일은 book.apply가 44%라고 어디를 말했다. 하지만 함수가 느린 이유는 셋 중 하나 — 명령이 많거나 / 명령은 적은데 메모리를 기다리거나 / 분기를 계속 틀리거나 — 이고 해법이 완전히 다르다. CPU는 내내 세고 있었다.

CPU는 자기 행동을 센다#

  • HW performance counter: 실리콘에 내장된 레지스터들이 cycles, instructions, cache 조회·미스, 분기·분기 미스, page fault를 집계. 보든 말든 세고 있어서 읽는 비용 ≈ 0.
  • Linux 정문: perf stat
  • 각 줄 = 이미 배운 메커니즘 (cache miss = M5 계층, branch miss = M5 flush, page fault = M6 첫 터치, context switch = M6 cold 재시작). 카운터가 더해주는 것 = 내 프로그램에서 실제로 얼마나 자주.
  • ⚠️ 주류 x86의 generic cache-references/cache-misses는 last-level cache(LLC) 접근을 셈 → 45%는 "로드 절반이 L1 미스"가 아니라 "앞 레벨에서 떨어진 요청의 거의 절반이 DRAM까지" → 훨씬 강한 진술.

Instructions per cycle을 먼저 읽어라#

  • 두 카운터의 비율 = instructions / cycles. 현대 코어는 superscalar(사이클당 여러 명령 retire).
    • > 2: 레지스터·L1 데이터로 조밀한 산술 → 코어가 꾸준히 일을 발행 → 빨라지려면 일을 줄여라 (더 나은 알고리즘, 연산 감소, M5 벡터화)
    • < 1: 대부분 stall → 명령 수준 영리함은 무용 → 무엇에 stall됐나? → 다른 카운터가 답
    • 심하게 메모리 bound면 ~0.1
  • ⚠️ 약어 충돌: 이 비율도 "IPC"로 줄이지만 Module 6의 inter-process communication과 무관.
  • ⚠️ 함정: spin loop는 아무것도 안 하면서 높은 비율로 명령을 retire → M4/M6의 busy-wait 설계는 훌륭한 비율을 보임. 높은 수치 = 코어가 바쁨, 유용한 일이라는 뜻 아님.

카운터는 조합으로 읽는다#

  • 위의 패턴표 참조. 마지막 행(false sharing)은 perf stat 총계로는 불가 — 총 미스 수는 "두 코어가 한 라인을 두고 싸운다"를 말해주지 못함 → perf c2c: 미스를 특정 캐시 라인 + 그걸 주고받는 코어 쌍에 귀속 → "데이터가 큼" vs "데이터가 공유됨" 구분. 작고 뜨겁고 튕기는 라인 = false sharing → alignas(64).

카운터가 말해주지 않는 것 (정직한 단서 3개)#

  1. 기계를 잴 뿐 의도는 모름: 레이턴시의 2%인 함수의 높은 미스율은 네 문제가 아님 → 프로파일링 먼저, 카운터 둘째.
  2. 코어별 HW: 공유/가상화 호스트에선 이웃이 포함·제외돼 오독 쉬움. HW 레지스터보다 많은 이벤트 요청 → 커널이 이벤트 간 time-slice 후 스케일링 = counter multiplexing → 정확한 카운트가 추정치로.
  3. 비율은 baseline 대비로만 의미: "45% cache miss"는 변경 전 같은 워크로드, 또는 빠르다고 여기는 버전의 같은 카운터를 알 때만 의미.
  • 실전 간극: perf stat은 프로세스 전체 합계인데 질문은 함수 하나 → 카운터 이벤트로 샘플링: perf record -e cache-misses → perf annotate / 함수별 리포트로 미스를 소스 라인에 귀속. Localize 후 characterize, 같은 도구에 이벤트만 다르게.
  • 결론: 프로파일이 "시간은 book.apply에" → 카운터가 "0.30 IPC, cache ref 45% 미스" → map lookup이 문제인지 더 이상 추측할 필요 없음. 프로파일은 비용을 위치시키고, 카운터는 이름 붙인다.
  • ✅ 체크포인트: 프로파일을 지배하는 함수 — 팀 A: 0.3 IPC + 45% cache miss / 팀 B: 2.4 IPC + 12% branch miss → A는 메모리 stall → 레이아웃·locality 개선, B는 코어는 바쁜데 분기를 틀림 → 분기를 예측 가능하게 or 제거. 프로파일에선 같은 증상, 정반대 처방.

4. Memory Bottleneck Identification#

핵심: 카운터가 메모리를 가리켰다(0.3 IPC, 절반 미스). 내 머신에선 거의 판결. 하지만 컨테이너 권한 없음, 프로덕션 호스트에 도구 없음, 면접관은 셸을 안 준다 → 시계 하나로 증명하는 법 + 그 답이 무엇을 강제하는지.

루프가 느린 두 가지 방식#

Compute-boundMemory-bound
속도를 정하는 것코어가 명령을 실행하는 속도데이터가 도착하는 속도
빨라지는 법산술을 줄임산술 유닛은 놀고 있음 → 명령 제거는 무의미 → 어떤 데이터를 만지나 / 어디 사나를 바꿔야
  • = Module 1 첫 주장("같은 O(n) 두 루프가 10배 차")을 답할 수 있는 질문으로. Big-O = 연산 수, 병목 = 어느 자원이 먼저 바닥나나.

Working-set test (도구 불필요)#

  • 같은 일을 작은 작업 집합 vs 큰 작업 집합에서 → 원소당 비용 관찰.
    • L1에 맞는 집합 = 캐시 속도 / L3 넘치면 DRAM.
    • 작업 집합이 커질 때 원소당 비용 증가 → 메모리 대기 / 평평 → CPU 대기.
  • 논리가 성립하는 이유 = 바꾸지 않은 것: 원소당 명령 수·알고리즘·분기 패턴 동일, 바뀐 건 데이터가 계층 어느 레벨에 사는지뿐 → 차이는 메모리 시스템에서만 나올 수 있음.
  • 데모 두 루프 (방문 횟수 동일, footprint만 다름):
    • 의존 읽기 체인 (각 스텝 주소 = 방금 로드한 값): L1에 맞으면 ~1ns, 넘치면 수십 ns — 매 스텝이 숨길 수 없는 새 미스.
    • 순차 math (쭉 읽으며 원소당 산술 충분): 크기와 무관하게 비용 유지 — ① 순차라 prefetcher가 앞서 가져와 레이턴시 숨김 ② 바이트당 산술이 충분해 메모리보다 코어가 먼저 바닥남.
  • 크기를 여러 개로 sweep → 지도가 됨: 한 레벨에 맞는 동안 평평, 넘칠 때마다 계단 → 계단이 대략 L1/L2/L3 경계. = 표에서 인용한 게 아니라 실제 머신에서 측정한 Module 5 계층.

Memory-bound의 두 종류#

Latency-boundBandwidth-bound
상황다음 주소를 현재 로드가 돌아와야 앎 → 접근을 겹칠 수 없음, 매번 풀 왕복접근 완벽 예측, prefetcher 정상 작동, 그런데도 메모리가 전달할 수 있는 것보다 빨리 바이트를 요구
예의존 체인, 포인터 체이싱 (prefetcher 무력)산술 거의 없는 스트리밍 (큰 배열 합산)
처방의존성 깨기, locality 개선 → 미스가 직렬화되지 않게접근 패턴은 이미 이상적 → 바이트를 덜 옮기기: 더 촘촘히 pack, hot/cold 필드 분리, 더 작은 타입

더 나은 알고리즘이 지는 이유 (모듈의 stub 질문)#

  • Big-O는 연산을 세고, 기계는 접근에 요금을 매긴다. 복잡도가 낮은 쪽이 메모리를 덜 예측 가능하게 만지면 둘이 갈라짐.
  • Module 3 재독 (진단 첨부):
    • std::map lookup O(log n) vs 정렬 vector 선형 스캔 O(n) → 수백 개면 vector가 보통 승. 트리 walk = 데모의 느린 열(의존 포인터 hop 체인), 스캔 = 빠른 열(prefetch 가능 stride).
    • unordered_map O(1)도 노드 체이싱으로 lookup당 캐시 미스.
  • 연산이 적은 알고리즘이 진 이유 = 연산 하나하나가 더 비쌌기 때문. working-set test가 논쟁 대신 시연하는 방법.

답이 "메모리"일 때 할 것#

  • 메모리 bound 루프는 산술을 줄여서 빨라지지 않는다. 본문 마이크로 최적화, unroll, 곱셈→시프트는 애초에 병목이 아니던 숫자를 움직임.
  • 도움되는 것 (이제 일반 선호가 아니라 증거 기반):
    1. 작업 집합 축소 → 더 빠른 레벨에 더 많이 (구조체 pack, hot/cold 필드 분리)
    2. 접근 패턴 예측 가능하게 → prefetcher가 숨기게 (연속 레이아웃, SoA — M5)
    3. 간접 참조 제거 → 원소마다 포인터 hop 없게 (M1 vector-of-pointers 함정, M3 노드 컨테이너)
    4. 원소당 만지는 바이트 감소 → 트래픽이 곧 비용
  • 전부 메모리 시스템의 일을 바꾸지, 산술을 싸게 만들지 않음.
  • ✅ 체크포인트: 수백 개 AAPL 주문 레코드에서 정렬 vector 선형 스캔 → std::map lookup으로 바꿨더니("O(log n) > O(n)") hot path 느려짐 → 트리 walk는 메모리에서 stall하는 의존 포인터 hop 체인, 스캔은 prefetch 가능 stride → 연산은 적어도 시간은 더. 프로파일러 없이 시연: 작은/큰 작업 집합에서 둘 다 돌려 map의 lookup당 비용은 오르고 스캔은 평평함을 보임.

5. Lock Contention Debugging#

핵심: 메모리 외에 스레드가 아무것도 안 하며 시간을 태우는 다른 방법 = 다른 스레드 기다리기. Module 4는 mutex 비용을 가르쳤고, 여기선 내가 안 짠 시스템에서, 먼저 재작성하지 않고 락이 문제임을 증명하는 법.

증상: 확장이 안 된다 (scaling test)#

  • 총 작업량 고정 → 1, 2, 4 스레드로 실행.
    • 깨끗이 병렬화 → 스레드 추가 시 빨라짐.
    • 락 뒤에 직렬화 → 안 빨라짐 (추가 용량을 한 번에 하나만 쥘 수 있는 자원 대기열에 소비).
  • 🚨 경보 버전: 스레드 추가 시 총 시간이 더 나빠짐 — 역설 아님. 스레드마다 같은 락 경합 + 커널 park/wake + 캐시 트래픽 증가, 실제 일은 그대로. 병렬로 더 많은 일이 아니라 병렬로 더 많이 기다리는 중.
  • 모듈에서 가장 싼 진단: 프로파일러·권한·코드 지식 불필요, 스레드 수 설정 + 실행 시간만.

Acquire를 계측하라#

  • scaling 곡선 = 무언가가 직렬화됨. 특정 락임을 증명 = 락을 측정: 시계 읽기 → mutex 획득 → 시계 읽기 → 차이 누적 = 일할 허락을 기다린 시간. 스레드 전체 합산 → 중요한 숫자 = 스레드 시간 중 일 대신 대기에 쓴 비율.
  • 프로덕션은 lock profiler나 mutex wrapper 내장 도구로.
  • 데모 (총 작업 고정, 스레드 수 변경): 행을 내려갈수록 wall time 상승, acquire당 대기가 한 자릿수 증가, 가용 스레드 시간 대부분이 대기. 단일 스레드 행 = 정직한 baseline (경쟁자 없으니 경합 없음 → 비경합 락 + 시계 2번 비용). 그 위는 전부 큐잉.

락 없는 경합 (함정)#

  • 여러 스레드가 atomic으로 갱신하는 카운터: 락 없음, 데드락 불가, 그래도 확장 안 됨 — 쓰기마다 캐시 라인이 코어 간 이동 (M5 일관성 트래픽). 극단 = false sharing (같은 변수도 아닌데 비용 지불).
  • 겉보기 동일 → 증거가 가리키는 곳으로 구분:
    락 경합캐시 라인 경합
    대기 위치acquire 안 (계측/lock profiler로 직접 보임)락이 어디에도 없음
    확인context-switches 증가 (커널에서 실제로 park)perf c2c: 한 hot line이 코어 간 튕김
    성격블로킹일관성

수정 순서 (사다리를 위에서부터)#

  1. 임계구역 축소 — 밖에서 계산, 안에서 발행. 락 안 할당·로그·I/O 금지. 경합은 락을 쥔 시간에 비례 → 최고 가치 변경.
  2. 샤딩 — 락 하나를 서로 다른 데이터를 덮는 여러 락으로 (예: 심볼별 락 → AAPL과 무관 티커가 충돌 안 함, 오더북 전체에 락 하나 ❌).
  3. 공유 제거 — 가능하면 스레드별 상태 + 마지막에 병합 (코스에 per-thread 카운터가 계속 나오는 이유).
  4. 그제야 lock-free — M4의 정직한 프레이밍: 진행 보장이지 속도 보장 아님, 비경합 mutex가 경합 lock-free 큐를 이길 수 있음.
  • 핵심 프레이밍: 경합은 락의 속성이 아니라 그 안에 넣은 일의 양의 속성. 5ns 쥐는 mutex × 4스레드 = 거의 공짜, 같은 mutex 5µs = 큐. 락은 안 바뀌었다.
  • ✅ 체크포인트: mutex 없이 std::atomic으로 갱신하는 공유 카운터가 1→4 스레드에서 전혀 안 빨라지고 약간 느려짐 → 캐시 라인이 쓰기마다 코어 간 이동, 비용은 블로킹이 아니라 일관성 트래픽 → perf c2c로 확인, 수정 = 스레드별 카운터 + 마지막 병합. (atomic이 몰래 mutex로 폴백하는 것도, 정상적 최적 결과도 아님)

6. Systematic Debugging Storytelling#

핵심: 도구 5개를 가진 것 ≠ 어느 걸 집을지 아는 것. 면접에서 "성능 문제를 고친 경험"을 물으면 방법을 듣고 있다 — 방법은 그들의 실제 문제로 일반화되고, 운 좋은 수정은 안 된다.

루프 (6단계, 이 순서로)#

  1. Observe — 느낌이 아니라 숫자: 어느 percentile이 얼마나 언제. "장 시작에 느린 느낌" → "p99.9가 중앙값의 10배, 첫 10분에 집중".
  2. Localize — 프로파일러로 어디 (드문 stall이면 샘플링 대신 per-event capture).
  3. Characterize — 카운터 / working-set test / 락 계측으로 왜 (같은 hot 함수가 메모리 stall·분기 bound·블록일 수 있음).
  4. Hypothesis — 틀릴 수 있게 구체적으로: "book lookup이 노드 기반 map에서 메모리 bound" ✅ / "map이 느림" ❌.
  5. Change exactly one thing.
  6. Verify against baseline — 올바른 숫자로: p99.9가 불만이었다면 더 나은 평균은 답이 아님.
  • 검증 실패(자주 있음) 시 0부터 재시작 아님 — 반증된 가설도 증거, 다음 가설을 좁힘.

아무것도 안 잡히면: Bisect#

  • 프로파일 평평, 카운터 평범, 느린 게 모습을 안 드러냄 → 가장 오래된 기법: 탐색 공간 반으로 → 재시험.
    • 파이프라인 후반부를 끄고 꼬리가 살아남나.
    • 어제 데이터를 오늘 빌드로 / 오늘 데이터를 어제 빌드로 재생 → 데이터 변경 vs 코드 변경 분리.
    • 숫자가 움직일 때까지 커밋을 거슬러.
  • 조잡해 보이지만 정교한 도구가 할 말이 없을 때 통하는 것. 내 코드에 없는 원인도 찾음: 커널 설정, 코어 affinity·메모리 배치 변경, 호스트의 noisy neighbor, 시장 데이터 모양 자체의 변화.

믿을 수 있는 baseline#

  • 지난주 숫자 인용 ❌ → 재측정 (머신·데이터·빌드 다 움직였음).
  • 테스트 안 하는 건 전부 고정: 같은 호스트, 입력, 부하, 컴파일러 플래그.
  • 큰 개선을 믿기 전에 Module 1의 "벤치마크가 거짓말하는 방법" 재독 — 일을 통째로 사라지게 한 변경은 일을 빠르게 한 변경과 똑같아 보인다. 수상하게 좋은 숫자 → 첫 가설은 "코드가 빨라졌다"가 아니라 "일이 삭제됐다".

이야기하기 — 모양: 증상 → 의심 → 증거 → 변경 → 결과 → 트레이드오프#

(예시 답변 요지 — 모듈의 worked example로 조립) 대시보드상 AAPL 피드 핸들러는 건강했다(평균·p99 ~1µs). 그런데 p99.9가 중앙값의 10배, 장 시작 첫 몇 분에 몰림 — 정확히 중요한 때. 프로파일해보니 예상한 파싱이 아니라 book 업데이트가 샘플의 44% (첫 추측이 틀렸음). 카운터: 그 함수는 ~0.3 IPC, cache ref 절반 미스 → 계산이 아니라 stall. working-set test로 확인: 작은 book에선 lookup 몇 ns, 전체 book에선 수십 ns → 산술이 아니라 메모리. book은 심볼 키 unordered_map → lookup마다 노드 체이싱. 밀집 심볼 id로 인덱싱하는 평평한 배열로 교체 → 예측 가능한 접근 1번. p99.9가 중앙값 근처로, 평균은 거의 안 움직임 (꼬리를 고치면 예상되는 모습). 트레이드오프: 이제 시작 시 전체 심볼 유니버스만큼 배열을 할당하고, 유니버스가 알려져 있고 유한해서만 동작. 같은 프로파일이 지목한 parse 복사가 다음이었지만, 이 변경을 단독으로 먼저 검증하려고 멈춤.

  • 이 답이 하는 일: 숫자와 percentile로 시작 / 첫 추측이 틀렸다고 인정(나머지를 믿게 만듦) / 모든 단계가 직관이 아니라 증거, 증거는 어디 → *왜*로 격상 / 변경은 하나 / 결과를 불만이었던 그 숫자로, 평균은 안 움직였다는 정직한 관찰 / 비용으로 끝맺음 (모든 최적화는 거래, 자기 거래를 말 못 하는 엔지니어는 생각을 안 끝낸 것).
  • ❌ 대부분 후보의 버전: "느려서 파서를 최적화했더니 30% 빨라졌어요" — percentile 없음, 증거 없음, 왜 파서를 골랐는지 없음, 트레이드오프 없음, 비교 대상 없는 숫자.

무엇이 평가되나#

  • perf 플래그 암기가 아니라: 의견보다 증거를 먼저 집는가, 평균과 꼬리가 다른 문제임을 아는가, 한 번에 하나 바꾸는가, 안 한 것과 그 이유를 말할 수 있는가, 수정의 비용을 아는가.
  • 이 습관들이 이 모듈 전체이자 앞 7개 모듈을 쓸모 있게 만드는 것: cost model은 뭐가 비쌀 수 있는지, 측정은 뭐가 실제로 비싼지를 말해준다.
  • ✅ 체크포인트: "allocator를 의심해서 memory pool 추가 + map을 flat array로 동시에 교체, 평균 20% 하락 → allocator가 문제였다" → 틀린 점: 두 변경이 같이 들어가 어느 쪽에도 귀속 불가, allocator 결론은 증거로 검증된 적 없음, 더 나은 평균은 꼬리 불만에 대한 답이 아님. 수정: baseline → localize·characterize 측정 → 하나만 변경 → 실제로 나빴던 percentile 검증.
  • 🎤 "어떻게 자신을 속이지 않나?" → 같은 호스트·데이터로 baseline 재측정, 한 번에 하나, 불만이었던 percentile 검증. 개선이 너무 좋아 보이면 빨라졌다고 가정하기 전에 일이 삭제됐다고 가정.
  • 🎤 "왜 한 번에 하나?" → 아니면 아무것도 귀속 불가. 합쳐서 4% 이득인 두 변경이 큰 승리 하나 + 회귀 하나일 수 있고, 둘 다 유지하게 됨.
