모든 게 같은 성질로 수렴: 연속적이고, 독립적이고, 직선적인 코드가 캐시·prefetcher·파이프라인·벡터화 모두를 행복하게 한다.

1. CPU Cache Hierarchy#

핵심: "메모리"는 하나가 아니라 층층의 스택. 한 층 내려갈수록 크고 느리다.

레벨위치상대 레이턴시 (모양만 기억)
Register코어 내부, 수십 개가장 빠름 — 산술은 여기서만
L1코어 전용, 아주 작음수 cycle (레지스터에 가까움)
L2코어 전용, 더 큼L1의 몇 배
L3코어 간 공유, 더 큼더 몇 배
DRAMGB 단위, allocator가 주는 곳수백 cycle (L1의 ~100배)
  • 로드는 L1부터 확인 → hit면 몇 cycle. miss면 L2→L3→DRAM으로 내려가며 방문한 레벨마다 레이턴시를 더함. 미스는 "작은 페널티"가 아니라 계단 내려가기.
  • 레벨 간 이동 단위 = 64B 캐시 라인 (Module 1). "fetch 비용"의 정확한 의미 = 미스가 얼마나 깊이 내려갔나.
  • 측정법(데모): 랜덤 셔플된 순환에서 포인터 체이싱(각 로드가 이전 로드에 의존 → HW가 추측 불가) + 작업 집합을 KB→수십 MB로 키움 → 접근당 시간이 계단식으로 상승 (한 레벨을 넘칠 때마다).

작업 집합을 빠른 레벨에#

  • 수십 년간 CPU는 크게 빨라지고 DRAM은 거의 그대로 → DRAM 한 번에 코어는 수백 명령 실행 가능. 계층의 목적 = 그 격차 숨기기.
  • Working set = 루프가 실제로 만지는 메모리. L1/L2에 맞으면 풀스피드, L3 넘어 DRAM으로 새면 대부분 대기.
  • Module 1 재해석: vector가 이기는 건 원소들이 64B 라인을 공유하며 L1으로 스트리밍되고 작업 집합이 컴팩트해서. list가 지는 건 흩어진 노드가 스텝마다 DRAM 미스 위험, 백만 노드는 빠른 레벨에 안 맞아서. 컨테이너가 핵심이 아니라 그 바이트가 계층 어디에 떨어지느냐가 핵심.
  • 🎤 면접 무브: 메모리를 평평하게 취급하지 말 것. "이 hot loop의 작업 집합은 어느 레벨에 사나?" — 매 iteration 재사용하는 수 KB는 L1(사실상 공짜), 수백 MB 스캔은 거의 매 라인 DRAM (루프 본문 트릭으로 못 숨김).
  • ✅ 체크포인트: vector 합산이 list 합산보다 몇 배 빠른 이유(계층 관점) → vector는 64B 라인에 레코드를 묶어 L1로 스트리밍(대부분 hit), list는 흩어진 노드마다 DRAM 미스 위험.
  • 🎤 "캐시 미스가 hit보다 훨씬 비싼 이유?" → hit는 L1 몇 cycle, miss는 L2·L3·DRAM을 내려가며 방문 레벨마다 지불. DRAM 왕복은 L1 hit의 ~100배 규모.

2. Cache Coherency & MESI#

배경: L1·L2는 코어 전용, L3만 공유 → 같은 64B 라인이 두 코어의 전용 캐시에 동시에 있을 수 있음. 한 코어가 쓰면 다른 코어는 stale 사본을 쥔다. HW는 coherence를 보장: 모든 코어가 위치마다 하나의 일관된 값을 봄 (사본이 여럿이어도 하나인 것처럼).

MESI — 모든 캐시 라인에 붙는 상태 태그#

상태의미
Modified이 코어만 가짐 + 변경됨 → 메모리가 stale, write-back 빚짐
Exclusive이 코어만 가짐 + 깨끗함
Shared깨끗한 읽기 전용 사본, 다른 코어도 가질 수 있음
Invalidstale, 사용 전 재fetch 필요
  • 불변식: S는 여러 코어 동시 가능(읽기 전용은 불일치할 수 없음). M/E는 최대 한 코어, 한 코어가 M이면 나머지는 전부 I. → 읽기는 자유롭게 공유, 쓰기는 불가.
  • 쓰기 = read-for-ownership: 다른 코어가 라인을 갖고 있으면 먼저 invalidate 메시지 → 그들 사본을 I로 → 소유권을 끌어옴 → 쓰기. 다른 코어가 같은 라인을 쥐고 있으면 쓰기는 절대 그냥 쓰기가 아니다.

경합 카운터가 기어가는 이유 (Module 4의 IOU 청산)#

  • 코어 A: B에 invalidate → 라인을 L1에 M으로 → +1 / 코어 B: 자기 사본 I → A에 invalidate → 라인 끌어옴 → +1 / 반복…
  • 매 증가마다 라인이 L1↔L1 이동, 코어 간 전송 수십 ns vs 비경합 L1 hit 몇 cycle.
  • fetch_add 명령 자체는 쌈. 비용 = 공유(일관성 트래픽)지 산술이 아님.
  • 단독 atomic이 공짜인 이유: writer 하나면 라인이 그 코어 L1에 M으로 머물러 매 증가가 로컬 hit.
  • 펜스 때문이 아님: relaxed(순서 보장 없음)로도 핑퐁은 일어남. 비용은 라인이 움직이는 것.

설계에 주는 교훈#

  • "atomic은 느리다"가 아니라 "자주 쓰이는 공유 위치는 확장성 함정" — 코어를 더 넣으면 한 라인을 운반하느라 더 느려짐 (하드웨어 추가가 성능을 빼는 첫 사례).
  • 읽기는 예외: 여러 코어가 S로 영원히 읽어도 무효화·트래픽 없음 → read-mostly 공유 데이터는 쌈.
  • 규칙: 뜨겁고 자주 쓰는 상태는 공유 경로에서 빼라 → 스레드별 카운터 + 마지막에 한 번 병합.
  • ✅ 체크포인트: 두 코어가 같은 atomic에 fetch_add를 반씩 → 한 코어 단독보다 느린 이유 → 라인이 두 코어 전용 L1 사이를 이동, 쓰기마다 상대 사본 무효화 → 매 증가가 로컬 hit 대신 코어 간 전송 대기. (atomic은 전역 락을 잡지 않음)
  • 🎤 "읽기 전용 데이터 공유는 비싼가?" → 아니다. S 상태로 무효화 없음. 비용은 공유 라인에 대한 쓰기.

3. False Sharing#

핵심: CPU는 변수가 아니라 캐시 라인의 소유권을 추적한다. 서로 다른 변수라도 같은 64B 라인에 있으면 → 진짜 공유와 똑같이 핑퐁.

  • 시나리오: 공유 카운터가 핑퐁 → Module 4 조언대로 스레드별 카운터로 교체 → long long counts[2]나 인접 struct 멤버로 배치 → 거의 안 빨라짐.
  • A가 a에 쓰면 라인 전체가 A에서 M, B에서 I → B가 b에 쓰면 라인을 끌어오며 A 무효화 → 핑퐁. data race도 오답도 없고, 라인만 매 증가마다 튕김.
  • "false" = 공유가 메모리 레이아웃의 우연, 로직엔 안 보임 → 고칠 건 알고리즘이 아니라 레이아웃.

해결: 패딩#

  • Module 4 SPSC ring의 head/tail에 붙은 alignas(64)의 이유: 두 인덱스가 한 라인이면 push마다 소비자 사본 무효화, pop마다 생산자 사본 무효화 → lock-free 큐가 자기 인덱스로 핑퐁.
  • 매직 넘버 이름: std::hardware_destructive_interference_size (64 하드코딩 대신).

찾는 법#

  • 증상: 스레드를 늘려도 안 빨라지고(때로는 느려지고) 락은 안 보임. → 뜨거운 스레드별 데이터의 레이아웃을 보고, 두 스레드의 쓰기가 64B 이내에 있는지 확인.
  • 도구: Linux perf c2c (cache-to-cache) — 튕기는 라인과 그 라인을 공유하는 변수를 정확히 지목. 더 거친 신호: perf stat에서 embarrassingly parallel해야 할 루프의 높은 캐시/일관성 stall.

면접에서 날카롭게 구분할 것#

Data race (Module 4)False sharing
종류정확성 버그 (UB, 오답)성능 버그
결과틀림매번 정확히 맞음, 느릴 뿐
고칠 곳동기화주소(레이아웃) — "바이트는 맞고 주소만 틀렸다"
  • ✅ 체크포인트: 스레드별 long long counts[8]로 바꿨는데 공유 버전과 비슷 → 8개 카운터가 한두 개 캐시 라인을 공유, 각자 다른 슬롯에 써도 라인이 핑퐁.

4. CPU Pipeline & Branch Prediction#

핵심: Module 1에서 측정만 했던 결과 — 같은 분기, 같은 일, 같은 Big-O인데 정렬 데이터가 셔플 데이터보다 몇 배 빠름 — 의 메커니즘.

파이프라인#

  • 조립 라인: fetch → decode → execute → memory → write-back. 단계를 겹쳐 실행 (명령1 execute 중 명령2 decode, 명령3 fetch).
  • 교과서 5단계, 현대 코어는 ~15–20단계 → 항상 15–20개 명령이 비행 중. (+ 사이클당 여러 명령 발행, 재배치까지 — 하지만 여기서 중요한 건 깊이)
  • 겹침 덕에 명령 하나가 여러 cycle 걸려도 거의 사이클당 1개 완료. 동시에 = 파이프라인 안에 반쯤 끝난 일이 항상 많다는 뜻.

예측 → 추측 실행 → flush#

  • 조건 분기의 방향은 execute(여러 단계 깊이)에서야 확정. 그때까지 멈추면 분기마다 라인이 빔 → CPU는 기다리지 않는다.
  • Branch predictor: 분기별 이력을 보고 평소 방향에 베팅 → 그 경로를 speculative execution.
  • 맞음(잘 행동하는 분기면 거의 항상) → 추측 공짜, 분기 확정 시점엔 이미 끝나 있음.
  • 틀림 → 비행 중 추측 명령 전부 쓰레기 → flush + 올바른 타깃에서 refill = Module 1의 bubble, 비용 ≈ 파이프라인 깊이 (~15–20 cycle).
  • 데모 곡선: taken 비율 0%·100%는 완벽히 예측 가능(빠름), 50% 동전 던지기가 최악 (봉우리).

정렬 vs 셔플#

  • if (value > limit) on 정렬 데이터: 한참 false → 나머지 true → 경계 하나 빼고 전부 적중.
  • 셔플 데이터: 동전 던지기 → 약 절반 미스 → 매번 풀 flush.
  • 처방 (Module 1과 동일, 이제 메커니즘 포함): ① 데이터를 정렬/그룹핑해 긴 동일 결과 run 만들기 ② branchless (양쪽 계산 후 점프 없이 선택 → 틀릴 분기가 없음).
  • ✅ 체크포인트: 순서만 다른 두 데이터셋에서 같은 데이터 의존 if, 하나는 빠르고 하나는 느림 → 예측 가능한 순서에선 거의 다 적중, 랜덤 순서에선 절반 미스 + 미스마다 flush. (명령 수 차이·캐시 미스·컴파일러 탓 아님)
  • 🎤 "분기 예측 실패 시 무슨 일?" → 틀린 경로로 추측 실행 중이던 명령 전부 flush, 올바른 타깃에서 refill. 파이프라인 깊이만큼(~15–20 cycle).

5. Prefetching & Streaming Access#

수수께끼: 랜덤 순환 포인터 체이싱 = 매 hop 거의 풀 DRAM 레이턴시(~100 cycle). 같은 횟수·같은 양의 메모리를 순차로 읽으면 수십 배 빠름. 둘 다 DRAM에 사는데? → CPU는 순차 패턴은 볼 수 있고, 랜덤은 못 본다.

HW prefetcher#

  • 전용 유닛이 접근 주소 흐름을 감시, 일정한 stride(라인 N, N+1, N+2…)를 보면 N+3, N+4를 요청 전에 캐시로.
  • 미묘한 점: DRAM 접근은 여전히 일어나고 여전히 ~100 cycle. 다만 백그라운드에서, 앞선 라인 작업과 겹쳐 일어나 파이프라인을 세우지 않음.
  • 순차 접근은 미스를 싸게 만드는 게 아니라 유용한 작업 뒤에 숨긴다. → 캐시보다 훨씬 큰 배열도 연속 스트리밍이면 거의 캐시 속도.

포인터 체이싱이 prefetcher를 무력화하는 이유#

  • node = node->next: 다음 주소가 방금 읽은 데이터 안에 있음 → 현재 로드가 끝나야 존재, 외삽할 stride도 없음.
  • prefetcher 유휴 → 매 hop이 겹칠 것 없는 풀 미스 → DRAM 레이턴시를 직렬로 지불.
  • vector vs list의 가장 깊은 이유: vector 스캔 = 완벽한 unit stride(prefetcher가 앞서감, 미스 사라짐). list = 구조상 포인터 체이싱(prefetcher 맹인, 노드마다 숨길 수 없는 stall). 격차의 대부분이 이 한 가지.

할 수 있는 것#

  • hot 접근을 순차로 — 이 코스의 모든 레이아웃 교훈은 사실 이 유닛에게 먹이 주기였음: 노드 컨테이너 대신 연속 배열, 한 필드만 스캔하면 SoA(필드마다 배열) > AoS, vector를 reserve해서 한 블록 유지.
  • __builtin_prefetch(addr): HW가 못 보는 패턴을 알 때 수동 힌트 (예: 현재 노드 처리 중 node->next->next prefetch). 메스: 틀리거나 타이밍이 나쁜 힌트는 대역폭 낭비 + 필요한 라인 축출 → 측정 후에만.
  • Non-temporal(streaming) store: 곧 다시 읽지 않을 대량 쓰기(큰 출력 버퍼 flush). 일반 쓰기는 라인을 먼저 캐시로 끌어와 곧 버릴 데이터로 캐시 오염 + hot 작업 집합 축출 → streaming store는 캐시를 건너뛰고 메모리로 직행. 역시 특수 도구.
  • 둘 다 존재 이유 = 자동 기계가 잘못 추측할 때 캐시에 뭐가 살지 관리.
  • ✅ 체크포인트: 1GB 배열 순차 스캔이 랜덤 접근보다 몇 배 빠름 (둘 다 원소당 1회) → prefetcher가 stride를 감지해 다음 라인을 미리 로드, DRAM 레이턴시가 작업과 겹침. 랜덤은 패턴이 없어 매번 풀 미스. (Big-O·분기 예측 탓 아님)

6. SIMD & Vectorization#

핵심: 데이터를 싸게 코어까지 가져오는 모든 노력이 여기서 소비된다. 한 명령이 여러 값을 한 번에 처리.

  • 스칼라 명령: 입력 1–2개 → 출력 1개.
  • 벡터 레지스터는 넓다: 128-bit = float 4개, 256-bit = 8개, 512-bit = 16개. SIMD(single instruction, multiple data) 명령 하나가 모든 슬롯(lane)에 같은 연산.
ISA폭float lane
SSE128-bit4
AVX/AVX2256-bit8
AVX-512512-bit16

컴파일러가 해준다 (auto-vectorization)#

  • -O2/-O3에서 연속 배열에 같은 연산을 적용하는 루프를 인식 → 레지스터 폭만큼씩 처리하도록 재작성 + 남는 원소용 스칼라 꼬리.
  • for (i) out[i] = a[i] * scale + b[i]; → 벡터 multiply-add 몇 개. intrinsic 한 줄도 안 씀.
  • 단, 여러 iteration을 동시에 돌려도 안전하다고 증명할 수 있을 때만.

벡터화의 세 조건 (각각 앞 레슨의 재등장)#

  1. 연속 데이터 — 벡터 로드는 인접 원소를 한두 캐시 라인에서 lane으로. list나 포인터 vector면 로드할 인접 원소가 없음. (첫 레슨의 locality)
  2. 독립 iteration — 8개를 동시에 돌리려면 8번째가 7번째 결과에 의존하면 안 됨. loop-carried dependency (acc = acc * 2 + a[i]) → lane 5가 lane 4를 기다림 → 원소 하나씩으로 후퇴.
  3. 단순한 제어 흐름 — 직선 본문은 깔끔히 벡터화. 원소별 데이터 의존 분기는 lane마다 다른 일을 해야 해서 복잡화/차단. (분기 레슨의 반대편: 예측 불가 분기는 미스 비용뿐 아니라 벡터화 자체를 앗아갈 수 있음)
  • 하나라도 어기면 조용히 스칼라로 폴백 — 놓친 속도를 볼 일도 없음. → 벡터화됐는지 확인 (예: -fopt-info-vec / -Rpass=loop-vectorize, 어셈블리 확인).

언제 쓰나#

  • 면접 무브는 AVX 손코딩이 아니라: hot loop가 data-parallel한지 알아보고(예: 배치 MarketUpdate의 price 스케일/합산) 컴파일러가 벡터화하기 쉽게 만들기 — 연속 저장(스캔 필드별 SoA), 내부 루프에 carried dependency·원소별 분기 없음, 최적화 켜기.
  • 손 SIMD/라이브러리는 마지막 2배가 필요한 전문 도구지 기본값 아님.
  • ✅ 체크포인트: 벡터화 가능한 루프 → for (i) c[i] = a[i] + b[i]; (연속 float, 독립 iteration). ✗ x = x * a[i] + b[i] (carried dependency), ✗ sum += nodes[i]->value (흩어진 노드).
  • 🎤 "SIMD가 나머지 성능과 어떻게 연결되나?" → 보상이다. 연속·독립·직선 코드가 캐시·prefetcher·파이프라인을 행복하게 하고, 그 조건이 곧 컴파일러가 넓게 갈 조건.
